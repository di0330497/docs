1EventBridge의 위치와 기본 흐름01-01

이벤트 주도 아키텍처와 EventBridge의 역할

애플리케이션들이 이벤트(상태 변화 알림)를 주고받아 연결되는 이벤트 주도 아키텍처에서, EventBridge는 그 이벤트를 받아 필요한 대상에 전달하는 AWS의 서버리스 이벤트 버스 서비스다.

#1문제 상황

기존에는 애플리케이션끼리 서로를 직접 호출하는 방식으로 연동했다. A가 B의 주소와 형식을 알고 직접 요청을 보내는 동기 호출이 대표적이고, 대상이 여러 개면 호출 코드가 그 수만큼 늘어난다. 이 방식은 받는 쪽이 변경되거나 장애로 응답하지 않으면 보내는 쪽도 함께 멈추고, 연결이 늘어날수록 어느 쪽이 어디에 붙어 있는지 관리하기 어려워진다. 또한 특정 사건에 반응해야 하는 시스템이 여러 개일 때, 각각을 일일이 호출하는 구조는 사건이 생길 때마다 호출이 중복·누락되기 쉬운 한계를 가진다.

#2핵심 질문

무언가가 일어났다는 사실을, 서로를 전혀 모르는 여러 시스템에 한 번의 전달로 알릴 방법은 없을까?

#3동작 예시

S3 버킷에 파일이 하나 올라오면, 그 사건을 이벤트로 만들어 EventBridge가 중앙에서 받고, 미리 등록된 규칙이 이를 감지해 Lambda 함수를 실행하고 별도로 감사 로그를 저장하는 전송까지 해낸다. 핵심은 파일을 올린 쪽이 누가 그 사실을 받아 처리하는지 전혀 모른다는 점이다. 사건의 사실만 버스에 던지면, 그 사실을 구독한 쪽들이 각자 반응한다.

#4동작 과정

  1. 이벤트 발생·게시S3 같은 소스에서 상태 변화가 생기면, 그 사실을 담은 이벤트가 EventBridge 버스에 올라온다.
  2. 규칙의 조건 매칭규칙이 이벤트 내용을 자신의 패턴과 비교해, 이 사건이 자신이 처리할 사건인지 판단한다.
  3. 타깃으로 전달조건에 맞는 규칙에 연결된 타깃(Lambda, SQS 등)에게 이벤트가 전달되어 각자 처리를 시작한다.

#1문제 상황

#3동작 예시

#2핵심 질문

Custom Event Bus는 AWS 계정이 이벤트를 받아 구독자에게 전달하는 신형 이벤트 버스로, 이름·엔드포인트·권한과 함께 생성된다.

#1문제 상황

AWS 계정에서 이벤트를 주고받는 기본 창구는 계정마다 하나씩 자동으로 생기는 기본 이벤트 버스(default event bus)였다. 모든 AWS 서비스가 발생시키는 이벤트는 이 버스 하나로 모였고, 규칙(rule)이 그 이벤트를 골라 타깃(target)으로 보냈다. 그런데 이 기본 버스에는 명확한 한계가 있었다. 버스가 하나뿐이라 팀별·서비스별로 이벤트 흐름을 분리할 수 없었고, 자체 애플리케이션이 만든 이벤트를 담을 전용 공간도 마땅치 않았다. 그래서 발생한 이벤트와 소비하는 쪽이 뒤섞여, 어느 이벤트가 어느 용도의 것인지 구분하고 통제하기 어려웠다.

#2핵심 질문

팀이나 용도별로 이벤트 흐름을 분리해, 자신이 만든 이벤트를 원하는 만큼 만들어 담을 수 있는 전용 버스는 어떻게 만들까?

#3동작 예시

Custom Event Bus는 사용자가 이름을 정해 따로 만드는 이벤트 버스다. 예를 들어 orders라는 이름의 커스텀 버스를 하나 만들면, 주문 관련 이벤트는 전부 이 버스로 발행하고 여기에만 구독 규칙을 달아 처리한다. 기본 버스와 완전히 분리된 공간이 생기는 셈이라, 주문팀은 자기 버스 안에서 이벤트를 마음대로 발행하고 원하는 대상에 연결할 수 있다.

#4동작 과정

  1. 이름 정하기버스 이름을 지정한다. 이름은 계정과 리전 안에서 고유해야 하며, 최대 256자의 영문·숫자·마침표·하이픈·언더스코어 조합으로 짓는다.
  2. 버스 생성콘솔이나 API로 이름을 지정해 버스를 만든다. 생성되면 그 계정·리전에 전용 이벤트 버스가 생기고, 해당 버스를 가리키는 ARN(리소스 주소)이 부여된다.
  3. 발행·구독 준비만들어진 버스에 이벤트를 발행하고, 규칙과 타깃을 연결해 이벤트를 받을 준비를 한다.

#5한 줄 요약

사용자가 이름을 정해 전용 이벤트 버스를 만들어, 기본 버스와 분리된 공간에서 이벤트를 발행하고 구독할 수 있게 하는 것

3단계 Custom Event Bus (신형 버스)

다른 AWS 계정이 내 Custom Event Bus에 이벤트를 보내거나 구독할 수 있게 버스 공유 정책을 설정하는 기능.

#1문제 상황

커스텀 버스는 원래 그 버스를 만든 계정에서만 쓸 수 있었다. 이벤트를 발행하는 애플리케이션과 그 이벤트를 소비하는 애플리케이션이 서로 다른 AWS 계정에 있는 경우, 발행 계정은 자기 버스에 이벤트를 넣어도 소비 계정의 버스로는 보낼 수 없었다. 그래서 계정 경계를 넘어 이벤트를 전달하려면 소비 계정 쪽에서 별도로 이벤트를 가져오는 구조를 직접 만들어야 했고, 계정이 많아질수록 이 연결 작업이 반복되고 관리가 어려웠다.

#2핵심 질문

다른 계정의 애플리케이션도 내 커스텀 버스에 이벤트를 보내거나, 내 버스의 이벤트를 다른 계정으로 전달하려면 어떻게 허용할까?

#3동작 예시

버스에 리소스 기반 정책(resource-based policy)을 붙여 다른 계정의 접근을 허용한다. 예를 들어 내 계정의 orders 버스에 "계정 B의 이벤트도 이 버스로 발행할 수 있다"는 정책과 "이 버스의 이벤트를 계정 B의 버스로 전달할 수 있다"는 정책을 함께 걸면, 계정 B는 자기 쪽에서 별도 장치 없이도 내 버스에 이벤트를 보내고 내 버스의 이벤트를 받아갈 수 있다.

#4동작 과정

  1. 정책 작성버스 ARN을 대상으로 지정하고, 다른 계정(Principal)에 PutEvents(이벤트 발행)나 타깃 전달 권한을 허용하는 정책을 만든다. 계정 전체나 특정 계정만 지정할 수 있다.
  2. 정책 연결작성한 정책을 콘솔의 버스 권한 화면이나 API로 버스에 연결한다. 이 시점부터 허용된 계정이 버스를 사용할 수 있다.
  3. 상대 계정에서 사용허용받은 계정은 자신의 애플리케이션에서 상대 버스 ARN을 지정해 이벤트를 발행하거나, 그 버스를 타깃으로 지정해 이벤트를 받아간다.

#5한 줄 요약

버스에 리소스 기반 정책을 걸어 다른 계정의 이벤트 발행과 수신을 허용함으로써 커스텀 버스를 계정 간에 공유하는 것

3단계 Custom Event Bus (신형 버스)

PutEvents API로 이벤트를 버스에 발행할 때의 페이로드 형식(콘텐츠 유형·이벤트 구조)과 이벤트 소스 지정 규칙.

#1문제 상황

이벤트를 버스에 넣을 때 아무 형식이나 담아 보내면 받는 쪽에서 해석하기 어렵다. 기존 방식은 각 애플리케이션이 자기 입맛대로 이벤트를 구성해 보내다 보니, 이벤트 안에 어떤 필드가 있고 그 값이 무엇을 뜻하는지가 발행자마다 제각각이었다. 이벤트를 받는 규칙은 이런 제각각인 구조를 일일이 맞춰 작성해야 했고, 새 발행자가 생길 때마다 그 형식을 다시 파악해야 했다.

#2핵심 질문

여러 발행자가 보내는 이벤트를 규칙이 일관되게 해석하려면 이벤트 페이로드를 어떤 공통 형식으로 정해야 할까?

#3동작 예시

EventBridge는 모든 이벤트를 JSON 객체 하나로 표현하고, 그 안에 공통 필드를 갖춘 구조를 요구한다. 예를 들어 주문 완료 이벤트는 "source": "myapp.orders", "detail-type": "Order Completed", "detail": {"orderId": "123", "amount": 5000} 같은 형태가 된다. source가 어디서 왔는지, detail-type이 어떤 사건인지, detail이 실제 내용인지를 규칙이 일관되게 읽을 수 있다.

#4동작 과정

  1. 공통 필드 채우기발행하는 이벤트에 source(발행 원천 식별자), detail-type(사건 종류), detail(실제 데이터 JSON) 등을 포함한다. detail의 본문은 항상 JSON 객체여야 한다.
  2. PutEvents로 발행PutEvents(이벤트 발행) API가 이벤트들을 받아 지정한 버스로 넣는다. 한 번 호출에 여러 이벤트를 묶어 보낼 수 있다.
  3. 버스 수신과 규칙 매칭발행된 이벤트가 버스에 도착하면, 규칙이 source·detail-type·detail의 값 패턴으로 이 이벤트를 매칭해 타깃으로 전달한다.

#5한 줄 요약

이벤트를 source·detail-type·detail로 구성된 JSON 페이로드로 발행하고, 규칙이 이 공통 형식의 값을 기준으로 이벤트를 매칭·전달하는 것

3단계 Custom Event Bus (신형 버스)

구독자가 이벤트 패턴과 타깃을 지정해 Custom Event Bus의 이벤트를 받아 연결하는 단계.

#1문제 상황

이벤트를 버스에 발행하는 것만으로는 아무 일도 일어나지 않는다. 이벤트가 버스에 들어와도, 그 이벤트를 받아 처리할 대상이 연결되어 있지 않으면 그대로 버려진다. 기존 방식은 이벤트를 보내는 쪽만 만들고 받는 쪽 연결을 잊어버려서, 이벤트가 발생했는데도 아무 반응이 없는 상태로 방치되는 일이 흔했다. 또 받는 대상을 버스 뒤에 미리 연결해두지 않으면 이벤트가 지나갈 길이 없었다.

#2핵심 질문

버스로 들어온 이벤트 중 원하는 것만 골라 특정 대상을 호출하려면 발행과 받는 사이에 무엇을 연결해야 할까?

#3동작 예시

버스와 타깃 사이에 구독(subscription) 역할을 하는 규칙(rule)을 만든다. 예를 들어 orders 버스에 "detail-type이 Order Completed인 이벤트만 주문 처리 Lambda 함수로 보낸다"는 규칙을 연결하면, 해당 이벤트가 버스에 들어올 때 규칙이 그 이벤트를 골라 Lambda 함수를 호출한다. 규칙이 곧 구독이며, 규칙 하나가 이벤트 패턴과 타깃을 묶는다.

#4동작 과정

  1. 규칙 만들기이름과 함께 이벤트 패턴(어떤 이벤트를 고를지)을 지정해 규칙을 만든다. 버스 하나에 여러 규칙을 둘 수 있다.
  2. 타깃 연결만든 규칙에 타깃(이벤트를 받아 처리할 AWS 리소스)을 하나 이상 지정한다. 규칙에 타깃이 연결되면 구독이 완성된다.
  3. 이벤트 매칭·전달버스에 이벤트가 들어오면 각 규칙이 패턴으로 이벤트를 판별하고, 매칭된 규칙이 이벤트를 자기 타깃으로 전달해 처리한다.

#5한 줄 요약

이벤트 패턴을 가진 규칙을 버스와 타깃 사이에 연결해, 조건에 맞는 이벤트만 골라 특정 대상에 전달하는 구독 구조를 만드는 것

#3동작 예시

#4동작 과정

  1. 타깃 선택규칙의 타깃 추가 화면에서 받을 서비스 종류를 고른다. SQS 큐, Lambda 함수, SNS 주제, Kinesis 스트림, Firehose 스트림, Step Functions 상태 머신, HTTP 엔드포인트, 그리고 이벤트 버스를 지정할 수 있다.
  2. 타깃 설정·권한 부여선택한 대상의 ARN(리소스 주소)을 지정하고, 규칙이 그 대상에 이벤트를 넣을 수 있도록 실행 역할(권한)을 연결한다.
  3. 전달과 처리매칭된 이벤트가 규칙에서 선택된 타깃으로 전달되고, 대상은 이벤트를 큐에 쌓거나 함수를 실행하는 식으로 처리한다.

이벤트 패턴을 이용해 버스에 도착한 이벤트 중 조건에 맞는 것만 타깃으로 전달되도록 걸러내는 기능.

#1문제 상황

규칙이 모든 이벤트를 그대로 받아 타깃으로 보낸다면, 타깃은 자신이 처리할 필요 없는 이벤트까지 모두 받게 된다. 기존 방식은 버스에 들어오는 이벤트를 종류와 상관없이 전부 타깃으로 넘겼기 때문에, 타깃 쪽에서 불필요한 호출로 비용이 나가고, 정작 필요한 이벤트와 섞여 처리 로직이 복잡해졌다. 예를 들어 Lambda 함수 하나가 수십 종류의 이벤트를 받아 매번 if 분기로 골라내야 하는 상황이 벌어졌다.

#2핵심 질문

버스로 들어오는 모든 이벤트가 아니라 원하는 조건의 이벤트만 타깃에 전달하려면 어떻게 걸러낼까?

#3동작 예시

규칙의 이벤트 패턴(event pattern)에 필터 조건을 적어 이벤트를 거른다. 예를 들어 detail-type이 Order Completed이고 detail.amount가 10000 이상인 경우만 보내고 싶다면, 패턴에 {"detail-type": ["Order Completed"], "detail": {"amount": [{"numeric": [">=", 10000]}]}}을 적는다. 이 규칙에 매칭되는 이벤트만 타깃으로 전달되고 나머지는 버려진다.

#4동작 과정

  1. 패턴 작성규칙의 이벤트 패턴에 source, detail-type, detail의 특정 필드 값을 조건으로 적는다. 정확한 값 일치, 숫자 범위, 존재 여부 등 여러 형태의 조건을 쓸 수 있다.
  2. 매칭 판정버스에 이벤트가 들어오면 규칙이 패턴의 각 조건과 이벤트의 필드 값을 대조해 매칭 여부를 판정한다.
  3. 선별 전달매칭된 이벤트만 타깃으로 보내고, 매칭되지 않은 이벤트는 그 규칙에서는 무시되어 다른 규칙이 있으면 그쪽 판정으로 넘어간다.

#5한 줄 요약

규칙의 이벤트 패턴에 필드 값 조건을 적어, 원하는 이벤트만 선별해 타깃에 전달하는 것

입력 변환과 배치

타깃에 전달할 이벤트 페이로드를 변환하거나(input transformation) 여러 이벤트를 묶어(batch) 보내는 기능.

#1문제 상황

기존 방식에서는 발행된 이벤트가 구독자(타깃)에게 그대로 전달됩니다. 이벤트에 불필요한 필드가 많아도, 구독자가 원하는 형태와 달라도 EventBridge는 이벤트를 있는 그대로 보냈습니다. 그래서 구독자 측의 Lambda 함수나 API가 매번 "필요 없는 필드를 걸러 내고, 이름을 바꾸고, 형식을 고치는" 변환 코드를 직접 작성해야 했고, 이벤트가 하나씩 도착할 때마다 변환과 호출이 반복되어 많은 이벤트를 처리할 때 비용과 지연이 커지는 문제가 있었습니다.

#2핵심 질문

구독자에게 이벤트를 보내기 전에 이벤트 내용을 원하는 형태로 바꾸고, 여러 건을 묶어서 한 번에 전달할 수는 없을까?

#3동작 예시

주문 이벤트에 user_id, order_total, internal_note 같은 필드가 있을 때, 구독자인 알림 Lambda는 order_total만 필요합니다. EventBridge의 입력 변환(input transformation)을 규칙에 설정해 두면, 발행된 원본 이벤트를 받는 즉시 내부적으로 { "amount": 1234 } 형태로 다시 조립한 뒤 Lambda에 전달합니다. Lambda 쪽에는 변환 코드가 하나도 필요 없고, 원하는 필드만 담긴 깨끗한 이벤트가 도착합니다. 반대로 배치(batching)를 켜면 도착한 주문 이벤트 10건이 개별 호출되지 않고 하나의 묶음으로 모여 SQS 큐에 한 번에 전달됩니다.

#4동작 과정

  1. 입력 변환 적용규칙에 입력 변환기를 등록하면, 매칭된 이벤트가 타깃으로 나가기 전에 원본 JSON에서 필요한 필드만 뽑아 새 JSON으로 다시 조립된다.
  2. 배치 묶기배치 설정을 켜면 일정 시간 또는 일정 건수만큼 이벤트를 모아 하나의 페이로드로 만든다. SQS, Kinesis, Firehose 등 배치를 지원하는 타깃이 대상이다.
  3. 타깃 전달변환되고 묶인 결과가 타깃에 도착한다. Lambda는 호출 횟수가 줄고, SQS는 메시지 수가 줄어 처리 비용과 지연이 줄어든다.

#5한 줄 요약

발행된 이벤트를 구독자에게 보내기 직전에 원하는 형태로 다시 조립하고 여러 건을 묶어 전달함으로써 구독자 쪽 변환 코드와 호출 비용을 없애는 것

재시도·데드레터 큐·구독 갱신

타깃 전달 실패 시 재시도 정책과 데드레터 큐로 보내는 처리, 그리고 구독 설정을 갱신하는 방법.

#1문제 상황

기존 방식에서는 규칙이 타깃에 이벤트를 보냈을 때 타깃이 일시적으로 다운되어 있거나 처리에 실패하면, 그 이벤트는 그대로 유실되었습니다. 재시도 정책이 없어서 한 번 실패하면 끝이었고, 실패한 이벤트가 어디에 쌓이는지도 확인할 수 없었습니다. 또 구독자(규칙)를 만들 때 버스 이름이나 이벤트 소스(event source, 이벤트를 보낸 출처)를 잘못 적으면 규칙이 아무 이벤트도 받지 못하는데, 그 사실을 알아채기도 어려웠습니다. 이벤트를 보내는 쪽과 받는 쪽이 서로 다른 팀이 운영하는 경우가 많아 이 문제는 더 잦았습니다.

#2핵심 질문

타깃이 잠시 실패해도 이벤트를 버리지 않고 다시 시도하며, 실패한 이벤트를 따로 보관하고, 변경된 구독 정보를 안전하게 반영할 수는 없을까?

#3동작 예시

주문 이벤트가 규칙과 매칭되어 Lambda를 호출했는데 Lambda가 순간적으로 오류를 반환했다고 합시다. EventBridge는 기본적으로 이 이벤트를 최대 185회까지, 간격을 늘려 가며(처음에는 짧게, 나중에는 길게) 다시 호출합니다. 그런데도 실패하면 이 이벤트를 데드레터 큐(dead-letter queue, 실패한 이벤트를 쌓아 두는 전용 큐)에 넣습니다. 나중에 이 큐를 조회하면 "어떤 이벤트가 왜 실패했는지"를 확인해 직접 처리할 수 있습니다.

#4동작 과정

  1. 재시도 실행타깃 전달이 실패하면 규칙에 설정된 재시도 정책(최대 시도 횟수와 시간 간격)에 따라 이벤트를 다시 보낸다. 시간이 지날수록 재시도 간격이 길어져 타깃이 복구될 시간을 준다.
  2. 데드레터 큐 보관재시도를 모두 소진해도 실패하면 이벤트를 데드레터 큐(DLQ)로 보낸다. 여기에 쌓인 이벤트는 유실되지 않으므로 나중에 원인을 조사해 다시 처리할 수 있다.
  3. 구독 갱신구독자 정보(버스 이름, 이벤트 소스, 규칙)를 변경할 때는 기존 구독을 갱신하는 API를 호출한다. 이때 신형 버스는 버스 이름과 이벤트 소스가 바뀌어도 기존 구독의 연결을 이어 받아 이벤트 흐름이 끊기지 않게 한다.

#5한 줄 요약

실패한 이벤트를 포기하지 않고 정책에 따라 재시도하고, 끝내 실패한 것은 데드레터 큐에 보관하며, 구독자 변경 시에도 이벤트 흐름을 끊지 않게 하는 전달 신뢰성 보장

순서 보장과 중복 제거

이벤트 전달 순서 보장(ordering)과 중복 이벤트 제거(deduplication)가 동작하는 방식.

#1문제 상황

기존 이벤트 버스에서는 이벤트가 도착한 순서와 무관하게 타깃에 전달될 수 있었고, 같은 이벤트가 두 번 전달되는 일도 있었습니다. 예를 들어 주문 취소 이벤트가 주문 생성 이벤트보다 먼저 도착하면 구독자인 재고 시스템이 "취소"를 먼저 보고 "생성"을 나중에 봐서 잘못된 재고 상태를 만들 수 있었습니다. 또 발행자가 같은 요청을 두 번 보내면 구독자가 같은 작업을 두 번 수행하는 중복 처리 문제가 발생했습니다. 순서가 중요한 금융 거래나 재고 관리에서는 이 두 문제가 곧바로 장애로 이어졌습니다.

#2핵심 질문

이벤트가 보내진 순서대로 타깃에 도착하게 하고, 같은 이벤트가 중복 전달되지 않게 하려면 어떻게 해야 할까?

#3동작 예시

같은 주문 건에 대해 "생성" 이벤트와 "취소" 이벤트가 차례로 발행된다고 합시다. 발행자는 두 이벤트에 같은 메시지 그룹 ID(message group ID, 순서를 묶는 단위)를 붙입니다. 신형 버스는 이 그룹 안에서는 이벤트를 보낸 순서 그대로 타깃에 전달하므로, 재고 시스템은 항상 "생성"을 먼저 받고 "취소"를 나중에 받습니다. 여기에 발행자가 이벤트마다 중복 제거 ID(deduplication ID, 같은 요청임을 구별하는 식별자)를 붙이면, 5분 안에 같은 ID를 가진 이벤트가 다시 들어와도 버스가 그것을 중복으로 판단해 한 번만 전달합니다.

#4동작 과정

  1. 그룹 지정발행자가 이벤트에 메시지 그룹 ID를 붙여 보낸다. 같은 그룹 ID를 가진 이벤트들만 서로 순서가 보장된다.
  2. 순서 유지 전달버스가 그룹 내 이벤트를 받은 순서대로 타깃에 전달한다. 그룹이 다르면 순서는 보장되지 않지만 서로 독립적으로 처리되어 전체 처리 속도는 유지된다.
  3. 중복 제거중복 제거 ID가 같은 이벤트가 5분 안에 다시 도착하면 버스가 두 번째 이벤트를 버리고 첫 번째 것만 전달한다. 발행자가 재시도로 같은 이벤트를 다시 보내도 구독자에게는 한 번만 도착한다.

#5한 줄 요약

메시지 그룹 ID로 순서를 묶어 보낸 순서대로 전달하고, 중복 제거 ID로 같은 이벤트의 재전달을 막아 구독자가 항상 올바른 순서와 한 번의 처리를 보장받게 하는 것

3Custom Event Bus (신형 버스)03-10

이벤트 리플레이

과거에 버스로 전달된 이벤트를 다시 재생(replay)해 구독자에게 재전송하는 기능.

#1문제 상황

기존 방식에서는 버스를 지나간 이벤트가 저장되지 않았습니다. 구독자의 버그로 특정 시간대의 이벤트 처리가 실패했거나, 새 구독자를 붙였는데 과거 이벤트가 필요해도 이미 지나간 이벤트를 다시 얻을 방법이 없었습니다. 그래서 장애 복구는 "지금부터 새로 들어오는 이벤트만 받자"로 끝나는 경우가 많았고, 유실된 기간의 데이터는 다른 시스템에서 수작업으로 복원해야 했습니다.

#2핵심 질문

이미 버스를 지나간 이벤트를 저장해 두었다가, 나중에 필요할 때 같은 흐름으로 다시 보낼 수는 없을까?

#3동작 예시

주문 처리 Lambda가 어제 오후 2시부터 3시 사이에 버그로 모든 이벤트 처리를 실패했다고 합시다. 그 시간대의 이벤트가 미리 아카이브(archive, 이벤트를 저장해 두는 저장소)에 보관되어 있었다면, 운영자는 "어제 14:00~15:00, 주문 버스"를 지정해 리플레이(replay, 저장된 이벤트를 다시 보내는 작업)를 실행합니다. 버스는 저장된 그 시간대의 이벤트를 다시 꺼내 규칙과 타깃에 그대로 보내므로, Lambda가 버그 수정 후 같은 이벤트를 다시 받아 제대로 처리할 수 있습니다.

#4동작 과정

  1. 아카이브 생성버스에 대해 아카이브를 만들고 보관할 이벤트 조건과 보관 기간(최대 1년)을 정한다. 조건에 맞는 이벤트가 버스를 지나갈 때마다 복사본이 아카이브에 쌓인다.
  2. 리플레이 시작리플레이 API로 어떤 버스의 어떤 시간 범위 이벤트를 다시 보낼지 지정한다. 리플레이 중에도 새 이벤트의 정상 흐름은 계속 유지된다.

Classic 이벤트 버스(default 버스와 Custom 버스)는 AWS 계정에 기본으로 존재하는 이벤트 버스로, 클라우드의 서비스 변경 이벤트(예: EC2 인스턴스 상태 변경)를 AWS 서비스들이 자동으로 보내 주는 통로 역할을 합니다.

  3. 이벤트 전달조건에 맞는 이벤트가 버스에 도착하면 규칙이 자동으로 타깃에 전달한다. 발행자와 구독자는 서로를 알 필요가 없어 한쪽이 바뀌어도 다른 쪽은 그대로다.

#1문제 상황

기본적으로 이벤트 버스는 같은 AWS 계정 안에서만 이벤트를 주고받습니다. 다른 계정이나 다른 리전에서 보낸 이벤트는 별도 설정 없이는 받아지지 않고, 내 버스가 다른 계정·리전으로 이벤트를 보내는 것도 허용되지 않습니다. 이 권한 문제를 콘솔의 단순 설정만으로는 어떤 계정의 어떤 이벤트를 받을지 세밀하게 정할 수 없어서, 허용 범위를 잘못 정하면 원치 않는 계정의 이벤트가 들어오거나 반대로 필요한 이벤트가 전달되지 않습니다.

#2핵심 질문

다른 계정이나 다른 리전에서 온 이벤트를 내 버스가 받도록, 그리고 내 버스가 다른 계정·리전으로 보내도록 안전하게 허용하려면?

#3동작 예시

계정 A의 버스가 계정 B의 버스로 이벤트를 보내게 하려면, 받는 쪽인 계정 B 버스에 리소스 기반 정책(resource-based policy)을 붙입니다. 정책 안에는 "계정 A의 특정 규칙이 보내는 이벤트를 받겠다"는 문장을 적고, 필요하면 어느 리전에서 오는 이벤트인지 조건도 추가합니다. 이 정책이 버스라는 자원에 붙어서 들어오는 이벤트의 발신자와 조건을 검사하고, 조건에 맞는 이벤트만 버스가 받습니다.

#4동작 과정

  1. 정책 작성받는 쪽 버스에 리소스 기반 정책을 추가해, 허용할 보내는 계정·규칙·리전을 조건으로 적은 허용 문장을 만듭니다. 같은 계정 안의 전송은 정책 없이 기본적으로 허용됩니다.
  2. 정책 적용정책을 버스에 붙이면, 그 버스로 들어오는 이벤트마다 발신 계정과 조건이 정책과 대조됩니다. 조건과 일치하는 이벤트만 버스에 들어와 규칙이 처리합니다.
  3. 전송 검증보내는 쪽에서 이벤트를 넣으면 버스가 정책 조건(계정·리전·규칙)과 대조해 허용되면 받고, 허용되지 않으면 거부합니다. 이를 통해 계정·리전을 넘는 전송만 조건부로 열 수 있습니다.

규칙의 개념과 생성

규칙(Rule)은 이벤트 패턴이나 일정과 일치하는 이벤트를 필터링해 지정된 대상(target)으로 전달하는 EventBridge의 핵심 구성 요소로, 이벤트 버스에 규칙을 만들어 생성한다.

#1문제 상황

버스에 들어오는 이벤트는 다양하고 많습니다. 그런데 실제로 처리해야 하는 것은 그중 일부입니다. 예를 들어 EC2 인스턴스가 종료된 상태에만 반응하면 되는 작업이 있는데, 버스만 있고 선택 기준이 없으면 모든 이벤트를 다 받아서 필요한 것만 골라내는 일을 애플리케이션 쪽에서 매번 해야 합니다. 관계없는 이벤트까지 전달되면 대상이 불필요한 호출을 받고, 필터 로직을 각 대상마다 따로 만들어야 해서 관리가 어렵습니다.

#2핵심 질문

버스에 들어오는 많은 이벤트 중 필요한 것만 골라 정해진 대상으로 보내려면?

#3동작 예시

EC2 인스턴스가 terminated 상태가 된 이벤트만 받고 싶을 때, 규칙에 이벤트 패턴(event pattern)을 적습니다. 예를 들어 source가 aws.ec2이고 detail-type이 EC2 Instance State-change Notification이며 detail.state가 terminated인 조건을 지정하면, 버스는 들어오는 이벤트마다 이 조건을 검사해 일치하는 경우에만 그 규칙이 이벤트를 대상(Lambda, SQS 등)으로 전달합니다. Enhanced Builder는 패턴을 화면에서 시각적으로 만들어 주고, Advanced Builder는 JSON 패턴을 직접 작성하게 해 줍니다.

#4동작 과정

  1. 조건 정의규칙에 일치시킬 이벤트 패턴을 지정합니다. 패턴은 source, detail-type, detail 필드의 값 조건으로 구성되며, 일정 기반으로 실행할 규칙도 만들 수 있습니다.
  2. 대상 지정일치한 이벤트를 보낼 대상(Lambda, SQS, SNS, 다른 이벤트 버스 등)을 규칙에 연결하고, 대상 호출에 필요한 IAM 역할을 지정합니다.
  3. 규칙 생성·처리 시작규칙을 버스에 만들면 이후 버스에 들어오는 이벤트마다 패턴을 검사해, 일치하는 이벤트만 해당 대상으로 전달합니다.

#1문제 상황

기존에 주기적인 작업을 실행하려면 서버(EC2 인스턴스)에 크론잡(cron job, 정해진 시각에 명령을 실행하는 예약 작업)을 직접 설치하고, 그 서버를 계속 켜두고 관리해야 했습니다. 서버가 꺼져 있으면 작업이 실행되지 않고, 서버 자체의 OS 업데이트나 장애까지 직접 챙겨야 하는 운영 부담이 있었습니다. 또 크론잡이 실패했는지도 별도로 감시해야 했습니다. 이벤트도 아닌데 매번 서버가 떠 있어야 한다는 점이 명확한 한계였습니다.

#2핵심 질문

서버를 직접 관리하지 않고도 정해진 시간마다 안정적으로 AWS 작업을 실행하려면 어떻게 해야 할까요?

#3동작 예시

매일 09:00에 데이터 백업을 실행하는 규칙을 만든다고 가정합니다. 규칙에 cron 표현식 0 9 * * ? *(매일 09시 00분을 뜻하는 일정 표현식)를 적어 두면, EventBridge가 그 시각이 되면 스스로 이벤트를 생성하여 백업 대상(예: Lambda 함수)으로 전달합니다. 작업을 실행할 서버를 두지 않아도 EventBridge가 시각을 감시하고 트리거를 대신합니다.

#4동작 과정

  1. 규칙 정의규칙에 rate(예: rate(5 minutes), 5분마다) 또는 cron(예: 0 9 * * ? *, 매일 09:00) 표현식과 대상을 지정합니다.
  2. 시각 도달 감지EventBridge가 시계를 기준으로 표현식과 일치하는 시각이 되었는지 판단하고, 그 시각에 자동으로 일정 이벤트를 생성합니다.
  3. 대상 호출생성된 이벤트가 규칙에 정의된 대상(백업용 Lambda 함수 등)으로 전달되어 작업이 실행되고 완료됩니다.

5규칙(Rule)05-04

규칙의 IaC: SAM·CloudFormation

규칙은 AWS SAM 템플릿 또는 AWS CloudFormation 템플릿으로 코드 형태로 정의해 버전 관리와 재사용이 가능한 인프라(IaC)로 관리할 수 있다.

#1문제 상황

기존에는 EventBridge 규칙을 AWS 콘솔에서 클릭으로 하나씩 만들었습니다. 규칙이 몇 개면 괜찮지만, 환경(개발·스테이징·프로덕션)마다 같은 규칙을 반복해서 만들어야 하거나 팀원이 규칙을 추가할 때마다 콘솔에서 같은 설정을 다시 해야 했습니다. 어떤 규칙이 어떤 설정으로 만들어졌는지 기록이 남지 않아, 나중에 규칙이 왜 이렇게 되어 있는지 추적하기 어렵고 실수로 잘못된 설정을 해도 확인할 방법이 없었습니다.

#2핵심 질문

규칙 설정을 코드로 관리해 버전을 남기고 어느 환경에서든 똑같이 재현할 수는 없을까요?

#3동작 예시

AWS SAM 템플릿(서버리스 애플리케이션을 정의하는 YAML 코드)에 규칙 정의를 한 번 작성해 둔다고 가정합니다. 이 템플릿 파일에 규칙의 이름, 이벤트 패턴, 대상을 적어 두면, 배포 명령(deploy) 한 번으로 개발 환경과 프로덕션 환경에 동일한 규칙이 동시에 만들어집니다. 규칙의 변경 이력은 코드 저장소(Git)에 그대로 남습니다.

#4동작 과정

  1. 템플릿 작성SAM 또는 CloudFormation 템플릿(AWS 리소스를 코드로 기술하는 YAML/JSON 파일)에 규칙과 대상을 정의합니다.
  2. 배포 실행템플릿을 AWS에 배포하면 CloudFormation이 템플릿 내용대로 규칙 리소스를 생성하거나 변경합니다.
  3. 환경 재현과 관리같은 템플릿을 다른 환경에 다시 배포해 동일한 규칙을 만들고, 이후 변경은 코드 수정 후 재배포로만 반영합니다.

#5한 줄 요약

규칙 정의를 코드 템플릿으로 선언하고 배포 명령만으로 어느 환경에서나 동일하게 생성·변경하는 인프라 관리 방식

6이벤트 패턴06-01

이벤트 패턴 문법

이벤트 패턴(event pattern)은 도착한 이벤트의 JSON 구조와 필드 값을 비교해 규칙이 그 이벤트에 반응할지 판단하는 조건식이다.

#1문제 상황

기존에는 버스에 들어오는 모든 이벤트를 규칙이 그대로 대상으로 전달했기 때문에, 관심 없는 이벤트까지 모두 처리 대상이 되었습니다. 예를 들어 주문 이벤트만 처리하면 되는데 결제, 배송, 취소 이벤트까지 함께 전달되어 대상(Lambda 등)이 불필요한 호출을 반복하고, 코드 안에서 다시 조건을 나눠 걸러내야 했습니다. 전달량이 늘어나 비용과 지연이 커지는 것이 명확한 한계였습니다.

#2핵심 질문

도착한 이벤트 중에서 내가 원하는 이벤트만 규칙이 골라내게 하려면 조건을 어떻게 적어야 할까요?

#3동작 예시

주문 완료 이벤트만 받는 규칙을 만든다고 가정합니다. 이벤트 패턴에 {"source": ["myapp.orders"], "detail-type": ["OrderPlaced"]}라고 적어 둡니다. 패턴 문법은 이벤트의 source(이벤트를 발생시킨 출처)와 detail-type(이벤트 종류) 필드 값이 지정한 값과 정확히 일치하는 이벤트만 통과시키는 조건식입니다.

#4동작 과정

  1. 패턴 작성JSON 객체 형태로 일치시키려는 필드 이름과 그 값을 배열로 적어 규칙에 붙입니다.
  2. 이벤트 비교이벤트가 버스에 도착하면 규칙이 패턴의 각 필드와 이벤트의 실제 필드 값을 하나씩 비교합니다.
  3. 일치 판정과 전달모든 조건이 일치하면 대상으로 전달하고, 하나라도 어긋나면 그 이벤트는 버려집니다.

#5한 줄 요약

JSON 객체로 적은 필드 조건에 이벤트가 모두 일치할 때만 규칙이 반응하게 하는 필터 조건식

6이벤트 패턴06-02

필드 값 매칭: 데이터 타입과 null

문자열·숫자·불리언 등 이벤트 필드의 데이터 타입에 맞춰 값을 비교하고, null과 빈 문자열 같은 특수 값을 별도 규칙으로 처리하는 매칭 방식이다.

#1문제 상황

기존에는 패턴에서 필드 값을 문자열로만 비교했습니다. 그런데 이벤트의 필드는 숫자(예: price: 1200), 불리언(예: isPaid: true), 문자열(예: status: "ok") 등 여러 데이터 타입으로 도착합니다. 타입을 고려하지 않고 값을 비교하면 숫자 1200과 문자열 "1200"이 서로 달라 매칭되지 않거나, 값이 아예 없는 필드(null)가 있어 어떤 조건에도 걸리지 않아 원하는 이벤트를 놓치는 문제가 있었습니다.

#2핵심 질문

문자열·숫자·불리언처럼 타입이 다른 값과, 값이 없는 null 필드까지 정확히 매칭하려면 어떻게 해야 할까요?

#3동작 예시

가격이 1200원 이상인 결제 이벤트만 받는 규칙을 만든다고 가정합니다. 패턴에 {"detail": {"price": [{"numeric": [">=", 1200]}]}}라고 적으면, price 필드의 숫자 값 1200, 1500은 매칭되고 문자열 "1200"은 매칭되지 않습니다. 같은 방식으로 null은 [null]로 적어 값이 없는 필드만 따로 매칭할 수 있습니다.

#4동작 과정

  1. 타입 확인비교할 필드가 문자열인지 숫자인지 불리언인지, 값이 있는지(null이 아닌지)를 먼저 확인합니다.
  2. 타입별 비교 작성문자열은 값 그대로, 숫자는 numeric 비교식(예: >= 1200), 불리언은 true/false, 값 없음은 null을 패턴에 적습니다.
  3. 매칭 판정이벤트 필드의 실제 타입과 값이 패턴 조건에 맞을 때만 규칙이 이벤트를 대상으로 전달합니다.

#5한 줄 요약

문자열·숫자·불리언·null 각 타입에 맞는 비교 방식을 패턴에 명시해 값과 값 없음을 정확히 필터링하는 것

6이벤트 패턴06-03

배열·복수 값·비교 연산자

배열 안의 여러 값, 여러 값 중 하나의 일치, 그리고 크기 비교 연산자(>, >=, <, <=)와 와일드카드를 활용해 한 패턴에서 다양한 조건을 표현하는 방법이다.

#1문제 상황

기존 패턴은 필드 값 하나와 정확히 일치하는 경우만 매칭했습니다. 그래서 필드가 배열(항목이 여럿인 값, 예: items: ["a", "b"])인 이벤트나, 여러 값 중 하나만 일치해도 되는 상황, 특정 값 이상/이하를 비교해야 하는 상황은 패턴 하나로 표현할 수 없었습니다. 조건마다 규칙을 여러 개 만들거나 코드 안에서 다시 판단해야 했습니다.

#2핵심 질문

배열 안의 값, 여러 값 중 하나의 일치, 크기 비교 같은 다양한 조건을 한 패턴 안에서 어떻게 표현할까요?

#3동작 예시

"error" 또는 "failed" 상태의 이벤트만 받는 규칙을 만든다고 가정합니다. 패턴에 {"detail": {"status": ["error", "failed"]}}라고 적으면 status가 error이거나 failed인 이벤트가 모두 매칭됩니다. 배열 필드는 {"detail": {"items": ["a"]}}로 적어 배열 안에 a가 하나라도 있으면 매칭되고, 크기 비교는 {"detail": {"price": [{"numeric": [">", 1000]}]}}처럼 적습니다.

#4동작 과정

  1. 조건 선택일치시키려는 것이 여러 값 중 하나인지, 배열 안의 값인지, 크기 비교인지 정합니다.
  2. 표현 작성여러 값은 값 배열(예: ["error", "failed"]), 배열 필드는 검사할 값, 크기 비교는 numeric 연산자(>, >=, <, <=)로 패턴에 적습니다.
  3. 하나라도 일치하면 전달나열한 조건 중 하나라도 맞거나 배열 안에 해당 값이 있으면 규칙이 이벤트를 대상으로 전달합니다.

#5한 줄 요약

값 목록·배열 포함·크기 비교 연산자를 한 패턴에 조합해 다양한 조건의 이벤트를 하나의 규칙으로 필터링하는 것

6이벤트 패턴06-04

패턴 모범 사례와 테스트

성능과 유지보수를 고려한 패턴 작성 모범 사례를 따르고, 패턴 테스트 도구로 실제 이벤트가 조건에 맞는지 검증하는 방법이다.

#1문제 상황

기존에는 패턴을 만들고 나서 실제로 조건이 맞는지 확인하려면 이벤트를 직접 발생시켜 규칙이 대상을 호출하는지 눈으로 지켜봐야 했습니다. 패턴이 복잡해질수록 어느 조건이 잘못되어 매칭이 안 되는지 찾기 어려웠고, 문서에 남지 않는 임시 규칙이나 필요 이상으로 넓은 조건이 쌓여 유지보수가 어려워졌습니다.

#2핵심 질문

패턴이 의도한 이벤트만 정확히 걸러내는지 배포 전에 어떻게 검증하고, 패턴을 오래 유지보수하기 쉽게 관리할까요?

#3동작 예시

주문 이벤트용 패턴을 만들었다고 가정합니다. EventBridge 콘솔의 패턴 테스트 도구에 실제 주문 이벤트 JSON을 붙여 넣고 "테스트"를 누르면, 이 패턴이 그 이벤트를 매칭하는지 아니면 매칭하지 않는지 즉시 알려줍니다. 배포 전에 이 검증을 통과한 패턴만 규칙에 반영합니다.

#4동작 과정

  1. 좁은 조건으로 작성source와 detail-type을 반드시 지정하고 구체적인 필드 조건만 넣어 불필요한 이벤트를 처음부터 제외합니다.
  2. 테스트 도구로 검증실제 이벤트 JSON을 테스트 도구에 넣어 매칭 여부를 확인하고, 조건을 수정하며 원하는 이벤트만 걸러지는지 반복 확인합니다.
  3. 이름과 변경 관리패턴이 포함된 규칙에 명확한 이름을 붙이고 설계 변경을 기록해 두어, 나중에 누가 봐도 조건과 목적을 알 수 있게 유지합니다.

#5한 줄 요약

구체적이고 좁은 조건으로 패턴을 작성하고 배포 전 테스트 도구로 검증해 원하는 이벤트만 안정적으로 거르는 것

7타깃과 전달07-01

타깃 개념과 AWS 서비스 타깃

규칙이 매칭된 이벤트를 실제로 보내는 목적지(대상)로, Lambda·SQS·SNS 같은 AWS 서비스가 대표적인 타깃이다.

#1문제 상황

규칙이 이벤트를 매칭하기만 하면 아무 일도 일어나지 않는다. 이벤트를 받아 실제 작업(알림 전송, 함수 실행, 데이터 저장)을 수행할 목적지가 필요하다. 목적지를 만들 때마다 호출 방식, 인증, 오류 처리(네트워크 실패나 서비스 과부하 시 재시도)를 일일이 코드로 작성해야 한다면 규칙이 늘어날수록 중복 코드가 쌓이고, 각 서비스의 API 형태가 달라 통합할 때마다 다른 코드를 짜야 한다.

#2핵심 질문

매칭된 이벤트를 어떤 서비스로 보내 실제 처리를 일으키게 할 것인가?

#3동작 예시

"주문 생성" 이벤트를 매칭하는 규칙에 Lambda 함수 하나를 타깃으로 등록해 둔다. 이벤트가 도착하면 버스가 그 이벤트를 함수 실행 요청으로 변환해 보내고, 함수가 주문 처리 로직을 실행한다. AWS 서비스 타깃(Lambda, SQS, SNS 등)은 호출과 인증, 결과 처리를 버스가 표준화된 방식으로 대신 해주는 목적지다.

#4동작 과정

  1. 규칙에 타깃 등록규칙을 만들 때 이벤트를 보낼 타깃(예: Lambda 함수)을 지정하고, 버스가 그 타깃을 호출할 권한을 가진 역할을 연결한다.

이벤트 리플레이

아카이브에 저장된 과거 이벤트를 다시 버스로 흘려보내 규칙과 타깃의 동작을 재현하거나 복구하는 기능이다.

#1문제 상황

이벤트 버스에 흐르는 이벤트는 규칙에 의해 처리되고 나면 그대로 사라진다. 이벤트가 지나간 뒤에는 어디에도 그 사본이 남지 않기 때문에, 같은 이벤트를 다시 처리하고 싶으면 원본 시스템이 처음부터 다시 이벤트를 보내야만 한다. 그런데 원본 시스템이 과거에 보낸 이벤트를 다시 보낼 수는 없다. 그 결과 규칙이나 타깃 로직을 고친 뒤 "과거의 이벤트로 제대로 동작하는지" 검증하고 싶어도 확인할 데이터가 없고, 이벤트 하나가 유실되어 복구가 필요해도 이미 지나간 이벤트는 다시 가져올 방법이 없다.

#2핵심 질문

지나간 이벤트를 어떻게 다시 꺼내서 같은 처리를 그대로 재현할 수 있을까?

#3동작 예시

리플레이는 아카이브에 저장된 이벤트의 재생 기능이다. 먼저 이벤트 버스의 아카이브에 과거 이벤트가 저장되어 있다고 가정한다. 사용자가 아카이브에 대해 리플레이를 시작하면, EventBridge가 아카이브에 저장된 이벤트를 다시 이벤트 버스로 흘려보낸다. 그 이벤트들이 버스를 다시 지나가면서 버스에 등록된 규칙이 다시 평가되고, 조건에 맞는 이벤트는 다시 타깃으로 전달된다. 같은 이벤트가 필요한 시점에 다시 처리되므로, 과거 사건을 재현하는 것과 같은 효과를 낸다.

#4동작 과정

  1. 시간 범위 지정아카이브에서 리플레이할 시작 시각과 종료 시각을 지정한다. 그 범위 안에 아카이브된 이벤트만 다시 재생된다.
  2. 이벤트 재생EventBridge가 지정된 시간 범위의 이벤트를 아카이브에서 꺼내 이벤트 버스로 다시 흘려보낸다. 규칙이 이 이벤트를 다시 평가한다.
  3. 타깃 재전달규칙 조건에 맞는 이벤트가 다시 타깃으로 전달된다. 이미 처리했던 이벤트와 쌍으로 중복이 생길 수 있으므로, 대상 애플리케이션은 중복 처리를 감안해야 한다.

#5한 줄 요약

아카이브에 저장된 과거 이벤트를 다시 이벤트 버스로 흘려보내 규칙과 타깃의 동작을 재현하거나 복구하는 기능

스키마 레지스트리와 스키마 검색

이벤트의 데이터 구조(스키마)를 저장·관리하는 레지스트리와, 등록된 스키마를 검색해 재사용하는 기능.

#1문제 상황

이벤트는 이름과 데이터(body)로 구성되는데, 그 데이터 안에 어떤 필드가 어떤 형식으로 들어 있는지는 어디에도 정의되어 있지 않았다. 이벤트를 보내는 쪽과 받는 쪽이 각자 자기 코드 안에 필드 이름과 형식을 하드코딩하다 보니, 필드 이름을 다르게 쓰거나 형식이 어긋나면 실행 중에만 오류가 드러났다. 또 새 팀원이 이벤트 구조를 파악하려면 코드를 뒤지거나 문서를 찾아봐야 했고, 같은 구조를 여러 곳에서 중복 정의하면서 관리 대상이 점점 흩어졌다.

#2핵심 질문

이벤트의 데이터 구조를 한곳에 모아 두고 필요할 때 검색해서 재사용할 수는 없을까?

#3동작 예시

스키마 레지스트리는 이벤트 구조(스키마)를 모아 두는 저장소다. 예를 들어 "주문 생성" 이벤트가 처음 버스에 등록되면, 등록 시 제출한 샘플이나 실제 이벤트를 바탕으로 그 구조가 레지스트리에 스키마로 저장된다. 나중에 다른 개발자가 "주문" 관련 구조가 있는지 레지스트리에서 검색하면 등록된 스키마를 찾아내고, 같은 이름을 쓰더라도 형식이 맞는지 대조할 수 있다.

#4동작 과정

  1. 레지스트리 생성계정에 스키마 레지스트리를 하나 만든다. 이벤트 버스와 스키마 레지스트리는 기본적으로 연결되어 이벤트 등록 시 스키마가 자동으로 기록된다.
  2. 스키마 등록·검색이벤트 구조가 스키마로 등록되면, 이름이나 키워드로 검색해 원하는 구조를 찾는다. 기존 스키마가 이미 있으면 중복 등록 대신 그것을 재사용할 수 있다.
  3. 스키마 재사용찾은 스키마를 기반으로 코드 바인딩을 생성하거나, 이벤트 구조를 확인하고 대조하여 다른 규칙·애플리케이션에서 같은 정의를 사용한다.

스키마 생성: 템플릿·JSON·추론

템플릿 사용, 이벤트 JSON 업로드, 이벤트 버스의 실제 이벤트로부터 추론 등 세 가지 방법으로 스키마를 만드는 과정.

#1문제 상황

스키마 레지스트리를 쓰려면 먼저 스키마를 만들어야 하는데, 스키마를 손으로 직접 정의하면 필드를 빠뜨리거나 형식을 잘못 적을 가능성이 있다. 또 이벤트를 이미 운영 중인 팀은 과거에 흘러간 모든 이벤트 구조를 수작업으로 다시 입력해야 하는 부담이 생긴다. 사람이 직접 만드는 방식만 있으면 최신 이벤트 구조가 스키마와 어긋나는 일이 빈번해진다.

#2핵심 질문

스키마를 손으로 일일이 정의하지 않고, 이미 있는 재료로 쉽게 만들 수는 없을까?

#3동작 예시

EventBridge는 세 가지 생성 경로를 제공한다. 첫째는 콘솔에서 제공하는 템플릿을 골라 원하는 이벤트 유형의 구조를 그대로 쓰는 방법이다. 둘째는 실제 이벤트의 JSON 샘플을 업로드하여 그 구조로 스키마를 만드는 방법이다. 셋째는 이벤트 버스에 연결된 스키마 레지스트리가 실제로 흐르는 이벤트를 관찰하여 구조를 자동으로 추론해 등록하는 방법이다. 셋째 경로는 이벤트가 지나갈 때마다 스키마가 자동으로 갱신되므로 사람이 빠뜨린 필드도 누락되지 않는다.

#4동작 과정

  1. 재료 준비템플릿을 고르거나, 업로드할 이벤트 JSON 샘플을 준비한다. 추론 방식을 쓰려면 이벤트 버스에 스키마 레지스트리를 연결해 둔다.
  2. 스키마 생성선택한 템플릿을 등록하거나 JSON 샘플을 업로드해 스키마를 만든다. 추론 방식은 레지스트리가 실제 이벤트에서 구조를 자동으로 만들어 등록한다.
  3. 등록·갱신생성된 스키마가 레지스트리에 저장되고, 이후 새 구조의 이벤트가 흐르면 추론 기능이 스키마를 최신 상태로 갱신한다.

코드 바인딩 생성

등록된 스키마로부터 Java, Python, TypeScript 등 언어별 데이터 클래스(코드 바인딩)를 생성해 이벤트 처리를 타입 안전하게 만드는 기능.

#1문제 상황

이벤트 데이터는 JSON으로 전달되므로, 애플리케이션 코드에서는 그 JSON을 직접 파싱하고 필드 이름을 문자열로 지정해 값을 꺼내야 했다. 필드 이름을 하나만 오타로 적어도 실행 중에야 오류가 나타났고, 구조가 바뀌면 문자열로 접근하는 모든 위치를 일일이 찾아 고쳐야 했다. 컴파일러나 에디터가 필드 오타나 형식 불일치를 미리 잡아 주지 못하므로, 이벤트 구조 변경은 런타임 장애의 흔한 원인이었다.

#2핵심 질문

등록된 스키마를 코드로 바꿔서 이벤트 데이터를 타입 안전하게 다룰 수는 없을까?

#3동작 예시

스키마 레지스트리에 등록된 스키마로부터 코드 바인딩을 생성하면, 그 스키마의 필드가 Java·Python·TypeScript 등의 데이터 클래스로 만들어진다. 예를 들어 "주문 생성" 스키마에서 코드 바인딩을 생성하면 OrderCreatedEvent 클래스가 나오고, 이벤트 데이터를 직접 파싱하는 대신 그 클래스의 인스턴스로 받아 필드를 문자열 오타 걱정 없이 접근할 수 있다.

#4동작 과정

  1. 스키마·언어 선택레지스트리에서 코드 바인딩을 만들 스키마를 고르고, 사용할 프로그래밍 언어를 지정한다.
  2. 바인딩 생성·다운로드EventBridge가 스키마의 각 필드를 해당 언어의 데이터 클래스로 변환한 코드 바인딩을 생성한다. 이를 압축 파일로 다운로드한다.
  3. 코드에 적용생성된 클래스를 애플리케이션 프로젝트에 추가하고, 이벤트 처리 로직에서 JSON 파싱 대신 그 클래스를 사용한다. 스키마가 바뀌면 바인딩을 다시 생성해 갱신한다.

API destinations

이벤트를 HTTP 엔드포인트(웹훅·REST API)로 직접 전달하는 대상 유형으로, AWS 밖의 서드파티 API도 호출 대상으로 삼을 수 있게 한다.

#1문제 상황

EventBridge의 규칙 타깃은 기본적으로 AWS 안의 서비스(SQS, Lambda, Step Functions 등)로 한정되던 것이 일반적이었다. AWS 밖에 있는 HTTP나 REST API, 예를 들어 자사 사내 시스템이나 외부 서드파티의 웹훅 엔드포인트로 이벤트를 보내려면 중간에 Lambda 함수를 두고 그 안에서 HTTP 클라이언트 코드를 직접 작성해 호출해야 했다. 그렇게 하면 이벤트마다 함수를 하나씩 만들고 관리해야 하므로, 단순한 "이벤트를 URL로 전달"이라는 목적에 비해 코드와 운영 부담이 크게 늘었다.

#2핵심 질문

AWS 밖의 HTTP 또는 REST API를 규칙 타깃으로 직접 지정해 이벤트를 바로 보낼 수는 없을까?

#3동작 예시

API destinations는 규칙 타깃으로 선택할 수 있는 HTTP 엔드포인트 유형이다. 설정에서 대상 URL과 HTTP 메서드, 헤더, 그리고 인증에 쓸 커넥션만 지정하면, 이벤트가 발생했을 때 EventBridge가 그 URL로 HTTP 요청을 직접 보낸다. 예를 들어 이벤트를 만들 때마다 외부 CRM의 REST API로 그 내용을 POST로 전달하는 규칙을, Lambda 한 줄 없이 만들 수 있다.

#4동작 과정

  1. API destination 설정규칙 타깃으로 API destination을 만들면서 호출할 URL, HTTP 메서드, 헤더와 인증 커넥션을 지정한다.
  2. 이벤트 → HTTP 요청 변환규칙에 맞는 이벤트가 발생하면 EventBridge가 이벤트 내용을 설정한 메서드·형식의 HTTP 요청으로 구성한다.
  3. 엔드포인트 전송·결과 처리요청이 대상 API로 전송되고, 응답 상태 코드에 따라 성공 처리되거나 실패 시 재시도 정책에 따라 다시 전송된다.

커넥션: 인증·상태·수명주기

API destinations가 API를 호출할 때 쓰는 인증 정보(API key·기본 인증·OAuth)와 권한 부여 상태, 생성·업데이트·비활성화·삭제 전반의 수명주기를 관리하는 설정 묶음.

#1문제 상황

API destinations가 외부 API를 호출할 때는 인증이 필요하다. API key, 사용자 이름과 암호, OAuth 토큰 같은 자격 증명을 어디에 두느냐가 문제였다. 이를 규칙 설정이나 코드 안에 그대로 적어 두면 자격 증명이 노출될 위험이 커지고, 각 타깃마다 같은 인증 정보를 중복으로 관리해야 했다. 또 OAuth처럼 토큰이 만료되는 방식은 갱신 시점을 누군가 직접 챙겨야 했다.

#2핵심 질문

외부 API 호출에 쓰는 인증 방식을 안전하게 한곳에 저장하고 상태와 수명주기까지 관리할 수는 없을까?

#3동작 예시

커넥션은 인증 정보를 담는 설정 묶음이다. 예를 들어 API destinations에 사용할 커넥션 하나를 만들면서 인증 유형을 "기본 인증"으로 고르고 사용자 이름과 암호를 입력하면, EventBridge가 그 값을 암호화해 보관한다. 이후 그 커넥션을 쓰는 API destination이 외부 API를 호출할 때 자동으로 그 인증 정보를 붙여 보낸다. OAuth를 쓰는 경우에는 커넥션을 만들 때 권한 부여(승인) 과정을 거쳐 토큰을 발급받고, 그 토큰도 커넥션에 저장된다.

#4동작 과정

  1. 커넥션 생성인증 유형(API key, 기본 인증, OAuth)을 고르고 자격 증명을 입력한다. 입력한 값은 보안 자격 증명 저장소에 암호화되어 보관된다. OAuth는 이 단계에서 권한 부여·토큰 발급을 완료한다.
  2. 상태 확인커넥션은 권한 부여 상태(승인됨, 만료됨 등)를 가지므로 승인이 완료됐는지 확인한다. OAuth 토큰이 만료되면 다시 권한 부여를 수행한다.
  3. 수명주기 관리커넥션을 업데이트해 인증 정보를 바꾸거나, 더 이상 쓰지 않으면 권한 부여를 해제하고 삭제한다. 삭제하면 그 커넥션을 쓰던 API destination의 호출도 함께 중단된다.

#5한 줄 요약

외부 API 호출에 쓰는 인증 방식과 자격 증명을 한곳에 암호화해 저장하고, 권한 부여 상태를 확인하며 생성·갱신·해제·삭제로 수명주기를 관리하는 설정 묶음

비공개 API 커넥션과 VPC

인터페이스 VPC 엔드포인트를 통해 VPC 내부·프라이빗 네트워크에 있는 비공개 API로 이벤트를 안전하게 보내는 커넥션 방식.

#1문제 상황

API destination(API 목적지)을 쓰면 EventBridge 가 이벤트를 외부 HTTP API 로 보낼 수 있다. 그런데 기본적으로 EventBridge 는 퍼블릭 인터넷을 통해 호출한다. 대상 API 가 VPC(가상 사설 클라우드) 안에 있어서 외부에서 직접 접근할 수 없는 경우, 기존 방식으로는 이벤트를 보낼 방법이 없었다. 인터넷을 우회하는 경로가 없으면 아무리 규칙을 잘 만들어도 요청이 도달조차 할 수 없다.

#2핵심 질문

VPC 내부에 있는 비공개 API 로도 EventBridge 가 이벤트를 안전하게 전달할 수 있게 하려면 어떻게 해야 할까?

#3동작 예시

커넥션(connection)을 만들 때 VPC ID 와 서브넷, 보안 그룹을 지정하면, EventBridge 가 VPC 내부의 API 를 호출하기 위한 전용 엔드포인트를 통해 바이패스(우회) 방식으로 요청을 보낸다. 즉 커넥션에 VPC 설정을 넣는 것만으로 퍼블릭 인터넷을 거치지 않는 개인 경로가 생긴다.

#4동작 과정

  1. 커넥션 생성VPC 안의 API 를 호출하기 위한 커넥션을 만들 때 VPC ID, 서브넷, 보안 그룹을 함께 등록한다. 이 정보가 호출 경로의 기준이 된다.
  2. 엔드포인트 경유EventBridge 는 커넥션 설정에 따라 VPC 의 비공개 IP 주소를 사용해 API 로 향하는 인터페이스 엔드포인트(인터넷을 거치지 않는 연결 지점)를 경유해 요청을 보낸다.
  3. 결과 전달API 응답을 받은 EventBridge 가 그 결과를 이벤트의 흐름대로 되돌려준다. 보안 그룹이 API 쪽 접근을 허용해야 응답까지 정상적으로 도착한다.

#5한 줄 요약

커넥션에 VPC 정보를 지정해 인터넷을 거치지 않는 비공개 경로로 EventBridge 가 VPC 내부 API 를 호출하게 하는 것

SaaS 파트너 이벤트 소스

Salesforce, Datadog, Zendesk 같은 SaaS 파트너가 자사 서비스의 이벤트를 이벤트 버스로 보내도록 연동하는 파트너 이벤트 소스.

#1문제 상황

EventBridge 로 이벤트를 받으려면 지금까지는 AWS 서비스나 자체 애플리케이션이 이벤트를 보내는 방식이었다. Salesforce, Zendesk 같은 SaaS(소프트웨어 구독 서비스)에서 발생하는 데이터 변경이나 알림은 EventBridge 로 직접 들어오지 않았고, 받으려면 SaaS 쪽에 별도 연동 코드를 만들고 AWS 에 이벤트를 전달하는 중간 다리를 직접 구축해야 했다.

#2핵심 질문

외부 SaaS 에서 발생한 이벤트를 별도의 연동 개발 없이 EventBridge 로 바로 받으려면 어떻게 해야 할까?

#3동작 예시

SaaS 파트너가 자신의 상품을 EventBridge 의 파트너 이벤트 소스로 등록해 두면, 사용자는 콘솔에서 해당 SaaS 와의 연결을 한 번 활성화하는 것만으로 그 SaaS 의 이벤트가 사용자의 이벤트 버스(이벤트가 모이는 통로)로 자동으로 흘러들어온다.

#4동작 과정

  1. 파트너 이벤트 소스 활성화콘솔에서 SaaS 파트너가 제공한 이벤트 소스를 찾아 연결을 활성화한다. 이때 상대 SaaS 쪽에서도 연동 승인 절차를 마쳐야 한다.
  2. 이벤트 수신SaaS 에서 이벤트가 발생하면 파트너가 운영하는 인프라가 그 이벤트를 사용자의 이벤트 버스로 전달한다. 사용자 측에서는 별도 수신 서버를 만들 필요가 없다.
  3. 규칙으로 처리버스에 도착한 SaaS 이벤트는 그 뒤로 일반 이벤트와 동일하게 규칙(조건 매칭)을 통해 필터링되어 원하는 대상으로 보내진다.

#5한 줄 요약

SaaS 파트너가 제공하는 이벤트 소스를 한 번 활성화하면 외부 SaaS 이벤트가 별도 연동 개발 없이 사용자의 이벤트 버스로 자동 유입되는 것

Pipes 개념·생성·권한

EventBridge Pipes의 핵심 개념, 파이프를 만드는 절차, 그리고 파이프가 소스·타깃 리소스에 접근하기 위해 필요한 IAM 권한을 다루는 항목이다.

#1문제 상황

기존에 이벤트를 다른 서비스로 보내려면 이벤트 버스와 규칙, 그리고 Lambda 함수 같은 중간 처리 코드를 조합해 파이프라인을 직접 구성해야 했다. 소스에서 데이터를 읽고, 내용을 바꾸고, 목적지로 보내는 일을 할 때마다 처리 로직을 코드로 작성하고 실행 환경과 권한을 따로 관리해야 했다. 데이터 흐름 하나를 만들려고 여러 서비스를 개별적으로 붙이는 작업이 반복되었다.

#2핵심 질문

소스에서 데이터를 읽어 가공하고 목적지로 보내는 일을 코드 작성 없이 한 서비스로 처리하려면 어떻게 해야 할까?

#3동작 예시

EventBridge Pipes 는 소스(데이터가 나오는 곳), 필터와 강화(가공 단계), 타깃(데이터가 도착하는 곳)을 콘솔에서 지정하고 연결하면, 그 사이의 데이터 이동과 처리를 AWS 가 대신 실행해 주는 통합 도구다. 코드 대신 설정만으로 하나의 데이터 흐름이 완성된다.

#4동작 과정

  1. 파이프 생성콘솔에서 파이프를 만들고 소스(예: SQS 큐)와 타깃(예: Lambda, Step Functions)을 선택한다. 이 연결 자체가 파이프의 뼈대가 된다.
  2. 권한 설정파이프가 소스에서 읽고 타깃에 쓰기 위한 IAM 역할(권한 부여용 역할)을 지정한다. 역할이 소스 읽기와 타깃 호출 권한을 가져야 파이프가 동작한다.
  3. 실행파이프가 시작 상태가 되면 소스에 도착한 데이터가 자동으로 흘러 타깃으로 전달된다. 흐름은 AWS 가 관리하므로 서버를 운영할 필요가 없다.

#5한 줄 요약

소스·가공·타깃을 설정으로 연결하면 코드 없이 데이터 흐름을 만들고 권한을 역할로 맡겨 AWS 가 실행해 주는 것

Pipes 소스 유형

Pipes가 이벤트를 읽어오는 원본(소스)의 종류를 설명한다 — SQS, Kinesis, DynamoDB 스트림, Amazon MQ, MSK, Apache Kafka 등.

#1문제 상황

파이프의 시작점인 소스는 데이터가 어디서 나오는지를 정하는 부분이다. 기존에는 소스마다 다른 방식으로 붙어야 해서, 데이터를 읽는 코드를 소스의 종류에 맞게 각각 작성하고 폴링(주기적으로 새 데이터가 있는지 확인하는 일) 주기까지 직접 관리해야 했다. SQS 를 쓰면 메시지를 받는 코드를, Kinesis 를 쓰면 스트림을 읽는 코드를 따로 만들어야 했다.

#2핵심 질문

종류가 다른 여러 데이터 소스를 동일한 방식으로 파이프에 연결하려면 어떻게 해야 할까?

#3동작 예시

Pipes 는 SQS 큐, Kinesis 스트림, DynamoDB 스트림, Amazon MSK 와 Apache Kafka 토픽, Amazon MQ 브로커를 모두 소스로 지정할 수 있다. 어느 소스를 골라도 파이프가 알아서 데이터를 읽어 들이므로 데이터를 가져오는 코드를 쓸 필요가 없다.

#4동작 과정

  1. 소스 선택파이프 생성 시 소스로 사용할 서비스와 그 안의 큐나 스트림 이름을 지정한다.
  2. 자동 읽기파이프가 소스에서 데이터를 자동으로 가져온다. 스트림 계열 소스는 지속적으로 흐르는 데이터를, 큐 계열 소스는 쌓인 메시지를 읽어서 파이프 안으로 밀어 넣는다.
  3. 다음 단계로 전달읽어 들인 데이터는 필터링·강화 단계를 거치도록 파이프가 다음 처리로 넘긴다.

#5한 줄 요약

파이프가 큐와 스트림 등 여러 소스 유형을 기본 지원해, 선택만 하면 데이터 수집 코드 없이 소스를 흐름의 시작점으로 사용하게 하는 것

11Pipes와 Scheduler11-03

Pipes 필터링과 강화(enrichment)

Pipes가 소스에서 받은 이벤트를 조건으로 걸러내는 필터링과, Lambda 등으로 이벤트에 데이터를 더하는 강화(enrichment) 기능을 설명한다.

#1문제 상황

소스에서 나온 데이터를 목적지로 그대로 보내는 것만으로는 부족한 경우가 많다. 불필요한 데이터를 걸러내고, 데이터에 부가 정보를 붙여야 할 때 기존에는 처리용 Lambda 함수를 직접 만들고 파이프라인에 끼워 넣어야 했다. 함수를 배포하고 권한을 설정하고 실패 처리를 관리하는 일이 데이터 흐름마다 반복되었다.

#2핵심 질문

중간에 데이터를 걸러내고 보강하는 작업을 별도 함수 운영 없이 파이프 안에서 처리하려면 어떻게 해야 할까?

#3동작 예시

파이프에는 소스와 타깃 사이에 필터링과 강화 단계를 설정으로 끼워 넣을 수 있다. 필터링은 조건에 맞는 데이터만 통과시키고, 강화는 Lambda 또는 API destination 을 호출해 데이터에 추가 정보를 붙여 다음 단계로 넘긴다.

#4동작 과정

  1. 필터링파이프에 조건을 지정하면 그 조건에 맞지 않는 데이터는 이후 처리를 건너뛰고 버려진다. 예를 들어 에러 상태의 메시지만 통과시키는 방식이다.

  3. 타깃 전달필터를 통과하고 강화까지 마친 최종 데이터가 타깃으로 전송된다.

EventBridge Scheduler 개요

일정(cron·rate)에 따라 AWS 리소스를 자동 호출하는 EventBridge Scheduler의 개요로, 기존 예약 규칙(legacy)과의 차이를 포함해 소개한다.

#1문제 상황

정해진 시각에 특정 작업을 실행하려면 기존에는 애플리케이션 안에 타이머를 넣거나, 별도 서버에서 크론 작업을 돌리고, 그 실행 결과와 실패 처리를 직접 관리해야 했다. 이런 방식은 실행할 서버를 계속 띄워 두어야 하고, 시간대·지연·재시도·실패 알림까지 전부 각자 구현해야 해서 관리 부담이 크다. 그리고 한 번 스케줄이 꼬이면 다음 실행까지 기다리는 동안 아무것도 할 수 없는 구조다.

#2핵심 질문

서버를 직접 띄워 타이머를 관리하지 않고도, 정해진 시간에 한 번 또는 반복적으로 AWS 서비스 작업을 실행할 수는 없을까?

#3동작 예시

"매주 월요일 오전 9시에 EC2 인스턴스를 시작한다"는 스케줄이 필요하다고 할 때, EventBridge Scheduler에 일정(크론 표현식)과 타깃(EC2 시작 API 호출)을 등록해 두면, 그 시각이 되면 AWS가 알아서 해당 API를 호출한다. 실행 시점 관리·재시도·실패 처리는 서비스가 담당한다.

#4동작 과정

  1. 스케줄 생성실행 시각(한 번 또는 반복 크론)과 실행할 타깃(EC2 시작, Lambda 호출, SQS 전송 등)을 지정해 스케줄을 등록한다.
  2. 시각 도달 시 실행등록된 시각·주기가 되면 Scheduler가 지정된 타깃을 호출하고, 실패하면 재시도 정책에 따라 다시 시도한다.
  3. 실행 확인·관리실행 결과와 지표를 확인하고, 스케줄을 일시 중지·해제하거나 삭제해 필요 없어진 작업을 멈춘다.

IAM: 자격 기반·리소스 기반 정책

EventBridge 접근을 IAM 자격 기반 정책(주체가 무엇을 할 수 있는지)과 리소스 기반 정책(버스가 누구를 허용하는지) 두 방식으로 제어한다.

#1문제 상황

EventBridge의 버스·규칙·파이프 등 리소스를 여러 사람과 서비스가 함께 쓰면, 누가 어떤 작업을 할 수 있는지 정하지 않으면 아무나 이벤트를 보내고, 규칙을 바꾸고, 다른 계정의 리소스까지 건드릴 수 있다. 권한을 아예 관리하지 않으면 과도한 접근이 그대로 허용되고, 반대로 전부 막아 버리면 정상 동작까지 멈춘다. 어떤 주체(사용자·역할)가 무엇을 할 수 있는지를 세밀하게 표현하는 방법이 없으면 보안과 동작 가능성 사이의 균형을 잡을 수 없다.

#2핵심 질문

이벤트 버스·규칙·파이프 같은 EventBridge 리소스에 대해 누가 어떤 작업을 할 수 있는지를 어떻게 명확하게 통제할까?

#3동작 예시

한 AWS 계정 안에서 개발팀 사용자에게 "이름이 dev-로 시작하는 규칙만 만들고 수정할 수 있다"는 권한을 주고 싶다면, 자격 기반 정책으로 그 사용자의 IAM 정책에 해당 작업(events:PutRule)과 리소스 조건(arn에 dev- 접두사)을 적는다. 반대로 "이 버스에 이벤트를 보내는 것을 다른 계정에 허용한다"는 것은 버스에 붙는 리소스 기반 정책으로 표현한다. 정책을 누구에게(자격) 붙이느냐, 리소스에 붙이느냐에 따라 통제의 방향이 달라진다.

#4동작 과정

  1. 자격 기반 정책사용자·그룹·역할(자격)에 정책을 붙여, 그 자격이 EventBridge의 어떤 작업(생성·수정·삭제)을 어떤 리소스에 대해 할 수 있는지 정한다.
  2. 리소스 기반 정책이벤트 버스·스키마 레지스트리 같은 리소스에 정책을 붙여, 어떤 계정·어떤 조건의 요청이 이 리소스에 접근할 수 있는지 정한다(주로 계정 간 이벤트 전송·수신).
  3. 권한 결합·평가요청이 들어오면 자격 기반 정책과 리소스 기반 정책이 함께 평가되어, 명시적 허용이 없으면 기본 거부되고 최종 허용 여부가 결정된다.

EventBridge가 규칙·파이프가 가리키는 타깃(Lambda, SQS, EC2 등)을 실행하려면 그 서비스의 리소스에 접근할 권한이 필요하다. 이때 사용자의 일회용 자격 증명을 오래 저장해 두는 방식은 만료·관리 문제가 생긴다. 또 다른 문제는 권한을 주고받는 과정에서 "이 요청이 진짜 내가 의도한 상대에게서 온 것인지"가 확실하지 않다는 것이다. 예를 들어 다른 계정의 상대방이 자기 계정의 리소스(예: S3 버킷)가 아닌, 나와 공유된 리소스에 대해 권한을 요청할 때 그 요청을 가로채거나 악용하는 시나리오(confused deputy, 혼동된 대리인)가 가능하다.

EventBridge가 타깃 서비스를 대신 실행할 때 필요한 권한을 안전하게 위임하고, 요청이 진짜 의도한 상대에게서 온 것임을 어떻게 보장할까?

#3동작 예시

규칙이 EC2 인스턴스를 시작하도록 만들 때, 규칙 실행용 IAM 역할을 만들어 EC2 시작 권한을 그 역할에 부여하고, 규칙에 "이 역할을 맡아라"라고 지정한다. 역할을 쓰면 사용자 자격 증명을 저장하지 않고도 권한이 위임된다. 여기에 더해 리소스 기반 정책(예: 다른 계정이 내 리소스에 접근할 때)에 "상대방의 계정 ID"를 조건으로 넣으면, 권한 도용자가 다른 계정에서 보낸 요청은 조건 불일치로 거부되어 혼동된 대리인 공격이 차단된다.

#4동작 과정

  1. 역할 생성·권한 부여타깃 서비스에 필요한 권한을 가진 IAM 역할을 만들고, 그 역할을 EventBridge가 맡을 수 있게 신뢰 정책을 설정한다.
  2. 규칙·파이프에 역할 연결규칙이나 파이프가 타깃을 호출할 때 이 역할을 사용하도록 지정해 권한을 위임한다.
  3. 조건으로 검증계정 간 접근을 허용하는 정책에는 aws:SourceArn·aws:SourceAccount 조건을 넣어, 요청이 내가 지정한 리소스·계정에서만 왔는지 검증하고 그 외 요청은 거부한다.

IAM 역할로 타깃 실행 권한을 위임하고, 정책에 출처 조건을 넣어 요청이 진짜 의도한 상대에게서 왔는지 검증함으로써 권한 도용을 막는 것

#1문제 상황

이벤트에는 결제 정보·개인 식별 정보처럼 민감한 데이터가 실릴 수 있다. EventBridge는 전송 중(네트워크) 암호화를 기본 제공하지만, 저장되는 데이터가 암호화되지 않으면 디스크에 남은 이벤트나 아카이브에서 데이터가 노출될 수 있다. 또 암호화 키를 AWS가 관리하는 기본 키 하나로만 쓰면 부서별·서비스별로 키를 분리해 통제하거나, 특정 키 사용을 감사하고, 키를 회전·폐기하는 요구사항을 맞출 수 없다.

#2핵심 질문

이벤트 버스에 실리는 데이터와 보관된 이벤트를 어떤 키로, 어떻게 암호화해서 저장될 때의 노출 위험을 막을까?

#3동작 예시

회사가 자체 KMS 키를 만들어 "결제 버스"에 연결해 두면, 그 버스를 통과하는 이벤트가 저장될 때 그 키로 암호화된다. 같은 키를 아카이브나 파이프 데이터 암호화에도 지정해 두면, 한 키로 버스·아카이브·파이프·커넥션 전체의 저장 데이터를 통일되게 암호화하고, 키 사용 로그로 누가 언제 키를 썼는지 추적할 수 있다.

#4동작 과정

  1. 키 지정EventBridge 리소스(이벤트 버스·아카이브·파이프·커넥션)에 KMS 키(자체 키 또는 AWS 관리형 키)를 암호화 키로 지정한다.
  2. 저장 데이터 암호화해당 리소스에 기록되는 이벤트·아카이브·연결 정보가 지정된 키로 암호화되어 저장된다.
  3. 키 권한·운영 관리키 정책으로 EventBridge가 키를 쓸 수 있게 허용하고, 키 교체·폐기·사용 감사를 통해 접근을 지속적으로 관리한다.

#1문제 상황

#3동작 예시

#4동작 과정

  2. 태그 활용IAM 정책(누가 무엇을 할 수 있는지 정의하는 권한 문서)에 태그 조건을 넣어 태그 기반 접근 제어를 적용하고, 콘솔 필터와 비용 보고서에서 리소스를 분류해서 관리한다.
  3. 한도·가용성 확인서비스 쿼터(계정별 최대 규칙 수, 초당 처리 이벤트 수 등)에서 현재 사용량과 한도를 보고, 초과가 우려되면 한도 증가를 요청한다. 기능 가용성 페이지로 리전별 지원 여부도 확인한다.

#3동작 예시

#4동작 과정

  2. 이벤트 흐름 추적전송 추적 기능을 켜면 이벤트가 버스에서 타깃까지 전달되는 각 구간의 처리 기록이 X-Ray에 쌓여, 어느 단계에서 지연·실패했는지 추적 차트로 확인한다.
  3. 보안 연결·외부 연동Interface VPC Endpoint로 EventBridge와 VPC를 프라이빗 연결하고, 관리형 Apache Kafka 커넥터를 사용해 Kafka 토픽과 이벤트를 주고받는다.
