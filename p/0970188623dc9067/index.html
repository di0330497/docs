1부. Secrets Manager 개요와 등장 배경001

시크릿(Secret)이란 무엇인가

시크릿이 무엇이고 왜 일반 설정값과 따로 다뤄야 하는지 이해합니다

회사에서 데이터베이스에 접속할 비밀번호를 잃어버리면 그날 업무가 통째로 멈추고, 반대로 아무나 볼 수 있는 곳에 적어 두면 누구든 그것을 읽고 그대로 쓸 수 있습니다. 시크릿(Secret)은 이렇게 외부에 드러나면 곧바로 피해로 이어지는 비밀값을 일반 설정값과 분리해, 안전하게 보관하고 꺼내 쓰도록 만든 개념입니다.

아파트 단지에 공용 사물함이 하나 있고 그 안에 각 세대의 우편함 열쇠와 관리사무소 출입 카드가 들어 있다고 생각해 봅니다. 각 세대는 자기 열쇠만 받아 자기 우편함만 열 수 있지만, 사물함 자체는 단단한 잠금장치로 보호되어 아무나 손댈 수 없습니다. 시크릿도 이와 같아서 값은 암호화된 저장소라는 금고에 두고, 권한이 확인된 애플리케이션에만 필요한 순간에 잠깐 꺼내 주며, 누가 언제 열었는지 기록이 남습니다.

반면 화면 밝기나 목록 크기처럼 감춰야 할 이유가 없는 일반 설정값은 그냥 설정 파일에 두어도 문제가 되지 않습니다.

정리하면 시크릿은 암호, API 키, 접근 토큰처럼 유출되는 순간 권한까지 넘겨주는 값이고, 그래서 일반 설정값과 다른 보관·접근·감사 절차를 갖는 대상입니다.

1부. Secrets Manager 개요와 등장 배경002

하드코딩된 자격 증명의 위험

코드와 저장소에 비밀번호를 적어 두면 어떤 경로로 새는지 설명합니다

개발자가 빠르게 테스트하려고 코드 안에 데이터베이스 비밀번호를 그대로 적어 두면 당장은 잘 돌아가지만, 그 한 줄이 회사의 모든 문을 여는 열쇠가 됩니다. 문제는 그 값이 코드와 함께 저장소(repository)로 복사되고 기록에 남으며, 빌드 결과물과 로그로도 흘러간다는 점입니다.

아파트 공동현관 비밀번호를 출입문 옆에 작은 메모로 붙여 두면, 입주민만 알던 정보가 지나가는 모든 사람에게 공개됩니다. 게다가 한 번 붙은 메모는 사진으로 찍혀 단체 대화방에 돌고, 관리인이 비밀번호를 바꿔도 문 옆 메모는 예전 숫자 그대로 남습니다.

하드코딩된 자격 증명도 똑같아서, 코드에 적힌 값은 저장소를 복제한 모든 사람의 컴퓨터에 함께 복사되고 커밋 기록(commit history)을 뒤지면 지운 뒤에도 되살아납니다. 그래서 비밀번호를 바꾸려면 코드를 고치고 다시 배포해야 하며, 그 사이 예전 값은 여전히 유효하게 남아 있습니다.

결국 하드코딩은 비밀을 코드라는 공개 매체에 인쇄해 배포하는 일과 같고, 자격 증명은 코드 밖의 저장소에서 실행 시점에 가져와야 합니다. 유출이 의심되면 코드를 고치는 것으로 끝내지 말고 해당 자격 증명 자체를 즉시 교체해야 합니다.

1부. Secrets Manager 개요와 등장 배경003

Amazon Secrets Manager 소개

이 서비스가 제공하는 기능을 한 장으로 정리합니다

서버를 새로 만들 때마다 데이터베이스 비밀번호를 어딘가에서 찾아 복사해 넣는 일을 반복하면, 사람마다 다른 값이 들어가고 어느 것이 최신인지 아무도 모르게 됩니다. Amazon Secrets Manager는 AWS가 제공하는 관리형 시크릿 저장 서비스로, 이런 비밀값의 보관과 꺼내 쓰기, 교체를 한곳에서 처리합니다.

호텔 프런트 데스크에 객실 열쇠를 보관하는 캐비닛이 있다고 생각해 봅니다. 청소 담당자와 정비 담당자, 프런트 직원은 각자 허용된 구역의 열쇠만 요청할 수 있고, 프런트는 누가 어떤 열쇠를 언제 가져갔는지 장부에 적습니다.

Secrets Manager도 마찬가지로 시크릿을 암호화해 보관하고, 권한 정책(IAM)을 통과한 요청에만 값을 건네며, 접근 기록을 남기고 정해진 주기로 비밀번호를 새 값으로 바꿔 줍니다. 애플리케이션은 코드에 값을 넣는 대신 실행 시점에 이름을 지정해 값을 요청하고, 캐시를 두어 매번 호출하지 않도록 설계할 수 있습니다.

정리하면 Secrets Manager는 시크릿의 저장과 암호화, 접근 제어, 자동 교체, 감사를 대신 맡는 관리형 서비스입니다. AWS 안의 데이터베이스든 외부 서드파티 API 키든 같은 방식으로 다룰 수 있다는 점이 이 서비스의 범위입니다.

Secrets Manager가 해결하는 문제

보관·암호화·교체·감사를 서비스가 대신 맡는다는 점을 설명합니다

비밀번호를 안전하게 두는 일은 저장만 잘한다고 끝나지 않고, 누가 읽었는지 확인하고, 주기적으로 바꾸고, 바꾼 값을 모든 시스템에 반영하는 일까지 이어집니다. 이 네 가지를 사람 손으로 처리하면 반드시 한 곳이 빠지고, 빠진 곳이 곧 사고 지점이 됩니다.

사무실 건물의 출입 카드를 관리하는 총무를 떠올려 보면, 카드를 금고에 보관하는 일, 발급 대장을 적는 일, 퇴사자 카드를 무효화하는 일, 정기적으로 카드를 재발급하는 일이 모두 따로 존재합니다. 총무가 한 명일 때는 이 네 가지가 맞물려 돌아가지만, 담당자가 바뀌거나 건물이 여러 개로 늘어나면 대장과 실제 카드가 어긋나기 시작합니다.

Secrets Manager는 이 네 가지를 서비스 한 곳으로 모아, 저장은 암호화된 저장소가, 발급 대장은 접근 로그와 감사 기록(CloudTrail)이, 카드 무효화는 자동 교체(rotation)가 맡도록 만듭니다. 자동 교체 때에는 새 값을 만들고 대상 데이터베이스에 반영한 뒤 저장소를 갱신하는 순서를 서비스가 관리하므로, 사람이 새벽에 직접 값을 바꾸지 않아도 됩니다.

결국 Secrets Manager가 해결하는 문제는 비밀값의 수명 주기 전체를 한 시스템의 책임으로 옮기는 것이고, 그래서 사람이 기억해야 할 예외가 줄어듭니다.

시크릿과 환경 변수 비교

환경 변수나 설정 파일에 값을 두는 방식과 무엇이 다른지 비교합니다

환경 변수(environment variable)는 애플리케이션에 값을 넘기는 가장 간단한 방법이라, 많은 팀이 비밀번호까지 환경 변수에 넣어 배포합니다. 하지만 환경 변수는 프로세스가 시작될 때 메모리에 평문으로 존재하고, 설정 화면과 로그, 디버그 출력에서 그대로 보일 수 있습니다.

현관문 앞에 "열쇠는 발매트 아래"라는 쪽지를 붙여 두는 것과, 경비실 금고에 열쇠를 맡기고 필요할 때 받아 가는 것의 차이라고 생각해 봅니다.

환경 변수는 앞의 쪽지와 비슷해서 값이 프로세스 환경에 그대로 들어 있고, 그 환경을 들여다볼 수 있는 사람이면 누구나 읽습니다. Secrets Manager는 뒤의 금고와 비슷해서 값은 암호화되어 밖에 있고, 애플리케이션은 권한을 증명한 뒤 필요한 순간에만 값을 받아 옵니다. 또 환경 변수는 값이 바뀌면 프로세스를 다시 시작해야 반영되지만, Secrets Manager는 저장된 값을 교체하고 애플리케이션이 다시 조회하면 새 값이 적용됩니다.

그래서 화면 크기나 로그 수준 같은 값은 환경 변수로 충분하지만, 유출되면 권한까지 넘어가는 값은 환경 변수에 두지 않고 별도 저장소에서 조회하는 편이 안전합니다.

시크릿과 파라미터 스토어 차이

Systems Manager 파라미터 스토어(Parameter Store)와 언제 무엇을 쓰는지 비교합니다

AWS에는 비밀값을 담을 수 있는 서비스가 두 개 이상 있어서, 처음 쓰는 팀은 Systems Manager 파라미터 스토어(Parameter Store)와 Secrets Manager 중 무엇을 골라야 하는지 자주 헷갈립니다. 둘 다 값을 암호화해 보관하고 권한을 걸 수 있지만 태생이 다르고, 그래서 잘하는 일도 다릅니다.

건물에 모든 직원이 쓰는 공용 사물함과, 대표 서명이 있어야 열리는 법인 금고가 함께 있다고 생각해 봅니다. 공용 사물함은 설정표나 기능 스위치, 접속 주소처럼 여럿이 공유하는 값을 빠르게 꺼내 쓰기 좋고, 법인 금고는 열쇠 하나가 곧 권한인 값을 좁은 인원에게만 다루게 합니다.

파라미터 스토어는 앞의 사물함에 가까워서 일반 설정값과 보안 문자열(SecureString)을 함께 두고 저렴하게 많이 담을 수 있지만, 내장된 자동 교체 기능은 제한적입니다. Secrets Manager는 뒤의 금고에 가까워서 데이터베이스 자격 증명의 자동 교체와 교체 시 대상 시스템 반영, 세밀한 감사에 강점이 있고 그만큼 비용이 더 듭니다.

정리하면 공용 설정값과 단순한 비밀값은 파라미터 스토어, 주기적 교체와 감사가 필요한 자격 증명은 Secrets Manager를 고르는 것이 일반적인 기준입니다. 다만 리전별 지원 범위와 요금은 환경마다 다르므로 도입 전에 공식 문서로 확인해야 합니다.

시크릿과 KMS 키의 차이

암호화하는 키와 그 키로 보호되는 값이 어떻게 다른지 구분합니다

서버 소스 코드에 데이터베이스 비밀번호를 그대로 적어 두면, 저장소를 열람할 수 있는 사람이나 백업 파일을 손에 넣은 사람이 그대로 로그인할 수 있습니다. 그래서 값은 코드 밖에 따로 보관하고 필요할 때만 꺼내 쓰는 시크릿 관리가 등장했는데, 그 설명에는 늘 KMS 키라는 이름이 함께 따라붙어 둘을 같은 것으로 오해하기 쉽습니다.

회사 금고와 그 금고의 열쇠를 떠올리면 관계가 분명해집니다. 금고 안에는 현금과 서류, 즉 데이터베이스 비밀번호나 API 키 같은 값이 들어 있으며 이것이 시크릿입니다.

금고 문을 잠그고 여는 열쇠는 금고 밖의 별도 열쇠 관리소에 맡겨 두는데, 이 열쇠가 KMS(Key Management Service, 암호화 키를 관리하는 서비스) 키입니다. 금고를 열어 내용물을 꺼내 오는 일이 시크릿 조회이고, 열쇠 관리소에 열쇠 사용 허가를 요청해 잠금을 푸는 일이 KMS의 복호화 호출입니다.

정리하면 시크릿은 보호받는 값 그 자체이고, KMS 키는 그 값을 암호화하고 다시 풀어내는 데 쓰이는 자격 증명입니다. 둘은 서로 대신할 수 있는 관계가 아니라 보호되는 것과 보호하는 수단의 관계입니다.

리전 종속 서비스라는 전제

시크릿이 리전마다 따로 존재한다는 기본 성질을 설명합니다

서울 리전에서 만들어 둔 데이터베이스 비밀번호를 도쿄 리전에 배포한 애플리케이션이 읽으려 하면, 이름도 계정도 맞는데 값이 없다는 오류를 만나게 됩니다. 리전이 다르면 같은 이름의 시크릿도 서로 다른 존재로 취급된다는 사실을 모르면 원인을 찾는 데 오래 걸립니다.

전국에 지점을 둔 은행을 생각하면 이해가 쉽습니다. 각 지점은 자기 금고와 자기 장부만 관리하고, 다른 지점의 금고 열쇠나 고객 명단을 대신 보관하지 않습니다.

AWS의 리전도 이와 같은 독립된 금고실이어서, 시크릿은 만들어진 리전 안에서만 존재하고 그 리전의 엔드포인트(endpoint, 접속 주소)를 통해서만 접근됩니다. 그래서 같은 서비스를 여러 리전에 두었다면 리전마다 같은 시크릿을 따로 만들어 각각 관리해야 하며, 값을 한 곳에서 고쳤다고 다른 리전이 자동으로 따라 바뀌지도 않습니다.

결국 시크릿은 리전에 묶여 사는 자원이고, 계정과 리전과 이름 세 가지가 모여야 하나의 시크릿을 가리키게 됩니다. 이 성질을 전제에 두고 복제와 동기화를 설계해야 합니다.

시크릿 보관료와 API 호출료가 어떻게 청구되는지 설명합니다

시크릿을 몇 개 만들어 두었을 뿐인데 매달 청구서에 항목이 생기고, 서비스가 커지자 호출량 때문에 금액이 눈에 띄게 늘어 당황하는 경우가 많습니다. 비용이 어디서 발생하는지 미리 알면 어떤 값을 시크릿으로 옮기고 어떤 값은 다른 수단에 둘지 판단할 수 있습니다.

전월세와 택배비를 나눠 생각하는 것과 비슷합니다. 시크릿을 하나 만들어 보관하고 있는 동안 발생하는 금액은 방을 계속 빌려 쓰는 월세처럼 개수와 시간에 따라 붙고, 애플리케이션이 값을 꺼내 갈 때마다 발생하는 금액은 택배를 부칠 때마다 내는 운임처럼 호출 건수에 따라 붙습니다.

그래서 시크릿을 수백 개 만들어 두고 거의 쓰지 않으면 보관 쪽 요금이, 하나의 시크릿을 매우 자주 조회하면 호출 쪽 요금이 커집니다. 구체적인 단가와 무료 구간은 시점과 리전에 따라 달라지므로 설계 전에 공식 요금표를 직접 확인해야 하며, 같은 값을 반복해서 읽는 코드는 캐싱(caching, 한 번 읽은 값을 잠시 들고 재사용하는 것)으로 호출 수를 줄이는 편이 좋습니다.

정리하면 요금은 시크릿을 보관하는 동안의 월별 요금과 API 호출 요금이라는 두 축으로 구성됩니다. 개수와 호출 빈도를 함께 관리하는 것이 비용 관리의 핵심입니다.

학습 로드맵

앞으로 배울 순서와 각 단계에서 무엇을 할 수 있게 되는지 정리합니다

시크릿 관리라는 말을 처음 들으면 무엇부터 손대야 할지 막막하고, 문서를 펼치면 ARN과 KMS와 IAM이 한꺼번에 쏟아져 더 혼란스럽습니다. 순서를 정해 두면 각 단계에서 무엇을 할 수 있게 되는지가 분명해져 훨씬 덜 헤맵니다.

운전을 배울 때 실내 조작, 주차 연습, 도로 주행 순으로 나아가는 것과 같습니다. 첫 단계에서는 콘솔에서 시크릿을 하나 만들고 값을 넣고 꺼내 보면서 시크릿이 어떤 모양의 자원인지 익힙니다. 다음 단계에서는 코드와 서버가 권한을 갖고 값을 읽어 가도록 IAM(Identity and Access Management, 접근 권한을 관리하는 서비스) 정책을 붙이는 법을 배웁니다. 그다음에는 값을 자동으로 돌려주는 교체(rotation)와 KMS 키로 감싸는 암호화, 여러 리전에 걸친 복제로 넓혀 갑니다.

각 단계는 앞 단계를 실제로 해 보았다는 전제 위에 서므로, 건너뛰면 뒤에서 만나는 오류의 의미를 읽어 낼 수 없습니다.

결국 이 주제의 학습은 시크릿을 만들고 꺼내는 감각에서 출발해 권한과 자동화로 확장되는 하나의 경로입니다. 단계마다 직접 손으로 확인하며 넘어가는 것이 가장 빠른 길입니다.

시크릿 ARN 구조 읽기

ARN의 각 조각이 리전·계정·이름을 어떻게 담는지 해부합니다

오류 메시지에 arn:aws:secretsmanager:...로 시작하는 긴 문자열이 등장하면 어디서 문제가 생겼는지 읽어 낼 수 없어 그대로 검색에 붙여 넣게 됩니다. 이 문자열의 각 조각만 알면 리전이 틀렸는지 계정이 틀렸는지 이름이 틀렸는지를 즉시 가려낼 수 있습니다.

택배 송장을 떠올리면 구조가 그대로 보입니다.

송장 맨 앞의 arn은 이것이 AWS 자원을 가리키는 식별자(ARN, Amazon Resource Name)임을 알리는 표시이고, 이어지는 aws는 파티션(partition, 상용·중국·정부용처럼 나뉜 AWS 영역)이며, secretsmanager는 어느 서비스의 자원인지를 적은 칸입니다. 그다음 ap-northeast-2 같은 조각은 도착지 리전, 열두 자리 숫자는 그 자원을 소유한 계정 번호입니다. 마지막 secret:prod/db-AbCdEf는 secret:이라는 자원 종류 표시 뒤에 시크릿 이름과 시스템이 붙인 임의의 여섯 글자 꼬리표가 이어진 형태로, 같은 이름을 다시 만들어도 이 꼬리표 때문에 서로 다른 자원이 됩니다.

정리하면 ARN은 파티션, 서비스, 리전, 계정, 자원 이름이 콜론으로 구분되어 늘어선 주소입니다. 권한 정책이나 다른 서비스에 시크릿을 지정할 때는 이 전체 문자열을 정확히 써야 합니다.

시크릿 이름 규칙

이름에 쓸 수 있는 문자와 /prod/db 같은 경로 형식을 설명합니다

이름을 prod/db/password처럼 정해 두었는데 코드에서는 prod-db-password로 적어 조회에 실패하는 일이 흔합니다. 이름은 사람이 붙이는 표시가 아니라 자원을 찾는 주소의 일부이므로, 허용되는 문자와 형식을 미리 알아 두어야 합니다.

아파트 단지의 동 번호와 호수 표기를 떠올리면 편합니다. 관리 규칙상 쓸 수 있는 글자가 정해져 있고, 층과 호수를 구분하는 구분자(separator)를 넣어 위치를 계층처럼 표현합니다. 시크릿 이름도 영문 대소문자와 숫자, 그리고 /, _, +, =, ., @, - 같은 일부 기호만 쓸 수 있으며 전체 길이에도 상한이 있습니다.

여기서 /는 단순한 글자가 아니라 경로를 나누는 구분자로 동작하므로, prod/db와 prod/db/password는 서로 다른 위치의 이름이 되고 콘솔에서도 폴더처럼 묶여 보입니다. 이름은 만든 뒤에 바꿀 수 없고, 지운 이름도 곧바로 다시 쓸 수 없는 경우가 있어 처음 정할 때 신중해야 합니다.

결국 시크릿 이름은 환경과 용도를 경로로 나눠 담는 식별자이며, 허용 문자와 길이 제한을 지켜야 조회가 성립합니다. 이름을 주소처럼 다루는 습관이 이후 권한 설계를 훨씬 단순하게 만듭니다.

버전(Version) 개념

시크릿 하나가 여러 개의 값을 동시에 가질 수 있는 구조를 설명합니다

서비스의 데이터베이스 비밀번호를 바꾸는 순간, 그 값을 쓰던 프로그램들이 한꺼번에 인증에 실패하며 장애가 시작됩니다. 새 값으로 바꾸는 일도, 옛 값으로 되돌리는 일도 두렵다면 그 문제를 풀기 위해 Amazon Secrets Manager는 시크릿 하나의 값을 덮어쓰지 않고 여러 개의 버전(Version)으로 나누어 보관합니다. 도서관에서 한 권의 책을 개정판이 나올 때마다 새 책으로 갈아치우지 않고, 같은 제목 아래 1판과 2판, 3판을 나란히 꽂아 두는 것과 같습니다. 책등에는 판을 구분하는 번호가 붙고, 대출대 앞에는 지금 빌려주는 판을 가리키는 표지가 놓입니다. 사서는 새 판을 꽂으면서 표지만 새 판 쪽으로 옮기고, 이전 판은 버리지 않고 서고에 남겨 둡니다. 그래서 새 판에서 오류가 발견되면 표지만 되돌려 곧바로 이전 판을 다시 빌려줄 수 있습니다.

정리하면 시크릿의 버전이란 하나의 시크릿 안에 시간 순으로 쌓이는 값의 세대이며, Secrets Manager는 값을 덮어쓰지 않고 새 버전을 추가하고 레이블로 어느 세대를 쓸지 지정합니다.

버전 ID(Version ID) 이해

버전마다 붙는 32자 식별자가 어떤 역할을 하는지 설명합니다

두 사람이 같은 시크릿의 값을 동시에 바꾸면, 나중에 어느 값이 언제 만들어졌는지 알 길이 없어 장애 원인을 찾는 데 몇 시간이 걸립니다. 그래서 Secrets Manager는 값을 저장할 때마다 사람이 붙인 이름이 아니라 시스템이 만든 고유한 식별자를 함께 남깁니다. 같은 주소로 여러 번 택배를 보내도 송장 번호가 매번 달라서, 어느 상자가 언제 보낸 것인지 정확히 집어낼 수 있습니다. 시크릿의 버전 ID(Version ID)도 이 송장 번호와 같아서, 32자리의 문자와 숫자로 이루어진 값이 버전 하나에 하나씩 붙습니다. 택배 기사가 주소만 보고 상자를 찾듯 사람은 AWSCURRENT 같은 레이블로 값을 꺼내지만, 문제를 추적할 때는 송장 번호에 해당하는 버전 ID로 그 상자를 정확히 지목합니다. 번호는 한 번 쓰이면 다른 버전에 다시 붙지 않으므로, 기록만 있으면 언제든 그때의 값을 그대로 되살릴 수 있습니다.

결국 버전 ID는 시크릿 값 하나하나에 부여되는 변경되지 않는 식별자이며, 사람이 읽는 레이블과 짝을 이루어 값의 이력을 정확히 가리키는 역할을 합니다.

스테이징 레이블(Staging Label)

레이블이 특정 버전을 가리키는 표지 역할을 한다는 점을 설명합니다

새 비밀번호를 저장했는데 프로그램이 계속 옛 비밀번호를 읽어 인증에 실패하는 일이 있습니다. 값은 분명히 저장됐지만 어느 값이 지금 써야 할 값인지 알려 주는 장치가 없었기 때문이고, Secrets Manager는 스테이징 레이블(Staging Label)이라는 표지로 그 문제를 해결합니다. 식당 입구에 걸린 오늘의 메뉴 표지판을 떠올리면 이해가 쉽습니다. 주방에서 요리가 바뀌어도 표지판은 늘 같은 자리에 걸려 있고, 손님은 표지판이 가리키는 요리만 주문하면 됩니다. 스테이징 레이블도 이와 같아서, 레이블 자체는 고정된 이름이지만 그 이름이 가리키는 버전은 새 값을 저장할 때마다 다른 버전으로 옮겨 갑니다. 프로그램은 버전 ID를 직접 외우지 않고 레이블 이름만 부르면 되므로, 값이 바뀌어도 코드를 고칠 필요가 없습니다.

정리하면 스테이징 레이블은 특정 버전을 가리키는 이동 가능한 표지이며, 애플리케이션은 레이블을 통해 값의 실제 위치를 몰라도 항상 원하는 버전을 얻습니다.

정리하면 커스텀 스테이징 레이블은 사용자가 정의한 이름으로 버전을 가리키는 표지이며, 하나의 시크릿에 여러 환경의 값을 나누어 담는 수단입니다.

시크릿 페이로드 형식

사용자 이름과 비밀번호를 하나의 문자열로 이어 붙여 저장하면, 나중에 프로그램이 그 문자열을 다시 쪼개야 하고 형식이 조금만 달라져도 값을 읽지 못합니다. 결국 시크릿 페이로드 형식은 값을 어떤 모양으로 담아 둘지 정하는 규칙이며, 여러 항목을 다룰 때는 키-값 JSON을 쓰는 것이 읽기와 활용 모두에 유리합니다.

시크릿 메타데이터와 태그

설명과 태그로 시크릿을 찾고 분류하는 방법을 설명합니다

시크릿이 두세 개일 때는 이름만으로도 충분하지만 수십 개를 넘어가면 어느 것이 결제 서비스용이고 어느 것이 테스트 환경용인지 사람이 기억으로 구분해야 합니다. 결국 담당자가 바뀌는 순간 잘못된 시크릿을 골라 쓰는 사고가 생기고, 이를 막으려고 Amazon Secrets Manager는 시크릿마다 설명(description)과 태그(tag)를 붙이는 수단을 제공합니다.

아파트 택배 보관함을 떠올리면 구조가 그대로 겹칩니다. 보관함 칸마다 붙은 호수와 이름이 시크릿 이름이고, 칸 앞에 붙여 둔 짧은 메모가 설명이며, 색깔 스티커처럼 붙였다 떼는 분류 표시가 태그입니다. 입주민은 호수만 보고도 찾지만 관리인은 스티커를 기준으로 같은 종류의 칸을 한꺼번에 골라낼 수 있고, 메모 덕분에 처음 온 사람도 이 칸이 무엇을 담는지 바로 압니다.

태그는 키와 값의 짝으로 여러 개 붙일 수 있어서, 예를 들어 환경이라는 키에 운영이라는 값을 달아 두면 운영용 시크릿만 모아 조회하거나 접근 권한을 나눌 때 기준으로 쓸 수 있습니다.

정리하면 시크릿의 이름은 식별자이고, 설명은 사람이 읽는 안내문이며, 태그는 검색과 분류와 권한 부여에 쓰이는 꼬리표입니다. 값 자체는 암호화되어 있어도 이 껍데기 정보는 평문으로 다뤄지므로, 어떤 정보를 적어 둘지 처음부터 규칙을 정해 두는 편이 좋습니다.

정리하면 시크릿은 생성, 교체, 삭제 예약, 삭제라는 상태를 가지며, 교체는 값을 갈아 끼우는 절차이고 삭제 예약은 되돌릴 수 있는 마지막 유예입니다. 예약을 취소하면 다시 사용 상태로 돌아오므로, 지우기 전에 한 번 더 확인할 여지를 남겨 둔 설계라고 볼 수 있습니다.

AWS CLI로 시크릿 만들기

create-secret 명령의 필수 인자와 결과값을 설명합니다

같은 시크릿을 여러 환경에 똑같이 만들어야 하는데 콘솔에서 손으로 반복하면 이름을 잘못 적거나 값을 빠뜨리기 쉽습니다. 이런 반복 작업은 AWS CLI의 create-secret 명령처럼 한 줄로 끝나는 도구에 맡기는 편이 안전합니다.

택배를 보낼 때 접수 전표에 받는 사람과 내용물을 적어야 하는 것과 같습니다. create-secret에서 반드시 있어야 하는 것은 시크릿 이름이고, 여기에 키와 값의 짝을 담은 문자열이나 일반 문자열을 값으로 넘깁니다. 선택 항목으로 설명과 태그, 암호화에 쓸 키, 교체 설정을 함께 줄 수 있으며, 값은 명령 기록에 남지 않도록 파일로 넘기는 방식을 권합니다.

접수를 마치면 접수증처럼 응답이 돌아오는데, 그 안에는 시크릿의 고유 식별자(ARN)와 이름, 생성 시각이 담겨 이후 조회나 권한 부여에 쓰입니다.

정리하면 create-secret은 이름을 필수로 받고 값과 설명과 태그를 선택적으로 받으며, 응답으로 ARN과 이름과 생성 시각을 돌려줍니다. 값을 명령줄에 그대로 적으면 셸 기록에 남을 수 있으므로 파일이나 다른 입력 경로를 쓰는 습관이 필요합니다.

CloudFormation으로 시크릿 정의

템플릿으로 시크릿을 코드화하는 기본 방법을 설명합니다

콘솔에서 만든 시크릿은 누가 어떤 설정으로 만들었는지가 화면 기록에만 남아, 다른 리전에 같은 구성을 다시 만들려면 손으로 반복해야 합니다. CloudFormation 템플릿에 시크릿을 적어 두면 구성이 파일로 남고 같은 파일로 몇 번이든 같은 결과를 만들 수 있습니다.

집을 지을 때 도면을 먼저 그리는 것과 같습니다. 템플릿은 어떤 자원을 만들지 적은 도면이고, 그 안의 시크릿 자원에는 이름과 설명과 태그, 암호화 키, 교체 설정 같은 항목을 속성으로 적습니다. 도면에 값을 그대로 적어 두면 저장소에 평문이 남으므로, 템플릿에는 시크릿의 골격만 적고 값은 다른 경로로 넣는 방식이 일반적입니다.

스택(템플릿 하나로 만들어진 자원 묶음)을 만들면 도면대로 자원이 생기고, 스택을 지우면 그 안의 시크릿도 함께 정리되어 손으로 만든 것보다 남는 것을 줄일 수 있습니다.

정리하면 CloudFormation에서는 시크릿도 템플릿의 자원으로 선언하고, 이름과 태그와 교체 설정 같은 속성을 코드로 관리합니다. 이렇게 해 두면 같은 정의를 여러 환경에 반복 적용하면서도 변경 이력을 파일로 남길 수 있습니다.

CloudFormation에서 값 채우기

비밀번호를 템플릿에 남기지 않고 런타임에 값을 넣는 방법을 설명합니다

템플릿에 데이터베이스 비밀번호를 그대로 적어 두면 그 파일이 저장소에 올라가는 순간 비밀번호도 함께 공개됩니다. 그래서 템플릿에는 값의 자리만 만들고, 스택을 만들 때 값을 넣도록 분리하는 방식이 쓰입니다.

이삿짐을 보낼 때 박스에 품목표만 붙이고 내용물은 도착한 뒤에 채우는 방식과 같습니다. 템플릿은 시크릿이라는 박스와 이름표만 정의하고, 값은 스택을 만들 때 입력 파라미터로 받거나 외부 참조로 넘깁니다. 파라미터로 값을 받는 방법도 있지만 그 값이 기록에 남을 수 있으므로 값을 가리는 옵션(NoEcho)을 함께 켜야 하고, 더 안전하게는 스택 생성 후 별도 절차로 값을 채우거나 다른 저장소를 참조하도록 구성합니다.

어떤 방식을 택하든 템플릿 파일 자체에는 비밀번호가 남지 않는다는 점이 핵심입니다.

정리하면 CloudFormation에서는 시크릿의 골격만 템플릿에 두고 실제 값은 배포 시점에 파라미터나 외부 참조, 후속 절차로 주입합니다. 이렇게 나누면 구성은 코드로 추적하면서 값은 코드 바깥에 두는 원칙을 지킬 수 있습니다.

3부. 시크릿 생성과 값 관리025

시크릿 값 조회하기

get-secret-value로 값을 읽는 방법과 응답 구조를 설명합니다

데이터베이스 비밀번호를 프로그램 코드 안에 적어 두면 값을 바꿀 때마다 코드를 고쳐 다시 배포해야 하고, 어느 서버가 아직 옛 값을 들고 있는지도 찾기 어렵습니다. Amazon Secrets Manager(시크릿 관리 서비스)에 값을 맡겨 두고 필요할 때만 꺼내 쓰면 이런 일이 줄어들며, 실제로 값을 꺼내는 동작을 맡는 명령이 get-secret-value(시크릿 값 조회)입니다.

아파트 입구의 무인 택배 보관함을 떠올리면 구조가 쉽게 잡힙니다. 집주인은 보관함 번호와 비밀번호만 알면 되고, 택배기사는 물건을 넣을 때마다 새 배송 기록을 남깁니다.

get-secret-value는 보관함 번호에 해당하는 시크릿 이름이나 ARN(자원을 가리키는 고유 주소)을 넘겨 칸을 여는 일이고, 돌아오는 응답에는 물건 자체인 SecretString(문자열 형태의 값) 또는 SecretBinary(이진 형태의 값)와 함께 VersionId(버전 식별자), CreatedDate(만들어진 시각)가 배송 기록처럼 함께 실려 옵니다. 그래서 값만 받는 것이 아니라 언제 넣은 어느 버전을 꺼냈는지까지 같이 확인하게 됩니다.

정리하면 get-secret-value는 시크릿 이름이나 ARN을 열쇠로 값을 읽고 그 값과 버전 정보를 한 응답에 담아 돌려주는 조회 API입니다. 호출 권한을 읽기 전용으로 좁혀 두면 값이 새어 나갈 통로를 줄일 수 있습니다.

시크릿 값 갱신하기

put-secret-value로 새 버전을 추가하는 방법을 설명합니다

비밀번호를 바꾸는 일은 생각보다 번거롭습니다. 여러 시스템에 같은 값을 손으로 옮겨 적다 보면 한 곳만 빠뜨려도 로그인이 실패하고, 어느 쪽이 최신인지도 금세 헷갈립니다. Secrets Manager는 값을 고칠 때 기존 값을 덮어쓰지 않고 새 버전으로 쌓아 올리며, 그 역할을 put-secret-value(시크릿 값 갱신)가 맡습니다.

무인 택배함에 새 택배를 넣는 상황과 비슷합니다. 기사는 칸에 물건을 넣고 '현재 배송' 표찰을 붙이며, 바로 앞의 물건은 버려지지 않고 '이전 배송' 표찰로 자리만 옮깁니다.

put-secret-value도 새 값을 넣으면서 VersionStage(버전에 붙는 표찰)를 AWSCURRENT로 달고, 직전 버전에는 AWSPREVIOUS를 붙여 남겨 둡니다. 덕분에 새 값으로 문제가 생기면 이전 표찰이 붙은 버전을 다시 현재로 되돌려 복구할 수 있습니다.

요약하면 put-secret-value는 기존 시크릿을 지우지 않고 새 버전을 추가하며, 어느 버전이 현재인지를 표찰로 관리하는 갱신 API입니다.

오래된 버전 정리

더 이상 쓰지 않는 버전을 지우는 조건과 주의점을 설명합니다

값을 자주 바꾸는 시크릿은 버전이 계속 쌓여, 어느 것이 지금 쓰이는지 눈으로 구분하기 어려워집니다. 게다가 오래된 버전에 옛 비밀번호가 그대로 남아 있으면 이미 폐기한 줄 알았던 값이 여전히 열쇠로 동작할 수 있습니다. 그래서 Secrets Manager에서는 더 이상 쓰지 않는 버전에 붙은 표찰을 떼어 접근 대상에서 빼는 정리가 필요합니다.

창고에 쌓인 옛 택배 상자를 생각하면 이해가 쉽습니다. 최근 상자에는 '현재' 표찰을 붙여 두고, 오래된 상자는 표찰을 떼어 목록에서 보이지 않게 만드는 식입니다.

표찰이 하나도 없는 버전은 더 이상 현재나 이전 버전으로 지목될 수 없어, 꺼내 쓰는 경로에서 사실상 빠지게 됩니다. 다만 버전을 곧바로 지우는 전용 명령이 있는지, 표찰을 뗀 버전이 언제 완전히 사라지는지는 환경과 문서 버전에 따라 다르므로 단정하지 말고 확인이 필요합니다. 핵심은 오래된 값을 방치하지 말고 표찰 관리로 접근 범위를 좁혀 두는 것이며, 이를 정기 점검 항목으로 두는 편이 안전합니다.

시크릿 이름 변경

이름을 바꾸면 ARN이 어떻게 달라지는지 설명합니다

시크릿 이름을 대충 붙여 두면 나중에 용도를 알아보기 어려워지고, 담당자가 바뀌면 어느 것이 운영용인지 찾느라 시간을 씁니다. 그래서 이름을 정리하려는 순간, 그 이름으로 접근하던 프로그램이 한꺼번에 멈출 수 있다는 점이 문제로 떠오릅니다. Secrets Manager에서 시크릿의 이름을 바꾸면 그 이름을 포함한 ARN(자원을 가리키는 고유 주소)도 함께 바뀝니다.

이사하면서 집 주소가 달라지는 상황과 같습니다. 짐은 그대로 있고 사는 사람도 그대로지만, 우편은 새 주소로만 도착하며 옛 주소로 보낸 편지는 돌아옵니다.

마찬가지로 이름을 바꾸면 옛 ARN으로 호출하던 코드는 값을 찾지 못하고, 그 ARN을 적어 둔 권한 정책도 대상을 잃게 됩니다. 게다가 비워진 옛 이름을 다른 시크릿이 차지할 수 있어, 옛 이름으로 부르던 호출이 엉뚱한 값을 받아 갈 위험도 있습니다. 정리하면 이름 변경은 값이 아니라 식별자가 바뀌는 작업이므로, 새 ARN을 권한 정책과 호출 코드에 함께 반영하고 옛 이름을 재사용하지 않도록 막아 두는 것이 핵심입니다.

삭제 예약과 복구

삭제 대기 기간 동안 값을 되살리는 방법을 설명합니다

운영 중인 시크릿을 잘못 지우면 인증이 한꺼번에 실패해 서비스가 멈추고, 값을 다시 만들려면 관련 시스템을 하나씩 돌며 새 비밀번호를 배포해야 합니다. 손이 미끄러진 한 번의 삭제가 하루치 장애로 이어지는 셈이라, Secrets Manager는 곧바로 지우지 않고 삭제를 예약해 두는 방식을 씁니다.

아파트 이사 예약과 비슷합니다. 관리사무소에 퇴거를 신청하면 바로 나가야 하는 것이 아니라 정해진 유예 기간이 지나야 계약이 끝나고, 그 사이에 마음이 바뀌면 신청을 취소하면 그만입니다.

delete-secret(시크릿 삭제)를 호출할 때 복구 기간을 정하면 그동안 시크릿은 삭제 대기 상태로 남아 값을 읽을 수 없고, 이 기간에 restore-secret(시크릿 복구)를 호출하면 원래 값과 버전이 그대로 되살아납니다. 유예 기간이 지나면 값은 사라지며, 같은 이름으로 다시 만들더라도 예전 값이 돌아오지는 않습니다.

결국 삭제 예약은 지우는 동작에 되돌릴 시간을 붙여 둔 장치이고, 복구 기간 설정과 복구 권한을 누가 가질지 정해 두는 것이 안전한 운영의 출발점입니다.

IAM 정책으로 접근 제어하기

누가 어떤 시크릿을 읽을 수 있는지 정하는 기본 구조를 설명합니다

여러 팀이 하나의 클라우드 계정을 함께 쓰는 환경에서 데이터베이스 비밀번호를 아무나 열람할 수 있다면 유출 사고는 시간문제가 됩니다. Amazon Secrets Manager는 시크릿(Secret, 비밀번호나 API 키처럼 노출되면 안 되는 값)을 한곳에 보관하고, IAM 정책(Policy, 누가 무엇에 어떤 동작을 할 수 있는지 적어 둔 권한 문서)으로 열람 범위를 통제합니다.

회사 건물의 출입 통제를 떠올리면 구조가 그대로 겹칩니다. 정책 문서는 층별로 누가 어느 방에 들어갈 수 있는지 적어 둔 출입 규칙표이고, 요청을 보내는 사용자나 서비스는 사원증을 찍는 사람이며, 시크릿의 ARN(리소스를 가리키는 고유 주소)은 몇 층 몇 호실인지를 나타냅니다. 규칙표에는 "이 사원증으로 이 호실의 문을 열 수 있다"처럼 동작(Action)과 대상(Resource)을 짝지어 적고, 허용(Allow)과 거부(Deny)를 함께 표시합니다.

사원증을 찍었을 때 규칙표에 허용이 적혀 있으면 문이 열리고, 아무 줄도 없거나 거부가 적혀 있으면 기본적으로 닫힌 채로 남습니다.

정리하면 Secrets Manager의 접근 제어는 요청 주체, 대상 시크릿, 허용된 동작을 정책 문서에 명시하고 그 조합이 맞을 때만 값을 돌려주는 구조입니다. 권한을 계정 전체가 아니라 시크릿 단위까지 좁혀서 줄 수 있다는 점이 핵심입니다.

리소스 기반 정책

시크릿에 직접 붙는 정책과 IAM 정책이 어떻게 다른지 비교합니다

새로 만든 서비스가 다른 팀 계정의 시크릿을 읽어야 하는데, 그 팀의 사용자 목록을 일일이 고치지 않고 해결하고 싶을 때가 있습니다. 이때 쓰는 것이 리소스 기반 정책(Resource-based Policy)이며, 권한을 사람에게 붙이는 대신 시크릿이라는 자원 자체에 붙이는 방식입니다.

같은 건물이라도 사원증에 권한을 적는 방식과, 방문 앞에 "이 명단에 있는 사람은 들어올 수 있음"이라는 종이를 붙이는 방식의 차이와 같습니다. IAM 정책(신원 기반 정책, Identity-based Policy)은 사원증을 가진 사람 쪽에 붙어서 그 사람이 어디까지 갈 수 있는지를 정하고, 리소스 기반 정책은 시크릿 문 앞에 붙어서 누구를 들여보낼지 자원 쪽에서 결정합니다. 그래서 리소스 기반 정책에는 어느 계정의 어떤 주체(Principal)를 허용하는지 적을 수 있어, 상대 계정의 사용자 목록을 고치지 않아도 접근을 열어 줄 수 있습니다.

두 정책이 함께 걸려 있으면 요청은 양쪽 조건을 모두 만족해야 통과하고, 명시적 거부는 어느 한쪽에만 있어도 즉시 막힙니다.

정리하면 신원 기반 정책은 "누가"에, 리소스 기반 정책은 "무엇이"에 권한을 적는 차이이며, Secrets Manager에서는 시크릿에 직접 정책을 붙여 교차 계정 접근을 여는 데 주로 씁니다. 어느 쪽이든 최종 판단은 두 정책을 합쳐서 이루어진다는 점을 기억하면 됩니다.

교차 계정 접근

다른 계정의 시크릿을 쓰게 만드는 설정 절차를 설명합니다

서비스가 늘어나면서 계정을 업무별로 나눠 두면, 결제 계정의 애플리케이션이 데이터 계정의 시크릿을 읽어야 하는 일이 생깁니다. 교차 계정 접근(Cross-account Access)은 이렇게 서로 다른 AWS 계정 사이에서 시크릿을 안전하게 주고받도록 설정하는 절차입니다.

이웃한 두 회사 건물 사이에 통행증을 주고받는 절차와 비슷합니다.

  • 먼저 시크릿을 가진 쪽(소유 계정)이 시크릿에 리소스 기반 정책을 붙여 상대 계정의 역할(Role, 필요할 때 잠시 빌려 쓰는 권한 신분)을 명시적으로 허용합니다.
  • 다음으로 시크릿을 쓰려는 쪽(사용 계정)의 역할에 그 시크릿을 읽는 권한과 상대 역할로 전환하는 권한을 부여합니다.
  • 마지막으로 시크릿이 고객 관리형 KMS 키로 암호화되어 있다면 그 키 정책에서도 상대 계정의 사용을 허용해야 복호화가 되며, 세 관문이 모두 열려야 값이 실제로 반환됩니다.

정리하면 교차 계정 접근은 시크릿 정책, 사용 계정의 역할 권한, KMS 키 정책이라는 세 지점을 함께 열어 주는 설정입니다. 하나라도 빠지면 접근 거부 오류가 난다는 점이 실무에서 가장 자주 걸리는 부분입니다.

VPC 엔드포인트로 접근 제한

사설 경로로만 접근하도록 인터페이스 엔드포인트를 구성하는 방법을 설명합니다

시크릿을 인터넷 구간을 거쳐 가져오면 경로 어딘가에서 트래픽을 들여다보거나 가로챌 여지가 남습니다. VPC 엔드포인트(VPC Endpoint)는 프라이빗 서브넷의 자원이 인터넷을 거치지 않고 AWS 서비스에 닿게 하는 사설 연결 통로입니다.

회사 건물과 옆 건물을 잇는 지하 전용 통로를 상상하면 이해가 쉽습니다. 인터페이스 엔드포인트(Interface Endpoint)는 서브넷 안에 사설 IP를 가진 네트워크 인터페이스를 만들어, Secrets Manager의 주소가 공인 인터넷 대신 그 사설 주소로 해석되게 합니다. 통로 입구에는 보안 그룹(Security Group, 출입을 허용할 포트와 대상을 적은 방화벽 규칙)을 걸어 어떤 자원이 들어올 수 있는지 제한하고, 엔드포인트 정책으로 어느 시크릿까지 허용할지 한 겹 더 좁힐 수 있습니다.

이렇게 하면 시크릿 요청은 사설 네트워크 안에서만 흐르고 인터넷 게이트웨이나 NAT를 거치지 않습니다.

정리하면 VPC 엔드포인트는 시크릿 접근 경로를 사설 네트워크로 한정해, 권한 설정과 별개로 네트워크 수준에서 한 번 더 접근을 제한하는 수단입니다.

최소 권한 원칙 적용

필요한 권한만 주는 설계를 어떻게 하는지 설명합니다

개발 편의를 위해 팀 전체에 관리자 권한을 주면, 한 사람의 키가 새는 순간 계정 전체가 위험해집니다. 최소 권한 원칙(Principle of Least Privilege)은 업무에 꼭 필요한 만큼만, 필요한 동안만 권한을 주는 설계 방식입니다.

호텔에서 청소 직원과 투숙객에게 같은 마스터키를 주지 않는 것과 같습니다.

  • 먼저 그 주체가 실제로 어떤 시크릿을 어떤 동작으로 쓰는지 목록을 만들고, 시크릿 ARN을 개별로 지정해 범위를 좁힙니다.
  • 다음으로 와일드카드 대신 필요한 동작만 적고, 조건(Condition)으로 요청 시점의 네트워크나 태그를 제한합니다.
  • 마지막으로 일정 기간 쓰이지 않은 권한을 걷어내는 점검을 반복하면 권한은 실제 사용량에 맞춰 줄어듭니다.

정리하면 최소 권한은 정책에 필요한 리소스와 동작만 남기고, 조건과 주기적 점검으로 그 범위를 계속 좁혀 가는 운영 습관입니다. 한 번 정해 두고 끝내는 설정이 아니라 사용 기록을 보며 다듬는 과정이라는 점이 중요합니다.

주요 IAM 액션 목록

GetSecretValue 같은 액션들이 각각 무엇을 허용하는지 정리합니다

시크릿 권한을 넓게 주면 읽기만 필요한 서비스가 값을 바꾸거나 지울 수도 있게 됩니다. 그래서 IAM 정책에는 어떤 동작(Action)을 허용하는지 하나씩 적어야 하며, Secrets Manager는 동작별로 권한을 나눠 둡니다.

도서관 창구 업무가 열람, 대출, 신착 등록, 폐기로 나뉘어 있는 것과 같습니다. GetSecretValue는 시크릿의 실제 값을 복호화해 돌려주는 가장 강한 읽기 동작이고, DescribeSecret은 값 없이 이름과 설명, 교체 여부 같은 정보만 보여 줍니다. ListSecrets는 계정 안의 시크릿 이름 목록을 훑는 동작이며, CreateSecret과 PutSecretValue, UpdateSecret은 새 시크릿을 만들거나 새 값 버전을 저장하고 설명을 고치는 쓰기 동작입니다. DeleteSecret은 삭제를 예약하고 RestoreSecret은 그 예약을 취소하며, GetResourcePolicy와 PutResourcePolicy는 시크릿에 붙는 정책을 읽고 바꾸고 TagResource는 분류용 태그를 다루는데, 값이 KMS 키로 암호화되어 있으므로 kms:Decrypt 권한이 함께 있어야 GetSecretValue가 성공합니다.

정리하면 시크릿 권한은 값 읽기, 정보 조회, 목록 조회, 쓰기, 삭제, 정책과 태그 관리로 나뉘며, 필요한 동작만 골라 부여하는 것이 안전합니다. 특히 값을 읽는 권한과 값을 쓰는 권한을 분리해 두면 사고 범위를 크게 줄일 수 있습니다.

조회 권한을 좁히는 패턴

경로와 태그 조건으로 권한 범위를 줄이는 방법을 설명합니다

시크릿을 하나의 계정에 모아 두면, 개발자 한 명에게 읽기 권한을 주려다 계정 안의 모든 시크릿을 열어 주게 되는 일이 생깁니다. 그렇다고 권한을 아예 빼앗으면 배포가 멈추므로, Amazon Secrets Manager는 정책에 조건을 붙여 읽을 수 있는 범위만 잘라내는 방식을 제공합니다.

회사 문서고를 떠올려 보면, 문서고 전체 열쇠를 주는 대신 삼 층 동편 비 열까지만 열리는 열쇠를 주는 것과 같습니다. 여기서 경로 조건은 캐비닛 서랍의 이름표에 해당하며, 정책의 Resource에 시크릿 ARN 뒤쪽 경로를 적어 그 아래에 있는 것만 허용합니다. 태그 조건은 서류에 붙은 색 라벨에 해당하며, Condition에 aws:ResourceTag 조건을 걸어 특정 라벨이 붙은 서류만 꺼내게 합니다.

뒤쪽을 와일드카드로 열어 두면 그 아래 모든 서랍이 대상이 되므로, 허용 목록을 좁게 적고 필요한 경로만 늘리는 편이 안전합니다. 정리하면 Secrets Manager의 조회 권한은 IAM 정책의 Resource 경로 조건과 리소스 태그 조건으로 좁히며, 계정 전체 허용 대신 필요한 이름 규칙과 라벨만 허용하는 것이 핵심입니다.

KMS 권한과 시크릿 권한의 관계

값을 읽으려면 두 권한이 모두 필요하다는 점을 설명합니다

시크릿을 읽는 권한만 주면 될 것 같지만, 실제로 값을 꺼내려는 순간 권한 부족으로 거부되는 경우가 흔합니다. Amazon Secrets Manager의 시크릿 값은 AWS KMS(Key Management Service, 키 관리 서비스)로 암호화되어 있어서, 시크릿 접근 권한과 키 사용 권한이 함께 있어야 복호화가 됩니다.

은행 금고를 떠올려 보면, 금고실 문을 통과하는 출입증과 금고 문을 여는 열쇠가 따로 있는 구조와 같습니다. Secrets Manager의 GetSecretValue 권한은 금고실 출입증에 해당하고, KMS의 Decrypt 권한은 금고 문 열쇠에 해당합니다. 출입증이 있어도 열쇠가 없으면 금고 앞에서 멈추고, 반대로 열쇠만 있어도 금고실에 들어갈 수 없습니다.

그래서 정책을 줄 때는 시크릿 ARN에 대한 허용과 그 시크릿이 쓰는 키 ARN에 대한 kms:Decrypt 허용을 한 쌍으로 맞춰 주어야 합니다. 결국 시크릿 값 조회는 IAM의 secretsmanager:GetSecretValue 권한과 KMS 키 정책 및 IAM의 kms:Decrypt 권한이 모두 충족될 때만 성공합니다.

서비스 연결 역할

교체와 복제에 쓰이는 자동 생성 역할의 정체를 설명합니다

Secrets Manager에서 자동 교체를 켜거나 시크릿을 다른 리전으로 복제하면, 사용자가 만들지 않은 역할이 어느새 목록에 나타납니다. 이것이 서비스 연결 역할(service-linked role)로, 서비스가 대신 작업을 수행하도록 미리 정의된 역할입니다.

아파트 위탁 관리 업체를 떠올려 보면, 입주민이 아무에게나 마스터키를 넘기지 않고 관리 업체 직원증을 발급해 정해진 업무만 하게 하는 것과 같습니다. 서비스 연결 역할은 이 직원증처럼 AWS가 이름과 권한을 미리 정해 두고, 계정에서 처음 그 기능을 쓸 때 자동으로 만들어집니다. 역할의 신뢰 정책에는 secretsmanager.amazonaws.com 같은 서비스 주체만 올 수 있어 다른 사용자가 빌려 쓸 수 없고, 부여되는 권한도 교체용 함수 호출이나 복제에 필요한 범위로 한정됩니다.

그래서 이 역할을 직접 손보기보다는 역할이 만들어질 수 있도록 iam:CreateServiceLinkedRole 권한을 허용해 두는 편이 일반적입니다. 정리하면 서비스 연결 역할은 교체와 복제 같은 기능을 위해 AWS가 자동 생성하고 관리하는 전용 역할이며, 사용자는 그 존재와 부여 권한을 확인하고 생성 권한만 열어 주면 됩니다.

4부. 접근 제어와 권한 설계040

접근 거부 원인 추적

AccessDenied가 났을 때 어느 정책부터 확인해야 하는지 설명합니다

권한을 다 줬다고 생각했는데 AccessDenied가 떨어지면, 어느 정책이 막고 있는지 찾느라 한참을 헤매게 됩니다. Amazon Secrets Manager의 접근 거부는 한 곳이 아니라 여러 정책이 겹쳐 결정되므로, 확인 순서를 정해 두면 원인을 훨씬 빨리 좁힐 수 있습니다. 건물 출입이 막혔을 때 경비실에서 사원증부터 확인하고, 그다음 방문 허가서와 부서별 출입 상한을 차례로 보는 것과 같습니다.

  • 먼저 호출하는 주체의 자격 증명 기반 정책(identity-based policy)에 해당 API가 허용되어 있는지 봅니다.
  • 다음으로 시크릿에 붙은 리소스 기반 정책(resource-based policy)이 그 주체를 허용하는지, 그리고 권한 경계(permissions boundary)나 조직의 서비스 제어 정책이 상한을 걸고 있지 않은지 확인합니다.
  • 값 조회라면 마지막으로 KMS 키 정책의 허용까지 확인해야 하며, CloudTrail의 AccessDenied 이벤트에 남은 오류 메시지가 어느 지점에서 막혔는지 알려 줍니다.

결국 AccessDenied는 자격 증명 기반 정책, 리소스 기반 정책, 권한 경계와 조직 정책, KMS 키 정책 순으로 훑고, CloudTrail 기록으로 막힌 지점을 확인하는 것이 가장 빠른 길입니다.

5부. 암호화와 키 관리041

시크릿은 어떻게 암호화되는가

저장 시 KMS로 암호화되는 전체 흐름을 설명합니다

시크릿을 콘솔에 붙여 넣으면 그 값이 어딘가에 그대로 저장된다고 생각하기 쉽지만, 실제로는 암호문으로 바뀐 뒤 저장됩니다. Amazon Secrets Manager는 저장 시 AWS KMS의 키로 암호화하는데, 이때 값을 직접 키로 감싸지 않고 봉투 암호화(envelope encryption) 방식을 씁니다.

이삿짐을 싸는 과정을 떠올려 보면, 큰 상자에 짐을 넣고 작은 자물쇠로 잠근 다음 그 자물쇠 열쇠만 경비실 금고에 맡기는 것과 같습니다. 여기서 큰 상자가 데이터 키(data key)로 암호화된 시크릿 값이고, 경비실 금고가 KMS 키입니다.

저장할 때 Secrets Manager는 KMS에 데이터 키 생성을 요청하고, 받은 평문 키로 값을 암호화한 뒤 그 키 자체는 KMS 키로 다시 암호화해 함께 보관합니다. 값을 읽을 때는 암호화된 데이터 키를 먼저 KMS로 풀고, 그 키로 본문을 복호화하므로 매번 큰 값을 KMS로 보내지 않아도 됩니다. 정리하면 시크릿 값은 KMS에서 받은 데이터 키로 암호화되고 그 데이터 키는 다시 KMS 키로 감싸 저장되는 봉투 암호화 구조이며, 조회 시에는 KMS의 복호화 권한이 반드시 필요합니다.

고객 관리형 키 선택

기본 키 대신 직접 만든 KMS 키를 쓰는 이유와 절차를 설명합니다

계정을 만들면 aws/secretsmanager라는 이름의 키가 자동으로 생기고, 대부분은 그 키를 그대로 씁니다. 그런데 규제 대응이나 키 교체 주기 관리가 필요해지면, 기본 키 대신 직접 만든 고객 관리형 키(customer managed key)를 골라야 하는 상황이 옵니다.

아파트 공용 마스터키와 우리 집 도어락을 떠올려 보면 차이가 분명해집니다. 기본 키는 공용 마스터키처럼 모든 세대에 같은 방식으로 쓰이지만, 고객 관리형 키는 우리 집에만 설치한 도어락처럼 키 정책과 교체 일정, 삭제 시점을 집주인이 직접 정할 수 있습니다.

절차는 KMS에서 대칭 키를 하나 만들고, 그 키의 정책에 시크릿을 쓰는 주체와 관리자를 적은 뒤, 시크릿을 만들 때나 다시 암호화할 때 그 키를 지정하면 됩니다. 이렇게 하면 키 사용 기록이 따로 남아 감사에 유리하고, 키를 비활성화하거나 삭제 예약을 걸어 접근을 한 번에 차단할 수 있습니다. 결국 고객 관리형 키는 키 정책과 수명 주기를 직접 통제하려는 경우에 선택하며, KMS에서 키를 만든 뒤 그 키를 시크릿에 연결하는 절차로 적용합니다.

KMS 키 정책과 시크릿

키 정책이 잘못되면 복호화가 실패하는 이유를 설명합니다

회사에서 시크릿 값을 꺼내려는데 시크릿 읽기 권한은 다 있는데도 복호화 오류가 나는 일이 있습니다. 원인은 시크릿 자체가 아니라 그 값을 감싼 KMS 키의 문지기 규칙인 키 정책(key policy)에 있는 경우가 많습니다. Secrets Manager는 시크릿 값을 저장할 때 KMS 키로 암호화하고, 값을 읽을 때 KMS에 복호화를 요청하는데, 이때 KMS는 요청자가 키 정책의 허용 목록에 있는지를 먼저 봅니다.

아파트 금고에 비유하면 KMS 키 정책은 금고 열쇠를 빌려줄 사람 명단이고, 시크릿은 그 금고 안에 든 봉투입니다. 명단에 없는 사람은 금고가 눈앞에 있어도 열쇠를 받지 못하므로 봉투를 꺼낼 수 없습니다. 키 정책은 키에 붙는 JSON 문서로, 누가 어떤 조건에서 이 키를 쓸 수 있는지 적혀 있습니다.

그래서 시크릿 읽기 권한을 아무리 넓게 줘도 키 정책에 그 주체가 없으면 복호화는 거부됩니다. 결국 키 정책은 KMS 키에 붙는 접근 제어 문서이고, 시크릿 읽기는 그 정책을 통과하는 것이 전제입니다.

5부. 암호화와 키 관리044

시크릿 키 교체

암호화 키를 바꾸는 절차와 기존 값 처리 방법을 설명합니다

같은 암호화 키를 오래 쓰면 키가 새어 나갈 위험이 쌓이지만, 키를 바꾸는 순간 기존에 그 키로 잠가 둔 값들이 어떻게 되는지가 더 큰 문제로 다가옵니다. 이때 필요한 절차가 키 교체(rotation)입니다. 회사 금고의 열쇠를 새것으로 바꾸는 것과 비슷한데, 열쇠만 바꾸고 금고 안 봉투를 새 열쇠로 다시 잠그지 않으면 다음에 열 수가 없습니다.

KMS에서 고객 관리 키의 자동 교체를 켜면 일정 주기마다 새 키 재료(backing key)가 만들어지지만 이전 재료도 함께 보관되어 과거 데이터를 계속 풀 수 있습니다. 한편 Secrets Manager의 시크릿 교체는 값 자체를 새 자격 증명으로 바꾸는 별개의 작업이며, 새 값은 다시 암호화되어 저장됩니다. 기존 값은 교체 뒤에도 이전 버전으로 남아 있어 문제가 생겼을 때 되돌릴 수 있습니다.

정리하면 암호화 키 교체는 키 재료를 갈아 끼우되 과거 데이터를 위해 옛 재료를 보관하는 방식이고, 값 교체는 새 자격 증명을 다시 암호화해 넣는 절차입니다.

암호화 컨텍스트

시크릿 ARN이 암호화 컨텍스트로 쓰이는 방식을 설명합니다

같은 키로 암호화한 시크릿이 여러 개 있을 때 그중 하나의 암호문이 다른 곳으로 복사되면, 키만 가진 사람은 어느 것이든 풀어 볼 수 있습니다. 그래서 암호화할 때 "이 값이 무엇인지"를 함께 묶어 두는데, 이것이 암호화 컨텍스트(encryption context)입니다. 택배에 비유하면 암호화 컨텍스트는 상자 겉면의 송장이고, 내용물은 봉인되어 있어도 송장에 적힌 주소와 받는 사람이 맞아야 배송이 완료됩니다.

암호화 컨텍스트는 암호화와 복호화 양쪽에 똑같이 넣어야 하는 키-값 쌍으로, 값 자체는 암호문에 저장되지 않고 복호화 조건으로만 쓰입니다. Secrets Manager는 시크릿의 ARN(Amazon Resource Name)을 암호화 컨텍스트로 넣어 암호화하고, 복호화할 때도 같은 ARN을 제시해야 합니다. 그래서 암호문을 다른 시크릿 자리로 옮기면 키 권한이 있어도 복호화가 거부되며, 이 정보는 KMS 감사 로그에 어떤 시크릿이 복호화됐는지 남기는 표식이 되기도 합니다.

암호화 컨텍스트는 값에 딸린 신원 표식이고, 시크릿 ARN을 넣어 두면 다른 위치로의 복사와 오용을 막는 잠금장치가 됩니다.

복제본과 KMS 키

리전마다 복제본용 키가 따로 필요한 이유를 설명합니다

시크릿을 여러 리전에 복제해 두면 한 리전에 장애가 나도 서비스가 살아남지만, 막상 복제본을 읽으려는 순간 복호화가 되지 않는 상황이 생깁니다. 원인은 KMS 키가 리전을 넘어가지 못한다는 점입니다. 지점마다 금고가 있는 회사에 비유하면, 서울 지점 금고 열쇠로 부산 지점 금고를 열 수 없는 것과 같습니다.

KMS 키는 리전별로 따로 존재하고 키 ARN에도 리전이 들어가므로, 다른 리전의 복제본은 그 리전의 키로 다시 암호화됩니다. 그래서 복제본마다 대상 리전에 키가 있어야 하고, Secrets Manager가 복제를 수행할 때 그 키로 값을 다시 감쌉니다. 키 정책도 리전별 키마다 따로 붙기 때문에, 원본 리전에서만 권한을 부여해 두면 복제본 읽기는 실패합니다.

결국 복제본과 KMS 키는 한 쌍으로 봐야 하며, 리전을 늘릴 때는 그 리전의 키와 키 정책까지 함께 준비해야 합니다.

전송 구간 보호

값이 오가는 구간이 어떻게 보호되는지 설명합니다

시크릿 값은 저장될 때만 감싸지는 것이 아니라 꺼내 쓰는 순간에도 네트워크를 지나갑니다. 이 구간이 평문이면 같은 망에 있는 누군가가 값을 그대로 가로챌 수 있습니다. 택배에 비유하면 내용물을 아무리 잘 포장해도 배송 중 봉투가 투명하면 소용이 없는 것과 같습니다.

Secrets Manager에 대한 모든 API 호출은 HTTPS(TLS)로 암호화되어 전송 구간이 보호되고, SDK는 접속하는 엔드포인트의 인증서를 검증해 가짜 서버에 값을 넘기지 않도록 합니다. 또한 요청에는 서명이 붙어(SigV4) 중간에서 내용이 바뀌면 서버가 그 요청을 거부합니다. 이 보호는 저장 시 암호화와는 별개의 계층으로, 값이 디스크에 있을 때와 회선을 지날 때를 각각 따로 지켜 주는 장치입니다.

그래서 전송 구간 보호는 TLS와 요청 서명으로 이루어지며, 저장 암호화와 함께 두 겹의 방어선을 만듭니다.

키 삭제 예약의 위험

KMS 키를 지웠을 때 시크릿이 어떻게 되는지 설명합니다

암호화 키를 지우면 그 키로 만든 시크릿도 함께 사라질 것 같지만, 실제로는 시크릿 목록에 이름과 메타데이터가 그대로 남고 값만 풀 수 없게 됩니다. 이 어중간한 상태가 가장 다루기 어렵습니다. 금고 열쇠를 녹여 버린 회사에 비유하면, 금고는 여전히 금고 자리에 있고 봉투도 들어 있지만 다시는 열 수 없는 것과 같습니다.

KMS 키 삭제는 즉시 처리되지 않고 7일에서 30일 사이의 대기 기간을 두고 예약되며, 그 기간에는 취소할 수 있습니다. 대기 기간이 지나 키가 실제로 사라지면 그 키로 암호화된 시크릿은 복호화 불가 상태가 되고 값을 되살릴 방법이 없습니다. 시크릿을 없애려면 키가 아니라 시크릿 자체를 삭제해야 하며, 키 삭제는 그 키를 쓰는 모든 데이터에 영향을 준다는 점을 먼저 확인해야 합니다.

Secrets Manager Agent

로컬 사이드카로 값을 캐시하는 도구의 쓰임을 설명합니다

애플리케이션이 값을 필요할 때마다 Secrets Manager를 직접 호출하면, 여러 프로세스가 동시에 시작하는 순간 요청이 몰려 응답이 느려지거나 한도에 걸려 실패하고, 네트워크가 잠깐 끊기면 값조차 읽지 못하는 일이 생깁니다.

Secrets Manager Agent는 이런 곤란을 줄이려고 애플리케이션 옆에 나란히 띄우는 작은 로컬 프로세스로, 값을 대신 받아 두고 전달하는 사이드카(sidecar) 방식의 도구입니다.

아파트 단지 입구에 무인 택배 보관함을 두는 상황과 비슷합니다. 택배 기사가 세대마다 문을 두드리는 대신 보관함에 물건을 넣어 두면, 각 세대는 자기 칸에서 물건만 꺼내면 되고 기사도 한 번에 일을 마칩니다.

여기서 Agent 프로세스가 보관함, 애플리케이션이 세대, Secrets Manager가 택배 기사에 대응하며, Agent는 받아 온 값을 메모리에 일정 시간 보관하고 애플리케이션에는 로컬 HTTP 엔드포인트로만 건네줍니다. 보관 시간(time to live)이 지나면 Agent가 백그라운드에서 미리 새 값을 채워 두므로 애플리케이션은 기다릴 일이 거의 없습니다. 다만 값이 회전(rotation)된 직후에는 잠시 예전 값이 보일 수 있어 보관 시간을 너무 길게 두지 않는 편이 좋습니다.

정리하면 Secrets Manager Agent는 애플리케이션과 Secrets Manager 사이에서 값을 캐시(cache)하고 로컬로 제공하는 사이드카로, 호출 수와 지연을 줄이고 일시적인 통신 장애에도 값을 계속 쓸 수 있게 해 줍니다.

Lambda에서 시크릿 사용

실행 환경 재사용을 활용해 호출을 줄이는 방법을 설명합니다

Lambda 함수가 호출될 때마다 Secrets Manager에 값을 물어보면, 호출이 잦은 함수일수록 요청 수와 지연이 함께 늘고 요청 한도에 부딪혀 장애로 이어지기 쉽습니다. Lambda에서 시크릿을 쓸 때 실행 환경(execution environment)의 재사용을 활용하는 이유가 여기에 있습니다.

사무실 책상에 사원증을 넣어 두는 상황과 같습니다. 매일 아침 출입증을 발급 창구에서 새로 받는 대신, 한 번 받아 책상 서랍에 넣어 두면 그 자리에서 계속 꺼내 쓸 수 있습니다.

Lambda의 실행 환경도 한 번 만들어진 뒤 다음 호출에 다시 쓰이므로, 처리 함수 바깥쪽에서 값을 읽어 변수에 담아 두면 그 환경이 살아 있는 동안은 다시 묻지 않습니다. 값을 읽는 일은 환경이 처음 만들어지는 초기화 단계에서 한 번만 일어나고, 이후 호출은 저장해 둔 값을 그대로 쓰게 됩니다. 새 환경이 만들어지는 콜드 스타트(cold start)에서는 다시 한 번 읽어야 하므로 첫 호출이 조금 느려질 수 있고, 값이 회전되면 오래된 값을 들고 있을 수 있습니다.

결국 핵심은 값을 처리 함수 밖의 전역 변수에 보관해 실행 환경 재사용에 얹는 것이며, 이것이 호출 수와 지연을 줄이는 가장 단순한 방법입니다.

ECS에서 시크릿 주입

태스크 정의에 값을 넣는 두 가지 방식을 설명합니다

컨테이너가 뜰 때마다 코드가 Secrets Manager를 직접 조회하면 시작 시간이 늘어나고, 조회 코드를 서비스마다 따로 관리해야 해서 실수가 잦아집니다. ECS에서 시크릿을 다루는 방식은 태스크 정의(task definition)에 값을 넣는 두 갈래로 나뉘며, 하나는 시작 시 환경 변수로 주입하는 방식이고 다른 하나는 애플리케이션이 직접 조회하는 방식입니다.

이삿짐을 옮기는 상황에 견주어 보면 이해가 쉽습니다. 새 집 문 앞까지 짐을 미리 배송해 두면 도착하자마자 바로 살림을 시작할 수 있지만, 무엇이 언제 도착하는지 관리사무소를 통해야 알 수 있습니다. 반대로 몸만 들어가서 필요한 물건을 그때그때 사러 다니면 자유롭지만 매번 시간이 듭니다.

태스크 정의의 secrets 항목에 값을 가리키는 참조를 적어 두면 ECS가 컨테이너를 띄우는 시점에 그 값을 읽어 환경 변수로 넣어 주고, 애플리케이션은 평범한 환경 변수를 읽는 것처럼 값을 씁니다. 반면 이미지 안에서 SDK를 호출해 직접 가져오면 어떤 시점에 어떤 값을 읽을지 코드가 통제할 수 있는 대신 시작 지연과 오류 처리를 직접 감당해야 합니다.

정리하면 ECS에서는 태스크 정의에서 참조를 걸어 시작 시 주입하는 방식과 코드에서 직접 조회하는 방식을 상황에 맞게 고르는 것이 핵심입니다.

EKS에서 시크릿 사용

Secrets Store CSI 드라이버로 볼륨에 마운트하는 방법을 설명합니다

쿠버네티스 클러스터에서 파드가 값을 필요할 때마다 외부 서비스에 물어보게 만들면, 파드마다 조회 코드가 흩어지고 시작 순서가 꼬이면 값 없이 뜨는 파드가 생깁니다. EKS에서 Secrets Store CSI 드라이버(Secrets Store CSI driver)를 쓰면 외부에 있는 값을 파일처럼 파드 안에 붙여 줄 수 있습니다.

집 현관 벽에 우편함을 달아 두는 것과 같습니다. 우편물이 올 때마다 우체국에 가서 찾는 대신, 벽에 달린 우편함을 열면 안에 들어 있으니 집 안에서는 그 상자만 보면 됩니다. 여기서 CSI 드라이버가 우편함을 다는 일꾼, SecretProviderClass가 어떤 값을 어디서 가져올지 적은 주문서, 볼륨 마운트가 파드 안에 붙는 우편함 자리에 해당합니다.

파드가 뜰 때 드라이버가 주문서대로 Secrets Manager에서 값을 읽어 볼륨에 파일로 내려 주고, 애플리케이션은 그 파일을 읽기만 하면 됩니다. 주문서에 동기화 설정을 넣으면 같은 값을 쿠버네티스 시크릿(Secret)으로도 만들어 두어 환경 변수로 쓰는 길도 열립니다.

정리하면 EKS에서는 CSI 드라이버와 SecretProviderClass로 값을 볼륨에 마운트해 파일로 쓰게 하는 것이 핵심이며, 이 방식은 조회 코드를 애플리케이션에서 걷어내 줍니다.

재시도와 폴백 설계

일시적 오류에 대비한 애플리케이션 측 대비책을 설명합니다

값을 한 번 받아 왔다고 해도 그 뒤의 통신이 언제나 잘 되리라는 보장은 없어서, 잠깐의 지연이나 오류만으로 서비스 전체가 멈추는 일이 흔히 생깁니다. 재시도와 폴백 설계는 이런 일시적 실패를 견디도록 애플리케이션 쪽에 미리 마련해 두는 대비책입니다.

은행 창구에서 번호표를 뽑고 기다리는 상황과 비슷합니다. 창구가 잠깐 닫혔을 때 무작정 같은 속도로 다시 줄을 서면 사람들이 한꺼번에 몰려 더 오래 기다리게 되므로, 잠시 쉬었다가 조금씩 간격을 늘려 다시 가는 편이 낫습니다.

재시도는 이렇게 대기 시간을 점점 늘리는 지수 백오프(exponential backoff)에 무작위 흔들기(jitter)를 더해 구현하고, 시도 횟수의 상한을 정해 무한 반복을 막습니다. 폴백은 새 값을 받지 못할 때를 대비해 마지막으로 성공한 값을 계속 쓰거나 미리 정한 기본값으로 물러서는 장치입니다. 여기에 일정 시간 동안 호출 자체를 멈추는 회로 차단기(circuit breaker)를 곁들이면, 이미 고장 난 대상을 계속 두드리며 자원을 낭비하지 않습니다.

정리하면 재시도는 간격을 늘려 가며 다시 시도하는 것, 폴백은 대신 쓸 값을 준비하는 것, 회로 차단기는 잠시 손을 떼는 것으로, 세 가지를 함께 두어야 일시적 오류가 장애로 번지지 않습니다.

시작 시점 로딩 전략

애플리케이션이 값을 언제 읽어야 하는지 설명합니다

값을 너무 늦게 읽으면 요청을 처리하는 도중에 조회가 끼어들어 첫 응답이 느려지고, 너무 이르게 한 번만 읽으면 회전된 값을 영영 모른 채 낡은 값을 계속 쓰게 됩니다. 시작 시점 로딩 전략은 애플리케이션이 값을 언제, 몇 번 읽을지 정하는 설계입니다.

여행을 떠날 때 짐을 챙기는 방식을 떠올리면 쉽습니다. 출발 전에 미리 다 챙기면 현지에서 허둥지둥할 일이 없지만 짐이 무거워지고, 현지에 도착해 필요할 때마다 사면 가볍지만 급할 때 발이 묶입니다.

시작 시 로딩은 애플리케이션이 뜨는 단계에서 값을 모두 읽어 두는 방식으로, 값이 없으면 아예 뜨지 않게 해 잘못된 상태로 서비스하는 것을 막습니다. 지연 로딩(lazy loading)은 실제로 그 값이 처음 필요해지는 순간에 읽는 방식으로, 쓰지 않는 값까지 미리 읽는 낭비를 줄입니다. 주기적 갱신은 값을 읽어 둔 뒤 일정 간격으로 다시 확인해 회전을 따라가는 방식이며, 실무에서는 시작 시 한 번 읽고 주기적으로 갱신하는 조합을 가장 많이 씁니다.

정리하면 값은 시작 시점에 한 번 확실히 읽어 실패를 빨리 드러내고, 그 뒤로는 주기적 갱신이나 캐시 만료 정책으로 회전을 따라가게 설계하는 것이 안전합니다.

교체가 필요한 이유

비밀번호를 주기적으로 바꾸는 것이 왜 필요한지 설명합니다

회사 데이터베이스의 비밀번호 하나가 협력업체 메신저 대화에 남은 채로 몇 년이 지나도 그대로 쓰이고 있다면, 그동안 누가 그 값을 봤는지 아무도 알 수 없습니다. Amazon Secrets Manager가 비밀 정보의 주기적 교체(rotation)를 기능으로 넣은 이유가 바로 이 불확실성을 줄이기 위해서입니다.

아파트 현관 비밀번호를 생각하면 이해가 쉽습니다. 한 번 정한 번호를 십 년 넘게 쓰면 이사 간 사람도, 수리 기사도 여전히 그 번호를 알고 있을 수 있으니 일정한 주기로 바꿔야 하고, 세대주가 바뀌는 날에는 주기와 상관없이 곧바로 새 번호로 바꿉니다.

비밀 정보도 마찬가지로 교체 주기가 돌아오면 새 값이 만들어지고, 값이 바뀐 순간부터 예전 값은 더 이상 통하지 않으므로 유출된 값이 쓸 수 있는 기간이 짧아집니다.

결국 교체는 완벽한 보안을 만드는 장치가 아니라, 값이 노출되었더라도 피해가 번지는 시간을 잘라 주는 안전장치입니다.

교체 방식 두 갈래

단일 사용자 교체와 교대 사용자 교체의 큰 그림을 비교합니다

데이터베이스 사용자를 새로 만들어야 하는지, 기존 사용자의 비밀번호만 갈아야 하는지는 교체를 설계할 때 가장 먼저 갈리는 선택입니다. Secrets Manager는 이 차이를 단일 사용자 교체(single-user rotation)와 교대 사용자 교체(alternating-user rotation)라는 두 가지 방식으로 정리해 둡니다.

아파트 경비실 열쇠를 비유로 들면, 단일 사용자 교체는 하나뿐인 열쇠의 모양을 주기마다 새로 깎아 계속 그 열쇠 하나만 쓰는 방식이고, 교대 사용자 교체는 열쇠 두 개를 만들어 두고 한쪽을 쓰는 동안 다른 쪽을 새로 깎아 두었다가 다음 차례에 바꿔 드는 방식입니다.

단일 방식은 관리할 계정이 하나라 단순하지만 비밀번호를 바꾸는 짧은 순간에는 이미 연결을 잡고 있던 프로그램이 끊길 수 있습니다. 교대 방식은 두 계정을 번갈아 쓰기 때문에 교체 중에도 한쪽 계정이 계속 살아 있어 서비스가 끊기지 않는다는 장점이 있습니다.

실제로는 중단 없이 운영해야 하는 시스템일수록 교대 사용자 교체를 고르는 경우가 많습니다.

교체 일정 설정

교체 주기와 일정 표현식을 어떻게 지정하는지 설명합니다

교체를 켜 두었다고 해도 언제 얼마의 간격으로 돌릴지 정하지 않으면 아무 일도 일어나지 않습니다. Secrets Manager는 교체 주기와 시작 시점을 일정 표현식(schedule expression)이라는 짧은 문자열로 지정하게 합니다.

이는 건물 청소 계약서에 적는 문구와 비슷합니다. "매일 새벽 네 시에"라고 적으면 날마다 그 시각에 사람이 오고, "한 달에 한 번 첫째 주 금요일 밤에"라고 적으면 그 규칙대로만 옵니다.

서비스에서는 rate 표현식으로 "며칠마다"처럼 간격을 적거나 cron 표현식으로 "매월 특정 요일 몇 시"처럼 시각을 콕 집어 적습니다. 여기에 교체를 시작할 시각을 따로 두어, 업무가 가장 한산한 시간대에 작업이 돌도록 맞추는 것이 일반적입니다.

정리하면 교체 일정은 얼마의 간격으로 돌릴지와 어느 시점부터 시작할지를 함께 적는 설정입니다.

교체 Lambda의 역할

교체 작업에서 Lambda 함수가 맡는 일을 설명합니다

비밀번호를 실제로 새로 만들고 데이터베이스 쪽에 반영하는 일은 Secrets Manager 본체가 아니라 사용자가 준비한 Lambda 함수가 맡습니다. 왜냐하면 대상 시스템이 데이터베이스인지, 외부 서비스의 API 키인지에 따라 값을 바꾸는 방법이 모두 다르기 때문입니다.

아파트 도어록을 예로 들면, 관리사무소는 "이번 주에 잠금장치를 새것으로 바꾸세요"라고 지시만 하고, 실제로 문을 열고 부품을 갈아 끼우는 일은 불러온 기사가 합니다. 이때 Lambda 함수가 그 기사에 해당하며, 새 자격 증명을 만들어 내고, 그것을 대상 시스템에 등록하고, 정상적으로 동작하는지 확인하는 일을 순서대로 처리합니다.

Secrets Manager는 정해진 시각에 이 함수를 호출하고, 함수가 성공적으로 끝났는지 결과를 받아 비밀 정보의 교체 상태를 갱신합니다.

그래서 교체를 쓰려면 대상 시스템에 맞는 Lambda 함수를 먼저 준비해 두어야 합니다.

교체 작업은 한 번에 뚝 끝나는 일이 아니라, 잘못될 경우를 대비해 네 단계로 나누어 진행됩니다. 각 단계는 생성(createSecret), 설정(setSecret), 시험(testSecret), 마무리(finishSecret)라는 이름을 가지며 Lambda 함수가 이 순서를 따라 호출됩니다.

새 집으로 이사하는 과정에 빗대면 이해가 쉽습니다. 먼저 새 집 열쇠를 새로 만들고, 그 열쇠가 실제로 문을 여는지 현관에서 시험해 보고, 문제가 없을 때만 기존 열쇠를 새 열쇠로 바꿔 주는 것입니다.

생성 단계에서는 새 비밀 값이 만들어져 대기 상태로 저장되고, 설정 단계에서는 그 값이 데이터베이스나 대상 서비스에 실제로 반영됩니다. 시험 단계에서는 새 값으로 정상 접속이 되는지 확인하며, 이 확인이 통과해야 마무리 단계에서 비밀 정보의 현재 값이 새 값으로 확정됩니다.

함수의 로그 그룹은 보통 함수 이름을 따른 이름으로 생성되고, 각 호출에는 요청 식별자가 붙어 있어 한 번의 교체 시도를 통째로 따라갈 수 있습니다. 실패 원인이 권한인지 네트워크 도달 문제인지 대상 시스템의 거부인지도 로그의 오류 메시지와 오류 유형으로 갈리므로, 메시지를 그대로 읽는 것이 가장 빠릅니다. 정리하면 교체 실패는 CloudWatch Logs에서 함수의 단계별 기록과 오류 메시지를 확인해 어느 지점에서 멈췄는지 찾는 것이며, 시크릿의 마지막 교체 시각과 교체 함수 지정도 함께 보면 자동 교체가 아예 돌지 않은 경우와 구분할 수 있습니다.

API 키·토큰처럼 자동화가 힘든 값의 처리 방침을 설명합니다

결제 대행사나 외부 메일 서비스가 발급한 API 키는 우리 쪽에서 새로 만들 권한이 없어서, 자동 교체가 시작되면 오히려 서비스가 멈출 수 있습니다. 자동 교체가 어려운 시크릿은 이런 값을 자동화 대상에서 빼고 사람이 관리하도록 남겨 두는 분류입니다.

집 열쇠를 우리가 복제할 수 없고 건물주만 만들어 주는 셈입니다. 건물주가 새 열쇠를 주기 전까지는 옛 열쇠를 계속 써야 하고, 새 열쇠를 받은 뒤에도 모든 세입자가 바꿔 들 때까지는 두 열쇠가 함께 통합니다.

그래서 외부 발급 값은 교체 주기를 길게 두거나 자동 교체를 끄고, 값이 바뀔 때 사람이 새 값을 저장하고 배포하는 순서를 정해 둡니다. Secrets Manager는 이런 시크릿도 저장과 암호화와 접근 제어를 그대로 해 주므로, 자동화가 안 된다는 이유로 평문 파일에 두는 일은 피해야 합니다.

정리하면 자동 교체가 어려운 시크릿은 발급 권한이 우리에게 없는 외부 값이며, 교체 주기와 사람의 개입 절차를 문서로 정해 두는 것이 핵심입니다. 자동화할 수 있는 부분과 사람이 확인해야 하는 부분을 나눠 두면 사고 없이 관리할 수 있습니다.

8부. 교체 고급 패턴081

수동 교체 절차

자동 교체가 불가능할 때 사람이 따라야 할 절차를 설명합니다

자동 교체가 꺼져 있는 시크릿은 아무도 건드리지 않으면 몇 년이 지나도 같은 값이 그대로 남습니다. 수동 교체 절차(manual rotation)는 그 값을 사람이 안전하게 갈아 끼우기 위해 순서를 정해 둔 작업 목록입니다.

은행 금고 비밀번호를 바꿀 때와 같습니다. 새 번호를 정해 두 사람이 함께 봉인하고, 금고 담당자에게 새 번호를 전달해 시험해 본 뒤, 마지막에 옛 번호가 적힌 봉투를 폐기합니다.

실제로는 새 값을 새 버전으로 저장하고, 그 값을 쓰는 응용 프로그램을 재배포하거나 설정을 갱신해 새 값을 읽게 만든 뒤, 이전 버전을 폐기하는 순서를 밟습니다. 교체한 날짜와 담당자, 적용한 시스템 목록을 기록해 두면 다음 교체 때 무엇을 확인해야 하는지 알 수 있습니다.

수동 교체는 새 값 저장, 적용 대상 갱신, 이전 값 폐기, 기록이라는 네 단계를 순서대로 지키는 일입니다. 급할 때 순서를 건너뛰면 옛 값이 남아 인증 실패가 뒤늦게 터집니다.

교체 실패 알림과 대응

실패 이벤트를 받아 조치하는 흐름을 설명합니다

교체가 새벽에 조용히 실패하면, 다음 날 아침 서비스가 데이터베이스에 붙지 못하고서야 그 사실을 알게 됩니다. 교체 실패 알림은 Amazon Secrets Manager가 교체 작업의 성공과 실패를 event로 내보내 사용자가 즉시 알 수 있게 하는 장치입니다.

택배 배송 알림과 같습니다. 배송이 완료되면 알림이 오지만 주소가 틀려 반송되면 그 사실도 알림으로 와서, 받는 사람이 다시 주소를 고칠 수 있습니다.

RDS 연동 구조

마스터 사용자와 교체 대상 사용자를 구분해 이해합니다

RDS 데이터베이스를 만들면 관리용 계정 하나가 자동으로 생기는데, 이 계정을 그대로 응용 프로그램에 쓰면 교체할 때 관리 권한까지 함께 흔들립니다. RDS 연동 구조는 이 관리용 계정과 실제로 교체 대상이 되는 응용 프로그램 계정을 나눠 이해하는 것이 출발점입니다.

아파트 관리사무소 열쇠와 세대 열쇠의 관계와 같습니다. 관리사무소 열쇠는 건물 전체를 여는 마스터 열쇠라서 세대마다 복사해 주지 않고, 세대 열쇠는 세대별로 따로 만들어 주고 잃어버리면 새로 발급합니다.

Secrets Manager는 마스터 사용자(master user) 자격 증명으로 접속해 교체 대상 사용자의 비밀번호를 바꾸고, 그 새 값을 시크릿의 새 버전으로 저장합니다. 교체 함수는 이 마스터 자격 증명을 따로 보관해야 하므로, 보통은 교체용 시크릿을 하나 더 두어 역할을 분리합니다.

RDS 연동의 핵심은 마스터 사용자는 교체를 수행하는 열쇠이고, 교체 대상 사용자는 응용 프로그램이 쓰는 열쇠라는 구분입니다. 두 열쇠를 같은 곳에 두면 교체의 의미가 사라집니다.

Aurora 연동

클러스터 엔드포인트와 사용자 관리 방식의 차이를 설명합니다

Aurora는 인스턴스 여러 개가 하나의 클러스터로 묶여 있어서, 접속 주소를 인스턴스별로 적어 두면 장애 조치 때 연결이 끊깁니다. Aurora 연동은 이런 클러스터 구조에 맞춰 엔드포인트와 사용자 관리 방식을 다르게 잡는 것입니다.

콜센터 대표번호와 상담원 내선번호의 차이와 같습니다. 대표번호 하나만 알면 상담원이 바뀌어도 같은 번호로 연결되지만, 특정 상담원 내선번호를 외우면 그 사람이 자리를 비우는 순간 연결되지 않습니다.

그래서 응용 프로그램에는 클러스터 엔드포인트(cluster endpoint)를 쓰고, 교체 함수는 마스터 자격 증명으로 클러스터에 접속해 대상 사용자의 비밀번호를 변경합니다. Aurora MySQL과 PostgreSQL은 사용자 관리 방식이 달라서, 교체 함수가 쓰는 SQL도 엔진에 맞게 달라집니다.

Aurora 연동에서는 접속은 클러스터 엔드포인트로, 교체는 엔진에 맞는 사용자 변경 구문으로 처리하는 것이 핵심입니다. 인스턴스 주소를 직접 적어 두는 방식은 교체보다 먼저 장애 조치에서 문제를 일으킵니다.

DynamoDB 접근 키 관리

장기 액세스 키 대신 임시 자격 증명을 쓰는 이유를 설명합니다

DynamoDB 테이블에 접근하려고 만든 장기 액세스 키(access key)를 코드나 설정 파일에 넣어 두면, 그 파일이 유출되는 순간 키를 바꾸기 전까지 누구나 테이블을 읽고 지울 수 있습니다. 그래서 Amazon Secrets Manager와 임시 자격 증명(temporary credentials)을 함께 써서, 필요할 때만 짧게 살아 있는 열쇠를 발급받는 방식이 쓰입니다. 아파트 정문 열쇠를 생각하면 쉽습니다. 만능 열쇠를 하나 만들어 모든 세대에 돌려 쓰면 잃어버렸을 때 집집마다 자물쇠를 바꿔야 하지만, 방문할 때마다 경비실에서 세 시간짜리 출입증을 받아 쓰면 그 시간이 지나면 자동으로 쓸모가 없어집니다. Secrets Manager는 경비실이 보관한 신뢰의 원천, 곧 키를 만들 권한을 가진 원본 자격 증명을 안전하게 보관하는 금고 역할을 하고, AWS Security Token Service(STS)가 그 금고를 근거로 짧게 만료되는 출입증을 발급합니다.

애플리케이션은 만료 전에 새 출입증을 다시 받아 갈아 끼우므로, 중간에 하나가 새어 나가도 피해는 그 짧은 시간으로 제한됩니다. 정리하면 DynamoDB 접근은 장기 액세스 키를 저장하는 대신 Secrets Manager에 보관한 상위 자격 증명으로 STS 임시 자격 증명을 발급받아 쓰고, 주기적으로 교체하는 구조입니다.

OAuth 토큰 보관

만료되는 액세스 토큰과 리프레시 토큰을 다루는 방법을 설명합니다

OAuth로 연동한 서비스의 액세스 토큰(access token)을 파일에 그대로 저장해 두면, 그 토큰이 만료되는 순간 연동이 끊기고 사용자는 다시 로그인해야 합니다. OAuth 토큰 보관은 짧게 만료되는 액세스 토큰과, 그것을 다시 발급받는 데 쓰는 리프레시 토큰(refresh token)을 구분해 안전하게 보관하는 방법입니다. 놀이공원 자유이용권과 연간회원권을 떠올리면 이해가 쉽습니다. 하루짜리 자유이용권은 그날이 지나면 입장이 막히지만, 연간회원권을 창구에 내면 다음 이용권을 다시 받을 수 있습니다. 여기서 액세스 토큰은 하루짜리 이용권, 리프레시 토큰은 연간회원권, 인증 서버는 발권 창구에 대응하며, 연간회원권을 아무에게나 보여 주지 않고 금고에 넣어 두듯 리프레시 토큰은 Secrets Manager에 보관합니다.

애플리케이션은 액세스 토큰이 만료되면 저장해 둔 리프레시 토큰으로 새것을 받아 오고, 리프레시 토큰마저 무효가 되면 그때 사용자에게 다시 로그인을 요청합니다. 정리하면 액세스 토큰은 짧은 수명의 작업용 자격 증명, 리프레시 토큰은 재발급용 장기 자격 증명으로 나누어 보관하고, 둘 다 Secrets Manager에서 암호화해 관리하는 것이 핵심입니다.

CloudFormation 동적 참조

템플릿에서 시크릿 값을 실행 시점에 가져오는 문법을 설명합니다

CloudFormation 템플릿에 데이터베이스 비밀번호를 그대로 적으면, 템플릿 파일을 보는 사람과 스택 이력에 모두 그 값이 남습니다. 동적 참조(dynamic reference)는 템플릿에는 값 대신 어디서 가져오라는 지시만 적고, 스택을 만들거나 갱신하는 시점에 Secrets Manager에서 실제 값을 가져오게 하는 문법입니다. 사내 문서에 별첨 자료 참조라고만 쓰고 실제 자료는 창고에서 꺼내 오는 방식과 같습니다. 문서를 작성하는 사람은 창고 위치만 적으면 되고, 문서가 실제로 쓰이는 순간 담당자가 창고에서 자료를 가져와 채웁니다. CloudFormation에서는 {{resolve:secretsmanager:시크릿이름:SecretString:키이름}} 형태로 적으며, 여기서 템플릿은 문서, 동적 참조는 별첨 표시, 스택 생성 시점은 문서를 실제로 완성하는 순간에 해당합니다.

값은 CloudFormation이 실행 중에 읽어 채우므로 템플릿 파일과 스택 이력에는 실제 비밀번호가 남지 않습니다. 즉 동적 참조는 템플릿과 시크릿을 분리해 두고 배포 시점에 값을 주입하는 문법이며, 값을 바꿀 때는 템플릿이 아니라 Secrets Manager의 시크릿을 갱신합니다.

9부. AWS 서비스 연동089

ECS와 EKS 주입 방식 비교

두 서비스가 값을 넘기는 방식의 차이를 비교합니다

컨테이너에 시크릿을 넘기는 방법이 서비스마다 달라서, ECS에서 되던 방식이 EKS에서는 그대로 통하지 않아 배포 직후 값이 비어 있는 사고가 납니다. ECS와 EKS의 주입 방식 차이는 값을 컨테이너 시작 시점에 밀어 넣는지, 실행 중에 스스로 읽어 가는지에 있습니다. 급식실 배식 방식에 빗대면 차이가 선명합니다. ECS는 배식대에서 반찬을 미리 그릇에 담아 건네주는 방식이라, 작업 정의(task definition)의 secrets 항목에 시크릿을 적어 두면 컨테이너가 뜰 때 환경 변수로 값이 채워집니다. EKS는 뷔페에 가까워서, Secrets Store CSI 드라이버로 시크릿을 볼륨으로 마운트해 파일처럼 읽게 하거나 파드가 IAM 권한으로 직접 조회합니다.

그래서 ECS는 작업 정의를 고쳐야 값이 바뀌고, EKS는 볼륨 마운트 방식이면 파드를 다시 띄워야 새 값이 반영됩니다. 정리하면 ECS는 작업 정의에 지정한 시크릿을 시작 시 환경 변수로 주입하고, EKS는 CSI 드라이버나 권한 기반 조회로 컨테이너가 값을 읽는 쪽에 가깝습니다.

CI/CD 파이프라인에서 사용

빌드 도구에서 시크릿을 안전하게 꺼내 쓰는 방법을 설명합니다

빌드 도구 설정에 배포용 키를 넣어 두면 파이프라인 로그나 저장소를 통해 키가 새고, 키를 바꾸려면 모든 파이프라인을 손봐야 합니다. CI/CD 파이프라인에서의 시크릿 사용은 빌드 도구가 자기 신분을 증명하고 그 실행에만 유효한 임시 권한을 받아 Secrets Manager에서 값을 꺼내는 방식입니다. 공장에 들어가는 협력업체 작업자를 생각하면 쉽습니다. 상시 출입증을 나눠 주는 대신, 작업자는 신분증을 제시하고 그날 그 공정에만 통하는 출입증을 받아 필요한 자재만 창고에서 꺼냅니다. 여기서 파이프라인 실행은 작업자, OIDC(외부 신원을 확인하는 연동 방식)는 신분증, IAM 역할은 임시 출입증, Secrets Manager는 자재 창고에 해당합니다.

실행마다 새로 발급된 임시 자격 증명을 쓰므로 오래 남는 키가 없고, 역할에 꼭 필요한 시크릿만 읽도록 권한을 좁힐 수 있습니다. 실제로는 CI/CD 도구가 OIDC로 IAM 역할을 AssumeRole하고, 그 임시 자격 증명으로 Secrets Manager에서 값을 읽어 빌드 단계에만 넘기는 구성이 권장됩니다.

AWS Backup과 시크릿

백업에 시크릿이 포함되는지와 별도 보관 필요성을 설명합니다

백업 계획에 데이터베이스 인스턴스를 넣어 두면 그 안에 설정된 접속 비밀번호까지 스냅샷에 함께 복제되는데, 백업 파일은 보통 원본보다 느슨한 접근 권한으로 보관되기 때문에 여기서 시크릿이 새는 사고가 생깁니다. 그래서 AWS Backup이 다루는 데이터의 사본과 Secrets Manager가 맡는 비밀의 수명주기를 서로 다른 계층으로 나눠 관리해야 한다는 원칙이 필요합니다.

아파트 이삿짐 보관 창고에 비유하면, 짐을 맡기면서 현관 열쇠를 짐 상자 안에 넣어 두는 것과 같습니다. AWS Backup은 짐 상자를 통째로 복제해 보관하는 서비스이고, 그 상자 안에 데이터베이스의 마스터 암호가 들어 있으면 백업본 자체가 열쇠 사본이 되어 창고 관리인 누구나 집에 들어올 수 있게 됩니다.

그래서 애플리케이션 설정에는 시크릿의 값이 아니라 시크릿의 이름이나 Amazon 리소스 이름(ARN)만 두고, 실제 값은 실행 시점에 Secrets Manager에서 가져오도록 만듭니다. 시크릿 자체의 보존이 필요하면 데이터 백업이 아니라 자동 교체와 리전 간 복제(replication) 기능으로 대응하는 것이 정석입니다. 정리하면 백업은 데이터의 사본을, Secrets Manager는 비밀의 수명주기를 맡는 서로 다른 계층이며, 데이터 백업 안에 비밀을 얹어 두지 않는 것이 핵심입니다.

서드파티 도구와 비교

HashiCorp Vault 같은 도구와의 차이를 비교합니다

여러 클라우드와 사내 서버가 섞인 환경에서 비밀을 한곳에 모으려 하면, 특정 클라우드에 매이지 않는 도구가 필요해집니다. 그 대표 주자가 HashiCorp Vault이고, AWS 안에서 같은 역할을 하는 Secrets Manager와 자주 비교됩니다.

아파트 단지로 비유하면 Vault는 단지 한복판에 직접 세운 사설 금고이고, Secrets Manager는 인근 은행의 임대 금고입니다. 사설 금고는 원하는 건물 어디에나 옮겨 세울 수 있지만 경비 인력과 출입 규정을 직접 갖춰야 하고, 임대 금고는 해당 지점 안에서만 쓰는 대신 경비와 출입 기록을 은행이 대신 관리해 줍니다.

실제로 Vault는 쿠버네티스나 사내 서버에도 설치할 수 있고 데이터베이스 자격 증명을 그때그때 발급하는 기능이 강점이며, Secrets Manager는 AWS 서비스와의 결합과 자동 교체, IAM(Identity and Access Management) 연동이 강점입니다. 비용 구조도 달라서 Vault는 운영 인력과 서버 비용을 직접 부담하고, Secrets Manager는 보관한 시크릿 개수와 API 호출량에 따라 과금됩니다. 결국 어느 쪽이 더 낫다기보다, 비밀이 사는 위치가 AWS 안에만 있는지와 운영 인력을 누가 대는지로 고르게 됩니다.

CloudTrail로 호출 추적

누가 언제 어떤 시크릿을 읽었는지 기록되는 방식을 설명합니다

운영 중에 데이터가 외부로 새는 사고가 나면 가장 먼저 확인하는 것이 누가 그 비밀을 읽어 갔는가입니다. 그 질문에 답하기 위해 AWS는 계정 안의 API 호출을 기록하는 CloudTrail(클라우드트레일)이라는 서비스를 제공합니다.

아파트에 금고실이 있다면 문 앞에 출입 대장을 두고 들어갈 때마다 이름과 시각과 목적을 적게 하는 것과 같습니다. Secrets Manager에 대한 GetSecretValue 같은 호출은 모두 CloudTrail 이벤트로 남아 요청자 신원, 호출 시각, 출발지 IP, 요청 파라미터가 함께 기록됩니다. 이 기록은 이벤트 기록(Event history)에서 최근 90일치를 바로 조회할 수 있고, 그보다 오래 보관하려면 추적(trail)을 만들어 S3 버킷으로 내보내야 합니다.

의심스러운 호출을 발견하면 해당 사용자나 역할의 권한을 즉시 회수하고 자동 교체로 값을 바꿔 이미 새어 나간 사본을 무효로 만듭니다. 즉 CloudTrail은 시크릿의 값이 아니라 접근 행위를 남기는 장부이며, 사고 조사와 권한 점검의 출발점이 됩니다.

관리 이벤트와 데이터 이벤트

GetSecretValue 기록이 어느 쪽에 남는지 설명합니다

CloudTrail을 켜 두었는데도 정작 시크릿을 읽은 기록이 보이지 않아 당황하는 경우가 많습니다. 이것은 CloudTrail의 이벤트가 관리 이벤트(management events)와 데이터 이벤트(data events)로 나뉘고, 기본 설정이 서로 다르기 때문입니다.

건물 로비에서 방문객 이름을 적는 장부와 각 세대 도어락에 남는 출입 기록을 나눠 생각하면 이해하기 쉽습니다. 관리 이벤트는 로비 장부에 해당해 리소스를 만들고 지우고 권한을 바꾸는 호출을 기본으로 기록하며, CreateSecret이나 DeleteSecret 같은 작업이 여기에 남습니다. 반면 GetSecretValue는 값을 실제로 꺼내는 호출이라 데이터 이벤트로 분류되고, 추적(trail)을 만들 때 데이터 이벤트를 켜지 않으면 아예 기록되지 않습니다.

데이터 이벤트는 발생량이 많아 요금이 따로 부과되므로, 추적 설정에서 시크릿 관련 이벤트만 골라 켜는 방식이 권장됩니다. 결국 누가 시크릿을 읽었는지 보려면 관리 이벤트가 아니라 데이터 이벤트를 켜야 하고, 이 구분을 모르면 기록이 없는 것처럼 보인다는 점이 핵심입니다.

EventBridge로 교체 이벤트 받기

택배를 보낼 때마다 배송 완료나 배송 실패 문자를 받는 것과 같습니다. Secrets Manager는 교체가 끝나면 성공 또는 실패를 나타내는 이벤트를 EventBridge(이벤트브리지)로 보내고, EventBridge는 그 사건에 걸린 규칙(rule)에 따라 대상을 호출합니다. 성공 이벤트는 배포 파이프라인이나 설정 갱신 작업에 연결하고, 실패 이벤트는 SNS(Simple Notification Service) 주제나 채팅 채널로 보내 담당자가 즉시 알 수 있게 합니다.

IAM Access Analyzer 점검

리소스 정책이 외부에 열려 있는지 확인하는 방법을 설명합니다

버킷 정책이나 키 정책은 한 줄만 잘못 써도 회사 밖 계정에 데이터가 열리는데, 그런 구멍은 눈으로 정책 문서를 읽어서는 좀처럼 찾기 어렵습니다. IAM Access Analyzer는 계정 안의 리소스 정책을 분석해 외부에 공유된 리소스를 표시해 주는 점검 도구입니다.

분석 범위는 계정 단위나 조직 단위로 정할 수 있어서, 여러 계정을 한 기준으로 볼 수도 있습니다. 정리하면 IAM Access Analyzer는 리소스 기반 정책을 근거로 외부 접근 가능성을 자동으로 찾아내는 서비스입니다.

시크릿 백업 전략

값을 안전하게 보관하고 복원할 수 있게 하는 방법을 설명합니다

아파트 관리사무소 금고에 세대별 열쇠를 보관한다고 생각해 보겠습니다. 금고 안의 물건이 시크릿 값이고, 금고 자체가 시크릿 관리 서비스이며, 금고를 여는 마스터키가 암호화 키(KMS key)입니다. 좋은 관리사무소는 금고 하나만 믿지 않고 봉인된 사본을 다른 동에 한 부 더 두고, 사본을 꺼낼 수 있는 사람과 시점을 장부에 적습니다.

백업도 같은 방식으로 값 자체를 암호화한 상태로 다른 리전이나 다른 계정에 두고, 복원 절차와 담당자를 문서로 남겨 두어야 실제 사고 때 쓸 수 있습니다.

정리하면 시크릿 백업은 값을 암호화된 채로 서비스 바깥의 별도 위치에 보관하고, 복원에 필요한 키와 절차를 함께 관리하는 일입니다. 백업이 있다는 사실보다 그 백업을 실제로 되살려 본 기록이 있는지가 더 중요합니다.

삭제 취소와 복구

실수로 지운 시크릿을 되살리는 절차를 설명합니다

삭제 버튼 한 번으로 운영 중인 데이터베이스 암호가 사라지면, 애플리케이션은 재시작하는 순간 접속에 실패하고 원래 값을 아무도 기억하지 못해 복구에 몇 시간이 걸립니다. 이런 실수를 전제로, 시크릿 관리 서비스는 삭제를 즉시 끝내지 않고 되돌릴 수 있는 유예 기간을 두는 방식을 제공합니다.

호텔에서 짐을 두고 나갔다고 생각해 보겠습니다. 프런트는 그 짐을 바로 버리지 않고 분실물 보관소에 일정 기간 맡겨 두고, 손님이 돌아와 찾겠다고 하면 태그를 확인해 그대로 돌려줍니다.

시크릿 삭제도 같은 구조여서, 삭제를 요청하면 정해진 유예 기간 동안 값이 남아 있고 그 안에 취소를 요청하면 원래 이름과 값으로 되살아납니다. 반대로 유예 기간이 지나면 서비스는 값을 실제로 지우며, 이때는 같은 이름으로 새 시크릿을 만들어 값을 다시 넣는 것 말고는 방법이 없습니다.

정리하면 삭제 취소는 유예 기간 안에서만 가능한 되돌리기이고, 복구는 그 기간이 지난 뒤에는 새로 만드는 작업이 됩니다. 그래서 삭제 전에 어떤 애플리케이션이 그 이름을 쓰는지 확인하고, 유예 기간을 충분히 길게 잡는 것이 안전합니다.

리전 장애 대비 개요

한 리전이 멈췄을 때를 대비하는 전체 그림을 설명합니다

한 리전의 데이터센터에 전원이나 네트워크 문제가 생기면 그 리전에만 두었던 시크릿은 읽을 수 없게 되고, 다른 리전의 서버들은 시작조차 못 합니다. 그래서 시크릿을 여러 리전에 나눠 두고 한 곳이 멈췄을 때 다른 곳으로 넘어가는 그림을 미리 그려 두는 것이 리전 장애 대비입니다.

여러 도시에 지점을 둔 식당 체인을 떠올려 보겠습니다. 레시피를 본점 금고에만 두면 본점이 불에 타는 날 전국 지점이 요리를 못 하게 되므로, 체인은 지점마다 봉인된 레시피 사본을 두고 사본을 여는 열쇠는 그 도시의 책임자가 따로 관리합니다.

리전 장애 대비도 같아서 주 리전의 시크릿을 다른 리전에 복제해 두고, 각 리전의 암호화 키를 그 리전에서 따로 관리합니다. 사고가 나면 애플리케이션이 다른 리전의 사본을 읽도록 방향을 바꾸고, 원래 리전이 돌아온 뒤에 다시 정리하는 순서로 움직입니다.

정리하면 리전 장애 대비는 복제, 리전별 키, 전환 절차라는 세 가지를 미리 갖추는 일입니다. 셋 중 하나만 빠져도 사고 당일에는 쓸 수 없는 대비가 됩니다.

교차 리전 복제 설정

복제본을 만들고 키를 구성하는 방법을 설명합니다

주 리전에만 시크릿을 두면 그 리전이 멈추는 순간 다른 리전의 서버가 접속 정보를 얻지 못해 서비스가 함께 멈춥니다. 교차 리전 복제는 이 문제를 풀기 위해 한 시크릿을 다른 리전에 읽기용 복제본으로 자동 복사하는 기능입니다.

본사 계약서 원본을 지사에도 사본으로 두는 회사를 생각해 보겠습니다. 본사가 원본을 고치면 지사 사본이 자동으로 따라 바뀌고, 지사 사본은 그 지사의 직인으로 봉인되어 지사 사람만 열 수 있습니다.

교차 리전 복제도 이와 같아서 복제본은 주 시크릿의 변경을 따라가지만 읽기 전용이라 복제본에서 값을 직접 고치지는 않습니다. 그리고 복제본을 만들 때 그 리전의 암호화 키를 따로 지정하므로, 각 리전에 키가 준비되어 있어야 설정이 완료됩니다.

정리하면 교차 리전 복제는 주 시크릿과 리전별 암호화 키를 짝지어 복제본을 만드는 설정입니다. 복제본은 읽기 전용이며 주 시크릿의 변경을 계속 따라간다는 점을 기억해야 합니다.

복제본 승격과 전환

장애 시 다른 리전으로 넘어가는 절차를 설명합니다

장애가 난 리전의 시크릿이 복제본만 남아 있는데 애플리케이션이 여전히 주 리전 주소를 바라보면, 값이 살아 있어도 아무도 읽지 못합니다. 복제본 승격은 이런 상황에서 복제본을 독립된 시크릿으로 바꿔 다른 리전이 주인이 되게 하는 절차입니다.

본점이 문을 닫은 날 지점장이 본점 권한을 넘겨받는 식당 체인을 생각해 보겠습니다. 지점은 그동안 받아 둔 위임장을 꺼내 자기 이름으로 서명하고, 배달 앱에 등록된 주문 전화번호도 지점 번호로 바꿉니다.

복제본 승격도 같아서 복제본을 독립된 시크릿으로 승격시키면 그 리전이 더 이상 다른 리전의 사본이 아닌 주인이 됩니다. 이어서 애플리케이션 설정의 리전과 이름을 바꾸고 재시작해 새 주인을 보게 하며, 원래 리전이 복구되면 어느 쪽을 주인으로 둘지 정해 정리합니다.

정리하면 복제본 승격은 복제본을 독립 시크릿으로 바꾸는 일이고, 전환은 애플리케이션이 그 시크릿을 보도록 설정을 바꾸는 일입니다. 승격과 전환을 따로 연습해 두어야 장애 당일에 순서를 헷갈리지 않습니다.

호출 한도와 스로틀링

초당 요청 한도에 걸렸을 때의 대응을 설명합니다

서버 수가 갑자기 늘거나 애플리케이션이 시작될 때 수백 개 인스턴스가 동시에 시크릿을 읽으면, 초당 요청 한도를 넘겨 일부 요청이 거부되고 서비스가 간헐적으로 실패합니다. 호출 한도와 스로틀링은 이렇게 몰리는 요청을 서비스가 감당할 수 있는 속도로 조절하는 장치입니다.

은행 창구에 번호표를 뽑아 기다리는 모습을 떠올려 보겠습니다. 창구 직원 수는 정해져 있어 초당 몇 명까지만 부를 수 있고, 번호표를 못 받은 손님은 잠시 뒤 다시 와서 줄을 서며, 급한 업무는 미리 예약해 두어 기다리지 않습니다.

시크릿 호출도 같아서 한도를 넘긴 요청에는 스로틀링 오류(ThrottlingException)가 돌아오고, 클라이언트는 그 오류를 보고 잠깐 기다렸다 다시 시도합니다. 이때 기다리는 시간을 조금씩 늘리는 지수 백오프(exponential backoff)를 쓰고, 같은 값을 여러 번 읽지 않도록 캐싱하거나 여러 시크릿을 묶어 가져오면 한도에 덜 부딪힙니다.

정리하면 호출 한도는 서비스가 정한 초당 요청 상한이고, 스로틀링은 그 상한을 넘겼을 때 요청을 거부하는 동작입니다. 재시도와 백오프, 캐싱을 기본값으로 넣어 두면 장애 상황에서도 실패가 눈덩이처럼 커지지 않습니다.

서비스 장애 시 폴백

시크릿을 읽지 못할 때 애플리케이션이 버티는 방법을 설명합니다

애플리케이션이 시작할 때 Amazon Secrets Manager에서 데이터베이스 비밀번호를 읽지 못하면, 서버는 뜨지도 못한 채 오류만 뿜고 결제와 로그인이 함께 멈춥니다. 장애의 원인이 내 코드가 아니라 시크릿 서비스 쪽 네트워크나 권한일 때도 서비스 전체가 죽는 구조라면, 시크릿을 못 읽는 순간을 견디는 설계인 폴백(fallback)을 준비해야 합니다.

아파트에 사는 사람이 정전을 겪을 때를 떠올리면 이해가 쉽습니다. 각 세대의 불이 꺼져도 복도와 계단의 비상등은 별도 배선과 배터리로 켜져 있어서, 주민들은 적어도 건물 밖으로 걸어 나갈 수 있습니다.

여기서 평상시 전력이 Secrets Manager에서 읽어 오는 최신 시크릿이고, 비상등 배터리는 미리 받아 둔 값이나 마지막으로 성공한 값을 담아 두는 로컬 캐시(cache)입니다. 그리고 정전이 길어질 때를 대비해 관리인이 발전기를 돌리듯, 재시도(retry)와 백오프(backoff)를 걸어 서비스가 회복되는 순간을 기다리게 합니다.

다만 비상등을 영원히 켜 둘 수 없듯이, 폴백 값은 만료 시각과 사용 기한을 정해 두고 그 뒤에는 반드시 새 값으로 바꿔야 합니다. 정리하면 폴백은 시크릿을 읽지 못해도 서비스가 완전히 멈추지 않도록, 마지막으로 확인한 값과 재시도 정책으로 버티게 하는 안전장치입니다.

권한 변경 사고 예방

이 상황은 아파트 출입 시스템을 바꾸는 일과 비슷합니다. 관리인이 현관 비밀번호를 바꾸기 전에 세대별 카드키, 택배 기사용 임시 번호, 청소 업체의 출입증이 모두 그 문을 쓴다는 사실을 먼저 목록으로 확인해야 합니다.

여기서 키 정책은 건물 마스터키의 사용 범위를 정한 규칙이고, IAM 정책은 세대와 업체마다 나눠 준 카드키의 권한입니다. 바꾸기 전에는 누가 이 시크릿을 참조하는지, 자동 교체(rotation)용 실행 역할(role)이 그 권한에 포함되는지를 확인하고, 가능하면 기존 정책을 복사해 두었다가 문제가 생기면 즉시 되돌립니다.

또한 삭제는 곧바로 하지 말고 대기 기간이 있는 삭제 예약을 쓰고, 변경은 업무 시간에 작은 범위부터 적용해 관측 가능한 상태에서 진행합니다. 결국 권한 변경 사고 예방은 키 정책과 IAM 정책을 고치기 전에 의존 관계를 확인하고 되돌릴 수단을 준비해 두는 운영 습관입니다.

유출 의심 시 대응

값이 샜을 때 교체·폐기·감사 순서를 설명합니다

개발자 저장소에 데이터베이스 비밀번호가 그대로 올라간 사실을 나중에 발견하면, 파일을 지우는 것만으로는 이미 복제된 사본까지 되돌릴 수 없습니다. 유출이 의심될 때는 지우기보다 먼저 그 값을 쓸모없게 만드는 순서가 정해져 있어야 하고, 그것이 교체와 폐기, 감사의 순서입니다.

이 순서는 집 열쇠를 잃어버렸을 때와 같습니다. 열쇠를 잃었다고 도둑이 언제 어느 문으로 들어올지 기다릴 수는 없으니, 우선 새 열쇠로 자물쇠를 바꾸고 교체하고, 잃어버린 열쇠는 더 이상 어떤 문도 열지 못하게 폐기하며, 그 열쇠로 누가 언제 들어왔는지 기록을 감사합니다.

여기서 교체는 새 시크릿 값을 만들어 애플리케이션이 그것을 쓰게 하는 일이고, 폐기는 이전 값을 무효로 만드는 일이며, 감사는 액세스 기록을 살펴 오용 흔적을 찾는 일입니다. 순서를 지키는 이유는 폐기를 먼저 하면 새 값이 배포되기 전에 서비스가 끊기고, 감사를 먼저 하면 그동안 공격자가 계속 같은 값을 쓸 수 있기 때문입니다.

교체 뒤에는 관련 로그와 CloudTrail 기록에서 해당 값의 사용 이력을 확인하고, 노출 경로를 막은 다음 재발 방지 규칙을 남깁니다. 정리하면 유출 의심 시 대응은 노출된 값을 새 값으로 교체하고, 이전 값을 폐기하고, 사용 기록을 감사하는 순서로 진행하는 사고 대응 절차입니다.

정기 운영 체크리스트

주기적으로 점검해야 할 항목을 정리합니다

시크릿은 한 번 만들면 끝이 아니라 교체 주기가 지나고 권한이 바뀌고 담당자가 퇴사하면서 조금씩 낡아 갑니다. 그래서 주기적으로 같은 항목을 같은 순서로 확인하는 운영 체크리스트(checklist)가 필요합니다.

이 일은 아파트 관리 사무소의 정기 점검표와 같습니다. 매달 소방 설비, 엘리베이터, 주차 차단기, 공동현관 잠금장치를 정해진 항목으로 확인하듯이, 시크릿도 교체 일정, 접근 권한, 사용처, 만료 예정 항목을 정기적으로 훑습니다.

체크 항목으로는 자동 교체가 실제로 성공하고 있는지, 교체 실패 알림이 울리고 있는지, 더 이상 쓰지 않는 시크릿이 남아 있는지, 값이 코드나 로그에 노출된 흔적이 없는지를 봅니다. 또한 접근 권한이 최소 권한(minimum privilege) 원칙에 맞는지, 담당자 변경으로 남은 권한이 없는지, 비용이 갑자기 늘지 않았는지도 함께 확인합니다.

점검 결과는 표로 남겨 지난달과 비교할 수 있어야 하고, 발견한 문제는 다음 점검까지 미루지 않고 바로 담당자와 기한을 정합니다. 결국 정기 운영 체크리스트는 시크릿의 교체와 권한, 노출, 비용을 같은 기준으로 반복 점검해 작은 이상을 장애로 키우지 않는 관리 방식입니다.

이 판단은 아파트 우편함을 정리하는 일과 비슷합니다. 한 사람이 여러 동의 우편을 받는다고 우편함 하나에 다 몰아넣으면 편하지만, 그 열쇠를 잃으면 전부 잃고 한 동만 이사해도 전체를 바꿔야 합니다.

여기서 시크릿 하나는 우편함 하나이고, 그 안에 담긴 여러 값은 같은 목적과 같은 권한을 가진 우편들입니다. 따라서 교체 주기와 접근 권한이 같은 값은 한 시크릿에 묶고, 권한이 다르거나 교체 시점이 다르거나 장애 영향 범위를 분리해야 하는 값은 나눕니다.

비용은 시크릿 개수와 API 호출 수에 따라 늘어나므로, 쓰지 않는 시크릿을 정리하고 같은 값을 여러 앱이 공유하도록 묶는 것만으로도 절감이 됩니다. 정리하면 시크릿 개수와 비용 최적화는 교체 주기와 권한이 같은 값은 묶고 다른 값은 나누는 기준으로 관리해, 보안 영향 범위와 비용을 함께 줄이는 일입니다.

애플리케이션 인스턴스가 수십 개이고 요청마다 시크릿을 새로 읽으면, 같은 값을 몇 초 만에 수천 번 다시 받아 오면서 호출 비용과 지연이 함께 늘어납니다. 호출 수를 줄이는 방법은 캐시와 배치(batch) 두 가지로 정리됩니다.

이것은 아파트 경비실에서 택배를 받는 방식과 같습니다. 택배가 올 때마다 경비실에 확인 전화를 걸면 경비원도 지치고 시간도 걸리지만, 아침에 오늘 올 택배 목록을 한 번에 받아 두면 하루 종일 그것으로 충분합니다.

또한 교체가 일어났을 때 캐시를 스스로 버리도록 알림이나 짧은 만료 시간을 두고, 여러 값이 필요하면 하나씩 부르지 말고 한 번에 묶어 요청합니다. 결국 API 호출 비용 줄이기는 시크릿 값을 캐시해 재사용하고 여러 요청을 배치로 묶어, 정확성은 유지하면서 호출 수와 지연을 낮추는 최적화입니다.

서비스 한도 정리

시크릿 수·버전 수·요청률 한도를 정리합니다

새벽 자동 배포가 갑자기 멈추고 서비스가 이전 버전에 머무는 일이 있습니다. 원인을 찾아보면 코드가 아니라 시크릿을 너무 자주 읽어 요청이 제한된 경우가 적지 않은데, 이 문제를 피하려면 서비스가 정해 둔 한도(quota)를 미리 알고 설계해야 합니다.

아파트 택배 보관함을 떠올려 보면, 보관함은 칸 수가 정해져 있고 한 칸에는 교체 이력표가 붙어 있는데 표가 너무 두꺼워지면 오래된 장은 떼어 내게 됩니다. 또 관리실 출입문은 일정 시간에 통과할 수 있는 인원이 정해져 있어 모두가 같은 시간에 몰리면 줄이 길어집니다.

Amazon Secrets Manager도 비슷하게 리전마다 보관할 수 있는 시크릿 개수와 시크릿 하나에 남길 수 있는 버전 수에 상한을 두고, 값을 읽는 호출은 초당 처리량 한도를 넘으면 스로틀링(throttling) 오류를 돌려줍니다. 그래서 값을 쓸 때마다 매번 호출하지 않고 짧은 시간 캐시(cache)에 담아 두거나, 자주 읽는 단순 설정은 파라미터 저장소(Parameter Store)로 옮겨 호출량을 나눕니다.

정리하면 시크릿 수와 버전 수는 저장 공간의 한도이고 요청률은 호출 속도의 한도이며, 두 가지 모두 계정과 리전 단위로 관리되므로 배포 규모와 재시도 횟수까지 계산해 두어야 합니다.

명명 규칙과 태깅 표준

조직 전체에서 이름과 태그를 맞추는 규칙을 설명합니다

시크릿이 수백 개로 늘면 이름이 제각각이 되어 어느 것이 운영 결제 키인지 찾지 못하고, 급한 배포 중에 개발용 키를 운영에 붙이는 사고가 생깁니다. 이름과 태그(tag)를 규칙으로 맞춰 두면 사람도 도구도 같은 방식으로 값을 찾고 걸러낼 수 있습니다.

도서관 청구기호를 떠올려 보면, 청구기호는 구역과 서가와 번호 순서가 정해져 있어 아무도 헤매지 않고, 같은 주제의 책은 별도의 색인표로 묶여 있습니다.

시크릿 이름도 서비스와 환경과 용도를 일정한 순서로 늘어놓는 계층 구조로 정하면 경로만 보고 소유자와 쓰임을 짐작할 수 있고, 태그에는 소유 팀과 환경, 데이터 등급, 교체 주기 같은 값을 붙여 비용 화면이나 권한 정책, 감사 화면에서 한꺼번에 걸러낼 수 있습니다. 이름에 비밀 값이나 고객 정보를 넣지 않는 것도 규칙의 일부입니다. 중요한 점은 이 규칙을 문서로만 남기지 않고, 시크릿을 만드는 배포 파이프라인이나 코드로 인프라를 정의하는 방식(IaC)에서 이름과 태그를 자동으로 채우게 하는 것입니다.

결국 이름은 유일성과 검색을 맡고 태그는 분류와 자동화를 맡으며, 둘을 함께 강제해야 개수가 늘어도 관리가 무너지지 않습니다.

환경별 시크릿 분리

개발·스테이징·운영 값을 나누는 기준을 설명합니다

개발 환경용 키로 운영 데이터를 건드리는 사고는 대개 설정 한 줄 차이에서 시작됩니다. 개발과 스테이징과 운영의 값을 저장 단계에서부터 나눠 두면 그런 사고가 지나갈 경로 자체가 줄어듭니다.

건물의 층별 회의실을 떠올려 보면, 3층 회의실과 9층 회의실은 이름이 같아도 다른 방이고 출입 카드도 따로 발급됩니다.

시크릿도 보통 계정 자체를 환경별로 나누거나, 같은 계정 안에서도 이름 규칙과 태그, 권한 정책(IAM policy)으로 경로를 갈라 접근을 통제합니다. 이렇게 나누면 개발자에게는 개발 경로만 열어 주고 운영 값은 배포 파이프라인의 역할만 읽게 할 수 있어, 사람의 실수로 운영 키가 새는 위험이 크게 줄어듭니다. 다만 값이 환경마다 중복되므로 교체 시점과 명명 규칙을 함께 관리해야 하고, 다른 리전으로 값을 복제하는 기능(replication)은 정해진 규칙 안에서만 쓰는 것이 좋습니다.

환경 분리는 저장 위치와 권한을 함께 나누는 일이며, 이름이 같아도 환경이 다르면 다른 시크릿이라는 원칙을 지키는 것이 핵심입니다.

흔한 안티패턴

코드 저장소에 비밀 키를 그대로 올리거나 모든 값을 하나의 거대한 시크릿에 몰아넣는 방식은 처음에는 편해 보이지만, 사고가 나면 피해 범위가 통째로 커집니다. 자주 반복되는 실수와 그 대안을 짚어 두면 같은 함정을 미리 피할 수 있습니다.

경비실 열쇠 걸이를 떠올려 보면, 모든 세대 열쇠를 한 고리에 달아 두면 관리하기는 편하지만 그 고리 하나가 새는 순간 단지 전체가 뚫립니다.

시크릿도 하나에 데이터베이스 주소와 비밀번호와 외부 서비스 키를 몰아넣으면 교체도 권한 분리도 불가능해지고, 값을 코드나 설정 파일에 직접 적으면 저장소 이력에 영원히 남습니다. 값이 바뀔 때마다 코드를 고쳐 다시 배포하는 방식, 교체(rotation)를 손으로만 하는 방식, 로그에 값을 찍어 두는 습관도 같은 부류의 실수입니다. 대안은 용도별로 시크릿을 쪼개고, 프로그램이 시작할 때 API로 읽어 캐시하며, 자동 교체와 접근 감사(audit)를 켜 두는 것입니다.

편하게 쓰려고 한곳에 모으고 코드에 박아 두는 습관이 가장 큰 위험이며, 쪼개기와 실행 시점 조회와 자동 교체가 기본값이 되어야 합니다.

기존 저장소에서 이전하기

설정 파일이나 다른 도구에 있던 값을 옮기는 절차를 설명합니다

설정 파일이나 오래된 도구에 흩어져 있던 비밀번호를 그대로 두면 누가 언제 읽었는지 알 수 없고, 교체도 손으로 해야 합니다. 이전은 값을 옮기는 일이라기보다 관리 책임을 넘기는 일이므로 순서를 지켜야 합니다.

이사할 때 새 집 열쇠를 먼저 받고, 짐을 옮긴 뒤에 옛 집 열쇠를 반납하듯 이전에도 정해진 순서가 있습니다.

먼저 옮길 값을 목록으로 만들고 각 값의 소유자와 쓰는 곳을 확인한 다음, 새 시크릿을 만들어 양쪽을 잠시 함께 운영하는 기간을 둡니다. 애플리케이션이 새 시크릿을 읽도록 바꾸고 정상 동작을 확인한 뒤에 원본 저장소에서 값을 지우고 저장소 이력까지 정리합니다. 이때 원본을 지우기 전에 값을 교체하면 이전 중인 서비스가 한꺼번에 멈출 수 있으므로, 교체는 이전이 끝난 뒤에 하는 것이 안전합니다.

결국 이전은 새 저장소 준비, 병행 운영, 전환 확인, 원본 삭제, 값 교체의 순서로 진행하며, 각 단계마다 되돌릴 방법을 남겨 두어야 합니다.

앞에서 다룬 규칙을 따로따로 적용하면 각각은 맞아 보이지만, 실제 운영에서는 이름과 권한과 한도와 교체가 서로 얽혀 문제를 만듭니다. 이들을 하나의 설계로 묶으면 장애와 사고를 함께 줄이는 운영 체계가 됩니다.

아파트 단지 관리를 떠올려 보면, 세대 명단과 출입 카드 발급 규칙과 정기 점검 일정과 관리 인력의 업무량이 함께 맞아야 단지가 유지됩니다.

시크릿 운영도 명명 규칙과 태그로 목록을 만들고, 환경별로 계정과 권한을 나누며, 교체 주기와 한도를 함께 정하는 하나의 설계로 묶입니다. 여기에 요청량 분산과 캐시 정책을 더하면 한도 초과로 배포가 멈추는 일을 막을 수 있고, 접근 감사 로그와 알림을 붙이면 이상한 조회를 일찍 발견할 수 있습니다. 사람이 손으로 하던 부분은 코드로 인프라를 정의하는 방식(IaC)으로 옮겨 규칙이 자동으로 지켜지게 하는 것이 마지막 단계입니다.

시크릿 관리는 저장 기능 하나가 아니라 명명과 권한과 한도와 교체와 감사를 한 묶음으로 설계하는 운영 체계이며, 작은 규칙을 자동화해 두는 것이 오래 가는 방식입니다.
