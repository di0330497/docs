  2. 예약 실행schedule 과 cron 표현식('0 9 * * 1' 같은 형태)으로 정해진 시간에 자동 실행합니다.

1문제 상황

워크플로에서 이슈 제목, PR 본문, 커밋 메시지 같은 사용자 입력을 run 스크립트에 직접 끼워 넣으면, 그 입력에 시스템 명령어나 환경 변수 참조가 포함될 수 있다. 예를 들어 이슈 제목이 echo $GITHUB_TOKEN이라면, 직접 실행하면 시크릿이 노출된다. 기존 방식은 입력과 코드의 경계를 구분하지 않아 인젝션 공격에 취약하다.

2핵심 질문

3동작 예시

이슈 제목이 rm -rf /라도, 환경 변수에 담고 echo로 출력하면 그 문자열이 실제 명령어로 해석되지 않는다. 입력이 데이터로만 취급되는 것이다.

4동작 과정

  1. 입력을 환경 변수에 격리이슈 제목이나 PR 본문을 직접 run에 쓰지 않고 env: 절을 통해 환경 변수로 전달한다.
  2. 스크립트에서 변수 참조명령 치환($(...) 또는 ` ... `)이나 이중 인용문 없이, 환경 변수로만 참조하거나 eval을 피한다.
  3. 결과입력이 명령어가 아닌 문자열로만 처리** — 특수 문자나 시스템 명령어가 포함되어도 실행되지 않는다.

1문제 상황

누가 만든 액션이든 버전을 지정하지 않고 사용하면, 그 액션이 나중에 악의적으로 변경되어도 워크플로가 자동으로 새 버전을 받는다. 포크 PR을 테스트할 때 pull_request_target 트리거를 쓰면 포크된 코드가 저장소의 시크릿에 접근할 수 있다. 자체 호스팅 러너가 침해당하면 기본 권한으로 민감한 작업을 수행할 수 있다. 기존 방식은 신뢰할 수 없는 코드 실행과 시크릿 노출의 경로가 많다.

2핵심 질문

4동작 과정

  1. 액션 버전 고정액션을 특정 커밋 SHA나 릴리스 태그로 명시하여 예기치 않은 업데이트를 방지한다.
  2. 포크 PR 시크릿 제한pull_request 트리거를 사용하고, 포크 PR 환경에서는 시크릿이 주입되지 않도록 설정한다.
  3. 러너 권한 격리자체 호스팅 러너에는 필요한 권한만 주고, GitHub 호스팅 러너와 권한 수준을 분리한다.

2핵심 질문

3동작 예시

4동작 과정

  1. 빌드 실행과 산출물 생성GitHub Actions 워크플로가 소스 코드를 컴파일하거나 패키징하여 jar, 바이너리 등을 만든다.
  2. 어테스테이션 생성그 산출물에 대해 워크플로가 커밋 SHA, workflow run ID, 빌드 시간 등을 포함한 서명된 증명서(어테스테이션, attestation)를 발급한다.
  3. 이후 검증개발자나 보안 도구가 다운로드한 산출물의 어테스테이션을 검증하면 출처, 무결성, 빌드 환경을 확인할 수 있다.

2핵심 질문

워크플로에서 코드를 어디로 배포할지, 배포 대상을 어떻게 구분하고 정의할 수 있을까?

3동작 예시

같은 빌드 결과물을 staging 환경에는 매 커밋마다 배포하고, production 환경에는 릴리스 태그가 달린 커밋만 배포하려면, 워크플로에서 if 조건으로 분기하고 각 환경을 명시하면 된다.

  2. 환경(environment) 정의배포 대상지를 production, staging, development 같은 이름으로 논리적으로 구분한다.
  3. 환경별 배포 규칙 설정각 환경마다 어느 브랜치에서만 배포할지, 누가 배포할 수 있는지 정의한다.

커스텀 배포 보호 규칙

3동작 예시

4동작 과정

  1. 태그 릴리스액션 코드를 깃허브 저장소에 커밋하고, git tag v1.0.0 으로 버전 태그를 만들어 푸시합니다.

1문제 상황

2핵심 질문

전체 워크플로 하나를 부품처럼 다른 워크플로에서 불러 쓸 수는 없을까?

3동작 예시

공용 워크플로 파일(예: .github/workflows/reusable-deploy.yml)에서 on: workflow_call: 로 트리거를 설정하고 inputs, outputs, secrets를 정의한 후, 다른 워크플로에서 uses: .github/workflows/reusable-deploy.yml@main 으로 호출하면, 깃허브가 그 워크플로의 모든 단계를 호출한 워크플로의 일부로 실행합니다.

4동작 과정

  1. 재사용 워크플로 작성.github/workflows/ 에 워크플로 파일을 만들고 on: workflow_call: 로 시작, inputs와 outputs을 선언합니다.
  2. 호출 워크플로에서 사용jobs 섹션에서 uses: <저장소>/.github/workflows/<파일명>@<브랜치> 로 호출하고, with: 로 입력값을 전달합니다.
  3. 실행호출 워크플로가 트리거되면, 재사용 워크플로의 모든 jobs가 마치 같은 워크플로에 있는 것처럼 실행됩니다.

4동작 과정

  2. 실행 제어 및 재실행완료된 실행 항목에서 "Re-run failed jobs" 로 실패한 잡만 다시 실행하거나 "Re-run all jobs"로 전체 재실행하며, 진행 중인 실행에서 "Cancel" 로 즉시 중단할 수 있습니다.

GitHub Actions를 사용할 때 특정 제약이 있다는 사실을 모른 채로 워크플로를 설계하면, 실행 중 갑자기 제한에 걸려 잡이 중단되거나 대기 상태에 빠질 수 있습니다. 잡 실행 시간, 동시 실행 수, 매트릭스 크기 등의 상한을 미리 알아야 예측 가능한 워크플로를 만들 수 있습니다.

2핵심 질문

GitHub Actions가 설정한 기본 상한이 무엇이고, 각각이 워크플로 설계에 어떤 영향을 미칠까요?

3동작 예시

무료 계정은 월 2,000분 무료 실행 시간이 있고, 각 잡은 기본 6시간(timeout-minutes로 조정 가능, 최대 35일)을 초과하면 중단되며, 동시 실행 수, 매트릭스 조합 개수(최대 256개), API 요청 속도(분당 한도) 등이 각각 제한되어 있습니다.

4동작 과정

  1. 기본 실행 시간 한도각 잡은 기본 6시간 내에 완료되어야 하며, timeout-minutes 로 조정 가능합니다. 무료 계정은 월 2,000분 총 실행 시간 제한이 있습니다.
  2. 동시 실행 및 매트릭스 제한같은 워크플로의 동시 실행 수와 매트릭스 조합(예: 3개 OS × 2개 Node 버전 = 6조합)의 최대 크기가 정해져 있어, 초과하면 대기 큐에 진입합니다.
  3. API 요청 속도 제한아티팩트 업로드, 상태 체크, 로그 기록 등 각 API 호출에는 분당 요청 수 제한이 있어, 초과하면 요청이 throttle 됩니다.

다른 CI에서 GitHub Actions로 이관

기존에 Jenkins·GitLab CI·CircleCI 같은 다른 CI 도구를 사용하고 있었다면, 그 도구의 설정 파일(Jenkinsfile·.gitlab-ci.yml·.circleci/config.yml 등)이 각각 다른 문법과 개념으로 작성되어 있습니다. 새로 GitHub를 CI/CD 플랫폼으로 옮기려고 해도, 기존 설정을 그대로 옮길 수 없고 처음부터 다시 작성해야 하는 번거로움이 있습니다.

2핵심 질문

기존 CI 도구의 설정을 GitHub Actions 문법으로 효율적으로 변환해서, 같은 빌드·테스트·배포 동작을 유지하면서 이관할 수 있을까?

3동작 예시

Jenkins에서 "이 단계에서 npm install 실행하고, 다음 단계에서 npm test 실행하면, 실패하면 빌드 중단" 같은 설정이 있었다면, GitHub Actions에서는 같은 순서와 조건을 YAML 문법으로 옮겨서 "jobs.build.steps[]에 run: npm install, run: npm test를 넣되, 실패 시 중단"이라고 작성하는 방식입니다.

4동작 과정

  1. 기존 CI 설정 분석Jenkins, GitLab CI, CircleCI의 설정 파일을 읽으면서 "어떤 이벤트에서 시작되는가", "어떤 명령어를 순서대로 실행하는가", "성공·실패 조건은 뭔가" 같은 핵심을 파악합니다.
  2. GitHub Actions 문법으로 변환분석한 동작을 .github/workflows/ 디렉토리의 YAML 파일로 작성하는데, 이벤트는 on: 필드로, 단계별 명령어는 jobs.steps로, 조건문은 if 필드로 옮깁니다.
  3. 동작 검증 및 세부 조정이관된 워크플로를 실제로 실행해보면서 기존 CI의 동작과 같은지 확인하고, 필요하면 환경 변수·인증 토큰 설정을 추가로 조정합니다.

5한 줄 요약

기존 CI 도구의 설정 로직과 실행 흐름을 GitHub Actions의 워크플로 문법으로 단계적으로 변환해서, 이미 구축된 자동화 파이프라인을 최소한의 수정으로 새 플랫폼에 옮기는 것
