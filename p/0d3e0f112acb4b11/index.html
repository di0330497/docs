Amazon EC2

AWS 퍼블릭 클라우드의 가상 서버 서비스 Amazon Elastic Compute Cloud(EC2) 자체 — 인스턴스·AMI·구매 옵션·네트워킹·스토리지 연결·운영까지, EC2 User Guide가 다루는 범위를 처음 배우는 사람이 순서대로 읽도록 재배열한 것. EC2 Auto Scaling·EBS·VPC 같은 인접 서비스는 EC2가 그것들을 어떻게 쓰는가 수준까지만 포함한다.

이어서 읽기
1EC2가 무엇인가 — 전체 지도인스턴스·AMI·스토리지·네트워크라는 낱말이 서로 어떻게 물리는지 먼저 알아야, 뒤의 모든 선택(타입·이미지·구매옵션)이 '무엇을 고르는 일'인지 이해된다.52인스턴스 타입 — 무엇을 빌리는가AMI도 스토리지도 네트워크 성능도 인스턴스 타입이 정한 하드웨어 위에서만 가능하므로, 빌릴 대상의 규격을 먼저 읽을 줄 알아야 한다.73AMI — 무엇으로 부팅하는가인스턴스를 실행하려면 반드시 AMI를 지정해야 한다. 타입(하드웨어)을 안 다음 이미지(소프트웨어)를 아는 순서라야 둘의 호환 조건이 이해된다.64인스턴스 실행과 접속타입과 AMI를 골랐으면 이제 실제로 띄우고 들어가는 법이 필요하다. 접속 수단은 이후 모든 실습·문제 해결의 전제다.85인스턴스 수명주기실행할 줄 알면 다음은 멈추고·재우고·되살리는 법이다. 상태별로 무엇이 보존되는가를 알아야 스토리지와 IP 이야기가 이해된다.66인스턴스 스토리지수명주기에서 '무엇이 사라지는가'를 본 다음이라야, EBS와 인스턴스 스토어의 차이가 규칙이 아니라 이유로 남는다.57네트워킹인스턴스가 뜨고 살아 있는 것을 확인했으면, 그것이 어디에 붙어 어떻게 도달되는가가 다음 문제다. 보안 그룹은 접속 실패의 1순위 원인이라 여기서 확정한다.78구매 옵션과 용량 확보인스턴스가 무엇이고 어떻게 띄우는지 안 다음이라야 '같은 인스턴스를 얼마에, 얼마나 확실히 얻는가'라는 질문이 성립한다.99보안운영 도구를 배우기 전에, 지금까지 만든 리소스를 누가 어떻게 만질 수 있는가를 정리해야 한다. IAM 역할은 뒤의 Systems Manager·CloudWatch 연동의 전제이기도 하다.610게스트 OS 운영인스턴스 안쪽은 AWS가 아니라 내가 관리한다. 드라이버·부팅 에이전트·시간은 성능과 장애 원인의 상당 부분을 차지한다.311모니터링·리소스 관리·문제 해결앞의 모든 리소스가 존재하는 상태라야 '무엇을 보고, 어떻게 찾고, 고장나면 무엇을 하는가'가 의미를 갖는다. 마지막에 두는 이유다.7

Amazon EC2란 무엇인가: 온디맨드 가상 서버가 대신해 주는 일

EC2는 AWS 클라우드에서 필요할 때 바로 빌려 쓰고 필요 없으면 반납하는 가상 서버(인스턴스) 서비스다.

#1문제 상황

전통적으로 서버가 필요하면 물리 하드웨어를 구매해야 했다. 데이터센터에 주문하고, 설치되길 기다리며, 배송과 설치 과정에 몇 주가 걸렸다. 용량을 잘못 계획하면 비용만 낭비했고, 더 이상 필요 없을 때도 매각하기 전까지 계속 비용을 냈다. 이 과정은 느리고 경직되어 있다.

#2핵심 질문

필요한 만큼만 빌려 쓰고, 필요 없으면 즉시 반납하는 가상 서버를 수 초 안에 준비할 수 있을까?

#3동작 예시

AWS의 데이터센터에는 이미 물리 서버들이 갖춰져 있다. EC2는 그 위에 소프트웨어 계층을 얹어 가상 서버(인스턴스)를 순간적으로 만들고 지운다. 버튼 클릭 몇 초 후 Linux나 Windows 운영체제가 실행되는 컴퓨터가 생긴다.

#4동작 과정

  1. 요청웹 콘솔이나 CLI에서 인스턴스의 사양(CPU, 메모리, 운영체제)을 명시해 실행을 요청한다
  2. 할당AWS가 자신의 물리 서버 위에 그 사양으로 가상 머신을 생성해 할당한다
  3. 청구인스턴스가 실행되는 순간부터 시간 단위로 비용이 청구되고, 종료하면 청구가 멈춘다

#5한 줄 요약

물리 서버 구매의 긴 대기와 초기 비용 부담을 없애고, 필요한 만큼만 빌려 쓸 수 있는 온디맨드 방식의 가상 서버다

#1문제 상황

물리 서버를 조립하려면 하드웨어(CPU, 메모리, 디스크), 운영체제, 네트워크 설정, 접속 보안 등 여러 부분을 맞춰야 한다. EC2도 마찬가지인데, 각 부분을 분리된 구성요소로 관리할 수 있다는 점이 차이다.

#2핵심 질문

가상 서버 인스턴스를 구성하려면 어떤 재료들이 필요할까?

#3동작 예시

EC2 인스턴스는 네 가지 핵심 부품으로 이루어진다. AMI(Amazon Machine Image)는 미리 구성된 운영체제 템플릿이다. EBS나 인스턴스 스토어 같은 스토리지는 디스크 데이터를 보관한다. 키 페어는 Linux 인스턴스에 SSH로 접속할 때 사용하는 암호화 열쇠다. 보안 그룹은 어떤 네트워크 트래픽을 들여보낼지 규칙으로 정의하는 방화벽이다.

#4동작 과정

  1. 이미지 선택AMI(OS 템플릿)를 고르면 그 운영체제가 인스턴스에 미리 설치된 상태로 부팅된다
  2. 저장소 구성EBS 볼륨(AWS 관리 디스크)의 크기를 정하거나 임시 디스크인 인스턴스 스토어를 쓸지 선택한다
  3. 보안 설정키 페어(접속용 암호키)를 지정하고, 보안 그룹의 방화벽 규칙으로 어떤 포트를 열거나 닫을지 정한다

#5한 줄 요약

OS 템플릿, 저장소, 접속 방식, 네트워크 규칙 같은 서버의 구성요소들을 독립적으로 조합해서 원하는 인스턴스를 만드는 것

#2핵심 질문

EC2 인스턴스를 지리적으로 어디에, 어떤 원칙으로 배치해야 할까?

#3동작 예시

AWS는 전 세계를 리전(Region)이라 부르는 독립적인 지역들로 나누었다(예: 서울 리전, 도쿄 리전). 각 리전 안에는 가용 영역(Availability Zone)이라 부르는 2개 이상의 독립적인 데이터센터가 있다. 서울 리전에 인스턴스 2개를 만들면 서로 다른 가용 영역에 자동으로 배치되어, 한 센터가 장애나도 다른 곳은 멀쩡히 살아있다.

#4동작 과정

  1. 리전 선택서비스 대상 사용자가 있는 지리적 리전을 고르면서 지연을 최소화하고 규제를 준수한다
  2. 가용 영역 분산고가용성이 필요하면 같은 리전 안의 서로 다른 가용 영역에 인스턴스를 여럿 배치한다
  3. 특수 배치극도로 낮은 지연이 필요하면 Local Zones나 Wavelength 같은 AWS 엣지 로케이션을 사용한다

첫 인스턴스 한 바퀴: 실행·접속·종료와 기본 모범 사례

인스턴스를 실행하고 키 페어로 접속한 뒤 사용이 끝나면 종료해 요금을 멈추는 것이 EC2의 기본 흐름이다.

#1문제 상황

서버를 처음 써본 사람들은 인스턴스를 켜기만 하고 꺼지 않아서 불필요한 비용을 낸다. 또는 보안 설정 없이 인스턴스를 노출된 상태로 두어 침입 피해를 입는다. 전체 생명주기를 이해하고 기본 모범 사례를 따르는 것이 중요하다.

#2핵심 질문

인스턴스를 안전하고 비용 효율적으로 관리하려면 어떤 순서로 다루어야 할까?

#3동작 예시

새 인스턴스의 기본 흐름은 세 단계다. 첫째, AWS 콘솔이나 CLI로 인스턴스 사양을 정하고 "Run" 또는 "Launch"하면 몇 초 후 "Running" 상태가 된다. 둘째, 키 페어 파일(AWS에 공개키를 저장하고, 사용자가 개인키를 보관)을 써서 SSH나 RDP로 접속하고, 필요한 소프트웨어를 설치하거나 설정을 한다. 셋째, 작업이 끝나면 "Stop"(나중에 재시작 가능, 스토리지 요금만 부과)이나 "Terminate"(영구 삭제)로 정리해서 청구를 멈춘다.

#4동작 과정

#3동작 예시

  2. 세대와 기능 읽기숫자는 세대(최신일수록 높음)를 나타내고, 그 뒤 소문자는 프로세서 종류(a=AMD, g=Graviton, d=로컬 스토리지, n=고성능 네트워킹)를 표시한다

#1문제 상황

모든 인스턴스가 똑같은 성능을 내지는 않는다. 웹 서버는 CPU와 메모리 균형이 필요하고, 데이터 분석 작업은 메모리가 많아야 하고, 데이터베이스 캐시는 초고속 메모리가 필요하고, 빅데이터 처리는 빠른 디스크 I/O가 필수다. 각 용도에 맞지 않는 인스턴스를 고르면 성능이 나쁘거나 불필요한 비용을 낸다.

#2핵심 질문

자신의 워크로드에 가장 효율적인 CPU, 메모리, 디스크 비율을 가진 인스턴스 패밀리는 무엇일까?

#3동작 예시

웹 애플리케이션 서버를 생각해보자. 평균적으로 CPU와 메모리가 균형 있게 필요해서 M 패밀리(범용)를 선택한다. 반면 비디오 인코딩이나 이미지 처리 같은 백그라운드 배치 작업은 CPU를 집중적으로 써야 하므로 C 패밀리(컴퓨팅 최적화)를 쓴다. 데이터 분석이나 메모리 내 캐시(Redis)는 R 패밀리(메모리 최적화)를 쓴다. 그리고 NoSQL 데이터베이스나 검색 엔진은 빠른 로컬 디스크가 중요해서 I 패밀리(스토리지 최적화)를 쓴다.

#4동작 과정

  1. 워크로드 분석애플리케이션이 주로 CPU를 많이 쓰는지, 메모리를 많이 쓰는지, 디스크 I/O를 많이 하는지 파악한다
  2. 패밀리 선택범용(M/T), 컴퓨팅 최적화(C), 메모리 최적화(R/X), 스토리지 최적화(I/D) 중 하나를 골라서 신청한다
  3. 크기 조정선택한 패밀리 안에서 실제 필요한 vCPU와 메모리에 맞춰 크기(small, medium, large 등)를 정한다

#4동작 과정

성능 손잡이: EBS 최적화·CPU 옵션·프로세서 상태 제어

인스턴스 성능은 EBS 최적화 대역폭, vCPU 수·하이퍼스레딩을 조절하는 CPU 옵션, C-state/P-state 같은 프로세서 상태 설정으로 미세 조정할 수 있다.

→ 05-03 참조

#1문제 상황

인스턴스 타입을 선택하면 그 타입이 제공하는 성능이 거의 고정됩니다. m5.large는 항상 m5.large의 성능을 제공합니다. 하지만 실제 워크로드에 따르면 일부는 네트워크 대역폭이 중요하고(EBS 집약적), 일부는 vCPU 수가 남아도는 문제가 있으며, 일부는 프로세서의 전력 소비 상태(P-state, C-state)를 조정해야 합니다. 이런 세밀한 조정이 불가능하면 비효율적입니다.

#2핵심 질문

같은 인스턴스 타입을 선택한 후 EBS 대역폭, vCPU 수, 프로세서 상태를 개별 조정해서 성능을 최적화할 수 있을까?

#3동작 예시

m5.xlarge는 기본값이 4 vCPU인데, 만약 애플리케이션이 라이선스당 2코어까지만 허용하면 vCPU를 2개로 줄일 수 있습니다. 또한 높은 I/O 작업이 필요하면 EBS 최적화(Enabled)를 켜서 EBS 대역폭을 확보합니다. 이 두 조정으로 같은 m5.xlarge도 다르게 작동합니다.

#4동작 과정

  1. EBS 최적화 설정인스턴스 시작 시 "EBS 최적화 활성화" 옵션을 켜면, 인스턴스의 네트워크 대역폭 일부가 EBS 통신에 예약됩니다. EBS 읽기/쓰기 성능이 중요한 데이터베이스나 캐시 서버에 유용합니다.
  2. CPU 옵션 조정인스턴스 시작 또는 실행 중(일부 타입)에 vCPU 수와 하이퍼스레딩 여부를 조정합니다. 4 vCPU를 2 vCPU로 줄이거나, 하이퍼스레딩을 끄는 방식입니다.
  3. 프로세서 상태 제어C-state(절전 상태), P-state(주파수 조절) 같은 프로세서 상태를 조정합니다. 높은 성능이 필요하면 C-state를 비활성화해 CPU가 절전하지 않게 하고, 전력 효율이 중요하면 P-state를 낮춥니다.

#5한 줄 요약

인스턴스 타입 선택 후 EBS 대역폭, vCPU 수, 프로세서 상태를 미세 조정해서 워크로드에 정확히 맞춘 성능을 구현하는 것

타입 고르고 바꾸기: 타입 검색·Compute Optimizer 추천·리사이즈

조건에 맞는 인스턴스 타입을 콘솔·CLI로 검색하고, Compute Optimizer 추천을 참고해 중지 후 타입을 바꾸는 방식으로 크기를 조정한다.

#1문제 상황

처음 인스턴스를 시작할 때 타입을 잘못 선택하면 문제가 생깁니다. 타입을 찾는 과정도 번거롭습니다(대신 150개가 넘는 타입이 있음). 또한 인스턴스가 이미 실행 중이면 타입을 바꾸기 위해 대기 시간이 필요합니다. 기존에는 타입 변경이 간단한 작업이 아니었습니다.

#2핵심 질문

조건에 맞는 인스턴스 타입을 쉽게 찾고, 필요시 중지 후 타입을 변경할 수 있을까?

#3동작 예시

AWS 콘솔에서 "2 vCPU, 4GB 메모리, 저비용" 같은 조건으로 검색하면 t3.medium, t4g.medium, m5.large 같은 후보들이 나옵니다. Compute Optimizer가 지난 30일 사용 패턴을 분석해 "m5.large는 과도할 것 같으니 t3.medium 추천"이라고 제시합니다. 사용자는 그 추천을 참고해 타입을 선택하고, 실수했으면 나중에 중지 → 타입 변경 → 재시작으로 수정합니다.

#4동작 과정

  1. 인스턴스 타입 검색AWS 콘솔이나 CLI에서 필요한 vCPU 수, 메모리, 네트워크 성능 같은 조건을 입력하면 조건을 만족하는 타입 목록이 나옵니다.
  2. Compute Optimizer 추천 참고인스턴스가 이미 실행 중이면 Compute Optimizer가 지난 30일의 실제 사용률(CPU, 메모리, 네트워크)을 분석해 최적 타입을 추천합니다.
  3. 리사이즈 작업EBS 루트 볼륨의 인스턴스만 해당(인스턴스 스토어는 불가). 인스턴스를 중지하고 타입을 변경한 후 재시작합니다. 중지 기간 동안 비용은 청구되지 않습니다(EBS 비용만 청구).

#5한 줄 요약

콘솔·CLI 검색과 Compute Optimizer 추천으로 적절한 인스턴스 타입을 찾고, 중지 후 리사이즈해 타입을 변경하는 방식

3AMI — 무엇으로 부팅하는가03-01

AMI란 무엇이며 무엇에 묶여 있는가: 리전·OS·아키텍처·루트 볼륨·가상화 타입

AMI는 인스턴스를 부팅할 때 쓰는 템플릿으로, OS·아키텍처·루트 볼륨 유형(EBS/인스턴스 스토어)·가상화 타입이 정해져 있고 리전 단위로 존재한다.

#1문제 상황

인스턴스를 시작하면 빈 가상 머신이 아니라 OS(Ubuntu, Amazon Linux, Windows)가 미리 설치되어 있어야 부팅 후 바로 사용할 수 있습니다. 이를 위해서는 인스턴스를 부팅할 디스크 이미지가 미리 준비되어 있어야 합니다. 또한 그 디스크는 특정 리전에만 존재하고, x86 아키텍처용(Intel/AMD)인지 Arm 아키텍처용(Graviton)인지도 결정되어 있으며, EBS 볼륨에 저장되는지 인스턴스 스토어(일시 스토리지)에 저장되는지도 미리 정해져 있습니다.

#2핵심 질문

인스턴스를 부팅할 때 OS와 기본 설정이 담긴 디스크 이미지(AMI)를 어떻게 정의하고 제약하는가?

#3동작 예시

"ami-0c123456789abcdef0"라는 AMI는 실제로 "us-east-1 리전, Ubuntu 20.04 LTS, x86_64 아키텍처, EBS 루트 볼륨, HVM 가상화" 같은 모든 정보를 담고 있습니다. 같은 AMI를 다른 리전(예: us-west-2)에서는 사용할 수 없으며, Arm 인스턴스(t4g)와도 호환되지 않습니다. 하지만 다른 리전으로 복사(copy)하면 새로운 AMI ID를 얻게 됩니다.

#4동작 과정

  1. AMI 기본 정보 결정어떤 OS를 쓸지(Ubuntu, Amazon Linux, CentOS, Windows), 아키텍처는 뭔지(x86_64 또는 arm64), 루트 볼륨은 어디에 저장할지(EBS 또는 인스턴스 스토어)를 미리 정합니다. 이 조합이 AMI를 만드는 기반입니다.
  2. 가상화 타입 선택HVM(Hardware Virtual Machine, 최신) 또는 PV(Paravirtual, 구식) 중 선택합니다. 현재는 거의 모든 AMI가 HVM입니다.
  3. 리전 바인딩AMI는 생성된 리전에만 존재합니다. 인스턴스를 다른 리전에서 시작하려면 먼저 그 리전으로 AMI를 복사해야 합니다.

#5한 줄 요약

인스턴스 부팅에 필요한 OS, 아키텍처, 루트 볼륨 유형, 가상화 방식을 조합한 디스크 이미지(AMI)를 리전 단위로 관리하는 것

AMI 찾기: 콘솔 카탈로그·SSM 퍼블릭 파라미터·Marketplace 유료 AMI

필요한 AMI는 콘솔/CLI 카탈로그 검색, SSM 퍼블릭 파라미터로 최신 ID 자동 조회, AWS Marketplace의 유료 AMI 중에서 고른다.

#1문제 상황

필요한 AMI를 찾는 방법이 여러 가지 있습니다. AWS 콘솔에서 직접 검색할 수도 있지만, 최신 버전을 매번 수동으로 찾아야 하는 번거로움이 있습니다. 또한 Marketplace의 유료 AMI(데이터베이스, 방화벽 등 사전 구성된 소프트웨어)도 있는데, 이것들의 라이선스와 가격을 일일이 확인해야 합니다. 자동화된 배포에서는 AMI ID를 하드코딩하기 어렵습니다.

#2핵심 질문

필요한 AMI를 효율적으로 찾고, 특히 최신 버전을 자동으로 추적할 수 있을까?

#3동작 예시

CloudFormation이나 Terraform으로 배포 코드를 작성할 때, Ubuntu 20.04 최신 버전을 매번 수동으로 찾는 대신 SSM 퍼블릭 파라미터 "/aws/service/ubuntu/com/canonical/ubuntu/server/20.04/stable/current/amd64/hvm/ebs-gp2"를 그대로 사용하면 항상 최신 AMI ID가 자동으로 조회됩니다. AWS가 Ubuntu를 업데이트하면 파라미터 값이 자동으로 갱신되므로 배포 코드는 수정할 필요가 없습니다.

#4동작 과정

  1. 콘솔 카탈로그 검색AWS 콘솔의 "EC2 → AMI"에서 소유자(Amazon, AWS Marketplace, 커뮤니티), OS, 아키텍처로 필터링하면 조건을 만족하는 AMI 목록이 나옵니다. 메타데이터(생성일, 루트 디바이스 타입)를 확인한 후 선택합니다.
  2. SSM 퍼블릭 파라미터 조회AWS Systems Manager의 Parameter Store에 보관된 공식 AMI ID를 CLI 또는 인프라 코드에서 조회합니다. 예: aws ssm get-parameters-by-path 명령으로 특정 경로의 파라미터를 자동으로 찾고 최신 값을 가져옵니다.
  3. Marketplace 탐색AWS Marketplace에서 필요한 소프트웨어(예: MongoDB, Splunk, Fortinet 방화벽)를 검색하면 구성된 AMI와 그 라이선스 조건, 시간당 추가 요금이 표시됩니다. 선택하면 해당 AMI로 인스턴스를 시작할 수 있습니다.

AMI 공유와 공개 제어

AMI는 특정 계정·조직에 공유하거나 퍼블릭으로 풀 수 있고, 퍼블릭 액세스 차단과 Allowed AMIs로 조직이 쓸 수 있는 이미지를 제한한다.

#1문제 상황

기존에는 만든 AMI가 자신의 계정에만 있고, 다른 조직이나 팀과 공유하려면 방법이 제한적이었습니다. 공유 범위를 세밀하게 제어할 수 없었고, 실수로 퍼블릭 공개되면 보안 문제가 될 수 있었습니다.

#2핵심 질문

팀 내부나 특정 조직에만 AMI를 공유하되, 퍼블릭 공개는 어떻게 막을 것인가?

#3동작 예시

AMI의 권한(permission)을 설정해서 특정 AWS 계정이나 조직 단위로 공개 범위를 제한할 수 있고, 조직 전체에 "이 AMI들만 써야 한다"는 정책(Allowed AMIs)을 적용할 수 있습니다.

#4동작 과정

인스턴스가 실행 중이면, 원격으로 셸에 접속해서 명령을 실행하거나 파일을 옮겨야 합니다. 리눅스 인스턴스와 윈도우 인스턴스는 접속 프로토콜이 다릅니다. 리눅스 서버에 접속하려면 전통적으로 Telnet이나 Rlogin을 썼지만 암호화가 없어서 위험했고, 윈도우 서버에는 원격 데스크톱(RDP)을 사용했습니다.

#2핵심 질문

리눅스와 윈도우에 원격으로 안전하게 접속하고 파일을 옮기려면 어떤 도구를 써야 하는가?

#3동작 예시

리눅스는 SSH(Secure Shell, 암호화된 원격 셸)를 사용합니다. 사용자가 ssh -i 개인키 사용자@인스턴스 명령으로 접속하면 암호화된 통신이 시작되고, 키 인증이 끝나면 인스턴스의 셸에 접속합니다. 윈도우는 RDP(Remote Desktop Protocol)를 사용해서 mstsc.exe 또는 리모트 데스크톱 클라이언트로 접속하면 그래픽 데스크톱 화면이 나타납니다.

#4동작 과정

  1. 프로토콜 선택 및 연결리눅스 인스턴스면 SSH로, 윈도우 인스턴스면 RDP로 접속합니다. SSH는 22번 포트, RDP는 3389번 포트를 기본으로 사용하며, 이 포트들이 보안 그룹에서 열려 있어야 합니다.
  2. 인증 및 세션 시작SSH는 개인키로 인증한 후 셸 프롬프트를 받고, RDP는 사용자 계정과 비밀번호(또는 MFA)로 인증한 후 데스크톱 세션을 받습니다.
  3. 파일 전송SSH를 쓰면 SCP(Secure Copy) 또는 SFTP(SSH File Transfer Protocol)로 파일을 로컬과 인스턴스 사이에 주고받습니다. RDP는 복사-붙여넣기나 클라이언트의 드라이브 리디렉션 기능으로 파일을 전송할 수 있습니다.

EC2 Instance Connect와 Instance Connect Endpoint

브라우저나 CLI에서 임시 키를 밀어 넣어 접속하는 방식으로, 엔드포인트를 쓰면 퍼블릭 IP 없는 프라이빗 인스턴스에도 붙을 수 있다.

#1문제 상황

SSH나 RDP로 접속하려면 반드시 인스턴스에 퍼블릭 IP나 탄력적 IP가 있어야 하고, 해당 포트(22번 또는 3389번)가 보안 그룹에서 열려 있어야 합니다. 하지만 보안상 많은 조직에서 퍼블릭 IP를 할당하지 않고 프라이빗 서브넷에만 인스턴스를 놓고 싶어 합니다. 또한 SSH 키나 비밀번호 관리도 복잡합니다.

#2핵심 질문

퍼블릭 IP 없이 인스턴스 포트를 열지 않고도 안전하게 접속할 수 있는 방법이 있을까?

#3동작 예시

EC2 Instance Connect Endpoint(접속 엔드포인트)를 사용합니다. 이 엔드포인트는 VPC 내부에 위치하고, AWS에서 임시 세션 토큰을 발급합니다. 사용자는 브라우저 콘솔이나 로컬 SSH 클라이언트로 이 엔드포인트에 접속하면, 엔드포인트가 프라이빗 인스턴스에 대한 트래픽을 중계해줍니다.

#4동작 과정

  1. 엔드포인트 배포VPC 내에 Instance Connect Endpoint를 한 개 배포합니다. 이것은 프라이빗 서브넷에 있으면서도 AWS가 관리하는 ENI(탄력적 네트워크 인터페이스)입니다.
  2. 임시 토큰 발급사용자가 브라우저 콘솔이나 CLI(aws ec2-instance-connect open-tunnel)로 요청하면, AWS가 임시 세션 토큰을 만들고 엔드포인트에 로컬 포트를 포워드합니다.
  3. 중계를 통한 접속사용자의 SSH 클라이언트가 로컬 포트(보통 localhost:22)에 접속하면, 엔드포인트가 프라이빗 인스턴스의 SSH 포트로 중계하므로 퍼블릭 IP나 보안 그룹 규칙 없이도 접속이 가능합니다.

Session Manager와 EC2 Serial Console — 포트를 열지 않는 접속

인바운드 포트를 전혀 열지 않고 SSM 에이전트나 시리얼 콘솔을 통해 셸이나 부팅 화면에 접근하는 방법.

#1문제 상황

SSH나 RDP는 인스턴스의 OS가 정상적으로 부팅되고 네트워크 서비스가 실행되어야만 접속할 수 있습니다. 하지만 인스턴스가 부팅 중일 때, 커널 패닉으로 멈췄을 때, 또는 잘못된 보안 그룹 설정으로 포트가 막혔을 때는 이 방법들이 작동하지 않습니다. 또한 SSH 키나 비밀번호 관리의 부담도 있습니다.

#2핵심 질문

OS가 완전히 부팅되지 않았거나 네트워크 접속이 불가능할 때도 인스턴스에 접근할 수 있는 방법이 있을까?

#3동작 예시

AWS Systems Manager의 Session Manager와 EC2 Serial Console을 사용합니다. 인스턴스에 SSM 에이전트를 설치하고 IAM 권한을 주면, AWS 콘솔이나 CLI에서 직접 세션을 열 수 있습니다. Serial Console은 더 낮은 수준에서 작동해서 부팅 메시지나 GRUB 메뉴 같은 시스템 콘솔 출력을 볼 수 있습니다.

#4동작 과정

  1. 에이전트 설치 및 IAM 권한 설정인스턴스에 SSM 에이전트를 설치하고(대부분 기본 설치됨), 해당 인스턴스 역할(IAM role)에 AmazonSSMManagedInstanceCore 정책을 연결합니다.
  2. AWS 콘솔이나 CLI에서 세션 개시사용자가 AWS 콘솔의 Session Manager 또는 aws ssm start-session 명령을 실행하면, AWS 백엔드가 SSM 에이전트를 통해 인스턴스에 암호화된 채널을 열고 셸 접속을 제공합니다.
  3. 포트 개방 불필요SSH나 RDP 포트가 열려 있지 않아도 되고, 개인키나 비밀번호를 입력할 필요도 없으며, IAM 권한 관리만으로 접속 통제가 됩니다. Serial Console은 더 낮은 수준의 시스템 콘솔 접근을 제공합니다.

#3동작 예시

AWS는 각 인스턴스 내부에서 링크로컬 주소 169.254.169.254에 메타데이터 서버를 띄웁니다. 인스턴스 내부의 애플리케이션이 이 주소에 HTTP 요청을 보내면, 자신의 메타데이터와 IAM 역할의 임시 자격 증명을 받을 수 있습니다. IMDSv1은 단순히 요청만 보내면 되지만 SSRF 공격에 취약하므로, IMDSv2는 요청할 때마다 임시 토큰을 먼저 받아야 합니다.

#4동작 과정

  1. IMDSv2 토큰 요청인스턴스 내부의 애플리케이션이 PUT /latest/api/token 요청을 보내고 TTL(유효 시간)을 지정하면, 메타데이터 서버가 임시 토큰을 발급합니다.

  3. IAM 자격 증명 자동 갱신인스턴스 역할이 있으면 /latest/meta-data/iam/security-credentials/역할이름 경로에서 임시 액세스 키, 시크릿 키, 세션 토큰을 받고, 만료되기 전에 자동으로 갱신됩니다.

인스턴스 상태 전이 지도: pending에서 terminated까지

EC2 인스턴스가 pending, running, stopping, stopped, shutting-down, terminated 상태를 오가며 각 상태에서 과금과 가능한 조작이 달라지는 흐름을 한눈에 보는 것.

#1문제 상황

인스턴스가 만들어지고 삭제되는 사이에 여러 상태를 거칩니다. 사용자는 인스턴스가 언제 사용 가능한지, 언제 비용이 부과되는지, 어느 상태에서 어떤 조작이 가능한지 알아야 합니다. 상태 전이를 모르면 인스턴스가 어떤 상황인지 판단하기 어렵고, 예상과 다른 비용이 부과될 수 있습니다.

#2핵심 질문

EC2 인스턴스는 생성부터 종료까지 어떤 상태들을 거치고, 각 상태에서 무엇이 가능하고 비용은 어떻게 되는가?

#3동작 예시

인스턴스는 pending → running → stopped → terminated 같은 선형적 흐름을 거치기도 하고, running → stopping → stopped → running 같이 같은 상태를 여러 번 오갈 수도 있습니다. 각 상태로의 진입은 사용자의 조작(시작, 중지, 종료) 또는 인스턴스의 내부 이벤트(비정상 종료)로 일어납니다.

#4동작 과정

  1. 인스턴스 시작pending → running** — RunInstances 명령으로 인스턴스를 만들면 pending 상태로 들어갔다가 OS가 부팅되고 네트워크가 설정되면 running 상태로 진입합니다. 이 시점부터 compute 시간에 대해 과금됩니다.
  2. 중지/종료 및 상태 전이사용자가 StopInstances를 호출하면 stopping 상태로 들어갔다가 stopped로 진입하고(이 상태에서는 compute 과금이 없음), TerminateInstances를 호출하면 shutting-down 상태를 거쳐 terminated가 되고(이 상태에서는 조작 불가능하고 과금도 없음), StartInstances로 다시 pending → running으로 갈 수 있습니다.
  3. 강제 재시작 및 특수 상황인스턴스가 비정상 종료되거나 호스트 유지보수가 필요하면 stopping-halted 상태를 거칠 수 있으며, 일부 상태에서는 상태 전이 중에 조작을 수락하지 않습니다.

인스턴스를 중지하면 메모리 내용과 인스턴스 스토어 데이터는 사라지고 EBS 볼륨과 프라이빗 IP는 남으며, 다시 시작하면 대개 호스트와 퍼블릭 IP가 바뀐다.

#1문제 상황

인스턴스를 중지하면 compute 비용이 나가지 않지만, 메모리나 스토리지 상태가 어떻게 되는지, 네트워크 설정이 유지되는지 불명확합니다. 또한 중지했던 인스턴스를 다시 시작할 때 호스트 머신이 바뀌면 퍼블릭 IP나 IP 주소도 바뀔 수 있다는 걸 모르면, 운영 중에 예상 밖의 접속 문제를 겪을 수 있습니다.

#2핵심 질문

#1문제 상황

컴퓨터가 네트워크 통신을 하려면 IP 주소가 필요하다. 하지만 EC2 인스턴스는 단순히 하나의 IP만으로는 부족할 수 있다. 내부 통신(VPC 내의 다른 인스턴스와 통신)을 위한 IP와 인터넷 통신을 위한 IP는 다르고, 여러 서비스를 동시에 운영하거나 고가용성을 위해 더 많은 IP가 필요할 수 있다. 또한 인스턴스를 재시작하면 IP가 변하는 경우도 있어서 안정성 문제가 생긴다.

#2핵심 질문

EC2 인스턴스가 VPC 내부와 외부에서 안정적으로 통신하려면 어떤 종류의 IP 주소들이 필요하고 어떻게 할당되는가?

#3동작 예시

인스턴스에는 기본적으로 VPC 내부 통신용 프라이빗 IPv4 주소(예: 10.0.1.5)가 자동으로 할당되고, 인터넷 통신이 필요하면 퍼블릭 IPv4 주소(AWS가 임시로 할당하거나 사용자가 탄력적 IP로 고정)를 추가로 연결할 수 있으며, IPv6 주소나 여러 프라이빗 IP 주소도 필요에 따라 동일 ENI에 할당할 수 있다.

#4동작 과정

  1. 프라이빗 IPv4 자동 할당인스턴스가 선택된 서브넷에서 시작되면 AWS가 자동으로 그 서브넷의 IP 범위에서 하나의 프라이빗 IP를 할당하며, 이는 인스턴스 재시작 후에도 유지된다.
  2. 퍼블릭 IP 할당 설정인스턴스 시작 시 퍼블릭 IPv4를 자동 할당하거나, 탄력적 IP(Elastic IP, 계정 소유의 고정 퍼블릭 IP)를 직접 연결하여 재시작 후에도 동일한 외부 IP를 유지한다.
  3. 추가 IP 할당 (필요시)로드 밸런싱, 다중 호스트명(multihoming), 또는 IPv6 지원이 필요하면 같은 네트워크 인터페이스에 여러 프라이빗 IP나 IPv6 주소를 추가 할당할 수 있다.

#1문제 상황

ENI는 인스턴스에 붙였다 뗄 수 있는 가상 랜카드로, 여러 개를 붙이거나 IP 프리픽스를 위임해 주소를 대량 할당할 수 있다.

→ 07-02 참조

#1문제 상황

물리 컴퓨터의 랜카드는 보통 하나지만, 여러 네트워크 경로가 필요하거나 고가용성을 위해 여러 개를 달 수 있다. EC2도 마찬가지인데, 기본 네트워크 인터페이스만으로는 여러 IP를 효율적으로 관리하거나, 인터페이스 장애 시 빠르게 전환하기 어렵다. 또한 대량의 IP를 할당해야 하는 상황에서는 각각 설정하는 것이 비효율적이다.

#2핵심 질문

EC2 인스턴스에 여러 개의 네트워크 인터페이스를 붙여서 더 많은 IP와 네트워크 경로를 동시에 지원하고, 필요하면 다른 인스턴스로 옮길 수 있을까?

#3동작 예시

ENI(Elastic Network Interface, 탄력적 네트워크 인터페이스)는 실제 네트워크 랜카드처럼 동작하는 가상 네트워크 인터페이스로, 인스턴스 실행 중에도 여러 개를 붙였다 뗄 수 있고, 각 ENI마다 여러 개의 프라이빗 IP를 할당하거나 퍼블릭 IP를 연결할 수 있으며, 심지어 한 인스턴스에서 분리해 다른 인스턴스에 연결하는 것도 가능하다.

#4동작 과정

  1. ENI 생성 및 사전 구성VPC 내에서 ENI를 생성하고, 프라이빗 IP 주소(또는 IP 프리픽스 위임)와 보안 그룹을 설정한다.
  2. 인스턴스에 ENI 연결인스턴스가 실행 중인 상태에서도 추가 ENI를 네트워크 인터페이스로 연결하면 새 인터페이스가 활성화된다.
  3. OS에서 인터페이스 구성 및 라우팅인스턴스 OS에서 eth0, eth1 등으로 새 인터페이스를 인식하고, 프라이빗 IP와 라우팅 규칙을 설정하여 각 인터페이스를 독립적으로 운영할 수 있다.

보안 그룹: 규칙 설계와 연결 추적

보안 그룹은 인스턴스 앞단의 가상 방화벽으로, 허용 규칙만 정의하며 연결 추적(stateful) 덕분에 응답 트래픽은 자동으로 통과한다.

#1문제 상황

EC2 인스턴스가 네트워크에 연결되면 외부의 원치 않는 트래픽(공격, 스캔, 스팸 등)으로부터 노출된다. 전통적인 방화벽은 들어오는 트래픽(인바운드)과 나가는 트래픽(아웃바운드)을 모두 명시적으로 정의해야 했는데, 이는 설정이 복잡하고, 특히 응답 트래픽을 위한 규칙을 일일이 작성해야 했다.

#2핵심 질문

EC2 인스턴스가 불필요한 트래픽은 차단하면서도, 정상적인 양방향 통신은 복잡한 규칙 작성 없이 어떻게 효율적으로 제어할 수 있을까?

#3동작 예시

보안 그룹은 인스턴스 앞단에 붙는 가상 방화벽으로, "허용할 규칙만" 정의하면 (예: TCP 22번 포트로 SSH 접속 허용, TCP 80번 포트로 HTTP 접속 허용) AWS의 내장된 "연결 추적(stateful firewall)" 기능이 그 규칙을 통해 들어온 요청의 응답 트래픽은 자동으로 통과시킨다.

#4동작 과정

  1. 보안 그룹 생성 및 인바운드 규칙 정의VPC 내에서 보안 그룹을 생성하고 인스턴스가 받을 트래픽을 정의한다 (예: 프로토콜=TCP, 포트=22, 소스=특정 IP 또는 보안 그룹).
  2. 인스턴스에 보안 그룹 적용인스턴스 시작 시 하나 이상의 보안 그룹을 선택하면 그 규칙들이 네트워크 인터페이스에 즉시 적용된다.
  3. 연결 추적으로 응답 자동 허용허용된 인바운드 규칙을 통해 들어온 요청에 대한 응답은 보안 그룹이 자동으로 추적하여 명시적인 아웃바운드 규칙 없이도 통과시킨다.

#5한 줄 요약

보안 그룹이 인스턴스의 네트워크 접근을 허용 규칙과 상태 추적(stateful tracking)으로 제어하여 불필요한 트래픽은 차단하고 허용된 통신의 양방향 흐름을 투명하게 보장하는 가상 방화벽

인스턴스 타입마다 네트워크 대역폭 상한과 MTU가 정해져 있고, ENA 기반 향상된 네트워킹으로 더 높은 처리량과 낮은 지연을 얻는다.

#1문제 상황

일반적인 가상 서버 네트워킹은 호스트 OS의 가상 NIC 드라이버를 거쳐 패킷을 보낸다. 이 과정에서 CPU 오버헤드가 크고, 대역폭이 제한된다. 높은 처리량이 필요한 작업(HPC, 고속 데이터 전송, 분산 시스템)에서는 네트워크 병목이 생긴다. 또한 MTU(Maximum Transmission Unit, 한 번에 보낼 수 있는 최대 패킷 크기)도 인스턴스 타입별로 정해져 있어 유연성이 떨어진다.

#2핵심 질문

인스턴스 타입의 제약 속에서 네트워크 성능을 더 효율적으로 높일 수 있을까?

#3동작 예시

ENA(Elastic Network Adapter)는 가상화 오버헤드를 줄이는 전용 네트워크 하드웨어 추상화 계층이다. 일반 가상 드라이버 대신 ENA 드라이버를 사용하면, EC2 인스턴스에서 직접 네트워크 하드웨어에 가까워져 CPU 사용률을 낮추면서도 더 많은 패킷을 더 빠르게 보낼 수 있다. ENA Express는 여기서 한 단계 더 나아가 VPC 내 인스턴스 간 통신을 더욱 최적화해 지연을 크게 줄인다.

#4동작 과정

  1. 네트워크 드라이버 선택기본 가상 NIC는 하이퍼바이저를 거쳐 패킷을 처리한다. ENA를 활성화한 인스턴스는 ENA 드라이버를 로드해서, 더 직접적인 경로로 패킷을 보내고 받는다.
  2. MTU와 대역폭 설정인스턴스 타입에 따라 최대 대역폭(예: 10Gbps, 25Gbps)과 지원하는 최대 MTU(최대 9,000 바이트)가 정해진다. 네트워크 성능을 최대한 활용하려면 이 값들을 인스턴스와 VPC 설정에 맞춰야 한다.
  3. ENA Express 선택VPC 통신에서 ENA Express를 활성화하면, 추가 하드웨어 최적화로 지연을 마이크로초 단위로 줄일 수 있다. 금융, 기계 학습 등 극도로 낮은 지연이 필요한 작업에 쓰인다.

#1문제 상황

EC2 인스턴스들이 일반 네트워킹으로 통신하면 VPC 라우팅, 스위치, 여러 물리적 거리를 거친다. 데이터 센터 내 같은 랙이라도 몇십 마이크로초의 지연이 발생한다. 고성능 컴퓨팅(HPC)이나 분산 머신 러닝 같이 인스턴스 간 통신이 매 순간 일어나는 작업에서는 이 지연이 전체 성능의 병목이 된다.

#2핵심 질문

여러 인스턴스가 수없이 주고받아야 하는 작업에서, 네트워크 지연을 극단적으로 줄일 수 있을까?

#3동작 예시

EFA(Elastic Fabric Adapter)는 HPC 전용 네트워크 어댑터로, 배치 그룹과 함께 사용하면 같은 물리적 서버나 가까운 서버들을 짧은 거리의 고속 네트워크로 직접 연결한다. 예를 들어 분산 학습에서 여러 GPU 인스턴스가 그래디언트(학습 가중치 업데이트)를 주고받을 때, EFA와 배치 그룹을 쓰면 평소보다 지연을 1/10 이하로 줄일 수 있다.

#4동작 과정

  1. 배치 그룹 생성원하는 배치 그룹 정책(클러스터, 파티션, 스프레드)을 선택해 그룹을 만든다. 클러스터 정책을 선택하면 인스턴스들이 같은 가용 영역의 가까운 하드웨어에 배치되도록 AWS가 보장한다.
  2. EFA 활성화배치 그룹에 속한 인스턴스에 EFA 네트워크 인터페이스를 붙인다. OS와 애플리케이션이 EFA 드라이버를 사용하게 되면, 가상화 오버헤드 없이 거의 물리적 네트워크 수준에 가까운 통신이 가능해진다.
  3. 통신 수행애플리케이션에서 MPI(Message Passing Interface) 같은 고성능 통신 라이브러리를 사용해 데이터를 주고받는다. EFA 덕분에 마이크로초 단위의 지연으로 메시지를 전달받는다.

#3동작 예시

#1문제 상황

온디맨드 가격은 어느 인스턴스에나 같은 시간당 가격을 적용한다. 장기간 특정 인스턴스를 고정으로 쓸 계획이면, 무조건 온디맨드 가격을 내야 한다. 또한 요구 사항이 조금 바뀌면(예: 인스턴스 타입 변경, 리전 이전) 계약이 끝날 때까지 원래 계획에 묶여 있다.

#2핵심 질문

특정 인스턴스를 정해진 기간 동안 보유하겠다고 약정하면 어떤 방식으로 할인을 받을 수 있을까?

#3동작 예시

#4동작 과정

  1. 예약 인스턴스 구매AWS 콘솔에서 인스턴스 타입(m5.large 등)과 스코프(리전 또는 특정 가용 영역), 클래스(표준 또는 컨버터블), 기간(1년 또는 3년)을 선택해 구매한다. 결제는 전액 선결제, 부분 선결제, 월별 결제 중 하나.

  3. 스코프와 클래스의 영향리전 스코프 RI는 그 리전 내 어떤 가용 영역에서든 할인을 받지만, 가용 영역 스코프는 정해진 한 가용 영역에서만 받는다. 컨버터블을 쓰면 기간 중에 인스턴스 타입을 바꿀 수 있어 유연하지만, 표준 RI보다 할인율이 낮다.

#1문제 상황

예약 인스턴스를 한 번 구매하면 약정 기간이 끝날 때까지 고정이다. 비즈니스 요구가 바뀌거나 예측이 틀려서 다른 사양의 인스턴스가 필요하면, 남은 기간을 무용지물로 두거나 새로 구매해야 한다.

#2핵심 질문

구매 후 변경된 요구 사항에 맞춰 예약 인스턴스를 유연하게 조정할 수는 없을까?

#3동작 예시

표준 RI(Reserved Instance)를 샀으면 수정으로 같은 타입의 가용 영역 스코프를 바꿀 수 있다(예: us-east-1a에서 us-east-1b로). 컨버터블 RI를 샀으면 다른 인스턴스 타입으로 "교환"할 수 있는데, 교환할 때 기간과 같은 가격 이상의 RI를 골라야 한다. 어느 쪽이든 예약을 팔고 싶으면, AWS RI 마켓플레이스에 올려서 남은 기간만큼 다른 고객에게 팔 수 있다.

#4동작 과정

  1. 수정 또는 교환표준 RI는 수정(가용 영역 스코프 변경, 인스턴스 크기 조정 같은 일부 변경)을 할 수 있다. 컨버터블은 교환 요청으로 다른 타입의 RI를 얻는다. 교환 시에는 기존 RI가 취소되고 새 RI가 발급된다.
  2. 마켓플레이스 판매더 이상 필요 없으면 AWS RI 마켓플레이스에 판매 요청을 올린다. 가격은 자유롭게 정할 수 있지만, 남은 기간이 중요한 판매 가능성의 요인이 된다. 구매자가 나타나면 남은 기간의 권리가 이전되고, 판매가를 받는다.
  3. 마켓플레이스 구매남은 기간의 RI를 저가에 사고 싶으면, 마켓플레이스에서 다른 사용자가 팔아주는 RI를 구매할 수 있다.

#1문제 상황

온디맨드 가격은 고정이고, 언제든 인스턴스를 시작할 수 있다. 대신 가격은 높다. 장시간 안정적으로 돌아야 하는 워크로드가 아니라면, 고정 가격을 낼 이유가 없다. 특히 배치 처리나 분석 작업처럼 시작·중단을 반복하거나, 잠깐 고성능 자원이 필요한 경우 비용이 낭비된다.

#2핵심 질문

사용 가능한 남는 용량을 활용해, 훨씬 저렴하게 인스턴스를 빌려 쓸 수는 없을까?

#3동작 예시

스팟 인스턴스는 AWS 데이터 센터의 남는 용량을 사용하는 인스턴스다. 온디맨드 가격이 시간당 $1이면, 스팟 가격은 공급 상황에 따라 시간당 $0.1~$0.5 정도로 심하게 변한다. 스팟 풀(같은 타입의 스팟 가격을 제시하는 가용 영역·인스턴스 타입 조합)별로 가격이 다르므로, 가격 이력을 보고 싼 풀에서 요청하면 된다. 대신 AWS가 용량을 회수해야 하면 2분 경고 후 인스턴스가 중단된다.

#4동작 과정

  1. 스팟 가격 이력 확인EC2 콘솔에서 스팟 가격 이력을 조회해 지난 3개월간 각 풀(가용 영역 + 인스턴스 타입)의 가격 변동을 본다. 가격 변동이 낮은 풀을 고르면 중단 가능성도 낮다.
  2. 스팟 요청 생성원하는 풀(또는 여러 풀)을 선택해 스팟 요청을 만든다. 입찰 가격을 온디맨드 이상으로 설정하면(기본값), 현재 스팟 가격이 입찰가 이하인 한 인스턴스가 공급된다.
  3. 인스턴스 실행 및 중단 대비스팟 인스턴스가 할당되면 일반 온디맨드처럼 쓴다. 중단 위험에 대비해 애플리케이션은 상태 저장(체크포인트)과 빠른 재시작을 지원해야 한다.

#3동작 예시

스팟 인스턴스 중단을 대비하는 방법은 세 가지다. 첫째, 중단 알림(2분 전에 EC2 인스턴스 메타데이터 API를 통해 알림)을 받아서 애플리케이션을 정상 종료한다. 둘째, 리밸런스 권고가 오면 새 스팟 인스턴스로 워크로드를 옮기고 이전 것을 중단한다. 셋째, 스팟 배치 점수(AWS가 계산하는 중단 확률 지표: 1~10, 낮을수록 안정적)를 보고 안정적인 풀에서만 요청한다.

#4동작 과정

  1. 중단 동작 설정스팟 요청 시에 인스턴스가 회수될 때 어떻게 할지 선택한다. 종료(terminate)는 인스턴스를 즉시 삭제하고, 중지(stop)는 일시 정지해 나중에 다시 시작할 수 있게 하며, 최대 절전(hibernate)은 메모리 상태를 디스크에 저장한다.
  2. 중단 알림과 정상 종료인스턴스가 회수 2분 전에 EC2 인스턴스 메타데이터(169.254.169.254)의 종료 알림 엔드포인트로 요청이 들어온다. 애플리케이션이 이를 감지해 현재 작업을 마무리하고 상태를 저장한 뒤 정상 종료한다.
  3. 리밸런스 권고와 배치 점수중단 위험이 높아지면 리밸런스 권고가 온다. 이때 새 스팟 인스턴스를 요청해 워크로드를 옮기고 기존 것을 정상 종료할 수 있다. 처음부터 배치 점수(1~2는 안정적, 8~10은 불안정)를 확인해 안정적인 풀만 고르는 것이 더 효과적이다.

#2핵심 질문

#4동작 과정

  1. 테넌시 옵션 선택인스턴스 생성 시 "전용 호스트"(물리 서버 독점) 또는 "전용 인스턴스"(당신 계정 전용 격리) 중 하나를 선택합니다.

→ 08-04 참조

#1문제 상황

온디맨드 인스턴스는 안정적이지만 비싸고, 스팟 인스턴스는 저렴하지만 언제든 뺏길 수 있습니다. 둘을 섞어 쓰는 것이 경제적이지만, 여러 인스턴스 타입을 조합하면서 온디맨드와 스팟을 배치하는 것을 직접 관리하는 것은 복잡합니다.

#2핵심 질문

온디맨드와 스팟을 섞어서 원하는 용량을 자동으로 채우고, 타입별 비용·가용성을 고려해 최적의 인스턴스를 선택하는 플릿을 만들 수 있을까?

#3동작 예시

한 요청에서 인스턴스 타입 여러 개(예: c5.large, m5.large, t3.large)와 구매 옵션(온디맨드 70%, 스팟 30%), 할당 전략(최저가 또는 분산)을 지정하면, EC2 Fleet이 현재 가격·가용성을 고려해 자동으로 조합을 결정하고 필요한 용량을 채웁니다.

#4동작 과정

  1. 플릿 설정 정의총 몇 개 인스턴스가 필요한지(또는 총 vCPU·메모리), 어느 인스턴스 타입들이 괜찮은지(속성 기반: 예를 들어 "2~8 vCPU, 4~16 GB 메모리"), 온디맨드와 스팟의 비율, 가중치(일부 타입을 더 우선할지), 할당 전략(최저가·분산·용량·우선순위 등)을 설정합니다.
  2. 인스턴스 선택 및 시작Fleet이 설정과 현재 가격·가용성을 고려해 최적 타입·구매 옵션 조합을 계산하고, 인스턴스를 띄웁니다(예: c5.large 온디맨드 3개 + t3.large 스팟 2개).
  3. 자동 유지 및 교체스팟이 뺏기거나 비용이 싼 타입이 나타나거나 타입 가용성이 떨어지면, Fleet이 자동으로 인스턴스를 교체해 설정된 상태를 유지합니다.

#2핵심 질문

#4동작 과정

인스턴스에 역할을 붙여 액세스 키를 심지 않고도 임시 자격 증명으로 AWS 서비스를 호출하게 하는 구조.

#1문제 상황

인스턴스 안에서 AWS API를 호출하려면(예: S3에서 파일 읽기, DynamoDB에 데이터 쓰기), 그 인스턴스에 AWS 접속 자격 증명(액세스 키·시크릿 키)을 심어야 합니다. 하지만 자격 증명을 평문 파일로 인스턴스에 저장하면, 해킹당했을 때 자격 증명이 유출되기 쉽고, 자격 증명을 갱신할 때마다 인스턴스를 수정해야 하는 번거로움이 있습니다.

#2핵심 질문

인스턴스에 자격 증명 파일을 넣지 않고도 AWS API를 호출할 수 있을까?

#3동작 예시

IAM 역할(Role)을 인스턴스에 붙이면, AWS가 인스턴스 내부에서만 접근 가능한 메타데이터 엔드포인트(http://169.254.169.254/...)를 통해 임시 자격 증명(토큰처럼 시간 제한이 있는 증명)을 자동으로 제공하고, 만료되면 알아서 새로 발급합니다. 인스턴스는 자격 증명 파일이 필요 없습니다.

#4동작 과정

  1. IAM 역할 생성"S3 읽기", "CloudWatch 로그 쓰기", "DynamoDB 접근" 등의 권한을 포함하는 IAM 역할을 정의합니다. 이 역할은 어떤 AWS 리소스에 접근할 수 있는지를 나타냅니다.
  2. 인스턴스 프로파일과 역할 연결인스턴스 프로파일(Instance Profile)이 IAM 역할을 감싸는 컨테이너 역할을 하며, 이를 EC2 인스턴스에 붙입니다. 인스턴스가 시작되면 AWS가 프로파일 정보를 인스턴스에 제공합니다.
  3. 애플리케이션에서 자동 자격 증명 사용인스턴스 안의 애플리케이션이 AWS SDK를 쓸 때, SDK가 메타데이터 엔드포인트에 요청을 보내 임시 자격 증명을 받아서 자동으로 API 호출에 포함시킵니다. 개발자는 자격 증명을 하드코딩할 필요가 없습니다.

CloudWatch 경보가 임계값을 넘으면 인스턴스를 자동으로 중지·종료·재부팅하거나 새 하드웨어로 복구하도록 설정하는 기능.

→ 11-02 참조

#1문제 상황

CloudWatch로 지표를 수집해도 문제를 감지하기만 하면 인스턴스가 느리거나 가동이 중단되어도 누군가 수동으로 확인하고 대응해야 한다. 관리자가 항상 모니터를 지키지 않는 경우가 대부분이므로, 문제 발생 후 발견까지의 시간이 길어져 장애 시간이 급격히 늘어난다.

#2핵심 질문

지표가 일정 수준을 넘으면 사람이 개입하지 않고 자동으로 인스턴스를 재시작하거나 조치할 수 있을까?

#3동작 예시

CloudWatch 경보는 특정 지표의 임계값(threshold)을 정의한 후, 그 값을 초과하면 미리 정의된 조치를 자동으로 실행한다. 예를 들어 "CPU가 90% 이상 2분 지속되면 인스턴스를 재부팅하라"는 경보를 설정하면, 조건을 만족할 때 자동으로 재부팅된다.

#4동작 과정

  1. 경보 규칙 설정CPU가 90% 이상 1분 이상 지속, 메모리가 85% 초과, 네트워크 수신량이 특정값 이상 같은 임계값을 정의한다.
  2. 조치 결정경보가 발동할 때 인스턴스를 중지하거나 종료하거나 재부팅하거나, 하드웨어 결함 감지 시 같은 구성으로 새 하드웨어(복구 기능)에 인스턴스를 옮긴다.
  3. 자동 실행조건을 만족하면 설정된 조치가 즉시 실행되고, 동시에 이메일이나 SNS 메시지로 관리자에게 알린다.

#5한 줄 요약

성능 저하나 장애를 자동으로 감지하고 사람의 개입 없이 미리 정의된 복구 조치를 즉시 실행하는 자동 응답 메커니즘

EventBridge 자동화와 CloudTrail 감사

인스턴스 상태 변화 같은 EC2 이벤트를 EventBridge 규칙으로 받아 자동 처리하고, 누가 어떤 EC2 API를 호출했는지는 CloudTrail 로그로 추적하는 방법.

#1문제 상황

CloudWatch 경보는 지표 값 기반으로만 작동한다. 그 외에 인스턴스가 실제로 중지되었는지, 보안 그룹이 변경되었는지, 또는 누가 언제 어떤 EC2 API를 호출했는지는 추적할 수 없다. 규정 준수나 보안 감시가 필요한 조직에서는 모든 관리 작업을 기록하고 추적해야 하는데, 이를 하는 도구가 없으면 누가 언제 뭘 했는지 알 수 없다.

#2핵심 질문

인스턴스 상태 변화 같은 이벤트를 자동으로 감지하고, 모든 EC2 API 호출을 누가 했는지까지 추적할 수 있을까?

#3동작 예시

EventBridge는 EC2 인스턴스 상태 변화(예: 중지 상태로 전환)를 감지하면 미리 정의된 규칙에 따라 Lambda 함수 실행, SNS 메시지 발송 같은 동작을 자동으로 한다. CloudTrail은 AWS 계정 내 모든 API 호출을 기록하므로, "누가, 어디서, 언제, 어떤 API를 호출했는지" 완전히 추적할 수 있다.

#4동작 과정

  1. EventBridge 규칙 설정"인스턴스가 'running'에서 'stopped'로 변경되면 Slack 채널로 알림 보내기", "종료되면 태그 정보를 S3에 저장하기" 같은 규칙을 정의하면 자동으로 처리된다.
  2. 이벤트 기반 자동화EC2의 상태 변화가 EventBridge로 흘러오면, 매칭되는 규칙이 자동으로 다른 AWS 서비스(Lambda, SNS, SQS)를 호출해서 추가 작업을 한다.
  3. CloudTrail 로깅모든 EC2 API 호출(RunInstances, StopInstances, ModifyInstanceAttribute, CreateSecurityGroup 등)을 기록하고, 각 호출의 호출자 신원, 소스 IP, 정확한 시각, API 파라미터를 저장한다.

#5한 줄 요약

인스턴스의 상태 변화를 이벤트 기반으로 자동 응답하고, 모든 관리 작업을 감시 레이어에서 추적 가능하게 하는 이벤트·감시 통합 체계

태그·리소스 찾기·Global View·서비스 할당량

리소스에 태그를 달아 분류·검색하고, Global View로 리전 전체 리소스를 한눈에 보며, 계정별 EC2 사용 한도(서비스 할당량)를 확인·증설하는 관리 기능.

#1문제 상황

조직이 커지면 수백 개, 수천 개의 EC2 인스턴스가 여러 리전·가용 영역에 흩어져 있다. 각 인스턴스가 어느 팀·프로젝트·환경에 속하는지, 누가 소유한 것인지 체계적으로 분류할 방법이 없으면 불필요한 자원을 찾기 어렵다. 또한 AWS 계정마다 사용할 수 있는 리소스에 제한(서비스 할당량)이 있는데, 이 한도를 초과하면 갑자기 새 인스턴스를 만들 수 없게 된다.

#2핵심 질문

수백 개의 인스턴스 중 특정 팀·환경·용도의 자원을 빠르게 찾고, 전체 사용량과 남은 할당량을 한눈에 볼 수 있을까?

#3동작 예시

태그는 인스턴스에 붙이는 키-값 쌍 레이블이다. (예: Environment=Production, Team=DataEng, CostCenter=Finance) Global View는 모든 리전의 리소스를 한 대시보드에서 보고 필터링하는 도구다. 서비스 할당량 콘솔에서는 현재 계정이 온디맨드 인스턴스 10개까지 사용 가능한데 6개를 사용 중이라는 식으로 한도와 사용량을 볼 수 있다.

#4동작 과정

  1. 태그 지정 및 분류인스턴스 생성 시 또는 생성 후에 "Environment:Prod", "Owner:alice@company.com", "Application:WebServer" 같은 태그를 붙인다.
  2. 태그 기반 검색·필터링콘솔이나 API에서 "Team=ML인 모든 인스턴스 종료", "Environment=Test인 인스턴스의 월별 비용 계산" 같은 작업을 태그 필터로 일괄 수행한다.
  3. 할당량 확인 및 증설서비스 할당량 콘솔에서 "이 리전의 On-Demand Linux 인스턴스: 최대 10개, 현재 6개 사용, 4개 남음" 같이 확인하고, 필요하면 AWS에 한도 증설을 요청한다.

태그와 검색을 통해 수많은 자원을 체계적으로 분류·추적하고, 할당량 가시성으로 리소스 한도를 관리하는 거버넌스 도구

EC2 Capacity Manager와 비용·사용량 가시성

온디맨드·예약·스팟 등 EC2 용량이 어디에 얼마나 쓰이는지 집계해 낭비와 비용을 파악하게 해주는 가시성 도구.

#1문제 상황

EC2 인스턴스를 구매하는 방법은 여러 가지다. 온디맨드(시간당 요금), 예약 인스턴스(장기 약정으로 할인), 스팟 인스턴스(저렴하지만 언제든 회수 가능)가 있다. 조직이 여러 옵션을 혼합해서 사용하면 어느 옵션이 얼마나 사용 중인지, 어디서 낭비가 생기는지 전혀 보이지 않는다. 비용 최적화 기회를 찾을 수 없으므로 불필요한 인스턴스에 계속 돈을 쓰거나, 저렴한 구매 옵션을 제대로 활용하지 못한다.

#2핵심 질문

온디맨드·예약·스팟 인스턴스가 리전·가용 영역·인스턴스 유형별로 얼마나 분산되어 있고, 각각의 비용은 얼마나 되는지 한눈에 볼 수 있을까?

#3동작 예시

EC2 Capacity Manager는 현재 실행 중인 모든 인스턴스를 구매 유형별(온디맨드 vs 예약 vs 스팟)로 카운트하고, 각 유형이 어느 리전·가용 영역·인스턴스 크기에 분산되어 있는지 차트로 시각화한다. 동시에 각 구매 옵션의 시간당·월별 비용을 계산해서 최적화 제안을 한다.

#4동작 과정

  1. 용량 집계현재 모든 리전의 실행 중인 EC2 인스턴스를 구매 옵션별로 분류한다. (온디맨드 37개, 예약 인스턴스 25개, 스팟 12개 같이)
  2. 분포 분석각 구매 유형이 어느 리전·가용 영역·인스턴스 유형(t3.medium, m5.large 등)에 얼마나 분산되어 있는지 시각화한다.
  3. 비용 및 최적화각 유형별 비용을 계산하고, "현재 온디맨드로 실행하는 5개 인스턴스를 스팟으로 바꾸면 월 3,000달러 절감 가능" 같은 최적화 제안을 한다.

#5한 줄 요약

EC2 용량의 분포와 비용 구조를 투명하게 보여줌으로써, 낭비를 발견하고 구매 전략을 최적화하게 하는 재무 가시성 도구

인스턴스가 안 뜨거나 접속이 안 될 때 원인을 찾는 방법과, EC2Rescue·콘솔 스크린샷·진단 인터럽트 같은 복구 도구 모음.

→ 11-01 참조

#1문제 상황

인스턴스가 실행되지 않거나 SSH·RDP로 접속할 수 없으면 원인을 찾기 극히 어렵다. 인스턴스 내부 OS 상태, 네트워크 설정, 커널 문제 등 여러 계층에서 오류가 발생할 수 있는데, 인스턴스 내부에 직접 접근할 수 없으므로 무엇이 잘못됐는지 알 방법이 거의 없다. 지금까지는 인스턴스를 삭제하고 새로 만드는 수밖에 없었다.

#2핵심 질문

인스턴스가 시작되지 않거나 접속이 안 될 때 원인을 빠르게 진단하고, 인스턴스를 삭제하지 않고 원격으로 복구할 수 있을까?

#3동작 예시

EC2는 2분마다 각 인스턴스의 상태를 자동 점검한다. 시스템 상태 확인(하드웨어, 네트워크)과 인스턴스 상태 확인(OS 응답)을 실행해서 실패하면 "System Status Check Failed" 같은 경고를 낸다. 접속 실패 시 EC2Rescue 도구를 실행하면 일반적인 결함(권한, 커널, 네트워크 설정)을 자동으로 진단하고 수정한다.

#4동작 과정

  1. 상태 자동 점검EC2는 2분 주기로 각 인스턴스의 시스템 상태(네트워크 도달 가능성, 하드웨어 결함) 및 인스턴스 상태(OS 응답성)를 확인하고, 실패하면 알림을 발송한다.
  2. EC2Rescue 실행SSH 접속 실패 등 문제 감지 시, EC2Rescue 도구를 자동으로 또는 수동으로 실행해서 권한 오류, 커널 드라이버 손상, 네트워크 설정 오류 같은 일반적인 결함을 진단하고 수정한다.
  3. 원격 진단콘솔 스크린샷으로 OS 부팅 메시지나 콘솔 출력을 원격으로 볼 수 있고, 진단 인터럽트를 발송하면 인스턴스가 메모리·시스템 상태 정보를 덤프해서 근본 원인을 분석할 수 있다.

인스턴스 장애를 자동으로 감지하고, 인스턴스 삭제 없이 진단 도구와 복구 스크립트로 원인을 파악·수정하는 원격 복구 체계
