EC2의 기초 — 가상 서버와 인스턴스 유형01-01

EC2의 정의와 구성 요소

Amazon EC2는 클라우드에서 확장 가능한 가상 서버(인스턴스)를 필요할 때 만들고 멈출 수 있는 컴퓨팅 서비스로, 인스턴스·AMI·인스턴스 유형·키 페어·보안 그룹·EBS 볼륨 등의 요소로 구성된다.

#1문제 상황

서버를 직접 운영하려면 물리 장비를 사서 데이터센터나 전산실에 두고, 전원·네트워크·저장장치를 연결하고 운영체제를 설치해야 한다. 트래픽이 늘면 그만큼 장비를 더 사서 배치해야 하고, 남는 장비는 놀리게 된다. 이런 방식은 하드웨어 비용이 크고 서버를 준비해 애플리케이션을 배포하기까지 시간이 오래 걸린다. 필요한 만큼만 서버를 만들고 쓰지 않을 때 줄일 수 있는 방법이 없다는 점이 가장 큰 한계다.

#2핵심 질문

물리 장비를 사지 않고도 필요한 만큼의 서버를 즉시 만들고, 필요 없어지면 줄이려면 어떻게 해야 하는가?

#3동작 예시

웹 서버 한 대가 필요하면 인스턴스 유형을 하나 고르고, 운영체제 이미지(AMI)와 키 페어, 보안 그룹을 지정해 인스턴스를 실행한다. 이때 인스턴스 유형이 CPU·메모리·네트워크·스토리지의 조합을 결정하고, EBS 볼륨이 디스크로 붙는다. 실행된 인스턴스는 클라우드 안의 가상 서버로 뜨고, 필요 없으면 중지하거나 종료할 수 있다.

#4동작 과정

  1. 인스턴스 구성 선택AMI(운영체제와 초기 소프트웨어가 담긴 이미지), 인스턴스 유형(하드웨어 사양 조합), 키 페어(접속용 인증 키), 보안 그룹(허용할 네트워크 규칙)을 정한다. 이 선택들이 실행될 가상 서버의 성격을 결정한다.
  2. 스토리지 연결EBS 볼륨을 루트 볼륨과 데이터 볼륨으로 붙여 디스크를 마련한다. 인스턴스를 멈춰도 데이터를 유지할 수 있다.
  3. 실행과 조정정한 사양으로 인스턴스가 뜨고, 사용량이 늘면 용량을 키우거나(scale up) 대수를 늘리고, 줄면 다시 낮춘다. 쓰는 만큼만 비용이 발생한다.

리전·가용 영역·토폴로지

리전은 지리적으로 분리된 AWS 데이터센터의 묶음이고 가용 영역(AZ)은 한 리전 안에서 전원·네트워크가 독립된 데이터센터로, EC2 인스턴스는 이 리전·AZ 토폴로지와 인스턴스 토폴로지 위에 배치된다.

#1문제 상황

서버를 한 곳의 데이터센터에만 두면 그 위치에 전원 장애나 네트워크 장애가 생겼을 때 서비스 전체가 멈춘다. 반대로 서버를 여러 곳에 흩어 두더라도, 각 위치가 얼마나 떨어져 있고 서로 독립적인지 관리하지 않으면 한쪽 사고가 다른 쪽으로 번질 수 있다. 물리적 위치와 격리 수준을 구분하지 않으면 가용성을 보장하기 어렵다는 한계가 있다.

#2핵심 질문

서버를 어디에 두어야 지연을 줄이면서 한 곳의 장애가 전체 서비스로 번지지 않게 할 수 있는가?

#3동작 예시

서울 사용자에게 빠르게 응답하려면 서울 리전을 골라 인스턴스를 둔다. 이때 같은 리전 안의 서로 다른 가용 영역(전원과 네트워크가 독립된 데이터센터) 두 곳에 인스턴스를 나눠 배치하면, 한 가용 영역에 장애가 나도 다른 쪽 인스턴스가 서비스를 이어받는다.

#4동작 과정

  1. 리전 선택리전은 지리적으로 분리된 데이터센터의 묶음이다. 사용자와 가까운 리전을 고르면 지연이 줄고, 데이터가 어느 지역에 저장되는지도 정해진다.
  2. 가용 영역 분산한 리전 안에서 전원·네트워크가 독립된 여러 가용 영역(AZ)을 골라 인스턴스를 나눠 둔다. 그래서 한 AZ의 장애가 다른 AZ로 번지지 않는다.
  3. 토폴로지 배치인스턴스에 지정한 토폴로지에 따라 어떤 AZ·호스트에 놓일지가 정해진다. 그래서 같은 AZ에 몰리지 않게 배치를 제어할 수 있다.

인스턴스 유형과 사양

인스턴스 유형은 CPU·메모리·스토리지·네트워크 성능의 조합을 이름으로 나타낸 규격으로, 워크로드 용도에 맞는 유형을 골라 인스턴스를 실행한다.

#1문제 상황

모든 애플리케이션이 같은 자원을 필요로 하지는 않는다. 어떤 프로그램은 CPU를 많이 쓰고, 어떤 것은 메모리를 많이 쓰며, 어떤 것은 저장장치나 네트워크를 많이 쓴다. 하드웨어 사양을 하나로 고정하면 특정 자원만 부족해지고 나머지는 남아 비용이 낭비된다. 워크로드에 맞는 자원 배합을 고를 수 없다는 것이 한계다.

#2핵심 질문

애플리케이션이 필요로 하는 자원 배합에 맞춰 서버 사양을 고르려면 어떻게 해야 하는가?

#3동작 예시

웹 서버처럼 CPU·메모리·네트워크를 비슷하게 쓰는 경우에는 범용 유형을, 대규모 연산을 하는 경우에는 컴퓨팅 최적화 유형을 고른다. 같은 이름의 유형 안에도 크기(size)가 여러 개 있어, 자원 요구량에 맞춰 크기를 키우거나 줄일 수 있다.

#4동작 과정

  1. 유형 이름 해석인스턴스 유형 이름은 패밀리와 크기를 담고 있다. 이름을 보면 어떤 자원에 특화된 계열인지와 규모를 읽을 수 있다.
  2. 카테고리 선택범용, 컴퓨팅 최적화, 메모리 최적화, 스토리지 최적화, 가속 컴퓨팅 같은 카테고리 중 워크로드 목적에 맞는 것을 고른다. 같은 작업이라도 어떤 자원을 쓰느냐에 따라 유리한 유형이 다르다.
  3. 크기 조정고른 유형 안에서 크기를 정해 CPU·메모리·네트워크 용량을 요구량에 맞춘다. 그래서 자원이 남거나 모자라는 낭비를 줄인다.

버스터블·GPU·Mac 인스턴스

버스터블 인스턴스는 평소 기준 성능을 쓰다가 필요할 때 CPU 크레딧으로 성능을 끌어올리는 유형이고, GPU 인스턴스는 그래픽·머신러닝 가속, Mac 인스턴스는 macOS 전용 워크로드를 위한 특수 유형이다.

#1문제 상황

일반적인 유형만으로는 모든 워크로드를 감당하기 어렵다. 하루 대부분은 CPU를 거의 쓰지 않다가 가끔 몰아서 쓰는 작업에 최대 성능 기준 사양을 계속 유지하면 비용이 과하게 든다. 반대로 그래픽 처리나 머신러닝처럼 대량 병렬 연산이 필요한 작업은 일반 CPU로는 너무 느리고, macOS에서만 돌아가는 소프트웨어는 일반 리눅스·윈도우 서버에서 실행할 수 없다.

#2핵심 질문

평소에는 조용하다가 가끔 몰아서 쓰는 작업, 대량 병렬 연산, macOS 전용 작업을 각각 어떻게 감당하는가?

#3동작 예시

T 계열 버스터블 인스턴스는 평소 기준 성능만 내다가 필요할 때 CPU 크레딧을 써서 기준을 넘는 성능을 낸다. GPU 인스턴스는 그래픽·머신러닝 가속을 위해 GPU를 붙여 제공하고, Mac 인스턴스는 macOS 전용 워크로드를 위해 macOS 환경을 제공한다.

#4동작 과정

  1. 버스터블로 평소 비용 절감T 계열은 기준 CPU 성능을 유지하며 크레딧을 모으고, 필요할 때 크레딧을 써서 기준 위로 성능을 끌어올린다. 그래서 대부분 조용한 작업의 비용을 낮춘다.
  2. 모드 선택크레딧이 바닥나면 성능을 기준으로 제한하는 표준 모드와, 초과분에 추가 요금을 내고 계속 성능을 내는 무제한 모드 중 하나를 고른다. 그래서 성능 상한과 요금 방식을 함께 정한다.
  3. 특수 유형 배치대량 병렬 연산은 GPU 인스턴스에, macOS 전용 작업은 Mac 인스턴스에 배치한다. 그래서 일반 CPU나 다른 운영체제로는 못 하던 작업을 처리한다.

#5한 줄 요약

버스터블로 평소 비용을 낮추고 GPU·Mac 같은 특수 유형으로 일반 인스턴스가 못 하는 작업을 감당하게 하는 것

EBS 최적화·CPU 옵션·프로세서 기능

EBS 최적화·CPU 옵션·프로세서 기능은 인스턴스의 스토리지 대역폭과 CPU 코어 수·스레드 수 같은 하드웨어 동작을 워크로드에 맞게 조정하는 설정이다.

#1문제 상황

인스턴스가 저장장치 입출력과 네트워크 통신을 같은 자원으로 처리하면, 디스크 읽기·쓰기가 몰릴 때 네트워크 트래픽과 서로 대역폭을 다퉈 성능이 흔들린다. 또 모든 작업이 CPU 코어를 전부 쓸 필요는 없는데 코어 수와 스레드 수를 그대로 두면 소프트웨어 라이선스 비용이 불필요하게 커질 수 있다. 워크로드에 맞게 입출력 대역폭과 CPU 동작을 조정할 수 없다는 것이 한계다.

#2핵심 질문

저장장치 입출력 대역폭과 CPU 코어·스레드 구성을 워크로드에 맞게 어떻게 조정하는가?

#3동작 예시

EBS 최적화 인스턴스는 저장장치 입출력 전용 대역폭을 따로 확보해 다른 트래픽과 대역폭을 다투지 않게 한다. CPU 옵션에서는 코어 수와 스레드 수를 지정해, 예를 들어 절반의 코어만 쓰도록 줄여 라이선스 비용을 낮출 수 있다. 프로세서 상태 제어로 CPU가 낼 수 있는 동작 상태도 조정한다.

#4동작 과정

  1. EBS 최적화 적용최적화된 구성 스택으로 EBS 입출력에 전용 대역폭을 배정한다. 그래서 저장장치 트래픽과 다른 트래픽 사이의 경합이 줄고 볼륨 성능이 안정된다.
  2. CPU 옵션 지정인스턴스 실행 시 코어 수와 스레드 수를 정한다. 그래서 실제로 쓰는 만큼만 CPU를 노출해 라이선스 비용을 줄일 수 있다.
  3. 프로세서 기능 제어프로세서 상태 제어 같은 기능으로 CPU 동작을 워크로드에 맞춘다. 그래서 성능과 비용을 함께 조율한다.

온디맨드와 예약 인스턴스

온디맨드는 쓰는 만큼 시간당 요금을 내는 기본 구매 방식이고, 예약 인스턴스는 1년 또는 3년 약정으로 대폭 할인된 요금을 받는 구매 옵션이다.

#1문제 상황

쓰는 만큼 초 단위로 요금을 내는 기본 방식만 쓰면, 오랫동안 꾸준히 돌아가는 서버에도 계속 높은 시간당 요금을 낸다. 반대로 앞으로 얼마나 쓸지 모르는데 미리 많이 사 두면 안 쓰는 자원에 돈을 묶어 두게 된다. 사용 패턴과 요금 방식을 연결하지 못하면 비용을 최적화할 수 없다는 것이 한계다.

#2핵심 질문

꾸준히 오래 쓰는 서버의 요금을 낮추면서도 필요한 만큼만 지불하려면 어떻게 해야 하는가?

#3동작 예시

언제 얼마나 쓸지 모르는 작업은 온디맨드로 초 단위 요금을 낸다. 반면 1년 또는 3년 동안 계속 돌릴 서버는 예약 인스턴스로 약정해 같은 사양을 훨씬 낮은 요금으로 쓴다. 예를 들어 매일 24시간 돌아가는 서버는 예약 인스턴스를, 가끔 띄우는 서버는 온디맨드를 고른다.

#4동작 과정

  1. 사용 패턴 판단서버가 상시로 오래 돌아가는지, 간헐적으로 띄우는지 먼저 본다. 그래서 어떤 구매 옵션이 유리한지 갈린다.
  2. 약정 여부 결정상시 사용이면 인스턴스 유형과 리전 같은 구성을 1년 또는 3년 약정하는 예약 인스턴스를 산다. 그래서 시간당 요금이 크게 낮아진다.
  3. 할인 적용 확인약정한 구성과 일치하는 인스턴스 사용분에 할인이 적용된다. 그래서 같은 사용량에도 청구 금액이 줄어든다.

Spot 인스턴스

Spot 인스턴스는 AWS의 남는 컴퓨팅 용량을 최대 90% 저렴하게 쓰는 대신, AWS가 용량을 필요로 하면 2분 전 통보로 회수할 수 있는 구매 옵션이다.

#1문제 상황

AWS에는 수요가 낮아 쓰이지 않고 남는 컴퓨팅 용량이 있다. 이 용량을 일반 요금으로만 제공하면 남는 자원은 놀고, 사용자는 비용을 크게 낮출 기회를 놓친다. 반대로 이 남는 용량을 쓰더라도 언제 회수될지 모르는 상태로 중요한 작업을 돌리면 갑자기 작업이 중단될 위험이 있다.

#2핵심 질문

남는 컴퓨팅 용량을 큰 할인으로 쓰되, 회수될 때 작업이 끊기지 않게 하려면 어떻게 해야 하는가?

#3동작 예시

중단돼도 다시 시작할 수 있는 배치 처리 작업에 Spot 인스턴스를 쓴다. 온디맨드보다 훨씬 낮은 가격으로 실행되며, AWS가 그 용량을 필요로 하게 되면 인스턴스가 회수된다. 이때 회수 사실을 미리 알리는 중단 공지가 오고, 사용자가 지정한 중단 동작에 따라 처리된다.

#4동작 과정

  1. 남는 용량 요청사용되지 않는 EC2 용량을 Spot 인스턴스로 요청한다. 그래서 온디맨드보다 훨씬 낮은 요금으로 실행된다.
  2. 가격과 공급 변동각 인스턴스 유형·가용 영역의 Spot 가격이 장기 수요와 공급에 따라 조정된다. 그래서 용량이 있는 동안 인스턴스가 돌아간다.
  3. 중단 대비AWS가 용량을 필요로 하면 회수되며, 회수 전에 중단 공지가 온다. 그래서 작업을 저장하거나 다른 인스턴스로 넘기는 등 중단 동작을 미리 정해 둘 수 있다.

Dedicated Hosts와 Dedicated Instances

Dedicated Hosts는 물리 서버 한 대를 통째로 전용하는 방식이고, Dedicated Instances는 같은 물리 서버를 다른 고객과 공유하지 않는 인스턴스 단위 전용 방식이다.

#1문제 상황

일반 EC2 인스턴스는 여러 고객의 인스턴스가 같은 물리 서버 위에 올라가는 공유 구조로 동작한다. 이 방식은 저렴하고 유연하지만, 어떤 물리 서버에 내 인스턴스가 놓이는지, 그 서버의 소켓·코어·호스트 ID가 무엇인지 전혀 알 수 없고 다른 고객의 워크로드와 자원을 나눠 쓴다. 소켓당 과금되는 상용 소프트웨어 라이선스를 쓰거나, 규제·보안상 물리적으로 분리된 하드웨어가 필요하거나, 특정 물리 서버에 인스턴스를 고정해야 하는 경우에는 이 공유 방식이 그대로 걸림돌이 된다. 물리 서버 단위의 가시성과 통제가 없으면 라이선스 조건을 증명할 수도, 배치를 보장할 수도 없다.

#2핵심 질문

내 인스턴스를 다른 고객과 물리적으로 분리하고, 어떤 물리 서버에 올라가는지까지 통제하려면 어떻게 해야 하는가?

#3동작 예시

라이선스가 소켓 수 기준인 데이터베이스 소프트웨어를 올린다고 하자. Dedicated Host를 물리 서버 한 대 단위로 할당하면 그 호스트의 소켓·코어 수가 그대로 드러나므로, 그 숫자에 맞춰 라이선스를 계상하고 인스턴스를 그 호스트에만 띄울 수 있다. 반대로 같은 물리 서버를 공유하지 않기만 하면 되는 요구라면 Dedicated Instances로 인스턴스 단위 전용을 선택할 수 있다.

#4동작 과정

  1. 물리 서버 전용 확보Dedicated Host를 할당하면 물리 서버 한 대가 내 계정 전용이 되고, 소켓·코어·호스트 ID 같은 하드웨어 정보가 보이며 인스턴스가 그 호스트 위에서만 실행된다.
  2. 라이선스·배치 제어기존에 보유한 라이선스(Bring your own licenses)를 그 호스트에 적용하고, 자동 배치(auto-placement)와 호스트 선호도(host affinity, 특정 호스트에 인스턴스를 묶어 두는 설정)로 어떤 호스트에 뜰지 고정할 수 있다.
  3. 공유·복구·유지보수호스트를 다른 계정과 공유하거나 회수할 수 있고, 호스트에 장애가 나면 호스트 복구(host recovery)가 인스턴스를 다른 호스트로 옮기며, 정기 유지보수는 host maintenance로 관리한다.

On-Demand Capacity Reservations

특정 가용 영역에 원하는 용량을 미리 확보해 두어, 필요할 때 반드시 인스턴스를 시작할 수 있게 보장하는 기능이다(확보 자체는 할인이 아님).

#1문제 상황

EC2 인스턴스는 원할 때 바로 띄울 수 있지만, 특정 가용 영역에서 그 인스턴스 타입의 용량이 소진되면 원하는 시점에 시작하지 못하고 용량 부족 오류를 만난다. 트래픽이 몰리는 행사나 정기 확장 시점, 규제상 고가용성을 보장해야 하는 상황에서는 이 "그때 가서 안 뜰 수도 있다"는 불확실성이 치명적이다. 할인형 상품인 Reserved Instances나 Savings Plans는 요금을 깎아 주지만, 특정 가용 영역의 물리 용량 자체를 붙잡아 두는 보장은 아니다. 그래서 할인과는 별개로 "필요한 순간에 반드시 뜬다"는 공급 보장만 따로 확보할 수단이 필요하다.

#2핵심 질문

특정 가용 영역에서 원하는 시점에 반드시 인스턴스를 시작하도록 용량을 미리 붙잡아 둘 수 있는가?

#3동작 예시

월말 정산 배치를 특정 가용 영역의 특정 인스턴스 타입으로 돌린다고 하자. 미리 그 가용 영역에 그 타입만큼의 Capacity Reservation을 만들어 두면, 그 용량은 예약 기간 동안 내가 쓸 수 있도록 잡혀 있어 정산 시점에 인스턴스를 그대로 시작할 수 있다. 예약은 할인이 아니라 자리 확보이며, 실제로는 인스턴스를 띄우지 않아도 그만큼 비용이 청구된다.

#4동작 과정

  1. 예약 생성원하는 가용 영역·인스턴스 타입·수량을 지정해 Capacity Reservation을 만들면, 그 용량이 예약 기간 동안 내 계정에 잡힌다.
  2. 인스턴스 시작 또는 수정인스턴스를 시작할 때 그 예약에 매칭해 띄우거나, 이미 뜬 인스턴스의 설정을 예약에 맞춰 붙인다. 이때 그 인스턴스는 예약된 용량을 우선 사용한다.
  3. 관리와 종료Move capacity·Split off capacity로 용량을 나누거나 옮기고, 취소(Cancel)하면 확보가 풀린다. 여러 예약을 묶어 그룹으로 관리하거나 다른 계정과 공유할 수도 있다.

#5한 줄 요약

특정 가용 영역의 용량을 미리 확보해 필요할 때 반드시 인스턴스가 시작되도록 공급을 보장하는 것

Capacity Blocks와 CR Resource Groups

Capacity Blocks는 미래의 특정 기간 동안 GPU 등 ML 용량을 시간 단위로 예약 구매하는 방식이고, CR Resource Groups는 여러 Capacity Reservation을 묶어 그룹 단위로 인스턴스를 배치·관리하는 기능이다.

→ 02-04 참조

#1문제 상황

GPU 같은 가속 하드웨어는 수요가 몰릴 때 용량이 빠르게 소진되어, 며칠 뒤로 예정된 모델 학습 작업을 원하는 시점에 시작하지 못하는 일이 생긴다. 이런 작업은 짧고 정해진 기간 동안만 대량의 가속 용량이 필요하지만, 그 시점의 공급을 미리 잡아 두지 않으면 계획 자체가 흔들린다. 한편 여러 개의 Capacity Reservation을 따로따로 만들면, 어느 예약이 어느 워크로드용인지, 남는 게 있는지 파악하기 어려워지고 배치도 예약 단위로 흩어진다. 기간 한정 예약과 여러 예약의 묶음 관리를 각각 다룰 방법이 필요하다.

#2핵심 질문

미래의 특정 기간에 필요한 가속 컴퓨팅 용량을 미리 사 두고, 여러 예약을 한 덩어리로 묶어 관리할 수 있는가?

#3동작 예시

다음 주 이틀간 대규모 학습을 돌린다고 하자. Capacity Blocks for ML은 그 기간을 시작·종료 시각으로 지정해 GPU 용량을 미리 구매하게 해 준다. 예약된 기간이 되면 그 용량 위에 인스턴스를 시작해 학습을 돌리고, 기간이 끝나면 반납된다. 여러 예약을 쓸 때는 Capacity Reservation Resource Group으로 묶어 그룹 단위로 인스턴스를 배치한다.

#4동작 과정

  1. 탐색과 구매원하는 인스턴스 타입·수량·기간을 조건으로 검색해 사용 가능한 Capacity Block을 찾고 구매해, 그 기간의 가속 용량을 확보한다.
  2. 그룹 구성여러 Capacity Reservation을 Resource Group으로 만들고 예약들을 그룹에 추가하면, 그룹을 하나의 배치 대상으로 삼아 인스턴스를 띄울 수 있다.
  3. 운영과 정리예약을 조회·연장·공유하고 그룹 안에서 인스턴스 수명주기를 관리하며, 필요 없어지면 그룹에서 제거하거나 그룹을 삭제한다. 상태 변화는 EventBridge로 모니터링한다.

#5한 줄 요약

기간을 정한 가속 컴퓨팅 용량을 미리 확보하고 여러 예약을 그룹으로 묶어 배치·운영하는 것

AMI — 이미지 개념과 수명주기03-01

AMI 개념과 검색

AMI(Amazon Machine Image)는 EC2 인스턴스를 실행하는 데 필요한 운영체제·애플리케이션·설정을 담은 이미지 템플릿으로, 공개·소유·공유 AMI를 카탈로그에서 검색해 골라 인스턴스를 시작한다.

#1문제 상황

서버를 새로 세울 때마다 운영체제를 설치하고, 필요한 패키지를 깔고, 설정을 맞추는 작업을 손으로 반복하면 시간이 오래 걸리고 매번 결과가 조금씩 달라진다. 어떤 인스턴스에 어떤 소프트웨어가 어떤 버전으로 들어 있는지도 사후에 추적하기 어렵다. Amazon EC2 인스턴스는 부팅에 필요한 소프트웨어가 담긴 이미지가 있어야 시작되는데, 그 이미지 규격과 호환 조건이 인스턴스 타입·리전마다 다르다. 아무 이미지나 아무 리전에서 쓸 수 없고, 어떤 이미지를 골랐는지가 보안·비용·동작에 그대로 영향을 준다.

#2핵심 질문

인스턴스를 시작할 때 필요한 소프트웨어 구성을 담은 이미지를 어떻게 골라야 하며, 그 이미지를 무엇으로 판별하는가?

#3동작 예시

웹 서버용 인스턴스를 띄운다고 하자. AWS가 제공하는 AMI, 누군가 공개한 public AMI, 다른 계정이 나에게 공유한 AMI, AWS Marketplace에서 구매한 paid AMI 중에서 카탈로그를 검색해 하나를 고른다. 고른 AMI에는 부팅 소프트웨어와 함께 어떤 블록 디바이스를 붙일지 정하는 block device mapping이 들어 있고, 그 AMI로 같은 구성의 인스턴스를 여러 대 찍어낼 수 있다.

#4동작 과정

  1. AMI 확보AWS 제공·public·공유·Marketplace 구매 AMI 중에서 검색해 가져온다. Systems Manager 파라미터로 최신 AMI ID를 조회할 수도 있다.

  3. 인스턴스 시작인스턴스를 시작할 때 그 AMI를 지정하면, AMI의 구성대로 부팅되고 같은 AMI로 여러 인스턴스를 반복 생성할 수 있다.

실행 중이거나 중지된 인스턴스 또는 스냅샷으로부터 자신만의 AMI를 만들어 재사용하고, S3 기반 AMI를 저장·복원하거나 다른 리전으로 복사해 보관한다.

#1문제 상황

남이 만든 AMI만 쓰면 우리 환경에 필요한 소프트웨어와 설정을 매번 부팅 후 스크립트로 다시 깔아야 한다. 이 반복 설치가 느리고, 설치 시점의 외부 저장소 상태나 버전 차이 때문에 인스턴스마다 구성이 미묘하게 달라지는 문제가 생긴다. 또한 손수 만든 구성을 이미지로 굳혀 두지 않으면 그 구성을 다른 리전이나 다른 계정에서 그대로 재현할 방법이 없다. 같은 서버를 다시 세우려고 처음부터 설정을 되풀이하게 된다.

#2핵심 질문

내가 원하는 구성이 이미 갖춰진 인스턴스에서 그 상태를 이미지로 굳혀 재사용하고 보관하려면 어떻게 하는가?

#3동작 예시

기존 AMI로 인스턴스를 하나 띄운 뒤 필요한 패키지를 설치하고 운영체제 설정을 맞춘다. 그 인스턴스에서 AMI를 생성하면 그때의 상태가 새 AMI로 저장되고, 이후 이 AMI로 띄우는 인스턴스는 추가 설치 없이 그 구성을 그대로 갖는다. 이때 생성 대상은 암호화된 EBS 볼륨(루트 볼륨 포함)도, 암호화하지 않은 볼륨도 될 수 있다.

#4동작 과정

  1. 인스턴스 준비기존 AMI로 인스턴스를 시작해 소프트웨어 설치와 OS 설정을 적용하고, 필요하면 Windows Sysprep으로 일반화한다.
  2. AMI 생성인스턴스에서 AMI를 만들거나, 루트 볼륨 스냅샷에서 AMI를 생성·등록한다. EBS 기반이면 스냅샷으로, S3 기반이면 AMI 도구로 만들어 변환할 수 있다.
  3. 저장과 복원만들어진 AMI를 보관하고, 필요할 때 다른 리전으로 복사하거나 store image task로 저장·복원한다.

AMI 수명주기 관리

AMI는 생성·사용·사용 중단(deprecate)·비활성화(disable)·등록 취소(deregister)의 수명주기를 거치며, 사용 현황을 추적하고 더 이상 필요 없는 AMI를 안전하게 정리한다.

#1문제 상황

AMI를 만들고 공유하다 보면 개수가 계속 늘어나, 어떤 AMI가 아직 쓰이고 어떤 것이 방치됐는지 파악하기 어려워진다. 오래된 AMI를 아무 확인 없이 지우면 그 AMI로 띄운 인스턴스나 참조 중인 리전·계정에 문제가 생길 수 있어, 삭제가 위험해진다. AMI는 리전마다 따로 존재하므로 복사본을 여러 리전에 두게 되고, 원본과 복사본의 관계나 각각이 언제 마지막으로 쓰였는지 추적하지 않으면 정리 기준을 세울 수 없다. 사용 현황을 확인한 뒤 안전하게 정리하는 절차가 필요하다.

#2핵심 질문

AMI가 언제 만들어지고 어디까지 복사됐으며 마지막으로 언제 쓰였는지 추적해, 안전하게 정리할 수 있는가?

#3동작 예시

한 리전에서 만든 AMI를 다른 리전으로 복사해 두었다고 하자. AMI usage와 last used 정보를 확인해 그 복사본이 오래 쓰이지 않았음을 확인한 뒤, 이 AMI를 더 이상 새 인스턴스에 쓰지 않도록 deprecate(사용 중단)로 표시한다. 그래도 기존 참조 때문에 곧바로 지우기 어렵다면 disable(비활성화)로 시작을 막고, 참조하는 리소스를 확인한 뒤에야 deregister(등록 취소)로 정리한다.

#4동작 과정

  1. 사용 현황 파악AMI usage를 조회하고 마지막 사용 시점과 이 AMI를 참조하는 리소스를 확인해, 아직 필요한지 판단한다.
  2. 단계적 차단deprecate로 더 이상 새로 쓰지 않도록 표시하고, disable로 인스턴스 시작을 막는다. deregister만으로는 즉시 삭제되지 않는 참조 관계를 확인한다.
  3. 정리와 보호실제로 필요 없어진 AMI를 deregister하고, 반대로 지우면 안 되는 AMI는 deregister 방지 설정으로 보호한다.

#5한 줄 요약

AMI를 만들고 복사하고 쓰임을 추적한 뒤 사용 중단·비활성화·등록 취소로 안전하게 정리하는 것

AMI 공유·암호화·결제

AMI를 특정 계정·조직·OU에 공유하거나 공개하고, 스냅샷을 KMS 키로 암호화하며, AWS Marketplace 유료 AMI와 소프트웨어 비용이 어떻게 청구되는지 이해한다.

#1문제 상황

AMI를 그냥 공개하면 누구나 내가 만든 이미지를 가져다 쓸 수 있지만, 반대로 공개된 AMI를 내가 쓸 때는 그 안에 무엇이 들어 있는지 보증되지 않아 신뢰할 수 없는 코드를 배포하는 것과 같은 위험이 따른다. 공유 범위를 통제하지 않으면 원치 않는 노출이나 무단 사용이 생긴다. 또한 공유받은 AMI가 암호화된 스냅샷을 쓰면 그 암호를 푸는 KMS 키 권한이 없어 시작이 막히고, AWS Marketplace의 유료 AMI는 소프트웨어 요금이 어디에 어떻게 청구되는지 알지 못하면 비용을 예측할 수 없다.

#2핵심 질문

AMI를 누구에게 어디까지 공유할지 통제하고, 암호화와 유료 소프트웨어 비용을 함께 관리하려면 어떻게 하는가?

#3동작 예시

조직 안에서만 쓰는 AMI라면 조직(organization)이나 OU 단위로 공유해 그 범위의 계정들이 쓰게 한다. 만약 그 AMI의 스냅샷이 KMS 키로 암호화돼 있으면, 공유받는 쪽이 시작할 수 있도록 그 키 사용을 허용해 주어야 한다. 마켓플레이스에서 유료 AMI를 구매하면 별도 소프트웨어 요금이 청구되므로, AMI billing 필드로 청구 내역을 확인한다.

#4동작 과정

  1. 공유 범위 지정특정 계정, 조직·OU, 또는 public 대상으로 AMI를 공유하되, Block public access 설정으로 무단 공개를 막는다.
  2. 암호화 권한 정리공유받은 쪽이 암호화된 스냅샷을 쓸 수 있도록 KMS 키 사용을 허용하고, 필요한 암호화 설정을 맞춘다.
  3. 결제와 정리Marketplace 유료 AMI는 구독을 관리하고 product code를 확인하며, AMI billing 정보로 청구 항목을 검증한다. 필요 없어진 공유는 취소한다.

#5한 줄 요약

시작 템플릿과 시작 옵션

인스턴스를 시작할 때 필요한 AMI·인스턴스 유형·보안 그룹·키 페어 등 여러 파라미터를 미리 저장해 재사용하는 재사용 가능한 구성 묶음이다.

#1문제 상황

인스턴스를 시작할 때마다 AMI ID, 인스턴스 유형, 네트워크 설정, 보안 그룹 같은 파라미터를 콘솔이나 CLI에서 하나씩 다시 입력해야 한다. 같은 구성으로 여러 대를 만들거나 반복해서 만들 때 이 입력이 매번 반복되어 시간이 들고, 사람이 손으로 넣다 보면 값이 조금씩 달라지는 실수도 생긴다.

#2핵심 질문

매번 반복 입력하는 시작 파라미터를 한 번만 저장해 두고 재사용할 수는 없을까?

#3동작 예시

자주 쓰는 AMI ID·인스턴스 유형·네트워크 설정을 담은 시작 템플릿을 하나 만들어 두면, 인스턴스를 시작할 때 파라미터를 다시 넣는 대신 그 템플릿만 지정하면 된다. 템플릿에는 번호가 붙은 버전을 여러 개 만들 수 있어, 각 버전이 서로 다른 파라미터를 가질 수 있고 시작 시 원하는 버전을 골라 쓸 수 있다.

#4동작 과정

  1. 템플릿 생성저장할 AMI ID, 인스턴스 유형, 네트워크 설정 같은 파라미터를 정해 시작 템플릿을 만든다. 이렇게 하면 이후 시작할 때 값을 다시 입력하지 않아도 된다.
  2. 버전 관리템플릿마다 번호가 붙은 버전을 여러 개 만들 수 있고, 각 버전은 서로 다른 파라미터를 담을 수 있다. 파라미터를 바꾸려면 기존 버전을 고치는 대신 새 버전을 만든다.
  3. 시작 시 적용콘솔, SDK, 명령줄 도구에서 파라미터 대신 템플릿을 지정해 인스턴스를 시작한다. 버전을 지정하지 않으면 기본 버전이 쓰이고, 어느 버전이든 기본 버전으로 설정할 수 있다.

인스턴스 시작 방법

콘솔 마법사, 시작 템플릿, 기존 인스턴스 복제, Marketplace AMI 등 여러 경로로 EC2 인스턴스를 생성하는 절차다.

#1문제 상황

인스턴스는 AMI에서 시작되는 가상 서버인데, 처음 쓰는 사람은 어떤 경로로 만들어야 하는지, 각 방법이 무엇을 요구하는지 알기 어렵다. 기존 인스턴스와 같은 구성을 다시 만들고 싶어도 매번 처음부터 파라미터를 채워야 하고, 필요한 소프트웨어가 미리 갖춰진 AMI를 쓰고 싶어도 그 경로를 몰라 헤맨다.

#2핵심 질문

목적에 따라 인스턴스를 어떤 경로로 시작하고, 기존 구성이나 미리 준비된 이미지를 어떻게 재사용할 수 있을까?

#3동작 예시

시작 마법사로 AMI와 인스턴스 유형을 고르며 처음 인스턴스를 만들 수 있고, 미리 저장한 시작 템플릿을 지정하면 파라미터를 다시 넣지 않고 시작할 수 있다. 기존 인스턴스를 복제하듯 같은 구성으로 새 인스턴스를 띄우거나, AWS Marketplace AMI에서 필요한 소프트웨어가 갖춰진 이미지를 골라 시작하는 경로도 있다.

#4동작 과정

  1. 경로 선택시작 마법사, 시작 템플릿, 기존 인스턴스 기반, Marketplace AMI 중 목적에 맞는 경로를 고른다. 이 선택이 이후 입력해야 할 항목을 결정한다.
  2. 파라미터 지정고른 경로에서 AMI(운영체제와 애플리케이션이 담긴 이미지), 인스턴스 유형, 네트워크와 키 페어 같은 값을 정한다. 템플릿을 쓰면 이 값들이 미리 채워진다.
  3. 시작과 확인인스턴스를 시작하고 실행 상태가 되면 접속한다. 시작한 뒤에는 사용한 만큼 요금이 발생하므로 유휴 상태여도 과금 대상임을 확인한다.

SSH와 RDP 접속

Linux 인스턴스는 SSH 클라이언트로, Windows 인스턴스는 RDP 클라이언트로 원격 접속하는 대표적인 방법이다.

#1문제 상황

인스턴스는 클라우드에 있으니 사용하는 컴퓨터에서 직접 화면을 볼 수 없고, 로그온하려면 원격 연결을 세워야 한다. 그런데 인스턴스 운영체제와 접속하는 컴퓨터의 운영체제에 따라 필요한 방법과 사전 조건이 다르며, 어떤 방법은 키 페어가, 어떤 방법은 인바운드 규칙이나 IAM 권한이 필요하다.

#2핵심 질문

인스턴스 운영체제와 내 컴퓨터 환경에 맞는 연결 방법은 무엇이고, 그때 무엇이 준비되어야 할까?

#3동작 예시

리눅스 인스턴스는 SSH 클라이언트로 접속하고, 윈도우 인스턴스는 RDP 클라이언트로 접속한다. 두 경우 모두 인스턴스에 인바운드 트래픽을 허용하는 규칙이 있어야 하고, SSH 클라이언트와 PuTTY는 키 페어와 인스턴스 쪽 소프트웨어를 필요로 하는 반면 Session Manager는 키 페어 없이 IAM 권한과 인스턴스 프로파일 역할로 접속한다.

#4동작 과정

  1. 방법 확인연결 표에서 인스턴스 운영체제와 접속 컴퓨터에 맞는 옵션을 고른다. 이 표가 각 방법에 필요한 인바운드 규칙, IAM 권한, 인스턴스 프로파일 역할, 키 페어 유무를 알려준다.
  2. 사전 조건 준비고른 방법에 맞춰 인바운드 트래픽 규칙을 열고, 필요한 IAM 권한을 부여하고, 키 페어와 소프트웨어를 준비한다.
  3. 접속과 전송SSH 클라이언트나 RDP 클라이언트로 세션을 열고, 필요하면 SCP나 RDP로 파일을 주고받는다.

EC2 Instance Connect와 Session Manager

공인 IP 없이 브라우저나 CLI로 SSH 세션을 열거나, Systems Manager를 통해 에이전트 기반으로 인스턴스에 접속하는 관리형 접속 수단이다.

#1문제 상황

기존 SSH 접속은 키 페어를 여러 사람이 나눠 관리해야 하고, 공인 IP가 있어야 하며, 누가 언제 접속했는지 감사하기도 어렵다. 접속이 필요한 사람마다 키를 배포하고 회수하는 일이 늘어나면서 키 관리 자체가 부담이 된다.

#2핵심 질문

키를 공유하고 관리하지 않으면서도 접속 권한을 통제하고 기록할 수 있는 방법은 없을까?

#3동작 예시

EC2 Instance Connect는 SSH 접속을 SSH 키 대신 IAM 정책과 보안 주체로 통제한다. 사용자가 연결하면 EC2 Instance Connect API가 SSH 공개 키를 인스턴스 메타데이터에 밀어 넣고, 그 키는 60초 동안만 남는다. 이 방식은 브라우저 기반 세션도, Session Manager를 통한 에이전트 기반 접속도 지원한다.

#4동작 과정

  1. 권한 확인사용자에게 붙은 IAM 정책이 해당 인스턴스 메타데이터에 공개 키를 밀어 넣는 것을 허용하는지 확인한다. 허용된 사용자만 다음 단계로 진행할 수 있다.
  2. 키 푸시와 접속연결 요청 시 EC2 Instance Connect API가 일시적인 SSH 공개 키를 인스턴스 메타데이터에 넣고, 그 키로 접속한다. 키는 60초 후 사라져 남지 않는다.
  3. 기록모든 연결 요청은 CloudTrail에 기록되어 누가 언제 접속했는지 감사할 수 있다.

키 페어

인스턴스 접속 시 사용자 인증에 쓰이는 공개 키와 개인 키의 쌍으로, AWS는 공개 키를 저장하고 개인 키는 사용자가 보관한다.

#1문제 상황

인스턴스에 접속할 때 상대가 정말 내가 맞는지 증명할 방법이 필요하다. 비밀번호만으로는 안전하지 않고, 접속할 때마다 자격 증명을 새로 만들면 관리가 복잡해진다. 또 개인 키를 잃어버리거나 다른 사람이 가지면 그 사람이 곧 내 인스턴스에 들어올 수 있다는 위험이 있다.

#2핵심 질문

접속할 때 내 신원을 안전하게 증명할 자격 증명은 어떻게 만들고 어디에 보관해야 할까?

#3동작 예시

공개 키와 개인 키 한 쌍을 만든다. 공개 키는 인스턴스에 저장되고, 개인 키는 사용자가 보관한다. 리눅스 인스턴스에서는 개인 키로 SSH 접속을 하고, 윈도우 인스턴스에서는 개인 키로 관리자 비밀번호를 복호화한 뒤 그 비밀번호로 접속한다.

#4동작 과정

  1. 키 페어 생성공개 키와 개인 키 쌍을 만든다. 인스턴스를 시작할 때 이 키 페어를 지정하면 공개 키가 인스턴스에 저장된다.
  2. 개인 키 보관개인 키는 안전한 곳에 보관한다. 개인 키를 가진 사람은 그 키 페어를 쓰는 인스턴스에 접속할 수 있기 때문이다.
  3. 접속에 사용리눅스는 개인 키로 SSH 접속을 하고, 윈도우는 개인 키로 관리자 비밀번호를 복호화해 접속한다.

인스턴스 메타데이터와 식별 정보

실행 중인 인스턴스가 자신의 인스턴스 ID·IP·IAM 자격 증명 등 정보를 링크로컬 주소에서 조회하는 서비스와, 인스턴스임을 증명하는 식별 문서다.

#1문제 상황

실행 중인 인스턴스는 자기 자신의 호스트 이름, 보안 그룹, 인스턴스 ID 같은 정보를 스스로 알아야 설정을 조정하거나 다른 서비스에 자신을 알릴 수 있다. 하지만 이 정보를 미리 AMI에 넣어 두면 모든 인스턴스가 같은 값을 갖게 되어 개별 인스턴스를 구분할 수 없다.

#2핵심 질문

실행 중인 인스턴스가 자기 자신의 정보와 자격 증명을 스스로 조회하려면 어디에서 가져와야 할까?

#3동작 예시

인스턴스는 링크로컬 주소에서 자신의 메타데이터를 조회한다. 메타데이터에는 호스트 이름, 이벤트, 보안 그룹 같은 속성 범주와, 시작 시 생성되는 인스턴스 ID 문서 같은 동적 데이터가 있다. 시작할 때 지정한 사용자 데이터도 이 메타데이터를 통해 읽을 수 있어, 실행 시점에 설정 파일을 바꾸는 데 쓸 수 있다.

#4동작 과정

  1. 메타데이터 조회인스턴스가 링크로컬 주소로 요청을 보내 호스트 이름, 보안 그룹, 인스턴스 ID 같은 속성을 읽는다. 이 값으로 실행 중인 자신을 설정한다.
  2. 동적 데이터와 사용자 데이터 접근시작 시 생성되는 인스턴스 ID 문서 같은 동적 데이터와, 시작할 때 넣은 사용자 데이터를 같은 경로에서 읽는다. 사용자 데이터로 실행 시점에 설정 파일을 바꿀 수 있다.
  3. 버전과 접근 제한IMDS 버전을 선택해 접근 방식을 정하고, 필요하면 접근을 제한한다. 이렇게 하면 필요한 정보만 안전하게 노출된다.

Windows 인스턴스 구성과 런치 에이전트

#1문제 상황

윈도우 인스턴스는 부팅할 때 초기 설정과 관리 작업을 해야 하는데, 이를 사람이 매번 직접 하면 인스턴스를 띄울 때마다 반복 작업이 생기고 설정이 빠지거나 달라질 수 있다. 인스턴스를 중지했다가 다시 시작하거나 재시작할 때도 같은 작업을 다시 해야 한다.

#2핵심 질문

윈도우 인스턴스가 부팅할 때 필요한 초기 설정과 관리 작업을 자동으로 수행하게 하려면 어떻게 해야 할까?

#3동작 예시

각 AWS 윈도우 AMI에는 기본 설정이 미리 적용된 윈도우 런치 에이전트가 들어 있다. 이 에이전트는 인스턴스가 시작될 때 작업을 수행하고, 인스턴스를 중지했다가 나중에 다시 시작하거나 재시작할 때도 실행된다. 용도에 따라 EC2Launch v2, EC2Launch v1, EC2Config 같은 다른 에이전트가 쓰인다.

#4동작 과정

  1. 에이전트 준비AWS 윈도우 AMI에 들어 있는 런치 에이전트가 기본 설정과 함께 준비되어 있다. 별도로 설치하지 않아도 시작 작업을 맡을 수 있다.
  2. 부팅 시 작업 수행인스턴스가 시작될 때 에이전트가 초기 설정과 관리 작업을 자동으로 수행한다. 이로써 반복 수작업이 사라진다.
  3. 재시작 시 재실행인스턴스를 중지했다가 다시 시작하거나 재시작할 때 에이전트가 다시 작동한다. 그래서 상태가 바뀌어도 설정이 유지된다.

Windows 운영과 장치 드라이버

Windows 인스턴스에서 GPU·ENA·NVMe 등 하드웨어 성능을 내기 위해 설치·업그레이드해야 하는 디바이스 드라이버 관리 방법이다.

#1문제 상황

EC2 인스턴스는 가상화된 하드웨어 위에서 동작하는데, 운영체제는 그 하드웨어와 직접 대화하지 못하고 장치 드라이버라는 소프트웨어를 통해 통신한다. 드라이버가 오래됐거나 맞지 않으면 네트워크·그래픽·스토리지 성능이 제대로 나오지 않고 시스템 오류나 예기치 않은 동작이 생긴다. 특히 성능에 큰 영향을 주는 네트워킹·그래픽·스토리지 드라이버는 최신 상태를 유지하는 것이 중요하다.

#2핵심 질문

Windows 인스턴스가 가상 하드웨어의 성능을 온전히 내려면 어떤 장치 드라이버를 어떻게 설치하고 갱신해야 하는가?

#3동작 예시

GPU가 필요한 Windows 인스턴스에 NVIDIA 드라이버가 없으면 그래픽 가속이 동작하지 않는다. 이때 AWS가 제공하는 NVIDIA 드라이버나 GRID·게이밍용 드라이버를 설치하면 그래픽 작업을 GPU로 처리할 수 있게 된다. 마찬가지로 ENA 드라이버를 설치하면 네트워크 대역폭을 더 높은 수준으로 쓸 수 있다.

#4동작 과정

  1. 드라이버 종류 확인인스턴스에 필요한 네트워크(ENA), 그래픽(NVIDIA/AMD), 스토리지(NVMe), 기타 Windows 장치 드라이버 중 어떤 것이 빠졌는지 확인한다. 여기서 무엇을 설치할지 결정된다.
  2. 공식 드라이버 설치·업그레이드AWS가 배포하는 드라이버 릴리스나 공용 드라이버를 내려받아 설치한다. NVMe 드라이버는 EBS·인스턴스 스토어 볼륨을 인식하는 데 필요하다.

중지·시작·재부팅·종료

EC2 인스턴스의 실행 상태를 바꾸는 기본 조작으로, 중지·시작은 인스턴스를 보존한 채 전원을 끄고 켜며 재부팅은 운영체제만 다시 시작하고 종료는 인스턴스를 영구 삭제한다.

#1문제 상황

인스턴스는 켜져 있는 동안 계속 사용료가 청구되고, 그 상태는 하나로 고정되지 않는다. 그냥 전원을 내리는 방식만 있으면 인스턴스를 보존한 채 잠시 멈추거나, 운영체제만 다시 시작하거나, 필요 없어진 인스턴스를 영구히 없애는 구분이 불가능하다. 그래서 상태를 바꾸는 조작이 각각 분리되어 있다.

#2핵심 질문

인스턴스를 없애지 않고 잠시 멈추거나, 운영체제만 재시작하거나, 완전히 삭제하려면 어떤 조작을 골라야 하는가?

#3동작 예시

개발 서버를 밤에 쓰지 않을 때 중지(stop)하면 인스턴스는 보존된 채 컴퓨팅 사용료가 멈춘다. 같은 인스턴스를 다시 시작(start)하면 이전 상태로 돌아온다. 반면 더 이상 필요 없는 테스트 서버는 종료(terminate)해서 영구히 삭제한다.

#4동작 과정

  1. 중지와 시작중지하면 인스턴스가 stopped 상태가 되어 컴퓨팅 사용료가 청구되지 않는다. 다시 시작하면 다른 호스트에서 시작될 수 있고, 연결된 EBS 볼륨 같은 자원은 상태와 무관하게 계속 과금된다.
  2. 재부팅재부팅(reboot)은 인스턴스를 삭제하지 않고 운영체제만 다시 시작한다. 인스턴스 ID와 설정이 유지된다.
  3. 종료종료(terminate)는 인스턴스를 영구 삭제한다. 종료 보호(termination protection)를 켜 두면 실수로 삭제되는 것을 막을 수 있고, 종료 시 데이터를 보존하도록 설정할 수도 있다.

인스턴스를 보존한 채 멈추고(중지), 운영체제만 다시 시작하고(재부팅), 완전히 없애는(종료) 상태 전환을 상황에 맞게 고르는 것

실행 중인 인스턴스의 메모리(RAM) 내용을 루트 EBS 볼륨에 저장한 뒤 중지해, 다시 시작할 때 애플리케이션 상태를 그대로 복원하는 기능이다.

→ 05-01 참조

#1문제 상황

애플리케이션이 부팅과 메모리 적재에 오래 걸리면, 인스턴스를 껐다 켤 때마다 처음부터 다시 준비해야 한다. 단순 중지·시작은 메모리(RAM) 내용을 사라지게 하므로 실행 중이던 프로세스와 상태가 초기화된다. 그래서 오래 걸리는 부트스트랩을 매번 반복하지 않도록 메모리 상태를 보존할 방법이 필요하다.

#2핵심 질문

인스턴스를 멈춰도 실행 중이던 메모리 상태를 그대로 되살릴 수는 없는가?

#3동작 예시

메모리에 큰 데이터를 올려 두고 오래 계산하는 인스턴스가 있다고 하자. 이 인스턴스를 최대 절전 모드로 중지하면 RAM 내용이 루트 EBS 볼륨에 저장된다. 이후 시작하면 저장해 둔 RAM 내용이 다시 적재되어, 이전에 돌던 프로세스가 그 상태 그대로 이어진다.

#4동작 과정

  1. 절전 요청인스턴스에 최대 절전이 활성화되어 있고 사전 조건을 만족할 때, EC2가 운영체제에 최대 절전(suspend-to-disk, 메모리 내용을 디스크에 저장하는 절전)을 지시한다.
  2. 메모리 저장RAM 내용이 루트 EBS 볼륨에 저장되고, 루트 볼륨과 연결된 데이터 볼륨이 유지된다. 인스턴스 ID도 그대로 남는다.
  3. 시작과 복원다시 시작하면 루트 볼륨이 이전 상태로 복원되고 RAM 내용이 재적재되며, 이전에 실행 중이던 프로세스와 연결된 데이터 볼륨이 다시 붙는다.

#5한 줄 요약

자동 복구와 은퇴

시스템 상태 검사에 실패한 인스턴스를 같은 인스턴스로 자동 복구하거나, AWS가 하드웨어 유지보수 등으로 인스턴스를 은퇴(retire)시켜 정지·종료를 예고하는 일을 다룬다.

#1문제 상황

인스턴스가 돌아가는 물리 호스트에 하드웨어나 소프트웨어 문제가 생기면 시스템 상태 검사에 실패하고 인스턴스에 접근하지 못할 수 있다. 관리자가 이를 알아채고 직접 손으로 옮기기 전까지 서비스는 멈춰 있게 된다. AWS가 이런 문제를 감지했을 때 사람 손 없이 가용성을 되살릴 방법이 필요하다.

#2핵심 질문

기반 하드웨어 문제로 인스턴스를 못 쓰게 됐을 때, 사람이 개입하지 않고 가용성을 되살릴 수 있는가?

#3동작 예시

인스턴스가 있는 호스트에 하드웨어 결함이 생겨 시스템 상태 검사가 실패했다고 하자. 이때 자동 복구가 설정돼 있으면 AWS가 그 인스턴스를 문제 있는 호스트에서 다른 정상 호스트로 옮겨 다시 띄운다. 사용자는 같은 인스턴스 ID로 계속 접근할 수 있다.

#4동작 과정

  1. 문제 감지AWS가 인스턴스가 기반 하드웨어나 소프트웨어 문제로 사용 불가 상태임을 감지한다. 이것이 시스템 상태 검사 실패로 나타난다.
  2. 인스턴스 복구복구 과정에서 AWS가 인스턴스를 문제 있는 호스트에서 다른 호스트로 옮기려 시도한다. 메커니즘은 단순화된 자동 복구와 CloudWatch 액션 기반 복구 두 가지가 있다.
  3. 은퇴 예고하드웨어 유지보수 등으로 인스턴스를 계속 둘 수 없으면 AWS가 인스턴스를 은퇴(retire)시켜 정지·종료 시점을 예고한다. 이용자는 그 전에 대응한다.

EBS 볼륨과 유형

Amazon EBS 볼륨은 EC2 인스턴스에 연결해 쓰는 네트워크 기반 블록 스토리지로, 워크로드에 따라 범용 SSD(gp3), 프로비저닝 IOPS SSD(io2), 처리량 최적화 HDD(st1), 콜드 HDD(sc1) 등 여러 유형 중에서 고른다.

→ 06-02 참조

#1문제 상황

인스턴스가 사라지면 그 안에 두었던 데이터도 함께 사라진다. 그래서 인스턴스 수명과 별개로 남는 저장 공간이 필요하고, 데이터베이스처럼 잦은 갱신이 있는 워크로드와 지속적인 디스크 스캔처럼 처리량이 중요한 워크로드는 요구가 서로 다르다. 하나의 저장 방식으로는 이런 다양한 요구를 감당하기 어렵다.

#2핵심 질문

인스턴스와 독립적으로 유지되면서 워크로드별 성능 요구에 맞는 블록 스토리지는 어떻게 고르는가?

#3동작 예시

데이터베이스를 돌리는 인스턴스에는 잦은 읽기·쓰기에 강한 범용 SSD(gp3)를 붙인다. 반대로 대용량을 순차적으로 훑는 로그 처리에는 비용이 낮은 처리량 최적화 HDD(st1)를 붙인다. 같은 인스턴스에 여러 EBS 볼륨을 붙일 수 있고, 볼륨과 인스턴스는 같은 가용 영역(Availability Zone, 데이터 센터를 나눈 물리적 구역)에 있어야 한다.

#4동작 과정

  1. 볼륨 생성스냅샷에서 만들거나 빈 볼륨을 만든다. 이 볼륨은 인스턴스와 별개로 수명을 가진다.
  2. 인스턴스에 연결같은 가용 영역에 있는 인스턴스에 볼륨을 붙여 물리 하드 드라이브처럼 사용한다. 한 인스턴스에 여러 볼륨을 붙일 수 있다.
  3. 유형 선택과 조정범용 SSD(gp3), 프로비저닝 IOPS SSD(io2), 처리량 최적화 HDD(st1), 콜드 HDD(sc1) 중에서 고른다. 최신 세대 볼륨과 인스턴스 유형에서는 운영 중에도 크기·IOPS·유형을 바꿀 수 있다.

EBS 볼륨 수명주기

EBS 볼륨 수명주기는 볼륨을 생성하고 인스턴스에 연결·사용한 뒤 크기나 성능을 변경하고, 필요하면 분리하거나 삭제하기까지의 일련의 단계를 말한다.

#1문제 상황

볼륨은 만들어 두기만 하면 끝이 아니라, 사용하다 보면 저장 공간이 부족해지고 성능이 모자라며, 필요 없어지면 비용을 계속 발생시킨다. 만들고 붙이고 쓰는 것만으로는 크기 변경, 분리, 삭제 같은 변화를 다룰 수 없다. 그래서 볼륨이 거치는 일련의 단계가 정해져 있다.

#2핵심 질문

EBS 볼륨을 만들고 쓴 뒤 크기·성능을 바꾸고, 필요하면 떼어내거나 지우기까지 어떤 순서로 진행하는가?

#3동작 예시

용량이 부족해진 데이터베이스 볼륨을 예로 들면, 운영 중에 볼륨 크기를 늘리도록 수정 요청한다. 수정이 반영되고 나면 인스턴스에 접속해 운영체제 명령으로 파일 시스템을 확장해야 늘어난 공간을 실제로 쓸 수 있다. 더 이상 필요 없으면 볼륨을 분리한 뒤 삭제해 저장 비용을 멈춘다.

#4동작 과정

  1. 생성과 연결스냅샷에서 또는 빈 볼륨으로 만든다. 사용하려면 볼륨과 같은 가용 영역에 있는 인스턴스에 붙이고, 인스턴스 안에서 사용할 수 있게 준비한다.
  2. 수정과 확장저장 요구가 바뀌면 언제든 크기나 성능을 바꾸도록 수정 요청한다. 반영 상태를 모니터링하고, 크기를 늘린 경우에는 파일 시스템도 확장한다.
  3. 분리와 삭제필요하면 볼륨을 인스턴스에서 떼어 다른 인스턴스에 붙인다. 더 이상 필요 없으면 삭제해 저장 비용을 멈춘다.

EBS 스냅샷

EBS 스냅샷은 특정 시점의 EBS 볼륨 데이터를 Amazon S3에 증분 저장해 두는 백업으로, 이를 이용해 새 볼륨을 만들거나 다른 리전으로 복사할 수 있다.

→ 06-05 참조

#1문제 상황

EBS 볼륨에 담긴 데이터는 AWS가 자동으로 백업해 주지 않는다. 볼륨이 손상되거나 실수로 지워지면 데이터를 되돌릴 방법이 없다. 게다가 매번 볼륨 전체를 복사해 백업하면 시간과 저장 비용이 그대로 늘어난다.

#2핵심 질문

EBS 볼륨 데이터를 시점 단위로 안전하게 백업하고, 그 백업으로 새 볼륨을 만들려면 어떻게 하는가?

#3동작 예시

어떤 볼륨의 스냅샷을 처음 만들면 그 시점의 모든 블록이 저장된다. 이후 데이터가 일부 바뀐 뒤 다시 스냅샷을 만들면, 가장 최근 스냅샷 이후 바뀐 블록만 저장된다. 이렇게 저장한 스냅샷으로 새 볼륨을 만들거나 다른 리전으로 복사할 수 있다.

#4동작 과정

  1. 스냅샷 생성볼륨의 특정 시점 복사본을 만든다. 이때 이전 스냅샷 이후 변경된 블록만 저장하는 증분 백업으로 동작해 시간과 비용을 줄인다.
  2. 공유·복사·보관스냅샷을 다른 계정과 공유하거나 다른 리전으로 복사할 수 있고, 잘 쓰지 않는 스냅샷은 아카이브로 보관해 비용을 낮춘다.
  3. 복원과 활용스냅샷에서 새 볼륨을 만든다. 아카이브한 스냅샷은 복원 과정을 거쳐 다시 사용할 수 있다.

#5한 줄 요약

EBS 볼륨의 특정 시점 데이터를 증분으로 저장해 두었다가 새 볼륨 생성이나 다른 리전 복사에 활용하는 백업

Data Lifecycle Manager와 Recycle Bin

Amazon Data Lifecycle Manager는 정책으로 EBS 스냅샷과 AMI 생성·보존·삭제를 자동화하는 서비스이고, Recycle Bin은 삭제한 스냅샷·볼륨·AMI를 보존 규칙에 따라 일정 기간 복구할 수 있게 잡아 두는 기능이다.

→ 06-03 참조

#1문제 상황

EBS 스냅샷과 AMI를 손으로 만들면, 언제 만들고 언제 지울지를 사람이 계속 기억해야 합니다. 스냅샷은 주기적으로 찍어야 데이터가 보호되는데, 담당자가 빠뜨리면 백업 공백이 생깁니다.

또 오래된 스냅샷을 정리하지 않으면 스토리지 비용이 계속 쌓입니다. 반대로 삭제를 너무 성급히 하거나 실수로 지우면 되돌릴 방법이 없어 복구가 불가능해집니다. 생성·보존·삭제를 매번 수동으로 관리하는 방식은 이 두 문제를 동시에 안고 있습니다.

#2핵심 질문

EBS 스냅샷과 AMI의 생성·보존·삭제를 사람 손에서 떼어내고, 삭제한 뒤에도 일정 기간 되살릴 수 있게 하려면 어떻게 해야 하는가?

#3동작 예시

"매일 새벽 3시에 볼륨 A의 스냅샷을 찍고, 7일이 지난 것은 자동으로 지운다"는 정책을 한 번 만들어 두면, Data Lifecycle Manager가 그 일정대로 스냅샷을 생성하고 오래된 것을 삭제합니다. 개발자가 매일 콘솔에 들어가 스냅샷을 손으로 만들 필요가 없고, 정책에 적힌 보존 기간이 지나면 자동으로 정리됩니다.

#4동작 과정

  1. 정책 생성스냅샷인지 AMI인지, 어떤 대상 볼륨·인스턴스에 적용할지, 얼마나 자주 만들지, 며칠 보존할지를 정책에 적습니다. 정책을 만들면 지정한 일정과 보존 규칙이 하나의 자동화 단위가 됩니다.
  2. 일정에 따른 실행정책의 스케줄(예: 매일, 매주)에 맞춰 Data Lifecycle Manager가 스냅샷이나 AMI를 생성하고, 태그로 이 자원이 어느 정책에서 만들어졌는지 표시합니다. 이 태그 덕분에 어느 스냅샷이 자동 생성분인지 나중에 추적할 수 있습니다.
  3. 보존 기간 경과 후 삭제보존 기간이 지난 스냅샷·AMI는 정책에 따라 자동 삭제됩니다. 이때 Recycle Bin에 보존 규칙을 걸어 두면 삭제된 자원이 곧바로 사라지지 않고 규칙에 정한 기간 동안 남아, 필요하면 복구할 수 있습니다.

#5한 줄 요약

EBS 스냅샷과 AMI의 생성·보존·삭제를 정책으로 자동화하고, 삭제된 자원은 Recycle Bin에 일정 기간 잡아 두어 되살릴 수 있게 하는 것

EBS 암호화·성능·보안

EBS 암호화는 KMS 키로 볼륨과 스냅샷의 데이터를 저장 시 암호화하고 연결된 인스턴스에서 투명하게 복호화하는 기능으로, 볼륨 유형·크기·인스턴스 대역폭 설정과 함께 EBS 성능과 보안을 좌우한다.

#1문제 상황

EBS 볼륨과 스냅샷에는 운영체제 이미지, 데이터베이스 파일처럼 민감한 데이터가 그대로 저장됩니다. 암호화를 하지 않으면 저장 매체에 있는 데이터가 그대로 노출되고, 인스턴스와 스토리지 사이를 오가는 데이터도 보호되지 않습니다.

직접 키 관리 인프라를 만들어 운영하는 방식은 키 생성·보관·교체·접근 통제를 모두 책임져야 해서 부담이 큽니다. 여기에 더해 볼륨 유형·크기 선택을 잘못하면 처리량이 부족해지고, 반대로 과하게 잡으면 비용이 낭비됩니다. 암호화와 성능을 각각 따로 챙기는 방식은 관리 부담과 설정 실수를 함께 키웁니다.

#2핵심 질문

별도 키 관리 인프라를 직접 만들지 않고도 EBS 데이터를 저장·전송 구간에서 안전하게 지키면서, 인스턴스가 낼 수 있는 성능까지 제대로 뽑아내려면 어떻게 해야 하는가?

#3동작 예시

암호화된 볼륨을 만들면 AWS KMS 키로 데이터가 저장 시점에 암호화됩니다. 이 볼륨을 인스턴스에 연결하면 인스턴스는 암호화 여부를 신경 쓰지 않고 평소처럼 읽고 쓸 수 있습니다. 복호화는 암호화 연산을 처리하는 서버에서 이루어지므로, 인스턴스에 연결된 상태에서도 데이터는 저장 구간에서 암호화된 채로 유지됩니다.

#4동작 과정

  1. KMS 키로 볼륨·스냅샷 암호화볼륨이나 스냅샷을 만들 때 사용할 KMS 키를 지정하면 저장 데이터가 암호화됩니다. 스냅샷에서 복원한 볼륨이나 암호화된 스냅샷에서 만든 자원도 같은 방식으로 암호화 상태가 이어집니다.
  2. 인스턴스에서 투명하게 사용인스턴스는 연결된 볼륨을 평소처럼 읽고 씁니다. 복호화는 암호화 연산을 처리하는 호스트에서 일어나므로 애플리케이션이 따로 복호화 코드를 넣을 필요가 없고, 인스턴스와 저장소 사이 전송 구간도 보호됩니다.
  3. 성능·보안 설정 조정볼륨 유형과 크기, 인스턴스의 EBS 대역폭을 워크로드에 맞게 정하고, IAM 정책으로 누가 어떤 볼륨·스냅샷에 접근할지 통제합니다. 이 설정들이 모여 실제 처리량과 접근 권한이 결정됩니다.

#5한 줄 요약

저장 데이터와 전송 데이터를 KMS 키로 암호화하면서, 볼륨 유형·대역폭·IAM 통제로 성능과 접근 권한을 함께 관리하는 것

인스턴스 스토어·루트 볼륨·블록 디바이스

인스턴스 스토어는 호스트에 물리적으로 붙은 임시 블록 스토리지, 루트 볼륨은 인스턴스가 부팅하는 볼륨, 블록 디바이스 매핑은 이런 볼륨들을 인스턴스의 어떤 디바이스 이름에 어떻게 붙일지 정의하는 설정이다.

→ 06-01 참조

#1문제 상황

인스턴스가 부팅하려면 운영체제가 올라갈 볼륨이 있어야 하고, 임시 데이터를 빠르게 다룰 공간도 필요합니다. 모든 저장 공간을 네트워크로 연결된 EBS로만 구성하면, 자주 바뀌는 임시 데이터까지 매번 네트워크를 거쳐야 해서 지연이 생깁니다.

또 호스트에 물리적으로 붙은 저장 공간은 인스턴스가 멈추거나 옮겨지면 내용이 사라진다는 특성이 있습니다. 이런 공간을 어디에 어떻게 붙일지, 어떤 이름으로 인스턴스에 노출할지를 정하지 않으면 운영체제가 저장 장치를 제대로 찾지 못합니다.

#2핵심 질문

빠르지만 사라지는 임시 저장 공간과, 부팅에 반드시 필요한 루트 볼륨을 인스턴스가 알아볼 수 있는 장치 이름에 어떻게 정확히 연결해 줄 것인가?

#3동작 예시

인스턴스를 띄우면서 루트 볼륨은 20GB EBS로, 추가로 호스트에 붙은 인스턴스 스토어 볼륨 하나를 함께 지정합니다. 인스턴스 안에서는 루트 볼륨이 부팅 디스크로, 인스턴스 스토어 볼륨이 별도의 임시 디스크로 보입니다. 캐시나 임시 파일은 인스턴스 스토어에 두어 빠르게 처리하고, 사라지면 안 되는 데이터는 EBS에 둡니다.

#4동작 과정

  1. 블록 디바이스 매핑 정의인스턴스나 AMI에 어떤 볼륨을 어떤 장치 이름에 붙일지 매핑을 적습니다. 루트 볼륨인지, EBS인지 인스턴스 스토어인지, 크기와 삭제 시 동작까지 이 매핑에 담깁니다.
  2. 인스턴스 시작 시 볼륨 연결인스턴스가 뜨면 매핑에 따라 볼륨이 정해진 장치 이름으로 연결됩니다. 운영체제는 이 장치를 디스크로 인식하고, 필요하면 사용할 수 있도록 초기화하거나 파일 시스템을 올립니다.
  3. 특성에 맞게 사용인스턴스 스토어는 호스트에 붙어 있어 빠르지만 인스턴스를 중지·종료하거나 다른 호스트로 옮기면 데이터가 사라집니다. 그래서 임시 데이터만 두고, 유지해야 할 데이터는 영속적인 EBS에 저장하는 식으로 역할을 나눕니다.

#5한 줄 요약

빠르지만 사라지는 인스턴스 스토어와 부팅용 루트 볼륨을 블록 디바이스 매핑으로 인스턴스에 정확히 연결해, 데이터 성격에 맞는 저장 공간을 쓰게 하는 것

#1문제 상황

스냅샷 안의 데이터를 확인하거나 스냅샷 사이의 변경분만 알아내려면, 기존에는 스냅샷으로 볼륨을 만들고 그 볼륨을 인스턴스에 붙여 비교해야 했습니다. 이 방식은 볼륨 생성과 인스턴스 운영 시간이 들고, 백업 서비스를 만드는 입장에서는 비용과 절차가 모두 부담입니다.

또 EBS 자원이 늘어나면 어디에 얼마나 쓰이는지, 볼륨 수가 한도에 얼마나 가까운지 파악하기 어려워집니다. 여러 서비스의 백업을 각각 따로 관리하면 일관된 백업 정책을 세우기도 힘듭니다.

#2핵심 질문

볼륨과 인스턴스를 새로 만들지 않고도 스냅샷 데이터를 직접 읽고 쓰고 비교하며, 흩어진 백업 관리와 자원 한도까지 한곳에서 관찰하려면 어떻게 해야 하는가?

#3동작 예시

백업 서비스를 운영하는 개발자가 EBS direct API로 스냅샷의 블록을 직접 읽어, 두 스냅샷 사이에서 바뀐 블록만 골라냅니다. 볼륨을 새로 만들지 않아도 변경분을 알 수 있어, 증분 백업을 훨씬 가볍게 만들 수 있습니다. 동시에 AWS Backup으로 여러 서비스의 백업을 한 정책 아래 묶고, CloudWatch와 EventBridge로 상태를 지켜봅니다.

#4동작 과정

  1. direct API로 스냅샷 직접 접근스냅샷의 블록 데이터를 API로 직접 읽고 쓰며, 두 스냅샷의 차이도 확인합니다. 볼륨 생성과 인스턴스 운영이라는 중간 단계를 건너뛰어, 변경분 추적과 온프레미스 데이터의 클라우드 반영이 가벼워집니다.
  2. AWS Backup으로 백업 중앙 관리EBS를 포함한 여러 서비스의 백업을 하나의 백업 계획으로 묶어 생성·보존을 관리합니다. 서비스마다 백업을 따로 설정하지 않아도 되어 정책이 일관됩니다.
  3. 모니터링·쿼터로 관찰과 제한CloudWatch 지표와 EventBridge 이벤트로 볼륨 상태를 지켜보고, 계정의 볼륨·스냅샷 수 같은 한도(쿼터)를 확인합니다. 사용량이 한도에 가까운지 파악해 자원을 늘리거나 정리합니다.

인스턴스 IP 주소와 호스트 이름

EC2 인스턴스는 생성 시 VPC 서브넷 대역에서 사설 IPv4 주소를 자동으로 받고, 공인 IPv4·IPv6·탄력적 IP를 선택적으로 가지며, 각 주소에 매핑되는 내부·외부 DNS 호스트 이름으로 식별된다.

→ 07-02 참조

#1문제 상황

인스턴스가 네트워크에서 통신하려면 주소가 있어야 하는데, 주소를 아무렇게나 붙이면 충돌이 나거나 외부에서 접근할 수 없습니다. 특히 인스턴스가 사설망 안에서만 쓰는 주소와 외부 인터넷에서 쓰는 주소는 역할이 다릅니다.

주소만 있고 이름이 없으면 사람이 대상을 기억하기 어렵고, 반대로 사설 주소와 공인 주소가 어떻게 대응하는지 헷갈리면 연결 설정이 자주 틀립니다. 어떤 주소가 어디서 붙고 어떤 이름으로 불리는지를 정리해 두지 않으면 인스턴스마다 접근 방식이 제각각이 됩니다.

#2핵심 질문

각 인스턴스에 사설·공인 주소와 그에 대응하는 호스트 이름을 어떤 규칙으로 붙여, 안과 밖에서 일관되게 찾아갈 수 있게 할 것인가?

#3동작 예시

VPC와 서브넷을 지정해 인스턴스를 띄우면, 인스턴스는 그 서브넷의 사설 주소 대역에서 사설 IPv4 주소를 자동으로 받습니다. 여기에 공인 IPv4 주소를 선택적으로 붙이면, 내부 통신은 사설 주소로, 외부 접속은 공인 주소로 이루어집니다. 각 주소에는 내부용·외부용 DNS 호스트 이름이 매핑되어 이름으로도 찾을 수 있습니다.

#4동작 과정

  1. 사설 IPv4 주소 자동 할당인스턴스를 만들 때 지정한 서브넷의 사설 대역에서 사설 IPv4 주소를 받습니다. VPC는 기본적으로 IPv4를 사용하며, 이 사설 주소가 인스턴스의 기본 통신 주소가 됩니다.
  2. 공인 주소·IPv6 선택적 추가필요하면 공인 IPv4 주소를 붙이고, VPC에 IPv6 대역을 연결했다면 인스턴스에 IPv6 주소도 줄 수 있습니다. 보조 사설 주소를 여러 개 붙여 한 인스턴스에 여러 주소를 쓰게 할 수도 있습니다.
  3. 호스트 이름으로 식별각 주소에 내부·외부 DNS 호스트 이름이 매핑됩니다. 내부 이름은 VPC 안에서, 외부 이름은 바깥에서 그 인스턴스를 가리키는 데 쓰여, 주소를 외우지 않고도 대상을 찾을 수 있습니다.

#5한 줄 요약

인스턴스에 사설 주소를 기본으로 주고 공인·IPv6 주소를 선택적으로 더하며, 각 주소를 DNS 호스트 이름에 매핑해 안과 밖에서 일관되게 식별하게 하는 것

탄력적 IP와 BYOIP

탄력적 IP(EIP)는 계정에 고정 할당되어 인스턴스나 ENI에 연결·재연결할 수 있는 공인 IPv4 주소이고, BYOIP는 자신이 보유한 공인 IP 대역을 AWS로 가져와 EC2 리소스에 사용하는 기능이다.

→ 07-01 참조

#1문제 상황

인스턴스에 붙는 공인 IPv4 주소는 인스턴스를 중지했다 다시 시작하면 바뀔 수 있습니다. 그래서 인스턴스를 재시작할 때마다 외부에 알려 준 주소가 달라지고, DNS 레코드나 방화벽 허용 목록을 다시 손봐야 하는 일이 생깁니다.

이 문제를 피하려고 주소를 고정해 두는 방법이 필요합니다. 또 이미 자체적으로 보유한 공인 IP 대역을 쓰던 조직은, 그 대역을 그대로 클라우드 리소스에 옮겨 쓰고 싶어 합니다. 주소를 매번 새로 받는 방식으로는 이런 요구를 채울 수 없습니다.

#2핵심 질문

인스턴스가 바뀌어도 주소를 그대로 유지하거나, 이미 보유한 공인 IP 대역을 AWS로 가져와 쓰려면 어떻게 해야 하는가?

#3동작 예시

탄력적 IP를 하나 할당받아 인스턴스 A에 연결해 두면, 인스턴스 A를 멈추고 다른 인스턴스 B를 띄운 뒤 같은 탄력적 IP를 B에 다시 연결할 수 있습니다. 외부에서는 주소가 그대로이므로, 접속 대상만 바뀌고 들어오는 주소는 변하지 않습니다. 이 주소를 도메인 DNS 레코드에 적어 두면 도메인이 계속 같은 곳을 가리킵니다.

#4동작 과정

  1. 주소 할당탄력적 IP를 계정에 할당하면, 계정이 그 주소를 놓아줄 때까지 계정 소유로 남습니다. 이 시점에 주소가 인스턴스에 묶이지 않고 계정 단위로 확보됩니다.
  2. 연결과 재연결탄력적 IP를 인스턴스나 네트워크 인터페이스에 연결합니다. 인스턴스에 문제가 생기거나 교체할 때는 같은 주소를 다른 인스턴스에 빠르게 다시 연결해, 외부에 알린 주소를 그대로 유지할 수 있습니다.
  3. 해제 또는 대역 반입더 이상 필요 없으면 주소를 반환(해제)합니다. 자체 보유한 공인 IP 대역을 쓰려면 그 대역을 AWS로 가져와(온보딩) 계정의 리소스에 할당해, 기존 주소 체계를 그대로 이어 쓸 수 있습니다.

#5한 줄 요약

공인 IPv4 주소를 계정에 고정해 인스턴스 사이에 재연결하며 유지하고, 보유한 주소 대역도 AWS로 가져와 쓰게 하는 것

네트워크 인터페이스(ENI)

네트워크 인터페이스(ENI)는 서브넷 안에 존재하는 가상 네트워크 카드로, MAC 주소·사설 IP·보안 그룹·연결 상태를 가지며 인스턴스에 연결하거나 분리할 수 있는 EC2 네트워킹의 기본 단위다.

→ 07-04 참조

#1문제 상황

인스턴스가 네트워크에 연결되려면 가상 네트워크 카드가 필요하고, 그 카드에는 주소·보안 규칙·연결 상태 같은 설정이 붙습니다. 이런 설정을 인스턴스에 직접 묶어 두면, 인스턴스를 옮기거나 바꿀 때마다 네트워크 설정을 처음부터 다시 잡아야 합니다.

또 한 인스턴스에 주소를 여러 개 주거나 네트워크를 분리해야 할 때, 설정을 재사용할 방법이 없으면 매번 새로 구성해야 합니다. 네트워크 설정을 인스턴스와 분리해 두고 필요할 때 붙였다 떼는 구조가 필요합니다.

#2핵심 질문

주소·보안 규칙·연결 상태 같은 네트워크 설정을 인스턴스와 분리해, 필요할 때 붙이고 떼고 재사용하려면 어떻게 해야 하는가?

#3동작 예시

네트워크 인터페이스 하나를 만들어 사설 IPv4 주소와 보안 그룹을 설정해 둡니다. 이 인터페이스를 인스턴스에 연결하면 인스턴스가 그 주소와 보안 규칙을 그대로 사용합니다. 인터페이스를 떼어 다른 인스턴스에 붙이면, 설정과 주소가 함께 따라가고 트래픽도 새 인스턴스로 향합니다.

#4동작 과정

  1. 인터페이스 생성과 속성 설정같은 가용 영역 안에서 네트워크 인터페이스를 만들고, 기본 사설 IPv4 주소와 보안 그룹, MAC 주소 같은 속성을 부여합니다. 이 속성들은 인터페이스에 붙어 다닙니다.
  2. 인스턴스에 연결인터페이스를 인스턴스에 연결하면 인스턴스가 그 네트워크 카드를 통해 통신합니다. 연결·분리·재연결을 해도 주소와 보안 그룹 같은 속성은 인터페이스를 따라 이동합니다.
  3. 주소·다중 인터페이스 관리필요하면 보조 사설 주소를 추가하거나 프리픽스를 위임하고, 여러 인터페이스를 붙여 네트워크를 나눌 수 있습니다. 쓰지 않는 인터페이스는 삭제해 정리합니다.

향상된 네트워킹과 EFA

향상된 네트워킹은 ENA 같은 전용 드라이버로 단일 루트 I/O 가상화를 사용해 대역폭과 패킷 처리 성능을 높이는 기능이며, EFA는 고성능 컴퓨팅·머신러닝 클러스터용으로 OS를 우회해 노드 간 지연을 크게 낮춘 네트워크 인터페이스다.

→ 07-03 참조

#1문제 상황

전통적인 가상 네트워크 인터페이스는 하이퍼바이저가 각 패킷을 소프트웨어로 중계해 가상 머신에 전달한다. 이 방식은 패킷마다 CPU가 개입해야 하므로 대역폭이 높아질수록 CPU 사용률이 함께 치솟고, 초당 처리할 수 있는 패킷 수(PPS)에 한계가 생기며 지연도 일정하게 낮추기 어렵다. 여러 노드가 촘촘히 데이터를 주고받는 HPC·머신러닝 클러스터에서는 이 소프트웨어 중계 비용과 노드 간 지연이 전체 연산 시간을 좌우하는 병목이 된다.

#2핵심 질문

소프트웨어 중계에 드는 CPU 비용과 노드 간 지연을 줄이면서 대역폭·패킷 처리량을 끌어올리려면 네트워크를 어떻게 다뤄야 하는가?

#3동작 예시

단일 루트 I/O 가상화(SR-IOV)를 쓰면 물리 네트워크 카드가 여러 개의 가상 기능(VF)을 노출하고, 인스턴스는 하이퍼바이저를 거치지 않고 자기 VF에 직접 접근한다. 인스턴스가 보낸 패킷은 소프트웨어 중계 대신 카드가 직접 처리하므로 CPU 개입이 줄고, 같은 물리 카드를 쓰는 노드들 사이에서는 지연이 낮고 일정하게 유지된다.

#4동작 과정

  1. 드라이버 준비ENA(Elastic Network Adapter) 같은 전용 드라이버를 인스턴스 OS에 설치한다. 드라이버가 있으면 운영체제가 SR-IOV 가상 기능을 인식해 하드웨어로 직접 경로를 연다.
  2. 인터페이스 활성화·큐 설정인스턴스가 지원하는 유형에서 향상된 네트워킹을 켜고 ENA 큐(queue, 패킷을 나눠 처리하는 작업 대기열) 수를 조정한다. 큐가 여러 개면 여러 CPU 코어가 패킷을 병렬로 처리해 PPS가 올라간다.
  3. 지연·대역폭 최적화ENA Express로 전송 계층 처리를 가속하거나, EFA(Elastic Fabric Adapter)를 붙여 OS 커널을 우회(bypass)하는 경로로 노드 간 통신을 처리한다. 그 결과 클러스터 통신 지연이 크게 낮아진다.

#5한 줄 요약

SR-IOV 전용 드라이버로 소프트웨어 중계 비용을 없애 대역폭과 패킷 처리량을 높이고, EFA로 커널을 우회해 노드 간 지연까지 낮추는 것

배치 그룹·MTU·보조 네트워크

배치 그룹은 인스턴스를 클러스터·분산·파티션 전략에 따라 물리 하드웨어에 배치해 지연과 장애 영향을 조정하는 기능이고, MTU는 인스턴스의 프레임 크기를, 보조 네트워크는 기본 VPC와 분리된 추가 네트워크 연결을 다룬다.

#1문제 상황

인스턴스를 그냥 여러 개 띄우면 어느 물리 하드웨어에 올라갈지 사용자가 정할 수 없다. 서로 긴밀하게 통신해야 하는 노드들이 멀리 떨어진 하드웨어에 흩어지면 지연이 커지고, 반대로 한 곳에 몰리면 하드웨어 하나가 죽을 때 여러 인스턴스가 함께 영향을 받는다. 또한 인스턴스가 주고받는 프레임 크기(MTU)가 경로마다 다르면 큰 패킷이 쪼개지거나 버려져 처리량이 떨어질 수 있다.

#2핵심 질문

인스턴스의 물리적 배치와 프레임 크기를 워크로드 특성에 맞게 조정해 지연·장애 영향·처리량을 원하는 방향으로 제어하려면 어떻게 해야 하는가?

#3동작 예시

지연에 민감한 HPC 애플리케이션은 클러스터(Cluster) 전략의 배치 그룹에 인스턴스를 넣어 한 가용 영역 안에 서로 가깝게 밀집 배치한다. 그러면 노드 간 네트워크 지연이 낮아지고, 같은 그룹 인스턴스끼리는 높은 대역폭의 통신 경로를 쓸 수 있다. 반대로 서로 장애를 격리해야 하는 복제 워크로드는 파티션(Partition) 전략으로 논리 파티션별로 다른 하드웨어에 흩어 배치한다.

#4동작 과정

  1. 전략 선택·생성워크로드에 맞는 배치 전략(클러스터·파티션·분산)을 정해 배치 그룹을 만든다. 전략에 따라 인스턴스가 한 AZ에 밀집하거나, 파티션·호스트별로 분산 배치된다.
  2. 인스턴스 배치 지정인스턴스를 띄울 때 그 배치 그룹을 지정한다. 이후 필요하면 인스턴스의 배치를 다른 그룹으로 옮겨 배치를 조정할 수 있다.
  3. MTU·보조 네트워크 조정인스턴스에 맞는 MTU(프레임 최대 크기)를 설정해 큰 패킷이 불필요하게 쪼개지지 않게 하고, 필요하면 기본 VPC와 분리된 보조 네트워크(Secondary Networks)로 별도 연결을 구성한다.

#5한 줄 요약

배치 전략·MTU·보조 네트워크로 인스턴스의 물리 배치와 네트워크 특성을 워크로드에 맞게 제어해 지연과 장애 영향을 조정하는 것

보안 개요와 규정 준수

EC2의 보안 책임 분담 모델과 데이터 보호·인프라 보안·복원력·규정 준수 검증 체계를 한눈에 정리한 보안 총괄 개념이다.

#1문제 상황

클라우드에서 인스턴스를 운영하면 물리 데이터센터의 보안은 AWS가 책임지지만, 그 위에서 실행되는 게스트 OS·애플리케이션·데이터·접근 제어는 사용자 몫이다. 이 경계를 구분하지 않으면 "클라우드니까 안전하다"고 오해해 네트워크 접근 통제나 데이터 보호를 빠뜨리기 쉽다. 또한 특정 업계·정부 규정을 따라야 하는 조직은 그 서비스가 어떤 규정 준수 검증을 통과했는지 근거를 확인해야 한다.

#2핵심 질문

AWS와 사용자가 각각 무엇을 책임지는지 구분하고, 데이터 보호·인프라 보안·복원력·규정 준수를 어떤 체계로 확인하고 갖추어야 하는가?

#3동작 예시

책임 분담 모델에서 AWS는 클라우드 자체의 보안(security of the cloud)을, 사용자는 클라우드 안에서의 보안(security in the cloud)을 담당한다. 예를 들어 사용자는 VPC와 보안 그룹을 구성해 인스턴스로 드나드는 네트워크 접근을 통제하는 책임을 진다. 한편 STIG(보안 기술 구현 지침) 같은 기준을 적용하려면 제공되는 설정과 스크립트를 내려받아 Systems Manager로 인스턴스에 반영해 규정 준수 상태를 맞춘다.

#4동작 과정

  1. 책임 경계 파악공동 책임 모델에서 AWS가 맡는 인프라 보안과 사용자가 맡는 게스트 OS·데이터·접근 통제를 구분한다. 이 경계를 알아야 놓치는 통제 항목이 줄어든다.
  2. 통제 적용데이터 보호·인프라 보안·복원력 요구에 맞춰 네트워크 접근 통제, 데이터 암호화, 백업·복구 체계를 갖춘다. 각 통제는 사용자 책임 영역에 배치된다.
  3. 규정 준수 검증AWS Compliance Programs와 서비스 범위 목록에서 해당 규정 검증 여부를 확인하고, STIG 같은 기준이 필요하면 설정·스크립트를 내려받아 Systems Manager로 인스턴스에 적용한다.

#5한 줄 요약

AWS와 사용자의 보안 책임 경계를 나누고 데이터 보호·인프라 보안·복원력·규정 준수 통제를 사용자 영역에 갖추게 하는 것

IAM 정책과 역할

EC2 API와 콘솔 작업을 누가 할 수 있는지 정의하는 자격 증명 기반 정책과, 인스턴스가 다른 AWS 서비스를 호출할 때 쓰는 IAM 역할을 다루는 접근 관리 개념이다.

#1문제 상황

여러 사용자·서비스가 하나의 AWS 계정에서 EC2를 함께 쓴다면, 아무 통제 없이 모두가 같은 자격 증명을 공유하게 된다. 그러면 누가 무엇을 할 수 있는지 구분되지 않고, 인스턴스 위의 애플리케이션이 다른 AWS 서비스를 호출하려면 자격 증명을 코드에 넣어야 해 노출 위험이 커진다. 권한을 사람마다·작업마다 세분화하지 않으면 실수로 리소스를 지우거나 과도한 권한이 새는 문제가 생긴다.

#2핵심 질문

자격 증명을 공유하지 않으면서 EC2 리소스에 대한 접근을 사용자·작업별로 안전하게 통제하려면 어떻게 해야 하는가?

#3동작 예시

개발자가 EC2 콘솔을 쓸 때는 자격 증명 기반 정책(identity-based policy)으로 "이 사용자는 이 인스턴스만 시작·중지할 수 있다"처럼 허용 범위를 정의한다. 인스턴스 위의 애플리케이션이 S3에 접근해야 할 때는 자격 증명을 코드에 넣는 대신 인스턴스에 IAM 역할을 붙여, 애플리케이션이 그 역할의 임시 보안 자격 증명을 받아 서비스를 호출하게 한다.

#4동작 과정

  1. 정책으로 권한 정의자격 증명 기반 정책에 누가 어떤 EC2 API·콘솔 작업을 할 수 있는지 적는다. API용·콘솔용 예제 정책과 AWS 관리형 정책을 참고해 필요한 권한만 부여한다.
  2. 역할 부여인스턴스가 다른 서비스를 호출해야 하면 그 인스턴스에 IAM 역할을 붙일 권한을 가진 사용자가 역할을 연결한다. 자격 증명을 공유하지 않고도 애플리케이션이 권한을 얻는다.
  3. 자격 증명 조회인스턴스는 연결된 역할의 임시 보안 자격 증명을 조회해 사용한다. 사람이 키를 심어두지 않아도 되고, 권한이 역할 단위로 통제된다.

#5한 줄 요약

자격 증명 기반 정책으로 작업 권한을 정의하고 인스턴스에는 역할을 붙여, 자격 증명을 공유하지 않고 EC2 접근과 서비스 호출을 통제하는 것

보안 그룹과 업데이트 관리

인스턴스로 드나드는 트래픽을 허용 규칙으로 제어하는 보안 그룹과, 인스턴스의 패치·소프트웨어 최신 상태를 유지하는 업데이트 관리를 묶은 보안 운영 개념이다.

#1문제 상황

인스턴스를 기본 설정 그대로 두면 필요한 포트는 열려 있고 불필요한 포트는 그대로 노출될 수 있다. 인스턴스마다 OS 방화벽을 개별 관리하면 규칙이 흩어져 관리가 어렵고, 어떤 트래픽이 허용되는지 한눈에 파악하기 힘들다. 또한 인스턴스에 설치된 OS·소프트웨어를 최신 상태로 유지하지 않으면 알려진 취약점이 그대로 남아 공격 대상이 된다.

#2핵심 질문

인스턴스로 드나드는 트래픽을 규칙으로 통제하고, 패치와 소프트웨어 최신 상태를 꾸준히 유지하려면 어떻게 관리해야 하는가?

#3동작 예시

인스턴스에 보안 그룹을 지정하면, 인바운드 규칙은 들어오는 트래픽을, 아웃바운드 규칙은 나가는 트래픽을 제어한다. 예를 들어 특정 IP 대역에서만 SSH 접속을 허용하는 인바운드 규칙을 넣으면 그 외의 접속 시도는 인스턴스에 닿기 전에 차단된다. 연결 추적(connection tracking) 덕분에 허용된 인바운드 연결의 응답 트래픽은 별도 아웃바운드 규칙 없이도 나갈 수 있다.

#4동작 과정

  1. 보안 그룹 생성·지정인스턴스를 띄울 때 하나 이상의 보안 그룹을 지정한다. 지정하지 않으면 VPC의 기본 보안 그룹이 적용되므로, 용도에 맞는 그룹을 직접 만들어 붙이는 편이 안전하다.
  2. 규칙 조정인바운드·아웃바운드 규칙을 용도별로 구성하고, 필요하면 인스턴스에 연결된 보안 그룹을 바꾼다. 허용 규칙 기반이라 명시적으로 연 트래픽만 통과한다.
  3. 업데이트 유지인스턴스의 패치와 소프트웨어를 최신 상태로 유지한다. 접근 통제와 최신 패치가 함께 갖춰져야 노출된 취약점이 줄어든다.

#5한 줄 요약

보안 그룹의 허용 규칙으로 인스턴스 트래픽을 통제하고 패치·소프트웨어를 최신으로 유지해 인스턴스를 안전하게 운영하는 것

NitroTPM·증명·Credential Guard·PrivateLink

NitroTPM 기반 인스턴스 증명, Windows Credential Guard, AWS PrivateLink로 EC2에 프라이빗하게 접근하는 하드웨어·네트워크 수준 보안 기능을 다루는 개념이다.

#1문제 상황

인스턴스가 정말 신뢰할 수 있는 소프트웨어와 부팅 과정으로 실행 중인지 외부에서 확인할 방법이 없으면, 부팅 단계가 변조되어도 그대로 서비스를 신뢰하게 된다. 운영자가 자기 관리하는 인스턴스에 마음대로 접근할 수 있는 환경에서는 민감한 데이터를 운영자로부터 격리하기도 어렵다. 또한 EC2 API를 퍼블릭 인터넷을 거치지 않고 사설로만 호출하고 싶은 요구도 있다.

#2핵심 질문

인스턴스에서 실행 중인 소프트웨어와 부팅 과정이 신뢰할 수 있음을 암호학적으로 증명하고, 접근을 사설 경로로 좁히려면 어떻게 해야 하는가?

#3동작 예시

증명(attestation)은 NitroTPM과 Attestable AMI를 기반으로 한다. 먼저 Attestable AMI를 만들어 그 안의 소프트웨어·설정에 대한 기준 측정값(reference measurements)을 확보해 둔다. 실행 중인 인스턴스는 NitroTPM이 만든 증명 문서(Attestation Document)를 내보내고, 검증자는 이 문서의 측정값을 기준값과 대조해 신뢰할 수 있는 소프트웨어만 돌고 있음을 암호학적으로 확인한다.

#4동작 과정

  1. AMI 준비Attestable AMI를 만들고 기준 측정값을 계산한다. 어떤 소프트웨어·설정이 포함됐는지의 기준이 되는 값이 여기서 정해진다.
  2. 증명 문서 생성대상 AWS KMS를 준비한 뒤 인스턴스에서 NitroTPM 증명 문서를 얻는다. 이 문서에는 실행 중인 환경의 측정값이 담긴다.
  3. 검증·활용증명 문서를 기준 측정값과 대조해 검증하고 AWS KMS와 연동한다. 신뢰가 확인된 경우에만 키를 쓸 수 있게 해 데이터를 운영자로부터 격리할 수 있다. Windows 인스턴스는 Credential Guard로 자격 증명 보호를 강화하고, EC2 접근은 AWS PrivateLink로 사설 경로를 구성한다.

#5한 줄 요약

NitroTPM 증명 문서와 기준 측정값을 대조해 인스턴스의 신뢰를 암호학적으로 증명하고, 데이터 격리·자격 증명 보호·사설 접근을 함께 갖추는 것

상태 검사와 인스턴스 상태

EC2가 인스턴스의 호스트(시스템)와 게스트 OS(인스턴스) 상태를 주기적으로 검사해 하드웨어·소프트웨어 결함 여부를 알려주는 상태 검사 기능.

→ 09-03 참조

#1문제 상황

인스턴스에 문제가 생겼을 때 사용자가 직접 로그인해 원인을 찾기 전까지는 장애 여부를 알기 어렵다. 하드웨어 결함인지, 게스트 OS 안의 문제인지, 연결된 볼륨 문제인지 구분되지 않으면 복구 방법도 정할 수 없다. 문제가 생기기 전에 미리 알림을 받지 못하면 애플리케이션이 이미 영향을 받은 뒤에야 상황을 인지하게 된다.

#2핵심 질문

인스턴스가 하드웨어·소프트웨어 수준에서 정상인지 주기적으로 자동 판별하고, 문제가 생기면 즉시 알 수 있게 하려면 어떻게 해야 하는가?

#3동작 예시

Amazon EC2는 시스템·인스턴스·연결된 EBS 상태 검사를 관리하며 모든 인스턴스에서 자동으로 실행한다. 검사는 매분 수행되어 통과 또는 실패 상태를 돌려주고, 모든 검사가 통과하면 인스턴스 전체 상태가 OK, 하나라도 실패하면 impaired가 된다. 애플리케이션 상태 검사는 선택(opt-in) 방식으로, 인스턴스에서 돌아가는 애플리케이션의 HTTP·HTTPS 응답을 직접 모니터링한다.

#4동작 과정

  1. 자동 검사 실행시스템·인스턴스·연결된 EBS 검사가 매분 자동 실행된다. 시스템 검사는 호스트(하드웨어) 상태를, 인스턴스 검사는 게스트 OS 상태를, EBS 검사는 연결된 볼륨 상태를 각각 살핀다.
  2. 결과 확인콘솔·AWS CLI·SDK에서 검사 결과를 본다. 통과·실패가 종합되어 인스턴스 전체 상태가 OK인지 impaired인지 표시되므로 원인 계층을 빠르게 좁힐 수 있다.
  3. 알림 구성상태 검사 알람을 만들어 실패 시 통보받고, 인스턴스 상태 변경 이벤트에 대한 알람도 함께 설정한다. 문제를 조기에 인지해 대응 시점을 앞당긴다.

#5한 줄 요약

시스템·인스턴스·EBS 상태를 매분 자동 검사해 인스턴스의 정상 여부를 계층별로 판별하고 알람으로 조기에 알려주는 것

예약 이벤트와 유지보수

AWS가 인스턴스에 대해 예고하는 재부팅·중지·종료·유지보수 같은 예정된 작업 일정을 미리 확인하고 대응하는 예약 이벤트.

#1문제 상황

AWS는 인프라 신뢰성과 성능을 유지하기 위해 인스턴스를 재부팅하거나 중지하거나 폐기(retire)하는 작업을 예약할 수 있다. 이런 작업은 자주 일어나지는 않지만, 사용자가 그 시점을 모른 채 지나가면 실행 중인 서비스가 갑자기 멈추거나 인스턴스가 사라질 수 있다.

기존에는 이런 예정된 작업을 사용자가 스스로 알 방법이 없어, AWS가 계정 이메일로 보내는 안내를 놓치면 대응 시점을 잃기 쉬웠다. 관리형 이벤트인 만큼 사용자가 직접 일정을 만들 수는 없고, 미리 확인하고 필요한 조치를 취하는 것만 가능하다.

#2핵심 질문

AWS가 예고한 재부팅·중지·폐기 같은 예정 작업을 미리 확인하고 원하는 시점에 대응하려면 어떻게 해야 하는가?

#3동작 예시

어느 인스턴스에 유지보수로 인한 재부팅 이벤트가 예약된다. AWS는 이벤트의 시작·종료 날짜 같은 세부 정보를 담아 계정에 연결된 이메일로 미리 알리고, 동시에 AWS Health 이벤트를 보낸다. 사용자는 콘솔이나 CLI로 예약된 이벤트 목록을 조회해 어떤 인스턴스가 언제 영향을 받는지 확인하고, 필요하면 재부팅 시점을 다른 시간대로 재조정(reschedule)할 수 있다.

#4동작 과정

  1. 이벤트 예약과 통지AWS가 인프라 유지보수를 위해 인스턴스의 재부팅·중지·폐기 일정을 예약하면, 시작·종료 날짜 같은 세부 정보를 계정 이메일로 미리 알리고 AWS Health 이벤트도 함께 보낸다. 그래서 사용자는 작업이 일어나기 전에 영향을 파악할 수 있다.
  2. 이벤트 조회와 태그 맞춤사용자는 콘솔이나 API로 자신의 인스턴스에 예약된 이벤트를 조회한다. 알림에 포함하거나 제거할 태그를 지정해 어떤 알림을 받을지 맞춤 설정할 수 있어, 관련 있는 이벤트만 골라 볼 수 있다.
  3. 재조정과 대응이벤트 유형에 따라 사용자가 작업 시점을 제어할 수 있다. 재부팅 등은 원하는 시간대로 재조정(reschedule)하거나 사용자 지정 이벤트 윈도(custom event window, 작업을 허용할 시간 구간)를 만들어, 서비스 영향이 적은 때로 옮긴다.

#5한 줄 요약

AWS가 예고한 재부팅·중지·폐기 같은 예정 작업을 미리 확인하고 시점을 조정해 서비스 중단을 통제하는 것

CloudWatch 지표와 알람

EC2가 CloudWatch로 내보내는 CPU·네트워크·디스크 등 지표를 수집·조회하고 임계값 알람으로 자동 대응하게 하는 모니터링.

#1문제 상황

인스턴스의 상태를 사람이 계속 눈으로 지켜볼 수는 없고, 문제가 터진 뒤에야 CPU나 네트워크가 한계에 도달한 것을 알게 되면 이미 늦다. EC2 콘솔이 보여주는 그래프만으로는 여러 인스턴스의 과거 추세를 비교하거나 임계값을 넘었을 때 자동으로 반응하게 만들기 어렵다.

이런 한계를 메우려면 원시 데이터를 모아 읽을 수 있는 지표로 가공하고, 값이 특정 수준을 넘으면 스스로 조치하게 하는 체계가 필요하다.

#2핵심 질문

인스턴스가 내보내는 지표를 수집해 임계값을 넘을 때 사람 개입 없이 자동으로 대응하게 하려면 어떻게 해야 하는가?

#3동작 예시

EC2 인스턴스의 CPU 사용률이 계속 올라 CPUUtilization 지표가 임계값을 넘는다. CloudWatch는 이 지표를 받아 알람을 울리고, 알람에 설정된 동작에 따라 그 인스턴스를 자동으로 중지·종료·재부팅하거나 복구(recover)한다. 사용자는 콘솔 그래프 대신 CloudWatch에서 같은 인스턴스의 지표를 조회하거나 여러 인스턴스의 통계를 모아 볼 수 있다.

#4동작 과정

  1. 지표 수집Amazon EC2가 CPU·네트워크·디스크 같은 원시 데이터를 CloudWatch로 내보내고, CloudWatch는 이를 읽을 수 있는 준실시간 지표로 가공한다. 기본적으로는 5분 주기로 전송되며, 인스턴스에서 상세 모니터링(detailed monitoring)을 켜면 1분 주기로 보낼 수 있다. 기록은 15개월간 보관되어 과거 이력을 조회할 수 있다.
  2. 통계 조회와 집계사용자는 특정 인스턴스의 지표 통계를 조회하거나, 여러 인스턴스·Auto Scaling 그룹·AMI 단위로 통계를 모아 비교한다. 콘솔의 모니터링 그래프로도 같은 데이터를 볼 수 있다.
  3. 알람 생성과 자동 동작지표에 임계값을 걸어 알람을 만들고, 조건이 충족되면 인스턴스를 중지·종료·재부팅·복구하는 식으로 자동 대응하게 연결한다. 그래서 사람이 지켜보지 않아도 이상 상황에 즉시 반응한다.

#5한 줄 요약

EC2가 내보내는 지표를 CloudWatch로 모아 임계값 알람과 자동 동작으로 인스턴스 이상에 대응하게 하는 것

자동화·감사·시간 동기화

EventBridge로 운영을 자동화하고 CloudTrail로 API 호출을 감사하며 Amazon Time Sync로 인스턴스 시계를 동기화하는 운영 작업.

#1문제 상황

여러 인스턴스를 손으로 관리하면 상태 변화에 즉시 반응하기 어렵고, 누가 어떤 API를 호출했는지 추적할 수 없으며, 인스턴스마다 시계가 어긋나 로그의 시간 순서가 뒤섞인다. AWS는 모니터링을 위해 상태 점검, CloudWatch 등 여러 도구를 제공하지만, 자동화·감사·시간 동기화는 각각 따로 챙겨야 하는 운영 작업이다.

이 세 가지를 갖추지 않으면 장애가 여러 지점에서 겹쳤을 때 원인을 좁히기 어렵고, 사후 감사도 불가능하다.

#2핵심 질문

운영 이벤트를 자동으로 처리하고, API 호출을 감사하며, 모든 인스턴스의 시계를 맞추려면 어떻게 해야 하는가?

#3동작 예시

인스턴스 상태가 바뀌는 이벤트가 발생하면 EventBridge가 이를 감지해 미리 정한 규칙에 따라 자동 작업을 실행한다. 같은 시각에 누군가 EC2 API를 호출하면 CloudTrail이 그 호출 기록을 남긴다. 그리고 각 인스턴스는 Amazon Time Sync Service에 연결해 시계를 동기화하므로, 여러 인스턴스의 로그 타임스탬프를 나란히 비교할 수 있다.

#4동작 과정

  1. 이벤트 자동화EventBridge가 EC2 상태 변화 같은 운영 이벤트를 받아 규칙에 따라 자동 작업을 실행한다. 그래서 사람이 매번 개입하지 않아도 정해진 반응이 일어난다.
  2. API 호출 감사CloudTrail이 계정에서 이루어진 API 호출을 기록으로 남긴다. 누가 언제 무엇을 호출했는지 추적할 수 있어 문제 원인 분석과 감사에 쓰인다.
  3. 시계 동기화인스턴스가 Amazon Time Sync Service(로컬 또는 퍼블릭 엔드포인트)를 통해 시각을 맞춘다. Linux 인스턴스에서는 타임스탬프를 비교할 수 있고 시간대도 바꿀 수 있어, 여러 인스턴스의 로그를 일관된 시간 기준으로 볼 수 있다.

EC2 Capacity Manager

계정과 조직 전반의 EC2 용량 사용량과 여유 용량을 한곳에서 조회하고 분석·내보내기 하는 용량 관리 도구.

#1문제 상황

대규모 조직이나 여러 계정을 쓰는 환경에서는 On-Demand, Spot, Capacity Reservations에 걸친 용량 사용량을 파악하려면 여러 소스에서 데이터를 손으로 모아야 한다. 계정마다 따로 보면 전체 여유 용량과 최적화 기회를 한눈에 볼 수 없고, 어느 리전에서 용량이 부족한지도 놓치기 쉽다.

이런 수작업 수집은 시간이 많이 들고 최신 상태를 반영하지 못해, 용량 관리 판단이 늦어진다.

#2핵심 질문

여러 계정과 리전에 흩어진 EC2 용량 사용량과 여유 용량을 한곳에서 파악하고 관리하려면 어떻게 해야 하는가?

#3동작 예시

Capacity Manager를 활성화하면 대시보드 하나에서 On-Demand, Spot, Capacity Reservations의 사용량이 매시간 갱신되어 모인다. AWS Organizations 연동을 켜면 조직의 모든 멤버 계정 용량 데이터를 단일 대시보드에서 리전별로 파고들어 조회하고, 상세 지표를 확인해 최적화 조치를 바로 취할 수 있다. 연동이 없으면 활성화한 개별 계정의 리소스만 모니터링한다.

#4동작 과정

  1. 활성화와 범위 설정Capacity Manager는 하나의 리전에서만 활성화할 수 있다. 조직 단위로 켜거나 계정 단위로 켤 수 있고, 조직 단위에서는 위임된 관리자(delegated administrator)를 등록하고 서비스 연결 역할(service-linked role, 서비스가 대신 쓰는 권한 역할)을 사용한다. 연동 여부에 따라 모니터링 범위가 조직 전체인지 단일 계정인지가 달라진다.
  2. 데이터 수집과 그룹화계정과 리전 전반의 용량 지표가 대시보드에 매시간 갱신되어 모인다. 사용자는 데이터를 태그 키 단위로 그룹화·필터링하고 모니터링할 태그 키를 관리해 원하는 기준으로 데이터를 정리한다.
  3. 조회와 내보내기콘솔에서 리전별로 상세 지표를 파고들어 최적화 기회를 찾는다. 데이터를 외부로 내보내려면 Amazon S3 버킷을 준비하고 데이터 내보내기를 생성해, 수집한 용량 정보를 파일로 꺼낼 수 있다.

시작·중지·종료 문제

인스턴스가 시작(launch)되지 않거나 중지(stop)·종료(terminate)가 실패할 때 확인해야 할 원인과 해결 절차를 정리한 문제 해결 항목.

#1문제 상황

인스턴스는 시작(launch)부터 중지(stop), 종료(terminate)까지 각 단계마다 실패할 수 있다. 시작이 안 되면 서비스를 올릴 수 없고, 중지가 안 되면 과금이 계속되며, 종료가 안 되면 자원이 남는다. 하지만 실패 원인이 권한·용량·설정 등 여러 곳에 흩어져 있어 어디부터 봐야 할지 막막하다.

AWS는 인스턴스 문제를 유형별로 정리한 문제 해결 절차를 제공하지만, 시작·중지·종료라는 각 단계의 실패는 별도로 점검해야 한다.

#2핵심 질문

인스턴스가 시작되지 않거나 중지·종료가 실패할 때 어떤 원인을 어떤 순서로 확인해야 하는가?

#3동작 예시

인스턴스 시작 요청이 실패한다. 이때는 인스턴스 시작 문제 절차에 따라 원인을 좁힌다. 반대로 실행 중인 인스턴스를 중지하려는데 중지가 완료되지 않으면 인스턴스 중지 문제 절차를, 종료 요청이 실패하면 인스턴스 종료 문제 절차를 각각 확인한다. 시작·중지·종료 세 갈래로 나누어 해당 절차의 점검 항목을 하나씩 대조하는 방식이다.

#4동작 과정

  1. 단계 식별문제가 시작(launch)·중지(stop)·종료(terminate) 중 어느 단계에서 생겼는지 먼저 가른다. 세 단계는 원인과 확인 항목이 달라, 어느 단계인지에 따라 볼 절차가 정해진다.
  2. 해당 절차 점검식별한 단계에 맞는 문제 해결 절차(Instance launch issues / Instance stop issues / Instance termination issues)를 열어 점검 항목을 순서대로 대조한다. 각 절차는 그 단계에서 흔히 발생하는 원인과 확인 방법을 제시한다.
  3. 조치와 재시도점검으로 찾은 원인을 바로잡은 뒤 요청을 다시 시도한다. 그래서 시작은 서비스를 올리고, 중지는 과금을 멈추며, 종료는 자원을 정리하는 본래 목적을 달성한다.

접속·부팅 문제

SSH나 RDP로 인스턴스에 접속되지 않거나 정상 부팅되지 않아 도달 불가 상태가 되었을 때 점검할 항목과 대처 방법.

#1문제 상황

인스턴스가 실행 중인데도 SSH나 RDP로 접속되지 않거나, 정상적으로 부팅되지 않아 도달 불가(unreachable) 상태가 될 수 있다. 이때 인스턴스 안으로 들어갈 수 없으니 로그를 볼 수도 없어, 재부팅해야 하는지 아니면 다른 조치가 필요한지 판단하기 어렵다.

접속과 부팅 문제는 원인이 방화벽·상태 점검 실패·잘못된 볼륨·호스트 장애 등 다양해, 눈에 보이는 단서 없이는 원인을 좁히기 힘들다.

#2핵심 질문

인스턴스에 접속되지 않거나 부팅이 안 될 때 화면 정보로 원인을 어떻게 진단하고 복구하는가?

#3동작 예시

Windows 인스턴스에 RDP로 접속되지 않는다. 이때는 서비스가 반환하는 스크린샷을 캡처해 화면 상태를 확인한다. 스크린샷에 흔한 오류 화면이 나타나면 그에 맞는 점검 항목을 적용하고, 화면만으로 판단이 안 되면 콘솔 출력(console output)을 가져와 부팅 과정의 메시지를 본다. 이 정보로 재부팅이 필요한지, 다른 복구가 필요한지 정한다.

#4동작 과정

  1. 진단 정보 수집도달 불가 인스턴스에 대해 콘솔 출력을 가져오거나 스크린샷을 캡처해 부팅·화면 상태를 확인한다. 인스턴스 안에 들어가지 못해도 이 정보로 문제 양상을 파악할 수 있다.
  2. 증상별 점검증상에 맞는 항목을 확인한다. Linux는 SSH 문제, 상태 점검 실패, 잘못된 볼륨에서 부팅하는 경우를, Windows는 RDP 문제·시작 문제·커널 문제와 흔한 화면 이미지를 대조한다. 호스트 컴퓨터 장애로 인한 인스턴스 복구(recovery)나 예기치 않게 재부팅된 경우도 이때 함께 본다.
  3. 복구 조치진단 결과에 따라 재부팅하거나 인스턴스를 복구한다. 재부팅은 도달 불가 인스턴스에도 적용할 수 있는 기본 조치라, 문제 해결과 일반 관리 양쪽에 쓰인다.

Windows 인스턴스는 관리자 암호를 잊거나 Sysprep(이미지 배포용 초기화 도구) 과정에서 문제가 생기면 접속이나 부팅이 막힌다. 커널 문제, 방화벽·RDP·네트워크 인터페이스 설정, 중지 오류나 부팅 루프, 손상된 레지스트리처럼 원인도 다양해 인스턴스 안에서 직접 고치기 어렵다.

이런 경우 다른 인스턴스에서 EBS 루트 볼륨을 붙여 로그를 모으고 복구해야 하는데, 그 작업을 손으로 하면 번거롭고 위험하다.

#2핵심 질문

접속이 막힌 Windows 인스턴스의 암호·Sysprep·부팅 문제를 인스턴스 밖에서 진단하고 복구하려면 어떻게 해야 하는가?

#3동작 예시

EC2Rescue for Windows Server를 실행하면 방화벽·RDP·네트워크 인터페이스 설정 문제, 중지 오류나 부팅 루프, 손상된 레지스트리 같은 문제를 진단한다. 이 도구는 다른 인스턴스의 EBS 루트 볼륨을 검사해 그 볼륨을 쓰는 Windows 인스턴스의 로그를 모을 수도 있어, 접속이 안 되는 인스턴스를 밖에서 복구할 수 있다. 관리자 암호는 EC2Launch v2, EC2Launch, EC2Config 같은 도구로 재설정한다.

#4동작 과정

  1. 도구 실행EC2Rescue를 실행해 문제를 진단·수집한다. 데이터 수집 모듈로 로그를 모으고 문제 영역을 찾으며, GUI·CLI·Systems Manager 등 상황에 맞는 방식으로 돌린다. 필요하면 다른 인스턴스의 EBS 루트 볼륨을 붙여 검사한다.
  2. 증상별 복구연결 문제(방화벽·RDP·네트워크 인터페이스), 부팅 문제(중지 오류·부팅 루프·손상된 레지스트리), 고급 로그 분석이 필요한 문제를 유형에 맞게 처리한다. 관리자 암호는 인스턴스에서 쓰는 초기화 도구(EC2Launch v2 / EC2Launch / EC2Config)에 맞춰 재설정한다.
  3. 확인과 재접속복구를 마치면 인스턴스에 다시 접속해 문제가 해소됐는지 확인한다. 그래서 접속·부팅이 막힌 Windows 인스턴스를 원래 용도로 되돌린다.

#3동작 예시

네트워크 접속이 안 되는 인스턴스에 직렬 콘솔로 연결하면, 마치 키보드와 모니터를 인스턴스의 직렬 포트에 직접 연결한 것처럼 명령을 입력할 수 있다. 콘솔 세션은 인스턴스 재부팅·중지 중에도 유지되어, 재부팅 시 처음부터 나오는 부팅 메시지를 그대로 볼 수 있다.

#4동작 과정

  1. 접근 권한 설정직렬 콘솔 접근은 기본적으로 비활성화되어 있어, 계정 차원에서 접근을 허용하고 IAM 정책으로 사용자 접근을 부여한다. 인스턴스 ID·리소스 태그 등으로 세밀하게 제어할 수 있다.
  2. 연결인스턴스에 네트워크 기능이 없어도 직렬 포트로 세션을 열어 명령을 입력한다. 세션은 재부팅·중지 중에도 유지된다.

Fleet 개념과 구성 옵션

EC2 Fleet는 온디맨드·스팟·예약 용량을 하나의 요청으로 원하는 총 용량만큼 대량 프로비저닝하는 기능으로, 시작 템플릿과 용량 목표·인스턴스 가중치·할당 전략 등의 옵션으로 구성된다.

#1문제 상황

인스턴스를 여러 대 띄울 때 기존에는 한 번에 하나씩 생성 요청을 보내야 했다. 수십·수백 대가 되면 같은 작업을 반복해야 하고, 온디맨드·스팟·예약 용량을 섞어 비용을 관리하기도 어렵다. 특정 인스턴스 유형의 재고가 없으면 대량 배포 자체가 지연된다.

#2핵심 질문

여러 인스턴스 유형과 구매 옵션을 섞어 원하는 총 용량을 한 번의 요청으로 확보하려면 어떻게 해야 할까?

#3동작 예시

시작 템플릿 하나와 총 목표 용량을 지정해 플릿을 만들면, 플릿이 온디맨드로 확보할 양과 스팟으로 확보할 양을 나눠 인스턴스를 한꺼번에 띄운다. 예를 들어 목표 용량 100대에 온디맨드 20대를 지정하면, 플릿은 가용 용량이 있을 때 온디맨드를, 최대 가격이 스팟 가격을 넘고 용량이 있을 때 스팟을 채워 전체 목표를 맞춘다.

#4동작 과정

  1. 시작 템플릿 지정인스턴스 설정(AMI·인스턴스 유형 등)을 담은 시작 템플릿이나 수동 파라미터로 각 인스턴스의 구성을 정한다.
  2. 용량 목표·가중치 설정총 목표 용량, 온디맨드·스팟 비중, 인스턴스 가중치(인스턴스마다 다른 용량을 하나의 단위로 환산하는 값), 할당 전략을 정한다.
  3. 할당 전략 실행정한 전략에 따라 여러 인스턴스 유형·구매 옵션에 걸쳐 용량을 채운다. 특정 유형의 재고에 의존하지 않는다.

#2핵심 질문

플릿의 생성부터 삭제까지 상태 변화와 용량을 어떻게 한곳에서 관리하고 감시할까?

#3동작 예시

#4동작 과정

  1. 생성·태그총 목표 용량, 온디맨드·스팟 용량, 시작 템플릿을 포함한 요청으로 플릿을 만들고 요청·인스턴스·볼륨에 태그를 붙인다.
  2. 조회·수정·삭제플릿 요청과 그 안의 인스턴스 상태를 조회하고, 필요하면 요청을 수정하거나 삭제한다. 요청은 상태 변화를 거친다.
  3. 모니터링CloudWatch 지표와 EventBridge 이벤트로 플릿의 용량과 프로비저닝 진행을 감시한다.

Spot Fleet과 할당량

Spot Fleet은 스팟 인스턴스만으로 목표 용량을 유지하는 레거시 플릿 방식이며, 플릿 관련 요청 수·용량 등은 Fleet 할당량으로 제한된다.

#1문제 상황

스팟 인스턴스만으로 목표 용량을 유지하려는 요구가 있었다. 하지만 스팟 요청을 개별로 다루면 여러 유형·가용 영역에 걸친 용량 유지가 번거롭고 상태 관리도 어렵다. 다만 Spot Fleet은 레거시 API로 추가 투자가 계획되어 있지 않아, 관리가 필요하면 EC2 Fleet을 쓰는 것이 권장된다.

#2핵심 질문

스팟 인스턴스만으로 목표 용량을 유지하되 콘솔 지원이 필요할 때 어떤 방식을 써야 할까?

#3동작 예시

스팟 인스턴스의 총 목표 용량과 선택적인 온디맨드 비중을 담은 요청을 만들고, AMI·키 페어를 직접 지정하거나 인스턴스 구성을 담은 시작 템플릿을 지정해 플릿을 만든다. 플릿은 가용 용량이 있을 때 온디맨드를, 최대 가격이 스팟 가격을 넘고 용량이 있을 때 스팟을 띄운다.

#4동작 과정

  1. 요청 생성스팟 목표 용량과 선택적 온디맨드 비중, AMI·키 페어 또는 시작 템플릿을 지정해 플릿을 만든다.
  2. 조회·수정·취소플릿 요청과 인스턴스를 조회하고, 요청을 수정하거나 취소(삭제)한다.
  3. 자동 확장·할당량 관리대상 추적·단계·예약 조정으로 목표 용량을 조정하되, 플릿 관련 요청 수·용량은 Fleet 할당량으로 제한된다.

#1문제 상황

트래픽이 늘면 인스턴스가 부족해 응답이 느려지고, 줄면 놀고 있는 인스턴스가 비용을 낭비한다. 기존에는 사람이 수요를 보고 인스턴스를 직접 늘리거나 줄여야 했고, 이 작업이 늦으면 서비스가 불안정해진다. 최소한 유지해야 할 대수도 수동으로 지키기 어렵다.

#2핵심 질문

수요가 늘고 줄 때 인스턴스 수를 사람 손 없이 알맞게 맞추려면 어떻게 해야 할까?

#3동작 예시

Auto Scaling 그룹이라는 인스턴스 모음을 만들고 최소 대수를 정하면, 그룹이 그 아래로 내려가지 않도록 보장한다. 최대 대수도 정하면 그 위로 올라가지 않게 하고, 희망 용량을 정하면 항상 그 수만큼 인스턴스를 유지한다. 조정 정책을 정하면 수요 변화에 따라 인스턴스를 늘리거나 줄인다.

#4동작 과정

  1. 그룹 정의인스턴스 모음인 Auto Scaling 그룹을 만들고 최소·최대·희망 용량을 정한다.
  2. 조정 정책 설정수요가 늘고 줄 때 인스턴스를 늘리거나 줄이는 규칙을 정한다.
  3. 자동 유지그룹이 최소·최대 범위를 벗어나지 않도록 인스턴스 수를 자동으로 맞춘다.

Auto Scaling 그룹 생성과 관리

Auto Scaling 그룹은 최소·최대·희망 용량을 기준으로 동일한 설정의 인스턴스 집합을 유지하고 관리하는 논리적 단위다.

#1문제 상황

인스턴스를 개별로 만들면 최소·최대 대수를 지키기 어렵고, 설정이 제각각이 되어 관리가 힘들다. 수요가 변할 때 어떤 인스턴스를 늘리고 줄일지도 사람이 판단해야 했다. 동일한 설정의 인스턴스 집합을 하나의 단위로 다룰 방법이 필요했다.

#2핵심 질문

최소·최대·희망 용량을 기준으로 동일 설정의 인스턴스 집합을 어떻게 만들고 관리할까?

#3동작 예시

시작 템플릿을 만들어 두고 그 템플릿을 설정 원본으로 삼아 Auto Scaling 그룹을 생성하면, 그룹이 템플릿에 담긴 AMI ID·인스턴스 유형·키 페어·보안 그룹·블록 디바이스 매핑 정보로 인스턴스를 띄운다. 여러 인스턴스 유형과 구매 옵션을 섞으려면 혼합 인스턴스 그룹으로 만들고 할당 전략과 인스턴스 가중치를 정한다.

#4동작 과정

  1. 그룹 생성시작 템플릿(또는 시작 구성)을 설정 원본으로 지정해 Auto Scaling 그룹을 만든다.
  2. 혼합 구성여러 인스턴스 유형·구매 옵션을 쓰려면 속성 기반 또는 수동 선택으로 유형을 정하고 인스턴스 가중치를 적용한다.
  3. 갱신·삭제그룹을 갱신하거나 인프라를 삭제하며, 필요하면 리소스 삭제 보호를 켠다.

태그·유지보수 정책·라이프사이클 훅·웜 풀

그룹과 인스턴스에 태그를 붙이고, 교체·축소 시 동작을 정하는 유지보수 정책과 라이프사이클 훅, 미리 준비된 인스턴스를 두는 웜 풀 기능이다.

→ 12-03 참조

#1문제 상황

Auto Scaling 그룹은 인스턴스를 자동으로 늘리고 줄이며 관리하지만, 기존에는 그 안의 인스턴스가 어떤 목적·팀·환경에 속하는지 구분할 방법이 없었다. 그래서 비용을 어디에 배분해야 할지, 특정 목적의 그룹만 골라 보려면 어떻게 해야 할지 알기 어려웠다.

또 그룹이 인스턴스를 교체하거나 축소할 때 인스턴스를 곧바로 종료시켰기 때문에, 종료 직전에 로그를 남기거나 열려 있는 연결을 정리할 시간이 없었다. 확장할 때도 새 인스턴스가 부팅과 초기화를 끝낼 때까지 기다려야 해서, 갑자기 늘어난 요청이 느리게 처리됐다.

#2핵심 질문

자동으로 늘고 줄고 교체되는 인스턴스를 식별하고, 교체·축소 시점을 통제하고, 새 인스턴스가 뜨는 지연까지 줄이려면 어떻게 해야 하는가?

#3동작 예시

그룹에 라이프사이클 훅(lifecycle hook)을 걸어 두면 인스턴스가 종료되기 전에 pending:terminating 상태로 붙잡혀 대기한다. 그동안 Lambda 함수가 로그를 저장소에 올리거나 로드밸런서 대상 그룹에서 그 인스턴스를 빼는 작업을 하고, 끝나면 CompleteLifecycleAction을 호출해 종료를 진행시킨다. 여기에 웜 풀(warm pool)을 두면 미리 초기화해 둔 인스턴스가 대기하다가 용량이 필요할 때 곧바로 그룹에 들어온다.

#4동작 과정

  1. 태그 부여와 필터링그룹과 인스턴스에 키/값 태그를 붙이고, 그 태그로 그룹을 검색·필터링하며 비용 배분과 태그 접근 제어에 사용한다.
  2. 유지보수 정책 지정인스턴스 교체나 축소가 일어날 때 최소 몇 개의 정상 인스턴스를 유지할지, 어떤 순서로 종료할지를 정해 가용성을 지킨다.
  3. 라이프사이클 훅과 웜 풀 연결인스턴스 시작·종료 시점에 훅으로 필요한 작업을 끼워 넣고, 미리 준비된 인스턴스 풀을 두어 확장 지연을 줄인다.

#5한 줄 요약

이 기능들자동 확장 그룹이 인스턴스를 다루는 시점과 방법을 세밀하게 통제해 식별과 안전한 교체, 빠른 확장을 함께 가능하게 하는 것

인스턴스 교체와 인스턴스 리프레시

인스턴스 리프레시는 새 AMI나 시작 템플릿 버전으로 그룹 내 인스턴스를 점진적으로 교체해 무중단 배포를 돕는 기능이다.

#1문제 상황

새 AMI나 새 시작 템플릿 버전을 만들었다고 해도, 이미 그룹에서 돌고 있는 인스턴스는 예전 설정 그대로 남아 있다. 예전에는 인스턴스를 하나씩 수동으로 종료해 그룹이 새 설정으로 다시 띄우게 하거나, 그룹 자체를 지우고 다시 만들어야 했다.

이런 수동 교체는 서비스가 잠시 중단될 수 있고, 새 인스턴스의 상태를 확인하지 않은 채 밀어붙이면 실패를 뒤늦게야 알게 된다. 교체 도중 문제가 생겨도 이전 설정으로 되돌리기 어렵다는 점도 큰 부담이었다.

#2핵심 질문

새 설정으로 기존 인스턴스를 서비스 중단 없이, 상태를 확인하며 한 번에 교체하려면 어떻게 해야 하는가?

#3동작 예시

그룹에 새 시작 템플릿 버전을 지정하고 인스턴스 리프레시(instance refresh)를 시작하면, 그룹이 인스턴스를 일정 비율씩 나누어 새 설정으로 교체한다. minHealthyPercentage로 한 번에 몇 %까지 교체할지, instanceWarmup으로 새 인스턴스가 준비됐다고 볼 시간을 정한다. 체크포인트를 두면 특정 비율에 도달할 때마다 멈춰 상태를 검증할 수 있다.

#4동작 과정

  1. 리프레시 시작새 시작 템플릿이나 AMI를 그룹에 반영하고, 원하는 최종 설정과 교체 비율을 정해 리프레시를 시작한다.
  2. 점진 교체정한 비율만큼 새 인스턴스를 띄우고 상태 확인이 끝난 뒤에 기존 인스턴스를 종료해 가용 인스턴스 수를 유지한다.
  3. 검증과 되돌리기체크포인트와 bake time으로 상태를 확인하고, 문제가 있으면 롤백으로 이전 설정 인스턴스를 복원한다. skip matching은 이미 새 설정인 인스턴스를 건너뛴다.

#5한 줄 요약

인스턴스 리프레시새 설정을 그룹 전체에 무중단으로 점진 반영하고, 문제가 생기면 되돌릴 수 있게 하는 것

스케일링 방법과 정책

스케일링 정책은 CloudWatch 지표 등에 따라 그룹 용량을 자동으로 조정하는 규칙으로, 대상 추적·단계·단순·예약 등 방식이 있다.

#1문제 상황

트래픽은 시간대와 요일에 따라 변하는데, 서버를 고정 대수로 두면 피크에 맞춰 놓은 자원이 한산할 때 놀고, 평균에 맞추면 피크에서 요청이 밀린다. 사람이 직접 서버를 늘리고 줄이면 반응이 늦고 조작 실수도 생긴다.

게다가 늘리는 방법도 한 가지가 아니다. 평소에는 지표를 보고 자동으로 조정하고, 업무 시간처럼 예측 가능한 구간은 미리 늘려두는 등 상황에 맞는 방식을 골라야 한다.

#2핵심 질문

수요 변화에 맞춰 그룹 용량을 자동으로, 그리고 상황에 맞는 방식으로 조정하려면 어떻게 해야 하는가?

#3동작 예시

대상 추적(target tracking) 정책에서 "평균 CPU 사용률 50%를 유지하라"고 지정하면, 그룹이 CloudWatch 지표를 관찰하며 그 값을 유지하도록 인스턴스를 늘리거나 줄인다. 여기에 예약 스케일링(scheduled scaling)을 더해 매일 아침 9시에 용량을 올리고 저녁 6시에 내리는 규칙을 함께 둘 수 있다.

#4동작 과정

  1. 방법 선택수동, 예약, 동적(대상 추적·단계·단순) 중에서 수요 패턴에 맞는 방식을 고른다.
  2. 경계와 워밍업 설정최소·최대 용량을 정하고, 새 인스턴스가 지표에 반영되기까지의 기본 인스턴스 워밍업 시간을 지정한다.
  3. 정책 실행지표가 조건을 벗어나면 정책이 용량을 조정하고, 쿨다운으로 연속 조정을 잠시 멈춰 용량이 출렁이는 것을 막는다.

예측 스케일링과 종료 제어

예측 스케일링은 과거 지표로 미래 수요를 예측해 미리 용량을 준비하고, 종료 제어는 축소 시 어떤 인스턴스를 먼저 종료할지 정하는 설정이다.

→ 12-06 참조

#1문제 상황

대상 추적 같은 반응형 스케일링은 부하가 이미 올라간 뒤에야 용량을 늘린다. 애플리케이션이 초기화에 시간이 오래 걸리면, 새 인스턴스가 준비되는 동안 사용자가 지연을 겪는다.

축소할 때도 문제가 있다. 아무 인스턴스나 먼저 종료하면 아직 처리 중인 작업이 있는 인스턴스가 사라질 수 있어, 확장만큼 축소도 신중하게 다뤄야 한다.

#2핵심 질문

과거 패턴으로 미리 용량을 준비하고, 축소할 때는 안전한 인스턴스부터 종료하려면 어떻게 해야 하는가?

#3동작 예시

예측 스케일링(predictive scaling)은 축적된 부하 이력을 분석해 다음 날 오전처럼 반복되는 피크에 필요한 용량을 미리 계산해 그룹을 늘려둔다. 종료 제어 쪽에서는 OldestInstance나 NewestInstance 같은 종료 정책을 지정하거나, Lambda로 커스텀 종료 정책을 만들어 축소 순서를 직접 정한다.

#4동작 과정

  1. 과거 데이터 분석이력 지표에서 일간·주간 주기를 찾아 미래의 부하를 예측한다.
  2. 사전 확장예측된 피크가 오기 전에 미리 용량을 올려, 초기화에 걸리는 시간을 확보한다.
  3. 안전한 축소종료 정책과 스케일인 보호(scale-in protection)로 어떤 인스턴스를 먼저 없앨지 정해, 작업 중인 인스턴스를 지킨다.

모니터링과 다른 서비스 연동

CloudWatch 지표와 상태 검사로 그룹을 모니터링하고, Elastic Load Balancing·EventBridge·SNS 등 다른 서비스와 연동해 동작을 자동화한다.

#1문제 상황

그룹이 인스턴스를 자동으로 늘리고 줄여도, 그 안의 인스턴스가 실제로 요청을 잘 처리하는지, 언제 비정상 상태가 됐는지 알기 어렵다. 상태를 보려면 관리자가 직접 콘솔이나 API를 확인해야 한다.

또 그룹의 상태 변화를 다른 시스템이 알아야 할 때가 많은데, 이를 위해 외부에서 API를 주기적으로 조회하는 방식은 변화를 늦게 발견하고 불필요한 호출을 만든다.

#2핵심 질문

그룹과 인스턴스의 상태를 지표와 상태 검사로 파악하고, 그 변화를 다른 서비스로 자동 전달하려면 어떻게 해야 하는가?

#3동작 예시

그룹의 상태 검사 유형을 ELB로 지정하고 health check grace period를 두면, 새 인스턴스는 준비될 때까지 검사에서 제외됐다가 로드밸런서 헬스 체크에 실패하면 그룹이 그 인스턴스를 교체한다. 인스턴스 리프레시나 웜 풀 같은 사건은 EventBridge 규칙으로 잡아 SNS나 Lambda로 내보낼 수 있다.

#4동작 과정

  1. 상태 검사EC2·ELB·커스텀 검사로 인스턴스 건강을 판단하고, grace period로 초기화 시간을 준다.
  2. 지표와 로그 수집CloudWatch 지표와 그래프, Health Dashboard, CloudTrail API 로그로 그룹 상태를 관찰한다.
  3. 서비스 연동Elastic Load Balancing, EventBridge, SNS, Capacity Reservations 같은 대상과 연결해 상태 변화에 자동으로 대응한다.

#5한 줄 요약

이 연동그룹의 상태를 관찰 가능하게 만들고 그 변화를 다른 서비스로 흘려보내 자동 대응을 가능하게 하는 것

EC2 Auto Scaling — 수요에 맞춘 자동 확장12-09

보안·API·문제 해결

IAM 권한과 VPC 엔드포인트 등 보안 구성, API를 통한 제어, 인스턴스 시작 실패 등 흔한 문제의 해결 방법을 다룬다.

#1문제 상황

그룹이 인스턴스를 자동으로 만들고 없애려면 IAM 권한이 필요하다. 그런데 이 권한이 넓으면 원치 않는 인스턴스 생성이나 종료가 가능해지고, 어떤 시작 템플릿으로 인스턴스를 만들 수 있는지도 통제되지 않는다.

또 그룹을 API로 제어하거나 자동화하다 보면 호출이 실패하거나 인스턴스가 아예 시작되지 않는 상황을 만난다. 이때 원인이 권한인지, 할당량인지, 설정인지 구분하지 못하면 문제를 풀기 어렵다.

#2핵심 질문

그룹에 필요한 최소 권한을 안전하게 부여하고, API로 제어하며, 시작 실패 같은 문제를 진단하려면 어떻게 해야 하는가?

#3동작 예시

Auto Scaling은 서비스 연결 역할(AWSServiceRoleForAutoScaling)을 통해 사용자를 대신해 인스턴스를 시작·종료한다. IAM 정책에 조건을 넣어 특정 그룹이나 역할만 정해진 시작 템플릿을 쓰도록 제한하면, 다른 사람이 임의의 템플릿으로 인스턴스를 만드는 것을 막을 수 있다. 프라이빗 연결이 필요하면 VPC 엔드포인트를 사용한다.

#4동작 과정

  1. 권한 설정IAM 정책과 관리형 정책, 서비스 연결 역할로 그룹이 수행할 수 있는 작업과 쓸 수 있는 템플릿을 제한한다.
  2. API와 SDK 제어AttachInstances, CreateAutoScalingGroup 같은 작업을 API나 SDK로 호출해 그룹을 다룬다.
  3. 문제 진단시작 실패, 할당량 초과, 권한 오류를 활동 이력과 API 응답으로 확인해 원인을 좁힌다.

#5한 줄 요약

이 영역그룹이 인스턴스를 대신 다루는 권한을 안전하게 좁히고, API로 제어하며, 실패 원인을 추적할 수 있게 하는 것

리소스 관리와 할당량

Auto Scaling 그룹·시작 템플릿 등 리소스의 서비스 할당량과 관련 리소스를 확인하고 관리하는 방법이다.

#1문제 상황

그룹과 시작 템플릿이 늘어나면 어떤 리소스가 어디에 얼마나 있는지 파악하기 어려워진다. 목적별로 그룹을 골라 보고 싶어도 구분할 수단이 없으면 전체를 하나하나 확인해야 한다.

또 AWS 계정에는 리전별로 만들 수 있는 그룹과 시작 구성 수에 한도가 있다. 이 한도를 모르고 리소스를 만들다 보면 어느 순간 생성이 실패하고, 그제서야 한계에 부딪혔음을 알게 된다.

#2핵심 질문

그룹과 시작 템플릿 같은 리소스를 태그로 찾아 관리하고, 리전별 생성 한도를 확인해 넘지 않게 하려면 어떻게 해야 하는가?

#3동작 예시

리소스에 태그를 붙이고 그 태그로 필터링하면 특정 목적의 그룹만 골라 볼 수 있고, 인스턴스 메타데이터에서도 자기 태그를 읽을 수 있다. Service Quotas 콘솔에서 Amazon EC2 Auto Scaling을 선택하면 리전별 그룹·시작 구성 할당량과 사용량을 확인하고 필요하면 증액을 요청할 수 있다.

#4동작 과정

  1. 리소스 찾기그룹과 시작 템플릿 등을 콘솔이나 API로 조회해 현재 만들어 둔 리소스를 파악한다.
  2. 태그로 관리리소스에 태그를 붙이고 태그 권한을 정한 뒤, 태그로 필터링하고 인스턴스 메타데이터로도 읽는다.
  3. 할당량 확인과 증액Service Quotas에서 리전별 한도와 사용량을 확인하고, 필요하면 증액을 요청한다.

#5한 줄 요약

이 영역그룹 관련 리소스를 태그로 식별·관리하고 리전별 한도를 확인해, 운영이 예상치 못한 한계에 부딪히지 않게 하는 것
