Amazon Aurora

Amazon Aurora를 MySQL·PostgreSQL 호환 저장소 계층 위에 계산 인스턴스를 올린 관리형 관계형 데이터베이스로 해석했다. Aurora 를 RDS 와 구분하는 핵심은 DB cluster(계산 인스턴스 다수 + 3개 가용 영역에 걸친 cluster volume) 구조이고, 그 구조에서 파생되는 Aurora Replica·cluster endpoint·failover 가 이 책의 뼈대가 된다. 순서는 무엇이 Aurora 인가 → 클러스터와 endpoint 로 붙는가 → 읽기를 늘리는가 → 리전을 넘나드는가 → 용량이 불규칙할 때(serverless) → Aurora 인지 엔진별 기능(parallel query·Fast DDL·Babelfish·analytics) → 버전을 어떻게 바꾸는가 → 백업과 복구 → 안전과 관측 → 데이터를 옮겨오는가 로 잡았다. 엔진별 깊은 DBA 문서(wait event 30여 개, autovacuum 세부, stored procedure 레퍼런스)는 항목이 아니라 세부 참고 자료로 보고 excluded 에 사유를 적었다.

Amazon RDS 와 마찬가지로 관리형 관계형 데이터베이스이지만, 저장소를 여러 인스턴스가 공유하는 클러스터 구조라 저장소가 인스턴스 수와 무관하게 최대 3배까지만 늘어난다.

#1문제 상황

Amazon RDS 는 AWS 가 관리형으로 제공하는 관계형 데이터베이스 서비스다. 이 서비스로 만든 서버는 데이터 저장과 쿼리 처리를 한 서버가 같이 맡는다. 서버를 키우려면 데이터까지 옮겨야 하고, 저장소가 늘어날 때마다 손본다.

Amazon Aurora 는 관계형 데이터베이스를 관리형으로 제공하면서 저장과 계산을 분리한다. Aurora DB cluster 안의 인스턴스들이 하나의 cluster volume 을 공유하므로, 인스턴스를 여러 대 붙여도 저장소를 다시 만들지 않는다. 이 구성의 개념이 separation of compute capacity and storage 다.

#2핵심 질문

데이터 저장을 그대로 둔 채 읽기를 처리하는 서버만 따로 늘릴 수 있을까?

#3동작 예시

주문 애플리케이션이 주 노드에 접속해 주문을 넣는다. 같은 클러스터의 복제 노드들은 그 데이터를 그대로 따라 읽는다. 읽기 요청을 복제 노드로 보내도 저장소는 하나뿐이라 데이터가 어긋나지 않는다.

#4동작 과정

  1. 클러스터를 만든다Aurora DB cluster 하나로 저장소와 그 위에서 쿼리를 처리할 DB 인스턴스 묶음을 함께 만든다.
  2. 인스턴스를 붙인다쓰기를 받는 primary (writer) DB instance 하나에 읽기 전용 Aurora Replica 를 더한다. 계산과 저장이 분리되어 인스턴스 추가만으로 읽기 처리량을 늘릴 수 있고, MySQL·PostgreSQL 과 호환되는 엔진으로 기존 코드를 그대로 쓴다.
  3. 확인해 볼 것콘솔의 클러스터 목록에서 클러스터에 속한 인스턴스 이름과 writer 표시가 보이는지 본다.

Cluster volume — 세 개 가용 영역에 복사되는 저장소

Aurora 클러스터의 데이터를 담는 저장소로, 같은 리전의 가용 영역 세 곳에 사본이 유지되며 한 곳이 손상되어도 나머지 두 곳의 사본으로 계속 동작한다.

먼저 알아야 할 것 01-01

→ 01-06 참조

#1문제 상황

일반적인 데이터베이스는 데이터가 든 파일과 쿼리를 처리하는 서버가 한 곳에 있다. 디스크 하나가 나면 데이터 접근이 함께 끊긴다.

Amazon Aurora 의 cluster volume 은 파일별로 따로 관리하지 않는 하나의 가상 저장소다. 데이터는 storage node 라는 저장 장치 세 곳에 복사되고, 한 곳이 닫혀도 I/O freeze 없이 다른 사본으로 이어 쓸 수 있다. 이 여유분을 관리하는 것이 reliability 다.

#2핵심 질문

저장 장치 한 곳이 멈춰도 데이터는 계속 쓰고 읽을 수 있는가?

#3동작 예시

클러스터가 돌아가는 중 한 가용 영역의 저장 장치에 장애가 난다. 클러스터는 멈추지 않고 남은 두 곳의 사본으로 쓰기를 이어 간다. 여유분을 미리 갖고 있어서 복구가 끝날 때까지도 지연이 크게 늘지 않는다.

#4동작 과정

  1. 사본을 나눠 둔다클러스터 생성 시 데이터의 사본이 가용 영역 세 곳의 storage node 에 나뉘어 저장된다. 이 상태를 six copies 라고 부르고, 클러스터 볼륨 전체가 하나의 논리적 저장소로 보인다.
  2. 읽고 고친다I/O 가 들어오면 각 사본에 함께 반영되며, 한 storage node 가 응답하지 않으면 그 요청만 남은 사본으로 넘어간다. 읽은 페이지를 함께 보관하는 survivable page cache 로 반복 읽기를 빠르게 처리한다.
  3. 여유분을 남긴다볼륨 여유분을 미리 확보해 두어 세 사본이 모두 필요한 쓰기에서도 흔들림이 적다. 여유분 크기는 클러스터 설정에서 고른다.
  4. 확인해 볼 것콘솔의 클러스터 정보에서 클러스터 볼륨이 만들어진 리전과 할당된 볼륨 상태를 본다.

Writer 와 reader — 쓰기 하나에 읽기 여러 개

클러스터에서 쓰기를 받는 DB 인스턴스 하나를 writer, 읽기 전용으로 연결되는 여러 DB 인스턴스를 reader 라고 부르며, 클러스터 엔드포인트가 이 역할 분담을 자동으로 감당한다.

먼저 알아야 할 것 01-02

#1문제 상황

클러스터에 인스턴스가 여러 대(→ 01-02) 있어도 애플리케이션은 접속할 이름을 하나만 알고 있다. 그 이름이 매번 같은 인스턴스로 가면 읽기 부하가 한 대에 몰리고, 그 인스턴스가 멈추면 접속을 직접 고쳐야 한다.

Aurora 는 writer DB instance 하나가 쓰기를 모두 받고, 읽기 전용 reader DB instance 들이 쓰기를 따라가는 구조를 쓴다. 그 복제본이 Aurora Replica 다. 클러스터 엔드포인트가 이 분담을 자동으로 이어 준다.

#2핵심 질문

한 접속 이름으로 쓰기 노드와 읽기 노드를 어떻게 나눠 갈까?

#3동작 예시

애플리케이션이 클러스터 엔드포인트로 접속해 주문을 넣으면 writer 인스턴스가 처리한다. 같은 클러스터의 reader 엔드포인트로 붙은 조회 요청은 읽기 전용 복제본이 처리한다. writer 가 바뀔 때 애플리케이션 설정은 그대로 둔다.

#4동작 과정

  1. 역할을 정한다writer DB instance 가 데이터 정의·변경 문장을 모두 처리하고, Aurora Replica 는 읽기 전용으로 따라간다. 복제본이 주 인스턴스의 데이터를 얼마나 늦게 따라왔는지를 replica lag 로 본다.
  2. 이름을 건다클러스터 엔드포인트는 writer 로, reader 엔드포인트는 replica 풀로 연결을 보내 준다. replica 간 이동은 synchronous replication 로 데이터가 일치한 복제본만 후보로 삼아 처리한다.
  3. 확인해 볼 것콘솔에서 클러스터의 엔드포인트 목록에 클러스터용과 리디 용 이름이 따로 있는지 본다.

가용성의 두 층 — 데이터의 가용성과 인스턴스의 가용성

Aurora의 가용성은 저장소를 여러 가용 영역에 복사해 데이터를 지키는 층과, reader 인스턴스를 여러 리전에 걸어 인스턴스 장애를 견디는 층으로 나뉜다.

먼저 알아야 할 것 01-03

#1문제 상황

데이터를 지키는 것과 서버를 지키는 것은 별개 문제다. 데이터를 사본으로 복사해 두어도(→ 01-02) 모든 인스턴스가 한 인스턴스 장애로 함께 멈출 수 있고, 반대로 인스턴스를 늘려도 데이터 사본이 없는 곳은 복구할 수 없다.

Aurora 는 두 층을 따로 다룬다. 하나는 High availability 로 데이터 사본을 두는 층이고, 다른 하나는 fault tolerance 로 어떤 인스턴스든 대신 처리하게 만드는 층이다.

#2핵심 질문

데이터와 인스턴스 가운데 어느 쪽이 끊겨도 서비스가 계속되게 할까?

#3동작 예시

클러스터의 writer 인스턴스 한 대가 멈춘다. 데이터는 여러 가용 영역에 복사되어 있고 나머지 인스턴스들이 살아 있으므로, promotion tiers 순서에 따라 새 writer 로 승격된 인스턴스가 쓰기를 이어 받는다.

#4동작 과정

  1. 데이터를 지킨다DB cluster 안의 데이터를 여러 가용 영역에 복사해 두고, 어떤 failure event 가 나도 데이터는 남는다. Multi-AZ DB cluster 로 지정하면 이 구성을 처음부터 요구할 수 있다.
  2. 인스턴스를 갈아탄다failover 가 일어나면 promotion tiers 가 정한 우선순위와 failover priority 를 보고 다음 인스턴스를 승격해 요청을 받게 한다.
  3. 확인해 볼 것콘솔의 클러스터 이벤트 목록에서 승격이 일어난 시각을 확인할 수 있는지 본다.

Aurora 버전 체계 — major version 2 와 3 은 어떻게 구분되나

Aurora의 버전은 덩어리 단위 변경이 일어난 major version 과 개별 기능 개선이 들어가는 minor version 으로 구분되며, 어떤 MySQL·PostgreSQL 버전과 호환되는지가 major version 에 대응한다.

먼저 알아야 할 것 01-01

#1문제 상황

같은 MySQL 라도 엔진 버전에 따라 쓸 수 있는 기능과 설정값이 달라진다. Aurora 의 버전 번호는 Community 버전 번호와 달라 보여서 무엇이 호환되는지 알기 어렵다.

Aurora versioning 규칙은 이를 정해 둔다. 어떤 Community DB 버전과 대응하는지가 major version 로 잡히고, 그 안의 개선은 minor version 으로 올라간다.

#2핵심 질문

내 클러스터가 어떤 DB 버전과 맞는지 번호만 보고 알 수 있는가?

#3동작 예시

Aurora MySQL 클러스터에 접속해 버전을 확인한다. version 함수는 대응하는 Community MySQL 버전을, aurora_version 함수는 Aurora 자체 버전을 돌려준다. 두 값을 나란히 놓고 major version 을 가늠한다.

#4동작 과정

  1. major version 을 읽는다major version 은 호환되는 Community DB 버전과 대응한다. 엔진 버전이 바뀌면 파라미터 이름이 사라지거나 기능이 달라질 수 있다.
  2. minor version 을 읽는다minor version 은 major 안에서 들어온 개별 개선을 가리킨다. 상위 지원 여부는 Aurora version support 가 관리한다.
  3. 긴 기간 돌리기정규 지원이 끝난 버전도 long-term support 를 신청해 검사와 패치를 이어 받을 수 있다.
  4. 확인해 볼 것클러스터에 접속해 버전을 알려 주는 함수를 실행해 표시된 Aurora engine version 을 확인한다.

리전과 가용 영역 — 클러스터가 앉는 자리

리전은 AWS의 독립된 데이터센터 묶음, 가용 영역은 같은 리전 안에서 서로 분리된 독립 데이터센터 단위이며, Aurora는 한 리전의 가용 영역 세 곳에 클러스터 저장소를 두어 한 곳의 장애를 견딘다.

먼저 알아야 할 것 01-02

#1문제 상황

클러스터 저장소는 가용 영역 세 곳에 복사된다(→ 01-02). 그런데 그 세 곳이 서로 분리된 위치이 아니라면 한 번의 장애로 사본이 함께 사라진다. 또 리전 안에서만 동작하는 기능과 어디서나 되는 기능이 섞여 있어 선택이 어렵다.

#2핵심 질문

클러스터를 어느 위치에 두고 어떤 기능이 어디서 되는지 어떻게 아는가?

#3동작 예시

같은 리전 안의 가용 영역 세 곳에 클러스터를 만들고 instances 를 나누어 배치한다. 한 위치에 문제가 생겨도 나머지 위치의 사본으로 계속 동작한다. Local Zones 같은 추가 위치는 엔진과 리전에 따라 지원 여부가 갈린다.

#4동작 과정

  1. 리전을 고른다AWS Region 은 완전히 독립된 지리 영역이며, Aurora 작업은 고른 리전 안에서만 수행된다. 리전마다 Aurora 클러스터 볼륨의 할당 단위가 다르다.
  2. 가용 영역을 알린다Availability Zone 은 리전 안에서 서로 격리된 여러 위치다. 어떤 기능이 어떤 리전과 엔진에서 되는지 미리 확인하고 고른다.
  3. 인스턴스 크기를 본다같은 리전 안에서도 DB instance class types 나 리전 전용 옵션의 지원 범위가 다르다. Local Zones 는 리전 가까이 두는 소형 위치다.
  4. 확인해 볼 것콘솔에서 클러스터의 리전과 각 인스턴스가 놓인 가용 영역 번호를 본다.

VPC 와 보안 그룹으로 클러스터 감싸기

Aurora 클러스터를 Amazon VPC 라는 자체 네트워크 안에 배치하고, 어떤 주소·포트에서 들어오는 연결만 허용하는 보안 그룹 규칙으로 외부 접근 범위를 정하는 것.

먼저 알아야 할 것 02-01

#1문제 상황

데이터베이스를 만든다고 해서 어디서나 붙을 수 있는 것은 아니다. 클라우드 안에서 클러스터가 자리 잡을 네트워크와, 그 안으로 들어올 수 있는 연결의 범위를 직접 정해야 한다.

Aurora 는 모든 새 클러스터를 기본 VPC 안에 만든다. VPC 는 IP 대역·서브넷·라우팅·접근 제어 목록을 직접 고를 수 있는 네트워크 환경이다(→ 01-06). 여기에 DB subnet group 과 security group 을 붙이면 클러스터가 앉을 자리와 들어오는 길이 정해진다.

#2핵심 질문

Aurora 클러스터를 어떤 네트워크 안에 두고, 어떤 연결만 허용할까?

#3동작 예시

주문 서비스의 DB 클러스터를 사설 서브넷에 만든다. 보안 그룹에서 애플리케이션 서버의 주소와 클라이언트 포트만 허용한다.

같은 VPC 안의 다른 서버에서 telnet 으로 클러스터 포트에 붙여 보면 연결이 막혀 있다.

#4동작 과정

  1. 네트워크를 고른다클러스터를 만들 VPC 를 정하고 그 안에서 서브넷을 나눈다. VPC 계층에서 이미 생성된 클러스터는 나중에 옮길 수 없다.
  2. 서브넷 묶음을 지정한다DB subnet group 은 클러스터 인스턴스가 놓일 서브넷 목록이다. Aurora 는 이 묶음으로 가용 영역 분산을 정한다(→ 01-06).
  3. 접근을 좁힌다security group 은 허용·차단 규칙을 담은 가상 방화벽이다. publicly accessible 을 켜지 않으면 private subnet 안에서만 클러스터에 닿는다.
  4. 확인해 볼 것클러스터 콘솔의 연결과 보안 화면에서 서브넷 그룹과 적용된 보안 그룹 이름을 확인한다.

Cluster endpoint — 어디로 붙을지 정하는 이름

클러스터 전체를 가리키는 DNS 이름으로, 쓰기가 가능한 주 노드로 자동 연결되며 장애 시 다른 노드로 넘어가게 해 애플리케이션이 접속 지점을 고치지 않게 해 주는 이름.

먼저 알아야 할 것 02-01

#1문제 상황

클러스터가 여러 인스턴스로 나뉘면 애플리케이션은 어디에 붙어야 하는지 매번 정해야 한다. 쓰기를 받는 인스턴스가 바뀌면 접속 문자열도 고쳐야 한다.

cluster endpoint 는 클러스터 전체를 가리키는 DNS 이름이다. 이 이름은 항상 현재 primary 인스턴스를 가리키고(→ 01-03), 그 인스턴스가 죽으면 Aurora 가 자동으로 새 primary 로 넘긴다. 그래서 애플리케이션은 접속 지점을 고치지 않는다.

#2핵심 질문

쓰기 노드가 바뀌어도 애플리케이션이 고치지 않고 계속 붙을 수 있는가?

#3동작 예시

애플리케이션은 설정에 cluster endpoint 주소 하나만 넣어 둔다. 새 클러스터에서 처음 데이터를 넣을 때도 이 주소로 연결한다.

primary 인스턴스 하나가 장애로 멈춰도 같은 주소로 계속 연결되고, 쓰기와 조회가 새로 선출된 인스턴스에서 처리된다.

#4동작 과정

  1. 이름을 만든다클러스터마다 cluster endpoint 가 하나 생긴다. 이 이름으로 insert·update·delete 같은 쓰기 작업과 read 조회를 모두 보낸다(→ 02-01).
  2. 연결을 받는다클라이언트는 이 DNS 이름을 그대로 써서 접속한다. 인스턴스를 직접 지정하지 않는다.
  3. 자동으로 넘긴다현재 primary 가 실패하면 Aurora 가 새 primary 로 failover 하고(→ 03-03), 이 이름은 그동안에도 연결 요청을 받는다.
  4. 확인해 볼 것콘솔의 클러스터 엔드포인트 화면에서 cluster endpoint 이름이 표시되는지 본다.

Reader endpoint 와 instance endpoint

reader endpoint 는 읽기 전용 복제 인스턴스들의 풀에, instance endpoint 는 특정 인스턴스 하나에 직접 붙는 이름으로 읽기와 쓰기를 각각 어디로 보낼지 고를 수 있게 해 준다.

먼저 알아야 할 것 02-03

→ 02-03 참조

#1문제 상황

조회만 하는 요청까지 쓰기 노드로 보내면(→ 02-03) 주 인스턴스의 부담이 커지고 전체 처리량이 줄어든다. 반대로 특정 인스턴스 하나만 보고 싶을 때도 늘 클러스터 전체로 붙을 수는 없다.

reader endpoint 는 읽기를 전용 복제 인스턴스들(→ 03-01) 사이에 나눠 보내고, instance endpoint 는 정해 둔 인스턴스 하나에만 직접 연결한다. 읽기와 쓰기를 어디로 보낼지 고를 수 있게 된다.

#2핵심 질문

읽기와 쓰기를 각각 어느 인스턴스로 보낼지 어떻게 고르는가?

#3동작 예시

목록 화면을 그리는 SELECT 질의를 애플리케이션의 읽기 설정에 넣는다. 그 설정의 주소는 reader endpoint 이다.

여러 복제본이 있는 클러스터에서는 연결 요청이 복제본들에 나뉘어 들어가고, 그 세션에서는 SELECT 같은 읽기 문장만 실행된다. replica 가 하나도 없으면 이 이름이 주 인스턴스로 연결된다.

#4동작 과정

  1. 읽기를 나눈다reader endpoint 가 각 연결 요청을 Aurora Replica 사이에서 load balance 한다. replica 수에 비례해 SELECT 동시 처리량이 늘어난다.
  2. 한 곳에 직접 붙는다특정 인스턴스에 diagnostic 처리를 몰아넣고 싶을 때는 instance endpoint 를 쓴다. 직접 붙으므로 쓰기도 가능하다.
  3. 대상을 좁힌다instance class 나 DB parameter group 이 같은 인스턴스만 한데 묶고 싶을 때는 custom endpoint 를 쓴다(→ 02-05). promotion tier 로 어느 인스턴스를 우선 붙일지도 정한다.
  4. 확인해 볼 것콘솔 엔드포인트 목록에서 reader endpoint 와 각 instance endpoint 가 따로 보이는지 확인한다.

→ 02-04 참조

#1문제 상황

읽기와 쓰기만 나눠 두면(→ 02-04) 용도가 세분화된 환경은 구분할 수 없다. 리포트를 돌릴 때 저사양 인스턴스로 보내고, 배치를 돌릴 때 다른 인스턴스로 보내려면 이름이 따로 있어야 한다.

custom endpoint 는 cluster endpoint 와 reader endpoint 처럼 읽기·쓰기 여부가 아니라 다른 기준으로 인스턴스를 묶는다. 클러스터마다 최대 다섯 개까지 만들 수 있다.

#2핵심 질문

같은 클러스터의 일부 인스턴스에만 연결을 보내는 이름을 어떻게 만드는가?

#3동작 예시

특정 AWS instance class 를 쓰는 인스턴스들만 골라 report-end 라는 custom endpoint 를 만든다. 사내 직원은 리포트 생성에 이 이름을 쓰고, 이 연결은 지정된 인스턴스 중 하나로 load balance 되어 들어간다.

이름을 만든 직후에는 연결이 없으므로, 인스턴스를 넣지 않으면 그 연결은 어떻게 처리되는지 Considerations for custom endpoints 항목에서 확인해야 한다.

#4동작 과정

  1. 묶음을 정한다이 이름이 가리킬 인스턴스들을 고른다. instance class 나 DB parameter group 같은 기준으로 나눌 수 있다.
  2. 역할을 정한다endpoint role 로 이 이름을 쓰기 전용으로 쓸지, 쓰기와 읽기 모두에 쓸지 지정한다. include the writer instance 를 켜면 주 인스턴스도 묶음에 넣는다.
  3. 연결을 나눈다이 이름으로 붙으면 Aurora 가 묶음 안에서 인스턴스를 하나 골라 연결을 처리한다.
  4. 확인해 볼 것콘솔에서 custom endpoint 목록에 만든 이름과 포함된 인스턴스가 보이는지 본다.

Aurora 클러스터의 동작을 정하는 설정값(이름-값 쌍) 묶음으로, 이를 골라 클러스터에 붙이면 시간 초과나 서버 수준 변수 같은 설정이 정해진다.

먼저 알아야 할 것 02-01

#1문제 상황

Aurora 는 여러 인스턴스가 저장소 하나를 함께 쓴다(→ 01-02). 그래서 데이터가 어떻게 배열될지 정하는 설정은 인스턴스마다 따로 두면 서로 어긋난다.

DB cluster parameter group 은 그런 설정값(parameters) 을 모아 두는 묶음이다. 이 묶음에는 engine defaults 로 들어 있는 기본값이 들어 있으며, 저장소 배치처럼 클러스터 전체에 하나만 있어야 하는 값이 여기에 속한다.

#2핵심 질문

클러스터 전체가 공유할 엔진 설정값을 어디에 모아 두고 바꾸는가?

#3동작 예시

클러스터를 만들 때 파라미터 그룹을 고른다. innodb_file_per_table 같은 저장소 배치 값이 이 그룹에서 온다. 시간을 기다리는 값을 바꾸려면 파라미터를 고쳐 새 그룹을 만들고 그 그룹을 클러스터에 붙인다.

인스턴스마다 달라도 되는 값, 예를 들어 메모리 버퍼 크기는 DB parameter group 이 따로 맡는다. AWS RDS 와 Aurora 양쪽에서 쓰는 컨테이너다.

#4동작 과정

  1. 그룹을 고른다클러스터에 적용할 DB cluster parameter group 을 지정한다. 엔진 기본값만 든 기본 그룹을 쓸 수도 있다.
  2. 값을 바꾼다parameters 중 바꿀 이름을 골라 새 값을 넣는다. static 과 dynamic 으로 나뉘어 언제 반영되는지가 다르다.
  3. 붙이거나 되돌린다resetting parameters 를 실행하면 그 그룹의 값을 기본값으로 되돌린다. 인스턴스 수준 파라미터는 DB parameter group 에 따로 둔다.
  4. 확인해 볼 것콘솔의 파라미터 그룹 화면에서 만든 그룹에 어떤 파라미터가 들어 있는지 확인한다.

Aurora Replica 추가하기

Aurora Replica 는 읽기 전용으로 쓰는 클러스터의 복제본 노드로, 클러스터에 최대 15개까지 추가할 수 있고 writer primary 의 데이터를 그대로 따라가면서 읽기 부하를 나눠 준다.

먼저 알아야 할 것 02-04

#1문제 상황

primary DB 인스턴스는 클러스터 저장소의 모든 데이터 변경을 수행한다(→ 01-03). 읽기 질의까지 다 여기에 몰리면 쓰기 처리량이 줄어든다.

Aurora Replica 는 primary 와 같은 저장소 볼륨에 연결되지만 읽기만 처리하는 인스턴스다. 여기에 읽기 부하를 내려 primary 가 데이터 변경에 몰두하게 만든다.

#2핵심 질문

primary 의 부담을 덜기 위해 읽기 전용 인스턴스를 어떻게 늘리는가?

#3동작 예시

읽기 처리량이 늘었다고 판단해 클러스터에 reader 인스턴스 하나를 추가한다. 생성한 인스턴스는 곧바로 읽기 전용으로 붙을 수 있고 reader endpoint 의 대상이 된다(→ 02-04).

클러스터에는 Aurora Replica 를 최대 15개까지 둘 수 있다.

#4동작 과정

  1. 추가한다Adding Aurora Replicas 를 따라 reader 인스턴스를 만든다. 콘솔에서 CreateDBInstance 를 실행해 크기와 파라미터 그룹을 고른다.
  2. 분산시킨다클러스터 가용성을 높이려면 primary 와 Replica 를 서로 다른 Availability Zones 에 나눠 배치한다(→ 01-06). Aurora serverless 클러스터에도 reader 인스턴스를 붙일 수 있다.
  3. 읽기를 돌린다Replica 는 같은 저장소를 따라가면서 read-only 문장만 처리한다. read scaling 이 실제로 일어나는 지점이다.
  4. 확인해 볼 것클러스터 콘솔의 인스턴스 목록에서 reader 인스턴스의 역할과 상태가 표시되는지 본다.

Auto Scaling 은 지정한 하나 이상의 지표(예: CPU 사용률)가 정해 둔 임계값을 넘었다가 내려갈 때마다 replica 를 자동으로 늘리고 줄여, 읽기 처리량에 맞춰 비용을 조절하게 해 주는 기능이다.

#1문제 상황

리더 인스턴스(→ 03-01) 수를 사람이 정하면, 갑자기 늘어난 읽기에는 버티지 못하고 조용한 시간엔 돈만 쓴다.

Aurora Auto Scaling 은 이 수를 자동으로 맞춘다. 정책에는 관리할 수 있는 최소·최대 replica 수가 들어 있고, 실제 부하는 Amazon CloudWatch 지표와 target 값으로 판단한다.

#2핵심 질문

#3동작 예시

#4동작 과정

  2. 범위를 정한다minimum and maximum replicas 로 관리 가능한 최소와 최대 reader 수를 정한다. target Aurora Replica count 는 목표 지표 값이다.

Failover — primary 가 바뀌는 순간

Failover 는 writer primary 인 DB 인스턴스에 장애가 생겼을 때 같은 가용 영역의 replica 가 자동으로 새 primary 로 승격되어 쓰기 작업을 계속 받게 하는 자동 전환 절차다.

먼저 알아야 할 것 01-04

→ 03-01 참조

#1문제 상황

Failover 는 클러스터에서 쓰기를 받는 writer primary 인 DB 인스턴스가 멈췄을 때 그 자리를 다른 인스턴스로 넘기는 절차다. Aurora 는 reader DB instance 를 새 primary 인스턴스로 승격해 Failing over an Aurora DB cluster 를 수행하고, reader 가 하나도 없을 때는 새 primary 인스턴스를 새로 만든다.

기존 방식으로는 primary 가 죽은 동안 쓰기가 전부 멈춘다. Failover 가 끝나면 writer primary 가 새로 정해져 쓰기가 이어진다.

#2핵심 질문

primary 인스턴스가 죽었을 때 쓰기 작업을 멈추지 않고 이어 갈 수 있을까?

#3동작 예시

주문 처리 중 writer primary 인 DB 인스턴스의 상태가 unhealthy 로 바뀐다. 같은 가용 영역의 reader 가 새 primary 로 승격되고, cluster endpoint 가 그 인스턴스로 넘어가 writes 를 계속 받는다.

읽기 전용이었던 reader endpoint 는 잠시 끊겼다가 승격된 primary 가 새 reader 로 다시 붙어 따라온다.

#4동작 과정

  1. 인스턴스를 고른다reader 가 있으면 그중 하나를 새 primary 로 승격하고 없으면 새 primary 인스턴스를 만든다. fast failover 로 동작할 때 보통 60초 안팎으로 서비스를 다시 받는다.
  2. 이름을 옮긴다cluster endpoint 가 쓰기 대상을 새 primary 로 바꾼다. 애플리케이션은 접속 이름을 그대로 두고 바뀐 primary 를 따라간다(→ 02-03).
  3. 직접 전환할 수도 있다계획된 점검 등에는 콘솔·CLI·RDS API 로 FailoverDBCluster 를 실행해 수동으로 전환한다.
  4. 확인해 볼 것RDS 콘솔의 클러스터 목록에서 Writer 표시가 어느 인스턴스로 옮겨갔는지 확인한다.

Read availability — failover 동안 읽기를 계속한다

Failover 가 일어나도 다른 replica 가 읽기 전용 writer 가 될 때까지 잠시 라우팅이 끊길 수 있어, 읽기 전용 클라이언트를 가용 영역마다 두는 분산 구조로 읽기 가능 시간을 확보하는 이야기다.

먼저 알아야 할 것 03-03

→ 03-03 참조

#1문제 상황

Failover 가 일어나면 reader 가 읽기 전용 writer 로 바뀔 때까지 라우팅이 잠시 끊긴다(→ 03-03). 그 사이 읽기 요청은 실패한다.

Read availability 는 이 공백을 줄인다. writer 인스턴스를 재시작할 때 각 가용 영역에서 읽기를 대신할 survivor replica 를 정해 두는 기능이다. rebooting an Aurora cluster 가 읽기를 계속 가능하게 한다.

#2핵심 질문

writer 인스턴스를 재시작해도 읽기 질의를 계속 처리할 수 있을까?

#3동작 예시

유지 보수를 위해 writer 인스턴스를 재시작한다. 각 가용 영역의 survivor page cache 를 가진 replica 가 읽기를 받아 넘겨 화면 조회 기능이 계속 돌아간다.

재시작이 끝나면 Aurora Replica 는 자동으로 재시작되지 않으므로, 나머지 reader 는 운영자가 순서를 정해 하나씩 재시작한다.

#4동작 과정

  1. 대신 읽을 replica 를 정한다writer 가 있을 때 읽기를 대신할 replica 를 가용 영역마다 지정한다. fast recovery after failover 로 쓰기 실패 뒤 읽기가 빨리 돌아온다.
  2. 재시작 중 읽기를 넘긴다writer 인스턴스를 재시작해도 reboot without read availability 가 아니라 지정된 replica 가 읽기 전용 연결을 이어 받는다.
  3. 나머지는 순서대로 돌린다Aurora Replicas don't restart automatically 이므로 운영자가 하나씩 재시작한다.
  4. 확인해 볼 것RDS 콘솔에서 각 reader 인스턴스의 상태가 읽기 가능으로 표시되는지 확인한다.

먼저 알아야 할 것 03-01

쓰기가 허용된 리전이 아닌 리전에서 실행한 쓰기 쿼리를 자동으로 최상위 리전 클러스터로 전달해 처리하고 결과를 돌려주는 기능.

#1문제 상황

Aurora Global Database는 여러 리전에 클러스터를 두지만(→ 04-01), 쓰기는 최상위 리전 하나에서만 가능하다(→ 04-02). 나머지 리전인 secondary cluster에서 곧바로 INSERT나 UPDATE를 보내면 읽기 전용 오류가 난다. 애플리케이션이 리전마다 다른 연결 문자열을 고르게 해야 했다.

write forwarding을 켜면 secondary cluster가 쓰기 문장을 primary cluster로 넘겨 처리한다. Aurora가 리전 사이 네트워크와 세션 정보를 알아서 전달한다.

#2핵심 질문

#3동작 예시

쓰기 뒤 같은 리전에서 그 주문을 읽으면 방금 넣은 값이 보인다. 데이터는 항상 primary에서 먼저 바뀌고 secondary로 복제된다.

#4동작 과정

  1. 쓰기 문장을 넘긴다read-only secondary가 받은 쓰기 SQL을 primary cluster로 전달한다. Aurora가 리전 간 연결과 세션·트랜잭션 맥락까지 함께 보내므로 애플리케이션은 넘긴 줄 모른다.
  2. primary에서 처리한다primary가 데이터를 바꾸고 커밋한 뒤 결과를 되돌려 준다. 이후 변경분이 다른 리전의 secondary로 복제된다.
  3. 확인해 볼 것secondary 클러스터의 상태에 write forwarding이 켜져 있는지, 그리고 headless 엔드포인트로 연결해 쓰기 문장이 처리되는지 콘솔에서 확인한다.

Local write forwarding — 같은 리전 안에서

한 리전에 여러 클러스터가 있을 때, 읽기 전용 복제본에 들어온 쓰기 쿼리를 같은 리전의 쓰기 클러스터로 넘겨 처리하는 기능으로 Global Database 의 write forwarding 과는 별개다.

먼저 알아야 할 것 04-04

→ 04-04 참조

#1문제 상황

Aurora Replica는 writer에게 비동기로 갱신 내용을 받는다(→ 03-01). 그래서 복제본에 바로 읽는 거래를 하면 방금 쓴 값을 못 볼 수 있다. 애플리케이션이 쓸 때마다 writer에 붙었다가 읽을 때 복제본으로 돌아가는 경로를 직접 짜야 했다(→ 04-04의 리전 간 위임과는 별개다).

local write forwarding을 켜면 복제본에서 읽기-쓰기 거래를 시작해도 그 거래가 writer로 전달돼 커밋된다. 애플리케이션은 어느 노드에 붙어 있는지 신경 쓰지 않는다.

#2핵심 질문

복제본에서 쓴 값을 같은 거래 안에서 바로 읽게 할 수 있을까?

#3동작 예시

애플리케이션이 Aurora Replica에 연결된 채 주문을 넣고 같은 거래에서 방금 넣은 주문을 다시 조회한다. 복제본이 거래를 writer DB instance로 넘겨 커밋하고 그 결과를 돌려주므로, 읽기 결과에 방금 쓴 값이 들어 있다.

#4동작 과정

  1. 거래를 넘긴다read/write 거래가 replica에서 시작되면 local write forwarding이 이를 writer로 전달한다. 읽기 전용 노드에서도 읽기-쓰기 거래를 그대로 건다.
  2. 커밋하고 되돌린다writer가 변경을 커밋한 결과를 복제본 연결로 돌려준다. 그래서 read consistency, 즉 쓰자마자 읽는 일관성이 확보된다.
  3. 확인해 볼 것클러스터에 local write forwarding이 활성화되어 있는지, 그리고 복제본에서 시작한 거래가 어느 노드에서 커밋됐는지 로그로 확인한다.

4. 리간을 넘어서 — Global Database와 write forwarding04-06

Global database 의 disaster recovery

한 리전이 통째로 죽을 때 다른 리전의 복제본을 최상위로 승격시켜 데이터베이스를 복구하고, 그 시점의 지연 시간(복구 시간 목표)을 다루는 절차.

먼저 알아야 할 것 04-03

#1문제 상황

단일 리전의 Aurora 클러스터는 가용 영역 세 곳 복사로 데이터와 인스턴스 장애를 견딘다(→ 01-02, 01-04). 하지만 리전 전체가 사라지는 수준의 사고는 그 범위를 넘는다. Global Database는 이런 리전 단위 사고에 대비한 business continuity and disaster recovery(BCDR) 보호를 한 단계 더 제공한다.

secondary cluster는 리전이 통째로 죽어도 남은 데이터로 새 최상위가 될 수 있다. 그 전환 시간만큼의 데이터 손실을 RPO로 관리한다.

#2핵심 질문

리전 전체가 끊겼을 때 다른 리전에서 데이터베이스를 어떻게 되살리나?

#3동작 예시

계획한 전환이 아니라 실제 리전 장애로 세 리전 클러스터가 모두 연결을 잃는다. 운영자가 남아 있는 파리 리전 secondary cluster를 switchover로 최상위 primary cluster로 올린다. 애플리케이션은 파리 리전의 쓰기 엔드포인트로 다시 붙어 작업을 이어 간다.

#4동작 과정

  1. 계획을 세운다Aurora Global Database로 언제 switchover를 부를지, 데이터 손실 허용 범위(RPO)를 어디로 잡을지 정한다. Aurora PostgreSQL은 RPO를 따로 관리하는 절차를 제공한다.
  2. 전환한다계획된 전환은 switchover, 계획되지 않은 정지에서의 전환은 failover 절차를 쓴다. secondary cluster를 새 최상위로 올리고 전역 엔드포인트가 그쪽을 가리키게 한다.
  3. 확인해 볼 것각 리전 클러스터의 상태와 secondary의 강등 여부를 콘솔에서 보고, 데이터베이스의 지연 시간이 허용 범위 안에 있는지 확인한다.

5. 불규칙한 부하 — Aurora serverless05-01

Aurora Serverless 가 무엇을 대신하는가

Aurora Serverless v2 는 미리 정해 둔 DB 인스턴스 크기나 리전당 용량 한도 대신 Aurora Capacity Unit(ACU) 상한만 지정해서, 워크로드의 필요량에 따라 저장소·버퍼·CPU 를 자동 조정한 과금 단위 구성 방식이다.

먼저 알아야 할 것 03-05

#1문제 상황

일반 Aurora는 DB 인스턴스 크기를 미리 골라 두기 때문에(→ 02-01), 부하가 몰리는 시간에는 모자라고 조용한 시간에는 돈을 쓴다. variable workloads, 즉 시간따라 들쭉날쭉한 트래픽에서는 사람이 수동으로 크기를 바꾸느라 밤새 큰 인스턴스를 띄워 두고 낭비를 막는 대신 자동 조정을 택한다.

Aurora serverless는 capacity를 필요량에 맞춰 자동 조절하고 사용한 만큼만 과금한다. 여러 테넌트를 함께 쓰는 구조와 개발·시험 환경에서 특히 유용하다.

#2핵심 질문

부하가 시간마다 달라질 때 인스턴스 크기를 사람이 정하지 않아도 되는가?

#3동작 예시

시험용 DB를 낮게 만들어 두었다가 밤새 배포 스크립트가 몰려 온다. Aurora serverless는 CPU와 메모리를 알아서 늘려 질의를 처리하고, 새벽에 부하가 가라앉으면 다시 줄인다.

#4동작 과정

  1. 상한을 정한다Aurora Capacity Unit(ACU) 단위의 최소·최대 범위를 지정한다. ACU는 저장소·버퍼·CPU를 함께 묶은 과금 단위다.
  2. 자동으로 맞춘다on-demand autoscaling이 워크로드 요구량에 따라 capacity를 늘리고 줄인다. 사용하지 않은 capacity에는 비용이 붙지 않는다.
  3. 확인해 볼 것콘솔의 용량 그래프에서 부하에 따라 ACU가 오르고 내려가는 것을 보고, 그 클러스터가 serverless 모드로 생성됐는지 확인한다.

5. 불규칙한 부하 — Aurora serverless05-02

ACU 단위 확장과 자동 일시정지

Aurora Serverless v2 는 설정한 최소·최대 ACU 범위 안에서 CPU·메모리 확장을 자동 수행하고, 0 ACU 로 강등되면 일시 정지(auto pause)되어 activity 가 다시 들어오면 재개된다.

먼저 알아야 할 것 05-01

#1문제 상황

Aurora serverless가 capacity를 자동으로 맞추더라도(→ 05-01), 아무도 붙지 않는 개발용 클러스터는 최소 ACU 값만큼 계속 켜져 있다. 완전히 잠든 시간에도 capacity 비용이 쌓인다.

auto-pause를 켜면 클러스터가 0 ACU까지 내려가 멈추고, activity가 다시 들어오면 재개된다. 멈춰 있는 동안에는 인스턴스 capacity에 대한 과금이 없다.

#2핵심 질문

한참 쓰이지 않는 클러스터를 어떻게 꺼 두어 비용을 아낄까?

#3동작 예시

주말 내내 아무도 붙지 않는 시험용 클러스터가 정해진 시간 동안 연결을 받지 못한다. 클러스터는 0 ACU로 강등되어 자동 일시정지(auto pause) 상태가 되고, 월요일 첫 연결에 곧바로 재개된다.

#4동작 과정

  1. 최솟값을 0으로 둔다클러스터의 minimum ACU를 0으로 지정하고 auto-pause를 켠다. scaling to 0 ACUs가 이 기준이다.
  2. 멈추고 다시 일어난다사용자가 만든 연결이 정해진 시간 동안 없으면 일시정지하고, 다음 activity가 들어오면 자동 재개한다. 멈춘 동안에는 인스턴스 capacity 과금이 없다.
  3. 확인해 볼 것콘솔에서 클러스터가 paused 상태로 바뀌었다가 다시 resumed 되는 것을 보고, 그 사이에 용량 그래프가 0에 머물렀는지 확인한다.

5. 불규칙한 부하 — Aurora serverless05-03

Serverless 클러스터 만들고 관리하기

Serverless v2 클러스터는 콘솔·CLI·API 로 엔진 버전과 최소/최대 ACU 를 지정해 생성하고, 이후 capacity range 변경·모니터링·모드 전환 같은 관리 동작을 같은 콘솔 경로에서 수행하는 절차를 다룬다.

먼저 알아야 할 것 05-01

#1문제 상황

DB 인스턴스 크기를 미리 정해 두지 않는 구성, 즉 Aurora Serverless 는 필요량에 따라 ACU 로 용량을 자동으로 정한다(→ 05-01). 그래서 provisioned writer 와 reader 를 그대로 두고 일부 인스턴스만 serverless 로 바꿀 수 있다.

Creating an Aurora serverless DB cluster 는 엔진 버전과 최소·최대 ACU 를 지정해 이 구성을 처음 만드는 작업이다. 이후 Managing Aurora serverless 로 capacity range 를 바꾸고 상태를 본다.

#2핵심 질문

Aurora Serverless 클러스터를 만들고 용량 범위를 어떻게 관리하는가?

#3동작 예시

트래픽이 불규칙한 서비스라 인스턴스 크기를 정하기 어렵다. 콘솔에서 엔진 버전과 최소·최대 ACU 를 골라 클러스터를 만든다.

클러스터 안에는 serverless reader 인스턴스가 붙고, 기존 provisioned writer 는 그대로 남는다. 이후 최소 ACU 를 올려 기준 용량을 넓힌다.

#4동작 과정

  1. 클러스터를 만든다Creating an Aurora serverless DB cluster 로 리전과 DB engine version, capacity range 를 정한다. 서버리스 인스턴스가 제공되는 리전과 호환되는 엔진 버전을 골라야 한다.
  2. 인스턴스를 붙인다converting a provisioned writer or reader 로 기존 provisioned 인스턴스를 serverless 인스턴스로 바꾼다. 같은 클러스터 안에 serverless 와 provisioned 인스턴스가 섞여 있어도 무방하다.
  3. 범위를 조절한다Managing Aurora serverless 에서 capacity range 를 바꾸고 상태를 확인한다.
  4. 확인해 볼 것RDS 콘솔의 클러스터 화면에서 DB 인스턴스 목록에 serverless 인스턴스가 따로 보이는지 확인한다.

5. 불규칙한 부하 — Aurora serverless05-04

Limitless Database — Postgres 테이블을 쪼개 늘린다

Limitless Database 는 하나의 논리 Postgres 데이터베이스를 여러 개 물리 shard 로 나누어 저장·병렬 처리하는 구조로, 단일 writer 범위를 넘고자 할 때 Aurora PostgreSQL 에서 쓰는 기능이다.

먼저 알아야 할 것 05-01

#1문제 상황

Aurora PostgreSQL은 클러스터당 writer 하나라(→ 01-03), 데이터가 커지면 하나의 인스턴스가 감당하는 쓰기 양을 넘어서기 쉽다. 이를 피하려면 여러 DB 인스턴스에 데이터를 나눠 담고 나눠 조회하는 구조를 애플리케이션 쪽에서 직접 짜야 했다.

Aurora PostgreSQL Limitless Database는 그 구조를 데이터베이스가 대신한다. 하나의 논리 데이터베이스를 여러 물리 shard로 쪼개 저장하고 병렬로 처리한다.

#2핵심 질문

단일 writer가 감당하지 못할 데이터를 어떻게 한 논리 데이터베이스로 다룰까?

#3동작 예시

측정 데이터 테이블이 수십억 행으로 자란 회사가 Limitless Database를 만든다. 테이블을 만들면 지정한 크기의 shard로 자동 분할되고, 질의는 여러 shard에 나뉘어 병렬로 실행된 뒤 결과가 합쳐진다.

#4동작 과정

  1. DB shard group을 만든다shard group은 하나의 shard 집합을 묶는 단위다. Creating a DB cluster that uses Aurora PostgreSQL Limitless Database로 클러스터와 shard group을 준비한다.
  2. 테이블을 쪼갠다Working with DB shard groups에서 테이블을 정해진 크기의 shard로 나누고, Loading data into Aurora PostgreSQL Limitless Database로 데이터를 넣는다.
  3. 질의를 나란히 돌린다Querying Aurora PostgreSQL Limitless Database에서 한 질의가 여러 shard에 나뉘어 실행된다. 각 shard는 물리 DB 인스턴스 하나에 해당한다.
  4. 확인해 볼 것콘솔에서 shard group에 속한 shard 목록과 shard별 크기가 어떻게 표시되는지 확인한다.

5. 불규칙한 부하 — Aurora serverless05-05

Limitless 의 shard 분할과 운영

Limitless 에서 shard group 은 고정 크기 shard 로 나눠지는 파티셔닝을 적용하고, shard 추가·모니터링·관리 동작으로 데이터 분포와 성능을 다루는 절차를 설명한다.

먼저 알아야 할 것 05-04

#1문제 상황

Limitless Database 가 데이터를 물리 shard 로 나눠 담으면(→ 05-04), 한 shard 가 커지거나 사용량이 몰리면 그 shard 만 느려진다. 이미 들어간 데이터를 옮기면서 크기를 줄이는 작업이 필요하다.

Limitless 는 splitting a shard 로 기존 shard 의 데이터를 새 shard 여러 개로 나눠 옮긴다. 사람이 시킬 수도 있고, 데이터가 지나치게 크거나 사용량이 지나치게 높으면 시스템이 스스로 나눈다.

#2핵심 질문

한 shard 에 데이터가 몰렸을 때 이를 어떻게 나눌까?

#3동작 예시

주문 테이블이 들어 있는 shard group 의 데이터가 지나치게 커졌다. DBA 가 해당 shard 를 분할한다.

분할이 끝나면 요청이 여러 shard 로 나뉘고, 각 shard 의 사용량이 고르게 낮아진다. 분할 진행 상황과 지연 시간은 Monitoring Limitless Database 화면에서 함께 본다.

#4동작 과정

  1. shard 를 나눈다splitting a shard 로 한 shard 의 데이터를 같은 크기의 새 shard 여러 개로 옮긴다. 이때 분할할 shard group 에 sharded table 이 하나 이상 있어야 하고, rds_aurora_limitless_cluster_admin 권한을 가진 사용자가 실행한다.
  2. shard group 을 더한다adding a DB shard group 으로 shard group 하나를 새로 만들어 shard 수를 늘린다. shard 당 저장 용량을 넘지 않게 이 단위로 나눈다.
  3. 살핀다Managing Limitless Database 로 설정과 shard 구성을 보고, Monitoring Limitless Database 로 shard별 사용량과 분할 상태를 확인한다.
  4. 확인해 볼 것콘솔의 Limitless Database 화면에서 shard 목록과 shard별 사용량이 어떻게 표시되는지 확인한다.

#5한 줄 요약

Limitless 의 shard 분할과 운영은 한 shard 에 몰린 데이터를 여러 shard 로 나눠 고르게 나누고 관리하는 것입니다.

먼저 알아야 할 것 02-06

#1문제 상황

애플리케이션이 Aurora 클러스터에 연결하려면 DB 연결을 유지하고 비밀번호를 들고 다녀야 한다. 짧게 끝나는 일 하나를 위해 서버를 띄우고 연결을 관리하는 비용이 든다.

Amazon RDS Data API 는 클러스터에 persistent connection 을 두지 않는다. 대신 안전한 HTTP 엔드포인트로 without an application server 질의를 보낸다. 서버 없이 곧바로 결과를 받는다.

#2핵심 질문

애플리케이션 서버 없이 클러스터에 SQL 질의를 어떻게 보내는가?

#3동작 예시

AWS Lambda 함수에서 Data API 를 호출해 고객 목록을 SELECT 한다. 함수는 클러스터 접속 정보를 설정하지 않는다.

요청에 Secrets Manager ARN 을 함께 실어 보내고, 결과가 JSON 으로 함수에 돌아온다. Lambda 는 VPC 안의 자원에 대한 설정 없이도 클러스터를 읽는다.

#4동작 과정

  1. 자격 증명을 맡긴다DB 비밀번호를 AWS Secrets Manager 에 저장해 둔다. 호출자는 그 비밀번호 대신 Secrets Manager ARN 을 보내고, 권한이 있는 사용자만 Data API 와 Secrets Manager 를 쓸 수 있다.
  2. 한 문장을 보낸다execute statement 로 SQL 문 하나를 보낸다. 여러 문을 한 번에 보내려면 batch execute statement 를 쓴다.
  3. 결과를 받는다호출은 HTTP 응답으로 돌아오며 DB 연결을 따로 닫을 필요가 없다. AWS SDK 로 Lambda·AppSync 같은 다른 AWS 서비스에서 바로 불러 쓸 수 있다.
  4. 확인해 볼 것콘솔의 Data API 화면에서 클러스터에 대한 권한과 엔드포인트가 어떤 이름으로 보이는지 확인한다.

Parallel query — 한 질의를 여러 코어로

Aurora MySQL 이 여러 대의 CPU 코어를 한꺼번에 빌려 SELECT 같은 읽기 질의를 나눠 동시에 처리해 결과를 훨씬 빨리 내주는 기능이다.

먼저 알아야 할 것 03-05

#1문제 상황

행이 수백만 개 있는 표를 대상으로 집계 질의를 걸면 한 코어가 순서대로 읽어 가야 해 시간이 오래 걸린다(→ 03-05). 보통 데이터는 이미 클러스터 공유 저장소에 흩어져 있다.

parallel query 는 공유 저장소 구조를 이용해 질의의 행 읽기와 계산을 여러 부분으로 나눈다. parallel query cluster 로 지정한 클러스터에서만 이 경로를 쓴다.

#2핵심 질문

수백만 행에 걸린 집계 질의를 어떻게 여러 코어로 나눠 처리하는가?

#3동작 예시

주문 표를 한 달 단위로 묶어 합계를 내는 질의를 몇 시간 동안 돌리던 서비스가 있다.

parallel query 를 켠 뒤 같은 질의를 실행한다. 화면에는 질의가 끝났다는 메시지만 짧은 시간 뒤 뜬다.

#4동작 과정

  1. cluster 로 지정한다parallel query DB cluster 를 만들어 이 최적화를 쓸 준비를 한다. 수백만 행 표와 분석성 질의가 있는 클러스터에서 효과가 크다.
  2. 켜고 끈다turning parallel query on and off 로 기능 사용 여부를 바꾼다. 일반 트랜잭션성 부하가 많은 클러스터에서는 꺼 두기도 한다.
  3. 질의를 다듬는다SQL constructs for parallel query 를 보고 어떤 문장 형태가 분할 대상이 되는지 확인한다. 조건문이나 조인 형태에 따라 대상 여부가 달라진다.
  4. 확인해 볼 것실행 기록에서 해당 SELECT 문이 parallel query 로 처리됐는지 나타나는지 확인한다.

Fast DDL — 표 구조를 거의 멈추지 않고 바꾼다

ALTER TABLE 로 표 구조를 바꿀 때 데이터베이스 전체를 멈추지 않고 짧은 시간 안에 끝내는 Aurora MySQL 의 스키마 변경 방식이다.

먼저 알아야 할 것 06-01

#1문제 상황

ALTER TABLE 로 표 구조를 바꾸면 일반 MySQL 은 표를 통째로 복사해 옮기느라 시간이 걸리고 그동안 다른 DML 이 막힌다(→ 06-01). 큰 표일수록 치명적이다.

Fast DDL 은 표 복사 없이 끝내고 임시 저장소도 쓰지 않는다. 다른 DML 문에 미치는 영향이 거의 없어 작은 인스턴스에서도 큰 표를 다룰 수 있게 된다.

#2핵심 질문

큰 표의 구조를 멈춤 없이 어떻게 빨리 바꾸는가?

#3동작 예시

운영 중인 주문 표에 열 하나를 추가해야 한다. 지난번에는 같은 작업이 몇 시간 걸렸다.

이번에는 Altering tables 로 열을 추가한다. 복사 로그 없이 짧은 시간 안에 문장이 끝난다.

#4동작 과정

  1. 바꿀 것을 고른다Fast DDL 대상은 열 추가·인덱스 생성 같은 작업이다. 문법 형태에 따라 걸리는 방식이 달라진다.
  2. 문을 실행한다Aurora MySQL version 3 에서는 ALGORITHM=INSTANT 를 붙인 instant DDL 로 처리한다. version 2 에서는 별도의 구현인 Fast DDL 이 동작한다.
  3. 부담을 확인한다metadata operations 이 만들어지는 동안 걸리는 부하를 본다. 저장은 clone 방식과 대비해 어떻게 쓰는지 설명한다.
  4. 확인해 볼 것같은 ALTER 문을 실행해 두고 다른 세션에서 해당 표에 INSERT 가 계속 들어가는지 확인한다.

Backtracking — 삭제 직전으로 되돌린다

DELETE 나 UPDATE 같은 파괴적인 문장이 실행되기 직전까지 데이터 상태를 기록해 두었다가 시간 골라 되돌릴 수 있게 하는 Aurora MySQL 기능이다.

먼저 알아야 할 것 06-02

#1문제 상황

DELETE 나 UPDATE 를 잘못 실행하면 일반적인 백업 복구 절차로 되돌린다(→ 08-02). 데이터 옮기고 클러스터를 새로 만드는 비용과 시간이 크다.

Backtracking 은 오류를 지운 문장 직전까지 되감는 수단이다. 단 특정 시각 복구의 대체는 아니다.

#2핵심 질문

파괴적인 문장을 잘못 실행했을 때 이전 상태로 어떻게 되돌리는가?

#3동작 예시

운영자가 WHERE 절을 빠뜨린 DELETE 를 실행해 주문 데이터가 사라진다.

관리 콘솔에서 바로 들어가 삭제 직전 시각으로 backtrack 을 실행한다. 데이터가 그 상태로 되감긴다.

#4동작 과정

  1. 기록 범위를 정한다configuring backtracking 으로 되감을 유지할 시간 범위인 backtrack window 를 정한다. 그 범위의 상태만 undo history 로 남는다.
  2. 되감는다Performing a backtrack 으로 고른 시각으로 클러스터를 되돌린다.
  3. 지켜본다Monitoring backtracking 으로 되감은 결과와 남은 기록을 확인하고, Backtracking a DB cluster 설정으로 기능을 다시 켠다.
  4. 확인해 볼 것콘솔의 backtrack 화면에 최근 backtrack 목록과 시각이 보이는지 확인한다.

Babelfish — PostgreSQL 로 SQL Server 를 쓴다

Aurora PostgreSQL 안에 SQL Server 용 T-SQL 문법과 저장 프로시저를 그대로 쓸 수 있게 해 주는 호환 계층이다.

먼저 알아야 할 것 06-01

#1문제 상황

SQL Server 로 만든 애플리케이션을 PostgreSQL 로 옮기려면 코드를 다시 쓰고 드라이버도 바꾼다(→ 06-01). 전통적인 이관 작업의 비용이 그대로 따라온다.

Babelfish 는 드라이버를 바꾸지 않고 코드 변경도 최소화한 채로 같은 애플리케이션을 Aurora PostgreSQL 에 붙인다.

#2핵심 질문

SQL Server 애플리케이션을 드라이버 바꾸지 않고 Aurora PostgreSQL 에서 어떻게 돌리는가?

#3동작 예시

기존 T-SQL 저장 프로시저를 호출하던 애플리케이션을 그대로 배포한다.

TDS 포트에 붙은 Babelfish 엔드포인트가 T-SQL 문장을 해석해 Aurora PostgreSQL 에서 실행한다. PostgreSQL 연결로도 같은 데이터에 접근한다.

#4동작 과정

  1. 아키텍처를 본다Babelfish architecture 는 SQL Server 저장 프로시저와 T-SQL 문장을 읽어 PostgreSQL 모드로 변환하는 두 갈래 구조로 동작한다. PostgreSQL 모드에서는 네이티브 PostgreSQL 도구를 그대로 쓴다.
  2. 엔드포인트를 붙인다TDS endpoint 는 SQL Server 의 wire-level 프로토콜인 TDS, 즉 Tabular Data Stream 을 받는 별도 리스너 포트다. 이 포트에 원래 방식으로 연결하는 클라이언트가 그대로 붙는다.
  3. 데이터를 옮긴다migrating a SQL Server database 절차를 따라 SQL Server 데이터를 Babelfish 로 옮기고 검증한다. Babelfish 는 PostgreSQL 연결로도 같은 데이터에 접근하게 해 준다.
  4. 확인해 볼 것클러스터의 포트 목록에 TDS 리스너 포트가 따로 보이는지 확인한다.

#1문제 상황

Amazon S3 는 객체 스토리지로, 데이터 레이크의 구조화 데이터를 여기에 파일로 두게 된다. 여기 쌓이는 표 형식 파일에는 Apache Iceberg 라는 표 규격과, 열 단위로 저장되는 Parquet 파일 형식이 쓰인다.

데이터 웨어하우스로 복사해 두는 ETL 파이프라인이 필요했다(→ 11-04). 데이터가 중복되고 인프라 비용과 항상 맞추는 일이 따라온다.

Analytics 는 그 복사 없이 질의하게 한다. 표와 파일은 그대로 두고 질의만 Aurora 로 당긴다.

#2핵심 질문

데이터를 복사하지 않고 데이터 레이크의 Iceberg 와 Parquet 를 어떻게 질의하는가?

#3동작 예시

S3 에 쌓인 Iceberg 주문 파티션을 다뤄야 한다. 여기에는 전형적인 ETL 파이프라인이 없는데도 결과가 필요하다.

foreign table 을 만들어 표준 SQL 로 질의한다. foreign table 을 Aurora PostgreSQL 표와 한 질의에서 조인해 결과도 함께 가져온다.

#4동작 과정

  1. 외부 표를 만든다foreign tables 로 Iceberg 나 Parquet 데이터를 가리키는 PostgreSQL 표를 정의한다. 대상은 Amazon S3, Amazon S3 Tables, AWS Glue Data Catalog 중 하나를 가리킬 수 있다.
  2. 질의를 보낸다표준 SQL 로 외부 표를 조회한다. how it works 는 데이터 이동이나 복제 없이 클라우드 파일을 직접 읽는 방식이다. 결과를 다른 저장소로 옮겨 쓰는 것도 가능하다.
  3. 한계를 본다Limitations 에서 지원하지 않는 SQL 형태와 대상 데이터의 제약을 확인한다.
  4. 확인해 볼 것클러스터의 스키마 목록에 만든 foreign table 이 보이는지 확인한다.

Query Plan Management — 실행 계획을 직접 고른다

Aurora PostgreSQL 이 데이터가 바뀔 때마다 미리 고른 여러 실행 계획 후보 중 비용이 가장 낮고 쓸 수 있는 계획을 골라 실행하게 하는 기능이다.

먼저 알아야 할 것 06-01

#1문제 상황

같은 SQL 문이라도 데이터가 늘면 옵티마이저가 고른 실행 계획이 갑자기 느린 쪽으로 바뀐다. Plan(질의를 실제로 실행할 순서와 방법을 적은 것)은 서버가 알아서 정하기 때문에 개발자가 막기 어렵다.

Query plan management는 여러 실행 계획을 미리 골라 두고 그중 쓸 수 있는 최저 비용 계획을 매번 고르게 한다.

#2핵심 질문

실행 계획이 느린 쪽으로 바뀔 때 내가 고른 계획으로 되돌릴 수 있을까?

#3동작 예시

운영 대시보드에서 특정 질의의 응답 시간이 갑자기 늘어난 것을 발견한다. 그 문을 기준선으로 등록해 두고 데이터가 늘어도 같은 방식으로 도는지 지켜본다.

계획이 갑자기 느린 쪽으로 바뀌면 등록해 둔 계획 중 비용이 가장 낮은 것이 다시 쓰인다.

#4동작 과정

  1. 기준선을 켠다apg_plan_mgmt.use_plan_baselines를 true로 두면 관리 대상 문마다 유효한 계획 중 최소 비용 계획을 고른다. 여러 후보를 Aurora PostgreSQL managed plans로 묶어 두는 단위다.
  2. 계획을 모아 둔다capturing Aurora PostgreSQL execution plans로 실행해 본 계획의 비용과 실제 시간을 저장한다. 후보는 dba_plans 뷰에서 볼 수 있다.
  3. 힌트로 좁힌다특정 계획만 써야 하는 문에는 query hints로 그 계획 하나만 쓰게 지정한다. 계획 변경 전에 비교하고 싶을 때 쓴다.
  4. 확인해 볼 것해당 문에 EXPLAIN ANALYZE를 실행해 옵티마이저가 어떤 계획을 고르는지 비용과 함께 보이는지 확인한다.

Aurora 업데이트와 패치의 구별

Aurora 업데이트는 기존 엔진 버전 안에서 서버 소프트웨어를 최신 수정 버전으로 교체해 보안·안정성 문제만 고치는 것이고, 패치는 이 교체 작업 자체를 자동 또는 수동으로 트리거하고 관리하는 절차를 이르는 말이다.

먼저 알아야 할 것 01-05

#1문제 상황

Aurora updates는 클러스터 서버 소프트웨어의 결함을 고치는 일이다. 어떤 수정 내용이 들어가는지는 patch level이라는 버전의 세 번째 자리로 구분한다.

패치는 이 교체를 언제 어떻게 실행할지 관리하는 절차라, 엔진은 그대로 두고 적용 시점만 다룬다.

#2핵심 질문

서버 재시작이 필요한 보안 수정 사항을 언제 어떻게 반영할까?

#3동작 예시

보안 공지가 올라온 회사가 클러스터 콘솔에서 업데이트 상태를 확인한다. 해당 엔진 버전의 마지막 patch level이 아직 적용되지 않았고, 다음 maintenance window가 화요일 새벽으로 잡혀 있다.

그 시간에 자동 업데이트가 돌아가 연결이 잠시 끊겼다가 돌아온다.

#4동작 과정

  1. 자동 반영을 정한다automatic minor version upgrades를 켜 두면 새 수정 버전이 나올 때 Aurora updates가 예약된 시간에 들어간다. major version은 대상이 아니다(→ 01-05).
  2. 시간을 정한다maintenance window를 지정해 그 구간에만 재시작이 일어나게 한다. 바쁜 낮 시간을 피한다.
  3. 일시 정지를 감당한다업데이트는 재시작이 필요해 잠시 연결이 끊긴다. 이 구간 동안 애플리케이션이 재연결하도록 설정해 둔다.
  4. 확인해 볼 것콘솔의 업데이트 항목에서 클러스터에 적용된 patch level과 다음 업데이트 예정 시각이 보이는지 확인한다.

무중단 패칭(Zero-downtime patching)

패치 적용 시 같은 리전 안에서 리더 복제본 등 다른 인스턴스에 패치를 먼저 적용해 메모리를 재사용한 뒤 리더의 역할을 넘기는 방식으로, 쓰기 연결을 끊지 않고 엔진 업데이트를 반영하는 기능이다.

먼저 알아야 할 것 07-01

→ 07-01 참조

#1문제 상황

Aurora MySQL 의 minor version을 올리려면 엔진 재시작이 필요하다(→ 07-01). 바쁜 시간에 그대로 올리면 처리 중이던 연결과 트랜잭션이 모두 사라진다. 그렇다고 한가할 때까지 기다리면 오래 기다린다.

zero-downtime patching은 이 둘의 중간을 택하는 방식이다.

#2핵심 질문

재시작이 꼭 필요한데 클라이언트 세션을 끊지 않고 엔진을 바꿀 수 있을까?

#3동작 예시

업무 시간이 몰리는 낮에 Aurora MySQL minor version 올리기를 요청한다. 엔진이 다른 replica를 먼저 갱신하고 그 메모리를 물려받은 뒤 primary 역할이 넘어간다.

애플리케이션 세션은 유지되고, 엔진 재시작 구간 동안만 처리량이 잠시 떨어진다.

#4동작 과정

  1. 사전 조건을 본다modifying the engine version으로 대상 버전을 정한다. 운영체제 패치와 major version에는 이 기능이 적용되지 않는다.
  2. 복제본부터 갱신한다Aurora Replicas patched first 규칙으로 읽기 복제본부터 새 버전으로 올린다. 그 메모리를 재사용하므로 전체 메모리를 다시 잡지 않는다.
  3. 역할을 넘긴다갱신된 복제본이 primary 역할을 이어받으면서 쓰기가 계속된다. 엔진 재시작 동안 수초에서 1분쯤 처리량이 낮아질 수 있다.
  4. 확인해 볼 것클러스터의 인스턴스 목록에서 갱신 대상이 복제본이 먼저 바뀌고 리더가 나중에 바뀌는지 순서를 확인한다.

주요 버전 업그레이드 사전 점검

Aurora MySQL 에서 3에서 8 같은 큰 버전 번호로 오르기 전에 업그레이드 전 검사(precheck)를 실행해 제거된 기능·지원되지 않는 파라미터 같은 호환성 문제를 미리 찾아 목록으로 보여주는 단계다.

먼저 알아야 할 것 07-01

→ 07-02 참조

#1문제 상황

major version upgrade는 엔진 소프트웨어뿐 아니라 아키텍처를 바꿔서 준비가 더 필요하다. 작은 수정 교체(→ 07-01)와 달리, 미리 알지 못한 항목 때문에 중간에 멈추면 되돌리기 어렵다.

Aurora 는 사전 검사를 통해 문제를 목록으로 먼저 보여 준다.

#2핵심 질문

큰 버전 번호를 올리기 전에 무엇이 깨지는지 어떻게 미리 알 수 있을까?

#3동작 예시

Aurora MySQL 3 버전에서 8 계열로 올리기 전에 업그레이드 전 검사(precheck)를 실행한다. 콘솔과 로그에 제거된 기능과 지원되지 않는 파라미터가 항목별로 나열된다.

이를 고친 뒤 같은 검사를 다시 돌려 통과를 확인하고 업그레이드를 진행한다.

#4동작 과정

  1. 검사를 돌린다major version upgrade prechecks를 실행해 현재 클러스터가 새 버전에서 막히는 지점을 모은다. community MySQL 의 검사 항목과 Aurora 자체 항목을 함께 쓴다.
  2. 목록을 고친다검출된 항목을 코드나 파라미터 측면에서 해결한다. 목록은 엔진 버전 조합별로 다르다.
  3. 같은 자리에서 올린다in-place upgrade로 기존 클러스터에서 곧바로 새 major version으로 바꿔 두 데이터베이스를 따로 두지 않는다. 실패하면 upgrade failures 로그로 중단 지점을 확인한다.
  4. 확인해 볼 것검사 결과 목록에 경고와 오류가 각각 어떤 항목으로 나오는지 확인한다.

PostgreSQL 논리 복제로 주요 버전 업그레이드하기

Aurora PostgreSQL 은 한 버전의 클러스터에서 내보낸 데이터베이스 객체의 변경분을 다른 새 버전 클러스터에 논리 복제(pglogical)로 계속 흘려보내는 방식으로 결국 원본 데이터베이스를 새 버전으로 전환해 업그레이드를 마무리한다.

먼저 알아야 할 것 07-03

→ 07-03 참조

#1문제 상황

Aurora PostgreSQL 을 큰 버전으로 올릴 때 한 번에 바꾸면 그동안 쓰기가 멈춘다. 사양 점검으로 걸린 문제까지 함께 풀어야 해서(→ 07-03) 전부 미리 해결하기 어렵다.

논리 복제를 쓰면 새 버전 클러스터를 띄워 놓고 데이터를 넘기며 전환을 늦출 수 있다.

#2핵심 질문

데이터베이스를 멈추지 않고 새 major version으로 넘어가는 방법은 무엇인가?

#3동작 예시

blue 클러스터(기존 버전) 스냅샷을 복제한 green 클러스터(새 버전)를 만든다. 논리 복제를 걸어 두면 이후 변경분이 계속 흘러 green 에 쌓인다.

애플리케이션이 green 을 다 읽고 쓰기 시작하면 전환이 끝난다.

#4동작 과정

  1. 논리 복제를 건다major version upgrade for Aurora PostgreSQL 을 위해 blue 에서 내보내는 logical slot을 만들어 green 이 이어받게 한다. 슬롯은 변경분을 놓치지 않기 위한 대기 지점이다.
  2. 데이터를 채운다Aurora fast cloning으로 write-through cache 방식으로 기존 데이터를 싣고, 논리 복제가 그 뒤의 변경분을 계속 채운다.
  3. 애플리케이션을 돌린다blue 는 읽기 전용으로 두고 쓰기를 green 으로 넘긴 뒤 이、蓝·green 전환으로 새 버전이 주 데이터베이스가 된다(→ 07-05).

  2. green 을 고친다엔진 버전 업그레이드나 파라미터 변경을 green 에만 적용해 시험하고 검증을 마친다.

  4. 확인해 볼 것배포 상태에서 blue 과 green 의 역할이 바뀌고 현재 프로덕션이 어느 쪽인지 표시되는지 확인한다.

Aurora 백업의 구조와 자동 백업

Aurora 는 클러스터의 모든 데이터 계층을 증분 방식(직전 백업 이후 바뀐 블록만 저장)으로 묶어 백업하며, 기본 보존 기간 동안 자동으로 이 백업을 매일 수행해 두었다가 지정한 기간이 지나면 지우는 자동 백업 방식을 쓴다.

먼저 알아야 할 것 02-01

#1문제 상황

클러스터를 만들면(→ 02-01) 데이터가 사라지는 경우에 대비할 방법이 필요하다. 파일을 직접 복사해 두면 쓰기 중에 데이터가 흔들릴 수 있고, 복구 지점을 매일 손으로 정해야 한다.

Aurora 는 cluster volume, 즉 클러스터 데이터가 담긴 저장 볼륨(→ 01-02)을 알아서 백업한다. 이 백업은 AWS Backup 으로 관리할 수 있고, 데이터는 Amazon S3 에 보관된다.

#2핵심 질문

Aurora 는 데이터를 얼마나 자주, 어디까지 안전하게 저장해 두는가?

#3동작 예시

운영팀이 주기적으로 클러스터 데이터를 별도 장소에 보존하려고 스냅샷을 떠 둔다(→ 08-03). 그 사이에도 Aurora 는 알아서 자동 백업을 이어 가고, 보존 기간이 지난 항목은 자동으로 지운다.

#4동작 과정

  1. 백업한다Aurora backs up your cluster volume automatically 라고 공식 문서에 적혀 있을 만큼, 클러스터 볼륨을 사용자가 부르지 않고 AWS 가 수행한다. 자동 백업은 continuous and incremental, 즉 계속 이어지며 직전 백업 뒤 바뀐 부분만 덧붙이는 방식으로 진행된다.
  2. 보관한다이렇게 모은 데이터는 Amazon S3 에 저장되고, 보존 기간(backup retention period)을 클러스터 생성·변경 시 1일에서 35일 사이로 정한다. 기간이 지난 자동 백업은 지워지며 retained automated backups 를 따로 지정해 더 오래 남길 수도 있다.
  3. 부담을 남기지 않는다쓰기가 이어지는 동안 백업이 함께 이뤄지므로 No performance impact 가 보장된다. 따로 transaction logs 를 다뤄 복구 지점을 만들 필요는 없고, 보존 기간 안의 어느 순간으로든 되돌릴 수 있다.
  4. 확인해 볼 것콘솔의 백업 설정에서 보존 기간이 몇 일로 되어 있는지 확인한다.

Point-in-time recovery — 특정 시각으로 되돌리기

Point-in-time recovery(특정 시각 복구)는 자동 백업에 남아 있는 데이터베이스 로그를 시간 순서로 다시 재생해 사용자가 고른 과거 시각(직전 5분 이내)의 상태로 클러스터를 되살리는 기능이다.

먼저 알아야 할 것 08-01

→ 08-01 참조

#1문제 상황

어플리케이션이 실수로 데이터를 지웠다(→ 06-03). 매일 떠 두는 스냅샷(→ 08-03)으로는 사고가 난 정확한 분을 되찾을 수 없다.

Point-in-time recovery(특정 시각 복구)는 자동 백업(→ 08-01) 기간 안의 아무 때로 클러스터를 되살린다. 자동으로 올라간 데이터베이스 로그가 S3 에 계속 쌓이므로 그 구간이 복구 대상이 된다.

#2핵심 질문

사고가 난 정확한 분의 데이터 상태로 Aurora 클러스터를 되돌리려면?

#3동작 예시

새벽 2시에 운영자가 실수로 DELETE 를 실행했다. 콘솔에서 Aurora 를 열면 되돌릴 수 있는 가장 이른 시각과 가장 늦은 시각이 보인다. 그 사이에서 사고 직전 시각을 고르면 새 클러스터가 그 상태로 올라온다.

#4동작 과정

  1. 시점을 고른다point-in-time recovery 는 AWS Backup 으로도 관리되는 기능이다. 어떤 시각이 복구 가능한지는 describe-db-clusters 명령의 EarliestRestorableTime 과 LatestRestorableTime 필드에서 확인한다.
  2. 복구한다고른 시각으로 새 클러스터를 만든다. Aurora 는 로그 레코드를 Amazon S3 에 계속 올려 두므로 그 시점까지 transaction logs 를 순서대로 다시 적용해 데이터 상태를 되살린다.
  3. 설정을 붙인다복원된 클러스터는 기본 VPC 보안 그룹과 기본 parameter group(→ 02-06)에 자동으로 붙는다. 원하는 보안 그룹(→ 09-01)이나 파라미터 그룹을 지정해 따로 붙일 수도 있다.
  4. 확인해 볼 것콘솔의 복원 화면에서 복구 가능한 가장 이른 시각과 가장 늦은 시각이 표시되는지 본다.

DB cluster snapshot 은 필요할 때 언제든 클러스터 전체 상태를 포착해 보관하는 수동 스냅샷으로, 자동 백업 보존 기간 밖의 시점도 유지되며 클러스터를 새 클러스터로 복원하는 출발점이 된다.

DB cluster snapshot 은 그 시점의 클러스터 전체를 이름 붙여 보관한다. 자동 백업과 달리 만료되지 않으며, 나중에 새 클러스터를 복원하는 출발점이 된다.

#2핵심 질문

자동 백업 주기와 무관하게 특정 시점의 클러스터 상태를 오래 남기려면?

#3동작 예시

#4동작 과정

  1. 이름을 붙여 뜬다CreateDBClusterSnapshot 으로 어떤 클러스터의 어떤 상태를 남길지 정한다. 클러스터가 available 상태여야 하며, 저장 볼륨 전체를 담기 때문에 데이터 크기와 임시 파일 크기에 따라 걸리는 시간이 달라진다.
  2. 오래 둔다manual snapshots 은 backup retention period 의 적용을 받지 않고 스냅샷이 만료되지 않는다. 매우 장기 보존이 필요하면 스냅샷 데이터를 Amazon S3 로 내보낸다(→ 08-05).
  3. 되돌린다이 스냅샷에서 클러스터를 새로 만들 수 있다. 단 엔진의 major version(→ 01-05)이 더 이상 지원되지 않으면 그 버전으로의 복원은 되지 않는다.
  4. 확인해 볼 것콘솔의 스냅샷 목록에 방금 만든 이름이 다른 스냅샷과 구분되어 보이는지 확인한다.

Aurora 스냅샷은 같은 리전이나 다른 리전으로 복사할 수 있고, 암호화된 스냅샷은 다른 AWS 계정과 공유하거나 대상 계정에서 직접 복사해 쓸 수 있어 백업 사본을 조직 밖에도 두고 활용한다.

먼저 알아야 할 것 08-03

→ 08-03 참조

#1문제 상황

스냅샷 하나(→ 08-03)만 있으면 그 리전이나 계정이 사라질 때 함께 사라진다. 사본을 따로 두려면 매번 스냅샷부터 다시 떠야 한다.

DB cluster snapshot copying 은 이미 있는 스냅샷을 그대로 복사해 새 스냅샷을 만든다. 복사된 결과는 manual snapshot 이 되고, 자동 백업도 복사 대상이 된다.

#2핵심 질문

Aurora 스냅샷 사본을 다른 리전이나 다른 AWS 계정에도 두려면?

#3동작 예시

분기마다 스냅샷 하나를 자동 백업과 수동 스냅샷에서 골라 다른 리전으로 복사한다. 복사된 스냅샷은 그 리전에서 새로운 사본으로 관리된다.

#4동작 과정

  1. 복사한다copying across accounts 와 같이 스냅샷 copying 은 같은 AWS Region 안에서도, AWS Regions 를 넘어서도, 한 번의 동작으로 다른 리전이나 계정까지 할 수 있다. 자동 백업에서 여러 장을 만들 수도 있지만 각 복사본은 서로 다른 식별자를 가져야 한다.
  2. 공유한다sharing a DB cluster snapshot 으로 다른 계정이 볼 수 있게 둘 수 있고, 공유받은 스냅샷은 그 계정에서도 복사 대상이 된다.
  3. 조건을 본다encrypted snapshot 은 암호화된 상태를 유지한 채 공유와 복사가 되고, 대상 계정 권한을 먼저 준비해야 한다. 보관한 스냅샷 데이터 양과 기간에 따라 요금이 붙는다.
  4. 확인해 볼 것콘솔의 스냅샷 목록에서 복사된 스냅샷이 원본과 별개의 항목으로 나타나는지 본다.

#2핵심 질문

Aurora MySQL 에서 외부 MySQL 로 binlog 복제

Aurora MySQL 클러스터는 읽기 전용 복제 인스턴스로 동작해 클러스터의 이진 로그(binlog)를 외부 MySQL 서버로 계속 보내는 이진 로그 복제(binlog replication)를 지원하므로, 클러스터에서 읽힌 데이터 변경이 외부 MySQL 에도 그대로 반영된다.

먼저 알아야 할 것 08-03

#1문제 상황

Aurora 로 옮긴 뒤에도 기존 MySQL 서버를 바로 지울 수는 없다(→ 11-01). 두 곳이 같은 데이터를 가져야 한다면 한쪽의 변경이 계속 넘어가야 한다.

Binary log (binlog) replication 은 MySQL 의 데이터 변경 기록인 이진 로그를 읽어 상대로 그대로 재생하는 방식이다. Aurora 는 이 방식을 쓰면 복제 원본이나 복제 대상 어느 쪽으로도 설 수 있다.

#2핵심 질문

Aurora 와 외부 MySQL 의 데이터를 계속 같은 상태로 맞추려면?

#3동작 예시

Aurora 로 이전 후 레거시 시스템이 아직 외부 MySQL 를 읽고 있다. 복제를 켜 두면 Aurora 에서 들어온 쓰기 변경이 곧바로 외부 서버에도 반영된다.

#4동작 과정

  1. 복제를 세운다setting up binlog replication 로 원본과 대상을 정하고 연결을 만든다. 대상은 RDS for MySQL 인스턴스일 수도, RDS 밖의 MySQL 일 수도, Aurora MySQL 클러스터일 수도 있다.
  2. GTID 로 맞춰 간다GTID-based replication 은 각 변경에 고유 번호를 붙여 누락과 중복 없이 이어지는 방식이다. 원본 MySQL 이 5.5 이후 버전을 쓰는지 먼저 본다. cross-Region read replica 로 다른 리전에 두거나 multi-source replication 으로 여러 원본을 한곳에 모을 수도 있다.
  3. 확인해 볼 것SHOW REPLICA STATUS 를 실행해 외부 서버 쪽 복제 상태가 나타나는지 확인한다.

보안 그룹으로 클러스터 접근 제한

보안 그룹은 허용·차단 규칙을 담은 가상 방화벽으로, 허용된 IP 대역에서만 클러스터로의 인바운드 연결만 성립하게 하여 나머지 모든 접근을 막는다.

먼저 알아야 할 것 02-02

#1문제 상황

클러스터를 만든 직후에는 네트워크 접근이 꺼져 있다(→ 02-01). 그런데 어디서 들어오는 연결을 열지 정하지 않으면 서비스가 외부에 노출된다.

security group 은 허용·차단 규칙을 담은 가상 방화벽으로, inbound rule 로 들어올 수 있는 출발점을 지정한다. 한 규칙은 같은 보안 그룹을 쓰는 모든 DB 클러스터에 함께 적용된다.

#2핵심 질문

Aurora 클러스터로 들어올 수 있는 연결을 어떻게 좁히는가?

#3동작 예시

애플리케이션 서버만 클러스터에 붙도록 해당 서버가 쓰는 보안 그룹을 출발점으로 지정한다. 나머지 주소에서 오는 연결은 전부 막힌다.

#4동작 과정

  1. 규칙을 정한다VPC security group 규칙 하나로 출발점을 정한다. 출발점은 주소 대역이거나 다른 보안 그룹이며, 보안 그룹을 출발점으로 삼으면 그 그룹을 쓰는 인스턴스 전체가 붙을 수 있다.
  2. 나가는 방향은 따로 본다VPC 보안 그룹은 들어오는 방향과 나가는 방향 규칙을 모두 갖고 있지만, 클러스터의 접근 제어는 inbound 쪽에서 이뤄진다.
  3. 알고리즘을 따른다best practices 로 계층별로 규칙을 나눠 만들고, 보안 그룹 하나에 규칙은 20개까지 지정할 수 있다. 같은 규칙이 여러 클러스터에reuse 되므로 공통 정책으로 둔다.
  4. 확인해 볼 것클러스터의 연결 정보 화면에 지정한 보안 그룹과 인바운드 규칙 목록이 보이는지 확인한다.

마스터 사용자와 DB 클러스터 관리자 자격

마스터 사용자는 Aurora 클러스터를 만들고 관리할 때 처음부터 만들어지는 관리자 계정이며, 이 자격이 클러스터와 그 안 데이터베이스에 대한 모든 권한을 가진다.

먼저 알아야 할 것 09-01

#1문제 상황

Aurora 클러스터를 만들면 첫 접속 계정이 자동으로 생긴다. 이 계정이 master user 로, 클러스터 전체와 그 안의 데이터베이스를 관리하는 user account privileges 를 전부 가진다(→ 09-01).

그래서 클러스터가 처음 만들어진 뒤 계정 하나를 애플리케이션 코드에 그대로 넣는 방식으로起步하기 쉽다. 대신 master user 와 master user password 를 애플리케이션에서 직접 쓰는 대신, 필요한 권한만 준 계정을 따로 만드는 방식을 권장한다.

#2핵심 질문

클러스터의 모든 권한을 가진 관리 계정을 애플리케이션에 노출하지 않고 어떻게 나눠 쓰는가?

#3동작 예시

주문 애플리케이션이 Aurora 클러스터에 접속할 계정을 만든다. 삽입과 조회만 하는 계정에는 그 두 권한만 주고, 클러스터를 만들거나 계정을 지우는 권한은 주지 않는다.

#4동작 과정

  1. 마스터 사용자를 받는다클러스터를 만들면 이름이 정해진 관리자 계정이 함께 생성된다. 생성 후에는 이름을 바꿀 수 없다.
  2. 권한을 나눈다애플리케이션에는 최소 권한만 가진 계정을 새로 만들고 그 자격으로 Database authentication 을 한다. 권한은 엔진별로 다른 이름으로 주어진다.
  3. 확인해 볼 것클러스터의 세부 정보에서 마스터 사용자 이름이 무엇으로 표시되는지 확인한다.

IAM 데이터베이스 인증

IAM 데이터베이스 인증은 AWS IAM 에서 발급한 인증 토큰(서명된 임시 자격 증명)을 비밀번호 대신 사용해 클러스터에 로그인하게 하는 방식이다.

먼저 알아야 할 것 09-02

#1문제 상황

데이터베이스 계정마다 비밀번호를 만들어 저장하고 배포할 때마다 갱신해야 한다(→ 09-02). 비밀번호가 코드나 설정 파일에 남으면 관리가 어려워진다.

IAM database authentication 은 이 비밀번호를 없앤다. Aurora 가 요청할 때마다 만든 authentication token, 즉 AWS Signature Version 4 로 서명된 임시 문자열을 자격 증명으로 쓴다. 수명은 15 분이며 Aurora MySQL 과 Aurora PostgreSQL 모두에서 동작한다.

#2핵심 질문

비밀번호를 저장하지 않고 IAM 자격으로 Aurora 클러스터에 로그인하려면?

#3동작 예시

애플리케이션이 IAM role 을 맡은 상태에서 클러스터에 접속한다. GenerateDbAuthToken 으로 토큰을 받아 접속 문자열에 넣고, 표준 데이터베이스 인증을 그대로 쓸 수도 있다.

#4동작 과정

  1. 연결을 허용한다IAM policy 로 어떤 주체가 어느 클러스터에 붙을 수 있는지 정한다. 네트워크 경로는 앞서 정한 보안 그룹이 막는다.
  2. 토큰을 만든다GenerateDbAuthToken 이 서명된 토큰을 반환한다. 이 토큰은 인증에만 쓰이고 세션이 열린 뒤에는 영향을 주지 않는다.
  3. 확인해 볼 것토큰으로 연결한 뒤 데이터베이스 안에서 현재 인증을 확인할 수 있는지 본다.

먼저 알아야 할 것 09-03

#1문제 상황

같은 표에 주민번호나 연락처처럼 민감한 값이 들어 있으면, 접속한 사람이 볼 수 있는 범위를 쿼리마다 직접 걸어야 한다(→ 09-03). 저장된 값까지 지우면 원본이 없어진다.

Aurora PostgreSQL dynamic masking 은 저장소를 건드리지 않고 이 문제를 푼다. pg_columnmask 확장이 만든 masking policies 가 사용자 role 과 정책 가중치를 보고 data masking functions 를 질의 시점에 적용한다. 내장 함수로 이메일과 문자를 가릴 수 있고, 부분 값을 와일드카드로 바꾸거나 나만의 함수를 만들 수 있다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 권한을 나눈다Identity and access management 와 AWS managed policies 로 역할별 접근 범위를 정한다. service-linked roles 는 Aurora 가 관리 동작에 쓸 역할을 대신 맡는다.
  2. 마스킹 정책을 붙인다pg_columnmask 로 열 수준 정책을 만들고 data masking functions 를 고른다. built-in 함수와 custom 함수, 여러 마스킹 전략 가운데 하나를 선택한다.
  3. 확인해 볼 것마스킹 정책이 걸린 열을 서로 다른 role 로 질의해 서로 다른 결과가 나오는지 본다.

Wait event 로 병목을 좁히기

질의가 느린 이유를 '무엇을 기다렸는지' 기준의 대기 이벤트(wait event) 로 분류해, CPU 사용이 아니라 잠금(l lock) 이나 I/O 같은 실제 병목 지점을 찾아내는 분석 방법.

먼저 알아야 할 것 10-02

#1문제 상황

CPU 사용률이 높다는 사실만으로는 질의가 왜 느린지 알 수 없다. Database Insights에서 시간이 긴 SQL 문은 찾을 수 있지만(→ 10-02), 그 안에서 무엇이 병목인지가 남는다.

Wait events는 Aurora MySQL이 질의를 실행하며 기다린 대상을 분류해 보여 주는 기록이다. 이 분류로 보면 CPU가 아니라 잠금이나 저장소 쓰기에서 시간이 쓰였는지 갈린다.

#2핵심 질문

느린 질의가 정말 무엇을 기다려서 느려진 걸까?

#3동작 예시

주문 조회 질의가 평소보다 훨씬 느려진 것을 알아차린다. Database Insights에서 해당 SQL 문을 집어 어떤 시간이 어디에 쓰였는지 본다.

기다린 대상 가운데 행 잠금(l lock)이 큰 비중을 차지한다. 동시 갱신이 같은 행을 붙들고 있어서 기다린 것으로 보고, 그 구간부터 손본다.

#4동작 과정

  1. 수집한다Aurora MySQL은 실행 중인 각 스레드의 상태(thread states)를 wait events 이름으로 나눠 기록한다. cpu는 CPU를 기다린 경우, io/aurora_redo_log_flush는 Aurora 저장소에 영구 데이터를 쓰는 경우다.
  2. 분류한다이 이름 목록은 tuning with wait events에서 병목 후보를 고르는 기준이 된다. essential concepts for tuning은 확인 순서와 함께 이 목록을 다룬다.
  3. 잠금을 좇는다동기화(synch) 계열 이름은 기다린 상대가 있었다는 뜻이다. synch/cond/innodb/row_lock_wait는 한 세션이 갱신할 행을 잠갔고 다른 세션이 같은 행을 건드리려 기다린 경우로, locking 문제의 대표 신호다.
  4. 확인해 볼 것Database Insights의 질의 상세에서 시간이 많이 걸린 대기 항목 이름이 어떻게 찍히는지 확인한다.

#3동작 예시

시험 환경이 먼저 필요해 스냅샷 경로를 고른다. RDS for PostgreSQL DB 스냅샷을 곧바로 Aurora PostgreSQL DB 클러스터로 이관해 데이터를 복원한다.

운영 환경은 Aurora 읽기 복제본 경로로 옮긴다. 복제 지연이 0이 되는 시점에 복제를 멈추고 그 복제본을 읽기·쓰기 가능한 단독 클러스터로 만든다.

#4동작 과정

  1. 스냅샷으로 옮긴다Migrating an RDS for PostgreSQL DB instance using a snapshot 경로로 스냅샷에서 Aurora PostgreSQL DB 클러스터를 바로 만든다.
  2. 복제본으로 옮긴다Migrating an RDS for PostgreSQL DB instance using an Aurora read replica 경로로 Aurora PostgreSQL 읽기 복제본을 RDS for PostgreSQL DB 인스턴스에 세운다.
  3. 끊는다두 인스턴스 간 replica lag가 0이 되면 복제를 멈춘다. 이때 그 복제본을 standalone Aurora PostgreSQL DB cluster로 바꾸어 읽기와 쓰기를 연다.
  4. 확인해 볼 것승격된 클러스터에 쓰기를 넣고 데이터가 정상적으로 들어가는지 확인한다.

11. 데이터를 옮겨오기 — 다른 데이터베이스에서 Aurora 로11-04

AWS DMS 로 자동으로 옮기기

AWS Database Migration Service(DMS)를 이용해 원본 DB 에서 Aurora 로 데이터를 옮기는 방식으로, 소스·대상 연결을 만들고 마이그레이션 태스크를 실행해 AWS 가 초기 데이터 적재와 이후 변경분 적용까지 자동 수행하게 한다.

먼저 알아야 할 것 11-01

#1문제 상황

Aurora 로 데이터를 옮길 때 원본 서버에 접속해 덤프를 떠 그대로 복원하면(→ 11-01) 옮기는 동안 원본을 건드려야 하고 시간도 오래 걸린다.

AWS DMS 는 AWS Database Migration Service(DMS), 즉 데이터베이스 사이의 데이터 옮김을 대신 수행하는 서비스다. 같은 엔진이며 호환되는 버전끼리라면 set up data migration 으로 원본을 Aurora 클러스터로 옮기고, 이후 변경분까지 이어서 적용할 수 있다.

#2핵심 질문

Aurora 로 데이터를 옮길 때 원본 데이터를 그대로 쓰게 하지 않고 어떻게 자동으로 옮길까?

#3동작 예시

엔지니어는 마이그레이션 대상 서버를 DMS 콘솔에 등록하고 새 Aurora 클러스터를 대상으로 지정한 뒤 마이그레이션 태스크를 실행한다.

Aurora 콘솔에서 auto-migrating databases 기능을 켜면 이 과정이 콘솔 안에서 시작된다. 콘솔의 상태 화면에서 넘어간 데이터 크기가 진행되며 보이며, 원본의 새 변경은 DMS 가 뒤이어 Aurora 쪽에 적용한다.

#4동작 과정

  1. 연결을 만든다원본과 대상 Aurora 클러스터를 DMS 에 각각 등록한다. 두 데이터베이스는 같은 엔진이어야 하며 엔진 버전이 호환되어야 한다.
  2. 데이터를 옮긴다set up data migration 태스크를 실행해 초기 데이터를 Aurora 에 싣는다. 원본이 1 TiB 보다 작으면 옮기는 데 시간과 자원이 덜 든다.
  3. 변경을 이어 간다managing migrations 로 실행 중인 태스크를 보며 복제 중인 상태를 확인한다. migrating 이후 생기는 변경도 DMS 가 대상에 계속 적용한다.
  4. 확인해 볼 것DMS 콘솔에서 태스크 상태가 ongoing 복제인지 보고 대상 Aurora 클러스터에 데이터가 들어왔는지 본다.

11. 데이터를 옮겨오기 — 다른 데이터베이스에서 Aurora 로11-05

Aurora 와 다른 DB 사이의 복제

Aurora 클러스터의 데이터를 다른 데이터베이스로 계속 넘기거나 그 반대 방향으로 받는 구성으로, 리플리케이션 계층을 세우는 방식이라 데이터 이관 후에도 양쪽 시스템이 함께 쓰이는 경우에 쓴다.

먼저 알아야 할 것 11-02

#1문제 상황

Aurora 클러스터 안에서는 각 DB 인스턴스 사이의 복제가 자동으로 돈다(→ 01-03). 그러나 클러스터 밖의 데이터베이스와 데이터를 나누려면 별도 구성이 필요하다.

이 구성은 replication with an external source 다. 어느 쪽을 출발점으로 삼으느냐에 따라 방향이 정해지고, 읽기 부하를 나눌지 리전 단위로 늘릴지에 따라 방식을 고른다.

#2핵심 질문

Aurora 와 다른 데이터베이스 사이에 데이터를 계속 주고받는 복제를 어떻게 세우는가?

#3동작 예시

Aurora 클러스터에서 읽힌 데이터 변경이 별도의 MySQL 서버에도 필요해 Replication with Aurora MySQL 을 세운다. Aurora 가 출발점이 되어 변경된 데이터를 그 서버로 밀어 넣는다.

반대로 PostgreSQL 쪽 데이터를 Aurora 로 당겨 올 때는 Replication with Aurora PostgreSQL 을 쓴다. 여러 리전에서 같은 데이터를 읽게 하고 싶으면 Aurora global databases 로 갈 수도 있다.

#4동작 과정

  1. 출발점을 정한다Aurora 가 소스인지 대상인지 먼저 고른다. 클러스터 밖의 서버는 버전과 엔진이 호환되어야 서로 복제할 수 있다.
  2. 방식을 고른다Replication with Aurora MySQL 과 Replication with Aurora PostgreSQL 은 각 엔진에서 밖으로 내보내거나 밖에서 받아들이는 방식이다. PostgreSQL logical replication 은 Publish/Subscribe 구조로 논리적 변경만 흘리는 방식이다.
  3. 확인해 볼 것대상 데이터베이스의 복제 상태 화면에서 Aurora 쪽 노드가 정상적으로 연결되어 복제 중인지 본다.

Aurora 요금과 모범 사례

Aurora 를 운영할 때의 비용 계산 기준과 권장되는 사용 패턴을 정리한 내용으로, db.instance 는 provisioned 요금과 Serverless v2(ACU) 요금으로 나뉘고 모범 사례는 성능과 안정성을 함께 챙기기 위한 지침을 담는다.

먼저 알아야 할 것 11-02

#1문제 상황

Aurora 의 비용은 클러스터가 아니라 DB instance 단위로 계산된다. 같은 기능이라도 인스턴스 크기와 과금 방식 선택에 따라 금액이 크게 달라진다.

그래서 운영자는 Aurora 요금 기준을 먼저 보고, Best practices with Aurora 를 기준으로 클러스터를 다루는 방식을 정한다.

#2핵심 질문

Aurora 를 운영할 때 무엇에 비용이 붙고 어떤 운영 지침을 따라야 하는가?

#3동작 예시

Aurora 클러스터를 만든 뒤 Cost Explorer 에서 어느 항목에 금액이 붙었는지 확인한다. On-Demand DB instances 로 켜 두면 사용 시간 만큼 과금되고,장기 유지할 계획이면 Reserved DB instances 로 바꿔 그 비용을 낮춘다.

운영자는 그와 별개로 Best practices with Aurora 를 보며 메모리를 얼마나 남겨야 하는지, 드라이버는 무엇을 쓸지 정한다.

#4동작 과정

  1. 계산 기준을 고른다비용은 DB instance billing for Aurora 를 따라 정해진다. On-Demand DB instances 는 사용량만큼, Reserved DB instances 는 미리 정해진 기간을 묶어 낸다.
  2. 운영 지침을 따른다메모리를 DB instance RAM 과 연결해 크기를 잡고, AWS database drivers 를 고르고, Working with DB parameter groups and DB cluster parameter groups 방식으로 파라미터를 관리한다. I/O operations 가 몰리는지 보고 조정한다.
  3. 확인해 볼 것Billing 콘솔에서 Aurora 항목 아래 어떤 사용 유형에 비용이 붙었는지 본다.
