1부. MySQL 시작과 환경001

관계형 데이터베이스란 무엇인가

표와 행으로 데이터를 저장하는 방식의 기본 개념

회원 명부를 엑셀 파일 하나에 몰아넣고 관리하다 보면, 한 사람의 주소를 바꾸는 순간 주문서 파일과 배송 파일에 남아 있는 옛 주소 때문에 같은 사람이 서로 다른 곳에 사는 것처럼 뒤섞이는 일이 생깁니다. 관계형 데이터베이스(relational database)는 이런 중복과 불일치를 없애기 위해 데이터를 여러 개의 표(table)로 나눠 저장하고, 표 사이의 관계를 번호로 묶어 두는 방식입니다. 아파트 관리사무소를 떠올리면 이해가 쉽습니다. 입주민 명부, 차량 등록 대장, 관리비 장부는 각각 다른 표로 관리되지만 모든 표에 같은 세대 번호가 적혀 있어서, 101동 502호라는 번호 하나만 보면 그 세대의 이름과 차량과 이번 달 관리비를 한 번에 찾아낼 수 있습니다.

세대 번호처럼 각 행을 유일하게 가리키는 값을 기본 키(primary key)라고 하고, 다른 표에서 그 번호를 참조하는 값을 외래 키(foreign key)라고 부릅니다. 관리사무소가 입주민 명부에서 세대를 지우기 전에 미납 관리비가 없는지 먼저 확인하듯, 데이터베이스도 이런 규칙을 지켜 표 사이의 연결이 끊어지지 않게 합니다. 정리하면 관계형 데이터베이스는 데이터를 행(row)과 열(column)로 이루어진 표에 나눠 담고, 키(key)로 표들을 연결해 중복을 줄이고 일관성을 지키는 저장 방식입니다. MySQL은 이 방식을 구현한 대표적인 프로그램이며, 지금도 많은 서비스가 이 구조 위에서 데이터를 관리하고 있습니다.

1부. MySQL 시작과 환경002

MySQL이란 무엇인가

MySQL의 정체와 MariaDB·PostgreSQL과의 차이

쇼핑몰의 상품 목록을 텍스트 파일에 적어 두면, 직원 두 명이 같은 파일을 동시에 고치는 순간 한 사람의 수정 내용이 흔적도 없이 사라지고 누가 마지막으로 저장했는지도 알 수 없게 됩니다. MySQL은 이런 사고를 막기 위해 여러 사람의 요청을 줄 세워 안전하게 처리하고, 전원이 꺼져도 데이터가 남도록 설계된 관계형 데이터베이스 관리 시스템(relational database management system)입니다. 택배 회사의 물류창고에 비유하면, 창고 건물 자체가 서버이고 그 안에서 물건을 넣고 꺼내는 작업을 지휘하는 관리 시스템이 MySQL입니다. 접수 직원이 운송장 번호로 물건을 조회하듯, 클라이언트는 SQL이라는 질의 언어로 요청을 보내고 MySQL은 그 요청을 해석해 어느 선반에 무엇이 있는지 찾아 결과를 돌려줍니다. 어떤 물건을 어디에 둘지 정하고 동시에 들어온 주문이 서로 부딪히지 않게 순서를 잡는 일도 MySQL이 맡습니다.

비슷한 일을 하는 프로그램으로 MariaDB와 PostgreSQL이 있는데, MariaDB는 MySQL에서 갈라져 나온 갈래라 명령문이 대부분 그대로 통하고, PostgreSQL은 표준 SQL 준수와 확장 기능 쪽에 무게를 둔 별도의 계보입니다. 정리하면 MySQL은 관계형 데이터베이스를 실제로 운영해 주는 오픈 소스 서버 프로그램이고, MariaDB와는 뿌리를 공유하지만 PostgreSQL과는 설계 철학을 달리합니다. 웹 서비스에서 널리 쓰이는 만큼 관련 문서와 도구를 구하기 쉽다는 점도 함께 기억해 둘 만합니다.

1부. MySQL 시작과 환경003

MySQL 서버 구조

클라이언트 요청이 스토리지 엔진까지 도달하는 경로

조회가 갑자기 느려졌을 때 문제가 네트워크 탓인지, 쿼리 문장 탓인지, 디스크 탓인지 구분하지 못하면 어디부터 손봐야 할지 막막해집니다. MySQL은 요청을 받는 접속 계층, 문장을 해석하는 계층, 실제로 데이터를 읽고 쓰는 스토리지 엔진(storage engine) 계층으로 역할을 나눠 두었기 때문에, 어느 단계에서 시간이 걸리는지 짚어 낼 수 있습니다. 회사에 비유하면 먼저 안내 데스크가 방문객의 신분을 확인하고 들여보내는 접속(connection) 계층이 있고, 접수된 요청서를 읽고 어떻게 처리할지 계획을 세우는 계층이 그 뒤를 잇습니다. 이 계층의 파서(parser)가 문장의 문법을 검사하고 옵티마이저(optimizer)가 같은 결과를 내는 여러 방법 중 비용이 적게 드는 경로를 골라 실행 계획을 만듭니다. 마지막으로 창고 현장 직원에 해당하는 스토리지 엔진이 실제 선반에서 데이터를 꺼내 오며, InnoDB나 MyISAM처럼 여러 엔진 중에서 표마다 하나를 골라 쓸 수 있습니다.

각 계층이 자기 일만 하도록 나뉘어 있어서 접속이 몰리는 문제와 디스크 읽기가 느린 문제를 따로 진단할 수 있습니다. 정리하면 MySQL 서버는 클라이언트 접속을 받는 계층, SQL을 해석하고 실행 계획을 세우는 계층, 데이터를 실제로 다루는 스토리지 엔진 계층이 차례로 이어지는 구조입니다. 요청 하나가 이 세 단계를 거쳐 처리된다는 점을 알면 성능 문제를 볼 때 어디를 먼저 살펴야 할지 판단하기 쉬워집니다.

설치와 초기 설정

윈도우·리눅스에서 MySQL을 설치하고 초기 설정을 마치는 법

설치는 금방 끝나지만 초기 설정을 건너뛰면 관리자 계정의 비밀번호를 잊거나, 다른 프로그램이 쓰는 포트와 부딪혀 접속이 되지 않는 일이 흔합니다. 윈도우와 리눅스 모두 설치 과정에서 접속 포트와 관리자 계정, 데이터를 둘 위치를 정하게 되어 있으니 이 부분을 꼼꼼히 확인하는 것이 중요합니다. 새집으로 이사하는 과정과 비슷합니다. 윈도우에서는 설치 파일을 실행해 설치 유형을 고르고, 함께 제공되는 설정 도구에서 포트 번호와 root 비밀번호, 서비스 자동 시작 여부를 정하면 됩니다. 리눅스에서는 패키지 관리자로 서버 패키지를 설치한 뒤 보안 설정 스크립트를 실행해 익명 계정과 원격 root 접속을 정리하는 절차가 이어집니다.

이사할 때 가구를 놓을 자리를 미리 정하듯 데이터 파일이 저장될 디렉터리와 문자 집합(character set)을 정해 두면 나중에 한글이 깨지는 문제를 줄일 수 있고, 설정을 마친 뒤에는 서비스가 정상적으로 떠 있는지 확인하고 방화벽에서 해당 포트를 열어 주어야 다른 컴퓨터에서도 접속할 수 있습니다. 정리하면 MySQL 설치는 프로그램을 복사하는 일에서 끝나지 않고, 포트와 관리자 계정, 데이터 저장 위치, 문자 집합을 정하고 서비스와 방화벽까지 확인해야 쓸 수 있는 상태가 됩니다. 이 단계에서 정한 값이 이후 접속과 백업의 기준이 되므로 어딘가에 기록해 두는 것이 좋습니다.

서버는 잘 돌아가는데 화면이 없는 원격 서버에 접속해야 한다면, 터미널에서 글자로 명령을 주고받는 방법을 알아야 합니다. mysql 클라이언트는 서버에 접속해 SQL 문장을 보내고 그 결과를 표 형태로 돌려받는 명령줄 프로그램입니다. 은행 창구에서 번호표를 뽑아 직원과 대화하는 과정과 비슷합니다. mysql -u 사용자 -p 처럼 접속 옵션을 주면 비밀번호를 묻고, 창구가 열리면 프롬프트에 SQL 문장을 한 줄씩 입력해 결과를 받습니다. 문장 끝에 세미콜론을 붙여야 여기까지가 한 건의 요청이라는 표시가 되고, 붙이지 않으면 다음 줄을 계속 이어 받는 상태로 기다립니다.

창구를 닫을 때는 exit나 quit를 입력하며, 서버에 직접 들어가지 않고 파일에 적어 둔 SQL을 한꺼번에 실행하려면 그 파일을 입력으로 넘겨주면 됩니다. 정리하면 mysql 클라이언트는 터미널에서 서버에 접속해 SQL을 입력하고 결과를 확인하는 대화형 도구이며, 접속 옵션과 세미콜론 규칙만 익히면 서버를 직접 조작할 수 있습니다.

데이터베이스 만들기와 선택

CREATE DATABASE와 USE로 작업 공간을 준비하는 법

서버에 접속한 뒤 표를 만들려고 하면, 그 표가 어느 데이터베이스에 속할지를 먼저 정해야 합니다. CREATE DATABASE와 USE는 이 작업 공간을 만들고 고르는 명령입니다. 새 사무실에 서류 캐비닛을 들이는 상황과 비슷합니다. CREATE DATABASE shop; 이라고 실행하면 shop이라는 이름의 캐비닛이 하나 생기고, USE shop; 이라고 실행하면 이제부터 서류를 넣고 꺼내는 작업이 그 캐비닛 안에서 이루어집니다. 캐비닛 안에 서랍을 만들듯 CREATE TABLE로 표를 만들면 그 표는 현재 선택된 캐비닛에 소속되고, 다른 캐비닛의 표를 쓰려면 이름 앞에 캐비닛 이름을 붙이거나 USE로 옮겨 가야 합니다.

SHOW DATABASES로 캐비닛 목록을 확인하고 SELECT DATABASE()로 지금 어느 캐비닛 앞에 서 있는지를 확인할 수 있습니다. 정리하면 데이터베이스는 표들을 담는 논리적인 작업 공간이고, CREATE DATABASE로 만들고 USE로 선택해 그 안에서 표를 다루게 됩니다. 하나의 MySQL 서버 안에 여러 데이터베이스를 두고 용도별로 나눠 쓸 수 있다는 점이 이 구조의 장점입니다.

접속 계정을 만들고 권한을 주는 첫 단계

데이터베이스에 접속하는 사람이 모두 최고 관리자 계정 하나를 같이 쓰면, 누가 실수로 중요한 표를 지웠는지 찾을 수 없고 퇴사한 사람의 접속도 막을 수 없습니다. MySQL은 이 문제를 해결하려고 사람마다 따로 쓰는 계정(USER)을 만들고, 계정마다 할 수 있는 일의 범위를 권한(PRIVILEGE)으로 정해 두었습니다.

회사 사옥에 비유하면 계정은 사원 한 명에게 발급되는 사원증이고, 비밀번호는 그 사원증에 걸린 본인 확인용 잠금장치입니다. 사원증에는 이름과 함께 어느 건물로 출입하는지가 적히는데, MySQL에서는 이것이 계정 이름 뒤에 붙는 호스트(HOST)이고 어느 컴퓨터에서 접속할 수 있는지를 가리킵니다. 그리고 사원증마다 열 수 있는 문이 달라서 어떤 사람은 자료를 보기만 하고 어떤 사람은 고치거나 지울 수 있는데, 이 문의 목록이 바로 권한입니다.

그래서 새 계정은 CREATE USER로 만들고 GRANT로 필요한 문만 열어 주는 순서로 준비합니다.

결국 사용자 계정은 접속 자체를 허용하는 신분이고, 권한은 그 신분이 데이터베이스 안에서 할 수 있는 행동의 목록입니다.

SQL 문의 종류

DDL·DML·DCL·TCL을 구분하는 기준

데이터베이스에 보내는 명령은 하는 일이 전혀 다른데도 모양이 비슷해서, 지우는 명령과 되돌리는 명령을 섞어 쓰면 작업 순서가 꼬이고 장애 때 원인을 가려내기 어려워집니다. 그래서 SQL(Structured Query Language)은 명령을 역할별로 나누어 DDL, DML, DCL, TCL 네 갈래로 구분합니다.

아파트 단지 관리에 비유하면 DDL은 건물의 골조를 세우고 증축하거나 철거하는 공사이고, DML은 세대 안에서 가구를 들이고 바꾸고 버리는 일상적인 살림입니다. DCL은 누가 어느 건물에 출입할 수 있는지 정하는 경비실의 명단이고, TCL은 이사처럼 여러 단계를 묶어 한 번에 끝내거나 전부 취소하는 절차입니다.

실제로 DDL에는 CREATE, ALTER, DROP이, DML에는 SELECT, INSERT, UPDATE, DELETE가, DCL에는 GRANT와 REVOKE가, TCL에는 COMMIT과 ROLLBACK이 들어갑니다. 이렇게 나누어 두면 어떤 명령이 구조를 바꾸고 어떤 명령이 데이터를 건드리는지 한눈에 구분할 수 있습니다.

다시 말해 SQL 문의 종류를 가르는 기준은 무엇을 대상으로 하는가이며, 구조는 DDL, 데이터는 DML, 권한은 DCL, 작업의 확정은 TCL이 맡습니다.

오류 메시지 읽는 법

그래서 오류를 만나면 문장을 지우기 전에 코드와 메시지를 먼저 읽고, 설명에 나온 단어를 그대로 검색해 원인을 좁히는 습관이 중요합니다.

요약하면 오류 메시지는 MySQL이 건네는 진단서이고, 코드는 증상의 이름, 설명은 원인의 해석, 위치는 문제가 난 지점을 가리킵니다.

테이블 만들기

CREATE TABLE로 열과 타입을 정의하는 기본 문법

표 없이 데이터를 파일에 마구 적어 두면 같은 이름이 두 번 들어가거나 숫자 칸에 글자가 섞이는 일이 생기고, 나중에 모아서 계산하려면 손으로 다시 정리해야 합니다. MySQL에서 표(table)는 이런 혼란을 막기 위해 열마다 담을 값의 종류와 규칙을 미리 정해 두는 저장 단위이고, 그 표를 새로 만드는 명령이 CREATE TABLE입니다.

물류창고에 비유하면 CREATE TABLE은 빈 선반을 세우면서 칸마다 어떤 물건을 어떤 크기로 넣을지 표찰을 붙이는 작업입니다. 괄호 안에 열 이름과 타입(TYPE)을 적는 것은 칸의 이름과 크기를 정하는 일이고, INT는 정수, VARCHAR는 길이가 정해진 글자, DATE는 날짜를 담는 칸입니다. 송장번호처럼 절대 겹치면 안 되는 칸에는 기본 키(PRIMARY KEY)를 붙이고, 비워 두면 안 되는 칸에는 NOT NULL을, 값을 넣지 않았을 때 자동으로 채울 칸에는 DEFAULT를 지정합니다.

이렇게 규칙을 먼저 정해 두면 잘못된 모양의 값이 들어오는 순간 MySQL이 거절하므로 창고에 엉뚱한 짐이 쌓이지 않습니다.

결국 테이블은 열과 타입, 그리고 제약 조건(constraint)으로 모양이 정의된 데이터의 그릇이며, CREATE TABLE은 그 그릇의 설계도를 확정하는 명령입니다.

테이블 구조 변경

ALTER TABLE로 열을 추가·수정·삭제하는 방법

표를 한 번 만들어 서비스에 쓰기 시작하면 열 이름이 마음에 들지 않거나 새 항목이 필요해지는 일이 반드시 생기는데, 그때 표를 지우고 다시 만들면 안에 있던 데이터가 모두 사라집니다. ALTER TABLE은 표를 없애지 않고 구조만 고치는 명령으로, 이미 쌓인 데이터를 유지한 채 열을 더하고 모양을 바꾸고 지울 수 있게 해 줍니다.

사람이 살고 있는 집을 고치는 것과 비슷해서, 벽을 새로 세우는 일이 열 추가(ADD COLUMN), 창문 크기를 바꾸는 일이 열 수정(MODIFY COLUMN), 필요 없는 벽을 허무는 일이 열 삭제(DROP COLUMN)입니다.

다만 살림이 그대로인 채 공사를 하듯이, 기존 데이터가 새 규칙을 만족하지 못하면 작업이 거절되므로 바꾸기 전에 어떤 값이 들어 있는지 확인해야 합니다. 특히 열을 지우는 명령은 그 열에 있던 값까지 함께 없애므로, 되돌릴 수 있는지 먼저 확인하고 가능하면 백업을 떠 둔 뒤 실행합니다. 열 위치를 옮기거나 이름만 바꾸는 작업도 같은 명령으로 처리할 수 있어서 표 전체를 다시 만들 필요가 없습니다.

정리하면 ALTER TABLE은 테이블 정의를 변경하는 DDL 명령이며, 데이터는 그대로 둔 채 열과 제약 조건의 구조만 조정하는 도구입니다.

테이블 삭제와 초기화

DROP과 TRUNCATE의 차이와 위험

회사 데이터베이스에서 오래된 테이블을 정리하려다 명령 한 줄을 잘못 입력해 고객 명단과 주문 기록이 통째로 사라지는 사고가 실제로 일어납니다. MySQL은 이런 일을 막기 위해 성격이 다른 세 가지 정리 명령, 즉 DELETE와 TRUNCATE와 DROP을 나누어 두었습니다.

아파트 단지 관리사무소를 떠올려 보면 차이가 분명해집니다.

DELETE는 세대를 하나씩 돌며 조건에 맞는 짐만 골라 내보내는 일이라 어떤 세대를 뺄지 지정할 수 있고 일을 되돌릴 수도 있지만 시간이 오래 걸립니다. TRUNCATE는 건물은 그대로 둔 채 모든 세대를 한 번에 비우는 일이라 구조와 설계는 남고 속도도 빠르지만 조건을 붙일 수 없고 되돌리기 어렵습니다. DROP은 세대를 비우는 수준을 넘어 건물 자체를 철거하는 일이라 테이블의 구조와 인덱스까지 함께 사라집니다.

정리하면 DELETE는 행 단위 삭제, TRUNCATE는 테이블 구조를 남긴 전체 초기화, DROP은 테이블 자체의 제거이며, 뒤로 갈수록 되돌리기 어렵고 위험이 큽니다.

기본 키(Primary Key)

행을 유일하게 식별하는 열의 역할과 규칙

고객 이름과 생년월일만으로 회원을 찾던 시스템에서 동명이인이 생기자 엉뚱한 사람의 주소가 바뀌고 포인트가 남의 계정으로 들어가는 일이 벌어집니다. 이 문제를 근본적으로 막으려고 모든 행에 붙는 단 하나의 식별자를 기본 키(Primary Key)라고 부릅니다.

아파트 단지에 사는 사람을 떠올려 보면 이해가 쉽습니다.

이름은 바뀔 수 있고 같은 이름의 주민도 여러 명이지만 동과 호수로 이루어진 주소는 단지 안에서 오직 하나뿐이라 택배도 안내 방송도 정확히 그 집을 찾아갑니다. 기본 키도 같은 원리로 값이 겹치지 않아야 하고 비어 있어서는 안 되며 테이블 하나에 하나만 둘 수 있습니다. 동호수도 함부로 바꾸면 기존 택배 기록이 모두 어긋나듯, 기본 키는 한 번 정하면 잘 바뀌지 않는 값을 고르는 것이 좋습니다.

정리하면 기본 키는 테이블의 각 행을 유일하게 식별하는 열로, 중복과 NULL을 허용하지 않는다는 규칙으로 데이터의 정확한 지목을 보장합니다.

2부. 데이터베이스와 테이블 설계015

외래 키(Foreign Key)

두 테이블의 관계를 강제하는 참조 제약

주문 테이블에 존재하지 않는 회원 번호가 적혀 있으면 그 주문은 주인을 찾지 못한 채 배송도 환불도 진행되지 못하고 쌓이기만 합니다. 이런 유령 데이터를 애초에 입력되지 못하게 막는 장치가 두 테이블의 관계를 강제하는 외래 키(Foreign Key)입니다.

택배 송장을 떠올려 보면 관계가 눈에 보입니다.

송장에 적힌 주소는 실제로 존재하는 집이어야 하고, 없는 주소를 적으면 택배사가 접수를 받지 않듯이 자식 테이블의 외래 키 값은 부모 테이블에 실제로 있는 값 중 하나이거나 아예 비어 있어야 합니다. 이 규칙을 참조 무결성이라고 부르며, 부모 쪽 주소가 사라질 때는 자식 주문이 남아 있는 한 삭제를 거부하거나 함께 정리하도록 정할 수 있습니다. 반대로 부모 테이블에는 없던 새 주소를 자식이 먼저 만들어 내는 것도 허용되지 않습니다.

정리하면 외래 키는 한 테이블의 열이 다른 테이블의 기본 키를 가리키게 하고, 그 값이 실제로 존재하도록 강제해 두 테이블의 관계와 데이터의 일관성을 지키는 제약입니다.

← 이전기본 키(Primary Key)다음 →유일 키(Unique Key)

2부. 데이터베이스와 테이블 설계016

유일 키(Unique Key)

중복을 허용하지 않는 제약의 동작 방식

같은 이메일 주소로 계정이 두 개 만들어지면 비밀번호를 잊었을 때 어느 계정으로 메일을 보내야 할지 알 수 없고, 한쪽만 탈퇴하면 남은 계정의 주인이 누구인지도 흐려집니다. 이렇게 중복되면 곤란한 열에 붙이는 장치가 유일 키(Unique Key)입니다.

회사 사원증을 떠올려 보면 동작이 단순합니다.

사원증 번호는 사람마다 달라서 두 사람이 같은 번호를 쓸 수 없지만, 아직 사원증을 받지 않은 사람처럼 번호가 비어 있는 상태는 있을 수 있습니다. 유일 키도 같은 방식으로 값의 중복을 막되 비어 있는 값은 허용하며, 테이블 하나에 여러 개를 붙일 수 있다는 점이 기본 키와 다릅니다. 또한 유일 키를 걸면 그 열로 빠르게 찾을 수 있도록 색인, 즉 인덱스가 함께 만들어져 조회 속도도 좋아집니다.

정리하면 유일 키는 한 열의 값이 서로 겹치지 않도록 보장하는 제약으로, 중복 없는 식별이 필요한 이메일이나 사번 같은 열에 붙여 씁니다.

← 이전외래 키(Foreign Key)다음 →NULL의 의미

2부. 데이터베이스와 테이블 설계017

NULL의 의미

값이 없음과 빈 문자열·0의 차이

설문 점수를 입력하지 않은 사람의 칸에 0을 대신 넣어 두면 평균이 실제보다 낮게 나오고, 연락처가 없는 사람의 칸에 빈 문자열을 넣어 두면 연락처 없음과 아직 모름이 뒤섞여 구분되지 않습니다. 값이 없다는 사실 자체를 표현하려고 데이터베이스는 NULL이라는 별도의 상태를 둡니다.

택배 송장을 떠올려 보면 세 가지가 어떻게 다른지 분명해집니다.

받는 사람 연락처 칸이 아예 비어 있는 것이 NULL이고, 그 칸에 없음이라고 적어 넣은 것이 빈 문자열이며, 나이 칸에 0을 적은 것은 실제로 0이라는 값입니다. NULL은 모른다거나 해당 없다는 뜻이라 0이나 빈 문자열과 크기를 비교할 수 없고, NULL과의 비교는 참도 거짓도 아닌 상태가 되어 등호로는 걸러낼 수 없습니다. 그래서 비어 있는지 확인할 때는 IS NULL이라는 전용 표현을 쓰고, 합계나 평균 같은 집계에서는 NULL이 빠진 채 계산됩니다.

정리하면 NULL은 값이 없음이 아니라 값이 정해지지 않았음을 나타내는 표시이며, 빈 문자열이나 0과는 전혀 다른 의미이므로 열을 만들 때 비어 있어도 되는지 미리 정해야 합니다.

← 이전유일 키(Unique Key)다음 →정규화(Normalization)

2부. 데이터베이스와 테이블 설계018

정규화(Normalization)

중복을 줄이도록 테이블을 나누는 원칙

주문을 받을 때마다 고객의 주소와 전화번호를 주문 표에 그대로 적어 두면, 고객이 이사를 한 번 할 때 수백 건의 주문을 모두 고쳐야 하고 일부만 고쳐지면 같은 고객이 서로 다른 주소로 남게 됩니다. 이런 중복과 어긋남을 줄이려고 표를 역할별로 나누는 원칙이 정규화(Normalization)입니다.

아파트 관리사무소 장부를 떠올려 보면 원칙이 자연스럽습니다.

세대 장부, 주민 장부, 차량 장부를 따로 두고 주민 장부에는 세대 번호만 적어 두면, 주소가 바뀌어도 세대 장부 한 줄만 고치면 되고 나머지 장부는 그 번호를 통해 같은 정보를 가리킵니다. 이렇게 나누면 같은 사실이 여러 곳에 중복되지 않아 수정이 한 번에 끝나고, 새 데이터를 넣거나 지울 때 생기는 모순도 줄어듭니다. 대신 나눠 둔 장부를 다시 합쳐 보려면 연결, 즉 조인이 필요해 조회가 조금 복잡해질 수 있습니다.

정리하면 정규화는 한 사실은 한 곳에만 저장되도록 테이블을 나눠 중복과 갱신 이상을 없애는 설계 원칙이며, 보통 기본 키와 외래 키로 나뉜 테이블을 다시 연결합니다.

← 이전NULL의 의미다음 →반정규화(Denormalization)

2부. 데이터베이스와 테이블 설계019

반정규화(Denormalization)

성능을 위해 일부러 중복을 두는 판단 기준

온라인 쇼핑몰을 운영하는데 주문 목록 화면을 열 때마다 몇 초씩 멈춘다면, 원인은 대개 정규화된 표 여러 개를 매번 다시 이어 붙이는 조회 비용에 있습니다. 반정규화(Denormalization)는 이 비용을 줄이려고 데이터 일부를 일부러 같은 값으로 한 번 더 저장하는 설계 기법이며, 데이터베이스 스키마 설계의 마지막 조정 단계에 속합니다.

아파트 관리사무소를 떠올려 보시면, 각 세대의 이름과 호수를 관리 대장 한 권에만 적어 두면 방문객이 올 때마다 대장을 펼쳐 찾아야 해서 시간이 걸립니다. 그래서 현관 게시판에 세대별 이름을 따로 한 번 더 적어 두면 확인은 빨라지지만, 입주자가 바뀌면 대장과 게시판 두 곳을 모두 고쳐야 하고 어느 한쪽을 놓치면 서로 다른 이름이 남습니다. 반정규화도 똑같아서, 조회가 잦은 값은 다른 표에 복사해 두어 읽기를 빠르게 만드는 대신, 원본이 바뀔 때 복사본까지 함께 갱신하는 관리 절차를 반드시 짝지어 두어야 합니다.

정리하면 반정규화는 중복을 실수로 남기는 것이 아니라, 읽기 성능과 쓰기 정합성 사이에서 이득이 더 큰 지점을 골라 중복을 승인하는 결정입니다. 따라서 조회 빈도와 변경 빈도를 먼저 재 보고, 중복된 값이 어긋나지 않도록 갱신 규칙을 문서로 남길 수 있을 때만 적용하는 것이 안전합니다.

ER 다이어그램

개체와 관계를 그림으로 정리하는 방법

요구사항을 말로만 주고받으면 개발자마다 머릿속 그림이 달라서, 나중에 주문 하나에 상품이 여러 개 담긴다는 사실을 뒤늦게 발견하고 표를 다시 뜯는 일이 생깁니다. ER 다이어그램(Entity-Relationship Diagram)은 데이터베이스에 담을 개체와 그 사이의 관계를 그림으로 합의해 두는 설계 도구입니다.

지하철 노선도를 떠올려 보시면, 역은 동그라미나 막대로, 역 사이를 잇는 선은 구간으로, 갈아타는 지점은 연결 표시로 그려져 있어서 글 설명 없이도 어디서 어떻게 이어지는지 한눈에 보입니다. ER 다이어그램에서도 개체(Entity)는 사각형, 개체가 가진 속성(Attribute)은 그 안이나 옆에 붙은 항목, 관계(Relationship)는 개체를 잇는 선으로 나타내고, 선 끝에 하나 또는 여럿을 뜻하는 표시를 붙여 한 명의 회원이 여러 주문을 남기는 식의 대응을 명시합니다. 노선도가 실제 선로를 대신하지 않듯 이 그림도 표를 만들어 주지는 않지만, 어느 표에 무엇이 들어가고 무엇이 무엇을 가리키는지를 사람들이 같은 그림으로 확인하게 해 줍니다.

정리하면 ER 다이어그램은 개체, 속성, 관계라는 세 요소로 데이터 구조를 시각화해 설계 단계의 오해를 줄이는 문서입니다. 그림을 먼저 합의하고 나서 표를 만들면, 나중에 구조를 고치는 비용을 크게 줄일 수 있습니다.

스키마 설계 실습

게시판·주문 데이터를 표로 설계해 보기

배운 문법만으로 바로 표를 만들면, 한 표에 글과 작성자와 댓글을 모두 밀어 넣어 같은 작성자 이름이 수백 번 반복되고 오타 하나로 동일 인물이 둘로 갈라집니다. 게시판과 주문 데이터를 표로 나눠 보는 실습은 정규화 원칙을 손으로 적용해 보는 과정이며, 스키마 설계의 기본 훈련입니다.

이삿짐을 싸는 상황을 떠올려 보시면, 냄비와 식기와 세제를 한 상자에 다 넣으면 나중에 냄비 하나를 꺼내려고 상자를 전부 뒤져야 합니다. 그래서 부엌살림은 부엌 상자, 욕실용품은 욕실 상자로 나누고 상자 겉면에 내용물을 적어 두면, 필요한 것만 골라 꺼내기가 쉬워집니다.

게시판도 마찬가지로 회원, 글, 댓글을 각각의 표로 나누고 글 표에는 작성자 번호만 적어 회원 표를 가리키게 하면, 작성자 이름은 한 곳에만 존재해 고칠 때도 한 번만 고치면 됩니다. 주문 데이터 역시 주문, 주문한 상품 항목, 상품을 따로 두고 주문 표에는 누가 언제 주문했는지만, 항목 표에는 어떤 상품을 몇 개 담았는지만 남기는 식으로 나눕니다.

정리하면 스키마 설계 실습은 실제 데이터를 보고 어떤 사실을 어느 표에 둘지 나누는 연습입니다. 한 값이 여러 곳에 중복되지 않게 나누고, 나뉜 표를 번호로 연결하는 습관이 핵심입니다.

명명 규칙과 스키마 관리

테이블·열 이름을 일관되게 짓는 규칙

표 이름이 user, Users, 회원, tbl_user처럼 제각각이면 새로 합류한 사람은 어느 것을 믿어야 할지 몰라 매번 물어보게 되고, 이름을 바꾸는 순간 이미 배포된 코드가 깨집니다. 명명 규칙(Naming Convention)은 표와 열의 이름을 짓는 약속을 문서로 고정해 두는 관리 방식이며, 스키마 관리의 일부입니다.

아파트 단지를 떠올려 보시면, 어떤 건물은 101동, 어떤 건물은 A동, 또 어떤 건물은 별관이라고 적혀 있으면 택배 기사가 같은 단지 안에서도 주소를 세 번 해석해야 합니다. 그래서 단지 전체가 숫자 동과 층과 호수로 통일된 표기법을 쓰면, 한 번만 읽어도 정확한 위치가 나옵니다. 데이터베이스도 표 이름은 소문자와 밑줄로, 열 이름은 의미가 드러나는 단어로, 주문과 회원을 잇는 열은 항상 같은 접미사를 붙이는 식으로 규칙을 정해 두면, 이름만 보고도 무엇을 담은 표인지 짐작할 수 있습니다.

정리하면 명명 규칙은 취향이 아니라 읽는 사람의 비용을 줄이는 계약이며, 스키마 관리란 그 계약을 문서와 변경 기록으로 유지하는 일입니다. 규칙을 먼저 정하고 나서 표를 만들면, 이름을 되돌리는 작업이 크게 줄어듭니다.

3부. 데이터 타입과 제약023

숫자 타입

INT·DECIMAL·FLOAT를 상황에 맞게 고르는 법

금액을 FLOAT로 저장해 두었다가 결제 합계가 원 단위에서 어긋나고, 회원 번호를 INT로 잡았다가 번호가 커지면서 더 이상 저장되지 않는 일이 벌어집니다. 숫자 타입(Numeric Type)을 상황에 맞게 고르는 일은 값을 담을 그릇의 모양과 크기를 미리 정하는 작업입니다.

택배를 보내는 상황을 떠올려 보시면, 작은 반지 하나에도 대형 이사 상자를 쓰면 배송비만 늘고, 반대로 큰 모니터를 봉투에 넣으면 상자가 찢어집니다. 그래서 물건에 맞는 상자를 고르듯, 셀 수 있는 개수나 번호에는 정수형(INT)을, 원 단위처럼 소수 오차가 있으면 안 되는 금액에는 고정 소수형(DECIMAL)을, 측정값처럼 근사치로 충분한 비율에는 부동 소수형(FLOAT)을 씁니다. 상자 크기에도 여유를 두어야 하듯 정수형은 담을 수 있는 범위가 정해져 있으므로, 늘어날 값을 감안해 범위를 고르고 금액에는 반올림 오차가 없는 타입을 고르는 것이 핵심입니다.

정리하면 숫자 타입 선택은 정확도가 필요한 값과 근사치로 충분한 값을 구분하는 판단입니다. 개수와 금액은 정확한 타입으로, 측정과 비율은 근사 타입으로 나누어 담는 것이 안전합니다.

문자열 타입

CHAR·VARCHAR·TEXT의 차이와 선택 기준

우편번호를 긴 문자열 칸에 넣어 두면 정해진 길이를 검사할 수 없어 앞자리 0이 사라진 값이 섞이고, 반대로 이름 칸을 고정 길이로 잡으면 긴 이름이 잘려 저장됩니다. 문자열 타입(Character Type)은 길이가 정해진 값과 길이가 변하는 값을 구분해 담는 그릇입니다.

우편물을 보내는 상황을 떠올려 보시면, 규격이 정해진 등기 봉투는 정해진 칸에만 주소를 적어 모든 봉투가 같은 크기로 쌓이고, 부피가 제각각인 물건은 내용물에 맞춰 늘어나는 포장지로 감쌉니다. 데이터베이스도 주민번호나 국가 코드처럼 길이가 항상 같은 값에는 고정 길이형(CHAR)을 쓰고, 이름이나 제목처럼 길이가 매번 다른 값에는 가변 길이형(VARCHAR)을 씁니다. 편지지처럼 아주 긴 글은 봉투가 아니라 별도의 긴 문서 보관함에 넣듯, 본문처럼 수천 자가 넘는 글은 긴 텍스트형(TEXT)으로 따로 담습니다.

정리하면 문자열 타입은 값의 최대 길이가 정해져 있는지, 매번 달라지는지를 기준으로 고르는 것입니다. 고정 길이는 CHAR, 가변 길이는 VARCHAR, 아주 긴 글은 TEXT로 나누어 담는 것이 기본 원칙입니다.

날짜와 시간 타입

DATE·DATETIME·TIMESTAMP의 차이와 시간대

배송 예정일을 '2026년 11월 12일'이라는 글자 그대로 저장해 두면, 그 값이 오늘보다 뒤인지 비교하거나 순서대로 정렬할 때마다 사람이 눈으로 읽어 판단해야 합니다. 게다가 서울에서 기록한 오후 3시와 런던에서 기록한 오후 3시가 같은 순간인지 구분할 수 없어 주문과 배송 기록이 뒤엉키는데, MySQL은 이 문제를 날짜와 시각 전용 타입으로 나누어 해결합니다. 택배 송장에 날짜만 적는 칸, 날짜와 시각을 함께 적는 칸, 그리고 전 세계 어느 지점에서든 같은 기준으로 환산해 읽는 칸이 따로 있다고 생각하면 이해가 쉽습니다.

DATE는 연월일만 담는 칸이라 '2026-11-12'처럼 시각 없이 배송 날짜만 기록할 때 씁니다. DATETIME은 연월일시분초를 적는 칸으로, 적어 넣은 시각을 시간대 정보 없이 그대로 보관하므로 한국 사무실의 벽시계 시간을 그대로 남기고 싶을 때 적합합니다. TIMESTAMP는 값을 세계 표준시(UTC)로 환산해 보관하고 조회하는 세션의 시간대에 맞춰 다시 보여 주는 칸이라, 여러 나라 지점이 같은 주문 시각을 각자의 현지 시간으로 보게 됩니다. 정리하면 DATE는 날짜만, DATETIME은 시간대 개념 없이 적힌 그대로의 날짜와 시각, TIMESTAMP는 세계 표준시 기준으로 저장되어 세션 시간대에 따라 표시가 바뀌는 값입니다. TIMESTAMP는 표현 범위가 1970년대부터 2038년까지로 좁고, 먼 미래의 날짜를 다뤄야 한다면 DATETIME이 안전하다는 점도 함께 기억해야 합니다.

문자 집합과 콜레이션

utf8mb4와 콜레이션이 정렬·비교에 미치는 영향

회원 이름에 이모지를 넣었더니 저장 단계에서 오류가 나고, 'Apple'과 'apple'이 서로 다른 값으로 취급되어 중복 가입이 막히지 않는 상황이 벌어질 수 있습니다. MySQL은 글자를 어떤 방식으로 저장할지 정하는 문자 집합(character set)과, 그 글자들을 어떤 순서로 비교하고 정렬할지 정하는 콜레이션(collation)을 따로 두어 이 두 문제를 나누어 다룹니다. 도서관에 책을 넣는 일에 비유하면, 문자 집합은 책 내용을 어떤 문자판으로 인쇄해 보관할지 정하는 규칙이고 콜레이션은 서가에 책을 어떤 순서로 꽂을지 정하는 규칙입니다.

utf8mb4는 한 글자를 최대 4바이트까지 담을 수 있는 문자 집합이라 이모지나 일부 특수 문자까지 저장할 수 있는 반면, 흔히 utf8이라고 부르는 3바이트 방식은 그런 글자를 담지 못해 오류를 냅니다.

콜레이션은 비교 규칙까지 정하는데, 대소문자를 무시하는 규칙을 쓰면 'Apple'과 'apple'이 같은 값으로 판정되어 중복 검사가 제대로 동작합니다. 다만 같은 문자열이라도 콜레이션이 다르면 비교 결과와 정렬 순서가 달라지므로, 조인하는 두 열의 콜레이션을 맞춰 두는 것이 좋습니다. 결국 문자 집합은 저장할 수 있는 글자의 범위를, 콜레이션은 비교와 정렬의 규칙을 결정하며, 요즘 새로 만드는 테이블에는 utf8mb4와 그에 맞는 콜레이션을 쓰는 것이 일반적입니다. 콜레이션을 바꾸면 인덱스를 다시 만들어야 할 수 있고 기존 데이터의 정렬 결과도 달라진다는 점은 미리 확인해야 합니다.

ENUM과 SET

정해진 값 목록을 열에 저장하는 방식

주문 상태를 '배송중', '배송 중', 'shipping'처럼 제각각 입력받으면 같은 상태인데도 통계가 갈라지고, 오타가 섞여 잘못된 값이 쌓입니다. MySQL은 열에 들어갈 수 있는 값을 미리 정해 두는 ENUM과 SET 타입으로 이 문제를 줄입니다. 회사 비품 신청서에 부서를 고르는 칸과, 복리후생 항목을 여러 개 체크하는 칸이 따로 있다고 생각하면 됩니다.

ENUM은 정해진 목록 중 하나만 고르는 칸이라 주문 상태나 성별처럼 값이 하나로 정해지는 항목에 쓰고, SET은 정해진 목록에서 여러 개를 동시에 고를 수 있는 칸이라 권한이나 관심 분야처럼 복수 선택이 필요한 항목에 씁니다.

두 타입 모두 목록에 없는 값을 넣으려 하면 오류를 내거나 빈 값으로 처리되므로 잘못된 입력이 원천적으로 줄어듭니다. 내부적으로는 각 값에 번호를 매겨 저장하므로 저장 공간이 작고 속도가 빠르지만, 목록에 새 값을 추가하려면 테이블 구조를 바꾸는 ALTER TABLE 작업이 필요합니다. 정리하면 ENUM은 허용된 값 중 하나를, SET은 허용된 값 중 여러 개를 저장하도록 제한하는 타입이며, 값의 일관성과 저장 효율을 얻는 대신 목록 변경이 번거롭다는 비용을 치릅니다. 값이 자주 바뀌거나 개수가 계속 늘어날 항목이라면 별도의 코드 테이블을 두는 편이 낫습니다.

JSON 열에 구조화된 데이터를 넣고 조회하는 법

상품마다 다른 옵션 정보를 담으려고 열을 계속 추가하다 보면 색상, 사이즈, 소재마다 빈 칸이 늘어나고, 새 옵션이 생길 때마다 테이블 구조를 고쳐야 합니다. MySQL의 JSON 타입은 이런 제각각인 부가 정보를 하나의 열 안에 구조를 가진 값으로 담게 해 줍니다. 택배 송장에 정해진 칸 외에 '배송 요청사항'을 적는 여백이 있고, 그 여백에 이름표와 값을 짝지어 적어 두면 나중에 필요한 값만 골라 읽을 수 있다고 생각하면 됩니다.

JSON 타입 열에는 {"color": "red", "size": "L"} 같은 값을 넣을 수 있어, 상품마다 다른 옵션을 표 구조 변경 없이 기록할 수 있습니다.

조회할 때는 JSON_EXTRACT 함수나 화살표 연산자로 특정 이름표의 값을 꺼내고, 화살표를 두 개 겹친 연산자를 쓰면 따옴표를 벗긴 값으로 꺼낼 수 있습니다. 자주 조회하는 값은 생성 열(generated column)로 뽑아 인덱스를 걸어 두면 매번 JSON 전체를 훑지 않아도 됩니다. 정리하면 JSON 타입은 스키마가 자주 달라지는 부가 정보를 유연하게 담는 수단이며, 값을 꺼내고 인덱스를 걸려면 전용 함수와 생성 열이 함께 필요합니다. 모든 데이터를 JSON으로 밀어 넣으면 정합성 검사와 조인에서 불리해지므로, 핵심 데이터는 일반 열로 두고 나머지만 JSON으로 담는 편이 좋습니다.

BLOB과 대용량 데이터

파일을 DB에 저장할 때의 장단점

계약서 PDF나 상품 사진을 서버 파일로만 보관하면, 서버를 옮기거나 백업을 맞출 때 DB에 있는 주문 기록과 파일이 따로 놀아 어느 쪽이 최신인지 알기 어려워집니다. MySQL은 이런 큰 이진 데이터를 BLOB이라는 타입으로 DB 안에 직접 담을 수 있게 해 줍니다. 창고에 물건 자체를 넣을지, 물건이 있는 위치를 적은 쪽지만 넣을지 고르는 상황과 비슷합니다.

BLOB(Binary Large Object)은 이미지나 문서 같은 이진 데이터를 그대로 저장하는 타입이고, 글자 데이터를 위한 TEXT와 달리 문자 집합 변환을 거치지 않습니다.

DB에 직접 넣으면 백업과 복구, 트랜잭션, 접근 권한을 한 곳에서 관리할 수 있다는 장점이 있지만, 데이터가 커질수록 DB 파일이 급격히 커지고 주고받는 양이 늘어 조회와 백업이 느려집니다. 그래서 큰 파일은 파일 시스템이나 오브젝트 스토리지에 두고 경로와 메타데이터만 DB에 저장하는 방식이 흔히 쓰입니다. 정리하면 BLOB은 이진 데이터를 DB 안에서 통합 관리할 수 있게 해 주지만 용량과 성능 부담을 함께 안고 갑니다. 파일 크기와 접근 패턴을 따져, 작고 트랜잭션 일관성이 중요한 데이터는 BLOB으로, 크고 자주 읽히는 파일은 외부 저장소로 나누는 판단이 필요합니다.

AUTO_INCREMENT

자동 증가 번호의 동작과 주의점

주문을 받을 때마다 사람이 주문 번호를 직접 세어 붙이면, 동시에 여러 건이 들어오는 순간 같은 번호가 두 번 나가거나 번호가 빠지는 일이 생깁니다. MySQL은 이런 고유 번호 매기기를 열에 자동으로 맡기는 AUTO_INCREMENT 기능을 제공합니다. 은행 입구의 번호표 발급기처럼, 테이블에 행을 하나 넣을 때마다 기계가 다음 번호를 하나씩 올려 발급한다고 생각하면 됩니다. AUTO_INCREMENT를 붙인 열은 값을 넣지 않아도 1부터 차례로 증가한 번호를 받고, 여러 클라이언트가 동시에 넣어도 서로 다른 번호를 받도록 처리됩니다.

방금 발급된 번호는 LAST_INSERT_ID() 함수로 확인하는데, 이 값은 접속 세션마다 따로 유지되어 다른 사람의 번호와 섞이지 않습니다. 다만 번호는 한 번 쓰면 되돌아오지 않아서, 행을 지우거나 입력을 롤백해도 그 번호는 다시 쓰이지 않고 빈 번호로 남습니다. 정리하면 AUTO_INCREMENT는 행을 넣을 때마다 유일한 정수 번호를 자동으로 매겨 주는 속성이며, 번호가 연속된다는 보장은 없습니다. 번호의 빈틈이 업무상 문제가 되는지 먼저 따져 보고, 순서가 꼭 필요한 값은 별도로 관리해야 합니다.

DEFAULT와 생성 열

기본값과 계산 열로 값을 자동 채우는 법

회원 명단을 관리하는데 가입일을 빠뜨리고 저장하는 사람이 하루에도 몇 명씩 생기면, 나중에 "언제 가입한 사람인지"를 아무도 알 수 없게 됩니다. 열마다 값을 채우는 규칙을 미리 정해 두고 싶을 때 쓰는 기능이 기본값(DEFAULT)과 생성 열(generated column)입니다.

아파트 관리 사무소를 떠올려 보면 이해가 쉽습니다. 입주 신청서를 받을 때 관리 사무소는 "신청 날짜" 칸이 비어 있으면 오늘 날짜를 자동으로 찍어 주고, 이사 날짜와 계약 기간이 적히면 "만료일" 칸을 사람이 계산하지 않아도 자동으로 채워 넣습니다.

여기서 신청 날짜 칸에 미리 세팅된 자동 날짜 도장이 기본값이고, 다른 칸의 값을 읽어 결과를 만드는 만료일 칸이 생성 열입니다. 기본값은 새 행을 넣을 때 그 열에 아무 값도 주지 않으면 대신 들어가는 값이고, 생성 열은 저장할 때마다 다른 열들을 참고해 계산된 결과가 자동으로 유지되는 열입니다. 다만 생성 열은 계산 결과를 저장해 두는 방식과 조회할 때마다 계산하는 방식이 버전에 따라 선택지가 다를 수 있으므로, 쓰려는 환경의 설명서를 확인하는 편이 안전합니다.

정리하면 DEFAULT는 값이 비었을 때 자동으로 채워지는 초기값을 정하는 것이고, 생성 열은 다른 열의 값으로부터 계산되는 파생 값을 열 차원에서 정의하는 것입니다. 두 기능 모두 "사람이 손으로 채우던 칸"을 데이터베이스가 대신 책임지게 만드는 장치입니다.

CHECK 제약

열 값의 범위를 DB 차원에서 검사하는 방법

쇼핑몰 재고 테이블에 수량이 -5로 들어가 있거나 나이 칸에 300살이 적혀 있으면, 그 뒤로 쌓이는 통계와 정산이 전부 어긋납니다. 프로그램 쪽에서 막으려 해도 다른 경로로 직접 입력하는 경우까지 다 통제하기는 어렵습니다.

아파트 경비실의 출입 규칙을 생각해 보면 비슷합니다. 경비실은 방문객 명부에 이름과 목적을 적게 하면서 "이 건물은 1호부터 20호까지만 있고, 방문 시간은 새벽 6시부터 밤 10시까지"라는 규칙을 문 앞에 붙여 둡니다.

규칙에 맞지 않는 기록은 명부에 아예 적히지 않고, 어느 출입구로 들어오든 같은 규칙이 적용됩니다. CHECK 제약도 똑같이, 열에 들어올 수 있는 값의 조건을 테이블 정의에 못 박아 두고 조건을 만족하지 않는 행은 저장 자체를 거부합니다. 예를 들어 수량은 0 이상이어야 한다거나 상태 값은 정해진 목록 중 하나여야 한다는 식으로 적어 둘 수 있습니다. 이 검사는 데이터를 넣거나 고치는 모든 경로에서 동일하게 동작하므로, 애플리케이션이 몇 개로 늘어나도 규칙이 흔들리지 않습니다.

결국 CHECK 제약은 열 값이 지켜야 할 범위나 조건을 데이터베이스 차원에서 선언하고, 위반하는 입력을 저장 단계에서 거부하는 안전장치입니다. 규칙을 코드가 아니라 데이터 구조 자체에 새겨 두는 셈입니다.

SELECT 기본 문법

원하는 열만 골라 조회하는 가장 기본형

수십 개 열이 있는 회원 테이블을 통째로 조회하면 화면에는 필요 없는 개인정보까지 잔뜩 뜨고, 정작 필요한 이름과 연락처는 스크롤을 한참 내려야 보입니다. 원하는 열만 골라서 보는 방법이 없으면 데이터를 볼 때마다 시간이 낭비됩니다.

택배 송장을 떠올려 보면 딱 맞습니다. 창고에 있는 물건 정보 전체를 다 보여 주는 대신, 송장에는 받는 사람 이름과 주소, 운송장 번호처럼 배송에 필요한 항목만 인쇄합니다. SELECT도 이와 같아서, 어떤 테이블에서 볼지 정하고 그다음에 필요한 열 이름을 콤마로 나열하면 그 열들만 결과로 나옵니다.

모든 열이 필요할 때는 별표를 쓰는 대신 열을 하나하나 적는 습관이 나중에 테이블 구조가 바뀌었을 때 결과가 흔들리지 않게 해 줍니다. 조회 결과의 열 이름은 AS를 붙여 보기 좋은 이름으로 바꿀 수도 있어서, 영문 열 이름을 한글 제목으로 보여 주고 싶을 때 유용합니다.

정리하면 SELECT는 데이터베이스에 "이 테이블에서 이 열들만 달라"라고 요청하는 문장이고, FROM은 그 대상 테이블을 가리킵니다. 조회의 출발점이 되는 가장 기본형이며, 뒤에 조건이나 정렬을 붙여 점점 정교해집니다.

4부. 기본 SQL — 조회034

WHERE 조건절

비교·논리 연산자로 행을 걸러내는 법

회원이 백만 명인 서비스에서 "지난달에 가입한 사람만" 보고 싶은데 전체 명단이 매번 그대로 나오면, 눈으로 걸러내는 일을 사람이 하게 됩니다. 조건에 맞는 행만 골라 오는 기능이 없으면 데이터가 늘어날수록 조회는 쓸모없어집니다.

도서관 사서를 떠올려 보면 이해가 쉽습니다. 서가 전체를 뒤지는 대신 "2010년 이후에 나온 책 중에서 저자가 김 씨인 것"처럼 조건을 정해 목록을 뽑습니다. WHERE 절도 똑같이, 열 값과 기준 값을 비교하는 조건을 적으면 그 조건을 만족하는 행만 결과에 남습니다.

크다·작다·같다 같은 비교 연산자와, 여러 조건을 동시에 만족시키는 AND, 둘 중 하나만 만족해도 되는 OR, 조건을 뒤집는 NOT을 조합해 원하는 범위를 좁혀 갑니다. 여기서 주의할 점은 NULL(값이 비어 있음을 나타내는 상태)은 보통의 같다 비교로는 걸리지 않아서 IS NULL처럼 따로 다뤄야 한다는 것입니다.

결국 WHERE는 조회 결과에서 어떤 행을 남길지 결정하는 필터입니다. SELECT가 열을 고르는 일이라면 WHERE는 행을 고르는 일이며, 두 가지를 함께 써야 원하는 데이터 조각만 정확히 꺼낼 수 있습니다.

4부. 기본 SQL — 조회035

ORDER BY 정렬

결과를 원하는 순서로 정렬하는 방법

게시판 글 목록이 입력된 순서 그대로 뒤죽박죽 나오면, 방금 올라온 글이 어디 있는지 찾느라 한참 헤매게 됩니다. 데이터베이스는 원하는 순서를 따로 지정하지 않으면 순서를 보장하지 않기 때문에, 정렬을 직접 요청해야 합니다.

택배 회사 창고의 분류 작업을 생각해 보면 비슷합니다. 물건을 아무렇게나 쌓아 두면 찾기 어렵지만, "도착 예정일이 빠른 것부터, 같은 날짜면 우편번호 순으로"처럼 기준을 정해 줄을 세우면 바로 꺼낼 수 있습니다.

ORDER BY도 기준 열을 적고 오름차순(ASC, 작은 값에서 큰 값으로)인지 내림차순(DESC, 큰 값에서 작은 값으로)인지 지정하면 그 순서대로 결과를 늘어놓습니다. 기준을 여러 개 적으면 앞의 기준이 같은 값일 때 뒤의 기준이 차례로 적용되므로, 정렬이 애매하게 흔들리는 일을 막을 수 있습니다. 또한 문자 정렬은 대소문자나 언어 설정에 따라 결과가 달라질 수 있어, 한글 정렬 순서 같은 부분은 환경을 확인하는 편이 좋습니다.

정리하면 ORDER BY는 조회 결과의 행 순서를 지정하는 절입니다. WHERE가 남길 행을 고르는 일이라면 ORDER BY는 남은 행을 어떤 순서로 늘어놓을지 정하는 일이며, 이 둘을 함께 써야 화면에 보여 줄 목록이 의도대로 정돈됩니다.

LIMIT과 페이징

앞에서 몇 개만 가져오는 법과 페이지 나누기

회원이 수십만 명인 서비스에서 목록 화면을 열 때마다 전체 명단을 다 불러오면 화면이 몇 초씩 멈추고 서버도 금세 지칩니다. 처음 몇 개만 보여 주고 나머지는 다음 장으로 넘기는 방식이 필요합니다.

두꺼운 전화번호부를 넘겨 보는 장면을 떠올려 보면 이해가 쉽습니다.

한 번에 책 전체를 펼쳐 놓는 대신 한 장에 정해진 줄 수만큼만 보여 주고, 다음 장을 볼 때는 앞에서 읽은 만큼을 건너뛰고 이어서 봅니다. LIMIT은 "몇 줄만 보여 달라"고 개수를 정하는 부분이고, 건너뛸 개수를 함께 적으면 그만큼을 지나친 지점부터 가져옵니다. 예를 들어 페이지당 10개씩 보여 준다면 첫 페이지는 건너뛸 개수 0에 10개, 두 번째 페이지는 10개를 건너뛰고 10개를 요청하는 식입니다. 다만 같은 순서를 보장하려면 ORDER BY를 반드시 함께 써야 하며, 건너뛸 개수가 아주 커지면 뒤쪽 페이지의 조회가 느려질 수 있다는 점은 환경에 따라 차이가 있습니다.

결국 LIMIT은 결과에서 가져올 행의 개수를 제한하는 절이고, 여기에 건너뛸 개수를 조합하면 페이지 나누기가 완성됩니다. 전체를 다 보여 주는 대신 필요한 만큼만 잘라 오는 것이 핵심입니다.

DISTINCT 중복 제거

같은 값을 한 번만 보여주는 방법

쇼핑몰 주문 표에서 "주문이 들어온 도시" 목록만 뽑으려는데 같은 도시 이름이 수백 줄씩 반복되어 정작 어떤 도시가 있는지는 알아보기 어렵습니다. 이때 SELECT 문에 DISTINCT를 붙이면 조회 결과에서 똑같은 행을 하나로 접어, 값의 종류만 남겨 줍니다.

아파트 경비실의 차량 출입 대장을 떠올려 보면 이해가 쉽습니다.

대장에는 같은 차가 하루에도 여러 번 적히지만, 경비원이 "오늘 어떤 차들이 들어왔나"를 확인할 때는 차량 번호별로 한 줄씩만 추려 봅니다. DISTINCT도 이와 똑같이 SELECT가 만들어 낸 결과 전체를 훑으면서, 모든 열의 값이 완전히 동일한 행만 하나로 합칩니다. 그래서 도시와 함께 가입일까지 두 열을 지정하면, 도시가 같아도 가입일이 다르면 서로 다른 행으로 남습니다. 즉 중복 여부는 개별 값이 아니라 행 단위의 값 조합으로 판단합니다.

정리하면 DISTINCT는 조회 결과 집합에서 값의 조합이 같은 행을 하나만 남기는 연산입니다. 중복 제거는 데이터를 가져온 뒤에 일어나므로, 정말 필요한 열만 골라야 원하는 단위로 종류를 셀 수 있습니다.

산술·문자열 함수

계산과 문자열 가공을 SQL 안에서 처리하기

주문 표에는 단가와 수량이 따로 저장되어 있을 뿐 총액 칸은 없어서, 화면을 만들 때마다 프로그램 코드로 곱셈을 다시 구현해야 합니다. 이름과 성이 나뉘어 저장된 값을 붙여 보여주는 일도 마찬가지로 번거롭습니다. 산술 함수와 문자열 함수는 이런 계산과 가공을 SQL 문 안에서 바로 처리해 주는 도구입니다.

편의점 계산대를 떠올려 보면 비유가 됩니다.

진열대의 상품에는 단가표만 붙어 있지만, 점원은 수량을 곱해 총액을 말하고 봉투에 이름표를 붙여 줍니다. 산술 함수는 더하기·빼기·곱하기·나누기와 나머지를 구하는 연산자로 총액 같은 새 값을 만들고, 문자열 함수는 CONCAT으로 두 문자열을 이어 붙이고 SUBSTRING으로 일부를 잘라내며 UPPER·LOWER로 대소문자를 바꿉니다. 앞뒤 공백을 지우는 TRIM이나 글자 수를 세는 LENGTH도 같은 계열입니다. 이 함수들은 값을 바꿔 저장하는 것이 아니라 조회하는 그 순간에만 계산된 결과를 돌려줍니다.

결국 산술 함수는 숫자 열로 새 값을 계산하고 문자열 함수는 문자 데이터를 원하는 모양으로 다듬는 기능입니다. 계산 규칙이 SQL 안에 한 번만 적히므로 화면과 보고서가 같은 결과를 보게 됩니다.

날짜 함수

날짜를 더하고 빼고 형식으로 바꾸는 법

회원 가입일에서 30일 뒤의 만료일을 구하거나, 저장된 날짜를 "2026년 11월" 같은 형태로 보여주려면 매번 프로그램 코드에서 날짜를 계산해야 합니다. 달력은 윤년과 월말이 얽혀 있어서 직접 계산하면 실수가 잦습니다. 날짜 함수는 이런 날짜 연산과 형식 변환을 데이터베이스 안에서 처리해 줍니다.

헬스장 회원권을 떠올려 보면 구조가 잘 보입니다.

회원이 등록한 날짜에 도장을 찍고, 정해진 이용 기간을 더해 만료일을 자동으로 적어 두면 직원이 달력을 넘겨 세지 않아도 됩니다. DATE_ADD는 날짜에 일정 기간을 더하고 DATE_SUB는 빼며, DATEDIFF는 두 날짜 사이의 일수 차이를 계산합니다. DATE_FORMAT은 날짜를 원하는 표기 형태의 문자열로 바꾸고, NOW나 CURDATE는 현재 시각과 오늘 날짜를 가져옵니다. 이렇게 계산된 결과 역시 저장된 값을 바꾸지 않고 조회 시점에만 만들어집니다.

정리하면 날짜 함수는 날짜에 기간을 더하고 빼는 연산과 표기 형식 변환을 맡는 기능입니다. 달력 계산의 복잡한 예외를 데이터베이스가 대신 처리하므로 결과가 일관되게 유지됩니다.

NULL 처리 함수

IFNULL·COALESCE로 빈 값을 다루는 법

주문서의 요청 사항 칸이 비어 있는 채로 저장되면, 화면에는 아무것도 나오지 않거나 계산 결과 전체가 비어 버리는 일이 생깁니다. NULL은 0도 빈 문자열도 아닌 "값이 정해지지 않았다"는 상태라서, 이것이 섞이면 산술 연산의 결과까지 NULL이 됩니다. IFNULL과 COALESCE는 이런 빈 값을 다루기 위한 함수입니다.

택배 송장 작성을 떠올려 보면 이해가 쉽습니다.

요청 사항이 비어 있는 송장에는 직원이 "없음" 도장을 찍어 빈칸을 남기지 않습니다. IFNULL은 한 값이 NULL이면 대신 넣을 값을 지정해 그 자리를 채우고, COALESCE는 여러 값 중에서 처음으로 NULL이 아닌 값을 골라 돌려줍니다. 이렇게 채운 값은 조회 결과에만 나타나며 원본 데이터가 바뀌지는 않습니다. 다만 NULL은 크기 비교나 등호 비교로 판별되지 않으므로, 조건을 걸 때는 IS NULL이나 IS NOT NULL을 따로 써야 합니다.

결국 NULL 처리 함수는 값이 비어 있을 때 보여 줄 대체 값을 정하는 장치입니다. 빈칸을 그대로 두면 계산이 무너지기 때문에, 화면에 내보내기 전에 어떤 값으로 채울지 정하는 습관이 중요합니다.

CASE 표현식

조건에 따라 다른 값을 돌려주는 분기

같은 표에 담긴 값이라도 금액대나 등급에 따라 다르게 표시해야 할 때가 많습니다. 이 판단을 프로그램 코드에 흩어 두면 조건이 바뀔 때마다 여러 곳을 고쳐야 합니다. CASE 표현식은 조건에 따라 다른 값을 돌려주는 분기를 SQL 문 안에서 직접 처리합니다.

택배 요금표를 떠올려 보면 비유가 됩니다.

창구 직원은 무게를 재 보고 "5킬로그램 미만이면 기본 요금, 그보다 무거우면 추가 요금"이라는 표를 보고 요금을 정합니다. CASE는 WHEN 절에 조건을 적고 THEN 절에 그 조건이 맞을 때 돌려줄 값을 적으며, 어느 조건에도 맞지 않을 때는 ELSE 절의 값이 쓰입니다. 위에서부터 차례로 조건을 검사해 처음 맞는 가지만 실행하므로, 조건을 적는 순서가 결과를 좌우합니다. 모든 WHEN이 빗나가고 ELSE도 없으면 결과는 NULL이 됩니다.

정리하면 CASE 표현식은 여러 조건을 순서대로 검사해 값 하나를 선택하는 분기 구조입니다. 판단 규칙이 조회 문 안에 모여 있으므로 조건이 바뀌어도 한 곳만 고치면 됩니다.

집계 함수

COUNT·SUM·AVG로 여러 행을 하나로 요약하기

주문이 하루에 수만 건씩 쌓이면, 전체 매출이 얼마인지 주문이 몇 건인지 사람이 하나씩 세어 볼 수 없습니다. 행을 그대로 나열하는 조회만으로는 규모를 파악하기 어렵습니다. 집계 함수는 여러 행의 값을 하나의 요약 값으로 접어 주는 기능입니다.

반장이 영수증 더미를 정리하는 모습을 떠올려 보면 이해가 쉽습니다. 영수증 장수를 세면 주문 건수가 되고, 금액을 모두 더하면 매출 합계가 되며, 더한 값을 장수로 나누면 평균이 됩니다.

COUNT는 행의 개수를, SUM은 값의 합계를, AVG는 평균을 구하고 MAX와 MIN은 가장 큰 값과 작은 값을 찾습니다. 이때 COUNT(*)는 행 자체를 세지만 COUNT(열)과 AVG는 NULL인 행을 빼고 계산하므로, 빈 값이 많으면 두 결과가 달라질 수 있습니다. 여러 행을 하나로 접는 연산이므로 다른 열을 함께 보려면 GROUP BY로 묶는 기준을 정해야 합니다.

결국 집계 함수는 많은 행을 세고 더하고 평균 내어 하나의 요약 값으로 바꾸는 도구입니다. 어떤 함수가 NULL을 어떻게 다루는지 알아야 숫자가 어긋나지 않습니다.

GROUP BY 그룹화

기준별로 묶어 집계하는 방법

온라인 쇼핑몰에서 지난달 주문 목록을 받았는데 주문이 수천 건이라, 지역별로 몇 건씩 팔렸는지 눈으로 셀 수 없는 상황을 생각해 보겠습니다. 이때 주문 하나하나를 보지 않고 같은 기준끼리 묶어 한 줄로 요약해 주는 기능이 바로 GROUP BY(그룹화)입니다.

아파트 관리사무소에서 택배를 동별로 나눠 놓는 상황을 떠올리면 이해가 쉽습니다. 택배기사가 상자마다 붙은 동 번호를 보고 101동 상자는 101동 칸에, 102동 상자는 102동 칸에 넣으면, 칸마다 상자가 몇 개인지 세기만 하면 됩니다.

데이터베이스도 GROUP BY 뒤에 적은 열의 값이 같은 행들을 한 칸으로 모으고, 그 칸마다 COUNT나 SUM 같은 집계 함수로 개수나 합계를 계산합니다. 이때 SELECT에 적는 열은 보통 묶는 기준이 된 열과 집계 결과뿐이며, 기준에 넣지 않은 열을 그대로 꺼내면 어느 행의 값을 보여줄지 정할 수 없어 오류가 납니다.

정리하면 GROUP BY는 행을 기준 값이 같은 것끼리 묶고 묶음마다 집계 함수를 적용해 요약표를 만드는 문법입니다. 원본 행은 그대로 두고, 보는 사람이 필요한 단위로 다시 접어서 보여주는 도구입니다.

4부. 기본 SQL — 조회044

HAVING 절

그룹 결과에 조건을 거는 법

지역별 주문 건수를 GROUP BY로 뽑았더니 결과가 수십 줄이라, 그중 주문이 많은 지역만 보고 싶은 상황을 생각해 보겠습니다. 이렇게 묶인 결과 전체에 조건을 걸어 걸러내는 절이 HAVING입니다.

택배 분류대를 다시 비유로 들면, 동별로 상자를 나눈 뒤 이번에는 상자가 다섯 개 이상 쌓인 칸만 창고로 옮기기로 정하는 단계가 HAVING에 해당합니다.

WHERE는 상자를 칸에 넣기 전에 상자 하나하나를 검사해 걸러내고, HAVING은 칸에 다 모으고 개수를 센 다음 그 칸 전체를 놓고 조건을 봅니다. 그래서 COUNT(*)처럼 묶은 뒤에야 나오는 값에 조건을 걸려면 반드시 HAVING을 써야 합니다. 실행 순서도 WHERE가 먼저, 그룹화가 다음, HAVING이 그 뒤라서 두 조건의 자리가 섞이면 원하는 결과가 나오지 않습니다.

결국 HAVING은 GROUP BY로 만들어진 그룹 결과에 조건을 거는 절이고, WHERE는 그룹화 전의 개별 행에 조건을 거는 절입니다. 집계 값에 조건을 걸 때는 HAVING, 원본 행을 걸러낼 때는 WHERE라고 구분하면 됩니다.

주문 100건의 평균 금액을 구했는데 실제로는 금액이 비어 있는 주문이 섞여 있어서 결과가 예상과 다르게 나오는 일이 생깁니다. 이때 COUNT, SUM, AVG 같은 집계 함수가 NULL(값이 없음)을 어떻게 다루는지 알면 이런 혼란을 피할 수 있습니다.

출석부에 이름은 있는데 서명 칸이 비어 있는 학생들을 떠올리면 이해가 쉽습니다. 선생님이 서명한 사람 수를 세면 빈칸은 자연히 빠지고, 서명 점수 합계도 빈칸을 0점으로 치지 않고 아예 세지 않습니다.

정리하면 COUNT(열), SUM, AVG는 NULL을 제외하고 계산하고, COUNT(*)만 NULL과 무관하게 행 수를 셉니다. AVG가 빈칸을 0으로 치지 않는다는 점을 기억하면 평균이 왜 다르게 나오는지 설명할 수 있습니다.

INSERT 문

한 행과 여러 행을 추가하는 문법

회원 명단을 관리하는데 새로 가입한 사람 정보를 표에 끼워 넣을 방법이 없다면, 매번 표 전체를 다시 만들거나 파일을 새로 저장해야 할 것입니다. 그래서 테이블에 행을 추가하는 전용 문법인 INSERT 문이 필요합니다.

택배 접수대에서 새 택배가 올 때마다 접수 장부의 다음 줄에 보내는 사람, 받는 사람, 주소를 적는 모습을 떠올리면 됩니다.

INSERT INTO 테이블 이름 뒤에 열 목록을 적고 VALUES에 그 순서대로 값을 채우면 한 행이 새 줄로 들어갑니다. 한 번에 여러 행을 넣고 싶으면 VALUES 뒤에 괄호 묶음을 쉼표로 이어 붙이면 되고, 이렇게 하면 행마다 문장을 반복하는 것보다 훨씬 빠릅니다. 열 목록을 생략할 수도 있지만 그러면 테이블에 정의된 열 순서를 그대로 따라야 하므로, 순서가 바뀌어도 안전하도록 열 이름을 적는 편이 좋습니다.

정리하면 INSERT는 테이블에 새로운 행을 추가하는 문장이며, 한 행이든 여러 행이든 VALUES로 값을 지정해 넣습니다. 넣는 값의 개수와 형식이 열 정의와 맞아야 하고, 기본키처럼 중복을 허용하지 않는 열의 값은 겹치지 않게 해야 합니다.

UPDATE 문

회원 수천 명의 주소가 바뀌었는데 한 사람씩 찾아 고치려면 며칠이 걸릴 것입니다. 조건에 맞는 행의 값만 골라 바꾸는 UPDATE 문이 없으면 이런 작업은 사실상 불가능합니다.

아파트 관리사무소에서 입주민 명부의 전화번호를 새 번호로 바꾸는 일을 생각해 보면 비슷합니다.

UPDATE 테이블 이름 SET 열 = 새 값 형태로 무엇을 바꿀지 적고, WHERE로 어느 줄을 바꿀지 지정하면 그 조건에 맞는 행만 새 값으로 갱신됩니다. 여러 열을 동시에 바꾸려면 SET 뒤에 쉼표로 이어 적으면 되고, 이때 WHERE에 적은 조건은 바꾸기 전의 값으로 평가됩니다. 가장 조심할 점은 WHERE를 빠뜨리는 경우인데, 그러면 명부 전체의 그 열이 같은 값으로 덮여 버립니다.

정리하면 UPDATE는 SET으로 바꿀 값을 정하고 WHERE로 대상 행을 좁혀서, 조건에 맞는 행만 수정하는 문장입니다. 실행 전에 같은 WHERE로 SELECT를 먼저 돌려 대상 행을 확인하는 습관이 사고를 막습니다.

DELETE 문

행을 지우는 법과 실수 방지 습관

잘못 입력한 주문 기록을 지우려고 WHERE 없이 문장을 실행했다가 테이블의 모든 행이 사라지는 사고가 실제로 자주 일어납니다. 그래서 행을 지우는 DELETE 문은 무엇을 지울지 정확히 지정하는 절차와 함께 익혀야 합니다.

창고에서 유통기한이 지난 상자만 골라 버리는 작업을 떠올리면 이해가 쉽습니다.

DELETE FROM 테이블 이름 WHERE 조건 형태에서 WHERE는 어떤 상자를 버릴지 정하는 기준이고, 조건에 맞는 행만 삭제됩니다.

조건을 적지 않으면 창고 전체를 비우는 것과 같아서 모든 행이 지워지므로, 지우기 전에 같은 조건으로 SELECT를 실행해 몇 건인지 세어 보는 것이 안전합니다. 또한 삭제는 되돌리기 어려우므로 중요한 데이터는 미리 백업하거나, 표시만 해 두고 조회에서 숨기는 방식을 함께 고려합니다.

정리하면 DELETE는 WHERE 조건에 맞는 행을 테이블에서 제거하는 문장이고, 조건이 없으면 전체 행이 대상이 됩니다. 지우기 전에 조회로 대상을 확인하고 백업을 남기는 습관이 DELETE 사고를 막는 핵심입니다.

INSERT ... SELECT와 UPSERT

조회 결과를 넣고 중복 시 갱신하는 법

회원 데이터를 정리하다 보면 다른 표에 있는 값을 이 표로 옮겨야 할 때가 있는데, 행이 수만 건만 되어도 하나씩 넣는 반복문은 몇 시간씩 걸립니다. 게다가 이미 있는 키와 같은 값이 들어오면 중복 오류로 작업이 멈춰 버려서, 넣기 전에 존재 여부를 매번 확인하는 코드를 따로 짜야 합니다.

창고를 하나 떠올려 보면 INSERT ... SELECT는 옆 창고의 재고 목록을 통째로 복사해 우리 창고 선반에 그대로 꽂는 작업입니다. 목록을 한 장씩 들고 오는 대신 한 번에 가져오므로 왕복이 줄고 속도가 붙습니다.

UPSERT(있으면 갱신, 없으면 삽입)는 여기에 규칙을 하나 더한 것으로, 이미 같은 자리에 물건이 있으면 새로 쌓지 않고 라벨만 최신 정보로 바꿔 답니다. MySQL에서는 ON DUPLICATE KEY UPDATE를 붙여 이 동작을 만들고, 중복을 판단하는 기준은 기본키나 유니크 인덱스(값이 겹치지 않게 보장하는 색인)입니다.

정리하면 INSERT ... SELECT는 조회 결과를 곧바로 다른 표에 대량으로 넣는 문장이고, UPSERT는 같은 문장에 중복 처리 규칙을 붙여 삽입과 갱신을 한 번에 끝내는 방식입니다. 덕분에 옮길 데이터가 많거나 같은 작업을 여러 번 돌려야 하는 상황에서도 코드가 짧아지고 결과가 예측 가능해집니다.

트랜잭션이란 무엇인가

여러 작업을 하나로 묶는 이유

계좌 이체를 생각해 보면 출금은 기록됐는데 입금 직전에 서버가 꺼지는 순간 돈이 사라진 것처럼 보이고, 반대로 입금만 두 번 기록될 수도 있습니다. 이렇게 두 개 이상의 변경이 따로 놀면 데이터는 쉽게 어긋나는데, 그것을 하나의 작업으로 묶어 주는 장치가 트랜잭션(transaction)입니다.

이삿짐을 옮기는 일에 빗대면, 트랜잭션은 소파 하나가 아니라 한 건의 이사 전체를 하나의 작업 단위로 삼는 것입니다. 소파를 실었는데 트럭이 고장 나면 소파만 새집에 두고 나머지를 옛집에 남기지 않고, 싣기 전 상태로 전부 되돌립니다.

작업을 시작할 때 BEGIN 또는 START TRANSACTION으로 단위를 열고, 그 안의 변경은 확정 전까지 다른 사람에게 완성된 값으로 보이지 않습니다. 단위 안의 어느 한 단계라도 실패하면 앞서 처리한 일까지 모두 취소되고, 전부 성공했을 때만 한꺼번에 반영됩니다.

즉 트랜잭션은 여러 SQL 문을 하나의 논리적 작업으로 묶어 전부 성공 아니면 전부 실패로 끝나게 하는 경계입니다. 이 경계가 있어야 데이터가 중간 상태로 어긋난 채 남는 사고를 막을 수 있습니다.

COMMIT과 ROLLBACK

변경을 확정하고 되돌리는 법

트랜잭션을 열어 놓고 확정도 취소도 하지 않으면 그 변경이 계속 임시 상태로 남아 잠금이 풀리지 않고, 다른 사람은 하염없이 기다리게 됩니다. 반대로 실수로 행을 지웠을 때 되돌릴 수단이 없다면 작은 오타 하나가 큰 사고가 됩니다.

문서를 쓰는 일에 빗대면 트랜잭션은 편집 화면을 열어 놓는 것이고, COMMIT(확정)은 저장 버튼, ROLLBACK(되돌리기)은 실행 취소 버튼입니다. 저장을 누르기 전까지 편집 내용은 내 화면에만 있고, 저장을 누르는 순간 비로소 파일이 바뀝니다.

ROLLBACK은 저장 전에 한 편집을 통째로 버리는 동작이라, 잘못 지운 줄을 되살릴 수 있습니다. 또한 두 명령 중 하나를 실행해야 트랜잭션이 닫히고 그동안 잡고 있던 잠금이 풀려서, 다른 세션(데이터베이스에 접속한 연결 하나)이 막히지 않습니다.

정리하면 COMMIT은 트랜잭션 안의 변경을 영구히 확정하고, ROLLBACK은 그 변경을 모두 취소해 시작 전 상태로 돌립니다. 두 명령을 제때 호출하는 습관이 데이터의 정확성과 동시 처리 능력을 함께 지켜 줍니다.

ACID 특성

원자성·일관성·고립성·지속성의 의미

트랜잭션으로 작업을 묶었다고 해도, 도중에 전원이 나가거나 두 사람이 같은 잔액을 동시에 읽으면 묶은 의미가 사라집니다. 그래서 데이터베이스는 트랜잭션에 지켜야 할 네 가지 약속을 걸어 두었고, 그 머리글자를 딴 것이 ACID입니다.

아파트 관리사무소의 관리비 장부를 떠올려 보면, 원자성(Atomicity)은 한 세대의 입금 기록과 잔액 갱신이 반드시 함께 처리되는 성질입니다. 일관성(Consistency)은 처리가 끝난 뒤에도 장부 합계와 실제 통장 잔액이 어긋나지 않도록 정해 둔 규칙이 지켜지는 성질입니다. 고립성(Isolation)은 두 직원이 같은 세대의 장부를 동시에 고치지 못하게 한 사람씩 순서를 지키는 성질이고, 지속성(Durability)은 도장까지 찍어 확정한 기록이 정전이나 사고 뒤에도 그대로 남는 성질입니다.

데이터베이스는 이 네 가지를 트랜잭션(여러 작업을 하나로 묶는 단위)마다 확인하고, 어느 하나라도 깨질 것 같으면 작업을 중단합니다.

결국 ACID는 전부 반영 아니면 전부 취소, 규칙 유지, 동시 작업의 간섭 차단, 확정된 결과의 보존이라는 네 가지 약속을 뜻합니다. 이 약속 덕분에 은행 이체나 주문, 재고처럼 틀리면 곤란한 업무를 데이터베이스에 맡길 수 있습니다.

격리 수준(Isolation Level)

네 가지 격리 수준과 각각의 부작용

여러 사람이 같은 표를 동시에 읽고 쓰면 아직 확정되지 않은 값을 읽거나, 같은 값을 두 번 읽었는데 결과가 달라지는 일이 생깁니다. 이런 간섭을 어디까지 허용할지 미리 정해 둔 단계가 격리 수준(Isolation Level)입니다.

문서를 여럿이 함께 고치는 상황에 빗대면, 격리 수준은 아직 저장하지 않은 타이핑까지 보여 줄지, 저장된 것만 보여 줄지, 아니면 한 사람씩만 손대게 할지를 정하는 규칙입니다. 가장 느슨한 READ UNCOMMITTED는 남의 미완성 문장까지 읽히는 dirty read를 허용하고, READ COMMITTED는 확정된 내용만 보여 주지만 다시 읽을 때 내용이 달라지는 non-repeatable read가 남습니다. MySQL InnoDB의 기본값인 REPEATABLE READ는 읽기 시작한 시점의 내용을 고정해 그 문제를 줄이며, 새 행이 끼어드는 phantom read는 갭 잠금(gap lock)으로 함께 막는 경우가 많습니다. 가장 엄격한 SERIALIZABLE은 작업을 사실상 한 줄로 세워 부작용을 없애는 대신 동시 처리 능력이 크게 떨어집니다.

정리하면 격리 수준은 동시에 도는 트랜잭션 사이의 간섭을 어디까지 허용할지 고르는 네 단계의 눈금입니다. 정확성이 더 중요하면 높은 수준을, 처리량이 더 중요하면 낮은 수준을 골라 균형을 맞춥니다.

잠금(Lock)의 종류

행 잠금과 테이블 잠금이 충돌하는 방식

두 사람이 같은 행을 동시에 고치면 나중에 저장한 값이 먼저 저장한 값을 소리 없이 덮어써서, 한쪽의 수정은 흔적도 없이 사라집니다. 이런 덮어쓰기를 막으려고 데이터베이스는 작업 중인 대상을 다른 작업이 건드리지 못하게 표시하는데, 그것이 잠금(Lock)입니다.

화장실에 빗대면 행 잠금(row lock)은 칸 하나의 문을 잠그는 것이라, 다른 사람은 그 칸만 피해서 다른 칸을 쓸 수 있습니다. 테이블 잠금(table lock)은 화장실 입구의 문을 통째로 잠그는 것이라, 한 사람이 들어가면 나머지 전부가 문 앞에서 기다립니다.

MySQL InnoDB는 행 단위 잠금을 기본으로 쓰고, 여러 행을 건드리는 UPDATE나 SELECT ... FOR UPDATE에서 그 행들에 잠금을 겁니다. 두 트랜잭션이 서로가 잡은 행을 기다리면 어느 쪽도 끝나지 않는 교착(deadlock)이 생기는데, MySQL은 이때 한쪽을 골라 강제로 롤백해 풉니다.

결국 잠금은 같은 데이터를 동시에 건드리지 못하게 범위를 나눠 표시하는 장치이고, 행 잠금은 정밀하지만 관리 비용이, 테이블 잠금은 단순하지만 대기 비용이 큽니다. 잠금 범위를 좁게 유지하고 트랜잭션을 짧게 끝내는 것이 충돌과 교착을 줄이는 길입니다.

교착 상태(Deadlock)

두 트랜잭션이 서로를 기다리다 막히는 상황

두 사람이 서로의 물건을 들고 있으면서 상대가 먼저 내려놓기만 기다리면, 둘 다 영원히 그 자리에 서 있게 됩니다. 데이터베이스에서도 두 작업이 서로가 잡고 있는 자원을 기다리다 아무것도 하지 못하는 상황이 생기는데, 이것이 교착 상태(Deadlock)입니다. 이사하는 날 두 세입자가 좁은 복도에서 각자 큰 짐을 하나씩 들고 마주친 장면을 떠올려 보겠습니다. 두 사람 모두 자기 짐을 먼저 내려놓아야 지나갈 수 있는데, 상대가 내려놓기만 기다린다면 복도는 그대로 막혀 버립니다.

여기서 짐은 데이터베이스의 행(Row)이고, 두 세입자는 그 행을 잠근 채 붙잡고 있는 트랜잭션(Transaction)입니다. 한 트랜잭션이 A 행을 잠근 뒤 B 행을 요청하고 다른 트랜잭션이 B 행을 잠근 뒤 A 행을 요청하면, 서로가 서로의 잠금이 풀리기만 기다리는 고리가 만들어집니다. 정리하면 교착 상태는 둘 이상의 트랜잭션이 각자 보유한 잠금(Lock)을 놓지 않은 채 상대의 잠금을 기다려 진행이 멈춘 상태입니다. MySQL의 InnoDB 같은 엔진은 이런 고리를 스스로 감지해 한쪽 트랜잭션을 실패시키는 방식으로 풀어 주고, 애플리케이션은 그 실패를 받아 다시 시도하도록 설계하는 것이 일반적입니다.

MVCC

읽기와 쓰기가 서로를 막지 않게 하는 구조

회사 공용 문서를 한 사람이 수정하는 동안 다른 사람들이 그 문서를 아예 열어 볼 수 없다면, 업무는 금세 줄을 서게 됩니다. 데이터베이스도 같은 문제를 겪는데, 이를 해결하려고 읽기와 쓰기가 서로를 막지 않도록 만든 구조가 MVCC(Multi-Version Concurrency Control, 다중 버전 동시성 제어)입니다. 도서관에서 사전 한 권을 여러 사람이 함께 보는 상황을 떠올려 보겠습니다. 누군가 내용을 고쳐 새 판을 만들 때 이전 판을 버리지 않고 서가에 그대로 남겨 두면, 읽는 사람은 자기가 집어 든 판을 마음 놓고 끝까지 볼 수 있습니다.

여기서 서가에 꽂힌 각 판이 데이터의 버전이고, 책을 집어 든 사람은 트랜잭션이며, 새 판을 만드는 일은 변경 작업입니다. 읽는 쪽은 자기 시작 시점의 판을 계속 보므로 쓰는 쪽의 잠금을 기다릴 필요가 없고, 쓰는 쪽도 읽는 쪽 때문에 멈추지 않습니다. 정리하면 MVCC는 데이터를 고칠 때 기존 값을 덮어쓰지 않고 새 버전을 따로 만들어 두어, 읽기 작업이 과거 시점의 값을 보게 하는 방식입니다. 덕분에 읽기와 쓰기가 서로의 잠금을 기다리지 않고 동시에 진행되며, MySQL의 InnoDB도 이 구조를 바탕으로 동작합니다.

자동 커밋 모드

autocommit 설정이 트랜잭션에 미치는 영향

명령 하나를 실행할 때마다 저장이 자동으로 확정된다는 사실을 모르면, 여러 작업을 한 묶음으로 되돌리려는 시도가 번번이 어긋납니다. MySQL에서 이 동작을 정하는 설정이 자동 커밋 모드(autocommit)입니다. 메신저에서 메시지를 한 줄 칠 때마다 곧바로 전송되는 방식과, 여러 줄을 다 쓴 뒤 전송 버튼을 한 번 누르는 방식을 비교해 보겠습니다. 자동 커밋이 켜져 있으면 명령 하나가 곧 한 번의 전송이 되어 바로 확정되고, 꺼져 있으면 사용자가 커밋(COMMIT)을 선언할 때까지 입력이 임시 보관함에 쌓입니다.

임시 보관함에 쌓인 내용은 롤백(ROLLBACK)으로 통째로 지울 수 있지만, 이미 전송된 줄은 되돌릴 수 없습니다. 그래서 자동 커밋이 켜진 상태에서 여러 명령을 묶고 싶다면 트랜잭션을 직접 시작해 경계를 정해 주어야 합니다. 정리하면 자동 커밋 모드는 SQL 문 하나를 하나의 트랜잭션으로 보고 실행 즉시 확정하는 설정입니다. MySQL은 기본값이 켜짐으로 되어 있어, 여러 작업을 하나로 묶거나 되돌릴 필요가 있을 때는 자동 커밋을 잠시 끄거나 트랜잭션 시작 문을 명시하는 편이 안전합니다.

트랜잭션 설계 실습

송금·재고 차감 시나리오로 안전하게 묶기

계좌에서 돈을 빼는 일은 성공했는데 입금 쪽에서 오류가 나면, 사라진 돈을 찾을 방법이 마땅치 않습니다. 송금과 재고 차감처럼 두 개 이상의 변경이 함께 성공해야 하는 경우를 안전하게 묶는 일이 트랜잭션 설계입니다. 택배 한 건을 처리할 때 보내는 사람 집에서 짐을 꺼내는 일과 받는 사람 집에 내려놓는 일을 따로 처리한다면, 중간에 사고가 나면 짐만 사라지고 끝납니다. 그래서 두 일을 하나의 운송장으로 묶어, 둘 다 끝나야 완료로 치고 하나라도 어긋나면 처음 상태로 되돌립니다.

송금에서는 출금과 입금이 이 두 동작에 해당하고, 재고 차감에서는 재고를 줄이는 일과 주문을 남기는 일이 같은 운송장에 묶입니다. 이때 확인과 변경 사이에 다른 작업이 끼어들지 않도록 잠금을 잡고, 실패가 나면 롤백(ROLLBACK)으로 되돌리며, 다시 시도해도 결과가 한 번만 반영되도록 설계합니다. 정리하면 트랜잭션 설계는 함께 성공해야 하는 변경들을 하나의 경계로 묶고, 그 경계 안에서 잠금과 롤백, 재시도 규칙을 정하는 일입니다. 송금과 재고 차감처럼 숫자가 어긋나면 바로 드러나는 시나리오로 연습하면 원자성(Atomicity)과 일관성(Consistency)의 감각을 익힐 수 있습니다.

인덱스란 무엇인가

책의 색인처럼 조회를 빠르게 하는 구조

수천 페이지짜리 책에서 특정 단어를 찾을 때 첫 장부터 한 장씩 넘기면 하루가 걸립니다. 데이터베이스에서도 같은 일이 벌어지는데, 이때 조회를 빠르게 해 주는 장치가 인덱스(Index)입니다. 책 맨 뒤에 붙은 색인을 떠올려 보겠습니다. 색인은 단어와 그 단어가 나오는 쪽 번호를 가나다순으로 늘어놓아, 본문을 훑지 않고도 원하는 쪽을 바로 펼 수 있게 합니다. 데이터베이스의 인덱스도 특정 칼럼의 값과 그 값이 저장된 위치를 정렬된 형태로 따로 보관하는 표입니다. 그래서 조건에 맞는 값을 찾을 때 전체 행을 처음부터 훑는 대신 인덱스에서 위치를 먼저 얻고 그 위치만 읽어 갑니다. 정리하면 인덱스는 테이블과 별도로 유지되는 정렬된 참조표로, 조회할 때 읽어야 할 범위를 크게 줄여 주는 구조입니다. 다만 값을 넣거나 바꿀 때마다 인덱스도 함께 갱신해야 하므로, 자주 찾는 조건에만 만들고 남발하지 않는 편이 좋습니다.

B-Tree 인덱스

MySQL이 기본으로 쓰는 인덱스 구조

값이 수백만 건 쌓인 표에서 원하는 한 건을 찾으려고 처음부터 끝까지 훑는다면, 데이터가 늘어날수록 조회 시간도 함께 늘어납니다. MySQL이 기본으로 쓰는 B-Tree 인덱스는 이 시간을 데이터 양과 거의 무관하게 유지하려고 만든 구조입니다. 도서관에서 책을 찾을 때 입구 안내판에서 층을 고르고, 그 층의 서가 안내판에서 구역을 고르고, 마지막으로 서가 앞에서 책을 집는 과정을 떠올려 보겠습니다. B-Tree 인덱스는 이처럼 여러 단계의 안내판을 층층이 쌓아 올린 나무 모양 구조로, 각 단계에서 갈래를 하나씩 고르며 내려갑니다.

맨 위 뿌리에서 시작해 중간 단계를 거쳐 맨 아래 잎에 이르면 실제 행의 위치를 얻고, 이 깊이는 데이터가 늘어도 아주 천천히만 늘어납니다. 그리고 잎끼리 순서대로 이어져 있어, 범위를 훑는 조회도 앞뒤로 이어진 구간만 읽으면 됩니다. 정리하면 B-Tree 인덱스는 정렬된 여러 층의 노드로 이루어져, 뿌리에서 잎까지 내려가는 몇 번의 비교로 원하는 값을 찾는 구조입니다. 스스로 균형을 맞추기 때문에 데이터가 늘어도 탐색 깊이가 크게 늘지 않고, 같은 이유로 범위 조회와 정렬에도 유리합니다.

인덱스 생성과 삭제

CREATE INDEX와 DROP INDEX 사용법

회원 테이블에 수십만 건의 행이 쌓이면 이메일 하나로 회원을 찾는 조회가 매번 테이블 전체를 처음부터 끝까지 훑게 됩니다. 그렇게 되면 화면이 몇 초씩 멈추고 동시에 들어오는 요청이 늘어날수록 서버는 금세 한계에 부딪힙니다. 이때 테이블과는 별도로 값이 정렬된 색인을 미리 만들어 두는 구조가 인덱스(index)이고, 그것을 만들고 없애는 명령이 CREATE INDEX와 DROP INDEX입니다.

도서관을 떠올리면 이해가 쉽습니다. 책이 수만 권 꽂힌 서가에서 원하는 책을 찾을 때 사서는 책장을 처음부터 훑지 않고 제목이나 저자별로 정리된 색인 카드를 먼저 펼칩니다. CREATE INDEX는 이런 색인 카드를 새로 만들어 정해진 순서로 늘어놓는 일이고, DROP INDEX는 더 이상 쓰지 않는 카드 묶음을 통째로 치우는 일에 해당합니다.

다만 카드를 만들려면 책 전체를 한 번 읽어 정리해야 하므로 시간이 들고, 새 책이 들어올 때마다 카드도 함께 갱신해야 하며 카드장도 자리를 차지합니다. 그래서 자주 조건으로 쓰는 열에만 인덱스를 만들고, 쓰이지 않게 된 인덱스는 DROP INDEX로 정리하는 편이 좋습니다.

정리하면 인덱스는 특정 열의 값을 미리 정렬해 두어 행을 빠르게 찾게 해 주는 별도 구조이며, CREATE INDEX로 만들고 DROP INDEX로 제거합니다. 조회 속도를 얻는 대신 저장 공간과 쓰기 비용을 지불하는 맞바꿈이라는 점이 핵심입니다.

복합 인덱스

여러 열을 묶은 인덱스의 열 순서 규칙

주문 테이블에서 회원 번호와 주문일을 함께 조건으로 거는 조회가 잦은데, 두 열에 각각 인덱스를 만들어 두면 한쪽 조건만으로 후보를 줄인 뒤 나머지는 일일이 확인해야 해서 여전히 느립니다. 여러 열을 정해진 순서로 묶어 하나의 색인으로 만든 것이 복합 인덱스(composite index)이고, 이때 열을 어떤 순서로 늘어놓는지가 성능을 가릅니다.

택배 물류센터를 생각해 보면 이해가 쉽습니다. 물건을 시 단위로 먼저 나누고 그 안에서 동, 다시 그 안에서 호수 순으로 정리해 두면 배송원이 목적지를 바로 찾아갑니다. 복합 인덱스도 같은 방식으로 첫 번째 열을 가장 큰 분류로 삼고 그 안에서 두 번째 열, 세 번째 열 순으로 정렬합니다.

그래서 앞쪽 열이 조건에 빠지면 뒤쪽 열만으로는 그 구역을 찾아갈 수 없고, 앞쪽 열을 범위 조건으로 쓰면 뒤쪽 열의 정렬 효과도 함께 누리기 어렵습니다. 결국 자주 함께 조회되는 열을 앞에서부터 나열하고, 등호 조건으로 쓰는 열을 앞에 두는 것이 일반적인 설계 요령입니다.

정리하면 복합 인덱스는 두 개 이상의 열을 왼쪽부터 순서대로 묶어 정렬한 인덱스이며, 조건에 앞쪽 열이 포함되는지가 그 인덱스를 쓸 수 있는지를 가릅니다. 열의 순서 자체가 인덱스의 일부라는 점을 기억해야 합니다.

커버링 인덱스

테이블을 읽지 않고 인덱스만으로 답하는 법

조회에 필요한 값이 몇 개 되지 않는데도 인덱스로 위치를 찾은 뒤 테이블까지 다시 가서 그 값을 읽어 오는 두 번의 일이 매번 벌어집니다. 인덱스 안에 조회에 필요한 열의 값까지 함께 담아 두면 테이블을 읽지 않고 인덱스만으로 답할 수 있는데, 이렇게 덮인 상태를 커버링 인덱스(covering index)라고 부릅니다.

도서관 색인 카드에 책의 위치뿐 아니라 저자와 출판연도까지 함께 적어 두었다고 상상해 보십시오. 그 정보를 묻는 질문에는 서가까지 걸어가지 않고 카드만 넘겨도 답할 수 있지만, 카드에 없는 내용은 결국 서가로 가서 책을 꺼내야 합니다.

커버링 인덱스도 똑같이, 조회에서 읽는 열이 모두 인덱스에 들어 있으면 인덱스 안에서 답이 완성됩니다. 그래서 조회에 쓰는 열을 인덱스 구성에 포함시키거나, 복합 인덱스의 열 목록을 조회 패턴에 맞춰 잡는 방식으로 만듭니다.

정리하면 커버링 인덱스는 조회가 필요로 하는 모든 열을 인덱스가 이미 갖고 있어 테이블 접근을 생략하게 해 주는 상태입니다. 인덱스가 조회를 덮는다는 표현 그대로, 읽어야 할 양을 줄이는 것이 목적입니다.

인덱스가 안 타는 경우

형 변환·함수·와일드카드가 인덱스를 막는 이유

인덱스를 만들어 두었는데도 조회가 느려지는 일이 흔한데, 대개는 조건을 가공해서 정렬된 색인의 순서를 쓸 수 없게 만든 경우입니다. 열에 함수를 씌우거나 다른 형으로 바꿔 비교하면 인덱스는 그대로 있어도 활용되지 못하고, 앞부분이 정해지지 않은 문자열 검색도 같은 결과를 낳습니다.

사전에서 단어를 찾는 상황을 떠올리면 이해가 쉽습니다. 김으로 시작하는 단어는 김 페이지를 곧바로 펼칠 수 있지만 김이 중간에 들어간 단어를 찾으려면 첫 장부터 끝까지 넘겨야 합니다. 인덱스는 값이 원래 모습 그대로 정렬되어 있다는 전제 위에서 동작하므로, 앞 글자가 정해지지 않은 와일드카드 검색은 그 정렬을 이용할 수 없습니다.

숫자 열을 문자열로 비교하는 형 변환이나 열을 함수로 감싸는 조건도 마찬가지로 카드의 순서가 의미를 잃게 만듭니다. 그래서 조건에서는 열을 가공하지 않고 값 쪽의 형태를 열에 맞춰 주는 것이 중요합니다.

정리하면 인덱스는 열의 원래 값과 그 정렬 순서를 전제로 동작하며, 형 변환·함수 적용·앞부분이 열린 와일드카드는 이 전제를 깨뜨려 인덱스 사용을 막습니다. 조건식이 인덱스의 정렬을 그대로 따라갈 수 있는지가 판단의 기준입니다.

실행 계획(EXPLAIN)

EXPLAIN으로 쿼리 처리 경로를 읽는 법

쿼리가 느릴 때 어디에서 시간을 쓰는지 알 수 없으면 짐작만으로 튜닝을 하게 되고, 잘못된 짐작은 오히려 상황을 나쁘게 만들기도 합니다. 데이터베이스가 쿼리를 어떤 순서와 방식으로 처리할지 미리 보여 주는 명령이 EXPLAIN, 곧 실행 계획(execution plan)을 확인하는 기능입니다.

내비게이션에서 목적지를 넣고 출발하기 전에 경로를 미리 보는 상황과 비슷합니다. EXPLAIN은 어떤 인덱스를 후보로 보는지(possible keys)와 실제로 고른 인덱스(key), 테이블을 어떤 방식으로 읽을지(type), 몇 행을 훑을 것으로 보는지(rows)를 표 형태로 보여 줍니다.

이 값들을 읽으면 조건이 인덱스를 타는지, 조인이 어떤 순서로 이뤄지는지, 불필요하게 많은 행을 스캔하는 지점이 어디인지가 드러납니다. 다만 rows 값은 통계를 바탕으로 한 추정치이므로 실제 처리량과 다를 수 있다는 점을 감안해야 합니다.

정리하면 EXPLAIN은 쿼리를 실행하지 않고 처리 경로와 예상 비용을 보여 주는 도구이며, 선택된 인덱스와 접근 방식, 예상 행 수를 통해 병목의 후보를 찾게 해 줍니다. 예상치는 어디까지나 추정이라는 한계를 알고 읽어야 합니다.

← 이전인덱스가 안 타는 경우다음 →EXPLAIN ANALYZE

6부. 인덱스와 실행 계획066

EXPLAIN ANALYZE

실제 실행 시간과 행 수로 계획을 검증하는 법

EXPLAIN이 보여 주는 행 수와 비용은 통계를 바탕으로 한 추정이라, 통계가 실제 데이터와 어긋나면 계획이 크게 틀릴 수 있습니다. 그래서 쿼리를 실제로 실행하면서 구간마다 걸린 시간과 실제로 지나간 행 수를 함께 재는 기능이 EXPLAIN ANALYZE입니다.

내비게이션이 알려 주는 예상 소요 시간과 실제 주행 기록의 차이를 비교하는 상황과 같습니다. EXPLAIN ANALYZE는 각 처리 단계가 실제로 몇 밀리초를 썼는지, 몇 행을 내보냈는지를 보여 주므로 예상과 실제가 크게 벌어진 지점을 바로 찾아낼 수 있습니다.

앞 단계의 추정 행 수가 실제보다 훨씬 작게 잡혀 있다면 그 지점이 잘못된 계획의 원인일 가능성이 큽니다. 다만 이 명령은 쿼리를 정말로 수행하므로, 데이터를 바꾸는 문장에 걸면 실제 변경이 일어난다는 점을 조심해야 합니다.

정리하면 EXPLAIN ANALYZE는 실행 계획을 실제 수행 결과와 대조해 단계별 소요 시간과 실제 행 수로 검증하는 도구입니다. 추정과 실측을 나란히 놓고 보는 것이 느린 쿼리를 고치는 가장 확실한 출발점입니다.

옵티마이저와 통계 정보

옵티마이저가 인덱스를 고르는 판단 근거

어제 0.1초 만에 끝나던 조회 쿼리(Query)가 오늘은 5초가 걸린다면, SQL 문장도 데이터도 그대로인데 결과만 달라진 상황이라 원인을 짚기 어렵습니다. MySQL은 이런 일을 막으려고 실행 계획(Execution Plan)을 세우는 옵티마이저(Optimizer)를 두고, 그 판단의 재료가 되는 통계 정보(Statistics)를 따로 모아 둡니다. 택배 회사의 배차 담당자를 떠올려 보면 이해가 쉽습니다. 어느 동네에 짐이 몰리는지, 어떤 길이 막히는지 적어 둔 배송 대장이 통계 정보이고, 그 대장을 펼쳐 보고 오늘의 경로를 고르는 사람이 옵티마이저입니다.

대장이 몇 달 전 기록이라면 담당자는 텅 빈 골목으로 차를 보내고, 실제 짐이 몰리는 길은 비워 두게 됩니다. 그래서 MySQL은 데이터가 들어오고 나갈 때 통계를 조금씩 고쳐 두고, 대량으로 넣은 뒤처럼 숫자가 어긋났을 때는 ANALYZE TABLE 명령으로 다시 세게 할 수 있습니다. 정리하면 옵티마이저는 통계 정보를 근거로 인덱스(Index)를 쓸지 말지, 테이블을 어떤 순서로 읽을지 비용(Cost)을 계산해 고르는 판단기입니다. 통계가 실제 데이터와 어긋나면 아무리 좋은 인덱스가 있어도 엉뚱한 계획이 나오므로, 통계를 최신으로 유지하는 일이 성능의 출발점입니다.

인덱스 설계 전략

어떤 열에 어떤 순서로 인덱스를 둘지 정하기

인덱스(Index)를 많이 만들수록 조회가 빨라질 것 같아서 눈에 띄는 열마다 걸어 두면, 정작 자주 쓰는 쿼리는 여전히 느리고 저장 공간만 부풀어 오릅니다. 인덱스 설계 전략은 어떤 열에, 어떤 순서로 인덱스를 둘지 미리 정하는 일이며, MySQL에서는 보통 B-Tree 인덱스를 기준으로 생각합니다. 도서관 색인 카드를 떠올려 보면 좋습니다. 저자, 출간 연도, 제목 순서로 정리한 카드는 저자를 먼저 아는 사람에게는 즉시 통하는 색인이지만, 제목만 아는 사람에게는 처음부터 끝까지 넘겨야 하는 종이 뭉치가 됩니다.

여러 열을 묶은 복합 인덱스(Composite Index)가 이 카드와 같아서, 앞에 놓인 열부터 조건에 쓰여야 뒤쪽 열까지 길이 열립니다. 그래서 조건절과 정렬에 실제로 등장하는 열을 앞세우고, 후보를 확 줄여 주는 선택도가 높은 열을 먼저 두는 것이 기본 순서입니다. 결국 인덱스 설계는 쿼리를 먼저 읽고 그 쿼리가 타는 길에 맞춰 색인을 만드는 작업입니다. 열 하나하나가 아니라 쿼리 묶음 전체를 보고 순서를 정해야 하며, 이미 있는 인덱스로 대신할 수 있는 중복 인덱스는 만들지 않는 것이 원칙입니다.

인덱스의 대가

쓰기 성능과 저장 공간에 드는 비용

조회가 느리다는 말에 인덱스(Index)를 열마다 걸었더니 이번에는 저장이 눈에 띄게 느려지고 디스크 사용량이 불어난 경험은 흔합니다. 인덱스는 조회를 빠르게 해 주는 대신 쓰기 성능과 저장 공간을 대가로 쓰는 구조라는 점을 먼저 알아야 합니다. 책 뒤에 붙는 색인을 생각하면 이 거래가 분명해집니다. 색인을 붙이면 원하는 내용을 빨리 찾지만, 본문을 고칠 때마다 색인도 함께 고쳐야 하고 종이도 더 듭니다.

MySQL에서 행을 넣거나 바꾸거나 지울 때마다 인덱스도 같이 정렬된 자리를 다시 잡아야 하므로 INSERT와 UPDATE, DELETE가 그만큼 느려집니다. 인덱스마다 별도의 저장 공간이 필요하고, 데이터가 늘수록 그 공간도 함께 늘어납니다. 그래서 인덱스는 조회 이득이 쓰기 비용보다 큰 곳에만 두는 것이 원칙입니다. 읽기가 압도적으로 많은 테이블이라면 넉넉히 걸어도 되지만, 쓰기가 잦은 테이블이라면 하나를 더 걸기 전에 정말 필요한지 따져야 합니다.

인덱스 진단 실습

느린 쿼리를 인덱스로 개선해 보기

회원 테이블에 100만 건이 쌓인 뒤 이메일로 회원 한 명을 찾는 쿼리가 몇 초씩 걸린다면, 화면은 멈춘 듯 보이고 사용자는 새로 고침을 누르게 됩니다. 이럴 때 무작정 인덱스(Index)를 걸기보다 실행 계획을 먼저 확인하고 근거를 세운 뒤 고치는 순서가 진단 실습의 기본입니다. EXPLAIN 문을 앞에 붙여 실행하면 MySQL이 어떤 인덱스를 쓰고 몇 행을 훑을지 보여 주는데, 이는 창고 지도를 펼쳐 놓고 어느 구역을 뒤지는지 확인하는 일과 같습니다. 지도에 전 구역을 훑는 것으로 나오면 인덱스가 없거나 쓰이지 못한 것이므로, 조건에 쓴 열에 맞는 인덱스를 만듭니다.

고친 뒤에는 같은 EXPLAIN과 실제 응답 시간을 다시 재서 훑는 행 수가 줄었는지 확인합니다. 인덱스를 썼는데도 느리다면 열 순서나 조건의 형태가 인덱스와 어긋난 경우가 많으므로 그 부분을 손봅니다. 요약하면 느린 쿼리는 실행 계획으로 원인을 확인하고, 인덱스를 추가한 뒤 다시 측정해 개선 폭을 확인하는 세 단계로 다룹니다. 눈대중이 아니라 측정값의 변화로 판단하는 것이 이 실습의 핵심입니다.

7부. 조인과 서브쿼리071

조인(JOIN)의 개념

두 테이블을 공통 열로 이어 붙이는 원리

고객의 이름과 주소, 그리고 그 고객이 낸 주문을 한 테이블에 모두 적으면 같은 고객 정보가 주문마다 되풀이되어 낭비가 생깁니다. 그래서 고객은 고객 테이블에, 주문은 주문 테이블에 나눠 담고, 두 테이블을 공통 열로 이어 붙여 함께 보는 조인(JOIN)을 씁니다. 택배 송장과 고객 명부를 떠올려 보면 원리가 그대로 보입니다. 송장에는 받는 사람의 고객 번호만 적혀 있고, 주소와 연락처는 고객 명부에 따로 있습니다.

두 장을 고객 번호라는 공통 열로 맞춰 붙이면 비로소 배달에 필요한 완전한 정보가 한 줄로 만들어집니다. 이때 기준이 되는 공통 열을 조인 조건(ON)이라 하고, MySQL은 이 조건이 맞는 짝을 찾아 두 테이블의 행을 하나로 합칩니다. 정리하면 조인은 테이블을 나눠 저장해 중복을 줄인 대신, 필요할 때 공통 열을 기준으로 다시 이어 붙이는 연산입니다. 어떤 행을 남기고 어떤 행을 버릴지에 따라 INNER JOIN과 OUTER JOIN 같은 종류가 갈립니다.

7부. 조인과 서브쿼리072

INNER JOIN

양쪽에 모두 있는 행만 가져오는 조인

두 테이블을 조인(JOIN)했더니 명부에 없는 번호의 송장이 결과에서 통째로 사라져 보이거나, 반대로 짝이 없는 줄이 섞여 들어와 집계가 틀어지는 일이 생깁니다. 양쪽에 실제로 존재하는 짝만 남기고 싶을 때 쓰는 것이 INNER JOIN입니다. 두 반의 명단을 맞추는 일을 생각하면 이해가 빠릅니다.

1반 명단과 2반 명단을 이름으로 맞출 때 양쪽에 다 있는 이름만 칠판에 적는다면 그것이 INNER JOIN입니다. 한쪽에만 있는 이름은 짝이 없으므로 결과에서 빠지고, 그래서 결과 행 수가 원래 어느 한쪽보다 적어질 수 있습니다. 기준이 되는 이름이 조인 조건(ON)이며, 조건이 참이 되는 조합만 골라 한 줄로 합칩니다. 결국 INNER JOIN은 조인 조건을 만족하는 행의 교집합만 돌려주는 조인입니다. 짝이 없는 행까지 남기고 싶다면 OUTER JOIN을 써야 하므로, 결과에서 빠진 것이 없는지 늘 확인해야 합니다.

7부. 조인과 서브쿼리073

LEFT·RIGHT JOIN

한쪽에만 있는 행까지 살리는 외부 조인

회원 명단과 주문 명단을 함께 보려고 두 표를 붙였더니, 한 번도 주문하지 않은 회원이 결과에서 통째로 사라져 버립니다. 주문 기록이 없는 회원도 빠짐없이 보고 싶다면 두 표를 맞대는 방식 자체를 바꿔야 하고, 그때 쓰는 것이 왼쪽 표를 기준으로 삼는 외부 조인(outer join)인 LEFT JOIN과 RIGHT JOIN입니다.

아파트 관리사무소에서 세대 명단과 주차 등록 명단을 대조하는 상황을 생각해 보면 이해가 쉽습니다. 세대 명단을 왼쪽에 두고 주차 명단을 오른쪽에 붙이면, 주차를 등록하지 않은 세대도 명단에 남고 주차 정보 칸만 비어 있는 상태로 표시됩니다. 반대로 주차 명단을 왼쪽에 두면 차량이 있는 세대만 기준이 되어, 등록 차량이 없는 세대는 다시 빠지게 됩니다.

즉 LEFT와 RIGHT는 어느 표를 기준 명단으로 삼느냐의 차이일 뿐이며, 기준 쪽의 행은 상대 표에 짝이 없어도 버리지 않고 빈칸으로 채워 남깁니다. 이렇게 짝이 없는 자리에 채워지는 빈 값을 NULL이라고 하며, 나중에 조건을 걸 때 이 NULL을 일반 값처럼 비교하면 원하는 결과가 나오지 않는다는 점을 기억해야 합니다.

정리하면 LEFT JOIN과 RIGHT JOIN은 한쪽 표의 모든 행을 보존하면서 다른 쪽의 일치하는 행을 덧붙이는 조인이고, 기준 표를 어디에 두느냐로 두 이름이 갈립니다.

7부. 조인과 서브쿼리074

CROSS JOIN과 자기 조인

모든 조합을 만들고 같은 표끼리 조인하기

가능한 조합을 하나도 빠뜨리지 않고 모두 늘어놓아야 할 때, 두 표를 조건 없이 붙이는 방법이 없다면 사람이 손으로 짝을 지어야 합니다. 이때 쓰는 것이 모든 조합을 만들어 내는 CROSS JOIN이고, 같은 표를 두 번 불러 스스로와 짝짓는 자기 조인(self join)은 그 조합을 한 표 안에서 만들어 내는 변형입니다.

옷가게에서 상의 세 벌과 하의 두 벌로 코디를 짜는 상황을 떠올려 보면 두 개념이 함께 잡힙니다. CROSS JOIN은 상의 목록과 하의 목록을 아무 조건 없이 이어 붙여 세 곱하기 두, 즉 여섯 가지 조합을 전부 만들어 냅니다. 자기 조인은 상의 목록 하나만 가지고도 같은 표를 두 개의 다른 이름으로 불러 놓고 서로 짝지어, 한 벌을 기준으로 다른 벌과의 조합을 만들어 내는 방식입니다.

이때 같은 표를 두 번 부르면 이름이 겹치므로 각각에 별칭(alias)을 붙여 구분하는데, 사원 표를 두 번 불러 각 사원과 그 사원의 상사를 나란히 놓는 것이 대표적인 활용입니다. 다만 CROSS JOIN은 조건이 없어 행 수가 곱해지므로, 큰 표끼리 걸면 결과가 순식간에 감당하기 어려운 크기로 불어난다는 점을 조심해야 합니다.

결국 CROSS JOIN은 조건 없이 모든 짝을 만드는 조합 생성기이고, 자기 조인은 같은 표에 별칭을 붙여 스스로를 상대 삼는 조인입니다.

조인 실행 방식

중첩 루프·해시 조인이 처리되는 모습

같은 조인 문장을 써도 표가 작을 때는 순식간에 끝나던 질의가 표가 커지자 몇 분씩 걸리는 일이 생깁니다. 조인은 문법만으로 끝나는 것이 아니라 내부적으로 짝을 찾는 절차를 거치는데, 데이터베이스는 표의 크기와 색인 여부를 보고 그 절차를 골라 씁니다.

택배 회사가 주문서와 배송지 목록을 대조하는 상황을 비유로 삼아 보겠습니다. 중첩 루프 조인(nested loop join)은 주문서를 한 장씩 집어 들고 그때마다 배송지 목록을 처음부터 훑어 일치하는 곳을 찾는 방식으로, 목록이 짧거나 색인이 있어 바로 찾아갈 수 있을 때 유리합니다. 해시 조인(hash join)은 목록이 너무 길어 매번 훑기 어려울 때, 작은 쪽 목록을 먼저 주소가 적힌 색인판처럼 정리해 두고 큰 쪽을 한 번만 지나가며 곧바로 짝을 찾아내는 방식입니다.

이 밖에도 양쪽을 미리 정렬해 두고 나란히 훑어 가며 맞추는 정렬 병합 조인(sort merge join)이 쓰이기도 하며, 어느 방식이 선택되는지는 데이터베이스가 비용을 어림잡아 정합니다.

정리하면 조인 실행 방식은 짝을 찾는 절차의 이름이고, 중첩 루프는 한 건씩 대조하고 해시 조인은 색인판을 만들어 한 번에 찾는 차이라고 할 수 있습니다.

서브쿼리

쿼리 안에 또 다른 쿼리를 넣는 방법

평균보다 많이 산 고객을 찾으려는데 평균값을 먼저 계산해 사람이 손으로 옮겨 적고 다시 질의를 돌려야 한다면, 데이터가 바뀔 때마다 같은 일을 반복해야 합니다. 이런 번거로움을 없애기 위해 질의 안에 또 다른 질의를 품어 그 결과를 조건으로 쓰는 방법이 서브쿼리(subquery)입니다.

회사에서 팀별 지출을 정산하는 상황을 떠올려 보면 구조가 그대로 보입니다. 먼저 전체 팀의 평균 지출을 구하는 작은 계산을 안쪽에서 끝내고, 그 결과 값을 바깥쪽 계산이 기준으로 삼아 평균을 넘는 팀만 골라내는 식입니다. 이때 안쪽 질의는 값 하나를 돌려주는 자리, 여러 값을 돌려주는 자리, 하나의 표처럼 쓰이는 자리 등 놓이는 위치에 따라 역할이 달라집니다.

안쪽 질의가 바깥 질의보다 먼저 한 번 실행되고 그 결과가 바깥 질의에 전달되는 것이 기본 흐름이며, 결과를 하나의 표처럼 FROM 절에 두는 형태는 파생 테이블(derived table)이라고 부릅니다.

정리하면 서브쿼리는 계산을 두 단계로 나누어 안쪽 결과를 바깥 조건으로 넘기는 구조이며, 중간 값을 사람이 옮겨 적지 않아도 되게 만드는 장치입니다.

IN·EXISTS

여러 값과 존재 여부를 비교하는 서브쿼리

어떤 고객이 주문을 한 적이 있는지 확인하려고 주문 표를 전부 불러와 눈으로 대조한다면, 고객이 늘어날수록 확인 작업은 끝이 없어집니다. 서브쿼리가 돌려준 결과를 조건으로 받아내는 대표적인 도구가 여러 값 중 하나에 해당하는지 보는 IN과, 해당하는 것이 하나라도 있는지 보는 EXISTS입니다.

도서관에서 회원 명단을 훑으며 대출 기록이 있는 사람만 표시하는 상황을 떠올려 보면 두 도구의 차이가 분명해집니다. IN은 대출 기록에서 뽑아낸 회원 번호 목록을 쪽지처럼 받아 들고, 회원 명단을 보며 그 쪽지에 적힌 번호 중 하나에라도 해당하면 표시합니다. EXISTS는 목록을 받아 들고 비교하는 대신, 회원 한 명마다 대출 기록 쪽에 물어보듯 달려가 해당 기록이 존재하는지만 확인하고 있으면 표시합니다.

그래서 앞의 방식은 값 목록을 만들어 두고 견주는 쪽이고, 뒤의 방식은 존재 여부만 따지므로 조건에 맞는 첫 건을 찾는 순간 확인을 멈출 수 있습니다. 다만 NOT IN은 목록에 빈 값이 섞이면 결과가 기대와 달라질 수 있어, 빈 값을 배제하는 조건을 함께 두는 편이 안전합니다.

정리하면 IN은 서브쿼리가 만든 여러 값과의 일치를, EXISTS는 서브쿼리 결과의 존재 여부를 판정하는 조건입니다.

상관 서브쿼리

바깥 행마다 다시 실행되는 서브쿼리

부서별로 평균 급여를 넘는 사원을 뽑으려고 전체 평균 하나만 구해 두면, 부서마다 기준이 달라야 하는 상황에서 답이 어긋납니다. 바깥 질의의 행 하나하나를 안쪽 질의가 참조하며 그 행에 맞는 기준을 새로 계산하는 방식이 상관 서브쿼리(correlated subquery)입니다.

반 전체 성적을 매기는 상황을 비유로 삼아 보겠습니다. 담임 선생님이 학생 한 명을 부를 때마다 그 학생이 속한 반의 평균을 새로 계산해 견주는 것과 같아서, 학생이 바뀌면 비교 기준도 함께 바뀝니다.

앞서 본 일반 서브쿼리는 안쪽 계산을 한 번만 끝내고 그 결과를 모든 행에 똑같이 적용하지만, 상관 서브쿼리는 안쪽 질의가 바깥 질의의 열을 참조하기 때문에 바깥 행마다 다시 실행됩니다. 이 구조 덕분에 행마다 다른 기준을 적용할 수 있지만, 바깥 행이 많으면 그만큼 안쪽 계산이 반복되어 느려질 수 있습니다.

그래서 색인을 잘 갖추거나 필요하면 조인으로 바꾸는 것이 성능을 지키는 길이며, 안쪽 결과가 바깥 행과 무관하다면 굳이 상관 구조를 쓸 이유가 없습니다. 정리하면 상관 서브쿼리는 바깥 질의의 값을 안쪽 질의가 참조하는 구조로, 행마다 기준을 새로 계산하는 대신 반복 실행이라는 비용을 치르는 방식입니다.

UNION과 UNION ALL

두 결과를 위아래로 합치는 법

온라인 쇼핑몰에서 지난달 주문 목록과 이번 달 주문 목록을 하나의 파일로 합쳐 달라는 요청을 받았다고 해봅시다. 두 표의 열 구성은 같은데 같은 손님이 두 달에 모두 주문했다면 그 사람을 한 번만 남길지 두 번 남길지에 따라 결과가 완전히 달라지므로, 두 조회 결과를 위아래로 이어 붙이는 UNION(유니온)과 UNION ALL(유니온 올)이 필요해집니다.

두 회사의 고객 명단을 하나로 합치는 상황을 생각해 봅시다.

A 회사 명단과 B 회사 명단을 탁자 위에 나란히 놓고 위에서부터 차례로 한 줄씩 옮겨 적는 것이 기본 동작이고, 이때 겹치는 이름을 걸러 내는지가 두 명령을 가릅니다. UNION ALL은 두 명단을 그대로 이어 붙여 중복을 확인하지 않으므로 빠르고, UNION은 이어 붙인 뒤 이름이 같은 줄을 하나만 남기도록 다시 한 번 훑어 정리합니다.

그래서 UNION은 정리 작업에 시간이 더 들고, 합쳐야 할 표가 클수록 그 차이는 커집니다.

정리하면 UNION ALL은 두 결과 집합(result set)을 중복 제거 없이 그대로 연결하고, UNION은 연결한 뒤 중복 행을 하나로 합쳐 반환합니다. 중복이 없다는 것을 이미 아는 상황이라면 UNION ALL을 쓰는 편이 낫고, 두 결과의 열 개수와 자료형이 서로 맞아야 한다는 조건은 둘 다 똑같이 지켜야 합니다.

조인 최적화

조인 순서와 인덱스로 조인을 빠르게 하기

회원 테이블과 주문 테이블을 붙여 손님별 주문 내역을 만드는데, 결과는 정확한데 조회가 몇 분씩 걸린다면 실무에서는 사실상 쓸 수 없는 기능이 됩니다. 같은 결과를 훨씬 짧은 시간에 얻도록 표를 붙이는 순서와 경로를 골라 주는 작업이 조인 최적화(join optimization)이고, 이는 DBMS(데이터베이스 관리 시스템)가 질의를 처리하는 계획을 세우는 영역에 속합니다.

도서관 사서가 두 권의 대출 장부를 대조하는 상황을 떠올려 보면 이해가 쉽습니다. 먼저 확인할 쪽을 작은 장부로 정하고, 큰 장부에서는 이름이 가나다순으로 정리된 색인을 펼쳐 해당 줄을 바로 찾는 것이 빠른 방법이며, 큰 장부를 처음부터 끝까지 넘기며 하나씩 맞춰 보는 것은 느린 방법입니다. 여기서 색인이 바로 인덱스(index)이고, 어느 장부를 먼저 펼칠지 정하는 것이 조인 순서입니다. 그리고 사서가 그때그때 감으로 정하지 않고 장부의 크기와 색인의 유무를 보고 미리 정해 둔 규칙에 따라 순서를 고르는 일이 질의 계획을 세우는 일에 해당합니다.

정리하면 조인 최적화는 조인 조건에 인덱스가 걸려 있는지, 각 표의 행이 얼마나 되는지를 근거로 조인 순서와 조인 방식(nested loop, hash join 등)을 정해 불필요한 전체 탐색을 줄이는 일입니다. 실행 계획(execution plan)을 확인해 인덱스가 실제로 쓰이는지 살펴보는 것이 출발점입니다.

윈도우 함수 기초

행을 유지한 채 그룹 기준으로 계산하는 법

직원 명단을 출력하면서 부서별 평균 급여를 각 직원 줄 옆에 나란히 보여 달라는 요구를 받았다고 해봅시다. 기존의 그룹 집계(GROUP BY)를 쓰면 부서 단위로 줄이 합쳐져 직원 개별 줄이 사라지므로, 행은 그대로 두고 그룹 기준 계산 결과만 옆에 붙이는 윈도우 함수(window function)가 필요해집니다.

학급 성적표를 떠올려 보면 구조가 그대로 겹칩니다. 학생 한 명당 한 줄은 그대로 남아 있고, 각 줄 옆의 빈칸에 그 학생이 속한 반의 평균 점수를 적어 넣는 것이 윈도우 함수의 동작입니다. 이때 어느 범위를 기준으로 계산할지를 정하는 부분이 OVER 절이고, 괄호 안에 PARTITION BY 반을 적으면 반마다 따로 평균을 내며 이를 생략하면 전체 학생을 한 범위로 봅니다. 성적표 전체를 다시 만들지 않고 옆칸만 채우는 셈이라 원본 줄의 개수와 순서가 그대로 유지됩니다.

정리하면 윈도우 함수는 OVER 절로 정의한 행의 범위(window)를 기준으로 집계나 순위를 계산하되 결과를 각 행에 붙여 돌려주는 함수입니다. GROUP BY가 여러 행을 하나로 접는 도구라면 윈도우 함수는 행을 접지 않고 계산값을 덧붙이는 도구라는 차이가 핵심입니다.

8부. 고급 SQL082

ROW_NUMBER·RANK

순위를 매기는 함수들의 차이

시험 성적을 정렬해 등수를 매기는데 같은 점수가 두 명 나왔을 때, 두 사람을 모두 1등으로 볼지 한 명은 1등 한 명은 2등으로 볼지를 정하지 못하면 명단을 확정할 수 없습니다. 점수가 같은 행을 어떻게 다룰지 정해 주는 함수가 ROW_NUMBER와 RANK이고, 이들은 윈도우 함수 중 순위를 매기는 갈래에 속합니다.

운동회 달리기 기록을 매기는 상황을 생각해 봅시다. 결승선을 동시에 통과한 두 사람에게 RANK는 둘 다 1등을 주고 다음 사람에게 3등을 주며, 이는 2등 자리를 비워 두는 방식입니다. 반면 ROW_NUMBER는 동시에 들어왔더라도 출석번호 같은 임의의 기준으로 한 사람을 1등, 다른 사람을 2등으로 줄을 세워 절대 같은 번호가 나오지 않게 합니다. 여기에 DENSE_RANK를 더하면 동점자에게 같은 등수를 주되 다음 등수를 건너뛰지 않아 1등, 1등, 2등이 됩니다.

정리하면 ROW_NUMBER는 정렬 기준 값이 같더라도 각 행에 1부터 중복 없는 일련번호를 부여하고, RANK는 같은 값에 같은 순위를 주면서 그만큼 다음 순위를 건너뜁니다. 조건에 맞는 한 건만 골라내야 할 때는 ROW_NUMBER, 실제 등수를 표시해야 할 때는 RANK를 씁니다.

누적 합계와 이동 평균

윈도우 프레임으로 구간 계산하기

일별 매출 표를 보면서 오늘까지의 누적 합계와 최근 7일 평균을 각 날짜 옆에 함께 표시해 달라는 요구를 받았다고 해봅시다. 행마다 계산 범위가 조금씩 달라지므로 한 번의 집계로는 답이 나오지 않고, 행마다 기준 구간을 옮겨 가며 계산하는 윈도우 프레임(window frame)이 필요합니다.

가계부를 쓰는 상황에 그대로 대응됩니다. 5일째 줄 옆에는 1일부터 5일까지의 지출을 더한 누적 합계를 적고, 같은 줄의 다른 칸에는 최근 7일치만 골라 평균을 냅니다. 이때 어디부터 어디까지 더할지를 정하는 표시가 ROWS BETWEEN이고, 앞쪽 경계를 첫 줄로 고정하면 누적 합계가 되며 시작과 끝을 함께 움직이면 이동 평균이 됩니다. 날짜가 하루 넘어갈 때마다 이 구간이 한 칸씩 미끄러지면서 다시 계산되는 셈입니다.

CTE(공통 테이블 식)

WITH로 쿼리를 이름 붙여 나누는 법

매출 쿼리가 서브쿼리 안에 또 서브쿼리가 겹쳐 몇 화면을 넘어가면, 나중에 손을 볼 때 어느 부분이 무엇을 계산하는지 알아내기 어렵고 같은 집계를 여러 번 반복해 적게 됩니다. 이렇게 긴 질의를 작은 조각으로 나누어 각각 이름을 붙이고 그 이름을 다시 불러 쓰는 문법이 CTE(공통 테이블 식, Common Table Expression)이며, 질의문 맨 앞의 WITH로 시작합니다.

요리 레시피를 정리하는 방식과 닮아 있습니다. 한 번에 모든 요리를 설명하면 순서가 엉키므로, 먼저 반죽을 만들어 반죽이라 이름 붙이고 소스를 만들어 소스라 이름 붙인 뒤 마지막 조리법에서 그 이름들을 불러 쓰는 것과 같습니다. WITH 절에서 첫 번째 조각의 이름과 계산 내용을 적고 쉼표로 이어 다음 조각을 적으면, 마지막 본문에서는 그 이름을 하나의 표처럼 조회할 수 있습니다.

같은 이름을 여러 곳에서 재사용할 수 있어 반복되는 집계를 한 번만 적으면 된다는 점이 서브쿼리와의 큰 차이입니다.

정리하면 CTE는 WITH로 이름 붙인 임시 결과 집합을 만들어 복잡한 질의를 읽기 쉬운 단위로 나누고 재사용하게 해 주는 기능입니다. 재귀(recursive) 옵션을 쓰면 자기 자신을 참조해 계층 구조를 펼치는 데에도 활용됩니다.

재귀 CTE

계층 구조를 스스로 반복해 펼치는 법

회사 조직도를 부서 번호와 상위 부서 번호만으로 저장해 두면, 특정 팀에서 최고 경영진까지 몇 단계를 거쳐 올라가는지, 또는 그 팀 아래에 누가누가 매달려 있는지를 한 번의 질의로 알아내기가 매우 어렵습니다. 이런 계층 구조를 스스로 반복해 펼치는 기능이 재귀 공통 테이블 표현식(Recursive CTE)입니다. 비유하자면 사원증 뒷면에 "내 위 상사" 한 명만 적혀 있는 회사입니다. 먼저 팀장의 사원증을 뽑아 시작점으로 삼고, 그다음에는 방금 뽑힌 사람들을 상사로 둔 사원증을 다시 찾아 붙입니다. 새로 찾은 사원증이 더 이상 나오지 않을 때까지 같은 동작을 되풀이하고, 나온 결과는 계속 한쪽에 차곡차곡 쌓입니다.

이렇게 시작 집합을 먼저 정하고 자기 자신을 참조하는 부분을 반복하는 구조 덕분에, 깊이가 몇 단계인지 미리 알지 못해도 끝까지 펼칠 수 있습니다. 재귀 CTE는 시작 집합을 만드는 부분(anchor member)과 자기 자신을 다시 부르는 반복 부분(recursive member)을 UNION ALL로 이어 붙이고, 새 행이 나오지 않으면 멈추는 구조입니다. 다만 순환 참조가 있으면 끝없이 돌 수 있으므로 깊이 제한이나 중복 차단 장치를 함께 두어야 합니다.

행을 열로 바꿔 요약표 만들기

지점별·월별 매출을 "지점, 월, 금액" 행으로만 쌓아 둔 표는 사람이 한눈에 비교하기 어렵고, 보고서에 붙이려면 손으로 옮겨 적어야 합니다. 이렇게 행으로 늘어선 값을 열로 바꿔 요약표를 만드는 기법이 피벗(Pivot)과 조건부 집계입니다. 비유하자면 편의점 본사 창고에 전표가 한 장씩 쌓이고, 진열대는 1월·2월·3월 칸으로 나뉘어 있는 상황입니다. 직원은 전표를 한 장씩 읽으면서 "이 전표가 1월 것이면 1월 칸에만 넣고 다른 칸에는 넣지 않는다"는 규칙으로 분류합니다. 칸마다 조건에 맞는 전표만 담기므로, 다 담은 뒤에는 각 칸의 금액을 더하기만 하면 월별 합계가 됩니다.

뷰(View)

자주 쓰는 쿼리를 이름 붙여 재사용하는 법

매일 같은 조회 쿼리를 복사해 붙여넣다 보면, 조건 하나가 바뀌었을 때 여러 곳을 찾아 고쳐야 하고 한 곳을 놓치면 서로 다른 숫자가 보고됩니다. 뷰(View)는 자주 쓰는 SELECT 쿼리에 이름을 붙여 데이터베이스 안에 저장해 두는 기능입니다. 아파트 관리사무소의 게시판을 떠올려 보면 이해가 쉽습니다. 관리사무소는 방문자 명단을 매번 처음부터 다시 만들지 않고, 정해진 양식에 맞춰 이번 달 주차 등록자 같은 목록을 붙여 둡니다.

뷰도 이와 같아서 어떤 테이블에서 어떤 조건으로 행을 골라낼지 정한 규칙을 이름 하나로 저장해 두고, 필요할 때마다 그 이름을 부르면 됩니다. 게시판에 붙은 종이가 원본 장부를 대신하는 것이 아니라 장부를 그때그때 읽어 보여 주는 것처럼, 뷰는 데이터를 따로 복사하지 않고 조회하는 순간 원본 테이블을 읽어 결과를 만들어 냅니다. 그래서 원본이 바뀌면 뷰를 통해 보이는 내용도 함께 바뀌고, 여러 사람이 같은 이름을 부름으로써 같은 기준의 데이터를 보게 됩니다. 뷰는 SELECT 문을 이름으로 감싼 가상의 테이블이며 실제 행을 저장하지 않고 조회 시점에 원본에서 결과를 계산합니다.

갱신 가능한 뷰

뷰를 통해 원본 테이블을 고칠 수 있는 조건

뷰를 조회용으로만 쓰다 보면, 화면에서 고친 값을 저장하려고 원본 테이블의 이름과 조건을 다시 알아내야 하는 번거로움이 생깁니다. 뷰를 통해 INSERT나 UPDATE, DELETE를 실행했을 때 그 변경이 원본 테이블에 반영되는 것을 갱신 가능한 뷰(updatable view)라고 합니다. 아파트 각 세대의 우편함에 이름표를 붙여 둔 경우를 생각해 봅니다. 이름표 하나가 정확히 한 세대의 우편함을 가리킬 때만 그 이름표를 떼어 다른 이름으로 바꾸거나 내용을 고칠 수 있습니다. 뷰도 마찬가지로, 뷰의 한 행이 원본 테이블의 한 행과 일대일로 대응하고 그 행이 어느 행인지 알 수 있어야 수정 내용이 원본까지 전달됩니다. 반면 여러 테이블을 이어 붙이거나 합계 같은 집계를 낸 뷰는 한 행이 여러 원본 행에서 나온 결과라서 무엇을 고쳐야 할지 정할 수 없어 수정이 막힙니다. 갱신 가능한 뷰는 각 행이 원본 테이블의 한 행과 명확히 대응될 때만 성립하고, 조인이나 집계가 들어간 뷰는 읽기 전용이 됩니다.

저장 프로시저

여러 SQL을 하나의 프로그램으로 묶는 법

송금처럼 여러 단계의 SQL이 순서대로 실행되어야 하는 작업을 매번 사람이 하나씩 입력한다면, 중간 단계를 빠뜨리거나 순서를 바꿔 데이터가 어긋나기 쉽습니다. 저장 프로시저(stored procedure)는 이런 SQL 묶음을 데이터베이스 서버 안에 이름을 붙여 저장해 두고 한 번의 호출로 실행하는 기능입니다. 은행 창구의 업무 매뉴얼과 같습니다. 창구 직원이 고객을 받을 때마다 신분증 확인, 잔액 조회, 출금, 기록을 즉흥적으로 처리하지 않고 정해진 매뉴얼을 순서대로 따르는 것과 같습니다.

저장 프로시저도 매뉴얼처럼 단계의 순서가 미리 정해져 있어 중간이 빠지지 않고, 매뉴얼을 한 번 잘 만들어 두면 누가 처리해도 같은 절차로 진행됩니다. 호출할 때 필요한 값은 매뉴얼의 빈칸처럼 인자(parameter)로 넘겨 받아 같은 절차를 다른 값에 되풀이해 쓸 수 있고, 절차를 바꿀 때는 매뉴얼 한 곳만 고치면 됩니다. 저장 프로시저는 여러 SQL 문과 제어 흐름을 서버에 저장한 하나의 실행 단위로, 호출과 인자를 통해 반복 작업을 일관되게 처리합니다.

저장 함수

값을 돌려주는 사용자 정의 함수 만들기

급여나 등급처럼 같은 계산 규칙을 여러 쿼리에서 되풀이해 쓴다면, 계산식이 조금만 바뀌어도 그 식이 들어간 모든 쿼리를 찾아 고쳐야 합니다. 저장 함수(stored function)는 이런 계산 규칙을 이름 붙여 데이터베이스에 저장하고, 쿼리 안에서 호출해 결과값 하나를 돌려받는 기능입니다. 아파트 택배 접수 창구에 무게와 거리를 넣으면 요금이 나오는 계산기를 한 대 놓아둔 것과 같습니다. 직원마다 암산하지 않고 같은 계산기를 쓰면 같은 조건에는 언제나 같은 요금이 나오고, 요금표가 바뀌면 계산기 한 대만 고치면 됩니다.

저장 함수도 값을 인자로 받아 정해진 식으로 계산한 뒤 결과값 하나를 돌려주며, 접수표의 어느 칸에서든 계산기를 부르듯 SELECT 문의 컬럼 자리나 조건 안에서 호출됩니다. 다만 계산기가 요금 하나만 내놓듯 저장 함수도 값을 하나만 돌려주고, 테이블의 여러 행을 직접 바꾸는 일은 하지 않습니다. 저장 함수는 입력값을 받아 정해진 계산을 수행하고 결과값 하나를 돌려주는, 쿼리 안에서 호출 가능한 사용자 정의 루틴입니다.

트리거

INSERT·UPDATE·DELETE에 자동으로 반응하는 장치

주문이 들어올 때마다 재고를 줄이고 기록을 남겨야 하는데, 담당 프로그램이 그 일을 빠뜨리면 재고와 실제 수량이 조용히 어긋납니다. 트리거(trigger)는 테이블에 INSERT나 UPDATE, DELETE가 일어날 때 미리 정해 둔 SQL을 자동으로 실행하는 장치입니다. 아파트 현관의 자동 센서등을 떠올리면 이해가 쉽습니다. 사람이 들어서면 스위치를 누르지 않아도 불이 켜지고 나가면 꺼집니다.

트리거도 이와 같이 행이 들어오거나 바뀌거나 지워지는 사건 자체를 감지해 정해진 동작을 스스로 실행합니다. 센서등이 사람이 아니라 문이 열렸다는 사건에 반응하듯, 트리거는 누가 실행했는지와 상관없이 테이블의 변화에만 반응합니다. 그래서 응용 프로그램이 여러 개로 늘어나도 같은 규칙이 한 곳에서 빠짐없이 지켜집니다. 트리거는 테이블의 변경 이벤트에 묶여 자동 실행되는 SQL 묶음으로, 데이터 변경과 함께 반드시 일어나야 하는 작업을 한 곳에 모아 둡니다.

이벤트 스케줄러

정해진 시간에 SQL을 자동 실행하는 법

매일 새벽에 지난 기록을 지우고 통계를 다시 계산해야 하는데, 사람이 출근해서 손으로 돌리면 하루는 잊히고 하루는 두 번 돌아 숫자가 틀어집니다. 이벤트 스케줄러(event scheduler)는 정해진 시각이나 일정한 간격마다 SQL을 자동으로 실행하도록 데이터베이스에 예약해 두는 기능입니다. 아파트의 정기 소독과 청소 예약과 같습니다. 관리사무소가 매주 화요일 오전 아홉 시라고 달력에 적어 두면 누가 기억하지 않아도 그 시각에 업무가 진행됩니다.

이벤트 스케줄러도 이와 같이 실행할 SQL과 실행 시각을 하나의 이벤트로 등록해 두고, 등록된 시각이 되면 서버가 스스로 그 SQL을 실행합니다. 달력의 반복 일정처럼 한 번만 할지 매일 또는 매주 반복할지 정할 수 있고, 필요 없어지면 예약을 지우듯 이벤트를 비활성화하면 됩니다. 다만 스케줄러 자체가 꺼져 있는 서버에서는 예약이 있어도 실행되지 않으므로 동작 여부를 미리 확인해야 합니다. 이벤트 스케줄러는 실행할 SQL과 실행 시각을 데이터베이스에 등록해 두고 서버가 정해진 때에 자동으로 실행하게 하는 예약 장치입니다.

동적 SQL과 PREPARE

문자열로 쿼리를 만들어 실행하는 법

저장 프로시저를 하나 만들어 두고 여러 테이블 이름과 조건에 두루 쓰고 싶었는데, 쿼리 문장이 전부 고정되어 있으면 그때마다 프로시저를 새로 만들어야 합니다. 이 곤란을 풀기 위해 SQL 문장 자체를 문자열로 조립해 실행 시점에 준비하는 기능이 동적 SQL(Dynamic SQL)이고, MySQL에서는 PREPARE 문이 그 중심을 맡습니다.

택배를 보낼 때 주소와 받는 사람이 매번 다른데 라벨을 미리 다 인쇄해 둘 수는 없으니, 주문이 들어올 때마다 빈칸이 뚫린 라벨 양식을 불러와 그 칸에만 값을 찍어 붙이는 방식에 비유할 수 있습니다.

PREPARE가 바로 그 빈칸 양식을 만드는 단계로, 물음표 자리표시자를 둔 쿼리 문자열을 서버가 미리 해석해 실행 계획을 세워 둡니다. EXECUTE에서 USING으로 값을 넘기면 찍힌 라벨이 완성되듯 문장이 실행되고, DEALLOCATE PREPARE로 양식을 반납해 자원을 정리합니다. 다만 값은 자리표시자로만 넣을 수 있고 테이블 이름이나 컬럼 이름처럼 구조를 바꾸는 부분은 문자열로 이어 붙여야 하므로, 그 부분의 따옴표 처리와 검증은 직접 해야 합니다.

정리하면 동적 SQL은 쿼리 문자열을 PREPARE로 준비하고 EXECUTE로 실행한 뒤 DEALLOCATE로 해제하는 흐름이며, 값은 자리표시자에 바인딩해 넘깁니다. 구조를 이루는 이름을 문자열로 붙일 때는 입력 검증을 거쳐야 SQL 인젝션(SQL Injection)을 막을 수 있습니다.

커서와 반복 처리

결과 집합을 한 행씩 처리하는 법

SELECT로 뽑은 결과가 수천 행인데 그 행마다 다른 조건으로 다른 테이블을 손봐야 한다면, 집합 단위로 한 번에 처리하는 SQL 문장만으로는 표현이 막힙니다. 이때 결과 집합을 한 행씩 꺼내 반복문으로 처리하도록 해 주는 것이 커서(Cursor)입니다.

공장 컨베이어 벨트에 물건을 한 줄로 올려 두고, 작업자가 벨트에서 물건을 하나씩 집어 가공한 뒤 다 떨어지면 벨트를 멈추는 장면에 비유할 수 있습니다.

DECLARE CURSOR로 결과 집합을 올릴 벨트를 선언하고, OPEN으로 SELECT 결과를 벨트 위에 올립니다. FETCH가 물건을 하나 집는 동작으로, 한 번 호출할 때마다 다음 행의 값이 변수에 담기고 더 꺼낼 행이 없으면 종료를 알리는 상태가 됩니다. 그 상태를 확인해 반복을 멈추고 CLOSE로 벨트를 정리하며, 이 반복은 저장 프로시저 안의 루프 문과 함께 쓰입니다.

정리하면 커서는 선언, 열기, 한 행씩 꺼내기, 닫기의 네 단계로 결과 집합을 행 단위로 순회하는 기능입니다. 행마다 개별 문장을 실행하므로 대량 데이터에서는 집합 기반 처리보다 느리다는 점을 기억하고, 꼭 필요할 때만 쓰는 것이 좋습니다.

핸들러와 오류 처리

프로시저 안에서 예외를 잡는 법

저장 프로시저가 중간에 없는 테이블을 건드리거나 중복 키를 만나면 그 자리에서 작업이 통째로 멈추고, 앞서 하던 변경은 어중간한 상태로 남을 수 있습니다. 이런 예외를 프로시저 안에서 붙잡아 정리하고 다음 흐름을 정할 수 있게 해 주는 것이 핸들러(Handler)입니다.

공장 라인 옆에 붙은 비상 대응 매뉴얼에 비유할 수 있는데, 어떤 사고가 났을 때 무엇을 할지를 미리 정해 둔 문서입니다.

DECLARE HANDLER 문이 그 매뉴얼을 거는 일로, CONTINUE는 조치를 한 뒤 하던 일을 계속하게 하고 EXIT는 프로시저를 빠져나오게 합니다. 조건 자리에는 중복 키나 없는 테이블 같은 특정 오류를 지정하거나 SQLEXCEPTION, SQLWARNING, NOT FOUND 같은 분류를 지정합니다. 매뉴얼의 조치 자리에 해당하는 본문에는 오류를 기록하거나 이전 상태로 되돌리는 ROLLBACK을 넣어 두고, 필요하면 RESIGNAL로 오류를 위로 다시 던집니다.

정리하면 핸들러는 프로시저 안에서 오류 조건과 대응 동작을 짝지어 선언해 두는 장치이고, CONTINUE와 EXIT로 오류 뒤의 흐름을 정합니다. 오류를 삼키기만 하면 원인을 놓치므로 기록과 되돌리기를 함께 두는 것이 안전합니다.

프로시저·트리거 운영 주의점

디버깅과 버전 관리가 어려운 이유

프로시저와 트리거는 데이터베이스 안에 코드를 넣어 두는 방식이라 편리하지만, 문제가 생겼을 때 어디서 무엇이 잘못됐는지 찾기가 훨씬 어렵습니다. 그래서 배포와 변경을 어떻게 관리할지 미리 정해 두지 않으면 운영이 금세 꼬이게 됩니다.

건물 벽 속에 묻어 둔 배관에 비유할 수 있는데, 물이 새도 어디서 새는지 알려면 벽을 뜯어야 하고 도면이 없으면 어느 배관이 언제 바뀌었는지 알 수 없습니다.

트리거는 특정 테이블의 입력, 수정, 삭제에 자동으로 딸려 실행되므로 개발자가 그 동작을 의식하지 못한 채 데이터를 바꾸게 됩니다. 디버깅 수단도 제한적이라 단계별로 실행해 보거나 값을 출력해 확인하기가 어렵고, 오류 메시지도 짧게만 남는 경우가 많습니다. 게다가 정의를 파일이 아니라 데이터베이스에 직접 넣는 일이 많아, 누가 언제 무엇을 바꿨는지 이력이 남지 않습니다.

정리하면 프로시저와 트리거는 코드를 데이터베이스에 두는 만큼 정의를 파일로 관리하고 변경 이력을 남기며, 트리거는 꼭 필요한 곳에만 최소로 두는 것이 안전합니다. 운영 환경에 넣기 전에 테스트 환경에서 같은 데이터로 미리 돌려 보는 절차도 함께 갖춰야 합니다.

계정과 호스트

사용자@호스트 표기와 접속 범위

데이터베이스에 접속할 때 사용자 이름만 맞으면 어디서든 들어올 수 있다면, 같은 이름을 쓰는 다른 서버나 다른 사람이 그 권한을 그대로 넘겨받게 됩니다. MySQL은 계정을 사용자 이름과 접속해 오는 호스트를 한 쌍으로 묶어 관리해 이 문제를 막습니다.

회사 출입증에 비유할 수 있는데, 출입증에는 이름만이 아니라 어느 건물, 어느 층까지 들어갈 수 있는지가 함께 적혀 있습니다.

MySQL의 계정도 사용자 이름과 호스트를 골뱅이 기호로 이어 붙인 형태로 적고, 이 둘이 모두 맞아야 로그인이 됩니다. 호스트 자리에는 localhost처럼 특정 이름을 쓰거나 192.168.0.% 같은 범위 표기, 모든 호스트를 뜻하는 %를 쓸 수 있습니다. 같은 사용자 이름으로 localhost와 % 계정을 따로 만들어 두면 서버 안에서 접속할 때와 밖에서 접속할 때 서로 다른 권한을 주는 식으로 범위를 나눌 수 있습니다.

정리하면 MySQL 계정은 사용자 이름과 호스트의 조합으로 식별되며, 이 조합이 접속 범위와 권한의 단위가 됩니다. %로 열어 둔 계정은 의도치 않은 곳에서도 접속을 허용하므로, 계정을 만들 때는 어디서 접속할지를 함께 좁혀 정하는 것이 중요합니다.

GRANT와 REVOKE

필요한 권한만 주고 회수하는 법

여러 사람이 같은 데이터베이스를 쓰는데 모두 관리자 권한을 가지면, 실수 한 번으로 테이블이 지워지거나 다른 사람의 작업이 망가집니다. 필요한 권한만 골라 주고 필요 없어지면 회수하는 절차가 필요하며, 그 역할을 GRANT와 REVOKE가 맡습니다.

호텔 카드키에 비유할 수 있는데, 투숙객에게는 자기 방 문만 열리는 키를 주고 청소 담당에게는 해당 층만 열리는 키를 줍니다.

GRANT 문은 어떤 계정에 어떤 데이터베이스나 테이블에서 SELECT, INSERT, UPDATE, DELETE 같은 어떤 동작을 허용할지 적어 카드키를 발급하는 일입니다. REVOKE 문은 그 반대로 발급한 권한을 회수해 키를 무효로 만드는 일이고, 권한을 바꾼 뒤에는 FLUSH PRIVILEGES로 서버가 바뀐 내용을 다시 읽게 합니다. 실무에서는 권한을 하나씩 나열하기보다 역할을 뜻하는 ROLE을 만들어 묶어 주는 방식이 관리하기 쉽습니다.

정리하면 GRANT는 계정에 필요한 동작만 골라 허용하고 REVOKE는 그 허용을 거두는 명령으로, 최소 권한만 주는 것이 원칙입니다. 권한은 사람이 아니라 역할 단위로 묶어 두면 입사와 퇴사 때 빠뜨리기 어렵습니다.

권한의 종류

전역·DB·테이블·열 단위 권한의 차이

데이터베이스 계정을 하나 만들면서 편하다는 이유로 모든 권한을 한꺼번에 주면, 그 계정의 비밀번호가 한 번 새는 순간 회사 데이터 전체가 삭제되거나 통째로 빠져나갈 수 있습니다. 그래서 MySQL은 권한을 전역(global), 데이터베이스(database), 테이블(table), 열(column) 단위로 층층이 나누어, 꼭 필요한 범위만 골라 주도록 설계되었습니다.

회사 사옥에 비유하면 전역 권한은 건물 마스터키와 같아서 어느 층 어느 방이든 열 수 있고, 데이터베이스 권한은 특정 층의 출입카드처럼 그 층 안에서만 통하고, 테이블 권한은 특정 회의실 열쇠라서 그 방 안의 서류에만 손이 닿습니다. 열 권한은 더 잘게 나뉘어 회의실 서류에서도 급여 항목 같은 특정 칸만 가리고 보여줄 수 있는 수준입니다.

권한을 확인할 때는 건물 관리대장처럼 안쪽 범위의 권한과 바깥쪽 범위의 권한을 함께 대조해야 하는데, MySQL은 전역 설정과 해당 범위 설정을 모두 만족할 때만 실제 작업을 허락합니다. 반대로 권한을 회수할 때는 가장 좁은 범위부터 정리해야 넓은 권한에 가려 남아 있는 출입증을 놓치지 않습니다. 결국 MySQL의 권한은 GRANT와 REVOKE로 관리되는 범위별 허가증이며, 범위를 좁게 줄수록 사고가 나도 피해 반경이 좁아집니다.

SQL 인젝션

입력값이 쿼리로 새어 들어오는 공격과 방어

로그인 창이나 검색창에 사용자가 입력한 값을 그대로 쿼리(query) 문자열에 이어 붙여 만들면, 입력란에 명령문 조각을 집어넣는 것만으로 인증을 통과하거나 테이블 전체를 읽히는 일이 벌어집니다. SQL 인젝션(SQL injection)은 이렇게 입력값이 데이터가 아니라 명령으로 해석되어 쿼리 안으로 새어 들어오는 공격이며, 이를 막는 것이 매개변수화 쿼리(prepared statement)입니다.

택배 접수 창구에 비유하면, 받는 사람 칸에는 이름만 적어야 하는데 어떤 손님이 그 칸에 "이 물건은 반송하지 말고 옆 사무실로 보내라"는 지시문을 적어 넣는 것과 같습니다. 접수 직원이 칸의 내용을 지시문으로 읽어버리면 택배는 엉뚱한 곳으로 가고, 창구 직원이 그 칸을 그저 글자 덩어리로만 취급하면 지시문은 아무 힘도 쓰지 못합니다.

매개변수화 쿼리는 바로 이 두 번째 방식으로, 쿼리의 뼈대를 먼저 정해 두고 입력값은 나중에 값 자리로만 채워 넣습니다. 여기에 더해 입력 길이와 형식을 검사하고, 애플리케이션 계정에 필요한 권한만 부여하면 사고가 나더라도 새어 나갈 수 있는 범위가 크게 줄어듭니다. 정리하면 SQL 인젝션은 코드와 데이터의 경계를 무너뜨리는 공격이고, 방어의 핵심은 입력을 절대 쿼리 문자열로 조립하지 않고 값으로만 바인딩하는 것입니다.

안전한 비밀번호 관리

해시·암호화와 계정 정책

회원 비밀번호를 데이터베이스에 그대로 저장하면, 백업 파일 하나가 유출되는 순간 모든 사용자의 비밀번호가 그대로 드러나고 다른 사이트까지 연쇄 피해가 번집니다. 그래서 비밀번호는 원문을 저장하지 않고 해시(hash) 값으로 바꿔 저장하며, 같은 비밀번호라도 사용자마다 다른 결과가 나오도록 소금(salt)을 더해 갈아 넣습니다.

금고에 비유하면 비밀번호 원문은 금고 안의 내용물이고, 해시는 그 내용물을 산산조각 내어 다시 맞출 수 없게 만든 뒤 조각 개수만 적어 두는 것과 같습니다. 소금은 사용자마다 조각을 흩뿌리는 방식을 다르게 해서, 두 사람이 같은 비밀번호를 써도 서로 다른 조각 더미가 남게 만듭니다.

로그인할 때 서버는 입력받은 비밀번호를 같은 방식으로 갈아 본 뒤 저장된 값과 비교할 뿐, 원문을 되살리지 않습니다. 여기에 계정 정책을 더해 최소 길이와 복잡도를 요구하고, 로그인 실패 횟수를 제한하고, 오래된 비밀번호의 재사용을 막고, 관리자 계정에는 이중 인증을 붙입니다. 결국 안전한 비밀번호 관리는 해시와 소금으로 원문을 남기지 않는 저장 방식, 그리고 계정 정책과 이중 인증으로 접근 자체를 좁히는 운영 방식의 합입니다.

감사와 접속 로그

누가 무엇을 했는지 기록으로 남기기

장애가 나거나 데이터가 이상하게 바뀌었을 때 누가 언제 무엇을 했는지 아무 기록도 없다면, 원인을 찾는 일은 추측 싸움으로 끝나고 책임 소재도 가릴 수 없습니다. 감사(audit)와 접속 로그는 이런 공백을 메우기 위해, 누가 어디서 접속했고 어떤 쿼리를 실행했으며 권한이 어떻게 바뀌었는지를 기록으로 남기는 장치입니다.

아파트 경비실의 출입 기록부에 비유하면, 접속 로그는 누가 몇 시에 정문을 지나 몇 동으로 갔는지를 적는 줄이고, 감사 로그는 그 사람이 집 안에서 가구를 옮겼는지 금고를 열었는지까지 남기는 줄입니다. 기록부를 아무리 자세히 써도 확인하는 사람이 없으면 소용이 없듯이, 로그는 주기적으로 들여다보고 이상한 접속이나 대량 조회 같은 패턴을 걸러내야 의미가 생깁니다.

또 기록 자체가 변조되면 증거로 쓸 수 없으므로, 로그는 데이터베이스와 분리된 저장소에 보관하고 접근 권한을 제한해야 합니다. 로그를 너무 많이 남기면 저장 공간과 성능을 잡아먹으므로 무엇을 남길지 정하는 것이 운영의 몫입니다. 정리하면 감사와 접속 로그는 데이터베이스의 출입 기록과 작업 일지이며, 사후 추적과 이상 징후 탐지를 가능하게 하는 기본 안전장치입니다.

논리 백업(mysqldump)

SQL 텍스트로 백업하고 복원하는 법

서버가 갑자기 멈추거나 잘못된 삭제 명령이 실행되면 데이터는 순식간에 사라지는데, 복구할 수단이 없다면 회사의 업무 기록이 통째로 증발하는 셈입니다. 논리 백업(logical backup)은 데이터 자체를 복사하는 대신, 테이블 구조와 데이터를 SQL 문장 텍스트로 풀어 적어 두는 방식이며 MySQL에서는 mysqldump가 대표적인 도구입니다.

가구를 옮기는 대신 집 안의 모든 가구를 조립 설명서로 적어 두는 것에 비유할 수 있습니다. 설명서에는 어떤 가구가 어디에 놓여 있었는지, 나사가 몇 개였는지가 순서대로 적히고, 복원은 그 설명서를 읽으며 하나씩 다시 조립하는 일이 됩니다.

그래서 백업 파일은 사람이 읽을 수 있는 텍스트라서 특정 테이블만 골라 복원하거나 다른 서버로 옮기기에 편하고, 데이터베이스 버전이 달라도 대체로 옮겨집니다. 다만 설명서를 적는 동안에도 집 안의 가구가 계속 움직이므로, 일관된 상태를 담으려면 트랜잭션(transaction)을 활용한 옵션을 주거나 쓰기를 잠시 멈춰야 하고, 데이터가 클수록 복원에 시간이 오래 걸립니다. 결국 mysqldump 기반 논리 백업은 재현 가능한 SQL 텍스트로 데이터를 보관하는 방식이며, 유연한 이전과 부분 복원에 강한 대신 속도와 일관성 관리가 관건입니다.

물리 백업

데이터 파일을 통째로 복사하는 백업 방식

데이터가 수백 기가바이트를 넘어가면 SQL 텍스트로 풀어 적는 백업은 몇 시간씩 걸리고, 그 사이 서비스가 멈춰 버릴 수 있습니다. 물리 백업(physical backup)은 이 문제를 피하기 위해 테이블 구조와 데이터가 담긴 데이터 파일 자체를 통째로 복사하는 방식입니다.

이삿짐을 하나하나 목록으로 적는 대신, 집을 트럭에 통째로 실어 나르는 것에 비유할 수 있습니다. 트럭에 실으려면 짐이 흐트러지지 않도록 순간을 붙잡아야 하듯이, 데이터 파일을 복사하는 동안에도 계속 쓰기가 일어나므로 파일이 서로 어긋난 상태로 복사될 수 있습니다.

그래서 InnoDB 같은 저장 엔진은 복사 시점의 일관된 상태를 만들어 주는 스냅샷(snapshot) 기능을 제공하고, 이를 활용하거나 서버를 잠시 정지한 상태에서 파일을 복사합니다. 복사한 파일은 그대로 되돌려 놓으면 되므로 복원이 빠르고 대용량에 유리하지만, 운영체제와 MySQL 버전, 파일 경로 같은 환경 조건이 맞아야 하며 백업 대상 파일의 범위를 정확히 알아야 합니다. 정리하면 물리 백업은 데이터 파일을 그대로 보관하는 방식으로, 일관된 시점을 확보하는 것이 성패를 가르고 대규모 시스템의 복구 시간을 크게 줄여 줍니다.

바이너리 로그

모든 변경을 순서대로 기록하는 로그

서비스 중인 데이터베이스에서 누군가 실수로 테이블을 지우고, 그 뒤로도 다른 작업자들이 새 주문을 계속 넣는 상황을 생각해 봅니다. 밤에 떠둔 백업만 있으면 그 뒤에 정상적으로 처리된 주문까지 함께 사라지므로, 변경 하나하나를 순서대로 남겨 두는 기록이 필요해집니다. 이 기록이 MySQL의 바이너리 로그(binary log)입니다.

은행 창구의 거래 일지와 같습니다. 창구 직원이 입금과 출금이 일어날 때마다 시간과 금액을 일지에 적어 두고, 사고가 나면 그 일지를 처음부터 다시 실행해 잔액을 되살리는 방식입니다.

MySQL에서는 이 일지가 서버가 실행한 변경을 담는 파일로 남고, 테이블을 고치거나 행을 넣고 지우는 작업 하나하나가 이벤트라는 단위로 기록됩니다. 무엇을 남길지는 설정에 따라 달라서, 실행한 명령문을 그대로 적는 방식과 실제로 바뀐 행(row, 표의 가로 한 줄)의 값만 적는 방식 중에서 고를 수 있습니다. 일지의 한 장이 꽉 차면 다음 장을 새로 펼치듯, 로그 파일도 정해진 크기에 도달하면 새 파일로 넘어가고 오래된 파일은 정해 둔 기간이 지나면 지워집니다.

바이너리 로그는 서버에서 일어난 모든 변경을 시간 순서대로 담아 두는 기록입니다. 이 기록이 있어야 백업 이후의 변경을 다시 흘려보내 특정 시점으로 되돌리거나, 다른 서버에 같은 변경을 그대로 적용할 수 있습니다.

시점 복구(Point-in-Time Recovery)

백업과 로그로 특정 시각까지 되돌리기

새벽 두 시에 백업을 받아 두었는데 오전 열한 시에 잘못된 일괄 수정이 돌아 데이터가 망가졌다고 해봅니다. 백업만 복원하면 새벽 두 시로 돌아가 그 사이 여덟 시간의 정상 주문이 사라지므로, 백업과 변경 기록을 함께 쓰는 방법이 필요합니다. 그 방법이 시점 복구(point-in-time recovery)입니다.

이는 인쇄해 둔 책을 기준으로 삼고, 그 뒤에 붙은 수정 메모를 원하는 지점까지만 다시 적용하는 일과 같습니다.

MySQL에서는 먼저 백업본을 복원해 기준 상태를 만들고, 그 백업 시각 이후의 바이너리 로그를 원하는 시각 직전까지 순서대로 재생합니다. 이때 재생을 멈출 지점을 정확히 잡는 일이 핵심이라, 시각을 지정하거나 트랜잭션(여러 변경을 한 묶음으로 처리하는 단위) 번호를 기준으로 삼습니다. 잘못된 작업이 시작된 지점을 찾아 그 바로 앞에서 멈추면, 피해를 준 변경만 건너뛰고 그 뒤의 정상 작업은 살릴 수 있습니다.

시점 복구는 백업으로 기준점을 세우고 바이너리 로그로 그 뒤의 변경을 원하는 순간까지 재생하는 절차입니다. 그래서 백업이 있어도 로그를 보관하지 않으면 원하는 시각으로 돌아갈 수 없습니다.

복제(Replication)

원본과 사본을 자동으로 동기화하는 구조

원본 서버 한 대로만 서비스하다가 그 서버의 디스크가 고장 나면, 백업을 복원하는 동안 서비스가 멈추고 그 사이 들어온 주문도 잃습니다. 그래서 같은 데이터를 가진 사본을 미리 만들어 두고 원본의 변경을 자동으로 따라가게 하는 구조를 씁니다. 이 구조가 복제(replication)입니다.

본사 장부와 지점 장부의 관계와 같습니다. 본사에서 거래가 일어날 때마다 장부에 적고 그 전표 사본을 지점으로 보내면, 지점은 받은 순서대로 자기 장부에 옮겨 적습니다.

MySQL에서 원본은 변경을 바이너리 로그에 남기고, 사본은 그 내용을 받아 릴레이 로그(relay log)라는 중간 파일에 잠시 쌓아 두었다가 자기 데이터에 적용합니다. 원본은 사본이 잘 받았는지 확인하지 않고 다음 일을 계속하는 비동기 방식이 흔해서, 사본은 원본보다 조금 늦은 상태일 수 있습니다.

복제는 원본이 남긴 변경 기록을 사본이 전달받아 같은 순서로 적용하는 구조입니다. 읽기 요청을 사본으로 나눠 보내 부하를 덜거나, 원본이 멈췄을 때 사본을 대신 세우는 데 씁니다.

복제 지연과 장애 대응

사본이 뒤처질 때 확인할 것

복제를 걸어 두었는데 사본에서 조회한 값이 원본과 몇 분씩 다르게 보이면, 방금 저장한 내용이 사라진 것처럼 보여 사용자가 혼란스러워합니다. 이렇게 사본이 원본을 따라가는 속도가 뒤처지는 현상을 복제 지연(replication lag)이라 하며, 원인을 좁혀 확인하는 절차가 필요합니다.

본사에서 물건을 계속 보내는데 지점에서 분류하는 사람이 한 명뿐이면 창고에 짐이 쌓이는 것과 같습니다.

확인할 것은 크게 세 가지로, 원본과 사본 사이의 네트워크가 느린지, 적용할 변경이 사본에 밀려 있는지, 한 번에 너무 큰 변경이 있었는지입니다. 사본이 원본보다 얼마나 뒤처졌는지는 초 단위 지표로 표시되지만 이 값이 항상 정확하지는 않으며, 큰 트랜잭션 하나가 끝나기를 기다리는 동안에는 지연이 크게 늘어납니다. 적용을 여러 스레드로 나눠 처리하는 설정을 쓰면 이런 지연을 줄일 수 있습니다.

복제 지연은 원본의 변경이 사본에 적용되기까지 남은 시간이 벌어진 상태입니다. 지연이 커지면 사본에서 읽은 값이 틀릴 수 있으므로, 방금 쓴 값을 곧바로 읽어야 하는 요청은 원본으로 보내는 식으로 나눠야 합니다.

장애 조치(Failover)

원본이 죽었을 때 서비스를 이어가는 절차

원본 서버가 갑자기 꺼지면 사본은 멀쩡한데도 쓰기 요청을 받을 곳이 없어 서비스가 멈춥니다. 이때 미리 정해 둔 절차에 따라 사본을 새 원본으로 세우는 일이 장애 조치(failover)입니다.

지점장이 갑자기 쓰러지면 부지점장이 곧바로 서명 권한을 넘겨받지만, 거래처에 새 결재선을 알리지 않으면 서류가 계속 옛 지점장에게 가는 것과 같습니다.

마찬가지로 사본을 새 원본으로 올린 뒤에는 접속 주소나 라우터 설정을 새 원본으로 바꿔 클라이언트가 다시 붙게 해야 합니다. 이때 사본이 원본의 변경을 어디까지 받았는지 확인하지 않으면 아직 적용하지 못한 변경이 사라질 수 있습니다. 또 두 서버가 동시에 원본이라고 주장하는 상태가 생기지 않도록, 옛 원본이 살아나면 먼저 격리하는 규칙도 함께 정해 둡니다.

장애 조치는 사본을 새 원본으로 승격하고 접속 경로를 그쪽으로 돌리는 절차입니다. 데이터가 얼마나 보존되는지와 옛 원본을 어떻게 격리하는지까지 정해 두어야 실제 장애에서 쓸 수 있습니다.

업그레이드

버전을 올릴 때 점검할 것과 순서

오래 쓴 데이터베이스를 새 버전으로 올리면 빨라지고 지원도 이어지지만, 준비 없이 올렸다가 서비스가 멈추는 일이 생깁니다. 그래서 무엇이 달라지는지 미리 확인하고 순서를 정해 진행하는 절차가 필요합니다.

건물을 고칠 때 먼저 설계도를 펴서 없어진 출입구가 있는지 확인하고, 세입자를 임시로 옮긴 뒤 층별로 순서대로 공사하는 것과 같습니다.

MySQL에서도 새 버전에서 없어지거나 이름이 바뀐 기능이 있는지 미리 점검하는 도구를 돌리고, 데이터와 설정을 백업한 뒤에 작업을 시작합니다. 사본을 먼저 올리고 원본을 나중에 올리면 문제가 생겼을 때 되돌릴 여지가 남습니다. 다만 한 번 올린 데이터 파일은 예전 버전으로 되돌아가지 못하는 경우가 많으므로, 되돌릴 계획은 미리 세워 두어야 합니다.

업그레이드는 새 버전에서 달라진 점을 점검하고 백업한 뒤, 사본에서 원본 순서로 올리는 작업입니다. 되돌리기 어려운 단계를 마지막에 두는 것이 안전합니다.

슬로우 쿼리 로그

느린 쿼리를 찾아내는 설정과 활용

쇼핑몰의 주문 조회 화면이 갑자기 몇십 초씩 멈춘다고 해도, 서버에는 수천 개의 쿼리가 쉴 새 없이 오가고 있어서 범인을 눈으로 찾아내기는 거의 불가능합니다. 그래서 실행 시간이 일정 기준을 넘은 쿼리만 따로 붙잡아 두는 장치가 필요한데, 그것이 슬로우 쿼리 로그(slow query log)입니다.

이 기능은 식당 주방에서 조리 시간이 유난히 오래 걸린 주문만 따로 적어 두는 장부와 같습니다.

먼저 long_query_time이라는 기준 시간을 정해 두면, 주방장은 그 시간을 넘긴 주문만 장부에 옮겨 적습니다. 장부에는 어떤 주문이었는지, 얼마나 걸렸는지, 몇 시에 들어왔는지가 함께 남기 때문에 나중에 그 요리법을 다시 들여다보며 어디서 손이 막혔는지 알 수 있습니다.

다만 장부를 너무 세세하게 적으면 기록 자체가 부담이 되므로, 평소에는 기준을 느슨하게 두고 이상할 때만 촘촘히 켜는 식으로 운용합니다.

정리하면 슬로우 쿼리 로그는 기준 시간을 넘긴 SQL 문을 자동으로 수집해 원인 분석의 출발점을 만들어 주는 기능이고, 여기에 실행 계획(EXPLAIN)을 함께 보면 왜 느린지까지 좁혀갈 수 있습니다.

12부. 성능 튜닝과 운영116

서버 설정 튜닝

버퍼 풀·커넥션 등 주요 변수 조정

데이터베이스 서버를 기본 설정 그대로 켜 두면, 장비 성능이 좋아도 메모리를 절반도 쓰지 못하거나 동시 접속이 조금만 늘어도 연결이 거절되는 일이 생깁니다. 이런 낭비와 병목을 줄이려고 서버가 뜰 때 읽는 변수 값을 용도에 맞게 조정하는 작업을 서버 설정 튜닝이라고 부릅니다.

이는 식당을 새로 열면서 창고 크기와 홀 직원 수를 손님 규모에 맞춰 정하는 일과 같습니다.

창고가 곧 버퍼 풀(buffer pool)로, 자주 찾는 재료를 가까이 쌓아 두는 공간이며 여기가 작으면 재료를 찾을 때마다 먼 저장고까지 다녀와야 합니다. 홀 직원 수는 동시에 붙을 수 있는 연결(connection) 수에 해당하고, 직원이 너무 적으면 손님이 문 앞에서 기다리다 돌아가며 너무 많으면 인건비만 새어 나갑니다.

그래서 실제 손님 수와 테이블 회전을 보며 두 값을 조금씩 올리고 내리면서 가장 편한 지점을 찾습니다.

결국 서버 설정 튜닝은 버퍼 풀 크기와 최대 연결 수처럼 서버의 자원을 나눠 쓰는 주요 변수를, 실제 부하를 보며 적정선으로 맞추는 일입니다.

현재 서버 상태를 수치로 확인하는 법

서버가 느려졌다는 이야기가 나왔을 때 어디가 얼마나 나쁜지 숫자로 말할 수 없으면, 튜닝은커녕 원인을 짚기도 어렵습니다. 그래서 서버가 스스로 세고 있는 상태 변수(status variable)를 주기적으로 읽어 현재 상태를 수치로 확인하는 모니터링이 필요합니다.

이것은 자동차를 운전할 때 계기판을 보는 일과 같습니다.

속도계와 수온계, 연료계가 각각 다른 값을 보여 주듯 서버도 처리한 쿼리 수, 초당 읽기와 쓰기, 현재 열려 있는 연결 수, 잠금 대기 시간 같은 항목을 따로따로 세어 둡니다. 운전자가 계기판 숫자를 한 번 읽고 끝내지 않고 시간에 따라 어떻게 변하는지 보듯, 이 값들도 일정 간격으로 두 번 읽어 차이를 계산해야 의미가 생깁니다.

경고등이 켜졌을 때 어느 계기가 올라갔는지 확인하는 요령처럼, 평소 값을 기록해 두면 이상이 생긴 순간 무엇이 달라졌는지 바로 대조할 수 있습니다.

정리하면 모니터링은 상태 변수를 시간에 따라 읽어 서버의 부하와 병목을 숫자로 드러내는 일이며, 평소 기준값을 알고 있어야 이상 신호를 알아챌 수 있습니다.

락 대기와 커넥션 문제

잠금·커넥션 고갈 상황 진단

한 트랜잭션이 수정 중인 행을 붙잡고 오래 끝내지 않으면 뒤따라온 작업들이 줄줄이 멈추고, 그 줄이 길어지면 연결이 쌓여 결국 새 접속까지 거절되는 상황이 옵니다. 락 대기(lock wait)와 커넥션 고갈은 이렇게 함께 나타나기 때문에 두 가지를 같이 봐야 원인이 보입니다.

이는 건물에 하나뿐인 공용 화장실 열쇠를 빌려 쓰는 상황과 같습니다.

누군가 열쇠를 들고 들어가 오래 나오지 않으면 문 앞에 줄이 서고, 줄이 복도까지 이어지면 새로 온 사람은 아예 들어가지도 못합니다. 이때 문 앞의 줄이 락 대기, 복도까지 이어진 사람들이 연결(connection)이고, 열쇠를 든 채 나오지 않는 사람이 끝나지 않은 트랜잭션입니다.

해결도 이 순서를 따라야 하므로, 누가 열쇠를 얼마나 들고 있는지 확인해 그 트랜잭션을 끝내고, 연결을 오래 잡아 두는 코드는 빨리 반납하도록 고칩니다.

결국 락 대기와 커넥션 문제는 오래 붙잡힌 잠금이 대기 줄을 만들고 그 줄이 연결 자원을 소진하는 연쇄이며, 잠금 보유 시간과 연결 반납 시점을 먼저 손봐야 합니다.

파티셔닝

큰 테이블을 물리적으로 나눠 관리하기

테이블 하나에 수억 건이 쌓이면 인덱스가 커지고, 오래된 데이터를 지우려 해도 한 번의 큰 삭제가 오래 걸려 서비스가 흔들립니다. 이런 큰 테이블을 기준에 따라 여러 조각으로 나눠 따로 관리하는 방법이 파티셔닝(partitioning)입니다.

이는 사무실 서류를 한 상자에 몰아넣지 않고 연도별 캐비닛에 나눠 보관하는 것과 같습니다.

캐비닛을 나눠 두면 작년 서류를 찾을 때 올해 칸을 열어 볼 필요가 없고, 오래된 묶음은 칸째로 버리면 됩니다. 데이터베이스에서도 날짜나 번호 같은 기준으로 조각을 정의해 두면, 조건에 맞는 조각만 읽어 응답이 빨라지고 조각 단위로 지우거나 백업하기가 쉬워집니다.

다만 어느 조각에도 해당하지 않는 조건으로 조회하면 모든 칸을 뒤져야 하므로, 나누는 기준은 실제 조회 조건을 보고 정해야 합니다.

정리하면 파티셔닝은 큰 테이블을 날짜 같은 기준으로 물리적인 조각으로 나눠, 조회 범위를 줄이고 삭제와 관리를 조각 단위로 처리하게 해 주는 구조입니다.

운영 체크리스트

실무에서 매일·매주 확인할 항목 정리

장애는 늘 예상치 못한 순간에 오지만, 돌아보면 대부분 그 전에 남아 있던 작은 신호를 놓친 경우가 많습니다. 그래서 매일과 매주 정해진 항목을 같은 순서로 확인하는 운영 체크리스트가 필요합니다.

이는 비행기 조종사가 이륙 전에 정해진 항목을 소리 내어 확인하는 절차와 같습니다.

연료와 계기, 문 잠금을 순서대로 짚듯, 데이터베이스도 매일 확인할 항목과 매주 확인할 항목을 나눠 두면 빠뜨림이 줄어듭니다. 매일은 디스크 여유 공간과 백업 성공 여부, 느린 쿼리 증가, 연결 수 추이처럼 바로 손볼 수 있는 것을 보고, 매주는 인덱스 사용률과 통계 갱신, 오래 걸리는 작업 일정처럼 시간을 두고 판단할 것을 봅니다.

항목마다 정상 범위와 담당자를 적어 두면, 숫자가 범위를 벗어났을 때 누가 무엇을 할지 고민하지 않아도 됩니다.

결국 운영 체크리스트는 매일의 상태 점검과 매주의 구조 점검을 항목과 정상 범위로 미리 정해, 장애를 사후 대응이 아니라 사전 발견으로 돌리는 장치입니다.
