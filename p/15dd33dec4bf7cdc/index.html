1부. EFS 개요와 파일 스토리지 기초001

파일 스토리지란 무엇인가

블록·오브젝트·파일 스토리지가 무엇이 다른지 쉬운 말로 잡는다

여러 사람이 같은 폴더를 열어 문서를 함께 고치는데, 서버마다 파일이 따로 놀아서 어느 것이 최신본인지 아무도 모르는 상황이 실제로 자주 벌어집니다. 이런 곤란을 없애려고 파일과 폴더라는 약속된 구조로 데이터를 다루는 방식이 파일 스토리지(file storage)이고, 그 아래에는 데이터를 다루는 세 가지 큰 갈래인 블록 스토리지(block storage), 오브젝트 스토리지(object storage), 파일 스토리지가 나란히 자리합니다. 도서관 하나를 떠올리면 셋의 차이가 쉽게 잡힙니다. 파일 스토리지는 책을 서가에 꽂고 이름표와 분류 번호를 붙여 두는 도서관이라서, 이용자는 제목과 위치만 알면 책을 펴 볼 수 있고 사서는 "몇 번째 서가 몇 층"이라는 경로로 책을 찾아 줍니다. 블록 스토리지는 책을 낱장으로 뜯어 번호만 매긴 창고에 가깝고, 오브젝트 스토리지는 책마다 고유 번호표를 붙여 아무 서가에나 넣어 두고 번호로만 꺼내는 방식입니다.

그래서 파일 스토리지는 폴더를 만들고 이름을 바꾸고 일부만 읽는 일이 잦은 공동 작업에 어울립니다. 정리하면 파일 스토리지는 데이터를 이름과 폴더 경로로 가리키며 여러 사용자가 동시에 열어 쓸 수 있게 해 주는 방식이고, 그래서 문서 공유나 소스 코드 보관처럼 사람이 직접 다루는 작업에 기본값처럼 쓰입니다.

NFS 프로토콜 기초

EFS가 쓰는 NFS v4.1이 클라이언트와 서버 사이에서 무엇을 해주는지 이해한다

서버 한 대에만 들어 있는 폴더를 다른 서버에서도 쓰고 싶은데, 그 서버의 운영체제가 다르면 파일을 읽는 규칙부터 달라 아예 열리지 않습니다. 이때 서로 다른 시스템이 파일을 주고받는 공통 대화법이 필요한데, 그중 하나가 NFS(Network File System)이고 EFS는 그중 NFS v4.1을 기반으로 삼습니다. 회사 우편실을 떠올려 보면 이해가 쉽습니다. 내 컴퓨터의 프로그램은 우편 창구에 "이 경로의 이 부분을 읽어 달라"는 주문서를 내고, NFS 서버는 그 주문서를 해석해 실제 저장 장치에서 해당 부분을 찾아 응답합니다. 주문서에는 읽기·쓰기·목록 보기 같은 동작이 정해진 형식으로 적혀 있어서, 운영체제가 달라도 같은 양식이면 서로 알아듣습니다.

이런 주문서 묶음을 정리한 것이 NFS v4.1 규격이며, 한 번 맺은 연결을 오래 유지하고 잠금(lock)을 다루는 규칙까지 포함해 여러 사람이 같은 파일을 동시에 고치는 상황을 견딥니다. 즉 NFS는 원격에 있는 폴더를 내 컴퓨터의 폴더처럼 보이게 만드는 네트워크 파일 공유 규약이고, EFS는 이 규약을 관리형 서비스로 감싸 서버를 직접 세우지 않아도 쓰게 해 주는 것입니다.

1부. EFS 개요와 파일 스토리지 기초003

Amazon EFS란 무엇인가

EFS가 제공하는 관리형 공유 파일 시스템의 정체를 이해한다

여러 대의 서버가 같은 파일을 봐야 하는데 파일 서버를 직접 만들면 디스크를 붙이고 이중화를 꾸미고 장애를 감시하는 일이 끝없이 따라붙습니다. Amazon EFS(Elastic File System)는 이 파일 서버 운영을 AWS에 맡기고 폴더만 빌려 쓰는 관리형 공유 파일 시스템(managed shared file system)입니다. 아파트 단지의 공용 창고를 떠올리면 구조가 그대로 대응됩니다. 입주민은 각자 자기 집 현관 열쇠를 쓰듯 자기 서버에서 EFS를 마운트(mount)하고, 공용 창고의 선반은 폴더와 파일로 나뉘어 있으며, 관리사무소는 창고가 넘치면 자동으로 넓히고 고장 난 선반을 알아서 바꿉니다. 여러 서버가 동시에 같은 선반을 열 수 있고, 어느 서버가 문을 닫아도 다른 서버가 보던 물건은 그대로 남습니다.

사용한 만큼만 요금을 내는 구조라 처음에 창고 크기를 정해 둘 필요도 없습니다. 정리하면 EFS는 NFS 기반의 공유 파일 시스템을 서버 관리 없이 제공하는 서비스이고, 여러 컴퓨트 자원이 같은 데이터를 동시에 읽고 써야 하는 작업에 적합합니다.

EFS와 EBS의 차이

공유 파일 시스템과 블록 볼륨을 언제 골라야 하는지 구분한다

한 대의 서버에만 붙는 디스크로는 여러 서버가 같은 파일을 함께 고치는 요구를 감당할 수 없고, 반대로 모든 데이터를 네트워크 공유로만 두면 부팅 디스크처럼 빠르고 단단한 저장이 필요한 자리가 비어 버립니다. 그래서 AWS는 성격이 다른 두 저장 방식을 나란히 제공하는데, 그것이 블록 볼륨인 EBS(Elastic Block Store)와 공유 파일 시스템인 EFS입니다. 사무실 책상을 떠올려 보면 구분이 분명해집니다. EBS는 내 책상 위의 개인 서랍이라서 나만 열 수 있고 내 책상에 붙어 있으며, 서랍을 다른 사람 책상으로 옮기려면 책상째로 옮겨야 합니다. EFS는 복도 끝 공용 캐비닛이라서 여러 사람이 동시에 문을 열 수 있고, 각자 자기 자리에서 같은 서류를 꺼내 씁니다.

개인 서랍은 빠르고 예측 가능하지만 공유가 안 되고, 공용 캐비닛은 공유가 되지만 네트워크를 거치므로 지연이 조금 더 붙습니다. 또 EBS는 크기와 성능을 미리 정해 두는 경우가 많고, EFS는 쓴 만큼 늘어납니다. 결국 EBS는 한 인스턴스에 붙는 블록 저장소이고 EFS는 여러 인스턴스가 동시에 마운트하는 파일 저장소이며, 동시 접근이 필요한지 여부가 둘을 가르는 기준입니다.

EFS와 S3의 차이

파일 시스템과 오브젝트 스토리지를 접근 방식과 용도로 구분한다

파일을 폴더에 넣어 두고 경로로 찾는 방식과, 고유한 키를 붙여 통에 넣고 키로 꺼내는 방식은 겉보기에는 비슷하지만 쓰임이 크게 갈립니다. EFS는 전자, S3(Simple Storage Service)는 후자에 해당하는 오브젝트 스토리지(object storage)이며, 어느 쪽을 고르느냐에 따라 프로그램을 고치는 방식까지 달라집니다. 물류 창고 두 곳을 비교해 보면 차이가 드러납니다. S3는 택배 보관소라서 물건마다 번호표를 붙여 넣고, 찾을 때는 그 번호표 하나로 통째로 꺼내며, 중간 부분만 살짝 고치는 일은 하지 않습니다. EFS는 내 서재라서 책을 꽂고 일부 페이지를 펴서 읽거나 한 줄만 고쳐 쓰는 일이 자연스럽고, 여러 사람이 동시에 같은 책을 펼칠 수도 있습니다.

그래서 S3는 사진·백업·로그처럼 통째로 넣고 통째로 꺼내는 대량 데이터에 강하고, EFS는 애플리케이션이 파일을 열어 조금씩 읽고 쓰는 작업에 맞습니다. 정리하면 EFS는 경로와 파일 단위 접근을 제공하는 공유 파일 시스템이고 S3는 키로 접근하는 오브젝트 스토리지이며, 부분 수정과 동시 편집이 필요한지가 선택의 갈림길입니다.

EFS와 FSx의 차이

관리형 파일 시스템 제품군 안에서 EFS가 차지하는 자리를 파악한다

파일 시스템이 필요한데 윈도우 공유 폴더나 고성능 병렬 연산용 파일 시스템처럼 특정 환경에 딱 맞는 것이 필요할 때, 범용 서비스 하나로 모두 덮으려 하면 설정이 어긋나거나 성능이 모자라는 일이 생깁니다. 그래서 AWS는 여러 관리형 파일 시스템을 묶어 FSx라는 제품군으로 제공하고, 그 안에서 EFS는 리눅스 환경의 범용 공유 파일 시스템 자리를 맡습니다. 아파트 단지의 편의시설로 비유하면 배치가 보입니다. EFS는 누구나 쓰는 공용 세탁실처럼 리눅스 서버 여러 대가 별다른 준비 없이 들어와 함께 쓰는 기본 시설이고, FSx for Windows File Server는 회의실 예약 시스템처럼 윈도우 전용 규칙과 권한 체계를 갖춘 별도 공간입니다. FSx for Lustre는 대형 공장의 컨베이어처럼 아주 많은 데이터를 동시에 빠르게 흘려보내는 데 특화된 시설이고, FSx for NetApp ONTAP이나 FSx for OpenZFS는 기존 장비의 기능을 그대로 옮겨 오고 싶은 경우를 위한 공간입니다.

즉 제품군 안에서 각 서비스는 운영체제와 성능 특성에 따라 자기 자리를 나눠 갖습니다. 결국 EFS는 리눅스 기반의 범용 NFS 공유 파일 시스템이고, FSx는 윈도우·고성능·기존 시스템 호환 같은 특수 요구를 채우는 제품군이며, 특별한 조건이 없다면 EFS가 기본 선택이 됩니다.

EFS의 리전과 가용 영역 구조

리전 단위 서비스가 여러 가용 영역에 데이터를 두는 방식을 이해한다

회사 공용 파일 서버가 건물 한 곳에만 있으면 그 층의 전원이 나가거나 건물 출입이 막히는 날 전 직원이 자료를 열지 못합니다. 아마존 EFS(Amazon Elastic File System)는 이 문제를 한 대의 서버가 아니라 한 지역 전체에 걸친 저장소로 바꿔 해결합니다.

아파트 단지에 비유하면 리전(Region)은 도시 하나이고, 가용 영역(Availability Zone)은 그 도시 안에서 전력과 상수도가 따로 들어오는 다른 동네입니다. EFS는 파일을 한 동네 창고에만 두지 않고 여러 동네의 창고에 나눠 보관하며, 각 동네 창고가 그 동네 주민의 출입구 역할을 합니다. 그래서 한 동네가 정전으로 멈춰도 다른 동네 창고는 그대로 열려 있어 주민들은 같은 주소로 계속 물건을 찾을 수 있습니다. 다만 이 구조는 한 도시 안에서만 성립하고, 도시 자체가 다르면 같은 파일 시스템을 그대로 이어 쓰지는 못합니다.

정리하면 EFS는 리전이라는 큰 행정 구역 안에서 가용 영역 단위로 데이터를 복제해 두는 서비스이고, 그래서 한 가용 영역의 장애가 곧 파일 손실이나 전면 중단으로 이어지지 않습니다. 반대로 리전을 넘는 이중화는 별도의 복제나 백업 설계로 직접 챙겨야 합니다.

EFS 요금 구조 개요

용량·처리량·접근·백업에 각각 얼마를 내는지 큰 그림을 잡는다

저장소를 월정액처럼 생각하고 쓰기 시작하면 청구서에서 처음 보는 항목 때문에 당황하는 일이 흔합니다. EFS(Amazon Elastic File System)의 요금은 저장한 양만 보는 단일 가격이 아니라 용량, 처리량, 접근, 백업이라는 네 축으로 나뉘어 부과됩니다.

아파트 단지 창고를 빌리는 경우와 같아서, 보관 면적에 대한 월세가 용량 요금이고 짐을 나르는 엘리베이터를 얼마나 오래 점유했는지가 처리량 요금입니다. 또 출입 카드를 찍고 문을 열어 준 횟수에 붙는 수수료가 접근 요금이고, 화재에 대비해 따로 떼어 둔 사본 창고의 유지비가 백업 요금입니다.

여기서 놓치기 쉬운 것은 같은 파일이라도 자주 꺼내는지 오래 방치하는지에 따라 단가가 달라진다는 점입니다. 그래서 총비용은 데이터 크기 하나로 예측되지 않고 접근 패턴과 보관 기간이 함께 결정합니다.

실제 단가와 과금 단위는 리전과 시점에 따라 달라지므로 설계 전에 해당 리전의 공식 요금표를 확인해야 합니다. 요약하면 EFS 비용은 용량, 처리량, 접근, 백업 네 항목의 합이며 각 항목은 서로 다른 사용 습관에 반응합니다.

EFS 사용 사례

어떤 워크로드에 EFS를 쓰면 잘 맞는지 판단한다

여러 대의 서버가 같은 파일을 동시에 고쳐야 하는데 각 서버 디스크에만 파일이 있으면 어느 것이 최신인지 아무도 장담하지 못합니다. EFS(Amazon Elastic File System)는 여러 서버가 동시에 붙어 쓸 수 있는 공유 파일 저장소가 필요한 순간을 위해 존재합니다.

사무실 공용 서류 캐비닛을 떠올리면 이해가 쉽습니다. 여러 직원이 각자 책상 서랍이 아니라 같은 캐비닛에서 서류를 꺼내고, 한 사람이 고친 서류를 다음 사람이 그대로 이어 받습니다. EFS도 이처럼 여러 컴퓨트 인스턴스가 같은 디렉터리를 동시에 탑재해 읽고 쓰는 구조를 전제로 만들어졌습니다.

그래서 웹 서버 여러 대가 업로드 이미지와 세션 파일을 함께 쌓는 경우, 배치 작업과 분석 작업이 같은 원본 데이터를 나눠 읽는 경우, 컨테이너 여러 개가 설정과 산출물을 공유하는 경우에 잘 맞습니다. 리눅스의 표준 파일 접근 방식(POSIX)을 그대로 쓰기 때문에 기존 애플리케이션을 거의 고치지 않고 옮길 수 있다는 점도 같은 맥락입니다. 정리하면 EFS는 공유와 동시 접근이 핵심 요구인 리눅스 기반 워크로드에 어울리는 파일 시스템입니다.

EFS를 쓰면 안 되는 경우

EFS가 맞지 않는 워크로드를 먼저 걸러내는 기준을 세운다

파일 하나를 여러 서버가 동시에 여는 일이 거의 없는 시스템에 공유 파일 시스템을 붙이면 비용과 복잡도만 늘어납니다. EFS(Amazon Elastic File System)는 공유 파일 접근이 필요할 때 강한 도구이지만, 그 조건이 없는 워크로드에는 맞지 않습니다.

아파트 공용 창고에 비유하면, 자기 집 안에 이미 넉넉한 수납장이 있는 사람에게 단지 창고 월세를 내라고 하는 셈입니다. 창고까지 걸어가는 시간과 관리 규칙이 붙는데 얻는 이득은 없습니다.

EFS가 맞지 않는 대표적인 경우는 운영체제 부팅 디스크처럼 블록 단위 접근이 필요한 워크로드, 아주 작은 파일을 초당 수만 번 여닫는 고부하 데이터베이스, 그리고 지연 시간이 극단적으로 짧아야 하는 실시간 처리입니다. 또 윈도우의 기본 파일 공유 방식(SMB)을 그대로 써야 하는 환경이나, 한 리전을 넘어 여러 지역에서 같은 파일을 동시에 고쳐야 하는 요구도 그대로는 해결되지 않습니다. 접근 빈도가 아주 낮고 보관만 오래 하는 데이터라면 더 저렴한 객체 저장소가 나은 선택인 경우가 많습니다.

결론적으로 공유가 필요 없거나, 블록 수준 제어가 필요하거나, 지연 시간 기준이 매우 엄격한 워크로드는 EFS를 첫 후보에서 빼는 것이 맞습니다.

파일 시스템 리소스(File System)

EFS에서 파일 시스템 하나가 무엇을 담는 단위인지 안다

서버를 새로 만들 때마다 저장 공간의 크기와 이름을 그때그때 정하면, 나중에 어느 저장소가 어느 팀의 것인지 아무도 정리하지 못하게 됩니다. EFS(Amazon Elastic File System)에서 파일 시스템(File System)은 이런 저장 공간을 하나의 이름과 하나의 신원으로 묶어 관리하는 기본 단위입니다.

아파트 단지의 창고 건물 한 동에 비유할 수 있습니다. 그 건물에는 고유한 주소가 붙고, 안에 들어갈 수 있는 사람과 보관 규칙이 따로 정해지며, 건물 단위로 관리비와 보험을 계산합니다. EFS의 파일 시스템도 마찬가지로 생성 시 정한 리전과 이름, 성능 모드와 처리량 모드, 암호화와 수명 주기 같은 설정을 자기 것이고, 그 아래 디렉터리와 파일이 모두 이 단위에 속합니다.

실제 용량은 미리 정하지 않아도 쓰는 만큼 늘어나고 줄어들기 때문에, 크기를 산정하는 대신 무엇을 담을지와 어떻게 보호할지를 정하는 것이 생성의 핵심입니다. 하나의 파일 시스템에는 여러 가용 영역의 탑재 대상이 붙어 여러 서버가 같은 건물에 동시에 드나들 수 있습니다.

정리하면 파일 시스템은 EFS에서 저장 공간, 접근 제어, 성능과 보호 정책이 한꺼번에 묶이는 관리 단위입니다.

탑재 대상도 가용 영역마다 하나씩 만들어지고, 각 대상은 그 가용 영역 안의 서브넷에 네트워크 주소를 갖습니다. 서버는 같은 가용 영역의 탑재 대상으로 접속할 때 가장 짧은 경로를 쓰고, 다른 가용 영역의 대상으로도 접속할 수는 있지만 그만큼 멀리 돌아갑니다. 그래서 가용 영역마다 탑재 대상을 두는 것이 지연 시간과 장애 대비의 기본형이며, 보안 그룹과 네트워크 접근 제어로 누가 이 정문을 지나갈 수 있는지 정합니다.

결론적으로 탑재 대상은 VPC 안에서 EFS로 들어가는 가용 영역별 출입구이고, 서버가 파일 시스템을 보려면 반드시 이 문을 통해야 합니다.

EFS의 데이터 저장 방식

파일이 여러 가용 영역에 어떻게 중복 저장되는지 안다

회사에서 중요한 계약서를 사무실 캐비닛 한 곳에만 보관하다가 그 건물에 화재가 나면 서류를 통째로 잃게 됩니다. 파일 서버도 한 데이터센터에만 자료를 두면 그곳이 멈추는 순간 서비스 전체가 멈추므로, 아마존은 파일을 여러 곳에 나눠 보관하는 Amazon EFS(Elastic File System, 관리형 파일 스토리지)를 내놓았습니다.

EFS의 저장 방식을 이해할 때는 여러 지점에 사본을 두는 회사의 문서 보관 체계를 떠올리면 쉽습니다. 회사는 원본 한 부만 남기는 대신 도시 곳곳의 창고에 같은 서류를 복제해 두고, 한 창고가 문을 닫아도 다른 창고에서 바로 꺼내 씁니다.

EFS도 파일 데이터를 하나의 리전(region, 지리적으로 묶인 데이터센터 군) 안에 있는 여러 가용 영역(Availability Zone, 서로 떨어진 데이터센터 묶음)에 걸쳐 중복 저장합니다. 창고마다 서류를 조금씩 나눠 넣고 각 조각의 사본을 다른 창고에 두듯, EFS는 데이터를 나눠 저장하면서 사본을 서로 다른 가용 영역에 배치합니다.

그래서 한 가용 영역에 장애가 생겨도 나머지 가용 영역의 사본으로 같은 파일을 계속 읽고 쓸 수 있습니다. 결국 EFS는 파일 데이터를 리전 내 여러 가용 영역에 자동으로 복제해 두는 관리형 파일 스토리지이며, 사용자는 복제 설정을 직접 만들지 않아도 이 중복성을 얻습니다.

EFS의 일관성 모델

여러 클라이언트가 볼 때 변경이 언제 반영되는지 이해한다

여러 서버가 같은 파일을 동시에 열어 놓고 한쪽이 고친 내용이 다른 쪽 화면에는 보이지 않는다면, 운영자는 어느 쪽이 진짜 최신인지 알 수 없어 혼란에 빠집니다. 이 문제를 규칙으로 정리한 것이 일관성 모델(consistency model)이고, EFS는 NFS(Network File System, 네트워크로 파일을 공유하는 표준)를 기반으로 자기만의 일관성 규칙을 제공합니다.

이때 회의실 공용 문서함을 떠올리면 이해가 쉽습니다. 사람들은 문서함에서 서류를 꺼내 자기 책상에서 읽고, 수정한 뒤 다시 넣을 때 문서함의 내용이 바뀝니다.

EFS는 이런 방식에 가까운 close-to-open 일관성(닫을 때와 열 때를 기준으로 최신성을 맞추는 규칙)을 따르는데, 파일을 닫는 시점에 변경 내용이 서버에 반영되고 파일을 다시 여는 시점에 최신 상태를 확인합니다. 그래서 이미 열어 둔 다른 클라이언트는 그 파일을 닫았다가 다시 열기 전까지 예전 내용을 볼 수 있습니다.

같은 파일을 여러 곳에서 동시에 수정하면 마지막에 기록된 내용이 남는 쪽으로 동작하므로, 동시 쓰기가 많은 작업은 응용 프로그램 쪽에서 조율하는 편이 안전합니다. 정리하면 EFS는 파일을 열고 닫는 시점을 기준으로 최신성을 보장하는 close-to-open 일관성을 제공하며, 이 규칙을 알아야 여러 서버가 함께 쓰는 환경에서 데이터를 오해하지 않습니다.

EFS의 메타데이터 동작

파일 이름·크기·권한 같은 정보를 어떻게 다루는지 안다

파일 서버가 파일 내용은 갖고 있지만 그 파일의 이름이나 소유자 정보를 잃어버리면, 자료는 분명히 존재하는데 아무도 찾아 쓰지 못하는 상황이 됩니다. 이렇게 파일에 딸린 정보를 다루는 부분이 메타데이터(metadata, 데이터를 설명하는 데이터)이고, EFS는 이 정보를 사용자 대신 관리해 줍니다.

도서관에 비유하면 서가에 꽂힌 책 내용이 데이터이고, 책등 라벨과 대출 카드에 적힌 위치와 상태가 메타데이터입니다. 사서가 라벨을 붙이고 대출 기록을 관리하듯, EFS는 파일 이름과 크기, 소유자, 권한, 생성 및 수정 시각 같은 POSIX(Portable Operating System Interface, 유닉스 계열 표준 규격) 메타데이터를 자동으로 붙이고 관리합니다.

이용자는 별도의 데이터베이스를 두지 않아도 되지만, 이런 정보를 읽고 고치는 작업은 파일 내용을 순서대로 읽는 것과 처리 경로가 달라 지연이 더 생길 수 있습니다. 실제로 작은 파일이 아주 많을 때 목록을 훑는 작업이 느리게 느껴지는 이유가 여기에 있습니다.

결국 EFS는 POSIX 메타데이터를 관리형으로 제공하는 대신, 메타데이터를 많이 건드리는 작업에서는 그 성능 특성을 미리 고려해야 합니다.

EFS의 파일 잠금(File Locking)

여러 서버가 같은 파일을 동시에 쓸 때의 잠금 방식을 안다

두 서버가 같은 파일을 동시에 열어 각자 내용을 고쳐 저장하면, 나중에 저장한 쪽이 앞서 저장한 내용을 조용히 덮어써 버립니다. 이런 사고를 막으려고 한쪽이 쓰는 동안 다른 쪽이 손대지 못하게 막는 장치가 파일 잠금(File Locking)이며, EFS는 NFS 규격의 잠금 기능을 통해 이를 제공합니다.

공용 회의실 문에 사용 중 팻말을 걸어 두는 모습을 생각하면 이해가 쉽습니다. 누군가 회의실을 쓰기 시작하면 팻말을 걸고, 다 쓰면 팻말을 떼어 다음 사람이 들어가게 하는 것과 같습니다.

EFS의 잠금은 파일 전체에 걸 수도 있고 파일 안의 특정 바이트 구간에만 걸 수도 있는데, 이는 문서 전체를 잠그는 대신 특정 페이지에만 표시를 붙이는 것에 해당합니다. 다만 이것은 권고형 잠금(advisory lock)이라서, 팻말을 무시하고 들어가는 프로그램은 막을 수 없으므로 잠금을 지키는 책임은 응용 프로그램에 있습니다.

잠금은 클라이언트 연결과 묶여 있어 연결이 끊기면 자동으로 풀리므로, 비정상 종료 뒤에 잠금이 영구히 남는 일은 줄어듭니다. 결국 EFS의 파일 잠금은 여러 서버가 같은 파일을 다룰 때 순서를 맞추는 NFS 기반의 협조적 장치이며, 이를 쓰는 프로그램이 규칙을 지켜야 효과가 있습니다.

EFS의 하드 링크와 심볼릭 링크

POSIX 링크가 EFS에서 어떻게 동작하는지 안다

같은 문서를 여러 부서에서 서로 다른 이름으로 접근해야 할 때 파일을 통째로 복사해 두면, 한쪽만 고쳐져 내용이 서로 어긋나는 문제가 생깁니다. 복사 대신 같은 데이터를 가리키는 두 번째 이름을 붙이는 방법이 링크(link)이며, EFS는 POSIX 파일 시스템으로서 하드 링크와 심볼릭 링크를 다룹니다.

아파트 현관을 여러 개 두는 경우와 사물함에 쪽지를 붙이는 경우를 나란히 떠올리면 두 방식의 차이가 보입니다. 하드 링크(hard link)는 같은 데이터에 이름표를 하나 더 붙이는 것으로, 어느 이름으로 열어도 똑같은 원본을 보며 원본이라는 구분 자체가 사라집니다. 심볼릭 링크(symbolic link)는 다른 이름표를 가리키는 쪽지를 붙이는 것으로, 실제 파일이 아니라 경로를 적어 둔 안내판에 가깝습니다.

그래서 하드 링크는 같은 파일 시스템 안에서만 만들 수 있고 원본 이름을 지워도 데이터가 남지만, 심볼릭 링크는 원본 경로가 사라지면 가리킬 곳을 잃고 깨집니다. EFS 환경에서 이 두 링크를 쓰는 도구나 운영체제에 따라 지원 범위가 조금씩 다를 수 있으므로, 실제 적용 전에 확인하는 편이 안전합니다.

정리하면 하드 링크는 하나의 데이터를 여러 이름이 공유하는 방식이고 심볼릭 링크는 경로를 통해 다른 파일을 가리키는 방식이며, 이 차이를 알아야 파일 정리와 배포를 안전하게 설계할 수 있습니다.

EFS의 파일 크기와 이름 제한

실제로 부딪히는 한계값을 정리한다

하루치 로그를 한 파일에 계속 이어 붙이다가 어느 순간 쓰기가 거부되면, 원인을 규격 한계에서 찾지 못해 한참을 헤매게 됩니다. EFS에도 파일 하나의 크기와 이름, 경로 길이에 분명한 한계가 있으므로 미리 알아 두어야 합니다.

창고 사물함의 크기와 이름표에 쓸 수 있는 글자 수가 정해져 있는 모습을 떠올리면 이해가 쉽습니다. 사물함이 아무리 커도 정해진 크기를 넘을 수 없고, 이름표 칸이 좁으면 긴 이름을 붙일 수 없듯, EFS에서도 파일 하나의 최대 크기와 이름 길이가 정해져 있습니다.

일반적으로 파일 하나는 수십 테비바이트(TiB, 1024기가바이트의 1024배) 규모까지 커질 수 있지만 그 이상은 허용되지 않고, 파일 이름은 255바이트 안팎으로 제한되어 한글 이름은 글자당 3바이트를 쓰므로 글자 수가 훨씬 줄어듭니다. 전체 경로 길이에도 상한이 있어 디렉터리를 지나치게 깊게 겹치면 문제가 생길 수 있습니다.

이런 수치는 서비스 지역이나 시점에 따라 달라질 수 있으므로 설계 단계에서 공식 문서의 최신 값을 확인하는 것이 좋습니다. 결국 EFS를 쓸 때는 파일 크기와 이름, 경로 길이의 한계를 먼저 확인하고 그 안에서 데이터 구조를 잡아야 예상치 못한 쓰기 실패를 피할 수 있습니다.

EFS와 POSIX 의미론

리눅스의 파일 권한·소유권 규칙이 그대로 적용되는 방식을 이해한다

여러 서버가 같은 폴더를 함께 쓰기 시작하면, 파일마다 누가 주인이고 누가 열어 볼 수 있는지가 서버마다 달라져 곤란한 일이 생깁니다. 어떤 서버가 만든 파일을 다른 서버가 열어 보지도 못하고, 관리자는 그 차이를 설명할 방법을 찾지 못합니다. 그래서 아마존 EFS(Amazon Elastic File System)는 리눅스가 파일을 다루는 표준 규칙인 POSIX(Portable Operating System Interface) 의미론을 그대로 지키는 공유 저장소로 만들어졌습니다.

회사의 공용 사물함을 떠올리면 이해가 쉽습니다. 사물함마다 주인이 적혀 있고(소유자), 같은 팀 사람들이 함께 쓰는 칸이 정해져 있으며(그룹), 읽기·쓰기·실행 가운데 무엇이 허용되는지가 붙어 있습니다(권한).

EFS도 똑같이 파일마다 소유자와 그룹, 그리고 읽기·쓰기·실행 권한을 숫자와 문자로 기록하고, 접속한 사용자가 그 규칙에 맞는지만 확인한 뒤 통과시킵니다. 덕분에 리눅스 서버에 로그인한 사용자와 같은 아이디·그룹 정보를 가진 사람만 정해진 방식으로 파일을 건드릴 수 있습니다.

결국 EFS는 단순한 저장 공간이 아니라, 리눅스의 사용자·그룹·권한 체계를 네트워크 너머에서도 그대로 유지하는 파일 시스템입니다. 서버마다 규칙을 따로 만들 필요 없이, 이미 익숙한 권한 관리 방식을 공유 저장소에 그대로 적용할 수 있습니다.

EFS의 탄력적 확장

용량을 미리 정하지 않고 자동으로 늘어나는 원리를 이해한다

저장 용량을 미리 사 두는 방식은 늘 곤란합니다. 넉넉히 사면 남는 공간에 돈을 계속 내야 하고, 아슬아슬하게 사면 파일이 쌓이는 순간 자리가 모자라 서비스가 멈춥니다. 아마존 EFS는 이 딜레마를 없애기 위해 용량을 미리 정하지 않고 쓰는 만큼 자동으로 늘어나는 탄력적 확장(elastic scaling)을 기본으로 합니다.

벽이 스스로 늘어나는 사무실 창고를 생각하면 됩니다. 물건을 넣을수록 선반이 자동으로 붙어 공간이 넓어지고, 물건을 치우면 그만큼 다시 줄어듭니다.

관리자가 창고 크기를 계약할 필요가 없고, 요금은 실제로 점유한 공간만큼만 매달 계산됩니다. EFS에서 파일을 쓰면 파일 시스템이 알아서 커지고, 지우면 사용량이 줄어 청구서에도 그대로 반영됩니다.

결론적으로 EFS의 확장은 사람이 개입하는 증설 작업이 아니라, 파일 사용량을 따라 저장 공간과 과금이 함께 움직이는 구조입니다. 용량 계획에 쓰던 시간을 줄이고, 갑자기 늘어난 데이터에도 중단 없이 대응할 수 있습니다.

EFS 파일 시스템 생성 절차

콘솔에서 파일 시스템을 만드는 순서를 따라 한다

처음 콘솔을 열면 파일 시스템을 만들면서 무엇을 먼저 정해야 하는지 몰라 화면 앞에서 막막해집니다. 항목이 많고, 잘못 고르면 나중에 서버에서 접속조차 되지 않기 때문입니다. 아마존 EFS에서 파일 시스템을 만드는 일은 이삿짐 보관 창고를 계약하는 절차와 비슷합니다.

먼저 창고 이름과 위치를 정하고(이름과 리전), 어느 단지 안에 둘지 고르며(VPC와 서브넷), 출입할 수 있는 사람 명단을 등록합니다(보안 그룹). 마지막으로 각 동마다 찾아갈 출입구를 세우면(탑재 대상), 그때부터 서버들이 주소로 창고를 찾아갈 수 있습니다.

순서를 지키는 것이 중요합니다. 네트워크와 접근 규칙을 먼저 정해 두어야 출입구를 세울 때 연결 검증이 통과하기 때문입니다.

결론적으로 콘솔에서의 생성 절차는 이름과 리전을 정하고, VPC·서브넷을 고르고, 보안 그룹을 붙이고, 탑재 대상을 만드는 네 단계로 정리됩니다. 한 번 만들어 두면 이후에는 여러 서버가 같은 파일 시스템을 주소만으로 함께 사용하게 됩니다.

VPC와 서브넷 선택

파일 시스템을 어느 네트워크에 둘지 정한다

파일 시스템을 회사 밖 아무 네트워크에나 두면, 정작 필요한 서버들은 접속하지 못하고 관계없는 곳에는 문이 열려 있는 상태가 됩니다. 그래서 EFS는 만들 때 어느 가상 네트워크에 둘지 정하게 합니다. 이 가상 네트워크를 VPC(Virtual Private Cloud)라고 부릅니다.

아파트 단지를 떠올리면 구조가 분명해집니다. VPC는 담장으로 둘러싸인 단지 전체이고, 서브넷은 그 안의 동이며, 각 동은 특정 가용 영역(Availability Zone)에 놓입니다. 파일 시스템은 단지 안에 지어지고, 서버가 접속하려면 같은 단지 안에서 동을 골라 들어가야 합니다.

즉 서브넷 선택은 창고를 어느 동 옆에 붙일지 정하는 일이며, 여러 동에 걸쳐 두면 어느 동에서든 가까운 출입구로 갈 수 있습니다.

결론적으로 VPC는 격리된 가상 네트워크, 서브넷은 가용 영역 단위의 구획이고, EFS는 그 구획들 안에서만 접근을 허용합니다. 이 구조 덕분에 파일 시스템은 인터넷에 직접 노출되지 않고 허용된 네트워크 안에서만 보입니다.

EFS용 보안 그룹 설정

NFS 2049 포트를 여는 인바운드 규칙을 만든다

파일 시스템을 다 만들었는데 서버에서 접속이 계속 시간 초과로 끝나는 경우가 흔합니다. 원인은 대개 네트워크 문을 열어 주지 않았기 때문입니다. EFS는 NFS(Network File System)라는 방식으로 파일을 주고받고, 이 방식은 2049번 포트를 사용합니다.

아파트 경비실의 출입 명단을 생각하면 됩니다. 보안 그룹은 건물에 들어올 수 있는 사람과 창구를 적어 둔 명단이고, 인바운드 규칙은 바깥에서 안으로 들어오는 방향의 허용 항목입니다.

명단에 2049번 창구를 열어 두지 않으면, 서버가 아무리 정확한 주소를 알아도 경비실에서 막힙니다. 그래서 EFS 쪽 보안 그룹에는 파일 시스템에 접속할 서버들의 보안 그룹을 소스로 지정하고, TCP 2049 포트를 허용하는 인바운드 규칙을 넣습니다.

결론적으로 EFS용 보안 그룹 설정의 핵심은 출처를 좁게 지정한 상태에서 NFS 포트인 TCP 2049를 인바운드로 여는 것입니다. 필요한 서버만 명단에 올리면 나머지 트래픽은 그대로 차단되므로, 편의와 안전을 함께 가져갈 수 있습니다.

탑재 대상 생성과 배치

가용 영역마다 탑재 대상을 두는 이유와 방법을 안다

탑재 대상을 만들지 않으면 서버는 파일 시스템의 주소를 알더라도 실제로 닿을 지점이 없어 연결에 실패합니다. 또 한 곳에만 두면 다른 가용 영역의 서버가 먼 길을 돌아가며 지연과 비용이 늘어납니다. 탑재 대상(mount target)은 파일 시스템에 접속할 수 있게 각 가용 영역에 세우는 출입구입니다.

아파트 단지의 각 동 출입구와 같습니다. 동마다 출입구가 있어야 그 동 주민이 바로 드나들 수 있고, 출입구가 한 동에만 있으면 나머지 동 사람들은 단지를 한 바퀴 돌아야 합니다.

그래서 EFS는 가용 영역마다 탑재 대상을 하나씩 두고, 각 대상에 그 서브넷의 사설 IP 주소를 붙입니다. 서버는 같은 가용 영역의 출입구로 접속하도록 이름이 자동으로 안내되므로, 다른 동으로 우회하는 일이 줄어듭니다.

결론적으로 탑재 대상은 가용 영역별 접속 지점이며, 여러 곳에 고르게 배치할수록 가용성과 응답 속도가 좋아집니다. 하나의 가용 영역이 흔들려도 다른 영역의 출입구가 남아 있어 서비스가 전부 멈추지 않습니다.

리눅스에서 EFS 마운트하기

mount 명령으로 파일 시스템을 붙이는 기본 절차를 익힌다

여러 대의 서버가 같은 자료를 나눠 써야 하는데 각 서버가 자기 디스크에만 파일을 두고 있다면, 한 대에서 고친 내용을 다른 대에서는 볼 수 없어 같은 작업을 서버마다 되풀이해야 합니다. 이때 네트워크 너머에 있는 공용 저장소를 내 서버의 디렉터리처럼 붙여 주는 작업이 마운트(mount)이고, 리눅스에서는 mount 명령으로 이것을 수행합니다.

아파트 단지에 공용 창고가 하나 있고 각 세대가 그 창고를 함께 쓴다고 생각해 보십시오. 세대 현관 옆에 창고로 통하는 문을 하나 내면 집 안에서 짐을 꺼내듯 창고 물건을 꺼낼 수 있는데, EFS(Elastic File System)가 그 공용 창고이고 서버의 빈 디렉터리가 문이 달릴 자리인 마운트 지점(mount point)입니다. mount 명령은 창고 주소에 해당하는 파일 시스템 ID나 DNS 이름과 문을 달 자리를 함께 지정해 그 문을 실제로 다는 시공이며, 문을 달기 전에는 그 자리가 아무것도 없는 빈 방이지만 문이 달리는 순간부터 그 방 안에 창고의 물건이 그대로 보입니다.

정리하면 EFS 마운트는 네트워크 파일 시스템을 로컬 디렉터리에 연결해 하나의 파일 구조처럼 보이게 만드는 일이고, mount 명령은 그 연결을 맺는 기본 절차입니다.

/etc/fstab에 영구 마운트 등록

재부팅 뒤에도 자동으로 붙게 설정한다

서버를 다시 켤 때마다 공용 저장소 연결이 끊겨 업무 프로그램이 파일을 찾지 못하고 멈춰 버리는 일이 흔합니다. 그래서 리눅스는 부팅 과정에서 읽는 목록 파일에 연결 정보를 적어 두는데, 그것이 /etc/fstab입니다.

이사할 때마다 매번 전화로 가구를 옮겨 달라고 하는 대신, 관리 사무소에 우리 집 창고 문은 늘 이 자리에 달아 달라고 적어 두는 장부를 떠올리면 이해가 쉽습니다. 그 장부의 한 줄에는 어떤 창고를 쓸지에 해당하는 장치 이름, 어느 자리에 문을 달지에 해당하는 마운트 지점, 어떤 방식으로 오갈지에 해당하는 파일 시스템 종류와 옵션이 나란히 적힙니다. 부팅할 때 시스템은 이 장부를 위에서 아래로 읽으며 각 줄을 하나씩 실행해 창고 문을 다시 답니다. 다만 잘못 적어 둔 줄이 있으면 부팅이 지연되거나 멈출 수 있으므로, 연결이 실패해도 부팅을 막지 않게 하는 옵션을 함께 두는 것이 좋습니다.

결국 /etc/fstab은 재부팅 뒤에도 마운트가 자동으로 유지되도록 연결 조건을 선언해 두는 설정 파일이고, 그 한 줄이 부팅 때 실행되는 mount 명령의 묶음 역할을 합니다.

EFS 마운트 헬퍼(amazon-efs-utils)

마운트 헬퍼가 대신 처리해 주는 일을 안다

mount 명령만으로 EFS를 붙이려면 주소를 확인하고 전송 방식과 옵션을 일일이 맞춰야 해서, 담당자가 바뀌면 같은 작업을 다시 익혀야 하는 부담이 생깁니다. 이 반복을 줄이려고 나온 것이 마운트 헬퍼인 amazon-efs-utils이고, 이것은 mount 명령이 특정 파일 시스템 종류를 만났을 때 대신 불려 나오는 도우미 프로그램입니다.

이삿짐을 옮길 때마다 트럭을 직접 빌리고 경로를 짜는 대신 이사 전문 업체에 맡기면 짐을 싸고 운반하고 자리를 잡는 일을 한 번에 처리해 주는 것과 같습니다. mount 명령에 파일 시스템 종류로 efs를 지정하면 헬퍼가 호출되어 접속 주소 해석과 필요한 옵션 구성, 그리고 전송 구간 암호화(TLS) 설정 같은 번거로운 절차를 대신 처리합니다. 또한 헬퍼에 함께 들어 있는 감시 프로그램이 마운트가 살아 있는지 주기적으로 확인해 끊어지면 다시 붙이는 일을 맡습니다.

정리하면 amazon-efs-utils는 EFS 마운트에 필요한 준비와 점검을 한 줄의 명령 뒤로 감춰 주는 도구이며, 사용자는 주소와 마운트 지점만 정하면 됩니다.

EFS 마운트 옵션 이해

vers·rsize·wsize·hard/soft 같은 옵션을 읽을 줄 안다

같은 저장소를 붙였는데 어떤 서버는 빠르게 동작하고 어떤 서버는 이유 없이 멈춰 서는 차이는 대개 마운트 옵션에서 갈립니다. 옵션은 서버와 저장소가 어떤 규칙으로 대화하고 자료를 주고받을지 정하는 값이며, vers, rsize, wsize, hard와 soft 같은 이름으로 표시됩니다.

이삿짐을 나르는 규칙에 빗대면 vers는 몇 번째 판의 대화법으로 이야기할지 정하는 것이고, rsize와 wsize는 한 번에 통째로 옮기는 짐 덩어리의 크기입니다. hard와 soft는 창고 문이 열리지 않을 때의 태도 차이로, hard는 문이 열릴 때까지 무한정 기다리고 soft는 정해진 시간이 지나면 포기하고 오류를 돌려줍니다. 데이터를 다루는 서버라면 잠깐의 지연을 견디고 끝까지 기다리는 hard가 안전하고, 기다리느라 화면이 멈추면 안 되는 작업이라면 soft를 검토하게 됩니다.

결국 이 옵션들은 대화 규칙과 전송 단위, 실패 시의 태도를 정하는 값이며, 업무 성격에 맞춰 고르는 것이 마운트 안정성을 좌우합니다.

TLS 마운트 설정

전송 중 암호화를 켜서 마운트하는 방법을 익힌다

공용 저장소로 오가는 자료에는 계약서나 고객 정보처럼 남에게 보이면 곤란한 내용이 섞이기 쉬운데, 암호화 없이 붙이면 같은 망을 지나는 사람이 내용을 들여다볼 수 있습니다. 그래서 EFS는 전송 구간만 암호화하는 방식인 TLS(Transport Layer Security)를 켠 마운트를 지원합니다.

공용 창고로 가는 길이 누구나 지나는 복도라면, 짐을 그대로 들고 걷는 대신 잠금 상자에 넣어 나르는 것과 같습니다. 상자를 여는 열쇠는 양쪽만 가지고 있으므로 길에서 상자를 들여다봐도 내용은 알 수 없고, 도착한 뒤에야 짐이 꺼내집니다. 실제로는 amazon-efs-utils의 헬퍼가 TLS 연결을 대신 맺어 주며, mount 명령에 tls 옵션을 붙여 이 방식을 켭니다. 다만 이 방식은 전송 중인 자료를 지킬 뿐 저장된 자료 자체를 암호화하지는 않으므로, 저장 상태의 암호화는 별도 설정으로 다룹니다.

정리하면 TLS 마운트는 서버와 EFS 사이를 오가는 통로에 암호화를 두르는 설정이고, 켜 두면 같은 망을 쓰는 다른 이용자로부터 자료를 지킬 수 있습니다.

윈도우에서 EFS 접근

윈도우 클라이언트로 EFS를 쓰는 방법과 제약을 안다

리눅스 서버끼리는 잘 붙던 저장소가 윈도우 PC에서는 드라이브처럼 보이지 않아 당황하는 경우가 많습니다. EFS는 리눅스 계열에서 널리 쓰이는 NFS(Network File System) 방식으로 공유되기 때문에, 윈도우가 기본으로 쓰는 공유 방식과 규격이 다르기 때문입니다.

다른 나라 전자제품을 가져왔을 때 플러그 모양이 달라 바로 꽂히지 않고 어댑터가 필요한 상황과 같습니다. 윈도우에는 NFS를 다루는 기능이 별도 구성 요소로 들어 있어 이를 켜야 하고, 그 뒤에야 원격 저장소를 네트워크 드라이브처럼 연결할 수 있습니다. 이때 윈도우 사용자 계정과 저장소 쪽 접근 권한을 어떻게 맞출지가 관건이 되며, 이 설정이 어긋나면 연결은 되는데 파일을 열지 못합니다. 또 리눅스에서 쓰던 방식과 성능이나 파일 잠금 동작이 같지 않을 수 있으므로, 여러 사람이 같은 파일을 동시에 고치는 업무라면 미리 시험해 보는 것이 안전합니다.

정리하면 윈도우에서 EFS를 쓰려면 NFS를 다루는 기능을 켜고 권한을 맞춰야 하며, 리눅스와 똑같이 동작한다고 가정하지 않는 것이 좋습니다.

온프레미스에서 EFS 접근

VPN·Direct Connect로 사내 서버에서 붙이는 구성을 안다

사내 서버실에서 돌던 배치 프로그램을 AWS로 옮겼는데, 그 프로그램이 읽어야 할 데이터는 클라우드의 공유 저장소에만 쌓여 있어 사내 서버가 아무리 찾아도 손이 닿지 않는 일이 생깁니다. 이때 사내 네트워크와 AWS를 VPN(Virtual Private Network, 암호화된 가상 사설 통로)이나 Direct Connect(전용 회선)로 이어 붙이면, 사내 서버도 EFS(Elastic File System, AWS의 관리형 공유 파일 저장소)를 자기 디스크처럼 마운트해 쓸 수 있습니다.

이 구성을 본사 건물과 신관 건물에 빗대어 보면 이해가 쉽습니다. EFS는 신관에 있는 공용 창고이고, 사내 서버는 본사에 앉은 직원이며, VPN은 두 건물 사이에 임시로 놓인 보안 통로, Direct Connect는 두 건물을 곧장 잇는 전용 복도입니다. 직원은 통로를 지나 창고 문 앞에 도착한 뒤 출입증을 대야 하는데, 이 출입증에 해당하는 것이 보안 그룹과 NFS(Network File System) 포트 허용 규칙입니다.

통로가 뚫려 있어도 출입증이 없거나 창고 주소를 잘못 적으면 문은 열리지 않습니다.

정리하면 온프레미스에서 EFS로 접근하는 일은 네트워크 연결(VPN 또는 Direct Connect), 라우팅과 DNS 이름 해석, 보안 그룹의 NFS 허용, 마운트 권한이라는 조건을 모두 만족할 때 성립합니다. 전용 회선은 대역폭과 안정성이 좋고 VPN은 빠르게 구성할 수 있다는 차이가 있습니다.

택배가 오지 않을 때를 떠올려 보면 점검 순서가 자연스럽게 그려집니다. 먼저 주소가 맞는지 확인하고, 다음으로 건물 현관까지 도로가 뚫려 있는지 보고, 그다음 경비실 출입 허가와 문 비밀번호를 확인합니다. EFS에서 주소는 파일 시스템 ID와 DNS 이름, 도로는 서브넷과 라우팅, 출입 허가는 보안 그룹과 네트워크 ACL의 NFS 포트 허용, 문 비밀번호는 IAM 권한과 마운트 헬퍼 설정에 해당합니다.

성능 모드(Performance Mode)

범용과 최대 I/O 두 모드가 무엇을 다르게 하는지 이해한다

수십 대의 서버가 같은 파일을 동시에 열어 작업하는 순간, 저장소는 데이터를 읽는 일보다 누가 먼저 들어왔는지 정리하는 일에 더 많은 힘을 쓰게 됩니다. EFS는 이런 갈등을 다루는 방식을 성능 모드(Performance Mode)라는 두 가지 선택지로 나누어 제공하며, 범용(General Purpose)과 최대 I/O(Max I/O)가 그것입니다.

아파트 단지 정문의 차량 통과 방식을 떠올리면 두 모드의 차이가 선명해집니다. 범용 모드는 차량을 한 줄로 세워 한 창구에서 빠르게 확인하는 방식이라 대기 시간이 짧고 순서가 안정적이지만, 동시에 몰리는 차량 수가 많아지면 줄이 길어집니다. 최대 I/O 모드는 차로를 여러 개 열어 두고 여러 차량을 동시에 통과시키는 방식이라 한 대의 대기 시간은 조금 늘어도 전체 처리량은 크게 올라갑니다.

두 모드는 파일 시스템을 만들 때 정하게 되며, 운영 중 변경에는 제약이 따르므로 처음 선택을 신중히 하는 것이 좋습니다.

결국 성능 모드는 동시 접속을 얼마나 많이 받아낼지와 개별 요청이 얼마나 빨리 끝날지를 맞바꾸는 설정입니다. 접속 수가 적고 응답이 빠르면 좋은 워크로드는 범용, 동시 접속이 매우 많은 워크로드는 최대 I/O가 어울립니다.

작은 동네 문구점을 떠올려 보면 이 모드의 성격이 잘 드러납니다. 손님이 몇 명 안 되는 가게에서는 계산대 하나만 있어도 줄이 생기지 않고, 점원이 손님과 눈을 맞추며 바로바로 응대하므로 기다리는 시간이 짧습니다. 범용 모드도 마찬가지로 파일을 여는 요청 하나하나를 빠르게 처리하며, 여러 서버가 붙어도 각 요청의 응답이 늦어지지 않습니다.

다만 계산대가 하나뿐이므로 손님이 갑자기 몰리면 초당 처리할 수 있는 요청 수에 한계가 드러납니다.

정리하면 범용 성능 모드는 낮은 지연 시간과 예측 가능한 응답을 내세우는 기본 모드이고, 동시 요청 수가 극단적으로 많지 않은 대부분의 업무에 적합합니다. 처리량 자체는 성능 모드보다 처리량 모드 설정으로 조정하는 것이 일반적입니다.

처리량을 정하는 세 가지 방식을 구분한다

같은 파일 시스템을 쓰는데 어떤 팀은 데이터가 잘 흐른다 하고 어떤 팀은 복사만 하면 한없이 느리다고 말하는 차이는 대개 처리량 설정에서 갈립니다. EFS는 처리량 모드(Throughput Mode)라는 이름으로 처리량을 정하는 세 가지 방식을 제공하며, 버스팅(Bursting), 프로비저닝(Provisioned), 엘라스틱(Elastic)이 그것입니다.

인터넷 요금제를 고르는 상황에 빗대면 세 방식이 한눈에 구분됩니다.

버스팅은 기본으로 쓸 수 있는 양이 저장한 데이터 양에 비례해 정해지고, 남는 한도가 있으면 순간적으로 더 빠르게 쓰는 방식입니다. 프로비저닝은 필요한 속도를 미리 정해 고정으로 사 두는 정액 요금제라서, 저장량과 무관하게 원하는 처리량을 확보할 수 있습니다. 엘라스틱은 실제 사용량에 맞춰 속도가 자동으로 늘고 줄어드는 방식이라, 몰렸다 비는 패턴이 불규칙한 업무에 잘 맞습니다.

정리하면 처리량 모드는 저장량에 비례해 몰아쓰는 버스팅, 원하는 속도를 미리 확보하는 프로비저닝, 사용량을 따라 자동으로 조절되는 엘라스틱으로 나뉩니다. 처리량 모드는 워크로드 변화에 따라 나중에 바꿀 수 있으므로, 처음에는 관측 결과를 보고 조정하는 편이 안전합니다.

기준 처리량과 크레딧으로 순간적으로 늘리는 원리를 안다

여러 서버가 같은 파일 저장소를 함께 쓰는 환경에서, 평소에는 조용하던 작업이 특정 시간에만 몰리면 저장소가 그 순간만큼은 버텨 주지 못해 대기 시간이 길어집니다. 이때 평소의 여유를 모아 두었다가 필요한 순간에 꺼내 쓰게 하는 방식이 Amazon EFS의 버스팅 처리량 모드(Bursting Throughput)입니다. 이 원리는 택배 회사가 평소 정해진 대수의 트럭으로 배송하는 모습과 같습니다. 회사는 매일 기본으로 쓸 수 있는 트럭 대수, 즉 기준 처리량(Baseline Throughput)을 정해 두는데, 이 값은 파일 시스템의 크기에 비례해 커집니다. 한가한 날 트럭을 덜 썼다면 그만큼의 여유가 크레딧(Credit)이라는 형태로 쌓이고, 물량이 몰리는 날에는 쌓아 둔 크레딧을 풀어 정해진 대수보다 많은 트럭을 한꺼번에 부릅니다.

크레딧이 바닥나면 다시 기본 트럭 대수로 돌아가므로, 순간적인 폭주에는 강하지만 오래 이어지는 부하는 감당하지 못합니다. 정리하면 버스팅 처리량 모드는 파일 시스템 크기에서 나오는 기준 처리량과, 쓰지 않고 남긴 처리량이 적립되는 크레딧을 합쳐 순간 처리량을 끌어올리는 방식입니다.

필요한 처리량을 직접 정해 고정으로 확보하는 방법을 안다

파일 시스템의 크기가 작은데도 많은 서버가 동시에 큰 파일을 읽고 써야 하는 환경이라면, 크기에 따라 처리량이 정해지는 방식은 애초에 출발선이 불리합니다. 필요한 처리량을 사용자가 직접 숫자로 정해 고정으로 확보하는 방식이 프로비저닝 처리량 모드(Provisioning Throughput)입니다. 이는 전세 버스를 한 대 빌리는 것과 비슷합니다. 승객이 몇 명이든 상관없이 정해진 크기의 버스를 정해진 기간 동안 전세로 확보해 두므로, 출퇴근 시간에 사람이 몰려도 자리가 갑자기 사라지지 않습니다. 여기서 전세 버스의 좌석 수가 사용자가 지정한 처리량(MiB/s 단위)에 해당하고, 계약 기간이 요금이 부과되는 기간에 해당하며, 승객이 적은 날에도 버스가 그대로 대기한다는 점이 고정 확보의 성격을 보여 줍니다.

대신 쓰지 않는 좌석도 요금이 나가므로, 실제 필요한 양을 관찰해 정하는 것이 중요합니다. 결국 프로비저닝 처리량 모드는 파일 시스템 크기와 무관하게 원하는 처리량을 직접 설정해 상시로 보장받는 방식이며, 부하가 꾸준하고 예측 가능할 때 알맞습니다.

탄력적 처리량(Elastic Throughput)

워크로드에 따라 처리량이 자동으로 늘고 주는 방식을 안다

업무량이 하루에도 몇 번씩 크게 출렁이는 환경에서는 고정으로 처리량을 사 두면 노는 시간에 돈이 새고, 순간 폭주에는 여전히 모자랄 수 있습니다. 사용량을 지켜보다가 필요할 때 자동으로 늘리고 줄여 주는 방식이 탄력적 처리량(Elastic Throughput)입니다. 이것은 놀이공원이 대기 줄 길이를 보고 입장 게이트 수를 실시간으로 바꾸는 것과 같습니다. 줄이 길어지면 게이트를 더 열어 손님을 빠르게 들여보내고, 줄이 짧아지면 게이트를 닫아 인력을 아낍니다. 여기서 게이트 수가 파일 시스템이 내주는 처리량이고, 줄의 길이가 실제로 밀려드는 읽기·쓰기 요청의 양이며, 게이트를 여닫는 판단이 별도 설정 없이 자동으로 이뤄진다는 점이 이 방식의 핵심입니다.

사용자는 최대치 같은 상한만 정해 두고 나머지는 맡기며, 요금은 실제로 쓴 만큼만 나갑니다. 정리하면 탄력적 처리량은 워크로드의 수요 변화를 따라 처리량이 자동으로 확장되고 축소되는 방식으로, 변화가 잦고 예측이 어려운 업무에 어울립니다.

처리량 모드 전환

운영 중에 모드를 바꿀 때의 영향과 절차를 안다

서비스를 운영하다 보면 처음 고른 처리량 모드가 실제 부하와 맞지 않는다는 사실을 뒤늦게 알게 되는데, 그때마다 파일 시스템을 새로 만들어 데이터를 옮기는 일은 현실적으로 어렵습니다. Amazon EFS는 운영 중인 파일 시스템의 처리량 모드를 바꾸는 전환 기능을 제공해 이 문제를 덜어 줍니다. 이는 살던 집을 옮기지 않고 전기 요금제만 바꾸는 것과 비슷합니다. 요금제를 바꾸는 동안에도 집에 불이 들어오고 냉장고가 돌아가듯, 모드 전환 중에도 파일 시스템은 계속 읽고 쓰기가 가능합니다. 다만 계량기 교체처럼 준비 작업이 필요한 구간이 있어 전환이 즉시 끝나지는 않으며, 그 사이에는 성능이 일시적으로 평소와 다르게 나타날 수 있으므로 한산한 시간에 진행하는 편이 안전합니다.

절차는 관리 콘솔이나 API에서 대상 파일 시스템을 고르고 원하는 모드를 지정해 변경을 요청한 뒤, 적용이 끝났는지 상태를 확인하는 순서로 진행합니다. 정리하면 처리량 모드 전환은 데이터를 옮기지 않고 파일 시스템의 처리량 정책만 바꾸는 작업이며, 전환에 걸리는 시간과 그동안의 성능 변동을 감안해 계획해야 합니다.

EFS의 지연 시간 특성

메타데이터 지연과 읽기·쓰기 지연이 어떻게 다른지 이해한다

파일을 다루는 프로그램이 느리다고 느껴질 때, 그 원인이 데이터를 옮기는 시간인지 아니면 파일의 위치나 정보를 확인하는 시간인지 구분하지 못하면 엉뚱한 곳을 손보게 됩니다. Amazon EFS의 지연 시간(latency)은 이 두 가지가 서로 다른 성격을 가진다는 점을 먼저 이해해야 합니다. 도서관에 비유하면 사서가 서가에서 책의 위치를 찾아 주는 시간과, 책을 펼쳐 내용을 읽는 시간은 다릅니다. 파일을 열거나 이름을 바꾸거나 목록을 조회하는 작업은 사서에게 물어보는 일에 해당하고, 이때 생기는 것이 메타데이터 지연(metadata latency)입니다. 반면 이미 열어 둔 파일에서 실제 내용을 읽고 쓰는 작업은 책장에서 책을 꺼내 읽는 일에 해당하며, 이때의 읽기·쓰기 지연(data latency)은 상대적으로 짧습니다.

그래서 파일이 작고 여러 개를 동시에 열어야 하는 작업은 사서를 몇 번이나 부르는 셈이 되어 전체 체감 속도가 느려지고, 큰 파일 하나를 순서대로 읽는 작업은 상대적으로 매끄럽게 느껴집니다. 결국 EFS의 지연 시간은 파일의 정보를 다루는 메타데이터 경로와 실제 데이터를 옮기는 경로로 나뉘며, 어떤 작업이 많은지에 따라 체감 성능이 달라집니다.

작은 파일이 많은 워크로드

소형 파일이 많을 때 성능이 왜 떨어지는지 안다

용량으로 보면 몇 기가바이트도 되지 않는 파일 수만 개를 다루는 작업이, 수십 기가바이트짜리 파일 하나를 다루는 작업보다 훨씬 오래 걸리는 경우가 흔합니다. 작은 파일이 많은 워크로드에서 성능이 떨어지는 이유는 처리량보다 파일 하나하나를 여는 동작의 수가 병목이 되기 때문입니다. 이는 택배로 치면 커다란 상자 몇 개를 보내는 일과, 봉투 수천 개를 보내는 일의 차이와 같습니다. 상자는 트럭에 한 번 실으면 끝이지만, 봉투는 하나하나 송장을 붙이고 주소를 확인하고 분류대를 거쳐야 하므로 짐의 무게는 가벼워도 손이 훨씬 많이 갑니다. 여기서 봉투 하나가 작은 파일 하나에 해당하고, 송장을 붙이고 분류하는 일이 그 파일의 정보를 확인하고 여는 메타데이터 작업에 해당합니다.

결국 전체 시간은 데이터의 양이 아니라 처리해야 할 파일의 개수와 그 동시 처리 능력에 좌우됩니다. 정리하면 작은 파일이 많은 워크로드는 초당 처리할 수 있는 파일 작업 수가 성능을 결정하며, 파일 수를 줄이거나 묶어서 다루는 방식으로 접근해야 합니다.

병렬 처리와 동시 접속 수

많은 클라이언트가 동시에 붙을 때의 한계를 안다

한 사무실에서 수십 명이 같은 서버의 파일을 동시에 열면, 먼저 온 사람의 복사가 끝날 때까지 나머지가 줄을 서서 기다리는 일이 생깁니다. Amazon EFS(Elastic File System)가 이런 상황을 견디도록 설계된 이유를 이해하려면 병렬 처리(parallel processing)와 동시 접속 수(concurrent connections)라는 두 가지 한계를 함께 봐야 합니다.

이 구조는 택배 물류센터와 비슷합니다. 센터에 상차구가 하나뿐이면 트럭이 아무리 많아도 한 대씩만 짐을 싣고 나가므로 전체 처리 속도가 늘지 않습니다.

상차구를 여러 개 만들고 각 트럭의 짐을 여러 직원이 나눠 옮기게 하면 같은 시간에 훨씬 많은 화물이 빠져나갑니다. EFS는 이 상차구의 수를 동시 접속 수로, 직원들이 나눠 일하는 방식을 병렬 처리로 대응시켜, 접속마다 독립된 통로를 열어 한 클라이언트의 느린 작업이 다른 클라이언트를 막지 않게 합니다.

정리하면 EFS의 성능은 저장 용량만으로 결정되지 않고, 동시에 붙는 클라이언트 수와 그 요청을 얼마나 병렬로 흘려보내는지에 크게 좌우됩니다. 따라서 워크로드를 설계할 때는 평균 사용량보다 최대 동시 접속 수를 먼저 가늠해야 합니다.

EFS 성능 측정 방법

fio 같은 도구로 실제 처리량과 지연을 재는 법을 익힌다

파일 시스템이 느린지 빠른지 체감만으로 판단하면 원인을 잘못 짚어 필요 없는 용량을 늘리거나 진짜 병목을 놓치게 됩니다. Amazon EFS의 실제 성능을 알려면 fio(flexible I/O tester) 같은 도구로 처리량(throughput)과 지연(latency)을 직접 재는 절차가 필요합니다.

이 과정은 이삿짐센터가 실제 짐을 실어 나르며 걸리는 시간을 재는 것과 같습니다.

어떤 트럭에 몇 개의 짐을 싣고(블록 크기), 몇 명이 동시에 오가고(병렬 작업 수), 짐 하나가 도착하기까지 얼마나 걸리는지(지연)를 조건을 바꿔 가며 기록합니다. fio는 이런 조건을 파일로 적어 두고 정해진 시간 동안 읽기와 쓰기를 반복해 초당 처리량과 응답 시간을 숫자로 남깁니다.

측정은 클라이언트 한 대에서 하는 경우와 여러 대에서 동시에 하는 경우를 나눠서 해야, 대역폭 부족인지 지연 문제인지 구분할 수 있습니다.

결국 EFS 성능 측정은 fio 같은 도구로 블록 크기와 동시 작업 수, 클라이언트 수를 바꿔 가며 처리량과 지연을 수치로 기록하는 일입니다. 이 기록이 있어야 용량 증설이나 클래스 변경 같은 판단을 감이 아니라 근거로 할 수 있습니다.

EFS 스토리지 클래스 개요

어떤 클래스가 있고 각각 언제 쓰는지 큰 그림을 잡는다

회사 문서고에 매일 꺼내 보는 서류와 몇 년에 한 번 확인하는 서류를 같은 값비싼 보관함에 넣어 두면 비용이 크게 낭비됩니다. Amazon EFS가 스토리지 클래스(storage class)를 나누는 이유도 여기에 있으며, 데이터를 얼마나 자주 읽는지에 따라 저장 단가와 특성을 다르게 고를 수 있게 합니다.

이는 아파트에서 물건을 두는 방식과 같습니다. 매일 쓰는 물건은 집 안 수납장에 두고, 가끔 쓰는 계절용품은 지하 창고에, 거의 쓰지 않는 짐은 외부 보관소에 맡깁니다.

EFS도 자주 읽고 쓰는 데이터는 표준(Standard)에, 가끔 읽는 데이터는 표준-IA(Standard-IA)나 원 존-IA(One Zone-IA)에 두며, 장기 보관용으로는 아카이브 계열 클래스를 고를 수 있습니다. 수납장을 옮기듯 클래스 사이를 자동으로 옮기는 수명 주기 정책(lifecycle policy)을 걸어 두면, 접근 빈도가 줄어든 파일이 알아서 저렴한 쪽으로 내려갑니다.

정리하면 EFS 스토리지 클래스는 접근 빈도와 내구성 요구에 따라 저장 단가를 달리 고르는 선택지이며, 표준과 표준-IA, 원 존-IA, 아카이브라는 큰 틀만 잡으면 됩니다. 어떤 클래스를 쓸지는 파일을 얼마나 자주 읽는지와 가용 영역 손실을 감당할 수 있는지로 결정합니다.

표준(Standard) 스토리지 클래스

자주 쓰는 데이터를 두는 기본 클래스의 성격을 안다

매일 열고 고치는 파일을 저렴한 보관용 클래스에 넣으면, 조회할 때마다 붙는 추가 비용과 느린 응답 때문에 전체 비용이 오히려 늘어날 수 있습니다. 그래서 Amazon EFS는 자주 쓰는 데이터를 두는 기본 클래스로 표준(Standard) 스토리지 클래스를 제공합니다.

이 클래스는 아파트 부엌의 냉장고 앞칸과 같습니다. 매일 꺼내 먹는 반찬을 가장 손이 닿기 쉬운 자리에 두듯, 자주 접근하는 파일은 여러 가용 영역(Availability Zone)에 걸쳐 중복 저장되어 읽기 지연이 낮고 한 구역이 멈춰도 데이터를 잃지 않습니다.

대신 저장 용량에 대한 단가가 다른 클래스보다 높게 책정되므로, 접근이 잦은 만큼 단가보다 응답성과 안정성을 우선하는 선택입니다. EFS를 만들 때 특별히 클래스를 지정하지 않으면 이 표준 클래스가 기본값이 됩니다.

결국 표준 클래스는 여러 가용 영역에 데이터를 복제해 높은 내구성과 낮은 지연을 주는 대신 저장 단가가 높은, 자주 쓰는 데이터용 기본 클래스입니다. 접근 빈도가 확실히 높은 공유 작업 공간이라면 이 클래스가 가장 무난한 출발점입니다.

표준-IA(Standard-IA) 클래스

가끔 읽는 데이터를 저렴하게 두는 방식을 안다

몇 달에 한 번 참고할까 말까 한 파일이 표준 클래스에 그대로 쌓이면, 쓰지 않는 용량에 높은 단가를 계속 내게 됩니다. Amazon EFS의 표준-IA(Standard-IA, Infrequent Access) 클래스는 이런 가끔 읽는 데이터를 여러 가용 영역에 그대로 두면서 저장 단가를 낮추기 위해 나왔습니다.

이는 계절이 지난 이불을 압축팩에 넣어 창고에 두는 것과 비슷합니다. 당장 쓰지 않는 물건이라도 버리지는 않고 꺼내 쓸 수 있게 보관하되, 자주 쓰는 물건보다 좀 더 번거로운 자리에 두는 방식입니다.

표준-IA도 데이터를 여러 가용 영역에 유지하므로 내구성은 표준과 같은 수준이지만, 접근할 때마다 용량당 조회 비용이 별도로 붙고 응답이 표준보다 느릴 수 있습니다. 그래서 수명 주기 정책으로 일정 기간 접근이 없던 파일만 이 클래스로 내리도록 설정하는 것이 일반적입니다.

정리하면 표준-IA는 자주 읽지 않는 데이터를 여러 가용 영역에 안전하게 보관하며 저장 단가를 낮추는 대신, 읽을 때 조회 비용과 약간의 지연을 감수하는 클래스입니다. 접근이 드물지만 지우기는 아까운 데이터에 어울립니다.

원 존-IA(One Zone-IA) 클래스

단일 가용 영역에 두는 저가 클래스의 장단점을 안다

비용을 최대한 줄이고 싶은데 데이터를 잃어도 다시 만들 수 있다면, 굳이 여러 가용 영역에 복제하는 값비싼 구성을 고집할 이유가 없습니다. Amazon EFS의 원 존-IA(One Zone-IA) 클래스는 데이터를 단일 가용 영역에만 두어 저장 단가를 더 낮춘 선택지입니다.

이는 회사 비품을 한 곳의 창고에만 보관하는 것과 같습니다. 창고를 여러 동 운영하면 화재나 정전이 나도 다른 동에서 꺼내 쓸 수 있지만, 한 동만 쓰면 그 창고에 문제가 생기는 순간 해당 비품을 전부 못 쓰게 됩니다.

원 존-IA는 이처럼 데이터를 한 가용 영역에만 저장하므로 저장 단가가 표준-IA보다 낮고, 대신 그 가용 영역 자체에 장애가 나면 데이터를 사용할 수 없게 될 위험을 감수합니다. 표준-IA와 마찬가지로 읽을 때 조회 비용이 붙으므로, 여러 가용 영역에 다시 복제해 두는 백업이나 원본이 따로 있는 데이터에 주로 씁니다.

결국 원 존-IA는 단일 가용 영역에만 데이터를 두어 저장 비용을 더 낮춘 대신, 해당 영역 장애 시 데이터 접근이 불가능해질 수 있는 클래스입니다. 다시 만들 수 있거나 다른 곳에 원본이 있는 가끔 읽는 데이터에 적합합니다.

수명 주기 관리(Lifecycle Management)

오래된 파일을 자동으로 저가 클래스로 옮기는 규칙을 만든다

회사 파일 서버에 몇 년치 자료가 쌓이면 아무도 열지 않는 옛 문서가 저장 공간의 절반을 차지하는 일이 생깁니다. 그래서 오래된 파일을 자동으로 값싼 저장 등급으로 옮기도록 규칙을 미리 정해 두는 기능이 바로 수명 주기 관리(Lifecycle Management)입니다.

집을 아파트라고 생각하면, 자주 쓰는 물건은 거실 수납장에 두고 계절이 지난 물건은 베란다 창고로, 몇 년째 꺼내지 않은 상자는 지하 창고로 내리는 것이 자연스럽습니다. 수명 주기 정책은 이사를 도와주는 관리인과 같아서, 물건이 마지막으로 꺼내진 날짜를 세어 두었다가 정해진 날이 지나면 알아서 아래층으로 옮겨 줍니다. 이때 옮길 조건은 며칠이나 몇 달 동안 손대지 않았는지로 정하고, 옮긴 뒤에도 필요하면 다시 꺼낼 수 있습니다.

관리인은 물건을 버리지 않고 자리만 바꾸므로, 규칙을 잘못 세우면 자주 쓰는 물건이 먼 창고로 가서 꺼내기 번거로워질 수도 있습니다.

정리하면 수명 주기 관리는 파일의 마지막 접근 시점과 경과 기간을 기준으로 EFS 파일을 더 저렴한 스토리지 클래스로 자동 전환하는 규칙입니다. 정책은 한 번 정해 두면 계속 돌아가므로, 초기 설계에서 전환 시점을 신중히 잡는 것이 중요합니다.

그래서 지난 사용 기록에서 파일이 얼마나 자주, 얼마나 오래 방치되는지를 먼저 확인한 뒤 시점을 정합니다.

스토리지 클래스 전환의 지연

정리하면 스토리지 클래스 전환은 즉시 끝나는 작업이 아니며, 전환에 걸리는 시간과 그동안의 접근 빈도를 함께 고려해 정책을 세워야 합니다.

EFS Intelligent-Tiering

접근 빈도에 따라 계층을 자동으로 고르는 방식을 안다

파일마다 언제 마지막으로 읽혔는지 사람이 일일이 지켜보며 등급을 바꾸는 일은 현실적으로 불가능하고, 규칙을 잘못 잡으면 비용이 오히려 늘어납니다. 그래서 접근 빈도를 스스로 지켜보며 계층을 자동으로 고르는 방식이 EFS Intelligent-Tiering(인텔리전트 티어링)입니다.

자동 변속기 차를 떠올리면, 운전자는 오르막인지 내리막인지 일일이 기어를 고르지 않고 차가 속도와 부하를 보고 알아서 단을 바꿉니다. EFS Intelligent-Tiering도 파일의 접근 기록을 스스로 살펴, 자주 읽히는 파일은 빠른 계층에, 한동안 조용한 파일은 저렴한 계층에 두는 판단을 대신합니다. 운전자가 변속 규칙을 바꿀 수 있듯이, 관리자는 얼마나 오래 접근이 없으면 계층을 바꿀지 같은 기준을 조정할 수 있습니다.

다만 자동이라고 해서 공짜는 아니어서, 계층을 옮기는 데 드는 비용과 다시 빠른 계층으로 돌아오는 경우를 함께 봐야 합니다.

정리하면 EFS Intelligent-Tiering은 파일 접근 빈도를 관찰해 스토리지 클래스를 자동으로 선택하고 전환하는 방식입니다. 규칙을 손으로 관리하는 부담을 줄이는 대신, 전환 비용이 발생한다는 점을 알고 설계해야 합니다.

정리하면 콜드 데이터는 접근 빈도가 낮은 대신 보관 의무가 있는 데이터로, 저렴한 스토리지 클래스에 두고 보관 기간과 삭제 기준을 함께 정해 관리해야 합니다.

그래서 한 달 동안 보관할 용량, 실제로 읽은 양, 계층을 옮긴 양을 각각 곱해 더한 총액으로 비교합니다. 여기에 데이터를 꺼내는 데 걸리는 시간과 다시 자주 읽게 될 가능성까지 감안해야 실제 선택이 흔들리지 않습니다.

정리하면 스토리지 클래스 선택은 저장 용량 요금과 접근 요금, 계층 전환 요금을 합산한 총비용으로 판단해야 합니다. 사용 패턴이 바뀌면 총액도 바뀌므로, 정기적으로 다시 계산해 정책을 조정하는 것이 좋습니다.

액세스 포인트(Access Point)

애플리케이션별로 출입구를 따로 만드는 개념을 이해한다

여러 애플리케이션이 하나의 파일 시스템을 함께 쓰다 보면, 어느 팀이 어디까지 들어가도 되는지 경계가 흐려집니다. 누군가 설정을 잘못 건드리면 전혀 상관없는 서비스까지 데이터를 잃는 사고가 나고, 그래서 Amazon EFS에는 애플리케이션마다 출입구를 따로 내주는 액세스 포인트(Access Point)라는 개념이 생겼습니다.

회사 건물 하나에 여러 부서가 입주해 있다고 생각해 보십시오. 건물 전체 정문 하나만 두면 아무나 모든 층을 돌아다닐 수 있지만, 부서마다 전용 출입문을 만들고 그 문을 지나면 해당 부서 구역으로만 이어지게 해 두면 동선 자체가 자연스럽게 분리됩니다.

액세스 포인트는 이 전용 출입문에 해당하며, 각 문에는 들어오는 사람의 신분(사용자 ID)과 처음 발을 들이는 위치(루트 디렉터리)가 미리 정해져 있습니다. 애플리케이션은 파일 시스템 주소 대신 자기 출입구 주소로 접속하고, 그 출입구에 걸린 규칙에 따라 권한과 경로가 자동으로 결정됩니다.

결국 액세스 포인트는 EFS 파일 시스템 안에서 애플리케이션별 접근 지점을 정의하는 관리 객체이며, 하나의 파일 시스템을 여러 서비스가 안전하게 나눠 쓰게 해 주는 장치입니다.

POSIX 사용자 강제

액세스 포인트가 접속 사용자를 지정 UID/GID로 고정하는 원리를 안다

리눅스에서 파일을 다루는 프로그램은 저마다 다른 사용자 계정으로 실행되는데, 컨테이너처럼 매번 새로 뜨는 환경에서는 이 계정 번호가 제각각이 되어 권한이 어긋나기 쉽습니다. 어떤 작업은 파일을 읽지 못해 멈추고, 어떤 작업은 엉뚱한 소유자로 파일을 만들어 다른 팀의 작업을 망가뜨립니다. POSIX 사용자 강제(POSIX user enforcement)는 이런 번호 불일치를 없애기 위해, 액세스 포인트로 들어오는 모든 접속을 지정한 사용자 ID(UID)와 그룹 ID(GID)로 고정하는 기능입니다.

아파트 경비실에서 택배를 받는 상황을 떠올려 보십시오. 입주민마다 다른 이름을 대게 하면 경비실 장부가 엉망이 되지만, 이 건물에서는 모든 택배를 "관리동 101호"라는 한 사람 앞으로만 접수하도록 규칙을 정해 두면 누가 와서 맡기든 장부에는 같은 이름이 적힙니다.

액세스 포인트에 UID와 GID를 지정해 두면, 실제 접속자가 누구든 파일 시스템 입장에서는 그 한 사람으로 보입니다. 그래서 파일을 만들든 읽든 소유자와 그룹이 늘 같게 유지되고, 여러 인스턴스가 같은 디렉터리를 공유해도 권한 충돌이 생기지 않습니다.

요약하면 POSIX 사용자 강제는 접속 주체의 신분을 액세스 포인트 단위로 통일해, 파일 소유권과 퍼미션 계산을 예측 가능하게 만드는 설정입니다.

액세스 포인트 루트 디렉터리

각 액세스 포인트가 바라보는 시작 경로를 정하는 법을 안다

파일 시스템 하나를 여러 서비스가 공유하면, 각 서비스가 최상위부터 모든 폴더를 볼 수 있게 되어 실수로 남의 데이터를 건드릴 위험이 커집니다. 서비스마다 보이는 세계를 좁혀 주면 이런 사고를 구조적으로 줄일 수 있는데, 그 역할을 하는 것이 액세스 포인트 루트 디렉터리(Access Point root directory)입니다.

큰 창고 건물을 빌렸다고 상상해 보십시오. 건물 전체 열쇠를 주는 대신, 각 업체에는 자기 구역으로 통하는 문만 주고 그 문을 지나면 자기 구역만 보이게 합니다.

액세스 포인트를 만들 때 루트 디렉터리 경로를 /app-a/data처럼 지정하면, 그 출입구로 들어온 클라이언트에게는 이 경로가 곧 최상위 폴더가 됩니다. 상위 폴더로 올라가려 해도 이미 자기 구역의 시작점이 그곳이므로 건물 전체를 돌아다닐 수 없습니다. 이 경로는 미리 존재해야 하고 접속에 쓰는 사용자에게 접근 권한이 있어야 하며, 경로를 비워 두면 파일 시스템 최상위가 그대로 시작점이 됩니다.

결국 액세스 포인트 루트 디렉터리는 애플리케이션이 보는 파일 시스템의 시야를 특정 경로로 잘라 주는 설정입니다.

액세스 포인트를 만들어 두기만 하고 실제 마운트에서 쓰지 않으면 아무 효과가 없습니다. 그래서 파일 시스템을 연결하는 시점에 어느 출입구로 들어갈지를 지정하는 절차가 중요합니다.

리조트에 도착해 프런트에서 객실 키를 받는 상황과 비슷합니다. 건물은 하나지만 프런트에서 "몇 호 투숙객인지"를 먼저 말해야 그 호실 열쇠를 받고, 그 키로는 자기 방만 열립니다.

먼저 콘솔이나 명령줄에서 액세스 포인트를 생성하고 POSIX 사용자와 루트 디렉터리를 정합니다. 그다음 마운트 헬퍼를 쓸 경우 accesspoint 옵션에 그 액세스 포인트 ID나 ARN을 넣어 연결하면, 커널이 그 출입구의 설정대로 사용자와 경로를 적용합니다. NFS 클라이언트로 직접 마운트할 때는 파일 시스템 주소 뒤에 /access-point/<액세스 포인트 ID> 형태의 경로를 붙이는 방식이 쓰이며, 이 형식과 지원 여부는 환경에 따라 다를 수 있으므로 공식 문서를 확인하는 편이 안전합니다.

정리하면 액세스 포인트는 생성만으로 끝나지 않고 마운트 옵션에 지정되어야 비로소 권한과 경로 규칙이 적용됩니다.

EFS의 POSIX 권한 체계

소유자·그룹·퍼미션 비트가 파일에 적용되는 방식을 안다

리눅스 서버에서 파일을 옮겨 왔는데 소유자와 권한이 그대로 유지되지 않으면, 배포 스크립트가 갑자기 실패하고 로그 파일에 접근 거부가 쏟아집니다. Amazon EFS는 이런 혼란을 막기 위해 POSIX 권한 체계(POSIX permissions)를 파일 단위로 그대로 따릅니다.

사무실 서류 캐비닛을 떠올려 보십시오. 각 서랍에는 관리 책임자(소유자)와 열쇠를 함께 쓰는 부서(그룹)가 적혀 있고, 그다음 읽기·쓰기·실행 권한이 누구에게 열려 있는지를 표시한 스티커가 붙어 있습니다.

EFS의 파일과 디렉터리에도 똑같이 소유자, 그룹, 그 외 사용자 세 갈래로 읽기(r)·쓰기(w)·실행(x) 비트가 붙고, 디렉터리의 실행 비트는 그 안으로 들어갈 수 있는지를 뜻합니다. 마운트된 리눅스에서는 이 값이 일반 파일처럼 보이고 chmod나 chown 같은 명령으로 다룰 수 있지만, 실제 판정은 EFS가 접속자의 UID와 GID를 기준으로 수행합니다. 따라서 액세스 포인트로 사용자를 고정해 두면 권한 계산이 단순해지고 예측 가능해집니다.

결국 EFS의 POSIX 권한 체계는 소유자·그룹·퍼미션 비트라는 리눅스의 익숙한 규칙을 네트워크 파일 시스템에도 그대로 적용한 구조입니다.

자격 증명 기반 정책과 리소스 기반 정책을 구분한다

파일 권한만으로는 "이 서버가 애초에 이 파일 시스템에 붙어도 되는가"라는 질문에 답하지 못합니다. 그래서 AWS는 파일 수준 규칙 앞단에 자격 증명 기반의 관문을 하나 더 두었고, 이것이 IAM 기반 EFS 접근 제어입니다.

호텔 로비를 생각해 보십시오. 정문 경비가 투숙객 명단으로 건물 출입 자체를 통제하고, 객실 층에서는 카드키가 방문을 여는지 판단합니다. 두 관문은 서로 다른 기준으로 작동하며 둘 다 통과해야 방에 들어갈 수 있습니다.

IAM 정책은 크게 두 종류로 나뉘는데, 사용자나 역할에 붙어 "무엇을 할 수 있는가"를 정하는 자격 증명 기반 정책(identity-based policy)과 파일 시스템 같은 리소스에 붙어 "누가 어떤 조건에서 접근할 수 있는가"를 정하는 리소스 기반 정책(resource-based policy)입니다. EFS는 리소스 기반 정책으로 특정 IAM 주체의 접근을 허용하거나 거부할 수 있고, 마운트 헬퍼를 통해 접속할 때는 클라이언트의 자격 증명이 함께 전달되어 이 정책이 평가됩니다. 이때 파일 시스템 정책과 IAM 정책, POSIX 권한이 모두 만족되어야 실제 읽기와 쓰기가 허용됩니다.

정리하면 IAM 기반 접근 제어는 네트워크 파일 시스템에 신원 기반 승인 계층을 더해, 누가 어떤 조건에서 접근할 수 있는지를 정책으로 명시하게 하는 체계입니다.

아파트 단지에 비유하면, 세대별 도어락이 아니라 단지 정문에서 명단을 확인하는 경비실에 해당합니다. 경비실은 방문자가 어느 동의 주민인지 아니면 외부인인지를 기준으로 출입을 허용하거나 거절하고, 그 판단 기준을 종이 한 장에 적어 두는데 이것이 정책 문서입니다.

이 문서에는 어떤 AWS 계정이나 IAM 주체를 허용할지, 액세스 포인트를 거치는 접근인지 직접 마운트인지 같은 조건을 함께 적습니다. 정책은 파일 시스템 하나에 하나만 붙고, 정책을 두지 않으면 소유 계정 바깥에서는 사실상 문이 닫힌 상태로 남습니다.

결국 파일 시스템 정책은 스토리지 문 앞에 세운 경비 규정이고, IAM이 사람마다 들고 다니는 사원증이라면 이쪽은 건물 쪽에 붙어 있는 허용 명단입니다.

공항에 비유하면 IAM 정책은 여권과 신분 확인으로 누가 공항에 들어올 수 있는지를 정하는 첫 관문입니다. 액세스 포인트는 탑승구 게이트에 해당해서, 같은 여권을 가진 사람이라도 항공편마다 게이트가 다른 것처럼 팀별로 다른 액세스 포인트를 두고 그 지점에서 다시 허용 여부를 확인합니다.

게이트마다 POSIX 사용자 ID와 그룹, 시작 디렉터리를 미리 정해 두기 때문에 통과한 사람은 자기 팀 공간에만 도착합니다. 두 겹은 어느 하나만 통과해서는 안 되고, 여권 확인과 게이트 확인을 모두 지나야 실제 파일에 닿을 수 있습니다.

정리하면 IAM은 주체가 EFS를 향해 요청을 보낼 수 있는지를, 액세스 포인트는 그 요청이 어느 디렉터리에 어떤 POSIX 권한으로 도착할지를 정하며, 두 정책이 모두 허용할 때 접근이 성립합니다.

EFS의 root 접근 제어

root_squash 같은 동작과 그 주의점을 안다

컨테이너를 root 사용자로 실행한 채 파일 시스템을 붙이면, 애플리케이션이 만든 파일까지 모두 root 소유가 되어 다른 사용자는 읽지도 고치지도 못하는 상황이 생깁니다. EFS는 접근하는 주체의 신분을 미리 정해 두는 방식으로 이 문제를 다루며, root 요청을 일반 사용자로 낮추어 취급하는 root squash 같은 동작이 여기에 속합니다.

호텔에 비유하면 root 사용자는 모든 객실을 여는 마스터키이고, root squash는 그 마스터키를 프런트에서 일반 투숙객 카드로 바꿔 주는 절차입니다. 마스터키를 그대로 들려 보내면 한 사람이 모든 방을 열 수 있으니, 기본은 카드를 낮춰 주는 쪽에 두는 것이 안전합니다.

액세스 포인트는 요청마다 정해진 POSIX 사용자와 그룹으로 신분을 바꿔 취급하므로, root로 들어와도 그 사용자의 권한까지만 행사합니다. 다만 이미지가 root로 파일을 만들도록 만들어져 있으면 이 낮춤 때문에 쓰기가 막힐 수 있어, 실행 사용자와 디렉터리 소유권을 함께 맞춰 두어야 합니다.

결국 root 접근 제어는 최고 권한을 그대로 넘기지 않고 미리 정한 신분으로 바꿔 받는 장치이며, 세부 동작은 구성과 환경에 따라 달라질 수 있으므로 적용 전에 확인이 필요합니다.

테넌트가 늘 때마다 파일 시스템을 하나씩 새로 만들면 비용과 관리 항목이 함께 불어나고, 반대로 아무 구분 없이 한 디렉터리에 몰아넣으면 실수 한 번에 남의 파일을 지우게 됩니다. EFS에서는 파일 시스템 하나를 두고 액세스 포인트와 디렉터리 구조로 팀별 공간을 나누는 설계가 흔히 쓰입니다.

오피스 빌딩에 비유하면 건물 하나를 층별로 임대해 주는 것과 같습니다. 각 층에는 그 팀 전용 출입 카드가 따로 있고, 카드에 적힌 층까지만 엘리베이터가 열리므로 다른 층 사무실에는 애초에 발을 들이지 못합니다.

액세스 포인트마다 시작 디렉터리를 그 팀 폴더로 지정하고 POSIX 사용자와 그룹을 팀별로 다르게 두면, 같은 파일 시스템 안에서도 층이 갈립니다. 여기에 팀별 태그와 액세스 포인트별 정책을 얹으면 어느 팀이 어느 문으로 들어왔는지가 감사 기록에 그대로 남습니다.

정리하면 하나의 EFS 위에 액세스 포인트를 팀 수만큼 만들고 각각의 시작 디렉터리와 POSIX 신분을 분리하는 것이 격리의 핵심이며, 파일 시스템을 쪼개는 대신 문을 쪼개는 방식입니다.

EFS 태깅과 거버넌스

태그로 소유자·비용·정책을 관리하는 방법을 안다

파일 시스템이 수십 개로 늘면 어느 것이 어느 팀의 것이고 누가 비용을 부담해야 하는지를 장부 없이는 알 수 없게 됩니다. EFS 태그는 파일 시스템과 액세스 포인트에 붙는 이름표로, 소유자와 비용, 정책 적용 대상을 기계가 읽을 수 있는 형태로 남깁니다.

택배 송장에 비유하면 이해가 빠릅니다. 송장에는 보내는 사람, 배송 방식, 취급 주의가 칸칸이 적혀 있고, 이 칸 덕분에 물건이 사람 손을 거치지 않고도 자동으로 분류됩니다.

태그도 마찬가지로 소유자와 팀, 비용 코드, 환경 같은 항목을 정해진 키로 적어 두면, 청구서에서 팀별 비용이 자동으로 갈리고 정책도 해당 태그가 붙은 자원에만 적용됩니다. 송장이 없으면 택배가 어디로 갈지 모르듯, 태그가 없으면 그 자원이 누구 것인지도 비용이 어디로 붙을지도 사후에 되짚기 어렵습니다.

결국 태깅은 자원에 붙는 송장이고, 태그 키와 값을 미리 표준으로 정해 두는 것이 거버넌스의 출발점이며, 이 표준이 있어야 비용 배분과 정책 적용이 사람의 기억에 기대지 않게 됩니다.

EFS와 VPC 네트워크

파일 시스템이 VPC 안에서 어떻게 도달되는지 이해한다

회사에 파일 서버를 새로 놓았는데 서버가 있는 쪽 네트워크가 바뀌는 순간 사무실 전체가 그 파일을 찾지 못해 업무가 멈춘 적이 있을 것입니다. Amazon EFS는 이런 파일 저장소를 사설 네트워크 안에서 안전하게 꺼내 쓰도록 만든 서비스이고, 그 중심에는 가상 사설망인 VPC(Virtual Private Cloud)가 있습니다.

이 구조는 아파트 단지에 비유할 수 있습니다. 단지 안에서만 출입할 수 있는 중앙 창고가 EFS 파일 시스템이고, 단지의 도로와 출입문 체계가 VPC입니다. 각 세대는 단지 도로를 통해서만 창고에 갈 수 있으므로, 다른 단지에 사는 사람은 도로가 이어져 있지 않으면 창고 문 앞에 설 수 없습니다.

EFS는 VPC 안의 서브넷마다 탑재 대상(mount target)이라는 출입구를 만들어 두고, 같은 VPC의 컴퓨팅 자원이 그 출입구를 통해 파일 시스템에 닿게 합니다.

정리하면 EFS는 VPC라는 사설 네트워크 경계 안에서만 도달할 수 있는 파일 저장소이며, 서브넷별 탑재 대상이 그 통로 역할을 합니다. 따라서 네트워크 설계가 곧 파일 시스템의 접근 범위를 정한다고 이해하면 됩니다.

탑재 대상의 IP와 DNS

마운트에 쓰는 DNS 이름과 IP 주소의 관계를 안다

서버 설정 파일에 파일 저장소 주소를 숫자로 적어 두었다가 저장소 쪽 사정으로 주소가 바뀌면서 접속이 끊긴 경험이 있다면, 그 불편이 어디서 생겼는지 짐작이 갈 것입니다. Amazon EFS는 마운트할 때 숫자 주소가 아니라 DNS 이름을 쓰도록 권장하며, 그 이름이 실제 탑재 대상의 IP 주소로 바뀌어 연결됩니다.

이 관계는 회사의 대표 전화번호와 내선 번호에 비유할 수 있습니다. 고객은 대표 번호 하나만 알면 되고, 교환기가 그 통화를 지금 근무하는 담당 부서의 내선으로 연결해 줍니다.

EFS에서 DNS 이름이 대표 번호라면 탑재 대상의 IP 주소는 그때그때 배정되는 내선 번호입니다. 파일 시스템을 만들면 가용 영역마다 탑재 대상이 생기고 각각 IP를 받는데, 이 IP는 영원히 고정된 약속이 아니라 환경에 따라 달라질 수 있으므로 설정에는 DNS 이름을 적는 것이 안전합니다.

즉 마운트는 DNS 이름을 기준으로 하고 IP는 그 이름이 가리키는 실제 연결 지점일 뿐이며, 이름을 써 두면 주소가 바뀌어도 설정을 고치지 않아도 됩니다.

EFS용 보안 그룹 설계

클라이언트와 탑재 대상 사이의 규칙을 설계한다

파일 저장소를 연결하면서 편하다는 이유로 네트워크 문을 활짝 열어 두면, 그 저장소에 닿아서는 안 되는 서버까지 같은 파일을 읽고 쓸 수 있게 됩니다. Amazon EFS는 보안 그룹(Security Group)이라는 가상 방화벽으로 이 통로를 통제하며, 클라이언트 쪽과 탑재 대상 쪽 양쪽에 규칙이 맞아야 연결됩니다.

이는 건물 경비실에 출입 명단을 두는 일과 같습니다. 탑재 대상에 붙는 보안 그룹은 창고의 문지기이고, 클라이언트에 붙는 보안 그룹은 방문자의 소속 증명서입니다.

문지기는 증명서에 적힌 집단만 들여보내므로, 창고 쪽 규칙에는 클라이언트 보안 그룹을 출처로 적고 파일 공유에 쓰는 NFS 포트(2049)를 허용합니다. 반대로 클라이언트 쪽에서도 창고로 나가는 통신이 허용되어야 하며, 두 방향 중 하나만 맞으면 마운트는 조용히 실패합니다.

결국 EFS 접근 제어는 보안 그룹 두 개를 짝으로 설계하는 일이며, 허용할 출처를 개별 IP가 아니라 보안 그룹 단위로 적는 것이 핵심입니다.

전송 중 암호화(TLS)

TLS 마운트가 무엇을 보호하고 무엇을 못 하는지 이해한다

같은 네트워크를 쓰는 누군가가 오가는 파일 내용을 들여다볼 수 있다면, 아무리 저장소 권한을 잘 나눠도 데이터는 이미 새는 셈입니다. Amazon EFS는 전송 중 암호화(encryption in transit)를 위해 TLS를 지원하며, 마운트할 때 이 옵션을 켜서 클라이언트와 파일 시스템 사이 구간을 보호합니다.

이 보호는 택배를 보낼 때 상자를 봉인 포장하는 일에 비유할 수 있습니다. 배송 기사와 지나가는 사람은 겉모습만 볼 수 있고 안의 내용은 볼 수 없으며, 받는 쪽에서 포장을 뜯어야 내용이 드러납니다.

TLS 마운트도 이와 같이 클라이언트와 탑재 대상 사이를 지나는 데이터를 암호문으로 바꿔, 중간에서 가로채도 읽지 못하게 합니다. 다만 포장이 도착한 뒤 창고에 어떻게 보관되는지까지 책임지는 것은 아니므로, 전송 중 암호화는 저장 중 암호화와 별개로 챙겨야 하는 층입니다.

정리하면 TLS는 이동하는 구간만 지키는 보호막이며, 저장된 데이터와 접근 권한은 각각 다른 수단으로 함께 설계해야 합니다.

저장 중 암호화

KMS 키로 저장 데이터를 암호화하는 방식을 안다

저장 장치가 교체되거나 폐기되는 과정에서 남아 있던 데이터가 그대로 읽힌다면, 서비스가 아무리 튼튼해도 소용이 없습니다. Amazon EFS는 이런 위험을 줄이기 위해 저장 중 암호화(encryption at rest)를 제공하며, 파일 시스템을 만들 때 암호화 여부와 사용할 키를 정합니다.

이는 서류를 금고에 넣어 두는 일과 비슷합니다. 금고를 통째로 가져가도 열쇠가 없으면 내용을 꺼낼 수 없고, 열쇠는 금고 밖의 열쇠 관리소가 보관합니다.

EFS에서 금고에 해당하는 것은 저장 매체이고, 열쇠 관리소는 AWS KMS(Key Management Service)입니다. 암호화된 파일 시스템은 저장 매체에 기록될 때 암호문으로 남고 읽을 때 KMS의 키로 풀리므로, 매체만 따로 빼내도 파일 내용은 드러나지 않습니다.

결국 저장 중 암호화는 물리적 매체 유출을 전제로 한 마지막 방어선이며, 키를 누가 관리하는지가 보안 수준을 가릅니다.

고객 관리형 KMS 키 사용

키 정책과 권한을 직접 관리할 때의 주의점을 안다

규정상 암호화 키의 수명과 사용 기록을 직접 통제해야 하는 조직이라면, 서비스가 알아서 관리하는 기본 키만으로는 설명이 부족할 수 있습니다. Amazon EFS는 저장 중 암호화에 쓸 키를 직접 만들어 지정하는 고객 관리형 키(customer managed key) 방식을 지원합니다.

이는 건물 마스터키를 경비 대행사에 맡기는 것과 직접 금고에 보관하는 것의 차이와 같습니다. 직접 보관하면 누가 언제 키를 썼는지 내 규칙대로 정할 수 있지만, 잃어버리거나 권한을 잘못 주면 문을 열 수 없는 책임도 내 몫입니다.

EFS에서 이 키는 KMS의 키 정책으로 누가 쓸 수 있는지 정해지고, 파일 시스템을 만들 때 키를 지정하면 이후 그 키 없이는 데이터를 읽을 수 없습니다. 따라서 키를 삭제 예약하거나 키 정책에서 EFS와 클라이언트의 사용 권한을 빼면, 파일 시스템은 그대로 남아 있어도 접근이 막힐 수 있습니다.

정리하면 고객 관리형 키는 통제권을 얻는 대신 운영 책임도 함께 떠안는 선택이며, 키 정책과 삭제 계획을 먼저 정해 두는 것이 안전합니다.

EFS와 PrivateLink

인터페이스 엔드포인트로 접근을 사설화하는 구성을 안다

회사 파일 서버를 클라우드로 옮기고 나면 뜻밖에도 인터넷을 타고 오가는 구간이 남아 있어 보안 검토에서 매번 걸리는 일이 생깁니다. Amazon EFS는 AWS가 관리해 주는 네트워크 파일 시스템이고, AWS PrivateLink는 그 파일 시스템에 닿는 길을 회사 사설망 안쪽으로만 묶어 주는 기능입니다.

아파트 단지를 떠올려 보면, 택배가 정문 공용 도로를 지나 경비실을 통과해야 들어오던 구조를 단지 지하로 바로 이어지는 전용 통로로 바꾸는 것과 같습니다.

PrivateLink에서 이 통로 역할을 하는 것이 인터페이스 엔드포인트(interface endpoint)인데, VPC 안에 사설 IP를 가진 네트워크 인터페이스를 만들어 두고 그 주소로 들어온 트래픽만 EFS로 넘겨 줍니다. 여기에 EFS용 사설 DNS 이름을 연결해 두면 애플리케이션은 설정을 조금 바꾸는 정도로, 경우에 따라서는 아무것도 고치지 않고 기존 마운트 경로를 그대로 씁니다. S3나 DynamoDB를 위해 쓰는 게이트웨이 엔드포인트(gateway endpoint)와 달리, 인터페이스 엔드포인트는 NFS 트래픽 자체를 사설 주소로 처리한다는 점이 다릅니다.

정리하면 PrivateLink는 인터페이스 엔드포인트를 통해 EFS 접근 경로를 VPC 사설 주소로 바꾸는 구성입니다. 덕분에 인터넷 게이트웨이나 NAT를 거치지 않고 파일 시스템을 쓰면서 접근 제어와 감사를 사설망 기준으로 맞출 수 있습니다.

교차 VPC 접근

피어링·Transit Gateway로 다른 VPC에서 붙는 법을 안다

한 서비스가 커지면 파일 시스템은 한 VPC에 두고 그 파일을 쓰는 애플리케이션은 다른 VPC로 나눠 두는 구성이 흔해지는데, 그때마다 VPC 밖에서는 파일 시스템이 보이지 않는다는 벽에 부딪힙니다. EFS는 마운트 대상(mount target)과 보안 그룹이 특정 VPC 안에 묶여 있어서, 다른 VPC에서 붙으려면 VPC 피어링(VPC peering)이나 AWS Transit Gateway 같은 연결 수단을 함께 설계해야 합니다.

여러 동으로 나뉜 회사 건물을 떠올려 보면, 각 동이 자기 출입문과 경비를 따로 두기 때문에 동과 동 사이에 문을 만들어 주지 않으면 서로 오갈 수 없습니다.

VPC 피어링은 두 동 사이에 전용 문을 하나 뚫는 방식이라 연결이 단순하고 빠르지만, 동이 늘어나면 문의 수가 조합만큼 늘어나 관리가 무거워집니다. Transit Gateway는 중앙 로비를 하나 두고 모든 동이 그 로비로만 이어지게 하는 방식이라, 새 동을 추가할 때 로비에 입구 하나만 만들면 됩니다. 어느 쪽이든 연결을 뚫은 다음에는 상대 VPC의 주소 대역을 EFS 마운트 대상의 보안 그룹 인바운드 규칙에 넣어 NFS 포트(2049)를 열어야 하고, 라우팅 테이블에도 상대 대역으로 가는 경로가 있어야 합니다.

정리하면 교차 VPC 접근은 피어링이나 Transit Gateway로 네트워크 경로를 만들고, 그 경로가 EFS 마운트 대상의 보안 그룹과 라우팅에서 허용될 때 성립합니다. 연결 수가 적고 단순하면 피어링이, 여러 VPC와 온프레미스 네트워크를 한곳에서 묶어야 하면 Transit Gateway가 잘 맞습니다.

EFS API 접근 로깅

CloudTrail로 누가 어떤 API를 호출했는지 본다

파일 시스템 설정이 어느 날 갑자기 바뀌었는데 누가 언제 바꿨는지 아무도 모르는 상황이 벌어지면, 원인을 찾을 단서조차 없습니다. AWS CloudTrail은 이런 제어 영역의 호출을 기록하는 서비스이고, EFS에 대한 API 호출도 여기에 남겨 누가 어떤 요청을 보냈는지 확인할 수 있습니다.

건물 관리실에 업무 일지를 두는 것과 비슷합니다. 누가 몇 시에 사무실에 들어왔는지가 아니라, 마스터키를 새로 만들었거나 경비 규칙을 바꾼 사람을 남기는 장부입니다.

CloudTrail은 파일 시스템 생성과 삭제, 파일 시스템 정책 변경, 마운트 대상 생성 같은 관리 이벤트를 API 이름, 호출자 신원, 시각, 출발 IP와 함께 기록합니다. 기록은 이벤트 기록(event history)에서 최근 것부터 훑어볼 수 있고, 오래 보관하려면 추적(trail)을 만들어 S3 버킷에 계속 쌓아 두면 됩니다. 다만 파일을 열어 읽고 쓴 행위 자체는 CloudTrail의 기본 기록 대상이 아니어서, 그 영역은 다른 감사 수단으로 채워야 합니다.

정리하면 CloudTrail은 EFS의 관리 API 호출을 남겨 설정 변경의 책임 소재를 밝히는 도구입니다. 파일 내용 접근 감사와는 역할이 다르다는 점을 구분해 두어야 합니다.

파일 접근 감사

어떤 파일에 접근했는지 감사하는 방법과 한계를 안다

규제 대상 데이터를 다루는 팀에서는 지난달에 누가 그 파일을 열었는지 묻는 질문을 받는데, 아무 기록이 없어 답하지 못하는 일이 생깁니다. 파일 접근 감사는 공유 파일 시스템 안에서 어떤 파일에 누가 접근했는지 남기는 작업이고, EFS에서는 운영체제 수준의 감사 도구와 AWS 쪽 로그를 조합해 접근합니다.

사무실 서류 캐비닛에 열쇠 대장을 두는 상황을 생각해 보면, 캐비닛 자체에 누가 열었는지 적는 장치가 없으면 경비실 기록으로는 누가 건물에 들어왔다까지만 알 수 있습니다.

EFS는 NFS 프로토콜을 따르는 파일 시스템이라, 마운트한 서버에서 리눅스의 auditd 같은 감사 데몬(audit daemon)을 돌려 파일 열기와 읽기 이벤트를 모으는 방식이 쓰입니다. 액세스 포인트(access point)와 파일 시스템 정책, POSIX 권한으로 접근 자체를 좁혀 두면 감사 로그의 양과 범위도 함께 줄어듭니다. 한계는 분명한데, 감사 데몬은 클라이언트 쪽에서 도는 것이라 마운트하지 않은 경로나 데몬이 꺼진 시간의 행위는 남지 않고, 로그를 모으고 보관하는 비용도 직접 감당해야 합니다.

정리하면 EFS의 파일 접근 감사는 서버 쪽 감사 도구로 파일 단위 기록을 모으고 AWS 로그로 제어 영역을 덮는 이중 구조입니다. 어디까지 기록되는지 범위를 먼저 정하고 한계를 문서로 남기는 일이 실제 운영에서는 더 중요합니다.

랜섬웨어와 파일 무결성

공유 파일 시스템을 노린 공격에 어떻게 대비하는지 안다

공유 파일 시스템은 여러 서버가 같은 데이터를 동시에 쓰는 구조라, 한 대의 서버가 감염되면 그 계정 권한으로 닿을 수 있는 파일이 한꺼번에 암호화되는 사고가 납니다. 랜섬웨어 대응은 결국 파일 무결성, 즉 데이터가 허가 없이 바뀌지 않았음을 보장하고 되돌릴 수 있게 만드는 문제로 모입니다.

회사 공용 창고와 재고 대장, 그리고 따로 떨어진 비상 재고 창고를 떠올려 보면 구조가 잘 맞습니다.

  • EFS에서는 먼저 권한을 좁히는 것이 기본인데, 애플리케이션마다 액세스 포인트와 POSIX 사용자를 따로 두고 필요한 디렉터리만 쓰게 하면 감염된 서버가 손댈 수 있는 범위가 그 좁은 구역으로 제한됩니다.
  • 다음은 백업인데, AWS Backup으로 EFS를 정기 백업하고 백업을 지우지 못하도록 볼트 잠금(Vault Lock)을 걸어 두면 공격자가 원본과 백업을 함께 지우는 시나리오를 막을 수 있습니다.
  • 마지막은 무결성 확인인데, 파일 해시를 주기적으로 계산해 두거나 백업 시점의 사본과 대조하면 변조 시점을 늦게라도 알아챌 수 있습니다.

정리하면 랜섬웨어 대비는 액세스 포인트와 권한으로 피해 범위를 줄이고, 삭제 방지가 걸린 백업으로 복구 지점을 확보하며, 해시 대조로 변조를 확인하는 세 겹의 구조입니다. 어느 하나만으로는 충분하지 않고 이 세 가지가 함께 있을 때 파일 무결성이 유지됩니다.

규정 준수와 암호화 정책

규제 요구에 맞춘 EFS 설정을 정리한다

금융이나 의료 데이터를 다루는 조직은 저장 데이터를 암호화하고 키를 누가 관리하는지 증명하라는 요구를 감사에서 받는데, 설정이 흩어져 있으면 증명 자료를 만드는 데만 몇 주가 걸립니다. 규정 준수 관점의 EFS 설정은 암호화 방식과 키 관리, 접근 통제, 로그 보존을 하나의 정책으로 묶어 설명할 수 있어야 한다는 뜻입니다.

금고와 열쇠 보관소, 그리고 금고 사용 일지로 비유할 수 있습니다.

EFS는 파일 시스템을 만들 때 저장 시 암호화(encryption at rest)를 켤 수 있고, 키는 AWS 관리형 키 대신 KMS 고객 관리형 키(customer managed key)를 골라 키 정책과 교체 주기를 직접 통제할 수 있습니다. 접근 통제는 보안 그룹과 파일 시스템 정책, 액세스 포인트로 나누어 걸고, 전송 구간은 TLS를 지원하는 마운트 헬퍼(mount helper)로 암호화합니다. 여기에 CloudTrail과 백업 보존 기간을 정해 두면 누가 설정을 바꿨고 얼마나 보관했는지에 대한 증거가 남습니다.

정리하면 규정 준수를 위한 EFS 구성은 KMS 키로 저장 데이터를 암호화하고, 보안 그룹과 파일 시스템 정책과 액세스 포인트로 접근을 제한하며, CloudTrail과 백업으로 기록과 보존을 증명하는 체계입니다. 규제마다 요구 수준이 다르므로 어떤 통제가 어떤 조항을 만족하는지 매핑해 두는 것이 실무의 출발점입니다.

EFS와 EC2

가장 기본이 되는 EC2 접속 구성을 만든다

웹사이트를 서버 한 대에 올려 잘 쓰다가 트래픽이 늘어 서버를 두 대로 늘리는 순간, 사용자가 올린 사진과 로그가 첫 번째 서버에만 남아 두 번째 서버로 접속한 사람은 그 파일을 찾지 못하는 일이 벌어집니다. Amazon EFS(Elastic File System)는 여러 EC2(Elastic Compute Cloud) 인스턴스가 같은 파일 시스템을 동시에 마운트(mount)해 함께 쓰도록 만든 완전 관리형 네트워크 파일 저장소로, 컴퓨팅과 저장을 분리하는 클라우드 설계의 기본 부품입니다.

아파트 단지에 비유하면 EC2 인스턴스는 각 세대이고, EFS는 단지 지하에 있는 공용 창고입니다. 각 세대가 자기 집에만 물건을 쌓아 두면 이사를 가거나 세대가 늘어날 때 물건이 사라지지만, 공용 창고에 넣어 두면 어느 세대든 같은 열쇠로 같은 물건을 꺼낼 수 있습니다.

세대마다 창고로 통하는 통로를 내고(NFS 프로토콜), 창고 주인은 물건이 늘어나면 선반을 자동으로 넓혀 주며 여러 세대가 동시에 같은 선반을 열어도 순서가 엉키지 않게 잠금을 관리합니다. 그래서 새 세대를 들일 때는 창고 주소만 알려 주면 되고, 세대가 나가도 창고의 물건은 그대로 남습니다.

정리하면 EFS는 여러 EC2 인스턴스가 NFS(Network File System)를 통해 동시에 붙어 쓰는 공유 파일 시스템이고, 용량은 실제 사용량에 따라 늘어나며 여러 가용 영역(Availability Zone)에 데이터를 복제해 가용성을 높입니다. 서버를 늘리고 줄이는 일과 파일을 보관하는 일을 분리해 두는 것이 EFS를 쓰는 핵심입니다.

EFS와 Auto Scaling

늘었다 줄었다 하는 인스턴스가 같은 파일을 공유하는 구조를 안다

트래픽이 몰리는 시간에만 서버를 늘렸다가 새벽에 줄이는 Auto Scaling을 붙여 두면, 늘어난 서버가 방금 전 서버가 저장한 파일을 보지 못해 주문서가 절반만 처리되는 일이 생깁니다. Amazon EFS는 이렇게 늘었다 줄었다 하는 EC2 인스턴스들이 모두 같은 파일 시스템을 공유하도록 해 주는 저장소입니다.

사무실 좌석을 고정석 대신 자유석으로 바꾼 회사를 생각해 보면, 직원은 늘고 줄어도 자리는 그때그때 배정되지만 서류 캐비닛은 사무실 한가운데 공용으로 하나만 둡니다. 신입이 어느 자리에 앉든 같은 캐비닛 서랍을 열 수 있고, 퇴근한 직원이 맡긴 서류도 다음 사람이 그대로 이어 받습니다.

Auto Scaling은 이 자유석 배정을 담당하는 총무이고, 새 직원이 들어올 때 EFS라는 공용 캐비닛 주소를 접속 설정에 적어 주면 별도 복사 작업 없이 바로 업무를 시작합니다. 직원 수가 열 배로 늘어도 캐비닛은 하나이므로 서류가 서로 어긋나지 않고, 캐비닛의 수납량은 회사가 미리 정하지 않아도 사용한 만큼 늘어납니다.

정리하면 Auto Scaling 그룹의 인스턴스들이 EFS를 공통 마운트 대상으로 삼으면, 인스턴스는 일회용이 되고 상태는 파일 시스템에 남습니다. 이 구조 덕분에 서버를 언제든 지우고 새로 만들 수 있는 무상태(stateless) 설계가 가능해집니다.

EFS와 컨테이너(ECS)

ECS 태스크가 EFS를 볼륨으로 쓰는 방법을 안다

컨테이너로 서비스를 돌리면 배포할 때마다 새 컨테이너가 이전 컨테이너를 대체하는데, 컨테이너 안에 파일을 저장해 두면 그 컨테이너가 사라지는 순간 파일도 함께 사라집니다. Amazon ECS(Elastic Container Service)에서 태스크가 Amazon EFS를 볼륨(volume)으로 붙여 쓰는 방식은 이 문제를 풀기 위한 구성입니다.

전시회장에 임시 부스를 세워 장사하는 상인에 비유하면, 부스를 철거하면 부스 안 선반에 둔 물건도 같이 사라지므로 중요한 물건은 전시장 뒤편 공용 창고(EFS)에 두어야 합니다. 부스를 다시 세울 때 창고 위치만 등록해 두면 새 부스에서도 같은 물건을 그대로 꺼내 쓸 수 있고, 여러 부스가 동시에 같은 창고를 봐도 각자 자기 구역을 나눠 쓸 수 있습니다.

기술적으로는 태스크 정의(task definition)에 EFS 파일 시스템 ID와 접근점(access point), 컨테이너에 연결할 경로를 볼륨으로 선언하고 여러 태스크가 같은 접근점을 공유하도록 설정합니다. 이때 EC2 시작 유형과 Fargate 시작 유형은 지원 방식과 요구 사항이 다를 수 있으므로, 쓰려는 시작 유형의 문서를 확인해야 합니다.

정리하면 ECS 태스크는 수명이 짧은 컴퓨팅 단위이므로 상태가 필요한 데이터는 EFS 같은 외부 볼륨에 두고, 태스크 정의에서 그 볼륨을 마운트해 쓰는 것이 기본 패턴입니다. 컨테이너를 몇 번을 갈아 끼워도 데이터는 그대로 남습니다.

EFS와 EKS

PersistentVolume으로 EFS를 붙이는 패턴을 익힌다

쿠버네티스(Kubernetes)에서 파드(pod)는 언제든 죽고 다시 만들어지는 존재라, 파드 안 디스크에 쓴 데이터는 재시작 한 번에 사라집니다. Amazon EKS(Elastic Kubernetes Service)에서 Amazon EFS를 PersistentVolume(영구 볼륨)으로 붙이는 패턴은 파드가 바뀌어도 같은 파일을 이어 쓰게 해 주는 방법입니다.

학교 사물함에 비유하면 파드는 매 학기 바뀌는 담임 선생님이고, PersistentVolume은 교무실 뒤편에 붙박이로 있는 사물함, PersistentVolumeClaim은 이 크기의 사물함 하나를 달라는 신청서입니다. 선생님이 바뀌어도 신청서에 적힌 사물함 번호는 그대로이므로 새 담임이 같은 사물함을 열어 이전 학기의 자료를 이어 받습니다.

EFS는 ReadWriteMany를 지원해 여러 파드가 동시에 같은 볼륨을 읽고 쓸 수 있으므로, 여러 복제본이 같은 업로드 폴더를 공유해야 하는 경우에 잘 맞습니다. 실제 구성은 EFS 파일 시스템과 접근점을 만들고, PersistentVolume과 PersistentVolumeClaim을 선언한 뒤 파드의 볼륨으로 연결하는 순서를 따릅니다.

정리하면 EKS에서 EFS는 파드의 수명과 분리된 영구 저장소로 동작하고, 파드는 PVC를 통해 그 저장소를 요청해 붙입니다. 저장소의 수명과 컴퓨팅의 수명을 분리하는 것이 이 패턴의 핵심입니다.

EFS CSI 드라이버

쿠버네티스에서 EFS를 동적으로 프로비저닝하는 원리를 안다

쿠버네티스에서 볼륨을 쓰려면 미리 PersistentVolume을 손으로 만들어 두어야 한다면, 애플리케이션이 늘 때마다 관리자가 저장소를 수작업으로 준비해야 합니다. EFS CSI(Container Storage Interface) 드라이버는 이런 신청이 들어오면 EFS 위에 저장 공간을 자동으로 만들어 주는 중개 프로그램입니다.

객실을 미리 다 만들어 두고 손님을 받는 대신 예약이 들어오면 그때그때 방을 배정하는 호텔에 비유할 수 있습니다. 손님(파드)은 프런트(드라이버)에 방을 달라고 하고, 프런트는 건물주(EFS)의 빈 공간에 방을 만들어 열쇠(접근점)를 건네줍니다.

이때 StorageClass가 어떤 등급의 방을 줄지 정하는 규정표 역할을 하고, 드라이버는 그 규정에 따라 접근점을 만들고 PersistentVolume을 자동으로 등록하는 동적 프로비저닝(dynamic provisioning)을 수행합니다. 드라이버는 각 노드에서 실제로 마운트를 수행하는 부분과 제어 평면에서 볼륨을 관리하는 부분으로 나뉘어 동작합니다.

정리하면 EFS CSI 드라이버는 쿠버네티스의 볼륨 요청을 EFS의 접근점 생성과 연결로 번역해 주는 구성 요소입니다. 덕분에 관리자는 저장소를 미리 만들지 않고 StorageClass와 PVC만 선언하면 됩니다.

EFS와 Lambda

함수가 공유 파일을 읽고 쓰는 구성을 안다

서버리스 함수는 요청이 올 때만 잠깐 실행되고 끝나므로, 함수 안의 임시 디스크에 파일을 써 두면 다음 호출에서는 그 파일이 없습니다. Amazon EFS를 함수에 마운트하면 이 짧은 실행 단위들이 같은 공유 파일을 읽고 쓸 수 있습니다.

행사장에서 그때그때 불려 오는 도우미(함수)에 비유하면, 도우미는 행사가 끝나면 자기 소지품과 함께 사라지지만 행사장 벽에 붙은 공용 게시판(EFS)의 내용은 다음 도우미에게도 그대로 보입니다. 도우미는 게시판에서 오늘의 안내문을 읽고 처리한 일을 다시 게시판에 적어 두므로, 서로 만난 적 없는 도우미들도 일을 이어 갈 수 있습니다.

구성할 때는 함수가 있는 VPC와 같은 네트워크에 EFS 마운트 대상(mount target)을 두고, 함수의 파일 시스템 설정에 접근점과 로컬 마운트 경로를 지정합니다. 여러 함수 인스턴스가 동시에 같은 파일을 고치면 순서가 엉킬 수 있으므로, 잠금이나 파일 분리 같은 동시성 처리를 함께 설계해야 합니다.

정리하면 Lambda 함수는 EFS를 로컬 경로처럼 마운트해 공유 파일을 읽고 쓸 수 있고, 네트워크와 권한, 동시 접근만 정리하면 됩니다. 함수의 수명과 데이터의 수명을 분리하는 것이 이 구성의 목적입니다.

EFS와 AWS Backup

백업 계획에 EFS를 넣는 방법을 안다

부서 공용 파일 서버의 자료를 누군가 실수로 지웠는데 복사본도 스냅샷도 없다면 복구는 사실상 불가능하고, 담당자는 어디까지가 원본인지부터 확인해야 하는 막막한 상황에 놓입니다. Amazon EFS는 여러 서버가 동시에 붙어 함께 쓰는 공유 파일 저장소인데, 이런 저장소까지 한곳에서 백업하고 싶다는 요구가 커지면서 AWS Backup이라는 관리형 백업 서비스에 EFS를 자원으로 등록하는 방식이 널리 쓰입니다. 여러 부서가 함께 쓰는 문서 창고를 떠올려 보면, 창고마다 직원이 따로 복사본을 떠 두는 대신 관리사무소가 "매일 밤 2시에 전체를 복사하고 30일치를 보관한다"는 규칙표를 한 장 만들어 두는 편이 훨씬 안전합니다. AWS Backup의 백업 계획(backup plan)이 바로 그 규칙표이고, 여기에 EFS 파일 시스템을 자원으로 할당(assign)하면 규칙표가 정한 주기와 보관 기간대로 백업이 자동으로 만들어집니다.

만들어진 백업은 백업 볼트(backup vault)라는 잠금 보관함에 차곡차곡 쌓이며, 원본과 다른 리전이나 다른 계정에 두면 사고 하나로 둘 다 잃는 일을 막을 수 있습니다. 여기에 수명 주기(lifecycle) 규칙을 붙이면 오래된 백업을 더 저렴한 콜드 스토리지로 옮겨 보관 비용을 줄일 수 있습니다. 정리하면 AWS Backup은 EFS를 비롯한 여러 저장소의 백업 시점과 보관 기간, 보관 위치를 백업 계획 하나로 통일해 관리하는 서비스이고, EFS는 그 계획에 등록되는 대상 자원 가운데 하나입니다.

EFS와 DataSync

온프레미스나 다른 스토리지에서 데이터를 옮기는 구성을 안다

온프레미스 파일 서버에 쌓인 수 테라바이트의 자료를 AWS로 옮겨야 하는데, 복사 도중 끊기면 처음부터 다시 해야 하고 옮긴 뒤 원본과 똑같은지 확인할 방법도 없다면 이사 자체가 두려운 일이 됩니다. AWS DataSync는 이런 대용량 데이터 이동을 전담하는 서비스로, 온프레미스 스토리지나 다른 클라우드 저장소와 Amazon EFS 사이를 안전하게 오가며 복사하도록 만들어졌습니다. 이사를 떠올려 보면, 짐을 하나씩 손으로 나르는 대신 이삿짐센터에 맡기고 출발지 주소와 도착지 주소, 무엇을 옮길지를 적은 견적서를 내는 편이 훨씬 정확합니다. DataSync의 작업(task)이 그 견적서에 해당하고, 출발지와 도착지를 각각 위치(location)로 지정하면 어느 쪽이든 EFS, S3, 온프레미스 파일 서버가 될 수 있습니다.

온프레미스처럼 AWS 밖에 있는 곳과 연결할 때는 그 건물 안까지 들어가 짐을 꾸리는 작업반이 필요한데, 이것이 현장에 설치하는 DataSync 에이전트(agent)입니다. 옮기는 과정에서는 변경된 부분만 다시 보내고 전송 후 무결성을 검사하며, 필요하면 주기적으로 다시 돌려 원본과 대상을 계속 같게 유지할 수 있습니다. 결국 DataSync는 위치와 작업이라는 두 가지 설정만으로 저장소 사이의 대량 복사를 예약하고 검증까지 수행하는 이동 전용 서비스이며, EFS는 그 이동의 출발지나 도착지로 지정되는 저장소 중 하나입니다.

EFS와 CloudWatch

지표와 로그를 어디서 어떤 이름으로 보는지 정리한다

공유 파일 시스템이 갑자기 느려졌는데 언제부터 왜 느려졌는지 아무도 답하지 못하면, 원인을 찾는 동안 서비스는 계속 느린 채로 버티게 됩니다. Amazon EFS는 상태를 스스로 알려 주지 않으므로, Amazon CloudWatch라는 모니터링 서비스로 지표(metric)와 로그를 모아 지켜보는 구성이 기본이 됩니다. 건물 관리실의 계기판을 떠올려 보면, 전기 계량기와 수도 계량기가 각각 이름표를 달고 수치를 올려 주듯 CloudWatch에는 EFS가 보내는 값들이 정해진 이름으로 쌓입니다. 대표적으로 현재 연결된 클라이언트 수를 나타내는 ClientConnections, 처리량 한도에 얼마나 가까운지를 보여 주는 PercentIOLimit, 버스트 크레딧 잔량인 BurstCreditBalance, 실제로 오간 바이트양인 MeteredIOBytes 같은 지표가 있습니다.

여기에 파일 접근 감사가 필요하면 액세스 포인트 단위로 액세스 로그를 남겨 CloudWatch Logs로 보내도록 설정할 수 있어, 누가 어떤 파일을 읽고 썼는지까지 추적할 수 있습니다. 이 값들에 경보(alarm)를 걸어 두면 한도에 가까워지는 순간을 사람이 지켜보지 않아도 알 수 있습니다. 정리하면 EFS의 상태는 CloudWatch의 지표와 로그로 관찰하며, 어떤 이름의 지표가 어느 한도를 뜻하는지 알아 두는 것이 장애를 빠르게 짚는 출발점입니다.

EFS와 EventBridge

파일 시스템 관련 이벤트를 자동화에 연결하는 법을 안다

새벽에 돌던 백업이 실패했는데 그 알림이 담당자 메일함에만 쌓여 있고 아무도 보지 않았다면, 문제는 다음 장애가 터질 때에야 드러납니다. Amazon EFS는 파일 시스템의 상태 변화를 이벤트로 내보낼 수 있고, Amazon EventBridge는 그 이벤트를 받아 정해진 자동 동작으로 연결하는 라우터 역할을 합니다. 아파트 경비실의 화재 경보를 떠올려 보면, 감지기가 울리는 순간 소방서에 신고가 가고 엘리베이터가 1층으로 내려오고 방송이 나가는 것이 이상적입니다. EventBridge의 이벤트 버스(event bus)가 그 신호선이고, 규칙(rule)은 "어떤 신호가 오면 무엇을 할지" 적어 둔 대응표이며, 이벤트 패턴(pattern)으로 신호의 종류와 대상을 걸러 냅니다.

EFS 쪽에서는 파일 시스템 생성이나 삭제 같은 상태 변경이 이벤트로 전달되고, 대응표에 맞는 이벤트가 들어오면 미리 지정한 대상(target)인 Lambda 함수, SNS 주제, Step Functions 워크플로 등이 자동으로 실행됩니다. 그래서 백업 실패를 감지해 담당자 호출과 재시도 작업을 한 번에 묶는 식의 자동화가 가능해집니다. 결국 EventBridge는 EFS가 내보내는 이벤트를 조건에 따라 걸러 필요한 작업으로 넘기는 허브이고, 사람이 알림을 확인하기를 기다리지 않고 대응하게 만드는 것이 핵심입니다.

EFS와 Transfer Family

SFTP로 EFS에 올리고 내리는 구성을 안다

거래처가 보안 규칙상 SFTP만 쓸 수 있다고 하는데 우리 쪽 저장소는 공유 파일 시스템이라 그대로는 접속 창구가 없어, 매번 사람이 파일을 옮겨 주는 일이 반복됩니다. AWS Transfer Family는 SFTP 같은 파일 전송 프로토콜을 관리형으로 제공하는 서비스로, 그 도착지나 출발지로 Amazon EFS를 지정할 수 있습니다. 건물 정문의 접수 데스크를 떠올려 보면, 방문자는 정문 창구에서만 신분을 확인받고 안쪽 사무실에는 직접 들어가지 않습니다. Transfer Family 서버가 그 정문 창구이고, 사용자(user)마다 등록한 SSH 공개 키가 신분증 역할을 하며, 사용자의 홈 디렉터리를 EFS 안의 특정 경로로 매핑하면 접수된 파일이 곧바로 공유 저장소의 정해진 서랍에 들어갑니다.

정문은 인터넷에 열려 있지만 안쪽 사무실은 그대로 가려져 있으므로, 저장소를 외부에 직접 노출하지 않고도 거래처와 파일을 주고받을 수 있습니다. 접속 기록과 전송 내역은 따로 남겨 감사에 쓸 수 있습니다. 정리하면 Transfer Family는 SFTP 접속 창구를 대신 세워 주고 그 뒤의 실제 보관은 EFS가 맡는 구조이며, 사용자별 키와 홈 경로 설정이 보안의 중심이 됩니다.

8부. AWS 서비스 통합090

EFS와 S3·FSx 조합

여러 스토리지를 역할별로 섞어 쓰는 설계를 안다

모든 파일을 저장소 하나에 몰아넣으면, 자주 읽는 작은 파일과 몇 년씩 보관만 하는 대용량 자료가 같은 값과 같은 성능을 쓰게 되어 비용도 성능도 어긋납니다. 그래서 Amazon EFS, Amazon S3, Amazon FSx를 각자의 잘하는 역할에 따라 섞어 쓰는 설계가 흔히 쓰입니다. 집 안의 냉장고와 창고와 금고를 떠올려 보면, 매일 꺼내 쓰는 것은 냉장고에, 계절 물건은 창고에, 귀중품은 금고에 두는 것이 자연스럽습니다. EFS는 여러 서버가 동시에 열고 고치는 공유 작업 공간, 즉 냉장고에 해당하고, S3는 객체 단위로 무한히 쌓아 두는 대용량 보관 창고에 해당합니다.

FSx는 특정 작업에 맞춰 튜닝된 전문 저장소 묶음으로, 고성능 컴퓨팅용인 FSx for Lustre, 윈도우 공유용인 FSx for Windows File Server, NetApp과 OpenZFS 기반 제품 등이 있어 하둡 분석이나 윈도우 애플리케이션처럼 요구가 뚜렷한 자리에 놓입니다. 이렇게 나눠 두면 작업 공간의 파일은 EFS에서 바로 고치고, 끝난 결과물만 S3로 넘겨 장기 보관하는 흐름을 만들 수 있습니다. 결국 저장소 선택은 무엇이 더 좋은가의 문제가 아니라 어떤 접근 방식과 성능, 보관 기간이 필요한가의 문제이며, EFS는 동시 편집이 필요한 공유 영역을 맡는 조각으로 자리합니다.

EFS 백업 개요

무엇을 어떤 방식으로 백업할 수 있는지 정리한다

파일 서버 한 대가 갑자기 망가지면 그 안에 있던 자료는 함께 사라지고, 복구할 사본이 없으면 팀은 몇 달 치 작업을 통째로 잃습니다. 그래서 Amazon EFS(Elastic File System)에는 파일 시스템 전체를 시점 단위로 보관해 두는 백업 기능이 마련되어 있습니다.

백업은 아파트 관리사무소가 세대별 짐을 창고에 맡기는 일과 비슷합니다. 관리사무소는 특정 날짜의 집 안 상태를 통째로 사진 찍듯 떠서 별도 창고인 백업 볼트(backup vault)에 넣어 두고, 원래 집이 불에 타도 그 기록을 보고 짐을 다시 채워 넣습니다.

백업은 증분 방식이라 처음 한 번만 전체를 뜨고 그 뒤로는 바뀐 부분만 더하므로 창고를 계속 새로 지을 필요가 없습니다. 보관 기간과 주기를 정책으로 정해 두면 사람이 매번 손대지 않아도 정해진 시각에 자동으로 돌아갑니다.

정리하면 EFS 백업은 파일 시스템의 특정 시점 상태를 백업 볼트에 증분으로 쌓아 두는 일이고, 그 결과물로 같은 리전이나 다른 리전에 새 파일 시스템을 되살릴 수 있습니다.

9부. 데이터 보호와 복구092

AWS Backup으로 EFS 백업

백업 계획과 보관 기간을 설정한다

백업을 파일 시스템마다 손으로 돌리면 담당자가 바뀌는 순간 아무도 돌리지 않게 되고, 정작 사고가 난 날에야 백업이 없다는 사실을 알게 됩니다. AWS Backup은 이런 백업을 한곳에서 계획적으로 관리하는 관리형 서비스이고, EFS는 그 서비스가 지원하는 대상 가운데 하나입니다.

백업 계획(backup plan)은 아파트 경비실의 순찰표와 같습니다. 순찰표에는 언제 어느 구역을 돌지와 얼마나 자주 돌지가 적혀 있고, 여기에 대상 자원을 묶은 자원 할당(resource assignment)을 붙이면 그 묶음의 모든 파일 시스템이 같은 순찰표를 따릅니다.

순찰 기록을 보관하는 창고가 백업 볼트이고, 볼트에는 보관 기간(lifecycle)을 적어 두어 오래된 기록을 콜드 스토리지로 내리거나 정해진 날에 지웁니다. 또한 백업 작업이 실패하면 알림을 받도록 구성할 수 있어, 사고가 나기 전에 빈틈을 발견하게 됩니다.

즉 AWS Backup에서 EFS를 백업한다는 것은 백업 계획으로 주기와 대상을 정하고 백업 볼트에 보관 기간을 걸어 두는 일이며, 그 덕분에 백업 여부를 사람이 기억하지 않아도 됩니다.

EFS 복원 절차

백업에서 새 파일 시스템으로 되살리는 순서를 익힌다

백업이 있어도 되살리는 순서를 모르면 사고 당일 복원은 대개 늦어지고, 급한 마음에 원본 위에 덮어써서 상황을 더 나쁘게 만들기도 합니다. EFS 복원은 백업에서 새 파일 시스템을 만들어 내는 절차이고, 원본을 건드리지 않는 것이 핵심입니다.

복원은 창고에 맡긴 짐을 새 집으로 배달시키는 일과 같습니다. 먼저 백업 볼트에서 어느 시점의 사본을 쓸지 고르고, 그 사본을 담을 새 집의 주소에 해당하는 새 파일 시스템의 ID나 이름을 지정합니다.

배달은 반드시 새 집으로만 가고 원래 살던 집에는 손을 대지 않으므로, 남아 있던 자료와 복원본을 나란히 놓고 비교할 수 있습니다. 복원 작업이 끝나면 새 파일 시스템을 마운트 대상에 연결하고 애플리케이션이 그쪽을 보도록 바꾼 뒤, 문제가 없음을 확인하고 나서 옛 파일 시스템을 정리합니다.

정리하면 EFS 복원은 복구 시점(recovery point)을 골라 새 파일 시스템으로 되살리고 마운트 대상을 새것으로 바꾸는 순서이며, 원본을 덮어쓰지 않는 것이 안전의 기본입니다.

EFS 복제(Replication)

같은 리전·다른 리전 복제가 어떻게 동작하는지 이해한다

한 리전에만 파일 시스템을 두면 그 리전 자체가 멈추는 사고에서 자료와 서비스가 함께 멈추고, 다른 지역으로 옮기려 해도 복사본이 없으면 손쓸 방법이 없습니다. EFS 복제(replication)는 파일 시스템의 내용을 다른 파일 시스템으로 계속 따라 붙여 두는 기능이고, 같은 리전 안에서도 다른 리전 사이에서도 설정할 수 있습니다.

복제는 본점 장부를 지점에 매일 필사해 두는 일과 비슷합니다. 본점 장부인 원본(source)에 새 항목이 적히면 그 차이만 지점 장부인 대상(destination)에 순서대로 옮겨 적고, 지점 장부는 읽기 전용이라 직원이 마음대로 고칠 수 없습니다.

처음에는 기존 내용을 한 번에 넘기고 그 뒤에는 바뀐 부분만 흘려보내므로, 지점 장부는 본점보다 조금 늦지만 거의 같은 상태를 유지합니다. 같은 리전 복제는 리전 안의 사고에, 다른 리전 복제는 리전 전체 장애나 지연 문제에 대비하는 쪽에 가깝습니다.

즉 EFS 복제는 원본의 변경분을 다른 파일 시스템에 계속 반영해 두는 일이고, 대상이 읽기 전용이라 원본과 섞이지 않으면서 대비책 역할을 합니다.

복제 기반 재해 복구 설계

장애 시 복제본으로 전환하는 절차를 만든다

재해 복구 계획을 문서로만 두면 정작 리전이 멈춘 날 누가 무엇을 어떤 순서로 바꿔야 하는지 몰라 복구가 몇 시간씩 밀립니다. EFS 복제로 다른 리전에 대기본을 두었다면, 장애 시 그 대기본을 주인공으로 세우는 절차까지 정해 두어야 실제로 쓸 수 있습니다.

이것은 아파트의 비상 발전기와 같습니다. 평소에는 본관 전력이 돌아가고 발전기에 해당하는 복제 대상 파일 시스템은 충전만 하다가, 정전이 나면 관리인이 차단기를 내리고 발전기 선로로 바꿔 올립니다.

미리 정해 둘 것은 무엇을 기준으로 정전을 판단할지, 누가 전환을 승인할지, 어느 애플리케이션이 어느 파일 시스템을 마운트하는지, 그리고 다시 본관으로 돌아올 때의 순서입니다. 복제 대상은 읽기 전용이므로 그대로는 서비스에 쓸 수 없고, 복제 관계를 끊고 쓰기가 가능한 상태로 만드는 단계가 필요하며, 되돌아올 때는 원본과 대기본의 내용 차이를 어떻게 맞출지도 정해야 합니다. 전환 훈련을 정기적으로 해 두면 문서에 적힌 순서가 실제로 맞는지 확인할 수 있습니다.

정리하면 복제 기반 재해 복구는 복제본을 유지하는 것에서 끝나지 않고, 판단 기준과 전환 순서, 복귀 절차를 미리 정해 두는 설계까지 포함합니다.

EFS 스냅샷 오해와 실제

스냅샷 기능이 없는 이유와 그 대안을 안다

EFS를 쓰던 사람이 볼륨 단위 서비스의 습관대로 스냅샷을 찾다가 없어서 당황하는 일이 흔하고, 그 자리에서 백업조차 불가능하다고 오해하기도 합니다. EFS에는 사용자가 직접 찍는 스냅샷 기능이 없고, 그 자리를 AWS Backup의 백업이 대신합니다.

이 차이는 건물을 통째로 복사하는 것과 방마다 사진을 찍는 것의 차이에 가깝습니다. 블록 스토리지의 스냅샷은 정해진 순간의 볼륨 상태를 한 장의 사진처럼 남기지만, EFS는 여러 서버가 동시에 접속하는 공유 파일 시스템이라 그런 사진 한 장을 찍어 두는 방식이 잘 맞지 않습니다.

대신 AWS Backup은 파일 시스템 전체를 시점별 복구 지점으로 보관하고, 증분으로 쌓아 공간을 아끼며, 보관 기간과 다른 리전 복사를 정책으로 붙일 수 있습니다. 또한 외부에서 직접 찍는 스냅샷은 같은 리전 안에 남는 경우가 많아 리전 장애까지 대비하기 어렵습니다. 그래서 EFS에서 스냅샷을 찾는 대신 백업 계획을 세우는 것이 올바른 접근입니다.

결국 EFS에 스냅샷이 없는 것은 기능이 빠진 것이 아니라 백업을 다른 서비스에 맡긴 설계 선택이고, 시점 복원이 필요하면 AWS Backup의 백업과 복원 절차를 쓰면 됩니다.

실수로 지운 파일 복구

휴지통이 없을 때 쓸 수 있는 복구 전략을 세운다

공유 파일 시스템을 여러 사람이 함께 쓰다 보면 누군가 파일을 지웠는데 아무도 그 사실을 모르는 일이 생깁니다. 특히 Amazon EFS(Elastic File System)처럼 서버 여러 대가 같은 디렉터리를 붙여 쓰는 환경에서는 삭제가 곧바로 모든 서버에 반영되고, 운영체제의 휴지통 같은 안전망이 없는 경우가 많아 난감해집니다. 그래서 휴지통이 없을 때 무엇을 근거로 되살릴 수 있는지 미리 정해 두는 전략이 필요합니다.

아파트 우편함을 생각해 보십시오. 누군가 실수로 우편함에서 봉투를 꺼내 버렸다면 우편함 안을 뒤져도 나오지 않습니다.

대신 경비실에 배달 기록이 남아 있고, 발송인이 보관한 사본이 있으며, 큰 우편물은 별도 창고에 한 부 더 보관해 둘 수 있습니다. 파일 복구도 같아서 원본이 사라진 자리 대신 다른 곳에 남은 흔적을 찾아야 합니다.

여기서 배달 기록은 파일의 변경 이력과 접근 로그, 발송인의 사본은 백업 저장소, 별도 창고는 다른 리전이나 다른 스토리지 클래스에 둔 복제본에 해당합니다.

정리하면, EFS 자체에는 휴지통 기능이 없으므로 AWS Backup으로 주기적인 백업을 남기고 버전 관리가 되는 저장소에 사본을 두는 것이 기본 대비책입니다. 사고가 나면 먼저 삭제 시각과 경로를 로그에서 좁힌 뒤 가장 가까운 시점의 백업을 별도 위치에 복원해 확인하고, 원본 위치로 되돌리는 순서로 진행합니다.

EFS 삭제와 보호

건물의 소방 설비와 비슷합니다. 아무리 조심하는 사람이라도 불이 날 수 있으니 경보기와 스프링클러를 미리 달아 두고, 비상구는 잠그지 않되 함부로 열 수 없게 합니다.

EFS에서는 삭제 방지 설정이 잠금장치, 리소스 정책과 IAM 권한이 출입 통제, AWS Backup이 비상 대피용 사본, CloudWatch 경보가 화재 경보기에 대응합니다. 평소에는 아무도 잠금장치를 신경 쓰지 않지만 사고 순간에는 그 장치 하나가 건물 전체를 지킵니다.

삭제 방지는 결국 권한을 좁히고, 삭제 전 확인 절차를 자동화에 넣고, 백업을 별도 계정이나 별도 보관함에 두는 세 가지로 모입니다. 사고가 이미 났다면 무엇이 언제 사라졌는지 기록으로 확정한 뒤 백업에서 복원하고, 같은 경로를 다시 지우지 못하도록 권한을 먼저 손보는 것이 순서입니다.

백업 비용 최적화

보관 기간과 콜드 스토리지로 비용을 줄인다

백업은 많이 남길수록 안전해 보이지만, 그만큼 매달 청구서가 올라가 어느 순간 예산을 압박합니다. 특히 변경이 잦은 공유 파일 시스템은 백업본이 빠르게 쌓이므로, 보관 기간과 저장 위치를 정하지 않으면 필요 없는 사본이 계속 비용을 만들어 냅니다.

창고를 빌리는 상황을 떠올려 보십시오. 매일 들어오는 물건을 모두 상온 창고에 두면 임대료가 감당이 안 되니, 최근 물건은 꺼내기 쉬운 앞쪽 선반에, 오래된 물건은 싼 옥상 창고로 옮깁니다. 그리고 일정 기간이 지난 물건은 아예 폐기 규칙을 정해 둡니다.

백업에서 앞쪽 선반은 최근 복구 시점, 옥상 창고는 콜드 스토리지(cold storage) 같은 저비용 계층, 폐기 규칙은 보관 기간 만료 정책에 해당합니다.

따라서 복구 목표에 맞춰 최근 며칠은 자주, 그 이전은 드물게 남기고 오래된 사본은 저렴한 계층으로 넘기는 규칙을 정해야 합니다. 여기에 백업 계획을 파일 시스템 단위로 나누고 실제 사용량과 청구 내역을 주기적으로 대조하면, 안전을 크게 줄이지 않으면서 비용만 덜어낼 수 있습니다.

RTO와 RPO 설계

EFS 기준으로 목표 복구 시간을 정하는 법을 안다

장애가 났을 때 "언제까지 복구할 것인가"와 "얼마나 최근 데이터까지 살릴 것인가"를 미리 정하지 않으면, 복구 작업은 현장에서 즉흥적으로 진행됩니다. 그 결과 서비스는 예상보다 오래 멈추고, 되살린 데이터가 어느 시점 것인지도 설명하지 못하는 상황이 생깁니다. 이 두 기준을 숫자로 합의해 두는 것이 RTO(Recovery Time Objective, 목표 복구 시간)와 RPO(Recovery Point Objective, 목표 복구 시점)입니다.

아파트 정전 대비를 생각해 보십시오. 관리사무소는 "정전 후 몇 분 안에 비상 발전기를 돌린다"는 목표와 "엘리베이터 기록은 몇 분 단위까지 잃어도 된다"는 허용치를 함께 정합니다.

발전기 준비 시간이 RTO이고, 마지막 저장 시점과의 간격이 RPO입니다. EFS에서는 백업 주기가 RPO를, 백업에서 복원해 서비스에 다시 붙이는 절차의 길이가 RTO를 결정합니다.

결국 RTO는 백업을 얼마나 빨리 되살릴 수 있는지에, RPO는 백업을 얼마나 자주 뜨는지에 달려 있습니다. 두 값을 정한 뒤에는 실제로 복원 훈련을 해서 걸린 시간을 재어 보고, 목표에 못 미치면 주기나 절차를 조정하는 것이 설계의 마무리입니다.

공유 파일 시스템은 눈에 보이지 않아서, 느려지고 있는지 한도에 닿았는지 화면만 봐서는 알기 어렵습니다. 문제가 터진 뒤에야 원인을 찾기 시작하면 이미 사용자는 영향을 받은 뒤이고, 어느 지표를 봐야 하는지조차 합의가 없으면 대응이 늦어집니다. 그래서 평소에 확인할 지표 목록을 미리 정해 두는 것이 필요합니다.

자동차 계기판을 떠올려 보십시오. 운전자는 속도계, 연료계, 엔진 경고등을 따로 외우지 않아도 어디를 봐야 하는지 압니다.

속도계는 처리량(Throughput), 연료계는 남은 용량과 크레딧, 경고등은 오류와 지연을 알려 주는 신호입니다. 계기판에 없는 고장은 정비소 진단기로 보듯, 세부 원인은 별도 로그와 지표로 파고들게 됩니다.

EFS에서 우선 보는 지표는 처리량과 허용 처리량 대비 사용률, 클라이언트 연결 수, 읽기와 쓰기 지연, 버스트 크레딧 잔량, 그리고 메타데이터 작업 부하입니다. 이 목록을 대시보드에 묶어 두고 정상 범위를 정해 두면, 이상이 생겼을 때 어느 지표가 먼저 흔들렸는지로 원인을 좁힐 수 있습니다.

BurstCreditBalance 읽기

버스트 크레딧이 바닥나는 상황을 지표로 읽는다

처리량이 갑자기 절반으로 떨어졌는데 설정을 바꾼 사람도 없고 오류도 없을 때, 원인은 대개 크레딧 고갈입니다. Amazon EFS는 기본 처리량 모드에서 평소 쌓아 둔 크레딧을 써서 순간적으로 속도를 높이는 구조라, 크레딧이 바닥나면 성능이 조용히 낮은 수준으로 내려갑니다. 이때 BurstCreditBalance(버스트 크레딧 잔량) 지표를 보면 상황이 바로 드러납니다.

휴대폰 보조 배터리를 생각해 보십시오. 평소 충전해 둔 전력을 필요할 때 꺼내 쓰고, 다 쓰면 충전될 때까지는 기본 전력으로만 돌아갑니다.

크레딧 잔량이 배터리 게이지, 충전 속도가 파일 시스템 크기와 사용량에 따른 적립량, 방전 후의 동작이 기준 처리량으로의 하락에 해당합니다. 게이지가 계속 바닥에 붙어 있다면 그 기기는 원래 소비가 충전보다 크다는 뜻입니다.

정리하면 BurstCreditBalance가 0에 머무는 시간이 길어지는 것은 지속 사용량이 적립량을 넘었다는 신호입니다. 이때는 파일 시스템을 키우거나 처리량 모드를 프로비저닝 방식으로 바꾸는 식으로 한도를 직접 올리고, 그 뒤 지표가 회복되는지 다시 확인해야 합니다.

PercentIOLimit 읽기

최대 I/O 모드에서 한계에 닿았는지 확인한다

밤새 돌린 배치 작업이 평소의 두 배로 늘어졌는데 서버 사양도 네트워크도 문제가 없어 보여 원인을 잡지 못하는 일이 있습니다. 이런 때 파일 시스템이 낼 수 있는 처리 한도의 어느 지점까지 왔는지를 숫자 하나로 알려 주는 값이 PercentIOLimit입니다.

아파트 단지 정문에 구형 개찰구와 신형 개찰구가 나란히 있다고 합시다. 관리실은 신형 개찰구의 혼잡도를 구형 개찰구가 시간당 100명을 처리하던 기준에 맞춰 몇 퍼센트인지 표시해 둡니다.

PercentIOLimit이 100에 가깝다는 것은 지금 파일 시스템이 옛 기준의 한도까지 꽉 찼다는 뜻이고, 이 값이 낮게 유지되면 아직 여유가 있다는 뜻입니다. 다만 이 지표는 최대 I/O(Max I/O) 모드로 만든 파일 시스템에서 의미가 있으며, 범용 모드에서는 해석이 다르므로 모드를 먼저 확인해야 합니다.

정리하면 PercentIOLimit은 최대 I/O 모드 파일 시스템이 예전 세대 기준의 한도에 얼마나 가까이 붙었는지 보여 주는 지표이고, 이 값이 100에 붙은 채 지연이 늘어난다면 처리 한도가 병목이라고 판단할 수 있습니다.

마운트 끊김과 재연결

네트워크가 끊겼을 때 클라이언트가 어떻게 동작하는지 안다

네트워크가 잠깐 끊기는 것은 흔한 일인데, 그때 클라이언트가 곧바로 포기해 버리면 읽던 파일이 끊기고 작업이 처음부터 다시 시작됩니다. NFS 클라이언트는 이 상황을 견디도록 만들어져 있어, 연결이 끊겨도 정해진 방식으로 다시 붙으려 시도합니다. 친구와 통화하다가 전화가 끊기면 곧바로 다시 거는 사람을 떠올려 보시면 비슷합니다. 통화가 끊긴 사실을 알아차리고, 잠깐 기다렸다가 다시 연결을 시도하며, 상대가 계속 받지 않으면 몇 번 더 시도한 뒤에야 포기합니다.

NFS 클라이언트도 마운트 옵션에 적힌 재시도 방식과 대기 시간에 따라 이 과정을 반복하고, 서버가 돌아오면 끊겼던 요청을 이어서 처리합니다. 다만 재시도를 오래 붙잡고 있으면 그 요청을 기다리는 프로그램이 함께 멈춰 있게 되므로, 기다리는 시간을 어디까지 허용할지가 옵션의 핵심입니다. 정리하면 마운트 끊김과 재연결은 NFS 클라이언트가 서버와의 연결이 끊겼을 때 재시도 횟수와 대기 시간에 따라 다시 붙는 동작이며, 이 값을 어떻게 두느냐가 일시적 장애를 견디는 힘과 멈춤의 길이를 함께 정합니다.

응답 없음(hang) 대응

NFS가 멈춘 것처럼 보일 때 무엇을 할지 안다

NFS로 연결된 디렉터리를 쓰던 프로그램이 아무 응답 없이 멈춰 서면, 그 프로그램뿐 아니라 그것을 기다리는 화면과 스크립트까지 줄줄이 멈춘 것처럼 보입니다. 이런 상태를 흔히 hang이라고 부르는데, 원인이 서버인지 네트워크인지 클라이언트인지 가려내야 엉뚱한 곳을 건드리지 않습니다. 아파트 엘리베이터가 문은 닫혔는데 층 표시도 없이 멈춰 선 상황을 떠올려 보시면, 그 앞에 선 사람들이 다른 길을 찾지 못하고 서 있는 모습이 이 상황과 닮았습니다.

먼저 그 요청이 정말 서버에 닿지 못하는 것인지, 서버는 응답했는데 클라이언트가 기다리는 것인지를 나눠 봐야 하고, 이를 위해 마운트 상태와 CloudWatch 지표, 네트워크 연결을 차례로 확인합니다. 서버 쪽에 문제가 없다면 클라이언트의 재시도 설정이 지나치게 길게 잡혀 있는지 살피고, 필요하면 해당 마운트를 정리해 멈춘 요청을 풀어 줍니다. 이때 강제로 끊는 조치는 기다리던 작업이 실패할 수 있으므로 무엇이 멈춰 있는지 먼저 확인한 뒤에 합니다. 결국 응답 없음 대응은 NFS 요청이 어디에서 멈췄는지를 서버, 네트워크, 클라이언트 순서로 가려내고 재시도 설정과 마운트 상태를 확인해 푸는 일이며, 이 순서를 알아 두면 당황하지 않고 원인을 좁힐 수 있습니다.

잘 쓰던 EFS가 어느 날 갑자기 느려지면, 애플리케이션이 느려진 것인지 저장소가 느려진 것인지부터 헷갈립니다. 이때 원인 후보를 정해진 순서로 훑으면 감으로 고치려다 시간을 쓰는 일을 줄일 수 있습니다. 수도꼭지를 틀었는데 물이 갑자기 약해진 상황을 떠올려 보시면, 건물 전체가 그런지 우리 집만 그런지를 먼저 확인하게 됩니다.

EFS도 마찬가지로, 같은 파일 시스템을 쓰는 다른 클라이언트도 느린지 확인해 범위를 좁힌 뒤, 처리량이 한도에 닿았는지, 읽기와 쓰기 비중이 바뀌었는지, 작은 파일을 많이 다루는 패턴으로 달라졌는지를 차례로 봅니다. 여기에 클라이언트 쪽 네트워크 지연과 마운트 옵션이 적절한지도 확인 목록에 넣어 두면 좋습니다. 한 번에 하나씩 후보를 지워 나가야 어느 변화가 실제 원인이었는지 남습니다. 정리하면 성능 급락 대응은 영향 범위를 먼저 확인한 뒤 처리량 한도, 접근 패턴, 네트워크와 마운트 설정을 차례로 점검하는 절차이며, 이 순서를 습관으로 두면 갑작스러운 저하 앞에서도 확인할 곳을 잃지 않습니다.

탑재 대상 교체와 AZ 장애

회사 건물 한 곳에만 파일 서버를 두면 그 건물에 정전이 오는 순간 전 직원의 작업이 멈춥니다. Amazon EFS(Elastic File System)를 쓰는 팀도 파일을 읽고 쓰는 통로인 탑재 대상(mount target)이 가용 영역(Availability Zone, AZ) 하나에만 매달려 있으면 같은 곤란을 겪습니다. 여기서 가용 영역이란 전력과 네트워크를 따로 갖춘 데이터센터 묶음을 말합니다. 아파트 단지에 여러 동이 있고 각 동 경비실에서 택배를 받는다고 생각해 보십시오. 탑재 대상은 각 동의 경비실이고, 가용 영역은 동 하나하나이며, 파일 시스템은 모든 동이 함께 쓰는 중앙 창고입니다. 어떤 동의 경비실이 문을 닫아도 주민은 옆 동 경비실로 걸어가 택배를 받을 수 있고, 중앙 창고의 물건은 그대로입니다.

그래서 설계할 때는 서로 다른 가용 영역에 탑재 대상을 여러 개 만들어 두고, 컴퓨터가 자기 영역의 경비실이 응답하지 않으면 다른 영역의 탑재 대상 주소로 다시 연결하도록 준비합니다. 다만 이미 열려 있던 연결은 끊기므로, 응용 프로그램이 재연결을 견디도록 함께 손봐야 합니다. 정리하면 탑재 대상은 가용 영역마다 하나씩 두어 단일 영역 장애를 피하고, 장애가 나면 다른 영역의 탑재 대상으로 경로를 바꾸는 것이 핵심입니다.

EFS에서도 처리량 모드나 성능 모드 같은 설정을 바꿀 때 변경 전 값을 기록하고, 시험용 파일 시스템이나 일부 클라이언트에서 먼저 검증한 뒤 전체로 확대하며, 문제가 생기면 기록한 값으로 되돌리는 롤백(rollback)을 준비합니다. 또한 마운트 옵션이나 접근 권한처럼 서버 쪽에서 건드리는 항목은 설정 변경과 함께 기록해 두어야 원인을 빨리 찾을 수 있습니다. 결국 설정 변경은 값의 기록, 작은 범위의 시험 적용, 원래 값으로의 복귀라는 세 단계를 묶어 하나의 절차로 운영하는 것이 안전합니다.

마이그레이션도 같은 방식으로, 먼저 EFS 파일 시스템과 탑재 대상을 만들고 보안 그룹과 접근 권한을 열어 둔 뒤, 복사 도구로 데이터를 옮기면서 변경분을 따라잡는 기간을 둡니다. 이 기간에는 응용 프로그램이 예전 저장소를 계속 쓰게 하고, 마지막에 읽기 전용으로 잠깐 멈춘 사이 남은 차이를 복사한 다음 경로를 EFS로 바꿉니다. 옮긴 뒤에는 파일 개수와 용량, 소유자와 권한이 원본과 같은지 대조하고, 문제가 있으면 예전 경로로 되돌릴 수 있게 원본을 한동안 지우지 않습니다. 정리하면 EFS 마이그레이션은 새 파일 시스템 준비, 이중 운영 기간을 둔 데이터 복사, 경로 전환과 검증, 원본 보존 순서로 진행하는 것이 핵심입니다.

이전 작업도 마찬가지로, 옮겨 갈 대상 스토리지의 용량과 접근 방식, 성능이 지금 쓰는 패턴을 감당하는지 먼저 확인하고 준비합니다. 그다음 복사 도구로 데이터를 옮기고, 응용 프로그램의 마운트 경로를 새 저장소로 바꾼 뒤 정상 동작을 확인하며, 이 확인이 끝날 때까지 EFS는 그대로 둡니다. 마지막으로 남은 접속이 없는지 살펴 탑재 대상과 파일 시스템을 정리하고, 백업 보존 기간이 끝난 뒤에야 완전히 삭제합니다. 결국 EFS 이전은 새 저장소 검증, 데이터 복사, 경로 전환과 동작 확인, 자원 정리라는 네 단계를 지키는 것이 핵심이며, 특히 삭제는 가장 마지막에 해야 합니다.

EFS 운영 자동화

IaC와 스크립트로 반복 작업을 줄인다

파일 시스템을 손으로 만들고 권한을 하나씩 맞추다 보면, 담당자가 바뀌는 순간 무엇을 어떤 값으로 만들었는지 알 수 없어 같은 작업을 처음부터 다시 하게 됩니다. Amazon EFS(Elastic File System) 운영 자동화는 이런 반복 작업을 사람 손에서 떼어내는 일입니다. 프랜차이즈 매장을 생각해 보십시오. 본사가 매뉴얼에 매장 크기와 진열 규칙을 적어 두면, 새 매장이 열릴 때마다 같은 기준으로 자동 세팅되고 점검도 같은 항목으로 이뤄집니다.

운영 자동화에서 이 매뉴얼에 해당하는 것이 코드로 선언한 인프라(IaC, Infrastructure as Code)이며, 파일 시스템과 탑재 대상, 보안 그룹, 접근점(access point)의 설정을 코드에 적어 두고 같은 코드로 몇 번이든 같은 결과를 만듭니다. 여기에 정기 점검 스크립트를 붙여 용량과 처리량 지표를 주기적으로 확인하고, 백업 생성과 오래된 복구 지점 정리 같은 작업을 예약해 두면 사람이 잊어도 규칙대로 돌아갑니다.

다만 자동화 코드도 변경 이력과 검토 절차를 함께 두어야 예상하지 못한 값이 한꺼번에 퍼지는 일을 막을 수 있습니다. 정리하면 EFS 운영 자동화는 인프라를 코드로 선언해 같은 결과를 반복해서 얻고, 점검과 정리 작업을 예약 실행으로 돌려 사람의 기억에 의존하지 않게 만드는 것입니다.

EFS 실무 설계 종합

배운 내용을 하나의 아키텍처로 묶어 본다

파일 저장소를 급하게 하나 붙여 두고 서비스를 키우다 보면, 어느새 성능은 부족하고 비용은 예상보다 크며 장애가 나면 어디서부터 손대야 할지 모르는 상태가 됩니다. Amazon EFS(Elastic File System) 실무 설계는 그동안 배운 선택지를 하나의 그림으로 묶어 이런 상태를 미리 피하는 일입니다. 아파트 단지를 처음 설계할 때를 떠올려 보십시오. 설계자는 몇 세대가 살지, 차가 몇 대 들어올지, 정전에 대비해 발전기를 어디에 둘지를 함께 정하고 도면 한 장에 담습니다.

EFS 설계도 같아서, 어떤 가용 영역에 탑재 대상을 둘지, 처리량 모드를 어떤 기준으로 고를지, 어떤 디렉터리를 누구에게 열어 줄지, 백업과 복구를 어떤 주기로 돌릴지를 한 문서에 나란히 적습니다. 여기에 비용을 좌우하는 저장 용량과 수명 주기 정책, 장애 때 다른 가용 영역으로 넘어가는 경로, 인프라를 코드로 관리하는 방식까지 붙여야 실제 운영에서 흔들리지 않습니다.

그리고 이 도면은 한 번 쓰고 끝나는 것이 아니라, 사용량과 지표를 보며 주기적으로 다시 그려야 합니다. 결국 좋은 EFS 설계는 가용 영역 배치, 성능 모드, 접근 권한, 백업, 비용, 자동화를 따로 고르지 않고 하나의 아키텍처로 함께 맞추는 것이며, 그 그림을 운영하면서 계속 갱신하는 태도가 완성도를 만듭니다.
