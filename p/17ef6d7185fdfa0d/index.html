1. Bedrock 의 뼈대 — 모델을 부를 자리01-01

Amazon Bedrock 란 무엇인가

AWS 계정에서 여러 회사와 자체 모델을 한 곳에서 빌려 쓸 수 있게 해 주는 관리형 서비스로, 모델을 직접 구동하는 서버를 스스로 만들지 않아도 됩니다.

#1문제 상황

생성형 AI 모델을 쓰려면 직접 서버를 사서 모델을 올리고GPU를 붙여 관리해야 한다. 회사마다 모델 사마다 따로 통합해야 한다.

Amazon Bedrock 는 그런 모델을 AWS 계정 안에서 빌려 쓰게 해 주는 서비스다. foundation model, 즉 많은 데이터를 학습해 여러 용도에 쓰이는 대형 AI 모델을 여러 회사와 함께 제공한다. fully managed, 즉 운영을 AWS 가 맡는 방식이라 서버를 스스로 세우지 않는다. 모델을 부르는 일은 API 요청 한 번이면 된다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 모델을 고른다Bedrock 콘솔의 모델 목록에서 필요한 foundation model을 선택한다. 한 계정 안에서 여러 회사의 모델이 함께 놓여 있어 같은 방식으로 비교한다.
  2. 요청을 보낸다선택한 모델의 API 주소로 프롬프트를 담아 보낸다. 응답에는 모델이 만든 답이 돌아온다. 완전 관리 방식이라 서버 준비와 확장을 직접 하지 않는다.

#4동작 과정

  1. 엔드포인트를 고른다bedrock-runtime 과 bedrock-mantle, 두 추론 엔드포인트가 있다. bedrock-runtime 은 리전별로 붙은 기본 주소이고 bedrock-mantle 은 서버 측 도구나 백그라운드 추론처럼 일부 기능만 있는 주소다.
  2. API 를 배운다선택한 엔드포인트가 어떤 APIs 를 지원하는지 표에서 확인한다. InvokeModel, Converse, Chat Completions, Responses, Messages 가 여기에 해당한다.
  3. 가용성을 확인한다Endpoint availability 로 모델별로 어느 엔드포인트를 지원하는지 본다. 격리와 비용 추적이 필요하면 inference profiles 를 함께 쓴다.
  4. 확인해 볼 것호출한 모델의 상세에서 선택한 엔드포인트가 지원 목록에 있는지 확인한다.

Invoke API는 가장 단순한 형태다. 요청 본문에 modelId와 prompt를 넣고, 한 번 호출해서 완성된 텍스트 하나를 받는다. 응답이 길면 요금이 아니라 잘린 응답이 돌아올 수 있으니 maxTokenToSample 같은 상한을 함께 둔다.

#2핵심 질문

프롬프트를 그대로 넘겨서 모델의 답 하나를 받는 가장 기본 호출은 어떻게 만드는가?

#3동작 예시

#4동작 과정

  1. 요청을 담는다호출할 모델을 modelId로 지정하고, 지시 문장을 prompt 필드에 넣는다. 모델이 각 벤더 형식으로 만든 요청 본문을 그대로 쓰기 때문에 모델마다 필드 이름이 다르다.
  2. 보낸다요청 본문을 엔드포인트로 전송해 모델이 답을 생성한다. 스트리밍이 필요하면 같은 방식의 응답 스트림 연산을 쓴다(→ 02-05에서 다룰 생성 조절 값).
  3. 읽어 쓴다응답 본문에서 생성된 텍스트를 꺼내 애플리케이션 화면이나 다음 처리로 넘긴다.
  4. 확인해 볼 것콘솔의 모델 실험 화면에서 모델을 고르고 질문 한 개를 넣어 같은 형태의 답이 돌아오는지 본다.

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 대화를 쌓는다앞선 질문과 답변을 messages, 즉 역할과 내용으로 이루어진 목록으로 이어 붙여 보낸다. 여러 턴에 걸친 대화의 맥락이 이 목록에 남는다.
  2. 역할 지시를 준다system 블록에 페르소나나 톤 같은 지시를 따로 넣는다. 대화 내용과 분리되어 매 요청마다 유지된다.
  3. 응답을 받는다Converse 연산으로 답을 받고, 실시간으로 흘러보내려면 스트리밍 연산을 쓴다. 모델마다 다른 추론 파라미터가 있어도 같은 자리로 넘길 수 있다(→ 02-05).
  4. 확인해 볼 것같은 messages를 서로 다른 두 모델에 보내고 요청 본문이 바뀌지 않는지 확인한다.

추론 파라미터

추론 파라미터 는 최대 출력 토큰 수·온도·top-p 같은 생성 조절 값으로, 모델이 다음 단어를 고를 때 얼마나 자유롭게 답할지를 결정한다.

먼저 알아야 할 것 02-02

#1문제 상황

같은 프롬프트를 넣어도 모델이 매번 다른 문장을 돌려주면 서비스 입장에서 결과가 들쭉날쭉하다. 답을 짧게 자르고 싶은데 모델은 계속 이어 쓰기도 한다.

추론 파라미터(inference parameters)는 이런 흔들림을 조절하는 값이다. 생성 길이와 자유도를 정해 두고 결과를 예측 가능하게 만든다.

#2핵심 질문

모델이 답을 고를 때의 자유도와 길이를 어디까지 좁힐 수 있는가?

#3동작 예시

요약 요청에 maxTokens를 낮춰 두면 긴 설명이 잘려 짧은 요약만 돌아온다. temperature를 낮추면 매번 비슷한 문장을 고르고, 높이면 표현이 달라진다.

#4동작 과정

  1. 분포를 좁힌다temperature를 낮춰 다음 토큰 후보의 분포를 좁힌다. 값이 낮을수록 답이 일관되고, 높을수록 다양해진다.
  2. 분포를 자른다topP는 확률이 높은 후보 몇 개만 남겨 뒤에 그린다. tailSampling은 정해진 값만 잘라 낸다.
  3. 길이를 막는다maxTokens는 생성할 토큰 수 상한이고, stopSequences는 지정한 문자열이 나오면 생성을 멈추게 한다. 이들은 주제와 길이 조절에 쓰인다.
  4. 확인해 볼 것같은 프롬프트를 temperature만 다르게 주고 몇 번씩 다시 호출해 문장이 얼마나 달라지는지 본다.

구조화된 출력과 사고 확장

구조화된 출력은 모델이 정해진 JSON 스키마에 맞춰 답을 내도록 강제하는 기능이고, 사고 확장은 모델이 답하기 전에 중간 추론 단계를 거치게 해 더 어려운 문제의 정답률을 높이는 기능이다.

#1문제 상황

모델에게 JSON으로 답해 달라고 지시만 해서는 스키마를 어긋난 출력이 종종 나온다(→ 02-05). 이를 파싱하다 에러가 나면 다시 시켜야 해서 번거롭다. 어려운 문제에서는 짧게 답하라고 재촉하면 오답이 늘어난다.

구조화된 출력(Structured Outputs)과 사고 확장으로 이 두 가지를 각각 해결한다.

#2핵심 질문

모델이 스키마에 맞는 답만 내게 하고, 어려운 문제에서는 더 깊게 생각하게 할 수 있는가?

#3동작 예시

주문 항목마다 이름·수량·가격을 고르는 스키마를 넘긴다. 모델은 설명문 없이 그 키만 가진 JSON을 돌려주어 바로 파싱한다.

#4동작 과정

  1. 스키마를 건다JSON schema로 필드와 타입을 정해 모델이 그 틀 안에서만 답하게 한다. 파싱 실패와 재시도 루프가 사라진다.
  2. 요청 필드를 고른다InvokeModel API에서는 output_config.format, 오픈 웨이트 모델에서는 response_format, Converse 계열에서는 outputConfig 쪽 필드를 쓴다.
  3. 사고를 펼친다extended thinking을 켜면 모델이 답을 내기 전에 중간 추론 단계를 거쳐 더 어려운 문제의 정답률을 높인다(→ 02-05의 생성 조절 값과 함께 쓴다).
  4. 확인해 볼 것같은 스키마 요청을 여러 번 보내 응답이 항상 정해진 키를 갖는지 확인한다.

Tool use는 모델이 직접 함수를 부르는 방식이다. 모델은 이름과 인자만 골라 보내고, 실행은 우리 코드가 맡는다.

#2핵심 질문

모델이 스스로 필요한 도구를 골라 우리 코드의 함수를 부르게 할 수 있는가?

#3동작 예시

사용자가 인기 곡을 묻는다. 모델은 곡 정보를 조회하는 도구가 필요하다고 판단해 그 함수의 이름과 라디오 이름 인자를 담아 요청으로 돌려준다. 우리 코드가 그 함수를 실행해 곡 제목을 되돌려주면 모델이 그 결과로 최종 답을 쓴다.

#4동작 과정

  1. 도구를 정의한다호출 가능한 함수의 이름·설명·인자 구조를 toolConfig로 함께 보낸다. 모델은 이 목록만 보고 무엇을 쓸지 고른다.
  2. 요청을 해석한다모델이 도구가 필요하다고 판단해 toolUse 블록으로 호출 이름과 인자를 돌려준다. function calling은 다른 진영에서 쓰는 이 방식의 호칭이다.
  3. 실행하고 돌려준다우리 애플리케이션이 그 함수를 실행해 결과를 toolResult로 붙여 다시 보낸다. 이 교환이 한 번에 몇 차례 반복될 수 있다.
  4. 확인해 볼 것도구 목록을 넘긴 채 질문했을 때 콘솔 응답에 toolUse 블록이 나타나는지 본다.

클라이언트 측과 서버 측 도구 사용

클라이언트 측 도구 사용은 Bedrock 이 도구 호출 요청을 우리 애플리케이션에 돌려주어 우리가 도구를 실행하고 결과를 되돌리는 방식이고, 서버 측 방식은 Bedrock 이 관리하는 샌드박스에서 도구를 직접 실행해 우리 코드가 개입하지 않는 방식이다.

먼저 알아야 할 것 03-01

→ 03-01 참조

#1문제 상황

Tool use(→ 03-01)에서는 도구 호출 요청을 받은 뒤 누가 실행할지 정해야 한다. 요청을 받은 애플리케이션이 직접 실행하면 도구 구현과 보안 제어를 우리가 다 맡는다.

Bedrock은 이 실행 주체를 기준으로 클라이언트 측과 서버 측 두 방식을 지원한다.

#2핵심 질문

#3동작 예시

가상 라디오의 인기 곡 조회를 클라이언트 측으로 처리한다. Bedrock이 호출 요청을 우리 애플리케이션에 돌려주자 우리가 데이터베이스를 조회해 곡 제목을 toolResult로 되돌린다. 서버 측이면 Bedrock이 관리하는 샌드박스가 같은 조회를 대신 수행한다.

#4동작 과정

  1. 방식을 고른다Client-side는 우리가 도구를 실행하고 Server-side는 Bedrock이 실행한다. 도구 구현을 우리 코드에 둘지 Bedrock에 맡길지 정한다.
  2. 호출을 받는다서버 측에서는 Bedrock이 샌드박스에서 직접 실행해 호출 순서와 결과를 정리한다. 이때 도구가 다시 모델을 불러 서로를 부르는 순환 의존(circular dependency)은 피해야 한다.
  3. 결과를 반영한다어느 방식이든 실행 결과가 모델로 돌아와 원래 질문에 대한 최종 답이 만들어진다.
  4. 확인해 볼 것같은 도구 정의로 두 방식을 각각 호출해 실행 주체와 응답 경로가 어떻게 다른지 비교한다.

#2핵심 질문

기대하는 답의 모양을 예시로 가르쳐서 모델이 형식을 스스로 지키게 할 수 있을까?

#3동작 예시

결제 문의 답변을 300건 적어 질문과 정답을 묶는다. 이 training data 로 fine-tuning job 을 넣는다.

학습이 끝난 모델은 같은 질문에도 첨부 안내와 문장 길이를 맞춰 답한다.

#4동작 과정

  1. 예시를 모은다입력이랑 기대 출력을 한 쌍씩 training data 로 모은다. 데이터 양과 형식은 대상 모델이 요구하는 조건을 따른다.
  2. 학습 작업을 낸다Submit a model fine-tuning job 으로 학습을 요청한다. 학습이 끝나면 전용 모델 이름으로 등록된다.
  3. 확인해 볼 것콘솔에서 fine-tuning job 상태가 완료로 바뀌고 새 모델 이름이 생겼는지 확인한다.

→ 04-02 참조

#1문제 상황

fine-tuning 을 걸어도 결과가 들쭉날쭉하다. 대개 학습에 넣은 예시의 형식과 분량이 맞지 않아서 그렇다(→ 04-02).

Prepare data for fine-tuning 은 그 데이터를 규격에 맞게 정리하는 단계다. hyperparameters 를 정하는 일까지 이 단계에서 다룬다.

#2핵심 질문

학습이 잘 먹히는 데이터를 어떤 형식과 분량으로 준비해야 하는가?

#3동작 예시

고객 문의 예문을 단일 질문에 단일 답 형식으로 다시 정리하고, 그중 2할을 validation 용으로 따로 뺀다.

training 과 validation 데이터를 둘 다 올려 작업은 시작된다.

#4동작 과정

  1. 형식에 맞춘다파일과 레코드 구조를 선택한 학습 방법과 모델의 요구에 맞춘다. 입력과 출력의 종류(모달리티)에 따라 필요한 형식이 달라진다.
  2. 검증을 남긴다training 과 validation 데이터를 나누고 각자의 분량 상한을 맞춘다. validation 을 지원하지 않는 방법도 있다.
  3. 학습 세기를 정한다epochs 는 전체 데이터를 몇 번 돌릴지 정하는 값이다. 학습률은 한 번의 학습에서 params 를 얼마나 바꿀지 정하는 값이다.
  4. 확인해 볼 것준비한 데이터 세트에서 training 과 validation 의 레코드 수를 따로 센다.

4단계 4. 모델을 내 것으로 만든다

정답 예시 대신 '좋은 답을 주면 보상(점수)'이라는 규칙만 주고 모델이 스스로 여러 답을 시도해 보며 점수가 좋은 쪽으로 자신의 행동을 다듬게 하는 학습 방법이다.

먼저 알아야 할 것 04-01

#1문제 상황

사람이 매번 좋은 답과 나쁜 답을 골라 정답을 붙여 주면 비용이 크고, 정답을 다 못 적는 일도 많다.

Reinforcement fine-tuning 은 정답 목록 대신 좋은 답을 주면 보상(점수)을 받는 규칙을 쓴다. 이 규칙은 reward functions 로 구현하고, 여러 답을 시도한 뒤 점수가 좋은 쪽을 남긴다.

#2핵심 질문

정답을 전부 적지 않고도 모델의 답 품질을 높이려면 어떻게 해야 하는가?

#3동작 예시

답의 길이와 금지어를 검사해 점수를 매기는 규칙을 만든다. 이 reward functions 로 RFT 작업을 낸다.

여러 번 시도한 뒤 높은 점수를 받은 답의 방식이 모델에 남는다. preference data 는 이런 비교 판단을 맡는다.

#4동작 과정

  1. 규칙을 정한다응답 품질을 매질 수 있는 명확한 성공 기준을 정해 보상 규칙으로 만든다. 기준이 모호하면 학습 결과도 갈팡이한다.
  2. 보상으로 최적화한다정답 쌍이 아니라 보상 신호를 반복으로 돌려 model's own answer 가 높은 점수를 얻도록 다듬는다.
  3. 확인해 볼 것콘솔에서 RFT 작업이 정상 완료되고 결과 모델이 등록됐는지 확인한다.

#5한 줄 요약

Reinforcement fine-tuning정답 대신 보상 점수를 반복해 주어 모델 스스로 좋은 답을 찾게 하는 것

Distillation — 큰 모델의 답으로 작은 모델을

크고 비싼 모델이 실제로 낸 답(추론 과정까지 붙은 것)을 학습 데이터로 삼아, 싸고 빠른 작은 모델이 그 답을 내도록 흉내 내게 만드는 학습 방법이다.

먼저 알아야 할 것 04-01

#1문제 상황

큰 모델은 정확하지만 느리고 비싸서 모든 요청에 쓰기 어렵다. Distillation 은 큰 모델이 실제로 낸 답(합성 데이터)을 학습 재료로 삼아, 같은 일을 더 싸고 빠르게 하는 모델을 만드는 학습 방법이다.

#2핵심 질문

비용이 크고 느린 큰 모델의 성능을 작은 모델에도 옮겨 담을 수 있을까?

#3동작 예시

고객 문의 답변 모델을 만들려고 한다. 대형 모델로 수천 건의 질문마다 답을 생성하고, 그 질문·답 쌍으로 소형 모델을 학습시킨 뒤 소형 모델만 운영 환경에 올린다.

#4동작 과정

  1. 모델을 고른다답을 만들어 줄 teacher model 과 그 답을 배워 쓸 student model 을 지정한다. 두 모델이 Distillation 을 함께 정한다.
  2. 데이터를 준비한다질문 목록을 .jsonl 파일로 만든다. 이것이 distillation job 의 입력이 되고 Bedrock 이 teacher model 로부터 응답을 생성한다.
  3. 답을 합성한다teacher model 응답이 합성 데이터(synthetic data)가 되어 student model 을 fine-tune 한다. 입력을 쓸 목적에 맞게 다듬고, 같은 설정은 clone a distillation job 로 복제해 다시 시작한다.
  4. 확인해 볼 것콘솔의 distillation job 목록에서 만든 job 의 상태와 사용된 teacher·student 모델 이름이 보이는지 확인한다.

#5한 줄 요약

Distillation큰 모델이 실제로 낸 답을 학습 데이터로 삼아 작은 모델이 그 수준을 따라 하도록 만드는 것

내 모델을 Bedrock 에 등록해 다른 커스텀 모델과 같은 방식으로 관리하려면 어떻게 하나?

  4. 확인해 볼 것커스텀 모델 목록에 등록된 모델의 이름과 상태가 보이는지 확인한다.

Guardrails 의 뼈대와 safeguard 계층

Guardrails 는 Bedrock 모델의 요청과 응답 사이에 사용자가 정한 차단 규칙을 끼워 넣어, 그 규칙에 걸리는 내용만 걸러 내고 나머지는 그대로 통과시키는 출구 검사 장치다.

먼저 알아야 할 것 03-03

#1문제 상황

챗봇이 해롭거나 개인정보를 포함한 말을 그대로 통과시키면 그대로 사용자에게 보인다. Bedrock Guardrails 는 여러 기반 모델에 같은 방식으로 동작하는 일관된 검사 계층을 둬서 사용자 입력과 모델 응답에서 원하지 않는 내용과 민감 정보를 잡아 낸다. safeguard tiers는 이 안에서 각각 따로 검사하는 안전장치 계층이다.

#2핵심 질문

모델이 주고받는 내용에서 해롭고 민감한 부분을 어떻게 걸러 낼까?

#3동작 예시

은행 앱의 AI 상담에 가드레일을 붙인다. 사용자가 투자 추천을 물으면 모델이 답을 만들기 전에 그 질문이 걸리고, 응답에는 민감한 식별 정보가 가려진 채로만 남는다.

#4동작 과정

  1. 만든다guardrail 하나를 만들고 그 안에 여러 safeguard tiers를 둔다. topic policy 같은 정책으로 어떤 주제를 막을지 정한다.
  2. 끼워 넣는다요청과 응답 사이에 가드레일을 세워 모든 요청이 이 검사를 지나가게 한다. 모델 종류가 달라도 같은 규칙이 적용된다.
  3. 사용처를 나눈다해로운 입력을 막는 챗봇, 불법 투자 조언을 거르는 은행 앱, 통화 요약에서 PII 를 가리는 콜센터처럼 용도마다 조합해 쓴다.
  4. 확인해 볼 것테스트 대화에서 차단된 메시지가 반환되는지, 대화에 붙인 guardrail 이름이 요청 설정에 보이는지 확인한다.

#5한 줄 요약

콘텐츠 필터와 금지 주제

콘텐츠 필터는 허기·혐오·폭력 등 유해한 범주별로 가중치를 정해 응답 안전도를 점수화하고, denied topics(금지 주제)는 미리 정해 둔 주제나 문맥을 아예 금지어로 등록해 걸리는 대화를 차단하는 방식이다.

먼저 알아야 할 것 05-01

#1문제 상황

가드레일(→ 05-01)이 있어도 어떤 대화가 위험한지는 모른다. 금지 주제와 유해 카테고리를 지정해야 어떤 응답을 막을지 정할 수 있다.

#2핵심 질문

가드레일이 어떤 대화 내용을 위험한 것으로 보고 막게 할까?

#3동작 예시

은행 AI 어시스턴트가 투자 조언을 하지 않게 하려고 금지 주제를 등록한다. 사용자가 암호화폐 관련 문의를 하면 프롬프트가 해당 주제로 판정되어 차단 메시지가 돌아온다.

#4동작 과정

  1. 필터를 정한다Configure content filters 에서 harmful content 범주별 강도를 정한다. 위반으로 보는 유해한 내용의 정도를 정한다.
  2. 주제를 쓴다Add denied topics 로 주제 이름과 200자 이내 정의를 넣는다. 정의를 통해 주제와 하위 주제를 판별한다.

contextual grounding check 는 모델의 답변이 제공된 참고문서(근거 자료)에 실제로 근거하는지를 문장과 문장 사이의 관계로 확인해, 문서를 보지 않고 지어냈지만 그럴듯한 답변을 걸러 내는 검사다.

먼저 알아야 할 것 05-03

#1문제 상황

단어와 PII(→ 05-03)는 형태만 본다. 문서를 안 읽고 그럴듯하게 지어낸 답변은 눈에 안 띄게 통과한다. contextual grounding check는 참고 문서에 실제로 서 있는지 따져 hallucination을 걸러 내는 검사다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 근거를 준다Add contextual grounding checks 를 켜고 참고 문서와 사용자 질문을 함께 넣는다. 요약·의역·질문 응답에 쓸 수 있다.
  2. 조각마다 본다검색된 문서를 조각 단위로 처리해 각 조각의 관련성을 본다. 하나라도 관련하면 전체 응답은 grounded 한 것으로 본다.
  3. 기준을 정한다grounded 판정을 내리는 threshold 를 조절해 통과 수준을 정한다.
  4. 확인해 볼 것스트리밍 응답에서 근거 없는 부분이 걸렸을 때 어떤 구간이 막히는지 확인한다.

#2핵심 질문

  3. 결과를 받는다위반 부분에 대해 구조화된 피드백을 돌려주므로 어디가 잘못됐는지 따로 볼 수 있다.

가드레일 버전과 계정 간 보호

가드레일 버전은 설정과 필터를 변하지 않는 번호로 붙여 조건부 필터를 안전하게 고치거나 되돌리고, 가드레일 적용(enforcement)은 계정·리전 단위로 어떤 가드레일을 반드시 통과시킬지 지정해 조직 밖으로 유출되지 않게 하는 통제다.

먼저 알아야 할 것 05-01

#1문제 상황

가드레일의 필터와 조건부 필터를 고치면 지금 동작하던 승인 흐름이 통째로 흔들린다(→ 05-01). 또 조직 안팎을 오가는 요청은 계정마다 서로 다른 가드레일을 거치게 되고 있어, 무엇이 어디로 빠지는지 추적하기 어렵다.

가드레일 버전은 그 설정에 변하지 않는 번호를 붙여 복구 지점을 남기고, Cross-account safeguards 는 계정과 리전 단위로 반드시 통과시킬 가드레일을 지정한다. Deploy a guardrail 은 그 지정된 가드레일을 실제 호출 경로에 붙이는 단계다. cross-Region inference 로 다른 리전에서 처리하는 요청에도 같은 가드레일을 적용할 수 있다.

#2핵심 질문

변경 중인 가드레일 때문에 서비스가 멈추지 않게 하면서 조직 밖으로 유출되지 않게 하려면?

#3동작 예시

새로운 금지 주제를 추가한 뒤 테스트가 깨진다. 운영 중인 차단 규칙을 되돌리고 새 버전을 다시 만든다.

이후 계정 단위에서 모든 요청이 지정된 가드레일을 지나도록 enforcement를 켜 두면, 다른 계정에서 온 요청도 같은 검사를 거친다.

#4동작 과정

  1. 버전을 만든다Working draft에서 Create version을 눌러 현재 설정을 고정한 번호를 붙인다. 같은 요청을 코드로 보내려면 CreateGuardrailVersion을 호출하고 가드레일 ID와 설명을 넘긴다.
  2. 버전 사이를 오간다조건부 필터를 고칠 때는 새 버전을 만들고, 문제가 생기면 기존 버전으로 되돌린다. 번호가 바뀌지 않아 이전 판정 기록과 비교할 수 있다.
  3. 보호를 건다계정·리전마다 통과해야 할 가드레일을 지정한다. 지정한 가드레일을 실제 요청에 붙이는 Deploy a guardrail 을 진행하고, 다른 리전에서 처리되는 요청에는 cross-Region inference 설정을 함께 확인한다.
  4. 확인해 볼 것가드레일 상세 화면의 Versions 목록에 새 버전이 목록에 올라와 있는지 확인한다.

고친 프롬프트를 검증한 뒤에만 실제 애플리케이션이 쓰게 할 수 있는가?

#3동작 예시

분류 지시를 손질한다. 프롬프트를 열어 편집 화면에서 문장을 고치고 저장한다.

Test a prompt로 시험 입력 몇 개를 넣어 응답을 본다. 괜찮은 버전만 남겨 애플리케이션이 참조하게 한다.

#4동작 과정

  1. 사본을 고친다Modify a prompt로 프롬프트 본문과 추론 설정을 바꾼 뒤 저장한다. 이름과 설명은 Overview 항목에서 따로 고칠 수 있고, API로는 UpdatePrompt 요청에 유지할 값과 바꿀 값을 함께 보낸다.
  2. 시험해 본다Test a prompt로 입력값을 넣어 모델 응답을 확인한다. 변수가 있는 지시라면 값만 바꿔 여러 경우를 같은 프롬프트로 시험할 수 있다.
  3. 버전으로 올린다검증된 프롬프트를 버전으로 남겨 Deploy to your application using versions 단계에서 애플리케이션이 참조하게 한다. 이때 프롬프트별로 시험이 끝난 상태인지 볼 수 있다.
  4. 확인해 볼 것프롬프트 상세 화면에 버전 목록이 쌓이고 최신 버전이 표시되는지 확인한다.

#1문제 상황

Simple optimization은 짧은 프롬프트 하나를 빠르게 다시 쓰는 쪽이고, Advanced Prompt Optimization은 최대 5개 모델에서 원본과 최적화 결과를 나란히 비교한다.

#4동작 과정

  1. 작업을 만든다Optimize and migrate prompts로 최적화 작업을 시작한다. 프롬프트 템플릿마다 변수 값으로 쓸 예시 입력을 함께 넣고, 기준이 되는 정답과 평가 지표를 준다.
  2. 고쳐 나간다Simple optimization은 짧은 프롬프트를 휴리스틱으로 빨리 다시 쓰고, Advanced Prompt Optimization은 여러 모델에서 원본과 optimized prompt를 함께 비교한다.
  3. 평가한다evaluation methods로 원본 대비 점수 차이를 확인한다. 모델을 바꾸면 현 모델을 기준으로 삼아 비교하고, 그대로 쓸 거면 같은 모델의 전후만 비교한다.
  4. 확인해 볼 것최적화 작업 상세에서 원본 프롬프트와 고친 프롬프트의 응답이 나란히 보이는지 확인한다.

#1문제 상황

모델은 요청마다 기억이 없다. 앞에서 나눈 맥락을 매번 다시 붙여 보내야 하고, 여러 단계를 거친 작업은 순서와 분기를 코드로 다 짜야 한다.

#2핵심 질문

#4동작 과정

  1. 세션으로 맥락을 잇는다Session management로 대화 기록을 session에 쌓아 두면 다음 호출에서 앞선 맥락을 이어서 쓴다. 모델은 매번 stateless라 맥락은 이 세션이 대신 들고 있다.
  2. 단계를 정의한다Flows의 시각적 빌더에서 프롬프트·조건·함수 단계를 노드로 잇는다. knowledge base나 AWS Lambda 같은 다른 AWS 서비스로 데이터를 넘길 수 있다.
  3. 불변 배포로 올린다시험해 본 흐름을 production에 몇 번의 클릭으로 배포한다. 배포된 흐름은 고칠 수 없는 상태로 굳어 시험한 것이 그대로 운영된다.
  4. 확인해 볼 것흐름 편집 화면에서 노드 순서와 조건 분기가 그래프로 보이는지 확인한다.

사람이 직접 본문을 읽고 점수를 매기는 평가와, 평가자로 삼은 다른 LLM이 같은 기준에 따라 점수를 매기는 평가 방식이 함께 쓰인다.

먼저 알아야 할 것 08-01

→ 08-01 참조

#1문제 상황

평가 데이터 세트로 돌린 지표는 사람이 없는 동안의 대푯값만 보여 준다(→ 08-01). 무엇이 틀렸는지 읽으려면 결국 사람이 원문을 하나씩 확인해야 한다.

LLM as a judge model evaluation jobs는 그 공란을 사람이 읽는 대신 평가용 모델이 대신 채점하게 하는 방식이다. LLM-as-judge 는 평가자로 삼은 모델이 같은 기준으로 점수를 매기는 것을 가리킨다.

#2핵심 질문

사람이 매번 붙지 않고도 모델의 답이 얼마나 나은지 점수로 재려면 어떻게 하지?

#3동작 예시

고객 문장 분류 모델을 평가한다. 생성 모델이 만든 답을 데이터 세트에 두고, 평가 모델이 정답성·완전성 같은 지표별로 점수를 매긴다.

Bedrock 콘솔의 Evaluations 페이지에서 점수 분포와 데이터 세트 앞부분 프롬프트들의 채점 이유가 보인다.

#4동작 과정

  1. 사람에게 맡긴다Human-based model evaluation jobs는 작업자를 붙여 데이터 세트의 각 답에 annotation을 직접 매기고 grading 기준에 따라 점수를 매긴다. 채점 기준은 작업자가 그대로 본다.
  2. 모델에게 맡긴다LLM as a judge model evaluation jobs는 생성 모델과 평가 모델 두 개를 쓴다. 평가 모델이 지표마다 채점 이유를 함께 적어 준다.
  3. 결과를 모은다완료된 점수와 설명은 콘솔 Evaluations 페이지에서 보고, 전체 리포트는 작업 만들 때 지정한 S3 버킷에서 받는다.
  4. 확인해 볼 것Evaluations 페이지의 지표 요약 카드에 점수별 응답 개수 분포가 보이는지 확인한다.

RAG 평가

검색해서 찾아온 문단을 근거로 모델이 답을 제대로 지켰는지를 보는 평가로, 검색 결과의 정확도와 답변의 근거 충실도를 따로 측정한다.

먼저 알아야 할 것 08-02

#1문제 상황

답변 품질이 낮으면 모델 문제인지 검색 문제인지 알 수 없다(→ 08-01). 둘을 한 점수로만 재면 무엇을 고칠지 정할 수 없다.

RAG evaluation jobs는 찾아온 문단과 만들어진 답을 함께 검사한다. 두 가지를 분리해 재는 것이 이 항목의 핵심이다.

#2핵심 질문

내 지식 베이스가 나쁜 건지 답을 만든 모델이 나쁜 건 어떻게 구분하지?

#3동작 예시

두 개의 지식 베이스를 같은 질문 세트로 평가한다. 리포트에 retrieval metrics와 groundedness가 나란히 나온다.

검색 점수가 낮은 쪽은 문서가 안 잡히는 knowledge base로, 높은 쪽은 답이 그 문단 밖으로 나간 것으로 읽힌다.

#4동작 과정

  1. 실행 종류를 고른다Retrieve only 는 찾아온 데이터만 보고, Retrieve and generate 는 찾은 데이터와 응답 생성 모델의 요약까지 함께 본다. 외부 RAG source 는 직접 가져온 inference response data 로 대신할 수 있다.
  2. 검색을 잰다retrieval metrics로 knowledge base가 관련 문단을 제대로 찾아왔는지 수치로 확인한다. 점수가 낮으면 청크·임베딩 설정부터 손본다.
  3. 답변을 잰다groundedness로 답이 찾아온 문단 안에 머물러 있는지 본다. 검색은 잘됐는데 이 점수가 낮으면 모델을 바꿀 차례다.
  4. 확인해 볼 것리포트에서 두 지표가 각각 항목으로 나뉘어 표시되는지 확인한다.

#5한 줄 요약

RAG 평가검색이 모은 문단과 모델이 쓴 답을 따로 재해 고칠 대상을 갈라내는 것

평가 리포트와 데이터 관리

먼저 알아야 할 것 08-02

→ 08-01 참조

#1문제 상황

평가로 숫자만 남고 왜 틀렸는지는 사라진다. 나중에 같은 실수를 되풀이하지 않으려면 지표별 점수와 그 점수가 붙은 실제 사례가 함께 남아야 한다.

Reports and metrics for model evaluation는 그 묶음을 표준으로 정해 둔 영역이다.

#2핵심 질문

평가 결과를 누가 다시 보고, 데이터 세트를 누가 관리하는가?

#3동작 예시

작업 상태가 Ready로 바뀐 뒤 Model evaluations 표에서 해당 작업을 연다. 지표별 점수와 채점 이유가 보인다.

전체 결과는 작업을 만들 때 지정한 S3 버킷에서 내려받는다.

#4동작 과정

  1. 리포트를 본다콘솔에서 지표 요약과 사례별 설명을 확인한다. metric aggregation으로 여러 실행 결과를 하나의 지표로 합칠 수 있다.
  2. 결과를 가져온다전체 리포트는 작업을 만들 때 지정한 S3 버킷에서 다운로드한다. 저장 방식은 Data management and encryption가 정한다.
  3. 데이터를 관리한다평가용 데이터 세트를 직접 올리고 고치고 지운다. 콘솔에서 데이터를 가져올 때 CORS requirements를 맞춰야 한다.
  4. 확인해 볼 것Model evaluations 표에서 상태가 Ready인 작업을 골라 지표 카드와 결과 파일이 함께 보이는지 확인한다.

서비스 계층 — 네 가지

요청이 몰릴 때 기다리는 정도와 비용·속도 사이의 타협을 정하는 네 가지 처리 방식(Standard·Priority·Flex·Reserved)으로, 같은 모델이라도 계층에 따라 응답 속도와 가격이 달라집니다.

먼저 알아야 할 것 02-05

#1문제 상황

기본 방식으로 모델을 부르면 사람이 많을 때 밀리고, 확충하려고 따로 사 두는 것도 어렵다. 응답 속도와 비용 가운데 하나를 포기해야 한다.

service tier로 이 타협을 골라 정한다. Reserved, Standard, Priority, and Flex tiers 네 가지가 있다.

#2핵심 질문

내 워크로드에서 기다리는 시간과 지불 비용을 어떤 조합으로 정할까?

#3동작 예시

결제 시스템처럼 멈추면 안 되는 앱은 Reserved tier로 처리량을 미리 확보한다. 밤에 몰리는 추천 질의는 Flex tier로 넘긴다.

요청이 예약량을 넘어 Reserved tier는 자동으로 Standard tier로 넘겨 멈추지 않게 한다.

#4동작 과정

  1. Guaranteed 자리가 필요하면Reserved tier는 분당 입력·출력 토큰 수를 미리 잡아 우선 처리 전원을 예약한다. 예약 기간은 1개월이나 3개월 단위다.
  2. 기본 처리는Standard tier는 예약 없이 쓰는 기본 계층이다. 미처리량과 가격이 낮은 계층으로 여유분을 흘려보낸다.
  3. 속도를 올리면Priority tier는 처리량에 상한을 두고 그 안에서 더 빠른 응답을 받는다. 상한은 필요한 만큼의 처리량만큼 키운다.
  4. 확인해 볼 것콘솔에서 호출 요청에 붙은 응답 헤더로 실제 처리된 계층 이름이 무엇인지 확인한다.

Provisioned Throughput — 미리 사 두다

사용하기 전에 시간당·시간당당 보장되는 처리량 단위(처리량 단위당 초당 토큰·요청 수)를 미리 구매해 두는 방식으로, 구매한 양만큼의 처리 속도를 계절이나 트래픽과 무관하게 확보할 수 있습니다.

먼저 알아야 할 것 09-01

#1문제 상황

트래픽이 몰리는 순간에는 기본 계층만으로 느려진다. 계층으로만 조정하면 어디까지 예약할지 정하기 어렵다(→ 09-01).

Provisioned Throughput은 필요한 만큼의 처리량을 미리 사 두는 방식이다.

#2핵심 질문

계절과 무관하게 일정한 처리 속도를 확보하려면 무엇을 사 두어야 하나?

#3동작 예시

일일 배치 시간에만 폭발하는 앱이 Model Units를 미리 구매해 둔다. 지정한 시간에 batch 트래픽을 몰아도 처리 속도가 떨어지지 않는다.

짧아도 되는 시간에 처리량을 높였다 낮추면 한 시간 단위 과금으로 합쳐진다.

#4동작 과정

  1. 고른다대상 모델을 정한다. 커스터마이징한 모델은 이 방식을 사 두어야 쓸 수 있다.
  2. 수량을 정한다Model Units 수를 고른다. MU는 한 분 동안 처리할 수 있는 입력 토큰 수와 생성할 수 있는 출력 토큰 수로 정해진 처리량 단위다.
  3. 얻는다구매한 양만큼의 model invocation이 보장된다. 한 시간 단위로 과금되고, 실제 요금은 모델과 MU 수에 따라 달라진다.
  4. 확인해 볼 것콘솔의 Provisioned Throughput 목록에서 구매한 모델과 Model Units 수가 어떻게 표시되는지 확인한다.

먼저 알아야 할 것 09-01

#1문제 상황

호출마다 모델 이름과 리전 조건을 직접 적어야 하면 코드가 늘어지고 조건이 바뀔 때 여러 곳을 고쳐야 한다. 사용량과 비용 기록도 어디에 붙는지 애매하다.

Inference profiles는 이 조건을 이름 하나로 묶는다.

#2핵심 질문

모델과 실행 조건이 바뀌어도 코드 한 곳만 고치려면 어떻게 부를까?

#3동작 예시

애플리케이션 inference profile 하나를 만들어 모든 요청이 그 ARN으로 가도록 한다. 실행마다 호출에 붙는 이름이 같아져 리전별 사용량과 비용이 한데 모인다.

리전 묶음과 추론 방식은 system-defined profile이 정해 둔 대로 쓰고, 호출할 때는 이름만 넘긴다.

#4동작 과정

  1. 이름을 정한다system-defined profile은 전역 접근과 리전 간 추론용 조건을 미리 정해 둔 것이다. application inference profile은 애플리케이션용으로 조건을 모아 담는다.
  2. 부른다inference profile ARN을 호출에 넣으면 Bedrock이 그 조건에 맞는 리전과 방식으로 요청을 보낸다.
  3. 지표를 본다CloudWatch logs로 invocation 로그를 남기면 이 이름 아래로 usage metrics가 모여 사용량을 볼 수 있다.
  4. 확인해 볼 것콘솔의 inference profile 목록에서 ARN과 묶인 리전·모델이 어떻게 보이는지 확인한다.

#1문제 상황

사용자가 가까운 리전에 모델이 없으면 요청이 거절되거나 먼 리전까지 기다려야 한다. 모델이 있는 리전에 미리 트래픽을 몰아주는 대신, 요청이 도착한 자리에서 처리할 곳을 정하게 했다.

Cross-Region inference가 그 정한다. 이때 요청을 보낼 수 있는 리전의 범위를 지정한 지리 영역(geo)에 따라 두 방식으로 나뉜다. Geographic cross-Region inference는 지정된 지리 영역 안의 리전만 고르고, Global cross-Region inference는 모든 상업 리전을 고를 수 있다.

#2핵심 질문

내 리전에 모델이 없을 때도 요청을 어디로 돌려 처리할지 어떻게 지정하지?

#3동작 예시

서울 리전에 없는 모델을 쓰기로 해 Geographic cross-Region inference 프로필을 부른다. 요청이 지정된 지리 영역 안의 상업 리전 하나가 골라 처리한다.

Global cross-Region inference를 쓰면 영역 제한 없이 어느 상업 리전이든 고를 수 있다.

#4동작 과정

  1. 영역을 정한다Geographic cross-Region inference는 지정한 지리 영역 안에서만 리전을 고르고, Global cross-Region inference는 모든 상업 리전에서 고른다.
  2. 지정한 곳으로 보낸다Cross-Region inference는 여러 AWS 리전에 걸친 compute로 요청을 나눠 처리한다. 어느 리전을 썼는지는 inference profile이 정해 준다(→ 09-03).
  3. 넘어갈 때를 대비한다한 리전이 응답하지 못하면 failover로 다른 리전이 이어받는다. 이 방식은 아직 Provisioned Throughput을 함께 쓰지 못한다(→ 09-02).
  4. 확인해 볼 것호출 응답에서 어느 리전이 요청을 처리했는지 표시되는지 확인한다.

#1문제 상황

요청이 한 건씩 들어오면 그때마다 모델을 깨워 답을 기다려야 하므로, 밤새 끝낼 백만 건은 비현실적이다. 응답을 기다리는 동안 돈만 나고 시간은 버린다.

Batch inference는 이렇게 들어오는 요청을 몰아서 한 번에 처리하는 방식이다. 답이 급하지 않은 일은 한 묶음으로 넘기고 나중에 결과를 한꺼번에 받는다.

#2핵심 질문

실시간으로 기다릴 수 없는 대량 작업을 어떻게 한 번에 처리할까?

#3동작 예시

운영팀이 지난달 고객 문의 5만 건을 분류하려고 문장을 JSONL 파일로 만들어 S3에 올린다. Batch inference 작업을 제출하고 job id를 받아 저장한다.

몇 시간 뒤 job 상태가 완료로 바뀌고, 같은 S3 버킷에 결과 파일이 나타난다. 팀은 그 파일을 내려받아 분류 결과로 쓴다.

#4동작 과정

  1. 입력을 정리한다Set up data 단계로 모델에 줄 요청을 InvokeModel 또는 Converse 형식의 JSONL 파일로 만들어 S3에 올린다. 각 줄은 독립 처리되므로 되물으며 주고받는 대화는 넣지 못한다.
  2. 작업을 제출한다batch job을 만들 때 모델과 입력·출력 버킷을 지정한다. 한 번의 요청으로 수만 건이 몰린 채로 처리된다.
  3. 결과를 가져온다View the results of a job 단계에서 완료된 batch job의 출력 파일을 S3에서 내려받는다. 도구 호출과 구조화된 출력은 이 방식에서 지원하지 않는다.
  4. 확인해 볼 것콘솔의 배치 추론 작업 목록에서 방금 제출한 job의 상태가 완료로 바뀌고 출력 버킷 경로가 보이는지 확인한다.

Prompt caching 과 할당량

이전에 보낸 긴 지시문 일부를 저장해 두었다가 다음 요청에서 다시 쓰지 않고 재사용하는 기능과, 이 재사용 가능 시간을 포함한 모델별 사용 한도의 총칭.

먼저 알아야 할 것 09-01

#1문제 상황

챗봇이 사용자가 올린 긴 문서를 매 질문마다 처음부터 다시 읽는다. 같은 내용을 반복 처리하므로 시간과 비용이 함께 늘어난다.

Prompt caching은 그 반복되는 앞부분을 저장해 두고 다시 쓰는 기능이다. 모델과 API에 따라 Implicit Prompt Caching과 Explicit Prompt Caching 두 방식이 있다.

#2핵심 질문

반복되는 긴 지시문을 매번 다시 읽지 않게 할 수 있나?

#3동작 예시

사내 규정집 200쪽을 붙여 받는 도움말 어시스턴트에서 첫 질문 뒤 같은 문서를 넣은 두 번째 질문이 들어온다.

두 번째 질문은 캐시된 앞부분을 재사용하므로 문서 처리 시간이 줄어든다. 화면에는 답이 같은 형식으로 나오고 뒤에는 캐시 적용 표시가 붙는다.

#4동작 과정

  1. 재사용할 앞부분을 정한다Implicit Prompt Caching은 Bedrock과 모델이 앞부분의 재사용 가능 여부를 알아서 판단한다. Explicit Prompt Caching은 요청 안에서 캐시 제어와 중단 지점을 직접 지정한다.
  2. 요청을 보낸다캐시가 걸린 지시문과 새 질문을 한 요청에 담아 보낸다. 모델은 저장된 앞부분을 다시 계산하지 않고 이어서 답을 만든다.
  3. 사용량을 확인한다Quotas는 모델별 사용 한도를 가리키며, 재사용 가능 시간 안에 몇 번 쓰였는지가 token counting으로 집계된다. 정확한 사전 계산은 CountTokens API로 할 수 있다.
  4. 확인해 볼 것호출 응답에 캐시된 토큰 수가 함께 표시되는지 콘솔의 모델 사용량 화면에서 본다.

#3동작 예시

  2. 자격과 리전을 준비한다호출에 필요한 권한을 확인하고, 데이터가 있는 리전과 처리 리전이 다르면 Cross Region support required 조건으로 지원 리역을 정한다.
  3. invocation을 건다하나 또는 여러 입력 파일을 묶어 invocation을 보내고 진행 상태를 확인한다. Bedrock Data Automation이 데이터를 구조화된 결과로 바꾸어 낸다.
  4. 확인해 볼 것작업 목록에서 invocation 상태가 완료로 바뀌고 출력 파일이 생성된 경로가 표시되는지 본다.

#1문제 상황

자동 추출을 켰는데 결과 모양이 문서마다 달라 downstream 코드를 따로 짜야 한다. 반대로 쓸모없는 항목까지 나오면 걸러 내는 것도 손이다.

이 항목은 그 사이를 정리한다. Standard output는 자료 종류마다 미리 정해진 기본 결과이고, Custom output and blueprints는 내가 정한 결과 모양을 따로 만드는 쪽이다. 여기서 blueprint는 입력 종류·뽑을 항목·출력 스키마(output schema)를 적은 처리 정의다.

#2핵심 질문

자동 추출 결과를 어떤 항목과 어떤 모양으로 받을지 어떻게 정할까?

#3동작 예시

개발자가 청구서에서 계정 번호와 청구월만 받고 싶어 blueprint를 만든다. 이 blueprint에 추출 옵션을 켠 project를 만들고 문서를 넣는다.

응답에는 요청한 두 항목이 담긴 output schema로 결과가 돌아온다. 표준 결과는 항목 유형마다 다른 옵션이 켜진 상태로 함께 온다.

#4동작 과정

  1. 기준을 정한다blueprint 없이 문서를 넣으면 그 파일 유형의 기본 표준 결과가 온다. blueprint나 project를 함께 쓰면 표준 결과와 나란히 사용자 정의 결과도 함께 돌아온다.
  2. project로 묶는다표준 출력 설정은 project에 저장되며, 자료 유형마다 표준 출력 설정을 하나씩 둔다. 일부 옵션은 project에서 켜고 끌 수 있다.
  3. 결과를 맞춘다output schema에 맞게 받으려면 blueprint에 뽑을 항목과 스키마를 적어 invocation을 건다. Standard output는 자료 유형마다 다른 기본·선택 옵션을 갖는다.
  4. 확인해 볼 것같은 자료에 project 안의 blueprint를 적용했을 때 응답에 표준 결과와 사용자 정의 결과가 함께 들어 있는지 본다.

#1문제 상황

#2핵심 질문

자동 추출 결과에 남아 있는 민감 정보를 어떻게 자동으로 감출 수 있나?

#4동작 과정

  1. 필터를 켠다PII 탐지는 Amazon Bedrock Guardrails의 Sensitive Information Filters를 쓴다. BDA 는 기본으로 꺼 두므로, 처리할 방식마다 overrideConfiguration으로 켜 준다.
  2. 문서를 넣는다Using the Bedrock Data Automation API로 invocation을 보내 추출과 마스킹을 한 번에 수행한다. 이 기능은 입력 자료나 blueprint는 고치지 않는다.
  3. 결과를 확인한다tagging inferences로 결과 항목에 표시를 남겨 두고, 마스킹된 JSON만 받아 사용한다. 마스킹 방식에 따라 값이 지워지거나 대체 표시자로 바뀐다.
  4. 확인해 볼 것결과 JSON에서 연락처 같은 personal 값이 가려진 표시자로 바뀐 채 나오는지 직접 열어 본다.

IAM 과 서비스 역할

IAM(신원 및 접근 관리, AWS 리소스에 누가 무엇을 할 수 있는지 정하는 체계) 정책으로 Bedrock 접근 권한을 부여하고, Bedrock 이 사용자 대신 AWS 리소스를 조작하게 하는 서비스 역할(service role)을 설정하는 방법.

먼저 알아야 할 것 11-01

#1문제 상황

Bedrock 을 쓰는 팀이 여러 사람이면 누가 모델을 호출할 수 있는지를 정해야 한다. AWS 는 이 판단을 IAM 이 맡는다.

IAM policies 는 AWS Identity and Access Management(IAM)의 신원과 권한 관리 체계다. IAM administrators 는 sign 인을 허용하는 주체와 Bedrock 자원 사용 권한을 정한다. Bedrock 이 S3 같은 자소를 대신 다루게 하려면 service roles 를 함께 건다.

#2핵심 질문

누가 Bedrock 을 호출할 수 있게 하고 Bedrock 은 권한을 어디까지 갖게 할까?

#3동작 예시

콘솔에서 S3 버킷을 데이터 소스로 붙이려는데 권한 오류가 난다. IAM 관리자가 사용자에게 identity-based policies 를 붙여 InvokeModel 권한을 주고, Bedrock 이 버킷을 읽도록 service roles 를 설정한다.

#4동작 과정

  1. 권한을 부여한다identity-based policies, 즉 주체에 직접 붙이는 정책으로 어떤 API 호출을 허용할지 적는다. 허가된 주체만 Bedrock 요청이 통과된다.
  2. 역할을 맡긴다service roles 를 만들어 Bedrock 이 사용자 대신 AWS 자원에 접근하게 한다. 서비스가 관리하는 동작은 이 역할 권한만으로 수행된다.
  3. 예외를 점검한다Amazon S3 버킷 접근 설정처럼 별도로 풀어 주는 권한이 있는지 확인한다. 필요한 권한이 빠지면 데이터 소스 연결이 막힌다.
  4. 확인해 볼 것권한이 없는 사용자로 콘솔에 들어가 모델 호출이 막히는지 확인한다.

먼저 알아야 할 것 11-02

#1문제 상황

API keys 는 자격 증명을 대신하는 짧은 문자열 키다. Console 에서 바로 발급하고 필요한 때에 폐기(revoke)한다.

#2핵심 질문

AWS 자격 증명 없이 Bedrock 을 호출할 임시 키를 어떻게 발급하고 없애는가?

#3동작 예시

샘플 코드를 로컬에서 돌려 보려고 한다. Bedrock 콘솔의 API keys 화면에서 Short-term API keys 탭을 열어 키를 생성하고, 이 키를 인증 헤더에 넣어 모델을 한 번 호출한다.

#4동작 과정

  1. 키를 만든다Console 의 API keys 화면에서 short-term 또는 long-term 키를 생성한다. short-term 은 최대 12 시간 또는 세션 길이 중 짧은 쪽까지 쓰고 생성에 쓴 IAM 주체의 permissions 를 그대로 물려받는다. long-term 은 정해 둔 만료일까지 살아 있고 권한이 붙은 IAM user 를 새로 만든다.
  2. 호출에 붙인다API keys 는 authorization header 로 전달된다. 키 자체는 로그에 남지 않지만 그 키로 한 API 호출은 모두 AWS CloudTrail 에 기록된다.
  3. 폐기한다필요 없어진 키는 revoke 해서 더 이상 쓰지 못하게 한다. 권한은 키가 가진 permissions 를 기준으로 검사된다.
  4. 확인해 볼 것콘솔의 API keys 목록에서 발급 시각과 만료 시각이 보이는지 확인한다.

#4동작 과정

  1. 기능별로 본다knowledge bases logging 으로 CloudWatch Logs 에 남은 처리 기록을 보고, Guardrails 와 Agents 는 CloudWatch Metrics 로 리소스 단위 상태를 확인한다.
  2. 사건을 건다Amazon EventBridge 규칙으로 Monitor event changes, 즉 작업 상태 변화가 생길 때 알림이나 후속 처리를 붙인다.
  3. 확인해 볼 것EventBridge 규칙 목록에 방금 만든 규칙의 상태가 ACTIVE 로 보이는지 확인한다.

#5한 줄 요약

기능별 모니터링리소스 단위 동작을 CloudWatch 로 보고 상태 변화는 EventBridge 로 받는 것

11. 권한과 관측 — 누구 것이고 무엇을 썼나11-06

비용 추적

Bedrock 사용량이 누구의 것인지 IAM 주체·요청 메타데이터 같은 태그로 식별해 AWS Cost Explorer 에서 모델별·기능별 요금을 분석하고 비용을 관리하는 방법.

먼저 알아야 할 것 11-04

#1문제 상황

여러 팀이 하나의 AWS 계정에서 Bedrock 을 쓰면 한 달 청구서만 보고는 요금이 어디서 나왔는지 알 수 없다. 어느 모델과 어느 기능이 돈을 태우는지 모르면 개선할 대상도 모른다.

비용 추적은 Bedrock 사용량에 주체를 붙여 AWS Cost Explorer 에서 따로 보는 일이다. 추적 방식은 하나만 써도 되고 섞어 써도 된다.

#2핵심 질문

Bedrock 요금을 누가 어느 모델에서 냈는지 나눠서 볼 수 있는가?

#3동작 예시

팀별 진행 상황을 살핀다. IAM 주체별로 요금을 나눠 IAM principal attribution 으로 사용자별 사용량을 보고, 애플리케이션 단위는 프로젝트로 묶어 본다.

#4동작 과정

  1. 추적 방식을 고른다IAM principal attribution 은 사용자별로, 프로젝트는 애플리케이션별로, per-request metadata 는 Per-request metadata tagging, 즉 호출마다 붙는 메타데이터로 요청 단위 실험까지 나눠 본다.
  2. 데이터를 모은다이렇게 붙은 정보는 비용 사용량 데이터(CUR)로 쌓인다.
  3. 분석한다AWS Cost Explorer 에서 classic CUR 과 CUR 2.0 를 나눠 보고 모델별·기능별 요금을 비교한다.
  4. 확인해 볼 것Cost Explorer 에서 주체별로 나뉜 Bedrock 사용 항목이 보이는지 확인한다.

#5한 줄 요약

비용 추적사용량에 주체를 붙여 Bedrock 요금을 나눠 보는 것
