1기준 세우기: 시험이 요구하는 판단 틀뒤에 나오는 모든 설계 선택이 '어떤 기준으로 옳은가'를 정하는 층이다. 이것 없이 서비스를 먼저 외우면 시나리오 문제에서 고를 근거가 없다.52다계정 거버넌스와 아이덴티티 토대프로페셔널 시나리오는 거의 항상 여러 계정을 전제한다. 계정 경계와 권한 평가 규칙을 먼저 알아야 네트워크·보안·비용 설계가 어디에 놓이는지 이해된다.73네트워크 연결 설계계정 경계가 정해지면 그 사이에 트래픽을 어떻게 흘릴지가 다음 문제다. 컴퓨트·데이터 서비스는 모두 이 네트워크 위에 놓인다.94보안 통제와 데이터 보호네트워크 경로가 정해진 뒤에야 그 위에서 무엇을 암호화하고 무엇을 탐지할지가 구체화된다. 모든 후속 아키텍처에 공통으로 얹히는 층이다.65컴퓨트·컨테이너·서버리스 선택보호된 네트워크 위에 무엇을 올릴지 고르는 단계다. 여기서 정한 컴퓨트 모델이 뒤의 확장·배포·비용 선택을 모두 제약한다.66스토리지와 데이터베이스 선택컴퓨트가 정해져도 데이터를 어디에 두느냐가 가용성·성능·비용을 결정한다. 목적별 저장소 판단은 뒤의 DR·마이그레이션 설계의 전제다.77신뢰성, 복원력, 재해 복구대상과 저장소를 알아야 '무엇이 무엇과 함께 죽는가'를 따질 수 있다. 시험 배점이 가장 두터운 층이며 도메인 1·2·3에 걸쳐 반복된다.78배포 자동화와 운영 관측설계가 서면 그것을 반복 가능하게 올리고 지켜보는 층이 필요하다. 도메인 3의 '지속적 개선'은 전부 이 위에서 이뤄진다.59성능과 엣지 전달안정적으로 도는 시스템을 빠르게 만드는 층이다. 트래픽 분산과 캐싱은 앞의 컴퓨트·저장소 선택을 전제로 해야 판단이 선다.510비용 최적화성능과 가용성의 값을 매기는 층이다. 앞에서 고른 구성의 대안을 비용 축으로 다시 평가한다.511마이그레이션과 현대화앞의 모든 층을 목표 상태로 삼아, 기존 워크로드를 거기로 옮기는 순서다. 목표 아키텍처를 모르면 이전 전략을 고를 수 없으므로 마지막에 둔다.6

1상대의 출발점 확인

AWS Solutions Architect Associate 시험은 개별 AWS 서비스의 구성과 사용 방법을 중심으로 묻습니다. 예를 들어 "S3 버킷 정책을 어떻게 작성하는가", "RDS 데이터베이스를 만드는 단계는 무엇인가" 같은 식입니다. 하지만 이 접근은 서비스들을 따로따로 다루기 때문에 여러 서비스를 조합해서 실제 조직의 복잡한 문제를 푸는 능력을 평가할 수 없습니다.

2질문 제기

조직이 마주한 실제 상황 속에서 여러 제약 조건 사이의 트레이드오프를 판단하고 설계할 수 있는 능력을 어떻게 측정할까?

3구조적 핵심 예시

SAP-C02 시험 문제의 형태는 다음과 같습니다: "스타트업이 매달 사용량이 10배씩 증가하고 있습니다. 현재 데이터베이스는 온프레미스 Oracle이고 라이선스 비용이 급증 중입니다. 또한 규정상 데이터는 특정 지역에만 보관해야 합니다. 비용과 성능, 규정 준수 사이의 트레이드오프를 고려해 어떤 설계를 제안하시겠습니까?" 이처럼 문제는 하나의 기술만 다루는 것이 아니라 조직 상황, 제약, 우선순위가 섞여 있습니다.

4단계별 동작 과정

  1. 문제의 맥락 해석시험 문제는 조직의 규모, 업무 특성, 현재 기술 스택, 규정 요구사항을 제시합니다. 지원자는 이 모든 것을 읽고 핵심 병목과 우선순위를 파악해야 합니다.
  2. 4개 도메인별 판단 적용조직 복잡성 설계(다계정·거버넌스), 신규 솔루션 설계(새로운 워크로드), 기존 솔루션 개선(마이그레이션·최적화), 마이그레이션 및 현대화(레거시 전환)라는 4개 도메인이 문제 상황에 어떻게 적용되는지 판단합니다.
  3. 설계 제안과 근거기술 선택뿐 아니라 왜 그 선택을 하는지, 다른 선택지는 왜 안 되는지를 설명해야 합니다.

1상대의 출발점 확인

기존 온프레미스 인프라는 특정 위치에 고정되어 있습니다. 만약 물리 데이터센터가 있는 도시에서 대규모 정전이나 자연재해가 발생하면 서비스가 중단됩니다. 또는 먼 지역의 사용자는 높은 지연 시간(latency)으로 인해 느린 응답을 받습니다. 그리고 데이터를 다른 국가로 옮기려면 규정 때문에 불가능할 수도 있습니다.

2질문 제기

3구조적 핵심 예시

AWS는 전 세계를 30개 이상의 리전(지리적 영역)으로 나누고, 각 리전은 3개 이상의 가용 영역(물리적으로 분리된 데이터센터 클러스터)으로 나눕니다. 예를 들어 서울 리전(ap-northeast-2)에 배포하면 서울 근처 3개 물리 데이터센터에 자동으로 분산되고, 하나가 고장 나도 나머지에서 계속 서비스됩니다.

4단계별 동작 과정

  1. 리전 선택사용자가 주로 있는 지리적 위치, 규정상 데이터 주권(특정 국가에만 저장해야 함), AWS 서비스 제공 여부를 확인합니다. 일본에서만 서비스하는 회사는 도쿄 리전을 선택하고, EU 고객 데이터는 유럽 리전에만 저장해야 합니다.
  2. 가용 영역 분산하나의 리전 내에서 애플리케이션과 데이터베이스를 여러 가용 영역에 걸쳐 배포합니다. 이를 통해 한 데이터센터의 장애가 전체 서비스를 멈추지 않도록 합니다.
  3. 비용과 성능의 균형리전이 멀어질수록 지연 시간이 증가하고 데이터 전송 비용도 올라갑니다. 따라서 사용자 밀집도와 비용을 고려해 가장 가까운 리전을 선택합니다.

Well-Architected Framework는 6개 기둥으로 아키텍처를 평가합니다: 운영 우수성(모니터링·자동화·프로세스), 보안(접근 제어·암호화·감시), 안정성(장애 복구·성능 유지), 성능 효율성(적절한 리소스·확장), 비용 최적화(낭비 제거·예약 구매), 지속 가능성(에너지 효율·탄소 감소). 각 기둥은 설계 원칙과 확인 질문을 제공합니다.

4단계별 동작 과정

  1. 각 기둥별 현 상태 평가보안은 충분한가, 모니터링은 어느 정도인가, 비용은 최적화되었는가를 체크리스트로 확인합니다.
  2. 기둥 간 트레이드오프 식별예를 들어 보안을 강화하면(접근 제어 추가) 운영이 복잡해지고, 비용을 줄이려다가(저사양 인스턴스) 성능이 떨어집니다. 이 충돌을 명시적으로 인식합니다.
  3. 조직 목표 맞춤 우선순위 정하기스타트업은 성능 효율성과 비용을 먼저, 금융기관은 보안과 안정성을 먼저 고려합니다.

AWS는 클라우드 자체의 보안을, 고객은 클라우드 안의 설정과 데이터를 책임지며 각 서비스의 할당량과 SLA가 설계의 상한선을 정한다.

1상대의 출발점 확인

기존 온프레미스 환경에서는 조직이 모든 인프라의 보안, 가용성, 성능을 직접 책임집니다. 클라우드로 전환하면 AWS가 일부를 담당한다는 것은 알지만, "내가 뭘 해야 하는지" "AWS가 뭘 보장하는지" 경계가 불명확합니다. 또한 각 서비스가 몇 개까지만 만들 수 있는지, 언제까지 사용 가능한지도 명시되어야 설계 시 제약으로 반영할 수 있습니다.

2질문 제기

클라우드 환경에서 보안과 가용성을 달성하기 위해 나는 무엇을 책임져야 하고, AWS는 무엇을 보장하며, 서비스 사용에는 어떤 한계가 있을까?

3구조적 핵심 예시

공동 책임 모델은 이렇게 나뉩니다: AWS는 인프라 자체(물리 데이터센터, 네트워크, 하이퍼바이저)의 보안을 책임지고, 고객은 EC2 인스턴스 OS 패치, 보안 그룹 설정, 데이터 암호화, 접근 권한 관리를 책임집니다. 예를 들어 데이터베이스(RDS)의 경우 AWS는 백업과 패치를 하지만, 고객은 네트워크 접근 제어와 데이터 암호화를 설정해야 합니다.

4단계별 동작 과정

  1. 책임 범위 명확히 하기각 AWS 서비스마다 책임선이 다릅니다. 관리형 서비스(RDS, DynamoDB)는 AWS가 더 많이 하고, 자관리 서비스(EC2)는 고객이 더 많이 합니다. 설계 시 어느 것을 선택할지 책임 범위에 따라 결정합니다.
  2. 서비스 할당량 확인S3 버킷은 계정당 100개까지, Lambda 동시 실행은 기본 1,000개 등 각 서비스의 상한이 있습니다. 설계 시 예상 사용량이 이 한계를 초과하면 사전에 할당량 증가를 요청해야 합니다.
  3. SLA 목표와 아키텍처 연결EC2는 99.99% 가용성 SLA를 제공하지만, 이는 가용 영역 내에서만 해당됩니다. 99.999% 가용성을 원하면 여러 가용 영역에 배포해야 합니다.

1상대의 출발점 확인

고객은 보통 "시스템이 빨라야 한다", "안정적이어야 한다", "언제든 복구 가능해야 한다" 같은 정성적 요구를 제시합니다. 하지만 이렇게는 설계안을 비교할 수 없습니다. 예를 들어 "빠르다"는 1초인가 100밀리초인가? "안정적이다"는 한 달에 1분 다운타임을 허용하는가 아니면 일 년에 1분인가? 이것을 명확히 하지 않으면 설계안도 구현도 검증도 불가능합니다.

2질문 제기

고객의 모호한 요구사항을 어떻게 측정 가능한 숫자로 바꿔서 설계안을 검증할 수 있을까?

3구조적 핵심 예시

고객이 "데이터베이스 장애 시 1시간 안에 복구되어야 한다"고 말하면, 이를 RTO(Recovery Time Objective) 1시간이라고 기록합니다. "최대 15분치 데이터 손실까지 허용한다"고 하면 RPO(Recovery Point Objective) 15분입니다. "시스템 응답 시간이 200밀리초 이내"라고 하면 KPI(Key Performance Indicator)입니다. 이 숫자들로 설계를 검증할 수 있습니다.

4단계별 동작 과정

  1. 업무 영향도 분석어느 업무가 언제까지 중단되면 회사에 손실인지 파악합니다. 결제 시스템은 15분 다운타임도 심각하지만, 보고서 조회는 하루 정도는 버틸 수 있습니다.
  2. RTO/RPO 결정업무별로 얼마나 빨리 복구해야 하는지(RTO), 최대 몇 분 데이터까지 잃을 수 있는지(RPO)를 정합니다. 이 숫자는 곧 필요한 기술 수준을 결정합니다. RTO 15분이면 자동 장애조치가 필요하고, RPO 0은 실시간 동기 복제가 필요합니다.
  3. KPI로 성능 확인복구 목표만이 아니라 평시 성능도 정의합니다. 응답 시간, 처리량, 에러율 등을 측정해서 SLA를 달성하는지 확인합니다.

→ 02-04 참조

1상대의 출발점 확인

각 AWS 계정의 IAM(Identity and Access Management) 권한을 따로 관리하면, 팀마다 다르게 설정할 위험이 있습니다. 예를 들어 개발팀은 의도치 않게 모든 리소스 삭제 권한을 줄 수 있고, 한 팀의 실수가 다른 팀 리소스를 지울 수 있습니다. 또한 규정상 "이 작업은 절대 하면 안 된다"는 규칙을 각 계정마다 따로 설정하기는 비효율적입니다.

2질문 제기

3구조적 핵심 예시

서비스 제어 정책(SCP)은 JSON 형식의 권한 정책으로, Organizations의 OU나 계정에 붙입니다. 예를 들어 "DenyDisableCloudTrail" SCP는 "모든 CloudTrail 로깅 비활성화 액션을 거부한다"는 규칙입니다. 이 정책을 루트 OU에 붙이면 그 아래의 모든 계정에서는 CloudTrail을 끌 수 없습니다. 개별 IAM 권한이 "CloudTrail 비활성화 가능"이라도, SCP가 최상위에서 "금지"라고 하면 그 작업은 불가능합니다.

4단계별 동작 과정

  1. 위험 행위 식별조직이 절대 허용하지 않을 작업을 정의합니다. 보안 정책 삭제, CloudTrail 비활성화, VPC 삭제, 루트 계정 접근 허용 등입니다.
  2. SCP 작성각 위험 행위를 거부하는 SCP를 JSON으로 작성합니다. 이 정책들을 "가드레일(guardrails)"이라고 부릅니다.
  3. 조직 전체에 적용가드레일 SCP를 루트 OU에 붙여서 모든 계정이 자동으로 상속받게 합니다. 이제 어떤 팀이든, 어떤 IAM 사용자든 이 정책을 우회할 수 없습니다.

퍼블릭 서브넷의 웹 서버는 인터넷 게이트웨이(IGW, Internet Gateway)를 통해 직접 인터넷과 양방향 통신을 한다. 프라이빗 서브넷의 데이터베이스는 NAT 게이트웨이(Network Address Translation Gateway)를 거쳐 아웃바운드 통신만 한다. 외부에서 프라이빗 리소스로 직접 연결할 수 없고, 프라이빗 리소스가 외부 API를 호출할 때만 NAT를 통해 나간다.

4단계별 동작 과정

  1. 퍼블릭 서브넷 설정라우팅 테이블에서 기본 경로(0.0.0.0/0, 모든 대상)를 인터넷 게이트웨이로 보낸다. 이 서브넷의 리소스는 인터넷과 직접 양방향 통신할 수 있다.
  2. 프라이빗 서브넷 설정NAT 게이트웨이(퍼블릭 서브넷에 배치)를 거쳐 아웃바운드 트래픽을 보내도록 라우팅 테이블을 구성한다. 외부에서 프라이빗 리소스로 직접 연결은 불가능하다.
  3. 트래픽 흐름프라이빗 리소스의 패킷이 NAT를 통과하면서 송신자 IP가 NAT의 IP(퍼블릭 IP)로 위장되어 나간다. 응답 패킷도 NAT를 거쳐 원래 프라이빗 리소스로 돌아온다.

1상대의 출발점 확인

기존에는 인스턴스 앞에 방화벽 규칙을 두거나 서브넷 경계에만 필터를 적용했습니다. 하지만 이 방식은 각 계층의 역할이 불명확하고, 한 계층이 실패해도 백업이 없으며, 상태 추적과 정책 적용이 섞여 관리가 복잡했습니다.

3구조적 핵심 예시

보안 그룹(Security Group)은 인스턴스에 붙는 상태 저장 방화벽으로, 들어온 요청을 기억하고 응답은 자동으로 허용합니다. 네트워크 ACL(NACL)은 서브넷 경계에서 작동하는 무상태 필터로, 들어오는 패킷과 나가는 패킷을 독립적으로 검사합니다. 두 계층이 함께 작동하면 트래픽이 도착할 때 먼저 NACL에서 거르고, 통과한 트래픽이 보안 그룹을 거쳐 인스턴스에 도달합니다.

4단계별 동작 과정

  1. 서브넷 진입 검사트래픽이 서브넷 경계에 도착하면 NACL이 무상태 규칙(즉, 왕복 패킷을 각각 검사)을 적용해 허용/거부를 판단합니다.
  2. 인스턴스 진입 검사NACL을 통과한 트래픽이 인스턴스의 보안 그룹에 도착하면, 상태 저장 방식으로 요청을 기억했다가 응답을 자동 허용합니다.
  3. 계층화된 제어각 계층이 독립적으로 작동하므로 한 계층의 규칙 실수가 다른 계층의 방어를 무너뜨리지 못합니다.

2질문 제기

VPC 피어링이 다중 연결과 다중 라우팅에서 전이성을 지원하지 않는 까닭은?

3구조적 핵심 예시

A-B 피어링은 A에 B 경로를 추가하고 B에 A 경로를 추가할 뿐입니다. B-C 피어링은 또 별개의 경로 쌍입니다. A의 라우팅 테이블에는 "B 대상은 이 피어링으로" 규칙만 있고, "C는 B를 거쳐 가라"는 규칙이 없으므로 A에서 출발한 C 향 트래픽은 경로를 찾지 못합니다.

4단계별 동작 과정

  1. 1:1 피어링 설정각 VPC 쌍마다 독립된 피어링 연결과 라우팅 항목을 만들어 직접 경로만 보장합니다.
  2. 라우팅 테이블의 한계각 VPC의 라우팅 테이블에는 직접 연결된 피어링 대상만 기록되므로, 간접 경로를 자동으로 따를 수 없습니다.
  3. CIDR 충돌 문제피어링 대상이 다른 VPC와 CIDR이 겹치면 라우팅 결정이 모호해져 피어링 생성 자체가 실패합니다.

Route 53은 헬스체크로 각 엔드포인트의 가용성을 모니터링하고(예: HTTP 응답 확인), 라우팅 정책(가중치: 트래픽 비율 분산, 지리: 지역별 선택, 지연: 지연 최소화)에 따라 DNS 쿼리에 다른 IP를 반환합니다. 장애 대상이 감지되면 그 IP를 응답에서 제외합니다.

4단계별 동작 과정

  1. 헬스체크 설정Route 53이 정기적으로 각 엔드포인트의 상태(예: HTTP 200 응답, TCP 연결)를 확인합니다.
  2. 라우팅 정책 적용DNS 쿼리가 들어올 때 정책(가중치, 지리, 지연 등)과 현재 헬스체크 결과를 바탕으로 응답할 IP 또는 엔드포인트를 결정합니다.
  3. 하이브리드 DNS 연동Route 53과 온프레미스 DNS 서버를 리졸버(DNS 쿼리 중계자)로 연결하면 양쪽 도메인을 통합으로 해석할 수 있습니다.

1상대의 출발점 확인

S3에 데이터를 저장할 때 그냥 평문으로 저장하거나, 각 애플리케이션이 자기 암호화 키를 따로 관리해야 한다. 문제점은 키가 코드에 섞여 있으면 소스 코드 유출 시 키도 함께 노출되고, 키를 교체하려면 모든 데이터를 다시 암호화해야 하며, 어떤 키로 어떤 데이터를 암호화했는지 추적이 어렵다는 점이다.

2질문 제기

3구조적 핵심 예시

S3 버킷에 파일을 올릴 때, S3가 KMS(암호화 키 관리 서비스)에 "이 데이터를 암호화해 주세요"라고 요청하면 KMS가 암호화 키를 내려주고, S3가 그 키로 데이터를 암호화한 뒤 저장한다. 나중에 파일을 내려받을 때 S3가 다시 KMS에 "이 데이터를 해독해 주세요"라고 요청해서 원본 데이터를 돌려준다.

4단계별 동작 과정

  1. 키 생성 및 권한 설정KMS에서 마스터 키(암호화와 해독의 기초가 되는 키)를 만들고, IAM 정책으로 누가 이 키를 쓸 수 있는지 지정한다.
  2. 서비스 연동S3, EBS, RDS 등이 KMS 키를 지정해서 저장 데이터 암호화를 활성화하면 사용자가 데이터를 보낼 때 자동으로 암호화된다.
  3. 키 교체 및 감시KMS가 연 1회 자동으로 키 버전을 올려 새로운 키로 암호화하고, CloudTrail이 모든 키 접근(누가 언제 조회했는지)을 기록해 감사한다.

1상대의 출발점 확인

네트워크 경계에서 방어할 것이 없거나 각 애플리케이션이 자체 방화벽 규칙을 관리한다. SQL 주입, XSS(크로스 사이트 스크립팅) 같은 웹 공격이 그대로 애플리케이션에 도달하고, DDoS 공격으로 서비스가 다운되며, 각 팀이 규칙을 다르게 설정해 보안이 일관성이 없다.

2질문 제기

WAF(웹 애플리케이션 방화벽)가 CloudFront나 로드 밸런서 앞에 붙어서 모든 HTTP 요청을 검사한다. 요청에 "' OR '1'='1" 같은 SQL 주입 패턴이 들어 있거나 자바스크립트 코드가 의심되면 그 요청을 차단한다. 동시에 Shield가 갑자기 특정 IP에서 초당 수백만 개의 요청이 몰리는 DDoS 트래픽을 감지하고 자동으로 필터링한다. Network Firewall은 VPC 경계에 놓여 비허가 프로토콜, 포트, IP 주소를 차단하고, Firewall Manager가 모든 계정의 규칙을 중앙에서 관리한다.

4단계별 동작 과정

  2. DDoS 방어Shield가 대규모 트래픽 폭증을 실시간으로 감지하면 공격 트래픽을 자동으로 흡수하거나 폐기하고, 정상 사용자 요청은 통과시킨다.
  3. 네트워크 경계 통제 및 중앙 관리Network Firewall이 VPC 진입점에서 프로토콜, 포트, IP 기반 규칙을 적용하고, Firewall Manager가 조직 전체 계정의 규칙을 한곳에서 관리한다.

3구조적 핵심 예시

GuardDuty가 CloudTrail 로그를 읽으면서 평상시와 다른 API 호출 패턴(예: 새벽 3시에 평소보다 수백 배 많은 데이터 다운로드)을 감지하면 "침해 징후"로 보고한다. 동시에 Inspector가 EC2 인스턴스의 OS와 설치된 소프트웨어 버전을 스캔해 알려진 취약점을 찾고, Macie가 S3에 저장된 개인정보나 신용카드 번호 같은 민감 데이터를 자동으로 분류한다. Detective가 이 모든 신호를 모아서 "계정 B에서 비정상 로그인이 발생했고, 5분 뒤 S3 접근 패턴이 급증했다"는 식으로 연결해 원인 추적을 돕는다.

4단계별 동작 과정

  1. 로그 분석 및 침해 탐지GuardDuty가 CloudTrail, VPC Flow Logs(네트워크 통신 기록) 등을 자동 분석해 비정상 API 호출, 비정상 네트워크 접근, 악성 IP와의 통신을 실시간으로 감지한다.
  2. 자산 취약점 스캔Inspector가 EC2와 ECR(컨테이너 이미지 저장소)의 OS·라이브러리 취약점을 스캔하고, Macie가 S3에서 개인정보, 금융 데이터 같은 민감 패턴을 자동으로 찾는다.
  3. 조사 자동화 및 시각화Detective가 GuardDuty의 탐지 결과들을 연결 분석해 침해 경로와 영향 범위를 그래프로 시각화해 보안팀의 빠른 대응을 돕는다.

3구조적 핵심 예시

Config가 S3 버킷의 "버전 관리 활성화 여부", "기본 암호화 설정" 같은 설정을 실시간으로 감시한다. 규정 위반이 탐지되면 Config 규칙이 그 사실을 보고하고, SSM Automation(AWS의 작업 자동화 도구)이 자동으로 S3 버킷 암호화를 켜 준다. CloudTrail은 누가 언제 어떤 API를 호출했는지를 로그에 남기고, Security Hub가 모든 계정의 Config, GuardDuty, IAM Access Analyzer 결과를 한곳에 모아 규정 준수 현황을 대시보드로 보여준다.

4단계별 동작 과정

  1. 설정 감시 및 규정 평가Config가 EC2, S3, RDS 등 리소스의 현재 설정을 스냅샷으로 저장하고, 관리자가 지정한 규칙(예: "S3는 반드시 암호화를 켜야 한다")에 따라 준수 여부를 자동 평가한다.
  2. API 호출 기록CloudTrail이 모든 계정의 모든 AWS API 호출을 중앙 로그에 기록해 누가 뭘 언제 했는지 추적 가능하게 한다.
  3. 위반 교정 및 중앙 보고Config 규칙 위반이 탐지되면 SSM Automation으로 자동 수정을 실행하고, Security Hub가 조직 전체의 규정 준수 상태를 한눈에 보여준다.

1상대의 출발점 확인

EC2 인스턴스를 선택할 때 CPU와 메모리 규격만 본다. 네트워크 처리량이 많은 일을 할 때는 일반 인스턴스가 무거워지고, 다른 AWS 고객 계정의 인스턴스와 같은 물리 서버를 공유하면서 성능 간섭(한쪽이 많이 쓸 때 다른 쪽이 느려짐)을 당할 수 있으며, 클러스터 컴퓨팅이 필요해도 인스턴스들이 물리적으로 떨어져 있으면 네트워크 지연시간이 크다.

2질문 제기

워크로드 성격에 맞는 인스턴스 타입을 고르고, 물리 서버 격리 수준과 네트워크 위치까지 세밀하게 제어할 수 없을까?

3구조적 핵심 예시

고성능 과학 계산이 필요하면 c6i 인스턴스(연산 최적화)를 고르고, 대규모 메모리를 쓰는 데이터 분석이면 r6i(메모리 최적화), 머신러닝 추론이면 g4dn(GPU 가속기 포함)을 택한다. 테넌시는 기본 "공유"를 쓰지만, 규정상 다른 고객과 같은 서버를 쓸 수 없으면 "전용" 테넌시를 선택한다. 병렬 처리 작업으로 인스턴스 간 통신이 많다면 여러 인스턴스를 "클러스터" 배치 그룹에 넣어 같은 가용 영역의 같은 물리 서버 집합에 배치함으로써 지연시간을 1밀리초 이하로 낮춘다.

4단계별 동작 과정

  1. 인스턴스 패밀리 선택범용(t, m 계열), 연산 최적화(c 계열), 메모리 최적화(r, x 계열), GPU 가속기(p, g, h 계열) 등 워크로드에 맞는 계열을 고르고, 세대(6i, 6a 등)에 따라 최신 성능 개선을 반영한다.
  2. 테넌시·배치 그룹 결정공유 테넌시에서 다른 고객과 서버를 나누거나, 비용을 내고 전용 테넌시를 사용한다. 클러스터·분산·분할 배치 그룹으로 인스턴스 배치를 제어해 네트워크 지연시간, 장애 영향 범위, 비용을 맞춘다.
  3. 성능 검증선택한 타입, 테넌시, 배치에서 실제 워크로드를 돌려 지연시간·처리량·비용이 요구사항을 만족하는지 확인한다.

EC2 Auto Scaling과 AWS Auto Scaling 정책

수요 변화에 따라 인스턴스 수를 자동으로 늘리고 줄이는 기능으로, 목표 추적·단계·예약 같은 정책으로 확장 규칙을 정한다.

1상대의 출발점 확인

EC2 인스턴스 개수를 수동으로 관리하려면 개발자가 지속적으로 트래픽을 감시하다가 부하가 올라오면 인스턴스를 추가하고, 내려가면 제거해야 합니다. 이 방식의 문제는 대응 시간입니다. 트래픽이 급증할 때 인스턴스 추가를 늦게 하면 기존 서버가 과부하되어 성능이 떨어지고, 반대로 미리 너무 많은 인스턴스를 띄워두면 불필요한 비용이 발생합니다.

2질문 제기

트래픽 변화에 자동으로 대응해서 서버 성능은 유지하면서 불필요한 비용은 줄일 수 있을까요?

3구조적 핵심 예시

EC2 Auto Scaling Group을 만들 때 "CPU 사용률이 70% 이상이면 인스턴스 2개를 추가하고, 30% 이하로 떨어지면 2개를 제거"라는 규칙을 정하면, AWS가 정해진 메트릭을 자동으로 감시했다가 조건이 맞을 때 인스턴스를 즉시 추가하거나 제거합니다.

4단계별 동작 과정

  1. 메트릭 감시CloudWatch가 EC2의 CPU, 네트워크 사용률 같은 지표를 계속 수집합니다.
  2. 정책 확인정해진 정책(목표 추적, 단계별, 예약된 확장)에 따라 현재 메트릭이 임계값을 넘었는지 확인합니다.
  3. 인스턴스 조정조건이 맞으면 Auto Scaling Group의 원하는 용량을 변경해서 인스턴스를 추가하거나 제거합니다.

컨테이너를 실행·오케스트레이션하는 AWS 서비스들로, ECS/EKS는 스케줄러, Fargate는 서버 없는 실행 방식, ECR은 이미지 저장소 역할을 한다.

1상대의 출발점 확인

애플리케이션을 배포할 때 서버의 OS, 설치된 라이브러리, 환경 변수를 모두 맞춰야 합니다. 개발자 로컬 환경에서는 정상 작동하던 코드도 운영 서버의 환경이 조금 다르면 실패하곤 합니다. 이 문제를 해결하려면 매번 환경 설정 문서를 따라 수동으로 구성하거나, 배포 자동화 스크립트를 복잡하게 관리해야 합니다.

2질문 제기

어느 서버에서나 완전히 동일한 환경에서 애플리케이션을 실행할 수 있는 방법이 있을까요?

3구조적 핵심 예시

컨테이너는 애플리케이션 코드와 필요한 모든 라이브러리, 설정을 하나의 패키지로 묶어서, 어느 서버에 배포하든 그 패키지 내부의 동일한 환경에서 실행됩니다.

4단계별 동작 과정

  1. 이미지 저장ECR(Elastic Container Registry)은 컨테이너 이미지를 중앙에서 저장하고 관리하는 저장소 역할을 합니다.
  2. 오케스트레이션ECS 또는 EKS가 어느 EC2 인스턴스에서 컨테이너를 실행할지 결정하고 배치합니다(ECS는 AWS 기반, EKS는 Kubernetes 표준).
  3. 실행Fargate는 서버를 직접 관리하지 않고 컨테이너만 지정하면 AWS가 알아서 실행하는 방식이고, EC2를 선택하면 인스턴스 관리는 개발자가 담당합니다.

AWS Lambda, API Gateway와 서버리스 설계 원칙

서버를 직접 관리하지 않고 이벤트가 올 때만 코드를 실행하고 API를 노출하는 방식으로, 상태를 두지 않고 작게 쪼개 설계하는 것이 핵심이다.

1상대의 출발점 확인

EC2 인스턴스는 항상 켜두어야 하고, 보안 패치도 직접 관리해야 합니다. 트래픽이 많지 않은 시간대에도 서버가 돌아가므로 비용이 발생하고, 갑자기 요청이 몰려도 미리 확장해두지 않으면 대응할 수 없습니다.

2질문 제기

코드만 올려두고 필요할 때만 자동으로 실행되며 관리 부담이 없는 방식이 있을까요?

3구조적 핵심 예시

HTTP 요청이 들어오면 Lambda 함수가 즉시 실행되어 응답을 반환하고 종료되며, 요청이 없는 동안은 아무 비용도 발생하지 않습니다.

4단계별 동작 과정

  1. 이벤트 발생API Gateway가 HTTP 요청을 받거나, 다른 AWS 서비스에서 이벤트가 발생합니다.
  2. 함수 실행Lambda가 이 이벤트를 받아서 코드를 실행하고, 동시에 여러 요청이 들어와도 자동으로 병렬 처리합니다.
  3. 응답 및 종료함수 실행이 끝나면 응답을 반환하고 리소스를 해제하며, 그 동안만 비용이 부과됩니다.

5본질 요약

1상대의 출발점 확인

EC2를 실행하려면 스토리지가 필요한데, 물리 서버처럼 고정된 디스크를 사용했을 때는 모든 용도(데이터베이스처럼 높은 IOPS가 필요한 경우, 웹 파일처럼 낮은 비용만 필요한 경우)에 같은 디스크 사양을 가져야 했습니다. 또 데이터가 손실되면 복구할 방법이 없었습니다.

2질문 제기

3구조적 핵심 예시

EBS(Elastic Block Storage)는 EC2에 붙이는 네트워크 기반의 블록 스토리지로, 용도에 따라 IOPS와 처리량이 다른 여러 볼륨 타입(gp3는 일반 목적, io2는 고성능 데이터베이스, st1은 대용량 스트리밍)을 고를 수 있습니다. 언제든 스냅샷(현재 디스크 상태의 사진)을 저장해두었다가 문제가 생기면 그 시점으로 복구할 수 있습니다. 반면 인스턴스 스토어는 물리 드라이브를 직접 붙이는 것처럼 매우 빠르지만, 인스턴스가 중지되거나 장애가 나면 데이터가 사라집니다.

4단계별 동작 과정

  1. 볼륨 타입 선택용도(초당 얼마나 많은 읽기/쓰기 작업이 필요한가, 처리량은 얼마인가)에 따라 gp3, io2, st1 중 하나를 선택해 EC2에 붙입니다.
  2. 스냅샷 백업필요할 때 "지금 이 디스크의 상태를 저장해둬"라고 명령하면 AWS가 증분 방식(변화된 부분만)으로 S3에 저장하고, 나중에 그 스냅샷에서 새 볼륨을 만들어 복구합니다.
  3. 인스턴스 스토어 결정매우 높은 IOPS가 필요하거나 임시 데이터만 저장하는 경우 인스턴스 스토어를 고르지만, 인스턴스 재배포나 장애 시 데이터가 사라진다는 점을 감수합니다.

1상대의 출발점 확인

여러 EC2 인스턴스가 있으면 각 인스턴스가 자신의 EBS 볼륨만 가졌고, 파일을 공유하려면 FTP나 별도의 공유 드라이브 같은 외부 시스템이 필요했습니다. 공유하는 과정에서 여러 서버가 같은 파일을 동시에 수정할 때 일관성 문제가 발생했고, 성능이 저하되며 관리 복잡도가 증가했습니다.

2질문 제기

여러 EC2 인스턴스가 하나의 파일 시스템을 동시에 읽고 쓸 수 있게 하려면?

3구조적 핵심 예시

EFS(Elastic File System)는 수백 개의 EC2 인스턴스가 마치 같은 드라이브를 쓰는 것처럼 동시에 접근하는 관리형 공유 파일 시스템입니다. FSx는 Windows 파일 공유(SMB 프로토콜)나 고성능 컴퓨팅용(Lustre 파일 시스템)을 위한 관리형 서비스입니다. 온프레미스(회사 데이터센터)의 서버들이 AWS 클라우드 스토리지(S3, EBS)에 접근하게 하려면 Storage Gateway를 온프레미스에 설치해 로컬 캐싱과 클라우드 동기화를 담당하게 합니다.

4단계별 동작 과정

  1. 파일 시스템 마운트EFS나 FSx를 EC2 여러 대에 NFS나 SMB 프로토콜로 마운트(연결)하면 파일 시스템 하나가 여러 곳에서 동시 접근 가능해집니다.
  2. 동시성 제어AWS가 파일 락(한 서버가 쓸 때 다른 서버는 기다리는 메커니즘)을 자동으로 관리해 여러 서버가 동시에 같은 파일을 수정해도 데이터 무결성을 보장합니다.

1상대의 출발점 확인

3구조적 핵심 예시

RDS(Relational Database Service)는 MySQL, PostgreSQL 같은 데이터베이스를 AWS가 자동으로 관리해주는 서비스입니다. Aurora는 RDS보다 3배 빠르고 클라우드에 최적화된 자체 엔진입니다. 다중 AZ(다중 가용 영역)는 메인 데이터베이스와 대기 데이터베이스를 다른 가용 영역에 두어 메인이 장애 나면 대기가 자동으로 인수인계(페일오버)합니다. 읽기 전용 복제본은 메인 데이터베이스의 복사본으로 SELECT 쿼리만 처리해 조회 부하를 분산합니다. 글로벌 데이터베이스는 여러 리전에 읽기 전용 복제본을 두어 각 리전의 사용자가 가까운 곳에서 빠르게 읽습니다.

4단계별 동작 과정

  1. 다중 AZ 페일오버메인 데이터베이스가 1A에, 대기 데이터베이스가 1B에 위치하면서 동기로 복제됩니다. 메인에 장애가 발생하면 DNS 레코드가 대기를 가리키도록 자동으로 변경됩니다.
  2. 읽기 복제본 확장애플리케이션이 쓰기는 메인에, 읽기는 복제본에 보내 쿼리 처리량을 늘립니다. 같은 리전 내에 여러 개의 복제본을 만들 수 있습니다.
  3. 글로벌 배포여러 리전에 읽기 전용 복제본을 두면 각 리전의 사용자가 지역적으로 가장 가까운 복제본에서 데이터를 읽으므로 지연 시간을 줄입니다.

키-값 NoSQL 데이터베이스로, 파티션 키 설계가 성능을 좌우하고 글로벌 테이블과 온디맨드·프로비저닝 용량 모드로 확장과 비용을 조절한다.

1상대의 출발점 확인

관계형 데이터베이스(RDS)는 JOIN과 복잡한 쿼리를 잘 지원하지만 여러 서버에 수평 확장(분산 저장)이 어렵고 데이터 구조가 미리 정해져야 했습니다. 트래픽이 급증하면 수직 확장(서버 사양 업그레이드)만 가능했고 비용이 높았으며, 정해지지 않은 데이터 구조(JSON 같은 유연한 형태)를 효율적으로 저장할 수 없었습니다.

2질문 제기

구조가 정해지지 않은 데이터를 매우 빠르고 자동으로 무한 확장 가능하게 저장할 수 있을까요?

3구조적 핵심 예시

DynamoDB는 키-값 데이터베이스(키를 던지면 값을 돌려주는 단순하고 빠른 방식)로, 내부적으로 파티션 키(데이터를 어느 서버에 보낼지 결정하는 키)에 따라 데이터를 자동으로 여러 서버에 나눠 저장합니다. 파티션 키 설계가 잘되면(예: 사용자 ID를 파티션 키로, 타임스탬프를 정렬 키로) 각 서버의 부하가 균등하게 분산돼 높은 성능이 나옵니다. 글로벌 테이블로 여러 리전에 복제하고, 온디맨드(사용한 만큼 비용, 트래픽 예측 불필요) 또는 프로비저닝(미리 용량을 정해 비용 절감) 모드를 선택합니다.

4단계별 동작 과정

  2. 글로벌 테이블 구성메인 테이블(한 리전)의 쓰기를 다른 리전들에 자동 복제하면 각 리전은 로컬 읽기/쓰기가 모두 가능해집니다.
  3. 용량 모드 선택트래픽이 불규칙하면 온디맨드 모드를, 트래픽이 예측 가능하면 프로비저닝 모드를 선택해 비용을 최적화합니다.

3구조적 핵심 예시

다중 AZ(다중 가용 영역)는 같은 리전(서울)의 다른 가용 영역(1A, 1B, 1C)에 애플리케이션과 데이터베이스를 중복 배치해서 한 AZ가 장애 나도 다른 AZ가 계속 서비스합니다. 다중 리전은 서울 리전 전체가 장애 나면 싱가포르 리전이 인수하는 수준의 대비입니다. 장애 격리 경계는 각 AZ/리전 간에 "이것이 깨져도 저것은 안 깨지도록" 하는 설계로, 예를 들어 서울 1A의 네트워크 장애가 1B로 전파되지 않게 합니다.

4단계별 동작 과정

  1. 다중 AZ 배치ELB(로드 밸런서)가 요청을 여러 AZ의 EC2에 분산하고, RDS 다중 AZ는 메인과 대기를 다른 AZ에 두어 메인 장애 시 대기가 인수합니다.
  2. 데이터 동기화메인 리전에서 쓰인 데이터가 대기 리전에 비동기로 복제돼 메인 리전 전체가 장애 나도 데이터 손실을 최소화합니다.
  3. 자동 페일오버헬스 체크(주기적으로 "너 살아있니?" 신호를 보냄)가 메인의 장애를 감지하면 자동으로 대기로 전환하고, DNS와 라우팅을 갱신해 사용자는 투명하게 대기로 접속하게 됩니다.

1상대의 출발점 확인

시스템의 여러 구성 요소(서비스 A, 서비스 B, 서비스 C)가 서로를 직접 호출했고, 하나가 느려지거나 먹통되면 다른 것들도 함께 영향받았습니다. 의존성이 강해 한 부분의 장애가 연쇄 장애로 번지고, 서비스 간 통신이 과도해 병목 현상이 발생했습니다.

2질문 제기

각 서비스가 서로 직접 의존하지 않으면서도 데이터와 이벤트를 신뢰성 있게 전달할 수 있을까요?

3구조적 핵심 예시

느슨한 결합은 서비스 A가 서비스 B를 직접 호출하지 않고, 그 사이에 큐(queue = 대기열)나 이벤트 버스를 둡니다. 예를 들어 주문 처리: (1) 주문 API가 주문을 SQS 큐에 넣고 (2) 결제 처리 워커가 큐에서 꺼내 처리한 후 (3) 결과를 SNS 토픽(주제별 메시지 채널)에 발행하면 (4) 배송과 통지 등 여러 서비스가 그것을 구독해 각자 처리합니다. 주문 API와 배송 서비스는 서로를 알지 못하고, 중간의 큐와 버스를 통해서만 통신합니다.

4단계별 동작 과정

  1. 메시지 생성 및 전송서비스가 SQS(점대점 큐), SNS(발행-구독 토픽), EventBridge(이벤트 라우팅)에 메시지와 이벤트를 넣습니다.
  2. 메시지 저장 및 라우팅AWS가 메시지를 저장했다가(내구성 보장) 조건에 맞는 구독자들에게 라우팅합니다. Step Functions는 다단계 워크플로(A 끝나면 B, B 끝나면 C)를 조율합니다.
  3. 수신 및 처리각 구독자와 워커가 메시지를 받아 자기 작업을 하고, 실패 시 재시도하거나 DLQ(죽은 메시지 큐)로 보내집니다.

3구조적 핵심 예시

자산 포트폴리오 평가 시트에 모든 온프레미스 애플리케이션을 나열하고, 각각에 대해 "복잡도"(높음/낮음)와 "비즈니스 가치"(높음/낮음)를 표시합니다. 간단한 웹 서버는 리호스트(온프레미스 VM을 그대로 AWS EC2로 옮김), 레거시 메인프레임은 폐기, 비즈니스 크리티컬한 ERP는 리팩터(클라우드에 맞춰 부분 수정)라는 식으로 각각 다른 R을 할당합니다.

  3. 우선순위·일정·리스크 수립비즈니스 영향도와 기술 난이도를 고려해 마이그레이션 순서를 정하고, 각 웨이브(단계)별 예산·일정·롤백 계획 수립.

온프레미스 서버와 의존 관계를 자동 수집해 한 화면에서 진행 상황을 보고, 함께 옮길 묶음(웨이브)을 짜는 도구들.

→ 11-01 참조

1상대의 출발점 확인

기존에는 온프레미스 서버들이 어떻게 연결되어 있는지, 어떤 의존 관계가 있는지 파악하기 위해 수동으로 조사해야 했습니다. 수십에서 수백 개의 서버가 있을 때 이를 모두 파악하고, 마이그레이션 우선순위를 결정하는 것이 매우 어렵고 시간이 오래 걸립니다.

2질문 제기

온프레미스의 모든 서버와 그들 간의 의존 관계를 자동으로 파악하고, 한 화면에서 어느 서버부터 어떤 순서로 옮길지 계획할 수 있을까요?

3구조적 핵심 예시

Application Discovery Service가 각 서버에 설치된 에이전트를 통해 프로세스, 네트워크 연결, 성능 메트릭을 자동 수집합니다. Migration Hub는 이 정보들을 모아 서버들의 관계도를 시각화하고, 함께 옮길 그룹(웨이브)을 정의할 수 있게 합니다. 예를 들어, 데이터베이스 서버가 웹 서버 3개를 지원한다면, 이를 한 웨이브로 묶어 함께 마이그레이션하도록 계획할 수 있습니다.

4단계별 동작 과정

  1. 자동 발견Application Discovery Service의 에이전트가 각 온프레미스 서버에 설치되어 실시간으로 프로세스, 네트워크 연결, 의존 관계를 수집합니다.
  2. 정보 수합수집된 데이터가 Migration Hub에 전송되어 모든 서버와 그 관계를 한눈에 볼 수 있는 형태로 정리됩니다.
  3. 웨이브 계획관리자가 서로 의존하는 서버들을 하나의 그룹(웨이브)으로 묶고, 각 웨이브를 차례대로 옮길 순서를 정합니다.

1상대의 출발점 확인

온프레미스 서버를 클라우드로 옮기려면 현재 운영 중인 서버를 중단해야 합니다. 이때 서비스가 멈추는 시간이 얼마나 길어질지 알 수 없고, 옮긴 후 제대로 작동하지 않을 위험도 있습니다. 큰 서버는 옮기는 데만 시간이 많이 걸립니다.

3구조적 핵심 예시

AWS Application Migration Service(MGN)는 원본 서버의 디스크를 지속적으로 복제해둡니다. 마이그레이션 날짜가 되면 마지막 변경분만 동기화한 후, 짧은 중단 시간(일반적으로 수 분) 동안 원본 서버를 끄고 복제본 데이터로 EC2 인스턴스를 실행합니다.

4단계별 동작 과정

  3. 인스턴스 시작복제된 디스크 데이터가 EC2 인스턴스의 루트 볼륨으로 사용되며, 인스턴스가 실행되어 원본 서버와 동일한 상태로 작동합니다.

데이터 전송 (DataSync, Transfer Family, Snow Family, S3 Transfer Acceleration)

데이터 양과 회선 속도, 기한에 따라 온라인 복사·표준 프로토콜·물리 장비 배송 중 맞는 전송 수단을 고르는 기준.

1상대의 출발점 확인

대용량 데이터를 온프레미스에서 AWS로 옮길 때, 회선 속도에 따라 며칠에서 몇 주가 걸릴 수 있습니다. 네트워크 대역폭 제약, 먼 거리로 인한 지연, 전송 중 오류 등의 문제가 있습니다. 물리적으로 매우 큰 데이터(수 페타바이트)는 인터넷으로 전송 불가능합니다.

2질문 제기

데이터의 양과 전송 시간 제약에 따라 어떤 방식으로 가장 빠르고 안전하게 옮길 수 있을까요?

3구조적 핵심 예시

AWS는 네 가지 데이터 전송 옵션을 제공합니다. DataSync는 온프레미스 스토리지(NFS, SMB)에서 S3/EFS로 자동 복사하고, Transfer Family는 SFTP/FTP/FTPS 프로토콜을 쓰는 기존 솔루션과 호환시킵니다. 수 테라바이트 이상은 Snow Family(물리 디바이스)를 배송받아 데이터를 담고 AWS에 반납하면 AWS가 S3로 로드합니다. S3 Transfer Acceleration은 CloudFront의 글로벌 엣지 로케이션을 통해 장거리 전송을 빠르게 합니다.

4단계별 동작 과정

  1. 데이터 양과 시간 평가옮길 데이터 크기와 마이그레이션 기한을 판단합니다. 수 기가바이트에서 테라바이트는 온라인, 수십 테라바이트 이상은 물리 배송을 고려합니다.
  2. 적합한 전송 수단 선택DataSync(자동 복사, NFS/SMB 지원), Transfer Family(기존 도구와 호환), S3 Transfer Acceleration(빠른 인터넷 전송), Snow Family(물리 디바이스) 중 선택합니다.
  3. 전송 실행선택한 수단으로 데이터를 S3 또는 EFS로 복사하며, 자동 검증으로 손실 없음을 보장합니다.

1상대의 출발점 확인

운영 중인 데이터베이스를 클라우드로 옮길 때, 현재 데이터베이스를 중단하면 서비스가 멈춥니다. 데이터베이스 엔진이 다르면(Oracle에서 PostgreSQL로 등) 테이블 스키마와 저장 프로시저(자동화 코드)도 새 엔진에 맞게 변환해야 합니다. 이 변환 작업은 매우 복잡하고 오류가 발생하기 쉽습니다.

2질문 제기

3구조적 핵심 예시

AWS DMS(Database Migration Service)는 원본 DB에서 변경사항을 실시간으로 읽어 대상 DB로 계속 반영합니다. 마이그레이션 날짜에는 마지막 변경분만 동기화한 후 애플리케이션 연결을 전환하면 되어 중단시간이 거의 없습니다. 데이터베이스 엔진이 다르면 SCT(Schema Conversion Tool)가 사전에 테이블 정의, 인덱스, 저장 프로시저 등을 새 엔진의 문법으로 자동 변환합니다.

4단계별 동작 과정

  1. 스키마 변환SCT가 원본 DB의 테이블 구조, 프로시저, 트리거(자동 실행 규칙)를 새 DB 엔진에 맞게 변환하고, 변환할 수 없는 부분은 수동 작업 항목으로 표시합니다.
  2. 연속 복제DMS가 원본 DB의 모든 데이터를 복사한 후, 그 이후로 발생하는 변경(INSERT, UPDATE, DELETE)을 실시간으로 대상 DB에 적용합니다.
  3. 전환 및 검증대상 DB의 데이터가 원본과 일치함을 확인한 후, 애플리케이션이 대상 DB로 연결하도록 전환합니다. 문제가 생기면 빠르게 원본으로 되돌릴 수 있습니다.

덩어리 애플리케이션을 서비스 단위로 쪼개고 Lambda·컨테이너와 용도에 맞는 데이터베이스로 바꿔 운영 부담을 줄이는 접근.

1상대의 출발점 확인

전통적인 애플리케이션은 여러 기능이 하나의 큰 덩어리에 들어있습니다. 한 기능을 수정하면 전체를 다시 빌드하고 배포해야 하며, 장애가 나면 전체 서비스가 영향을 받습니다. 데이터는 하나의 큰 관계형 데이터베이스에 저장되어, 다양한 데이터 패턴에 최적화되지 못합니다. 이런 구조는 인프라 운영 비용이 크고, 빠른 변화에 대응하기 어렵습니다.

2질문 제기

하나의 큰 애플리케이션을 여러 작은 서비스로 쪼개고, 데이터와 인프라를 용도에 맞게 다양화해 유지보수를 줄이고 확장성을 높일 수 있을까요?

3구조적 핵심 예시

전자상거래 애플리케이션이 주문, 결제, 배송, 추천 기능을 하나로 가지고 있다면, 이를 각각 Lambda(서버리스) 또는 마이크로서비스(작은 컨테이너)로 분리하고, 각 서비스가 필요한 데이터만 저장합니다. 주문 데이터는 관계형 DB(RDS), 사용자 세션은 캐시(ElastiCache), 로그는 NoSQL(DynamoDB), 추천 엔진은 메모리 DB(MemoryDB)에 각각 저장합니다. 이렇게 하면 각 서비스를 독립적으로 개선하고, 필요한 만큼만 리소스를 쓸 수 있습니다.

4단계별 동작 과정

  1. 서비스 분해모놀리스의 기능을 비즈니스 단위(도메인)별로 분리하고, 각각을 Lambda 함수 또는 컨테이너 기반 마이크로서비스로 구현합니다.
  2. 데이터 현대화각 서비스가 접근하는 데이터 패턴에 맞게 데이터베이스를 선택합니다. 간단한 쿼리는 DynamoDB, 복잡한 조인이 필요하면 RDS, 실시간 분석은 Redshift, 검색은 OpenSearch를 사용합니다.
  3. 인프라 자동화Lambda는 서버를 관리하지 않으므로 자동 스케일링되고, 사용한 만큼만 비용을 냅니다. 컨테이너 기반 서비스는 ECS/EKS로 오케스트레이션합니다.

5본질 요약

하나의 거대한 애플리케이션을 독립적인 서비스로 쪼개고, 각각에 최적화된 데이터 저장소와 서버리스·컨테이너 기반 인프라를 사용해 운영 효율성과 확장성을 높이는 것
