AWS Certified SysOps Administrator – Associate

사용자가 적은 토픽 이름은 'AWS Certified SysOps Administrator – Associate' 이지만, 이 시험의 현행 정품 이름은 'AWS Certified CloudOps Engineer - Associate (SOA-C03)' 이다. 시험 안내서 Comparison 페이지가 SOA-C02 와 SOA-C03 의 개칭과 도메인 구성을 직접 비교해 주고 있고, SOA-C02 에 있던 6번째 도메인(Cost and Performance Optimization 12%) 이 SOA-C03 에서 사라져 비용 요소가 다른 도메인으로 흡수되었다. 그래서 목차는 SOA-C03 의 정품 계층을 따른다 — 5개 콘텐츠 도메인(22·22·22·16·18%) 아래 13개 태스크, 태스크 아래 53개 Skill. 앞 단계는 시험 지도(무엇을 재는지·범위 밖·채점·비중), 뒤 11단계는 도메인 1~5의 태스크 순서를 그대로 따른다. 이름이 달라졌다는 사실 자체가 01-01 과 01-04 에서 짚을 내용이다.

운영자가 인스턴스 CPU 사용량을 본다. 기준치를 넘는 순간 알람이 울려 SNS 로 알림이 간다(→ 02-05).

누가 API 호출을 남겼는지도 함께 확인하려고 AWS CloudTrail 기록을 뒤진다.

#4동작 과정

  1. 지표를 모은다Amazon CloudWatch 로 인스턴스와 서비스의 CPU 같은 지표를 모아 시간에 따라 남긴다.
  2. 기록을 남긴다AWS CloudTrail 로 누가 어떤 API 를 불렀는지 남겨 둔다. 로그는 지표와 따로 모으는 기록이다.
  3. 알람과 필터를 건다기준을 넘는 구간만 드러내도록 알람과 필터를 정한다. 지표를 Prometheus 방식으로 다루려면 Amazon Managed Service for Prometheus 로 보낼 수 있다.
  4. 확인해 볼 것CloudWatch 콘솔에서 알람 목록에 만든 규칙이 상태를 가지고 나타나는지 본다.

CloudWatch 알람 — 복합 알람과 호출 가능한 동작

CloudWatch 알람은 지표가 임계값을 넘으면 알려 주도록 만든 규칙으로, 여러 알람 조건이 모두 맞아야 발화하는 복합 알람과 알람 트리거 동작(알림, 자동 복구·인스턴스 재부팅 같은 자동 조치)이 있다.

먼저 알아야 할 것 02-02

→ 02-02 참조

#1문제 상황

CloudWatch 알람은 지표 값이 정한 임계값에 닿으면 상태를 바꾸고 알려 주는 규칙이다(→ 02-01). 이때 알람은 두 가지 일을 맡는다. 하나는 발화했을 때 무엇을 호출할지 정하는 invoking actions, 즉 호출 가능한 동작을 고르는 것이다.

알람 하나에 여러 지표 조건을 묶은 composite alarms, 즉 복합 알람을 두면 서로 다른 자원의 조건이 모두 맞았을 때만 한 번만 울리게 할 수 있다. 알람이 울린 뒤의 알림 전달은 → 02-05에서 다룬다.

#2핵심 질문

여러 조건을 한 번에 묶어 알람을 울리고, 울릴 때 자동으로 실행할 동작까지 지정하려면?

#3동작 예시

운영자가 웹 서버 두 대의 CPU 사용률을 하나의 복합 알람으로 묶었다. 화면에는 정상 상태로 보인다가 어느 한 대라도 CPU가 기준을 넘는 순간 상태가 alarming으로 바뀌고, 호출 동작으로 자동 조치 항목이 실행되며 화면의 상태 이력에 남는다.

#4동작 과정

  1. 지표와 임계값을 정한다알람 하나가 지켜볼 지표와 비교 기준을 고른다. 트리거 동작과 알람 상태가 바뀐 시각을 콘솔에 남겨 나중에 어떤 값 때문에 울렸는지 확인한다.
  2. 여러 조건을 묶는다composite alarms는 하위 알람 여러 개를 가진다. 하위 조건이 모두 맞는 규칙을 잡으면 알람이 하나만 올라온다.
  3. 호출 가능한 동작을 붙인다알람이 발화할 때 실행할 동작을 고른다. 알림 보내기나 인스턴스 재부팅 같은 자동 조치가 여기에 해당하고, 다른 시스템으로 넘길 때는 Amazon EventBridge를 대상으로 삼는다.
  4. 확인해 볼 것CloudWatch 콘솔의 알람 목록에서 복합 알람의 상태와 하위 알람 목록, 발화 시각이 함께 보이는지 확인한다.

#1문제 상황

CloudWatch 대시보드는 여러 지표를 한 화면에 배치해 보여 주는 화면이다. 크로스 계정 대시보드는 다른 AWS 계정의 지표를, 크로스 리전 대시보드는 다른 리전의 지표를 함께 불러와 한 화면에 모은다. 이제 여러 계정과 리전의 상태를 한 곳에서 본다.

#2핵심 질문

여러 AWS 계정과 리전에 흩어진 지표와 알람을 한 화면으로 어떻게 합칠까?

#3동작 예시

#4동작 과정

  1. 화면을 만든다대시보드를 만들고 그 위에 위젯을 놓는다. 위젯 하나가 그리는 그래프나 표를 정한다.
  2. 다른 계정과 리전을 연결한다크로스 계정 대시보드는 계정 간에 지표를 공유하도록 권한을 주고, 크로스 리전 대시보드는 다른 리전의 지표를 불러온다. 이제 여러 계정과 리전의 지표가 한 화면에 모인다.
  3. 공유한다대시보드를 링크로 공유해 다른 사람이 같은 화면을 열어 본다. 알람과 인스턴스 상태도 위젯으로 올릴 수 있다.
  4. 확인해 볼 것대시보드 위젯 목록에서 다른 계정과 다른 리전의 지표가 한 화면에 함께 그려지는지 확인한다.

알림을 SNS 로 보낸다

CloudWatch 알람이 발화했을 때 알림을 받도록 Amazon SNS 주제를 알람의 알림 대상으로 지정하고, 그 주제에 구독자를 붙여 이메일·문자 같은 통보 채널로 메시지가 전달되게 만드는 것.

먼저 알아야 할 것 02-04

→ 02-04 참조

#1문제 상황

CloudWatch 알람이 발화하면 상태만 바뀐다(→ 02-03). 화면을 계속 들여다보지 않는 사람은 그 사실을 즉시 알 수 없다.

알람의 알림 대상으로 Amazon SNS 주제를 지정하면 이 문제가 사라진다. Amazon SNS는 주제에 붙은 구독자에게 메시지를 넘기는 통보 서비스로, 이메일이나 문자 같은 통보 채널을 제공한다. 알람이 울린 이유가 담당자에게 곧바로 닿는다.

#2핵심 질문

알람이 발화했을 때 담당자에게 자동으로 알려 주려면?

#3동작 예시

운영자가 알람에 알림 대상으로 등록된 SNS 주제를 열어 본다. 그 주제에는 팀 Distribution List와 당번 핸드폰이 구독자로 붙어 있다. 알람이 발화하면 메일과 문자가 함께 도착하고, 알람의 상태 이력에 알림이 발화한 시각이 함께 남는다.

#4동작 과정

  1. 주제를 만든다Amazon SNS 주제를 만들고 통보에 쓸 이름을 정한다. 하나를 여러 알람이 함께 쓸 수 있다.
  2. 구독자를 붙인다주제에 구독자를 등록한다. 수신자 메일 주소나 문자 번호를 넣으면 알림이 그 통보 채널로 전달된다.
  3. 알람에 알림 대상으로 지정한다CloudWatch 알람의 알림 대상 목록에 그 SNS 주제를 추가한다(→ 02-03). 발화 상태가 바뀔 때마다 주제가 알림을 보낸다.
  4. 확인해 볼 것SNS 주제 화면에 구독자가 초록불로 활성화되어 있고 알람의 알림 대상 목록에 주제가 보이는지 확인한다.

성능 지표에서 병목을 찾는다

CloudWatch 에서 수집한 성능 지표와 로그를 함께 보면서 어느 자원(CPU·네트워크·I/O)이 한계에 닿았는지 숫자로 확인해 병목 구간을 좁히는 일.

먼저 알아야 할 것 02-01

#1문제 상황

서비스가 느려졌다는 보고만 들어도 어느 자원 때문인지 바로 알 수는 없다(→ 02-01). 지표를 따로 열어서 하나씩 대조하는 동안 시간이 흐른다.

이 일을 하는 방식은 정해져 있다. CloudWatch 지표와 로그를 나란히 놓아 어느 자원이 한계에 닿았는지 숫자로 확인하고 그 구간을 좁힌다. 좁혀진 지표를 알람 조건으로 바꾸면 같은 문제가 다시 오면 바로 잡힌다(→ 02-03).

#2핵심 질문

느려진 서비스에서 어느 자원이 한계에 닿았는지 지표로 어떻게 좁히는가?

#3동작 예시

주문 API 응답이 느려진다고 보고가 들어온다. 운영자는 CloudWatch에서 CPU 사용량, 네트워크 입출력, 디스크 I/O 그래프를 같은 시간축으로 열어 본다. CPU는 평균 수준인데 네트워크 아웃풋만 한계에 붙어 있어, 병목이 외부로 나가는 구간 쪽임을 짚는다.

#4동작 과정

  1. 시간대를 맞춘다여러 지표를 같은 시간 범위로 겹쳐 본다. 먼저 이상이 시작된 시점을 눈으로 잡는다.

→ 03-01 참조

#1문제 상황

자동 복구는 이 공백을 없앤다. Amazon EC2 Auto Recovery는 인스턴스 장애를 감지하면 신선한 인스턴스로 자동 이전해 가용성을 회복하는 기능이다. 사람이 개입하기 전에 정해진 규칙대로 되돌리는 설계가 가능해진다.

#2핵심 질문

인스턴스 장애가 났을 때 사람이 개입하지 않고 자동으로 정상 상태로 되돌리려면?

#3동작 예시

#4동작 과정

  1. 규칙을 정한다어떤 조건을 장애로 볼지 정하고 그때 무엇을 실행할지 나열한다. AWS CloudTrail은 누가 무엇을 호출했는지 남겨 복구가 왜 일어났는지 사후에 확인하게 해 준다.
  2. 자동 복구를 건다Amazon EC2 Auto Recovery 같은 기능을 켜 두고 Auto Scaling 그룹으로 대체 인스턴스를 늘려 둔다. 그러면 실패한 자리에 정상 인스턴스가 차례로 채워진다.
  3. 실행을 맡긴다알람이 발화하면 정해진 코드를 실행해 상태를 되돌릴 수도 있다. AWS Lambda로 복구 절차를 작성하고 AWS DevOps Agent에게 자정에 이 복구 절차를 점검하고 실행하게 둔다.
  4. 확인해 볼 것인스턴스 화면에서 자동 복구 설정이 켜져 있는지, 교체된 인스턴스가 정상 상태로 표시되는지 확인한다.

먼저 알아야 할 것 03-02

→ 03-02 참조

#1문제 상황

자동 복구 규칙은 조건 하나씩만 감시한다(→ 03-02). 이벤트가 여럿이면 대상마다 따로 연결하고, 규칙이 안 먹힐 때 어디서 끊겼는지 찾기도 어렵다.

Amazon EventBridge는 이 연결을 대신한다. EC2 상태 변경이나 CloudWatch 알람 같은 이벤트를 규칙으로 걸러 AWS Lambda 같은 대상에 전달한다. 규칙 문제도 규칙의 실패 지점과 이벤트 본문 기록으로 좁혀 찾는다.

#2핵심 질문

시스템 이벤트를 조건에 맞는 여러 대상에 자동으로 넘기고 전달이 안 되는 원인은 어떻게 찾는가?

#3동작 예시

운영자가 EC2 인스턴스가 stopped 상태가 되는 순간 자동 복구를 돌리게 한다. 이벤트 버스에 규칙 하나를 만들어두면 인스턴스가 재부팅될 때마다 Lambda 함수가 자동으로 호출되고 처리 결과가 기록에 남는다.

#4동작 과정

  1. 이벤트를 보낸다이벤트 버스에는 시스템 이벤트가 모여든다. 인스턴스 상태 변경이나 알람 상태 변화가 여기에 들어온다.
  2. 규칙으로 걸러 전달한다패턴을 적은 규칙이 이벤트를 고르고 지정한 대상으로 보낸다. AWS Step Functions를 대상으로 삼으면 여러 작업을 순서대로 이어 붙일 수 있다.
  3. 문건을 보강한다이벤트를 다른 값으로 바꿔 대상에 넘길 수 있다. 그래서 대상 쪽 코드는 원본 값 대신 보강된 값을 쓰게 된다.
  4. 확인해 볼 것EventBridge 규칙 화면에서 규칙 상태가 활성인지, 실패한 규칙의 실패 지점 목록이 보이는지 확인한다.

먼저 알아야 할 것 03-02

#1문제 상황

AWS Systems Manager 자동화는 이 반복 작업을 미리 적어 둔 순서로 실행한다. 자동화 런북이라 부르는 문서가 그 순서이고, EC2 인스턴스처럼 관리할 수 있는 자원이 대상이다.

#2핵심 질문

#3동작 예시

운영자가 EC2 인스턴스 20대의 디스크 설정을 바꿔야 한다. 같은 명령을 20번 칠 필요 없이 자동화 런북을 한 번 실행해 대상 인스턴스에 같은 단계가 차례로 적용된다.

실행 화면에는 단계별로 성공과 실패가 남고 실패한 인스턴스만 다시 짚어 처리할 수 있다.

#4동작 과정

  1. 런북을 고른다Create or run custom and predefined Systems Manager Automation runbooks, 즉 미리 있는 런북을 고르거나 직접 만든다. 자동화 문서 안에서 AWS Lambda 호출 같은 단계로 작업을 잇는다.
  2. 대상과 단계를 정한다실행할 인스턴스를 대상 지정하고 각 단계의 입력을 채운다. 조건 분기를 넣어 특정 경우에만 도는 단계도 넣는다.
  3. 실행하고 상태를 본다AWS SDKs나 사용자 스크립트에서 같은 런북을 호출할 수 있고, 실행 결과는 단계별 상태로 남는다. 반복 작업은 automate tasks and streamline processes on AWS, 즉 사람의 개입을 줄이는 쪽으로 이어진다.
  4. 확인해 볼 것Systems Manager 콘솔의 Automation 실행 기록에서 각 단계의 상태와 로그를 열어 본다.

  1. 지표를 본다CPUCreditUsage 같은 성능 지표와 resource tags, 즉 자원을 분류해 붙이는 이름표를 함께 쓴다. 태그별로 어느 그룹이 느린지 비교해 병목을 좁힌다.

EBS 성능 지표와 볼륨 유형

EBS 볼륨의 지연 시간과 처리량, IOPS 같은 성능 지표를 측정하고 gp3·io2 등 볼륨 유형과 provisioned IOPS 설정을 골라 인스턴스에 맞는 디스크 성능을 만드는 일이다.

먼저 알아야 할 것 04-02

#1문제 상황

인스턴스 CPU 여유가 있는데도 애플리케이션이 느릴 때 원인은 디스크 쪽일 수 있다. 그런데 디스크 설정은 기본값으로 두고 아무도 안 본다.

Amazon EBS의 성능 지표를 분석하고 볼륨 유형을 골라 디스크 성능을 올리고 비용을 낮추는 것이 이 항목이다.

#2핵심 질문

디스크가 병목일 때 어떤 지표를 보고 어떤 볼륨 유형으로 바꾸나?

#3동작 예시

데이터베이스 인스턴스가 평소보다 느려졌다. 운영자는 해당 Amazon EBS 볼륨의 지연 시간 그래프가 평소보다 높게 유지되는 것을 본다.

원인을 찾고 처리하는 troubleshooting 과정을 거쳐, 처리량 한계에 걸린 볼륨을 provisioned IOPS를 늘린 볼륨으로 바꿔 다시 붙인다.

#4동작 과정

  1. 성능 지표를 분석한다Analyze Amazon EBS performance metrics, 즉 볼륨별 지연 시간·처리량·IOPS 지표를 본다. 어느 볼륨이 한계에 닿았는지 숫자로 확인한다.
  2. 원인을 좁힌다지표가 나쁜 볼륨이 단일인지 여러 개인지 보고, 인스턴스 사양이 발목을 잡는지 확인해 문제를 troubleshooting issues로 정리한다.
  3. 볼륨 유형을 바꾼다optimize volume types to improve performance and reduce cost, 즉 gp3 같은 범용 유형과 io2 같은 고성능 유형 중 workloads에 맞는 쪽을 고른다. 필요하면 provisioned IOPS를 조정해 성능과 비용을 함께 맞춘다.

#4동작 과정

#4동작 과정

  2. 규칙으로 걸러 낸다이벤트의 종류와 값이 조건에 맞으면 규칙이 발화한다. 여기서 어느 대상을 부를지 정하고 AWS Lambda 같은 함수나 Systems Manager 문서를 연결한다.
  3. 여러 단계를 잇는다AWS Step Functions는 여러 작업을 순서대로 묶어 하나의 흐름으로 실행한다. AWS DevOps Agent는 이런 이벤트 대응 흐름을 사람이 직접 고치지 않게 보조하는 기능이다.

IAM 기능 구현

AWS IAM(누가 어떤 AWS 자원에 무엇을 할 수 있는지를 정하는 권한 관리 서비스)의 정책·역할·정책 변형·하드닝 옵션을 실제로 설정해 필요한 최소 권한만 허용하는 것.

먼저 알아야 할 것 01-03

#1문제 상황

사람마다 AWS 계정을 만들면 퇴사자 계정이 남고, 계정을 빌려 쓰면 기록이 뒤섞인다. 권한을 느슨하게 주면 누구가 무엇을 했는지 알 수 없다.

IAM 기능 구현은 AWS IAM에서 누가 어느 자원에 무엇을 할 수 있는지 직접 정책으로 정하는 일이다. 계정 하나를 두고 사람 수만 늘리며 최소 권한만 남긴다.

#2핵심 질문

사람과 프로그램마다 필요한 권한만 정확히 어떻게 허용할까?

#3동작 예시

운영자가 EC2 인스턴스를 시작해야 한다. IAM 콘솔의 정책에서 그 동작에 해당하는 항목만 골라 역할에 붙인다. 같은 계정의 다른 사람은 인스턴스 삭제 권한을 따로 가져야 하며, 그 권한은 그 사람에게만 보인다.

#4동작 과정

  1. 권한 문장을 만든다IAM 정책은 자원·동작·조건을 세 부분으로 적는 규칙 문서다. 어느 행위(예: 볼륨 생성)를 어느 자원에 허락할지를 이 문장으로 지정한다.
  2. 역할로 나눠 준다roles는 사람이나 프로그램에 권한 묶음을 붙이고 넘기는 단위다. federated identity는 사내 디렉터리 같은 외부 인증 체계의 신분을 AWS 계정으로 연결해 로그인하게 한다.
  3. 자원에 붙인다resource policies는 버킷이나 스냅샷 같은 자원 자체에 붙여, 그 자원에 접근할 수 있는 주체를 지정한다. policy conditions는 태그나 IP 같은 조건이 맞을 때만 허용되도록 좁힌다.
  4. 확인해 볼 것IAM 콘솔에서 정책 목록을 열어 각 정책에 어떤 조건과 자원이 적혀 있는지 확인한다.

접근 문제 추적과 감사는 AWS CloudTrail 같은 감사 로그와 IAM 분석 도구로 지난 행동을 뒤집어 보는 일이다.

#3동작 예시

#4동작 과정

  1. 기록을 모은다AWS CloudTrail은 계정 안에서 일어난 API 호출을 누가 언제 무엇을 했는지 시간순으로 남는다. 회사의 모든 리전에서 기록을 켜 두는 편이 좋다.
  2. 권한 밖 사용을 찾아낸다IAM Access Analyzer는 정책에 적힌 허용 범위를 넘어 자원에 붙은 접근 권한이 있는지 찾아 낸다.
  3. 어떻게 될지 먼저 시험한다IAM policy simulator는 어떤 정책 아래에서 특정 호출이 허용되는지 되짚어 보여 준다. Troubleshoot and audit access issues by using AWS tools 는 이 확인 절차를 통째로 가리키는 시험 항목이며, 요청 경로를 따라 문제 구간을 좁힐 때는 AWS X-Ray 도 쓴다.
  4. 확인해 볼 것CloudTrail 콘솔에서 Look up Events 화면으로 특정 주체의 호출만 골라 목록이 뜨는지 확인한다.

#1문제 상황

계정을 늘리면 서로 다른 팀이 자원을 서로 건드릴 수 있다. 계정을 하나씩 직접 관리하면 정책 적용이 늦고 빠진 곳이 생긴다.

다중 계정 전략은 AWS Organizations로 계정들을 하나의 조직 아래 묶어 상위 규칙을 강제하는 일이다.

#2핵심 질문

여러 계정에 같은 보안 상한을 어떻게 빠짐없이 적용할까?

#3동작 예시

운영 계정과 개발 계정, 보안 계정이 나뉘어 있다. 서비스 제어 정책을 조직 전체에 붙이고 나면, 어떤 계정에서도 특정 리전 자원을 만들 수 없게 된다. 위반 시도는 조직 콘솔에서 거부된 정책 항목으로 남는다.

#4동작 과정

  1. 계정을 묶는다AWS Organizations가 여러 계정을 하나의 조직 아래 두고 계정 목록과 루트 권한을 관리한다. 상위 계정 하나만 건드리면 전체에 영향을 준다.
  2. 상한을 정한다service control policies는 조직에 붙은 계정이 무엇을 할 수 있는지의 상한을 정한다. IAM 정책과 달리 "할 수 없는 것"을 금지하는 방식으로 동작한다.
  3. 사람을 한군데로 모은다IAM Identity Center는 여러 계정에 대한 로그인과 권한 승인을 한 곳에서 처리하게 해 계정마다 별도 아이디를 만들지 않게 한다.
  4. 확인해 볼 것Organizations 콘솔의 계정 목록에서 각 계정이 어느 organizational unit 아래 묶여 있는지 확인한다.

Trusted Advisor 보안 점검 결과로 조치한다

AWS Trusted Advisor 의 보안 점검 항목(공개 접근Bucket, 다중 요소 인증 미적용 등) 중 위험 표시를 확인하고 해당 설정을 직접 고치는 것.

먼저 알아야 할 것 09-03

#1문제 상황

보안 설정을 하나씩 확인하려면 버킷과 계정, 권한 항목을 계속 열어 봐야 한다. 무엇이 위험한지 우선순위도 정하기 어렵다.

AWS Trusted Advisor는 이런 항목을 정해진 기준으로 훑어 위험 표시를 남긴다. 이 표시를 보고 직접 고치는 것이 Trusted Advisor 보안 점검 결과로 조치하는 일이다.

#2핵심 질문

어느 보안 설정이 위험한지 어떻게 한눈에 알아낼까?

#3동작 예시

Trusted Advisor 대시보드의 보안 항목에서 경고 표시가 뜬 자원이 보인다. 그 항목을 눌러 어떤 버킷이 공개 접근을 허용하는지 확인하고, 해당 버킷의 접근 설정을 직접 고친 뒤 표시가 사라지는지 본다.

#4동작 과정

  1. 점검을 돌린다AWS Trusted Advisor가 보안 항목의 기준에 맞춰 설정을 검사한다. 공개 접근이 허용된 버킷, 다중 요소 인증이 없는 계정 같은 대상을 색깔로 구분해 보여 준다.
  2. 순서를 정한다경고 표시 가운데 위험도가 높은 항목부터 골라 처리한다. 이 결과가 remediation, 즉 발견한 문제에 대한 조치 대상으로 이어진다.
  3. 설정을 고친다표시된 항목이 가리키는 자원으로 이동해 실제 설정을 수정한다. Trusted Advisor는 혼자 고칠 수 없어 사람이 손대야 하는 부분을 그대로 남겨 둔다.
  4. 확인해 볼 것Trusted Advisor 콘솔의 보안 항목에서 표시가 붙은 자원이 몇 개 남아 있는지 확인한다.

먼저 알아야 할 것 09-04

#1문제 상황

감사 시점마다 설정이 규정에 맞는지를 한 항목씩 수작업으로 확인하면 시간이 오래 걸리고 놓치는 곳이 생긴다. 규정 항목이 바뀔 때마다 다시 뒤지는 것도 부담이다.

AWS Config는 설정이 바뀔 때마다 기록을 남기고 규칙으로 자동 검사한다. AWS Config conformance packs는 여러 규칙을 규범 묶음으로 한 번에 적용한다.

#2핵심 질문

설정이 규정을 계속 지키는 상태를 유지하려면 어떻게 확인할까?

#3동작 예시

공개 접근을 금지라는 기준을 걸어 두면 누군가 버킷 공개 설정을 켜는 순간 기록이 쌓이고 규칙이 위반으로 표시한다. 대시보드에서 위반 리소스 목록이 어느 정도 쌓였는지 바로 본다.

#4동작 과정

  1. 기록을 남긴다AWS Config는 지원 서비스의 설정 변경 내용을 시간순으로 기록해 두고, 어느 리전과 어느 서비스를 대상으로 볼지 고를 수 있다.
  2. 규칙을 건다규칙 하나가 요구 사항 하나를 검사한다. 감사 대상에 맞춰 여러 규칙을 모은 것이 AWS Config conformance packs로, 규범 하나를 통째로 배포한다.
  3. 위반을 알린다규칙이 어긋난 리소스를 표시하고 알림을 보낸다. 고치는 것까지 자동화할 수도 있어 사람이 나중에 확인한다.
  4. 확인해 볼 것AWS Config 콘솔에서 리소스별 설정 기록과 규칙의 현재 준수 여부를 열어 본다.

데이터 분류 체계

기업의 데이터를 민감도 수준에 따라 범주별로 나누고 각 범주에 맞는 암호화·접근 권한·보관 방식을 정해 두는 체계.

먼저 알아야 할 것 09-01

#1문제 상황

모든 데이터를 같은 방식으로 다루면 기밀 데이터와 공개 데이터가 같은 권한을 받고 같은 암호화 수준을 받는다. 한 버킷이 유출되면 전부가 노출된다.

데이터 분류 체계는 데이터를 민감도별로 범주에 나누고 범주마다 암호화·접근 권한·보관 방식을 정하는 체계다. 정한 뒤에는 Implement and enforce a data classification scheme, 즉 그 규칙을 실제로 강제한다. 가장 엄격한 요구는 Amazon Macie로 S3 버킷 안의 민감 정보를 자동으로 찾아낼 수 있다.

#2핵심 질문

어떤 데이터를 누구까지 허용하고 어디까지 암호화할 것인가?

#3동작 예시

#4동작 과정

VPC 구성

VPC(가상 사설 클라우드)는 AWS 계정 안에서 격리된 가상 네트워크 영역으로, 서브넷·IP 대역·라우팅 테이블·게이트웨이 같은 구성 요소를 직접 조합해 원하는 사내망 구조를 만들고 그 안에서 인스턴스 등 자원을 동작시키는 것.

먼저 알아야 할 것 01-02

#1문제 상황

인스턴스를 만들면 자동으로 붙는 기본 네트워크를 쓰게 되는데, 이 구조로는 어떤 트래픽을 어디로 내보낼지 정할 수 없다. 사내망 구분을 스스로 만들어야 한다.

VPC는 계정 안의 격리된 가상 네트워크로, 그 안에서 자원을 돌린다. 이 항목의 일은 Configure a VPC, 즉 구성 요소를 직접 조합하는 것이다. 서비스 이름은 Amazon VPC다.

#2핵심 질문

어떤 서브넷과 경로로 나눠야 내 트래픽이 정한 곳만 오가게 되는가?

#3동작 예시

운영자가 VPC를 만들고 두 개의 퍼블릭·프라이빗 서브넷(→ 11-02)을 나눈다. 프라이빗 서브넷의 EC2는 인터넷으로 직접 나갈 수 없고 NAT 게이트웨이를 통해서만 나간다.

결과적으로 DB 인스턴스는 외부에서 도달할 수 없게 된다.

#4동작 과정

  1. 영역과 주소를 나눈다VPC와 그 안의 여러 Availability Zone에 걸친 서브넷을 만들고 각 서브넷의 IP 대역을 정한다.
  2. 경로를 정한다route tables에 각 서브넷의 목적지별 경로를 적는다. internet gateway를 붙여 외부로 나가고, NAT 게이트웨이와 egress-only internet gateway로 필요한 출구만 연다.
  3. 경계를 세운다security groups로 인스턴스별, network ACLs로 서브넷별로 들어오고 나가는 트래픽을 막는다. 두 설정은 방향 지정 여부가 다르다.
  4. 확인해 볼 것VPC 콘솔의 라우팅 테이블 목록에서 서브넷별로 어느 게이트웨이로 나가는 경로가 적혀 있는지 확인한다.

사설 네트워킹 연결은 VPN 터널이나 Direct Connect 같은 방식으로 온-premises(사내 데이터센터)와 VPC를 이어 사내망과 클라우드 사이의 트래픽을 공인 인터넷 없이 암호화된 통로로 주고받는 구성.

→ 11-01 참조

#1문제 상황

VPC 안의 인스턴스(→ 11-01)는 기본적으로 공인 인터넷으로는 나가지 못하고, 사내 데이터센터와도 연결되어 있지 않다. 사내망에 있는 기존 시스템과 데이터를 주고받으려면 별도의 통로를 만들어야 한다.

Configure private networking connectivity는 그 통로를 만드는 설정이다. VPC peering, AWS Transit Gateway, AWS Site-to-Site VPN, AWS Client VPN이 여기에 속한다.

#2핵심 질문

사내 데이터센터와 VPC 사이를 공인 인터넷 없이 어떻게 이어 붙일까?

#3동작 예시

사내망의 서버가 S3에 있는 데이터를 읽어야 한다. 운영자가 VPC peering 연결을 만들고 두 쪽 라우팅 테이블에 경로를 추가한다.

이후 사내 서버에서 S3로 나가는 요청이 암호화된 채 VPC를 지나 S3에 도착한다.

#4동작 과정

  1. 연결 방식을 고른다같은 계정의 두 VPC는 VPC peering로 직접 잇는다. 여러 VPC와 여러 사내 데이터센터를 한 허브에 붙일 때는 AWS Transit Gateway를 쓴다.
  2. 암호화된 터널을 연다사내 데이터센터와는 AWS Site-to-Site VPN 터널을 만든다. 사용자 PC에서 VPC 안의 사내 앱으로 직접 접속할 때는 AWS Client VPN을 쓴다.
  3. 내부 서비스만 연다S3나 DynamoDB 같은 AWS 서비스에 공인 인터넷을 거치지 않고 붙이려면 VPC endpoints를 만든다. AWS PrivateLink로 해당 서비스만 VPC 안에서만 해석·연결되게 한다.
  4. 확인해 볼 것VPC 콘솔의 Peering connections 목록에서 상태가 Active로 보이는지, 사내 서버에서 VPC 안 주소로 통신이 되는지 확인한다.

#1문제 상황

네트워크에 방어 기능을 켜 두지 않으면 웹 공격과 대량 트래픽이 그대로 도달한다. 그런데 어떤 보호 기능이 켜져 있는지, VPC Flow Logs로 무엇이 오가는지 한 화면에서 확인하지 못하면 노출 상태를 놓친다.

Audit AWS network protection services는 한 계정 안에서 이 보호 설정들을 점검하는 일이다.

#2핵심 질문

내 VPC에 어떤 네트워크 보호가 설정되어 있고 어디가 노출되어 있는지 어떻게 확인하지?

#3동작 예시

운영자가 AWS Console의 Shield 콘솔을 열어 구독 상태를 본다. Standard 보호만 걸려 있고 Advanced는 꺼져 있다.

Network Firewall에는 아무 정책도 없고, VPC Flow Logs는 두 개의 서브넷에서만 켜져 있다. 어디를 고쳐야 할지가 바로 보인다.

#4동작 과정

  1. 보호 기능을 켠다AWS Shield는 네트워크 계층 공격을 완화하고 자동 보호를 제공한다. Advanced 등급은 DDoS 공격 정황과 쇼핑카트를 지원한다.
  2. 트래픽을 거른다AWS WAF는 HTTP 요청을 규칙으로 걸러 차단한다. AWS Network Firewall은 VPC 안에서 패킷 자체를 상태 추적하며 걸러 낸다.
  3. 이름 조회를 막는다Route 53 Resolver DNS Firewall는 Route 53 Resolver가 넘기는 질의 중 위험한 도메인 이름을 차단한다. VPC Flow Logs로 오간 흐름을 함께 보면 어디서 들어왔는지 알 수 있다.
  4. 확인해 볼 것Shield 콘솔에서 구독 등급이 무엇으로 표시되고, Firewall Manager의 정책 목록에 어떤 상태로 나오는지 본다.

#1문제 상황

Optimize the cost of network architectures는 흐름을 본 뒤 대역폭과 연결 요소를 고치는 작업이다.

#2핵심 질문

어떤 네트워크 요소가 비용을 끌어올리는지 어떻게 찾아 고칠까?

#3동작 예시

운영자가 AWS Cost Explorer에서 서비스별 비용을 연다. Network가 높은데, VPC 안의 인스턴스가 프라이빗 서브넷에서 S3로만 나가고 있었다.

NAT 게이트웨이로 모두 나가고 있었기 때문에 S3 데이터 전송 비용이 계속 붙었다. VPC endpoints로 경로를 바꿨다.

#4동작 과정

  1. 어디에 돈을 쓰는지 본다AWS Cost Explorer와 AWS Cost and Usage Reports로 서비스와 리전별 비용을 나눠 본다. 비용 관리는 Cloud financial management가 맡는다.
  2. 불필요한 요소를 걷는다NAT 게이트웨이를 지나는 트래픽이 S3 같은 내부 서비스로만 간다면 VPC endpoints(→ 11-02)로 우회한다. 쓰지 않는 Elastic IP addresses는 반납한다.
  3. 약정으로 비용을 고정한다사용량이 예상 가능한 트래픽은 Savings Plans으로 묶어 지출을 일정하게 만든다.
  4. 확인해 볼 것VPC 콘솔의 NAT gateways 목록에 상태가 available로 남은 게이트웨이가 있는지 확인한다.

#1문제 상황

VPC 안의 인스턴스가 외부 도메인 이름을 물으면 기본 AWS DNS 서버가 답을 모른다. 직접 만든 이름 서버를 붙여도 어떤 질의를 어디로 보낼지 관리하기 어렵다.

Configure DNS는 이름 조회 흐름을 직접 설계해 정하는 일이다.

#2핵심 질문

어떤 이름 조의를 어느 서버로 보내 VPC 안 이름이 내부에서만 풀리게 할까?

#3동작 예시

운영자가 사내 전용 이름 db.internal의 호스트존을 만들고 프라이빗 호스트존으로 VPC 두 곳에 연다.

VPC 안 인스턴스가 db.internal을 물으면 Route 53 Resolver가 내부 주소로 답하고, 인터넷에서는 이 이름이 보이지 않는다.

#4동작 과정

  1. 호스트존을 만든다Amazon Route 53에서 도메인 하나를 담는 호스트존을 만들고 그 안에 A, CNAME 같은 레코드를 만든다.
  2. 안에서만 풀리게 한다프라이빗 호스트존을 VPC에 연결하면 그 VPC 안에서만 해석되고 밖으로 나가지 않는다.
  3. 질의를 나눠 보낸다Route 53 Resolver에 규칙을 만들어 특정 도메인만 사내 DNS 서버로 넘기고 나머지는 AWS DNS로 보내게 한다.
  4. 확인해 볼 것Route 53 콘솔의 Hosted zones에서 프라이빗 호스트존 목록에 연결된 VPC가 보이는지 확인한다.

#1문제 상황

도메인 하나에 서버가 여러 대 있으면 어디로 보낼지 규칙이 없다. 같은 도메인이 어느 리전에서 느린지, 어떤 이름이 외부에서 왔는지 추적할 기록도 없다.

Implement Route 53 routing policies, configurations, and query logging이 이 둘을 다룬다.

#2핵심 질문

한 도메인의 요청을 어느 리소스로 보낼지 정하고 그 과정을 기록하려면 어떻게 하나?

#3동작 예시

운영자가 가중치 레코드 두 개를 만들고 서울 리전에 80, 도쿄 리전에 20을 준다. DNS 질의 결과가 두 리전에 8대 2대로 나뉜다.

질의 로깅을 켜자 CloudWatch Logs에 어떤 도메인이 어디서 조회됐는지 기록이 남는다.

#4동작 과정

  1. 정책을 고른다Amazon Route 53의 레코드에 단순, 가중치, 지연 시간, 장애 기반, 지리 위치 정책 가운데 하나를 붙인다. 어떤 리소스로 보낼지 이 정책이 정한다.
  2. 레코드를 붙인다같은 이름에 여러 레코드를 만들고 각 값(가중치나 지역 등)을 채운다.
  3. 질의를 남긴다질의 로깅을 켜면 모든 DNS 질의가 CloudWatch Logs로 넘어온다. 설정 변경 이력은 별도의 변경 로그로 남는다.
  4. 확인해 볼 것Route 53 콘솔에서 호스트존의 상태가 정상으로 보이는지, CloudWatch Logs 그룹에 질의 기록이 쌓이는지 본다.

콘텐츠와 서비스 배포는 CloudFront로 정적 콘텐츠와 API를 엣지 가까운 곳에서 전송해 지연을 줄이고, Origin Shield나 S3 같은 오리진 앞단에 방패를 두어 DDoS와 오버로드를 완화하는 구성.

먼저 알아야 할 것 11-06

→ 11-01 참조

#1문제 상황

S3나 API를 원래 위치에서만 제공하면 먼 지역 사용자마다 지연이 크다. 또한 한 리전이 차면 서비스 전체가 느려진다.

Configure content and service distribution은 요청을 가까운 곳에서 처리하게 해 이 문제를 없앤다.

#2핵심 질문

사용자가 사는 곳과 가까운 곳에서 콘텐츠와 API를 전달하려면 어떻게 하나?

#3동작 예시

사용자가 서울에서 S3의 이미지 주소를 요청한다. Amazon CloudFront가 가까운 엣지에서 캐시된 파일을 즉시 준다.

S3까지 갔다 오지 않으므로 첫 응답이 짧아지고, 원본 S3로 들어오는 요청 수는 크게 줄어든다.

#4동작 과정

  1. 배포를 만든다Amazon CloudFront에서 원본(S3 버킷이나 API)을 지정해 배포를 만든다. 사용자에게 가까운 엣지에서 파일을 캐시해 건넨다.
  2. API까지 앞세운다API도 같은 방식으로 배포해 엣지에서 캐시 가능한 응답은 처리한다.
  3. 경로를 고정한다AWS Global Accelerator를 쓰면 고정 IP로 모든 리전의 엔드포인트에 빨리 연결시켜 줄인다. DDoS 완화와 오버로드 보호는 CloudFront 기본 기능으로 함께 켜진다.
  4. 확인해 볼 것CloudFront 콘솔에서 배포 상태가 Deployed로 나오고, 캐시 적중률 지표가 기록되는지 확인한다.

12. 도메인 5 태스크 3 — 네트워크 연결 문제 해결12-01

VPC 구성 문제 해결

서브넷·라우팅 테이블·게이트웨이 등 VPC 안에서 통신이 끊기는 원인을 찾아 설정 오류를 고치는 일.

먼저 알아야 할 것 11-01

#1문제 상황

VPC 안에서 인스턴스가 인터넷이나 다른 서브넷으로 갑자기 닿지 못하면 어디서 막혔는지 알 수 없다(→ 11-01). 통신은 서브넷, route tables, network ACLs, security groups, transit gateways, NAT gateways 를 차례로 지나간다. VPC configuration troubleshooting 은 이 중 어느 문이 잠겨 있는지 찾아 여는 일이다. VPC Reachability Analyzer 는 두 끝점 사이 경로를 훑어 막힌 지점을 짚어 준다.

#2핵심 질문

두 리소스 사이의 통신이 막혔을 때 어느 구성 요인이 그를 막고 있는가?

#3동작 예시

서브넷에 있던 웹 서버가 주문 API를 호출하지 못해_orders가 쌓인다. 관리자는 인스턴스에 SSH로 들어가 curl을 돌리고 VPC Reachability Analyzer에 두 리소스를 넣어 본다. 경로 중 internet gateway 앞 단계가 차단된 것으로 나온다.

#4동작 과정

  1. 끝점을 정한다통신이 안 되는 출발 리소스와 도착 리소스를 먼저 확정한다. VPC Reachability Analyzer 로 경로 상 어느 지점까지 도달하는지 본다.
  2. 문 하나씩 연다security groups 규칙에서 출발·도착·포트, network ACLs 의 Inbound·Outbound 규칙 순으로 확인한다. route tables 의 라우트 대상이 NAT gateways 나 internet gateway 를 향하는지 본다.
  3. 전환점을 본다transit gateways 를 거치는 경로라면 다른 VPC 와의 연결 상태를 함께 본다. 고친 뒤 같은 경로를 다시 분석해 막혔던 지점이 사라졌는지 본다.
  4. 확인해 볼 것VPC Reachability Analyzer 결과에서 차단으로 표시된 문이 사라지고, 이전에 닿지 않던 두 리소스 사이에 통신이 성립하는지 확인한다.

#5한 줄 요약

VPC 구성 문제 해결서브넷부터 라우팅·보안 문까지 이어진 경로에서 막힌 지점을 찾아 여는 것

12. 도메인 5 태스크 3 — 네트워크 연결 문제 해결12-02

네트워크 로그 수집과 해석

VPC Flow Logs 같은 접속 기록을 모았다가 어느 지점에서 통신이 막혔는지 읽어내는 작업.

먼저 알아야 할 것 12-01

→ 12-01 참조

#1문제 상황

트래픽이 안 나간다는 사실은 알지만 그 통신이 어디까지 갔는지는 설정 화면에 남지 않는다. 그래서 정체를 세우려면 VPC 안의 통신 기록을 남겨야 한다.

네트워크 로그 수집과 해석은 VPC flow logs 를 남기고 읽는 일이다. 흐름이 끊긴 지점을 짚을 수 있고, 앞 항목의 설정 문제(→ 12-01)와 짝을 이룬다.

#2핵심 질문

이 통신 기록에서 어디서 흐름이 끊겼는지 어떻게 읽어내는가?

#3동작 예시

유량 급증으로 외부 호출이 느려졌다. 운영자는 VPC flow logs 를 CloudWatch Logs로 보내 두고 실패한 요청의 출발·도착 IP 를 찾는다. ACCEPT 다음 REJECT 가 반복되는 줄이 두 서브넷 사이에서만 나타난다.

#4동작 과정

  1. 기록을 켠다VPC flow logs 로 서브넷과 VPC 수준에서 통과·거부된 흐름을 남긴다. cloud watch logs 로 보내 시간순으로 모은다.
  2. 나머지 층도 모은다ELB access logs 로 부하 분산 상태를, AWS WAF web ACL logs 로 차단된 요청을 본다. CloudFront logs 로 오리진 도달 여부를 확인한다.
  3. 막힌 지점을 짚는다같은 5분 구간에서 API 요청만 실패한다면 reject 난 흐름이 어느 지점에서 시작되는지 읽는다. container logs 를 겹쳐 보면 애플리케이션이 실제로 시도했는지도 확인된다.
  4. 확인해 볼 것로그에서 REJECT 가 시작되는 첫 줄의 출발·도착 항목이 어느 서브넷인지 확인한다.

#5한 줄 요약

네트워크 로그 수집과 해석통과와 거부가 남은 기록을 시간순으로 읽어 흐름이 끊긴 지점을 좁히는 것

12. 도메인 5 태스크 3 — 네트워크 연결 문제 해결12-03

CloudFront 캐시 문제

CDN(웹 콘텐츠를 가까운 곳에서 대신 내려주는 서버망)이 오래된 파일이나 잘못된 파일을 계속 내보내 캐시 설정을 바로잡는 일.

먼저 알아야 할 것 12-02

→ 12-02 참조

#1문제 상황

S3 에서 이미 이미지를 교체했는데 방문자는 예전 파일을 본다. 배포는 성공했는데 사용자는 CDN(웹 콘텐츠를 가까운 곳에서 대신 내려주는 서버망)이 옛 사본을 계속 내보내고 있어서다(→ 11-07).

CloudFront caching issue 식별과 복구는 Amazon CloudFront 가 언제 오리진에 새로 물어보고 언제 옛 사본을 되풀이하는지 다시 맞추는 일이다.

#2핵심 질문

CloudFront 가 오래된 내용을 내보내는 원인을 어떻게 찾아 고치는가?

#3동작 예시

전체 사이트를 새로 올렸는데 절반 방문자에게 예전 배너가 보인다. 운영자는 해당 파일의 캐시 정책과 헤더 설정을 본다. 오리진은 새 파일을 내보내는데 캐시 정책이 캐시를 너무 오래 두도록 되어 있다.

#4동작 과정

  1. 누가 내보내는지 확인한다CloudFront logs 에서 어떤 엣지 위치가 어떤 파일을 언제 내보냈는지 본다. 요청이 리다이렉트되어 엣지 밖으로 나간 경우도 함께 확인한다.
  2. 만료 규칙을 본다캐시 정책의 TTL 과 Cache-Control 헤더를 확인해 오리진 갱신 시점보다 캐시가 오래 남는지 살핀다. 파일 키 구분 방식이 배포 구조와 맞지도 본다.
  3. 무효화한다고친 뒤 해당 경로의 캐시를 무효화해 새 파일이 당겨지도록 한다.
  4. 확인해 볼 것이전에 오던 URL을 다시 열어 새 파일이 내려가는지 확인한다.

#5한 줄 요약

CloudFront 캐시 문제 해결엣지 위치별 내보내기 기록을 읽고 만료 규칙과 무효화로 옛 사본이 돌지 않게 하는 것

하이브리드 연결과 사설 연결 문제

온-premises 사내망과 AWS, 또는 사내 데이터센터끼리전용선과 전용선 게이트웨이(Direct Connect)로 잇는 회선이 끊기거나 느려지는 원인을 찾는 일.

먼저 알아야 할 것 12-02

→ 12-03 참조

#1문제 상황

사내망에서 올라오는 주문 데이터가 특정 시간대만 느려진다. VPC 안 설정은 멀쩡한데 문제는 온-premises(사내 데이터센터)와 클라우드를 잇는 구간에 있을 수밖에 없다.

하이브리드·다중 VPC 환경의 문제는 VPN 터널 상태와 회선 단절 지점을 확인해 좁힌다. 12-02의 로그 해석이 앞단 조사가 된다.

#2핵심 질문

사내 데이터센터와 AWS 사이의 사설 연결이 끊기거나 느려지는 원인을 어디서 찾는가?

#3동작 예시

새벽 3시에만 배치 작업이 느려진다. 운영자는 VGW(전용선 게이트웨이) 뒤의 VPN 연결 상태를 확인해 세션이 반복해서 재설정되는 것을 본다. 동시에 Direct Connect 회선의 가상 인터페이스 상태도 본다.

#4동작 과정

  1. 어느 구간인지 나눈다연결이 끊겼는지 느린 것인지 먼저 구분한다. 회선 계층과 VPN 터널 계층을 따로 본다.
  2. 설정과 경로를 확인한다VPN 터널의 사전 공유 키와 라우팅이 온-premises 쪽 대역으로 가는지 대조한다. Direct Connect 를 쓴다면 가상 인터페이스가 활성 상태인지 본다.
  3. 경계 쪽을 본다사설 연결이 서브넷 간 Security Group 과 라우팅_TABLE 단계에서 막히지 않았는지 함께 확인한다.
  4. 확인해 볼 것터널 상태 화면에서 연결이 살아 있는지, 마지막 재설정 시점이 언제인지 확인한다.

CloudWatch 네트워크 모니터링

CloudWatch 지표와 경보로 네트워크 처리량·오류율·연결 상태를 주기적으로 확인해 이상 징후를 미리 잡아내는 활동.

먼저 알아야 할 것 12-04

→ 12-04 참조

#1문제 상황

사용자가 불평하기 전까지 네트워크가 어떤 상태였는지는 아무도 모른다. 그래프와 알람이 있으면 이상 징후가 쌓이는 시점에 바로 알 수 있다(→ 02-01).

CloudWatch network monitoring 구성과 분석은 이런 확인을 주기적으로 돌리는 일이다.

#2핵심 질문

네트워크의 처리량과 오류율이 평소와 다른지는 어디에서 확인하는가?

#3동작 예시

평소보다 외부 유입량이 갑자기 늘었다. 운영자는 CloudWatch 대시보드에서 NAT 게이트웨이의 아웃바운드 처리량 그래프를 확인하고, 오류율이 기준을 넘자 알람이 온 것을 본다.

#4동작 과정

  1. 볼 대상을 고른다Amazon CloudWatch 에서 VPC 유입·유출 바이트, NAT 게이트웨이 처리량, 로드 밸런서의 대상 상태 같은 네트워크 지표를 본다.
  2. 비교 기준을 정한다지표를 정상 구간과 겹쳐 보고 어느 시점에 틀어났는지 본다.
  3. 알람으로 미리 알린다임계값이 넘는 구간에 알람을 걸어 사람이 보기 전에 알림을 받게 한다.
  4. 확인해 볼 것대시보드에서 평소 구간과 다른 폭이 보이는 네트워크 지표 하나를 골라 그 시점을 확인한다.
