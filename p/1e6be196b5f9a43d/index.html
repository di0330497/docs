1Helm이 무엇이고 어떻게 동작하는가Chart·Repository·Release라는 세 어휘와 클라이언트 전용 아키텍처를 모르면 이후 모든 명령의 의미가 안 잡힌다52남이 만든 차트 가져다 쓰기차트를 직접 만들기 전에 소비자 입장의 전체 왕복(찾기→설치→확인→삭제)을 먼저 겪어야 저작의 목적이 보인다63릴리스 수명주기 다루기업그레이드·롤백·대기·적용 방식은 설치를 아는 상태에서만 이해되고, 실무 운영의 대부분을 차지한다64차트의 구조템플릿 문법을 배우기 전에 그 문법이 담기는 파일과 메타데이터의 자리를 먼저 알아야 한다65템플릿 언어의 기본기차트 저작의 심장. 객체·함수·흐름제어·명명 템플릿은 이후 모든 저작 항목의 문법 전제다86템플릿으로 실제 차트 완성하기문법을 안 뒤에야 스키마 검증·파일 임베딩·API 호환·디버깅 같은 실제 저작 작업이 의미를 갖는다67차트를 조합하기: 의존성과 서브차트단일 차트를 만들 수 있게 된 다음에야 여러 차트를 엮는 규칙(스코프·global·조건)이 필요해진다68배포 시점 제어: 훅, 테스트, CRD차트가 렌더되는 것과 클러스터에 적용되는 순서는 다른 문제다. 리소스를 다 만들 줄 안 뒤에 순서를 배운다69차트를 패키징하고 배포하기내 차트가 완성된 다음의 문제. 저장소·레지스트리·서명은 남에게 넘기는 순간에만 필요하다610확장과 운영기본 워크플로가 손에 익은 뒤에 붙이는 것들. 플러그인·후처리·저장 백엔드·권한은 전부 선택적 확장이다611잘 만든 차트의 규칙만들 줄 아는 사람에게만 의미가 있는 규범. 공개 배포를 염두에 둔 마지막 다듬기다312코드로서의 Helm과 이행CLI 사용자를 넘어설 때만 필요한 마무리. 1Helm이 무엇이고 어떻게 동작하는가01-01

쿠버네티스 매니페스트 관리의 문제와 Helm이 내놓은 답

수십 개의 YAML 매니페스트를 환경마다 복사·수정하던 문제를, Helm은 값으로 조립되는 하나의 패키지로 묶어 해결한다.

1상대의 출발점 확인

쿠버네티스에 애플리케이션을 배포할 때 YAML 매니페스트 파일이 필요하다. 개발, 스테이징, 프로덕션 환경에는 레플리카 수, 이미지 버전, 리소스 제한 같은 값만 다르고 구조는 같은 매니페스트가 여러 개 필요하다. 기존에는 각 환경마다 YAML 파일을 복사한 후 값을 직접 수정하는 방식을 썼는데, 환경이 많고 개별 설정이 복잡할수록 파일 관리와 버전 추적이 어려워진다.

2질문 제기

환경마다 다른 값들을 효율적으로 관리하면서도 코드 중복을 없애고 배포를 표준화하려면?

3구조적 핵심 예시

Helm은 YAML 파일을 템플릿으로 만들고 변수를 심어둔다. 그 변수에 환경별로 다른 values.yaml 파일을 연결해 렌더링하면, 한 세트의 템플릿으로 모든 환경의 최종 매니페스트가 생성된다.

4단계별 동작 과정

  1. 템플릿 작성YAML 매니페스트 안의 고정 부분은 그대로 두고, 바뀌어야 할 부분(예: replicas, image tag)을 {{ .Values.변수명 }} 형태로 변수화한다.
  2. 값 정의values.yaml 파일에 변수의 기본값을 선언한다.
  3. 병합 및 배포템플릿과 values.yaml을 병합해 최종 YAML을 생성한 뒤 쿠버네티스 클러스터에 적용한다.

5본질 요약

세 가지 핵심 개념 - Chart, Repository, Release

Chart는 배포 패키지, Repository는 차트를 모아둔 저장소, Release는 클러스터에 실제 설치된 차트의 한 인스턴스다.

1상대의 출발점 확인

쿠버네티스 리소스 배포 시 YAML 매니페스트를 직접 작성하고 버전 관리한다. 하지만 같은 애플리케이션을 여러 번 배포하거나 다른 팀과 공유해야 할 때 파일 자체만으로는 충분하지 않다. 배포 단위의 정의, 저장소 접근, 배포 후 상태 추적이 표준화되지 않아 번거롭다.

2질문 제기

배포 패키지를 재사용 가능하게 정의하고, 여러 팀이 공유하며, 설치 이력을 추적하려면?

3구조적 핵심 예시

한 개의 Chart는 하나의 애플리케이션 배포에 필요한 모든 템플릿과 기본값을 담은 패키지다. Repository는 차트들을 모아 두는 저장소(일반 Git 저장소도 가능, 공식 Helm 저장소도 있음)이고, Release는 그 차트를 특정 클러스터에 설치한 인스턴스로, 설치 시점의 values를 기록해둔다.

4단계별 동작 과정

  1. Chart 정의애플리케이션 배포에 필요한 템플릿 파일들과 Chart.yaml(메타데이터), values.yaml(기본값)을 한 디렉토리에 모아 하나의 배포 단위로 정의한다.
  2. Repository에 등록차트들을 저장소에 올려 다른 팀이나 다른 클러스터에서 접근 가능하게 한다.
  3. Release 설치저장소에서 차트를 내려받아 클러스터에 설치하면, Helm은 설치 이력(Release)을 클러스터 내부에 저장해 나중에 업그레이드나 롤백을 할 수 있다.

5본질 요약

배포를 Chart(패키지)로 표준화하고, Repository로 공유하며, Release로 설치 이력을 추적해 재사용 가능한 배포 단위를 만드는 것

1상대의 출발점 확인

Helm과 쿠버네티스는 각각 버전이 올라가며, 특정 Helm 버전이 모든 쿠버네티스 버전을 지원하지는 않는다. Helm 2의 Tiller 제거(Helm 3), 클라이언트 전용 구조 확립(Helm 3), 그리고 Helm 4로의 진화를 거치며 쿠버네티스 API와의 호환성도 변했다.

2질문 제기

어떤 Helm 버전이 어떤 쿠버네티스 버전 범위를 안전하게 지원하는가?

3구조적 핵심 예시

Helm 4는 공식적으로 쿠버네티스 1.26~1.29 범위를 지원하고, 그 이상의 버전은 "지원 범위 밖이지만 작동할 가능성이 높다"는 정책을 따른다. 너무 오래된 쿠버네티스 버전(1.25 이하)은 API 호환성이 떨어져 작동하지 않을 가능성이 높다.

4단계별 동작 과정

  1. 버전 스큐 정책 확인공식 문서의 버전 스큐 정책 페이지에서 각 Helm 버전별로 테스트하고 공식 지원하는 쿠버네티스 버전 범위를 확인한다.
  2. 설치된 버전 확인helm version(클라이언트 버전), kubectl version(클러스터의 쿠버네티스 버전)으로 각각의 버전을 확인한다.
  3. 호환성 판단설치된 Helm과 쿠버네티스 버전이 지원 범위에 포함되는지 확인한다. 범위 밖이면 업그레이드 계획을 세운다.

저장소 등록과 차트 검색

helm repo add 로 차트 저장소를 등록하고 helm search 로 원하는 차트를 찾는 방법이다.

1상대의 출발점 확인

Helm으로 차트를 설치하려면 어디서 차트를 찾는지 알아야 한다. 공식 Helm 저장소(Artifact Hub)에 수많은 차트가 있지만, 로컬에는 아무것도 등록되지 않은 상태다. 차트를 찾고 설치하려면 먼저 저장소를 등록하고 인덱스를 로컬에 내려받아야 한다.

2질문 제기

원하는 차트를 어떻게 찾고, 어느 저장소에서 내려받을 것인가?

3구조적 핵심 예시

helm repo add bitnami https://charts.bitnami.com/bitnami 명령으로 Bitnami 저장소를 로컬에 등록하면, Helm은 그 저장소의 index.yaml을 내려받아 캐시해둔다. 그 후 helm search repo nginx를 실행하면 로컬 캐시에서 nginx를 포함하는 차트 목록을 찾아 보여준다.

4단계별 동작 과정

  1. 저장소 추가helm repo add 명령으로 저장소 이름과 URL(보통 HTTPS 주소)을 등록한다. Helm은 그 저장소의 Chart 메타데이터 인덱스(index.yaml)를 로컬 캐시(~/.cache/helm/repository/)에 내려받는다.
  2. 인덱스 갱신helm repo update를 실행해 모든 등록된 저장소의 인덱스를 최신 상태로 갱신한다.
  3. 차트 검색helm search repo 차트이름으로 등록된 저장소들에서 해당 이름을 포함하는 차트를 검색해 버전, 설명, 저장소 출처를 표시한다.

설치 전에 차트 들여다보기: helm show와 helm pull

helm show 로 차트의 메타데이터·기본값·README 를 미리 보고 helm pull 로 차트 자체를 내려받아 확인하는 단계다.

1상대의 출발점 확인

helm search 명령으로 차트를 찾긴 했지만, 그 차트가 실제로 무엇을 설치하고 어떤 설정 옵션이 있는지 알 수 없다. 저장소에서 바로 설치하면 차트 구조와 기본값을 미리 확인할 기회가 없어서, 설치 후 예상과 다른 리소스가 생기는 경우가 발생할 수 있다.

2질문 제기

차트를 설치하기 전에 그 내용물과 설정 옵션을 미리 어떻게 확인하는가?

3구조적 핵심 예시

helm show values bitnami/nginx는 Bitnami nginx 차트의 기본 values.yaml을 화면에 보여주고, helm show chart bitnami/nginx는 Chart.yaml(차트 메타데이터)을, helm show readme bitnami/nginx는 차트의 README를 보여준다. 더 깊이 들여다보려면 helm pull bitnami/nginx로 차트 전체를 내려받아 로컬에서 직접 확인할 수 있다.

4단계별 동작 과정

  1. 메타데이터와 설명 확인helm show chart와 helm show readme로 차트의 이름, 버전, 설명, 유지보수자, 의존성 정보를 먼저 확인한다.
  2. 기본 설정값 확인helm show values로 차트가 설치할 때 사용하는 모든 기본값(replicas, image 버전, 리소스 제한 등)을 확인하고, 환경에 맞춰 어떤 값들을 오버라이드해야 할지 판단한다.
  3. 전체 차트 내려받기더 자세한 검토가 필요하면 helm pull로 차트 전체(템플릿 파일, values.yaml, Chart.yaml, README 등)를 tar.gz로 내려받아 로컬에서 압축 해제해 모든 파일을 확인한다.

기존에는 쿠버네티스에 배포하려면 매니페스트 파일(YAML)을 직접 작성하고 kubectl apply로 각각 적용했다. 이 방식의 문제는 복잡한 애플리케이션이 수십 개의 리소스(Pod, Service, ConfigMap 등)로 이루어져 있을 때, 모든 파일을 수동으로 관리하고 설치 순서를 맞춰야 하며, 같은 애플리케이션을 여러 클러스터나 네임스페이스에 설치할 때마다 파일을 복사해서 수정해야 한다는 점이다.

2질문 제기

여러 쿠버네티스 리소스를 패키지처럼 한 번에 설치하고, 같은 설정을 다른 네임스페이스나 클러스터에 쉽게 재사용할 수 있는 방법은 없을까?

3구조적 핵심 예시

helm install my-release nginx-stable/nginx 명령 하나로 Nginx 차트가 정의한 Deployment, Service, ConfigMap, Ingress 등 여러 쿠버네티스 리소스가 클러스터에 동시에 생성된다. 이때 "my-release"라는 이름으로 이 설치 단위를 추적하고, 특정 네임스페이스(기본값은 default)에 모든 리소스가 격리되어 생성된다.

4단계별 동작 과정

  1. 차트 로드지정한 차트(예: nginx-stable/nginx)를 Helm 저장소에서 찾거나 로컬에서 읽어 메니페스트 템플릿을 준비한다.
  2. 템플릿 렌더링차트의 values.yaml(기본 설정값)에 따라 템플릿을 처리하여 최종 쿠버네티스 매니페스트 문자열을 생성한다.
  3. 리소스 생성 및 추적최종 매니페스트를 클러스터에 적용하고, "my-release"라는 릴리스 이름과 지정한 네임스페이스 정보와 함께 설치 기록을 Helm 내부에 저장한다.

5본질 요약

리비전과 릴리스 이력

Helm은 설치·업그레이드마다 리비전 번호를 매겨 클러스터에 이력으로 저장하며, helm history로 그 목록을 볼 수 있다.

1상대의 출발점 확인

Helm이 릴리스를 설치하고 나중에 값을 바꿔 업그레이드하면, 클러스터에는 새로운 버전이 적용되지만 이전 상태로 복구해야 할 때 복구하기가 어렵다. 기존에는 변경 이력을 직접 기록하거나 클러스터 스냅샷을 보관하는 방식에만 의존했고, 어떤 설정이 언제 바뀌었는지 추적할 수 없었다.

2질문 제기

Helm으로 설치하고 여러 번 업그레이드할 때, 각 변경 시점의 설정과 리소스 상태를 기록하고 확인하는 방법은?

3구조적 핵심 예시

helm install my-release nginx-stable/nginx로 처음 설치하면 리비전 1이 생성되고, helm upgrade my-release nginx-stable/nginx --set replicas=5로 업그레이드하면 리비전 2가 생성된다. helm history my-release를 실행하면 리비전 1(replicas=1일 때), 리비전 2(replicas=5로 변경된 상태) 등 각 시점의 기록이 표시된다.

4단계별 동작 과정

  1. 리비전 번호 자동 부여설치나 업그레이드할 때마다 Helm이 순차적으로 리비전 번호를 증가시킨다.
  2. 상태 저장각 리비전마다 그 시점의 설정값, 렌더링된 매니페스트, 생성 시간을 Helm 내부 저장소(클러스터 내 Secret이나 ConfigMap)에 저장한다.
  3. 이력 조회helm history 명령으로 모든 리비전의 목록과 상태를 확인할 수 있다.

helm upgrade와 값 재사용 규칙

helm upgrade는 기존 릴리스를 새 리비전으로 갱신하며, --set/-f로 준 값과 이전 값을 --reuse-values·--reset-values 규칙에 따라 합친다.

1상대의 출발점 확인

릴리스를 처음 설치한 후 나중에 업그레이드할 때, 이전의 모든 설정값을 다시 명시해야 하는지, 아니면 명시하지 않은 값은 차트의 기본값으로 되돌아가는지 혼동하기 쉽다. 예를 들어 처음 설치할 때 --set replicas=3을 붙였는데, 이미지 버전만 업그레이드하려고 --set image.tag=1.25.1만 붙이면 replicas가 기본값 1로 되돌아갈 수 있다. 이는 의도치 않은 설정 변경을 초래한다.

2질문 제기

릴리스를 업그레이드할 때 이전 설정값을 유지할지, 새로 지정한 값만 적용할지 제어하는 방법은?

3구조적 핵심 예시

helm install my-release nginx --set replicas=3 --set resources.requests.memory=512Mi로 설치한 후, 나중에 helm upgrade my-release nginx --set image.tag=1.25.1 --reuse-values를 실행하면 이전의 replicas=3과 resources.requests.memory=512Mi는 유지되면서 image.tag만 1.25.1로 변경된다. 반대로 --reset-values 옵션을 쓰면 이전 설정을 모두 무시하고 새로 지정한 값과 차트의 기본값만 적용된다.

4단계별 동작 과정

  1. 이전 릴리스 정보 조회업그레이드 대상 릴리스의 이전 리비전에서 적용되었던 값들을 조회한다.
  2. 값 병합 규칙 적용--reuse-values면 이전 값과 새로 지정한 값을 합치거나(충돌하면 새로운 값이 우선), --reset-values면 이전 값을 모두 버리고 새로운 값과 차트 기본값만 사용한다.
  3. 새 리비전 생성최종 병합된 값으로 템플릿을 렌더링하고 새로운 리비전으로 클러스터에 적용한다.

helm upgrade my-release nginx-stable/nginx --set replicas=10이 실패했을 때, helm rollback my-release 1을 실행하면 릴리스가 리비전 1(이전에 안정적으로 작동하던 상태)로 되돌아가고, 그 리비전의 모든 리소스와 설정값이 복구된다. 또는 처음부터 helm upgrade my-release nginx --set replicas=10 --rollback-on-failure를 붙이면 업그레이드 중 오류가 감지되면 자동으로 이전 리비전으로 되돌아간다.

4단계별 동작 과정

  1. 이전 리비전 검증롤백할 대상 리비전(예: 리비전 1)의 정보를 조회하여 해당 설정과 리소스가 존재하는지 확인한다.
  2. 이전 매니페스트 재적용그 리비전의 렌더링된 매니페스트를 클러스터에 다시 적용한다.
  3. 새 리비전 생성롤백도 하나의 변경 사항이므로 새로운 리비전 번호가 부여되고, 히스토리에 롤백 기록이 남는다.

준비 완료 대기: --wait, --timeout, kstatus

--wait는 생성된 리소스가 실제로 준비 상태가 될 때까지 Helm이 기다리게 하고, --timeout은 그 대기 한도를 정한다.

→ 03-03 참조

1상대의 출발점 확인

Helm이 매니페스트를 API 서버에 제출하면 즉시 "배포 완료"로 보고되지만, 쿠버네티스가 실제로 Pod를 생성하고 준비 상태에 도달하는 과정은 비동기적으로 진행된다. 따라서 명령이 완료되어도 애플리케이션이 아직 시작되지 않았거나, 준비 프로브(readiness probe)를 통과하지 못했을 수 있다.

2질문 제기

쿠버네티스가 실제로 리소스를 준비할 때까지 Helm이 반환되지 않도록 하려면 어떻게 해야 할까?

3구조적 핵심 예시

Helm이 --wait 플래그로 Pod가 Running 상태가 되고 준비 프로브를 통과할 때까지 기다리며, --timeout으로 최대 대기 시간을 제한하고, kstatus라는 상태 확인 라이브러리가 각 리소스 타입(Pod, Deployment, StatefulSet 등)의 준비 조건을 확인하는 방식으로 동작한다.

4단계별 동작 과정

  1. --wait 플래그 활성화helm install 또는 helm upgrade에서 --wait를 지정하면, Helm이 매니페스트를 제출한 후 즉시 반환하지 않고 대기 상태로 진입한다.
  2. --timeout으로 대기 시간 한계 설정무한 대기를 방지하기 위해 --timeout 값(예: 5m)을 설정하면, 그 시간 내에 준비가 완료되지 않을 경우 오류로 종료한다.
  3. kstatus로 준비 완료 판단Helm이 각 리소스의 현재 상태를 주기적으로 확인하고, 모든 Pod가 Ready 상태이고 Deployment의 desired replica 개수가 ready 상태에 도달하면 완료로 인정한다.

Server-Side Apply와 리소스 소유권

매니페스트 적용을 API 서버가 필드 단위로 병합하게 해, 어떤 도구가 어느 필드를 소유하는지 관리하는 방식이다.

1상대의 출발점 확인

Helm이 매니페스트를 적용할 때 전체 문서를 한 덩어리로 취급하므로, 다른 도구(예: 자동 스케일러, 모니터링 에이전트)나 사용자가 같은 쿠버네티스 리소스의 특정 필드를 수정하면 충돌이 발생한다. 어느 도구가 어느 필드를 책임지는지 관리 체계가 없어서 예상치 못한 변경이 일어난다.

2질문 제기

3구조적 핵심 예시

API 서버가 매니페스트를 필드 단위로 분석하고, 각 필드마다 "누가 마지막으로 이 필드를 변경했는가"를 기록하는 ManagedFields(관리 필드) 메타데이터를 유지하므로, Helm은 차트가 정의한 필드만 소유하고, 다른 컨트롤러는 자신이 관리하는 필드만 수정하는 구조로 분리된다.

4단계별 동작 과정

  1. Server-Side Apply 방식 전환Helm이 kubectl apply --server-side와 동일한 메커니즘을 사용하여 매니페스트를 API 서버에 제출한다.
  2. 필드 단위 소유권 추적API 서버가 각 필드마다 관리 필드(ManagedFields) 항목을 생성해서, 어느 도구가 마지막으로 변경했는지 기록하고, 필드별 충돌 여부를 판단한다.
  3. 충돌 감지 및 병합 처리같은 필드를 여러 도구가 수정하려 하면 API 서버가 충돌을 보고하고, 관리되지 않는 필드는 자동으로 병합된다.

Chart.yaml에 반드시 있어야 하는 apiVersion·name·version 세 필드와, version이 따라야 하는 SemVer 2 규칙을 다룬다.

3구조적 핵심 예시

Chart.yaml에 description(사람이 읽을 수 있는 용도 설명), type(Application·Library 구분), appVersion(배포되는 소프트웨어 버전), kubeVersion(쿠버네티스 최소·최대 버전 범위), deprecated(지원 종료 여부) 같은 선택 필드를 기록해서, 사용자는 한눈에 차트의 특성과 호환 범위를 파악하고, 자동 도구는 설치 가능 여부와 마이그레이션 필요성을 판단한다.

4단계별 동작 과정

  1. description과 type으로 차트의 성격 표시description 필드에 "PostgreSQL database" 같은 간단한 설명을 기록하고, type: Application(실제 애플리케이션을 배포하는 차트)·type: Library(다른 차트가 포함해서 사용할 헬퍼)로 역할을 구분하므로, 검색 결과에서 사용자가 필요한 차트를 빠르게 찾을 수 있다.
  2. appVersion과 kubeVersion으로 호환성 범위 정의appVersion은 차트가 배포하는 소프트웨어의 버전(예: appVersion: 14.5는 PostgreSQL 14.5를 배포함을 의미)이고, kubeVersion: >=1.21.0-0 <1.30.0 같은 조건을 기록해서, 현재 클러스터 버전과 비교할 수 있다.
  3. deprecated로 생명주기 관리deprecated: true를 설정하면, 차트 저장소와 Helm 클라이언트가 이 버전의 차트가 더 이상 유지보수되지 않음을 표시하고, 사용자는 다른 차트로 마이그레이션 계획을 세울 수 있다.

values.yaml과 값이 만들어지는 계층

차트 기본값 values.yaml 위에 사용자 파일과 --set 값이 겹쳐지며 최종 값이 결정되는 우선순위 구조다.

1상대의 출발점 확인

Helm 템플릿에서 값을 참조할 때, 여러 출처(기본값, 사용자 파일, 명령줄 옵션)가 있으면 어느 것이 최종 결정될지 불명확해서, 예상과 다른 결과가 배포된다. 값의 우선순위 규칙이 명확하지 않으면 설정 중복과 충돌이 발생한다.

2질문 제기

Helm 차트의 기본값, 사용자가 제공한 파일, 명령줄 옵션이 충돌할 때 어느 것이 최종 결정될까?

3구조적 핵심 예시

values.yaml(차트 제작자의 기본값, 예: replicaCount: 1) → -f custom.yaml(사용자 파일, 예: replicaCount: 3) → --set key=value(명령줄 옵션, 예: --set replicaCount=5) 순서로 겹쳐지면서, 뒤의 값이 앞의 값을 덮어쓰는 계층 구조로 최종값 replicaCount: 5가 결정된다.

4단계별 동작 과정

  1. 차트의 기본값(values.yaml) 로드Helm이 차트 내부의 values.yaml을 먼저 읽어서 모든 기본값(replicaCount: 1, image.repository: nginx 등)을 메모리에 로드한다.
  2. 사용자 파일과 --set 옵션으로 값 덮어쓰기helm install -f custom.yaml은 YAML 파일을 읽어서 기본값 위에 병합하고, --set 플래그(helm install --set key=value)는 각 플래그마다 지정한 값으로 덮어써서, 최종 값을 구성한다.
  3. 최종 값으로 템플릿 렌더링모든 우선순위를 거쳐 결정된 값들을 모아서 .Values 변수로 템플릿에 전달하고, Helm이 템플릿 내의 모든 {{ .Values.replicaCount }}, {{ .Values.image.repository }} 같은 참조를 실제 값으로 치환한다.

4단계별 동작 과정

  1. CRD 설치쿠버네티스 클러스터에 새로운 리소스 타입을 정의하는 CRD를 먼저 등록한다. 이를 통해 나중에 올 다른 매니페스트들이 이 리소스 타입을 참조할 수 있다.
  2. 서브차트 설치charts/ 폴더의 종속 차트들을 설치한다. 부모 차트의 값을 일부 상속받으면서 독립적으로 동작한다.
  3. 메인 매니페스트 설치 및 안내 출력templates/ 폴더의 YAML 파일들이 렌더링되어 쿠버네티스에 배포되고, NOTES.txt의 내용이 설치 완료 메시지로 출력된다.

  3. .Chart 사용차트 메타데이터 접근. (예: {{ .Chart.Name }}, {{ .Chart.Version }})

값을 함수에 넘기거나 | 로 이어 가공하는 방식이며, 표준 Go 함수에 더해 Sprig 라이브러리의 수백 개 함수를 쓸 수 있다.

1상대의 출발점 확인

기존 방식에서는 템플릿에서 기본적인 값 대입만 할 수 있었다. 문자열을 대문자로 변환, 리스트를 정렬, 기본값 채우기 같은 데이터 가공은 별도 처리가 필요했다. 간단한 변형도 템플릿 외부에서 처리해야 하므로 템플릿 재사용성과 독립성이 떨어졌다.

2질문 제기

템플릿 안에서 값을 직접 가공하고 변형할 수 있는 방법이 있을까?

3구조적 핵심 예시

함수를 사용하거나 파이프라인(|)으로 여러 함수를 연결한다. 표준 Go 함수와 Sprig 라이브러리의 수백 개 함수(문자열 처리, 리스트 조작, 수학 연산 등)를 활용할 수 있다.

4단계별 동작 과정

  1. 함수 호출{{ default "replica: 1" .Values.replicas }} 처럼 함수명 뒤에 인자를 전달한다.
  2. 파이프라인 연결{{ .Values.name | upper | quote }} 처럼 | 로 여러 함수를 순서대로 연결한다. 왼쪽 결과가 오른쪽 함수의 입력이 된다.
  3. Sprig 함수 활용표준 Go 함수 외에 Sprig 라이브러리가 추가 함수를 제공해 더 복잡한 데이터 처리를 템플릿 내에서 처리한다.

5본질 요약

함수와 파이프라인으로 값을 템플릿 내에서 직접 가공하고, Sprig 라이브러리의 다양한 함수로 복잡한 변형을 처리하는 것

1상대의 출발점 확인

기존 방식에서는 Sprig 라이브러리가 수백 개의 함수를 제공하는데, 실무에서는 정해진 몇 가지만 반복해서 썼다. 이 함수들의 용도를 명확히 알지 못하면 매번 문서를 찾아야 했다. 흔하지 않은 함수까지 다 배우면 시간낭비고, 필수 함수를 정확히 아는 것이 먼저였다.

2질문 제기

실무에서 반복적으로 나타나는 핵심 함수들은 무엇이고, 각각 언제 쓰는가?

3구조적 핵심 예시

default는 값이 없을 때 기본값 채우기, quote는 문자열을 큰따옴표로 감싸기(YAML 문법 안전), required는 값이 반드시 있어야 함을 강제, toYaml은 맵이나 리스트를 YAML 형식으로 변환, tpl은 문자열 값을 다시 템플릿으로 해석, lookup은 클러스터에서 이미 생성된 리소스 조회한다.

4단계별 동작 과정

  1. 기본값 및 필수값 처리default로 누락된 값을 채우고, required로 반드시 입력되어야 할 값을 체크한다. (예: {{ required "name is required" .Values.name }})
  2. 문자열 안전성quote로 따옴표를 붙여 YAML 파싱 오류 방지한다. (예: {{ .Values.username | quote }})
  3. 구조체 변환 및 고급 처리toYaml로 객체를 YAML로 변환, tpl로 템플릿 내용을 재평가, lookup으로 기존 클러스터 상태를 확인한다.

5본질 요약

값 검증, YAML 안전성, 구조체 변환, 클러스터 상태 조회 등 실무에서 자주 필요한 작업을 미리 만들어둔 함수들을 통해 템플릿을 더 견고하고 유연하게 만드는 것

흐름 제어와 변수

조건 분기(if/else), 범위 축소(with), 반복(range)으로 매니페스트를 동적으로 만들고, 변수와 루트 컨텍스트 $ 로 스코프 문제를 푼다.

1상대의 출발점 확인

Kubernetes 매니페스트는 정적인 YAML 파일이다. 조건에 따라 필드를 다르게 설정하거나 같은 구조를 반복해야 할 때는, 수동으로 여러 파일을 만들고 관리해야 한다.

2질문 제기

조건과 반복에 따라 매니페스트 내용을 동적으로 바꾸려면 어떻게 할까?

3구조적 핵심 예시

템플릿에서 {{ if .Values.tls.enabled }} 라고 쓰면, 사용자가 values.yaml에서 tls.enabled: true로 설정했을 때만 그 블록 내의 YAML이 최종 매니페스트에 포함된다.

4단계별 동작 과정

  1. 조건 검사if .Values.조건명 문법으로 참/거짓을 판단하고, else 나 else if 로 다른 경로를 지정할 수 있다.
  2. 범위 축소with .Values.database 라고 쓰면 그 블록 내에서 현재 스코프(컨텍스트)가 database 객체로 바뀌고, 안에서는 .port 처럼 더 간단하게 접근할 수 있다. $ 를 쓰면 루트로 돌아갈 수 있다.
  3. 반복 생성range .Values.replicas 나 range $index, $value := .Values.items 처럼 리스트를 순회하면서 각 항목에 대한 YAML 블록을 여러 번 생성한다.

5본질 요약

템플릿 안에 조건·반복·스코프 변경 문법을 넣어, 같은 템플릿 코드로 여러 형태의 최종 매니페스트를 만들어내는 것

명명 템플릿

반복되는 조각을 define 으로 이름 붙여 두고 include/template 으로 재사용하며, 관례상 _helpers.tpl 에 모아 둔다.

1상대의 출발점 확인

큰 차트에서는 deployment.yaml, service.yaml, configmap.yaml 등 템플릿 파일이 많아진다. 각 파일 안에서 레이블 설정, 보안 설정, 환경 변수 등 비슷한 코드 조각이 반복된다. 한 줄만 바꾸려면 여러 파일을 열어야 한다.

2질문 제기

반복되는 YAML 조각을 한곳에 모아 두고 여러 템플릿에서 재사용할 수 있을까?

3구조적 핵심 예시

_helpers.tpl 파일에 {{- define "mychart.labels" }} 라고 정의해 두고, deployment.yaml에서 {{ include "mychart.labels" . }} 라고 쓰면 그 자리에 정의된 템플릿 코드가 삽입된다.

4단계별 동작 과정

  1. 이름 붙여 정의define "이름" }}...{{ end }} 로 재사용할 YAML 블록을 이름 붙여 저장해 둔다. 관례상 _helpers.tpl 파일에 모은다.
  2. 호출과 삽입include "이름" . 로 정의된 템플릿을 호출하고, 현재 스코프 . 를 건넨다. 호출한 자리에 그 템플릿의 결과 코드가 삽입된다.
  3. 독립적 재사용같은 이름 붙은 템플릿은 deployment, service, configmap 등 어디서나 호출할 수 있으므로, 공통 설정을 한 곳에서만 관리하면 된다.

5본질 요약

반복되는 YAML 조각을 define으로 이름 붙여 두고 include나 template로 재사용하면서, 공통 로직을 한곳에서 관리하는 것

Go 데이터 타입과 YAML의 함정

문자열·숫자·불리언·맵·리스트 같은 타입 차이와, 따옴표·들여쓰기·yes/no 해석 등 YAML 특유의 실수 지점을 이해한다.

1상대의 출발점 확인

Helm 템플릿은 Go 언어로 동작하고, 최종 결과는 YAML 형식이다. Go의 타입(문자열, 숫자, 불리언, 맵, 리스트) 체계와 YAML의 타입 해석 규칙이 다르면, 예상과 달리 매니페스트가 생성된다. 예를 들어 port: 8080 은 숫자지만, 문자열로 감싸지 않으면 따옴표 여부에 따라 정수 또는 문자열로 읽힐 수 있다.

2질문 제기

Go 템플릿 언어에서 다룬 데이터가 YAML로 변환될 때 올바르게 해석되려면 무엇에 주의해야 할까?

3구조적 핵심 예시

{{ .Values.port }} 가 Go에서는 정수 8080이지만, YAML에 port: 8080 으로 나오면 kubectl은 이를 정수로 읽는다. 그런데 {{ .Values.enabled }} 가 Go boolean true라면 YAML에 enabled: true 로 나가는데, YAML 파서가 yes, no, true, false 등을 불리언으로 해석하는지 여부가 결정되는 것이다.

4단계별 동작 과정

  1. Go 타입 이해템플릿 안에서 .Values 로 가져온 값은 Go의 string, int, bool, map, slice 타입으로 유지되며, 함수나 연산자는 이 타입을 기준으로 동작한다.
  2. YAML 직렬화템플릿 엔진이 Go 값을 YAML 텍스트로 변환할 때, 숫자는 따옴표 없이 출력되고, 문자열은 따옴표로 감싸거나 멀티라인으로 표시된다. 불리언이나 null 도 YAML 특정 형식으로 변환된다.
  3. 파싱 주의점YAML 수신자(kubectl, kubelet, API 서버)가 yes, no, on, off, true, false 를 어떻게 읽는지, 들여쓰기나 스칼라(scalar) 스타일이 의미를 바꾸는지 염두에 두고, 필요하면 quote 나 toJson 같은 함수로 명시적으로 형식을 정해야 한다.

5본질 요약

Go 타입과 YAML 표현 사이의 격차를 이해하고, 필요시 타입 변환 함수를 써서 의도한 데이터 형식이 최종 매니페스트에 올바르게 반영되도록 하는 것

values 파일 설계와 접근 패턴

차트의 설정값을 values.yaml에 두고 템플릿에서 .Values로 꺼내 쓰는 기본 구조와, 값 이름·기본값·중첩 깊이를 정하는 요령.

1상대의 출발점 확인

초기에는 매니페스트 파일을 하드코딩해서 쓴다. 다른 환경(개발, 스테이징, 운영)에 배포할 때마다 파일을 복사해서 값을 수정하거나, 여러 버전을 관리해야 한다. 어떤 값이 바뀔 수 있는지 알기 어렵고, 템플릿과 설정값이 분리되지 않는다.

2질문 제기

매니페스트의 설정값을 템플릿과 분리해서 관리하고, 사용자가 쉽게 바꿀 수 있는 구조는 어떻게 만들까?

3구조적 핵심 예시

values.yaml 파일에 replicaCount: 3, image.tag: latest, service.port: 80 등 모든 설정값을 담아 두고, 템플릿에서는 {{ .Values.replicaCount }} 처럼 접근한다. 설치할 때 helm install --values custom-values.yaml 로 다른 값 파일을 넘기면, 그 값이 기본값을 덮어쓴다.

4단계별 동작 과정

  1. 설정값 구조 설계비슷한 설정끼리 묶어 중첩된 맵 구조로 만든다. 예: image.repository, image.tag, image.pullPolicy 는 모두 image 아래에 둔다. 기본값을 설정하고, 주석으로 의미를 남긴다.
  2. 템플릿에서 접근{{ .Values.설정.경로 }} 형태로 값을 읽고, 기본값 지정이 필요하면 {{ .Values.key | default "기본값" }} 처럼 쓴다.
  3. 사용자 입력 반영설치 시 -f user-values.yaml 옵션이나 --set key=value 플래그로 사용자가 넘긴 값이 기본 values.yaml과 병합되어 템플릿에 전달된다.

5본질 요약

설정값을 values.yaml에 체계적으로 모아 두고, 템플릿에서 .Values로 접근하게 함으로써 코드와 설정을 분리하고 재사용성을 높이는 것

values.schema.json으로 값 검증하기

JSON Schema 파일을 차트에 넣어 사용자가 넘긴 값의 타입·필수 여부·범위를 설치 전에 자동으로 검사하는 방법.

→ 06-01 참조

1상대의 출발점 확인

사용자가 values.yaml을 작성하거나 --set 플래그로 값을 넘길 때, 잘못된 타입(문자열 대신 숫자, 필수값 누락 등)이나 범위 밖의 값(음수 개수, 유효하지 않은 모드)을 지정할 수 있다. 이 오류는 Kubernetes 리소스 생성 시점에나 실행 중에 드러나, 문제 추적이 어렵다.

2질문 제기

사용자가 차트를 설치하기 전에, 넘긴 값의 타입·필수 여부·범위가 올바른지 미리 검사할 수 있을까?

3구조적 핵심 예시

values.schema.json 파일에 JSON Schema 형식으로 replicaCount 는 정수이고 1 이상이어야 한다, image.pullPolicy 는 "Always", "IfNotPresent", "Never" 중 하나여야 한다는 규칙을 써 두면, helm install 이나 helm lint 실행 시 이 규칙에 맞는지 자동으로 검사하고 위반하면 오류를 낸다.

4단계별 동작 과정

  1. 스키마 정의JSON Schema 문법으로 각 값의 type, required 여부, minimum/maximum, enum (선택지 목록) 등을 명시한다.
  2. 설치 전 검증helm install, helm upgrade, helm lint 명령어가 스키마를 읽어 사용자가 넘긴 값(values.yaml, --set 플래그)과 비교하고, 위반하면 설치를 중단하고 오류 메시지를 출력한다.
  3. 명확한 피드백어느 필드가 잘못되었고, 어떤 타입·범위가 필요한지 알려줌으로써 사용자가 빠르게 고칠 수 있게 한다.

5본질 요약

차트 안의 설정 파일이나 스크립트를 .Files 객체로 읽어 ConfigMap 같은 매니페스트에 그대로 담는 방법.

1상대의 출발점 확인

애플리케이션 설정 파일(설정값, 인증서, 스크립트 등)을 Kubernetes에 배포할 때, 그 내용을 values.yaml에 문자열로 담거나 ConfigMap 매니페스트에 직접 써 넣어야 한다. 파일이 크거나 멀티라인 포맷(JSON, YAML 등)이면 이스케이프하고 들여쓰기를 맞추기 번거롭다.

2질문 제기

차트 디렉토리 안의 설정 파일이나 스크립트를 그대로 읽어 ConfigMap이나 Secret에 담을 수 있을까?

3구조적 핵심 예시

차트 폴더에 files/app-config.json 파일이 있으면, 템플릿에서 {{ .Files.Get "files/app-config.json" }} 라고 쓰면 그 파일의 전체 내용이 문자열로 반환되어 ConfigMap에 key-value로 저장된다.

4단계별 동작 과정

  1. 파일 위치 지정차트 루트 안의 상대 경로로 포함할 파일을 지정한다(예: files/, config/).
  2. 템플릿에서 읽기{{ .Files.Get "경로" }} 로 파일 내용을 문자열로 가져오거나, {{ .Files.Glob "pattern" }} 로 패턴에 맞는 여러 파일의 목록을 얻는다.
  3. 매니페스트에 삽입읽은 내용을 ConfigMap이나 Secret의 data 필드에 key-value 쌍으로 넣거나, 복수 파일의 경우 range 로 루프를 돌아 여러 항목을 생성한다.

쿠버네티스 API 버전 대응과 폐기 API 마이그레이션

클러스터 버전에 따라 달라지는 apiVersion을 .Capabilities로 분기하고, 폐기된 API를 새 버전으로 옮기는 작업.

1상대의 출발점 확인

템플릿에 고정된 apiVersion(예: apps/v1beta1)을 적으면, 새로운 쿠버네티스 버전에서는 그 API가 폐기되어 설치 오류가 발생한다. 매번 쿠버네티스 버전이 업그레이드될 때마다 템플릿을 수정해야 하고, 여러 클러스터의 버전이 다르면 같은 차트를 쓸 수 없다.

2질문 제기

어떤 쿠버네티스 버전에서든 그 클러스터가 지원하는 API 버전을 자동으로 선택해 설치하려면 어떻게 할까?

3구조적 핵심 예시

.Capabilities.APIVersions를 이용해 클러스터가 지원하는 API 목록을 확인한 후, 조건문으로 분기하는 방식. 예를 들어 if .Capabilities.APIVersions.Has "apps/v1" 이라고 물어보면 클러스터가 그 API를 지원하면 true, 안 하면 false를 반환하고, 이에 따라 다른 apiVersion을 사용하는 매니페스트를 렌더링한다.

4단계별 동작 과정

  1. 클러스터 능력 조회helm이 클러스터에 접속해 현재 쿠버네티스 버전이 지원하는 API 목록과 기능(리소스 종류, CRD 등)을 .Capabilities 객체로 수집한다.
  2. 템플릿에서 조건 판단렌더링 시 .Capabilities.APIVersions.Has로 특정 API가 있는지 확인하고, if-else로 어느 apiVersion과 필드를 쓸지 결정한다.
  3. 버전에 맞춘 매니페스트 생성선택된 apiVersion으로 최종 YAML을 만들어, 그 클러스터에서 실행 가능한 형태만 배포한다.

5본질 요약

클러스터가 지원하는 API를 .Capabilities로 조회한 후 템플릿 조건문으로 자동 선택해, 고정된 apiVersion 대신 클러스터 버전에 맞는 API를 동적으로 사용하는 것

1상대의 출발점 확인

템플릿을 잘못 작성했을 때 문제를 찾기 어렵다. 차트를 설치한 후 오류가 나거나, 렌더링된 YAML이 예상과 다르거나, 쿠버네티스가 거부하는 매니페스트가 배포될 수 있다. 오류가 발생하면 이미 클러스터에 부분 배포된 상태일 수 있다.

2질문 제기

템플릿의 문법 오류, 렌더링 결과, 쿠버네티스 검증을 실제 설치 전에 미리 단계적으로 확인할 방법은 무엇일까?

3구조적 핵심 예시

세 단계 검증: helm lint → helm template --debug → helm install --dry-run. 첫 번째는 차트 문법만 검사하고, 두 번째는 변수가 대입된 최종 YAML을 눈으로 확인하고, 세 번째는 쿠버네티스 API 서버가 승인 가능한 형태인지 검증한다.

4단계별 동작 과정

  1. 문법 검사 (helm lint)Chart.yaml, values.yaml, 템플릿 파일의 YAML 구조, 필수 필드 존재 여부, 값 범위를 자동으로 검사해 즉시 오류를 보고한다.
  2. 렌더링 결과 확인 (helm template --debug)변수를 values에 대입해 최종 생성될 YAML을 표준출력으로 출력하고 --debug 플래그는 렌더링 중간 단계 정보도 함께 표시해 변수 치환 과정을 추적할 수 있게 한다.
  3. 쿠버네티스 검증 (helm install --dry-run)실제 설치하지 않고 매니페스트를 쿠버네티스 API 서버에 제출해, 리소스 생성이 가능한지, 필드명이 올바른지 등을 미리 확인한다.

Chart.yaml의 dependencies 목록에 이름·버전 범위·저장소를 적어 다른 차트를 부품처럼 끌어다 쓰고, alias로 같은 차트를 다른 이름으로 여러 번 넣을 수 있다.

1상대의 출발점 확인

프로메테우스, 그래프프나, Elasticsearch 같은 인기 있는 소프트웨어 차트들이 이미 공개 Helm 저장소에 준비되어 있다. 이들을 매번 처음부터 새로 만들 수는 없으므로 기존 차트를 재사용해야 하는데, 현재로서는 수동으로 파일을 내려받아 폴더에 넣는 방법밖에 없다.

2질문 제기

다른 사람이 만든 공개 차트를 내 차트에 포함시켜 사용하도록 선언하려면 어떻게 할까?

3구조적 핵심 예시

Chart.yaml의 dependencies 배열에 각 의존 차트의 이름(name), 버전 범위(version), 저장소 URL(repository), 그리고 선택적으로 별칭(alias)을 항목으로 추가한다. 예를 들어 - name: prometheus, version: "^15.0.0", repository: "https://prometheus-community.github.io/helm-charts", alias: monitoring 처럼 적으면 "여기서 프로메테우스 15버전대를 써야 한다"는 의도를 명시하는 것이다.

4단계별 동작 과정

  1. Chart.yaml에 의존성 항목 작성각 의존성마다 name(필수), version(버전 범위: ^1.0, >=1.0 <2.0 등), repository(저장소 URL) 필드를 기입하고, 같은 차트를 다른 이름으로 여러 번 쓰려면 alias를 추가한다.
  2. 의존성 정보 저장Chart.yaml의 dependencies 섹션이 "어떤 부품이 필요한지" 선언만 하는 상태이며, 실제 파일은 아직 존재하지 않는다.
  3. 이후 단계 준비이 선언을 바탕으로 helm dependency update가 실제 파일을 내려받고 버전을 확정하게 된다.

helm dependency로 의존성 가져오기와 Chart.lock

helm dependency update가 선언된 의존성을 charts/ 폴더로 내려받고 실제 확정 버전을 Chart.lock에 기록해 빌드를 재현 가능하게 만든다.

1상대의 출발점 확인

Chart.yaml에 의존성을 적으면 설치 의도는 명확하지만, 실제 차트 파일이 없어서 helm install이 실패한다. 또한 매번 설치할 때 저장소에서 최신 버전을 받으면 버전이 바뀔 수 있어, 동일한 환경을 재현하기 어렵다.

2질문 제기

의존 차트를 실제로 내려받고, 나중에 같은 버전으로 언제나 동일한 빌드를 만들 수 있도록 버전을 고정하려면 어떻게 해야 할까?

3구조적 핵심 예시

helm dependency update 명령이 Chart.yaml의 의존성 정보를 읽고 각 차트를 저장소에서 다운로드해 charts/ 폴더에 저장하며, 동시에 실제 다운로드된 정확한 버전과 파일 체크섬을 Chart.lock에 기록해, 다음번 설치에서도 정확히 같은 버전만 사용하게 만든다.

4단계별 동작 과정

  1. Chart.yaml 읽기 및 버전 결정helm이 의존성 목록의 버전 범위(예: ^1.5)를 읽고, 해당 범위 내에서 다운로드할 정확한 버전(예: 1.5.7)을 결정한다.
  2. 저장소에서 차트 다운로드지정된 repository URL에서 각 차트의 확정 버전을 내려받아 charts/ 폴더에 압축 또는 전개된 형태로 저장한다.
  3. Chart.lock 생성 및 업데이트실제 다운로드된 각 차트의 버전, 저장소, 다이제스트(파일 체크섬)를 Chart.lock 파일에 기록해, 재현 가능한 빌드 상태를 확보한다.

5본질 요약

의존성을 charts/ 폴더에 다운로드하고 확정 버전과 체크섬을 Chart.lock에 기록해, 모든 팀원과 배포 환경에서 정확히 동일한 버전으로 설치 가능하게 보장하는 메커니즘

조건부 의존성:condition과 tags

condition은 특정 값이 true일 때, tags는 묶음 라벨이 켜졌을 때만 해당 서브차트를 설치하도록 하는 on/off 스위치다.

1상대의 출발점 확인

모든 의존 차트가 항상 필요한 건 아니다. 개발 환경에서는 로깅 스택이 필요 없을 수도 있고, 프로덕션에서만 모니터링을 켜야 할 수도 있다. 현재는 의존성을 모두 필수로 포함하기 때문에, 불필요한 차트까지 설치돼 리소스를 낭비하거나 설치에 실패한다.

2질문 제기

특정 환경이나 설정에 따라 선택된 의존 차트만 설치하고 나머지는 제외할 수 있을까?

3구조적 핵심 예시

각 의존성에 condition 필드를 붙이면(예: condition: logging.enabled) values.yaml에서 logging.enabled가 true일 때만 해당 차트를 포함하고, tags 필드를 붙이면(예: tags: [monitoring]) values.yaml의 tags.monitoring=true일 때만 활성화되도록 한다.

4단계별 동작 과정

  1. 의존성별 조건 지정Chart.yaml에서 각 의존성마다 condition과 tags 필드를 추가해, 어떤 조건에서 활성화될지 선언한다(예: prometheus 의존성에 condition: prometheus.enabled 추가).
  2. values로 조건 제어values.yaml에서 prometheus.enabled: true/false, 또는 tags.monitoring: true/false 식으로 상황에 맞게 값을 설정한다.
  3. 설치 시 포함 여부 결정helm install 시 values를 읽어 각 의존성의 조건을 평가하고, 조건이 true인 서브차트만 포함하며 false인 것은 제외한다.

서브차트 값 오버라이드와 스코프 규칙

부모 values.yaml에서 서브차트 이름을 키로 감싸 값을 덮어쓸 수 있고, 서브차트는 자기 스코프 안의 값만 보며 부모 값은 볼 수 없다.

1상대의 출발점 확인

서브차트는 자신의 values.yaml을 가지고 있어서 기본 설정값이 고정되어 있다. 부모 차트에서 서브차트의 설정을 바꾸려면 복잡한 방법을 써야 하거나 아예 불가능할 수 있어, 부모와 서브차트의 설정 일관성을 맞추기 어렵다.

2질문 제기

부모 차트의 values에서 서브차트의 기본값을 원하는 대로 덮어쓸 수 있을까?

3구조적 핵심 예시

부모 values.yaml에서 서브차트 이름을 최상위 키로 만들고 그 아래에 값을 중첩 작성하면(예: prometheus: { retention: 30d, replicas: 2 }), 설치 시 helm이 이 값들을 서브차트의 기본값에 병합하면서 부모 값을 우선 적용한다.

4단계별 동작 과정

  1. 부모 values에 서브차트 섹션 작성부모 values.yaml에서 서브차트 이름을 최상위 키로 만들고, 그 아래 서브차트에 전달할 설정값을 YAML 형태로 중첩해서 쓴다.
  2. helm이 값 병합부모에서 지정한 값과 서브차트의 기본 values.yaml을 merge하되, 부모 값이 서브차트 기본값을 덮어쓴다.
  3. 서브차트는 자신의 스코프만 참조서브차트의 템플릿은 자신의 .Values 아래 값만 보고, 부모 차트의 값에는 직접 접근하지 못하며 global(이후 항목)을 통해서만 공유 값을 사용한다.

5본질 요약

global 값과 import-values

global 블록은 모든 차트가 공유하는 값이고, import-values는 서브차트의 값을 부모 스코프로 끌어올려 재사용하게 해준다.

→ 07-04 참조

1상대의 출발점 확인

여러 서브차트가 공통으로 써야 하는 값(예: 이미지 레지스트리 주소, 도메인, 네임스페이스)이 있을 때, 각 서브차트마다 반복해서 지정해야 해서 번거롭고, 중복 때문에 값을 수정할 때 실수하기 쉽다.

2질문 제기

부모와 모든 서브차트가 함께 접근할 수 있는 공유 값을 어떻게 정의하고 활용할까?

3구조적 핵심 예시

values.yaml의 global 블록에 공유할 값을 정의하면(예: global: { domain: example.com, registry: gcr.io }), 모든 차트(부모·모든 서브차트)에서 .Values.global.domain 형태로 접근 가능하고, import-values를 Chart.yaml의 의존성에 선언해 특정 서브차트의 값을 부모 스코프로 끌어올릴 수도 있다.

4단계별 동작 과정

  1. global 값 정의부모 values.yaml의 global 섹션에 모든 차트가 공유할 값(도메인, 레지스트리, 인증서 등)을 작성하고, 모든 템플릿에서 .Values.global로 이 값에 접근할 수 있다.
  2. import-values 선언Chart.yaml의 의존성 항목에 import-values 필드를 추가해, 특정 서브차트의 값(예: prometheus의 retention)을 부모 values 구조로 끌어올릴 경로를 지정한다.
  3. 부모와 서브차트가 동일 값 참조부모와 다른 서브차트들이 global 블록의 같은 값을 참조하고, import-values로 끌어올린 값도 부모 스코프에서 접근 가능해 중복 설정을 제거할 수 있다.

라이브러리 차트와 엄브렐라 차트 패턴

라이브러리 차트는 설치되지 않고 공용 템플릿만 제공하는 차트이고, 엄브렐라 차트는 여러 서브차트를 한 번에 배포하려고 묶은 상위 차트다.

1상대의 출발점 확인

차트들이 각각 독립적으로 배포되거나, 여러 관련된 차트를 함께 배포하려면 각 차트를 개별적으로 helm install로 실행해야 한다. 또한 여러 차트에 공통으로 필요한 템플릿(Deployment, Service, ConfigMap 등)이 있으면 반복 작성해야 한다.

2질문 제기

여러 개의 관련 차트를 어떻게 단일 배포 명령으로 함께 설치하고, 동시에 반복되는 템플릿 코드는 어떻게 공유할 것인가?

3구조적 핵심 예시

데이터베이스, 캐시, 모니터링을 한 번에 배포하는 시스템에서, 이 세 개의 차트를 각각 helm install로 실행하는 대신, 상위 차트 하나가 이들을 모두 포함하고 있어서 단 한 번의 명령으로 세 개 모두를 배포하고, 동시에 공통 리소스는 라이브러리 차트로 분리해 각 서브차트에서 include해서 재사용한다.

4단계별 동작 과정

  1. 라이브러리 차트 역할라이브러리 차트는 설치 대상이 아니라 다른 차트들이 참조할 공용 템플릿 코드를 제공한다. Chart.yaml에서 type: library로 지정하면, 이 차트는 직접 배포되지 않고 Deployment, Service 같은 공통 템플릿만 제공한다.
  2. 엄브렐라 차트 구성엄브렐라 차트는 Chart.yaml의 dependencies 섹션에서 여러 서브차트(database, cache, monitoring 등)를 나열하고, helm dependency update로 이들을 charts/ 디렉터리에 다운로드한다.
  3. 통합 배포 및 관리엄브렐라 차트를 helm install하면, 내부의 모든 서브차트가 차례대로 설치되며, 각 서브차트의 values를 상위 차트의 values.yaml에서 한 번에 관리할 수 있다.

1상대의 출발점 확인

일반적인 배포는 helm이 템플릿을 렌더링해서 쿠버네티스 리소스를 apply하는 것으로 끝난다. 하지만 실제 운영에서는 배포 전후로 데이터베이스 마이그레이션, 캐시 초기화, 헬스 체크 같은 추가 작업이 필요한데, 이를 별도로 수동으로 실행해야 한다.

2질문 제기

3구조적 핵심 예시

새 애플리케이션 버전을 배포하기 전에 데이터베이스 마이그레이션 Job을 실행하고, 배포 후에는 모니터링 시스템에 배포 이벤트를 기록하고, 롤백 시에는 이전 데이터베이스 상태로 되돌리는 이 일련의 작업들을 배포 프로세스에 자동으로 끼워 넣는 것이다.

4단계별 동작 과정

  1. 훅 정의템플릿 파일에 helm.sh/hook 애노테이션을 달아서 어떤 이벤트(pre-install, post-install 등)에서 실행할지 지정한다. 훅은 실제로는 Job이나 Pod 같은 쿠버네티스 리소스다.

훅을 사용할 때 정확히 어느 시점에 실행되는지 알아야만 올바른 순서대로 작업을 배치할 수 있다. pre-install과 post-install이 정확히 어느 단계인지, upgrade와 install에서는 어떻게 다른지 모르면 훅 순서를 잘못 배치하기 쉽다.

3구조적 핵심 예시

  2. 업그레이드와 롤백 시점의 훅 이벤트pre-upgrade 훅, 리소스 업그레이드 실행, post-upgrade 훅 순이고, 롤백 시에는 pre-rollback 훅, 이전 버전으로의 변경 실행, post-rollback 훅 순서다.

1상대의 출발점 확인

훅이 여러 개 있을 때, 실행 순서가 정해지지 않으면 원치 않는 순서대로 실행될 수 있다. 예를 들어, 데이터베이스 마이그레이션 훅이 애플리케이션 시작 훅보다 먼저 실행되어야 하는데, 순서가 뒤바뀌면 실패한다. 또한 훅 리소스가 배포 후에도 클러스터에 남아 있으면 불필요한 자원을 낭비한다.

3구조적 핵심 예시

post-install 이벤트에서 데이터베이스 마이그레이션, 캐시 워밍업, 헬스 체크를 모두 실행해야 하는데, 각각 다른 가중치를 지정해서 데이터베이스(가중치 0) → 캐시(가중치 1) → 헬스 체크(가중치 2) 순으로 실행하고, 각각이 성공하면 자동으로 리소스를 지우는 것이다.

4단계별 동작 과정

  1. 가중치로 순서 결정helm.sh/hook-weight 애노테이션에 숫자를 지정한다. 같은 이벤트 안에서 낮은 가중치부터 높은 가중치 순서대로 실행된다.
  2. 실행 후 리소스 처리 결정helm.sh/hook-delete-policy 애노테이션으로 훅 리소스를 언제 지울지 지정한다. hook-succeeded(훅 성공 후), hook-failed(훅 실패 후), before-hook-creation(다음 훅 생성 전) 중 선택하거나 조합할 수 있다.
  3. 순서대로 실행 및 정리Helm이 각 훅을 가중치 순서대로 생성하고, 각 훅이 완료되면 삭제 정책에 따라 리소스를 정리한다.

8배포 시점 제어: 훅, 테스트, CRD08-06

CRD를 차트에 담는 법과 제약

CRD는 crds/ 디렉터리에 넣으면 템플릿보다 먼저 설치되지만 업그레이드·삭제는 Helm이 관리하지 않는다.

1상대의 출발점 확인

Kubernetes의 기본 리소스(Deployment, Service 등) 말고도, 특정 컨트롤러가 관리하는 Custom Resource Definition(CRD)을 배포해야 할 때가 있다. 하지만 CRD는 일반 리소스와 달리 특수한 처리가 필요한데, 차트 템플릿에 섞여 있으면 설치 순서 문제가 발생한다.

2질문 제기

차트에 CRD를 포함시킬 때, 일반 리소스보다 먼저 설치되도록 하고, 라이프사이클을 올바르게 관리하려면 어떻게 할 것인가?

3구조적 핵심 예시

Custom Resource를 정의하는 CRD를 먼저 설치한 후, 그 CRD의 인스턴스(예: MyCustomResource)를 생성하는 순서다. CRD가 없으면 Custom Resource를 생성할 수 없으므로, 이 순서가 자동으로 보장되어야 한다.

4단계별 동작 과정

  1. CRD 파일 배치CRD YAML 파일을 crds/ 디렉터리에 넣는다. 이 디렉터리의 파일들은 일반 templates/ 의 파일보다 먼저 설치된다.
  2. CRD 설치helm install을 실행하면, Helm이 crds/ 의 모든 CRD를 먼저 클러스터에 생성한다.
  3. CRD 라이프사이클 한계CRD는 설치되지만, 업그레이드(차트 버전 변경)나 삭제(helm delete) 시에는 Helm이 CRD를 자동으로 수정하거나 삭제하지 않는다. CRD 수정과 삭제는 수동으로 진행해야 한다.

5본질 요약

crds/ 디렉터리로 CRD를 다른 리소스보다 먼저 설치하되, CRD의 수정과 삭제는 Helm이 관리하지 않도록 하는 메커니즘

  2. 다이제스트 기반 참조 저장태그 대신 myrepo/mychart@sha256:abc123... 형태의 다이제스트 기반 참조를 기록합니다.
  3. 정확한 버전으로 설치helm install -r myrepo --version sha256:abc123... 처럼 다이제스트로 설치하면, 정확히 그 콘텐츠의 차트만 설치됩니다.

1상대의 출발점 확인

Helm은 템플릿을 렌더링해서 YAML 매니페스트를 생성한 다음 바로 쿠버네티스에 적용한다. 하지만 배포 직전에 매니페스트를 수정해야 하는 경우가 있다. 예를 들어 조직의 규칙에 맞게 레이블을 추가하거나, kustomize로 패치를 적용하거나, 보안 정책을 자동으로 주입해야 할 때, 현재는 Helm 배포 후 별도의 kubectl 명령이나 외부 스크립트를 수동으로 실행해야 한다.

3구조적 핵심 예시

개발자가 포스트 렌더러 프로그램(kustomize 실행 스크립트)을 작성한 후 helm install --post-renderer 플래그로 경로를 지정한다. Helm이 템플릿을 렌더링해서 YAML 매니페스트를 만들면, 그 결과를 포스트 렌더러 프로그램의 표준 입력(stdin)으로 보낸다. 프로그램은 매니페스트를 받아서 kustomize로 처리한 후 수정된 버전을 표준 출력(stdout)으로 돌려주고, Helm은 그 수정된 매니페스트를 쿠버네티스에 적용한다.

4단계별 동작 과정

  1. 포스트 렌더러 작성표준 입력에서 YAML 매니페스트를 받아서 처리하고 표준 출력으로 결과를 내보내는 실행 가능한 프로그램(Go/Bash/Python 등)을 준비한다.
  2. Helm 명령에 등록helm install 또는 helm upgrade 할 때 --post-renderer <프로그램경로> 플래그를 추가한다.
  3. 자동 처리 및 배포Helm이 렌더링한 매니페스트를 포스트 렌더러로 보내면 프로그램이 수정한 결과를 Helm이 받아서 쿠버네티스에 적용한다.

3구조적 핵심 예시

  2. 권한 설정Secret/ConfigMap 백엔드는 쿠버네티스 RBAC 권한만 필요하고, SQL 백엔드는 데이터베이스 테이블 접근 권한(CREATE TABLE, SELECT, INSERT, UPDATE, DELETE)이 필요하다.

RBAC로 Helm 사용 권한 설계

Helm 이 사용자 자격증명으로 동작하므로 Kubernetes RBAC 로 네임스페이스별 설치·조회 권한을 나누는 설계.

1상대의 출발점 확인

Helm은 사용자의 자격증명(kubeconfig 내 토큰)을 사용해서 kubectl처럼 쿠버네티스 API를 호출한다. Helm 명령이 성공하려면 사용자에게 필요한 쿠버네티스 권한(리소스 생성/수정/삭제)이 있어야 한다. 하지만 팀 규모가 커지면 누가 어느 네임스페이스에서 어떤 작업을 할 수 있는지 일일이 확인해야 하고, 실수로 권한을 과하게 부여하거나 부족하게 부여하는 문제가 생긴다.

2질문 제기

팀원들이 각자 필요한 네임스페이스와 작업만 할 수 있도록 Helm 사용 권한을 세분화할 수 있는가?

3구조적 핵심 예시

팀 리더가 RBAC Role/RoleBinding을 정의한다. 예를 들어 dev-team 역할은 namespace-dev에서 Deployment/Service/ConfigMap 리소스만 관리하도록, qa-team 역할은 namespace-qa에서 같은 리소스를 관리하되 읽기만 허용하도록 설정한다. 각 팀원의 kubeconfig에 해당 역할이 연결되면, helm install을 실행할 때 Helm은 사용자의 자격증명으로 쿠버네티스 API를 호출하고, 쿠버네티스 API 서버는 해당 사용자가 그 Role에 지정된 권한만 가졌는지 확인한 후 요청을 허가하거나 거부한다.

4단계별 동작 과정

  1. Helm 관련 RBAC 역할 정의각 팀이나 사용자별로 필요한 권한(get, create, update, delete 등)과 대상 리소스(Pod, Deployment, Secret 등), 네임스페이스 범위를 Role에 명시한다.
  2. 역할 바인딩정의한 Role을 특정 사용자, 서비스 계정, 그룹에 RoleBinding으로 연결한다.
  3. Helm 명령 실행 시 권한 검증사용자가 helm install 같은 명령을 실행하면 Helm은 사용자의 토큰으로 API 서버에 요청을 보내고, 서버는 사용자의 RoleBinding에 따라 접근을 허용 또는 거부한다.

1상대의 출발점 확인

차트 개발자가 CRD(Custom Resource Definition, 쿠버네티스 확장 리소스)와 서브차트(다른 차트가 의존하는 차트) 의존성을 자유롭게 다루면, CRD 설치 순서 문제, 업그레이드 중 충돌, 의존하는 차트가 조건부로 활성화되지 않는 경우 같은 문제가 발생합니다.

2질문 제기

3구조적 핵심 예시

Helm이 차트를 설치할 때 CRD 폴더의 파일을 먼저 처리한 후 나머지 매니페스트와 서브차트 의존성을 순서대로 처리합니다. CRD는 한 번 설치되면 차트 삭제 시에도 남고, 업그레이드 중에도 새 버전으로 교체되지 않으므로, CRD 스키마 변경이 하위 호환성을 깨면 클러스터 전체가 영향을 받습니다.

4단계별 동작 과정

  1. CRD 파일 배치charts/crds/ 폴더에 CRD 매니페스트를 배치하면 Helm이 다른 리소스보다 먼저 설치합니다. 이때 CRD는 helm uninstall에서도 삭제되지 않도록 설정하는 것이 관례입니다.
  2. 의존성 선언과 조건부 활성화Chart.yaml의 dependencies 항목에서 서브차트를 선언할 때, enabled: false 같은 조건을 추가해 특정 환경에서만 설치되게 제어합니다. 이렇게 하면 선택적 기능(예: 모니터링, 로깅)을 필요한 경우만 포함 가능합니다.
  3. 공개 차트 품질 검증Helm Hub나 커뮤니티 저장소에 올리기 전에 helm lint로 차트 구문을 점검하고, 여러 쿠버네티스 버전에서 테스트해 CRD와 의존성이 제대로 작동하는지 확인합니다.

Go SDK로 Helm 동작 호출하기

helm 명령어 대신 Go 코드에서 Helm 라이브러리를 불러와 설치·업그레이드 같은 동작을 프로그램으로 실행하는 방법이다.

1상대의 출발점 확인

helm install, helm upgrade 같은 CLI 명령어를 터미널에서 실행하고 결과를 stdout/stderr로 받는 방식에서는, 스크립트가 명령어 실행 결과를 파싱해야 하고, 오류 처리가 복잡하며, 배포 자동화 시스템이 헬름 설치를 통제하기 어렵습니다.

2질문 제기

Go 프로그램에서 헬름 설치·업그레이드를 직접 코드로 호출하려면 어떻게 해야 할까요?

3구조적 핵심 예시

Helm 팀이 공개한 Go SDK(golang.org/x/helm/pkg/...)를 import해서 Release, Install, Upgrade 같은 구조체와 메서드를 사용하면, CLI 없이도 프로그램 내에서 차트를 설치하고 버전을 올릴 수 있습니다. 반환값이 Go 구조체이므로 JSON/YAML로 파싱할 필요가 없습니다.

4단계별 동작 과정

  1. SDK 초기화Go 코드에서 helmclient 패키지를 불러와 Helm 클라이언트 인스턴스를 만듭니다. 이때 쿠버네티스 클러스터 접근 정보(kubeconfig)를 전달합니다.
  2. 차트 설치/업그레이드 호출client.InstallChart() 또는 client.UpgradeChart() 메서드를 호출하면서 차트명, 네임스페이스, values 등을 파라미터로 넘깁니다. 메서드는 설치 완료까지 기다리고 Release 객체를 반환합니다.
  3. 결과 처리Release 객체에서 버전, 상태, 설치된 리소스 목록 등을 직접 접근해서 다음 단계(예: 헬스 체크, 로깅)로 연결합니다.

5본질 요약

Helm CLI를 거치지 않고 Go 코드에서 직접 Helm 라이브러리를 호출해 차트 배포를 자동화하고, 프로그래밍 방식으로 결과를 처리하는 것

공식 문서https://helm.sh/docs/sdk/gosdk

Helm 3에서 Helm 4로 이행하기

기존 Helm 3 환경과 차트를 Helm 4에서 깨지지 않게 옮기기 위해 달라진 점과 점검 항목을 확인하는 과정이다.

1상대의 출발점 확인

Helm 3에서 차트와 릴리스를 관리해온 환경에서 명령어, 설정 파일, 보안 모델이 모두 Helm 3 기준으로 작동하는데, Helm 4가 출시되면서 일부 명령어 옵션, 저장소 구조, 권한 관리 방식이 변경될 수 있고, 기존 릴리스가 호환되지 않으면 클러스터 마이그레이션이 필요해집니다.

2질문 제기

Helm 3 환경의 차트와 릴리스를 Helm 4에서 깨지지 않게 옮기려면 무엇을 확인해야 할까요?

3구조적 핵심 예시

Helm 3에서 설치한 릴리스 정보는 쿠버네티스 Secret으로 저장되는데, Helm 4는 이 Secret 형식을 읽되 일부 필드 이름이 변경되거나 새로운 메타데이터가 추가될 수 있습니다. 따라서 먼저 현재 릴리스 목록을 백업하고, Helm 3 차트의 Chart.yaml과 values.yaml이 Helm 4 스키마를 만족하는지 점검한 후에 업그레이드합니다.

4단계별 동작 과정

  1. 현재 상태 백업helm list -a, helm get values <release> 명령으로 모든 릴리스와 설정값을 저장해서, 문제 발생 시 롤백할 수 있게 준비합니다.
  2. 차트 호환성 확인각 차트의 Chart.yaml에서 apiVersion, 메타데이터, 의존성 선언이 Helm 4 스펙을 따르는지 helm lint로 검증합니다. 필요하면 차트를 수정합니다.
  3. 단계적 업그레이드테스트 클러스터에서 Helm 4를 설치해 기존 릴리스가 정상 작동하는지 확인한 후, 프로덕션 클러스터를 Helm 4로 업그레이드합니다.

5본질 요약

Helm 3에서 축적한 릴리스 데이터와 차트를 Helm 4 형식으로 호환성을 유지하면서 마이그레이션하고, 업그레이드 중 장애를 예방하기 위해 사전 검증과 백업을 수행하는 것

공식 문서https://helm.sh/docs/changelog

자주 겪는 문제와 명령 치트시트

설치 실패·릴리스 꼬임 같은 흔한 오류의 해결법과 자주 쓰는 helm 명령을 한눈에 모아둔 요약이다.

1상대의 출발점 확인

각 helm 명령어를 매번 개별적으로 찾아보거나, 에러가 발생했을 때 문서 전체를 검색해야 하므로, helm install이 실패해도 왜 실패했는지 빠르게 파악하기 어렵고, 릴리스가 꼬였을 때 되돌리는 과정도 명확하지 않습니다.

2질문 제기

Helm 사용 중 자주 마주치는 오류와 해결 방법을 빠르게 찾고, 자주 쓰는 명령을 한눈에 보려면 어떻게 해야 할까요?

3구조적 핵심 예시

Helm 공식 문서의 CheatSheet 페이지는 설치 실패(FAILED, PENDING 상태), 릴리스 충돌(같은 이름의 릴리스가 이미 존재), values 오류 같은 일반적 문제마다 원인과 해결 명령(helm rollback, helm delete, helm upgrade --force)을 정리해두었으므로, 문제 증상에 맞춰 바로 명령을 실행할 수 있습니다.

4단계별 동작 과정

  1. 문제 증상 파악helm status <release>, helm describe로 현재 릴리스 상태를 확인해 FAILED, PENDING, ImagePullBackOff 같은 상태 코드를 읽습니다.
  2. 원인 매칭과 명령 실행CheatSheet에서 해당 증상의 해결 명령을 찾아서(예: helm rollback, helm get values, helm delete --purge) 실행합니다.
  3. 예방 명령 활용향후 설치 시 helm install --dry-run --debug를 먼저 실행해서 리소스 충돌이나 값 오류를 미리 발견합니다.

5본질 요약

Helm 운영 중 발생하는 일반적 오류들을 원인별로 분류하고, 각각에 대응하는 helm 명령어와 디버깅 방법을 한 문서에 모아, 신속한 문제 해결과 재발 방지를 돕는 것

공식 문서https://helm.sh/docs/intro/CheatSheet
