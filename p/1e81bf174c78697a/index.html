이어서 읽기

AWS의 풀매니지드 API 게이트웨이 서비스로, REST API·HTTP API·WebSocket API 세 제품군을 생성·배포·모니터링·보안·외부 제공한다. 공식 문서가 'REST / HTTP / WebSocket' 세 제품군과 '개발→배포·게시→보호→모니터링' 수명주기로 나뉘므로, 가장 일반적인 해석인 '세 제품군을 한 토픽으로, 기능은 자주 쓰는 것부터'를 택했다. REST API를 중심으로 기본기를 깔고, 그 경량 대안인 HTTP API와 다른 패러다임인 WebSocket API를 뒤에 배치했다.

API Gateway 서비스 개요

Amazon API Gateway는 AWS에서 REST·HTTP·WebSocket API를 만들고 배포·보안·모니터링하며 백엔드 서비스에 연결해주는 완전관리형 서비스다.

1상대의 출발점 확인

API를 외부에 제공하려면 기존에는 백엔드 서버를 직접 준비하고, 그 서버에서 URL을 노출하고, 인증·속도 제한·로그 기록을 서버 코드 안에 하나씩 구현해야 했다. 서버가 여러 개로 늘어나면 관리 지점도 그만큼 늘어나고, 보안 설정이 코드마다 다르게 흩어지며, 트래픽이 몰릴 때는 서버를 미리 추가로 준비해야 했다. 즉 API를 만들고 운영하는 모든 부담이 개발자와 운영자에게 그대로 쌓였다.

2질문 제기

API를 만들고 배포하고 보호하는 일을 백엔드 코드와 분리해 한 곳에서 자동으로 처리할 수는 없을까?

3구조적 핵심 예시

함수 하나(예: 특정 데이터를 돌려주는 Lambda 핸들러)가 있을 때, API Gateway에 GET /users라는 엔드포인트를 하나 정의해 두면, 클라이언트가 그 URL을 호출했을 때 게이트웨이가 요청을 받아 Lambda를 실행하고 결과를 JSON으로 돌려준다. 개발자는 함수의 로직만 신경 쓰면 되고, URL 제공·인증·로그 기록·트래픽 확장은 게이트웨이가 대신 처리한다.

4단계별 동작 과정

  1. API 생성과 정의콘솔이나 CLI에서 엔드포인트(URL 경로와 메서드)를 만들고, 각 엔드포인트가 연결될 백엔드를 지정한다.
  2. 배포정의한 API를 스테이지(예: prod)에 배포하면 외부에서 호출 가능한 고정 URL이 만들어진다.
  3. 요청 처리클라이언트 요청이 들어오면 게이트웨이가 인증과 검증을 거쳐 백엔드에 전달하고, 백엔드 응답을 다시 클라이언트에게 돌려준다. 트래픽이 늘어도 게이트웨이가 자동으로 확장된다.

API Gateway 핵심 개념

API Gateway의 핵심 개념은 API·리소스·메서드·통합·배포·스테이지로, 클라이언트 요청이 게이트웨이를 거쳐 백엔드로 전달되는 흐름을 이룬다.

1상대의 출발점 확인

기존 서버에서는 API가 곧 서버 코드 안에 있어서, 어떤 경로가 어떤 처리를 하는지가 코드와 설정 파일에 섞여 있었다. 배포할 때마다 서버 전체를 다시 올려야 하고, 지금 어떤 버전이 실제로 서비스 중인지 추적하기 어려웠으며, 개발 환경과 운영 환경을 나누는 것도 서버마다 다르게 설정해야 했다.

2질문 제기

API를 코드에서 분리된 체계로 표현하고 버전을 관리해 외부에 노출하려면 어떤 구성 요소들이 필요할까?

3구조적 핵심 예시

GET /items/{id}라는 경로 하나를 보면, API는 전체 엔드포인트의 묶음이고, 리소스는 /items, 메서드는 GET, 통합은 그 요청이 실제로 처리되는 대상(Lambda 함수나 HTTP 서버)이다. 이 정의를 배포로 묶어 스테이지(예: dev, prod)에 올리면 클라이언트가 호출할 수 있는 고정 URL이 생긴다. 같은 API 정의에서 환경별로 스테이지를 여러 개 둘 수 있어서 개발용과 운영용 URL을 따로 관리한다.

4단계별 동작 과정

  1. 정의리소스(경로)와 메서드(GET, POST 등)를 만들고, 각 메서드에 통합(뒷단 처리 대상)을 연결한다.
  2. 배포정의한 API를 배포로 묶어 스테이지에 게시한다. 스테이지마다 서로 다른 URL과 환경 설정을 가진다.
  3. 호출클라이언트가 스테이지 URL로 요청을 보내면 게이트웨이가 통합을 실행해 백엔드의 결과를 돌려준다.

5본질 요약

REST API와 HTTP API 선택

API Gateway에서는 기능이 풍부한 REST API와 저비용·저지연이 장점인 HTTP API 중 요구 사항에 맞는 API 유형을 선택한다.

1상대의 출발점 확인

API Gateway에서 API를 처음 만들 때 어떤 유형을 골라야 할지가 헷갈린다. 두 유형 모두 비슷하게 생긴 REST 스타일 API를 만들 수 있어서, 기능 차이를 모르고 아무거나 고르면 나중에 필요한 기능이 없어서 다시 만들어야 하는 상황이 온다. 반대로 기능이 필요 없는 단순한 API인데 과하게 기능이 많은 유형을 고르면 비용과 지연만 늘어난다.

2질문 제기

기능을 더 많이 쓰는 것과 속도·비용을 더 챙기는 것 중, 지금 만들 API에는 어느 쪽이 맞을까?

3구조적 핵심 예시

사용자 목록을 돌려주는 GET /users 하나만 필요하고 Lambda에 연결해 JSON을 그대로 주고받는 API라면 HTTP API로 충분하다. 반면 API 키 사용량 플랜(호출 횟수 제한과 과금 단위), 요청·응답 본문을 변환하는 매핑 템플릿, WAF(웹 방화벽) 연동이 필요하면 REST API를 골라야 한다. REST API는 기능이 많지만 요청당 비용이 더 높고 지연이 조금 더 크다.

4단계별 동작 과정

  1. 요구 기능 확인인증·검증·변환·사용량 플랜 등 필요한 기능 목록을 뽑고, REST API만 지원하는 기능이 있는지 대조한다.
  2. 유형 선택요청을 그대로 백엔드에 전달하는 Lambda 프록시 중심의 단순한 API는 HTTP API로, 고급 기능이 필요하면 REST API로 정한다.
  3. 생성과 확정콘솔에서 유형을 지정해 API를 만들고, 필요한 기능이 지원되는지와 비용을 확인한 뒤 사용한다.

5본질 요약

풍부한 기능이 필요한지 저비용·저지연이 더 중요한지에 따라 REST API와 HTTP API 중 하나를 골라 만드는 선택 문제

API Gateway 사용 사례

API Gateway는 서버리스 애플리케이션의 API 앞단, 마이크로서비스 통합, 레거시 시스템 노출 등 다양한 시나리오에서 API를 만들고 운영하는 데 사용된다.

1상대의 출발점 확인

서버리스 구조에서 Lambda 함수를 외부에서 호출하려면 SDK(코드 라이브러리)나 특별한 호출 방식을 써야 해서 일반 HTTP 클라이언트로는 바로 부르기 어렵다. 함수를 그냥 외부에 드러내면 인증과 접근 제어를 함수마다 따로 구현해야 하고, 함수가 여러 개 늘어나면 호출할 엔드포인트가 여기저기 흩어진다.

2질문 제기

Lambda 함수나 기존 시스템을 안전한 단일 API 경로로 묶어 외부에 내놓으려면 무엇이 필요할까?

3구조적 핵심 예시

주문 처리 앱이 있다면 결제·재고·배송을 담당하는 Lambda 함수 3개를 API Gateway 하나에 모아 /payments, /inventory, /shipping이라는 각각의 경로로 노출한다. 클라이언트는 게이트웨이 URL 한 곳만 알면 되고, 나중에 한 함수의 내부 구현을 바꿔도 URL은 그대로 유지된다.

4단계별 동작 과정

  1. 백엔드 연결각 Lambda 함수나 기존 HTTP 서버를 API Gateway의 통합으로 등록한다.
  2. 경로 구성엔드포인트별로 메서드와 인증·속도 제한을 설정해 하나의 API로 묶는다.
  3. 운영게이트웨이 URL 하나로 모든 백엔드를 호출하고, 호출 지표와 로그를 한곳에서 모니터링한다.

사전 조건과 첫 API 만들기

API Gateway 사용을 시작하려면 AWS 계정과 IAM 권한 등 사전 조건을 갖춘 뒤, 콘솔이나 CLI로 첫 REST API를 만들고 배포해 호출해본다.

1상대의 출발점 확인

API를 만들기 전에 갖춰야 할 것이 있다. AWS 계정이 없으면 콘솔에 접속 자체가 안 되고, 계정은 있어도 API Gateway나 Lambda를 다룰 권한(IAM 권한)이 없으면 API를 정의해도 실제 호출 단계에서 막힌다. 이 사전 조건을 건너뛰고 바로 만들기를 시작하면 어디서 막혔는지 찾는 데 오히려 시간을 더 쓴다.

2질문 제기

계정과 권한이 준비된 상태에서 첫 REST API를 만들고 배포해 실제로 호출해 보려면 어떤 순서로 해야 할까?

3구조적 핵심 예시

콘솔에서 API 생성을 선택하고 예시 API(예: PetStore)를 그대로 불러온 뒤, 배포 버튼으로 스테이지를 만들어 URL을 발급받고, 그 URL을 브라우저나 curl(명령줄 요청 도구)로 호출해 JSON 응답이 돌아오는 것을 확인한다. 전체 과정이 콘솔 클릭 몇 번으로 끝난다.

4단계별 동작 과정

  1. 사전 준비AWS 계정과 함께 API Gateway 및 Lambda 등 필요한 서비스의 권한(IAM 권한)이 있는지 확인한다.
  2. 생성과 배포콘솔이나 CLI로 REST API를 만들고 스테이지에 배포해 호출 가능한 URL을 얻는다.
  3. 호출 확인발급된 URL로 요청을 보내 정상 응답을 받는지 확인하고, 실패하면 권한과 통합 설정을 점검한다.

API 엔드포인트 유형

API 엔드포인트 유형은 edge-optimized(엣지 최적화)·Regional(리전)·Private(프라이빗) 세 가지로, API가 어디서 어떻게 트래픽을 서빙할지 결정한다.

1상대의 출발점 확인

API를 어디에 두느냐를 정하지 않으면 문제가 생긴다. 전 세계 사용자를 상대하는 API를 한 지역의 서버에만 두면 먼 지역의 사용자는 응답이 느리고, 반대로 VPC(가상 사설 네트워크) 안에서만 접근해야 하는 내부 API를 일반 공개 URL로 열어버리면 보안상 외부에 노출된다. 엔드포인트 유형을 처음에 정하지 않으면 이런 상황에서 다시 만들거나 설정을 바꿔야 한다.

2질문 제기

API가 어디서 트래픽을 받고 서빙할지를 세 가지 유형 중 어떤 것으로 정해야 할까?

3구조적 핵심 예시

전 세계 사용자를 상대하는 서비스는 edge-optimized(엣지 최적화)를 써서 AWS 엣지 네트워크(전 세계에 분산된 지점)가 요청을 받아 사용자와 가까운 곳에서 응답하게 한다. 한 리전 안에서만 쓰는 서비스는 Regional(리전)을, VPC 안에서만 접근해야 하는 내부 API는 Private(프라이빗)을 쓴다.

4단계별 동작 과정

  1. 유형 결정사용자 분포와 접근 범위(전 세계·단일 리전·VPC 내부)에 따라 쓸 유형을 고른다.
  2. 생성 시 지정API를 만들 때 엔드포인트 유형을 선택해 설정하고, 프라이빗의 경우 접근 가능한 네트워크 구성을 함께 지정한다.
  3. 서빙설정된 유형대로 게이트웨이가 요청을 받아 처리한다. 엣지 최적화는 가까운 엣지가, 리전은 해당 리전이, 프라이빗은 VPC 내부에서만 응답한다.

2단계 REST API — 메서드와 요청·응답

REST API는 리소스(경로) 트리 위에 HTTP 메서드(GET, POST 등)가 붙어 하나의 메서드를 이루는 구조다.

1상대의 출발점 확인

REST API를 처음 접하면 "API 하나 = URL 하나"라고 생각하기 쉽다. 그러나 실제 API는 URL 경로만으로 완성되지 않는다. 서버에는 같은 경로라도 GET, POST, PUT, DELETE처럼 요청 종류에 따라 다른 동작을 수행하는 처리 로직이 여러 개 붙을 수 있다. 기존 방식에서 이 처리 로직을 구분하려면 경로를 억지로 나누거나(예: /user/create, /user/delete) URL 안에 동작 이름을 넣는 식으로 우회해야 했다. 이렇게 하면 경로가 금방 지저분해지고, 같은 데이터에 대한 조회와 생성이 서로 다른 주소로 분산되어 관리도 어려워진다. 한계점은 명확하다. URL 하나로는 "무엇을" 다루는지만 표현할 수 있고 "어떻게" 다룰지(조회인지, 생성인지, 삭제인지)는 담을 수 없다는 것이다.

2질문 제기

하나의 리소스(다루는 대상)에 대해 서로 다른 동작을 어떻게 구분해서 처리할 수 있을까?

3구조적 핵심 예시

API Gateway의 REST API는 리소스 트리 위에 HTTP 메서드가 붙어 하나의 메서드를 이룬다. 예를 들어 /items라는 리소스가 있다면, 여기에 GET이 붙은 메서드는 "목록 조회"를, POST가 붙은 메서드는 "새 항목 생성"을, DELETE가 붙은 메서드는 "항목 삭제"를 각각 담당한다. 이때 /items라는 경로(리소스)는 공유하지만 메서드가 다르므로 요청이 어느 쪽으로 가야 하는지가 메서드로 결정된다. 리소스가 "무엇을" 다루는지, 메서드가 "어떻게" 다루는지를 나누어 표현하는 것이 구조의 핵심이다.

4단계별 동작 과정

  1. 리소스(Resource) 정의API의 경로 트리를 만든다. 예: /items, /items/{id}처럼 중괄호로 묶으면 동적인 값(경로 파라미터)을 받는 리소스가 된다.
  2. 메서드(Method) 부착각 리소스에 GET, POST, PUT, DELETE 같은 HTTP 메서드를 하나씩 붙여 하나의 메서드(API 작업 단위)를 만든다. 이때 각 메서드는 이후 통합(Integration) 단계에서 연결할 백엔드 처리가 각각 따로 설정된다.
  3. 요청 수신과 전달클라이언트가 보낸 HTTP 요청이 들어오면 API Gateway가 요청의 경로와 메서드 조합을 보고 짝이 맞는 메서드 설정을 찾아 그 백엔드로 전달한다. 요청이 끝나면 그 결과를 클라이언트에 돌려준다.

1상대의 출발점 확인

클라이언트가 API를 호출할 때 보내는 요청에는 URL 경로뿐 아니라 쿼리 스트링(예: ?page=2), 헤더(인증 토큰 등), 본문(JSON 데이터)에 추가 정보가 실린다. 기존 방식에서는 백엔드 서버가 이 요청을 받아 그때그때 직접 파싱(내용을 까서 읽는 작업)해서 필요한 값을 꺼냈다. 그런데 이렇게 하면 클라이언트가 보낸 값이 제대로 들어왔는지, 어떤 이름으로 전달되는지에 대한 약속이 코드 안에 흩어져 버린다. 필수 값이 누락되어도 백엔드에 도달하고 나서야 오류가 발견되고, 백엔드 코드가 바뀌면 요청 형식의 기준도 따라 흔들린다. 한계점은 명확하다. 요청에서 어떤 값을 어떻게 뽑을지가 코드마다 제각각이어서, API 진입점에서 일관된 기준을 잡을 수 없다는 것이다.

클라이언트 요청에서 백엔드로 넘겨야 할 값을 어디서, 어떤 기준으로 추출할 것인가?

3구조적 핵심 예시

메서드 요청 구성은 API Gateway가 클라이언트 요청에서 값을 추출하는 방법을 미리 정해 두는 설정이다. 예를 들어 요청 본문의 {"title": "책"}에서 title이라는 필드를 뽑아 백엔드에 넘긴다고 하자. 메서드 요청 구성의 본문 매핑 설정에서 $input.json('$.title') 같은 표현으로 "본문의 title 필드를 가져온다"고 적어 두면, API Gateway가 요청이 들어올 때마다 그대로 실행한다. 쿼리 파라미터나 헤더도 마찬가지로 "이 이름의 파라미터를 그대로 백엔드에 전달한다"고 지정한다. 설정이 곧 약속이 되어, 백엔드 코드가 바뀌어도 요청 진입점의 기준은 흔들리지 않는다.

4단계별 동작 과정

  1. 파라미터 지정(쿼리·경로·헤더)메서드 요청 구성에서 클라이언트가 보낼 것으로 기대하는 쿼리 스트링, 경로 파라미터(경로의 중괄호 값), 헤더의 이름과 필수 여부를 선언한다. 이 값들은 그대로 백엔드 요청으로 전달된다.
  2. 본문 매핑 설정요청 본문 중 어떤 부분을 백엔드로 넘길지를 매핑 표현식으로 정한다. 필요하면 매핑 템플릿을 써서 본문을 백엔드가 원하는 형태로 변환할 수도 있다.
  3. 요청 수신 시 추출·전달실제 요청이 들어오면 API Gateway가 설정된 규칙대로 값을 뽑아 백엔드에 전달한다. 이때 필수로 선언한 값이 없으면 그 요청을 거부할 수 있다.

1상대의 출발점 확인

API를 호출한 클라이언트에게는 상태 코드(200, 404 등)와 응답 본문, 응답 헤더가 돌아간다. 기존 방식에서는 백엔드가 내보내는 응답을 그대로 클라이언트에게 전달했다. 그런데 백엔드가 반환하는 형식은 서버 내부 구조에 맞춰져 있어서, 예를 들어 백엔드는 오류를 {"error": "not found"}로 돌려주는데 클라이언트 쪽 문서에는 404와 다른 형식이 약속되어 있을 수 있다. 백엔드 응답을 있는 그대로 통과시키면 클라이언트가 기대하는 포맷과 상태 코드 체계가 서버 구현에 종속되어 버린다. 한계점은 명확하다. 응답 형식이 백엔드 구현의 변화에 그대로 흔들려, 클라이언트와의 계약(문서상의 응답 규격)을 지킬 수 없다는 것이다.

3구조적 핵심 예시

메서드 응답 구성은 "무엇을 클라이언트에게 돌려줄지"의 계약을 정하는 설정이다. 예를 들어 백엔드가 성공 시 {"result": 3}이라는 본문을 돌려준다고 하자. 메서드 응답 구성에서 상태 코드 200과 응답 본문 모델(이 형식으로 내보낸다는 정의), 헤더(예: Access-Control-Allow-Origin)를 선언해 두면, API Gateway가 백엔드의 통합 응답을 이 형식에 맞춰 클라이언트에게 보낸다. 백엔드가 내부적으로 조금 다른 형식으로 응답해도, 통합 응답 단계(메서드 응답의 반대 방향 변환)에서 맞춘 뒤 내보내므로 클라이언트가 보는 응답 규격은 고정된다.

4단계별 동작 과정

  1. 상태 코드 선언클라이언트에게 노출할 상태 코드를 정의한다(예: 200, 400, 500). 각 상태 코드는 메서드 응답 구성의 하나의 항목이 된다.
  2. 응답 헤더·본문 형식 지정각 상태 코드에 대해 돌려줄 응답 헤더의 이름과 본문의 형식(모델)을 지정한다. 이 선언이 클라이언트 문서와 일치하는 계약이 된다.
  3. 통합 응답과 연결백엔드가 돌려준 응답이 어떤 상태 코드 항목으로 매핑될지를 통합 응답 설정에서 정한다. 실제 호출이 오면 API Gateway가 그 매핑대로 응답을 변환해 클라이언트에게 돌려준다.

3구조적 핵심 예시

요청 검증은 모델(JSON Schema 기반의 데이터 형식 정의)을 이용해 요청을 미리 검사하는 기능이다. 예를 들어 본문 모델에 title은 반드시 문자열이고 price는 0 이상의 숫자라고 정의해 둔다. 클라이언트가 price에 문자열을 넣어 보내면, API Gateway가 본문을 모델과 대조해 형식이 맞지 않음을 판정하고 400 오류를 돌려준다. 이때 백엔드는 아예 호출되지 않는다. 쿼리·경로·헤더 파라미터도 모델의 required 목록에 들어 있으면 누락 시 같은 방식으로 진입점에서 거부된다.

4단계별 동작 과정

  1. 모델 정의요청 형식을 기술하는 모델 데이터 모델(JSON Schema)을 만든다. 각 필드의 타입, 필수 여부, 허용 범위를 여기에 적는다.
  2. 메서드에 검증 연결메서드의 요청 검증 설정을 켜고, 본문 검증은 어떤 모델을 쓸지, 파라미터 검증은 쿼리·경로·헤더의 필수 여부를 검사할지를 지정한다.
  3. 검사 후 통과 또는 거부요청이 들어오면 API Gateway가 모델과 대조해 통과한 요청만 백엔드로 보낸다. 실패한 요청은 400 오류와 함께 원인을 돌려주고 백엔드 호출은 일어나지 않는다.

3구조적 핵심 예시

프록시 리소스와 ANY 메서드는 모든 경로·메서드를 하나의 통합으로 받아내는 설정이다. 경로 정의에 {proxy+}라는 이름의 리소스를 만들면 그 아래의 모든 하위 경로가 전부 이 리소스로 들어오고, 여기에 ANY라는 메서드를 붙이면 GET, POST, PUT, DELETE 등 모든 HTTP 메서드가 이 메서드 하나로 들어온다. 예를 들어 백엔드 Lambda 함수를 이 ANY 메서드에 프록시 통합으로 연결해 두면, /products, /products/42, /users/7/orders 중 어떤 요청이 와도 그대로 Lambda로 전달된다. 원래 경로와 메서드 정보는 통합 요청에 함께 실려 백엔드가 직접 판단할 수 있다.

4단계별 동작 과정

  1. 프록시 리소스 정의{proxy+} 경로로 리소스를 만든다. 이 리소스는 그 아래에 존재하는 모든 하위 경로를 대표한다.
  2. ANY 메서드 부착그 리소스에 ANY라는 메서드를 붙인다. ANY는 모든 HTTP 메서드의 요청을 받아들이는 메서드다.
  3. 단일 통합으로 중계이 ANY 메서드에 백엔드(예: Lambda)를 프록시 통합으로 연결한다. 들어온 모든 요청의 경로·메서드·헤더·본문을 그대로 백엔드에 전달하고, 백엔드 응답을 다시 클라이언트에게 돌려준다.

3단계 REST API — 통합(Integration)

REST API 메서드가 백엔드(Lambda, HTTP, AWS 서비스, 프라이빗, 모의)로 요청을 전달하는 방식을 정하는 단계로, 각 요청에 맞는 통합 유형 하나와 프록시/비프록시 방식을 고른다.

1상대의 출발점 확인

REST API의 메서드는 요청을 받아들이기만 하고 실제 처리는 하지 않는다. 실제 처리는 백엔드가 한다. 그런데 백엔드의 종류는 다양하다. 코드를 실행해 주는 Lambda 함수가 될 수도, EC2나 온프레미스(자체 운영 서버)에 띄운 HTTP 서버가 될 수도, 다른 AWS 서비스가 될 수도 있다. 기존 방식에서는 이런 서로 다른 백엔드를 연결하는 방법이 제각각이라, API 게이트웨이 역할을 하는 코드가 각 백엔드의 호출 규격에 맞춰 따로따로 구현되어야 했다. 백엔드가 바뀌면 그 연결 코드도 다시 고쳐야 했다. 한계점은 명확하다. 하나의 API 정의에서 서로 다른 종류의 백엔드로 요청을 넘기는 방법을 일관된 방식으로 정할 수 없다는 것이다.

2질문 제기

종류가 서로 다른 백엔드로 요청을 넘기는 방식을 어떻게 하나의 선택지로 통일해서 정할 수 있을까?

3구조적 핵심 예시

통합 유형 선택은 각 메서드가 "어떤 백엔드에, 어떤 방식으로" 요청을 전달할지를 고르는 단계다. API Gateway의 REST API는 통합 유형으로 Lambda, HTTP, AWS 서비스, 프라이빗, 모의(Mock)의 다섯 가지를 제공한다. 예를 들어 메서드가 Lambda 함수를 호출하도록 하려면 통합 유형으로 Lambda를, 자체 호스팅한 HTTP 서버를 호출하려면 HTTP를, Step Functions 같은 AWS 서비스를 호출하려면 AWS 서비스를 선택한다. 여기에 프록시(통합 방식을 그대로 중계) 방식과 비프록시(요청·응답 매핑을 직접 지정) 방식을 함께 고른다. 이 선택 하나만 바뀌면 요청이 가는 백엔드도 그에 따라 달라진다.

4단계별 동작 과정

  1. 백엔드 종류에 따른 통합 유형 선택Lambda / HTTP / AWS 서비스 / 프라이빗 / 모의 중에서 이 메서드가 연결할 백엔드에 맞는 통합 유형 하나를 고른다. 모의 통합은 백엔드 없이 API Gateway가 미리 정한 응답을 돌려주는 유형이다.
  2. 프록시/비프록시 방식 결정프록시 방식을 고르면 요청을 변환 없이 그대로 백엔드에 넘기고 응답도 그대로 돌려받는다. 비프록시 방식을 고르면 요청·응답 매핑(템플릿)을 직접 작성해 변환을 정한다.
  3. 통합 설정 입력과 연결선택한 유형에 필요한 값(예: Lambda 함수 ARN, HTTP 엔드포인트 URL, AWS 서비스 동작)을 적어 메서드와 백엔드를 연결한다. 이후 요청이 오면 API Gateway가 이 설정대로 백엔드를 호출한다.

Lambda 프록시 통합

클라이언트 요청 전체를 그대로 Lambda 함수의 event 객체로 넘기고, Lambda가 반환하는 JSON 형식의 응답을 그대로 클라이언트에 되돌려주는 가장 단순한 Lambda 통합 방식이다.

1상대의 출발점 확인

API Gateway가 백엔드인 Lambda 함수를 호출하는 기존 방식(커스텀 통합)에서는 요청과 응답을 주고받기 전에 매핑 템플릿을 일일이 작성해야 했습니다. 클라이언트가 보낸 헤더, 쿼리, 경로, 본문 값을 Lambda가 받을 수 있는 자리로 옮기고, Lambda가 돌려주는 응답도 API Gateway가 클라이언트에게 돌려줄 HTTP 응답 형태로 다시 변환해야 했습니다. 요청·응답 형태가 조금만 바뀌어도 매핑 규칙을 고쳐야 했고, 그 규칙이 많아지면 관리가 어려워졌습니다.

2질문 제기

매핑 규칙을 하나도 작성하지 않고, 클라이언트의 요청 전체를 Lambda에 그대로 넘기고 Lambda의 응답을 그대로 되돌려줄 수는 없을까?

3구조적 핵심 예시

API Gateway가 Lambda 프록시 통합으로 요청을 받으면, 들어온 HTTP 요청 전체를 그대로 담은 event 객체를 만들어 Lambda 함수의 입력으로 전달합니다. 이 event 안에는 HTTP 메서드, 경로, 쿼리 문자열, 헤더, 본문, 소스 IP 등이 전부 들어 있습니다. Lambda는 이 event를 읽어 필요한 로직을 실행하고, statusCode(응답 상태 코드), headers(응답 헤더), body(응답 본문)를 담은 JSON 객체를 반환합니다. API Gateway는 그 JSON을 그대로 클라이언트에 HTTP 응답으로 되돌려줍니다.

4단계별 동작 과정

  1. 요청 수집클라이언트가 보낸 HTTP 요청 전체(메서드, 경로, 헤더, 쿼리, 본문)를 그대로 담은 event 객체를 구성해 Lambda 함수에 전달한다.
  2. Lambda 처리 및 응답 구성Lambda가 event 객체에서 필요한 값을 꺼내 로직을 실행하고, statusCode·headers·body를 가진 응답 JSON을 만들어 반환한다.
  3. 응답 전달API Gateway가 Lambda가 반환한 JSON을 그대로 파싱하여 HTTP 응답 상태 코드와 헤더, 본문으로 바꿔 클라이언트에게 되돌려준다.

5본질 요약

매핑 규칙 없이 클라이언트 요청 전체를 Lambda의 event로 넘기고 Lambda의 응답 JSON을 그대로 HTTP 응답으로 되돌려주는 가장 단순한 Lambda 통합 방식

1상대의 출발점 확인

Lambda 프록시 통합은 매핑 작업이 필요 없어 편리하지만, Lambda가 받는 입력 형태와 돌려주는 응답 형태가 API Gateway의 규칙에 묶여 있습니다. 클라이언트의 요청이 그대로 event로 들어가므로 Lambda가 원하는 형식으로 골라 받을 수 없고, 백엔드 응답도 statusCode·headers·body 구조의 JSON이어야 합니다. 기존 Lambda 함수가 이미 다른 형식의 입력을 받도록 짜여 있거나, API Gateway가 백엔드 응답을 기다리지 않고 요청만 넘기고 싶은 경우에는 프록시 통합으로는 맞출 수 없습니다.

2질문 제기

매핑 템플릿으로 주고받는 데이터를 원하는 형태로 직접 변환하고, 백엔드의 응답을 기다리지 않는 호출도 할 수는 없을까?

3구조적 핵심 예시

API Gateway가 커스텀 통합에서 요청을 받으면, 미리 정의한 매핑 템플릿을 적용해 클라이언트 요청의 일부(예: 경로 파라미터와 본문의 특정 필드)만 뽑아 Lambda가 원하는 모양의 JSON으로 변환해 전달합니다. Lambda는 그 입력을 받아 처리하고 응답을 돌려주면, API Gateway가 다시 매핑 템플릿을 적용해 클라이언트가 받을 응답 형태(예: 상태 코드와 본문만 있는 형태)로 변환합니다.

4단계별 동작 과정

  1. 통합 요청 변환매핑 템플릿으로 클라이언트 요청의 일부를 뽑아 백엔드가 원하는 형태의 입력으로 변환한다. 호출 유형을 Event로 설정하면 API Gateway가 Lambda의 응답을 기다리지 않고 요청만 넘긴다.
  2. Lambda 처리변환된 입력으로 Lambda가 로직을 실행하고 결과를 반환한다. 동기 호출이면 응답을 돌려주고, 비동기(Event) 호출이면 Lambda가 요청을 받은 시점에서 처리만 수행한다.
  3. 통합 응답 변환매핑 템플릿으로 Lambda의 응답을 클라이언트에게 돌려줄 HTTP 응답 형태로 변환한다.

HTTP 통합과 응답 스트리밍

공개 HTTP(S) 엔드포인트를 백엔드로 연결하는 통합으로, 전송 모드를 STREAM으로 설정하면 대용량 응답을 조각 단위로 클라이언트에 흘려보낼 수 있다.

1상대의 출발점 확인

백엔드가 Lambda가 아니라 기존에 공개된 HTTP 서버(예: 사내 웹 API나 외부 REST 서비스)라면, Lambda용 통합 방식은 쓸 수 없습니다. 기존 HTTP 통합에서는 API Gateway가 백엔드의 응답 전체를 받아 모은 뒤에야 클라이언트에게 한 번에 전달했습니다. 응답이 크거나, 생성에 오래 걸리는 콘텐츠(예: 대용량 파일, 실시간 데이터)인 경우 클라이언트는 백엔드가 응답을 끝까지 만들 때까지 기다려야 했고, 응답 전체가 메모리에 쌓이므로 부담도 컸습니다.

2질문 제기

클라이언트의 요청을 공개된 HTTP(S) 백엔드로 그대로 전달하면서, 대용량 응답은 완성될 때까지 기다리지 않고 바로 조각 단위로 흘려보낼 수는 없을까?

3구조적 핵심 예시

API Gateway가 HTTP 통합으로 요청을 받으면, 백엔드로 설정한 공개 HTTP(S) 엔드포인트 URL로 요청을 전달합니다. 전송 모드를 STREAM으로 설정하면, 백엔드가 응답을 조금씩 만들어 내보낼 때 API Gateway가 그 조각을 받는 대로 즉시 클라이언트에게 전달합니다. 클라이언트는 전체 응답이 끝나기 전부터 첫 조각을 받아 화면에 표시할 수 있습니다.

4단계별 동작 과정

  1. 요청 전달API Gateway가 클라이언트의 요청을 통합 대상으로 지정된 공개 HTTP(S) 엔드포인트 URL로 그대로 보낸다.
  2. 응답 스트리밍 시작전송 모드가 STREAM이면 백엔드가 보내는 응답의 첫 조각이 도착하는 즉시 API Gateway가 이를 클라이언트에게 전달하기 시작한다. 버퍼링 모드(BUFFERED)라면 응답 전체를 모은 뒤에 보낸다.
  3. 조각 단위 전송백엔드가 응답을 계속 내보내는 동안 API Gateway가 조각을 받는 대로 흘려보내고, 마지막 조각이 전달되면 응답이 끝난다.

5본질 요약

프라이빗 통합과 VPC 링크

VPC 링크를 통해 API Gateway가 같은 VPC 안의 Network Load Balancer 뒤에 있는 프라이빗 리소스(예: ECS, 온프레미스 서버)에 접근하게 하는 통합 방식이다.

1상대의 출발점 확인

보안상의 이유로 백엔드(예: ECS 컨테이너나 온프레미스 서버)를 인터넷에 노출하지 않고 VPC 안에만 두는 경우가 많습니다. 그런데 기존의 Lambda 통합이나 HTTP 통합은 인터넷을 통해 공개된 대상에만 요청을 보낼 수 있어, VPC 안에만 있는 리소스에는 연결할 수 없었습니다. 백엔드를 인터넷에 공개하면 보안 위험이 생기고, 닫아 두면 API Gateway가 접근할 방법이 없었습니다.

2질문 제기

백엔드를 인터넷에 공개하지 않고도, 같은 VPC 안에 있는 프라이빗 리소스에 API Gateway가 안전하게 접근하게 할 수는 없을까?

3구조적 핵심 예시

API Gateway가 요청을 받으면, VPC 링크를 통해 VPC 내부로 연결됩니다. VPC 링크는 API Gateway와 VPC 안의 Network Load Balancer(NLB)를 연결해 주는 통로입니다. NLB는 요청을 받아 뒤에 있는 프라이빗 리소스(예: ECS 서비스의 컨테이너)로 전달합니다. 백엔드는 인터넷에 노출되지 않고 VPC 안에서만 트래픽을 주고받습니다.

4단계별 동작 과정

  1. VPC 링크 생성API Gateway가 접근할 VPC에 NLB를 준비하고, API Gateway와 그 NLB를 연결하는 VPC 링크를 생성한다.
  2. 프라이빗 통합 설정REST API의 통합 대상으로 해당 VPC 링크와 NLB의 리스너(포트와 프로토콜)를 지정한다.
  3. 요청 전달클라이언트 요청이 들어오면 API Gateway가 VPC 링크를 통해 NLB로 보내고, NLB가 뒤의 프라이빗 리소스(예: ECS, 온프레미스 서버)로 전달해 응답을 되돌려받는다.

1상대의 출발점 확인

클라이언트가 보내는 값은 헤더, 쿼리 문자열, 경로, 본문 등 여러 위치에 제각각 흩어져 있습니다. 그런데 백엔드는 자신이 원하는 위치와 이름으로 값을 받아야 합니다. 예를 들어 클라이언트는 본문 JSON의 userId 필드로 보내는데, 백엔드는 헤더의 X-User-Id로 받는 식입니다. 값의 위치와 이름이 안 맞으면 매번 백엔드 코드에서 값을 찾아 다시 꺼내야 하고, 어떤 필드가 어디로 들어오는지 일일이 맞춰야 했습니다.

2질문 제기

클라이언트가 보낸 헤더·쿼리·경로·본문 값을 백엔드가 원하는 위치와 이름으로 옮겨 주거나 고정값으로 대체해 주는 규칙을 만들 수는 없을까?

3구조적 핵심 예시

REST API에서 통합 요청이나 통합 응답에 파라미터 매핑 규칙을 정의하면, API Gateway가 요청을 백엔드로 보내기 전에 값을 옮겨 줍니다. 예를 들어 클라이언트가 보낸 쿼리 문자열 ?limit=10을 백엔드가 기대하는 헤더 X-Limit: 10으로 바꿔 보내는 식입니다. 백엔드의 응답 중 특정 값(예: JSON의 status 필드)을 클라이언트에게 돌려줄 HTTP 상태 코드로 바꾸는 변환도 이 규칙으로 합니다.

4단계별 동작 과정

  1. 매핑 규칙 작성통합 요청(또는 통합 응답) 설정에서 클라이언트 값의 출처(헤더·쿼리·경로·본문)와 백엔드로 보낼 위치·이름, 또는 고정값을 지정한다.
  2. 값 변환 수행요청이 지나갈 때 API Gateway가 규칙을 적용해 값을 읽어 지정된 위치와 이름으로 옮기거나 고정값으로 대체한다.
  3. 변환된 요청 전달변환이 끝난 요청을 백엔드로 보내고, 응답 통로에서도 같은 방식으로 백엔드 응답을 클라이언트용 형태로 변환해 되돌려준다.

3구조적 핵심 예시

  3. 응답 변환백엔드 응답에 등록된 응답 매핑 템플릿이 있으면 그 형식으로 바꾼 뒤 클라이언트에게 반환한다.

1상대의 출발점 확인

브라우저는 보안 규칙 때문에 현재 페이지의 도메인과 다른 도메인(오리진 — 프로토콜·도메인·포트 조합)으로 API를 호출할 때, 실제 요청 전에 사전 요청(Preflight — OPTIONS 메서드로 호출 가능 여부를 묻는 요청)을 먼저 보내고 응답에 Access-Control-Allow-Origin 헤더가 없으면 실제 응답을 차단한다. CORS 헤더를 구성하지 않은 기존 방식에서는 브라우저 기반 클라이언트가 다른 도메인에 있는 API를 아무리 호출해도 결과를 사용할 수 없었다. 그 한계는 정적 사이트 같은 프론트엔드와 API 서버의 도메인이 달라질 때마다 별도 프록시를 두거나 헤더를 직접 관리해야 한다는 점이다.

2질문 제기

브라우저가 다른 도메인에서도 우리 API를 호출할 수 있게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

프론트엔드(https://app.example.com)에서 https://api.example.com/products 를 fetch로 호출한다. API Gateway 메서드에 CORS를 활성화하면, Gateway가 OPTIONS 사전 요청에 대해 Access-Control-Allow-Origin: https://app.example.com 같은 헤더를 자동으로 포함해 응답하고, 실제 GET 요청의 응답에도 같은 허용 헤더를 붙여 준다. 브라우저는 이 헤더를 확인한 뒤에야 응답을 프론트엔드 코드에서 사용할 수 있다.

  1. 사전 요청 수신브라우저가 실제 요청 전에 OPTIONS 메서드로 사전 요청을 보낸다.
  2. 허용 헤더 응답API Gateway가 설정된 Access-Control-* 헤더(허용 오리진·메서드·헤더)를 담아 사전 요청에 응답한다.
  3. 실제 요청 처리브라우저가 사전 요청을 통과시키고 실제 요청을 보내면, Gateway는 응답에 Access-Control-Allow-Origin 헤더를 다시 붙여 반환하고 브라우저가 그 결과를 사용한다.

API Gateway가 특정 Content-Type(image·video 등)의 본문을 base64 문자열이 아닌 원본 바이너리로 처리하도록 지정하는 설정

1상대의 출발점 확인

API Gateway는 기본적으로 페이로드를 텍스트 데이터(JSON)로 다룬다. 그래서 image나 video 같은 바이너리 데이터를 주고받을 때 기존 방식은 본문을 base64 문자열(바이너리 데이터를 텍스트 문자로 인코딩한 형식)로 변환해 전달했다. 그 결과 전송되는 데이터 크기가 늘어나고, 클라이언트와 백엔드 양쪽에서 인코딩·디코딩 작업을 반복해야 했다. 그 한계는 대용량 파일일수록 오버헤드가 커지고, 원본 바이너리 형식을 그대로 보존해야 하는 경우에 맞지 않다는 점이다.

2질문 제기

이미지나 비디오 같은 바이너리 데이터를 base64로 감싸지 않고 원본 그대로 주고받을 수는 없을까?

4단계별 동작 과정

  1. 타입 등록binaryMediaTypes 설정에 바이너리로 처리할 Content-Type(image/png, video/mp4 등)을 등록한다.
  2. 바이너리 전달해당 Content-Type의 요청·응답 본문을 base64 변환 없이 원본 바이너리 그대로 백엔드와 주고받는다.
  3. 헤더 유지 응답Content-Type을 포함한 헤더를 유지한 채 최종 응답을 클라이언트에게 반환한다.

1상대의 출발점 확인

API의 정의(메서드, 통합 설정 등)를 아무리 수정해도, 수정된 상태를 배포(변경 사항을 확정해 서비스에 반영하는 작업)하지 않으면 실제 호출에는 반영되지 않는다. 기존 방식에서는 배포라는 개념이 없으면 "언제 어떤 상태가 서비스되는지"가 통제되지 않고, 개발 환경과 운영 환경의 URL을 구분해서 제공할 구조도 없어서 모든 변경이 바로 반영되거나 반영되지 않는 이분법만 존재했다. 그 한계는 변경 사항의 반영 시점을 정할 수 없고, 환경별로 서로 다른 버전을 같은 API에서 서비스할 수 없다는 점이다.

2질문 제기

API의 변경 사항을 확정해 특정 환경의 URL로 서비스에 반영하려면 어떻게 해야 할까?

3구조적 핵심 예시

개발 중인 API를 수정한 뒤 "dev"라는 스테이지로 배포하면 https://api-id.execute-api.region.amazonaws.com/dev/... 형태의 URL이 생성되고, 그 URL은 배포 시점의 API 스냅샷을 서비스한다. 다시 수정한 뒤 새 배포를 만들어 같은 "dev" 스테이지에 올리면 URL은 그대로 두고 내용만 새 스냅샷으로 교체된다. "prod" 스테이지에는 이전 버전을 그대로 둘 수 있다.

4단계별 동작 과정

  1. 배포 생성API의 현재 상태를 스냅샷으로 고정한 배포(deployment)를 만든다.
  2. 스테이지 연결만들어진 배포를 원하는 스테이지(stage — API 버전의 환경 단위, 예: dev, prod)에 올려 그 스테이지의 URL을 부여한다.
  3. 서비스 노출클라이언트가 해당 스테이지 URL로 호출하면 그 스냅샷 기준의 API가 응답한다. 스테이지마다 서로 다른 배포를 각각 서비스할 수 있다.

4단계별 동작 과정

카나리아 릴리스

새 배포를 스테이지 트래픽의 일부에만 적용해 점진적으로 검증한 뒤 전체로 승격(promote)하는 릴리스 방식.

1상대의 출발점 확인

API Gateway에 새 버전의 API를 배포하면 기본적으로 스테이지(배포된 API 버전이 살아 있는 환경 단위)의 트래픽 전체가 즉시 새 버전으로 전환됩니다. 코드에 오류가 있거나 응답 형식이 바뀌어 클라이언트가 깨지는 경우, 문제를 발견한 시점에는 이미 모든 사용자가 새 버전을 호출하고 있어 장애 영향 범위가 전체 사용자로 커집니다. 배포를 되돌리려면 다시 이전 버전을 배포해야 하고, 그 사이에도 오류 응답이 계속 나갑니다. 이렇게 전량 교체 방식은 새 버전을 안전하게 검증할 수단이 없다는 한계가 있습니다.

2질문 제기

새 배포를 전체 사용자에게 한꺼번에 적용하지 않고, 일부 트래픽으로 먼저 검증한 뒤 점진적으로 확대할 수는 없을까요?

3구조적 핵심 예시

스테이지에 카나리아 릴리스를 켜면 새 배포는 카나리아(전체 트래픽 중 일부 비율로 나가가는 새 버전)로 배포되고, 기존 배포는 나머지 트래픽을 계속 받습니다. 예를 들어 카나리아 비율을 10%로 설정하면 요청 100건 중 10건은 새 버전으로, 90건은 기존 버전으로 보내집니다. 새 버전이 안정적이라고 확인되면 카나리아를 전체 트래픽으로 승격(promote)해 새 버전이 모든 요청을 처리하게 만듭니다.

4단계별 동작 과정

  1. 카나리아 배포스테이지에 새 버전을 카나리아로 배포하고 이때 받을 트래픽 비율(예: 10%)을 정합니다. 기존 버전은 그대로 남아 나머지 요청을 처리합니다.
  2. 비율 기반 트래픽 분배API Gateway가 요청마다 카나리아 비율에 따라 새 버전과 기존 버전 중 하나로 보냅니다. 새 버전 응답과 기존 버전 응답을 함께 관찰하며 오류율·지연 시간을 비교합니다.
  3. 승격 또는 폐기문제가 없으면 카나리아를 전체 트래픽으로 승격해 새 버전만 남기고, 문제가 있으면 카나리아를 폐기해 기존 버전을 그대로 유지합니다.

커스텀 도메인 이름

API Gateway가 발급한 기본 실행 URL 대신 소유한 도메인 이름으로 API를 호출할 수 있게 연결하는 기능.

1상대의 출발점 확인

API Gateway는 API를 배포하면 스테이지마다 기본 실행 URL(예: https://api-id.execute-api.region.amazonaws.com/stage)을 자동으로 발급합니다. 이 URL은 API마다 임의의 식별자가 붙고 리전 이름이 들어가 있어 길고 기억하기 어렵습니다. 클라이언트 코드에 이런 URL이 그대로 들어가면 도메인을 바꿀 수 없고, 회사의 브랜드와도 맞지 않습니다. 관리·보안 정책도 이 임의 도메인 기준으로 잡아야 해서 운영이 불편합니다.

2질문 제기

길고 임의적인 기본 실행 URL 대신, 내가 소유한 도메인 이름으로 API를 호출하게 만들 수는 없을까요?

3구조적 핵심 예시

api.example.com이라는 도메인을 소유하고 있다면, 이 도메인에 대한 SSL 인증서(HTTPS 통신에서 신원을 증명하는 증서)를 등록한 커스텀 도메인 이름을 API Gateway에 만들고, 이 도메인을 특정 API의 스테이지에 연결합니다. 그 후 DNS(도메인 이름을 IP 주소로 바꿔주는 시스템) 설정에서 api.example.com이 커스텀 도메인 이름이 부여한 대상 주소를 가리키게 하면, 클라이언트는 https://api.example.com으로 해당 API를 호출하게 됩니다.

4단계별 동작 과정

  1. 커스텀 도메인 이름 생성과 연결소유한 도메인의 SSL 인증서를 등록하고, API Gateway에서 커스텀 도메인 이름을 만든 뒤 연결할 API와 스테이지를 지정합니다. 커스텀 도메인 이름은 연결된 스테이지의 기본 실행 URL을 대신해 요청을 받아 해당 API로 전달합니다.
  2. DNS 레코드 설정도메인 서비스에서 api.example.com이 API Gateway가 알려준 대상 주소(API Gateway 도메인)를 가리키도록 CNAME(별칭 레코드)을 추가합니다.
  3. Path 매핑으로 호출 경로 정리필요에 따라 커스텀 도메인 경로(예: /v1)를 특정 스테이지에 매핑해, URL에 스테이지 이름을 직접 노출하지 않고 원하는 경로로 API를 호출하게 합니다.

API 캐싱과 콘텐츠 압축

응답을 캐시해 백엔드 부하와 대기 시간을 줄이고, 페이로드를 압축해 전송량을 줄이는 성능 최적화 기능.

1상대의 출발점 확인

클라이언트가 같은 API를 반복 호출하면 매번 API Gateway를 거쳐 백엔드(실제 데이터를 만들어 주는 서버)까지 요청이 전달되고, 백엔드는 같은 계산을 다시 수행해 응답을 만듭니다. 응답 내용이 자주 바뀌지 않는데도 매번 재계산하면 백엔드 부하가 쌓이고, 네트워크를 오가는 동안 응답이 크면 전송 시간도 길어져 지연 시간이 늘어납니다. 데이터가 많아 응답 페이로드(요청·응답으로 주고받는 본문 데이터)가 크면 대역폭 비용까지 증가합니다.

2질문 제기

변하지 않는 응답을 매번 백엔드까지 가서 다시 만들지 않게 하고, 큰 응답은 줄여서 보낼 수는 없을까요?

3구조적 핵심 예시

API 메서드에 캐시를 켜면 첫 요청의 응답이 API Gateway의 캐시(지정한 용량의 임시 저장 공간)에 저장되고, 같은 키(예: 같은 경로·쿼리 파라미터)의 다음 요청은 백엔드로 가지 않고 캐시에 저장된 응답을 즉시 돌려줍니다. 응답 압축을 켜면 클라이언트가 압축을 지원한다고 알려올 때 API Gateway가 응답 본문을 gzip(데이터 압축 형식)으로 줄여 보냅니다.

4단계별 동작 과정

  1. 캐시 적중 판정요청이 들어오면 API Gateway가 캐시 키(요청 경로·파라미터 조합)로 저장된 응답이 있는지 확인합니다. 있으면 백엔드 호출 없이 캐시 응답을 즉시 반환합니다.
  2. 캐시 미스 시 백엔드 호출과 저장저장된 응답이 없으면 백엔드로 요청을 보내 응답을 받은 뒤, 그 응답을 캐시에 저장하고 TTL(캐시 유지 시간)을 적용합니다.
  3. 응답 압축 전송클라이언트가 Accept-Encoding 헤더로 압축을 지원하면 응답 본문을 gzip으로 압축해 전송하고, 크기가 줄어든 페이로드를 받은 클라이언트는 이를 풀어서 사용합니다.

반복되는 응답을 API Gateway 단계에서 캐시해 백엔드 부하와 지연 시간을 줄이고, 응답 본문을 압축해 전송량과 대역폭 비용을 줄이는 성능 최적화 기능

커스텀 도메인 라우팅과 DNS 장애 조치

커스텀 도메인으로 들어온 트래픽을 API 매핑과 라우팅 규칙에 따라 보낼 API에 분배하고 DNS 장애 조치로 가용성을 높이는 기능.

1상대의 출발점 확인

커스텀 도메인 하나는 기본적으로 연결된 하나의 API만 받아줍니다. 도메인을 바꾸지 않고 다른 API로 트래픽을 보내려면 DNS 레코드를 직접 수정해 대상 주소를 바꿔야 하는데, DNS 변경은 전파(변경 사항이 전 세계 DNS 서버에 퍼지는 과정)에 시간이 걸려 즉시 반영되지 않습니다. 또 하나의 API가 장애로 응답하지 못할 때 같은 도메인으로 들어오는 트래픽을 정상 API로 옮길 수단이 없어, 단일 지점 장애가 그대로 사용자에게 전달됩니다.

2질문 제기

커스텀 도메인 하나로 여러 API에 트래픽을 분배하고, 특정 API가 죽어도 DNS를 손대지 않고 정상 API로 트래픽을 돌릴 수는 없을까요?

3구조적 핵심 예시

API Gateway의 엣지 최적화 커스텀 도메인(라우팅 모드를 지원하는 커스텀 도메인 형태)은 경로별 라우팅 규칙을 가집니다. 예를 들어 api.example.com/orders는 주문 API로, api.example.com/users는 사용자 API로 보내도록 설정해 두면, 도메인 하나가 경로만으로 여러 API를 구분합니다. 각 라우팅 규칙에는 우선순위가 매겨진 대상 API 목록을 둘 수 있어, 첫 번째 API가 장애로 응답하지 못하면 자동으로 다음 대상으로 요청을 보냅니다.

4단계별 동작 과정

  1. 도메인과 라우팅 규칙 생성커스텀 도메인을 만들고 경로(예: /orders)마다 기본 대상이 될 API와 스테이지를 우선순위와 함께 등록합니다.
  2. 경로 기반 분배요청이 도메인으로 들어오면 경로에 맞는 라우팅 규칙을 찾아 그 규칙의 첫 번째 대상 API로 요청을 전달합니다.
  3. 장애 조치첫 번째 대상이 장애로 판정되면 같은 규칙의 다음 순위 대상 API로 요청을 자동 전달하고, 도메인 자체는 계속 같은 주소로 동작합니다.

5본질 요약

IAM 권한과 호출 제어

IAM 권한과 AWS Signature Version 4 서명 요청으로 API 메서드 호출을 허용하거나 거부하는 접근 제어 방식.

1상대의 출발점 확인

API를 배포만 하면 스테이지 URL을 아는 누구든 그 API를 호출할 수 있습니다. 호출을 제한하지 않으면 외부에서 무단으로 데이터를 읽거나, 요금이 부과되는 호출이 늘어나 비용이 커집니다. API 키나 토큰만으로는 "누가 호출하는지"를 AWS 계정 차원에서 검증하기 어렵고, 서버 간 호출처럼 AWS 내부 자격 증명으로 실행되는 요청은 개별적으로 관리가 필요합니다.

2질문 제기

AWS 계정의 자격 증명(자격 증명)과 권한 체계를 그대로 이용해, 특정 사용자·서비스만 특정 API 메서드를 호출하게 제어할 수는 없을까요?

3구조적 핵심 예시

API 메서드의 인증 방식을 AWS IAM(사용자·역할·정책으로 AWS 접근 권한을 관리하는 서비스)으로 설정해 두면, 호출자는 AWS Signature Version 4(자격 증명의 비밀 키로 요청에 서명하는 방식)로 서명한 요청을 보냅니다. 예를 들어 GetUser 역할을 가진 응용 프로그램만 GET /users를 호출할 수 있게 IAM 정책으로 허용하고, 그 외 요청은 거부됩니다. API Gateway는 받은 서명을 검증하고, 호출자의 IAM 권한에 그 메서드 호출이 허용되어 있는지 확인해 통과시킵니다.

4단계별 동작 과정

  1. 요청 서명호출자가 자격 증명의 액세스 키와 시크릿 키로 요청의 본문·헤더·시간을 조합해 Signature Version 4 서명을 만들고, 이를 헤더에 넣어 요청을 보냅니다.
  2. 서명 검증과 권한 확인API Gateway가 서명이 유효한지(발신자가 자격 증명의 소유자인지) 확인하고, 호출자의 IAM 정책에 해당 메서드 호출을 허용하는 권한이 있는지 검사합니다.
  3. 허용 또는 거부유효한 서명과 허용 권한이 모두 확인되면 요청을 백엔드로 전달하고, 서명이 틀리거나 권한이 없으면 403(권한 없음) 응답을 돌려줍니다.

리소스 정책

API 리소스에 JSON 정책을 붙여 허용된 계정·IP·VPC 등에서만 접근하게 하는 리소스 기반 접근 제어.

1상대의 출발점 확인

IAM 권한은 "호출자(누구)"를 기준으로 접근을 제어합니다. 하지만 호출자 기준 제어만으로는 "어디서(어떤 IP 대역·VPC)" 오는 요청인지, "어느 AWS 계정"에서 오는 요청인지를 한 번에 막을 수 없습니다. 예를 들어 회사 사무실 IP 대역 밖에서 온 요청을 전부 차단한다거나, 특정 AWS 계정의 서비스만 호출하게 하려면 각 호출자의 IAM 설정을 개별로 관리해야 하는데, 호출자 수가 많아질수록 관리가 어렵습니다.

2질문 제기

각 호출자의 개별 권한 설정과는 별개로, API 리소스 자체에 "이런 조건에서만 접근 가능"이라는 규칙을 붙일 수는 없을까요?

3구조적 핵심 예시

API에 리소스 정책(JSON으로 작성된 접근 규칙 문서)을 붙이면, 예를 들어 "오피스 IP 대역 203.0.113.0/24(사무실 네트워크 주소 범위)에서 오는 요청만 허용"하고 나머지는 모두 거부하도록 설정할 수 있습니다. 정책은 호출자와 무관하게 API가 받는 모든 요청에 적용되므로, 정책 조건에 맞지 않는 요청은 어떤 자격 증명을 쓰든 API에 도달하기 전에 거부됩니다.

4단계별 동작 과정

  1. 정책 작성과 적용리소스 정책에 허용할 계정·IP 대역·VPC 등의 조건을 JSON으로 작성해 API에 붙입니다.
  2. 요청 조건 대조요청이 들어오면 API Gateway가 요청의 출처(호출 계정, 소스 IP, VPC 여부)를 정책 조건과 대조합니다.
  3. 허용 또는 거부조건에 맞는 요청만 다음 인증·권한 단계로 진행하고, 조건에 맞지 않는 요청은 거부 응답을 돌려줍니다.

Lambda 권한 부여자

요청 시 Lambda 함수가 토큰이나 요청 컨텍스트를 검증해 IAM 정책을 반환하는 사용자 지정 권한 부여 방식.

1상대의 출발점 확인

API Gateway는 기본적으로 API 키만 있으면 요청을 통과시키는 방식으로 동작했다. API 키는 요청을 보내는 클라이언트가 누구인지는 구분해 주지만, 그 클라이언트가 어떤 권한을 가졌는지, 요청에 담긴 토큰이 유효한지까지는 검증하지 못한다. 그래서 API 자체는 열려 있고, 인증과 권한 검사는 백엔드 서버가 매번 따로 해야 했다. 백엔드마다 토큰 검증 코드를 중복 구현해야 하고, 인증에 실패한 요청도 일단 API까지 통과한 뒤에야 걸러지므로 불필요한 백엔드 부하와 보안 허점이 생겼다.

2질문 제기

API Gateway가 요청을 백엔드로 보내기 전에, 들어온 토큰이나 요청 내용을 검사해 통과 여부를 스스로 결정할 수는 없을까?

3구조적 핵심 예시

클라이언트가 Authorization 헤더에 "Bearer <토큰>" 형식의 토큰을 넣어 요청을 보내면, Lambda 권한 부여자로 지정된 Lambda 함수가 그 토큰을 받는다. 이 함수는 토큰의 서명과 만료 시간을 확인하고, 유효하면 "이 요청을 허용한다"는 IAM 정책(어떤 리소스에 어떤 동작을 허용할지 적은 문서)을 돌려준다. API Gateway는 이 정책에 따라 요청을 통과시키거나 거부한다. 토큰이 없거나 유효하지 않으면 함수가 거부 정책을 반환하고 클라이언트는 401 응답을 받는다.

4단계별 동작 과정

  1. 토큰 검증Lambda 함수가 요청 헤더에서 토큰을 꺼내 서명, 만료 시간, 발급처를 확인해 유효성을 판단한다.
  2. 정책 반환검증 결과에 따라 허용 또는 거부를 나타내는 IAM 정책(어느 리소스에 어떤 작업을 허용할지 정의한 문서)을 API Gateway에 돌려준다.
  3. 요청 처리 결정API Gateway가 반환된 정책을 보고 요청을 백엔드로 보내거나, 401/403 응답을 클라이언트에 돌려보낸다.

5본질 요약

API Gateway가 백엔드로 요청을 보내기 전에 Lambda 함수가 토큰을 검증하고 IAM 정책으로 승인 여부를 결정하게 하는 사용자 지정 권한 부여 방식

Cognito 사용자 풀 권한 부여자

Amazon Cognito 사용자 풀이 발급한 토큰을 검증해 요청을 승인하는 권한 부여 방식.

1상대의 출발점 확인

사용자 가입과 로그인을 직접 구현할 때는 비밀번호 저장, 토큰 발급, 만료 처리, 재발급 같은 인증 관련 코드를 전부 백엔드에 직접 작성해야 했다. Token Authorizer를 쓰더라도 토큰 검증 로직을 담당하는 Lambda 함수를 하나 더 만들고 유지해야 했다. 계정 수가 늘어날수록 인증 코드를 관리하고 보안 취약점을 막는 부담이 커졌고, 로그인·가입 화면부터 토큰 만료 관리까지 매 API마다 비슷한 작업을 반복해야 했다.

2질문 제기

가입과 로그인, 토큰 발급과 검증까지 전부 관리해 주는 인증 서비스를 API Gateway에 바로 연결할 수는 없을까?

3구조적 핵심 예시

Amazon Cognito 사용자 풀(사용자 계정과 로그인 정보를 저장·관리하는 서비스)이 사용자 가입과 로그인을 전담한다. 사용자가 로그인하면 Cognito가 ID 토큰과 액세스 토큰을 발급하고, 클라이언트는 이 토큰을 요청에 실어 보낸다. API Gateway는 Cognito 사용자 풀 권한 부여자로 설정된 인증 방식을 통해 토큰의 서명과 유효성을 Cognito 쪽 설정만으로 검증하고, 통과한 요청만 백엔드로 보낸다. 토큰 검증을 위한 별도 함수는 필요 없다.

4단계별 동작 과정

  1. 토큰 발급사용자가 Cognito 사용자 풀에 로그인하면 Cognito가 서명된 토큰(발급처와 만료 정보가 담긴 인증용 문자열)을 클라이언트에 발급한다.
  2. 토큰 검증클라이언트가 토큰을 실어 보낸 요청을 API Gateway가 Cognito 설정에 등록된 공개 키로 서명과 만료를 검증한다.
  3. 요청 전달 또는 거부검증에 성공하면 요청에 포함된 사용자 정보와 함께 백엔드로 전달하고, 실패하면 401 응답을 돌려보낸다.

상호 TLS와 백엔드 인증서

클라이언트 인증서를 요구하는 상호 TLS와, API Gateway가 백엔드로 보내는 요청의 신원을 증명하는 백엔드 인증서로 API를 보호하는 기능.

1상대의 출발점 확인

기존에는 클라이언트가 API Gateway에 접속할 때 TLS(통신을 암호화하는 보안 계층)로 서버의 신원만 확인했다. 서버가 클라이언트의 신원을 확인하지 않으므로, 유효한 인증 정보만 있으면 누구든 요청을 보낼 수 있었다. 반대로 API Gateway가 백엔드로 요청을 보낼 때는 백엔드가 호출하는 쪽의 신원을 확인할 방법이 없어, 백엔드가 공개된 주소에 노출되면 외부에서 직접 요청을 보낼 위험이 있었다.

2질문 제기

클라이언트도 증명서를 제시하게 하여 API에 접근하는 주체를 양쪽에서 확인하고, API Gateway가 백엔드에 보내는 요청도 신뢰할 수 있는 출처임을 증명할 수는 없을까?

3구조적 핵심 예시

상호 TLS를 켜면 클라이언트가 API Gateway에 접속할 때 자신의 클라이언트 인증서도 함께 제출해야 한다. API Gateway는 등록해 둔 신뢰할 수 있는 인증서 목록과 대조해 일치하는 경우에만 요청을 받아들인다. 반대로 API Gateway가 백엔드로 요청을 보낼 때는 백엔드 인증서(API Gateway가 요청에 서명할 때 사용하는 증명서)를 사용해 자신의 신원을 증명하고, 백엔드는 이 증명서를 확인한 요청만 허용한다.

4단계별 동작 과정

  1. 클라이언트 인증서 확인클라이언트가 인증서를 제출하면 API Gateway가 미리 등록된 신뢰 인증서 목록과 대조하고, 키 사용 정보까지 확인해 맞지 않으면 연결을 거부한다.
  2. 요청 수락인증서가 유효한 요청만 백엔드 단계로 통과시킨다.
  3. 백엔드 인증서 서명API Gateway가 요청을 백엔드로 보낼 때 백엔드 인증서로 서명해, 백엔드가 이 요청이 API Gateway에서 왔음을 확인하고 수락한다.

AWS WAF와 스로틀링

AWS WAF 웹 ACL로 악성 트래픽을 차단하고, 계정·메서드 단위 스로틀링으로 요청 속도를 제한해 API를 보호하는 기능.

1상대의 출발점 확인

API가 공개되면 정상 사용자 외에도 SQL 주입 같은 악성 요청이나 대량의 자동 요청이 계속 들어올 수 있다. 기존에는 이런 트래픽을 걸러내려면 별도 방화벽 장비를 두거나 백엔드 서버에서 일일이 요청을 검사해야 했다. 또 요청이 한꺼번에 몰리면 백엔드가 처리 한도를 넘어 느려지거나 다운될 수 있었는데, 이를 막을 속도 제한 기능도 API 앞 단계에 기본으로 없었다.

2질문 제기

백엔드에 도달하기 전에 악성 트래픽을 차단하고, 요청 속도를 제한해 과부하로부터 API를 보호할 수는 없을까?

3구조적 핵심 예시

AWS WAF(웹 요청을 규칙으로 검사해 차단하는 관리형 방화벽)의 웹 ACL을 API Gateway에 연결하면, SQL 주입 패턴이나 특정 IP의 과도한 요청 같은 조건에 맞는 요청을 API에 들어오기 전에 차단한다. 여기에 스로틀링(일정 시간 동안 허용할 요청 수를 제한하는 기능)을 함께 설정하면 초당 요청 수가 한도를 넘으면 추가 요청에 429 응답(요청이 너무 많다는 오류)을 돌려보낸다. 두 기능 모두 백엔드 호출 전 단계에서 동작한다.

4단계별 동작 과정

  1. WAF 규칙 검사요청이 API Gateway에 도착하면 웹 ACL의 규칙들이 SQL 주입이나 악성 패턴을 포함하는지 검사하고, 해당하면 즉시 차단한다.
  2. 속도 제한 확인통과한 요청에 대해 계정 수준이나 메서드 단위로 설정된 초당 허용량을 넘겼는지 확인하고, 넘겼으면 429 응답을 돌려보낸다.
  3. 정상 요청 전달모든 검사를 통과한 요청만 백엔드로 전달된다.

1상대의 출발점 확인

기존 REST API는 인터넷을 통해 누구나 접근할 수 있는 공개 엔드포인트로 배포되었다. 공개 주소가 있으면 방화벽 규칙이나 인증으로 막더라도 인터넷 경로 자체가 열려 있어, 공격 표면이 생기고 보안 검토 부담이 컸다. 회사 내부 시스템처럼 인터넷에 전혀 노출되면 안 되는 API는 공개 엔드포인트 방식으로는 요구사항을 충족할 수 없었다.

2질문 제기

API를 인터넷에 노출하지 않고, VPC 안의 내부 네트워크에서만 호출 가능한 형태로 제공할 수는 없을까?

3구조적 핵심 예시

프라이빗 REST API는 API Gateway에 인터페이스 VPC 엔드포인트(인터넷을 거치지 않고 VPC 내부에서 AWS 서비스에 연결하는 진입점)를 연결해 배포된다. VPC 안의 리소스들은 이 엔드포인트의 프라이빗 DNS 주소로 API를 호출한다. 요청은 인터넷에 나가지 않고 AWS 내부 네트워크를 통해서만 전달되므로, 인터넷에서 주소를 찾을 수 없고 VPC 외부에서는 접근할 방법이 없다.

4단계별 동작 과정

  1. 엔드포인트 연결VPC에 인터페이스 VPC 엔드포인트를 만들고, 이 엔드포인트가 단계(스테이지)의 프라이빗 DNS 주소로 API Gateway에 연결되도록 설정한다.
  2. 내부 호출VPC 안의 클라이언트가 프라이빗 DNS 주소로 요청을 보내면, 요청은 인터넷을 거치지 않고 엔드포인트를 통해 API Gateway에 도달한다.
  3. 엔드포인트 정책 적용엔드포인트에 연결된 리소스 정책으로 특정 계정이나 VPC에서 온 요청만 허용하는 접근 제어가 적용된다.

1상대의 출발점 확인

API를 외부 고객이나 여러 팀에 제공할 때, 기존에는 호출 횟수나 사용량을 고객별로 구분해 제한할 방법이 없었다. 모든 호출자가 동일하게 취급되므로 특정 고객이 과도하게 호출하면 전체 API 성능에 영향을 줄 수 있었고, 고객별로 다른 요금이나 서비스 수준을 적용하기도 어려웠다. 누가 얼마나 호출했는지 측정하고 통제하는 기능이 API 앞 단계에 없었다.

2질문 제기

고객별로 서로 다른 호출 한도와 속도 제한을 설정하고, 누가 얼마나 사용했는지 측정·관리할 수는 없을까?

3구조적 핵심 예시

고객에게 API 키(호출자를 식별하는 고유 문자열)를 발급하고, 이 키를 사용 계획(속도 제한과 할당량을 묶어 정의한 설정)에 연결한다. 클라이언트는 요청에 API 키를 실어 보내고, API Gateway는 키를 보고 어떤 사용 계획이 적용되는지 찾아낸다. 그 계획의 초당 허용량을 넘으면 429 응답, 일정 기간 할당량을 소진하면 429 응답을 돌려보내고, 사용량 기록은 별도 로그로 남겨 고객별 호출 수를 확인할 수 있다.

4단계별 동작 과정

  1. 키와 사용 계획 연결API 키를 생성해 고객에게 발급하고, 그 키를 속도 제한(초당 요청 수)과 할당량(일정 기간 최대 호출 수)이 설정된 사용 계획에 연결한다.
  2. 요청 시 키 확인클라이언트가 요청 헤더에 실어 보낸 API 키를 API Gateway가 확인해 해당 사용 계획의 한도와 대조한다.
  3. 한도 적용과 기록한도를 넘은 요청에는 429 응답을 돌려보내고, 정상 호출은 사용량 기록에 집계해 고객별 측정·관리에 활용한다.

3구조적 핵심 예시

  2. 스테이지에 문서 연결정의한 문서 콘텐츠를 특정 스테이지(배포 단위)에 연결한다. 스테이지마다 서로 다른 문서 버전을 게시할 수 있다.
  3. 문서 페이지 게시API Gateway가 문서를 HTML 페이지로 만들어 스테이지 URL로 공개한다. 호출자는 이 페이지에서 요청/응답 형식을 확인하고 그대로 호출할 수 있다.

HTTP API 개요와 라우트

HTTP API는 API Gateway가 제공하는 더 단순하고 저렴한 API 유형으로, 라우트(메서드+경로)가 들어온 요청을 백엔드 통합으로 연결한다.

1상대의 출발점 확인

REST API는 메서드·모델·권한·스테이지 등 기능이 많아 구성할 것이 많고 비용도 상대적으로 높다. Lambda를 연결해 단순한 API를 만들려는 경우에는 이런 기능 대부분이 필요 없다. 기존 방식은 필요한 것보다 훨씬 많은 설정을 하고, 그 설정에 맞는 비용까지 지불해야 했다.

2질문 제기

Lambda 연동 같은 단순한 API를 더 쉽게, 더 싸게 만들 방법은 없을까?

3구조적 핵심 예시

HTTP API에서 라우트(메서드+경로)가 들어온 요청을 백엔드 통합에 바로 연결한다. 예를 들어 GET /items 라우트를 Lambda 함수에 연결해 두면, 클라이언트가 GET /items로 요청을 보냈을 때 그 Lambda 함수가 호출되고 결과가 응답으로 돌아간다. 설정은 라우트 하나와 통합 대상 하나뿐이다.

4단계별 동작 과정

  1. HTTP API 생성REST API 대신 HTTP API 유형으로 API를 만든다. 기능이 줄어든 대신 구성이 단순하고 비용이 낮다.
  2. 라우트 정의메서드와 경로를 조합한 라우트를 정의한다. 예: GET /items, POST /items. 와일드카드 경로(예: /items/{id})도 쓸 수 있다.
  3. 통합 연결각 라우트에 백엔드 통합을 연결한다. 요청이 오면 해당 통합이 실행되어 백엔드(주로 Lambda)의 결과가 응답으로 반환된다.

HTTP API 통합과 파라미터 변환

HTTP API 통합은 Lambda·HTTP·AWS 서비스·프라이빗 백엔드 연결 방식을 뜻하며, 파라미터 매핑으로 요청/응답의 헤더·쿼리·경로 변수를 변환한다.

1상대의 출발점 확인

호출자가 보내는 요청 형식과 백엔드가 기대하는 형식이 항상 같지는 않다. 클라이언트는 쿼리 파라미터로 보내는데 백엔드는 경로 변수를 기대한다든지, 헤더 이름이 다르다든지 하는 경우가 흔하다. 기존 방식은 이런 불일치를 백엔드 코드 안에서 일일이 맞추거나, 별도 변환 로직을 만들어 처리해야 했다. 백엔드마다 기대 형식이 다르면 그 수만큼 변환 코드를 유지해야 한다.

2질문 제기

호출자와 백엔드의 요청·응답 형식이 다를 때, 게이트웨이에서 형식을 맞춰 전달할 수 없을까?

3구조적 핵심 예시

파라미터 매핑으로 요청의 쿼리 파라미터·헤더·경로 변수를 백엔드가 기대하는 위치로 옮긴다. 예를 들어 클라이언트가 ?page=2로 보낸 값을, Lambda가 읽는 경로 변수 /items/{page}의 page로 바꿔 전달하도록 매핑을 정의하면, 클라이언트 형식과 백엔드 형식이 달라도 요청이 정상 처리된다.

4단계별 동작 과정

  1. 통합 유형 선택라우트에 연결할 통합 방식을 정한다. Lambda, HTTP 엔드포인트, AWS 서비스, 프라이빗 백엔드 중에서 대상에 맞게 고른다.
  2. 파라미터 매핑 정의요청과 응답의 헤더·쿼리·경로 변수를 어떻게 바꿀지 매핑 규칙을 작성한다. 값, 위치, 변환 방식도 지정할 수 있다.
  3. 요청 전달요청이 오면 매핑 규칙에 따라 형식을 변환해 백엔드로 보내고, 백엔드의 응답도 매핑에 따라 변환해 클라이언트로 돌려준다.

HTTP API 권한 부여

HTTP API 권한 부여는 JWT·Lambda·IAM 세 가지 방식으로 호출자를 검증해 API 접근을 제어하는 기능이다.

1상대의 출발점 확인

API를 열어 두면 아무나 호출할 수 있어 데이터 노출이나 악용 위험이 있다. 그렇다고 인증 로직을 직접 구현하면 자격 증명 발급·검증·만료 처리까지 모두 관리해야 해서 부담이 크다. 기존 방식은 백엔드 코드 안에 인증을 넣든지, 자체 인증 서버를 만들어야 했기 때문에 API마다 중복된 인증 처리가 생겼다.

2질문 제기

HTTP API를 호출하는 사람이 누구인지 검증하고, 허용된 요청만 백엔드로 통과시키려면 어떻게 해야 할까?

3구조적 핵심 예시

HTTP API의 JWT 권한 부여를 설정하면, 외부 자격 증명 제공자(예: Amazon Cognito)가 발급한 토큰을 API Gateway가 요청마다 검증한다. 예를 들어 클라이언트가 Authorization 헤더에 토큰을 담아 보내면, API Gateway가 그 토큰의 서명과 만료 여부를 확인하고 유효할 때만 라우트를 실행해 백엔드로 연결한다.

4단계별 동작 과정

  1. 권한 부여 방식 선택JWT, Lambda, IAM 세 가지 중에서 검증 방식을 고른다. JWT는 자격 증명 제공자의 토큰을, Lambda는 직접 작성한 검증 로직을, IAM은 AWS 자격 증명을 사용한다.
  2. 자격 증명 소스 설정JWT라면 토큰 발급자와 검증에 쓸 서명 키, 토큰이 들어오는 위치(보통 Authorization 헤더)를 지정한다. Lambda라면 검증 함수와 파라미터를 정한다.
  3. 요청 검증 후 실행요청이 오면 설정한 방식으로 자격 증명을 검증하고, 유효하면 라우트의 통합을 실행하고 유효하지 않으면 접근 거부 응답을 돌려준다.

HTTP API 배포·스테이지·보안 정책

HTTP API 배포와 스테이지는 변경 사항을 환경별 URL로 서비스하는 과정이며, 보안 정책은 연결에 사용할 TLS 보안 프로토콜을 정한다.

1상대의 출발점 확인

기존 방식에서는 API를 수정할 때마다 수정된 코드를 서버에 다시 올려야 했고, 올린 즉시 운영 중인 사용자들이 바로 그 변경 사항을 받게 됐습니다. 그래서 테스트를 위해 잠깐이라도 변경 사항을 따로 띄워 보려면 서버를 하나 더 준비하고 설정을 복사하는 등 수동 작업이 필요했습니다. 또 보안 연결도 서버마다 별도로 인증서를 설치하고 교체 시기를 직접 관리해야 했습니다.

2질문 제기

변경 사항을 운영에 영향을 주지 않으면서 환경별로 나누어 서비스하고, 연결 보안 정책까지 한곳에서 관리할 수는 없을까?

3구조적 핵심 예시

HTTP API에서 배포(deploy)는 현재 API 정의의 스냅샷을 만들어 스테이지(stage)라는 환경 URL에 붙이는 작업입니다. 예를 들어 개발용 스테이지 dev를 만들면 https://{api-id}.execute-api.ap-northeast-2.amazonaws.com/dev 같은 URL이 생기고, 같은 API 정의를 prod 스테이지에도 배포하면 각각 다른 URL로 서로 다른 버전이 서비스됩니다. 이때 스테이지마다 TLS 보안 정책(연결을 암호화하는 데 사용할 프로토콜 버전 집합)을 따로 지정할 수 있습니다.

4단계별 동작 과정

  1. 배포 생성API 정의의 변경 사항을 반영한 새 배포 버전을 만듭니다. 배포는 그 시점의 정의를 고정한 스냅샷입니다.
  2. 스테이지 연결만든 배포를 특정 스테이지(환경 이름)에 연결합니다. 스테이지 이름이 URL 경로에 그대로 나타나고, 스테이지별로 서로 다른 배포 버전을 서비스할 수 있습니다.
  3. 보안 정책 적용스테이지의 보안 정책에서 TLS 프로토콜(암호화 통신 규약) 버전을 지정합니다. 지정한 버전 이상으로만 클라이언트가 연결할 수 있어 오래된 취약한 프로토콜을 차단할 수 있습니다.

5본질 요약

API 정의의 스냅샷인 배포를 환경별 스테이지 URL에 연결해 변경 사항을 안전하게 나누어 서비스하고, 스테이지 단위로 TLS 보안 정책까지 통제하는 것

HTTP API 커스텀 도메인과 모니터링

HTTP API 커스텀 도메인은 소유한 도메인 이름을 API에 연결하는 기능이고, 모니터링은 CloudWatch 지표·로그로 API 상태를 관찰하는 기능이다.

1상대의 출발점 확인

기존 방식에서는 API가 AWS가 자동으로 부여한 기본 도메인({api-id}.execute-api.리전.amazonaws.com)으로만 호출됐습니다. 이 주소는 길고 회사 브랜드와 무관해서 사용자에게 노출하기 어색했고, 리전이나 API를 바꾸면 주소가 통째로 달라져 클라이언트 코드를 고쳐야 했습니다. 또한 API가 잘 동작하는지 확인하려면 서버 로그에 직접 들어가 일일이 살펴봐야 했고, 오류가 늘었는지 장애가 났는지 알려면 별도로 로그를 뒤져야 했습니다.

2질문 제기

API를 소유한 도메인 이름으로 안정적으로 노출하면서, 동작 상태와 오류를 한곳에서 관찰할 수는 없을까?

3구조적 핵심 예시

커스텀 도메인 이름은 api.example.com처럼 내가 소유한 도메인을 API Gateway에 연결하는 기능입니다. ACM(인증서 관리 서비스)에서 받은 TLS 인증서(도메인의 암호화 연결을 증명하는 인증서)를 도메인 이름에 붙이고, DNS에서 api.example.com을 API Gateway가 준 대상 주소로 연결하면 그 도메인으로 API를 호출할 수 있습니다. 모니터링은 CloudWatch(모든 AWS 리소스의 지표와 로그를 모아 보여주는 서비스)가 자동으로 수집한 호출 수, 지연 시간, 4xx·5xx 오류 수 등을 그래프와 로그로 보여줍니다.

4단계별 동작 과정

  1. 도메인 연결사용할 커스텀 도메인 이름을 만들고, 그 도메인의 TLS 인증서를 ACM에서 가져와 연결합니다. DNS 설정으로 도메인이 API Gateway의 대상 주소를 가리키게 하면 도메인이 API로 연결됩니다.
  2. 지표 확인CloudWatch에서 호출 횟수, 평균 지연 시간(요청부터 응답까지 걸린 시간), 4xx·5xx 오류 개수 같은 지표를 대시보드로 봅니다. 이상 징후가 보이면 시각적으로 바로 드러납니다.
  3. 로그 분석CloudWatch Logs에 남는 접근 로그로 개별 요청의 상세 내용(누가, 언제, 어떤 경로를 호출했는지)을 조회해 오류 원인을 추적합니다.

5본질 요약

소유한 도메인 이름으로 API를 호출 가능하게 만들고, CloudWatch 지표와 로그로 API의 상태와 오류를 한곳에서 관찰하는 것

WebSocket API 개요

양방향·영구 연결 기반 API로, 클라이언트와 서버가 실시간으로 메시지를 주고받게 해주는 API Gateway의 API 유형

1상대의 출발점 확인

기존의 REST API는 요청-응답 방식입니다. 클라이언트가 요청을 보낼 때만 서버가 응답을 돌려주므로, 서버가 먼저 클라이언트에게 데이터를 보내려면 클라이언트가 다시 요청하도록 기다리거나 폴링(클라이언트가 일정 간격으로 계속 물어보는 방식)을 써야 했습니다. 채팅, 실시간 알림, 게임 상태 동기화처럼 서버 쪽에서 새로운 이벤트가 자주 생기는 서비스에서는 폴링이 불필요한 요청을 반복해 트래픽을 낭비하고, 그 사이에 생긴 이벤트는 전달이 늦어져 실시간성이 떨어졌습니다.

2질문 제기

서버가 능동적으로 데이터를 밀어내고, 클라이언트와 서버가 한 번 연결된 뒤 계속 쌍방향으로 주고받을 수는 없을까?

3구조적 핵심 예시

WebSocket API는 한 번 연결이 맺어지면 그 연결을 계속 유지한 채 양쪽이 언제든 메시지를 보낼 수 있게 하는 API 유형입니다. 예를 들어 채팅방에 들어온 클라이언트는 WebSocket 연결(양방향으로 메시지를 주고받을 수 있게 열어둔 통로)을 맺고, 다른 사용자가 메시지를 보내면 서버가 그 연결을 통해 즉시 메시지를 밀어내므로 클라이언트가 요청하지 않아도 화면에 바로 나타납니다. 연결 상태를 그대로 유지하기 때문에 그동안 REST처럼 매번 요청을 새로 만들 필요가 없습니다.

4단계별 동작 과정

  1. 연결 수립클라이언트가 WebSocket URL로 연결 요청을 보내면 핸드셰이크(연결 전에 서로 통신 규칙을 확인하는 교환)가 일어나고 연결이 맺어집니다. 연결마다 고유한 연결 ID가 부여됩니다.
  2. 양방향 메시지 송수신클라이언트와 서버가 맺어진 연결을 통해 서로 메시지를 보냅니다. 서버는 Lambda 등 백엔드가 만든 결과를 연결 ID를 통해 특정 클라이언트에게 밀어낼 수 있습니다.
  3. 연결 종료클라이언트나 서버가 연결을 닫으면 연결이 해제되고, 서버 쪽에서 해당 클라이언트의 상태를 정리합니다.

한 번 맺은 연결을 유지한 채 클라이언트와 서버가 언제든 메시지를 주고받게 하여 실시간 양방향 통신을 가능하게 하는 것

9WebSocket API09-02

연결·기본 라우트 관리

$connect·$disconnect·$default 같은 라우트 키와 라우트 정의로 WebSocket 연결 수립과 기본 메시지 흐름을 관리하는 방법

1상대의 출발점 확인

기존 방식에서는 WebSocket 연결이 생기고 끊기는 시점과 처음 오는 메시지가 무엇인지에 따라 서버가 어떤 일을 해야 하는지가 코드에 흩어져 있었습니다. 연결이 들어왔을 때 사용자 정보를 기록하고, 연결이 끊겼을 때 정리하고, 그 사이에 오는 메시지를 처리하는 로직이 각각 따로 분기돼 있어서 새로운 메시지 유형이 늘 때마다 처리 코드를 일일이 연결해야 했고, 어떤 메시지가 어디로 가는지 한눈에 파악하기 어려웠습니다.

2질문 제기

연결의 시작과 끝, 그리고 메시지의 종류에 따라 실행할 처리를 명확한 규칙으로 한곳에 정의할 수는 없을까?

3구조적 핵심 예시

WebSocket API는 라우트 키(route key)라는 문자열로 메시지의 종류를 구분합니다. 클라이언트가 보낸 메시지 본문의 첫 줄이 {"action": "sendMessage"}라면 라우트 키는 sendMessage가 되고, API Gateway는 그 키에 매핑된 백엔드(Lambda 등)를 호출합니다. 연결이 맺어질 때는 $connect, 연결이 끊길 때는 $disconnect, 어떤 라우트 키와도 맞지 않는 메시지에는 $default라는 특수한 라우트 키가 자동으로 사용됩니다.

4단계별 동작 과정

  1. 연결 시작 처리클라이언트가 연결을 맺으면 $connect 라우트가 실행됩니다. 여기서 인증하거나 접속 정보를 기록하고, 결과에 따라 연결을 허용하거나 거부할 수 있습니다.
  2. 메시지 라우팅연결된 뒤 온 메시지의 라우트 키를 확인해 그 키에 등록된 라우트의 백엔드로 전달합니다. $default는 등록된 키와 일치하지 않는 모든 메시지를 받습니다.
  3. 연결 종료 처리연결이 끊기면 $disconnect 라우트가 실행되어 사용자 상태 제거 등 정리 작업을 합니다.

5본질 요약

$connect, $disconnect, $default 같은 라우트 키와 라우트 정의로 WebSocket 연결의 수립과 종료, 메시지 흐름을 규칙에 따라 자동으로 처리하는 것

9WebSocket API09-03

WebSocket 통합과 라우트 응답

라우트에 백엔드 통합(Lambda 등)을 연결하고 통합 결과를 라우트 응답으로 클라이언트에 되돌려주는 구성

1상대의 출발점 확인

기존 방식에서는 클라이언트가 보낸 메시지를 실제로 처리하려면 서버가 직접 백엔드 함수를 호출하고, 그 결과를 다시 특정 클라이언트에게 보내는 연결 관리 코드까지 전부 직접 작성해야 했습니다. 어떤 메시지가 어떤 백엔드로 가는지 매핑 테이블을 직접 만들고, 응답을 보낼 때는 해당 클라이언트의 연결 ID를 찾아 그 연결로 전송하는 로직을 서버 코드 안에 중복해서 구현해야 했습니다.

2질문 제기

메시지가 들어왔을 때 어느 백엔드로 보낼지와 그 결과를 어떤 클라이언트에게 되돌려줄지를 서버 코드 없이 선언적으로 정할 수는 없을까?

3구조적 핵심 예시

통합(integration)은 라우트와 백엔드를 연결하는 설정입니다. 예를 들어 sendMessage 라우트에 Lambda 통합을 붙여 두면, 클라이언트가 {"action": "sendMessage", "data": "hello"}를 보냈을 때 API Gateway가 그 메시지를 해당 Lambda에 전달합니다. Lambda가 처리한 결과는 통합 응답(integration response) 설정에 따라 다시 그 라우트로 보낸 응답으로서 클라이언트에게 되돌아가거나, 다른 연결 ID를 지정해 다른 클라이언트에게 전달할 수도 있습니다.

4단계별 동작 과정

  1. 통합 연결라우트에 통합 유형(AWS 서비스, Lambda 등)과 대상 리소스(ARN: AWS 리소스를 가리키는 고유 주소)를 지정해 메시지가 백엔드로 전달되게 합니다.
  2. 백엔드 처리Lambda 등 통합 대상이 메시지를 받아 처리하고, 그 결과를 연결 ID가 담긴 형태로 돌려줍니다.
  3. 라우트 응답 반환API Gateway가 통합 결과를 라우트 응답 설정에 맞게 변환해, 요청을 보낸 클라이언트나 지정된 연결 ID의 클라이언트에게 되돌려줍니다.

5본질 요약

라우트에 백엔드 통합을 연결하고 통합 결과를 라우트 응답으로 변환해 클라이언트에게 되돌려주는 구성을 통해 메시지 처리 흐름을 선언적으로 만드는 것

9WebSocket API09-04

WebSocket 액세스 제어

IAM 권한·Lambda REQUEST authorizer 등으로 WebSocket API의 연결과 메시지 전송을 통제하는 방법

1상대의 출발점 확인

기존 방식에서는 WebSocket 연결이 맺어진 뒤에는 누가 메시지를 보내든 일단 백엔드로 전달됐고, 사용자 구분과 권한 확인을 서버 코드 안에서 매번 직접 구현해야 했습니다. 연결 요청 시점의 인증과 연결 후 메시지마다의 인증을 서로 다른 곳에서 처리하다 보니 인증 규칙이 코드에 분산되고, 특정 사용자만 일부 라우트를 쓰게 하려면 라우트마다 조건을 따로 작성해야 했습니다.

2질문 제기

WebSocket 연결을 맺을 때와 메시지를 보낼 때마다 누구인지 확인하고, 라우트별로 통제할 수는 없을까?

3구조적 핵심 예시

WebSocket API의 액세스 제어는 연결 요청과 메시지 전송 두 시점에 나뉘어 적용됩니다. 예를 들어 Lambda REQUEST authorizer(요청을 검사해 승인 여부를 판정하는 Lambda 함수)를 $connect 라우트에 붙여 두면, 연결을 시도할 때 헤더의 토큰을 검사해 유효하지 않으면 연결 자체를 거부하고 유효하면 범위(scope)를 부여합니다. IAM 권한(누가 어떤 API 작업을 할 수 있는지 지정하는 권한 체계)은 메시지가 라우트로 들어올 때마다 해당 라우트를 호출할 권리가 있는지 검사하는 데 씁니다.

4단계별 동작 과정

  1. 연결 시 인증클라이언트가 연결을 요청하면 $connect 라우트가 authorizer를 실행해 토큰·인증 정보를 검증하고, 결과에 따라 연결을 허용하거나 거부하고 연결에 부여할 권한 범위를 정합니다.
  2. 메시지 전송 시 검사연결된 클라이언트가 메시지를 보내면 IAM 권한 정책으로 해당 라우트를 호출할 자격이 있는지 확인합니다.
  3. 라우트별 처리메시지가 승인된 라우트로 전달되어 백엔드가 처리하고, 허용되지 않은 경우 요청이 거부됩니다.

1상대의 출발점 확인

기존 REST API 방식에서는 클라이언트가 요청을 보낼 때만 서버가 응답합니다. 클라이언트가 받은 데이터를 서버가 먼저 보내고 싶으면, 서버는 클라이언트가 다음에 요청을 보낼 때까지 기다렸다가 그 응답에 실어 보내야 합니다. 채팅, 알림, 실시간 가격 변동처럼 서버가 먼저 말을 걸어야 하는 상황에서는 매번 클라이언트가 짧은 주기로 새 요청을 보내(polling) 바뀐 게 있는지 확인해야 하므로 쓸데없는 트래픽이 발생하고, 데이터가 실제로 바뀐 시점과 확인 시점 사이에 지연이 생깁니다.

2질문 제기

서버와 클라이언트가 연결을 한 번 맺은 뒤, 서버가 원할 때 아무 때나 그 연결된 클라이언트에게 메시지를 보낼 수는 없을까?

3구조적 핵심 예시

WebSocket API에서 클라이언트 하나가 연결을 맺으면 API Gateway는 그 연결에 connectionId라는 고유 식별자를 부여합니다. 서버(백엔드)가 특정 클라이언트에게 메시지를 보내려면 그 connectionId를 받아서 API Gateway에 제공합니다. API Gateway가 해당 연결이 아직 살아 있는지 확인하고, 살아 있다면 그 연결로 메시지를 실어 보냅니다. 이때 서버가 직접 네트워크 주소를 알 필요 없이 연결 ID 하나만으로 대상이 정해집니다.

4단계별 동작 과정

  1. 연결과 ID 발급클라이언트가 WebSocket URL로 연결을 요청하면 핸드셰이크(연결을 맺기 위한 초기 교섭)가 끝나고 API Gateway가 연결마다 고유한 connectionId를 발급합니다. 백엔드는 연결 이벤트에서 이 ID를 받아 저장해 둡니다.
  2. 메시지 전송백엔드가 @connections API에 connectionId와 보낼 내용을 담아 호출합니다. API Gateway(실제로는 실행 역할을 가진 Lambda 함수가 이 호출을 수행)가 그 connectionId의 연결이 아직 유효한지 확인하고, 유효하면 해당 연결로 메시지를 전송합니다.
  3. 연결 상태 관리와 정리API Gateway는 연결이 끊겼거나(클라이언트 접속 종료) 더 이상 유효하지 않은 connectionId로 메시지 전송을 시도하면 오류를 돌려주므로, 백엔드는 그 연결을 저장소에서 삭제해 연결 상태를 최신으로 유지합니다.

1상대의 출발점 확인

WebSocket API를 하나 만들어 두기만 하면 아무도 접속할 수 없습니다. 이전 단계에서는 연결 하나에 메시지를 보내는 방법만 다뤘고, 그 API를 실제 사용자가 쓰게 만드는 배포(Deployment)와 스테이지(Stage) 개념, 누가 접속해도 되는지를 정하는 보안 정책, 그리고 운영 중인 API가 제대로 도는지 확인할 모니터링 구성은 따로 갖춰야 합니다. 이것들을 설정하지 않으면 개발이 끝나도 서비스를 내놓을 수 없고, 문제가 생겨도 원인을 알 수 없습니다.

4단계별 동작 과정

  1. 배포와 스테이지 연결API 스냅샷을 만들어 스테이지에 배포합니다. 스테이지마다 고유 URL이 생기고, 같은 API를 다른 스테이지에 각각 다른 버전으로 배포할 수 있습니다. 스테이지 변수로 라우팅할 백엔드 주소도 스테이지별로 다르게 지정할 수 있습니다.

  3. 모니터링 구성CloudWatch 지표(성공·실패·지연 시간 등의 수치)와 실행 로그(연결·메시지·오류 처리 기록)를 스테이지 단위로 켜서 배포된 API의 상태와 오류를 실시간으로 확인합니다.

  3. 알람 설정지표가 임계값을 넘으면 알림을 주도록 CloudWatch 알람을 만들고, 알림 대상(이메일 등)을 연결합니다. 오류율이 치솟는 순간 운영자가 즉시 통보받습니다.

1상대의 출발점 확인

지표로는 "오류가 많다"는 사실만 알 수 있고, "어떤 요청이, 어떤 내용으로, 어떤 결과를 받았는지"는 알 수 없습니다. 장애 원인을 찾으려면 특정 시각에 들어온 요청 하나하나를 들여다봐야 하는데, 이러저러한 로그를 켜 두지 않으면 API Gateway는 요청 내용을 남기지 않으므로 문제가 생겼을 때 재현할 수 없습니다. 지표만으로는 부족해 요청 단위의 기록이 필요한 상황입니다.

2질문 제기

지표 너머에서, 들어온 요청 하나하나가 어떻게 처리되고 어떤 결과를 냈는지 상세 기록을 남겨 장애를 추적할 수는 없을까?

3구조적 핵심 예시

API Gateway는 두 종류의 로그를 CloudWatch Logs로 보냅니다. 실행 로그(Execution Log)는 요청 처리의 내부 과정으로, 요청이 도착한 시각, 호출된 백엔드, 백엔드의 응답, 오류 메시지까지 담깁니다. 액세스 로그(Access Log)는 요청·응답의 메타데이터 한 줄로, 요청자 IP, 경로, 메서드, 응답 상태 코드, 걸린 시간을 사용자가 지정한 형식으로 남깁니다. 이 두 기록으로 "그 시각 그 요청이 왜 실패했는지"를 단계별로 재구성할 수 있습니다.

  1. 로그 그룹 설정과 권한 부여CloudWatch Logs에 로그 그룹을 만들고, API Gateway가 거기에 로그를 쓸 수 있게 IAM 역할(실행 역할)에 권한을 부여합니다.
  2. 로깅 켜기와 형식 지정스테이지 설정에서 실행 로그를 켜고 로그 수준(오류만 또는 전부)을 정하며, 액세스 로그는 남길 필드를 담은 로그 형식 템플릿을 지정합니다.
  3. 로그 조회와 추적CloudWatch Logs에서 해당 로그 그룹을 열어 시각·요청 ID로 검색하고, 요청이 API Gateway에서 백엔드로 가는 과정과 응답을 따라가며 오류 원인을 확인합니다.

2질문 제기

3구조적 핵심 예시

  1. 확장 작성x-amazon-apigateway-* 접두어를 가진 속성(예: x-amazon-apigateway-integration, x-amazon-apigateway-auth)을 OpenAPI 정의의 해당 위치에 추가한다.
  2. 가져오기 적용이 정의 파일을 API Gateway로 가져오면 표준 부분은 API 구조로, 확장 부분은 통합·인증·게이트웨이 응답 등 API Gateway 설정으로 변환된다.
  3. 동작 확인확장 설정이 반영된 API가 배포되어, 정의 파일에 적힌 대로 백엔드 호출과 인증이 실제로 수행된다.

11단계 OpenAPI·자동화·한도

AWS CLI·SDK 등 코드 기반 방법으로 REST API를 생성·구성·배포해 콘솔 수작업 없이 API 생명주기를 자동화하는 방식이다.

1상대의 출발점 확인

API Gateway에서 API를 만들고 스테이지에 배포하는 일은 콘솔에서 클릭으로 할 수 있다. 하지만 운영 환경에서는 같은 작업을 여러 계정·여러 리전에 반복해야 하고, 배포 절차가 매번 같아야 재현 가능하다. 콘솔 수작업은 절차가 사람마다 달라지고 기록이 남지 않아, 같은 API를 두 번째 만들거나 CI/CD(지속적 통합·배포) 파이프라인에 넣기가 어렵다.

2질문 제기

API 생성부터 배포까지의 전체 과정을 사람 손을 거치지 않고 코드로 반복 실행할 수는 없을까?

3구조적 핵심 예시

AWS CLI 명령 하나로 aws apigateway create-rest-api를 실행해 REST API를 만들고, 이어서 리소스·메서드·통합을 명령으로 추가한 뒤 create-deployment로 스테이지에 배포한다. 같은 명령 묶음을 다시 실행하면 동일한 절차로 API가 또 만들어진다.

4단계별 동작 과정

  1. 생성AWS CLI나 SDK로 REST API와 리소스, 메서드, 통합 대상을 코드에서 정의해 만든다.
  2. 구성요청·응답 매핑, 인증, 스테이지 변수 등 상세 설정을 명령으로 추가해 API 구성을 완성한다.
  3. 배포create-deployment 명령으로 스테이지에 배포해 클라이언트가 호출할 수 있는 엔드포인트 URL을 만들고, 이 전체 과정을 스크립트·파이프라인에 넣어 자동 실행한다.

5본질 요약

AWS CLI·SDK로 API의 생성·구성·배포 전체를 코드로 실행해, 콘솔 수작업 없이 API 생명주기를 반복 가능하게 자동화하는 것

11OpenAPI·자동화·한도11-04

11단계 OpenAPI·자동화·한도

API Gateway의 계정·API 유형별 한도(쿼터), 스로틀링, 데이터 전송 등 운영 시 꼭 알아야 할 제약과 중요 참고 사항을 모아 둔 문서다.

1상대의 출발점 확인

API Gateway는 리전마다 계정 단위로 적용되는 한도(쿼터)가 있다. 예를 들어 리전당 REST API 개수, API당 스테이지 개수, 초당 처리할 수 있는 요청 수(스로틀링) 같은 제약이 정해져 있다. 이 한도를 모른 채 API를 설계하면, 나중에 API 수가 늘거나 트래픽이 몰릴 때 갑자기 요청이 거부되거나 생성 자체가 실패한다. 콘솔 화면에서는 이런 제약이 눈에 잘 보이지 않아, 운영 중에 처음 문제를 발견하는 경우가 많다.

2질문 제기

API가 늘어나고 트래픽이 몰려도 멈추지 않으려면 어떤 한도를 알고 설계해야 할까?

3구조적 핵심 예시

REST API를 하나 더 만들려는데 이미 해당 리전의 계정 한도(예: 리전당 REST API 최대 수)에 도달했다면, 생성 요청이 실패하고 한도 초과 오류가 돌아온다. 반대로 스테이지별로 초당 요청 한도를 넘는 트래픽이 들어오면, 초과분은 429 Too Many Requests 응답으로 거부된다.

4단계별 동작 과정

  1. 한도 확인API 유형(REST API, HTTP API, WebSocket)별 계정·리전 한도와 스테로틀링 기준을 공식 문서에서 사전에 확인한다.
  2. 한도 초과 처리초당 요청 한도를 넘으면 스테로틀링이 작동해 초과 요청이 429 응답과 함께 거부되고, 리소스 생성 한도를 넘으면 생성 작업이 실패한다.
  3. 완화 적용필요한 경우 한도 증가 요청을 하거나, 여러 리전·여러 API에 부하를 분산하고 캐시·백오프(재시도 지연)를 적용해 한도 안에서 운영한다.

5본질 요약

계정·API 유형별 쿼터와 스로틀링 한도를 명확히 알고 설계해, 한도 초과로 인한 생성 실패와 트래픽 거부를 예방하는 것
