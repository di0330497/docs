이어서 읽기

AWS의 고가용성·확장 가능한 DNS 웹 서비스. 도메인 등록, DNS 라우팅(호스티드 존·레코드·라우팅 정책), 헬스 체크/장애 조치라는 세 기능과 VPC Resolver·DNS Firewall·Traffic Flow·Profiles 같은 부가 기능을 아우른다. 가장 일반적인 해석인 '도메인 등록 + DNS 서비스 + 헬스 체크'라는 공식 안내를 기준으로, 실무에서 가장 많이 쓰는 DNS 라우팅을 중간에 크게 배치했다.

1DNS와 Route 53 개요01-01

1단계 DNS와 Route 53 개요

인터넷에서 사람이 읽을 수 있는 이름(도메인 이름)과 기기가 찾아가는 숫자 주소(IP 주소)의 관계를 설명하는 개념.

#1문제 상황

인터넷의 모든 기기는 숫자 주소인 IP 주소(예: 203.0.113.5)로 서로를 찾아간다. 그런데 사람이 숫자 주소를 외우기 어렵고, 서버를 옮기면 IP가 바뀌어 숫자를 직접 입력하던 방식은 그때마다 깨진다. 그래서 기존에는 사람이 읽을 수 있는 이름(도메인 이름, 예: example.com)을 숫자 주소에 연결하는 별도의 체계가 필요했다. 이름만으로는 통신이 되지 않고, 숫자만으로는 사람이 관리하지 못하는 두 세계 사이를 잇는 연결 고리가 바로 도메인 이름과 IP 주소의 관계다.

#2핵심 질문

사람이 기억하는 이름 example.com이 어떻게 그 서버의 정확한 숫자 주소로 이어지는가?

#3동작 예시

브라우저 주소창에 example.com을 입력하면 브라우저는 그 이름만으로는 목적지를 모르므로, 먼저 DNS라는 이름-주소 대응표에서 이 이름의 IP 주소를 찾아낸 뒤에야 그 주소로 요청을 보낸다. 이름은 사람용 라벨이고, IP 주소는 기기가 실제로 찾아가는 위치다.

#4동작 과정

  1. 이름 입력사용자가 브라우저에 example.com을 입력한다.
  2. 주소 조회DNS가 example.com에 대응하는 IP 주소를 찾아 브라우저에 알려준다.
  3. 연결 수립브라우저가 그 IP 주소로 요청을 보내 서버와 통신을 시작한다.

도메인 등록, DNS 라우팅, 리소스 헬스 체크라는 세 가지 핵심 기능을 제공하는 AWS의 확장 가능한 DNS 웹 서비스.

#1문제 상황

기존에는 도메인 이름을 사고(도메인 등록), 그 도메인에 대한 DNS 질의에 응답하고(라우팅), 서버가 살아 있는지 확인하는 일(헬스 체크)을 서로 다른 업체의 서로 다른 서비스로 처리했다. 각 서비스의 설정 화면을 오가며 등록 정보, DNS 레코드, 상태 점검 결과를 따로 관리해야 했고, 어느 한 곳의 설정이 어긋나면 도메인은 등록됐는데 웹사이트가 열리지 않는 식의 문제가 생겼다. 이 세 작업은 모두 이름과 서버를 연결한다는 공통점이 있는데도 분리되어 있어 관리가 흩어졌다.

#2핵심 질문

도메인 등록부터 DNS 응답, 서버 상태 확인까지 한 서비스에서 묶어 관리할 수는 없을까?

#3동작 예시

Route 53 하나로 example.com을 등록하고, 등록한 도메인의 DNS 레코드를 만들고, 그 도메인이 가리키는 웹 서버에 헬스 체크를 걸어 두는 일이 모두 끝난다. 등록·라우팅·헬스 체크가 같은 콘솔 안에서 연결되어 있어 설정이 어긋나기 어렵다.

#4동작 과정

  1. 도메인 등록Route 53에서 example.com 이름을 등록해 이 도메인의 소유권을 확보한다.
  2. DNS 라우팅호스티드 존 안에 레코드를 만들어 example.com 질의가 웹 서버 IP로 향하도록 응답한다.
  3. 헬스 체크 연동웹 서버를 주기적으로 확인하고, 장애가 감지되면 응답 대상을 정상 서버로 바꾼다.

1DNS와 Route 53 개요01-03

1단계 DNS와 Route 53 개요

루트·TLD 네임 서버와 권한 있는 네임 서버, 재귀 리졸버가 계층적으로 협력해 도메인 이름을 IP 주소로 해석하는 구조.

#1문제 상황

DNS가 모든 도메인 이름의 IP 주소를 한 서버에 다 모아 두고 답한다고 가정하면, 그 서버 하나가 전 세계 모든 질의를 감당해야 하고 서버가 죽으면 인터넷 전체 주소 조회가 멈춘다. 실제로는 어떤 서버도 모든 도메인을 알지 못한다. 대신 루트 네임 서버, TLD 네임 서버(최상위 도메인 담당, 예: .com 담당), 권한 있는 네임 서버(특정 도메인 담당), 재귀 리졸버(사용자 대신 질의를 수행하는 중계자)가 각자 자기 몫만 알고 계층적으로 협력한다. 한 서버가 전부를 알아야 한다는 가정이 바로 이 구조가 해결하는 문제다.

#2핵심 질문

하나의 서버가 모든 도메인을 외우지 않고도 전 세계 DNS 질의에 정확히 답할 수 있게 하려면 어떻게 나눠 맡아야 하는가?

#3동작 예시

www.example.com을 조회하는 질의는 재귀 리졸버가 루트 네임 서버에 "example.com을 아는 서버를 알려달라"고 묻고, 루트가 .com TLD 네임 서버를 안내하고, TLD가 example.com의 권한 있는 네임 서버를 안내하고, 마지막으로 권한 있는 네임 서버만이 www.example.com의 IP를 정확히 답한다. 각 층은 자기 아래 층의 위치만 안내하고, 정답은 맨 아래 권한 있는 서버가 가진다.

#4동작 과정

  1. 루트에 안내 요청재귀 리졸버가 루트 네임 서버에 질의해 example.com을 담당하는 .com TLD 서버의 위치를 받는다.
  2. TLD에 안내 요청리졸버가 .com TLD 네임 서버에 질의해 example.com의 권한 있는 네임 서버 위치를 받는다.
  3. 권한 서버에서 정답 획득리졸버가 권한 있는 네임 서버에 질의해 www.example.com의 IP 주소를 받아 사용자에게 전달한다.

#5한 줄 요약

루트·TLD·권한 있는 네임 서버와 재귀 리졸버가 각자 일부만 알고 계층적으로 안내하며 협력해 이름을 IP 주소로 해석하는 분산 구조

1DNS와 Route 53 개요01-04

1단계 DNS와 Route 53 개요

클라이언트의 DNS 질의가 재귀 리졸버를 거쳐 권한 있는 서버로부터 응답을 받고, 그 응답이 TTL 동안 캐시되어 재사용되는 전체 흐름.

#1문제 상황

DNS 질의를 할 때마다 매번 루트부터 권한 있는 네임 서버까지 계층 전체를 거쳐 응답을 받으면, 그때마다 여러 번의 네트워크 왕복이 생겨 페이지가 열리는 시간이 늘어난다. 권한 있는 네임 서버 입장에서도 같은 이름에 대한 질의가 반복될수록 부하가 쌓인다. 기존에는 응답을 어디에도 보관하지 않아서 같은 질문을 무한히 처음부터 다시 물어야 했다.

#2핵심 질문

한 번 받은 DNS 응답을 재사용해서 반복 질의의 지연과 부하를 줄일 수는 없을까?

#3동작 예시

첫 방문자가 example.com을 조회하면 재귀 리졸버가 계층 전체를 거쳐 IP를 받아 답하면서 그 응답을 TTL(응답의 유효 수명, 초 단위 값) 동안 캐시(임시 보관)해 둔다. TTL이 끝나기 전에 두 번째 방문자가 같은 이름을 물으면 리졸버는 계층을 다시 거치지 않고 보관해 둔 응답을 즉시 답한다. TTL이 만료된 뒤에야 다시 계층 조회를 시작한다.

#4동작 과정

  1. 최초 질의와 응답클라이언트 질의가 재귀 리졸버를 거쳐 권한 있는 서버까지 전달되고, 응답이 TTL 값과 함께 돌아온다.
  2. TTL 동안 캐시리졸버가 응답을 TTL 시간만큼 보관하고, 같은 이름 질의는 보관된 값으로 즉시 답한다.
  3. TTL 만료 후 재조회TTL이 지나면 캐시를 버리고 다음 질의 때 계층 조회를 다시 수행해 최신 응답을 받는다.

#5한 줄 요약

도메인의 DNS 설정을 담는 컨테이너인 호스티드 존과, 그 안에서 이름을 값(IP 주소 등)에 연결하는 레코드의 개념.

→ 03-01 참조

#1문제 상황

하나의 도메인에는 여러 가지 설정이 필요하다. example.com은 웹 서버 IP로, www.example.com은 별칭으로, 메일을 받으려면 메일 서버 정보까지 적어야 한다. 이런 이름-값 쌍을 어디에도 담지 않고 흩어 두면 어떤 레코드가 이 도메인에 속하는지, 어디에 추가해야 하는지 알 수 없다. 기존에는 도메인별로 설정을 모아 두는 그릇이 명확하지 않아 관리가 어렵고 실수가 잦았다.

#2핵심 질문

한 도메인의 DNS 설정을 한곳에 모아 두고, 각 설정을 이름과 값의 형태로 관리하려면 무엇이 필요한가?

#3동작 예시

example.com에 대한 호스티드 존(도메인의 DNS 설정 전체를 담는 컨테이너)을 하나 만들면, 그 안에 "example.com → 웹 서버 IP"라는 A 레코드, "mail.example.com → 메일 서버"라는 MX 레코드, "www.example.com → example.com"이라는 CNAME 레코드처럼 이름을 값에 연결하는 레코드들을 여러 개 넣을 수 있다. DNS 질의가 오면 이 존 안의 레코드가 곧 답이 된다.

#4동작 과정

  1. 호스티드 존 생성example.com의 호스티드 존을 만들면 이 도메인 전용의 DNS 설정 그릇이 생긴다.

도메인을 등록하는 주체의 역할과 Route 53에서 등록할 수 있는 최상위 도메인(TLD)의 종류를 다루는 개념이다.

#1문제 상황

기존에 도메인 이름을 사용하려면 누군가에게 등록을 신청해야 한다. 그런데 도메인 등록은 한 곳에서 끝나는 일이 아니라 역할이 나뉘어 있다. 최상위 도메인(TLD, 주소 맨 끝의 .com, .kr 같은 부분)의 종류와 운영 주체를 정하는 기관(ICANN), 특정 TLD를 실제로 관리하는 레지스트리, 그리고 사용자와 계약해 등록을 접수하는 레지스트라(등록 대행 기관)가 따로 존재한다. 기존 방식의 문제는 이 역할 구분을 모르면 "도메인을 샀다"는 것이 실제로는 레지스트라와의 계약일 뿐이라는 점을 놓치기 쉽고, 어떤 TLD에 어떤 이름을 등록할 수 있는지 한눈에 파악하기 어렵다는 점이다. 사용자 입장에서는 누구에게 신청해야 하는지, 어떤 최상위 도메인 범위 안에서 신청할 수 있는지를 등록 전에 명확히 알아야 한다.

#2핵심 질문

도메인 이름을 등록하려면 누구에게, 그리고 어떤 최상위 도메인 범위 안에서 신청해야 하는가?

#3동작 예시

웹 서비스를 공개하려는 회사가 "example.com"이라는 도메인을 쓰고 싶다면, 그 회사는 Route 53의 도메인 등록 화면에서 example.com을 검색해 신청한다. 이때 Route 53이 레지스트라 역할을 하여 .com TLD를 관리하는 레지스트리로 등록을 대행해 준다. 사용자는 레지스트리와 직접 거래하지 않고 Route 53이라는 한 창구만 거치면 된다.

#4동작 과정

  1. 등록 주체 확인사용자가 Route 53을 통해 도메인 등록을 신청하면, Route 53이 레지스트라로서 등록 업무를 대행한다.
  2. 최상위 도메인 선택신청하려는 이름이 속한 TLD(.com, .net, .org, .kr 등)가 Route 53에서 지원되는지, 그리고 그 TLD의 정책에 맞는지 확인한다.
  3. 레지스트리에 등록 전달신청 내용을 해당 TLD의 레지스트리에 전달해 도메인이 실제로 등록되고 사용자 소유로 기록된다.

#5한 줄 요약

사용자가 레지스트리와 직접 거래하지 않고, Route 53이라는 등록 대행 창구를 통해 지원되는 최상위 도메인에 도메인 이름을 등록하게 해 주는 것

#1문제 상황

기존에는 도메인 등록 기간이 끝나면 도메인을 잃어버리는 문제가 흔했다. 등록 기간은 유한하므로(보통 1~10년) 갱신하지 않으면 만료되어 서비스가 중단된다. 또 도메인을 다른 등록 대행 기관으로 옮기거나 소유권이 바뀌는 사고를 막으려면 잠금(transfer lock) 설정이 필요하다. 여기에 더해 도메인 이름이 실제로 어느 네임 서버(DNS 질의에 응답하는 서버)를 향해야 하는지도 정해져야 도메인으로 웹사이트에 접속할 수 있다. 이 설정들을 제대로 관리하지 않으면 도메인은 이름만 있고 실제 서비스로 연결되지 않는다.

#2핵심 질문

도메인 등록 기간을 어떻게 갱신·연장하고, 무단 이전을 막는 잠금과 네임 서버는 어떻게 관리하는가?

#3동작 예시

"myapp2026.com"의 등록 기간이 1년 남았다면, Route 53에서 자동 갱신을 켜두고 등록 기간을 연장(예: 1년 더)한다. 동시에 전송 잠금을 활성화해 다른 등록 대행 기관으로의 무단 이전을 막고, 네임 서버를 지정해 이 도메인으로 접속하면 어떤 DNS가 응답할지를 정한다.

#4동작 과정

  1. 갱신·연장 설정자동 갱신을 켜거나 등록 기간을 연장해 도메인이 만료되지 않도록 등록 기간을 늘린다.
  2. 전송 잠금 활성화도메인에 잠금을 걸어 소유자 동의 없이 다른 등록 대행 기관으로 옮겨가지 못하게 한다.
  3. 네임 서버 지정이 도메인이 사용할 네임 서버(도메인에 대한 DNS 질의에 응답하는 서버)를 Route 53 콘솔에 입력한다.

#5한 줄 요약

도메인 등록 기간을 갱신·연장하고, 무단 이전을 막는 잠금과 DNS 질의를 받는 네임 서버를 한곳에서 관리하게 해 주는 것

도메인 등록 기간을 갱신하고, 만료·삭제된 도메인을 복원하거나 등록을 삭제하며, 청구 보고서를 내려받는 작업이다.

#1문제 상황

기존에는 도메인 기간이 만료된 뒤의 절차가 불명확했다. 갱신 기한을 놓치면 도메인이 만료되고, 일정 시간이 지나면 삭제되어 다른 사람이 가져갈 수 있다. 또 만료된 도메인을 살리려면 복원 절차와 추가 비용이 필요하고, 더 이상 쓰지 않는 도메인은 삭제해야 청구가 계속되지 않는다. 이 모든 과정의 비용이 어떻게 청구되었는지도 확인하려면 청구 보고서가 필요하다.

#2핵심 질문

만료된 도메인을 갱신·복원하고, 쓰지 않는 도메인을 삭제하며, 비용 내역은 어떻게 확인하는가?

#3동작 예시

"myapp2026.com"이 실수로 갱신되지 않아 만료 단계에 들어갔다면, Route 53에서 복원을 신청해 등록 기간을 되살린다. 더 이상 쓰지 않는 "oldapp.com"은 콘솔에서 삭제를 요청하고, 청구 보고서를 내려받아 등록·복원 비용이 얼마였는지 확인한다.

#4동작 과정

  1. 갱신·복원만료 전 도메인은 갱신하고, 만료되어 복원 기간 안에 있는 도메인은 복원 비용을 지불하고 되살린다. 복원 기간이 지나 삭제된 도메인은 되살릴 수 없다.
  2. 삭제더 이상 쓰지 않는 도메인에 대해 삭제를 요청하면 등록이 철회되고 이후 청구가 발생하지 않는다.
  3. 청구 보고서 확인Route 53에서 청구 보고서를 내려받아 등록·갱신·복원 등 항목별 비용 내역을 확인한다.

#1문제 상황

기존에는 도메인을 다른 등록 대행 기관(레지스트라)으로 옮기려면 어디서 어떻게 시작해야 하는지 모르는 경우가 많았다. 도메인은 자유롭게 이동할 수 있는 것이 아니라서, 소유권 확인, 잠금 해제, 인증 코드 확보, 이전 상태 확인 같은 사전 조건을 갖춰야 이전이 진행된다. 아무 준비 없이 이전을 신청하면 실패하거나, 잠금이 걸려 있어 진행조차 안 되는 문제가 생긴다.

#2핵심 질문

도메인 등록을 한 등록 대행 기관에서 다른 등록 대행 기관으로 옮기려면 어떤 절차를 거쳐야 하는가?

#3동작 예시

"myapp2026.com"을 다른 회사에서 Route 53으로 옮기려면, 먼저 기존 회사에서 전송 잠금을 해제하고 인증 코드(이전을 허락하는 코드)를 발급받는다. 그 코드를 Route 53의 도메인 이전 화면에 입력해 신청하고, 소유자 이메일로 온 승인 요청을 확인하면 며칠 안에 이전이 완료되어 Route 53에서 관리된다.

#4동작 과정

  1. 사전 점검기존 등록 대행 기관에서 잠금을 해제하고, 이전을 허락하는 인증 코드를 받으며, 도메인이 등록된 지 60일 이상 지났는지 같은 조건을 확인한다.
  2. 이전 신청Route 53에 인증 코드를 입력해 이전을 신청하고, 소유자 이메일로 온 승인 요청을 확인한다.
  3. 이전 완료 확인이전 상태를 콘솔에서 확인하고, 이전이 완료되면 도메인 등록 기간이 1년 연장되며 이후 Route 53에서 갱신과 설정을 관리한다.

2도메인 등록02-07

2단계 도메인 등록

도메인에 DNSSEC을 구성해 위조된 DNS 응답을 막고, WHOIS·RDAP로 도메인 등록 정보를 조회하는 작업이다.

#1문제 상황

기존에는 도메인 이름이 누구 소유인지 조회하는 일과 DNS 응답이 진짜인지 확인하는 일이 분리되어 있었다. 일반 DNS는 도메인에 대한 응답이 위조되었는지 검증하지 않아, 공격자가 가짜 DNS 응답을 보내 사용자를 다른 서버로 유도하는 위조 공격에 취약하다. 또 도메인 등록 정보(소유자, 등록일, 만료일)를 확인하려면 WHOIS나 RDAP라는 조회 수단을 따로 알아야 했다. 이 두 기능을 모르면 도메인 소유권 확인도, DNS 응답 신뢰성 확보도 어렵다.

#2핵심 질문

도메인의 DNS 응답이 위조되지 않았음을 보장하고, 도메인 등록 정보는 어떻게 조회하는가?

#3동작 예시

"myapp2026.com"에 DNSSEC을 구성하면, 사용자가 이 도메인의 주소를 묻는 DNS 질의를 보낼 때 응답에 디지털 서명이 붙는다. 응답을 받은 쪽은 그 서명을 검증해 위조된 응답인지 진짜인지 판별한다. 그리고 별도로 RDAP나 WHOIS를 사용하면 이 도메인의 등록자·등록일·만료일 같은 등록 정보를 조회할 수 있다.

#4동작 과정

  1. DNSSEC 키 구성Route 53에서 도메인에 DNSSEC 키(디지털 서명에 쓰이는 키)를 등록해, 이 도메인의 DNS 응답에 서명이 붙도록 만든다.
  2. 응답 검증DNS 질의에 대한 응답이 서명 검증을 통과하면 진짜 응답이고, 통과하지 못하면 위조로 간주하고 버린다.
  3. 등록 정보 조회WHOIS나 RDAP(등록 정보 조회용 공개 프로토콜)로 도메인의 소유자·등록일·만료일을 조회한다.

#5한 줄 요약

DNSSEC으로 위조된 DNS 응답을 막고, WHOIS·RDAP로 도메인 등록 정보를 누구나 조회할 수 있게 해 주는 것

3단계 호스티드 존 — DNS 서비스의 컨테이너

호스티드 존은 한 도메인(예: example.com)과 그 서브도메인의 DNS 레코드를 담는 Route 53의 컨테이너로, 공개 호스티드 존과 프라이빗 호스티드 존 두 종류가 있다.

#1문제 상황

DNS는 도메인 이름을 IP 주소로 바꿔 주는 시스템이다. 예전에 도메인 하나를 운영하려면 해당 도메인의 레코드(도메인 이름과 IP 주소의 연결 정보)를 어디에 저장하고 누가 응답할지 일일이 정해야 했다. 도메인이 여러 개라면 관리 대상이 흩어져서, 어떤 서버가 어떤 도메인을 담당하는지 파악하고 갱신하기 어렵다. 이렇게 도메인과 레코드의 소속이 명확하지 않은 상태에서는 질의(도메인 이름을 IP로 풀어 달라는 요청)가 들어와도 어느 곳에 묻고 어느 곳에 기록해야 할지 혼란이 생긴다.

#2핵심 질문

도메인 하나에 속한 레코드들을 어디에 모아 두고 누가 그 도메인에 대한 질의를 책임질 것인가?

#3동작 예시

example.com 이라는 도메인을 운영한다고 하자. Route 53에 호스티드 존을 하나 만들면, example.com 과 www.example.com 같은 서브도메인의 모든 레코드가 그 존 안에 담긴다. 이후 인터넷의 누군가 example.com 의 IP를 물어보면 Route 53은 그 호스티드 존에서 답을 찾아 돌려준다.

#4동작 과정

  1. 호스티드 존 생성Route 53 콘솔이나 API에 도메인 이름(example.com)을 지정해 호스티드 존을 만든다.
  2. 레코드 등록생성된 존 안에 해당 도메인과 서브도메인의 레코드(A 레코드 등)를 넣는다.
  3. 질의 응답인터넷의 질의가 들어오면 Route 53이 그 존 안의 레코드를 찾아 IP 주소를 응답한다.

#5한 줄 요약

도메인 하나와 그 서브도메인의 모든 DNS 레코드를 한 컨테이너에 모아 두고, 그 도메인에 대한 질의를 Route 53이 대신 처리하게 만드는 것

3호스티드 존 — DNS 서비스의 컨테이너03-02

3단계 호스티드 존 — DNS 서비스의 컨테이너

공개 호스티드 존은 인터넷에서 도메인 질의를 받아 처리하는 호스티드 존으로, 콘솔이나 API로 생성·이름 서버 조회·목록 확인·삭제할 수 있다.

#1문제 상황

호스티드 존을 만들기 전에는 도메인에 대한 DNS 관리가 외부 DNS 제공자의 화면이나 설정 파일에 의존했다. 도메인 등록 대행 기관에서 제공하는 기본 DNS 설정만으로는 레코드를 원하는 만큼 자유롭게 추가하거나 수정하기 어렵고, 변경 이력이나 일관된 관리 수단이 부족했다. 여러 도메인을 한곳에서 만들고 조회하고 삭제하는 절차도 서비스마다 달라 통일된 관리가 힘들었다.

#2핵심 질문

인터넷에서 질의를 받는 호스티드 존을 AWS 계정 안에서 어떻게 만들고, 확인하고, 없앨 수 있는가?

#3동작 예시

Route 53 콘솔에서 example.com 을 도메인 이름으로 넣고 "호스티드 존 생성"을 실행한다. 생성이 끝나면 Route 53이 그 존에 대한 이름 서버 4개(NS 레코드에 적힌 서버 주소)를 돌려주고, 이 존은 인터넷의 도메인 질의를 즉시 받을 준비가 된다.

#4동작 과정

  1. 생성콘솔 또는 API로 도메인 이름을 지정해 공개 호스티드 존을 만든다. 결과로 이름 서버 4개가 반환된다.
  2. 조회·확인호스티드 존 목록에서 생성 상태와 이름 서버를 확인하고, 필요하면 변경한다. 더 이상 안 쓰면 삭제한다.

#1문제 상황

호스티드 존이 있으면 그 안에 레코드를 넣어야 도메인 이름이 실제로 IP 주소로 풀린다. 레코드를 만들 때 무엇을 써야 하는지 모르면 A 레코드와 CNAME 레코드의 차이조차 혼동하기 쉽고, 이름에 와일드카드(*)를 쓰는 규칙이나 TTL(캐시 보존 시간)의 의미를 잘못 이해하면 응답이 늦게 갱신되거나 예상치 못한 값을 돌려줄 수 있다. 아무 규칙 없이 레코드를 흩어서 관리하면 어떤 레코드가 어떤 도메인 이름을 담당하는지도 알기 어렵다.

#2핵심 질문

레코드 하나가 어떤 요소들로 구성되고, 각 요소를 어떤 규칙으로 지정해야 DNS가 올바로 응답하는가?

#3동작 예시

example.com 에 대해 "이름=www.example.com, 타입=A, 값=192.0.2.10, TTL=300초, 라우팅 정책=단순"이라는 레코드를 하나 만든다. 이 다섯 요소가 레코드의 전부이며, 질의가 들어오면 이 값 그대로 응답에 사용된다.

#4동작 과정

  1. 이름·타입 지정레코드가 응답할 도메인 이름(예: www.example.com)과 레코드 타입(A, CNAME, MX 등)을 정한다. 이름은 와일드카드(*)를 쓸 수 있는 경우가 있다.
  2. 값·TTL 지정응답할 값(IP 주소 등)을 넣고, 다른 DNS 서버가 이 응답을 얼마나 오래 보관해 둘지 TTL(초)을 지정한다.
  3. 라우팅 정책 선택단순(항상 같은 값)이나 가중치·지연 기반 라우팅 등 응답 방식을 정해 레코드를 완성한다.

#5한 줄 요약

이름·타입·값·TTL·라우팅 정책이라는 다섯 요소로 하나의 DNS 응답 단위를 정의하고, 그 규칙에 따라 질의에 대한 답을 결정하는 것

입력창에 웹사이트 주소를 입력했을 때 브라우저가 그 이름을 IP 주소로 바꾸는 질의를 보내면, Route 53은 그 도메인에 적혀 있는 A 레코드(도메인 이름을 IPv4 주소로 연결하는 가장 기본적인 레코드)의 값을 찾아 IP 주소를 돌려줍니다. 같은 도메인에 여러 레코드 타입이 함께 적혀 있어도, 질의의 종류에 따라 해당 타입만 골라 응답하는 것이 DNS 질의의 기본 동작입니다.

#4동작 과정

  2. 레코드 작성호스티드 존에 이름, 타입, 값(TTL 등 설정 포함)을 입력해 해당 질의가 들어왔을 때 돌려줄 답을 등록한다.
  3. 질의 응답실제 DNS 질의가 오면 Route 53이 질의 종류와 일치하는 레코드를 찾아 값을 돌려주고, 이 과정이 매 질의마다 반복된다.

#1문제 상황

CNAME 레코드는 도메인 이름을 다른 도메인 이름으로 연결하는 유일한 수단으로 널리 쓰였지만, 두 가지 명확한 제약이 있었습니다. 첫째, 도메인의 가장 위쪽인 존 루트(apex, 예: example.com)에는 CNAME을 만들 수 없습니다. CNAME은 그 이름에 다른 레코드가 존재하면 안 되기 때문입니다. 둘째, CNAME으로 연결된 이름은 DNS가 다시 한 번 질의를 추가로 수행해야 하므로 응답 경로가 하나 더 생깁니다. AWS 리소스(ELB, CloudFront, S3 웹사이트 등)는 도메인 이름으로 주소가 주어지는데, 정작 존 루트에서 그 이름으로 연결할 방법이 없어 배포 구조를 짜기 어려운 것이 기존 방식의 한계입니다.

#2핵심 질문

"존 루트(apex)에서도 AWS 리소스를 직접 가리키면서 추가 질의 없이 응답할 방법은 없을까?"

#3동작 예시

example.com을 CloudFront 배포에 연결한다고 가정합니다. CNAME을 쓰려면 www.example.com 같은 별도 이름을 만들어 거기에 CNAME을 걸어야 하지만, 별칭(Alias) 레코드를 쓰면 example.com 자리에 그대로 CloudFront 도메인 이름을 값으로 넣을 수 있습니다. Route 53은 이 값을 DNS 응답에서 곧바로 IP 주소로 바꾸어 돌려줍니다.

#4동작 과정

  1. 레코드 종류 선택대상이 AWS 리소스면 별칭(Alias) 레코드를, AWS 바깥의 일반 도메인 이름이면 CNAME 레코드를 선택한다.
  2. 값 입력별칭 레코드에는 AWS 리소스 이름을, CNAME에는 연결할 도메인 이름을 값으로 넣는다.
  3. 질의 응답별칭 레코드는 Route 53이 내부적으로 값을 IP로 변환해 한 번에 응답하고, CNAME은 응답에 다른 도메인 이름을 실어 보내 조회자가 다시 질의하게 한다.

#3동작 예시

#4동작 과정

  1. 존 파일 준비BIND 형식으로 레코드를 적은 텍스트 파일을 준비하고, 가져온 뒤 충돌하지 않도록 파일 내용을 확인한다.
  2. 가져오기 실행Route 53 가져오기 기능으로 파일을 올려 기존 레코드와 병합하거나 대체하는 방식으로 한 번에 등록한다.
  3. 동작 제약 확인·응답DNS 응답 크기 제한과 EDNS0(큰 UDP 응답을 주고받기 위한 DNS 확장) 등 제약을 확인한 뒤, 질의에 맞는 응답을 정상적으로 돌려준다.

"DNS 질의가 들어올 때마다 상황에 따라 어떤 서버로 보낼지 다르게 결정하려면 어떻게 해야 하는가?"

#3동작 예시

#4동작 과정

  2. 레코드 구성같은 도메인 이름 아래 정책에 필요한 레코드들을 만들고 각각의 값과 조건(가중치, 지역, 상태 확인 등)을 넣는다.

#4동작 과정

#1문제 상황

기존 라우팅 정책들은 사용자의 위치나 지연 시간을 기준으로 응답을 정하지만, 정작 "어떤 네트워크(IP 대역)에서 왔는지"를 직접 보고 응답을 바꾸는 방법은 없다. 회사 내부망 사용자에게는 내부 서버를, 외부 사용자에게는 공개 서버를 알려주는 식의 제어는 DNS 설정만으로 불가능했다. 다중값 응답의 경우, 여러 서버 중 정상 서버 하나만 돌려주는 기능도 기본 라우팅에는 없다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 규칙 등록IP 기반 라우팅은 CIDR 범위와 응답 레코드를 짝지어 등록하고, 다중값 응답 라우팅은 각 레코드에 헬스 체크를 연결해 등록한다.
  2. 질의 처리IP 기반 라우팅은 질의가 온 IP가 어느 CIDR 범위에 속하는지 확인하고, 다중값 응답 라우팅은 헬스 체크 상태를 조회해 정상 레코드를 걸러낸다.
  3. 응답 반환IP 기반 라우팅은 해당 범위의 레코드 IP를, 다중값 응답 라우팅은 정상 레코드 중 무작위로 고른 레코드들의 IP를 답으로 돌려준다.

#2핵심 질문

IP 주소가 아니라 AWS 리소스의 이름만으로 트래픽을 그 리소스로 보낼 수는 없을까?

#3동작 예시

#4동작 과정

  1. 별칭 레코드 생성도메인에 별칭(Alias) 레코드를 만들고, 대상 유형에서 라우팅할 AWS 리소스(로드 밸런서, CloudFront, S3 버킷, EC2 등)를 선택한다.
  2. 리소스 주소 조회질의가 오면 Route 53이 해당 리소스가 현재 사용하는 IP 주소나 호스트 이름을 AWS 내부에서 조회한다.
  3. 최신 주소 응답조회된 주소를 DNS 답으로 돌려주고, 리소스의 IP가 바뀌어도 다음 질의부터는 새로운 주소로 응답한다.

트래픽 정책과 정책 레코드

Traffic Flow에서 만든 트래픽 정책을 생성·관리하고, 이를 도메인 이름에 연결하는 정책 레코드로 배포하는 과정

#1문제 상황

기존에는 각 DNS 레코드를 하나씩 만들고, 라우팅 정책(가중치, 지연 시간, 장애 조치 등)을 레코드마다 개별 설정해야 했다. 트래픽 분산 구성을 바꾸려면 레코드를 일일이 수정해야 했고, 복잡한 분산 규칙을 재사용하거나 다른 도메인에 같은 규칙을 적용하려면 처음부터 다시 설정해야 했다. 설정 내용과 실제 적용된 레코드가 분리되어 있지 않아서 구성 관리가 어렵고 실수하기 쉬웠다.

#2핵심 질문

복잡한 트래픽 분산 규칙을 한 번 만들어 두고 여러 도메인에 재사용하면서, 설정과 실제 배포를 분리해서 관리할 수는 없을까?

#3동작 예시

콘솔의 Traffic Flow 화면에서 두 지역의 엔드포인트를 절반씩 나누는 "지연 시간 기반 50:50 분산" 트래픽 정책을 만든다. 이 정책을 example.com 레코드에 연결하면 정책 레코드가 생성되어 그 순간부터 DNS 쿼리에 그 규칙이 적용된다. 나중에 같은 정책을 blog.example.com에도 그대로 연결해서 재사용한다.

#4동작 과정

  1. 트래픽 정책 생성Traffic Flow 편집기에서 엔드포인트(트래픽이 갈 목적지)와 라우팅 규칙을 조합해 정책을 만들고 버전을 저장한다. 정책을 수정할 때마다 새 버전 번호가 붙어 이전 설정으로 되돌릴 수 있다.
  2. 정책 레코드 생성만든 정책을 적용할 도메인 이름을 선택하면, 그 정책이 연결된 정책 레코드가 호스팅 영역에 배포된다. 정책의 규칙이 그대로 DNS 응답에 반영되기 시작한다.
  3. 재사용과 수정같은 정책을 다른 도메인에 또 연결하고, 정책을 새 버전으로 수정하면 그 정책을 쓰는 모든 정책 레코드에 변경이 한 번에 적용된다.

#2핵심 질문

트래픽 정책의 동작을 프로그램이 읽고 만들 수 있도록, 정책의 내용을 어떤 구조의 문서로 기술해야 할까?

#3동작 예시

하나의 트래픽 정책 문서는 최상위 요소 하나와 그 안에 포함된 여러 규칙 요소로 구성된 트리 구조의 JSON 문서다. 예를 들어 최상위 요소에서 시작해 첫 번째 규칙으로 가중치 라우팅(각 엔드포인트에 비율을 나눠 주는 방식)을 지정하고, 그 규칙 안의 엔드포인트 목록에 두 지역의 리소스와 가중치 값을 적는 식이다.

#4동작 과정

  1. 최상위 요소 정의문서의 시작점이 되는 최상위 요소(트래픽 정책 문서 전체를 감싸는 단위)를 지정하고, 그 안에 어떤 규칙이 첫 번째로 실행될지 연결한다. 규칙 요소 하나가 곧 하나의 분산 동작이다.
  2. 규칙 요소 작성각 규칙 요소에 유형(가중치, 지연 시간, 장애 조치 등)을 지정하고, 데이터 소스(트래픽을 보낼 대상 목록)나 하위 규칙을 연결한다. 다단계로 중첩하면 조건에 따라 다른 규칙으로 분기하는 복잡한 정책을 표현할 수 있다.
  3. JSON으로 직렬화완성된 트리 구조를 JSON 형식의 텍스트로 변환해 API 호출에 사용한다. 이 문서가 곧 트래픽 정책의 내용 그 자체라서, 같은 형식이면 누가 봐도 동일한 정책으로 재현된다.

헬스 체크 유형

Route 53이 리소스 가용성을 검사하는 헬스 체크의 세 가지 유형(엔드포인트·계산식·CloudWatch 알람)을 구분해 주는 항목.

#1문제 상황

DNS는 원래 질의에 대해 등록된 IP 주소를 그대로 응답할 뿐, 그 서버가 실제로 살아 있는지 알지 못한다. 장애 조치 라우팅을 쓰더라도 "어느 쪽이 정상인지"를 판단할 근거가 없으면 트래픽을 옮길 수 없다. 그런데 확인 대상은 단순히 특정 서버의 응답일 수도 있고, 여러 지표를 조합한 계산 결과일 수도 있으며, AWS의 다른 서비스가 이미 관리하는 상태일 수도 있다. 모든 경우를 한 가지 방식으로 검사하면 정확한 판단이 어렵다.

#2핵심 질문

상태를 확인하는 대상과 방식이 다른 여러 상황에서, 리소스의 가용성을 판단할 헬스 체크를 어떤 유형으로 나누어 제공해야 할까?

#3동작 예시

웹 서버의 /health 경로를 직접 요청해 응답을 확인하는 엔드포인트 헬스 체크, 두 엔드포인트의 건강 상태를 조합해 "둘 다 죽었을 때만 실패"라고 판정하는 계산식 헬스 체크, 그리고 EC2 인스턴스의 CPU 사용률이 높을 때 울리는 CloudWatch 알람을 그대로 상태로 쓰는 CloudWatch 알람 헬스 체크를 각각 만들 수 있다.

#4동작 과정

  1. 엔드포인트 헬스 체크인터넷 상의 IP 주소나 도메인에 지정된 프로토콜(HTTP, HTTPS, TCP)로 요청을 보내고 응답이 오는지, 상태 코드가 설정값과 맞는지를 검사한다. 가장 기본적인 유형으로, Route 53이 직접 대상을 확인한다.
  2. 계산식 헬스 체크여러 개의 기존 헬스 체크 상태를 하나의 표현식으로 묶어 판정한다. 예를 들어 주 리소스와 백업 리소스의 상태를 AND나 OR로 조합해 하나의 결과를 낸다.
  3. CloudWatch 알람 헬스 체크CloudWatch(리소스 지표를 수집·알림하는 서비스) 알람의 상태(OK, ALARM)를 그대로 헬스 체크 상태로 사용한다. 알람이 울리면 Unhealthy로 간주되며, 별도의 요청 검사 없이 지표 기반 판단이 가능하다.

헬스 체크 생성과 건강 판정

헬스 체크를 만들 때 지정하는 설정 값과 Route 53이 요청 간격·실패 임계값 등을 기준으로 Healthy/Unhealthy를 판정하는 방식을 다루는 항목.

#1문제 상황

헬스 체크를 만들 수만 있다고 해서 상태 판정이 정확해지지는 않는다. 검사를 얼마나 자주 보낼지, 몇 번 실패해야 실패로 확정할지, 어떤 응답을 정상으로 볼지를 정하지 않으면 일시적 지연 하나로 정상 서비스를 죽은 것으로 오판할 수 있다. 또한 검사자가 어디서 오는지에 따라 방화벽이나 네트워크 환경 때문에 오탐이 생기기도 한다. 그래서 판정 기준을 명확히 설정하고 검사가 어디서 실행되는지를 이해해야 한다.

#2핵심 질문

일시적인 네트워크 지연을 장애로 오판하지 않으면서, 진짜 장애를 놓치지 않도록 헬스 체크의 판정 기준을 어떻게 설정해야 할까?

#3동작 예시

웹 서버 엔드포인트에 대해 요청 간격 30초, 실패 임계값 3으로 설정한 헬스 체크를 만든다. 검사자가 30초마다 요청을 보내고, 연속 3번 실패해야 Unhealthy로 바뀌며, 다시 연속 3번 성공해야 Healthy로 되돌아온다. 이렇게 하면 한두 번의 일시적 실패는 장애로 처리되지 않는다.

#4동작 과정

  1. 설정 값 지정검사할 엔드포인트(IP·도메인·포트)와 프로토콜, 요청 간격(요청을 보내는 주기, 기본 30초), 실패 임계값(몇 번 연속 실패해야 실패로 확정할지)을 정한다. HTTP 계열이면 정상으로 볼 상태 코드 범위도 선택한다.
  2. 정기 검사 실행Route 53의 검사 지점들이 설정된 간격으로 대상에 요청을 보낸다. 검사 지점의 위치와 수에 따라 요청이 어디서 오는지가 달라지므로, 방화벽에서 해당 위치의 요청을 허용해야 오탐이 나지 않는다.
  3. 건강 상태 판정연속 실패 횟수가 설정한 실패 임계값에 도달하면 상태가 Healthy에서 Unhealthy로 전환되고, 이후 연속 성공 횟수가 임계값에 도달하면 다시 Healthy로 전환된다. 이 상태가 장애 조치 라우팅의 판단 근거가 된다.

#5한 줄 요약

요청 간격·실패 임계값·정상 응답 기준을 설정하고 검사 지점이 정기적으로 요청을 보내, 연속 실패와 연속 성공 횟수로 Healthy/Unhealthy를 판정하는 것

헬스 체크 관리와 모범 사례

헬스 체크의 비활성화·반전·삭제·태깅 등 사후 관리 방법과 헬스 체크 운영 모범 사례를 설명하는 항목.

→ 12-02 참조

#1문제 상황

헬스 체크는 만들고 나서 그대로 두면 되는 것이 아니다. 검사를 일시적으로 중단해야 하는 상황(점검, 배포 중)이 생기면 헬스 체크가 계속 실패를 누적해 불필요한 장애 조치를 유발한다. 또한 헬스 체크가 어떤 서비스·환경을 담당하는지 관리 표시가 없으면 체크가 늘어날수록 파악이 어려워지고, 더 이상 쓰지 않는 체크를 방치하면 요금과 혼선만 남는다. 운영 관점의 관리 방법이 없다면 헬스 체크 자체가 장애 요인이 된다.

#2핵심 질문

점검·배포 같은 일시적 상황에서 오탐을 막고, 여러 헬스 체크를 식별하고 정리하며 운영할 수 있는 방법은 무엇일까?

#3동작 예시

배포 중인 서버에 대해 헬스 체크의 실패 알림이 울리지 않도록 헬스 체크를 일시 비활성화하거나 상태를 반전(정상이면 Unhealthy로 표시)시켜 검사 결과의 의미를 바꾸고, 각 체크에 환경 태그를 붙여 운영 중 어느 체크가 어떤 서비스를 보는지 구분한다. 더 이상 쓰지 않는 체크는 삭제한다.

#4동작 과정

  1. 일시 제어점검 중에는 헬스 체크를 비활성화해 검사 결과를 무시하거나, 반전 옵션(검사 성공을 Unhealthy로, 실패를 Healthy로 바꾸는 설정)을 켜서 알람 규칙과의 연동 방식을 바꾼다. 이런 설정은 POST 요청처럼 외부에서도 제어할 수 있다.
  2. 식별과 태깅헬스 체크에 이름과 태그(키-값 쌍)를 부여해 어떤 리소스를 담당하는지 표시한다. 태그로 검색·필터링·비용 구분이 가능해져 체크가 많아져도 관리가 유지된다.
  3. 삭제와 정리담당 리소스가 사라진 헬스 체크는 삭제한다. 다만 삭제하면 그 체크를 참조하는 계산식 헬스 체크나 장애 조치 레코드의 동작이 바뀔 수 있으므로 참조 관계를 확인한 뒤 지운다. 모범 사례로, 동일한 대상의 헬스 체크가 세 곳 이상의 검사 지점 위치에 걸쳐 실행되도록 구성해 한 지역의 검사 실패가 전체 오판으로 번지지 않게 한다.

#5한 줄 요약

헬스 체크를 비활성화·반전·삭제·태깅으로 일시 제어하고 정리하며, 검사 지점 분산 같은 운영 기준을 지켜 오탐 없이 관리하는 것

DNS 장애 조치 구성

헬스 체크 결과에 따라 트래픽이 정상 리소스로 전환되도록 active-active/active-passive 장애 조치 라우팅을 구성하는 방법을 안내하는 항목.

→ 05-05 참조

#1문제 상황

장애 조치를 하려면 우선 "누가 정상인지"를 아는 헬스 체크가 있어야 하지만, 헬스 체크만으로는 트래픽이 정상 리소스로 실제로 옮겨가지 않는다. DNS 레코드가 헬스 체크 결과를 어떤 방식으로 반영할지, 그리고 주 리소스가 복구됐을 때 어떻게 돌아올지를 구성해 두지 않으면 장애 조치는 동작하지 않는다. 또한 서비스가 항상 모든 리소스를 함께 써야 하는지(active-active), 하나는 대기로 두어야 하는지(active-passive)에 따라 구성이 달라져야 한다.

#2핵심 질문

헬스 체크 결과에 따라 트래픽이 정상 리소스로 전환되고 복구 시 다시 돌아오도록 DNS 라우팅을 어떤 구조로 구성해야 할까?

#3동작 예시

장애 조치 라우팅 정책을 쓰는 두 개의 레코드를 만든다. 주 레코드는 기본으로 활성(active) 상태에 있고 헬스 체크를 연결하며, 백업 레코드는 대기(passive) 상태로 같은 도메인의 별도 리소스를 가리킨다. 주 레코드의 헬스 체크가 Unhealthy가 되면 Route 53은 대기 레코드의 리소스로 응답을 바꾼다.

#4동작 과정

  1. 운영 방식 선택서비스가 모든 리소스를 동시에 사용해도 되면 active-active(모든 레코드에 헬스 체크를 연결하고, 실패한 레코드만 응답에서 제외하는 방식)를, 주 리소스 하나가 모든 트래픽을 받고 나머지는 대기로 두려면 active-passive(주 레코드에만 헬스 체크를 연결하고 실패 시 대기 레코드로 전환하는 방식)를 선택한다.
  2. 레코드와 헬스 체크 연결장애 조치 라우팅 정책의 레코드들을 만들고, 각 레코드에 검사할 헬스 체크를 연결한다. 레코드마다 헬스 체크가 하나씩 붙거나, 계산식 헬스 체크로 여러 검사를 묶을 수 있다.
  3. 장애 시 응답 전환과 복구연결된 헬스 체크가 Unhealthy가 되면 그 레코드는 DNS 응답에서 제외되어 트래픽이 정상 레코드로 흐른다. 헬스 체크가 Healthy로 복구되면 원래 레코드가 다시 응답에 포함되어 트래픽이 자동으로 되돌아온다.

#5한 줄 요약

active-active 또는 active-passive 구조로 레코드에 헬스 체크를 연결해, 헬스 체크 상태에 따라 DNS 응답을 정상 리소스로 자동 전환하고 복구 시 되돌리는 것

헬스 체크 상태 모니터링과 알림

헬스 체크 상태와 실패 원인을 확인하고 CloudWatch 지표·알람으로 상태 변화를 모니터링하고 알림을 받는 방법을 다루는 항목.

#1문제 상황

헬스 체크가 장애를 감지해도 그 사실을 사람이 알아차리지 못하면 장애 조치는 되었을지라도 원인 파악과 대응이 늦어진다. 헬스 체크 상태가 언제, 왜 바뀌었는지를 확인할 방법이 없으면 일시적 오탐인지 실제 장애인지조차 구분하기 어렵고, 여러 체크가 동시에 실패했을 때 어느 것이 원인인지 추적할 수 없다. 상태 변화를 눈으로 보고 받을 수 있는 모니터링·알림 체계가 없다면 헬스 체크 운영은 반쪽이다.

#2핵심 질문

헬스 체크의 현재 상태와 실패 원인을 확인하고, 상태가 변하는 순간을 지표와 알림으로 알아챌 수 있는 방법은 무엇일까?

#3동작 예시

콘솔의 헬스 체크 목록에서 특정 체크를 열어 최근 상태 변화 이력과 각 검사 지점의 실패 원인(연결 거부, 타임아웃, 상태 코드 불일치 등)을 확인한다. 동시에 그 헬스 체크가 내보내는 CloudWatch 지표(HealthyHostCount 등)에 알람을 연결해, 상태가 Unhealthy로 바뀌는 순간 이메일이나 SNS(문자·이메일 등으로 알림을 보내는 서비스) 알림을 받는다.

#4동작 과정

  1. 상태 확인콘솔의 상태 페이지나 GetHealthCheckStatus API로 각 헬스 체크의 현재 상태를 확인한다. Route 53은 헬스 체크가 언제 생성·수정·삭제되었는지 감사 로그(AWS CloudTrail)에도 기록한다.
  2. 지표 관찰헬스 체크마다 CloudWatch 지표가 자동으로 게시되므로, 상태가 Healthy/Unhealthy로 바뀐 횟수나 검사 지점별 실패 원인을 차트로 살펴본다. 실패 원인 코드가 무엇인지에 따라 네트워크 문제인지 응용 계층 문제인지 가늠할 수 있다.
  3. 알람 설정과 수신CloudWatch 알람을 만들어 헬스 체크 지표가 임계값에 닿으면(예: 상태가 Unhealthy가 되면) SNS 주제로 알림을 보낸다. 이후 상태 변화가 생길 때마다 이메일·문자 등으로 통지를 받아 바로 대응한다.

DNSSEC 서명 개요

DNS 응답의 위·변조를 막기 위해 호스티드 존의 레코드에 디지털 서명을 입히는 DNSSEC 서명의 개념과 동작 원리.

#1문제 상황

일반적인 DNS 질의에서는 클라이언트가 리졸버(중계 서버)에 도메인 이름을 물어보고, 리졸버는 권위 있는 DNS 서버(도메인 이름의 최종 정답을 가진 서버)에서 받은 IP 주소를 그대로 돌려준다. 이 응답은 암호화되지도 않았고 무결성을 검증하는 장치도 없다. 그래서 공격자가 리졸버와 권위 서버 사이의 응답을 가로채 가짜 IP 주소로 바꿔치기하면, 사용자는 자신도 모르는 사이에 악성 서버로 접속하게 된다. 이렇게 DNS 응답을 위·변조하는 공격은 사용자 측에서 알아차릴 방법이 없다.

#2핵심 질문

클라이언트가 받은 DNS 응답이 진짜 권위 있는 서버가 서명한 정당한 응답인지 어떻게 확인할 수 있을까?

#3동작 예시

호스티드 존(레코드들의 묶음)에 DNSSEC을 켜면, Route 53이 그 존의 모든 레코드에 대해 디지털 서명(데이터에 암호화 방식으로 찍는 전자 도장)을 만들어 함께 게시한다. 클라이언트 측 리졸버는 응답에 붙은 서명을 존의 공개 키로 검증해서, 서명이 맞으면 응답이 전송 중에 바뀌지 않았다고 확신한다.

#4동작 과정

  1. 서명 생성Route 53이 존의 각 레코드 집합에 대한 디지털 서명을 만들어 DNS 응답과 함께 제공한다.
  2. 질의와 검증리졸버가 응답과 서명을 받아 존의 공개 키로 서명을 풀어 본다. 서명이 레코드 내용과 일치하면 정상, 일치하지 않으면 위·변조된 것으로 판단한다.
  3. 신뢰 전달존의 공개 키는 부모 존이 서명한 DS 레코드(자식 존의 키 정보를 부모 존에 등록한 레코드)로 보증되므로, 검증은 최상위까지 이어진 체인을 따라 이뤄진다.

#5한 줄 요약

DNS 응답에 디지털 서명을 입혀 클라이언트가 응답의 진위와 무결성을 암호로 검증할 수 있게 만드는 것

DNSSEC 활성화와 신뢰 체인

KMS 키로 호스티드 존의 DNSSEC 서명을 켜고 부모 존에 DS 레코드를 등록해 존 간 신뢰 체인을 세우는 과정.

→ 04-03 참조

#1문제 상황

호스티드 존에 DNSSEC을 켜지 않은 상태에서는 레코드에 서명이 없어서 클라이언트가 응답의 진위를 검증할 길이 없다. 서명만 만들어 놓아도 부족한데, 그 서명을 검증할 공개 키를 누가 보증하는지가 정해져 있어야 한다. 공개 키를 자체적으로만 신뢰하면 공격자가 키까지 바꿔치기할 수 있기 때문이다. 그래서 DNSSEC은 "누가 이 키를 인증했는가"를 부모 존이 서명한 DS 레코드로 연결하는 체인 구조를 요구한다.

#2핵심 질문

존의 서명을 검증할 공개 키가 진짜 그 존의 것임을 어떻게 외부에서 확인하게 할까?

#3동작 예시

Route 53에서 호스티드 존의 DNSSEC을 켜면 KMS 키(암호화 키를 안전하게 보관·관리하는 AWS 서비스의 키)로 서명이 시작되고, 콘솔은 이 존의 공개 키를 담은 DS 레코드(부모 존에 등록하는 자식 키 정보) 값을 알려준다. DNSSEC을 지원하는 부모 존에 이 DS 레코드를 등록하면, 부모가 자식 존의 키를 서명으로 보증하면서 신뢰 체인(위에서 아래로 이어지는 검증 연결)이 완성된다.

#4동작 과정

  1. 서명 활성화호스티드 존의 DNSSEC 서명을 켜고 KMS 고객 관리 키를 지정한다. 이 키가 존의 서명을 만들고 관리한다.
  2. DS 레코드 등록부모 존이나 도메인 등록 대행사에 DS 레코드를 등록해서, 부모 존이 이 존의 키를 보증하게 만든다.
  3. 체인 완성과 확인리졸버가 부모 존의 서명으로 자식 존의 키를 검증하고, 그 키로 실제 레코드의 서명을 검증해서 전체 신뢰 체인이 동작한다.

#5한 줄 요약

KMS 키로 존에 서명을 켜고 부모 존에 DS 레코드를 등록해, 부모가 자식의 키를 보증하는 신뢰 체인을 세우는 것

8DNSSEC08-03

키 관리

DNSSEC 서명에 쓰는 키 서명 키(KSK)와 영역 서명 키(ZSK)를 KMS 고객 관리 키와 함께 관리·교체하는 작업.

#1문제 상황

DNSSEC에는 서로 다른 역할의 키가 두 종류 있다. 영역 서명 키(ZSK)는 실제 레코드 데이터에 서명을 하고, 키 서명 키(KSK)는 그 ZSK 자체에 서명해서 ZSK의 신뢰성을 보증한다. KSK는 부모 존의 DS 레코드에 연결되므로 공개되는 값이 바뀌면 DS 레코드도 함께 갱신해야 한다. 키를 한 번 만들어 평생 쓰면 키가 유출됐을 때 서명 전체가 위조될 수 있으므로, 주기적으로 키를 새것으로 교체하고 DS 레코드를 맞춰 갱신하는 관리 작업이 필요하다.

#2핵심 질문

KSK와 ZSK를 안전하게 보관하면서, 키 교체 때 DS 레코드와 서명 체인이 끊기지 않게 하려면 어떻게 해야 할까?

#3동작 예시

Route 53에서는 KSK와 ZSK를 KMS 고객 관리 키로 관리한다. DNSSEC을 켜면 Route 53이 KSK 하나와 ZSK 하나를 KMS에 만들고, ZSK는 일정 주기로 자동 교체되며 KSK는 사용자가 직접 교체 시점을 정한다. KSK를 교체하면 콘솔이 새 DS 레코드 값을 제공하고, 사용자가 부모 존의 DS 레코드를 새 값으로 바꾸면 체인이 계속 이어진다.

#4동작 과정

  1. 키 생성과 역할 분리KMS에 KSK와 ZSK를 만들고, ZSK는 레코드 서명에, KSK는 ZSK 서명에 각각 사용한다.
  2. ZSK 자동 교체Route 53이 ZSK를 주기적으로 새 키로 바꾸고 새 ZSK로 레코드를 다시 서명한다. ZSK는 KSK가 보증하므로 DS 레코드 갱신 없이 교체된다.
  3. KSK 수동 교체와 DS 갱신사용자가 KSK를 새 키로 교체하면 새 DS 레코드 값을 부모 존에 등록하고, 이전 DS 레코드가 사라질 때까지 충분한 시간을 두고 이전 키를 제거한다.

#5한 줄 요약

KSK와 ZSK를 KMS 고객 관리 키로 나누어 관리하고, ZSK는 자동으로 KSK는 DS 레코드 갱신과 함께 교체해 서명 체인을 끊기지 않게 유지하는 것

비활성화·무존재 증명·문제 해결

DNSSEC 서명을 끄는 절차, 존재하지 않는 이름에 대한 무존재 증명 원리, 그리고 서명 관련 문제를 진단하는 방법.

#1문제 상황

DNSSEC은 존재하는 레코드에 서명을 붙이지만, 존재하지 않는 이름에 대한 질의(예: 없는 하위 도메인)는 서명할 데이터 자체가 없다. 그런데도 리졸버는 "이 이름은 없다"는 응답을 신뢰해야 한다. 이름이 없다는 부정적 응답에 서명이 없으면, 공격자가 "그런 이름은 없다"는 가짜 응답을 만들어 정상 서비스를 차단할 수 있다. 또한 서명 키나 DS 레코드 설정이 어긋나면, 정상적인 응답도 리졸버가 검증에 실패해 버리는 문제가 생긴다.

#2핵심 질문

존재하지 않는 이름에 대한 응답도 위조할 수 없게 하면서, 서명 설정이 잘못됐을 때는 어떻게 진단할까?

#3동작 예시

Route 53은 존재하지 않는 이름에 대해 NSEC 또는 NSEC3 레코드(존에 없는 이름 범위를 증명하는 레코드)에 서명을 붙여 응답한다. 이 서명된 레코드는 "이 이름은 이 존에 없다"는 사실 자체를 암호로 증명하므로, 공격자가 부정적 응답을 위조해도 검증에서 걸러진다.

#4동작 과정

  1. 무존재 증명 응답없는 이름에 대한 질의가 오면 Route 53이 해당 이름이 존재하지 않음을 증명하는 NSEC/NSEC3 레코드와 서명을 돌려준다.
  2. 검증과 판정리졸버가 그 서명을 검증해 "없음" 응답이 정당한 것임을 확인한다.
  3. 문제 진단서명 검증이 실패하면 Route 53 콘솔의 DNSSEC 상태를 확인해 서명이 꺼졌는지, DS 레코드가 키와 불일치하는지, 키 교체가 어긋났는지 찾아 고친다.

#5한 줄 요약

존재하지 않는 이름까지 서명된 무존재 증명 레코드로 보호해 부정적 응답의 위조까지 막고, 서명 상태 점검으로 문제를 진단하는 것

9VPC Resolver와 하이브리드 DNS09-01

VPC Resolver 개요

VPC와 온프레미스, VPC 간의 DNS 질의를 처리하고 중계해서 하이브리드 DNS 환경을 가능하게 하는 Route 53의 리졸버 서비스

#1문제 상황

기본적으로 각 VPC(가상 네트워크)는 AWS가 제공하는 DNS 서버를 쓰고, VPC 안의 리소스는 이 서버로 도메인 이름을 풀어낸다. 그러나 이 기본 서버는 VPC 내부 리소스와 AWS 서비스의 이름만 풀 수 있고, 온프레미스(사내 데이터센터)의 사설 도메인 이름이나 VPC와 VPC 사이의 이름은 알지 못한다. 그래서 온프레미스 서버와 VPC를 하나의 DNS 체계로 묶으려면, 양쪽의 DNS 질의를 서로 중계해 줄 별도의 장치가 필요해진다.

#2핵심 질문

VPC와 온프레미스, 그리고 VPC 사이의 DNS 질의를 한 체계 안에서 서로 주고받게 하려면 어떻게 해야 할까?

#3동작 예시

VPC Resolver는 VPC를 위한 DNS 리졸버 서비스로, VPC 안의 인스턴스가 던지는 질의를 받아 온프레미스 DNS 서버로 보내거나, 반대로 온프레미스에서 들어온 질의에 VPC 내부 이름을 답해 준다. 이 중계가 있으면 양쪽이 서로의 사설 도메인 이름을 한 DNS 체계처럼 풀어낼 수 있다.

#4동작 과정

  1. 질의 수신VPC 안의 인스턴스가 이름을 풀기 위해 질의를 보내면 Resolver가 이를 받는다.

#2핵심 질문

Resolver DNS Firewall 개요

VPC 안팎의 DNS 질의가 악성 도메인(멀웨어·피싱 등)으로 향하지 못하도록 차단·허용을 제어하는 Route 53 Resolver의 방화벽 기능이다.

#1문제 상황

VPC 안의 인스턴스가 DNS 질의를 보내면 VPC Resolver가 그 이름을 그대로 풀어 응답을 돌려준다. 기본 상태에서는 어떤 도메인 이름이든 질의가 허용되므로, 악성 도메인(멀웨어 배포지, 피싱 사이트 등)을 호출하는 프로그램이 있어도 Resolver는 정상 응답을 주고 만다. 인스턴스가 감염되면 그 악성 도메인과의 통신이 계속 성립되어 데이터 유출·추가 감염의 통로가 막히지 않는다.

#2핵심 질문

VPC 안에서 악성 도메인으로 향하는 DNS 질의 자체를 막을 수는 없을까?

#3동작 예시

어떤 인스턴스가 알려진 멀웨어 도메인 malware.example.net을 질의했을 때, Resolver DNS Firewall이 연결된 VPC라면 이 질의를 규칙과 대조해 차단(블록) 동작을 취하고, 인스턴스에는 차단 응답이 돌아가며 질의한 프로그램은 통신을 시작하지 못한다. 이렇게 질의 단계에서 이름을 거르기 때문에 악성 서버와의 연결이 성립되기 전에 막히는 것이 이 기능의 핵심 흐름이다.

#4동작 과정

  1. 규칙 그룹 연결VPC에 DNS Firewall 규칙 그룹(도메인 이름별 동작 목록)을 연결해 보호를 적용한다.
  2. 질의 판별VPC 안에서 발생하는 DNS 질의를 Resolver가 규칙 그룹의 도메인 목록과 대조해 차단·허용·경고(알림만) 중 하나의 동작을 결정한다.
  3. 동작 적용결정된 대로 차단이면 응답을 막고, 허용이면 정상 응답을 주며, 관련 이벤트를 기록해 관리자가 확인할 수 있게 한다.

#5한 줄 요약

VPC 안팎의 DNS 질의를 도메인 이름 기준으로 검사해 악성 도메인으로 향하는 요청을 차단·제어하는 DNS 계층 방화벽

규칙 그룹과 규칙

도메인 이름 기준으로 DNS 질의를 처리하는 규칙(어떤 동작을 취할지)을 하나로 묶어 관리하는 단위로, 규칙 그룹을 VPC에 연결해 실제 보호를 적용한다.

#1문제 상황

DNS 질의를 막으려면 어떤 도메인에 어떤 동작을 취할지 기준이 필요하지만, 도메인 이름 하나하나를 VPC에 직접 나열해 연결하는 방식은 관리가 산만해지고, 같은 기준을 여러 VPC에 적용하려면 같은 설정을 반복해서 만들어야 한다. 도메인이 늘어날수록 어느 VPC에 어떤 차단 목록이 적용됐는지 파악하기 어려워진다.

#2핵심 질문

여러 도메인에 대한 차단·허용 기준을 한 덩어리로 묶어 VPC마다 쉽게 적용할 수는 없을까?

#3동작 예시

"악성 도메인 차단" 규칙 그룹 하나를 만들어 그 안에 malware1.com은 차단, malware2.net은 차단, 내부 도메인 허용 같은 규칙들을 담아 두고, 이 규칙 그룹 하나를 VPC A, VPC B에 각각 연결하면 두 VPC 모두 같은 보호 기준을 즉시 적용받는다. 도메인을 추가로 막으려면 규칙 그룹 안의 목록만 고치면 연결된 모든 VPC에 반영된다.

#4동작 과정

  1. 규칙 생성도메인 이름과 그 도메인에 취할 동작(차단, 허용, 경고)을 정해 개별 규칙을 만든다.
  2. 규칙 그룹 구성만든 규칙들을 하나의 규칙 그룹으로 묶고, 우선순위(priority)를 정해 어느 규칙을 먼저 적용할지 결정한다.
  3. VPC 연결규칙 그룹을 보호하려는 VPC에 연결하여, 그 VPC의 질의가 규칙 그룹 기준으로 처리되게 한다.

#5한 줄 요약

도메인별 동작(규칙)을 하나의 규칙 그룹으로 묶어 VPC에 연결함으로써, 차단 기준을 한 번 정의해 여러 VPC에 일관되게 적용하는 관리 단위

도메인 리스트와 고급 보호

차단하거나 허용할 도메인 이름을 모아 둔 목록(관리형·사용자 관리형)과, 그 목록을 넘어서는 고급 보호 기능(Advanced DNS Protections)을 제공하는 기능군이다.

#1문제 상황

규칙 하나에 도메인 이름을 하나씩 적는 방식으로는 차단 대상이 수천 개가 되면 관리가 불가능해진다. 또한 차단 목록에 없는 새로 등장한 악성 도메인은 별도 대응이 없으면 그대로 통과된다. 도메인 이름만으로는 "방금 만들어진 악성 도메인"이나 "목록에 없는 의심 도메인"을 잡아낼 수 없어, 수동 목록 관리만으로는 공격에 뒤처진다.

#2핵심 질문

도메인 이름을 목록 단위로 관리하면서, 목록에 없는 악성 도메인까지 막을 수는 없을까?

#3동작 예시

"AWS 관리형 악성 도메인 리스트"를 규칙 그룹에 연결해 두면, AWS가 지속적으로 갱신하는 수천 개의 알려진 악성 도메인 이름이 그대로 차단 기준이 된다. 여기에 더해 고급 보호(Advanced DNS Protections)를 켜면, 예를 들어 짧은 시간 안에 없는 이름(존재하지 않는 도메인)을 대량으로 질의하는 행위(랜덤 도메인 공격의 징후)를 탐지해 추가로 차단할 수 있다.

#4동작 과정

  1. 도메인 리스트 연결관리형(서비스가 제공) 또는 사용자 관리형(직접 등록) 도메인 리스트를 규칙 그룹에 연결해 차단·허용 기준으로 삼는다.
  2. 고급 보호 구성기존 도메인 리스트로는 잡지 못하는 공격 패턴(랜덤 도메인 질의 등)을 탐지하는 고급 보호 옵션을 활성화해 추가 보호 계층을 켠다.
  3. 질의 대조와 차단VPC의 질의가 연결된 리스트와 고급 보호 규칙에 대조되고, 일치하는 악성 도메인·탐지된 패턴에 대해 차단이 적용된다.

#5한 줄 요약

차단·허용할 도메인 이름을 목록(관리형·사용자 관리형)으로 관리하고 고급 보호로 목록 밖 공격 패턴까지 탐지해, 도메인 차단 기준을 확장·자동화하는 기능

VPC 보호 적용·공유·이벤트

규칙 그룹을 VPC에 연결해 보호를 적용하고, 규칙 그룹을 다른 계정과 공유하며, 차단된 질의 등의 이벤트를 EventBridge로 받아 모니터링하는 과정이다.

#1문제 상황

규칙 그룹을 만들기만 하면 단독으로 동작하지 않는다. 실제로 VPC에 연결해 보호를 적용하고, 그 결과 어떤 질의가 차단됐는지 알 수 있어야 운영이 가능하다. 다만 기업 환경에서는 VPC가 여러 계정에 흩어져 있어 한 계정에서 만든 규칙 그룹을 다른 계정의 VPC에 직접 연결할 수 없고, 차단이 발생해도 어디에도 알림이 없으면 관리자가 이상 징후를 눈치채기 어렵다.

#2핵심 질문

규칙 그룹을 여러 계정의 VPC에 적용하고, 차단 발생 사실을 자동으로 알 수는 없을까?

#3동작 예시

보안 팀 계정에서 만든 규칙 그룹을 AWS Resource Access Manager(RAM)로 개발 계정과 공유하면, 개발 계정의 VPC 콘솔에서 그 규칙 그룹을 선택해 연결할 수 있다. 이후 개발 환경에서 차단된 질의가 생기면 그 내용이 이벤트로 Amazon EventBridge에 전달되고, 이를 구독하는 시스템이 "오늘 10시, instance-1이 malware.com 질의로 차단됨" 같은 사실을 받아 모니터링 도구로 보낸다.

#4동작 과정

  1. 보호 적용규칙 그룹(직접 만든 것 또는 공유받은 것)을 대상 VPC에 연결하여 그 VPC에 DNS Firewall 보호를 적용한다.
  2. 그룹 공유규칙 그룹을 RAM으로 다른 계정과 공유해, 여러 계정이 같은 차단 기준을 재사용하고 각자 자기 VPC에 연결한다.
  3. 이벤트 수신차단·허용된 질의 등이 발생할 때마다 DNS Firewall이 이벤트를 EventBridge로 내보내고, 연결된 규칙이 이를 받아 알림·모니터링에 활용한다.

#5한 줄 요약

규칙 그룹을 VPC에 연결해 보호를 적용하고, RAM으로 계정 간 공유하며, 차단 이벤트를 EventBridge로 전달해 실제 보호와 그 관찰을 잇는 운영 절차

Route 53 Profiles

프라이빗 호스팅 영역·Resolver 규칙·DNS Firewall 규칙 그룹 등을 한곳에 모아 여러 VPC와 계정에 일관되게 적용하는 재사용 가능한 DNS 설정 묶음이다.

#1문제 상황

기존에는 프라이빗 호스팅 영역과 Resolver 규칙을 VPC마다 개별적으로 연결하고 설정했다. VPC가 여러 개라면 같은 설정을 VPC 수만큼 반복해서 만들어야 했고, 계정이 여러 개라면 계정 경계를 넘어 설정을 공유하기도 어려웠다. 설정을 바꿀 때도 VPC마다 일일이 찾아가 수정해야 해서 일부 VPC에 누락되거나 VPC마다 서로 다른 설정이 적용되는 문제가 생겼다.

#2핵심 질문

여러 VPC와 계정에 같은 DNS 설정을 매번 따로 만들지 않고 한 번에 일관되게 적용할 수는 없을까?

#3동작 예시

Route 53 Profiles는 프라이빗 호스팅 영역, Resolver 규칙, DNS Firewall 규칙 그룹을 하나의 프로필에 모아 둔다. 이 프로필 하나를 여러 VPC에 연결하면, 프로필에 포함된 설정 전부가 연결된 모든 VPC에 동시에 적용된다. 예를 들어 프로필 하나에 프라이빗 호스팅 영역 3개와 Resolver 규칙 2개를 담고 VPC 5개에 연결하면, 5개 VPC 모두가 그 3개 영역과 2개 규칙을 한꺼번에 사용하게 된다.

#4동작 과정

  1. 프로필 생성과 구성프라이빗 호스팅 영역·Resolver 규칙·DNS Firewall 규칙 그룹을 프로필에 추가해 DNS 설정 묶음을 만든다.
  2. 프로필 연결프로필을 대상 VPC에 연결한다. 프로필에 담긴 설정 전부가 연결된 VPC에 적용된다.
  3. 설정 변경 전파프로필의 내용을 나중에 추가·수정·삭제하면 연결된 모든 VPC에 그 변경이 함께 반영된다.

#5한 줄 요약

DNS 설정 묶음을 한 번만 만들어 여러 VPC·계정에 일괄 적용해 설정 중복과 불일치를 없애는 것

CloudWatch 모니터링

Route 53이 호스팅 영역·헬스 체크·Resolver 등 리소스의 상태와 성능 지표를 CloudWatch로 보내 경보·조회할 수 있게 하는 모니터링 기능.

#1문제 상황

기존에는 DNS 설정을 해 두면 그 뒤에 서비스가 정상인지, 쿼리가 얼마나 들어오는지 확인할 방법이 마땅치 않았다. Route 53이 처리하는 트래픽과 리소스 상태를 보여 주는 지표가 없어서 문제가 생겨도 DNS 계층에서 원인을 찾기 어려웠고, 헬스 체크가 실패하거나 쿼리가 급증해도 그 사실을 제때 알 수 없었다.

#2핵심 질문

Route 53이 처리하는 DNS 트래픽과 리소스 상태를 한곳에서 보고, 이상이 있을 때 바로 통보받을 수는 없을까?

#3동작 예시

Route 53은 호스팅 영역의 DNS 쿼리 수, 헬스 체크의 상태 전환 횟수 같은 지표를 CloudWatch에 자동으로 보낸다. CloudWatch 대시보드에서 이 지표를 그래프로 조회할 수 있고, 특정 지표가 기준 값(예: 헬스 체크 실패 횟수)을 넘으면 CloudWatch 경보가 이메일이나 SNS 주제로 알림을 보낸다.

#4동작 과정

  1. 지표 수집Route 53이 호스팅 영역·헬스 체크·Resolver 등 리소스의 지표(DNS 쿼리 수, 헬스 체크 상태 등)를 CloudWatch로 보낸다.
  2. 조회와 대시보드CloudWatch 콘솔에서 지표를 선택해 기간별 그래프로 조회하고, 여러 지표를 대시보드에 모아 한눈에 본다.

데이터 보호와 보안 구조

전송·저장 데이터 보호, DNSSEC 서명, 인프라 보안, 복원력 등 Route 53의 전체 보안 계층을 이루는 구조.

#1문제 상황

기존 방식에서 DNS 쿼리와 응답은 일반적으로 암호화되지 않은 상태로 오간다. 중간에서 쿼리 내용을 보거나 응답을 조작할 수 있고, DNS 응답이 위조되어 사용자를 잘못된 주소로 보낼 수도 있다(DNS 스푸핑). 또한 한 곳에만 의존하는 구조라면 일부 서버나 지역에 장애가 났을 때 도메인 이름 해석 자체가 멈출 위험이 있다.

#2핵심 질문

#3동작 예시

Route 53은 전 세계에 분산된 네임 서버(anycast)로 운영되어 일부 서버나 지역에 장애가 나도 다른 서버가 응답을 계속한다. DNSSEC를 켜면 호스팅 영역의 레코드에 디지털 서명이 붙어, 응답을 받는 쪽이 그 서명을 확인해 응답이 위조되지 않았는지 검증할 수 있다. 쿼리·응답이 오가는 경로에서는 전송 암호화가 제공되고, 호스팅 영역 설정 등 저장 데이터도 암호화되어 보관된다.

#4동작 과정

  1. 전송·저장 보호DNS 쿼리·응답이 오가는 경로에서 전송 암호화를 제공하고, 호스팅 영역 등 저장 데이터를 암호화해 보관한다.
  2. DNSSEC 서명호스팅 영역에 DNSSEC를 활성화하면 레코드에 디지털 서명이 붙어, 응답을 받는 쪽이 위조 여부를 검증할 수 있다.
  3. 분산 운영전 세계 서버로 트래픽을 분산해 일부 서버나 지역에 장애가 나도 이름 해석이 계속된다.

DNS 서비스 마이그레이션

기존 도메인이나 다른 DNS 서비스에서 Route 53으로 네임 서버와 레코드를 옮겨 DNS 관리를 이전하는 절차.

#1문제 상황

기존에는 도메인 등록 대행사나 다른 DNS 제공업체가 운영하는 네임 서버를 통해 도메인 이름이 IP 주소로 바뀌었다. 해당 제공업체의 웹 화면에서 레코드를 하나씩 입력하고, 그 서버가 장애가 나면 도메인 전체가 풀리지 않는 등 제어 범위가 제한적이었다. 또 기존 제공업체는 AWS 리소스와 긴밀하게 연동되는 기능(헬스 체크 기반 라우팅 등)을 쓰기 어려웠다. 이 상태에서는 트래픽을 AWS로 옮기려 해도 DNS 응답 속도와 안정성을 제대로 관리할 수 없었다.

#2핵심 질문

기존 DNS 제공업체가 응답하던 도메인을 중단 없이 Route 53으로 이전하려면 어떻게 해야 할까?

#3동작 예시

운영 중인 도메인 example.com이 기존 제공업체의 네임 서버로 응답하고 있다고 하자. Route 53에 호스팅 영역을 만들고 NS 레코드(이 도메인을 담당할 Route 53 네임 서버 목록)와 레코드들을 동일하게 복사한 뒤, 도메인 등록 대행사에서 네임 서버를 Route 53의 네임 서버 4개로 교체한다. 이 순간부터 새 DNS 조회는 Route 53이 응답하고, 기존 제공업체와 Route 53이 동일한 레코드를 갖고 있는 동안에는 서비스 중단 없이 이전이 끝난다.

#4동작 과정

  1. Route 53에 호스팅 영역 생성이전할 도메인 이름으로 호스팅 영역(도메인의 레코드를 모아두는 컨테이너)을 만들고, AWS가 부여한 네임 서버 4개의 이름을 확인한다.
  2. 레코드 복사와 TTL 축소기존 제공업체의 모든 레코드를 동일하게 복사하고, TTL(캐시에 응답을 보관하는 시간)을 미리 줄여 네임 서버 변경 후 구버전 응답이 오래 남지 않게 한다.
  3. 네임 서버 교체와 확인도메인 등록 대행사에서 NS 레코드를 Route 53의 네임 서버 4개로 바꾸고, 며칠간 기다린 뒤 레코드가 정상 응답하는지 확인하면 이전이 완료된다.

  3. 자동화와 모니터링변경은 CLI나 IaC로 진행하고, CloudWatch(지표와 로그를 모아 알림을 주는 서비스)로 조회 수와 오류를 감시한다.

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

#1문제 상황

호스팅 영역(도메인의 레코드를 모아두는 컨테이너)과 레코드를 만들 때, 많은 운영팀은 개수 제한이 없다고 생각하고 필요한 만큼 계속 추가한다. 하지만 Route 53에는 계정당 만들 수 있는 호스팅 영역 수, 호스팅 영역당 레코드 수, 헬스 체크 수 등 한도가 정해져 있다. 이 한도를 모른 채 서비스를 확장하면 어느 순간 생성 요청이 거부되고, 이미 만든 리소스를 정리해야 하는 상황이 벌어진다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 현재 사용량 확인콘솔이나 AWS CLI(명령줄 도구)로 호스팅 영역·레코드·헬스 체크의 현재 개수를 한도와 비교한다.
  2. 한도 상향 또는 정리한도에 가까우면 지원 요청으로 상향을 신청하거나 쓰지 않는 리소스를 삭제해 여유를 만든다.
  3. IP 범위 적용DNS 서버 IP 주소 범위 목록을 확인해 방화벽과 보안 그룹에 반영한다.

REST·RPC API와 자동화

REST API(호스팅 영역·레코드·헬스 체크)와 RPC API(도메인 등록·Resolver)로 Route 53을 프로그래밍 방식으로 제어하고 자동화하는 방법.

#1문제 상황

Route 53을 운영할 때 대부분의 팀은 AWS 관리 콘솔에서 호스팅 영역(도메인의 레코드를 모아두는 컨테이너)과 레코드를 하나씩 클릭해서 만든다. 이 방식은 개수가 적을 때는 빠르지만, 도메인이 수십 개로 늘면 반복 작업이 많아지고, 사람이 화면을 잘못 조작하면 레코드가 잘못 등록될 위험이 크다. 같은 작업을 여러 계정에 반복해야 하는 경우에는 시간당 할 수 있는 일에 한계가 생긴다.

#2핵심 질문

콘솔에서 손으로 반복하던 DNS 작업을 코드로 한 번에 처리하려면 어떻게 해야 할까?

#3동작 예시

새 도메인 example.com을 등록하고 호스팅 영역을 만든 뒤 A 레코드(도메인 이름과 IP 주소를 연결하는 레코드) 하나를 추가하는 작업을 생각하자. REST API(HTTP 방식으로 호스팅 영역·레코드·헬스 체크를 제어하는 인터페이스)에 담당 도메인과 레코드 정보를 담은 요청을 보내면, Route 53이 리소스를 만들고 변경 ID를 돌려준다. 이 요청을 스크립트에 담아 두면 같은 작업을 새 도메인마다 반복 실행할 수 있고, 도메인 등록이나 Resolver(조건부 DNS 전달 기능)는 별도 RPC API로 제어한다.

#4동작 과정

  1. API 요청 구성AWS CLI(명령줄 도구) 또는 SDK(프로그래밍 언어용 라이브러리)로 호스팅 영역 생성·레코드 변경 요청을 만든다.
  2. 요청 전송과 응답 확인서명(API 요청에 붙이는 인증 정보)을 포함해 Route 53 API로 보내고, 변경 ID와 상태를 확인한다.
  3. 자동화 반영이 과정을 배포 스크립트에 넣어 새 리소스가 생길 때마다 레코드가 자동으로 추가되도록 만든다.
