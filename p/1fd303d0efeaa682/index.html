1부. 웹 애플리케이션과 HTTP 기초001

웹 애플리케이션의 구조

브라우저와 서버와 데이터베이스가 요청을 주고받는 큰 그림

온라인 쇼핑몰에서 상품을 눌렀는데 화면이 하얗게 멈추고, 결제를 마친 뒤에도 주문 내역이 흔적 없이 사라진다면 아무도 그 쇼핑몰을 다시 찾지 않을 것입니다. 웹 애플리케이션(Web Application)은 이런 곤란을 없애기 위해 브라우저와 서버와 데이터베이스가 정해진 순서로 대화하도록 만든 구조입니다. 이 구조는 손님이 주문서를 적어 카운터에 넘기는 식당과 같습니다.

브라우저는 주문서를 쓰는 테이블이고, 서버는 주문을 해석해 조리를 지시하는 주방이며, 데이터베이스는 재료가 얼마나 남았는지 적어 둔 재고 장부입니다. 손님이 주문서(요청, request)를 내면 서버가 그 내용을 읽고 장부를 확인한 뒤, 완성된 접시(응답, response)를 다시 테이블로 돌려보냅니다. 서버는 요리법만 알고 재료의 양은 장부에 물어보기 때문에, 두 곳의 역할이 섞이지 않아야 주문이 엉키지 않습니다. 정리하면 웹 애플리케이션은 클라이언트인 브라우저가 요청을 보내고 서버가 이를 처리하며 데이터베이스가 상태를 보관하는 삼층 구조입니다. 화면을 그리는 일, 규칙을 판단하는 일, 기록을 보관하는 일을 나눠 맡기기에 한 곳이 느려져도 나머지가 버텨 주고 문제의 위치도 빨리 찾을 수 있습니다.

HTTP 요청과 응답

메서드와 상태 코드, 헤더와 본문이 각각 무슨 역할을 하는지

물건을 보낼 때 상자 겉면에 받는 사람도, 보낸 사람도, 무엇이 들었는지도 적지 않는다면 택배 회사는 그 상자를 어디로 보내야 할지 알 수 없습니다. HTTP(HyperText Transfer Protocol)는 브라우저와 서버가 이런 정보를 빠짐없이 주고받도록 정해 둔 편지의 형식입니다. 이 형식은 주문서와 영수증이 한 쌍으로 오가는 거래와 같습니다.

요청(request)에는 어떤 방식으로 처리할지 알리는 메서드(method), 찾는 대상의 주소, 그리고 짐에 해당하는 본문(body)이 담깁니다. 응답(response)에는 처리 결과를 세 자리 숫자로 알리는 상태 코드(status code)와, 함께 실어 보내는 헤더와 본문이 들어갑니다. 예를 들어 GET은 보여 달라는 뜻이고 POST는 이 내용을 받아 처리해 달라는 뜻이며, 200은 잘 처리됨, 404는 찾는 것이 없음, 500은 서버 쪽 문제를 가리킵니다. 결국 HTTP는 메서드와 상태 코드라는 약속된 표기를 통해, 요청과 응답이 서로 짝을 이루며 오해 없이 전달되게 하는 통신 규약입니다.

URL의 구조

주소가 서버에서 어떤 경로와 파라미터로 해석되는지

같은 건물 안에서 3층 왼쪽 끝 방이라는 말만 듣고 찾아가면, 복도가 여러 갈래로 갈라지는 순간 길을 잃기 쉽습니다. URL(Uniform Resource Locator)은 인터넷이라는 거대한 건물에서 원하는 자원의 위치를 끝까지 지정해 주는 완전한 주소 체계입니다. URL은 아파트 동과 층과 호수, 그리고 현관 비밀번호까지 한 줄에 적어 둔 안내문과 같습니다.

맨 앞의 http:// 나 https:// 는 어떤 방식으로 드나들지 정하는 규칙이고, 그 뒤의 도메인(domain)은 건물 이름, 이어지는 경로(path)는 몇 층 몇 호인지를 가리킵니다. 물음표 뒤의 쿼리 문자열(query string)은 현관 비밀번호처럼 덧붙이는 조건이며, 이름과 값이 등호로 묶이고 앰퍼샌드로 이어집니다. 예를 들어 /product/detail?item=7&color=red 라면 detail 이라는 방까지 간 뒤 item 이 7, color 가 red 라는 조건을 함께 보내라는 뜻입니다. 정리하면 URL은 프로토콜, 호스트, 경로, 쿼리로 나뉘며, 서버는 이 주소를 읽어 어떤 자원을 어떤 조건으로 돌려줄지 판단합니다.

HTTP 헤더의 종류

Host, Cookie, User-Agent, Content-Type이 전달하는 정보

택배 상자에 받는 사람 이름만 적고 취급 주의 표시를 빼먹으면, 물건은 도착해도 깨지거나 엉뚱한 사람에게 전달될 수 있습니다. HTTP 헤더(header)는 본문에 담기지 않는 이런 부가 정보, 곧 배송 안내문을 요청과 응답 양쪽에 붙이는 자리입니다. 헤더는 상자 겉면에 붙은 라벨 묶음과 같습니다.

Host는 이 요청이 어느 서버를 찾는 것인지 알려 주어, 한 서버가 여러 도메인을 함께 운영할 때 길잡이가 됩니다. Cookie는 브라우저가 들고 있던 신분증을 서버에 제출하는 부분이고, User-Agent는 어떤 브라우저와 기기에서 왔는지를 적어 두는 이름표입니다. Content-Type은 본문이 어떤 형식인지, 예컨대 JSON 인지 HTML 인지 이미지인지를 알려 주어 받는 쪽이 내용을 올바르게 해석하게 합니다. 결국 헤더는 Host, Cookie, User-Agent, Content-Type처럼 본문 밖의 문맥 정보를 전달해, 서버와 브라우저가 같은 내용을 서로 다르게 이해하지 않도록 돕는 장치입니다.

쿠키와 세션

로그인 상태가 브라우저와 서버 사이에서 유지되는 원리

로그인해서 장바구니에 물건을 담았는데 페이지를 넘길 때마다 로그인이 풀리고 담은 물건이 사라진다면 쇼핑을 이어갈 수 없습니다. 쿠키(cookie)와 세션(session)은 이런 곤란을 막기 위해, 서버가 이용자를 기억하도록 만든 장치입니다. 이 원리는 놀이공원 입구에서 손목에 채워 주는 입장 팔찌와 같습니다.

서버는 로그인한 이용자에게 알아보기 어려운 세션 아이디(session ID)를 발급해 자기 쪽 저장소에 그 사람의 상태를 적어 두고, 브라우저에는 그 번호만 쿠키로 건네줍니다. 이후 브라우저는 요청마다 쿠키를 자동으로 첨부하고, 서버는 번호를 보고 아까 그 손님이라고 알아보아 장바구니와 로그인 상태를 이어 갑니다. 그래서 실제 신분 정보는 서버에 남고 브라우저에는 열쇠 조각만 있는 셈이며, 이 열쇠가 남에게 복사되지 않도록 HTTPS와 만료·보안 속성을 함께 쓰는 일이 중요합니다. 정리하면 쿠키는 브라우저에 남는 작은 표식이고 세션은 서버가 그 표식에 연결해 두는 상태 저장소로, 두 가지가 짝을 이뤄 로그인 상태를 유지합니다.

HTTPS와 TLS

통신을 암호화해서 도청과 변조를 막는 방식

카페의 공용 와이파이에서 비밀번호를 입력했는데, 같은 네트워크에 있던 누군가가 그 값을 그대로 들여다보고 있었다면 상상만 해도 끔찍합니다. HTTPS(HyperText Transfer Protocol Secure)는 이렇게 통신이 엿보이거나 중간에 바뀌는 일을 막기 위해, HTTP를 암호화 계층 위에 올린 방식입니다. 그 원리는 봉인 스티커가 붙은 등기 우편과 같습니다.

TLS(Transport Layer Security)는 편지를 봉투에 넣기 전에 열쇠로 잠그고, 받는 쪽만 풀 수 있는 열쇠를 안전하게 나눠 가지도록 절차를 밟습니다. 잠그기 전에 서버는 인증서(certificate)를 내밀어 자기가 그 사이트가 맞다는 사실을 제삼의 인증 기관을 통해 증명하고, 브라우저는 그 증명을 확인한 뒤에야 대화를 시작합니다. 이렇게 하면 내용은 암호문이 되어 도청해도 읽을 수 없고, 중간에서 한 글자라도 바꾸면 무결성 검사에서 어긋나 변조가 드러납니다. 결국 HTTPS는 TLS라는 암호화와 인증의 계층을 통해 기밀성과 무결성, 그리고 상대가 진짜인지 확인하는 신뢰를 함께 확보하는 통신 방식입니다.

리버스 프록시(Reverse Proxy)

서버 앞에서 요청을 대신 받아 넘겨주는 구조

웹 서버를 인터넷에 그대로 노출하면 서버의 실제 주소와 내부 구조가 방문자에게 모두 드러나고, 여러 서비스가 하나의 주소를 함께 쓰고 싶을 때도 곤란한 일이 생깁니다. 이때 서버 앞에 요청을 대신 받아 넘겨주는 중간 단계를 세우는데, 그것이 리버스 프록시(Reverse Proxy)입니다. 아파트 정문의 경비실을 떠올리면 이해하기 쉽습니다. 방문객은 각 세대의 현관문을 직접 찾아가지 않고 경비실에서 용건을 말하며, 경비실은 어느 동 어느 호로 안내할지 스스로 판단해 연결해 줍니다.

여기서 방문객은 웹 브라우저이고, 경비실이 리버스 프록시, 안내받는 세대들이 뒤쪽의 실제 서버입니다. 경비실은 방문객의 요청을 대신 접수해 알맞은 서버로 전달하고, 서버가 돌려준 응답을 다시 방문객에게 건네며, 세대의 정확한 위치는 밖에 알려주지 않습니다. 정리하면 리버스 프록시는 클라이언트와 서버 사이에서 요청을 대신 받아 내부 서버로 중계하고 응답을 되돌려 주는 앞단의 대리 서버이며, 덕분에 실제 서버의 주소를 감추고 여러 서비스를 하나의 주소 뒤로 묶을 수 있습니다.

로드 밸런서(Load Balancer)

여러 서버로 트래픽을 나눠 보내는 방식

사용자가 몰리는 순간 서버 한 대가 모든 요청을 떠안으면 응답이 느려지다가 결국 멈춰 버리고, 그 서버가 죽으면 서비스 전체가 함께 멈춥니다. 그래서 같은 일을 하는 서버를 여러 대 두고 요청을 나눠 보내는 장치를 앞에 세우는데, 이것이 로드 밸런서(Load Balancer)입니다. 마트 계산대를 생각해 보면 구조가 그대로 보입니다. 손님들이 한 계산대에만 줄을 서면 금세 엉키지만, 안내 직원이 줄이 짧은 계산대로 손님을 돌려 보내면 전체가 매끄럽게 흘러갑니다.

여기서 손님은 사용자의 요청이고, 안내 직원이 로드 밸런서, 각 계산대가 뒤쪽 서버입니다. 안내 직원은 지금 어느 계산대가 한가한지, 혹은 순서대로 한 바퀴씩 돌리는 방식으로 손님을 배분하며, 한 계산대가 고장 나면 그곳을 빼고 나머지로만 안내합니다. 즉 로드 밸런서는 들어오는 요청을 여러 서버에 분산해 한 곳에 부하가 몰리지 않게 하고, 일부 서버가 멈춰도 서비스가 계속 돌아가게 만드는 분배 장치입니다.

CDN

콘텐츠를 사용자 가까운 곳에서 전달하는 캐시망

서버가 먼 나라에 하나뿐이면 그곳에서 멀리 떨어진 사용자는 사진 한 장을 받는 데도 오래 기다려야 하고, 같은 파일을 수만 명이 동시에 받으면 원본 서버가 버티지 못합니다. 이 문제를 콘텐츠를 사용자 가까운 곳에 미리 복제해 두는 방식으로 푸는데, 그것이 CDN(Content Delivery Network)입니다. 동네 편의점에 물건이 채워지는 방식을 떠올리면 됩니다. 손님은 본사 대형 창고까지 가지 않고 집 앞 편의점에서 물건을 사며, 편의점은 인기 있는 물건을 미리 조금씩 받아 두었다가 바로 건네줍니다.

여기서 손님이 사용자, 편의점이 사용자와 가까운 위치에 놓인 캐시 서버, 본사 창고가 원본 서버입니다. 사용자가 파일을 요청하면 가장 가까운 캐시 서버가 먼저 응답하고, 그곳에 파일이 없을 때만 원본 서버에서 받아 오며, 한 번 받아 둔 파일은 다음 손님에게 그대로 재사용됩니다. 정리하면 CDN은 전 세계 여러 지점에 캐시 서버를 두고 사용자와 가장 가까운 곳에서 콘텐츠를 전달하는 분산 캐시망으로, 응답 시간을 줄이고 원본 서버의 부담을 크게 덜어 줍니다.

DNS와 도메인

도메인 이름이 서버 주소로 바뀌는 과정

사람은 숫자로 된 서버 주소를 외우기 어려워서, 그런 주소만 있다면 사이트를 열 때마다 어디에 적어 두었는지 찾아 헤매야 합니다. 그래서 기억하기 쉬운 이름을 붙이고 그 이름을 실제 주소로 바꿔 주는 체계를 따로 두었는데, 이것이 도메인(Domain)과 DNS(Domain Name System)입니다. 휴대폰 연락처를 떠올리면 정확히 같은 일이 벌어집니다. 우리는 번호를 외우지 않고 저장된 이름을 눌러 전화를 걸며, 휴대폰이 그 이름에 연결된 번호를 찾아 대신 걸어 줍니다.

여기서 이름이 도메인, 저장된 번호가 IP 주소, 이름을 번호로 바꿔 주는 휴대폰 속 장부가 DNS입니다. 장부는 한 권에 다 들어 있지 않고 여러 기관에 나뉘어 있어서, 앞부분부터 차례로 물어보며 최종 주소를 찾아내고, 한 번 찾은 결과는 잠시 기억해 두어 매번 처음부터 묻지 않습니다. 즉 도메인은 사람이 읽는 주소이고 DNS는 그 이름을 서버의 IP 주소로 변환해 주는 분산된 조회 체계이며, 이 변환이 끝나야 브라우저가 실제 서버에 접속할 수 있습니다.

OWASP Top 10

여기서 체크리스트가 OWASP Top 10, 점검 항목 하나하나가 취약점 범주, 점검 대상 건물이 우리가 만든 웹 애플리케이션입니다. 목록은 여러 보안 전문가의 경험과 실제 사고 통계를 모아 등급을 매기고 몇 년에 한 번 갱신되며, 항목마다 왜 위험한지와 어떻게 줄일지가 함께 실립니다. 요약하면 OWASP Top 10은 웹에서 가장 흔하고 영향이 큰 취약점 범주를 모아 순위로 정리한 공개 목록으로, 보안 점검의 우선순위를 잡는 공통 출발점이 됩니다.

SQL 인젝션(SQL Injection)

입력값이 데이터베이스 쿼리에 섞여 들어가는 공격

웹 페이지의 입력 칸에 들어온 값을 검사하지 않고 그대로 데이터베이스 질의문에 이어 붙이면, 사용자가 보낸 글자가 명령의 일부로 해석되어 원래 의도하지 않은 데이터까지 읽히거나 지워질 수 있습니다. 이렇게 입력값이 질의문에 섞여 들어가 명령을 조작하는 공격이 SQL 인젝션(SQL Injection)입니다. 은행 창구에서 서류를 접수하는 상황을 생각해 보면 위험이 분명해집니다. 창구 직원이 손님이 적어 낸 내용을 확인하지 않고 그대로 업무 지시서에 옮겨 적는데, 손님이 빈칸에 자기 요청 대신 다른 지시문을 한 줄 끼워 넣는다면 직원은 그것까지 정식 지시로 처리하게 됩니다.

여기서 손님이 사용자의 입력값, 업무 지시서가 데이터베이스 질의문, 확인 없이 그대로 옮겨 적는 직원이 입력값을 문자열로 이어 붙이는 프로그램입니다. 입력값에 따옴표나 명령어 조각을 넣으면 질의문의 구조 자체가 바뀌어 조건이 항상 참이 되거나 다른 명령이 덧붙여질 수 있습니다. 정리하면 SQL 인젝션은 사용자 입력이 데이터베이스 질의문의 일부로 해석되면서 공격자가 질의를 마음대로 바꾸는 취약점이며, 입력값을 명령이 아닌 값으로만 다루도록 분리해야 막을 수 있습니다.

크로스 사이트 스크립팅(XSS)

악성 스크립트가 다른 사용자의 브라우저에서 실행되는 공격

게시판에 댓글을 남길 수 있는 사이트에서 공격자가 댓글 칸에 다른 사용자의 화면에서 실행될 명령을 몰래 심어 두면, 그 글을 여는 사람의 브라우저가 그 명령을 대신 실행해 버립니다. 피해자는 아무 잘못도 하지 않았는데 로그인 상태 그대로 개인정보가 빠져나가거나 계정이 넘어갈 수 있어서, 서버가 아니라 사용자의 브라우저에서 벌어지는 이 문제를 막으려고 크로스 사이트 스크립팅(XSS, Cross-Site Scripting)이라는 방어 개념이 생겼습니다.

아파트 공용 게시판에 누구나 쪽지를 붙일 수 있는데, 어떤 쪽지에 "이 글을 읽는 사람은 관리실에 자기 집 열쇠를 갖다 달라"는 지시가 적혀 있다고 해 봅니다. 주민들은 게시판을 믿고 쪽지를 읽으니 그 지시를 자기 일처럼 따라 하고, 정작 지시를 붙인 사람은 멀리서 결과만 받아 챙깁니다.

관리인은 쪽지를 붙이기 전에 남의 열쇠를 넘기라는 문구가 섞여 있는지 확인해 걸러 내야 하고, 이미 붙은 쪽지는 주민이 지시가 아니라 글자 그대로만 읽도록 처리해 두어야 합니다. 이 확인과 처리가 곧 입력값 검증과 출력 인코딩이며, 브라우저가 원래 하지 말아야 할 스크립트를 실행하지 않도록 제한하는 정책이 마지막 안전장치가 됩니다.

정리하면 XSS는 사용자가 넣은 값이 다른 사용자의 화면에 그대로 실려 그 사람의 브라우저에서 스크립트로 실행되는 취약점이고, 입력 검증과 출력 인코딩, 그리고 스크립트 실행을 제한하는 정책으로 막습니다.

명령어 인젝션(Command Injection)

입력값이 운영체제 명령으로 실행되는 공격

사진을 올리면 서버가 자동으로 크기를 줄여 주는 기능이 있다고 할 때, 파일 이름 칸에 이름 대신 운영체제가 알아듣는 명령을 끼워 넣으면 서버가 그 명령까지 함께 실행해 버립니다. 그래서 서버가 외부 입력을 운영체제 명령으로 조립해 실행하는 구조 자체를 위험하게 보고, 이를 명령어 인젝션(Command Injection)이라 부르며 입력과 명령을 분리하는 방식으로 막습니다.

식당에서 손님이 주문서에 "김치찌개" 대신 "김치찌개, 그리고 창고 문 열어라"라고 적어 내면, 주방 직원이 주문서를 문장 그대로 읽어 창고까지 열어 주는 상황과 같습니다. 주방은 원래 요리만 만들면 되는데 주문서에 적힌 문장을 명령으로 받아들였기 때문에 손님이 주방 전체를 부리게 된 것입니다.

따라서 접수 창구에서 메뉴판에 있는 이름인지 먼저 확인하고, 손님이 적은 문장을 명령으로 조립하지 않으며, 꼭 필요한 경우에도 메뉴 이름만 골라 쓰도록 해야 합니다. 서버도 마찬가지로 외부 값을 셸(shell)에 그대로 넘기지 않고 정해진 기능만 호출하도록 바꾸는 것이 근본 대책입니다.

정리하면 명령어 인젝션은 사용자 입력이 운영체제 명령의 일부로 해석되어 서버에서 임의의 명령이 실행되는 취약점입니다.

2부. 웹 공격의 이해015

경로 트래버설(Path Traversal)

상위 경로 표기로 서버의 다른 파일에 접근하는 공격

파일을 내려받는 주소에 파일 이름이 그대로 들어가는 사이트에서, 누군가 이름 자리에 상위 폴더로 올라가는 표기를 넣으면 원래 공개하려던 폴더를 벗어나 서버의 설정 파일이나 계정 정보까지 내려받을 수 있습니다. 이렇게 되면 웹에서 보여 주려던 자료의 범위가 무의미해지므로, 경로를 조립해 파일을 찾는 방식을 경로 트래버설(Path Traversal) 취약점이라 부르고 요청 경로를 제한하는 방식으로 막습니다.

도서관 창구에서 직원에게 "3번 서가 맨 위 칸"이라고 말하면 그 책을 갖다 주는데, 어떤 사람이 "3번 서가에서 위로 두 층 올라가 관리실 금고"라고 말해도 직원이 그대로 따라 간다면 문제가 됩니다. 창구 직원은 자기 담당 구역 밖으로는 가지 말아야 하고, 요청받은 위치가 정말 대출 가능한 서가 안인지 먼저 확인해야 합니다.

사이트도 같은 이치로 사용자가 준 이름을 경로에 그대로 붙이지 않고, 허용한 폴더 안의 정해진 파일 목록에서만 고르게 해야 합니다. 이름 안에 상위 폴더 표기가 섞여 있는지 걸러 내는 검사도 함께 필요합니다.

정리하면 경로 트래버설은 상위 경로 표기로 웹이 공개하는 범위 밖의 파일에 접근하는 공격이고, 경로를 정규화한 뒤 허용 범위 안인지 검사하는 것이 핵심입니다.

파일 업로드 취약점

검사 없는 업로드가 실행 가능한 파일로 이어지는 경로

사진 첨부만 받는 게시판에 누군가 사진 대신 서버에서 실행되는 프로그램 파일을 올리고 그 주소를 직접 열면, 서버가 그 파일을 프로그램으로 실행해 버릴 수 있습니다. 업로드 기능은 편리함과 위험이 종이 한 장 차이라서, 파일 업로드 취약점은 검사 없는 업로드가 실행 가능한 파일로 이어지는 경로로 설명됩니다.

아파트 경비실이 택배를 받아 두는데, 상자에 무엇이 들었는지 확인하지 않고 보관실에 그대로 넣는다고 해 봅니다. 어떤 상자 안에 보관실 문을 여는 도구가 들어 있었다면, 경비실은 택배를 맡아 준 것뿐인데 집 열쇠를 내준 셈이 됩니다.

그래서 경비실은 받는 상자의 종류와 크기를 확인하고, 보관실 안에서는 절대 열리지 않는 곳에 두며, 정해진 물건만 받도록 목록을 정해 두어야 합니다. 서버도 확장자와 실제 내용을 함께 확인하고, 저장 위치를 실행되지 않는 곳으로 분리하며, 올라온 파일에 새 이름을 붙이는 방식으로 막습니다.

정리하면 파일 업로드 취약점은 검사 없이 저장된 파일이 서버에서 실행되는 일로 이어지는 문제이고, 저장 위치 분리와 내용 검사가 핵심 방어입니다.

2부. 웹 공격의 이해017

서버 측 요청 위조(SSRF)

서버가 대신 내부 주소를 요청하게 만드는 공격

쇼핑몰이 상품 이미지 주소를 입력받아 서버가 대신 가져와 보여 주는 기능이 있을 때, 그 주소 자리에 외부에 공개되지 않은 내부 서버 주소를 넣으면 서버가 자기 내부망을 스스로 찔러 보게 됩니다. 방화벽이 밖에서 들어오는 요청은 막아도 서버 자신이 안쪽으로 보내는 요청은 통과시키기 때문에, 서버 측 요청 위조(SSRF, Server-Side Request Forgery)는 위험한 우회로가 됩니다.

회사에서 대표 비서에게 "이 주소로 가서 서류를 받아 오라"고 부탁하면, 비서는 사원증이 있어서 일반 직원은 못 들어가는 전산실에도 들어가 서류를 가져옵니다. 부탁한 사람이 밖에서 온 장난 메일이었다면, 회사는 비서의 권한으로 내부 자료를 스스로 꺼내 준 셈이 됩니다.

그래서 비서에게 아무 주소나 주지 말고 회사가 정한 목록의 주소만 가도록 하고, 내부 주소로 향하는 요청은 애초에 보내지 못하게 해야 합니다. 서버도 요청 가능한 주소를 허용 목록으로 제한하고, 내부 대역으로 가는 연결을 차단해야 합니다.

정리하면 SSRF는 서버가 공격자가 지정한 내부 주소로 대신 요청을 보내 내부 자원에 접근하게 하는 취약점입니다.

2부. 웹 공격의 이해018

취약점 스캐너와 자동 공격

공격 도구가 사이트를 훑고 시도하는 방식

사이트 하나를 손으로 훑으면 취약한 곳을 찾는 데 며칠이 걸리지만, 도구를 쓰면 몇 시간 만에 수천 개 주소를 훑고 알려진 약점을 차례로 시도할 수 있습니다. 이렇게 자동으로 약점을 찾아내는 취약점 스캐너(vulnerability scanner)와 그 뒤를 잇는 자동 공격은, 사람의 실수와 시간을 기다리지 않는다는 점에서 방어하는 쪽에 특히 부담이 됩니다.

아파트 단지에 누군가 들어와 세대마다 현관문 손잡이를 하나씩 돌려 보고, 잠기지 않은 집의 명패만 적어 가는 상황과 같습니다. 한 집을 오래 공략하는 것이 아니라 문이 많다는 점을 이용해 빠르게 훑고, 열려 있는 곳을 찾으면 그때만 안으로 들어갑니다.

경비실이 세대 하나하나를 지키는 대신, 같은 사람이 여러 집 문을 연달아 건드리는 패턴을 알아채고 차단하는 방식이 필요합니다. 여기에 더해 문이 잠겨 있는지 스스로 점검해 두면, 훑는 사람이 헛걸음하는 시간이 길어집니다.

정리하면 취약점 스캐너는 알려진 약점 목록을 대량의 요청으로 시험하는 도구이고, 자동 공격은 그 결과를 바탕으로 반복해서 시도하는 흐름이며, 반복 패턴을 알아채는 탐지와 스스로 점검하는 절차가 방어의 중심이 됩니다.

2부. 웹 공격의 이해019

제로데이(Zero-day)

아직 알려지지 않은 취약점이 WAF 운영에서 갖는 의미

회사에서 쓰는 쇼핑몰 프로그램에 아무도 모르는 구멍이 하나 있고, 공격자가 그 구멍을 먼저 찾아내 마음대로 드나든다고 해 보겠습니다. 프로그램을 만든 회사조차 그 구멍의 존재를 아직 알지 못하니 고칠 방법도 없는데, 이런 아직 알려지지 않은 취약점을 제로데이(Zero-day)라고 부르며 WAF 운영에서 가장 다루기 어려운 상대입니다.

아파트 관리사무소가 모든 세대의 잠금장치를 점검한다고 생각해 보겠습니다. 관리사무소는 알려진 잠금장치 결함 목록을 들고 집집마다 확인하고, 목록에 있는 결함은 즉시 수리해 줍니다. 그런데 아직 아무도 보고하지 않은 새로운 방식으로 문이 열린다면, 목록에는 그 항목이 없으니 점검은 그냥 지나쳐 버리고 수리도 이뤄지지 않습니다.

제로데이 대응은 이 목록에 없는 침입을 잡아내는 일이라, 알려진 서명(signature, 공격 패턴)만 대조하는 방식으로는 잡히지 않고 평소와 다른 행동을 살피는 이상 행위 탐지 쪽으로 무게가 옮겨갑니다.

정리하면 제로데이는 공격 패턴이 공개되기 전의 취약점이라 기존 서명 대조로는 막기 어렵습니다. 그래서 WAF는 알려진 공격을 거르는 동시에 비정상 행동을 관찰하고, 취약점이 공개되면 신속히 가상 패치(virtual patching, 코드를 고치지 않고 WAF 규칙으로 공격을 차단하는 것)를 적용하는 식으로 대비합니다.

2부. 웹 공격의 이해020

웹 셸(Web Shell)

침해 이후 서버에 심어 두는 원격 조종 파일

공격자가 웹 서버의 허점을 한 번 뚫고 들어간 뒤, 아무도 눈치채지 못하게 몇 달씩 드나들며 자료를 빼간다고 해 보겠습니다. 이때 공격자가 서버 안에 심어 두는, 웹 브라우저로 접속해 명령을 내리는 작은 파일이 있는데 이것이 웹 셸(Web Shell)이며 WAF가 막아야 할 침해 이후 단계의 대표적인 흔적입니다.

건물 안에 들어온 사람이 창고 구석에 자기만 아는 작은 문을 하나 만들어 두었다고 생각해 보겠습니다. 그 문은 정문 경비를 거치지 않고도 드나들 수 있어서, 나중에 정문 보안이 강화되어도 그는 계속 건물 안으로 들어올 수 있습니다.

웹 셸도 똑같이 서버가 실행하는 스크립트 파일 하나로 만들어져, 공격자는 평범한 웹 요청 속에 명령을 실어 보내 그 파일을 실행시킵니다. 그래서 정상적인 페이지 요청처럼 보이는 통신 안에 명령이 숨어 있고, 파일 이름이나 경로를 조금씩 바꾸면 탐지도 쉽지 않습니다.

웹 셸은 취약점을 뚫고 들어온 뒤 서버에 남겨 두는 원격 조종용 스크립트 파일로, 침해가 이미 일어났다는 신호입니다. WAF는 업로드되는 파일의 내용과 형태를 검사하고 이런 파일이 실행되는 경로를 차단하는 방식으로 침해 이후의 발판을 걷어내는 역할을 맡습니다.

심층 방어(Defense in Depth)

한 겹이 뚫려도 다음 겹이 막는 사고방식

보안 장비를 하나 잘 갖춰 두면 모든 공격을 막을 수 있을 것 같지만, 그 장비의 허점 하나가 뚫리는 순간 회사 전체가 그대로 노출됩니다. 그래서 한 겹이 뚫려도 다음 겹이 막아 주도록 여러 층의 방어를 겹쳐 놓는 사고방식을 심층 방어(Defense in Depth)라고 부릅니다.

아파트 단지의 출입 구조를 떠올려 보겠습니다. 단지 정문에서 차량을 확인하고, 건물 출입문에서 한 번 더 카드를 찍고, 세대 현관문에서 또 한 번 잠금을 풀어야 집 안에 들어갈 수 있습니다. 정문 경비가 잠깐 자리를 비워도 건물 문과 현관문이 남아 있어서 침입자는 결국 마지막 문 앞에서 멈추게 됩니다.

심층 방어도 같은 방식으로, 네트워크 방화벽이 포트를 좁히고 WAF가 웹 요청을 검사하고 애플리케이션 자체가 입력을 다시 검증하는 식으로 서로 다른 층이 서로 다른 실수를 메워 줍니다.

정리하면 심층 방어는 완벽한 한 겹을 믿는 대신 서로 다른 여러 겹을 겹쳐 두는 설계 원칙입니다. WAF는 그 겹 중 애플리케이션 계층을 담당하는 한 층이며, 다른 층이 뚫렸을 때 마지막으로 요청을 걸러 주는 자리에 서 있습니다.

3부. 방어 계층과 WAF의 위치022

WAF란 무엇인가

애플리케이션 계층에서 요청을 들여다보고 거르는 방화벽

회사 홈페이지가 정상적인 방문자처럼 보이는 요청에 데이터베이스 내용을 통째로 넘겨주고 나서야 문제를 알아차린다면, 그때는 이미 늦습니다. 이런 요청을 애플리케이션 계층에서 들여다보고 거르는 방화벽이 WAF(Web Application Firewall, 웹 응용 프로그램 방화벽)입니다.

아파트 정문 경비원이 방문객의 이름만 확인하는 것이 아니라 어떤 목적으로 왔는지, 가방에 무엇을 들었는지까지 살피는 모습을 떠올려 보겠습니다. 경비원은 정해진 금지 목록과 평소와 다른 점을 함께 보며, 수상한 방문객은 안으로 들이지 않고 기록을 남깁니다.

WAF도 사용자가 보낸 HTTP 요청의 주소, 파라미터(parameter, 요청에 함께 실려 오는 값), 헤더(header, 요청에 붙는 부가 정보), 본문을 하나씩 열어 보고 공격 패턴과 대조합니다. 여기서 걸리면 요청을 그대로 막거나 기록만 남기고 통과시키는 모드로 동작하며, 이 판단을 규칙(rule)의 집합인 정책(policy)으로 관리합니다.

WAF는 웹 요청의 내용을 애플리케이션 계층에서 검사해 악의적인 요청을 걸러내는 방화벽입니다. 서버와 데이터베이스 앞에 서서 정상적인 사용자는 통과시키고 공격 의도가 담긴 요청은 막는 관문 역할을 합니다.

3부. 방어 계층과 WAF의 위치023

네트워크 방화벽과의 차이

포트와 IP만 보는 방화벽이 놓치는 것을 WAF가 보는 이유

네트워크 방화벽은 80번, 443번처럼 정해진 포트만 열어 두면 안전하다고 판단하지만, 정작 공격은 그 열어 둔 포트 안으로 정상 트래픽처럼 들어옵니다. 포트와 IP 주소만 보는 방화벽이 놓치는 이 영역을 들여다보는 것이 WAF이며, 두 장비는 보는 층이 다릅니다.

아파트 정문에서 사람인지 차량인지만 확인하고 들여보내는 경비와, 들어온 사람의 가방까지 열어 보는 경비를 비교해 보겠습니다. 첫 번째 경비는 출입 자체를 통제하므로 허가되지 않은 사람은 막지만, 허가받은 사람이 위험한 물건을 들고 오는 것은 알아채지 못합니다. 네트워크 방화벽이 첫 번째 경비에 해당하고, WAF는 두 번째 경비처럼 허용된 통로로 들어온 요청의 내용까지 확인합니다.

그래서 네트워크 방화벽은 IP와 포트, 프로토콜을 기준으로 연결을 허용하거나 차단하고, WAF는 그 연결 안에서 오가는 HTTP 요청의 주소와 값, 본문을 기준으로 판단합니다.

정리하면 네트워크 방화벽은 어디로 연결할 수 있는지를, WAF는 연결된 요청이 무엇을 하려는지를 봅니다. 둘은 대체 관계가 아니라 서로 다른 층을 맡는 보완 관계이므로 함께 두어야 빈틈이 줄어듭니다.

WAF가 막을 수 있는 것과 없는 것

한계를 알아야 정책 설계가 흔들리지 않는다

WAF를 도입하면 모든 웹 공격이 사라질 것이라 기대하기 쉽지만, 실제로는 WAF가 볼 수 없는 자리에서 벌어지는 문제가 적지 않습니다. 그래서 정책을 설계하기 전에 WAF가 무엇을 막고 무엇을 막지 못하는지 분명히 아는 것이 중요합니다.

아파트 정문에 설치된 검색대를 떠올려 보겠습니다. 검색대는 가방에 든 물건을 잘 찾아내지만, 주민이 직접 들여온 물건이나 이미 집 안에 있던 물건, 그리고 검색대를 지나지 않는 지하 주차장 쪽으로 들어온 물건은 잡지 못합니다.

WAF도 마찬가지로 SQL 인젝션(SQL Injection)이나 크로스 사이트 스크립팅(Cross-Site Scripting)처럼 요청에 실려 오는 공격은 잘 막지만, 서버 자체의 설정 오류나 이미 심어진 웹 셸, 애플리케이션 로직의 설계 결함은 요청만 봐서는 알아채기 어렵습니다. 또한 암호화된 트래픽을 복호화하지 않고 통과시키면 내용을 볼 수 없고, 공격이 극히 드물게 섞여 들어오는 경우에는 탐지 규칙이 놓칠 수도 있습니다.

정리하면 WAF는 애플리케이션 계층의 요청을 검사해 알려진 공격 유형을 상당 부분 걸러내지만, 설정과 코드의 결함, 내부에서 시작된 침해까지 모두 해결하지는 못합니다. 그래서 WAF 정책은 막을 수 있는 것을 확실히 막는 데 집중하고, 막지 못하는 영역은 코드 점검과 취약점 관리로 따로 채우는 설계가 필요합니다.

취약점과 WAF의 관계

코드를 고치기 전까지 시간을 벌어주는 임시 방어

쇼핑몰을 운영하는 회사에서 게시판 입력창 하나가 사용자의 입력을 제대로 걸러내지 못하고 있다고 해 봅시다. 공격자는 그 허점을 이용해 데이터베이스의 회원 정보를 통째로 빼내려 하고, 정작 그 코드를 고치려면 개발 일정을 잡고 테스트하고 배포하는 데 몇 주가 걸립니다.

그 몇 주 동안 서버를 그대로 노출할 수는 없으니, 우리는 요청이 애플리케이션에 닿기 전에 한 번 걸러 주는 장치를 세우기로 했습니다. 이것이 웹 애플리케이션 방화벽, 즉 WAF (Web Application Firewall) 입니다. 아파트 현관의 도어락이 고장 났는데 새 부품이 오려면 시간이 걸리는 상황을 떠올려 보십시오. 도어락 자체를 고치는 일은 전문가의 손을 기다려야 하지만, 그동안 경비원을 현관 앞에 세워 두면 수상한 사람이 문을 열고 들어오는 것은 막을 수 있습니다. 경비원은 출입 명단과 수상한 행동 목록을 들고 서서, 평소 오가는 주민은 그냥 통과시키고 문을 억지로 뜯으려는 사람만 붙잡습니다.

WAF도 똑같이 요청마다 정해 둔 공격 패턴 목록과 대조하고, 정상적인 요청은 그대로 서버로 흘려보내며 목록에 걸리는 요청만 잘라 냅니다. 그러므로 WAF는 취약점이라는 구멍 자체를 메우는 장치가 아니라, 구멍이 메워질 때까지 공격이 그 구멍에 도달하지 못하게 막는 임시 방어입니다. 업계에서는 이를 가상 패치 (virtual patching) 라고 부르며, 근본적인 해결은 언제나 코드를 고치는 일이라는 점을 함께 기억해야 합니다.

WAF와 IPS의 차이

탐지 위치와 차단 방식에서 갈리는 공통점과 차이

서버가 분명히 이상한 요청을 받고 있는데도 네트워크에 놓인 보안 장비는 아무 반응이 없어서 답답했던 적이 있을 것입니다. 그 장비는 패킷이 어디서 어디로 가는지만 보고, 그 안에 담긴 웹 요청의 내용까지는 들여다보지 않기 때문입니다. 이 지점에서 침입 방지 시스템, 즉 IPS (Intrusion Prevention System) 와 WAF가 서로 다른 역할로 갈라집니다. 택배를 검사하는 두 사람을 상상해 보십시오. 한 사람은 택배 차량이 허가된 곳에서 왔는지, 상자 겉면에 위험 표시가 있는지, 무게가 지나치게 무겁지는 않은지를 봅니다. 다른 한 사람은 상자를 열어 안쪽에 든 물건의 목록까지 확인합니다.

앞사람이 IPS라면 뒷사람이 WAF이며, IPS는 IP 주소와 포트와 프로토콜 수준에서 이상한 흐름을 막고, WAF는 URL과 파라미터와 쿠키와 본문처럼 HTTP 요청의 속 내용을 읽고 판단합니다. 두 장비 모두 차단을 할 수 있지만 IPS는 네트워크 경로에 직접 끼어들어 흐름 자체를 끊고, WAF는 보통 서버 앞에 프록시 (proxy) 로 서서 요청을 대신 받아 넘깁니다. 정리하면 IPS는 네트워크 계층에서 넓게 훑는 방어이고 WAF는 웹 애플리케이션 계층에서 깊게 파고드는 방어이며, 둘은 대체 관계가 아니라 서로 다른 층을 맡는 보완 관계입니다.

WAF와 RASP의 차이

경계에서 막는 방식과 애플리케이션 안에서 막는 방식

건물 입구에서 아무리 꼼꼼히 검색해도, 이미 들어온 사람이 안에서 서류를 조작하거나 금고를 여는 행동까지는 막기 어렵습니다. 웹 서비스도 마찬가지여서, 정상처럼 보이는 요청이 애플리케이션 안에서 위험한 동작으로 이어지는 경우에는 경계에 세운 WAF가 알아채기 힘듭니다. 그래서 등장한 것이 애플리케이션 실행 중에 스스로를 지키는 RASP (Runtime Application Self-Protection) 입니다. 아파트로 비유하면 WAF는 정문 경비실이고 RASP는 각 세대 안에 설치된 스마트 잠금장치입니다. 경비실은 사람이 건물에 들어오기 전에 소지품을 확인하고 명단에 없는 사람을 돌려보내지만, 세대 안에서 벌어지는 일은 알지 못합니다. 반면 스마트 잠금장치는 그 집의 문이 실제로 열리려는 순간에 작동하고, 누가 어떤 방식으로 열쇠를 돌리는지까지 감지합니다.

RASP는 애플리케이션 코드와 같은 공간에서 실행되며 데이터베이스 질의나 파일 접근 같은 위험한 함수가 호출되는 순간을 지켜보다가, 입력값이 공격 의도로 흘러 들어오면 그 실행을 중단시킵니다. 즉 WAF는 요청이 애플리케이션에 도착하기 전 경계에서 HTTP 내용을 검사하는 방식이고, RASP는 코드가 실제로 실행되는 안쪽에서 동작을 감시하는 방식이며, 두 방식은 서로의 사각지대를 메우는 관계입니다.

WAF와 API 게이트웨이

인증과 사용량 제한과 검사가 겹치는 지점

서비스가 커지면서 모바일 앱과 외부 파트너가 쓰는 API (Application Programming Interface) 가 수십 개로 늘어나자, 각 API마다 인증을 따로 붙이고 사용량을 따로 세는 일이 감당이 안 되기 시작했습니다. 그 결과 트래픽을 한 곳으로 모아 공통 처리를 맡기는 API 게이트웨이 (API gateway) 가 등장했고, 보안 담당자는 그 앞에서 WAF를 어디에 두어야 하는지 고민하게 됩니다. 건물 로비의 안내데스크를 떠올려 보십시오. 방문객은 먼저 안내데스크에서 출입증을 확인받고, 하루에 몇 번까지 방문할 수 있는지 정해진 횟수를 넘기면 더 이상 들어가지 못하며, 가방에 위험한 물건이 없는지도 이 자리에서 확인합니다. 출입증 확인이 인증이고, 방문 횟수 제한이 사용량 제한 (rate limit) 이며, 가방 검사가 바로 WAF가 맡는 공격 패턴 검사입니다.

API 게이트웨이는 어느 서버로 요청을 보낼지 길을 안내하고 호출 기록을 남기는 일까지 하므로, 검사 기능과 겹치는 부분이 생깁니다. 그래서 어떤 구성에서는 게이트웨이 안에 WAF 기능을 함께 켜고, 어떤 구성에서는 게이트웨이 앞단에 별도 WAF를 세워 검사를 먼저 통과시킵니다. 핵심은 인증과 사용량 제한과 검사가 서로 다른 목적을 가진 기능이라는 점이며, API 게이트웨이가 문지기 역할을 하더라도 웹 공격 패턴을 깊이 보는 일은 WAF에 맡기는 경우가 많습니다.

PCI DSS가 요구하는 웹 방화벽 조항의 실제 의미

신용카드 정보를 다루는 회사라면 한 번쯤 외부 감사에서 웹 방화벽을 두고 있느냐는 질문을 받게 됩니다. 카드 정보를 안전하게 다루기 위한 국제 표준인 PCI DSS (Payment Card Industry Data Security Standard) 가 공개 웹 애플리케이션 보호를 명시적으로 요구하기 때문입니다. 문제는 이 조항이 단순히 장비를 사 두면 된다는 뜻이 아니라는 점입니다. 건물의 소방 설비를 떠올려 보십시오. 소화기와 스프링클러를 설치하는 것만으로 끝나지 않고, 정기적으로 점검하고 기록을 남기고 고장 난 부품을 바꿔야 법적 요건을 충족합니다.

PCI DSS 요구사항 6.6도 같은 구조여서, 공개 웹 애플리케이션에 대한 공격을 지속적으로 탐지하고 차단하라고 요구하며, 그 방법으로 코드 검토를 하거나 웹 방화벽을 설치하는 두 가지 길을 제시합니다. 웹 방화벽을 택했다면 규칙을 최신으로 유지하고, 차단 기록을 보관하고, 점검 이력을 남겨야 감사에서 인정을 받습니다. 따라서 규제 대응은 WAF를 도입하는 것으로 끝나지 않고 운영 증거를 쌓는 일까지 포함하며, 조항이 요구하는 것은 장비의 존재가 아니라 지속적인 탐지와 차단의 증명입니다.

WAF 도입 판단

어떤 상황에서 필요하고 어떤 상황에서 과한 선택인지

직원 몇 명이 쓰는 사내 업무 도구에 웹 방화벽을 붙이면, 정작 지켜야 할 자원은 늘어나는데 관리할 사람은 없어서 오히려 부담이 커집니다. 반대로 회원 정보와 결제를 다루는 공개 서비스인데 아무 방어도 없다면 하루아침에 큰 사고를 겪을 수 있습니다. 그래서 도입 여부는 유행이 아니라 상황을 따져 결정해야 하는 문제입니다. 아파트 단지에 경비원을 둘지 정하는 일과 비슷합니다. 세대 수가 많고 외부인 출입이 잦고 귀중품이 오가면 경비원은 필수이고, 반대로 출입문이 하나뿐인 작은 건물에 상주 경비를 두면 비용만 나갑니다.

WAF가 필요한 경우는 공개 인터넷에 노출된 웹 서비스가 있고, 개인정보나 결제 정보를 다루며, 카드 업계 규제의 적용을 받거나, 개발팀이 취약점 대응에 쓸 시간이 늘 부족한 상황입니다. 반대로 인터넷에서 접근할 수 없는 내부 시스템이거나 트래픽이 거의 없는 정적 사이트이고 이미 사용 중인 클라우드 서비스에 기본 방어가 포함되어 있다면 별도 WAF는 과한 선택일 수 있습니다. 결론적으로 도입을 정하기 전에 오탐을 처리할 인력과 로그를 볼 사람이 있는지 먼저 확인해야 하며, 규칙을 조정하고 결과를 지켜보는 운영이 뒤따르지 않는 WAF는 비용만 쓰고 효과는 거의 없는 장비가 됩니다.

4부. WAF의 배포 방식031

리버스 프록시형 WAF

서버 앞에 세워 모든 요청을 통과시키는 배포

웹 서버를 인터넷에 그대로 노출하면 공격자가 서버의 주소와 구조를 그대로 보면서 마음껏 두드릴 수 있고, 서버는 정상 요청과 공격 요청을 구분할 방법이 없어 일일이 다 받아 내야 합니다. 그래서 서버 바로 앞에 모든 요청을 대신 받아 넘겨 주는 중간 장비를 세우고, 그 장비가 요청을 검사한 뒤에만 서버로 들여보내는 방식이 나왔는데 이것이 리버스 프록시형 WAF입니다. 이 구조는 회사 건물 정문의 경비실과 같습니다. 방문객은 회사 사무실로 곧장 들어가지 못하고 반드시 경비실 앞을 지나야 하는데, 경비실은 방문 목적과 소지품을 확인하고 출입 명단에 없는 사람이나 수상한 사람은 안으로 보내지 않고 돌려보냅니다. 여기서 경비실이 WAF, 방문객이 사용자의 요청, 사무실이 웹 서버에 해당하며, 경비실이 직접 안내를 받아 처리하는 것처럼 프록시가 서버를 대신해 응답을 주고받기도 합니다.

덕분에 방문객은 사무실이 몇 층 어느 자리에 있는지 알 수 없고, 서버의 실제 주소도 외부에 드러나지 않습니다. 정리하면 리버스 프록시(reverse proxy)형 WAF는 서버 앞단에 배치되어 들어오는 모든 HTTP 요청이 반드시 거쳐 가게 만들고, 그 지점에서 규칙에 따라 요청을 허용하거나 차단하며 서버의 위치까지 가려 주는 배포 방식입니다.

4부. WAF의 배포 방식032

투명 프록시형 WAF

네트워크 경로에 끼어들어 존재를 드러내지 않는 배포

서버 앞에 장비를 세우려면 네트워크 구성도와 서버 주소를 모두 바꿔야 하고, 서비스가 여러 대로 늘어날수록 이 작업은 사람 손이 많이 가는 골칫거리가 됩니다. 그래서 주소를 바꾸지 않고도 네트워크 경로 중간에 몰래 끼어들어 검사하는 방식이 생겼는데, 이것이 투명 프록시형 WAF입니다. 이 방식은 건물 복도에 설치된 자동문과 비슷합니다. 지나가는 사람은 문이 있다는 걸 의식하지 않고 그냥 걸어가지만, 문은 지나가는 모든 사람을 한 명씩 살피고 위험한 물건을 든 사람은 복도로 들여보내지 않습니다. 사람들이 가던 길을 바꾸지 않아도 된다는 점이 핵심이며, 여기서 복도가 네트워크 경로, 자동문이 WAF, 통행인이 요청입니다.

문이 몰래 끼어들어도 목적지 주소는 그대로이므로 서버 설정을 고칠 필요가 없고, 그래서 관리자는 장비가 있다는 사실조차 잊고 지낼 수 있습니다.

다만 경로를 우회하는 길이 있으면 검사를 피할 수 있으므로, 모든 트래픽이 반드시 그 지점을 지나도록 네트워크를 설계하는 것이 중요합니다. 정리하면 투명 프록시(transparent proxy)형 WAF는 트래픽 경로에 직접 개입해 요청을 가로채 검사하되 주소나 설정을 바꾸지 않으므로, 사용자와 서버 모두에게 존재가 드러나지 않는 배포 방식입니다.

브리지형 WAF

물리적인 연결선 사이에 장비를 넣는 배포

WAF를 도입하려는데 서버 설정도 바꾸기 싫고 네트워크 구조도 손대고 싶지 않다면 선택지가 거의 없어 보입니다. 이럴 때 물리적인 연결선 사이에 장비를 하나 끼워 넣는 가장 단순한 방법이 쓰이는데, 이것이 브리지형 WAF입니다. 이는 건물과 건물 사이에 놓인 연결 통로에 검문소를 설치하는 것과 같습니다. 두 건물은 원래 이어진 길로 오가지만, 그 길 한가운데에 검문소가 생기면서 지나가는 사람과 짐은 모두 검문소를 통과해야 합니다. 여기서 두 건물이 서버와 인터넷 구간, 연결 통로가 네트워크 선, 검문소가 WAF에 해당하며, 검문소는 자기 주소를 따로 갖지 않고 지나가는 흐름을 그대로 이어 주면서 내용만 들여다봅니다.

그래서 IP 주소나 라우팅 설정을 크게 바꾸지 않아도 되고, 장비에 문제가 생기면 선을 원래대로 되돌리기만 하면 됩니다. 정리하면 브리지(bridge)형 WAF는 두 네트워크 구간 사이에 장비를 물리적으로 연결해 통과하는 트래픽을 검사하는 방식으로, 구성 변경이 적고 장애 시 우회가 쉬운 대신 그 구간을 지나는 흐름만 볼 수 있다는 한계가 있습니다.

웹 서버 모듈로 설치해 서버 안에서 검사하는 배포

장비를 따로 사서 네트워크에 넣는 일은 비용도 시간도 만만치 않고, 서버가 한 대뿐인 작은 서비스에는 오히려 과합니다. 그래서 웹 서버가 원래 갖고 있는 확장 기능에 검사 모듈을 끼워 넣는 방법이 쓰이는데, 이것이 플러그인형 WAF입니다. 이는 집 현관문에 다는 스마트 잠금장치와 같습니다. 문을 새로 만들거나 집 구조를 바꾸지 않고, 원래 있던 문에 장치만 달면 누가 들어오려는지 확인하고 필요하면 문을 열어 주지 않습니다. 여기서 현관문이 웹 서버, 잠금장치가 WAF 모듈, 집 안이 웹 애플리케이션이며, 잠금장치는 문에 붙어 있으므로 집 안에 들어온 뒤의 일까지는 관여하지 못합니다.

설치가 간단하고 서버 한 대의 비용만 들지만, 서버가 여러 대면 각각에 설치해야 하고 서버 자체에 부담이 더해지며 서버가 뚫리면 검사 기능도 함께 무력해질 수 있습니다. 정리하면 플러그인형 WAF는 웹 서버의 모듈(module) 형태로 설치되어 서버 안에서 요청을 검사하는 방식으로, 도입이 가볍고 저렴한 대신 서버 자원을 나눠 쓰고 보호 범위가 그 서버 안으로 한정됩니다.

4부. WAF의 배포 방식035

클라우드형 WAF

DNS나 프록시를 통해 외부에서 검사하는 배포

공격 트래픽이 갑자기 몰리면 장비 한 대로는 감당하지 못하고, 장비를 늘리려면 예산과 설치 기간이 다시 필요해집니다. 그래서 검사 기능을 내 장비가 아닌 외부 서비스로 맡기고 트래픽을 그곳을 거쳐 오게 하는 방식이 널리 쓰이는데, 이것이 클라우드형 WAF입니다. 이는 택배를 보낼 때 집 앞에 놓는 공동 택배함과 비슷합니다. 택배 기사는 각 집을 직접 찾아가지 않고 한곳의 함에 물건을 넣고, 함은 정해진 규칙에 따라 받을 물건인지 확인한 뒤 집으로 전달합니다. 여기서 택배 기사가 공격자나 사용자, 공동 택배함이 클라우드 WAF, 집이 웹 서버에 해당하며, 집 주소를 외부에 알리지 않아도 되는 점이 큽니다.

실제로는 도메인의 주소를 클라우드 쪽으로 돌리거나 트래픽이 클라우드를 거치도록 설정하며, 검사 용량은 사업자가 알아서 늘려 주고 규칙도 계속 갱신됩니다.

대신 인터넷 연결과 외부 사업자에 의존하게 되고, 요청이 한 번 더 먼 길을 지나므로 지연이 생길 수 있습니다. 정리하면 클라우드형 WAF는 DNS 설정이나 프록시 경유를 통해 트래픽을 외부 사업자의 검사 지점으로 보내는 방식으로, 장비 없이 용량을 늘릴 수 있고 서버 주소를 숨길 수 있지만 외부 서비스 의존이 따른다는 특징이 있습니다.

웹 호스팅을 쓰는 사람은 자기 서버 설정을 마음대로 건드릴 수 없고, 보안 장비를 따로 붙일 권한도 없는 경우가 많습니다. 이런 환경에서는 인프라를 제공하는 사업자가 기본으로 켜 두는 웹 방화벽에 기대게 되는데, 이것이 호스팅형 WAF입니다. 이는 아파트 관리사무소가 단지 출입구에 공동으로 경비를 세워 두는 것과 같습니다. 세입자는 경비를 따로 고용하지 않아도 되고, 관리사무소가 정한 출입 규칙이 모든 세대에 똑같이 적용됩니다. 여기서 관리사무소가 호스팅 사업자, 공동 경비가 WAF, 세대가 각자의 웹 사이트이며, 세입자는 경비의 세부 규칙을 직접 바꿀 수 없습니다.

그래서 추가 비용과 설치 부담이 거의 없고 최소한의 방어가 자동으로 보장되지만, 세밀한 설정이나 우리 사이트만의 예외 처리는 어렵고 사업자가 제공하는 범위를 벗어나기 힘듭니다. 정리하면 호스팅형 WAF는 인프라 사업자가 기본 옵션으로 제공하는 웹 방화벽으로, 손쉽게 최소한의 보호를 얻는 대신 제어권이 사업자에게 있어 세밀한 튜닝에는 한계가 있는 배포 방식입니다.

4부. WAF의 배포 방식037

아웃오브밴드 배포

차단하지 않고 복제된 트래픽만 관찰하는 배포

새 웹 방화벽(WAF, Web Application Firewall)을 켜자마자 정상 사용자의 접속이 느려지거나 갑자기 끊긴다면, 서비스 팀은 차라리 방화벽을 끄고 싶어질 것입니다. 이런 부담 없이 규칙이 제대로 동작하는지 먼저 확인하고 싶을 때 쓰는 방식이 아웃오브밴드 배포(out-of-band deployment)입니다. 이 방식은 트래픽을 막는 위치가 아니라 복제된 사본만 받아 보는 위치에 WAF를 두는 배포 형태입니다.

택배 회사로 비유하면 이해가 쉽습니다. 실제 배송을 담당하는 기사와 별개로, 모든 주문서를 똑같이 한 부 더 복사해 검사 담당 직원 책상에 올려놓는 것입니다. 검사 직원은 복사본을 읽으며 "이 주문은 수상하다"고 표시만 하고, 실제 배송은 원래 기사가 그대로 진행합니다.

즉 트래픽을 흘려보내는 경로와 검사하는 경로가 분리되어 있고, 검사 결과는 로그(log)와 경보의 형태로만 남습니다. 그래서 탐지 규칙이 오탐(정상 요청을 공격으로 잘못 판단하는 것)을 내도 실제 서비스는 다치지 않고, 어떤 규칙이 어떤 요청을 잡는지 데이터를 모을 수 있습니다.

이렇게 충분히 검증한 뒤에 인라인(inline, 트래픽 경로 위에 직접 놓는 방식)으로 옮기는 것이 안전한 순서입니다.

정리하면 아웃오브밴드 배포는 차단 기능 없이 트래픽 사본만 검사하는 감시 모드이며, WAF 도입의 첫 단계에서 오탐 위험을 줄이고 규칙을 튜닝(tuning, 규칙을 현장에 맞게 조정하는 것)하는 용도로 쓰입니다.

4부. WAF의 배포 방식038

인라인 배포와 지연

검사가 응답 시간에 더하는 비용을 다루는 방법

WAF를 트래픽 경로 위에 직접 세우면 공격을 즉시 막을 수 있지만, 그 대가로 모든 요청이 검사를 통과해야 하므로 응답이 느려질 수 있습니다. 사용자는 화면이 뜨기를 기다리다가 창을 닫고, 매출은 그만큼 새어 나갑니다. 인라인 배포(inline deployment)의 핵심 과제는 바로 이 검사가 더하는 시간, 즉 지연(latency)을 어떻게 감당할 것인가입니다.

고속도로 톨게이트를 떠올리면 됩니다. 차를 세워 한 대씩 확인하면 확실하지만 줄이 길어지고, 검문소를 여러 개 두면 그만큼 더 밀립니다.

그래서 실제 운영에서는 검사를 몇 단계로 나눠 아주 빠른 확인은 앞단에서, 정밀한 검사는 필요할 때만 수행하고, 한 번 통과한 연결은 일정 시간 기억해 두어 매 요청마다 처음부터 검사하지 않습니다. 또 규칙 수를 줄이거나 패턴 매칭을 빠르게 처리하는 장비를 쓰고, 정적 파일처럼 검사가 필요 없는 요청은 아예 건너뛰게 설정합니다.

결국 인라인 배포는 보안과 속도의 맞교환이며, 지연을 줄이는 일은 규칙을 최소화하고 검사 범위를 좁히고 결과를 재사용하는 세 가지 방향으로 이루어집니다. 목표 응답 시간과 허용 가능한 지연 폭을 먼저 정해 두고 그 안에서 규칙을 설계하는 것이 원칙입니다. 다만 허용 가능한 지연 수치는 서비스 특성과 장비 환경에 따라 크게 달라지므로 일률적으로 단정할 수는 없습니다.

4부. WAF의 배포 방식039

이중화와 고가용성

WAF가 고장 나도 서비스가 멈추지 않게 설계하는 방법

WAF를 인라인으로 세운 순간, 그 장비는 서비스의 목숨줄이 됩니다. WAF 한 대가 고장 나면 뒤에 있는 서버가 멀쩡해도 사용자는 아무것도 볼 수 없습니다.

그래서 WAF는 절대 단일 개체로 두지 않고, 하나가 죽어도 다른 하나가 이어받도록 설계합니다. 이것이 이중화(redundancy)와 고가용성(high availability)의 문제입니다.

아파트의 비상 계단과 소방 설비를 생각하면 됩니다. 평소에는 엘리베이터만 쓰지만, 정전이 되면 비상 계단이 즉시 역할을 대신해야 하고, 소방 설비는 늘 같은 상태로 대기하고 있어야 합니다.

WAF도 마찬가지로 두 대 이상을 나란히 두고 같은 규칙을 공유하게 하며, 한 대의 상태를 다른 대가 계속 지켜보다가 이상이 감지되면 몇 초 안에 트래픽을 넘겨받습니다. 이때 두 장비의 설정과 규칙 버전이 어긋나 있으면 절체 순간에 검사가 달라지므로, 설정을 한곳에서 배포하고 동기화하는 관리가 함께 필요합니다.

또한 넘겨받는 쪽이 감당할 수 있는 처리량을 미리 확보해 두어야 하며, 평상시에도 주기적으로 한쪽을 끄는 훈련을 해 두어야 실제 고장에서 당황하지 않습니다.

정리하면 이중화는 여분의 WAF를 준비하는 것이고 고가용성은 그 여분이 실제로 자동으로 역할을 넘겨받게 만드는 운영 체계입니다. 장비 이중화만으로 끝내지 말고 규칙 동기화, 용량 여유, 절체 훈련 세 가지를 함께 갖추어야 서비스가 멈추지 않습니다.

4부. WAF의 배포 방식040

WAF 우회 경로 차단

WAF를 거치지 않고 원본 서버로 붙는 길을 막는 방법

WAF를 성실히 운영하고 있는데도 공격이 성공했다면, 공격자가 WAF를 뚫은 것이 아니라 WAF를 지나가지 않은 길로 들어왔을 가능성이 큽니다. 원본 서버의 주소를 직접 알고 있다면 방화벽 앞문을 돌아가지 않고 뒷문으로 들어올 수 있기 때문입니다. 이 문제가 WAF 우회 경로(bypass path)이며, WAF 운영에서 가장 흔히 놓치는 구멍입니다.

큰 건물의 경비실을 생각해 보십시오. 정문에는 경비원이 서 있지만, 지하 주차장 입구나 화물용 엘리베이터, 옥상 통로가 열려 있으면 경비는 아무 의미가 없습니다.

WAF도 마찬가지로, 서버가 공인 인터넷 주소를 직접 갖고 있거나 예전에 쓰던 주소가 그대로 살아 있으면 그 길로 들어온 트래픽은 검사를 받지 않습니다. 그래서 원본 서버는 WAF에서 오는 트래픽만 받도록 접근을 제한하고, 남아 있는 옛 주소와 임시 주소를 정리하며, 서버가 스스로 외부로 나가는 통신까지 점검해야 합니다.

개발·테스트용 서버나 관리용 접속 경로가 운영 서버와 같은 규칙 없이 열려 있는 경우도 같은 구멍이 됩니다.

결론적으로 WAF 우회 차단은 방화벽 규칙을 늘리는 일이 아니라, 원본 서버로 통하는 모든 길을 목록으로 만들고 WAF 경유만 남기는 작업입니다. 정기적으로 외부에서 서버 주소를 스캔해 WAF를 거치지 않고 응답하는 지점이 없는지 확인하는 것이 실질적인 점검 방법입니다.

시그니처 기반 탐지

알려진 공격 패턴과 비교해 잡아내는 방식

이미 세상에 알려진 공격은 대개 비슷한 모양으로 반복됩니다. 같은 취약점을 노리는 요청이 수천 번씩 되풀이되는데, 매번 새로 고민하지 않고 "이런 모양이 오면 공격"이라고 미리 적어 두면 훨씬 빠르게 막을 수 있습니다. 이렇게 알려진 공격 패턴과 비교해 잡아내는 방식이 시그니처 기반 탐지(signature-based detection)입니다.

경찰의 지명 수배 목록을 떠올리면 됩니다. 수배 전단에는 얼굴 사진과 특징이 적혀 있고, 검문소 직원은 지나가는 사람을 그 목록과 비교해 일치하면 붙잡습니다.

WAF도 요청의 주소, 파라미터, 본문 안에서 특정 문자열이나 구조를 찾아 미리 정의된 패턴과 대조합니다. 예를 들어 데이터베이스 명령을 끼워 넣는 공격의 특징적인 구절이 보이면 즉시 차단 대상으로 표시합니다.

이 방식은 이미 아는 공격에 대해 매우 빠르고 정확하며, 판단 근거가 명확해 로그를 읽기도 쉽습니다.

다만 목록에 없는 처음 보는 공격은 잡지 못하므로, 시그니처 기반 탐지는 규칙을 꾸준히 갱신하는 운영이 생명입니다. 그리고 정상 요청이 우연히 패턴과 닮아 차단되는 오탐이 생길 수 있어, 규칙을 그대로 켜기보다 관찰 기간을 두고 조정하는 것이 안전합니다. 알려진 위협을 막는 기본 방어선으로 이해하면 됩니다.

화이트리스트와 블랙리스트

허용 목록과 차단 목록이라는 정반대 접근

보안 설정을 하다 보면 "무엇을 막을까"만 고민하게 되는데, 막을 것을 세는 방식은 목록이 끝없이 늘어납니다. 반대로 "무엇만 허용할까"를 정하면 목록이 짧고 명확해집니다. 이 두 가지 정반대 접근이 블랙리스트(blacklist, 차단 목록)와 화이트리스트(whitelist, 허용 목록)입니다.

회사 출입 관리로 비교해 보겠습니다.

블랙리스트 방식은 출입 금지 명단을 만들어 그 사람만 막는 것이고, 화이트리스트 방식은 출입증을 가진 사람만 들여보내는 것입니다.

블랙리스트는 평소 통행이 자유로워 편하지만 명단에 없는 새로운 침입자에게는 무력합니다. 화이트리스트는 모르는 대상이 기본적으로 차단되므로 안전하지만, 새로 합류한 직원이나 예상치 못한 정상 요청까지 막혀 업무가 막힐 수 있어 목록 관리가 곧 운영의 핵심이 됩니다.

WAF에서는 관리자 페이지 접속이나 결제 콜백처럼 대상이 명확한 경로에 화이트리스트를 쓰고, 광범위하게 알려진 악성 주소 차단에는 블랙리스트를 쓰는 식으로 섞어 적용합니다. 핵심은 기본값을 무엇으로 둘 것인가이며, 차단을 기본으로 두는 쪽이 보안상 유리하다는 것이 일반적인 원칙입니다. 다만 업무 중단 위험과의 균형이 필요하므로 서비스 중요도에 따라 선택이 달라집니다.

5부. 검사 규칙의 원리043

부정 보안 모델(Negative Security)

나쁜 것을 막고 나머지는 통과시키는 기본값

웹 서버를 운영하다 보면 어느 날 갑자기 게시판에 스크립트가 잔뜩 박힌 글이 올라오고, 그 글을 열어 본 방문자들의 로그인 정보가 새어 나가는 일이 생깁니다. 이런 사고를 막으려고 만든 방화벽의 첫 번째 사고방식이 부정 보안 모델(Negative Security)입니다.

이 모델은 아파트 정문 경비원이 수첩에 적힌 출입 금지 명단을 들고 서 있는 모습과 같습니다. 명단에는 폭력배나 사기꾼처럼 이미 문제를 일으킨 유형이 적혀 있고, 경비원은 그 유형에 해당하는 사람만 세워서 돌려보냅니다.

명단에 없는 사람은 누구든 별다른 확인 없이 그냥 통과시키는데, 이것이 나쁜 것을 막고 나머지는 허용한다는 기본값입니다. 장점은 새로운 주민이나 방문객이 와도 미리 등록할 필요가 없어 편하다는 것이고, 단점은 처음 보는 새로운 유형의 침입자는 명단에 없으니 그대로 들여보낸다는 점입니다.

정리하면 부정 보안 모델은 알려진 공격 패턴 목록을 만들고 그 목록에 걸리는 요청만 차단하며, 목록에 없는 요청은 기본적으로 허용하는 방식입니다. 그래서 새로운 공격이 등장할 때마다 목록을 계속 갱신해야 하고, 목록에 없는 공격은 막지 못한다는 한계를 함께 기억해야 합니다.

5부. 검사 규칙의 원리044

긍정 보안 모델(Positive Security)

좋은 것만 허용하고 나머지는 막는 기본값

허용 목록을 만들지 않고 운영하던 쇼핑몰에서, 공격자가 평소와 전혀 다른 형태의 요청을 보내 데이터베이스를 통째로 내려받은 적이 있습니다. 그 뒤로 많은 조직이 아는 것만 들여보낸다는 반대 방향의 사고방식을 택했는데, 그것이 긍정 보안 모델(Positive Security)입니다.

이 모델은 사원증이 있는 사람만 사무실 문을 열 수 있는 회사와 같습니다. 출입 시스템에는 이 사람은 이 문을 통과해도 된다는 허용 명단이 미리 등록되어 있고, 명단에 없는 사람은 이유를 묻지 않고 막습니다.

대신 명단에 없는 정상 요청, 예를 들어 새로 입사한 직원이나 미리 예약하지 않은 방문객도 함께 막히기 때문에 등록 절차를 꾸준히 관리해야 합니다. 또 서비스가 다루는 요청의 모양을 아주 구체적으로 알아야 명단을 만들 수 있으므로, 준비 비용이 부정 보안 모델보다 큽니다.

즉 긍정 보안 모델은 정상 요청의 형식을 먼저 정의하고 그 형식에 맞는 요청만 허용하며 나머지는 모두 차단하는 방식입니다. 처음 보는 공격에도 강하지만, 정상 동작을 잘못 막는 오탐(false positive)을 줄이려면 허용 규칙을 정교하게 유지해야 합니다.

정규화(Normalization)

인코딩을 풀어 같은 공격을 같은 모양으로 만드는 처리

같은 공격인데 철자를 조금씩 바꿔 보내면 방화벽이 알아보지 못하고 그대로 통과시키는 일이 흔합니다. 이 문제를 줄이려고 요청을 비교하기 전에 같은 모양으로 다듬는 처리를 하는데, 이것이 정규화(Normalization)입니다.

이 처리는 택배 회사가 주소를 입력하는 방식과 비슷합니다. 고객이 서울시 강남구, 서울 강남구, Seoul Gangnam-gu처럼 제각각 적어 보내도, 회사는 이를 정해진 표기 하나로 바꿔 적은 뒤 배송 경로를 계산합니다.

정규화도 마찬가지로 퍼센트 인코딩, 대소문자, 중복 슬래시, 상대 경로 표기처럼 표현만 다른 입력을 원래 의미의 표준 형태로 되돌립니다. 이렇게 한 뒤에 검사하면 공격자가 표현만 살짝 바꿔 규칙을 피해 가는 시도를 같은 공격으로 인식할 수 있습니다.

정리하면 정규화는 인코딩을 풀고 표기를 통일해, 의미가 같은 요청을 같은 모양으로 만드는 전처리 단계입니다. 검사 규칙을 쓰기 전에 반드시 거쳐야 하며, 정규화 순서를 잘못 잡으면 검사 자체가 무력해질 수 있습니다.

5부. 검사 규칙의 원리046

정규식 기반 룰

규칙을 패턴으로 적는 방식과 그 표현의 한계

관리자가 이런 요청은 막아 달라고 말로 설명하면, 이를 기계가 알아들을 수 있는 형태로 적어야 실제 차단이 됩니다. 그때 가장 널리 쓰이는 표기법이 정규식 기반 룰입니다.

이는 우체국 창구 직원이 받는 사람 이름이 김으로 시작하고 주소에 특정 단어가 들어간 편지만 따로 빼라는 지시를 받는 것과 같습니다. 정규식(regular expression)은 이런 문자열의 모양을 기호로 적는 문법으로, 숫자 세 자리나 특정 단어 뒤에 오는 따옴표 같은 조건을 한 줄로 표현합니다.

방화벽은 요청에서 검사할 부분을 뽑아 이 패턴과 맞춰 보고, 맞으면 차단합니다. 다만 패턴은 글자 모양만 보기 때문에 문법이 조금만 달라지거나 패턴을 지나치게 넓게 쓰면 정상 요청까지 막거나 공격을 놓치게 됩니다.

즉 정규식 기반 룰은 차단 조건을 문자열 패턴으로 적어 두고 요청이 그 패턴과 일치하는지 비교하는 방식입니다. 빠르고 간단하지만, 표현의 한계와 오탐과 미탐 사이의 줄타기를 항상 감수해야 합니다.

5부. 검사 규칙의 원리047

파서 기반 검사

요청을 구조로 읽어들여 필드 단위로 검사하는 방식

정규식만으로 요청을 검사하던 시절에는, 공격자가 주석이나 이상한 공백을 섞어 패턴을 피해 가면 그대로 뚫렸습니다. 그래서 요청을 글자가 아니라 구조로 읽어 들인 뒤 필드 단위로 검사하는 방식이 등장했는데, 이것이 파서 기반 검사입니다.

이 방식은 세관 직원이 택배 상자를 열어 품목별로 신고서와 대조하는 일과 같습니다. 파서(parser)는 HTTP 요청을 헤더, 쿼리 문자열, 본문 같은 구성 요소로 나누고 각 값을 이름과 값의 쌍으로 분해합니다.

검사 엔진은 이렇게 나뉜 필드마다 이 필드는 숫자만 와야 한다, 이 필드의 길이는 이 정도여야 한다는 규칙을 적용합니다. 구조를 먼저 이해하고 검사하므로, 표현을 살짝 바꾸는 회피 기법에 훨씬 덜 흔들립니다.

정리하면 파서 기반 검사는 요청을 문법에 따라 해석해 필드 단위로 나눈 뒤 각 필드의 형식과 값을 검사하는 방식입니다. 구조를 이해한다는 점에서 정규식보다 정확하지만, 파서가 요청을 잘못 해석하면 검사 자체가 어긋날 수 있습니다.

5부. 검사 규칙의 원리048

프로토콜 검증

HTTP 문법 자체를 어기는 요청을 걸러내는 방법

정상적인 브라우저는 HTTP라는 약속에 맞춰 요청을 보내지만, 공격 도구는 그 약속을 일부러 어기거나 애매하게 만들어 방화벽의 검사를 헷갈리게 합니다. 이런 요청을 걸러 내는 방법이 프로토콜 검증입니다.

이 검증은 우체국이 규격에 맞지 않는 우편물을 접수하지 않는 것과 같습니다. 봉투 크기, 우표 위치, 주소 기재 방식이 정해져 있고, 이를 어긴 우편물은 내용을 보기도 전에 반송됩니다.

프로토콜 검증도 요청 줄의 형식, 헤더 이름과 값의 문법, 본문 길이 표시와 실제 본문 크기의 일치 여부처럼 HTTP 문법 자체를 확인합니다. 문법을 어긴 요청은 정상 사용자가 보낼 이유가 없으므로, 내용 검사에 앞서 먼저 걸러 내는 관문 역할을 합니다.

즉 프로토콜 검증은 HTTP 문법을 지키지 않는 요청을 내용과 무관하게 차단하는 첫 단계 검사입니다. 문법 오류를 일찍 걸러 내면 뒤따르는 파싱과 패턴 검사가 훨씬 안정적으로 동작합니다.

관리하는 웹 서버에 하루에도 수만 건의 접속이 들어오는데, 그중에는 이미 다른 곳에서 공격을 퍼부은 이력이 있는 주소가 섞여 있습니다. 요청 내용을 하나하나 뜯어보기 전에는 그 사실을 알 수 없어서 서버가 쓸데없는 검사 비용을 치르게 되는데, 평판 기반 차단은 바로 이 지점에서 보낸 쪽의 이력부터 확인해 이미 나쁜 평판이 쌓인 상대를 문전에서 돌려보내는 방식이며 웹 애플리케이션 방화벽(WAF)의 첫 검사 단계 가운데 하나입니다.

아파트 단지 경비실에 비유하면 이해가 쉽습니다. 경비원은 방문객의 짐을 일일이 열어보기 전에 먼저 명단을 확인하는데, 이 명단이 바로 평판 정보입니다. 전에 소란을 피운 사람의 이름과 얼굴이 적힌 차단 명단에 있으면 정문에서 돌려보내고, 처음 보는 사람이면 명단 조회만 하고 안으로 들여보낸 뒤 나중에 짐 검사를 맡깁니다.

평판 데이터베이스는 여러 기관이 공유하는 이 명단이고, IP 주소와 도메인 이름이 그 명단의 항목이 됩니다.

결국 평판 기반 차단은 IP 주소와 도메인의 과거 이력을 미리 조회해 위험한 상대를 비용이 큰 검사 전에 걸러내는 기법입니다.

학습 단계에서는 정상 요청의 길이, 매개변수 개수, 헤더 구성 같은 특징값의 분포를 모아 기준선을 만들고, 판정 단계에서는 새 요청이 그 기준선에서 얼마나 떨어져 있는지를 점수로 계산합니다.

다만 정상 범위가 자주 바뀌는 서비스에서는 오탐이 늘고, 왜 걸렸는지 사람에게 설명하기 어렵다는 한계가 있습니다.

정리하면 머신러닝 기반 탐지는 정상 요청의 통계적 기준선을 학습해 두고 그로부터의 이탈 정도로 이상 요청을 판정하는 방식이며, 서명이 없는 공격을 잡는 대신 오탐과 설명 가능성이라는 비용을 함께 안고 갑니다.

ModSecurity

오픈소스 WAF 엔진의 구성과 동작 흐름

웹 서버 앞단에 방화벽을 세웠는데 어떤 요청을 막아야 할지 판단하는 두뇌가 없으면 그 장치는 그냥 통과만 시키는 관문이 됩니다. 그 판단을 맡는 오픈소스 엔진이 ModSecurity이며, 웹 서버에 모듈로 붙어 요청과 응답을 검사하고 룰에 따라 차단 여부를 정합니다.

ModSecurity에서는 연결 단계, 요청 헤더 단계, 요청 본문 단계, 응답 단계로 검사 지점이 나뉘고, 각 지점마다 룰이 순서대로 평가됩니다. 엔진은 룰을 읽어 변수를 뽑고 연산자로 조건을 확인한 뒤 액션으로 기록과 차단과 통과를 결정하며, 이 모든 과정의 결과가 감사 로그(audit log)에 남습니다.

결국 ModSecurity는 웹 서버에 붙어 정해진 검사 지점마다 룰을 평가하고 그 결과를 로그로 남기는 오픈소스 룰 엔진입니다.

ModSecurity 룰 문법

SecRule의 변수와 연산자와 액션 구조

차단 규칙을 자연어 문장으로 적어 두면 사람마다 해석이 달라지고 기계가 자동으로 평가할 수도 없습니다. 그래서 ModSecurity는 검사 대상과 조건과 조치를 한 줄에 정해진 순서로 적는 SecRule 문법을 쓰며, 룰 파일은 이런 한 줄들의 목록으로 이루어집니다.

택배 집하장의 분류 지시문을 떠올리면 구조가 그대로 보입니다. 지시문은 어느 택배를 볼 것인가, 무엇을 확인할 것인가, 확인 결과가 참이면 어떻게 할 것인가라는 세 칸으로 나뉘는데, SecRule의 변수와 연산자와 액션이 각각 이 칸에 해당합니다.

변수는 검사할 요청의 부분을 가리키고, 연산자는 그 값이 정규식과 맞는지 길이가 기준을 넘는지 같은 조건을 판정하며, 액션은 차단(deny)과 기록(log)과 통과(pass) 같은 처리를 정합니다. 한 줄에 이 셋이 모두 들어가므로 룰을 읽으면 무엇을 왜 어떻게 다루는지가 한눈에 드러납니다.

정리하면 SecRule은 변수로 검사 대상을 고르고 연산자로 조건을 판정하고 액션으로 처리를 정하는 한 줄짜리 규칙 형식입니다.

6부. ModSecurity와 OWASP CRS053

룰 ID와 메타데이터

룰을 찾고 분류하기 위한 태그와 심각도

룰이 수백 수천 개로 늘어나면 비슷한 규칙이 겹치고, 어떤 요청이 왜 막혔는지 로그만 보고는 알기 어려워집니다. 그래서 각 룰에 고유 번호와 설명, 분류 태그, 심각도를 함께 적어 두는데, 이것이 룰 ID와 메타데이터입니다.

도서관 서가를 떠올리면 이해가 빠릅니다. 책마다 청구기호가 붙어 있어 같은 책을 다시 찾을 수 있고, 주제 분류표와 난이도 표시 덕분에 서가 전체를 훑지 않고도 필요한 책을 골라낼 수 있습니다.

룰의 ID는 이 청구기호처럼 중복되지 않는 번호이고, 태그는 주제 분류표처럼 공격 유형별로 룰을 묶는 표식이며, 심각도(severity)는 이 룰이 걸렸을 때 얼마나 급한 일인지를 나타내는 등급입니다. 메시지(msg)에는 무슨 문제인지 짧은 설명이 들어가서, 차단 로그 한 줄만 보고도 담당자가 원인을 좁힐 수 있습니다.

결국 룰 ID와 메타데이터는 각 룰을 유일하게 식별하고 분류와 우선순위를 붙여, 룰 집합을 관리하고 탐지 결과를 해석할 수 있게 하는 표지입니다.

6부. ModSecurity와 OWASP CRS054

변환 함수(Transformation)

검사 전에 입력값을 바꾸는 함수들의 용도

공격 문자열을 URL 인코딩으로 감싸거나 대소문자를 섞으면 룰의 정규식이 원본 그대로는 맞지 않게 됩니다. 검사 전에 입력을 표준형으로 바꿔 놓는 기능이 변환 함수(Transformation)이며, ModSecurity의 룰에서는 t: 로 시작하는 액션으로 지정합니다.

택배 집하장에서 송장을 읽는 상황을 생각해 보면 됩니다. 어떤 송장은 서울을 서울이라고 적고, 어떤 송장은 서울특별시라고 적고, 또 어떤 송장은 띄어쓰기와 약어가 뒤섞여 있어서 그대로 대조하면 같은 주소인데도 다른 값으로 읽힙니다.

그래서 집하장은 분류기에 넣기 전에 주소를 정해진 표기로 고쳐 쓰는데, 변환 함수가 바로 이 정규화 작업을 합니다. 소문자로 바꾸는 lower, URL 인코딩을 푸는 urlDecode, 겹친 공백을 줄이는 compressWhitespace 같은 함수를 액션에 나열하면, 엔진이 원본 값을 그 형태로 바꾼 뒤 연산자로 검사합니다.

정리하면 변환 함수는 검사 직전에 입력값을 표준 형태로 바꿔, 표기만 살짝 비튼 우회가 룰을 빠져나가지 못하게 하는 전처리 단계입니다.

6부. ModSecurity와 OWASP CRS055

요청 단계와 응답 단계

어느 처리 시점에 룰이 실행되는지

웹 방화벽을 붙였는데도 홈페이지에 이상한 스크립트가 그대로 박혀 나오거나, 이미 나간 응답에 민감한 정보가 실려 나가는 일이 있습니다. WAF(웹 애플리케이션 방화벽)는 검사를 어느 시점에 하느냐에 따라 무엇을 막을 수 있는지가 달라지는데, 이를 구분한 것이 요청 단계와 응답 단계입니다.

회사에 우편실이 하나 있다고 생각해 보십시오. 바깥에서 들어오는 소포는 접수 창구를 지날 때 열어 보고 위험한 물건이 들었으면 되돌려 보내며, 이때를 요청 단계(request phase)라고 합니다. 반대로 회사가 바깥으로 내보내는 소포는 발송 직전에 한 번 더 검사하는데, 이때가 응답 단계(response phase)입니다.

우편실은 두 창구를 모두 거치게 하되 어느 창구에서 무엇을 볼지를 규칙표로 정해 두고, 접수 창구에서는 주소와 내용물을, 발송 창구에서는 혹시 새어 나가는 서류가 없는지를 봅니다.

정리하면 요청 단계는 클라이언트가 보낸 입력값을, 응답 단계는 서버가 돌려주는 출력값을 검사하는 시점이며, 같은 룰이라도 어느 단계에 걸려 있느냐에 따라 잡아낼 수 있는 공격이 달라집니다.

6부. ModSecurity와 OWASP CRS056

OWASP CRS

공용 룰셋이 기본으로 제공하는 방어 범위

웹 방화벽을 설치하고 나서 룰을 직접 짜야 한다고 생각하면 손이 잘 붙지 않고, 결국 아무 검사도 하지 않는 빈 방화벽만 남기 쉽습니다. OWASP CRS(Open Web Application Security Project Core Rule Set)는 이런 수고를 덜어 주려고 여러 보안 전문가가 함께 만든 공용 룰셋입니다.

아파트 경비실에 표준 점검표가 붙어 있는 모습을 떠올려 보십시오. 순찰할 때 무엇을 살펴야 하는지 항목별로 적혀 있어서 새로 온 경비원도 같은 기준으로 문단속과 주차장을 확인합니다.

CRS도 마찬가지로 SQL 삽입이나 크로스사이트 스크립팅처럼 널리 알려진 공격 유형을 항목으로 정리해 두고, 요청이 들어올 때마다 그 목록과 대조합니다. 다만 경비실 점검표가 모든 사고를 막지는 못하듯, CRS도 알려진 유형을 넓게 덮는 것이지 그 사이트만의 업무 규칙까지 알지는 못합니다.

요약하면 CRS는 흔한 웹 공격을 빠르게 막아 주는 기본 룰 모음이며, 여기에 사이트별 규칙을 얹어 보완하는 것이 일반적인 구성입니다.

6부. ModSecurity와 OWASP CRS057

CRS 파라노이아 레벨

룰셋 강도를 1단계부터 4단계까지 조절하는 방법

같은 룰셋을 그대로 쓰는데 어떤 사이트는 정상 결제가 계속 막히고 어떤 사이트는 공격을 흘려보냅니다. CRS는 룰을 켜고 끄는 대신 검사 강도를 단계로 조절하는데, 이를 파라노이아 레벨(paranoia level)이라 부릅니다.

아파트 경비실의 검문 강도를 1단계부터 4단계까지 조절한다고 생각해 보십시오. 1단계는 출입증 없는 사람만 세우는 느슨한 검문이라 주민 불편이 거의 없지만, 2단계부터는 가방을 열어 보고 3단계와 4단계로 갈수록 복장과 소지품까지 확인해 의심스러운 점을 더 많이 잡아냅니다. 대신 강도를 올릴수록 택배기사나 방문객처럼 정상인 사람이 세워지는 일도 함께 늘어납니다.

CRS에서도 레벨이 올라갈수록 더 엄격하고 예외가 적은 룰이 추가되어, 낮은 단계는 오탐이 적고 높은 단계는 방어가 촘촘해지는 맞교환이 생깁니다.

결국 파라노이아 레벨은 룰셋의 검사 강도를 한 단계씩 높이는 손잡이이며, 서비스 특성과 오탐을 어디까지 감수할지를 보고 1단계부터 올려 가며 조정하는 것이 보통입니다.

CRS 예외 처리

오탐이 나는 룰만 골라 제외하는 방법

CRS를 켜 두면 정상적인 게시글이나 검색어가 공격으로 오인되어 차단되는 오탐이 생깁니다. 이때 룰셋 전체를 끄면 방어가 통째로 사라지므로, 문제를 일으킨 룰만 골라 제외하는 예외 처리가 필요합니다.

회사 정문 보안 검색대에 예외 명단을 붙여 두는 상황을 생각해 보십시오. 검색대 자체는 그대로 두고, 매번 걸리지만 문제가 없는 특정 부서의 노트북 같은 물품만 명단에 올려 통과시킵니다.

이때 무엇이 걸렸는지 확인하는 것이 먼저인데, 로그에서 룰 번호와 매치된 부분을 보고 나서야 어느 룰을 예외로 둘지 정할 수 있습니다. 명단은 룰 번호와 적용할 경로나 변수를 좁혀 지정하는 식으로 만들고, 사이트 전체에 풀어 버리면 그 룰이 막아 주던 공격까지 함께 열리므로 범위를 좁게 잡아야 합니다.

정리하면 예외 처리는 룰셋을 유지한 채 특정 룰의 적용 범위만 비켜 주는 작업이며, 로그로 원인을 확인하고 최소 범위로 지정하는 것이 핵심입니다.

ModSecurity 로그 해석

차단 로그에서 룰 ID와 매치된 부분을 읽는 방법

사용자가 페이지가 안 열린다고 문의해 왔는데 서버 로그에는 흔적이 없으면 원인을 찾기가 막막합니다. ModSecurity는 요청을 막을 때 그 이유를 로그에 남기는데, 그 로그를 읽는 법을 알면 어떤 룰이 무엇을 문제 삼았는지 되짚을 수 있습니다.

택배가 반송될 때 운송장에 반송 사유 코드와 어느 구간에서 걸렸는지가 함께 적혀 오는 것과 같습니다.

ModSecurity 로그에는 룰을 식별하는 번호(ID)와 그 룰이 요청의 어느 부분을 매치했는지, 즉 변수 이름과 실제로 잡힌 문자열이 함께 기록됩니다. 사유 코드만 보고 짐을 다시 보내면 또 반송되듯, 룰 번호만 확인하고 넘어가면 같은 차단이 반복되므로 매치된 부분까지 읽어야 입력값의 어디가 문제인지 알 수 있습니다. 로그에는 심각도와 처리 결과도 붙어 있어서, 막은 것인지 기록만 한 것인지도 함께 구분됩니다.

요약하면 ModSecurity 로그는 룰 ID, 매치된 변수와 값, 처리 결과를 한 줄에 담고 있으며, 이 세 가지를 함께 읽어야 차단 원인을 정확히 짚을 수 있습니다.

정리하면 성능 튜닝은 검사 범위와 깊이를 조절해 처리 비용을 낮추는 작업이며, 지연과 방어 수준 사이의 균형점을 측정으로 찾는 것이 핵심입니다.

AWS WAF

웹 ACL과 룰과 룰 그룹의 구조

쇼핑몰 웹 서버를 운영하는데 악성 요청을 막으려고 조건을 하나씩 덧붙이다 보면 어느새 수십 개의 규칙이 뒤엉켜, 어떤 규칙이 먼저 적용되는지 아무도 설명하지 못하는 상황이 됩니다. 그래서 요청을 통과시킬지 막을지 판정하는 하나의 큰 단위 아래에 개별 판정 규칙과 그 규칙의 묶음을 층층이 두는 구조가 필요하고, 이것이 AWS WAF의 기본 골격입니다.

아파트 정문 경비실을 떠올리면 이해가 쉽습니다. 경비실 하나가 담당하는 검문 절차 전체가 웹 ACL(Access Control List, 접근 제어 목록)이고, 신분증을 확인한다거나 방문 목적을 묻는다 같은 개별 검문 항목이 룰입니다. 같은 검문 항목을 여러 동에 똑같이 적용해야 할 때 매번 복사하지 않고 매뉴얼 한 권으로 묶어 두는 것이 룰 그룹이며, 경비원은 정해진 순서대로 검문을 처리합니다. 순서가 중요한 이유는 앞의 룰이 이미 통과시킨 요청은 뒤의 룰을 볼 필요가 없기 때문이고, 그래서 예외를 앞에 두는 식으로 우선순위를 설계합니다.

결국 AWS WAF는 웹 ACL이라는 판정 단위 아래 룰을 두고, 재사용할 룰은 룰 그룹으로 묶어 순서대로 평가하는 계층 구조입니다.

결국 관리형 룰은 검증된 룰셋을 받아 기본 방어선을 빠르게 세우고, 현장에 맞는 조정만 직접 하는 방식입니다.

7부. 클라우드 WAF 운영063

Cloudflare WAF

대시보드 중심 룰 관리와 관리형 규칙의 특징

여러 지역에 서비스를 두면 지역마다 방화벽 정책을 따로 관리해야 해서 설정이 어긋나는 일이 잦습니다. Cloudflare WAF는 사용자 요청이 CDN(콘텐츠 전송 네트워크) 엣지를 지나갈 때 검사하고, 대시보드 한 곳에서 정책을 관리하는 방식으로 이 문제를 풉니다.

오탐(False Positive)

정상 요청을 공격으로 잘못 판단하는 문제

WAF가 정상 요청을 공격으로 잘못 판단하면, 사용자는 로그인도 결제도 하지 못하고 담당자는 원인을 찾아 헤매게 됩니다. 이런 오탐(False Positive)은 룰이 부정확해서 생기는 경우도 있지만, 서비스가 평소와 다른 형태의 요청을 보내기 시작해서 생기는 경우도 많습니다. 예를 들어 게시판에 코드 조각을 올리는 기능은 공격 패턴과 비슷한 문자열을 정상적으로 포함합니다. 공항 검색대에 견주면 이해가 쉽습니다. 위험한 물건을 잡아내려고 기준을 지나치게 넓히면 물병이나 노트북까지 걸려 줄이 길어지고, 반대로 기준을 좁히면 진짜 위험한 물건을 놓칩니다. 검색대 직원이 계속 같은 물건을 보며 기준을 조정하듯, WAF도 걸린 요청을 사람이 확인해 예외를 등록하고 룰을 다듬어야 균형이 잡힙니다. 결국 오탐은 차단을 강하게 만들수록 함께 늘어나는 비용이며, 걸린 요청을 검토해 예외와 룰을 조정하는 반복 작업이 WAF 운영의 핵심이 됩니다.

오탐 줄이기

예외와 룰 조정과 임계값으로 오탐을 낮추는 절차

정상 고객이 물건을 사려고 결제 화면을 열었는데 갑자기 접근이 차단되어 장바구니가 사라지는 일이 생깁니다. 공격을 막으려고 세운 방어 장치가 공격이 아닌 요청까지 공격으로 판단할 때 이를 오탐(False Positive)이라고 하며, 오탐을 줄이는 일은 방화벽 운영의 절반을 차지합니다.

아파트 경비실을 떠올려 보면, 경비원이 모든 택배 상자를 흔들어 보고 위험한 물건이 든 상자만 막아야 하는데 겁이 나서 상자 크기와 무게 기준을 너무 빡빡하게 잡으면 정상 택배까지 반송되는 것과 같습니다.

  • 그래서 먼저 차단 기록을 보고 실제 공격인지 정상 요청인지 하나씩 확인해 공격이 아닌 것으로 판명된 요청은 예외 목록에 올립니다.
  • 다음으로 특정 규칙이 특정 사이트에서 유난히 자주 걸린다면 그 규칙의 민감도를 낮추거나 적용 범위를 좁히는 룰 조정을 합니다.
  • 마지막으로 점수 기반 탐지라면 차단으로 넘어가는 임계값을 조금 높여 애매한 요청은 통과시키고 확실한 공격만 막도록 맞춥니다.

정리하면 오탐 줄이기는 예외 등록과 룰 조정과 임계값 조정을 차단 기록이라는 증거를 보며 반복하는 절차입니다. 이 세 가지를 한 번에 크게 바꾸면 무엇 때문에 달라졌는지 알 수 없으니 한 번에 하나씩 바꾸고 결과를 다시 확인하는 태도가 중요합니다.

미탐(False Negative)

공격을 놓치는 원인과 그것을 줄이는 방법

공격자가 서버에 침투해 고객 정보를 빼갔는데 방화벽 기록에는 아무 일도 없었던 것처럼 남는 경우가 있습니다. 공격을 공격으로 알아보지 못해 그냥 통과시키는 것을 미탐(False Negative)이라고 하며, 오탐과 반대 방향의 위험입니다.

아파트 경비원이 낯선 사람을 막는 데만 익숙해져서 소방 점검 옷을 입고 들어오는 침입자를 그냥 통과시켜 버리는 상황과 같습니다.

미탐이 생기는 이유는 크게 세 가지인데 규칙이 아직 알려지지 않은 공격 방식을 모르는 경우, 인코딩이나 대소문자를 바꿔 검사를 피하는 경우, 그리고 검사 대상에서 빠진 경로나 파라미터가 있는 경우입니다.

  • 이를 줄이려면 먼저 모든 요청과 응답을 남기는 로그를 확보하고 알려진 공격 패턴을 주기적으로 갱신해야 합니다.
  • 또한 정상 요청과 공격 요청을 함께 넣어 탐지 여부를 확인하는 모의 시험을 정기적으로 돌리고, 검사에서 빠진 경로가 없는지 설정을 점검합니다.

결국 미탐은 규칙의 최신성과 검사 범위의 완전성 그리고 검증 체계라는 세 축을 꾸준히 관리해야 줄어듭니다. 오탐을 줄이려고 기준을 느슨하게 풀수록 미탐이 늘어나므로 두 수치를 함께 보며 균형점을 찾아야 합니다.

예외 정책 관리

예외가 쌓여 구멍이 되는 것을 막는 관리 방법

장애를 급히 막으려고 예외를 하나 등록했는데 몇 달 뒤에는 아무도 왜 그 예외가 있는지 모르는 상태가 됩니다. 예외는 방화벽에 뚫린 작은 구멍이라서 관리하지 않으면 그 구멍들이 모여 방어 전체를 무력하게 만듭니다.

아파트 공용 출입문에 비상용 열쇠를 하나 숨겨 두는 것과 같아서, 처음에는 급한 일을 해결해 주지만 열쇠가 몇 개씩 늘고 아무도 회수하지 않으면 누가 드나드는지 알 수 없게 됩니다.

그래서 예외마다 신청한 사람과 사유와 만료일을 반드시 적게 하고, 만료일이 지나면 자동으로 사라지도록 만듭니다. 또 예외가 어떤 규칙을 어떤 경로에서 얼마나 넓게 풀어 주는지 범위를 최소로 잡고, 주기적으로 목록을 다시 검토해 더 이상 필요 없는 것은 지웁니다. 변경 이력도 함께 남겨 두면 나중에 사고가 났을 때 어떤 예외가 원인인지 추적할 수 있습니다.

결국 예외 정책 관리는 예외를 금지하는 일이 아니라 기한과 범위와 이력을 갖춘 임시 조치로 다루는 일입니다. 예외 목록이 곧 방화벽의 실제 방어 범위라는 점을 기억해야 합니다.

경로별 정책

로그인과 검색과 업로드 경로마다 다르게 적용하는 방법

쇼핑몰의 로그인 화면과 상품 검색 화면과 사진 업로드 화면은 받는 입력의 성격이 전혀 다른데 같은 규칙을 똑같이 적용하면 어딘가는 불편하고 어딘가는 뚫립니다. 그래서 요청이 향하는 경로를 기준으로 검사 강도와 규칙 묶음을 다르게 적용하는 것을 경로별 정책이라고 합니다.

회사 건물에 들어갈 때 방문객은 안내데스크에서 신분을 확인하고 직원은 사원증으로 통과하며 서버실은 별도 출입증을 요구하는 것과 같습니다.

로그인 경로에는 비밀번호 대입 반복과 특수문자 삽입을 집중적으로 보고, 검색 경로에는 스크립트 삽입 시도를 중점적으로 보며, 업로드 경로에는 파일 형식 검사를 붙이는 식입니다. 반대로 공개 게시판처럼 누구나 글을 쓰는 경로는 차단보다 기록과 속도 제한을 우선해 정상 이용자를 막지 않도록 조정합니다. 경로 분류가 틀리면 정책도 틀어지므로 실제 서비스 구조를 반영해 목록을 먼저 정확히 만드는 것이 출발점입니다.

경로별 정책은 모든 요청을 같은 잣대로 재지 않고 요청이 하는 일에 맞춰 검사 도구를 골라 쓰는 방식입니다. 정책이 늘어날수록 관리 부담도 늘어나므로 경로를 너무 잘게 나누지는 않는 것이 좋습니다.

파라미터별 검사

입력 항목마다 검사 강도를 달리하는 방법

택배 접수 창구에서 보내는 사람 이름은 한글과 숫자만 받고, 물품 설명은 길게 받아도 되고, 무게는 숫자만 받는 것과 같습니다.

숫자만 와야 하는 나이 항목에 글자가 들어오면 그것 자체가 비정상 신호이므로 즉시 차단하고, 자유로운 글을 받는 본문 항목은 위험한 태그만 골라 막습니다. 길이 제한도 항목마다 다르게 두어 이름에 수천 자가 들어오는 요청은 내용을 보기도 전에 거부합니다. 정의되지 않은 파라미터가 몰래 붙어 오는 경우도 있으므로 허용 목록에 없는 항목은 무시하거나 차단합니다.

파라미터별 검사는 무엇을 받을지 미리 정해 두고 그 형식에서 벗어난 입력을 걸러 내는 방식입니다. 검사 규칙을 항목 정의와 함께 관리해야 서비스가 바뀔 때 규칙도 같이 따라갈 수 있습니다.

파일 업로드 검사

  • 먼저 확장자를 허용 목록 방식으로 제한해 이미지와 문서 등 필요한 형식만 통과시킵니다.
  • 다음으로 요청에 함께 오는 MIME 타입을 확인하는데 이 값은 조작될 수 있으므로 파일 앞부분의 실제 바이트를 읽어 형식을 다시 판별합니다.
  • 마지막으로 업로드된 파일을 웹에서 바로 실행되지 않는 저장소에 두고 이름을 새로 부여해 원래 이름에 담긴 경로 조작을 막습니다.

결국 파일 업로드 검사는 이름과 신고된 형식과 실제 내용 세 가지를 대조해 허용된 형식만 받아들이는 절차입니다. 검사만으로 부족할 때를 대비해 저장 위치와 실행 권한을 함께 제한해 두는 것이 안전합니다.

인코딩과 이중 인코딩

인코딩을 바꿔 가며 들어오는 공격을 잡는 방법

위험한 문자열을 그대로 보내면 차단된다는 것을 아는 공격자는 같은 글자를 다른 표기로 바꾸거나 여러 겹으로 감싸서 보냅니다. 검사 장비가 눈앞의 글자만 보고 판단하면 그 속뜻을 알아채지 못하므로, 요청을 표준 형태로 되돌린 뒤 검사하는 인코딩 정규화(encoding normalization)가 웹 방화벽(Web Application Firewall, WAF)의 기본 처리로 자리 잡았습니다. 사내 우편 분류 담당자를 떠올려 보면 이해가 쉽습니다. 접수 창구에서 받은 봉투에 수신인 이름이 한글, 로마자 표기, 약어로 제각각 적혀 있으면 담당자는 같은 사람 앞으로 가는 우편인 줄 모르고 엉뚱한 곳으로 보냅니다.

그래서 담당자가 모든 봉투를 표준 이름으로 먼저 고쳐 적는데, 이 작업이 정규화에 해당합니다. 이중 인코딩(double encoding)은 이 고쳐 적기를 한 번만 하도록 속이는 수법이라 두 번째 겹이 풀리지 않은 채 검사대를 통과합니다. 결국 WAF는 요청을 더 이상 풀리지 않을 때까지 반복해서 디코딩해 표준 형태로 만든 뒤 검사하고, 원래 표기까지 함께 대조해 인코딩을 바꿔 가며 들어오는 공격을 잡습니다.

정책 변경 관리

누가 언제 무엇을 바꿨는지 남기는 절차

담당자 한 명이 급하게 예외 규칙을 추가한 뒤 기록을 남기지 않으면, 다음 주에 장애가 났을 때 누가 왜 바꿨는지 아무도 설명하지 못합니다. 이렇게 정책이 제멋대로 쌓이는 것을 막으려고, 누가 언제 무엇을 어떤 이유로 바꿨는지 남기고 검토를 거치게 하는 정책 변경 관리(change management) 절차를 웹 방화벽(Web Application Firewall, WAF) 운영에 붙입니다. 아파트 관리사무소의 공용 시설 변경을 떠올리면 이해가 쉽습니다. 지하 주차장 출입문 비밀번호를 바꿀 때 담당자가 혼자 정해서 알려 주면 나중에 문제가 생겼을 때 누가 언제 바꿨는지 확인할 길이 없습니다.

그래서 변경 신청서에 사유와 기간을 적고, 관리소장의 승인을 받고, 변경 대장에 날짜와 담당자를 기록하는 순서를 둡니다. WAF도 마찬가지로 변경 요청, 승인, 적용, 기록의 네 단계를 거치고, 바꾸기 전 설정을 백업해 두었다가 문제가 생기면 곧바로 되돌립니다. 이 절차가 있으면 정책은 개인의 기억이 아니라 남은 기록으로 관리되고, 장애 원인을 찾는 시간과 책임 소재를 다투는 일이 크게 줄어듭니다.

REST API의 특징

WAF가 API를 다룰 때 달라지는 점

사람이 쓰는 웹 화면은 요청 모양이 몇 가지로 정해져 있지만, 앱과 서버가 주고받는 인터페이스는 주소와 데이터 형식이 훨씬 다양해서 기존 방식의 검사로는 절반도 걸러내지 못합니다. 그래서 REST API(자원을 주소로 표현하고 HTTP 동사로 조작하는 방식)를 다룰 때 웹 방화벽(Web Application Firewall, WAF)은 검사 기준을 크게 바꿔야 합니다. 아파트 택배 보관소를 떠올려 보면 이해가 쉽습니다. 입주민이 직접 찾으러 오는 경우에는 얼굴을 확인하고 이름을 부르면 되지만, 배송 기사가 하루에도 수백 개를 쏟아 붓는 경우에는 누가 보낸 것인지, 어떤 물건인지 겉모습만으로는 알 수 없습니다.

그래서 보관소는 송장 번호와 예약 목록을 대조하는 방식으로 바뀌는데, WAF가 REST API를 대할 때도 이와 같이 주소 경로, HTTP 메서드, 헤더, 본문 구조를 조합해 정상 요청인지 판단합니다. 또 응답 본문에 주민등록번호 같은 민감 정보가 섞여 나가지 않는지도 함께 봐야 하는데, 이는 화면 위주 검사에서는 하지 않던 일입니다. 결국 REST API 환경의 WAF는 정해진 주소 몇 개를 막는 장치가 아니라, 자원 경로와 메서드 조합별로 허용 규칙을 세우고 요청과 응답 양쪽을 검사하는 장치가 됩니다.

JSON과 XML 본문 검사

공격 코드를 이미지 파일이나 일반 텍스트에 숨겨 보내면 겉모습만 보는 검사는 그대로 통과시키고 맙니다. 그래서 요청 본문(body)이 JSON(키와 값의 쌍으로 이루어진 데이터 형식)이나 XML(태그로 구조를 표시하는 데이터 형식)처럼 구조를 가질 때는, 그 구조를 풀어 안쪽 값까지 들여다보는 본문 검사가 필요합니다. 택배 접수 창구를 떠올려 보면 이해가 쉽습니다. 겉봉투에 적힌 품목란만 보고 "서류"라고 믿으면 상자 안에 무엇이 들었는지 알 수 없으므로, 접수원은 상자를 열어 안쪽 포장까지 확인합니다. 이때 상자 안에 작은 상자가 또 들어 있으면 그것도 열어 봐야 하는데, JSON과 XML의 중첩 구조가 바로 이 작은 상자에 해당합니다.

웹 방화벽(Web Application Firewall, WAF)은 본문을 문법에 따라 해석(파싱)해 키와 값을 하나씩 꺼내 보고, 허용된 항목 이름과 값의 형식에서 벗어난 부분이 없는지 검사합니다. 문법이 깨진 본문이나 지나치게 깊이 겹친 구조는 그 자체로 거부하는 경우가 많습니다. 결국 본문 검사는 데이터의 겉포장이 아니라 안쪽 값의 내용과 구조를 확인해, 구조화된 형식으로 위장한 공격을 걸러내는 일입니다.

API 스키마 검증

OpenAPI 스키마로 요청 형식을 강제하는 방법

앱 개발자와 서버 개발자가 데이터 형식을 서로 다르게 이해하면, 오타 하나나 숫자 자리에 글자가 들어간 요청이 그대로 서버까지 도달해 오류를 일으킵니다. 이 어긋남을 입구에서 잡으려고 API의 형식을 미리 문서로 정의해 두고 그 문서와 대조하는 스키마 검증(schema validation)을 쓰며, OpenAPI는 그런 규격을 기계가 읽을 수 있게 적는 대표적인 표기법입니다. 아파트 입주 신청서 접수를 떠올리면 이해가 쉽습니다. 접수 창구에 신청서 양식이 붙어 있으면 담당자는 칸의 개수와, 이름은 글자로, 생년월일은 숫자 여덟 자리로 적혔는지만 확인하면 되고, 형식이 어긋난 서류는 그 자리에서 돌려보냅니다.

이때 양식 자체가 스키마이고, OpenAPI 문서는 그 양식을 누구나 같은 방식으로 읽을 수 있게 표준 서식으로 인쇄해 둔 것에 해당합니다. 웹 방화벽(Web Application Firewall, WAF)은 이 양식을 미리 받아 두고 들어오는 요청의 필수 항목, 값의 종류, 길이, 허용 범위를 하나씩 대조하며, 정해진 양식에 없는 항목이 끼어 있으면 거부합니다. 결국 스키마 검증은 서버가 처리하기 전에 요청의 모양을 규격과 맞춰 보는 관문으로, 예상하지 못한 입력이 애플리케이션까지 흘러드는 통로를 좁혀 줍니다.

GraphQL 보호

쿼리 깊이와 복잡도를 제한해 남용을 막는 방법

하나의 주소로 원하는 데이터를 자유롭게 조합해 달라고 요청할 수 있는 GraphQL에서는, 악의적인 사용자가 한 번의 요청에 끝없이 겹친 질의를 담아 보내 서버를 마비시킬 수 있습니다. 그래서 질의의 깊이와 복잡도에 상한을 두는 보호 장치가 필요하고, 이것이 웹 방화벽(Web Application Firewall, WAF)이 GraphQL을 다룰 때의 핵심 과제가 됩니다. 무한 리필 뷔페를 떠올려 보면 이해가 쉽습니다. 접시에 음식을 담는 것은 자유지만, 한 접시에 산처럼 쌓거나 남겨 버리면 뒤에 온 손님이 먹을 것이 없어집니다.

그래서 식당은 한 접시에 담을 수 있는 양과 한 번에 가져갈 수 있는 접시 수를 정해 두는데, 질의 깊이(depth) 제한이 겹겹이 파고드는 요청의 층수를 제한하는 것이라면 복잡도(complexity) 제한은 한 번에 요구하는 데이터의 총량을 제한하는 것입니다. WAF는 질의를 받으면 미리 계산한 점수로 비용을 어림하고, 정해진 한도를 넘으면 서버에 전달하기 전에 잘라냅니다. 결국 GraphQL 보호는 자유로운 질의 형식에 비용 계산과 상한이라는 질서를 더해, 적은 요청으로 큰 부담을 주는 남용을 막는 일입니다.

속도 제한(Rate Limiting)

요청 빈도를 기준으로 남용을 막는 방법

가게 앞에 줄이 길게 늘어서 있는데 한 사람이 같은 계산대에 초당 수십 번씩 물건을 밀어 넣는다면 정상 손님은 계산을 할 수 없게 됩니다. 웹 서비스도 똑같아서, 한 사용자가 짧은 시간에 요청을 무한히 보내면 서버 자원이 그것만 처리하다가 정상 이용자가 응답을 받지 못하는 상황이 벌어집니다. 속도 제한(Rate Limiting)은 이런 남용을 막기 위해 일정 시간 동안 허용되는 요청 횟수를 정해 두는 방법입니다.

큰 아파트 단지의 엘리베이터를 떠올리면 이해가 쉽습니다. 관리실은 한 세대가 특정 시간대에 엘리베이터를 몇 번까지 탈 수 있는지 정해 두고, 정해진 횟수를 넘긴 세대에는 잠시 기다렸다가 다시 이용하라고 안내합니다.

여기서 세대를 구분하는 주소가 바로 사용자나 IP 단위이고, 허용 횟수를 세는 관리실의 장부가 요청 횟수를 기록하는 카운터이며, 기다리라는 안내가 요청을 잠시 거절하거나 늦추는 응답입니다. 이 장부를 얼마의 시간 동안 몇 번까지로 정할지가 정책이고, 그 정책을 서버 앞단에서 적용하면 응용 프로그램이 직접 처리해야 할 부담이 크게 줄어듭니다.

속도 제한은 시간당 요청 수나 초당 요청 수 같은 기준으로 동작하며, 웹 방화벽(WAF)에서는 이를 이용해 자동화 도구의 반복 접근이나 무차별 대입 시도를 조기에 억제합니다. 핵심은 모든 요청을 똑같이 다루지 않고, 발신 주소나 계정 단위로 허용 폭을 나누어 정상 사용과 남용을 구분하는 데 있습니다.

봇 탐지

자동화된 트래픽과 사람의 트래픽을 구분하는 방법

온라인 쇼핑몰에 실제 고객 대신 수백 개의 가상 계정이 동시에 접속해 재고를 조회하고 장바구니를 채운다면, 사람인 고객은 느려진 화면과 꺼진 버튼만 보게 됩니다. 이런 자동화된 트래픽은 사람이 눌러서 만드는 것이 아니므로 속도만 보고는 정상 방문자와 구분하기 어렵습니다. 봇 탐지(Bot Detection)는 이렇게 자동으로 움직이는 트래픽과 사람이 직접 보내는 트래픽을 구분해 내는 방법입니다.

아파트 경비실에서 방문객을 확인하는 장면을 생각해 보겠습니다. 경비원은 신분증만 보지 않고, 걷는 모습, 말투, 방문 목적을 함께 살펴 사람인지 아닌지를 판단합니다.

봇 탐지도 마찬가지로 요청 하나만 보는 것이 아니라 마우스 움직임, 화면 스크롤, 요청 사이의 간격, 브라우저 정보의 일관성 같은 여러 흔적을 함께 봅니다. 이 흔적들이 사람의 행동 패턴과 얼마나 비슷한지 점수를 매기고, 그 점수를 기준으로 정상 방문자와 자동화 도구를 나누는 것이 기본 구조입니다.

웹 방화벽(WAF)은 이렇게 모은 신호를 규칙과 평판 정보에 결합해 의심스러운 클라이언트를 식별하고, 필요하면 차단이나 추가 확인으로 넘깁니다. 결국 봇 탐지는 단일 요청의 모양이 아니라 행동의 맥락을 읽어 자동화 여부를 가려내는 기술입니다.

CAPTCHA도 마찬가지로 모든 방문자에게 묻지 않고, 행동이 의심스럽거나 요청이 몰리는 순간에만 그림 속 글자를 읽거나 도형을 맞히는 과제를 제시합니다. 사람은 이 과제를 쉽게 통과하지만 자동화 도구는 그 과정을 흉내 내기 어려워 막히게 되고, 통과한 방문자에게는 일정 시간 유효한 확인 표시가 부여됩니다.

이 확인 표시를 챌린지 토큰이라고 하며, 웹 방화벽(WAF)은 이를 발급하고 검증해 이후 요청이 사람 확인을 거쳤는지 판단합니다. 요즘은 과제 난이도를 조절하거나 아예 보이지 않게 처리하는 방식도 쓰이며, 환경에 따라 구현 형태는 달라질 수 있습니다.

스크래핑 방어

콘텐츠를 대량으로 긁어가는 행위를 막는 방법

상품 정보와 가격, 리뷰를 정성껏 쌓아 둔 쇼핑몰에 하루 만에 전체 페이지가 그대로 복제되어 다른 사이트에 올라간다면, 그 노력은 순식간에 경쟁자의 자산이 됩니다. 콘텐츠를 대량으로 긁어가는 행위를 스크래핑(Scraping)이라고 하며, 이를 막는 것이 스크래핑 방어입니다.

도서관을 비유로 들어 보겠습니다. 정상 이용자는 필요한 책 몇 권을 골라 읽지만, 누군가가 서가 전체를 사진으로 찍어 가려 한다면 사서는 대출 규칙을 두고 반복 촬영을 제지합니다.

스크래핑 방어도 같은 원리로, 한 사용자가 짧은 시간에 너무 많은 페이지를 요청하는지 세고, 요청 간격이 지나치게 규칙적인지 살피며, 로그인 없이 볼 수 있는 범위를 제한합니다. 여기에 페이지마다 사람에게는 보이지 않는 가짜 링크나 데이터를 심어 두면, 그것까지 따라가는 자동 수집 도구를 쉽게 가려낼 수 있습니다.

웹 방화벽(WAF)은 이런 요청 빈도와 접근 패턴을 규칙으로 삼아 스크래핑을 탐지하고 차단합니다. 정상 검색 엔진의 수집은 허용하면서 과도한 대량 수집만 걸러내는 균형 잡기가 이 기술의 핵심입니다.

크리덴셜 스터핑 방어

탈취된 계정 정보를 대입하는 공격을 막는 방법

다른 사이트에서 유출된 아이디와 비밀번호 목록을 그대로 가져와 우리 서비스의 로그인 창에 하나씩 대입하는 공격이 있습니다. 사용자가 여러 곳에 같은 비밀번호를 쓰는 습관을 노린 이 방식은, 단 한 번의 성공으로 실제 계정을 탈취할 수 있어 위험합니다. 크리덴셜 스터핑(Credential Stuffing) 방어는 이렇게 탈취된 계정 정보를 대입하는 공격을 막는 방법입니다.

아파트 현관 비밀번호를 무작위로 눌러 보는 사람을 떠올려 보겠습니다. 경비실은 한 집의 비밀번호를 몇 번 틀리면 잠시 입력을 막고, 같은 사람이 여러 집을 돌며 시도하는 모습을 발견하면 아예 출입을 제한합니다.

크리덴셜 스터핑 방어도 똑같이 계정 단위로 실패 횟수를 세어 일정 횟수를 넘으면 잠그고, 하나의 발신 주소가 여러 계정에 걸쳐 로그인을 시도하는지도 감시합니다. 여기에 로그인 시도 속도 제한과 의심스러운 접속에 대한 추가 확인을 결합하면, 자동 대입의 성공 확률을 크게 떨어뜨릴 수 있습니다.

웹 방화벽(WAF)은 로그인 경로에 대한 요청 패턴을 분석해 이런 대량 대입을 탐지하고 차단합니다. 여러 방어 수단을 겹쳐 두는 것이 핵심이며, 비밀번호 재사용을 줄이는 사용자 교육도 함께 필요합니다.

DDoS와 WAF

대량 트래픽 앞에서 WAF가 버틸 수 있는 범위

트래픽이 갑자기 수십 배로 늘어나 서버가 응답을 멈추면, 공격인지 단순한 인기 폭발인지 구분할 겨를도 없이 서비스는 닫히게 됩니다. 분산 서비스 거부(DDoS, Distributed Denial of Service) 공격은 여러 곳에서 동시에 대량 요청을 보내 서비스를 마비시키는 방식이며, 이때 웹 방화벽(WAF)이 어디까지 버틸 수 있는지가 중요한 질문이 됩니다.

아파트 정문에 갑자기 수천 명이 몰려든 상황을 생각해 보겠습니다. 경비원 한 명이 한 명씩 신분을 확인하는 것으로는 감당이 되지 않으므로, 단지 차원에서 정문 앞 도로를 통제하고 정해진 인원만 들여보내는 절차가 필요합니다.

마찬가지로 웹 방화벽은 요청의 내용을 검사해 악성 요청을 걸러내는 데 강하지만, 검사 자체에도 처리 능력이 필요하기 때문에 트래픽 양이 한계를 넘으면 병목이 될 수 있습니다. 그래서 실제 구조에서는 트래픽을 여러 곳에 분산해 흡수하는 서비스(CDN)나 대용량 트래픽 정화 장비를 앞단에 두고, 웹 방화벽은 걸러진 뒤 남은 요청의 내용을 검사하는 역할을 맡깁니다.

정리하면 웹 방화벽은 대량 트래픽 자체를 흡수하는 장비가 아니라 응용 계층의 요청을 검사하는 방어선이며, DDoS 대응은 앞단의 분산·정화 계층과 함께 설계해야 효과가 있습니다.

WAF 로그의 구조

어떤 필드가 남고 그 필드로 무엇을 알 수 있는지

웹 서비스가 요청을 막았는데 그 이유를 아무도 설명하지 못하면 운영자는 사용자 문의에 답할 수 없고, 공격이 실제로 들어왔는지도 확인할 수 없습니다. 그래서 WAF(Web Application Firewall)는 요청을 처리할 때마다 판단 근거를 필드 단위로 남기는데, 이것이 WAF 로그입니다. 택배 한 건마다 송장이 붙듯, WAF 로그도 요청 한 건마다 정해진 칸을 채웁니다.

시간과 출발지 IP, 요청이 향한 호스트와 경로, 사용한 메서드, 그리고 허용인지 차단인지의 판정이 기본 칸입니다. 차단이라면 어떤 규칙(rule)이 어떤 조건에서 걸렸는지를 규칙 식별자와 메시지로 함께 적고, 필요하면 헤더와 본문의 일부도 증거로 남깁니다. 이 칸들을 나란히 놓으면 누가 언제 무엇을 시도했고 시스템이 어떻게 판단했는지가 한 줄에서 재구성됩니다. 정리하면 WAF 로그는 요청의 신원, 대상, 판정, 근거를 담는 구조화된 기록이며, 사후 분석과 규칙 조정의 출발점입니다.

WAF는 로그를 파일이나 네트워크 전송(syslog)으로 수집 서버에 넘기고, 수집 서버는 전처리와 버퍼링을 거쳐 저장소와 SIEM(Security Information and Event Management)으로 전달합니다. 이때 전송이 끊겨도 유실되지 않도록 큐를 두고, 원본은 보존 기간을 정해 따로 남깁니다. 결국 수집 파이프라인은 흩어진 판정 기록을 하나의 흐름으로 모아 저장과 분석에 연결하는 배관이며, 그 신뢰성이 곧 로그의 가치입니다.

감사 로그

정책 변경 이력을 남기고 확인하는 방법

방화벽 정책이 어느 날부터 공격을 막지 못해 사고가 났는데, 누가 언제 어떤 룰을 꺼 두었는지 아무도 설명하지 못하면 원인을 찾을 수도, 같은 일이 다시 벌어지는 것을 막을 수도 없습니다. 그래서 정책을 바꾸는 모든 행위를 지워지지 않게 기록으로 남기는 장치가 감사 로그(audit log)입니다.

회사 건물의 카드키 출입 기록을 떠올려 보면 이해가 쉽습니다. 누가 어느 문을 몇 시에 열었는지가 자동으로 남듯이, 감사 로그는 변경을 요청한 계정과 시각, 바뀐 항목의 이전 값과 이후 값, 그리고 변경 사유를 한 줄로 묶어 남깁니다.

그 기록은 변경을 수행한 사람도 지울 수 없는 별도의 저장소에 쌓이고, 룰을 배포할 때마다 자동으로 생성되도록 만듭니다. 그래야 나중에 문제가 생겼을 때 무엇이 언제 달라졌는지를 되짚어 볼 수 있습니다. 정리하면 감사 로그는 방화벽 룰의 변경 이력을 계정과 시각, 변경 전후 값, 사유 단위로 보존해 사고 원인 추적과 책임 소재 확인을 가능하게 하는 기록 체계입니다. 확인 절차는 이 로그를 정기적으로 검토하고 변경 승인 절차와 대조하는 것으로 마무리됩니다.

상관 분석

WAF 로그를 다른 로그와 엮어 사건을 보는 방법

WAF 로그만 보면 차단 한 줄만 남아서, 그 요청이 실제로 성공했는지 아니면 공격자가 다른 경로로 들어왔는지 알 수 없습니다. 그래서 여러 시스템의 로그를 같은 시간축에 놓고 엮어 하나의 사건으로 묶는 상관 분석(correlation analysis)이 필요합니다.

택배 분실 사건을 조사하는 상황을 떠올려 보면 쉽습니다. 기사 앱 기록과 창고 출입 기록, 경비실 영상의 시각을 나란히 놓아야 어디서 사라졌는지 보이듯이, 상관 분석은 WAF 로그에 웹 서버 접근 로그, 인증 로그, 데이터베이스 감사 로그를 같은 요청 식별자와 시각으로 이어 붙입니다.

이렇게 이어 붙인 묶음이 하나의 사건이 되고, 탐지 규칙은 그 사건 안에서 특정한 순서가 나타날 때 경보를 냅니다. 시간 동기화와 식별자 통일이 갖춰져야 연결이 끊기지 않습니다. 정리하면 상관 분석은 서로 다른 로그를 시간과 식별자로 연결해 단일 요청을 하나의 사건으로 재구성하는 분석 기법입니다. WAF는 막았는지 여부를, 다른 로그는 실제로 영향을 받았는지 여부를 답해 주므로 둘을 합쳐야 판단이 완성됩니다.

포렌식

침해 사고 때 WAF 로그로 흔적을 재구성하는 방법

침해 사고가 터진 뒤에 WAF 화면에는 차단 건수만 남아 있어서 공격자가 어떤 요청으로 들어왔고 무엇을 가져갔는지 설명할 수 없는 경우가 많습니다. 그래서 사고 흔적을 시간 순서대로 되살리는 포렌식(forensics) 작업에서 WAF 로그가 중요한 재료가 됩니다.

집에 도둑이 든 뒤 현관 기록과 방문자 장부를 겹쳐 보는 상황을 떠올리면 비슷합니다. 언제 누가 들어왔고 어느 문이 열려 있었는지를 시간순으로 맞춰야 동선이 그려지듯이, 포렌식은 WAF의 요청 기록과 차단·통과 판정, 웹 서버 응답 코드, 인증 성공 시각을 같은 시간축에 놓고 순서를 재구성합니다.

이때 로그가 덮어써지지 않도록 보존 기간과 무결성을 미리 정해 두어야 증거로 쓸 수 있습니다. 통과된 요청과 차단된 요청을 함께 봐야 진짜 성공한 침입이 드러납니다. 정리하면 포렌식은 WAF 로그를 포함한 여러 기록을 시간축으로 정렬해 침해 경로와 범위를 밝히는 사후 분석 절차입니다. 평소에 보존 기간과 원본 보관 방식을 정해 두는 것이 이 절차의 성패를 가릅니다.

개인정보와 로그

요청 본문을 남길 때의 위험과 마스킹 방법

요청 본문을 그대로 로그에 남기면 비밀번호나 주민등록번호 같은 값이 평문으로 쌓여, 로그 저장소가 곧 개인정보 유출 창구가 됩니다. 그래서 본문을 남길 때는 무엇을 남기고 무엇을 가릴지 정하는 마스킹(masking) 규칙이 필요합니다.

택배 송장을 보관할 때 받는 사람 전화번호 가운데 자리를 가리는 것과 같습니다. 송장에 이름과 주소는 남겨도 민감한 번호는 가려 두듯이, 마스킹은 정해진 필드 이름을 찾아 값을 별표로 바꾸거나 해시(hash) 값으로 대체한 뒤에 저장합니다.

비밀번호와 카드 번호처럼 아예 남기면 안 되는 항목은 기록 대상에서 제외하는 것이 원칙입니다. 보존 기간을 짧게 잡고 접근 권한을 최소 인원으로 제한하는 것도 함께 갖춰야 합니다. 정리하면 개인정보를 지키는 로그 설계는 수집 항목 최소화, 민감 값 마스킹, 보존 기간과 접근 권한 제한이라는 세 가지 축으로 정리됩니다. 사고 조사에 필요한 정보와 개인정보가 겹치는 지점을 미리 표시해 두면 이 균형을 잃지 않습니다.

룰 업데이트 주기

새로 나온 공격에 맞춰 룰을 갱신하는 주기와 절차

새 공격 기법이 나온 뒤에 룰이 몇 달씩 그대로라면, 방화벽은 최신 공격 앞에서 이름만 남은 장비가 됩니다. 그래서 새로 알려진 공격에 맞춰 룰을 갱신하는 주기와 절차를 미리 정해 두어야 합니다.

백신 접종 시기를 정해 두고 맞는 것과 비슷합니다. 유행하는 병이 바뀌면 맞는 백신도 바뀌듯이, 룰 갱신은 공급처가 배포하는 최신 룰 묶음을 받아 테스트 환경에서 먼저 적용해 보고, 오탐이 늘지 않는지 확인한 뒤 운영 환경에 반영하는 순서로 진행합니다.

긴급도가 높은 공격은 즉시 반영하는 빠른 경로를 따로 두고, 일반 갱신은 정해진 주기에 맞춰 묶어서 처리합니다. 반영 뒤에는 차단 건수와 오탐 신고 추이를 며칠간 지켜봅니다. 정리하면 룰 업데이트는 공급처 배포, 테스트 적용, 오탐 확인, 운영 반영, 사후 관찰이라는 다섯 단계를 정해진 주기로 반복하는 운영 절차입니다. 주기만 정하고 검증 절차를 두지 않으면 갱신이 곧 장애가 됩니다.

WAF 장애 대응

WAF 자체에 문제가 생겼을 때의 판단과 조치

WAF 자체가 응답하지 않으면 모든 웹 요청이 함께 멈출 수 있어서, 방화벽을 세운 일이 서비스 전체를 멈추는 단일 장애점이 됩니다. 그래서 WAF에 문제가 생겼을 때 무엇을 먼저 판단하고 어떻게 조치할지 미리 정해 두어야 합니다.

아파트 정문 경비원이 갑자기 자리를 비운 상황과 비슷합니다. 경비원이 없으면 출입을 전면 통제할지, 임시로 문을 열어 두고 순찰을 늘릴지 결정해야 하듯이, WAF 장애 때는 서비스를 막는 차단 모드와 통과시키는 통과 모드(fail open) 중 어느 쪽으로 갈지 정한 정책에 따라 움직입니다.

서비스 중단이 더 큰 손실이면 통과 쪽으로 두되 임시로 다른 계층의 방어를 강화하고, 그 사실을 즉시 기록하고 알립니다. 원인 파악은 최근 배포된 룰과 설정 변경 이력을 먼저 확인하는 순서로 좁혀 갑니다. 정리하면 WAF 장애 대응은 단일 장애점 인식, 차단과 통과 모드 결정, 임시 대체 방어, 변경 이력 확인이라는 네 가지 판단으로 구성됩니다. 장애를 복구한 뒤에는 반드시 원인과 조치를 감사 로그와 함께 남겨 다음 장애를 줄입니다.

페일오픈과 페일클로즈

WAF 고장 시 통과시킬지 막을지 선택하는 기준

WAF가 갑자기 멈추거나 내부 오류가 나면 트래픽을 검사할 수 없는 순간이 생깁니다. 그때 모든 요청을 그냥 통과시킬지 아니면 전부 차단할지 미리 정해 두지 않으면, 서비스는 엉뚱한 방향으로 무너집니다. 이 선택 규칙을 각각 페일오픈(fail-open)과 페일클로즈(fail-close)라고 부릅니다.

아파트 정문 경비실에 비유하면 이해가 쉽습니다. 경비원이 잠시 자리를 비웠을 때 주민과 택배를 모두 그냥 들여보내는 것이 페일오픈이고, 문을 잠그고 아무도 못 들어오게 하는 것이 페일클로즈입니다.

페일오픈은 서비스가 계속 돌아가지만 검문이 사라진 틈을 내주고, 페일클로즈는 안전을 지키는 대신 정상 주민까지 문 앞에서 막히게 합니다. 그래서 결제와 개인정보처럼 사고가 크게 번지는 업무는 페일클로즈를, 공개 안내 페이지처럼 막힘의 손해가 더 큰 곳은 페일오픈을 고르는 식으로 업무별로 기준을 나눕니다.

정리하면 페일오픈은 장애 시 검사를 건너뛰고 통과시키는 정책, 페일클로즈는 장애 시 차단을 유지하는 정책이며, 어느 쪽이 무조건 옳다기보다 서비스가 감당할 수 있는 위험과 손실을 먼저 정해 두는 것이 핵심입니다.

설정 백업

WAF 정책을 내보내고 보관하는 방법

WAF 정책은 수백 줄의 규칙과 예외, 차단 목록이 얽힌 결과물이라 누군가 규칙 하나를 잘못 지우는 것만으로도 서비스가 뚫리거나 막힙니다. 그런데 그 정책을 따로 복사해 두지 않으면 사고가 난 뒤 무엇이 원래 설정이었는지 알 방법이 없습니다. 그래서 정책을 파일로 내보내 보관하는 설정 백업(backup)이 필요합니다.

회사 문서 서랍에 비유할 수 있습니다. 계약서 원본을 서랍에 넣어 두고 사본은 다른 층 금고에 두듯, WAF의 현재 정책 전체를 설정 파일 형태로 내보내고 날짜와 버전을 붙여 별도 저장소에 둡니다.

내보낼 때는 규칙 본문뿐 아니라 적용 순서, 예외 처리, 로그 설정까지 함께 담아야 나중에 같은 동작을 재현할 수 있습니다. 그리고 정책을 바꾸기 전에는 반드시 백업을 먼저 뜨고, 보관본이 실제로 열리는지 주기적으로 확인합니다. 백업 파일은 암호화하고 접근 권한을 좁혀, 정책을 되돌리려는 사람과 정책을 가져가려는 사람을 모두 관리합니다.

설정 백업은 WAF 정책을 재현 가능한 파일로 내보내 날짜와 버전을 붙여 안전한 곳에 보관하는 작업이며, 변경 전 백업과 정기 검증이 함께 있을 때 비로소 쓸모가 있습니다.

설정 복구

백업으로 정책을 되돌리는 절차와 확인 방법

규칙을 잘못 올린 뒤 오탐이 쏟아지거나 업그레이드 직후 정책이 초기화되어 버리면 서비스는 몇 분 만에 마비됩니다. 그때 처음부터 규칙을 다시 짜는 것은 사실상 불가능하므로, 미리 떠 둔 설정을 다시 불러오는 절차가 있어야 합니다. 이것이 설정 복구(restore)입니다.

이사할 때 가구 배치도를 보고 집을 원래대로 되돌리는 일과 비슷합니다. 배치도에 해당하는 백업 파일을 펴고, 지금 집 구조에 해당하는 장비 모델과 소프트웨어 버전이 그때와 같은지 먼저 확인한 뒤, 가구를 하나씩 제자리에 놓듯 정책을 순서대로 적용합니다.

복구는 한 번에 전부 밀어 넣기보다 검사 모드에서 먼저 적용해 정상 트래픽이 막히지 않는지 보고, 문제가 없을 때 차단 모드로 전환합니다. 또한 복구 전 현재 상태도 따로 백업하고, 복구 후에는 규칙 개수와 적용 순서, 로그 적재 여부를 항목별로 대조해 확인합니다.

설정 복구는 백업 파일로 정책을 되돌리는 절차이며, 환경 일치 확인과 검사 모드 선적용, 복구 후 항목 대조라는 세 단계를 거칠 때 안전하게 끝납니다.

WAF도 평균 처리량이 아니라 피크 시간대의 초당 요청 수와 동시 연결 수를 기준으로 잡고, 검사 깊이에 따라 요청당 비용이 달라지므로 여유율을 더합니다. 또한 장비를 이중화하면 한 대가 멈췄을 때 남은 한 대가 전체 부하를 받게 되므로 이 경우까지 계산에 넣습니다. 여기에 로그 저장 공간과 향후 트래픽 증가분을 반영해 최종 사양을 정합니다.

용량 산정은 피크 시간대의 초당 요청 수와 동시 연결 수를 기준으로 검사 비용과 여유율을 더해 장비 사양을 정하는 작업이며, 평균값이 아니라 최대 부하를 보는 것이 핵심입니다.

WAF에서는 규칙 수와 정규식 사용, 대용량 요청 본문 검사, 로그 기록량, 연결 재사용 설정을 주로 봅니다. 측정은 평균이 아니라 느린 요청의 상위 구간을 봐야 원인이 드러납니다. 또한 WAF를 잠시 우회한 경로와 비교해 지연이 WAF 구간에서 늘어난 것인지 확인하면 원인 후보를 크게 줄일 수 있습니다.

성능 저하를 찾을 때는 뒤쪽 서버와 WAF, 네트워크 구간을 나눠 측정하고 규칙 복잡도와 검사 대상 크기, 로그 부하를 순서대로 확인하는 것이 정석입니다.

신뢰 프록시와 전달 헤더

X-Forwarded-For 값을 믿어도 되는지 판단하는 방법

웹 서비스가 로드 밸런서나 CDN 뒤에 놓이면 서버가 보는 접속 주소는 실제 방문자의 것이 아니라 중간 장비의 것이 됩니다. 그 상태에서 WAF(웹 애플리케이션 방화벽)가 차단 규칙을 적용하면 모든 요청이 같은 주소에서 온 것처럼 보여 한 사람의 공격이 전체 사용자의 차단으로 번지고, 반대로 공격자 한 명만 골라 막을 수도 없습니다. 그래서 중간 장비가 원래 방문자의 주소를 X-Forwarded-For 같은 전달 헤더(forwarded header)에 적어 넘기고, WAF는 그 값을 참고해 판단합니다. 이 구조는 택배와 비슷합니다. 집 앞 경비실이 모든 택배를 대신 받으면 입주민은 보낸 사람이 누구인지 알 수 없으니, 경비실이 운송장에 원래 보낸 사람 이름을 적어 두는 셈입니다.

그런데 이 운송장은 누구나 종이를 바꿔 쓸 수 있어서, 택배를 보내는 사람이 자기 이름 옆에 아무 이름이나 적어 넣을 수 있습니다. 전달 헤더도 요청을 보내는 쪽이 직접 조작할 수 있는 값이라, 아무 검증 없이 믿으면 공격자가 자기 주소를 남의 주소로 위장해 차단을 피하거나 남을 차단시키는 일이 생깁니다. 해결의 핵심은 이 헤더를 누가 붙였는지 구분하는 것입니다. 서버는 자기가 신뢰한다고 등록한 프록시(trusted proxy)의 주소 목록을 정해 두고, 요청이 정말 그 장비를 거쳐 왔을 때만 헤더 값을 인정하며, 그 앞에 붙은 값은 무시하고 오른쪽에서부터 신뢰 경계를 따라가며 실제 주소를 고릅니다. 결국 전달 헤더는 신뢰 프록시 목록과 함께 설정해야 의미가 있고, 그 목록을 넓게 잡으면 WAF의 모든 주소 기반 판단이 무력해진다는 점이 요점입니다.

보안 사고도 마찬가지로 WAF 경보와 로그로 침해 여부를 확인하고, 해당 경로나 계정을 임시로 차단해 피해를 좁히고, 관련 서비스와 고객에게 알린 다음, 보존한 로그로 침입 경로를 재구성합니다. 마지막으로 재발을 막을 규칙과 패치를 반영하고, 그 결과를 다음 대응 때 쓸 수 있게 문서로 남깁니다. 정리하면 사고 대응은 탐지, 차단과 격리, 통보, 원인 분석, 재발 방지, 기록의 순서를 따르며, WAF는 이 흐름에서 차단 규칙과 감사 로그(audit log)를 동시에 제공하는 역할을 합니다. 순서를 미리 정해 두고 연습해 두지 않으면 실제 사고 때 판단이 늦어지고 증거가 사라진다는 것이 이 절차의 존재 이유입니다.

WAAP는 이처럼 웹 요청 검사, API 요청의 형식과 권한 확인, 봇의 행동 패턴 판별, 대량 트래픽 흡수를 하나의 정책 체계로 묶어 운영합니다. 결국 WAAP는 WAF를 대체하는 새 장비가 아니라, 방어 범위를 웹에서 API와 자동화 트래픽과 가용성까지 넓힌 상위 개념입니다. 보호 대상이 늘어난 만큼 정책도 한 곳에서 일관되게 관리해야 하며, 어느 한 축만 설정해 두고 나머지를 비워 두면 전체 방어에 구멍이 생깁니다.

오랫동안 보안은 회사 내부 네트워크는 안전하고 바깥은 위험하다는 전제 위에 서 있었습니다. 그런데 재택 근무와 클라우드가 퍼지면서 내부망 안에도 침입자가 있고, 외부에서 정상적으로 일하는 사람도 많아져 이 전제가 무너졌습니다. 제로 트러스트(zero trust)는 위치가 아니라 매 요청의 신원과 상태를 확인하자는 원칙이고, WAF는 그 원칙이 웹 요청 단위에서 실제로 작동하는 지점 중 하나입니다. 사무실 출입으로 비교하면 이해가 쉽습니다. 예전에는 한 번 정문을 통과하면 건물 안을 자유롭게 다닐 수 있었지만, 제로 트러스트 건물은 방마다 문이 있고 들어갈 때마다 사원증과 방문 목적을 다시 확인합니다.

WAF는 이 방마다 서 있는 검사원처럼 요청마다 누가 보냈는지, 무엇을 하려는지, 지금 허용된 사용자인지를 확인하고 통과 여부를 판단합니다. 그래서 인증 토큰 검사, 세션 상태 확인, 요청 형식 검증 같은 요소가 WAF 정책에 함께 들어갑니다. 정리하면 제로 트러스트는 신뢰의 기준을 네트워크 위치에서 신원과 요청 맥락으로 옮기는 원칙이고, WAF는 그 원칙을 매 요청 검사로 구현하는 도구입니다. WAF만 도입한다고 제로 트러스트가 완성되는 것은 아니며, 인증과 권한 관리 체계가 함께 갖춰져야 검사 결과가 의미를 가집니다.

서비스 메시와 WAF

사이드카와 게이트웨이에서 검사하는 방식

서비스가 수십 개로 쪼개지면 서로 주고받는 내부 통신이 폭발적으로 늘어나는데, 그 통신에는 WAF가 지켜 주지 않는 구간이 생깁니다. 외부에서 들어오는 요청은 막아도 서비스 사이를 오가는 요청이 오염되어 있으면 내부에서 피해가 번지고, 각 서비스마다 보안 설정을 따로 넣으면 빠뜨리는 곳이 반드시 나옵니다. 서비스 메시(service mesh)는 이 통신을 각 서비스 옆에 붙은 작은 대리 프로세스로 통일해 처리하고, 그 지점에 검사 기능을 넣어 내부 구간까지 방어를 확장합니다. 이 구조는 아파트 단지의 우편함과 비슷합니다. 각 세대 앞에 우편함을 두고 관리사무소가 모든 우편함의 배달 규칙을 한꺼번에 관리하면, 세대마다 따로 규칙을 정할 필요가 없습니다.

서비스 메시에서는 서비스 옆에 붙는 사이드카(sidecar)라는 보조 프로세스가 우편함 역할을 하고, 단지 입구 격인 게이트웨이(gateway)가 외부에서 오는 요청을 먼저 검사합니다. 검사 정책을 한 곳에서 배포하면 사이드카와 게이트웨이가 같은 규칙을 따르므로, 어떤 서비스가 새로 생겨도 빠짐없이 적용됩니다. 결국 서비스 메시 환경에서의 WAF는 별도 장비 한 대가 아니라 게이트웨이와 사이드카에 분산되어 요청마다 검사하는 형태가 됩니다. 다만 사이드카 검사는 부하와 지연을 늘릴 수 있어, 모든 통신을 다 검사할지 중요한 구간만 검사할지 정책으로 정해 두는 판단이 필요합니다.

상호 TLS(mTLS)

인증서로 클라이언트를 확인하는 방법

서버가 자기 신분을 인증서로 증명하는 것만으로는 부족한 순간이 있습니다. 서버는 접속한 클라이언트가 정말 그 서비스가 맞는지 알 방법이 없어서, 내부 API 주소를 알아낸 다른 프로그램이 정당한 서비스인 척 요청을 보내도 구분하지 못합니다. 상호 TLS(mutual TLS)는 이때 서버와 클라이언트가 서로 인증서를 주고받아 양쪽 신원을 모두 확인하는 방식입니다. 이것은 회사 간 계약 창구와 같습니다. 방문자가 상대 회사의 사원증을 확인하는 것만으로는 부족하고, 상대도 우리 쪽 담당자의 사원증을 확인해야 거래가 성립합니다.

mTLS에서는 양쪽이 각자 인증서를 제시하고, 상대 인증서가 신뢰하는 발급 기관의 것인지 확인한 뒤에야 암호화된 통신을 시작합니다. 그래서 인증서를 발급하고 회수하는 관리 체계와, 어느 인증서를 신뢰할지 정하는 신뢰 저장소가 함께 필요합니다. 정리하면 상호 TLS는 TLS 연결에서 서버 인증에 그치지 않고 클라이언트 인증서까지 검증해 통신 양쪽의 신원을 확정하는 방식입니다. 서비스 간 통신이나 관리자 접속처럼 상대를 확실히 가려야 하는 구간에 주로 쓰이며, 인증서가 유출되면 신원 확인이 뚫리므로 발급과 폐기 관리가 방어의 절반을 차지합니다.

시크릿 관리

WAF 설정에 담긴 키와 토큰을 안전하게 다루는 방법

WAF 설정 파일에 인증 키나 접근 토큰을 그대로 적어 두면, 그 파일을 백업하거나 저장소에 올리는 순간 비밀 값이 함께 복사되어 누구나 읽을 수 있게 됩니다. 이런 유출은 방화벽이 막아 주는 외부 공격이 아니라 방화벽 자체의 열쇠가 새는 일이므로, 설정에 들어가는 비밀 값을 따로 보관하고 필요할 때만 불러 쓰는 시크릿 관리(secret management)가 필요합니다.

아파트 관리실에는 현관 비밀번호와 창고 열쇠, 설비 점검 계정이 모두 적힌 장부가 있는데, 이 장부를 게시판에 붙여 두면 경비를 세우는 의미가 사라집니다. 대신 열쇠는 중앙 금고에 넣어 두고, 필요한 사람이 본인 확인을 거쳐 잠깐 꺼내 쓰고 바로 반납하게 합니다.

WAF도 같은 방식으로, 설정에는 비밀 값 자체가 아니라 금고에서 꺼내 오라는 참조만 적고 실제 값은 접근 권한이 통제된 별도 저장소에서 구동 시점에 주입합니다. 이렇게 하면 설정 파일이 복사되거나 유출되어도 바로 쓸 수 있는 열쇠가 남지 않고, 누가 언제 꺼내 갔는지 기록도 남습니다.

결국 시크릿 관리는 설정과 비밀 값을 분리하고, 비밀 값은 접근 통제와 감사 기록이 있는 저장소에서 짧게 빌려 쓰게 만드는 일입니다.

취약점 관리와의 연계

스캐너 결과와 WAF 룰을 연결하는 방법

애플리케이션 취약점 스캐너가 결함 목록을 뽑아 냈는데 그 결과가 문서 폴더에만 쌓이면, WAF는 그 결함이 있다는 사실을 모른 채 요청을 계속 통과시킵니다. 스캐너의 발견과 방화벽의 차단 규칙을 이어 주는 취약점 관리 연계가 있어야 발견이 실제 방어로 바뀝니다.

건강검진과 처방에 비유하면, 검진 결과지에 혈압이 높다고 적혀 있어도 담당 의사가 그 종이를 보지 못하면 약이 나가지 않습니다. 검진 결과가 진료 기록으로 넘어가고, 의사가 그 기록을 보고 처방을 내며, 다음 검진에서 약효를 확인하는 흐름이 한 줄로 이어져야 합니다.

취약점 관리 연계도 마찬가지로, 스캐너가 결함의 위치와 공격 방식을 정해진 형식으로 넘기고, WAF는 그 정보를 근거로 해당 결함을 노리는 요청 패턴에 규칙을 걸며, 이후 스캔에서 그 결함이 다시 잡히는지로 규칙의 효용을 확인합니다. 이때 결함 번호와 규칙 번호를 서로 대응시켜 두면, 나중에 코드가 고쳐졌을 때 어떤 규칙을 걷어낼지도 추적할 수 있습니다.

정리하면 취약점 관리 연계는 스캐너의 발견, WAF의 규칙, 재검증 결과를 같은 식별자로 묶어 관리하는 절차입니다.

가상 패치(Virtual Patching)

코드를 고치지 않고 취약점을 가리는 방법

쇼핑몰 코드에서 입력 검증 결함이 발견됐는데 수정 배포가 다음 달 정기 배포에나 가능하다면, 그동안 공격자는 같은 지점을 마음껏 두드려 볼 수 있습니다. 코드를 고치지 않고 WAF 규칙으로 그 결함을 노리는 요청만 걸러내는 가상 패치(virtual patching)가 이 공백을 메웁니다.

아파트 현관 유리문에 금이 갔는데 새 유리를 주문하려면 몇 주가 걸린다고 해 봅니다. 그동안 문을 못 쓰게 둘 수는 없으니, 금 간 자리 앞에 임시 차단판을 대고 그 틈으로 손이 들어오지 못하게 합니다.

가상 패치는 이 임시 차단판과 같아서, 취약한 기능 자체는 그대로 두되 그 기능으로 들어오는 위험한 요청만 WAF가 먼저 가로막습니다. 다만 차단판은 문을 새로 다는 것이 아니므로, 정식 수정이 배포되면 규칙을 걷어내고 실제 코드를 고쳐야 하며, 우회 경로가 없는지도 함께 확인해야 합니다.

결국 가상 패치는 정식 패치가 나오기 전까지의 임시 방어이며, 취약점을 없애는 것이 아니라 공격이 닿는 길을 좁히는 조치입니다.

WAF 효과 측정

차단 건수가 아니라 위험 감소로 성과를 평가하는 방법

WAF 성과를 차단 건수로만 보고하면, 트래픽이 늘어서 함께 늘어난 숫자를 성과로 착각하기 쉽습니다. 심한 경우에는 잘못 만든 규칙이 정상 사용자를 막은 것도 차단 건수로는 그럴듯하게 보입니다. 그래서 성과는 막은 횟수가 아니라 위험이 얼마나 줄었는지로 재야 합니다.

아파트 경비실에 비유하면, 순찰 중에 문을 잠근 횟수를 세는 것은 성과가 아닙니다. 중요한 것은 실제로 열려 있던 문이 몇 개였고, 그 문이 잠긴 뒤 도난 시도가 얼마나 줄었는지입니다.

WAF도 같은 방식으로, 보호 대상 자산과 그 자산을 노리는 공격의 성공 가능성, 규칙이 그 경로를 얼마나 좁혔는지를 짝지어 봐야 합니다. 오탐으로 정상 거래가 막힌 비율과 차단 뒤에 우회 시도가 늘었는지도 함께 봐야 숫자가 성과로 둔갑하지 않습니다.

정리하면 WAF 효과 측정은 차단량이 아니라 노출된 위험의 감소와 정상 트래픽이 입은 피해를 함께 저울질하는 일입니다.

WAF 자체 보안 테스트

WAF를 공격해 탐지와 차단을 검증하는 방법

WAF를 켜 두었다는 사실만으로는 어떤 공격을 실제로 잡는지 알 수 없습니다. 규칙 순서가 어긋나 있거나 예외 설정이 넓게 열려 있으면 탐지가 조용히 비켜 갈 수 있습니다. 그래서 일부러 공격을 흘려 보내 탐지와 차단이 동작하는지 확인하는 자체 보안 테스트가 필요합니다.

아파트 방범 테스트에 비유하면, 경비원을 배치했다고 끝이 아니라 일부러 잠그지 않은 창문을 찾아보고 실제로 경보가 울리는지 확인하는 절차가 필요합니다. 어떤 창문이 열려 있었는지, 경보가 몇 초 만에 울렸는지, 출동이 제대로 이어졌는지를 차례로 봅니다.

WAF 테스트도 같은 방식으로, 알려진 공격 패턴을 차단되어야 할 구간과 정상 구간에 나눠 보내고, 막혀야 할 요청이 통과하지 않는지 정상 요청이 함께 막히지는 않는지를 확인합니다. 테스트는 운영 환경이 아니라 별도 검증 환경에서 먼저 하고, 결과는 규칙 번호와 함께 기록해 두어야 나중에 규칙을 바꿀 때 비교 기준이 됩니다.

결국 WAF 자체 보안 테스트는 방어 장비를 공격자 입장에서 두드려 보고 탐지와 차단의 빈틈을 미리 찾는 점검입니다.

학습 로드맵

배운 내용을 실무 순서로 다시 정리하는 방법

WAF를 배울 때 규칙 문법부터 외우면 정작 현장에서 무엇을 먼저 손대야 하는지 알기 어렵습니다. 배운 조각을 실무 순서로 다시 엮어 주는 학습 로드맵이 있어야 지식이 일이 됩니다.

요리를 배우는 사람에 비유하면, 칼 잡는 법과 재료 손질을 따로 배우는 것만으로는 한 끼가 나오지 않습니다. 장을 보고, 재료를 다듬고, 순서대로 불을 조절하고, 마지막에 간을 보는 흐름을 한 번 끝까지 해 봐야 몸에 붙습니다.

WAF 학습도 같은 순서를 따르면 좋습니다. 먼저 보호할 서비스와 트래픽 흐름을 파악하고, 그다음 요청이 어느 지점을 지나는지 확인한 뒤, 기본 규칙을 켜고 오탐을 줄이며, 마지막으로 효과 측정과 자체 테스트로 되돌아봅니다. 이때 각 단계마다 무엇을 근거로 판단했는지 적어 두면 다음 서비스에 같은 순서를 다시 적용하기 쉬워집니다.

정리하면 학습 로드맵은 문법 암기가 아니라 파악, 배치, 조정, 검증의 순환을 실제 서비스 하나로 끝까지 돌려 보는 훈련입니다.
