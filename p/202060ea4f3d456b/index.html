이어서 읽기
1CloudFront가 무엇이고 요청이 어떻게 처리되는가이후 모든 설정은 '엣지에서 요청을 받아 오리진으로 간다'는 흐름 위에 얹히므로, 그 흐름과 용어가 먼저다.52배포를 이루는 구성 요소캐싱·보안·엣지 함수 모두 '어떤 오리진의 어떤 캐시 동작에 붙이는가'로 설정되므로, 그 뼈대를 먼저 세운다.63캐싱을 제어하는 정책들CloudFront를 쓰는 이유 자체가 캐싱이고, 정책 3종은 이후 요청·응답 동작 이해의 전제다.74요청과 응답이 실제로 어떻게 오가는가정책을 설정한 뒤 '왜 이 헤더가 사라졌지', '왜 502가 나지'를 풀려면 CloudFront의 전달 규칙을 알아야 한다.55캐시된 콘텐츠를 바꾸는 법캐싱을 이해한 직후에 '그럼 바뀐 파일은 어떻게 반영하나'가 바로 따라온다.36가용성과 성능을 끌어올리는 장치기본 전달이 동작한 다음에 붙이는 것들이고, 오리진·캐시 동작 개념을 전제로 한다.57내 도메인으로 서비스하고 HTTPS를 강제하기실서비스 전환의 필수 관문이며, 이후 인증서 기반 mTLS·테넌트 인증서의 전제가 된다.58누가 무엇에 접근할 수 있는지 통제하기오리진·캐시 동작·HTTPS가 서 있어야 그 위에 접근 제어를 얹을 수 있다.99엣지에서 코드로 요청을 바꾸기정책만으로 안 되는 로직을 다루는 단계라, 캐시 키·요청/응답 동작·접근 제어를 모두 전제한다.910여러 도메인을 한 설정으로: 멀티테넌트 배포표준 배포의 모든 설정을 이해한 뒤라야 '무엇을 상속하고 무엇을 덮어쓰는가'가 의미를 갖는다.511관측: 지표, 로그, 비용운영 단계의 도구이며, 앞의 모든 기능이 무엇을 남기는지 알아야 읽을 수 있다.512미디어 전송, 문제 해결, 운영 한계특수 워크로드와 장애 대응은 앞의 모든 개념을 조합해 읽는 마무리 단계다.5

CDN으로서의 CloudFront와 대표 사용 사례

CloudFront는 전 세계 엣지 서버에 콘텐츠를 캐시해 사용자와 가까운 곳에서 빠르게 전달하는 AWS의 CDN 서비스로, 정적 파일 배포·동적 API 가속·동영상 스트리밍 등에 쓰인다.

#1문제 상황

웹 사이트나 애플리케이션의 콘텐츠(이미지, 동영상, API 응답 등)를 사용자에게 전달할 때, 기존 방식은 모든 요청이 원본 서버 하나로 집중된다. 사용자가 지구 반대편에 있으면 거리가 멀어 응답이 느려지고, 여러 사용자가 동시에 요청하면 원본 서버의 부하가 급증한다.

#2핵심 질문

전 세계 어디에 있는 사용자든 동일하게 빠르게 콘텐츠를 받으려면 어떻게 해야 할까?

#3동작 예시

미국에 있는 웹 서버에서 호스팅되는 이미지를 한국 사용자가 요청했을 때, CloudFront는 한국 지역의 엣지 로케이션(캐시 서버)에 이미지의 복사본을 저장해두었다가 그곳에서 즉시 전달한다.

#4동작 과정

  1. 오리진 등록CloudFront에 원본 콘텐츠가 있는 서버 주소를 지정
  2. 전 세계 엣지 배치AWS가 운영하는 200개 이상의 엣지 로케이션에 콘텐츠 복사본 자동 배포
  3. 사용자 요청 처리사용자는 자신과 가장 가까운 엣지에서 빠르게 콘텐츠를 받음

#5한 줄 요약

CloudFront는 원본 서버의 콘텐츠를 전 세계 엣지 서버에 캐시해 사용자와 가장 가까운 곳에서 빠르게 전달하는 AWS의 콘텐츠 전달 네트워크(CDN) 서비스입니다.

#3동작 예시

#4동작 과정

  1. POP(엣지 로케이션)에서 요청 수신사용자에게 지리적으로 가장 가까운 엣지 로케이션이 요청을 받음
  2. 리전 엣지 캐시 확인엣지 로케이션에 콘텐츠가 없으면 더 큰 용량의 리전 엣지 캐시에서 조회
  3. 원본 서버 접근리전 엣지 캐시에도 없으면 원본 서버에서 콘텐츠를 가져와 캐시 계층에 저장

  3. 재사용같은 정책을 다른 배포의 캐시 동작에도 붙일 수 있어서 일관성 있는 캐시 설정을 유지합니다.

오리진 요청에 항상 붙일 사용자 지정 헤더를 설정하는 방법과, CloudFront가 뷰어 정보(국가·디바이스 등)를 담아 자동으로 추가하는 헤더들.

→ 03-02 참조

#1문제 상황

기존에는 뷰어의 요청 헤더를 그대로 오리진에 보냈는데, 이렇게 하면 뷰어가 조작할 수 있는 헤더(예: Host, User-Agent)도 함께 가기 때문에 오리진이 신뢰할 수 없다. 또한 요청자의 지역, 디바이스 정보 같은 것을 오리진이 자동으로 알 수 없었다.

#2핵심 질문

오리진에 항상 특정 값을 붙여서 보내고, 동시에 뷰어 정보를 자동으로 전달할 수 있을까?

#3동작 예시

모든 오리진 요청에 Authorization 헤더를 CloudFront가 자동으로 붙여서 오리진이 이 값으로 CloudFront의 정당한 요청인지 검증하도록 할 수 있다. 동시에 CloudFront-Viewer-Country 헤더를 덧붙여 요청자의 국가를 오리진이 알 수 있게 한다.

#4동작 과정

  1. 커스텀 헤더 설정배포 설정에서 오리진 커스텀 헤더로 항상 보낼 값들(예: Authorization, X-Custom-Key)을 정의한다.
  2. CloudFront 전용 헤더 추가CloudFront는 자동으로 CloudFront-Viewer-Country(국가), CloudFront-Is-Mobile-Viewer(모바일 여부), CloudFront-Is-Desktop-Viewer(데스크톱 여부) 같은 헤더를 덧붙인다.
  3. 오리진으로 전달커스텀 헤더와 자동 헤더를 모두 포함한 요청이 오리진에 도착한다.

Range GET과 압축 전송

파일의 일부 구간만 요청하는 Range GET을 CloudFront가 처리하는 방식과, 응답을 gzip·Brotli로 압축해 전송량을 줄이는 기능.

#1문제 상황

일반적으로 클라이언트가 파일을 요청하면 서버는 전체 파일을 처음부터 끝까지 전송한다. 대용량 파일(예: 영상)을 재생할 때 특정 시점부터 보거나, 끊긴 다운로드를 이어받을 수 없다. 또한 압축 없이 전송하면 네트워크 대역폭을 낭비한다.

#2핵심 질문

서버 리소스 낭비 없이 원하는 파일의 일부만 받고, 데이터를 압축해서 전송량을 줄일 수 있을까?

#3동작 예시

HTTP Range 헤더를 요청에 포함시키면 "1000바이트부터 2000바이트까지만 달라"고 명시할 수 있다. CloudFront는 이 요청을 받으면 지정된 범위만 오리진에서 가져와 회신한다. 동시에 응답을 gzip이나 Brotli로 압축해서 전송 크기를 40~70% 줄인다.

#4동작 과정

  1. Range 요청 수신클라이언트가 Range: bytes=1000-2000 헤더를 담아 요청하면 CloudFront 엣지는 이를 인식한다.
  2. 오리진에 부분 요청 전달CloudFront는 캐시에 해당 범위가 없으면, 같은 Range를 포함해 오리진에 요청해 필요한 부분만 받는다.
  3. 압축 적용 및 응답받은 데이터를 gzip(또는 Brotli)으로 압축한 뒤 206 Partial Content 상태 코드와 함께 클라이언트에게 돌려준다.

대용량 파일을 부분 단위로 전송하고 압축으로 네트워크 트래픽을 줄임으로써 대역폭 효율과 사용자 경험을 동시에 개선하는 것

오리진이 돌려준 3xx·4xx·5xx 응답을 CloudFront가 어떻게 다루는지와, 사용자에게 보여줄 자체 오류 페이지를 지정하는 방법.

#1문제 상황

오리진 서버가 오류를 반환하면(404, 500 등) CloudFront는 기본적으로 그 오류 응답을 그대로 클라이언트에게 전달한다. 이 경우 사용자는 딱딱한 기본 오류 메시지만 본다. 서비스 브랜드나 다음 단계를 안내하는 커스텀 오류 페이지를 보여줄 수 없다.

#2핵심 질문

특정 오류 코드에 대해 자신만의 오류 페이지를 보여주고, 필요하면 다른 경로의 파일로 대체할 수 있을까?

#3동작 예시

오리진이 404를 응답하면 CloudFront 설정에서 "404일 때는 내 도메인의 /404.html을 보여줘"라고 지정해두고, 해당 파일을 오리진에 미리 올려둔다. CloudFront는 404 응답을 받으면 자동으로 /404.html을 가져와 클라이언트에게 보낸다.

#4동작 과정

  1. 오류 코드 감지오리진이 3xx, 4xx, 5xx 상태 코드를 응답하면 CloudFront가 받는다.
  2. 커스텀 에러 페이지 매핑 확인CloudFront 배포 설정에서 해당 오류 코드에 맞춘 커스텀 페이지 경로가 지정되어 있는지 확인한다.
  3. 에러 페이지 제공지정된 경로의 파일을 오리진에서 가져와 오류 코드와 함께 클라이언트에게 반환한다.

#5한 줄 요약

같은 파일을 덮어쓰는 대신 image_v2.jpg처럼 이름이 다른 새 파일을 올려 캐시를 기다리지 않고 즉시 새 콘텐츠를 서비스하는 방법이다.

#1문제 상황

캐시 시간(TTL)을 길게 설정하면 사용자에게 빨리 전달되지만, 파일을 수정했을 때 새 버전이 엣지에 나타날 때까지 기다려야 한다. 반대로 TTL을 짧게 설정하면 업데이트는 빠르지만 엣지와 오리진의 왕복 요청이 늘어 캐시 효율이 떨어진다.

#2핵심 질문

기존 파일 이름을 그대로 두고 캐시가 만료될 때까지 기다리지 않고, 즉시 새 내용을 서비스할 수 있을까?

#3동작 예시

같은 파일을 image.jpg가 아니라 image_v2.jpg처럼 파일명에 버전 번호나 해시값을 붙여서 새로 올린다. CloudFront는 새 파일명을 처음 보는 것이므로 캐시에 없다고 판단해 오리진에서 가져온다. 기존 이미지를 찾는 사용자는 여전히 image.jpg를 받고, 새로운 코드에서는 image_v2.jpg를 요청해 즉시 새 이미지를 받는다.

#4동작 과정

  1. 새 파일명으로 업로드수정된 콘텐츠를 image_v2.jpg 같이 고유한 이름으로 오리진에 올린다.
  2. 코드/설정 업데이트HTML이나 CSS에서 새 파일명을 참조하도록 변경한다.
  3. 즉시 제공사용자는 새 파일명으로 요청하면 CloudFront가 캐시에 없으므로 오리진에서 최신 버전을 가져온다.

#2핵심 질문

#3동작 예시

Origin Shield로 오리진 앞에 한 겹 더

#1문제 상황

CloudFront 엣지 로케이션들이 각각 독립적으로 오리진에 요청하면, 엣지 개수만큼 오리진 요청이 늘어난다. 오리진 서버의 로드가 커지고, 캐시 미스 시간이 길어진다. 또한 엣지 로케이션마다 조금씩 다른 타이밍에 같은 파일을 요청해 오리진이 중복 처리하는 비효율이 생긴다.

#2핵심 질문

여러 엣지가 같은 파일을 동시에 요청할 때, 오리진이 한 번만 처리하고 그 결과를 모든 엣지가 공유할 수 있을까?

#3동작 예시

Origin Shield는 오리진과 엣지 사이에 배치된 추가 캐시 계층이다. 엣지들이 오리진에 직접 요청하지 않고 Origin Shield에 먼저 요청한다. Origin Shield 캐시에 있으면 즉시 반환하고, 없으면 Origin Shield가 한 번만 오리진에 요청해 받은 응답을 엣지들과 공유한다.

#4동작 과정

  1. 엣지에서 Origin Shield 요청캐시 미스가 발생한 엣지가 오리진이 아니라 Origin Shield에 요청한다.
  2. 중앙 캐시 확인Origin Shield 캐시에 있으면 엣지에 반환한다. 없으면 오리진에 한 번만 요청한다.
  3. 결과 공유Origin Shield가 오리진의 응답을 받으면 자신의 캐시에 저장하고, 요청한 엣지뿐 아니라 다른 엣지도 이후 요청 시 이 캐시에서 받을 수 있다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 스테이징 배포 생성새로운 설정으로 테스트 목적의 CloudFront 배포를 따로 만듭니다.
  2. 트래픽 분산 설정프로덕션 배포에서 실제 들어오는 요청 중 지정한 비율(예: 10%)을 스테이징 배포로 보내고 나머지는 기존 배포로 보내도록 설정합니다.
  3. 검증 후 승격스테이징이 받은 트래픽의 로그, 응답 시간, 에러율 등을 확인해서 문제가 없으면 그 설정을 운영 배포에 적용하고 스테이징은 삭제합니다.

WebSocket과 gRPC 트래픽

단순 HTTP 요청·응답이 아닌 양방향 지속 연결과 gRPC 호출도 CloudFront가 그대로 통과시켜 처리하는 방법

#1문제 상황

CloudFront는 기본적으로 HTTP/HTTPS 요청에 대해 응답을 받아 캐싱하고 반환하는 요청-응답 방식으로 설계되었습니다. 하지만 WebSocket은 클라이언트와 서버가 연결을 계속 유지하면서 양방향으로 실시간 데이터를 주고받는 방식이고, gRPC는 HTTP/2를 기반으로 바이너리 메시지를 스트리밍하는 방식이라 일반적인 웹 캐싱 규칙에 맞지 않습니다.

#2핵심 질문

CloudFront가 단순 HTTP 요청-응답이 아닌 양방향 지속 연결과 바이너리 스트리밍도 오리진에 그대로 통과시켜 처리할 수 있을까?

#3동작 예시

웹소켓 채팅 애플리케이션이 CloudFront를 통해 오리진에 연결될 때, 클라이언트가 HTTP 업그레이드 요청(HTTP를 WebSocket으로 전환하는 요청)을 보내면 CloudFront는 그 요청을 오리진에 그대로 전달하고, 업그레이드가 성공하면 클라이언트와 오리진 사이의 지속 연결 채널을 계속 열어 둡니다.

#4동작 과정

  1. 업그레이드 요청 통과HTTP에서 WebSocket으로 업그레이드하는 Upgrade 헤더를 포함한 요청이 들어오면 CloudFront가 그것을 오리진에 그대로 전달합니다.
  2. 연결 확립오리진이 업그레이드를 수락하면 HTTP 연결이 WebSocket 연결로 전환되고, CloudFront는 클라이언트와 오리진 사이의 양방향 통신 채널을 유지합니다.
  3. 양방향 데이터 흐름이후 클라이언트가 보내는 메시지와 오리진이 보내는 메시지가 CloudFront를 거쳐 양쪽을 오가며, CloudFront는 이 데이터를 캐싱하지 않고 그대로 중계합니다.

#5한 줄 요약

#2핵심 질문

#3동작 예시

뷰어와 CloudFront 사이의 HTTPS

사용자 브라우저에서 엣지까지 구간을 암호화하고, HTTP 요청을 HTTPS로 리디렉션하거나 아예 막도록 뷰어 프로토콜 정책을 설정하는 것.

#1문제 상황

HTTP 통신에서는 사용자의 브라우저와 CloudFront 엣지 사이의 모든 데이터가 평문으로 전송되어 제3자(예: 같은 네트워크의 공격자)가 중간에서 내용을 읽거나 조작할 수 있습니다. 보안을 위해서는 이 구간을 암호화해야 합니다.

#2핵심 질문

사용자의 브라우저와 CloudFront 엣지 사이의 통신을 HTTPS로 암호화하고, HTTP 요청은 자동으로 HTTPS로 변환하거나 차단할 수 있을까?

#3동작 예시

CloudFront 배포의 "뷰어 프로토콜 정책(Viewer Protocol Policy)"을 "HTTPS Only"로 설정하면, 사용자가 http://www.example.com으로 접속했을 때 자동으로 https://www.example.com으로 리디렉션되고, 이후의 모든 통신은 TLS로 암호화됩니다.

#4동작 과정

#1문제 상황

#2핵심 질문

  1. OAC 생성CloudFront 콘솔에서 OAC를 만들면, AWS가 고유한 서명 용도 인증서를 생성합니다.
  2. 배포에 OAC 연결CloudFront 배포의 오리진 설정에서 방금 만든 OAC를 선택하면, CloudFront가 S3로 보내는 모든 요청에 OAC 서명을 붙입니다.

VPC 안의 ALB나 EC2는 프라이빗 서브넷에만 존재해 인터넷으로 노출되지 않습니다. 전에는 이런 리소스를 CloudFront 오리진으로 쓰려면 공인 IP를 할당하거나 NAT 게이트웨이를 거쳐야 했는데, 이렇게 하면 프라이빗 리소스가 인터넷에 노출되는 보안 위험이 생깁니다.

AWS Resource Access Manager로 VPC 오리진 같은 리소스를 다른 계정과 공유해 여러 계정의 배포가 함께 쓰게 하는 방법이다.

#1문제 상황

VPC 오리진(프라이빗 서브넷에 있는 로드 밸런서나 애플리케이션 서버)을 다른 AWS 계정의 CloudFront 배포에서 쓰려면 VPC 피어링이나 PrivateLink 같은 복잡한 네트워크 설정이 필요했다. 계정 간 오리진 공유가 번거롭고, 각 계정이 자기 오리진을 따로 만들어야 했다.

#2핵심 질문

AWS Resource Access Manager로 VPC 오리진을 다른 계정과 쉽게 공유해서 네트워크 설정 없이 여러 배포가 같은 오리진을 쓸 수 있을까?

#3동작 예시

계정 A의 프라이빗 로드 밸런서를 AWS RAM에서 계정 B에 공유하도록 설정하면, 계정 B의 CloudFront 배포가 그 로드 밸런서를 오리진으로 직접 선택해 사용할 수 있다. VPC 피어링 같은 추가 설정 없이 CloudFront 콘솔에서 공유된 오리진이 목록에 나타나고 바로 사용 가능하다.

#4동작 과정

  1. RAM에서 오리진 리소스 식별 및 공유계정 A가 AWS RAM 콘솔에서 공유할 VPC 오리진(로드 밸런서, 자동 스케일링 그룹)을 지정하고 계정 B 또는 조직에 공유 설정.
  2. 공유 초대 전달 및 수락RAM이 계정 B에 초대를 보내고, 계정 B가 RAM 콘솔에서 초대를 수락해 해당 오리진에 접근 권한 획득.
  3. 공유된 오리진으로 배포 생성계정 B의 CloudFront 콘솔에서 배포를 만들 때 공유된 오리진이 선택 가능하게 나타나며, 그것을 선택해 배포 생성.

AWS RAM으로 VPC 오리진 같은 리소스를 계정 간에 공유해서 복잡한 네트워크 설정 없이 여러 계정의 CloudFront 배포가 같은 프라이빗 오리진을 사용하게 해주는 것
