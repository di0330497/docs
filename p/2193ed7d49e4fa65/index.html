IaC 와 Terraform: 선언형 프로비저닝이 푸는 문제

원하는 인프라의 최종 상태를 코드로 적어두면 Terraform 이 실제 환경을 거기에 맞춰주는 방식으로, 손으로 클릭하던 구축을 반복 가능하게 만든다.

1상대의 출발점 확인

기존에는 인프라를 손으로 구축했다. AWS 콘솔을 열어서 EC2 인스턴스를 클릭으로 만들고, 보안 그룹 설정을 손으로 입력하고, 로드 밸런서를 수동으로 구성한다. 이 방식의 문제는 같은 환경을 다시 만들려면 또 손으로 클릭해야 하고, 누가 뭘 바꿨는지 기록이 없으며, 같은 인프라를 여러 환경에 만들기가 힘들다.

2질문 제기

인프라 구성을 반복 가능하고 버전 관리할 수 있게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

Terraform은 인프라의 최종 상태를 코드(HCL)로 적어둔다. 예를 들어 "AWS에 t2.micro 인스턴스 1개, security group 하나" 라고 .tf 파일에 적어놓으면, terraform apply 를 실행할 때마다 실제 AWS 환경이 그 상태와 일치하도록 만든다.

4단계별 동작 과정

  1. 코드로 선언인프라의 최종 모습을 HCL(HashiCorp Configuration Language)이라는 언어로 작성한다. 손으로 구성하는 것이 아니라 텍스트로 적는다.
  2. 계획 확인terraform plan 을 실행하면 지금 상태와 원하는 상태의 차이를 비교해서, 어떤 자원이 추가될지, 변경될지, 삭제될지 미리 보여준다.
  3. 자동 적용terraform apply 를 실행하면 Terraform 이 계획한 변경을 자동으로 실제 클라우드 환경에 반영한다.

설정을 쓰고(Write), 무엇이 바뀔지 미리 보고(Plan), 승인해서 실제로 반영하는(Apply) 세 단계가 Terraform 사용의 전부다.

  3. JSON 대안같은 블록·인자 구조를 JSON 형식으로도 쓸 수 있으며, Terraform이 자동으로 읽을 수 있다.

Terraform은 한 디렉터리 안의 모든 .tf 파일을 순서 없이 합쳐 하나의 설정으로 읽고, .tfvars로 변수값을, override 파일로 일부 설정을 덮어쓴다.

1상대의 출발점 확인

큰 프로젝트에서 설정을 한 파일에만 쓰면 수천 줄이 되어 유지보수가 어렵다. 설정을 여러 파일로 나눌 때 파일 읽기 순서가 중요하면 순서를 관리해야 하고, 개발·스테이징·운영 환경마다 다른 변수값을 써야 할 때 코드와 분리해서 관리할 방법이 필요하다.

2질문 제기

설정 파일을 여러 개로 나누되, Terraform이 읽고 병합하는 방식은 무엇일까?

3구조적 핵심 예시

한 디렉터리에 여러 .tf 파일을 놓으면: `` project/ main.tf variables.tf outputs.tf terraform.tfvars `` Terraform은 이 파일들을 순서 없이 합쳐 하나의 설정으로 간주한다.

  1. .tf 파일 읽기Terraform은 작업 디렉터리의 모든 .tf 파일을 읽는다. 파일명이나 정의 순서는 영향 없고, 블록 타입·이름으로만 중복 검사를 한다.
  2. .tfvars 파일terraform.tfvars (자동 로드) 또는 -var-file 옵션으로 지정한 .tfvars 파일에서 변수명 = 값 형태로 입력 변수의 값을 로드한다.
  3. override 파일override.tf 또는 _override.tf 같은 override 파일은 같은 이름의 리소스·변수를 덮어쓰므로, 환경별로 일부 설정만 바꿀 때 유용하다.

terraform 블록: required_version, required_providers, backend

terraform 블록은 코드가 아니라 Terraform 자신에 대한 설정으로, 필요한 CLI 버전·프로바이더 목록·상태 저장 백엔드를 선언한다.

1상대의 출발점 확인

Terraform 코드를 쓸 때 사용할 프로바이더(AWS, Google Cloud 등)의 버전을 명확히 지정하지 않으면 팀원마다 다른 버전을 쓸 수 있다. 코드가 어떤 Terraform CLI 버전을 필요로 하는지 명시되지 않으면 구버전에서 실행되어 오류가 난다. 상태(state)를 어디에 저장할지 정해지지 않으면 로컬 파일과 원격 저장소가 섞여 협업이 혼란스럽다.

2질문 제기

Terraform 자체의 설정(CLI 버전, 프로바이더 버전, 상태 저장소)을 코드에서 어떻게 선언할 수 있을까?

3구조적 핵심 예시

terraform 블록은 코드가 아니라 Terraform 프로그램 자신에 대한 메타 설정이다: ``hcl terraform { required_version = ">= 1.0" required_providers { aws = { source = "hashicorp/aws" version = "~> 5.0" } } backend "s3" { bucket = "my-terraform-state" key = "prod/terraform.tfstate" region = "us-east-1" } } ``

4단계별 동작 과정

  1. required_version코드를 실행할 Terraform CLI 최소·최대 버전을 지정한다. 버전 조건을 만족하지 않으면 terraform init 에서 오류를 낸다.
  2. required_providers각 프로바이더의 출처(source, 보통 hashicorp/aws 형태)와 버전 범위를 선언하면, Terraform이 자동으로 해당 버전을 다운로드해서 쓴다.
  3. backend상태 파일을 저장할 위치와 방식을 지정한다. local (기본값, 로컬 디스크), s3 (AWS S3), azurerm (Azure) 등 옵션이 있고, 원격 백엔드를 쓰면 팀원 전원이 같은 상태를 공유할 수 있다.

프로바이더란: 플러그인 구조와 레지스트리

1상대의 출발점 확인

Terraform 코드를 쓸 때 AWS, Azure, Google Cloud 같은 실제 클라우드 환경과 통신해야 하는데, 각 클라우드 제공자마다 API가 다르고 인증 방식도 다릅니다. Terraform 코드가 직접 모든 클라우드 API를 알고 있으면 코드가 너무 복잡해지고, 새로운 클라우드가 나올 때마다 Terraform 자체를 수정해야 합니다.

2질문 제기

Terraform은 어떻게 AWS, Azure, Google Cloud 같은 서로 다른 클라우드들의 API를 통일된 방식으로 다룰 수 있을까요?

3구조적 핵심 예시

프로바이더는 AWS 클라우드라는 외부 시스템과 Terraform 사이에 앉아 있는 번역 계층(플러그인)입니다. AWS provider는 AWS API 호출을 알고 있고, aws_instance라는 리소스 타입을 Terraform이 선언하면, provider가 내부적으로 AWS EC2 API를 호출해 실제 인스턴스를 만듭니다.

1상대의 출발점 확인

3구조적 핵심 예시

4단계별 동작 과정

  1. 버전 범위 정의required_providers 블록에서 각 프로바이더의 허용 버전 범위를 지정합니다.
  2. 초기 선택 및 기록첫 번째 terraform init 에서 범위 안에 있는 최적 버전을 선택하고, 버전과 해시값을 .terraform.lock.hcl 에 기록합니다.
  3. 이후 실행에서 재현다음 terraform init 실행들은 잠금 파일을 읽고 기록된 버전만 받도록 강제합니다.

Terraform 코드만 있으면 어떤 인프라가 실제로 만들어졌는지 알 수 없습니다. EC2 인스턴스를 5개 만들도록 설정했는데, 3개만 실제로 존재할 수도 있고, 누군가 수동으로 추가 인스턴스를 만들었을 수도 있습니다. Terraform이 변경을 적용할 때는 현재 실제 상태와 목표 상태를 비교해야 "어떤 리소스를 새로 만들고, 어떤 리소스를 고치고, 어떤 리소스를 지울 것인가"를 계산할 수 있습니다. 코드만으로는 이 계산이 불가능합니다.

2질문 제기

설정 코드와 실제 클라우드 리소스들을 어떻게 연결해서 변경사항을 계산할까요?

3구조적 핵심 예시

상태 파일은 설정한 각 리소스의 AWS ID나 이름, 속성들을 JSON 형식으로 기록해둔 데이터베이스입니다. aws_instance.web이라는 리소스가 있으면 상태 파일에는 "이것은 인스턴스 ID: i-0123456"이라고 저장됩니다. Terraform이 변경을 적용할 때는 설정 코드를 읽고, 상태 파일을 읽어서 비교합니다.

4단계별 동작 과정

  1. 설정과 현실 비교Terraform이 설정 코드를 읽고 상태 파일에서 실제로 만들어진 리소스들을 찾아 둘을 대조합니다.
  2. 변경 계획 수립설정에 있지만 상태에 없는 리소스는 "생성", 설정에 없지만 상태에는 있는 리소스는 "삭제", 둘 다 있지만 속성이 다르면 "수정"으로 계획합니다.
  3. 계획 실행사용자가 승인하면 Terraform이 이 계획을 실행하고, 동시에 상태 파일을 새로운 상태로 업데이트합니다.

5본질 요약

원격 상태와 백엔드 개념

상태 파일을 로컬 디스크 대신 공유 저장소에 두어 팀이 함께 쓰게 하는 구조가 원격 상태이고, 그 저장 위치와 방식을 정하는 설정이 백엔드다.

1상대의 출발점 확인

상태 파일을 로컬 디스크에만 저장하면, 각 팀원의 컴퓨터에 다른 상태 파일이 남습니다. 개발자 A가 인스턴스를 3개 만들고 git에 커밋했는데, 개발자 B는 로컬 상태에서 인스턴스가 0개인 줄 알고 작업합니다. 그러면 상태의 일관성이 깨지고, 누가 무엇을 만들었는지 충돌합니다. 팀이 같은 인프라를 관리하려면 모두가 하나의 상태 파일을 봐야 합니다.

2질문 제기

팀의 모든 멤버가 같은 상태를 공유하려면 상태 파일을 어디에 두어야 할까요?

3구조적 핵심 예시

S3, Azure Blob Storage, Google Cloud Storage 같은 공유 저장소에 상태 파일을 올려두고, 모든 팀원이 그 파일을 읽고 쓰도록 설정합니다. 누군가 변경을 적용하면 공유 저장소의 상태 파일이 업데이트되고, 다른 사람이 terraform plan을 실행하면 항상 최신 상태를 읽습니다.

4단계별 동작 과정

  1. 백엔드 지정terraform 블록 안에 backend 블록을 추가해 상태를 저장할 위치(s3, azurerm, gcs 등)를 명시합니다.
  2. 자동 동기화Terraform이 작업할 때마다 자동으로 그 백엔드에 접속해 상태를 읽고 쓰므로, 팀원들이 따로 상태 파일을 주고받을 필요가 없습니다.
  3. 일관된 상태 유지모든 팀원의 Terraform 명령어가 같은 상태 파일을 대상으로 작동하므로 충돌이 일어나지 않습니다.

3구조적 핵심 예시

  3. 초기화terraform init을 실행해 백엔드를 활성화하면 Terraform이 그 저장소에 접속해 상태를 관리하기 시작합니다.

상태 잠금과 force-unlock

동시에 두 명이 적용해 상태가 깨지지 않도록 작업 중 상태를 잠그며, 잠금이 비정상으로 남으면 force-unlock 으로 푼다.

1상대의 출발점 확인

상태 파일이 공유되면 새로운 문제가 생깁니다. 개발자 A와 B가 동시에 terraform apply를 실행하면 어떻게 될까요? A는 상태를 읽고 변경을 계산 중인데 B가 같은 상태를 쓰기 시작하면, 상태 파일이 일관성 없는 상태로 남습니다. 두 변경이 섞여서 일부 리소스는 두 번 생성되거나, 일부는 누락될 수 있습니다.

2질문 제기

여러 사람이 동시에 상태를 수정하려고 할 때 상태 파일의 손상을 어떻게 방지할까요?

3구조적 핵심 예시

사람 A가 terraform apply를 시작하면 상태 파일이 잠김 상태로 표시되고, 사람 B의 terraform 명령어는 "상태가 잠겨있습니다"라는 오류로 대기합니다. A가 적용을 완료하면 상태가 해제되어 B가 진행합니다.

4단계별 동작 과정

  1. 잠금 획득누군가 terraform plan이나 apply를 시작하면, 백엔드가 자동으로 상태에 잠금 메타데이터를 기록합니다.
  2. 다른 사람 대기이 시간에 다른 사람이 같은 상태에 접근하려 하면 "Lock ID: xxx 사용자가 잠금 중"이라는 메시지와 함께 대기 또는 실패합니다.
  3. 잠금 해제작업이 끝나면 자동으로 잠금이 풀려 다음 사람이 진행할 수 있습니다.

5본질 요약

상태 잠금은 동시에 여러 명이 상태를 수정하는 것을 방지해 인프라 상태의 일관성과 무결성을 보호하는 메커니즘입니다.

7상태(state)07-07

상태 고치기

실제 인프라는 그대로 둔 채 상태 안의 주소를 옮기거나 항목을 빼거나 프로바이더를 바꾸고, 특정 리소스를 재생성 대상으로 표시하는 수술용 명령들이다.

1상대의 출발점 확인

설정과 상태가 불일치할 때가 있습니다. 누군가 수동으로 리소스를 지웠는데 상태에는 남아있거나, 리소스 이름을 바꿨는데 상태는 옛 이름을 가지고 있습니다. 또는 리소스를 다른 모듈로 옮기거나 프로바이더를 변경해야 할 때도 있습니다. 이런 경우 실제 클라우드 리소스는 건드리지 않으면서 상태만 수정해야 합니다. 상태 파일의 JSON을 손으로 편집하는 것은 위험합니다.

2질문 제기

실제 인프라는 그대로 두면서 상태 파일의 내용만 수정하려면 어떻게 할까요?

3구조적 핵심 예시

리소스 이름을 aws_instance.web에서 aws_instance.server로 바꾸려면 terraform state mv aws_instance.web aws_instance.server를 실행하면 상태의 주소만 바뀌고 실제 EC2 인스턴스는 그대로입니다. 상태에서 완전히 제거하려면 terraform state rm aws_instance.web을 씁니다.

4단계별 동작 과정

  1. 주소 이동terraform state mv <기존주소> <새주소>로 상태 파일의 리소스 주소를 옮기거나 이름을 바꿉니다. 실제 리소스는 변하지 않습니다.
  2. 상태에서 제거terraform state rm <주소>로 상태 파일에서만 리소스를 제거합니다. 클라우드의 실제 리소스는 남아있습니다.
  3. 고급 수술terraform state replace-provider로 리소스의 프로바이더를 바꾸거나, terraform taint <주소>로 특정 리소스를 다음 apply 때 재생성하도록 표시합니다.

모듈이란: 루트 모듈과 자식 모듈

모듈은 함께 쓰이는 .tf 파일 묶음으로, 명령을 실행하는 디렉터리가 루트 모듈이고 그 안에서 호출되는 것이 자식 모듈이다.

기존에는 모든 리소스와 설정을 main.tf 파일에 나열하거나 하나의 디렉터리에 .tf 파일을 여러 개 두었습니다. 이런 방식은 설정 코드가 복잡해질수록 어떤 부분이 어떤 역할을 하는지 파악하기 어렵고, 같은 리소스 정의를 여러 프로젝트에서 반복해서 작성해야 했습니다.

2질문 제기

재사용 가능하고 조직화된 코드 단위로 인프라 설정을 어떻게 구성할 수 있을까요?

3구조적 핵심 예시

모듈은 함께 쓰이는 .tf 파일들의 묶음입니다. terraform apply 명령을 실행하는 디렉터리가 루트 모듈이 되고, 그 안에서 module 블록으로 호출되는 다른 디렉터리의 파일 묶음이 자식 모듈이 됩니다. 예를 들어 ec2 디렉터리에 AWS 인스턴스 생성 코드를 모아두면, 루트 모듈에서 module "web" { source = "./ec2" } 처럼 호출해 재사용할 수 있습니다.

4단계별 동작 과정

  1. 루트 모듈 정의terraform apply 명령을 실행하는 디렉터리의 main.tf 파일에 module 블록을 작성합니다.
  2. 자식 모듈 호출source 인자에 자식 모듈의 위치(로컬 경로, Git 저장소 등)를 지정하고 입력 변수를 전달합니다.
  3. 출력 받기module.<모듈명>.<출력값> 형태로 자식 모듈이 정의한 output을 루트 모듈에서 받아 사용합니다.

module 블록 호출: 입력, 출력, 메타인자

module 블록에 source 와 입력 변수를 주어 자식 모듈을 호출하고, module.<이름>.<출력> 으로 결과를 받으며 count·for_each·depends_on 같은 메타인자를 쓸 수 있다.

1상대의 출발점 확인

기존에는 리소스를 직접 정의할 때 resource 블록에 모든 설정값을 하드코딩했습니다. 이 방식은 다른 상황에서 값만 바꿔 쓸 수 없었으므로, 같은 리소스를 여러 번 만들 때마다 코드를 복사하고 값을 일일이 수정해야 했습니다.

2질문 제기

모듈의 입력과 출력을 다루면서도 count·for_each처럼 여러 개를 동시에 호출할 수 있을까요?

3구조적 핵심 예시

module 블록은 자식 모듈을 호출하는 문법입니다. source에 위치를 지정하고, 변수명=값 형태로 입력 변수를 전달하며, module.<이름>.<출력명>으로 결과를 받습니다. 메타인자(count, for_each, depends_on 등)를 붙이면 resource 블록처럼 여러 개 인스턴스를 생성하거나 순서를 제어할 수 있습니다.

4단계별 동작 과정

  1. module 블록 작성module "이름" { source = "경로" var_name = value } 형태로 자식 모듈을 호출하고 입력값을 전달합니다.
  2. 메타인자 적용count나 for_each를 module 블록에 추가해 조건부·반복 호출을 하거나, depends_on으로 생성 순서를 명시합니다.
  3. 출력값 참조module.web.instance_ip 같은 형태로 자식 모듈이 정의한 output 값을 다른 리소스에서 사용합니다.

기존에는 사람마다 모듈 디렉터리를 만드는 방식이 달랐습니다. 어떤 파일에 변수가 정의되었고 어떤 파일에 리소스가 있는지 일정한 규칙이 없었으므로, 다른 사람이 작성한 모듈을 이해하고 수정하기 어려웠습니다.

3구조적 핵심 예시

표준 구조는 모듈 디렉터리 안에 main.tf(리소스 정의), variables.tf(입력 변수 정의), outputs.tf(출력값 정의), README.md(문서)를 배치하는 것입니다. 예를 들어 vpc 모듈이라면 vpc/main.tf에는 AWS VPC와 서브넷 생성, variables.tf에는 cidr_block·region 같은 입력값, outputs.tf에는 vpc_id·subnet_id 같은 결과값을 정의합니다.

  2. 작은 모듈 조합vpc, security_group, ec2 같은 작은 단위 모듈을 만들어, 더 큰 루트 모듈에서 이들을 module 블록으로 호출하며 조합합니다.
  3. 문서화README.md에 모듈의 용도, 입력값 설명, 출력값, 사용 예시를 기입해 다른 사람도 쉽게 쓸 수 있게 합니다.

모듈 안의 프로바이더: 상속과 명시적 전달

자식 모듈은 기본적으로 호출자의 프로바이더 설정을 상속하며, 별칭 프로바이더가 필요하면 providers 인자로 명시적으로 전달한다.

1상대의 출발점 확인

기존에는 자식 모듈에서 리소스를 만들 때 각 모듈이 독립적으로 프로바이더(aws, google, azurerm 등)를 설정했습니다. 이 방식은 프로바이더 설정이 중복되고, AWS 계정이나 리전이 바뀔 때마다 모든 모듈을 수정해야 했습니다.

2질문 제기

자식 모듈에서 프로바이더를 매번 정의하지 않으면서도 올바른 프로바이더 설정을 적용할 수 있을까요?

3구조적 핵심 예시

기본적으로 자식 모듈은 루트 모듈의 프로바이더 설정을 자동으로 상속합니다. 루트의 terraform block에 provider "aws" { region = "us-east-1" }이 정의되어 있으면, 자식 모듈의 resource도 같은 프로바이더를 사용합니다. 하지만 별칭 프로바이더(provider "aws" { alias = "eu" })가 필요하면, module 블록의 providers 인자로 명시적으로 전달합니다.

4단계별 동작 과정

  1. 상속 활용루트의 provider 블록에 설정하면, 자식 모듈의 리소스가 자동으로 그 프로바이더를 사용합니다. 별도 설정 불필요합니다.
  2. 별칭 프로바이더 선언여러 AWS 리전이나 계정을 쓸 때, 루트에서 provider "aws" { alias = "eu" region = "eu-west-1" } 같이 별칭을 정의합니다.
  3. providers 인자로 전달module "web_eu" { source = "./web" providers = { aws = aws.eu } }처럼 module 블록에 providers 맵을 붙여 자식 모듈에 특정 프로바이더를 명시적으로 전달합니다.

모듈 게시와 버전 관리

정해진 저장소 이름과 Git 태그 규칙을 지켜 레지스트리에 모듈을 게시하고, 호출 측은 version 제약으로 특정 버전을 고정해 쓴다.

1상대의 출발점 확인

기존에는 팀이 만든 모듈을 공유하는 표준 방식이 없었습니다. Git 저장소에 코드를 올려도 어느 버전이 안정적인지, 어떻게 호출해야 하는지 문서가 일정하지 않았고, 사용 중인 모듈이 업데이트되면 여러 프로젝트에서 호환성 문제가 발생할 수 있었습니다.

2질문 제기

3구조적 핵심 예시

3구조적 핵심 예시

  1. 코드 구조 변경리소스 이름, 모듈 경로, 변수명 등을 새로운 구조로 바꾼다.

1상대의 출발점 확인

4단계별 동작 과정

  1. 컴포넌트 정의tfcomponent.hcl 파일에서 여러 모듈을 변수와 출력으로 연결해 하나의 재사용 가능한 패키지로 정의합니다.
  2. 배포 구성 생성tfdeploy.hcl 파일에서 정의한 컴포넌트를 환경별(dev, prod), 지역별(us-east, ap-southeast) 등으로 여러 배포(deployment) 항목으로 선언합니다.
  3. 배포 실행terraform stack deploy 명령어로 각 배포 구성을 순서대로 plan/apply하면, 모든 환경과 영역에 컴포넌트가 일관되게 배포됩니다.

Terraform 내부: 그래프, 실행 순서, JSON 포맷

1상대의 출발점 확인

인프라 코드에서는 여러 리소스가 서로 연결되어 있다. 예를 들어 VPC를 먼저 만들어야 서브넷을 만들 수 있고, 서브넷이 있어야 EC2 인스턴스를 배포할 수 있다. 전통적으로는 이러한 의존관계를 개발자가 직접 파악하고 리소스 선언 순서를 맞춰야 했는데, 파일이 커지거나 리소스가 많아지면 순서를 놓치기 쉽다. Terraform은 이 문제를 자동으로 해결한다.

2질문 제기

Terraform이 수백 개의 리소스가 어떤 순서로 만들어져야 하는지 어떻게 자동으로 파악할까?

3구조적 핵심 예시

VPC에 EC2 인스턴스의 보안 그룹이 참조된다고 하자. aws_security_group.app 이 aws_vpc.main 을 참조하고, aws_instance.app 이 aws_security_group.app 을 참조한다면, Terraform은 이 참조 관계들을 읽어 VPC → 보안 그룹 → EC2 순서로 만들어야 한다는 것을 자동으로 안다.

4단계별 동작 과정

  1. 리소스 간 참조 관계 분석Terraform이 모든 리소스의 resource "type" "name" 선언을 읽고, 각 리소스 속성 내에서 다른 리소스를 참조하는 부분 (예: aws_security_group.app) 을 찾아낸다.
  2. 방향 그래프(DAG, Directed Acyclic Graph) 생성각 리소스를 정점으로, 참조 관계를 간선으로 하는 그래프를 만든다. 순환 의존성이 없다면 이 그래프는 항상 위에서 아래로 흐른다.
  3. 위상 정렬(Topological Sort)로 실행 순서 결정그래프에서 의존성이 없는 리소스부터 위아래로 정렬해 동작 순서를 확정한다. 같은 단계에 속한 리소스들은 병렬로 실행할 수도 있다.

Go 로 직접 프로바이더를 만들 때 쓰는 공식 SDK 인 Plugin Framework 로 리소스·데이터소스·스키마를 정의하는 방법.

1상대의 출발점 확인

AWS, Azure, GCP 같은 클라우드 서비스와 Terraform을 연결하는 것이 프로바이더(provider)다. 과거에는 프로바이더를 개발하려면 Terraform의 저수준 SDK를 직접 다루며 리소스, 속성, 검증 로직을 일일이 손으로 작성해야 했다. 이 과정은 복잡하고 오류가 많았으며, 개발자마다 다른 방식으로 구현하는 문제가 생겼다.

2질문 제기

프로바이더 개발자들이 리소스와 데이터소스를 일관되고 표준화된 방식으로 정의할 수 있도록 하려면?

3구조적 핵심 예시

AWS 프로바이더에서 aws_instance 리소스를 정의한다고 하면, Plugin Framework 을 쓸 때는 리소스 타입을 구조체로 선언하고, 그 안에 instance_type, ami_id, tags 같은 각 속성의 이름, 타입(string, number, bool, list, map), 필수 여부, 기본값, 검증 규칙을 한 곳에 명시한다.

4단계별 동작 과정

  1. 리소스 타입 정의Go 구조체로 리소스를 선언하고, 각 필드가 Terraform 속성에 어떻게 매핑되는지 명시한다.
  2. 스키마(Schema) 작성속성의 이름, 데이터 타입, 필수/선택 여부, 검증 규칙, 도움말을 JSON 같은 형식으로 정의해 Terraform이 설정 파일을 검증하고 자동 완성을 지원하도록 한다.
  3. CRUD 함수 구현Create(만들기), Read(조회), Update(수정), Delete(삭제) 함수를 Go로 작성해 실제 API 호출을 처리한다.

레지스트리 프로토콜과 프로바이더 게시

Terraform 이 프로바이더·모듈을 내려받을 때 쓰는 HTTP 레지스트리 프로토콜과, 만든 프로바이더를 서명해 게시하는 절차.

1상대의 출발점 확인

프로바이더 개발이 끝나면, 사용자들이 이를 다운로드해 설치해야 한다. 과거에는 수동으로 컴파일한 바이너리를 배포하고, 사용자가 특정 디렉터리에 직접 놓아야 했다. 이 방식은 버전 관리가 어렵고, 정확한 바이너리를 찾기 힘들었으며, 보안 검증도 이루어지지 않았다.

2질문 제기

Terraform 사용자가 terraform init 명령 한 번으로 프로바이더를 자동으로 찾아 다운로드하고 설치할 수 있게 하려면?

3구조적 핵심 예시

사용자의 Terraform 파일에 terraform { required_providers { aws = { source = "hashicorp/aws" } } } 이라고 선언하면, terraform init 이 정의된 HTTP 레지스트리 API에 쿼리를 보내 "hashicorp/aws 의 최신 버전이 뭐고, 어디서 받을 수 있나" 를 묻고, 응답으로 받은 다운로드 URL에서 바이너리를 받아 설치한다.

4단계별 동작 과정

  1. 프로바이더 컴파일 및 서명프로바이더 소스를 여러 OS/아키텍처용으로 컴파일해 바이너리를 만들고, 배포 검증을 위해 암호화 서명(Signature)을 붙인다.
  2. HTTP 레지스트리 API로 메타데이터 등록프로바이더 이름, 버전, 각 버전의 다운로드 URL, 서명값, 지원 플랫폼 정보를 레지스트리에 업로드한다.
  3. Terraform 클라이언트가 API 조회 및 설치terraform init 이 레지스트리 API를 호출해 버전과 바이너리 URL을 얻고, 다운로드 후 서명을 검증한 뒤 설치한다.

12내부 구조와 확장12-04

사설 레지스트리와 정책 라이브러리

조직 내부 모듈·프로바이더를 사내 레지스트리로 공유하고, Sentinel·OPA 정책 세트로 배포 규칙을 강제하는 방식.

1상대의 출발점 확인

조직에서는 반복되는 인프라 패턴이 있다. 예를 들어 보안 팀이 정의한 VPC 구조, 네트워크 정책, IAM 역할 설정을 모든 팀이 따르도록 하고 싶다. 하지만 모든 모듈과 프로바이더가 공개 레지스트리에만 올라가면, 내부 표준을 강제할 수 없고, 누가 어디서 어떤 코드를 사용하는지 추적하기 어렵다. 또한 배포 전에 보안·규정 검증을 자동으로 할 방법이 없다.

2질문 제기

조직이 내부 표준 모듈과 정책을 중앙화해 안전하게 공유하고, 모든 배포가 조직의 규칙을 따르도록 강제하려면?

3구조적 핵심 예시

Terraform Cloud의 사설 레지스트리에 조직의 VPC 모듈을 myorg/vpc/aws 라고 올리고, Sentinel 정책으로 "모든 EC2 인스턴스는 반드시 이 VPC를 사용해야 한다" 같은 규칙을 정의한 후, 팀이 terraform apply 를 실행할 때마다 정책 엔진이 자동으로 검증해 규칙 위반이 있으면 배포를 차단한다.

4단계별 동작 과정

  1. 사설 레지스트리에 모듈/프로바이더 업로드Terraform Cloud 의 사설 레지스트리에 조직만 사용하는 모듈과 프로바이더를 올린다. 버전 관리와 접근 제어가 이루어진다.
  2. Sentinel/OPA 정책 정의배포 시 자동으로 검증할 규칙들을 정책 코드로 작성한다. 예: 허가되지 않은 인스턴스 타입 사용 금지, 태그 필수, 특정 보안 그룹만 허용 등.
  3. Apply 전 정책 자동 검증사용자가 terraform apply 를 실행하면, Terraform Cloud 가 계획(plan)을 받아 정책 엔진에 통과시켜 규칙 위반이 없는지 확인한다. 위반이 있으면 배포를 차단한다.

버전 호환성 약속, 업그레이드, 주변 도구

Terraform v1 계열이 지키는 언어 호환성 약속과 안전한 업그레이드 방법, 그리고 함께 쓰는 생태계 도구들.

1상대의 출발점 확인

소프트웨어는 버전이 올라가면서 언어나 문법이 바뀔 수 있다. 예를 들어 Python 2에서 Python 3로 넘어갈 때 많은 코드가 깨졌듯이, Terraform도 과거에는 메이저 버전 업그레이드 시 기존 설정 파일을 크게 수정해야 했다. 조직은 현재 버전에 머물러야 하는 압박을 받거나, 업그레이드마다 인프라 코드 전체를 수정해야 했다.

2질문 제기

Terraform 사용자가 버전을 올려도 기존 코드가 깨지지 않는다는 보장을 받을 수 있을까?

3구조적 핵심 예시

Terraform 1.0부터 1.9까지 출시되었는데, 언어 문법과 리소스 정의 방식이 호환된다는 약속 하에, 2년 전에 작성한 1.1 버전의 설정 파일이 오늘날 1.9 버전에서도 그대로 실행되고 동일한 결과를 낸다.

4단계별 동작 과정

  1. v1 계열 호환성 약속 선언Terraform 팀이 공식적으로 v1.0 이후 버전들이 언어, 함수, 리소스 속성을 하위 호환(backward compatible)하겠다고 약속한다.
  2. 요구 버전 명시인프라 코드에서 terraform { required_version = ">= 1.0, < 2.0" } 으로 최소·최대 버전을 지정하면, 사용자가 호환되지 않는 버전으로 실행할 때 자동으로 오류를 낸다.
  3. 업그레이드 전 검증사용 중인 프로바이더, 모듈, 커스텀 함수가 새 버전에서도 동작하는지 테스트(terraform plan, terraform validate)를 거친 뒤 업그레이드한다.

v1 계열의 언어 호환성 약속과 버전 관리 체계로 조직의 인프라 코드 투자를 장기적으로 보호하는 안정성 보장
