1AWS Backup의 위치와 동작 원리01-01

백업 중앙화 서비스의 역할

여러 AWS 서비스의 백업을 한곳에서 만들고 관리·모니터링할 수 있게 해주는 완전관리형 중앙 백업 서비스.

#1문제 상황

기존에는 EC2, RDS, S3, EFS 같은 서비스마다 백업 방법이 따로 있었다. EC2는 AMI나 EBS 스냅샷, RDS는 자체 자동 백업, S3는 버전 관리와 복제를 각각 설정해야 했다. 그 결과 백업 주기, 보존 기간, 복원 방법, 모니터링이 서비스별로 제각각이었고, 어디에 어떤 백업이 있는지 한눈에 파악하기 어려웠다. 운영자는 서비스마다 다른 콘솔을 오가며 설정해야 했고, 일부 서비스는 백업 설정이 누락되는 일도 흔했다.

#2핵심 질문

여러 AWS 서비스의 백업을 하나의 정책과 한 곳에서 관리할 수는 없을까?

#3동작 예시

EC2 한 대와 RDS 하나를 함께 백업한다고 할 때, AWS Backup을 쓰면 하나의 백업 플랜에 두 서비스를 모두 할당해 둘 수 있다. 플랜이 정한 시간이 되면 AWS Backup이 두 서비스의 백업을 자동으로 만들어 한 콘솔에서 목록을 확인하고, 필요할 때 같은 화면에서 복원한다. 서비스별 설정을 각자 찾아다닐 필요가 없다.

#4동작 과정

  1. 플랜 정의관리자가 백업 실행 시각, 보존 기간, 보관 위치(볼트) 같은 규칙을 하나의 백업 플랜으로 만든다.
  2. 리소스 할당이 플랜에 EC2, RDS 등 백업할 리소스를 태그나 ARN(리소스 고유 식별자)으로 지정한다.
  3. 자동 실행과 확인정해진 시각에 AWS Backup이 할당된 리소스의 백업을 만들고, 결과는 하나의 대시보드에서 확인한다.

1AWS Backup의 위치와 동작 원리01-02

동작 방식: 플랜→할당→볼트→복원

백업 플랜(일정·보존 규칙)을 만들고 리소스를 할당하면 백업이 볼트에 저장되며, 필요할 때 볼트에서 복원하는 일련의 흐름으로 서비스가 동작한다.

#1문제 상황

기존 백업 방식은 각 서비스가 자기만의 절차를 가졌다. 백업을 만들고 보관하고 복원하는 단계가 서비스마다 다른 콘솔과 다른 개념으로 흩어져 있었다. 예를 들어 RDS의 자동 백업과 EC2의 스냅샷은 만드는 방법과 보존 규칙이 달라서, 통일된 절차로 관리하려면 별도 스크립트나 도구를 붙여야 했다.

#2핵심 질문

백업의 생성부터 보관, 복원까지 하나의 일관된 절차로 묶을 수는 없을까?

#3동작 예시

하루 한 번 30일간 보관하는 백업이 필요하다면, 그 규칙을 담은 백업 플랜 하나를 만들고 EC2 인스턴스에 할당한다. 이후 AWS Backup이 매일 백업을 만들어 지정한 볼트(백업을 보관하는 저장소)에 넣고, 30일이 지난 백업은 자동으로 지운다. 복원이 필요하면 볼트에서 해당 백업을 골라 새 리소스로 복원한다.

#4동작 과정

  1. 플랜 생성실행 시각, 빈도, 보존 기간, 대상 볼트를 정한 백업 플랜을 만든다.
  2. 할당과 실행플랜에 리소스를 할당하면 정해진 시각에 백업 작업이 실행되어 백업이 볼트에 저장된다.

백업 플랜 개념

백업 플랜은 어떤 리소스를 언제·어떻게 백업하고 얼마나 보관할지 정의하는 AWS Backup의 핵심 구성 단위다.

#1문제 상황

기존에는 백업을 만들 때마다 시각, 주기, 보존 기간을 각각 직접 지정했다. 서비스별 스냅샷을 수동으로 만들거나, 주기적 실행을 위해 별도 스크립트와 스케줄러를 구성해야 했다. 백업 규칙이 여러 설정과 코드에 흩어져 있어서, 나중에 보존 기간을 바꾸려면 여러 곳을 수정해야 했고 일관성을 유지하기 어려웠다.

#2핵심 질문

백업의 시각·빈도·보존 기간이라는 규칙을 한곳에 정리해 한 번 설정해두고 재사용할 수는 없을까?

#3동작 예시

"매일 02시에 백업하고 30일간 보관한다"는 규칙을 백업 플랜 하나로 만든다. 이 플랜은 여러 리소스에 함께 적용할 수 있고, 보존 기간은 플랜의 규칙 한 곳만 고치면 모든 적용 대상에 동시에 반영된다. 규칙을 바꾼 뒤에도 이미 만들어진 백업은 기존 규칙대로 보관된다.

#4동작 과정

  1. 규칙 생성백업 실행 시각과 빈도, 보존 기간, 대상 볼트를 담은 규칙을 플랜 안에 정의한다.
  2. 리소스 할당같은 규칙을 적용할 리소스들을 플랜에 할당한다.
  3. 정기 실행플랜 규칙을 바꾸면 이후 실행부터 새 규칙이 적용되어 백업이 자동으로 생성·보관된다.

2백업 플랜02-02

플랜 생성과 옵션·백업 창

콘솔·CLI·API로 백업 플랜을 만들고 백업 규칙(빈도·보존 기간)과 백업 창(백업이 시작될 수 있는 시간대)을 설정하는 절차다.

#1문제 상황

백업을 만들려면 먼저 무엇을 언제 얼마나 보관할지 정해야 한다. 기존 방식은 EC2 인스턴스나 RDS 데이터베이스 같은 자원마다 각각 다른 콘솔에 들어가서 스냅샷(특정 시점의 저장 사본)을 수동으로 만들고, 오래된 스냅샷은 직접 지워야 했다. 자원 종류마다 설정 화면과 방법이 달라서 규칙이 일관되지 않았고, 자동화하려면 서비스마다 별도의 스크립트나 예약 작업을 따로 관리해야 했다. 그 결과 백업 규칙이 자원마다 제각각이 되고, 만든 뒤 관리하지 않아 스토리지 비용이 계속 쌓이는 문제가 흔했다.

#2핵심 질문

백업 규칙을 자원 종류와 무관하게 한곳에서 한 번에 정의하고 자동 실행할 수는 없을까?

#3동작 예시

AWS Backup의 백업 플랜(Backup plan) 하나를 만들면, 그 플랜 안에 "백업 창(Backup window)"과 "보존 기간(Retention period)" 같은 규칙을 적고, 태그(자원에 붙이는 이름표)만 지정하면 그 태그를 가진 EC2, RDS, EFS 같은 모든 자원이 같은 규칙으로 자동 백업된다. 즉 백업 시점은 플랜이 정하고, 누가 백업될지는 태그가 정한다.

#4동작 과정

  1. 플랜 생성과 규칙 정의콘솔에서 백업 플랜을 만들면서 백업 창(백업이 실행될 수 있는 시간 범위)과 보존 기간(백업을 며칠 또는 몇 달간 유지할지)을 지정한다.
  2. 자원 연결플랜에 태그 조건(예: "Environment=Production" 같은 키-값 쌍)이나 특정 자원 ID를 지정하면 AWS Backup이 매칭되는 자원을 플랜에 연결한다.
  3. 자동 실행과 정리백업 창 안에서 백업이 자동으로 만들어지고, 설정한 보존 기간이 지난 백업은 자동으로 삭제된다.

플랜 갱신·삭제·요약

기존 플랜의 규칙·설정을 변경하거나 플랜을 삭제하고, 플랜 요약 페이지에서 백업 범위와 상태를 확인하는 작업이다.

#1문제 상황

한 번 만든 백업 규칙은 운영이 바뀌면 고쳐야 한다. 기존에는 자원마다 스크립트나 예약 작업을 직접 찾아가 수정해야 했고, 한 플랜의 변경이 어떤 자원에 적용되는지 파악하기 어려웠다. 또 더 이상 쓰지 않는 백업 규칙을 지울 때도 어디에 설정했는지 일일이 확인해야 했고, 삭제가 실제 백업 데이터에 어떤 영향을 주는지 명확하지 않아서 건드리기 꺼려지는 경우가 많았다. 규칙이 많아질수록 현재 어떤 규칙이 돌고 있는지 전체를 보는 것 자체가 어려운 일이었다.

#2핵심 질문

백업 규칙을 만든 뒤 실제 운영에 맞게 안전하게 고치고 지우고 전체 현황을 한눈에 볼 수는 없을까?

#3동작 예시

백업 플랜은 언제든 콘솔에서 편집할 수 있고, 바꾼 규칙은 다음 백업 실행부터 그 플랜에 연결된 모든 자원에 적용된다. 플랜을 지워도 이미 만들어진 백업은 볼트(백업이 저장되는 보관소)에 남아 지워지지 않으며, 플랜 요약 화면에서 각 플랜이 몇 개의 자원을 백업하고 있는지와 최근 실행 결과를 한 화면에서 볼 수 있다.

#4동작 과정

  1. 플랜 갱신플랜을 편집해 백업 창, 보존 기간, 대상 태그를 고치면 저장 즉시 새 규칙으로 갱신되고 다음 실행부터 반영된다.

태그 또는 리소스 ARN(JSON)을 지정해 특정 리소스를 백업 플랜에 등록(opt in)하는 할당 방법이다.

#1문제 상황

백업 플랜이 어떤 자원을 백업할지 정하는 방법을 정해야 한다. 기존 방식은 백업 대상을 하나씩 콘솔에 등록했기 때문에 자원이 늘면 등록 작업이 반복되었고, 새 자원을 만들어도 백업에 자동으로 포함되지 않았다. 자원이 많아지면 목록을 일일이 관리해야 해서 빠뜨리기 쉬웠고, 환경(개발/운영)별로 다른 규칙을 적용하기도 번거로웠다. 대상 선정 기준이 명확하지 않으면 "백업이 되는 줄 알았는데 안 되는" 자원이 생기는 문제가 있었다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 태그 조건 지정플랜 할당에 태그 키-값(예: "Backup=Yes")을 적으면 그 태그가 붙은 모든 자원이 대상이 되고, 이후 새로 만들어진 자원도 태그만 있으면 자동 포함된다.
  2. ARN 직접 지정특정 자원만 백업하려면 해당 자원의 ARN을 할당 목록에 직접 추가한다.
  3. JSON 규칙 적용태그와 ARN 조건을 JSON으로 조합해 "이 태그를 가지되 이 자원은 제외" 같은 세밀한 할당 규칙을 적용한다.

볼트 개념·생성·삭제

백업 볼트(Backup vault)는 복구 지점과 백업을 담는 AWS Backup의 컨테이너로, 백업을 보관·조직화하는 기본 단위이며 생성·삭제 시 암호화 키와 태그를 설정한다.

#1문제 상황

백업이 만들어지면 그 데이터를 어디에 보관할지 정해야 한다. 기존 방식은 EC2 스냅샷은 EC2 콘솔의 스냅샷 목록에, RDS 백업은 RDS 콘솔에 저장되어 서비스마다 보관 위치와 관리 화면이 분산되어 있었다. 그래서 전체 백업이 어디에 얼마나 쌓여 있는지 한눈에 보기 어려웠고, 서비스별로 접근 권한과 보관 정책을 각각 관리해야 했다. 백업 데이터의 위치와 소유권이 서비스에 묶여 있어서 통합 관리가 어려웠다.

#2핵심 질문

#3동작 예시

AWS Backup의 백업 볼트(Backup vault)는 모든 AWS 서비스의 백업을 한곳에 모으는 저장 컨테이너다. EC2, RDS, EFS, DynamoDB 등 어떤 서비스의 백업이든 같은 볼트에 저장된다. 볼트를 만들 때는 이름과 KMS 키(암호화에 쓰는 키)를 지정하면 되고, 만들어진 볼트는 콘솔의 볼트 목록에서 상태와 저장된 백업 수를 한 번에 확인할 수 있다. 볼트는 더 이상 쓰지 않을 때 삭제할 수 있다.

#4동작 과정

볼트 접근 정책은 볼트에 부여하는 리소스 기반 정책으로, 해당 볼트의 백업·복원·삭제 작업을 수행할 수 있는 IAM 사용자와 역할을 제어한다.

#1문제 상황

백업 데이터는 보안에 민감해서 누가 볼트에 백업을 넣고, 누가 복원하고, 누가 삭제할 수 있는지 통제해야 한다. 기본 설정만으로는 볼트 소유 계정의 사용자들이 모두 같은 권한을 가져서, 실수로 백업을 지우거나 권한이 없는 사람이 백업에 접근하는 사고가 날 수 있었다. IAM 정책(사용자·역할에 권한을 부여하는 규칙)만으로는 계정 안팎의 다양한 주체(다른 계정, 역할, 서비스)별로 볼트 접근을 세밀하게 나누기 어려웠다.

#2핵심 질문

#4동작 과정

  1. 정책 작성JSON으로 Principal(누구에게: 계정, 역할, 사용자)과 Action(무엇을: Backup, Restore, Delete 같은 작업), Condition(조건)을 정의한다.
  2. 볼트에 연결작성한 정책을 특정 볼트에 연결하면 그 볼트에 대한 접근 규칙이 즉시 적용된다.

볼트 락: WORM 보존

볼트 락(Vault Lock)은 볼트에 WORM(Write Once Read Many) 모델을 적용해 설정한 보존 기간 동안 백업의 삭제·변경을 막는 규정 준수 기능이다.

#1문제 상황

기존 백업 볼트는 보존 정책으로 복구 지점을 일정 기간 보관하도록 지정하지만, 권한이 있는 사용자나 역할이 그 정책을 바꾸거나 복구 지점을 직접 삭제할 수 있었다. 루트 사용자처럼 높은 권한을 가진 계정이 탈취되거나 악의적으로 행동하면, 백업 자체가 통째로 삭제될 수 있고 랜섬웨어 공격자가 백업을 먼저 파괴하면 복구할 수단 자체가 사라진다. 보존 기간을 길게 잡아도 "누군가 마음만 먹으면 지울 수 있다"는 한계는 남는다.

#2핵심 질문

백업을 아무도 — 심지어 최고 권한 관리자도 — 수정하거나 삭제할 수 없게 고정하려면 어떻게 해야 할까?

#3동작 예시

볼트 락은 한 번 켜서 확정하면 되돌릴 수 없는 잠금 규칙을 볼트(백업을 담는 저장 공간)에 거는 기능이다. 예를 들어 랜섬웨어가 모든 서버를 암호화해도, 볼트 락이 걸린 볼트 안의 복구 지점은 아무도 삭제할 수 없으므로 공격 전 시점으로 복원할 수 있다.

#4동작 과정

  1. 잠금 시작볼트에 볼트 락을 활성화하면 72시간의 검토 기간이 시작된다. 이 기간 안에는 잠금을 되돌릴 수 있다.
  2. 잠금 확정검토 기간 안에 락을 확정하면 볼트와 그 안의 복구 지점에 변경 불가 규칙이 영구 적용된다. 지정한 보존 기간이 끝나기 전에는 어떤 권한으로도 수정·삭제가 불가능하다.
  3. 보존·복원WORM(한 번 쓰면 읽기만 가능한 방식) 규칙에 따라 복구 지점이 자동으로 보존되고, 복원 명령만 허용된다. 보존 기간이 끝나야 비로소 삭제가 가능해진다.

기존 백업은 복구 지점이 생성되는 즉시 볼트에 보관되고, 백업을 관리하는 자격 증명만 있으면 언제든 목록을 보고 복원하거나 삭제할 수 있었다. 공격자가 관리 권한을 얻으면 백업을 바로 찾아 지워버릴 수 있고, 볼트 자체를 삭제해 백업 전체를 잃을 수도 있다. 물리적으로 네트워크를 분리하는 에어갭(격리) 방식은 안전하지만 전용 하드웨어와 별도 운영 절차가 필요해 비용이 크고 적용이 어렵다.

#2핵심 질문

복원은 자유롭게 하면서도 백업이나 볼트의 삭제를 지연·차단해 공격자의 손을 막으려면 어떻게 해야 할까?

#3동작 예시

논리적 에어갭 볼트는 백업이 완료되면 복구 지점을 "준비 중" 상태로 보관한다. 이 상태의 복구 지점은 삭제가 거부되고, 볼트 자체도 삭제가 거부된다. 삭제 요청이 들어와도 24시간에서 72시간 사이의 유예 기간이 지나야 실제로 삭제되므로, 관리자는 그 사이에 삭제 요청을 발견하고 막을 수 있다.

#4동작 과정

  1. 복구 지점 생성과 격리백업이 완료되면 복구 지점이 준비 중 상태로 볼트에 들어가고, 즉시 삭제 불가 상태가 된다. 볼트 삭제도 거부된다.
  2. 삭제 요청과 유예누군가 복구 지점을 지우려 하면 바로 지워지지 않고 설정된 유예 기간(보통 24시간 이상) 동안 삭제 대기 상태가 된다.
  3. 유예 만료 후 삭제 여부 결정유예 기간이 끝나기 전에는 삭제가 실행되지 않는다. 관리자가 이 기간 안에 요청을 확인해 막거나, 기간이 지난 뒤에만 삭제가 진행된다.

#5한 줄 요약

백업 복구 지점과 볼트의 삭제를 자동으로 지연·차단하여 공격자가 관리 권한을 얻어도 즉시 백업을 파괴하지 못하게 하는 것

다자간 승인(MPA)

다자간 승인(MPA)은 논리적 에어갭 볼트의 복원·삭제 등 중요한 작업에 최소 두 명의 다른 승인자 승인을 요구해 단독 악의적 행위를 차단하는 기능이다.

#1문제 상황

기존에는 볼트 락 해제나 볼트 삭제 같은 민감한 작업도 해당 권한을 가진 사용자나 역할 하나만 있으면 실행할 수 있었다. 권한이 하나의 자격 증명에 집중되어 있어, 그 계정이 탈취되면 공격자가 혼자서 백업을 지우거나 보존 규칙을 풀어버릴 수 있다. 권한 검사가 "가진 사람이 실행한다" 한 겹뿐이라, 단일 실패 지점이 그대로 남는다.

#2핵심 질문

백업에 대한 위험한 작업을 한 사람의 판단만으로 실행할 수 없게 하려면 어떻게 해야 할까?

#3동작 예시

다자간 승인(MPA)은 볼트 락 해제나 볼트 삭제 같은 보호 대상 작업에 대해 서로 다른 역할의 승인을 요구한다. 예를 들어 한 역할이 볼트 삭제를 요청해도, 그 요청과 별개의 역할이 승인해야 작업이 진행된다. 한 자격 증명만으로는 요청과 승인을 동시에 채울 수 없으므로, 단일 계정 탈취만으로는 백업을 파괴할 수 없다.

#4동작 과정

  1. 보호 설정볼트에 MPA를 켜면, 요청을 내는 역할과 승인을 하는 역할이 분리되어 지정된다.
  2. 요청과 승인 대기보호 대상 작업(볼트 락 해제, 볼트 삭제 등)이 요청되면, 요청자와 다른 역할의 승인이 있을 때까지 작업이 실행되지 않고 대기한다.
  3. 승인 후 실행·기록승인이 완료되면 작업이 실행되고, 요청·승인 내역이 감사 로그에 남는다.

#5한 줄 요약

볼트 락 해제나 볼트 삭제 같은 민감 작업을 서로 다른 역할의 승인을 받아야만 실행되게 하여 단일 권한 탈취로 백업이 파괴되는 것을 막는 것

온디맨드 백업

백업 플랜과 무관하게 지금 필요한 시점에 즉시 백업을 한 번 생성하는 수동 백업 방식으로, 복구 지점이 바로 만들어지고 보존 기간만 지정하면 된다.

#1문제 상황

예약 기반 백업은 백업 계획에 지정된 시각에만 실행되므로, 주기적 보호에는 좋지만 "지금 이 순간"의 상태를 남겨두기에는 부족하다. 예를 들어 큰 변경을 적용하기 직전이나 서비스 출시 직전에 상태를 확보하고 싶어도, 다음 예약 시각이 몇 시간 뒤라면 그 사이의 위험을 그대로 감수해야 한다. 또 예약 방식은 해당 리소스가 백업 계획에 연결되어 있어야만 동작한다.

#2핵심 질문

예약 주기와 상관없이, 지금 필요한 순간에 백업을 하나 즉시 만들려면 어떻게 해야 할까?

#3동작 예시

온디맨드 백업은 사용자가 명령을 내리는 즉시 백업 작업이 만들어져 실행된다. 예를 들어 데이터베이스에 큰 스키마 변경을 적용하기 직전에 온디맨드 백업을 실행하면, 변경 전 상태의 복구 지점이 그 자리에서 하나 확보된다.

#4동작 과정

  1. 요청대상 리소스(예: EC2, RDS, S3)와 보존 기간을 지정해 온디맨드 백업을 요청한다.
  2. 백업 실행AWS Backup이 백업 볼트에 복구 지점을 만들고, 지정한 보존 기간까지 보관한다. 기존 예약 백업과 독립적으로 실행된다.
  3. 복구 지점 확인·사용생성된 복구 지점을 백업 볼트 목록에서 확인하고, 이후 복원 작업의 대상으로 사용한다.

연속 백업과 PITR

데이터 변경을 지속적으로 기록해 과거 특정 시점(초 단위)으로 되돌릴 수 있게 하는 백업 방식으로, 백업 플랜에 연속 백업 규칙을 추가해 활성화한다.

#1문제 상황

스냅샷 기반 백업은 하루 한 번처럼 정해진 시점에만 복구 지점을 만들기 때문에, 그 시점 사이의 변경 사항은 백업에 반영되지 않는다. 예를 들어 백업이 밤 2시에 실행되는데 낮 3시에 데이터를 잘못 지웠다면, 복원해도 밤 2시 상태까지만 돌아갈 수 있고 그 사이의 수 시간간 데이터 손실을 감수해야 한다. 복구가 가능한 시점이 "마지막 백업 시각" 하나뿐이라는 한계가 있다.

#2핵심 질문

정해진 시점이 아니라, 몇 분 전의 아무 시점으로나 데이터를 되돌리려면 어떻게 해야 할까?

#3동작 예시

연속 백업은 데이터의 변경 사항을 계속 기록해 두고, 사용자가 임의의 시점을 지정하면 그 시점의 상태로 복구 지점을 만들어 준다. 예를 들어 낮 3시 14분에 데이터를 잘못 지웠다면 3시 13분을 지정해 복원하면 되고, 손실은 1분 분량으로 줄어든다.

#4동작 과정

  1. 연속 기록 시작백업 계획에서 연속 백업 옵션을 켜면, AWS Backup이 지원 서비스의 데이터 변경 사항을 계속 추적해 기록한다.
  2. 복원 시점 선택복원 화면에서 되돌아가고 싶은 시점을 지정하면, 그 시점까지 기록된 변경 사항을 기준으로 복구 지점이 생성된다.
  3. 복구 지점 복원생성된 복구 지점으로 리소스를 복원한다. 지정한 시점 이후의 변경 사항은 결과에 포함되지 않는다.

#5한 줄 요약

데이터 변경 사항을 계속 기록해 두고 사용자가 고른 임의 시점의 복구 지점을 만들어, 마지막 백업 이후의 데이터 손실 폭을 최소화하는 것

백업 작업 관리: 중지·목록

실행 중인 백업 작업을 즉시 중지하거나, 계정의 백업(복구 지점)과 작업 상태를 콘솔·CLI로 목록 조회해 관리하는 기능.

#1문제 상황

기존에는 백업 작업이 어느 서비스에서 실행 중인지, 성공했는지 실패했는지를 알려면 각 서비스의 콘솔을 따로 열어 확인해야 했다. 또 실행 중인 백업 작업을 멈출 수단이 명확하지 않아, 실수로 시작된 대량 백업이나 오래 걸리는 작업을 끝날 때까지 그대로 기다려야 했다. 잘못 실행된 작업이 전체 자원을 소모해도 중간에 끊을 방법이 마땅치 않았다.

#2핵심 질문

여러 곳의 백업 작업을 한곳에서 보고, 실행 중인 작업을 필요할 때 즉시 중지하려면 어떻게 해야 할까?

#3동작 예시

AWS Backup 콘솔의 백업 작업 화면에서 실행 중·완료·실패한 모든 작업이 상태와 함께 한 목록으로 보인다. 예를 들어 잘못된 볼트를 대상으로 한 대량 백업이 실수로 실행 중이라면, 그 작업을 선택해 중지 명령을 내리면 즉시 중단되고 목록에 중지됨 상태로 기록으로 남는다.

#4동작 과정

  1. 목록 조회백업 작업 탭에서 전체 작업을 상태(실행 중·완료·실패·중지됨), 시작 시간, 대상 볼트와 함께 조회한다.
  2. 중지 요청실행 중인 작업을 선택해 중지를 요청하면, 작업이 중단 상태가 된다.
  3. 이력 확인 및 재시도중지된 작업과 실패한 작업(실패 사유 포함)을 목록에서 확인하고, 필요하면 해당 리소스에 대해 다시 백업을 요청한다.

백업 검색

태그, 리소스 유형, 시간 범위, 리소스 ID 등 조건으로 백업(복구 지점)의 메타데이터를 빠르게 찾아 확인하는 검색 기능.

#1문제 상황

기존에는 백업된 데이터를 찾으려면 백업 파일 목록을 일일이 열어 보거나, 백업이 저장된 대상(예: 스토리지 버킷, 볼륨 스냅샷)에 직접 접근해서 내용을 뒤져야 했다. 백업 파일의 이름만으로는 어떤 데이터가 들어 있는지 알 수 없어서, 원하는 시점의 특정 리소스를 찾으려면 여러 백업을 전부 열어보는 수밖에 없었고, 백업 수가 늘어날수록 찾는 시간도 함께 늘어났다.

#2핵심 질문

수많은 백업 중에서 원하는 데이터가 들어 있는 백업을 어떻게 빠르게 찾을 수 있을까?

#3동작 예시

AWS Backup의 검색 기능은 백업된 리소스의 메타데이터(리소스 이름, 태그, 백업 생성 시각, 리소스 유형 등)를 검색 대상으로 삼아, 백업 내용물을 실제로 열지 않고도 조건을 지정해서 원하는 백업을 찾아준다. 예를 들어 "가장 최근에 생성된, 'prod' 태그가 붙은 RDS 백업" 같은 조건을 걸면 조건에 맞는 백업만 목록으로 보여 준다.

#4동작 과정

  1. 검색 조건 지정찾고 싶은 항목을 기준으로 검색 필터(리소스 유형, 태그, 생성 시각, 리소스 이름 등)를 설정한다.

5백업 복사·태그·계층05-01

백업 복사와 태그 복사

백업이 완료된 복구 지점의 사본을 만들고 원본 백업에 있던 태그를 사본에도 그대로 복사하는 기능.

#1문제 상황

백업은 기본적으로 생성된 볼트에만 남습니다. 재해에 대비해 다른 위치에 백업 사본을 두고 싶으면 별도 도구로 복사 작업을 직접 만들고 관리해야 했고, 원본 리소스에 붙어 있던 태그도 사본에는 자동으로 따라가지 않아 일일이 다시 달아야 했습니다. 태그가 없으면 백업을 보고도 어떤 서비스·환경의 것인지 식별하기 어렵고, 비용을 부서·프로젝트별로 배분하는 것도 어렵습니다.

#2핵심 질문

백업 사본을 만들 때 원본에 붙어 있던 태그까지 함께 복사해 사후 식별과 관리를 가능하게 하려면?

#3동작 예시

백업 플랜에 복사 규칙(copy rule)을 하나 추가하면 새 복구 지점(백업)이 생성될 때마다 지정한 대상 볼트로 자동 복사됩니다. 같은 플랜에서 태그 복사 옵션을 켜면 원본 리소스에 붙어 있던 태그가 복구 지점과 그 복사본에 그대로 적용됩니다. 덕분에 백업을 만들 때와 복사할 때를 분리해 생각할 필요 없이, 플랜이 두 작업을 한 번에 처리합니다.

복원 개요

복원은 백업된 복구 지점에서 리소스를 다시 만들어 내는 작업이며, 리소스 유형별로 복원 대상·방식·절차가 정해져 있다.

#1문제 상황

기존에는 백업을 만들어 두어도 실제로 데이터를 되살리는 복원 작업은 대부분 수동으로 처리했다. 리소스 종류마다 해당 서비스의 콘솔에 직접 들어가서 백업 이미지를 찾고, 새 인스턴스나 새 테이블을 만들고, 연결 정보를 다시 설정하는 식이었다. 이 방식은 서비스마다 화면과 절차가 달라서 매번 새로 배워야 했고, 복원이 제대로 되었는지 확인하는 일도 사람이 일일이 해야 했다. 그 결과 절차 중간에 설정을 빠뜨리거나 복원 위치를 잘못 지정하는 실수가 잦았고, 검증이 늦어져 장애가 오래 지속되는 경우가 많았다.

#2핵심 질문

백업해 둔 데이터를 단 하나의 일관된 절차로 안전하게 되살릴 수는 없을까?

#3동작 예시

AWS Backup 콘솔의 복원 기능 하나로, RDS 데이터베이스 백업을 고르고 대상 리전과 새 인스턴스 사양을 지정하면, AWS Backup이 백업 저장소에서 데이터를 읽어 새 DB 인스턴스를 만들어 데이터를 되돌려 준다. 원본 인스턴스는 건드리지 않으므로 복원 중에도 기존 서비스는 그대로 동작한다.

#4동작 과정

#1문제 상황

기존에는 데이터베이스와 파일 시스템을 복원할 때 서비스마다 전혀 다른 절차를 따라야 했다. RDS는 RDS 콘솔에서 스냅샷을 찾아 새 인스턴스로 복원하고, DynamoDB는 테이블 복원 메뉴를 따로 찾아야 했으며, EFS나 FSx 같은 파일 시스템은 또 별도의 복원 화면을 사용했다. 절차가 제각각이라 운영자는 여러 서비스의 복원 방법을 모두 익혀야 했고, 백업 도구가 달라지면 백업 보관 위치도 흩어져 어디에 무엇이 있는지 파악하기 어려웠다.

#2핵심 질문

#3동작 예시

#4동작 과정

  2. 데이터 복원 실행AWS Backup이 백업에서 데이터를 읽어 새 데이터베이스 인스턴스 또는 새 파일 시스템을 생성한다.
  3. 새 리소스 확인생성된 리소스의 연결 정보(데이터베이스 엔드포인트, 파일 시스템 ID 등)를 확인하고 애플리케이션에 연결한다.

#1문제 상황

#2핵심 질문

#3동작 예시

EC2 인스턴스의 백업을 복원하면 백업 시점의 디스크 상태가 담긴 이미지로 새 인스턴스가 만들어진다. CloudFormation 스택 백업을 복원하면 스택을 정의한 템플릿 전체가 다시 실행되면서 그 안의 인스턴스, 보안 그룹, 로드 밸런서 등이 한 번에 재구성된다.

#4동작 과정

  1. 복원할 리소스 선택복구할 EC2 인스턴스, 가상 머신, 또는 CloudFormation 스택의 백업을 고르고 대상 리전과 사양을 지정한다.
  2. 통합 복원 실행AWS Backup이 백업 데이터로 새 인스턴스를 생성하거나, 스택 템플릿 전체를 재배포해 포함된 리소스들을 함께 만든다.

복원 테스팅

복원 테스팅은 복구 지점이 실제로 유효한지 자동 복원 실행으로 주기적으로 검증해 백업의 복원 가능성을 보장하는 기능이다.

#1문제 상황

기존에는 백업이 실제로 복원 가능한지 확인하려면 직접 복원 작업을 실행하고 사람이 일일이 결과를 검증해야 했다. 복원은 시간과 비용이 드는 작업이라 자주 시도하지 않았고, 그래서 실제 재해 상황에서 복원을 시작하고 나서야 백업이 손상되었거나 설정이 잘못되었다는 사실을 발견하는 경우가 많았다. 검증 과정이 없던 백업은 "백업했다"는 사실만 있고, 실제로 되살릴 수 있는지는 확인되지 않은 상태였다.

#2핵심 질문

실제 재해가 오기 전에 복원이 제대로 되는지 정기적으로 자동 검증할 수는 없을까?

#3동작 예시

AWS Backup의 복원 테스팅은 복원 테스트 계획을 만들어 두면, 지정한 백업을 실제로 격리된 환경에 복원해 보고 미리 정한 검증 조건을 통과하는지 자동으로 판정한다. 예를 들어 "이 백업 계획의 백업은 매주 복원 테스트를 통과해야 한다"는 규칙을 걸어 두면 매주 자동으로 복원이 시도되고 결과가 기록된다.

#4동작 과정

  1. 테스트 계획 정의테스트할 백업, 복원 대상 리소스 유형, 통과 기준(예: 복원 성공 상태 확인)을 지정한다.
  2. 자동 복원 실행정해진 주기에 따라 AWS Backup이 백업을 실제로 복원하고 검증 데이터를 수집한다. 실제 운영 리소스와 분리된 환경에서 실행된다.
  3. 판정과 알림복원 성공 여부를 기준에 따라 판정하고, 결과를 콘솔에 기록하며 EventBridge(이벤트 알림 서비스)를 통해 실패를 통지한다.

백업이 잘 되고 있는지 확인하려면 보통 사람이 대시보드를 열어 백업 작업의 성공·실패를 하나씩 눈으로 확인한다. 여기에 감사(감사: 규정이나 사내 정책대로 백업이 이루어지고 있는지 증거를 남기며 점검하는 일) 요건이 붙으면 문제가 커진다. 예를 들어 "모든 리소스가 최소 1년 보관 규칙으로 백업되어야 한다"는 정책이 있어도, 리소스가 수백 개라면 사람이 일일이 확인할 수 없고, 확인했다 해도 그 기록이 남지 않아 규정 준수 증거로 쓸 수 없다. 또한 문제를 발견해도 누가 언제 고쳤는지 추적할 방법이 없어서, 점검 자체가 반복 가능한 절차가 되지 못한다. 규모가 커질수록 사람 눈에 의존한 점검은 누락과 증거 부족이라는 두 가지 한계에 부딪힌다.

#2핵심 질문

백업이 정책대로 이루어지고 있는지를 자동으로 검사하고, 어긋난 부분을 발견하면 바로잡아 그 기록까지 남길 수는 없을까?

#3동작 예시

AWS Backup Audit Manager(감사 관리자)는 사용자가 만든 프레임워크(감사 프레임워크: "이런 규칙으로 백업되어야 한다"는 검사 항목 모음)를 기준으로, 계정 안의 모든 백업 대상을 주기적으로 검사한다. 예를 들어 "백업 볼트(백업 저장소)에 KMS(키 관리 서비스) 암호화가 적용되어 있는가" 같은 컨트롤(개별 검사 항목)을 프레임워크에 넣어 두면, Audit Manager가 그 규칙을 위반한 리소스 목록을 자동으로 찾아낸다. 통합 측면에서는 AWS Audit Manager(AWS의 별도 감사 서비스)와 연결해, Backup 쪽의 검사 결과가 조직 전체 감사 증거에 함께 실리게 할 수 있다.

#4동작 과정

  1. 프레임워크와 컨트롤 설정사용자가 검사하고 싶은 규칙(컨트롤)을 골라 프레임워크(검사 항목 묶음)를 만들고, 어느 리소스 범위를 검사할지 지정한다. 백업 작업 전체에서 규칙 위반 여부 검사가 필요한 리소스를 추적하도록 켜 둔다.
  2. 자동 검사와 위반 탐지Audit Manager가 정기적으로 각 리소스의 설정·백업 이력을 프레임워크의 컨트롤과 대조해, 규칙을 지키는지(준수) 위반하는지(비준수) 판정하고 그 결과를 대시보드에 표시한다.
  3. 리메디에이션(바로잡기)과 증거 기록위반 리소스가 발견되면 해당 리소스에 백업 계획을 연결하거나 설정을 고쳐 위반을 해소하고, AWS Audit Manager와의 통합으로 검사 결과와 조치 기록이 감사 보고서에 반영되어 규정 준수 증거로 남는다.

#1문제 상황

#2핵심 질문

여러 AWS 계정에 흩어져 있는 백업 구성을 하나의 조직 단위에서 일관되게 만들고 관리할 수는 없을까?

#3동작 예시

AWS Organizations(여러 AWS 계정을 하나의 조직으로 묶어 관리하는 서비스)를 사용하면, 관리 계정(조직 전체를 통제하는 대표 계정) 하나에서 조직 전체에 적용할 백업 정책을 만들 수 있다. 그 정책을 조직 단위(OU: 계정들을 묶어 두는 그룹)에 연결하면, 해당 그룹에 속한 모든 계정의 리소스가 그 백업 정책을 자동으로 따라간다. 계정 개별 설정이 아니라 조직 구조에 정책을 붙이는 방식이라, 계정이 늘어나도 새 계정에는 정책이 자동 적용된다.

#4동작 과정

  1. 조직 구성과 정책 작성관리 계정에서 AWS Organizations로 계정들을 조직 단위로 묶고, 조직 전체에 쓸 백업 정책(백업 계획·보관 규칙 묶음)을 만든다.
  2. 조직 단위에 정책 연결만든 백업 정책을 대상 조직 단위에 연결하면, 그 안의 모든 계정이 정책 정의를 상속(이어받음)해 일관된 백업 규칙을 갖게 된다.
  3. 계정별 실행과 중앙 확인각 계정은 상속받은 정책에 따라 백업 작업을 실행하고, 관리 계정에서는 조직 전체의 백업 상태·정책 적용 범위를 한곳에서 확인한다.

EventBridge·CloudWatch·SNS 알림

백업 작업의 상태 변화를 EventBridge 이벤트, CloudWatch 지표, SNS 알림으로 감지해 통보받는 기능.

#1문제 상황

백업 실패를 알려면 사람이 대시보드를 직접 열어야 했으므로, 백업이 실패해도 당장 알 수 없고 다음 점검 때 발견하는 일이 많았다. 대시보드는 "보러 가야" 보이는 도구라서, 실패가 발생한 순간에 알림을 받으려면 별도의 장치가 필요하다. 또한 지표가 숫자로만 흘러가면 어느 지표가 이상인지 사람이 판단해야 하고, 실패 건수를 평균으로만 보면 개별 작업의 실패가 묻히기도 한다. 상태를 능동적으로 전달해 주는 채널이 없다는 것이 핵심 한계다.

#2핵심 질문

#3동작 예시

AWS Backup은 백업·복원 작업의 상태 변화(성공·실패·시작 등)를 이벤트(사건: 시스템에서 발생한 상태 변화)로 만들어 Amazon EventBridge(이벤트를 받아 규칙에 따라 다른 서비스로 전달하는 서비스)에 보낸다. 예를 들어 "백업 작업 실패" 이벤트가 오면 EventBridge 규칙이 그것을 감지해 Amazon SNS(알림 메시지를 이메일·문자 등으로 보내는 서비스) 주제로 전달하고, 등록된 담당자에게 실패 알림 메일이 즉시 발송된다. 이벤트라는 공통 형식 덕분에 알림뿐 아니라 다른 AWS 서비스를 트리거(후속 동작을 시작하게 함)하는 것도 가능하다.

#4동작 과정

  1. 이벤트 발생AWS Backup이 백업 작업의 상태 변화(성공·실패·복원 완료 등)를 이벤트로 만들어 EventBridge로 보낸다.
  2. 규칙에 의한 전달EventBridge의 규칙이 특정 이벤트 패턴(예: "실패" 이벤트)과 일치하는 것을 감지하면, 규칙에 지정된 대상으로 이벤트를 전달한다. 대상은 SNS 주제나 다른 AWS 서비스가 될 수 있다.
  3. 알림 수신과 후속 조치SNS가 이메일·문자 등으로 담당자에게 알림을 보내고, 필요하면 다른 서비스가 후속 작업(예: 로그 기록, 복구 시도)을 실행한다. 지표의 경우 CloudWatch(지표를 수집·저장하고 임계값을 넘으면 알리는 서비스)가 백업 지표를 모아 두고, 설정한 임계값을 넘으면 같은 방식으로 알림을 낸다.

#3동작 예시

AWS CloudTrail(계정 안에서 일어난 API 호출을 기록하는 서비스)은 AWS Backup을 포함한 모든 AWS 서비스의 조작을 로그(기록)로 남긴다. 예를 들어 누군가 백업 계획을 만들거나 삭제하면, CloudTrail은 "누가(사용자), 언제(시각), 무엇을(API 호출 이름), 어떤 리소스에"라는 내용의 이벤트(사건 기록)를 생성해 이벤트 기록 화면에 저장한다. 이 기록은 AWS Backup 콘솔에서 본 백업 작업 결과와는 별개로, API 수준의 조작 전부를 담는다.

#4동작 과정

  1. API 호출 감지 및 기록사용자나 도구가 AWS Backup의 API를 호출하면(예: 백업 계획 생성, 볼트 삭제), CloudTrail이 그 호출을 이벤트로 기록하고 콘솔의 이벤트 기록에 저장한다.
  2. 상세 정보 확인이벤트 기록에서 해당 이벤트를 열면 호출한 사용자·시각·요청 내용·응답 결과 등 상세 정보를 확인한다.
  3. 영구 보관과 추가 분석필요하면 이벤트를 S3(객체 저장소)에 영구 보관하거나 다른 분석 도구로 전달해, 사고 조사·감사 때 과거 조작 기록을 근거로 사용한다.

보안 개요·데이터 보호·암호화

AWS Backup 보안 모델의 전체 그림으로, 저장·전송 데이터 암호화(KMS 키)를 포함해 백업 데이터를 보호하는 메커니즘을 개괄한다.

#1문제 상황

백업 데이터는 원본과 별개로 저장되지만, 그 저장소(볼트: 백업 저장소)에 아무나 접근할 수 있거나 데이터가 평문으로 저장된다면 백업이라는 안전장치가 오히려 데이터 유출 경로가 된다. 원래 백업을 만들면 데이터가 기본적으로 AWS 관리형 암호화(서비스가 소유한 키로 자동 암호화)로 저장되지만, 회사가 자체 키로 관리해야 하는 규정(예: 키를 직접 관리해야 하는 보안 정책)이 있으면 기본 설정만으로는 기준을 충족하지 못한다. 또한 누가 볼트에 접근해 백업을 보거나 삭제할 수 있는지에 대한 통제가 없으면, 권한이 넓은 계정 하나가 모든 백업을 지울 수 있는 상황도 가능하다. 저장 데이터의 암호화와 접근 통제가 백업 보안의 핵심인데, 이 둘을 명시적으로 구성하지 않으면 안전하다고 보기 어렵다.

#2핵심 질문

백업 데이터가 저장되는 동안 안전하게 암호화되고, 접근 권한이 통제되어 유출이나 삭제로부터 보호되게 할 수는 없을까?

#3동작 예시

AWS Backup은 백업을 볼트에 저장할 때 KMS(키 관리 서비스) 암호화 키로 데이터를 암호화한다. 기본적으로는 AWS가 관리하는 키가 자동 사용되지만, 사용자가 자신의 KMS 키를 만들어 볼트에 지정할 수도 있다. 예를 들어 회사 키 관리 정책에 따라 자체 키를 생성해 백업이 저장되는 볼트에 연결하면, 그 볼트에 저장되는 모든 백업 데이터가 그 키로 암호화된다. 여기에 볼트 접근 정책(볼트 액세스 정책: 누가 그 볼트에 백업을 넣거나 꺼내거나 삭제할 수 있는지를 정의하는 규칙)을 함께 설정하면, 데이터 보호(암호화)와 접근 통제가 백업 저장소 단위에서 한 번에 적용된다.

#4동작 과정

  1. 키와 볼트 구성사용자가 KMS 키를 준비하고 볼트(백업 저장소)에 연결해, 앞으로 저장되는 백업 데이터가 그 키로 암호화되도록 한다. 기본을 쓰면 AWS 관리형 키로 자동 암호화된다.
  2. 접근 정책 설정볼트 액세스 정책으로 이 볼트에 백업을 보내고, 복원하고, 삭제할 수 있는 주체와 조건을 정의해 접근을 통제한다. IAM(이용자 권한 관리 서비스) 권한과 함께 적용된다.
  3. 암호화된 저장과 보호 확인백업 데이터가 지정된 키로 암호화된 채 볼트에 저장되고, 권한 없는 요청은 정책에 따라 차단된다. 복원 시에는 권한과 키가 모두 확인된 뒤에만 데이터가 제공된다.

#5한 줄 요약

백업 데이터를 KMS 암호화 키로 저장 시 암호화하고 볼트 접근 정책으로 접근을 통제해, 저장 중인 백업을 유출·삭제로부터 보호하는 것

IAM: 인증과 접근 제어

AWS Backup을 사용하는 주체(사용자·역할)를 인증하고, 정책으로 백업 생성·복원·볼트 접근 등 권한을 세밀하게 제어하는 체계다.

#1문제 상황

백업을 관리하려면 EC2 스냅샷 생성, 볼트 저장, 복원 같은 작업을 AWS에서 실행할 수 있어야 한다. 기존 방식은 계정의 루트 사용자(모든 권한을 가진 계정 소유자)나 광범위한 관리자 권한으로 이 작업을 처리했다. 이렇게 하면 백업을 만들기 위해 계정 전체의 권한이 노출되고, 누가 어떤 백업을 만들고 지웠는지 개별적으로 추적·제한하기 어렵다. 또 업무별로 "백업만 담당하는 사람"에게 과한 권한을 주게 되어 실수나 오용의 범위가 커진다.

#2핵심 질문

누가 어떤 백업 작업을 할 수 있는지를 계정 전체 권한 없이 개별적으로 통제할 수 있을까?

#3동작 예시

백업 담당자에게만 백업 전용 권한을 주는 경우를 보면, 관리자는 IAM에서 해당 담당자용 IAM 사용자(로그인할 수 있는 개별 신분)를 만들고 여기에 AWSBackupFullAccess 정책(백업 서비스의 모든 작업을 허용하는 미리 정의된 권한 묶음)을 붙인다. 이 사용자는 백업을 만들고 복원할 수 있지만 EC2 인스턴스를 새로 생성하거나 다른 서비스를 건드리는 권한은 없다.

#4동작 과정

  1. 인증IAM 사용자나 역할이 자격 증명(암호 또는 액세스 키)으로 AWS에 로그인해 "누구인지"를 확인한다.
  2. 권한 평가요청한 백업 작업을 IAM 정책(어떤 작업을 허용할지 적은 규칙)과 대조해 허용 여부를 판단한다. 정책에 없으면 거부된다.
  3. 작업 수행·기록허용된 백업 작업만 실행되고, 모든 호출은 CloudTrail(AWS API 호출 기록 서비스)에 남아 누가 무엇을 했는지 나중에 확인할 수 있다.

서비스 역할·관리형 정책·연결 역할

AWS Backup이 AWS 리소스에 접근하도록 부여하는 IAM 서비스 역할·AWS 관리형 정책·서비스 연결 역할(service-linked role) 구성이다.

#1문제 상황

백업 서비스는 사용자 대신 EC2 스냅샷, S3 객체, RDS 데이터베이스 등 다른 AWS 서비스에 접근해야 한다. 기존 방식은 이 접근에 사용자 개인의 자격 증명(액세스 키)을 서비스에 저장해 쓰는 경우가 많았다. 그러면 자격 증명이 유출될 위험이 있고, 만료되면 백업이 멈추며, 권한이 과하게 주어지기 쉽다. 자격 증명을 서비스가 직접 보관한다는 것 자체가 보안 취약점이다.

#2핵심 질문

백업 서비스가 사용자의 개인 자격 증명을 보관하지 않고도 다른 AWS 서비스에 안전하게 접근할 수 있을까?

#3동작 예시

백업 플랜을 처음 만들면 AWS Backup이 자동으로 연결 역할(service-linked role, AWS가 생성·관리하는 전용 역할)인 AWSServiceRoleForBackup을 만들고, 여기에 관리형 정책(백업 작업에 필요한 권한을 AWS가 미리 정의해 둔 정책)인 AWSBackupServiceRolePolicyForBackup을 붙인다. 이 역할을 백업 플랜에 지정하면 AWS Backup은 사용자 키 없이 그 역할로 S3와 EC2에 접근해 백업을 만든다.

#4동작 과정

  1. 역할 생성최초 백업 작업 시 연결 역할이 자동으로 만들어지고, 수명주기(생성·갱신·삭제)도 AWS가 관리한다.
  2. 정책 부여관리형 정책이 역할에 필요한 최소 권한을 연결해, 백업에 필요한 서비스만 접근 가능하게 한다.
  3. 역할 위임사용자가 백업 플랜에서 이 역할을 지정하면, AWS Backup이 그 역할의 신분으로 다른 서비스에 접근해 백업·복원을 수행한다.

무결성과 맬웨어 보호

체크섬 검증으로 백업 데이터 무결성을 유지하고, 맬웨어 감지 옵션으로 복원 시 악성 파일 유입 위험을 차단하는 보호 기능이다.

#1문제 상황

백업은 나중에 복원해서 쓰는 데이터이므로, 저장·전송 과정에서 내용이 변조되거나 악성코드에 감염되면 복원해도 안전하지 않다. 기존 방식은 백업을 만들고 저장하기만 하고, 그 데이터가 원본과 같은지 또는 악성 파일을 포함하는지 확인할 수단이 없는 경우가 대부분이었다. 검증이 없으면 손상된 백업을 그대로 복원해 감염을 퍼뜨리거나, 잘못된 데이터를 신뢰하게 되는 사고가 난다.

#2핵심 질문

백업 안의 데이터가 변조되거나 악성코드에 감염됐는지 복원 전에 어떻게 확인할까?

#3동작 예시

AWS Backup은 백업 저장과 복원 시 체크섬(데이터가 같은지 비교하는 검증 값)으로 내용이 원본과 일치하는지 확인하고, 맬웨어 보호 기능이 백업된 데이터 안에서 알려진 악성 코드를 탐지한다. 감염이 발견된 백업은 보고되고, 사용자는 그 백업으로 복원하지 않도록 판단할 수 있다.

#4동작 과정

  1. 무결성 검증백업을 저장하거나 복원할 때 체크섬을 비교해 전송·저장 중 데이터가 변조되지 않았는지 확인한다.
  2. 맬웨어 검사맬웨어 보호가 백업된 파일을 악성 코드 시그니처(알려진 악성 패턴)와 대조해 감염 여부를 탐지한다.
  3. 결과 보고검증 실패나 감염 발견 결과를 사용자에게 보고해, 손상된 백업으로 복원하는 사고를 미리 막는다.

법적 보존(legal hold)

복구 시점에 법적 보존을 걸어 보존 기간·규칙과 무관하게 백업이 삭제·만료되지 않도록 잠그는 기능이다.

#1문제 상황

소송이나 규제 조사가 진행되는 동안에는 관련된 백업을 어떤 이유로든 삭제하면 안 된다. 기존 방식은 볼트 락(WORM, 설정 후 되돌릴 수 없는 보존 잠금)으로 전체 볼트를 잠그거나, 보존 기간을 길게 잡아 수동으로 관리했다. 볼트 락은 되돌릴 수 없게 설정해야 하고 볼트 전체에 적용되어, 특정 시점의 백업만 유연하게 보존해야 하는 법적 요구에는 맞지 않는다. 보존 기간만으로는 기간이 지나면 자동 삭제되어 조사 중인 데이터가 사라질 수 있다.

#2핵심 질문

소송·규제 조사가 끝날 때까지 특정 백업이 어떤 경로로도 삭제되지 않게 하려면 어떻게 해야 할까?

#3동작 예시

법무팀이 조사 대상 시점의 복구 지점(백업 하나)에 legal hold를 적용하면, 그 백업은 보존 기간이 지나 자동 삭제 대상이 되거나 누군가 수동으로 삭제를 시도해도 삭제되지 않는다. 조사가 끝나고 legal hold를 해제한 뒤에야 그 백업은 다시 삭제할 수 있다.

#4동작 과정

  1. 보존 대상 지정보존할 복구 지점을 선택해 legal hold를 적용한다.
  2. 삭제 차단hold가 걸린 백업은 자동 보존 기간 만료 삭제와 수동 삭제 요청 모두 거부된다.
  3. 해제 후 삭제 허용조사 종료 후 legal hold를 해제하면 그때부터 백업을 삭제할 수 있다.

#2핵심 질문

쿼터(한도)

계정당 AWS Backup 리소스 사용량에 적용되는 기본 한도(쿼터)와 증가 요청 방법을 안내하는 문서.

#1문제 상황

AWS Backup을 사용하려면 백업 계획, 백업 볼트, 복구 시점(복구 지점), 백업 작업 등 리소스를 계속 만들어 나간다. 이 리소스들은 만들고 싶은 만큼 무한정 만들 수 있는 것이 아니라 AWS 계정마다 개수·크기·속도에 상한이 정해져 있다. 계획만 세우고 실행하면, 상한에 걸려 백업 생성이 실패하거나 API 호출이 거부되는 상황이 발생한다. 어떤 한도가 있는지 알지 못하면 운영 중에 갑자기 실패를 만나게 된다.

#2핵심 질문

백업을 아무리 많이 만들고 싶어도, AWS Backup이 계정에 허용하는 한도를 넘지 않으면서 안정적으로 운영하려면 어떻게 해야 할까?

#3동작 예시

계정의 백업 볼트 개수 한도가 예를 들어 1,000개라고 할 때, 1,000번째 볼트까지 만들었다면 1,001번째 볼트 생성 시도는 실패로 끝난다. 이 한도는 지역(리전)마다 별도로 적용되며, AWS 콘솔의 Service Quotas 페이지에서 현재 사용량과 기본 한도를 확인할 수 있다. 필요한 경우 한도 증가 요청을 통해 상한을 올릴 수도 있다.

#4동작 과정

  1. 한도 확인AWS 콘솔의 Service Quotas 또는 AWS CLI로 계정이 가진 AWS Backup 리소스별 기본 한도를 확인한다. 한도는 리소스 종류(볼트, 계획, 작업 등)마다 다르고 리전마다 따로 적용된다.
  2. 사용량 점검과 계획현재 만들어진 리소스 수를 세어 한도에 가까워졌는지 판단하고, 증가가 필요하면 Service Quotas에서 한도 증가 요청을 제출한다.
  3. 한도 내 운영증가 요청이 승인되기 전까지는 기존 볼트·계획을 정리하거나 백업 주기를 조정해 사용량을 한도 안에 유지하면서 백업을 계속 실행한다.

  1. 동작 선택수행하려는 작업(계획 생성, 볼트 만들기, 작업 실행, 복원 시작, 상태 조회 등)에 해당하는 API 이름을 찾는다. API 참조 문서에는 동작별 요청 파라미터가 정리되어 있다.
  2. 요청 구성과 호출필요한 파라미터(리소스 이름, IAM 역할, 기존 리소스 ID 등)를 채워 AWS CLI·SDK·HTTP 요청으로 API를 호출한다.
  3. 응답 확인반환된 작업 ID나 리소스 ID를 받아 다음 작업에 사용하거나, GetBackupJob 등의 조회 API로 작업 진행 상태를 확인한다.

#5한 줄 요약

AWS Backup의 모든 기능을 만들기·조회·삭제·실행 단위의 API 호출로 노출해서, 콘솔 없이 프로그램과 스크립트로 백업 전체를 자동화할 수 있게 하는 것
