1AWS Backup의 출발점01-01

AWS Backup이 해결하는 문제와 중앙 집중식 데이터 보호

여러 AWS 서비스에 흩어진 백업을 서비스별로 따로 관리하지 않고 한 곳에서 정책으로 통합 관리·감사하게 해주는 완전관리형 서비스다.

1상대의 출발점 확인

기존에는 각 AWS 서비스마다 자체 백업 기능이 있었습니다. EC2(EBS 스냅샷), RDS(자동 백업), DynamoDB(스냅샷), EFS(스냅샷) 등이 따로따로 백업을 관리했습니다. 이렇게 되면 서비스별로 다른 인터페이스를 사용해야 하고, 보존 기간·복원 정책·감사 로그가 제각각이라 통일된 백업 전략을 실행하기 어렵습니다. 특히 여러 서비스를 쓰는 환경에서는 어느 리소스가 백업되고 있는지, 복구 정책이 무엇인지 파악하기 까다로워집니다.

2질문 제기

여러 AWS 서비스의 백업을 한 곳에서 정책으로 통합 관리하고 감시할 수 있는 방법이 있을까요?

3구조적 핵심 예시

AWS Backup은 전체 조직의 백업 정책을 하나의 계획으로 정의하고, 그 계획을 여러 서비스의 리소스들에게 한 번에 할당합니다. 예를 들어 '본프로덕션 DB는 매일 오전 2시에 백업하고 30일 유지'라는 규칙 한 개를 만들면, 그 규칙이 RDS·DynamoDB·S3 등 여러 서비스에 속한 리소스들을 동시에 관리합니다.

4단계별 동작 과정

  1. 백업 정책 정의사용자가 AWS Backup 콘솔에서 백업 계획을 만들 때, 언제 백업할지(일정), 얼마나 보관할지(보존 기간), 어디에 저장할지(암호화·교차 리전 전송 여부)를 정합니다.
  2. 리소스 할당그 계획을 EBS 볼륨, RDS 인스턴스, DynamoDB 테이블 등에 태그나 명시적 선택으로 할당하면, 서비스별 자체 백업 기능을 사용하는 대신 AWS Backup이 통일된 방식으로 관리합니다.
  3. 중앙 감시·복구AWS Backup 대시보드에서 모든 리소스의 백업 상태, 저장된 복구 지점, 복원 이력을 한 곳에서 볼 수 있으며, 언제든 복구 지점을 선택해 복원을 시작할 수 있습니다.

5본질 요약

AWS의 여러 서비스에 산재한 백업 기능들을 하나의 중앙 통제 지점으로 통합해 정책 기반의 일관된 데이터 보호와 감시를 제공하는 것

1AWS Backup의 출발점01-02

핵심 구성요소와 첫 백업: 계획·규칙·볼트·복구 지점·작업

백업 계획(플랜) 안의 규칙이 일정과 보존을 정하고, 실행되면 백업 작업이 생겨 복구 지점이 볼트에 저장되는 것이 AWS Backup의 기본 흐름이다.

1상대의 출발점 확인

AWS Backup을 처음 쓸 때는 용어가 혼란스러울 수 있습니다. '계획'과 '규칙', '볼트'와 '복구 지점', '작업'이 각각 무엇이고 어떻게 연결되는지 이해해야 실제 백업을 시작할 수 있습니다. 기존의 단순한 버튼식 백업(한 번에 클릭해서 완료)과 달리, AWS Backup은 여러 계층으로 이루어진 구조를 가지고 있어서 각 요소를 명확히 알아야 합니다.

2질문 제기

백업 계획을 세운 뒤 실제 백업 데이터가 어디에 어떻게 저장되고, 복원 시점까지의 전체 흐름이 어떻게 진행될까요?

3구조적 핵심 예시

백업 계획 하나를 만들면, 그 안에 여러 개의 백업 규칙이 들어가고, 각 규칙은 정해진 일정에 맞춰 실행되어 '작업'을 생성합니다. 각 작업이 완료되면 그 결과물(변경 데이터나 스냅샷)이 암호화되어 '복구 지점'이라는 복원 가능한 데이터로 '볼트'라는 저장소에 쌓입니다.

4단계별 동작 과정

  1. 백업 계획과 규칙 생성사용자가 콘솔에서 백업 계획을 만들고, 그 안에 규칙을 추가합니다. 각 규칙은 실행 빈도(매일, 매주 등)와 보존 기간(며칠·몇 개월 보관할지)을 정합니다.
  2. 작업 실행 및 복구 지점 생성정한 시간에 AWS Backup 서비스가 자동으로 작업을 시작하고, 대상 리소스(EC2, RDS, 등)에서 데이터를 수집해 암호화하고, 각 작업이 완료되면 복구 지점(Point In Time Recovery, PITR) 객체를 생성합니다.
  3. 볼트에 저장 및 관리생성된 모든 복구 지점은 AWS Backup 볼트(Vault, 보호된 저장소)에 저장되며, 사용자는 대시보드에서 언제든 목록을 보고 원하는 복구 지점을 선택해 복원 작업을 시작할 수 있습니다.

EBS·RDS·DynamoDB·EFS·S3 등 어떤 리소스가 어떤 기능(연속 백업, 교차 리전 복사 등)과 리전에서 지원되는지 가용성 표로 확인하는 방법이다.

1상대의 출발점 확인

AWS Backup이 모든 서비스와 기능을 다 지원하지는 않습니다. EBS·RDS·DynamoDB·EFS·S3 등 어떤 서비스가 지원되는지, 각 기능(예: PITR, 증분 백업, 교차 리전 복사)이 어느 리전에서 이용 가능한지 알아야 합니다. 공식 문서의 가용성 표를 제대로 읽지 못하면, 특정 리소스를 백업하려다가 갑자기 기능이 지원되지 않는 상황에 마주칠 수 있습니다.

2질문 제기

우리가 쓰는 서비스와 리전이 AWS Backup에서 지원되고, 필요한 기능들이 모두 가용한지 어떻게 빠르게 확인할 수 있을까요?

3구조적 핵심 예시

공식 문서의 가용성 표는 행에 서비스명(EBS, RDS, DynamoDB 등)을 나열하고, 열에 기능(스냅샷 백업, PITR, 증분 백업, 교차 리전)과 리전을 표시합니다. 예를 들어 'RDS의 PITR은 미국 동부·유럽 서부에서만 지원'이라면, 다른 리전의 RDS를 PITR로 백업할 수는 없는 것입니다.

4단계별 동작 과정

  1. 지원 서비스 확인공식 문서의 가용성 표에서 가장 왼쪽 행을 보고, 백업하려는 서비스(예: EC2의 EBS, 관계형 데이터베이스는 RDS)가 명시되어 있는지 확인합니다.
  2. 필요한 기능·리전 매칭각 서비스마다 지원되는 백업 방식(스냅샷, PITR, 증분)과 리전을 확인하고, 사용 중인 리전이 포함되어 있는지 확인합니다.
  3. 제약 사항 확인원하는 기능이 아직 베타이거나 특정 리전에서만 지원되면, 현재 설계를 조정하거나 일시적으로 기존 방식(서비스 자체 백업)을 사용할 계획을 세웁니다.

서비스 옵트인과 리전 설정

AWS Backup으로 관리할 서비스는 리전별로 옵트인(사용 설정)을 켜야 해당 리소스를 백업 계획에 할당할 수 있다.

1상대의 출발점 확인

AWS Backup을 활성화했다고 해서 모든 AWS 서비스가 자동으로 백업되는 것은 아닙니다. 각 서비스를 명시적으로 옵트인(설정 활성화)해야만 해당 서비스의 리소스를 백업 계획에 할당할 수 있습니다. 옵트인 과정을 모르면, 백업 계획을 만들었는데도 원하는 리소스가 할당되지 않는 문제가 발생합니다.

2질문 제기

AWS Backup으로 특정 서비스의 리소스를 관리하려면, 그 서비스를 미리 어떻게 준비해야 할까요?

3구조적 핵심 예시

AWS Backup 콘솔의 설정 메뉴에서 'AWS 서비스 옵트인'을 열면, RDS·DynamoDB·EBS·EFS 등 각 서비스마다 체크박스가 있습니다. 원하는 서비스의 체크박스를 켜면, 그 서비스의 리소스들이 AWS Backup의 백업 계획에 할당 가능한 상태가 됩니다. 리전별로 따로 옵트인해야 하므로, 사용 중인 리전 개수만큼 이 작업을 반복합니다.

4단계별 동작 과정

  1. 옵트인 페이지 접근AWS Backup 콘솔 > 설정 > AWS 서비스 옵트인으로 이동합니다.
  2. 서비스 및 리전 선택백업할 서비스(예: RDS, DynamoDB)를 찾아 체크 표시를 하고, 현재 작업 중인 리전을 설정합니다. 각 리전마다 개별 옵트인이 필요합니다.
  3. 할당 대기옵트인 후 몇 분이 지나면 해당 서비스의 리소스들이 백업 계획에서 선택 가능해지며, 태그나 명시적 선택으로 백업 계획에 할당할 수 있습니다.

1AWS Backup의 출발점01-05

스냅샷 백업·연속 백업·증분 백업의 차이

스냅샷은 시점별 사본, 연속 백업은 변경 로그로 특정 시각까지 복원(PITR)을 가능하게 하며, 증분은 직전 이후 변경분만 저장해 비용을 줄이는 방식이다.

1상대의 출발점 확인

백업 데이터를 저장하는 방식은 여러 개입니다. 기존에는 주로 스냅샷 방식만 알려졌는데, 스냅샷은 정해진 시간(매일 밤 2시)에만 전체 데이터를 복사해 저장하므로, 백업 시간 사이에 발생한 변경 사항은 복구할 수 없습니다. 예를 들어 오전 1시에 중요한 테이블을 삭제했는데 가장 최근 스냅샷이 어제 밤이면, 하루 치 데이터가 손실됩니다.

2질문 제기

스냅샷의 타이밍 문제를 해결하고, 임의의 특정 시각으로 복원할 수는 없을까요?

3구조적 핵심 예시

3구조적 핵심 예시

  2. 복사 규칙 추가같은 규칙 내에서 다른 리전(cross-region) 또는 다른 계정(cross-account)의 볼트로 복사하도록 대상과 복사 정책(시간, 보존 기간)을 설정한다.
  3. 자동 실행백업이 기본 볼트에 저장되면, 정해진 복사 규칙에 따라 자동으로 대상 볼트로도 복제된다.

3구조적 핵심 예시

4단계별 동작 과정

  1. 리소스별 옵션 선택백업 규칙에서 Windows EC2의 경우 VSS 활성화, S3의 경우 ACL 포함 여부와 객체 태그 포함 여부를 설정한다.
  2. 심화 정보 수집활성화된 옵션에 따라, 백업 시점에 애플리케이션 정합성 데이터(VSS)나 객체의 메타데이터(ACL, 커스텀 태그)를 함께 캡처한다.
  3. 완전 복구 실현복구 시 수집한 추가 정보가 함께 복원되어 권한, 설정, 데이터 일관성을 포함한 원본 상태를 정확히 재현한다.

백업 볼트는 복구 지점(백업)을 담아 두는 논리적 컨테이너로, 콘솔·CLI로 만들고 비어 있을 때만 삭제할 수 있다.

2질문 제기

3구조적 핵심 예시

AWS Backup에서 볼트(vault)는 비유하면 창고 같은 논리적 저장소다. EC2, RDS, DynamoDB, EBS 등 여러 서비스에서 나온 백업 복구 지점(recovery point)들을 한 볼트에 모아둔다. 같은 볼트에 저장된 백업들은 동일한 암호화 설정, 접근 제어, 보관 정책을 공유한다.

4단계별 동작 과정

  1. 생성AWS 콘솔이나 CLI에서 새로운 볼트를 만들 때 이름, 암호화 키(KMS), 그 외 설정을 지정하면 해당 AWS 리전에 논리적 컨테이너가 생성된다.
  2. 사용백업 계획이나 온디맨드 백업(on-demand backup, 즉시 실행하는 백업)을 실행할 때 대상 볼트를 지정하면, 생성된 백업 복구 지점이 그 볼트에 저장된다.
  3. 삭제볼트를 삭제하려면 그 안의 모든 백업 복구 지점을 먼저 삭제해야 하고, 그 볼트를 지정한 백업 계획도 제거해야 한다. 비어 있는 상태에서만 삭제할 수 있다.

볼트 암호화 키(KMS) 선택

볼트를 만들 때 지정하는 KMS 키는 그 볼트에 저장되는 백업을 암호화하며, 리소스 유형에 따라 원본 키가 그대로 쓰이기도 한다.

1상대의 출발점 확인

백업을 저장할 때 암호화를 하지 않으면 저장된 데이터가 평문 상태로 저장되어 보안 위험이 크다. 그렇다고 매번 애플리케이션 코드에서 직접 암호화 로직을 구현하면 복잡하고 실수하기 쉽다.

2질문 제기

백업 볼트에 저장되는 모든 백업을 자동으로 암호화하되, 암호화 키를 누가 어떻게 관리하도록 할 것인가?

3구조적 핵심 예시

볼트를 만들 때 KMS(Key Management Service) 고객 마스터 키(Customer Master Key, CMK)를 선택하면, 그 볼트에 저장되는 모든 백업 복구 지점이 자동으로 그 키로 암호화된다. 같은 볼트에 저장되는 EC2 스냅샷이든, RDS 백업이든, EBS 볼륨 백업이든 모두 동일한 KMS 키로 보호된다.

4단계별 동작 과정

  1. 키 지정볼트 생성 시 KMS 키를 선택한다. AWS 관리형 키(AWS managed key)를 사용하거나, 자신의 계정에서 생성한 고객 관리형 키(Customer managed key)를 지정할 수 있다.
  2. 자동 암호화백업이 그 볼트에 저장될 때, AWS Backup 서비스가 자동으로 선택된 KMS 키를 사용해 암호화를 수행한다. 따로 애플리케이션에서 암호화 코드를 작성할 필요가 없다.
  3. 원본 서비스의 암호화EBS나 RDS 같은 일부 서비스가 이미 자체 암호화 키로 암호화된 리소스를 백업하는 경우, 그 원본 키가 그대로 유지되고 볼트의 KMS 키는 추가로 적용될 수도, 적용되지 않을 수도 있다. 서비스마다 동작이 다르다.

볼트 액세스 정책

볼트에 붙이는 리소스 기반 IAM 정책으로, 누가 그 볼트의 백업을 복사·삭제·복원할 수 있는지 제한한다.

1상대의 출발점 확인

기존에는 백업 리소스 접근 권한을 IAM 정책으로만 관리했는데, 이 방식은 정책이 너무 광범위하거나 누가 실제로 접근 권한을 가지고 있는지 추적하기 어려웠다. 특히 여러 팀이나 계정에서 같은 백업 리소스에 접근해야 할 때 보안 통제가 약해졌다.

2질문 제기

특정 백업 볼트에 대해 누가 백업을 복사, 삭제, 복원할 수 있는지를 그 볼트 수준에서 직접 제한하려면 어떻게 해야 할까?

3구조적 핵심 예시

백업 볼트에 리소스 기반 IAM 정책(resource-based policy)을 붙인다. 이 정책은 "이 볼트에 저장된 백업에 대해서는 특정 계정의 특정 역할만 복사·삭제·복원 작업을 할 수 있다"는 식으로 규칙을 정의한다.

4단계별 동작 과정

  1. 정책 작성볼트 생성 후, 그 볼트의 액세스 정책 탭에서 리소스 기반 정책을 JSON 형태로 작성한다. 어떤 AWS 계정, 어떤 IAM 역할, 어떤 작업(backup:CopyRecoveryPoint 등)을 허용할지 명시한다.
  2. 정책 적용작성한 정책을 저장하면 AWS Backup이 해당 볼트에 정책을 적용한다. 이 정책은 그 볼트에 접근하려는 모든 요청에 먼저 평가된다.
  3. 접근 제어누군가 그 볼트의 백업을 대상으로 작업을 시도할 때, 정책에서 허용된 주체(principal)와 작업이 아니면 거부된다. IAM 정책과 별도로 이 리소스 기반 정책에서도 명시적 허용이 필요하다.

논리적 에어갭 볼트(LAG)

AWS가 소유한 키로 암호화되고 변경 불가능하게 잠긴 별도 볼트로, 계정이 침해돼도 백업을 지키고 다른 계정과 공유해 복원할 수 있다.

1상대의 출발점 확인

일반적인 백업 볼트의 경우, 백업이 저장된 후에도 같은 계정의 관리자나 악의적 사용자가 그 백업을 삭제하거나 수정할 수 있다. 계정이 침해당했을 때 백업까지 함께 손상되면 복구할 수 없는 재앙이 된다. 따라서 계정 침해로부터 백업을 보호하는 별도의 메커니즘이 필요했다.

2질문 제기

동일 계정의 악의적 관리자나 침해당한 계정으로부터 백업을 물리적·논리적으로 격리해 보호하려면 어떻게 해야 할까?

3구조적 핵심 예시

논리적 에어갭 볼트(Logically Air-Gapped vault, LAG)는 일반 백업 볼트와 별개로, AWS가 소유한 암호화 키로 보호되고 변경 불가능하게 잠긴 특수한 볼트다. 같은 계정이라도 일반 사용자나 관리자 권한으로는 이 볼트의 백업을 삭제하거나 복구 지점의 보관 기간을 줄일 수 없다.

4단계별 동작 과정

  1. 별도 볼트 생성LAG 볼트는 일반 볼트와 별도로 AWS 백업 콘솔이나 API에서 생성된다. 이 볼트를 생성하면 AWS가 관리하는 고정된 암호화 키가 자동으로 적용되고, 계정의 KMS 키 접근 권한과 무관하게 보호된다.
  2. 일방향 복사백업 계획에서 1차 대상으로 LAG 볼트를 지정하면, 정기적으로 생성되는 백업 복구 지점이 이 LAG 볼트로 자동 복사된다. 일단 LAG 볼트에 저장되면 그곳에서는 변경이나 삭제가 불가능하다.
  3. 격리된 복원LAG 볼트에 저장된 백업은 일반 권한으로 복원할 수 없고, 특별한 복원 권한 또는 AWS RAM(Resource Access Manager) 공유를 통해 다른 계정에서만 접근 가능하다.

에어갭 볼트로 1차 백업 보내기와 RAM 공유 복원

백업 플랜의 1차 대상을 논리적 에어갭 볼트로 지정하고, AWS RAM으로 그 볼트를 공유해 다른 계정에서 바로 복원하는 방식이다.

→ 03-04 참조

1상대의 출발점 확인

백업을 두 곳에 만들 때 기존 방식은 백업 계획을 두 개 만들어서 각각을 다른 볼트로 보내거나, 복사 규칙을 통해 일반 백업을 다른 볼트로 수동 복사하는 방식이었다. 보호된 볼트와 일반 볼트의 관계가 명확하지 않고, 복원 권한 설정도 번거로웠다.

2질문 제기

일반 백업 계획에서 주요 백업을 에어갭 볼트로 직접 보내고, 다른 계정에서도 그 백업을 복원할 수 있도록 하려면 어떻게 설정해야 할까?

3구조적 핵심 예시

백업 계획의 백업 규칙에서 1차 대상(primary backup destination)을 일반 볼트로, 복사 규칙(copy rule)에서 복사 대상을 LAG 볼트로 지정한다. 그러면 매 백업마다 자동으로 일반 볼트에 저장되고 동시에 LAG 볼트로도 복사된다. LAG 볼트의 백업 복구 지점에 대한 복원 권한은 AWS RAM으로 다른 계정에 공유하면, 그 계정에서 바로 복원할 수 있다.

4단계별 동작 과정

  1. 1차 백업 + 복사 규칙 설정백업 계획의 규칙에서 일반 볼트를 1차 대상으로 지정하고, 복사 규칙에서 같은 또는 다른 리전의 LAG 볼트를 지정한다. 빈도, 보관 기간 등을 각각 설정할 수 있다.
  2. 자동 복사 실행백업이 실행될 때마다 복구 지점이 일반 볼트에 먼저 저장되고, 그 직후 LAG 볼트로 자동 복사된다. 양쪽의 복구 지점은 독립적으로 보관 기간이 적용된다.
  3. RAM 공유로 다른 계정 접근 허용LAG 볼트를 AWS RAM으로 다른 계정에 공유하면, 공유받은 계정의 사용자도 그 LAG 볼트의 백업 복구 지점을 자신의 계정에서 직접 복원할 수 있다. 복구 지점 데이터는 원본 계정의 자원을 사용하되, 공유받은 계정에서 즉시 활용할 수 있다.

다자 승인(Multi-party approval)

에어갭 볼트의 복구처럼 민감한 작업을 실행하기 전에 지정된 승인자 팀의 동의를 받도록 강제하는 장치다.

→ 03-04 참조

1상대의 출발점 확인

기존에는 백업 복원 같은 중요한 작업도 권한이 있으면 한 사람이 즉시 실행할 수 있었다. 실수나 악의적 행동을 막기 위해 여러 사람의 동의가 필요한 경우에도 수동으로 메일 승인을 받거나 팀 채팅으로 확인하는 식이어서 공식적인 기록이 남지 않았다.

2질문 제기

백업 복원이나 다른 민감한 작업을 실행하기 전에 지정된 여러 승인자의 명시적 승인이 자동으로 요구되도록 하려면 어떻게 설정할 것인가?

3구조적 핵심 예시

에어갭 볼트에 다자 승인 정책을 설정하면, 그 볼트의 백업을 복원하려는 사람이 복원 요청을 보낼 때 시스템이 자동으로 미리 지정된 승인자 목록에 알림을 보낸다. 승인자들이 각각 콘솔이나 API에서 명시적으로 승인해야만 복원이 진행된다.

4단계별 동작 과정

  1. 정책 설정에어갭 볼트의 설정에서 다자 승인 정책을 활성화하고, 승인이 필요한 작업(예: RecoveryPointRestoration) 목록과 최소 몇 명의 승인자가 필요한지를 지정한다. 승인자 목록은 IAM 역할이나 계정으로 정의된다.
  2. 작업 요청사용자가 해당 작업(백업 복원 등)을 실행하려고 하면 AWS Backup이 요청을 임시 보류(pending approval) 상태로 저장하고 지정된 승인자들에게 알린다. 작업은 즉시 실행되지 않는다.
  3. 승인 및 실행승인자들이 AWS 콘솔이나 API에서 요청을 검토하고 승인하면, 지정된 최소 승인 수에 도달하면 그 시점부터 요청된 작업이 자동으로 실행된다. 거부되면 작업은 취소된다.

온디맨드 백업 만들기

백업 계획의 일정을 기다리지 않고 지금 즉시 특정 리소스의 백업(복구 지점)을 한 번 만드는 방법.

1상대의 출발점 확인

기존 방식에서는 백업을 만들기 위해 반드시 정해진 일정 시간을 기다려야 합니다. 백업 계획(backup plan)을 설정한 후 스케줄에 따라 자동으로 실행되는 시간을 대기해야 하는데, 만약 긴급하게 지금 당장 특정 리소스의 백업이 필요한 상황에서는 그 일정을 기다릴 수 없다는 한계가 있습니다.

2질문 제기

스케줄을 기다리지 않고 지금 즉시 특정 리소스의 백업을 만들 수 있는 방법이 있을까요?

3구조적 핵심 예시

온디맨드(on-demand) 백업은 AWS Backup 콘솔에서 보호할 리소스를 선택해 즉시 "지금 백업하기" 버튼을 누르면, 그 순간부터 현재 상태의 스냅샷을 바로 만드는 방식입니다.

4단계별 동작 과정

1상대의 출발점 확인

백업 작업을 시작했을 때 그것이 얼마나 진행됐는지, 또는 정말 제대로 실행되고 있는지 확인할 방법이 없다면 불안합니다. 또한 리소스의 크기가 클수록 매번 전체를 다시 백업하는 것은 시간이 오래 걸리고 저장 공간을 낭비하게 되는 문제가 있습니다.

2질문 제기

실행 중인 백업이 어느 정도까지 진행됐는지 확인하고, 이후 백업은 처음처럼 전체를 다시 하는 게 아닌 변경된 부분만 저장할 수는 없을까요?

3구조적 핵심 예시

AWS Backup은 콘솔에서 각 백업 작업의 상태를 "진행 중", "완료됨", "실패함" 같이 표시하고, 처음 백업은 모든 데이터를 복사하지만 그 이후 백업부터는 변경된 부분만 추가로 저장하는 증분(incremental) 방식을 사용합니다.

4단계별 동작 과정

  1. 첫 백업(전체 백업)리소스의 모든 데이터를 전부 복사해 기준점을 만듭니다.
  2. 이후 백업(증분 백업)마지막 백업 이후 변경되거나 추가된 부분만 찾아서 저장하므로, 저장 공간을 절약하고 속도가 빠릅니다.
  3. 상태 확인Backup 콘솔의 작업 탭에서 각 백업의 진행률, 남은 시간, 완료 여부 등을 실시간으로 확인할 수 있습니다.

1상대의 출발점 확인

기존 백업 방식은 특정 시점에만 백업을 만들기 때문에, 그 사이에 데이터가 손상되거나 변경되는 일이 생기면 가장 가까운 백업 시점까지만 되돌릴 수 있습니다. 예를 들어 백업이 매일 자정에 만들어진다면, 정오에 실수가 발생해도 전 날 자정 상태로만 복구할 수 있고, 그 사이 12시간의 데이터 변화는 모두 손실되는 문제가 있습니다.

2질문 제기

3구조적 핵심 예시

4단계별 동작 과정

  1. 연속 기록 시작PITR을 활성화한 리소스에 대해 AWS Backup이 모든 쓰기(write) 작업과 변경사항을 계속 로그에 기록합니다.
  2. 보존 기간 설정예를 들어 35일 보존이라 설정하면, 지난 35일간의 모든 변경 기록이 유지됩니다.
  3. 원하는 시점으로 복구문제가 생기면 콘솔에서 복구하고 싶은 정확한 시간을 선택해 그 상태로 되돌릴 수 있습니다.

데이터베이스에 "환경:운영(environment: production)"이라는 태그가 있으면, 그 데이터베이스의 백업도 같은 태그를 들고 만들어진다. 백업을 만든 후 "담당자:김철수"라는 태그를 추가하면 같은 정보가 복구 지점(actual backup data)에도 쌓인다.

4단계별 동작 과정

  1. 태그 정책 설정백업 계획을 세울 때 '원본 태그 복사' 옵션을 켜서 원본의 모든 태그나 특정 태그만 골라서 복사할지 결정한다.
  2. 백업 생성 시 태그 자동 복사백업이 만들어질 때 설정한 태그들이 복구 지점(recovery point, 백업 데이터 한 개)에 함께 붙는다.
  3. 복구 지점 태그 관리만들어진 백업에 나중에 새 태그를 추가하거나 기존 태그를 수정·삭제할 수 있으므로 시간에 따라 변하는 정보를 계속 반영할 수 있다.

  2. 검색 조건 설정필요한 파일을 이름, 크기, 시간 범위로 지정해서 검색한다.

1상대의 출발점 확인

S3(Simple Storage Service) 백업은 보통 표준 스토리지(Standard)에 저장되는데, 거기서 계속 두면 저장 비용이 계속 나간다. 특히 규제나 감사를 위해 7년 이상 보관해야 하는 데이터는 보관 기간이 길어서 누적 비용이 크다.

2질문 제기

오래된 S3 백업을 값싼 저장소로 자동 옮겨서 보관 비용을 줄일 수 있을까?

3구조적 핵심 예시

4단계별 동작 과정

  2. 자동 이동 실행시간이 지나면 AWS Backup이 자동으로 오래된 백업을 저렴한 계층(Glacier, Deep Archive 같은 콜드 스토리지)으로 옮긴다.
  3. 필요시 복구콜드 스토리지의 백업이 필요하면 꺼내는데, 콜드 스토리지는 꺼내는 데 시간이 걸릴 수 있다.

EC2·EBS 백업과 Windows VSS 정합성

EC2 인스턴스와 EBS 볼륨을 스냅샷으로 백업하고, Windows 애플리케이션은 VSS 를 써서 쓰기 중이던 데이터까지 일관되게 담는 방법.

1상대의 출발점 확인

EC2(Elastic Compute Cloud, 가상 서버)나 EBS(Elastic Block Store, 저장 장치)를 백업할 때 스냅샷(snapshot, 특정 시점의 데이터 복사본)을 만든다. 하지만 서버가 애플리케이션을 실행 중이라면, 백업 중에 데이터가 쓰여질 수 있다. 특히 Windows 애플리케이션(데이터베이스, 파일 서버 등)은 여러 파일을 동시에 수정하고 있을 수 있어서, 불완전한 상태의 데이터가 백업에 들어갈 위험이 있다.

2질문 제기

서버가 실행 중일 때도 데이터의 일관성(쓰기 중이던 데이터까지 완전하게)을 보장하면서 백업할 수 있을까?

3구조적 핵심 예시

Windows 데이터베이스 서버에서 거래 기록을 쓰고 있는 중에 스냅샷을 만들 때, VSS(Volume Shadow Copy Service, 윈도우 백업 서비스)가 그 순간 데이터의 "완전한 스냅샷"을 만들어서, 쓰기 중이던 데이터도 일관된 상태로 담긴다.

4단계별 동작 과정

  1. VSS 스냅샷 요청AWS Backup이 Windows 서버에 VSS를 통해 "지금 상태의 일관된 스냅샷을 만들어라"고 요청한다.
  2. 애플리케이션 일시 정지 및 스냅샷 생성VSS가 실행 중인 애플리케이션을 순간 일시 정지하고, 그 사이에 EBS 스냅샷을 만든다. 이 방식을 애플리케이션 일관성 스냅샷(Application-consistent snapshot)이라 한다.
  3. 백업 데이터 저장만들어진 스냅샷이 AWS Backup에 저장되어, 복구 시 데이터 무결성이 보장된다.

5본질 요약

Windows VSS를 활용해서 애플리케이션 실행 중에도 데이터의 일관성을 유지하면서 EBS를 백업하는 것

1상대의 출발점 확인

기존에는 S3의 객체(파일)들이 삭제되거나 손상되면 복구 수단이 제한적이었다. 버전 관리(versioning)를 켜두면 이전 버전을 복구할 수 있지만, 실수로 버킷 전체를 삭제했거나 오래된 버전을 다 지우면 복구가 불가능했다.

2질문 제기

S3 버킷의 객체를 중앙에서 일관되게 백업하고 삭제·손상·버전 손실 상황에서 복구할 수 있을까?

3구조적 핵심 예시

회사 문서 버킷에서 실수로 중요 파일이 삭제되었을 때, AWS Backup에서 어제 백업한 버킷 스냅샷으로 돌아가서 그 파일만 복구하거나, 전체 버킷을 특정 시점으로 복원할 수 있다.

4단계별 동작 과정

  1. 백업 계획 설정S3 버킷(또는 특정 객체)을 AWS Backup의 대상으로 지정하고 백업 주기(매일, 매주 등)를 정한다.
  2. 연속 백업 수행AWS Backup이 설정한 주기나 연속으로 S3의 객체와 메타데이터(객체 속성)를 백업한다.
  3. 복구 수행필요할 때 객체 단위로 복구하거나 버킷 전체를 특정 시점으로 복원할 수 있다.

5본질 요약

1상대의 출발점 확인

2질문 제기

3구조적 핵심 예시

관계형 데이터베이스(RDS MySQL), 문서 데이터베이스(DocumentDB), 그래프 데이터베이스(Neptune)를 모두 AWS Backup의 단일 정책으로 백업하면, 콘솔 한 곳에서 모든 데이터베이스의 복구 지점을 관리하고, "2024-01-15 오후 3시 정확히" 그 상태로 복구할 수 있다.

4단계별 동작 과정

  1. 통합 백업 정책 정의AWS Backup에서 백업할 리소스에 다양한 데이터베이스 유형(RDS, Aurora, DocumentDB, Neptune, Aurora DSQL)을 모두 포함시키고 백업 주기와 보관 기간을 정한다.
  2. 스냅샷과 연속 백업 수행각 데이터베이스 종류에 적맞은 방식으로 스냅샷(시점 백업)을 만들거나 연속 로그(트랜잭션 기록)를 백업한다.
  3. 시점 복구특정 시점의 데이터베이스 상태로 새로운 데이터베이스 인스턴스(또는 기존 인스턴스)를 복구할 수 있다.

5본질 요약

DynamoDB 고급 기능·Redshift·Timestream 백업

DynamoDB 고급 백업(수명주기·복사 지원)과 Redshift 클러스터·Timestream 시계열 테이블의 백업 특성.

1상대의 출발점 확인

DynamoDB, Redshift, Timestream은 각각 데이터를 관리하는 AWS 서비스인데, 각자의 방식으로만 백업이 가능했다. DynamoDB 테이블이 손상되었을 때 복구 지점이 여러 곳에 흩어져 있었고, 어느 시점으로 복원할지 선택하기 어려웠다. Redshift 클러스터와 Timestream 테이블도 마찬가지로 각 서비스 내부의 백업 기능만 사용할 수 있어, 통일된 정책으로 관리하거나 중앙에서 모든 복구 지점을 보기 어려웠다.

2질문 제기

여러 데이터 서비스(DynamoDB, Redshift, Timestream)를 통일된 방식으로 주기적 백업하면서 복구 지점을 중앙에서 관리할 수 있을까?

3구조적 핵심 예시

DynamoDB 테이블의 경우, AWS Backup 계획에 포함시키면 매일 자정에 자동으로 백업이 생성되고, 그 백업을 30일간 보관하다가 자동 삭제하도록 설정할 수 있다. 같은 계획에 Redshift 클러스터도 추가하면 클러스터의 증분 스냅샷이 함께 관리되고, Timestream 테이블을 포함시키면 시계열 데이터의 시점 복구(PITR) 백업도 같은 정책으로 처리된다.

4단계별 동작 과정

  1. 백업 정책 설정AWS Backup 계획에 DynamoDB, Redshift, Timestream을 포함시키고, 백업 빈도(매 시간, 매일 등), 보관 기간(일수), 수명주기 규칙(오래된 백업 자동 삭제)을 정한다.
  2. 자동 백업 실행정해진 시간에 AWS Backup이 각 서비스에 접근해 스냅샷을 생성하고, 메타데이터와 함께 AWS Backup 볼트에 저장한다.
  3. 중앙 복구 지점 관리AWS Backup 콘솔에서 DynamoDB, Redshift, Timestream의 모든 복구 지점을 한곳에서 보고, 필요한 순간에 복원할 수 있다.

1상대의 출발점 확인

EFS와 FSx는 관리형 파일 시스템이고 Storage Gateway는 온프레미스 스토리지를 클라우드와 연결하는 서비스인데, 각각 다르게 백업되었다. EFS는 스냅샷으로만 백업 가능했고, FSx와 Storage Gateway는 자체 백업 기능에만 의존했다. 여러 파일 시스템을 일관되게 백업하고 특정 파일이나 특정 시점의 볼륨만 복원하려면 복잡한 수동 작업을 거쳐야 했다.

2질문 제기

다양한 파일 시스템과 스토리지 장치를 하나의 백업 정책으로 관리하면서 개별 파일이나 볼륨을 선택적으로 되살릴 수 있을까?

3구조적 핵심 예시

4단계별 동작 과정

  1. 파일 시스템 및 볼륨 등록EFS, FSx(Windows, Lustre), Storage Gateway 볼륨을 AWS Backup 계획에 포함시키고, 백업 빈도와 보관 기간을 설정한다.
  2. 증분 백업 생성AWS Backup이 정해진 시간에 파일 시스템의 변경된 블록만 캡처하여 저장하므로 백업 크기와 저장 비용을 줄일 수 있다.
  3. 파일/볼륨 단위 복원백업에서 필요한 파일이나 볼륨 범위를 지정해 새로운 리소스로 복원하거나 기존 시스템에 병합한다.

EKS 클러스터 백업과 복합 복구 지점

쿠버네티스 클러스터의 리소스 정의와 영구 볼륨을 하나의 묶음(복합 복구 지점)으로 함께 백업·복원하는 기능.

1상대의 출발점 확인

EKS(쿠버네티스) 클러스터는 여러 구성 요소로 이루어져 있다. 클러스터의 리소스 정의(배포된 애플리케이션 설정)와 데이터를 저장하는 영구 볼륨(EBS)이 각각 다르게 백업되었다. 전체 클러스터를 일관되게 복원하려면 각 부분을 따로따로 복구해야 했고, 리소스와 데이터의 시점을 맞추기가 어려웠다.

2질문 제기

쿠버네티스 클러스터의 리소스 정의와 데이터 볼륨을 하나의 복구 지점으로 함께 백업해서 한 번에 복원할 수 있을까?

3구조적 핵심 예시

4단계별 동작 과정

  1. 클러스터 리소스 캡처AWS Backup 에이전트가 클러스터의 etcd(쿠버네티스 설정 저장소)에서 모든 리소스 정의를 추출하고 메타데이터로 저장한다.
  2. 영구 볼륨 스냅샷동시에 클러스터에 연결된 EBS 볼륨들의 스냅샷을 생성하여 볼륨 내 데이터 상태를 캡처한다.
  3. 복합 복구 지점 생성리소스 정의와 볼륨 스냅샷을 하나의 복구 지점으로 그룹화해 저장하고, 복원 시 둘을 함께 새 클러스터에 적용한다.

복원의 공통 절차와 복원 메타데이터

복구 지점을 골라 리소스 유형별 복원 메타데이터를 채워 새 리소스로 되살리는 공통 흐름이다.

1상대의 출발점 확인

백업을 생성했다면 언젠가는 복원해야 한다. 기존에는 각 AWS 서비스마다 복원 방법이 달랐다. EC2를 복원하려면 인스턴스 유형, VPC, 보안 그룹을 모두 지정해야 했고, RDS를 복원하려면 또 다른 형식의 파라미터를 입력해야 했다. 복원에 필요한 메타데이터(원래 설정 정보)를 직접 찾아 입력하는 과정이 번거로웠고 실수하기 쉬웠다.

2질문 제기

여러 리소스 유형의 백업을 복원할 때 공통된 절차와 메타데이터 관리 방식으로 일관성 있게 처리할 수 있을까?

3구조적 핵심 예시

AWS Backup 콘솔에서 복구 지점을 선택한 후 복원 버튼을 클릭하면, 리소스 유형별 복원 양식이 자동으로 제시된다. 양식에는 이전 백업 시점의 메타데이터(원래 인스턴스 유형, 네트워크 설정, 태그 등)가 기본값으로 채워져 있어 필요한 항목만 수정하면 된다.

4단계별 동작 과정

1상대의 출발점 확인

EC2, EBS, EFS, FSx, Storage Gateway는 모두 컴퓨팅과 스토리지를 담당하는 리소스이지만, 각각의 복원 절차가 달랐다. EC2 인스턴스를 복원하면 데이터는 EBS 볼륨에만 있고, 마운트되지 않은 다른 EBS 볼륨은 별도로 복원해야 했다. EFS를 전체 복원하려면 새로운 마운트 포인트를 수동으로 생성해야 했고, FSx 볼륨도 특정 위치에만 복원 가능했다.

2질문 제기

컴퓨트와 스토리지 리소스들(EC2, EBS, EFS, FSx, Storage Gateway)을 각각의 특성에 맞춰 선택적으로 복원하면서도 통일된 절차로 처리할 수 있을까?

3구조적 핵심 예시

4단계별 동작 과정

  1. 복원 범위 지정복구 지점에서 EC2, EBS, EFS, FSx, Storage Gateway를 개별 선택하거나 함께 선택한다.
  2. 복원 메타데이터 설정각 리소스 유형별로 복원 위치, 인스턴스 유형, 네트워크 설정, 암호화 키 등을 지정한다. 원본 메타데이터가 기본값으로 제공된다.
  3. 선택적 복원 실행지정된 범위와 메타데이터로 복원을 진행하며, 필요하면 복원 상태를 모니터링한다.

  2. 복원 파라미터 정의새 인스턴스의 이름, 인스턴스 클래스(크기), 보안 그룹, 데이터베이스 포트 등을 설정합니다.
  3. 자동 복원 실행AWS Backup이 선택된 스냅샷 데이터를 새 인스턴스에 자동으로 로드하고 복원 상태를 모니터링합니다.

4단계별 동작 과정

  1. 복원 대상 리소스와 시점 선택S3, EKS, VM 등 리소스 유형과 되돌릴 시점(예: 장애 발생 1시간 전)을 지정합니다.
  2. 연속 백업 로그 추적선택한 시점까지의 모든 변경 사항(파일 생성·삭제, 설정 변경)을 백업 로그에서 찾아내고 순서대로 재현합니다.
  3. 새 리소스 또는 기존 위치에 복원복원된 상태를 새로운 S3 버킷이나 EKS 클러스터로 생성하거나, 기존 리소스의 해당 위치에 덮어씁니다.

AWS Backup 보안은 AWS 공동 책임 모델 위에서 인프라 보안, 백업 데이터 무결성, 장애 복원력의 세 축으로 구성된다.

백업은 미션 크리티컬한 데이터를 담으므로 보안이 필수입니다. 그런데 기존에는 누가 백업 데이터를 보호할 책임이 있는지, 누가 암호화하고 누가 무단 접근을 방지하는지, 장애 상황에서 어떻게 복구할지가 불명확했습니다.

AWS Backup의 보안 책임과 구조는 어떻게 나뉘어 있을까?

3구조적 핵심 예시

AWS Backup이 고객 데이터를 저장할 때, AWS는 데이터 센터의 물리 보안, 네트워크 격리, 암호화 기술을 담당하고(AWS의 책임), 고객은 누가 백업에 접근할 수 있는지를 IAM 정책으로 제한하고(고객의 책임), 둘이 함께 데이터를 보호합니다.

4단계별 동작 과정

관리형 정책과 IAM 서비스 역할

AWS 가 미리 만들어 둔 관리형 정책과, AWS Backup 이 사용자 대신 리소스를 백업·복원할 때 맡는 IAM 서비스 역할이다.

1상대의 출발점 확인

IAM 정책을 처음부터 다 작성하는 것은 매우 복잡하고 실수하기 쉽습니다. 또한 AWS Backup 서비스 자신도 고객 리소스(RDS, EBS, S3 등)에 접근해서 백업해야 하는데, 권한이 없으면 작동하지 않습니다.

2질문 제기

AWS Backup과 사용자의 권한을 쉽고 안전하게 설정할 수 있을까?

3구조적 핵심 예시

AWS가 이미 "AWSBackupFullAccess"라는 표준 관리형 정책(권한 묶음)을 만들어 두었으므로, 관리자가 이 정책 하나를 IAM 사용자에게 할당하면 기본 권한이 자동으로 주어집니다. 동시에 AWS Backup 서비스 자신도 "AWSBackupServiceRole"이라는 역할을 맡아서 고객 리소스(RDS, EBS 등)에 접근할 권한을 갖습니다.

4단계별 동작 과정

  1. AWS 관리형 정책 적용관리자가 사용자나 그룹에 AWS가 사전 정의한 정책(AWSBackupFullAccess, AWSBackupOperatorAccess 등)을 할당합니다.
  2. AWS Backup 서비스 역할 생성AWS Backup 서비스가 고객 리소스를 백업·복원하기 위해 필요한 권한을 명시한 서비스 역할(AWSBackupServiceRole)을 자동으로 생성합니다.
  3. 역할 신뢰 관계 설정서비스 역할이 "aws-backup.amazonaws.com" 서비스만 신뢰하도록 설정해서 다른 서비스의 권한 오용을 방지합니다.

서비스 연결 역할 3종

백업·복사, Audit Manager 보고서, 복원 테스트용으로 AWS Backup 이 자동 생성해 쓰는 세 가지 서비스 연결 역할이다.

1상대의 출발점 확인

기존에는 AWS Backup이 백업·복사·감사 작업을 수행할 때마다 각각의 권한 정책을 수동으로 생성하고 관리했어야 했다. 어느 권한이 필요한지 파악하기 어렵고, 권한을 잘못 설정하면 작업이 실패하며, 권한 정책을 업데이트할 때마다 수동으로 수정해야 하는 문제가 있었다.

2질문 제기

AWS Backup이 필요한 권한을 자동으로 갖추고, 유지보수 없이 항상 최신 상태로 유지하려면 어떻게 해야 할까?

3구조적 핵심 예시

AWS Backup이 EC2 인스턴스를 백업할 때, AWS가 미리 정의한 서비스 연결 역할(AWSBackupServiceRolePolicyForBackup)을 자동으로 생성하여, AWS Backup이 그 역할을 써서 EC2에 접근한다. 사용자는 이 역할의 존재만 알고 있으면 되고, 권한 내용은 AWS가 관리한다.

4단계별 동작 과정

  1. 역할 자동 생성AWS Backup에서 처음 작업을 실행할 때, AWS가 필요한 서비스 연결 역할을 자동으로 생성한다.
  2. 권한 할당역할에는 해당 작업(백업, 복사, 감사 보고서 생성, 복원 테스트)에 필요한 모든 권한이 미리 포함되어 있다.
  3. AWS 관리 업데이트새로운 기능이 추가되거나 권한이 변경되면, AWS가 역할의 권한 정책을 자동으로 업데이트한다.

5본질 요약

혼동된 대리인 방지와 네트워크 경로

다른 계정이 AWS Backup 을 대리인처럼 악용하지 못하게 조건 키로 막고, 백업 트래픽이 지나는 네트워크 경로를 통제하는 방법이다.

1상대의 출발점 확인

교차 계정 백업 설정에서, 다른 AWS 계정이 악의적으로 AWS Backup 권한을 빌려 원래는 할 수 없는 작업을 수행하는 공격이 가능했다. 또한 백업 트래픽이 공개 인터넷을 지나가면서 가로챌 위험이 있었다.

2질문 제기

다른 계정의 악의적 접근을 막으면서, 동시에 백업 트래픽의 경로를 안전하게 제한하려면 어떻게 해야 할까?

3구조적 핵심 예시

A 계정의 AWS Backup이 B 계정의 리소스를 백업할 때, 백업 요청에 A 계정의 고유 ID(SourceAccount)를 태그로 붙인다. B 계정의 정책에서 이 ID를 확인해서만 권한을 허락하므로, C 계정이 A 계정의 이름을 사칭해도 통과하지 못한다.

4단계별 동작 과정

  1. 조건 키 설정교차 계정 백업 시 정책에 aws:SourceAccount 조건을 추가하여, 특정 계정에서의 요청만 허락한다.
  2. 네트워크 경로 제한AWS PrivateLink나 VPC 엔드포인트를 사용해 백업 트래픽이 공개 인터넷을 지나지 않도록 설정한다.
  3. 정책 검증요청이 들어올 때마다, SourceAccount 조건과 네트워크 경로를 확인하고 조건에 맞아야만 진행한다.

5본질 요약

백업 암호화와 데이터 보호

백업은 저장 중과 전송 중 모두 암호화되며, KMS 키로 백업 볼트와 복구 지점의 암호화를 제어한다.

1상대의 출발점 확인

백업 데이터는 장시간 보관되는 중요한 정보이지만, 저장할 때와 네트워크를 통해 전송할 때 모두 평문으로 남아 있으면 탈취 위험에 노출된다.

2질문 제기

백업 데이터를 저장 중과 전송 중 모두 안전하게 암호화하면서, 복원할 때는 빠르게 복호화하려면 어떻게 해야 할까?

3구조적 핵심 예시

AWS Backup이 EC2 스냅샷을 백업 볼트에 저장할 때, 지정한 KMS 키(고객 관리형 또는 AWS 관리형)로 암호화해 저장하고, 복사나 교차 지역 이동 시에도 암호화 상태를 유지한다.

4단계별 동작 과정

  1. 저장 중 암호화백업 볼트에서 모든 복구 지점(스냅샷, 데이터베이스 백업 등)을 KMS 키로 암호화하여 저장한다.
  2. 전송 중 암호화스토리지로 데이터를 옮기거나 교차 지역 복사할 때 TLS/HTTPS 채널을 사용해 암호화 상태를 유지한다.
  3. 복원 시 자동 복호화복원 요청이 들어오면 백업 시스템이 자동으로 KMS 키로 복호화한 뒤 원본 리소스로 복원한다.

5본질 요약

Vault Lock: 거버넌스 모드와 컴플라이언스 모드

볼트에 WORM 잠금을 걸어 백업 삭제·보존 변경을 막는 기능으로, 되돌릴 수 있는 거버넌스 모드와 아무도 못 푸는 컴플라이언스 모드가 있다.

→ 04-05 참조

1상대의 출발점 확인

백업 데이터가 중요할수록, 실수로 삭제되거나 보존 정책이 임의로 변경될 위험이 커진다. 기존에는 권한만으로는 이런 변경을 완전히 방지할 수 없었고, 악의적이거나 실수적인 백업 삭제를 막기 어려웠다.

2질문 제기

백업을 법적·기술적으로 변조 불가능하게 잠금으로써, 실수로 인한 삭제나 정책 변경을 원천 차단하려면 어떻게 해야 할까?

3구조적 핵심 예시

백업 볼트에 WORM(Write-Once-Read-Many) 잠금을 설정하면, 설정된 보존 기간 동안 복구 지점을 삭제하거나 보존 정책을 변경할 수 없고, 읽기만 가능해진다.

4단계별 동작 과정

  1. 거버넌스 모드 설정볼트에 잠금을 걸되, 특정 권한(aws:BypassVaultLock)을 가진 사용자는 일정 조건(예: 관리자 승인)하에 잠금을 해제할 수 있다.
  2. 컴플라이언스 모드 설정볼트에 절대적 잠금을 걸어, 어떤 권한을 가진 사용자라도 잠금을 해제할 수 없게 한다.
  3. 잠금 적용설정한 모드로 잠금이 활성화되면, 보존 기간이 끝날 때까지 복구 지점 삭제와 정책 변경이 기술적으로 불가능하다.

5본질 요약

WORM 메커니즘으로 백업 정책을 기술적으로 불변성(Immutability)으로 만들어, 권한이나 관리자 실수로도 변경 불가능하게 하는 것

법적 보존(Legal hold)

소송·감사 등을 이유로 특정 복구 지점이 보존 기간이 끝나도 삭제되지 않게 붙잡아 두는 장치다.

1상대의 출발점 확인

법적 소송이나 규제 감사가 진행 중일 때, 정기적인 백업 보존 정책에 따라 중요한 증거 데이터가 자동으로 삭제될 수 있다. 이런 삭제는 법적 문제를 초래하고, 나중에 증거를 재현하기 어렵다.

2질문 제기

원래 보존 정책의 만료 날짜와 관계없이, 특정 복구 지점을 법적 사유로 무기한 보존해야 할 때 어떻게 하면 될까?

3구조적 핵심 예시

4단계별 동작 과정

백업 플랜·볼트·리소스 할당 등을 CloudFormation 템플릿으로 코드화해 반복 배포하는 방식.

→ 03-02 참조

1상대의 출발점 확인

백업 플랜, 볼트, 리소스 할당을 콘솔에서 하나하나 만들어야 하고, 다른 계정이나 리전으로 복사하려면 같은 과정을 반복해야 하며, 배포 기록이 남지 않아 어떤 설정이 언제 변경됐는지 추적하기 어렵습니다.

2질문 제기

백업 플랜과 볼트를 코드로 정의해서 여러 환경에 일관되게 배포하고 버전 관리할 수 있을까요?

3구조적 핵심 예시

CloudFormation 템플릿(YAML 파일)에서 AWS::Backup::BackupPlan(일정), AWS::Backup::BackupVault(저장소), AWS::Backup::ResourceAssignment(리소스 선택) 리소스를 정의한 후 템플릿을 배포하면, 콘솔 작업 없이 모든 리소스가 자동으로 생성됩니다.

4단계별 동작 과정

  1. 템플릿 작성백업 플랜의 일정, 볼트 암호화 설정, 리소스 할당 규칙을 JSON/YAML로 코드화합니다.
  2. 스택 배포CloudFormation이 템플릿을 스택으로 생성해 정의된 AWS Backup 리소스를 자동으로 생성합니다.
  3. 버전 관리 및 업데이트템플릿을 Git에서 관리하고, 변경사항이 생기면 스택을 업데이트해 일관성 있게 적용합니다.

5본질 요약

CloudFormation 템플릿으로 AWS Backup 리소스를 코드화해서 반복 배포, 버전 관리, 여러 환경 동기화를 자동화하는 것

AWS Backup API·CLI와 지원 프로토콜

콘솔 대신 API와 CLI로 백업을 자동화할 때 쓰는 오퍼레이션과 지원되는 요청 프로토콜 정리.

1상대의 출발점 확인

AWS Backup 작업을 모두 콘솔 GUI에서 수동으로 실행해야 하고, 반복되는 작업을 자동화할 방법이 없어 운영 부담이 크고 휴먼 에러 가능성이 높습니다.

2질문 제기

콘솔 대신 API와 CLI로 백업 작업을 자동으로 실행하고 스케일링할 수 있을까요?

3구조적 핵심 예시

관리자가 터미널에서 aws backup start-backup-job --backup-vault-name prod-vault --resource-arn arn:aws:rds:... 명령을 실행하거나, Python 스크립트에서 boto3 라이브러리로 CreateBackupPlan API를 호출하면 AWS Backup이 요청을 처리해 백업을 시작합니다.

4단계별 동작 과정

  1. CLI 작업AWS CLI 명령어(start-backup-job, create-backup-plan 등)를 셸 스크립트나 크론 작업에 넣어 반복 실행 가능하게 설정합니다.
  2. API 호출boto3(Python), SDK for JavaScript, Go SDK 등 언어별 라이브러리로 프로그래밍 방식으로 AWS Backup 오퍼레이션을 호출합니다.
  3. 요청 프로토콜AWS Backup API는 HTTPS(REST)를 지원해 네트워크 연결만 있으면 어느 환경(온프레미스, Lambda, EC2)에서도 호출할 수 있습니다.

5본질 요약

AWS Backup API와 CLI가 콘솔 작업을 프로그래밍으로 자동화해서 운영 규모를 늘리고 휴먼 에러를 줄이는 것

공식 문서https://docs.aws.amazon.com/aws-backup/latest/devguide/api-reference.html

할당량과 문제 해결

AWS Backup의 서비스 할당량 한도와 작업 실패 시 원인별 대처법을 다루는 트러블슈팅 가이드.

1상대의 출발점 확인

AWS Backup 서비스 한도를 모르고 있다가 작업이 갑자기 실패하거나, 백업이 안 되는 경우 원인을 직관적으로 알 수 없어 시간을 낭비해 대처합니다.

2질문 제기

AWS Backup의 서비스 한도는 무엇이고 작업이 실패했을 때 원인을 어떻게 파악할까요?

3구조적 핵심 예시

AWS Backup의 할당량에는 "리전당 백업 플랜 수 제한(기본 10개)", "한 번에 백업 가능한 리소스 크기 상한" 같은 것이 있고, 작업 실패 로그에 "VolumeNotFound" "InsufficientBackupVaultPermissions" 같은 구체적인 오류 코드가 기록됩니다.

4단계별 동작 과정

  1. 할당량 확인AWS Service Quotas 콘솔이나 CLI에서 현재 사용량과 한도를 확인하고, 필요하면 할당량 인상 요청을 제출합니다.
  2. 작업 로그 조회AWS Backup 콘솔이나 CloudWatch Logs에서 실패한 작업의 오류 메시지와 스택 트레이스를 확인해 원인을 파악합니다.
  3. 대처법 적용오류 코드별로 IAM 권한 추가, 리소스 상태 확인, 네트워크 연결성 검사 같은 조치를 취합니다.

5본질 요약

AWS Backup 할당량 문서와 작업 로그의 오류 코드가 서비스 한도와 실패 원인을 명시해서 운영 중 발생하는 문제를 빠르게 진단하고 해결하는 것
