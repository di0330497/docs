1VPC라는 그릇 이해하기VPC가 무엇이고 어디에 놓이는지를 먼저 잡아야, 뒤에 나오는 IP·라우팅·게이트웨이가 '무엇 안에서 일어나는 일'인지 말이 된다.62IP 주소 설계VPC와 서브넷은 만들 때 CIDR를 먼저 정해야 하고 나중에 되돌리기 어렵다. 주소 체계를 알아야 그 다음의 생성 작업이 의미를 갖는다.63VPC와 서브넷 만들기주소 설계를 실제 리소스로 옮기는 단계다. 여기서 만든 VPC·서브넷·네트워크 인터페이스가 이후 라우팅·보안의 조작 대상이 된다.54라우팅게이트웨이를 아무리 붙여도 라우트가 없으면 트래픽은 가지 않는다. 인터넷·VPN·엔드포인트 모두 라우팅 규칙 위에서 동작하므로 게이트웨이보다 먼저 온다.65인터넷과 연결하기가장 먼저·가장 자주 필요한 외부 연결이다. 라우트 테이블을 익힌 직후에 배워야 '게이트웨이 + 라우트'가 한 세트로 붙는다.66DNS와 DHCP연결이 되어도 이름이 풀리지 않으면 통신은 실패한다. 인터넷 연결 직후, 그리고 피어링·엔드포인트의 DNS 이야기가 나오기 전에 필요하다.47보안 통제연결을 만든 다음에는 반드시 그 연결을 좁혀야 한다. 보안 그룹과 NACL은 앞에서 만든 서브넷·ENI·라우트 위에서만 의미를 갖는다.78AWS PrivateLink로 프라이빗하게 서비스 접근인터넷 경로 없이 AWS 서비스·타사 서비스에 닿는 방법이다. 라우팅·보안·DNS를 모두 쓰기 때문에 그 뒤에 와야 한다.69다른 VPC·온프레미스와 연결하기VPC 하나를 완전히 다룰 수 있게 된 다음에야 여러 VPC와 데이터센터를 잇는 선택지를 비교할 수 있다.810여러 계정·대규모 주소 운영VPC 하나가 아니라 수십·수백 개를 다루기 시작할 때 필요한 도구들이다. 앞의 개별 개념을 다 알아야 '무엇을 대신 관리해 주는가'가 이해된다.511관측·검증·문제 해결모든 구성요소를 알아야 로그의 필드와 분석 결과를 읽을 수 있다. 마지막에 두어 앞의 지식을 진단 능력으로 바꾼다.8

1VPC라는 그릇 이해하기01-01

Amazon VPC란 무엇인가: 논리적으로 격리된 가상 네트워크

AWS 클라우드 안에 나만 쓰는 논리적으로 격리된 가상 네트워크를 만들고, 그 안에서 AWS 자원을 실행하게 해주는 서비스다.

1상대의 출발점 확인

클라우드 서비스 초기에는 여러 사용자가 같은 물리 인프라를 공유했습니다. 인터넷 연결은 모두가 같은 경로를 타고, 서버 방화벽 설정도 해당 서버 단위에서만 가능했습니다. 이렇게 되면 내 네트워크 설정을 내가 완전히 제어할 수 없고, 보안상 다른 사용자의 트래픽이나 설정이 간섭할 가능성이 있었습니다.

2질문 제기

AWS 클라우드 안에서 내가 온전히 통제할 수 있는 격리된 네트워크를 어떻게 만들 수 있을까요?

3구조적 핵심 예시

AWS가 물리 서버의 가상화 기술을 네트워크 계층까지 확대한 것입니다. 한 대의 물리 라우터와 스위치를 여러 개의 논리 네트워크로 분할해서, 각 사용자가 마치 자신만의 독립적인 네트워크 하드웨어를 가진 것처럼 작동하게 만드는 원리입니다.

4단계별 동작 과정

  1. IP 대역 할당VPC를 만들 때 사용할 IP 주소 범위(CIDR 블록이라고 하는, 10.0.0.0/16 형태의 표기)를 정해줍니다.
  2. 서브넷 생성할당받은 IP 범위를 더 작은 조각으로 나누어 각 가용 영역(데이터센터)에 배치합니다.
  3. 트래픽 규칙 적용라우트 테이블과 보안 그룹(방화벽처럼 작동하는 규칙)을 설정해서 어떤 트래픽이 들어오고 나갈지 제어합니다.

5본질 요약

AWS의 물리 인프라를 논리적으로 분할해서 각 사용자가 격리된 가상 네트워크를 독점적으로 사용하고 완전히 제어하게 하는 것

VPC는 하나의 리전 안에만 존재하고 그 리전의 여러 가용 영역(AZ)에 걸쳐 서브넷을 둘 수 있으며, AZ 간 통신은 AWS 자체 글로벌 네트워크를 탄다.

1상대의 출발점 확인

여러 물리 데이터센터에 걸쳐 인프라를 구축할 때는 각 센터마다 별도의 네트워크를 만들고, 센터 간 통신을 위해 공개 인터넷 경로를 사용하거나 비용이 많이 드는 전용선을 구매해야 했습니다. 이렇게 되면 지역별 네트워크 관리가 복잡해지고, 센터 간 통신이 느리거나 불안정할 수 있었습니다.

2질문 제기

VPC가 한 리전의 여러 가용 영역에 걸쳐 하나의 통합된 네트워크로 작동하려면 어떻게 해야 할까요?

3구조적 핵심 예시

AWS가 자신의 데이터센터들 사이에 독자적인 고속 파이버 네트워크를 깔아둔 것입니다. 이 네트워크는 AWS 내부에만 존재하고 인터넷을 거치지 않기 때문에, 한 VPC의 트래픽이 여러 데이터센터를 거쳐도 빠르고 안전합니다.

4단계별 동작 과정

  1. VPC는 단일 리전 존재VPC를 생성할 때 특정 리전(지역)을 선택하면, 그 VPC는 그 리전의 경계 안에만 존재합니다.
  2. 여러 가용 영역에 서브넷 배치한 VPC 내에서 같은 리전의 여러 가용 영역(AZ라고 하는, 독립적인 데이터센터 그룹)에 서브넷을 나누어 배치합니다.
  3. AWS 프라이빗 네트워크로 연결AZ 간의 모든 트래픽은 AWS의 내부 글로벌 네트워크(인터넷을 거치지 않음)를 통해 이동합니다.

VPC 구성요소 지도: 서브넷·라우트 테이블·게이트웨이·엔드포인트

VPC는 IP 대역을 쪼갠 서브넷, 트래픽 방향을 정하는 라우트 테이블, 외부와 잇는 게이트웨이, AWS 서비스로 바로 붙는 엔드포인트가 조립된 구조다.

1상대의 출발점 확인

단순한 인터넷 연결만으로는 복잡한 네트워크 요구사항을 충족할 수 없습니다. 특정 서버만 외부에 노출하고 싶고, AWS의 특정 서비스(데이터베이스, 스토리지 등)와는 인터넷을 거치지 않고 연결하고 싶으며, 서브넷 간의 트래픽을 선택적으로 차단하거나 허용하고 싶을 수 있습니다. 이런 세밀한 제어가 없으면 보안과 성능 모두 문제가 됩니다.

2질문 제기

VPC 안에서 트래픽을 세밀하게 제어하고 AWS 서비스와 효율적으로 연결하려면 어떤 구성요소들이 필요할까요?

3구조적 핵심 예시

VPC는 도시의 인프라처럼 설계되어 있습니다. IP 대역을 서브넷(구역)으로 쪼개고, 각 구역 간의 트래픽 방향을 라우트 테이블(도로 표지판 같은 역할)로 정하고, 외부와 연결하는 게이트웨이(출입문)와 AWS 서비스와 직접 연결하는 엔드포인트(전용 통로)를 배치하는 구조입니다.

4단계별 동작 과정

  1. 서브넷으로 IP 대역 분할VPC의 IP 범위를 더 작은 단위(서브넷)로 나누어서, 각 서브넷이 별도의 역할을 하도록 구성합니다(예: 웹 서버 서브넷, 데이터베이스 서브넷 등).
  2. 라우트 테이블로 트래픽 방향 정의각 서브넷마다 라우트 테이블을 할당해서, 특정 대역의 트래픽이 어디로 갈지 결정합니다(예: 0.0.0.0/0 트래픽은 인터넷 게이트웨이로, 172.31.0.0/16은 VPC 내부로).
  3. 게이트웨이와 엔드포인트로 내외부 연결인터넷 게이트웨이(인터넷으로 나가는 문)와 NAT 게이트웨이(프라이빗 서브넷에서 나가는 문), 그리고 VPC 엔드포인트(AWS 서비스와 직접 연결하는 프라이빗 통로)를 배치합니다.

AWS가 각 리전에 미리 만들어 두는 인터넷 연결 가능한 VPC와 AZ별 서브넷으로, 별도 설정 없이 바로 인스턴스를 띄울 수 있다.

VPC를 처음부터 수동으로 설계하고 구축하는 것은 복잡합니다. IP 범위를 정하고, 가용 영역별로 서브넷을 만들고, 인터넷 게이트웨이를 연결하고, 라우트 테이블을 설정해야 합니다. 이 모든 단계를 거쳐야 비로소 서버를 띄울 수 있습니다.

2질문 제기

VPC 설계 없이 즉시 서버를 실행할 수 있는 네트워크가 미리 준비되어 있다면 어떨까요?

3구조적 핵심 예시

AWS는 각 리전마다 미리 설정된 기본 VPC를 자동으로 만들어 두는 것입니다. 이 VPC는 이미 인터넷 게이트웨이가 연결되어 있고, 각 가용 영역에 기본 서브넷이 미리 할당되어 있으며, 라우트 테이블도 설정되어 있습니다.

4단계별 동작 과정

  1. 계정 생성 시 기본 VPC 자동 생성AWS 계정을 만드는 순간, 각 리전에 자동으로 기본 VPC(10.0.0.0/16 범위)가 생성됩니다.
  2. 각 AZ에 기본 서브넷 자동 할당그 리전의 모든 가용 영역마다 기본 서브넷(10.0.0.0/20, 10.0.1.0/20 등)이 자동으로 만들어집니다.
  3. 인터넷 게이트웨이와 라우트 설정 완료기본 VPC는 이미 인터넷 게이트웨이와 라우트 테이블이 연결되어 있어서, 서브넷의 인스턴스가 바로 인터넷에 연결 가능합니다.

  2. VPC 자체는 무료VPC 생성, 서브넷 생성, 라우트 테이블 설정 같은 기본 구성요소는 요금이 없습니다.
  3. 특정 기능과 데이터 전송에만 과금NAT 게이트웨이(프라이빗 서브넷에서 아웃바운드 트래픽을 처리하는 기능), VPC 엔드포인트(AWS 서비스와 프라이빗 연결), 리전 간 또는 가용 영역 간 데이터 전송 같은 고급 기능에는 비용이 발생합니다.

2질문 제기

VPC를 구축하기 전에 어떤 설계 항목들을 미리 결정해야 할까요?

3구조적 핵심 예시

VPC 설계는 건설 프로젝트의 초기 계획처럼 작동합니다. 기초(권한, IP 설계)를 먼저 정하고, 규모(가용 영역 개수)와 접근로(외부 연결 방식)를 결정한 후에 실제 구축을 시작해야 변경으로 인한 비용과 복잡도를 최소화할 수 있습니다.

4단계별 동작 과정

  1. 권한 설정과 IP CIDR 블록 결정IAM(신원 관리 서비스)에서 VPC 조작 권한을 정하고, 사용할 IP 범위(예: 10.0.0.0/16)를 선택해서 향후 확장을 고려합니다.
  2. 가용 영역 개수와 서브넷 분할 계획가용성과 비용을 고려해서 사용할 AZ 개수를 정하고(보통 2~3개), 각 AZ에서 서브넷을 어떻게 나눌지(공개 서브넷, 프라이빗 서브넷 등) 계획합니다.
  3. 외부 연결 방식 선택인터넷과 직접 연결할지(인터넷 게이트웨이), NAT를 쓸지, 또는 온프레미스와 연결할지(VPN, Direct Connect) 사전에 결정합니다.

2IP 주소 설계02-01

CIDR 표기와 프라이빗 IPv4 주소 범위

10.0.0.0/16 처럼 '주소/프리픽스 길이'로 IP 대역을 표기하는 방법과, 인터넷에 직접 쓰지 않고 사설망에 쓰도록 예약된 RFC 1918 주소 범위(10.x, 172.16~31.x, 192.168.x).

1상대의 출발점 확인

IP 주소를 개별적으로 관리하면 대량의 주소를 그룹으로 할당하거나 빌려주기 어렵습니다. 예를 들어 "192.168.1.1, 192.168.1.2, 192.168.1.3, ... 192.168.1.254"를 모두 나열해야 하는데, 범위가 커지면 관리 불가능해집니다. 또한 인터넷에 직접 연결되는 공개 IP와 내부망에만 쓰는 사설 IP를 구분해야 하는데, 이를 안 하면 보안과 주소 할당이 충돌할 수 있습니다.

2질문 제기

IP 주소 대역을 효율적으로 표기하고 관리하려면, 그리고 인터넷 노출을 피하면서 사설망을 구축하려면 어떻게 할까요?

3구조적 핵심 예시

CIDR(Classless Inter-Domain Routing)는 "기본 주소/프리픽스 길이" 형태로 IP 대역을 단 한 줄에 표기합니다. 10.0.0.0/16은 10.0.0.0부터 10.0.255.255까지의 65,536개 주소를 나타냅니다. 슬래시 뒤의 숫자가 작을수록 더 큰 범위이고, 클수록 더 작은 범위입니다.

4단계별 동작 과정

  1. CIDR 표기로 IP 대역 표현10.0.0.0/16, 172.16.0.0/12, 192.168.0.0/24 같이 기본 주소와 프리픽스 길이로 대역을 정의합니다. 프리픽스 길이는 네트워크 부분의 비트 수를 나타내고, 뒤는 호스트 부분입니다.
  2. RFC 1918 주소 범위가 사설망 전용인터넷 표준에서 10.0.0.0/8(10.0.0.0~10.255.255.255), 172.16.0.0/12(172.16.0.0~172.31.255.255), 192.168.0.0/16(192.168.0.0~192.168.255.255)을 사설망 전용으로 예약했습니다. 이 범위는 인터넷 라우터가 절대 전달하지 않으므로 안전합니다.
  3. 서브넷은 CIDR 범위를 더 작게 분할VPC의 CIDR 블록(예: 10.0.0.0/16)을 더 작은 서브넷 CIDR(예: 10.0.1.0/24, 10.0.2.0/24)로 쪼개서 각 가용 영역이나 기능별로 할당합니다.

VPC를 처음 만들 때 IPv4 주소 범위를 정해야 한다. 기존에는 이 범위를 정하면 VPC 생명주기 내내 고정적으로 사용했어야 했고, 주소 공간이 부족해지면 새로운 VPC를 만들어야 했다. 이는 네트워크 구성의 변경이 매우 제한적이었다는 뜻이다.

2질문 제기

VPC를 만들 때 정하는 초기 주소 범위를 나중에 늘리거나 줄일 수 있을까?

3구조적 핵심 예시

VPC의 초기 IPv4 CIDR 블록은 /16부터 /28까지 크기를 지정할 수 있다. 예를 들어 10.0.0.0/16을 선택했다면, 이후에 10.1.0.0/16 같은 보조 CIDR 블록(secondary CIDR block)을 추가할 수 있다. 각 보조 CIDR도 /16부터 /28 범위여야 한다. 필요 없는 보조 CIDR은 나중에 제거할 수 있다.

4단계별 동작 과정

  1. 초기 CIDR 블록 지정VPC를 만들 때 기본 IPv4 CIDR 블록의 크기를 결정한다. /16은 약 65,000개, /24는 약 250개 주소를 제공한다.
  2. 보조 CIDR 추가기본 블록만으로는 부족할 때, 별도의 보조 CIDR 블록을 VPC에 추가하면 두 범위의 주소가 모두 VPC 안에서 라우팅된다.
  3. 블록 제거더 이상 필요 없는 보조 CIDR은 언제든 제거할 수 있지만, 기본 CIDR 블록은 VPC가 존재하는 한 유지된다.

2질문 제기

서브넷에 할당할 수 있는 실제 주소 개수는 서브넷 크기보다 왜 항상 5개 적을까?

3구조적 핵심 예시

/24 서브넷은 256개 주소(10.0.1.0부터 10.0.1.255까지)를 가진다. 이 중 10.0.1.0(네트워크 주소), 10.0.1.1(라우터), 10.0.1.2(DNS), 10.0.1.3(미래용), 10.0.1.255(브로드캐스트)는 AWS가 예약해두므로, 실제로 인스턴스에 할당할 수 있는 주소는 10.0.1.4부터 10.0.1.254까지 251개뿐이다.

4단계별 동작 과정

  1. AWS의 예약 주소 처리서브넷을 만드는 순간 5개 주소가 자동으로 예약된다. 이 주소들은 인스턴스에 할당할 수 없다.
  2. CIDR 예약 설정필요하면 추가로 특정 IP 범위를 미리 잡아두는 CIDR 예약을 직접 만들 수 있다. 예를 들어 10.0.1.100~10.0.1.110을 미리 예약하면, 그 범위는 나중에 인스턴스에 쓸 수 없다.
  3. Network Address Usage 모니터링NAU는 서브넷 안에서 사용 중인 주소의 비율을 백분율로 보여준다. 이를 통해 주소 고갈 위험을 미리 감지할 수 있다.

1상대의 출발점 확인

지금까지 VPC와 서브넷의 대부분은 IPv4만 사용했다. IPv4 주소 부족은 오랜 문제지만, 기존 애플리케이션과의 호환성 때문에 IPv4를 계속 유지해야 했다. 이제 IPv6을 함께 쓰거나 IPv6만 쓰는 방식이 필요해졌다.

2질문 제기

VPC 안에서 IPv4와 IPv6을 함께 쓸 수 있을까?

3구조적 핵심 예시

VPC에서 IPv6을 사용하려면, 먼저 VPC에 /56 크기의 IPv6 블록을 할당한다. 그 다음 각 서브넷에 그 범위 안에서 /64 크기를 할당한다. 예를 들어 VPC의 IPv6 블록이 2600:1f13:fe4:6c00::/56이라면, 서브넷 A는 2600:1f13:fe4:6c00::/64, 서브넷 B는 2600:1f13:fe4:6c01::/64를 받는 식이다. 이렇게 하면 그 서브넷의 인스턴스들은 IPv4와 IPv6 주소를 동시에 얻는다.

4단계별 동작 과정

  1. VPC에 IPv6 블록 할당AWS로부터 IPv6 CIDR 블록(/56)을 받아 VPC에 연결한다. 주소 범위는 AWS가 결정한다.
  2. 서브넷에 IPv6 CIDR 할당VPC의 IPv6 블록을 나눠 각 서브넷에 /64를 할당한다. 이제 서브넷은 IPv4와 IPv6 모두를 가진다(듀얼 스택).
  3. IPv6 전용 서브넷 옵션IPv4는 필요 없고 IPv6만 쓸 서브넷을 만들 수도 있다. 이 경우 서브넷은 IPv4 CIDR 없이 IPv6 /64만 가진다.

1상대의 출발점 확인

개발자들은 보통 IPv4만 알고 일해왔다. IPv4는 32비트 주소(xxx.xxx.xxx.xxx 형태), 공개 주소는 한정적이므로 프라이빗 주소가 필요하고, NAT로 변환해야 한다. 그런데 IPv6은 주소 길이, 표기법, 그리고 프로토콜 수준의 동작이 완전히 다르다.

2질문 제기

IPv4와 IPv6은 VPC 내에서 주소 구성과 통신 방식이 어떻게 다를까?

3구조적 핵심 예시

IPv4는 32비트 주소를 10진법 4개 그룹으로 표기한다(192.168.1.1). VPC 내 프라이빗 IPv4는 외부 네트워크와 직접 통신할 수 없으므로 NAT 게이트웨이를 거쳐야 한다. 반면 IPv6은 128비트 주소를 16진법으로 표기하며(2001:db8::1), 프라이빗과 공개 구분이 없다. IPv6 주소는 기본적으로 외부에서 도달 가능하다.

4단계별 동작 과정

  1. 주소 길이와 표기법IPv4는 32비트(약 43억 개), IPv6은 128비트(약 340조 조 개 주소). IPv4는 10진법, IPv6은 16진법 표기다.
  2. 퍼블릭과 프라이빗IPv4는 퍼블릭/프라이빗이 엄격하게 구분되어 프라이빗은 NAT 없이 외부로 나갈 수 없다. IPv6은 모든 주소가 기본적으로 라우팅 가능하다.
  3. 지원 기능보안 그룹, 네트워크 ACL 등 거의 모든 기능이 IPv4와 IPv6을 동시에 지원하지만, 일부 AWS 서비스는 IPv6만 지원하지 않는다.

3구조적 핵심 예시

EC2 인스턴스가 인터넷과 통신하려면 퍼블릭 IPv4 주소가 필요하다. 이 주소는 4가지 출처 중 하나에서 온다. 첫째, 인스턴스를 시작할 때 AWS가 자동으로 붙이는 임시 퍼블릭 IP(인스턴스 정지 시 반환). 둘째, 계정이 소유하는 Elastic IP(고정적이고 재할당 가능). 셋째, 회사나 조직이 이미 소유한 주소를 AWS로 가져오는 BYOIP. 넷째, Load Balancer나 NAT Gateway 같은 AWS 서비스가 자신의 용도로 쓰는 주소.

4단계별 동작 과정

  1. EC2 퍼블릭 IP인스턴스를 시작하고 자동 할당 IPv4 설정을 켜면 AWS가 퍼블릭 IP를 임시로 부여한다. 인스턴스를 정지하면 주소가 반환되고, 재시작할 때 다른 주소를 받는다.
  2. Elastic IP계정이 영구적으로 소유할 IP를 미리 할당하면, 같은 인스턴스에 붙였다 떼었다 할 수 있다. 인스턴스를 정지해도 유지되고, 인스턴스를 삭제하고 나중에 새 인스턴스에 붙일 수 있다.
  3. BYOIP와 서비스 관리형이미 소유한 주소 범위를 AWS에 가져와 사용하거나, ALB나 NAT Gateway처럼 AWS가 관리하는 서비스의 고정 주소를 쓸 수 있다.

3구조적 핵심 예시

탄력적 네트워크 인터페이스(ENI): 리소스가 VPC에 붙는 방식

ENI는 서브넷에 속한 가상 랜카드로, EC2를 비롯한 리소스는 이 인터페이스를 통해 사설 IP·보안 그룹·MAC 주소를 갖고 VPC 네트워크에 연결된다.

1상대의 출발점 확인

물리 서버의 네트워크 카드는 하드웨어적으로 한 장만 고정되어 있고, 그 카드에 MAC 주소·IP·네트워크 설정이 직결된다. VPC 같은 가상 환경에서 EC2 인스턴스 같은 소프트웨어 리소스는 물리 카드를 가질 수 없는데, 그러면 어떻게 사설 IP를 갖고, 보안 설정을 적용하고, 네트워크에 연결할까?

2질문 제기

EC2를 비롯한 리소스는 VPC 네트워크에 어떻게 연결되고, 사설 IP와 보안 설정은 어디에 저장되나?

3구조적 핵심 예시

EC2 인스턴스가 생성될 때 지정한 서브넷에 자동으로 하나의 ENI(가상 랜카드)가 생성된다. 이 ENI에는 사설 IP·공인 IP(선택)·보안 그룹·MAC 주소가 할당되고, EC2는 이 ENI를 통해서만 네트워크 통신을 수행한다.

4단계별 동작 과정

  1. 서브넷에 ENI 생성지정한 서브넷 내에서 사용할 가상 랜카드 인터페이스를 생성한다.
  2. IP와 보안 설정 할당생성된 ENI에 사설 IP, 필요 시 공인 IP, 보안 그룹, MAC 주소를 부여한다.
  3. 리소스 연결EC2 등의 인스턴스가 이 ENI를 통해 VPC 네트워크로 송수신을 수행한다.

라우트 테이블의 구조: 목적지·대상·local 라우트·메인 라우트 테이블

라우트 테이블은 '어떤 목적지 IP 대역(destination)으로 가는 트래픽을 어떤 대상(target)으로 보낼지' 적어둔 규칙 표이며, VPC 안 통신용 local 라우트는 지울 수 없고 명시적으로 연결 안 된 서브넷은 메인 라우트 테이블을 따른다.

1상대의 출발점 확인

전통 네트워크에서 라우팅은 라우터가 패킷의 목적지 IP를 보고 어느 포트로 보낼지 결정하는 방식이었다. VPC는 클라우드 네트워크이지만 이 원리는 같고, 라우팅을 제어하려면 목적지별로 어디로 보낼지 명시해야 한다. 단순한 한 두 줄의 규칙으로는 복잡한 VPC를 관리할 수 없다.

2질문 제기

VPC 내 트래픽을 제어하기 위해 라우트 테이블이 정의하고 저장하는 정보는 무엇인가?

3구조적 핵심 예시

라우트 테이블은 "목적지 대역 10.0.1.0/24 → 인터넷 게이트웨이", "목적지 대역 10.0.0.0/16 → local(같은 VPC 내)", "목적지 대역 192.168.0.0/16 → VPN 게이트웨이" 이런 식으로 규칙을 기록한 표다. 패킷이 오면 그 목적지 IP와 비교해서 어느 규칙에 맞는지 찾아 그 대상으로 보낸다.

4단계별 동작 과정

  1. 라우트 규칙 등록목적지 IP 대역(destination)과 그 트래픽을 보낼 대상(target)을 쌍으로 라우트 테이블에 입력한다.
  2. Local 라우트 고정VPC 내부 통신용 local 라우트(예: 10.0.0.0/16 → local)는 자동으로 생성되고 사용자가 삭제할 수 없다.

2질문 제기

3구조적 핵심 예시

  2. 대역이 같을 때 정적 우선겹치는 정적 라우트(직접 설정한 규칙)가 BGP 동적 라우트(외부에서 자동 전파된 규칙)보다 우선한다.
  3. 규칙 적용선택된 라우트의 대상(target)으로 트래픽을 전송한다.

2질문 제기

3구조적 핵심 예시

4단계별 동작 과정

  2. 인바운드 필터링인바운드 규칙으로 들어오는 트래픽(포트, 프로토콜, 출발지)을 명시적으로 허용합니다. 규칙에 맞지 않으면 자동 차단됩니다.
  3. 상태 저장 응답인바운드로 허용된 트래픽의 응답은 아웃바운드 규칙을 검사하지 않고 자동으로 통과시킵니다.

3구조적 핵심 예시

네트워크 ACL: 상태 비저장 규칙과 번호 순 평가

서브넷 경계에서 동작하는 방화벽으로, 허용·거부 규칙을 번호 순으로 평가하며 인바운드와 아웃바운드를 각각 따로 열어야 한다.

1상대의 출발점 확인

보안 그룹은 인스턴스에 붙는 상태 저장 방화벽이다. 들어온 연결의 응답 패킷은 자동으로 허용되므로, 인바운드만 명시하면 된다. 하지만 서브넷 전체에 대해 명시적 거부(특정 IP 범위를 아예 차단)를 적용해야 하거나, 모든 인스턴스의 보안 그룹을 일일이 수정하지 않고 한 군데서 규칙을 관리해야 할 때는 인스턴스 수준의 제어로는 부족하다.

2질문 제기

서브넷 경계에서 모든 트래픽을 상태 없이 번호 순서대로 평가하고, 명시적 거부 규칙으로 원치 않는 통신을 차단할 수 있을까?

3구조적 핵심 예시

네트워크 ACL에 규칙을 번호로 매겨 등록한다. "규칙 100: 소스 10.0.1.0/24, TCP 80 → 허용", "규칙 110: 모든 소스 → 거부"라고 설정하면, 서브넷으로 들어오는 트래픽이 규칙 100을 만족하면 허용되고, 아니면 규칙 110에서 거부된다. 이 평가 순서는 번호가 작은 것부터 시작되므로, 규칙 번호를 10씩 띄어서 관리하면 나중에 규칙을 삽입할 여유가 생긴다.

4단계별 동작 과정

  1. 인바운드 규칙 번호 순 평가서브넷으로 들어오는 패킷이 인바운드 규칙을 번호 순서대로 확인한다. 첫 번째 일치하는 규칙(허용 또는 거부)이 최종 결정이 되며, 이후 규칙은 평가되지 않는다.
  2. 아웃바운드 규칙 독립 평가나가는 패킷은 아웃바운드 규칙을 같은 방식으로 평가한다. 인바운드와 아웃바운드는 완전히 독립적이므로, 80번 포트 인바운드를 열어도 아웃바운드에 명시적으로 규칙을 추가하지 않으면 응답 패킷이 나갈 수 없다.
  3. 상태 비저장 특성으로 양방향 명시보안 그룹과 달리, ACL은 연결 상태를 기억하지 않는다. 따라서 클라이언트에서 요청이 올 때와 서버에서 응답을 보낼 때 각각 규칙을 만족해야 통신이 이루어진다.

보안 그룹과 네트워크 ACL 비교, 그리고 Path MTU Discovery

적용 범위·상태 저장 여부·규칙 평가 방식의 차이를 정리하고, MTU 탐색에 필요한 ICMP를 막지 않도록 주의하는 내용이다.

→ 07-02, 07-04 참조

1상대의 출발점 확인

보안 그룹과 네트워크 ACL은 모두 트래픽을 제어하지만, 적용 범위와 작동 방식이 다르다. 두 기술을 혼용할 때, 규칙을 정확히 이해하지 못하면 예상과 다르게 통신이 차단될 수 있다. 또한 네트워크 통신의 기초를 이루는 ICMP 같은 프로토콜을 실수로 차단하면, 경로 최대 전송 단위 탐색(Path MTU Discovery) 같은 필수 기능이 실패해 통신 오류가 발생한다.

2질문 제기

보안 그룹과 네트워크 ACL의 차이를 언제 어느 것을 써야 하는지 판단하고, 필수 통신 프로토콜을 보호해야 할까?

3구조적 핵심 예시

보안 그룹은 인스턴스(ENI)에 붙어서 상태를 추적한다. "HTTP 80번 포트 인바운드 허용"이라고 설정하면, 들어온 요청의 응답 패킷은 자동으로 나간다. 반면 네트워크 ACL은 서브넷 모두에 적용되고 상태를 기억하지 않는다. 아웃바운드 규칙에 임시 포트 범위(1024~65535)를 명시하지 않으면, 응답 패킷이 서브넷을 빠져나갈 수 없다.

4단계별 동작 과정

  1. 적용 범위와 상태 추적 차이보안 그룹은 개별 인스턴스의 네트워크 인터페이스(ENI)에 붙어 들어오고 나가는 연결의 상태를 기억한다. 네트워크 ACL은 서브넷 모두에 동시에 적용되며 상태를 관리하지 않으므로, 인바운드와 아웃바운드를 모두 명시해야 한다.
  2. 규칙 충돌 시 더 제한적인 쪽이 우선보안 그룹의 규칙이 허용을 해도, 네트워크 ACL의 번호 순 평가에서 거부되면 트래픽은 흐르지 않는다. 따라서 ACL 규칙을 먼저 검토하고, 그 안에서 보안 그룹으로 세밀하게 제어하는 방식이 효과적이다.
  3. ICMP와 MTU 탐색 보호ICMP 타입 3(목적지 도달 불가)과 프래그멘테이션 필요 메시지는 경로의 최적 패킷 크기를 찾기 위해 필수다. 네트워크 ACL에서 ICMP를 전부 차단하면, 대용량 파일 전송이나 복잡한 통신 경로에서 패킷이 손실되거나 연결이 끊길 수 있다.

VPC·서브넷 퍼블릭 액세스 차단(VPC BPA)

계정·VPC·서브넷 수준에서 인터넷 게이트웨이를 통한 인바운드/아웃바운드 통신을 한 번에 끄는 상위 차단 스위치다.

1상대의 출발점 확인

보안 그룹과 네트워크 ACL은 규칙 하나하나를 수동으로 관리해야 한다. 조직 전체에서 인터넷 게이트웨이를 통한 인바운드 접근을 아예 차단하고 싶다면(예: 공개되면 안 될 데이터베이스를 보호하기 위해), 모든 VPC의 보안 그룹과 ACL 규칙을 찾아 확인하고 수정해야 한다. 이 작업은 번거롭고, 실수로 빠뜨린 규칙이 있을 수 있다.

2질문 제기

계정이나 VPC 전체에서 인터넷 게이트웨이를 통한 모든 인바운드 및 아웃바운드 접근을 개별 규칙 수정 없이 한 번에 차단할 수 있을까?

3구조적 핵심 예시

VPC Public Access Block(VPC BPA)은 스위치처럼 작동한다. 계정 수준에서 "Restrict public internet access" 플래그를 켜면, 그 계정의 모든 VPC와 서브넷이 인터넷 게이트웨이를 통한 통신을 할 수 없게 된다. 보안 그룹이나 ACL 규칙을 일일이 수정할 필요가 없다.

4단계별 동작 과정

  1. 계정 수준 전역 설정AWS 계정 전체에서 인터넷 게이트웨이를 통한 인바운드 및 아웃바운드 차단 플래그를 설정할 수 있다. 조직의 보안 표준을 모든 리소스에 일관되게 적용한다.
  2. VPC와 서브넷 수준 세밀 제어특정 VPC나 서브넷만 다른 정책이 필요하다면, 그 수준에서 별도의 플래그를 설정해 오버라이드할 수 있다. 상위 수준의 설정이 더 제한적인 쪽으로 작동한다.
  3. 기존 규칙 위의 상위 계층 차단VPC BPA는 보안 그룹, 네트워크 ACL, 라우팅 테이블 위에 추가되는 상위 차단 스위치다. 낮은 수준의 규칙이 허용해도, VPC BPA가 차단하면 트래픽은 흐르지 않는다.

Amazon VPC의 IAM: 정책·관리형 정책·서비스 연결 역할

누가 어떤 VPC 리소스를 만들고 바꿀 수 있는지를 IAM 정책·AWS 관리형 정책·서비스 연결 역할로 통제하는 체계다.

1상대의 출발점 확인

VPC 리소스(인스턴스, 보안 그룹, 네트워크 인터페이스 등)를 만들고 수정하는 권한은 IAM 정책으로 제어했다. 각 사용자나 역할에 필요한 권한(예: ec2:DescribeSecurityGroups, ec2:CreateSecurityGroup)을 정책으로 일일이 작성하고 할당했다. 조직이 커지고 역할이 다양해지면, 비슷한 권한 조합을 반복해서 만들고 유지관리해야 하므로 일관성을 유지하기 어렵다.

2질문 제기

VPC 리소스를 관리할 권한을 체계적으로 나누고, 조직의 일반적인 역할(예: 네트워크 관리자)에 필요한 권한을 중앙에서 정의할 수 있을까?

3구조적 핵심 예시

AWS는 미리 만든 관리형 정책(managed policy)을 제공한다. "AmazonVPCFullAccess" 정책은 VPC, 서브넷, 보안 그룹, 라우팅 테이블 등 거의 모든 VPC 작업을 허용하는 권한을 묶어두었다. 관리자는 이 정책을 IAM 역할에 붙이기만 하면, 그 역할을 맡은 사용자나 서비스가 자동으로 권한을 갖는다.

4단계별 동작 과정

  1. IAM 정책 작성VPC 리소스별 필요 작업(Create, Describe, Delete 등)을 "ec2:*" 형태의 액션(action)으로 나열하고, 특정 리소스만 적용 대상이 되도록 ARN(Amazon Resource Name)으로 제한한다.
  2. AWS 관리형 정책 활용VPC 관리자, 개발자, 감시 전용 같은 일반적인 역할에 필요한 권한을 AWS가 미리 정의한 정책으로 제공한다. 조직은 이를 그대로 쓰거나 복사해 커스터마이즈할 수 있다.
  3. 서비스 연결 역할(Service-linked role) 자동 생성VPC Endpoint, VPC Flow Logs, NAT Gateway 같은 기능을 사용할 때, AWS가 자동으로 서비스용 IAM 역할을 만들어 VPC 리소스에 접근할 수 있게 한다. 사용자가 명시적으로 역할을 생성할 필요가 없다.

AWS PrivateLink 개념: VPC 엔드포인트로 프라이빗 접근

인터넷 게이트웨이나 NAT 없이, VPC 안에서 AWS 서비스나 다른 VPC의 서비스에 AWS 내부망으로만 연결하는 기능이다.

1상대의 출발점 확인

VPC에서 AWS 서비스(S3, DynamoDB 등)나 다른 VPC의 서비스에 접근하려면, 인터넷 게이트웨이를 통해 인터넷으로 나갔다가 돌아오거나, NAT 게이트웨이를 써서 비용을 들여야 했다. 또한 인터넷 경로를 거치므로 보안 위험이 증가하고, 인터넷 연결이 없으면 접근이 차단된다.

2질문 제기

인터넷을 거치지 않고 AWS 내부 네트워크를 통해 AWS 서비스나 다른 VPC의 서비스에 프라이빗하게 접근할 수 있을까?

3구조적 핵심 예시

AWS PrivateLink는 VPC 엔드포인트(VPC Endpoint)를 제공한다. S3에 프라이빗하게 접근하려면, VPC 안에 S3 게이트웨이 엔드포인트를 만들고, 라우팅 테이블에 "S3로 가는 트래픽은 인터넷 게이트웨이가 아니라 이 엔드포인트로 보내라"고 설정한다. 그러면 S3로 향하는 모든 통신이 AWS 내부 네트워크를 타고 이동하며 인터넷을 거치지 않는다.

4단계별 동작 과정

  1. VPC 엔드포인트 생성사용자가 VPC 안에 엔드포인트를 만든다. S3와 DynamoDB는 게이트웨이 엔드포인트로 제공되며(요금 없음), 다른 AWS 서비스와 제3자 SaaS는 인터페이스 엔드포인트(약간의 시간당 요금)로 제공된다.
  2. 라우팅 테이블 또는 DNS 설정게이트웨이 엔드포인트는 라우팅 테이블에 자동으로 경로를 추가한다. 인터페이스 엔드포인트는 프라이빗 IP 주소를 갖는 네트워크 인터페이스(ENI, Elastic Network Interface)로 작동하며, DNS나 직접 호출로 접근할 수 있다.
  3. AWS 내부망 통신애플리케이션이 S3나 DynamoDB에 요청을 보내면, VPC 내부의 엔드포인트가 중개해 AWS 내부망을 통해 서비스로 전달하고, 응답을 받는다.

게이트웨이 엔드포인트: Amazon S3와 DynamoDB

라우팅 테이블에 경로를 추가해 S3와 DynamoDB로 가는 트래픽을 AWS 내부망으로 보내는, 요금이 없는 엔드포인트다.

→ 04-01 참조

1상대의 출발점 확인

인터페이스 엔드포인트는 시간당 요금이 들고, VPC 안에 새로운 네트워크 인터페이스를 추가하므로 관리 부담이 있다. S3와 DynamoDB는 AWS 내에서 요청량이 가장 많은 서비스이므로, 이들에 한해서는 더 단순하고 저렴한 방식이 필요했다.

2질문 제기

S3와 DynamoDB로 가는 프라이빗 트래픽을 라우팅 테이블만으로 제어하면서 추가 비용 없이 보낼 수 있을까?

3구조적 핵심 예시

게이트웨이 엔드포인트는 라우팅 테이블에 한 줄을 추가하는 방식이다. 라우팅 테이블에 "대상 주소 = S3의 IP 범위 목록(AWS가 제공하는 접두사 목록, pl-xxxx) → 라우팅 대상 = vpce-S3"이라고 쓰면, S3로 향하는 모든 트래픽이 인터넷 게이트웨이가 아니라 게이트웨이 엔드포인트로 보내진다. 네트워크 인터페이스를 만들 필요가 없고, 별도의 비용도 없다.

4단계별 동작 과정

  1. 게이트웨이 엔드포인트 생성VPC에서 S3 또는 DynamoDB 게이트웨이 엔드포인트를 만든다. 이 작업은 인스턴스나 네트워크 인터페이스를 새로 프로비저닝(provisioning, 준비)하지 않는다.
  2. 라우팅 테이블 경로 추가해당 엔드포인트가 작동할 서브넷의 라우팅 테이블에, 서비스로 향하는 트래픽을 엔드포인트로 보내는 경로를 추가한다. AWS는 서비스의 IP 대역을 접두사 목록(Prefix List)으로 제공하므로, 정확한 IP 범위를 일일이 입력할 필요가 없다.
  3. 트래픽 라우팅인스턴스가 S3나 DynamoDB에 요청을 보내면, 라우팅 테이블의 경로에 따라 게이트웨이 엔드포인트로 향하고, 엔드포인트가 내부적으로 서비스로 전달한다.

1상대의 출발점 확인

AWS 서비스(S3, DynamoDB, SNS 등)를 사용하려면 보통 인터넷 게이트웨이를 통해 공개 인터넷으로 나가 AWS의 공개 엔드포인트에 접속해야 합니다. 이 방식은 트래픽이 공개 인터넷을 거치므로 보안 우려가 있고, NAT 게이트웨이 같은 추가 구성이 필요해 비용이 늘어납니다.

2질문 제기

3구조적 핵심 예시

인터페이스 엔드포인트는 VPC 내 서브넷에 프라이빗 IP 주소를 가진 가상 네트워크 인터페이스(ENI)를 만들어, 그 인터페이스를 통해 AWS 서비스에 접속하게 합니다. 예를 들어 S3에 접속할 때 기존 방식은 인터넷 게이트웨이 → 공개 IP → AWS 공개 엔드포인트를 거치지만, 인터페이스 엔드포인트 방식은 서브넷 내부 프라이빗 IP에서 직접 S3 서비스로 향하는 경로가 생깁니다.

4단계별 동작 과정

  1. 엔드포인트 생성대상 서비스(예: S3, DynamoDB)를 선택하고 어느 VPC의 어느 서브넷에 엔드포인트를 만들지 지정하면, AWS가 해당 서브넷에 ENI(가상 네트워크 인터페이스)를 자동으로 생성하고 프라이빗 IP를 할당합니다.
  2. 보안 그룹 구성엔드포인트에 접근할 보안 그룹 규칙을 설정하여 VPC 내 어떤 리소스가 이 엔드포인트로 통신할 수 있는지 제어합니다.
  3. 프라이빗 DNS 활성화프라이빗 DNS 이름 활성화 옵션을 켜면 s3.amazonaws.com 같은 서비스의 원래 주소가 자동으로 엔드포인트의 프라이빗 IP로 변환되어, 애플리케이션 코드를 변경할 필요 없이 기존 방식 그대로 사용 가능합니다.

1상대의 출발점 확인

엔드포인트를 만들고 나면 VPC 내 누구나 그 엔드포인트를 통해 서비스에 접근할 수 있습니다. 하지만 실제로는 특정 팀만 특정 리소스에만 접근하도록 제한해야 할 경우가 많습니다. 보안 그룹은 네트워크 계층의 접근만 제어하므로, 서비스 수준에서 더 세밀한 권한 제어가 필요합니다.

2질문 제기

3구조적 핵심 예시

엔드포인트에 IAM 정책(Identity and Access Management 정책, 권한 명세)을 붙여서 특정 계정의 특정 역할만 특정 리소스(예: 특정 S3 버킷)에만 접근하도록 제한할 수 있습니다. 동시에 엔드포인트의 상태가 바뀌면(활성화됨, 비활성화됨, 오류 발생 등) SNS(Simple Notification Service, 메시지 발행 서비스)를 통해 자동으로 알림을 받습니다.

4단계별 동작 과정

  1. IAM 정책 추가엔드포인트에 IAM 형식의 정책을 설정하여 principal(주체, 누가), action(행동, 무엇을), resource(자원, 어디에) 조합으로 접근을 제한합니다. 예를 들어 "개발팀 역할은 이 S3 버킷의 읽기만 허용"처럼 지정할 수 있습니다.
  2. 접근 시도 검증VPC 내 리소스에서 엔드포인트를 통해 서비스에 접근할 때, 엔드포인트가 먼저 IAM 정책을 확인해서 요청 주체가 대상 리소스에 접근할 권한이 있는지 검증합니다.
  3. 상태 변화 알림엔드포인트의 상태가 변하면(예: 서비스 장애로 비활성화) SNS가 사전에 구성한 알림 채널(메일, Slack 등)로 즉시 알림을 전송합니다.

1상대의 출발점 확인

지금까지는 AWS가 만든 관리형 서비스(S3, DynamoDB 등)에만 엔드포인트로 접근했습니다. 그런데 내가 만든 서비스를 다른 계정의 VPC에서 안전하게 사용하게 하려면 어떻게 해야 할까요? 인터넷을 통해 공개하면 보안이 약해지고, VPN을 각각 설정하는 것도 복잡합니다.

2질문 제기

3구조적 핵심 예시

Network Load Balancer(NLB, 고성능 네트워크 수준의 트래픽 분배 장치) 뒤에 내 서비스를 배치하고, 그 NLB를 "엔드포인트 서비스"로 AWS에 등록하면, 다른 계정의 VPC에서 "인터페이스 엔드포인트"를 만들어 내 서비스에 프라이빗하게 접속할 수 있습니다. 이 과정에서 다른 계정의 소유자가 먼저 접근을 요청하면 나는 그 요청을 수락해야만 연결이 활성화됩니다.

4단계별 동작 과정

  1. 서비스 등록내 서비스를 NLB로 감싸고, 이 NLB를 AWS PrivateLink의 엔드포인트 서비스로 등록하며, 어느 계정들이 접근 요청을 할 수 있는지(또는 모두 허용할지) 지정합니다.
  2. 접근 요청 수신다른 계정의 사용자가 내 엔드포인트 서비스 이름을 가지고 그들의 VPC에서 인터페이스 엔드포인트를 만들면, 내 계정으로 접근 요청이 들어옵니다.
  3. 요청 수락 및 연결 활성화나는 대기 중인 요청을 검토한 후 수락하면 그 계정의 VPC가 나의 서비스에 프라이빗하게 접속할 수 있게 됩니다.

1상대의 출발점 확인

엔드포인트는 주로 특정 서비스에 접근하는 데 쓰입니다. 하지만 방화벽, 침입 탐지 시스템 같은 보안 어플라이언스는 모든 트래픽을 검사하고 필터링하는 역할을 하므로, 단순 접근 엔드포인트로는 부족합니다. 트래픽 흐름을 중간에 가로채서 보안 어플라이언스로 보낸 다음 계속 진행시키는 구조가 필요합니다.

3구조적 핵심 예시

연결 방식 고르기: 피어링·Transit Gateway·PrivateLink·VPN

VPC 를 다른 VPC 나 사내망에 이을 때 1:1 피어링, 허브형 Transit Gateway, 서비스 단위 PrivateLink, 인터넷 경유 암호화 터널 VPN 중 무엇을 쓸지 고르는 기준.

1상대의 출발점 확인

VPC는 격리된 네트워크이므로 다른 VPC나 온프레미스(사내) 데이터센터와 통신할 수 없습니다. VPC를 여러 개 만들고 조직이 커질수록 이들 간의 연결 필요성이 생깁니다. 연결 방식마다 복잡도, 확장성, 보안, 비용이 다르므로, 상황에 맞는 방식을 골라야 합니다.

2질문 제기

여러 VPC를 연결할 때, 두 VPC만 이을지, 많은 VPC를 허브처럼 한 곳에서 관리할지, 서비스 단위로만 공유할지, 아니면 인터넷 경유로 암호화해서 이을지 무엇을 선택해야 할까요?

3구조적 핵심 예시

연결 방식은 크게 네 가지입니다. VPC 피어링은 두 VPC 사이의 1:1 직접 연결(간단하지만 VPC가 많으면 복잡), Transit Gateway는 중앙 허브를 통한 다대다 연결(확장 가능), PrivateLink는 특정 서비스만 공유(보안 강화), VPN은 인터넷 경유 암호화 터널(온프레미스와 연결 시 주로 사용)입니다.

4단계별 동작 과정

  1. 피어링과 Transit Gateway 비교피어링은 두 VPC를 직접 이으므로 전체 CIDR 범위가 통신 가능하고 설정이 단순하지만, VPC가 10개 이상이면 연결 수가 급증하고 관리가 어려워집니다. Transit Gateway는 중앙의 라우팅 허브를 통해 여러 VPC를 한 곳에서 연결하므로 확장성이 좋습니다.
  2. PrivateLink의 차별점전체 VPC를 연결하지 않고 특정 서비스(예: 데이터베이스, 메시지 큐)만 공유하므로 보안이 강화되고, 서비스 단위 접근 제어가 가능합니다.
  3. VPN 선택 기준온프레미스 데이터센터와 연결하거나, 인터넷을 거치면서도 암호화가 필요할 때는 VPN을 사용합니다.

VPC 피어링 없이는 한 VPC에서 다른 VPC로 트래픽을 보낼 수 없습니다. 같은 계정의 VPC 두 개를 연결하려고 해도, 다른 계정의 VPC를 연결하려고 해도, 단순히 라우트 테이블만 설정해서는 작동하지 않습니다. 명시적인 피어링 관계를 먼저 만들고 양쪽이 동의해야 통신이 이루어집니다.

2질문 제기

두 VPC를 프라이빗하게 직접 연결하려면 어떤 절차를 거쳐야 할까요?

3구조적 핵심 예시

피어링 연결은 한쪽 VPC의 소유자가 다른 쪽 VPC에 "연결 요청"을 보내는 것으로 시작됩니다. 요청을 받은 쪽 VPC의 소유자가 수락해야만 연결이 활성화되고, 그 후에야 두 VPC 간의 트래픽이 흐를 수 있습니다.

4단계별 동작 과정

  1. 요청 생성한쪽 VPC의 소유자가 상대 VPC ID와 계정 ID(다른 계정인 경우)를 지정해서 피어링 요청을 생성합니다. 요청 상태는 "pending acceptance(수락 대기중)"가 됩니다.
  2. 요청 수락상대 VPC의 소유자가 AWS 콘솔이나 API에서 대기 중인 요청을 찾아 수락하면, 피어링 연결 상태가 "active(활성)"로 변합니다.
  3. 활성화 완료양쪽 피어링 연결이 active 상태가 되면 비로소 두 VPC 간의 직접 통신이 가능해집니다.

1상대의 출발점 확인

피어링 연결이 active 상태가 되어도 즉시 통신되지 않습니다. 피어링은 물리적 연결만 만들 뿐, 네트워크 트래픽이 실제로 흐르려면 라우팅 규칙이 있어야 합니다. 또한 보안 그룹은 기본적으로 같은 VPC 내의 리소스만 참조하므로, 다른 VPC의 리소스를 참조하려면 추가 설정이 필요합니다.

2질문 제기

3구조적 핵심 예시

VPC A의 서브넷 라우트 테이블에 "VPC B의 CIDR 범위로 가는 트래픽은 피어링 연결을 거쳐라"는 규칙을 넣고, VPC B의 라우트 테이블에도 역으로 "VPC A의 CIDR은 피어링을 거쳐"라고 설정해야 양쪽이 서로를 찾을 수 있습니다. 동시에 보안 그룹에서 상대 VPC의 CIDR이나 상대 리소스의 보안 그룹 자체를 참조하는 규칙을 추가하면 통신이 허용됩니다.

4단계별 동작 과정

  1. 라우팅 설정VPC A 내 서브넷의 라우트 테이블에 "destination(목대지)는 VPC B의 CIDR, target(경로)는 피어링 연결"이라는 항목을 추가합니다. VPC B도 마찬가지로 역방향 라우트를 설정해야 왕복 통신이 가능합니다.
  2. 보안 그룹 참조 활성화VPC A의 EC2 보안 그룹 ingress(수신) 규칙에 VPC B의 CIDR을 명시하거나, 또는 VPC B의 특정 보안 그룹 자체를 참조하는 규칙을 추가해서 통신을 허용합니다.
  3. 프라이빗 DNS 해석(선택)프라이빗 DNS를 활성화하면 상대 VPC의 호스트명을 프라이빗 IP로 자동 변환하여, IP 주소를 직접 입력하지 않고도 호스트명으로 접근할 수 있습니다.

피어링의 한계: 전이성 없음, CIDR 중복, 문제 해결

피어링은 A-B, B-C 가 있어도 A-C 로 이어지지 않고(전이성 없음), IP 대역이 겹치면 아예 맺을 수 없다는 제약과 그 진단 방법.

1상대의 출발점 확인

기존 방식: VPC를 따로 만들 때 각 VPC는 독립적으로 존재했고, 두 VPC 사이를 연결하려면 피어링(VPC Peering Connection)을 명시적으로 만들어야 했다. 하지만 피어링은 직접 연결된 두 VPC만 통신할 수 있고, A-B, B-C 피어링이 있어도 A와 C는 자동으로 통신되지 않는다(전이성 없음). 또한 피어링을 만들기 전에 두 VPC의 IP 대역(CIDR)이 겹치지 않는지 먼저 확인해야 하는데, 겹치면 피어링 자체를 만들 수 없다.

2질문 제기

A-B, B-C를 연결했을 때 A에서 C로 바로 통신할 수 없다면, 여러 VPC를 촘촘히 연결해야 할 때는 어떻게 해야 할까?

3구조적 핵심 예시

피어링의 전이성 부족 문제를 직접 보면, 세 VPC A(10.0.0.0/16), B(172.16.0.0/16), C(192.168.0.0/16)가 있을 때: - A ↔ B: 피어링 연결 O (CIDR 겹치지 않음) - B ↔ C: 피어링 연결 O (CIDR 겹치지 않음) - A ↔ C: 피어링이 없으므로 직접 통신 불가 (B를 거쳐도 A의 라우트 테이블에 C에 가는 경로가 없음)

4단계별 동작 과정

  1. 피어링 연결 확인두 VPC 간에 피어링 연결을 만들 때 먼저 CIDR 대역이 겹치지 않는지 확인한다. 겹치면 피어링을 만들 수 없다(제약).
  2. 라우트 테이블 설정각 VPC의 라우트 테이블에서 피어링된 VPC로 가는 경로를 직접 추가해야 한다. 이 경로는 자동으로 만들어지지 않는다.
  3. 통신 제약 적용A가 B를 거쳐 C에 가려 해도 A의 라우트 테이블에는 C로 가는 경로가 없으므로, A에서 출발한 트래픽은 C에 도달하지 못한다(전이성 없음).

Transit Gateway: 리전 라우터 개념과 연결(attachment) 유형

수많은 VPC·VPN·Direct Connect 를 별 모양으로 한 곳에 꽂아 서로 통신하게 해주는 리전 단위 클라우드 라우터와, 거기에 꽂는 연결(attachment) 종류.

1상대의 출발점 확인

기존 방식: 피어링은 두 VPC마다 연결을 만들어야 하고 라우트 테이블도 일일이 구성해야 하며, CIDR이 겹치면 아예 연결할 수 없었다. 만약 5개 VPC를 모두 서로 연결하려면 10개의 피어링 연결(5×4÷2)을 만들어야 하고, 각각에 라우트 테이블을 설정해야 한다. 또한 온프레미스 네트워크도 연결해야 하면 별도의 VPN 게이트웨이를 또 만들어야 한다.

2질문 제기

여러 VPC와 온프레미스를 중앙의 한 곳에서 관리하면서 서로 연결할 수는 없을까?

3구조적 핵심 예시

Transit Gateway는 리전 단위의 중앙 라우터처럼 작동한다. 5개의 VPC를 모두 Transit Gateway에 연결(attachment)하면, 각 VPC는 Transit Gateway의 라우트 테이블 하나만 참조하고, Transit Gateway가 내부적으로 트래픽을 모든 VPC에 분배한다.

4단계별 동작 과정

  1. 중앙 라우터 생성Transit Gateway를 특정 리전에 만든다. 이 Gateway는 여러 네트워크를 연결하는 중앙 허브 역할을 한다.
  2. 연결(Attachment) 만들기VPC, VPN, Direct Connect(전용선) 등 여러 네트워크를 Transit Gateway에 연결한다. 각 연결은 attachment라는 객체로 표현되며, 각 attachment는 고유한 라우트 테이블에 할당된다.
  3. 라우팅 설정Transit Gateway의 라우트 테이블에서 특정 CIDR 대역에 대해 어떤 attachment로 트래픽을 보낼지 결정한다. 각 VPC는 Transit Gateway 내부의 라우팅만 참조하면 된다.

어떤 attachment 가 어떤 라우트 테이블에 연결(association)되고 어떤 경로가 전파(propagation)되는지로 트래픽 흐름을 나누는 Transit Gateway 의 라우팅 구조.

→ 09-05 참조

1상대의 출발점 확인

기존 방식: Transit Gateway에 여러 VPC를 연결하면, 이제 attachment들이 서로 통신해야 하는데 누가 누구와 통신할지를 제어해야 한다. 만약 모든 attachment가 모든 다른 attachment와 통신할 수 있다면, 보안 그룹처럼 격리 정책이 없으므로 원치 않는 트래픽도 통과한다. 또한 어떤 CIDR 대역으로의 트래픽이 어느 attachment로 가야 하는지 정의할 중앙 집중식 라우팅 규칙이 필요하다.

2질문 제기

Transit Gateway에 여러 attachment가 연결되었을 때, 어떤 attachment가 어떤 라우트 테이블에 속하고 어디로 트래픽을 보낼지를 어떻게 관리할까?

3구조적 핵심 예시

Transit Gateway는 여러 라우트 테이블을 가질 수 있고, 각 attachment는 하나의 라우트 테이블에 association(관련)된다. 예를 들어 "프로덕션 라우트 테이블"에는 프로덕션 VPC들의 attachment가 모여 있고, 이 테이블에는 프로덕션 간 통신 경로만 있다. 반면 "개발 라우트 테이블"에는 개발 VPC들의 attachment가 있고, 프로덕션과 개발 간에는 통신 경로가 없다.

4단계별 동작 과정

  1. 라우트 테이블 생성 및 associationTransit Gateway에 여러 라우트 테이블을 만들고, 각 attachment(VPC, VPN 등)를 특정 라우트 테이블에 association한다. 같은 테이블에 속한 attachment들이 통신할 수 있는 기본 구조가 된다.
  2. 라우트 전파(Propagation)각 attachment가 자신의 CIDR 대역을 자신이 속한 라우트 테이블에 자동으로 등록(propagate)할 수 있도록 설정하거나, 수동으로 정적 라우트(static route)를 추가한다.
  3. 정책 테이블(Policy Table) 적용라우트 테이블에 정책을 추가해, 특정 CIDR에서 오는 트래픽을 거부하거나 특정 attachment로만 보내는 세밀한 제어를 한다.

Site-to-Site VPN: 가상 프라이빗 게이트웨이·고객 게이트웨이·이중 터널

사내 라우터(고객 게이트웨이)와 AWS 쪽 게이트웨이를 인터넷 위 암호화 터널 두 개로 이어 온프레미스와 VPC 를 연결하는 서비스.

1상대의 출발점 확인

기존 방식: 사내 네트워크와 AWS VPC를 연결할 때 인터넷을 그대로 쓰면 트래픽이 암호화되지 않아 보안 위험이 크다. 따라서 사내 라우터(고객 게이트웨이라고 부름)와 AWS 쪽 게이트웨이를 명시적으로 연결해야 하고, 그 사이의 모든 트래픽을 암호화해야 한다. 이런 용도로 인터넷 위에 암호화된 터널(VPN 터널)을 만든다.

2질문 제기

인터넷을 거쳐 사내 네트워크와 AWS를 안전하게 연결하려면 어떻게 해야 할까?

3구조적 핵심 예시

VPN 터널은 사내 라우터와 AWS 게이트웨이 사이에 인터넷 위의 암호화 통로를 만드는 것이다. 이 터널은 두 개가 기본이다. 예를 들어 첫 번째 터널(터널 1)이 끊어지면 두 번째 터널(터널 2)이 자동으로 트래픽을 받으므로, 한쪽이 장애 나도 통신이 끊기지 않는다.

4단계별 동작 과정

  1. 게이트웨이 설정AWS 쪽에 Virtual Private Gateway(VPG, VPC 쪽 게이트웨이)를 만들고, 사내 쪽에 Customer Gateway(고객 게이트웨이)를 등록한다. 고객 게이트웨이는 실제로는 사내 라우터의 공인 IP와 지원하는 암호화 방식 정보다.
  2. VPN 연결 생성Virtual Private Gateway와 Customer Gateway 사이에 VPN Connection을 만든다. AWS가 자동으로 두 개의 암호화 터널을 만들고 각 터널마다 고유한 암호화 키를 생성한다.
  3. 트래픽 흐름사내 네트워크의 트래픽이 Customer Gateway에 도착하면, 터널 중 활성화된 것으로 암호화되어 인터넷을 건너 AWS로 전달되고, Virtual Private Gateway에서 복호화되어 VPC 내부로 라우팅된다.

1상대의 출발점 확인

기존 방식: Site-to-Site VPN 터널을 만들면 기본적으로 두 개 터널이 만들어지지만, VPN은 인터넷을 타므로 네트워크 지연과 대역폭 제약이 있을 수 있다. 또한 사내 라우터 쪽이 장애 나면 Customer Gateway는 정상이더라도 사내 쪽 연결이 끊기고, AWS 쪽 Virtual Private Gateway가 장애 나면 전체 연결이 끊긴다. 따라서 높은 가용성이 필요하면 추가 조치가 필요하다.

2질문 제기

VPN 터널이 두 개여도 사내 라우터나 AWS 게이트웨이가 장애 나면 막히는데, 이를 어떻게 보호할 수 있을까?

3구조적 핵심 예시

VPN 터널의 이중화는 여러 계층에서 이루어진다. 터널 레벨에서는 두 터널이 기본으로 있고, Customer Gateway 레벨에서는 두 대의 사내 라우터를 Active-Standby나 Active-Active로 구성할 수 있다. 또한 AWS 쪽 Virtual Private Gateway도 여러 리전의 게이트웨이와 조합하거나 Direct Connect라는 전용선을 함께 쓸 수 있다.

4단계별 동작 과정

  1. 터널 암호화·라우팅 옵션 설정VPN 터널의 Phase 1(IKE) 단계에서 암호화 알고리즘을 정하고, Phase 2(IPsec)에서 데이터 암호화 방식을 정한다. 라우팅은 정적 라우팅(수동으로 경로를 지정)이나 동적 라우팅(BGP로 자동 경로 교환)으로 설정한다.
  2. Customer Gateway 이중화사내에 두 대 이상의 라우터를 놓고 각각 AWS에 VPN을 만든다(각 라우터가 각각 Customer Gateway가 됨). VPN 1이 장애 나도 VPN 2가 트래픽을 받는다.
  3. Direct Connect 조합더 높은 안정성과 성능이 필요하면 AWS Direct Connect(전용 물리 회선)를 동시에 구성한다. VPN은 인터넷용 백업, Direct Connect는 주요 연결로 쓸 수 있다.

VPC 서브넷 공유(AWS RAM): 소유자와 참여자

VPC 소유 계정이 AWS RAM으로 서브넷을 다른 계정에 공유해, 참여자가 같은 서브넷에 리소스를 만들면서도 VPC 자체는 소유자만 관리하게 하는 기능이다.

1상대의 출발점 확인

기존 방식: 각 팀이나 사업부가 자신의 AWS 계정을 따로 가지고 독립적으로 VPC와 서브넷을 관리했다. 하지만 회사 규모가 커지면서 여러 계정이 같은 서브넷에서 리소스를 만들어야 하는 경우가 생겼다. 그럴 때마다 같은 서브넷을 각 계정마다 복제하거나, 중복된 IP 주소를 피하려고 아주 복잡하게 관리했다.

2질문 제기

한 VPC의 서브넷을 다른 AWS 계정도 사용하게 하면서, 서브넷 자체의 관리는 원래 소유자가 하려면 어떻게 해야 할까?

3구조적 핵심 예시

VPC 서브넷 공유는 AWS Resource Access Manager(RAM)를 통해 이루어진다. VPC 소유 계정이 "이 서브넷을 계정 B, C, D와 공유하겠다"고 선언하면, 계정 B, C, D는 그 서브넷에 EC2, RDS 같은 리소스를 만들 수 있다. 하지만 서브넷의 CIDR, 라우트 테이블 같은 핵심 설정은 VPC 소유자만 바꿀 수 있다.

4단계별 동작 과정

  1. 공유 리소스 등록VPC 소유 계정에서 공유할 서브넷을 AWS RAM 공유 리소스로 등록한다.
  2. 참여자 계정 초대공유 리소스에 다른 계정들을 초대하거나 조직(Organization) 전체에 공개한다. 초대받은 계정들(참여자)은 공유 요청을 수락한다.
  3. 리소스 생성 및 격리참여자 계정들은 공유받은 서브넷에서 자신의 리소스를 만들 수 있고, 각 계정은 자신이 만든 리소스만 관리한다. VPC와 서브넷 자체는 소유 계정이 관리한다.

IPAM 개념: 스코프·풀·할당

IPAM은 IP 주소를 스코프(프라이빗/퍼블릭 영역)와 그 안의 풀(주소 묶음), 풀에서 나가는 할당으로 계층 관리하는 AWS의 IP 주소 관리 도구다.

1상대의 출발점 확인

기존 방식: 수십 개의 VPC를 만들 때 각 VPC에 할당할 IP 대역(CIDR)을 수동으로 정하고, 스프레드시트에 기록하고, 중복이 없는지 일일이 확인했다. 또한 퍼블릭 IP 주소도 구분해서 관리해야 했고, AWS 가용 영역(AZ)이나 리전마다 서브넷을 만들 때마다 CIDR을 나누는 계획을 세워야 했다. 규모가 크면 이런 작업이 매우 복잡해진다.

2질문 제기

수많은 VPC, 서브넷, 퍼블릭/프라이빗 IP를 일관되게 관리하고 중복을 자동으로 피할 수는 없을까?

3구조적 핵심 예시

IPAM(IP Address Manager)은 계층 구조로 IP를 관리한다. 최상위에 스코프(scope)가 있는데, 이는 프라이빗 IP 영역과 퍼블릭 IP 영역으로 나뉜다. 각 스코프 안에는 풀(pool)이 있고, 풀은 회사 전체, 리전별, 팀별 같은 단위로 큰 IP 대역을 묶는다. 그 풀에서 VPC나 서브넷에 할당(allocation)할 IP 대역을 나누어 준다.

4단계별 동작 과정

  1. 스코프 정의IPAM을 활성화할 때 프라이빗 스코프(사내 IP)와 퍼블릭 스코프를 정의한다. 각 스코프는 독립적으로 관리된다.
  2. 풀 구성각 스코프 안에 풀을 만든다. 예를 들어 프라이빗 스코프에 "전사 풀(10.0.0.0/8)", "서울 리전 풀(10.0.0.0/16)", "개발팀 풀(10.0.0.0/20)" 같이 위계적으로 구성할 수 있다. 더 작은 풀은 상위 풀에서 일부를 떼어낸다.
  3. 할당 및 모니터링VPC나 서브넷을 만들 때 IPAM에서 특정 풀에서 IP를 할당받는다. IPAM은 이미 할당된 IP를 추적하므로 중복을 피하고, 남은 주소 수도 보여준다.

1상대의 출발점 확인

2질문 제기

수십 개 이상의 AWS 계정에서 주소 충돌 없이, 정해진 규칙에 따라 VPC 주소를 자동으로 할당받게 하려면?

3구조적 핵심 예시

중앙 IPAM 풀에 10.0.0.0/8을 등록한 후, "모든 개발 계정은 /20 단위, 모든 프로덕션 계정은 /18 단위로만 할당 가능" 같은 규칙을 설정한다. 각 계정의 개발자가 VPC 생성 시 IPAM API를 호출하면, 규칙과 충돌 확인을 거쳐 자동으로 다음 사용 가능한 CIDR(예: 10.5.0.0/20)을 받는다.

4단계별 동작 과정

  1. 풀 등록 및 규칙 설정AWS Organizations 최상위에서 IPAM을 활성화하고, 조직 전체가 쓸 주소 풀(CIDR 범위)과 할당 규칙(넷마스크, 태그 조건)을 정의한다.
  2. 자동 할당각 계정의 VPC 생성 시 IPAM에 할당 요청을 보내면, 규칙 검증을 거쳐 중복 없는 다음 CIDR을 자동으로 반환한다.
  3. 감시 및 재사용할당된 CIDR의 사용 현황을 IPAM 대시보드에서 보고, 반환되거나 해제된 주소는 풀에 다시 편입된다.

1상대의 출발점 확인

VPC·서브넷·보안 그룹 등 리소스마다 계정·리전 단위 상한이 있으며, 일부는 상향 요청이 가능하고 사용량은 비용 보고서로 확인한다.

1상대의 출발점 확인

기존에는 VPC, 서브넷, 보안 그룹, 라우트 테이블 등 리소스를 필요한 대로 무한정 만들 수 있다고 가정했습니다. 그러다 어느 시점에 "이 리소스는 더 이상 생성할 수 없습니다" 같은 오류가 발생하면 그제야 상한이 있다는 것을 알게 되었고, 비용이 어디서 나오는지 파악하기 어려우며, 자신의 계정 전체에서 리소스 사용량이 어느 정도인지도 알 수 없었습니다.

2질문 제기

VPC 리소스는 얼마나 많이 만들 수 있으며, 비용과 사용량은 어디서 확인할 수 있을까요?

3구조적 핵심 예시

AWS 계정에서 VPC는 리전당 최대 5개까지만 만들 수 있고, 서브넷은 VPC당 200개 한도가 있으며, 보안 그룹은 VPC당 500개까지다. 더 필요하면 AWS 콘솔의 Service Quotas에서 상향 요청을 할 수 있고(대부분 자동 승인 또는 수 시간 내 심사), VPC 관련 비용(데이터 전송, NAT 게이트웨이 사용료 등)은 AWS 빌링 대시보드의 비용 탐색기에서 월단위로 추이를 확인할 수 있습니다.

4단계별 동작 과정

  1. 할당량 확인AWS 콘솔의 Service Quotas 페이지를 열어 VPC, 서브넷, 보안 그룹 등 각 리소스의 현재 한도와 사용 중인 개수를 조회합니다.
  2. 상향 요청한도에 도달했거나 더 필요한 경우, 해당 할당량 옆의 "요청(Request)" 버튼을 클릭해 상향 신청하며, 대부분의 요청은 자동으로 승인됩니다.
  3. 비용 모니터링AWS 빌링 대시보드의 비용 탐색기에서 VPC 관련 서비스(NAT 게이트웨이, 데이터 전송, VPC 엔드포인트 등)의 월간 비용을 조회하고 추세를 추적합니다.

  2. 리소스 생성예제의 구성도를 보면서 순서에 따라 VPC, 서브넷, 라우팅 테이블, 인터넷 게이트웨이, 보안 그룹을 생성하고 각각을 올바르게 연결합니다.
  3. 검증 및 테스트EC2 인스턴스를 배포해 공개 서브넷의 웹 서버는 인터넷에서 접근이 가능하고, 비공개 서브넷의 데이터베이스 서버는 외부 노출이 없으며, 웹 서버에서 데이터베이스로의 내부 통신은 가능한지 실제로 테스트합니다.
