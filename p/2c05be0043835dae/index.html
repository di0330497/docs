VPC의 정의와 동작 방식

Amazon VPC는 AWS 클라우드 안에 사용자가 직접 정의한 사설 가상 네트워크를 만들고, 그 안에서 서브넷·라우팅·게이트웨이로 트래픽을 통제하는 서비스다.

#1문제 상황

데이터센터에서는 서버를 사서 랙에 넣고 스위치와 라우터를 직접 배선해 네트워크를 만들었다. 서버 한 대를 늘리려면 장비 구매와 설치를 기다려야 하고, 주소 대역과 라우팅 규칙도 관리자가 손으로 정하고 유지해야 했다.

클라우드에서 리소스를 그냥 띄우면 이런 통제 계층이 사라진다. 어떤 리소스가 어떤 대역을 쓰고 누구와 통신할 수 있는지 격리해 두지 않으면, 접근 범위를 관리자가 일관되게 제한하기 어렵다.

#2핵심 질문

클라우드에 올린 리소스를 데이터센터처럼 내가 정한 주소 범위와 통제 규칙 안에 격리해 둘 수는 없을까?

#3동작 예시

10.0.0.0/16 대역으로 VPC를 만들고 리전 안 각 가용 영역마다 서브넷을 하나씩 두면, 그 안에 띄운 EC2 인스턴스는 각자 서브넷 범위의 사설 IP를 받는다. 여기에 인터넷 게이트웨이를 붙이고 라우팅 테이블에 외부로 나가는 경로를 넣은 서브넷의 인스턴스만 인터넷과 통신하고, 나머지 서브넷의 인스턴스는 VPC 내부에서만 통신한다.

#4동작 과정

  1. CIDR 지정VPC를 만들 때 10.0.0.0/16 같은 사설 IP 대역을 정한다. 이 대역이 VPC 안 모든 주소의 뿌리가 되고, 이후 서브넷은 이 대역을 쪼개서 가져간다.
  2. 서브넷과 라우팅정한 대역을 나눠 가용 영역마다 서브넷을 만들고, 라우팅 테이블(패킷을 어디로 보낼지 적어 둔 규칙 목록)로 트래픽 경로를 정한다. 그래서 같은 VPC 안에서도 서브넷마다 도달할 수 있는 목적지가 달라진다.
  3. 게이트웨이 연결인터넷 게이트웨이나 NAT 게이트웨이를 붙여 VPC와 외부의 연결 여부를 결정한다. 이 연결이 없으면 리소스는 사설 대역 안에만 머문다.

#5한 줄 요약

클라우드 안에 사용자가 정의한 사설 가상 네트워크를 만들어 주소·라우팅·게이트웨이로 리소스 간 트래픽을 직접 통제하는 것

기본 VPC와 기본 서브넷

기본 VPC는 계정 생성 시 각 리전에 자동으로 만들어지는 인터넷 연결 가능한 VPC로, 리전마다 하나의 서브넷과 기본 라우팅·보안 설정이 함께 제공된다.

#1문제 상황

VPC를 처음부터 직접 설계하려면 CIDR 대역, 서브넷, 라우팅 테이블, 인터넷 게이트웨이를 하나씩 만들어 연결해야 한다. 네트워크 구성이 익숙하지 않은 사람에게는 EC2 인스턴스 하나 띄우기 전에 넘어야 할 관문이 여러 개인 셈이다.

그래서 VPC를 아직 만들지 않은 계정에서는 바로 리소스를 띄울 대상이 없고, 첫 사용이 지연된다. AWS는 이 진입 장벽을 없애기 위해 계정마다 기본 구성을 미리 준비해 둔다.

#2핵심 질문

VPC와 서브넷을 직접 설계하지 않아도 바로 인스턴스를 띄울 수 있는 기본 구성이 있지 않을까?

#3동작 예시

계정을 만들고 각 리전에 들어가면 기본 VPC가 하나씩 이미 존재한다. 이 VPC에는 가용 영역마다 퍼블릭 서브넷이 있고 인터넷 게이트웨이와 DNS 확인 설정이 붙어 있어서, 아무 설정 없이 EC2 인스턴스를 그대로 실행하면 바로 인터넷과 통신하는 구조가 된다.

#4동작 과정

  1. 자동 생성계정이 만들어지면 각 리전에 기본 VPC가 하나씩 함께 생성된다. 그래서 사용자가 별도 작업을 하지 않아도 시작할 대상이 이미 있다.
  2. 기본 구성 포함기본 VPC에는 가용 영역별 퍼블릭 서브넷, 인터넷 게이트웨이, DNS 확인 설정이 들어 있다. 그래서 인스턴스를 띄우면 바로 외부와 통신할 수 있다.
  3. 수정과 확장필요하면 기본 VPC의 구성 요소를 바꾸거나 서브넷을 추가할 수 있다. 빠른 시작과 공개 인스턴스 용도에 적합하다.

#5한 줄 요약

계정마다 각 리전에 인터넷 연결이 준비된 VPC와 서브넷을 미리 제공해, 별도 설계 없이 바로 리소스를 띄울 수 있게 하는 것

VPC 생성·삭제와 리소스 맵

VPC를 CIDR 블록과 테넌시를 지정해 만들고, 더 이상 필요 없을 때 리소스 의존성을 정리한 뒤 삭제하며, 리소스 맵으로 VPC 안의 구성 요소 관계를 시각적으로 확인한다.

#1문제 상황

VPC는 그 자체만 만들면 안에 아무것도 넣을 수 없다. 서브넷, 라우팅 테이블, 게이트웨이 같은 자원이 함께 있어야 그 안에 EC2 같은 리소스를 배치할 수 있다.

그래서 VPC를 하나씩 손으로 만들면 어떤 자원이 서로 연결돼 있는지 놓치기 쉽고, 반대로 정리할 때는 무엇이 무엇에 매달려 있는지 파악되지 않아 삭제가 막힌다. 구성 요소 간 관계를 한눈에 보여 주는 수단이 필요하다.

#2핵심 질문

VPC를 만들 때 필요한 자원을 함께 구성하고, 그 관계를 확인하고 안전하게 정리하려면 어떻게 해야 할까?

#3동작 예시

콘솔에서 Create VPC를 열고 Resources to create에서 VPC and more를 고르면, CIDR 대역과 가용 영역 개수를 지정하는 것만으로 서브넷·라우팅 테이블·인터넷 게이트웨이까지 한 번에 만들어진다. 생성 후 리소스 맵을 열면 VPC 안의 서브넷과 게이트웨이가 어떤 라우팅으로 이어져 있는지 그림으로 확인할 수 있다.

#4동작 과정

  1. VPC와 자원 생성CIDR 대역을 정해 VPC를 만들고, 서브넷·라우팅 테이블·게이트웨이를 함께 생성한다. 그래서 별도 조립 없이 그 안에 리소스를 배치할 수 있는 상태가 된다.
  2. 구성 확인리소스 맵으로 VPC 안 구성 요소와 연결 관계를 시각적으로 본다. 그래서 라우팅이 어디로 향하는지 빠르게 점검할 수 있다.
  3. 삭제 전 정리더 이상 필요 없으면 자원 간 의존성을 먼저 정리한 뒤 VPC를 삭제한다. 콘솔에서 한 작업을 IaC 코드로 생성해 같은 구성을 다시 만들 수도 있다.

#5한 줄 요약

VPC와 딸린 자원을 한 번에 구성하고 그 연결 관계를 확인한 뒤 의존성을 정리해 안전하게 정리·재현할 수 있게 하는 것

CIDR과 IP 주소 설계

VPC와 서브넷은 CIDR 표기(예: 10.0.0.0/16)로 사설 IP 주소 범위를 나누어 가지며, 이 대역 설계가 향후 확장성과 다른 네트워크와의 충돌 여부를 결정한다.

→ 01-05 참조

#1문제 상황

네트워크 주소를 아무렇게나 잡으면 나중에 문제가 된다. 대역이 너무 좁으면 서브넷을 더 쪼갤 자리가 없어 리소스를 늘리지 못하고, 이미 쓰는 대역과 겹치면 온프레미스나 다른 네트워크와 연결할 때 주소가 충돌한다.

그래서 VPC를 만들 때 정하는 주소 대역은 단순한 설정값이 아니라 앞으로의 확장 여지와 연결 가능성을 좌우하는 결정이 된다. 대역을 나누는 표기와 규칙을 먼저 이해해야 한다.

#2핵심 질문

VPC와 서브넷의 주소 범위를 어떤 규칙과 크기로 나눠야 확장성과 연결성을 확보할 수 있을까?

#3동작 예시

VPC에 10.0.0.0/16을 지정하면 65,536개의 주소를 쓸 수 있고, 이 안에서 10.0.0.0/24와 10.0.1.0/24 같은 더 작은 블록을 떼어 각각 서브넷에 준다. 이 서브넷들은 같은 VPC 대역에 속하므로 주소가 겹치지 않고, 나중에 서브넷을 추가하려면 남겨 둔 대역에서 다시 떼어 쓰면 된다.

#4동작 과정

  1. CIDR 표기 이해주소는 10.0.0.0/16처럼 CIDR 표기로 적는다. 슬래시 뒤 숫자가 작을수록 담을 수 있는 주소 수가 많아진다.
  2. VPC 대역 지정VPC를 만들 때 IPv4 CIDR 블록을 반드시 하나 지정한다. 허용되는 블록 크기는 /16(65,536개)부터 /28(16개)까지이며, 사설 IPv4 대역에서 고르는 것이 권장된다.
  3. 서브넷으로 분할VPC 대역을 더 작은 서브넷 CIDR 블록으로 나눠 각 가용 영역에 배정한다. 그래서 대역 설계 하나가 이후 서브넷 추가와 다른 네트워크와의 연결 여부를 결정한다.

#5한 줄 요약

CIDR 표기로 사설 주소 범위를 나눠 VPC와 서브넷에 배정함으로써 확장 여지와 네트워크 간 충돌 없는 연결을 미리 확보하는 것

IPv6 지원과 듀얼스택

VPC와 서브넷에 IPv6 CIDR 블록을 연결하면 IPv4와 IPv6 주소를 함께 쓰는 듀얼스택 구성이 되어, 리소스가 두 주소 체계로 통신할 수 있다.

→ 01-04 참조

#1문제 상황

VPC와 서브넷은 기본적으로 IPv4 주소 체계로 동작한다. IPv4 주소는 개수가 한정돼 있어, 규모가 커지거나 IPv6만 지원하는 대상과 통신해야 할 때는 IPv4만으로는 대응이 어렵다.

그러나 VPC를 처음부터 IPv6 전용으로 새로 만들면 기존 리소스와 설정을 그대로 옮길 수 없다. IPv4 전용 서브넷에서 IPv6 전용 서브넷으로 넘어가는 마이그레이션 경로가 없기 때문이다.

#2핵심 질문

이미 IPv4로 돌아가는 VPC에 IPv6를 더해 두 주소 체계를 함께 쓰려면 어떻게 해야 할까?

#3동작 예시

IPv4 전용으로 쓰던 VPC에 IPv6 CIDR 블록을 연결하면 그 VPC는 듀얼스택 모드가 된다. 이때 리소스는 IPv4로도, IPv6로도, 또는 둘 다로 통신할 수 있고, 두 주소 체계의 통신은 서로 독립적으로 이뤄진다. 서브넷에도 IPv6 CIDR 블록을 연결해야 그 서브넷의 네트워크 인터페이스가 IPv6 주소를 받는다.

#4동작 과정

  1. VPC에 IPv6 연결기존 IPv4 VPC에 IPv6 CIDR 블록을 연결한다. 그래서 VPC 자체가 두 주소 체계를 다루는 상태가 된다.
  2. 서브넷에 IPv6 연결서브넷에도 IPv6 CIDR 블록을 연결하고 IPv6 주소 지정 속성을 켠다. 그래서 그 서브넷에서 만든 네트워크 인터페이스가 IPv6 주소를 받는다.
  3. 듀얼스택 통신리소스가 IPv4와 IPv6로 각각 통신한다. IPv4 지원은 끌 수 없고, 두 체계는 서로 독립적으로 동작한다.

#5한 줄 요약

기존 IPv4 VPC에 IPv6를 더해 리소스가 두 주소 체계로 통신하는 듀얼스택 구성을 만드는 것

AWS IP 범위와 프리픽스 리스트

AWS가 공개하는 리전별 IP 주소 범위(ip-ranges.json)는 서비스가 사용하는 공인 IP 대역을 알려주고, 관리형 프리픽스 리스트는 이런 CIDR 집합을 재사용 가능한 이름으로 묶어 보안 규칙에 활용하게 한다.

#1문제 상황

AWS 서비스와 통신하면서 그 트래픽을 보안 규칙으로 허용하거나 차단하려면 상대가 쓰는 공인 IP 대역을 알아야 한다. 서비스마다 대역이 조금씩 바뀌는데, 이 값을 사람이 추측하거나 목록으로 손수 관리하면 빠뜨리거나 낡은 값이 남기 쉽다.

그래서 규칙에 CIDR을 하나씩 직접 적는 방식은 대역이 바뀔 때마다 여러 규칙을 함께 고쳐야 하고, 어떤 서비스가 어떤 대역을 쓰는지 확인할 근거도 약해진다.

#2핵심 질문

AWS 서비스가 쓰는 IP 대역을 신뢰할 수 있는 출처에서 얻어 보안 규칙에 재사용할 수는 없을까?

#3동작 예시

AWS는 고객이 흔히 쓰는 서비스의 현재 IP 주소 범위를 JSON 형식으로 공개한다. 이 정보로 어떤 트래픽이 AWS에서 오는지 식별하고, 특정 AWS 서비스로 가는 또는 그로부터 오는 트래픽을 허용하거나 차단하는 규칙을 만들 수 있다. 일부 서비스는 이 대역을 AWS 관리형 프리픽스 리스트라는 이름으로 제공해, CIDR 묶음을 이름 하나로 규칙에 넣게 해 준다.

#4동작 과정

  1. 범위 취득AWS가 공개하는 ip-ranges JSON을 받아 서비스별 주소 범위를 확인한다. 모든 서비스가 공개되는 것은 아니고, 고객이 흔히 쓰는 서비스 위주로 제공된다.
  2. 규칙에 반영얻은 CIDR을 보안 규칙에 적어 허용·차단을 정한다. 서비스가 제공하는 AWS 관리형 프리픽스 리스트를 쓰면 여러 CIDR을 하나의 이름으로 묶어 관리할 수 있다.
  3. 직접 관리필요한 대역을 직접 묶어 고객 관리형 프리픽스 리스트로 만들어 재사용하고 공유할 수도 있다. BYOIP로 AWS에 가져온 대역은 공개 JSON에 포함되지 않는다.

#5한 줄 요약

AWS가 공개한 IP 대역과 프리픽스 리스트를 근거로 삼아 서비스 트래픽을 허용·차단하는 규칙을 일관되게 관리하는 것

서브넷 생성과 IP 속성

VPC CIDR 범위 안에서 서브넷 CIDR을 지정해 서브넷을 만들고, 퍼블릭 IPv4 자동 할당·IPv6 CIDR 연결 등 IP 주소 속성을 설정하는 것.

#1문제 상황

VPC 대역만 정해서는 리소스를 배치할 수 없다. 리소스는 서브넷 안에 들어가고, 그 서브넷의 주소 설정에 따라 각 리소스가 어떤 주소를 받는지가 정해진다.

서브넷을 만들 때 IP 관련 속성을 정하지 않으면 인스턴스가 공인 IPv4 주소를 받지 못하거나, IPv6를 쓰려 해도 주소가 할당되지 않는 일이 생긴다. 주소 체계를 어떤 기준으로 켜고 끄는지 미리 알아야 한다.

#2핵심 질문

서브넷을 만들 때 어떤 IP 속성을 어떻게 정해야 인스턴스가 필요한 주소를 제대로 받을까?

#3동작 예시

기본이 아닌 서브넷은 IPv4 공인 주소 자동 할당 속성이 기본적으로 꺼져 있고, 기본 서브넷은 켜져 있다. 그래서 같은 인스턴스를 띄워도 어느 서브넷에 넣느냐에 따라 공인 IPv4 주소를 자동으로 받는지가 달라진다. IPv6 주소 지정 속성은 모든 서브넷에서 기본적으로 꺼져 있어, 켜려면 서브넷에 IPv6 CIDR 블록이 연결돼 있어야 한다.

#4동작 과정

  1. 서브넷 생성VPC CIDR 범위 안에서 서브넷 CIDR을 지정해 서브넷을 만든다. 그래서 리소스를 배치할 주소 공간이 생긴다.
  2. IPv4 속성 설정공인 IPv4 주소 자동 할당 속성을 켜거나 끈다. 그래서 그 서브넷에서 만든 인스턴스가 공인 주소를 자동으로 받을지가 정해진다.
  3. IPv6 속성 설정서브넷에 IPv6 CIDR 블록을 연결한 뒤 IPv6 주소 지정 속성을 켠다. 그래서 그 서브넷의 네트워크 인터페이스와 인스턴스가 IPv6 주소를 받는다.

#5한 줄 요약

VPC 대역 안에서 서브넷 CIDR을 정하고 IPv4·IPv6 주소 속성을 켜고 꺼서 인스턴스가 받을 주소를 통제하는 것

라우트 테이블의 개념과 유형

서브넷이나 게이트웨이에 연결되어 목적지 CIDR별로 트래픽을 어디로 보낼지 규칙을 담는 라우트 테이블과, 서브넷용·게이트웨이용 등 그 유형을 이르는 개념.

#1문제 상황

서브넷은 IP 주소 범위를 나눠 담는 그릇일 뿐, 그 안에서 나간 패킷이 어디로 향할지는 스스로 정하지 못한다. 서브넷마다 "이 목적지로 가는 트래픽은 저 게이트웨이로 보낸다"는 규칙을 사람이 하나하나 붙여 주지 않으면, 인스턴스가 같은 VPC 안의 다른 서브넷조차 찾지 못한다.

VPC를 만들 때 자동으로 따라오는 기본 규칙 하나만으로는 부족하다. 서브넷별로 인터넷을 열어 줄 곳과 닫아 둘 곳이 다르고, 나중에 만든 서브넷은 어느 규칙을 따를지 명시적으로 지정해야 하기 때문이다. 어떤 규칙도 연결되지 않은 서브넷은 목적지를 알 수 없어 트래픽이 버려진다.

#2핵심 질문

서브넷에서 나온 트래픽의 목적지별 다음 경로를 어떤 규칙 묶음으로 정하고, 그 묶음을 서브넷·게이트웨이 중 어디에 붙이는가?

#3동작 예시

서브넷 A에 연결된 라우트 테이블에 10.0.0.0/16 → local 과 0.0.0.0/0 → igw-1234 두 줄이 있다고 하자. 인스턴스가 같은 VPC의 10.0.5.10으로 패킷을 보내면 첫 줄과 맞아 local(내부 연결)로 처리되고, 8.8.8.8로 보내면 0.0.0.0/0과 맞아 인터넷 게이트웨이로 나간다. 목적지 CIDR이 더 구체적인 줄이 먼저 선택된다.

#4동작 과정

  1. 규칙 묶음 준비VPC를 만들면 메인 라우트 테이블이 자동 생성되고, 별도로 연결하지 않은 모든 서브넷이 이 메인 테이블을 따른다. 필요한 서브넷에는 커스텀 라우트 테이블을 새로 만들어 붙인다.
  2. 목적지와 대상 짝짓기각 라우트는 목적지(Destination, 트래픽이 향할 IP 범위)와 대상(Target, 그 트래픽을 넘길 게이트웨이·네트워크 인터페이스·연결)을 한 쌍으로 담는다. VPC 내부 통신용 local 라우트는 IPv4·IPv6 각각 기본으로 들어 있다.
  3. 연결과 전파라우트 테이블을 서브넷에 연결하면 그 서브넷 라우트 테이블이 되고, 게이트웨이에 연결하면 게이트웨이 라우트 테이블이 된다. 가상 사설 게이트웨이 같은 대상을 붙이면 그쪽 학습 경로가 전파(Propagation)되어 자동으로 채워진다.

#5한 줄 요약

목적지 CIDR별 다음 경로 규칙을 담은 라우트 테이블을 서브넷·게이트웨이에 연결해 VPC 안팎의 트래픽 방향을 정하는 것

라우트 구성과 예제

라우트 테이블에 로컬·인터넷 게이트웨이·NAT·피어링 등 목적지와 대상을 짝지어 라우트를 구성하는 방법과 대표 예제.

#1문제 상황

목적지와 대상이라는 두 칸만 있는 라우트 테이블은, 그 두 칸에 무엇을 넣느냐에 따라 서브넷의 성격이 완전히 달라진다. 인터넷 게이트웨이를 대상으로 넣으면 공인 통신이 열리고, NAT 장치를 넣으면 나가는 트래픽만 열린다. 어떤 대상을 넣을 수 있는지 모르면 서브넷을 의도한 대로 구성할 수 없다.

서브넷을 공용으로 만들려면 인터넷 게이트웨이로 가는 라우트를 추가해야 하는데, 이 한 줄을 빠뜨리면 인스턴스에 공인 IP가 있어도 인터넷에 닿지 못한다. 반대로 프라이빗 서브넷에서 NAT나 VPC 피어링, 게이트웨이 엔드포인트로 향하는 경로를 넣지 않으면 외부나 다른 VPC의 자원에 접근할 길이 없다.

#2핵심 질문

서브넷의 용도에 맞춰 어떤 목적지와 대상을 라우트로 짝지어야 원하는 통신이 열리는가?

#3동작 예시

서브넷을 공용으로 만들려면 그 서브넷 라우트 테이블에 0.0.0.0/0 → 인터넷 게이트웨이 라우트를 추가한다. 그러면 인스턴스가 공인 IPv4 주소를 가질 때 인터넷과 주고받을 수 있다. 프라이빗 서브넷은 같은 0.0.0.0/0을 NAT 장치로 보내 아웃바운드만 허용한다.

#4동작 과정

  1. 대상 종류 고르기인터넷 게이트웨이(공용 양방향), NAT 장치(아웃바운드 전용), 가상 사설 게이트웨이(온프레미스 VPN·Direct Connect), VPC 피어링 연결(다른 VPC), 게이트웨이 VPC 엔드포인트(S3·DynamoDB), 이그레스 전용 인터넷 게이트웨이(IPv6 아웃바운드), 전송 게이트웨이, 미들박스 어플라이언스, 프리픽스 리스트(IP 범위 묶음), Gateway Load Balancer 엔드포인트 중에서 목적에 맞는 대상을 정한다.
  2. 라우트 추가·교체라우트 테이블을 만들어 목적지 CIDR과 대상을 지정해 라우트를 넣는다. 메인 라우트 테이블을 새 테이블로 교체하거나, 서브넷·게이트웨이에 라우트 테이블을 연결해 적용 범위를 정한다.
  3. 확인과 문제 해결원하는 대상으로 트래픽이 도달하는지 점검하고, 닿지 않으면 목적지·대상 짝이나 서브넷 연결이 맞는지 확인한다. local 라우트의 대상을 바꿨다면 복원 여부도 함께 살핀다.

라우트 서버로 동적 라우팅

BGP를 사용하는 라우트 서버를 만들어 VPC 라우트를 동적으로 학습·전파하게 하는 Amazon VPC Route Server 기반 동적 라우팅.

#1문제 상황

기본 VPC 라우팅은 사람이 라우트 테이블에 목적지와 대상을 직접 적어 넣는 정적 방식이다. 장애가 나서 트래픽 경로를 다른 대상으로 돌려야 할 때마다 관리자가 라우트를 손으로 고쳐야 하고, 여러 경로를 쓰는 구성에서는 반영이 늦어 그동안 통신이 끊긴다.

이 정적 방식은 서드파티 네트워크 장비나 온프레미스 라우터와의 연동에도 약하다. 외부 장비가 아는 경로 정보를 VPC 라우트 테이블에 자동으로 반영할 방법이 없어, 경로가 바뀔 때마다 양쪽을 사람이 맞춰 줘야 관리 부담이 커진다.

#2핵심 질문

VPC 안팎의 경로 변경을 사람이 손대지 않고 자동으로 반영해 장애에 견디게 하려면 어떻게 하는가?

#3동작 예시

VPC Route Server를 만들고 인터넷 게이트웨이 라우트 테이블에 연결한 뒤, 외부 라우터와 BGP 세션을 맺는다. 외부 라우터가 10.1.0.0/16 경로를 광고하면 그 경로가 대상 라우트 테이블에 자동으로 채워지고, 그 라우터가 죽으면 같은 경로가 빠지면서 다른 경로로 트래픽이 돌아간다.

#4동작 과정

  1. 라우트 서버 생성과 연결필요한 IAM 역할 권한을 설정하고 라우트 서버를 만든 뒤 VPC에 연결하고 라우트 서버 엔드포인트를 생성한다. 이 엔드포인트가 외부 장비와 BGP를 주고받는 접점이 된다.
  2. 전파 켜기라우트 서버 전파(Propagation)를 활성화해 어떤 라우트 테이블에 학습한 경로를 채울지 정한다. 서브넷에 연결되지 않은 VPC 라우트 테이블, 서브넷 라우트 테이블, 인터넷 게이트웨이 라우트 테이블을 지원한다.
  3. BGP 세션 수립라우트 서버 피어를 만들고 외부 장비에서 BGP 세션을 시작한다. 세션이 서면 외부 장비가 광고한 IPv4·IPv6 경로가 VPC 라우트 테이블에 동적으로 갱신되어 장애 시 자동 재라우팅된다.

#5한 줄 요약

BGP를 말하는 라우트 서버가 외부 장비의 경로를 VPC 라우트 테이블에 자동으로 채우고 걷어가 라우팅 장애 복구를 자동화하는 것

미들박스 라우팅과 트래픽 검사

방화벽·IDS 등 보안 어플라이언스(미들박스)를 거치도록 서브넷 간·외부 트래픽 경로를 재구성하고, 미들박스 라우팅 마법사로 트래픽을 검사하게 하는 구성.

#1문제 상황

기본 VPC 라우팅은 트래픽을 목적지로 곧장 보낸다. 그래서 서브넷 사이를 오가는 트래픽이나 외부로 나가는 트래픽이 방화벽·침입 탐지(IDS) 같은 보안 어플라이언스를 거치지 않고 목적지에 바로 도달한다.

이런 보안 장비(미들박스)를 중간에 끼워 넣으려면 경로를 여러 갈래로 다시 짜야 한다. 검사할 트래픽을 어플라이언스가 있는 서브넷으로 보내고, 검사를 마친 트래픽을 다시 원래 목적지로 넘기는 라우트를 손으로 만들어야 하는데, 이 과정에서 라우트를 조금만 잘못 짜면 트래픽이 어플라이언스에서 맴돌거나 사라진다.

#2핵심 질문

서브넷 사이·외부로 향하는 트래픽이 반드시 보안 어플라이언스를 거치도록 경로를 어떻게 재구성하는가?

#3동작 예시

서브넷 A에서 서브넷 B로 가는 트래픽을 검사하려면, 보안 어플라이언스가 있는 미들박스 서브넷을 중간에 둔다. 서브넷 A의 라우트는 목적지 B를 미들박스의 네트워크 인터페이스로 보내고, 미들박스의 라우트는 검사를 마친 트래픽을 B로 넘긴다. 검사하지 않을 트래픽은 곧장 B로 보낸다.

#4동작 과정

  1. 마법사 실행VPC 콘솔의 미들박스 라우팅 마법사를 열고, 어플라이언스로 보낼 트래픽의 출발과 도착을 정한다. 사전 요구 사항을 확인한 뒤 필요한 라우트 테이블과 라우트(hop)를 자동으로 만들도록 지정한다.
  2. 경로 자동 구성마법사가 검사 대상 트래픽을 미들박스 어플라이언스나 Gateway Load Balancer로 우회시키는 라우트 테이블과 라우트를 만든다. 검사 후 원래 목적지로 되돌리는 라우트도 함께 구성된다.
  3. 결과 확인구성이 끝나면 각 서브넷의 라우트 테이블을 확인해 트래픽이 어플라이언스를 거쳐 목적지에 도달하는지 점검한다. 단일 네트워크 인터페이스로 라우팅하는 경우와 서브넷 간 검사 시나리오별 동작이 의도대로인지 살핀다.

#5한 줄 요약

보안 어플라이언스를 경유하도록 서브넷 트래픽의 라우트를 재구성해 VPC 안팎의 통신을 검사하게 하는 것

서브넷 공유와 영역 확장

AWS RAM으로 서브넷을 다른 계정과 공유하고, Local Zones·Wavelength·Outposts 같은 다른 영역(Zone)으로 VPC를 확장하는 것.

#1문제 상황

여러 계정이 각자 VPC를 만들면, 계정 사이 통신마다 피어링이나 전송 게이트웨이를 따로 연결해야 한다. 계정이 늘수록 연결이 계속 늘어나 관리가 복잡해지고, 통신 경로도 계정마다 제각각이 되어 중앙에서 통제하기 어려워진다.

또 하나의 VPC는 원래 하나의 리전 안에 있는 가용 영역에만 서브넷을 둘 수 있다. 그래서 사용자와 가까운 Local Zones, 통신 지연이 중요한 Wavelength, 온프레미스에 두는 Outposts 같은 다른 영역으로 워크로드를 옮기려면 별도 구성이 필요했다.

#2핵심 질문

중앙에서 관리하는 하나의 VPC를 여러 계정과 여러 영역으로 어떻게 넓혀 쓸 수 있는가?

#3동작 예시

VPC 소유자가 서브넷 하나를 AWS Organizations의 같은 조직에 속한 다른 계정과 공유한다. 참여 계정은 그 서브넷에 EC2 인스턴스나 RDS 데이터베이스를 직접 만들 수 있고, 두 계정의 자원은 VPC 내부 라우팅을 그대로 이용해 서로 통신한다. 소유자와 다른 참여자의 자원은 참여 계정이 보거나 고칠 수 없다.

#4동작 과정

  1. 서브넷 공유VPC 소유자가 AWS RAM(Resource Access Manager)으로 서브넷을 같은 조직의 다른 계정에 공유한다. 공유 전에 소유자와 참여자에게 필요한 권한·요건이 갖춰졌는지 확인한다.
  2. 참여 계정의 자원 배치공유받은 참여 계정은 그 서브넷에 EC2·RDS·Redshift·Lambda 같은 자원을 만들고 수정·삭제한다. 자기 자원에는 접근하되 다른 참여자나 소유자의 자원에는 손대지 못하며, 요금과 사용량은 소유자·참여자별로 구분해 청구된다.
  3. 영역 확장같은 VPC를 Local Zones·Wavelength·Outposts 같은 다른 영역에도 넓힌다. 각 영역에 서브넷을 만들어 워크로드를 사용자·온프레미스 가까이에 두고, VPC 라우팅을 그대로 활용한다.

#5한 줄 요약

하나의 VPC 서브넷을 여러 계정과 다른 영역으로 공유·확장해 VPC 내부 라우팅을 여러 곳에서 함께 쓰게 하는 것

DHCP 옵션 세트와 DNS 속성

VPC에 연결하는 DHCP 옵션 세트로 도메인·DNS·NTP 같은 네트워크 구성을 인스턴스에 전달하고, VPC의 DNS 확인·DNS 호스트 이름 속성을 설정하는 것.

#1문제 상황

TCP/IP 네트워크의 모든 장치는 통신하려면 IP 주소가 필요하다. 예전에는 관리자가 장치마다 IP 주소를 손으로 지정했지만, 장치가 늘면 하나하나 관리하기 어렵고 주소가 겹치는 실수도 생긴다.

IP 주소를 자동으로 나눠 주더라도, 장치가 어느 DNS 서버를 쓸지, 어떤 도메인에 속할지, 시간을 어디서 맞출지는 별도로 알려 줘야 한다. VPC 안의 인스턴스가 이런 네트워크 구성 정보를 매번 사람이 넣어 주지 않고 스스로 받아 쓰게 하려면 설정을 한곳에 모아 전달할 방법이 필요하다.

#2핵심 질문

VPC 안 장치들이 IP 주소와 DNS·도메인·NTP 같은 네트워크 구성을 자동으로 받아 쓰게 하려면 무엇을 설정하는가?

#3동작 예시

VPC에 DHCP 옵션 세트를 연결하고 그 안에 DNS 서버 주소와 도메인 이름을 넣는다. 그러면 EC2 인스턴스가 부팅할 때 Amazon DHCP 서버에 요청을 보내 IP 주소 임대와 함께 그 DNS 서버 주소·도메인 정보를 받아 간다. 관리자가 인스턴스마다 DNS 주소를 직접 입력할 필요가 없다.

#4동작 과정

  1. 옵션 세트 만들기DHCP 옵션 세트에 VPC 장치들이 쓸 DNS 서버, 도메인 이름, NTP 서버 같은 값을 담는다. 이 세트가 VPC의 네트워크 구성을 한곳에서 정하는 단위가 된다.
  2. VPC에 연결하기만든 DHCP 옵션 세트를 VPC에 연결해, VPC 안 장치가 요청할 때 이 값을 받도록 한다. 장치는 Amazon DHCP 서버와 통신해 IP 주소 임대와 구성 정보를 가져온다.
  3. DNS 속성 설정하기VPC의 DNS 확인(DNS resolution)과 DNS 호스트 이름(DNS hostnames) 속성을 켜거나 끈다. 인스턴스에 부여된 DNS 호스트 이름을 확인하고, 필요하면 VPC의 DNS 속성을 조회·갱신한다.

#5한 줄 요약

VPC에 연결한 DHCP 옵션 세트와 DNS 속성으로 인스턴스가 IP·DNS·도메인·NTP 구성을 자동으로 받게 하는 것

인터넷 게이트웨이와 이그레스 전용 게이트웨이

VPC의 서브넷이 인터넷과 통신하도록 VPC에 연결하는 게이트웨이로, 양방향 통신을 허용하는 인터넷 게이트웨이와 아웃바운드만 허용하는 이그레스 전용 인터넷 게이트웨이가 있다.

#1문제 상황

VPC는 기본적으로 격리된 사설 네트워크라, VPC 안의 인스턴스는 인터넷과 아무 통신도 하지 못한다. 공인 IP를 가진 인스턴스라도 VPC와 인터넷 사이를 이어 주는 통로가 없으면 외부에 닿지 못하고, 외부에서도 그 인스턴스로 접속할 수 없다.

그렇다고 모든 서브넷에 양방향 인터넷 통로를 열면, 인터넷에서 프라이빗 서브넷의 자원으로 들어오는 연결까지 허용되어 보안이 약해진다. 나가는 통신은 필요하지만 외부에서 들어오는 연결은 막아야 하는 서브넷에는 양방향 통로와 다른 성격의 출구가 필요하다.

#2핵심 질문

서브넷에 인터넷 통신을 열되, 양방향으로 열 서브넷과 나가는 방향만 열 서브넷을 어떻게 나누는가?

#3동작 예시

서브넷 라우트 테이블에 인터넷 게이트웨이를 향하는 라우트를 넣으면 그 서브넷이 공용 서브넷이 되어, 공인 IPv4 주소나 IPv6 주소를 가진 인스턴스가 인터넷과 양방향으로 통신한다. 나가는 통신만 필요하면 이그레스 전용 인터넷 게이트웨이를 향하는 라우트를 넣어, VPC 안 자원은 인터넷으로 나갈 수 있지만 인터넷에서 안으로 들어오지는 못한다.

#4동작 과정

  1. 게이트웨이 생성·연결인터넷 게이트웨이를 만들어 VPC에 연결한다. 이 게이트웨이는 수평 확장되고 중복 구성이라 가용성 위험이나 대역폭 제약을 만들지 않으며, IPv4와 IPv6 트래픽을 모두 다룬다.
  2. 라우트 지정서브넷 라우트 테이블에 인터넷 게이트웨이로 향하는 라우트를 추가하면 그 서브넷이 공용이 되고, 인터넷을 향하는 트래픽의 대상이 된다. IPv4 통신에서는 게이트웨이가 네트워크 주소 변환도 수행한다.
  3. 이그레스 전용 추가외부에서 들어오는 연결은 막고 나가는 통신만 열려면 이그레스 전용 인터넷 게이트웨이를 만들어 서브넷에 아웃바운드 인터넷 접근을 추가한다. 더 이상 필요 없는 게이트웨이는 삭제한다.

#5한 줄 요약

서브넷 라우트에 인터넷 게이트웨이 또는 이그레스 전용 인터넷 게이트웨이를 지정해 양방향·아웃바운드 전용 인터넷 통신을 여는 것

NAT 게이트웨이

프라이빗 서브넷의 인스턴스가 인터넷으로 나가는 트래픽을 대신 처리해 주어, 외부에서의 인바운드 연결은 막으면서 아웃바운드 연결만 가능하게 하는 관리형 게이트웨이다.

#1문제 상황

프라이빗 서브넷의 인스턴스는 인터넷 게이트웨이로 향하는 경로가 없어 외부 서비스와 통신할 수 없다. 하지만 소프트웨어 업데이트나 외부 API 호출처럼 나가는 통신은 필요하고, 동시에 외부에서 그 인스턴스로 먼저 접속을 걸어오는 것은 막아야 한다.

이때 인스턴스마다 공인 IP를 직접 붙이면 외부에서 곧바로 인바운드 연결이 들어올 수 있고, 프라이빗 서브넷이라는 격리 목적 자체가 무너진다. 그래서 나가는 트래픽만 대신 처리해 줄 별도의 관리형 구성 요소가 필요하다.

#2핵심 질문

프라이빗 서브넷의 인스턴스가 외부로는 나갈 수 있게 하면서, 외부에서 들어오는 연결은 어떻게 막을 수 있을까?

#3동작 예시

프라이빗 서브넷의 EC2 인스턴스가 외부 패키지 저장소에 접속한다고 하자. 이 인스턴스의 라우팅 테이블은 인터넷 대신 NAT 게이트웨이를 목적지로 지정한다. 인스턴스가 보낸 패킷의 출발지 주소는 NAT 게이트웨이에 연결된 주소로 바뀌어 나가고, 응답이 돌아오면 NAT 게이트웨이가 다시 원래 인스턴스 주소로 되돌려 전달한다.

#4동작 과정

  1. NAT 게이트웨이 생성퍼블릭 서브넷에 만들고 Elastic IP 주소를 연결한다. 이때 연결 유형을 퍼블릭(기본)으로 두면 외부 인터넷, 프라이빗으로 두면 다른 VPC나 온프레미스 네트워크로 통신한다.
  2. 라우팅 지정프라이빗 서브넷의 라우팅 테이블에 외부로 가는 트래픽의 목적지를 NAT 게이트웨이로 지정한다. 그러면 인스턴스는 공인 IP 없이도 NAT 게이트웨이를 거쳐 나가게 된다.
  3. 주소 변환과 응답 반환NAT 게이트웨이가 출발지 주소를 자신의 주소로 바꿔 내보내고, 돌아온 응답을 원래 인스턴스 주소로 되돌린다. 외부에서 먼저 시작한 연결은 허용되지 않는다.

#5한 줄 요약

프라이빗 서브넷의 아웃바운드 트래픽만 대신 처리해 외부 통신은 열고 인바운드 연결은 닫아 두는 관리형 주소 변환 게이트웨이

NAT 모니터링·문제 해결과 NAT 인스턴스

NAT 게이트웨이의 상태를 CloudWatch 지표로 감시하고 문제를 진단하는 방법과, EC2 인스턴스에 NAT 기능을 직접 구성하는 NAT 인스턴스를 다룬다.

#1문제 상황

NAT 게이트웨이를 배치한 뒤에는 트래픽이 실제로 처리되는지, 용량이 부족하지 않은지 확인할 방법이 필요하다. 상태를 보지 않으면 연결 실패가 생겨도 원인을 알 수 없고, 어느 지점에서 막히는지도 찾기 어렵다.

또한 관리형 NAT 게이트웨이 대신 EC2 인스턴스에 NAT 기능을 직접 구성하는 선택지도 있다. 이 경우 세부 설정을 직접 제어할 수 있지만, 그만큼 상태 감시와 장애 대응도 사용자가 책임져야 한다.

#2핵심 질문

NAT 트래픽의 상태를 어떻게 감시하고, 관리형 NAT 게이트웨이 대신 직접 만든 NAT 구성은 언제 쓰는가?

#3동작 예시

NAT 게이트웨이의 CloudWatch 지표를 보면 처리한 바이트 수와 연결 수 같은 값이 시간대별로 기록된다. 평소보다 연결 수가 크게 치솟는 구간이 보이면, 그 지표에 임계값을 걸어 알람을 만들 수 있다. 알람이 울리면 어떤 시점에 트래픽이 늘었는지 지표를 되짚어 원인을 좁힌다.

#4동작 과정

  1. 지표 수집NAT 게이트웨이가 처리한 트래픽과 연결 관련 값이 CloudWatch 지표와 차원(dimension, 지표를 특정 대상에 묶는 식별자)으로 전달된다.
  2. 지표 확인과 알람 설정콘솔에서 NAT 게이트웨이 지표를 조회해 추세를 보고, 임계값을 넘으면 통보되도록 CloudWatch 알람을 만든다.
  3. 대안 구성 검토관리형 NAT 게이트웨이 대신 EC2 인스턴스에 NAT 기능을 구성한 NAT 인스턴스를 쓰는 경우, 두 방식의 차이를 비교해 필요한 쪽을 고르고 문제 발생 시 지표와 구성을 대조해 진단한다.

탄력적 IP 주소

인스턴스나 NAT 게이트웨이 같은 리소스에 고정적으로 연결해 두고 필요할 때 다시 매핑해 재사용할 수 있는 퍼블릭 IPv4 주소다.

#1문제 상황

인스턴스를 중지했다가 다시 시작하거나 교체하면, 자동으로 붙어 있던 공인 IPv4 주소가 바뀔 수 있다. 외부에서 그 주소로 접속하도록 설정해 둔 곳이 있다면, 주소가 바뀌는 순간 연결이 끊기고 설정을 다시 맞춰야 한다.

고정된 공인 주소가 없으면 장애로 인스턴스를 교체할 때마다 대외 엔드포인트가 달라져, 서비스가 유지되는 듯 보여도 실제 접속 지점은 계속 흔들린다. 이 흔들림을 없애 줄 고정 공인 IPv4 주소가 필요하다.

#2핵심 질문

인스턴스가 바뀌어도 외부에 노출되는 공인 IPv4 주소를 그대로 유지하려면 어떻게 해야 할까?

#3동작 예시

어떤 인스턴스에 탄력적 IP 주소를 연결해 두고 외부에 이 주소를 안내한다고 하자. 그 인스턴스에 장애가 나서 다른 인스턴스로 교체해야 할 때, 같은 탄력적 IP 주소를 새 인스턴스에 다시 연결한다. 외부에서 보는 주소는 그대로이므로 접속 지점이 바뀌지 않는다.

#4동작 과정

  1. 주소 확보계정의 탄력적 IP 주소를 할당받는다. 이 주소는 계정에 남아 있어 필요할 때 다시 쓸 수 있는 고정된 퍼블릭 IPv4 주소다.
  2. 리소스에 연결원하는 인스턴스나 네트워크 인터페이스에 이 주소를 연결한다. 연결 대상은 같은 계정의 VPC 안 리소스면 된다.
  3. 다시 매핑인스턴스에 장애가 나거나 교체가 필요하면 같은 주소를 다른 인스턴스로 옮겨 연결한다. 주소를 유지한 채 대상만 바뀌므로 외부 엔드포인트가 일관되게 남는다.

#5한 줄 요약

보안 그룹

인스턴스(ENI) 수준에서 허용 규칙만으로 인바운드·아웃바운드 트래픽을 제어하는 상태 기반 가상 방화벽.

#1문제 상황

VPC 안의 인스턴스는 기본적으로 여러 방향의 트래픽에 노출될 수 있다. 어떤 트래픽을 통과시키고 어떤 트래픽을 막을지 정해 두지 않으면, 필요 없는 포트와 출발지에서 들어오는 연결까지 그대로 도달한다.

VPC를 만들면 기본 보안 그룹 하나가 함께 생기지만, 여기에 규칙을 제대로 채우지 않으면 인스턴스별로 필요한 통신을 세밀하게 나눌 수 없다. 리소스마다 허용 범위를 따로 정의할 수 있는 제어 수단이 필요하다.

#2핵심 질문

인스턴스에 도달하고 인스턴스에서 나가는 트래픽을, 허용한 것만 통과하도록 어떻게 제어할까?

#3동작 예시

EC2 인스턴스에 보안 그룹을 하나 연결하고, 인바운드 규칙으로 특정 출발지와 포트 범위, 프로토콜만 허용한다고 하자. 그러면 그 조건에 맞는 트래픽만 인스턴스에 도달하고, 조건 밖의 트래픽은 버려진다. 아웃바운드 규칙도 같은 방식으로 목적지와 포트, 프로토콜을 지정한다.

#4동작 과정

  1. 보안 그룹 생성VPC에 보안 그룹을 만든다. VPC를 만들 때 함께 생기는 기본 보안 그룹과는 별개로, 목적에 맞는 그룹을 추가할 수 있다.
  2. 규칙 정의인바운드 규칙에는 출발지·포트 범위·프로토콜을, 아웃바운드 규칙에는 목적지·포트 범위·프로토콜을 지정한다. 이 규칙들로 허용할 트래픽을 정한다.
  3. 리소스에 연결보안 그룹을 인스턴스 같은 리소스에 연결한다. 그러면 그 리소스가 주고받는 트래픽 중 규칙에 맞는 것만 통과한다.

네트워크 ACL

서브넷 수준에서 허용·거부 규칙을 번호 순서대로 평가해 트래픽을 제어하는 상태 비저장 필터.

→ 04-01 참조

#1문제 상황

보안 그룹은 인스턴스 단위로 트래픽을 제어하므로, 서브넷 전체에 대해 특정 트래픽을 통째로 막거나 허용하는 규칙을 걸기 어렵다. 서브넷 경계에서 여러 인스턴스에 공통으로 적용할 필터가 따로 필요하다.

또한 규칙을 거부 기준으로 걸고 싶을 때, 허용만 정의하는 방식만으로는 서브넷 단위의 차단을 표현하기 어렵다. 서브넷에 들어오고 나가는 트래픽을 번호 순서로 평가해 허용과 거부를 함께 다루는 계층이 필요하다.

#2핵심 질문

서브넷 경계에서 들어오고 나가는 트래픽을, 허용과 거부 규칙을 순서대로 평가해 어떻게 제어할까?

#3동작 예시

VPC에 서브넷 두 개가 있고 각 서브넷에 네트워크 ACL이 하나씩 연결되어 있다고 하자. 어떤 트래픽이 VPC로 들어오면 라우터가 목적지 서브넷으로 보내고, 그 서브넷의 ACL이 규칙을 번호 순으로 보며 이 트래픽을 통과시킬지 막을지 정한다. 나가는 트래픽도 같은 ACL이 판단한다.

#4동작 과정

  1. ACL 준비기본 네트워크 ACL을 그대로 쓰거나, 보안 그룹 규칙과 비슷한 형태의 사용자 지정 ACL을 새로 만든다. 사용자 지정 ACL은 VPC에 보안 계층을 하나 더 얹는다.
  2. 규칙 작성과 평가인바운드·아웃바운드 규칙에 허용 또는 거부를 적고 번호를 매긴다. 트래픽이 오면 낮은 번호부터 차례로 맞춰 보며 처음 일치하는 규칙의 판단을 따른다.
  3. 서브넷에 연결만든 ACL을 대상 서브넷에 연결한다. 그러면 그 서브넷으로 들어오고 나가는 트래픽이 ACL 규칙에 따라 허용되거나 거부된다.

트래픽 프라이버시와 전송 중 암호화

VPC 내부 트래픽의 사적 처리와 전송 중 암호화를 강제하는 설정과 개념.

#1문제 상황

VPC 안에서 오가는 트래픽이 항상 암호화된다는 보장은 없다. 어떤 리소스 사이의 통신은 평문으로 흐를 수 있고, 이 상태를 파악하지 않으면 암호화가 빠진 구간을 놓치기 쉽다.

규정 준수를 위해서는 어느 트래픽이 암호화되고 어느 트래픽이 평문인지 확인하고, 나아가 전송 중 암호화를 강제할 수단이 필요하다. 구간별로 흩어진 설정을 사람이 일일이 점검하는 방식으로는 일관성을 지키기 어렵다.

#2핵심 질문

VPC 안팎을 오가는 트래픽의 암호화 여부를 어떻게 확인하고, 전송 중 암호화를 어떻게 강제할까?

#3동작 예시

VPC Encryption Controls를 켜면 트래픽 흐름의 암호화 상태를 한곳에서 감시할 수 있다. 평문으로 통신을 허용하는 리소스가 있으면 그것을 식별해 알려 준다. 이를 바탕으로 전송 중 암호화를 강제하는 방향으로 설정을 조정한다.

#4동작 과정

  1. 상태 감시VPC Encryption Controls가 리전 안의 트래픽 흐름 암호화 상태를 모아 보여 준다. 이를 통해 어느 구간이 평문인지 드러난다.
  2. 평문 리소스 식별평문 통신을 허용하고 있는 리소스를 찾아낸다. 무엇을 손봐야 하는지 대상이 분명해진다.
  3. 암호화 강제애플리케이션 계층 암호화와 Nitro 시스템 하드웨어의 내장 전송 암호화를 함께 활용해 전송 중 암호화를 강제한다. 이 기능은 Nitro 인스턴스를 넘어 Fargate, Application Load Balancer, Transit Gateway 등 다른 AWS 서비스로도 확장된다.

IAM 정책으로 VPC 리소스의 생성·수정·삭제 권한을 부여하고 제한하는 접근 제어 방식.

#1문제 상황

반대로 권한을 세밀하게 나누지 않으면, 어떤 사용자는 조회만 하면 되는 상황에서도 리소스를 바꿀 수 있게 된다. 누가 어떤 VPC 작업을 할 수 있는지 명확히 정하는 접근 제어 체계가 필요하다.

#2핵심 질문

VPC 리소스의 생성·수정·삭제 권한을 누구에게 어떤 범위로 부여하고 제한할 수 있을까?

#3동작 예시

관리자가 IAM 정책을 작성해 어떤 사용자에게는 VPC 리소스를 조회하는 권한만 주고, 다른 사용자에게는 특정 리소스를 만들고 바꾸는 권한을 부여한다고 하자. 이 사용자가 VPC 작업을 요청하면, IAM이 그 사용자의 정책과 요청 내용을 맞춰 보고 허용 여부를 판단한다.

#4동작 과정

  1. 주체 확인IAM이 요청을 보낸 사용자나 역할이 누구인지 인증한다. 이 단계에서 요청자가 어떤 신원인지가 정해진다.
  2. 정책으로 권한 판단그 신원에 붙은 정책과 요청한 VPC 작업을 대조해 허용할지 결정한다. 정책에 없는 작업은 허용되지 않는다.
  3. 권한 범위 관리AWS 관리형 정책이나 서비스 연결 역할(서비스가 다른 서비스에서 동작하도록 미리 정의된 역할)을 활용해 권한을 부여하고, 문제가 생기면 정책과 요청을 대조해 원인을 찾는다.

VPC 퍼블릭 액세스 차단(BPA)

VPC와 서브넷에 퍼블릭 IP나 인터넷 게이트웨이 경로 등 퍼블릭 액세스가 생기지 않도록 계정·조직 차원에서 차단하는 기능.

#1문제 상황

AWS 계정에는 여러 VPC와 서브넷이 있고, 각 리소스마다 퍼블릭 IP를 붙이거나 인터넷 게이트웨이로 가는 라우트를 추가할 수 있다. 담당자가 서브넷 하나에 실수로 인터넷 게이트웨이 경로를 넣거나 인스턴스에 퍼블릭 IP를 할당하면, 그 리소스는 의도치 않게 인터넷에서 접근 가능해진다. 계정이 커질수록 수십 개 서브넷의 설정을 사람이 하나하나 확인하는 방식으로는 이런 노출을 막기 어렵다.

#2핵심 질문

계정과 조직 전체에서 퍼블릭 액세스가 새로 생기는 것을 사후 점검이 아니라 원천적으로 막을 수는 없을까?

#3동작 예시

한 서브넷에 인터넷 게이트웨이로 향하는 라우트를 추가하려 한다. 이때 VPC BPA가 Bidirectional 모드로 켜져 있고 그 서브넷이 제외 목록에 없으면, 라우트를 추가해도 트래픽이 실제로 인터넷 게이트웨이를 통과하지 못한다. 설정은 존재하지만 통신은 차단되는 식이다.

#4동작 과정

  1. 모드 선택Bidirectional은 인터넷 게이트웨이와 egress-only 인터넷 게이트웨이로 드나드는 모든 트래픽을, Ingress-only는 VPC로 들어오는 인터넷 트래픽을 막는다.
  2. 예외 지정차단하지 않을 트래픽이 있으면 VPC나 서브넷 단위로 exclusion을 적용해 그 대상을 차단에서 제외한다.
  3. 적용과 감사계정·조직 차원에서 차단이 적용되고, 어떤 영향이 생기는지 미리 평가하고 모니터링해 예외와 감사 기록을 관리한다.

VPC를 구성할 때 기본값만 따르면 서브넷을 단일 가용 영역에 몰아 넣거나, 보안 그룹과 네트워크 ACL 규칙을 느슨하게 열어 두기 쉽다. 이런 구성은 한 가용 영역에 장애가 나면 서비스 전체가 멈추고, 열어 둔 포트로 불필요한 트래픽이 들어오는 문제로 이어진다. 개별 설정은 각각 동작해도 전체가 안전하고 견고한지 판단할 기준이 없다.

#2핵심 질문

VPC를 안전하고 장애에 강하게 만들기 위해 어떤 원칙을 기본으로 삼아야 할까?

#3동작 예시

프로덕션 애플리케이션 서브넷을 만들 때 같은 VPC 안의 서로 다른 가용 영역에 서브넷을 두 개 이상 만든다. 각 가용 영역은 전원·네트워크·연결이 이중화된 별도 데이터 센터이므로, 하나에 장애가 나도 다른 쪽 서브넷의 인스턴스가 트래픽을 계속 처리한다.

#4동작 과정

  1. 다중 AZ 배치애플리케이션 서브넷을 여러 가용 영역에 만들어 한 영역 장애에도 서비스가 유지되게 한다.
  2. 계층별 트래픽 제어보안 그룹으로 서브넷 안 인스턴스로 가는 트래픽을, 네트워크 ACL로 서브넷 경계의 인바운드·아웃바운드 트래픽을 제어한다.
  3. 접근 관리와 검증IAM으로 VPC 안 AWS 리소스 접근을 관리하고, 규정 준수 검증과 인프라 보안·복원력 지침에 따라 구성을 점검한다.

VPC Flow Logs 기본

VPC 내 네트워크 인터페이스를 오가는 IP 트래픽의 메타데이터(허용/거부, 출발지·목적지, 포트, 바이트 수 등)를 수집해 기록하는 모니터링 기능으로, 패킷 내용이 아니라 흐름 정보를 남긴다.

#1문제 상황

인스턴스에 트래픽이 예상대로 오가지 않을 때, 어느 규칙이 막고 있는지, 어디서 어디로 얼마나 오갔는지 알 방법이 없다. 보안 그룹 규칙을 하나씩 바꿔 보며 추측하거나 인스턴스에 직접 접속해 확인해야 한다. 이런 방식은 이미 지나간 트래픽을 되짚기 어렵고, 규칙이 지나치게 제한적인지 판단할 근거도 남지 않는다.

#2핵심 질문

VPC 안 네트워크 인터페이스를 오가는 트래픽을 나중에 확인하고 분석할 수 있게 기록으로 남길 수는 없을까?

#3동작 예시

프라이빗 서브넷의 EC2 인스턴스에 대한 네트워크 인터페이스 하나를 대상으로, 허용된 트래픽만 캡처하는 흐름 로그를 만든다. 이 로그가 남긴 레코드를 S3 버킷으로 게시하면, 그 인터페이스를 오간 트래픽의 출발지·목적지·포트·허용 여부를 나중에 조회할 수 있다.

#4동작 과정

  1. 대상 지정VPC, 서브넷, 네트워크 인터페이스 중 하나를 골라 흐름 로그를 만든다. 서브넷이나 VPC를 고르면 그 안의 모든 네트워크 인터페이스가 감시된다.
  2. 캡처 범위 선택허용된 트래픽, 거부된 트래픽, 전체 트래픽 중 무엇을 기록할지 정한다.
  3. 레코드 게시감시 대상 인터페이스의 흐름이 레코드로 기록되고, 지정한 게시 대상으로 전달되어 조회·분석에 쓰인다.

Flow Logs 게시 대상

수집된 Flow Log 레코드를 CloudWatch Logs, Amazon S3, Amazon Data Firehose 중 어디로 전달할지 지정하는 게시 대상을 말한다.

#1문제 상황

흐름 로그는 데이터를 계속 만들어 내지만, 그것을 어디에 쌓아 두느냐에 따라 조회와 분석 방식이 달라진다. 목적지를 정하지 않으면 레코드가 전달되지 않고, 권한이 없으면 로그를 만들었는데도 데이터가 목적지에 도착하지 않는다. 각 목적지마다 필요한 설정과 권한이 달라 담당자가 헷갈리기 쉽다.

#2핵심 질문

수집한 흐름 로그 레코드를 어떤 목적지로 보내고, 그 전달에 필요한 권한은 어떻게 준비할까?

#3동작 예시

흐름 로그 하나를 만들어 레코드를 CloudWatch Logs의 로그 그룹으로 보내면, 콘솔에서 로그 스트림을 열어 레코드를 바로 확인할 수 있다. 같은 레코드를 S3 버킷으로 보내면 여러 개의 로그 파일로 쌓여 장기 보관과 대량 분석에 쓰인다.

#4동작 과정

  1. 목적지 선택레코드를 보낼 곳을 CloudWatch Logs, Amazon S3, Amazon Data Firehose 중에서 고른다. 이 전달 경로와 권한 구성을 subscription이라고 부른다.
  2. 권한 준비레코드를 목적지로 보내려면 게시를 허용하는 IAM 역할과, 목적지 쪽 버킷 정책·키 정책 같은 권한을 갖춘다.
  3. 게시와 조회흐름 로그를 만들면 지정한 로그 그룹, 버킷, 전달 스트림으로 레코드가 전달되고, 그곳에서 레코드를 꺼내 본다.

Flow Logs 분석과 권한

게시된 Flow Log 레코드를 Athena 같은 도구로 조회·분석하고, 게시에 필요한 IAM 역할과 권한을 구성하는 방법을 다룬다.

#1문제 상황

흐름 로그를 S3에 쌓아 두기만 하면, 어떤 리소스가 트래픽을 가장 많이 주고받는지, 거부된 연결이 많은 IP가 어디인지 바로 알기 어렵다. 로그 파일을 직접 내려받아 들여다보는 방식은 데이터가 늘수록 감당이 안 된다. 또 게시에 필요한 IAM 역할과 정책이 제대로 갖춰지지 않으면 로그가 목적지까지 전달되지 않는다.

#2핵심 질문

쌓인 흐름 로그를 SQL로 조회해 유의미한 정보를 뽑아내려면 어떻게 해야 하고, 그 게시 권한은 누가 어떻게 관리할까?

#3동작 예시

흐름 로그를 저장한 S3 버킷을 대상으로 Amazon Athena에서 표준 SQL 질의를 실행한다. 그러면 VPC 안에서 트래픽을 가장 많이 주고받는 리소스나 거부된 TCP 연결이 가장 많은 IP 주소를 골라낼 수 있다.

#4동작 과정

  1. 조회 환경 준비콘솔이나 AWS CLI로 CloudFormation 템플릿을 생성해, Athena 분석에 필요한 AWS 리소스와 미리 정의된 질의를 만든다.
  2. 질의 실행미리 정의된 질의를 돌리거나 직접 SQL을 작성해 S3에 쌓인 흐름 로그를 조회하고 인사이트를 얻는다.
  3. 권한 관리게시와 분석에 필요한 IAM 정책과 서비스 연결 역할, 관리형 정책을 구성하고 문제가 생기면 트러블슈팅한다.

#5한 줄 요약

S3에 쌓인 흐름 로그를 Athena 같은 도구로 SQL 조회해 인사이트를 얻고, 그 게시·분석 권한을 IAM으로 관리하게 하는 것

#2핵심 질문

VPC의 상태와 사용량을 지표로 지켜보고, 한도 도달 전에 대비하려면 무엇을 봐야 할까?

#3동작 예시

#4동작 과정

  1. 지표 수집Amazon VPC가 VPC에 관한 데이터를 CloudWatch로 게시하고, 이를 시간에 따른 값의 집합인 지표로 조회한다.
  2. 모니터링 설정NAU 모니터링을 켜거나 끄고, NAU 지표와 차원을 확인해 필요하면 CloudWatch 알람을 건다.
  3. 사용·비용 확인청구 및 사용 보고서로 VPC 사용량과 비용을 확인하고, VPC 네트워크 구성을 파악한다.

Reachability Analyzer

원본과 대상 리소스 사이의 네트워크 경로를 구성·구성 정보 기반으로 정적 분석해 두 리소스가 실제로 통신 가능한지 도달 가능성을 진단하는 도구다.

#1문제 상황

두 리소스가 통신이 안 될 때, 원인이 보안 그룹인지 네트워크 ACL인지 라우트 테이블인지 서브넷 설정인지 한눈에 알기 어렵다. 실제로 패킷을 보내 보며 어느 구간에서 막히는지 하나씩 확인하는 방식은 시간이 오래 걸리고, 설정이 여러 겹 얽혀 있으면 놓치기 쉽다.

#2핵심 질문

패킷을 실제로 보내지 않고도 두 리소스 사이가 도달 가능한지, 막힌다면 어느 구성 요소가 막는지 알 수 없을까?

#3동작 예시

VPC 안의 인스턴스와 인터넷 게이트웨이 사이의 도달 가능성을 분석한다. 도달 가능하면 두 지점 사이의 가상 경로를 구간별로 보여 주고, 도달 불가능하면 경로를 막고 있는 구성 요소가 무엇인지 짚어 준다.

#4동작 과정

  1. 경로 분석원본과 대상 리소스 사이의 네트워크 경로를 설정 정보만으로 정적으로 분석한다. 실제 패킷을 보내지 않는다.
  2. 결과 확인도달 가능하면 두 리소스 사이 가상 경로를 구간별로 보여 주고, 불가능하면 막고 있는 구성 요소를 식별한다.
  3. 대상 확장인스턴스, 인터넷 게이트웨이, 네트워크 인터페이스, 트랜짓 게이트웨이와 그 연결, VPC 엔드포인트와 서비스, VPC 피어링 연결, VPN 게이트웨이 등 여러 리소스 사이를 분석한다.

#5한 줄 요약

실제 트래픽 없이 구성 정보만으로 두 리소스 사이 도달 가능성을 정적으로 분석하고 막는 요소를 짚어 주는 진단 도구

Traffic Mirroring

지정한 필터 조건에 맞는 VPC 내 트래픽을 복사해 모니터링 어플라이언스나 대상으로 전달함으로써 실제 패킷을 검사·분석할 수 있게 하는 기능이다.

#1문제 상황

VPC 안에서 오가는 트래픽을 점검하려면 기존에는 각 인스턴스에 에이전트를 설치하거나 애플리케이션 로그를 남겨 확인하는 방식을 썼다. 그런데 이 방식은 애플리케이션 계층에서 이미 처리된 결과만 남기 때문에, 네트워크 계층에서 실제로 오간 패킷 자체를 들여다볼 수 없다.

침입 시도나 이상 트래픽을 잡아내려면 원본 패킷을 그대로 검사해야 하는데, 로그 기반 방식으로는 패킷 내용·헤더·프로토콜 수준의 단서를 얻기 어렵다. 게다가 전체 트래픽을 다 복사해 분석 장비로 보내면 비용과 부하가 커지고, 관심 없는 트래픽까지 섞여 분석 효율이 떨어진다.

#2핵심 질문

서비스를 멈추지 않고 VPC 안의 실제 패킷을 골라서 검사할 수는 없을까?

#3동작 예시

EC2 인스턴스의 ENI(탄력적 네트워크 인터페이스, 인스턴스에 붙는 가상 네트워크 카드)를 소스로 지정하고, 보안 점검용 인스턴스를 대상으로 지정한다. 필터에서 포트 443만 통과하도록 규칙을 걸면, 그 인스턴스로 오가는 HTTPS 트래픽만 복사되어 점검 인스턴스로 전달된다. 소스 인스턴스의 통신은 그대로 이어지고, 복사본만 별도로 분석된다.

#4동작 과정

  1. 세션 정의소스를 모니터링할 ENI(탄력적 네트워크 인터페이스, 인스턴스에 붙는 가상 네트워크 카드)로, 대상을 복사본을 받을 점검 장비로, 필터를 어떤 트래픽을 복사할지 정하는 규칙 집합으로 지정해 하나의 세션을 만든다. 이로써 "무엇을 어디로 보낼지"가 확정된다.
  2. 트래픽 복사와 필터링세션에 걸린 필터 규칙에 맞는 패킷만 골라 복사하고, 필요하면 패킷 앞부분만 잘라 용량을 줄인다. 관심 트래픽만 빠져나가 분석 대상이 좁혀진다.
  3. 대상으로 전달복사본을 개별 인스턴스나 NLB·GWLB(트래픽을 분산·중계하는 로드 밸런서) 뒤의 점검 장비 집합으로 보낸다. 원본 통신은 영향 없이 흐르고, 별도 경로에서 패킷 검사가 이루어진다.

#5한 줄 요약

원본 통신에 영향을 주지 않고 조건에 맞는 실제 패킷만 복사해 점검 장비로 보내는 것

VPC 피어링 — VPC 간 1:1 사설 연결06-01

VPC 피어링의 개념과 동작

두 VPC를 1:1로 사설 연결해 서로의 사설 IP로 통신하게 하는 AWS 네트워킹 기능

#1문제 상황

VPC는 계정 전용의 논리적으로 격리된 가상 네트워크라서, 서로 다른 VPC에 있는 인스턴스끼리는 기본적으로 통신할 수 없다. 같은 회사 계정 안의 두 VPC라도, 또는 다른 계정·다른 리전의 VPC라도 마찬가지로 서로 단절되어 있다.

이 둘을 연결하려고 인터넷 게이트웨이나 VPN을 거치게 하면 트래픽이 공용 경로나 별도 장비를 지나게 되어, 지연이 늘고 구성도 복잡해진다. 사설 IP로 단순하게 통신하고 싶어도 마땅한 1:1 연결 수단이 없는 것이 문제다.

#2핵심 질문

서로 격리된 두 VPC를 공용 인터넷이나 별도 장비 없이 사설 IP로 직접 통신하게 할 수는 없을까?

#3동작 예시

VPC A와 VPC B 사이에 피어링 연결을 하나 만들면, 두 VPC가 마치 하나의 네트워크 안에 있는 것처럼 사설 IPv4/IPv6 주소로 통신한다. 이 연결은 게이트웨이나 VPN이 아니라 AWS가 기존 VPC 인프라를 이용해 만든 논리적 연결이고, 단일 장애 지점이나 대역폭 병목이 없다.

#4동작 과정

  1. 연결 요청한쪽 VPC에서 다른 VPC로 피어링 연결을 요청한다. 이때 두 VPC는 같은 계정일 수도, 다른 계정일 수도 있고 서로 다른 리전에 있어도 된다. 이로써 두 VPC 사이에 사설 연결이 성립된다.
  2. 수락요청받은 쪽 VPC의 소유자가 연결을 수락하면 피어링 연결이 활성화된다. 이 시점에 두 VPC는 논리적으로 연결된 상태가 된다.
  3. 사설 IP 통신활성화된 연결을 통해 양쪽 인스턴스가 사설 IPv4 또는 IPv6 주소로 서로 통신한다. 게이트웨이·VPN·별도 물리 장비를 거치지 않아 단순하고 병목이 없다.

#5한 줄 요약

두 VPC를 1:1 사설 연결로 이어 서로의 사설 IP로 직접 통신하게 하는 것

VPC 피어링 — VPC 간 1:1 사설 연결06-02

피어링 연결 생성과 라우팅

피어링 연결을 요청·수락한 뒤 양쪽 VPC 라우팅 테이블에 상대 CIDR 경로를 추가해야 트래픽이 흐르는 절차

#1문제 상황

피어링 연결을 만들어 수락하기만 하면 바로 트래픽이 흐를 것 같지만, 실제로는 그렇지 않다. 각 VPC의 서브넷에 연결된 라우팅 테이블에 상대 VPC로 가는 경로가 없으면, 패킷은 어디로 보내야 할지 알지 못해 통신이 되지 않는다.

기본 라우팅 테이블에는 자기 VPC 대역(local) 경로만 있어서, 상대 VPC 대역으로 향하는 트래픽의 목적지를 지정해 주지 않는다. 연결은 존재하지만 경로가 없어 트래픽이 그 연결을 타지 못하는 상태가 문제다.

#2핵심 질문

피어링 연결을 만든 뒤 양쪽에 무엇을 추가해야 실제 트래픽이 흐르기 시작할까?

#3동작 예시

VPC A와 VPC B가 피어링으로 연결되어 있을 때, VPC A의 라우팅 테이블에 "목적지 = VPC B의 CIDR 대역, 대상 = 피어링 연결 ID(pcx-...)"인 경로를 넣는다. VPC B에는 반대로 "목적지 = VPC A의 CIDR 대역, 대상 = 같은 피어링 연결 ID" 경로를 넣는다. 양쪽에 이 경로가 있어야 비로소 인스턴스끼리 사설 IP로 통신한다.

#4동작 과정

  1. 연결 생성과 수락한쪽 VPC에서 피어링 연결을 요청하고 다른 쪽에서 수락한다. 이 단계까지는 두 VPC 사이에 연결만 존재하고 경로는 없는 상태다.
  2. 라우팅 테이블 갱신양쪽 VPC에서 상대 인스턴스가 있는 서브넷에 연결된 라우팅 테이블에, 목적지를 상대 VPC의 CIDR 블록(또는 그 일부)으로, 대상을 피어링 연결 ID로 하는 경로를 추가한다. 이로써 트래픽이 그 연결로 향할 길이 생긴다.
  3. 통신 시작양쪽에 경로가 갖춰지면 사설 IPv4 트래픽이 흐르기 시작한다. IPv6 CIDR 블록이 연결되어 있으면 IPv6 경로도 따로 추가해야 그 대역으로도 통신한다.

#5한 줄 요약

연결을 수락한 뒤 양쪽 라우팅 테이블에 상대 CIDR 경로를 넣어야 트래픽이 실제로 흐른다는 점

VPC 피어링 — VPC 간 1:1 사설 연결06-03

피어링 구성 패턴과 시나리오

전체 CIDR 또는 특정 주소로 라우팅하는 구성 방식과 계정·리전·조직을 넘나드는 피어링 시나리오

#1문제 상황

피어링 연결을 어디까지, 어떤 범위로 열어줄지 정하지 않으면 관리가 어려워진다. 상대 VPC의 모든 리소스와 통신하도록 넓게 열면 구성이 단순하지만, 그 VPC로 향하는 모든 트래픽이 피어링 연결을 지나게 되어 트래픽이 몰리면 병목이 될 수 있다.

반대로 필요한 곳만 골라 열려고 하면 규칙이 세밀해지는 대신 관리할 경로가 늘어난다. 어떤 트래픽을 연결을 통해 보낼지 목적에 맞게 나눠 설계해야 하는 것이 문제다.

#2핵심 질문

피어링 연결로 어떤 트래픽을 어느 범위까지 흘려보내야 효율과 통제를 함께 잡을 수 있을까?

#3동작 예시

전체 VPC를 여는 구성에서는 각 VPC의 라우팅 테이블에 상대 VPC 전체 대역으로 향하는 경로를 하나씩 넣는다. 이러면 어느 리소스든 상대 VPC의 어느 리소스와도 통신할 수 있어 관리가 단순하다. 반대로 특정 주소 구성에서는 상대 VPC 안의 특정 서브넷·리소스로만 향하는 세밀한 경로를 넣어, 꼭 필요한 트래픽만 연결을 지나게 한다.

#4동작 과정

  1. 전체 대역 경로 구성각 VPC 라우팅 테이블에 상대 VPC CIDR 전체를 향하는 경로를 넣어, 상대 VPC의 모든 리소스와 통신을 허용한다. 구성은 단순해지지만 트래픽이 많아지면 연결이 병목이 될 수 있다.
  2. 특정 주소 경로 구성상대 VPC의 특정 서브넷·리소스로만 향하는 더 세밀한 경로를 넣어, 연결을 지나는 트래픽을 필요한 만큼으로 제한한다. 연결 부하를 줄일 수 있지만 관리할 경로가 늘어난다.
  3. 시나리오 확장같은 계정 안의 VPC끼리뿐 아니라 다른 계정의 VPC, 다른 리전의 VPC와도 피어링할 수 있다. 어떤 대역을 어디로 열지 시나리오에 맞춰 경로와 접근 범위를 정한다.

#5한 줄 요약

상대 VPC 전체를 열지 특정 주소만 열지 목적에 맞게 경로 범위를 정해 트래픽을 통제하는 것

Transit Gateway — 다수 네트워크의 허브07-01

Transit Gateway의 개념과 설계

여러 VPC·온프레미스 네트워크를 하나의 중앙 허브에 연결해 라우팅을 단순화하는 리전 단위 가상 라우터로, 스포크를 허브에 붙이는 허브-앤-스포크 설계의 중심이다.

#1문제 상황

VPC가 몇 개 안 될 때는 VPC 피어링으로 1:1 연결을 만들면 된다. 하지만 VPC가 늘어나면 각 VPC를 서로 1:1로 잇는 연결 수가 급격히 늘어나 관리가 감당하기 어려워진다. VPC마다 상대마다 라우팅 테이블을 손봐야 하고, 새 네트워크를 하나 붙일 때마다 기존 연결을 다시 조정해야 한다.

온프레미스 네트워크까지 섞이면 VPN·Direct Connect 연결을 VPC마다 따로 구성해야 해서 구성이 더 복잡해진다. 연결이 늘수록 전체 구조가 얽히고, 트래픽이 어디를 거쳐 가는지 파악하기도 어려워진다.

#2핵심 질문

수많은 VPC와 온프레미스 네트워크를 1:1 연결의 얽힘 없이 하나로 이을 수는 없을까?

#3동작 예시

Transit Gateway 하나를 중앙 허브로 만들고, 여러 VPC와 온프레미스 네트워크를 각각 어태치먼트(허브에 붙이는 연결부)로 붙인다. 새 네트워크는 허브에 하나만 붙이면 기존 연결을 건드리지 않고 전체와 통신한다. 중앙에서 라우팅이 관리되어 연결 구조가 단순해진다.

#4동작 과정

  1. 허브 생성리전 단위 가상 라우터인 Transit Gateway를 만든다. 이 허브가 여러 네트워크를 잇는 단일 중심이 된다.
  2. 어태치먼트 연결VPC, VPN, Direct Connect 게이트웨이, 다른 Transit Gateway와의 피어링 등을 어태치먼트로 허브에 붙인다. 네트워크를 추가할 때마다 허브에 하나씩 연결하면 된다.
  3. 중앙 라우팅허브가 어태치먼트들 사이의 트래픽 경로를 결정하고 전달한다. 리전 간에는 Transit Gateway끼리 피어링으로 이어지고, AWS 데이터 센터 사이 트래픽은 물리 계층에서 자동 암호화된다.

#5한 줄 요약

여러 VPC와 온프레미스 네트워크를 하나의 중앙 허브에 모아 라우팅을 단순화하는 것

Transit Gateway — 다수 네트워크의 허브07-02

Transit Gateway 생성과 관리

ASN·기본 라우트 테이블·DNS 지원 같은 옵션을 지정해 Transit Gateway를 만들고 태그·수정·삭제와 리소스 공유 수락까지 관리한다.

#1문제 상황

중앙 허브를 만들려면 ASN, 라우팅 테이블, DNS 지원 같은 옵션을 정해야 하는데, 이런 값을 잘못 잡거나 사후에 관리하지 못하면 라우팅이 꼬이거나 연결이 예상과 다르게 동작한다. 여러 어태치먼트를 붙이고 나면 어떤 허브가 어떤 목적에 쓰이는지 식별하기도 어려워진다.

허브를 만든 뒤에는 태그를 붙여 관리하고, 필요하면 설정을 수정하거나 리소스 공유를 수락하고, 다 쓰면 삭제해야 한다. 이런 관리 작업을 놓치면 불필요한 리소스가 남거나 소유자가 아닌 계정에서 붙인 연결을 통제하지 못하는 문제가 생긴다.

#2핵심 질문

Transit Gateway를 만들 때 무엇을 정하고, 만든 뒤에는 어떻게 관리해야 할까?

#3동작 예시

콘솔에서 Transit Gateway를 만들면 라우팅에 쓸 기본 Transit Gateway 라우팅 테이블이 함께 생성되어, 기본 연결 라우팅 테이블과 기본 전파 라우팅 테이블로 쓰인다. 이 기본 테이블을 만들지 않으면 나중에 직접 만들어야 한다. Name 태그를 붙여 목적별로 허브를 구분한다.

#4동작 과정

  1. 생성과 기본 테이블Transit Gateway를 만들면 기본 라우팅 테이블이 생성되어 기본 연결·전파 테이블로 지정된다. 이로써 별도 설정 없이도 연결을 붙일 기반이 갖춰진다.
  2. 옵션과 태그 관리ASN(자율 시스템 번호, BGP 라우팅에서 네트워크를 구분하는 번호)·DNS 지원 등 옵션을 지정하고, Name 태그 등으로 허브를 식별한다. 암호화 지원은 생성 시에는 켤 수 없고, 허브가 available 상태가 된 뒤 수정으로 켠다.
  3. 수정·공유·삭제설정을 수정하고, 리소스 공유로 받은 어태치먼트를 수락하며, 다 쓰면 허브를 삭제한다. 이 관리 절차로 허브를 최신 상태로 유지하고 불필요한 리소스를 정리한다.

VPC·네트워크 기능 어태치먼트

VPC와 서브넷을 Transit Gateway에 연결하는 VPC 어태치먼트와 방화벽 같은 네트워크 기능 어플라이언스를 연결하는 네트워크 기능 어태치먼트를 생성·수정·삭제한다.

#1문제 상황

Transit Gateway라는 허브를 만들어도 VPC를 여기에 붙이지 않으면 그 VPC의 트래픽은 허브를 지나지 않는다. VPC를 붙일 때는 각 가용 영역에서 서브넷 하나씩을 지정해 트래픽의 출입 지점으로 삼아야 하는데, 이 서브넷 지정을 소홀히 하면 일부 가용 영역의 리소스가 허브에 닿지 못한다.

어태치먼트가 서브넷이 있는 가용 영역에만 트래픽 출입점을 제공하기 때문에, 어태치먼트가 없는 가용 영역의 리소스는 Transit Gateway에 도달할 수 없다. 방화벽 같은 네트워크 기능 어플라이언스를 붙이는 경우에는 별도의 연결과 라우팅 구성이 필요해 관리도 더 까다롭다.

#2핵심 질문

VPC와 네트워크 기능 어플라이언스를 Transit Gateway에 안정적으로 붙이려면 어떻게 해야 할까?

#3동작 예시

VPC를 Transit Gateway에 붙일 때 각 가용 영역에서 서브넷 하나씩을 지정한다. 이 서브넷들이 허브로 드나드는 트래픽의 출입 지점이 된다. 같은 가용 영역 안의 다른 서브넷에 있는 리소스로 가려면, 그 어태치먼트 서브넷의 라우팅 테이블에 대상 서브넷으로 향하는 경로가 있어야 트래픽이 도달한다.

#4동작 과정

  1. VPC 어태치먼트 생성VPC를 붙일 때 각 가용 영역에서 서브넷 하나씩을 트래픽 출입점으로 지정해 어태치먼트를 만든다. 이로써 그 VPC가 허브를 통해 다른 네트워크와 통신할 발판이 생긴다.
  2. 경로와 보안 설정어태치먼트 서브넷의 라우팅 테이블에 대상 서브넷 경로를 구성하고, 보안 그룹 인바운드 규칙을 갱신한다. 그래야 같은 가용 영역의 다른 서브넷 리소스까지 트래픽이 닿는다.
  3. 기능 어태치먼트 연결방화벽 같은 네트워크 기능 어플라이언스는 별도의 네트워크 기능 어태치먼트로 붙이고, 그 어태치먼트를 통해 트래픽이 흐르도록 라우팅을 구성한다. 검사 경로가 갖춰지면 어플라이언스를 거쳐 트래픽이 전달된다.

#5한 줄 요약

VPN·Client VPN·Direct Connect 어태치먼트

Site-to-Site VPN·VPN Concentrator·Client VPN·Direct Connect 게이트웨이를 Transit Gateway에 연결해 원격·온프레미스 네트워크를 허브에 통합한다.

#1문제 상황

여러 VPC와 온프레미스 데이터센터를 함께 운영하면 각 VPC마다 별도의 VPN 연결을 따로 만들고 관리해야 했다. 원격 사용자와 지사가 늘어날수록 VPN 터널 수가 제곱으로 늘고, 각 VPC의 라우트 테이블을 개별적으로 손봐야 했다. Transit Gateway 이전에는 이런 연결들이 특정 VPC에 붙어 있어서, 그 VPC가 사라지거나 설정이 바뀌면 온프레미스 접속 전체가 흔들렸다. Site-to-Site VPN·Client VPN·Direct Connect를 하나의 중앙 지점에 모아 관리할 방법이 없었다.

#2핵심 질문

원격지·온프레미스 연결을 각 VPC에 흩어 붙이지 않고 하나의 허브에 통합해 관리할 수 있을까?

#3동작 예시

Site-to-Site VPN 연결 하나를 Transit Gateway에 어태치먼트로 붙이는 경우를 보자. 먼저 온프레미스 쪽 VPN 장비 정보를 담은 customer gateway(고객 게이트웨이)를 지정하고, 그 위에 VPN 연결을 만든다. 이 VPN 연결을 Transit Gateway에 어태치먼트로 연결하면, 그때부터 VPN을 지나는 트래픽은 개별 VPC가 아니라 Transit Gateway의 라우트 테이블 규칙에 따라 목적지를 찾는다.

#4동작 과정

  1. 어태치먼트 생성VPN 연결·VPN Concentrator·Client VPN·Direct Connect 게이트웨이 중 하나를 골라 Transit Gateway에 붙인다. Site-to-Site VPN은 고객 게이트웨이를 반드시 지정해야 하며, 정적 경로 방식이면 라우트를 Transit Gateway 라우트 테이블에 먼저 넣어야 한다.
  2. 라우트 전파·정적 경로 설정어태치먼트가 붙으면 그 라우트가 라우트 테이블로 전파된다. 필요하면 관리자가 정적 라우트를 직접 추가해 경로를 세밀하게 제어한다.
  3. 연결 상태 관리만든 어태치먼트는 상태를 조회하고, 더 이상 필요 없으면 삭제한다. Client VPN 어태치먼트는 요청을 수락하거나 거절하는 절차를 거친다.

#5한 줄 요약

피어링·Connect 어태치먼트

서로 다른 리전·계정의 Transit Gateway를 연결하는 피어링 어태치먼트와, SD-WAN 등 타사 어플라이언스를 라우팅 도메인에 넣는 Connect 어태치먼트·Connect 피어를 다룬다.

#1문제 상황

Transit Gateway 하나만으로는 서로 다른 리전이나 다른 계정의 네트워크까지 한 번에 연결할 수 없었다. 리전 간 트래픽을 주고받으려면 각 리전의 Transit Gateway를 별도로 연결해야 했고, SD-WAN 같은 타사 어플라이언스를 라우팅 경로에 넣으려면 우회 장치를 따로 구성해야 했다. 연결 대상이 계정 경계를 넘으면 소유자가 다르기 때문에 상대방의 동의 없이 연결을 만들 수 없다는 점도 문제였다.

#2핵심 질문

서로 다른 리전·계정의 Transit Gateway와 타사 어플라이언스를 하나의 라우팅 구조로 안전하게 연결할 수 있을까?

#3동작 예시

서로 다른 리전에 있는 Transit Gateway A와 B를 연결한다고 하자. A에 피어링 어태치먼트를 만들면서 상대 B의 식별자를 지정하면 요청이 생긴다. B 소유자가 그 요청을 수락해야 연결이 성립하고, 그다음 A의 라우트 테이블에 "B로 가려면 이 피어링 어태치먼트로" 라는 정적 라우트를 추가해야 트래픽이 실제로 흐른다.

#4동작 과정

  1. 피어링 어태치먼트 생성·수락내 계정 또는 다른 계정의 Transit Gateway를 대상으로 피어링 어태치먼트를 만든다. 상대가 다른 계정이면 그 소유자가 요청을 수락해야 연결된다. 리전 내·리전 간 모두 가능하며 IPv4·IPv6를 지원한다.
  2. 라우트 추가두 Transit Gateway 사이에 트래픽을 흘리려면 라우트 테이블에 피어링 어태치먼트를 가리키는 정적 라우트를 넣는다. 각 피어링 대상에는 고유한 ASN(자율 시스템 번호, 네트워크를 식별하는 번호)을 쓰는 것이 권장된다.
  3. Connect 어태치먼트로 타사 연결SD-WAN 같은 타사 어플라이언스를 넣을 때는 Connect 어태치먼트와 Connect 피어를 만들어 라우팅 도메인에 포함시킨다. 필요 없어지면 피어·어태치먼트 순서로 삭제한다.

#5한 줄 요약

리전·계정이 다른 Transit Gateway와 타사 어플라이언스를 피어링·Connect 어태치먼트로 연결해 하나의 라우팅 구조로 묶는 것

Transit Gateway — 다수 네트워크의 허브07-06

Transit Gateway 라우트 테이블

어태치먼트의 라우트를 담아 트래픽 경로를 결정하는 라우트 테이블로, 어소시에이션·프로퍼게이션·정적 라우트·프리픽스 리스트 참조로 경로를 제어한다.

#1문제 상황

어태치먼트를 아무리 많이 붙여도 트래픽이 어디로 갈지 결정하는 규칙이 없으면 연결은 의미가 없다. 기존에는 각 VPC의 라우트 테이블이 자기 VPC 안의 경로만 알았기 때문에, VPC 여러 개와 VPN을 넘나드는 전체 경로를 한눈에 관리할 수 없었다. 경로가 여러 개 얽히면 어느 경로가 우선인지, 어떤 어태치먼트를 어느 테이블에 넣을지 정할 기준도 흩어져 있었다.

#2핵심 질문

여러 어태치먼트 사이에서 트래픽이 갈 목적지를 규칙으로 어떻게 일관되게 결정할까?

#3동작 예시

VPC A에서 온 트래픽을 VPN 뒤의 온프레미스 대역으로 보내야 한다고 하자. VPC A 어태치먼트를 라우트 테이블에 어소시에이트(연결)하면, 그 테이블이 VPC A에서 나가는 트래픽의 경로를 판단한다. 목적지 대역이 VPN 어태치먼트로 프로퍼게이션(경로 자동 전파)됐다면, 그 대역으로 가는 패킷은 VPN 어태치먼트로 전달된다.

#4동작 과정

  1. 라우트 테이블 생성·어소시에이트라우트 테이블을 만들고 어태치먼트를 연결한다. VPC·VPN·VPN Concentrator·Client VPN·Direct Connect 게이트웨이·피어링·Connect 어태치먼트가 모두 대상이 된다.
  2. 경로 전파·정적 라우트어소시에이트된 어태치먼트의 경로가 테이블로 프로퍼게이션된다. 하나의 어태치먼트를 여러 테이블에 전파할 수도 있다. 필요하면 정적 라우트를 만들어 동적 경로 장애 시 백업 경로로 쓰거나 프리픽스 리스트를 참조해 경로를 묶는다.
  3. 정비·정리라우트 테이블을 S3로 내보내 감사하거나 백업하고, 프로퍼게이션을 끄거나 어소시에이션을 해제하고, 더 이상 필요 없으면 테이블을 삭제한다.

Transit Gateway 정책 테이블

출발지·목적지 어태치먼트 같은 조건으로 트래픽을 특정 라우트 테이블로 유도해 세그먼트 간 라우팅을 중앙에서 제어하는 정책 기반 라우팅 기능이다.

#1문제 상황

기존 Transit Gateway 라우팅은 목적지 IP 주소만 보고 경로를 정했다. 그래서 목적지가 같은 두 트래픽이라도 출발지나 포트가 다르면 서로 다른 경로로 보내고 싶어도 보낼 수 없었다. 보안 어플라이언스로 특정 트래픽만 검사에 보내거나, 사용자 집단별로 다른 네트워크 경로를 태우는 일을 목적지 주소만으로는 표현할 수 없었다.

#2핵심 질문

목적지 IP가 같아도 출발지·포트·프로토콜 같은 조건으로 트래픽을 다른 라우트 테이블로 유도할 수 있을까?

#3동작 예시

출발지 대역이 일반 사용자인 트래픽과 관리자 대역인 트래픽이 같은 목적지로 간다고 하자. 정책 테이블에 출발지 주소를 조건으로 하는 규칙을 순서대로 넣으면, 매칭된 패킷은 규칙이 지정한 특정 라우트 테이블로 보내진다. 그래서 일반 사용자 트래픽만 보안 어플라이언스 검사를 거치게 할 수 있다.

#4동작 과정

  1. 정책 테이블 생성·규칙 작성정책 테이블을 만들고, 출발지·목적지 IP, 출발지·목적지 포트, 프로토콜 같은 패킷 속성을 조건으로 삼는 규칙을 순서대로 채운다.
  2. 규칙 평가·유도들어온 패킷을 규칙과 위에서부터 대조해 매칭되면, 그 규칙이 가리키는 특정 라우트 테이블로 트래픽을 보낸다. 목적지 IP만 보던 기존 방식과 달리 같은 목적지라도 흐름별로 다른 전달이 가능하다.
  3. 어소시에이트·관리정책 테이블을 Transit Gateway에 어소시에이트해 적용하고, 규칙을 수정·삭제하거나 어소시에이션을 해제해 정책을 바꾼다.

#5한 줄 요약

#1문제 상황

#2핵심 질문

여러 VPC와 서브넷에 흩어진 수신자에게 데이터 한 번으로 동시에 전달할 수 있을까?

#3동작 예시

윈도우 서버 인스턴스 하나가 시세 데이터를 여러 수신 인스턴스에 뿌린다고 하자. Transit Gateway에 멀티캐스트 도메인을 만들고, 소스를 등록한 뒤 각 수신 인스턴스를 그룹 멤버로 등록한다. 그러면 소스는 데이터를 한 번만 보내고, Transit Gateway가 멀티캐스트 라우터 역할을 해 여러 서브넷의 수신자에게 복제·전달한다.

#4동작 과정

  1. 도메인 생성멀티캐스트 트래픽을 다룰 도메인을 만든다. 수신자가 IGMP(인터넷 그룹 관리 프로토콜)로 직접 참여를 알리는 방식과, 소스·멤버를 미리 지정하는 정적 소스 방식 중에서 고른다.
  2. VPC·서브넷 연결VPC 어태치먼트와 그 안의 서브넷을 도메인에 연결한다. 이로써 어떤 서브넷이 멀티캐스트를 받을 수 있는지 정해진다.
  3. 소스·멤버 등록그룹에 소스와 수신 멤버를 등록하고 필요하면 해제한다. 공유가 필요하면 도메인을 다른 계정과 공유할 수 있다.

어태치먼트·트래픽 기준으로 요금을 나누는 미터링 정책과, Transit Gateway를 지나는 트래픽을 기록하는 Flow Logs로 사용량과 비용을 추적한다.

#1문제 상황

기본 Transit Gateway 비용 배분은 데이터를 보낸 쪽, 즉 출발 어태치먼트를 소유한 계정에 처리가격이 붙는 방식이다. 여러 계정이 하나의 허브를 공유하면 실제로 이득을 보는 쪽과 비용을 내는 쪽이 어긋날 수 있다. 또 어떤 트래픽이 얼마나 오갔는지 기록이 없으면, 누가 얼마를 썼는지 근거를 대기 어렵고 문제를 추적하기도 힘들다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 미터링 정책 작성규칙 번호가 낮은 것부터 순서대로 평가되는 규칙을 만든다. 어태치먼트 유형·특정 ID·네트워크 주소 같은 트래픽 속성을 조건으로 지정하고, 매칭되면 그 규칙이 정한 계정에 비용이 배분된다.
  2. 미들박스 지정비용 배분 대상에 미들박스 어태치먼트를 추가하거나 제거해, 어느 장비를 거치는 트래픽을 어떻게 청구할지 관리한다.
  3. Flow Logs로 기록Transit Gateway를 지나는 트래픽을 Flow Logs로 캡처한다. 기록을 CloudWatch Logs, Amazon S3, Amazon Data Firehose 같은 목적지로 보내 조회·처리하고, 필요하면 로그를 삭제하거나 태그를 관리한다.

Site-to-Site VPN — 온프레미스 연결08-01

Site-to-Site VPN의 개념과 터널

온프레미스 네트워크와 VPC를 공용 인터넷 위의 IPsec VPN 터널로 안전하게 연결하는 관리형 서비스다.

#1문제 상황

기본적으로 Amazon VPC 안에 띄운 인스턴스는 온프레미스 네트워크나 원격 장치와 통신할 수 없다. VPC는 자기 안에서만 격리된 사설 주소 공간을 쓰기 때문에, 사무실 서버나 데이터센터 장비와 같은 사내 네트워크로 나가는 길이 따로 없다.

이를 공용 인터넷에 그대로 열어 연결하면 경로는 뚫리지만 오가는 데이터가 암호화되지 않아 노출된다. 그래서 온프레미스와 VPC 사이를 안전하게 잇는 별도의 관리형 연결 수단이 필요하다.

#2핵심 질문

인터넷에 노출하지 않고 온프레미스 네트워크와 VPC를 안전하게 연결하려면 어떻게 해야 하는가?

#3동작 예시

VPC에 연결된 가상 프라이빗 게이트웨이와 온프레미스의 고객 게이트웨이 장치 사이에 IPsec VPN 연결을 만든다. 이 연결은 두 개의 터널로 구성되어, 한쪽 터널에 장애가 생기면 트래픽이 자동으로 다른 터널로 넘어가 접속이 끊기지 않는다. AWS가 정기 점검을 할 때도 두 터널 중 하나만 잠시 비활성화되므로 나머지 터널로 통신이 유지된다.

#4동작 과정

  1. VPN 연결 생성온프레미스 장치를 나타내는 고객 게이트웨이와 VPC 쪽 가상 프라이빗 게이트웨이를 지정해 IPsec VPN 연결을 만든다. 이때 연결은 자동으로 두 개의 터널을 갖는다.
  2. 터널 협상과 인증양쪽 장치가 IPsec(인터넷 구간 트래픽을 암호화하는 프로토콜) 파라미터와 사전 공유 키 같은 인증 정보를 맞춰 터널을 세운다.
  3. 라우팅으로 트래픽 전달라우팅을 구성해 어떤 트래픽을 이 연결로 보낼지 정하면, VPC와 온프레미스 사이 트래픽이 설정한 터널을 통해 오간다.

고객 게이트웨이와 장치 구성

고객 게이트웨이는 온프레미스 쪽 VPN 장치를 AWS에 나타내는 리소스로, 그 장치를 요구사항에 맞게 구성해야 연결된다.

#1문제 상황

Site-to-Site VPN 연결은 온프레미스 쪽 실제 VPN 장치와 AWS 사이에서 이뤄지는데, AWS는 그 장치가 무엇인지 알지 못한다. 장치 정보를 등록하지 않으면 어떤 장비와 터널을 맺을지 정할 수 없다.

게다가 온프레미스 장치는 네트워크 관리자가 직접 구성해야 한다. 터널 파라미터, 방화벽 규칙, 라우팅 설정이 AWS가 기대하는 요구사항과 어긋나면 연결은 만들어도 실제로 트래픽이 흐르지 않는다.

#2핵심 질문

온프레미스 VPN 장치를 AWS가 인식하고 연결이 실제로 동작하려면 무엇을 등록하고 어떻게 구성해야 하는가?

#3동작 예시

온프레미스 방화벽 장비를 고객 게이트웨이 리소스로 등록할 때, 그 장치의 공인 IP 주소와 라우팅 방식(정적 또는 BGP)을 함께 지정한다. 이후 장치 쪽에서는 AWS가 안내한 대로 IPsec 터널용 포트와 프로토콜을 방화벽에서 허용하고, 제공된 구성 파일을 참고해 라우팅과 터널 파라미터를 설정한다.

#4동작 과정

  1. 고객 게이트웨이 등록온프레미스 장치를 AWS 리소스로 나타내기 위해 장치의 IP 주소와 라우팅 유형을 지정한다. 이 리소스가 이후 VPN 연결의 온프레미스 끝점이 된다.
  2. 장치 구성 적용장치 제조사별 구성 파일(정적·동적 라우팅별로 제공)을 참고해 터널 파라미터와 라우팅을 장치에 설정한다. 방화벽 규칙으로 필요한 트래픽을 허용한다.
  3. 연결 검증두 터널이 정상적으로 올라오는지 확인한다. 한쪽 장치에 장애가 생기면 다른 터널로 자동 전환되어 접속이 유지된다.

Site-to-Site VPN — 온프레미스 연결08-03

라우팅 옵션과 아키텍처

Site-to-Site VPN은 정적 라우팅과 BGP 기반 동적 라우팅 중에서 고르며, 이 선택이 터널·경로 우선순위와 이중화 아키텍처를 좌우한다.

#1문제 상황

VPN 연결을 여러 개 만들면 가상 프라이빗 게이트웨이는 어떤 트래픽을 어느 연결로 보낼지 판단해야 한다. 이때 사용할 수 있는 라우팅 방식이 정해져 있지 않으면 경로가 겹치거나 우선순위가 뒤엉켜 트래픽이 의도한 연결로 가지 않는다.

또 연결이 하나뿐이면 그 연결이 끊기는 순간 온프레미스와의 통신 전체가 끊긴다. 라우팅 선택과 이중화 구성을 함께 설계하지 않으면 안정성이 확보되지 않는다.

#2핵심 질문

VPN 연결이 여러 개일 때 트래픽을 어느 연결로 보낼지 정하고, 연결 장애에도 끊기지 않게 하려면 라우팅을 어떻게 설계해야 하는가?

#3동작 예시

가상 프라이빗 게이트웨이는 정적으로 지정한 경로 또는 BGP(Border Gateway Protocol, 네트워크 간 경로를 자동으로 교환하는 라우팅 프로토콜)로 광고된 경로를 보고 트래픽을 알맞은 VPN 연결로 보낸다. 같은 목적지 경로가 양쪽에 있으면 정적으로 할당한 경로가 BGP 광고 경로보다 우선한다. BGP 광고를 쓰기로 하면 정적 경로는 지정할 수 없다.

#4동작 과정

  1. 라우팅 유형 선택연결을 만들 때 정적 라우팅과 동적(BGP) 라우팅 중 하나를 정한다. 이 선택에 따라 이후 경로 지정 방법이 달라진다.
  2. 경로 지정정적이면 목적지 대역을 직접 지정하고, 동적이면 BGP로 온프레미스가 광고하는 경로를 받는다. 동일한 경로가 겹치면 정적 경로가 우선한다.
  3. 서브넷 라우트 테이블 갱신트래픽을 VPN 연결로 보내도록 서브넷의 라우트 테이블을 수정한다. 이렇게 해야 VPC 안 인스턴스의 트래픽이 터널로 향한다.

#5한 줄 요약

정적·동적 라우팅 선택과 이중화 구성으로 여러 VPN 연결 사이에서 트래픽 경로와 우선순위를 결정하는 것

VPN 연결 생성과 관리

가상 프라이빗 게이트웨이 또는 Transit Gateway를 대상으로 VPN 연결을 만들고, 터널 옵션·정적 경로·대상 게이트웨이를 관리한다.

#1문제 상황

VPN 연결은 한 번 만들고 끝나는 것이 아니다. 대상 게이트웨이를 바꾸거나, 터널 옵션을 조정하거나, 정적 경로를 수정해야 하는 상황이 계속 생긴다. 이런 변경을 할 방법이 없으면 연결을 지우고 새로 만들어야 한다.

또 연결에 쓰이는 인증 정보가 노출되거나 인증서가 만료되면 보안이 약해진다. 연결·게이트웨이·고객 게이트웨이를 만들고 지우고 교체하는 일련의 관리 절차가 필요하다.

#2핵심 질문

VPN 연결을 만들고 난 뒤 대상 게이트웨이·터널 옵션·경로·인증 정보를 안전하게 바꾸고 정리하려면 어떻게 관리해야 하는가?

#3동작 예시

VPN 연결의 대상 게이트웨이를 가상 프라이빗 게이트웨이에서 Transit Gateway로 바꾸는 경우, 기존 연결의 대상을 수정하는 방식으로 처리한다. 터널 옵션이나 정적 경로도 연결을 다시 만들지 않고 수정할 수 있다. 인증 정보가 노출되면 사전 공유 키를 교체하고, 터널 끝점 인증서는 주기적으로 회전한다.

#4동작 과정

  1. 연결 생성대상 게이트웨이(가상 프라이빗 게이트웨이 또는 Transit Gateway)와 고객 게이트웨이를 지정해 VPN 연결을 만든다. 두 개의 터널이 함께 생성된다.
  2. 옵션·경로 관리터널 옵션, 대상 게이트웨이, 고객 게이트웨이, 정적 경로를 필요에 따라 수정한다. 인증 정보가 노출되면 자격 증명을 교체한다.
  3. 정리더 이상 필요 없는 연결과 고객 게이트웨이를 삭제한다. 가상 프라이빗 게이트웨이는 VPC에서 분리한 뒤 삭제한다.

보안·모니터링·할당량

VPN 연결의 데이터 보호와 IAM 접근 제어, CloudWatch·로그 기반 터널 상태 모니터링, 그리고 연결·게이트웨이 할당량을 다룬다.

#1문제 상황

VPN 연결을 만들었다고 끝이 아니라, 오가는 데이터를 보호하고 누가 이 리소스를 조작할 수 있는지 통제해야 한다. 접근 제어를 하지 않으면 권한 없는 사용자가 연결 설정을 바꾸거나 삭제할 수 있다.

또 터널이 실제로 살아 있는지 알 방법이 없으면 장애를 한참 뒤에나 발견한다. 연결·게이트웨이 같은 리소스에는 만들 수 있는 개수 한도가 있어, 이를 넘기 전에 파악하지 못하면 배포가 막힌다.

#2핵심 질문

VPN 연결의 데이터와 접근을 안전하게 지키고, 터널 상태를 관찰하며, 리소스 한도를 넘지 않게 관리하려면 어떻게 해야 하는가?

#3동작 예시

사전 공유 키 같은 인증 정보는 AWS Secrets Manager에 저장해 관리할 수 있다. 터널이 올라와 있는지는 CloudWatch 지표로 확인하고, 특정 터널 상태가 일정 시간 지속되면 알람을 걸어 알림을 받는다. 누가 VPN 리소스를 만들고 수정할 수 있는지는 IAM 정책으로 제한한다.

#4동작 과정

  1. 데이터·자격 증명 보호IPsec으로 트래픽을 암호화하고, 사전 공유 키는 Secrets Manager에 저장하는 등 인증 정보를 안전하게 관리한다.
  2. 접근 제어IAM 정책으로 VPN 리소스를 조작할 수 있는 주체와 범위를 제한한다. 필요하면 서비스 연결 역할을 사용한다.
  3. 모니터링과 한도 관리CloudWatch 지표와 로그로 터널 상태를 관찰하고 알람을 설정한다. 연결·게이트웨이의 할당량을 확인해 한도 안에서 운영한다.

Client VPN — 사용자 단위 원격 접속09-01

Client VPN의 개념과 인증

AWS Client VPN은 관리형 VPN 서비스로, 사용자가 OpenVPN 기반 클라이언트 소프트웨어를 통해 VPC나 온프레미스 네트워크에 원격 접속할 수 있게 하며, Active Directory·상호 인증서·SAML 2.0 연동 등으로 접속 사용자를 인증한다.

#1문제 상황

Site-to-Site VPN은 네트워크와 네트워크를 잇는 방식이라, 재택근무자나 이동 중인 개별 사용자가 자기 노트북으로 VPC에 접속하려면 별도 수단이 필요하다. 이런 사용자 접속용 VPN을 직접 구축하면 서버를 띄우고 인증서와 확장을 관리해야 하는 운영 부담이 크다.

또 사용자마다 접속을 허용할지 판단할 인증 수단이 필요하다. 인증 없이 열면 아무나 사내 자원에 접근할 수 있고, 사용자가 늘어날 때 서버가 따라 확장되지 않으면 접속이 몰릴 때 서비스가 버티지 못한다.

#2핵심 질문

개별 사용자가 어디서든 VPC와 온프레미스 자원에 안전하게 접속하도록, 인증과 확장을 갖춘 관리형 접속 수단을 어떻게 제공하는가?

#3동작 예시

사용자는 OpenVPN 기반 클라이언트 소프트웨어를 설치해 Client VPN 엔드포인트에 접속한다. 이때 접속한 사용자를 인증하는 방식으로 Active Directory, 상호 인증서, SAML 2.0 기반 싱글 사인온 중 하나를 쓴다. 인증이 끝나면 사용자는 허용된 VPC 자원이나 온프레미스 자원에 접근한다.

#4동작 과정

  1. 엔드포인트 준비Client VPN 엔드포인트를 만들고 클라이언트가 접속할 대상과 인증 방식을 지정한다. TLS로 암호화된 연결을 제공한다.
  2. 사용자 인증사용자가 OpenVPN 클라이언트로 접속하면 Active Directory, 상호 인증서, SAML 2.0 중 설정한 방식으로 신원을 확인한다.
  3. 자원 접근인증된 사용자에게 허용된 네트워크로 트래픽을 전달한다. 사용자 수가 늘면 서비스가 자동으로 확장되어 접속을 수용한다.

#5한 줄 요약

엔드포인트 운영과 접근 제어

Client VPN 엔드포인트는 클라이언트가 접속하는 대상으로서 생성·수정·삭제하며, 대상 네트워크 연결·라우트·인증서 폐기 목록과 인증 규칙(authorization rule)으로 어느 사용자가 어떤 네트워크에 접근할지 제어한다.

#1문제 상황

Client VPN 엔드포인트를 만들어 사용자를 받기 시작하면, 어느 사용자가 어떤 네트워크에 접근할 수 있는지 통제해야 한다. 아무 제한 없이 두면 한 사용자가 접근해서는 안 되는 자원까지 열람할 수 있다.

또 접속한 사용자를 확인하고 문제가 있는 접속을 끊을 수 있어야 하며, 클라이언트가 쓸 구성 파일과 인증서를 배포하고 만료·폐기된 인증서는 차단해야 한다. 이런 운영 요소를 관리하지 않으면 보안과 가용성이 무너진다.

#2핵심 질문

Client VPN 엔드포인트에서 사용자별로 접근 범위를 제한하고, 접속·인증서·라우트를 어떻게 운영하고 통제하는가?

#3동작 예시

엔드포인트에 인증 규칙(authorization rule)을 추가해 특정 사용자 그룹이 특정 대상 네트워크 대역에만 접근하도록 허용한다. 사용자가 접속하면 현재 연결 목록에서 접속 상태를 확인할 수 있고, 필요하면 그 연결을 끊을 수 있다. 더 이상 신뢰할 수 없는 클라이언트 인증서는 인증서 폐기 목록(CRL)에 넣어 접속을 차단한다.

#4동작 과정

  1. 엔드포인트 생성·수정클라이언트가 접속할 엔드포인트를 만들고, 대상 네트워크를 연결하며 필요한 라우트와 보안 그룹을 설정한다.
  2. 접근 제어 부여인증 규칙으로 어느 사용자가 어떤 네트워크에 접근할지 허용 범위를 정한다. 인증서 폐기 목록으로 폐기된 인증서의 접속을 막는다.
  3. 운영과 정리접속 중인 클라이언트 연결을 확인하고 필요하면 종료한다. 로그로 연결 기록을 남기고, 필요 없는 엔드포인트와 라우트는 삭제한다.

#5한 줄 요약

Client VPN 엔드포인트에서 인증 규칙으로 사용자별 접근을 제한하고 접속·인증서·라우트를 운영하며 통제하는 것

디바이스 포스처

디바이스 포스처는 접속하는 클라이언트 장비의 보안 상태를 CrowdStrike·Jamf·JumpCloud 같은 신뢰 공급자로부터 확인하고, Cedar 기반 정책으로 그 결과에 따라 VPN 접속 허용 여부를 결정하는 기능이다.

#1문제 상황

기존 Client VPN은 접속하는 사람이 누구인지만 확인했다. 인증서나 아이디·비밀번호를 통과하면 그 사람이 쓰는 장비의 상태는 보지 않고 그대로 접속을 허용했다. 그래서 정상 계정으로 로그인했더라도 백신이 꺼져 있거나 디스크 암호화가 안 된 장비가 사내 네트워크에 들어올 수 있었다. 사용자 신원 검사만으로는 장비 자체의 위험을 걸러내지 못하는 것이 한계다.

#2핵심 질문

접속하는 사람이 아니라 그 사람이 쓰는 장비의 보안 상태까지 확인해 접속 허용 여부를 정할 수 있을까?

#3동작 예시

Client VPN 엔드포인트에 CrowdStrike·Jamf·JumpCloud 같은 디바이스 신뢰 공급자를 연결한다. 이 공급자는 각 장비 위에 장비 상태를 설명하는 서명된 주장, 즉 디바이스 포스처 토큰을 만들어 둔다. 예를 들어 "이 장비는 디스크가 암호화되어 있고 규정을 준수한다"는 내용이 토큰 안에 담긴다. 운영자는 인증 정책에 "디스크 암호화가 된 장비만 허용" 같은 요구 조건을 적고, Client VPN이 토큰을 그 조건과 대조해 통과 여부를 결정한다.

#4동작 과정

  1. 공급자 연결Client VPN 엔드포인트에 신뢰 공급자(CrowdStrike·Jamf·JumpCloud 등 장비 상태를 확인해 주는 외부 서비스)를 설정하면, 각 장비에 서명된 디바이스 포스처 토큰이 준비된다. 이제 신원 정보 옆에 장비 상태 정보가 함께 생긴다.
  2. 정책 작성인증 정책에 장비가 만족해야 할 요구 조건을 적는다. 이 정책은 누가 접속하느냐가 아니라 어떤 상태의 장비가 접속하느냐를 판정하는 기준이 된다.
  3. 평가와 적용장비가 접속할 때마다 토큰을 정책과 대조하고, 세션이 유지되는 동안에도 5분마다 다시 평가한다. 조건을 만족하지 못하면 연결을 거부하고, 세션 중 기준이 깨지면 그 세션을 끊는다.

#5한 줄 요약

사용자 신원뿐 아니라 장비의 보안 상태를 신뢰 공급자로부터 확인해, 그 결과에 따라 Client VPN 접속을 허용하거나 차단하는 것

보안·모니터링·문제 해결

Client VPN의 보안(IAM·데이터 보호·모범 사례)과 CloudWatch 기반 모니터링, 그리고 DNS 해석·인증·터널 연결 등 접속 문제를 진단하는 문제 해결 방법을 다룬다.

#1문제 상황

Client VPN을 운영하면 접속 자체는 되는데 원하는 대로 트래픽이 흐르지 않는 상황이 자주 생긴다. 예를 들어 엔드포인트 DNS 이름이 해석되지 않거나, 트래픽이 서브넷 사이에 나뉘어 흐르지 않거나, Active Directory 그룹에 대한 인증 규칙이 기대대로 동작하지 않을 수 있다. 또한 어떤 계정이 어떤 엔드포인트에 접근할 수 있는지, 세션이 얼마나 오래 유지되는지를 관리자가 통제하고 관찰할 수단이 필요하다. 접속이 안 되는 이유를 모른 채 원인을 짐작만 하면 복구가 늦어진다.

#2핵심 질문

Client VPN을 안전하게 통제하고, 접속이 안 될 때 원인을 어디서 확인해 고칠 수 있을까?

#3동작 예시

접속이 되지 않는 사용자가 있다고 하자. 클라이언트 소프트웨어가 TLS 오류를 내는지, 사용자 이름·비밀번호 오류를 내는지, 아니면 엔드포인트 DNS 이름을 해석하지 못하는지를 먼저 구분한다. 관리자는 CloudWatch 지표로 엔드포인트의 현재 연결 수와 트래픽 양을 확인하고, IAM 정책과 인증 규칙으로 누가 접속을 승인받았는지 대조한다. 이렇게 클라이언트가 낸 오류 메시지, CloudWatch 지표, 접속 승인 설정을 나눠 보면 원인이 어느 지점인지 좁힐 수 있다.

#4동작 과정

  1. 보안 통제IAM으로 Client VPN 자원에 대한 접근 권한을 나누고, 데이터 보호와 인프라 보안 설정을 적용한다. 그래서 어떤 관리자·서비스가 어떤 엔드포인트를 다룰 수 있는지 분리된다.
  2. 모니터링CloudWatch 지표로 엔드포인트의 연결 수와 트래픽 사용량을 수집해 본다. 그래서 문제가 생겼을 때 언제 얼마나 몰렸는지 수치로 확인할 수 있다.
  3. 문제 해결DNS 해석 실패, 서브넷 분할 라우팅 이상, AD 그룹 인증 불일치, TLS·인증·포트 오류 등 증상별로 원인을 좁혀 조치한다. 그래서 접속 실패를 짐작이 아니라 근거로 진단하게 된다.

#5한 줄 요약

IAM·데이터 보호로 접근을 통제하고 CloudWatch 지표와 증상별 진단으로 접속 문제를 확인·해결하는 것

PrivateLink 개념과 인터페이스 엔드포인트

AWS PrivateLink는 VPC, 서비스, 온프레미스 사이를 인터넷에 노출하지 않고 사설로 연결하는 기술로, 인터넷 게이트웨이 없이 서비스에 접근하도록 서브넷에 ENI(탄력적 네트워크 인터페이스)를 만들어 주는 인터페이스 엔드포인트를 제공한다.

#1문제 상황

사설 서브넷의 인스턴스가 AWS 서비스나 다른 VPC의 서비스에 접속하려면 원래 인터넷 게이트웨이, NAT 장비, 공인 IP, Direct Connect, Site-to-Site VPN 중 하나가 필요했다. 이 방식은 트래픽이 인터넷 경로를 거치게 되어 노출 위험이 생기고, 접근 경로도 복잡해진다. 또한 어떤 API 엔드포인트와 서비스가 사설 서브넷에서 도달 가능한지 세밀하게 통제하기 어렵다. 연결을 위해 공인 주소 대역을 따로 관리해야 하는 부담도 따른다.

#2핵심 질문

인터넷에 노출하지 않고 VPC에서 서비스로 사설 연결을 만들 수 있을까?

#3동작 예시

사설 서브넷에 인스턴스가 있고, 그 서브넷에 인터페이스 엔드포인트를 만든다고 하자. 이 엔드포인트는 서브넷 안에 ENI(탄력적 네트워크 인터페이스, 서브넷에 꽂히는 가상의 네트워크 카드)를 하나 만들어 사설 IP 주소를 갖는다. 인스턴스는 그 사설 IP로 요청을 보내고, 트래픽은 AWS가 관리하는 사설 경로를 통해 목적 서비스로 전달된다. 인터넷 게이트웨이나 NAT를 거치지 않아도 서비스에 도달한다.

#4동작 과정

  1. 엔드포인트 생성접속하려는 AWS 서비스나 서비스 이름을 지정해 인터페이스 엔드포인트를 만든다. 그러면 선택한 서브넷에 사설 IP를 가진 ENI가 생긴다.
  2. 이름 해석 연결서비스의 DNS 이름을 엔드포인트의 사설 IP로 해석하도록 설정하면, 인스턴스가 평소 쓰던 서비스 이름 그대로 사설 주소를 받는다. 그래서 애플리케이션 설정을 바꾸지 않고도 사설 경로로 접속한다.
  3. 사설 통신인스턴스의 요청이 ENI를 통해 AWS 내부 사설 경로로 목적 서비스에 도착한다. 그래서 인터넷 게이트웨이·NAT·공인 IP 없이 트래픽이 VPC 밖으로 노출되지 않는다.

#5한 줄 요약

인터넷 게이트웨이 없이 서브넷에 ENI를 만들어 서비스에 사설로 접근하게 하는 것

게이트웨이 엔드포인트와 Gateway Load Balancer

게이트웨이 엔드포인트는 라우팅 테이블에 경로를 추가해 S3·DynamoDB 같은 서비스로 가는 트래픽을 사설로 전달하는 방식이고, Gateway Load Balancer 엔드포인트는 가상 어플라이언스(방화벽·IDS)로 트래픽을 검사·전달하기 위한 PrivateLink 연결이다.

→ 10-01 참조

#1문제 상황

사설 서브넷의 인스턴스가 Amazon S3나 DynamoDB에 접속하려면 원래 인터넷 게이트웨이나 NAT 장비를 거쳐 공용 서비스 엔드포인트로 나가야 했다. 이 경로는 트래픽이 외부로 나가게 만들고 NAT 비용과 관리 부담을 더한다. 한편 방화벽·IDS 같은 가상 어플라이언스로 트래픽을 검사하려면, 트래픽을 어플라이언스로 유도하고 다시 원래 목적지로 되돌리는 경로를 직접 구성해야 했다. 이 구성은 라우팅이 복잡해지고 이중화가 어렵다.

#2핵심 질문

S3·DynamoDB 접속과 가상 어플라이언스 검사 트래픽을 인터넷이나 NAT 없이 사설로 처리할 수 있을까?

#3동작 예시

S3로 가는 트래픽을 게이트웨이 엔드포인트로 보내려면 라우팅 테이블에 S3의 접두사 목록을 목적지로 하고 엔드포인트를 대상으로 하는 경로를 하나 추가한다. 그러면 인스턴스가 S3로 보내는 요청이 공용 인터넷으로 나가지 않고 엔드포인트를 통해 전달된다. 반대로 방화벽 어플라이언스로 트래픽을 검사시키려면 Gateway Load Balancer 엔드포인트를 만들어, 어플라이언스로 트래픽을 넘기고 검사 후 원래 목적지로 되돌린다.

#4동작 과정

  1. 게이트웨이 엔드포인트 경로 추가S3·DynamoDB용 게이트웨이 엔드포인트를 만들고 라우팅 테이블에 경로를 넣는다. 그러면 그 서비스로 가는 트래픽이 인터넷 게이트웨이나 NAT를 거치지 않고 사설로 전달된다.
  2. 어플라이언스 검사 경로 구성Gateway Load Balancer 뒤에 방화벽·IDS 같은 가상 어플라이언스를 두고 Gateway Load Balancer 엔드포인트를 만든다. 그러면 검사가 필요한 트래픽이 어플라이언스를 거쳐 흐른다.
  3. 검사 후 전달Gateway Load Balancer가 어플라이언스로 트래픽을 넘기고, 검사를 마친 트래픽을 원래 목적지로 되돌린다. 그래서 보안 검사가 끼어들어도 최종 도착지는 그대로 유지된다.

엔드포인트 서비스 공유

엔드포인트 서비스는 Network Load Balancer 뒤의 서비스를 다른 VPC나 계정에 PrivateLink로 공개하는 자원으로, 서비스 제공자가 엔드포인트 서비스를 만들고 허용 대상을 지정해 소비자가 인터페이스 엔드포인트로 접속하게 한다.

#1문제 상황

서비스 제공자가 자기 VPC 안의 서비스를 다른 VPC나 다른 계정의 고객에게 제공하려면, 인터넷에 공개 엔드포인트를 열거나 VPC 피어링 같은 연결을 고객마다 따로 구성해야 했다. 공개 엔드포인트는 노출 위험이 있고, 피어링은 고객이 늘수록 관리할 연결이 계속 늘어난다. 고객 입장에서도 제공자의 서비스에 접속하려면 자신의 네트워크 설정과 주소 체계를 맞춰야 하는 부담이 있었다. 양쪽 모두 연결을 늘릴수록 관리 비용이 커지는 구조다.

#2핵심 질문

내 VPC의 서비스를 인터넷에 노출하지 않고 다른 VPC나 계정에 안전하게 공개할 수 있을까?

#3동작 예시

서비스 제공자가 자기 VPC에 Network Load Balancer를 만들고 그것을 프런트로 삼아 엔드포인트 서비스를 구성한다. 그리고 특정 AWS 계정(주체)에게만 이 서비스에 접속할 권한을 부여한다. 소비자는 자신의 VPC에 인터페이스 엔드포인트를 만들어 그 서비스에 접속하고, 연결은 사설로 이뤄진다. 제공자는 허용한 계정만 받고, 소비자는 피어링 없이 사설 접속을 얻는다.

#4동작 과정

  1. 프런트 구성제공자가 VPC에 Network Load Balancer를 만들고, 엔드포인트 서비스를 만들 때 그 로드 밸런서를 선택한다. 그래서 서비스를 향하는 사설 진입점이 정의된다.
  2. 허용 대상 지정특정 AWS 주체(계정)에게 접속 권한을 부여한다. 그래서 아무나 접속하지 못하고 허용된 소비자만 연결할 수 있다.
  3. 소비자 접속소비자가 자기 VPC에 인터페이스 엔드포인트를 만들어 서비스에 연결한다. 그래서 피어링이나 공개 엔드포인트 없이 사설로 서비스를 사용한다.

리소스·네트워크 접근과 권한

#2핵심 질문

#4동작 과정

  1. 엔드포인트 정책 부착각 엔드포인트에 정책을 붙여 어떤 주체가 어느 서비스·리소스에 접근할 수 있는지 제한한다. 그래서 연결이 열려 있어도 허용 범위 밖의 접근은 막힌다.

  3. 접근 검증과 유지엔드포인트 정책과 IAM 정책이 함께 평가되어 접근이 허용되거나 거부된다. 그래서 자원과 네트워크 구간이 늘어나도 통제 지점이 유지된다.

VPC IPAM — IP 주소 계획과 추적11-01

IPAM의 개념과 구성

VPC IPAM(IP Address Manager)은 AWS에서 VPC와 서브넷의 IP 주소 공간을 중앙에서 계획·할당·추적하도록 돕는 관리형 서비스로, IPAM·범위(scope)·풀(pool)로 구성된다.

#1문제 상황

여러 계정과 리전에 걸쳐 VPC와 서브넷을 만들다 보면 IP 주소 대역이 어디에 얼마나 쓰였는지 한눈에 파악하기 어렵다. 담당자가 손으로 CIDR을 나눠 적어 두면 대역이 겹치거나 낭비되어도 알아채기 늦다. 또한 어떤 리소스가 어떤 주소 대역을 언제부터 쓰고 있는지 이력이 남지 않아, 연결 문제를 진단하거나 비즈니스 규칙에 맞는지 점검하기 어렵다. Bring Your Own IP(BYOIP) 대역을 여러 리전·계정에서 공유하는 것도 별도로 관리해야 한다.

#2핵심 질문

여러 계정과 리전의 IP 주소 공간을 중앙에서 계획·할당·추적할 수 있을까?

#3동작 예시

IPAM을 만들고 그 안에 범위(scope)를 두고, 범위 아래에 풀(pool)을 만든다. 풀에는 사내에서 쓰기로 한 CIDR 대역을 등록한다. 이후 VPC를 만들 때 그 풀에서 CIDR을 자동으로 할당받도록 하면, 어떤 대역이 어느 VPC에 배정됐는지 IPAM이 기록으로 남긴다. 운영자는 풀별로 사용 중인 주소와 남은 주소를 한 곳에서 본다.

#4동작 과정

  1. IPAM과 범위 구성IPAM을 만들고 그 안에 라우팅·보안 도메인 성격의 범위(scope)를 둔다. 그래서 조직의 IP 공간이 목적별로 나뉘어 관리된다.
  2. 풀에 대역 등록범위 아래에 풀(pool)을 만들고 사용할 CIDR 대역을 넣는다. 그래서 어떤 대역에서 어떤 주소를 배정할지 규칙의 기준이 생긴다.
  3. 할당과 추적VPC를 만들 때 풀에서 CIDR을 할당받고, IPAM이 배정 이력을 기록한다. 그래서 주소 사용 현황과 할당 이력을 중앙에서 확인할 수 있다.

VPC IPAM — IP 주소 계획과 추적11-02

IPAM 풀과 CIDR 할당

IPAM 풀은 IP 주소 공간을 계층적으로 나눠 담는 컨테이너로, 상위 풀에서 CIDR을 프로비저닝하고 VPC·서브넷 등에 할당할 수 있다.

#1문제 상황

VPC를 만들려면 반드시 IP 주소 범위인 CIDR 블록을 지정해야 하는데, 이 값을 사람이 손으로 정하다 보면 여러 계정과 리전에 걸쳐 같은 대역이 겹치는 일이 생깁니다. 겹친 대역은 라우팅 충돌과 연결 장애로 이어지고, 나중에 알아차리면 이미 배포된 자원들의 주소를 다시 매기는 복잡한 재번호 작업을 해야 합니다.

또한 각 계정이 자기 주소만 보고 따로 계획을 세우면 전체 조직의 IP 인벤토리를 한눈에 볼 수 없어, 남는 공간은 놀리고 필요한 곳은 부족해지는 불균형이 쌓입니다. 미래 확장을 위해 여유 공간을 미리 떼어 두는 것도 계정별로는 사실상 불가능합니다.

#2핵심 질문

여러 계정과 리전의 IP 주소 공간을 겹치지 않게 나누고, 남겨 둘 공간까지 한 곳에서 계획·할당하려면 어떻게 해야 하는가?

#3동작 예시

조직 전체를 담당하는 최상위 풀에 큰 대역(예: 10.0.0.0/8)을 넣고, 그 아래에 리전별 하위 풀을 만듭니다. 개발 계정용 하위 풀에는 10.1.0.0/16을 프로비저닝해 두고, 개발팀이 VPC를 만들 때 이 풀에서 10.1.2.0/24를 선택하게 하면, 겹침 없이 상위 대역 안에서만 잘려 나가며 아직 쓰지 않은 나머지 공간은 다음 리소스를 위해 그대로 예약됩니다.

#4동작 과정

  1. 풀 생성과 계층 구성최상위 IPv4/IPv6 풀을 만들고 그 아래에 리전·개발용 하위 풀을 붙여, 큰 주소 공간을 담는 컨테이너를 단계별로 나눕니다. 이렇게 하면 상위에서 정한 대역 안에서만 하위가 잘려 겹침이 원천적으로 막힙니다.
  2. CIDR 프로비저닝과 할당 전략 지정상위에서 하위 풀로 CIDR을 프로비저닝(풀에 주소 대역을 넣는 것)하고, 할당 전략(allocation strategy, 어떤 순서로 다음 CIDR을 꺼낼지 정하는 규칙)을 정해 둡니다. 그래서 리소스를 만들 때마다 사람이 대역을 고르지 않아도 규칙에 따라 순서대로 배정됩니다.
  3. 리소스에 할당과 공유VPC·서브넷 같은 리소스에 할당(allocate, 풀의 CIDR을 리소스에 연결하는 것)하고, AWS RAM으로 풀을 다른 계정과 공유합니다. 그래서 여러 계정이 하나의 IP 계획을 함께 쓰면서 낭비 없이 주소를 재사용할 수 있습니다.

VPC IPAM — IP 주소 계획과 추적11-03

IP 공간 관리와 운영

IPAM으로 풀과 범위를 편집·공유하고 CIDR을 프로비저닝·해제하며 할당 전략을 정의하는 등 IP 주소 공간을 지속적으로 운영·관리하는 방법을 다룬다.

#1문제 상황

IP 주소 계획은 한 번 세워 두면 끝나는 일이 아니라, 조직이 커지고 리전이 늘면서 풀을 편집하고 범위를 추가하며 대역을 회수하는 일이 계속 생깁니다. 이런 운영 작업을 개별 계정에서 제각각 처리하면 누가 어느 대역을 가져갔는지 추적이 끊기고, 회수한 공간이 제대로 반영되지 않아 계획과 실제가 어긋납니다.

또한 여러 계정이 IPAM을 쓰는 환경에서는 위임된 IPAM 관리자 계정이 관리 작업을 수행하도록 역할이 나뉘어야 합니다. 관리자 지정 없이 아무 계정이나 풀과 범위를 고치면 권한과 책임이 흐려집니다.

#2핵심 질문

한번 만든 IP 주소 계획을 조직 변화에 맞춰 편집·회수·공유하며 계속 일관되게 운영하려면 무엇을 관리해야 하는가?

#3동작 예시

부서 개편으로 한 사업부가 쓰던 대역을 다른 리전으로 옮겨야 할 때, IPAM 관리자가 해당 리소스의 VPC CIDR을 다른 범위로 이동시키고 더는 필요 없는 하위 풀의 CIDR을 풀에서 디프로비저닝(회수)합니다. 회수된 대역은 즉시 다른 하위 풀에 다시 프로비저닝할 수 있어, 주소 공간이 놀지 않고 재배치됩니다.

#4동작 과정

  1. 범위와 풀 편집IPAM의 범위(scope, 관리 대상 주소 공간을 묶는 단위)를 추가하고 풀을 편집해 리전·부서별로 나눕니다. 그래서 조직 개편에 맞춰 관리 경계를 다시 그릴 수 있습니다.
  2. CIDR 프로비저닝·디프로비저닝과 이동풀에 CIDR을 넣거나 빼고, VPC CIDR을 범위 간에 이동시킵니다. 그래서 더는 안 쓰는 대역을 회수해 필요한 곳으로 돌리고 계획과 실제 배치를 다시 맞춥니다.
  3. 운영 정책 적용과 위임SCP로 VPC 생성 시 IPAM 사용을 강제하고, ABAC로 관리 작업 권한을 정하며, 위임된 관리자 계정이 작업을 수행하게 합니다. 그래서 승인된 경로로만 주소가 할당되고 관리 책임이 한곳에 모입니다.

#5한 줄 요약

IP 주소 공간을 편집·회수·이동·공유하는 운영 작업을 관리자 계정에 모아, 계획과 실제 배치를 계속 일치시키는 것

VPC IPAM — IP 주소 계획과 추적11-04

리소스 검색과 사용 추적

IPAM이 VPC 등 리소스의 CIDR 사용 현황을 수집·모니터링하고 IP 주소 할당 이력을 조회할 수 있게 하는 추적 기능을 설명한다.

#1문제 상황

IPAM이 관리하지 않는 기존 계정에는 이미 만들어진 VPC와 서브넷이 흩어져 있습니다. 이런 자원의 CIDR 사용 현황을 파악하려면 계정마다 콘솔을 열어 손으로 대조해야 하고, 그 사이 어떤 대역이 얼마나 쓰였는지 최신 상태를 알기 어렵습니다.

또한 어느 CIDR이 실제로 얼마나 채워졌는지, 어떤 주소가 언제 누구에게 할당됐는지 이력이 없으면 사용률이 낮은 대역을 찾아내지 못해 주소 고갈이 다가와도 대비할 수 없습니다. 큰 규모·다중 계정 환경일수록 이 눈먼 상태가 위험합니다.

#2핵심 질문

IPAM이 직접 만들지 않은 기존 리소스까지 포함해, IP 주소 할당·사용률·소비 추세를 한곳에서 파악하려면 어떻게 해야 하는가?

#3동작 예시

리소스 검색(resource discovery)을 만들어 조직의 여러 계정·리전에 흩어진 VPC와 서브넷을 수집하게 하면, IPAM이 그 CIDR 사용 현황을 자동으로 가져옵니다. 대시보드에서 대역별 사용률 막대를 보면 어느 /16이 10%만 쓰였는지 드러나고, 그 남는 공간을 새 프로젝트에 돌릴 판단을 할 수 있습니다.

#4동작 과정

  1. 리소스 검색으로 수집조직·계정·리전을 지정해 리소스 검색을 만들면 IPAM이 그 안의 VPC·서브넷 CIDR을 찾아 모읍니다. 그래서 관리 밖에 있던 자원까지 인벤토리에 편입됩니다.
  2. 사용 현황 집계와 모니터링CIDR·범위·IPAM 단위로 할당·사용률·소비 추세를 집계하고 대시보드와 CloudWatch 지표로 보여줍니다. 그래서 안 쓰거나 비효율적으로 쓰이는 주소를 골라낼 수 있습니다.
  3. 이력 조회와 개선IP 주소 할당 이력과 공인 IP 인사이트를 조회해 언제 무엇이 배정됐는지 확인하고 계획을 조정합니다. 그래서 주소 고갈을 미리 막고 자원을 효율적으로 씁니다.

#5한 줄 요약

흩어진 리소스까지 끌어와 IP 주소의 할당·사용률·이력을 한곳에서 보여주어, 낭비를 찾아내고 고갈을 막게 하는 것

VPC IPAM — IP 주소 계획과 추적11-05

BYOIP와 튜토리얼

보유한 공인 IP 주소(BYOIP)를 IPAM으로 가져와 관리하는 절차와 콘솔·CLI로 IPAM과 풀을 구성하는 실습 튜토리얼을 안내한다.

#1문제 상황

기업이 이미 보유한 공인 IP 대역을 AWS로 가져오려면(BYOIP) 절차가 복잡하고, IPAM을 쓰지 않으면 가져온 공인 주소 공간을 조직의 여러 계정에 나눠 줄 방법이 없습니다. 계정별로 따로 가져와야 하니 같은 대역을 중복 관리하게 됩니다.

또한 IPAM을 쓰지 않으면 보유 공인 IP를 리전마다 따로 온보딩해야 하므로, 여러 리전에 자원을 두는 조직은 같은 작업을 반복하며 시간을 낭비합니다. 처음 IPAM을 구성하는 절차 자체도 콘솔과 CLI 중 무엇으로 어떻게 시작할지 막막합니다.

#2핵심 질문

보유한 공인 IP 주소 공간을 한 번만 AWS에 가져와 조직 전체와 여러 리전에 나눠 쓰려면 어떻게 해야 하는가?

#3동작 예시

공인 IPv4 대역을 보유한 회사가 IPAM에 그 대역을 한 번 온보딩한 뒤, IPAM 풀을 통해 서울·버지니아 같은 여러 리전의 EC2 인스턴스와 로드 밸런서에 같은 공인 주소 공간을 배분합니다. 도메인 제어를 검증해 대역 소유권을 확인하면, 리전마다 다시 가져오는 작업 없이 조직 계정들에 주소가 나뉩니다.

#4동작 과정

  1. IPAM과 풀 구성콘솔이나 AWS CLI로 IPAM과 풀을 만들고, 필요하면 ASN(자율 시스템 번호, 인터넷에서 망을 식별하는 번호)까지 함께 가져옵니다. 그래서 공인 주소를 담을 기반이 준비됩니다.
  2. 보유 IP 온보딩과 소유권 검증보유한 IPv4/IPv6 CIDR을 가져오고 도메인 제어를 검증해 그 대역이 내 것임을 확인합니다. 그래서 검증된 공인 공간만 AWS 자원에 쓸 수 있게 됩니다.
  3. 배포와 활용검증된 대역을 IPAM 풀에서 각 리전·계정의 리소스에 배분하고, CloudFront나 순차 Elastic IP 할당 등에 활용합니다. 그래서 공인 주소를 조직 전체에서 나눠 쓰고 재사용할 수 있습니다.

#5한 줄 요약

보유한 공인 IP 공간을 한 번만 AWS에 가져와 IPAM으로 조직 전체와 여러 리전에 나눠 쓰게 하는 것

VPC IPAM — IP 주소 계획과 추적11-06

IPAM 보안·할당량·참고

IPAM의 IAM 기반 접근 제어와 서비스 연결 역할, 사용 할당량(쿼터), 관련 정보를 정리한 참고 문서를 제공한다.

#1문제 상황

IPAM은 조직의 IP 주소 계획 전체를 좌우하므로 아무 사용자나 풀을 만들고 CIDR을 회수하게 두면 주소 계획이 훼손될 수 있습니다. 그런데 AWS 보안 자격 증명을 공유하지 않고 여러 사용자·서비스에 필요한 만큼만 권한을 나눠 주는 일은 직접 설계하면 복잡합니다.

또한 IPAM이 다른 AWS 서비스와 연동해 동작하려면 서비스가 대신 행동할 수 있는 역할이 필요하고, 어떤 관리형 정책이 붙는지, 계정마다 몇 개까지 만들 수 있는지(할당량)를 모르면 운영 중에 예기치 않게 한도에 부딪힙니다.

#2핵심 질문

IPAM에 대한 접근을 자격 증명 공유 없이 안전하게 나누고, 서비스가 쓰는 역할과 사용 한도를 어떻게 관리해야 하는가?

#3동작 예시

IAM 정책으로 특정 사용자에게는 IPAM 조회만, IPAM 관리자 계정의 사용자에게는 풀 생성과 CIDR 프로비저닝까지 허용하도록 나눕니다. IPAM이 리소스를 다루기 위해 만드는 서비스 연결 역할(service-linked role)은 직접 정의하지 않아도 AWS가 자동으로 생성·관리하므로, 관리자는 관리형 정책을 붙여 권한만 정하면 됩니다.

#4동작 과정

  1. 자격 증명으로 주체 식별AWS 보안 자격 증명으로 사용자·서비스·애플리케이션을 식별하고, IAM으로 IPAM 자원에 대한 접근 범위를 정합니다. 그래서 자격 증명을 공유하지 않고 필요한 만큼만 권한을 줍니다.
  2. 서비스 연결 역할과 관리형 정책IPAM용 서비스 연결 역할(IPAM이 리소스에 접근하도록 미리 정의된 역할)을 AWS가 대신 만들어 관리하고, 관리형 정책으로 권한을 부여합니다. 그래서 서비스 연동에 필요한 권한을 안전하게 처리합니다.
  3. 할당량 관리계정별 IPAM 관련 기본 개수 한도를 파악하고, 필요하면 증가를 요청합니다. 그래서 운영 중 한도 초과로 작업이 막히는 일을 미리 피합니다.

#5한 줄 요약

IAM으로 IPAM 접근을 자격 증명 공유 없이 나누고, 서비스 연결 역할·관리형 정책·할당량으로 안전하게 운영하게 하는 것

예제와 할당량 — 실전 구성과 한도12-01

VPC 구성 예제와 CLI 튜토리얼

테스트 환경, 웹·DB 서버, 프라이빗 서브넷처럼 자주 쓰는 VPC 구성 시나리오를 예제로 보여주고, AWS CLI로 VPC를 처음부터 만드는 단계별 튜토리얼을 제공하는 문서 묶음이다.

#1문제 상황

VPC를 처음부터 직접 설계하려면 IP 대역, 서브넷, 라우팅 테이블, 연결 옵션을 모두 스스로 정해야 하는데, 막상 시작하면 무엇을 어떤 순서로 만들어야 하는지 감이 잡히지 않습니다. 요구 사항이 다른 환경마다 어떤 구조가 맞는지도 판단이 어렵습니다.

또한 콘솔로만 구성을 익히면 이를 코드나 자동화로 옮길 때 다시 막힙니다. AWS CLI로 VPC를 처음부터 만드는 절차를 단계별로 따라 해 본 경험이 없으면 실제 자동화 구성에서 순서와 의존 관계를 놓치기 쉽습니다.

#2핵심 질문

용도별 VPC 구조를 참고하고 AWS CLI로 처음부터 만들어 보려면 어떤 예제와 절차를 따라야 하는가?

#3동작 예시

프라이빗 서브넷에 EC2 인스턴스를 두고 NAT 게이트웨이로 아웃바운드 인터넷만 허용하는 구성을 예제로 따라 합니다. 프라이빗 서브넷의 라우팅 테이블이 NAT 게이트웨이를 가리키게 하면, 인스턴스는 공인 IP 없이도 패키지 설치 같은 외부 통신을 할 수 있습니다.

#4동작 과정

  1. 예제로 구조 파악테스트 환경, 웹·DB 서버, 프라이빗 서브넷과 NAT 구성 등 용도별 VPC 예제를 보고 요구에 맞는 구조를 고릅니다. 그래서 대역·서브넷·라우팅 설계를 처음부터 고민하지 않아도 됩니다.
  2. CLI로 단계별 생성Getting started 튜토리얼을 따라 AWS CLI로 VPC와 서브넷을 순서대로 만듭니다. 그래서 콘솔이 아니라 명령으로 구성하는 흐름과 의존 관계를 익힙니다.
  3. 프라이빗 서브넷과 NAT 완성프라이빗 서브넷과 NAT 게이트웨이를 붙여 아웃바운드만 허용하는 구성을 완성합니다. 그래서 실제 운영에 가까운 형태를 CLI로 재현합니다.

용도별 VPC 구조를 예제로 보여주고 AWS CLI로 처음부터 만들어 보게 해, 설계 판단과 자동화 구성을 함께 익히게 하는 것

VPC 할당량

VPC, 서브넷, 라우팅 테이블, 보안 그룹, 인터넷/NAT 게이트웨이 등 VPC 리소스마다 정해진 기본 개수 한도와 이를 조정(증가) 요청하는 방법을 정리한 페이지다.

#1문제 상황

VPC와 그 안의 리소스는 계정·리전마다 만들 수 있는 개수에 한도가 정해져 있습니다. 이 기본 한도를 모르고 설계하면 리소스를 만들다가 갑자기 생성을 거부당하고, 원인을 찾느라 시간을 허비합니다.

한도는 대부분 리전 단위로 적용되고 일부는 조정이 가능한데, 어떤 항목이 조정 가능한지, 조정하면 어떤 다른 한도까지 함께 올라가는지를 모르면 계획을 세울 수 없습니다. 특히 여러 VPC를 대량으로 두는 환경에서는 이 한도 관리가 곧 설계 제약이 됩니다.

#2핵심 질문

VPC 리소스마다 정해진 기본 개수 한도를 어떻게 파악하고, 필요한 만큼 늘리려면 어떻게 요청하는가?

#3동작 예시

리전당 VPC 수의 기본 한도가 있고 이 항목은 조정 가능합니다. VPC를 늘리려 한도 증가를 요청하면 리전당 인터넷 게이트웨이 한도도 같은 양만큼 함께 올라가므로, VPC와 게이트웨이를 짝지어 늘려야 하는 상황에서 두 한도를 따로 챙길 필요가 없습니다.

#4동작 과정

  1. 한도 확인VPC, 서브넷, 라우팅 테이블, 보안 그룹 등 리소스별 기본 개수 한도를 표에서 확인합니다. 그래서 지금 설계가 어느 한도에 닿는지 미리 알 수 있습니다.
  2. 조정 가능 여부 판단항목별로 조정 가능 여부와 상한을 확인하고, 리전 단위 적용인지 계정 단위인지 구분합니다. 그래서 어떤 한도는 늘릴 수 있고 어떤 것은 설계로 피해야 하는지 판단합니다.
  3. 증가 요청과 반영조정 가능한 항목에 대해 한도 증가를 요청하면 해당 리전의 관련 자원 한도까지 함께 조정됩니다. 그래서 리소스를 대량으로 두는 설계도 한도 안에서 진행할 수 있습니다.

#5한 줄 요약

VPC 리소스별 기본 한도와 조정 규칙을 정리해, 한도에 맞춘 설계와 필요한 증가 요청을 가능하게 하는 것
