#1문제 상황

AWS 보안 분야는 매우 넓다. 클라우드 인프라 보안, 데이터 암호화, 접근 제어, 규정 준수, 사고 대응까지 다양한 영역을 다룬다. 따라서 시험을 준비할 때 어떤 부분에 가중치를 두고 공부해야 하는지, 모든 AWS 서비스를 알아야 하는 것은 아닌지 불명확한 경우가 생긴다.

#2핵심 질문

AWS Certified Security - Specialty(SCS-C03) 시험에서 실제로 출제되는 보안 영역은 몇 개이고, 각 영역별로 얼마나 비중 있게 출제되며, 어떤 AWS 서비스들이 시험 범위에 포함되는가?

#3동작 예시

SCS-C03 시험은 6개 도메인으로 나뉜다. 각 도메인마다 배점이 정해져 있고(예: 도메인 A는 전체의 23%), 각 도메인 내에서 출제 대상이 될 AWS 서비스의 목록(In-Scope)과 대상이 아닐 서비스(Out-of-Scope)가 명시되어 있다. 예를 들어 'IAM 및 계정 관리' 도메인에서는 IAM, STS, Cognito가 In-Scope이지만, AppStream은 Out-of-Scope다.

#4동작 과정

  1. 도메인 구성 파악6개 도메인(탐지, 사고 대응, 인프라 보안, IAM, 데이터 보호, 보안 거버넌스)이 정의되고 각각 배점이 할당된다.
  2. 서비스 범위 확인각 도메인별로 출제 대상 서비스와 대상이 아닌 서비스 목록을 확인하여 공부 방향을 결정한다.
  3. 학습 우선순위 설정배점이 높은 도메인과 그 안의 In-Scope 서비스에 집중하고, Out-of-Scope 항목은 제외한다.

#5한 줄 요약

이 시험무한정한 AWS 보안 지식이 아니라 정확하게 정의된 6개 도메인과 그 안의 특정 서비스들에 대한 깊이 있는 이해를 검증하는 것

책임 공유 모델과 Well-Architected 보안 기둥

AWS는 클라우드 '자체'의 보안을 맡고 고객은 클라우드 '안'에 올린 데이터·설정·접근권한의 보안을 맡는다는 경계 구분이며, 그 고객 몫을 설계 원칙으로 정리한 것이 Well-Architected 보안 기둥이다.

#1문제 상황

온프레미스 환경에서는 기업이 네트워크 케이블부터 데이터 센터 물리 보안까지 모든 것을 직접 관리한다. 하지만 클라우드 환경에서는 AWS가 데이터 센터, 전원, 네트워크 장비, 하드웨어를 관리한다. 그렇다면 클라우드로 옮기면 보안 책임이 전부 AWS에 있는 걸까? 아니다. 고객이 남은 보안 책임을 져야 하는데, 그 경계가 불명확하면 보안 구멍이 생긴다.

#2핵심 질문

AWS가 맡는 보안 책임과 고객이 맡아야 할 보안 책임의 경계는 어디인가?

#3동작 예시

책임 공유 모델은 이렇게 나뉜다. AWS는 호스트 운영체제, 데이터 센터 접근 제어, 물리 보안, 네트워크 인프라를 맡는다. 고객은 EC2 인스턴스 위에 설치한 애플리케이션, 데이터베이스 안의 데이터, IAM 정책, 암호화 키 관리를 맡는다. S3 버킷을 예로 들면, AWS는 S3 서비스 자체의 버그를 없애고 가용성을 보장하는 일을 하고, 고객은 누가 그 버킷에 접근할 수 있는지(버킷 정책), 그 버킷 안의 데이터를 암호화할지 말지를 결정해야 한다.

#4동작 과정

  1. AWS의 책임 영역클라우드 '자체'의 보안을 담당한다. 인프라, 물리 보안, 서비스 가용성, 기본 네트워크 보안을 AWS가 설계하고 운영한다.
  2. 고객의 책임 영역클라우드 '안에 올린' 것들의 보안을 담당한다. IAM 정책 설정, 데이터 암호화, 네트워크 설정, 애플리케이션 보안을 고객이 구현한다.
  3. Well-Architected 보안 기둥AWS가 고객의 책임 영역을 설계 원칙으로 정리한 것이 'Well-Architected 보안 기둥'이다. 이를 따르면 클라우드 환경에서 고객 몫의 보안을 체계적으로 구현할 수 있다.

#5한 줄 요약

AWS 인프라와 고객의 데이터·설정 보안의 책임을 명확히 나누어, 각자 자신의 영역에 집중하도록 하는 것

1시험 기준과 AWS 보안 모델01-03

AWS 요청의 해부: 계정·리전 경계, ARN, SigV4 서명, 인증과 권한 부여의 분리

모든 AWS API 호출은 ARN으로 대상을 가리키고 SigV4로 서명되어 '누구인지(인증)'를 증명한 뒤, 별도로 정책이 '무엇을 해도 되는지(권한 부여)'를 계정·리전 경계 안에서 판정하는 구조다.

#1문제 상황

사용자가 AWS API를 호출할 때, 시스템은 "이 사람이 정말 자신이 주장하는 사람인가?"와 "이 사람이 이 작업을 하도록 허가받았는가?"라는 두 질문을 독립적으로 검증해야 한다. 이전에 이 두 검증이 섞여 있으면, 한 가지만 실패해도 정책을 올바르게 평가할 수 없다.

#2핵심 질문

AWS API 호출 때 누가 요청하는지 증명하고, 그 사람이 그 작업을 할 권한이 있는지 확인하는 과정이 어떻게 분리되어 있는가?

#3동작 예시

요청이 들어오면 세 단계를 거친다. 첫째, 요청이 아마존이 정말 보낸 요청인지 SigV4 서명으로 검증한다. 둘째, 요청의 아이덴티티(누가 보냈는지)를 조회한다. 셋째, 그 아이덴티티에 연결된 정책들을 찾아 요청된 작업(예: "s3:GetObject")을 그 정책들이 명시적으로 허가했는지 확인한다. ARN(Amazon Resource Name)은 대상 자원을 가리키는 주소이고, 계정과 리전은 정책 평가의 경계다.

#4동작 과정

  1. 요청 도착 및 서명 검증모든 AWS API 호출은 SigV4 서명(디지털 서명)을 포함한다. AWS는 이 서명을 확인하여 요청이 합법적인 자격 증명으로 보내졌는지 검증한다.
  2. 아이덴티티(인증) 확인서명이 유효하면, AWS는 어떤 IAM 사용자·역할·루트 계정이 이 요청을 보냈는지 파악한다. 이것이 "누구인가?"의 답이다.
  3. 정책 평가(권한 부여)그 아이덴티티에 부여된 모든 정책(연결된 정책, 인라인 정책, 신뢰 정책)을 모아 요청된 작업(예: s3:PutObject)과 대상 ARN이 정책의 Effect: Allow에 명시되어 있는지 확인한다. 이 평가는 요청의 계정과 리전 내에서만 유효하다.

#5한 줄 요약

인증(서명 검증으로 누구인지 파악)과 권한 부여(정책으로 무엇을 할 수 있는지 판정)를 분리하여, 각 단계가 독립적으로 동작하고 실패 사유가 명확하도록 하는 것

루트 사용자·IAM 사용자·액세스 키: 장기 자격 증명과 계정 보안 기준

계정을 만들 때 생기는 루트 사용자와 사람이 쓰는 IAM 사용자, 그리고 만료되지 않는 액세스 키를 어떻게 보호하고 최소한으로만 쓰는지 다룬다.

#1문제 상황

AWS 계정을 만들 때 생기는 루트 사용자(root user)는 계정의 모든 권한을 가진다. 초기 설정이나 계정 복구 같은 특수 작업에만 필요하지만, 편의상 루트 사용자로 일상 업무를 하는 팀도 있다. 그러면 루트 자격 증명이 많은 사람에게 공유되고, 한 번 탈취되면 계정 전체가 위험해진다.

#2핵심 질문

계정 내 여러 사람이 각각 다른 권한을 가지고 접근하되, 루트 계정 자격 증명은 최소한으로 보호하려면 어떻게 해야 하는가?

#3동작 예시

IAM 사용자는 각 사람이나 애플리케이션마다 개별로 만드는 자격 증명이다. 각 IAM 사용자에게는 필요한 권한만 정책으로 부여한다. 액세스 키(Access Key ID와 Secret Access Key)는 IAM 사용자가 프로그래매틱(API 또는 CLI)으로 AWS에 접근할 때 쓰는 장기 자격 증명이다. 루트 사용자의 액세스 키는 만들지 않는 것이 권장 실무다. 대신 각 사람이 자신의 IAM 사용자로 작업하고, 루트 사용자는 계정 복구나 결제 설정 변경 같은 루트 권한이 필수인 작업에만 쓴다.

#4동작 과정

  1. IAM 사용자 생성각 팀원이나 서비스 별로 IAM 사용자를 만든다. 각 사용자는 고유의 자격 증명을 받는다.
  2. 권한 할당각 IAM 사용자에게 필요한 정책만 부여한다. 예를 들어 개발자는 EC2와 S3는 접근하되 IAM 정책 수정은 할 수 없도록 설정한다.
  3. 루트 보호루트 사용자는 암호를 강력하게 하고(비밀번호 20자 이상, 특수문자 포함), MFA(Multi-Factor Authentication)를 반드시 활성화하고, 루트 액세스 키는 생성하지 않는다. 루트가 필요한 작업만 루트로 수행한다.

#5한 줄 요약

이 체계루트 권한을 최소화하고 각 사용자에게 필요한 권한만 주되, 모든 작업을 개별 IAM 사용자로 추적 가능하게 하는 것

2인증: 누가 접근하는가02-02

IAM 역할·신뢰 정책과 AWS STS 임시 자격 증명

역할은 '누가 빌려 쓸 수 있는지'를 신뢰 정책으로 정해 두고, AssumeRole 로 짧게 살아 있는 임시 자격 증명을 발급받아 쓰는 방식이다.

#1문제 상황

IAM 사용자의 액세스 키는 만료되지 않는 장기 자격 증명이다. 액세스 키가 누출되면 그 키를 명시적으로 삭제할 때까지 악의적 접근이 계속될 수 있다. 또한 EC2 인스턴스 위의 애플리케이션에 액세스 키를 저장하면, 그 인스턴스가 해킹당할 때 키도 함께 노출된다.

#2핵심 질문

액세스 키를 저장하지 않으면서도, 특정 범위 안에서만 유효하고 자동으로 만료되는 임시 자격 증명을 어떻게 발급하는가?

#3동작 예시

IAM 역할(Role)은 "누가 이 역할을 빌려 쓸 수 있는가"를 신뢰 정책(Trust Policy)으로 정한다. 예를 들어 'EC2-App' 역할의 신뢰 정책에는 "EC2 서비스만 이 역할을 맡을 수 있다"고 기재된다. EC2 인스턴스가 시작될 때 이 역할을 받으면, AWS STS(Security Token Service)가 임시 자격 증명(임시 액세스 키 + 세션 토큰)을 발급한다. 이 임시 자격 증명은 기본 1시간 유효하고 자동으로 만료된다.

#4동작 과정

  1. 역할 및 신뢰 정책 정의IAM 역할을 만들고, 그 역할을 누가 맡을 수 있는지를 신뢰 정책으로 명시한다. 예: "arn:aws:iam::ACCOUNT:role/EC2-App"의 신뢰 정책에 EC2 서비스의 principal(정책 주체)을 등록한다.
  2. AssumeRole 요청EC2 인스턴스가 시작될 때 자동으로 이 역할을 맡는다(AssumeRole 호출). AWS STS가 이를 감지하고 신뢰 정책을 확인한다.
  3. 임시 자격 증명 발급STS가 임시 액세스 키, 시크릿 키, 세션 토큰, 만료 시각을 포함한 임시 자격 증명을 발급한다. 인스턴스의 애플리케이션은 액세스 키를 저장할 필요 없이 메타데이터 서비스에서 이 임시 자격 증명을 주기적으로 갱신한다.

#5한 줄 요약

액세스 키라는 장기 자격 증명 대신 STS가 발급하는 단기 임시 자격 증명을 사용하여, 자격 증명의 노출 시간을 제한하고 관리 부담을 줄이는 것

외부 ID 연동: SAML 2.0·OIDC 페더레이션, IAM Roles Anywhere, AWS Directory Service

회사 IdP나 온프레미스 워크로드의 신원을 AWS 역할에 연결해, IAM 사용자를 만들지 않고도 AWS 에 로그인·접근하게 만드는 방법이다.

#1문제 상황

회사가 이미 자신의 아이덴티티 프로바이더(IdP)를 운영하고 있다면(Active Directory, Okta, Google Workspace 등), AWS의 IAM 사용자를 따로 만들고 암호를 관리하는 것은 중복이다. 또한 온프레미스 서버가 AWS 리소스에 접근해야 한다면, 그 서버에 장기 자격 증명을 저장하기는 위험하다.

#2핵심 질문

회사의 기존 신원 관리 시스템의 사용자 신원을 AWS 역할과 연결하여, AWS에서 새로운 사용자를 만들지 않고도 인증과 권한을 부여할 수 있는가?

#3동작 예시

SAML 2.0 페더레이션은 회사 IdP(예: Active Directory)가 사용자를 인증한 후, SAML Assertion이라는 토큰을 AWS에 전달한다. AWS는 이 어서션을 검증한 후 해당 사용자를 IAM 역할에 매핑하고 임시 자격 증명을 발급한다. OIDC는 같은 역할을 하지만 OpenID Connect 표준을 쓴다. IAM Roles Anywhere는 X.509 인증서를 가진 온프레미스 서버도 AWS STS와 통신하여 임시 자격 증명을 받을 수 있게 한다. AWS Directory Service는 AWS 클라우드 안에 Active Directory를 구축하거나 기존 온프레미스 AD와 연결하는 서비스다.

#4동작 과정

  1. 페더레이션 신뢰 설정AWS에 외부 IdP를 신뢰하는 역할(예: 'SAML-FederatedRole')을 만든다. 이 역할의 신뢰 정책에 회사 IdP의 메타데이터를 등록한다.
  2. 사용자 인증사용자가 회사 IdP(예: Active Directory)에 로그인한다. IdP는 사용자를 검증하고 SAML Assertion을 생성한다.
  3. AWS 임시 자격 증명 발급SAML Assertion을 들고 AWS에 접근하면, AWS STS가 Assertion의 서명을 검증한 후 미리 설정된 역할로 매핑하여 임시 자격 증명을 발급한다. 사용자는 AWS IAM 사용자 계정 없이도 AWS에 접근한다.

#5한 줄 요약

이 연동회사의 기존 신원 시스템의 신원을 AWS 역할에 연결하여, IAM 사용자 중복 관리를 피하고 외부 조직(파트너사, 온프레미스)도 AWS에 접근 가능하게 하는 것

AWS IAM Identity Center: ID 소스·권한 집합·액세스 포털

여러 계정의 사람 접근을 한곳에서 관리하는 서비스로, ID 소스에서 사용자를 가져와 권한 집합을 할당하고 액세스 포털로 로그인시킨다.

#1문제 상황

회사가 여러 AWS 계정을 운영한다면, 한 사람이 여러 계정에 접근할 때마다 각 계정의 IAM 사용자를 만들고 암호를 따로 관리해야 한다. 계정이 10개, 사람이 50명이면 최대 500개의 IAM 사용자를 관리하게 된다. 또한 사람이 팀을 옮기거나 회사를 나가면 모든 계정에서 그 사람의 접근을 일일이 삭제해야 한다.

#2핵심 질문

여러 AWS 계정에 걸쳐 한 사람의 접근을 한곳에서 관리하면서도, 계정별·역할별 권한을 유연하게 할당할 수 있는가?

#3동작 예시

AWS IAM Identity Center는 이런 문제를 푼다. 먼저 ID 소스(Identity Source)에서 사용자를 가져온다. ID 소스는 Internal Directory(AWS 내부 사용자 저장소), 외부 IdP(Active Directory, Okta), AWS Directory Service 중 하나다. 그 다음 권한 집합(Permission Set)을 정의한다. 권한 집합은 "이 권한 모음은 여러 계정의 어떤 역할에 해당하는가"를 정의한다. 예를 들어 'Developer-PermissionSet'은 개발 계정에서 개발자 역할, 스테이징 계정에서 개발자 역할을 나타낼 수 있다. 마지막으로 액세스 포털(Access Portal)에서 사용자는 로그인하면 자신이 접근 가능한 계정과 역할 목록을 본다.

#4동작 과정

  1. ID 소스 등록회사의 신원 저장소(Internal Directory, AD, Okta 등)를 IAM Identity Center에 연결한다. 사용자와 그룹이 자동으로 동기화된다.
  2. 권한 집합 정의"개발자", "관리자" 같은 권한 집합을 만든다. 각 권한 집합은 여러 계정의 IAM 역할(또는 정책)에 매핑된다.
  3. 계정별 권한 할당특정 사용자나 그룹을 특정 계정의 특정 권한 집합에 할당한다. 예: "Alice 사용자 → 개발 계정의 개발자 권한 집합". 그러면 Alice는 액세스 포털에 로그인했을 때 해당 계정의 역할을 자동으로 맡는다.

#5한 줄 요약

여러 AWS 계정의 접근을 한곳의 ID 소스에서 관리하고, 권한 집합이라는 재사용 가능한 권한 모음으로 대규모 조직의 접근 제어를 단순화하는 것

Amazon Cognito: 사용자 풀과 자격 증명 풀로 앱 사용자 인증

앱 최종 사용자를 위한 인증 서비스로, 사용자 풀은 로그인과 토큰 발급을, 자격 증명 풀은 그 토큰을 AWS 임시 자격 증명으로 바꿔 준다.

#1문제 상황

앱이 사용자를 인증하려면 복잡한 로그인 로직을 직접 구축하거나 외부 서비스에 의존했다. 자체 구축하면 개발 비용이 크고, 세션 관리·암호 저장·MFA 같은 보안 요구사항을 놓치기 쉽다.

#2핵심 질문

모바일·웹 앱의 수백만 사용자를 안전하게 인증하고 AWS 리소스에 접근시키려면?

#3동작 예시

Cognito는 두 부분으로 이뤄진다. 사용자 풀(User Pool)이 사용자 등록·로그인을 처리해서 JWT 토큰(로그인 증명서)을 발급한다. 자격 증명 풀(Identity Pool)이 그 JWT 토큰을 받아서 임시 AWS 접근 키(AWS 리소스를 쓸 수 있는 임시 자격증명)로 교환한다. 앱 사용자는 사용자 풀에서 로그인하면 토큰을 받고, 그것을 자격 증명 풀에 제출하면 S3·DynamoDB 등을 직접 호출할 수 있는 임시 자격 증명을 얻는다.

#4동작 과정

  1. 사용자 풀에서 인증사용자가 앱에 아이디·비번을 입력하면 Cognito가 검증하고 JWT 토큰을 발급한다.
  2. 자격 증명 풀에서 교환앱이 그 JWT 토큰을 자격 증명 풀에 제출하면 Cognito가 임시 AWS 접근 키·비밀 키·세션 토큰을 준다.
  3. AWS 리소스 접근앱이 받은 임시 자격 증명으로 S3, DynamoDB, Lambda 등을 직접 호출할 수 있다.

#5한 줄 요약

Cognito는 앱 최종 사용자를 위한 인증 서비스로, 사용자 풀이 로그인과 토큰 발급을, 자격 증명 풀이 그 토큰을 AWS 임시 자격 증명으로 바꾼다.

인증 실패 진단: CloudTrail userIdentity·세션·MFA 조건 문제 해결

로그인이나 역할 전환이 막혔을 때 CloudTrail 의 userIdentity 필드로 '누가 어떤 자격 증명으로 호출했는지'를 확인해 원인을 좁히는 방법이다.

#1문제 상황

사용자 로그인이나 IAM 역할 전환이 막혔을 때 개발자는 "접근 거부됨"이라는 에러만 본다. 정확히 어디서·누가·왜 거부했는지는 알 수 없었다.

#2핵심 질문

실패한 인증·권한 호출의 구체적 원인을 어떻게 찾을까?

#3동작 예시

CloudTrail은 AWS의 모든 API 호출을 기록하는 감시 로그다. 실패한 로그인도 기록되는데, 그 기록의 userIdentity 필드에 "누가·어떤 자격 증명으로·어디서 호출했는가"가 정확히 담긴다. 이 필드의 type(IAMUser인지 AssumedRole인지), principalId(호출자 ID), accountId(계정), 그리고 errorCode·errorMessage를 함께 읽으면 MFA 빠짐, 정책 거부, 신뢰 관계 부재 같은 구체적 원인을 즉시 파악할 수 있다.

#4동작 과정

  1. CloudTrail 이벤트 조회AWS 콘솔의 CloudTrail 섹션에서, 또는 Athena로 SQL 쿼리해서 실패 시간대의 이벤트를 찾는다.
  2. userIdentity 필드 분석이벤트의 userIdentity.type, principalId, accountId를 확인해 호출자가 누구이고 어떤 자격 증명을 썼는지 파악한다.
  3. 에러 메시지와 조건 검토errorCode가 "AccessDenied", "UnauthorizedOperation", "InvalidParameterValue" 등 어떤 유형인지, Condition에 MFA 또는 IP 제약이 있었는지 확인해 원인을 좁힌다.

#5한 줄 요약

CloudTrail의 userIdentity 필드와 에러 메시지는 인증·권한 실패의 원인을 "누가·어디서·왜"라는 구체적 맥락으로 드러낸다.

3권한 부여: 무엇을 할 수 있는가03-01

IAM 정책 문서 문법: Effect·Action·Resource·Principal·Condition

JSON 한 장에 '누가(Principal) 무엇을(Action) 어디에(Resource) 어떤 조건에서(Condition) 허용/거부(Effect)'를 적는 것이 IAM 정책이다.

#1문제 상황

권한을 "누가 뭘 할 수 있나"라고 입으로 말했다. 일관성 없고 기록이 남지 않으며, 권한 감시나 감사가 불가능했다.

#2핵심 질문

복잡한 권한을 명확하게 한 문서로 정의하려면?

#3동작 예시

IAM 정책은 JSON 한 장이고, 다섯 가지 요소로 구성된다. Effect는 "Allow" 또는 "Deny". Principal은 누가(사용자, 역할, 계정, AWS 서비스). Action은 무엇을 하는가(s3:GetObject, ec2:TerminateInstances 같은 API 동작). Resource는 어디에 적용하는가(S3 버킷, EC2 인스턴스 같은 AWS 리소스). Condition은 옵션으로 "언제·누구일 때"를 추가로 제한한다(IP 주소, 시간, MFA 존재 여부 등).

#4동작 과정

  1. Effect와 Principal 결정허용할지 거부할지 정하고, 누가 이 정책을 받는지 명시한다.
  2. Action과 Resource 지정허용할 API 동작(Action)을 나열하고, 그 동작이 적용될 AWS 리소스(Resource)를 ARN(Amazon Resource Name·리소스 주소) 형태로 명시한다.
  3. Condition으로 세밀한 제약 추가옵션으로 조건 키(시간, IP, MFA 토큰 존재 등)를 추가해 권한을 더 제한한다.

#5한 줄 요약

IAM 정책은 Effect·Principal·Action·Resource·Condition 다섯 요소를 JSON으로 정의해 권한의 전체를 명시적으로 기록하는 규칙이다.

3권한 부여: 무엇을 할 수 있는가03-02

자격 증명 기반 정책과 리소스 기반 정책, 교차 계정 접근

권한은 '사람에 붙이는 정책'과 '물건에 붙이는 정책' 두 곳에서 나오며, 계정이 다르면 양쪽 모두에서 허용돼야 통과한다.

→ 03-03 참조

#1문제 상황

권한을 한 곳에만 정했다. 사용자나 역할에만 정책을 붙이거나 리소스에만 붙였다. 다른 AWS 계정의 사용자가 우리 S3 버킷에 접근해야 할 때는 어디에 권한을 주는지 불분명했다.

#2핵심 질문

다른 AWS 계정의 사용자가 우리 리소스에 접근할 때 권한은 어디에 정할까?

#3동작 예시

권한은 두 곳에서 나온다. 자격 증명 기반 정책(Identity-Based Policy)은 IAM 사용자·역할에 붙는 정책으로 "이 사람이 뭘 할 수 있다"를 정의한다. 리소스 기반 정책(Resource-Based Policy)은 S3 버킷, SQS 큐, IAM 역할의 신뢰 정책 같은 리소스에 붙는 정책으로 "이 리소스를 누가 쓸 수 있다"를 정의한다. 교차 계정 접근(다른 AWS 계정의 주체가 우리 리소스를 사용하는 경우)이 필요하면, 접근자 측에는 "상대 계정의 리소스를 쓸 수 있다"는 자격 증명 기반 정책이 있어야 하고, 리소스 측에는 "저 계정의 주체들을 받아들인다"는 리소스 기반 정책이 있어야 한다. 둘 다 "Allow"여야 접근이 가능하다.

#4동작 과정

  1. 자격 증명 기반 정책 부여다른 계정의 사용자 또는 역할에 "arn:aws:s3:::partner-bucket/*"에 대한 s3:GetObject 권한을 준다. 이는 "권한이 있다"는 신호일 뿐 아직 리소스 접근은 실행되지 않는다.
  2. 리소스 기반 정책 설정우리 S3 버킷의 버킷 정책에 "저 계정의 사람들을 허용한다"는 문구를 명시적으로 추가한다.
  3. 양쪽 정책 검증API 호출 시 AWS는 주체 쪽 정책과 리소스 쪽 정책을 모두 검사한다. 하나라도 "Deny"면 거부되고, 둘 다 "Allow"거나 명시하지 않은 상태여야 접근이 허가된다.

#1문제 상황

권한 정책이 여러 곳에서 겹칠 때 누가 이기는지 불명확했다. 자격 증명 정책도 있고, 리소스 정책도 있고, 조직 상위 정책도 있으면 최종 결과가 무엇인지 계산하기 어려웠다.

#2핵심 질문

여러 정책이 겹칠 때 AWS는 최종 권한을 어떻게 결정할까?

#3동작 예시

AWS의 정책 평가는 정해진 순서와 규칙을 따른다. 가장 중요한 규칙은 "명시적 Deny(명시적 거부)가 우선"이다. 어떤 정책이든 하나라도 "Deny"라고 명시했으면 모든 다른 "Allow"는 무시되고 거부된다. 명시적 Deny가 없으면, 조직의 SCP(Service Control Policy), 리소스 기반 정책, 자격 증명 기반 정책, 권한 경계(Permission Boundary·권한의 상한선), 세션 정책(임시 자격 증명에 붙는 정책)을 순서대로 검사한다. 모두 "Allow"이거나 정책이 없는 상태여야(implicit allow) 최종 허용된다.

#4동작 과정

  1. 명시적 거부 우선 검사모든 정책에서 "Deny"가 있는지 먼저 확인한다. 하나라도 있으면 평가를 중단하고 "Access Denied"를 반환한다.
  2. 조직·리소스·자격 증명 정책 순차 검사명시적 Deny가 없으면 SCP(조직 차원의 상위 정책), 리소스 기반 정책, 자격 증명 기반 정책을 순서대로 검사한다. 모두 "Allow"이거나 정책이 없어야 진행된다.
  3. 권한 경계와 세션 정책 최종 확인권한 경계(역할이 갖를 수 있는 최대 권한)와 세션 정책(임시 토큰의 추가 제약)을 통과해야 최종 허용된다.

조건 키로 만드는 ABAC와 데이터 경계(Data Perimeter)

태그·조건 키를 기준으로 권한을 정하고(ABAC), 신뢰하는 아이덴티티·리소스·네트워크 밖으로 데이터가 새지 않도록 울타리를 치는 방식이다.

→ 03-01 참조

#1문제 상황

권한을 주려면 매번 정책을 추가하거나 수정해야 했다. 개발팀 인원이 10명 늘면 정책에 그 10명을 일일이 추가했다. 조직 구조가 바뀌거나 사람이 이동할 때마다 정책 관리가 복잡했다.

#2핵심 질문

권한 정책을 수정하지 않으면서도 조직 변화에 맞춰 권한을 자동으로 확장할 수 있을까?

#3동작 예시

ABAC(Attribute-Based Access Control)는 태그(key-value 쌍 형태의 속성)를 기준으로 권한을 정한다. 모든 개발자에게 "department=engineering" 태그를 붙이고, 정책의 Condition에 "aws:PrincipalTag/department":"engineering"이라고 쓰면, 그 태그를 가진 모든 주체가 자동으로 권한을 얻는다. 새로운 개발자가 와도 태그만 달면 정책 수정 없이 권한을 받는다. 데이터 경계(Data Perimeter)는 이를 확장해서, 신뢰하는 자격 증명·리소스·네트워크만 데이터에 접근하도록 울타리를 치는 방식이다.

#4동작 과정

  1. 태그 기반 분류조직 구조를 나타내는 태그(team, project, cost-center, environment 등)를 사용자·역할·리소스에 붙인다.
  2. 조건 키 정책으로 권한 정의정책의 Condition에 "aws:PrincipalTag" 또는 "aws:ResourceTag"를 사용해 특정 태그를 가진 주체와 리소스만 권한을 받도록 작성한다.
  3. 데이터 경계로 신뢰 영역 제한신뢰할 수 있는 자격 증명 출처(예: 기업 계정), 리소스 위치(예: 특정 VPC), 네트워크(예: 기업 네트워크)를 명시적으로 허용하고, 그 밖의 요청은 명시적으로 거부한다.

#5한 줄 요약

ABAC와 데이터 경계는 태그와 조건 키로 권한을 동적으로 관리하고, 신뢰 영역 밖의 접근을 차단하는 확장성 높은 보안 모형이다.

역할 유형 구분: 서비스 역할·서비스 연결 역할·인스턴스 프로파일·실행 역할

#1문제 상황

권한이 필요한 것은 사람뿐이라고 생각했다. EC2 인스턴스나 Lambda 함수가 AWS 리소스를 써야 할 때 고정된 Access Key(사용자 자격 증명)를 코드에 직접 박아 넣었다. 자격 증명이 유출되면 위험하고, 회전(주기적 교체)이 어렵다.

#2핵심 질문

EC2, Lambda, 컨테이너 같은 워크로드와 AWS 서비스가 임시 자격 증명을 안전하게 받아서 쓰려면?

#3동작 예시

IAM 역할은 인간이 아닌 것들(워크로드, AWS 서비스)을 위한 임시 자격 증명을 발급하는 메커니즘이다. 역할은 네 가지 유형이 있다. 서비스 역할(Service Role)은 EC2나 Lambda가 맡는 역할이고, 신뢰 정책에 "ec2.amazonaws.com" 같은 AWS 서비스를 명시한다. 서비스 연결 역할(Service-Linked Role)은 RDS, ECS 같은 AWS 관리 서비스가 자동으로 만들고 관리하는 역할이다(예: RDS가 CloudWatch에 로그를 쓰기 위해 자동으로 만든다). 인스턴스 프로파일(Instance Profile)은 EC2 인스턴스에만 붙이는 컨테이너이고, 그 안에 서비스 역할을 넣는다. 실행 역할(Execution Role)은 ECS 작업이나 Fargate 컨테이너가 맡는 역할이다.

#4동작 과정

  1. 신뢰 정책 설정역할의 신뢰 정책(Trust Policy)에 "AWS 서비스 ec2.amazonaws.com이 이 역할을 맡을 수 있다" 또는 "ECS 작업이 이 역할을 맡을 수 있다"는 Principal을 명시한다.
  2. 권한 정책 부여역할에 "s3:GetObject", "dynamodb:Query", "cloudwatch:PutMetricData" 같은 권한 정책을 붙여 워크로드가 할 수 있는 일을 정의한다.
  3. 워크로드에 역할 할당EC2를 생성할 때 인스턴스 프로파일을 지정하고, Lambda 함수를 만들 때 실행 역할 ARN을 지정한다. AWS는 자동으로 임시 자격 증명을 생성하고 주입한다.

#5한 줄 요약

IAM 역할은 워크로드와 AWS 서비스가 임시 자격 증명을 얻는 메커니즘이며, 역할 유형(서비스 역할, 서비스 연결 역할, 인스턴스 프로파일, 실행 역할)에 따라 쓰임새와 관리 방식이 다르다.

#1문제 상황

기존에는 애플리케이션 코드에 "이 사용자가 이 문서를 볼 수 있는가" 같은 권한 판단 로직이 여러 곳에 흩어져 있었습니다. 백엔드 코드마다 다르게 구현되고, 권한 규칙을 바꾸려면 코드를 수정해서 다시 배포해야 합니다. 여러 마이크로서비스에서 권한 로직이 중복되고, 일관성을 유지하기도 어렵습니다.

#2핵심 질문

애플리케이션의 권한 판단 로직을 코드에서 빼내 한곳에서 정책으로 관리할 수 있을까요?

#3동작 예시

Amazon Verified Permissions는 Cedar라는 정책 언어를 사용하여 권한 규칙을 정의합니다. 앱 코드에서는 "이 사용자가 이 문서를 읽을 수 있나?"를 Verified Permissions 엔진에 질문하면, 엔진이 Cedar 정책을 평가하여 "allow" 또는 "deny"로 즉시 답변합니다. 권한 규칙을 바꾸려면 Cedar 정책만 수정하면 되고, 앱 코드는 손댈 필요가 없습니다.

#4동작 과정

  1. 권한 판단 요청애플리케이션이 "principal(주체)=사용자A, action(행동)=Read, resource(자원)=문서B"를 Verified Permissions에 보냅니다.
  2. 정책 평가서비스가 Cedar로 작성된 정책들을 순서대로 평가하여 이 조합이 허용되는지 확인합니다.

암호화 기본과 봉투 암호화(Envelope Encryption)

데이터는 빠른 데이터 키로 암호화하고 그 데이터 키를 다시 상위 키(KMS 키)로 감싸서 보관하는 2단 구조가 봉투 암호화이며, AWS 저장 데이터 암호화의 기본 원리다.

#1문제 상황

데이터를 암호화하려면 암호화 키가 필요하다. 문제는 그 키 자체를 어디에 어떻게 보관할지다. 키가 노출되면 암호화된 데이터도 함께 무의미해진다.

#2핵심 질문

암호화된 데이터의 키도 안전하게 보관하려면 어떻게 해야 할까?

#3동작 예시

데이터를 빠른 데이터 암호화 키(DEK)로 암호화하고, 그 데이터 키를 상위 마스터 키(KMS 키)로 다시 암호화해 보관한다. 데이터와 암호화된 데이터 키가 함께 저장된다.

#4동작 과정

  1. 데이터 암호화효율성이 좋은 데이터 암호화 키(DEK)로 실제 데이터를 암호화한다.
  2. 키 암호화그 데이터 키를 더 강력한 마스터 키(상위 키, 일반적으로 KMS 키)로 암호화해 보관한다.
  3. 복호화필요할 때 마스터 키로 데이터 키를 먼저 복호화한 후, 그 데이터 키로 실제 데이터를 복호화한다.

KMS 접근 제어: 키 정책·grant·교차 계정 사용·권한 진단

KMS 키 사용 권한은 키 정책이 뿌리이고 IAM 정책과 grant 가 그 위에서 권한을 위임하며, 교차 계정 사용은 키 정책과 상대 계정 IAM 정책이 모두 허용해야 성립한다.

→ 03-02 참조

#1문제 상황

일반 리소스는 IAM 정책만으로 접근 제어가 끝난다. KMS 키는 다르다. IAM 정책만으로는 충분하지 않다.

#2핵심 질문

IAM 정책만으로는 암호화 키의 접근을 충분히 제어할 수 없다면 어떻게 해야 할까?

#3동작 예시

KMS 키의 접근은 키 정책(key policy)이 기초가 되고, 그 위에 IAM 정책과 grant(임시 권한)가 올라간다. 모든 계층이 허용해야 실제로 사용할 수 있다.

#4동작 과정

  1. 키 정책 설정키 자체에 정책을 붙여서 "누가 이 키를 사용할 수 있는가"를 정한다.
  2. IAM과 grant 위임키 정책이 허용한 범위 내에서 IAM 정책으로 일반 권한을 부여하고, grant로 임시 권한을 위임한다.
  3. 교차 계정 접근A 계정의 사용자가 B 계정의 KMS 키를 쓰려면 B 계정의 키 정책과 A 계정의 IAM 정책이 모두 명시적으로 허용해야 한다.

#5한 줄 요약

키 정책을 기초로 하여 IAM과 grant가 그 위에서 권한을 제어하는 다층 구조로, 같은 권한을 여러 계층에서 확인함으로써 오류와 악의적 접근을 방지하는 것

#2핵심 질문

#3동작 예시

  2. BYOK 방식외부에서 256비트 키 재료를 생성하고 AWS 도구로 임포트 하면 KMS가 그것을 저장하고 관리한다.
  3. 사용자 지정 키 스토어키 재료의 저장 위치를 CloudHSM 클러스터나 외부 관리 시스템에 두고 KMS가 그곳과 통신하여 암복호화 작업을 수행한다.

AWS CloudHSM: 클러스터·HSM 사용자·키 관리와 KMS 선택 기준

#1문제 상황

#2핵심 질문

내 VPC 안에서 전용 하드웨어 보안 모듈을 직접 운영하며 완전히 내가 통제해야 한다면?

#3동작 예시

#4동작 과정

  1. 클러스터 생성내 VPC의 각 가용성 영역에 전용 HSM 인스턴스를 배치한다.
  2. HSM 사용자와 키 관리HSM 관리자 사용자를 생성하고, 그 사용자로 로그인하여 HSM 사용자를 생성하고 키를 만든다.
  3. 애플리케이션 연동애플리케이션이 PKCS#11 표준 또는 CloudHSM 클라이언트를 통해 HSM과 통신하여 암복호화 작업을 수행한다.

#5한 줄 요약

AWS가 관리하는 공유 하드웨어 대신 내 VPC 안에 전용 하드웨어 보안 모듈을 직접 배치하여 키 재료와 암복호화 정책을 100% 내가 통제하는 것

인증서 관리: ACM 발급·검증·갱신과 AWS Private CA 계층·폐기

ACM 은 공인 TLS 인증서를 도메인 소유 검증으로 발급하고 자동 갱신해 주며, 내부용 인증서는 AWS Private CA 로 루트·하위 CA 계층을 세워 발급·폐기한다.

#1문제 상황

TLS 인증서는 공인 인증 기관(CA)에서 발급받거나 내가 직접 만든다. 공인 인증서는 도메인 소유권 증명이 필요하고 유효 기간이 정해진다. 내부용 인증서는 신뢰할 기관이 없으면 클라이언트마다 수동으로 설정해야 한다.

#2핵심 질문

공인 인증서의 자동 발급과 갱신, 그리고 내부용 계층적 인증서 체계를 AWS에서 어떻게 관리할까?

#3동작 예시

ACM은 도메인 소유권을 검증하여 공인 TLS 인증서를 발급하고 자동 갱신한다. AWS Private CA는 내 루트 CA를 AWS에서 생성 및 관리하고, 그 루트 CA 아래에 하위 CA를 만들어 내부 서비스용 인증서를 발급한다.

#4동작 과정

  1. ACM도메인을 등록하면 ACM이 소유권을 검증(이메일 또는 DNS 레코드)하고 공인 인증서를 발급한 후 만료 30일 전에 자동으로 갱신한다.
  2. Private CA 계층 구축AWS Private CA 루트 CA를 생성하고, 그 아래에 하위 CA를 만든다.
  3. 내부 인증서 발급 및 폐기하위 CA에서 내부 서비스나 클라이언트용 인증서를 발급하고, 필요시 인증서를 폐기한다.

#5한 줄 요약

S3 접근 제어 계층: 버킷 정책·퍼블릭 액세스 차단·액세스 포인트·프리사인드 URL

S3 데이터 접근은 버킷 정책과 IAM, 퍼블릭 액세스 차단, 액세스 포인트, 한시적 프리사인드 URL 이 겹겹이 겹쳐 최종 허용 여부가 결정된다.

#1문제 상황

기존에는 S3 접근을 IAM 정책 하나로 제어했다. 그러나 실수로 버킷을 공개하거나, 루트 계정 자격증명으로 모든 데이터에 접근할 수 있다는 위험이 남는다. 보안 팀이 실제 설정을 모를 수도 있다.

#2핵심 질문

IAM 정책 하나만으로는 부족한 S3 접근을 여러 계층에서 동시에 제어할 수 있을까?

#3동작 예시

S3의 접근 제어는 버킷 정책(버킷 수준 규칙), 퍼블릭 액세스 차단(자동 차단 설정), 액세스 포인트(다중 진입점별 정책), 프리사인드 URL(한시적 허가)이 모두 "그리고(AND)"로 작동한다. 한 계층이라도 거부하면 접근은 불가능하다.

#4동작 과정

  1. 버킷 정책 확인요청자의 IAM 자격증명이 버킷 정책의 조건을 만족하는가 검사.
  2. 퍼블릭 액세스 차단 적용설정된 차단 규칙(예: 모든 퍼블릭 ACL 거부)이 요청을 차단하는지 확인.
  3. 액세스 포인트/프리사인드 URL 검증액세스 포인트 정책이나 프리사인드 URL의 만료 시간을 확인해 최종 허용 결정.

#5한 줄 요약

버킷 정책, 퍼블릭 액세스 차단, 액세스 포인트, 프리사인드 URL이 겹겹이 겹쳐 최종 접근 허용 여부를 결정하는 다층 제어 메커니즘

S3 암호화 선택: SSE-S3·SSE-KMS·버킷 키·SSE-C·클라이언트 측 암호화

S3 는 키를 누가 쥐느냐에 따라 SSE-S3·SSE-KMS(버킷 키로 KMS 호출 절감)·SSE-C·클라이언트 측 암호화로 나뉜다.

#1문제 상황

기존에는 S3에 저장된 데이터가 암호화되지 않은 채로 남을 수 있다. AWS 계정에 접근하면 누구나 평문 데이터를 읽을 수 있다. 규정에서 저장 중 암호화를 요구하면, 어떤 방식으로 암호화할지 반드시 선택해야 한다.

#2핵심 질문

S3에 저장될 때 암호화 키를 누가 관리하느냐에 따라 어떻게 암호화 방식이 달라질까?

#3동작 예시

SSE-S3는 AWS가 키를 관리하고, SSE-KMS는 AWS Key Management Service가 키를 관리하며(감사 기록 남음), SSE-C는 클라이언트가 매번 암호화 키를 제공하고, 클라이언트 측 암호화는 데이터가 S3에 도착하기 전에 이미 암호화된다. 키 소유권 범위가 다르다.

#4동작 과정

  1. 데이터 전송클라이언트가 S3에 데이터를 업로드할 때 암호화 방식을 명시하거나 기본값 사용.
  2. S3 측 암호화 적용SSE-S3 또는 SSE-KMS인 경우 S3 또는 KMS가 데이터를 암호화해 저장.
  3. 버킷 키 옵션SSE-KMS 사용 시 버킷 키를 활성화하면 KMS 호출을 줄여 비용 절감.

#5한 줄 요약

키 관리 책임(AWS, KMS 서비스, 클라이언트)에 따라 SSE-S3, SSE-KMS, SSE-C, 클라이언트 측 암호화 중 적절한 방식을 선택해 저장 중 암호화를 구현하는 것

무결성과 변경 불가: 버전 관리·S3 Object Lock·Glacier Vault Lock·체크섬·코드 서명

버전 관리와 Object Lock 같은 WORM 보존, 체크섬·서명으로 데이터가 지워지거나 몰래 바뀌지 않도록 못을 박는다.

#1문제 상황

기존에는 S3에 저장된 데이터가 삭제되거나 몰래 수정될 수 있다. 특히 규정 요구 사항이나 법적 보존 기간이 있다면 데이터 손상을 감지하고 방지해야 한다.

#2핵심 질문

저장된 데이터가 실제로 손상되지 않았고, 적절한 기간 동안 삭제되지 않도록 보장할 수 있을까?

#3동작 예시

버전 관리(Versioning)는 모든 변경 이력을 보존해 롤백 가능하게 하고, S3 Object Lock은 지정 기간 동안 삭제나 수정 자체를 불가능하게 못박으며(WORM: Write Once Read Many), 체크섬과 코드 서명은 업로드 후 데이터가 변조되지 않았음을 검증한다.

#4동작 과정

  1. 버전 관리 활성화모든 객체 변경 시마다 이전 버전을 보존해 이력 추적 가능.
  2. Object Lock/Vault Lock 설정지정된 보존 기간(Retention) 또는 법적 보유(Legal Hold) 동안 삭제·수정 차단.
  3. 체크섬·서명 검증업로드 후 저장된 데이터의 해시값이나 디지털 서명으로 무결성 확인.

#5한 줄 요약

버전 관리, Object Lock 같은 WORM 보존, 체크섬과 서명으로 데이터가 지워지거나 몰래 수정되지 않도록 보호하는 것

서비스별 저장 암호화: EBS·RDS·DynamoDB·EFS·FSx 와 기본 암호화 강제

블록·DB·파일 스토리지는 각자 KMS 기반 저장 암호화 옵션을 가지며, 계정 기본 암호화와 정책으로 미암호화 생성을 막는다.

→ 05-01 참조

#1문제 상황

기존에는 각 AWS 서비스(EBS, RDS, DynamoDB, EFS, FSx)가 독립적으로 동작하며, 저장 중 암호화 설정을 매번 개별적으로 활성화해야 한다. 실수로 암호화 없이 인스턴스나 데이터베이스를 만들 수 있다.

#2핵심 질문

각 서비스의 저장 암호화를 개별 설정하지 않고, 계정 전체에서 미암호화 리소스 생성을 애초에 막을 수 있을까?

#3동작 예시

EBS, RDS, DynamoDB, EFS, FSx 모두 KMS 기반 저장 암호화 옵션을 제공하며, 각 서비스별로 기본 암호화를 활성화하면 새로 생성되는 모든 리소스가 자동으로 암호화된다. 또한 SCP(서비스 제어 정책)나 IAM 정책으로 암호화 없는 리소스 생성을 아예 차단할 수 있다.

#4동작 과정

  1. 서비스별 기본 암호화 활성화각 서비스(EBS, RDS 등)의 계정 설정에서 기본 암호화 옵션 켬.
  2. KMS 키 지정각 서비스가 사용할 마스터 키(기본값 또는 고객 관리 키) 선택.
  3. 정책으로 강제SCP나 IAM 정책으로 암호화 미지정 리소스 생성 거부.

#5한 줄 요약

블록·데이터베이스·파일 스토리지 서비스에서 각각 KMS 기반 저장 암호화를 기본값으로 설정하고, 정책으로 미암호화 리소스 생성을 강제로 방지하는 것

수명 주기·보존·백업: S3 Lifecycle·Data Lifecycle Manager·AWS Backup·DataSync

데이터를 언제 옮기고 지우고 백업할지 규칙으로 자동화해 보존 요건과 비용을 동시에 지킨다.

#1문제 상황

기존에는 데이터를 수동으로 옮기거나 지우거나 백업해야 한다. 규정에서 요구하는 보존 기간과 실제 비즈니스 필요 기간이 다를 수 있고, 규칙을 빠뜨리면 규정 위반이나 불필요한 비용 낭비가 생긴다.

#2핵심 질문

데이터를 언제 어디로 옮기고, 언제 지우고, 언제 백업할지를 자동으로 실행할 수 있을까?

#3동작 예시

S3 Lifecycle은 객체 나이에 따라 자동으로 스토리지 클래스를 변경하거나 삭제하는 규칙이고, Data Lifecycle Manager는 EBS나 RDS 스냅샷 자동 생성·삭제 규칙이며, AWS Backup과 DataSync는 데이터를 다른 리전이나 계정으로 자동 복제한다.

#4동작 과정

  1. 라이프사이클 규칙 정의S3 Lifecycle이나 DLM으로 객체/스냅샷 이동·삭제 시점 및 조건 설정.
  2. 자동 실행규칙에 따라 AWS가 지정된 시간에 자동으로 작업 수행.
  3. 백업 정책 적용AWS Backup으로 주기적 백업, DataSync로 복제 자동화해 보존 요건·RTO·RPO 충족.

#5한 줄 요약

데이터 수명 주기와 백업 규칙을 자동화해 보존 규정 요건과 비용 최적화를 동시에 달성하는 것

7전송 중 데이터와 사설 연결07-01

VPC 격리 설계: 서브넷·라우팅·NAT·Transit Gateway 와 세분화 검증

퍼블릭/프라이빗 서브넷과 라우팅 테이블, NAT 게이트웨이, Transit Gateway 로 네트워크를 계층 분리하고 의도대로 격리됐는지 확인하는 설계 방법.

#1문제 상황

기존에는 EC2, RDS, Lambda 등이 모두 같은 네트워크 공간에 있으면 한 서비스가 침해되면 다른 모든 서비스에 바로 접근 가능하다. 누구나 누구에게나 접근할 수 있다.

#2핵심 질문

AWS 리소스들 사이에서 의도한 통신만 가능하고, 불필요한 통신은 원천 차단할 수 있을까?

#3동작 예시

퍼블릭 서브넷에는 인터넷 노출이 필요한 리소스(ALB, NAT 게이트웨이)만 두고, 프라이빗 서브넷에는 데이터베이스나 백엔드 서버를 두며, NAT 게이트웨이를 거쳐야만 프라이빗 리소스에서 인터넷 접근 가능하게 한다. Transit Gateway를 써서 VPC 여러 개를 연결하되, 라우팅 테이블로 각 리소스 간 흐름을 명시적으로 제어한다.

#4동작 과정

  1. 서브넷 계층화퍼블릭/프라이빗/격리 서브넷을 분리하고 각 역할 지정.
  2. 라우팅 테이블 설정각 서브넷의 라우팅 테이블로 트래픽 경로 명시(예: 프라이빗 서브넷은 NAT 게이트웨이 거쳐야만 아웃바운드 가능).
  3. Transit Gateway 및 격리 검증여러 VPC를 연결하되, 각 연결의 라우팅을 세분화하고, 보안 그룹·NACL로 최종 검증.

#5한 줄 요약

서브넷, 라우팅 테이블, NAT 게이트웨이, Transit Gateway로 네트워크를 의도한 대로 계층화하고 격리하는 것

전송 중 암호화 강제: ELB 보안 정책·TLS 종료 지점·서비스 내부 암호화

로드밸런서 TLS 정책과 종료 지점 선택, 서비스별 전송 중 암호화 옵션으로 평문 통신을 막는 통제.

#1문제 상황

기존에는 클라이언트와 서버 사이 통신이 HTTP(평문) 또는 TLS(암호화)로 이뤄질 수 있다. 평문 통신은 중간에 도청 가능하고, 구 TLS 버전은 취약점이 있을 수 있다.

#2핵심 질문

모든 통신을 현재 보안 기준에 맞는 TLS로 강제하고, 약한 프로토콜은 차단할 수 있을까?

#3동작 예시

ALB/NLB의 보안 정책(Security Policy)을 지정하면, 지원할 TLS 버전(예: TLSv1.2 이상) 및 암호 모음(Cipher Suite)이 정해진다. TLS 정책을 "ELBSecurityPolicy-TLS-1-2-2017-01" 같은 사전 정의 정책으로 설정하면, 그보다 낮은 버전 클라이언트 연결은 거부된다. 또한 HTTP 요청이 들어오면 HTTPS로 리다이렉트하는 규칙을 설정해 평문 통신을 원천 차단한다.

#4동작 과정

  1. 로드밸런서 TLS 정책 설정ELB 리스너에 보안 정책(Security Policy) 지정해 지원할 TLS 버전·암호 모음 결정.
  2. HTTP 리다이렉트HTTP 요청을 HTTPS로 자동 리다이렉트해 평문 통신 차단.
  3. 서비스 내부 암호화마이크로서비스 간 통신도 TLS로 암호화해 내부 트래픽 보호.

#5한 줄 요약

로드밸런서 TLS 정책과 HTTP 리다이렉트, 서비스 간 TLS 강제로 평문 통신을 완벽히 차단하는 것

인터넷을 거치지 않고 VPC 안에서 AWS 서비스나 타사 서비스에 사설로 접속하게 하고, 엔드포인트 정책으로 그 통로에서 허용할 API 를 제한하는 기능.

#1문제 상황

기존에 EC2 인스턴스에서 AWS 서비스(S3, DynamoDB, SNS 등)에 접속하려면 인스턴스가 인터넷에 나갔다가 AWS 서비스로 들어가야 했다. 이는 데이터가 공개 인터넷을 거치므로 네트워크 지연이 생기고, NAT Gateway 같은 비용이 드는 구성을 해야 했으며, 보안상 인터넷 경로에 노출되는 문제가 있었다.

#2핵심 질문

AWS 서비스에 접속할 때 인터넷을 거치지 않고 VPC 안 사설 네트워크만으로 접근할 수 있을까?

#3동작 예시

VPC 엔드포인트는 VPC 내부에 AWS 서비스로 가는 직통로를 만든다. EC2에서 S3에 접속하려 할 때, 인터넷 게이트웨이를 거치지 않고 VPC 안의 엔드포인트 인터페이스를 통해 곧바로 S3에 연결된다. 주소 이름이 S3 API 도메인으로 설정되어 있어서 애플리케이션 코드 변경 없이 작동한다.

#4동작 과정

  1. 엔드포인트 생성VPC와 서브넷 안에 엔드포인트 인터페이스(VPC 엔드포인트가 내부 네트워크 인터페이스)를 배치하고, 이를 대상 AWS 서비스(S3, DynamoDB 등)와 연결한다.
  2. 트래픽 라우팅EC2 인스턴스에서 해당 서비스 주소로 요청을 보내면 라우팅 테이블이 자동으로 트래픽을 엔드포인트로 보낸다.
  3. 정책 기반 필터링엔드포인트 정책에 따라 어떤 API 호출을 허용할지, 어떤 IAM 주체가 접근할 수 있을지를 제한한다.

하이브리드 연결: Site-to-Site VPN·Direct Connect·MACsec

온프레미스와 AWS 를 잇는 IPsec VPN, 전용 회선(Direct Connect), 회선 계층 암호화(MACsec) 의 보안 특성과 선택 기준.

#1문제 상황

기존에 온프레미스 데이터센터를 AWS와 연결하려면 공개 인터넷 경로를 사용했다. 이는 해킹 위험이 높고, 암호화 없이 데이터가 노출될 수 있으며, 전용 회선이 없어 불안정한 속도와 지연을 겪었다.

#2핵심 질문

온프레미스와 AWS 사이에 안전하고 안정적인 전용 연결을 어떻게 구성할까?

#3동작 예시

Site-to-Site VPN은 온프레미스의 고객 게이트웨이(회사 네트워크의 VPN 장비)와 AWS의 가상 프라이빗 게이트웨이(VPC의 VPN 종단점) 사이에 IPsec 터널을 만든다. 모든 데이터가 이 암호화된 터널을 통해 흐르므로 인터넷 경로에서도 보안을 유지한다.

#4동작 과정

  1. VPN 터널 수립고객 게이트웨이와 가상 프라이빗 게이트웨이가 IPsec 핸드셰이크(암호화 키 교환)를 하고 양방향 암호화 연결을 만든다.
  2. 트래픽 라우팅온프레미스 네트워크에서 AWS VPC 대역으로 가는 트래픽은 자동으로 VPN 터널로 라우팅된다.
  3. Direct Connect 선택VPN이 인터넷 기반이므로 지연이 일정하지 않은 경우, 전용 회선(Direct Connect)을 통해 AWS 데이터센터에 직결하면 일정한 성능과 더 높은 대역폭을 얻는다.

#5한 줄 요약

하이브리드 연결온프레미스와 AWS 사이에 암호화되고 격리된 통로를 만드는 것으로, VPN으로 빠르게 시작하거나 Direct Connect로 안정성과 성능을 보장합니다

원격 접근: AWS Client VPN 과 AWS Verified Access

사용자 단말에서 사내 리소스로 접속할 때 VPN 터널을 쓰는 방식과, VPN 없이 사용자·기기 신뢰 조건으로 매 요청을 검사하는 방식의 비교.

#1문제 상황

기존에 원격 직원이 회사 네트워크의 내부 리소스(데이터베이스, 파일 서버 등)에 접근하려면 VPN 클라이언트를 설치하고 VPN 서버에 연결해야 했다. 매번 VPN으로 접속해야 하는 번거로움이 있었고, VPN 설정이 복잡했으며, 기기 자체가 안전한지 확인할 수 없었다.

#2핵심 질문

사용자와 기기의 신뢰 상태를 먼저 검증한 후, VPN 없이 애플리케이션마다 접근을 제어할 수 있을까?

#3동작 예시

AWS Client VPN은 사용자의 노트북에 VPN 클라이언트를 설치해 VPN 터널을 통해 VPC 내부 리소스에 접근하는 기존 VPN 방식이다. AWS Verified Access는 VPN을 설치하지 않고, 각 요청 전에 사용자의 ID(예: SSO 로그인)와 기기의 상태(예: 안티바이러스 실행 중)를 검증한 후에만 요청을 VPC로 라우팅한다.

#4동작 과정

  1. Client VPN 경로클라이언트가 VPN 소프트웨어를 실행하고 VPN 서버에 접속한 후 VPC 내부 리소스에 터널을 통해 접근한다.
  2. Verified Access 경로사용자가 웹 요청을 보낼 때 중간의 Verified Access 엔드포인트가 사용자 ID와 기기 신뢰도를 확인한 후 요청을 통과시킨다.
  3. 제어의 차이Client VPN은 전체 터널 진입을 제어하고, Verified Access는 개별 애플리케이션 요청마다 신뢰 조건을 검사해 더 세밀한 제어가 가능하다.

#5한 줄 요약

AWS Client VPN과 Verified Access원격 사용자 접근의 보안 방식을 선택하는 것으로, VPN은 터널 기반 접근을 제공하고 Verified Access는 요청 단위 신뢰 검증을 통해 VPN의 복잡성을 제거합니다

보안 그룹과 네트워크 ACL: 상태 저장/비저장 차이와 트러블슈팅

보안 그룹은 인스턴스 단위의 상태 저장(허용 규칙만) 방화벽이고 네트워크 ACL은 서브넷 단위의 비저장(허용·거부, 번호 순 평가) 방화벽이라 응답 트래픽 처리 방식이 달라 접속 장애 원인이 갈린다.

#1문제 상황

기존에는 인스턴스 수준에서만 방화벽을 설정했고(보안 그룹), 서브넷 수준의 추가 필터링이 없었다. 인스턴스 간 또는 외부 트래픽이 복잡할 때 어느 계층에서 차단되는지 파악하기 어려웠고, 특정 프로토콜의 응답 트래픽이 차단될 수 있다는 개념이 없어 접속 장애를 진단하기 힘들었다.

#2핵심 질문

방화벽 규칙이 양방향 트래픽(요청과 응답)을 어떻게 다르게 처리해서 트래픽 손실이 생길까?

#3동작 예시

EC2 인스턴스가 외부 API에 HTTP 요청을 보낼 때, 보안 그룹은 아웃바운드 요청에 자동으로 응답 트래픽을 허용하지만 네트워크 ACL은 인바운드 규칙 목록에서 해당 응답 포트 번호를 찾아야만 응답을 받을 수 있다는 차이가 생긴다. 같은 설정이라도 보안 그룹은 작동하고 네트워크 ACL만 응답을 버린다.

#4동작 과정

  1. 보안 그룹 (상태 저장)아웃바운드 허용 규칙이 있으면, 돌아오는 응답 트래픽의 포트 번호나 출처를 자동으로 추적해 답복 규칙 없이도 응답을 받아들인다.
  2. 네트워크 ACL (비저장)인바운드·아웃바운드 규칙을 따로 평가하고, 응답이 돌아올 때도 인바운드 규칙 목록을 처음부터 점검한다. 응답 포트를 명시적으로 열어야 한다.
  3. 트러블슈팅보안 그룹만으로는 작동하지만 네트워크 ACL을 추가하면 차단되는 경우, 네트워크 ACL의 인바운드 규칙에서 응답 포트(에프메랄 포트)를 확인해야 한다.

#5한 줄 요약

보안 그룹과 네트워크 ACL인스턴스와 서브넷 계층에서 각각 다른 방식으로 상태를 추적하는 방화벽으로, 상태 저장 여부가 응답 트래픽 처리를 크게 다르게 하므로 함께 설정할 때 양쪽 규칙을 점검해야 합니다

AWS Network Firewall 과 Route 53 Resolver DNS Firewall

Network Firewall은 VPC 트래픽을 방화벽 엔드포인트로 라우팅해 상태 비저장·상태 저장 규칙으로 검사하고, Resolver DNS Firewall은 VPC에서 나가는 DNS 질의를 도메인 목록 기준으로 차단한다.

#1문제 상황

기존에는 보안 그룹과 네트워크 ACL로 IP와 포트 기반 필터링만 할 수 있었다. 트래픽의 내용(어떤 URL인지, 악성 도메인인지)을 검사할 수 없었고, DNS 기반의 위협을 막을 수 없었으며, VPC 전체 트래픽을 일관된 정책으로 검사할 중앙 집중식 방화벽이 없었다.

#2핵심 질문

VPC를 나가는 모든 트래픽을 깊게 검사하고, DNS 쿼리까지 도메인 정책으로 차단할 수 있을까?

#3동작 예시

AWS Network Firewall은 VPC를 나가는 모든 트래픽을 방화벽 엔드포인트를 통해 라우팅해 상태 기반 규칙(예: TCP 핸드셰이크 후에만 데이터 전송 허용)과 상태 비기반 규칙(예: 특정 도메인으로 가는 HTTPS 패킷 차단)을 동시에 검사한다. 같은 시간에 Route 53 Resolver DNS Firewall은 VPC 내부의 DNS 쿼리(내부 DNS 해석)를 가로채 이 도메인을 조회하는 것 자체를 차단할 수 있다.

#4동작 과정

  1. Network Firewall 규칙 평가트래픽이 방화벽 엔드포인트에 도착하면 상태 저장 세션 추적 후 정책(상태 저장·비저장 규칙)을 순서대로 적용한다.

기존에는 각 EC2 인스턴스를 수동으로 만들어서 개별적으로 패치를 적용하고 보안 설정을 구성했다. 이 방식은 매번 시간이 오래 걸리고, 설정하는 사람마다 누락이나 편차가 발생하며, 보안 기준을 일관되게 유지하기가 어려웠다.

#2핵심 질문

모든 EC2 인스턴스가 처음부터 같은 안전한 상태로 시작할 수 있을까?

#3동작 예시

기준이 되는 이미지(골든 AMI)에 최신 패치, 보안 설정, 필요한 소프트웨어를 한 번 적용한다. 이후 새 인스턴스를 만들 때마다 이 골든 AMI에서 시작하면 모든 인스턴스가 처음부터 같은 안전한 상태를 갖게 된다. EC2 Image Builder를 사용하면 이 과정을 자동화할 수 있어서, 기준 변경 후 새 버전을 자동으로 빌드·테스트·배포할 수 있다.

#4동작 과정

  1. 기준 이미지 구성기본 이미지에 최신 보안 패치, OS 설정, 필요한 소프트웨어를 적용해 골든 AMI(또는 컨테이너 이미지)를 만든다.
  2. 자동 빌드 및 테스트EC2 Image Builder를 설정해서 정의된 기준이 바뀔 때마다 새 이미지를 자동으로 빌드하고 보안 테스트를 실행한다.
  3. 배포 및 사용검증된 새 이미지를 프로덕션에 배포하고, 모든 새 인스턴스가 그걸 기반으로 시작하게 한다.

  2. 세션 시작 및 인증사용자가 Session Manager로 세션을 시작하면 IAM이 권한을 검증한 후 암호화된 채널을 열고, 브라우저 또는 CLI로 접속할 수 있게 한다.

#3동작 예시

#4동작 과정

#1문제 상황

  1. 최소 권한 역할 정의워크로드가 필요로 하는 API 권한을 나열하고 역할에 정책을 붙입니다. 예를 들어 Lambda 함수는 CloudWatch Logs에만 쓸 수 있도록 logs:CreateLogGroup, logs:CreateLogStream, logs:PutLogEvents만 허용합니다.

AWS CloudTrail: 관리·데이터·네트워크 활동 이벤트와 이벤트 기록

계정에서 누가 무엇을 언제 호출했는지 API 단위로 남기는 감사 로그로, 관리 이벤트·데이터 이벤트·네트워크 활동 이벤트 세 종류와 최근 90일치 이벤트 기록 조회를 제공한다.

#1문제 상황

AWS 계정에서 발생하는 모든 API 호출을 기록하지 않으면, 누가 무엇을 언제 실행했는지 추적할 수 없습니다. 과거에는 AWS 콘솔 로그인 기록이나 IAM 접근 키 감사 같은 제한된 정보만 얻을 수 있었습니다. 하지만 실제로는 수천 개의 API 호출이 매초 발생하고, 보안 사고나 실수 삭제가 발생해도 어느 권한자가 언제 어떤 API를 호출했는지 알 수 없었습니다.

#2핵심 질문

계정에서 모든 API 호출을 누가, 무엇을, 언제 실행했는지 파악할 수 있는 감사 증거를 남기려면 어떻게 해야 하는가?

#3동작 예시

특정 IAM 사용자가 EC2 인스턴스를 삭제했다고 가정합니다. CloudTrail은 TerminateInstances API 호출 시점에 누구(principal ARN)가 호출했는지, 어느 IP에서 호출했는지, 성공했는지 실패했는지 기록합니다. 이 기록을 통해 언제 누가 어떤 권한으로 삭제를 시도했는지 정확히 추적할 수 있습니다.

#4동작 과정

  1. 이벤트 발생 및 캡처AWS API 호출(관리 이벤트: EC2 시작, S3 권한 변경), 데이터 이벤트(S3 GetObject, DynamoDB 스캔), 네트워크 활동 이벤트(Route 53 쿼리) 등이 CloudTrail에 기록됩니다.

  3. 분석 및 감시CloudWatch Logs나 Athena로 이벤트를 검색·분석하고, EventBridge로 특정 API 패턴을 감지했을 때 자동 응답을 실행합니다.

AWS 인프라와 애플리케이션에서는 CloudTrail(API 호출)과 별도로 운영체제 로그, 애플리케이션 로그, 데이터베이스 쿼리 로그 등 수많은 로그가 발생합니다. 이 로그들이 각 서버에 분산되어 저장되면, 보안 사고 발생 시 각 서버에 접속해 로그를 수집해야 하고, 로그 보관 기간도 불일치하며, 민감정보(비밀번호, 신용카드 번호)가 노출될 위험이 있습니다.

#1문제 상황

다양한 로그 소스(CloudTrail, CloudWatch Logs, VPC 플로우 로그, 애플리케이션 로그)를 모아도 원본 로그 형식이 제각각입니다. CloudTrail은 JSON, 플로우 로그는 텍스트 필드, 애플리케이션 로그는 자유 형식입니다. 이 로그들을 함께 분석하려면 각각을 파싱해 일관된 형식으로 변환해야 하고, 여러 시스템의 로그를 연결해 상관 분석하려면 복잡한 쿼리를 작성해야 합니다.

#2핵심 질문

#4동작 과정

  1. 로그 수집 및 형식 통일CloudTrail Lake(이벤트 데이터 스토어)는 CloudTrail 이벤트를 자동으로 수집하고, Athena는 S3에 저장된 로그를 구조화된 테이블로 변환합니다. OpenSearch는 여러 로그 소스를 색인화해 통합 검색을 가능하게 합니다.
  2. SQL/쿼리 언어로 검색CloudTrail Lake와 Athena는 SQL, Logs Insights는 자체 쿼리 언어로 로그를 검색합니다. 예: SELECT * FROM events WHERE principal_arn LIKE '%suspicious-user%' AND event_time > timestamp('2024-01-01').
  3. 상관 분석 및 시각화검색 결과를 Managed Grafana나 OpenSearch Dashboards로 시각화해 공격 패턴, 이상 행동, 규정 위반을 한눈에 볼 수 있습니다.

#1문제 상황

기업은 AWS 로그뿐만 아니라 온프레미스 방화벽 로그, 타사 클라우드 공급자(Azure, GCP) 로그, SIEM 시스템 로그 등 여러 보안 소스에서 로그를 수집합니다. 하지만 각 소스가 서로 다른 스키마(필드 이름, 데이터 타입)를 사용하면, 로그를 한곳으로 모아도 분석이 어렵고, 같은 보안 이벤트를 여러 형식으로 봐야 하며, 통합 분석 도구를 구축하기 복잡해집니다.

#2핵심 질문

AWS, 온프레미스, 타사 클라우드의 보안 로그를 표준 스키마로 정규화해 한곳에 모으고 바로 분석하려면 어떻게 해야 하는가?

#3동작 예시

보안팀이 Palo Alto Networks 방화벽(온프레미스), AWS CloudTrail(클라우드), Okta(SaaS 인증)의 로그를 모두 수집합니다. Security Lake에 이들을 연결하면 OCSF(Open Cybersecurity Schema Framework) 표준 스키마로 자동 변환되어 모두 동일한 필드로 저장됩니다. 예: 모든 로그의 "user_name", "event_type", "severity" 필드가 일관되므로, 한 쿼리로 "높음 심각도 이벤트 중 이 사용자가 연루된 것" 을 모든 소스에서 검색할 수 있습니다.

#4동작 과정

  1. 로그 수집 및 자동 정규화Security Lake에 AWS 계정, 온프레미스 데이터소스, 타사 클라우드를 연결하면 자동으로 각 로그가 OCSF 표준으로 변환되어 전용 S3 데이터 레이크(Parquet 형식)에 저장됩니다.
  2. 통합 쿼리모든 로그가 같은 필드 이름을 사용하므로 Athena나 다른 SQL 도구로 한 번의 쿼리로 모든 소스를 함께 검색할 수 있습니다.
  3. 구독자 분석보안팀뿐 아니라 규정 준수팀, SOC(보안운영센터) 분석가 같은 구독자가 사전 정규화된 데이터를 곧바로 분석 도구에 전달해 별도의 데이터 파이프라인을 만들 필요가 없습니다.

#5한 줄 요약

AWS, 온프레미스, 타사 클라우드 보안 로그를 OCSF 표준 스키마로 자동 정규화해 전용 S3 데이터 레이크에 모으고, 구독자가 바로 SQL로 분석할 수 있게 하는 것

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 지표 수집CloudWatch가 EC2, RDS, Lambda 등 AWS 리소스의 CPU, 메모리, 요청 수, 오류율 같은 수치를 주기적으로 측정하고 저장합니다.
  2. 경보 평가설정한 임계값과 실시간 지표를 비교해서 조건을 만족하면 경보 상태로 전환합니다. 예를 들어 "CPU가 80% 초과 5분 지속"이면 경보를 울립니다.
  3. 알림 전달경보는 EventBridge 규칙으로 SNS, Lambda, SQS, 이메일 등 지정한 대상으로 자동 전달됩니다.

#4동작 과정

EC2, S3, RDS 등 리소스의 설정을 수작업으로 확인하고 수기로 수정해야 했습니다. 설정 변화를 놓치기 쉽고, 수백 개 리소스가 있을 때는 추적 불가능합니다. 보안 규칙이 언제 누가 어떻게 바꿨는지도 알 수 없습니다.

#2핵심 질문

모든 리소스의 설정을 계속 감시하고 규칙에 맞지 않으면 자동으로 바로잡을 수 있을까요?

#3동작 예시

Config는 보안그룹 규칙으로 "인바운드 포트 22(SSH)는 0.0.0.0/0에서 허용하면 안 됨"이라는 규칙을 설정해두었다고 가정합니다. 누군가 포트 22를 개방하면 Config가 비준수로 판단해 SSM 자동화로 그 규칙을 자동 삭제합니다.

#4동작 과정

  1. 설정 변화 기록리소스 생성, 변경, 삭제 이벤트를 감지해 설정 스냅샷을 자동으로 기록합니다. S3에 설정 이력을 저장하므로 언제 뭐가 바뀌었는지 추적 가능합니다.
  2. 규칙 기반 평가설정한 규칙(예: "보안그룹은 HTTPS만 허용", "RDS는 암호화 필수")과 비교해서 준수/비준수를 판단합니다.
  3. 자동 수정비준수 리소스가 발견되면 Systems Manager 자동화(Automation) 또는 Lambda로 설정을 자동 복구합니다.

→ 11-01 참조

#1문제 상황

CloudWatch, CloudTrail, VPC 흐름 로그, 경보 등을 설정했는데 데이터가 쌓이지 않거나 경보가 울리지 않을 때가 있습니다. 이 경우 원인을 찾기 위해 IAM 권한, KMS 키, 대상 설정 등을 수작업으로 하나씩 확인해야 합니다.

#2핵심 질문

#3동작 예시

CloudTrail이 S3 버킷으로 로그를 보내야 하는데 로그가 쌓이지 않는다고 가정합니다. 원인은 보통 세 가지: (1) CloudTrail의 IAM 역할에 S3 쓰기 권한이 없음, (2) S3 버킷의 정책이 CloudTrail을 거부함, (3) S3 암호화 KMS 키 정책에 CloudTrail이 없음. 순서대로 확인해 고치면 로그 기록이 시작됩니다.

#4동작 과정

  1. IAM 권한 확인CloudWatch에서 SNS로 메시지를 보내려면 역할의 정책에 sns:Publish 권한이 있어야 합니다. CloudTrail이 S3로 쓰려면 s3:PutObject 권한이 필요합니다. 이 권한들이 역할과 정책에 있는지 확인합니다.
  2. KMS 및 대상 서비스 검증암호화된 로그는 KMS 키 정책에 서비스 권한이 명시되어 있는지 확인합니다. SNS 주제, SQS 큐, Lambda 함수 등 대상이 올바르게 구성되었는지, 대상이 활성 상태인지 검증합니다.
  3. 서비스 간 연결 확인EventBridge 규칙이 활성화되어 있는지, 이벤트를 감지하는 패턴이 맞는지 확인합니다. CloudTrail이 실제로 로그를 기록하고 있는지 시험 이벤트로 검증합니다.

#2핵심 질문

12사고 대응·포렌식·감사12-05

사고 대응·포렌식·감사

백업에서 안전한 상태로 되돌리고, 복구 절차와 복원력을 평가·장애 주입으로 실제로 작동하는지 검증하는 단계.

#1문제 상황

보안 사고 대응 계획을 세우고 조치를 실행하지만, 실제로 백업에서 복구할 수 있는지, 복구하는 데 얼마나 걸리는지, 복구 후 애플리케이션이 정상 작동하는지 확인하지 않습니다. 문제는 막상 대응 시점에 백업이 손상되었거나 복구 절차가 실제로는 작동하지 않을 수 있다는 것입니다.

#2핵심 질문

침해 후 복구 계획이 정말로 작동하고 애플리케이션이 정상 상태로 돌아가는지 미리 검증할 수 있을까요?

#3동작 예시

정기적으로 테스트 환경에서 프로덕션 백업을 실제로 복원해보고, Application Recovery Controller로 페일오버를 연습하며, Fault Injection Simulator(FIS)로 의도적으로 라우팅 장애나 네트워크 지연을 일으켜 복구 절차가 실제로 작동하는지, 복구 시간이 목표치(RTO) 안에 들어오는지 확인합니다.

#4동작 과정

  1. 백업 복원 검증정기적으로 백업 이미지를 테스트 환경에 실제로 복원해서 데이터 무결성을 확인하고, 복원 절차의 실패점을 미리 파악합니다.
  2. 복구 절차 실행 및 시간 측정Application Recovery Controller(ARC)로 페일오버나 페일백 절차를 실제로 실행해 얼마나 걸리는지 측정하고, RTO(목표 복구 시간)를 달성하는지 검증합니다.
  3. 장애 주입 및 복원력 평가Resilience Hub로 아키텍처의 복원력을 점수화하고, FIS로 가용 영역 장애·인스턴스 종료·네트워크 지연 등을 의도적으로 주입해 대응 계획의 실효성을 확인합니다.

#5한 줄 요약

백업 복원·복구 절차·장애 주입을 통해 침해 후 정상 상태로의 복구가 실제로 가능한지 미리 테스트하고 대응 역량과 복원력을 평가하는 활동

12사고 대응·포렌식·감사12-06

사고 대응·포렌식·감사

규정 준수 증거를 자동 수집·보고서화하고 AWS 인증서와 아키텍처 점검 도구로 보안 상태를 주기적으로 검토하는 활동.

#1문제 상황

규정 준수(컴플라이언스) 증명을 위해 조직은 각 규정(SOC 2, HIPAA, PCI-DSS 등)이 요구하는 증거(로그, 설정 스냅샷, 접근 기록 등)를 수동으로 모으고 보고서를 작성합니다. 문제는 증거 수집에 시간이 오래 걸리고, 최신 상태를 유지하기 어려우며, 아키텍처의 보안 상태를 체계적으로 점검할 방법이 없다는 것입니다.

#2핵심 질문

규정 준수 증거를 자동으로 수집하고, AWS 아키텍처의 보안 상태를 주기적으로 점검할 수 있을까요?

#3동작 예시

Audit Manager가 SOC 2 규정에 필요한 증거(CloudTrail API 로그, 권한 변경 기록, MFA 사용 현황 등)를 CloudTrail·Config·CloudWatch Logs에서 자동으로 수집해서 보고서화하고, Artifact에서 AWS의 공식 SOC 2 감사 보고서를 다운로드하며, Well-Architected Tool로 아키텍처의 보안·신뢰성·성능 등을 점수화하고, Trusted Advisor로 계정의 보안 베스트 프랙티스 위반을 자동 검사합니다.

#4동작 과정

  1. 규정 준수 증거 자동 수집 및 평가Audit Manager가 정해진 규정(템플릿)에 필요한 증거를 CloudTrail, AWS Config, CloudWatch Logs에서 자동으로 수집해서 규격에 맞게 정리하고 준수 상태를 점수화합니다.
  2. AWS 인증서 및 아키텍처 평가Artifact에서 AWS의 공식 인증서(SOC 2, ISO 27001 등)를 다운로드하고, Well-Architected Tool에서 5가지 기둥(운영 우수성, 보안, 신뢰성, 성능 효율, 비용 최적화)에 따라 아키텍처를 평가합니다.
  3. 보안 베스트 프랙티스 검사 및 개선 권고Trusted Advisor가 계정 전체의 보안·비용·성능·내결함성·서비스 제한 위반을 자동으로 검사하고 개선 권고를 제공합니다.

#5한 줄 요약

Audit Manager·Artifact·Well-Architected Tool·Trusted Advisor를 통해 규정 준수 증거를 자동 수집하고 AWS 보안 상태를 주기적으로 검증하는 지속적인 감시·개선 활동
