IAM이 무엇을 결정하는가01-01

IAM이 푸는 문제와 IAM을 쓰는 시점

IAM은 누가 AWS의 어떤 자원에 무엇을 할 수 있는지를 계정 차원에서 통제하는 서비스이며, 사람·워크로드가 AWS 자원에 접근해야 할 때 쓴다.

#1문제 상황

AWS 계정의 모든 사람이 루트 사용자의 자격 증명을 공유해서 작업하면 어떤 일이 일어나는가. 첫째, 모든 사람이 모든 자원에 모든 권한을 가지므로 실수나 악의적 행동을 막을 수 없다. 둘째, 누가 언제 무엇을 했는지를 추적할 방법이 없어 감사와 규정 준수가 불가능하다. 셋째, 루트 자격 증명이 하나라도 유출되면 계정 전체가 위험해진다.

#2핵심 질문

대규모 조직에서 수많은 개발자, 운영자, 서비스가 각각 필요한 권한만 가지고 AWS 자원에 접근하도록 하려면 어떻게 할까?

#3동작 예시

회사의 개발팀 Alice는 데이터베이스 읽기만 가능하고, 인프라팀 Bob은 EC2 인스턴스를 시작/중지할 수 있으며, Lambda 함수는 S3 버킷에만 접근 가능하도록 각각 다른 권한을 부여하는 방식.

#4동작 과정

  1. 신원 생성각 사람과 서비스에 대응하는 IAM 사용자나 역할을 계정 내에 만든다.
  2. 권한 할당JSON 형식의 정책 문서를 통해 각 신원이 어떤 자원에서 어떤 작업을 할 수 있는지를 정의하고 할당한다.
  3. 요청 시 검증AWS 자원에 접근하는 요청이 들어오면, 요청자의 신원과 그에 붙은 정책을 확인해 허용 또는 거부를 결정한다.

#5한 줄 요약

IAM계정 내에서 여러 신원에게 각각 다른 수준의 권한을 부여해 누가 무엇을 할 수 있는지를 세밀하게 통제하는 서비스

AWS 요청의 구성 요소와 요청 컨텍스트

모든 AWS 호출은 프린시펄·작업·리소스·환경 정보가 담긴 하나의 요청으로 만들어지고, 그 묶음(요청 컨텍스트)을 기준으로 허용 여부가 판정된다.

#1문제 상황

AWS에 요청을 보낼 때, 요청 자체에는 그것이 누구로부터 온 것인지, 무엇을 하려는 것인지, 어느 자원을 대상으로 하는지 정보가 흩어져 있다. 서비스가 이 요청을 평가하려면 이 정보들을 한데 모아 종합적으로 판단해야 하는데, 산재된 정보로는 정책 기반 권한 검사가 불가능하다.

#2핵심 질문

AWS 서비스가 들어온 요청을 평가할 때 어떤 정보를 종합적으로 참고해야 할까?

#3동작 예시

사용자 Alice가 ap-northeast-1 리전의 prod-db 데이터베이스에 대해 ModifyDBInstance 작업을 요청했다는 정보 묶음에서, Alice는 프린시펄(요청자), ModifyDBInstance는 작업, prod-db는 리소스, ap-northeast-1과 요청 시간은 환경 정보가 된다.

#4동작 과정

  1. 요청 전송사용자나 애플리케이션이 자격 증명과 함께 AWS 서비스에 요청을 보낸다.
  2. 요청 컨텍스트 조립AWS는 요청에서 프린시펄(요청자), 작업(Action, 어떤 서비스의 어떤 동작), 리소스(Resource, 대상 자원), IP 주소와 시간 같은 환경 정보(Condition)를 추출해 하나의 컨텍스트로 묶는다.
  3. 정책 평가IAM은 이 컨텍스트를 프린시펄에 붙은 정책 및 리소스에 붙은 정책과 대비해 허용할지 거부할지를 판정한다.

#5한 줄 요약

요청 컨텍스트는 AWS 서비스가 "누가 무엇을 어느 자원에 하려는지"를 완전히 파악하기 위해 요청에서 뽑아내는 정보 묶음이며, IAM의 정책 평가는 이 컨텍스트를 기준으로 이뤄집니다.

IAM이 무엇을 결정하는가01-03

인증과 인가의 분리, 프린시펄·엔터티 용어

인증은 요청자가 누구인지 확인하는 단계이고 인가는 그 신원에 권한이 있는지 판정하는 단계로, IAM은 사용자·역할 같은 엔터티를 프린시펄로 삼아 둘을 나눠 처리한다.

#1문제 상황

기존 방식에서 계정 전체가 하나의 신원(루트 계정)으로만 작동하면, 누구인지 확인하는 단계 자체가 없다. 모든 요청이 같은 신원에서 오는 것으로 취급되므로 개별 권한 검사가 의미를 잃는다.

#2핵심 질문

요청자의 신원을 먼저 확인한 후 그 신원이 실제로 어떤 권한을 가진 사람/서비스인지 따로 판정할 필요가 왜 있을까?

#3동작 예시

개발자 Charlie가 AWS 콘솔에 로그인할 때, 먼저 사용자 이름과 비밀번호로 Charlie가 실제로 Charlie임을 확인(인증)하고, 그 다음에 Charlie라는 사용자 신원에 붙은 정책을 확인해 S3 읽기 권한만 있는지, EC2 관리 권한까지 있는지를 판정(인가)한다.

#4동작 과정

  1. 인증요청에 포함된 자격 증명(접근 키, 임시 토큰, 콘솔 로그인 정보 등)을 검증해 프린시펄(요청자)이 실제로 본인임을 확인한다.
  2. 엔터티 식별그 프린시펄이 IAM 사용자(영구 신원)인지, 역할(임시 권한을 가지는 신원)인지, AWS 계정 자체인지 식별한다.
  3. 인가확인된 엔터티에 붙은 정책들을 모아서, 요청된 작업과 리소스에 대한 권한이 있는지 평가해 최종 허용/거부를 결정한다.

#5한 줄 요약

인증과 인가의 분리는 "당신이 누구인가"를 먼저 확인한 후 "당신에게 이 권한이 있는가"를 판정하는 체계로, 이를 통해 같은 계정 내에서도 세밀한 권한 통제가 가능합니다.

권한과 정책이 접근을 관리하는 방식

권한은 JSON 정책 문서로 표현되어 아이덴티티나 리소스에 붙고, 요청이 들어오면 관련 정책을 모아 평가해 허용·거부를 결정한다.

→ 03-02 참조

#1문제 상황

IAM이 없으면 권한 정보 자체가 없다. 루트 계정 자격 증명을 가지는 것 자체만으로 모든 작업이 가능하고, 개별 사용자나 서비스에게 제한된 권한을 부여할 방법이 없다. 따라서 권한을 체계적으로 관리하거나 감사할 수 없다.

#2핵심 질문

수백 수천 명의 사용자와 서비스가 각각 다른 권한을 가져야 할 때, 이를 어떻게 일관되고 추적 가능하게 관리할 것인가?

#3동작 예시

다음 JSON 정책이 개발자 그룹에 붙어 있으면, 그 그룹의 모든 구성원은 정책에 명시된 작업(GetObject, PutObject)을 dev-bucket이라는 S3 버킷 내에서만 수행할 수 있다: ``json { "Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"], "Resource": "arn:aws:s3:::dev-bucket/*" } ``

#4동작 과정

  1. 정책 작성JSON 형식으로 Effect(Allow/Deny), Action(작업), Resource(자원), Condition(조건) 등을 정의한 정책 문서를 만든다.
  2. 정책 연결이 정책을 사용자, 역할, 그룹 같은 아이덴티티나 S3 버킷 같은 리소스에 직접 붙인다.
  3. 요청 평가요청이 들어오면, 프린시펄에 붙은 모든 정책과 리소스에 붙은 정책을 모아서, 요청된 작업이 명시적 허용(Allow)에 맞는지, 명시적 거부(Deny)가 있는지, 아니면 둘 다 없는지(거부)를 판정한다.

#5한 줄 요약

정책은 권한을 코드화한 JSON 문서로서 누가 무엇을 할 수 있는지를 선언적으로 정의하고, IAM은 들어온 요청이 정책 기준에 맞는지를 자동으로 평가하는 방식으로 대규모 권한 관리를 가능하게 합니다.

ARN과 IAM 식별자로 대상을 가리키기

ARN은 AWS 자원 하나하나를 전역에서 유일하게 지목하는 표준 이름 형식으로, 정책에서 대상 리소스를 특정할 때 쓰인다.

#1문제 상황

권한을 설정할 때 "S3 버킷", "이 EC2 인스턴스"처럼 자연어로 표현하면 두 가지 문제가 생긴다. 첫째, AWS의 수백만 개 자원 중 정확히 어느 것을 가리키는지 모호하고, 둘째, 정책이 인간 언어에 의존하면 자동 평가가 불가능하다.

#2핵심 질문

AWS 계정 내의 특정 자원 하나를 컴퓨터가 이해할 수 있는 유일한 이름으로 어떻게 표현할 것인가?

#3동작 예시

미국 동부 리전의 prod-bucket이라는 S3 버킷의 모든 객체를 지목하려면 ARN(Amazon Resource Name)으로 arn:aws:s3:::prod-bucket/*라고 정확하게 명시한다. 이 표기법이면 전세계 AWS 환경에서도 정확히 그 버킷만 지목된다.

#4동작 과정

  1. ARN 구조 파악ARN은 arn:partition:service:region:account-id:resource 형식으로, 파티션(aws 또는 aws-cn), 서비스(s3, ec2, iam 등), 리전, 계정 ID, 자원을 순서대로 담아 전역 유일성을 보장한다.
  2. 정책에서 사용JSON 정책의 Resource 필드에 ARN을 그대로 쓰거나 와일드카드(*)를 사용해 여러 자원을 한번에 지목한다.
  3. IAM 식별자 조합사용자, 역할, 그룹을 지목할 때도 ARN이나 엔터티의 이름/ID를 쓰며, 정책 평가 시 IAM 서비스는 이 식별자들을 그대로 대비해 일치 여부를 판정한다.

#5한 줄 요약

ARN은 AWS의 모든 자원을 유일하게 식별하는 표준 표기법으로, 정책에서 누가 어느 자원에 접근할 수 있는지를 기계 가능한 형태로 정확하게 명시할 수 있게 해줍니다.

AWS 계정 루트 사용자와 루트 자격 증명 관리

계정 생성 시 만들어지는 모든 권한을 가진 최상위 신원으로, MFA 를 켜고 평소에는 쓰지 않는 것이 원칙이다.

#1문제 상황

AWS 계정을 생성하면 자동으로 루트 사용자가 만들어진다. 이 루트 사용자는 계정 내의 모든 자원에 모든 권한을 가지고 있으므로 계정 전체를 완전히 통제할 수 있다. 하지만 권한이 너무 크기 때문에, 루트 자격 증명이 노출되거나 실수로 루트 사용자가 자원을 삭제하면 계정 전체가 위험해진다. 또한 누가 루트 계정으로 무엇을 했는지 추적하기 어렵다.

#2핵심 질문

계정 관리에 필요한 루트 권한과 일상적 작업 중에 필요한 최소 권한을 어떻게 분리할까?

#3동작 예시

새로운 AWS 계정의 루트 사용자로 처음 로그인해서 MFA 기기를 설정하고, AdministratorAccess 권한을 가진 IAM 사용자를 하나 만든 후, 그 사용자로 대부분의 작업을 진행하면서 루트 자격 증명은 금고에 보관하는 방식.

#4동작 과정

  1. 루트 사용자 보호루트 계정 이메일 주소(계정 소유권을 증명하는 유일한 수단)와 비밀번호를 안전하게 보관한 후, 멀티 팩터 인증(MFA, 물리 토큰이나 인증 앱)을 반드시 활성화한다.
  2. 관리자 사용자 생성AdministratorAccess 정책을 붙인 IAM 사용자 또는 역할을 만들어 루트 권한이 필요한 대부분의 관리 작업을 그 사용자로 수행한다.
  3. 루트 사용자 최소화루트 사용자는 계정 설정 변경, 루트 비밀번호 초기화, 결제 정보 수정 같은 특수한 상황에서만 사용하고 평소에는 접근하지 않는다.

#5한 줄 요약

루트 사용자계정의 최상위 소유자 신원으로, 권한이 무제한이기 때문에 노출 위험을 최소화하고 일상 작업은 제한된 권한의 IAM 사용자/역할로 수행해야 합니다

계정 설정 — 계정 ID와 계정 별칭, 콘솔 사인인 URL

12자리 계정 ID 를 확인하고 읽기 쉬운 별칭을 만들어 콘솔 로그인 URL 을 알아보기 쉽게 바꾸는 방법이다.

#1문제 상황

AWS 계정마다 12자리의 숫자로 이루어진 계정 ID(예: 123456789012)가 있다. 이 ID는 전역에서 유일하고 ARN 같은 리소스 식별자에 들어가지만, 사용자들이 기억하고 공유하기 어렵고 콘솔 로그인 URL도 https://123456789012.signin.aws.amazon.com/console처럼 복잡하다.

#2핵심 질문

계정 ID 대신 회사나 팀 이름처럼 읽기 쉬운 별칭을 써서 콘솔 로그인을 간편하게 할 수 있을까?

#3동작 예시

회사 이름이 "acme-corp"라면, 계정 ID는 여전히 123456789012이지만 별칭을 "acme-corp"로 설정하면, 직원들은 https://acme-corp.signin.aws.amazon.com/console로 로그인할 수 있다.

#4동작 과정

  1. 계정 ID 확인IAM 콘솔이나 루트 사용자 계정 설정 페이지에서 자신의 12자리 계정 ID를 확인한다. 이 ID는 고정되며 변경할 수 없다.
  2. 계정 별칭 생성IAM 콘솔의 계정 설정 섹션에서 고유한 별칭을 입력한다. 별칭은 AWS 전체에서 유일해야 한다.
  3. 콘솔 로그인 URL 활용별칭이 생성되면 https://{별칭}.signin.aws.amazon.com/console 형식의 로그인 URL을 사용할 수 있고, IAM 사용자나 임시 자격 증명도 이 URL을 통해 로그인한다.

#5한 줄 요약

계정 별칭은 12자리 숫자 계정 ID를 사람이 읽기 쉬운 형태로 대응시키는 선택 설정으로, 콘솔 로그인과 계정 참조를 간편하게 해줍니다.

#2핵심 질문

#4동작 과정

#1문제 상황

IAM 사용자가 10명 있고 모두 같은 권한이 필요하다면, 각 사용자에게 정책을 하나하나 붙여야 한다. 권한을 바꿀 때도 10명 모두에게 일일이 적용해야 하므로 실수하기 쉽고 관리 비용이 높다.

#2핵심 질문

같은 권한을 가진 여러 사용자의 권한을 한 번에 관리할 수 있는 방법이 있을까?

#3동작 예시

"개발팀"이라는 그룹을 만들고 5명의 개발자 사용자를 넣은 뒤, 그룹에 "S3 접근" 정책을 붙인다. 그러면 이 5명 모두가 자동으로 S3 접근 권한을 얻는다. 개발팀 구성이 바뀌면 사용자를 그룹에서 빼거나 추가하면 된다.

#4동작 과정

  1. 그룹 생성그룹을 만들고 이름을 정한다 (예: "개발팀", "운영팀").

  3. 정책 붙이기그룹 전체에 정책을 연결하면, 그룹에 속한 모든 사용자가 그 권한을 갖는다.

사용자 그룹여러 사용자를 논리적으로 묶어 정책을 그룹 단위로 관리함으로써 권한 변경을 효율적으로 하고 실수를 줄이는 것

IAM 리소스에 태그 붙이기

사용자·역할·정책 등 IAM 리소스에 키-값 태그를 달아 분류하고 태그 기반 접근 제어의 토대로 삼는 것이다.

#1문제 상황

IAM에는 사용자, 역할, 정책 같은 여러 리소스가 있다. 이들이 무엇인지, 누가 만들었는지, 어떤 프로젝트에 쓰이는지를 한눈에 알기 어렵다. 리소스가 많아질수록 관리와 검색이 복잡해진다.

#2핵심 질문

IAM 리소스를 분류하고 특정 조건에 따라 접근을 제어하려면 어떻게 해야 할까?

#3동작 예시

개발팀이 만든 모든 IAM 사용자에 "환경=개발", "팀=개발팀"이라는 태그를 붙인다. 나중에 "환경=개발"이라는 태그가 붙은 리소스만 필터링해서 찾거나, 태그 기반으로 접근을 제한할 수 있다.

#4동작 과정

  1. 태그 설계리소스를 분류할 키와 값을 정한다 (환경, 팀, 비용 센터 등).
  2. 태그 추가IAM 리소스를 만들 때 또는 만든 후에 태그를 붙인다.
  3. 태그 기반 접근 제어정책에서 태그 조건을 명시해, 특정 태그가 붙은 리소스에만 접근하게 제어한다.

#5한 줄 요약

AWS 보안 자격 증명의 종류와 프로그래밍 액세스

AWS 는 콘솔 로그인용 암호, API·CLI 용 액세스 키, 임시 자격 증명 등 용도가 다른 여러 자격 증명을 제공하며, 무엇을 쓸지는 사람이 접속하는지 프로그램이 접속하는지에 따라 갈린다.

#1문제 상황

AWS에 접근하는 방법은 콘솔 웹 페이지에 로그인하는 것뿐이라고 생각하기 쉽다. 하지만 CLI로 명령어를 실행하거나 애플리케이션 코드에서 AWS API를 호출할 때는 다른 형태의 증명이 필요하다.

#2핵심 질문

사람이 콘솔에 로그인하는 방식과 프로그램이 API 요청을 서명하는 방식에서 어떤 자격 증명을 어떻게 쓸까?

#3동작 예시

개발자 A는 AWS 콘솔에 로그인할 때 사용자명과 암호를 써서 접근한다. 그 같은 개발자 A가 터미널에서 AWS CLI 명령어를 실행할 때는 액세스 키 ID와 비밀 키를 사용한다. 동일인이지만 접근 방식이 다르면 자격 증명의 종류도 달라진다.

#4동작 과정

  1. 콘솔 접근사람이 AWS 웹 콘솔에 로그인할 때는 암호나 MFA를 사용한다.
  2. 프로그래매틱 접근CLI나 SDK 같은 프로그램이 AWS API를 호출할 때는 액세스 키(API 요청을 서명하는 긴 문자열 쌍)를 사용한다.
  3. 임시 자격 증명역할(role, 한시적으로 권한을 빌려가는 방식)을 쓸 때는 일정 시간 유효한 임시 토큰을 받아 사용한다.

#5한 줄 요약

자격 증명접근 방식(콘솔 로그인 vs API 호출)과 생명주기(장기 vs 단기)에 따라 여러 종류를 제공해, 각각에 맞는 보안과 편의성을 보장하는 것

콘솔 암호와 계정 암호 정책

IAM 사용자가 콘솔에 로그인할 때 쓰는 암호와, 계정 전체에 최소 길이·복잡도·만료 같은 규칙을 강제하는 암호 정책이다.

#1문제 상황

IAM 사용자마다 자기 암호를 정하도록 하면, 누군가는 "password"처럼 약한 암호를 만들 수 있다. 또는 아무도 암호를 바꾸지 않아 오래된 암호로 계정이 침해될 위험이 있다.

#2핵심 질문

계정 전체에 적용할 수 있는 암호의 최소 강도와 주기적 변경 규칙을 어떻게 강제할까?

#3동작 예시

계정의 암호 정책을 "최소 14자, 대문자·숫자·특수문자 포함, 90일마다 변경"으로 설정한다. 그러면 이 계정의 모든 IAM 사용자가 이 규칙을 따라 암호를 만들고 바꿔야 한다.

#4동작 과정

  1. 정책 설정암호의 최소 길이, 복잡도 요구사항, 유효 기간을 정한다.
  2. 정책 적용이 규칙이 계정의 모든 사용자에게 자동으로 적용된다.
  3. 암호 변경 강제암호 유효 기간이 끝나면 사용자가 새 암호로 바꿔야 한다.

#5한 줄 요약

암호 정책계정 단위에서 암호의 강도와 갱신 주기를 일괄 규정해, 사람의 판단에 의존하지 않고 최소 보안 기준을 자동으로 강제하는 것

#1문제 상황

액세스 키는 CLI나 SDK에서 AWS API 요청에 서명하는 데 쓰인다. 한 번 발급되면 만료 기한이 없는 장기 자격 증명이다. 만약 실수로 코드에 노출되거나 장시간 바뀌지 않으면, 그 키를 아는 누구나 계정의 리소스에 접근할 수 있다.

#2핵심 질문

장기 액세스 키를 안전하게 관리하면서 유출되었을 때 빠르게 대응하려면 어떻게 해야 할까?

#3동작 예시

#4동작 과정

  1. 생성사용자의 새 액세스 키(ID와 비밀 키 쌍)를 만든다.
  2. 로테이션주기적으로(예: 3~6개월마다) 새 키를 만들고 애플리케이션을 업데이트한 뒤, 기존 키를 비활성화 또는 삭제한다.
  3. 보호키를 코드 저장소에 커밋하지 않고, 환경 변수나 보안 저장소에 보관한다.

#2핵심 질문

#3동작 예시

서비스별 자격 증명, 서버 인증서, 베어러 토큰

→ 03-01 참조

#1문제 상황

지금까지 배운 자격 증명은 주로 일반적인 형태였다. 사용자 이름과 암호, 액세스 키 같은 것들이다. 하지만 AWS의 각 서비스들은 저마다 다른 인증 방식을 필요로 할 수 있다. 예를 들어 CodeCommit은 git 저장소에 접근하기 위해 고유한 자격 증명이 필요하고, 일부 서비스는 HTTPS 통신을 위해 서버 인증서를 요구하며, 특정 API들은 베어러 토큰이라는 특수한 형태의 인증을 사용한다. 이렇게 다양한 자격 증명 형태들이 존재한다는 것이 기존의 단순한 자격 증명 체계의 한계다.

#2핵심 질문

특정 서비스에 접근할 때만 필요한 전용 자격 증명들은 어떻게 관리하고 사용해야 할까?

#3동작 예시

CodeCommit에서 git 저장소에 접근하려면, 일반 AWS 액세스 키로는 부족하고 CodeCommit 전용 자격 증명을 따로 생성해야 한다. IAM 콘솔에서 사용자를 선택하고 'CodeCommit 자격 증명' 탭으로 가서 사용자 이름과 암호를 생성하면, 이 자격 증명으로만 git clone이나 git push 같은 코드 커밋 작업이 가능하다.

#4동작 과정

  1. 서비스 식별애플리케이션이 특정 서비스(CodeCommit, Keyspaces 등)에 접근하려 한다.
  2. 전용 자격 증명 생성IAM에서 해당 서비스 전용의 자격 증명을 만든다. 예를 들어 CodeCommit이면 사용자 이름과 암호, 일부 서비스면 서버 인증서나 베어러 토큰 같은 형태다.
  3. 자격 증명 사용애플리케이션이 생성된 자격 증명으로 해당 서비스의 API나 프로토콜(git, https 등)에 접근한다.

역할 — 신원을 빌려 쓰는 방식04-01

IAM 역할과 신뢰 정책, 혼동된 대리자 문제

역할은 특정 주체가 잠시 빌려 쓰는 권한 묶음이며, 누가 빌릴 수 있는지는 신뢰 정책이 정하고 이를 느슨하게 두면 제3자가 권한을 대신 쓰게 되는 혼동된 대리자 문제가 생긴다.

#1문제 상황

지금까지는 주체(사용자, 서비스 등)가 고정된 자격 증명을 들고 직접 AWS 리소스에 접근했다. 하지만 실제로는 여러 주체가 임시로 권한이 필요한 경우가 많다. 예를 들어 개발자가 평소에는 읽기 권한만 가지다가 배포할 때만 특정 권한이 필요하거나, 외부 회사의 애플리케이션이 우리 AWS 계정의 리소스에 접근해야 하는 경우다. 고정된 자격 증명만으로는 이런 임시적이고 유동적인 권한 할당을 관리하기 어렵다.

#2핵심 질문

누가 어떤 권한을 임시로 빌려 쓸 수 있도록 안전하게 통제할 수 있을까?

#3동작 예시

역할은 권한 묶음에 불과하고 그 자체로는 아무도 아니다. 역할에 신뢰 정책을 붙여야 한다. 신뢰 정책은 "이 역할을 누가 빌릴 수 있는가"를 정의하는 규칙이다. 예를 들어 "이 Lambda 함수만 이 역할을 빌릴 수 있다"거나 "우리 AWS 계정의 사용자 john만 이 역할을 빌릴 수 있다"같은 식으로 신뢰 정책을 좁게 설정하면 권한이 의도한 대상에게만 전달된다.

#4동작 과정

  1. 역할 생성필요한 권한들을 모아 역할이라는 권한 묶음을 만든다.
  2. 신뢰 정책 설정역할에 "누가 이 역할을 빌릴 수 있는가"를 정의하는 신뢰 정책을 붙인다. 신뢰 정책이 느슨하면 의도하지 않은 주체가 권한을 가져갈 수 있는데, 이를 혼동된 대리자(Confused Deputy) 문제라 한다.
  3. 역할 차용허락된 주체만 역할을 임시로 빌려 쓰고, 일시적으로 권한을 행사한 뒤 반환한다.

#5한 줄 요약

역할 사용 시나리오와 역할 만들기

#1문제 상황

역할이 존재한다는 것은 알았지만, 실제로 어떤 상황에서 역할을 만들고 사용하는지는 명확하지 않을 수 있다. 어떤 경우에 사용자 대신 역할을 쓸까? 다양한 시나리오가 있다. 한 AWS 계정의 사용자가 다른 AWS 계정의 리소스에 접근해야 할 때, AWS가 제공하는 서비스(EC2, Lambda 등)가 당신의 다른 리소스에 접근해야 할 때, 또는 외부 조직의 계정이나 애플리케이션이 당신의 리소스에 접근해야 할 때 역할을 만든다. 시나리오마다 역할의 신뢰 정책과 권한이 달라진다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 접근 상황 파악누가 어디의 리소스에 접근해야 하는지 판단한다. 계정 간 접근인지, 서비스가 다른 리소스에 접근하는 건지, 외부 ID 연동인지 식별한다.
  2. 역할 생성 및 신뢰 정책 설정상황에 맞게 역할을 만들고 신뢰 정책에 접근을 허용할 주체를 정의한다. 계정 간이면 다른 계정의 ARN(리소스 식별자)을 신뢰 정책에, 서비스 접근이면 서비스의 주체 식별자를 신뢰 정책에 기록한다.
  3. 권한 연결역할에 리소스에 접근하는 데 필요한 권한들을 정책으로 붙인다.

서비스 연결 역할(service-linked role)

AWS 서비스가 자기 일을 하려고 미리 정의된 형태로 붙여 쓰는, 그 서비스 전용의 역할이다.

#1문제 상황

역할을 일반적으로 만들려면 신뢰 정책과 권한 정책을 명시적으로 설정해야 한다. 하지만 AWS의 일부 서비스들은 자신의 기본 기능을 하려고 특정 권한들이 항상 필요하다. 예를 들어 Application Load Balancer가 정상 여부를 확인하는 헬스 체크를 하려면 특정 권한이 필요하고, RDS가 자동 백업을 수행하려면 특정 권한이 필요하다. 이런 권한들을 매번 사용자가 직접 만들고 설정하는 것은 비효율적이다.

#2핵심 질문

#3동작 예시

ALB(Application Load Balancer)를 만들면, AWS가 "ALB는 이 일들을 하려면 이런 권한들이 필요해"라고 미리 정의해 둔 역할을 자동으로 붙인다. 사용자는 역할을 만들거나 신뢰 정책을 설정할 필요가 없다. 서비스 연결 역할은 AWS가 미리 그 서비스 전용으로 정의해 둔 고정된 형태의 역할이다.

#4동작 과정

  1. 서비스 생성사용자가 ALB나 RDS 같은 AWS 서비스 인스턴스를 만든다.
  2. 서비스 연결 역할 자동 생성AWS가 해당 서비스가 필요로 하는 권한을 미리 정의한 역할을 자동으로 생성하고 서비스에 붙인다.
  3. 서비스 정상 작동서비스가 그 역할을 사용해 필요한 작업(헬스 체크, 백업 등)을 수행한다.

역할 전환과 전환·전달(PassRole) 권한

사용자가 역할로 갈아타려면 전환 권한이, 서비스에 역할을 넘겨주려면 iam:PassRole 권한이 필요하다.

#1문제 상황

사용자가 역할을 빌려 쓰려면 두 가지 조건이 필요하다. 첫째, 역할의 신뢰 정책이 그 사용자를 허용해야 한다(신뢰 정책은 이미 배웠다). 둘째, 사용자가 "이 역할로 전환하겠다"는 행동을 할 권리가 있어야 한다. 마찬가지로 서비스에 역할을 넘겨주는 것도 권한이 필요하다. 사용자가 EC2를 만들 때 "이 EC2에 이 역할을 붙여다오"라고 하려면, iam:PassRole이라는 특수 권한이 필요하다. 이 두 권한이 없으면 역할의 신뢰 정책이 아무리 허용해도 역할을 쓸 수 없다.

#2핵심 질문

역할을 빌려 쓰거나 서비스에 넘겨주려면 어떤 권한이 필요할까?

#3동작 예시

개발자 alice가 역할 "prod-deploy"로 전환해서 배포 작업을 하려고 한다. alice는 "prod-deploy" 역할의 신뢰 정책에 포함되어 있고, 또한 alice의 사용자 정책에 "sts:AssumeRole" 권한이 있어야 한다. 이 두 조건이 모두 충족되면 alice는 역할을 빌려 쓸 수 있다. 만약 sts:AssumeRole 권한이 없으면, 신뢰 정책이 alice를 허용해도 전환할 수 없다.

#4동작 과정

  1. 사용자 또는 서비스가 역할 사용 요청사용자가 역할로 전환하거나(사용자 → 역할), 서비스를 만들면서 역할을 붙여달라고 요청한다(서비스 ← 역할).
  2. 권한 확인역할로 전환하려면 sts:AssumeRole 권한, 서비스에 역할을 붙이려면 iam:PassRole 권한이 요청자에게 있어야 한다. 이 두 권한 중 하나라도 없으면 요청이 거절된다.
  3. 역할 사용 허락 또는 거부권한이 있으면 신뢰 정책을 확인한다. 신뢰 정책이 요청자를 허용하면 역할을 빌려주고, 거부하면 요청을 거절한다.

#1문제 상황

애플리케이션이 AWS 리소스에 접근하려면 자격 증명이 필요하다. 전통적인 방식은 코드에 액세스 키를 하드코딩하거나 환경 변수로 전달하는 것이었다. 하지만 이는 보안 위험이 크다. 액세스 키가 코드 저장소에 노출되거나, 누군가 서버에 접근하면 자격 증명이 탈취될 수 있다. 또한 액세스 키를 로테이션할 때마다 코드를 수정하고 배포해야 한다. EC2 인스턴스 프로파일은 이 문제를 해결한다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 역할 생성애플리케이션이 필요로 하는 권한을 가진 역할을 만든다.
  2. 인스턴스 프로파일 생성 및 역할 붙임인스턴스 프로파일에 그 역할을 붙인다. 인스턴스 프로파일은 EC2와 IAM 역할 사이의 연결고리다.

#3동작 예시

역할의 권한 정책을 변경하면 그 순간부터 새로 발급되는 임시 자격 증명은 새로운 권한으로 작동합니다. 하지만 이전에 발급된 자격 증명은 여전히 유효한 상태입니다. 이를 즉시 무효화하려면 STS의 RevokeSessionToken 같은 API를 사용하거나, 역할의 신뢰 정책에서 이전 세션을 조건으로 차단하는 방식을 사용해야 합니다.

#4동작 과정

  1. 신뢰 정책 또는 권한 정책 수정콘솔이나 API로 역할의 신뢰 정책이나 권한 정책을 변경하면 즉시 적용됩니다. 이후 새로 발급되는 임시 자격 증명부터 새로운 정책이 적용됩니다.
  2. 이미 발급된 자격 증명 취소필요시 관리자가 해당 세션의 임시 자격 증명을 명시적으로 취소하거나, 신뢰 정책에 조건을 추가해 기존 세션의 유효성을 검증하도록 설정합니다.
  3. 역할 삭제역할이 더 이상 필요 없으면 역할을 완전히 삭제합니다. 이때 역할에 할당된 인라인 정책도 함께 삭제됩니다.

AWS STS가 발급하는 만료 시간이 정해진 자격 증명으로, 장기 액세스 키를 저장하지 않고도 안전하게 AWS를 호출하게 해준다.

#1문제 상황

전통적인 방식은 각 사용자나 애플리케이션에 장기 액세스 키를 발급해 AWS를 호출하게 합니다. 이 키는 생성 후 사라지지 않으므로 유출되면 계속 사용될 수 있고, 권한을 회수하려면 키를 삭제해야 합니다. 또한 권한 회수 후에도 이전에 발급된 키로는 계속 호출 가능한 시간 차이가 생깁니다.

#2핵심 질문

장기 액세스 키를 저장하지 않고도 일정 시간만 유효한 자격 증명으로 AWS를 호출할 수 있는 방법이 있을까요?

#3동작 예시

AWS STS(Security Token Service)는 사용자나 애플리케이션이 요청할 때 접근 토큰(AccessKeyId), 비밀 키(SecretAccessKey), 보안 토큰(SessionToken)으로 이루어진 임시 자격 증명을 발급합니다. 이 자격 증명은 지정된 만료 시간 이후 자동으로 무효화됩니다.

#4동작 과정

  1. STS에 자격 증명 요청사용자나 애플리케이션이 STS 엔드포인트에 요청을 보냅니다. 요청에는 역할을 맡을 것인지, 아니면 기존 자격의 임시 버전을 원하는지 등이 포함됩니다.
  2. 임시 자격 증명 발급STS가 접근 토큰, 비밀 키, 보안 토큰 세 가지를 포함한 임시 자격 증명 세트를 반환합니다. 동시에 만료 시간(기본 1시간, 최대 12시간)을 지정합니다.
  3. 임시 자격으로 AWS 호출발급받은 임시 자격 증명으로 AWS 서비스 API를 호출합니다. 만료 시간이 지나면 그 자격 증명은 더 이상 사용할 수 없습니다.

AWS STS와 임시 자격 증명05-02

STS API 비교 — AssumeRole 계열과 GetSessionToken/GetFederationToken

역할을 맡는 AssumeRole 계열과 기존 사용자 자격을 임시 자격으로 바꾸는 GetSessionToken/GetFederationToken은 호출 주체·유효 기간·권한 범위가 서로 다르다.

#1문제 상황

STS에는 여러 API가 있는데, 그 차이를 모르면 상황에 맞지 않는 API를 호출하게 됩니다. 예를 들어 다른 역할의 권한으로 작동하고 싶을 때 GetSessionToken을 호출하면 기존 사용자의 권한만 임시 자격으로 바뀌므로 원하는 권한을 얻을 수 없습니다.

#2핵심 질문

어떤 상황에서 AssumeRole을 쓰고 어떤 상황에서 GetSessionToken이나 GetFederationToken을 써야 할까요?

#3동작 예시

AssumeRole은 호출자가 대상 역할의 신뢰 정책 조건을 만족하는지 확인 후, 조건을 만족하면 그 역할의 권한으로 임시 자격 증명을 발급합니다. 반면 GetSessionToken은 호출한 사용자 자신의 기존 자격을 가지고 임시 버전만 만들어주므로, 호출자의 권한은 변하지 않습니다.

#4동작 과정

  1. AssumeRole호출자의 신원과 권한을 확인하고, 대상 역할의 신뢰 정책 조건(예: 특정 AWS 계정인지, 특정 외부 ID를 전달했는지)을 검증한 후, 조건을 만족하면 그 역할의 권한으로 임시 자격을 발급합니다.
  2. GetSessionToken/GetFederationToken호출자의 기존 자격을 확인하고, 호출자의 권한에서 더 제한된 권한으로 임시 자격을 발급합니다(선택적 세션 정책으로 제한). 호출자의 기본 권한을 초과할 수 없습니다.
  3. 사용 결과의 차이AssumeRole의 결과는 다른 역할의 권한이고, GetSessionToken의 결과는 같은 사용자이지만 더 제한된 권한입니다.

#5한 줄 요약

AssumeRole은 다른 역할의 신뢰 정책 조건을 확인한 후 그 역할의 권한으로 전환하고, GetSessionToken/GetFederationToken은 호출자 자신의 권한을 임시 버전으로 바꾼다는 점의 근본적인 차이

#1문제 상황

AWS STS는 기본적으로 글로벌 엔드포인트(sts.amazonaws.com)를 제공하며, 이 엔드포인트는 us-east-1 리전에 집중되어 있습니다. 따라서 다른 리전의 애플리케이션이나 사용자가 STS를 호출할 때 지연이 발생합니다. 또한 글로벌 엔드포인트가 장애나 과부하 상태가 되면 다른 리전의 서비스도 영향을 받습니다.

#2핵심 질문

#3동작 예시

STS는 글로벌 엔드포인트 외에 각 AWS 리전별 엔드포인트를 제공합니다(예: ap-northeast-1, eu-west-1). 해당 리전의 엔드포인트를 활성화하고 SDK나 CLI에서 그 리전을 지정하면, 요청이 가장 가까운 곳에서 처리되므로 지연이 줄어듭니다.

#4동작 과정

  1. AWS IAM 콘솔에서 STS 리전 엔드포인트 활성화필요한 각 리전별 STS 엔드포인트를 활성화합니다. 기본적으로 글로벌 엔드포인트는 항상 활성화되어 있고, 추가 리전은 선택적으로 활성화합니다.
  2. SDK 또는 CLI 설정에서 리전 지정애플리케이션 코드에서 STS 클라이언트를 생성할 때 사용할 리전을 명시적으로 지정합니다(예: region='ap-northeast-1').
  3. 요청 자동 라우팅이후 STS 요청은 지정된 리전의 엔드포인트로 자동 라우팅되므로, 지연이 감소하고 글로벌 엔드포인트 장애의 영향을 덜 받습니다.

#5한 줄 요약

STS 리전 엔드포인트를 활성화해 지리적으로 가까운 곳에서 임시 자격을 발급받도록 라우팅함으로써 지연을 줄이고 장애 격리를 개선한다는 것

AWS STS와 임시 자격 증명05-06

세션 태그와 ABAC(속성 기반 접근 제어)

역할을 맡을 때 키-값 세션 태그를 전달해, 사용자 속성과 리소스 태그를 비교하는 방식으로 권한을 동적으로 부여한다.

#1문제 상황

전통적인 IAM 정책은 리소스 ARN이나 작업(Action)을 하드코딩합니다. 예를 들어 개발자 역할의 정책에 "arn:aws:s3:::project-a-bucket/*에 접근 허용"이라고 써야 합니다. 사용자나 프로젝트가 많아지면 각각에 대한 정책을 모두 작성해야 하고, 사용자가 다른 프로젝트로 옮기면 정책을 변경해야 합니다.

#2핵심 질문

사용자의 부서, 팀, 프로젝트 같은 속성에 따라 자동으로 권한을 달리할 수 있을까요?

#3동작 예시

AssumeRole을 호출할 때 세션 태그(키-값 쌍)를 Tags 파라미터로 전달합니다. 예를 들어 {Key: "Department", Value: "Engineering"} 태그를 전달하면, 권한 정책에서 aws:PrincipalTag/Department 조건으로 이 값을 확인할 수 있습니다. 정책에서 "Department == Engineering인 경우에만 그 리소스 접근 허용"이라고 쓰면, 같은 역할을 맡아도 태그 값에 따라 권한이 동적으로 결정됩니다.

#4동작 과정

  1. 세션 태그와 함께 AssumeRole 호출AssumeRole API에 역할 ARN과 함께 키-값 쌍의 세션 태그를 전달합니다(예: Department, Team, Project 태그).
  2. 권한 정책에서 세션 태그 조건 확인역할의 권한 정책에 aws:PrincipalTag/키 == 값 형태의 조건을 추가합니다. AWS IAM이 정책을 평가할 때 현재 세션의 태그와 비교합니다.
  3. 동적 권한 부여조건이 일치하면 해당 작업이 허용되고, 일치하지 않으면 거부됩니다. 같은 역할이어도 세션 태그에 따라 접근 가능한 리소스가 달라집니다.

#5한 줄 요약

역할을 맡을 때 세션 태그라는 동적 속성을 지정하고, 권한 정책에서 그 속성을 조건으로 사용해 접근을 제어하는 속성 기반 접근 제어(ABAC)를 구현한다는 것

페더레이션 시나리오 개관

회사 디렉터리나 외부 로그인으로 이미 인증된 사용자를 IAM 사용자 생성 없이 역할로 매핑해 AWS 에 접근시키는 방식의 전체 그림.

#1문제 상황

보통 AWS에 접근하려면 IAM 사용자를 하나씩 만들어야 하고, 각 사용자에게 비밀번호나 접근 키를 발급해 관리합니다. 하지만 많은 조직은 이미 Active Directory, Okta, Google Workspace 같은 디렉터리 서비스에서 직원을 관리하고 있고, 직원들이 이미 그곳에서 인증됩니다. 그런데 AWS 접근을 위해 각 직원마다 IAM 사용자를 따로 만들고 비밀번호를 다시 발급하고 관리하는 것은 비효율적이고 보안 위험을 증가시킵니다.

#2핵심 질문

이미 다른 인증 서비스에서 신뢰받는 사용자를 AWS IAM 사용자 생성 없이 역할로 직접 매핑해 접근시킬 수 있을까요?

#3동작 예시

회사의 Active Directory에서 직원이 인증되면, 그 인증 정보를 AWS가 신뢰하는 공급자로 등록하고, AWS 역할 신뢰 정책을 그 공급자가 발급한 토큰만 받도록 설정합니다. 직원이 콘솔에 접근할 때 Active Directory 인증 토큰을 AWS에 제시하면, AWS가 그 토큰을 검증 후 역할을 부여하고 세션을 열어줍니다.

#4동작 과정

  1. 외부 신원 공급자 등록AWS IAM에 신뢰할 외부 인증 서비스(Active Directory, Okta, Google 등)를 공급자로 등록합니다.
  2. 역할의 신뢰 정책 설정해당 공급자가 발급한 토큰만 그 역할을 맡도록 역할의 신뢰 정책을 구성합니다.
  3. 사용자 인증 및 접근사용자가 외부 서비스에서 인증되고 토큰을 받으면, 그 토큰으로 AWS 역할을 맡아 접근합니다.

회사 디렉터리나 외부 로그인 서비스의 기존 인증을 AWS가 신뢰해 IAM 사용자 생성 없이 역할로 직접 매핑하는 방식

OIDC 자격 증명 공급자와 웹 아이덴티티 페더레이션

Google·GitHub Actions·Kubernetes 같은 OIDC 공급자가 발급한 토큰을 신뢰해 역할을 맡게 하는 구성.

#1문제 상황

Google, GitHub, Kubernetes 같은 서비스는 각각 자신만의 인증 토큰을 발급합니다. 이들을 직접 지원하려면 AWS가 각 서비스의 토큰 형식과 검증 방법을 일일이 구현해야 합니다. 또한 새로운 서비스가 나올 때마다 AWS가 대응해야 하므로 확장성이 떨어집니다.

#2핵심 질문

표준화된 토큰 형식을 통해 여러 다른 외부 서비스의 사용자와 워크로드를 AWS에서 일관되게 인증할 수 있을까요?

#3동작 예시

GitHub Actions 가 CI/CD 작업을 실행할 때, GitHub이 발급한 OIDC 토큰을 AWS STS에 제시합니다. AWS는 미리 GitHub을 OIDC 공급자로 등록했고 GitHub의 공개키를 알고 있으므로, 토큰의 서명을 검증해 신뢰한 후 임시 자격 증명을 발급합니다.

#4동작 과정

  1. OIDC 공급자 등록외부 서비스(Google, GitHub, Kubernetes 등)의 OIDC 메타데이터 URL을 AWS에 등록해 AWS가 그 공급자의 공개키를 획득합니다.
  2. 토큰 발급 및 교환외부 서비스가 사용자나 워크로드를 인증해 OIDC 토큰을 발급하면, 그 토큰으로 AWS STS(Security Token Service, 임시 자격 증명 발급 서비스)에 접근권을 요청합니다.
  3. 토큰 검증 및 역할 부여AWS가 공개키로 토큰 서명을 검증하고, 토큰 내용이 역할 신뢰 정책과 일치하면 임시 자격 증명을 발급합니다.

외부 신원과의 연동06-03

SAML 2.0 페더레이션 구성과 어설션

기업 IdP 가 보내는 SAML 어설션의 속성으로 역할과 세션을 결정해 AWS 접근을 허용하는 구성.

#1문제 상황

많은 기업은 Okta, Ping Identity, Active Directory Federation Services 같은 엔터프라이즈 SSO(Single Sign-On) 서비스를 운영하고 있어서 직원들이 이미 그곳에서 인증됩니다. 그러나 AWS는 이들 서비스와 직접 통신하는 대신, 표준화된 메시지 형식인 SAML(Security Assertion Markup Language)을 통해서만 인증 정보를 받으므로, 기업은 SAML 형식으로 인증 정보를 AWS에 전달하도록 설정해야 합니다.

#2핵심 질문

기업 SSO 서비스의 인증 정보를 SAML 형식으로 AWS에 보내 역할을 결정할 수 있을까요?

#3동작 예시

직원이 회사의 Okta 로그인 페이지에서 인증되면, Okta는 그 직원의 부서, 역할 등의 정보를 담은 SAML 어설션(인증 증명서)을 생성합니다. 사용자가 AWS 콘솔로 이동할 때 Okta는 이 어설션을 AWS에 전달하고, AWS는 Okta의 공개키로 어설션 서명을 검증한 후, 어설션 속성(예: "부서=엔지니어링")을 읽어 매핑된 역할을 부여합니다.

#4동작 과정

  1. SAML 공급자 등록AWS에 기업 IdP(Identity Provider)의 메타데이터를 등록해 AWS가 그 IdP의 공개키와 인증서 정보를 알게 합니다.
  2. SAML 어설션 생성 및 전달사용자가 기업 IdP에서 인증되면 IdP가 사용자 속성을 포함한 SAML 어설션을 생성해 AWS로 전송합니다.
  3. 어설션 검증 및 역할 매핑AWS가 공개키로 어설션 서명을 검증하고, 어설션의 속성(department, role 등)을 읽어 미리 설정된 매핑에 따라 IAM 역할과 세션 시간을 결정합니다.

#5한 줄 요약

OIDC나 SAML은 표준화된 페더레이션이지만, 기업이 독자적으로 개발한 인증 시스템을 쓰거나 매우 특수한 비즈니스 로직이 필요한 경우가 있습니다. 이런 경우 표준 페더레이션이 아닌 자체 시스템과 AWS를 연결해야 하는데, 사용자를 AWS 콘솔로 직접 로그인시키는 방법이 명확하지 않습니다.

#2핵심 질문

자체 인증 시스템의 사용자가 AWS 콘솔에 자동으로 로그인하게 할 수 있을까요?

#3동작 예시

회사의 자체 로그인 페이지에서 사용자가 인증되면, 백엔드는 AWS STS API를 호출해 그 사용자를 위한 임시 자격 증명(Access Key, Secret Access Key, Session Token)을 받습니다. 그 자격 증명을 사용해 AWS 콘솔 로그인 URL을 생성한 후, 사용자의 브라우저를 그 URL로 리다이렉트하면 사용자가 암호를 입력하지 않고도 콘솔에 로그인됩니다.

#4동작 과정

  1. 사용자 인증자체 인증 시스템이 사용자를 확인하고 인증합니다.
  2. STS 임시 자격 증명 획득백엔드가 AWS STS의 AssumeRole API를 호출해 해당 사용자에게 매핑된 역할의 임시 자격 증명을 받습니다.
  3. 콘솔 로그인 URL 생성 및 리다이렉트임시 자격 증명으로 콘솔 로그인 URL을 생성하고 사용자 브라우저를 그 URL로 리다이렉트하면 사용자가 자동 로그인됩니다.

외부 신원과의 연동06-05

아웃바운드 페더레이션 — AWS 워크로드가 외부 서비스에 인증

반대 방향으로, AWS 역할이 발급받은 토큰을 외부 서비스가 신뢰하게 해 장기 비밀 없이 인증하는 방식.

#1문제 상황

지금까지의 페더레이션은 모두 외부에서 AWS로 들어오는 단방향입니다. 반대로 AWS에서 실행되는 워크로드(예: Lambda, EC2)가 외부 서비스(예: GitHub, 다른 클라우드)에 접근할 때는 어떻게 할까요? 보통은 외부 서비스의 API 토큰이나 비밀번호를 AWS에 저장했다가 사용하는데, 이는 장기 비밀을 관리해야 하므로 보안이 취약합니다.

#2핵심 질문

AWS 워크로드가 장기 비밀번호 없이 외부 서비스에 자신의 정체를 증명하고 인증받을 수 있을까요?

#3동작 예시

AWS Lambda 함수가 GitHub의 API에 접근해 배포해야 할 때, Lambda는 AWS STS를 통해 임시 토큰을 생성합니다. 그 토큰에는 "이것은 특정 AWS 계정의 특정 역할이 만든 것"이라는 정보가 서명되어 있습니다. GitHub이 미리 그 AWS 계정의 공개키를 신뢰하도록 설정했다면, GitHub이 토큰을 검증해 Lambda를 인증하고 API 접근을 허용합니다.

#4동작 과정

Effect, Action, NotAction

Effect는 허용(Allow)/거부(Deny)를 정하고, Action은 대상 API 작업 목록을, NotAction은 나열한 작업만 빼고 나머지 전부를 가리킨다.

#1문제 상황

권한의 핵심은 "어떤 작업을 허용하거나 거부할 것인가"인데, 허용할 작업을 일일이 나열하면 새로운 AWS 서비스나 API가 추가될 때마다 정책을 갱신해야 합니다. 또한 "이 서비스는 제외하고 모두 허용"처럼 역으로 생각하려면 허용되지 않은 것들을 일일이 찾아 나열해야 하므로 번거롭습니다.

#2핵심 질문

특정 작업들을 효율적으로 허용하거나, 제외된 작업들을 제외한 나머지를 일괄 허용할 수 있을까요?

#3동작 예시

"Action": ["ec2:*"]는 EC2 서비스의 모든 API 작업을 허용하고, "NotAction": ["iam:*", "s3:*"]는 IAM과 S3를 제외한 모든 API 작업을 허용한다는 뜻입니다. 와일드카드와 함께 사용하면 정책을 간결하게 유지할 수 있습니다.

#4동작 과정

  1. Effect 결정허용(Allow) 또는 거부(Deny)를 먼저 결정합니다.
  2. Action 또는 NotAction 지정영향받을 작업 범위를 정합니다. Action은 나열된 작업만 해당되고, NotAction은 나열된 작업을 제외한 모든 작업이 해당됩니다.
  3. AWS의 판단사용자의 API 요청이 들어오면 AWS는 요청된 작업을 Effect, Action/NotAction과 비교해 허용할지 거부할지 판단합니다.

Resource, NotResource, Principal, NotPrincipal

Resource/NotResource는 작업이 적용될 대상 ARN을, Principal/NotPrincipal은 리소스 기반 정책에서 누가 요청자인지를 지정한다.

#1문제 상황

지금까지 정책으로 "누가" 어떤 작업을 할 수 있는지 정했습니다. 하지만 "무엇에" 그 작업을 할 수 있는지, 그리고 누가 요청자인지를 구체적으로 지정할 필요가 있습니다.

#2핵심 질문

정책이 적용될 대상 리소스와 그 리소스에 접근할 주체를 구체적으로 지정하려면 어떻게 해야 할까요?

#3동작 예시

S3 버킷의 특정 폴더 안에 있는 파일들에만 접근 권한을 주고 싶을 때, Resource는 그 폴더의 ARN(리소스 식별자)을 명시합니다. 또는 Lambda 함수가 특정 IAM 역할만 호출할 수 있게 하려면, 리소스 기반 정책의 Principal에 그 역할의 ARN을 명시합니다.

#4동작 과정

  1. 대상 지정 (Resource/NotResource)Resource는 작업이 적용될 AWS 리소스를 ARN으로 명시하고, NotResource는 그 반대로 "이 리소스들 제외"를 지정해 정책의 범위를 좁힙니다.
  2. 요청자 지정 (Principal/NotPrincipal)리소스 기반 정책(S3 버킷 정책 등)에서만 사용되며, 누가 그 리소스에 접근할 수 있는지(사용자·역할·서비스)를 명시합니다.
  3. 두 요소의 차이자격 증명 기반 정책은 Resource만 사용하고(사용자에게 붙으니까 "누가"는 이미 정해짐), 리소스 기반 정책은 Principal도 함께 사용합니다(리소스에 붙으니까 "누가" 접근할지 명시해야 함).

#4동작 과정

  1. 정책 변수 (Policy Variables)${aws:username}, ${aws:userid} 같은 변수는 요청 시점의 실제 값으로 자동 치환되어 정책 하나를 여러 사용자에게 재사용 가능하게 합니다.

AWS의 아홉 가지 정책 유형 한눈에

AWS 권한은 자격 증명 기반·리소스 기반·권한 경계·SCP·RCP·세션 정책·ACL·VPC 엔드포인트 정책 등 여러 유형으로 나뉘며, 각각 적용 지점과 역할이 다르다.

#1문제 상황

지금까지 "정책을 사용자에게 붙인다" 정도로만 이해했습니다. 하지만 AWS에는 정책을 붙이는 위치와 방식에 따라 여러 유형이 있습니다.

#2핵심 질문

AWS 권한 제어에 사용되는 모든 정책 유형이 무엇이고, 각각 어디에 어떻게 적용될까요?

#3동작 예시

어떤 사용자가 S3 파일에 접근하려면, 그 사용자에게 붙은 정책(자격 증명 기반 정책)과 그 S3 버킷에 붙은 정책(리소스 기반 정책)이 모두 허용해야 합니다. 또한 조직 내에서 SCP(서비스 제어 정책)로 특정 서비스 자체를 차단했다면, 개별 정책이 허용해도 접근이 불가능합니다.

#4동작 과정

  1. 자격 증명 기반 정책 (4가지)사용자·그룹·역할에 붙는 정책이며, 관리형 정책(재사용 가능)과 인라인 정책(일회용), 그리고 권한 경계(상한선)와 세션 정책(임시 제한)이 있습니다.
  2. 리소스 기반 정책 (2가지)S3 버킷, SQS 큐 등 특정 리소스에 붙는 정책이며, 리소스 기반 정책과 ACL(접근 제어 리스트, 더 단순한 형식)이 있습니다.
  3. 조직 수준의 제어 정책 (3가지)SCP(전체 계정의 권한 상한선), RCP(권한 위임 경계), VPC 엔드포인트 정책(특정 VPC 내에서만 접근 허용)으로, 개별 정책보다 상위에서 전체 권한을 제약합니다.

정책을 사용자·리소스·조직 수준에서 계층적으로 적용해서 개별 권한부터 전사적 제약까지 일관되게 관리하는 것

#1문제 상황

정책을 "사용자가 무엇을 할 수 있는가"만 정의했습니다. 하지만 "리소스가 누구에게 접근을 허용할 것인가"도 별도로 정의해야 하는 경우가 있습니다.

#2핵심 질문

정책을 사용자에게 붙일 때와 리소스에 붙을 때 어떻게 다르고, 어느 것을 사용해야 할까요?

#3동작 예시

사용자 Alice가 S3 버킷 my-bucket의 파일을 다운로드하려면, (1) Alice의 IAM 사용자에 붙은 정책에서 "s3:GetObject" 작업을 허용해야 하고, (2) my-bucket에 붙은 정책에서도 Alice(또는 그 역할)의 Principal을 허용해야 합니다. 이 둘 중 하나라도 거부하면 접근이 불가능합니다.

#4동작 과정

  1. 자격 증명 기반 정책사용자·그룹·역할에 붙는 정책이며, "이 주체가 어떤 작업을 할 수 있는가"를 정의합니다. Principal을 명시하지 않습니다(주체가 이미 정해짐).
  2. 리소스 기반 정책S3 버킷, Lambda 함수, SNS 주제 등 특정 리소스에 붙는 정책이며, "이 리소스에 누가 접근할 수 있는가"를 정의합니다. Principal을 명시해야 합니다.
  3. 권한 판정 로직양쪽 정책이 모두 "허용"해야 접근 가능하고(AND 조건), 둘 중 하나라도 "거부"하면 접근 불가능합니다(거부가 최우선).

관리형 정책과 인라인 정책, 그리고 선택 기준

여러 대상에 재사용·버전 관리되는 독립 객체가 관리형 정책, 특정 하나에만 박혀 함께 삭제되는 것이 인라인 정책이다.

#1문제 상황

정책을 작성할 때마다 어디에 저장하고 어떻게 관리할지 정하지 않았습니다. 같은 정책을 여러 사용자에게 붙이려면 복사해야 하고, 정책을 수정할 때마다 모든 복사본을 수정해야 합니다.

#2핵심 질문

정책을 작성할 때 독립적인 객체로 만들지, 아니면 사용자에게 바로 박아넣을지 어떻게 판단할까요?

#3동작 예시

회사의 모든 개발자가 AWS CloudWatch 로그 조회 권한을 가져야 한다면, 관리형 정책 하나를 만들어서 모든 개발자에게 붙입니다. 나중에 권한을 추가해야 하면 그 정책 하나만 수정하면 됩니다. 반면 특정 프로젝트 리더만 그 프로젝트의 S3 버킷에 접근할 수 있게 하려면, 그 리더의 사용자 객체에 인라인 정책으로 박아넣습니다.

#4동작 과정

  1. 관리형 정책독립적인 AWS 리소스로 존재하며, 버전 관리·변경 이력 추적이 가능하고, 여러 사용자·그룹·역할에 붙을 수 있습니다. AWS가 제공하는 사전 정의 관리형 정책과 사용자가 만드는 고객 관리형 정책이 있습니다.
  2. 인라인 정책특정 사용자·그룹·역할에만 종속된 정책이며, 그 주체가 삭제되면 함께 삭제됩니다. 사용 통계나 버전 관리가 없고, 일회용 또는 매우 특수한 권한에 쓰입니다.
  3. 선택 기준재사용할 가능성이 있거나 여러 대상에 붙으려면 관리형 정책, 특정 사용자만의 특수한 권한은 인라인 정책으로 판단합니다.

권한 경계(permissions boundary)

자격 증명에 부여할 수 있는 권한의 최대 한도를 정하는 정책으로, 권한을 주지는 않고 상한선만 씌운다.

#1문제 상황

기존에 정책을 연결하면 그 정책이 허용하는 모든 권한이 즉시 자격 증명에 부여된다. 예를 들어 관리자가 실수로 S3 전체 접근 권한이 있는 정책을 신입 개발자에게 연결해버리면, 그 신입은 즉시 조직의 모든 S3 버킷을 지울 수 있게 된다. 정책을 연결하는 것으로는 실수를 제한할 방법이 없다.

#2핵심 질문

자격 증명에 부여된 권한의 최대 범위를 사전에 제한할 수 있는 방법은 없을까?

#3동작 예시

권한 경계는 자격 증명이 가질 수 있는 권한의 상한선을 먼저 정해두고, 그 위에만 정책을 연결하는 방식이다. 관리자가 권한 경계를 "S3와 EC2만 허용"으로 설정해두면, 그 자격 증명에 "전체 AWS 권한"이라는 정책을 연결해도 실제로는 S3와 EC2 범위 내에서만 작동한다. 정책과 권한 경계의 교집합만 최종 허용된다.

#4동작 과정

  1. 권한 경계 설정자격 증명에 상한선이 될 정책을 권한 경계로 지정한다.
  2. 정책 연결평소처럼 권한 정책을 자격 증명에 연결한다.
  3. 교집합 판정요청 시 정책 허용 + 권한 경계 허용이 동시에 맞아야만 최종 허용된다.

#1문제 상황

IAM 정책은 개별 자격 증명(사용자, 역할) 차원에서만 작동한다. 하지만 조직 구조에서는 계정 하나 전체나 여러 계정, 네트워크 대역, 리소스 공유 같은 상위 수준에서도 제어가 필요하다. IAM 정책만으로는 계정 수준의 권한을 통제하거나 조직 전체 정책을 일괄 적용할 수 없다.

#2핵심 질문

개별 자격 증명을 넘어 조직·계정·네트워크·리소스 공유 수준에서 권한을 제어할 수 있는 방법은 무엇인가?

#3동작 예시

SCP(Service Control Policy)는 조직의 계정들에 대해 일괄적으로 권한의 상한선을 적용하는 정책이다. 예를 들어 조직이 "모든 계정에서 삭제 작업은 금지"로 SCP를 설정하면, 그 조직 소속 계정들의 모든 사용자는 아무리 많은 권한이 있어도 삭제 작업을 할 수 없다. 각 계층(조직, 부서, 계정)마다 서로 다른 제어 도구가 있다.

#4동작 과정

  1. SCP/RCP 설정조직 또는 계정 수준에서 모든 자격 증명에 적용할 상한선 정책을 지정한다.

정책 평가 로직 — 기본 거부에서 최종 결정까지

모든 요청은 기본 거부에서 출발해 명시적 거부 > 명시적 허용 > 암묵적 거부 순서로 최종 허용 여부가 결정된다.

#1문제 상황

정책이 여러 개 붙으면 어느 정책이 우선되는지, 거부가 있으면 허용이 있어도 작동하는지 불확실하다. 정책들이 상충할 때 최종 허용 여부를 어떤 규칙으로 결정하는지 몰라서, 예상 밖의 거부나 허용이 생긴다.

#2핵심 질문

여러 정책이 있을 때 어느 것을 우선으로 최종 허용 여부를 결정하는 규칙은 무엇인가?

#3동작 예시

모든 요청은 기본 거부 상태에서 출발한다. 조건을 만족하는 명시적 거부(Explicit Deny) 정책이 하나라도 있으면 최종 거부가 된다. 명시적 거부가 없으면 명시적 허용(Explicit Allow) 정책이 하나 이상 있는지 확인하고, 있으면 최종 허용, 없으면 암묵적 거부(Implicit Deny)로 최종 거부된다.

#4동작 과정

  1. 기본 거부 상태 시작요청은 거부 상태에서 평가를 시작한다.
  2. 명시적 거부 확인정책 중 해당 요청을 명시적으로 거부하는 것이 하나라도 있으면 즉시 거부되고 평가가 끝난다.

#2핵심 질문

#4동작 과정

  3. 신뢰 계정 리소스 권한 확인신뢰 계정 역할의 권한 정책에서 접근하려는 리소스 작업이 허용되는지 확인한다.

관리자·개발자·재무 담당 등 흔한 직무에 맞춰 AWS가 미리 만들어 둔 관리형 정책과, IAM 서비스가 제공하는 AWS 관리형 정책 목록이다.

→ 09-02 참조

#1문제 상황

권한 정책을 직접 만들면 맞는지 확인하기 어렵고, 직무에 맞는 권한을 모두 고려하기 쉽지 않다. 관리자는 매번 어떤 권한을 줄지 일일이 정하고, 실제로 그것이 직무에 맞는지 검토해야 한다.

#2핵심 질문

흔한 직무들이 실제로 필요한 권한이 이미 정해진 패턴이 있을까?

#3동작 예시

AWS는 "개발자", "운영 담당자", "재무 담당" 같은 직무를 자주 하는 사람들을 위해 이미 정책을 만들어두었다. 예를 들어 "개발자 정책"에는 EC2, RDS, S3 등을 다루는 권한이 미리 모여 있다.

#4동작 과정

  1. 직무 선택사용자의 직무(개발자, 운영 담당자, 재무 담당 등)를 정한다.
  2. AWS 관리형 정책 확인AWS가 그 직무를 위해 이미 만들어둔 관리형 정책을 찾는다.
  3. 정책 연결AWS 관리형 정책을 사용자나 역할에 바로 연결한다.

#5한 줄 요약

직무별로 필요한 권한을 미리 패키징한 관리형 정책을 제공해, 권한 설계 시간을 크게 줄이는 것

태그로 접근을 제어하기

리소스와 자격 증명에 붙인 태그를 정책 조건으로 비교해, 정책을 일일이 늘리지 않고도 접근을 나누는 ABAC 방식이다.

#1문제 상황

권한을 나누려면 보통 사용자마다, 역할마다 정책을 따로 만든다. 예를 들어 A팀에는 A 프로젝트 리소스만 접근하게 하고, B팀에는 B 프로젝트 리소스만 접근하게 하려면, 정책을 여러 개 만들어야 한다. 팀이나 프로젝트가 늘어나면 정책도 계속 늘어난다.

#2핵심 질문

정책을 일일이 만들지 않고도, 리소스 태그 하나로 접근을 나눌 수는 없을까?

#3동작 예시

AWS 리소스에 "project: alpha", "owner: devteam" 같은 태그를 붙인다. 정책에서 조건을 만들어 "내가 가진 'project' 태그와 리소스의 'project' 태그가 같은 경우만 접근 허용"이라고 정한다. 정책을 새로 만들지 않아도 된다.

#4동작 과정

  1. 리소스 태그 지정EC2, RDS, S3 같은 각 리소스에 project, owner 같은 태그를 붙인다.
  2. 자격 증명 태그 지정사용자나 역할에도 같은 형식의 태그를 붙인다.
  3. 정책 조건 설정정책에서 "리소스 태그 == 자격 증명 태그"인 경우만 접근을 허용한다고 명시한다.

#5한 줄 요약

태그 일치 여부로 접근을 제어해, 정책을 따로 만들지 않고도 팀이나 프로젝트별 접근을 자동으로 나누는 것

데이터 퍼리미터로 신뢰 경계 긋기

신뢰하는 자격 증명·리소스·네트워크의 범위를 정책으로 못 박아, 조직 밖으로의 데이터 이동을 원천 차단하는 가드레일이다.

#1문제 상황

기존 권한 정책은 "누가 어떤 리소스에 접근할 수 있는가"만 제어한다. 하지만 데이터가 조직 밖의 계정이나 서비스로 유출되는 것은 막지 못한다. 권한을 받은 사람이 데이터를 외부로 빼내려고 하면 정책만으로는 막을 수 없다.

#2핵심 질문

데이터가 신뢰할 수 있는 계정이나 네트워크에서만 오고 가도록 보장할 수는 없을까?

#3동작 예시

정책을 만들 때, 접근을 허용하되 그 데이터가 조직 내부 AWS 계정으로만 복사되거나, 특정 네트워크에서만 보내진다는 조건을 추가한다. 이 조건을 벗어나는 요청은 "허용 권한이 있어도" 막힌다.

#4동작 과정

  1. 신뢰 범위 정의신뢰하는 AWS 계정, IP 범위, 네트워크를 정한다.
  2. 정책에 조건 추가정책에서 데이터 흐름이 이 범위 안에 있는 경우만 허용한다는 조건을 명시한다.
  3. 범위 밖 요청 차단범위 밖에서 온 요청은 권한이 있어도 정책 조건에 걸려 차단된다.

#5한 줄 요약

권한을 줄 때 데이터 이동 방향과 범위를 동시에 제한해, 조직 밖으로의 데이터 유출을 정책 수준에서 원천 차단하는 것

Account access manager로 워크포스에 계정 접근 할당

회사 직원(워크포스) 자격 증명에 여러 AWS 계정의 IAM 역할을 할당해, 접근 포털에서 골라 들어가게 해주는 기능이다.

#1문제 상황

대규모 조직에서 직원들이 여러 AWS 계정에 접근해야 할 때, 각 계정마다 따로 로그인해야 한다. 어느 계정에 어떤 역할이 있는지 추적하기 어렵고, 직원이 어떤 계정에 접근할 수 있는지 관리하기도 복잡하다.

#2핵심 질문

회사 직원이 여러 AWS 계정에 쉽게 접근하면서, 어느 계정에 무슨 역할이 있는지는 한 곳에서 관리할 수는 없을까?

#3동작 예시

Account access manager는 직원 디렉토리에 있는 직원 계정 정보를 AWS와 연결하고, 그 직원이 접근 가능한 여러 AWS 계정과 역할을 한 포털에서 보여준다. 직원이 포털에서 원하는 계정의 역할을 클릭하면 그 계정으로 로그인된다.

#4동작 과정

  1. 직원 디렉토리 연결회사의 직원 정보(직원 ID, 직급, 소속팀)를 AWS와 연결한다.
  2. 계정과 역할 할당각 직원이 접근할 수 있는 AWS 계정과 그 계정 내 역할을 정해서 할당한다.
  3. 포털에서 접근직원이 포털에 로그인하면 자신이 접근 가능한 모든 계정 목록이 나타나고, 클릭해서 선택할 수 있다.

#5한 줄 요약

직원 ID와 AWS 계정을 중앙에서 연결해, 여러 AWS 계정에 일관되게 접근권을 할당하고 관리하는 것

임시 위임으로 파트너 제품에 한시 권한 부여

파트너 애플리케이션이 필요한 순간에만 승인을 받아 한시적으로 계정 권한을 얻고, 끝나면 회수되는 위임 방식이다.

#1문제 상황

보안 업체나 모니터링 업체 같은 파트너 제품이 계정 권한이 필요할 때, 보통 장기적인 접근 자격증명을 주거나 역할을 연결해둔다. 이렇게 되면 파트너 제품이 계속 권한을 가지고 있어서, 불필요해지면 수동으로 권한을 회수해야 한다.

#2핵심 질문

파트너가 특정 작업을 하는 동안만 권한을 받고, 끝나면 자동으로 회수될 수는 없을까?

#3동작 예시

임시 위임은 파트너 애플리케이션이 권한을 요청하면, 미리 정해진 시간 동안만 유효한 임시 자격증명을 준다. 시간이 지나면 그 토큰은 자동으로 무효가 되고, 파트너는 더 이상 그 권한을 쓸 수 없다.

#4동작 과정

  1. 파트너 신청파트너 제품이 권한을 요청한다. 예: "S3 데이터를 읽기 위해 1시간 권한 필요".
  2. 승인 및 위임관리자가 요청을 승인하고, 1시간 유효기간이 있는 임시 자격증명을 발급한다.
  3. 자동 회수1시간 후 그 자격증명은 자동으로 만료되어, 파트너는 더 이상 접근할 수 없다.

#5한 줄 요약

파트너 애플리케이션에 필요한 기간만 유효한 임시 자격증명을 주고 자동으로 회수해, 불필요한 장기 권한 노출을 막는 것

IAM 보안 모범 사례와 대표 사용 사례

루트 사용자 보호, MFA, 최소 권한 등 AWS가 권장하는 IAM 운영 원칙과 그것이 쓰이는 실제 업무 시나리오다.

#1문제 상황

IAM 권한 설정을 명확한 기준 없이 하면, 시간이 지날수록 권한 구조가 복잡해지고 누가 무엇을 할 수 있는지 파악하기 어려워진다. 특히 루트 사용자(AWS 계정을 처음 만들 때 자동 생성되는 관리자)를 일상 작업에 계속 쓰면, 그 계정 정보가 유출될 때 전체 AWS 환경이 손상될 위험이 크다.

#2핵심 질문

계정 보안 위험을 줄이고 권한을 일관되게 관리하려면 어떤 원칙을 따라야 할까?

#3동작 예시

루트 사용자는 계정 생성과 결제 정보 변경 같은 중요도 높은 작업만 하고, 일상적인 서비스 운영·개발·테스트는 IAM으로 만든 일반 사용자나 역할에게 필요한 권한만 주는 방식이다. 각 사용자나 역할은 자신이 해야 할 작업에 필요한 최소한의 권한만 받는다.

#4동작 과정

  1. 루트 사용자 보호루트 사용자 액세스 키는 만들지 않고, 루트 사용자로는 콘솔 로그인할 때만 MFA(다중 인증, 휴대폰 인증 같은 추가 확인 단계)를 반드시 활성화한다.
  2. 최소 권한 원칙 적용각 IAM 사용자·역할·그룹에 필요한 권한만 부여하고, "모든 권한 허용" 같은 와일드카드는 피한다.
  3. 모니터링과 정기 검토CloudTrail로 모든 API 호출을 기록하고, Access Analyzer로 권한 설정을 정기적으로 점검해 과도하거나 불필요한 권한을 찾아낸다.

#5한 줄 요약

IAM 보안 모범 사례는 루트 사용자를 보호하고 최소 권한 원칙을 적용해 권한 누수로 인한 보안 사고를 예방하는 운영 원칙이다.

IAM 밖의 보안 기능과 데이터 보호·복원력·규정 준수

IAM만으로 끝나지 않는 보안 — 암호화·로깅·복원력·컴플라이언스 등 주변 서비스와 책임 공유 모델을 함께 보는 관점이다.

#1문제 상황

IAM만으로는 전체 보안을 완성할 수 없다. IAM은 "누가 무엇을 할 수 있나"를 제어하는 접근 통제일 뿐이다. 저장된 데이터를 암호화하지 않으면, 접근 권한이 있는 사람이 데이터를 평문으로 읽을 수 있다. API 호출을 기록하지 않으면, 누가 언제 뭘 했는지 알 수 없다. 백업이 없으면, 실수로 데이터를 삭제했을 때 복구할 방법이 없다.

#2핵심 질문

IAM 권한 제어만으로는 부족한 보안·복원력·컴플라이언스 영역을 어떻게 함께 다뤄야 할까?

#3동작 예시

IAM으로 S3 버킷(저장소) 접근자를 제한하고, KMS(암호화 서비스)로 그 버킷의 데이터를 암호화하고, CloudTrail로 버킷의 모든 접근 기록을 남기고, S3 버전 관리로 실수로 삭제한 파일을 복구할 수 있도록 하는 방식이다.

#4동작 과정

  1. 접근 통제IAM 정책으로 누가 S3 버킷에 접근할 수 있는지, 어떤 작업을 할 수 있는지 정의한다.

IAM API 호출과 SigV4 서명

IAM·STS API 요청은 액세스 키로 만든 AWS Signature Version 4 서명을 붙여야 인증된다.

#1문제 상황

API를 호출할 때 액세스 키를 요청 헤더에 직접 넣으면 키 자체가 네트워크에서 노출되고, 요청이 변조되었는지 확인할 방법이 없다.

#2핵심 질문

액세스 키와 시크릿 키로 AWS 서버가 요청자를 증명하고 요청 무결성을 보장하려면 어떻게 할까?

#3동작 예시

SigV4는 액세스 키, 시크릿 키, 요청 내용(HTTP 메서드·경로·헤더·바디)을 모두 포함한 암호 서명을 만들어 요청 헤더에 붙인다. AWS 서버는 이 서명을 검증해 요청자 신원과 무결성을 확인한다.

#4동작 과정

  1. 요청 생성API 호출자가 HTTP 요청을 구성하고, 요청 시각(Timestamp)과 크레덴셜(credential, 즉 액세스 키)을 정의한다.
  2. 서명 계산시크릿 키로 요청 전체(HTTP 메서드, 경로, 헤더, 쿼리·바디)를 해시하여 Signature를 생성한다.
  3. 요청 전송 및 검증서명을 Authorization 헤더에 붙여 AWS로 전송하면, AWS는 같은 방식으로 서명을 재계산해 일치 여부로 요청자와 내용을 검증한다.

IAM·STS VPC 엔드포인트, 할당량, 함께 동작하는 서비스

IAM·STS를 인터페이스 VPC 엔드포인트로 사설 호출하고, 리소스 개수 할당량과 타 AWS 서비스 연동 범위를 파악한다.

#1문제 상황

EC2·Lambda 등의 컴퓨팅 리소스가 IAM·STS 요청을 인터넷 경로로 AWS 퍼블릭 엔드포인트에 보내면, 인터넷 경로를 거치므로 보안 위험이 높고, 트래픽이 인터넷으로 노출되며, VPC 경계 밖의 통신이므로 제어하기 어렵다.

#2핵심 질문

IAM·STS 요청을 VPC 내부 사설 경로로만 보내려면 어떻게 할까?

#3동작 예시

VPC 엔드포인트(PrivateLink)를 설정하면 VPC 내 리소스가 인터넷을 거치지 않고 AWS 백본 네트워크를 통해 직접 IAM·STS 서비스에 접근할 수 있다.

#4동작 과정

  1. VPC 엔드포인트 생성해당 VPC에서 IAM·STS 엔드포인트를 인터페이스 타입으로 생성하고 서브넷·보안 그룹을 할당한다.
  2. 라우팅 설정ENI(탄력적 네트워크 인터페이스)에 할당된 프라이빗 IP로 요청이 자동 라우팅되도록 설정한다.
  3. 트래픽 흐름VPC 내 리소스가 요청을 보내면 엔드포인트의 ENI를 통해 AWS 내부 네트워크로 직접 전송되고, 인터넷 게이트웨이를 거치지 않는다.
