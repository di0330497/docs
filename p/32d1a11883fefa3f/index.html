로드 밸런서가 푸는 문제와 ELB가 대신 해주는 일

들어오는 트래픽을 여러 대상에 자동으로 나눠 보내고 고장난 대상은 빼주는 관리형 분산 장치가 ELB다.

1상대의 출발점 확인

여러 대의 서버에 요청을 분산하려면 누가 어느 서버로 보낼지 결정해야 한다. 기존에는 DNS 라운드 로빈이나 수동 설정으로 이를 처리했는데, 어떤 서버가 고장 났을 때 자동으로 감지하고 그 서버로는 요청을 보내지 않는 일도 직접 관리해야 했다. 또한 트래픽이 늘어나면 어느 서버부터 부하가 높아지는지, 어떤 서버가 응답 불가 상태인지를 계속 모니터링해야 하는 번거로움이 있었다.

2질문 제기

여러 서버에 요청을 자동으로 분배하면서 동시에 고장 난 서버는 제외하는 방법은?

3구조적 핵심 예시

클라이언트가 로드 밸런서의 단일 주소로 요청을 보낸다. 로드 밸런서는 그 요청을 받은 뒤 뒤에 있는 여러 서버 중 하나를 선택해서 요청을 전달한다. 동시에 각 서버의 상태를 계속 확인해서 응답하지 않는 서버가 있으면 그 서버는 제외하고 나머지 서버들에게만 요청을 보낸다.

4단계별 동작 과정

  1. 요청 수신클라이언트가 로드 밸런서의 주소로 요청을 보낸다.
  2. 대상 선택 및 상태 확인로드 밸런서가 뒤에 있는 서버들의 상태를 확인하고 건강한 서버 중 하나를 선택한다.
  3. 요청 전달선택된 서버로 요청을 보내고 응답을 클라이언트에게 돌려보낸다.

3구조적 핵심 예시

ALB는 HTTP 헤더의 경로와 호스트명을 읽어서 판단한다(L7 애플리케이션 계층). NLB는 TCP/UDP의 포트 정보만 보고 극저지연으로 처리한다(L4 전송 계층). GWLB는 IP 패킷을 그대로 보안 어플라이언스(방화벽 같은 것)로 넘긴다(L3 네트워크 계층). CLB는 전 세대 유형으로 기본적인 L4 기능만 한다.

4단계별 동작 과정

  1. ALB (L7)HTTP/HTTPS 헤더를 읽어 경로(/api, /admin) 또는 호스트명(api.example.com, web.example.com)으로 어느 대상 그룹으로 보낼지 판단한다.
  2. NLB (L4)TCP/UDP 포트 정보만 보고 극히 빠르고 안정적으로 분산하며 고정 IP, 극저지연을 제공한다.
  3. GWLB (L3) / CLBGWLB는 IP 어플라이언스 앞단에서 동작하고, CLB는 구세대이므로 기본 L4 기능만 한다.

3구조적 핵심 예시

인터넷 경계 로드 밸런서는 공인 IP(예: 203.0.113.50)를 가지고 외부 클라이언트의 요청을 받는다. 내부(internal) 로드 밸런서는 사설 IP(예: 10.0.1.50)를 가지고 VPC 안에서만 동작하며, 웹 계층에서 데이터베이스 계층으로 보내는 요청 같은 내부 트래픽만 처리한다.

  2. 내부 로드 밸런서사설 IP로 VPC 내부에서만 동작하며, 예를 들어 웹 서버 계층에서 애플리케이션 서버 계층으로 요청을 분배한다.

3구조적 핵심 예시

4단계별 동작 과정

  1. DNS 조회클라이언트가 로드 밸런서의 DNS 이름을 조회하고 노드의 IP 주소를 받는다.

  3. 대상 라우팅노드가 헬스 체크(상태 검사)를 통과한 정상 대상 중 하나를 선택해서 요청을 전달하고, 대상에서 온 응답을 클라이언트에게 돌려보낸다.

각 노드가 자기 영역뿐 아니라 모든 영역의 등록된 대상으로 트래픽을 분산하게 하는 설정이다.

→ 02-01 참조

1상대의 출발점 확인

로드 밸런서는 각 가용 영역(AZ, Availability Zone)마다 노드를 배치한다. 기본적으로 각 노드는 같은 AZ의 대상에만 트래픽을 보내므로, 특정 AZ로 트래픽이 몰렸을 때 그 영역의 대상에만 부하가 집중되고 다른 영역의 리소스는 남는 상황이 생긴다.

2질문 제기

로드 밸런서가 자기 영역의 대상만 사용할 때 생기는 불균형을 어떻게 해결할까?

3구조적 핵심 예시

AZ-A에 로드 밸런서 노드 1개와 웹 서버 2개가 있고, AZ-B에 노드 1개와 서버 2개가 있을 때, 교차 영역을 활성화하지 않으면 AZ-A의 노드가 모든 트래픽을 같은 AZ의 서버 2개에만 보낸다. 교차 영역을 활성화하면 AZ-A의 노드도 AZ-B의 서버로 트래픽을 보낼 수 있어서 전체 4개 서버가 고르게 사용된다.

4단계별 동작 과정

  1. 모든 대상 등록모든 AZ의 대상을 하나의 대상 그룹에 등록한다.
  2. 교차 영역 활성화노드가 같은 AZ뿐만 아니라 다른 AZ의 정상 대상도 선택 가능하도록 설정한다.
  3. 균등 분산각 노드가 모든 AZ의 정상 대상 중에서 라우팅 알고리즘에 따라 고르게 선택한다.

서브넷 선택과 IP 주소 여유, Local Zone·Outpost

로드 밸런서는 지정한 서브넷에 노드용 IP를 잡으므로 서브넷마다 충분한 여유 주소가 필요하며, Local Zone과 Outpost에도 배치할 수 있다.

1상대의 출발점 확인

로드 밸런서를 만들 때 서브넷을 선택하면, 로드 밸런서는 그 서브넷에서 실제 노드용 IP 주소를 할당받는다. 만약 서브넷의 남은 주소가 부족하면 노드를 배치할 수 없거나, 나중에 트래픽 증가 시 확장할 수 없다.

2질문 제기

로드 밸런서 노드가 필요로 하는 IP 주소를 서브넷이 충분히 제공할 수 없으면 어떻게 될까?

3구조적 핵심 예시

/28 서브넷(총 16개 주소)에 이미 EC2 인스턴스와 기타 리소스가 사용 중인 주소들이 있을 때, 로드 밸런서를 배치하려면 여유 주소가 4~5개 이상 필요하다. 여유가 없으면 배치 자체가 실패하거나, 나중에 트래픽이 증가해서 노드를 추가하려 할 때 할당받을 주소가 없어진다.

4단계별 동작 과정

  1. 서브넷 지정로드 밸런서가 배치될 각 AZ의 서브넷을 선택한다.
  2. IP 예약로드 밸런서는 각 서브넷에서 노드용 주소를 미리 할당받고 예약한다.
  3. 확장 고려트래픽 증가 시 노드를 추가하려면 서브넷에 계속 여유 주소가 있어야 한다.

1상대의 출발점 확인

2질문 제기

로드 밸런서가 IPv4와 IPv6 클라이언트를 모두 받으면서 네트워크 구성에 맞게 주소를 제공할 수 있을까?

3구조적 핵심 예시

IPv4 클라이언트는 로드 밸런서의 IPv4 주소로 접속하고, IPv6 클라이언트는 IPv6 주소로 접속한다. dualstack-without-public-ipv4 옵션을 선택하면 로드 밸런서는 공인 IPv4는 없지만 IPv4와 IPv6 주소를 모두 제공해서, 프라이빗 IP만 사용하는 내부 네트워크에서도 IPv4 클라이언트를 지원할 수 있다.

4단계별 동작 과정

  1. 주소 체계 선택IPv4, dualstack(듀얼스택, IPv4+IPv6), dualstack-without-public-ipv4 중 하나를 선택한다.
  2. DNS 레코드 등록선택한 주소 체계에 맞춰 A 레코드(IPv4) 또는 AAAA 레코드(IPv6)를 DNS에 등록한다.
  3. 클라이언트 연결클라이언트의 네트워크 설정에 따라 IPv4 또는 IPv6 주소로 로드 밸런서에 접속한다.

1상대의 출발점 확인

로드 밸런서를 설정했어도 방화벽(보안 그룹, 네트워크 ACL)이 트래픽을 막으면 통신이 안 된다. 기존에는 어떤 포트와 방향을 열어야 하는지 명확하지 않아서, 설정 후에도 연결 문제가 발생할 수 있다.

2질문 제기

MTU·점보 프레임과 로드 밸런서가 쓰는 공인 IP

로드 밸런서 노드의 최대 전송 단위 제한과 노드가 사용하는 공인 IP 주소 범위를 알아야 패킷 손실과 방화벽 허용 문제를 피할 수 있다.

1상대의 출발점 확인

로드 밸런서와 대상 사이의 네트워크 경로마다 패킷의 최대 크기 제한(MTU, Maximum Transmission Unit)이 있다. 이를 무시하면 패킷이 손실되거나 전송이 실패한다. 또한 로드 밸런서 노드의 공인 IP 주소 범위를 모르면 방화벽이나 보안 정책에서 이 IP들을 차단할 수 있다.

2질문 제기

로드 밸런서의 패킷 크기 제한과 공인 IP 주소 범위를 어떻게 파악해서 안정적인 통신을 보장할까?

3구조적 핵심 예시

4단계별 동작 과정

  2. 공인 IP 범위 조회AWS에서 제공하는 로드 밸런서 노드의 공인 IP 주소 범위를 확인한다.
  3. 방화벽 및 경로 최적화방화벽이 해당 IP를 허용하고, MTU 문제가 없는지 네트워크 경로를 테스트한다.

ALB 리스너 구성과 기본 규칙

리스너는 지정한 포트·프로토콜로 들어오는 요청을 받아 규칙에 따라 대상 그룹으로 넘기는 진입점이며, 어떤 규칙에도 걸리지 않은 요청은 기본 규칙이 처리한다.

1상대의 출발점 확인

기존 로드밸런서는 들어온 모든 요청을 같은 방식으로 처리했다. 포트나 프로토콜별로 다르게 처리할 수 없었고, 요청의 내용을 읽어서 다른 대상 그룹으로 보낼 방법이 없었다. ALB는 리스너라는 진입점을 두어 포트·프로토콜별로 들어온 요청을 받고, 규칙으로 요청의 내용을 읽어 적절한 대상 그룹으로 보낼 수 있게 했다.

2질문 제기

들어온 요청을 어디서 받아서, 어떤 규칙에 따라 어느 대상에게 보낼 것인가?

3구조적 핵심 예시

ALB가 포트 80과 443에 각각 리스너를 만든다면, 포트 80의 HTTP 요청은 "HTTP 80 리스너"가 받고, 포트 443의 HTTPS 요청은 "HTTPS 443 리스너"가 받는다. 각 리스너는 자신에게 붙은 규칙 목록을 읽어 들어온 요청의 조건을 확인하고, 첫 번째로 맞는 규칙의 작업을 실행한다. 어떤 규칙도 맞지 않으면 기본 규칙(default rule)이 처리한다.

4단계별 동작 과정

  1. 리스너 수신ALB가 지정한 포트·프로토콜로 들어온 요청을 리스너가 받는다.
  2. 규칙 매칭리스너가 자신의 규칙 목록을 순서대로 읽어서, 요청이 그 규칙의 조건에 맞는지 확인한다.
  3. 작업 실행 또는 기본 규칙규칙이 맞으면 그 규칙의 작업을 실행하고, 맞는 규칙이 없으면 기본 규칙의 작업을 실행한다.

규칙의 구조와 평가 순서

규칙은 우선순위·조건·작업 세 부분으로 이루어지며, 낮은 우선순위 번호부터 차례로 평가해 처음 맞는 규칙 하나만 실행한다.

1상대의 출발점 확인

규칙이 많아지면 여러 규칙이 같은 요청에 맞을 수 있다. 규칙이 많을 때 어느 규칙을 먼저 실행할지 정하지 않으면, 요청이 여러 규칙에 의해 충돌하게 되거나 예기치 않은 대상으로 보내질 수 있다.

2질문 제기

수많은 규칙이 모두 같은 요청에 맞을 때, 어느 규칙을 먼저 적용할 것인가?

3구조적 핵심 예시

ALB가 규칙 A(우선순위 1: 호스트가 api.example.com), 규칙 B(우선순위 2: 경로가 /admin), 규칙 C(우선순위 10: 모든 요청)를 가진다면, 호스트가 api.example.com이고 경로가 /admin인 요청이 들어올 때 ALB는 규칙 A부터 확인해서 규칙 A와 맞으므로 규칙 A의 작업만 실행한다. 규칙 B와 C는 평가되지 않는다.

4단계별 동작 과정

  1. 우선순위 정렬각 규칙에 붙은 우선순위 번호(1부터 시작, 숫자가 작을수록 높은 우선순위)로 규칙을 정렬한다.
  2. 차례대로 평가가장 높은 우선순위(낮은 번호) 규칙부터 요청과 조건을 맞춰본다.
  3. 첫 매칭 규칙 실행처음으로 조건이 맞은 규칙의 작업을 실행하고 나머지 규칙은 평가하지 않는다.

조건 유형

호스트 헤더, 경로, HTTP 헤더, HTTP 요청 메서드, 쿼리 문자열, 소스 IP 같은 요청의 여러 속성을 조건으로 삼아 트래픽을 갈라낸다.

1상대의 출발점 확인

로드밸런서가 단순히 IP 주소나 포트만 보고 배분한다면, API 요청과 웹 페이지 요청을 구분할 수 없고, 특정 사용자나 특정 브라우저만 다른 대상에 보낼 수도 없다. ALB의 조건 유형은 HTTP 요청의 여러 속성을 읽어서 세밀한 구분을 가능하게 한다.

2질문 제기

요청의 어떤 부분을 보고 트래픽을 다르게 처리할 것인가?

3구조적 핵심 예시

웹 서버가 example.com과 api.example.com에 모두 응답해야 한다면, 조건으로 "호스트 헤더가 api.example.com"을 설정한 규칙을 만들어 API 전용 대상 그룹으로 보내고, 다른 규칙으로 "호스트 헤더가 example.com"인 요청을 웹 전용 대상 그룹으로 보낼 수 있다.

4단계별 동작 과정

  1. HTTP 헤더 읽기ALB가 들어온 요청의 Host, User-Agent, Authorization 같은 HTTP 헤더를 읽는다.
  2. 경로와 쿼리 확인URL의 경로(/admin, /api/users) 및 쿼리 문자열(?key=value)을 확인한다.
  3. 메서드와 소스 IP 검토HTTP 메서드(GET, POST, DELETE) 및 클라이언트의 소스 IP 주소도 조건으로 삼을 수 있다.

작업 유형

조건에 맞은 요청을 대상 그룹으로 전달(forward)하거나, 다른 URL로 리디렉션하거나, 대상 없이 고정 응답을 바로 돌려줄 수 있다.

1상대의 출발점 확인

규칙이 요청과 맞았을 때 대상 그룹으로만 보낼 수 있다면 유연성이 제한된다. 클라이언트를 다른 URL로 리디렉션해야 하거나, 서버를 거치지 않고 ALB 자체에서 응답해야 하는 경우도 있다.

2질문 제기

규칙이 맞은 요청을 어떻게 처리할 것인가?

3구조적 핵심 예시

http://example.com/old-page 로 들어온 요청에 대해 작업을 "redirect"로 설정해 https://example.com/new-page 로 리디렉션할 수 있다. 또는 /health-check 경로의 요청에 대해 작업을 "fixed-response"로 설정해 대상 서버를 거치지 않고 ALB에서 바로 200 OK 응답을 돌려줄 수 있다.

4단계별 동작 과정

  1. Forward 작업요청을 지정한 대상 그룹으로 보내서 백엔드 서버가 처리하게 한다.
  2. Redirect 작업요청을 다른 URL이나 프로토콜로 리디렉션해서 클라이언트가 새 주소로 다시 요청하도록 한다.
  3. Fixed-Response 작업백엔드를 거치지 않고 ALB 자체에서 상태 코드와 응답 본문을 즉시 돌려준다.

3구조적 핵심 예시

4단계별 동작 과정

  1. 경로 재작성규칙의 설정에 따라 요청의 URL 경로를 변환한다(/v1/users → /users).
  2. 호스트 헤더 재작성규칙의 설정에 따라 Host 헤더를 변환한다(example.com → internal-api.local).
  3. 변환된 요청 전달변환된 요청을 대상 그룹으로 보내서 백엔드가 올바른 경로와 호스트에서 처리하도록 한다.

  3. 가중 랜덤각 대상에 가중치를 설정하고, 그 비율에 따라 무작위로 선택해서 보낸다.

스티키 세션: lb_cookie와 app_cookie

같은 클라이언트의 연속 요청을 같은 대상으로 보내는 기능으로, 로드 밸런서가 만든 쿠키(lb_cookie)나 애플리케이션이 만든 쿠키(app_cookie)를 기준으로 삼는다.

1상대의 출발점 확인

로드 밸런서가 단순히 라운드 로빈(순서대로 돌아가며 분산)으로 요청을 나누면, 같은 클라이언트의 연속 요청이 다른 서버로 갈 수 있다. 로그인 정보, 장바구니, 세션 데이터처럼 첫 요청 때 서버A에 저장된 정보가 다음 요청에서 서버B로 가면 존재하지 않아 기능이 깨진다.

2질문 제기

같은 클라이언트의 연속 요청을 항상 같은 서버로 보낼 수 있을까?

3구조적 핵심 예시

로드 밸런서가 첫 요청에 응답할 때 쿠키를 담거나 감지해서, 다음 요청이 올 때 그 쿠키를 보고 어느 서버로 보낼지 기억하는 방식이다.

4단계별 동작 과정

  1. 쿠키 생성 또는 감지첫 요청이 오면 로드 밸런서는 서버A를 선택해 요청을 보낸다. 응답이 오면 로드 밸런서가 자신이 만든 쿠키를 담거나(lb_cookie, 로드 밸런서가 생성), 응답 헤더에 있는 애플리케이션 쿠키를 읽어서 어느 서버인지 기록해둔다(app_cookie, 애플리케이션이 생성).
  2. 클라이언트가 쿠키 저장클라이언트는 응답 헤더의 Set-Cookie에 들어 있는 쿠키를 자신의 브라우저에 저장한다.
  3. 같은 서버로 라우팅다음 요청 때 클라이언트가 쿠키를 요청 헤더에 포함시켜 보내면, 로드 밸런서는 그 쿠키 값을 확인해 이전에 선택했던 서버A로 다시 보낸다.

1상대의 출발점 확인

로드 밸런서의 대상은 항상 EC2 인스턴스나 온프레미스 서버처럼 계속 실행되는 웹 서버였다. 이런 서버들은 항상 떠 있어야 하기 때문에 트래픽이 적어도 비용이 든다.

2질문 제기

장기 실행 서버 대신 필요할 때만 실행되는 Lambda 함수를 로드 밸런서의 대상으로 쓸 수 있을까?

3구조적 핵심 예시

ALB가 들어온 HTTP 요청을 Lambda가 받을 수 있는 형태(JSON 이벤트)로 변환해서 함수를 호출하고, 함수의 반환값을 다시 HTTP 응답으로 돌려주는 방식이다.

4단계별 동작 과정

  1. 요청을 JSON 이벤트로 변환ALB가 HTTP 요청(메서드, 경로, 헤더, 바디 등)을 JSON 형식의 이벤트 객체로 변환해서 Lambda에 전달한다.
  2. Lambda 함수 실행Lambda 서비스가 그 이벤트를 받아 함수의 핸들러를 실행하고, 함수가 처리 결과를 JSON으로 반환한다(예: 상태 코드 200, 바디는 처리 결과).
  3. 응답을 HTTP로 변환ALB가 Lambda의 반환값(상태 코드, 헤더, 바디)을 읽어 다시 HTTP 응답으로 구성해서 클라이언트에 보낸다.

HTTP 버전과 대상 그룹 프로토콜 버전(gRPC 포함)

ALB는 클라이언트와 HTTP/1.1·HTTP/2로 통신하고, 대상 그룹에는 HTTP1·HTTP2·gRPC 중 무엇으로 요청을 보낼지 따로 정할 수 있다.

1상대의 출발점 확인

로드 밸런서는 클라이언트와 정해진 HTTP 버전으로만 통신했고, 백엔드 서버에도 같은 버전으로만 요청을 보냈다. 하지만 HTTP/2나 gRPC 같은 최신 프로토콜은 멀티플렉싱(여러 요청을 하나의 연결로 동시 처리)이나 이진 형식으로 성능이 훨씬 좋아서, 클라이언트와는 하위 호환을 유지하면서 백엔드에는 고성능 프로토콜을 쓸 필요가 있다.

2질문 제기

클라이언트와는 HTTP/1.1로 받지만 빠른 백엔드와는 HTTP/2나 gRPC로 통신할 수 있을까?

3구조적 핵심 예시

ALB가 클라이언트와의 연결과 백엔드로의 연결을 따로 관리하면서, 각 대상 그룹마다 "이 그룹의 서버들과는 HTTP/1, HTTP/2, 또는 gRPC 중 무엇으로 통신할지"를 따로 설정할 수 있다는 것이다.

4단계별 동작 과정

  1. 클라이언트 프로토콜 협상클라이언트가 연결할 때 ALPN(Application Layer Protocol Negotiation, 어떤 프로토콜을 쓸지 협상하는 TLS 확장)을 통해 HTTP/1.1이나 HTTP/2 중 하나를 선택한다.
  2. 대상 그룹 프로토콜 확인ALB는 요청이 도착한 대상 그룹의 프로토콜 설정을 확인한다(예: "이 그룹은 gRPC만 지원").
  3. 프로토콜 변환 및 전달ALB는 클라이언트로부터 받은 HTTP/1.1 요청을 필요하면 gRPC 형식으로 변환해서 백엔드로 보낸다. 응답도 다시 원래 프로토콜로 변환해 돌려준다.

ALB는 HTTP 연결을 WebSocket으로 업그레이드하는 요청을 그대로 통과시키고, 백엔드 연결 재사용(다중화)과 킵얼라이브로 연결 비용을 줄인다.

1상대의 출발점 확인

로드 밸런서는 요청-응답 구조(클라이언트가 요청하면 서버가 응답하는 방식)에 최적화되어 있었다. WebSocket처럼 한 번 연결 후 서버와 클라이언트가 양쪽 방향으로 계속 데이터를 주고받아야 하는 경우나, 백엔드와의 연결을 재사용하지 못하고 계속 새로 만들어야 하는 상황에서는 비효율적이었다.

2질문 제기

WebSocket으로 업그레이드하는 요청을 로드 밸런서가 그대로 통과시키고, 연결을 효율적으로 재사용할 수 있을까?

3구조적 핵심 예시

클라이언트가 "이 HTTP 연결을 WebSocket으로 업그레이드해 달라"는 요청(Upgrade 헤더)을 보내면, ALB는 그 헤더를 그대로 백엔드로 전달해서 업그레이드를 중개하고, 이후 양방향 데이터 흐름을 투과적으로 처리한다.

4단계별 동작 과정

  1. 업그레이드 요청 통과클라이언트의 WebSocket 업그레이드 요청(Upgrade: websocket 헤더 포함)을 ALB가 변조 없이 그대로 백엔드로 보낸다. 백엔드가 업그레이드를 승인하면 HTTP 연결이 WebSocket으로 전환된다.
  2. 연결 다중화 및 유지업그레이드된 WebSocket 연결 위에서 ALB는 여러 클라이언트의 데이터를 하나의 백엔드 연결로 다중화(multiplexing, 여러 흐름을 하나로 통합)할 수 있고, 요청이 없어도 연결을 끊지 않는 킵얼라이브(keep-alive)로 유지한다.
  3. 양방향 데이터 흐름연결이 유지되는 동안 클라이언트가 메시지를 보내면 그대로 백엔드로 도착하고, 백엔드가 보낸 메시지도 그대로 클라이언트에 도착한다.

HTTPS 리스너·인증서·SNI

HTTPS 리스너는 ALB에서 TLS를 끝내며, 기본 인증서 하나에 추가 인증서를 붙여 SNI로 도메인마다 알맞은 인증서를 골라 제공한다.

1상대의 출발점 확인

웹 서버가 HTTPS 요청을 받으려면 각 서버가 인증서를 가져야 했다. 또한 하나의 서버 IP는 보통 하나의 도메인 인증서만 제공할 수 있었으므로, 여러 도메인을 지원하려면 IP 주소가 여러 개 필요했다.

2질문 제기

하나의 로드 밸런서에서 여러 도메인의 HTTPS 요청을 받되, 도메인마다 다른 인증서를 제공할 수 있을까?

3구조적 핵심 예시

ALB의 HTTPS 리스너가 TLS를 끝내면서(terminate) 기본 인증서를 설정하고 추가 인증서들을 여러 개 붙인 다음, 클라이언트가 연결할 때 SNI(Server Name Indication, 클라이언트가 어느 도메인에 접속하려는지 알려주는 TLS 확장)로 도메인명을 보면 그에 맞는 인증서를 선택해 제공한다.

4단계별 동작 과정

  1. 기본 및 추가 인증서 등록HTTPS 리스너를 만들 때 기본 인증서(예: *.example.com)를 지정하고, 특정 도메인용 인증서들(예: api.example.com, mobile.example.com)을 여러 개 추가로 등록한다.
  2. SNI로 도메인 파악클라이언트가 TLS 핸드셰이크할 때 "나는 api.example.com에 접속할 거야"라고 SNI 확장에 도메인명을 담아 보낸다.
  3. 알맞은 인증서 제공ALB는 SNI 값을 보고 등록된 인증서 목록에서 그 도메인에 맞는 인증서를 찾아서 제공한다. 만약 등록되지 않은 도메인이면 기본 인증서로 폴백(fallback)한다.

NLB는 프로토콜·출발지/목적지 IP·포트 등을 해시해 하나의 연결(흐름)을 통째로 같은 대상에 보내고, 그 연결이 끝날 때까지 유지한다.

1상대의 출발점 확인

일반적인 로드 밸런싱은 각 패킷이나 요청을 독립적으로 처리하므로, 하나의 TCP 연결에 속한 패킷들이 서로 다른 백엔드 서버로 분산될 수 있습니다. 이 경우 프로토콜 동작이 깨지거나 상태 정보가 불일치할 수 있습니다.

2질문 제기

하나의 연결에 속한 모든 패킷을 같은 대상으로 보낼 수 있을까요?

3구조적 핵심 예시

NLB가 프로토콜, 출발지 IP, 목적지 IP, 출발지 포트, 목적지 포트 다섯 개 값(5튜플)으로 해시를 계산하면, 같은 연결의 모든 패킷이 항상 같은 해시값을 가져 동일한 대상으로 전달됩니다.

4단계별 동작 과정

  1. 5튜플로 해시 계산연결의 프로토콜과 양쪽 끝점 정보로 고유한 해시값을 계산합니다.
  2. 해시값으로 대상 결정해시값을 대상 개수로 나눈 나머지로 어느 대상에 보낼지 결정합니다.
  3. 연결 종료까지 같은 대상 유지그 연결이 끝날 때까지 모든 패킷이 같은 대상으로 유지됩니다.

TLS 리스너는 NLB에서 암호를 풀어 대상에는 평문으로 넘기며, ALPN으로 상위 프로토콜을 협상하고 세션 재개로 핸드셰이크 비용을 줄인다.

→ 05-03 참조

1상대의 출발점 확인

기존 방식에서 NLB가 요청을 받으면 데이터를 그대로 암호화된 상태에서 뒤의 대상으로 넘긴다. 이 방식의 한계는 NLB가 트래픽 내용을 볼 수 없어서 상위 프로토콜의 특성에 맞게 분산할 수 없고, 각 대상이 클라이언트와 별도로 TLS 핸드셰이크를 하느라 연결 설립 비용이 크다는 점이다.

2질문 제기

3구조적 핵심 예시

클라이언트가 HTTPS(HTTP/2) 요청을 보내면 NLB의 TLS 리스너가 암호화를 풀어서 데이터를 읽는다. ALPN 확장에서 이 요청이 HTTP/2 프로토콜이라는 것을 알고 HTTP/2를 처리하는 대상 그룹으로 보낸다. 다음 요청 시 클라이언트가 이전 세션 티켓을 보내면, NLB는 전체 핸드셰이크 대신 세션 재개 과정만 수행해서 왕복 시간을 단축한다.

4단계별 동작 과정

  1. TLS 핸드셰이크 및 암호 해제클라이언트 초기 요청에서 NLB가 TLS 핸드셰이크를 수행하고, 이후 모든 데이터 트래픽을 복호화한다.
  2. ALPN을 통한 프로토콜 협상클라이언트 hello 메시지의 ALPN 확장에서 지원하는 상위 프로토콜(HTTP/1.1, HTTP/2, HTTP/3 등)을 확인하고, NLB가 그에 맞는 대상 그룹을 선택한다.
  3. 세션 재개로 핸드셰이크 단축클라이언트가 이전 세션 ID나 세션 티켓을 제시하면, 전체 암호화 협상 대신 축약된 재개 과정만 거쳐서 연결 설립 시간과 계산 비용을 절약한다.

1상대의 출발점 확인

기존 방식에서 NLB 리스너는 요청을 받으면 하나의 대상 그룹으로만 보낸다. 여러 백엔드 그룹에 나누고 싶으면 별도의 리스너를 여러 개 만들어야 한다. 이는 포트를 많이 차지하고 관리가 복잡하다는 한계가 있다.

3구조적 핵심 예시

NLB 리스너의 기본 작업(default action)을 "대상 그룹 A: 70%, 대상 그룹 B: 30%"로 설정한다. 들어오는 TCP/UDP 흐름이 이 비율에 따라 두 그룹에 자동으로 분산된다.

  2. 가중치 기반 분산새로운 연결 또는 UDP 흐름이 들어오면, 각 대상 그룹에 부여된 가중치에 따라 그 흐름이 어느 그룹으로 갈지 결정된다.

클라이언트 IP 보존·프록시 프로토콜 v2·비정상 대상 처리

대상이 실제 클라이언트 IP를 보게 하는 보존 설정과, 연결 앞에 메타데이터를 붙이는 프록시 프로토콜 v2 옵션이다.

1상대의 출발점 확인

기존 방식에서 NLB가 대상 서버로 요청을 보낼 때, TCP 연결의 출발지 IP는 NLB 노드의 IP로 바뀐다. 대상 서버는 실제 클라이언트 IP를 알 수 없어서 클라이언트 식별, 지역 기반 처리, 접근 제어 등이 어렵다. 또한 비정상 대상이 분산에 계속 포함되면 요청이 실패한다.

2질문 제기

대상 서버가 실제 클라이언트 IP를 알게 하고, 동시에 비정상 서버를 자동으로 제외하려면?

3구조적 핵심 예시

NLB 대상 그룹의 클라이언트 IP 보존을 켜면, TCP 연결의 출발지가 NLB 노드 IP 대신 클라이언트의 실제 IP로 유지된다. 또는 프록시 프로토콜 v2를 활성화하면, NLB가 데이터 앞에 "PROXY TCP4 10.0.1.100 10.0.2.50 12345 80\r\n" 같은 헤더를 붙여서 클라이언트 정보를 전달한다.

4단계별 동작 과정

  1. 클라이언트 IP 전달 방식 선택클라이언트 IP 보존(같은 서브넷 내 직접 회신) 또는 프록시 프로토콜 v2 헤더(메타데이터 삽입)를 선택해서, 대상이 실제 클라이언트를 식별할 수 있게 한다.
  2. 대상 헬스 체크NLB가 주기적으로 각 대상에 헬스 체크(TCP 연결 시도, HTTP GET 요청 등)를 보내고, 응답 상태를 기록한다.
  3. 비정상 대상 제외헬스 체크에 실패한 대상을 비정상으로 표시하고, 이후의 새 연결은 정상인 대상들로만 분산한다.

NLB는 서브넷마다 고정 IP(원하면 탄력적 IP)를 가지며, 대상 연결에 쓸 소스 포트가 모자라면 포트 할당 오류가 난다.

1상대의 출발점 확인

기존 방식에서 로드밸런서가 대상과 연결을 맺을 때, 자신의 소스 포트(1024~65535 범위의 임시 포트)를 하나씩 사용한다. 대상이 많고 연결이 오래 유지되는 환경에서는 사용 가능한 소스 포트가 금방 고갈되어 더 이상 새로운 연결을 만들 수 없는 포트 할당 오류가 발생한다. 또한 로드밸런서의 IP가 변하면 DNS 갱신이 지연되면서 클라이언트 연결에 영향을 미친다.

2질문 제기

3구조적 핵심 예시

4단계별 동작 과정

  1. NLB 노드의 IP 구성각 가용 영역의 NLB 노드가 VPC 서브넷의 고정 사설 IP를 할당받고, 필요하면 그 위에 탄력적 공개 IP를 추가한다.
  2. 보조 IP로 포트 풀 확대같은 ENI에 여러 개의 보조 사설 IP를 추가로 설정하면, 대상 연결의 출발지 IP 선택지가 늘어나고 포트 풀도 배수로 커진다.
  3. 포트 할당 오류 회피사용 가능한 (출발지 IP, 포트) 조합이 충분하면, 수백만 개의 동시 연결이 있어도 새로운 연결을 맺을 때 포트를 할당받을 수 있다.

2질문 제기

  3. 연결 종료 및 자원 회수타임아웃된 연결을 양쪽에 종료 신호를 보내고, 상태 추적 테이블에서 제거해서 메모리와 연결 슬롯을 해제한다.

1상대의 출발점 확인

NLB는 IP와 포트만 본다(L4 계층). ALB는 HTTP 경로, 호스트명, 헤더 등을 본다(L7 계층). 일반적으로 둘 다 필요한 경우, 별도의 인프라를 구성하거나 애플리케이션에서 라우팅을 직접 처리한다. 또한 크로스 VPC 트래픽은 공개 인터넷을 거치거나 별도의 VPN 연결이 필요해서 보안과 성능이 떨어진다.

2질문 제기

NLB의 L4 성능과 고정 IP, ALB의 L7 애플리케이션 라우팅, 그리고 안전한 크로스 VPC 통신을 모두 갖출 수 있을까?

3구조적 핵심 예시

4단계별 동작 과정

  1. NLB 대상으로 ALB 지정NLB의 대상 그룹 타입을 "IP"로 설정하고, ALB의 ENI 주소를 등록한다. 이제 NLB가 수신한 모든 L4 흐름을 ALB로 포워딩한다.
  2. ALB에서 L7 라우팅ALB가 NLB로부터 받은 연결을 HTTP/HTTPS 계층에서 분석해서, 요청 경로, 호스트명, 헤더, 쿼리 파라미터 등에 따라 뒤의 각 대상 그룹(실제 애플리케이션 서버들)에 라우팅한다.
  3. PrivateLink 엔드포인트 서비스 구성NLB를 PrivateLink 엔드포인트 서비스의 네트워크 로드 밸런서로 등록하면, 다른 VPC(또는 온프레미스 AWS 연결)의 사용자가 VPC 엔드포인트를 만들어서 인터넷을 거치지 않고 개인 연결로 이 NLB에 접속할 수 있다.

  2. GENEVE 캡슐화원본 패킷을 UDP 6081 포트의 GENEVE 프로토콜로 감싸서 어플라이언스 주소로 보냅니다.

GWLB 엔드포인트(VPC 엔드포인트)는 검사받을 VPC 안에 놓이는 진입·출구 지점이며, 라우팅 테이블의 다음 홉을 이 엔드포인트로 지정해 트래픽을 어플라이언스로 우회시킨다.

1상대의 출발점 확인

2질문 제기

4단계별 동작 과정

흐름 고정과 대상 페일오버

GWLB는 5-튜플(또는 3-튜플) 해시로 같은 흐름을 항상 같은 어플라이언스에 보내며, 대상이 비정상이 되면 기존 흐름을 어떻게 처리할지(유지 또는 재분배) 페일오버 동작으로 설정한다.

1상대의 출발점 확인

같은 TCP 연결(흐름)이 검사 도중 어플라이언스 A에서 B로 옮겨가면, 어플라이언스 A에서 추적 중인 상태 정보가 B에는 없어서 검사 정책이 불일치하거나 보안 위험이 발생할 수 있습니다. 특히 방화벽이나 IDS는 연결 상태를 지속적으로 추적해야 하므로 이런 변경은 심각한 문제입니다.

2질문 제기

같은 연결이 검사 중인 어플라이언스에 계속 유지되면서도 장애 상황에 유연하게 대응하려면 어떻게 해야 할까요?

3구조적 핵심 예시

출발지 IP 203.0.113.1, 출발지 포트 50000, 목적지 IP 192.0.2.100, 목적지 포트 80, 프로토콜 TCP의 조합(5-튜플)을 해싱하면 항상 같은 값이 나오므로, GWLB가 이 값을 기반으로 항상 같은 어플라이언스를 선택합니다.

4단계별 동작 과정

  1. 흐름 식별GWLB가 패킷의 출발지·목적지 IP, 포트, 프로토콜(5-튜플) 또는 출발지·목적지 IP와 프로토콜만(3-튜플)으로 흐름을 식별합니다.
  2. 해시 계산 및 대상 선택식별된 흐름의 해시값을 계산하여 항상 같은 어플라이언스를 선택합니다.
  3. 페일오버 처리선택된 어플라이언스가 비정상이 되면, 설정된 페일오버 정책(기존 흐름 유지 또는 재분배)에 따라 대응합니다.

5본질 요약

흐름 해시로 같은 연결을 항상 같은 어플라이언스로 보냄으로써 상태 추적이 일관되게 유지되고, 페일오버 정책으로 장애 상황의 흐름 처리 방식을 명확히 합니다

GWLB의 제약: MTU·비대칭 흐름·유휴 타임아웃

GENEVE 헤더가 붙어 실효 MTU가 줄고, 흐름이 양방향 모두 같은 어플라이언스로 가야 하며, 일정 시간 패킷이 없으면 흐름 상태가 사라지는 등 설계 시 유의할 제약이 있다.

1상대의 출발점 확인

기술의 장점만 보면 GWLB를 모든 네트워크 환경에 적용할 수 있을 것처럼 보이지만, GENEVE 캡슐화, 흐름 고정, 상태 유지 같은 구조적 특성으로 인해 실제 설계 단계에서 고려해야 할 제약들이 있습니다.

2질문 제기

GWLB를 도입할 때 패킷 크기, 트래픽 흐름, 타임아웃 관리 측면에서 피해야 할 문제는 무엇일까요?

3구조적 핵심 예시

표준 이더넷 MTU가 1500바이트인데, GENEVE 헤더가 8바이트 추가되면 전체 크기가 1508바이트가 되어 1500을 초과합니다. 이를 막으려면 사전에 1492바이트 이하로 MTU를 낮춰두어야 패킷 단편화를 피할 수 있습니다.

4단계별 동작 과정

  1. MTU 감소GENEVE 캡슐화 오버헤드로 인해 실효 MTU가 약 1492바이트로 줄어들므로, 네트워크 인터페이스나 애플리케이션 수준에서 이를 고려해야 합니다.
  2. 양방향 흐름 고정클라이언트에서 서버로 가는 흐름과 서버에서 클라이언트로 오는 응답이 모두 같은 어플라이언스를 거쳐야 하므로, 비대칭 라우팅이 있으면 검사가 불완전해집니다.
  3. 유휴 타임아웃 관리일정 시간 동안 패킷이 없는 흐름은 상태가 삭제되므로, 오래 연결을 유지하는 애플리케이션은 주기적으로 트래픽을 보내거나 타임아웃 값을 조정해야 합니다.

5본질 요약

GWLB가 구조적으로 MTU 감소, 양방향 흐름 고정, 유휴 타임아웃이라는 제약을 갖고 있으므로, 네트워크 설계 단계부터 이를 명시적으로 고려하고 대비해야 합니다

3구조적 핵심 예시

1상대의 출발점 확인

일반적인 Access Log는 로드 밸런서가 받은 요청과 응답 상태만 기록합니다. 하지만 요청이 백엔드에 전달되기도 전에, TLS 핸드셰이크 단계에서 실패하거나 대상이 헬스 체크를 통과하지 못한 경우는 기록되지 않습니다. 따라서 요청이 아예 도달하지 못한 원인을 추적할 수 없습니다.

2질문 제기

3구조적 핵심 예시

Connection Log는 TCP 연결 수립 → TLS 핸드셰이크 → ALB가 요청을 받는 일련의 과정 각 단계의 성공/실패를 기록합니다. Health Check Log는 ALB가 대상을 "정상인가?"라고 주기적으로 확인할 때의 응답 결과를 따로 기록합니다. 요청이 도달하지 못했다면 이 두 로그에서 실패 지점을 찾을 수 있습니다.

4단계별 동작 과정

  1. 연결 로그 생성클라이언트가 ALB에 연결하려 할 때 TCP/TLS 핸드셰이크 시작·완료·실패 각 단계의 타이밍, 송수신 바이트, 실패 코드를 기록합니다.
  2. 헬스 체크 로그 생성ALB가 정해진 간격으로 각 대상에 HTTP 요청(또는 TCP 핸드셰이크)을 보내어, 응답 여부와 상태 코드를 기록합니다.
  3. 로그 분석요청이 도달하지 못했다면 Connection Log에서 TLS 실패를, Health Check Log에서 대상 비정상을 찾아 원인을 특정합니다.

요청 추적(X-Amzn-Trace-Id)

Application Load Balancer가 각 요청에 붙여 주는 고유 식별자 헤더로, 로드 밸런서 로그와 백엔드 로그를 같은 요청끼리 연결해 준다.

1상대의 출발점 확인

4단계별 동작 과정

  1. 추적 ID 생성ALB가 클라이언트에게서 요청을 받을 때마다 고유한 추적 ID를 생성합니다.
  2. 헤더 삽입과 전달X-Amzn-Trace-Id 헤더에 ID를 넣어서 백엔드 대상으로 전달합니다.
  3. 로그 연결ALB Access Log에는 헤더 값이 기록되고, 백엔드가 로그를 남길 때 이 헤더를 읽어서 함께 기록하면, 양쪽 로그를 같은 ID로 조인할 수 있습니다.

9운영·복원력·보안, 그리고 남은 문제09-03

영역 이동(zonal shift)과 영역 자동 이동

한 가용 영역에 장애가 의심될 때 그 영역으로 가는 트래픽을 잠시 빼는 기능이며, 자동 이동은 AWS가 이를 알아서 수행한다.

1상대의 출발점 확인

AWS의 가용 영역(AZ)에 장애가 발생하면, 일반적으로는 AWS가 인식하고 자동으로 복구할 때까지 기다려야 합니다. 응용 프로그램이 빠르게 대응하고 싶어도, 로드 밸런서가 계속 그 영역으로 트래픽을 보내기 때문에 사용자는 오류를 경험하게 됩니다.

2질문 제기

가용 영역의 장애 징후가 보이면, 즉시 그 영역으로 가는 트래픽을 빼고 다른 영역으로 우회할 수 있을까요?

3구조적 핵심 예시

Zonal Shift는 한 가용 영역을 일시적으로 트래픽에서 제외하는 기능입니다. 수동 방식(Zonal Shift)에서는 운영자가 의심되는 영역을 지정해서 그 영역의 대상을 트래픽 풀에서 제거합니다. 자동 방식(Automatic Zonal Shift)에서는 AWS가 가용 영역의 이상을 감지하면 자동으로 같은 작업을 수행합니다.

4단계별 동작 과정

  1. 장애 감지운영자가 수동으로 감지하거나, AWS 시스템이 자동으로 가용 영역의 이상을 감지합니다.
  2. Shift 시작해당 영역을 Zonal Shift 기능으로 지정하면, ALB가 그 영역의 대상으로 새로운 연결을 보내지 않습니다. 기존 연결은 graceful하게 종료됩니다.
  3. 복구 대기 후 복원영역이 정상화되면 shift를 해제해서 다시 트래픽을 받도록 합니다.

구형 CLB가 아직 제공하는 기능과, ALB/NLB로 옮겨 가는 마이그레이션 방법.

1상대의 출발점 확인

AWS는 처음에 Classic Load Balancer(CLB)라는 오래된 로드 밸런서만 제공했다. 이후 ALB(Application Load Balancer)와 NLB(Network Load Balancer)가 나왔고, 새 서비스는 ALB/NLB로 권장하지만 CLB는 아직 동작한다. 기존 시스템이 CLB 위에 있으면 언제까지 유지할지, 언제 옮길지 결정해야 한다.

2질문 제기

오래된 Classic Load Balancer를 쓰고 있을 때 ALB나 NLB로 옮겨야 할 필요가 있고, 옮기려면 어떤 단계를 거쳐야 할까?

3구조적 핵심 예시

CLB는 간단한 L4 로드 밸런싱(포트 기반)만 하는데, ALB는 L7 로드 밸런싱(URL 경로나 호스트 이름 기반)을 할 수 있고, NLB는 극도로 빠른 성능이 필요한 경우에 쓴다. CLB에서 ALB로 옮기려면 기존 CLB의 설정을 ALB 형식으로 다시 만들고, 트래픽을 조금씩 옮긴 후 CLB를 끈다.

4단계별 동작 과정

  1. 현황 파악기존 CLB가 처리하는 프로토콜(HTTP, HTTPS, TCP), 포트, 헬스 체크 설정을 기록한다.
  2. ALB 또는 NLB 생성같은 설정으로 새 로드 밸런서를 만들고, 대상 그룹을 구성한다.
  3. 트래픽 전환DNS를 천천히 바꾸거나 가중치 기반 라우팅으로 점진적으로 트래픽을 옮긴 후, 안정화되면 CLB를 삭제한다.

5본질 요약

오래된 CLB의 역할을 ALB나 NLB로 대체하되, 기존 설정을 옮기고 서비스 중단 없이 단계적으로 전환하는 마이그레이션 방법
