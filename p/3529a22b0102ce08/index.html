1. EKS의 경계 — 관리형 Kubernetes 는 무엇을 대신해 주는가01-01

Amazon EKS 란 무엇인가

Amazon EKS 는 AWS 가 운영·보안·패치까지 맡아 주는 관리형 Kubernetes 서비스로, 고객이 컨트롤 플레인(클러스터를 관리하는 부분) 을 직접 띄우지 않고도 컨테이너 묶음인 워크로드만 실행하게 해 준다.

#1문제 상황

Kubernetes 를 직접 세우려면 컨트롤 플레인(클러스터를 관리하는 부분) 을 설치하고 패치하고 장애 때마다 고쳐야 한다. 작업량만 늘고 워크로드는 그대로다.

Amazon EKS 는 managed Kubernetes service 로, 그 운영을 AWS 가 맡는다. 관리 영역인 control plane 과 Kubernetes API endpoint 를 고객이 돌리지 않고도 컨테이너 묶음을 실행하며, EKS add-ons 로 필요한 기능을 붙인다.

#2핵심 질문

Kubernetes 클러스터의 관리 부담을 누가 대신해 줄까?

#3동작 예시

개발팀이 주문 서비스 이미지 몇 개를 올리려고 EKS 콘솔로 들어간다. 클러스터를 만들고 노드를 붙인 뒤 Deployment 매니페스트를 적용하면 Pod가 뜬다.

노드가 고장 나도 컨트롤 플레인 쪽은 AWS 가 알아서 교체한다.

#4동작 과정

  1. 클러스터를 만든다컨트롤 플레인과 노드를 함께 세워 Kubernetes API endpoint 로 요청을 받는다. EKS add-ons 를 붙이면 DNS 나 로드 밸런서 같은 주변 기능이 함께 들어온다.
  2. 워크로드를 올린다매니페스트를 적용해 Pod를 원하는 수만큼 배치한다.
  3. 확인해 볼 것콘솔의 클러스터 목록에서 클러스터 상태가 ACTIVE 로 표시되는지 본다.

EKS 아키텍처 — 관리 영역과 노드의 역할

EKS 아키텍처는 AWS 가 관리하는 컨트롤 플레인이 API 서버·스케줄러·상태 저장 등을 돌고, 고객 계정의 서브넷에 놓인 노드(컴퓨팅 자원) 가 실제 Pod 를 실행하며, 둘 사이를 네트워크와 인증이 잇는 구조다.

먼저 알아야 할 것 01-01

#1문제 상황

클러스터를 한 덩어리로 생각하면 안 된다. 요청을 받아 배치를 정하는 부분과 실제로 컨테이너를 실행하는 부분은 서로 다른 곳에서 돌아간다.

EKS 아키텍처는 이 둘을 EKS control plane 과 worker node 로 나눈다.

#2핵심 질문

요청을 처리하는 쪽과 실제로 앱을 돌리는 쪽은 어떻게 나뉘는가?

#3동작 예시

개발자가 kubectl 로 Pod를 하나 더 만들라고 한다. 요청은 관리 영역의 API 서버로 들어가고 스케줄링 결과가 고객 서브넷의 노드로 전달된다. 노드가 그 지시대로 컨테이너를 띄운다.

#4동작 과정

  1. 요청을 받는다EKS control plane 이 API 서버와 상태 저장 계층인 etcd 로 선언된 상태를 관리한다. 인스턴스는 여러 가용 영역에 흩어져 두어 한 대가 멈춰도 남은 것이 이어받는다.
  2. 컨테이너를 실행한다worker node 가 스케줄러가 정한 위치에서 Pod를 돌린다. 노드를 묶어 AWS 가 관리하게 하는 managed node group 을 쓰는 경로가 기본이다.
  3. 확인해 볼 것kubectl get nodes 로 노드 목록과 Ready 상태가 보이는지 확인한다.

Kubernetes 핵심 개념 — 워크로드가 도는 규칙

Kubernetes 는 원하는 상태를 선언한 매니페스트(YAML 로 쓴 설정) 를 보고, 그 상태에 맞춰 Pod 를 배치·교체·복구하는 규칙 체계로, 클러스터·컨텍스트·네임스페이스·Deployment·Pod 같은 오브젝트가 기본 단위가 된다.

먼저 알아야 할 것 01-01

#1문제 상황

Kubernetes 는 매니페스트(YAML 로 쓴 설정) 를 보고 그 상태에 맞춰 알아서 고친다. 기본 단위는 Pod, Deployment, Service, namespace 이며, 모든 요청은 Kubernetes API 를 거쳐 kubectl 이 전달한다.

#2핵심 질문

원하는 상태를 선언하면 실행 중인 것이 알아서 맞춰지는가?

#3동작 예시

개발자가 Deployment 매니페스트를 kubectl 로 적용해 Pod 3개를 요청한다. 하나가 죽으면 나머지 둘이 요청을 받다 상태를 보고 클러스터가 새 Pod를 다시 띄운다.

#4동작 과정

  1. 상태를 선언한다namespace 안에서 Deployment 와 Service 를 매니페스트로 만든다. Service 는 요청을 받을 이름과 같은 Pod 묶음을 가리킨다.
  2. 맞춰지게 한다Kubernetes API 가 차이를 보고 Pod 를 추가하거나 교체한다. Pod 를 담는 최소 실행 단위이자 직접 다루기 가장 작은 대상이다.
  3. 확인해 볼 것kubectl get pods 로 Pod 상태가 Running 으로 표시되는지 확인한다.

kubectl 은 Kubernetes 클러스터에 명령을 보내는 공식 명령줄 도구이고, eksctl 은 그 위에 클러스터와 노드 그룹을 한 번에 만드는 래퍼 도구로, 둘 다 로컬에 설치해 자격 증명을 연결해야 쓸 수 있다.

먼저 알아야 할 것 01-01

#1문제 상황

kubectl 은 클러스터 안의 자원을 관리하는 공식 명령줄 도구이고, eksctl 은 EKS 클러스터를 만들고 바꾸고 지우는 전용 도구다. AWS CLI 를 넘어 이 둘을 더 설치해 명령으로 처리한다.

#2핵심 질문

#3동작 예시

개발자가 로컬에 kubectl 과 eksctl 을 설치하고 AWS 자격 증명을 연결한다. 이후 eksctl 한 줄로 클러스터를 세우고 kubectl 로 Pod 상태를 반복해서 본다.

#4동작 과정

  1. kubectl 을 설치한다클러스터 안의 자원을 관리하는 주 명령줄 도구로, 클러스터 Kubernetes 버전과 맞는 바이너리를 받는다.
  2. eksctl 을 설치한다EKS 클러스터를 만들고 바꾸고 지우는 전용 도구로, on-premises 클러스터도 다룬다.
  3. 연결한다AWS CLI 의 자격 증명을 쓰고 kubeconfig 에 클러스터 주소를 담아 어느 클러스터로 명령이 갈지 정한다. 클러스터 안에서 각 노드가 관리하는 에이전트는 kubelet 이다.
  4. 확인해 볼 것kubectl config current-context 로 지금 연결된 클러스터 이름이 나오는지 본다.

#2핵심 질문

#4동작 과정

  4. 확인해 볼 것클러스터 노드 목록에서 새로 추가된 노드가 Auto Mode 로 표시되는지 확인한다.

여러 대의 워커 컴퓨터(노드)을 하나의 묶음으로 묶어 AWS 가 생성·관리하게 하고, 그 위에 사용자의 컨테이너 워크로드를 올리는 방식이다.

#1문제 상황

managed node group 은 이 일을 묶어서 맡는다. AWS 는 이 클라우드 인프라와 클러스터 서비스를 제공하는 회사다.

#2핵심 질문

이 위에 Pod 가 배치된다.

#4동작 과정

  1. 묶음을 만든다create managed node group 으로 노드 그룹을 정의한다. 각 node group 은 지정한 여러 Availability Zone 에 걸쳐 돈다.
  2. 노드를 준비한다모든 노드는 Amazon EC2 Auto Scaling group 의 일부로 만들어지며, 자원은 고객 AWS 계정 안에서 돈다. 사용자가 따로 인스턴스를 준비하거나 등록할 필요가 없다.
  3. 갱신을 맡긴다노드 업데이트와 종료는 기존 앱이 끊기지 않도록 드레인 하며 진행된다. launch template 과 capacity type으로 그룹 전체에 적용되는 설정을 지정한다.
  4. 확인해 볼 것콘솔에서 노드 그룹의 노드 수가 설정한 desired size 에 맞춰 서 있는지 확인한다.

warm pool 을 켜두면 교체 전에 미리 노드를 띄운다.

#4동작 과정

  1. 변경할 값을 고른다노드 수를 정한다. desired size 와 maximum size 는 언제나 함께 본다.
  2. 새 노드의 모양을 정한다launch templates 로 AMI 와 시작 설정을 고르고, 업데이트 방식은 update behavior 로 정한다. warm pool 을 켜두면 교체 전에 새 노드를 미리 준비한다.
  3. 교체를 진행한다EKS 가 새 노드를 만들고 기존 노드를 차례로 비우고 교체한다. EKS optimized AMI 를 쓰면 최신 보안 패치와 운영체제 업데이트가 함께 적용된다.
  4. 확인해 볼 것콘솔에서 업데이트 상태가 완료로 넘어가고 노드 수가 desired size 로 유지되는지 확인한다.

→ 03-02 참조

#1문제 상황

노드 그룹(워커 컴퓨터 묶음, → 03-01)을 미리 정한 개수만큼 만들어 두면, 사람이 노드를 늘리지 않으면 Pod 가 자리에 못 박힌다. 노드가 반대로 많으면 비용만 오른다.

노드 그룹의 자동 크기 조정과 영역 이동은 이 두 문제를 자동으로 푼다. 사용량에 맞춰 노드 수를 조절하고, 한 영역이 죽으면 다른 영역으로 옮긴다.

#2핵심 질문

#3동작 예시

#4동작 과정

  2. 노드를 늘린다 줄인다새 Pod 자리가 모자라면 워커 노드를 추가하고, 남는 노드가 쌓이면 제거한다. Karpenter는 규모와 성능에 맞춰 노드 종류와 수를 스스로 고르는 자동 확장 도구다.
  3. 영역을 옮긴다zonal shift는 한 Availability Zone(서로 분리된 가용 영역)이 통째로 응답하지 않을 때 다른 영역으로 Pod 를 옮기는 기능이다.
  4. 확인해 볼 것콘솔에서 노드 그룹의 노드 수가 시간에 따라 바뀐 기록과 Pending Pod 수를 확인한다.

AWS Fargate는 그 준비를 없앤다. 어떤 Pod 를 Fargate 에서 돌릴지만 알려 주면 나머지는 AWS 가 한다.

#2핵심 질문

노드 준비 없이 컨테이너만 바로 올릴 수 있을까?

#3동작 예시

테스트용 Pod 하나를 올릴 때 인스턴스 유형을 고르지 않는다. Fargate profile 로 Pod 를 지정하고 기다리면 곧바로 실행 상태가 된다.

로그는 설정한 Fargate logging 목적지인 CloudWatch Logs로 흘러간다.

#4동작 과정

  1. 지정한다클러스터에 Fargate profile을 만들고 어떤 Pod 를 대상으로 삼을지 정한다. profile은 사용할 CPU·메모리와 실행할 네임스페이스·라벨을 담는 설정 단위다.
  2. 스케줄한다AWS 가 만든 컨트롤러가 일반 Pod 를 Fargate 로 보내 실행한다. 이 서버리스 컴퓨팅 방식은 사용자가 서버를 준비하거나 크기를 결정하지 않는다.
  3. 확인해 볼 것kubectl로 Pod 의 노드 이름 자리에 Fargate 실행 표시가 붙는지 확인한다.

self-managed nodes는 사용자가 그 판단을 직접 하는 길이다. 대신 준비와 갱신을 전부 자신이 맡는다.

#2핵심 질문

#4동작 과정

  1. 환경을 고른다노드를 돌릴 운영체제를 정한다. Amazon Linux는 AWS 가 관리하는 배포판이고, Bottlerocket은 보안 업데이트가 잦은 축소 이미지로, 컨테이너와 노드 구성 요소를 최소로 둔 운영체제다.
  2. 클러스터에 붙인다launch nodes와 node bootstrap 설정으로 인스턴스를 띄우고 EKS 클러스터에 등록한다. 모든 노드는 EKS 노드 IAM 역할을 써야 한다.
  3. 확인해 볼 것kubectl get nodes에서 등록한 인스턴스가 Ready 로 보이는지 확인한다.

VPC 와 서브넷 요건은 EKS 가 요구하는 네트워크 조건을 정해 둔 규칙이다. Amazon EKS 는 서로 다른 Availability Zone 에 있는 서브넷 최소 두 개를 요구한다.

#2핵심 질문

클러스터가 요구하는 네트워크 조건은 무엇일까?

#4동작 과정

  1. VPC 를 고른다VPC requirements에 맞춰 DNS 활성화와 서브넷이 VPC 안에서 충분히 나뉘어 있는지를 확인한다. 이미 있는 VPC 를 쓰면 된다.

  4. 확인해 볼 것콘솔의 클러스터 서브넷 목록에 두 개 이상의 영역이 모두 잡혀 있는지 확인한다.

Amazon VPC CNI — Pod IP 를 VPC 에서 온다

Amazon VPC CNI 애드온은 각 Pod 에 VPC 서브넷의 실제 IP 주소(탄력 IP 가능)를 직접 배정해 줄이 없이 VPC 안에서 Pod 가 통신하게 만든다.

먼저 알아야 할 것 04-01

→ 04-01 참조

#1문제 상황

Pod 는 보통 클러스터 안의 별도 주소 대역에서 주소를 받는다(→ 04-01). 그래서 VPC 안의 다른 서비스가 Pod 주소로 바로 접근하기 어렵고 주소 관리도 따로 필요하다.

Amazon VPC CNI는 이 간극을 없앤다. IP address management를 애드온이 맡는다.

#2핵심 질문

Pod 에 VPC 안의 진짜 IP 주소를 어떻게 붙일까?

#3동작 예시

Pod manifest를 올리면 Pod 에 VPC 서브넷의 사설 IP 주소가 배정된다. 같은 VPC 의 다른 서비스가 그 주소로 바로 통신하고, NAT 를 거치지 않고 외부로 나간다.

#4동작 과정

  1. 애드온을 설치한다Amazon VPC CNI 를 클러스터의 각 EC2 노드에 배포한다. EKS Auto Mode에서는 pod networking이 기본 포함되어 따로 설치하지 않는다.

#1문제 상황

Kubernetes 에는 기본적으로 어떤 IP·포트·연결도 제한하는 규칙이 없다. Pod 이든 클러스터 밖 리소스든 자유롭게 통신한다.

네트워크 정책(network policies)은 Pod 로 들어오고 나가는 트래픽(restrict traffic)을 IP 주소나 포트 단위로 골라 허용하거나 차단한다. AWS 의 Amazon VPC CNI 애드온이 이 기능을 지원하며, 규칙은 네임스페이스 단위로 적용된다(→ 04-02).

#3동작 예시

#4동작 과정

  1. 규칙을 만든다대상 Pod 에 라벨을 붙이고 그 라벨을 목적지로 지정한 네트워크 정책을 작성한다. 허용할 포트를 나열하면 그 조건 밖의 통신은 전부 막힌다.
  2. 막는 범위를 정한다한 네임스페이스 전체를 막는 default deny 규칙을 먼저 깔고 필요한 통신만 다시 허용하는 방식으로 좁힌다. 옆 팀의 워크로드까지 격리할 때 쓴다.
  3. 네트워크 정책 에이전트를 확인한다Pod 안에서 규칙을 실제로 거르는 network policy agent 가 각 노드에서 돌아 있는지 본다.
  4. 확인해 볼 것kubectl 로 정책과 Pod 의 라벨이 의도한 대로 붙어 있는지 확인한다.

CoreDNS 와 kube-proxy — 이름 찾기와 주소 옮기기

CoreDNS 는 서비스 이름을 IP 로 바꿔 주는 클러스터 내부 DNS 서버이고, kube-proxy 는 서비스가 가리키는 Pod 가 바뀌면 이를 노드의 규칙(iptables/ipvs)에 반영해 주소를 옮긴다.

먼저 알아야 할 것 04-02

#1문제 상황

Pod 는 IP 가 바뀌고 새로 생기거나 사라진다. 그럼에도 컨테이너는 상대 이름으로 서로를 찾아야 하고, 서비스가 가리키는 Pod 가 바뀌면 그 주소도 옮겨져야 한다.

CoreDNS 는 클러스터 안의 DNS 서버로 서비스 이름의 DNS resolution 을 해 주고, kube-proxy 는 그 결과를 각 노드의 규칙에 반영해 연결을 유지한다.

#2핵심 질문

#3동작 예시

Pod 이 하나 재생성되어 IP 가 바뀌어도 이름은 그대로다.

#4동작 과정

  1. DNS 서버를 돌린다노드가 하나 이상 있는 클러스터에는 기본으로 CoreDNS 복제본 두 개가 배포된다. 클러스터의 모든 Pod 가 여기서 이름을 IP 로 바꾼다.
  2. 이름을 IP 로 바꾼다CoreDNS 는 DNS resolution 을 수행해 클러스터 내부의 서비스 이름을 찾아 필요한 Pod 로 연결시킨다. 유입량이 크면 노드마다 DNS 캐시를 두는 node-local DNS cache 로 나누어 부하를 낮춘다.
  3. 주소를 옮긴다kube-proxy 는 서비스가 가리키는 Pod 가 바뀐 것을 보고 노드의 iptables·ipvs 규칙을 고쳐 트래픽이 새 Pod 로 가게 한다.
  4. 확인해 볼 것kubectl 로 CoreDNS 의 Pod 가 원하는 수만큼 준비되었는지 확인한다.

CPU·메모리 같은 사용률 지표를 보고 같은 일을 하는 포드(컨테이너 묶음)의 복사본 개수를 자동으로 늘렸다 줄이는 기능으로, 늘리려면 먼저 지표를 수집하는 Metrics Server가 클러스터에 설치돼 있어야 한다.

#1문제 상황

Horizontal Pod Autoscaler(HPA)는 CPU 사용률을 보고 그 포드 개수를 자동으로 조정한다. 지표를 만들어 주는 지표 수집 도구(metrics server)가 클러스터에 있어야 동작한다.

부하가 늘 때 같은 일을 하는 포드 개수를 어떻게 자동으로 맞춰 주는가?

#3동작 예시

CPU 사용률 목표치를 50퍼센트로 지정해 둔다. 주문이 몰리며 그 수치를 넘어서면 포드가 하나씩 추가된다.

부하가 내려가면 필요 없어진 포드가 줄어 노드가 다른 앱에 다시 쓰인다. 이 조정을 target tracking 방식이라고 한다.

#4동작 과정

  1. 지표를 준비한다클러스터에 metrics server 를 설치해 각 포드의 CPU·메모리 사용량을 수집한다. HPA 자체는 별도 설치 없이 표준 API 리소스로 동작한다.
  2. 목표를 정한다Deployment 등에 HPA 를 지정하고 목표 CPU 사용률과 최소·최대 포드 수를 적는다.
  3. 개수를 조정한다HPA 가 metrics server 의 값을 읽어 현재 목표에서 벗어나면 포드 수를 늘리거나 줄인다.
  4. 확인해 볼 것kubectl 로 HPA 상태를 보고 현재 포드 수와 목표 사용률이 보이는지 확인한다.

포드마다 필요한 CPU·메모리 양을 관찰해 각 컨테이너의 자원 요청량(상한·하한 사이 값)을 자동으로 다시 지정해 줘서, 워크로드를 늘리는 대신 늘리는 대신 포드를 더 효율적으로 실행하는 기능.

→ 05-02 참조

#1문제 상황

포드를 늘리는 방법만 있으면 한 포드가 노드 자원을 과하게 잡아 노드 수까지 불어나게 된다. 어떤 자원을 늘릴지 정해 자동으로 개수를 조절하는 것을 Autoscaling이라 부르며, 각 컨테이너의 requests and limits, 즉 자원 요청량과 상한을 사람이 정해 둔 상태라 낭비가 남는다.

Vertical Pod Autoscaler(VPA)는 각 컨테이너의 container resources 를 관찰해 알맞은 크기로 다시 지정한다.

#2핵심 질문

각 컨테이너의 자원 요청량을 실제 사용량에 맞춰 어떻게 다시 정할까?

#3동작 예시

지금은 2코어와 1기가바이트를 요청하는 포드가 있지만 실제로는 그 절반만 쓴다. VPA를 켜 두면 관찰 기간 뒤 요청량을 낮게 고쳐 준다.

그러면 같은 노드에 더 많은 포드를 올릴 수 있다.

#4동작 과정

  1. 지표를 준비한다클러스터에 metrics server 가 있어야 각 컨테이너의 실제 사용량을 알 수 있다.
  2. VPA 를 배포한다Vertical Pod Autoscaler 를 클러스터에 설치하고 대상 네임스페이스에 배포한다.
  3. 요청량을 다시 지정한다VPA 가 관찰한 사용량으로 각 컨테이너의 요청량을 정해 준다. 한정된 자원을 효율적으로 쓰게 되어 노드 수를 줄일 수 있다.
  4. 확인해 볼 것kubectl 로 VPA 상태를 보고 어떤 컨테이너의 요청량이 바뀐 것인지 확인한다.

클러스터에 미리 묶어 둔 구성 요소를 설치해 Cilium 네트워크 플러그인이나 CoreDNS 같은 필수 기능을 직접 만들지 않고 붙이는 방법.

먼저 알아야 할 것 05-01

#1문제 상황

네트워크 플러그인이나 CoreDNS 같은 구성 요소는 클러스터가 조금만 다르게 만들어져도 직접 설치하고 맞춰 봐야 한다. 매번 버전과 설정을 관리하는 것도 일이다.

Amazon EKS 애드온은 이런 구성 요소를 미리 묶어 두었다가 필요한 것만 골라 붙이는 방식이다. VPC CNI 플러그인·kube-proxy·CoreDNS 같은 self-managed 애드온은 모든 클러스터에 자동 설치된다.

#2핵심 질문

클러스터에 필요한 구성 요소를 버전과 설정까지 보장된 상태로 어떻게 붙이는가?

#3동작 예시

AWS 애드온 목록에서 CoreDNS 애드온을 고르고 create an add-on 으로 설치한다. 설치된 버전과 설정이 콘솔에 그대로 표시된다.

이후 애드온 업데이트가 나오면 콘솔에서 새 버전을 선택해 올린다.

#4동작 과정

  1. 애드온 종류를 고른다목록에는 AWS 가 관리하는 AWS add-ons, 커뮤니티가 만든 community add-ons, Marketplace add-ons 가 있다. 앞의 기능인 관측성 에이전트나 네트워킹·스토리지 드라이버가 여기에 속한다.
  2. 설치한다필요한 애드온을 골라 create an add-on 으로 클러스터에 배포하고 버전을 고른다.
  3. 설정을 바꾼다기본 설정을 수정하거나 호환되는 새 버전으로 업데이트한다. 애드온마다 지원 범위가 다르다.
  4. 확인해 볼 것콘솔에서 설치된 애드온의 이름과 상태가 활성 상태로 보이는지 확인한다.

#1문제 상황

EKS 애드온(→ 05-04)은 자동으로 바뀌지 않는다. 새 버전이 나오거나 클러스터의 Kubernetes 마이너스 버전을 올려도 그대로 남는다. 그래서 애드온이 구버전이면 새 Kubernetes 버전과 맞지 않아 기능이 다르게 동작한다.

애드온 버전 맞추고 바꾸기는 클러스터별로 애드온의 update an add-on 작업을 직접 요청해 특정 버전에 고정하거나 호환되는 새 버전으로 올리는 것이다.

#2핵심 질문

#3동작 예시

EKS가 애드업을 대신 올리고, 상태가 정상으로 표시되는지 화면에서 확인한다.

#4동작 과정

  1. 버전을 살핀다애드온에 IAM 역할이 필요한지 확인하고, 고를 버전이 클러스터와 맞는지 review 한다. 이 확인 절차를 verify compatibility 라 부른다.
  2. 업데이트를 건다클러스터별 애드온 업데이트를 시작하면 EKS가 대신 update an add-on 을 수행한다. customize fields 로 설정 값을 함께 넘길 수 있다.
  3. 애드온을 뗀다더 이상 쓰지 않을 애드온은 remove an add-on 으로 삭제하고, 되돌릴 이전 버전을 함께 정리한다.
  4. 확인해 볼 것콘솔의 애드온 목록에서 대상 애드온 상태가 Active 로 표시되는지 본다.

#3동작 예시

  2. 검증기를 붙인다Gatekeeper 를 admission controller 로 두고 Ratify 를 AWS Signer 플러그인과 함께 웹훅으로 붙이거나, Kyverno 를 정책 엔진으로 AWS Signer 플러그인 설정해 쓴다.

  4. 확인해 볼 것서명하지 않은 이미지를 배포해 보아 Pod 가 뜨지 않고 거부되는지 본다.

6. 스토리지를 붙인다 — Pod 밖의 디스크06-01

Amazon EBS CSI — 블록 스토리지

EBS CSI 드라이버는 포드가 각자 전용 블록 스토리지 볼륨(하드디스크처럼 통째로 붙는 저장 공간)을 요청해 마운트할 수 있게 해 주는 컨테이너 스토리지 인터페이스(CSI, 쿠버네티스가 외부 스토리지를 다루게 하는 표준 규격) 드라이버다.

먼저 알아야 할 것 04-02

→ 06-05 참조

#1문제 상황

Pod 가 만들어졌다가 사라지면(→ 01-03) 그 안의 데이터도 함께 사라진다. 데이터베이스용 Pod 에는 Pod 가 죽어도 남는 저장 공간이 필요하다.

Amazon EBS CSI — 블록 스토리지 는 Amazon EBS 볼륨의 생성과 삭제까지 맡는 컨테이너 스토리지 인터페이스(CSI, 쿠버네티스가 외부 스토리지를 다루게 하는 표준 규격) 드라이버로, 이렇게 전용 디스크를 붙여 준다.

#2핵심 질문

Pod 마다 사라지지 않는 전용 블록 스토리지를 어떻게 붙일까?

#3동작 예시

상태가 있는 워크로드를 배포하면서 볼륨을 요청한다. EBS CSI 드라이버가 StorageClass 라는 설정에 따라 Amazon EBS 볼륨을 만들고 persistent volume 으로 Pod 에 붙인다.

Pod 를 지우고 다시 만들어도 데이터베이스 파일이 그대로 남아 있다.

#4동작 과정

  1. 드라이버를 둔다EKS 클러스터에 EBS CSI driver 를 설치해 노드에서 볼륨 작업을 받는다. EKS Auto Mode 클러스터는 설치가 필요 없고, Fargate Pod 에는 Amazon EBS 볼륨을 붙일 수 없다.
  2. 요청한다매니페스트에서 persistent volume claim 을 만들면 드라이버가 볼륨 생명 주기를 관리한다. 일회용 임시 볼륨도 같은 방식으로 만든다.
  3. 보호한다볼륨 암호화가 필요한 경우 StorageClass 에 암호화 설정을 담아 EBS 볼륨을 암호화해 만든다.
  4. 확인해 볼 것볼륨을 붙인 Pod 에서 파일을 쓰고 Pod 를 다시 만든 뒤 파일이 남아 있는지 본다.

EFS CSI 드라이버는 여러 포드가 동시에 읽고 쓸 수 있는 네트워크 파일 시스템 볼륨을 붙여 주어, 포드 수나 노드 수가 바뀌어도 같은 파일이 보이는 공유 디스크 역할을 하게 한다.

먼저 알아야 할 것 06-01

#1문제 상황

같은 파일을 여러 Pod 가 함께 써야 한다. 전용 블록 볼륨(→ 06-01)은 한 번에 한 Pod 만 붙일 수 있고, Pod 수나 노드 수가 바뀌면 연결도 다시 잡아야 한다.

Amazon EFS CSI — 공유 파일 시스템 은 여러 Pod 가 동시에 붙어 쓰는 네트워크 파일 시스템을 제공해 이 문제를 푼다.

#2핵심 질문

몇 개의 Pod 라도 같은 파일을 함께 볼 수 있게 어떻게 공유할까?

#3동작 예시

여러 Pod 가 같은 디렉터리의 설정 파일을 읽고 기록한다. EFS CSI driver 가 붙은 볼륨을 쓰면 어느 Pod 에서 쓰든 다른 Pod 에 바로 보인다.

Pod 를 늘려도 공유 디스크는 그대로 하나다.

#4동작 과정

  1. 드라이버를 배포한다Amazon EFS CSI driver 를 EKS 클러스터에 설치한다. Windows 컨테이너 이미지에서는 쓸 수 없다.
  2. 볼륨을 붙인다EFS 파일 시스템을 persistent volume 으로 마운트해 여러 컨테이너가 동시에 접근하게 한다. 이처럼 여러 곳에서 같이 붙는 성질을 ReadWriteMany 라고 한다.
  3. 할당 방법을 정한다드라이버를 직접 지정해 미리 만든 볼륨을 붙이는 방식과, StorageClass 로 요청 시 새 파일 systems 를 만드는 방식이 있다. Fargate Pod 에는 후자를 쓸 수 없다.
  4. 확인해 볼 것두 Pod 의 같은 경로에 쓴 파일이 상대 Pod 에서 보이는지 본다.

FSx 계열 CSI — HPC와 엔터프레이즈 파일 시스템

FSx CSI 드라이버는 Lustre·ONTAP·OpenZFS 같은 Amazon FSx 파일 시스템을 CSI 규격으로 붙여, 고성능 병렬 처리나 엔터프라이즈 NAS 요구를 쿠버네티스 워크로드에서 쓰게 한다.

먼저 알아야 할 것 06-01

#1문제 상황

공유 파일 시스템(→ 06-02)이 있어도 대규모 병렬 처리에서는 처리량과 지연 시간 요구가 남는다. 엔터프라이즈 환경은 NAS 기능이 필요하고, 클라우드 위에서 그 기능과 성능을 함께 얻기 어렵다.

FSx 계열 CSI — HPC와 엔터프라이즈 파일 시스템 은 이런 요구에 맞는 파일 시스템을 CSI 규격으로 붙여 준다.

#2핵심 질문

병렬 처리와 엔터프라이즈 NAS 기능이 필요한 워크로드에 어떤 파일 시스템을 붙일까?

#3동작 예시

여러 노드의 계산 작업이 같은 데이터셋을 나눠 읽는다. Pod 에 Amazon FSx for Lustre 볼륨을 CSI 볼륨으로 붙이면 많은 노드가 동시에 고속으로 읽는다.

엔터프라이즈 파일 요구에는 Amazon FSx for NetApp ONTAP 이 쓰이고, 여러 파일 시스템의 자주 읽는 부분을 모으는 데는 Amazon File Cache 가 쓰인다.

#4동작 과정

  1. 종류를 고른다병렬 처리에는 Amazon FSx for Lustre 를, 엔터프라이즈 NAS 기능에는 Amazon FSx for NetApp ONTAP 를, POSIX 파일 요구에는 Amazon FSx for OpenZFS 를 고른다.
  2. 드라이버를 붙인다고른 파일 시스템의 CSI driver 를 EKS 클러스터에 배포해 그 파일 시스템의 생명 주기를 클러스터가 관리하게 한다.
  3. 성능을 보탠다반복 읽기가 많은 워크로드에는 여러 파일 시스템의 데이터를 앞둔 Amazon File Cache 를 함께 둔다.
  4. 확인해 볼 것Pod 안에서 파일 systems 가 마운트된 경로가 보이는지 ls 로 확인한다.

S3를 볼륨으로 — Mountpoint와 S3 Files

S3 CSI 드라이버는 S3 버킷의 객체를 POSIX 파일처럼 읽고 쓰는 볼륨으로 제시해, S3에 있는 데이터셋을 디스크처럼 쓰는 워크로드(S3 Files는 애초에 파일로 관리되는 버킷)를 포드에 연결한다.

먼저 알아야 할 것 06-01

#1문제 상황

객체 스토리지에 둔 데이터셋을 계산 워크로드에서 디스크처럼 쓰고 싶다. 객체를 직접 읽는 코드를 짜지 않으면 여러 Pod 가 같은 데이터를 각자 받아 써야 한다.

S3를 볼륨으로 — Mountpoint와 S3 Files 는 버킷을 볼륨으로 제시해 애플리케이션 코드를 바꾸지 않고 붙게 한다.

#2핵심 질문

S3 버킷을 코드 수정 없이 Pod 의 디스크처럼 어떻게 쓸까?

#3동작 예시

워크로드에서 S3 에 놓인 학습 데이터셋을 읽는다. Mountpoint for Amazon S3 가 붙은 볼륨을 경로에 마운트하면 애플리케이션은 파일을 여는 것처럼 그대로 읽는다.

애니메이션을 등 aggregate throughput 을 높이면서 코드는 바뀌지 않는다.

#4동작 과정

  1. 볼륨으로 제시한다Mountpoint for Amazon S3 CSI driver 가 버킷을 object storage as file system 형태로 컨테이너에 보여 준다.
  2. 파일을 관리하는 버킷을 고른다처음부터 파일 단위로 관리되는 버킷은 Amazon S3 Files 로 다룬다.
  3. 쓰기 방식을 정한다기본은 read-only mount 다. 읽기 전용으로 붙이면 버킷의 객체는 그대로 두고 읽기만 한다.
  4. 확인해 볼 것마운트한 경로에서 버킷의 파일 목록이 보이는지 본다.

클러스터 엔드포인트 접근

EKS 클러스터의 컨트롤 플레인(마스터)은 API 서버 엔드포인트 하나를 노출하며, 이 주소의 공개·비공개 범위를 클러스터 생성 시 정하는 것이 클러스터 엔드포인트 접근이다.

먼저 알아야 할 것 04-01

#1문제 상황

kubectl 은 클러스터의 API 서버로 명령을 보낸다(→ 01-06). 그래서 클러스터를 만들면 Amazon EKS 가 그 주소 하나를 자동으로 만든다.

기본은 이 control plane endpoint를 누구에게나 열어 둔 상태라 인터넷에서 아무나 요청이 닿는다. cluster endpoint access를 설정하면 누가 밖에서 안으로 들어올 수 있는지를 정해 둘 수 있다. 공개 주소인 public endpoint와 VPC 안 주소인 private endpoint가 함께 있다.

#2핵심 질문

클라우드 API 서버 주소를 누구에게까지 열어 두어야 하는가?

#3동작 예시

회사가 사내망에서만 클러스터에 붙으려 한다. 클러스터를 만들 때 퍼블릭 접근을 끄고 프라이빗 접근만 켠다. 이후 사내망의 개발자 PC에서 kubectl 명령이 API 서버로 전달되고, 인터넷에서는 주소 자체에 닿지 못한다.

#4동작 과정

  1. 만들 때 정한다클러스터 생성 화면에서 endpoint access configuration를 고른다. public access와 private access를 각각 켜고 끌 수 있다.
  2. 권한을 함께 확인한다API 서버는 AWS Identity and Access Management(IAM, AWS 리소스 권한)과 Kubernetes Role Based Access Control(RBAC)로 보호된다. 범위를 좁혀도 인증은 이 둘이 맡는다.
  3. 확인해 볼 것콘솔의 클러스터 상세에서 cluster public endpoint와 cluster private endpoint 주소가 어떤 상태로 표시되는지 본다.

Private cluster — 인터넷 없이 닫힌 클러스터

Private cluster는 컨트롤 플레인 엔드포인트가 VPC 안의 프라이빗 IP로만 열리고 퍼블릭 액세스 엔드포인트가 없는 형태의 클러스터로, 외부 인터넷과 단절된 사내 환경에서 운영된다.

먼저 알아야 할 것 07-01

→ 07-01 참조

#1문제 상황

프라이빗 엔드포인트만 열면 API 서버 쪽은 닫히지만(→ 07-01), 노드와 워크로드는 여전히 인터넷으로 나간다. 이미지가 필요할 때마다 어디서 받는지가 문제다.

private cluster는 이 나가는 길까지 닫는다. 대신 VPC 안 컨테이너 레지스트리에서 이미지를 받고, 필요한 것만 밖으로 내보낸다.

#2핵심 질문

클러스터에서 인터넷을 막고도 필요한 자원은 어떻게 주고받는가?

#3동작 예시

운영팀이 데이터 처리 워크로드만 VPC 안에 두고 외부 연결을 원하지 않는다. 노드가 이미지를 VPC 안의 Amazon Elastic Container Registry에서 받게 하고, 컨트롤 플레인도 지정한 경로로만 나간다. 외부와는 egress-only internet access 경로 하나만 남는다.

#4동작 과정

  1. 이미지 경로를 VPC 안에 둔다노드가 VPC 안 컨테이너 레지스트리에서 이미지를 pull 하도록 요구한다. 그래서 클러스터가 인터넷을 못 쓰는 조건을 채운다.
  2. 나가는 길을 좁힌다데이터 평면 egress를 닫고, 컨트롤 플레인에서 나가는 트래픽은 control plane egress 설정으로 다룬다.
  3. 확인해 볼 것클러스터에 노드를 붙였을 때 Pod 이벤트나 노드 상태에서 이미지 관련 오류가 나는지 본다.

Access entry 로 사람 권한 주기

access entry 는 AWS IAM 주체 하나를 클러스터의 IAM 주체와 매핑해 Kubernetes API 권한을 부여하는 규칙이며, principal type 과 정책 Arn 을 함께 지정한다.

먼저 알아야 할 것 08-01

#1문제 상황

IAM 자격 증명으로 kubectl 이 들어온다고(→ 08-01) 끝이 아니다. 그 자격 증명이 클러스터에서 무엇을 할 수 있는지가 정해져야 한다.

이 대응 관계를 규칙 하나로 적는 것이 access entry다. 예전에는 aws-auth ConfigMap에 적었다(→ 08-03).

#2핵심 질문

어떤 IAM 주체를 클러스터에 들이고 무엇을 허용할 것인가?

#3동작 예시

개발팀의 IAM 역할에 클러스터 접근을 준다. access entry를 만들면서 IAM 주체의 Amazon Resource Name(ARN)을 적고, Kubernetes 그룹과 AWS access scope에 접근 범위를 지정한다. 그 뒤 같은 역할의 사람은 kubectl 로 클러스터 오브젝트를 볼 수 있다.

#4동작 과정

  1. 인증 방식을 맞춘다먼저 authentication mode을 access entries를 쓸 수 있는 값으로 바꿔 둔다.
  2. 주체를 하나만 넣는다access entry 하나에는 IAM 주체 하나의 ARN만 적는다. 같은 주체가 두 항목에 들어갈 수 없다.
  3. 권한을 정한다associate access policies로 정책을 붙이고 Kubernetes 그룹과 AWS access scope로 범위를 좁힌다. 역할 ARN에는 경로를 포함할 수 있다.
  4. 확인해 볼 것콘솔에서 클러스터의 접근 항목 목록에 만든 항목이 목록되는지 본다.

aws-auth ConfigMap 에서 access entries 로

예전에는 클러스터의 aws-auth ConfigMap 에 사용자와 역할을 매핑해 접근을 허용했지만, 이제는 그 대신 콘솔·CLI·API 로 access entry 를 직접 만들고 ConfigMap 은 더 이상 쓰지 않는다.

먼저 알아야 할 것 08-02

#1문제 상황

예전에는 클러스터 안의 aws-auth ConfigMap 이라는 설정 파일에 사용자나 역할을 적어 클러스터 API 접근을 허용했다. 그래서 어떤 주체가 무슨 역할을 가지는지 한 파일을 직접 손봐야 했다.

지금은 그 대신 콘솔·CLI·API 로 직접 만드는 목록을 쓴다. 이 목록을 access entries 라고 하며, access entry 하나는 IAM 주체 하나에 클러스터 API 권한을 붙인 규칙이다(→ 08-02). 권한이 IAM 쪽에서 관리되고 ConfigMap 은 더 이상 쓰지 않는다.

#2핵심 질문

이미 만들어 둔 aws-auth ConfigMap 매핑을 access entry 로 옮겨 같은 권한을 유지하려면?

#3동작 예시

기존 ConfigMap 에 개발자 역할 세 개를 넣어 둔 클러스터가 있다. 운영자가 콘솔의 액세스 항목 화면에서 같은 IAM 주체 세 개를 access entry 로 만들고, 확인이 끝나면 ConfigMap 의 해당 줄을 지운다.

결과적으로 클러스터 접근 권한이 ConfigMap 가 아니라 IAM 계층에서 관리되는 목록으로 남는다.

#4동작 과정

  1. 확인한다클러스터가 어떤 인증 모드로 동작하는지 본다. API_AND_CONFIG_MAP 모드에서는 같은 IAM 역할이 양쪽에 있으면 access entry 쪽 매핑이 우선한다.
  2. 옮긴다기존 ConfigMap 항목을 access entry 로 하나씩 만든다. ConfigMap 항목에는 접근 정책을 붙일 수 없으므로, 정책 Arn 이 필요하면 반드시 access entry 로 만들어야 한다.
  3. 지운다옮긴 뒤 ConfigMap 에서 해당 항목을 제거한다. aws-auth ConfigMap 또는 Fargate 노드 그룹을 위해 EKS 가 만든 항목은 그대로 둔다.
  4. 확인해 볼 것콘솔의 액세스 항목 목록에 옮긴 주체와 역할이 보이는지 확인한다.

#5한 줄 요약

먼저 알아야 할 것 08-02

#1문제 상황

클러스터에 붙는 사람의 권한은 보통 IAM 자격 증명으로 인정받는다(→ 08-02). 그러면 사내 로그인 체계는 계정에 별도로 만들어야 하고, AWS 계정을 쓰지 않는 사람은 붙기 어렵다.

OIDC provider 연결은 외부에 이미 있는 로그인 체계를 그대로 받아 Amazon EKS 가 쓸 수 있게 한다. 로그인한 사람이 IAM 권한으로 클러스터에 붙는다.

#2핵심 질문

사외 로그인 체계의 계정으로 클러스터에 붙으려면?

#3동작 예시

사내 계정 관리 서버가 OpenID Connect, 즉 웹 로그인끼리 신원을 주고받는 표준 방식을 이미 쓰고 있다. 그 서버의 주소를 IAM OIDC provider 로 등록해 클러스터에 연결한다.

로그인을 마친 사용자가 만든 kubectl 토큰을 클러스터가 서명 확인하고, IAM 에서 정한 권한만큼 Kubernetes API 를 쓸 수 있게 된다.

#4동작 과정

  1. 등록한다IAM OIDC provider 를 만들어 사내 로그인 서버의 주소와 클라이언트 식별자를 IAM 에 알린다. 이 등록이 클러스터가 그 서버를 믿는 근거가 된다.
  2. 연결한다그 주소를 cluster OIDC issuer 로 삼아 클러스터의 인증 설정에 묶는다. 이제 발급된 토큰의 서명을 클러스터가 직접 확인할 수 있다.
  3. 붙인다로그인한 사용자를 Kubernetes 역할과 rolebinding 에 묶어 권한을 준다. 사내 계정 체계와 IAM 과 연결된 경우에도 쓸 수 있다.
  4. 확인해 볼 것콘솔의 액세스 항목 목록에 OIDC 로 로그인한 사람이 항목으로 나타나는지 확인한다.

#5한 줄 요약

OIDC 공급자 연결은 사외 로그인 체계의 신원 증명을 클러스터가 받아들이게 해 권한을 함께 쓰게 하는 설정입니다.

IRSA — Pod 에 IAM 역할 붙이기

IAM Roles for Service Accounts(IRSA)는 클러스터의 OIDC 공급자와 IAM 역할의 신뢰 관계를 연결한 뒤 ServiceAccount 에 role-arn 주석을 붙여 그 Pod가 해당 AWS 권한으로 동작하게 하는 방식이다.

먼저 알아야 할 것 08-04

#1문제 상황

Pod 안의 애플리케이션이 AWS 서비스를 호출하려면 요청에 서명할 자격 증명이 필요하다. 키를 컨테이너에 직접 넣으면 노드와 Pod 가 늘어날 때마다 관리가 늘어난다.

IAM roles for service accounts, 줄여 IRSA 는 Kubernetes 서비스 계정에 IAM 역할을 묶어 이 문제를 없앤다.

#2핵심 질문

Pod 안의 애플리케이션에 AWS 권한을 키 배포 없이 어떻게 주나?

#3동작 예시

이미지가 S3 버킷에서 파일을 읽는 워크로드를 만든다. 그 Pod 가 쓰는 ServiceAccount 에 role-arn 주석과 클러스터 OIDC 주소가 담긴 주석을 넣는다.

Pod 가 부팅되면 클러스터가 web identity token, 즉 이 Pod 의 신원을 담은 서명 토큰을 발급하고, AWS 는 이를 확인해 임시 자격 증명을 건넨다. 애플리케이션은 그 자격 증명으로 버킷을 읽는다.

#4동작 과정

  1. 역할을 준비한다클러스터 OIDC issuer 를 신뢰 조건에 넣은 IAM 역할을 만든다. 이 신뢰가 cross-account IAM 권한을 쓸 때도 같은 방식으로 필요하다.
  2. 연결한다ServiceAccount 에 role-arn 주석과 OIDC issuer 주석을 붙인다. 이 주석이 Pod 와 IAM 역할 사이의 연결 고리다.
  3. 사용한다Pod 안에서 AWS SDK 나 AWS CLI 가 해당 역할의 임시 자격 증명을 받아 AWS API 를 호출한다. 키를 컨테이너에 넣지 않아도 된다.
  4. 확인해 볼 것워크로드의 Pod 안에서 AWS CLI 로 역할 정보를 조회해 어떤 역할이 붙었는지 확인한다.

#5한 줄 요약

IRSA 는 Kubernetes ServiceAccount 에 IAM 역할을 연결해 Pod 안의 애플리케이션이 키 배포 없이 그 권한을 쓰게 하는 방식입니다.

EKS Pod Identity — IRSA 를 대신하는 새 길

EKS Pod Identity 는 클러스터의 인증 에이전트가 노드에서 실행 중인 Pod 들의 신원을 관찰해 클라우드 계층의 컨테이너 자격 증명과 연결해 주는 방식으로, ServiceAccount 에 role-arn 을 적지 않고도 IAM 역할을 부여한다.

먼저 알아야 할 것 08-05

#1문제 상황

IRSA 는 역할과 클러스터의 OIDC 주소를 Pod 맘대로 적어야 했다(→ 08-05). 그래서 역할이 여러 계정에 걸치면 같은 설정이 반복되고, 어떤 Pod 가 어떤 역할인지도 설정 안에서 찾아야 한다.

EKS Pod Identity 는 그 주석 대신 클라우드 계층의 연결 정보로 역할을 배정한다. ServiceAccount 에 role-arn 을 적지 않아도 된다.

#2핵심 질문

Pod 에 AWS 권한을 주되 클라우드 쪽 연결 정보로 관리하려면?

#3동작 예시

S3 에서 파일을 읽는 Pod 가 있는 클러스터에서 역할 매핑을 하나 등록한다. 등록에는 클러스터 이름, 네임스페이스, ServiceAccount 이름, 사용할 EKS Pod Identity role 이 들어간다.

Pod Identity Agent 가 노드에서 실행 중인 Pod 를 지켜보다가 그 ServiceAccount 에 연결된 역할을 찾아 건넨다. 애플리케이션은 자격 증명 없이 임시 자격 증명으로 버킷을 읽는다.

#4동작 과정

  1. 준비한다클러스터에 Pod Identity Agent 를 설치해 EKS Pod Identity 를 켠다. 컨테이너 자격 증명이 이 에이전트 역할로 만들어진다.
  2. 연결한다EKS Pod Identity association 을 만들어 하나의 역할과 네임스페이스 안의 ServiceAccount 를 묶는다. 같은 애플리케이션이 여러 클러스터에 있으면 같은 형태의 연결을 각 클러스터에 만든다.
  3. 사용한다Pod 가 자격 증명을 요구하면 에이전트가 이 association 을 보고 EKS Pod Identity role 의 임시 자격 증명을 준다. ServiceAccount 주석은 필요 없다.
  4. 확인해 볼 것콘솔에서 만들어진 연결이 클러스터·네임스페이스·ServiceAccount 항목으로 보이는지 확인한다.

#5한 줄 요약

EKS Pod Identity 는 클러스터의 에이전트가 Pod 를 관찰해 IAM 역할을 배정하게 하는, ServiceAccount 주석이 필요 없는 새 경로입니다.

EKS 버전 체계

EKS 가 클러스터의 Kubernetes 버전과 이를 받치는 EKS 자체의 플랫폼 버전을 따로 관리하는 구분 체계로, 클러스터는 마이너스 세 자리(예: 1.32) 단위로, 플랫폼은 운영 패치와 컴포넌트 업데이트가 담기는 묶음 단위로 올라간다.

먼저 알아야 할 것 01-03

#1문제 상황

Kubernetes 의 기능이 계속 올라가니 클러스터도 자주 갱신해야 한다. 그런데 "무엇을 갱신하고 있는지"가 한 번호로는 드러나지 않는다. 같은 Kubernetes 버전이라도 EKS 쪽에 고친 내용이 다르다.

EKS versioning 은 Kubernetes versions 와 platform versions 를 분리해 관리한다. control plane version 은 그 안에서 컨트롤 플레인 구성요소가 어느 묶음으로 빌드되었는지를 가리킨다.

#2핵심 질문

클러스터가 어떤 Kubernetes 버전이고 그 위에 어떤 EKS 수정이 올라가 있는지 어떻게 구분하나?

#3동작 예시

운영자가 EKS 콘솔에서 클러스터의 상태를 본다. 화면에는 Kubernetes 1.32 라는 버전과 그 버전을 받치는 EKS 자체 버전이 따로 보인다.

새 Kubernetes 버전이 나오면 지원 대상 목록에 추가되고, 같은 Kubernetes 버전 안에서도 platform version 이 올라가며 컨트롤 플레인 구성요소가 갱신된다.

#4동작 과정

  1. 알아본다EKS 문서의 versioning 페이지에서 어떤 Kubernetes 버전이 지금 제공되는지 본다. 지원되는 버전 목록과 지원 정책이 여기에 모여 있다.
  2. 구분한다클러스터의 Kubernetes version 과 이를 받치는 platform version 을 따로 읽는다. 버전마다 여러 platform version 이 붙을 수 있다.
  3. 추적한다platform version 별 변경 내용을 확인하며 클러스터가 어느 묶음 위에서 돌고 있는지 파악한다.
  4. 확인해 볼 것콘솔의 클러스터 상세 화면에서 Kubernetes 버전과 EKS 버전이 두 항목으로 보이는지 확인한다.

#5한 줄 요약

EKS 버전 체계는 클러스터가 도는 Kubernetes 버전과 그 위의 EKS 수정 묶음을 따로 관리하는 방식입니다.

표준 지원과 확장 지원

Kubernetes 버전마다 정해진 기간 동안 무료로 패치와 도움을 주는 표준 지원과, 그 기간이 지난 뒤에도 유료로 계속 유지해 주는 확장 지원을 나눈 지원 등급 체계로, 확장 지원으로 넘어가면 클러스터당 추가 요금이 붙는다.

먼저 알아야 할 것 09-01

→ 09-01 참조

#1문제 상황

Kubernetes 버전은 계속 올라가지만 모든 앱이 즉시 새 버전으로 갈 수는 없다. 오래된 버전을 무조건 끊으면 운영 중인 서비스가 위험해진다.

standard support 와 extended support 를 나누면 남은 기간이 짧아도 일정을 정해 두고 이전 버전으로 내려올 수 있다.

#2핵심 질문

오래된 Kubernetes 버전을 유지해야 할 때 지원 범위를 어떻게 정하나?

#3동작 예시

Kubernetes 1.32 를 쓰는 팀이 새 버전으로 올리기까지 시간이 걸린다. 이 버전은 표준 지원 기간이 남아 있어 EKS releases 기준의 새 패치를 계속 받고, 버전에 중요한 변경이 생기면 그 목록에서 미리 확인한다.

기간이 지난 뒤에도 버전을 유지하고 싶다면 확장 지원으로 넘어가고, 그에 맞는 추가 비용을 부담한다.

#4동작 과정

  1. 알아본다어떤 버전이 지금 표준 지원이고 지원 기간이 얼마나 남았는지 지원 페이지에서 확인한다.
  2. 대비한다표준 지원 중인 버전들의 릴리스 노트를 보고, upcoming 버전에서 미리 기본으로 켜지는 동작이 있는지 확인한다.
  3. 결정한다바로 올리지 못하면 버전을 유지한 채 기다리거나, 추가 비용을 내고 확장 지원으로 기간을 이어간다.
  4. 확인해 볼 것EKS 콘솔의 버전 목록에서 각 버전의 지원 등급과 남은 기간이 표시되는지 확인한다.

#5한 줄 요약

표준 지원과 확장 지원은 Kubernetes 버전을 무료로 유지할 기간과 유료로 더 유지할 기간을 나누어 정하는 지원 등급 체계입니다.

Kubernetes 버전 올리기

클러스터를 더 최신 Kubernetes 버전으로 바꾸는 작업으로, 처음에는 다음 마이너스 버전까지만 한 단계씩 올라가고 이후에는 여러 단계를 한 번에 건너뛸 수 있으며, 업그레이드 순서와 허용 범위는 EKS 가 정한 정책에 따라 정해진다.

먼저 알아야 할 것 09-02

→ 09-01 참조

#1문제 상황

새 Kubernetes 버전이 EKS 에 제공돼도 올리면 새 버전이 가져오는 큰 변화가 기존 앱을 깨뜨릴 수 있다. 아무 때나 올리면 되돌릴 틈도 없다.

update Kubernetes version 은 처음에는 다음 마이너스 버전까지만 한 단계씩 오르도록 정하고, 그 이후에는 여러 단계를 건너뛸 수 있게 한다.

#2핵심 질문

운영 중인 클러스터를 새 Kubernetes 버전으로 올리면서 위험을 어떻게 낮추나?

#3동작 예시

운영 팀이 새 버전 제공 소식을 보고 테스트 클러스터를 먼저 1.32 에서 1.33 으로 올려 같은 앱을 돌려 본다. 문제가 없으면 단계별로 운영 클러스터를 올리고, 정해 둔 upgrade window 안에 컨트롤 플레인만 갱신한다.

업그레이드 후 문제가 보이면 허용된 기간 안에 이전 버전으로 되돌린다.

#4동작 과정

  1. 검토한다라이프사이클 문서와 릴리스 노트를 보고 새 버전의 큰 변화부터 확인한다. 운영 클러스터에 바로 올리지 않고 CI 로 앱 동작을 먼저 시험한다.
  2. 올린다upgrade policy 와 upgrade window 에 맞추어 다음 마이너스 버전으로 갱신한다. 처음에는 한 단계씩만 오르고 그 뒤에는 여러 단계를 한 번에 건너뛸 수 있다.

  4. 확인해 볼 것콘솔에서 클러스터의 Kubernetes 버전이 올바른 값으로 바뀌었는지 확인한다.

내려가기 — 롤백과 Auto Mode 클러스터

버전 업그레이드 후 문제가 생겼을 때 이전 Kubernetes 버전으로 되돌리는 절차로, 일반 클러스터는 콘솔이나 명령 도구에서 롤백을 요청하고, 자동 모드로 만들어진 클러스터는 노드와 애드온을 자동 관리하므로 업그레이드와 마찬가지로 이전 버전으로 되돌리는 경로를 따라 처리한다.

먼저 알아야 할 것 09-03

→ 09-03 참조

#1문제 상황

Kubernetes 버전을 한 단계 올린 뒤(→ 09-03) 애플리케이션이 호환되지 않거나 사라진 API를 쓰거나 동작이 이상해질 수 있다. 이때 앞으로 더 올리는 방법으로는 과거로 갈 수 없다. EKS version rollback은 클러스터의 Kubernetes control plane을 이전 마이너스 버전으로 되돌려 알려진 좋은 상태로 복구하는 기능이다. EKS Auto Mode는 노드와 애드온을 AWS가 대신 관리하는 클러스터 구성 방식이라, 되돌릴 때 같은 자동 관리 경로를 따라 처리한다. 네이티브와 애드온, 예외는 따로 확인해야 한다.

#2핵심 질문

버전 업그레이드 후 문제가 생겼을 때 이전 Kubernetes 버전으로 어떻게 되돌아갈까?

#3동작 예시

1.31로 올린 직후 배포한 워크로드가 Kubernetes 예전 API 때문에 죽었다. 운영자가 롤백을 요청한다. 요청이 진행되면 콘솔의 상태가 롤백 진행으로 바뀌고, 끝나면 클러스터가 다시 1.30에서 동작한다.

#4동작 과정

  1. 롤백 대상을 확인한다롤백 readiness insight로 되돌릴 수 있는 상태인지 보고, 준비가 안 된 워크로드는 미리 고친다.
  2. 노드를 준비한다EKS Auto Mode가 아니라면 클러스터와 같은 Kubernetes 버전의 EKS-optimized AMI로 워커 노드를 갱신해 둔다.
  3. 컨트롤 플레인을 되돌린다콘솔이나 명령 도구로 롤백을 요청하면 API 서버와 컨트롤러가 이전 마이너스 버전으로 돌아간다. EKS Auto Mode 클러스터는 auto mode rollback 경로를 따라 처리한다.
  4. 확인해 볼 것콘솔의 클러스터 대시보드에서 Kubernetes 버전이 이전 마이너스로 내려갔는지 본다.

시크릿 암호화

Kubernetes의 Secret 오브젝트에 평문으로 저장되는 비밀값을 암호화 키로 암호화해 저장되게 하는 설정으로, 클러스터의 데이터 암호화 키(KMS 키)를 따로 지정해 관리한다.

먼저 알아야 할 것 10-01

#1문제 상황

애플리케이션이 쓰는 비밀번호와 토큰은 Kubernetes Secret 오브젝트에 담긴다. 이 값은 클러스터의 데이터 저장소 etcd에 평문으로 남는다. 누가 etcd를 읽으면 비밀값이 그대로 나온다. 시크릿 암호화는 이 값을 AWS KMS 키로 암호화해 저장하게 한다. 이때 쓰는 방식이 envelope encryption, 데이터 키로 실제 데이터를 감싸는 구조다.

#2핵심 질문

Kubernetes Secrets의 비밀값을 평문으로 남기지 않고 암호화해 저장하려면 어떻게 해야 할까?

#3동작 예시

운영자가 클러스터에 KMS 키를 지정해 시크릿 암호화를 켠다. 이후 DB 비밀번호를 넣은 Secret을 kubectl로 만든다. kubectl get secret으로 값을 꺼내 보려 하면 암호화된 값만 보인다. 원문은 KMS 키가 있는 계정 권한자가 풀어야 나온다.

#4동작 과정

  1. 키를 고른다대칭 키이고 암호화와 복호화를 모두 하며 클러스터와 같은 리전에 있는 AWS KMS 키를 고른다.
  2. 키를 권한에 건다다른 계정의 키를 쓴다면 해당 IAM 주체가 그 키를 쓸 수 있게 권한을 준다.
  3. 암호화를 적용한다etcd encryption 설정을 켜면 Kubernetes API Data 전체가 기본으로 암호화된다. AWS Secrets Manager의 비밀값도 같은 키로 함께 넣을 수 있다.
  4. 확인해 볼 것etcd에 저장된 Secret 데이터가 암호화된 값으로 보이는지 kubectl로 확인한다.

인증서 서명과 CA 교체

클러스터의 모든 구성요소가 서로를 믿을 수 있게 해 주는 자체 서명 인증 기관(CA)의 인증서를 직접 서명하고, 그 인증서를 주기적으로 교체해 유출 시의 위험을 낮추는 작업이다.

먼저 알아야 할 것 10-01

#1문제 상황

클러스터 안의 구성요소와 클라이언트는 서로를 인증서로만 믿는다. 인증 기관이 그대로 남아 있으면 그 인증서가 한 번 새어 나간 뒤로는 교체 수단이 없다. certificate signing과 CA rotation은 이 신뢰의 출발점을 직접 관리하는 절차다.

#2핵심 질문

클러스터의 인증서 서명을 직접 처리하고 CA를 교체하려면 어떤 자원을 쓰는가?

#3동작 예시

운영자가 클라이언트 인증서를 직접 받아야 해서 CertificateSigningRequest를 만들어 승인 요청을 낸다. 요청이 승인되면 서명된 인증서를 받아 클라이언트에 심고, 이 주기로 CA 인증서를 교체한다.

#4동작 과정

  1. 서명 요청을 만든다CertificateSigningRequest(CSR) 리소스로 X.509 인증서 발급을 요청한다. 서명 주체는 signerName으로 지정한다.
  2. 승인하고 서명한다요청이 승인될 때만 해당 signer가 서명한다. 클러스터 certificate authority가 이 서명 요청을 처리한다.
  3. 교체한다CA rotation으로 클러스터 인증 기관 인증서를 갈아 끼우고, 만료가 가까운 인증서를 서명 요청 없이 직접 재서명한다.
  4. 확인해 볼 것kubectl get csr에서 요청이 Approved 상태로 바뀌었는지 본다.

#5한 줄 요약

RBAC 강화와 기본 역할 정리

Kubernetes 역할 기반 접근 제어(RBAC) 규칙을 좁게 다듬고 기본으로 만들어 둔 역할 중 필요 없는 것을 지워서, 클러스터 관리자의 권한이 지나치게 넓어지지 않게 만드는 작업이다.

먼저 알아야 할 것 08-02

#1문제 상황

add-on을 DaemonSet으로 설치하면 그 서비스 계정은 클러스터의 모든 노드에서 돈다(→ 05-04). 그래서 CSI 드라이버 같은 구성요소가 넓은 권한을 그대로 갖는다. 노드의 침해가 그 권한을 그대로 물려받는다. Kubernetes RBAC 규칙과 기본 역할을 다시 좁혀 권한의 범위를 줄여야 한다.

#2핵심 질문

클러스터 구성요소가 갖는 넓은 RBAC 권한을 어떻게 좁힐 수 있을까?

#3동작 예시

설치된 add-on 목록을 보고 각 DaemonSet의 서비스 계정이 어디까지 접근하는지 확인한다. 필요 없는 동작만 남겨 Role 규칙으로 다시 만든 뒤, 기본으로 만들어 둔 역할 중 아무도 쓰지 않는 것을 지운다.

#4동작 과정

  1. 권한을 훑는다CSI 드라이버와 DaemonSet add-on의 서비스 계정이 갖는 Role·ClusterRole 규칙을 나열한다.
  2. 규칙을 좁힌다least privilege 기준으로 필요한 동작만 남기고, 노드 전역이 아니라 Pod 단위 토큰 범위를 쓴다.
  3. 기본 것을 정리한다쓰지 않는 default roles and users를 지워, kubectl로 확인되는 계정 목록을 줄인다.
  4. 확인해 볼 것kubectl auth can-i로 Pod의 서비스 계정이 실제로 무엇을 할 수 있는지 확인한다.

#1문제 상황

#2핵심 질문

먼저 알아야 할 것 10-01

#1문제 상황

클러스터와 컨테이너 이미지를 직접 관리하면 설정을 누락하거나 오래된 패키지를 그대로 두기 쉽다(→ 10-01). 무엇을 어디까지 점검해야 안전한지는 문서마다 달라 판단하기 어렵다.

취약점 분석은 정해진 기준에 맞춰 설정과 알려진 취약점을 자동으로 검사하는 방법이다. 이때 CIS Kubernetes Benchmark, 즉 EKS 보안 설정을 점검하는 화면 승인 기준이 사용된다. 클러스터가 산업 규제 기준을 맞추는지는 compliance validation으로 확인하고, 보안 분석은 Amazon GuardDuty로, 수집한 데이터의 모음과 분석은 Amazon Security Lake로 이어 갈 수 있다.

#2핵심 질문

클러스터가 안전하게 설정되어 있고 규제 요건을 충족하는지 어떻게 반복해서 확인하는가?

#3동작 예시

운영자가 EKS 문서의 분석 절차를 따라 클러스터와 노드의 설정을 검사한다. 컨트롤 플레인 로그 활성화 여부 같은 항목이 기준에 맞는지 항목별로 표시되고, 이미지로 빌드된 컨테이너에서는 알려진 취약점이 있는 라이브러리 목록이 나온다.

결과를 보고 필요한 항목을 고쳐 적용하고, 다시 같은 검사를 돌려 기준에 맞는지 확인한다.

#4동작 과정

  1. 기준을 고른다CIS Kubernetes Benchmark에서 검사할 항목을 정한다. 이 기준은 고객이 Kubernetes 구성의 보안을 책임지는 EC2 노드(관리형과 직접 관리형을 모두 포함)에 적용된다.
  2. 분석을 돌린다configuration and vulnerability analysis를 실행해 설정과 취약점을 나눠 검사한다. 설정은 기준 항목별 판정으로, 취약점은 이미지에 포함된 라이브러리의 알려진 문제로 확인한다.
  3. 연결해 본다compliance validation으로 규제 기준 충족을 확인하고, Amazon GuardDuty로 EKS의 보안 이벤트를 분석한다. 모아 둔 보안 데이터를 Amazon Security Lake로 모으면 여러 계정 결과를 한곳에서 살필 수 있다.
  4. 확인해 볼 것분석 결과 화면에서 항목별 판정 결과와 컨테이너 이미지의 취약점 목록이 각각 나타나는지 본다.

CloudWatch 와 로그

EKS 컨트롤 플레인과 워크로드가 남기는 로그·지표를 Amazon CloudWatch 로 보내 저장하고 검색·알림하는 방식으로, 감사 기록은 CloudTrail 로 따로 남긴다.

먼저 알아야 할 것 11-01

→ 11-01 참조

#1문제 상황

클러스터에서 무슨 일이 일어나는지 보려면 로그를 어디서부터 찾아야 하는지 매번 정해야 한다(→ 11-01). API 서버가 느려진 원인은 지표로, 누가 무엇을 바꿨는지는 기록으로 따로 봐야 한다.

CloudWatch 로그는 지표와 로그를 한곳에 모으고 알림까지 건다. EKS 기본 지표는 AWS/EKS 네임스페이스에 1분 간격으로 쌓인다.

#2핵심 질문

컨트롤 플레인과 워크로드의 지표와 로그를 어디에 모아 두고 어떻게 찾아 보는가?

#3동작 예시

운영자가 CloudWatch 콘솔의 Logs Explorer에서 control plane logs를 시간대로 좁혀 본다. 컨테이너가 먼저 죽은 로그가 남아 있고, 같은 시간대 지표에서는 API 요청 처리량과 autoscaling group 지표가 함께 확인된다.

누가 클러스터를 바꿨는지는 별도로 AWS CloudTrail 기록에서 찾는다.

#4동작 과정

  1. 지표와 로그를 받는다Amazon CloudWatch가 EKS 기본 지표를 1분 주기로 AWS/EKS 네임스페이스에 내고, control plane logging을 켜 두면 컨트롤 플레인 구성요소의 로그가 CloudWatch Logs로 모여 온다. Logs Explorer에서 시간과 키워드로 좁혀 실패한 요청을 찾는다.
  2. 관측 범위를 넓힌다CloudWatch Observability Operator를 애드온으로 설치하면 확장 관측 기능을 쓸 수 있다. Auto Scaling group 지표와 CloudWatch Container Insights로 컨테이너별 사용량까지 좁혀 본다.
  3. 감사를 나눈다설정과 API 호출의 주체는 AWS CloudTrail 기록으로 따로 남겨 확인한다. CloudWatch Logs의 기록과 역할이 다르다.
  4. 확인해 볼 것Logs Explorer에서 control plane logging이 켜진 EKS 의 로그 그룹 목록과, AWS/EKS 네임스페이스의 1분 주기 지표가 나타나는지 본다.

Prometheus 와 네트워크 관측

컨테이너에서 Prometheus 같은 오픈소스 지표 수집 도구를 붙여 클러스터와 네트워크 흐름을 직접 관측하는 영역으로, AWS 의 관리형 관측 기능과 나란히 쓰인다.

먼저 알아야 할 것 11-01

#1문제 상황

AWS 가 주는 기본 지표만으로는 컨테이너가 내보내는 상세 지표와 Pod 사이의 네트워크 흐름을 볼 수 없다(→ 11-02). 그대로 두고 넘어가면 병목이 있는 구간을 찾지 못한다.

Prometheus 는 특정 주기마다 대상의 주소를 긁어 모아 질의·저장·경보를 제공하는 모니터링 도구다. 이를 컨테이너에 붙여 Prometheus metrics 를 직접 모으고, container network observability 로 네트워크 흐름까지 살핀다.

#2핵심 질문

컨테이너가 내보내는 상세 지표와 Pod 사이 네트워크 흐름을 직접 모아 어떻게 보는가?

#3동작 예시

운영자가 클러스터에 Prometheus 수집기를 두고 컨테이너의 지표 주소를 등록한다. 수집된 지표를 PromQL 질의로 묶어 요청 처리량과 지연을 그래프로 비교하고, 그 지표를 Amazon Managed Service for Prometheus 로 보내 저장과 경보를 맡긴다.

Pod 사이 통신 지표는 container network observability 항목에서 확인한다.

#4동작 과정

  1. Prometheus 를 세운다관리형 옵션인 Amazon Managed Service for Prometheus 와 오픈소스 옵션 중 하나를 고라 설치한다. Prometheus 는 대상 주소를 주기적으로 긁어 질의와 저장, 경보까지 맡는다.
  2. 신호를 긁는다컨테이너가 노출하는 지표 주소에 수집 대상을 등록해 Prometheus metrics 를 모은다. control plane metrics 를 담는 것이 대표적 활용 사례이며, ADOT Operator 가 붙은 컨테이너에서는 OpenTelemetry 형식으로 정리된 신호를 함께 받는다.
  3. 네트워크를 본다container network observability 를 켜면 컨테이너 네트워크 지표가 함께 나온다. Prometheus 계측과 짝지어 병목 구간을 좁힌다.
  4. 확인해 볼 것질의 화면에서 컨테이너 하나가 내보낸 지표 목록이 항목별로 조회되는지 확인한다.

#1문제 상황

클러스터 하나의 비용만 나오면 어느 팀이 얼마를 쓰는지 알 수 없다(→ 11-02). 사용하지 않는 자원을 잘라 낼 대상도 고르기가 어렵다.

cost monitoring은 클러스터 비용을 네임스페이스와 Pod 단위로 나눠 보여 준다. 비용이 어느 지점에서 나왔는지 알 수 있어 자원 사용량과 예산을 근거로 고칠 수 있다.

#2핵심 질문

클러스터 비용을 네임스페이스와 Pod 단위로 나눠 어디에 얼마나 쓰이는지 어떻게 확인하는가?

#3동작 예시

운영자가 AWS Billing 콘솔에서 EKS 비용을 네임스페이스별로 나눠 본다. Pod 단위 목록에서 자원 요청량보다 실제 사용량이 큰 워크로드를 찾고, 크기를 조정하거나 다른 오토스케일링 방법을 고른다(→ 05-03).

내부 도구로 나누고 싶다면 Kubecost 를 클러스터에 설치해 같은 지점별 비용을 본다.

#4동작 과정

  1. 분할한다AWS Billing 의 split cost allocation data for Amazon EKS 를 켠다. 다른 AWS 서비스와 같은 Billing 콘솔 화면에서 Kubernetes 비용을 같이 정리해 볼 수 있다.
  2. 지점별로 본다view costs by Pod 로 내려가 Pod 매의 비용을 확인한다. 네임스페이스와 서비스 단위로 묶어 비교하면 팀 별 지출이 드러난다.
  3. 도구로 나눈다자체 기준이 필요하면 Kubecost 를 클러스터에 설치해 cost allocation 로 자원과 라벨 단위 비용을 따로 보여 준다.
  4. 확인해 볼 것Billing 콘솔에서 네임스페이스별 비용 항목과 Pod 단위 목록이 나타나는지 확인한다.

다른 AWS 서비스와 함께 쓰기

EKS 와 CloudFormation 같은 AWS 서비스를 서로 연결해 인프라를 코드로 관리하고 백업·연동을 구성하는 방법들이다.

먼저 알아야 할 것 11-01

#1문제 상황

클러스터의 백업과 인프라 구성을 직접 관리하면 운영자가 빠졌을 때 그대로 멈춘다(→ 11-01). 보안 이벤트도 다른 화면에서 따로 찾아야 한다.

EKS 는 여러 AWS 서비스와 붙어 동작한다. 각 서비스가 EKS 를 쓰거나, EKS 가 그 서비스를 호출해 추가 기능을 얻는다.

#2핵심 질문

EKS 와 다른 AWS 서비스를 연결해 백업과 구성·보안 업무를 함께 처리하려면 무엇을 쓰는가?

#3동작 예시

운영자가 AWS Backup 으로 클러스터의 볼륨과 상태를 정기 저장하도록 설정한다. 인프라는 AWS CloudFormation 으로 템플릿에서 다시 만들고, 보안 이벤트는 Amazon Detective 로 분석한다.

다른 클러스터와는 Amazon VPC Lattice 로 낮은 지연으로 연결한다.

#4동작 과정

  1. 백업과 구성을 맡긴다AWS Backup 으로 EKS 클러스터를 통째로 정기 저장하고, AWS CloudFormation 템플릿으로 EKS 리소스를 코드로 다시 만든다. 저장된 시점으로 되돌리는 경로도 함께 정한다.
  2. 보안을 연다Amazon Detective 로 EKS 보안 이벤트를 분석하고 Amazon GuardDuty 로 위협을 찾는다. Amazon EKS Connector 로는 클러스터 상태를 다른 도구에서 본다.
  3. 연결을 잇는다Amazon VPC Lattice 로 클러스터 사이의 안전한 저지연 통신을 만들고, AWS Secrets Manager 로 애플리케이션 비밀값을 관리한다.
  4. 확인해 볼 것AWS Backup 콘솔에서 EKS 클러스터가 백업 계획 항목에 포함되어 목록에 보이는지 확인한다.
