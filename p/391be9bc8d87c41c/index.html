1부. Windows Server 개요와 설치001

Windows Server 정의

서버 운영체제가 데스크톱 운영체제와 무엇이 다른지

회사에 컴퓨터가 스무 대쯤 늘어나면, 각자 쓰는 컴퓨터 한 대에 파일을 흩어 두고 일을 하다가 누군가의 컴퓨터가 꺼지는 순간 자료가 통째로 사라지는 일이 생깁니다. 한 사람이 인쇄를 걸어도 다른 사람의 컴퓨터를 거쳐야 하고, 누가 어떤 파일을 열어 두었는지도 알 수 없어서 일이 자주 엉킵니다. Windows Server는 이렇게 여러 사람이 함께 쓰는 일을 한곳에 모아 처리하려고 만든 서버 운영체제(server operating system)입니다. 비유하자면 회사 전체를 위한 아파트 관리실과 같습니다. 각 세대가 자기 집 안에서 살림을 하는 것이 데스크톱 운영체제라면, 관리실은 현관 열쇠를 관리하고 택배를 모아 두고 정전이 났을 때 발전기를 돌리는 일을 대신 맡습니다.

Windows Server도 같은 방식으로 사용자 계정과 권한을 한곳에서 관리하고, 여러 사람이 동시에 접속해도 견디도록 설계된 파일 공유와 인쇄 서비스를 제공합니다. 또한 서버가 스스로 재부팅 없이 오래 돌아가도록 만들어져 있고, 원격에서 여러 서버를 한꺼번에 다루는 관리 도구도 함께 들어 있습니다. 정리하면 Windows Server는 한 사람의 작업을 빠르게 하는 운영체제가 아니라, 여러 사람의 요청을 안정적으로 나눠 받고 관리하는 것을 목적으로 하는 운영체제입니다. 그래서 화면을 예쁘게 꾸미는 기능보다 계정 관리, 파일 공유, 원격 관리 같은 기능이 중심에 놓입니다.

Windows Server 에디션

Standard와 Datacenter 등 에디션 차이와 선택 기준

서버를 사려고 견적을 내면 같은 이름의 제품이 여러 가격으로 나와 있어서 무엇을 골라야 할지 막막해집니다. 싼 것을 골랐다가 나중에 가상 머신을 더 띄우려는 순간 라이선스가 모자라 뒤늦게 돈을 더 쓰는 일도 생깁니다. Windows Server 에디션(edition)은 이런 선택을 미리 정리해 둔 등급표입니다. 비유하자면 택배 회사의 차량 등급과 같습니다. 소형 택배차는 한 동네를 도는 데 충분하지만 물량이 늘면 여러 대를 굴려야 하고, 대형 트럭은 한 번에 많은 짐을 실을 수 있는 대신 값이 비쌉니다.

Standard는 소형차에 해당해 물리 서버 한 대와 그 위의 가상 환경을 제한된 수만큼 다루는 용도이고, Datacenter는 대형 트럭에 해당해 가상 머신을 많이 띄우는 환경을 전제로 합니다. 두 에디션은 기본 기능이 같고 가상화 권한과 일부 대규모 기능에서 갈리므로, 앞으로 늘어날 가상 머신 수를 먼저 가늠한 뒤 고르는 것이 순서입니다. 정리하면 에디션은 성능 등급이 아니라 허용되는 사용 범위를 나눈 표이고, Standard와 Datacenter의 차이는 주로 가상화 권한에서 갈립니다. 실제 등급 구성과 이름은 버전마다 달라질 수 있으므로 도입 시점의 공식 문서를 확인해야 합니다.

Windows Server 라이선싱

코어 기반 라이선스 계산과 가상화 권한

서버를 새로 들여놓고 나서 예산 담당자에게 청구서를 보여 주면, 서버 한 대 값보다 라이선스 항목이 더 크게 찍혀 있어 당황하는 경우가 많습니다. 게다가 가상 머신을 몇 개 띄웠는지에 따라 추가 비용이 발생해서, 계산 근거를 모르면 예산을 세울 수가 없습니다. Windows Server 라이선싱(licensing)은 이 비용을 어떤 단위로 세는지 정한 규칙입니다. 비유하자면 아파트 관리비를 세대 수와 면적으로 나눠 내는 방식과 비슷합니다. 관리비는 사람 수가 아니라 면적이라는 기준으로 매겨지듯, 서버 라이선스는 물리 CPU의 코어(core) 수를 기준으로 계산합니다.

코어가 많은 서버일수록 더 많은 라이선스가 필요하고, 그 라이선스가 허락하는 범위 안에서만 가상 머신을 띄울 수 있습니다. 즉 코어 수를 세어 필요한 라이선스를 산 뒤, 그 라이선스가 보장하는 가상화 권한만큼만 가상 머신을 운영하는 구조입니다. 정리하면 라이선싱은 서버 대수보다 코어 수와 가상화 권한을 중심으로 비용을 매기는 체계이며, 계획 없이 가상 머신을 늘리면 비용이 예상보다 커집니다. 세부 계산 방식과 최소 코어 규정은 버전과 계약 형태에 따라 다르므로 도입 전에 확인이 필요합니다.

1부. Windows Server 개요와 설치004

서버 하드웨어 요구 사항

CPU·메모리·디스크의 최소 사양과 권장 사양

서버를 조립해 놓고 운영체제를 설치했더니 설치가 끝나지 않거나, 겨우 켜 놓았는데 사용자가 몇 명 붙자마자 화면이 멈추는 일이 있습니다. 원인을 찾아보면 대개 메모리가 부족하거나 디스크 자리가 모자란, 아주 기초적인 부분이었습니다. 서버 하드웨어 요구 사항(hardware requirements)은 이런 실패를 설치 전에 걸러 내기 위해 최소선과 권장선을 정해 둔 기준입니다. 비유하자면 이사를 갈 때 짐의 양과 방의 크기를 먼저 맞춰 보는 것과 같습니다. 최소 사양은 짐을 겨우 밀어 넣을 수 있는 방의 크기이고, 권장 사양은 사람이 지나다닐 공간까지 남겨 두는 크기입니다.

CPU는 동시에 접속하는 사용자를 받아 내는 힘, 메모리는 한 번에 펼쳐 놓고 일하는 책상의 넓이, 디스크는 짐을 쌓아 둘 창고에 해당합니다. 최소 사양은 설치와 시험 가동이 가능한 선일 뿐이고, 실제 운영에서는 사용자 수와 서비스 종류를 감안해 권장 사양 이상으로 잡는 것이 안전합니다. 정리하면 하드웨어 요구 사항은 CPU, 메모리, 디스크의 최소선과 권장선을 제시해 설치 실패와 초기 성능 부족을 막는 기준입니다. 정확한 수치는 버전과 설치 옵션에 따라 다르므로 설치하려는 버전의 공식 문서를 기준으로 삼아야 합니다.

설치 매체 만들기

ISO와 부팅 USB로 설치 매체를 준비하는 방법

서버를 처음 세팅하는 날, 정품 이미지를 내려받아 두었다고 생각했는데 USB가 인식되지 않거나 부팅 중에 멈춰서 몇 시간을 허비하는 일이 흔합니다. 파일을 그냥 복사해 넣은 USB는 부팅용으로 만들어지지 않았기 때문에 서버가 그 안의 설치 프로그램을 찾지 못합니다. 설치 매체(installation media)는 서버가 스스로 부팅해 설치를 시작할 수 있도록 준비한 ISO 이미지나 부팅 USB를 말합니다. 비유하자면 이사할 집에 미리 넣어 두는 안내 표지판과 같습니다. ISO는 설치 파일 전체를 한 덩어리로 담은 이미지 파일이고, 부팅 USB는 그 이미지를 USB에 풀어 넣어 서버가 켜질 때 가장 먼저 읽는 표지판 역할을 하게 만든 것입니다.

서버의 부팅 순서를 USB나 광학 매체로 바꿔 두면 서버가 하드디스크 대신 그 매체를 먼저 읽고 설치 화면을 띄웁니다. 매체를 만들 때는 이미지를 그대로 기록하는 도구를 써야 하며, 파일만 끌어다 놓는 방식으로는 부팅이 되지 않습니다. 정리하면 설치 매체는 ISO 이미지를 부팅 가능한 형태로 준비한 것으로, 서버가 설치 프로그램을 스스로 찾아 실행하게 만드는 출발점입니다. 매체 제작 도구와 펌웨어 설정 방식은 환경마다 다르므로 사용하는 서버의 설명서를 함께 확인해야 합니다.

Server Core와 데스크톱 경험

두 설치 옵션의 차이와 선택 기준

서버를 설치할 때 화면이 그림과 창으로 가득한 설치 옵션을 고르면 익숙해서 편하지만, 그 화면을 유지하는 데 드는 자원과 보안 부담이 계속 따라붙습니다. 반대로 검은 명령 창만 있는 옵션을 고르면 다루기 어렵다는 이유로 망설이게 됩니다. Server Core와 데스크톱 경험(Desktop Experience)은 이 둘 중 무엇을 설치할지 정하는 선택지입니다. 비유하자면 사무실을 꾸미는 방식의 차이입니다. 데스크톱 경험은 책상과 의자, 안내 데스크까지 갖춘 사무실이라 누구나 들어와 바로 일할 수 있지만 그만큼 공간과 관리가 필요합니다. Server Core는 필요한 장비만 놓은 작업실이라 처음에는 낯설지만, 창을 그리는 구성 요소가 빠져 있어 자원을 적게 쓰고 공격받을 표면도 좁습니다.

두 옵션은 같은 운영체제의 다른 설치 형태이며, 관리 방식도 화면 조작과 원격 관리 도구로 갈립니다. 그래서 서버를 직접 만질 일이 많은지, 원격에서 자동화로 관리할 것인지가 선택의 기준이 됩니다. 정리하면 Server Core와 데스크톱 경험은 기능을 더하거나 덜어 자원 사용과 보안 노출, 관리 편의를 맞바꾸는 두 가지 설치 형태입니다. 어떤 옵션이 제공되는지와 전환 가능 여부는 버전에 따라 다르므로 설치 전에 확인해야 합니다.

초기 설정과 컴퓨터 이름

설치 직후 이름과 네트워크 주소를 잡는 절차

서버를 막 설치하고 전원을 켜면 이름이 WIN-8K3LQ2처럼 무작위로 붙어 있고 네트워크 주소도 공유기에서 자동으로 받아 오는 상태라, 며칠 뒤 재부팅 한 번에 주소가 달라져 원격 접속과 파일 공유가 한꺼번에 끊기는 일이 생깁니다. 이런 곤란을 없애려고 설치 직후에 서버의 이름과 네트워크 주소를 사람이 직접 정해 두는 절차를 거치는데, 이것이 초기 설정입니다.

이사 간 새 집에 들어가면 먼저 현관에 명패를 달고 택배가 찾아올 수 있도록 도로명 주소를 확정하는 일부터 하는 것과 같습니다. 컴퓨터 이름(hostname)은 현관 명패에 해당해서 서버를 부르는 유일한 이름이 되고 같은 네트워크 안에서 중복되면 안 됩니다. IP 주소는 도로명 주소처럼 서버가 네트워크에서 차지하는 위치를 정하는 값이며, 자동으로 받는 대신 고정 IP(static IP)로 지정해 두면 재부팅을 해도 바뀌지 않습니다. 서브넷 마스크(subnet mask)와 기본 게이트웨이(default gateway)는 각각 우리 동네의 범위와 동네를 빠져나가는 큰길 입구를 가리키고, DNS 서버는 상대의 이름을 주소로 바꿔 주는 전화번호부 역할을 합니다.

이름을 바꾼 뒤에는 보통 재부팅이 필요하고, 주소를 손으로 넣을 때는 같은 주소를 쓰는 장치가 없는지 먼저 확인해야 합니다. 결국 초기 설정은 호스트 이름과 고정 IP 주소, 서브넷 마스크, 기본 게이트웨이, DNS 서버를 정해 서버가 항상 같은 이름과 같은 주소로 불리도록 만드는 작업입니다.

서버 관리자(Server Manager)

역할과 기능을 설치하고 관리하는 기본 콘솔

서버를 한 대 세우고 나면 웹 사이트를 띄우고 파일 공유를 열고 백업 도구를 붙이는 등 할 일이 줄줄이 남는데, 설치 화면과 설정 창을 저마다 다른 곳에서 찾아 헤매다 보면 무엇을 이미 켰고 무엇이 빠졌는지 기억하기 어렵습니다. 그래서 마이크로소프트는 설치 직후 기본으로 뜨는 서버 관리자(Server Manager)라는 한 화면에서 역할과 기능을 설치하고 상태를 관리하도록 만들었습니다.

이 도구는 건물 하나를 맡은 관리사무소와 같아서, 입주자에게 실제 서비스를 제공하는 부서가 역할(role)이고 그 부서가 일을 하려고 갖추는 장비와 도구가 기능(feature)입니다. 예를 들어 웹 서버(IIS)라는 부서를 들이면 그 부서가 쓰는 압축 모듈이나 인증 모듈이 기능으로 함께 딸려 오고, 관리사무소는 어느 부서가 언제 문을 열었는지 대시보드에 적어 둡니다.

여러 서버를 한꺼번에 다룰 때는 서버를 그룹으로 묶어 두고 한 번의 지시로 같은 역할을 설치할 수 있습니다. 다만 역할을 추가하면 재부팅이 필요할 수 있고, 서비스가 이미 돌고 있는 서버에서는 다른 프로그램과 충돌하지 않는지 확인해야 합니다. 결국 서버 관리자는 역할과 기능이라는 두 층으로 설치 단위를 나누고, 설치 상태와 이벤트를 한 콘솔에서 보여 주는 기본 관리 도구입니다.

Windows Admin Center

브라우저 기반 서버 관리 도구의 설치와 용도

서버를 관리하려면 서버 앞에 앉거나 서버마다 원격 접속 도구를 따로 설치해야 했고, 담당자가 여러 명이면 누가 어떤 설정을 바꿨는지도 뒤섞였습니다. Windows Admin Center는 이런 불편을 줄이려고 브라우저 창 하나로 여러 서버를 관리하도록 만든 도구입니다.

이 도구는 관리사무소 책상 위에 놓인 통합 모니터와 같습니다. 각 세대에 해당하는 서버에는 게이트웨이(gateway)라는 중계 프로그램이 설치되어 브라우저의 요청을 서버로 전달하고, 관리자는 주소와 인증서만으로 그 화면에 접속합니다. 화면에는 성능, 저장소, 네트워크, 역할 설치 같은 메뉴가 패널로 나뉘어 있어 서버 한 대를 고르면 그 서버의 상태가 그 자리에 표시됩니다.

기능을 더하려면 확장(extension)을 붙이는 방식이라 필요한 것만 골라 쓸 수 있습니다. 일반적으로 443 포트에 인증서를 붙여 HTTPS로 접속하는 구성이 권장되고, 도메인 환경이 아니어도 사용할 수 있습니다. 결국 Windows Admin Center는 게이트웨이를 통해 브라우저에서 서버의 상태와 설정을 다루는 웹 기반 관리 도구입니다.

원격 관리 기초

WinRM과 원격 데스크톱으로 서버에 접속하는 방법

서버는 보통 데이터센터나 잠긴 전산실에 있어서, 설정 하나를 바꾸려 해도 매번 그 앞까지 걸어가야 한다면 작은 일도 하루해가 됩니다. 이때 멀리서 서버를 다루는 길이 원격 관리이고, 명령을 보내는 WinRM(Windows Remote Management)과 화면을 그대로 보는 원격 데스크톱(Remote Desktop, RDP)이 그 중심입니다.

두 방법은 집에 직접 찾아가지 않고 일을 처리하는 방식에 비유할 수 있습니다. WinRM은 전화로 심부름을 시키는 것과 같아서 정해진 형식의 명령을 보내면 서버가 결과만 돌려주고, 원격 데스크톱은 영상통화로 상대방 방 안을 보면서 직접 손을 쓰는 것과 같습니다. WinRM은 5985(암호화하지 않은 HTTP)와 5986(HTTPS) 포트를 쓰고 RDP는 3389 포트를 쓰므로 방화벽에서 해당 포트가 열려 있어야 하며, 접속하는 계정에는 그 서버를 관리할 권한이 있어야 합니다.

인터넷에 그대로 노출하면 무차별 대입 공격의 표적이 되므로 사설망이나 VPN 안에서만 열어 두는 구성이 안전합니다. 결국 원격 관리는 WinRM으로 명령을 전달하고 RDP로 화면을 공유해, 서버가 있는 곳까지 가지 않고도 설정과 점검을 끝내는 방법입니다.

PowerShell이란

명령과 스크립트로 서버를 다루는 셸

서버 한 대에 같은 설정을 손으로 열 번 반복하다 보면 순서를 하나 건너뛰거나 값을 다르게 넣는 실수가 반드시 생기고, 그 실수는 새벽에 장애로 돌아옵니다. PowerShell은 이런 반복 작업을 명령과 스크립트로 적어 두고 그대로 다시 실행하도록 만든 셸(shell)입니다.

이 셸은 일을 대신해 주는 로봇 조수와 같습니다. 사람이 서비스 목록을 가져오라는 식으로 동사와 명사로 된 한 줄의 명령을 주면 로봇이 그 동작을 수행하고, 같은 명령을 파일에 적어 두면 밤에도 정해진 순서대로 반복합니다. 로봇이 가진 개별 동작을 cmdlet이라 부르고, 결과는 글자 덩어리가 아니라 이름과 상태 같은 항목을 가진 개체(object)로 돌려주기 때문에 다음 동작이 그 항목을 그대로 받아 쓸 수 있습니다.

Windows에 기본으로 들어 있고, 서버 관리자에서 마우스로 하던 일의 상당 부분을 같은 명령으로 처리할 수 있습니다. 다만 실행 정책(execution policy)이나 권한 설정에 따라 스크립트가 막힐 수 있어 처음에는 현재 상태를 확인하고 진행해야 합니다. 결국 PowerShell은 cmdlet이라는 명령을 조합해 서버 작업을 다시 실행할 수 있는 스크립트로 바꾸는 자동화 셸입니다.

cmdlet과 파이프라인

명령을 이어 붙여 데이터를 처리하는 방식

명령 하나로 원하는 결과를 얻기 어려울 때마다 사람이 중간 결과를 복사해 다른 프로그램에 붙여 넣는다면, 그 사이에 값이 틀어지고 작업은 금세 끊깁니다. cmdlet과 파이프라인은 이 중간 단계를 사람 손에서 떼어 내기 위해 만든 방식입니다.

공장 컨베이어 벨트를 떠올리면 됩니다. Get-Service처럼 목록을 만들어 내는 cmdlet이 벨트의 첫 공정이고, Where-Object는 조건에 맞는 것만 남기는 검사대, Sort-Object는 순서를 정리하는 마무리 공정입니다. 각 공정은 완성품을 통째로 넘기지 않고 개체(object) 단위로 하나씩 흘려보내며, 세로 막대(|) 하나가 그 벨트를 이어 줍니다. 그래서 중간에 파일로 저장하거나 화면에서 값을 다시 옮겨 적을 필요가 없습니다.

cmdlet 이름은 Get-Service, Stop-Service처럼 동사-명사(Verb-Noun) 규칙을 따라 어떤 일을 하는지 이름만 보고 짐작할 수 있습니다. 결국 cmdlet은 한 가지 일을 하는 작은 명령이고, 파이프라인은 그 명령들을 이어 붙여 데이터를 단계별로 가공하는 연결 방식입니다.

PowerShell 도움말 활용

Get-Help로 사용법을 스스로 찾는 방법

명령 이름은 겨우 기억해 냈는데 어떤 값을 어떤 순서로 붙여야 하는지 몰라 화면 앞에서 멈춰 서 본 적이 있을 것입니다. 인터넷 검색조차 막힌 폐쇄된 서버라면 막막함은 더 커지는데, PowerShell은 이런 상황을 위해 명령을 실행하는 도구 안에 설명서를 함께 넣어 두었고 그것을 여는 명령이 Get-Help입니다.

이것은 백화점 안내데스크와 같습니다. 매장이 수백 개인 건물에서 손님이 안내데스크에 가면 원하는 매장의 위치와 이용 방법을 바로 알려 주듯이, Get-Help 뒤에 궁금한 명령 이름을 붙이면 그 명령이 무엇을 하는지와 어떤 값을 받는지를 그 자리에서 보여 줍니다.

뒤에 -Examples를 붙이면 실제로 그 명령을 사용한 사례만 골라 보여 주어 따라 하기 쉬워지고, -Full을 붙이면 매뉴얼 전체를 펼쳐 보듯 모든 항목을 자세히 보여 줍니다. 안내 책자가 낡았다면 Update-Help로 최신판으로 바꿔 둘 수 있는데, 이때는 인터넷 연결이 필요합니다.

정리하면 Get-Help는 PowerShell에 내장된 도움말 조회 명령으로, 명령의 용도와 매개변수, 사용 예를 화면에서 바로 확인하게 해 줍니다. 즉 외부 자료 없이도 스스로 사용법을 찾아낼 수 있게 하는 첫 번째 습관입니다.

개체와 속성

PowerShell이 출력하는 개체의 구조를 읽는 법

명령을 실행했더니 결과가 표처럼 보이는데 화면 폭에 잘려 일부만 보이고, 그중 값 하나만 다른 프로그램에 넘기려 해도 방법을 찾기 어렵습니다. PowerShell은 결과를 글자가 아닌 개체(object)로 내보내기 때문에 이 문제를 다른 방식으로 풉니다.

이것은 택배 상자에 붙은 송장과 같습니다. 상자 하나가 개체 하나이고, 송장의 칸칸이 이름과 주소와 무게처럼 각각의 속성(property)인데, 화면에 보이는 표는 송장의 일부 칸만 인쇄한 것에 불과합니다.

Get-Member를 붙이면 그 상자에 어떤 칸이 있는지 송장 전체를 확인하듯 속성과 동작의 목록을 보여 주고, Select-Object로 원하는 칸만 골라 새 표를 만들 수 있습니다. 파이프(|)는 상자를 다음 담당자에게 그대로 넘기는 일이라, 중간에 글자로 바뀌지 않아 정보가 손실되지 않습니다.

정리하면 PowerShell의 출력은 속성과 동작을 가진 개체이며, Get-Member와 Select-Object로 그 구조를 읽고 필요한 값만 꺼내 쓰는 것이 핵심입니다.

이것은 아파트 단지의 관리 방송과 같습니다. 관리사무소에서 방송 설비를 켜고 전달할 내용을 말하면 지정한 동의 세대에 한 번에 같은 안내가 퍼지고, 각 세대가 처리한 결과가 다시 사무실로 모여 오는 구조인데, Invoke-Command가 방송이고 -ComputerName이 방송할 동의 목록, -ScriptBlock이 방송 내용입니다. 방송이 닿으려면 각 동에 스피커가 설치되어 있어야 하듯이, 대상 서버에서는 WinRM(Windows Remote Management)이라는 원격 관리 서비스가 켜져 있어야 합니다.

결과는 서버마다 따로 묶여 돌아오므로 어느 서버가 성공하고 어느 서버가 실패했는지 구분해 볼 수 있습니다. 한 대만 상대할 때는 Enter-PSSession으로 그 서버의 콘솔에 들어간 것처럼 작업할 수도 있습니다.

정리하면 Invoke-Command는 WinRM을 통해 여러 원격 컴퓨터에 같은 스크립트 블록을 실행시키고 컴퓨터별 결과를 모아 주는 명령입니다.

이것은 요리 레시피 카드와 같습니다. 재료를 미리 그릇에 담아 두면 조리 중에 꺼내 쓰기만 하면 되는데, 값을 담아 두는 변수(variable)가 그 그릇이고 $name처럼 달러 표시로 시작하는 이름을 붙입니다.

조건문(if)은 '간이 싱거우면 소금을 더한다'처럼 상황에 따라 다른 동작을 고르는 단계이고, 반복문(foreach, while)은 '접시 열 개에 하나씩 담기'처럼 같은 동작을 여러 번 되풀이하는 단계입니다. 이 단계들을 위에서 아래로 적어 둔 파일이 .ps1 확장자를 가진 스크립트이고, 실행 정책(Execution Policy) 설정에 따라 실행이 막혀 있을 수 있다는 점은 환경마다 다르므로 미리 확인해야 합니다.

정리하면 스크립트는 변수에 값을 담고 조건문과 반복문으로 흐름을 정해 여러 명령을 한 번에 실행하는 파일이며, 손으로 반복하던 작업을 재현 가능한 형태로 굳혀 두는 수단입니다.

PowerShell 모듈

기능 묶음을 가져와 명령을 확장하는 방법

필요한 기능이 PowerShell에 기본으로 들어 있지 않아 매번 긴 코드를 새로 짜거나, 다른 사람이 만든 명령을 쓰려면 그 코드를 어디선가 복사해 와야 한다면 작업이 계속 같은 자리에서 맴돕니다. 모듈(module)은 관련된 명령과 함수를 한 묶음으로 포장해 두었다가 필요할 때 불러 쓰는 단위입니다.

이것은 가구를 조립할 때 쓰는 공구함과 같습니다. 기본 공구만으로 대부분 조립할 수 있지만 나사 종류가 달라지면 드릴 세트를 따로 꺼내야 하는데, 그 세트가 모듈이고 Import-Module로 공구함을 열어 작업대에 올려놓는 셈입니다.

Get-Module은 지금 작업대에 있는 공구함 목록을 보여 주고, Find-Module이나 Install-Module은 아직 없는 세트를 창고에서 가져오는 일에 해당하며 이때는 인터넷 저장소인 PowerShell Gallery를 사용합니다. 최근 버전은 명령을 실행할 때 그 명령이 든 모듈을 알아서 찾아 불러오는 자동 로딩도 지원하므로, 설치만 되어 있다면 매번 Import-Module을 치지 않아도 됩니다.

정리하면 모듈은 명령과 함수를 하나로 묶어 배포하고 불러오는 단위이며, 필요한 기능을 설치하고 가져와 기본 명령 집합을 넓혀 쓰는 것이 모듈 활용의 핵심입니다.

작업 스케줄러(Task Scheduler)

스크립트와 프로그램을 정해진 시간에 실행하기

매일 새벽에 서버 백업을 돌려야 하는데 담당자가 휴가를 가거나 깜빡 잊으면, 정작 필요한 순간에 되살릴 자료가 없어 곤란해집니다. 이런 일을 사람의 기억에 맡기는 방식을 없애려고 만든 것이 Windows Server의 작업 스케줄러(Task Scheduler)이며, 스크립트와 프로그램을 정해진 시각이나 사건에 맞춰 자동으로 실행해 주는 도구입니다.

아파트 관리사무소의 자동 안내 방송을 떠올려 보면 구조가 그대로 겹칩니다. 매일 오전 일곱 시라는 시각이 되면 방송 장비가 켜져서 정해진 안내 문구를 내보내는데, 여기서 '언제'를 정하는 조건을 트리거(trigger), '무엇을' 할지를 정하는 대상을 동작(action)이라 하고, 이 둘을 묶어 이름을 붙여 둔 예약 한 건이 태스크(task)입니다. 방송 장비를 켤 수 있는 사람이 정해져 있듯 각 태스크에는 실행 계정이 지정되고, 공사 중에는 방송을 하지 말라는 공지처럼 특정 조건에서는 실행하지 말라는 제한도 함께 붙일 수 있습니다.

관리사무소가 방송 목록을 한 장에 적어 두고 매일 같은 방식으로 돌리듯, 스케줄러는 등록된 태스크 목록을 읽어 조건이 맞는 것만 실행하고 결과를 기록으로 남깁니다.

정리하면 작업 스케줄러는 트리거로 실행 시점을, 동작으로 실행할 프로그램이나 스크립트를, 실행 계정으로 그 일을 할 권한을 정해 두는 예약 실행 도구입니다. 사람이 자리에 없어도 같은 일이 같은 시각에 반복되도록 만드는 것이 이 기술의 핵심입니다.

원하는 상태 구성(DSC)

설정을 선언하면 시스템이 맞춰 가는 관리 방식

서버 열 대의 설정을 손으로 하나씩 맞추다 보면, 한 대만 빠뜨리거나 누군가 나중에 슬그머니 바꿔 놓아서 같은 역할의 서버인데도 동작이 달라지는 일이 생깁니다. 이렇게 '지금 어떻게 되어 있는가'를 사람이 계속 확인하는 대신 '어떻게 되어 있어야 하는가'만 적어 두면 시스템이 스스로 그 상태로 맞춰 가게 만든 것이 원하는 상태 구성(Desired State Configuration, DSC)입니다.

아파트 관리사무소 게시판에 층별 청소 기준표를 붙여 두는 상황과 같습니다. 기준표에는 '복도에는 먼지가 없어야 하고 소화기는 지정된 자리에 있어야 한다'처럼 결과만 적혀 있고, 그 일을 실제로 하는 것은 청소 용역과 설비 업체이며, 이렇게 한 가지 항목을 처리하는 담당자를 리소스(resource)라 부릅니다. 기준표 자체가 구성(configuration) 문서이고, 적용 대상이 되는 각 세대나 층이 노드(node)이며, 기준표와 현장을 대조해 어긋난 부분을 다시 손보게 하는 관리반장 역할이 로컬 구성 관리자(Local Configuration Manager, LCM)입니다.

그래서 누군가 소화기를 옮겨 놓으면 반장이 다음 점검 때 기준표대로 되돌려 놓고, 이미 기준에 맞는 항목은 건드리지 않습니다.

결국 DSC는 구성 문서에 원하는 상태를 선언하고, 각 노드의 로컬 구성 관리자가 리소스를 통해 그 상태와 실제 상태의 차이를 없애는 관리 방식입니다. 명령을 순서대로 내리는 대신 도달해야 할 상태를 적어 둔다는 점이 이 기술의 핵심입니다.

로컬 계정과 그룹

단일 서버에서 사용자를 만들고 권한을 주는 방법

서버 한 대를 개발자 셋과 운영자 둘이 함께 쓰는데 사람마다 따로 계정을 만들지 않으면, 누가 무엇을 했는지 알 수도 없고 한 사람이 나가면 비밀번호를 전부 바꿔야 하는 번거로움이 생깁니다. 이 문제를 서버 한 대 안에서 해결하는 기본 단위가 로컬 계정(Local Account)과 로컬 그룹(Local Group)이며, 계정은 사람 한 명의 신분을, 그룹은 그 사람들을 묶는 권한 단위를 뜻합니다.

회사 건물의 출입증과 부서 체계를 떠올리면 이해가 쉽습니다. 직원마다 이름이 적힌 개인 출입증이 하나씩 있고 이 출입증이 로컬 계정에 해당하며, 출입증을 만들 때는 아이디와 비밀번호가 함께 발급됩니다. 권한은 개인 출입증에 하나하나 붙이지 않고 '개발팀' '운영팀' 같은 부서에 문을 열어 두는데, 이 부서가 로컬 그룹이고 사람이 부서를 옮기면 출입증을 새로 만들지 않고 소속만 바꿔 주면 됩니다.

새로 들어온 사람도 해당 부서에 넣기만 하면 그 부서가 쓰던 문이 그대로 열리고, 나간 사람은 출입증을 회수하듯 계정을 사용하지 못하게 막으면 됩니다.

정리하면 로컬 계정은 그 서버에서만 통하는 개인 신분이고, 로컬 그룹은 그 계정들을 묶어 권한을 한 번에 주고 회수하는 도구입니다. 사람 수가 늘어날수록 개별 계정보다 그룹 단위로 관리하는 편이 안전하고 빠릅니다.

사용자 계정 제어(UAC)

관리자 권한 상승이 필요한 이유와 동작 방식

관리자로 로그인해 놓고 인터넷을 둘러보다가 평소처럼 프로그램 하나를 설치했는데, 그 프로그램이 몰래 시스템 파일까지 바꿔 놓아 서버가 이상해지는 일이 실제로 있었습니다. 그래서 관리자 권한을 늘 쥐고 있지 말고 정말 필요한 순간에만 잠깐 빌려 쓰게 만든 장치가 사용자 계정 제어(User Account Control, UAC)입니다.

회사 금고를 다루는 절차와 같습니다. 평소 직원은 자기 책상과 회의실 열쇠만 가지고 다니는데 이것이 표준 사용자 권한이고, 금고에서 돈을 꺼내야 할 때만 팀장의 서명을 받은 결재서를 들고 가는 것이 관리자 권한 상승입니다. 관리자 계정으로 로그인해 있어도 실제로는 표준 권한으로 일하다가, 시스템 설정을 바꾸는 작업을 요청하는 순간 화면이 어두워지며 '허용하시겠습니까'를 묻는 동의 창이 뜨고, 여기서 승인해야만 관리자 권한이 담긴 토큰(token)이 함께 발급됩니다.

결재서 없이 금고 문을 열 수 없듯 승인 없이는 그 작업이 진행되지 않으므로, 사용자가 지금 무슨 일이 벌어지는지 한 번은 인지하게 됩니다.

정리하면 UAC는 관리자 권한을 상시로 주지 않고 작업 단위로 승인을 받아 잠깐만 부여하는 안전장치입니다. 권한 상승이 필요한 이유는 그만큼 잘못됐을 때 시스템 전체가 다치기 때문입니다.

3부. 계정과 인증 기반023

액세스 제어 목록(ACL)

파일과 개체에 누가 무엇을 할 수 있는지 지정하기

같은 부서 사람끼리 쓰는 공유 폴더가 있는데, 누구는 읽기만 되어야 하고 누구는 파일을 고칠 수 있어야 하는데도 아무에게나 같은 권한이 주어지면 중요한 자료가 실수로 지워집니다. 파일과 폴더, 프린터 같은 개체마다 누가 어떤 행위를 할 수 있는지 적어 두는 명단이 액세스 제어 목록(Access Control List, ACL)입니다.

아파트 공용 창고 대여 명단을 떠올려 보면 구조가 같습니다. 명단에는 '101호는 캠핑 장비를 빌릴 수 있다', '관리사무소는 모든 물건을 반출할 수 있다'처럼 한 줄씩 적혀 있는데, 이 한 줄 하나를 액세스 제어 항목(Access Control Entry, ACE)이라 합니다. 각 줄에는 대상이 되는 사용자나 그룹, 허용인지 거부인지, 그리고 읽기·쓰기·삭제처럼 어디까지 허용하는지가 함께 적히고, 창고 전체에 적용되는 규칙이 하위 칸에도 자동으로 따라 내려가는 상속(inheritance)이라는 방식도 있습니다.

여러 줄이 동시에 걸릴 때는 거부가 허용보다 먼저 적용되므로, 큰 그룹에 허용을 열어 두었더라도 특정인에게 거부를 적어 두면 그 사람은 들어갈 수 없습니다.

정리하면 ACL은 개체마다 붙는 허용과 거부 항목의 목록이고, 각 항목이 누구에게 무엇을 허락하는지를 한 줄씩 담고 있습니다. 권한을 사람이 아니라 개체 쪽에 적어 둔다는 점이 이 방식의 핵심입니다.

인증과 인가

로그인과 권한 부여가 어떻게 다른지

건물에 들어오려는 사람에게 이름만 물어보고 곧바로 서버 관리 화면까지 열어 주면, 그 사람이 누구인지도 확인하지 못한 채 가장 중요한 문을 내준 셈이 됩니다. 이때 필요한 두 단계가 서로 다른 일이라는 점을 구분한 것이 인증(Authentication)과 인가(Authorization)입니다.

회사 로비의 절차를 떠올려 보면 둘의 차이가 분명해집니다. 로비에서 사원증과 비밀번호로 본인이 맞는지 확인하는 단계가 인증이고, 확인이 끝난 뒤에야 '이 사람은 개발팀이니 서버실은 되고 회계팀 자료실은 안 된다'를 판단해 출입문을 열어 주는 단계가 인가입니다. 사원증이 있어도 모든 문이 열리지 않고 부서별 출입 카드에 적힌 범위만 열리듯, 인증은 신분을 확인하는 일이고 인가는 그 신분에 어떤 권한이 있는지 정하는 일입니다.

그래서 비밀번호를 바꾸는 일은 인증 쪽 문제이고 파일을 못 열게 하는 일은 인가 쪽 문제이며, 두 단계 중 하나만 허술해도 보안은 뚫립니다.

정리하면 인증은 '당신이 누구인지'를 확인하는 절차이고, 인가는 '당신이 무엇을 할 수 있는지'를 정하는 절차입니다. 로그인이 되었다고 해서 모든 권한이 생기는 것은 아니라는 점이 이 구분의 핵심입니다.

NTLM과 Kerberos

윈도우가 쓰는 두 인증 방식의 차이

회사에서 파일 서버에 접속했는데, 누구에게는 아무 문제 없이 열리던 폴더가 다른 사람 앞에서는 계속 암호를 다시 묻는 상황이 벌어질 수 있습니다. 이 곤란을 없애려고 윈도우는 사용자가 한 번 로그인하면 그 자격 증명으로 서버마다 믿음을 확인하는 인증 방식을 마련했고, 그 중심에 NTLM(윈도우의 오래된 인증 방식)과 Kerberos(티켓을 발급해 신원을 확인하는 인증 방식)가 나란히 있습니다.

아파트 단지로 비유하면, NTLM은 방문객이 집집마다 초인종을 누르고 집주인과 직접 얼굴을 확인하는 방식과 같습니다. 집주인은 문 앞의 사람이 맞는지만 확인하면 되지만, 같은 사람이 열 집을 돌면 열 번 확인해야 하고 그 확인 기록도 집집마다 흩어집니다.

Kerberos는 단지 관리실에서 출입증을 한 장 발급받는 방식이라, 관리실이 신원을 한 번 확인해 두면 각 동의 경비원은 출입증의 유효성만 보면 됩니다. 즉 NTLM은 서버마다 사용자 정보를 주고받는 도전-응답 방식이고, Kerberos는 중앙의 키 배포 센터(도메인 컨트롤러)가 티켓을 발급해 서버가 그 티켓만 검사하는 방식입니다.

정리하면 NTLM은 서버와 클라이언트가 매번 직접 확인하는 구식 인증이고, Kerberos는 도메인 환경에서 티켓 한 장으로 인증을 끝내는 방식이며, 그래서 요즘 도메인 환경은 Kerberos를 우선 쓰고 NTLM은 호환용으로 남겨 둡니다.

서비스 계정과 자격 증명

서버가 쓰는 계정을 안전하게 보관하고 관리하기

백업 프로그램이 새벽마다 서버에 접속해 파일을 복사하는데, 그 프로그램에 사람의 계정을 써 두면 그 직원이 퇴사하는 순간 백업이 조용히 멈춥니다. 그래서 서버가 스스로 쓰는 전용 계정을 따로 만들고 그 비밀번호를 안전하게 보관하는 관리 방식이 필요해졌고, 이것이 서비스 계정(사람이 아닌 프로그램이 쓰는 계정)과 자격 증명(접속에 필요한 아이디·비밀번호 같은 신원 정보)이라는 개념입니다.

아파트 경비실 열쇠 꾸러미에 비유하면, 직원마다 들고 다니는 개인 열쇠와 달리 경비실에는 청소·점검 업체가 쓰는 공용 열쇠가 따로 걸려 있습니다. 공용 열쇠는 누가 언제 썼는지 기록을 남기고, 업체가 바뀌면 열쇠만 새로 만들어 걸면 되며, 열쇠 꾸러미는 아무나 꺼내지 못하게 잠긴 캐비닛에 넣어 둡니다.

서비스 계정도 같은 원리로 프로그램마다 하나씩 만들고, 권한은 그 프로그램이 하는 일에 필요한 최소한만 주며, 비밀번호는 사람이 외우지 않고 관리 도구가 주기적으로 바꿔 줍니다. 윈도우에서는 이런 교체를 대신 처리해 주는 관리형 서비스 계정이라는 기능도 있습니다.

결국 서비스 계정은 프로그램 전용 신원이고 자격 증명은 그 신원을 증명하는 열쇠이며, 둘을 사람 계정과 분리해 두고 최소 권한과 주기적 교체로 관리하는 것이 핵심입니다.

계정 보호를 위한 정책 설계

직원 한 명의 비밀번호가 유출되면 공격자는 그 계정으로 밤새 수천 번 로그인을 시도할 수 있고, 반대로 잠금 장치를 너무 예민하게 걸면 출장 중인 직원이 업무를 못 하게 됩니다. 이 두 위험 사이의 균형을 정해 두는 것이 암호 정책(비밀번호의 길이와 복잡도·변경 주기를 정하는 규칙)과 계정 잠금 정책(로그인 실패가 반복될 때 계정을 일정 시간 막는 규칙)입니다.

현관 도어락에 비유할 수 있습니다. 비밀번호를 네 자리에서 여섯 자리로 늘리고 쉬운 숫자를 피하게 하면 짐작으로 열릴 확률이 크게 줄고, 다섯 번 틀리면 1분 동안 입력을 막는 기능은 무작정 눌러 보는 시도를 끊어 줍니다.

다만 잠금 시간을 너무 길게 잡으면 손님이 문 앞에서 발만 동동 구르게 되므로, 실패 허용 횟수와 잠금 시간은 조직의 상황에 맞게 조정해야 합니다. 윈도우에서는 이런 규칙을 도메인 단위 정책으로 정해 모든 계정에 같은 기준을 적용합니다.

결국 암호 정책은 추측하기 어려운 비밀번호를 유지하게 하고 계정 잠금 정책은 반복 시도를 차단하며, 두 정책을 함께 설계해야 계정을 안전하면서도 업무를 막지 않는 수준으로 지킬 수 있습니다.

디렉터리 서비스 개념

사용자와 자원 정보를 한곳에서 관리하는 이유

회사에 직원이 스무 명만 되어도 서버마다 계정을 따로 만들기 시작하면 금세 감당이 안 됩니다. 누군가 퇴사했을 때 어느 서버의 계정이 아직 남아 있는지 아무도 확신하지 못하고, 새로 들어온 사람은 같은 아이디를 여러 번 만들며 시간을 버리게 됩니다. 디렉터리 서비스(Directory Service)는 이렇게 흩어진 사용자와 자원 정보를 한곳에 모아 두고 필요할 때마다 꺼내 보게 만드는 상위 개념의 기술입니다.

아파트 관리사무소를 떠올리면 이해가 쉽습니다. 관리사무소가 보관하는 입주민 명부가 곧 디렉터리이고, 명부를 기준으로 방문객을 확인하고 출입카드를 발급하는 창구의 업무가 디렉터리 서비스입니다. 세대마다 나눠 준 출입카드는 사용자를 증명하는 수단이 되고, 체육관이나 주차장 같은 시설을 쓸 수 있는 권한도 명부에 적힌 자격에 따라 달라집니다.

그래서 명부 한 곳만 고치면 모든 시설의 출입 기준이 동시에 바뀌고, 관리사무소는 세대마다 명부를 따로 만들지 않습니다.

정리하면 디렉터리 서비스는 사용자와 자원, 권한 정보를 계층 구조로 저장해 두고 조회와 인증을 대신 처리하는 저장소이며, 여러 시스템이 같은 명부를 공유하게 해 관리의 중복을 없애는 기술입니다.

Active Directory 개요

AD DS가 제공하는 기능과 구성 요소

서버가 열 대만 넘어가도 각 서버가 자기 계정과 암호 규칙을 따로 들고 있으면, 사용자는 서버마다 다른 암호를 외워야 하고 관리자는 누가 어떤 권한을 가졌는지 한눈에 볼 수 없습니다. Active Directory(AD)는 이런 계정과 정책, 자원 정보를 한 체계로 묶어 관리하도록 마이크로소프트가 만든 디렉터리 서비스이며, 그중 핵심 역할을 하는 것이 AD DS(Active Directory Domain Services)입니다.

대기업의 인사본부를 비유로 삼아 보겠습니다. 인사본부가 직원 정보를 어떤 항목으로 기록할지 정한 서식이 스키마(Schema)이고, 지점마다 배치된 인사 담당자가 그 서식에 맞춰 명부를 관리하는 모습이 도메인 컨트롤러입니다.

직원이 사원증을 내밀면 본인 여부를 확인해 주는 절차가 케르베로스(Kerberos) 인증이고, 전 지점 직원의 이름과 소속을 빠르게 찾아 주는 통합 주소록이 글로벌 카탈로그(Global Catalog)입니다. 인사본부는 이 기록을 표준 형식으로 조회할 수 있게 LDAP(Lightweight Directory Access Protocol)라는 창구도 열어 두어, 다른 업무 시스템이 직원 정보를 가져다 쓸 수 있게 합니다.

결국 AD DS는 도메인이라는 관리 범위 안에서 계정과 권한, 정책을 중앙에 모으고, 인증과 조회를 표준 프로토콜로 제공해 여러 서버와 응용 프로그램이 같은 사용자 정보를 믿고 사용하게 하는 기반 서비스입니다.

도메인·트리·포리스트

AD의 논리적 구조를 이루는 단위

회사가 커져 지점이 늘어나면 모든 지점을 하나의 명부로 관리하기도 어렵고, 반대로 지점마다 완전히 따로 관리하면 본사 방침이 반영되지 않습니다. Active Directory는 이 문제를 해결하려고 관리 범위를 도메인(Domain), 트리(Tree), 포리스트(Forest)라는 세 층으로 나누어 논리적 구조를 만듭니다.

프랜차이즈 카페에 빗대면 구조가 잘 드러납니다. 한 매장이 자기 직원과 재고를 관리하는 단위가 도메인이고, 같은 브랜드 이름을 이어 쓰는 매장들의 묶음이 트리이며, 서로 다른 브랜드를 함께 소유한 그룹 전체가 포리스트입니다. 매장마다 명부를 따로 두되 같은 브랜드끼리는 이름 체계를 공유하고, 그룹 전체를 아우르는 공통 규칙은 포리스트 수준에서 정하는 식입니다.

도메인은 보안 경계이자 복제의 단위이기도 해서, 한 도메인의 관리자가 다른 도메인 자료를 마음대로 손대지 못하고 명부 변경도 도메인 안에서 먼저 퍼집니다.

정리하면 도메인은 계정과 정책을 담는 기본 관리 단위, 트리는 도메인 이름의 계층을 이어 붙인 묶음, 포리스트는 트리들을 모두 포함하는 최상위 경계이며, 이 세 층이 함께 AD의 논리적 구조를 이룹니다.

도메인 컨트롤러

AD 데이터를 보유하고 인증을 처리하는 서버

사용자가 로그인할 때마다 어느 서버가 본인 확인을 맡을지 정해져 있지 않다면, 인증 요청은 아무 데나 흩어지고 권한 판단도 서버마다 달라집니다. 도메인 컨트롤러(Domain Controller)는 Active Directory 데이터를 직접 보유하면서 로그인과 권한 확인을 처리하는 서버로, 도메인 구조가 실제로 돌아가게 하는 중심입니다.

회사 정문의 경비실을 떠올려 보겠습니다. 경비실이 들고 있는 출입 명부가 AD 데이터베이스이고, 방문자가 사원증을 내밀면 명부와 대조해 통과 여부를 알려 주는 일이 인증입니다. 건물마다 경비실을 두고 같은 명부 사본을 나눠 가지면 어느 문으로 들어와도 동일한 판정을 받을 수 있는데, 이렇게 변경 내용을 서로 맞춰 가는 과정이 복제(Replication)입니다.

한 경비실이 공사를 하느라 문을 닫아도 다른 경비실이 같은 명부로 응대할 수 있어서, 도메인 컨트롤러를 여러 대 두면 인증이 멈추는 일을 줄일 수 있습니다.

결국 도메인 컨트롤러는 AD DS의 데이터를 저장하고 복제하며 케르베로스 인증과 LDAP 조회를 응답하는 서버이고, 그래서 도메인마다 최소 두 대 이상을 두는 구성이 권장됩니다.

AD DS 설치

새 포리스트를 만들고 첫 도메인 컨트롤러를 세우는 절차

새로 만든 회사에 직원 명부가 없으면 급여도 권한 관리도 매번 손으로 처리해야 하고, 나중에 명부를 만들려면 이미 흩어진 계정을 다시 정리해야 합니다. 그래서 Windows Server에서는 서버 관리자에서 AD DS 역할을 추가한 뒤 그 서버를 도메인 컨트롤러로 승격시켜, 새 포리스트의 첫 도메인을 세우는 절차부터 시작합니다.

새 학교를 개교하는 과정과 비슷합니다. 먼저 교무실을 꾸미는 일이 AD DS 역할 설치이고, 학생 명부를 어떤 이름 규칙으로 만들지 정하는 일이 새 포리스트와 루트 도메인 이름을 정하는 단계입니다. 명부를 찾아올 수 있도록 주소 안내판을 세우는 일은 DNS 서버 역할을 함께 설치하는 것에 해당하고, 초기에는 이 서버가 자기 자신을 이름 서버로 바라보게 설정합니다.

마지막으로 교무실 열쇠를 따로 보관하는 것처럼 디렉터리 서비스 복원 모드(DSRM) 암호를 정해 두고 승격을 마치면, 그 서버가 첫 도메인 컨트롤러가 되어 이후 계정과 정책을 받아들일 준비를 마칩니다.

정리하면 새 포리스트 구성은 AD DS 역할 추가, 도메인 이름과 DNS 설정, DSRM 암호 지정, 승격 확인의 순서로 진행되며, 승격이 끝난 서버가 해당 도메인의 첫 도메인 컨트롤러가 됩니다.

조직 구성 단위(OU) 설계

조직 구조를 반영해 개체를 나누는 방법

도메인 하나에 계정이 수천 개씩 쌓이면, 부서별로 다른 암호 정책을 적용하거나 신입 관리자에게 특정 범위만 맡기기가 매우 번거로워집니다. 조직 구성 단위(OU, Organizational Unit)는 개체를 조직 구조에 맞춰 나눠 담는 그릇으로, 정책 적용과 관리 권한 위임의 범위를 사람이 다루기 쉬운 크기로 잘라 주는 장치입니다.

사무실의 서류 캐비닛을 생각해 보겠습니다. 서랍 하나하나가 OU이고 그 안에 꽂힌 서류가 사용자와 컴퓨터 같은 개체이며, 서랍 앞면에 붙은 규칙표가 그 범위에 적용되는 그룹 정책입니다. 부서별로 서랍을 나누면 영업팀 서랍에만 영업용 프로그램 설치 규칙을 붙일 수 있고, 서랍 열쇠를 팀장에게 주는 일이 관리 권한 위임이 됩니다.

다만 서랍을 너무 잘게 나누면 규칙표를 여러 장 붙여야 하고 찾기도 어려워지므로, 실제로 정책이나 권한이 달라지는 지점을 기준으로 나누는 것이 좋습니다.

정리하면 OU 설계는 부서나 지역 같은 조직 구조를 반영해 개체를 나누되, 정책 적용과 권한 위임이 필요한 단위를 기준으로 깊이를 최소화하는 방식으로 해야 유지보수가 쉬워집니다.

AD 개체 관리

사용자·그룹·컴퓨터 계정을 만들고 관리하기

회사에 직원이 백 명쯤 되면 컴퓨터마다 따로 계정을 만들고 누가 어디에 접근하는지 손으로 적어 두는 방식은 금세 한계에 부딪힙니다. 이런 곤란을 없애려고 계정 정보를 중앙에 모아 두고 로그인과 권한을 한꺼번에 처리하는 디렉터리 서비스가 나왔고, 그중 마이크로소프트의 것이 액티브 디렉터리(Active Directory)이며 그 안에 들어 있는 사용자·그룹·컴퓨터 계정 하나하나를 개체(object)라고 부릅니다.

아파트 관리사무소를 떠올리면 이해가 쉽습니다.

입주자에게 출입 카드를 발급하는 일이 사용자 계정을 만드는 일이고, 카드에 어느 동 어느 호인지 적어 두는 것이 계정의 소속 정보를 지정하는 일입니다. 같은 층 주민을 묶어 공용 시설을 쓰게 하는 것이 그룹이고, 세대마다 설치된 현관 잠금장치를 관리대장에 올리는 것이 컴퓨터 계정입니다.

이사를 가면 카드 정보를 고치고 퇴거하면 카드를 즉시 정지하듯이 계정도 옮기고 비활성화하며, 이런 변경 기록이 한 곳에 남기 때문에 누가 언제 무엇을 바꿨는지 확인할 수 있습니다.

결국 액티브 디렉터리의 개체 관리는 사용자 계정, 그룹, 컴퓨터 계정을 조직 구조에 맞춰 만들고 고치고 없애는 일이며, 그 결과가 한곳에 모여 인증과 권한 판단의 근거가 됩니다.

그룹 전략

보안 그룹과 배포 그룹을 설계하는 기준

권한을 사람마다 하나씩 직접 주다 보면 입사와 퇴사가 반복될수록 어느 계정에 무슨 권한이 붙었는지 아무도 설명하지 못하는 상태가 됩니다. 그래서 액티브 디렉터리에서는 사람을 그룹에 넣고 그 그룹에 권한을 주는 방식을 쓰며, 용도에 따라 보안 그룹(security group)과 배포 그룹(distribution group)으로 나눕니다.

아파트 단지를 비유하면 보안 그룹은 출입문과 엘리베이터를 여는 권한 카드이고, 배포 그룹은 공지 문자를 돌릴 때 쓰는 연락처 묶음입니다. 카드 묶음은 문을 여는 데만 쓰이고 문자를 보내지는 못하며, 연락처 묶음은 소식을 전하는 데만 쓰이고 문을 열지는 못합니다.

그래서 설계할 때는 먼저 업무별로 권한 묶음을 만들고, 그 권한 묶음에 사람을 직접 넣기보다 부서나 역할을 나타내는 그룹을 거쳐 넣는 층을 두며, 이렇게 하면 사람이 바뀌어도 권한 구조는 그대로 유지됩니다. 메일 같은 응용 프로그램의 배포 목록은 별도로 관리해 권한과 소식을 섞지 않는 것이 원칙입니다.

정리하면 보안 그룹은 접근 권한을 부여하는 단위, 배포 그룹은 메일 같은 배포를 위한 단위이며, 그룹을 몇 겹으로 나눠 설계하는 이유는 사람의 이동과 권한의 변화를 분리해 관리하기 위해서입니다.

사이트와 복제

여러 지점 사이의 AD 데이터 복제 구조 이해

본사와 지사가 멀리 떨어져 있는데 모든 로그인 요청이 본사 서버로 몰리면 느린 회선 때문에 아침마다 로그인이 지연되고, 회선이 끊기면 지사 전체가 업무를 못 하게 됩니다. 액티브 디렉터리는 이 문제를 사이트(site)와 복제(replication)라는 개념으로 풀며, 사이트는 네트워크 속도가 빠른 하나의 구역을 뜻합니다.

전국의 지점이 같은 장부를 각자 한 권씩 보관하는 편의점 체인을 생각하면 쉽습니다. 각 지점은 자기 장부로 바로 업무를 처리하고, 새로 생긴 기록은 정해진 시간표에 따라 다른 지점에 전달되며, 이때 사이트 안에서는 자주 촘촘하게, 사이트 사이에서는 회선 비용과 시간을 고려해 덜 자주 주고받습니다.

전달 경로와 시간표를 계산해 주는 것이 지식 일관성 검사기(Knowledge Consistency Checker)이고, 사이트 사이의 연결에는 비용과 일정을 붙여 어느 회선을 먼저 쓸지 정합니다. 한 지점이 고장 나도 다른 지점의 장부가 남아 있으니 업무가 멈추지 않고, 대신 같은 값이 모든 지점에 도달하기까지는 짧은 시차가 생깁니다.

즉 사이트는 복제를 묶는 네트워크 경계이고 복제는 그 경계 안팎의 일정에 따라 변경 내용을 퍼뜨리는 과정이며, 이 구조 덕분에 지사는 자기 서버로 로그인하면서도 결국 같은 정보를 공유하게 됩니다.

신뢰 관계

도메인과 포리스트 사이의 신뢰를 맺는 방법

인수합병으로 회사 두 곳이 한 지붕 아래 들어왔는데 서로 다른 도메인에 계정이 따로 있어, 협업하려면 사람마다 계정을 두 개씩 만들고 관리해야 하는 번거로움이 생깁니다. 이때 한쪽 도메인의 인증을 다른 쪽이 믿어 주도록 연결하는 것이 신뢰 관계(trust)이며, 도메인과 포리스트 사이에 맺습니다.

옆 단지와 상호 방문 협약을 맺는 것과 같아서, 우리 단지 카드를 상대 경비실이 확인해 주면 상대 단지 시설을 쓸 수 있습니다. 한쪽만 상대 카드를 인정하는 것이 단방향 신뢰(one-way trust)이고, 서로 인정하면 양방향 신뢰(two-way trust)이며, A가 B를 믿고 B가 C를 믿을 때 A와 C도 이어지는 성질을 전이(transitive)라고 합니다.

같은 포리스트 안의 도메인끼리는 이런 신뢰가 자동으로 맺어지지만, 다른 포리스트나 외부 도메인과는 관리자가 직접 만들고 방향과 범위를 정해야 합니다. 협약을 넓게 열어 두면 예상치 못한 사람까지 상대 시설을 쓰게 되므로, 필요한 방향으로만 열어 두는 것이 안전합니다.

결국 신뢰 관계는 서로 다른 도메인의 계정을 상대 쪽에서도 인정해 주는 약속이고, 방향과 전이 여부를 분명히 해 두어야 권한이 예상보다 넓어지는 일을 막을 수 있습니다.

FSMO 역할

다섯 가지 단일 마스터 역할의 의미와 이전 방법

도메인 컨트롤러를 여러 대 두면 같은 정보를 나눠 갖기 때문에 대개는 문제가 없지만, 계정 번호를 나눠 주거나 이름 중복을 판정하는 일처럼 동시에 여럿이 하면 충돌하는 작업이 있습니다. 그래서 액티브 디렉터리는 이런 작업마다 한 대만 담당하도록 정해 두었고, 이를 유연한 단일 마스터 작업(FSMO, Flexible Single Master Operations) 역할이라고 부릅니다.

관리사무소 창구 다섯 개를 떠올리면 이해가 쉽습니다. 도면과 규정을 고치는 창구, 동과 호수를 새로 정하는 창구, 주민 번호를 나눠 주는 창구, 시계와 긴급 방송을 맡는 창구, 다른 단지와의 명부 대조를 맡는 창구가 각각 하나씩만 열려 있습니다.

실제로는 스키마 마스터(schema master), 도메인 명명 마스터(domain naming master), RID 마스터(RID master), PDC 에뮬레이터(PDC emulator), 인프라스트럭처 마스터(infrastructure master)의 다섯 가지이며, 앞의 두 개는 포리스트에 하나씩, 나머지 셋은 도메인마다 하나씩 있습니다. 담당 창구가 문을 닫으면 그 업무만 멈추고 나머지 업무는 계속되며, 창구를 옮길 때는 새 담당자를 정해 권한을 넘기고 예전 담당자를 정리하되 옮기기 전에 복제가 제대로 끝났는지 확인해야 합니다.

정리하면 FSMO 역할은 여럿이 동시에 처리하면 안 되는 다섯 가지 작업의 단일 담당자를 정한 제도이고, 역할의 종류와 이전 절차를 알고 있어야 장애 때 혼란 없이 대응할 수 있습니다.

글로벌 카탈로그

포리스트 전체 검색을 담당하는 카탈로그 서버

포리스트에 도메인이 여러 개 있으면 다른 도메인의 사용자를 찾을 때마다 그 도메인의 컨트롤러에 다시 물어봐야 해서 검색이 느려지고, 담당 서버가 꺼지면 찾기 자체가 안 됩니다. 이 문제를 해결하려고 포리스트 전체의 주요 정보를 모아 둔 서버를 따로 두는데, 이것이 글로벌 카탈로그(global catalog)입니다.

여러 지점의 명부를 전부 베끼는 대신 이름과 소속처럼 자주 찾는 항목만 한 권으로 요약해 둔 색인 책과 같습니다. 이 색인 책에는 각 개체의 속성 가운데 일부만 담기므로 부분 속성 집합(partial attribute set)이라고 부르고, 색인이 있으면 어느 지점 사람인지 먼저 찾아낸 뒤 해당 지점에 상세 정보를 확인합니다.

로그인할 때도 이 색인을 통해 소속 그룹을 빠르게 확인하므로, 글로벌 카탈로그를 가진 서버는 로그인 경로에 놓이게 됩니다. 그래서 지사처럼 사용자가 많은 곳에는 글로벌 카탈로그 서버를 함께 두어 본사 회선이 끊겨도 로그인이 되게 설계합니다.

결국 글로벌 카탈로그는 포리스트 전체를 대상으로 한 요약 색인을 들고 있는 서버이고, 전체 정보가 아니라 자주 쓰는 일부 속성만 담아 검색 속도와 가용성을 함께 얻는 구조입니다.

5부. Active Directory 운영과 고급 기능043

읽기 전용 도메인 컨트롤러(RODC)

지점에 두는 도메인 컨트롤러의 용도와 제약

지점 사무실 직원들이 본사 데이터센터에 있는 도메인 컨트롤러로 매번 로그온을 시도하면 네트워크가 끊길 때 업무가 멈추고, 그렇다고 지점에 일반 도메인 컨트롤러를 그대로 두면 서버가 도난당하는 순간 회사 전체 계정 정보가 함께 유출됩니다. 이 두 가지 곤란을 동시에 줄이려고 만든 것이 읽기 전용 도메인 컨트롤러(Read-Only Domain Controller, RODC)입니다. 택배 회사에 비유하면 본사 물류창고가 원본 장부를 가진 곳이고, 지점 대리점은 배송 조회만 할 수 있는 사본 목록을 받아 두는 곳입니다. 대리점 직원은 손님에게 배송 상태를 알려줄 수 있지만 목록에 없는 내용을 새로 적어 넣거나 고칠 수는 없고, 변경이 필요하면 본사에 요청해 원본 장부를 고친 뒤 갱신된 목록을 다시 받습니다.

RODC도 같은 방식으로 계정 인증과 조회는 지점에서 처리하되, 계정 암호 같은 중요한 정보는 기본적으로 저장하지 않고 변경 요청은 쓰기 가능한 도메인 컨트롤러로 넘깁니다. 또 RODC에 어떤 계정 정보를 복제할지 미리 정해 두는 암호 복제 정책(Password Replication Policy)을 두어, 서버가 넘어가도 피해 범위를 그 계정들로 한정합니다. 정리하면 RODC는 지점의 로그온 속도와 본사의 계정 보호를 함께 잡기 위해, 복제는 받되 쓰기는 하지 않는 제한된 도메인 컨트롤러입니다. 다만 어떤 기능이 제한되는지는 도메인과 운영 환경에 따라 다르므로 도입 전에 확인이 필요합니다.

AD 휴지통

삭제된 개체를 원래 위치로 복원하는 기능

관리자가 실수로 조직 구성 단위(OU)를 지우면 그 안의 사용자와 그룹이 한꺼번에 사라지고, 예전에는 백업에서 되살린 뒤 권한과 연결 관계를 손으로 다시 맞춰야 했습니다. 이 곤란을 없애려고 만든 기능이 Active Directory 휴지통(AD Recycle Bin)입니다. 아파트 관리사무소의 분실물 보관함에 비유하면, 주민이 실수로 내놓은 물건은 곧바로 폐기되지 않고 보관함에 들어가며 관리사무소는 그것이 어느 집 어느 자리에서 나왔는지 기록해 둡니다. 주인이 찾아오면 같은 자리에 그대로 돌려놓을 수 있고, 보관 기간이 지나면 그때 폐기됩니다.

AD 휴지통도 삭제된 개체를 완전히 지우지 않고 삭제된 개체 컨테이너(Deleted Objects Container)에 남겨, 개체의 원래 위치와 속성을 유지한 채 복원 명령 한 번으로 되돌립니다. 다만 이 기능을 쓰려면 숲의 기능 수준을 올려야 하고, 보관 기간이 지나면 복원할 수 없습니다. 정리하면 AD 휴지통은 삭제를 즉시 파괴가 아닌 보관으로 바꿔, 삭제된 개체를 원래 위치로 간단히 복원하게 해 주는 기능입니다.

AD 백업과 복구

시스템 상태 백업으로 도메인 컨트롤러를 되살리기

도메인 컨트롤러의 디스크가 고장 나거나 잘못된 변경이 도메인 전체로 퍼지면 로그온도 그룹 정책도 멈추고 사용자는 아무것도 할 수 없게 됩니다. 이때 도메인 컨트롤러를 다시 세우는 기준점이 되는 것이 시스템 상태 백업(System State Backup)입니다. 아파트 관리사무소가 시설 도면의 봉인 사본을 별도 금고에 두는 것에 비유할 수 있습니다. 원본 도면이 불에 타면 봉인 사본으로 건물 구조를 되살리지만, 봉인한 뒤에 진행한 공사 내역은 사본에 없으므로 그 부분은 다시 손봐야 합니다.

시스템 상태 백업도 마찬가지로 Active Directory 데이터베이스(ntds.dit), 레지스트리, 시스템 파일, 인증서 서비스 정보처럼 서버가 도메인 컨트롤러로 동작하는 데 필요한 요소를 한 묶음으로 저장합니다. 복구는 디렉터리 서비스 복원 모드(Directory Services Restore Mode)로 부팅해 백업 시점으로 되돌리는 방식으로 하며, 백업 이후에 바뀐 내용은 다른 도메인 컨트롤러와의 복제로 다시 채웁니다. 정리하면 시스템 상태 백업은 도메인 컨트롤러 한 대를 백업 시점 상태로 되살리는 최소 필수 묶음이고, 복구 뒤에는 복제 상태를 점검해야 합니다.

이렇게 나눠 두면 새 직원이 들어와도 관리사무소장이 일일이 뛰어다니지 않아도 되고, 사고가 나면 피해 범위도 그 동 안에서 멈춥니다.

정리하면 Active Directory의 권한 위임은 조직 단위라는 경계를 기준으로 계정과 컴퓨터를 관리할 범위를 나눠 주는 일이며, 위임 제어 마법사로 필요한 권한만 골라 부여하면 최소한의 권한으로 충분한 일을 하게 만들 수 있습니다.

이름 해석 개념

사람이 쓰는 이름을 IP 주소로 바꾸는 원리

사람은 203.0.113.25 같은 숫자 주소를 수십 개씩 외울 수 없고, 서버의 주소가 바뀔 때마다 문서와 설정에 적힌 숫자를 전부 고쳐야 한다면 업무가 마비됩니다. 그래서 사람이 쓰는 이름을 그 이름에 해당하는 IP 주소로 바꿔 주는 절차가 필요하고, 이것을 이름 해석(name resolution)이라고 합니다.

연락처 앱에 비유하면, 우리가 '김철수'를 눌렀을 때 앱이 저장된 전화번호를 찾아 걸어 주는 것과 같습니다. 이름 해석을 요청하는 쪽(클라이언트)은 이름을 들고 물어보고, 이름과 주소를 알고 있는 서버(네임서버)가 그 이름에 맞는 IP 주소를 돌려줍니다. 앱이 연락처를 한 곳에만 저장하지 않고 여러 곳을 확인하듯, 이름 해석도 가까운 서버가 모르면 상위 서버에 차례로 물어보며 답을 찾습니다.

답을 받은 클라이언트는 그 주소로 실제 접속을 하고, 한동안은 같은 질문을 반복하지 않도록 답을 기억해 둡니다.

정리하면 이름 해석은 사람이 읽기 쉬운 이름을 컴퓨터가 쓰는 IP 주소로 변환하는 과정이며, DNS(Domain Name System)라는 체계가 이 변환을 맡아 분산된 네임서버들의 협력으로 답을 찾아냅니다.

존·레코드·네임서버가 각각 맡는 역할

도메인 이름과 IP 주소의 대응 관계를 아무도 정해 두지 않으면 같은 이름이 서로 다른 주소를 가리키거나, 이름을 물어봐도 답해 줄 곳이 없어 접속이 실패합니다. 이 대응 관계를 체계적으로 나눠 보관하고 응답하는 역할을 맡는 요소가 존(zone)·레코드(record)·네임서버(name server)입니다.

회사 인사 기록에 비유하면, 부서별로 나눠 둔 인사 명부가 존이고, 명부의 한 줄 한 줄이 레코드이며, 명부를 보관하고 문의에 답하는 인사 창구가 네임서버입니다. 존은 example.com처럼 관리 범위가 정해진 이름 공간으로, 그 안에 속한 이름과 주소의 대응을 책임집니다. 레코드는 특정 이름이 어떤 IP 주소를 쓰는지, 메일은 어디로 보내야 하는지 같은 사실을 한 줄씩 적어 둔 항목입니다.

네임서버는 이 명부를 실제로 들고 있으면서 다른 컴퓨터의 질문을 받아 해당 레코드를 찾아 답해 주고, 한 대가 아니라 여러 대로 나눠 두어 한 곳이 멈춰도 해석이 계속되게 합니다.

정리하면 존은 관리 단위로 나눈 이름 공간, 레코드는 그 안에 적힌 개별 대응 정보, 네임서버는 그 정보를 보관하고 응답하는 서버이며, 이 셋이 맞물려 DNS가 동작합니다.

DNS 레코드 유형

A·AAAA·CNAME·MX 등 레코드의 쓰임

이름 하나에 주소만 적어 두면 웹 서버는 찾을 수 있어도 메일을 어디로 보내야 하는지, 여러 대의 서버로 부하를 나누려면 어떻게 해야 하는지는 알 수 없습니다. 그래서 DNS는 담으려는 사실의 종류마다 레코드 유형(record type)을 따로 두어, 같은 이름이라도 목적에 맞는 답을 꺼내 쓸 수 있게 했습니다.

택배 송장에 비유하면, 송장에는 받는 사람·주소·배송 방법 칸이 정해져 있고 각 칸에 맞는 내용을 적어야 배송이 됩니다. A 레코드는 이름에 IPv4 주소를 연결하는 가장 기본 칸이고, AAAA 레코드는 같은 역할을 IPv6 주소로 합니다. CNAME 레코드는 이름을 다른 이름으로 넘겨 주는 칸이라 실제 주소가 바뀌어도 이쪽만 고치면 되며, MX 레코드는 그 도메인의 메일을 받을 서버를 지정합니다.

이 밖에도 서비스 위치를 알려 주는 SRV나 텍스트 정보를 담는 TXT처럼 목적별 칸이 더 있고, 필요한 칸만 정확히 채워야 조회가 의도대로 동작합니다.

정리하면 DNS 레코드 유형은 이름에 딸린 사실을 종류별로 구분해 적는 형식이며, A와 AAAA는 주소를, CNAME은 이름의 별칭을, MX는 메일 수신처를 나타내는 식으로 각 유형이 맡은 역할이 정해져 있습니다.

DNS 포워딩과 조건부 전달자

외부 이름 조회를 다른 DNS 서버로 넘기는 방법

사내 이름만 관리하는 DNS 서버가 외부 인터넷 주소까지 혼자 찾으려 하면, 루트부터 시작하는 전체 조회를 매번 떠안아 응답이 느려지고 설정도 금세 낡습니다. 그래서 안쪽 서버가 모르는 이름만 바깥의 다른 DNS 서버에 대신 물어보도록 넘기는 기능이 DNS 포워딩(forwarding)이고, 특정 도메인만 정해진 서버로 보내는 변형이 조건부 전달자(conditional forwarder)입니다.

회사 우편실을 떠올리면 이해가 쉽습니다. 우편실은 사내 부서 이름은 자기가 다 알지만 외부로 나가는 편지는 배달 경로를 일일이 짜지 않고 늘 거래하는 우체국에 통째로 넘기는데, 이것이 포워딩입니다. 우체국 주소를 하나만 적어 두면 이후 외부로 나가는 우편은 전부 그곳을 거치게 됩니다.

조건부 전달자는 여기에 예외 규칙을 붙이는 것으로, 협력사 A 앞으로 간 편지는 늘 A 전용 우편함에 직접 넣으라는 식으로 도메인마다 담당 우편함을 지정합니다. 이렇게 하면 직원 모두가 외부 우편 규칙을 외울 필요 없이 우편실 한 곳만 알면 됩니다.

정리하면 DNS 포워딩은 내부 DNS 서버가 알지 못하는 이름 질의를 지정한 상위 DNS 서버로 넘겨 대신 해석하게 하는 설정이고, 조건부 전달자는 그 넘김을 특정 도메인에만 한정해 적용하는 규칙입니다.

DNS 동적 업데이트

클라이언트가 자기 레코드를 자동 등록하게 하기

PC가 DHCP로 새 주소를 받거나 서버 이름이 바뀔 때마다 관리자가 레코드를 손으로 고치면, 몇 대만 되어도 누락과 오타가 쌓이고 이름 해석이 조용히 깨집니다. 그래서 클라이언트가 자기 레코드를 DNS 서버에 스스로 등록하고 갱신하게 만든 것이 DNS 동적 업데이트(dynamic update)입니다.

아파트 관리사무소를 떠올리면 구조가 그대로 보입니다. 예전에는 입주자가 바뀔 때마다 직원이 명부를 고쳤지만, 동적 업데이트는 입주자가 들어오면 직접 입주 신고서를 내고 나갈 때 말소 신고를 하게 합니다. 신고를 받은 사무소는 명부(존 파일, zone)에 이름과 호수를 적어 두고, 신고가 없거나 오래된 항목은 임대 기간(lease)이 끝나면 자동으로 지웁니다.

다만 아무나 명부를 고칠 수 있으면 곤란하므로 신분 확인 절차를 두어 등록 권한을 제한하는데, 이것이 보안 동적 업데이트(secure update)입니다.

정리하면 DNS 동적 업데이트는 클라이언트와 DHCP 서버가 A 레코드와 PTR 레코드를 DNS에 자동으로 등록하고 갱신하고 삭제하는 기능이며, 믿을 수 있는 주체만 쓰도록 권한을 좁히는 것이 운영의 핵심입니다.

6부. DNS와 DHCP057

DNSSEC

DNS 응답의 위조를 막는 서명 방식

공격자가 DNS 응답을 중간에서 가로채 엉뚱한 주소를 돌려주면, 사용자는 주소창에 맞는 이름을 쳤는데도 가짜 은행 사이트로 끌려갑니다. 응답이 진짜 서버에서 나왔는지 확인할 방법이 없다는 점이 문제의 뿌리이고, 이를 서명으로 막는 방식이 DNSSEC입니다.

등기우편을 떠올리면 이해가 쉽습니다. 보통 편지는 받는 사람이 누가 보냈는지 알 수 없지만, 발신자가 도장을 찍고 우체국이 그 도장이 진짜임을 확인해 주면 내용이 바뀌지 않았다는 것까지 알 수 있습니다.

DNSSEC는 존(zone)마다 공개키와 개인키 한 쌍을 두고, 개인키로 레코드 묶음에 서명해 RRSIG라는 서명 레코드를 붙이며, 공개키는 DNSKEY 레코드로 공개합니다. 응답을 받은 쪽은 그 서명을 검증해 내용이 변조되지 않았는지 확인하고, 검증에 실패한 응답은 신뢰하지 않고 버립니다. 이 신뢰는 상위에서 하위로 이어지는데, 부모 존이 자식 존의 공개키 요약값(DS)에 서명하는 방식으로 루트까지 사슬이 연결됩니다.

정리하면 DNSSEC는 DNS 레코드에 디지털 서명을 붙여 응답의 출처와 무결성을 검증하는 확장으로, 내용을 감추는 암호화가 아니라 위조를 걸러내는 장치입니다.

DNS 문제 해결

nslookup과 로그로 이름 해석 장애를 찾기

사용자가 인터넷이 안 된다고 말할 때 실제로는 웹 서버가 아니라 이름 해석이 실패한 경우가 많고, 원인은 클라이언트 설정과 DNS 서버와 포워딩과 레코드 중 어디에든 있을 수 있습니다. 그래서 nslookup 같은 도구로 어느 단계에서 끊겼는지 좁혀 가는 절차가 필요합니다.

택배가 오지 않았을 때 집 앞만 보지 않고 물류 단계를 하나씩 확인하는 것과 같습니다.

먼저 클라이언트가 어느 DNS 서버를 바라보고 있는지 ipconfig /all 같은 명령으로 확인해, 엉뚱한 서버를 가리키고 있지 않은지 봅니다. 다음으로 nslookup으로 그 서버에 직접 질의해 응답 코드를 읽는데, 이름이 없다는 NXDOMAIN과 서버가 해석하지 못했다는 SERVFAIL과 응답이 아예 없는 시간 초과는 각각 원인이 다릅니다. 마지막으로 DNS 서버의 로그와 캐시를 확인해 질의가 도달했는지, 포워더가 응답했는지, 낡은 캐시가 남아 있지는 않은지 살핍니다.

정리하면 DNS 문제 해결은 클라이언트 설정, 질의 응답 코드, 서버 로그와 캐시를 순서대로 확인해 실패 지점을 좁히는 작업이며, 추측으로 설정을 바꾸기 전에 어느 단계가 끊겼는지 먼저 가리는 것이 중요합니다.

6부. DNS와 DHCP059

DHCP 개념

IP 주소를 자동으로 나눠 주는 원리

PC를 새로 설치할 때마다 IP 주소와 서브넷 마스크와 게이트웨이와 DNS를 손으로 적으면, 같은 주소를 두 대에 주는 충돌이나 오타로 인한 통신 불가가 반복됩니다. 주소를 자동으로 빌려주고 일정 기간이 지나면 회수하는 방식이 DHCP(Dynamic Host Configuration Protocol)입니다.

호텔 프런트를 떠올리면 원리가 그대로 보입니다. 투숙객이 오면 프런트가 빈 방 번호를 내주고, 체크아웃하면 그 방을 회수해 다음 손님에게 다시 줍니다.

DHCP 서버는 주소 풀(scope)에서 주소를 빌려주고 임대 기간(lease)을 정하는데, 클라이언트는 발견과 제안과 요청과 확인의 네 단계를 거쳐 방을 배정받습니다. 임대가 끝나기 전에 계속 쓰고 싶으면 갱신을 요청하고, 기간이 지나도록 갱신이 없으면 주소는 반납되어 다시 풀로 돌아갑니다.

정리하면 DHCP는 주소와 네트워크 설정을 서버가 임대 형식으로 자동 배포하고 회수하는 프로토콜이며, 그래서 관리자는 개별 PC가 아니라 주소 풀과 임대 기간을 관리하게 됩니다.

6부. DNS와 DHCP060

DHCP 범위와 예약

범위·옵션·예약으로 주소를 관리하기

주소를 무작정 나눠 주면 프린터나 서버처럼 늘 같은 주소여야 하는 장비가 재부팅 후 다른 주소를 받아 접속이 끊깁니다. 그래서 나눠 줄 구간과 함께 제공할 설정을 정하고 특정 장비에는 주소를 고정해 두는 관리가 필요하며, 이를 범위(scope)와 예약(reservation)으로 처리합니다.

호텔로 비유하면 층별로 배정된 객실 구역이 범위이고, 모든 객실에 기본으로 갖춰 두는 비품이 옵션이며, 단골손님의 지정석이 예약입니다.

범위는 어느 주소부터 어느 주소까지 나눠 줄지 정하는 구간으로, 서버가 쓰는 주소는 제외 범위(exclusion)로 빼 두어 충돌을 막습니다. 옵션은 게이트웨이 주소와 DNS 서버 주소, 임대 기간처럼 클라이언트가 함께 받아야 하는 값을 정하는 항목입니다. 예약은 장비의 MAC 주소와 IP 주소를 짝지어 두어, 그 장비가 물을 때마다 같은 주소를 주도록 하는 설정입니다.

정리하면 DHCP 범위는 나눠 줄 주소 구간과 기본 설정을 정의하는 단위이고, 예약은 그 안의 특정 주소를 정해진 장비에만 묶어 두는 방법입니다.

디스크와 볼륨

물리 디스크를 논리 볼륨으로 나누는 구조

새 서버에 하드디스크 두 개를 꽂았는데 운영체제가 하나의 덩어리로만 보여 주고, 나중에 디스크 하나가 고장 나도 어느 부분이 문제인지 바로 알 수 없어 복구에 시간이 걸립니다. 이런 혼란을 없애려고 등장한 개념이 디스크(disk)와 볼륨(volume)을 구분하는 구조입니다. 회사 건물에 비유하면 물리 디스크는 실제로 세워진 건물이고 볼륨은 그 건물 안에서 부서별로 나눠 쓰는 사무실 구역과 같습니다. 건물 하나에 사무실이 여러 개 들어가듯 물리 디스크 하나에도 볼륨을 여러 개 만들 수 있고, 반대로 여러 건물을 하나의 사무실처럼 통로로 이어 붙일 수도 있습니다. 운영체제는 건물 자체가 아니라 사무실 단위로 열쇠를 나눠 주기 때문에, 사용자는 볼륨에만 접근하고 실제 자기 위치는 신경 쓰지 않습니다.

그래서 볼륨을 하나 지우더라도 같은 디스크의 다른 볼륨은 그대로 남습니다. 정리하면 물리 디스크는 데이터가 실제로 저장되는 하드웨어이고, 볼륨은 운영체제가 그 공간을 논리적으로 나눠 관리하는 단위입니다.

파일 시스템

NTFS와 ReFS의 차이와 선택 기준

저장 공간을 아무렇게나 채우면 파일이 어디서 시작해 어디서 끝나는지 기록이 없어 조각 하나만 어긋나도 파일 전체를 잃습니다. 그 기록 규칙을 정한 것이 파일 시스템(file system)이고, Windows Server에서는 주로 NTFS와 ReFS 중 하나를 고릅니다. 택배 창고 비유로 보면 파일 시스템은 물건마다 붙이는 송장과 선반 배치도입니다. NTFS는 오래 쓰인 방식이라 파일마다 권한을 세밀하게 걸고 압축과 암호화, 변경 기록까지 폭넓게 지원합니다. ReFS(Resilient File System)는 큰 데이터를 다루는 서버를 겨냥해 만들어졌고, 디스크 오류를 스스로 감지해 고치며 아주 큰 볼륨을 다루는 데 강점이 있습니다.

다만 ReFS는 부팅 볼륨으로 쓸 수 없고 일부 오래된 기능을 지원하지 않으므로, 부팅과 일반 공유는 NTFS, 대용량 백업 저장소는 ReFS처럼 역할을 나누는 것이 일반적입니다. 즉 파일 시스템은 저장 공간에 파일을 배치하고 추적하는 규칙이며, 호환성과 기능이 넓은 NTFS와 대용량·자가 복구에 강한 ReFS를 용도에 맞춰 선택하면 됩니다.

파티션 방식

MBR과 GPT 파티션의 차이와 변환

디스크 한 장에 운영체제를 두 개 설치하려 했더니 두 번째 위치를 기록할 자리가 없어 첫 번째만 인식되는 일이 있습니다. 디스크의 어느 구역에 무엇이 있는지 적어 두는 표의 형식이 바로 파티션 방식(partition scheme)이며, 오래된 MBR과 현재의 GPT로 나뉩니다. 아파트 단지의 호수 배치도에 비유하면, MBR은 입구 게시판 한 장에 세대 위치를 적는 방식이고 GPT는 단지 전체를 여러 장으로 나눠 중복 보관하는 방식입니다. MBR은 2TB까지만 주소를 매길 수 있고 기본 파티션도 네 개로 제한되지만, GPT는 훨씬 큰 용량을 다루고 파티션 수 제한이 사실상 없으며 배치도를 두 곳에 나눠 보관해 하나가 손상돼도 복구할 수 있습니다. GPT는 UEFI 부팅과 짝을 이루고, MBR은 전통적인 BIOS 부팅과 함께 쓰여 왔습니다.

변환은 데이터를 지우고 다시 만드는 방식이 일반적이므로, 가능하면 처음부터 GPT로 구성하는 편이 안전합니다. 파티션 방식은 디스크의 구역 정보를 담는 표의 형식이고, 2TB와 파티션 네 개라는 한계를 넘으려면 GPT를 선택해야 합니다.

저장소 공간(Storage Spaces)

여러 디스크를 묶어 풀과 가상 디스크 만들기

서버마다 남는 공간이 조금씩 있는데 정작 필요한 곳에는 용량이 모자라 손으로 파일을 옮겨 다녀야 합니다. 여러 물리 디스크를 묶어 하나의 커다란 저장소로 쓰게 해 주는 기능이 저장소 공간(Storage Spaces)입니다. 창고 여러 동을 하나의 물류 센터로 묶는 비유가 잘 맞습니다. 먼저 디스크들을 모아 풀(pool)이라는 공동 창고를 만들고, 그 위에 가상 디스크(virtual disk)라는 선반 구역을 원하는 크기로 얹습니다. 이때 미러(mirror)나 패리티(parity) 같은 방식을 고르면 같은 물건을 여러 동에 나눠 보관해 한 동이 무너져도 데이터가 살아남습니다.

창고를 늘리려면 디스크만 추가해 풀에 넣으면 되고, 가상 디스크의 크기는 나중에 키울 수 있습니다. 정리하면 저장소 공간은 물리 디스크를 풀이라는 공간으로 묶고 그 위에 가상 디스크를 만들어, 용량 확장과 이중화를 소프트웨어로 처리하는 기능입니다.

소프트웨어 RAID

동적 디스크로 구성하는 RAID 수준별 특성

값비싼 RAID 카드를 사지 않고도 디스크 두 개 중 하나가 죽었을 때 데이터를 지키고 싶은 요구가 있습니다. 운영체제가 직접 여러 디스크를 묶어 이중화하는 방식이 소프트웨어 RAID이고, Windows Server에서는 동적 디스크(dynamic disk)로 구성합니다. 택배 회사의 배송 조합에 비유할 수 있습니다. RAID 0은 짐을 나눠 싣는 방식이라 두 배로 빠르지만 한 차가 사고 나면 그 짐은 사라지고, RAID 1은 똑같은 차를 두 대 보내 한 대가 멈춰도 배송이 이어집니다. RAID 5는 짐과 복구용 표식을 세 대 이상에 나눠 실어 한 대가 고장 나도 나머지로 복원하며, 공간 효율과 안전을 절충합니다.

다만 소프트웨어 RAID는 CPU를 쓰고 부팅 볼륨 구성에 제약이 있어, 성능이 중요한 곳은 하드웨어 컨트롤러를 쓰는 편이 낫습니다. 즉 소프트웨어 RAID는 동적 디스크로 여러 디스크를 묶어 RAID 0·1·5 같은 수준을 운영체제 안에서 구현하는 방식이며, 속도와 안전과 비용의 균형을 보고 수준을 고르면 됩니다.

iSCSI

네트워크로 블록 스토리지를 연결하는 방법

서버의 저장 공간이 부족해 디스크를 더 사려 했지만 서버를 열 수 없는 상황이라면, 다른 곳에 있는 저장 장치를 마치 내 서버의 디스크처럼 붙이고 싶어집니다. 이때 일반 네트워크를 통해 블록 저장소를 연결하는 규격이 iSCSI(Internet Small Computer System Interface)입니다. 이사를 가지 않고 창고만 따로 빌리는 것에 비유할 수 있습니다. 내 컴퓨터 안의 iSCSI 초기자(initiator)가 네트워크 건너편의 iSCSI 대상(target)에게 접속을 요청하고, 인증이 끝나면 그 저장 공간이 로컬 디스크처럼 나타납니다. 짐을 실어 나르는 통로는 IP 네트워크이므로 스위치만 있으면 거리 제약이 크게 줄고, 케이블 대신 기존 랜을 쓸 수 있습니다.

다만 같은 회선을 다른 통신과 나눠 쓰면 지연이 생기므로, 실무에서는 전용 네트워크나 별도 VLAN으로 분리하는 경우가 많습니다. 결국 iSCSI는 SCSI 명령을 IP 패킷에 담아 보내 원격의 블록 저장소를 로컬 디스크처럼 쓰게 하는 방식이며, 성능을 위해 네트워크 분리가 함께 고려되어야 합니다.

SMB 공유

폴더를 네트워크에 공유하고 접근 권한 설정하기

회사에서 부서 자료를 각자 컴퓨터에만 두면, 담당자가 자리를 비우거나 PC가 꺼지는 순간 그 자료는 아무도 열 수 없는 섬이 됩니다. 이런 곤란을 없애기 위해 네트워크를 건너 다른 컴퓨터의 폴더를 내 폴더처럼 열어 주는 약속이 SMB(Server Message Block) 공유입니다. 아파트 단지에 공용 창고를 하나 두었다고 생각해 보십시오. 창고 문은 하나지만 입주민마다 다른 열쇠를 받고, 관리사무소가 누구에게 어느 선반을 열어 줄지 명단을 관리합니다.

윈도에서 폴더를 공유하면 그 폴더가 공용 창고가 되고, 공유 설정 화면에서 정하는 접근 권한이 바로 열쇠를 줄 사람의 명단이 됩니다. 사용자는 탐색기 주소창에 서버 이름과 공유 이름을 입력해 그 창고를 자기 드라이브처럼 연결하고, 파일을 읽고 쓰는 요청은 SMB라는 공용 언어로 서버에 전달됩니다. 정리하면 SMB 공유는 폴더 하나를 네트워크의 공용 창고로 열어 두고 사용자별 열쇠로 출입을 통제하는 방식입니다. 파일은 서버 한 곳에 모아 두고, 허용된 사용자만 그 목록을 보고 고칠 수 있게 됩니다.

공유 권한과 NTFS 권한

두 권한이 겹칠 때 실제로 적용되는 결과

폴더를 공유했는데 아무나 들어와 모든 파일을 지울 수 있다면 공유는 편리함보다 사고의 통로가 됩니다. 반대로 잠그기만 하고 아무에게도 열어 주지 않으면 자료가 있어도 쓸 수 없으니, 윈도는 공유 권한과 NTFS(New Technology File System) 권한이라는 두 겹의 자물쇠를 둡니다. 건물 정문 경비와 각 사무실 문 잠금을 떠올려 보십시오. 공유 권한은 정문에서 누구를 건물 안에 들일지 정하는 규칙이고, NTFS 권한은 방마다 누가 들어가 무엇을 할 수 있는지 정하는 규칙입니다.

두 규칙을 모두 통과해야 실제로 파일에 닿을 수 있으므로, 결과는 둘 중 더 좁게 잠근 쪽을 따릅니다. 예를 들어 공유 권한에서 모든 사람에게 변경을 허용했더라도 NTFS 권한이 읽기만 주었다면 사용자는 읽기까지만 할 수 있고, 반대의 경우도 마찬가지입니다. 또한 한 사용자가 여러 그룹에 속해 있으면 NTFS 권한은 거부를 제외하고 허용된 것들을 합쳐서 넓게 적용합니다. 결국 실제 적용되는 권한은 공유 권한과 NTFS 권한을 겹쳐 놓았을 때 가장 제한적인 값이고, 그래서 설계할 때는 공유 권한을 넉넉히 두고 NTFS 권한으로 세밀하게 조이는 방식을 흔히 씁니다. 두 권한의 차이를 알고 나누어 두면 같은 폴더를 부서별로 다르게 쓸 수 있습니다.

섀도 복사본

파일의 이전 버전을 남겨 두는 기능

보고서를 잘못 고쳐 저장한 뒤 원래대로 되돌리고 싶어도, 저장이 끝난 파일에는 되돌릴 지점이 남지 않습니다. 이런 실수를 줄이려고 윈도는 정해진 시점의 파일 상태를 따로 남겨 두는 섀도 복사본(Shadow Copy) 기능을 제공합니다. 물류 창고에서 매일 밤 재고 전체를 사진으로 찍어 두는 모습을 생각해 보십시오. 물건을 옮기거나 버려도 어젯밤 사진에는 그대로 남아 있어, 문제가 생기면 사진을 보고 그때 상태로 되돌릴 수 있습니다.

섀도 복사본은 파일을 통째로 복제하는 대신 볼륨의 상태를 시점 단위로 기록하고, 사용자는 탐색기의 이전 버전 항목에서 그 시점의 파일을 열어 복원합니다. 이 기록을 만드는 역할은 VSS(Volume Shadow Copy Service)가 맡고, 예약된 시간이나 특정 작업 직전에 자동으로 만들어지도록 설정할 수 있습니다. 정리하면 섀도 복사본은 저장 시점마다 볼륨의 상태를 남겨 두어 사용자가 스스로 과거 파일을 꺼내 쓰게 하는 장치입니다. 다만 같은 디스크에 함께 보관되는 경우가 많으므로, 디스크 자체가 고장 나는 상황까지 막아 주는 백업과는 역할이 다릅니다.

데이터 중복 제거

같은 데이터를 한 번만 저장해 공간을 줄이는 원리

같은 양식의 문서와 같은 첨부 파일이 수천 개씩 쌓이면 저장 공간은 금세 바닥나고, 백업에 걸리는 시간도 함께 늘어납니다. 데이터 중복 제거(Deduplication)는 이렇게 똑같은 내용이 반복되는 낭비를 없애 공간을 줄이는 기술입니다. 아파트 단지 택배 보관소에 같은 책이 백 권 들어왔다고 생각해 보십시오. 책을 백 권 쌓아 두는 대신 한 권만 서가에 두고 나머지 아홉십아홉 장에 같은 책을 가리키는 표를 붙이면, 찾는 사람은 그대로 책을 받으면서 공간은 한 권만 차지합니다.

중복 제거도 파일을 일정한 크기의 조각으로 나누고 각 조각의 지문을 계산해, 이미 있는 조각이면 새로 저장하지 않고 그 조각을 가리키는 정보만 남깁니다. 그래서 서로 다른 파일이라도 안쪽 내용이 같으면 공간이 겹쳐 줄어들고, 원본 파일을 열 때는 가리키던 조각을 다시 모아 완전한 파일로 보여 줍니다. 이 처리는 보통 파일 서버에서 주기적인 작업으로 돌며, 자주 쓰는 데이터는 압축하지 않고 그대로 두는 식으로 부하를 나눕니다. 결국 데이터 중복 제거는 같은 내용을 한 번만 저장하고 나머지는 그것을 가리키게 만드는 원리이며, 문서와 백업처럼 반복이 많은 데이터에서 효과가 큽니다. 반대로 이미 압축되었거나 조각마다 내용이 다른 데이터에서는 줄어드는 폭이 작습니다.

파일 서버 역할

파일 서버를 구축하고 관리하는 기본 절차

부서마다 자료를 각자 PC에 나눠 두면 최신본이 어느 것인지 알 수 없고, 직원이 늘 때마다 같은 자료를 다시 복사해야 합니다. 파일 서버 역할은 이렇게 흩어진 자료를 한 곳에 모아 여러 사람이 같은 기준으로 쓰게 만드는 윈도 서버의 기능 묶음입니다. 아파트 관리사무소를 새로 차리는 절차와 비슷합니다.

  • 먼저 사무실을 마련하듯 저장할 디스크와 볼륨을 준비하고, 서버 관리자에서 파일 서버 역할을 추가해 필요한 기능을 설치합니다.
  • 다음으로 자료를 넣을 선반을 만들듯 폴더를 만들고 공유를 열어 이름과 경로를 정하며, 출입 명단에 해당하는 권한을 사용자와 그룹에 맞춰 부여합니다.
  • 마지막으로 정전이나 고장에 대비한 백업 계획을 세우고, 남은 공간과 접속 상태를 주기적으로 확인하도록 감시 항목을 걸어 둡니다.

정리하면 파일 서버 역할은 저장 공간을 준비하고, 공유와 권한을 만들고, 백업과 감시로 유지하는 일련의 절차입니다. 이 순서를 지키면 자료의 위치와 접근 범위가 한 곳에서 관리되어, 사용자마다 다른 사본을 들고 헤매는 일이 줄어듭니다.

분산 파일 시스템(DFS)

DFS 네임스페이스가 그 대표 번호에 해당하며, 사용자는 하나의 시작 경로 아래 폴더를 따라 내려가 각 서버의 공유에 닿습니다. 관리자는 폴더마다 실제 대상을 여러 곳으로 지정해 두었다가 한 곳이 응답하지 않으면 다른 대상으로 연결되게 할 수 있고, 서버 사이의 내용을 맞추는 복제 기능을 함께 쓰면 지점 간 자료도 같은 상태로 유지됩니다. 정리하면 DFS는 여러 서버의 공유를 논리적인 하나의 폴더 구조로 묶고, 그 아래에서 실제 위치와 복제를 관리하는 방식입니다. 덕분에 사용자는 서버 이름이 바뀌거나 한 대가 멈춰도 같은 경로를 계속 쓸 수 있습니다.

직원이 급하게 문서를 고치려는데 다른 사람이 열어 두었다는 이유로 저장이 되지 않고, 공유 폴더 자체가 열리지 않아 부서 업무가 멈추는 일이 생깁니다. 파일 서버 장애 대응은 이런 잠금과 손상 상황에서 원인을 확인하고 서비스를 되살리는 절차입니다.

사무실 회의실을 떠올려 보면 상황이 잘 맞아떨어집니다. 안에서 누군가 문을 잠그고 나오지 않으면 밖에서는 아무리 급해도 들어갈 수 없으니, 관리자는 어떤 회의가 열려 있는지 확인해 사용이 끝난 세션을 정리합니다. 파일 잠금(lock)도 같은 원리로, 어떤 계정이 어떤 파일을 열고 있는지 확인해 열어 둔 프로그램을 닫게 하거나 필요하면 관리 권한으로 잠금을 해제합니다.

반대로 공유 자체가 손상된 경우는 무너진 선반을 다시 세우는 일에 가깝고, 이때는 최근 백업에서 폴더를 복원한 뒤 공유 권한과 접근 경로를 다시 확인합니다.

정리하면 파일 서버 장애 대응은 열린 세션과 잠금을 정리하는 절차와, 백업으로 공유를 되살리는 복구 절차를 함께 갖추는 일입니다. 서둘러 손대기보다 원인을 확인하고 되돌릴 지점을 먼저 확보하는 순서가 중요합니다.

가상화 개념

하이퍼바이저가 물리 자원을 나눠 주는 원리

서버 한 대를 프로그램 하나 때문에 사 두었는데 그 프로그램이 CPU를 거의 쓰지 않아 자원이 놀고, 새 업무가 생길 때마다 서버를 또 사야 하는 상황이 반복됩니다. 가상화(virtualization)는 한 대의 물리 서버를 여러 대처럼 나눠 쓰는 기술이며, 그 중심에는 자원을 배분하는 하이퍼바이저(hypervisor)가 있습니다.

건물주가 층마다 호실을 나눠 임대하는 아파트를 생각하면 됩니다. 건물은 하나지만 호실마다 별도 문과 계량기가 있어 세입자는 자기 집만 쓰는 것처럼 느끼고, 관리사무소는 전체 전기와 수도 용량을 호실별로 배분하고 한 집의 누수가 다른 집으로 번지지 않게 막습니다. 하이퍼바이저가 하는 일이 정확히 이 관리사무소 역할로, 물리 CPU와 메모리, 디스크를 쪼개 각 가상 머신(virtual machine)에 할당하고 서로의 영역을 침범하지 못하게 격리합니다.

그래서 한 가상 머신이 멈추더라도 같은 건물의 다른 가상 머신은 계속 돌아갑니다.

결국 가상화는 하이퍼바이저가 물리 자원을 논리적으로 분할해 여러 운영체제에 나눠 주는 구조입니다. 서버 한 대의 남는 자원을 낭비하지 않고, 격리라는 안전장치 위에서 여러 업무를 함께 돌리는 것이 핵심입니다.

Hyper-V 설치

역할을 켜고 가상 스위치를 구성하기

가상 머신을 써 보려고 마음먹었지만 어디서부터 손대야 할지 몰라 설치 화면 앞에서 멈추는 경우가 많습니다. Hyper-V는 Windows Server에 기본으로 들어 있는 가상화 기능으로, 역할을 켜고 가상 스위치까지 구성해야 비로소 쓸 수 있습니다.

새 사무실에 가구를 들이기 전에 전기와 수도 인입 공사를 먼저 하는 것과 같습니다. 서버 관리자(Server Manager)에서 Hyper-V 역할을 추가하는 일이 공사 승인에 해당하고, 설치가 끝나면 재부팅으로 기능이 정상 동작하는지 확인합니다. 그다음 가상 스위치(virtual switch)를 만들어 물리 네트워크 어댑터와 연결해야 가상 머신이 바깥과 통신할 수 있는데, 이는 사무실 벽에 콘센트와 수도꼭지를 다는 작업과 같습니다.

이 순서를 건너뛰면 가상 머신을 만들어도 네트워크가 잡히지 않습니다.

정리하면 Hyper-V 설치는 역할 추가, 재부팅, 가상 스위치 구성이라는 세 단계로 끝나는 준비 작업입니다. 물리 네트워크와 연결되는 스위치를 먼저 만들어 두어야 이후 가상 머신이 쓸 통로가 확보됩니다.

가상 머신 생성

가상 머신에 디스크와 메모리를 할당하기

신입 사원에게 자리와 책상을 내주는 일에 비유할 수 있습니다. 책상이 좁으면 서류를 펼 수 없듯이 메모리를 너무 적게 주면 운영체제가 버벅이고, 반대로 큰 책상만 잡아 두고 쓰지 않으면 그 자리는 다른 사람이 못 씁니다. 디스크도 마찬가지로 처음부터 정한 크기를 다 차지하는 고정 방식과, 실제로 쓴 만큼만 늘어나는 동적 방식이 있어 용도에 맞게 골라야 합니다.

생성 마법사에서 세대, 메모리, 가상 디스크, 네트워크 연결을 차례로 지정하면 하나의 가상 머신이 완성됩니다.

결국 가상 머신 생성은 물리 서버의 자원을 얼마씩 떼어 줄지 정하고 그 몫을 디스크와 메모리로 구체화하는 작업입니다. 넉넉하게 잡아 두는 것보다 실제 업무 부하를 기준으로 배분해야 남는 자원을 낭비하지 않습니다.

가상 스위치

외부·내부·전용 스위치의 차이

가상 머신을 여러 대 만들었더니 어떤 것은 회사 네트워크에서 접속이 되고 어떤 것은 서로만 통하고, 왜 이런 차이가 생기는지 알기 어렵습니다. 그 차이를 만드는 것이 가상 스위치(virtual switch)이며, Hyper-V는 외부·내부·전용 세 가지 종류를 제공합니다.

건물 출입구를 생각하면 세 가지가 금방 구분됩니다. 외부 스위치는 건물 정문처럼 물리 네트워크 어댑터에 연결되어 가상 머신이 회사 LAN과 인터넷으로 나갈 수 있게 하고, 내부 스위치는 건물 로비처럼 호스트와 가상 머신이 서로 통하되 바깥으로는 나가지 못합니다. 전용 스위치는 같은 층 세입자끼리만 오가는 복도에 가까워 가상 머신끼리는 통신하지만 호스트는 그 통로에 들어올 수 없습니다.

그래서 시험용 격리 환경은 내부나 전용으로, 실제 서비스는 외부로 연결하는 식으로 용도에 맞게 고릅니다.

정리하면 세 스위치의 차이는 호스트와 외부 네트워크에 각각 연결되느냐로 갈립니다. 외부는 바깥 통신까지, 내부는 호스트와의 통신까지, 전용은 가상 머신끼리의 통신만 허용한다고 기억하면 됩니다.

Hyper-V 네트워킹 고급

NIC 팀과 MAC 주소 설정 이해하기

한 대의 물리 서버 위에서 여러 가상 머신을 돌리는데 물리 랜카드가 하나뿐이라면, 모든 가상 머신의 통신이 그 한 줄에 몰려 느려지고 랜카드가 고장 나는 순간 서버 위의 가상 머신이 전부 동시에 끊깁니다. 이 곤란을 풀기 위해 Hyper-V는 여러 물리 네트워크 어댑터를 하나처럼 묶는 NIC 팀(NIC Teaming)과, 가상 머신마다 겹치지 않는 MAC 주소(네트워크 카드에 부여되는 고유 식별자)를 관리하는 체계를 함께 제공합니다.

아파트 한 동으로 생각하면 이해가 쉽습니다. 우편물이 쏟아지는데 출입구가 하나뿐이면 택배기사들이 그 앞에서 줄을 서고, 그 출입구가 공사로 막히면 배달이 전부 멈춥니다. NIC 팀은 출입구 여러 개를 하나의 안내데스크로 묶는 일이라서, 택배기사가 어느 출입구로 들어와도 같은 데스크에 닿고 한 곳이 막혀도 나머지 출입구로 배달이 이어집니다.

MAC 주소는 각 세대의 우편함 번호에 해당하는데, 번호가 겹치면 남의 우편물이 잘못 들어가듯 네트워크에서도 주소 충돌이 생기므로 Hyper-V는 가상 스위치를 통해 가상 머신마다 번호를 부여하고 필요하면 고정해 둡니다.

정리하면 NIC 팀은 여러 물리 어댑터를 논리적으로 하나로 묶어 대역폭과 이중화를 얻는 기능이고, MAC 주소 설정은 가상 스위치가 가상 머신마다 계층 2 식별자를 할당하거나 고정하도록 관리하는 일입니다. 이 둘을 함께 설계해야 한 줄에 몰리는 병목과 단일 어댑터 고장을 동시에 피할 수 있습니다.

검사점과 실시간 마이그레이션

가상 머신을 멈추지 않고 되돌리거나 옮기기

서버에 패치를 적용하기 직전의 상태로 되돌리고 싶을 때 되돌릴 지점이 없으면 손쓸 방법이 없고, 노후 서버를 교체하려고 가상 머신을 끄면 그 위에서 돌던 서비스가 그 시간만큼 멈춥니다. Hyper-V는 이 두 가지를 해결하려고 검사점(Checkpoint)과 실시간 마이그레이션(Live Migration)을 제공합니다.

이사를 떠올리면 두 기능이 구분됩니다. 검사점은 방 안의 가구 배치를 그대로 사진으로 찍어 두는 일이라서, 무엇이든 잘못됐을 때 사진을 보고 그 배치로 되돌립니다. 실시간 마이그레이션은 살아 있는 사람이 짐을 옮기는 동안에도 새 집에서 생활이 끊기지 않게 하는 이사라서, 먼저 메모리 상태를 새 호스트로 복사해 두고 그사이 바뀐 부분만 짧게 따라잡은 뒤 마지막 순간에 주인을 넘깁니다.

그래서 사용자는 잠깐의 연결 지연만 느끼고 가상 머신이 꺼졌다 켜지는 구간은 보지 못합니다.

정리하면 검사점은 가상 머신의 디스크와 메모리 상태를 특정 시점으로 되돌리는 스냅샷이고, 실시간 마이그레이션은 메모리 내용을 미리 옮기고 변경분만 동기화해 서비스 중단을 최소화하며 호스트를 바꾸는 기술입니다.

Hyper-V 복제

다른 호스트로 가상 머신을 계속 복제하기

본사 데이터센터에만 가상 머신이 있으면 화재나 정전처럼 그 건물 전체가 멈추는 사고가 났을 때 업무 시스템을 되살릴 방법이 없습니다. Hyper-V 복제(Hyper-V Replica)는 이 상황을 대비해 다른 호스트로 가상 머신을 계속 복사해 두는 기능이며, 장애가 나면 그 복사본을 켜서 업무를 이어가게 합니다.

회사 서류를 매일 다른 지점으로 복사해 두는 모습과 같습니다. 원본 사무실의 서류철이 갱신되면 정해진 주기마다 변경분이 지점으로 배달되고, 지점은 그것을 받아 같은 순서로 다시 정리해 둡니다. 본사가 불에 타도 지점 서류철이 남아 있어 업무를 이어갈 수 있고, 본사가 복구되면 방향을 반대로 돌려 지점의 내용을 다시 가져올 수도 있습니다.

정리하면 Hyper-V 복제는 기본 서버(Primary)의 가상 머신을 복제 서버(Replica)로 주기적으로 전송해 두는 재해 복구 수단이며, 전송 주기와 보존할 복구 지점 수를 정해 두고 필요할 때 복제본을 장애 조치(failover)로 기동합니다.

장애 조치 클러스터

클러스터로 가상 머신 가용성을 높이기

가상 머신을 한 호스트에만 올려 두면 그 호스트가 점검으로 재부팅되는 순간 가상 머신도 함께 내려가고, 관리자는 야간에 손으로 다시 켜야 합니다. 장애 조치 클러스터(Failover Cluster)는 여러 호스트를 하나의 팀으로 묶어 이런 단일 고장을 견디게 하는 구조입니다.

은행 창구 여러 개가 같은 금고를 함께 쓰는 모습을 생각하면 됩니다. 창구 직원들은 서로 살아 있는지 계속 신호를 주고받고, 한 창구가 갑자기 문을 닫으면 남은 창구가 그 손님과 업무를 넘겨받아 처리합니다. 누가 대표인지 정하는 규칙도 필요한데, 이것이 쿼럼(Quorum)이라서 창구가 반으로 갈라졌을 때 어느 쪽이 진짜라는 판단이 서지 않으면 양쪽 모두 업무를 멈춰 데이터가 둘로 갈라지는 사고를 막습니다.

가상 머신의 디스크도 한 곳에 묶어 두고 여러 호스트가 함께 읽고 쓰는 공유 스토리지 형태로 구성하는 것이 일반적입니다.

정리하면 장애 조치 클러스터는 호스트 사이의 하트비트(생존 신호)와 쿼럼 판정으로 장애를 감지하고, 가상 머신 역할을 다른 노드로 자동 이동시켜 가용성을 높이는 기술입니다.

컨테이너 개요

가상 머신과 컨테이너의 차이와 쓰임

응용 프로그램을 서버마다 손으로 설치하면 라이브러리 버전이 조금씩 달라 같은 프로그램이 어느 서버에서는 뜨고 어느 서버에서는 뜨지 않는 일이 생깁니다. 컨테이너(Container)는 이 문제를 줄이려고 응용 프로그램과 그 실행에 필요한 요소를 한 덩어리로 묶어 어디서든 같은 방식으로 실행되게 하는 기술이며, 가상 머신과 자주 비교됩니다.

가상 머신은 건물마다 기초 공사부터 새로 하는 방식이고, 컨테이너는 규격이 정해진 화물 상자를 쓰는 방식에 가깝습니다. 가상 머신은 하이퍼바이저 위에 운영체제를 통째로 올리므로 서로 완전히 격리되지만 그만큼 무겁고 부팅이 느립니다.

컨테이너는 호스트의 운영체제 커널을 함께 쓰면서 프로세스와 파일 시스템만 격리하므로 상자가 가볍고 몇 초 만에 뜨며, 같은 상자를 여러 개 복제해 늘리는 일도 쉽습니다. 대신 커널을 공유하기 때문에 격리 수준은 가상 머신보다 낮고, 호스트 커널과 다른 종류의 운영체제를 그대로 올릴 수는 없습니다.

정리하면 컨테이너는 커널을 공유하며 응용 프로그램 실행 환경을 격리하는 가벼운 단위이고, 강한 격리와 다양한 운영체제가 필요하면 가상 머신을, 빠른 배포와 높은 밀도가 필요하면 컨테이너를 선택합니다.

Windows 컨테이너 실습

이미지와 컨테이너를 만들고 실행하기

실습은 보통 틀을 만드는 단계부터 시작하는데, 베이스 이미지를 내려받아 필요한 파일과 설정을 추가하는 명령을 Dockerfile 같은 정의 파일에 적고 빌드해 새 이미지를 만듭니다. 그다음 실행 명령으로 컨테이너를 띄우면 격리된 환경에서 응용 프로그램이 돌아가고, 실행 중인 컨테이너 목록을 확인해 상태를 살피며 필요 없으면 정지하고 제거합니다. 이미지는 레지스트리(이미지를 보관하고 내려받는 저장소)에 올려 다른 서버에서도 같은 틀을 그대로 받아 쓸 수 있습니다.

정리하면 이미지는 변경되지 않는 실행 환경 정의이고 컨테이너는 그 이미지로부터 만들어진 실행 인스턴스이며, 빌드와 실행과 정리라는 세 동작이 Windows 컨테이너 실습의 기본 흐름입니다.

TCP/IP 기초

IP 주소·서브넷 마스크·게이트웨이 이해하기

사무실 컴퓨터 한 대가 인터넷에 연결되지 않으면 다른 사람들은 같은 스위치에 꽂혀 있는데도 아무 일이 없다는 듯이 지나갑니다. 이런 때 필요한 것이 컴퓨터끼리 주소를 주고받고 데이터를 나누는 공통 규칙인 TCP/IP(Transmission Control Protocol/Internet Protocol)입니다. TCP/IP는 택배 회사의 배송 체계와 비슷합니다. IP 주소는 택배 송장에 적힌 도로명 주소이고, 서브넷 마스크는 어디까지가 같은 동네인지 알려 주는 경계선이며, 게이트웨이는 우리 동네 밖으로 나가는 물류 창고입니다. 택배 기사는 송장의 주소를 보고 같은 동네면 직접 배달하고 다른 동네면 창고로 넘기며, TCP는 짐이 중간에 흩어져도 순서대로 다시 맞춰 받는 사람이 온전한 상자를 받게 합니다. 정리하면 IP 주소는 목적지를, 서브넷 마스크는 같은 네트워크의 범위를, 게이트웨이는 다른 네트워크로 나가는 출구를 뜻합니다. 이 세 가지가 맞물려야 서버는 비로소 바깥 세상과 대화할 수 있습니다.

서브넷과 CIDR

네트워크 주소를 나누는 계산 방법

회사에 컴퓨터가 스무 대뿐인데 6만 개가 넘는 주소를 한 덩어리로 받으면 나머지 주소는 놀게 되고, 같은 주소 범위 안의 모든 장비가 서로의 잡음을 다 듣게 됩니다. 이 문제를 해결하려고 네트워크를 작은 단위로 쪼개는 서브넷(subnet)과, 그 크기를 비트 수로 적는 CIDR(Classless Inter-Domain Routing) 표기법이 나왔습니다. 서브넷은 한 동짜리 아파트를 층이나 호수 단위로 다시 나누는 일과 같습니다. CIDR의 슬래시 뒤 숫자는 건물 전체에서 몇 층까지를 한 구역으로 볼지 정하는 표지판이고, 그 숫자가 클수록 한 구역에 들어가는 집이 적어집니다.

각 구역에는 그 구역을 대표하는 대표 호수인 네트워크 주소와 맨 끝 호수인 브로드캐스트 주소가 따로 있어 실제로 사람이 쓸 수 있는 집은 둘만큼 줄어듭니다. 관리자는 이 구역 표지판만 바꿔서 같은 주소 대역을 부서별로 나눠 줄 수 있습니다. 결국 서브넷은 하나의 주소 대역을 목적에 맞게 분할하는 방식이고, CIDR은 그 분할 크기를 접두사 길이로 간결하게 적는 규칙입니다. 주소를 아끼고 잡음을 줄이는 것이 두 개념의 공통된 목적입니다.

라우팅 기초

서버가 다른 네트워크로 패킷을 보내는 원리

서버가 다른 네트워크의 주소로 패킷을 보냈는데 어디로 넘겨야 할지 모르면 그 패킷은 그 자리에서 사라지고, 사용자는 응답 없는 화면만 보게 됩니다. 이 길 안내를 맡는 것이 라우팅(routing)이며, 라우터는 목적지까지의 경로를 담은 라우팅 테이블을 보고 다음 홉을 정합니다. 라우팅은 우체국 간의 분류 체계와 같습니다. 각 우체국은 자기 책상 위의 배송표인 라우팅 테이블에 어느 지역으로 가는 우편은 어느 우체국으로 넘기라고 적어 두고, 표에 없는 주소는 기본적으로 상급 우체국인 기본 게이트웨이로 보냅니다.

보낸 편지는 목적지까지 한 번에 가지 않고 여러 우체국을 거치며, 각 우체국은 자기 앞의 한 구간만 책임집니다. 경로가 여러 개면 더 짧거나 신뢰할 만한 쪽을 골라 표에 우선순위로 적어 둡니다. 정리하면 라우팅은 목적지 주소를 기준으로 다음 장비를 결정하는 과정이고, 이 결정을 모아 둔 것이 라우팅 테이블입니다. 서버도 자기 테이블에 없는 목적지는 게이트웨이로 넘긴다는 점에서 작은 라우터처럼 동작합니다.

NIC 팀 구성

여러 랜카드를 묶어 대역폭과 이중화를 확보하기

랜카드 한 장에 의존하는 서버는 그 카드나 케이블이 고장 나는 순간 네트워크에서 통째로 끊기고, 트래픽이 몰리는 시간에는 대역폭이 모자라 서비스가 느려집니다. 이 두 가지를 함께 해결하려고 여러 개의 NIC(Network Interface Card)를 하나처럼 묶는 NIC 팀 구성(NIC teaming)을 씁니다. NIC 팀은 차로를 여러 개 둔 고속도로와 같습니다. 차로를 늘리면 한 번에 지나가는 차의 양이 늘어나 대역폭이 커지고, 한 차로가 공사로 막혀도 나머지 차로로 차가 흐르듯 카드 하나가 죽어도 통신이 유지됩니다.

어느 차로로 차를 보낼지 정하는 신호등 역할을 팀 구성 소프트웨어가 맡고, 스위치 쪽에서도 같은 묶음으로 인식하도록 설정을 맞춰야 합니다. 묶는 방식에 따라 대역폭을 합치는 구성과 한쪽이 대기하는 이중화 구성으로 나뉩니다. 결국 NIC 팀 구성은 물리적인 랜카드 여러 장을 논리적인 하나의 연결로 묶어 처리량과 가용성을 함께 높이는 기술입니다. 서버와 스위치 양쪽 설정이 어긋나면 오히려 장애가 생기므로 구성 방식을 서로 맞추는 것이 중요합니다.

네트워크 정책 서버(NPS)

RADIUS로 접속 인증을 중앙에서 처리하기

사무실 곳곳에 무선 공유기와 VPN 장비가 늘어나면 각 장비마다 계정을 따로 만들고 관리해야 하고, 퇴사자의 계정이 어딘가에 남아 있는 일이 생깁니다. 이 문제를 없애려고 접속 인증을 한 곳에서 처리하는 NPS(Network Policy Server)와 그 표준인 RADIUS(Remote Authentication Dial-In User Service)가 쓰입니다. NPS는 건물마다 따로 있던 경비실을 하나의 통합 출입 데스크로 바꾼 것과 같습니다. 각 층의 출입문인 무선 공유기와 VPN 장비는 스스로 판단하지 않고 데스크에 이 사람을 들여보내도 되는지 물어보고, 데스크는 중앙 명부인 디렉터리 서비스와 정책을 확인해 허용이나 거절을 답합니다.

그래서 명부 한 곳만 고치면 모든 출입문의 규칙이 동시에 바뀌고, 어느 문에서 누가 언제 들어왔는지도 한곳에 기록됩니다. 이때 문 쪽 장비를 RADIUS 클라이언트, 데스크 역할을 하는 서버를 RADIUS 서버라고 부릅니다. 정리하면 NPS는 RADIUS 프로토콜로 여러 접속 장비의 인증과 권한 판단을 중앙 서버에 모으는 역할을 합니다. 계정 관리와 감사 기록을 한 지점으로 모아 일관된 접속 정책을 유지하는 것이 핵심입니다.

VPN 서버

원격 사용자를 사내망에 안전하게 연결하기

재택근무자가 집에서 사내 파일 서버에 접속하려면 인터넷이라는 공개된 길을 지나야 하는데, 암호화 없이 보낸 데이터는 중간에서 들여다보이거나 바꿔치기될 수 있습니다. 이 위험을 줄이면서 외부 사용자를 사내망 안쪽으로 데려오는 장치가 VPN(Virtual Private Network) 서버입니다. VPN은 공용 도로 위에 놓인 전용 터널과 같습니다. 사용자 컴퓨터와 VPN 서버가 먼저 서로를 확인하고 암호 키를 맞춘 뒤, 그 사이를 지나는 모든 데이터를 터널 안에 넣어 감싸므로 밖에서는 내용이 보이지 않습니다.

터널을 빠져나온 데이터는 사내망에 들어선 것으로 취급되어 사설 IP 주소를 받고, 서버는 사용자가 실제로 어디에 있든 사내 자원에 접근하는 것처럼 동작합니다. 터널을 여는 쪽을 클라이언트, 받아 주는 쪽을 VPN 서버라고 합니다. 결국 VPN 서버는 공용 인터넷 위에 암호화된 통로를 만들어 원격 사용자를 사내망의 일부로 편입시키는 기술입니다. 인증과 암호화가 함께 갖춰져야 이 통로가 실제로 안전해집니다.

DirectAccess

사용자가 의식하지 않아도 연결되는 원격 접속 구성

출장이나 재택근무 중인 직원이 사내 파일 서버에 접속하려면 VPN 프로그램을 직접 실행하고, 계정을 입력하고, 연결이 맺어질 때까지 기다리는 과정을 매번 반복해야 합니다. 이런 번거로움 때문에 직원들은 사내 자원 접속을 미루게 되고, 보안 담당자는 누가 언제 어떤 경로로 들어왔는지 일관되게 통제하기 어려워집니다. DirectAccess는 사용자가 연결을 의식하지 않아도 인터넷이 닿는 순간 사내망으로 향하는 암호화 통로를 자동으로 열어 주는 원격 접속 기술입니다.

이 기술은 사원증을 목에 걸고 다니는 사무실의 자동문과 같습니다. 직원이 문 앞에 서기만 하면 사원증을 읽고 문이 알아서 열리듯이, 노트북이 인터넷에 연결되면 DirectAccess 클라이언트가 사내 터널을 스스로 맺습니다.

이때 사내의 정책 서버가 노트북의 백신 상태와 패치 여부를 확인하고, 기준을 통과한 기기에만 접속을 허용합니다. 접속에 필요한 설정은 그룹 정책(Group Policy)으로 중앙에서 배포되며, 실제 통로는 IPsec으로 암호화되어 사용자는 어떤 절차도 밟지 않습니다.

정리하면 DirectAccess는 별도 로그인 없이 인터넷이 닿는 곳이면 어디서든 사내 자원으로 암호화된 경로를 자동으로 열어 주는 기술이며, 기기 상태 점검과 정책 배포를 함께 묶어 운영하는 것이 핵심입니다.

원격 데스크톱 서비스(RDS)

여러 사용자가 서버에서 데스크톱을 쓰게 하기

이 구조는 책상과 서류함을 갖춘 공유 오피스 건물과 같습니다. 건물에는 가구와 비품이 한 벌씩만 있어도 입주자마다 자기 호실 열쇠를 받아 자기 공간처럼 쓰듯이, 서버에는 응용 프로그램과 데이터가 한 벌만 설치되고 사용자는 원격 데스크톱 클라이언트로 자기 세션에 접속합니다.

세션 호스트 역할을 하는 서버가 사용자마다 화면과 키보드 입력을 따로 처리하므로 서로의 작업이 섞이지 않습니다. 사용자가 여러 명일 때는 연결 브로커가 어느 서버의 세션으로 보낼지 정해 주고, 세션은 사용자가 로그오프할 때까지 유지됩니다.

결국 RDS는 프로그램을 사용자 PC가 아니라 서버에 두고 화면만 전달하는 방식으로, 설치와 패치와 백업을 한곳에서 처리하게 해 주는 기술입니다.

이는 건물 정문의 경비실과 같습니다. 방문객은 여러 출입구를 돌아다니지 않고 정문 하나만 지나며, 경비가 신분을 확인한 뒤 안내해 주듯이 게이트웨이는 443 포트로 들어온 요청을 받아 사용자를 인증하고 내부의 원격 데스크톱 서버로 연결을 넘깁니다. 웹 액세스는 로비에 붙은 안내판처럼 사용자가 이용할 수 있는 데스크톱 목록을 브라우저에 보여 주고, 클릭하면 연결 파일을 내려 주거나 원격 데스크톱 웹 클라이언트로 이어 줍니다.

내부 서버는 인터넷에 직접 노출되지 않고 게이트웨이 뒤에 숨어 있으므로, 외부에 공개되는 지점을 한 곳으로 줄일 수 있습니다.

즉 RDS 게이트웨이는 외부 접속을 HTTPS 한 지점으로 모아 인증과 중계를 처리하는 관문이고, 웹 액세스는 그 관문을 브라우저라는 익숙한 도구로 이용하게 해 주는 구성입니다.

원격 접속 문제 해결

연결 실패 원인을 단계별로 좁히기

원격 접속이 갑자기 끊기면 사용자는 물론 관리자도 원인이 네트워크인지, 계정 권한인지, 서버 설정인지 한눈에 알기 어렵습니다. 이럴 때는 증상을 한 번에 고치려 들지 말고, 연결이 지나가는 구간을 앞에서부터 하나씩 확인하며 원인을 좁혀야 합니다.

이 과정은 택배가 어디쯤 와 있는지 배송 이력을 보는 일과 비슷합니다. 집 주소가 맞는지 확인하는 단계가 서버 이름이 IP 주소로 제대로 풀리는지 보는 일이고, 물류센터를 지났는지 보는 단계가 해당 포트까지 실제로 닿는지 확인하는 일입니다. 다음으로 받는 사람이 맞는지 보듯 계정과 권한을 확인하고, 마지막으로 물건을 두는 창고가 열려 있는지 보듯 서버의 원격 데스크톱 서비스 상태와 세션 한도, 방화벽과 게이트웨이 설정을 확인합니다.

각 단계에서 성공과 실패가 갈리면 그 지점이 원인 후보가 되므로, 추측으로 설정을 바꾸지 않고 확인된 지점만 손봅니다.

정리하면 원격 접속 문제 해결은 이름 풀이, 포트 도달, 인증, 서비스 상태 순으로 구간을 나눠 확인하는 절차이며, 이 순서를 지키는 것만으로도 불필요한 설정 변경을 크게 줄일 수 있습니다.

IIS 개요

윈도우 웹 서버의 구조와 요청 처리 흐름

사용자에게 웹 페이지를 보여 주려면 요청을 받아 파일을 찾아 돌려주는 서버 프로그램이 필요합니다. IIS(Internet Information Services)는 윈도우 서버에 기본으로 들어 있는 웹 서버로, 이런 요청 처리를 운영체제 차원에서 담당합니다.

IIS의 동작은 홀에서 주문을 받고 주방에서 음식을 만드는 식당과 같습니다. 손님의 주문을 가장 먼저 받아 접수하는 곳이 HTTP 요청을 받는 커널 드라이버인 http.sys이고, 접수된 주문이 어느 매장의 것인지 확인하는 역할이 사이트와 바인딩을 연결하는 서비스입니다. 실제로 파일을 읽고 응용 프로그램을 실행하는 주방은 작업자 프로세스(w3wp)이며, 이 프로세스는 응용 프로그램 풀 단위로 나뉘어 돌아갑니다.

정적 파일은 그 자리에서 바로 전달되고, 동적 페이지는 등록된 모듈을 거쳐 처리된 결과가 응답으로 나갑니다.

결국 IIS는 요청 접수, 사이트 판별, 작업자 프로세스 처리라는 층으로 나뉜 윈도우의 웹 서버이며, 이 구조를 이해하면 사이트와 응용 프로그램 풀을 어디에 나눠야 하는지도 자연스럽게 보입니다.

IIS 사이트와 응용 프로그램 풀

웹 사이트를 만들고 격리해 운영하기

한 서버에 여러 웹 사이트를 올렸을 때 한 사이트의 프로그램 오류가 다른 사이트까지 멈추게 하면 곤란합니다. 그래서 IIS는 사이트와 응용 프로그램 풀이라는 두 단위로 웹 서비스를 만들고 서로 격리해 운영합니다.

이는 한 건물에 여러 호실이 들어간 오피스 빌딩과 같습니다. 사이트는 호실의 주소에 해당하며, IP 주소와 포트, 호스트 이름을 조합한 바인딩으로 어느 요청이 어느 호실로 갈지 정합니다. 응용 프로그램 풀은 호실마다 따로 설치된 전기 차단기와 같아서, 한 호실에서 과부하가 걸려도 다른 호실의 불은 꺼지지 않습니다.

실제로는 풀마다 별도의 작업자 프로세스가 배정되므로 한 사이트가 자원을 과도하게 쓰거나 예외로 죽어도 다른 사이트는 영향을 받지 않고, 정해진 시간이나 메모리 기준에 따라 프로세스를 스스로 재활용합니다.

정리하면 사이트는 요청을 받을 주소와 콘텐츠를 묶는 단위이고, 응용 프로그램 풀은 그 사이트를 실행하는 프로세스를 격리하는 단위이며, 이 둘을 목적에 맞게 나누는 것이 안정적인 웹 서버 운영의 출발점입니다.

IIS 보안과 인증서

HTTPS 바인딩과 인증 방식 설정하기

사내 업무 시스템을 IIS(인터넷 정보 서비스, Internet Information Services)로 열어 두었는데 로그인 화면에서 아이디와 비밀번호가 암호화되지 않은 채 네트워크를 그대로 흘러간다면, 같은 사무실의 누군가가 그것을 들여다볼 수 있습니다. 이 문제를 막기 위해 웹 서버에 인증서를 연결해 통신 전체를 암호화하고 접속자를 확인하는 설정이 HTTPS 바인딩과 인증 방식입니다.

회사 건물에 비유하면 HTTPS 바인딩은 정문에 설치한 보안 게이트이고, 인증서는 그 건물이 정말 우리 회사 건물임을 증명하는 현판입니다. 방문자는 현판을 보고 사칭이 아님을 확인한 뒤 게이트를 통과하고, 그다음 경비원이 사원증을 요구해 들어올 수 있는 사람인지 다시 확인합니다. IIS에서는 사이트마다 443 포트에 인증서를 묶는 바인딩을 만들고, 익명 인증을 끄고 윈도우 인증이나 클라이언트 인증서 매핑 같은 방식을 켜서 이 두 단계를 구성합니다.

인증서가 만료되면 게이트 현판이 떨어져 나간 셈이라 방문자에게 경고가 뜨므로 갱신 일정을 미리 잡아 두어야 합니다.

정리하면 HTTPS 바인딩은 서버와 브라우저 사이의 통신을 인증서로 암호화하는 연결 설정이고, 인증 방식은 그 연결 위에서 사용자가 누구인지 서버가 판별하는 절차입니다. 두 가지를 함께 갖추어야 도청과 사칭을 동시에 막을 수 있습니다.

Active Directory 인증서 서비스(AD CS)

내부 인증서를 발급하는 PKI 구축

직원 수백 명이 쓰는 사내 시스템마다 공인 인증기관에서 인증서를 사서 붙이다 보면 비용도 부담이고, 내부 서버 이름처럼 외부에 공개되지 않은 대상은 공인 인증서를 발급받기도 어렵습니다. 이때 회사 안에 자체 인증기관을 세워 내부용 인증서를 직접 발급하고 관리하는 체계가 Active Directory 인증서 서비스(AD CS, Active Directory Certificate Services)입니다.

회사에 비유하면 AD CS는 사내 증명서 발급 부서이고, 루트 인증기관은 그 부서의 최종 직인을 가진 본부, 하위 인증기관은 지점의 발급 창구입니다. 신청자가 필요한 증명서 종류를 적어 창구에 내면 창구는 본부의 직인으로 서명한 증명서를 만들어 주고, 이 증명서를 받아 간 사람은 다른 부서에서도 신분을 인정받습니다. 이때 어떤 증명서를 어떤 조건으로 내줄지 정한 서식이 인증서 템플릿이고, 신청자의 계정 정보는 Active Directory에서 그대로 가져옵니다.

그래서 AD CS를 세울 때는 먼저 루트 인증기관을 만들고 그 아래 발급용 인증기관을 두는 계층을 설계하는 것이 기본입니다.

정리하면 AD CS는 Active Directory를 기반으로 사내 인증기관을 구축해 서버와 사용자, 장비용 인증서를 직접 발급하는 PKI(공개 키 기반 구조, Public Key Infrastructure)입니다. 외부 의존과 비용을 줄이면서 내부 통신의 암호화와 신원 확인을 한 체계 안에서 관리할 수 있습니다.

인증서 템플릿과 자동 등록

인증서를 자동으로 발급하고 갱신하기

인증서를 필요한 사람에게 하나씩 손으로 발급하다 보면 수백 명분을 처리하는 데 시간이 걸리고, 만료일을 놓쳐 서비스가 갑자기 멈추는 일도 생깁니다. 이 반복 작업을 사람 손에서 떼어 내기 위해 인증서 템플릿과 자동 등록(Auto-Enrollment) 기능을 함께 씁니다.

정기 배송에 비유하면 인증서 템플릿은 어떤 물건을 어떤 포장으로 보낼지 정해 둔 상품 규격서이고, 자동 등록은 그 규격에 맞춰 주문이 자동으로 나가고 도착 전에 다음 물건이 미리 준비되는 체계입니다. 관리자가 템플릿에서 용도와 유효기간, 신청 권한을 정해 두면 사용자나 서버는 그 규격을 신청서에 적어 넣기만 하면 됩니다. 자동 등록 정책을 그룹 정책으로 배포하면 컴퓨터가 로그온할 때나 정해진 시점에 스스로 신청하고, 만료가 가까워지면 같은 방식으로 갱신합니다.

덕분에 관리자는 개별 신청을 처리하는 대신 규격과 권한만 관리하면 됩니다.

정리하면 인증서 템플릿은 발급 조건을 미리 정의한 설계도이고, 자동 등록은 그 설계도에 따라 클라이언트가 스스로 인증서를 신청하고 갱신하게 만드는 정책입니다. 두 가지를 갖추면 발급과 갱신이 사람 손을 거치지 않아 만료로 인한 장애가 크게 줄어듭니다.

WSUS 개요

윈도우 업데이트를 중앙에서 배포하는 구조

회사 컴퓨터 수백 대가 각자 마이크로소프트 업데이트 서버에 접속해 패치를 받으면 인터넷 회선이 몰리고, 어떤 PC는 패치가 됐고 어떤 PC는 안 된 상태가 섞여 버립니다. 이 문제를 중앙에서 정리하기 위해 사내에 업데이트 배포 서버를 두는 구조가 WSUS(윈도우 서버 업데이트 서비스, Windows Server Update Services)입니다.

택배 집하장에 비유하면 WSUS 서버는 각 가정으로 바로 가지 않고 물건을 모아 두는 동네 집하장입니다. 마이크로소프트의 업데이트 서버에서 필요한 패치를 집하장까지 한 번만 받아 오고, 사내 컴퓨터들은 인터넷 대신 집하장에서 패치를 가져갑니다. 집하장은 어떤 물건을 누구에게 보낼지 목록으로 관리하므로 관리자는 승인한 업데이트만 직원 PC에 내려보낼 수 있습니다.

이 구조 덕분에 외부 회선 사용이 줄고 배포 여부를 서버 한 곳에서 확인할 수 있습니다.

정리하면 WSUS는 업데이트를 중앙 서버에 모아 두고 클라이언트가 그 서버에서 받아 가게 하는 배포 구조입니다. 승인과 그룹 관리로 패치 적용 시점을 회사 사정에 맞게 통제할 수 있다는 점이 핵심입니다.

WSUS 구성과 승인

업데이트 그룹과 승인 규칙 운영하기

업데이트를 한꺼번에 모든 PC에 밀어 넣으면 업무 시간에 재부팅이 몰리거나, 특정 프로그램과 충돌하는 패치가 전사로 퍼질 수 있습니다. 그래서 WSUS에서는 컴퓨터를 그룹으로 나누고 업데이트를 승인하는 절차를 먼저 구성합니다.

학교 급식에 비유하면 컴퓨터 그룹은 학년과 반이고, 승인은 오늘 어떤 메뉴를 어느 반까지 내보낼지 정하는 결정입니다. 영업팀 PC와 서버실 장비를 서로 다른 반으로 나누어 두면 먼저 시범 반에만 배식하고, 문제가 없으면 나머지 반으로 넓힐 수 있습니다. 승인 규칙을 정해 두면 중요한 보안 업데이트는 자동으로 통과시키고 나머지는 관리자가 검토하게 만들 수도 있습니다.

어떤 업데이트를 거부하면 그 항목은 해당 그룹에 배포되지 않으므로 문제가 생긴 패치는 즉시 차단할 수 있습니다.

정리하면 WSUS 구성의 핵심은 컴퓨터 그룹으로 대상을 나누고 업데이트마다 승인 상태를 관리하는 것입니다. 그룹과 승인 규칙을 잘 설계해야 패치를 안전하게 단계적으로 퍼뜨릴 수 있습니다.

패치 주기와 롤백 계획 세우기

Exchange Server 개요

사내 메일 서버의 구성 요소와 배포 형태

회사에서 메일 한 통을 보낼 때마다 상대 주소를 확인하고 스팸을 걸러 내고 보낸 편지함에 사본을 남기는 일을 각자 컴퓨터가 떠맡는다고 생각하면 금세 엉망이 됩니다. Exchange Server는 이런 접수와 보관, 전달을 한곳에서 맡아 주는 사내 메일 서버 제품으로, 마이크로소프트의 메일과 일정 플랫폼 계열에 속합니다.

아파트 단지에 비유하면 각 세대에 우편함이 있고 관리사무소가 배달과 보관을 도맡는 구조와 같습니다. 직원마다 주어지는 사서함(mailbox)은 세대별 우편함에 해당하고, 그 우편함들을 한 건물에 모아 둔 데이터베이스는 관리사무소의 보관 창고입니다. 메일을 받아 상대편으로 넘기는 전송 서비스는 택배 기사와 관리사무소를 잇는 배달 통로이고, 직원이 쓰는 Outlook 같은 프로그램은 우편함을 열어 보는 열쇠입니다.

이 부품들을 회사 건물 안에 직접 세우면 온프레미스(on-premises) 배포가 되고, 마이크로소프트가 운영하는 클라우드를 빌려 쓰면 Exchange Online 구독이 됩니다.

정리하면 Exchange Server는 사서함과 데이터베이스, 전송 서비스가 맞물려 메일을 접수하고 보관하고 배달하는 메일 서버입니다. 같은 기능을 직접 설치하느냐 클라우드로 빌리느냐가 배포 형태의 차이입니다.

메일 서비스 운영

메일 흐름과 큐를 점검하고 문제를 해결하기

사용자가 메일이 오지 않는다고 하는데 서버 어디가 막혔는지 알 수 없으면 사서함을 하나하나 열어 보는 수밖에 없어 시간만 흘러갑니다. 메일 서비스 운영은 메일이 어느 경로로 흘러가고 어디에 쌓여 있는지 확인해 막힌 지점을 찾아내는 일입니다.

택배 물류센터에 비유하면 메일 흐름(mail flow)은 벨트를 따라 움직이는 컨베이어, 큐(queue)는 아직 분류되지 않고 쌓여 있는 택배 더미와 같습니다. 큐가 끝없이 늘어나면 배달이 밀린 것이므로 Queue Viewer 같은 도구로 쌓인 항목과 실패 사유를 확인합니다. 주소를 찾지 못해 반송되는 항목은 NDR(배달 못 함 보고서)로 발신자에게 돌아가고, 사내 서버에서 외부로 나가는 길은 send connector와 스마트 호스트(smart host) 설정이 맡습니다.

그래서 점검은 큐 길이, 재시도 횟수, 커넥터 설정, 이름 해석 순서로 좁혀 갑니다.

정리하면 메일 서비스 운영은 메일 흐름을 따라가며 큐와 커넥터, 이름 해석을 차례로 확인해 막힌 곳을 푸는 일입니다.

서버 보안 기준

최소 권한과 공격 표면 축소 원칙

서버에 접속하는 사람 모두에게 관리자 권한을 주면 실수 한 번이나 계정 하나가 뚫리는 것만으로 서버 전체가 넘어갑니다. 서버 보안 기준은 이런 사고를 줄이려고 누구에게 무엇을 허용할지 미리 정해 두는 규칙입니다.

아파트 관리에 비유하면 최소 권한(least privilege)은 각 세대에 자기 집 열쇠만 주고 공용 창고 열쇠는 필요한 사람에게만 건네는 것과 같습니다. 공격 표면 축소(attack surface reduction)는 쓰지 않는 창문과 문을 아예 벽으로 막아 침입자가 들어올 구멍 자체를 줄이는 일입니다. 여기에 서비스 계정은 사람 이름 대신 용도별로 만들고, 관리자 작업은 따로 분리된 계정으로만 하며, 쓰지 않는 역할(role)과 기능은 설치하지 않는 원칙이 붙습니다.

설정을 바꿀 때는 기준 문서에 적힌 값과 실제 서버를 비교해 어긋난 부분을 근거와 함께 되돌립니다.

정리하면 서버 보안 기준은 최소 권한과 공격 표면 축소라는 두 축으로 권한과 노출을 함께 줄이는 것입니다. 이 두 원칙이 서면 사고가 났을 때 피해 범위도 훨씬 좁아집니다.

Windows Defender와 방화벽

서버에서 악성코드와 포트를 통제하기

서버가 인터넷에 연결된 순간부터 악성코드 감염 시도와 포트 스캔이 끊이지 않는데, 보호 장치 없이 두면 몇 분 만에 뚫릴 수 있습니다. Windows Defender는 서버 안에서 돌아가는 악성코드 방어 기능이고, Windows 방화벽은 서버로 드나드는 네트워크 연결을 통제하는 기능입니다.

건물 경비에 비유하면 Defender는 건물 안으로 들어온 사람의 소지품을 검사하는 검색대, 방화벽은 정해진 출입구 외에는 문을 열어 주지 않는 경비원입니다. 검색대는 실시간 검사(real-time protection)로 파일이 열리는 순간 확인하고, 의심스러운 파일은 격리(quarantine)해 따로 가둡니다. 경비원은 인바운드(inbound) 규칙으로 허용한 포트만 열고 나머지는 막으며, 아웃바운드(outbound) 규칙으로 서버가 밖으로 나가는 길도 제한할 수 있습니다.

서버에서는 원격 관리용 포트처럼 꼭 필요한 몇 개만 열고, 규칙마다 누가 왜 필요한지 적어 두는 것이 좋습니다.

정리하면 Windows Defender와 방화벽은 한쪽은 파일과 프로세스를, 다른 쪽은 네트워크 연결을 맡아 두 겹으로 서버를 지키는 구조입니다.

BitLocker

서버 디스크 암호화와 복구 키 보관

서버가 들어 있는 디스크를 누군가 떼어 가 다른 컴퓨터에 꽂으면 계정 암호와 무관하게 파일이 그대로 읽힙니다. BitLocker는 이런 물리적 탈취에 대비해 디스크 전체를 암호화하는 윈도우 기능이며, 서버에서는 저장 장치 암호화의 기본 수단으로 쓰입니다.

금고에 비유하면 디스크 암호화는 서류를 금고에 넣는 일, 복구 키(recovery key)는 금고 열쇠를 잃었을 때 쓰는 예비 열쇠입니다. 부팅할 때 TPM(신뢰 플랫폼 모듈)이라는 작은 칩이 부팅 환경이 바뀌지 않았는지 확인하고, 문제가 없으면 잠금을 풀어 운영체제가 시작됩니다. 디스크를 다른 기계로 옮기거나 펌웨어가 바뀌면 이 확인이 실패해 복구 키를 요구하는데, 그 키를 서버 안에만 두면 함께 잠겨 버립니다.

그래서 복구 키는 Active Directory나 별도 관리 서비스에 보관하고, 정기적으로 꺼내 확인하는 절차를 둡니다.

정리하면 BitLocker는 디스크 전체를 암호화해 물리적 탈취를 막고, TPM과 복구 키로 잠금 해제를 통제하는 방식입니다. 암호화보다 중요한 것은 복구 키를 잃지 않게 보관하는 일입니다.

감사 정책과 이벤트 로그

무슨 일이 있었는지 기록으로 남기기

새벽에 누가 관리자 계정으로 로그인해 파일을 지웠는데 아무 기록도 없다면 무슨 일이 있었는지 확인할 방법이 없습니다. 감사 정책(audit policy)은 로그온과 파일 접근, 권한 변경 같은 사건을 기록하도록 미리 켜 두는 설정이고, 그 결과가 이벤트 로그(event log)에 쌓입니다.

건물 출입 기록부에 비유하면 감사 정책은 어떤 문에 기록기를 달지 정하는 일, 이벤트 로그는 그 기록기가 남긴 시간과 이름의 목록입니다. 기록기는 사건마다 종류와 결과를 적는데, 윈도우에서는 보안(Security) 로그에 로그온 성공과 실패, 계정 변경, 개체 접근이 남습니다. 다만 기록을 모두 켜면 로그가 금세 차고 서버 성능도 떨어지므로, 필요한 항목만 골라 켜고 로그 크기와 보존 기간을 정합니다.

로그는 한곳에 모아 두어야 하는데, 서버가 뚫린 뒤 공격자가 자기 흔적을 지울 수 있기 때문입니다.

정리하면 감사 정책으로 무엇을 기록할지 정하고 이벤트 로그를 별도 저장소에 모아 두는 것이 사후 확인의 바탕이 됩니다.

성능 모니터

카운터로 CPU·메모리·디스크 병목을 찾기

사용자가 "서버가 느리다"고 말할 때 어디가 느린지 알 수 없다면, 서버에 접속해 프로그램 몇 개를 껐다 켜 보는 추측만 반복하게 됩니다. 성능 모니터(Performance Monitor)는 CPU·메모리·디스크·네트워크의 상태를 숫자로 계속 기록해, 그 추측을 근거로 바꿔 주는 Windows Server의 기본 도구입니다.

성능 모니터는 아파트 관리실의 계량기함과 같습니다. 관리실 직원이 각 세대의 전기·수도 사용량을 세는 것처럼, 이 도구는 CPU 사용률이나 남은 메모리 같은 항목을 카운터(counter)라는 이름으로 일정 간격마다 읽어 시간별 그래프로 남깁니다. 어떤 카운터를 볼지는 사람이 고르고, 그 값을 어디에 얼마 동안 저장할지도 사람이 정합니다.

그래서 "디스크 응답 시간이 길다", "메모리가 부족해 디스크로 넘치는 일이 잦다"처럼 병목의 위치를 짚을 수 있습니다.

정리하면 성능 모니터는 카운터를 수집·기록해 병목 지점을 찾아내는 진단 도구이고, 평소 값을 미리 기록해 두어야 장애 순간의 이상한 숫자를 알아볼 수 있습니다.

이것은 여러 지점에서 오는 택배 송장을 한 물류센터에 모으는 일과 비슷합니다. 각 택배기사가 자기 구역에서 찍은 송장이 흩어져 있으면 분실 건을 찾기 어렵지만, 본사 시스템 한 곳에 모이면 어느 지점에서 멈췄는지 바로 보입니다. 서버도 마찬가지로 각 서버의 이벤트 로그를 중앙의 수집 서버로 보내면, 한 화면에서 여러 대의 기록을 나란히 놓고 볼 수 있습니다.

로그에는 보통 언제, 어느 구성 요소가, 어떤 수준(정보·경고·오류)으로 무엇을 했는지가 담기고, 수집 방식은 운영체제 기본 기능을 쓰거나 별도 수집 도구를 두는 등 환경에 따라 달라집니다.

결국 이 체계의 핵심은 사건을 실시간으로 지켜보는 것이 아니라, 흩어진 기록을 한곳에 남겨 두었다가 필요할 때 시간축으로 재구성하는 데 있습니다.

Windows Server 백업

시스템과 데이터를 정기적으로 백업하기

디스크 하나가 갑자기 고장 나거나 랜섬웨어가 파일을 잠가 버리면, 그 서버에서 몇 년치 자료가 한순간에 사라질 수 있습니다. Windows Server 백업은 시스템과 데이터를 정해진 주기로 다른 매체에 복사해 두어, 이런 사고 뒤에도 원래 상태로 되돌릴 수 있게 하는 기능입니다.

백업은 이사 전에 짐을 따로 한 부 더 포장해 두는 일과 같습니다. 짐을 트럭에 싣는 것만으로는 사고가 났을 때 되돌릴 방법이 없지만, 같은 내용을 다른 상자에 담아 다른 창고에 두면 최소한 그 상자는 살아남습니다.

서버에서는 운영체제와 설정을 포함한 시스템 상태, 일반 파일과 폴더, 데이터베이스처럼 별도 절차가 필요한 항목을 각각 백업 대상으로 정하고, 전체 백업과 그 뒤의 변경분만 담는 백업을 조합해 보관합니다. 중요한 것은 백업을 만들어 두는 데서 끝내지 않고, 실제로 복원해 보는 시험을 정기적으로 해야 한다는 점입니다.

정리하면 Windows Server 백업은 시스템 상태와 데이터를 주기적으로 별도 매체에 보관하고 복원 가능성까지 확인하는 것이 핵심이며, 백업 주기와 보관 기간은 데이터 중요도에 맞춰 정합니다.

재해 복구 계획

장애 시나리오별 복구 목표와 절차 세우기

서버실이 침수되거나 데이터센터 전체가 정전으로 멈추면, 백업이 있어도 무엇을 어떤 순서로 되살릴지 정해 두지 않았다면 복구는 그 자리에서 시작됩니다. 재해 복구 계획(Disaster Recovery Plan)은 이런 상황을 미리 시나리오로 나눠, 복구 목표와 절차를 문서로 정해 두는 일입니다.

이 계획은 건물의 소방 대피 계획과 같습니다. 불이 났을 때 "일단 나가자"가 아니라, 어느 출구로 누가 무엇을 들고 몇 분 안에 어디로 모일지를 미리 정해 두어야 실제 상황에서 움직일 수 있습니다.

서버 쪽에서도 두 가지 목표를 먼저 정합니다. 얼마만큼의 데이터 손실까지 감수할지(복구 시점 목표, RPO)와 서비스를 몇 시간 안에 다시 열어야 하는지(복구 시간 목표, RTO)가 그것이고, 이 숫자에 따라 백업 주기와 대기 장비, 이전할 장소가 결정됩니다. 여기에 화재·침수·랜섬웨어 같은 시나리오별로 담당자와 연락 순서, 복구 절차를 붙입니다.

결론적으로 재해 복구 계획은 RPO와 RTO라는 두 목표를 먼저 합의하고, 시나리오별 절차와 담당자를 문서로 남겨 두는 것이며, 세워 두기만 하지 않고 모의 훈련으로 검증해야 비로소 의미가 생깁니다.

서비스 중단 시 원인 파악과 복구 순서

서비스가 멈추면 여러 사람이 동시에 서버에 접속해 저마다 다른 설정을 건드리고, 정작 원인은 아무도 기록하지 않는 일이 흔히 벌어집니다. 장애 대응 절차는 이런 혼선을 막기 위해, 중단 상황에서 누가 무엇을 어떤 순서로 확인하고 조치할지를 미리 정해 둔 규칙입니다.

핵심은 장애 대응이 즉흥적 복구가 아니라 영향 범위 파악, 원인 추적, 단일 변경, 기록과 회고로 이어지는 정해진 순서라는 점입니다.

버전 업그레이드와 마이그레이션

새 버전으로 옮기는 사전 점검과 절차

오래된 버전을 그대로 쓰면 보안 패치가 끊기고, 새 소프트웨어가 요구하는 기능을 지원하지 못해 결국 서비스 전체가 발목을 잡힙니다. 버전 업그레이드와 마이그레이션은 서버의 운영체제나 응용 프로그램을 새 버전으로 옮기는 작업으로, 사전 점검과 절차 없이 진행하면 예상치 못한 중단이 생깁니다.
