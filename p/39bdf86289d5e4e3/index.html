1부. 리버스 프록시의 개념과 역할001

리버스 프록시란 무엇인가

클라이언트 대신 요청을 받아 뒤쪽 서버로 넘기는 중개자의 역할

회사에 서버가 하나뿐인데 그 주소를 그대로 외부에 알려 두면, 방문자가 갑자기 몰려드는 순간 접속이 끊기고 내부 구조까지 그대로 드러나게 됩니다. 리버스 프록시(reverse proxy)는 바로 이 지점에서 등장하는데, 클라이언트의 요청을 대신 받아 뒤쪽 서버로 넘기고 서버가 만든 응답을 다시 클라이언트에게 돌려주는 중개자입니다.

비유하자면 아파트 단지의 경비실과 같습니다. 택배 기사는 각 세대의 현관문을 하나하나 찾아가지 않고 단지 입구의 경비실에 물건을 맡기고, 경비실은 호수와 이름을 확인해 알맞은 세대로 전달합니다. 이때 세대는 기사에게 집 안을 보여줄 필요가 없고, 기사도 단지의 내부 출입 구조를 알 필요가 없습니다.

리버스 프록시도 요청을 받아 어느 서버로 보낼지 판단하고, 뒤쪽 서버는 자기 존재를 드러내지 않은 채 응답만 돌려줍니다.

정리하면 리버스 프록시는 클라이언트와 서버 사이에서 요청과 응답을 중계하는 서버 측 프록시입니다. 덕분에 뒤쪽 서버는 직접 노출되지 않고, 운영자는 중개 지점 한 곳에서 접속 제어와 분산 같은 정책을 모아 다룰 수 있습니다.

포워드 프록시와 리버스 프록시의 차이

누구를 대신하느냐로 갈리는 두 프록시의 방향

사내 네트워크에서 직원 컴퓨터가 외부 사이트에 곧바로 접속하면 누가 어디에 접속했는지 통제할 방법이 없고 각 PC가 외부에 그대로 노출됩니다. 이때 나서는 것이 포워드 프록시(forward proxy)이며, 반대로 서버 쪽에서 외부의 요청을 받아 주는 역할이 리버스 프록시(reverse proxy)입니다.

두 프록시의 차이는 누구를 대신하느냐로 갈립니다. 회사 우편물에 비유하면, 직원이 보내려는 편지를 대신 접수해 규칙에 맞는지 확인한 뒤 발송하는 우편 담당자가 포워드 프록시이고, 회사의 대표 주소로 들어온 편지를 부서별로 나눠 전달하는 접수 창구가 리버스 프록시입니다. 편지를 보내는 쪽의 대리인이면 포워드, 편지를 받는 쪽의 대리인이면 리버스라는 구분입니다.

정리하면 포워드 프록시는 클라이언트를 대신하여 바깥으로 나가는 요청을 중계하고, 리버스 프록시는 서버를 대신하여 안으로 들어오는 요청을 중계합니다. 그래서 포워드 프록시는 주로 사용자 보호와 접속 통제에, 리버스 프록시는 서버 보호와 서비스 운영에 쓰입니다.

1부. 리버스 프록시의 개념과 역할003

리버스 프록시가 필요한 이유

서버를 직접 노출하지 않고 운영을 유연하게 만들기 위해

서버 한 대에 서비스를 올려 두고 그 주소를 그대로 공개하면, 서버가 고장 나는 순간 서비스 전체가 멈추고 서버의 내부 구성까지 외부에 드러납니다. 리버스 프록시(reverse proxy)는 이런 위험을 서버 앞단에서 흡수하기 위해 필요해진 계층입니다.

백화점 건물에 비유하면 이해가 쉽습니다. 손님은 몇 층에 어느 매장이 있는지 알 필요 없이 정문 하나로 들어오고, 안내 데스크가 용건에 따라 층과 매장을 알려 줍니다. 매장이 이전하거나 새로 문을 열어도 정문의 위치는 그대로이고, 손님은 바뀐 내부 사정을 알 필요가 없습니다.

리버스 프록시도 외부에는 하나의 주소만 노출하고, 뒤쪽 서버의 증설이나 교체는 그 뒤에서 조용히 처리합니다.

결국 리버스 프록시는 서버를 직접 노출하지 않게 하고, 서버 구성이 바뀌어도 서비스 주소를 그대로 유지하게 해 줍니다. 운영자는 이 중개 지점에서 암호화와 접근 제어, 트래픽 분산 같은 정책을 한곳에 모아 적용할 수 있습니다.

1부. 리버스 프록시의 개념과 역할004

리버스 프록시의 요청 처리 흐름

요청 수신부터 응답 반환까지 한 트랜잭션이 지나는 경로

사용자가 주소를 입력했는데 요청이 어느 서버로 가야 하는지 정해져 있지 않으면, 서버 앞단은 매번 즉흥적으로 판단해야 하고 그 판단이 흩어지면 장애 원인도 찾기 어려워집니다. 리버스 프록시(reverse proxy)는 요청 하나가 지나는 경로를 한 줄로 정리해 이 혼란을 없앱니다.

호텔 프런트에 비유하면 흐름이 그대로 드러납니다. 손님이 프런트에 도착해 예약 이름을 말하면, 프런트는 예약 장부를 확인해 해당 객실로 안내하고, 객실에서 올라온 요청 사항은 다시 프런트를 거쳐 손님에게 전달됩니다.

리버스 프록시도 먼저 클라이언트의 요청을 받아 주소와 경로를 확인하고, 그 정보를 기준으로 뒤쪽 서버를 골라 요청을 넘기며, 서버가 만든 응답을 받아 클라이언트에게 돌려줍니다. 이때 어느 서버로 보낼지 정하는 규칙을 라우팅(routing)이라고 부릅니다.

정리하면 하나의 트랜잭션은 요청 수신, 대상 서버 선택, 요청 전달, 응답 반환의 순서로 흐릅니다. 모든 요청이 같은 관문을 지나기 때문에 기록과 정책 적용도 이 한 지점에서 일관되게 이루어집니다.

리버스 프록시와 API 게이트웨이의 관계

겹치는 역할과 나뉘는 책임의 경계

서비스가 여러 개로 늘어나면 클라이언트는 인증을 어디서 받아야 하는지, 어떤 주소로 어떤 기능을 불러야 하는지 매번 새로 알아야 합니다. 리버스 프록시(reverse proxy)와 API 게이트웨이(API gateway)는 모두 이 복잡함을 앞단에서 정리하려는 장치이며, 실제로는 같은 소프트웨어가 두 역할을 겸하는 경우도 많습니다.

큰 건물의 안내 데스크에 비유하면 경계가 보입니다. 방문객을 정문에서 맞아 엘리베이터까지 안내하는 일은 리버스 프록시가 하는 일이고, 방문 목적을 확인해 출입증을 발급하고 담당 부서까지 연결해 주는 일은 API 게이트웨이가 맡는 일입니다. 안내 데스크 직원 한 명이 두 일을 모두 할 수도 있지만, 출입증 발급 규칙처럼 업무마다 달라지는 처리는 별도의 절차가 필요합니다.

그래서 게이트웨이는 인증과 사용량 제한, 요청 형식 변환처럼 API에 특화된 기능을 더 맡는 쪽으로 발전했습니다.

정리하면 리버스 프록시는 요청을 올바른 서버로 전달하는 일반적인 중계 계층이고, API 게이트웨이는 그 위에서 API 단위의 정책을 다루는 계층입니다. 두 역할은 서로 대립하는 것이 아니라 겹치며, 규모와 요구에 따라 한 제품으로 합쳐 쓰기도 하고 나눠 쓰기도 합니다.

같은 소프트웨어가 함께 맡을 수 있는 두 가지 일

서버 한 대로 감당하기 어려운 요청이 몰리면 응답이 느려지고 결국 접속이 끊기는데, 서버를 여러 대로 늘려도 요청이 한 대에만 쏠리면 늘린 의미가 없습니다. 리버스 프록시(reverse proxy)와 로드 밸런서(load balancer)는 이 문제를 앞단에서 함께 다루는 장치입니다.

은행 창구에 비유하면 두 역할이 자연스럽게 겹칩니다. 고객은 번호표를 뽑아 한 줄로 서고, 안내 직원이 비어 있는 창구로 고객을 보내며, 어떤 창구가 잠시 닫히면 다음 고객을 다른 창구로 안내합니다. 리버스 프록시는 고객의 용건을 받아 알맞은 창구로 보내는 접수대이고, 로드 밸런서는 여러 창구에 고객을 고르게 나누는 안내 직원입니다. 실제 제품에서는 이 두 기능이 한 소프트웨어 안에 함께 들어 있는 경우가 흔합니다.

정리하면 리버스 프록시는 요청을 어느 서버로 보낼지 결정하는 중계 계층이고, 로드 밸런서는 그 결정에서 여러 서버에 부하를 나누는 역할을 맡습니다. 역할은 개념상 구분되지만 같은 소프트웨어가 함께 수행할 수 있어, 운영에서는 하나의 앞단 구성으로 묶어 설명하기도 합니다.

리버스 프록시와 CDN의 관계

오리진 앞에 서는 프록시와 사용자 가까이에 서는 프록시

사용자가 몰리는 서비스에서 모든 요청이 한 대의 서버로 직접 들어오면 그 서버는 금세 숨이 차고, 멀리 떨어진 사용자는 매번 먼 길을 왕복하며 기다리게 됩니다. 이 곤란을 풀려고 서버 앞에 요청을 대신 받아 넘기는 리버스 프록시(reverse proxy)를 두고, 그중에서도 사용자와 가까운 곳에 콘텐츠 사본을 두는 CDN(Content Delivery Network)을 함께 씁니다.

이 관계는 공장과 동네 배송 거점으로 비유할 수 있습니다. 공장은 물건을 실제로 만드는 오리진(origin) 서버이고, 공장 정문의 접수처는 주문을 정리해 어느 라인으로 보낼지 판단하는 리버스 프록시입니다. 동네 배송 거점은 잘 나가는 물건을 미리 조금씩 쌓아 두는 CDN의 엣지(edge) 서버로, 손님이 가까운 거점에서 바로 받으면 공장까지 가지 않아도 됩니다.

거점에 없는 물건만 접수처를 거쳐 공장으로 올라가고, 그 결과는 다시 거점에 채워집니다.

정리하면 리버스 프록시는 오리진 앞에서 요청을 통제하고 분배하는 문지기이고, CDN은 그 앞에서 사용자와 가까운 곳에 사본을 두는 캐시 계층입니다. 둘은 경쟁 관계가 아니라 층이 다른 역할이며, CDN이 리버스 프록시 기술을 응용해 만들어진 경우도 많습니다.

여러 서비스가 서로를 호출하는 구조에서 통신 규칙을 각 프로그램 안에 직접 심으면, 언어와 버전이 늘 때마다 같은 코드를 서비스 수만큼 고쳐야 합니다. 이 반복을 없애려고 각 서비스 옆에 트래픽을 대신 처리하는 작은 프록시를 붙이는 설계가 나왔고, 이런 프록시들을 한데 묶어 관리하는 체계를 서비스 메시(service mesh)라고 부릅니다.

아파트 단지로 비유하면 이해가 쉽습니다. 각 세대가 서비스이고, 세대 문 앞에 한 명씩 붙는 전용 심부름꾼이 사이드카(sidecar) 프록시입니다.

집주인은 심부름꾼에게만 말하면 되고, 택배를 받거나 다른 세대에 물건을 보내는 일은 심부름꾼이 알아서 처리합니다. 어느 집에 누가 사는지, 실패하면 몇 번 다시 시도할지, 통행증을 어떻게 확인할지는 단지 관리사무소가 정해 모든 심부름꾼에게 같은 규칙으로 내려 줍니다.

정리하면 사이드카는 애플리케이션 옆에서 통신을 대신 맡는 리버스 프록시이고, 서비스 메시는 그 사이드카들과 중앙 제어부를 합쳐 만든 관리 체계입니다. 애플리케이션은 자기 일에만 집중하고, 연결·보안·관측은 프록시 계층이 나눠 맡는 구조입니다.

이득과 비용은 건물 현관에 보안 데스크를 두는 일과 비슷합니다. 데스크가 있으면 방문객 확인과 택배 접수를 한곳에서 처리할 수 있고, 각 세대는 문을 활짝 열어 둘 필요가 없습니다.

이 차이는 한 건물의 안내 데스크 직원을 다섯 명 두고 성격을 비교하는 것과 같습니다.

Nginx는 오래 일해 온 만능 직원으로 정적 파일 제공과 캐시, 프록시를 폭넓게 처리하고 설정 파일로 일을 시킵니다. Envoy는 계측에 강한 직원으로 서비스 간 통신의 세부 지표와 정책을 정교하게 다루며 서비스 메시의 데이터 경로로 자주 쓰입니다. HAProxy는 속도와 안정성에 특화된 직원이고, Caddy는 인증서 발급과 갱신을 스스로 처리하는 자동화형, Traefik은 컨테이너 환경에서 서비스 변화를 읽어 경로를 스스로 갱신하는 동적형입니다.

정리하면 이 제품들은 모두 요청을 대신 받아 넘기는 같은 계열이지만, 설정 방식과 자동화 수준, 관측 기능의 무게가 다릅니다. 어떤 제품이 절대적으로 좋다기보다 운영 환경과 팀의 익숙함에 맞춰 고르는 문제입니다.

프록시가 읽고 고쳐 쓰는 시작줄·헤더·본문

브라우저와 서버가 대화할 때 주고받는 내용이 정해진 형식 없이 제각각이면, 중간에서 요청을 해석해야 하는 프록시는 무엇을 읽어야 할지 알 수 없습니다. 그래서 HTTP(HyperText Transfer Protocol)는 요청과 응답 모두 시작줄, 헤더, 본문이라는 세 층으로 구조를 통일했습니다.

이 구조는 편지 한 통과 똑같습니다.

정리하면 HTTP 메시지는 시작줄로 무엇을 어디로 보낼지, 헤더로 어떤 조건인지, 본문으로 실제 내용을 나눠 담는 형식입니다. 리버스 프록시가 할 수 있는 일은 대부분 이 세 층을 읽고 일부를 바꿔 쓰는 데서 나옵니다.

HTTP 헤더의 종류와 역할

종단 간 헤더(End-to-End)와 홉 간 헤더(Hop-by-Hop)를 구분하는 이유

프록시가 요청을 중계하다 보면 어떤 정보는 최종 수신자까지 그대로 가야 하고, 어떤 정보는 바로 앞 연결에서만 의미가 있습니다. 이 둘을 구분하지 않으면 캐시가 엉뚱한 응답을 재사용하거나 중간 처리 흔적이 다음 구간까지 남아 오해를 부르는데, HTTP 헤더(header)는 이런 정보를 이름과 값의 쌍으로 실어 보내는 표찰입니다. 택배 상자에 붙은 받는 사람 주소와 송장 번호는 어느 물류센터를 거치든 끝까지 유지돼야 하는 정보이고, 각 허브에서만 쓰는 분류 바코드나 경로 스티커는 다음 구간으로 넘어갈 때 떼어 내는 정보입니다.

종단 간 헤더(End-to-End)는 앞의 경우로, 수신자에게 의미 있는 내용이라 프록시가 함부로 고치지 않고 그대로 전달합니다. 홉 간 헤더(Hop-by-Hop)는 뒤의 경우로, 딱 한 구간의 연결 상태를 다루므로 프록시가 받아서 처리한 뒤 다음 구간으로 넘길 때 제거하거나 새로 씁니다. Connection, Keep-Alive, Transfer-Encoding처럼 연결 자체를 다루는 헤더가 홉 간에 속하고, 나머지 대부분은 종단 간으로 취급됩니다. 정리하면 HTTP 헤더는 종단 간과 홉 간으로 나뉘고, 프록시는 홉 간 헤더만 소비하고 다시 쓰며 종단 간 헤더는 그대로 흘려보냅니다. 이 구분 덕분에 여러 프록시를 거치는 경로에서도 연결 관련 정보가 누적되거나 잘못 재사용되는 일을 막을 수 있습니다.

Connection 헤더와 keep-alive

연결을 재사용할지 끊을지 정하는 규칙

웹 페이지 하나를 열어도 수십 개의 요청이 오가는데, 요청마다 연결을 새로 맺으면 그때마다 시간이 붙어 화면이 눈에 띄게 느려집니다. 이 비용을 줄이려고 연결을 한 번 맺고 여러 요청에 재사용하는 규칙이 생겼고, 그 규칙을 조율하는 표찰이 Connection 헤더입니다. 전화로 문의를 여러 건 하는 상황을 생각하면, 한 건마다 끊고 다시 걸면 연결음과 인사에 시간이 들지만 통화를 유지한 채 다음 문의를 이어가면 훨씬 빠릅니다. 여기서 Connection 헤더는 통화를 계속 유지하자는 신호인 keep-alive와 이번 통화로 끝내자는 close를 주고받는 말과 같습니다.

다만 연결 유지 여부는 양쪽이 합의해야 하므로, 한쪽이 close를 보내면 상대는 응답 뒤에 연결을 닫고 다음 요청은 새 연결로 받습니다. HTTP/1.1에서는 별말이 없으면 연결을 유지하는 것이 기본값이고, 유휴 연결을 오래 붙잡아 자원이 묶이지 않도록 시간 제한과 최대 요청 수를 함께 두는 경우가 많습니다. 결국 Connection 헤더는 이 연결을 다음 요청에도 쓸지 지금 끊을지를 정하는 협상 표찰이고, keep-alive는 그중 유지 쪽 선택입니다. 프록시는 이 값을 자기 다음 구간의 연결 정책에 맞게 다시 판단해야 하며, 클라이언트와 서버 사이의 약속을 그대로 복사해 넘기면 안 됩니다.

Host 헤더와 가상 호스팅

하나의 IP와 포트에서 여러 사이트를 구분하는 기준

서버는 요청을 받으면 Host 값으로 설정에 등록된 사이트를 찾아 그 사이트의 문서와 인증서를 고르고, 값이 없거나 등록되지 않은 이름이면 기본 사이트로 보내거나 오류를 돌려줍니다. HTTPS에서는 인증서 선택도 이 이름에 기대므로, 이름이 어긋나면 브라우저가 경고를 띄울 수 있습니다. 정리하면 Host 헤더는 같은 IP와 포트로 들어온 요청을 도메인 이름에 따라 다른 사이트로 나눠 주는 기준이고, 가상 호스팅은 이 값을 이용해 서버 자원을 공유하는 방식입니다. 프록시는 이 값을 바꾸지 않고 그대로 전달해야 하며, 이름을 기준으로 라우팅할 때는 표기 형식까지 정확히 맞춰야 합니다.

URL 구조와 경로 매칭

스킴·호스트·경로·쿼리가 라우팅에 쓰이는 방식

들어온 요청을 여러 서버와 서비스로 나눠 보내려면 주소에서 어떤 부분을 봐야 하는지 정해져 있어야 하는데, 그냥 문자열 전체를 비교하면 같은 대상을 가리키는 주소도 서로 다른 것으로 취급됩니다. 이 판단의 기준이 되는 것이 URL(Uniform Resource Locator)의 구조이고, 프록시는 그 구성 요소를 뜯어 경로 매칭에 씁니다. 편지를 보낼 때 배송 방법, 건물 주소, 동과 호수, 그리고 참고 사항을 나눠 적는 것과 비슷합니다. 스킴(scheme)은 http나 https처럼 어떤 방식으로 접근할지를, 호스트(host)는 어느 서버로 갈지를, 경로(path)는 그 서버 안의 어느 자원인지를, 쿼리(query)는 같은 자원에 덧붙이는 조건을 나타냅니다.

프록시는 보통 호스트와 포트로 목적지 서버를 고르고, 경로의 앞부분을 규칙과 대조해 어느 서비스로 넘길지 정합니다. 이때 대소문자, 끝의 슬래시, 중복 슬래시, 퍼센트 인코딩, 상위 경로 이동 표기를 어떻게 다루느냐에 따라 매칭 결과가 달라지므로 규칙을 명확히 정해야 합니다. 정리하면 URL은 스킴, 호스트, 경로, 쿼리로 나뉘고, 프록시의 라우팅은 호스트로 대상을 고른 뒤 경로 규칙으로 세부 서비스를 가리는 방식으로 동작합니다. 경로 매칭 규칙은 정규화 방식까지 문서로 남겨 두어야 예상치 못한 우회나 잘못된 전달을 막을 수 있습니다.

HTTP/1.1의 한계

연결 하나에 요청 하나, 그리고 헤드 오브 라인 블로킹

HTTP/1.1에서는 연결 하나에 요청을 보내고 응답을 받은 뒤에야 다음 요청을 보낼 수 있어, 앞선 응답이 늦어지면 뒤에 줄 선 요청들이 함께 멈춥니다. 이 현상을 헤드 오브 라인 블로킹(head-of-line blocking)이라고 부르며, 브라우저가 연결을 여러 개 여는 우회로를 쓰게 만든 원인입니다. 은행 창구가 하나뿐인 지점을 생각하면, 앞사람의 서류 심사가 길어지면 뒤에 선 사람들은 자기 업무가 짧아도 함께 기다려야 합니다. HTTP/1.1의 연결이 바로 이 창구 하나에 해당하고, 요청은 줄을 서고 응답은 보낸 순서대로 돌아옵니다.

그래서 브라우저는 창구를 여러 개 여는 것처럼 서버와의 연결을 여러 개 맺어 병렬로 요청하지만, 연결마다 악수와 초기 설정 비용이 들고 서버 자원도 더 씁니다. 게다가 응답 크기를 모르는 경우 앞부분만 먼저 보내는 방식도 순서를 지켜야 해서, 큰 응답 하나가 뒤의 작은 응답들을 막는 문제는 완전히 사라지지 않습니다. 정리하면 HTTP/1.1은 연결 하나에서 요청과 응답이 순서대로 오가므로 앞선 요청이 뒤를 막는 구조적 한계를 안고 있습니다. 이 한계를 연결을 늘리는 방식으로 우회하다 보니 비용이 커졌고, 이것이 뒤에 나온 HTTP/2가 연결 하나에서 여러 요청을 동시에 다루도록 설계된 배경입니다.

HTTP/2의 특징

멀티플렉싱과 헤더 압축이 프록시 계층에 주는 변화

HTTP/1.1에서 연결을 여러 개 늘려도 연결마다 붙는 비용과 순서 대기 문제가 남아, 요청이 많은 화면일수록 지연이 쌓입니다. HTTP/2는 하나의 연결 안에서 여러 요청과 응답을 동시에 주고받는 멀티플렉싱(multiplexing)과 반복되는 헤더를 압축하는 방식을 도입해 이 구조를 바꿨고, 그 결과 프록시가 다루는 연결의 모양도 달라졌습니다. 왕복 두 차로 도로를 여러 차선으로 넓히고 차량마다 번호표를 붙이는 모습을 생각하면 이해가 쉽습니다. 도로 자체는 하나지만 차선이 나뉘어 여러 차가 동시에 달릴 수 있고, 응답은 번호표로 자기 차선을 찾아가므로 순서가 뒤섞여 도착해도 조립할 수 있습니다.

헤더 쪽은 매 요청마다 같은 이름과 값을 되풀이하지 않도록 한 번 보낸 목록을 기준으로 달라진 부분만 표시해, 앞선 요청이 뒤를 막는 부담을 크게 줄입니다. 다만 하나의 연결을 여러 사용자가 공유하면 어느 요청이 누구 것인지 구분하는 정보가 필요하고, 오래된 중계 장비가 이 형식을 이해하지 못해 협상이 깨지는 경우도 있어 프록시는 양쪽 구간의 형식을 따로 협상합니다. 정리하면 HTTP/2는 연결 하나에서 여러 스트림(stream)을 동시에 다루는 멀티플렉싱과 헤더 압축으로 HTTP/1.1의 순서 대기 문제를 완화합니다. 프록시는 클라이언트 쪽과 서버 쪽의 프로토콜 버전을 각각 협상하고 그 사이에서 변환하므로, 양쪽이 같은 버전을 쓴다고 가정하지 않는 것이 중요합니다.

HTTP/3와 QUIC

UDP 기반 전송이 프록시 구성에 미치는 영향

웹 서버 앞에 리버스 프록시(Reverse Proxy)를 세워 두면 대개 문제가 없어 보이지만, 최신 브라우저가 UDP(User Datagram Protocol) 위에 만든 QUIC(Quick UDP Internet Connections)로 먼저 접속을 시도하는 순간 이야기가 달라집니다. 프록시가 TCP(Transmission Control Protocol)만 받도록 열려 있으면 그 첫 시도는 조용히 실패하고, 사용자는 이유도 모른 채 더 느린 예전 방식으로 되돌아간 접속을 쓰게 되는데, HTTP/3는 이 QUIC 위에서 동작하는 HTTP의 세 번째 큰 버전이라서 전송 계층을 바꾼 일이 곧 프록시 구성의 문제가 됩니다.

은행 창구에 비유하면 기존 TCP 방식은 번호표를 뽑아 한 줄로 서는 구조라서 앞사람의 거래가 끝나야 뒷사람 차례가 오고 창구 직원은 한 손님만 붙잡고 있습니다. QUIC은 손님마다 전담 창구를 따로 내주고 직원 한 명이 여러 창구를 동시에 보는 구조라서, 한 창구가 막혀도 다른 창구의 거래는 계속 진행됩니다.

문제는 프록시가 손님을 창구 번호로 기억한다는 점인데, 손님이 휴대폰 망에서 사무실 와이파이로 옮겨 다녀도 같은 손님임을 알아보려면 연결 ID(Connection ID) 같은 별도 표식이 필요합니다. 게다가 QUIC은 봉투 겉면까지 암호로 싸 두기 때문에, 프록시가 예전처럼 봉투에 적힌 주소를 읽고 길을 정하던 방식도 그대로 쓸 수 없습니다.

정리하면 HTTP/3 환경의 프록시는 UDP 443번 포트로도 손님을 받아야 하고, 연결 ID를 기준으로 세션을 이어 붙이며, 암호화되지 않은 응용 계층 정보를 근거로 요청을 나눠야 합니다. 동시에 HTTP/2 이하로 접속하는 클라이언트를 위해 TCP 경로를 함께 열어 두는 이중 구성이 현실적인 답이 됩니다.

프록시 관련 표준 헤더

Forwarded·X-Forwarded-For·X-Forwarded-Proto가 담는 정보

프록시를 한 대만 쓰면 별일 없지만 앞단에 로드 밸런서(Load Balancer)와 CDN(Content Delivery Network)까지 겹치면 오리진 서버가 보는 접속자의 주소는 매번 같아집니다. 그래서 누가 공격했는지, 어느 지역에서 느린지 로그로 확인할 수 없게 되는데, 이 빈자리를 메우려고 요청이 경유한 사실을 기록으로 남기는 헤더들이 생겼습니다.

사내 품의서에 결재란이 줄줄이 붙어 있듯이, 요청도 지나온 단계마다 자기 이름을 한 칸씩 적어 두면 맨 끝에서 전체 경로를 되짚을 수 있습니다.

X-Forwarded-For는 그 결재란에 해당하며, 처음 접속한 클라이언트 주소부터 가까운 프록시 주소까지 쉼표로 이어 붙인 목록입니다. X-Forwarded-Proto는 원래 요청이 https였는지 http였는지, 즉 첫 손님이 암호화된 문으로 들어왔는지를 적어 두는 칸입니다. Forwarded는 이런 관행을 하나의 표준 문법으로 정리한 헤더로, 경유지 주소와 프로토콜을 for와 proto 같은 이름표와 함께 담습니다.

정리하면 이 헤더들은 오리진이 잃어버린 접속자의 출처를 되살리는 장부이며, 다만 값은 클라이언트가 위조할 수 있으므로 프록시가 직접 덮어쓰고 마지막 신뢰 구간의 값만 믿어야 합니다. 또한 X-Forwarded-로 시작하는 헤더들은 널리 쓰이지만 공식 표준은 아니라는 점도 함께 기억해야 합니다.

리버스 프록시의 배치 위치

경계 네트워크(DMZ)와 오리진 앞, 어디에 두는가

서버를 인터넷에 그대로 내놓으면 하루에도 수천 번씩 포트를 훑는 자동 스캔과 취약점 탐색을 정면으로 맞게 됩니다. 그래서 공개해도 되는 문만 외곽에 두고 실제 서버는 그 뒤에 숨기는 배치가 기본이 되는데, 이 외곽 구역을 경계 네트워크(DMZ, Demilitarized Zone)라 부르고 그 입구에 리버스 프록시를 세웁니다.

아파트 단지에 비유하면 단지 정문 경비실이 리버스 프록시이고, 각 동 출입구는 오리진 서버이며, 정문 옆에 따로 둔 택배 보관소가 DMZ입니다. 방문객은 반드시 정문에서 신분을 확인받고 목적지를 말해야 하며, 정문을 통과하지 않은 사람은 어느 동에도 들어갈 수 없습니다. 택배 보관소는 외부에서 물건이 닿는 곳이지만 거실로 통하는 문은 없어서, 그곳이 뚫려도 집 안까지 곧바로 이어지지는 않습니다.

같은 이유로 리버스 프록시는 오리진 앞에서 요청을 검사하고 걸러 낸 뒤 통과한 것만 안쪽으로 넘깁니다.

정리하면 리버스 프록시는 인터넷과 오리진 사이의 유일한 통로로 두고, 오리진은 사설 주소만 갖게 하여 직접 접근 경로를 없애는 것이 핵심입니다. DMZ는 외부 노출을 감수하는 완충 구역이고, 오리진은 그보다 한 겹 더 안쪽에 두는 것이 일반적인 배치입니다.

한 단계로 끝낼지 여러 단계로 나눌지

공항에 비유하면 체크인 카운터와 보안 검색대, 탑승구가 각각 다른 일만 하는 것과 같습니다. 체크인은 신분과 표를 확인하고, 보안 검색대는 위험물만 걸러 내고, 탑승구는 좌석 순서대로 사람을 태웁니다. 한 창구가 붐벼도 다른 창구는 자기 일을 계속하고, 문제가 생기면 어느 단계가 막혔는지 즉시 드러납니다.

다만 단계가 늘면 그만큼 대기 줄과 확인 절차가 반복되므로, 각 단계가 넘겨주는 정보를 표준 헤더 같은 공통 양식으로 맞춰 두어야 합니다.

정리하면 단일 프록시는 소규모에 적합하고, 보안 경계와 캐시나 압축 같은 부가 기능을 분리해야 할 규모라면 CDN과 로드 밸런서, 리버스 프록시를 역할별로 층층이 두는 다중 계층 구성이 낫습니다. 층을 나눌수록 지연이 한 번씩 더 붙는다는 비용도 함께 계산해야 합니다.

업스트림(Upstream)의 개념

프록시가 요청을 넘겨줄 대상 서버의 집합

프록시 설정 화면을 열면 업스트림(Upstream)이라는 항목이 눈에 띄는데, 이 값을 잘못 적으면 프록시는 살아 있는데도 모든 요청이 실패합니다. 업스트림은 프록시가 요청을 넘겨줄 대상 서버의 집합을 가리키며, 리버스 프록시 구성에서 요청이 최종적으로 도착할 목적지 목록입니다.

택배 회사의 허브 터미널에 비유하면, 도착한 물건을 어느 지점으로 보낼지 적힌 배송 지점 목록이 업스트림입니다. 터미널 직원은 물건을 직접 소비자에게 주지 않고 목록에 있는 지점으로 넘기며, 지점 하나가 공사를 하면 목록에서 잠시 빼 두고 다른 지점으로 돌립니다. 목록에는 주소뿐 아니라 그 지점이 지금 몇 건을 감당할 수 있는지, 응답이 정상인지 확인한 상태 점검 결과도 함께 붙습니다.

그래서 업스트림은 단순한 주소 한 줄이 아니라 주소와 상태를 묶은 묶음이며, 프록시는 이 묶음을 보고 어디로 보낼지 고릅니다.

정리하면 업스트림은 리버스 프록시가 신뢰하고 넘겨줄 백엔드 서버 그룹이고, 그룹을 어떻게 묶고 상태를 어떻게 확인하느냐가 가용성을 좌우합니다. 업스트림을 한 대만 두면 그 한 대가 멈추는 순간 서비스 전체가 멈춘다는 점도 기억해야 합니다.

가상 서버(Virtual Server) 설정

호스트와 포트 단위로 요청을 나누는 기본 단위

한 대의 서버에 회사 홈페이지와 관리자 화면, API를 함께 올리면 접속 주소가 하나뿐이라 어느 요청이 어느 서비스로 가야 하는지 구분할 방법이 없습니다. 이때 호스트 이름과 포트를 기준으로 요청을 갈라 주는 단위가 가상 서버(Virtual Server)이며, 리버스 프록시가 여러 서비스를 한 입구에서 받는 근거가 됩니다.

오피스 빌딩 로비에 비유하면, 건물 주소는 하나지만 안내데스크가 방문객에게 어느 회사를 찾는지 물어 층을 안내하는 것과 같습니다. 같은 주소로 와도 회사 이름이 다르면 다른 층으로 가고, 같은 회사라도 정문과 화물 출입구라는 다른 문으로 오면 받는 창구가 달라집니다. 이때 회사 이름에 해당하는 것이 호스트 헤더이고, 정문과 화물 출입구에 해당하는 것이 포트 번호입니다.

안내데스크는 이 두 가지를 조합해 목적지를 정하고, 목록에 없는 이름이 오면 아무 데도 보내지 않고 정중히 돌려보냅니다.

정리하면 가상 서버는 하나의 수신 포트와 하나의 프로세스 안에서 호스트 이름과 포트 조합마다 따로 정의되는 라우팅 단위이며, 여기에 인증서와 문서 루트, 업스트림을 각각 묶을 수 있습니다. 설정이 겹치면 먼저 걸리는 규칙이 이기므로, 기본으로 돌려보낼 가상 서버를 하나 정해 두는 것이 안전합니다.

호스트 기반 라우팅

도메인 이름을 보고 백엔드를 고르는 방법

한 대의 서버에 여러 웹사이트를 올려 두면 겉으로는 주소만 다를 뿐 실제로는 같은 컴퓨터로 요청이 들어옵니다. 이때 무엇을 보고 어느 사이트로 보낼지 정하지 못하면 방문자는 엉뚱한 사이트를 보게 되고 운영자는 서버를 사이트마다 따로 사야 하는 부담을 집니다. 그 판단을 대신 해 주는 장치가 리버스 프록시(Reverse proxy)의 호스트 기반 라우팅(Host-based routing)입니다.

아파트 경비실을 떠올리면 이해가 쉽습니다. 택배기사가 상자만 두고 가면 경비실은 어느 집 것인지 알 수 없지만, 송장에 받는 사람 이름이 적혀 있으면 그 이름을 보고 해당 동으로 보냅니다. 여기서 받는 사람 이름이 요청에 자동으로 붙는 호스트(Host) 값, 곧 도메인 이름이고, 경비실이 리버스 프록시이며, 각 동이 뒤에 숨은 백엔드(backend) 서버입니다.

프록시는 요청이 들어오면 주소의 도메인 부분만 읽어 미리 정해 둔 표와 대조하고, 표에 적힌 서버로 요청을 그대로 넘깁니다. 사이트가 늘어도 표의 줄만 늘리면 되므로 서버를 새로 들이지 않고도 대응할 수 있습니다.

정리하면 호스트 기반 라우팅은 요청의 Host 헤더에 담긴 도메인 이름을 기준으로 어느 백엔드로 보낼지 결정하는 방식입니다. 하나의 진입점(entry point)에서 여러 서비스를 도메인 단위로 나눠 운영할 수 있게 해 줍니다.

경로 기반 라우팅

URL 경로 접두사로 서비스를 분기하는 방법

하나의 도메인 아래에서 여러 서비스를 운영하면 요청 주소의 앞부분이 모두 같아집니다. 서버 입장에서는 들어온 요청이 회원 서비스 것인지 주문 서비스 것인지 구분할 단서가 없어 곤란해집니다. 이때 URL 경로를 단서로 삼는 방식이 경로 기반 라우팅(Path-based routing)입니다.

큰 회사 건물의 안내데스크를 떠올리면 쉽습니다. 방문객이 "3층 회계팀"이라고 말하면 안내데스크는 층과 부서를 확인해 해당 층으로 안내하는데, 이때 방문객이 말한 목적지가 URL 경로(path)이고 안내데스크가 리버스 프록시, 층별 부서가 백엔드 서비스입니다.

프록시는 경로의 앞부분인 접두사(prefix)를 미리 정한 규칙과 비교해 가장 길게 일치하는 규칙을 고릅니다. 그래서 /api/users 로 시작하는 요청은 회원 서비스로, /api/orders 로 시작하는 요청은 주문 서비스로 갈라 보낼 수 있습니다. 규칙에 없는 경로는 기본 서비스로 보내거나 오류 응답으로 처리합니다.

정리하면 경로 기반 라우팅은 URL 경로의 접두사를 기준으로 백엔드를 분기하는 방식입니다. 도메인을 하나로 유지하면서 서비스 경계를 주소 구조에 그대로 드러낼 수 있다는 점이 장점입니다.

헤더·쿼리 기반 라우팅

요청 내용을 조건으로 삼는 고급 분기

같은 주소로 들어온 요청이라도 모바일 앱에서 온 것인지 브라우저에서 온 것인지, 한국어 사용자인지 영어 사용자인지에 따라 다른 응답을 줘야 할 때가 있습니다. 주소만 보고는 이런 차이를 알 수 없어 모든 요청이 같은 곳으로 흘러가 버립니다. 요청에 함께 실린 부가 정보를 조건으로 삼는 것이 헤더·쿼리 기반 라우팅입니다.

병원 접수를 비유로 들 수 있습니다. 접수 창구 직원은 환자가 어디가 아픈지, 어떤 진료를 원하는지 듣고 알맞은 진료과로 보내는데, 이때 환자가 알려 주는 증상이 요청 헤더(header)와 쿼리 문자열(query string)이고 접수 창구가 리버스 프록시입니다.

헤더는 요청에 자동으로 붙는 신분 정보에 가깝고, 쿼리 문자열은 주소 뒤에 물음표와 함께 붙는 사용자의 명시적 조건입니다. 프록시는 이 값들을 표와 대조해, 예를 들어 모바일 앱 요청은 경량 API로 보내고 특정 버전을 요청한 클라이언트는 구버전 서버로 보냅니다. 조건이 여러 개 겹칠 때 어느 규칙을 먼저 볼지는 관리자가 정한 우선순위를 따릅니다.

정리하면 헤더·쿼리 기반 라우팅은 요청의 부가 정보를 조건으로 백엔드를 고르는 방식입니다. 무중단 배포나 버전 분리처럼 세밀한 제어가 필요할 때 특히 유용합니다.

경로 재작성(Path Rewrite)

백엔드가 기대하는 경로 모양으로 바꿔 넘기는 규칙

프록시 뒤의 백엔드는 자기만의 경로 규칙을 가지고 있는 경우가 많습니다. 외부에서는 /api/users 로 들어오지만 내부 서버는 /users 만 받도록 만들어져 있으면, 그대로 넘겼을 때 찾는 문서가 없다는 오류가 납니다. 이 간극을 메우는 규칙이 경로 재작성(Path rewrite)입니다.

사내 우편을 비유로 들 수 있습니다. 외부에서 온 봉투에는 회사 대표 주소와 부서 이름이 적혀 있지만 사내 우편함은 3층 302호 같은 내부 코드로만 배달하므로, 우편실 직원이 주소를 내부 규격으로 다시 적어 넣습니다. 여기서 우편실 직원이 리버스 프록시, 봉투에 적힌 외부 주소가 원래 경로, 내부 코드가 백엔드가 기대하는 경로입니다.

프록시는 정해 둔 규칙에 따라 경로의 앞부분을 떼어 내거나 다른 문자열로 바꾼 뒤 요청을 넘깁니다. 이때 조건과 치환 방식을 정규식(regular expression)으로 쓰는 경우가 많아, 규칙이 잘못되면 엉뚱한 경로로 바뀔 수 있으므로 주의가 필요합니다.

정리하면 경로 재작성은 프록시가 백엔드로 넘기기 직전에 요청 경로를 백엔드가 아는 모양으로 바꾸는 처리입니다. 덕분에 백엔드 코드를 고치지 않고도 외부에 노출되는 주소 체계를 그대로 유지할 수 있습니다.

리다이렉트와 URL 정규화

끝 슬래시·대소문자·스킴을 정리하는 처리

같은 페이지를 가리키는 주소가 /docs, /docs/, /Docs 처럼 여러 가지로 존재하면 검색 엔진은 이를 서로 다른 문서로 보고, 사용자는 즐겨찾기가 어긋나 헷갈립니다. 이 표기 차이를 하나로 모으는 처리가 리다이렉트와 URL 정규화(URL normalization)입니다.

아파트 주소 표기를 떠올리면 쉽습니다. 어떤 사람은 101동 1001호라고 적고 어떤 사람은 101-1001이라고 적어도 같은 집이며, 관리사무소가 창구에서 101동 1001호로만 적어 달라고 안내하는 것이 정규화입니다. 이때 관리사무소가 리버스 프록시이고, 표기가 제각각인 주소가 들어온 URL, 통일된 표기가 정규 URL(canonical URL)입니다.

프록시는 끝 슬래시(trailing slash)의 유무, 대소문자, http와 https 같은 스킴(scheme) 차이를 규칙에 따라 하나로 정합니다. 다른 표기로 들어온 요청에는 정규 주소를 알려 주며 다시 요청하도록 되돌려 보내는데, 이 응답이 리다이렉트(redirect)이며 영구적인지는 상황에 따라 301과 302 같은 상태 코드로 구분합니다.

정리하면 리다이렉트와 URL 정규화는 여러 표기의 주소를 하나의 정규 URL로 모으고, 나머지는 그 주소로 다시 요청하게 만드는 처리입니다. 중복 콘텐츠를 줄이고 링크와 캐시가 일관되게 동작하도록 돕습니다.

프록시 체인과 Via 헤더

여러 프록시를 거칠 때 경로를 남기는 방법

요청이 백엔드에 닿기까지 여러 대의 프록시를 거치는 구성이 흔합니다. 문제가 생겼을 때 어느 구간에서 지연되었는지, 누가 요청을 변형했는지 알 수 없으면 원인을 찾기가 매우 어렵습니다. 그래서 거쳐 간 프록시를 요청에 기록으로 남기는 장치가 Via 헤더(Via header)입니다.

택배 중간 허브를 비유로 들 수 있습니다. 물건이 출발지에서 도착지로 가는 동안 여러 허브를 지나며, 각 허브가 송장에 도착 스탬프를 찍어 두면 나중에 어디를 거쳤는지 한눈에 보입니다. 여기서 허브가 각각의 프록시, 송장이 HTTP 요청, 스탬프가 Via 헤더 항목이며, 이렇게 여러 프록시를 줄줄이 거치는 구성을 프록시 체인(proxy chain)이라고 합니다.

프록시는 요청을 넘길 때 Via 헤더에 자신의 이름과 사용한 프로토콜 버전을 덧붙이고, 응답이 돌아올 때도 같은 정보가 따라붙습니다. 다만 이 기록은 스스로 신고하는 방식이라 신뢰의 경계를 넘을 때는 위조될 수 있고, 실제 클라이언트 주소를 확인하려면 별도의 전달 헤더를 함께 봐야 합니다.

정리하면 프록시 체인은 요청이 여러 프록시를 순서대로 거치는 경로이고, Via 헤더는 그 경로를 요청과 응답에 남기는 표식입니다. 운영과 장애 분석에서 경로를 추적하는 단서가 됩니다.

무중단 배포를 위한 트래픽 전환

카나리와 블루그린을 프록시 설정으로 구현하기

새 버전을 배포할 때마다 서비스를 잠시 멈춘다면, 그 시간에 접속한 사용자는 화면 대신 오류를 보게 되고 결제 도중이던 사람은 처음부터 다시 해야 합니다. 그래서 서버를 세워 둔 채 손님을 새 버전으로 옮겨 태우는 무중단 배포가 필요해졌고, 그 이동을 실제로 집행하는 자리가 사용자와 서버 사이에 선 리버스 프록시(Reverse Proxy)입니다.

큰 마트가 계산대 시스템을 새것으로 바꾸는 상황을 생각해 보겠습니다. 가장 안전한 방법은 새 시스템으로 돌아가는 계산대 구역을 건물 한쪽에 통째로 만들어 두고, 준비가 끝난 뒤 입구에 선 안내 직원이 손님을 새 구역으로 돌리기 시작하는 것인데 이것이 블루그린(Blue-Green) 배포입니다. 반대로 기존 계산대를 그대로 둔 채 새 시스템 계산대 한두 대만 옆에 세우고, 전체 손님 가운데 십 분의 일만 먼저 그쪽으로 보내 계산을 시켜 보는 방식이 카나리(Canary) 배포입니다. 두 경우 모두 손님은 어느 계산대가 새것인지 알 필요가 없고, 안내 직원이 들고 있는 배분표의 숫자만 고치면 비율이 바뀌며, 새 계산대에서 계산이 막히면 곧바로 손님을 기존 쪽으로 되돌릴 수 있습니다.

정리하면 무중단 배포는 프록시가 요청을 어느 서버로 보낼지 정하는 규칙, 즉 업스트림(Upstream) 묶음과 가중치를 서비스 중에 바꾸는 일입니다. 카나리는 그 비율을 조금씩 올리는 방식이고, 블루그린은 대상을 한 번에 갈아 끼우는 방식으로 같은 도구를 다르게 쓰는 것입니다.

프록시 설정의 계층 구조

전역·서버·위치 블록이 겹칠 때 적용되는 순서

프록시 설정 파일이 커지면 같은 값을 여러 곳에 되풀이해 적게 되고, 그러다 한 군데를 고치고 다른 곳을 놓치면 어떤 주소는 새 설정대로, 어떤 주소는 옛 설정대로 움직입니다. 이 혼란을 막으려고 설정은 전역, 서버, 위치라는 겹겹의 블록으로 나뉘고, 안쪽으로 갈수록 구체적인 규칙이 바깥 규칙을 덮어쓰는 계층 구조를 이룹니다.

회사 규정집을 떠올려 보겠습니다. 본사가 정한 공통 규정이 있고, 각 지사가 그 아래에 자기 사정을 담은 규정을 두며, 팀 단위로 더 좁은 규정을 두는데, 어느 팀의 일은 그 팀 규정을 먼저 보고 팀 규정이 없을 때 지사 규정, 그것도 없을 때 본사 규정을 봅니다. 프록시 설정도 똑같아서 전역 블록의 값이 모든 서버에 기본값으로 흘러가고, 서버 블록에서 다시 적으면 그 서버에만 적용되며, 위치 블록에서 또 적으면 그 주소에만 적용됩니다. 다만 시간 제한이나 헤더 추가처럼 여러 개를 나열하는 종류의 지시자는 값을 물려받아 합치는 것이 아니라 그 블록에 하나라도 적히는 순간 상위 목록을 쓰지 않는 경우가 많으므로, 같은 항목을 안쪽에서 다시 적었다면 바깥 값이 살아 있지 않다고 보고 확인하는 편이 안전합니다.

결국 이 구조의 핵심은 반복을 줄이되 예외는 가까운 곳에서 처리한다는 것이고, 그래서 설정을 읽을 때는 가장 안쪽 블록부터 위로 거슬러 올라가며 실제로 적용되는 값을 확인해야 합니다.

4부. Nginx로 시작하는 리버스 프록시033

Nginx의 구조와 이벤트 모델

워커 프로세스가 적은 자원으로 많은 연결을 받는 방식

동시 접속이 수만 개로 늘어나는 순간, 연결 하나마다 프로세스나 스레드를 새로 만들어 붙이는 방식은 메모리와 전환 비용이 걷잡을 수 없이 불어나 서버가 먼저 지쳐 버립니다. Nginx는 연결을 담당하는 프로세스를 몇 개만 두고 그 안에서 수많은 연결을 번갈아 상대하는 방식으로 이 문제를 풀어냅니다.

손님이 많고 홀 직원은 몇 명뿐인 식당을 생각해 보겠습니다. 직원은 한 테이블의 주문을 받아 주방에 넘긴 뒤 그 앞에 서서 요리를 기다리지 않고, 곧바로 옆 테이블로 가서 주문을 받고 물을 따라 주며, 주방에서 요리가 나왔다는 신호가 오면 그때 해당 테이블로 가져다줍니다. 여기서 홀 직원이 워커 프로세스(Worker Process)이고, 주문을 접수해 두는 장부가 이벤트(event) 대기 목록이며, 준비가 끝난 일부터 처리하도록 직원을 움직이는 규칙이 이벤트 루프(Event Loop)입니다. 직원 수를 정하고 새 직원을 채용하거나 아픈 직원을 교체하는 매니저 역할은 마스터 프로세스(Master Process)가 맡고, 손님을 어느 직원에게 붙일지는 운영체제가 나눠 줍니다.

이렇게 하면 연결이 늘어도 프로세스 수는 그대로이므로 자원이 완만하게 늘고, 기다리는 동안 다른 일을 할 수 있어 놀고 있는 시간이 줄어듭니다.

정리하면 Nginx는 마스터가 워커를 관리하고 각 워커가 비동기 방식으로 다수의 연결을 동시에 상대하는 구조이며, 이것이 적은 자원으로 많은 연결을 받는 이유입니다.

Nginx 설치와 디렉터리 구조

패키지 설치 뒤 설정 파일이 놓이는 자리

Nginx를 쓰기로 하고 검색해 보면 설정을 고치라는 안내와 함께 여러 경로가 뒤섞여 나와, 어느 파일이 진짜 설정이고 어디에 웹 문서를 넣어야 하는지 헷갈리기 쉽습니다. 이 혼동은 설치 방법에 따라 파일이 놓이는 자리가 다르기 때문에 생기며, 패키지로 설치하면 정해진 자리에 이미 모든 것이 배치되어 있습니다.

가구가 다 놓인 집에 입주하는 상황을 떠올려 보겠습니다. 직접 목재를 사서 짜면 배치를 내 마음대로 정할 수 있지만 어디에 무엇을 둘지 스스로 정해야 하고, 지어진 집에 들어가면 주방, 창고, 서재의 자리가 이미 정해져 있어 그 규칙만 익히면 됩니다. 패키지 설치가 뒤쪽에 해당하는데, 설정 파일은 보통 etc 아래 nginx 디렉터리에 모여 있고 그 안의 nginx.conf가 중심 문서 역할을 합니다. 손님에게 보여 줄 웹 문서는 share나 var 아래의 html 디렉터리에 두고, 접속 기록과 오류 기록은 log 아래 nginx 디렉터리에 쌓이며, 실행 파일은 보통 usr 아래의 sbin 디렉터리에 있습니다.

설정 파일을 처음 열면 중괄호가 여러 겹으로 겹쳐 있어 어디서부터 읽어야 할지 막막하고, 닫는 괄호 하나를 잘못 지우면 서버 전체가 시작되지 않습니다. 그래서 이 파일은 역할이 다른 몇 개의 큰 블록으로 나뉘어 있고, 각 블록이 맡은 일을 알면 겹친 구조가 한눈에 들어옵니다.

건물 관리 규칙서를 상상해 보겠습니다. 맨 앞에는 건물 전체에 적용되는 기본 방침이 적혀 있고, 그다음에는 정문과 후문의 출입 게이트를 몇 개 열고 어떻게 운영할지에 대한 규칙이 오며, 그 뒤에는 입주사 모두에게 공통으로 알리는 안내문이 붙습니다.

여기서 맨 앞의 기본 방침이 main 블록이고, 게이트 운영 규칙이 events 블록이며, 공통 안내문이 http 블록입니다. http 블록 안에는 다시 입주사 하나하나에 해당하는 server 블록이 들어가고, 그 안에 회사 내 부서에 해당하는 location 블록이 들어갑니다.

흔한 실수는 게이트 운영 규칙을 http 안에 넣거나 입주사 규칙을 http 바깥에 두는 것인데, 블록마다 자리가 정해져 있으므로 넣을 수 있는 위치가 아닌 곳에 쓰면 설정 검사 단계에서 오류로 걸립니다.

정리하면 nginx.conf는 전역 설정을 담는 main, 연결 처리 방식을 정하는 events, 웹 서버로서의 공통 규칙을 담는 http로 뼈대가 이루어지고, 그 아래에 server와 location이 차례로 이어지는 구조입니다.

요청을 받아 처리 규칙으로 나누는 단위

한 대의 서버에 여러 도메인을 올리고, 같은 도메인 안에서도 주소에 따라 전혀 다른 프로그램으로 요청을 넘겨야 하는 순간이 옵니다. 이때 무엇을 기준으로 요청을 나눌지 정하지 않으면 모든 요청이 엉뚱한 곳으로 흘러가고, 규칙은 금세 손댈 수 없을 만큼 뒤엉킵니다.

아파트 단지의 택배 배송을 생각해 보겠습니다. 택배 기사는 먼저 단지 안의 어느 동으로 갈지 정하고, 동에 도착한 뒤에는 몇 호의 우편함에 넣을지 정합니다.

여기서 동을 고르는 기준이 도메인 이름과 포트 번호이고, 이 하나의 동이 server 블록입니다. 호수를 고르는 기준이 주소 뒤의 경로이고, 이 하나의 세대가 location 블록입니다. 기사는 도착한 주소의 경로를 앞에서부터 읽어 가장 잘 맞는 호수를 찾아 넣고, 맞는 호수가 없으면 동 안에 정해 둔 기본 호수로 보냅니다.

그래서 같은 동 안에서도 첫 번째 주소는 파일을 그대로 돌려주고 두 번째 주소는 뒤쪽 서버로 넘기며 세 번째 주소는 다른 도메인으로 튕겨 보내는 식으로 규칙을 나눌 수 있습니다.

정리하면 server는 어떤 이름과 포트로 들어온 요청을 받을지 정하는 단위이고, location은 그 안에서 경로를 기준으로 요청을 처리 규칙에 배분하는 단위이며, 이 두 층이 프록시 설정에서 요청을 나누는 기본 골격입니다.

proxy_pass의 동작

업스트림으로 요청을 넘기는 지시어의 정확한 의미

백엔드 프로그램이 8080 포트에서 돌고 있는데 바깥 사용자는 80번과 443번으로만 접속해야 한다면, 내부 포트를 그대로 공개하거나 서버 주소가 바뀔 때마다 사용자에게 새 주소를 알려야 하는 곤란이 생깁니다. 이때 바깥 요청을 대신 받아 안쪽으로 넘겨 주는 지시어가 proxy_pass이며, 리버스 프록시 설정의 중심에 있습니다. 회사 대표번호 교환원을 떠올리면 구조가 그대로 겹칩니다. 외부 전화는 대표번호 하나로만 들어오고, 교환원이 용건을 확인해 해당 부서의 내선 번호로 연결해 주는데, proxy_pass 뒤에 적는 주소가 바로 그 내선 번호입니다. 다만 교환원이 전화를 그대로 넘기는 것이 아니라 새로 걸어 연결하듯, nginx도 클라이언트와 맺은 연결과 별개로 업스트림과 새 연결을 열어 요청을 보냅니다.

그래서 원래 접속자의 주소 같은 정보는 저절로 전달되지 않고, 주소 끝에 경로를 함께 적었는지에 따라 백엔드가 받는 경로가 달라지므로 설정서를 확인해 가며 맞춰야 합니다. 결국 proxy_pass는 location이 고른 요청을 지정한 업스트림 서버로 전달하고 그 응답을 되돌려 주는 지시어이며, 전달되는 경로와 부가 정보는 설정에 따라 달라진다는 점이 핵심입니다.

proxy_set_header 사용법

백엔드에 전달할 헤더를 직접 정하는 방법

프록시를 한 겹 두는 순간 백엔드의 접속 로그에는 모든 방문자가 같은 주소로 찍히고, 원래 어떤 도메인으로 들어왔는지도 사라집니다. 이 상태로는 장애 분석도 접근 제어도 할 수 없으므로, 백엔드에 넘길 헤더를 직접 정하는 proxy_set_header가 필요합니다. 택배 접수 창구에서 직원이 송장의 보낸 사람 칸을 다시 적는 장면을 생각하면 이해가 쉽습니다. 중간에서 다시 포장하며 원래 송장이 사라졌으니, 접수 직원이 확인한 내용을 새 송장에 옮겨 적어야 배송지에서도 누가 보냈는지 알 수 있습니다. proxy_set_header Host는 이렇게 원래의 도메인 이름을 다시 적는 일이고, X-Real-IP나 X-Forwarded-For는 실제 접속자 주소를 덧붙이는 일이며, X-Forwarded-Proto는 원래 요청이 http였는지 https였는지 알려 주는 표시입니다.

이 지시어를 쓰지 않으면 해당 헤더는 비어 있거나 업스트림 주소로 바뀐 채 전달됩니다. 정리하면 proxy_set_header는 업스트림으로 나가는 요청의 헤더 값을 설정 문법으로 지정하는 지시어이며, 덕분에 백엔드는 프록시 뒤에서도 원래 요청의 정체를 복원할 수 있습니다.

업스트림 그룹 정의

여러 백엔드를 묶고 분배 규칙을 붙이는 법

백엔드 서버 한 대로만 서비스하면 그 한 대가 멈추는 순간 전체가 멈추고, 사용자가 몰리는 시간에는 한 대가 감당하지 못해 응답이 밀립니다. 그래서 여러 백엔드를 하나의 묶음으로 등록하고 그 안에서 요청을 나눠 보내는 upstream 그룹 정의를 씁니다. 은행 창구를 여러 개 열어 두고 번호표를 나눠 주는 모습과 같습니다. upstream 블록 안에 server를 여러 줄 적는 것이 창구를 차례로 여는 일이고, 별말이 없으면 요청은 창구 순서대로 돌아가며 배정되는 라운드로빈(round robin) 방식이 기본입니다. 성능이 좋은 창구에 손님을 더 보내려면 weight로 비중을 주고, 대기 중인 손님이 적은 창구로 보내려면 least_conn을, 같은 손님은 늘 같은 창구로 보내려면 ip_hash를 고릅니다.

어느 창구가 문을 닫으면 다음 창구로 안내가 넘어가듯, 응답하지 않는 서버는 건너뛰고 남은 서버로 요청이 향합니다. 결국 upstream은 여러 백엔드를 이름 하나로 묶고 그 이름에 분배 규칙을 붙이는 장치이며, 프록시는 proxy_pass에 그 이름을 적어 묶음 전체를 상대로 요청을 보냅니다.

모든 요청을 백엔드 프로그램으로 넘기면 이미지, 스타일시트, 스크립트 같은 변하지 않는 파일까지 애플리케이션이 읽고 내보내야 해서 정작 처리해야 할 업무가 밀립니다. 그래서 앞단의 nginx가 정적 파일은 직접 내주고 나머지만 프록시로 넘기는 분담이 필요하며, 이때 root와 alias, try_files가 기준을 만듭니다. 음식점 홀 직원과 주방의 역할 나누기를 떠올리면 됩니다. 손님이 물 한 병을 달라고 하면 홀 직원이 바로 건네고, 조리가 필요한 요리는 주방으로 넘기는데, 정적 파일이 물 한 병이고 프록시가 주방인 셈입니다.

root는 매장 주소에 손님이 말한 위치를 그대로 이어 붙여 파일을 찾는 방식이고, alias는 손님이 말한 위치를 다른 실제 경로로 갈아 끼우는 방식이라 둘을 섞으면 경로가 어긋납니다. try_files는 적어 둔 후보를 앞에서부터 확인해 처음 존재하는 것을 내주고, 아무것도 없으면 마지막 항목으로 넘기므로 이를 이용해 없는 주소만 백엔드로 보낼 수 있습니다. 정리하면 정적 자원은 root나 alias로 nginx가 직접 서빙하고, 존재하지 않는 경로나 동적 요청만 try_files와 location으로 프록시에 배분하는 것이 두 역할을 나누는 핵심입니다.

설정 문법 검사와 리로드

nginx -t와 -s reload로 무중단 반영하기

설정 파일을 고치고 곧바로 서비스를 재시작하면, 오타 하나나 빠진 세미콜론 하나로 웹 서버 전체가 뜨지 못해 방문자는 빈 화면을 보게 됩니다. 그래서 적용 전에 문법을 확인하는 nginx -t와, 연결을 끊지 않고 설정만 바꿔 넣는 -s reload 절차를 씁니다. 공장 라인의 교대 근무를 떠올려 보면 순서가 분명해집니다. 새 작업 지시서를 들고 라인에 투입하기 전에 관리자가 내용이 규격에 맞는지 먼저 검토하는데, 이것이 nginx -t이며 파일을 읽어 문법과 경로를 확인할 뿐 실제 동작은 바꾸지 않습니다. 검토를 통과하면 기존 작업자는 하던 일을 끝까지 마무리하고 새 작업자가 같은 자리에 들어오는데, -s reload가 이와 같아서 새 설정을 읽은 뒤 새 연결은 새 기준으로 받고 이미 처리 중인 요청은 끝까지 마칩니다.

반대로 검토를 건너뛰고 바로 재시작하면 지시서에 오류가 있을 때 라인 전체가 멈추듯 서비스가 중단될 수 있습니다. 결국 nginx -t는 적용 전 설정의 유효성을 검사하는 명령이고, nginx -s reload는 실행 중인 프로세스를 유지한 채 새 설정으로 교체하는 신호이며, 두 단계를 순서대로 밟는 것이 무중단 반영의 기본입니다.

4부. Nginx로 시작하는 리버스 프록시043

Nginx 설정의 흔한 실수

슬래시 위치와 프록시 헤더 누락 같은 함정

리버스 프록시(역방향 프록시)를 처음 세우고 주소를 눌러 보면 서버는 분명히 떠 있는데 화면에는 404가 뜨거나, 백엔드 로그의 접속 주소가 전부 프록시 자신의 주소로 찍히는 일이 자주 벌어집니다. 그 원인은 대개 Nginx 설정의 슬래시 한 글자와 헤더 두어 줄이 빠진 것뿐인데, 처음 하는 사람은 그 한 글자를 찾느라 반나절을 씁니다.

아파트 현관에 경비실을 두고 방문객을 안내하는 상황을 떠올려 보면, proxy_pass 뒤에 슬래시를 붙이는지 여부는 경비실이 방문객의 목적지 표를 그대로 넘길지, 아니면 앞부분을 떼고 안쪽 호수만 불러 줄지를 정하는 것과 같습니다.

location /api/ 에 대해 proxy_pass http://backend/ 처럼 뒤에 슬래시를 붙이면 /api/ 부분이 잘려 나가고, 슬래시 없이 쓰면 /api/ 까지 그대로 백엔드에 전달되어 백엔드가 /api/hello 를 기대하는지 /hello 를 기대하는지에 따라 404가 갈립니다.

헤더도 같은 이치여서 proxy_set_header Host $host 로 원래 도메인을 넘기지 않으면 백엔드는 자기가 어떤 이름으로 불렸는지 모르고, X-Real-IP 와 X-Forwarded-For, X-Forwarded-Proto 를 넘기지 않으면 모든 접속이 프록시 주소에서 온 것처럼 보이며 https 판정도 틀어집니다. 웹소켓(WebSocket)을 쓴다면 Upgrade 와 Connection 헤더를 넘기도록 따로 적어 주어야 하고, 이 한 줄이 없으면 연결이 붙었다가 바로 끊깁니다.

정리하면 슬래시는 경로를 자를지 말지 정하는 표지이고, Host 와 X-Forwarded-* 헤더는 원래 방문객의 신원과 출처를 백엔드에 그대로 전하는 통행증입니다. 설정을 바꾼 뒤에는 nginx -t 로 문법을 먼저 확인하고 실제 요청 한 건을 백엔드 로그에서 직접 확인하는 습관이 이런 실수를 가장 빨리 줄여 줍니다.

다른 프록시로의 이전

Nginx 설정을 Envoy·Caddy로 옮길 때 달라지는 점

Nginx로 잘 돌아가던 리버스 프록시를 다른 제품으로 옮기면, 똑같이 보이던 설정이 갑자기 다른 방식으로 동작해서 장애가 나는 경우가 많습니다. 특히 Nginx의 location 블록과 proxy_set_header 를 그대로 옮겨 적으면 된다고 생각했다가, 그 제품에는 그 개념 자체가 없다는 것을 뒤늦게 알게 됩니다.

이사에 비유하면 Nginx는 짐을 다 싼 뒤 한 번에 트럭에 실어 보내는 방식이고, Envoy는 이삿짐 목록을 중앙 관리소에서 실시간으로 내려받는 방식이며, Caddy는 집 주소만 적으면 열쇠와 명패까지 알아서 만들어 주는 방식입니다.

Nginx에서 server 와 location, proxy_pass 로 적던 것은 Envoy에서는 리스너(listener)와 라우트(route), 클러스터(cluster)라는 세 층으로 나뉘고, 설정을 파일로 고쳐 재시작하는 대신 xDS 라는 API로 동적으로 받아 갈 수 있습니다. Caddy는 Caddyfile 이라는 훨씬 짧은 문법을 쓰고, 도메인만 적어 두면 인증서 발급과 갱신을 ACME 로 자동 처리합니다. 반대로 Nginx에서 rewrite 나 if 블록으로 처리하던 복잡한 조건 분기는 옮길 곳이 마땅치 않아 라우트 규칙을 다시 설계해야 하는 경우가 생깁니다.

결국 이전 작업의 핵심은 설정 문법을 번역하는 것이 아니라, 정적 설정을 다시 읽는 구조인지 API로 설정을 받는 구조인지, TLS 인증서 관리를 누가 맡는지를 먼저 파악하는 것입니다. 옮기기 전에 실제 트래픽을 복제해 두 제품에 동시에 흘려 보고 응답과 헤더를 비교하면 차이를 훨씬 안전하게 찾을 수 있습니다.

5부. TLS와 인증서045

TLS의 목적과 핸드셰이크

암호화·무결성·인증을 세우는 첫 대화

카페 와이파이에 접속해 비밀번호를 입력하면, 그 순간 같은 공유기에 붙은 누군가가 오가는 내용을 그대로 들여다볼 수 있다면 어떤 일이 벌어질까요. 로그인 정보와 카드 번호가 평문으로 흘러다니는 이 곤란을 막기 위해, 통신 양 끝이 서로를 확인하고 암호화 규칙을 정하는 첫 대화를 설계한 것이 TLS(Transport Layer Security)이며, HTTPS는 이 TLS를 HTTP 위에 얹은 것입니다.

택배를 보낼 때 내용물을 잠글 상자를 먼저 고르고, 받는 사람이 진짜 그 사람인지 신분증으로 확인하고, 봉인 테이프가 뜯기지 않았는지 확인하는 절차를 생각하면 됩니다.

TLS 핸드셰이크(handshake)는 이 세 가지를 한 번에 하는 절차로, 어떤 암호 방식과 키 길이를 쓸지 서로 맞추는 협상, 서버가 자기 인증서를 내밀어 신원을 증명하는 인증, 그리고 앞으로 쓸 대칭키를 안전하게 만들어 나누는 키 교환이 차례로 오갑니다. 이 대화가 끝나면 양쪽은 같은 대칭키를 들고 있고, 이후의 실제 데이터는 그 키로 암호화되어 기밀성을 얻고, 메시지 인증 코드로 변조 여부를 확인해 무결성을 얻습니다. 절차가 짧을수록 빨라서 TLS 1.3 에서는 왕복 횟수를 줄여 첫 연결을 더 빠르게 만들었고, 한 번 연결한 상대와는 다시 협상하지 않고 이어 쓰는 방식도 함께 쓰입니다.

정리하면 TLS는 암호화(기밀성), 변조 방지(무결성), 상대 확인(인증)이라는 세 목표를 핸드셰이크 한 번으로 세우는 규약입니다. 그래서 브라우저 주소창의 자물쇠는 내용이 안전하다는 뜻이라기보다, 이 대화가 암호화되었고 상대가 그 도메인의 주인임을 확인했다는 뜻으로 읽어야 합니다.

5부. TLS와 인증서046

대칭키와 비대칭키

TLS가 두 방식을 함께 쓰는 이유

앞서 본 TLS 핸드셰이크에서 양쪽이 같은 열쇠를 나눠 갖는다고 했는데, 그 열쇠를 암호화되지 않은 회선으로 어떻게 안전하게 전달할 수 있을지가 곧바로 문제가 됩니다. 열쇠를 그냥 보내면 도청당하고, 열쇠를 보내지 않으면 암호를 풀 수 없으니, 이 모순을 풀기 위해 등장한 것이 두 종류의 열쇠를 함께 쓰는 방식입니다.

회사 금고에 비유하면 대칭키는 금고 하나에 열쇠 하나를 쓰는 방식으로 빠르지만 그 열쇠를 상대에게 건네는 순간이 위험하고, 비대칭키는 자물쇠는 누구나 채울 수 있지만 여는 열쇠는 주인만 가진 방식이라 열쇠를 건네지 않고도 안전하게 주고받을 수 있습니다.

대칭키(symmetric key) 암호는 암호화와 복호화에 같은 키를 쓰는 방식으로 AES 같은 알고리즘이 여기에 속하며, 계산이 가벼워 대량의 데이터를 빠르게 처리합니다. 비대칭키(asymmetric key) 암호는 공개키(public key)와 개인키(private key) 한 쌍을 쓰며, 공개키로 잠근 것은 개인키로만 열 수 있어 키를 미리 나눠 줄 필요가 없지만 계산이 무겁습니다. 그래서 TLS는 두 방식을 역할에 따라 나눠 쓰는데, 신원 확인과 키 합의는 비대칭 방식으로 처리하고 실제 데이터는 대칭키로 암호화합니다.

결국 대칭키는 속도를, 비대칭키는 안전한 키 전달을 맡고, 두 방식을 조합해야 빠르면서도 열쇠를 노출하지 않는 통신이 완성됩니다. 최근의 TLS 1.3 에서는 키 합의에 주로 타원곡선 디피-헬만(ECDHE) 방식을 쓰는데, 이는 양쪽이 각자 비밀값을 만들어 공개값만 교환하고 같은 키에 도달하는 방식입니다.

5부. TLS와 인증서047

인증서와 인증 기관(CA)

서버의 신원을 제3자가 보증하는 구조

웹사이트에 접속했을 때 주소창의 자물쇠가 떠 있어도, 그 사이트가 정말 우리가 생각한 그 회사인지 확인하지 않으면 낯선 사이트에 아이디와 비밀번호를 고스란히 넘기게 됩니다. 서버가 저는 맞습니다라고 스스로 말하는 것만으로는 믿을 수 없기 때문에, 제3자가 그 신원을 보증해 주는 구조가 필요하고 그것이 인증서(certificate)와 인증 기관(CA, Certificate Authority)입니다.

아파트 입주 때 관리사무소가 신분증을 확인하고 출입증을 발급해 주는 상황을 떠올리면 됩니다.

서버는 자기 도메인 이름과 공개키를 적은 내용을 만들고, 인증 기관에 심사를 요청해 그 내용 위에 기관의 서명을 받는데, 이렇게 서명이 붙은 문서가 인증서입니다. 브라우저는 세상의 인증 기관 목록과 그 기관의 공개키를 미리 들고 있다가, 서버가 내민 인증서의 서명을 그 공개키로 풀어 보고 진짜인지 확인합니다. 인증서에는 도메인 이름, 유효 기간, 발급자, 공개키가 담기고, 브라우저는 지금 접속한 주소가 인증서에 적힌 이름과 맞는지, 기간이 지나지 않았는지까지 함께 봅니다.

정리하면 인증서는 서버가 자기 공개키와 이름을 담아 인증 기관의 서명을 받은 신분증이고, CA는 그 신분증을 발급하고 보증하는 제3자입니다. 이 구조 덕분에 우리는 그 서버를 직접 만나 본 적이 없어도, 신뢰하는 기관의 서명 하나로 상대의 신원을 확인할 수 있습니다.

5부. TLS와 인증서048

인증서 체인과 루트 신뢰

브라우저가 인증서를 믿기까지의 사슬

브라우저가 인증서 하나를 받아 들고 그 서명을 확인하려는데, 그 인증서를 서명한 기관의 인증서조차 누군가의 서명이 필요하다면 확인은 끝나지 않습니다. 이 끝없는 되물음을 끊어 주는 것이 미리 신뢰하기로 정한 루트 인증서이고, 그 사이에 놓인 중간 인증서들을 잇는 구조가 인증서 체인(certificate chain)입니다.

회사 결재에 비유하면 담당자의 결재를 팀장이, 팀장의 결재를 본부장이 승인하는데, 본부장의 권한은 회사가 처음부터 인정하기로 한 규정에서 나오는 것과 같습니다.

서버는 자기 인증서(리프, leaf)와 함께 그것을 서명한 중간 인증서를 보내고, 브라우저는 그 중간 인증서를 다시 상위 인증서로 확인하며 위로 올라가다가 마지막에 운영체제나 브라우저에 내장된 루트 인증서(root certificate)에 닿으면 그 사슬을 믿습니다. 중간 인증서를 서버가 함께 보내지 않으면 브라우저는 사슬을 이을 수 없어 인증서 체인이 불완전하다는 경고를 내는데, 실제 운영에서 자주 만나는 실수입니다. 루트 인증서는 기기에 미리 설치되어 있으므로, 그 루트를 신뢰 목록에서 빼면 그 아래 모든 인증서가 한꺼번에 무효가 됩니다.

정리하면 인증서 체인은 리프 인증서에서 중간 인증서를 거쳐 루트 인증서까지 이어지는 서명의 사슬이고, 루트 신뢰는 그 사슬의 끝을 기기가 미리 인정해 두는 약속입니다. 그래서 서버를 세울 때는 리프와 중간 인증서를 모두 내려 주는지, 클라이언트가 쓰는 기기의 루트 저장소에 그 루트가 들어 있는지를 함께 확인해야 합니다.

TLS 종료(TLS Termination)

암호화를 프록시에서 끝내고 내부는 평문으로 보내기

회사 안에 서버를 여러 대 두고 바깥에서 오는 암호화된 접속을 그때마다 서버마다 처리하게 하면, 서버마다 인증서를 따로 발급하고 갱신해야 하고 암호화를 푸는 연산까지 각자 떠안아야 합니다. 그 부담을 한 곳에 모으려고 두는 장치가 리버스 프록시(Reverse Proxy: 바깥 요청을 대신 받아 안쪽 서버로 넘기는 서버)의 TLS 종료(TLS Termination)입니다.

아파트 정문 경비실을 떠올리면 이해가 쉽습니다. 택배 기사가 비밀번호가 걸린 금고를 들고 와도 경비실에서 직접 열어 내용물을 확인하고, 안쪽 세대에는 그 내용물만 전달하는 구조입니다.

여기서 금고를 여는 열쇠가 인증서이고, 금고를 여는 행위가 암호화 해제이며, 경비실이 리버스 프록시, 세대가 백엔드 서버(Backend Server: 실제로 일을 처리하는 내부 서버)에 해당합니다. 즉 바깥과 프록시 사이 구간만 암호화되고, 프록시에서 안쪽 서버로 가는 구간은 평문(Plain Text: 암호화되지 않은 상태)으로 흐릅니다.

그래서 TLS 종료는 인증서 관리와 암호 연산을 한 지점으로 모아 주는 대신, 내부망이 이미 신뢰할 수 있는 사설 구간이라는 전제를 요구합니다. 핵심은 암호화의 끝점을 백엔드가 아니라 프록시로 옮긴다는 점입니다.

TLS 재암호화(Re-encryption)

프록시에서 복호화한 뒤 백엔드와 다시 암호화하기

TLS 종료만 쓰면 프록시와 백엔드 사이가 평문으로 흘러, 같은 네트워크에 접근할 수 있는 누군가가 내용을 그대로 들여다볼 수 있습니다. 내부망도 안전하다고 단정할 수 없는 환경이라면 이 구간이 곧 구멍이 되고, 그 구멍을 메우려고 프록시가 다시 암호를 거는 방식이 TLS 재암호화(Re-encryption)입니다.

택배 비유로 옮기면 이렇습니다. 경비실에서 금고를 열어 내용을 확인한 뒤, 세대에 보낼 때는 다시 다른 자물쇠로 잠가서 보내는 것입니다. 경비실이 리버스 프록시, 첫 번째 자물쇠가 방문자와 프록시 사이의 암호화, 두 번째 자물쇠가 프록시와 백엔드 사이의 새 암호화이며, 두 자물쇠의 열쇠는 서로 다를 수 있습니다.

이렇게 하면 프록시는 내용을 검사하거나 헤더를 고칠 수 있으면서도, 안쪽 구간을 지나는 데이터는 다시 암호화된 상태로 유지됩니다.

정리하면 TLS 재암호화는 암호를 한 번 풀었다가 다시 거는 이중 구간 구성이고, 대신 인증서와 연산 비용이 양쪽에 모두 필요해집니다. 보안을 위해 편의를 조금 내주는 선택이라고 볼 수 있습니다.

TLS 패스스루

복호화 없이 암호화된 채로 넘기는 방식과 그 대가

프록시가 암호를 풀려면 그 도메인의 인증서와 개인 키를 반드시 쥐고 있어야 하는데, 규정상 그 키를 프록시에 둘 수 없거나 내용을 아예 들여다보면 안 되는 서비스라면 이 전제부터 무너집니다. 그래서 프록시가 내용을 보지 않고 암호화된 연결을 그대로 백엔드까지 넘기는 TLS 패스스루(TLS Passthrough)가 필요해집니다.

은행 금고 수송차가 건물 로비를 그냥 통과하는 모습을 생각하면 됩니다. 로비 직원은 차가 어느 층으로 가는지만 확인하고 봉인은 건드리지 않으며, 봉인을 여는 일은 목적지 방에서만 일어납니다. 여기서 로비가 리버스 프록시, 수송차의 봉인이 클라이언트(Client: 접속을 요청하는 쪽)와 백엔드 사이의 암호화, 목적지 방이 백엔드 서버입니다.

프록시는 어느 서버로 보낼지만 판단하고 연결의 암호화는 양 끝단에서 직접 맺어집니다.

그 대가는 분명합니다. 프록시가 요청 내용을 볼 수 없으니 경로 기반 라우팅이나 요청 수정, 캐싱 같은 기능을 쓸 수 없고, 인증서도 백엔드가 직접 관리해야 합니다. 보안과 통제 사이에서 어느 쪽을 우선할지 정하는 문제인 셈입니다.

SNI와 다중 도메인 인증서

하나의 포트에서 여러 도메인을 암호화로 나누기

서버 한 대에 여러 도메인을 올리면 접속마다 어느 도메인의 인증서를 내밀어야 하는지가 문제가 됩니다. 암호화는 요청 주소를 보기 전에 시작되므로, 예전에는 도메인마다 IP 주소를 따로 주거나 모든 이름을 한 인증서에 몰아넣는 방법밖에 없었습니다.

SNI(Server Name Indication: 암호화 협상 단계에서 클라이언트가 알려 주는 목적지 도메인 이름)는 이 문제를 푸는 표시판입니다. 아파트 현관에 들어서며 "몇 동 몇 호로 갑니다"라고 먼저 말하는 것과 같습니다.

방문객이 도메인 이름을 먼저 알려 주면, 현관 직원인 리버스 프록시가 그 이름에 맞는 인증서를 골라 내밉니다. 이름마다 인증서를 따로 두는 방식과, 여러 이름을 한 장에 담은 다중 도메인 인증서(SAN 인증서: 여러 도메인을 함께 적은 인증서)를 쓰는 방식이 모두 이 표시판 위에서 동작합니다.

따라서 SNI 덕분에 하나의 포트와 하나의 IP에서도 도메인별로 다른 암호화를 제공할 수 있습니다. 다만 이름이 암호화되지 않은 채로 오가는 경우가 있어, 그 자체를 감추려는 목적이라면 별도의 보완이 필요합니다.

Let's Encrypt와 자동 갱신

무료 인증서 발급과 만료 전 갱신 자동화

인증서는 발급보다 유지가 더 번거롭습니다. 만료일이 지나면 접속하는 모든 사용자에게 경고 화면이 뜨고 서비스는 사실상 멈추는데, 서버가 수십 대로 늘어나면 사람이 달력에 표시해 가며 하나씩 갱신하기는 어렵습니다. 게다가 유료 인증서는 비용과 심사 절차가 함께 따라옵니다.

Let's Encrypt(렛츠 인크립트: 무료로 인증서를 발급하는 공개 인증 기관)는 이 과정을 자동화하는 쪽으로 문제를 풀었습니다. 정기 구독으로 잡지를 받아 보는 것과 비슷합니다.

발급 절차가 기계적으로 정해져 있어 서버가 스스로 신청하고 받아 오며, 유효 기간이 짧은 대신 자동 갱신을 전제로 설계되었습니다. 여기서 신청을 처리하는 도구가 ACME 프로토콜(Automated Certificate Management Environment: 인증서 발급과 갱신을 자동으로 주고받는 규약)이고, 실제 갱신 작업은 예약된 작업이나 프록시 자체 기능이 주기적으로 수행합니다. 갱신이 성공하면 프록시가 새 인증서를 다시 읽어 들여 즉시 교체합니다.

요점은 무료라는 점보다 자동이라는 점입니다. 짧은 주기로 자동 갱신되는 구조를 갖추면 만료 사고 자체가 거의 사라지고, 사람이 개입할 여지도 그만큼 줄어듭니다.

HSTS와 HTTPS 강제

브라우저가 평문 접속을 거부하게 만드는 설정

주소창에 도메인만 입력하면 브라우저는 암호화되지 않은 HTTP로 먼저 접속을 시도합니다. 그 순간 평문 요청이 네트워크를 지나가고, 이를 가로채는 공격자는 사용자를 가짜 사이트로 돌려세울 수 있습니다. 서버가 HTTPS로 넘기도록 설정해 두어도, 그 첫 번째 평문 요청은 이미 노출된 뒤입니다.

HSTS(HTTP Strict Transport Security: 브라우저에게 이 도메인은 앞으로 암호화로만 접속하라고 알려 주는 응답 헤더)는 이 첫걸음을 막습니다. 건물 출입 규정을 한 번 등록해 두면 이후로는 평문 출입구 자체가 잠기는 것과 같습니다.

서버가 이 규칙을 한 번 내려 보내면 브라우저는 그 도메인을 기억해 두고, 다음부터는 HTTP 요청을 보내지 않고 곧바로 HTTPS로 접속합니다. 유효 기간은 헤더에 함께 실려 오고, 만료 전에 다시 받아 두어야 규칙이 유지됩니다. 인증서에 문제가 생겼을 때도 사용자가 경고를 무시하고 넘어갈 수 없게 만드는 점은 엄격함의 대가입니다.

정리하면 HSTS는 리버스 프록시가 내려 주는 응답 헤더 한 줄로, 브라우저가 평문 접속을 스스로 거부하게 만드는 장치입니다. HTTPS를 켜는 일과, HTTPS만 허용하도록 강제하는 일은 서로 다른 단계라는 점이 핵심입니다.

상호 TLS(mTLS)

클라이언트 인증서로 양방향 신원을 확인하기

리버스 프록시 뒤에 서버가 여러 대 있는 구조에서 프록시가 서버에 접속할 때 서버만 신원을 확인하고 프록시 쪽은 아무나 통과시키면, 네트워크 안쪽에서 위장한 프로세스가 서버 포트에 붙어도 걸러지지 않습니다. 상호 TLS(mutual TLS, mTLS)는 클라이언트와 서버가 서로 인증서를 제시해 양방향으로 신원을 확인하는 TLS 확장으로, 이 구멍을 막는 해결책입니다. 아파트 출입구에 비유하면 일반 TLS는 방문객이 건물 명패만 확인하는 것과 같아서 건물이 진짜인지만 따지고 방문객이 누구인지는 묻지 않습니다. mTLS는 방문증을 내밀어야 문이 열리는 구조와 같아서, 클라이언트가 자기 인증서를 제시하면 서버가 그 인증서를 신뢰하는 인증기관(CA, certificate authority)이 서명했는지 확인합니다. 서버도 자기 인증서를 내밀기 때문에 양쪽이 상대의 명패와 방문증을 동시에 검사하는 셈입니다.

리버스 프록시는 백엔드로 갈 때 자기 클라이언트 인증서를 함께 보내고, 서버는 그것을 검증한 뒤에야 요청을 받아들입니다. 정리하면 mTLS는 TLS 핸드셰이크 과정에서 양쪽이 인증서를 교환해 상호 검증하는 방식입니다. 리버스 프록시와 백엔드 사이, 서비스 메시 내부 통신처럼 신뢰 경계 안쪽에서도 상대를 확인해야 할 때 사용합니다.

인증서 만료 장애 대응

만료 직전과 직후에 무엇을 확인하고 복구하는가

리버스 프록시에 설치한 인증서가 만료되면 브라우저는 경고 화면을 띄우고 API 클라이언트는 핸드셰이크를 거부해, 코드를 한 줄도 바꾸지 않았는데 서비스가 오류로 멈춥니다. 만료는 예고 없이 터지는 장애라서, 만료 직전에 미리 점검하고 만료 직후에 빠르게 복구하는 절차를 따로 마련해 두어야 합니다. 아파트 공동현관 출입증에 유효기간이 찍혀 있어 기간이 지나면 경비원이 문을 열어 주지 않는 것과 같습니다. 만료가 다가오면 관리사무소가 갱신 대상과 새 출입증 발급 여부를 먼저 확인하듯, 프록시에 설치된 인증서의 만료 시각과 인증서 체인 전체, 자동 갱신 작업의 실행 기록을 확인합니다.

만료된 뒤에는 새 출입증이 실제로 발급됐는지, 경비실 단말기에 반영됐는지 확인하듯, 새 인증서 배포와 리로드가 실행 중인 프로세스에 반영됐는지, 중간 인증서(intermediate)가 빠지지 않았는지 살핍니다. 그리고 출입증을 쓰는 세대가 여러 곳이면 각 세대 단말기도 갱신해야 하듯, CDN과 캐시, 클라이언트 쪽 신뢰 저장소까지 확인해야 합니다. 실제 용어로 정리하면, 인증서 만료 대응은 만료일과 체인 상태와 자동 갱신 동작을 사전에 점검하고, 만료 시에는 배포와 리로드 반영 여부, 체인 누락, 종단 클라이언트 영향을 순서대로 확인해 복구하는 절차입니다.

로드 밸런싱의 목적

부하 분산과 가용성 확보를 함께 얻는 이유

서버 한 대에 모든 요청이 몰리면 그 서버는 점점 느려지다가 결국 죽고, 그 순간 서비스 전체가 멈춥니다. 로드 밸런싱(load balancing)은 여러 서버에 요청을 나눠 보내 부하를 분산하고, 한 대가 멈춰도 나머지가 요청을 받아내 가용성을 지키는 구조입니다. 은행 창구에 비유하면 창구가 하나뿐일 때는 줄이 끝없이 길어지고 그 직원이 자리를 비우면 업무가 전부 멈춥니다. 로드 밸런서는 번호표를 받아 빈 창구로 안내하는 안내원과 같습니다.

안내원은 창구가 몇 개인지, 어느 창구가 바쁜지 살펴 손님을 나눠 보내고, 한 창구가 문을 닫으면 그 창구를 목록에서 빼고 나머지로 보냅니다. 덕분에 손님은 오래 기다리지 않고, 직원 한 명이 쉬어도 은행은 계속 돌아갑니다. 비유를 걷어내면 로드 밸런서는 헬스 체크(health check)로 정상 서버 목록을 유지하면서 요청을 분배해 처리량과 가용성을 함께 높이는 장치입니다. 리버스 프록시가 이 역할을 겸하는 경우가 많습니다.

라운드 로빈 방식

순서대로 돌아가며 분배하는 기본 알고리즘

서버마다 남은 일이 다른데도 요청이 한 곳으로만 계속 가면 그 서버만 줄이 길어지고 나머지는 놀게 됩니다. 라운드 로빈(round robin)은 서버 목록을 순서대로 한 번씩 돌아가며 요청을 나누는, 가장 기본적인 분배 방식입니다. 카드 딜러가 왼쪽부터 한 장씩 나눠 주듯, 첫 요청은 1번 서버, 다음은 2번, 3번, 그리고 다시 1번으로 돌아갑니다. 서버 목록과 현재 순번만 기억하면 되기 때문에 구현이 단순하고, 요청 수가 비슷하면 결과도 고르게 나뉩니다.

다만 서버 성능이 다르거나 어떤 요청이 유난히 오래 걸리면 차례는 공평해도 실제 부하는 고르지 않을 수 있습니다. 그래서 서버가 목록에서 빠지면 그 자리를 건너뛰도록 순번을 조정합니다. 정리하면 라운드 로빈은 서버 목록을 순환하며 요청을 균등하게 배분하는 방식이고, 부하가 균질하고 서버 사양이 비슷한 환경에서 단순함이 장점입니다.

6부. 로드 밸런싱059

가중치 분배

서버 성능 차이를 비율로 반영하기

성능이 두 배 좋은 서버와 절반인 서버를 똑같이 한 번씩 번갈아 쓰면 좋은 서버는 놀고 약한 서버만 바빠집니다. 가중치 분배(weighted distribution)는 서버마다 비율(가중치, weight)을 부여해 이런 성능 차이를 분배 비율에 반영하는 방식입니다. 카페에서 주문을 숙련 직원과 신입 직원에게 나눌 때, 주문을 반씩 나누지 않고 숙련 쪽에 더 많이 넘기는 것과 같습니다. 가중치 분배는 이 비율을 숫자로 정해 두는 일입니다. 3대 1로 정하면 네 번 중 세 번은 성능 좋은 서버로, 한 번은 약한 서버로 요청이 갑니다.

비율이 유지되도록 순번표를 늘어놓고 돌리는 가중 라운드 로빈(weighted round robin)이나, 매 요청마다 가중치를 더해 대상을 고르는 알고리즘을 씁니다. 서버를 추가하거나 뺄 때는 그 서버의 가중치만 조정하면 됩니다. 실제 용어로 정리하면, 가중치는 처리 능력이나 남은 자원을 반영한 상대값이며 절대 성능을 보장하는 숫자가 아니므로 부하 분포를 지켜보며 조정합니다.

최소 연결(Least Connections) 방식

바쁜 서버를 피해 한가한 곳으로 보내기

요청 수를 고르게 나눠도 오래 걸리는 요청이 몰린 서버는 순식간에 꽉 찹니다. 최소 연결(least connections) 방식은 지금 열려 있는 연결이 가장 적은 서버로 새 요청을 보내, 바쁜 서버를 피해 한가한 곳으로 안내하는 방식입니다. 마트 계산대 여러 곳 중 손님이 가장 적게 줄 선 곳으로 가는 것과 같습니다. 로드 밸런서는 서버마다 현재 열려 있는 연결 수를 계속 세고 있고, 새 요청이 오면 그 수가 가장 작은 서버를 고릅니다.

계산대 앞 손님이 많다는 것은 처리할 일이 아직 남아 있다는 뜻이므로, 단순히 순서대로 돌리는 방식보다 실제 대기 상태를 더 잘 반영합니다. 여기에 서버 성능 차이까지 반영하려면 연결 수를 가중치로 나눠 비교하는 가중 최소 연결(weighted least connections)을 씁니다. 정리하면 최소 연결 방식은 서버의 현재 동시 연결 수를 기준으로 분배하며, 연결이 오래 유지되거나 요청마다 처리 시간 편차가 큰 서비스에서 특히 효과적입니다.

해시 기반 분배

같은 키는 같은 서버로 보내는 일관성

회원 한 명이 로그인하고 장바구니에 물건을 담았는데, 새로 고침을 할 때마다 장바구니가 비어 보인다면 사용자는 사이트를 믿지 못할 것입니다. 서버가 여러 대인데 요청이 매번 아무 서버로나 흩어지면, 앞서 저장한 정보를 들고 있는 서버를 다시 만나지 못해 이런 일이 생깁니다. 해시 기반 분배(hash-based distribution)는 사용자나 키 값을 계산해 서버를 정하는 방식으로, 같은 키는 언제나 같은 서버로 가게 만듭니다. 아파트 우편물을 생각하면 이해가 쉽습니다. 각 세대 번호를 일정한 규칙으로 나눈 나머지를 구해 담당 우편함을 정해 두면, 같은 집 앞으로 오는 편지는 몇 번이든 같은 함에 꽂힙니다. 이때 세대 번호가 키, 나머지를 구하는 계산이 해시, 담당 우편함이 서버에 해당합니다.

그래서 그 집의 우편물은 아무리 많이 와도 한 곳에 모이고, 관리자는 그 함만 열어 보면 됩니다. 반대로 함이 하나 없어지면 그 함에 배정되던 세대만 담당이 바뀌고, 나머지 세대는 그대로 남습니다. 정리하면 해시 기반 분배는 요청의 키를 해시 함수(hash function)로 변환해 서버 목록 위에 고정 배치하는 기법이며, 같은 키의 요청이 항상 같은 서버로 가도록 보장하는 것이 핵심입니다. 다만 서버가 늘거나 줄면 배정이 얼마나 흔들리는지는 해시 방식에 따라 달라지므로, 재배치 범위를 줄이는 변형 기법을 함께 검토하는 것이 보통입니다.

세션 유지(Sticky Session)

상태를 가진 서비스에서 사용자를 한 서버에 붙잡아 두기

결제 직전까지 진행한 단계가 다음 화면에서 사라지거나, 로그인을 했는데도 계속 로그인 화면으로 돌아온다면 사용자는 화면이 고장 났다고 느낄 것입니다. 서버가 여러 대인 환경에서 각 서버가 자기 메모리에만 사용자 상태를 들고 있으면, 요청이 다른 서버로 넘어가는 순간 그 상태가 사라집니다. 세션 유지(sticky session)는 상태를 가진 서비스를 위해 특정 사용자의 요청을 같은 서버에 계속 붙잡아 두는 방식입니다. 호텔에 장기 투숙하는 손님을 떠올리면 비슷합니다. 손님마다 담당 객실과 담당 직원이 정해져 있어서, 식당에서 주문하든 프런트에 문의하든 그 담당 직원이 계속 응대합니다. 손님의 짐과 요청 사항이 그 직원의 수첩에 적혀 있으니, 다른 직원에게 넘어가면 처음부터 다시 설명해야 하는 상황을 막는 것입니다.

이때 손님을 구분하는 표식이 쿠키(cookie)나 클라이언트 주소 같은 식별자이고, 담당 직원이 바로 세션 정보를 들고 있는 서버입니다. 대신 그 직원이 퇴근하면 손님의 수첩도 함께 사라지므로, 서버 장애 시 세션이 끊기는 약점이 따라옵니다. 정리하면 세션 유지는 로드 밸런서(load balancer)가 사용자별로 고정된 업스트림 서버를 기억하고 그쪽으로 요청을 보내는 방식이며, 세션 정보를 서버 메모리에 두는 구조에서 꼭 필요합니다. 세션을 외부 저장소로 옮기면 유지 없이도 같은 효과를 낼 수 있다는 점은 함께 기억할 만합니다.

상태 확인(Health Check)

죽은 서버를 자동으로 제외하는 판단 기준

트래픽을 받던 서버 한 대가 조용히 멈췄는데도 로드 밸런서가 계속 그 서버로 요청을 보내면, 사용자 다섯 명 중 한 명꼴로 오류 화면을 보게 됩니다. 서버가 살아 있는지 확인하지 않으면 장애가 절반쯤 조용히 섞여 들어오는 셈입니다. 상태 확인(health check)은 서버가 정상인지 주기적으로 물어보고, 답하지 못하는 서버를 자동으로 대상에서 빼는 장치입니다. 건물 경비실이 각 층 순찰을 도는 모습을 생각해 보면 됩니다. 경비원은 일정한 간격으로 각 층에 무전을 보내 응답이 오는지 확인하고, 몇 번을 불러도 대답이 없으면 그 층을 문제 구역으로 표시해 출입을 막습니다.

이때 무전을 보내는 주기가 검사 간격, 대답이 없는 횟수가 실패 임계값, 출입 차단이 트래픽 제외에 해당합니다. 그리고 그 층이 다시 응답하면 표시를 풀어 정상으로 되돌립니다. 여기서 중요한 것은 무엇을 물어보느냐인데, 문이 열리는지만 보는지 실제 업무가 돌아가는지까지 보는지에 따라 판단의 정확도가 달라집니다. 정리하면 상태 확인은 로드 밸런서가 업스트림 서버에 주기적으로 요청을 보내 응답과 상태를 판정하고, 실패가 누적된 서버를 분배 대상에서 자동 제외하는 기능입니다. 검사 간격과 임계값을 너무 민감하게 잡으면 잠깐의 지연에도 서버가 빠지므로, 서비스 특성에 맞춰 조정하는 것이 필요합니다.

수동 제외와 서킷 브레이커

장애 서버를 사람이 또는 시스템이 빼는 방법

점검을 하려고 서버를 내렸는데도 그 서버로 요청이 계속 들어오면, 관리자는 급하게 전체를 멈추는 선택을 하게 됩니다. 반대로 장애가 난 서버에 요청이 몰리면 그 서버는 더 깊이 무너지고 대기 중인 사용자만 늘어납니다. 수동 제외는 사람이 직접 대상을 빼는 방법이고, 서킷 브레이커(circuit breaker)는 시스템이 스스로 판단해 빼는 방법입니다. 아파트 누전 차단기를 떠올리면 두 방법의 차이가 분명해집니다. 사람이 공사를 할 때는 두꺼비집을 손으로 내려 그 집만 전기를 끊습니다. 반면 합선으로 전류가 갑자기 치솟으면 차단기가 알아서 툭 떨어져 불이 나기 전에 회로를 끊습니다. 손으로 내린 스위치는 공사가 끝나야 사람이 다시 올리고, 저절로 떨어진 차단기는 원인이 해소된 뒤 일정 시간이 지나면 다시 올려 봅니다.

여기서 전류가 오류율, 차단기가 임계 조건, 다시 올려 보는 동작이 일부 트래픽을 흘려보내는 시험 단계에 대응합니다. 정리하면 수동 제외는 운영자가 관리 화면이나 설정으로 특정 업스트림 서버를 분배 대상에서 빼는 조작이고, 서킷 브레이커는 오류율과 시간 초과 같은 지표가 임계치를 넘으면 호출 자체를 차단하고 회복을 시험하는 자동 보호 장치입니다. 점검처럼 예고된 상황은 수동으로, 갑작스러운 장애는 서킷 브레이커로 대응하는 식으로 역할을 나누는 것이 일반적입니다.

느린 시작(Slow Start)

새로 투입된 서버에 부하를 천천히 올리기

새 서버를 투입하자마자 다른 서버와 똑같은 양의 트래픽을 주면, 아직 준비가 덜 된 그 서버는 순식간에 과부하로 멈출 수 있습니다. 캐시가 비어 있고 연결도 맺어지지 않은 상태에서 갑자기 큰 부하를 받으면 응답이 느려지고, 느린 응답은 다시 대기와 재시도로 번집니다. 느린 시작(slow start)은 새로 투입된 서버에 보내는 몫을 작게 시작해 일정 시간에 걸쳐 정상 수준까지 올리는 방식입니다. 수영장에서 물에 들어가는 순서를 생각하면 비슷합니다. 발끝부터 담그고 몸이 적응하면 조금씩 더 들어가고, 마지막에는 어깨까지 잠깁니다. 처음부터 뛰어들면 놀라서 몸이 굳는 것과, 서버가 준비 없이 큰 부하를 받는 것이 같은 이치입니다.

이때 물에 담그는 깊이가 서버에 보내는 트래픽 비중, 적응하는 시간이 설정된 상승 구간에 해당합니다. 새 서버가 예열되면 그때는 다른 서버와 같은 비중으로 부하를 나눠 받습니다. 정리하면 느린 시작은 로드 밸런서가 새 업스트림 서버의 가중치(weight)를 낮게 두고 시간에 따라 서서히 올려, 캐시 예열과 연결 수립이 끝난 뒤 정상 부하로 넘어가게 하는 기능입니다. 갑작스러운 부하로 인한 초기 장애를 줄이는 대신, 예열이 끝나기 전까지는 그 서버의 여유 용량을 충분히 쓰지 못한다는 점도 함께 이해해야 합니다.

커넥션 풀과 업스트림 keep-alive

백엔드와의 연결을 재사용해 지연 줄이기

요청이 올 때마다 백엔드와 연결을 새로 맺으면, 실제 데이터를 주고받기 전에 인사하는 시간이 매번 붙습니다. 사용자가 적을 때는 티가 안 나지만 초당 요청이 많아지면 이 인사 시간이 쌓여 지연이 눈에 띄게 늘고, 연결을 맺고 끊는 자원 소모도 커집니다. 커넥션 풀(connection pool)과 업스트림 keep-alive는 이 연결을 재사용해 지연을 줄이는 방법입니다. 식당의 단골 자리를 떠올리면 이해가 쉽습니다. 손님이 올 때마다 테이블을 새로 만들고 치우는 대신, 미리 마련해 둔 몇 개의 테이블에 순서대로 앉히고 손님이 나가면 바로 다음 손님을 받습니다.

테이블을 몇 개 준비해 둘지가 풀의 크기, 손님이 나가도 테이블을 없애지 않고 그대로 두는 것이 keep-alive, 빈 테이블이 없을 때 잠시 기다리는 것이 대기열에 해당합니다. 테이블이 부족하면 손님이 밖에서 줄을 서고, 너무 많이 준비하면 쓰지 않는 자리만 자리를 차지합니다. 정리하면 커넥션 풀은 백엔드로 가는 연결을 미리 만들어 두고 빌려주고 돌려받는 구조이고, 업스트림 keep-alive는 한 번 맺은 연결을 요청이 끝난 뒤에도 닫지 않고 다음 요청에 다시 쓰는 설정입니다. 풀 크기와 유휴 연결 유지 시간을 서버와 네트워크 상황에 맞게 정하는 것이 지연과 자원 사이의 균형을 잡는 일입니다.

분배 알고리즘 선택 기준

트래픽 특성에 맞는 방식을 고르는 법

여러 대의 서버가 요청을 나눠 받는 구조에서 배분 규칙을 대충 정해 두면, 어떤 서버는 요청이 밀려 응답이 늦어지고 어떤 서버는 놀고 있는 상황이 생깁니다. 그래서 서버마다 처리 능력과 요청의 성격이 다르다는 점을 전제로, 트래픽 특성에 맞는 분배 알고리즘(load balancing algorithm)을 골라야 합니다.

은행에 창구가 다섯 개 있고 손님마다 볼일 걸리는 시간이 다르다고 생각해 보면 이해가 쉽습니다. 손님을 무조건 한 명씩 돌아가며 배정하는 방식은 순번(round robin)이고, 지금 처리 중인 손님이 가장 적은 창구로 보내는 방식은 최소 연결(least connections)입니다. 업무가 오래 걸리는 창구가 있다면 그 창구에 가중치(weight)를 낮게 주거나, 볼일 종류가 같은 손님은 늘 같은 창구로 보내 담당자가 맥락을 이어받게 합니다.

즉 창구의 능력, 손님이 머무는 시간, 볼일의 연속성 중 무엇이 문제인지 먼저 관찰하고 그에 맞는 규칙을 고르는 것입니다.

정리하면 분배 알고리즘은 순번, 최소 연결, 가중치 분배, 해시 기반 고정 분배 같은 선택지 중에서 고르는 것이며, 정답은 요청의 길이와 편차, 서버 성능 차이를 보고 판단합니다. 먼저 병목이 어디서 생기는지 측정한 뒤 규칙을 정하는 순서가 중요합니다.

세션 없는 설계로의 전환

스티키 세션을 없애기 위한 상태 분리

로그인한 사용자의 정보를 서버 한 대의 메모리에만 담아 두면, 그 서버가 잠깐 멈추거나 다른 서버로 요청이 넘어가는 순간 사용자는 갑자기 로그아웃됩니다. 이 문제를 피하려고 같은 사용자를 같은 서버로 묶는 스티키 세션(sticky session)을 쓰지만, 서버를 늘리거나 줄일 때 균형이 깨지므로 상태를 서버 밖으로 분리하는 세션 없는(stateless) 설계로 옮겨 갑니다.

단골손님이 자주 오는 식당을 떠올려 보면, 점원이 손님의 취향을 머릿속에 기억하는 방식은 그 점원이 그만두면 함께 사라집니다. 대신 손님마다 취향 카드를 만들어 계산대 옆 공용 서랍에 두면, 어느 점원이 응대해도 같은 카드를 꺼내 볼 수 있습니다.

여기서 카드가 세션 정보, 서랍이 공용 저장소이고, 점원은 각각의 서버에 해당합니다. 카드에 적힌 식별자만 요청에 함께 실어 보내면 어느 점원이든 같은 내용을 꺼내 쓸 수 있어, 손님을 특정 점원에게 묶어 둘 이유가 사라집니다.

기술적으로는 세션 데이터를 외부 저장소로 옮기고 요청마다 세션 식별자만 주고받게 만들어, 서버가 스스로 아무것도 기억하지 않는 상태 비저장 구조로 바꾸는 것입니다. 그렇게 해야 서버를 자유롭게 늘리고 줄여도 사용자 경험이 흔들리지 않습니다.

프록시 캐시의 원리

응답을 저장해 다음 요청에 재사용하는 구조

같은 페이지를 요청할 때마다 원본 서버가 매번 처음부터 응답을 만들어 보내면, 인기 있는 페이지 하나에 순간적으로 몰린 요청을 서버가 감당하지 못합니다. 그래서 원본 서버 앞에 프록시(proxy)를 두고 한 번 만든 응답을 잠시 저장해 두었다가 다음 요청에 그대로 돌려주는 프록시 캐시(proxy cache)를 씁니다.

동네 빵집을 떠올려 보면, 손님이 올 때마다 반죽부터 시작하면 줄이 끝없이 길어지므로 인기 있는 빵은 미리 구워 진열대에 올려 둡니다. 진열대에 있는 빵은 계산대까지 가지 않고 바로 건네주며, 진열대가 비었거나 시간이 오래 지난 빵만 본점에 새로 요청합니다.

여기서 본점이 원본 서버(origin server), 진열대가 캐시 저장 공간, 빵의 이름과 종류가 캐시 키(cache key)입니다. 그리고 언제 구운 빵인지 표시한 시간이 신선도(freshness)가 되어, 그 시간이 지나면 다시 본점에 물어보게 됩니다.

정리하면 프록시 캐시는 응답을 키 단위로 저장하고 유효한 동안 재사용해 원본 서버의 부담과 응답 지연을 함께 줄이는 구조입니다. 저장할지 여부와 얼마나 오래 둘지는 응답에 붙는 헤더가 결정합니다.

캐시 키 설계

무엇을 기준으로 같은 응답인지 판단하는가

캐시를 붙였는데 엉뚱한 사용자에게 다른 사람의 화면이 보이거나, 언어를 바꿨는데 이전 언어 페이지가 계속 나오는 사고가 있습니다. 이는 무엇을 같다고 볼지 정하는 캐시 키(cache key) 설계가 틀어졌기 때문이며, 캐시는 키가 같으면 같은 응답이라고 믿는다는 점이 출발점입니다.

도서관에서 책을 제목만으로 찾는다고 생각해 보면, 같은 제목의 다른 판본이나 번역본이 모두 한 칸에 섞여 들어갑니다. 그래서 색인 카드에는 제목뿐 아니라 저자, 판본, 언어까지 함께 적어 서로 다른 책을 구분합니다.

캐시도 마찬가지로 요청 주소(URL)와 호스트, 그리고 응답이 달라지는 조건인 언어나 압축 방식 같은 헤더 값을 키에 포함시켜야 합니다. 반대로 아무 정보나 다 넣으면 키가 지나치게 쪼개져 같은 응답을 다시 저장하는 일이 잦아지고 적중률이 떨어집니다.

결국 캐시 키는 요청을 구분하는 최소한의 기준을 정하는 설계이며, 응답 내용이 달라지는 요소는 반드시 넣고 그렇지 않은 요소는 빼는 판단이 핵심입니다. 이 기준을 잘못 잡으면 성능보다 사고가 먼저 늘어납니다.

Cache-Control 헤더

신선도와 재검증을 지시하는 표준 헤더

캐시가 저장한 응답을 언제까지 믿어도 되는지 정해 두지 않으면, 사용자는 이미 바뀐 가격이나 공지를 한참 뒤에야 보게 됩니다. 이 기간을 응답마다 명시하는 표준 헤더가 Cache-Control이며, 신선도(freshness)와 재검증(revalidation)을 지시하는 역할을 합니다.

편의점 우유를 떠올려 보면, 병마다 유통기한 스티커가 붙어 있어 점원이 매번 맛을 보지 않아도 언제까지 팔 수 있는지 압니다.

max-age는 유통기한처럼 남은 유효 시간을 초 단위로 적은 값이고, no-store는 아예 진열하지 말라는 지시, no-cache는 진열은 하되 내보내기 전에 반드시 확인하라는 지시입니다. 유통기한이 지나면 점원이 본사에 재고를 확인하듯, 캐시도 기간이 지나면 원본 서버에 재검증을 요청합니다. public과 private은 공용 진열대에 둘지 특정 손님에게만 줄지를 가르는 표시입니다.

정리하면 Cache-Control은 응답을 얼마나 오래 재사용할 수 있는지, 그리고 다시 쓸 때 원본에 확인할지를 지시하는 헤더입니다. 이 값을 정하지 않으면 캐시는 저마다 임의로 판단하게 됩니다.

ETag와 Last-Modified

조건부 요청으로 본문 전송을 줄이는 방법

캐시에 담긴 응답이 오래되어 본문 전체를 다시 받아야 하는 상황이 잦으면, 네트워크 대역과 시간이 그대로 낭비됩니다. 내용이 바뀌지 않았다면 본문을 보내지 않고 그대로라는 짧은 답만 주는 조건부 요청(conditional request)이 이 낭비를 줄이며, 그 판단 기준이 ETag와 Last-Modified입니다.

계약서 사본을 주고받는 상황을 생각해 보면, 상대가 매번 서류 전체를 다시 보내는 대신 제가 가진 것은 3판이라고만 물어볼 수 있습니다. 그러면 보관 담당자는 그 판본이 최신이라고 한마디로 답하고, 사본은 다시 만들지 않습니다.

여기서 판본 번호가 ETag이고, 서류를 마지막으로 고친 날짜가 Last-Modified입니다. 브라우저는 If-None-Match에 ETag 값을, If-Modified-Since에 날짜를 실어 보내고, 서버는 내용이 같으면 본문 없이 304 응답을 돌려줍니다.

결국 ETag와 Last-Modified는 응답 내용의 판본을 식별하는 표식이고, 조건부 요청은 그 표식만 주고받아 본문 전송을 줄이는 방법입니다. 본문이 큰 정적 파일일수록 이 절약 효과가 커집니다.

온라인 쇼핑몰에서 가격을 내렸는데 몇 시간이 지나도 손님 화면에는 옛 가격이 그대로 보인다면, 주문도 매출도 엉킵니다. 캐시 무효화(cache invalidation)는 이렇게 한 번 저장해 둔 응답이 실제 내용과 어긋나지 않도록, 오래된 것을 지우거나 새것으로 갈아 끼우는 전략입니다.

아파트 현관 게시판을 떠올려 보면 이해가 쉽습니다. 게시판은 캐시, 붙어 있는 안내문은 캐시된 응답, 안내문을 붙이고 떼는 관리인은 프록시, 게시판을 보는 입주민은 사용자에 해당합니다.

관리인은 새 공지가 나오면 옛 종이를 떼고 새 종이를 붙이며, 종이마다 언제까지 유효하다고 적어 두어 기한이 지나면 입주민이 스스로 최신 내용을 확인하게 합니다. 문제는 게시판이 한 곳이 아니라 동별로 여러 개라서, 한 곳만 고치면 다른 동 입주민은 여전히 옛 공지를 보게 된다는 점입니다.

실제로는 응답에 붙는 유효 기간(TTL)이 지나면 자동으로 버려지게 하고, 급할 때는 purge 요청으로 특정 주소의 저장본을 즉시 지우며, 파일 이름이나 주소에 버전 표시를 붙여 새 주소를 쓰게 하는 방식으로 어긋남을 막습니다.

주방의 조리대와 창고를 떠올려 보면 구조가 그대로 겹칩니다. 조리대는 캐시가 놓이는 저장 공간, 창고는 원본 서버, 조리대 위의 재료는 캐시된 응답, 주문은 사용자 요청입니다.

적중률은 주문된 재료가 조리대 위에 이미 있어서 창고까지 가지 않은 비율을 뜻하므로, 자주 쓰는 재료를 앞쪽에 두고 자주 쓰지 않는 것은 과감히 치워 공간을 비워야 합니다. 여기에 더해 메뉴 이름을 제각각 부르면 같은 재료를 여러 번 꺼내게 되므로, 주소와 매개변수를 하나의 규칙으로 정리해 같은 요청이 같은 열쇠로 묶이게 해야 합니다.

정리하면 적중률은 캐시 저장 공간의 크기, 유효 기간, 요청 열쇠 설계, 그리고 캐시해도 되는 응답인지의 판단이 함께 맞물려 올라가며, 낮은 적중률은 곧 원본 서버의 부하로 되돌아옵니다.

호텔 프런트의 서류함을 떠올려 보면 좋습니다. 공용 서랍은 여러 손님이 함께 쓰는 캐시, 개인 서류는 개인화된 응답, 서류에 붙은 이름표는 캐시 열쇠, 프런트 직원은 프록시입니다.

이름표 없이 개인 서류를 공용 서랍에 넣으면 다음 손님이 남의 서류를 받게 되므로, 열쇠에 손님을 구분하는 표시를 반드시 넣거나 아예 개인 서류는 공용 서랍에 넣지 말아야 합니다. 또 응답에 개인용이라는 표시를 붙여 중간의 공유 캐시가 저장하지 못하게 하고, 같은 주소라도 쿠키나 인증 정보에 따라 내용이 달라진다면 그 사실을 응답에 적어 캐시가 함부로 재사용하지 않게 합니다.

실제로는 캐시 열쇠에 쿠키나 인증 정보를 포함하고, 응답 헤더로 개인용·저장 금지를 지정하며, 공통 부분과 개인 부분을 나눠 공통 부분만 캐시하는 방식으로 동적 콘텐츠를 안전하게 다룹니다.

마이크로 캐싱

아주 짧게 캐시해 순간 트래픽을 흡수하기

인기 상품을 여는 순간 같은 요청이 1초에 수천 번 들어오면, 원본 서버는 같은 계산을 수천 번 반복하다가 버티지 못합니다. 마이크로 캐싱(micro caching)은 아주 짧은 시간 동안만 응답을 저장해, 순간적으로 몰리는 같은 요청을 하나의 결과로 흡수하는 방법입니다.

아파트 경비실에 택배 조회를 맡기는 상황을 떠올려 보면 이해가 됩니다. 경비실은 프록시, 조회 결과는 응답, 칠판에 적어 두는 메모는 짧은 유효 기간의 캐시, 조회를 요청하는 주민들은 동시에 들어온 같은 요청입니다.

경비원은 첫 주민의 조회만 실제로 확인하고 그 결과를 칠판에 적어 두었다가, 몇 초 안에 들어온 나머지 주민에게는 칠판을 보고 그대로 답하며, 시간이 지나면 메모를 지우고 다시 확인합니다. 같은 요청이 줄을 서는 동안 첫 요청이 아직 계산 중이라면, 뒤의 요청들은 그 결과를 기다렸다가 함께 받게 됩니다. 이렇게 하면 원본이 처리하는 횟수는 크게 줄고, 짧은 시간이라 내용이 낡을 위험도 거의 없습니다.

정리하면 마이크로 캐싱은 유효 기간을 1초 안팎으로 아주 짧게 잡아 순간 트래픽과 동시 요청 몰림을 흡수하는 기법이며, 원본 부하를 크게 낮추는 대신 짧은 지연과 약간의 신선도 손실을 감수합니다.

이삿짐을 압축팩에 넣어 옮기는 장면을 떠올리면 됩니다. 짐은 응답 본문, 압축팩은 압축 알고리즘, 짐을 받는 쪽은 브라우저, 이삿짐센터 직원은 프록시에 해당합니다.

다만 상대가 압축을 풀 도구를 갖고 있는지 먼저 물어야 하므로, 브라우저는 요청마다 받아들일 수 있는 방식을 알려 주고 서버나 프록시는 그중 하나를 골라 압축한 뒤 어떤 방식으로 눌렀는지 표시를 붙입니다. 프록시는 이 협상을 대신 처리하고 이미 압축된 응답은 다시 누르지 않으며, 압축은 처리 장치를 쓰는 일이라 트래픽이 많은 곳에서는 비용과 이득을 함께 저울질합니다.

실제로는 요청의 수용 가능 압축 목록과 응답의 압축 방식 표시가 짝을 이루어 협상이 끝나고, 사진·영상처럼 이미 압축된 자료는 다시 눌러도 줄지 않으므로 글 위주의 응답에 집중하는 것이 이득입니다.

저수지와 수도관을 떠올리면 두 방식이 갈립니다. 저수지는 버퍼, 물은 응답의 바이트, 수도관은 클라이언트와의 연결, 수문은 프록시가 데이터를 내보내는 시점입니다.

저수지에 물을 모으면 전체 양과 상태를 확인하고 한 번에 보낼 수 있지만 물이 차기 전까지는 아무것도 나가지 않고, 수도관으로 바로 흘리면 첫 물방울이 빨리 도착하는 대신 전체 길이를 미리 알 수 없어 길이를 알리는 표시 대신 조각 단위 전송 표시를 씁니다. 프록시는 응답을 모아 압축하거나 캐시에 넣기에 유리한지, 아니면 첫 바이트를 빨리 보내는 것이 중요한지를 보고 중간에서 어느 쪽으로 기울지 정합니다.

정리하면 버퍼링은 메모리를 더 쓰는 대신 크기 파악과 압축·검사에 유리하고, 스트리밍은 지연을 줄이는 대신 흐름 제어와 조각 전송 표시가 필요하며, 프록시는 응답의 성격에 따라 두 방식을 섞어 씁니다.

정리하면 리버스 프록시는 이미지와 스크립트, 스타일시트처럼 내용이 잘 바뀌지 않는 파일을 캐시와 압축, 만료 표시를 활용해 앞단에서 직접 응답하고 동적인 요청만 백엔드로 넘깁니다. 그 결과 서버의 자원은 정작 계산이 필요한 일에 쓰입니다.

타임아웃과 재시도 설계

느린 백엔드를 기다릴 시간과 다시 시도할 조건

백엔드가 응답을 주지 않는데 프록시가 무작정 기다리면 사용자는 화면이 멈춘 줄 알고 창을 닫아 버리고, 그 기다림에 묶인 연결은 다른 요청까지 붙잡습니다. 그래서 리버스 프록시에는 기다릴 시간의 한계인 타임아웃(timeout)과 실패했을 때 다시 시도하는 재시도(retry) 규칙을 미리 정해 둡니다.

음식 배달에 비유하면 프록시는 주문을 받아 가게에 전달하는 접수 앱이고, 백엔드는 실제로 음식을 만드는 가게입니다.

접수 앱이 무한정 기다리면 손님은 배가 고픈 채로 하염없이 화면만 보게 되므로, 몇 초까지 기다릴지 제한 시간을 정해 두고 넘기면 실패로 처리합니다. 실패했을 때는 곧바로 다시 주문할 수 있지만, 가게가 이미 음식을 만들고 있었을 수 있으니 횟수를 제한하고 간격을 점점 늘려 가며 다시 시도합니다. 특히 결제처럼 같은 주문이 두 번 처리되면 곤란한 일은 재시도를 하지 않거나, 한 번만 처리되도록 표시를 붙여 구분합니다.

결국 타임아웃은 기다림에 상한을 두어 자원이 묶이는 것을 막는 장치이고, 재시도는 일시적인 실패를 사용자 모르게 넘기는 장치입니다. 다만 다시 보내도 안전한 요청인지 먼저 따져야 하므로 두 설정은 항상 함께 설계합니다.

클라이언트별 동시 연결을 제한하는 방법

연결은 한 번 열면 서버의 메모리와 파일 기술자(file descriptor)라는 자원을 하나씩 차지하는데, 클라이언트 하나가 연결을 수천 개 열어 두면 다른 사용자를 받을 자리가 남지 않습니다. 리버스 프록시는 이런 독점을 막으려고 클라이언트별로 동시에 유지할 수 있는 연결 수에 상한을 둡니다.

아파트 주차장에 비유하면 주차 면 하나가 연결 하나이고, 주차 면이 유한한데 한 세대가 차를 열 대씩 세워 두면 다른 세대는 댈 곳이 없습니다.

입구 안내판이 세대별로 몇 면까지 허용하는지 세어 두고, 한도를 넘는 차는 자리가 날 때까지 들이지 않습니다. 이미 들어온 차가 나가면 그만큼 자리가 다시 생기므로, 기다리던 차가 순서대로 들어옵니다. 다만 한도가 너무 낮으면 브라우저가 이미지를 여러 개 동시에 받을 때 스스로 줄을 서게 되어 체감 속도가 느려질 수 있습니다.

연결 수 제한은 클라이언트마다 동시 연결의 상한을 두어 한 주체가 서버 자원을 독점하지 못하게 하는 장치입니다. 전체 상한과 개별 상한을 함께 두고, 정상적인 브라우저 동작을 방해하지 않을 만큼의 값을 실제 트래픽을 보며 정합니다.

프록시 헤더도 요청을 보내는 쪽이 임의로 값을 넣을 수 있어, 서버가 이를 그대로 신뢰하면 접속 기록과 차단 정책이 모두 오염됩니다. 그래서 신뢰하는 프록시가 직접 덧붙인 값만 인정하고 나머지는 버리거나 초기화하는 규칙이 필요합니다. 결국 프록시 헤더 위조 방지는 헤더의 존재가 아니라 누가 마지막으로 그 값을 썼는지를 기준으로 신뢰 경계를 정하고, 그 경계 밖에서 온 값은 신뢰하지 않는 원칙으로 정리됩니다.

요청 스머글링(Request Smuggling)

프론트와 백엔드의 본문 해석 차이를 악용하는 공격

같은 요청 하나가 앞단 장비에는 하나로 보이는데 뒤쪽 서버에는 두 개로 전달되어, 공격자가 의도하지 않은 두 번째 요청을 몰래 실행시키는 사고가 있습니다. 앞단과 뒷단이 본문의 길이를 해석하는 방식이 다르기 때문이며, 이 틈을 노리는 공격이 요청 스머글링(request smuggling)입니다. 택배를 받을 때 경비실은 큰 박스 하나로 세고 세대는 그 안의 작은 상자 두 개로 나눠 받는다고 생각해 보면 구조가 보입니다. 경비실이 큰 박스 하나라고 적어 보낸 기록과 세대가 실제로 연 상자 수가 어긋나면, 뒤에 붙은 상자는 누가 보낸 것인지 확인되지 않은 채 다음 배송으로 넘어갑니다.

요청 스머글링도 앞단이 본문의 끝을 판단한 지점과 뒷단이 판단한 지점이 달라, 남은 조각이 다음 요청의 앞부분으로 붙어 버립니다. 그래서 양쪽이 같은 규칙으로 본문 길이와 전송 방식을 해석하도록 맞추고, 해석이 갈릴 수 있는 애매한 요청은 아예 거부하는 편이 안전합니다. 결국 요청 스머글링은 프론트와 백엔드의 본문 경계 해석 차이를 없애고, 그 차이가 생길 수 있는 요청을 받지 않는 것으로 막습니다.

호스트 헤더 공격

Host 조작으로 라우팅과 캐시를 흔드는 수법

같은 웹사이트인데 어떤 사용자는 다른 페이지로 안내되고, 캐시에는 엉뚱한 내용이 저장되어 다른 사람에게 그대로 전달되는 일이 생길 수 있습니다. 요청에 실린 Host(호스트, 접속하려는 사이트 이름) 값이 라우팅과 캐시 판단의 기준이 되는데, 이 값을 보내는 쪽이 마음대로 바꿀 수 있기 때문이며, 이를 악용하는 수법이 호스트 헤더 공격입니다. 건물 안내데스크에 방문객이 저는 5층 사람이라고 스스로 적어 내고, 안내데스크가 확인 없이 그 말대로 5층으로 보내 준다고 생각해 보면 됩니다. 방문객이 옆 건물 5층이라고 적으면 안내데스크는 우리 건물이 아닌 곳의 규칙을 대신 적용하거나, 반대로 엉뚱한 층에 안내를 붙여 두게 됩니다.

호스트 헤더도 서버가 어느 사이트로 온 요청인지 가르는 근거인데, 허용 목록에 없는 값을 그대로 받아들이면 다른 사이트용 응답이 섞이거나 비밀번호 재설정 링크가 공격자 주소로 만들어집니다. 그래서 실제로 서비스하는 호스트 이름만 목록으로 정해 두고, 목록에 없는 요청은 거부하거나 기본 호스트로 되돌려야 합니다. 정리하면 호스트 헤더 공격은 신뢰할 수 있는 사이트 이름 목록을 고정하고, 그 목록에 없는 Host 값을 라우팅과 캐시 판단에 쓰지 않도록 막는 것으로 방어합니다.

봇 차단과 레이트 리밋 정책

자동화 트래픽을 구분해 다루기

로그인 페이지에 짧은 시간에 수천 번의 시도가 몰려 서버가 느려지고, 정상 사용자까지 함께 기다리게 되는 상황이 흔합니다. 사람과 자동화 프로그램을 구분해 트래픽을 다루는 것이 봇 차단(bot mitigation)과 레이트 리밋(rate limit, 요청 횟수 제한) 정책입니다. 회사 정문에서 방문객에게 하루 방문 횟수와 방문 목적을 적게 하는 절차를 떠올리면 이해가 쉽습니다. 정문 직원은 짧은 시간에 같은 사람이 반복해서 들어오려 하면 잠시 기다리게 하고, 사람이 아닌 자동 설비처럼 보이는 방문은 아예 들이지 않습니다.

봇 차단도 요청의 속도와 간격, 헤더 모양 같은 특징을 보고 자동화로 판단해 차단하거나 추가 확인을 요구하고, 레이트 리밋은 같은 출처에서 오는 요청 수를 일정 시간 동안 제한합니다. 두 정책 모두 정상 사용자를 막지 않도록 한도를 여유 있게 두고, 차단과 허용의 기준을 기록해 두는 것이 중요합니다. 정리하면 봇 차단과 레이트 리밋은 요청의 출처와 패턴을 근거로 자동화 트래픽을 구분하고, 허용 가능한 속도를 넘는 요청을 제한해 서비스 전체를 지키는 정책입니다.

WAF와 프록시의 결합

규칙 기반 차단을 앞단에 붙이는 구성

리버스 프록시(reverse proxy)를 세워 두면 서버를 직접 노출하지 않고 트래픽을 나눠 줄 수 있지만, 들어오는 요청이 정상 사용자의 것인지 공격 시도인지는 판단하지 못합니다. 그래서 프록시 앞단에 WAF(Web Application Firewall, 웹 방화벽)를 붙여, 요청이 서버에 닿기 전에 미리 정해 둔 규칙으로 걸러내는 구성이 쓰입니다.

아파트 정문을 생각하면 이해가 쉽습니다. 방문 목적을 확인하고 안내하는 안내데스크가 리버스 프록시라면, WAF는 그 앞에서 소지품 검색 규칙표를 들고 위험한 물건을 먼저 가려내는 보안 검색대입니다.

검색대는 어떤 모양의 물건은 반입 금지라는 규칙 목록을 가지고 있고, 목록에 걸리면 안내데스크에 도달하기도 전에 되돌려 보냅니다. 규칙은 주민 명단이나 과거 사고 기록을 보고 계속 갱신되며, 검색대를 통과한 방문객만 안내데스크에서 목적지 층을 배정받습니다.

결국 이 구성은 리버스 프록시가 하는 분배와 암호화 연결 종료 위에, WAF라는 규칙 기반 검문 단계를 한 겹 더 얹은 것입니다. 두 장치를 분리해 두면 차단 규칙만 따로 손보거나 로그를 따로 모을 수 있어 운영이 편해집니다.

보안 헤더와 응답 위생

CSP·X-Content-Type-Options를 프록시에서 붙이기

여러 서버와 오래된 애플리케이션이 섞인 환경에서는 보안 헤더(security header)를 하나하나 손으로 맞추기 어렵고, 한 곳만 빠져도 그 경로가 그대로 구멍이 됩니다. 그래서 모든 응답이 지나는 리버스 프록시에서 CSP(Content Security Policy, 콘텐츠 보안 정책)와 X-Content-Type-Options 같은 헤더를 일괄로 붙이는 방식이 쓰입니다.

택배 물류센터를 떠올리면 비슷합니다. 각 지점이 알아서 포장하고 보내는 대신, 모든 택배가 반드시 거치는 중앙 분류센터에서 취급 주의 스티커를 한 번에 붙이는 구조입니다.

CSP는 이 물건에 붙은 외부 부품은 여기 목록에 있는 것만 쓸 수 있다고 알려 주는 스티커이고, X-Content-Type-Options는 포장에 적힌 품목과 실제 내용물이 다르면 그대로 믿지 말라고 못 박는 스티커입니다. 분류센터는 원래 포장을 뜯지 않고 스티커만 덧붙이므로, 뒤쪽 서버는 헤더를 신경 쓰지 않아도 됩니다.

이렇게 하면 응답 위생(response hygiene)이 한 지점에서 보장되고, 새로 배포된 서비스도 자동으로 같은 보호를 받습니다. 다만 CSP는 허용할 출처를 잘못 적으면 정상 화면이 깨질 수 있어, 먼저 관찰 모드로 기록한 뒤 조여 가는 편이 안전합니다.

WebSocket 프록시

양방향 연결을 유지하려면 무엇이 필요한가

일반 HTTP 프록시는 요청이 오면 응답을 돌려주고 연결을 정리하는 방식이라, 서버가 먼저 말을 걸어야 하는 채팅이나 실시간 알림에는 맞지 않습니다. WebSocket(웹소켓)은 한 번 열린 연결을 계속 살려 두고 양쪽이 언제든 데이터를 주고받는 규약이고, 프록시는 이 연결을 끊지 않고 중계해야 합니다.

전화 통화에 비유할 수 있습니다. HTTP가 편지를 보내고 답장을 받는 왕복이라면, WebSocket은 연결이 성립된 뒤 끊을 때까지 선로가 열려 있는 통화입니다.

프록시는 통화를 중계하는 교환원처럼, 처음의 HTTP 요청에 담긴 업그레이드(Upgrade) 요청을 보고 두 구간을 이어 붙입니다. 이때 연결 유지 시간(timeout)이 짧으면 대화 중간에 선로가 끊기므로 늘려야 하고, 중간 장비가 헤더를 바꾸거나 데이터를 오래 담아 두면 실시간성이 무너집니다.

결국 WebSocket 프록시의 핵심은 한 번 성립된 연결을 오래 유지하고, 데이터를 가공하지 않고 그대로 흘려보내는 설정입니다. 여러 서버로 나눌 때는 같은 사용자의 연결이 같은 서버로 가도록 고정하는 것도 함께 고려해야 합니다.

Server-Sent Events 프록시

서버가 밀어주는 스트림을 중계하는 법

알림이나 진행률 표시처럼 서버가 새 소식을 계속 밀어 줘야 하는 화면은, 클라이언트가 주기적으로 다시 물어보는 방식으로는 지연과 낭비가 큽니다. SSE(Server-Sent Events, 서버 전송 이벤트)는 하나의 HTTP 응답을 열어 둔 채 서버가 텍스트 조각을 계속 덧붙여 보내는 규약이고, 프록시는 이 긴 응답을 끊지 않고 흘려보내야 합니다.

라디오 방송에 비유하면 쉽습니다. 일반 응답이 주문할 때마다 한 곡씩 받는 음원 구매라면, SSE는 주파수를 맞춰 두면 계속 흘러나오는 라디오 방송입니다.

프록시는 중계 송신소 역할을 하는데, 응답을 한 번에 다 받아서 넘기려 하면 방송이 끝날 때까지 아무것도 전달되지 않으므로 조각이 올 때마다 바로 넘겨야 합니다. 또 캐시가 응답을 붙잡거나 압축이 조각을 모아 두면 소식이 늦게 도착하므로, 해당 경로는 캐시하지 않고 버퍼링도 끄는 설정이 필요합니다.

이렇게 하면 서버는 한 방향으로만 계속 보내고, 브라우저는 같은 연결에서 이벤트를 순서대로 받습니다. WebSocket보다 단순한 대신 서버에서 클라이언트로만 보낼 수 있다는 점이 한계입니다.

gRPC와 HTTP/2 프록시

바이너리·스트리밍 RPC를 다루는 설정

서비스끼리 주고받는 호출이 늘면, 텍스트로 주고받는 기존 방식은 데이터가 커지고 연결을 매번 새로 맺는 비용도 무시할 수 없습니다. gRPC는 HTTP/2 위에서 동작하며 이진 형식으로 메시지를 주고받는 원격 호출 규약이고, 프록시는 이런 이진 데이터와 스트리밍을 그대로 다뤄야 합니다.

여러 나라 지사를 잇는 국제 택배망에 비유할 수 있습니다. 기존 HTTP/1.1이 서류를 종이로 한 건씩 보내는 방식이라면, HTTP/2는 한 대의 트럭에 여러 칸을 나눠 실어 보내는 방식이고, gRPC의 이진 형식은 내용을 압축해 포장한 화물입니다.

프록시는 이 트럭을 중계하는 물류 거점인데, 짐을 풀어 내용을 읽으려 하면 포장 규격을 알아야 하고, 모르는 채로 뜯으면 화물이 깨집니다. 그래서 프록시는 스트림을 칸 단위로 나눠 전달하고, 헤더와 트레일러를 그대로 보존하며, 긴 스트리밍 호출이 끝날 때까지 연결을 유지해야 합니다.

결국 gRPC 프록시는 연결을 하나로 재사용하는 HTTP/2의 특징과 이진 메시지 형식을 훼손하지 않는 것이 핵심입니다. 중간 장비가 HTTP/1.1로 낮춰 버리면 동작하지 않으므로, 구간마다 프로토콜 협상을 확인해야 합니다.

WebRTC와 UDP 트래픽

TCP 중심 프록시가 다루기 어려운 영역

화상 통화나 실시간 게임은 몇백 밀리초만 늦어도 대화가 겹치고, 패킷 하나가 유실되면 화면이 멈추는 TCP의 재전송 방식이 오히려 방해가 됩니다. WebRTC(웹 실시간 통신)는 UDP(User Datagram Protocol) 위에서 지연을 우선해 미디어를 주고받는 기술이고, TCP 연결을 중심으로 설계된 일반 프록시로는 다루기 어렵습니다.

우편과 전단지 배포의 차이에 비유할 수 있습니다. TCP가 수신 확인과 재발송을 보장하는 등기 우편이라면, UDP는 확인 없이 빠르게 던져 두는 전단지 배포에 가깝습니다.

리버스 프록시는 등기 우편을 접수하고 보관하는 창구라서, 확인 절차가 없는 전단지를 중계할 통로가 없습니다. 게다가 WebRTC는 처음 연결을 맺을 때 상대의 공인 주소를 알아내는 과정(시그널링, Signaling)을 거치고, 이후에는 UDP 구간을 직접 오가므로 프록시가 그 흐름에 끼어들기 어렵습니다.

그래서 이런 트래픽은 프록시를 우회하도록 두고, 시그널링과 접속 정보 교환만 프록시 뒤에서 처리하는 식으로 역할을 나누는 경우가 많습니다. 정리하면 HTTP 기반 프록시는 TCP 중심의 요청-응답 흐름에 맞춰져 있어, 지연에 민감한 UDP 미디어는 별도의 경로와 장비로 다루는 것이 일반적입니다.

TCP·UDP 스트림 프록시

L7이 아닌 L4에서 그대로 흘려보내기

웹 프록시를 HTTP 내용까지 읽어서 주소를 바꾸는 방식으로만 만들어 두면, 암호화된 연결이나 HTTP가 아닌 임의의 프로토콜은 손댈 곳이 없어 그대로 막혀 버립니다. 그래서 등장한 것이 응용 계층의 내용은 들여다보지 않고 연결만 이어 주는 TCP·UDP 스트림 프록시(stream proxy)입니다.

아파트 단지의 상수도 배관을 생각하면 이해가 쉽습니다. 관리실은 어느 집에서 물을 쓰는지, 물이 무슨 용도인지 알 필요가 없고 밸브를 열어 관로만 정확히 이어 주면 됩니다.

스트림 프록시도 마찬가지로 클라이언트와 서버 사이에 두 개의 소켓(socket)을 열고, 한쪽에서 읽은 바이트를 그대로 다른 쪽으로 흘려보냅니다. 이때 목적지 주소와 포트만 보고 판단하므로 L4(전송 계층) 프록시라고 부르고, 읽은 바이트를 잠시 담아 두는 버퍼(buffer)의 크기와 방향만 조절하면 됩니다. 결국 스트림 프록시는 연결의 양 끝을 이어 주는 배관이며, 내용을 해석하지 않기에 암호화 트래픽과 비 HTTP 프로토콜까지 그대로 중계할 수 있습니다.

대용량 파일 업로드 중계

본문을 통째로 버퍼링하지 않고 넘기는 방법

수 기가바이트짜리 파일을 프록시가 통째로 메모리에 받아 두었다가 넘기면, 서버 메모리가 금세 차고 업로드가 끝날 때까지 아무것도 전달되지 않아 시간이 두 배로 늘어납니다. 이를 피하려고 쓰는 것이 본문을 흘려보내며 중계하는 스트리밍(streaming) 방식입니다.

택배 집하장에서 10톤 트럭이 도착했을 때 창고에 짐을 전부 쌓아 두었다가 다시 트럭에 싣지 않는 것과 같습니다. 집하장은 짐을 조금씩 옮겨 싣는 컨베이어 벨트를 놓고, 앞 트럭에서 내린 상자를 뒤 트럭으로 바로 넘깁니다.

프록시도 요청 본문(request body)을 작은 조각(chunk) 단위로 읽어 업스트림 서버에 즉시 쓰고, 읽는 속도와 쓰는 속도가 다르면 잠시 기다리는 역압(backpressure)으로 흐름을 조절합니다. 이때 메모리에는 조각 하나만 있으면 되므로 파일 크기와 무관하게 메모리 사용량이 일정하고, 첫 바이트가 도착하는 시간도 짧아집니다.

정리하면 대용량 중계의 핵심은 저장 후 전달이 아니라 읽는 즉시 흘려보내는 것이고, 버퍼 크기와 역압 제어가 안정성을 좌우합니다.

다운로드 가속과 Range 요청

부분 전송 요청을 프록시가 중계하는 법

큰 파일을 한 연결로만 받으면 회선 하나의 속도에 묶여 다운로드가 오래 걸리고, 중간에 끊기면 처음부터 다시 받아야 합니다. 이때 쓰는 것이 파일의 일부분만 요청하는 Range 요청과, 이를 여러 연결로 나눠 중계하는 프록시입니다.

이사할 때 큰 장롱을 트럭 한 대에 통째로 싣지 않고 여러 대의 트럭이 구간을 나눠 나르는 것과 비슷합니다.

클라이언트는 Range 헤더에 원하는 바이트 구간을 적어 보내고, 프록시는 그 요청을 업스트림에 그대로 전달하거나 여러 구간으로 쪼개 동시에 보냅니다. 서버가 206 Partial Content로 응답하면 프록시는 Content-Range 헤더의 시작과 끝 위치를 확인해 조각들을 올바른 순서로 붙여 넘깁니다.

여러 구간이 동시에 진행되므로 전체 대역폭을 더 쓸 수 있지만, 서버가 Range를 지원하지 않으면 200 응답이 오므로 이때는 나눠 받기를 포기해야 합니다. 결국 Range 중계는 파일을 구간으로 나눠 병렬로 옮기는 방식이며, 206 응답과 Content-Range의 정확한 처리, 그리고 서버 지원 여부 확인이 핵심입니다.

쿠키와 세션의 프록시 처리

도메인·경로·보안 속성을 바꿔 넘기기

프록시가 원래 도메인 대신 다른 도메인으로 서비스를 노출하면, 브라우저는 도메인이 달라진 쿠키(cookie)를 보내지 않아 로그인이 계속 풀립니다. 이 문제를 풀려고 프록시가 쿠키의 Domain·Path·Secure 같은 속성을 바꿔 넘기는 쿠키 재작성(cookie rewriting)을 합니다.

본사 우편실이 지점의 우편물을 대신 받아 다시 발송하는 상황과 같습니다. 우편실은 봉투에 적힌 주소(Domain)와 담당 부서(Path)를 자기 기준으로 고쳐 붙이고, 잠금 봉투(Secure) 여부도 경로가 HTTPS인지에 맞춰 조정합니다.

쿠키도 마찬가지로 Set-Cookie 헤더의 Domain을 프록시 도메인에 맞추고, Path는 실제 노출 경로로 바꾸며, SameSite와 만료 시각은 서비스 정책에 맞게 유지합니다. 세션 식별자를 서버가 아니라 프록시가 들고 있는 구조라면, 쿠키 값 자체를 다른 값으로 치환해 업스트림에는 원래 값을, 클라이언트에는 가짜 값을 주는 방식도 씁니다.

정리하면 프록시에서의 쿠키 처리는 주소와 범위를 다시 붙이는 작업이며, Domain·Path·Secure·SameSite를 일관되게 맞춰야 로그인과 세션이 끊기지 않습니다.

CORS와 프록시

사전 요청과 응답 헤더를 프록시가 다루는 방식

브라우저는 다른 출처(origin)로 보내는 요청을 기본으로 막고, 허용 여부를 서버가 응답 헤더로 알려 주어야 통과시킵니다. 프록시를 두면 출처가 같아지도록 만들거나, 이 CORS(Cross-Origin Resource Sharing) 헤더를 대신 붙여 줄 수 있습니다.

방문객이 다른 회사 건물에 들어갈 때 경비실에 미리 명단을 올리고 허락을 받는 절차와 같습니다.

브라우저는 본 요청 전에 OPTIONS 메서드로 사전 요청(preflight)을 보내 어떤 메서드와 헤더가 허용되는지 묻고, 서버는 Access-Control-Allow-Origin 같은 헤더로 답합니다. 프록시가 같은 출처에 있으면 브라우저 입장에서는 사전 요청 자체가 필요 없어지고, 프록시가 업스트림 응답을 받아 헤더를 추가하거나 고쳐서 클라이언트에 돌려줄 수도 있습니다.

다만 인증 정보를 함께 보내는 요청은 Allow-Origin에 와일드카드를 쓸 수 없고 Allow-Credentials를 명시해야 하므로, 이 부분은 설정을 단정하지 말고 실제 동작을 확인해야 합니다.

결국 CORS 문제를 프록시로 푸는 방법은 출처를 하나로 모으거나 응답 헤더를 중계 시점에 정리하는 것이며, 사전 요청과 인증 정보 처리 규칙을 함께 맞추는 것이 핵심입니다.

다중 테넌트 라우팅

요청 속성으로 테넌트를 구분하는 설계

하나의 서비스가 여러 고객사(테넌트, tenant)의 데이터를 함께 다루면, 요청이 어느 고객의 것인지 잘못 판단하는 순간 다른 회사의 데이터가 섞여 나갑니다. 그래서 프록시 단계에서 요청 속성을 보고 테넌트를 확정해 각자의 백엔드로 보내는 다중 테넌트 라우팅(multi-tenant routing)이 필요합니다.

호텔 프런트 데스크가 예약 번호와 이름을 확인해 손님을 맞는 객실로 안내하는 것과 같습니다. 프런트는 예약 정보라는 요청 속성을 근거로 층과 객실을 정하고, 같은 이름이라도 예약 번호가 다르면 다른 방으로 보냅니다.

프록시도 호스트 이름, 경로 접두사, 헤더의 테넌트 식별자, 인증 토큰의 클레임 같은 속성으로 테넌트를 판별하고, 그 결과를 업스트림 주소나 헤더에 반영합니다. 이때 판별 규칙의 우선순위를 정해 두지 않으면 같은 요청이 서로 다른 테넌트로 해석될 수 있으므로, 규칙을 한 곳에 모으고 일관되게 적용해야 합니다.

정리하면 다중 테넌트 라우팅은 요청에 실린 식별 정보를 근거로 목적지를 가르는 설계이며, 판별 규칙의 단일화와 테넌트 경계의 명확한 검증이 안전을 좌우합니다.

레거시 프로토콜 중계

구형 시스템을 감싸 안전하게 노출하는 방법

구형 시스템이 예전 방식으로만 대화를 받아들이면, 새 시스템은 그 말을 알아듣지 못해 연결 자체를 포기하게 됩니다. 이때 중간에 서서 양쪽 말을 서로 통하게 바꿔 주는 것이 레거시 프로토콜 중계(legacy protocol relay)입니다. 오래된 아파트에 새 택배 기사가 찾아온 상황을 떠올리면 쉽습니다. 새 기사는 정해진 앱으로만 문을 열 수 있지만 그 아파트 경비실은 종이 장부와 구형 인터폰만 씁니다.

그래서 경비실에 새 단말기를 하나 두고, 앱의 요청을 받아 인터폰 신호로 바꿔 호출한 뒤 결과를 다시 앱 형식으로 돌려주게 합니다. 이때 단말기는 내용을 해석하지 않고 형식만 바꿔 전달하며, 허용된 호출만 통과시켜 구형 시스템이 감당할 수 있는 범위를 지킵니다. 결국 레거시 프로토콜 중계는 구형 시스템을 고치지 않은 채 앞단에서 프로토콜(protocol)을 변환해 안전하게 노출하는 계층입니다. 덕분에 교체 비용과 위험을 미루면서 새 시스템과 나란히 운영할 수 있습니다.

트래픽 미러링

실제 요청을 복제해 새 버전에 흘려보내기

새 버전을 내놓기 전에 실제 요청으로 시험하고 싶지만, 사용자를 새 시스템으로 보내는 순간 문제가 생기면 되돌릴 수 없습니다. 이 위험을 줄이려고 실제 요청을 복제해 새 버전에만 흘려보내는 트래픽 미러링(traffic mirroring)을 씁니다. 원본 편지를 보내면서 사본을 하나 더 만들어 다른 부서에 참고용으로 돌리는 사무실을 생각하면 됩니다. 프록시가 들어오는 요청을 그대로 처리해 응답하는 한편, 같은 요청의 복제본을 따로 떠서 신버전 서버로 보냅니다.

신버전이 보낸 응답은 사용자에게 돌아가지 않고 버려지거나 기록만 되며, 원본 응답 속도에 영향을 주지 않도록 복제 전송은 보통 비동기로 이뤄집니다. 다만 복제된 요청이 실제 결제나 메일 발송 같은 부수 효과를 일으키지 않도록 쓰기 동작을 막거나 분리된 환경으로 보내야 합니다. 트래픽 미러링은 사용자에게 보이는 응답과 시험용 복제 흐름을 분리해, 실서비스와 같은 입력으로 새 버전을 검증하는 기법입니다. 관찰만 하고 결과는 버린다는 점이 카나리 배포와 다른 핵심입니다.

액세스 로그 설계

무엇을 남기고 무엇을 남기지 않을지

모든 요청을 다 남기면 저장 비용이 감당이 안 되고, 반대로 너무 적게 남기면 장애가 났을 때 무슨 일이 있었는지 알 수 없습니다. 그래서 무엇을 남기고 무엇을 남기지 않을지 먼저 정하는 액세스 로그 설계(access log design)가 필요합니다. 건물 출입 기록부를 만드는 일과 비슷합니다. 누가, 언제, 어느 문으로 들어와 어디로 갔는지는 남기되, 가방 안에 뭐가 들었는지까지 적지는 않습니다.

프록시도 시각, 클라이언트 주소, 메서드와 경로, 상태 코드, 처리 시간, 응답 크기, 요청 식별자 정도를 기본으로 남기고, 비밀번호나 토큰, 개인 식별 정보처럼 민감한 값은 기록 전에 가립니다. 또 보존 기간과 샘플링 비율을 정해 두어야 로그가 무한정 쌓이지 않습니다. 정리하면 액세스 로그는 요청 한 건을 재현하고 추적할 수 있는 최소 정보만 남기고 민감 정보는 지우는 설계입니다. 목적과 보존 기간을 먼저 정하는 것이 형식보다 앞섭니다.

로그 포맷과 구조화

로그도 시각, 수준, 서비스 이름, 요청 식별자, 메시지를 각각 키와 값으로 분리해 JSON 같은 형식으로 남기면, 검색 도구가 특정 필드만 골라 세거나 거를 수 있습니다. 대신 필드 이름과 시각 표기, 수준 이름 같은 규칙을 팀 전체가 미리 맞춰야 효과가 납니다. 로그 포맷과 구조화는 로그를 읽는 대상이 사람에서 프로그램으로 넓어졌다는 변화를 담는 작업입니다. 필드 규칙을 통일해 두면 수집과 분석이 훨씬 단순해집니다.

지연 시간 측정

프록시 구간과 백엔드 구간을 나눠 보기

이 값들의 차이로 연결 수립 시간, 업스트림 대기 시간, 응답 전송 시간을 따로 계산할 수 있습니다. 이렇게 나눠 두면 느림이 네트워크 구간인지 백엔드 처리인지 빠르게 가려낼 수 있습니다. 지연 시간 측정의 핵심은 요청 하나에 여러 시각 도장을 찍어 구간별 소요를 분리하는 것입니다. 합계만 보지 않고 구간을 나눠야 개선 지점이 보입니다.

반대로 다시 정상 응답이 이어지면 목록에 되돌려 놓는데, 이 판단 기준을 너무 예민하게 잡으면 잠깐의 지연에도 서버가 빠져 전체 용량이 흔들립니다. 그래서 실패 횟수, 확인 주기, 복귀 조건을 함께 조정하며, 단순한 응답 여부뿐 아니라 대기 요청 수나 오류 비율 같은 지표도 같이 봅니다. 업스트림 상태 모니터링은 개별 백엔드의 건강을 주기적으로 재고 판정해 트래픽 분배에 반영하는 체계입니다. 확인과 복귀의 기준을 신중히 잡아야 불필요한 흔들림 없이 가용성을 지킬 수 있습니다.

에러율과 상태 코드 분포

문제를 조기에 감지하는 신호

리버스 프록시 뒤에 있는 서버가 조용히 절반의 요청에 실패하고 있는데도 아무도 모르는 상황이 있습니다. 전체 응답 시간의 평균만 보는 화면은 이런 부분적인 고장을 평균값 속에 묻어 버리기 때문에, 실패의 크기와 성격을 따로 지켜보는 지표가 필요합니다.

택배 회사를 생각해 보면, 하루에 나간 상자 중 몇 개가 되돌아왔는지를 세는 반송률과, 사유가 주소 오류인지 파손인지를 나눠 세는 사유별 분류가 함께 있어야 합니다. 반송률은 실패의 전체 크기를 알려 주고, 사유별 분류는 어디를 먼저 고쳐야 하는지를 알려 줍니다.

프록시가 남기는 접근 로그의 상태 코드(status code)가 바로 이 사유별 분류에 해당하는데, 200번대는 정상 처리, 400번대는 요청 자체가 잘못된 경우, 500번대는 뒤쪽 서버 쪽 사고, 502번과 504번은 뒤쪽 서버와 연락이 끊기거나 응답이 늦은 경우로 읽습니다. 여기에 400번대와 500번대를 따로 세는 비율을 얹으면, 이용자가 잘못한 일과 우리 쪽이 잘못한 일을 섞지 않고 볼 수 있습니다.

결국 에러율은 실패의 크기를, 상태 코드 분포는 실패의 성격을 보여 주는 두 축이며, 프록시 계층에서 이 둘을 함께 집계해야 사용자의 항의가 들어오기 전에 문제를 알아챌 수 있습니다.

분산 추적(Distributed Tracing)

요청 ID로 여러 구간을 하나로 잇기

요청 하나가 프록시를 지나 여러 마이크로서비스를 거치는데, 사용자가 느린 화면을 신고했을 때 어느 구간에서 시간이 새는지 알 수 없으면 담당자들은 서로 자기 쪽은 문제가 없다고 말하게 됩니다. 이때 요청마다 고유한 식별자를 붙여 구간별 기록을 하나로 묶는 분산 추적(Distributed Tracing)이 답이 되며, 리버스 프록시는 그 식별자를 처음 만들어 붙이는 출발점 역할을 합니다.

택배 한 건에 송장번호가 하나 붙어 있고, 집하장과 중간 터미널과 배송 기사가 각각 그 번호로 도착 시각과 출발 시각을 찍어 두면, 나중에 어느 구간에서 이틀이나 멈춰 있었는지 한눈에 드러납니다.

분산 추적도 같은 원리여서, 프록시가 요청마다 추적 ID(trace ID)를 발급해 뒤로 넘길 때 헤더에 실어 보내면 각 서비스는 그 ID와 자기 구간의 시작 시각과 끝 시각, 그리고 자기를 호출한 상위 구간 정보를 남깁니다. 이렇게 모인 조각을 같은 ID끼리 이어 붙이면 요청 하나가 지나온 전체 경로가 나무 모양으로 그려지고, 어느 구간이 병목인지가 시간 비중으로 드러납니다.

프록시는 여기에 자기 구간을 하나 더 얹고, 뒤쪽으로 ID를 전달하지 않는 서비스가 있으면 추적이 그 자리에서 끊기므로 헤더 전달 규칙을 정해 두는 것이 중요합니다.

정리하면 분산 추적은 요청 ID를 공통 열쇠로 삼아 흩어진 구간 기록을 하나의 흐름으로 복원하는 기법이고, 그 첫 고리를 프록시에서 놓치지 않아야 전체 그림이 완성됩니다.

설계의 핵심은 증상이 아니라 원인에 가까운 신호를 고르는 일이라서, 서버 한 대의 CPU 사용률 같은 중간 지표보다 이용자가 실제로 실패를 겪고 있는지를 보여 주는 에러율과 지연 시간의 상위 백분위 값이 경보의 기준이 됩니다. 경보에는 심각도와 담당자, 그리고 같은 경보가 반복될 때 하나로 묶어 주는 조건을 함께 적어 두고, 대시보드는 위에서부터 서비스 전반, 세부 엔드포인트, 개별 인스턴스 순으로 내려가며 보도록 배치합니다.

결국 대시보드는 현재를 넓게 보여 주는 창이고 알림은 행동이 필요한 순간만 찌르는 신호이며, 둘의 역할을 섞지 않아야 경보가 의미를 잃지 않습니다.

용량 산정과 부하 테스트
