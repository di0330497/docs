데이터를 파일에 직접 저장하고 애플리케이션마다 읽고 쓰는 코드를 만들면, 여러 사용자가 동시에 접근할 때 값이 서로 덮어써지고 일부만 저장되는 문제가 생긴다. 또 데이터를 어떤 규칙으로 넣고 꺼낼지가 프로그램마다 제각각이면, 도구를 바꾸거나 서버를 옮길 때마다 저장 형식과 접근 코드를 전부 다시 만들어야 한다. 여러 사람이 같은 데이터를 안전하게 공유하고, 정해진 질의 언어로 다룰 수 있는 공용 저장·관리 시스템이 필요해졌다.

#2핵심 질문

여러 애플리케이션이 하나의 데이터를 안전하게 공유하고 표준 질의 언어로 다루려면 무엇이 필요한가?

#3동작 예시

MySQL 서버를 설치해 실행하면, 클라이언트가 SQL 문장을 보내고 서버가 그것을 해석해 저장된 데이터를 읽거나 바꾼다. 예를 들어 SELECT name FROM users WHERE id = 1;을 보내면 서버는 users 테이블에서 id가 1인 행을 찾아 name 열 값만 돌려준다. 저장 위치나 파일 형식을 클라이언트가 몰라도 되고, 서버가 동시 접근과 권한을 관리한다.

#4동작 과정

  1. 릴리스 선택MySQL은 Innovation과 LTS 두 흐름으로 배포된다. Innovation은 새 기능이 빠르게 들어가는 릴리스이고, LTS(Long-Term Support)는 장기 지원을 목표로 안정성과 지원 기간을 중시하는 릴리스다.
  2. 표준 준수서버는 SQL 표준을 상당 부분 따르되, 표준과 다른 자체 확장 문법도 함께 제공한다. 표준 준수 범위와 차이는 문서의 Standards Compliance 항목에서 확인한다.
  3. 질의 처리클라이언트가 보낸 SQL을 서버가 접수해 문법을 검사하고, 권한과 대상을 확인한 뒤 데이터를 읽거나 변경하고 결과를 반환한다.

설치 개요와 플랫폼별 설치(Unix 바이너리·Windows·macOS)

설치 전 공통 고려 사항과 함께 Unix/Linux 바이너리, Windows, macOS 등 플랫폼별로 MySQL을 설치하는 방법을 정리한 항목이다.

#1문제 상황

MySQL을 쓰려면 먼저 서버 프로그램과 클라이언트 도구를 컴퓨터에 설치해야 한다. 그런데 운영체제마다 파일 배치와 실행 방식이 다르고, 같은 운영체제에서도 압축 파일을 풀어 쓰는 방식과 설치 관리자를 쓰는 방식이 나뉜다. 설치 안내 없이 아무 패키지나 받으면 지원되지 않는 플랫폼이거나 서버와 클라이언트 버전이 어긋나서, 뒤늦게 실행이 안 되거나 데이터 형식이 맞지 않는 문제가 생긴다.

#2핵심 질문

내 운영체제와 설치 방식에 맞는 MySQL 버전과 배포판을 어떻게 골라 설치하는가?

#3동작 예시

Windows에서는 MSI 설치 관리자를 실행하면 서버가 설치되고 MySQL Configurator가 초기 설정을 도와준다. Unix/Linux에서 범용 바이너리를 쓰면 압축을 푼 디렉터리를 정하고 초기화 명령으로 데이터 디렉터리를 만든 뒤 서버를 시작한다. 두 경우 모두 "지원 플랫폼 확인 → 버전 선택 → 패키지 확보 → 설치" 순서를 따른다.

#4동작 과정

  1. 지원 플랫폼과 버전 확인설치 전에 자신의 운영체제가 지원 목록에 있는지, 어떤 버전과 배포판을 받아야 하는지 먼저 정한다. 문서의 Supported Platforms와 Which MySQL Version and Distribution to Install이 기준을 제공한다.
  2. 패키지 확보와 무결성 검증공식 배포처에서 설치 파일을 받고, MD5 체크섬이나 GnuPG로 파일이 변조·손상되지 않았는지 확인한다. 이 단계를 건너뛰면 손상된 파일을 설치할 수 있다.
  3. 플랫폼별 설치 수행Unix/Linux 범용 바이너리는 압축을 풀어 배치하고, Windows는 MSI와 Configurator를, macOS는 네이티브 패키지를 이용한다. 설치 후에는 데이터 디렉터리 초기화와 서버 기동이 뒤따른다.

→ 01-02 참조

#1문제 상황

Linux에서 MySQL을 설치하는 방법은 하나가 아니다. 배포판 기본 저장소에서 받거나, Oracle이 제공하는 전용 저장소를 쓰거나, RPM·Debian 패키지·Docker 이미지를 쓰거나, 소스 코드를 직접 컴파일할 수 있다. 각 방법은 지원 범위와 업데이트 방식이 달라서, 아무 방법이나 고르면 배포판에 없는 버전이 설치되거나 이후 업그레이드 경로가 어긋난다. 상황에 맞는 설치 방식을 명확히 정하는 것이 문제다.

#2핵심 질문

Linux에서 어떤 설치 방식을 골라야 버전과 업데이트 경로를 예측 가능하게 관리할 수 있는가?

#3동작 예시

Oracle은 전용 저장소 사용을 권장한다. 예를 들어 MySQL Yum Repository를 시스템에 등록하면 yum 같은 패키지 관리자로 서버를 설치하고 이후에도 같은 명령으로 업데이트할 수 있다. 패키지 관리자가 의존성과 버전을 처리하므로 설치와 업그레이드가 일관된다.

#4동작 과정

  1. 방식 선택Yum/APT/SLES 저장소, Oracle의 RPM·Debian 패키지, Docker 컨테이너, 배포판 네이티브 저장소, 소스 컴파일 중에서 환경과 지원 요구에 맞는 방식을 고른다. Oracle 배포판을 쓰는 방법을 권장한다.
  2. 저장소 등록과 설치선택한 저장소를 시스템에 등록하고 패키지 관리자로 서버를 설치한다. 등록해 두면 이후 버전 올리기도 같은 통로로 처리된다.
  3. 소스 설치나 서비스 관리특수한 요구가 있으면 소스에서 컴파일해 설치한다. 그 밖에는 systemd로 서버를 시작·중지·자동 기동하도록 관리한다.

설치 후 초기화·테스트와 초기 계정 보안

설치 후 데이터 디렉터리 초기화, 서버 기동 테스트, 그리고 초기 root 계정 보안 설정까지의 과정을 다루는 항목이다.

#1문제 상황

설치만 끝내면 서버는 바로 쓸 수 있는 상태가 아니다. 데이터를 담을 디렉터리와 권한 정보를 담은 테이블이 준비되지 않았으면 서버가 시작되지 않는다. 게다가 초기 상태의 root 계정은 비밀번호가 없거나 알려진 값이라, 그대로 외부에 열어 두면 누구나 접속해 데이터를 읽고 지울 수 있다. 초기화와 보안 설정을 빠뜨리면 이후 모든 작업이 불안정하거나 위험해진다.

#2핵심 질문

설치 직후 서버를 쓸 수 있게 만들고 초기 계정을 안전하게 잠그려면 무엇을 해야 하는가?

#3동작 예시

서버가 설치된 뒤 데이터 디렉터리를 초기화하면 시스템 테이블과 grant 테이블이 생성된다. 이어서 서버를 시작하고 클라이언트로 접속해 간단한 질의가 응답하는지 확인한다. 마지막으로 초기 root 계정에 비밀번호를 설정하고 원격 접속을 막아, 기본 자격 증명으로 들어올 수 없게 만든다.

#4동작 과정

  1. 데이터 디렉터리 초기화저장 공간과 권한·계정 정보를 담는 grant 테이블을 만든다. 일부 설치 방식(Windows MSI·Configurator, Oracle의 서버 RPM·Debian 패키지 등)은 이 과정을 자동으로 처리한다.
  2. 서버 기동과 테스트서버를 시작한 뒤 클라이언트로 접속해 질의가 정상 응답하는지 확인한다. 여기서 실패하면 초기화나 설정 문제를 먼저 해결한다.
  3. 초기 계정 보안초기 MySQL 계정의 비밀번호를 설정하고 불필요한 원격 접속을 차단하며, 필요하면 부팅 시 자동 시작·중지를 설정한다.

업그레이드 준비와 경로

기존 MySQL 설치를 9.7 LTS로 올리기 전에 대상 버전과 지원되는 상향 경로(예: 8.0/8.4 → 9.7) 및 릴리스 간 변경 사항을 확인하고 백업·점검 등 사전 요구사항을 준비하는 단계

#1문제 상황

사용 중인 MySQL을 상위 버전으로 올리려 할 때, 아무 버전에서나 곧바로 최신으로 건너뛸 수 있는 것은 아니다. 중간에 거쳐야 하는 릴리스가 있고, 릴리스마다 제거되거나 기본값이 바뀐 기능이 있어서 준비 없이 진행하면 서버가 시작되지 않거나 데이터가 손상될 수 있다. 또 업그레이드는 되돌리기 어려운 작업이라, 사전 점검과 백업 없이 실행하면 문제가 생겼을 때 복구할 방법이 없다.

#2핵심 질문

현재 버전에서 9.7 LTS로 안전하게 올리려면 어떤 경로와 사전 준비가 필요한가?

#3동작 예시

8.0이나 8.4에서 9.7로 올리는 경우, 문서의 Upgrade Paths를 확인해 지원되는 상향 경로인지 먼저 검사한다. 이어서 9.7에서 달라지거나 제거된 항목을 점검하고, 데이터와 설정을 백업한 뒤 실제 업그레이드 절차로 넘어간다. 준비 단계에서 경로가 어긋나면 여기서 중단한다.

#4동작 과정

  1. 경로와 변경 사항 확인현재 버전에서 목표 9.7까지 지원되는 상향 경로인지 확인하고, 릴리스별 변경·제거·기본값 변화를 미리 살핀다. 3.5 Changes in MySQL 9.7이 근거가 된다.
  2. 백업과 사전 점검데이터와 설정을 백업하고, 업그레이드 대상이 무엇인지 파악한다. 문제 발생 시 되돌릴 수 있는 지점을 확보한다.
  3. 모범 사례 적용준비와 실행에 관한 권장 절차(Best Practices)에 따라 순서를 지킨다. 이 준비가 끝나야 실제 업그레이드 실행으로 넘어간다.

Unix/Linux 바이너리·패키지 설치, YUM/APT/SLES 저장소, Windows, Docker 등 설치 방식과 플랫폼에 맞는 절차로 실제 MySQL 서버를 상위 버전으로 교체·재기동하는 작업

#1문제 상황

업그레이드 준비가 끝났어도 실제 실행은 설치 방식마다 다르다. Unix/Linux 바이너리·패키지 설치, Yum/APT/SLES 저장소 설치, Windows 설치, Docker 설치가 각각 다른 절차를 요구한다. 방식에 맞지 않는 순서로 진행하면 예전 바이너리와 새 데이터 디렉터리가 섞이거나, 서버가 뜨지 않거나, 남은 구성 요소가 갱신되지 않아 오류가 난다. 또 업그레이드는 되돌리기 어려워 실행 중 문제 진단이 중요하다.

#2핵심 질문

내 설치 방식과 플랫폼에 맞춰 실제 서버 교체와 재기동을 어떻게 수행하는가?

#3동작 예시

Unix/Linux의 바이너리 설치에서 In-Place Upgrade는 이전 서버를 종료하고, 기존 바이너리나 패키지를 새 버전으로 교체한 뒤, 기존 데이터 디렉터리 위에서 서버를 다시 시작하고 갱신이 필요한 나머지 부분을 올린다. 데이터를 그대로 두고 프로그램만 교체하는 방식이다.

#4동작 과정

  1. 방식 결정In-Place Upgrade(기존 데이터 디렉터리를 그대로 두고 바이너리·패키지만 교체)와 Logical Upgrade(덤프를 내보내 새 서버에 다시 적재) 중에서 상황에 맞는 방법을 고른다. 저장소 설치면 Yum/APT/SLES 통로를 쓴다.
  2. 서버 종료와 교체실행 중인 서버를 안전하게 종료하고, 이전 바이너리나 패키지를 새 버전으로 바꾼다. Windows는 Windows용 절차를, Docker는 컨테이너 이미지 교체 절차를 따른다.
  3. 재기동과 잔여 갱신기존 데이터 디렉터리로 서버를 다시 시작하고, 업그레이드가 필요한 남은 구성 부분을 갱신한다. 문제가 생기면 Upgrade Troubleshooting 절차로 원인을 찾는다.

테이블 재구축·데이터베이스 복사·다운그레이드

업그레이드 후 테이블/인덱스를 재구축(REPAIR·ALTER 등)해 호환성을 맞추고, 데이터베이스를 다른 서버로 복사하며, 필요 시 데이터 손실 없이 이전 버전으로 되돌리는 방법

#1문제 상황

업그레이드나 다운그레이드 후에는 예전 테이블과 인덱스가 새 버전의 데이터 형식이나 문자 집합 처리 방식과 맞지 않을 수 있다. 예를 들어 콜레이션(문자열 비교·정렬 규칙)의 오류가 수정되면, 그 규칙을 쓰는 문자 열의 인덱스를 다시 만들어야 한다. 또 CHECK TABLE이나 mysqlcheck가 테이블 수리·업그레이드를 요구하기도 한다. 이런 상태를 방치하면 질의 결과가 틀리거나 인덱스가 정상 동작하지 않는다.

#2핵심 질문

버전이 바뀐 뒤 어긋난 테이블과 인덱스를 다시 맞추고, 필요하면 이전 버전으로 안전하게 되돌리려면 어떻게 하는가?

#3동작 예시

콜레이션 변경으로 인덱스를 다시 만들어야 할 때는 Dump and Reload Method로 테이블 데이터를 덤프해 내보낸 뒤 다시 적재하거나, ALTER TABLE Method로 테이블을 재구축한다. 필요에 따라 REPAIR TABLE로 수리하기도 한다. 데이터를 새 형식에 맞게 다시 써 넣는 방식이다.

#4동작 과정

  1. 재구축 필요 여부 판단CHECK TABLE이나 mysqlcheck가 알려주는 수리·업그레이드 요구, 그리고 데이터 형식·문자 집합 처리 변경 여부를 확인해 재구축이 필요한 대상을 정한다.
  2. 재구축 방법 실행Dump and Reload, ALTER TABLE, REPAIR TABLE 중 상황에 맞는 방법으로 테이블이나 인덱스를 다시 만든다. 다른 버전이 테이블을 다룰 수 없어 생긴 문제라면 덤프·재적재 방식을 쓴다.
  3. 복사와 다운그레이드데이터베이스를 다른 서버로 옮길 때는 제공되는 복사 절차를 따르고, 이전 버전으로 되돌려야 하면 Downgrading MySQL 절차로 데이터 손실 없이 다운그레이드한다.

튜토리얼 — 접속과 데이터베이스 기초 조작

mysql 클라이언트로 서버에 접속·해제하고, 데이터베이스와 테이블을 만들고 조회하며 정보를 얻는 기본 사용 흐름을 익히는 입문 튜토리얼이다.

#1문제 상황

MySQL 서버를 처음 설치하면 서버 프로세스만 떠 있을 뿐, 사용자가 어떤 순서로 접속하고 무엇을 입력해야 하는지 알 길이 없다. 클라이언트 프로그램마다 옵션과 문법이 달라 입문자는 접속 파라미터(호스트·사용자·비밀번호)를 어디에 어떤 형태로 넘기는지부터 막힌다.

이 상태에서는 서버가 정상인지 확인할 방법도, 데이터를 담을 데이터베이스를 만들고 테이블에 값을 넣는 절차도 없어 아무 작업도 시작할 수 없다. 공식 매뉴얼도 이 진입 절차를 별도 장으로 묶어 순서대로 안내할 필요가 있었다.

#2핵심 질문

서버에 접속하고, 데이터를 담을 데이터베이스와 테이블을 만든 뒤 정보를 조회하기까지의 최소 흐름은 무엇인가?

#3동작 예시

mysql 클라이언트를 띄우고 호스트(-h), 사용자(-u), 비밀번호(-p)를 주어 서버에 연결하면 mysql> 프롬프트가 나타난다. 여기에 CREATE DATABASE menagerie; 를 입력해 데이터베이스를 만들고, USE menagerie; 로 선택한 뒤 CREATE TABLE pet (...); 로 테이블을 생성한다. 이후 SHOW TABLES; 나 DESCRIBE pet;, SELECT * FROM pet; 같은 문장을 입력하면 현재 데이터베이스의 테이블 목록·구조·행 데이터가 바로 출력된다.

#4동작 과정

  1. 서버 접속과 해제mysql -h host -u user -p 형태로 클라이언트를 실행하면 지정한 호스트의 서버에 인증해 연결하고 mysql> 프롬프트를 띄운다. 작업이 끝나면 quit 또는 exit 를 입력해 연결을 닫는다.
  2. 데이터베이스와 테이블 생성CREATE DATABASE 로 데이터베이스를 만들고 USE 로 그 데이터베이스를 선택한다. 이어 CREATE TABLE 로 열(컬럼)과 타입을 정의한 테이블을 만들면 이제 데이터를 담을 그릇이 준비된다.
  3. 데이터 적재와 조회INSERT 나 LOAD DATA 로 행을 넣고, SELECT ... WHERE ... ORDER BY ... 로 원하는 행을 골라낸다. SHOW·DESCRIBE 계열 문장은 데이터베이스·테이블·열의 정보를 돌려주어 현재 구조를 파악하게 해준다.

#1문제 상황

대화형 mysql 세션에서는 사람이 문장을 하나씩 입력하며 결과를 눈으로 확인하지만, 같은 문장을 매번 반복 입력하거나 정해진 순서를 여러 번 재현하기는 번거롭다. 스케줄러나 배포 작업에서 매번 손으로 프롬프트에 타이핑할 수도 없다.

문장을 파일에 모아 두고 통째로 실행하는 방법이 없으면 반복 작업은 자동화되지 않는다. 또 실습 단계에서는 특정 결과를 뽑는 대표 쿼리 패턴과, 웹 서버에서 MySQL에 붙는 방법을 어디서 배워야 하는지가 드러나지 않는다.

#2핵심 질문

대화형 입력 대신 파일에 담은 문장을 한꺼번에 실행하고, 그 결과를 다시 쓰기 위한 대표 쿼리와 연동 방식은 무엇인가?

#3동작 예시

실행할 SQL 문장을 batch-file 에 적어 두고 셸에서 mysql < batch-file 로 리다이렉션하면, 클라이언트가 그 파일의 문장을 순서대로 읽어 실행하고 결과를 출력한다. 접속 파라미터가 필요하면 mysql -h host -u user -p < batch-file 처럼 옵션을 붙이고, 파일에 문제를 일으키는 특수 문자가 있으면 mysql -e 'source batch-file' 로 실행한다.

#4동작 과정

  1. 스크립트 준비와 입력 리다이렉션실행할 문장들을 파일 하나에 모으고, 셸의 입력 리다이렉션(<)이나 source 로 mysql 에 넘긴다. 대화형 타이핑 없이도 같은 문장 묶음을 반복 실행할 수 있게 된다.
  2. 배치 실행과 오류 처리클라이언트가 파일의 문장을 차례로 실행해 결과를 표준 출력으로 내보낸다. 중간에 실패한 문장이 있어도 스크립트를 계속 진행하게 할 수 있어, 여러 단계를 한 번에 돌리는 자동화에 맞는다.
  3. 결과 재활용과 웹 연동출력 결과를 다시 가공하거나 대표 쿼리 패턴으로 원하는 행을 뽑아내고, Apache 같은 웹 서버에서 MySQL에 접속해 데이터를 읽고 쓰는 구성으로 확장한다.

MySQL에 포함된 각종 프로그램의 종류를 개관하고, 프로그램 공통의 명령행 옵션과 접속·인증 옵션을 지정하는 방법을 설명한다.

#1문제 상황

MySQL 설치에는 서버와 클라이언트, 설치·관리 도구 등 여러 실행 파일이 함께 들어 있어, 무엇이 어떤 역할을 하고 어떻게 부르는지 모르면 필요한 프로그램을 찾지 못한다. 프로그램마다 옵션 이름도 제각각이라, 접속 정보를 어디에 지정해야 하는지 매번 헷갈린다.

플랫폼마다 포함되는 프로그램이 다르고, 배포 패키지에 따라 서버용과 클라이언트용이 나뉘어 있어 개관 없이 개별 문서만 보면 전체 그림이 잡히지 않는다.

#2핵심 질문

설치된 여러 MySQL 프로그램은 각각 무슨 역할이며, 공통으로 접속과 동작을 지정하는 옵션은 어떻게 다루는가?

#3동작 예시

서버에 붙어 문장을 실행하는 것은 mysql 클라이언트이고, 서버를 띄우는 것은 mysqld 서버 프로그램이다. mysql -h host -u user -p 처럼 호스트·사용자·비밀번호 옵션을 붙여 대상을 지정하고, 같은 옵션을 명령행 대신 옵션 파일에 적어 두면 실행할 때 그 값이 적용된다.

#4동작 과정

  1. 프로그램 종류 파악설치에 어떤 실행 파일이 있는지 개괄을 통해 서버·클라이언트·관리·설치용으로 나누어 파악한다. 각 프로그램의 문서에는 호출 문법과 지원하는 옵션이 함께 표시된다.

#3동작 예시

서버를 처음 설치하면 데이터 디렉터리 아래에 여러 하위 디렉터리가 생긴다. 그중 mysql 디렉터리에는 서버가 실행 중에 필요로 하는 정보를 담은 데이터 사전 테이블과 시스템 테이블이 들어 있고, 사용자가 만든 각 데이터베이스마다 그 이름과 같은 하위 디렉터리가 하나씩 대응한다. 서버는 이 경로를 기준으로 스키마를 찾고 로그 파일을 기록한다.

#4동작 과정

  1. 데이터 디렉터리 지정서버가 시작할 때 datadir 설정에 적힌 경로를 데이터 저장의 기준 위치로 삼는다. 이 아래에 각 데이터베이스에 대응하는 하위 디렉터리와 테이블·로그 파일이 놓인다.
  2. mysql 시스템 스키마 읽기mysql 디렉터리를 mysql 시스템 스키마(서버 운영에 필요한 계정·권한 등 메타데이터를 담는 표준 데이터베이스)로 사용해, 서버가 실행 중에 필요한 정보를 여기서 읽는다.
  3. 서버 로그 기록오류·일반·슬로우 쿼리 같은 서버 로그가 같은 영역에 파일로 남아, 서버에 무슨 일이 있었는지 사후에 확인할 수 있게 한다.

#1문제 상황

서버에 새 기능을 넣으려면 서버 코드를 다시 빌드해 배포해야 한다면, 기능 하나를 추가할 때마다 전체를 멈추고 교체해야 한다. 서드파티가 만든 인증 방식이나 감사 기능처럼 MySQL 기본 배포에 없는 기능을 붙이려면 통합 방법도 제각각이라 관리가 어렵다. MySQL은 서버를 다시 빌드하지 않고도 기능을 끼웠다 뺄 수 있는 확장 방식을 제공해 이 문제를 해결한다. 다만 확장 방식이 하나가 아니어서, 어떤 것을 언제 쓰는지 구분해야 한다.

#2핵심 질문

서버를 다시 빌드하지 않고 기능을 추가하거나 제거하려면 어떤 확장 방식을 써야 하는가?

#3동작 예시

오류 로그를 남기는 컴포넌트 하나를 설치한다고 하자. 서버는 로더블 함수로 등록된 함수를 SQL 문에서 호출해 실행하고, 컴포넌트는 서버와 다른 컴포넌트가 서비스로 노출한 기능을 서로 주고받는 방식으로 붙는다. 설치와 제거는 서버를 멈추지 않고 명령으로 처리된다.

#4동작 과정

  1. 컴포넌트 설치서버에 기능을 추가하는 컴포넌트를 설치하면, 컴포넌트가 제공하는 서비스가 서버와 다른 컴포넌트에서 쓸 수 있게 된다. 컴포넌트끼리는 오직 이 서비스로만 상호작용한다.
  2. 플러그인 로드서버 플러그인은 서버 시작 시점에 정해진 방식으로 로드되어, 인증·스토리지 엔진 같은 기능을 서버에 붙인다.
  3. 로더블 함수 등록CREATE FUNCTION으로 로더블 함수를 등록하면, SQL 문에서 그 함수를 불러 실행할 수 있게 되어 서버 기능이 SQL 계층까지 확장된다.

다중 인스턴스 운영과 디버깅

한 머신에서 포트·데이터 디렉터리·소켓을 달리해 여러 mysqld 인스턴스를 동시에 운영하는 방법과, 서버 문제를 추적하기 위한 디버깅 기법.

#1문제 상황

운영 중인 서버 하나를 멈추지 않고 새 버전을 시험하고 싶거나, 여러 사용자에게 각자 관리하는 별도의 서버를 주고 싶을 때, 머신마다 서버를 하나씩만 돌려야 한다면 장비가 그만큼 필요해진다. 또 서버가 예상과 다르게 동작할 때 무엇이 문제인지 추적할 수단이 없으면 원인을 좁히지 못한다. MySQL은 한 머신에서 여러 인스턴스를 동시에 돌리는 방법과, 서버 문제를 추적하는 디버깅 기법을 함께 제공해 이 두 문제를 다룬다. 운영을 건드리지 않고 시험 서버를 따로 띄울 수 있게 하는 것이 핵심이다.

#2핵심 질문

머신 하나에서 여러 MySQL 인스턴스를 충돌 없이 동시에 돌리려면 무엇을 서로 다르게 잡아야 하는가?

#3동작 예시

같은 머신에서 두 mysqld를 띄운다고 하자. 첫 번째는 3306 포트와 데이터 디렉터리 A를, 두 번째는 다른 포트와 데이터 디렉터리 B를 쓰게 하고 각기 다른 소켓 파일을 갖게 한다. 서버가 공유하는 자원을 겹치지 않게 나눠 주면 두 인스턴스가 서로 간섭하지 않고 각자 독립적으로 동작한다.

#4동작 과정

  1. 자원 분리 설정인스턴스마다 포트·데이터 디렉터리·소켓을 서로 다른 값으로 잡아, 두 서버가 같은 파일이나 통신 지점을 두고 충돌하지 않게 한다.
  2. 데이터 디렉터리 각각 준비인스턴스별로 데이터 디렉터리를 따로 만들어 초기화한다. 각 인스턴스는 자기 디렉터리의 데이터와 mysql 시스템 스키마만 본다.
  3. 개별 기동과 문제 추적각 mysqld를 자기 설정으로 띄우고, 클라이언트는 접속할 포트나 소켓을 지정해 원하는 인스턴스에 붙는다. 문제가 생기면 디버깅 기법으로 어느 인스턴스의 무슨 동작이 어긋났는지 추적한다.

일반 보안 지침과 공격 대비

MySQL 서버를 운영할 때 비밀번호 노출, SQL 인젝션, 권한 오남용 같은 흔한 공격을 막기 위해 지켜야 하는 기본 보안 수칙을 정리한 지침.

#1문제 상황

MySQL을 기본 상태로 두면 비밀번호가 평문으로 노출되거나, 애플리케이션이 입력값을 그대로 SQL에 붙이면서 SQL 인젝션 공격에 뚫리거나, 필요 이상으로 넓은 권한을 가진 계정이 남아 있을 수 있다. 이런 상태에서는 서버에 접속할 수 있는 사람이 데이터 전체를 읽거나 지울 수 있다. 이 문제들은 특정 취약점 하나가 아니라 운영 전반의 습관에서 비롯되므로, 서버를 세우고 유지하는 동안 계속 지켜야 할 기본 수칙이 필요하다. MySQL은 이런 흔한 공격을 막기 위한 일반 보안 지침을 정리해 제공한다.

#2핵심 질문

서버를 기본 상태로 두었을 때 생기는 흔한 공격을 막으려면 운영에서 무엇을 지켜야 하는가?

#3동작 예시

애플리케이션이 사용자 입력으로 로그인 쿼리를 만들 때, 입력값을 그대로 문자열에 이어 붙이면 공격자가 조건을 조작한 문장을 넣어 인증을 우회할 수 있다. 반대로 입력을 값으로만 넘기도록 처리하고 계정마다 필요한 권한만 부여하면, 같은 입력이 들어와도 서버가 요청을 거부한다.

#4동작 과정

  1. 비밀번호 보호계정 비밀번호가 노출되지 않도록 다루고, 접속에 쓰는 자격 증명이 평문으로 새지 않게 관리한다.
  2. 인젝션 방어와 권한 최소화입력값을 SQL 문장에 직접 붙이지 않고 값으로 전달하며, 계정에는 작업에 필요한 만큼만 권한을 준다.
  3. 공격 대비 설정 점검보안 관련 mysqld 옵션과 변수를 확인하고, 서버를 일반 사용자로 실행하는 등 설치를 공격에 더 강하게 만드는 설정을 적용한다.

접근 제어와 계정 관리

사용자 계정을 만들고 권한을 부여·회수하며, 어떤 사용자가 어떤 데이터베이스 객체에 접근할 수 있는지 서버가 판단하는 권한 시스템.

#1문제 상황

서버에 접속한 모든 사용자에게 모든 데이터베이스를 열어 주면, 아무 계정이나 남의 데이터를 읽거나 지울 수 있다. 반대로 계정과 권한을 사람이 손으로 관리하면 누가 무엇에 접근할 수 있는지 일관되게 판단하기 어렵고, 권한을 잘못 남겨 둔 계정이 그대로 방치되기 쉽다. MySQL은 계정을 만들고 권한을 부여·회수하는 절차와, 어떤 사용자가 어떤 객체에 접근할 수 있는지 서버가 판단하는 규칙을 함께 제공해 이 문제를 해결한다. 접속을 허용할지와 요청을 허용할지를 두 단계로 나눠 판단하는 것이 핵심이다.

#2핵심 질문

어떤 사용자가 어떤 데이터베이스 객체에 접근할 수 있는지 서버는 무엇을 근거로 판단하는가?

#3동작 예시

사용자가 클라이언트로 접속하면, 서버는 먼저 계정 이름과 비밀번호가 맞는지 확인해 연결을 받아들일지 정한다. 연결이 성립한 뒤 SELECT 문을 보내면, 서버는 그 계정에 해당 테이블을 읽을 권한이 있는지 다시 확인하고 없으면 요청을 거부한다. 같은 계정이라도 접속은 되지만 특정 요청은 막힐 수 있다.

#4동작 과정

  1. 계정 생성과 권한 부여계정을 만들고 GRANT로 필요한 권한을 준다. 권한은 계정이 어떤 객체에 무엇을 할 수 있는지를 정한 규칙이 된다.
  2. 연결 검증(1단계)접속 요청이 오면 서버가 계정 이름·비밀번호와 접속 조건을 확인해 연결 자체를 받아들일지 판단한다.
  3. 요청 검증(2단계)과 권한 회수연결된 뒤 각 SQL 요청마다 그 계정의 권한을 확인해 허용 여부를 정하고, 필요 없어진 권한은 REVOKE로 회수해 접근 범위를 좁힌다.

암호화 연결(TLS) 구성

클라이언트와 서버 사이의 통신을 TLS 인증서로 암호화해 네트워크 도청과 변조를 막도록 MySQL을 설정하는 방법.

#1문제 상황

클라이언트와 서버 사이 연결이 암호화되어 있지 않으면, 네트워크에 접근할 수 있는 사람이 오가는 트래픽을 들여다보고 주고받는 데이터를 그대로 읽을 수 있다. 네트워크를 통해 정보를 안전하게 옮겨야 하는 상황에서는 이런 평문 연결을 그대로 둘 수 없다. MySQL은 TLS 인증서를 사용해 연결을 암호화함으로써 이 문제를 해결한다. 암호화 알고리즘은 전송 내용을 읽지 못하게 할 뿐 아니라, 알려진 여러 공격에 견디도록 보안 요소를 갖춰 선택해야 한다.

#2핵심 질문

네트워크 도청과 변조를 막으려면 클라이언트와 서버 사이 연결을 어떻게 암호화하는가?

#3동작 예시

서버에 TLS 인증서와 키를 준비하고 암호화 연결을 쓰도록 설정한 뒤, 클라이언트가 그 서버에 접속하면 두 지점 사이에 암호화된 통신이 성립한다. 이때 오가는 데이터는 암호화되어, 중간에서 트래픽을 가로채도 내용을 알아볼 수 없다.

#4동작 과정

  1. 인증서 준비SSL과 RSA 인증서·키를 만들거나 준비해, 서버가 자신을 증명하고 통신을 암호화할 재료를 갖춘다.
  2. 서버에 암호화 설정서버가 암호화 연결을 사용하도록 설정하고, 허용할 TLS 프로토콜과 암호 스위트를 정해 안전한 조합만 받아들이게 한다.
  3. 클라이언트 접속과 세션 재사용클라이언트가 암호화된 연결로 서버에 접속해 데이터를 안전하게 주고받고, 필요하면 이전에 성립한 SSL 세션을 재사용해 다시 협상하는 비용을 줄인다.

데이터 마스킹·엔터프라이즈 암호화·SELinux·FIPS

민감 데이터를 가리는 마스킹, 암호화 함수 제공, 운영체제 접근 통제(SELinux), 연방 표준 암호 모드(FIPS)를 통해 데이터 보호 수준을 높이는 기능 묶음.

#1문제 상황

기존에는 DB 계정에 SELECT 권한을 주면 테이블의 모든 컬럼이 그대로 노출된다. 운영 데이터를 개발·테스트 환경으로 복제하면 주민번호나 카드번호 같은 민감 정보가 함께 따라가고, 그 사본이 유출 경로가 된다.

또 암호화와 접근 통제를 애플리케이션 코드에서만 처리하면, 서버가 뚫리거나 내부자가 DB에 직접 접속할 때 그 방어가 한꺼번에 무력화된다. 데이터베이스와 운영체제 수준에서 노출을 줄이는 장치가 따로 필요하다.

#2핵심 질문

애플리케이션 코드가 아니라 데이터베이스와 운영체제 수준에서 민감 정보를 가리고 암호화하며 접근 자체를 통제하려면 어떻게 해야 하는가?

#3동작 예시

권한이 제한된 계정으로 신용카드 번호 컬럼을 조회하면, 마스킹 함수가 원본 대신 뒤 네 자리만 남기고 나머지를 가린 값을 돌려준다. 같은 쿼리라도 원본 조회 권한이 있는 계정은 원래 값을 보고, 그렇지 않은 계정은 가려진 값만 본다.

#4동작 과정

  1. 마스킹MySQL Enterprise Data Masking이 제공하는 함수로 조회 시점에 민감 컬럼 값을 가려 반환한다. 원본은 그대로 남고 계정에 따라 보이는 출력만 달라진다.
  2. 암호화MySQL Enterprise Encryption 함수가 데이터를 암호화·복호화하고 서명·검증하는 기능을 SQL 수준에서 제공한다.
  3. 운영체제·표준 통제SELinux가 mysqld 프로세스가 접근할 수 있는 파일과 동작을 정책으로 제한하고, FIPS 모드에서는 연방 표준을 통과한 암호 알고리즘만 쓰도록 강제한다.

백업 유형·방법·전략

데이터를 잃지 않도록 물리적·논리적 백업의 종류와 방법을 고르고, 전체·증분 백업과 바이너리 로그를 조합해 복구 목표에 맞는 백업 전략을 세우는 것.

#1문제 상황

디스크 고장이나 실수로 인한 삭제, 잘못 실행된 UPDATE가 발생하면 데이터가 사라진다. 백업이 없으면 서비스를 멈추고 손실을 그대로 감수해야 한다.

그런데 아무 방법이나 하나 골라 백업해도 문제가 남는다. 복구에 필요한 시점까지 되돌릴 수 없거나, 백업하는 동안 서비스가 멈추는 식이다. 어떤 데이터를 어떤 방식으로 겹쳐 쌓을지 정해 두지 않으면 장애 때 되살릴 수 있는 범위가 정해지지 않는다.

#2핵심 질문

어떤 데이터를 어떤 방식으로 백업하고 어떤 조합으로 복구해야, 원하는 시점까지 데이터를 되살릴 수 있는가?

#3동작 예시

하루 한 번 mysqldump로 논리 백업을 뜨고, 그 사이의 변경은 바이너리 로그로 계속 쌓아 두는 조합을 쓴다. 복구할 때는 밤에 뜬 덤프를 먼저 복원한 뒤, 그 이후의 바이너리 로그를 순서대로 재적용해 원하는 시점까지 따라잡는다.

#4동작 과정

  1. 백업 유형 선택물리 백업은 데이터 파일을 그대로 복사해 복원이 빠르지만 엔진·버전에 묶이고, 논리 백업은 SQL 문 형태로 뽑아 이식성이 좋다. 상황에 맞는 쪽을 고른다.
  2. 백업 방법 실행mysqldump 같은 도구로 전체 백업을 뜨고, 증분 변경은 바이너리 로그에 남겨 두어 두 가지를 겹쳐 쌓는다.
  3. 복구 전략 적용전체 백업을 복원한 뒤 바이너리 로그를 재적용해, 목표 시점(point-in-time, 특정 시각까지 되돌리는 것)까지 되돌린다. 이 순서를 미리 정해 두어야 장애 때 헤매지 않는다.

백업과 복구06-02

mysqldump 백업과 시점 복구(PITR)

mysqldump로 데이터베이스를 SQL 덤프로 백업하고, 백업 시점 이후의 바이너리 로그를 재적용해 특정 시각이나 트랜잭션 직전 상태로 되돌리는 시점 복구 기법.

#1문제 상황

전체 백업만 하루 한 번 떠 두면, 백업 직후 몇 시간 안에 잘못된 DELETE가 실행됐을 때 그 변경을 통째로 되돌릴 수 없다. 백업 파일에는 그 시점의 상태만 들어 있고 그 뒤의 변경 이력이 없기 때문이다.

결국 잘못된 변경 하나 때문에 그 사이에 정상 처리된 데이터까지 함께 버려야 한다. 전체 백업만으로는 "문제가 생긴 직전"으로 되돌아갈 수 없다.

#2핵심 질문

전체 백업 이후의 변경 이력을 이용해, 문제가 생긴 직전 시점으로 정확히 되돌리려면 어떻게 해야 하는가?

#3동작 예시

밤 12시에 mysqldump로 일관된 시점의 백업을 뜨고, 그때의 바이너리 로그 위치를 함께 기록해 둔다. 오후 2시에 실수로 테이블을 지우면, 백업을 복원한 뒤 12시부터 오후 2시 직전까지의 바이너리 로그 이벤트만 골라 재적용한다.

#4동작 과정

  1. 논리 백업 생성mysqldump가 일관된 시점의 데이터를 SQL 문 형태로 뽑아 저장한다. 이때 백업이 끝난 위치를 바이너리 로그 좌표로 남겨 둔다.
  2. 바이너리 로그 보관백업 이후의 모든 데이터 변경이 바이너리 로그에 순서대로 쌓인다. 이 로그가 되돌리기의 재료가 된다.
  3. 시점 복구 실행백업을 복원한 뒤 바이너리 로그를 지정한 시각이나 위치까지 재적용한다. 문제 직전에서 멈추면 그 이후의 잘못된 변경은 적용되지 않는다.

MyISAM 테이블 유지보수와 충돌 복구

myisamchk와 CHECK/REPAIR TABLE 등으로 MyISAM 테이블의 손상 여부를 점검·수리하고 충돌 후 데이터를 복구하는 절차.

#1문제 상황

MyISAM 테이블은 데이터 파일(.MYD)과 인덱스 파일(.MYI)로 나뉘어 저장된다. 서버가 갑자기 죽으면 두 파일이 서로 어긋나거나 인덱스가 깨질 수 있고, 그 상태로 다시 조회하면 잘못된 결과가 나오거나 에러가 발생한다.

문제는 서버가 이 손상을 스스로 복구해 주지 않는다는 점이다. 관리자가 직접 점검하고 수리하지 않으면 손상된 테이블이 그대로 남는다.

#2핵심 질문

충돌로 손상된 MyISAM 테이블을 점검하고, 데이터를 최대한 살리면서 복구하려면 어떻게 해야 하는가?

#3동작 예시

서버를 멈춘 상태에서 myisamchk 도구로 .MYI 인덱스를 검사하고, 손상이 확인되면 인덱스를 다시 만든다. 데이터 파일이 깨진 경우에는 복구 옵션을 단계별로 올려 가며 살릴 수 있는 행을 최대한 건진다.

#4동작 과정

  1. 점검CHECK TABLE이나 myisamchk로 테이블과 인덱스의 이상 여부를 먼저 확인한다. 손상 여부를 알아야 복구 방식을 정할 수 있다.
  2. 수리REPAIR TABLE이나 myisamchk의 복구 옵션으로 깨진 인덱스를 재생성하고, 필요하면 데이터 파일에서 읽을 수 있는 행을 복원한다.
  3. 정리·최적화복구 후 테이블을 최적화하고 정기 점검 일정을 세워, 같은 손상이 다시 쌓이지 않게 관리한다.

#1문제 상황

반대로 인덱스를 아무렇게나 많이 만들면 쓰기 작업마다 인덱스도 함께 갱신해야 해서 저장 공간과 쓰기 비용이 늘어난다. 조건 표현이 인덱스를 타지 못하면 만들어 둔 인덱스도 효과가 없다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 대상 선정조회에서 자주 조건과 조인에 쓰이는 컬럼을 골라 인덱스를 만든다. 읽기 비용이 큰 쿼리부터 겨냥한다.
  2. 인덱스 활용 확인실행 계획으로 해당 인덱스가 실제로 사용되는지 본다. 컬럼에 함수를 씌우거나 형을 바꾸면 인덱스를 타지 못하므로 조건 표현을 조정한다.
  3. 유지·조정사용되지 않는 인덱스는 줄이고 필요한 조합은 추가한다. 쓰기 비용과 저장 공간의 균형을 맞춘다.

#2핵심 질문

#2핵심 질문

실행 계획과 EXPLAIN

EXPLAIN으로 옵티마이저가 고른 조인 순서·접근 방식·사용 인덱스를 확인해 쿼리 성능 문제를 진단하는 방법이다.

#1문제 상황

쿼리가 느릴 때 그 원인이 WHERE 조건인지, 조인 순서인지, 인덱스가 안 쓰인 것인지 겉으로는 알 수 없다. 옵티마이저는 내부적으로 여러 접근 방식을 비교해 하나를 고르지만 그 선택 과정은 사용자에게 보이지 않는다. 그래서 원인을 모른 채 쿼리를 고치면 엉뚱한 부분을 손대게 된다.

#2핵심 질문

옵티마이저가 어떤 조인 순서·접근 방식·인덱스를 골랐는지 어떻게 확인할 수 있을까?

#3동작 예시

EXPLAIN을 쿼리 앞에 붙여 실행하면 그 쿼리를 실제로 돌리지 않고 실행 계획만 표로 보여준다. 각 행마다 어떤 테이블에 어떤 방식으로 접근하고 어떤 인덱스를 쓰는지 나온다. type이 ALL이면 전체 행을 훑는 풀 스캔이라는 뜻이고, key에 인덱스 이름이 있으면 그 인덱스를 사용했다는 뜻이다.

#4동작 과정

  1. 계획 요청EXPLAIN으로 옵티마이저가 고른 계획을 요청한다. 쿼리는 실행되지 않고 계획 정보만 반환된다.
  2. 결과 해석접근 방식(type), 사용 인덱스(key), 예상 검사 행 수(rows), 추가 정보(Extra)를 읽는다. 인덱스 미사용·풀 스캔·정렬 발생 지점이 드러난다.
  3. 원인 수정 후 재확인인덱스를 추가하거나 쿼리를 고친 뒤 같은 EXPLAIN을 다시 실행한다. 계획이 바뀌었는지 비교해 개선 효과를 확인한다.

언어 구조(리터럴·식별자·키워드·식·주석)

SQL 문을 구성하는 기본 재료인 리터럴 값, 객체 이름(식별자), 키워드, 식, 주석이 무엇이고 어떻게 표기하는지를 다루는 영역이다.

#1문제 상황

SQL 문은 문자열과 숫자, 테이블·컬럼 이름, 명령 키워드, 계산식, 설명용 주석이 뒤섞여 만들어진다. 이 요소들의 표기법이 정해져 있지 않으면 같은 문장을 서버가 어디까지 값으로 읽고 어디부터 이름으로 읽을지 판단할 수 없다. 예를 들어 이름과 문자열을 구분하는 규칙이 없으면 SELECT 뒤에 온 토큰이 컬럼인지 값인지 확정되지 않아 파싱 자체가 흔들린다. MySQL은 이 재료들의 작성 규칙을 11장 Language Structure로 따로 묶어, 문장을 해석하는 기준을 고정한다.

#2핵심 질문

SQL 문을 이루는 값·이름·키워드·식·주석을 서버가 헷갈리지 않게 표기하려면 각각 어떤 규칙을 따라야 하는가?

#3동작 예시

SELECT 'name', name FROM user; 한 줄에서 첫 번째 name은 작은따옴표로 감싼 문자열 리터럴이라 값으로 취급되고, 두 번째 name은 따옴표가 없어 컬럼 식별자로 취급된다. SELECT와 FROM은 예약어 키워드라 명령으로 해석되고, 맨 앞의 SELECT 'name', name은 값을 계산하는 식이 된다. 같은 철자라도 감싸는 방식에 따라 값과 이름이 갈리는 것이 이 장의 핵심 규칙이다.

#4동작 과정

  1. 토큰 분리서버가 문장을 공백과 기호 기준으로 잘라 각 조각이 리터럴·식별자·키워드·연산자 중 무엇인지 분류한다. 따옴표로 감싼 것은 리터럴, 맨 이름은 객체 식별자로 나뉜다.
  2. 이름 해석식별자로 분류된 조각을 데이터베이스·테이블·컬럼 이름으로 확정한다. 대소문자 구분과 길이 제한 같은 규칙이 여기서 적용되어, 어떤 이름을 같은 것으로 볼지 결정된다.
  3. 식 평가와 주석 제거남은 값과 연산자를 식(Expression)으로 묶어 계산하고, --나 #, /* */로 표시된 주석은 해석 대상에서 빼낸다. 그래서 실행 결과에는 주석이 영향을 주지 않는다.

#3동작 예시

컬럼을 VARCHAR(20) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci로 정의하면, 그 컬럼에는 utf8mb4 방식으로 문자가 저장되고 비교할 때는 대소문자와 악센트를 구분하지 않는 규칙으로 정렬된다. 반면 연결 설정이 다른 문자 집합이면 서버가 클라이언트와 주고받는 문자열을 변환하며, 변환이 불가능한 문자는 손실될 수 있다. 두 규칙이 어디에 지정됐는지에 따라 결과가 달라지는 것이 핵심이다.

#4동작 과정

  1. 문자 집합 선택저장할 문자를 부호로 표현하는 방식을 정한다. 유니코드를 쓰려면 더 넓은 문자를 담는 문자 집합을 골라야 이모지나 여러 언어 문자가 깨지지 않는다.
  2. 콜레이션 지정비교·정렬 순서를 정한다. 대소문자 구분 여부와 악센트 구분 여부가 여기서 결정되어 WHERE 비교와 ORDER BY 결과가 달라진다.
  3. 계층별 적용과 연결서버·데이터베이스·테이블·컬럼 순으로 기본값이 정해지고, 클라이언트 연결 시 사용하는 문자 집합까지 맞춰야 주고받는 데이터가 변환 과정에서 어긋나지 않는다.

데이터 타입

컬럼에 저장할 수 있는 값의 종류(수치·날짜시간·문자열·공간·JSON 등)와 각 타입의 저장 방식·기본값·저장 용량을 정의한다.

#1문제 상황

컬럼에 어떤 값이든 다 넣을 수 있게 두면 저장 공간을 낭비하고, 값의 형식을 보장할 수 없어 비교·계산에서 예상 밖의 결과가 나온다. 숫자를 문자열로 저장하면 정렬이 사전 순서가 되어 크기 비교가 어긋나고, 날짜를 아무 형식으로나 넣으면 범위 검색이 제대로 동작하지 않는다. 값의 종류마다 허용 범위와 저장 방식이 다른데 이를 컬럼 단위로 못 박지 않으면 데이터 품질을 유지할 근거가 없다. MySQL은 13장에서 수치·날짜시간·문자열·공간·JSON 등 저장할 수 있는 값의 종류와 각 타입의 표현·저장 용량을 정의한다.

#2핵심 질문

컬럼에 저장할 값의 종류와 크기를 미리 정해 저장 공간과 계산 정확도를 함께 확보하려면 어떤 타입을 골라야 하는가?

#3동작 예시

금액을 다루는 컬럼을 정수 타입 INT로 만들면 소수점 이하를 담을 수 없고, 부동소수점 타입 DOUBLE로 만들면 근사값이라 반올림 오차가 쌓일 수 있다. 대신 고정소수점 타입 DECIMAL(10,2)로 정의하면 소수 둘째 자리까지 정확히 저장되어 합계 계산이 어긋나지 않는다. 같은 숫자라도 타입 선택에 따라 저장 방식과 계산 결과가 달라진다.

#4동작 과정

  1. 값 종류 분류컬럼에 들어올 값을 수치·날짜시간·문자열·공간·JSON 중 어디에 속하는지 정한다. 분류에 따라 사용할 수 있는 타입 목록과 연산 방식이 갈린다.
  2. 타입과 크기 결정고른 종류 안에서 저장 범위와 길이를 정한다. 정수는 담을 자릿수에 따라, 문자열은 최대 길이에 따라 저장 공간과 허용 범위가 달라진다.
  3. 기본값과 저장 규칙 적용값이 빠졌을 때 채울 기본값과 실제 저장에 필요한 바이트 수가 정해진다. 이 규칙이 적용되어 범위를 벗어난 값이나 형식이 맞지 않는 값은 저장 단계에서 걸러진다.

함수·연산자 개요와 기본 함수(수치·날짜·문자)

SQL에서 값을 계산·변환하는 함수와 연산자의 전체 구조를 개괄하고, 수치·날짜시간·문자열을 다루는 기본 함수들을 정리한다.

#1문제 상황

값을 더하거나 자르거나 날짜를 바꾸는 작업을 매번 애플리케이션 코드에서 처리하면, 서버가 이미 가진 값을 꺼내 앱으로 보냈다가 다시 돌려보내는 왕복이 반복된다. 여러 행을 조건에 맞게 가공하려면 그만큼 데이터를 옮기는 비용이 커지고, 앱마다 반올림·날짜 계산 규칙이 달라 결과가 어긋나기도 한다. 계산 규칙을 서버 한 곳에 모을 필요가 있는데, 어떤 함수와 연산자가 있고 타입이 다를 때 어떻게 변환되는지 기준이 없으면 쿼리마다 결과가 흔들린다. MySQL은 14장에서 내장 함수·연산자 목록과 수치·날짜시간·문자열을 다루는 기본 함수, 식 평가 시의 타입 변환 규칙을 정리한다.

#2핵심 질문

값을 서버 안에서 계산·변환해 왕복을 줄이려면 어떤 함수와 연산자를 쓰고, 타입이 다를 때는 어떻게 판단하는가?

#3동작 예시

SELECT UPPER(name), ROUND(price, 2), DATE_ADD(created, INTERVAL 7 DAY) FROM orders;에서 UPPER는 문자열을 대문자로, ROUND는 수치를 소수 자리로 반올림하고, DATE_ADD는 날짜에 7일을 더한다. 세 함수 모두 데이터를 서버 밖으로 내보내지 않고 식 안에서 값을 바꾼다. 이렇게 함수를 식에 넣으면 계산이 한 번의 쿼리 안에서 끝난다.

#4동작 과정

  1. 식 평가와 타입 변환식에 섞인 값과 연산자를 순서대로 계산한다. 숫자와 문자열처럼 타입이 다른 값이 만나면 비교·계산이 가능하도록 변환 규칙이 먼저 적용된다.
  2. 함수 적용문자열·수치·날짜시간 값에 각각 맞는 함수가 실행되어 값을 변환한다. 연산자 우선순위에 따라 계산 순서가 정해져 결과가 확정된다.
  3. 결과 조합변환된 값들이 식 단위로 합쳐져 최종 결과 집합이 만들어진다. 그래서 같은 데이터라도 어떤 함수와 연산자를 쓰느냐에 따라 반환 값이 달라진다.

전문 검색·캐스트·XML·비트·암호화·잠금·정보 함수

전문 검색, 타입 캐스트, XML 처리, 비트 연산, 암호화·압축, 잠금, 서버 정보 조회에 쓰이는 내장 함수와 연산자를 다룬다.

#1문제 상황

단순한 값 비교만으로는 본문 안의 단어를 찾거나, 문자열을 특정 타입으로 바꾸거나, XML 조각에서 값을 뽑거나, 비트 단위로 플래그를 다루는 작업을 처리하기 어렵다. 또 값을 암호화·압축하거나 특정 자원에 잠금을 걸거나 현재 서버·연결 정보를 조회하려면 일반 연산자로는 닿지 않는 별도 기능이 필요하다. 이런 요구가 생길 때마다 앱에서 값을 꺼내 처리하면 데이터를 왕복시키는 비용이 커진다. MySQL은 14.9~14.15에서 전문 검색, 캐스트, XML, 비트, 암호화·압축, 잠금, 정보 조회에 쓰이는 내장 함수와 연산자를 따로 제공한다.

#2핵심 질문

본문 검색·형 변환·XML·비트·암호화·잠금·정보 조회처럼 일반 비교로 처리할 수 없는 작업을 서버 안에서 하려면 어떤 함수를 쓰는가?

#3동작 예시

본문에서 단어를 찾을 때 MATCH(content) AGAINST('database')를 쓰면 문장 안의 해당 단어를 검색해 관련 행을 찾는다. 문자열을 정수로 바꾸려면 CAST('123' AS SIGNED), 연결 정보를 확인하려면 CONNECTION_ID()를 쓴다. 각 함수가 담당하는 영역이 달라, 필요한 작업에 맞는 함수를 골라 식 안에 넣는다.

#4동작 과정

  1. 작업 영역 판별하려는 일이 검색·형 변환·XML 처리·비트 연산·암호화·잠금·정보 조회 중 어디에 속하는지 정한다. 영역마다 사용할 수 있는 함수 집합이 다르다.
  2. 함수 실행고른 함수가 입력값을 받아 해당 작업을 수행한다. 캐스트는 값을 다른 타입으로 바꾸고, 암호화 함수는 값을 변환하며, 잠금 함수는 자원에 대한 획득을 시도한다.
  3. 결과 반영변환·검색·잠금 결과가 식의 값이나 서버 상태로 반영된다. 그래서 같은 데이터라도 어떤 함수를 적용하느냐에 따라 반환 값과 서버 동작이 달라진다.

공간·JSON·복제 함수

기하 데이터를 다루는 공간 함수, JSON 문서를 생성·검색·수정하는 JSON 함수, 복제 상태와 제어에 쓰이는 복제 함수를 다룬다.

#1문제 상황

좌표나 도형 같은 기하 데이터는 단순 값 비교로 거리나 포함 관계를 계산할 수 없고, 구조가 자유로운 JSON 문서는 통째로 저장하면 특정 키의 값을 꺼내거나 일부만 고치기 어렵다. 또 복제 구성에서는 어느 서버가 어디까지 반영했는지, 복제를 멈추거나 재개하려면 상태를 조회하고 제어할 수단이 필요하다. 이런 데이터를 앱에서 꺼내 처리하면 문서 전체를 왕복시키는 비용이 커지고 형식 검증도 앱마다 달라진다. MySQL은 14.16~14.18에서 기하 데이터를 다루는 공간 함수, JSON을 생성·검색·수정하는 JSON 함수, 복제 상태와 제어에 쓰이는 복제 함수를 제공한다.

#2핵심 질문

기하 데이터와 JSON 문서를 서버 안에서 계산·검색·수정하고 복제 상태까지 제어하려면 어떤 함수를 쓰는가?

#3동작 예시

JSON 컬럼에서 특정 키를 꺼낼 때 JSON_EXTRACT(doc, '$.name')을 쓰면 문서 안 name 값을 뽑아낸다. 일부만 바꾸려면 JSON_SET(doc, '$.age', 30)으로 해당 키만 갱신하고, 두 지점 사이 거리를 구하려면 ST_Distance(p1, p2)를 쓴다. 문서나 좌표를 통째로 옮기지 않고 필요한 부분만 서버가 계산한다.

#4동작 과정

  1. 대상 판별다루는 값이 기하 데이터인지, JSON 문서인지, 복제 관련 상태인지 구분한다. 대상에 따라 호출할 함수 묶음이 갈린다.
  2. 함수 적용JSON이면 값 검색·생성·수정 함수가, 기하이면 거리·포함 관계 계산 함수가 실행된다. JSON 인자는 유효한 JSON 값이어야 하며, 아니면 오류가 난다.
  3. 결과 반영계산·수정된 값이나 변경된 복제 상태가 결과로 돌아온다. 그래서 같은 문서라도 어떤 함수를 적용하느냐에 따라 반환 값과 데이터 상태가 달라진다.

집계·윈도우·벡터·성능 스키마 함수와 정밀 산술

여러 행을 하나로 요약하는 집계 함수, 행 그룹별 순위·누적을 계산하는 윈도우 함수, 벡터 연산·성능 스키마 조회 함수, 그리고 정확한 소수 연산을 위한 정밀 산술 규칙을 다룬다.

#1문제 상황

여러 행의 합계나 평균을 구하려면 행을 하나씩 가져와 앱에서 더해야 하고, 그룹별 순위나 누적값을 계산하려면 다시 정렬하고 반복 계산해야 한다. 이 방식은 행 수가 늘수록 왕복과 메모리 사용이 커지며, 부동소수점으로 누적 합계를 내면 반올림 오차가 쌓여 정확한 값을 보장할 수 없다. 또 벡터 연산이나 서버 내부 성능 지표 조회처럼 일반 함수로 닿지 않는 계산은 별도 수단이 필요하다. MySQL은 14.19~14.26에서 여러 행을 하나로 요약하는 집계 함수, 그룹별 순위·누적을 구하는 윈도우 함수, 벡터·성능 스키마 함수와 정확한 소수 연산을 위한 정밀 산술 규칙을 제공한다.

#2핵심 질문

여러 행을 요약·순위화하고 벡터·성능 지표를 계산하며 소수 연산의 정확도를 지키려면 서버에서 어떤 함수를 쓰는가?

#3동작 예시

SELECT dept, SUM(salary) FROM emp GROUP BY dept;는 부서별 급여 합계를 한 번의 쿼리로 구하고, ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC)는 부서별 급여 순위를 매긴다. 부서 전체 행을 앱으로 가져와 계산할 필요 없이 서버가 그룹 단위로 값을 요약한다.

#4동작 과정

  1. 그룹 묶기GROUP BY로 행을 부분집합으로 나눈다. 같은 그룹에 속한 값들이 하나의 계산 단위로 모인다.
  2. 함수 계산각 그룹에 집계 함수가 적용되어 합계·평균·개수 같은 단일 값이 만들어지고, 윈도우 함수는 정렬 기준에 따라 순위나 누적값을 계산한다. 정밀 산술 규칙이 적용되면 소수 연산의 정확도가 유지된다.
  3. 결과 반환그룹별 결과가 행 단위로 합쳐져 최종 집합이 만들어진다. 그래서 같은 데이터라도 어떤 함수와 그룹 기준을 쓰느냐에 따라 요약 값이 달라진다.

#5한 줄 요약

여러 행을 그룹 단위로 요약·순위화하고 벡터·성능 지표와 정밀 소수 연산을 서버 안에서 계산하는 것

SQL 문 — DDL과 DML

데이터베이스·테이블·인덱스 같은 객체를 정의·변경·삭제하는 DDL 문과, 행을 조회·삽입·수정·삭제하는 DML 문을 다룬다.

#1문제 상황

데이터베이스는 데이터를 담는 그릇과 그 안의 실제 데이터로 나뉜다. 그릇의 모양을 바꾸는 일과 데이터를 넣고 빼는 일은 성격이 전혀 다른데, 이를 같은 명령으로 처리하면 구조 변경 중에 데이터가 어중간하게 바뀌거나 롤백 범위가 엉킨다. 그래서 MySQL은 문장을 정의 계열과 조작 계열로 분리해 관리한다.

구조를 바꾸는 명령은 실행되는 순간 저장 구조 자체를 다시 만든다. 반면 행을 다루는 명령은 여러 건을 묶어 한 트랜잭션으로 취소할 수 있다. 이 둘의 차이를 구분하지 않으면 구조 변경을 되돌리려다 실패하거나, 잠금이 오래 걸려 다른 작업이 밀리는 문제가 생긴다.

#2핵심 질문

데이터베이스 객체를 만드는 문장과 그 안의 행을 다루는 문장을 왜 나눠서 다뤄야 하는가?

#3동작 예시

CREATE TABLE users (id INT, name VARCHAR(50))를 실행하면 테이블이라는 객체가 새로 정의된다. 이어서 INSERT INTO users VALUES (1,'kim')을 실행하면 그 테이블에 실제 행 하나가 들어간다. 앞 문장은 users라는 그릇의 구조를 만들고, 뒤 문장은 그 그릇에 값을 채운다.

#4동작 과정

  1. DDL 실행CREATE·ALTER·DROP처럼 데이터베이스·테이블·인덱스 같은 객체를 정의·변경·삭제하는 문장을 실행한다. 객체 구조 자체가 바뀐다.
  2. DML 실행SELECT·INSERT·UPDATE·DELETE처럼 테이블의 행을 조회·삽입·수정·삭제하는 문장을 실행한다. 그릇의 구조는 그대로 두고 내용만 달라진다.
  3. 트랜잭션 경계 적용DML은 COMMIT이나 ROLLBACK으로 묶어 되돌릴 수 있지만, DDL은 실행 즉시 반영되어 되돌릴 수 없다. 그래서 구조 변경과 데이터 변경은 시점을 나눠 처리한다.

#5한 줄 요약

객체의 구조를 다루는 DDL과 그 안의 행을 다루는 DML을 분리해, 정의 변경과 데이터 변경을 서로 다른 규칙으로 처리하게 하는 것

트랜잭션·복제·프리페어드·복합 문

트랜잭션과 잠금을 제어하는 문, 복제 관련 문, 미리 컴파일해 실행하는 프리페어드 문, 그리고 저장 프로그램 안에서 쓰는 복합 문 구문을 다룬다.

→ 08-08 참조

#1문제 상황

여러 행을 하나의 작업으로 묶어 처리하다 보면 도중에 실패했을 때 앞부분만 반영되는 문제가 생긴다. 또 같은 SQL을 반복 실행할 때마다 매번 파싱하고 실행 계획을 세우면 비용이 커진다. 서버를 여러 대로 늘리면 한 곳에서 일어난 변경을 다른 곳에도 전달할 방법이 필요하다.

각 문제는 따로 발생하지만 모두 SQL 문장 차원에서 해결 수단이 필요하다. 변경을 되돌리거나 확정하는 제어, 미리 준비해 두고 실행하는 문장, 서버 간 변경 전달, 그리고 저장 프로그램 안에서 조건·반복을 표현하는 구문이 각각 요구된다.

#2핵심 질문

여러 문장을 하나의 단위로 묶거나 미리 준비하거나 다른 서버로 전달하려면 어떤 문장들을 써야 하는가?

#3동작 예시

START TRANSACTION으로 시작해 두 건의 UPDATE를 실행한 뒤, 두 번째가 실패하면 ROLLBACK을 호출한다. 그러면 첫 번째 UPDATE까지 함께 취소되어 아무 행도 바뀌지 않는다. 반대로 성공하면 COMMIT으로 두 변경을 한꺼번에 확정한다.

#4동작 과정

  1. 트랜잭션·잠금 제어START TRANSACTION·COMMIT·ROLLBACK과 SAVEPOINT로 로컬 트랜잭션의 시작·확정·취소 지점을 관리한다. 여러 변경을 한 단위로 묶거나 중간 지점까지 되돌릴 수 있다.
  2. 프리페어드 문 실행문장을 미리 준비해 두고 값만 바꿔 반복 실행한다. 매번 파싱하지 않아 같은 형태의 문장을 여러 번 실행할 때 비용이 줄어든다.
  3. 복제·복합 문 처리복제 관련 문으로 한 서버의 변경을 다른 서버에 전달하고, 저장 프로그램 안에서는 IF·LOOP 같은 복합 문 구문으로 조건과 반복을 표현한다. 결과적으로 트랜잭션·재사용·서버 확장·절차 제어가 SQL 문 차원에서 이뤄진다.

#5한 줄 요약

트랜잭션 제어·프리페어드 문·복제 문·복합 문 구문을 통해 여러 변경을 한 단위로 묶고, 문장을 재사용하고, 서버 간에 전달하고, 절차를 표현하게 하는 것

관리·유틸리티 문과 데이터 딕셔너리

서버 관리와 계정·권한·상태 조회에 쓰이는 관리 문, 유틸리티 성격의 문, 그리고 메타데이터를 저장하는 데이터 딕셔너리의 구조와 동작을 다룬다.

→ 08-08 참조

#1문제 상황

예전 MySQL은 데이터베이스 객체 정보를 메타데이터 파일과 비트랜잭션 테이블, 스토리지 엔진별 딕셔너리에 나눠 저장했다. 같은 정보가 여러 곳에 흩어지면 서버가 비정상 종료됐을 때 서로 어긋나 복구가 어렵고, 객체 정보를 조회할 때마다 파일을 읽어야 해 느리다.

또 서버를 운영하려면 계정·권한·상태를 조회하고 관리하는 별도 문장이 필요하다. 객체 정보가 흩어져 있으면 이런 관리 작업도 일관된 원본을 보장받기 어렵다.

#2핵심 질문

데이터베이스 객체 정보를 한 곳에서 트랜잭션으로 관리하면서 서버 운영에 필요한 관리·조회 문장까지 일관되게 다루려면 어떻게 해야 하는가?

#3동작 예시

CREATE TABLE로 테이블을 만들면 그 테이블의 정의가 트랜잭션 데이터 딕셔너리에 기록된다. 이후 SHOW나 INFORMATION_SCHEMA 조회로 이 정의를 읽으면, 파일을 뒤지는 대신 딕셔너리에서 같은 정보를 일관되게 가져온다.

#4동작 과정

  1. 관리 문 실행계정·권한·상태를 다루는 관리 문으로 서버를 운영하고, 유틸리티 성격의 문으로 필요한 정보를 확인한다. 서버 전반의 설정과 접근을 통제한다.
  2. 딕셔너리에 기록객체가 생성·변경되면 그 정보가 트랜잭션 방식의 데이터 딕셔너리에 저장된다. 메타데이터가 파일에 흩어지지 않고 한 곳에서 원자적으로 관리된다.
  3. 통합 조회·캐시딕셔너리 데이터는 트랜잭션으로 저장되고 객체 캐시를 거쳐 INFORMATION_SCHEMA와 통합되어 조회된다. 그 결과 객체 정보가 항상 일관된 원본에서 읽힌다.

#5한 줄 요약

객체 정보를 트랜잭션 데이터 딕셔너리 한 곳에 모아 관리하고, 그 원본을 관리·조회 문장과 INFORMATION_SCHEMA가 함께 일관되게 읽게 하는 것

InnoDB 스토리지 엔진09-01

InnoDB 개요 — ACID와 멀티버전(MVCC)

MySQL의 기본 스토리지 엔진인 InnoDB가 트랜잭션의 ACID 속성을 보장하기 위해 커밋된 데이터와 변경 전 버전을 함께 관리하는 멀티버전 동시성 제어(MVCC) 구조를 갖춘 엔진이라는 개요.

→ 09-03 참조

#1문제 상황

여러 사용자가 동시에 같은 데이터를 읽고 쓰면, 아직 확정되지 않은 변경을 다른 사용자가 읽어 잘못된 값을 보는 문제가 생긴다. 읽기 작업이 쓰기 작업을 기다리게 하면 동시성이 떨어지고, 반대로 아무 제어 없이 두면 데이터가 깨진다.

서버가 갑자기 멈추면 진행 중이던 변경이 어중간한 상태로 남는다. 이런 상황에서 데이터를 잃지 않고 복구하려면 변경을 확정·취소할 수 있고, 장애 후 다시 맞춰 넣을 수 있는 기반이 필요하다.

#2핵심 질문

동시에 읽고 쓰는 상황에서도 데이터 정합성을 지키고 장애 후 복구까지 보장하려면 어떻게 해야 하는가?

#3동작 예시

어떤 트랜잭션이 행 값을 10에서 20으로 바꾸고 아직 커밋하지 않았다. 이때 다른 트랜잭션이 그 행을 읽으면 10을 본다. 변경 전 버전을 따로 보관해 두기 때문에, 확정되지 않은 20이 아니라 확정된 10이 읽힌다.

#4동작 과정

  1. ACID 보장InnoDB의 DML 동작은 커밋·롤백·장애 복구를 갖춘 트랜잭션으로 실행되어 원자성·일관성·격리성·지속성 모델을 따른다. 변경이 어중간하게 남지 않는다.
  2. 변경 전 버전 보관값을 바꿀 때 이전 버전을 함께 유지한다. 읽는 쪽은 자신의 시점에 맞는 버전을 골라 읽어, 쓰기와 읽기가 서로 기다리지 않는다.
  3. 행 수준 잠금여러 트랜잭션이 같은 행에 동시에 접근할 때 행 단위로 잠금을 걸어 충돌을 제어한다. 그 결과 동시성을 유지하면서도 정합성이 지켜진다.

#5한 줄 요약

InnoDB 아키텍처 — 메모리·디스크 구조

InnoDB가 버퍼 풀·로그 버퍼 등 메모리 구조와 테이블스페이스·리두 로그·언두 로그 등 디스크 구조로 나뉘어 데이터를 읽고 쓰는 전체 구성.

#1문제 상황

디스크는 메모리보다 훨씬 느리다. 데이터를 요청할 때마다 디스크를 직접 읽으면 응답이 느려지고, 변경할 때마다 즉시 디스크에 쓰면 그 느린 속도가 전체 처리량을 떨어뜨린다.

또 갑자기 전원이 꺼지면 메모리에만 있던 변경은 사라진다. 그래서 메모리에 올려 빠르게 처리하되, 꺼져도 복구할 수 있도록 디스크에 남기는 구조가 동시에 필요하다.

#2핵심 질문

메모리의 속도를 활용하면서도 장애 시 데이터를 잃지 않으려면 데이터를 메모리와 디스크에 어떻게 나눠 둬야 하는가?

#3동작 예시

자주 쓰는 페이지를 버퍼 풀이라는 메모리 공간에 올려 두면, 같은 데이터를 다시 요청할 때 디스크를 읽지 않고 메모리에서 바로 준다. 변경 내용은 먼저 메모리에 반영하고, 리두 로그에는 디스크에 먼저 기록해 둔다.

#4동작 과정

  1. 메모리 구조 사용버퍼 풀과 로그 버퍼 같은 메모리 구조가 자주 쓰는 페이지와 변경 기록을 담아 빠르게 처리한다. 디스크 접근이 줄어 응답이 빨라진다.
  2. 변경을 로그에 먼저 기록변경 내용을 리두 로그에 먼저 남긴다. 실제 데이터 파일 반영이 늦어도 장애 후 로그로 다시 적용할 수 있다.
  3. 디스크 구조에 저장테이블스페이스·리두 로그·언두 로그 같은 디스크 구조가 데이터와 변경 전 버전을 영구히 보관한다. 그 결과 속도와 내구성을 함께 얻는다.

#5한 줄 요약

버퍼 풀·로그 버퍼 같은 메모리 구조로 빠르게 처리하고 변경을 리두 로그에 먼저 남긴 뒤 테이블스페이스·언두 로그로 영구 저장해, 속도와 내구성을 함께 확보하는 것

InnoDB 잠금과 트랜잭션 모델

InnoDB가 여러 트랜잭션의 동시 접근을 제어하기 위해 사용하는 행 수준 잠금 방식과 격리 수준, 트랜잭션 처리 규칙.

→ 09-01 참조

#1문제 상황

여러 트랜잭션이 같은 행을 동시에 수정하려 하면 나중 변경이 앞 변경을 덮어써 값이 유실될 수 있다. 반대로 테이블 전체를 잠그면 관계없는 행까지 기다려야 해 동시성이 크게 떨어진다.

또 읽는 쪽이 어느 시점의 데이터를 보느냐에 따라 결과가 달라진다. 동시성이 높은 환경에서는 충돌을 감지하고, 필요하면 한쪽을 기다리게 하거나 중단시키는 규칙이 필요하다.

#2핵심 질문

여러 트랜잭션이 같은 데이터를 동시에 다뤄도 값을 잃지 않고 일관된 결과를 보려면 잠금과 격리를 어떻게 정해야 하는가?

#3동작 예시

한 트랜잭션이 특정 행을 UPDATE하면 그 행에 잠금이 걸린다. 다른 트랜잭션이 같은 행을 수정하려 하면 잠금이 풀릴 때까지 기다린다. 서로 다른 행을 다루는 트랜잭션끼리는 기다리지 않고 동시에 진행한다.

#4동작 과정

  1. 잠금 설정변경하는 행에 행 수준 잠금을 건다. 같은 행을 노리는 다른 트랜잭션만 기다리게 하고 나머지는 막지 않는다.
  2. 격리 수준 적용트랜잭션마다 어느 시점의 데이터를 볼지 격리 수준으로 정한다. 읽는 쪽이 확정되지 않은 변경을 보지 않게 한다.
  3. 충돌·교착 처리잠금이 서로 얽혀 교착이 생기면 InnoDB가 한쪽 트랜잭션을 중단시켜 풀어 준다. 그 결과 동시성을 유지하면서 값 유실과 불일치를 막는다.

#5한 줄 요약

행 수준 잠금과 격리 수준으로 동시 접근을 제어하고 교착을 감지해 풀어, 여러 트랜잭션이 값을 잃지 않고 일관되게 처리되게 하는 것

InnoDB 테이블의 시작 옵션과 시스템 변수 설정, 테이블·페이지 압축 방식, 그리고 행을 저장하는 로우 포맷(ROW_FORMAT) 종류.

#1문제 상황

InnoDB의 성능과 자원 사용은 버퍼 풀 크기, 스레드 수, I/O 관련 설정 같은 값에 좌우된다. 이 값들을 서버 환경에 맞게 정하지 않으면 메모리가 부족하거나 디스크 I/O가 몰려 처리량이 떨어진다.

데이터가 커지면 디스크 공간과 읽기 비용도 함께 늘어난다. 같은 데이터를 더 적은 공간에 저장하고 덜 읽으려면 압축 방식과 행을 저장하는 형식을 환경에 맞게 고를 필요가 있다.

#2핵심 질문

서버 환경에 맞춰 InnoDB의 설정값과 압축·행 저장 형식을 어떻게 정해야 성능과 공간을 함께 관리할 수 있는가?

#3동작 예시

버퍼 풀 크기를 늘리면 메모리에 올려 둘 수 있는 페이지가 많아져 디스크 읽기가 줄어든다. 또 테이블을 압축해 저장하면 같은 데이터가 차지하는 디스크 공간이 줄고, 페이지에 더 많은 행이 담겨 읽는 횟수가 줄어든다.

#4동작 과정

  1. 구성 값 설정시작 옵션과 시스템 변수로 버퍼 풀 크기·스레드 수·I/O 관련 값을 환경에 맞게 정한다. 자원이 용도에 맞게 배분된다.
  2. 압축 방식 선택테이블·페이지 압축 방식으로 저장 데이터의 크기를 줄인다. 디스크 공간과 읽기 비용이 함께 줄어든다.
  3. 행 형식 지정테이블의 ROW_FORMAT(행을 저장하는 형식)을 골라 행을 저장하는 방식을 정한다. 그 결과 공간 효율과 처리 성능이 환경에 맞게 조정된다.

InnoDB 디스크 I/O·Online DDL·데이터 암호화

InnoDB의 파일 공간·디스크 I/O 관리 방식과 서비스 중에도 스키마를 변경하는 Online DDL, 그리고 저장 데이터를 암호화하는 기능.

#1문제 상황

데이터베이스는 ACID 설계 모델을 지키기 위해 디스크 읽기·쓰기를 반복하는데, 이 I/O 양이 많아지면 I/O 하위 시스템이 포화되어 응답이 느려진다. 또 디스크 공간을 정리하지 않으면 저장 장치가 꽉 차서 서비스가 멈출 수 있다. 여기에 운영 중에 테이블 구조를 바꾸면 테이블을 잠그는 동안 다른 작업이 대기해야 하고, 저장된 데이터가 평문으로 남아 있으면 디스크를 탈취당했을 때 내용이 그대로 노출된다.

#2핵심 질문

디스크 I/O와 파일 공간을 효율적으로 관리하면서, 서비스를 멈추지 않고 스키마를 바꾸고, 저장 데이터까지 안전하게 지키려면 어떻게 해야 하는가?

#3동작 예시

InnoDB는 변경된 페이지를 즉시 디스크에 쓰지 않고 버퍼 풀에 모아 두었다가, 데이터베이스가 한가할 때나 모든 페이지를 내려야 할 때로 미룬다. 그 사이 변경 기록은 리두 로그에 먼저 남겨 두기 때문에, 갑자기 서버가 꺼져도 다시 시작할 때 변경 내용을 복구할 수 있다.

#4동작 과정

  1. I/O 분산과 파일 공간 관리InnoDB는 버퍼 풀에 쌓인 변경 페이지를 한 번에 밀어 넣는 방식으로 디스크 접근을 묶고, 테이블스페이스 파일을 나누어 저장 공간을 관리한다. 그래서 불필요한 I/O가 줄고 장치가 꽉 차는 일을 피할 수 있다.
  2. Online DDL운영 중에 인덱스 추가나 컬럼 변경 같은 스키마 변경을 수행할 때, 테이블 전체를 잠그지 않고 변경 중에도 읽기·쓰기를 허용하는 방식으로 처리한다. 그래서 서비스를 멈추지 않고 구조를 바꿀 수 있다.
  3. 데이터 암호화와 공간 회수저장 데이터를 암호화해 디스크에 기록하고, TRUNCATE TABLE 같은 명령으로 테이블이 차지한 공간을 다시 운영체제로 돌려준다. 그래서 데이터 유출 위험을 낮추고 공간을 재사용할 수 있다.

InnoDB가 디스크 I/O와 파일 공간을 관리하면서 서비스 중단 없이 스키마를 바꾸고 저장 데이터를 암호화해 데이터 신뢰성과 보안을 함께 지키는 것

InnoDB의 상태를 관찰하는 모니터와 백업·복구 절차, 그리고 InnoDB가 지원하는 최대값과 제약 사항.

#1문제 상황

InnoDB는 내부 상태를 눈으로 볼 수 없는 구조라서, 성능이 느려져도 어느 부분이 병목인지 알기 어렵다. 데이터가 손상되거나 잘못 삭제되면 되돌릴 수단이 없으면 복구가 불가능하고, 테이블·인덱스에는 최대 크기와 구조적 제약이 있어 이를 넘는 설계를 하면 동작하지 않는다. 그래서 운영자는 상태를 관찰하고, 백업·복구 절차를 갖추고, 지원 한계를 미리 알아야 한다.

#2핵심 질문

InnoDB의 내부 상태를 관찰하고 데이터를 백업·복구하며, 넘어설 수 없는 한계를 미리 아는 방법은 무엇인가?

#3동작 예시

InnoDB 모니터를 켜면 표준 모니터가 버퍼 풀 사용량, 대기 중인 잠금, 진행 중인 트랜잭션 같은 내부 상태를 텍스트로 출력한다. 운영자는 이 출력을 주기적으로 확인해 어떤 트랜잭션이 잠금을 오래 잡고 있는지 파악한다.

#4동작 과정

  1. 모니터 활성화표준 모니터와 잠금 모니터를 설정으로 켜면, InnoDB 내부 상태(버퍼 풀·잠금·트랜잭션)를 주기적으로 출력한다. 그래서 성능 문제의 원인을 눈으로 확인할 수 있다.
  2. 정보 스키마와 성능 스키마 조회InnoDB 관련 INFORMATION_SCHEMA 테이블과 Performance Schema 통합을 통해 상태 값을 SQL로 조회한다. 그래서 모니터 출력 대신 질의로 지표를 뽑아낼 수 있다.
  3. 백업·복구와 한계 확인백업·복구 절차와 복제 연동, 문제 해결 절차를 적용하고, 최대값·제약 사항 목록을 확인해 설계가 한계 안에 있는지 점검한다. 그래서 장애 대비와 설계 검증이 가능하다.

InnoDB가 내부 상태를 관찰하는 수단과 백업·복구 절차, 그리고 넘을 수 없는 한계를 명시해 운영자가 데이터를 안정적으로 지키도록 돕는 것

InnoDB 스토리지 엔진09-07

대체 스토리지 엔진(MyISAM·MEMORY·CSV 등)

InnoDB 외에 MySQL이 제공하는 MyISAM, MEMORY, CSV, ARCHIVE, BLACKHOLE, MERGE, FEDERATED 등 여러 스토리지 엔진과 그 선택 방법.

#1문제 상황

MySQL은 데이터를 읽고 쓰는 방식을 스토리지 엔진에 위임하는데, 모든 상황에 InnoDB 하나만 맞는 것은 아니다. 트랜잭션이 필요 없는 읽기 위주 작업, 메모리에만 올려 두는 임시 데이터, 파일로 직접 주고받는 데이터처럼 성격이 다른 요구가 있다. 하나의 엔진만 쓰면 이런 요구를 감당하지 못하거나 불필요하게 무거운 처리를 하게 된다.

#2핵심 질문

용도에 맞게 다른 스토리지 엔진을 골라 쓸 수 있고, 그 선택은 어떻게 하는가?

#3동작 예시

테이블을 만들 때 ENGINE=MyISAM 처럼 엔진 이름을 지정하면 그 테이블은 해당 엔진의 저장·조회 방식을 따른다. 예를 들어 MEMORY 엔진을 지정하면 테이블 데이터가 메모리에만 올라가 서버가 재시작되면 사라지고, CSV 엔진을 지정하면 데이터가 쉼표로 구분된 텍스트 파일로 저장되어 다른 프로그램이 바로 읽을 수 있다.

#4동작 과정

  1. 엔진 선택CREATE TABLE 문이나 서버 설정으로 테이블마다 사용할 스토리지 엔진을 지정하고, 기본 엔진도 설정할 수 있다. 그래서 같은 서버 안에서도 테이블별로 저장 방식을 달리할 수 있다.
  2. 엔진별 저장·조회MyISAM은 트랜잭션 없이 빠른 읽기를, MEMORY는 메모리 상주 데이터를, CSV는 텍스트 파일 형식을, ARCHIVE·BLACKHOLE·MERGE·FEDERATED 등은 각자의 목적에 맞게 데이터를 다룬다. 그래서 작업 성격에 맞는 처리가 가능하다.
  3. 아키텍처 확인MySQL 스토리지 엔진 아키텍처 개요를 통해 서버가 엔진을 어떻게 교체·연결하는지 확인하고, 각 엔진의 제약을 파악해 선택을 검증한다. 그래서 잘못된 엔진 선택을 피할 수 있다.

#5한 줄 요약

MySQL이 여러 스토리지 엔진을 제공하고 테이블 단위로 골라 쓰게 해, 작업 성격에 맞는 저장·조회 방식을 선택하게 하는 것

비동기 복제

한 서버(소스)의 변경을 바이너리 로그로 다른 서버(레플리카)에 전달해 비동기로 재적용하는 전통적 MySQL 복제 방식이다.

#1문제 상황

서버 한 대에 모든 데이터를 두면 그 서버가 죽는 순간 서비스가 멈추고, 읽기 요청이 몰리면 한 대의 자원으로는 감당하기 어렵다. 그래서 데이터를 다른 서버에 복사해 두는 방식이 필요했는데, 원본 서버가 변경을 적용한 뒤 복제 서버에 전달하고 복제 서버가 다시 적용하는 동안에는 시간차가 생긴다. 이 시간차 때문에 복제 서버에서 읽은 값이 원본보다 뒤처져 있을 수 있다.

#2핵심 질문

원본 서버의 변경을 다른 서버들에 전달해 데이터를 복사해 두되, 원본이 전달 결과를 기다리지 않는 구조는 어떻게 동작하는가?

#3동작 예시

원본 서버에서 INSERT나 UPDATE 같은 변경이 커밋되면 그 변경이 바이너리 로그에 기록된다. 복제 서버는 이 로그를 받아 자신의 릴레이 로그에 저장한 뒤 다시 실행하며, 원본은 복제 서버가 적용을 끝냈는지 기다리지 않고 다음 트랜잭션을 계속 처리한다.

#4동작 과정

  1. 변경 기록원본 서버가 트랜잭션을 커밋하면 변경 내용이 바이너리 로그에 순서대로 기록된다. 그래서 이후 복제 서버가 이 로그를 근거로 같은 변경을 재현할 수 있다.
  2. 로그 전달과 재적용복제 서버의 수신 스레드가 바이너리 로그를 받아 릴레이 로그(중간 저장 파일)에 쓰고, 적용 스레드가 그 내용을 실행해 자신의 데이터에 반영한다. 그래서 원본과 복제 서버 데이터가 같은 순서로 갱신된다.
  3. 비동기 처리와 읽기 분산원본은 복제 서버의 적용 완료를 기다리지 않으므로 지연이 생길 수 있지만, 그 대신 복제 서버를 읽기 전용으로 두어 읽기 요청을 나눌 수 있다. 그래서 처리량을 늘릴 수 있다.

#5한 줄 요약

원본 서버가 바이너리 로그로 변경을 전달하고 복제 서버가 이를 비동기로 재적용하게 해, 데이터 복사본과 읽기 분산을 확보하는 것

그룹 복제

여러 서버가 하나의 그룹으로 묶여 트랜잭션을 합의(합의 프로토콜)로 검증하고 모든 노드에 동일 순서로 적용하는 동기적 복제 플러그인이다.

#1문제 상황

비동기 복제는 원본이 복제 서버의 적용 완료를 기다리지 않기 때문에, 원본이 갑자기 죽으면 아직 전달되지 않은 변경이 사라질 수 있고 복제 서버 중 어느 것이 최신인지 판단하기 어렵다. 여러 서버가 동시에 쓰기를 받으면 서로 다른 순서로 변경이 적용되어 데이터가 어긋날 위험도 있다. 그래서 서버들의 상태를 하나로 합의해 관리할 방법이 필요하다.

#2핵심 질문

여러 서버가 같은 변경을 같은 순서로 적용하고, 어느 서버가 최신인지 스스로 합의하게 하려면 어떻게 해야 하는가?

#3동작 예시

한 서버에서 트랜잭션이 커밋되면 그 변경은 그룹 전체에 배포되어 합의 절차를 거친다. 과반수 서버가 그 변경을 승인하면 모든 멤버가 동일한 순서로 적용하고, 승인되지 못한 변경은 버려진다. 그래서 멤버들의 데이터 상태가 어긋나지 않는다.

#4동작 과정

  1. 그룹 구성여러 서버를 하나의 그룹으로 묶고, 단일 프라이머리 또는 다중 프라이머리 모드로 동작 방식을 정한다. 그래서 쓰기를 받을 서버와 복제 관계가 명확해진다.
  2. 합의와 순서 결정커밋된 변경을 그룹에 배포하고 합의 프로토콜로 검증해 모든 멤버가 같은 순서로 적용하도록 순서를 확정한다. 그래서 서버마다 데이터가 달라지는 문제를 막는다.
  3. 적용과 상태 확인확정된 순서대로 각 멤버가 변경을 적용하고, 멤버 상태 테이블과 통계 테이블로 그룹 상태를 모니터링한다. 그래서 문제가 생긴 멤버를 파악하고 대응할 수 있다.

#5한 줄 요약

여러 서버가 그룹으로 묶여 트랜잭션을 합의로 검증하고 동일한 순서로 적용하게 해, 데이터 일관성과 고가용성을 함께 확보하는 것

MySQL Shell과 Document Store

MySQL Shell을 사용해 JSON 문서를 다루는 Document Store 기능으로, 스키마 없이 컬렉션에 문서를 저장하고 조회할 수 있게 해주는 인터페이스다.

#1문제 상황

관계형 테이블은 컬럼 구조를 미리 정해야 하므로, 형태가 자주 바뀌는 데이터를 다루면 스키마를 계속 고쳐야 한다. 또 애플리케이션에서 JSON 문서를 다루는 방식과 데이터베이스에 저장하는 방식이 따로 놀아, 문서를 저장하고 조회하려면 변환 작업이 필요하다. 그래서 스키마 없이 문서를 그대로 저장하고 조회할 수 있는 통로가 필요하다.

#2핵심 질문

별도의 스키마 정의 없이 JSON 문서를 컬렉션에 저장하고 조회할 수 있는 방법은 무엇인가?

#3동작 예시

MySQL Shell에서 컬렉션을 만들고 문서를 추가하면, 문서는 그대로 저장되고 이후 필드 값을 기준으로 조회할 수 있다. 이때 데이터는 결국 MySQL의 테이블에 저장되지만, 사용자는 문서 단위로 다루기 때문에 컬럼 구조를 따로 정의하지 않아도 된다.

#4동작 과정

  1. MySQL Shell 접속MySQL Shell을 열고 서버에 접속해 JavaScript 또는 Python 모드로 전환한다. 그래서 문서 저장 기능을 명령과 코드로 다룰 수 있다.
  2. 컬렉션과 문서 다루기컬렉션을 만들고 JSON 문서를 추가·조회하며, 필요하면 문서를 관계형 테이블로 변환하거나 테이블의 문서를 다룬다. 그래서 스키마 없이도 데이터를 저장·검색할 수 있다.
  3. X Plugin 연결X Plugin을 통해 문서 저장 기능을 쓰는 연결을 구성하고, 필요하면 암호화 연결이나 압축, 인증 방식을 함께 설정한다. 그래서 안전하게 문서 기반 데이터를 주고받을 수 있다.

#5한 줄 요약

MySQL Shell과 X Plugin을 통해 스키마 정의 없이 JSON 문서를 컬렉션에 저장·조회하게 해 주는 것

InnoDB Cluster와 ReplicaSet

InnoDB Cluster는 그룹 복제와 MySQL Router를 묶어 고가용성과 자동 페일오버를 제공하는 구성이고, InnoDB ReplicaSet은 그룹 복제 없이 비동기 복제로 읽기 확장·전환을 제공하는 구성이다.

→ 10-02 참조

#1문제 상황

복제를 직접 구성하면 서버 여러 대를 수동으로 묶고, 어느 서버가 죽었을 때 새 원본을 정하는 작업도 사람이 해야 한다. 서버 대수가 늘수록 설정과 전환 절차가 복잡해지고, 장애 순간에 대응이 늦어지면 서비스 중단이 길어진다. 그래서 서버 묶음을 하나의 구성으로 관리하고 장애 전환을 자동으로 처리할 방법이 필요하다.

#2핵심 질문

여러 MySQL 서버를 하나의 구성으로 묶어 고가용성과 자동 전환을 제공하고, 필요하면 복제 기반 읽기 확장도 하려면 어떻게 해야 하는가?

#3동작 예시

InnoDB Cluster를 구성하면 최소 세 대의 서버가 그룹 복제로 묶이고, MySQL Router가 애플리케이션 연결을 받아 현재 원본 서버로 보낸다. 원본 서버에 장애가 나면 그룹이 새 원본을 정하고 Router가 연결을 새 서버로 돌려, 애플리케이션이 서버 주소를 바꾸지 않아도 계속 동작한다.

#4동작 과정

  1. 구성 생성MySQL Shell을 사용해 여러 서버를 InnoDB Cluster로 묶고, 그룹 복제 설정과 서버 역할을 자동으로 구성한다. 그래서 서버들을 수동으로 조율하지 않아도 된다.
  2. 연결 라우팅MySQL Router가 애플리케이션 연결을 받아 읽기·쓰기 대상에 맞는 서버로 전달한다. 그래서 애플리케이션은 개별 서버 주소를 알 필요가 없다.
  3. 자동 전환과 읽기 확장원본 서버에 장애가 나면 그룹이 자동으로 새 원본을 선출해 전환하고, 그룹 복제 없이 비동기 복제만으로 읽기 확장과 전환을 원하면 InnoDB ReplicaSet을 사용한다. 그래서 장애 대응과 읽기 분산을 목적에 맞게 선택할 수 있다.

#5한 줄 요약

그룹 복제와 MySQL Router를 묶어 여러 서버에 고가용성과 자동 페일오버를 제공하고, 비동기 복제 기반의 읽기 확장 구성도 선택하게 하는 것

복제와 고가용성10-05

NDB Cluster

데이터를 여러 노드에 분산 저장하고 메모리 기반으로 동작해 고가용성과 높은 처리량을 제공하는 MySQL의 분산 클러스터 스토리지 엔진이다.

#1문제 상황

기본 MySQL 서버는 하나의 장비에서 데이터를 처리하고, 그 데이터는 로컬 디스크의 InnoDB 스토리지 엔진에 저장된다. 서버 한 대가 멈추면 그 서버가 가진 데이터에 접근할 수 없고, 처리량도 그 한 대의 CPU와 메모리 한도 안에서만 늘릴 수 있다. 여러 장비로 부하를 나누려 해도 데이터가 로컬에 묶여 있어 노드 사이에 같은 데이터를 일관되게 유지하기가 어렵다.

#2핵심 질문

여러 대의 장비에 데이터를 나눠 담으면서도 한 대가 죽어도 서비스가 계속되고 처리량을 함께 키우려면 어떻게 해야 하는가?

#3동작 예시

NDB Cluster는 데이터 노드 여러 대에 같은 데이터 조각의 복제본을 서로 다른 노드 그룹에 나눠 둔다. 어떤 데이터 노드가 멈추면 그 노드가 맡던 조각의 복제본을 가진 다른 노드가 처리를 대신 이어받는다. 애플리케이션은 SQL 엔드포인트인 MySQL 서버를 통해 평소처럼 SQL을 보내고, 서버는 그 요청을 NDB 스토리지 엔진을 거쳐 데이터 노드들에 분산 처리한다.

#4동작 과정

  1. 관리 노드 기동클러스터 전체 구성 정보를 들고 있는 관리 노드를 먼저 띄운다. 각 노드가 어떤 역할로 몇 대 붙는지를 이 노드가 관리하므로, 나머지 노드가 여기에 등록해 클러스터 구성을 확정한다.
  2. 데이터 노드와 MySQL 서버 연결데이터 노드들이 데이터를 조각(프래그먼트)과 복제본으로 나눠 저장하고, SQL을 받는 MySQL 서버(NDB 스토리지 엔진을 활성화한 서버)들이 그 데이터 노드들에 붙는다. 그래서 SQL 요청이 여러 데이터 노드에 걸쳐 병렬로 처리된다.
  3. 복제본 동기화와 장애 대응각 데이터 조각의 복제본을 노드 그룹 안의 다른 노드가 유지하다가, 한 노드가 멈추면 남은 복제본으로 처리를 넘긴다. 그 결과 데이터 유실 없이 서비스가 계속되고, 노드를 추가하면 처리량과 저장 용량을 함께 늘릴 수 있다.

#5한 줄 요약

데이터를 여러 노드에 분산 저장하고 메모리 기반으로 동작해 고가용성과 높은 처리량을 제공하는 MySQL의 분산 클러스터 스토리지 엔진

파티셔닝

하나의 큰 테이블을 파티션이라는 여러 조각으로 나눠 물리적으로 분할 저장하면서도 논리적으로는 하나의 테이블로 다루게 하는 기능이다.

#1문제 상황

테이블 하나가 수억 건으로 커지면, 조건에 맞는 행을 찾을 때도 인덱스와 데이터 전체를 넓게 훑어야 해 조회가 느려진다. 오래된 데이터를 지우려 해도 관련 없는 최신 데이터가 섞여 있어 한 번의 큰 삭제 작업이 오래 걸리고, 그동안 다른 작업이 밀린다. 테이블을 서로 다른 여러 테이블로 쪼개 두면 애플리케이션이 어느 테이블을 볼지 직접 골라야 하는 부담이 생긴다.

#2핵심 질문

테이블 하나를 여러 조각으로 나눠 저장하면서도 애플리케이션은 그대로 하나의 테이블로 다루게 하려면 어떻게 해야 하는가?

#3동작 예시

주문 테이블을 주문 연도 기준으로 나눈다고 하면, RANGE 파티셔닝으로 2023년 주문은 한 파티션, 2024년 주문은 다른 파티션에 저장하도록 정의한다. 애플리케이션은 SELECT ... FROM orders WHERE order_year = 2024처럼 평소와 같은 SQL을 보내고, MySQL은 조건에 맞는 파티션만 골라 읽는다. 오래된 연도의 파티션은 통째로 버리면 되므로 삭제도 그 조각 단위로 빠르게 끝난다.

#4동작 과정

  1. 파티션 키 정의테이블을 만들 때 어떤 컬럼 값을 기준으로 조각을 나눌지(예: 범위, 목록, 해시) 정한다. 이 기준에 따라 각 행이 어느 파티션에 들어갈지가 결정된다.
  2. 행 저장과 분배들어오는 행은 정의된 규칙에 따라 해당 파티션에 저장된다. 겉으로는 테이블 하나지만 저장은 여러 조각으로 나뉘어 이뤄진다.
  3. 파티션 프루닝(Pruning, 불필요한 조각 걸러내기)조회 조건이 파티션 키와 맞으면 MySQL이 읽어야 할 파티션만 추려 나머지를 건너뛴다. 그 결과 훑는 데이터 양이 줄어 조회가 빨라지고, 파티션 단위 관리로 오래된 데이터 정리도 쉬워진다.

스토어드 오브젝트(루틴·트리거·이벤트·뷰)

서버 안에 저장되어 재사용되는 데이터베이스 객체로, 저장 프로시저·함수(루틴), 트리거, 이벤트 스케줄러, 뷰를 아우른다.

#1문제 상황

애플리케이션이 여러 언어와 여러 서버에 흩어져 있으면, 같은 데이터 처리 로직을 각 프로그램이 따로 구현하게 된다. 이러면 한쪽 로직만 바뀌어도 다른 쪽과 결과가 어긋나고, 어떤 처리가 언제 실행됐는지 추적하기도 어렵다. 데이터 변경 시 반드시 함께 해야 하는 부수 작업을 애플리케이션에 맡기면, 그 애플리케이션을 우회해 직접 SQL을 실행했을 때는 그 작업이 빠져 데이터가 어긋난다.

#2핵심 질문

여러 애플리케이션이 공통으로 써야 하는 처리 로직과 데이터 규칙을 서버 안에 저장해 일관되게 실행하려면 어떻게 해야 하는가?

#3동작 예시

주문이 들어올 때 재고를 줄이는 처리를 저장 프로시저로 서버에 만들어 둔다고 하면, 각 애플리케이션은 그 프로시저를 호출하기만 하고 로직은 서버 안 한 곳에만 존재한다. 또 재고가 바뀔 때마다 이력을 남겨야 한다면, 재고 테이블에 트리거를 걸어 두어 어떤 경로로 값을 바꾸든 자동으로 이력이 기록되게 한다. 매일 밤 통계를 갱신해야 한다면 이벤트 스케줄러에 작업을 등록해 정해진 시각에 서버가 스스로 실행하게 한다.

#4동작 과정

  1. 정의와 저장저장 프로시저·함수(루틴), 트리거, 이벤트, 뷰를 CREATE 문으로 서버에 등록한다. 이 정의는 서버 안에 저장되어 이름으로 다시 호출된다.
  2. 실행 시점에 따른 동작루틴은 호출될 때, 트리거는 테이블의 삽입·수정·삭제 시점에, 이벤트는 예약한 시각에 각각 실행된다. 뷰는 저장된 SELECT 정의를 통해 실제 테이블을 대신 조회하게 한다.
  3. 권한 확인과 결과 반영서버는 실행 요청에 대해 해당 객체에 대한 권한을 확인하고 처리한다. 그 결과 여러 애플리케이션이 같은 로직과 규칙을 공유하게 되어 중복 구현과 불일치가 줄어든다.

처리 로직과 데이터 규칙을 서버 안에 저장해 이름으로 호출·자동 실행되게 함으로써 여러 애플리케이션이 같은 방식을 공유하게 하는 것

INFORMATION_SCHEMA

데이터베이스·테이블·컬럼·권한 등 서버의 메타데이터를 표준 SQL 형태의 읽기 전용 테이블로 조회할 수 있게 하는 시스템 스키마다.

#1문제 상황

서버에 어떤 데이터베이스와 테이블이 있고 각 컬럼이 어떤 타입인지, 누가 어떤 권한을 가졌는지 알아내려면 서버 내부 정보를 뒤져야 한다. 예전에는 이런 정보를 서버마다 다른 SHOW 명령의 출력 형태로만 볼 수 있어, 프로그램이 결과를 읽어 처리하기가 번거로웠다. 여러 서버의 테이블 목록을 한 번에 비교하려 해도 출력 형식이 제각각이라 자동화하기 어려웠다.

#2핵심 질문

서버의 구조와 권한 같은 메타데이터를 프로그램이 표준 SQL로 일관되게 조회하려면 어떻게 해야 하는가?

#3동작 예시

현재 데이터베이스의 테이블 이름과 엔진, 행 수 추정치를 알고 싶다면 SELECT TABLE_NAME, ENGINE, TABLE_ROWS FROM INFORMATION_SCHEMA.TABLES WHERE TABLE_SCHEMA = 'mydb'처럼 평범한 SELECT를 실행한다. 이 결과는 다른 테이블을 조회할 때와 똑같은 행과 열 형태로 돌아오므로, 애플리케이션이 결과를 그대로 읽어 처리할 수 있다. 컬럼 정보는 COLUMNS 테이블, 권한 정보는 관련 권한 테이블에서 같은 방식으로 조회한다.

#4동작 과정

  1. 메타데이터 노출서버가 관리하는 데이터베이스·테이블·컬럼·권한 같은 정보를 읽기 전용 테이블로 드러낸다. 사용자가 값을 직접 바꾸는 것이 아니라 조회만 하는 대상이다.
  2. 표준 SQL로 조회INFORMATION_SCHEMA 이름 아래의 테이블을 일반 SELECT 문으로 질의한다. WHERE와 JOIN도 쓸 수 있어 원하는 조건만 골라낼 수 있다.
  3. 프로그램 친화적 결과결과가 다른 조회와 같은 표 형태로 돌아와 코드로 다루기 쉽다. 그 결과 서버마다 다른 명령 출력에 기대지 않고 메타데이터를 일관되게 자동 처리할 수 있다.

Performance Schema

서버 내부의 실행·대기·I/O·메모리 사용 같은 성능 관련 이벤트를 계측해 테이블로 모니터링할 수 있게 하는 스키마다.

#1문제 상황

서버가 느려졌을 때 어느 SQL이 시간을 잡아먹는지, 어느 자원에서 대기가 쌓이는지 알기 어렵다. 실행 중인 SQL을 잠깐 보는 명령은 그 순간의 목록만 보여 줄 뿐, 이벤트가 얼마나 걸렸고 어떤 대기와 얽혔는지는 남기지 않는다. 그래서 병목을 짐작으로 추측하다 실제 원인을 놓치기 쉽다.

#2핵심 질문

서버 안에서 일어나는 실행·대기·I/O 같은 성능 이벤트를 시점별로 기록해 정확히 들여다보려면 어떻게 해야 하는가?

#3동작 예시

어떤 SQL이 오래 걸리는지 보고 싶다면 Performance Schema의 문장 요약(다이제스트) 테이블에서 같은 형태의 SQL별로 총 실행 시간과 실행 횟수를 조회한다. 같은 종류의 SQL을 하나로 묶어 통계를 내므로, 여러 번 반복돼 누적 시간이 큰 문장을 찾아낼 수 있다. 대기가 몰리는 지점을 보려면 대기 이벤트 테이블을 조회해 어느 자원에서 오래 기다렸는지 확인한다.

#4동작 과정

  1. 계측 대상 지정서버 안의 어떤 활동을 측정할지 계측기(instrument)와 소비자(consumer)를 켜고 끈다. 측정 범위를 좁히면 부담을 줄이면서 필요한 정보만 모을 수 있다.
  2. 이벤트 수집스레드의 실행과 대기, 파일·뮤텍스 같은 활동이 일어날 때마다 시간과 함께 계측되어 테이블에 기록된다. 실행 중인 현재 이벤트와 누적된 과거 이벤트가 각각의 테이블에 쌓인다.
  3. 테이블 조회로 진단기록된 데이터를 SQL로 조회해 어느 문장과 자원이 병목인지 확인한다. 그 결과 추측이 아니라 수집된 수치를 근거로 성능 문제를 짚어낼 수 있다.

#5한 줄 요약

서버 내부의 실행·대기·I/O 같은 성능 이벤트를 계측해 테이블로 제공함으로써 병목을 수치로 진단하게 하는 모니터링 스키마

#1문제 상황

Performance Schema는 성능 데이터를 아주 세밀하게 모으지만, 원시 테이블과 컬럼 이름이 내부 구조 기준이라 사람이 바로 읽고 해석하기 어렵다. 어떤 값을 보려면 여러 테이블을 조인해 원하는 형태로 다시 가공해야 하고, 매번 같은 조회를 손으로 짜는 일이 반복된다. 진단에 필요한 계산과 정리를 조회할 때마다 직접 하는 것은 번거롭고 실수도 생긴다.

#2핵심 질문

Performance Schema가 모은 원시 성능 데이터를 사람이 바로 읽고 쓰는 형태로 정리하려면 어떻게 해야 하는가?

#3동작 예시

어떤 문장이 누적 시간을 많이 썼는지 보고 싶을 때, Performance Schema의 여러 테이블을 직접 조인하는 대신 sys 스키마의 뷰를 조회한다. 이 뷰는 이미 실행 시간과 횟수 등 필요한 값만 읽기 좋은 형태로 정리해 두었으므로 한 번의 조회로 결과를 얻는다. 설정을 바꾸거나 진단 보고서를 만들 때는 sys 스키마가 제공하는 저장 프로시저를 호출해 필요한 작업을 대신 수행하게 할 수 있다.

#4동작 과정

  1. 원시 데이터 위에 뷰 구성Performance Schema와 INFORMATION_SCHEMA의 데이터를 조인·요약해 사람이 읽기 쉬운 뷰로 미리 정의해 둔다. 사용자는 그 뷰를 평범한 SELECT로 조회한다.
  2. 함수와 프로시저 제공값을 보기 좋게 바꾸는 함수와, 성능 설정을 바꾸거나 진단 보고서를 만드는 저장 프로시저를 함께 제공한다. 반복 작업을 호출 한 번으로 처리하게 해 준다.
  3. 진단 작업에 바로 사용튜닝과 진단에 자주 쓰는 조회를 이 뷰와 프로시저로 바로 실행한다. 그 결과 원시 테이블을 직접 가공하지 않고도 성능 상태를 빠르게 파악할 수 있다.

#1문제 상황

애플리케이션은 Java, Python, C++, Node.js, PHP 등 서로 다른 언어와 환경에서 작성된다. MySQL 서버는 클라이언트와 정해진 규칙으로 대화하므로, 각 언어가 이 규칙을 직접 구현해야 한다면 언어마다 접속·질의 처리 코드를 처음부터 만들어야 한다. 그렇게 되면 언어별로 동작이 제각각이 되고, 프로토콜이 바뀔 때마다 모든 구현을 각자 고쳐야 한다.

#2핵심 질문

#3동작 예시

Java 프로그램에서 MySQL에 접속할 때는 Connector/J 드라이버를 사용하고, Python에서는 Connector/Python으로 접속한다. 각 드라이버는 해당 언어가 쓰기 편한 인터페이스를 제공하면서 내부적으로는 MySQL 서버와 정해진 프로토콜로 대화한다. ODBC처럼 여러 언어가 공통으로 쓰는 표준 인터페이스를 통해 접속하려면 Connector/ODBC를 사용한다.

#4동작 과정

  1. 드라이버 설치와 선택사용하는 언어에 맞는 커넥터를 설치한다. 언어별로 공식 드라이버가 제공되므로 그 언어의 관례에 맞는 방식으로 코드를 작성한다.
  2. 연결과 SQL 실행애플리케이션이 드라이버를 통해 서버에 연결하고 SQL 문을 보낸다. 드라이버가 그 요청을 서버가 알아듣는 프로토콜 형식으로 바꿔 주고, 응답을 다시 그 언어가 다루는 형태로 돌려준다.
  3. 공통 인터페이스로도 접근C API나 ODBC 같은 저수준·표준 인터페이스를 쓰면 여러 언어가 서버 자원에 같은 방식으로 접근한다. 그 결과 각 언어가 프로토콜을 직접 구현하지 않고도 MySQL에 연결하고 SQL을 실행할 수 있다.

엔터프라이즈 에디션 개요

백업, 보안, 감사, 방화벽, 스레드 풀 등 상용 부가 기능을 포함한 MySQL 상용 배포판이다.

#1문제 상황

무료로 배포되는 MySQL Community Edition은 트랜잭션 안전성과 ACID 준수, 커밋·롤백·충돌 복구·행 단위 잠금까지 갖춘 서버를 제공하지만, 운영에 필요한 백업·보안·감사·방화벽 같은 부가 기능은 포함하지 않는다. 그래서 실서비스 운영자는 별도 도구를 조합해야 하고, 온라인 상태에서 데이터를 안전하게 백업하거나 접속을 통제·감사하는 작업을 서버 차원에서 일관되게 처리하기 어렵다.

#2핵심 질문

서버 본체는 같은데 운영에 필요한 백업·보안·감사·방화벽·스레드 풀 기능을 한 제품에서 일관되게 제공받을 수는 없을까?

#3동작 예시

MySQL Enterprise Edition은 Community Edition과 동일한 MySQL Server를 기반으로 하면서, 그 위에 MySQL Enterprise Backup, Security, Encryption, Audit, Firewall, Thread Pool, Data Masking and De-Identification, Telemetry 같은 상용 구성 요소를 함께 묶어 제공한다. 예를 들어 운영 중인 서버에서 백업이 필요하면 별도 스크립트 대신 Enterprise Backup 구성 요소를 사용하고, 접속을 통제하려면 Enterprise Firewall 구성 요소를 켜는 식으로, 하나의 배포판 안에서 운영 기능을 선택해 활성화한다.

#4동작 과정

  1. 공통 서버 기반Community Edition과 같은 MySQL Server를 설치해 트랜잭션·ACID·커밋·롤백·충돌 복구·행 단위 잠금 기능을 그대로 사용한다. 서버 자체 동작은 동일하다.
  2. 상용 구성 요소 추가백업(Enterprise Backup), 보안·암호화(Enterprise Security, Encryption), 감사(Enterprise Audit), 방화벽(Enterprise Firewall), 스레드 풀(Enterprise Thread Pool), 데이터 마스킹(Data Masking and De-Identification), 원격 측정(Telemetry) 구성 요소를 배포판에 함께 포함한다.
  3. 운영 기능 활성화필요한 구성 요소만 골라 켜서 모니터링과 온라인 백업, 접속 통제 같은 운영 작업을 서버 차원에서 처리한다. 그래서 별도 도구 조합 없이 백업·보안·감사를 한 제품 안에서 운영할 수 있다.

Workbench와 Telemetry(OpenTelemetry)

MySQL Workbench는 서버를 시각적으로 관리·설계하는 GUI 도구이고, MySQL Telemetry는 OpenTelemetry로 서버의 트레이스·메트릭·로그를 수집·전송하는 기능이다.

#1문제 상황

서버를 운영하다 보면 어떤 쿼리가 느린지, 어디서 병목이 생기는지 파악해야 하는데, 서버가 남기는 정보는 로그 파일이나 상태 변수처럼 제각각 흩어져 있어 앱과 서버를 하나의 흐름으로 추적하기 어렵다. 또 서버를 설치·설계·관리하려면 명령줄만으로는 전체 구조를 파악하기 번거롭다.

#2핵심 질문

서버가 내는 트레이스·메트릭·로그를 표준 형식으로 모아 앱과 함께 관측하고, 서버 구조도 시각적으로 관리할 수는 없을까?

#3동작 예시

MySQL Telemetry는 OpenTelemetry(OTel, 애플리케이션과 서버의 관측 데이터를 공통 형식으로 내보내는 오픈소스 표준)를 서버 구성 요소로 포함해, 트레이스(요청이 지나간 경로), 메트릭(수치 지표), 로그를 밖으로 내보낸다. 예를 들어 서버에서 트레이스 수집을 켜면 쿼리 처리 흐름이 OTel 형식으로 전송되어, 같은 형식을 쓰는 관측 도구에서 앱 호출과 서버 작업을 이어서 볼 수 있다. 서버 구조 설계·관리는 MySQL Workbench라는 GUI 도구로 처리한다.

#4동작 과정

  1. OTel 지원 설치서버에 OpenTelemetry 지원 구성 요소를 설치한다. 이를 통해 트레이스·메트릭·로그를 공통 표준 형식으로 다룰 준비가 된다.
  2. 수집 대상별 설정Telemetry 변수(수집 동작을 제어하는 설정값)로 트레이스·메트릭·로그를 각각 켜고, 전송 형식과 대상을 지정한다. 그래서 필요한 관측 데이터만 골라 내보낼 수 있다.
  3. 수집·전송서버가 트레이스, 메트릭(서버 미터·서버 메트릭), 로깅 데이터를 만들어 OTel 형식으로 내보낸다. 그래서 앱과 서버를 같은 형식으로 이어 디버깅·테스트의 세밀도가 높아진다.

#1문제 상황

MySQL을 쓰다 보면 특정 기능이 어떻게 동작하는지, 마주친 에러가 무엇을 뜻하는지 매번 매뉴얼 전체를 뒤져야 한다. 질문은 일반·스토리지 엔진·SQL 모드·보안·복제 등 영역별로 흩어져 있고, 에러 메시지도 어느 계층에서 나온 것인지 알기 어려워 원인을 좁히기 힘들다.

#2핵심 질문

영역별로 자주 나오는 질문과 에러 메시지의 구성·해석, 주요 용어 정의를 한데 모아 빠르게 찾을 수는 없을까?

#3동작 예시

FAQ 부록은 General, Storage Engines, Server SQL Mode, Stored Procedures and Functions, Triggers, Views, INFORMATION_SCHEMA, Migration, Security, NDB Cluster, 중국어·일본어·한국어 문자 집합, Connectors & APIs, C API·libmysql, Replication, Enterprise Thread Pool, InnoDB Change Buffer, InnoDB Data-at-Rest Encryption, Virtualization Support 같은 주제별 질문을 나눠 제공한다. 에러는 Error Message Sources and Elements(에러 메시지의 출처와 구성 요소), Error Information Interfaces(에러 정보를 얻는 인터페이스), Problems and Common Errors(흔한 문제와 오류)로 안내하고, 마지막에 MySQL Glossary가 용어를 정의한다. 예를 들어 에러를 만나면 먼저 그 메시지가 어느 출처·구성 요소로 이루어졌는지 확인해 원인 범위를 좁힌다.

#4동작 과정

  1. 영역별 질문 조회FAQ에서 현재 문제가 속한 영역(일반, 스토리지 엔진, 보안, 복제 등)을 골라 해당 질문을 읽는다. 그래서 매뉴얼 전체를 뒤지지 않고 좁혀 볼 수 있다.
  2. 에러 메시지 해석에러 메시지의 출처와 구성 요소를 확인하고, 어떤 인터페이스로 에러 정보를 얻는지 파악한다. 그래서 메시지에서 어느 계층 문제인지 가려낸다.
  3. 용어·사례 대조흔한 문제와 오류 항목, Glossary의 용어 정의와 대조한다. 그래서 문제를 재현·해결하고 용어를 정확히 이해한다.
