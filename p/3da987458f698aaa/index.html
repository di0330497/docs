1부. 웹 보안 기초와 AWS WAF 입문001

AWS WAF란 무엇인가

웹 요청을 들여다보고 허용·차단 규칙을 적용하는 서비스의 역할

작은 온라인 쇼핑몰을 운영하는데 어느 날 주문 입력창에 의미 없는 문자열이 초당 수백 건씩 밀려들어 서버가 응답을 멈춰 버렸다고 생각해 봅시다. 그 요청들을 하나하나 사람이 걸러낼 수는 없으니, 들어오는 요청의 내용을 미리 들여다보고 정해 둔 기준에 맞지 않으면 서버에 닿기 전에 돌려보내는 장치가 필요해집니다. 그 역할을 하는 것이 AWS의 클라우드 서비스인 AWS WAF(Web Application Firewall)입니다.

이것은 아파트 정문의 경비실과 같습니다. 경비원이 방문객의 명함과 소지품을 확인하듯, WAF는 요청에 담긴 IP 주소, 헤더(header), 본문(body)의 내용을 미리 작성해 둔 규칙(rule)과 하나씩 대조합니다. 규칙은 통과시키는 허용(allow), 막는 차단(block), 막지는 않고 세기만 하는 계수(count)로 나뉘고, 이런 규칙들을 한데 묶은 웹 ACL(Web ACL) 단위로 어느 사이트에 적용할지 정합니다.

규칙에 걸린 요청은 실제 서버인 오리진(origin)에 도달하기 전에 그 자리에서 거절되므로, 서버는 정상 요청을 처리하는 일에만 집중할 수 있습니다.

정리하면 AWS WAF는 CDN이나 로드 밸런서 앞단에서 HTTP 요청의 내용을 검사하고 허용과 차단을 결정하는 웹 애플리케이션 방화벽이며, 그 판단 기준은 사용자가 정의한 규칙과 웹 ACL로 관리됩니다.

웹 요청이 서버에 닿는 경로

브라우저에서 오리진까지 거치는 구간과 공격이 끼어들 수 있는 지점

브라우저 주소창에 주소를 입력하면 화면이 곧바로 뜨는 것처럼 보이지만, 그 요청은 생각보다 여러 구간을 거쳐 서버에 도착합니다. 이 구간을 모르면 공격이 어디쯤에서 끼어들 수 있는지도 알 수 없고, 방어 장치를 어디에 두어야 하는지도 판단할 수 없습니다.

택배가 집까지 오는 과정과 같습니다. 브라우저는 먼저 주소를 IP 주소로 바꾸는 DNS(Domain Name System) 조회를 하고, 이는 택배를 보내기 전에 수취인 주소를 확인하는 일에 해당합니다. 그다음 CDN(Content Delivery Network)이나 로드 밸런서(load balancer) 같은 중간 거점을 지나는데, 이는 물류 허브에서 짐을 나눠 싣는 단계와 같고, 마지막으로 실제 내용을 가진 오리진 서버가 요청을 처리합니다.

공격자는 주소 조회 단계에서 가짜 주소를 흘리거나, 중간 거점에서 요청을 대량으로 부풀리거나, 오리진에 직접 의미 없는 요청을 밀어 넣는 식으로 끼어들 수 있습니다.

즉 웹 요청은 이름 해석, 중간 전달, 오리진 처리의 세 구간을 지나며, WAF 같은 방어 장치는 보통 중간 거점과 오리진 사이에서 요청 내용을 검사하는 위치에 놓입니다.

WAF와 네트워크 방화벽의 차이

IP·포트를 보는 방화벽과 요청 내용을 보는 WAF의 시야 차이

서버를 보호한다고 하면 흔히 방화벽을 떠올리지만, 어떤 방화벽을 두느냐에 따라 볼 수 있는 것이 전혀 달라집니다. IP 주소와 포트만 막는 방화벽을 두고도 정상처럼 보이는 요청에 실린 공격에 속수무책으로 당하는 일이 생깁니다.

이것은 건물 경비와 우편물 검사의 차이에 가깝습니다. 네트워크 방화벽(network firewall)은 출입문을 지키는 경비원처럼 어디서 왔는지(IP 주소)와 몇 번 출입구로 오는지(포트)만 확인하고, 그 안에 무엇이 들었는지는 보지 않습니다. 반면 WAF는 도착한 우편물을 뜯어보는 검사원처럼 HTTP 요청의 헤더, 파라미터(parameter), 본문에 어떤 문장이 들어 있는지까지 읽습니다.

그래서 같은 주소에서 온 같은 포트의 요청이라도, 방화벽은 통과시키고 WAF는 내용을 근거로 막을 수 있습니다. 다루는 계층으로 말하면 방화벽은 전송 계층까지, WAF는 그 위의 응용 계층을 봅니다.

결국 네트워크 방화벽은 연결 자체를 통제하고 WAF는 연결 안의 내용을 통제하며, 두 장치는 서로를 대체하는 것이 아니라 층을 나누어 함께 쓰입니다.

OWASP Top 10 훑어보기

웹에서 가장 흔한 취약점 열 가지의 큰 그림

웹 사이트를 만드는 사람들은 저마다 다른 실수를 하지만, 공격자들이 노리는 허점은 놀랄 만큼 비슷한 곳에 몰려 있습니다. 그 허점들을 매번 처음부터 조사하는 대신, 널리 알려진 것부터 순서대로 살펴볼 수 있게 정리해 둔 목록이 있습니다.

이것은 병원의 건강검진 항목표와 같습니다. OWASP(Open Worldwide Application Security Project)라는 비영리 단체가 웹에서 가장 흔한 취약점 열 가지를 모아 Top 10이라는 이름으로 공개하는데, 이는 검진표에 혈압과 혈당처럼 우선 확인할 항목을 적어 둔 것과 같습니다. 각 항목에는 어떤 상황에서 문제가 생기는지와 어떻게 줄일 수 있는지가 함께 실려 있어, 개발팀은 자기 서비스가 어느 항목에 해당하는지 짚어 볼 수 있습니다.

다만 이 목록은 위험도와 발생 빈도를 바탕으로 몇 년마다 개정되므로, 항목의 순서나 구성은 판(version)에 따라 달라질 수 있습니다.

요약하면 OWASP Top 10은 웹 애플리케이션 보안에서 가장 자주 문제 되는 취약점 범주를 정리한 참고 목록이며, 개별 서비스에 그대로 적용되는 절대 기준이 아니라 우선순위를 잡기 위한 출발점입니다.

SQL 인젝션(SQL Injection)

입력값에 SQL을 섞어 데이터베이스를 조작하는 공격의 원리

로그인 화면의 아이디 칸에 이상한 문자열을 넣었을 뿐인데 비밀번호 없이 관리자로 들어가지는 사고가 실제로 일어납니다. 입력값이 데이터베이스에 전달되는 명령문의 일부로 그대로 붙어 버리기 때문인데, 이것이 SQL 인젝션(SQL Injection)입니다.

이것은 택배 접수 창구의 서식과 같습니다. 창구 직원이 접수증의 한 칸에 적힌 내용을 그대로 읽어 업무 지시로 처리한다고 할 때, 악의적인 사람이 그 칸에 "이 건은 배송 보류" 같은 지시문을 적어 넣으면 직원은 그것을 고객의 요청이 아니라 회사 지시로 받아들입니다.

SQL 인젝션도 똑같이, 사용자가 넣은 값이 SQL(Structured Query Language) 질의문 안에 문자열로 이어 붙으면서 원래의 조건절을 무력화하거나 추가 명령을 끼워 넣습니다. 그래서 입력값을 질의문과 분리해 넘기는 준비된 질의(prepared statement)를 쓰고, 입력 형식을 검증하는 것이 근본적인 대비가 됩니다.

정리하면 SQL 인젝션은 사용자 입력이 데이터베이스 질의문의 구조를 바꾸도록 만드는 공격이며, 입력을 명령이 아닌 값으로만 취급하게 만드는 것이 핵심 방어입니다.

크로스 사이트 스크립팅(XSS)

다른 사용자의 브라우저에서 악성 스크립트가 실행되는 공격

게시판에 남긴 댓글 하나 때문에 그 글을 읽은 다른 사용자의 로그인 정보가 빠져나가는 일이 있습니다. 서버는 아무 문제 없이 댓글을 저장했지만, 그 안에 섞인 스크립트가 읽는 사람의 브라우저에서 실행되기 때문이며, 이를 크로스 사이트 스크립팅(XSS, Cross-Site Scripting)이라고 합니다.

이것은 공용 게시판에 남의 이름으로 쪽지를 붙이는 것과 같습니다. 사이트가 사용자가 쓴 글을 그대로 게시판에 붙이면, 공격자는 그 글에 "이 쪽지를 읽는 사람은 자기 지갑을 이 사람에게 넘겨라" 같은 문장을 숨겨 넣습니다.

피해자의 브라우저는 그 사이트를 신뢰하므로, 숨은 스크립트가 피해자의 쿠키(cookie)나 세션(session) 정보를 읽어 공격자에게 보내도록 동작할 수 있습니다. 대비의 기본은 출력할 때 꺾쇠괄호 같은 특수 문자를 무해한 형태로 바꾸는 이스케이프(escape) 처리와, 스크립트 실행을 제한하는 정책입니다.

결국 XSS는 신뢰받는 사이트의 화면을 통해 다른 사용자의 브라우저에서 악성 스크립트가 실행되는 공격이며, 저장된 내용을 화면에 내보낼 때 실행 코드가 아닌 글자로 다루는 것이 핵심입니다.

경로 탐색(Path Traversal)

../ 를 이용해 허용된 폴더 밖의 파일을 읽어가는 공격

인터넷 쇼핑몰의 상품 이미지 페이지는 보통 파일 이름 하나를 주소에 담아 서버로 보내고, 서버는 정해진 폴더에서 그 이름의 파일을 찾아 돌려줍니다. 그런데 이 이름을 검사 없이 그대로 받아들이면, 누군가 폴더를 빠져나가는 표시를 끼워 넣어 회사 내부 문서나 비밀번호가 적힌 설정 파일까지 읽어 갈 수 있게 됩니다.

호텔의 세탁물 창고를 떠올리면 이해가 쉽습니다. 창고 직원은 손님이 적어 낸 쪽지에 적힌 경로를 의심 없이 따라가 물건을 가져오는 역할만 맡고 있습니다. 문제는 누군가 쪽지에 창고 밖으로 나가 위층 지배인실 금고를 가져오라고 적어 내는 경우인데, 직원은 그것도 창고 안의 선반 이름인 줄 알고 그대로 다녀옵니다.

그래서 접수 창구에서 쪽지에 적힌 경로가 정말 우리 창고 안을 가리키는지, 밖으로 나가는 표시가 섞여 있지 않은지를 먼저 확인해야 합니다.

실제 기술에서는 사용자가 보낸 파일 경로에서 상위 폴더로 올라가는 표시인 "../"를 걸러 내고, 허용된 폴더 안에 실제로 존재하는 파일인지 확인한 뒤에만 읽도록 만듭니다. 이것이 경로 탐색(Path Traversal)을 막는 핵심입니다.

서버 측 요청 위조(SSRF)

서버가 내부 주소로 요청을 보내게 만드는 공격

회원가입 화면에서 프로필 사진을 가져오거나 다른 사이트의 글을 미리 보여 주려고, 서버가 사용자 대신 주소를 열어 보는 기능이 흔히 쓰입니다. 이때 서버가 아무 주소나 받아들이면, 공격자는 서버에게 회사 내부에서만 열리는 관리 페이지나 클라우드의 임시 자격 증명 주소를 대신 불러 오게 만들 수 있습니다.

사내에서 심부름을 도맡는 직원을 떠올려 보면 좋습니다. 이 직원은 사무실 열쇠와 내부 출입증을 가지고 있어서, 다른 부서가 주소를 적어 주면 그대로 다녀옵니다. 평소에는 바깥 업체에 보낼 서류를 받아 오는 일만 했는데, 쪽지에 3층 잠긴 문서고의 인사 기록이라고 적혀 있어도 심부름은 심부름이라며 열쇠로 문을 열고 가져옵니다.

바깥 사람이 직접 들어갈 수 없는 곳을, 안쪽 사정을 잘 아는 직원의 다리를 빌려 우회해 들어간 셈입니다.

그래서 서버가 대신 요청을 보낼 때는 미리 정한 허용 목록에 있는 주소만 부르게 하고, 내부망이나 클라우드 메타데이터 같은 사설 주소는 아예 차단해야 합니다. 이것이 서버 측 요청 위조(SSRF)를 막는 핵심입니다.

WAF가 막을 수 있는 것과 없는 것

애플리케이션 코드에서 고쳐야 할 부분과의 경계

방화벽을 세워 두면 웹 공격은 모두 막힌다고 생각하기 쉽지만, 실제 침해 사고를 보면 정상적인 요청 모양을 한 공격이 적지 않습니다. 그래서 어떤 문제는 웹 애플리케이션 방화벽(WAF)이 막을 수 있고 어떤 문제는 애플리케이션 코드를 고쳐야 하는지, 그 경계를 알아 두는 것이 중요합니다.

건물 로비의 경비원을 떠올리면 이 경계가 분명해집니다. 경비원은 가방 속을 들여다보고 흉기나 위험물처럼 미리 정해진 위험 신호를 찾아내는 일을 잘합니다. 하지만 입주민증을 정상적으로 찍고 들어온 사람이 사흘 동안 열 번씩 무료 시식 코너를 이용해도, 그건 한 사람에 한 번이라는 사내 규칙을 어긴 일이라 경비원이 알 도리가 없습니다.

마찬가지로 WAF는 이미 알려진 공격 패턴과 비정상적인 요청 모양은 걸러 내지만, 로그인한 사용자가 남의 글 번호를 바꿔 조회하는 권한 문제나 쿠폰 중복 사용 같은 업무 규칙의 허점은 판단하지 못합니다.

정리하면 WAF는 요청 자체의 모양을 보고 거르는 장치이고, 권한 확인과 입력 검증과 업무 규칙은 애플리케이션 코드가 책임져야 합니다. 이 경계를 넘어서까지 WAF에 맡기려 하면 막아야 할 정상 요청까지 함께 막히기 쉽습니다.

1부. 웹 보안 기초와 AWS WAF 입문010

AWS WAF 요금 구조

Web ACL·규칙·요청 수가 청구서에 어떻게 반영되는지

웹 애플리케이션 방화벽(WAF)을 켜 두면 요금이 어떻게 나오는지 몰라서, 월말 청구서를 보고 처음 예상보다 훨씬 큰 금액에 놀라는 경우가 있습니다. AWS WAF는 크게 세 가지, 즉 판정 단위인 Web ACL과 그 안에 들어가는 규칙, 그리고 실제로 검사한 요청 수를 기준으로 비용을 계산합니다.

유료 주차장을 떠올리면 구조가 그대로 겹칩니다.

  • 우선 주차장 하나를 운영한다는 기본 계약이 매달 발생하는데, 이것이 요청을 판정하는 가장 바깥 틀인 Web ACL입니다.
  • 다음으로 출입구마다 설치하는 감지 장비가 규칙인데, 장비를 몇 대 두느냐에 따라 요금이 붙고 장비마다 매달 기본료가 따로 있습니다.
  • 마지막으로 실제로 드나든 차량을 한 대씩 세어 요금을 매기듯, WAF도 검사한 요청 수를 백만 건 단위로 묶어 계산합니다.

그래서 규칙을 많이 만들수록, 그리고 트래픽이 많을수록 청구서가 올라가며, 정확한 단가는 시기와 리전에 따라 달라질 수 있습니다.

결국 AWS WAF 요금은 Web ACL이라는 판정 틀의 기본료, 규칙마다의 기본료, 검사한 요청 수의 세 축으로 이해하면 됩니다. 이 구조를 알고 있으면 규칙을 늘리기 전에 비용이 얼마나 붙는지 미리 가늠할 수 있습니다.

2부. Web ACL과 연결 대상011

Web ACL(웹 ACL)이란

규칙 묶음을 담아 요청을 판정하는 최상위 컨테이너

규칙을 이 앱에는 이렇게, 저 앱에는 저렇게 따로따로 걸어 두면 어느 요청이 어떤 기준으로 차단됐는지 한눈에 알기 어렵고, 설정이 조금만 늘어도 관리가 엉킵니다. 그래서 AWS WAF는 여러 규칙을 한 바구니에 담아 요청 하나하나를 최종 판정하는 최상위 틀을 두는데, 이것이 Web ACL입니다.

아파트 단지 정문의 경비 초소를 떠올려 보면 이해가 쉽습니다. 초소에는 출입과 관련된 검문 항목이 순서대로 적힌 판정 대장이 한 권 놓여 있는데, 이 대장이 바로 Web ACL입니다. 대장에는 차량 번호 조회, 방문 목적 확인, 심야 시간 통제 같은 항목이 번호 순으로 적혀 있고, 각 항목이 곧 규칙이며 앞 번호에서 걸리면 뒤 항목은 보지 않고 결론을 냅니다.

그리고 대장 어디에도 해당하지 않는 사람을 어떻게 할지, 즉 통과시킬지 막을지 정해 두는데 이것이 기본 동작입니다.

실제로 Web ACL은 하나 이상의 규칙을 담고, 규칙을 평가할 순서와 아무 규칙에도 걸리지 않았을 때의 기본 동작을 함께 정의하며, CloudFront나 로드 밸런서 같은 자원에 연결해 씁니다. 그래서 규칙을 새로 만들 때도 어느 Web ACL에 넣을지만 정하면 같은 기준이 일관되게 적용됩니다.

CloudFront와 WAF 연결

엣지 지점에서 요청을 검사하는 구성

사용자가 먼 곳에서 접속하면 요청은 바다를 건너 먼 리전의 서버까지 갔다가 돌아오느라 느려지고, 그 먼 곳에서 공격 트래픽까지 받아 내면 서버가 쉽게 지칩니다. CloudFront로 사용자와 가까운 엣지 지점에서 콘텐츠를 전달하고 그 앞단에 AWS WAF를 붙이면, 공격을 서버에 닿기 전에 걸러 낼 수 있습니다.

전국에 물류 거점을 둔 택배 회사를 떠올리면 구성이 그대로 대응됩니다. 각 지역의 물류 거점이 CloudFront인데, 손님이 가까운 거점에 물건을 맡기면 먼 본사 창고까지 가지 않아도 빠르게 받아 볼 수 있습니다. 이 거점 입구에 검문소를 하나 두는 것이 WAF를 연결하는 일이고, 의심스러운 짐은 여기서 바로 돌려보내며 통과한 짐만 본사 창고로 보냅니다.

그래서 본사 창고, 즉 원본 서버는 정상 요청만 받게 되어 부담이 크게 줄어듭니다.

정리하면 CloudFront는 사용자와 가까운 엣지에서 응답을 대신 전달하는 계층이고, AWS WAF는 그 엣지에 붙여 요청을 검사하는 계층이라, 둘을 함께 두면 차단도 빠르고 원본 보호도 됩니다. 실제 설정은 CloudFront 배포에 Web ACL을 연결하는 방식으로 이루어집니다.

Application Load Balancer와 WAF 연결

리전 단위 로드 밸런서 앞에서 검사하는 구성

회사 서비스가 커지면서 서버 한 대로는 트래픽을 감당하지 못해 여러 대로 나눠 받게 되면, 그 앞에 Application Load Balancer(애플리케이션 로드 밸런서, 줄여서 ALB)를 세워 요청을 분배합니다. 그런데 이 분배 장치를 설치했을 뿐 보안 검사는 따로 붙이지 않으면, 악성 요청도 정상 요청과 똑같이 여러 서버로 고르게 흩어져 들어가 피해가 순식간에 번집니다.

이 구조는 아파트 단지 정문 경비실과 같습니다. ALB는 방문객을 여러 동으로 안내하는 안내 데스크이고, WAF(Web Application Firewall, 웹 애플리케이션 방화벽)는 그 안내 데스크 바로 앞에 앉아 수상한 사람을 걸러내는 경비원입니다. AWS 콘솔에서는 ALB를 만들 때 연결된 웹 ACL(Web Access Control List, 접근 제어 규칙 묶음)을 지정하는 방식으로 경비원을 배치하며, 이때 ALB와 웹 ACL이 같은 리전(region, 물리적 데이터 센터 묶음)에 있어야 합니다.

경비원을 통과한 방문객만 안내 데스크에 도달하므로, 서버들은 이미 검사를 마친 요청만 받게 됩니다.

정리하면 Application Load Balancer에 WAF를 연결한다는 것은 리전 단위 로드 밸런서 앞단에서 웹 요청을 검사하고 통과 여부를 결정하는 구성이며, 검사 위치가 서버가 아니라 진입점이라는 점이 핵심입니다.

API Gateway와 WAF 연결

REST·HTTP API 엔드포인트를 보호하는 방법

서버 없이 API(Application Programming Interface, 프로그램끼리 대화하는 창구)만 열어 두고 운영하는 서비스는 그 창구 주소 하나로 전 세계에 노출됩니다. 이때 아무 검사 없이 두면 자동화된 도구가 초당 수천 건의 요청을 쏟아부어 요금을 폭발시키거나, 비정상 입력으로 백엔드 로직을 흔들어 놓습니다.

이 상황은 택배 회사의 물류 창고 입구와 비슷합니다. API Gateway(API 게이트웨이)는 주문을 접수해 알맞은 창고로 넘기는 접수 창구이고, WAF는 그 창구 앞에서 송장을 확인하고 의심스러운 화물을 되돌려 보내는 검문소입니다. REST API와 HTTP API 모두 각 단계(stage)에 웹 ACL을 연결할 수 있어서, 주소 체계를 바꾸지 않고도 입구에 검문소를 세울 수 있습니다.

검문소를 통과하지 못한 요청은 접수 창구까지 오지 않으므로 백엔드가 처리할 일 자체가 줄어듭니다.

결국 API Gateway와 WAF의 연결은 REST·HTTP API 엔드포인트 앞에서 요청을 먼저 심사해 통과분만 백엔드로 보내는 보호 방식이며, 엔드포인트를 바꾸지 않고 규칙만 덧붙인다는 점이 장점입니다.

Verified Access와 WAF 연결

사내 앱 접근 제어 위에 WAF를 얹는 구성

이것이 AWS Verified Access(사용자와 기기 상태로 사내 앱 접근을 판단하는 접근 제어 서비스)와 AWS WAF(웹 요청을 규칙으로 검사하는 방화벽)를 이어 붙이는 구성입니다. 건물에 비유하면 Verified Access는 출입증과 신원을 확인하는 경비원이고, WAF는 그 앞에서 소포와 서류를 검사하는 검수대입니다. 검수대는 택배 상자에 위험한 것이 들었는지, 주소가 이상한지, 같은 사람이 하루에 수백 개를 보내지는 않는지를 먼저 봅니다. 문제가 없는 요청만 경비원에게 넘어가고, 경비원은 그제서야 출입증이 유효한지와 노트북이 회사 규정을 지키는지를 확인해 문을 열어 줍니다. 이렇게 하면 자격은 있지만 내용이 위험한 요청이 문 안쪽까지 들어오는 일이 줄어듭니다.

정리하면, WAF는 요청의 형식과 패턴을 걸러 내는 앞단의 검사 장치이고 Verified Access는 사용자와 기기의 신뢰를 판단하는 뒷단의 출입 심사이며, 두 층을 이 순서로 세울 때 사내 앱의 문은 한 겹 더 단단해집니다.

리전 Web ACL과 글로벌 Web ACL

범위(Scope) 선택이 배포 가능한 리소스를 가르는 방식

WAF 규칙을 다 만들어 놓고도 배포 직전에 이 규칙이 어디까지 적용되는가 하는 지점에서 막히는 일이 생깁니다. CloudFront처럼 전 세계 엣지에서 도는 서비스와 특정 리전의 로드 밸런서는 규칙을 두는 위치가 다르고, 범위를 잘못 고르면 대상 목록에 아예 나타나지 않아 붙일 수 없기 때문입니다.

그래서 AWS WAF는 Web ACL(규칙 묶음을 담는 그릇)을 만들 때 범위(Scope)를 먼저 고르게 하고, 이 선택이 리전 Web ACL과 글로벌 Web ACL을 갈라 놓습니다. 비유하면 글로벌 Web ACL은 본사가 모든 지점에 내려보내는 공통 보안 규정이고, 리전 Web ACL은 각 지점이 자기 건물에 맞춰 세우는 현관 검사대입니다. 본사 규정은 전 지점의 정문과 창구에 똑같이 적용되지만, 지점 검사대는 그 지점 건물 안에서만 작동합니다.

실제로 글로벌 범위는 CloudFront 배포를 대상으로 하며 콘솔에서는 us-east-1 리전에 만들어지고, 리전 범위는 Application Load Balancer, API Gateway, AppSync 같은 리전 리소스를 대상으로 합니다. 그래서 규칙 내용이 같아도 대상이 다르면 Web ACL을 따로 만들어야 하고, 하나의 Web ACL을 두 범위에 겹쳐 쓸 수는 없습니다. 정리하면 범위 선택은 규칙의 내용이 아니라 어느 리소스에 붙일 수 있는가를 결정하는 첫 단추이고, 보호할 대상을 먼저 정한 뒤 범위를 고르는 순서가 안전합니다.

규칙(Rule)의 구성 요소

조건·동작·우선순위가 모여 하나의 규칙이 되는 구조

WAF를 처음 만지면 규칙을 하나씩 따로 배우게 되어, 왜 어떤 요청은 막히고 어떤 요청은 통과하는지 설명하기 어려워집니다. 실제 요청은 여러 규칙을 차례로 지나가며 판정을 받고, 그 판정은 조건과 동작과 순서가 맞물려 만들어지기 때문입니다.

그래서 규칙(Rule)은 무엇을 볼 것인가인 조건, 걸렸을 때 무엇을 할 것인가인 동작, 몇 번째로 볼 것인가인 우선순위, 이 세 가지가 모여 하나의 판단 단위가 됩니다. 우편실 비유로 보면 조건은 봉투에서 확인할 항목입니다. 발신 주소가 해외인지, 봉투 크기가 규격을 벗어났는지, 같은 주소에서 오늘 몇 통이 왔는지를 먼저 살핍니다. 동작은 그 항목에 걸렸을 때 담당자가 하는 일이고, 반송할지, 열어 볼지, 그냥 통과시킬지가 여기서 정해집니다. 우선순위는 서류가 쌓인 순서로, 먼저 본 담당자가 반송이라고 찍으면 뒤 담당자는 더 볼 것 없이 그 결론을 따릅니다.

정리하면 규칙은 조건으로 대상을 찾고 동작으로 결론을 내며 우선순위로 그 결론의 차례를 정하는 묶음이고, 이 셋 중 하나만 어긋나도 의도한 차단은 일어나지 않습니다.

3부. Web ACL과 규칙의 구조022

규칙 동작: Allow·Block·Count

조건을 만족한 요청을 어떻게 처리할지 정하는 방법

규칙을 막 만들어 배포하면, 잘못 만든 규칙 하나가 정상 사용자를 통째로 막아 버리는 사고가 자주 납니다. 그래서 WAF는 조건에 걸린 요청을 무조건 막는 대신, 그 요청을 어떻게 처리할지를 규칙마다 따로 고르게 해 두었습니다. 이 선택지가 Allow(허용), Block(차단), Count(세기만 함) 세 가지 동작입니다.

건물 안내데스크 비유로 보면, 방문객의 서류를 확인한 직원이 세 가지 도장 중 하나를 찍는 것과 같습니다. Allow는 통과 도장으로, 이 요청은 문제 없다고 확정하고 바로 들여보냅니다. Block은 반려 도장으로, 요청을 즉시 돌려보내고 뒤의 규칙들은 그 요청을 더 살피지 않습니다. Count는 기록만 도장으로, 문은 그대로 열어 주되 어떤 요청이 이 조건에 걸렸는지를 지표와 로그로 남깁니다.

정리하면 세 동작은 차단의 강도가 아니라 판단의 확신도를 담는 장치이고, 새 규칙은 대개 Count로 먼저 관찰한 뒤 Block으로 올리는 순서를 밟습니다.

3부. Web ACL과 규칙의 구조023

우선순위(Priority)와 평가 순서

낮은 번호의 규칙부터 평가되는 방식

규칙을 여러 개 붙여 놓으면, 같은 요청이 두 규칙에 동시에 걸리는 순간이 반드시 생깁니다. 이때 어느 규칙이 이기는지 정해져 있지 않으면 결과가 매번 달라져 원인을 찾을 수 없게 되므로, WAF는 규칙마다 우선순위(Priority)라는 번호를 붙여 순서를 고정합니다.

공장 검수 라인 비유로 보면, 컨베이어 벨트 위의 부품이 번호가 낮은 검사대부터 차례로 지나갑니다. 1번 검사대가 불합격 도장을 찍으면 부품은 그 자리에서 라인 밖으로 빠지고, 뒤의 5번, 10번 검사대는 그 부품을 다시 보지 않습니다. 반대로 1번 검사대가 통과나 기록만으로 넘기면 부품은 계속 흘러가 다음 검사대의 판단을 받습니다. 그래서 우선순위는 단순한 정렬 번호가 아니라, 앞선 규칙의 결론이 뒤의 규칙을 무시하게 만드는 힘을 가집니다.

실무에서는 넓게 잡는 규칙을 뒤쪽 번호에, 예외적으로 확실히 막아야 하는 규칙을 앞쪽 번호에 두어 충돌을 설계로 정리합니다. 정리하면 WAF는 우선순위가 낮은 번호의 규칙부터 요청을 평가하고, 차단이나 허용처럼 결론을 내는 동작을 만나면 그 지점에서 평가를 멈춥니다.

3부. Web ACL과 규칙의 구조024

기본 동작(Default Action)

어떤 규칙에도 걸리지 않은 요청의 최종 처리

규칙을 아무리 촘촘히 짜도, 어떤 조건에도 해당하지 않는 요청은 반드시 남습니다. 이 요청을 어떻게 할지 정해 두지 않으면 WAF는 판단을 내리지 못하고, 서비스는 통과와 차단 사이에서 예측할 수 없는 상태가 됩니다. 그래서 모든 Web ACL에는 기본 동작(Default Action)이라는 마지막 한 칸이 있고, 여기에는 Allow(허용)나 Block(차단) 중 하나만 고릅니다.

아파트 정문 경비실 비유로 보면, 방문객이 여러 확인 절차를 거쳤는데 어느 절차에도 걸리지 않은 경우에 경비원이 마지막으로 내리는 결론과 같습니다. 절차마다 출입 금지 명단이 있고, 그 명단에 없는 사람은 경비원이 미리 정해 둔 규칙에 따라 문을 열어 주거나 돌려보냅니다. 기본 동작이 허용이면 명단에 없는 사람은 모두 들어오고, 기본 동작이 차단이면 명단에 있는 사람만 들어옵니다.

그래서 공개 서비스는 대개 허용을 기본으로 두고 위험한 요청만 규칙으로 걸러 내며, 사내 시스템처럼 닫힌 곳은 차단을 기본으로 두고 허가된 요청만 통과시킵니다. 정리하면 기본 동작은 규칙들이 모두 지나간 뒤 남은 요청에 적용되는 최종 판정이고, 이 한 칸의 선택이 서비스의 성격을 공개형과 폐쇄형으로 가릅니다.

문장(Statement)

규칙 안에서 매칭 조건을 표현하는 기본 단위

웹 서비스로 들어오는 요청을 걸러내는 규칙을 만들 때, 무엇을 막을지 아무렇게나 적으면 규칙이 지나치게 넓어져 정상 고객까지 차단하거나, 반대로 너무 좁아 공격을 그냥 통과시키게 됩니다. AWS WAF는 이런 판단을 문장(Statement)이라는 작은 단위로 나누어 적게 함으로써, 규칙의 조건을 명확하고 검증 가능한 형태로 유지합니다.

택배 물류센터의 입고 검수대를 떠올려 보면, 검수원은 이 상자를 반품할지를 통째로 결정하지 않고 송장 번호가 주문과 같은지, 박스가 찢어지지 않았는지, 무게가 기준을 넘는지를 차례로 확인합니다.

여기서 확인 항목 하나하나가 문장이고, 송장 번호 일치라는 문장은 요청의 특정 필드가 지정한 문자열과 같은지를 보는 식으로 표현됩니다. 이런 검수 항목을 모아 찢어졌거나 무게가 넘으면 반품처럼 판단을 묶은 것이 규칙이며, 문장은 그 재료로만 쓰이고 통과와 차단 같은 최종 결정은 규칙이 내립니다. 그래서 같은 문장을 여러 규칙에서 다시 쓰거나, 나중에 조건 하나만 바꿔 끼우는 식으로 손볼 수 있습니다.

정리하면 문장은 요청의 한 가지 속성을 검사하는 최소 판단 단위이고, 규칙은 그 문장들을 조합해 차단과 허용을 결정하는 상위 묶음입니다. 조건을 작게 쪼개 두면 무엇이 왜 걸렸는지 설명하기 쉬워지고, 잘못된 규칙 하나가 서비스 전체를 망가뜨리는 일도 줄어듭니다.

3부. Web ACL과 규칙의 구조026

AND·OR·NOT 논리 결합

여러 문장을 조합해 조건을 좁히거나 넓히는 방법

규칙을 만들다 보면 특정 주소에서 들어오는 요청이면서 로그인 시도일 때만 막고 싶은 것처럼 두 가지 이상을 동시에 따져야 하는 경우가 생깁니다. 조건을 하나만 쓰는 규칙으로는 이런 요구를 표현할 수 없어서, 정상 요청을 함께 막거나 반대로 원하는 요청을 놓치게 됩니다.

회사 건물 출입 데스크를 떠올려 보면, 경비원은 사원증이 있고 방문 목적이 배송일 때만 출입을 허용하는 식으로 두 조건을 동시에 요구합니다.

이것이 AND 결합으로, 두 문장이 모두 참이어야 규칙이 성립하므로 조건이 좁아지고 차단 범위가 줄어듭니다. 반대로 야간이거나 주말이면처럼 둘 중 하나만 맞아도 되는 경우는 OR 결합이라 조건이 넓어지고, 사원증이 없는 경우가 아니면처럼 결과를 뒤집는 NOT 결합은 예외 구간을 잘라낼 때 씁니다. 경비원이 조건을 겹쳐 볼 때 순서를 정해야 하는 것처럼, WAF에서도 결합을 묶는 순서에 따라 판단 결과가 달라질 수 있습니다.

정리하면 AND는 모든 조건의 충족, OR는 하나 이상의 충족, NOT은 조건의 반전을 뜻하며, 이 세 가지를 조합해 규칙 하나가 정교한 판단을 하도록 만듭니다. 다만 결합이 많아질수록 규칙을 읽기 어려워지므로, 어떤 조건이 실제로 걸렸는지 확인할 수 있게 단순하게 유지하는 것이 좋습니다.

3부. Web ACL과 규칙의 구조027

범위 축소 문장(Scope-down Statement)

규칙 그룹 안에서 특정 요청만 평가하도록 좁히는 방법

관리형 규칙 그룹(managed rule group)을 통째로 켜 두면 그 안의 수백 가지 검사가 내 서비스의 모든 요청에 적용되어, 정상 트래픽까지 막히거나 검사 비용이 불필요하게 늘어납니다. 범위 축소 문장(Scope-down Statement)은 규칙 그룹에 들어가기 전에 이런 요청만 검사하라고 범위를 미리 좁혀 주는 장치입니다.

공항 보안 검색대를 떠올려 보면, 액체류 검사 절차 자체는 정해져 있지만 그 절차를 모든 승객에게 똑같이 적용하지 않고 국제선 환승객처럼 대상이 되는 사람만 그 줄로 보냅니다.

여기서 검사 절차 전체가 규칙 그룹이고, 누구를 그 줄에 세울지 정하는 안내판이 범위 축소 문장입니다. 범위 축소 문장이 참인 요청만 규칙 그룹 안의 검사들이 평가하고, 거짓인 요청은 그 그룹을 건너뛰어 다음 규칙으로 넘어갑니다. 그래서 규칙 그룹 자체는 그대로 두고 앞단의 조건 한 줄만 바꿔 검사 대상을 조절할 수 있습니다.

정리하면 범위 축소 문장은 규칙 그룹 평가의 입구 조건으로, 그룹 내부 규칙을 수정하지 않고도 적용 대상을 한정하는 수단입니다. 대상을 좁혀 두면 오탐과 불필요한 검사를 줄이면서 필요한 요청은 그대로 보호할 수 있습니다.

3부. Web ACL과 규칙의 구조028

레이블(Label)

규칙이 요청에 붙이는 표식과 그 쓰임

요청 하나가 여러 규칙을 차례로 지나가는데, 앞선 규칙이 이미 이 요청은 봇으로 보인다고 판단했더라도 그 결론이 뒤의 규칙에 전달되지 않으면 같은 검사를 처음부터 다시 해야 합니다. 레이블(Label)은 규칙이 요청에 붙이는 표식으로, 이런 판단 결과를 요청에 실어 다음 규칙이 읽을 수 있게 합니다.

택배 분류창고를 떠올려 보면, 첫 검수대에서 이상이 발견된 상자에는 파손 의심 스티커를 붙여 두고 뒤쪽 작업대에서는 내용을 다시 뜯어 보지 않고 스티커만 보고 처리합니다.

레이블이 바로 그 스티커이고, 이름은 규칙을 만들 때 직접 정하며 요청이 흐르는 동안에만 유지되는 임시 표식입니다. 규칙이 매칭되면 레이블이 붙고, 붙지 않은 요청에는 아무 영향이 없으며, 같은 요청에 여러 레이블이 동시에 붙을 수도 있습니다. 스티커를 붙이는 것만으로 상자를 반품하지 않듯, 레이블은 차단이나 허용을 결정하지 않고 뒤 규칙이 참고할 근거만 남깁니다.

정리하면 레이블은 규칙이 요청에 남기는 이름표로, 앞선 판단의 결과를 뒤 규칙에 전달하는 가벼운 신호입니다. 덕분에 같은 검사를 반복하지 않고도 규칙들을 역할별로 나누어 조립할 수 있습니다.

레이블 매칭 문장(Label Match)

앞선 규칙이 붙인 레이블을 조건으로 재사용하는 방법

앞선 규칙이 요청에 봇 의심 같은 레이블을 붙여 두어도, 뒤의 규칙이 그 표식을 읽지 않으면 아무 일도 일어나지 않습니다. 레이블 매칭 문장(Label Match Statement)은 이렇게 붙은 레이블을 조건으로 삼아, 표식이 있는 요청만 골라내는 문장입니다.

앞서 본 분류창고에서 파손 의심 스티커가 붙은 상자만 골라 별도 라인으로 보내는 작업대를 생각하면 이해가 쉽습니다.

작업대 직원은 상자 내용을 다시 확인하지 않고 스티커의 문구를 스캔해 해당 상자만 집어내는데, 이것이 레이블 매칭 문장의 동작과 같습니다. 조건에는 레이블 이름을 적고, 이름이 정확히 같은지 또는 정해진 접두사로 시작하는지를 기준으로 매칭 여부를 정합니다. 스티커가 없으면 그 상자가 그 라인을 지나가지 않듯, 레이블이 없는 요청은 이 문장에 걸리지 않아 다음 규칙으로 넘어갑니다.

정리하면 레이블 매칭 문장은 앞선 규칙이 붙인 레이블을 조건으로 재사용해, 판단을 여러 규칙에 걸쳐 이어 붙이는 연결부입니다. 이 문장 덕분에 복잡한 검사 흐름을 한 규칙에 몰아넣지 않고 단계별로 나누어 관리할 수 있습니다.

3부. Web ACL과 규칙의 구조030

사용자 지정 응답(Custom Response)

차단할 때 돌려줄 상태 코드와 본문을 정하는 방법

공격으로 판단해 요청을 차단할 때 서버가 아무 설명 없는 기본 오류 화면만 돌려주면, 정상 사용자는 무엇이 잘못됐는지 알 수 없어 같은 동작을 반복하다 또 막힙니다. 사용자 지정 응답(Custom Response)은 차단하는 순간에 돌려줄 상태 코드와 본문을 관리자가 직접 정하게 하는 기능입니다.

건물 주차장 입구를 떠올려 보면, 등록되지 않은 차량에 차단기가 아무 표시 없이 막아서기만 하면 운전자는 고장인지 규정인지 알 수 없습니다.

대신 방문 차량은 안내 데스크에 등록하세요 같은 안내판을 함께 세워 두면 같은 차단이라도 이유와 다음 행동을 알려 줄 수 있는데, 이것이 사용자 지정 응답입니다. 응답 코드는 403처럼 차단을 뜻하는 값으로 두고, 본문에는 짧은 안내 문구나 JSON을 담으며, 응답 헤더도 함께 지정할 수 있습니다. 안내판 문구가 정해져 있어도 차단 자체가 사라지지는 않듯, 사용자 지정 응답은 거부 결정을 바꾸지 않고 그 결정을 알리는 방식만 바꿉니다.

정리하면 사용자 지정 응답은 차단 시 반환할 상태 코드와 헤더, 본문을 규칙 단위로 정하는 설정입니다. 응답을 미리 정리해 두면 사용자는 이유를 이해하고 개발자는 문의 대응과 로그 분석을 훨씬 수월하게 할 수 있습니다.

4부. 매칭 조건과 요청 검사031

IP 집합 매칭(IP Set)

허용·차단할 IP 대역 목록을 만들어 쓰는 방법

회사 서비스에 하루 수천 건의 의심스러운 접속이 들어오는데, 막아야 할 주소가 수십 개에서 수백 개로 늘어나면 규칙 하나하나를 손으로 고치는 일은 금방 한계에 부딪힙니다. 이런 곤란을 줄이려고 AWS WAF(웹 애플리케이션 방화벽)에는 허용하거나 차단할 IP 주소 대역을 목록으로 묶어 두고 한 번에 참조하는 IP 집합(IP Set) 기능이 있습니다.

아파트 경비실에 출입 금지 명단이 있다고 생각해 보겠습니다. 명단을 문 앞 안내문에 적어 두면 주민이 바뀔 때마다 붙은 종이를 모두 뜯어고쳐야 하지만, 경비실 장부 한 권에 이름을 적고 현관 경비에게 "장부에 없으면 들여보내지 말라"는 지시만 내리면 됩니다.

IP 집합도 마찬가지로 주소들을 한 장부에 모아 두고, 규칙에서는 그 장부의 이름만 가리킵니다. 그래서 차단할 주소가 늘거나 줄어도 규칙 자체는 건드리지 않고 장부의 목록만 고치면 됩니다.

결국 IP 집합은 여러 IP 주소나 대역(CIDR)을 하나의 이름으로 관리해 규칙에서 반복해서 재사용하게 해 주는 자원이고, 덕분에 대상 주소가 바뀌어도 규칙을 다시 쓰지 않고 판정 대상을 통째로 갈아 끼울 수 있습니다.

← 이전사용자 지정 응답(Custom Response)다음 →지리적 매칭(Geo Match)

4부. 매칭 조건과 요청 검사032

지리적 매칭(Geo Match)

요청이 들어온 국가를 기준으로 판정하는 방법

해외에서만 반복해서 들어오는 공격이 있는데 로그를 하나하나 뒤져 어느 나라에서 접속했는지 확인하며 대응하려면 시간이 너무 오래 걸립니다. 그래서 요청이 들어온 국가를 기준으로 허용과 차단을 정하는 지리적 매칭(Geo Match)이 쓰입니다.

해외 택배를 받는 상황을 떠올려 보겠습니다. 택배 상자에는 어느 나라에서 출발했는지 알려 주는 국가 표시가 붙어 있어서, 받는 쪽은 상자를 열어 보지 않고도 그 표시만 보고 특정 국가에서 온 소포는 통관 단계에서 돌려보낼 수 있습니다.

지리적 매칭도 요청을 보낸 쪽의 국가 정보를 기준으로 판정하는데, 이 국가 정보는 요청자의 IP 주소를 별도의 데이터베이스에 대조해 추정한 값입니다. 그래서 정확한 위치라기보다 대략적인 출처 구분으로 이해해야 하며, 같은 나라 안에서도 판정이 어긋날 수 있다는 점을 감안해야 합니다.

결국 지리적 매칭은 IP 주소에서 추정한 국가 코드를 조건으로 삼아 규칙을 적용하는 방식이고, 주소 목록을 일일이 관리하지 않고도 특정 국가 전체를 한꺼번에 다루게 해 줍니다.

← 이전IP 집합 매칭(IP Set)다음 →헤더 매칭(Header Match)

4부. 매칭 조건과 요청 검사033

헤더 매칭(Header Match)

특정 HTTP 헤더 값으로 요청을 구분하는 방법

같은 주소로 들어온 요청이라도 어떤 앱이 보냈는지, 어떤 형식의 데이터를 원하는지에 따라 처리를 달리해야 하는데, 모든 요청을 똑같은 규칙으로 판정하면 정상 사용자까지 막히기 쉽습니다. 헤더 매칭(Header Match)은 요청에 딸려 오는 HTTP 헤더의 값을 보고 이런 요청을 구분하는 방법입니다.

택배 상자 겉면에 붙은 송장을 떠올려 보겠습니다. 송장에는 받는 사람과 주소뿐 아니라 "취급 주의", "냉장", "지정일 배송" 같은 칸이 따로 적혀 있어서, 물류센터는 상자를 열어 보지 않고도 그 표기만 보고 분류를 정합니다. HTTP 헤더도 요청에 함께 붙는 이런 표기 칸과 같아서, 브라우저 종류나 사용 언어, 데이터 형식 같은 정보가 이름과 값의 쌍으로 담겨 있습니다. 헤더 매칭은 이 이름과 값을 조건으로 삼아, 해당 표기가 붙은 요청만 골라 허용하거나 차단합니다.

결국 헤더 매칭은 HTTP 헤더의 이름과 값을 검사 조건으로 쓰는 기능이고, 요청의 겉모습에 드러난 단서만으로도 성격이 다른 트래픽을 골라낼 수 있게 해 줍니다.

← 이전지리적 매칭(Geo Match)다음 →본문 매칭(Body Match)

4부. 매칭 조건과 요청 검사034

본문 매칭(Body Match)

요청 본문 안의 문자열을 찾아 검사하는 방법

게시판 글쓰기나 로그인 요청처럼 데이터가 본문에 담겨 오는 경우에는 겉에 보이는 주소만 보고 그 안에 무엇이 들어 있는지 알 수 없습니다. 본문 매칭(Body Match)은 요청 본문 안의 문자열을 직접 찾아보고 판정하는 기능입니다.

택배 상자를 받았을 때 겉면만 확인하고 내용물은 열어 보지 않는 경우가 많지만, 위험한 물품이 들었는지 확인해야 하는 상황이라면 상자를 열어 안을 살펴야 합니다. 본문 매칭은 이처럼 요청의 겉포장에 해당하는 주소나 헤더가 아니라, 상자 안의 내용물에 해당하는 본문을 펼쳐 보고 특정 문자열이 들어 있는지 확인합니다.

다만 본문은 크기가 클 수 있어서 검사 범위를 앞부분 몇 킬로바이트로 제한하는 식으로 동작하는 경우가 많고, 그 범위를 넘는 뒷부분은 검사되지 않을 수 있습니다. 그래서 큰 파일 업로드처럼 본문이 긴 요청에서는 모든 내용이 검사된다고 단정하기 어렵습니다.

결국 본문 매칭은 요청 본문에서 지정한 문자열이나 패턴을 찾아 조건으로 쓰는 기능이고, 주소나 헤더에는 드러나지 않는 위험한 입력을 걸러 내는 데 목적이 있습니다.

← 이전헤더 매칭(Header Match)다음 →URI 경로 매칭(URI Path)

4부. 매칭 조건과 요청 검사035

URI 경로 매칭(URI Path)

요청 경로를 기준으로 규칙을 나누는 방법

웹사이트에는 관리자 화면, 결제 화면, 일반 게시판처럼 성격이 전혀 다른 주소가 한 도메인 안에 섞여 있는데, 모든 경로에 같은 규칙을 적용하면 관리자 화면은 너무 느슨해지고 게시판은 너무 빡빡해집니다. URI 경로 매칭(URI Path)은 요청이 어떤 경로로 들어왔는지를 기준으로 규칙을 나누는 방법입니다.

큰 건물에서 층마다 출입 정책이 다른 상황을 떠올려 보겠습니다. 1층 로비는 누구나 들어올 수 있지만 서버실이 있는 지하와 임원실이 있는 최상층은 별도 출입증이 필요하고, 안내데스크는 방문객이 말한 층수를 보고 어느 문으로 보낼지 정합니다. URI 경로 매칭도 이 안내데스크처럼 요청 주소에서 도메인 뒤에 붙는 경로 부분을 읽고, 그 경로가 어느 구역에 속하는지에 따라 서로 다른 규칙을 적용합니다. 예를 들어 관리자 구역 경로에는 더 엄격한 검사를, 공개 게시판 경로에는 비교적 느슨한 검사를 붙이는 식입니다.

결국 URI 경로 매칭은 요청 URL의 경로를 조건으로 삼아 규칙을 구역별로 나누는 기능이고, 같은 서비스 안에서도 민감한 화면과 공개 화면을 다른 정책으로 보호하게 해 줍니다.

← 이전본문 매칭(Body Match)다음 →쿼리 문자열 매칭(Query String)

4부. 매칭 조건과 요청 검사036

쿼리 문자열 매칭(Query String)

URL 뒤 파라미터 값을 검사하는 방법

검색 결과나 상품 목록처럼 주소 뒤에 물음표와 함께 조건이 잔뜩 붙어 오는 요청이 있는데, 그 조건 값에 공격 문자열이 숨어 들어오면 겉보기에는 평범한 주소라도 위험할 수 있습니다. 쿼리 문자열 매칭(Query String)은 URL 뒤에 붙는 파라미터 값을 검사하는 방법입니다.

식당에서 주문서를 받았을 때 메뉴 이름만 보고 주방에 넘기지 않고, "덜 맵게", "양파 빼기" 같은 요청 사항 칸까지 확인하는 상황을 떠올려 보겠습니다. 쿼리 문자열은 이 요청 사항 칸과 같아서, 물음표 뒤에 이름과 값의 쌍으로 늘어서는 파라미터들이 여기에 해당합니다.

쿼리 문자열 매칭은 이 값들을 조건으로 삼아 특정 문자열이 들어오면 차단하거나, 정해 둔 허용 목록에 있는 값만 통과시키는 식으로 동작합니다. 이렇게 하면 경로는 멀쩡한데 파라미터만 조작해 들어오는 요청을 따로 걸러 낼 수 있습니다.

결국 쿼리 문자열 매칭은 URL의 물음표 뒤에 오는 파라미터 이름과 값을 검사 조건으로 쓰는 기능이고, 경로만 보아서는 알 수 없는 조작된 입력을 잡아내는 역할을 합니다.

← 이전URI 경로 매칭(URI Path)다음 →HTTP 메서드 매칭

4부. 매칭 조건과 요청 검사037

HTTP 메서드 매칭

GET·POST 같은 메서드로 요청을 구분하는 방법

웹 서비스에는 조회만 허용하고 수정은 막아야 하는 화면이 있는데, 주소만 보고 요청을 판단하면 사용자가 삭제를 눌러 보내는 요청과 목록을 보는 요청이 같은 주소로 들어와 구분되지 않습니다. 그래서 요청이 어떤 종류의 동작을 원하는지 알려 주는 표시를 조건으로 삼아 걸러 내는 기능이 필요하고, 이것이 HTTP 메서드 매칭(HTTP method matching)입니다. 아파트 정문 경비실에 방문객이 오면 경비원은 이름표만 보지 않고 용건이 방문인지 택배 배달인지 이사인지부터 확인합니다. 이때 용건을 적어 내는 표식이 HTTP 메서드이고, GET은 보여 달라는 뜻, POST는 새로 만들어 달라는 뜻, DELETE는 지워 달라는 뜻을 담습니다.

규칙에 GET 요청만 통과시킨다고 정하면 경비원은 표식이 GET인 사람만 들여보내고 나머지는 문 앞에서 돌려보냅니다. 같은 주소라도 표식에 따라 통과와 차단이 갈리므로, 관리자는 화면별로 허용할 동작을 하나씩 지정해 둘 수 있습니다. 정리하면 HTTP 메서드 매칭은 요청 줄에 적힌 동작 표식, 즉 GET·POST·PUT·DELETE 같은 메서드 값을 조건으로 삼아 허용 여부를 가르는 규칙입니다. 주소가 같아도 의도가 다르면 다른 요청으로 취급한다는 점이 핵심입니다.

← 이전쿼리 문자열 매칭(Query String)다음 →단일 헤더와 다중 헤더 매칭

4부. 매칭 조건과 요청 검사038

단일 헤더와 다중 헤더 매칭

헤더 조건을 하나만 볼지 조합해서 볼지의 차이

공격자는 차단을 피하려고 같은 요청에 헤더를 조금씩 바꿔 가며 수십 번 보내는 경우가 많습니다. 헤더 하나만 보고 판단하면 이런 변형을 놓치기 때문에 여러 헤더를 함께 조건으로 묶는 방식이 필요하고, 이것이 단일 헤더 매칭(single header matching)과 다중 헤더 매칭(multiple header matching)의 차이입니다. 택배 회사에서 물건을 받을 때를 생각하면, 단일 헤더 매칭은 송장에 적힌 받는 사람 이름 하나만 확인하는 것과 같습니다. 이름이 맞으면 통과시키므로 규칙이 단순하고 처리도 빠르지만, 이름만 같으면 주소가 달라도 그냥 지나갑니다.

다중 헤더 매칭은 받는 사람과 주소, 연락처까지 여러 항목을 동시에 대조하는 방식으로, 모든 조건이 맞아야 통과시키므로 훨씬 정교합니다. 대신 조건이 늘어날수록 확인할 항목이 많아져 규칙이 복잡해지고, 어떤 헤더를 쓸지 미리 정확히 파악해 두어야 합니다. 정리하면 단일 헤더 매칭은 헤더 한 개의 값으로 판단하고, 다중 헤더 매칭은 둘 이상의 헤더 값을 모두 만족해야 하는 조건으로 묶어 판단하는 규칙입니다. 정확도가 필요한 구간에는 다중 헤더를, 단순한 차단에는 단일 헤더를 쓰는 식으로 나눕니다.

← 이전HTTP 메서드 매칭다음 →크기 제한 규칙(Size Constraint)

4부. 매칭 조건과 요청 검사039

크기 제한 규칙(Size Constraint)

본문·헤더가 일정 크기를 넘으면 차단하는 방법

로그인 화면에 아주 긴 글을 한꺼번에 밀어 넣거나 본문을 수십 메가바이트로 부풀려 보내면, 서버는 그 내용을 읽고 해석하는 데 자원을 쏟다가 정상 사용자에게 응답하지 못하게 됩니다. 이런 과대한 요청을 애초에 들이지 않도록 크기를 기준으로 잘라 내는 장치가 크기 제한 규칙(Size Constraint)입니다. 우체국 창구에서 소포를 접수할 때 무게와 크기를 재서 기준을 넘으면 받지 않는 것과 같습니다. 창구 직원은 내용물을 하나하나 뜯어보지 않고 규격 초과 여부만 확인해 바로 돌려보내므로, 뒤에 줄 선 사람들의 시간도 지킬 수 있습니다.

크기 제한 규칙도 본문 전체 길이, 헤더 한 줄의 길이, 쿼리 문자열 길이처럼 미리 정한 항목의 바이트 수를 재어 기준을 넘으면 요청을 차단합니다. 이때 기준값은 서비스가 정상적으로 받는 최대치보다 조금 넉넉하게 잡아 두어야 정상 요청까지 막는 일이 없습니다. 정리하면 크기 제한 규칙은 본문·헤더·쿼리 문자열의 크기를 재어 정해진 한도를 넘는 요청을 검사 전에 차단하는 규칙입니다. 내용을 들여다보기 전에 규모로 먼저 거르는 가장 값싼 방어선입니다.

4부. 매칭 조건과 요청 검사040

본문 검사 한도와 JSON 처리

어디까지 검사하는지와 JSON 본문이 해석되는 방식

요청 본문이 아무리 커도 앞부분 몇 킬로바이트만 검사한다면, 뒤쪽에 공격 문구를 숨겨 넣은 요청은 그대로 통과하게 됩니다. 반대로 본문 전체를 끝까지 읽으면 처리 비용이 커지므로, 어디까지 검사할지 정하는 한도와 본문 구조를 해석하는 방식이 함께 문제가 되며 이것이 본문 검사 한도(body inspection limit)와 JSON 처리입니다. 공항 검색대에서 가방을 검사할 때 정해진 크기까지만 화면에 올려 보는 것과 비슷합니다. 검색대 길이를 넘는 가방은 화면에 다 담기지 않으므로, 규정상 그 지점까지만 확인하고 나머지는 별도 절차로 넘깁니다.

본문 검사 한도도 같은 원리로, 요청 본문에서 읽어 해석할 최대 바이트 수를 정해 두고 그 지점까지만 검사합니다. 본문이 JSON(JavaScript Object Notation) 형식이면 요청을 단순한 글자 덩어리가 아니라 키와 값으로 이루어진 구조로 풀어서, 특정 필드의 값만 골라 검사할 수 있습니다. 정리하면 본문 검사 한도는 검사 대상 본문의 최대 길이를 정한 값이고, JSON 처리는 그 본문을 구조로 해석해 필드 단위로 검사할 수 있게 하는 기능입니다. 한도를 넘는 부분은 검사되지 않는다는 사실을 전제로 규칙을 설계해야 합니다.

남이 만든 규칙 묶음을 그대로 가져다 쓰는 개념

직접 규칙을 만들면 흔한 공격 패턴을 하나하나 조사해 조건을 적어 넣어야 하고, 새 취약점이 나올 때마다 손보아야 합니다. 이 반복 작업을 줄이려고 전문가 집단이 미리 만들어 둔 규칙 묶음을 그대로 가져다 쓰는 제도가 관리형 규칙 그룹(Managed Rule Group)입니다. 아파트에서 세대마다 청소 도구를 사서 직접 관리하는 대신, 관리사무소가 계약한 전문 업체가 공용 구역을 정기적으로 점검하는 것과 같습니다. 업체는 새로운 오염 유형이 나타나면 자기 매뉴얼을 갱신하므로 입주민은 따로 알아볼 필요가 없습니다.

관리형 규칙 그룹도 마찬가지로, 제공자가 규칙 내용과 갱신을 맡고 사용자는 그룹을 규칙 집합에 붙이기만 하면 됩니다. 다만 그룹 안에 어떤 규칙이 들어 있는지, 어떤 요청을 차단으로 볼지, 예외를 어디에 둘지는 사용자가 확인하고 조정해야 합니다. 정리하면 관리형 규칙 그룹은 규칙 작성과 최신화를 제공자에게 맡기고 사용자는 그 묶음을 골라 적용하는 방식입니다. 편리한 만큼 그룹의 성격과 예외 설정을 이해하고 쓰는 것이 중요합니다.

AWS 관리형 규칙

AWS가 직접 운영하는 기본 규칙 그룹의 종류와 성격

관리형 규칙 그룹을 쓰기로 했더라도 어떤 그룹을 골라야 하는지 모르면 적용 자체가 어렵습니다. 그래서 AWS는 용도가 다른 여러 기본 규칙 그룹을 직접 만들어 운영하고 있으며, 이것이 AWS 관리형 규칙(AWS Managed Rules)입니다. 아파트 경비 업무를 예로 들면, 외부인 출입을 막는 일과 주차 위반을 단속하는 일과 소방 설비를 점검하는 일에는 서로 다른 기술이 필요합니다. AWS 관리형 규칙도 이처럼 목적별로 나뉘어, 흔한 웹 공격 패턴을 모은 기본 규칙 집합과 특정 서버 소프트웨어의 알려진 취약점을 겨냥한 규칙 집합, 악성으로 알려진 IP 주소 목록을 다루는 규칙 집합 같은 형태로 제공됩니다.

사용자는 자기 서비스가 쓰는 기술과 노출된 위험에 맞는 그룹을 골라 붙이고, 필요하면 개별 규칙을 빼거나 예외로 처리합니다. AWS가 내용을 갱신하므로 새로 알려진 공격 패턴은 사용자가 손대지 않아도 그룹에 반영되는 경우가 많습니다. 정리하면 AWS 관리형 규칙은 AWS가 직접 작성하고 갱신하는 규칙 그룹의 모음으로, 공격 유형과 대상 기술에 따라 나뉘어 제공됩니다. 어떤 그룹이 무엇을 막는지 확인한 뒤 서비스에 맞는 것만 골라 적용하는 것이 핵심입니다.

파트너 관리형 규칙 그룹

마켓플레이스에서 서드파티 규칙 그룹을 고르는 기준

웹 방화벽을 직접 운영하는 팀은 특정 공격 유형의 규칙을 처음부터 손수 만들다가, 새로운 공격 패턴이 쏟아질 때마다 대응이 늦어지는 일을 겪습니다. 이런 부담을 줄이려고 AWS는 보안 전문 업체가 만든 규칙 묶음을 마켓플레이스에서 구독해 쓰는 파트너 관리형 규칙 그룹(Partner Managed Rule Group) 방식을 제공합니다.

이것은 아파트 관리 사무소가 경비 업체를 선정하는 일과 비슷합니다. 관리 사무소는 모든 순찰을 직접 하지 않고, 실적과 담당 범위가 검증된 업체를 골라 계약하고, 그 업체가 순찰 중 발견한 문제를 보고하게 합니다. 규칙 그룹도 마찬가지로 어떤 위협을 주로 막는지와 오탐 경향, 갱신 주기, 지원 체계를 견주어 고르고, 고른 그룹을 웹 ACL(접근 제어 목록, 어떤 요청을 허용하고 막을지 정한 규칙의 모음)에 붙이면 그 업체가 갱신한 규칙이 자동으로 적용됩니다.

다만 규칙의 내용을 우리가 들여다볼 수 없고 동작만 조정할 수 있는 경우가 많으므로, 도입 전에 계수(Count) 모드로 먼저 흘려보내 오탐이 얼마나 생기는지 확인하는 편이 안전합니다. 정리하면 파트너 관리형 규칙 그룹은 검증된 외부 공급자의 규칙 묶음을 구독해 우리 웹 ACL에 연결하는 것이며, 고르는 기준은 방어 범위와 오탐 위험, 갱신 속도, 지원과 비용입니다.

이것은 스마트폰 앱 업데이트와 비슷합니다. 앱은 새 기능과 버그 수정을 담아 버전을 올리고, 자동 업데이트를 켜 두면 어느새 화면 구성이 달라져 있습니다. 규칙 그룹도 공급자가 새 공격 패턴을 반영해 새 버전을 내놓고, 우리가 그 버전을 웹 ACL에 지정하면 판정 기준이 그 시점부터 달라집니다.

관리형 규칙 그룹은 보통 기본 버전으로 자동 반영되는 반면, 파트너 규칙 그룹처럼 버전을 직접 골라 고정하는 경우에는 우리가 바꾸지 않는 한 그대로 유지되므로, 바꿀 때는 먼저 계수 모드로 관찰한 뒤 차단으로 전환하는 것이 좋습니다. 정리하면 버전은 규칙 그룹의 판정 기준이 담긴 묶음의 번호이고, 업데이트는 그 기준이 바뀌는 사건이므로, 어떤 버전을 쓸지와 언제 올릴지를 운영 절차로 정해 두어야 합니다.

5부. 관리형 규칙 그룹045

WCU(웹 ACL 용량 단위)

규칙이 차지하는 용량을 세는 단위와 한도

규칙을 이것저것 붙이다 보면 어느 순간 웹 ACL 저장이나 수정이 거부되면서 한도 초과라는 메시지를 만나게 됩니다. 이때 기준이 되는 것이 WCU(웹 ACL 용량 단위, Web ACL Capacity Unit)로, 규칙과 규칙 그룹이 차지하는 처리 용량을 세는 단위입니다.

이것은 창고의 부피 제한과 비슷합니다. 짐마다 크기가 달라서 무게가 아니라 부피로 자리를 계산하고, 창고에 넣을 수 있는 총 부피가 정해져 있으면 큰 짐 몇 개로도 금방 꽉 찹니다. 마찬가지로 규칙마다 요구하는 WCU가 다르고, 문자열 일치처럼 단순한 규칙은 적게, 정규식이나 IP 집합 대조처럼 복잡한 규칙은 많게 계산되며, 웹 ACL 하나에 담을 수 있는 총량에도 한도가 있습니다.

그래서 규칙을 추가할 때는 개수가 아니라 WCU를 확인하고, 같은 목적이라면 더 적은 용량을 쓰는 방식으로 묶는 것이 좋습니다. 정리하면 WCU는 웹 ACL이 감당해야 하는 규칙의 처리 부피를 재는 단위이며, 한도에 여유를 남겨 두는 것이 운영의 기본입니다.

5부. 관리형 규칙 그룹046

규칙 동작 재정의(Action Override)

관리형 규칙의 동작을 Count 등으로 바꾸는 방법

관리형 규칙 그룹을 그대로 켜 두면, 공급자가 차단으로 정해 둔 규칙이 우리 서비스에서는 정상 요청까지 막아 버리는 일이 생깁니다. 이런 때 규칙 자체를 끄지 않고 판정의 결과만 바꾸는 기능이 규칙 동작 재정의(Action Override)입니다.

이것은 아파트 경비실의 지시 체계와 비슷합니다. 경비 업체가 야간에 이 사람은 출입 금지라는 지침을 내려도, 관리 사무소가 일단 명단에 적기만 하고 실제로 막지는 말라고 지시를 덮어쓸 수 있습니다. 규칙 동작 재정의도 특정 규칙이나 그룹 전체에 대해 차단(Block)을 계수(Count)로, 또는 계수를 차단으로 바꾸는 식으로 결과만 덮어쓰고, 규칙의 탐지 조건은 그대로 둡니다.

이렇게 하면 무엇이 걸리는지 기록은 남기면서 서비스 영향은 없앨 수 있고, 충분히 확인한 뒤 원래 동작으로 되돌리면 됩니다. 정리하면 동작 재정의는 규칙의 탐지 내용은 유지한 채 판정 결과만 우리 환경에 맞게 바꾸는 안전장치입니다.

관리형 규칙 도입 순서

바로 차단하지 않고 Count부터 시작하는 이유와 절차

새 관리형 규칙 그룹을 바로 차단 모드로 켜면, 그 규칙이 예상하지 못한 정상 트래픽까지 막아 서비스 장애로 이어지는 일이 흔합니다. 그래서 도입은 차단이 아니라 계수(Count)부터 시작하는 순서로 진행합니다.

이것은 새로 온 경비원을 바로 정문에 세우지 않는 것과 비슷합니다. 먼저 안내 데스크에서 이 사람이었다면 막았을 것이라고 표시만 하게 하고, 그 표시를 며칠 모아 보며 오탐이 어떤 요청에서 나오는지 확인합니다. 오탐이 줄어들면 예외 처리로 걸러 낼 대상을 정리하고, 그다음에야 차단으로 바꿉니다.

이때 CloudWatch 지표나 로그로 계수된 요청의 비율과 출처를 보면서 단계마다 되돌릴 수 있는 상태를 유지하는 것이 핵심입니다. 정리하면 계수로 관찰하고, 예외를 정리하고, 차단으로 전환하는 세 단계가 관리형 규칙 도입의 기본 순서입니다.

5부. 관리형 규칙 그룹048

봇 제어 규칙 그룹(Bot Control)

자동화 트래픽을 분류하고 처리하는 관리형 규칙

티켓을 사재기하는 자동 프로그램이나, 로그인을 무차별로 시도하는 스크립트가 정상 사용자와 똑같은 요청 모양으로 들어오면 단순한 차단 규칙으로는 걸러 내기 어렵습니다. 이런 자동화 트래픽을 분류하고 처리하도록 만든 관리형 규칙 그룹이 봇 제어(Bot Control)입니다.

이것은 놀이공원 입구의 매표 방식과 비슷합니다. 매표소는 줄을 선 사람을 무조건 같은 것으로 보지 않고, 손에 든 표와 예약 정보, 줄서는 속도 같은 단서로 일반 관람객과 되팔이를 나눕니다. 봇 제어도 요청의 서명이나 브라우저 흔적, 접속 빈도 같은 단서로 트래픽을 사람과 자동화로 분류하고, 검색 엔진처럼 허용할 봇은 통과시키고 의심스러운 것은 차단하거나 검증 퍼즐로 돌립니다.

분류 결과는 라벨로 남아 다른 규칙에서 함께 쓸 수 있고, 어떤 봇을 허용할지는 우리가 직접 지정해야 합니다. 정리하면 봇 제어는 트래픽을 사람과 자동화로 나누고 그 결과에 따라 통과와 차단, 검증을 결정하는 관리형 규칙 그룹입니다.

5부. 관리형 규칙 그룹049

계정 탈취 방지 규칙 그룹(ATP)

로그인 시도의 이상 행동을 탐지하는 규칙 그룹

아이디와 비밀번호 조합을 자동으로 수천 번 넣어보는 공격이 성공하면, 정상 사용자의 계정이 그대로 탈취되어 결제와 개인정보 조회까지 이어집니다. AWS WAF의 계정 탈취 방지 규칙 그룹(ATP, Account Takeover Prevention)은 이런 로그인 시도의 이상 행동을 탐지하도록 미리 만들어진 관리형 규칙 묶음입니다.

아파트 경비실에 비유하면, 경비원은 모든 세대의 초인종을 차례로 누르는 사람과 같은 집 문을 몇 분 안에 수십 번 두드리는 사람을 정상 방문객과 구분해서 봅니다. ATP도 마찬가지로 로그인 요청만 따로 모아 관찰하면서, 짧은 시간에 실패가 반복되는지, 여러 계정 이름을 훑고 있는지, 사람이 직접 입력한 것과 다른 자동화의 흔적이 있는지를 규칙별로 확인합니다.

경비원이 다른 동까지 돌며 문을 열어보는 사람을 기록으로 남기듯, ATP는 그런 요청에 표시를 붙여 이후 규칙이 차단이나 추가 인증을 결정하게 합니다. 이 규칙 그룹은 제공자가 계속 갱신하므로 운영자는 로그인 경로에 연결하고, 오탐이 나는 부분만 개별 규칙 설정으로 조정하면 됩니다.

정리하면 ATP는 로그인 요청의 빈도와 패턴을 관리형 규칙으로 감시해 계정 탈취 시도를 조기에 걸러내는 규칙 그룹입니다. 다만 이것만으로 모든 공격이 막히지는 않으므로, 비밀번호 정책이나 다중 인증(MFA) 같은 인증 계층의 보호와 함께 써야 효과가 있습니다.

알려진 악성 입력 규칙 그룹

공격에 자주 쓰이는 입력 패턴을 막는 규칙 그룹

오래된 플러그인이나 공개된 취약점을 노리는 요청은 겉보기에 평범한 파라미터처럼 보이지만, 실제로는 서버 명령을 실행시키거나 파일을 읽어내려는 입력인 경우가 많습니다. AWS WAF의 알려진 악성 입력 규칙 그룹(Known Bad Inputs)은 이렇게 공격에 자주 쓰이는 입력 패턴을 미리 목록으로 만들어 막는 관리형 규칙 묶음입니다.

건물 출입구의 검색대에 반입 금지 물품 목록이 붙어 있는 모습을 떠올리면 이해가 쉽습니다. 검색대 직원은 가방을 하나하나 뜯어보지 않고, 목록에 적힌 모양과 일치하는 물건이 있는지만 확인해 통과 여부를 정합니다.

목록은 보안팀이 새로운 위험한 물건을 발견할 때마다 갱신되고, 현장 직원은 목록이 바뀌면 자동으로 새 기준을 따릅니다. 이 규칙 그룹도 같은 방식으로 요청의 헤더와 본문, 쿼리 문자열 안에서 알려진 공격 문자열의 흔적을 찾고, 발견되면 해당 요청을 차단합니다.

즉 알려진 악성 입력 규칙 그룹은 취약점 공격에 쓰이는 대표적인 입력 패턴을 목록 기반으로 걸러내는 안전장치입니다. 목록에 없는 새로운 형태의 공격은 잡지 못하므로, 다른 규칙 그룹과 함께 여러 겹으로 배치하는 것이 일반적입니다.

속도 기반 규칙(Rate-based Rule)

일정 시간에 요청이 몰리면 자동으로 차단하는 방법

정상적인 사용자는 하루에 몇 번만 접속하는데, 같은 주소에서 1초에 수백 건의 요청이 들어오기 시작하면 그것은 사람의 사용이 아니라 자동화된 공격일 가능성이 큽니다. AWS WAF의 속도 기반 규칙(Rate-based Rule)은 일정 시간 동안 같은 기준으로 들어온 요청 수를 세어, 정해 둔 한도를 넘으면 자동으로 차단하는 기능입니다.

아파트 정문 경비실에서 방문증을 발급하는 상황이 좋은 비유입니다. 경비원은 방문객이 누구인지 일일이 심사하는 대신, 한 사람이 5분 안에 방문증을 몇 장이나 요구하는지를 세어 봅니다.

평소라면 한두 장이면 충분한데 수십 장을 요구한다면, 그 사람이 다른 세대의 문을 열어보려 한다고 판단해 발급을 멈추는 것입니다. 속도 기반 규칙도 같은 방식으로, 정해 둔 기간 동안 한도를 넘긴 요청에 대해 차단이나 CAPTCHA, 사용자 정의 응답 같은 조치를 적용합니다.

정리하면 속도 기반 규칙은 요청의 내용보다 발생 빈도를 기준으로 삼아, 짧은 시간에 몰리는 자동화 트래픽을 자동으로 억제하는 장치입니다. 한도와 집계 기간은 서비스의 정상 트래픽 규모를 보고 정해야 하며, 너무 낮게 잡으면 정상 사용자까지 함께 막힐 수 있습니다.

속도 기반 규칙의 집계 키

IP·헤더·쿠키 중 무엇을 기준으로 셀지 정하는 방법

속도 기반 규칙을 켜 두어도 무엇을 하나로 묶어서 셀지를 정하지 않으면, 서로 다른 사용자의 요청이 한 덩어리로 합쳐져 엉뚱한 차단이 생깁니다. 이때 기준이 되는 값이 집계 키(Aggregation Key)이며, AWS WAF는 IP 주소나 HTTP 헤더, 쿠키, 쿼리 문자열 같은 값을 기준으로 요청을 묶어 셉니다.

아파트 택배 보관함을 정리하는 상황에 비유할 수 있습니다. 택배를 세대 번호로 묶어 셀지, 받는 사람 이름으로 묶어 셀지에 따라 같은 양의 택배도 전혀 다른 그림이 됩니다.

세대 번호로 묶으면 한 집에 사는 여러 사람의 택배가 하나로 합쳐지고, 이름으로 묶으면 같은 집이라도 사람마다 따로 계산됩니다. 집계 키도 이와 같아서, IP 주소를 기준으로 하면 한 공유기 뒤의 여러 사용자가 한 사람처럼 취급되고, 쿠키나 헤더 값처럼 사용자마다 다른 값을 기준으로 하면 훨씬 세밀하게 나눌 수 있습니다.

결국 집계 키는 무엇을 한 사람으로 볼 것인가를 정하는 설정이며, 서비스의 사용자 구조와 프록시 환경을 고려해 골라야 합니다. 잘못 고르면 정상 사용자가 함께 차단되거나, 반대로 공격자가 키를 바꿔 가며 한도를 피해 갈 수 있습니다.

평가 창(Evaluation Window)

몇 초 동안의 요청을 세는지 정하는 방법

속도 기반 규칙에서 한도 100건이라는 숫자만 정하면, 그 100건이 1분 동안인지 10분 동안인지에 따라 전혀 다른 규칙이 됩니다. 이 기간을 정하는 설정이 평가 창(Evaluation Window)이며, AWS WAF에서는 1분에서 10분 사이의 값 중에서 고릅니다.

고속도로 과속 단속 카메라를 떠올리면 이해가 쉽습니다. 같은 차가 1분 동안의 평균 속도로 측정되는지, 5분 동안의 평균으로 측정되는지에 따라 단속 여부가 달라집니다.

짧게 보면 갑자기 몰아치는 순간을 잘 잡아내지만 잠깐의 튐에도 민감해지고, 길게 보면 순간적인 폭주를 놓치기 쉽습니다. 평가 창도 같은 원리로, 짧은 창은 짧고 강한 공격에 민감하고 긴 창은 지속적으로 조금씩 들어오는 공격을 더 잘 드러냅니다.

정리하면 평가 창은 요청을 몇 분 동안 모아서 셀지를 정하는 시간 범위이며, 규칙의 민감도와 반응 속도를 좌우합니다. 창을 길게 잡으면 한도에 도달하기까지 시간이 걸려 차단이 늦어질 수 있으므로, 공격 유형과 정상 트래픽의 리듬을 함께 보고 정해야 합니다.

속도 기반 규칙과 레이블 결합

집계 결과에 레이블을 붙여 다른 규칙과 연결하는 방법

속도 기반 규칙이 한도를 넘긴 요청을 곧바로 차단하면, 그 요청이 정상 사용자의 것일 때 되돌릴 방법이 없습니다. 그래서 AWS WAF는 한도를 넘긴 요청에 레이블(Label)이라는 표시를 붙이고, 그 표시를 다른 규칙이 읽어 추가 판단을 하도록 연결할 수 있습니다.

택배 물류센터에서 분류 직원이 무게나 크기가 이상한 상자에 빨간 스티커를 붙이는 모습을 생각하면 됩니다. 그 상자를 바로 반송하지 않고, 스티커를 본 검수 담당자가 별도 구역에서 내용을 확인한 뒤 반송이나 통과를 결정합니다.

스티커 자체는 판단이 아니라 표시이고, 최종 결정은 스티커를 읽는 다음 단계가 맡는 구조입니다. WAF에서도 속도 기반 규칙은 요청에 레이블만 붙이고, 차단이나 CAPTCHA, 로그 기록 같은 조치는 그 레이블을 조건으로 삼는 별도 규칙이 수행합니다.

즉 레이블 결합은 세는 규칙과 처리하는 규칙을 분리해, 같은 집계 결과를 여러 규칙이 각자 다른 방식으로 활용하게 하는 구조입니다. 이렇게 해 두면 한도 초과 요청을 곧바로 막지 않고 관찰만 하다가, 확신이 설 때 차단으로 전환하는 운용도 가능합니다.

6부. 속도 제한과 봇 대응055

속도 제한의 오탐 관리

정상 사용자가 함께 차단되지 않도록 조정하는 방법

짧은 시간에 요청을 많이 보내는 쪽을 막으려고 속도 제한(rate-based rule)을 걸어 두면, 사무실 전체가 회선 하나를 함께 쓰는 정상 사용자나 이미지와 스크립트를 한꺼번에 불러오는 정상 페이지가 공격자와 똑같이 걸리는 일이 생깁니다. 이렇게 정상 트래픽을 공격으로 잘못 판정하는 것을 오탐(false positive)이라 부르는데, 오탐이 늘면 실제 고객이 차단되어 매출과 신뢰가 함께 새기 때문에 임계값을 정하고 조정하는 일 자체가 운영의 핵심이 됩니다.

아파트 정문 경비실을 떠올려 보면 이해가 쉽습니다. 경비원이 하루에 몇 번까지 출입을 허용할지 정해 두면, 한 세대에 사람이 여러 명 살아도 문을 여는 쪽은 한 사람처럼 보이기 때문에 그 세대 전체가 하루치 출입 횟수를 다 써 버릴 수 있습니다.

그래서 경비원은 개인이 아니라 세대 단위로 세고, 몇 분 동안의 출입을 묶어서 판단하며, 문제가 되는 세대만 따로 불러 확인하는 식으로 규칙을 다듬습니다. 속도 제한도 마찬가지로 어떤 기준으로 묶어 셀지(집계 키, aggregation key), 몇 초 동안의 요청을 볼지(평가 시간 창), 몇 건에서 막을지를 함께 조정해야 합니다.

실제 AWS WAF에서는 IP 주소나 헤더, 경로 같은 집계 키를 무엇으로 잡고, 시간 창을 몇 초로 두며, 임계값을 어느 수준에 둘지를 접속 로그와 차단 로그를 보며 단계적으로 올리는 방식으로 오탐을 관리합니다.

사람과 봇을 구분하는 신호

자동화 트래픽을 가려내는 단서에는 무엇이 있는지

자동화 스크립트가 회원가입 폼을 수천 번 채우거나 상품 재고와 가격을 빠르게 긁어 가면, 서버는 정상 사용자보다 먼저 그 요청들에 자원을 빼앗기고 데이터도 통째로 복제됩니다. 그래서 요청 하나하나를 사람이 보낸 것인지 프로그램이 보낸 것인지 가려내는 일이 필요하고, 그 판단의 근거가 되는 단서들을 신호(signal)라고 부릅니다.

공항 입국 심사대를 떠올려 보면 이 단서들의 성격이 잘 드러납니다. 심사관은 여권이 위조되지 않았는지 보고, 여행 목적을 묻고, 대답하는 표정과 말투가 자연스러운지 살피며, 앞사람과 똑같은 대답을 반복하지는 않는지 확인합니다.

웹 요청에서도 브라우저가 스스로 밝히는 이름(User-Agent)과 실제로 보내는 헤더가 서로 맞는지, 자바스크립트가 실행되는 환경인지, 마우스 이동과 키 입력 같은 상호작용이 있는지, 같은 경로를 기계적으로 반복 호출하는지가 각각 하나의 단서가 됩니다. 다만 어느 신호 하나만으로 단정하지 않고 여러 신호를 겹쳐 볼수록 판정이 정확해집니다.

정리하면 사람과 봇을 가르는 신호는 요청의 내용, 브라우저 환경의 일관성, 상호작용의 흔적, 반복 패턴 같은 관찰 가능한 특징이며, AWS WAF의 봇 제어(Bot Control)는 이런 신호를 조합해 요청에 사람인지 봇인지 표시를 붙입니다.

봇 제어의 토큰 기반 검증

브라우저에 발급한 토큰으로 봇을 가려내는 방법

요청마다 붙는 헤더와 이름표는 프로그램이 얼마든지 흉내 낼 수 있어서, 그것만으로는 사람이 보낸 요청인지 확신하기 어렵습니다. 그래서 사이트는 브라우저에 위조하기 어려운 증표를 한 번 발급하고, 이후 요청에 그 증표가 실려 오는지를 확인하는 방식으로 판단을 단단하게 만듭니다.

회사 사옥 출입증을 생각하면 구조가 그대로 보입니다. 방문자는 안내데스크에서 신분을 확인하고 사진과 유효기간이 적힌 출입증을 받아 목에 겁니다. 이후에는 경비원이 얼굴을 다시 묻지 않고 출입증의 발급처 서명과 유효기간만 확인해 통과시키며, 출입증이 없거나 서명이 맞지 않으면 정문에서 다시 발급 절차를 밟게 합니다.

웹에서는 사이트가 브라우저에 서명된 토큰(token)을 내려 주고, 브라우저가 스크립트를 실행해 그 토큰을 붙여 요청을 보내면 서버가 서명과 유효 시간을 검사해 통과 여부를 정합니다. 이때 토큰은 특정 사이트와 연결되어 있고 짧은 시간만 유효하기 때문에, 다른 곳에서 복사해 와도 그대로 쓸 수 없습니다.

결국 토큰 기반 검증은 브라우저가 실제로 스크립트를 실행할 수 있는 환경인지 확인하면서, 발급 시점과 서명이 검증된 증표를 요청마다 함께 받는 방식이며, AWS WAF에서는 이런 토큰을 챌린지나 봇 제어 규칙이 발급하고 검사합니다.

봇 제어의 목표 동작 설정

봇을 차단·지연·허용 중 무엇으로 처리할지 정하는 방법

건물 경비원의 대응 매뉴얼을 떠올려 보면 선택지가 자연스럽게 구분됩니다. 수상한 방문자는 문 앞에서 돌려보낼 수 있고, 정체가 애매하면 안내데스크로 불러 신분을 한 번 더 확인하게 할 수 있고, 문제가 없는 사람은 그냥 통과시키며, 아직 판단이 서지 않는 대상은 출입은 허용하되 기록만 남겨 둘 수 있습니다.

정리하면 목표 동작 설정은 탐지 결과를 차단, 검증 요구, 허용, 집계 중 어느 처리로 이어 붙일지 정하는 일이며, 이 선택이 서비스 품질과 오탐 규모를 좌우합니다.

챌린지(Challenge)와 CAPTCHA

은행 창구에서 본인 확인을 하는 장면과 비슷합니다. 창구 직원은 신분증만으로 부족하면 생년월일이나 거래 내역 같은 추가 질문을 던지고, 대답이 맞으면 업무를 처리해 주며, 자동 응답 전화로는 그 질문에 제대로 답하기 어렵습니다.

웹에서 챌린지는 사용자가 특별히 무언가를 입력하지 않아도 브라우저가 백그라운드에서 연산을 수행하는 동안 잠깐 기다렸다가 통과시키는 방식이고, 캡차는 글자나 그림을 고르게 하는 등 사람이 쉽게 풀고 프로그램은 어려운 문제를 직접 제시합니다. 두 방식 모두 통과하면 앞서 설명한 토큰이 발급되어 이후 요청이 매끄럽게 이어지고, 실패하면 다시 시도하거나 차단으로 넘어갑니다.

정리하면 챌린지는 사용자 부담을 거의 늘리지 않으면서 브라우저 환경을 확인하는 검증이고, 캡차는 사람의 인지 능력을 직접 요구하는 검증이며, 둘 다 차단과 허용 사이의 완충 지대로 동작합니다.

정리하면 정상 봇 허용 설계는 검증된 봇의 신원을 확인해 허용 목록으로 관리하고, 허용 범위를 필요한 경로로 좁히며, 규칙 평가 순서를 함께 설계하는 일입니다.

IP 신뢰도(IP Reputation) 규칙

아파트 경비실에 붙은 출입 주의 명단을 떠올리면 이해가 쉽습니다. 경비원은 명단 자체를 직접 만들지 않고 관리 본부가 매일 갱신해 보내 주는 자료를 받아 두었다가, 방문객이 올 때마다 명단과 대조해 위험 등급을 확인합니다.

AWS WAF의 관리형 규칙 그룹도 같은 역할을 하는데, AWS가 평판 데이터를 계속 갱신하고 규칙은 요청이 들어온 주소를 그 데이터와 비교해 위험하다고 판단되면 차단하거나 집계만 하도록 동작합니다. 명단이 갱신되는 주기와 등급 기준은 AWS가 정하므로, 운영자는 어느 등급에서 어떤 조치를 취할지만 규칙에서 정하면 됩니다.

정리하면 IP 신뢰도 규칙은 요청의 IP 주소를 AWS가 관리하는 평판 데이터와 대조해 위험도를 판정하고, 그 결과에 따라 차단이나 관찰 같은 조치를 자동으로 취하는 기능입니다.

익명 IP 목록(Anonymous IP List)

VPN·프록시·토르 트래픽을 구분해 다루는 방법

해외에서만 서비스하는 쇼핑몰인데 국내 주소로 접속하는 이용자가 갑자기 늘었다면, 그중 상당수는 실제 위치를 숨기는 도구를 거쳐 들어온 접속일 수 있습니다. 이런 접속은 정상 이용자일 수도 있지만 자동 가입이나 재고 조회 같은 악용의 통로가 되기도 해서, AWS WAF는 VPN(가상 사설망)·프록시·토르 같은 익명화 수단을 쓴 주소를 따로 모은 익명 IP 목록(Anonymous IP List)을 제공합니다.

아파트 주차장에서 번호판을 가린 채 들어오는 차량을 생각해 보면 됩니다. 경비원은 그 차가 나쁜 목적이라고 단정할 수는 없지만, 번호판을 가렸다는 사실만으로도 별도 확인 대상으로 분류해 기록해 둡니다.

익명 IP 목록도 마찬가지로, 요청이 들어온 주소가 알려진 익명화 서비스 대역에 속하는지를 확인해 표시해 주고, 운영자는 그 표시를 근거로 차단할지 아니면 집계만 할지를 규칙에서 정합니다. 모든 익명 접속을 무조건 막으면 정상 이용자도 함께 막히므로, 이 목록은 판단의 재료로 쓰고 최종 결정은 운영 정책에 맡기는 구조입니다.

정리하면 익명 IP 목록은 VPN·프록시·토르처럼 출처를 숨기는 수단을 통해 들어온 요청을 식별해 주는 평판 기반 목록이며, 차단 여부는 이 목록을 참고해 운영자가 규칙으로 결정합니다.

위협 인텔리전스 규칙 그룹

알려진 공격자 IP 목록을 차단에 활용하는 방법

한 번 공격에 쓰였던 서버 주소는 다른 사이트를 공격할 때 다시 등장하는 경우가 많습니다. 그런데 개별 서비스 운영자가 전 세계의 그런 주소를 직접 수집하기는 현실적으로 불가능해서, AWS WAF는 위협 인텔리전스 규칙 그룹(Threat Intelligence Rule Group)이라는 형태로 알려진 공격자 주소 목록을 미리 묶어 제공합니다.

아파트 관리사무소가 경찰서에서 받은 수상한 차량 명단을 경비실에 붙여 두는 상황과 비슷합니다. 경비원은 명단을 스스로 만들지 않고 본부가 보내 준 자료를 그대로 받아 차량이 들어올 때 대조하며, 명단에 있으면 출입을 막거나 기록을 남깁니다.

위협 인텔리전스 규칙 그룹도 AWS가 관리하는 위협 정보를 바탕으로 만들어지고, 요청이 들어온 주소가 그 목록에 해당하면 차단이나 집계 같은 조치를 자동으로 수행합니다. 운영자는 규칙 그룹을 연결하고 어떤 조치를 쓸지만 정하면 되므로, 별도 수집 체계 없이도 알려진 공격자를 걸러낼 수 있습니다. 다만 목록에 없다고 안전이 보장되는 것은 아니어서, 다른 규칙과 함께 쓰는 것이 일반적입니다.

정리하면 위협 인텔리전스 규칙 그룹은 AWS가 수집·관리하는 알려진 공격자 IP 정보를 규칙 형태로 제공해, 요청 주소를 그 정보와 대조해 차단에 활용하게 해 주는 관리형 규칙 그룹입니다.

평판 기반 규칙의 오탐 위험

공유 IP 환경에서 평판 규칙이 정상을 막는 이유

평판 기반 규칙을 켜 두었다가 정상 고객이 갑자기 차단됐다는 신고를 받는 일이 생깁니다. 원인은 대개 주소를 혼자 쓰지 않는 환경인데, 회사 사무실이나 이동통신사처럼 수많은 사용자가 하나의 공인 IP를 함께 쓰는 경우 그중 한 명의 오남용만으로 주소 전체의 평판이 나빠질 수 있기 때문입니다.

아파트 한 동이 공동 현관 출입증 하나를 함께 쓰는 상황을 떠올려 보면 이해가 쉽습니다. 어떤 세대가 그 출입증을 부정하게 사용해 관리사무소가 출입증을 정지시키면, 같은 출입증을 쓰던 다른 모든 세대가 함께 문 앞에서 막힙니다.

평판 기반 규칙도 주소 단위로 판정하기 때문에 같은 구조의 문제를 안고 있고, 그래서 처음에는 차단보다 집계(Count) 모드로 켜서 어떤 요청이 걸리는지 관찰한 뒤 범위를 좁히는 방식이 권장됩니다. 또 평판 점수는 외부 데이터에 기반하므로 등급 기준이 바뀌면 판정 결과도 달라질 수 있다는 점을 감안해야 합니다.

정리하면 평판 기반 규칙의 오탐은 대개 다수가 공유하는 IP 주소를 개인 단위로 판정하는 데서 비롯되며, 관찰 모드로 시작해 예외를 정리하고 차단 범위를 단계적으로 넓히는 것이 안전합니다.

ASN 기반 판별

자율 시스템 번호로 트래픽 출처를 묶어 보는 방법

공격을 막으려고 문제 주소를 하나씩 목록에 넣다 보면 금세 목록이 수천 개로 불어나고, 정작 그 주소들은 며칠 만에 다른 주소로 바뀌어 버립니다. 그래서 주소 하나하나가 아니라 그 주소를 운영하는 네트워크 전체를 묶어 보는 방법이 필요하고, 이때 기준이 되는 번호가 ASN(자율 시스템 번호, Autonomous System Number)입니다.

택배를 회사 단위로 분류하는 상황과 비슷합니다. 개별 기사가 누구인지 일일이 기억하는 대신 어느 택배사 소속인지를 보면 그 물량의 성격을 훨씬 빠르게 판단할 수 있습니다.

ASN도 같은 방식으로, 하나의 사업자가 관리하는 주소 대역을 하나의 번호로 묶어 표현하며 AWS WAF에서는 요청이 어느 ASN에서 왔는지를 조건으로 규칙을 만들 수 있습니다. 예를 들어 클라우드 사업자 대역에서 오는 요청만 따로 세거나, 특정 사업자 대역을 차단 대상으로 지정하는 식입니다.

정리하면 ASN 기반 판별은 개별 IP 주소 대신 그 주소를 운영하는 네트워크 단위로 트래픽을 묶어 판단하는 방식이며, IP가 자주 바뀌는 환경에서 규칙을 단순하고 안정적으로 유지하는 데 쓰입니다.

IP 집합 자동 갱신

외부 위협 목록을 IP 집합에 주기적으로 반영하는 방법

위협 목록을 규칙에 반영해 두어도 며칠만 지나면 절반 이상이 쓸모없는 정보가 되고, 공격자들이 주소를 계속 바꾸기 때문에 사람이 주기적으로 복사해 붙여넣는 방식으로는 최신 상태를 유지하기 어렵습니다. 이 문제를 풀기 위해 AWS WAF는 IP 집합(IP Set)이라는 주소 묶음을 만들어 두고 외부에서 자동으로 채우는 구조를 제공합니다.

아파트 정문에 붙는 출입 제한 명단을 생각해 보면 이해가 쉽습니다. 경비원이 매일 손으로 명단을 고쳐 쓰는 대신, 관리 본부가 갱신한 파일을 정해진 시각에 자동으로 인쇄해 붙여 준다면 명단은 항상 최신으로 유지됩니다.

IP 집합도 같은 역할을 하는데, 규칙은 집합을 참조하고 집합의 내용은 외부 위협 목록을 제공하는 쪽에서 주기적으로 밀어 넣거나 스크립트가 갱신합니다. 이때 갱신 작업은 AWS의 API(응용 프로그램 인터페이스)를 호출하는 방식으로 이루어지며, 갱신이 실패하면 이전 내용이 그대로 남기 때문에 규칙이 갑자기 비는 일은 없습니다.

정리하면 IP 집합 자동 갱신은 규칙이 참조하는 주소 묶음을 외부 위협 목록과 주기적으로 동기화해, 사람이 손대지 않아도 차단 대상이 최신 상태로 유지되게 하는 운영 방식입니다.

지리적 차단의 실무 기준

국가 단위 차단을 결정할 때 검토할 항목

해외에서 쏟아지는 자동화된 공격 요청 때문에 정상 고객의 접속까지 느려지고, 로그에는 우리가 서비스하지도 않는 나라의 주소만 수천 건씩 쌓이는 상황이 생깁니다. 지리적 차단(geographic blocking)은 요청이 들어온 IP 주소의 국가를 판별해 특정 국가의 접속을 규칙으로 막는 AWS WAF의 기능이며, IP 주소 하나만으로 후보를 크게 줄일 수 있는 첫 단계 방어입니다.

이를 아파트 단지의 출입 정책에 비유하면 이해가 쉽습니다. 단지 관리 규정에 "정해진 지역에서 온 방문객과 택배만 정문에서 받는다"는 조항을 넣고, 경비원은 그 지역 명단에 있는 사람만 통과시키는 방식입니다.

여기서 국가 코드가 경비원이 들고 있는 명단이 되고, IP 주소의 국가 판정이 방문객 신분 확인이 되며, 허용과 차단의 결정은 정문 통과 여부가 됩니다.

다만 실제 주민이 해외에 나가 있거나 출장 중이라면 정당한 방문객까지 함께 막히므로, 차단을 켜기 전에 관찰(count) 모드로 어떤 요청이 걸리는지 며칠간 기록해 두어야 합니다.

그래서 실제 운영에서는 VPN이나 모바일 통신망 때문에 국가 판정이 틀릴 수 있다는 한계를 인정하고, 허용할 국가와 예외로 둘 경로를 문서로 먼저 정하는 절차가 함께 필요합니다. 결국 지리적 차단은 IP 주소의 국가 정보를 기준으로 허용과 차단을 나누는 규칙이며, 서비스 대상 국가와 해외 이용자, 오판 가능성을 함께 검토한 뒤 좁은 범위부터 적용하는 것이 안전합니다.

프록시·CDN 뒤의 실제 클라이언트 IP

X-Forwarded-For에서 진짜 요청자를 찾는 방법

서버 앞에 프록시나 CDN을 두면 속도와 안정성은 좋아지지만, WAF와 서버가 보는 접속 주소가 모두 프록시의 주소로 바뀌어 실제 요청자가 누구인지 알 수 없게 됩니다. X-Forwarded-For는 이런 중계 구간을 지나면서 원래 클라이언트의 IP를 덧붙여 전달하는 HTTP 헤더이고, AWS WAF에서는 이 헤더의 값을 기준으로 IP를 판정하는 전달 IP 설정(forwarded IP config)을 사용할 수 있습니다.

이를 회사 사내 우편에 비유하면, 여러 부서를 거쳐 온 문서 봉투 겉면에 전달한 사람의 이름이 도장처럼 차례로 찍히는 것과 같습니다. 봉투를 처음 보낸 사람의 이름이 맨 앞에 찍히고 마지막으로 전달한 사람의 이름이 맨 뒤에 찍히므로, 봉투를 받은 사람은 맨 앞자리를 보면 발신자를 알 수 있습니다.

그러나 겉면에 이름을 아무나 적을 수 있듯이 이 헤더도 클라이언트가 임의로 조작할 수 있어, 아무 값이나 믿지 말고 우리가 신뢰하는 프록시가 붙인 값만 골라 읽어야 합니다.

그래서 보통은 신뢰하는 중계 장비의 수를 세어 오른쪽에서 몇 번째 값을 볼지 정하고, 그보다 앞의 값은 무시합니다.

정리하면 실제 클라이언트 IP는 X-Forwarded-For의 값 가운데 신뢰 경계 안에서 마지막으로 추가된 주소를 뜻합니다. 로그에서는 WAF가 기록한 clientIp가 프록시 주소인지 먼저 확인하고, CloudFront를 앞에 둔 구성이라면 CloudFront가 따로 제공하는 클라이언트 주소 헤더를 함께 보는 것이 정확합니다.

IP 기반 규칙과 개인정보

IP를 수집·보관할 때 지켜야 할 기준

공격을 막겠다고 모든 접속 IP를 무기한 저장하면, 그 기록 자체가 개인의 위치와 이용 패턴을 드러내는 개인정보 더미가 되어 유출 사고 때 더 큰 문제가 됩니다. IP 기반 규칙은 접속 주소를 기준으로 허용과 차단을 판단하는 WAF 기능인데, 판단에 쓰는 순간부터 수집과 보관의 책임이 따라붙습니다.

이를 아파트 경비실의 방문 기록부에 비유할 수 있습니다. 기록부에 방문자 이름과 시각, 방문 목적을 적어 두면 나중에 문제가 생겼을 때 확인할 수 있지만, 아무나 열람하고 몇 년씩 방치하면 그 자체가 사생활 침해가 됩니다.

그래서 기록부에 적는 항목을 최소로 정하고, 열람 권한을 경비 책임자 한 사람으로 좁히며, 정해진 기간이 지나면 파기하는 규칙을 함께 두는 것입니다.

WAF 로그에서도 IP 주소는 개인을 추정할 수 있는 정보로 볼 수 있으므로 수집 목적을 분명히 하고 보관 기간을 정하며 접근을 제한해야 하고, 국내 개인정보보호법과 해외 이용자가 있는 경우의 GDPR 같은 기준을 함께 확인해야 합니다.

결국 IP는 보안 판단의 근거이자 개인을 추정할 수 있는 정보이므로, 수집 목적과 보관 기간, 접근 권한, 파기 절차를 규칙과 로그 설계에 함께 못 박아야 합니다.

허용 목록(Allow List) 우선 설계

정상 트래픽을 먼저 통과시키는 규칙 배치 방법

차단 규칙만 쌓아 두면 정상 사용자가 애매한 조건에 걸려 막히는 일이 생기고, 그때마다 예외를 덧붙이다 보면 규칙은 점점 더 뒤엉킵니다. 허용 목록(Allow List) 우선 설계는 확실히 정상이라고 판단되는 트래픽을 먼저 통과시키고, 남은 요청에만 차단 검사를 적용하는 규칙 배치 방식입니다.

이를 공항 보안 검색에 비유하면, 탑승권과 신분증을 먼저 확인해 탑승객임이 확인된 사람만 검색대로 보내는 절차와 같습니다. 확인되지 않은 사람은 검색대 앞에서 더 자세히 심사하고, 확인된 사람은 같은 확인 절차를 반복하지 않습니다.

WAF에서도 규칙은 위에서부터 차례로 평가되고 먼저 일치한 규칙이 최종 결정을 내리므로, 허용 규칙을 위에 두면 아래의 차단 규칙이 그 요청을 건드리지 않습니다.

다만 허용 목록이 넓으면 공격자도 그 안에 들어올 수 있으므로, 사내 고정 IP나 검증된 검색 봇처럼 범위가 좁고 신뢰할 수 있는 대상만 올려야 합니다. 또한 허용 규칙에는 카운트 모드를 함께 걸어 실제로 얼마나 통과하는지 먼저 지켜보는 것이 좋습니다.

정리하면 허용 목록 우선 설계는 신뢰가 확인된 트래픽을 앞단에서 통과시키고 나머지를 차단 규칙으로 넘기는 배치이며, 허용 범위를 좁게 유지하고 관찰 기간을 거치는 것이 핵심입니다.

WAF 로깅 개요

어떤 로그를 어디로 보낼 수 있는지 전체 그림

요청이 차단됐는데 왜 차단됐는지 알 수 없으면 규칙을 고칠 수도, 오탐을 증명할 수도 없어 운영이 추측에 의존하게 됩니다. WAF 로깅은 WAF가 요청마다 내린 판단과 그 근거를 외부 저장소로 내보내는 기능이며, AWS WAF는 로그를 CloudWatch Logs와 S3 버킷, Kinesis Data Firehose 세 곳으로 보낼 수 있습니다.

이를 건물 CCTV에 비유하면, 카메라가 찍는 것만으로는 부족하고 녹화본을 어디에 보관하고 누가 언제까지 지켜보는지가 정해져야 합니다. 영상은 저장 장치에 쌓이고, 사건이 생기면 해당 시각의 영상을 꺼내 확인하며, 보관 기간이 지나면 자동으로 지워집니다.

WAF 로그에서 녹화 시각에 해당하는 것은 요청 시각이고, 화면에 비친 장면은 요청 주소와 헤더, 차단 여부이며, 저장 장치를 고르는 일이 로그 대상 선택이 됩니다.

CloudWatch Logs는 바로 검색하고 경보를 걸기에 좋고, S3는 장기 보관과 비용에 유리하며, Firehose는 다른 분석 도구로 흘려보내는 통로 역할을 합니다.

결국 WAF 로깅은 판단 결과와 요청 정보를 목적에 맞는 저장소로 보내는 체계이고, 남길 항목과 보관 기간을 먼저 정하는 것이 운영의 출발점입니다.

CloudWatch Logs로 로그 보내기

로그 그룹을 만들어 요청 기록을 남기는 방법

WAF를 켜 두기만 하고 로그를 보내지 않으면, 차단이 갑자기 늘어나도 언제 무엇이 막혔는지 사후에 확인할 방법이 없습니다. CloudWatch Logs는 AWS의 로그 저장과 검색을 맡는 서비스이고, WAF의 로그 대상(logging destination)으로 지정하면 요청 기록이 로그 그룹(log group)에 차곡차곡 쌓입니다.

이를 회사 문서 보관소에 서류함을 하나 만드는 일에 비유할 수 있습니다. 먼저 서류함을 만들고 이름표를 붙인 뒤, 결재가 끝난 문서가 그 함에 자동으로 들어가도록 규칙을 걸어 두는 순서입니다.

WAF에서는 로그 그룹 이름이 정해진 접두사로 시작해야 한다는 조건이 있어 이름 규칙을 미리 확인해야 하고, WAF가 로그를 보낼 수 있는 권한도 함께 설정해야 합니다.

서류함에 보관 기간을 정하듯 로그 그룹에도 보존 기간(retention)을 설정해 오래된 로그가 무한정 쌓이지 않게 합니다.

정리하면 WAF 로그를 CloudWatch Logs로 보내려면 로그 그룹을 만들고 WAF의 로그 대상으로 지정한 뒤 권한과 보존 기간을 정하는 순서를 따르면 됩니다.

S3로 로그 보내기

장기 보관용으로 로그를 버킷에 쌓는 방법

웹 서비스를 운영하다 보면 몇 달 전에 어떤 요청이 차단됐는지 확인해야 할 일이 생기지만, 화면에서 보이는 로그는 며칠치만 남아 있어서 그때가 되면 아무것도 남아 있지 않습니다. S3로 로그 보내기는 이렇게 사라지는 기록을 장기 보관용 저장소인 S3(Simple Storage Service) 버킷에 차곡차곡 쌓아 두는 방법이고, AWS WAF는 로깅 설정에서 대상으로 이 버킷을 지정하는 방식으로 연결됩니다.

회사 문서를 매일 서류함에 넣어 두면 금방 꽉 차지만, 일정 기간이 지난 서류를 창고로 옮겨 상자째 쌓아 두면 책상은 넓게 유지되고 과거 기록도 필요할 때 꺼낼 수 있습니다.

WAF는 요청 한 건마다 판정 결과를 담은 기록을 만들고, 이를 정해진 형식의 파일로 묶어 버킷 안의 폴더 구조에 날짜별로 넣습니다. 버킷은 파일을 넣는 통로와 꺼내는 통로가 분리된 보관 창고 역할을 하고, 보관 기간이 지난 파일은 수명 주기 규칙에 따라 자동으로 정리되거나 더 싼 저장 등급으로 옮겨집니다. 이렇게 해 두면 로그를 조회하는 WAF 본체의 부담은 늘지 않으면서 수년치 기록을 남길 수 있습니다.

정리하면 WAF 로그를 S3 버킷으로 내보내는 것은 판정 기록을 장기 보관용 객체 저장소에 날짜별 파일로 적재하는 구성이며, 조회용 저장소와 보관용 저장소를 나누어 운영하는 것이 핵심입니다.

Data Firehose로 로그 보내기

로그를 다른 저장소로 흘려보내는 파이프라인 구성

WAF 로그를 한 곳에만 쌓아 두면 그 저장소가 지원하지 않는 분석 도구를 쓰고 싶을 때 기록을 다시 옮겨야 하고, 로그 양이 갑자기 늘면 저장이 밀리기도 합니다. Data Firehose로 로그 보내기는 이런 기록을 목적지까지 자동으로 흘려보내는 전송 파이프라인을 만드는 구성이고, WAF의 로깅 대상 가운데 하나로 Firehose 전송 스트림을 지정해 연결합니다.

아파트에서 나오는 재활용품을 각 집이 직접 처리하지 않고 단지 안 집하장에 모으면, 집하장이 분류해서 재활용 업체나 소각장으로 알아서 보내 주는 것과 비슷합니다.

WAF는 요청 기록을 전송 스트림으로 넘기기만 하고, 스트림은 들어온 기록을 정해진 크기나 시간 단위로 묶어 압축한 뒤 지정한 목적지로 전달합니다. 목적지가 S3 버킷이면 파일로 쌓이고, 분석 도구나 다른 저장 서비스면 그쪽 형식에 맞춰 들어가며, 전송에 실패한 기록은 별도 보관 위치에 남겨 나중에 다시 처리할 수 있습니다. 그래서 로그를 받는 쪽을 바꾸고 싶을 때도 WAF 설정을 건드리지 않고 파이프라인의 목적지만 바꾸면 됩니다.

정리하면 Firehose는 WAF가 만든 로그를 받아 여러 목적지로 안정적으로 전달하는 관리형 전송 파이프라인이며, 수집과 전달을 분리해 저장처를 유연하게 바꿀 수 있게 해 주는 것이 핵심입니다.

로그의 시각 항목은 요청이 들어온 때를, 출발지 주소 항목은 요청이 어디서 왔는지를 알려 주고, 요청 경로와 방식 항목은 무엇을 하려던 요청인지를 보여 줍니다. 판정 항목에는 허용인지 차단인지가, 규칙 항목에는 어떤 규칙이 그 판정을 냈는지가 들어가며, 종료 코드 같은 항목은 요청이 최종적으로 어떻게 처리됐는지를 남깁니다. 이 칸들을 나란히 놓고 보면 왜 이 요청이 막혔는지가 문장처럼 읽힙니다.

정리하면 WAF 로그는 요청 시각, 출발지, 경로, 판정, 규칙 같은 이름 있는 필드의 묶음이고, 필드의 의미를 알면 한 건의 기록에서 차단 원인을 바로 짚어낼 수 있습니다.

로그 필터링(Logging Filter)

필요한 요청만 골라 기록해 비용을 줄이는 방법

모든 요청을 다 기록하면 정상 트래픽이 대부분을 차지해 정작 문제가 된 기록을 찾기 어렵고, 저장 비용도 요청 수에 비례해 계속 늘어납니다. 로그 필터링(Logging Filter)은 이런 기록 가운데 조건에 맞는 요청만 남기도록 걸러서 필요한 것만 남기고 비용을 줄이는 방법입니다.

건물 출입 기록을 모든 사람에 대해 남기면 장부가 금세 두꺼워지지만, 새벽 시간대나 특정 출입구처럼 관심 있는 조건만 기록하게 바꾸면 장부는 얇아지고 궁금한 장면은 그대로 남습니다.

WAF에서는 필터에 조건을 적고 그 조건의 기록을 남길지 버릴지를 정하는 방식으로 동작하며, 기본 기록을 끄고 차단된 요청만 남기는 식의 조합이 자주 쓰입니다. 조건은 판정 결과나 규칙 이름, 요청 경로, 출발지 대역 같은 값으로 만들 수 있어서 업무에 필요한 범위를 좁혀 갈 수 있습니다. 다만 필터를 잘못 잡으면 조사에 필요한 기록까지 사라지므로, 평소에는 넓게 남기고 비용이 문제가 된 뒤에 좁히는 순서가 안전합니다.

정리하면 로깅 필터는 남길 요청의 조건을 정해 기록량을 줄이는 장치이며, 조사에 필요한 최소한의 기록은 유지하면서 비용을 관리하는 균형이 핵심입니다.

로그 보존과 비용

보존 기간과 저장 위치가 비용에 미치는 영향

로그를 오래 남기려고 하면 저장 요금이 계속 쌓이고, 반대로 보존 기간을 짧게 잡으면 나중에 감사나 장애 조사에서 근거를 잃습니다. 로그 보존과 비용은 이 두 요구가 부딪히는 지점을 다루는 문제이고, WAF 로그에서는 어디에 얼마나 오래 둘지를 정하는 설정이 비용의 대부분을 좌우합니다.

이삿짐 보관 창고를 생각해 보면 자주 꺼내는 물건은 집 안 가까운 곳에 두고, 일 년에 한 번 볼 물건은 먼 창고의 싼 자리에 두는 것이 합리적입니다.

로그도 최근 며칠치는 자주 조회하는 저장소에 두고 오래된 기록은 단가가 낮은 보관 등급으로 옮기면 같은 양을 훨씬 적은 비용으로 유지할 수 있습니다. 여기에 보관 기간을 정해 두면 그 기간이 지난 파일이 자동으로 삭제되어 사람이 손대지 않아도 비용이 늘지 않습니다. 또 조회가 거의 없는 기록은 압축된 상태로 두고 필요할 때만 꺼내는 편이 유리합니다.

정리하면 보존 비용은 저장 위치의 단가와 보존 기간, 조회 빈도 세 가지로 결정되며, 자주 보는 기록과 가끔 보는 기록을 나누어 두는 설계가 비용을 크게 줄여 줍니다.

CloudWatch 지표 모니터링

BlockedRequests 같은 지표로 이상을 감지하는 방법

차단이 급증해도 대시보드를 사람이 계속 들여다보지 않으면 알아채기 어렵고, 로그는 쌓여 있어도 지금 이상한 일이 벌어지는지는 바로 보이지 않습니다. CloudWatch 지표 모니터링은 요청 수나 차단 건수 같은 숫자를 일정 간격으로 집계해 두고 그 값이 평소와 다를 때 알려 주는 방법이고, AWS WAF는 이런 지표를 CloudWatch로 보냅니다.

아파트 관리실이 각 세대의 전기 사용량을 매시간 숫자로 받아 두면, 평소와 다른 세대를 바로 찾아낼 수 있는 것과 같습니다.

WAF는 처리한 요청 수, 허용된 요청 수, 차단된 요청 수(BlockedRequests) 같은 값을 규칙과 연결해 주기적으로 내보내고, CloudWatch는 이를 시계열로 쌓아 그래프로 보여 줍니다. 여기에 임계값을 정한 경보를 걸어 두면 차단 건수가 몇 분 사이에 크게 늘었을 때 메일이나 알림으로 통보받게 됩니다. 지표만으로는 이유를 알 수 없으므로 알림을 받은 뒤 로그에서 해당 시간대의 기록을 확인하는 순서로 원인을 좁힙니다.

정리하면 CloudWatch 지표 모니터링은 WAF가 내보내는 요청 수와 차단 건수 같은 수치를 모아 임계값을 넘을 때 알리는 구조이며, 숫자로 이상을 먼저 감지하고 로그로 원인을 확인하는 조합이 핵심입니다.

경보(Alarm) 설계

차단 급증을 알려주는 경보를 만드는 방법

차단이 갑자기 늘어나도 아무도 모르고 지나가면, 서비스는 이미 느려진 뒤에야 사고를 알게 됩니다. 그래서 WAF(웹 애플리케이션 방화벽)의 차단 수치를 지켜보다가 평소와 다를 때 사람에게 알려주는 경보(Alarm) 설계가 필요합니다.

아파트 경비실의 순찰 기록을 떠올리면 이해가 쉽습니다. 경비원이 매일 몇 명이 출입했는지 적어 두기만 하면 기록은 남지만 이상한 일은 놓치므로, 평소보다 새벽 출입이 크게 늘면 관리사무소에 연락이 가도록 기준을 정해 두어야 합니다.

WAF 경보도 같은 구조로, 어떤 지표(차단된 요청 수, 4xx 응답 비율 등)를 볼지 정하고, 몇 분 동안 얼마를 넘으면 넘어섰다고 볼지 임계값을 정하고, 그 조건이 유지될 때 누구에게 어떤 방식으로 알릴지를 미리 묶어 두는 것입니다. 여기에 너무 예민한 기준은 새벽 호출만으로도 울려 사람이 경보를 무시하게 만들므로, 실제 트래픽 패턴을 며칠 관찰한 뒤 기준을 잡는 편이 좋습니다.

정리하면 경보 설계는 WAF의 차단 지표에 임계값과 관찰 기간, 통보 대상을 정해 붙이는 일이며, 목적은 사고를 대신 막는 것이 아니라 이상 징후를 사람이 가장 먼저 알아채게 하는 것입니다.

8부. 로깅과 모니터링080

샘플 요청(Sampled Requests)

최근 요청 표본으로 규칙 동작을 눈으로 확인하는 방법

규칙을 켜 두었는데 정상 사용자가 막히기 시작하면, 어느 요청이 왜 걸렸는지 알 수 없어 원인을 짐작만 하게 됩니다. 이때 WAF가 최근 요청의 일부를 그대로 보관해 보여주는 샘플 요청(Sampled Requests) 기능으로 규칙이 실제로 어떻게 동작했는지 눈으로 확인할 수 있습니다.

회사 택배 접수대를 떠올려 보면, 접수 직원이 모든 상자를 보관하지는 않고 문제가 생긴 상자 몇 개만 옆 선반에 남겨 두는 것과 비슷합니다.

WAF도 들어온 요청 전부를 저장하지 않고 일부만 표본으로 남기며, 그 표본에는 요청이 들어온 시각, 출발지 IP, 요청 경로, HTTP 메서드, 그리고 어느 규칙에 걸려 허용·차단·Count 중 무엇으로 처리됐는지가 함께 붙습니다. 그래서 표본 한 줄을 열어 보면 "이 요청이 이 조건 때문에 막혔다"는 사실을 추측이 아니라 기록으로 확인할 수 있고, 같은 형태의 요청이 반복되는지도 눈에 들어옵니다.

다만 표본은 전체가 아니라 일부이므로, 표본에 없다고 그 요청이 없었다는 뜻은 아닙니다.

정리하면 샘플 요청은 WAF가 최근 트래픽에서 남긴 표본 요청 기록이며, 규칙 튜닝과 오탐 확인에서 가장 먼저 들여다보는 현장 증거입니다.

Count 모드로 관찰하기

차단 대신 세기만 해서 영향 범위를 파악하는 방법

새 규칙을 바로 차단으로 켜면, 그 규칙이 잘못 잡은 정상 요청까지 함께 막혀 서비스 장애로 이어질 수 있습니다. 그래서 규칙이 실제로 어떤 요청을 잡아내는지 먼저 세어 보기만 하는 Count 모드로 관찰하는 절차가 필요합니다.

아파트 출입 게이트에 새 잠금장치를 달 때, 바로 문을 잠그지 않고 "잠갔더라면 막혔을 사람"의 명단만 먼저 뽑아 보는 것과 같습니다.

WAF의 규칙 동작은 보통 허용(Allow), 차단(Block), 세기(Count)로 나뉘고, Count 모드는 조건에 맞는 요청을 차단하지 않고 몇 건이 걸렸는지만 지표로 남깁니다. 며칠 관찰하면 이 규칙에 걸린 요청이 하루 몇 건인지, 그중 정상 사용자로 보이는 요청이 얼마나 섞였는지가 숫자로 드러나므로, 영향 범위를 가늠한 뒤 차단으로 바꿀지 조건을 좁힐지 결정할 수 있습니다.

이때 걸린 요청의 표본까지 함께 보면 숫자만으로는 알 수 없는 실제 요청 모양을 확인할 수 있습니다.

정리하면 Count 모드는 차단 권한을 잠시 내려놓고 규칙의 적중 횟수만 기록하게 하는 관찰 모드이며, 차단 전에 영향 범위를 재는 안전장치 역할을 합니다.

규칙 튜닝 절차

오탐을 찾아 조건을 좁혀가는 순서

규칙을 세워 두면 언젠가는 정상 요청이 규칙에 걸리는 오탐(False Positive)이 생기는데, 그때 규칙을 통째로 끄면 진짜 공격까지 함께 열리게 됩니다. 그래서 오탐을 찾아 조건을 좁혀 가는 규칙 튜닝 절차를 순서대로 밟아야 합니다.

아파트 경비실의 방문객 명단을 고치는 일과 비슷합니다.

먼저 어떤 요청이 막혔는지 샘플 요청에서 확인해 걸린 규칙과 조건을 특정하고, 다음으로 그 요청이 정말 정상인지 업무 담당자에게 확인해 오탐인지 판단합니다. 오탐으로 확인되면 규칙을 끄는 대신 조건에 예외를 더하거나 범위를 좁혀 그 요청만 빠져나가게 하고, 마지막으로 같은 규칙을 Count 모드로 잠시 돌려 다른 정상 요청이 또 걸리는지 다시 확인합니다.

이 순서를 건너뛰고 바로 차단을 켜면 같은 문제가 다른 형태로 반복되므로, 확인과 수정과 재확인을 한 묶음으로 돌리는 것이 핵심입니다.

정리하면 규칙 튜닝은 샘플 요청으로 대상 규칙을 찾고, 오탐 여부를 확인하고, 조건을 좁혀 예외를 넣고, Count 모드로 재확인하는 순서로 진행되는 반복 절차입니다.

예외 처리 설계

정상 요청을 규칙에서 빼는 방법과 그 위치

관리 도구나 결제 콜백처럼 늘 같은 형태로 들어오는 정상 요청이 보안 규칙에 걸리면, 그 요청을 억지로 규칙에 맞추느라 시간을 쓰거나 규칙 전체를 꺼 버리게 됩니다. 그래서 정상 요청만 규칙에서 빼내는 예외 처리 설계가 필요하고, 어디에 예외를 두느냐가 안전을 좌우합니다.

회사 정문 경비실에 "이 협력사 직원은 명단 확인 없이 통과"라고 적힌 출입 허가증을 붙이는 일과 같습니다.

예외는 보통 규칙 하나에 조건을 더하는 방식과, 특정 요청을 규칙 평가 전에 통과시키는 방식으로 나뉘는데, 앞의 방식은 그 규칙에만 영향을 주므로 범위가 좁고 안전합니다. 반대로 넓은 범위를 통째로 빼면 그 구간이 공격에 그대로 노출되므로, IP 하나나 경로 하나처럼 최대한 좁게 지정하고 왜 필요한지를 남겨 두어야 합니다.

또 예외를 넣은 뒤에는 그 예외가 실제로 필요한 요청만 통과시키는지 Count 모드로 확인하는 편이 좋습니다.

정리하면 예외 처리 설계는 정상 요청을 규칙 평가에서 제외하는 일이며, 가능하면 규칙 단위의 좁은 예외를 쓰고 넓은 면제는 피하는 것이 원칙입니다.

보안 규칙과 비즈니스 규칙의 분리

목적이 다른 규칙을 나눠 관리하는 방법

보안을 위해 만든 규칙과 서비스 운영을 위해 만든 규칙을 한 덩어리로 섞어 두면, 운영 요구로 규칙을 고칠 때 보안이 함께 약해지고 사고가 났을 때 원인도 찾기 어려워집니다. 그래서 목적이 다른 규칙을 보안 규칙과 비즈니스 규칙으로 나눠 관리하는 설계가 필요합니다.

회사 건물의 보안팀과 운영팀을 떠올리면 이해가 쉽습니다.

보안팀은 외부인 출입을 막는 것이 목적이고 운영팀은 직원이 일을 잘하게 돕는 것이 목적인데, 두 팀의 규정을 한 문서에 섞으면 예외 하나를 추가할 때 누구 승인으로 바뀌었는지 알 수 없게 됩니다. WAF에서도 SQL 삽입이나 알려진 공격 패턴을 막는 규칙은 보안 규칙으로, 특정 경로의 접근을 제한하거나 트래픽을 나누는 규칙은 비즈니스 규칙으로 나누어 두면 변경 권한과 검토 절차를 다르게 가져갈 수 있습니다.

이렇게 나누면 보안 규칙은 함부로 손대지 않으면서 비즈니스 규칙만 자주 고칠 수 있고, 지표와 경보도 목적별로 따로 볼 수 있습니다.

정리하면 이 분리는 차단 목적의 보안 규칙과 운영 목적의 비즈니스 규칙을 별도 묶음으로 두어 변경 이력과 책임, 경보 기준을 각각 관리하는 방식입니다.

Web ACL 테스트 전략

스테이징과 운영에서 규칙을 검증하는 방법

새로 만든 차단 규칙을 아무 검증 없이 운영 환경에 올렸다가 정상 고객의 결제 요청까지 막혀 버리는 일이 흔히 벌어집니다. 이 곤란을 줄이려고 운영과 똑같이 꾸린 환경에서 규칙을 먼저 시험해 보는 절차가 필요하고, 이것이 Web ACL(웹 요청을 검사하는 규칙 묶음) 테스트 전략입니다.

아파트 단지에 새 출입 통제 장치를 달 때 바로 정문에 붙이지 않고, 먼저 후문이나 지하 주차장 입구 같은 시험용 출입구에서 며칠 돌려 보는 것과 같습니다.

시험용 출입구에서는 카운트 모드, 즉 막지는 않고 통과시키면서 기록만 남기는 설정으로 규칙을 돌려 누가 걸리는지 명단을 확인합니다. 통과한 명단과 걸린 명단을 실제 주민 명부와 대조해 정상 주민이 섞여 있는지 보고, 그 결과로 규칙의 조건을 좁힙니다. 정문에 옮길 때도 전체가 아니라 한 동씩 옮기듯 소수의 트래픽에만 먼저 적용해 며칠 지켜봅니다.

정리하면 Web ACL 테스트 전략은 스테이징 환경에서 카운트 모드로 규칙을 먼저 돌려 오탐을 확인하고, 소량 트래픽에 점진 적용한 뒤 전체로 넓히는 순서입니다. 핵심은 차단을 마지막 단계에 두고, 그 앞의 모든 단계에서 기록과 비교로 근거를 쌓는 것입니다.

로그 기반 오탐 분석

로그에서 잘못 차단된 정상 요청을 찾아내는 방법

차단 규칙을 켠 뒤로 특정 지역 고객만 간헐적으로 로그인이 안 된다는 문의가 들어오는데, 규칙이 수백 줄이라 어디서 걸렸는지 눈으로 찾기 어렵습니다. 이때 필요한 것이 차단 기록을 뒤져 잘못 막힌 정상 요청을 골라내는 로그 기반 오탐(false positive, 정상을 잘못 차단함) 분석입니다.

택배 회사가 분류 기준을 너무 빡빡하게 잡아 멀쩡한 택배까지 반송하고 있는 상황과 같습니다.

반송 목록에는 반송 사유가 한 줄씩 적혀 있으니, 그 사유별로 건수를 세어 어느 기준이 가장 많이 오작동하는지 먼저 봅니다. 다음으로 반송된 송장 번호를 고객 주문 기록과 하나씩 맞춰 보며 실제로 받았어야 할 택배가 몇 건인지 확인합니다. 이 대조가 끝나면 문제의 기준을 없애는 대신 조건을 한 칸 느슨하게 바꾸고, 같은 사유가 다시 늘어나는지 며칠간 지켜봅니다.

정리하면 로그 기반 오탐 분석은 차단 로그에서 규칙별 차단 건수와 사유를 세고, 막힌 요청을 실제 정상 트래픽과 대조해 잘못 막힌 비율을 확인하는 작업입니다. 건수 자체가 아니라 정상 요청과의 대조가 판단의 기준이라는 점이 핵심입니다.

규칙 변경의 영향 범위

규칙 하나를 바꿀 때 영향받는 요청을 가늠하는 방법

아파트 중앙 난방의 온도 기준을 한 도 낮추면 그 기준을 함께 쓰는 모든 세대가 동시에 영향을 받는 것과 같습니다.

먼저 이 규칙이 어느 주소, 어느 경로, 어느 헤더 조건을 보고 판정하는지 나열해 그 조건에 걸리는 요청의 범위를 그립니다. 그 범위 안에 사람이 쓰는 화면 요청뿐 아니라 자동화된 서버 간 호출이 섞여 있는지 확인하는 것이 특히 중요합니다. 마지막으로 그 범위의 요청량이 전체에서 차지하는 비중을 로그로 재어, 잘못될 경우 감당할 수 있는 규모인지 판단합니다.

정리하면 규칙 변경의 영향 범위는 규칙이 참조하는 조건과 그 조건에 걸리는 요청의 목록, 그리고 그 요청량의 비중으로 가늠합니다. 조건이 겹치는 다른 규칙까지 함께 확인해야 실제 영향 범위를 다 볼 수 있습니다.

카나리 배포와 점진 적용

일부 트래픽에만 새 규칙을 적용하는 방법

규칙을 한 번에 전체 트래픽에 적용하면 문제가 생겼을 때 피해 범위가 곧 전체가 됩니다. 그래서 새 규칙을 소량의 트래픽에만 먼저 태워 보고 이상이 없으면 조금씩 늘리는 방식이 쓰이고, 이것이 카나리 배포(canary deployment, 소량 선적용)와 점진 적용입니다.

회사에서 새 사내 규정을 전 직원에게 동시에 시행하지 않고 한 부서에서 몇 주 돌려 본 뒤 나머지 부서로 넓히는 것과 같습니다.

먼저 새 규칙을 별도 규칙 묶음으로 만들어 전체 요청 중 작은 비율에만 그 묶음을 연결합니다. 그 비율의 트래픽에서 차단 건수와 오류율을 보며, 기존 규칙만 적용된 나머지 트래픽과 수치를 나란히 비교합니다. 차이가 허용 범위 안이면 비율을 한 단계 올리고, 범위를 벗어나면 비율을 0으로 되돌려 영향받은 요청을 그 소수로 한정합니다.

정리하면 카나리 배포는 새 규칙을 별도 규칙 묶음으로 분리해 소량 트래픽에만 연결하고, 기존 트래픽과 지표를 비교하며 비율을 올리는 방식입니다. 문제가 생겨도 피해를 소량에 가둘 수 있다는 것이 이 방식의 값어치입니다.

롤백 계획

새 규칙이 문제를 일으켰을 때 되돌리는 방법

새 규칙을 켠 지 몇 분 만에 정상 주문이 급감하는데, 담당자가 규칙 이름과 이전 설정을 기억하지 못해 되돌리는 데만 한 시간이 걸리는 상황이 있습니다. 그래서 규칙을 바꾸기 전에 되돌릴 방법과 순서를 미리 정해 두는 롤백(rollback, 이전 상태로 되돌리기) 계획이 함께 있어야 합니다.

아파트 엘리베이터를 점검할 때 문제가 생기면 바로 원래 운행 모드로 돌릴 수 있도록 복구 절차와 담당자를 먼저 정해 두는 것과 같습니다.

규칙을 바꾸기 전에 지금 설정을 파일이나 문서로 남겨 두고, 되돌릴 때 무엇을 어떤 순서로 되돌릴지 한 줄씩 적습니다. 되돌리기는 새 규칙을 끄는 것에서 끝나지 않고, 연결했던 규칙 묶음과 비율 설정까지 원래대로 돌려야 완결됩니다. 되돌린 뒤에는 차단 건수와 오류율이 변경 전 수치로 회복되는지 확인하고, 그 확인이 끝나야 상황 종료로 봅니다.

정리하면 롤백 계획은 변경 전 설정의 사본, 되돌리는 순서와 담당자, 되돌린 뒤의 확인 지표 세 가지로 이루어집니다. 되돌리는 행동 자체보다 되돌린 결과를 확인하는 절차가 계획의 본체입니다.

아파트 각 세대의 두꺼비집 차단기를 번호 대신 안방 에어컨처럼 적어 두면 급할 때 어느 것을 내려야 하는지 바로 알 수 있는 것과 같습니다.

규칙 이름에는 적용 대상과 목적, 만든 날짜를 담아 이름만 보고도 무엇을 막는 규칙인지 짐작할 수 있게 합니다. 이름 옆에는 이 규칙이 막으려는 공격의 근거와, 걸리면 어떤 요청이 영향받는지를 한두 줄로 적어 둡니다. 규칙을 바꿀 때마다 바꾼 이유와 날짜를 같은 자리에 덧붙여, 나중에 이력만 읽어도 판단의 흐름이 이어지게 합니다.

정리하면 규칙 명명과 문서화는 이름에 대상과 목적을 담고, 목적과 근거, 영향 범위, 변경 이력을 규칙 옆에 남기는 일입니다. 이 기록이 있어야 다음 사람이 규칙을 두려움 없이 고치거나 지울 수 있습니다.

WAF API와 SDK

규칙을 코드로 만들고 바꾸는 방법

콘솔 화면에서 마우스로 규칙을 하나씩 만들다 보면 같은 규칙을 여러 계정에 똑같이 복제하기가 어렵고, 클릭 한 번을 잘못 눌러 차단 규칙이 느슨해져도 그 사실을 알아채기 어렵습니다. 이런 반복 작업과 실수를 줄이기 위해 AWS WAF는 규칙을 프로그램으로 다룰 수 있는 API(Application Programming Interface)와 SDK(Software Development Kit)를 함께 제공합니다.

이것은 본사와 지점이 있는 프랜차이즈 회사와 비슷합니다. 본사의 주문 접수 창구가 API인데, 지점은 정해진 양식에 어떤 규칙(rule)을 어떤 조건(statement)으로 판정하고 위반 시 어떤 동작(action)을 할지 적어 보내기만 하면 됩니다.

SDK는 그 창구에 맞춰 언어별로 미리 인쇄해 둔 주문서 세트로, Python이나 Java 같은 익숙한 언어로 요청을 조립하게 해 줍니다. 덕분에 지점마다 직원이 전화로 설명하지 않아도 같은 내용이 같은 형태로 전달됩니다.

결국 API는 Web ACL과 규칙, IP 집합(IPSet)을 HTTPS 요청으로 생성하고 수정하고 삭제하는 통로이며, SDK는 그 요청을 각 프로그래밍 언어의 함수로 감싸 준 도구입니다.

AWS CDK로 Web ACL 관리

프로그래밍 언어로 규칙을 조립하는 방법

YAML 템플릿이 수백 줄로 길어지면 비슷한 규칙을 반복해서 적어야 하고, 환경별로 값만 조금씩 다른 부분을 조건문 없이 관리하기가 번거롭습니다. AWS CDK(Cloud Development Kit)는 TypeScript나 Python 같은 프로그래밍 언어로 인프라를 적게 해 주는 도구로, 최종적으로는 CloudFormation 템플릿을 만들어 냅니다.

이것은 가구 공장의 모듈 조립과 비슷합니다. 다리와 상판과 서랍 같은 표준 부품을 조립품(construct)이라고 부르는데, 서랍 달린 책상을 한 번 조립품으로 만들어 두면 다음에는 그 조립품을 호출하는 한 줄로 같은 책상을 다시 만들 수 있습니다.

반복문으로 서랍 개수를 바꾸고 변수로 나사 규격을 바꾸는 것도 언어의 기능을 그대로 씁니다. 이렇게 조립한 결과는 synth라는 단계에서 표준 조립 설명서, 즉 CloudFormation 템플릿으로 출력됩니다.

결국 CDK는 construct라는 부품을 프로그래밍 언어로 조합해 인프라를 정의하고, 배포 직전에 CloudFormation 템플릿으로 변환해 적용하는 방식입니다.

운영 중인 Web ACL을 콘솔에서 곧바로 고치면 검토도 테스트도 없이 규칙이 서비스에 반영되고, 표현식 하나를 잘못 써서 정상 사용자까지 막히는 사고가 납니다. 이 문제를 줄이려면 규칙 변경을 코드 저장소에 올리고 CI/CD(지속적 통합과 지속적 배포) 파이프라인을 거쳐 배포하는 흐름을 만듭니다.

이것은 공장의 품질 검사 라인과 비슷합니다. 원자재에 해당하는 규칙 변경은 먼저 저장소에 pull request로 올라와 동료의 검토를 받고, 검사대에서는 문법 검사와 테스트로 그 규칙이 의도한 요청만 막는지 확인합니다.

검사를 통과한 제품은 시운전 라인인 스테이징 Web ACL에 먼저 설치되어 실제 트래픽 일부로 시험되고, 여기서도 문제가 없을 때에만 운영 라인으로 넘어갑니다. 문제가 생기면 이전 제품으로 되돌리는 롤백 절차가 함께 준비되어 있습니다.

결국 CI/CD에 WAF를 넣는다는 것은 규칙 변경을 코드로 저장소에 남기고, 자동 검증과 스테이징 시험과 승인과 배포와 롤백을 정해진 순서로 실행하는 체계를 갖추는 일입니다.

Web ACL 변경 이력 관리

결국 Web ACL 변경 이력 관리는 구성을 코드로 남겨 커밋과 diff로 비교하고, CloudTrail과 WAF 로그로 실제 변경과 판정 결과를 대조해 원인 추적과 되돌리기를 가능하게 하는 일입니다.

WAF 비용 최적화

요청 수와 규칙 수를 줄여 비용을 낮추는 방법

웹 서비스가 커지면 방어 장비에 들어오는 요청이 함께 늘어나고, 그 요청 하나하나를 검사할 때마다 비용이 붙습니다. 게다가 규칙을 이것저것 추가하면 검사 단위가 늘어나 청구서가 예상과 다르게 불어나는 일이 생깁니다. AWS WAF(웹 애플리케이션 방화벽)의 비용 최적화는 요청 수와 규칙 수를 함께 줄여, 방어 수준은 유지하면서 지출을 낮추는 작업입니다. 아파트 경비실을 떠올려 보시면 이해가 쉽습니다. 경비원은 들어오는 사람 수만큼 명단 확인 시간을 받고, 확인 항목이 하나 늘 때마다 추가 수당이 붙습니다.

그래서 관리사무소는 우선 경비실에 아예 오지 않아도 되는 방문객, 예를 들어 정문에서 이미 걸러진 택배 기사나 내부 직원은 굳이 재확인하지 않도록 동선을 정리합니다. 이것이 요청 수를 줄이는 일이고, 동시에 명단 확인 항목을 꼭 필요한 몇 개로 합치는 것이 규칙 수를 줄이는 일입니다. 여기에 한 번 확인한 방문객을 잠시 기억해 두는 장부를 두면 같은 사람을 반복해서 조회하지 않아도 됩니다. 정리하면, AWS WAF 비용은 처리한 요청 수와 배포한 규칙·규칙 그룹 수에 비례해 발생하므로, 캐시나 앞단 필터로 검사 대상 요청 자체를 줄이고 중복·불필요 규칙을 통합하며 로그 보관 기간과 범위를 조정하는 것이 핵심입니다.

WCU 한도 관리

용량 한도에 걸리지 않게 규칙을 설계하는 방법

규칙을 아무리 많이 만들어도 한 계정이 순간적으로 처리할 수 있는 검사 용량에는 한계가 있습니다. 트래픽이 몰리는 시간에 이 한도를 넘기면 새로 추가한 규칙이 배포되지 않거나 검사가 밀리는 상황이 생깁니다. AWS WAF는 이런 검사 능력을 WCU(WAF Capacity Unit)라는 단위로 환산해 관리하며, WCU 한도 관리는 이 용량 예산 안에서 규칙을 설계하는 방법입니다. 회사 출입 게이트의 검문 인력을 생각해 보시면 됩니다. 검문소에는 배치된 인원만큼 시간당 처리할 수 있는 통행량이 정해져 있고, 신분증 확인, 차량 수색, 서류 대조처럼 절차가 복잡한 검문일수록 더 많은 인원을 잡아먹습니다.

그래서 보안팀은 가장 중요한 검문 몇 개를 남기고, 이미 다른 곳에서 확인된 사항은 빼거나 여러 절차를 한 번에 처리하는 방식으로 인원을 아낍니다. 이렇게 절차마다 필요한 인원을 미리 계산해 두면, 새 검문을 추가할 때 남는 인원이 있는지 바로 판단할 수 있습니다. 결국 WCU는 규칙의 문자열 일치, 정규식, IP 집합 참조 같은 조건이 소모하는 용량을 수치로 드러낸 것이며, 비용이 큰 조건을 줄이고 규칙 그룹을 재사용하며 한도 여유를 주기적으로 확인하는 것이 안전한 운영의 기본입니다.

검사 규칙이 많고 복잡할수록 차로가 좁아지는 셈이고, 요청 수가 몰릴 때는 대기 행렬이 길어집니다. 반면 톨게이트를 여러 개 두거나, 미리 등록된 차량을 따로 빼 주면 흐름이 훨씬 가벼워집니다. 정리하면 WAF 검사는 요청마다 추가되는 고정 지연과 트래픽이 몰릴 때 커지는 대기 지연을 함께 만들 수 있으므로, 규칙 수와 순서를 단순하게 유지하고 정적 콘텐츠는 캐시로 우회시키는 설계가 응답 시간 관리의 핵심입니다.

WAF 장애의 유형

설정 오류·한도 초과·연동 문제를 구분하는 방법

대응도 각각 다릅니다. 오작동이면 감지 설정을 조정하고, 과부하면 회선을 나누고, 단선이면 연결을 복구해야 합니다. 정리하면 설정 오류는 차단·허용 규칙이나 예외 처리의 잘못으로 특정 요청만 막히는 형태로, 한도 초과는 WCU나 요청 한도에 부딪혀 배포·검사가 지연되는 형태로, 연동 문제는 로그나 다른 서비스와의 연결 실패로 나타나므로 로그와 지표를 층별로 확인하는 것이 진단의 출발점입니다.

오탐으로 인한 서비스 장애 대응

갑자기 정상 요청이 막힐 때 확인하는 순서

어느 날 갑자기 정상 사용자가 로그인도 결제도 하지 못한다는 신고가 들어옵니다. 서버 지표는 멀쩡한데 특정 요청만 차단되고 있다면, 그것은 공격을 막으려던 규칙이 정상 트래픽을 공격으로 잘못 판정한 오탐일 가능성이 큽니다. 오탐으로 인한 서비스 장애 대응은 정상 요청이 갑자기 막힐 때 무엇을 어떤 순서로 확인할지 정해 두는 절차입니다. 아파트 출입 시스템을 생각해 보시면 상황이 그려집니다. 주민 등록이 갱신되지 않아 정상 주민의 카드가 튕기기 시작하면, 경비실은 우선 차단 목록을 확인하고, 최근에 바뀐 출입 규칙이 있는지 보고, 문제가 된 카드만 예외로 풀어 준 뒤 원인을 정리합니다.

급할수록 문을 활짝 열어 두는 대신, 영향 범위를 좁혀 예외를 적용하는 것이 안전합니다. 확인 순서는 차단 로그에서 막힌 요청의 규칙 이름을 찾고, 최근 배포 이력을 대조하고, 해당 규칙만 일시적으로 세지 않도록 되돌리는 순서입니다. 결국 오탐 대응의 핵심은 WAF 로그에서 어떤 규칙이 어떤 조건으로 요청을 막았는지 먼저 특정하고, 영향받는 규칙만 좁게 예외 처리해 서비스를 먼저 살린 뒤, 규칙 조건을 보정하고 재발 감시 체계를 남기는 것입니다.

긴급 차단 해제 절차

잘못된 규칙을 즉시 무력화하는 방법

잘못 만든 규칙 하나가 정상 사용자까지 차단하면, 오픈 시간대에 서비스 전체가 멈춘 것처럼 보입니다. 긴급 차단 해제 절차는 Web ACL(웹 접근 제어 목록)에서 문제 규칙을 찾아 즉시 무력화하고 서비스부터 되살리는 대응 순서입니다.

아파트 정문 경비실에 비유하면 이해가 쉽습니다. 갑자기 모든 방문객을 막는 지시가 내려와 주민까지 못 들어오면, 먼저 그 지시를 쓴 종이를 찾아 책상에서 치우고 통행을 재개한 뒤 원인을 조사합니다.

Web ACL도 마찬가지로 어느 규칙이 요청을 막았는지 로그와 지표로 확인하고, 해당 규칙의 동작을 차단에서 통과로 바꾸거나 규칙 그룹 연결을 잠시 해제합니다. 규칙을 지우지 않고 우선순위가 낮은 임시 허용 규칙을 앞에 두는 방법도 같은 효과를 냅니다.

결국 이 절차의 핵심은 문제 규칙을 삭제하는 것이 아니라 영향 범위를 좁혀 즉시 무력화한 뒤, 로그로 원인을 확인하고 규칙을 고쳐 다시 켜는 것입니다.

Web ACL 백업

규칙 구성을 파일로 남겨 두는 방법

규칙을 오래 손대다 보면 잘 돌던 설정이 어느 순간 망가지고, 무엇이 달라졌는지 아무도 기억하지 못하는 상황이 생깁니다. Web ACL 백업은 규칙 구성 전체를 파일로 남겨 두어 언제든 비교하고 되돌릴 수 있게 하는 작업입니다.

아파트 관리사무소가 소방 설비 도면을 따로 보관하는 것과 같습니다. 도면이 있으면 공사 뒤에 어느 배관이 바뀌었는지 대조할 수 있고, 사고가 나면 원래 상태로 복원할 수 있습니다.

Web ACL도 JSON 형식의 규칙 정의를 내려받아 파일로 보관하고, 사람이 바꾸는 규칙은 변경 전후 내용을 함께 기록해 두는 것이 좋습니다. AWS에서는 get-web-acl 같은 API로 구성을 가져와 버전 관리 저장소에 커밋하는 방식이 흔히 쓰입니다.

정리하면 백업은 규칙 구성의 스냅샷과 변경 기록을 함께 남기는 일이며, 이것이 있어야 장애 때 빠르게 비교하고 복원할 수 있습니다.

Web ACL 복구

백업한 구성으로 되살리는 절차

백업 파일만 있고 되살리는 순서를 모르면, 장애 중에 손으로 규칙을 다시 만들다가 또 다른 설정을 빠뜨리기 쉽습니다. Web ACL 복구는 남겨 둔 구성과 이전 버전을 근거로 서비스 동작을 정상 상태로 되돌리는 절차입니다.

이사한 집에 가구 배치도를 붙잡고 원래 자리로 물건을 놓는 일과 비슷합니다. 배치도와 현재 집을 하나씩 대조해 빠진 물건을 채우고, 잘못 놓인 것을 옮기면 집이 원래 모습을 되찾습니다.

복구도 백업한 JSON과 현재 Web ACL을 대조해 빠진 규칙 그룹과 규칙 설정을 확인하고, 우선순위와 기본 동작까지 같은지 살핀 뒤 적용합니다. 되돌린 뒤에는 로그와 지표로 차단 비율이 원래 수준으로 돌아왔는지 확인해야 합니다.

결국 복구는 파일을 그대로 덮어쓰는 일이 아니라, 백업 구성과 현재 상태를 대조해 빠진 요소를 채우고 적용 뒤 동작까지 검증하는 절차입니다.

규칙 그룹 버전 고정

자동 업데이트로 인한 동작 변화를 막는 방법

규칙 그룹을 참조만 해 두면 관리하는 쪽에서 새 버전을 내보낼 때 내 서비스 동작도 조용히 바뀔 수 있습니다. 규칙 그룹 버전 고정은 참조할 버전을 명시해 자동 업데이트의 영향을 막는 방법입니다.

아파트에 들어오는 택배 규정이 본사에서 자주 바뀌는데, 우리 건물은 특정 날짜의 규정집을 정해 두고 그대로 쓰는 것과 같습니다. 규정집을 새로 받으려면 관리인이 직접 교체해야 하므로, 어느 날 갑자기 수령 조건이 달라지는 일이 없습니다.

Web ACL에서 규칙 그룹을 연결할 때 버전 번호를 지정하면 이후 새 버전이 나와도 연결은 그대로 유지되고, 바꾸고 싶을 때만 버전을 올려 교체합니다. 새 버전은 먼저 카운트 모드로 시험해 차단 대상이 얼마나 늘어나는지 확인하는 편이 안전합니다.

정리하면 버전 고정은 규칙 그룹의 변경 시점을 내가 정하게 만드는 장치이며, 변경은 시험과 검증을 거쳐 의도적으로만 반영해야 합니다.

한도 초과 오류 대응

WCU·규칙 수 한도에 걸렸을 때의 조치

규칙을 계속 추가하다 보면 어느 순간 저장이 거부되거나 배포가 실패하는데, 원인은 성능 한도 때문인 경우가 많습니다. 한도 초과 오류 대응은 Web ACL이 감당할 수 있는 규칙 수와 용량 한도를 넘지 않도록 구성을 줄이거나 나누는 작업입니다.

창고에 물건을 계속 쌓다가 선반 하중을 넘기면 창고 관리자가 입고를 막는 것과 같습니다. 물건을 버리는 대신 쓰지 않는 것을 정리하고, 무거운 것은 다른 창고로 옮기면 같은 공간에 더 많은 물건을 둘 수 있습니다.

Web ACL도 처리 용량을 WCU(웹 ACL 용량 단위)로 계산하므로, 조건이 겹치는 규칙을 합치거나 쓰지 않는 규칙을 지워 용량을 줄입니다. 그래도 부족하면 Web ACL을 나누어 연결하거나 관리형 규칙 그룹의 범위를 조정합니다.

결국 한도 초과는 오류를 무시할 문제가 아니라, WCU와 규칙 수를 기준으로 구성을 다이어트하거나 분산해야 하는 신호입니다.

연동 리소스 장애

CloudFront·ALB 장애가 WAF 동작에 미치는 영향

WAF는 요청을 직접 받는 장치가 아니라 앞단의 배포나 로드 밸런서에 붙어 동작하므로, 그 리소스가 흔들리면 WAF도 정상적으로 일할 수 없습니다. 연동 리소스 장애는 CloudFront나 ALB(응용 로드 밸런서)의 문제가 Web ACL 동작과 로그에 어떤 영향을 주는지 이해하는 일입니다.

아파트 정문 경비원이 검문을 하려 해도 정문 자체가 공사로 막혀 있으면 검문은커녕 출입 자체가 되지 않는 상황과 같습니다. 경비원이 아무리 성실해도 문이 고장 나면 통행이 멈추고, 우회 통로가 열리면 검문 없이 사람이 지나갈 수도 있습니다.

CloudFront 배포가 멈추거나 ALB가 비정상 상태가 되면 WAF는 차단할 요청을 받지 못해 로그가 비고 지표가 끊기며, 연결 설정이 어긋나면 차단이 적용되지 않는 경로가 생길 수 있습니다. 그래서 장애를 볼 때는 WAF 설정과 함께 연결된 배포와 로드 밸런서의 상태를 같이 확인해야 합니다.

정리하면 WAF는 연동 리소스를 통해 요청을 보는 구조이므로, 그 리소스의 장애는 곧 WAF의 사각지대이며 두 계층을 함께 점검해야 원인을 가릴 수 있습니다.

감사와 변경 추적

누가 언제 규칙을 바꿨는지 남기는 방법

새벽에 정상 사용자의 접속이 갑자기 차단되어 장애가 났는데, 아무도 누가 언제 규칙을 바꿨는지 답하지 못하면 복구는커녕 원인을 찾는 일부터 막막해집니다. 그래서 규칙을 바꾼 사람과 시각, 바뀐 내용을 자동으로 남기는 감사(audit)와 변경 추적(change tracking)이 필요하며, AWS WAF에서는 CloudTrail과 Web ACL 변경 기록을 함께 묶어 이 문제를 풉니다.

회사 규정집을 고치는 과정을 떠올려 보면, 규정집의 조항이 곧 Web ACL의 규칙이고 개정 요청서는 규칙을 바꾸는 API 호출입니다. 접수대 장부에 요청자 이름과 시각, 바뀐 조항이 적히듯 CloudTrail은 누가 어떤 권한으로 규칙 변경을 요청했는지 기록합니다.

개정 전후 사본을 함께 보관하듯 WAF는 변경 전후의 규칙 구성을 남겨 무엇이 달라졌는지 대조할 수 있게 합니다. 그 장부를 정해진 기간 동안 잠가 두어야 나중에 문제가 생겼을 때 되짚을 수 있고, 장부를 고칠 수 있으면 기록은 아무 의미가 없습니다.

결국 감사와 변경 추적은 Web ACL 규칙 변경을 CloudTrail과 변경 기록으로 남겨, 사고가 났을 때 원인과 책임 범위를 되짚을 수 있게 하는 운영 절차입니다.

사고 후 재발 방지

장애 회고에서 규칙과 절차를 개선하는 방법

같은 장애가 몇 달 간격으로 되풀이되는데 매번 임시로 규칙만 고치고 끝내면, 팀은 같은 자리에서 계속 넘어집니다. 그래서 장애를 겪은 뒤 원인과 대응을 정리하고 규칙과 절차 자체를 바꾸는 회고(post-incident review)와 재발 방지 대책이 필요합니다.

아파트 엘리베이터가 멈춘 뒤 관리사무소가 점검표를 다시 만드는 일을 생각하면, 사고 기록은 고장 일지, 원인 분석은 점검 결과표, 규칙 변경은 개정된 점검표, 절차 변경은 정비 업체 호출 순서입니다. 고장 일지에는 언제 어떤 증상이 있었는지 사실만 적고, 점검 결과표에서는 왜 그 부품이 마모됐는지 원인을 따로 짚습니다.

그 결과로 점검표에 빠져 있던 항목을 채워 넣고, 정비 업체를 부르는 순서도 실제 대응에서 막혔던 지점을 기준으로 고칩니다. 중요한 것은 개정된 점검표가 다음 점검 때 실제로 쓰이는지 확인하는 일이며, 쓰이지 않는 대책은 회고 문서만 예쁘게 남깁니다.

정리하면 사고 후 재발 방지는 장애 회고에서 원인을 사실과 구분해 분석하고, 그 결과를 WAF 규칙과 운영 절차에 반영해 다음 사고를 막는 활동입니다.

다중 계정 Web ACL 운영

여러 계정의 WAF 구성을 한곳에서 관리하는 방법

계정이 수십 개로 늘어나면 각 계정 담당자가 저마다 Web ACL을 만들고 규칙을 조금씩 다르게 설정해, 같은 공격에도 어떤 계정은 막고 어떤 계정은 뚫리는 상황이 생깁니다. 그래서 여러 계정의 WAF 구성을 한곳에서 관리하는 다중 계정 운영 방식이 필요하고, AWS에서는 Organizations로 계정을 묶고 중앙에서 규칙과 로그를 관리합니다.

여러 동이 있는 아파트 단지에서 각 동 경비실이 따로 순찰표를 쓰던 것을, 관리사무소의 통합 관제실 한 곳에서 모든 동의 순찰 상황을 보게 바꾸는 것과 같습니다. 각 동 경비실은 자기 건물 출입을 맡는 계정이고, 통합 관제실 화면은 모든 계정의 Web ACL과 로그를 모아 보는 중앙 관리 지점이며, 순찰 기준표는 공통으로 쓰는 규칙 묶음입니다.

관제실에서 기준을 정하면 각 동은 그 기준을 자기 상황에 맞게 적용하고, 새로 입주한 동이 생겨도 같은 방식으로 관리 대상에 들어옵니다. 다만 중앙에서 모든 것을 직접 조작하면 현장 대응이 느려지므로, 공통 기준은 중앙이 정하고 세부 예외는 계정이 맡는 경계를 정해 두어야 합니다.

결국 다중 계정 Web ACL 운영은 Organizations로 계정을 묶고 중앙에서 규칙과 로그를 관리하되, 공통 기준과 현장 예외의 경계를 정하는 방식입니다.

AWS Firewall Manager

아파트 관리사무소가 모든 세대에 소방 설비 기준을 내려보내고, 기준을 지키지 않는 세대를 찾아내 직접 시정 요구를 넣는 것과 같습니다. 관리 규정은 Firewall Manager 정책이고, 적용 대상 세대는 조직 안의 계정이나 특정 태그가 붙은 자원이며, 준수 여부를 확인하는 점검은 정책 위반 자원을 찾아내는 기능입니다.

새로 이사 온 세대도 관리 대상 목록에 들어오면 자동으로 같은 기준이 적용되고, 기준에 어긋난 자원은 목록에 올라 담당자가 바로 알 수 있습니다. 다만 정책은 강제이므로 예외가 필요한 계정은 미리 대상에서 빼 두어야 하고, 잘못된 정책 하나가 조직 전체에 퍼질 수 있다는 점도 감안해야 합니다.

정리하면 AWS Firewall Manager는 조직 단위로 WAF 정책을 내려보내고 위반 자원을 찾아내, 계정별 설정 차이에서 생기는 보안 구멍을 막는 서비스입니다.

보안 정책 자동 적용

기준서를 한 번 고치면 이미 깔린 노트북과 앞으로 들어올 노트북 모두 같은 설정으로 맞춰지고, 대상에서 빠진 자원은 목록으로 보고됩니다. 그래서 배포 전에는 정책을 적용할 범위를 태그와 조직 단위로 좁혀 확인하고, 배포 뒤에는 위반 자원 목록이 비어 있는지 보는 절차가 필요합니다.

결국 보안 정책 자동 적용은 정책에 규칙을 담아 대상 계정과 자원에 일괄 배포하고, 새 자원까지 같은 기준으로 맞추는 운영 방식입니다.

Shield와 WAF의 역할 분담

DDoS 방어와 웹 공격 방어의 경계

트래픽이 갑자기 폭증해 서비스가 멈추는 상황과, 트래픽 양은 정상인데 악성 요청만 골라 들어오는 상황은 원인도 대응도 다릅니다. 그래서 대량 트래픽을 흡수하고 걸러내는 DDoS 방어와 요청 내용을 검사하는 웹 공격 방어를 나눠 맡기며, AWS에서는 Shield와 AWS WAF가 이 역할을 나눕니다.

건물 경비를 생각하면, 차단봉과 경비 인력은 정문 앞 도로로 몰려오는 차량 행렬을 세우고, 출입구 직원은 들어오려는 사람의 신분과 소지품을 확인합니다. 도로 정체를 막는 차단봉이 Shield이고, 신분 검사를 하는 출입구 직원이 WAF이며, 차단봉이 있어도 신분 검사는 대신하지 못하고 그 반대도 마찬가지입니다.

그래서 차단봉이 서 있는 동안에도 출입구에서는 요청 한 건 한 건의 형식과 내용을 보고, 출입구 규칙으로는 감당할 수 없는 규모의 트래픽 폭주는 차단봉 쪽에서 흡수합니다. 두 장치가 같은 건물을 지키지만 보는 층위가 달라서, 한쪽 설정을 바꿨을 때 다른 쪽이 막아 주리라고 기대하면 안 됩니다.

정리하면 Shield는 대규모 트래픽 폭주를 흡수하는 DDoS 방어를, WAF는 요청 내용을 검사해 악성 웹 공격을 거르는 일을 맡는 역할 분담입니다.

Network Firewall과의 차이

VPC 수준 방화벽과 WAF를 함께 쓰는 구성

웹 서비스 앞에 방화벽을 하나만 두고 모든 차단을 그곳에서 처리하려 하면 규칙이 금세 엉킵니다. 네트워크 경계에서 걸러야 할 연결과 웹 요청 안에서 걸러야 할 공격은 보는 단위가 다르기 때문이며, 그래서 AWS는 VPC(Virtual Private Cloud) 수준의 Network Firewall과 애플리케이션 앞의 WAF(Web Application Firewall)를 나눠 제공합니다.

아파트 단지에 비유하면 Network Firewall은 단지 정문 경비실입니다. 정문에서는 어느 차량이 어느 동으로 들어가는지, 출입증이 있는지 같은 큰 흐름을 확인하고 출입 자체를 통제합니다. 반면 WAF는 각 동 로비의 안내데스크로, 방문 목적과 들고 온 물건의 내용까지 들여다보며 수상한 요청을 돌려보냅니다.

이처럼 Network Firewall은 IP와 포트, 프로토콜 단위로 통과 여부를 정하고, WAF는 HTTP 요청의 헤더와 본문, URL 패턴을 보고 악성 요청을 걸러 냅니다. 실무에서는 정문에서 한 번 거르고 로비에서 한 번 더 확인하듯, Network Firewall을 먼저 통과시킨 트래픽을 로드 밸런서나 CloudFront 앞의 Web ACL(접근 규칙 묶음)이 다시 검사하게 구성합니다. 역할을 계층으로 나눠 두면 규칙이 단순해지고 한쪽을 고쳐도 다른 쪽 판단이 흔들리지 않습니다.

GuardDuty 탐지와 WAF 차단 연결

탐지 결과를 자동 차단으로 이어 붙이는 방법

공격 징후는 로그 어딘가에 찍히지만, 사람이 그 로그를 보고 수동으로 차단 규칙을 만들기까지는 이미 피해가 커집니다. 그래서 AWS는 위협 탐지 서비스인 GuardDuty가 찾아낸 결과를 WAF의 차단 규칙으로 자동 연결하는 구성을 지원합니다.

아파트 단지로 비유하면 GuardDuty는 단지 곳곳의 CCTV를 보며 수상한 사람을 찾아내는 관제실입니다. 관제실은 이상 행동을 발견하면 정문 경비실에 무전을 넣고, 경비실은 그 사람의 출입을 즉시 막습니다. 이때 관제실이 혼자 문을 잠그려 하면 현장 판단이 늦어지므로, 탐지와 차단의 역할을 나눠 두는 것이 핵심입니다.

기술적으로는 GuardDuty가 위협 목록을 만들고 EventBridge로 사건을 흘려보내면, Lambda 같은 자동화가 그 내용을 읽어 WAF의 IP 집합(IP set)이나 규칙에 추가하는 흐름이 흔히 쓰입니다. 정리하면 GuardDuty는 무엇이 수상한지 판단하는 탐지 계층이고, WAF는 그 판단을 실제 요청 차단으로 집행하는 계층입니다. 다만 자동 차단은 오탐 시 정상 사용자를 막을 수 있으므로, 처음에는 차단 대신 카운트 모드로 관찰한 뒤 범위를 좁혀 가는 것이 안전합니다.

Security Hub와 규정 준수

WAF 설정을 보안 점검 항목으로 관리하는 방법

건물마다 소방 점검표를 붙여 두고 항목별로 통과 여부를 표시하는 모습을 떠올리면 쉽습니다. 점검표에는 소화기 위치, 비상구 잠금 여부처럼 미리 정해진 항목이 있고, 관리자는 각 호실을 그 항목에 맞춰 확인해 표시만 합니다. Security Hub의 보안 표준도 이와 같아서, 로깅이 켜져 있는지, 규칙이 비어 있지 않은지 같은 항목을 자동으로 확인하고 통과와 실패를 기록합니다. 여러 계정의 결과가 한 점검표에 모이므로 조직 전체에서 어느 계정의 WAF가 미흡한지 한눈에 비교할 수 있습니다.

즉 Security Hub는 WAF 자체를 차단하는 도구가 아니라, Web ACL의 로깅과 규칙, 연결 상태를 정해진 보안 표준에 비추어 지속적으로 채점하는 관리 계층입니다. 실패 항목은 자동 수정이나 알림으로 이어 붙일 수 있어, 점검이 문서가 아니라 운영 절차로 자리 잡습니다.

WAF Classic에서 옮겨온 이유

이전 세대 서비스가 폐기되고 현행 WAF로 통합된 배경

예전 WAF Classic 시절에는 규칙 하나를 만들 때마다 조건과 필터를 따로 등록하고 서로 연결해야 해서, 설정이 늘고 의도가 흐려졌습니다. 이 구조가 운영 부담과 실수 가능성을 키우자 AWS는 규칙을 한 문서 안에 선언적으로 적는 현행 WAF로 통합했습니다.

요리에 비유하면 예전 방식은 재료를 하나씩 따로 주문하고, 어느 팬에 언제 넣을지를 별도 표에 적어 두는 것과 같았습니다. 재료를 바꾸려면 주문서와 표를 함께 고쳐야 했고, 둘 중 하나만 고치면 요리가 엉뚱하게 나왔습니다. 현행 WAF는 재료와 조리 순서를 한 장의 레시피에 적듯, 규칙과 조건을 JSON 형태의 한 문서로 선언하면 그대로 평가됩니다. 그래서 규칙을 복사해 재사용하기 쉽고, 관리형 규칙 그룹을 그대로 붙이거나 버전을 관리하는 일도 자연스러워졌습니다.

결국 WAF Classic이 폐기되고 현행 WAF로 통합된 배경은, 흩어진 조건과 규칙을 하나의 Web ACL과 규칙 문서로 모아 일관되게 평가하기 위해서입니다. 이전 세대의 개념이 사라진 것이 아니라 같은 판단을 더 단순한 구조로 표현하게 된 변화로 보면 됩니다.

멀티 CDN·하이브리드 환경의 WAF

AWS 밖 오리진과 함께 쓰는 구성

서비스가 여러 CDN(content delivery network)을 쓰거나 일부 서버를 회사 건물에 두면, 보호 장치가 한 곳에만 있어 우회 경로가 생깁니다. 그래서 AWS 밖 오리진까지 포함한 전체 경로를 기준으로 WAF를 어디에 세울지 정해야 합니다.

출입구가 여러 개인 건물을 떠올리면 이해가 쉽습니다. 정문에만 경비를 세우면 옆문으로 들어오는 사람은 아무 검문도 받지 않습니다. 그래서 건물주는 모든 출입구에 같은 기준의 검문을 세우거나, 옆문을 아예 하나의 정문으로 합쳐 버립니다.

기술적으로는 CloudFront 배포마다 Web ACL을 붙여 모든 진입점에 같은 규칙을 적용하고, AWS 밖 오리진으로 직접 들어오는 경로는 네트워크 방화벽이나 오리진 쪽 인증으로 따로 막습니다. 정리하면 멀티 CDN·하이브리드 환경의 WAF는 특정 배포 하나를 지키는 것이 아니라, 모든 진입 경로에 같은 규칙을 걸고 우회로를 봉쇄하는 설계가 됩니다. 경로마다 규칙이 다르면 공격자는 가장 느슨한 문을 찾아가므로, 진입점 목록을 먼저 그려 두는 것이 출발점입니다.

실무 Web ACL 설계 종합

배운 요소를 모아 하나의 Web ACL을 설계하는 방법

여러 요소를 하나의 Web ACL(접근 규칙 묶음)로 합치는 순간, 규칙 순서와 예외 처리에서 판단이 갈립니다. 그래서 앞에서 배운 로깅, 관리형 규칙, 속도 제한, 자동 차단을 어떤 순서로 쌓을지 정하는 설계가 필요합니다.

경비반의 근무 매뉴얼을 만든다고 생각하면 순서가 자연스럽습니다. 먼저 누가 들어오는지 기록하는 출입 대장을 정하고, 그다음 알려진 출입 금지 명단과 대조하며, 마지막에 같은 사람이 반복해서 오가면 잠시 출입을 제한합니다. Web ACL도 같아서 로깅을 먼저 켜서 무엇이 들어오는지 보이게 하고, 관리형 규칙 그룹으로 알려진 공격 패턴을 거른 뒤, 속도 기반 규칙으로 과도한 요청을 제한합니다. 여기에 예외 IP 집합과 사용자 정의 규칙을 덧붙이고, 규칙은 기본 동작을 허용으로 두되 확신이 없는 규칙은 카운트로 먼저 관찰합니다.

결국 좋은 Web ACL은 규칙을 많이 넣는 것이 아니라, 로깅으로 관측하고 관리형 규칙과 속도 제한으로 거르며 차단은 검증된 뒤에 켜는 순서의 설계입니다. 이 순서를 지키면 오탐으로 서비스를 멈추지 않으면서도 필요한 방어를 차곡차곡 쌓을 수 있습니다.
