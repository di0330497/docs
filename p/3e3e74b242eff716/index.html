컨테이너 이미지는 읽기 전용 레이어가 쌓인 묶음이고, 이를 팀·서버 어디서나 같은 버전으로 내려받게 보관·배포하는 저장소가 레지스트리다.

1상대의 출발점 확인

기존에는 애플리케이션을 배포할 때 소스 코드와 라이브러리, 설정 파일들을 모두 각 서버에 직접 설치해야 했습니다. 개발 환경에서는 정상 작동하던 애플리케이션이 운영 서버에서는 라이브러리 버전 차이, OS 차이, 설정 누락 등으로 인해 다르게 작동하거나 실패했습니다. 이러한 "내 컴퓨터에서는 잘 되는데 저 서버에서는 안 됨" 문제를 반복 해결하기 위해, 애플리케이션과 그 실행에 필요한 모든 것(운영체제, 라이브러리, 설정)을 한 묶음으로 패키징하는 방식이 필요했습니다.

2질문 제기

3구조적 핵심 예시

컨테이너 이미지는 읽기 전용 레이어들의 적층입니다. 맨 아래 기본 OS 레이어 위에 필요한 라이브러리를 설치한 레이어, 그 위에 애플리케이션 코드를 넣은 레이어가 쌓입니다. 각 레이어는 이전 상태에서 달라진 부분만 저장하므로, 같은 기본 OS를 쓰는 여러 이미지는 그 부분을 중복 저장하지 않습니다. 이 완성된 이미지를 실행하면 컨테이너가 되는데, 이 이미지를 안전하게 보관하고 여러 서버에서 내려받게 하는 중앙 저장소가 레지스트리입니다.

4단계별 동작 과정

  2. 이미지 저장만들어진 이미지를 레지스트리에 push(업로드)하면, 중앙 저장소에 저장되고 버전(태그)이 기록됩니다.
  3. 이미지 배포어떤 서버나 배포 도구에서 그 이미지를 pull(내려받으면), 저장된 레이어 묶음 그대로 내려받아 컨테이너로 실행합니다.

3구조적 핵심 예시

  2. 보안과 규정 자동화저장된 이미지는 자동으로 암호화되고, 취약점 스캔(ECR image scanning)이 실행되며, IAM 정책과 리포지토리 정책으로 접근 권한을 중앙에서 통제합니다.

3구조적 핵심 예시

ECR 이미지의 전체 주소는 aws_account_id.dkr.ecr.region.amazonaws.com/repository_name:tag 형태입니다. 예: 123456789012.dkr.ecr.us-east-1.amazonaws.com/backend:v1.2.3. 앞의 aws_account_id.dkr.ecr.region.amazonaws.com 부분이 레지스트리 주소(어느 계정·리전의 저장소인지)이고, 뒤의 backend:v1.2.3 부분이 이미지 이름과 태그(그 저장소 안의 어느 이미지인지)입니다.

  2. 리포지토리와 태그 추가그 주소 뒤에 슬래시(/)를 붙이고 리포지토리 이름을 적으면, "이 저장소 안의 어느 이미지인지" 지정합니다. 콜론(:) 뒤에 태그(v1.0, latest 등)를 붙이면 그 리포지토리 안의 특정 버전을 가리킵니다.
  3. docker push/pull 실행Docker 클라이언트는 이 전체 URI를 보고, 먼저 어느 레지스트리로 가야 하는지 앞부분에서 파악한 후, 그 안의 리포지토리와 태그를 찾아서 이미지를 push하거나 pull합니다.

x86과 ARM처럼 여러 아키텍처용 이미지를 하나의 태그로 묶는 이미지 인덱스(매니페스트 리스트)와 ECR이 지원하는 매니페스트 포맷 이야기다.

1상대의 출발점 확인

일반적으로 x86 CPU용 이미지와 ARM(예: Apple M1) CPU용 이미지는 별도로 만들고, 별도의 태그로 저장해야 합니다. 사용자가 자신의 환경에 맞는 이미지를 일일이 선택해야 합니다.

2질문 제기

3구조적 핵심 예시

각 아키텍처별로 이미지를 빌드한 후, 이미지 인덱스(매니페스트 리스트)라는 메타데이터를 만들어 각 아키텍처 이미지를 가리키게 하면, 클라이언트가 pull할 때 자신의 아키텍처에 맞는 이미지를 자동으로 선택합니다.

4단계별 동작 과정

  1. 각 아키텍처별 이미지 빌드 및 태깅x86 이미지와 ARM 이미지를 각각 빌드하고, 각각 다른 태그로 ECR에 푸시합니다. 예: my-app:1.0-amd64, my-app:1.0-arm64
  2. 이미지 인덱스(매니페스트 리스트) 생성docker buildx build --platform linux/amd64,linux/arm64 -t my-app:1.0 . 같은 도구로 하나의 매니페스트 리스트를 만들어 모든 아키텍처 이미지를 가리키게 합니다.
  3. 하나의 태그로 ECR에 등록매니페스트 리스트를 my-app:1.0 태그로 ECR에 푸시하면, 클라이언트가 이 태그를 pull할 때 자신의 아키텍처에 맞는 이미지를 자동으로 받습니다.

Helm 차트와 OCI 아티팩트 푸시

2질문 제기

컨테이너 이미지뿐 아니라 Helm 차트, SBOM 같은 다양한 아티팩트도 ECR 하나에서 통합으로 관리할 수 있을까?

3구조적 핵심 예시

OCI(Open Container Initiative) 표준 포맷을 따르는 모든 아티팩트가 ECR에 푸시 가능합니다. 예를 들어 Helm 차트를 OCI 포맷으로 패키징한 후 helm push my-chart-0.1.0.tgz oci://123456789.dkr.ecr.region.amazonaws.com/charts로 ECR에 올릴 수 있습니다.

4단계별 동작 과정

  1. OCI 아티팩트 패키징Helm 차트, Terraform 모듈 등을 OCI 표준 포맷으로 패키징합니다. (Helm은 3.7 이상에서 기본 지원)
  2. ECR에 푸시패키징된 아티팩트를 oci://REGISTRY_URL/REPOSITORY:TAG 형식으로 ECR에 업로드합니다.
  3. ECR에서 배포필요할 때 ECR에서 아티팩트를 다운로드하고, Helm이나 Terraform 같은 배포 도구로 사용합니다.

이미지 풀과 레이어 다운로드

클라이언트가 매니페스트를 받고 필요한 레이어만 서명된 URL로 내려받는 과정이 이미지 풀이며, 이미 가진 레이어는 다시 받지 않는다.

1상대의 출발점 확인

이미지를 pull할 때 단순히 전체 이미지 데이터를 받는다면, 이미 로컬에 있는 레이어도 다시 받아야 하므로 불필요한 다운로드가 발생합니다.

2질문 제기

필요한 레이어만 효율적으로 다운로드하고, 이미 있는 레이어는 건너뛸 수 있을까?

3구조적 핵심 예시

클라이언트가 매니페스트(이미지의 구성 정보)를 먼저 받아서 필요한 레이어 목록을 확인한 후, 각 레이어를 개별적으로 다운로드합니다. ECR이 발급한 서명된 URL(임시 다운로드 링크)로만 다운로드되므로, 이미 있는 레이어는 체크섬으로 검증해 다시 받지 않습니다.

4단계별 동작 과정

  1. 매니페스트 요청 및 수신클라이언트가 GET /v2/REPOSITORY/manifests/TAG로 이미지의 메타데이터(구성, 레이어 목록)를 ECR에서 받습니다.
  2. 필요한 레이어 식별매니페스트에 나열된 각 레이어의 체크섬과 크기를 확인하고, 로컬에 이미 있는지 검증합니다.
  3. 서명된 URL로 레이어 다운로드없는 레이어만 ECR이 제공한 서명된 URL로 개별 다운로드합니다. (이미 있으면 스킵)

5본질 요약

docker pull이 먼저 매니페스트로 필요한 레이어를 파악한 후 개별적으로 다운로드하므로, 이미 있는 레이어를 재다운로드하지 않아 대역폭과 시간을 절약한다는 것

1상대의 출발점 확인

비슷한 여러 이미지를 ECR에 저장할 때, 같은 레이어(OS 기본 이미지, 공통 라이브러리 등)가 여러 번 중복으로 저장됩니다. 다른 리포지토리에 같은 레이어가 있어도 인식하지 못하고 다시 업로드해야 합니다.

2질문 제기

같은 레이어를 여러 리포지토리에서 재사용할 때 중복 저장을 피할 수 있을까?

3구조적 핵심 예시

새 이미지를 푸시할 때, 각 레이어마다 같은 레지스트리 내의 다른 리포지토리에 이미 있는 레이어가 있는지 확인하고, 있으면 그것을 참조만 걸어서 재사용합니다. 실제로 레이어 데이터를 다시 업로드하지 않습니다.

4단계별 동작 과정

  1. 레이어 존재 여부 확인새 이미지의 각 레이어에 대해, 같은 ECR 레지스트리의 다른 리포지토리에 체크섬이 일치하는 레이어(blob, 이미지의 바이너리 데이터)가 있는지 조회합니다.
  2. 참조 링크 생성해당 레이어가 존재하면, 새 이미지에서도 같은 blob을 가리키도록 링크를 생성합니다. (blob mounting)
  3. 업로드 생략이미 존재하는 blob에 대해서는 업로드 단계를 건너뛰므로, 업로드 시간과 스토리지 용량을 절약합니다.

5본질 요약

blob mounting으로 같은 ECR 레지스트리 내의 다른 리포지토리에 있는 레이어를 재참조하므로, 중복 저장과 불필요한 업로드 시간을 없앨 수 있다는 것

태그 불변성(immutability)과 예외 필터

한 번 쓴 태그를 덮어쓰지 못하게 리포지토리에 걸어 두는 설정이며, 특정 태그 접두사만 예외로 덮어쓰기를 허용하는 필터도 함께 지정할 수 있다.

1상대의 출발점 확인

리포지토리에 v1.0, v2.0 같은 중요한 버전 태그를 정해 놓으면, 팀원이 실수로 다른 이미지를 같은 태그로 덮어쓸 수 있다. 이러면 버전 관리가 뒤죽박죽되고 어떤 이미지가 실제 v1.0인지 추적할 수 없게 된다.

ECR이 IAM과 맞물리는 방식

ECR의 모든 API 호출은 IAM 자격 증명으로 인증되고, IAM 정책과 리포지토리 정책이 함께 평가되어 허용 여부가 결정된다.

1상대의 출발점 확인

AWS 계정에서 누가 ECR 리포지토리를 만들고, 누가 이미지를 푸시하고, 누가 이미지를 pull 할 수 있을지 정해야 한다. 권한 체계를 만들려면 IAM이 ECR과 어떻게 상호작용하는지 이해해야 한다.

2질문 제기

ECR의 모든 작업 권한은 어떻게 결정될까?

3구조적 핵심 예시

IAM 사용자가 ECR 리포지토리에 이미지를 푸시하려 하면, 먼저 그 사용자에게 할당된 IAM 정책이 "ecr:PutImage" 같은 ECR 권한을 포함하는지 확인되고, 동시에 리포지토리 정책도 "이 사용자의 호출을 허용하는가"를 평가한다. 둘 다 허용해야 푸시가 성공한다.

4단계별 동작 과정

  1. IAM 자격 증명 확인ECR API 호출을 시도한 주체(사용자, 역할, 서비스 계정 등)를 식별한다.
  2. IAM 정책 평가그 주체에게 할당된 IAM 정책을 확인해 필요한 ECR 권한이 있는지 판단한다.
  3. 리포지토리 정책 평가리포지토리 정책을 확인해 그 주체의 호출을 명시적으로 허용하는지 판단하고, 둘 다 허용해야 API 호출이 성공한다.

사용자·역할에 붙이는 정책으로 어떤 ECR 작업을 허용할지 정하며, AWS가 미리 만든 관리형 정책이나 리소스 태그 조건으로 범위를 좁힐 수 있다.

1상대의 출발점 확인

기존에는 AWS 사용자나 역할을 만든 후 ECR에 접근할 때마다 "이 사용자가 뭘 할 수 있는가"를 수동으로 관리했다. ECR 정책이 없으면 모든 사용자가 모든 리포지토리에 push/pull 할 수 있거나, 아니면 전혀 못 하게 된다.

2질문 제기

특정 사용자나 역할이 ECR에서 정확히 어떤 작업만 수행할 수 있게 제한할 수 있는가?

3구조적 핵심 예시

IAM 정책(Identity and Access Management 정책, 즉 사용자나 역할에 붙이는 규칙)을 작성해서 사용자 또는 역할에 연결한다. 예를 들어 "개발자 역할"이 "특정 리포지토리에서만 이미지를 pull 할 수 있다"는 정책을 붙이면, 그 역할로 로그인한 누구든 그 범위 내에서만 작동한다.

4단계별 동작 과정

  1. 정책 작성JSON 형식으로 Action(pull, push 같은 ECR 작업), Resource(어떤 리포지토리), Effect(허용/거부) 등을 정의한다.
  2. 정책 연결만든 정책을 사용자, 그룹, 역할에 붙인다. AWS 관리형 정책(AWS가 미리 만든 일반적인 정책)을 직접 쓸 수도 있고, 커스텀 정책을 만들어 붙일 수도 있다.
  3. 태그 조건리소스 태그(Key=Environment, Value=prod 같은 라벨)를 조건으로 추가해서 정책 범위를 더 좁힐 수 있다. 예를 들어 "prod 태그가 붙은 리포지토리에서만 pull"이라고 제한할 수 있다.

리포지토리 정책 - 리소스 기반 권한

리포지토리 자체에 붙이는 JSON 정책으로, 누가 그 리포지토리에 push/pull 할 수 있는지를 리소스 쪽에서 직접 지정한다.

1상대의 출발점 확인

지금까지는 "사용자나 역할 입장에서 뭘 할 수 있는가"를 정의했다. 하지만 반대 방향도 있다. "리포지토리 입장에서 누가 이 리포지토리를 건드릴 수 있는가"를 정하는 것도 필요하다. 그렇지 않으면 리포지토리마다 일일이 사용자 정책을 수정해야 한다.

2질문 제기

리포지토리 자체에 누가 push/pull 할 수 있는지를 직접 지정할 수 있는가?

3구조적 핵심 예시

리포지토리에 JSON 정책을 붙인다. 이 정책은 "Principal: arn:aws:iam::계정123:user/alice는 push와 pull을 허용" 같은 방식으로, 어떤 주체(사용자, 역할, 다른 계정 등)가 이 특정 리포지토리에서 무엇을 할 수 있는지를 정의한다.

4단계별 동작 과정

  1. 정책 작성누가(Principal, 사용자 ARN 같은 신원), 무엇을(Action, pull/push), 어느 리소스에(이 리포지토리), 허용할지(Effect: Allow)를 JSON으로 정의한다.
  2. 리포지토리에 붙임이 정책을 리포지토리 자체에 연결하면, 조건을 만족하는 사람들이 그 리포지토리에 접근할 수 있다.
  3. 우선순위IAM 정책(사용자 정책)과 리포지토리 정책(리소스 정책) 중 하나라도 거부하면 접근이 막힌다. 양쪽이 모두 허용해야 작동한다.

2질문 제기

3구조적 핵심 예시

4단계별 동작 과정

  1. 정책 작성Principal 필드에 다른 계정의 ARN을 넣고, Action에 "ecr:GetDownloadUrlForLayer", "ecr:BatchGetImage" 등 pull 관련 권한을 지정한다.
  2. 리포지토리에 붙임이 정책을 리포지토리에 연결하면, 해당 계정의 자격이 있는 사용자가 pull 할 수 있다.

서비스 연결 역할과 혼동된 대리인 방지

ECR이 복제 등 작업을 대신 수행하도록 만들어진 전용 IAM 역할과, 다른 서비스가 내 리소스를 오용하지 못하게 막는 조건 키 사용법이다.

1상대의 출발점 확인

ECR 복제 같은 작업을 할 때 ECR 서비스 자체가 내 대신 다른 계정의 리포지토리에 접근해야 한다. 이때 ECR이 누구 신분으로 그 일을 하는가가 중요했다. 기존에는 "누가 ECR을 대신 작동시키는가"를 명확히 제어하지 않으면, ECR이 과도한 권한을 갖거나 다른 서비스가 내 리소스를 오용할 위험이 있었다.

2질문 제기

ECR이나 다른 서비스가 내 리소스를 건드릴 때, 어떤 신분을 가지고 어디까지만 행동하도록 제한할 수 있는가?

3구조적 핵심 예시

서비스 연결 역할(Service Linked Role, AWS 서비스가 사용하기 위해 미리 만들어진 IAM 역할)을 사용한다. ECR 복제라면 "ECR이 사용할 수 있는 역할"을 지정해서, ECR이 그 역할의 권한 범위 내에서만 다른 계정에 접근하게 한다. 동시에 조건 키(Condition)를 정책에 추가해서 "arn:aws:iam::다른계정:root 라는 주체만 내 리소스에 접근 가능" 같은 식으로 혼동된 대리인(Confused Deputy Problem, 서비스가 잘못된 계정에 접근하는 문제)을 방지한다.

4단계별 동작 과정

  1. 서비스 연결 역할 생성AWS가 미리 정의한 서비스 연결 역할(예: AWSServiceRoleForECRReplication)을 활성화한다. 이 역할에는 ECR이 필요로 하는 기본 권한이 이미 들어있다.
  2. 신뢰 정책 설정서비스 연결 역할의 신뢰 정책(이 역할을 누가 맡을 수 있는가)을 확인해서 ECR 서비스만 이 역할을 쓸 수 있도록 제한한다.
  3. 조건 키로 추가 제한정책에 "Condition": {"StringEquals": {"aws:SourceAccount": "123456789012"}} 같은 조건을 붙여서, 복제를 요청한 계정이 정확히 내 계정인지를 검증한다. 이렇게 하면 다른 계정이나 서비스가 내 리소스를 잘못 건드릴 수 없다.

개발 중에는 이미지를 계속 만들고 리포지토리에 쌓는다. 하지만 시간이 지나면 옛날 이미지들이 쌓여서 저장 비용이 늘어난다. 기존에는 관리자가 수동으로 "이 이미지는 이제 안 쓰니까 삭제해야겠다"고 판단해서 일일이 삭제해야 했다.

3구조적 핵심 예시

라이프사이클 정책은 리포지토리에 규칙을 붙여서 "태그가 없는 이미지 중 7일 이상 된 것은 자동으로 지워" 같은 조건을 설정한다. ECR이 매일 조건을 확인해서 맞는 이미지를 찾으면 자동으로 삭제한다.

4단계별 동작 과정

  1. 규칙 정의어떤 이미지를 삭제할지를 tagStatus(태그 있음/없음), countType(개수 기준/일수 기준), 기준값(예: 7일 또는 10개) 등으로 정의한다.
  2. 우선순위 적용여러 규칙이 있으면 rulePriority(숫자가 작을수록 먼저 실행) 순서대로 적용된다. 높은 우선순위 규칙이 "보관"으로 표시한 이미지는 낮은 우선순위 규칙의 삭제 대상이 될 수 없다.
  3. 자동 실행정책을 리포지토리에 붙이면 ECR이 정기적으로 확인해서 조건 맞는 이미지를 action(지우기 또는 만료 표시)에 따라 처리한다.

스캔 결과는 콘솔·CLI로 확인하고, EventBridge 이벤트로 스캔 완료 알림을 자동화하며 스캔 실패 시 원인을 진단한다.

→ 09-01 참조

1상대의 출발점 확인

ECR에서 이미지를 스캔하면 취약점 결과가 생기는데, 그 결과를 누가 확인할지, 언제 확인할지 정하기 어렵습니다. 매번 콘솔에 들어가 결과를 수동으로 확인하거나, CLI를 직접 실행해야 합니다. 중요한 취약점이 발견되어도 누구에게도 알림이 가지 않으므로, 발견되는 즉시 팀에 알릴 수 없습니다.

2질문 제기

스캔 결과를 간단히 조회하고, 중요한 취약점이 발견되면 자동으로 팀에 알림을 보내려면 어떻게 해야 할까요?

3구조적 핵심 예시

ECR 스캔이 완료되면, 콘솔이나 aws ecr describe-image-scan-findings 명령으로 취약점 목록(CVE 번호, 심각도)을 즉시 조회할 수 있습니다. 동시에 그 스캔 이벤트를 EventBridge로 보내도록 설정하면, EventBridge가 규칙에 따라 SNS 메시지 발송이나 Lambda 함수 실행 같은 자동화를 트리거합니다.

4단계별 동작 과정

  1. 스캔 결과 저장스캔이 끝나면 ECR이 취약점 정보(개수, 심각도, CVE ID, CVSS 점수 등)를 리포지토리에 저장합니다.
  2. 콘솔·CLI 조회ECR 콘솔의 리포지토리 탭에서 직접 취약점 목록을 보거나, describe-image-scan-findings CLI 명령으로 JSON 형태의 상세 정보를 받습니다.
  3. EventBridge 이벤트 발송스캔 완료 이벤트가 EventBridge로 발행되면, 설정된 규칙(예: "Critical 심각도 취약점이 발견됨")에 맞는 대상으로 자동 알림을 보냅니다.

5본질 요약

스캔 결과를 조회하는 여러 방식(콘솔, CLI)과 자동 알림 수단(EventBridge)을 함께 제공해서, 취약점을 빠르게 파악하고 문제 해결을 시작할 수 있게 하는 것

관리형 서명과 AWS Signer

관리형 서명은 ECR이 AWS Signer와 연동해 푸시된 이미지에 디지털 서명을 자동으로 붙여 출처를 증명하게 해준다.

1상대의 출발점 확인

이미지를 배포할 때, 그 이미지가 정말 우리가 빌드한 것인지 확인할 방법이 없습니다. 누군가 이미지를 변조했거나 다른 사람이 같은 태그로 이미지를 푸시했어도 구분할 수 없습니다. 이미지의 출처를 증명하려면 별도로 서명 메커니즘을 만들거나 외부 도구를 연동해야 합니다.

2질문 제기

ECR에 푸시되는 이미지가 신뢰할 수 있는 출처에서 왔다는 것을 자동으로 증명할 수 있을까요?

3구조적 핵심 예시

ECR에서 관리형 서명 기능을 켜면, 이미지가 푸시될 때 AWS Signer 서비스가 자동으로 그 이미지에 디지털 서명을 붙입니다. 서명은 암호화된 인증서로 생성되며, 나중에 배포 시 그 서명이 유효한지 검증하면 이미지의 진정성을 확인할 수 있습니다.

4단계별 동작 과정

  1. 관리형 서명 활성화ECR 리포지토리에서 서명 설정을 켜면, AWS Signer와의 연동이 시작됩니다.
  2. 이미지 푸시 시 자동 서명개발자가 이미지를 푸시하면, Signer가 자동으로 이미지 다이제스트(이미지의 고유 해시)에 디지털 서명을 붙이고 ECR에 저장합니다.
  3. 배포 전 서명 검증쿠버네티스나 컨테이너 런타임에서 배포 정책을 설정해 Signer의 인증서로 서명을 검증하면, 신뢰할 수 없는 이미지는 배포되지 않습니다.

5본질 요약

이미지가 ECR에 도착하는 순간 자동으로 디지털 서명을 붙여서, 그 이미지가 신뢰할 수 있는 빌드 파이프라인에서 나왔다는 것을 증명하는 것

수동 서명(Notation)과 서명 검증

Notation CLI로 이미지에 직접 서명을 붙이고, 배포 전에 그 서명이 신뢰할 수 있는 것인지 검증한다.

→ 08-06 참조

1상대의 출발점 확인

관리형 서명은 ECR이 자동으로 해 주지만, 서명 방식을 더 세밀하게 제어하거나 특정 조건에서만 서명을 하고 싶을 수 있습니다. 또는 ECR 외부에서 빌드된 이미지에 서명을 붙이고 싶을 수도 있습니다. 이런 경우 Notation 같은 수동 서명 도구를 사용해야 합니다.

2질문 제기

개발자가 직접 이미지에 서명을 붙이고, 그 서명이 신뢰할 수 있는지 검증하려면 어떻게 해야 할까요?

3구조적 핵심 예시

Notation CLI를 사용하면, 개발자가 명령어로 ECR의 이미지에 서명을 붙일 수 있습니다. 예를 들어 notation sign 123456789012.dkr.ecr.us-east-1.amazonaws.com/my-repo:latest 명령을 실행하면, 개발자의 개인 키(signing key)로 그 이미지에 서명이 생성되고 ECR에 저장됩니다.

4단계별 동작 과정

  1. Notation CLI 설정개발자 환경에 Notation을 설치하고, 서명에 사용할 개인 키와 인증서를 준비합니다.
  2. 이미지에 서명 붙이기Notation 명령으로 ECR의 특정 이미지를 지정해 서명을 생성합니다. 서명은 이미지 다이제스트를 기준으로 생성되며, ECR에 메타데이터로 저장됩니다.
  3. 배포 전 서명 검증배포 시스템(쿠버네티스 정책이나 런타임)이 Notation으로 서명을 검증하면, 신뢰할 수 없는 서명은 배포가 차단됩니다.

개발자가 자신의 개인 키로 이미지에 직접 서명을 붙여서, 그 이미지가 신뢰할 수 있는 사람(또는 엔티티)에 의해 승인되었음을 증명하는 것

9레지스트리 차원의 자동화 — 복제·풀스루 캐시·생성 템플릿09-01

복제(replication)가 하는 일과 그 한계

레지스트리에 푸시된 이미지를 다른 리전이나 다른 계정의 ECR로 자동 복사해 주는 기능으로, 규칙 설정 이후 새로 푸시된 이미지에만 적용된다.

1상대의 출발점 확인

ECR은 각 AWS 리전마다 별도의 레지스트리입니다. 한 리전에 푸시된 이미지가 다른 리전에도 필요하면, 사용자가 직접 각 리전에 푸시하거나 별도의 복사 메커니즘을 만들어야 합니다. 계정이 여러 개라면 각 계정의 ECR에도 이미지를 옮겨야 하는데, 이 모든 것을 수동으로 관리하기는 번거롭습니다.

2질문 제기

한 리전의 ECR에 푸시된 이미지를 자동으로 다른 리전이나 다른 계정의 ECR로 복사하려면 어떻게 해야 할까요?

3구조적 핵심 예시

ECR 복제 기능을 켜고 규칙을 설정하면, 예를 들어 "모든 prod-* 리포지토리의 이미지를 us-east-1에서 eu-west-1로 자동 복사"하도록 정할 수 있습니다. 그 다음부터 prod-web:v1.0 이미지를 us-east-1 ECR에 푸시하면, ECR이 자동으로 같은 이미지를 eu-west-1 ECR에도 복사합니다.

4단계별 동작 과정

  1. 복제 규칙 설정원본 리전의 ECR 레지스트리에서 복제 규칙을 만들고, 어떤 리포지토리를 어디로 복사할지(다른 리전 또는 다른 계정)를 정합니다.
  2. 이미지 푸시개발자가 이미지를 원본 리전에 푸시합니다.
  3. 자동 복제 실행규칙에 맞는 이미지가 감지되면, ECR이 그 이미지를 대상 리전이나 대상 계정의 ECR에 자동으로 복사합니다.

5본질 요약

한 번 설정한 복제 규칙에 따라, 그 이후로 푸시되는 이미지 중에서 규칙에 맞는 것들을 자동으로 다른 리전이나 다른 계정으로 배포하는 것

복제 구성: 규칙·필터·대상

레지스트리 단위로 복제 규칙을 만들고 리포지토리 이름 프리픽스 필터와 대상 리전·계정을 지정해 어떤 이미지를 어디로 보낼지 정하는 설정이다.

1상대의 출발점 확인

복제 기능이 있다는 것을 알아도, 구체적으로 어떤 이미지를 어디로 어떻게 복사할지 정하기는 복잡합니다. 모든 이미지를 모든 리전으로 보낼 필요는 없고, 특정 리포지토리나 특정 이미지 태그만 복사하고 싶을 수 있습니다. 또한 어느 리전에, 또는 어느 계정에 복사할지도 정해야 합니다.

2질문 제기

복제 규칙에서 어떤 이미지를 선별하고, 어디로 보낼지를 정확하게 지정하려면 어떻게 해야 할까요?

3구조적 핵심 예시

복제 구성에서 규칙을 만들 때, 필터 섹션에서 리포지토리 이름 프리픽스(예: "prod-")와 이미지 태그 필터(예: "v*" 정규식)를 지정하고, 대상 섹션에서 대상 리전(us-east-1, eu-west-1 등)과 대상 계정 ID를 선택합니다. 이렇게 설정하면 "prod-로 시작하는 리포지토리이면서 v로 시작하는 태그"인 이미지만 지정된 리전과 계정으로 복사됩니다.

4단계별 동작 과정

  1. 규칙 생성ECR 레지스트리 설정에서 복제 규칙을 추가하고, 규칙의 이름과 설명을 지정합니다.
  2. 필터 지정리포지토리 이름 필터(프리픽스나 정규식)와 이미지 태그 필터를 입력해서, 어떤 이미지가 이 규칙에 맞을지 정합니다.
  3. 복제 대상 지정대상 리전 목록과 대상 AWS 계정 ID를 지정하면, 규칙에 맞는 이미지가 그 모든 대상으로 자동 복제됩니다.

교차 계정 복제 권한 — 어느 계정에 무엇을 두는가

복제 소스 계정은 복제 규칙을, 대상 계정은 소스 계정의 복제를 허용하는 레지스트리 권한 정책을 각각 가지고 있어야 교차 계정 복제가 동작한다.

→ 05-01 참조

1상대의 출발점 확인

복제 규칙을 만들고 대상 계정을 지정했다고 해서 자동으로 다른 계정의 ECR에 이미지가 들어가지 않습니다. AWS 계정은 서로 독립적이므로, 한 계정이 다른 계정의 리소스에 접근하려면 명시적인 권한이 필요합니다. 권한 설정 없이는 "접근 거부" 에러가 발생하고 복제가 실패합니다.

2질문 제기

복제 소스 계정과 대상 계정 사이에서 이미지를 주고받기 위한 권한을 어떻게 설정해야 할까요?

3구조적 핵심 예시

Account A(소스)에서 Account B(대상)로 복제할 때, Account A의 ECR 레지스트리 정책에는 "이 레지스트리에 복제 규칙을 설정한다"는 권한이 필요하고, Account B의 ECR 레지스트리 정책에는 "Account A가 우리 레지스트리에 이미지를 복사하도록 허용한다"는 권한이 필요합니다. 두 가지 권한이 모두 갖춰져야만 복제가 동작합니다.

4단계별 동작 과정

  1. 소스 계정 준비Account A의 ECR 레지스트리 권한 정책에서 복제 권한을 설정합니다. 보통 이 정책은 Account A 자신이 복제를 구성할 수 있도록 허용하는 것입니다.
  2. 대상 계정 권한 설정Account B의 ECR 레지스트리 권한 정책에 "Account A의 principal(보통 루트 계정 또는 역할)이 Account B의 ECR에 이미지를 푸시하고 저장할 수 있다"는 권한 문장을 추가합니다.
  3. 복제 실행두 계정의 권한 설정이 완료되면, Account A의 복제 규칙에 따라 이미지가 Account B로 자동 복사됩니다.

5본질 요약

소스 계정과 대상 계정이 서로 명시적인 권한을 주고받음으로써, 신뢰할 수 있는 계정 간에만 이미지 복제가 일어나도록 제어하는 것

풀스루 캐시 규칙 — 업스트림 레지스트리를 내 레지스트리에 동기화

Docker Hub 같은 외부(업스트림) 레지스트리 이미지를 처음 당길 때 내 프라이빗 레지스트리에 자동으로 캐시 리포지토리를 만들어 저장하고 이후 동기화해 주는 규칙이다.

1상대의 출발점 확인

Docker Hub 같은 외부 레지스트리에서 이미지를 직접 당겨올 때마다 네트워크 요청이 발생하고, 같은 이미지를 여러 번 당기면 반복 다운로드로 인한 지연이 생긴다.

2질문 제기

외부 레지스트리의 이미지를 처음 한 번만 당겨서 자동으로 내 프라이빗 레지스트리에 저장하고, 이후로는 내부에서 빠르게 재사용할 수 있을까?

3구조적 핵심 예시

ECR 풀스루 캐시는 docker pull 요청이 오면, 먼저 규칙에 설정된 업스트림 레지스트리에서 이미지를 가져오고, 그것을 규칙의 프리픽스 경로로 ECR 리포지토리에 캐시 리포지토리를 자동으로 생성해서 저장한다.

4단계별 동작 과정

  1. 규칙 생성업스트림 레지스트리(Docker Hub, Quay.io 등)와 ECR에 저장할 프리픽스를 지정해 풀스루 캐시 규칙을 만든다.
  2. 첫 요청 시 캐시규칙의 프리픽스 경로로 docker pull 요청이 들어오면, ECR은 업스트림 레지스트리로 이미지를 가져와 자동으로 프리픽스 리포지토리를 생성하고 저장한다.
  3. 이후 재사용다음 요청부터는 ECR 내부의 캐시 이미지를 바로 제공하므로 네트워크 지연 없이 빠르게 이미지를 사용할 수 있다.

인증이 필요한 업스트림 레지스트리는 자격 증명을 ecr-pullthroughcache/ 접두어의 Secrets Manager 시크릿에 저장하고, ECR이 이를 읽을 수 있는 권한을 부여해 사용한다.

1상대의 출발점 확인

공개 레지스트리(Docker Hub 기본 이미지 등)에서는 인증 없이 이미지를 당겨올 수 있지만, 비공개 업스트림 레지스트리(회사 프라이빗 Quay.io 등)의 이미지를 당기려면 사용자명과 암호 같은 자격 증명이 필요하다.

2질문 제기

풀스루 캐시 규칙이 인증 정보 없이 비공개 업스트림 레지스트리에 접근할 수 없을 때, 어떻게 안전하게 자격 증명을 ECR에 제공할 수 있을까?

3구조적 핵심 예시

Secrets Manager라는 AWS 보안 저장소에 업스트림 레지스트리의 사용자명과 암호(또는 토큰)를 ecr-pullthroughcache/ 접두어로 저장하고, ECR이 풀스루 캐시를 실행할 때 Secrets Manager 읽기 권한을 통해 그 자격 증명을 가져와 업스트림에 인증한다.

4단계별 동작 과정

  1. 시크릿 저장업스트림 레지스트리의 인증 정보(사용자명, 암호/토큰)를 ecr-pullthroughcache/ 접두어의 Secrets Manager 시크릿에 저장한다.
  2. 권한 설정ECR 서비스 역할(또는 풀스루 캐시를 실행하는 주체)에 Secrets Manager의 GetSecretValue 권한을 부여한다.
  3. 캐시 시 인증풀스루 캐시가 업스트림 레지스트리에 접근할 때, Secrets Manager에서 자격 증명을 읽어서 인증한 뒤 이미지를 당겨온다.

캐시 규칙 검증·프리픽스 커스터마이즈·캐시 이미지 당겨오기

규칙 생성 시 지정한 ECR 리포지토리 프리픽스로 업스트림 경로를 매핑하고, 규칙 검증으로 권한을 확인한 뒤 그 프리픽스 경로로 이미지를 당기면 캐시가 채워진다.

1상대의 출발점 확인

풀스루 캐시 규칙을 만든 후에도 실제로 이미지를 당길 때까지는 업스트림 레지스트리와의 연결이 정상인지, 인증 정보가 맞는지, 프리픽스 매핑이 올바른지 확인할 수 없다.

2질문 제기

규칙을 생성한 뒤 실제 사용 전에 업스트림 접근을 미리 검증하고, 원하는 프리픽스로 이미지를 캐시할 수 있을까?

3구조적 핵심 예시

ECR은 규칙 생성 완료 후 규칙 검증(Validate) 기능을 제공하는데, 이는 지정된 업스트림 레지스트리에 연결 가능한지, Secrets Manager의 자격 증명이 유효한지를 미리 확인해주고, 이후 규칙의 프리픽스 경로로 docker pull 요청이 들어오면 upstream_image_name을 ecr_repository_prefix/upstream_image_name 형태로 매핑해서 ECR 리포지토리에 저장한다.

4단계별 동작 과정

  1. 규칙 검증생성한 풀스루 캐시 규칙을 검증하면 ECR이 업스트림 레지스트리 접근, 자격 증명 유효성, Secrets Manager 권한 등을 미리 확인한다.
  2. 프리픽스 매핑규칙의 프리픽스(예: public/docker)와 업스트림 경로(예: library)가 결합되어, docker pull 요청 시 public/docker/library/nginx 같은 형태로 ECR 리포지토리에 이미지가 저장된다.
  3. 캐시 이미지 당겨오기클라이언트가 규칙의 프리픽스 경로로 이미지를 요청하면, ECR이 업스트림에서 가져온 뒤 그 경로의 리포지토리에 저장하고 클라이언트에 전달한다.

복제나 풀스루 캐시로 리포지토리가 자동 생성될 때 적용할 암호화·태그 변경 불가·수명 주기 정책·리포지토리 정책 등을 프리픽스별로 미리 정의해 두는 템플릿이다.

1상대의 출발점 확인

복제(replication)나 풀스루 캐시로 리포지토리가 자동 생성될 때, 각 리포지토리마다 암호화 설정, 태그 변경 불가 정책, 수명 주기 정책, 리포지토리 접근 정책 등을 일일이 적용하기는 번거롭고 설정 일관성을 보장하기 어렵다.

2질문 제기

3구조적 핵심 예시

ECR 리포지토리 생성 템플릿은 프리픽스(예: public/*, backend/*)별로 암호화 설정(SSE-KMS 키 지정), 태그 변경 불가, 수명 주기 정책(오래된 이미지 자동 삭제), 리포지토리 정책(접근 권한) 등을 미리 선언해 두면, 복제나 풀스루 캐시로 그 프리픽스 범위의 리포지토리가 생성될 때 자동으로 모든 설정이 적용된다.

4단계별 동작 과정

  1. 템플릿 정의프리픽스 패턴(예: prod/*, dev/*)과 적용할 설정(암호화 방식, 정책, 수명 주기 규칙 등)을 리포지토리 생성 템플릿으로 미리 등록한다.
  2. 자동 생성 시 적용복제나 풀스루 캐시로 리포지토리가 새로 생성되면, 리포지토리 이름이 템플릿의 프리픽스 패턴과 일치하는지 확인하고 일치하는 템플릿의 모든 설정을 자동으로 적용한다.
  3. 일관성 보장매번 수동으로 설정하지 않아도 모든 자동 생성 리포지토리가 보안·정책·접근 관리에서 일관된 상태로 유지된다.

저장 데이터 암호화 — AES256·SSE-KMS·DSSE-KMS

ECR 리포지토리는 생성 시 암호화 방식을 고르며, 기본은 S3 관리 키의 AES256이고 KMS 키로 관리하려면 SSE-KMS, 이중 암호화가 필요하면 DSSE-KMS를 선택한다.

1상대의 출발점 확인

ECR 리포지토리의 이미지 데이터는 AWS S3에 저장되는데, 저장된 데이터가 암호화되지 않으면 저장소에 물리적으로 접근하거나 데이터 접근 권한이 있는 내부자가 데이터를 열어볼 수 있다.

2질문 제기

ECR에 저장된 이미지 데이터를 어떤 암호화 방식으로 보호할까?

3구조적 핵심 예시

ECR 리포지토리 생성 시 암호화 방식을 선택할 수 있다. 기본값은 AWS에서 관리하는 S3 관리 키로 AES256 대칭 암호화를 하는 것이고, 자신의 KMS(Key Management Service, 암호화 키 관리 서비스) 키를 사용하려면 SSE-KMS를 선택하면 되고, 더 강한 보안이 필요하면 KMS 키로 한 번 더 감싸는 DSSE-KMS를 선택할 수 있다.

4단계별 동작 과정

  1. 암호화 방식 선택리포지토리 생성 시 AES256(기본, AWS 관리), SSE-KMS(사용자 KMS 키), DSSE-KMS(이중 암호화) 중 하나를 선택한다.
  2. 이미지 저장 시 암호화이미지를 푸시하면 ECR은 선택된 방식으로 데이터를 암호화한 뒤 S3에 저장한다.
  3. 이미지 풀 시 복호화이미지를 당길 때 ECR은 저장된 암호화 데이터를 복호화해서 클라이언트에 전달한다.

KMS 그랜트와 암호화에 필요한 IAM 권한

SSE-KMS 리포지토리를 만들면 ECR이 사용자 대신 KMS 그랜트를 생성하므로, 리포지토리 생성·이미지 푸시/풀 주체에게 kms:CreateGrant·Decrypt 같은 권한이 필요하다.

1상대의 출발점 확인

SSE-KMS로 암호화된 ECR 리포지토리를 만들 때, ECR은 사용자 KMS 키를 사용해서 데이터를 암호화·복호화해야 하는데, 단순히 리포지토리 생성자에게만 KMS 권한이 있으면 다른 팀원이 그 리포지토리에서 이미지를 푸시/풀할 때 권한 부족 오류가 발생한다.

2질문 제기

SSE-KMS 암호화를 쓰는 리포지토리에서 이미지를 푸시/풀하는 여러 사용자나 서비스에게 KMS 키 접근 권한을 어떻게 일괄 관리할까?

3구조적 핵심 예시

ECR이 SSE-KMS 리포지토리를 생성하면, ECR 서비스 역할(서비스가 사용하는 권한 세트)을 대신해서 자동으로 KMS 그랜트(Grants, 임시 권한 부여 메커니즘)를 생성한다. 이 그랜트는 kms:CreateGrant, kms:Decrypt, kms:GenerateDataKey 같은 필요한 암호화 작업 권한을 담고 있고, 리포지토리에 접근하는 주체(개발자, CI/CD 파이프라인 등)는 이 그랜트를 통해 KMS 키를 사용할 수 있다.

4단계별 동작 과정

  1. 그랜트 자동 생성SSE-KMS 리포지토리 생성 시 ECR이 자동으로 KMS 그랜트를 생성하고, 그 그랜트에 암호화/복호화에 필요한 권한을 포함한다.
  2. IAM 정책 설정리포지토리에 접근하는 주체(사용자, 역할 등)의 IAM 정책에 kms:CreateGrant, kms:Decrypt, kms:DescribeKey 같은 권한을 명시적으로 추가한다.
  3. 푸시/풀 시 권한 검증사용자나 서비스가 이미지를 푸시/풀하면 ECR이 주체의 IAM 권한과 KMS 그랜트를 함께 검증한 뒤 암호화/복호화를 허용한다.

1상대의 출발점 확인

1상대의 출발점 확인

3구조적 핵심 예시

4단계별 동작 과정

서비스 할당량과 스로틀링

1상대의 출발점 확인

기존 방식은 ECR을 쓸 때 어느 정도까지 쓸 수 있는지 명확히 알지 못하는 것입니다. 할당량을 모르면 의도치 않게 한계를 초과했을 때 갑자기 API가 실패하고, 왜 실패했는지도 모르며, 한계값을 어떻게 늘릴 수 있는지도 알 수 없습니다.

2질문 제기

ECR이 정한 한계값(할당량)이 무엇이고, 초과하면 어떤 오류가 발생할까요?

3구조적 핵심 예시

ECR의 기본 할당량은 계정당 리포지토리 1000개, 리포지토리당 이미지 1000개, API 호출 속도(초당 읽기 25회, 쓰기 20회)입니다. 만약 PutImage를 초당 21회 호출하면 20회 한계를 초과해 스로틀링이 발생하고, 추가 요청은 429 에러(Too Many Requests)를 받아 실패합니다.

4단계별 동작 과정

  1. 할당량 종류 파악AWS Service Quotas 콘솔에서 ECR의 리포지토리 수, 이미지 수, API 호출 속도 한계를 확인합니다.
  2. 사용량 모니터링CloudWatch 지표와 사용량 리포트로 현재 사용량을 계속 관찰해 할당량에 근접함을 감지합니다.
  3. 초과 시 대응할당량을 넘으면 스로틀링 오류가 반환되므로, Service Quotas에서 증가를 요청하거나 API 호출 패턴을 최적화합니다.

5본질 요약

1상대의 출발점 확인

3구조적 핵심 예시

푸시 실패 메시지가 떴을 때 순서대로 확인할 체크리스트를 생각해보면: ECR 인증 토큰이 아직 유효한가 → IAM 권한(ecr:GetDownloadUrlForLayer, ecr:BatchGetImage 등)이 있는가 → 네트워크 연결이 정상인가 → 리포지토리가 실제로 존재하는가. 이 순서대로 확인하면 대부분의 원인을 찾을 수 있다.

4단계별 동작 과정

  2. 인증과 권한 점검ECR에 로그인했는지, 토큰이 만료되지 않았는지, IAM 역할에 필요한 ECR 권한(에러에 따라 다르지만 대개 ecr:PutImage, ecr:GetDownloadUrlForLayer 등)이 할당됐는지 확인한다.
  3. 네트워크와 리포지토리 상태 확인AWS CLI로 aws ecr describe-repositories 명령으로 리포지토리가 존재하는지 확인하고, 인스턴스나 개발 머신에서 ECR 엔드포인트(프라이빗 엔드포인트 사용 시)에 도달할 수 있는지, 방화벽이나 보안 그룹이 막고 있지 않은지 점검한다.

ECS와 EKS에서 ECR 이미지 사용하기

ECS 태스크 정의나 EKS 파드 스펙에 ECR 이미지 URI를 적고, 실행 역할(또는 노드 역할)에 ECR 풀 권한을 줘서 컨테이너를 띄우는 방법.

1상대의 출발점 확인

이제까지 이미지를 ECR에 저장했지만, 실제로 그 이미지를 컨테이너로 실행해야 한다. ECS나 EKS 같은 컨테이너 실행 플랫폼이 ECR에서 이미지를 가져와 띄우려면, 실행 역할(ECS의 ecsTaskExecutionRole) 또는 노드 역할(EKS 워커 노드의 NodeInstanceRole)이 ECR에 접근할 권한을 가져야 한다. 하지만 많은 개발자가 이미지는 푸시했는데 실행 단계에서 권한 오류로 막히는 경험을 한다.

2질문 제기

ECS 태스크나 EKS 파드가 ECR의 이미지를 가져와 실행하려면 어떤 권한을 어디에 부여해야 할까?

3구조적 핵심 예시

ECS 태스크 정의(task definition)에 이미지 URI를 123456789.dkr.ecr.us-east-1.amazonaws.com/my-app:latest 형태로 명시하면, ECS 에이전트(EC2나 Fargate 위에서 돌고 있는 서비스)가 이 URI를 읽고 ECR에 접근하려고 시도한다. 이때 에이전트가 가진 IAM 역할의 권한을 바탕으로 이미지를 풀한다. 권한이 없으면 이 시점에 즉시 실패한다.

4단계별 동작 과정

  1. 실행 역할(또는 노드 역할)을 ECR 접근 권한으로 구성ECS의 경우 ecsTaskExecutionRole(또는 커스텀 역할)에 AmazonEC2ContainerRegistryReadOnly 정책을 붙인다. EKS 워커 노드의 경우 NodeInstanceRole에 같은 정책을 붙인다. 정책에는 ecr:GetAuthorizationToken, ecr:GetDownloadUrlForLayer, ecr:BatchGetImage 등의 액션이 포함된다.
  2. 이미지 URI를 태스크 정의나 파드 스펙에 기재ECS는 태스크 정의의 containerDefinitions 섹션의 image 필드에 ECR URI를 입력한다. EKS는 파드 YAML의 spec.containers[].image 에 같은 URI를 입력한다.
  3. 컨테이너 실행 시도ECS 에이전트나 EKS kubelet이 지정된 이미지를 ECR에서 풀해서 로컬 스토리지에 저장 후 실행한다.

Docker Hub 같은 외부 레지스트리의 이미지를 풀 스루 캐시나 복제·재푸시로 ECR에 옮겨 담는 이전 작업.

1상대의 출발점 확인

많은 조직이 Docker Hub나 Quay 같은 외부 레지스트리에서 이미 이미지를 관리하고 있다. 이런 이미지들을 전부 수작업으로 로컬에 풀한 후 ECR에 푸시하려면 각 이미지마다 명령을 실행해야 하고, 외부 레지스트리에 계속 의존하면 외부 서비스 장애나 대역폭 제한에 영향을 받는다. 기존 이미지를 ECR로 옮겨가려면 체계적인 방법이 필요하다.

2질문 제기

Docker Hub 같은 외부 레지스트리의 이미지를 ECR로 옮기되, 수작업을 최소화하고 지속해서 이용할 수 있도록 하려면?

3구조적 핵심 예시

풀 스루 캐시(pull-through cache)를 설정하면 ECR이 외부 레지스트리의 대리인(proxy) 역할을 한다. 개발자가 123456789.dkr.ecr.us-east-1.amazonaws.com/docker-hub/nginx:latest 같은 ECR 주소로 요청하면, ECR이 실제로는 Docker Hub의 nginx 이미지를 뒤에서 받아 캐시하고 돌려준다. 다음에 같은 이미지를 요청하면 ECR 캐시에서 바로 제공한다.

4단계별 동작 과정

  1. 풀 스루 캐시 규칙 생성AWS Console이나 CLI로 aws ecr create-pull-through-cache-rule 명령을 실행해 외부 레지스트리(Docker Hub, Quay 등)의 별칭을 ECR에 등록한다. 예: docker-hub → Docker Hub.
  2. 개발자가 ECR 주소로 풀 요청개발자는 docker pull 123456789.dkr.ecr.us-east-1.amazonaws.com/docker-hub/nginx:latest 형태로 ECR에서 받는다. ECR은 뒤에서 실제 Docker Hub로 가서 이미지를 가져온다.
  3. 캐시 적립과 재사용ECR이 이미지를 받아 로컬 캐시에 저장하고, 다음 요청부터는 ECR 캐시에서 빠르게 제공한다.

5본질 요약

ECR을 외부 레지스트리의 캐싱 대리인(proxy)으로 동작하게 하여 외부 이미지를 필요할 때 ECR을 통해 받고, 자동으로 캐시에 저장해 대역폭과 시간을 절약하면서도 기존 외부 레지스트리에 대한 의존성을 유지하는 것

ECR Public: 퍼블릭 레지스트리·갤러리·카탈로그 데이터

누구나 인증 없이 이미지를 받아갈 수 있는 공개 레지스트리로, Amazon ECR Public Gallery에 노출되며 카탈로그 데이터(설명·로고·사용법)로 소개 페이지를 꾸민다.

1상대의 출발점 확인

사설 ECR 리포지토리는 인증된 사용자만 이미지를 받을 수 있다. 반면 오픈소스 프로젝트나 일반 공개 용 이미지는 누구나 접근할 수 있어야 한다. 기존에는 Docker Hub Public을 이용했지만, AWS는 자체 퍼블릭 레지스트리 서비스를 제공해 AWS 인프라 내에서 직접 공개 이미지를 관리하고 배포할 수 있도록 했다.

2질문 제기

누구나 인증 없이 접근할 수 있는 공개 이미지 저장소를 ECR에서 운영하려면 어떻게 구성할까?

3구조적 핵심 예시

ECR Public Gallery는 Docker Hub의 "official images" 탭 같은 역할을 한다. 사용자가 docker pull public.ecr.aws/docker/nginx 명령을 실행하면, ECR이 인증 없이 이 이미지를 돌려준다. 동시에 Gallery에는 이미지의 설명, 로고, 사용 가이드, 보안 스캔 결과 같은 카탈로그 메타데이터(metadata)가 표시되어 사용자가 이미지를 선택할 때 참고할 수 있다.

4단계별 동작 과정

  1. 퍼블릭 리포지토리 만들기AWS CLI나 Console에서 aws ecr-public create-repository 명령을 실행한다. 이 리포지토리는 기본적으로 누구나 풀할 수 있도록 설정된다.
  2. 카탈로그 메타데이터 등록리포지토리의 설명, 로고, README, 소스 코드 링크(원본 저장소 URI) 등을 부여한다. 이 정보는 ECR Public Gallery의 이미지 상세 페이지에 표시된다.
  3. 이미지 푸시 및 공개개발자가 이미지를 푸시하면, Gallery에 자동으로 등록되어 누구나 접근 가능해진다.

5본질 요약

ECR의 인증 없는 퍼블릭 레지스트리로서, 누구나 이미지를 풀할 수 있도록 공개하되, 카탈로그 메타데이터(설명, 로고, 사용법)를 함께 제공해 이미지 검색과 선택을 용이하게 하는 것

ECR Public 리포지토리와 이미지 운영

퍼블릭 리포지토리를 만들고 이미지를 푸시·풀·태그·삭제하며 공개 배포를 관리하는 일상 운영.

→ 12-03 참조

1상대의 출발점 확인

퍼블릭 리포지토리를 만든 후 일상적으로 이미지를 푸시하고, 버전을 관리하고, 오래된 이미지를 삭제하는 것은 사설 리포지토리와 비슷하지만, 퍼블릭이므로 공개되는 이미지의 품질과 일관성을 더 신경써야 한다. 태그 전략, 메타데이터 유지보수, 이미지 삭제 정책을 제대로 관리하지 않으면 사용자에게 혼란을 준다.

2질문 제기

퍼블릭 리포지토리의 이미지를 체계적으로 푸시·태그·삭제하고 메타데이터를 최신으로 유지하려면?

3구조적 핵심 예시

리포지토리에 nginx 이미지를 여러 버전으로 푸시한다면, latest, 1.24, 1.24.0 같은 태그를 붙여 배포한다. 이때 각 버전의 이미지에 대해 설명을 별도로 기입하고, 보안 스캔 결과를 확인한 후 공개한다. 오래된 버전은 주기적으로 삭제하되, 사용자의 의존성이 없는지 먼저 확인해야 한다.

4단계별 동작 과정

  1. 이미지 빌드 및 태그 지정개발자가 Dockerfile을 빌드해 로컬에서 이미지를 생성한 후, docker tag my-image:latest public.ecr.aws/org/my-image:latest, docker tag my-image:1.24 public.ecr.aws/org/my-image:1.24 등의 명령으로 ECR 퍼블릭 주소로 태그를 붙인다.
  2. ECR 퍼블릭에 푸시 및 메타데이터 설정docker push public.ecr.aws/org/my-image:latest 명령으로 푸시한 후, AWS CLI로 리포지토리의 설명, 각 이미지의 타그 정보를 업데이트한다.
  3. 이미지 삭제 및 정리더 이상 필요 없는 태그는 aws ecr-public batch-delete-image 명령으로 삭제한다.

5본질 요약

ECR 퍼블릭 리포지토리에 이미지를 푸시·태그·삭제하고, 설명과 스캔 결과 같은 메타데이터를 일관되게 유지하여 공개 사용자에게 신뢰할 수 있는 이미지를 제공하는 것

Podman 등 다른 클라이언트로 ECR 쓰기, 그리고 SDK·코드 예제

Docker 말고 Podman·Finch 같은 OCI 클라이언트나 AWS SDK/CLI 코드로 ECR에 인증하고 이미지를 다루는 방법.

1상대의 출발점 확인

지금까지는 docker 명령(docker push, docker pull)으로 ECR에 접근하는 방식을 썼다. 하지만 Docker가 항상 최선의 선택은 아니다. 일부 개발 환경은 Podman이나 Finch 같은 경량 컨테이너 런타임을 쓰고, 자동화 스크립트는 AWS SDK나 CLI 코드로 이미지를 다루기도 한다. 이런 다양한 클라이언트들이 모두 ECR에 접근하려면, 각각의 인증 방식을 이해해야 한다.

2질문 제기

Docker가 아닌 Podman, Finch, AWS SDK 등 다양한 도구에서 ECR에 인증하고 이미지를 다루려면?

3구조적 핵심 예시

ECR 인증의 핵심은 Authorization Token(임시 토큰)을 획득하는 것이다. aws ecr get-login-password 명령을 실행하면 임시 토큰을 받는다. Docker는 이 토큰을 자동으로 처리하지만, Podman이나 직접 코드를 쓸 때는 이 토큰을 명시적으로 받아 docker login 같은 명령에 전달해야 한다. AWS SDK는 내부적으로 IAM 역할의 자격증명(credentials)을 이용해 토큰을 자동으로 생성해 API 호출에 실어보낸다.

4단계별 동작 과정

  1. ECR 인증 토큰 획득aws ecr get-login-password --region us-east-1 명령으로 토큰을 받는다. 이 토큰은 기본 12시간 유효하다.
  2. 클라이언트에 토큰 제공Docker CLI라면 docker login -u AWS -p <token> <ecr-url> 형태로 로그인한다. Podman도 동일한 명령 구조를 쓴다. AWS SDK(Python, Node.js 등)라면 내부적으로 IAM 자격증명을 읽어 요청에 포함시킨다.
  3. 이미지 풀/푸시 실행인증 후 docker/podman pull, docker/podman push 또는 SDK 메서드(예: boto3의 ecr.get_download_url_for_layer)를 호출한다.

5본질 요약

ECR에 접근하는 모든 클라이언트(Docker, Podman, AWS SDK)가 임시 Authorization Token을 획득하거나 IAM 자격증명을 제시해 인증을 받은 후, OCI(Open Container Initiative) 표준 프로토콜로 이미지를 주고받도록 통일하는 것
