Kubernetes의 정의와 문서 구조

Kubernetes는 컨테이너화된 애플리케이션의 배포·확장·운영을 자동화하는 오픈소스 컨테이너 오케스트레이션 플랫폼이다.

#1문제 상황

여러 대의 서버에 컨테이너를 직접 배포하던 방식에서는 각 서버에 접속해 컨테이너를 하나씩 실행하고, 어느 서버에 무엇이 떠 있는지 사람이 직접 관리해야 했다. 서버 한 대가 죽으면 그 위의 컨테이너는 멈춘 채로 남고, 트래픽이 늘어 컨테이너를 더 띄우려면 다시 수작업으로 서버를 찾아 명령을 내려야 했다. 이 방식은 서버와 컨테이너 수가 늘수록 배포·확장·복구 작업이 사람 손에 묶여 느려지고 실수가 잦아진다.

#2핵심 질문

컨테이너를 여러 대의 서버에 걸쳐 사람이 일일이 개입하지 않고도 배포·확장·운영할 수는 없을까?

#3동작 예시

kubectl apply -f deployment.yaml 한 번으로 웹 애플리케이션 컨테이너 3개를 띄우도록 선언하면, Kubernetes는 클러스터 안에서 놀고 있는 노드를 찾아 그 위에 컨테이너를 배치하고, 3개 중 하나가 죽으면 새 컨테이너를 다시 만들어 개수를 3개로 맞춘다. 사용자는 서버를 지정하지 않고 "3개를 유지하라"는 의도만 전달한다.

#4동작 과정

  1. 선언 접수사용자가 YAML로 원하는 상태를 적어 API 서버에 보내면, 클러스터는 그 내용을 저장하고 목표 상태로 삼는다.
  2. 상태 조정컨트롤러(원하는 상태와 실제 상태를 계속 비교하는 관리 프로세스)가 차이를 발견하면 Pod(컨테이너를 감싼 최소 실행 단위)를 만들거나 지워 차이를 줄인다.
  3. 배치와 유지스케줄러가 새 Pod를 실행할 노드를 고르고, 각 노드의 kubelet(노드에서 컨테이너 실행을 담당하는 에이전트)이 컨테이너를 띄워 목표 상태를 실제로 유지한다.

#5한 줄 요약

원하는 상태를 선언하면 클러스터가 스스로 그 상태를 맞추도록 컨테이너 배포·확장·운영을 자동화하는 것

클러스터 아키텍처

클러스터는 제어 플레인(API 서버, etcd, 스케줄러, 컨트롤러 매니저)과 워커 노드(kubelet, kube-proxy, 컨테이너 런타임)로 구성되어 애플리케이션을 실행·관리한다.

#1문제 상황

컨테이너를 한 대의 서버에서만 돌리면 그 서버가 고장 나는 순간 애플리케이션 전체가 멈춘다. 여러 서버로 나눠 돌리려 해도 어떤 서버에 어떤 컨테이너를 둘지, 서버가 죽었을 때 그 컨테이너를 어디서 다시 띄울지를 사람이 판단해야 한다. 게다가 어느 서버가 살아 있고 각 서버에서 무슨 컨테이너가 도는지 통합된 정보가 없으면 판단 자체가 불가능해진다.

#2핵심 질문

여러 대의 서버를 하나의 논리적 단위로 묶어, 일부가 고장 나도 애플리케이션을 계속 돌릴 수 있는 구조는 어떻게 만드는가?

#3동작 예시

노드 3대짜리 클러스터에서 제어 플레인의 API 서버가 "웹 Pod 3개를 유지하라"는 상태를 갖고 있다. 노드 하나가 전원이 꺼지면 각 노드의 kubelet이 상태를 보고하지 못하게 되고, 컨트롤러 매니저(상태를 원하는 값으로 맞추는 관리자)가 이를 감지해 사라진 Pod 수만큼 새 Pod를 다른 노드에 만들어 전체 개수를 다시 3개로 복구한다.

#4동작 과정

  1. 제어 플레인이 상태를 보관API 서버(모든 요청이 지나가는 관문)가 클러스터의 원하는 상태를 받고, etcd(상태를 저장하는 분산 키-값 저장소)에 그 내용을 기록해 유지한다.
  2. 컨트롤러가 차이를 계산컨트롤러 매니저와 스케줄러가 저장된 원하는 상태와 실제 상태를 비교해 어떤 Pod를 어느 노드에 만들어야 할지 결정한다.
  3. 노드가 실제로 실행각 워커 노드의 kubelet이 배정된 Pod의 컨테이너를 컨테이너 런타임으로 띄우고, kube-proxy(노드의 네트워크 규칙을 관리하는 컴포넌트)가 서비스 트래픽이 오갈 길을 열어 준다.

#5한 줄 요약

제어 플레인이 상태를 판단하고 워커 노드가 실행을 맡는 역할 분담으로, 여러 서버를 하나의 고장 감내 클러스터로 묶는 것

API와 오브젝트

Kubernetes 오브젝트는 클러스터의 의도된 상태를 담은 영속적 레코드로, YAML/JSON의 spec과 status로 표현되며 API 서버를 통해 관리된다.

#1문제 상황

컨테이너를 서버에 직접 띄우던 방식에서는 "지금 무엇이 실행 중이어야 하는가"라는 정보가 사람의 머릿속이나 스크립트 안에만 있었다. 그 결과 누군가 컨테이너를 임의로 지우거나 서버가 재부팅돼도 클러스터는 원래 있어야 할 상태를 알지 못해 아무 조치도 하지 못한다. 명령을 내리는 방식은 "이렇게 하라"는 절차만 남기고, 최종적으로 어떤 상태여야 하는지는 기록으로 남기지 않는다.

#2핵심 질문

클러스터가 스스로 유지해야 할 목표 상태를 사람이 명확히 기록하고 관리하려면 무엇이 필요한가?

#3동작 예시

Deployment 오브젝트 하나를 YAML로 작성해 spec.replicas: 3이라고 적어 API 서버에 보내면, 이 기록은 클러스터에 영속적으로 저장된다. 이후 누군가 Pod 하나를 삭제해도 Kubernetes는 저장된 spec과 현재 상태를 비교해 부족한 Pod를 다시 만들어 개수를 3개로 되돌린다.

#4동작 과정

  1. 의도 기록 생성사용자가 오브젝트를 YAML이나 JSON으로 정의해 API 서버에 제출하면, spec(원하는 상태)과 status(현재 관측된 상태)를 가진 영속적 레코드로 저장된다.
  2. 상태 비교해당 오브젝트를 담당하는 컨트롤러가 spec과 status의 차이를 주기적으로 확인한다.
  3. 차이 해소차이가 있으면 컨트롤러가 오브젝트를 생성·수정·삭제해 status를 spec에 맞추고, 결과가 다시 저장된다.

#5한 줄 요약

원하는 상태를 spec에 담아 영속적 오브젝트로 기록하고, 시스템이 그 기록과 실제 상태의 차이를 계속 메우게 하는 것

워크로드와 네임스페이스

워크로드는 클러스터에서 실행되는 애플리케이션을 나타내는 오브젝트(Pod, Deployment 등)이고, 네임스페이스는 하나의 물리 클러스터를 여러 논리적 가상 클러스터로 나누는 단위다.

#1문제 상황

Pod(컨테이너를 감싼 최소 실행 단위)를 하나씩 직접 만들면, 노드에 장애가 나서 그 위의 Pod가 사라졌을 때 사용자가 새 Pod를 손수 다시 만들어야 한다. Kubernetes는 그 수준의 실패를 최종으로 취급하기 때문에 노드가 나중에 복구돼도 죽은 Pod는 돌아오지 않는다. 또한 하나의 물리 클러스터를 여러 팀이 함께 쓰면 오브젝트 이름이 서로 충돌하고, 팀별로 자원을 구분해 관리할 경계도 없다.

#2핵심 질문

Pod 여러 개를 자동으로 관리하고, 하나의 클러스터를 여러 팀이 충돌 없이 나눠 쓰려면 어떻게 해야 하는가?

#3동작 예시

Deployment로 replicas: 3을 지정하면 그 뒤에서 ReplicaSet이 Pod 3개를 유지한다. 같은 클러스터에서 dev 네임스페이스와 prod 네임스페이스를 나누면, 두 곳에 똑같이 web이라는 이름의 Deployment를 만들어도 서로 다른 오브젝트로 취급되어 충돌하지 않는다.

#4동작 과정

  1. 워크로드가 Pod 집합을 정의Deployment 같은 상위 오브젝트가 "이런 Pod를 몇 개 유지하라"는 규칙을 담고, 컨트롤러가 그 규칙에 맞는 Pod 집합을 대신 관리한다.
  2. 컨트롤러가 개수를 맞춤ReplicaSet이 현재 Pod 수와 원하는 수를 비교해 부족하면 만들고 남으면 줄여, 지정한 개수를 유지한다.
  3. 네임스페이스가 범위를 나눔각 오브젝트를 네임스페이스 안에 배치해 이름과 자원을 논리적으로 분리하고, 같은 물리 클러스터를 여러 가상 클러스터처럼 나눠 쓴다.

#5한 줄 요약

상위 워크로드가 Pod 집합을 자동 관리하고 네임스페이스가 그 범위를 나눠, 하나의 클러스터를 안전하게 공유하고 유지하게 하는 것

Pod와 컨테이너 — 실행 단위02-01

Pod 기초

Pod는 하나 이상의 컨테이너를 묶어 같은 노드에서 함께 실행하고 네트워크·스토리지를 공유하게 하는 쿠버네티스의 최소 배포 단위다.

#1문제 상황

애플리케이션 컨테이너를 각각 따로 서버에 띄우면, 서로 긴밀히 협력해야 하는 프로세스들이 다른 서버로 흩어져 네트워크로만 통신해야 한다. 이 경우 같은 로컬 저장소를 공유하거나 localhost로 빠르게 주고받는 구조를 만들 수 없고, 함께 있어야 의미가 있는 프로세스를 같은 서버에 묶어 두는 것도 자동화되지 않는다. 개별 컨테이너를 하나씩 배치하는 방식은 "함께 실행돼야 하는 컨테이너 묶음"이라는 단위를 표현하지 못한다.

#2핵심 질문

같은 노드에서 함께 실행되고 네트워크·저장소를 공유해야 하는 컨테이너들을 하나의 단위로 다룰 수는 없을까?

#3동작 예시

웹 서버 컨테이너와 그 로그를 읽어 밖으로 전달하는 컨테이너를 하나의 Pod에 함께 넣으면, 두 컨테이너는 같은 노드에 함께 배치되고 같은 네트워크 공간을 써서 localhost로 통신하며 같은 볼륨을 공유한다. 둘은 항상 함께 스케줄되고 함께 옮겨진다.

#4동작 과정

  1. Pod로 묶음 정의하나 이상의 컨테이너와 그 실행 방법을 하나의 spec으로 정의해 Pod를 만든다.
  2. 함께 배치스케줄러가 Pod를 하나의 노드에 통째로 배정하고, 그 안의 컨테이너들은 같은 Linux 네임스페이스와 cgroup(자원을 격리·제한하는 커널 기능)을 공유한다.
  3. 컨테이너 실행 유지노드의 kubelet이 컨테이너 런타임을 통해 컨테이너를 띄우고, 시작 시점에는 init 컨테이너(본 컨테이너 전에 순서대로 실행되는 초기화 컨테이너)가 먼저 돌아 준비를 마친다.

#5한 줄 요약

함께 실행돼야 하는 컨테이너들을 한 노드에 묶어 네트워크·저장소를 공유하게 하는 최소 배포 단위를 제공하는 것

Pod와 컨테이너 — 실행 단위02-02

Pod 고급 구성과 생명주기

Pod가 생성되어 Pending·Running·Succeeded·Failed 단계를 거쳐 종료되기까지의 상태 변화와 그 사이 컨테이너에 적용되는 재시작·프로브 등의 동작 규칙이다.

#1문제 상황

컨테이너를 그냥 실행만 하면, 프로세스가 살아 있어도 요청을 처리할 준비가 안 됐는지, 아니면 교착 상태로 멈춰 응답만 못 하는지를 클러스터가 구분하지 못한다. 그래서 준비 안 된 컨테이너로 트래픽이 들어가거나, 응답하지 않는 컨테이너가 계속 떠 있는 채 방치된다. 또한 Pod가 시작하고 끝나는 과정에서 어느 시점에 컨테이너를 다시 시작해야 하는지에 대한 규칙이 없으면 상태 관리가 사람마다 제각각이 된다.

#2핵심 질문

Pod가 생성되고 종료되기까지, 각 컨테이너의 건강 상태를 판단해 트래픽을 보내고 다시 시작할 시점을 어떻게 정할까?

#3동작 예시

컨테이너에 readiness 프로브(트래픽을 받을 준비가 됐는지 확인하는 검사)와 liveness 프로브(컨테이너가 살아 있는지 확인하는 검사)를 설정하면, readiness가 통과할 때까지는 서비스가 이 Pod로 트래픽을 보내지 않고, liveness가 실패하면 kubelet이 그 컨테이너를 다시 시작한다. 준비 전에는 트래픽을 막고, 멈추면 재시작한다.

#4동작 과정

  1. Pending에서 시작Pod가 만들어져 노드에 배정되기 전까지 Pending 단계에 머물고, 초기화가 필요한 컨테이너가 순서대로 실행된다.
  2. Running과 상태 점검주 컨테이너 중 하나라도 정상 시작하면 Running으로 넘어가고, kubelet이 프로브를 실행해 컨테이너 상태를 계속 추적한다.
  3. 종료와 재시작 판정프로세스가 끝나면 성공은 Succeeded, 실패는 Failed로 표시되며, 재시작 정책(restart policy)에 따라 컨테이너를 다시 시작할지 결정된다.

#5한 줄 요약

Pod의 상태 단계와 프로브·재시작 규칙으로 컨테이너의 건강을 판단해 트래픽과 복구 시점을 정하는 것

컨테이너와 이미지

컨테이너는 이미지에서 실행되는 격리된 프로세스이며, 이미지는 애플리케이션 실행에 필요한 파일과 설정을 담은 읽기 전용 템플릿이다.

#1문제 상황

애플리케이션을 각 서버에 직접 설치하던 방식에서는 실행 환경마다 라이브러리 버전과 설정이 조금씩 달라, 개발 환경에서 되던 것이 운영에서 안 되는 문제가 반복됐다. 어떤 서버에는 어떤 버전이 깔렸는지가 사람마다 다르게 기록돼 재현이 어려웠고, 새 서버에 같은 환경을 다시 만드는 데도 많은 수작업이 필요했다. 실행에 필요한 파일과 설정을 하나로 묶어 어디서나 동일하게 돌릴 방법이 없었다.

#2핵심 질문

애플리케이션과 그 실행에 필요한 모든 의존성을 하나로 묶어 어떤 노드에서도 같게 실행하려면 무엇이 필요한가?

#3동작 예시

애플리케이션과 의존성을 담은 이미지를 만들어 레지스트리에 올리고, Pod spec의 image에 그 이미지 이름과 태그를 적으면, kubelet이 각 노드에서 그 이미지를 내려받아 컨테이너로 실행한다. 노드가 바뀌어도 같은 이미지 이름을 참조하므로 동일한 환경이 그대로 재현된다.

#4동작 과정

  1. 이미지 빌드와 푸시애플리케이션과 의존성을 담은 읽기 전용 이미지를 만들어 레지스트리에 올린다.
  2. 참조 해석Pod가 이미지이름:태그 형태로 이미지를 가리키면, 레지스트리 주소가 생략된 경우 기본 레지스트리를 기준으로 실제 이미지를 찾는다.
  3. 내려받아 실행kubelet이 컨테이너 런타임을 통해 노드에 이미지를 받아 컨테이너 프로세스로 실행하고, 이미지는 읽기 전용 템플릿으로 남아 재사용된다.

애플리케이션과 의존성을 이미지로 묶어 어떤 노드에서든 같은 환경으로 실행되게 하는 것

Windows 컨테이너

Windows 컨테이너는 Windows 노드에서 Windows 커널을 공유하며 실행되도록 만든 컨테이너로, 리눅스 컨테이너와 다른 이미지·런타임·네트워킹 방식을 따른다.

#1문제 상황

기존에는 리눅스 컨테이너를 중심으로 클러스터를 운영했다. 리눅스 컨테이너는 리눅스 커널의 기능을 사용해 프로세스를 격리하므로, 리눅스 커널 위에서만 동작한다. 그런데 조직에는 윈도우 기반 애플리케이션이 여전히 큰 비중을 차지한다. 윈도우 애플리케이션을 리눅스 컨테이너로 그대로 옮길 수 없으니, 별도의 오케스트레이터를 따로 두고 관리해야 했다. 이 때문에 리눅스 워크로드와 윈도우 워크로드를 각각 다른 도구로 운영하며 운영 효율이 떨어졌다. Windows 컨테이너는 이런 윈도우 애플리케이션의 프로세스와 의존성을 패키징해 담는 수단을 제공한다.

#2핵심 질문

리눅스와 윈도우 워크로드를 하나의 쿠버네티스 클러스터에서 함께 오케스트레이션하려면 무엇이 필요한가?

#3동작 예시

윈도우 컨테이너를 실행하려면 클러스터가 여러 운영체제로 구성되어야 한다. 컨트롤 플레인은 리눅스에서만 실행할 수 있지만, 워커 노드는 윈도우 또는 리눅스로 배포할 수 있다. 그래서 기존 리눅스 클러스터에 윈도우 노드를 추가하면, 윈도우 컨테이너를 담은 파드를 그 윈도우 노드에 스케줄링할 수 있다. 파드에 윈도우 컨테이너를 스케줄링하는 방식은 리눅스 기반 컨테이너를 스케줄링하는 것과 비슷하다.

#4동작 과정

  1. 노드 준비기존 리눅스 클러스터에 Windows Server 2022 또는 Windows Server 2025 를 실행하는 윈도우 워커 노드를 포함시킨다. 컨트롤 플레인은 리눅스에 그대로 두므로, 클러스터가 두 운영체제를 함께 갖게 된다.
  2. 스케줄링윈도우 컨테이너를 담은 파드가 만들어지면 스케줄러가 이 파드를 윈도우 노드에 배치한다. 윈도우 컨테이너는 윈도우 노드의 윈도우 커널을 공유하며 실행되므로 리눅스 노드에는 배치되지 않는다.
  3. 공통 관리배치된 파드는 리눅스 워크로드와 같은 쿠버네티스 API 로 관리된다. 그 결과 운영체제와 무관하게 하나의 오케스트레이터로 두 종류 워크로드를 함께 배포·운영할 수 있다.

#5한 줄 요약

윈도우 애플리케이션을 리눅스와 같은 클러스터에서 오케스트레이션하기 위해 윈도우 노드에서 윈도우 커널을 공유해 실행하는 컨테이너

워크로드 컨트롤러

Pod의 복제 수·배치·업데이트를 대신 관리해 원하는 상태를 유지하도록 하는 상위 오브젝트(Deployment·ReplicaSet·StatefulSet·DaemonSet 등)

#1문제 상황

애플리케이션은 결국 파드 안의 컨테이너로 실행된다. 그런데 개별 파드를 하나하나 직접 관리하는 것은 큰 수고가 든다. 예를 들어 파드 하나가 실패하면 사용자가 직접 새 파드를 띄워 대체해야 한다. 파드가 여러 개라면 어느 것을 몇 개 유지할지, 어떻게 교체하고 갱신할지도 모두 손으로 챙겨야 한다. 이 방식으로는 원하는 상태를 안정적으로 유지하기 어렵다.

#2핵심 질문

개별 파드를 일일이 관리하지 않고 원하는 실행 상태를 안정적으로 유지하려면 무엇이 필요한가?

#3동작 예시

Deployment 는 가장 흔히 쓰이는 워크로드 오브젝트로, 상태를 갖지 않는 애플리케이션 워크로드 관리에 잘 맞는다. Deployment 안의 파드는 서로 교체 가능하므로 필요하면 대체될 수 있다. 사용자가 Deployment 라는 워크로드 오브젝트를 정의하면, 컨트롤 플레인이 그 명세에 따라 파드 오브젝트를 대신 관리한다. 그래서 파드가 실패해도 지정한 상태를 맞추기 위해 새 파드가 자동으로 만들어진다.

#4동작 과정

  1. 상위 오브젝트 생성사용자가 파드보다 높은 추상화 수준을 나타내는 워크로드 오브젝트를 쿠버네티스 API 로 만든다. Deployment 는 내부적으로 ReplicaSet 을 통해 동작하고, StatefulSet·DaemonSet 등은 각기 다른 방식으로 파드를 관리한다.
  2. 파드 자동 관리컨트롤 플레인이 정의된 명세를 바탕으로 파드 오브젝트를 대신 생성·교체한다. 파드가 실패하면 사용자가 손대지 않아도 새 파드로 대체되어 복제 수가 유지된다.
  3. 용도별 선택교체 가능한 무상태 워크로드는 Deployment, 고유한 정체성이 필요한 파드는 StatefulSet, 모든 노드에 하나씩 띄우는 워크로드는 DaemonSet 을 쓴다. 그 결과 워크로드 성격에 맞는 컨트롤러로 배치·업데이트가 자동화된다.

#5한 줄 요약

개별 파드를 직접 관리하는 수고를 없애기 위해 파드의 복제 수·배치·업데이트를 대신 처리하고 원하는 상태를 유지하는 상위 오브젝트

Job과 CronJob

완료를 목표로 한 일회성·정기 작업을 실행하는 컨트롤러로, Job은 지정 횟수만큼 Pod를 완료시키고 CronJob은 크론 스케줄에 따라 Job을 생성한다

#1문제 상황

Deployment 나 StatefulSet 같은 상시 실행형 컨트롤러는 서비스를 계속 살아 있게 유지하는 데 맞춰져 있다. 그런데 실제 작업에는 끝나면 멈추는 일회성 작업이 많다. 배치 계산이나 데이터 처리를 한 번만 돌리고 끝내는 식이다. 이런 작업을 상시 실행형 컨트롤러로 관리하면 작업이 끝난 뒤에도 파드가 계속 떠 있어 자원이 낭비된다. 또 실패했을 때 성공할 때까지 다시 시도하는 동작이 기본 제공되지 않는다.

#2핵심 질문

완료가 목표인 일회성·정기 작업을 성공할 때까지 안정적으로 실행하려면 어떻게 해야 하는가?

#3동작 예시

Job 은 하나 이상의 파드를 만들고, 지정한 수만큼 성공적으로 끝날 때까지 파드 실행을 계속 재시도한다. 예를 들어 파드 하나를 끝까지 완료시키는 단순한 Job 을 만들 수 있다. 첫 번째 파드가 실패하거나 삭제되면(노드 하드웨어 고장이나 재부팅 등으로), Job 이 새 파드를 시작해 작업을 이어간다. 정해진 횟수의 성공적인 완료에 도달하면 그 작업은 완료된 것으로 본다.

#4동작 과정

  1. 작업 생성Job 이 완료를 목표로 한 일회성 작업을 나타내며, 필요한 파드를 만든다. 완료할 성공 횟수를 명세에 지정한다.
  2. 재시도와 추적파드가 성공적으로 종료될 때마다 Job 이 그 완료 횟수를 추적한다. 파드가 실패하거나 삭제되면 Job 은 성공 횟수에 도달할 때까지 새 파드를 실행한다.
  3. 정리와 정기 실행지정한 성공 횟수에 도달하면 작업이 완료되고, Job 을 삭제하면 그 Job 이 만든 파드도 정리된다. 정해진 스케줄에 따라 Job 을 만들고 싶으면 CronJob 을 사용한다.

#5한 줄 요약

끝나면 멈추는 일회성·정기 작업을 지정한 성공 횟수까지 재시도하며 완료시키는 컨트롤러

워크로드 오토스케일링

부하·지표에 따라 워크로드의 복제 수(Pod 개수)나 자원 할당을 자동으로 조정해 수요에 맞추는 기능

#1문제 상황

워크로드에 걸리는 부하는 시간에 따라 변하는데, 사람이 미리 파드 개수나 자원 할당을 정해 두면 변하는 수요에 맞추기 어렵다. 부하가 몰리는 때에는 파드가 부족해 처리하지 못하고, 부하가 줄면 남는 파드가 자원을 계속 차지한다. 관리자가 직접 파드 수를 늘리고 줄이거나 자원 정의를 고쳐야 하므로 대응이 늦고 수고가 든다. 그래서 수요 변화에 탄력적으로 반응하기 어렵다.

#2핵심 질문

부하와 자원 수요의 변화에 맞춰 워크로드 규모를 스스로 조정하려면 어떻게 해야 하는가?

#3동작 예시

쿠버네티스는 현재 자원 수요에 따라 워크로드를 확장하거나 축소할 수 있다. 확장하는 방법은 두 가지다. 하나는 워크로드가 관리하는 파드 개수(복제 수)를 늘리거나 줄이는 것이고, 다른 하나는 파드가 쓰는 CPU·메모리 같은 자원을 제자리에서 조정하는 것이다. 앞의 방식을 수평 확장, 뒤의 방식을 수직 확장이라고 한다.

#4동작 과정

  1. 수동 확장명령줄 도구로 복제 수를 늘리거나 줄여 수평 확장하고, 워크로드의 자원 정의를 고쳐 수직 확장한다. 관리자가 직접 시점과 규모를 정한다.
  2. 자동 확장쿠버네티스가 부하와 지표를 보고 복제 수나 자원 할당을 자동으로 조정한다. 그 결과 사람이 개입하지 않아도 수요 변화에 맞춰 규모가 바뀐다.
  3. 범위 확장파드 단위를 넘어 노드 수까지 자동으로 조정할 수 있다. 이렇게 하면 클러스터 전체가 자원 수요 변화에 더 탄력적이고 효율적으로 반응한다.

#5한 줄 요약

부하와 자원 수요 변화에 맞춰 워크로드의 파드 개수나 자원 할당을 자동으로 조정해 탄력적으로 대응하는 기능

스케줄러와 노드 배치

kube-scheduler 가 새로 만든 파드에 대해 조건에 맞는 노드를 골라 배치하는 기본 동작과 흐름을 다루는 개념.

#1문제 상황

파드는 컨테이너를 실행할 노드 위에서 돌아가야 하는데, 새로 만들어진 파드에는 처음에 어느 노드에서 실행할지가 정해져 있지 않다. 노드마다 남은 자원과 조건이 다르므로, 사용자가 파드마다 노드를 직접 지정하는 것은 비현실적이다. 잘못 배치하면 특정 노드에 부하가 몰리거나 자원이 부족한 노드에 파드가 올라간다. 그래서 파드가 뜰 때마다 조건에 맞는 노드를 자동으로 정해 주는 절차가 필요하다.

#2핵심 질문

새로 만들어진 파드에 대해 조건에 맞는 최적의 노드를 어떻게 자동으로 골라 배치할 것인가?

#3동작 예시

kube-scheduler 는 쿠버네티스의 기본 스케줄러이며 컨트롤 플레인의 일부로 실행된다. 이 스케줄러는 아직 노드가 배정되지 않은 새로 만들어진 파드를 살펴본다. 파드가 발견될 때마다 그 파드를 실행하기에 가장 좋은 노드를 찾는 일을 맡는다. 파드와 그 안의 컨테이너는 요구 조건이 각기 다를 수 있으므로, 스케줄러는 파드가 요구하는 스케줄링 조건을 충족하지 못하는 노드를 걸러낸다.

#4동작 과정

  1. 파드 관찰스케줄러가 노드가 배정되지 않은 새 파드를 계속 지켜본다. 파드를 발견하면 그 파드의 노드 배치 결정을 맡는다.
  2. 노드 선별파드의 요구 조건을 충족하지 못하는 노드를 걸러내고, 남은 노드 중 가장 적합한 노드를 고른다. 컨테이너와 파드마다 요구가 달라 이 걸러내기 과정이 필요하다.
  3. 배치 결정고른 노드를 파드에 배정하면, 그 노드의 Kubelet 이 파드를 실제로 실행한다. 원한다면 API 로 특정 노드를 직접 지정하거나, 기본 스케줄러 대신 직접 만든 스케줄링 컴포넌트를 쓸 수도 있다.

고급 스케줄링

노드 셀렉터·어피니티·안티어피니티·토폴로지 분산 제약 등으로 파드를 특정 노드에 유도하거나 흩어 배치하는 기법.

#1문제 상황

기본 스케줄러는 노드에 파드를 고르게 흩어 놓는 등 합리적인 배치를 자동으로 해 준다. 그래서 대부분의 경우 배치 제약을 따로 줄 필요가 없다. 하지만 어떤 상황에서는 파드가 어느 노드에 가는지를 직접 통제해야 한다. 예를 들어 SSD 가 붙은 노드에 파드를 두거나, 서로 통신을 많이 하는 두 서비스의 파드를 같은 가용 영역에 함께 두고 싶을 때다. 기본 배치만으로는 이런 세밀한 요구를 만족시키기 어렵다.

#2핵심 질문

파드를 특정 노드로 유도하거나 여러 노드에 흩어 배치하도록 배치 규칙을 어떻게 지정하는가?

#3동작 예시

파드에 제약을 걸어 특정 노드에서만 실행되게 하거나, 특정 노드에서 실행되기를 선호하게 할 수 있다. 이때 여러 방법이 있으며 권장되는 방식은 모두 레이블 셀렉터(노드에 붙은 키-값 꼬리표를 조건으로 고르는 규칙)를 사용해 노드를 선택한다. 노드에는 레이블을 붙일 수 있고, 쿠버네티스는 클러스터의 모든 노드에 표준 레이블 집합도 채워 넣는다.

#4동작 과정

  1. 후보 지정nodeSelector 필드로 노드 레이블과 일치하는 노드를 고르거나, nodeName 필드로 특정 노드를 직접 지정한다. 이것이 파드가 갈 노드를 좁히는 첫 단계다.
  2. 선호도 세분화어피니티와 안티어피니티로 특정 노드에 끌어들이거나 피하도록 유도하고, 파드 토폴로지 분산 제약(Pod topology spread constraints)으로 파드를 여러 영역에 흩어 배치한다. 그 결과 단순 일치를 넘어 더 세밀하게 배치를 조절할 수 있다.
  3. 자동 배치 보완제약을 따로 주지 않으면 스케줄러가 자원이 부족한 노드를 피하는 등 합리적으로 배치한다. 그래서 꼭 필요한 경우에만 제약을 더해 통제한다.

제거(Eviction)와 우선순위

리소스 부족 시 파드를 축출하는 동작과 PodPriority·선점(preemption)으로 중요한 파드를 우선 배치하는 기제.

#1문제 상황

클러스터의 자원은 한정되어 있어, 모든 파드를 항상 원하는 대로 띄워 둘 수는 없다. 노드에 자원이 부족해지면 이미 떠 있는 파드 중 일부를 내보내야 한다. 그런데 파드마다 중요도가 다르다. 아무 기준 없이 파드를 내보내면 서비스에 꼭 필요한 중요한 파드가 먼저 밀려날 수 있다. 또 새 파드가 자원이 없어 스케줄되지 못할 때, 낮은 중요도의 파드를 정리해 자리를 만드는 절차도 필요하다.

#2핵심 질문

자원이 부족할 때 어떤 파드를 먼저 내보내고, 중요한 파드를 어떻게 우선 배치할 것인가?

#3동작 예시

파드에는 우선순위를 줄 수 있다. 우선순위는 다른 파드와 비교한 그 파드의 중요도를 나타낸다. 어떤 파드가 스케줄되지 못하면, 스케줄러는 더 낮은 우선순위의 파드를 선점(내보내어 자리를 비우는 것)해 그 대기 중 파드가 스케줄될 수 있게 한다. 이렇게 하면 중요한 파드가 자원 경쟁에서 우선권을 갖는다. 다만 모든 사용자를 신뢰할 수 없는 클러스터에서는 악의적 사용자가 최고 우선순위로 파드를 만들어 다른 파드를 밀어낼 수 있으므로, 관리자는 ResourceQuota(네임스페이스별 자원·오브젝트 수를 제한하는 장치)로 높은 우선순위 파드 생성 자체를 막을 수 있다.

#4동작 과정

  1. 우선순위 정의PriorityClass(PriorityClass 이름과 정수 우선순위 값을 매핑하는, 네임스페이스에 속하지 않는 오브젝트)를 하나 이상 추가한다. 이 클래스가 어떤 이름이 어떤 우선순위 값을 갖는지 정한다.
  2. 파드에 지정파드의 priorityClassName 을 추가한 PriorityClass 중 하나로 설정한다. 보통은 파드를 직접 만들지 않고 Deployment 같은 컬렉션 오브젝트의 파드 템플릿에 지정한다.
  3. 선점 동작파드가 스케줄되지 못하면 스케줄러가 더 낮은 우선순위의 파드를 선점해 그 파드를 스케줄 가능하게 만든다. 그 결과 중요한 파드가 먼저 자리를 확보한다.

#5한 줄 요약

파드에 우선순위를 부여해 자원이 부족할 때 낮은 우선순위 파드를 내보내고 중요한 파드를 우선 배치하는 기제

리소스 관리

컨테이너·파드에 CPU·메모리 requests와 limits를 지정해 스케줄링과 런타임 자원 사용을 제어하는 방법.

#1문제 상황

파드 여러 개가 한 노드에 올라가면 각 컨테이너가 CPU와 메모리를 얼마나 쓸지 미리 정해 두지 않는 한, 특정 컨테이너가 자원을 독점해 다른 컨테이너가 밀려날 수 있다. 스케줄러도 어느 노드에 파드를 놓을지 판단할 근거가 없어, 자원이 꽉 찬 노드에 파드를 배치한 뒤 실행 시점에 실패하는 일이 생긴다.

컨테이너 하나가 메모리를 끝없이 늘리면 그 노드의 다른 워크로드까지 함께 죽고, CPU를 계속 점유하면 옆 컨테이너의 응답이 느려진다. 자원 요구량을 선언하지 않은 채로는 이런 충돌을 예방할 방법이 없다.

#2핵심 질문

컨테이너가 쓸 CPU와 메모리를 미리 선언하게 해서 스케줄링과 실행 시점 자원 사용을 함께 통제하려면 어떻게 해야 하는가?

#3동작 예시

컨테이너에 requests: cpu 250m(0.25코어), limits: memory 256MiB를 지정한다. 스케줄러는 이 파드를 배치할 때 노드에 최소 0.25코어만큼의 여유가 있는지 보고, kubelet은 그 노드에서 컨테이너 메모리가 256MiB를 넘지 않도록 강제한다. 노드에 여유가 많으면 이 컨테이너는 0.25코어보다 더 많은 CPU를 일시적으로 쓸 수도 있다.

#4동작 과정

  1. 요구량 선언파드 템플릿의 각 컨테이너에 requests(보장받을 최소량)와 limits(넘을 수 없는 최대량)를 적는다. 이 선언이 있어야 이후 판단이 가능해진다.
  2. 스케줄링 판단kube-scheduler가 파드의 requests 합계를 보고 그만큼 자원을 제공할 수 있는 노드를 고른다. 요구량을 선언한 덕분에 배치가 실행 전에 결정된다.
  3. 런타임 강제kubelet과 컨테이너 런타임이 limits를 집행해, requests는 최소한 그 컨테이너 몫으로 확보하고 limits를 넘는 사용은 막는다. 그 결과 한 컨테이너가 노드 전체 자원을 잡아먹지 못한다.

#5한 줄 요약

컨테이너별 CPU·메모리 requests와 limits를 선언하게 해 스케줄러의 배치 판단과 kubelet의 런타임 자원 집행을 하나로 묶는 것

동적 리소스 할당(DRA)

GPU 같은 특수 장치를 DeviceClass·ResourceClaim 등 API로 선언적으로 요청·할당하는 동적 리소스 할당 개념.

#1문제 상황

GPU, FPGA, 네트워크 가속기 같은 특수 장치는 개수와 종류가 노드마다 다르고 같은 종류라도 세부 속성이 제각각이다. 기존에는 이런 장치를 정수 개수로만 요청할 수 있어, 어떤 장치가 어떤 속성을 가졌는지 세밀하게 고르거나 여러 컨테이너가 한 장치를 나눠 쓰게 만들기 어려웠다.

이 방식으로는 새 장치 종류가 들어올 때마다 스케줄러와 노드에 별도 처리를 붙여야 했고, 장치의 상태나 속성을 파드 정의에 반영하는 것도 번거로웠다.

#2핵심 질문

특수 장치를 개수만이 아니라 속성과 종류까지 선언적으로 요청하고 여러 파드가 나눠 쓰도록 하려면 어떻게 해야 하는가?

#3동작 예시

클러스터 관리자가 DeviceClass(장치 종류 정의)를 만들어 두면, 사용자는 ResourceClaim(장치 요청서)에 필요한 장치 속성을 적고 파드에서 그 claim을 참조한다. Kubernetes는 조건에 맞는 장치를 골라 claim에 할당하고, 그 장치에 접근할 수 있는 노드에 파드를 배치한다. 이는 PersistentVolumeClaim으로 스토리지를 요청하는 방식과 비슷한 경험을 준다.

#4동작 과정

  1. 클래스 정의장치 드라이버와 클러스터 관리자가 DeviceClass로 어떤 장치를 어떤 속성 기준으로 제공할지 선언한다. 요청 가능한 대상이 미리 정리된다.
  2. claim으로 요청사용자가 ResourceClaim에 원하는 장치 조건을 적고 파드가 이를 참조한다. 파드 정의와 실제 장치 배정이 분리된다.
  3. 할당과 배치스케줄러가 조건에 맞는 장치를 claim에 할당하고 그 장치에 접근 가능한 노드에 파드를 놓는다. 장치 종류가 늘어도 같은 API 흐름으로 처리된다.

#5한 줄 요약

특수 장치를 DeviceClass와 ResourceClaim으로 선언적으로 요청·공유하게 해 장치 할당을 스케줄링과 자연스럽게 잇는 것

Service와 엔드포인트

Service는 레이블 셀렉터로 고른 Pod 집합에 안정적인 가상 IP와 DNS 이름을 제공하고 트래픽을 분산하는 추상화이며, 엔드포인트(EndpointSlice)는 그 뒤에서 실제 트래픽을 받을 Pod 주소 목록을 추적한다.

#1문제 상황

Deployment로 앱을 굴리면 파드는 필요에 따라 계속 생성되고 삭제되며, 각 파드는 자기 IP를 새로 받는다. 그래서 클라이언트가 특정 파드 IP로 직접 연결하면 그 파드가 사라지는 순간 연결이 끊기고, 살아 있는 파드가 몇 개인지 이름이 무엇인지도 실행 중에는 알기 어렵다.

파드 IP를 코드에 박아 두는 방식은 이렇게 계속 바뀌는 대상을 따라가지 못한다. 사용하는 쪽 애플리케이션을 매번 고치지 않고도 안정적으로 접근할 방법이 필요하다.

#2핵심 질문

계속 생겼다 사라지는 파드 집합에, 클라이언트가 고정된 주소로 안정적으로 접근하게 하려면 어떻게 해야 하는가?

#3동작 예시

레이블 셀렉터 app=web을 가진 Service를 만들면, 셀렉터에 맞는 모든 web 파드가 이 Service 뒤에 묶인다. 클라이언트는 개별 파드 IP 대신 Service의 가상 IP나 DNS 이름으로 접속하고, 트래픽은 그 뒤의 살아 있는 파드 중 하나로 분산된다. 파드가 교체돼도 클라이언트가 보는 주소는 그대로다.

#4동작 과정

  1. 셀렉터로 대상 묶기Service가 레이블 셀렉터로 조건에 맞는 파드 집합을 정의한다. 클라이언트는 개별 파드가 아니라 이 집합을 상대하게 된다.
  2. 가상 IP와 DNS 부여Service에 안정적인 가상 IP(ClusterIP)와 DNS 이름이 주어진다. 클라이언트는 이 고정 주소로 접속한다.
  3. 엔드포인트 추적과 분산EndpointSlice(실제 트래픽을 받을 준비된 파드 주소 목록)가 그 뒤에서 갱신되고, 프록시가 그 목록으로 트래픽을 나눈다. 파드가 바뀌어도 주소록만 갱신되면 연결이 유지된다.

#5한 줄 요약

레이블로 고른 파드 집합에 안정적인 가상 IP와 DNS 이름을 주고, 그 뒤의 실제 파드 주소 목록을 EndpointSlice로 추적해 트래픽을 분산하는 것

Ingress와 Gateway API

Ingress는 클러스터 외부의 HTTP/HTTPS 트래픽을 호스트·경로 규칙에 따라 내부 Service로 라우팅하는 리소스이고, Gateway API는 그 역할을 더 표현력 있게 나눈 차세대 라우팅 API 집합이다.

#1문제 상황

Service는 클러스터 안쪽에 안정적인 주소를 주지만, 외부에서 들어오는 HTTP/HTTPS 트래픽을 호스트나 경로에 따라 여러 서비스로 나눠 보내려면 별도 장치가 필요하다. 서비스마다 외부 노출용 로드밸런서를 따로 두면 비용과 관리 부담이 커진다.

또 Service 단위 노출만으로는 example.com/api와 example.com/web을 각각 다른 서비스로 보내거나, 한 진입점에서 TLS를 종료하는 같은 규칙을 한 곳에 모아 정의하기 어렵다.

#2핵심 질문

외부 HTTP/HTTPS 트래픽을 호스트와 경로 규칙에 따라 내부 서비스 여러 개로 한 진입점에서 나눠 보내려면 어떻게 해야 하는가?

#3동작 예시

Ingress 리소스에 "호스트가 example.com이고 경로가 /api인 요청은 api-svc로, 나머지는 web-svc로 보낸다"는 규칙을 적는다. Ingress 컨트롤러가 이 규칙을 읽어 실제 프록시 설정으로 반영하면, 클라이언트는 하나의 주소로 접속하지만 경로에 따라 다른 서비스가 응답한다.

#4동작 과정

  1. 규칙 정의Ingress 리소스에 호스트·경로와 그에 대응할 백엔드 Service를 적는다. 라우팅 의도가 API 객체로 선언된다.
  2. 컨트롤러 반영Ingress 컨트롤러가 이 규칙을 감시해 실제 로드밸런서·프록시 설정으로 바꾼다. 선언만 하면 트래픽 경로가 만들어진다.
  3. 요청 분기외부 요청이 진입점에 도착하면 호스트와 경로 규칙에 따라 알맞은 내부 서비스로 전달되고, 필요하면 TLS 종료도 이 지점에서 처리된다.

#5한 줄 요약

클러스터 외부의 HTTP/HTTPS 트래픽을 호스트·경로 규칙으로 정의해 여러 내부 서비스로 라우팅하는 진입점을 제공하는 것

DNS와 트래픽 라우팅

클러스터 DNS(CoreDNS)는 Service와 Pod에 이름을 부여해 Service 이름이나 파드별 DNS 레코드로 접근하도록 하고, 라우팅 규칙이 그 이름을 실제 엔드포인트로 이어 준다.

#1문제 상황

Service가 가상 IP를 받아도 그 IP를 애플리케이션 코드에 직접 적으면, 서비스를 옮기거나 다시 만들 때마다 설정을 고쳐야 한다. 파드 IP도 마찬가지로 계속 바뀌므로 IP를 하드코딩하는 방식은 유지보수가 어렵다.

또 클러스터 안에는 이름이 같은 서비스가 여러 네임스페이스에 존재할 수 있어, 어느 범위의 이름을 찾는지 구분해 주지 않으면 엉뚱한 대상을 가리킬 수 있다.

#2핵심 질문

IP 대신 이름으로 서비스와 파드에 접근하고, 이름 조회 범위를 네임스페이스에 맞게 다루려면 어떻게 해야 하는가?

#3동작 예시

prod 네임스페이스의 data 서비스를 test 네임스페이스의 파드에서 쓸 때, 그냥 data로 조회하면 파드 자신의 네임스페이스인 test만 찾아 결과가 없고, data.prod로 조회하면 원하는 서비스를 찾는다. kubelet이 파드의 DNS 설정을 잡아 두기 때문에 컨테이너는 IP가 아니라 이 이름으로 접속할 수 있다.

#4동작 과정

  1. 레코드 발행Kubernetes가 Service와 Pod에 DNS 레코드를 만들어 클러스터 DNS에 게시한다. 이름과 대상을 잇는 정보가 준비된다.
  2. 파드 DNS 설정kubelet이 각 파드의 DNS 설정을 구성해, 네임스페이스와 클러스터 기본 도메인을 조회 목록에 넣는다. 조회 범위가 파드마다 정해진다.
  3. 이름 해석과 연결컨테이너가 이름으로 조회하면 네임스페이스 규칙에 따라 DNS가 답을 주고, 그 결과가 실제 엔드포인트로 이어진다. IP를 몰라도 접속이 성립한다.

#5한 줄 요약

서비스와 파드에 DNS 이름을 부여하고 네임스페이스 기준으로 조회 범위를 정해, IP 대신 이름으로 안정적으로 접근하게 하는 것

네트워크 정책과 클러스터 네트워킹

NetworkPolicy는 Pod 간 인그레스·이그레스 트래픽을 레이블과 포트 기준으로 허용·차단하는 규칙이며, 클러스터 네트워킹은 모든 Pod가 서로 통신하도록 만드는 CNI 기반 네트워크 모델을 말한다.

#1문제 상황

기본 클러스터 네트워크에서는 모든 파드가 서로 통신할 수 있다. 편리하지만, 침해당한 파드 하나가 있으면 같은 클러스터의 다른 파드로 마음대로 접근할 수 있어 피해 범위가 넓어진다.

IP나 포트 수준에서 누가 누구와 통신할 수 있는지 제한하려 해도, 파드 IP는 계속 바뀌기 때문에 방화벽 규칙처럼 고정 주소로 관리하기가 어렵다.

#2핵심 질문

파드 IP가 계속 바뀌는 환경에서 누가 누구와 통신할 수 있는지 레이블과 포트 기준으로 제한하려면 어떻게 해야 하는가?

#3동작 예시

role=db 파드에 "role=api 파드로부터 오는 5432 포트 트래픽만 허용"하는 NetworkPolicy를 적용한다. 그러면 다른 파드가 아무리 같은 네트워크에 있어도 db 파드에 접속하지 못한다. 이 규칙이 실제로 강제되려면 클러스터가 NetworkPolicy를 지원하는 네트워크 플러그인을 써야 한다.

#4동작 과정

  1. 대상 선택NetworkPolicy가 레이블 셀렉터로 규칙을 적용할 파드를 고른다. 고정 IP 대신 레이블로 대상을 지정한다.
  2. 허용 규칙 정의인그레스와 이그레스 규칙에 허용할 상대 파드·네임스페이스·IP 대역과 포트를 적는다. 명시된 흐름만 통과하도록 경계가 정해진다.
  3. 플러그인이 집행CNI 네트워크 플러그인이 이 규칙을 실제 패킷 필터링으로 반영한다. 그 결과 허용되지 않은 연결은 파드에 도달하지 못한다.

#5한 줄 요약

파드 간 인그레스·이그레스 트래픽을 레이블과 포트 기준으로 허용·차단해 클러스터 내부 통신 범위를 통제하는 것

스토리지 — 볼륨과 영구 볼륨06-01

볼륨 기초

컨테이너가 쓰는 데이터를 Pod 수명과 분리해 보관하려고 파드에 마운트하는 저장 공간으로, emptyDir·hostPath·configMap 등 다양한 종류가 있다.

#1문제 상황

컨테이너의 디스크 파일은 컨테이너가 멈추거나 다시 시작되면 사라진다. 로그나 임시 데이터라면 괜찮지만 설정 파일이나 처리 결과를 컨테이너 안에만 두면 재시작 때마다 유실된다.

또 같은 파드 안의 두 컨테이너가 데이터를 주고받거나, 파드를 넘어 데이터를 유지해야 할 때 컨테이너 파일시스템만으로는 방법이 없다.

#2핵심 질문

컨테이너가 다시 시작돼도 데이터를 남기고, 같은 파드의 컨테이너끼리 파일을 공유하려면 어떻게 해야 하는가?

#3동작 예시

파드에 emptyDir 볼륨을 정의하고 두 컨테이너가 그 볼륨을 각자 경로에 마운트하면, 한 컨테이너가 쓴 파일을 다른 컨테이너가 바로 읽는다. ConfigMap을 볼륨으로 마운트하면 설정 파일이 컨테이너 안에 파일로 나타나고, 파드가 교체돼도 볼륨 정의에 따라 다시 채워진다.

#4동작 과정

  1. 볼륨 정의파드 스펙의 volumes에 emptyDir, hostPath, configMap 등 목적에 맞는 종류를 적는다. 파드 수준에서 저장 공간이 선언된다.
  2. 컨테이너에 마운트각 컨테이너의 volumeMounts로 그 볼륨을 특정 경로에 연결한다. 컨테이너는 이 경로를 통해 데이터에 접근한다.
  3. 공유와 유지같은 볼륨을 여러 컨테이너가 함께 쓰면 파일이 공유되고, 종류에 따라 파드 재시작이나 그 이상의 수명 동안 데이터가 남는다. 컨테이너 수명과 데이터 수명이 분리된다.

#5한 줄 요약

컨테이너 파일시스템과 분리된 저장 공간을 파드에 마운트해, 데이터를 공유하고 컨테이너 재시작 너머로 유지하는 것

스토리지 — 볼륨과 영구 볼륨06-02

영구 볼륨과 프로비저닝

관리자가 미리 만들거나 스토리지 클래스로 동적 생성하는 클러스터 차원의 저장소(PV)를, Pod의 요청(PVC)과 연결해 쓰는 방식이다.

#1문제 상황

Pod 안에서 쓰는 일반 볼륨은 Pod와 수명을 같이한다. Pod가 삭제되면 그 안에 저장한 데이터도 함께 사라지고, 다른 Pod가 같은 데이터를 이어받을 방법도 없다. 또한 컨테이너 이미지나 코드가 "스토리지가 NFS인지 클라우드 디스크인지"를 직접 알아야 하면, 같은 애플리케이션을 다른 환경으로 옮길 때마다 스토리지 설정을 고쳐야 한다.

#2핵심 질문

Pod의 수명과 무관하게 데이터를 유지하고, 스토리지의 실제 구현을 몰라도 원하는 용량을 요청해 쓸 수 있게 하려면 어떻게 해야 하는가?

#3동작 예시

PVC에 5Gi와 접근 모드를 적어 제출하면, 클러스터는 조건에 맞는 PV를 찾아 연결한다. 관리자가 미리 만들어 둔 PV가 있으면 그것을 쓰고, StorageClass가 지정되어 있으면 스토리지 시스템이 그 자리에서 새 볼륨을 만들어 준다. Pod는 그 PVC를 볼륨으로 마운트하기만 하면 실제 스토리지가 무엇인지 알 필요가 없다.

#4동작 과정

  1. 요청(PVC) 생성사용자가 용량·접근 모드·StorageClass를 적은 PersistentVolumeClaim을 만든다. 이는 Pod가 노드 자원을 요청하듯 스토리지를 요청하는 오브젝트다.
  2. 볼륨 확보와 바인딩컨트롤 플레인이 조건에 맞는 PersistentVolume을 찾아 PVC와 1:1로 묶는다. 미리 만든 PV가 없고 StorageClass가 있으면 동적 프로비저닝(요청 시 자동 생성)으로 새 PV를 만든다.
  3. Pod에 마운트Pod가 PVC 이름으로 볼륨을 참조하면 연결된 PV의 실제 저장소가 컨테이너 안 경로에 마운트된다. PV는 Pod와 별개 수명을 가지므로 Pod가 사라져도 데이터는 남는다.

#5한 줄 요약

스토리지의 실제 구현과 사용을 분리해, Pod 수명과 무관하게 데이터를 유지하고 용량을 요청해 쓰게 하는 것

스냅샷과 클로닝

기존 볼륨의 특정 시점 상태를 복사해 두는 스냅샷과, 그 데이터 소스로 새 볼륨을 복제하는 CSI 볼륨 클로닝 기능이다.

→ 06-02 참조

#1문제 상황

운영 중인 볼륨의 데이터를 잃지 않으려면 특정 시점 상태를 통째로 복사해 두어야 하는데, 스토리지마다 복사 방식과 명령이 제각각이다. 게다가 기존 볼륨과 같은 내용으로 새 볼륨을 만들려 해도 스토리지별 도구를 따로 배워야 하고, 배포 파일에는 그런 복제 절차를 표현할 방법이 없었다.

#2핵심 질문

스토리지 종류와 무관하게 볼륨의 특정 시점 복사본을 만들고, 그 복사본으로 새 볼륨을 복제하려면 어떻게 해야 하는가?

#3동작 예시

PVC를 가리키는 VolumeSnapshot을 만들면 CSI 드라이버가 그 볼륨의 현재 상태를 스냅샷으로 뜬다. 이후 그 스냅샷을 dataSource로 지정한 새 PVC를 만들면, 스냅샷 내용이 채워진 별도 볼륨이 생성된다. 복원과 복제가 모두 같은 방식으로 이뤄진다.

#4동작 과정

  1. 스냅샷 요청사용자가 대상 PVC와 VolumeSnapshotClass를 적은 VolumeSnapshot을 만든다. 클래스는 그 스토리지에 맞는 드라이버와 속성을 지정한다.
  2. 스냅샷 생성CSI 드라이버가 볼륨의 특정 시점 상태를 복사해 VolumeSnapshotContent를 만들고, 이를 VolumeSnapshot과 묶는다.
  3. 복제·복원새 PVC의 dataSource에 스냅샷이나 기존 PVC를 적으면 드라이버가 그 내용으로 새 볼륨을 만든다. 원본은 그대로 두고 복사본만 새로 생긴다.

볼륨의 특정 시점 상태를 표준 API로 복사해 두고, 그 복사본으로 새 볼륨을 복제·복원하게 하는 것

스토리지 — 볼륨과 영구 볼륨06-04

스토리지 운영 태스크

기본 StorageClass 변경, PV 회수 정책·접근 모드 변경, 스토리지 사용량 제한 등 클러스터 스토리지를 관리하는 운영 작업이다.

#1문제 상황

클러스터에는 StorageClass가 여러 개 있고, PVC에 클래스를 적지 않으면 기본으로 표시된 하나가 자동으로 쓰인다. 설치 시 정해진 기본값이 워크로드에 맞지 않거나, 볼륨을 다 쓴 뒤 데이터를 남길지 지울지 정하는 회수 정책이 상황과 어긋나도 각 오브젝트를 따로 손대지 않으면 그대로 유지된다. 스토리지가 계속 늘어나도 상한이 없으면 사용량이 무한정 커질 수 있다.

#2핵심 질문

기본 StorageClass, 회수 정책, 접근 모드, 사용량 한도처럼 클러스터 차원의 스토리지 동작을 운영자가 어떻게 바꾸고 통제하는가?

#3동작 예시

kubectl patch로 기본 StorageClass의 어노테이션을 옮기면, 이후 클래스를 지정하지 않은 PVC는 새 기본 클래스로 프로비저닝된다. 또 PV의 reclaimPolicy를 Retain에서 Delete로 바꾸면, 그 PV가 해제될 때 실제 스토리지도 함께 삭제된다.

#4동작 과정

  1. 기본 클래스 지정대상 StorageClass에 기본 표시 어노테이션을 붙이고 기존 기본 클래스에서는 뗀다. 클래스를 안 적은 PVC가 어디로 갈지가 바뀐다.

구성(ConfigMap·Secret)

애플리케이션 설정값과 비밀번호·토큰 같은 민감 정보를 컨테이너 이미지와 분리해 클러스터 오브젝트로 저장하고 Pod 에 주입하는 자원으로, ConfigMap 은 일반 설정을, Secret 은 민감 데이터를 담는다.

#1문제 상황

설정값과 비밀번호를 코드나 컨테이너 이미지 안에 하드코딩하면, 개발·운영 환경마다 값이 달라질 때 이미지를 다시 빌드해야 하고 민감 정보가 이미지에 그대로 남아 유출 위험이 커진다. 같은 이미지를 여러 환경에 올리면서 환경별 값만 바꾸는 것도 어렵다.

#2핵심 질문

환경마다 달라지는 설정과 민감 정보를 이미지 밖으로 분리해, 같은 이미지를 그대로 두고 주입할 수 있는가?

#3동작 예시

ConfigMap에 DATABASE_HOST=db-svc 같은 키-값을 담아 두고, Pod가 이를 환경 변수로 읽게 하거나 볼륨으로 마운트해 설정 파일로 쓰게 한다. 비밀번호·토큰처럼 민감한 값은 Secret에 담아 같은 방식으로 주입한다. 이미지에는 값이 없고 배포 시점에 클러스터 오브젝트에서 채워진다.

#4동작 과정

  1. 오브젝트 생성일반 설정은 ConfigMap에, 민감 데이터는 Secret에 키-값으로 저장한다. Secret은 별도 타입으로 다뤄 노출을 줄인다.
  2. Pod에 연결Pod가 ConfigMap·Secret을 환경 변수, 명령 인자, 또는 볼륨 안의 파일로 참조한다. 컨테이너는 값을 직접 들고 있지 않다.
  3. 값 갱신 반영볼륨으로 마운트한 설정은 원본 오브젝트가 바뀌면 파일 내용도 갱신되고, 환경 변수로 넣은 값은 Pod를 다시 만들 때 반영된다. 어느 쪽이든 이미지 재빌드 없이 여러 Pod의 설정을 바꿀 수 있다.

보안 개요

클라우드 네이티브 환경에서 클러스터를 이루는 계층별(클라우드·클러스터·컨테이너·코드)로 공격 표면을 이해하고, Kubernetes 가 제공하는 보안 기능과 책임 범위를 조망하는 개념이다.

#1문제 상황

클러스터는 클라우드 인프라, 노드 OS, 컨테이너 런타임, 애플리케이션 코드가 겹겹이 쌓인 구조라 한 겹만 뚫려도 전체가 위험해진다. 그런데 각 보안 조치를 어디까지 클러스터가 책임지고 어디부터 사용자 책임인지 구분하지 않으면, 중요한 층을 비워 두거나 이미 제공되는 기능을 중복 구현하게 된다.

#2핵심 질문

클러스터를 이루는 여러 계층에서 공격 표면을 어떻게 나눠 보고, 각 계층의 보안을 어디까지 Kubernetes가 책임지는가?

#3동작 예시

API 서버는 TLS로 통신 구간을 암호화하고, 저장 데이터 암호화(encryption at rest)를 켜면 저장소에 남는 값도 암호문이 된다. 인증·인가를 거쳐 API 접근을 제한하고, 민감 정보는 Secret으로 따로 다룬다. 이런 조치가 각각 어느 계층의 어떤 문제를 막는지를 함께 보는 것이 이 개요의 목적이다.

#4동작 과정

  1. 계층 나누기클라우드·인프라, 클러스터, 컨테이너, 코드 네 계층으로 나눠 각 계층의 공격 지점을 정리한다. 어느 계층이 누구 책임인지 경계가 드러난다.
  2. 기본 통제 적용API 접근 제어(TLS, 인증·인가), 저장 암호화, Secret 같은 Kubernetes 기본 기능을 배치한다. 통제되지 않은 접근 경로를 줄인다.
  3. 점검·강화보안 체크리스트로 계층별 항목을 대조하고, 멀티테넌시 같은 환경에서는 격리 요구를 더한다. 빠진 층을 찾아 보완한다.

인증과 인가

API 서버에 접근하는 사용자·프로세스의 신원을 확인하는 인증(Authentication)과, 확인된 신원이 어떤 동작을 할 수 있는지 권한을 판정하는 인가(Authorization) 절차다.

#1문제 상황

API 서버에는 여러 사용자와 클러스터 내부 프로세스가 접근한다. 아무 확인 없이 요청을 받으면 누구든 남의 리소스를 읽거나 지울 수 있고, 반대로 요청자를 확인했더라도 그가 무엇까지 해도 되는지 정하지 않으면 모든 권한을 그대로 주게 된다.

#2핵심 질문

API 서버에 접근한 주체가 누구인지 확인하고, 그 주체가 어떤 동작을 할 수 있는지 어떻게 판정하는가?

#3동작 예시

사용자가 유효한 인증서를 제시하면 클러스터 CA 서명 여부로 신원을 확인하고, 인증서의 common name에서 사용자 이름을 얻는다. 이어서 RBAC 규칙이 그 사용자에게 특정 네임스페이스의 Pod 조회 권한만 있는지 판정한다. 인증은 신원 확인, 인가는 허용 여부 판정으로 나뉜다.

#4동작 과정

  1. 인증요청이 제시한 인증서·토큰 등으로 주체의 신원을 확인한다. Kubernetes는 사용자를 서비스 어카운트(클러스터가 관리하는 워크로드 신원)와 일반 사용자로 나눈다.
  2. 인가확인된 신원에 대해 RBAC 같은 규칙으로 이 요청을 허용할지 판정한다. 권한이 없으면 요청은 거부된다.
  3. 어드미션 통과 후 저장인가까지 통과한 요청은 저장 전에 어드미션 단계를 거친 뒤 오브젝트로 반영된다. 접근 제어가 순서대로 겹쳐 적용된다.

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 어드미션 검증·변형저장 전에 어드미션 컨트롤러가 요청 내용을 검사(validating)하거나 고쳐 쓴다(mutating). 정책 위반은 차단되고 빠진 값은 채워진다.
  2. 서비스 어카운트 부여Pod에 서비스 어카운트를 지정해 API 접근용 신원을 준다. 이 신원에 인가 규칙을 걸어 권한을 제한한다.
  3. 인증서 발급·관리CertificateSigningRequest로 X.509 인증서를 신청하고 CA가 서명해 발급한다. 구성 요소 간 통신이 이 인증서로 검증된다.

Pod 를 최소 권한으로 실행하도록 만드는 표준(Pod Security Standards)과 이를 강제하는 어드미션 메커니즘으로, 권한 상승·호스트 접근·커널 기능 노출을 제한한다.

#1문제 상황

기존에는 PodSecurityPolicy 라는 어드미션 리소스로 파드의 권한을 제한했다. 클러스터 관리자가 정책 객체를 만들고 사용자·서비스어카운트에 바인딩해야 동작했으며, 설정이 복잡하고 정책이 사라지면 그 정책에 기대던 파드가 갑자기 만들어지지 않았다. 또 파드가 특권 모드로 실행되거나 호스트 경로를 마운트하면 노드 전체가 위험해질 수 있는데, 이런 권한 상승을 막을 일관된 기준이 없었다.

#2핵심 질문

#4동작 과정

  1. 제출사용자가 파드 매니페스트를 API 서버에 보내면, API 서버가 어드미션 체인에서 Pod Security Admission 을 호출한다.
  2. 판정네임스페이스 라벨로 정해진 등급(Privileged·Baseline·Restricted)에 따라 파드 스펙을 검사하고, 위반하면 생성·수정을 거부한다.
  3. 적용통과한 파드만 스케줄되어 실행되고, Restricted 등급은 seccomp·capabilities·runAsNonRoot 같은 하드닝 설정을 요구한다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 접근 통제TLS 로 API 트래픽을 암호화하고, 인증·인가(RBAC)·어드미션으로 누가 무엇을 할 수 있는지 제한한다.
  2. 데이터 보호etcd 저장 데이터를 암호화하고 시크릿 접근을 최소화하며 감사 로그로 API 요청을 기록한다.
  3. 노드·네트워크 보호노드 접근을 제한하고 sysctl·네트워크 정책으로 파드와 노드의 공격 표면을 줄인 뒤 서명된 아티팩트를 검증한다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 등록kubelet 이 API 서버에 자신을 등록해 Node 객체가 만들어지고, 컨트롤 플레인이 그 객체가 유효한지 확인한다.
  2. 감시kubelet 이 컨테이너 런타임과 함께 파드 스펙을 받아 실행하고, 주기적으로 노드와 파드 상태를 API 서버에 보고한다.
  3. 수명주기 처리노드 종료·재시작·스왑 같은 상황에서 kubelet 이 상태를 갱신하고, 조건과 taint 에 따라 파드 배치와 퇴거가 이뤄진다.

노드에는 OS와 Kubernetes 자체를 돌리는 시스템 데몬(system daemon — 노드가 정상 동작하도록 백그라운드에서 늘 실행되는 프로그램)이 함께 돌아간다. 기본 설정에서는 Pod가 노드의 전체 용량을 사용할 수 있어서, 시스템 데몬에 쓸 자원을 따로 떼어두지 않으면 Pod와 시스템 데몬이 같은 CPU·메모리를 두고 경쟁하게 된다. 그 결과 노드 전체가 자원 부족 상태에 빠지는 문제가 생긴다.

#2핵심 질문

시스템 데몬과 워크로드가 한 노드에서 자원을 두고 경쟁하지 않도록 어떻게 배분할 것인가?

#3동작 예시

노드에 8GiB 메모리가 있고 시스템 데몬에 1GiB를 예약해 두면, 스케줄러는 이 노드에 Pod를 배치할 때 7GiB만 가용하다고 보고 그 범위 안에서만 Pod를 올린다. 실제 메모리가 꽉 차서 데몬이 밀려나는 일이 없도록, 배치 단계에서부터 예약분을 제외하고 계산하는 방식이다.

#4동작 과정

  1. 가용 용량 계산kubelet이 노드의 전체 용량에서 시스템 데몬용으로 예약한 양(kube-reserved, system-reserved)과 축출 임계값(eviction threshold — 자원이 부족할 때 Pod를 내보내는 기준선)을 빼서 Node Allocatable(할당 가능 용량)을 계산한다.
  2. 스케줄링 반영계산된 Node Allocatable이 노드의 배치 가능 자원으로 API 서버에 알려지고, 스케줄러는 이 값만 보고 Pod를 배치하므로 예약분은 처음부터 제외된다. 그래서 데몬이 쓸 자리가 남는다.
  3. 정책 적용CPU 관리 정책·메모리 관리 정책·토폴로지 관리 정책을 kubelet 설정 파일에 지정해, 예약분 설정과 함께 노드마다 워크로드 밀도에 맞는 자원 배분을 완성한다.

설치 개요와 환경 선택

Kubernetes를 학습용·개발용·운영용 중 어떤 환경에 어떤 도구로 설치할지 결정하는 출발점으로, minikube·kind 같은 로컬 도구부터 클라우드·프로덕션 도구까지 선택지를 안내하는 개요다.

#1문제 상황

Kubernetes를 처음 접하면 클러스터를 어디에 어떻게 올려야 할지부터 막힌다. 노트북에 직접 설치하는 방식, 클라우드 관리형 서비스, 데이터센터용 도구가 각각 다르고, 유지보수 부담·보안·통제 수준·보유 자원·운영 인력에 따라 적합한 선택이 달라진다. 환경을 잘못 고르면 학습 목적에는 과한 구성이 되거나, 반대로 운영에 필요한 통제를 못 갖추게 된다.

#2핵심 질문

내 목적과 여건에 맞는 Kubernetes 설치 방식과 환경은 무엇인가?

#3동작 예시

Kubernetes를 배우는 단계라면 커뮤니티가 지원하는 로컬 도구로 노트북에 클러스터를 띄우는 것이 가장 빠르고, 직접 관리하고 싶지 않다면 인증된 관리형 서비스를 고르면 된다. 이때 kube-apiserver나 kube-proxy 같은 컴포넌트는 가능한 한 컨테이너 이미지로 배포하고 Kubernetes가 그 이미지들을 관리하게 하는 것이 권장된다. 다만 컨테이너를 실행하는 주체인 kubelet은 이 방식에 포함될 수 없다.

#4동작 과정

  1. 목적 판별학습용인지 운영용인지 먼저 정하고, 학습 환경과 프로덕션 환경에 맞는 도구 목록을 확인한다. 유지보수 용이성·보안·통제·자원·운영 전문성 중 무엇을 우선할지 정한다.
  2. 환경 선택로컬이면 커뮤니티 지원 도구로, 직접 관리가 부담이면 관리형 서비스로, 직접 구축이면 배포 도구나 턴키 클라우드 솔루션으로 방향을 정한다. 이때 컨테이너 런타임(container runtime — 컨테이너를 실제로 실행하는 소프트웨어)을 무엇으로 쓸지도 함께 정한다.
  3. 적용과 검증선택한 방식으로 클러스터를 설치하고 노드 구성이 제대로 됐는지 검증한다. 규모가 큰 클러스터나 여러 존에 걸친 구성이 필요하면 그에 맞는 고려사항을 추가로 확인한다.

kubeadm으로 클러스터 구축

kubeadm init과 kubeadm join으로 컨트롤 플레인과 워커 노드를 초기화·연결해 실제 프로덕션급 Kubernetes 클러스터를 구성하는 절차다.

#1문제 상황

Kubernetes 클러스터를 손으로 구성하려면 인증서 발급, 컴포넌트 설정, 노드 간 연결, 네트워크 설정을 하나씩 맞춰야 한다. 이 과정은 단계가 많고 순서를 틀리면 클러스터가 뜨지 않아, 처음 시도하는 사람은 어디서 잘못됐는지 찾기 어렵다. 게다가 그렇게 만든 클러스터가 모범 사례를 따르는지, 적합성 검사(Conformance test — Kubernetes 규격을 지키는지 확인하는 시험)를 통과하는지도 보장되지 않는다.

#2핵심 질문

모범 사례를 따르는 클러스터를 최소한의 수작업으로 어떻게 세울 것인가?

#3동작 예시

kubeadm init을 컨트롤 플레인 노드에서 한 번 실행하면 그 노드가 컨트롤 플레인이 되고, 출력되는 join 명령을 워커 노드에서 실행하면 그 노드가 클러스터에 합류한다. 이 두 명령만으로 최소 동작 클러스터(minimum viable cluster — 규격을 만족하는 가장 기본적인 클러스터)가 구성된다.

#4동작 과정

  1. 사전 준비리눅스 머신을 준비하고 머신마다 2GiB 이상 메모리를 확보하며, 컨트롤 플레인 노드에는 CPU를 2개 이상 두고, 모든 머신 사이에 네트워크가 완전히 연결되게 한다. 여기에 컨테이너 런타임과 kubeadm을 설치한다.
  2. 컨트롤 플레인 초기화컨트롤 플레인 노드에서 kubeadm init을 실행해 인증서와 컴포넌트를 세우고 클러스터를 부트스트랩(초기화)한다. 이 과정에서 워커 노드가 합류할 때 쓸 부트스트랩 토큰(일회성 합류 자격 증명)이 만들어진다.
  3. 워커 노드 합류각 워커 노드에서 init이 출력한 kubeadm join 명령을 실행해 클러스터에 연결한다. 이후 kubeadm은 토큰 관리와 클러스터 업그레이드 같은 생애주기 기능도 제공한다.

kubeadm 참조

kubeadm init·join·upgrade·config·certs 등 kubeadm 하위 명령과 각 옵션의 사용법을 정리한 공식 레퍼런스다.

#1문제 상황

kubeadm은 클러스터를 세우고 관리하는 여러 하위 명령을 제공하는데, 각 명령이 어떤 동작을 하고 어떤 옵션을 받는지 일일이 기억하기 어렵다. 초기화를 되돌리거나, 인증서를 다루거나, 설정을 점검하려 할 때 정확한 명령과 옵션을 모르면 잘못된 조작으로 클러스터를 망가뜨릴 수 있다. 그래서 명령별 사용법을 한곳에 정리한 레퍼런스가 필요하다.

#2핵심 질문

kubeadm의 각 하위 명령과 옵션은 정확히 어떻게 사용하는가?

#3동작 예시

kubeadm init으로 만든 변경을 이 머신에서 되돌리고 싶으면 kubeadm reset을 사용하고, 클러스터 업그레이드는 kubeadm upgrade로 수행한다. 이때 각 명령이 제공하는 하위 단계와 옵션을 레퍼런스에서 확인해 필요한 것만 실행한다.

#4동작 과정

  1. 명령 확인kubeadm init은 컨트롤 플레인 노드를 부트스트랩하고, kubeadm join은 워커 노드를 클러스터에 합류시킨다는 것을 먼저 파악한다. 이 둘이 클러스터를 세우는 기본 경로다.
  2. 운영 명령 확인업그레이드는 kubeadm upgrade, 토큰 관리는 kubeadm token, 초기화 되돌리기는 kubeadm reset, 인증서 관리는 kubeadm certs로 수행한다는 것을 익힌다. 각 명령의 하위 단계와 옵션도 함께 확인한다.
  3. 설정 명령 확인kubeadm config로 클러스터 설정을 다루고, kubeconfig·version 같은 나머지 명령과 구현 세부 사항까지 레퍼런스에서 확인해 필요한 조작을 정확히 실행한다.

#2핵심 질문

이미 돌아가는 kubeadm 클러스터를 안전하게 확장하고 갱신하려면 무엇을 해야 하는가?

#3동작 예시

#4동작 과정

  1. 노드 추가새 머신에서 kubeadm join을 실행해 리눅스 또는 윈도우 워커 노드를 기존 클러스터에 합류시킨다. 그래서 클러스터가 워크로드를 더 받을 수 있게 확장된다.
  2. 인증서 관리kubeadm certs로 클러스터 인증서를 점검하고 갱신한다. 그래서 인증서 만료로 클러스터가 멈추는 일을 미리 막는다.
  3. 업그레이드와 재구성kubeadm upgrade로 클러스터를 상위 버전으로 올리고, 필요하면 클러스터를 재구성하거나 패키지 저장소를 바꾼다. 리눅스 노드와 윈도우 노드는 각각의 절차에 따라 갱신한다.

서비스를 크게 끊지 않으면서 클러스터를 새 버전으로 올리고 점검하려면 어떻게 해야 하는가?

#3동작 예시

업그레이드할 때는 컨트롤 플레인을 먼저 새 버전으로 올리고, 그다음 클러스터의 노드를 올리고, kubectl 같은 클라이언트도 맞춰 올린다. 마지막으로 새 버전에서 바뀐 API에 맞게 매니페스트와 리소스를 조정한다. 새 버전의 변경 사항을 반영해 리소스 정의를 손보는 단계까지가 한 번의 업그레이드에 포함된다.

#4동작 과정

  1. 컨트롤 플레인 먼저클러스터의 컨트롤 플레인 컴포넌트를 새 버전으로 올린다. 그래서 새 버전의 API를 받아들일 준비가 갖춰진다.
  2. 노드와 클라이언트이어서 클러스터의 각 노드를 순서대로 갱신하고 kubectl 같은 클라이언트도 맞춰 올린다. 노드를 내려 점검할 때는 안전하게 드레인(drain — 노드에서 워크로드를 다른 곳으로 옮기고 비우는 것)해 서비스 중단을 줄인다.
  3. 리소스 조정새 버전에 딸린 API 변경에 맞게 매니페스트와 리소스를 조정한다. 그래서 업그레이드 뒤에도 워크로드가 정상 동작한다.

할당량과 네임스페이스 태스크

네임스페이스별로 CPU·메모리 등의 자원 할당량을 제한하고 네임스페이스로 클러스터를 나누는 태스크다.

#1문제 상황

하나의 클러스터를 여러 팀이 함께 쓰면, 한 네임스페이스(namespace — 클러스터 안에서 리소스를 논리적으로 나누는 단위)의 Pod가 CPU와 메모리를 마음대로 많이 쓰며 다른 팀의 몫까지 잡아먹을 수 있다. 상한이 없으면 특정 워크로드가 노드 자원을 독점해 다른 워크로드가 밀려나는 일이 생긴다. 그래서 네임스페이스별로 쓸 수 있는 총량을 정해둘 필요가 있다.

#2핵심 질문

한 클러스터를 여러 네임스페이스로 나눠 쓸 때 자원 총량을 어떻게 제한하는가?

#3동작 예시

네임스페이스 하나에 ResourceQuota 오브젝트를 만들고 그 안에 requests.cpu와 메모리 상한을 적으면, 그 네임스페이스에서 도는 모든 Pod가 쓸 수 있는 자원의 합이 이 값으로 제한된다. 예를 들어 메모리 상한을 정해두면 그 네임스페이스의 Pod들이 합쳐서 그 이상을 요청할 수 없다.

#4동작 과정

  1. 네임스페이스 분리먼저 네임스페이스를 만들어 이 실습의 리소스가 클러스터의 나머지와 격리되게 한다. 그래서 팀이나 목적별로 자원을 따로 셀 수 있게 된다.
  2. 할당량 정의ResourceQuota에 requests.cpu 같은 총량 상한을 적는다. 그래서 그 네임스페이스에서 쓸 수 있는 자원의 합이 정해진다.
  3. 세부 정책 적용필요하면 네임스페이스의 기본 메모리·CPU 요청과 제한, 최소·최대 제약, Pod 개수 할당량, API 오브젝트 할당량까지 설정한다. 그래서 네임스페이스 단위로 자원 쓰임새를 촘촘히 통제한다.

네트워크 정책 태스크

파드 간 트래픽을 허용·차단하는 NetworkPolicy 규칙을 선언하고 적용하는 태스크다.

#1문제 상황

쿠버네티스 클러스터에 아무 설정을 하지 않으면, 같은 클러스터 안의 모든 파드는 서로 자유롭게 통신할 수 있다. 프런트엔드 파드가 데이터베이스 파드에 직접 접속해도, 관계없는 다른 네임스페이스의 파드가 내부 서비스에 붙어도 기본적으로 막는 규칙이 없다.

이 기본 개방 상태는 편리하지만, 한 파드가 침해당하면 공격자가 클러스터 안의 다른 파드로 옮겨 다니기 쉬워 보안 경계가 사실상 없다. 그래서 "어떤 파드가 어떤 파드와 통신할 수 있는가"를 관리자가 직접 선언해서 통제할 방법이 필요했다.

#2핵심 질문

클러스터 안 파드 사이의 트래픽을 누가 어디로 보낼 수 있는지 규칙으로 선언해 통제하려면 어떻게 해야 하는가?

#3동작 예시

기본 네임스페이스에서 role=db 라벨이 붙은 파드로 가는 인바운드 트래픽을, role=frontend 라벨이 붙은 파드에서만 허용하는 예를 든다. 먼저 NetworkPolicy 오브젝트를 만들면서 podSelector 로 대상 파드(role=db)를 고르고, ingress 규칙의 from 에 podSelector 로 출처 파드(role=frontend)를 지정한다.

이 정책을 적용하면 같은 네임스페이스의 다른 파드가 db 파드의 포트에 접속을 시도해도 차단되고, frontend 라벨을 가진 파드의 트래픽만 통과한다. 정책이 하나도 없는 나머지 파드들은 여전히 기본 개방 상태로 남는다.

#4동작 과정

  1. 정책 오브젝트 생성관리자가 NetworkPolicy 매니페스트를 작성해 API 서버에 적용한다. 어떤 파드를 대상으로(podSelector), 어느 방향의(ingress/egress) 트래픽을, 어떤 출처에서 허용할지 선언한다. 이 시점에는 규칙이 선언만 된 상태다.
  2. 네트워크 제공자 적용클러스터 노드에서 실제 트래픽을 처리하는 네트워크 제공자(Antrea, Calico, Cilium, Kube-router 등 네트워크 정책을 지원하는 플러그인)가 이 정책을 감시하고 노드의 패킷 필터링 규칙으로 옮긴다. 제공자가 없으면 정책 오브젝트는 저장될 뿐 실제로 아무 트래픽도 막지 못한다.
  3. 트래픽 판정과 차단파드가 상대 파드로 패킷을 보낼 때 노드의 필터링 규칙이 정책에 맞는지 검사한다. 허용 규칙에 해당하면 통과시키고, 어떤 규칙에도 걸리지 않으면 차단해 전달하지 않는다. 그 결과 대상 파드는 지정된 출처의 트래픽만 받는다.

#5한 줄 요약

파드 간 트래픽 허용·차단 규칙을 선언형 오브젝트로 정의하고 네트워크 제공자가 이를 실제 패킷 필터링으로 집행하게 하는 것

TLS와 인증서 태스크

클러스터 내 서비스 통신에 쓰이는 TLS 인증서를 발급·배포·관리하는 태스크다.

#1문제 상황

클러스터 안에서 서비스끼리, 그리고 클라이언트가 API 서버와 통신할 때 평문으로 주고받으면 중간에서 내용을 훔쳐보거나 위조할 수 있다. 그래서 TLS로 암호화해야 하는데, 인증서를 사람이 일일이 발급하고 만료 전에 교체하는 방식은 파드 수가 늘수록 감당이 안 된다.

게다가 아무나 서명 요청을 보내면 안 되므로 신뢰할 수 있는 인증 기관(CA, 인증서에 서명해 주는 주체)의 통제 아래에서 발급돼야 한다. 클러스터가 이 발급·서명·배포·갱신을 API로 처리해 주는 절차가 필요했다.

#2핵심 질문

클러스터가 인증서 발급 요청을 받아 CA로 서명하고, 그 인증서를 워크로드에 배포·갱신하는 일을 어떻게 자동화할 수 있는가?

#3동작 예시

서비스가 클라이언트 인증서를 필요로 할 때, 관리자는 CertificateSigningRequest(CSR, 인증서 서명 요청) 오브젝트를 만들어 certificates.k8s.io API에 제출한다. 여기에는 서명받을 공개키와 신원 정보가 담긴다.

클러스터 관리자가 kubectl certificate approve로 이 요청을 승인하면, 컨트롤 플레인의 서명자가 요청에 서명해 완성된 인증서를 돌려준다. 신청한 쪽은 발급된 인증서를 받아 서비스에 설치하고, 그 인증서는 클러스터가 통제하는 CA를 신뢰하는 상대에게 유효하게 검증된다.

#4동작 과정

  1. CSR 제출워크로드나 관리자가 공개키와 신원을 담은 서명 요청 오브젝트를 만들어 certificates.k8s.io API에 등록한다. 이 단계에서 요청은 아직 승인도 서명도 되지 않은 대기 상태다.
  2. 승인과 서명클러스터 관리자가 해당 요청을 검토해 승인하면, 컨트롤 플레인의 인증서 서명자가 신청된 CA 키로 서명해 인증서를 생성한다. 승인되지 않은 요청은 서명되지 않아 쓸 수 없다.
  3. 발급·배포·갱신서명된 인증서가 요청 주체에게 전달되어 서비스에 설치된다. 만료 전에 교체하려면 새 요청을 내거나 kubelet 인증서 회전처럼 자동 갱신을 구성해, 사람 손을 거치지 않고 새 인증서로 바뀌게 한다.

dockershim·런타임 마이그레이션

제거된 dockershim에서 containerd 같은 CRI 호환 컨테이너 런타임으로 노드를 옮기는 태스크다.

#1문제 상황

예전 쿠버네티스는 컨테이너를 돌리기 위해 Docker Engine에 붙는 dockershim이라는 중간 계층을 노드에 내장하고 있었다. Docker Engine 자체는 쿠버네티스 전용이 아니라 자체 API를 쓰기 때문에, 쿠버네티스가 정한 표준 인터페이스인 CRI(Container Runtime Interface, 컨테이너 런타임이 갖춰야 할 공통 규격)와 맞물리도록 이 변환 계층이 필요했다.

문제는 이 계층을 쿠버네티스 프로젝트가 계속 유지해야 한다는 부담이었다. CRI를 직접 구현한 런타임이 이미 여럿 나온 상황에서, 별도 변환 계층을 안고 가는 대신 쿠버네티스는 1.20에서 dockershim 폐기를 예고하고 1.24 릴리스에서 제거했다. 그 결과 Docker Engine을 dockershim으로 쓰던 노드는 업그레이드 전에 다른 런타임으로 옮겨야 한다.

#2핵심 질문

dockershim이 제거된 뒤에도 노드에서 컨테이너를 계속 돌리려면 컨테이너 런타임을 어떻게 확인하고 무엇으로 바꿔야 하는가?

#3동작 예시

한 노드에서 kubectl get nodes -o wide로 상태를 보면 노드가 어떤 컨테이너 런타임을 쓰는지 드러난다. 여기에 docker://...로 표시되면 그 노드는 dockershim을 거쳐 Docker Engine을 쓰고 있다는 뜻이므로 마이그레이션 대상이다.

이 노드의 런타임을 containerd로 바꾸려면 kubelet 설정에서 컨테이너 런타임 소켓 경로를 CRI 규격의 containerd 소켓으로 바꾼다. 노드에서 kubelet을 재시작하면 kubelet이 이 소켓을 통해 containerd와 직접 대화하고, 그 뒤로는 dockershim 없이 파드가 뜨고 멈춘다.

#4동작 과정

  1. 영향 여부 확인노드가 어떤 런타임을 쓰는지 점검해 dockershim에 의존하는지 판단한다. Docker Engine을 런타임으로 쓰고 있다면 해당 노드가 마이그레이션 대상이다. 순수하게 containerd나 CRI-O를 이미 쓰고 있다면 dockershim 제거의 영향을 받지 않는다.
  2. 런타임 교체Docker Engine에서 containerd 같은 CRI 호환 런타임으로 노드를 옮긴다. kubelet이 바라보는 런타임 소켓을 CRI 엔드포인트로 바꾸고, 노드에 관련 소프트웨어와 CNI(파드 네트워크를 붙여 주는 플러그인) 설정을 갖춘다.
  3. 검증과 부수 작업 정리kubelet을 재시작해 노드가 정상 등록되고 파드가 뜨는지 확인한다. 런타임이 바뀌면 도커 소켓에 기대던 모니터링·보안 에이전트나 docker 명령 사용도 함께 손봐야 하며, CNI 플러그인 관련 오류가 나면 네트워크 설정을 점검한다.

#1문제 상황

애플리케이션을 파드 하나로 직접 띄우면 그 파드가 죽는 순간 서비스가 멈춘다. 파드를 여러 개 띄워도 어느 것을 늘리고 줄일지, 새 버전으로 바꿀 때 기존 파드를 언제 내릴지 사람이 판단해야 하므로 운영 부담이 크다.

상태를 저장하지 않는 애플리케이션과 각 인스턴스가 고유 이름과 저장소를 가져야 하는 애플리케이션은 요구가 다르다. 전자는 복제와 무중단 교체가 쉽지만, 후자는 순서와 식별자를 지켜야 하므로 같은 방식으로 다룰 수 없다. 두 경우를 각각 다루는 표준 워크로드가 필요했다.

#2핵심 질문

상태 없는 애플리케이션과 상태를 가진 애플리케이션을 각각 실행하고, 인스턴스 수를 조절하며 무중단으로 갱신하려면 어떻게 해야 하는가?

#3동작 예시

상태 없는 애플리케이션은 Deployment로 실행한다. Deployment에 원하는 복제본 수를 적어 두면 컨트롤러가 그 수만큼 파드를 맞춰 띄우고, 파드 하나가 죽으면 자동으로 새 파드를 만들어 수를 유지한다.

새 버전으로 바꿀 때는 이미지 태그를 바꿔 적용한다. 그러면 컨트롤러가 새 버전 파드를 하나씩 띄우면서 준비된 것을 확인한 뒤 기존 파드를 하나씩 내려, 잠깐의 전환을 거치며 서비스가 끊기지 않게 교체한다. 트래픽이 늘면 복제본 수를 올리는 scale로 파드를 더 띄운다.

#4동작 과정

  1. 워크로드 정의와 실행상태가 없으면 Deployment, 각 인스턴스에 고유 식별자와 저장소가 필요하면 StatefulSet으로 애플리케이션을 선언한다. 컨트롤러가 선언한 파드 사양대로 파드를 만들어 실행한다.
  2. 확장과 유지원하는 복제본 수를 바꾸면 컨트롤러가 파드를 늘리거나 줄여 그 수에 맞춘다. 파드가 비정상 종료되면 다시 만들어 원하는 수를 유지하고, PodDisruptionBudget으로 자발적 중단 시 최소 가용 수를 지킨다.
  3. 무중단 갱신새 버전 사양을 적용하면 컨트롤러가 새 파드를 띄우고 준비 상태를 확인한 뒤 기존 파드를 순차적으로 내린다. 문제가 생기면 이전 버전으로 되돌릴 수 있어, 서비스 중단 없이 버전을 바꾼다.

Job 운영 태스크

완료를 목표로 하는 일회성·배치 작업을 Job과 CronJob으로 실행하고, 병렬 처리·실패 정책·자동 정리를 구성하는 태스크 모음이다.

#1문제 상황

Deployment나 StatefulSet 같은 워크로드는 파드가 계속 떠 있는 것을 목표로 한다. 그런데 데이터 마이그레이션, 배치 집계처럼 한 번 끝나면 그만인 작업은 다르다. 이런 일을 계속 실행되는 워크로드로 돌리면 작업이 끝난 뒤에도 파드가 남아 자원을 낭비하고, 완료 여부를 따로 판단해야 한다.

또한 이런 작업은 여러 파드가 같은 일을 나눠 처리하거나, 실패한 파드만 다시 시도하거나, 정해진 시각마다 반복해야 하는 경우가 많다. 완료를 목표로 하고 병렬 처리·재시도·주기 실행을 다루는 별도 워크로드가 필요했다.

#2핵심 질문

끝나면 종료되는 일회성·배치 작업을, 병렬 처리와 실패 정책과 주기 실행까지 포함해 어떻게 안정적으로 돌릴 수 있는가?

#3동작 예시

한 번만 끝나면 되는 작업은 Job으로 만든다. 처리할 항목이 여러 개면 completions에 총 처리 개수, parallelism에 동시에 돌릴 파드 수를 적어, 파드 여러 개가 작업을 나눠 맡고 지정한 개수만큼 성공하면 Job이 완료로 표시된다.

실패한 파드는 Job이 정한 재시도 횟수 안에서 다시 실행된다. 정해진 시각마다 반복하려면 CronJob으로 감싸 스케줄을 적어 두면, 그 시각마다 컨트롤러가 새 Job을 만들어 실행한다.

#4동작 과정

  1. 작업 정의처리할 일의 성격에 맞춰 Job 사양을 쓴다. 총 완료 개수, 동시 실행 수, 재시도 한도를 정하고, 주기 실행이면 CronJob에 스케줄을 적는다. 이때 파드가 성공으로 끝나는 조건이 명확해야 한다.
  2. 병렬 실행과 실패 처리컨트롤러가 parallelism만큼 파드를 띄워 작업을 나눠 처리하게 한다. 파드가 실패하면 정책에 따라 다시 실행하거나 포기하고, 재시도해도 안 되는 실패는 backoffLimit 같은 한도로 멈춘다.
  3. 완료 확인과 정리지정한 개수만큼 파드가 성공하면 Job이 완료 상태가 된다. 끝난 Job과 파드는 남겨 두거나 정리 정책으로 자동 삭제해 자원을 회수하고, 주기 작업이면 다음 시각에 새 Job이 만들어진다.

완료를 목표로 하는 작업을 Job과 CronJob으로 정의해, 컨트롤러가 병렬 실행·재시도·주기 실행을 관리하고 끝나면 정리하게 하는 것

DaemonSet 태스크

모든(또는 일부) 노드에 Pod 하나씩을 띄워 로그 수집·모니터링 같은 노드 단위 데몬을 배포하고 롤링 업데이트·롤백하는 태스크 모음이다.

#1문제 상황

로그 수집기나 노드 모니터링 에이전트는 클러스터의 모든 노드에 하나씩 떠 있어야 한다. 이걸 Deployment로 띄우면 복제본 수가 노드 수와 맞지 않아 특정 노드에 몰리거나, 노드가 늘고 줄어도 자동으로 따라가지 못한다.

로그를 노드에서 직접 모으는 일처럼 노드마다 정확히 하나가 필요한 작업은, 노드가 추가될 때 자동으로 하나가 뜨고 노드가 사라지면 함께 정리돼야 한다. 또 이 에이전트들을 새 버전으로 바꿀 때 전체 노드를 한꺼번에 멈추지 않고 순차적으로 교체할 방법이 필요했다.

#2핵심 질문

모든 노드(또는 일부 노드)에 파드 하나씩을 자동으로 배치하고, 새 버전으로 순차 교체하거나 되돌리려면 어떻게 해야 하는가?

#3동작 예시

노드마다 로그 수집 파드를 하나씩 띄우려면 DaemonSet을 만든다. 사양에 파드 템플릿만 적어 두면 컨트롤러가 각 노드를 살펴 아직 해당 파드가 없는 노드마다 하나씩 배치한다.

새 노드가 클러스터에 추가되면 그 노드에도 자동으로 파드가 하나 생기고, 노드가 빠지면 그 위의 파드도 함께 사라진다. 일부 노드에만 띄우고 싶으면 nodeSelector나 어피니티로 대상 노드를 좁혀, 예를 들어 특정 라벨이 붙은 노드에만 배치하게 한다.

#4동작 과정

  1. 대상 노드 선택DaemonSet에 파드 템플릿을 정의하고, 필요하면 nodeSelector나 노드 어피니티로 어느 노드에 배치할지 좁힌다. 컨트롤러는 이 조건에 맞는 노드를 배치 대상으로 삼는다.
  2. 노드마다 하나 배치컨트롤러가 배치 조건에 맞는 각 노드에 파드가 하나씩 있는지 확인하고, 없는 노드에 파드를 만든다. 노드가 새로 추가되면 그 노드에도 자동으로 하나가 뜬다.
  3. 롤링 업데이트와 롤백파드 템플릿을 바꾸면 컨트롤러가 노드별로 파드를 하나씩 새 버전으로 교체한다. 새 버전에 문제가 있으면 이전 리비전으로 롤백해, 노드를 통째로 멈추지 않고 되돌린다.

#5한 줄 요약

오브젝트 관리 태스크

kubectl 명령형·선언형 방식과 Kustomize로 쿠버네티스 오브젝트를 생성·수정·패치·삭제하며 관리하는 태스크 모음이다.

#1문제 상황

오브젝트를 만들고 고치는 방식은 크게 두 가지다. 명령형은 kubectl create, kubectl edit처럼 명령을 한 줄씩 실행해 즉시 반영하는 방식이고, 선언형은 원하는 상태를 파일에 적어 두고 그것을 적용하는 방식이다.

명령을 하나씩 실행하면 무엇을 어떻게 바꿨는지 기록이 남지 않아, 나중에 같은 상태를 재현하거나 여러 환경에 똑같이 적용하기 어렵다. 반대로 파일을 손으로 관리하면 환경마다 조금씩 다른 값을 일일이 복사·수정해야 해서 실수가 늘고, 어떤 변경이 언제 들어갔는지 추적하기 힘들다.

#2핵심 질문

오브젝트를 명령형으로 즉시 다루면서도, 선언형 파일과 겹쳐 쓰는 변경을 재현 가능하고 추적 가능하게 관리하려면 어떻게 해야 하는가?

#3동작 예시

한 오브젝트의 복제본 수만 급히 늘릴 때는 kubectl patch로 바뀔 부분만 지정해 그 자리에서 고친다. 예를 들어 replica 수를 담은 조각만 보내면 나머지 필드는 건드리지 않고 그 값만 갱신된다.

여러 환경에 같은 구성을 반복 적용할 때는 파일을 선언형으로 관리한다. 공통 부분은 그대로 두고 환경별로 다른 값만 겹쳐 정의하는 Kustomize를 쓰면, 원본을 복사하지 않고도 환경마다 조금 다른 결과를 만들어 적용할 수 있다.

#4동작 과정

  1. 방식 선택급한 단일 변경은 kubectl 명령형으로 즉시 처리하고, 여러 번 재현하거나 여러 환경에 적용할 구성은 파일로 선언한다. 같은 오브젝트를 두 방식으로 번갈아 다루면 소유권이 엉킬 수 있어 주된 방식을 정한다.
  2. 적용과 패치선언형이면 작성한 파일을 kubectl apply로 적용해 원하는 상태와 현재 상태의 차이만 반영한다. 일부 필드만 고칠 때는 kubectl patch로 바뀔 부분만 보내 나머지를 유지한 채 갱신한다.
  3. 차이 확인과 정리적용한 뒤 kubectl diff로 파일과 실제 상태가 얼마나 다른지 확인하고, 필요 없는 오브젝트는 삭제한다. 선언형으로 관리하면 무엇을 적용했는지 기록이 남아 같은 상태를 다시 만들 수 있다.

#5한 줄 요약

#1문제 상황

Pod를 특별한 지정 없이 띄우면 컨테이너는 노드가 허용하는 만큼 CPU와 메모리를 마음대로 쓸 수 있다. 여러 Pod가 한 노드에 몰리면 한 컨테이너가 메모리를 크게 잡아 다른 컨테이너가 밀려나거나 노드 전체가 불안정해진다.

또 GPU나 그 밖의 특수 장치는 아무 Pod에나 자동으로 붙지 않는다. 어떤 Pod가 어떤 장치를 얼마나 쓸지 알려주는 절차가 없으면, 스케줄러는 그런 장치가 있는 노드를 알맞게 골라 배치하지 못한다.

#2핵심 질문

컨테이너마다 필요한 컴퓨팅 자원과 특수 장치를 어떻게 정확히 요청하고 제한할 것인가?

#3동작 예시

컨테이너에 resources.requests로 cpu: "250m", memory: "64Mi"를 적으면 스케줄러는 CPU 0.25코어와 메모리 64MiB를 낼 수 있는 노드를 골라 Pod를 배치한다. 여기에 resources.limits로 memory: "128Mi"를 함께 적으면 그 컨테이너가 128MiB를 넘겨 쓰려는 순간 메모리 부족으로 종료된다. GPU처럼 개수로 세는 확장 리소스는 requests와 limits에 같은 값을 적어야 하며, 해당 장치가 있는 노드에만 Pod가 간다.

#4동작 과정

  1. 자원 요청·제한 지정Pod 스펙에 컨테이너별 requests(보장받을 양)와 limits(넘길 수 없는 상한)를 적는다. 스케줄러는 requests 합계를 보고 노드를 고르고, 노드의 kubelet은 limits에 맞춰 CPU를 조절하고 메모리 초과 시 컨테이너를 종료한다.
  2. 확장 리소스·장치 할당nvidia.com/gpu 같은 확장 리소스나 DRA(장치를 종류·속성으로 골라 붙이는 방식)로 장치를 요청하면, 장치 플러그인이나 드라이버가 붙어 있는 노드에만 Pod가 배치되고 컨테이너에 장치가 연결된다. 장치 메타데이터는 파일 형태로 컨테이너에 노출되어 앱이 어떤 장치가 붙었는지 읽을 수 있다.
  3. 서비스 품질 결정·조정requests와 limits를 어떻게 적었는지에 따라 Pod의 QoS 등급(Guaranteed·Burstable·BestEffort)이 정해지고, 노드에 자원이 부족할 때 누구를 먼저 내보낼지가 이 등급으로 갈린다. 이후 필요한 경우 실행 중인 컨테이너나 Pod의 CPU·메모리 값을 재시작 없이 늘리거나 줄일 수 있다.

#1문제 상황

컨테이너 이미지를 그대로 띄우면 앱은 이미지에 들어 있는 기본 설정으로만 돈다. 설정 값이 바뀌어도 이미지를 다시 만들어야 하고, 앱이 살아 있는지 확인할 방법도 없으며, 여러 컨테이너가 같은 파일을 주고받을 통로도 없다.

또 이미지에는 자격 증명이나 환경별 주소가 하드코딩되기 쉽다. 민감 정보를 이미지에 넣지 않고 밖에서 주입하거나, 어떤 노드에 Pod를 올릴지, 어떤 계정 권한으로 실행할지를 세밀하게 정하는 수단이 없으면 운영이 곧 막힌다.

#2핵심 질문

이미지를 다시 만들지 않고 Pod와 컨테이너의 실행 방식·설정·상태 점검을 어떻게 세부 조정할 것인가?

#3동작 예시

ConfigMap에 앱 설정 값들을 키-값으로 담아 두고, Pod의 환경 변수나 볼륨으로 그 ConfigMap을 연결하면 설정이 컨테이너 안으로 들어간다. 여기에 liveness probe를 httpGet으로 걸어 두면 kubelet이 주기적으로 그 주소를 찔러 보고, 응답이 없으면 컨테이너를 다시 시작한다. 설정을 바꿀 때는 ConfigMap만 고치고 Pod를 다시 띄우면 되며 이미지는 손대지 않는다.

#4동작 과정

  1. 설정 주입ConfigMap이나 Secret을 환경 변수, 볼륨, 파일 형태로 컨테이너에 넣는다. 이미지 밖에서 설정과 민감 정보를 공급하므로 같은 이미지를 여러 환경에서 재사용할 수 있다.
  2. 동작 규칙 지정실행할 명령·인자, 보안 컨텍스트(실행 사용자·권한 같은 실행 조건), init 컨테이너(본 컨테이너 전에 한 번 도는 준비 작업), 여러 컨테이너가 공유하는 프로세스 네임스페이스나 볼륨을 정한다. 컨테이너가 어떤 권한과 어떤 자원으로 시작할지가 이 단계에서 확정된다.
  3. 상태 점검·수명 주기 연결liveness(살아 있는지), readiness(트래픽 받을 준비가 됐는지), startup(느린 시작이 끝났는지) 프로브를 붙이고, 컨테이너 수명 주기 이벤트에 실행할 핸들러와 노드 배치 규칙(affinity 등)을 연결한다. 문제가 생기면 kubelet이 자동으로 재시작하거나 트래픽에서 빼고, 조건에 맞는 노드에 Pod가 자리 잡는다.

#2핵심 질문

설정과 민감 정보를 이미지 밖에서 만들어 컨테이너 안으로 어떻게 안전하게 전달할 것인가?

#3동작 예시

#4동작 과정

  1. 데이터 정의·저장명령·인자, 환경 변수, ConfigMap·Secret 같은 오브젝트로 설정과 자격 증명을 클러스터에 저장한다. Secret은 kubectl이나 구성 파일, Kustomize로 만들 수 있고 값은 이미지 밖에 남는다.
  2. 컨테이너에 주입Pod 스펙에서 그 값들을 환경 변수나 볼륨으로 컨테이너에 연결한다. init 컨테이너가 먼저 값을 읽어 다른 변수를 만들 수도 있고, Pod 자신의 이름·IP 같은 정보도 환경 변수나 파일로 컨테이너에 노출된다.
  3. 런타임에 사용컨테이너가 시작할 때 주입된 변수와 파일을 읽어 동작한다. 설정이 바뀌면 오브젝트만 갱신하고 Pod를 다시 띄우면 새 값이 반영되어, 이미지를 다시 빌드하지 않고도 환경을 바꿀 수 있다.

#1문제 상황

Pod는 클러스터 안에서만 유효한 IP를 받고, 다시 만들어지면 IP가 바뀐다. 그래서 클라이언트가 Pod IP를 직접 가리키면 Pod가 재시작될 때마다 연결이 끊기고, 여러 Pod로 트래픽을 나눌 방법도 없다.

클러스터 밖에서 접속하려면 노드 포트나 방화벽 규칙을 따로 다뤄야 하고, 프론트엔드와 백엔드가 서로를 찾으려면 이름 해석(DNS)과 서비스 주소가 필요하다. 이런 연결 수단이 없으면 배포한 앱에 아무도 접근하지 못한다.

#2핵심 질문

#3동작 예시

Service를 만들면 여러 Pod에 걸쳐 고정된 가상 IP와 DNS 이름이 생기고, 그 이름으로 들어온 요청이 뒤의 Pod들로 분산된다. 클러스터 밖에서 잠깐 확인하려면 kubectl port-forward로 내 컴퓨터의 로컬 포트를 특정 Pod의 포트에 이어 붙여, 외부 노출 없이 접속할 수 있다. 외부 공개가 필요하면 LoadBalancer 타입 Service로 외부 주소를 받는다.

#4동작 과정

  1. 서비스로 묶기셀렉터로 Pod들을 골라 Service에 연결하면, Service는 고정된 가상 IP와 DNS 이름을 갖고 요청을 뒤의 살아 있는 Pod로 분산한다. Pod가 교체돼도 클라이언트가 보는 주소는 그대로다.
  2. 연결 통로 열기port-forward나 프록시로 로컬에서 포트를 이어 붙이고, 외부 공개가 필요하면 LoadBalancer나 NodePort로 클러스터 밖 접점을 만든다. 이때 클러스터 DNS가 서비스 이름을 주소로 풀어 주어 프론트엔드가 백엔드를 이름으로 부를 수 있다.
  3. 접근·확인클라이언트는 서비스 이름이나 외부 주소로 앱에 닿는다. 대시보드 같은 도구로 배포 상태를 보고, 실행 중인 컨테이너 이미지 목록을 조회하거나 같은 Pod 안 컨테이너끼리 공유 볼륨으로 데이터를 주고받으며 연결을 검증한다.

#2핵심 질문

문제가 앱·Pod·Service·클러스터 중 어디에서 생겼는지 어떻게 좁혀 나갈 것인가?

#3동작 예시

Pod가 뜨지 않으면 먼저 kubectl describe pod로 이벤트를 읽어 스케줄링이나 이미지 풀 실패 같은 단서를 찾고, kubectl logs와 --previous로 종료 직전 로그를 본다. 실행 중인 컨테이너 안을 직접 봐야 하면 kubectl exec로 셸을 열어 상태를 확인한다. Service가 안 되면 엔드포인트 목록과 셀렉터를 대조해 어느 단계에서 끊겼는지 좁힌다.

#4동작 과정

  1. 증상 수집describe로 이벤트와 상태를, logs로 출력을, exec로 컨테이너 내부를 확인한다. Pod 실패 이유를 파악하고 앱·Pod·Service 중 어디를 볼지 정한다.
  2. 원인 좁히기Service면 엔드포인트와 DNS·셀렉터를, StatefulSet이면 순서와 볼륨을, init 컨테이너면 초기화 단계 로그를 본다. 문제 계층을 하나씩 지워 가며 실제 원인에 가까워진다.
  3. 클러스터·노드 확인앱 문제가 아니면 노드 상태와 자원 지표 파이프라인, crictl 같은 도구로 클러스터와 노드를 점검한다. 모니터링·로그를 켜 두면 재현되지 않는 문제도 흔적을 남겨 원인을 확정할 수 있다.

#1문제 상황

kubectl이 없으면 클러스터에 명령을 보낼 수 없고, 있어도 클러스터의 API 서버 버전과 너무 벌어지면 명령이 어긋난다. 또 운영 클러스터 없이 연습하거나 개발하려면 로컬에 클러스터를 띄워야 하는데, 직접 구성하는 일은 번거롭고 환경마다 다르다.

운영체제마다 설치 방법이 달라, 무엇을 어떤 순서로 설치하고 어떻게 설정 파일을 두어야 하는지가 정해져 있지 않으면 첫걸음부터 막힌다.

#2핵심 질문

클러스터를 다루고 로컬에서 연습할 도구를 각 운영체제에 어떻게 설치하고 설정할 것인가?

#3동작 예시

Linux·macOS·Windows 각각에 맞는 방법으로 kubectl을 설치하고, kubeconfig 파일에 접속할 클러스터 정보를 두면 kubectl get pods 같은 명령이 그 클러스터로 간다. 클러스터가 없다면 kind나 minikube로 로컬에 클러스터를 띄워, 개인 컴퓨터에서 바로 명령을 연습할 수 있다.

#4동작 과정

  1. kubectl 설치사용하는 운영체제에 맞는 방식으로 kubectl을 설치한다. 이 도구 하나로 앱을 배포하고, 리소스를 조회·관리하며, 로그를 볼 수 있다.
  2. 접속 설정kubeconfig에 클러스터 주소와 인증 정보를 적어 kubectl이 어느 클러스터로 명령을 보낼지 정한다. 여러 클러스터를 오갈 때는 컨텍스트를 전환한다.
  3. 로컬 클러스터 준비kind나 minikube로 개인 컴퓨터에 클러스터를 띄운다. kind는 Docker나 Podman이 필요하고, minikube는 단일 노드 또는 여러 노드 로컬 클러스터를 만들어 연습과 개발에 쓴다.

확장 개요와 CRD

쿠버네티스의 기본 기능을 바꾸지 않고 API와 컨트롤러를 추가해 클러스터를 확장하는 방식과, 사용자가 직접 정의한 리소스 종류를 등록하는 CustomResourceDefinition(CRD)의 개념이다.

#1문제 상황

쿠버네티스에 기본으로 들어 있는 리소스 종류만으로는 조직마다 다른 요구를 다 담을 수 없다. 없는 기능이 필요할 때마다 쿠버네티스 소스 자체를 고치거나 별도 서비스를 따로 운영하면, 클러스터와 도구가 따로 놀고 관리 부담이 커진다.

기본 리소스만 있으면 사용자는 새 종류의 설정을 kubectl로 다룰 수 없고, 그 종류에 대한 자동 처리를 붙일 표준 방법도 없다. 기능을 더하려면 클러스터를 멈추고 코어를 건드려야 하는 상황이 반복된다.

#2핵심 질문

쿠버네티스의 기본 기능을 바꾸지 않고 API와 리소스 종류를 어떻게 더할 것인가?

#3동작 예시

CRD(CustomResourceDefinition, 사용자가 새 리소스 종류를 등록하는 정의)를 클러스터에 적용하면, 그때부터 kubectl get으로 그 종류의 오브젝트를 기본 Pod 다루듯 조회하고 만들 수 있다. CRD는 무엇을 저장할 수 있는지(스키마)와 버전만 정의하고, 실제 동작은 별도의 커스텀 컨트롤러가 그 오브젝트를 지켜보며 처리한다.

#4동작 과정

  1. API 확장 등록CRD를 적용해 새 리소스 종류를 API에 등록한다. 이 시점에 kubectl로 그 종류의 오브젝트를 만들고 읽을 수 있게 되며, 클러스터는 재시작 없이 확장된다.
  2. 오브젝트 생성·저장사용자가 그 종류의 오브젝트를 만들면 API 서버가 스키마와 버전 규칙에 따라 검증해 저장한다. 기본 리소스와 똑같은 방식으로 다뤄진다.
  3. 컨트롤러가 처리별도의 커스텀 컨트롤러가 그 오브젝트를 감시하다가 원하는 상태로 만들기 위해 실제 작업을 수행한다. 이렇게 리소스와 컨트롤러를 묶은 것이 Operator 패턴이며, 장치를 붙이는 Device Plugin처럼 다른 영역도 같은 방식으로 확장된다.

#5한 줄 요약

기본 기능을 건드리지 않고 API에 새 리소스 종류를 등록하고 컨트롤러로 처리해, 클러스터를 필요에 맞게 확장하는 것

확장 태스크

애그리게이션 레이어, 커스텀 리소스, 확장 API 서버, 멀티 스케줄러 등 클러스터를 실제로 확장하는 절차를 단계별로 안내하는 태스크 모음이다.

#1문제 상황

기본 쿠버네티스가 제공하는 리소스 종류와 기본 스케줄러, 기본 접근 경로만으로는 조직마다 다른 요구를 모두 담을 수 없습니다. 사내 전용 리소스를 기존 API에 추가하려 해도 코어 API 서버 코드를 직접 고치지 않으면 새 종류를 얹을 수 없고, 특수한 배치 기준을 반영하려 해도 기본 스케줄러의 판단 규칙을 그대로 두면 방법이 없습니다. 이런 요구를 매번 코어에 밀어 넣으면 업그레이드할 때마다 충돌이 생기고, 외부에서 클러스터 API에 접근하는 경로도 하나로 고정되어 환경별 요구를 반영하기 어렵습니다.

#2핵심 질문

코어를 뜯어고치지 않고도 API·스케줄러·접근 경로를 각각 확장하려면 어떤 절차를 따라야 하는가?

#3동작 예시

확장 API 서버를 하나 띄우고 애그리게이션 레이어(요청을 알맞은 서버로 넘겨 주는 계층)에 등록하면, 클라이언트가 /apis/<그룹>/... 경로를 호출했을 때 코어 API 서버가 그 요청을 등록된 확장 API 서버로 전달합니다. 그러면 코어를 다시 빌드하지 않고도 새 리소스 그룹이 kubectl과 다른 클라이언트에서 정상 리소스처럼 보입니다.

#4동작 과정

  1. 확장 지점 고르기애그리게이션 레이어, 커스텀 리소스, 확장 API 서버, 멀티 스케줄러, 프록시, kubectl 플러그인 중 어떤 방식으로 요구를 풀지 정합니다. 무엇을 바꾸려는지에 따라 등록할 대상이 달라집니다.
  2. 확장 서버·구성 등록하기확장 API 서버를 애그리게이션 레이어에 등록하거나, 추가 스케줄러를 배포하고 프록시·Konnectivity로 API 접근 경로를 구성합니다. 이 단계에서 확장이 클러스터의 실제 요청 흐름에 연결됩니다.
  3. 동작 확인하기등록한 리소스·스케줄러·경로가 정상 응답하는지 클라이언트로 확인합니다. 그 결과 코어 수정 없이 원하는 기능이 클러스터에 더해집니다.

클러스터를 만들고 앱을 배포·조회·확장·업데이트·노출하는 흐름을 처음부터 끝까지 한 번에 따라 하려면 어떻게 하는가?

#4동작 과정

  1. 클러스터 만들기미니큐브로 로컬에 클러스터를 만듭니다. 이때부터 kubectl이 통신할 대상이 생겨 이후 명령이 실제로 동작합니다.

  3. 노출·확장·업데이트하기서비스로 앱을 외부에 노출하고, 복제 수를 늘려 확장한 뒤, 새 버전으로 롤링 업데이트합니다. 그 결과 앱의 생애주기 전반을 한 흐름으로 익히게 됩니다.

#4동작 과정

  2. 이전 경로 확인Deprecated API Migration Guide가 폐기되는 API마다 대체 API와 이전 방법을 안내한다. 그래서 매니페스트를 미리 고쳐 업그레이드 중단을 피할 수 있다.
  3. 보안 정보 확인Kubernetes Issues and Security 페이지가 Kubernetes Issue Tracker, Kubernetes Security and Disclosure Information, Official CVE Feed로 연결한다. 그래서 이슈 추적, 취약점 공개 절차, CVE(공개된 보안 취약점 식별자) 목록을 한 지점에서 확인할 수 있다.

문서 기여

오타 수정부터 새 문서 작성, 풀 리퀘스트와 리뷰까지 쿠버네티스 공식 문서에 기여하는 방법을 안내한다.

#1문제 상황

쿠버네티스 문서는 릴리스마다 API와 기능이 바뀌는데, 문서가 그 변화를 따라가지 못하면 사용자는 틀린 설명을 읽게 된다. 기존에는 문서 수정 권한과 절차가 분명하지 않아 오타 하나를 고치려 해도 어디에 어떻게 요청해야 하는지 알기 어려웠다.

문서를 관리하는 SIG Docs(쿠버네티스 문서를 담당하는 특별 관심 그룹)가 있지만, 기여자가 정해진 절차와 형식을 모르면 작성한 글이 반영되지 않고 리뷰 단계에서 막힌다. 그래서 참여 경로와 역할, 검토 규칙을 명확히 안내할 필요가 생겼다.

#2핵심 질문

신규 참여자도 정해진 절차와 형식에 맞춰 쿠버네티스 공식 문서에 기여하려면 무엇을 따라야 할까?

#3동작 예시

문서 한 페이지에서 오타를 발견한 사람이 풀 리퀘스트(변경 내용을 검토받기 위해 올리는 요청)를 열면, 리뷰어가 변경을 확인하고 승인하면 그 내용이 사이트에 반영된다. 이때 어느 브랜치를 기준으로 어떻게 수정하고 리뷰를 어떻게 받는지가 문서 기여 안내에 단계별로 정리되어 있다.

#4동작 과정

  1. 역할과 절차 파악참여자가 SIG Docs의 역할과 책임, Reviewing changes, Reviewing pull requests, PR wranglers(풀 리퀘스트를 정리·분류하는 담당), Issue Wranglers 같은 안내를 읽고 자신이 맡을 수 있는 일을 정한다. 그래서 처음 참여해도 어떤 순서로 움직여야 하는지 알게 된다.
  2. 변경 작성과 로컬 확인새 문서나 수정 내용을 Writing a new topic, Documentation Style Guide, Page content types 같은 규칙에 맞춰 작성하고 Previewing locally로 결과를 확인한 뒤 Opening a pull request로 요청을 올린다. 그래서 형식 규칙을 지킨 변경이 리뷰에 들어간다.
  3. 리뷰와 릴리스 반영풀 리퀘스트가 리뷰와 승인을 거쳐 병합되고, Documenting a feature for a release, Generating Reference Documentation for a Release 같은 절차를 통해 릴리스 문서에 반영된다. 그래서 기여한 내용이 공식 문서로 배포된다.
