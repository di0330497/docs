쿠버네티스가 푸는 문제와 클러스터 전체 구조

컨테이너를 사람이 일일이 돌보지 않아도 되게, 여러 대의 머신을 하나의 클러스터로 묶어 배포·확장·복구를 자동으로 관리하는 시스템이다.

1상대의 출발점 확인

기존에는 개발팀이 컨테이너를 직접 관리해야 했다. 어떤 서버에 어떤 컨테이너를 띄울지 정해야 하고, 서버가 죽으면 다른 서버에 옮겨야 하고, 트래픽이 늘어나면 수동으로 컨테이너를 더 띄워야 한다. 모든 일을 사람이 직접 조정해야 했다.

2질문 제기

컨테이너를 인프라 전체에 자동으로 배치하고, 장애 시 자동으로 복구하고, 부하에 따라 자동으로 확장하려면?

3구조적 핵심 예시

쿠버네티스는 여러 대의 머신(노드)을 하나의 클러스터로 묶는다. 사용자가 "앱 3개를 실행해"라고 선언하면, 쿠버네티스의 스케줄러는 자유로운 리소스가 있는 노드에 그 앱들을 배치한다. 한 노드가 죽으면, 그 위의 앱들을 다른 노드로 옮긴다. 이 모든 것이 자동으로 일어난다.

4단계별 동작 과정

  1. 클러스터 구성여러 머신(노드)과 중앙 제어실(컨트롤 플레인)로 이뤄진다. 컨트롤 플레인은 원하는 상태를 저장하고, 각 노드의 상태를 감시한다.
  2. 상태 선언사용자가 YAML 파일로 "이 앱 3개를 실행해"라고 쓴다. 이것이 원하는 상태(desired state)다.
  3. 자동 조정컨트롤 플레인이 계속 확인한다. 만약 앱이 2개만 실행 중이면 1개를 더 띄운다. 노드가 다운되면 그 위의 앱들을 다른 노드로 옮긴다.

5본질 요약

여러 머신을 하나의 자동 관리 시스템으로 만들어, 사람이 매번 손으로 조정하지 않아도 앱이 항상 원하는 상태로 유지되도록 하는 것

기존에는 관리자가 각 서버에 접속해 직접 명령을 했다. "이 서버에 이 앱을 띄워", "저 서버의 앱을 종료해" 같은 식으로 하나하나 지시했다. 서버가 많아질수록 관리할 것이 늘어났고, 실수도 많아졌다.

2질문 제기

수백 개의 머신에서 수천 개의 앱이 정확하게 원하는 대로 실행되고 있는지, 자동으로 확인하고 조정하려면?

3구조적 핵심 예시

쿠버네티스는 두 부분으로 나뉜다. 컨트롤 플레인은 뇌 역할이다. API 서버(메시지 수신처)와 스케줄러(배치 계획), 컨트롤러 매니저(문제 감지 및 수정)가 여기에 있다. 각 노드에는 kubelet(지시 받아서 실행하는 작업자)과 kube-proxy(통신 담당)가 있다.

4단계별 동작 과정

  1. 지시 전달사용자가 API 서버에 요청을 보낸다(예: "app 3개를 실행해"). API 서버가 이를 저장한다.
  2. 스케줄링 및 배치스케줄러가 각 노드의 리소스를 확인하고, 어느 노드에 앱을 띄울지 정한다. kubelet이 그 지시를 받아 컨테이너를 시작한다.
  3. 지속적 확인 및 조정컨트롤러 매니저가 현재 상태를 계속 확인한다(이를 컨트롤 루프라고 부름). 앱이 다운되면 새것을 띄우고, 노드가 죽으면 다른 곳으로 옮긴다.

3구조적 핵심 예시

쿠버네티스에서 모든 것은 API 오브젝트다. 각 오브젝트는 두 부분을 가진다: spec은 "내가 원하는 것"이고, status는 "지금 실제로 돌아가는 상태"다. 예를 들어 Pod 오브젝트라면, spec에는 "Ubuntu 이미지로 Nginx를 실행해"라고 적고, status에는 "지금 Running 상태, IP는 10.0.0.5"라고 기록된다.

4단계별 동작 과정

  1. 사용자가 spec 정의kubectl 또는 API로 YAML 파일을 보낸다. 여기에 "이 설정으로 앱을 실행해"라고 적혀 있다.
  2. API 서버가 저장API 서버는 이 선언을 저장한다. 이때부터 쿠버네티스가 이 상태를 "원하는 것"으로 본다.
  3. 실제 실행 및 상태 업데이트kubelet과 다양한 컨트롤러가 status를 업데이트한다(예: "실행 중", "재시작됨", "에러"). 컨트롤 루프가 계속 spec과 status를 비교해서 맞춘다.

Pod는 하나 이상의 컨테이너를 묶는 쿠버네티스의 배포 단위다. 예를 들어 Nginx 컨테이너와 로그 수집 사이드카 컨테이너를 한 Pod에 넣으면, 둘 다 같은 Pod 내에서 같은 IP 주소를 가지고, 로컬호스트(127.0.0.1)로 통신하고, 같은 스토리지를 마운트할 수 있다.

4단계별 동작 과정

  2. Pod 생성kubectl apply 명령으로 API 서버에 이 매니페스트를 보낸다. 스케줄러가 어느 노드에 이 Pod를 배치할지 정한다.
  3. 컨테이너 실행 및 상태 관리kubelet이 노드에서 그 Pod의 컨테이너들을 모두 시작한다. 한 컨테이너가 다운되면 kubelet이 자동으로 재시작한다(restartPolicy에 따라).

컨테이너 이미지·레지스트리·풀 정책

컨테이너 이미지는 앱과 실행 환경을 담은 패키지이며, 레지스트리에서 어떤 태그를 언제 내려받을지는 imagePullPolicy 로 정한다.

1상대의 출발점 확인

기존에는 개발자가 Docker 이미지를 만들면, 각 서버에 그 이미지를 수동으로 받아야 했다. 어떤 이미지를 받을지, 언제 새 버전을 받을지는 관리자가 손으로 정했다. 서버가 많을수록 이 과정이 번거로웠고, 버전 관리도 복잡했다.

2질문 제기

클러스터의 수백 개 노드에서 일관되게 올바른 버전의 컨테이너 이미지를 받고, 필요할 때 업데이트할 수 있을까?

3구조적 핵심 예시

Pod 매니페스트에 이미지를 지정한다(예: nginx:1.21). 그러면 kubelet이 그 이미지를 레지스트리(이미지 창고, 보통 Docker Hub나 개인 레지스트리)에서 받아온다. 그런데 매번 같은 이미지를 또 받을지, 아니면 이미 있는 것을 쓸지는 imagePullPolicy(이미지 가져오기 정책)로 정한다.

4단계별 동작 과정

  1. 이미지 지정Pod 정의에 "image: myapp:v1.2.3"이라고 적는다. 이 문자열이 레지스트리 주소, 이미지 이름, 태그(버전)를 담는다.
  2. 레지스트리에서 가져오기kubelet이 지정된 imagePullPolicy를 확인한다. Always(항상 가져옴), Never(없으면 에러), IfNotPresent(없을 때만 가져옴) 중 하나다. IfNotPresent면 로컬에 이미 있는지 확인하고, 없으면 받는다.
  3. 컨테이너 시작이미지가 준비되면 kubelet이 그것으로 컨테이너를 시작한다. 같은 이미지를 쓰는 다른 Pod들은 같은 로컬 복사본을 재사용한다(디스크 절약).

Pod 생명주기·재시작 정책·종료와 라이프사이클 훅

Pod는 Pending에서 Running·Succeeded·Failed로 이어지는 상태를 거치며, restartPolicy와 종료 유예 시간·postStart/preStop 훅이 그 전환을 제어한다.

1상대의 출발점 확인

컨테이너를 실행할 때 시작과 종료만 관리하던 환경에서는 예상치 못한 실패 시 누구도 재시작하지 않고, 종료 직전에 정리 작업(예: 연결 종료, 캐시 플러시)을 할 방법이 없습니다. Pod를 이해하려면 먼저 Pod가 거치는 구체적인 상태들과 각 상태 전환에 개입하는 정책들을 알아야 합니다.

2질문 제기

Pod가 여러 상태를 거치면서 충돌, 종료, 재시작할 때 어느 상태에서 어떤 액션을 취할지 어떻게 정의할 것인가?

3구조적 핵심 예시

Pod는 Pending(대기 중) → Running(실행 중) → Succeeded(성공 종료) 또는 Failed(실패 종료) 순서로 상태가 바뀌며, 각 상태 전환마다 restartPolicy 정책과 라이프사이클 훅(postStart, preStop)이 개입해 행동을 제어합니다.

4단계별 동작 과정

  1. 상태 전이와 정책 판단kubelet이 Pod 상태를 감시하다가 컨테이너가 충돌하면, restartPolicy(Always/OnFailure/Never)에 따라 즉시 재시작할지, 특정 조건에만 재시작할지, 아니면 방치할지를 판단합니다.
  2. 라이프사이클 훅 실행컨테이너 시작 직후 postStart 훅을 실행하고(초기화 작업), 종료 직전 preStop 훅을 실행해서(정리 작업) 안전한 상태 전환을 보장합니다.
  3. 종료 유예 시간 적용Pod 삭제 신호가 오면 terminationGracePeriodSeconds 동안 기다렸다가 컨테이너를 강제 종료하므로, 진행 중인 작업을 마칠 수 있습니다.

5본질 요약

프로브: liveness·readiness·startup

kubelet이 컨테이너를 주기적으로 진단해 재시작할지(liveness), 트래픽을 보낼지(readiness), 기동을 기다릴지(startup)를 판단하는 검사다.

1상대의 출발점 확인

컨테이너 프로세스가 떠 있다고 해서 정상 작동 중인 것은 아닙니다. 교착 상태에 빠진 앱, 무한 루프에 갇힌 서버, 메모리 누수로 응답 불가인 상태도 프로세스는 실행 중입니다. 따라서 실제로 정상인지 주기적으로 진단할 방법이 필요합니다.

2질문 제기

실행 중인 컨테이너가 정말 정상인지, 트래픽을 받을 준비가 되었는지, 기동이 완료되었는지 어떻게 판단할 것인가?

3구조적 핵심 예시

kubelet이 HTTP 요청, 셸 명령 실행, TCP 연결 시도 같은 진단 방법(프로브)으로 컨테이너를 주기적으로 확인해서, 실패 횟수에 따라 재시작하거나 트래픽 제외 여부를 결정합니다.

4단계별 동작 과정

  1. Liveness 프로브kubelet이 주기적으로 컨테이너에 신호를 보내고 실패하면 재시작이 필요한 상태로 판단합니다. 예를 들어 웹 서버의 /healthz 엔드포인트가 2xx 응답을 주지 않으면 실패 카운트가 증가합니다.
  2. Readiness 프로브컨테이너가 떠 있어도 데이터베이스 연결 대기 중이면 트래픽을 받으면 안 됩니다. readiness 프로브가 실패하면 서비스의 엔드포인트 목록에서 제외됩니다.
  3. Startup 프로브앱 시작이 오래 걸리는 경우 liveness와 readiness 판정이 너무 일찍 나올 수 있으므로, startup 프로브가 성공할 때까지 다른 프로브들을 유예합니다.

Init 컨테이너와 사이드카 컨테이너

Init 컨테이너는 앱 컨테이너보다 먼저 순차 실행되어 준비 작업을 끝내고, 사이드카는 앱과 나란히 계속 떠서 로깅·프록시 같은 보조 기능을 맡는다.

1상대의 출발점 확인

Pod는 하나의 주요 애플리케이션 컨테이너만 떠 있었으므로, 시작 전 준비(예: 환경 설정, 데이터 다운로드)나 실행 중 보조 기능(예: 로그 수집, 프록시)을 할 수 없었습니다. 이들을 모두 주 애플리케이션 코드에 넣어야 했습니다.

2질문 제기

Pod 시작 전에 순차적으로 준비 작업을 하고, 실행 중에도 주 애플리케이션과 함께 보조 기능을 계속 실행하려면 어떻게 할 것인가?

3구조적 핵심 예시

Init 컨테이너는 앱 컨테이너 시작 전에 정해진 순서대로 모두 실행되고 종료되는 반면, 사이드카 컨테이너는 앱 컨테이너와 나란히 계속 떠서 로깅, 프록시, 모니터링 같은 보조 역할을 합니다.

4단계별 동작 과정

  1. Init 컨테이너 순차 실행Pod 시작 시 spec.initContainers에 정의된 컨테이너를 앞에서부터 하나씩 실행합니다. 각 Init 컨테이너는 성공(exit code 0)해야만 다음 컨테이너로 진행하고, 실패하면 정책에 따라 재시도합니다.
  2. 앱 컨테이너 시작모든 Init 컨테이너가 종료한 후 spec.containers의 주 애플리케이션 컨테이너가 시작됩니다.
  3. 사이드카 컨테이너 계속 실행앱 컨테이너와 같은 네트워크, 볼륨을 공유하는 추가 컨테이너가 앱과 함께 계속 실행되어 로깅, 모니터링, 프록시 기능을 제공합니다.

1상대의 출발점 확인

일반적으로 Pod는 쿠버네티스 API 서버를 통해 배포되고, 각 컨테이너는 독립된 프로세스로 격리됩니다. 그러나 kubelet이 직접 관리해야 하는 시스템 컴포넌트(API 서버, etcd 자체)를 부트스트래핑할 때 API 서버가 없고, 디버깅 시 이미 떠 있는 Pod에 임시로 컨테이너를 넣어야 합니다.

3구조적 핵심 예시

정적 Pod는 파일 시스템의 manifest 파일을 읽어 kubelet이 직접 관리하고, 임시 컨테이너는 이미 떠 있는 Pod에 런타임에 추가되어 디버깅을 돕고, 사용자 네임스페이스는 Pod 내 프로세스의 UID/GID를 호스트와 다르게 매핑해 권한 격리를 강화합니다.

4단계별 동작 과정

  1. 정적 Pod 관리kubelet이 /etc/kubernetes/manifests/ 같은 지정 경로의 YAML 파일을 주기적으로 읽고 Pod를 생성·유지합니다. API 서버가 없어도 작동하므로 쿠버네티스 자체의 핵심 컴포넌트를 부트스트래핑할 때 사용됩니다.
  2. 임시 컨테이너 추가이미 실행 중인 Pod에 debug 필드로 임시 컨테이너를 (API 서버를 통해) 추가할 수 있고, 이 컨테이너는 같은 네트워크, 볼륨, IPC 네임스페이스를 공유하므로 문제 진단에 도움이 됩니다.
  3. 사용자 네임스페이스 격리spec.hostUsers: false를 설정하면 Pod 내 컨테이너의 UID/GID가 호스트 상의 다른 범위로 매핑되어 컨테이너 탈출 시 호스트 권한 상승 위험을 줄입니다.

ReplicaSet과 Deployment - 롤아웃·롤백·스케일

ReplicaSet은 Pod 복제본 수를 유지하고, Deployment는 그 위에서 새 버전을 점진적으로 교체(롤아웃)하거나 되돌리고(롤백) 개수를 조절한다.

1상대의 출발점 확인

예전에는 Pod을 직접 만들었는데, 서버가 다운되면 사라져 버렸습니다. Pod의 복제본을 여러 개 직접 만들 수도 있지만, 하나가 죽으면 다시 만들어야 하고 일일이 관리해야 했습니다. 또한 새 버전의 애플리케이션으로 업그레이드할 때 기존 Pod을 모두 지우고 새로 만들어야 했기 때문에 서비스가 잠깐 중단되거나 문제 발생 시 되돌리기 어려웠습니다.

2질문 제기

Pod 복제본의 개수를 자동으로 유지하면서, 새 버전으로 업그레이드할 때 몇 개씩 단계적으로 바꿔가며 오래된 버전도 잠깐 유지했다가 문제 생기면 즉시 되돌릴 수 있을까요?

3구조적 핵심 예시

Deployment를 만들 때 "항상 3개의 Pod이 실행 중이어야 한다"고 선언합니다. 쿠버네티스는 이를 ReplicaSet(Pod 개수 관리 컨트롤러)으로 구현해 Pod이 다운되면 자동으로 새 Pod을 만듭니다. 새 버전을 배포하면 Deployment는 기존 ReplicaSet을 유지하면서 새 ReplicaSet을 천천히 늘렸다가 기존 것을 줄입니다. 문제가 생기면 새 ReplicaSet을 0으로 줄이고 기존 ReplicaSet을 다시 늘려 되돌립니다.

4단계별 동작 과정

  1. ReplicaSet으로 Pod 복제본 유지Deployment 안의 ReplicaSet이 지정된 개수만큼 Pod을 계속 실행합니다. Pod이 하나 죽으면 ReplicaSet이 새 Pod을 자동으로 만듭니다.
  2. 새 버전 배포 시 단계적 교체(롤아웃)Deployment 정의를 새 이미지로 바꾸면, 기존 ReplicaSet은 유지하고 새 ReplicaSet을 만들어 Pod을 천천히 교체합니다. 예를 들어 3개 중 1개씩 바뀝니다.
  3. 문제 발생 시 즉시 되돌리기(롤백)새 버전이 문제를 일으키면 kubectl rollout undo로 기존 ReplicaSet을 다시 활성화하고 새 버전을 0으로 줄여 순식간에 원래 상태로 돌아갑니다.

5본질 요약

ReplicaSet이 Pod 개수를 자동 유지하고, Deployment가 그 위에서 새 버전과 기존 버전을 동시에 관리하며 단계적 교체와 즉시 롤백을 가능하게 하는 구조

StatefulSet과 상태 있는 애플리케이션

StatefulSet은 각 Pod에 고정된 이름·순서·전용 스토리지를 부여해 데이터베이스처럼 상태를 가진 앱을 운영하게 해주는 컨트롤러다.

1상대의 출발점 확인

Deployment로 관리되는 Pod은 모두 동등합니다. 언제든 죽고 다시 태어날 수 있으며, 새로운 Pod이 이전 Pod과 동일하게 작동합니다. 하지만 데이터베이스나 캐시 같은 상태를 가진 애플리케이션은 다릅니다. 각 Pod이 고유한 데이터를 들고 있고, 특정 순서에 따라 시작되어야 하며, 재시작되어도 같은 Pod이어야 하고 자신의 스토리지를 다시 붙여야 합니다. Deployment로는 이런 요구 조건을 맞출 수 없습니다.

2질문 제기

각 Pod에 고정된 이름과 전용 스토리지를 부여해서 상태를 가진 애플리케이션을 안전하게 관리할 수 있을까요?

3구조적 핵심 예시

StatefulSet으로 MySQL 복제본 3개를 만든다면, Pod은 mysql-0, mysql-1, mysql-2처럼 고정된 이름을 갖습니다. 각각 mysql-0-pvc, mysql-1-pvc, mysql-2-pvc라는 전용 스토리지가 붙어 있습니다. mysql-0이 죽으면 mysql-0이라는 이름의 새 Pod이 나타나서 기존 스토리지를 다시 붙이므로, 데이터가 손실되지 않습니다.

4단계별 동작 과정

  1. Pod에 고정된 이름과 순서 부여StatefulSet이 만드는 각 Pod은 0부터 시작하는 고정된 번호를 이름에 붙입니다. 시작도 순서대로 진행됩니다(0번이 Ready 상태가 되어야 1번이 시작).
  2. 각 Pod 전용의 스토리지 자동 생성각 Pod마다 전용 PersistentVolumeClaim(저장소 예약)이 자동 생성되고, Pod이 재시작되어도 같은 스토리지가 다시 붙습니다.
  3. 상태 유지 및 복구Pod이 다운되면 같은 이름의 새 Pod이 기존 스토리지를 가져가므로 데이터와 상태가 유지됩니다.

5본질 요약

각 Pod에 고정된 이름과 번호, 그리고 전용 스토리지를 부여해 데이터베이스처럼 상태를 지니는 애플리케이션을 안정적으로 관리하는 컨트롤러

DaemonSet

DaemonSet은 클러스터의 모든(또는 조건에 맞는) 노드마다 Pod을 하나씩 띄워 로그 수집기·모니터링 에이전트 같은 노드 단위 작업을 담당한다.

1상대의 출발점 확인

Deployment를 쓰면 클러스터의 어느 노드에 Pod이 배치될지 제어하기 어렵습니다. 클러스터의 모든 노드에서 동시에 실행되어야 하는 작업들(로그 수집, 모니터링, 보안 에이전트)이 있는데, Deployment만으로는 각 노드에 하나씩 띄우도록 보장할 수 없습니다. 노드를 추가하면 이런 Pod들도 자동으로 그 노드에 띄워져야 합니다.

2질문 제기

클러스터의 모든(또는 조건에 맞는) 노드마다 Pod을 정확히 하나씩 자동으로 띄우고 유지할 수 있을까요?

3구조적 핵심 예시

로그 수집기를 DaemonSet으로 만들면, 현재 10개의 노드가 있을 때 Pod이 정확히 10개 만들어지고 각 노드마다 1개씩 실행됩니다. 새 노드 2개가 추가되면 자동으로 Pod 2개가 생성되고, 노드 1개가 제거되면 거기 붙어 있던 Pod도 자동으로 정리됩니다.

4단계별 동작 과정

  1. 노드 목록 감시DaemonSet은 클러스터의 모든 노드를 추적합니다. 선택자(selector)나 테인트 용인(toleration) 규칙을 써서 대상 노드 범위를 필터링할 수도 있습니다.
  2. 각 노드에 Pod 배치대상 노드마다 정확히 1개의 Pod을 만들어서 실행합니다. 노드가 추가되면 즉시 그 노드에 Pod을 생성합니다.
  3. Pod 자동 정리노드가 제거되거나 조건을 더 이상 만족하지 않으면, 거기 붙어 있던 Pod이 자동으로 삭제됩니다.

5본질 요약

Job과 CronJob - 병렬 배치 처리

Job은 끝나면 완료되는 일회성 작업을 병렬 개수까지 지정해 실행하고, CronJob은 그 Job을 정해진 시각마다 반복 생성한다.

1상대의 출발점 확인

Deployment는 계속 실행되어야 하는 애플리케이션(웹 서버)을 위한 것입니다. 하지만 데이터 처리, 보고서 생성, 정기 백업 같은 작업은 시작해서 완료되면 끝나야 합니다. 이런 일회성 작업을 Deployment로 관리하면, Pod이 완료되어도 계속 재시작되어 불필요한 자원을 낭비합니다. 또한 병렬로 여러 작업을 동시에 실행하거나 실패한 것을 재시도하는 로직을 별도로 만들어야 합니다.

2질문 제기

완료되면 끝나는 작업을 정해진 개수만큼 병렬로 실행하고, 실패한 작업은 자동 재시도하며, 언제 완료되었는지 추적할 수 있을까요?

3구조적 핵심 예시

Job으로 1000개의 파일을 처리하는 작업을 정의할 때, 병렬도(parallelism)를 10으로 설정하면 Pod 10개가 동시에 실행되어 파일을 나눠 처리합니다. 한 Pod이 실패하면 Job이 자동으로 재시도하고, 모든 작업이 성공하면 Job은 완료 상태로 표시되고 Pod은 종료됩니다.

4단계별 동작 과정

  1. Job 생성 및 병렬 Pod 실행Job 정의에서 병렬도와 완료할 작업 개수를 지정하면, 해당 개수만큼 Pod이 동시에 실행됩니다.
  2. 작업 진행 추적 및 실패 재시도Job은 완료된 Pod의 개수를 세고, 실패한 Pod이 있으면 재시도 정책에 따라 새 Pod을 만듭니다. 재시도 횟수 제한도 설정할 수 있습니다.
  3. 완료 및 상태 기록지정된 개수만큼 모든 Pod이 성공하면 Job은 완료됩니다. 로그와 상태는 보존되어 나중에 조회할 수 있습니다.

5본질 요약

일회성 작업을 병렬로 실행하고 완료를 추적하며 실패를 자동 재시도하는 Job이고, 이를 정해진 시각에 반복 생성하는 CronJob

소유자·파이널라이저·가비지 컬렉션

오브젝트는 ownerReference로 부모를 가리키며, 부모가 지워지면 자식도 자동 정리되고 파이널라이저가 붙어 있으면 뒷정리가 끝날 때까지 삭제가 보류된다.

1상대의 출발점 확인

쿠버네티스에서 Deployment를 만들면 그 안에 ReplicaSet이 생기고 그 안에 Pod이 생깁니다. Deployment를 지우려 할 때 어떤 오브젝트부터 지워야 할까요? Pod을 먼저 지우면 ReplicaSet이 새 Pod을 만듭니다. ReplicaSet을 지우지 않고 Deployment만 지워버리면 Deployment는 없는데 Pod은 떠돌아다닙니다. 이런 부모-자식 관계를 명확히 하지 않으면 고아 오브젝트가 남아 자원을 낭비합니다.

2질문 제기

부모 오브젝트가 지워질 때 자식 오브젝트도 자동으로 정리하고, 필요하면 정리 전에 뒷정리 작업을 먼저 마칠 수 있을까요?

3구조적 핵심 예시

Deployment를 지우면, Deployment 오브젝트는 ownerReference라는 필드로 자신이 만든 ReplicaSet을 가리킵니다. 쿠버네티스는 Deployment가 삭제되는 것을 감지하고, ownerReference를 통해 ReplicaSet을 찾아 함께 삭제합니다. ReplicaSet도 같은 방식으로 자신이 만든 Pod들을 추적하고 있어서, Pod도 자동으로 정리됩니다.

4단계별 동작 과정

  1. 부모-자식 관계 기록오브젝트를 생성할 때 ownerReference에 부모의 정보를 기록합니다. 이를 통해 누가 이 오브젝트를 만들었고 지울 권한이 있는지를 추적합니다.
  2. 파이널라이저로 뒷정리 준비오브젝트에 finalizer를 붙이면, 삭제 요청이 들어와도 즉시 지워지지 않고 파이널라이저 조건이 완료될 때까지 보류됩니다. 예를 들어 데이터베이스 레코드를 삭제하거나 외부 자원을 정리합니다.
  3. 가비지 컬렉션 실행부모가 삭제되고 파이널라이저 조건이 완료되면, 자식 오브젝트들이 자동으로 찾아져서 순서대로 정리됩니다.

5본질 요약

클러스터 네트워킹 모델과 네트워크 플러그인

모든 파드가 NAT 없이 서로의 IP로 직접 통신할 수 있어야 한다는 쿠버네티스 네트워킹 규칙과, 이를 실제로 구현하는 CNI 플러그인.

1상대의 출발점 확인

기존 데이터센터 네트워크에서는 가상 머신(VM)들이 NAT(주소 변환)를 통해 통신합니다. 각 VM의 내부 IP는 외부에서 모르고, 라우터가 NAT 테이블을 관리하면서 통신을 중개합니다. 쿠버네티스의 Pod은 VM처럼 각자의 IP를 가지고 있는데, Pod은 매우 빠르게 생성되고 삭제됩니다. 이런 환경에서 NAT 기반 통신은 복잡하고 비효율적입니다.

2질문 제기

클러스터 내의 모든 Pod이 NAT 없이 서로의 IP 주소로 직접 통신할 수 있을까요?

3구조적 핵심 예시

Flannel이나 Calico 같은 CNI 플러그인은 클러스터의 모든 노드에 가상 네트워크를 만들어, 각 노드가 관리하는 Pod들을 이 가상 네트워크에 연결합니다. Pod A(노드 1)에서 Pod B(노드 2)로 패킷이 가면, 각 노드의 네트워크 인터페이스가 패킷을 캡슐화하거나 라우팅하여 목적지 노드에 전달하고, 거기서 다시 풀어 Pod B에 도착시킵니다. NAT는 거치지 않고 IP는 전체 클러스터에서 유일합니다.

4단계별 동작 과정

  1. 클러스터 네트워킹 규칙 정의쿠버네티스는 모든 Pod이 모든 다른 Pod과 NAT 없이 직접 통신해야 한다는 규칙을 정합니다. 이를 위해 Pod마다 클러스터 전체에서 유일한 IP를 부여해야 합니다.
  2. CNI 플러그인이 네트워크 구현CNI(Container Network Interface, 컨테이너 네트워크 규약) 플러그인이 실제 네트워크를 구성합니다. 각 노드에 가상 네트워크 드라이버를 깔아 Pod 트래픽을 캡슐화하거나 라우팅하고, 클러스터 전체가 하나의 논리적 네트워크가 되도록 만듭니다.
  3. 서비스 DNS와 함께 작동Service 오브젝트가 Pod들의 변하는 IP를 고정된 이름으로 모아주고, DNS가 이를 해석해 Pod 간 통신을 이름으로 할 수 있게 합니다.

Service와 서비스 타입

수시로 바뀌는 파드 집합에 고정된 이름과 주소를 부여하는 오브젝트로, ClusterIP·NodePort·LoadBalancer·ExternalName 타입이 있다.

1상대의 출발점 확인

파드의 IP 주소는 파드가 재시작되거나 스케일링될 때마다 바뀐다. 파드를 직접 IP로 접근하면, 파드가 다시 실행될 때마다 새로운 IP를 찾아야 하고 연결이 끊어진다. 또한 여러 파드에 요청을 분산해야 할 때 클라이언트가 모든 파드 IP를 관리하는 것은 불가능하다.

2질문 제기

자주 변하는 파드 집합을 고정된 이름과 주소로 어떻게 접근할까?

3구조적 핵심 예시

Service는 라벨 선택자(label selector)로 특정 파드들을 찾아 하나의 고정된 ClusterIP 주소를 할당한다. 클라이언트는 파드 IP가 아니라 이 Service의 고정 IP로 접근하고, Service가 그 요청을 뒤의 파드들로 분배한다.

4단계별 동작 과정

  1. Service 생성 및 파드 연결Service가 라벨 선택자로 "app=web" 같은 라벨을 가진 모든 파드를 찾아 등록한다.
  2. 고정 주소 할당Service에 이름과 클러스터 내부 IP(ClusterIP)가 자동으로 부여된다.
  3. 트래픽 분배클라이언트가 Service IP로 요청하면 Service가 등록된 파드 중 하나를 선택해 전달한다.

EndpointSlice·kube-proxy와 가상 IP 구현

서비스 뒤의 실제 파드 주소 목록(EndpointSlice)을 kube-proxy가 노드의 규칙으로 옮겨 가상 IP를 실제 트래픽 전달로 바꾸는 구조.

1상대의 출발점 확인

Service의 고정된 IP가 실제로 존재하는 파드들로 트래픽을 전달하려면, 가상 IP를 실제 파드 IP로 변환하는 메커니즘이 필요하다. 이 변환을 직접 구현하면 복잡하고 확장성이 떨어진다.

2질문 제기

Service의 가상 IP가 뒤의 여러 파드 주소로 어떻게 변환되고 분배될까?

3구조적 핵심 예시

EndpointSlice는 Service가 대상으로 하는 파드들의 현재 IP 주소 목록을 관리한다. 각 노드의 kube-proxy가 이 목록을 읽어 노드의 iptables 또는 IPVS(가상 서버) 규칙으로 변환한다. 트래픽이 도착하면 이 규칙이 가상 IP를 실제 파드 IP로 바꾼다.

4단계별 동작 과정

  1. EndpointSlice 관리Service 뒤의 파드가 추가되거나 제거될 때마다 EndpointSlice가 현재 파드 IP 목록을 갱신한다.
  2. kube-proxy가 규칙 설정각 노드의 kube-proxy가 EndpointSlice를 감시하다가 변화를 감지하면, 노드의 iptables 또는 IPVS 규칙을 수정한다.
  3. 트래픽 변환파드에서 Service IP로 트래픽을 보내면, 노드의 네트워크 규칙이 자동으로 목표 주소를 실제 파드 IP로 변환한다.

5본질 요약

EndpointSlice와 kube-proxy는 Service의 가상 IP를 실제 파드 주소로 변환하는 협력 구조로, 트래픽이 올바른 파드에 도달하게 합니다.

볼륨의 개념과 종류

컨테이너가 재시작돼도 데이터를 유지하거나 파드 안에서 파일을 공유하도록 파드에 붙이는 디렉터리로, 수명이 파드와 같은 임시 볼륨부터 외부 저장소까지 여러 종류가 있다.

2질문 제기

파드 재시작 후에도 데이터를 유지하고, 같은 파드 내 컨테이너가 파일을 공유하려면 어떻게 할까?

3구조적 핵심 예시

emptyDir 볼륨은 파드가 생성될 때 노드에 임시 디렉터리를 만들어서 같은 파드의 여러 컨테이너가 그 디렉터리에 접근해 파일을 공유한다. persistentVolume은 외부 저장소(클라우드 스토리지, NFS 등)와 연결되어, 파드가 재시작돼도 데이터가 유지된다.

4단계별 동작 과정

  1. 볼륨이 파드에 마운트됨파드 정의에 따라 각 컨테이너가 특정 볼륨을 특정 경로에 마운트한다.
  2. 컨테이너가 마운트 경로로 접근컨테이너의 애플리케이션은 마운트된 경로에서 파일을 읽고 쓸 수 있다.
  3. 데이터 유지 여부는 볼륨 종류에 따름emptyDir은 파드 삭제 시 함께 제거되지만, persistentVolume이나 hostPath는 파드 재시작 후에도 데이터가 남아 있다.

PersistentVolume·PVC 생명주기

실제 저장 장치를 나타내는 PersistentVolume과 사용자가 용량·접근모드를 요청하는 PVC가 바인딩·사용·반환(Reclaim) 단계를 거치며 파드와 독립적으로 데이터를 관리하는 구조다.

1상대의 출발점 확인

컨테이너 내부에 저장한 데이터는 컨테이너가 삭제되면 함께 사라집니다. 파드가 재시작되거나 노드에서 제거되면 그 안의 모든 데이터가 손실됩니다. 데이터를 영구적으로 보존하려면 파드 외부의 저장소를 매번 직접 관리해야 하고, 여러 파드가 같은 데이터에 접근해야 할 때도 저장소 연결을 수동으로 처리해야 합니다.

2질문 제기

파드가 재시작되거나 삭제되어도 데이터는 어떻게 유지할 수 있을까요?

3구조적 핵심 예시

PersistentVolume(PV)은 클러스터에 존재하는 실제 저장 장치(디스크)의 리소스 표현이고, PersistentVolumeClaim(PVC)은 사용자가 "2GB, 읽기-쓰기 권한"처럼 용량과 접근 모드로 저장소를 신청하는 요청서입니다. 이 둘이 바인딩되면 파드는 PVC를 통해 저장소에 접근합니다.

4단계별 동작 과정

  1. 바인딩 단계관리자가 미리 만든 PV와 사용자가 제출한 PVC의 용량·접근 권한·스토리지클래스가 맞으면 둘이 연결됩니다.
  2. 사용 단계파드가 PVC를 볼륨으로 마운트해 데이터를 읽고 씁니다. 파드가 삭제되거나 노드가 변경되어도 PV의 데이터는 남아있습니다.
  3. 반환 단계PVC를 삭제하면 Reclaim Policy(반환 정책: Delete·Retain·Recycle 중 선택)에 따라 PV의 데이터를 삭제하거나 보존합니다.

1상대의 출발점 확인

저장소가 필요할 때마다 관리자가 직접 PV를 미리 만들어 두어야 합니다. PV의 크기가 부족하면 새로운 PV를 생성한 뒤 바인딩해야 하고, 여러 파드가 각각 다른 크기와 성능의 저장소를 요청하면 관리 복잡도가 늘어납니다. 미리 만들어 둔 PV가 사용되지 않으면 자원이 낭비되고, 필요한 시점에 PV가 없으면 파드 배치가 지연됩니다.

2질문 제기

PVC를 요청하는 순간 필요한 크기의 저장소를 자동으로 만들 수 없을까요?

3구조적 핵심 예시

StorageClass는 저장소의 종류를 미리 정의해 두는 설정서입니다(예: "빠른 SSD", "일반 HDD", "저비용 클라우드 스토리지"). PVC를 만들 때 원하는 StorageClass를 지정하면, 쿠버네티스가 그 규격에 맞는 PV를 자동으로 생성하고 바인딩합니다. 이를 동적 프로비저닝이라 합니다.

4단계별 동작 과정

  1. StorageClass 정의저장소 공급자(provisioner: AWS EBS, GCP Persistent Disk, NFS 등)와 그 속성(IOPS, 암호화 여부, 복제 정책)을 미리 선언합니다.
  2. PVC 생성 및 자동 할당사용자가 "5GB + 이 StorageClass"를 요청하면, 쿠버네티스가 자동으로 해당 공급자에 PV 생성을 지시합니다.
  3. 스케줄링 고려노드별 잔여 용량을 감안해 PV를 최적의 노드에 할당하므로, 저장소 부족으로 인한 파드 배치 실패를 줄입니다.

볼륨 스냅샷과 데이터 소스

VolumeSnapshot으로 특정 시점의 볼륨 상태를 떠 두고, 그 스냅샷이나 기존 PVC를 dataSource 로 삼아 새 볼륨을 복제·복원할 수 있다.

1상대의 출발점 확인

특정 시점의 데이터를 보관하려면 전체 내용을 수동으로 복사해야 합니다. 여러 파드가 같은 데이터로 시작해야 하면 매번 복사 과정을 반복해야 하고, 복사 중 오류가 발생하면 처음부터 다시 시작해야 합니다. 실행 중인 볼륨에서 데이터를 복사하면 데이터 일관성 문제가 생길 수 있고, 대용량 데이터 복사는 시간이 오래 걸립니다.

2질문 제기

볼륨의 특정 시점 상태를 스냅샷으로 떠 두고, 그것으로부터 새 볼륨들을 빠르게 만들 수 없을까요?

3구조적 핵심 예시

VolumeSnapshot은 실행 중인 PV의 상태를 특정 시점에 캡처해 둔 것입니다. 그 스냅샷이나 기존 PVC를 dataSource로 지정해 새 PVC를 만들면, 원본 데이터가 새 볼륨으로 복제됩니다. 복사하는 동안 원본 PV는 계속 사용할 수 있으며, 스냅샷 기술을 지원하는 저장소는 전체 복사 대신 효율적인 증분 복제를 수행합니다.

4단계별 동작 과정

  1. 스냅샷 생성실행 중인 PV의 상태를 특정 시점에 캡처해 VolumeSnapshot 리소스로 저장합니다. 스냅샷 생성 중에도 원본 볼륨은 정상 작동합니다.
  2. 데이터 소스 지정새 PVC를 만들 때 dataSource 필드에 VolumeSnapshot이나 기존 PVC를 지정합니다.
  3. 볼륨 복제 또는 복원지정한 소스의 데이터를 새 볼륨으로 복제하거나, 실수로 삭제된 데이터를 스냅샷에서 복원합니다.

7리소스 관리와 스케줄링07-01

리소스 요청·제한·QoS와 인플레이스 리사이즈

컨테이너에 CPU·메모리를 얼마나 보장(requests)하고 얼마까지 허용(limits)할지 정하면 파드의 QoS 등급이 결정되며, 최신 버전에서는 파드를 재시작하지 않고 이 값을 바꿀 수 있다.

→ 07-08 참조

1상대의 출발점 확인

파드가 얼마나 많은 CPU와 메모리를 사용할지 미리 정하지 않으면, 한 파드가 노드의 모든 자원을 독점해서 다른 파드들이 실행될 수 없게 됩니다. 미리 제한을 정해 둬도 나중에 값을 바꾸려면 파드를 종료하고 새로 만들어야 하므로, 서비스가 중단되고 기존 상태가 초기화됩니다.

2질문 제기

파드를 재시작하지 않고도 CPU·메모리 한계를 조정할 수 없을까요?

3구조적 핵심 예시

requests는 파드가 "최소 이만큼 보장받겠다"는 예약이고, limits는 "이 이상 쓸 수 없다"는 상한선입니다. 두 값의 조합에 따라 파드의 QoS 등급(Guaranteed·Burstable·BestEffort)이 결정되며, 리소스 부족 시 등급이 낮은 파드부터 제거됩니다. 최신 쿠버네티스에서는 인플레이스 리사이즈 기능으로 파드를 재시작하지 않고 이 값들을 변경할 수 있습니다.

4단계별 동작 과정

  1. 요청과 제한 설정컨테이너마다 requests(보장 최소값)와 limits(상한값)를 선언하면, 두 값의 관계에 따라 QoS 등급이 할당됩니다.
  2. QoS에 따른 스케줄링 및 축출Guaranteed 파드부터 우선 배치되고, 리소스 부족 시 BestEffort 파드부터 제거됩니다.
  3. 인플레이스 리사이즈실행 중인 파드의 requests·limits를 변경하면, 컨테이너를 재시작하지 않고 새 값이 적용됩니다.

LimitRange·ResourceQuota로 네임스페이스 제한

LimitRange는 개별 파드·컨테이너의 기본값과 상·하한을, ResourceQuota는 네임스페이스 전체가 쓸 수 있는 자원 총량과 오브젝트 개수를 제한한다.

1상대의 출발점 확인

각 파드의 requests·limits만 정해놓으면, 한 네임스페이스 안에서 여러 사용자가 마음대로 파드를 만들어 전체 노드 리소스를 낭비할 수 있습니다. 개별 파드의 최대·최소 자원 규모에 대한 기본값도 없어서 파드마다 설정이 제각각이고 일관성이 떨어집니다. 조직의 팀이나 프로젝트별로 자원을 공정하게 분배할 방법이 없습니다.

2질문 제기

개별 파드와 네임스페이스 전체의 자원 사용을 동시에 제한할 수 없을까요?

3구조적 핵심 예시

LimitRange는 개별 파드·컨테이너가 쓸 수 있는 자원의 기본값과 상·하한을 정하는 정책입니다. ResourceQuota는 네임스페이스 전체가 사용할 수 있는 자원 총량과 파드·PVC 같은 오브젝트의 개수까지 제한합니다. 둘을 함께 쓰면 개별 파드의 무분별한 자원 사용과 네임스페이스 차원의 과다 할당을 동시에 방지할 수 있습니다.

4단계별 동작 과정

  1. LimitRange 적용네임스페이스에 LimitRange를 만들면, 새 파드의 requests·limits가 그 정책에 맞지 않으면 생성이 거부되고, 명시하지 않은 값은 기본값으로 자동 채워집니다.
  2. ResourceQuota 설정네임스페이스에 ResourceQuota를 만들면, 그 안의 모든 파드가 쓸 수 있는 CPU·메모리 합계와 생성할 수 있는 오브젝트 개수가 제한됩니다.
  3. 정책 위반 시 차단할당량을 초과하면 추가 리소스 요청이 거부되고, 관리자가 할당량을 늘려야만 진행할 수 있습니다.

확장 리소스·GPU·hugepages와 동적 리소스 할당(DRA)

CPU·메모리 외의 GPU 같은 장치는 확장 리소스나 DRA(ResourceClaim·DeviceClass)로 선언하고 요청해 파드에 붙인다.

1상대의 출발점 확인

리소스 요청은 CPU와 메모리만 가능하고, GPU나 특수 네트워크 인터페이스 같은 다른 자원은 이름 기반으로만 요청할 수 있습니다. 복잡한 할당 정책이나 공유 자원의 세부 제어가 불가능하고, 파드가 정확히 어떤 장치를 받았는지 파악하기 어렵습니다. 같은 GPU를 여러 파드가 함께 사용해야 할 때도 충돌 제어가 제한적입니다.

2질문 제기

CPU·메모리 외의 GPU나 특수 장치는 어떻게 요청하고 할당할까요?

3구조적 핵심 예시

기존 확장 리소스는 노드가 "nvidia.com/gpu=4"처럼 선언하고 파드가 그 이름으로 요청하는 방식입니다. 최신 동적 리소스 할당(DRA)은 DeviceClass(장치의 종류와 기능을 정의)와 ResourceClaim(파드가 필요한 기능을 요청)을 쌍으로 사용해 더 세밀한 제어가 가능합니다. ResourceClaim을 통해 파드는 어떤 구체적인 장치를 받았는지도 알 수 있습니다.

4단계별 동작 과정

  1. 확장 리소스 또는 DeviceClass 선언노드가 GPU·hugepages 같은 특수 자원의 보유 개수를 선언하거나, 복잡한 요구사항은 DeviceClass로 정의합니다.
  2. 파드가 자원 요청파드의 컨테이너가 requests에 자원 이름(nvidia.com/gpu)을 명시하거나, DRA 방식으로 ResourceClaim을 제출합니다.
  3. 스케줄러가 할당파드를 배치할 노드를 선택하면서 요청한 특수 자원의 보유 여부를 확인하고, 할당이 완료되면 파드가 그 자원을 사용할 수 있습니다.

kube-scheduler와 스케줄링 프레임워크

kube-scheduler는 노드를 걸러내고(filter) 점수를 매겨(score) 파드를 배치하며, 그 단계마다 플러그인을 끼워 넣는 구조가 스케줄링 프레임워크다.

1상대의 출발점 확인

파드가 어느 노드에 배치될지 정하는 과정이 고정적이고 불투명합니다. 조직의 특수한 정책(예: 특정 팀의 파드는 특정 노드만 사용, 지역별 배치 규칙, 비용 최소화)을 반영하기 어렵고, 스케줄러를 수정하려면 쿠버네티스 코드를 직접 변경하거나 서드파티 스케줄러를 따로 운영해야 합니다.

2질문 제기

기본 스케줄링 알고리즘에 조직의 정책을 플러그인으로 끼워 넣을 수는 없을까요?

3구조적 핵심 예시

kube-scheduler는 모든 파드를 어느 노드에 배치할지 정하는 쿠버네티스 컴포넌트입니다. 스케줄링 프레임워크는 그 과정을 여러 단계(필터링·점수 매기기 등)로 나누고 각 단계마다 플러그인을 끼울 수 있도록 설계했습니다. 조직이 필요한 로직을 플러그인으로 만들어 설정하면, 쿠버네티스 코드를 수정하지 않고도 스케줄링 정책을 확장할 수 있습니다.

4단계별 동작 과정

  1. 필터링 단계파드의 requests·nodeSelector·affinity와 노드의 taints·labels를 보고 배치 가능한 노드들을 걸러냅니다. 커스텀 플러그인은 추가 조건을 검사해 후보를 더 줄입니다.
  2. 점수 매기기 단계필터링을 통과한 노드들에 우선순위 점수를 부여합니다. 기본은 리소스 분배 균형이지만, 플러그인이 조직 정책(비용·지역·팀별 규칙)에 따라 점수를 조정할 수 있습니다.
  3. 바인딩 단계가장 높은 점수를 받은 노드를 선택해 파드를 그 노드에 할당합니다.

7리소스 관리와 스케줄링07-05

노드 선택: nodeSelector·어피니티·테인트/톨러레이션

파드 쪽에서 원하는 노드를 고르는 nodeSelector·어피니티와, 노드 쪽에서 파드를 밀어내는 테인트/톨러레이션으로 배치를 제어한다.

1상대의 출발점 확인

처음에는 쿠버네티스가 파드를 단순히 자동으로 아무 노드에나 배치했습니다. 하지만 실제로는 어떤 파드는 GPU가 필요하고, 어떤 파드는 특정 가용 영역(존)에 있어야 하며, 어떤 노드는 시스템 용도로만 예약해야 합니다. 이런 제약 없이 배치하면 요구사항을 만족할 수 없습니다.

2질문 제기

특정 파드를 원하는 특정 노드 또는 노드 그룹에만 배치하려면?

3구조적 핵심 예시

GPU 파드가 필요하면, 파드 정의에 "GPU 있는 노드에만 실행"이라고 적고, 노드에는 "gpu=true" 라벨을 붙입니다. 반대로 노드 쪽에서 "이 노드는 시스템만" 테인트를 두면, 특별 허용(톨러레이션)이 없는 파드는 그 노드에 올라올 수 없습니다.

4단계별 동작 과정

  1. 파드 측 선택 조건 설정nodeSelector로 단순 라벨 조건을, 어피니티(affinity)로 더 복잡한 선호도(선호하지만 필수는 아님)를 지정합니다.
  2. 노드 측 거부 규칙 적용테인트(taint)를 노드에 붙이면 그 테인트와 맞지 않는 톨러레이션(tolerance)을 가진 파드는 올라올 수 없습니다.
  3. 스케줄러의 배치 판단쿠버네티스 스케줄러가 파드를 배치할 노드를 고를 때 파드의 선택 조건과 노드의 테인트를 모두 확인해 적합한 노드를 찾습니다.

  2. 우선순위 클래스 적용PriorityClass로 파드마다 우선순위 숫자를 정의하고, 파드가 이 클래스를 참조합니다.

1상대의 출발점 확인

노드는 리눅스 커널, kubelet, 컨테이너 런타임 등 시스템 프로세스가 항상 일정량의 CPU와 메모리를 사용합니다. 기존 방식에서 kubelet이 이 시스템 리소스를 고려하지 않으면, 파드들이 할당받을 수 있는 용량을 계산할 때 실제 가용 리소스보다 많게 책정되어 파드 간 자원 경쟁이 심해지고, 결국 스왑으로 인한 성능 저하나 노드 불안정이 발생합니다.

2질문 제기

kubelet이 시스템이 반드시 필요한 리소스를 미리 떼어두고, 파드에게는 그 나머지만 할당할 수 있을까?

3구조적 핵심 예시

노드의 CPU가 4개, 메모리가 16GB인 경우, kubelet 설정에서 --kube-reserved 플래그로 "CPU 500m, 메모리 2GB"를 예약하면, kubelet은 스케줄러에게 "이 노드의 할당 가능 리소스는 CPU 3.5개, 메모리 14GB"라고 보고합니다. 그러면 파드들은 그 한도 내에서만 할당받고, 나머지 CPU 500m과 메모리 2GB는 시스템 프로세스가 사용할 수 있습니다.

4단계별 동작 과정

  1. 설정 값 정의kubelet의 설정 파일(kubelet-config.yaml) 또는 시작 플래그(--kube-reserved, --system-reserved, --eviction-hard)로 시스템이 예약할 리소스 양과 스왑 사용 정책을 선언합니다.
  2. 가용 용량 재계산kubelet이 노드의 실제 전체 리소스에서 예약된 양을 빼서, 스케줄러가 알고 있는 할당 가능 용량을 갱신합니다.
  3. 파드 스케줄링 및 실행스케줄러는 이 갱신된 용량을 기준으로 파드를 배치하고, kubelet은 cgroup 설정으로 파드의 리소스 사용을 그 한도에서 강제합니다.

CPU·메모리·토폴로지 매니저와 cgroup v2

노드 안에서 CPU 코어와 메모리를 어떻게 배분·정렬할지 결정하는 kubelet 리소스 매니저들과, 그 배분을 실제로 강제하는 리눅스 cgroup v2 계층이다.

1상대의 출발점 확인

일반적인 노드에서 CPU와 메모리는 모두 같은 속도로 접근 가능합니다. 하지만 NUMA(Non-Uniform Memory Access) 아키텍처를 가진 고성능 서버에서는 CPU 코어가 특정 메모리 영역에 가까워 빠르고, 다른 메모리 영역에는 느립니다. 기존 방식에서 리소스 할당이 이 물리적 위치를 고려하지 않으면, 파드가 멀리 떨어진 메모리에 접근하면서 레이턴시가 늘어나고 전체 성능이 저하됩니다.

2질문 제기

파드가 요청한 CPU와 메모리를 모두 같은 물리적 위치(토폴로지)에서 할당해 접근 속도를 최대화할 수 있을까?

3구조적 핵심 예시

NUMA 시스템에서 CPU 0-3은 메모리 버스 A에, CPU 4-7은 메모리 버스 B에 붙어 있습니다. 토폴로지 매니저가 파드 요청을 받으면 "CPU 2개 필요, 메모리 4GB 필요"를 분석해 CPU 0-1(버스 A)에 메모리도 같은 버스 A에서 할당하도록 정렬합니다. 이렇게 하면 그 파드는 빠른 로컬 메모리 접근이 보장됩니다.

4단계별 동작 과정

  1. 토폴로지 정보 수집kubelet이 노드의 CPU와 메모리 배치 정보(NUMA 토폴로지)를 수집하고, 어느 CPU가 어느 메모리 영역에 가까운지 매핑합니다.
  2. 리소스 정렬 결정파드의 리소스 요청이 들어오면, 토폴로지 매니저가 그 요청을 만족하는 CPU와 메모리 조합을 찾되, 같은 토폴로지 영역에서만 선택합니다.
  3. cgroup v2로 강제선택된 CPU와 메모리 위치를 cgroup v2의 cpuset과 memory.nodes 세팅에 기록해, 리눅스 커널이 그 범위 내에서만 리소스 할당을 수행하도록 합니다.

5본질 요약

토폴로지 매니저가 NUMA 아키텍처의 물리적 위치를 고려해 CPU와 메모리를 함께 할당하고, cgroup v2가 그것을 커널 수준에서 강제함으로써 메모리 접근 속도를 최적화하는 것

Kubernetes는 리눅스 컨트롤 플레인 아래에 Windows 워커 노드를 붙여 Windows 컨테이너를 실행할 수 있으며, 지원 기능과 제약이 리눅스와 다르다.

1상대의 출발점 확인

2질문 제기

Kubernetes 클러스터에서 Windows 컨테이너를 실행하는 것이 가능할까?

3구조적 핵심 예시

4단계별 동작 과정

  1. Windows 노드 준비Windows Server 운영체제가 설치된 머신에 kubelet과 컨테이너 런타임(containerd 또는 Docker)을 설치하고, 클러스터에 조인합니다.
  2. 파드 스펙에서 Windows 지정파드 매니페스트의 nodeSelector 또는 taint/toleration으로 그 파드가 Windows 노드에서 실행되어야 함을 명시합니다.
  3. Windows 컨테이너 실행스케줄러가 파드를 Windows 노드에 배치하고, kubelet이 Windows 컨테이너 이미지를 받아 실행합니다.

클러스터 접근 제어 개요와 인증

API 서버 요청은 인증 → 인가 → 어드미션 3단계를 거치며, 인증은 "누가 요청했는가"를 인증서·토큰·OIDC 등으로 확인하는 첫 관문이다.

1상대의 출발점 확인

초기 Kubernetes 클러스터는 API 서버에 누가 접근했든 요청이 즉시 처리됩니다. 그래서 누가 요청을 보냈는지, 그 사람이 실제 권한을 가진 사람인지, 어떤 동작을 하려는 것인지 검증 없이 허용되므로, 보안 위험이 매우 큽니다.

2질문 제기

API 서버가 각 요청이 정말 신뢰할 수 있는 사용자에게서 온 것이고, 그 사용자가 그 요청을 할 권한이 있는지 어떻게 확인할까?

3구조적 핵심 예시

kubectl 클라이언트가 API 서버에 파드 생성 요청을 보낼 때, ~/.kube/config에 저장된 클라이언트 인증서(.crt, .key)를 HTTP 헤더에 포함시킵니다. API 서버는 이 인증서를 클러스터의 CA(인증 기관) 인증서로 검증해 "이 요청은 alice라는 사용자에게서 온 것이 확실하다"고 확인합니다.

4단계별 동작 과정

  1. 인증(Authentication)클라이언트가 인증서, 토큰, 또는 기타 자격증명을 요청에 포함시키고, API 서버의 인증 모듈이 이를 검증해 "이 사용자는 alice"라고 확인합니다.
  2. 인가(Authorization)인증에 성공한 요청에 대해 인가 모듈(주로 RBAC)이 "alice 사용자가 파드 생성 권한을 가지고 있나?"를 확인합니다.
  3. 어드미션(Admission)인가를 통과한 요청이 저장되기 직전에 어드미션 컨트롤러가 정책 규칙(예: "모든 파드는 리소스 제한이 있어야 함") 준수 여부를 검증합니다.

ServiceAccount와 파드에서의 API 접근

ServiceAccount는 사람이 아닌 파드가 API 서버에 접근할 때 쓰는 신원으로, 수명이 짧은 토큰이 파드에 자동 마운트된다.

1상대의 출발점 확인

사람(개발자, 관리자)은 kubectl이나 REST API로 Kubernetes에 접근할 때 사용자 계정이 필요합니다. 하지만 파드 안의 애플리케이션 프로세스도 API 서버와 통신해야 할 경우(예: 다른 파드 정보 조회, 자신의 설정 업데이트)가 있는데, 사람용 사용자 계정으로는 이를 표현할 수 없습니다.

2질문 제기

파드 안의 애플리케이션이 API 서버에 요청할 때, 어떤 신원으로 그 요청이 온 것인지 증명할 수 있을까?

3구조적 핵심 예시

파드가 생성될 때 자동으로 "default" ServiceAccount가 할당되고, Kubernetes가 짧은 수명의 JWT 토큰을 생성해 파드의 /var/run/secrets/kubernetes.io/serviceaccount/token 파일에 마운트합니다. 파드 내 애플리케이션이 이 파일에서 토큰을 읽어 HTTP Authorization 헤더에 "Bearer <token>"으로 담아 보내면, API 서버가 그것을 검증해 "이 요청은 default ServiceAccount에서 온 것"이라고 확인합니다.

4단계별 동작 과정

  1. ServiceAccount 할당파드가 생성될 때 매니페스트에서 지정된 ServiceAccount(또는 기본값 "default")가 파드에 할당됩니다.
  2. 토큰 생성 및 마운트Kubernetes가 그 ServiceAccount의 이름으로 짧은 수명의 토큰을 생성해 시크릿으로 저장하고, 파드의 /var/run/secrets/kubernetes.io/serviceaccount 디렉토리에 마운트합니다.
  3. API 요청 수행파드 내 애플리케이션이 token 파일을 읽어 API 호출 헤더에 포함시키고, API 서버가 그 토큰으로 ServiceAccount를 식별하고 인가 단계로 진행합니다.

5본질 요약

Kubernetes가 파드마다 ServiceAccount라는 고유한 신원을 부여하고, 짧은 수명의 토큰을 자동으로 마운트함으로써 파드 내 프로세스가 API 서버에 신뢰할 수 있는 신원으로 접근할 수 있게 하는 것

인가: RBAC·Node·ABAC·Webhook

인증된 사용자가 어떤 리소스에 무슨 동작을 할 수 있는지 결정하는 단계로, 역할 기반의 RBAC가 사실상 표준 모드다.

1상대의 출발점 확인

인증으로 "누가 요청했는가"가 확인되면, 그 다음은 "그 사용자가 이 동작을 할 권한이 있는가"를 판단해야 합니다. 기존 방식에서 인증만 통과하면 모든 사용자가 클러스터의 모든 리소스에 모든 동작(생성, 수정, 삭제)을 할 수 있으므로, 보안과 거버넌스가 불가능합니다.

2질문 제기

인증된 사용자가 특정 리소스에 대해 특정 동작을 할 권한을 가지고 있는지, 어떻게 결정할 것인가?

3구조적 핵심 예시

"pod-reader"라는 Role을 "pods 리소스에 대해 get, list, watch 동작만 허용"이라고 정의하고, developer 사용자에게 RoleBinding으로 이 역할을 할당합니다. 그러면 developer는 파드를 조회하거나 목록을 볼 수 있지만, 파드를 생성하거나 삭제할 수는 없습니다. 다른 사용자나 리소스에는 이 Role의 권한이 적용되지 않습니다.

4단계별 동작 과정

  1. Role 정의Role(네임스페이스 범위) 또는 ClusterRole(전체 클러스터 범위)에서 리소스와 그 리소스에 허용되는 동작(get, list, watch, create, update, delete 등)을 명시합니다.
  2. RoleBinding 생성사용자, 그룹, 또는 ServiceAccount를 Role에 바인딩합니다. 이것이 "이 사용자는 이 역할의 권한을 가진다"는 규칙입니다.
  3. 요청 평가API 서버의 인가 모듈이 인증된 사용자의 모든 바인딩을 검색해, 요청하는 리소스와 동작이 어떤 Role에 허용되어 있는지 확인합니다.

5본질 요약

인가를 통과한 요청이 저장되기 직전에 객체를 검증하거나 변형하는 관문으로, 웹훅 대신 CEL 식으로 클러스터 내부에서 정책을 표현할 수도 있다.

1상대의 출발점 확인

인가까지 통과한 요청은 검증 없이 즉시 클러스터에 저장됩니다. 그래서 권한이 있는 사용자라도 보안 정책이나 조직 규칙을 어긴 객체(예: 리소스 제한 없는 파드, 루트 권한으로 실행되는 컨테이너)를 생성할 수 있고, 이는 클러스터 안정성을 해칩니다.

2질문 제기

인가를 통과한 요청이 저장되기 직전에, 그 객체가 조직의 보안 정책과 규칙을 만족하는지 어떻게 검증할 수 있을까?

3구조적 핵심 예시

ValidatingAdmissionPolicy로 "모든 파드는 CPU와 메모리 limit을 가져야 한다"는 정책을 CEL(Common Expression Language) 식으로 작성하면, 그 조건 없이 파드 생성 요청이 들어올 때 어드미션 컨트롤러가 그 식을 평가해 거부합니다. 동시에 MutatingAdmissionPolicy로 "limit이 없으면 기본값을 자동 추가"하는 변형 규칙을 등록하면, 사용자 요청은 자동으로 정책에 맞게 수정되어 저장됩니다.

4단계별 동작 과정

  1. 인가 통과 후 가로채기인가를 통과한 요청(객체 생성, 수정)이 etcd에 저장되기 직전에 어드미션 단계에서 멈춥니다.
  2. 정책 평가등록된 ValidatingAdmissionPolicy(검증 정책)의 CEL 식을 요청의 객체에 대해 평가하거나, MutatingAdmissionPolicy(변형 정책)를 실행해 필요시 객체를 수정합니다. 또는 웹훅(외부 API)을 호출해 검증/변형합니다.
  3. 허용 또는 거부정책 결과가 허용이면 객체를 저장하고, 거부이면 사용자에게 오류를 반환합니다.

Pod Security Standards와 Pod Security Admission

1상대의 출발점 확인

기존에는 쿠버네티스 클러스터에 파드를 배포할 때 관리자가 파드 매니페스트에서 어떤 보안 설정이 필요한지 각각 수동으로 설정했습니다. 예를 들어, 특정 파드가 root 권한으로 실행되지 않는지, 특정 시스템콜을 차단해야 하는지 등을 일일이 결정해야 했습니다. 이러한 방식은 일관된 보안 정책을 강제하기 어렵고, 개발팀과 보안팀 간 기준이 달라질 수 있습니다.

2질문 제기

쿠버네티스 클러스터에 배포되는 모든 파드의 보안 수준을 사전에 정한 기준에 맞춰 일관되게 강제할 수 있을까요?

3구조적 핵심 예시

Pod Security Standards(PSS)는 파드의 보안을 privileged(제한 없음), baseline(기본 보안 강화), restricted(엄격한 보안) 세 단계로 정의합니다. 관리자는 네임스페이스에 label을 붙여서 "이 네임스페이스의 모든 파드는 restricted 수준을 만족해야 한다"고 선언하면, Pod Security Admission(어드미션 플러그인, 쿠버네티스가 새 파드를 받아들일 때 거치는 보안 검증 단계)이 매니페스트를 자동으로 검사해 기준에 맞지 않는 파드는 거부합니다.

4단계별 동작 과정

  1. 정책 선언관리자가 네임스페이스에 pod-security.kubernetes.io/enforce=restricted 같은 label을 붙여서 어느 수준의 보안을 강제할지 지정합니다.
  2. 파드 배포 요청개발자가 kubectl apply로 파드 매니페스트를 제출하면 쿠버네티스 API 서버가 받습니다.
  3. 검증과 판단Pod Security Admission이 매니페스트의 securityContext, privileged 모드, 호스트 경로 접근 등을 네임스페이스의 정책과 비교해서 기준에 맞으면 승인, 맞지 않으면 거부합니다.

3구조적 핵심 예시

4단계별 동작 과정

  1. 매니페스트에 securityContext 설정파드나 컨테이너 스펙에 runAsUser, runAsNonRoot, seccomp, AppArmor 정책을 선언합니다.

kubeadm으로 클러스터 부트스트랩

kubeadm init 으로 컨트롤 플레인을 만들고 join 으로 노드를 붙여 최소한의 동작 가능한 클러스터를 세우는 표준 도구다.

1상대의 출발점 확인

쿠버네티스 클러스터를 직접 구축할 때, 관리자가 수작업으로 etcd, API 서버, scheduler, controller-manager, kubelet 등 각 컴포넌트를 일일이 설치하고 인증서를 발급하고 설정 파일을 작성해야 한다면 매우 복잡합니다. kubeadm은 이 모든 과정을 자동화해주는 공식 도구입니다.

2질문 제기

여러 대의 서버에서 쿠버네티스 클러스터를 빠르게, 일관되게 구축할 수 있을까요?

3구조적 핵심 예시

kubeadm은 두 가지 명령어로 클러스터를 만듭니다. 첫째, kubeadm init을 컨트롤 플레인이 될 서버에 실행하면, kubeadm이 필요한 인증서를 자동 생성하고 etcd, API 서버, scheduler, controller-manager를 정적 파드(Static Pod, 마스터 노드에서 kubelet이 직접 관리하는 파드)로 띄웁니다. 둘째, kubeadm join 명령어를 워커 노드에서 실행하면, 그 노드가 클러스터에 자동으로 등록되고 kubelet이 시작됩니다.

4단계별 동작 과정

  1. 컨트롤 플레인 초기화kubeadm init을 실행하면, kubeadm이 필요한 인증서와 설정 파일을 생성하고, 컨트롤 플레인 컴포넌트(API 서버, etcd, scheduler 등)를 kubelet으로 실행합니다.
  2. 네트워크 애드온 설치kubectl을 사용해 클러스터 네트워킹을 담당할 CNI(Container Network Interface) 플러그인(Flannel, Calico 등)을 설치합니다.

1상대의 출발점 확인

기본 kubeadm으로 구축한 클러스터는 컨트롤 플레인이 한 대의 서버에만 있습니다. API 서버나 etcd가 있는 그 서버가 죽으면, 클러스터 전체가 더 이상 명령을 받을 수 없습니다. 실행 중인 파드는 계속 돌지만, 새 파드를 만들거나 기존 파드를 관리할 수 없게 됩니다.

2질문 제기

3구조적 핵심 예시

컨트롤 플레인을 여러 대의 서버에 복제합니다. 예를 들어, 서버 A, B, C 세 대에 각각 API 서버, scheduler, controller-manager를 배포하고, etcd도 세 대에서 분산 클러스터로 실행합니다. 로드 밸런서가 클라이언트 요청을 세 API 서버에 분산하면, A 서버가 죽어도 B, C의 API 서버가 요청을 처리합니다.

4단계별 동작 과정

  1. 여러 컨트롤 플레인 생성kubeadm으로 첫 번째 컨트롤 플레인을 init으로 만든 후, --control-plane 플래그로 join 명령어를 실행해 나머지 컨트롤 플레인 서버들을 클러스터에 추가합니다.
  2. etcd 클러스터 구성etcd는 여러 인스턴스가 합의(consensus) 알고리즘을 통해 상태를 동기화합니다. 각 컨트롤 플레인 서버의 etcd가 서로 연결되어 데이터를 복제합니다.
  3. 로드 밸런서 배치API 서버 앞에 로드 밸런서를 두어 클라이언트 요청을 여러 API 서버에 분산시키고, 한 서버가 다운돼도 다른 서버가 처리합니다.

3구조적 핵심 예시

노드를 추가할 때는 kubeadm join으로 새 노드를 클러스터에 등록하면, 스케줄러가 자동으로 새 파드를 그 노드에 배치합니다. 노드 업그레이드할 때는 먼저 kubectl drain으로 노드를 '배수(Drain)' 상태로 만들어 그 노드의 모든 파드를 다른 노드로 옮기고, 업그레이드를 진행한 후, 다시 uncordon으로 파드 수신 가능 상태로 전환합니다.

  2. 노드 업그레이드 준비kubectl cordon으로 노드를 '신규 파드 미할당' 상태로 전환하고, kubectl drain으로 기존 파드를 다른 노드로 graceful 마이그레이션(사전 통지와 함께 안전하게 이동)합니다.
  3. 버전 업그레이드 완료노드에서 kubelet과 kubeadm을 새 버전으로 업그레이드하고 재부팅한 후, kubectl uncordon으로 다시 파드 할당 가능 상태로 전환합니다.

CNI·DNS 같은 애드온과 각종 프록시, 클라우드 연동을 담당하는 cloud-controller-manager 를 붙여 클러스터를 완성하는 부분이다.

1상대의 출발점 확인

Kubernetes 클러스터의 핵심 컴포넌트(API 서버, kubelet, controller-manager)만으로는 Pod 간 네트워크 통신이 작동하지 않고, 클러스터 내 서비스 이름 해석도 불가능하며, 클라우드 인프라와 자동 연동도 이루어지지 않습니다. 클러스터 초기화 후에는 Pod이 떠도 통신할 수 없고, 외부 로드밸런서를 자동으로 생성할 수 없는 상태입니다.

2질문 제기

클러스터를 실제로 사용 가능한 상태로 만들기 위해 어떤 네트워킹, DNS, 클라우드 연동 기능을 추가해야 하는가?

3구조적 핵심 예시

클러스터 초기화 후 CoreDNS라는 DNS Pod을 실행하면 클러스터 내 서비스가 nginx-service.default.svc.cluster.local 같은 이름으로 해석되고, Calico나 Flannel 같은 CNI(Container Network Interface) 플러그인을 설치하면 각 노드의 Pod들이 실제로 IP 패킷을 교환할 수 있게 됩니다. AWS나 GCP 같은 클라우드에서 쓸 때는 cloud-controller-manager가 Service의 type을 LoadBalancer로 설정하면 클라우드 API를 호출해 외부 로드밸런서를 자동으로 생성합니다.

4단계별 동작 과정

  1. CNI 플러그인 설치클러스터 네트워크 CIDR 범위를 정하고, 각 노드에 Pod IP 서브넷을 할당한 뒤, 노드 간 네트워크 터널링(VXLAN 같은 방식) 또는 라우트를 설정해 Pod 간 직접 통신을 가능하게 합니다.
  2. DNS 애드온 배포CoreDNS를 클러스터 내에 Pod으로 실행하고, kubelet이 모든 Pod의 /etc/resolv.conf를 CoreDNS 주소로 자동 설정해 서비스 이름 해석을 가능하게 합니다.
  3. 클라우드 컨트롤러 실행cloud-controller-manager가 LoadBalancer 서비스나 PersistentVolume 같은 리소스 변화를 감시해서 클라우드 인프라 API를 호출하고 실제 리소스를 생성합니다.

컴포넌트 플래그·피처 게이트·APF와 대규모 클러스터

각 컴포넌트의 실행 플래그와 피처 게이트로 기능을 켜고 끄며, API Priority and Fairness 등으로 대규모 클러스터의 부하를 다스리는 튜닝 영역이다.

1상대의 출발점 확인

Kubernetes 컴포넌트들은 배포 초기에 고정된 기능 세트로만 작동하며, 실험적이거나 신기능을 켜거나 끌 수 없습니다. 또한 클러스터 규모가 커지면 API 서버에 수천 개의 동시 요청이 몰려 서버가 과부하되고, 중요한 작업(노드 상태 갱신, 데이터베이스 백업)과 일반 폴링 요청이 동등하게 취급되어 응답 지연이 생깁니다.

2질문 제기

대규모 클러스터에서 특정 기능을 선택적으로 켜고, API 서버 과부하를 요청의 우선순위로 관리하려면 어떻게 해야 하는가?

3구조적 핵심 예시

API 서버를 시작할 때 --feature-gates=PodSchedulingReadiness=true,DynamicResourceAllocation=true 같은 플래그로 베타나 알파 기능을 켠다. 대규모 클러스터에서는 API Priority and Fairness(APF)를 활성화해 들어오는 요청의 우선순위(FlowSchema)를 정의하고, 각 우선순위 그룹에 수용 가능한 동시 요청 수(PriorityLevelConfiguration)를 할당한다. 예를 들어 control-plane 요청은 100명, 일반 사용자 요청은 20명으로 정하면, 할당량을 초과한 요청들은 대기열에 들어가거나 거절됩니다.

4단계별 동작 과정

  1. 런타임 기능 제어각 컴포넌트(API 서버, kubelet, scheduler) 시작 시 --feature-gates 플래그로 특정 기능을 활성화하거나 비활성화합니다.
  2. 우선순위 정책 정의FlowSchema로 요청을 분류(사용자, 리소스, 동사)하고, 각 분류를 PriorityLevelConfiguration으로 매핑해 우선순위와 대역폭을 설정합니다.
  3. 요청 처리 및 스로틀링API 서버가 들어온 요청을 FlowSchema와 매칭하고, 해당 우선순위 그룹의 할당량을 확인한 뒤, 여유가 있으면 즉시 처리하고, 초과하면 대기하거나 거절합니다.

로깅 아키텍처와 시스템 로그

컨테이너가 표준출력으로 남긴 로그를 노드가 저장하고 수집기가 모아 보관하는 구조와, 컨트롤 플레인 구성요소의 시스템 로그 체계.

1상대의 출발점 확인

Pod 안의 애플리케이션이 표준출력에 남기는 로그는 노드의 /var/log/pods 디렉터리에만 저장되어, Pod이 삭제되거나 노드가 재부팅되면 로그도 함께 사라집니다. kubelet이나 kube-apiserver 같은 컨트롤 플레인 컴포넌트의 시스템 로그는 노드의 /var/log에 분산되어 있어 클러스터 전체 로그를 한곳에서 볼 수 없고, 장기간 보관하기 어렵습니다.

2질문 제기

클러스터 전체의 애플리케이션 로그와 시스템 로그를 중앙에서 수집해 장기간 보관하고 검색하려면 어떻게 해야 하는가?

3구조적 핵심 예시

각 노드에 Fluentd나 Logstash 같은 로그 수집 에이전트를 DaemonSet으로 실행하면, 에이전트가 노드의 /var/log/pods와 /var/log/kubelet.log 등을 감시해 로그가 생기는 즉시 읽습니다. 수집 에이전트는 Pod의 메타데이터(네임스페이스, Pod 이름, 라벨)를 붙여서 Elasticsearch 같은 중앙 저장소에 전송하고, Kibana에서 전체 클러스터 로그를 검색할 수 있게 됩니다.

4단계별 동작 과정

  1. 로그 생성각 노드의 kubelet이 Pod의 표준출력을 파일로 저장하고, 컨트롤 플레인 컴포넌트들은 자신의 로그를 /var/log 에 남깁니다.
  2. 로그 수집각 노드에서 실행되는 로그 수집 에이전트(Fluentd, Logstash)가 로그 파일을 주기적으로 읽고 Pod 메타데이터를 추가해 중앙 백엔드로 전송합니다.
  3. 로그 보관 및 검색Elasticsearch 같은 저장소에서 로그를 시간 기반으로 인덱싱해 보관하고, Kibana나 kubectl logs 명령어로 조회 및 필터링이 가능하게 합니다.

메트릭과 모니터링 파이프라인

1상대의 출발점 확인

Kubernetes의 kubelet은 Pod과 노드의 CPU, 메모리, 네트워크 사용량을 실시간으로 측정하지만, 이를 수집하는 표준 메커니즘이 없으면 kubectl top pod 명령어를 사용할 수 없고, Kubernetes 대시보드에서 리소스 사용률을 시각화할 수 없습니다. 메트릭이 어디에도 저장되지 않아 과거 데이터도 추적 불가능합니다.

2질문 제기

Pod과 노드의 CPU, 메모리 같은 메트릭을 중앙에서 수집해 현재 상태를 조회하고 과거 데이터를 분석하려면 어떻게 해야 하는가?

3구조적 핵심 예시

kubelet 내의 cAdvisor(컨테이너 성능 분석 도구)가 각 Pod의 CPU, 메모리, 네트워크 통계를 매 초마다 측정해서 kubelet의 메트릭 엔드포인트(/metrics)에 노출합니다. 클러스터 내에 metrics-server Pod을 배포하면, 이 서버가 모든 노드의 kubelet 메트릭을 주기적으로 스크래핑(가져가)해서 메모리에만 보관합니다. kubectl top pod 명령어는 metrics-server에 쿼리해 최근 메트릭을 얻습니다. 더 오래된 데이터와 추세 분석이 필요하면 Prometheus가 metrics-server를 계속 스크래핑해 시계열 데이터베이스에 저장합니다.

4단계별 동작 과정

  1. 메트릭 생성kubelet의 cAdvisor가 각 Pod의 CPU, 메모리, 네트워크 통계를 매 초마다 측정하고, kubelet의 /metrics 엔드포인트를 통해 Prometheus 형식으로 노출합니다.
  2. 메트릭 수집metrics-server가 kubelet의 메트릭 엔드포인트를 주기(기본 15초)마다 스크래핑해서 메모리에 보관하며, Prometheus는 선택적으로 같은 메트릭을 시계열 데이터베이스에 장기 저장합니다.
  3. 메트릭 조회 및 시각화kubectl top, Kubernetes 대시보드, Prometheus 웹 UI, Grafana 같은 도구에서 현재 메트릭이나 과거 데이터를 조회해 그래프와 알림에 활용합니다.

1상대의 출발점 확인

API 서버에 들어온 요청이 인증, 인가, 검증을 거쳐 실제 리소스로 저장되는 과정이 블랙박스처럼 보이며, 어느 컴포넌트에서 병목이 생기는지, 요청이 왜 실패했는지 추적하기 어렵습니다. 또한 누가 언제 어떤 리소스에 어떤 작업을 했는지 기록이 남지 않아 보안 감사와 문제 진단이 불가능합니다.

2질문 제기

API 요청이 컴포넌트 사이를 지나가는 경로와 모든 사용자 작업을 투명하게 추적하고 기록하려면 어떻게 해야 하는가?

3구조적 핵심 예시

OpenTelemetry 트레이싱을 활성화하면, API 서버에 들어온 요청 하나가 "trace" 단위로 감싸져서, 인증, 인가, 검증, etcd 저장 등 각 처리 단계를 "span"이라는 구간으로 기록합니다. 각 span에는 시작·종료 시간이 기록되어 병목을 찾을 수 있습니다. 동시에 감사 로깅(audit logging)을 활성화하면, API 서버가 모든 요청을 JSON 이벤트로 기록해서 어느 사용자(사람 또는 서비스 어카운트)가 어떤 리소스(Pod, Deployment)에 어떤 동작(create, delete, patch)을 했고 언제 했는지 남깁니다.

4단계별 동작 과정

  1. 트레이싱 계측API 서버와 kubelet 같은 핵심 컴포넌트가 OpenTelemetry SDK를 사용해 처리 단계마다 span을 기록하고, trace ID를 전파해 요청의 전체 경로를 연결합니다.
  2. 감사 이벤트 기록API 서버가 RequestReceived, ResponseComplete 같은 단계마다 감사 이벤트(사용자, 리소스, 작업, 결과)를 JSON이나 웹훅으로 남깁니다.
  3. 추적 및 분석Jaeger 같은 백엔드에서 trace를 시각화해 지연을 분석하고, ELK 스택이나 커스텀 대시보드에서 감사 로그를 검색해 특정 사용자나 리소스의 작업 이력을 추적합니다.

1상대의 출발점 확인

Pod이 시작되지 않거나 서비스가 응답하지 않을 때 원인을 파악하기 위해 여러 명령어를 수동으로 조합해야 하고, 각 단계의 출력을 해석해야 합니다. Pod이 이미 종료되었으면 내부에서 무엇이 잘못되었는지 직접 확인할 수 없고, 실행 중인 Pod에 exec로 들어갔을 때도 애플리케이션 상태 변화를 실시간으로 추적하기 어렵습니다.

2질문 제기

Pod이 실행되지 않거나 예상과 다르게 작동할 때 원인을 빠르게 찾고 진단하려면 어떤 도구를 순서대로 사용해야 하는가?

3구조적 핵심 예시

Pod이 떠지지 않으면 kubectl describe pod <name> 으로 Events와 Status를 확인해 "ImagePullBackOff" (이미지 다운로드 실패), "CrashLoopBackOff" (애플리케이션 반복 크래시), "CreateContainerConfigError" (설정 오류) 같은 상태 코드와 원인 메시지를 봅니다. 그다음 kubectl logs <pod> 로 애플리케이션이 남긴 표준출력 로그를 확인해 시작 오류를 봅니다. 만약 Pod이 init 컨테이너 단계에서 막혀 있으면 kubectl logs <pod> -c <init-container> 로 init 로그를 별도로 봅니다. Pod이 시작되었지만 내부 동작이 의심스럽면 kubectl debug -it <pod> --image=busybox 로 같은 네임스페이스에 디버그 컨테이너를 임시로 띄워 네트워크, 환경 변수, 마운트 상태를 조사합니다.

  2. 애플리케이션 로그 확인kubectl logs로 컨테이너와 init 컨테이너의 표준출력 로그를 읽어 애플리케이션 시작 오류, 런타임 예외를 파악합니다.
  3. 임시 디버그 컨테이너 실행kubectl debug로 같은 Pod 내 또는 같은 노드에 임시 컨테이너를 띄워 네트워크 연결성, DNS 해석, 파일시스템, 환경 변수를 직접 진단합니다.

4단계별 동작 과정

  1. 요청 구성클라이언트가 리소스 경로(예: /api/v1/namespaces/default/pods)와 HTTP 메서드(get, list, watch, create, update, patch, delete 등을 HTTP 동사로 매핑)를 조합해 REST 요청을 만들어 kube-apiserver로 보낸다.

  3. 응답 반환결과를 JSON 형태로 클라이언트에 반환한다. watch 요청이면 연결을 닫지 않고 계속해서 변경 이벤트를 스트림 형태로 보낸다.

쿠버네티스 API는 계속 진화한다. 새로운 기능이 추가되거나 리소스 스키마가 바뀐다. 하지만 이미 배포 중인 수많은 클라이언트와 자동화 스크립트는 기존 API 형식에 의존하고 있다. 호환성을 끊으면 모든 사용자가 동시에 업그레이드해야 하는데, 이는 현실적으로 불가능하다.

2질문 제기

쿠버네티스 API를 진화시키면서도 기존 클라이언트들의 호환성을 보장할 수 있을까?

3구조적 핵심 예시

Deployment 리소스는 처음 alpha에서 출시되고, 안정화되면서 beta, 그리고 v1이 된다. 각 단계에서 새로운 필드가 추가될 수 있다. 이 과정에서 /apis/apps/v1/deployments와 /apis/apps/v1beta1/deployments 두 개의 API 경로가 동시에 존재한다. 클라이언트는 자신이 원하는 버전을 선택해서 요청할 수 있고, etcd에는 그 리소스의 데이터가 스토리지 버전(예: v1)으로 하나만 저장된다.

4단계별 동작 과정

  1. 버전 단계별 출시새로운 기능이나 변경이 필요하면 alpha 버전을 먼저 출시한다. 초기 사용자가 테스트한 후 피드백을 받아 개선하고, beta를 거쳐 최종적으로 v1으로 승격한다. 각 단계는 별개의 API 경로를 가진다.
  2. 폐기 정책 적용alpha는 일반적으로 몇 개 릴리스 후 폐기되고, beta는 더 오래 유지된다. 폐기 예정일과 마지막 지원 버전이 미리 공지되어 클라이언트가 마이그레이션할 시간을 준다.
  3. 스토리지 버전 관리여러 API 버전이 존재하더라도 etcd에는 하나의 스토리지 버전으로만 저장된다. kube-apiserver가 v1beta1 요청을 받으면 내부적으로 스토리지 버전으로 변환해 저장하고, 조회할 때는 요청한 버전으로 변환해 반환한다.

5본질 요약

API의 여러 버전을 동시 운영해서 클라이언트의 업그레이드 일정을 유연하게 하고, 구형 버전은 폐기 정책에 따라 단계적으로 제거하면서 kube-apiserver 진화 속도를 높이는 것

12API 심화와 확장12-03

CustomResourceDefinition과 오퍼레이터 패턴

CRD로 나만의 리소스 종류를 API에 추가하고, 그 리소스를 감시하며 실제 운영 작업을 자동 수행하는 컨트롤러를 붙인 것이 오퍼레이터 패턴이다.

1상대의 출발점 확인

쿠버네티스는 Pod, Deployment, StatefulSet 등 표준 리소스를 제공한다. 하지만 조직이나 팀마다 고유한 워크로드가 있다. 데이터베이스 클러스터, 메시지 큐, 캐시 시스템 같은 복잡한 애플리케이션을 쿠버네티스 리소스로 표현하고 관리하고 싶지만, 표준 리소스에는 없다. 커스텀 리소스를 API에 추가할 방법이 필요하다.

2질문 제기

쿠버네티스에 없는 새로운 리소스 종류를 직접 API에 추가해서 관리할 수 있을까?

3구조적 핵심 예시

CRD로 "DatabaseCluster"라는 새로운 리소스 타입을 정의한다. 그러면 /apis/example.com/v1/databaseclusters 경로가 생기고, kubectl get databaseclusters로 조회할 수 있다. 사용자가 DatabaseCluster YAML을 만들어 apply하면, etcd에 저장된다. 동시에 Operator 컨트롤러가 이 DatabaseCluster 리소스를 계속 감시하다가, 생성되면 실제로 데이터베이스 인스턴스를 프로비저닝하고, 업데이트되면 클러스터를 변경하고, 삭제되면 정리한다.

4단계별 동작 과정

  1. CRD 등록CustomResourceDefinition 매니페스트를 작성해서 새로운 리소스의 스키마(필드, 타입, 버전 등)를 정의하고 kube-apiserver에 등록한다.
  2. API 엔드포인트 생성kube-apiserver가 CRD를 받으면 자동으로 Get, List, Watch, Create, Update, Patch, Delete 엔드포인트를 생성하고, 해당 리소스의 데이터를 etcd에 저장한다.
  3. Operator 자동화Operator(커스텀 컨트롤러)가 CRD 리소스의 생성, 변경, 삭제 이벤트를 감시하다가 변경이 감지되면, 실제 운영 작업(예: 데이터베이스 초기화, 복제본 조정, 백업)을 자동으로 수행한다.

5본질 요약

CRD로 API에 새로운 리소스를 등록하고, Operator 컨트롤러로 그 리소스를 감시하며 선언형 명세에 맞춰 자동으로 운영하는 확장 가능한 인프라 관리 패턴

12API 심화와 확장12-04

애그리게이션 레이어·스케줄러 확장·kubectl 플러그인

별도 API 서버를 apiserver 경로에 이어 붙이거나(애그리게이션), 스케줄링 프레임워크 플러그인으로 배치 로직을 바꾸거나, kubectl-* 실행 파일로 CLI 명령을 늘리는 확장 지점들이다.

1상대의 출발점 확인

쿠버네티스의 기본 기능만으로는 모든 요구사항을 충족할 수 없다. 스케줄링 로직을 조직에 맞게 바꾸거나, API에 새로운 엔드포인트를 추가하거나, CLI 명령을 확장하고 싶을 수 있다. 핵심은 kube-apiserver나 kube-scheduler 같은 핵심 컴포넌트의 코드를 수정하지 않으면서도 이런 확장을 가능하게 해야 한다는 것이다.

2질문 제기

쿠버네티스의 핵심 컴포넌트를 건드리지 않으면서도 API, 스케줄링, CLI를 확장할 수 있을까?

3구조적 핵심 예시

APIServer Aggregation은 별도로 운영하는 API 서버(예: 메트릭 서버)를 kube-apiserver 앞에 붙인다. APIService 리소스로 경로를 등록하면, /apis/metrics.k8s.io 요청이 자동으로 그 서버로 프록시된다. Scheduling Framework Plugin은 스케줄러의 특정 단계(예: Filter, Score)에서 작동하는 플러그인을 등록해서 배치 로직을 바꾼다. kubectl 플러그인은 kubectl-{name} 형태의 실행 파일을 PATH에 두면 kubectl {name} 명령으로 자동으로 실행된다.

4단계별 동작 과정

  1. APIServer Aggregation별도 API 서버를 먼저 띄우고, APIService 리소스로 kube-apiserver에 등록한다. kube-apiserver가 해당 경로의 요청을 받으면 등록된 서버로 자동으로 프록시하고, 응답을 클라이언트에 반환한다.
  2. Scheduling Framework Plugin플러그인 인터페이스를 구현한 코드를 컴파일해서 KubeSchedulerConfiguration에 등록한다. kube-scheduler가 Pod을 배치할 때 각 단계(PreFilter, Filter, Score, Bind 등)에서 등록된 플러그인들을 호출해 로직을 적용한다.
  3. kubectl 플러그인kubectl-{command-name} 형태의 실행 파일을 PATH의 어디든 두면, kubectl {command-name} 입력 시 자동으로 찾아 실행한다. 플러그인은 kubectl의 설정과 컨텍스트를 상속받는다.

5본질 요약

쿠버네티스의 API 서버, 스케줄러, CLI를 플러그인과 애그리게이션 방식으로 설계해서, 핵심 코드 변경 없이 독립적인 확장 컴포넌트를 붙일 수 있게 하는 것
