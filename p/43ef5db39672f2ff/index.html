이어서 읽기

Microsoft가 만드는 서버용 운영체제 Windows Server 자체와, 그 위에서 동작하는 기본 역할·기능(디렉터리, 파일/스토리지, 네트워크, 가상화, 클러스터링, 원격 접근, 보안·운영)을 처음 배우는 사람이 순서대로 읽을 수 있게 재배열한 것. IIS·System Center·Azure Local 등 별도 문서 세트를 가진 제품은 경계만 표시하고 제외한다.

Windows Server 2025 (현재 LTSC stable). 일부 개념은 2016~2022에서 이어지는 공통 개념이며, 2025 신규 항목은 그 사실을 항목 안에서 밝힌다.

1Windows Server라는 플랫폼 이해하기무엇을 설치하고 어떤 판을 사야 하는지 정하지 못하면 이후 모든 단계가 시작되지 않는다.42설치하고 첫 구성 끝내기관리 도구를 붙이기 전에 서버가 켜져 있고 이름·주소·활성화가 끝나 있어야 한다.43서버를 다루는 도구 갖추기이후 모든 역할은 이 도구들 위에서 설치·구성되므로, 도구를 먼저 손에 쥐어야 한다.44네트워크와 이름 확인 기반 만들기Active Directory는 DNS 위에서만 동작한다. 도메인을 세우기 전에 주소와 이름 체계를 먼저 세운다.65Active Directory 도메인 서비스이후의 파일 권한, 클러스터, 원격 데스크톱, 인증서가 모두 도메인 아이디를 전제로 한다.76계정, 그룹, 정책으로 통제하기디렉터리가 서 있어야 계정과 정책이 의미를 갖고, 이 통제가 이후 권한·자격 증명 보호의 토대가 된다.57인증과 인증서계정이 있다는 것과 그것을 안전하게 증명하는 것은 다른 문제다. 이후 TLS·SMB 암호화·RDS 게이트웨이가 모두 여기에 기댄다.48스토리지와 파일 서비스디스크에서 볼륨, 볼륨에서 공유, 공유에서 프로토콜 순으로 쌓아야 파일 서버가 이해된다. 이후 클러스터·Hyper-V 스토리지의 전제이기도 하다.99Hyper-V 가상화스토리지와 네트워크를 이해한 뒤라야 가상 디스크·가상 스위치가 무엇을 얹은 것인지 보인다. 이후 클러스터·SDN·실드 VM의 전제다.710고가용성과 소프트웨어 정의 인프라단일 서버 기술을 모두 이해한 다음에야 '여러 대를 하나처럼 묶는' 계층이 성립한다.711원격 접근과 원격 데스크톱인증·인증서·가상화가 준비된 뒤에 사용자에게 데스크톱과 앱을 내보내는 계층을 올린다.512보안 강화, 업데이트, 운영모든 구성 요소를 안 다음에 그것들을 지키고 최신으로 유지하고 문제를 진단하는 층이 온다.7

1Windows Server라는 플랫폼 이해하기01-01

Windows Server가 하는 일과 클라이언트 Windows와의 차이

Windows Server는 여러 사용자·기기에 파일, 인증, 웹, 가상화 같은 서비스를 24시간 제공하도록 만들어진 서버용 운영체제로, 개인 작업용인 클라이언트 Windows와 역할·기능·확장성 면에서 다르다.

1문제 상황

클라이언트 Windows는 개인의 작업 환경을 위해 설계되었다. 한 사람이 로그인해서 문서를 만들고, 프로그램을 실행하고, 컴퓨터를 종료한다. 업데이트를 위해 재부팅하거나 보안 패치를 적용할 때도 그 사람의 작업을 멈춘다. 하지만 회사의 파일 서버, 인증 서버, 데이터베이스 서버는 상황이 다르다. 100명의 직원이 동시에 접속해서 파일을 읽고 쓰고, 퇴근 후에도 자동화 작업이 돌아가야 하고, 보안 업데이트가 있어도 서비스를 멈출 수 없다. 클라이언트 Windows는 이 환경을 지탱할 수 없다.

2핵심 질문

여러 사용자와 기기가 동시에 접속하여 파일, 인증, 웹, 가상화 같은 서비스를 안정적으로 이용할 수 있는 플랫폼이 필요하지 않은가?

3동작 예시

회사의 파일 서버는 Windows Server를 실행한다. 아침 9시에 직원 100명이 각각의 PC에서 동시에 로그인하고 공유 폴더에 접속해서 파일을 다운로드한다. 각 PC의 요청을 서버가 받아서 처리하고, 같은 파일에 동시에 접근하는 경우를 제어하고, 누가 어떤 권한을 가졌는지 확인해서 승인 또는 거부한다. 저녁 6시 퇴근 후에도 백업 작업이 자동으로 돌아가고, 새벽에 보안 업데이트를 설치해도 다시 켜지면 백그라운드에서 조용히 업데이트를 진행한다. 이 모든 것이 Windows Server의 역할이다.

4동작 과정

  1. 역할 기반 기능 제공클라이언트 Windows는 한 사람의 작업만 지원하지만, Windows Server는 파일 공유, 인증 관리, 웹 서버, 데이터베이스 호스팅 같은 특정 역할을 안정적으로 수행하도록 만들어졌다.
  2. 동시 다중 사용자 접속 처리클라이언트 Windows는 한 번에 한 사용자 로그인만 지원하지만, Windows Server는 네트워크를 통해 수백 명이 동시에 접속해도 각 요청을 공정하게 처리한다.
  3. 24시간 무중단 운영 설계클라이언트 Windows는 업데이트 후 재부팅하면 사용자만 영향받지만, Windows Server는 보안 업데이트, 롤링 업그레이드, 장애 자동 복구 같은 기능으로 서비스를 계속 유지한다.

5한 줄 요약

여러 사용자와 기기가 동시에 파일, 인증, 웹, 가상화 같은 서비스를 24시간 안정적으로 이용하도록 설계된 서버용 운영체제

Windows Server는 주로 Standard와 Datacenter 에디션으로 나뉘며, 코어 기반 라이선스에 CAL이 더해지고 에디션에 따라 실행할 수 있는 가상 머신(OSE) 수와 고급 기능이 달라진다.

1문제 상황

소프트웨어 라이선싱은 보통 한 가지 방식만 제공한다. 하지만 Windows Server를 쓰는 회사들의 규모는 매우 다르다. 10명이 일하는 스타트업은 물리 서버 1대에 파일 서버와 인증 서버를 돌리면 되지만, 1000명이 일하는 기업의 데이터센터는 한 대의 고가 물리 서버에서 20개의 가상 머신을 동시에 구동해야 한다. 같은 가격 정책으로는 소규모 회사는 낭비하고, 대규모 기업은 기능 부족으로 고생한다.

2핵심 질문

Windows Server를 설치해서 처음 부팅하면 아직 준비가 덜 되었다. 서버는 "ServerXXXX"라는 기본 이름으로 지어지고, IP 주소는 DHCP 서버에서 자동으로 할당받는다. DHCP 서버가 없으면 169.x.x.x 같은 주소를 임시로 받는다. 시간도 정확하지 않을 수 있다. 네트워크의 다른 서버나 애플리케이션은 이 서버를 찾거나 인증할 때 이름, IP, 시간 정보가 필요한데, 이런 기본값들은 프로덕션 환경에서 쓸 수 없다.

2핵심 질문

설치 직후 서버를 네트워크에서 안정적으로 찾을 수 있고 원격에서 관리 가능하도록 하려면 무엇을 먼저 설정해야 할까?

3동작 예시

새로 설치한 파일 서버가 DHCP에서 192.168.1.100이라는 IP를 받았는데, DHCP 임대 시간이 끝나면 다른 기기에 그 주소를 줄 수 있다. 그러면 클라이언트는 파일 서버를 찾지 못한다. 서버에 고정 IP 192.168.1.50을 설정하고 이름을 "FileServer01"로 지으면, 네트워크의 모든 기기가 항상 같은 주소에서 찾을 수 있다.

4동작 과정

4동작 과정

  2. NLB 부하 분산들어오는 클라이언트 요청을 여러 서버에 자동으로 분배하되, 같은 클라이언트의 요청은 같은 서버로 보내 세션을 유지한다.

1문제 상황

Active Directory가 여러 도메인 컨트롤러에 복제될 때, 기존에는 모든 정보가 단순히 복사되기만 했다. 하지만 이렇게 되면 스키마(개체의 속성 정의)를 바꿀 때 어디서 바꿀지, 어떻게 일관되게 유지할지 불명확해진다. 또한 포리스트 전체에서 특정 사람을 찾으려면 모든 도메인 컨트롤러에 일일이 물어봐야 하는 비효율이 발생한다.

2핵심 질문

3동작 예시

4동작 과정

  2. 글로벌 카탈로그로 포리스트 검색각 도메인 DC는 자신의 도메인 데이터만 가지지만, 글로벌 카탈로그 서버는 포리스트의 모든 도메인에서 사람·컴퓨터·그룹의 이름과 기본 정보만 복제해서 보유한다. 사용자가 다른 도메인의 사람을 검색하면 글로벌 카탈로그가 빠르게 결과를 준다.
  3. FSMO 역할로 단일 처리 보장스키마 마스터, 도메인 이름 마스터, RID 마스터, PDC 에뮬레이터, 인프라 마스터라는 5가지 역할이 각각 한 DC에만 있어서, 이 작업들(스키마 변경, 도메인 추가, RID 할당, 하위 호환성 유지, 그룹 멤버십 업데이트)은 충돌 없이 진행된다.

사이트, 복제 토폴로지, KCC

사이트는 네트워크의 물리적 위치 구분이고, KCC가 사이트와 링크 정보를 바탕으로 DC 간 복제 연결 토폴로지를 자동으로 만든다.

1문제 상황

기존에는 모든 DC가 같은 네트워크 속도라고 가정하고 복제를 했다. 하지만 실제로는 같은 건물의 DC들끼리는 빠른 네트워크로 연결되고, 다른 지사의 DC와는 느린 WAN 링크로 연결된다. 이렇게 되면 빠른 링크에서는 자주 복제해도 되지만 느린 링크에서는 복제량을 줄여야 한다. 그런데 이를 손으로 일일이 설정하면 매우 복잡하다.

2핵심 질문

네트워크의 물리적 위치에 따라 DC 간 복제 흐름을 자동으로 최적화할 수 있을까?

3동작 예시

회사에 서울 본사(DC 5개), 부산 지사(DC 2개), 대구 지사(DC 1개)가 있다고 하자. 본사의 DC들끼리는 고속 LAN으로 연결되어 있으므로 복제를 자주 해야 한다. 하지만 부산-서울 간은 느린 WAN 링크로 연결되어 있으므로 복제를 덜 자주 한다. 이를 수동으로 설정하려면 매우 번거롭지만, 각 위치를 "사이트"로 정의하고 링크의 대역폭을 설정하면 KCC(Knowledge Consistency Checker)가 자동으로 각 사이트 내에서는 빠른 복제, 사이트 간에는 느린 복제로 최적화한다.

4동작 과정

  1. 사이트 정의와 링크 설정관리자가 각 물리적 위치를 사이트(Site)로 정의하고, 사이트 링크(Site Link)를 만들어 각 링크의 비용(대역폭 부하)을 설정한다. 예를 들어 본사-부산 간 WAN 링크는 비용 100, 본사 내부 LAN은 비용 1로 설정한다.
  2. KCC가 복제 토폴로지 자동 생성KCC는 사이트와 링크 정보를 바탕으로 각 DC가 어디에서 복제를 받아야 하는지 자동으로 계산한다. 최소 비용 경로를 따라가므로, 서울 DC는 본사 내 다른 DC에서 먼저 받고 부산 DC는 서울을 통해 받는 방식으로 효율적으로 배치된다.
  3. 변경 복제와 주기적 복제변경이 생기면 사이트 내에서는 즉시 복제가 시작되고, 사이트 간에는 설정된 간격(예: 3시간)으로 복제된다. 이렇게 네트워크 부하를 조절하면서도 모든 DC가 최종적으로 같은 데이터를 가지게 된다.

신뢰 관계와 다중 포리스트

신뢰는 한 도메인·포리스트의 사용자가 다른 쪽 자원에 인증받을 수 있게 하는 연결이며, 여러 포리스트를 통합할 때 핵심이 된다.

1문제 상황

기존에는 각 AD 도메인이 완전히 독립적이어서, A 도메인의 사용자가 B 도메인의 자원에 접근하려면 B 도메인에서 별도의 계정을 만들어야 했다. 또한 포리스트가 다르면 (예: 회사가 합병되었을 때) 양쪽의 사용자가 서로의 자원에 접근할 길이 없었다.

2핵심 질문

다른 도메인이나 포리스트의 사용자가 자신의 계정으로 다른 쪽 자원에 인증받고 접근할 수 있을까?

3동작 예시

A회사와 B회사가 합병되었을 때, A 포리스트의 사용자가 B 포리스트의 파일 서버에 접근하려면 신뢰 관계(Trust)를 설정해야 한다. "B 포리스트는 A 포리스트의 사용자를 신뢰한다"는 신뢰 관계를 만들면, A의 사용자가 B의 자원에 접근할 때 A의 인증 정보를 그대로 사용할 수 있다. B 쪽은 A의 신뢰성을 믿고 추가 인증을 요구하지 않는다.

4동작 과정

  1. 신뢰 관계 설정두 도메인 또는 포리스트 간에 신뢰 관계를 설정한다. "A가 B를 신뢰" 또는 "B가 A를 신뢰"처럼 방향이 있다. 방향은 권한의 흐름을 정하는데, A가 B를 신뢰하면 A의 사용자가 B의 자원에 접근할 때 B는 A의 인증을 믿는다.
  2. 사용자 인증과 권한 확인A 포리스트의 사용자가 B 포리스트의 파일 서버에 접근하면, 서버는 A로부터의 신뢰 관계를 확인하고 사용자의 인증 정보를 수락한다. 별도의 비밀번호나 계정이 필요 없다.
  3. 다중 포리스트 통합 관리신뢰 관계를 체계적으로 설정하면, 여러 포리스트가 있어도 사용자는 자신의 계정으로 모든 포리스트의 자원에 접근할 수 있다. 합병이나 조직 개편 시에도 기존 계정 구조를 유지하면서 자원 접근을 통합할 수 있다.

기존에는 지사에 배치된 DC도 일반 DC와 같아서 모든 데이터를 저장했다. 하지만 지사는 보안이 약한 환경일 수 있어서, DC가 탈취되면 전체 AD 데이터베이스가 노출된다. 또한 실수로 중요한 개체(사용자, 그룹)를 삭제해도 복구 방법이 제한적이었다. 그리고 시간이 지나면서 AD 데이터베이스가 조각나거나 비효율적으로 저장될 수 있었다.

2핵심 질문

지사의 DC를 안전하게 배치하면서도 실수로 삭제된 데이터를 되살리고, 데이터베이스를 효율적으로 유지할 수 있을까?

3동작 예시

본사에 쓰기 가능한 일반 DC가 있고, 지사에 읽기 전용 DC(RODC)를 배치한다고 하자. RODC는 패스워드를 따로 저장하지 않으므로 탈취되어도 사용자 암호가 노출되지 않는다. 또한 누군가 AD에서 사용자를 실수로 삭제해도 AD 휴지통 기능이 활성화되어 있으면 특정 기간 내에 되살릴 수 있다. 게다가 ntdsutil 같은 도구로 AD 데이터베이스를 정기적으로 정비하면 조각난 저장 공간을 정리할 수 있다.

4동작 과정

  1. RODC 배치와 선택적 동기화지사에 읽기 전용 DC(RODC)를 배치하면, 패스워드를 저장하지 않으므로 물리적 탈취의 위험이 줄어든다. 필요한 데이터만 본사의 DC에서 선택적으로 동기화되므로 네트워크 부하도 적다.
  2. AD 휴지통으로 실수 복구AD 휴지통을 활성화하면, 삭제된 개체가 일정 기간(기본 180일) 동안 복구 가능한 상태로 유지된다. 실수로 사용자나 그룹을 삭제해도 관리자가 요청하면 해당 개체와 그 속성을 모두 복구할 수 있다.
  3. 데이터베이스 정비와 전체 복구시스템 상태 백업으로 AD 전체를 정기적으로 백업하고, ntdsutil로 AD 데이터베이스의 조각을 정리한다. 큰 장애가 나면 권한 있는 복원(Authoritative Restore)으로 백업 시점의 상태로 전체 AD를 복구할 수 있다.

사용자·그룹·컴퓨터 계정과 보안 식별자(SID)

Active Directory에서 사람·컴퓨터·그룹은 각각 계정 개체로 저장되고, 이름이 아니라 절대 바뀌지 않는 고유 번호인 SID로 권한이 판별된다.

1문제 상황

기존에는 사람이나 컴퓨터를 이름으로만 구별했다. 하지만 사용자의 이름을 바꾸거나 그룹의 이름을 변경하면, 그 사용자나 그룹이 가지던 권한이 어디로 가는지 불명확해진다. 또한 다른 도메인의 같은 이름 사용자와 구별할 수 없다.

2핵심 질문

이름이 바뀌어도 권한이 계속 유지되고, 전 세계에서 유일하게 식별할 수 있는 방법이 있을까?

3동작 예시

"김철수"라는 사용자 계정이 있다고 하자. 이 사용자의 이름을 "김철수-ENG"로 바꾼다면, 기존 이름 기반 권한 시스템에서는 권한을 잃을 수 있다. 하지만 각 계정이 만들어질 때 부여받는 SID(보안 식별자, 예: S-1-5-21-2623811516-3723811111-3421881699-1001)라는 고유 번호로 권한을 관리하면, 이름을 바꿔도 권한은 유지된다. 또한 SID는 전 세계에서 유일하므로 도메인이 다른 다른 "김철수"와도 구별된다.

4동작 과정

  1. 계정 생성과 SID 할당사용자, 그룹, 컴퓨터 계정을 AD에 만들 때 각각 절대 바뀌지 않는 SID가 할당된다. SID는 도메인의 도메인 SID와 RID(상대 식별자)를 조합하여 만들어진다.
  2. 권한을 SID로 관리파일이나 자원에 대한 권한을 설정할 때, 사용자/그룹의 이름이 아니라 SID를 저장한다. 예를 들어 "이 폴더의 읽기 권한 = SID-XXX"라고 저장되므로, 나중에 사용자 이름을 바꿔도 권한은 유지된다.
  3. SID 기반 권한 확인사용자가 자원에 접근할 때, 시스템은 사용자의 SID와 그 사용자가 속한 그룹의 SID들을 검사하여 권한이 있는지 판단한다.

5한 줄 요약

그룹 정책: 적용 순서, 링크, 필터링

그룹 정책(GPO)은 사이트→도메인→OU 순으로 겹쳐 적용되며, 링크·상속·보안 필터링으로 누구에게 적용될지 조절한다.

1문제 상황

기존에는 각 컴퓨터를 따로따로 설정했다. 예를 들어 100개 컴퓨터에 같은 방화벽 규칙을 적용하려면 모두 일일이 로그인해서 설정해야 했다. 또한 특정 그룹에만 다른 규칙을 적용하려면 누가 어느 컴퓨터에 속하는지 추적하기 어려웠다.

2핵심 질문

일괄적으로 여러 컴퓨터에 같은 설정을 적용하면서도, 특정 그룹이나 조직 단위에만 다른 규칙을 적용할 수 있을까?

3동작 예시

회사의 마케팅팀은 별도의 브라우저 보안 정책이 필요하고, 개발팀은 개발 도구 접근 권한이 필요하다고 하자. 그룹 정책(GPO)을 만들어서 마케팅팀의 OU(조직 단위)에 링크하면 마케팅팀 컴퓨터에만 마케팅 정책이 적용된다. 동시에 개발팀의 OU에 다른 정책을 링크하면 개발팀에는 개발 정책이 적용된다. 또한 정책 내에서 보안 필터링을 설정하면, "이 정책은 개발팀 그룹의 멤버들에게만 적용"처럼 세밀하게 제어할 수 있다.

4동작 과정

  1. 정책 생성과 사이트·도메인·OU에 링크관리자가 그룹 정책(GPO)을 만들고, 사이트(물리적 위치) 또는 도메인, OU(조직 단위)에 링크한다. 예를 들어 "보안 정책"을 마케팅 OU에 링크하면, 그 OU 아래의 모든 컴퓨터에 정책이 적용된다.
  2. 겹침 적용과 상속정책은 사이트 → 도메인 → OU 순으로 겹쳐서 적용된다. 상위 레벨의 정책이 먼저 적용되고, 하위 레벨의 정책이 덮어씌운다(상속). 따라서 도메인 레벨에서 기본 보안 정책을 정하고, OU 레벨에서 세부 정책을 오버라이드할 수 있다.
  3. 보안 필터링으로 세밀한 제어같은 OU에 속한 컴퓨터라도 특정 보안 그룹에만 정책을 적용하려면 필터링을 설정한다. 예를 들어 "이 정책은 '개발팀' 그룹의 멤버에게만 적용"이라고 설정하면, 같은 OU의 다른 그룹 사용자는 이 정책을 받지 않는다.

권한 위임과 최소 권한 관리, JEA

필요한 작업에 필요한 만큼의 권한만 넘겨주는 원칙이며, JEA는 관리자 권한 없이 정해진 PowerShell 명령만 실행하게 해준다.

1문제 상황

기존에는 관리자 계정이 모든 권한을 가지고 있었다. 누군가 특정 작업(예: 사용자 생성)만 해야 할 때도 관리자 계정 전체를 주거나, 또는 그 사람에게 관리자 권한을 넘겨야 했다. 이렇게 되면 권한이 과해지고, 실수나 보안 위협 시 피해가 커진다.

2핵심 질문

관리자 권한 없이도 특정 작업만 실행하게 하면서, 그 권한을 감시하고 제한할 수 있을까?

3동작 예시

헬프데스크 직원이 사용자 암호 초기화와 잠금 해제만 해야 한다고 하자. 기존에는 이를 위해 관리자 권한을 줘야 했지만, JEA(Just Enough Administration)를 설정하면 "이 직원은 Reset-ADAccountPassword 명령만 실행 가능"이라고 정할 수 있다. 그러면 그 직원은 관리자 권한 없이도 암호 초기화만 할 수 있고, 다른 관리 작업은 실행할 수 없다.

4동작 과정

  1. 최소 권한 원칙으로 권한 설계각 역할이 필요한 최소한의 권한만 정한다. 예를 들어 헬프데스크는 암호 초기화 및 해제, 개발팀은 테스트 환경의 VM 시작/종료만 필요하다고 파악한다.
  2. JEA 세션 구성PowerShell의 JEA를 설정하여, 특정 사용자가 특정 명령만 실행하는 제한된 PowerShell 세션을 만든다. 예를 들어 헬프데스크 세션에서는 Reset-ADAccountPassword, Unlock-ADAccount 두 명령만 허용한다.
  3. 감시와 기록JEA 세션에서 실행된 모든 명령을 자동으로 기록하므로, 누가 언제 어떤 명령을 실행했는지 추적할 수 있다. 이를 통해 실수나 악의적 행동을 사후에 감지하고 책임을 추적할 수 있다.

1문제 상황

기존에는 Windows 서비스가 실행될 때 사용할 계정의 암호를 IT 관리자가 직접 설정하고 정기적으로 수동으로 바꾸는 방식을 썼습니다. 이렇게 하면 암호를 사람이 알고 있기 때문에 보안 위험이 생기고, 여러 서버에서 같은 서비스를 실행할 때 암호를 일일이 동기화해야 하며, 암호 변경을 놓치면 서비스가 중단되는 문제가 발생합니다.

2핵심 질문

서비스가 쓰는 계정의 암호를 사람이 관리하지 않고도 안전하게 자동으로 관리할 수 있을까요?

3동작 예시

gMSA(그룹 관리 서비스 계정)는 Active Directory가 백그라운드에서 30일마다 자동으로 복잡한 암호를 만들어서 그 계정에 적용하고, 도메인에 가입한 서버들이 필요할 때마다 AD에서 현재 암호를 자동으로 받아가서 서비스를 실행하는 방식입니다. 관리자는 암호를 알 필요가 없고, 서비스는 항상 최신 암호로 실행됩니다.

4동작 과정

  1. AD에서 gMSA 계정 생성관리자가 AD 관리 도구에서 gMSA 계정을 만들 때, Active Directory가 그 계정에 복잡한 암호를 자동으로 생성하고 저장합니다.
  2. 도메인 서버에서 서비스 설정관리자가 Windows 서버의 서비스 설정에서 실행 계정을 이 gMSA로 지정하면, 그 서버는 AD에 접속해서 현재 유효한 암호를 자동으로 가져갑니다.
  3. 자동 암호 갱신30일마다 Active Directory가 암호를 새로 만들고, 도메인에 가입한 모든 서버의 서비스들이 다음 실행 때 자동으로 새 암호를 받아서 사용합니다.

2핵심 질문

3동작 예시

Windows LAPS는 Active Directory가 각 컴퓨터마다 서로 다른 복잡한 로컬 관리자 암호를 자동으로 생성해서 AD에 암호화된 상태로 저장하고, 권한이 있는 관리자만 AD 관리 도구나 PowerShell에서 필요할 때마다 그 암호를 조회할 수 있게 하는 방식입니다.

Windows 인증: Kerberos와 NTLM이 동작하는 방식

사용자가 누구인지 증명하는 절차로, 도메인에서는 티켓을 주고받는 Kerberos를 기본으로 쓰고 옛 방식인 NTLM은 챌린지-응답으로 대체 동작한다.

1문제 상황

도메인에 가입한 컴퓨터들에서 사용자가 로그인하거나 다른 서버의 자원에 접근할 때, 그 사용자가 정말 본인인지 확인하는 절차가 필요합니다. 옛 방식인 NTLM은 비밀번호를 해시해서 매번 서버에 직접 제시하기 때문에 암호가 노출되거나 스니핑(eavesdropping)될 위험이 있습니다.

2핵심 질문

도메인 환경에서 사용자 신원을 안전하게 증명하되, 암호를 직접 네트워크에 드러내지 않을 수 있을까요?

3동작 예시

Kerberos는 도메인의 Key Distribution Center(KDC, 키 배포 센터)라는 신뢰 가능한 제3자가 사용자와 서버 사이의 암호화된 티켓(ticket)을 중개하는 방식입니다. 사용자가 로그인할 때 KDC에서 임시 증명서(TGT, Ticket Granting Ticket)를 받고, 서버에 접근할 때는 그 TGT를 제시해서 해당 서버용 티켓을 받은 뒤, 그 티켓을 서버에 제시합니다. 암호는 초기 로그인 때만 사용되고 이후는 암호화된 티켓만 오갑니다.

4동작 과정

  1. 초기 인증 (AS-REQ/AS-REP)사용자가 로그인할 때 Kerberos Authentication Server(AS, 인증 서버)에 비밀번호 해시를 제시하면, AS가 검증 후 그 사용자가 일정 기간 동안 다른 서비스에 접근할 수 있는 TGT 티켓을 발급합니다.
  2. 서비스 접근 (TGS-REQ/TGS-REP)사용자가 특정 서버의 자원에 접근하려 할 때, Kerberos Ticket Granting Server(TGS, 티켓 발급 서버)에 TGT를 제시해서 그 서버용 Service Ticket을 받습니다.
  3. 서버 접근 검증사용자가 서버에 Service Ticket을 제시하면, 서버는 티켓이 유효한지(위조되지 않았는지, 만료되지 않았는지) 확인 후 접근을 허가합니다.

1문제 상황

2핵심 질문

3동작 예시

AD CS(Active Directory Certificate Services)는 Windows Server가 인증서 발급 기관이 되어 조직 내부의 인증서를 발급·관리하는 역할입니다. 루트 CA(최고 인증기관)를 설치한 뒤, 그 아래에 보조 CA를 계층적으로 구성하고, 인증서 템플릿(template)을 통해 사용자·컴퓨터·서비스 각각에 필요한 인증서 규격을 미리 정의해두면, 요청이 들어올 때 자동으로 발급하거나 관리자가 승인해서 발급합니다.

4동작 과정

  1. CA 계층 구성관리자가 루트 CA 서버(최고 신뢰 기관)를 설치하고, 그 루트 CA의 인증서를 이용해 하위 CA 서버들을 인증해서 CA 계층을 만듭니다. 루트 CA는 보안을 위해 대부분 오프라인 상태로 유지합니다.
  2. 인증서 템플릿 설정관리자가 AD CS 관리 도구에서 인증서 템플릿을 만들 때, 사용자용·컴퓨터용·웹 서버용 등 목적에 맞게 유효 기간, 용도(사용 목적), 암호화 알고리즘 등을 미리 정의합니다.
  3. 자동 등록 또는 승인 발급사용자나 컴퓨터가 템플릿에 따라 인증서를 요청하면, AD CS는 템플릿 설정에 맞게 자동으로 발급하거나, 관리자가 수동으로 승인한 후 발급합니다.

2핵심 질문

3동작 예시

Schannel(Secure Channel)은 Windows의 보안 서비스 공급자(SSP, Security Support Provider)로, TLS/SSL 통신을 처리하는 암호 모듈입니다. 관리자가 Windows 레지스트리(registry)에서 TLS 버전(예: TLS 1.2 이상만 활성화), 사용 가능한 암호 모음(예: 약한 암호 제외), 인증서 검증 정책 등을 설정하면, 그 컴퓨터의 모든 애플리케이션이 Schannel을 통해 이 설정을 따릅니다.

4동작 과정

  1. 레지스트리를 통한 TLS 버전 제어관리자가 Windows 레지스트리의 Schannel 항목에서 지원할 TLS 버전을 명시적으로 활성화하거나 비활성화하고, 약한 옛 버전(예: SSL 3.0, TLS 1.0)을 비활성화합니다.
  2. 암호 모음(Cipher Suite) 설정Schannel에서 사용할 수 있는 암호화 알고리즘, 키 교환 방식, 해시 알고리즘 등을 그룹 정책(GPO)이나 레지스트리를 통해 순서대로 우선순위를 정합니다.
  3. 애플리케이션의 자동 적용웹 서버, 데이터베이스 클라이언트, 원격 데스크톱 등 TLS를 사용하는 모든 애플리케이션은 Schannel의 설정을 자동으로 따르므로, 관리자는 한 곳에서 조직 전체의 암호화 정책을 제어합니다.

1문제 상황

조직의 직원이 인트라넷의 Active Directory에 로그인해서 내부 앱은 잘 쓸 수 있지만, 외부 클라우드 서비스나 파트너 조직의 웹 애플리케이션에 접근하려면 별도의 계정을 만들고 따로 로그인해야 합니다. 이렇게 되면 사용자는 여러 개의 암호를 관리해야 하고, 각 조직은 외부 사용자의 계정을 따로 유지관리해야 하므로 복잡합니다.

2핵심 질문

조직의 내부 계정 하나로 외부의 여러 웹 애플리케이션에 한 번의 로그인으로 접근할 수 있을까요?

3동작 예시

AD FS(Active Directory Federation Services)는 조직의 내부 Active Directory를 외부 애플리케이션과 신뢰 관계(federation trust)로 연결해서, 사용자가 내부 AD에 로그인한 후 외부 앱에 접근할 때 AD가 사용자의 신원 정보를 클레임(claim, 사용자 속성과 권한을 담은 디지털 증명)으로 만들어서 외부 앱에 전달합니다. 외부 앱은 AD FS를 신뢰하므로 그 클레임을 받아 사용자를 자동으로 인정합니다.

4동작 과정

  1. 조직 간 신뢰 관계 수립AD FS와 외부 애플리케이션(또는 그 애플리케이션을 운영하는 다른 조직의 AD FS) 사이에 신뢰 관계(federation trust)를 설정하고, 어떤 클레임을 주고받을지 미리 정의합니다.
  2. AD FS의 클레임 발급사용자가 내부 AD에 로그인한 후 외부 앱에 접근하려 하면, AD FS는 Active Directory에서 그 사용자의 정보(부서, 그룹 소속, 권한 등)를 읽어서 클레임으로 변환해 외부 앱으로 전달합니다.
  3. 웹 애플리케이션 프록시를 통한 인터넷 노출AD FS를 직접 인터넷에 노출하면 보안 위험이 크므로, 웹 애플리케이션 프록시(WAP, Web Application Proxy)라는 역방향 프록시(reverse proxy)를 인터넷 경계에 배치해서 외부 사용자의 요청을 받아 내부 AD FS에 중계하고, AD FS의 응답을 외부 사용자에게 돌려줍니다.

3동작 예시

4동작 과정

  2. 파티션 생성 및 포맷초기화된 디스크의 미할당 영역에서 파티션을 생성해서 크기를 정하고, 그 파티션을 NTFS(또는 다른 파일 시스템)로 포맷해서 파일을 저장할 수 있는 파일 시스템 구조를 만듭니다.
  3. 드라이브 문자 할당Windows가 포맷된 파티션을 볼륨으로 인식하고, 관리자가 필요에 따라 드라이브 문자(D:, E: 등)를 할당해서 사용자와 애플리케이션이 파일을 읽고 쓸 수 있게 합니다.

파일 시스템 선택: NTFS와 ReFS

NTFS는 호환성과 기능이 풍부한 기본 파일 시스템이고, ReFS는 대용량·데이터 무결성과 복원력에 최적화된 파일 시스템이다.

1문제 상황

2핵심 질문

3동작 예시

4동작 과정

  2. 주기적 무결성 검사백그라운드에서 자동으로 저장된 파일들을 읽고 체크섬과 비교해 손상 여부를 감지합니다.
  3. 오류 감지 시 자동 복구손상이 발견되면 ReFS는 미러링이나 패리티 데이터로 원본을 복원합니다.

4동작 과정

  3. 자동 동기화 및 폴백한 서버에 변경이 생기면 DFS 복제가 다른 서버들에 자동으로 반영하고, 일부 서버가 다운되어도 나머지 서버에서 계속 최신 데이터를 제공합니다.

Hyper-V는 하드웨어 바로 위에서 도는 Type-1 하이퍼바이저로, 부모 파티션(호스트)과 자식 파티션(VM)을 나눠 물리 서버 한 대에서 여러 OS를 동시에 돌리게 해 주는 Windows Server 역할이다.

1문제 상황

기존에는 하나의 물리 서버에 하나의 OS만 설치되고 실행됩니다. 이 방식은 서버의 CPU와 메모리를 낭비합니다. 예를 들어 서버의 전체 성능의 30%만 쓰는 애플리케이션이 있으면 나머지 70%는 활용되지 않습니다. 또한 그 OS에 문제가 생기면 그 서버에서 돌던 모든 워크로드가 영향을 받고, 각각 다른 OS가 필요한 여러 애플리케이션을 동시에 돌릴 수 없습니다.

2핵심 질문

3동작 예시

Hyper-V는 Windows Server의 하드웨어 바로 위에서 도는 Type-1 하이퍼바이저입니다. 부모 파티션(Parent Partition)이라 불리는 호스트 OS가 실제 하드웨어를 관리하고, 그 위에 여러 개의 자식 파티션(Child Partition)이라 불리는 가상 머신이 각각의 OS를 독립적으로 실행합니다.

4동작 과정

  1. 하이퍼바이저 부팅서버가 켜질 때 Hyper-V 하이퍼바이저가 먼저 로드되어 하드웨어를 직접 제어하고, 그 다음 부모 파티션(호스트 OS)이 하이퍼바이저 위에서 실행
  2. 자식 파티션 격리각 가상 머신이 독립적인 메모리 공간, CPU 시간, 디스크 공간을 할당받아서 한 VM의 장애나 크래시가 다른 VM이나 호스트에 영향을 주지 않음
  3. 자원 공할호스트가 물리 하드웨어를 중앙에서 관리하고 각 VM이 필요한 만큼 자원 할당

2핵심 질문

3동작 예시

4동작 과정

  2. 저장소 QoS 설정각 VM이나 워크로드마다 최소/최대 IOPS와 처리량(Throughput) 한도를 설정한다.
  3. 자동 대역폭 제어실시간으로 IOPS 사용량을 측정해서, 설정된 한도를 초과하는 요청을 지연시켜 다른 워크로드에 영향을 주지 않게 한다.

2핵심 질문

3동작 예시

4동작 과정

2핵심 질문

3동작 예시

4동작 과정

  2. RD 게이트웨이 배포인터넷 경계에 RD 게이트웨이를 배치하고, 모든 원격 연결이 게이트웨이를 거치도록 설정한다.
  3. 암호화 연결과 중계사용자가 게이트웨이에 HTTPS로 연결해서 인증하면, 게이트웨이는 사용자 자격증명과 CAL을 확인한 후 내부 RDS 서버로 연결을 중계한다.

1문제 상황

외부(카페, 집, 출장지)에서 일하는 직원이 회사 네트워크 자원(공유 폴더, 프린터, 사내 시스템)에 접속하려면, 직원의 장치가 사내 네트워크에 논리적으로 연결되어야 한다. 기존에는 VPN 클라이언트를 매번 수동으로 켰는데, 사용자가 실수로 끄거나 연결을 재설정해야 할 때마다 불편했다. 또한 지점 사무실에서 본사 자원을 쓸 때 같은 파일을 여러 번 다운로드해서 대역폭이 낭비되었다.

2핵심 질문

3동작 예시

4동작 과정

  1. Always On VPN 정책 배포관리자가 그룹 정책으로 VPN 프로필을 직원 장치에 배포하고, 자동 연결 규칙을 설정한다.
  2. NPS 인증과 규정 검증VPN 연결 요청이 오면 NPS 서버가 사용자 계정, 장치의 보안 상태(방화벽 활성화, 안티바이러스 설치 등)를 검증한다.
  3. BranchCache로 대역폭 절약지점 사무실에 캐시 서버를 두고, 각 지점의 사용자가 다운로드한 파일을 지역적으로 캐시해서, 같은 파일 재다운로드 시 본사 대신 캐시에서 제공한다.

1문제 상황

서버를 운영하다 보면 악성코드나 공격자가 OS 커널을 조작해서 깊숙한 수준에서 보안을 우회하려고 한다. 기존에는 방화벽과 접근 제어만으로 외부 공격을 막았고, 내부 보안 설정도 수동으로 일일이 했다. 하지만 펌웨어 수준의 공격이나 커널 권한 상승 공격에는 OS 보안만으로는 막을 수 없었다. 또한 보안 설정이 흩어져 있어서, 관리자마다 다르게 설정할 수 있었다.

2핵심 질문

펌웨어부터 OS까지 신뢰할 수 있는 부팅 과정을 보장하고, 깊숙한 커널 수준의 공격을 원천적으로 차단할 수 있을까?

3동작 예시

Secured-core server는 먼저 서버의 UEFI 펌웨어가 진정한 마이크로소프트 코드만 실행하도록 서명을 검증하고, TPM(Trusted Platform Module, 신뢰할 수 있는 하드웨어 칩) 칩이 부팅 과정의 각 단계를 측정해서 조작을 감지한다. OS 부팅 후에는 VBS(Virtualization-Based Security, 가상화 기술을 이용한 격리 보안)라는 기능이 커널 권한 수준에서 보호되는 공간을 만들어, 커널 드라이버도 접근할 수 없게 한다.

4동작 과정

  1. UEFI 보안 부팅과 TPM 측정서버 전원을 킬 때 UEFI 펌웨어가 부팅 코드의 서명을 검증하고, TPM이 각 부팅 단계의 해시값(데이터를 요약한 값)을 기록해서 이전과 같은지 확인한다.
  2. VBS 격리 환경 구성Windows 커널이 부팅 후 VBS를 활성화해서 격리된 메모리 공간을 만들고, Credential Guard(자격증명 보호) 같은 보안 기능이 그 안에서 실행되어 드라이버나 커널 공격으로부터 독립된다.
  3. 보안 기준선 정책 적용관리자가 마이크로소프트 권장 보안 기준선(어느 기능을 켤지, 어느 포트를 닫을지 등)을 그룹 정책으로 일괄 배포해서 모든 서버에 통일된 보안 설정을 적용한다.

3동작 예시

4동작 과정

  1. 격리 영역 생성VBS 기술로 OS와 분리된 메모리 공간을 커널 수준에서 만듭니다.
  2. 자격 증명 저장로그인할 때 암호와 Kerberos 티켓을 이 격리 영역에만 저장하고, 일반 OS 메모리에는 저장하지 않습니다.
  3. 필요시 검증서버가 네트워크 리소스에 접근해야 할 때, 일반 OS는 격리 영역에 요청을 보내고 검증 결과만 받습니다.
