Windows Server 기초 — 에디션·설치·인증01-01

Windows Server의 정의와 시작

Windows Server는 파일·인쇄, 디렉터리, 가상화 같은 서버 역할을 제공하도록 마이크로소프트가 만든 서버 운영체제다.

#1문제 상황

일반 데스크톱 운영체제는 한 사람이 화면 앞에서 앱을 쓰는 상황을 기준으로 만들어졌다. 그래서 여러 사용자가 동시에 접속해 파일을 공유하거나, 공용 저장소·인쇄 대기열·디렉터리 같은 공통 기능을 한 대의 컴퓨터가 계속 떠받치는 상황에는 맞지 않는다.

이런 공통 기능을 개인용 컴퓨터마다 흩어 두면 계정과 권한을 따로 관리해야 하고, 한 대가 꺼지면 그 위에 얹은 서비스가 같이 멈춘다. 조직 규모가 커질수록 이 방식은 보안과 확장 모두에서 감당이 안 된다.

#2핵심 질문

여러 사용자와 애플리케이션이 동시에 의존하는 공통 서버 기능을 한 대의 컴퓨터에서 안정적이고 안전하게 계속 제공하려면 무엇이 필요한가?

#3동작 예시

한 대의 물리 서버에 Windows Server를 설치하고 파일 서버 역할을 켜 두면, 사내 여러 직원의 PC가 같은 폴더를 네트워크로 접속해 동시에 읽고 쓴다. 서버는 각 사용자의 계정과 권한을 확인한 뒤 파일 접근을 허용하고, 웹 애플리케이션과 가상 머신 같은 다른 역할도 같은 장비 위에서 함께 돌릴 수 있다.

#4동작 과정

  1. 역할 설치관리자가 서버 관리자나 Windows Admin Center에서 파일·인쇄, 디렉터리, 가상화 같은 서버 역할(서버가 제공하는 기능 묶음)을 골라 켠다.
  2. 자원과 권한 연결서버가 하드웨어 자원 위에 그 역할들을 올리고, 접속한 사용자와 애플리케이션의 인증·권한을 확인해 요청을 처리한다.
  3. 서비스 제공과 확장클라이언트는 네트워크로 이 서버의 기능을 쓰고, 필요하면 온프레미스·하이브리드·클라우드로 같은 운영 기반을 넓혀 간다.

에디션과 릴리스

Windows Server는 기능 범위와 가상화 권한에 따라 Essentials·Standard·Datacenter·Azure Edition 등 여러 에디션과 정기 릴리스로 나뉜다.

#1문제 상황

Windows Server를 모든 조직에 똑같은 한 가지 형태로만 내놓으면, 서버 한 대짜리 소규모 사업장과 수백 대를 가상화하는 대기업이 같은 조건을 강요받는다. 반대로 기능을 다 열어 두면 필요 없는 조직까지 가상화 권한과 고급 기능의 비용을 치러야 한다.

그래서 기능 범위와 가상화 권한, 제공되는 릴리스 시점을 기준으로 제품을 나눠야 했고, 어느 에디션을 어디에 쓸지 판단하는 일 자체가 새 문제가 된다.

#2핵심 질문

기능 범위와 가상화 권한이 다른 에디션·릴리스 중에서 우리 환경에 맞는 것을 어떻게 고르는가?

#3동작 예시

서버 한 대에 가상 머신을 여러 개 올리려는 조직은 Datacenter 에디션을 골라 가상화 권한을 넓게 가져가고, 물리 서버 몇 대에 역할을 하나씩만 올리는 조직은 Standard 에디션으로 필요한 역할만 켠다. 가상 머신을 거의 쓰지 않는 소규모 환경은 더 가벼운 에디션을 검토하고, Azure에서 관리하는 환경은 Azure Edition의 기능을 함께 본다.

#4동작 과정

  1. 요구 확인필요한 역할과 기능, 올릴 가상 머신 수, 라이선스 방식과 관리 환경을 먼저 정리한다.
  2. 에디션 비교Standard·Datacenter·Datacenter: Azure Edition 등의 역할·기능 표(에디션이 어떤 기능을 제공하는지 정리한 목록)를 대조해 가상화 권한과 기능 차이를 확인한다.
  3. 릴리스·서비스 채널 확정대상 버전과 서비스 채널(업데이트를 어떤 주기와 방식으로 받을지 정한 통로), 하드웨어 요구사항, 잠금과 한도까지 확인해 최종 에디션을 정한다.

기능 범위와 가상화 권한, 릴리스·서비스 조건에 따라 제품을 나눠 조직 규모에 맞는 서버 기반을 고르게 하는 것

설치·업그레이드·핫패치

설치 미디어로 새로 설치하거나 기존 버전을 제자리에서 올리는 업그레이드, 재부팅 없이 패치하는 핫패치로 서버를 최신 상태로 유지하는 방법이다.

#1문제 상황

서버 운영체제는 한 번 설치하면 끝이 아니라, 보안 패치를 계속 받고 새 버전으로 옮겨 가야 지원과 최신 기능을 유지할 수 있다. 그런데 예전 방식은 새 버전으로 가려면 서버를 통째로 다시 설치하거나 별도 장비로 이전해야 했고, 그동안 서비스가 멈췄다.

패치도 마찬가지였다. 보통의 업데이트는 적용 뒤 재부팅이 필요해, 항상 켜져 있어야 하는 서버에서는 짧지 않은 중단이 반복됐다.

#2핵심 질문

서비스 중단을 최소화하면서 서버를 새 버전으로 올리고 최신 보안 상태로 유지하려면 어떤 방법을 써야 하는가?

#3동작 예시

재부팅을 감수하기 어려운 서버에는 핫패치를 켜 두어, 매달의 일부 패치를 재부팅 없이 적용하고 나머지 달에만 재부팅하도록 운영한다. 반대로 새 하드웨어로 넘어가면서 구성을 정리하려는 서버는 설치 미디어로 새로 설치한 뒤 역할과 설정을 옮긴다.

#4동작 과정

  1. 방법 선택다운타임 허용 범위와 하드웨어 요구사항을 기준으로 제자리 업그레이드, 새로 설치, 마이그레이션, 클러스터 롤링 업그레이드, 에디션 변환 중 하나를 고른다.
  2. 설치 옵션 결정Server Core(그래픽 데스크톱 없이 명령줄과 원격 관리로 운영하는 최소 설치)와 데스크톱 환경 설치 중 하나를 정하고, 지원되는 업그레이드 경로와 제한을 확인한다.
  3. 적용과 유지설치 미디어나 업그레이드로 새 버전을 올린 뒤, 핫패치나 확장 보안 업데이트로 재부팅 부담을 줄이며 최신 상태를 유지한다.

#5한 줄 요약

서비스 중단과 재부팅 부담을 줄이는 방법으로 서버를 새 버전으로 올리고 최신 보안 상태로 유지하는 것

정품 인증과 KMS

정품 인증은 윈도우 라이선스를 활성화하는 절차이고, KMS는 사내 서버가 여러 클라이언트의 인증을 대신 처리해 주는 방식이다.

#1문제 상황

윈도우 제품은 사용 권한을 확인하기 위해 정품 인증을 거쳐야 한다. 서버와 클라이언트가 수백 대인 조직에서 각 컴퓨터가 인터넷의 인증 서버에 직접 붙어 하나씩 인증받는 방식은, 외부 연결이 막힌 사내망에서는 아예 동작하지 않고 관리도 번거롭다.

그래서 인증을 사내에서 대신 처리할 서버가 필요해졌고, 그 서버를 어떻게 두고 클라이언트를 어떻게 붙일지가 운영 문제로 남는다.

#2핵심 질문

인터넷에 직접 나가지 못하는 사내 컴퓨터들의 정품 인증을 한 곳에서 대신 처리하려면 어떻게 해야 하는가?

#3동작 예시

사내망 안에 KMS 호스트를 하나 세워 두면, 같은 네트워크의 서버와 클라이언트가 그 호스트에 접속해 인증을 받는다. KMS 호스트는 전용 장비일 필요가 없어 다른 서비스와 함께 돌릴 수 있고, 서버 운영체제에서 도는 호스트는 서버와 클라이언트 양쪽 컴퓨터를 모두 인증할 수 있다.

#4동작 과정

  1. 호스트 준비사내망 안에 KMS 호스트(KMS 클라이언트의 인증 요청을 대신 처리하는 서버)를 세우고, 호스트의 역할과 인증 대상 범위를 정한다.
  2. 클라이언트 연결각 컴퓨터가 KMS 클라이언트로 동작하며 사내망의 KMS 호스트에 접속해 인증을 요청하고, 자동 가상 머신 활성화 같은 방식으로 가상 머신도 함께 처리한다.
  3. 운영과 문제 해결호스트를 교체하거나 옮길 때 인증이 끊기지 않도록 관리하고, 인증 실패 시 Slmgr.vbs 같은 도구와 DNS 설정을 확인해 원인을 찾는다.

#5한 줄 요약

사내 서버가 여러 컴퓨터의 정품 인증을 대신 처리해 외부 연결 없이 라이선스를 활성화하는 것

Server Core 설치 옵션

Server Core는 GUI 없이 명령줄과 원격 관리로만 운영하는 최소 설치 옵션으로, 공격 표면과 유지보수 부담을 줄인다.

#1문제 상황

서버에 그래픽 데스크톱과 그래픽 관리 도구를 모두 설치하면, 화면으로 다루기는 편하지만 그만큼 실행되는 구성 요소와 서비스가 늘어난다. 늘어난 구성 요소는 공격자가 노릴 수 있는 표면이 되고, 패치해야 할 대상도 그만큼 많아진다.

항상 켜 두고 원격으로만 쓰는 서버라면, 화면 앞에 앉아 조작할 일이 거의 없는데도 이 부담을 계속 안고 가게 된다.

#2핵심 질문

화면 조작이 거의 필요 없는 서버에서 공격 표면과 유지보수 부담을 줄이려면 어떤 설치 옵션을 골라야 하는가?

#3동작 예시

설치 마법사에서 Server Core를 고르면 표준 그래픽 인터페이스가 설치되지 않아, 관리자가 PowerShell이나 서버 구성 도구(SConfig)로 명령줄에서 설정하고 이후에는 원격 관리 도구로 서버를 다룬다. 그래픽 요소와 그래픽 관리 도구가 꼭 필요한 경우에만 데스크톱 환경 설치를 고른다.

#4동작 과정

  1. 설치 옵션 선택설치 마법사에서 Server Core와 데스크톱 환경 설치 중 하나를 고르고, Server Core는 그래픽 인터페이스 없이 설치된다.
  2. 기본 설정SConfig나 PowerShell로 네트워크, 컴퓨터 이름, 도메인 가입 같은 초기 작업을 처리한다.
  3. 원격 운영과 패치원격 관리 도구로 서버를 운영하고, 메모리 덤프 파일 설정과 패치까지 이 환경에 맞게 관리한다.

#5한 줄 요약

관리 개요와 Azure 연계

Windows Server 관리는 Server Manager·Windows Admin Center 같은 도구로 로컬·원격 서버를 관리하고 Azure 연계 서비스로 그 범위를 확장하는 것이다.

#1문제 상황

서버가 한 대일 때는 화면 앞에서 직접 설정해도 문제가 없다. 하지만 서버가 여러 대로 늘고 원격지·클라우드까지 섞이면, 각 서버에 따로 접속해 같은 작업을 반복하는 방식은 시간이 많이 들고 설정이 서로 어긋나기 쉽다.

게다가 재해 복구나 상태 점검처럼 서버 밖에서 봐야 하는 일은 로컬 도구만으로는 감당이 안 된다.

#2핵심 질문

여러 대의 로컬·원격 서버를 한곳에서 일관되게 관리하고 그 범위를 클라우드까지 넓히려면 무엇을 써야 하는가?

#3동작 예시

관리자가 Windows Admin Center로 여러 서버를 한 화면에서 관리하고, 같은 서버를 Azure Arc에 연결해 두면 Azure 쪽 도구로도 상태를 보고 정책을 적용할 수 있다. 로컬에서는 MMC 같은 기존 관리 도구를 그대로 쓰면서, 재해 복구가 필요한 서버는 Azure Site Recovery로 보호한다.

#4동작 과정

  1. 관리 도구 선택Windows Admin Center, 로컬 관리 도구, Azure Arc, System Center 같은 주요 도구 중 환경에 맞는 것을 고른다.
  2. 로컬·원격 통합 관리MMC 같은 로컬 도구와 원격 관리 도구로 서버의 애플리케이션·네트워크·웹 서비스를 하나의 인프라로 묶어 관리한다.

Server Manager

Windows Server에 기본 내장된 GUI 기반 서버 관리 콘솔로, 로컬·원격 서버의 역할과 기능 추가·제거, 이벤트·성능 확인, 서버 그룹 관리를 한 화면에서 수행한다.

#1문제 상황

서버마다 역할과 기능을 설치하고 상태를 확인하려면 관리자가 각 서버에 직접 로그인하거나 원격 데스크톱(RDP) 연결을 열어야 했다. 서버 수가 늘어날수록 화면을 하나씩 오가며 같은 작업을 반복해야 했고, 물리적 접근이나 원격 접속 설정이 없으면 아예 관리할 수 없었다.

#2핵심 질문

여러 대의 Windows 서버를 물리 접근이나 RDP 연결 없이 한 화면에서 관리할 수는 없을까?

#3동작 예시

관리자 데스크톱에서 Server Manager를 열고 서버 그룹에 원격 서버 세 대를 추가하면, 한 화면의 타일에 각 서버의 역할·이벤트·성능 데이터가 함께 표시된다. 서버를 하나씩 열지 않고도 목록 전체의 상태를 보고, 필요한 서버의 역할 추가 작업을 그 자리에서 실행할 수 있다.

#4동작 과정

  1. 로컬·원격 서버 등록Server Manager가 로컬 서버와 원격 서버를 관리 대상 목록에 등록한다. 이렇게 해서 관리자는 접속을 오가지 않고 한 콘솔에서 여러 서버를 바라본다.
  2. 역할·기능 적용역할과 기능 추가·제거, Features on Demand 구성을 선택한 서버에 원격으로 적용한다. 그래서 서버에 직접 들어가지 않아도 구성이 반영된다.

RSAT와 OpenSSH

RSAT는 원격 Windows Server의 역할·기능을 관리할 수 있게 해 주는 관리 도구 모음이고, OpenSSH는 Windows Server에 포함된 오픈소스 SSH 클라이언트·서버로 원격 셸 접속과 키 기반 인증을 제공한다.

#1문제 상황

원격 Windows Server의 역할과 기능을 관리하려면 그 서버에 직접 접속해 콘솔을 다루는 방식이 기본이었다. 관리자 PC와 서버의 도구가 서로 맞지 않으면 작업 자체가 성립하지 않았고, 원격 셸 접속은 별도 도구를 따로 설치해야 했다. 이 때문에 관리 환경을 서버마다 개별적으로 준비해야 하는 부담이 있었다.

#2핵심 질문

관리자 PC에서 원격 서버의 역할·기능을 관리하고 셸로 접속하려면 무엇을 설치해야 할까?

#3동작 예시

Windows 클라이언트에 RSAT를 설치하면 Server Manager 같은 관리 도구가 그 PC에 생기고, 이 도구로 원격 서버의 역할과 기능을 직접 다룰 수 있다. 같은 PC에서 OpenSSH 클라이언트를 켜면 명령줄로 서버에 접속해 셸 작업을 할 수 있어, 그래픽 도구와 터미널을 한 관리자 PC에서 함께 쓴다.

#4동작 과정

  1. RSAT 설치관리자 PC나 서버에 Remote Server Administration Tools를 설치한다. 설치 방식은 플랫폼에 따라 달라지므로 해당 환경에 맞는 방법을 고른다. 그래서 클라이언트에서 원격 역할·기능 관리가 가능해진다.
  2. OpenSSH 활성화와 설정Windows에 포함된 OpenSSH 클라이언트·서버를 켜고 서버 구성 옵션을 정한다. 그래서 원격 셸 접속 통로가 열린다.
  3. 키 기반 인증과 정책 적용비밀번호 대신 키 기반 인증을 설정하고 그룹 정책으로 OpenSSH를 관리한다. 그래서 접속 보안과 일관된 설정을 유지한다.

Windows Admin Center 개요와 설치

Windows Admin Center는 브라우저 기반의 경량 서버 관리 도구로, 서버·클러스터·Hyper-V 등을 설치형 웹 게이트웨이를 통해 원격 관리하며 다양한 설치 형태를 선택할 수 있다.

#1문제 상황

서버를 관리하려면 서버마다 관리 도구를 설치하고 관리자 PC에도 같은 도구를 맞춰 두어야 했다. 도구가 설치된 PC에서만 관리할 수 있어 여러 사용자가 같은 서버를 함께 관리하기 어려웠고, 관리 지점이 늘어날수록 접속 환경을 각각 준비해야 했다.

#2핵심 질문

서버에 도구를 깔지 않고 웹 브라우저로 여러 사용자가 원격 서버를 관리할 수는 없을까?

#3동작 예시

Windows PC나 원격 서버에 Windows Admin Center 게이트웨이를 설치하면, 사용자는 브라우저로 그 게이트웨이에 접속해 서버·클러스터·Hyper-V를 관리한다. 설치 형태를 고르고 게이트웨이를 한 번 세워 두면 여러 사용자가 같은 관리 화면을 공유할 수 있다.

#4동작 과정

  1. 설치 형태 결정지원 운영 체제와 배포 목적을 보고 설치 옵션 중 알맞은 형태를 고른다. 그래서 환경에 맞는 게이트웨이 구성이 정해진다.
  2. 설치 프로그램 실행Windows Admin Center 설치 프로그램을 받아 게이트웨이를 설치할 PC나 서버에서 실행한다. 그래서 관리 웹 게이트웨이가 만들어진다.
  3. 접속과 다중 사용 준비브라우저로 게이트웨이에 접속하고 사용자 접근 옵션과 네트워크 요구 사항을 맞춘다. 그래서 여러 사용자가 원격 서버를 함께 관리한다.

Windows Admin Center 구성과 사용

Windows Admin Center 게이트웨이 설치 후 설정·사용자 접근 권한·확장·연결 대상을 구성하고, 서버와 가상 머신·클러스터를 실제로 관리하는 방법이다.

#1문제 상황

게이트웨이를 설치하기만 하면 관리 대상과 권한이 자동으로 정리되지 않는다. 누가 어떤 자원에 접근할 수 있는지, 어떤 확장 도구를 쓸 수 있는지, 인증서는 언제 갱신할지가 정해져 있지 않으면 여러 사용자가 쓰는 관리 환경이 어긋난다.

#2핵심 질문

게이트웨이를 설치한 뒤 접근 권한과 관리 대상을 어떻게 정하고 실제 서버를 관리할까?

#3동작 예시

게이트웨이 설정에서 사용자 수준 항목을 바꾸면 그 사용자에게만 적용되고, 게이트웨이 수준 항목을 바꾸면 게이트웨이의 모든 사용자에게 적용된다. 관리자는 여기서 확장을 설치하고 공유 연결을 등록한 뒤, 그 연결을 통해 서버와 가상 머신·클러스터를 관리 화면에서 직접 다룬다.

#4동작 과정

  1. 설정 구분사용자 수준 설정과 게이트웨이 수준 설정을 나눠 구성한다. 그래서 개인 프로필과 전체 공통 설정이 서로 섞이지 않는다.
  2. 권한과 연결 등록사용자 접근 제어와 권한을 정하고 확장·공유 연결을 추가한다. 그래서 관리 대상 자원이 목록에 올라온다.
  3. 관리 실행과 유지서버·가상 머신·클러스터를 관리하면서 PowerShell 자동화, 웹소켓 검증, 인증서 갱신을 처리한다. 그래서 관리 작업과 보안 유지가 같은 화면에서 이어진다.

#2핵심 질문

#3동작 예시

Windows Admin Center 게이트웨이를 Azure에 등록하면, 관리 화면 안에서 Azure Backup으로 서버를 보호하거나 Azure Monitor로 상태를 수집하고 Azure Arc로 서버를 연결할 수 있다. 게이트웨이를 한 번 등록하면 이후 버전으로 업데이트해도 설정이 유지된다.

#4동작 과정

  1. 게이트웨이 등록Windows Admin Center 게이트웨이를 Azure에 등록한다. 이 등록은 게이트웨이마다 한 번만 하면 되고 업데이트 후에도 보존된다. 그래서 Azure 서비스와 통신할 자격이 생긴다.
  2. 하이브리드 서비스 연결Azure Backup·Azure File Sync·Azure Monitor·Azure Network Adapter 같은 서비스를 관리 대상에 붙인다. 그래서 온프레미스 서버가 Azure 기능의 보호와 관측을 받는다.

Windows Admin Center 확장 개발

Windows Admin Center의 도구·솔루션·게이트웨이 플러그인 확장을 SDK와 개발 환경으로 만들고 패키징·게시하는 방법이다.

#1문제 상황

Windows Admin Center가 기본 제공하는 도구만으로는 특정 장비나 업무에 필요한 관리 기능을 모두 담을 수 없다. 새 요구가 생길 때마다 게이트웨이 자체를 고치는 방식은 유지보수가 어렵고, 기본 도구와 사용자 정의 기능이 한 화면에서 섞이지도 않았다.

#2핵심 질문

Windows Admin Center의 도구와 기능을 개발자가 직접 확장해 붙일 수는 없을까?

#3동작 예시

개발자가 SDK로 도구 확장을 만들어 게이트웨이에 올리면, 관리 화면의 연결 대상에 그 확장 도구가 새 항목으로 나타난다. 도구 확장 안에 모듈이나 iFrame을 넣어 자체 UI를 붙이고, PowerShell을 호출해 서버에 원하는 작업을 실행하도록 구성할 수 있다.

#4동작 과정

  1. 확장 유형 선택도구 확장, 솔루션 확장, 게이트웨이 플러그인 중 만들 것을 고른다. 그래서 목적에 맞는 확장 구조가 정해진다.

WSUS·System Insights·인벤토리 로깅

WSUS는 중앙에서 업데이트를 배포·승인하는 서비스, System Insights는 서버 리소스 사용을 예측 분석하는 기능, SIL·UAL은 소프트웨어와 사용자 접근 정보를 수집하는 인벤토리 로깅 기능이다.

#1문제 상황

각 서버가 마이크로소프트 업데이트를 스스로 내려받아 설치하면, 관리자는 어떤 서버에 어떤 업데이트가 언제 적용됐는지 한눈에 알 수 없다. 서버 대수가 늘수록 인터넷 회선과 대역폭도 서버마다 반복 사용되고, 문제가 생긴 업데이트를 골라 되돌리기도 어렵다. 게다가 서버에 어떤 소프트웨어가 깔렸고 누가 접근했는지, 앞으로 자원이 얼마나 더 필요할지도 서버마다 따로 확인해야 했다. 중앙에서 업데이트를 통제하고, 자원 사용을 예측하며, 소프트웨어·사용자 접근 정보를 모으는 기능이 각각 필요해졌다.

#2핵심 질문

여러 서버의 업데이트·자원 사용·설치 정보를 한 지점에서 통제하고 수집하려면 어떻게 해야 하는가?

#3동작 예시

관리자가 WSUS 서버 한 대를 세워 업데이트 원본을 내려받게 한다. 이 서버가 마이크로소프트 업데이트 카탈로그와 동기화해 목록을 확보하면, 관리자는 각 업데이트를 "승인"할지 결정하고 클라이언트 서버들은 인터넷이 아니라 이 WSUS 서버에서만 업데이트를 받는다. 같은 시점에 System Insights가 각 서버의 CPU·스토리지 사용 추세를 수집해 예측 값을 만들고, SIL이 설치된 소프트웨어 목록을, UAL이 어떤 사용자가 어떤 역할에 접근했는지 기록을 각각 모은다.

#4동작 과정

  1. 중앙 서버 구성과 동기화WSUS 서버 역할을 설치하고 업데이트를 내려받을 원본과 동기화 일정을 정한다. 이때 승인할 업데이트와 클라이언트가 속할 컴퓨터 그룹 기준이 함께 정해진다.
  2. 승인과 배포, 그리고 클라이언트 보고관리자가 업데이트를 승인하면 클라이언트 서버는 그룹 정책(자동 업데이트 동작을 지정하는 규칙)에 따라 WSUS 서버에서 업데이트를 받고, 설치 결과를 다시 서버에 보고한다. 그래서 서버별 설치 상태가 한 화면에 모인다.
  3. 정보 수집과 정리System Insights가 자원 사용을 예측 분석하고, SIL(소프트웨어 인벤토리 로깅)과 UAL(사용자 접근 로깅)이 소프트웨어·접근 기록을 수집한다. 오래된 업데이트와 불필요한 데이터는 Server Cleanup Wizard로 정리한다.

서버 하드웨어·전력 튜닝

서버의 CPU 전원 관리(PPM)와 전력 정책, 하드웨어 구성을 워크로드 특성에 맞게 조정해 성능과 전력 소비의 균형을 맞추는 튜닝.

#1문제 상황

서버를 기본 설정 그대로 두면 하드웨어 성능을 충분히 쓰지 못하거나, 반대로 전력을 불필요하게 소비한다. 예를 들어 CPU가 유휴 상태에서 주파수를 낮추는 전원 관리가 켜져 있으면 지연에 민감한 작업에서 응답이 흔들리고, 반대로 항상 최고 성능으로 고정하면 전기 요금이 커진다. 또 프로세서 코어 수·주파수·메모리 구성 같은 하드웨어 선택이 워크로드 특성과 맞지 않으면 병목이 생긴다. 그래서 하드웨어 구성과 전력 정책을 워크로드에 맞춰 조정하는 작업이 필요하다.

#2핵심 질문

서버의 하드웨어 구성과 전력 정책을 워크로드에 맞게 조정해 성능과 전력 소비의 균형을 어떻게 맞출 것인가?

#3동작 예시

지연에 민감한 서버에서는 프로세서 전원 관리(PPM)의 최소 프로세서 상태를 높게 잡아 CPU가 낮은 주파수로 내려가지 않게 하고, 전력 절감이 우선인 서버에서는 반대로 유휴 시 주파수를 낮추도록 둔다. 하드웨어는 64비트 프로세서를 고르고, 더 많은 연산 자원이 필요하면 코어 수를 늘릴지 코어 주파수를 높일지 워크로드에 맞춰 정한다.

#4동작 과정

  1. 워크로드 특성 파악서버가 지연에 민감한지, 처리량이 중요한지, 전력 예산이 얼마인지 먼저 정한다. 이 기준이 뒤의 모든 조정 값을 결정한다.
  2. 하드웨어 구성 선택64비트 프로세서와 코어 수·주파수, 메모리 구성을 워크로드에 맞춘다. 병목이 될 만한 부분을 미리 줄여 두는 단계다.
  3. 전력 정책 조정PPM(프로세서 전원 관리)과 전력 정책을 목표에 맞게 설정한다. 지연 우선이면 유휴 시 주파수 하강을 막고, 절감 우선이면 하강을 허용해 성능과 소비의 균형을 맞춘다.

역할별 튜닝 — AD·파일·웹·RDS

도메인 컨트롤러(AD DS), 파일 서버(SMB/NFS), 웹 서버(IIS), 원격 데스크톱 서비스(RDS)처럼 서버가 맡은 역할별로 구성 요소와 카운터를 조정해 처리량을 높이는 방법.

#1문제 상황

서버는 기본 설정에서 다양한 용도로 쓸 수 있게 만들어져 있어, 특정 역할에만 몰아 쓰면 그 역할에 필요한 자원이 부족해진다. 도메인 컨트롤러는 LDAP 질의와 인증을 처리하는데 메모리와 사이트 구성이 부족하면 로그온이 느려지고, 파일 서버는 SMB/NFS 처리량이 병목이 되며, 웹 서버는 요청 처리 방식에 따라 대기 시간이 커진다. 원격 데스크톱 서비스는 다수 사용자의 세션을 동시에 다뤄 메모리·CPU 사용 패턴이 일반 서버와 다르다. 역할마다 중요하게 봐야 할 구성 요소와 성능 카운터가 다른데, 기본값 하나로는 각 역할의 처리량을 끌어올리기 어렵다.

#2핵심 질문

서버가 맡은 역할마다 어떤 구성 요소와 카운터를 조정해야 처리량을 높일 수 있는가?

#3동작 예시

도메인 컨트롤러라면 사이트 정의와 하드웨어·메모리 사용, LDAP 관련 설정을 점검하고, 파일 서버라면 SMB 파일 서버의 처리량 관련 설정을 확인한다. 웹 서버라면 IIS 처리 방식과 HTTP 버전별 동작을 조정하고, 원격 데스크톱 서비스라면 세션 수에 맞춰 자원 배분을 손본다. 같은 장비라도 어떤 역할을 얹었는지에 따라 조정할 지점이 달라진다.

#4동작 과정

  1. 역할과 목표 정하기이 서버가 도메인 컨트롤러인지 파일·웹·RDS 서버인지, 그리고 최소 지연인지 최대 처리량인지 목표를 정한다. 목표가 조정 방향을 결정한다.
  2. 역할별 구성 요소 조정AD DS는 사이트 정의·메모리 사용·LDAP을, 파일 서버는 SMB/NFS 처리량을, IIS는 요청 처리와 HTTP 동작을, RDS는 세션 자원 배분을 각각 손본다. 역할에 맞는 부분만 건드려 효과를 집중시킨다.
  3. 카운터로 확인역할별 성능 카운터(자원 사용을 수치로 보여 주는 지표)를 보고 조정 결과가 실제로 처리량이나 지연을 개선했는지 확인한다. 개선이 없으면 조정 값을 다시 맞춘다.

→ 03-02 참조

#1문제 상황

Hyper-V 가상화 서버는 여러 가상 머신이 프로세서·메모리·입출력 장치를 나눠 쓰기 때문에, 물리 서버 한 대를 쓰는 경우와 병목이 생기는 위치가 다르다. 가상 머신 수가 늘면 프로세서·메모리·스토리지 I/O·네트워크 I/O 중 어디에서 먼저 한계가 오는지 파악하기 어렵다. 또 캐시·메모리 관리, 네트워크 서브시스템, 소프트웨어 정의 네트워킹(SDN) 같은 운영체제 계층 설정이 기본값이면 가상 환경의 자원을 충분히 쓰지 못한다. 어느 계층이 실제 병목인지 찾아 그 부분을 조정하는 작업이 필요하다.

#2핵심 질문

가상화 계층과 운영체제 서브시스템 중 어디를 조정해야 가상 환경의 병목을 줄일 수 있는가?

#3동작 예시

가상 머신들이 몰린 호스트에서 스토리지 I/O 대기가 커지면 저장소 경로 설정을 점검하고, 네트워크 지연이 크면 네트워크 어댑터 설정과 인터페이스 순서를 확인한다. 캐시·메모리 관리가 원인이면 메모리 관련 설정을, SDN을 쓰는 환경이면 게이트웨이 성능 관련 설정을 조정한다. 물리 CPU·메모리가 충분한데도 느리면 원인은 가상화 계층이나 서브시스템 쪽일 가능성이 크다.

#4동작 과정

  1. 병목 계층 찾기프로세서·메모리·스토리지 I/O·네트워크 I/O 지표를 보고 어느 계층이 먼저 한계에 닿았는지 확인한다. 가상화 환경에서는 이 구분이 조정의 출발점이다.
  2. 해당 서브시스템 조정캐시·메모리 관리, 네트워크 어댑터와 인터페이스 순서, SDN 게이트웨이 등 병목으로 확인된 계층의 설정을 조정한다. 한 계층씩 바꿔 원인을 좁혀 나간다.
  3. 다시 측정해 확인같은 지표를 다시 재서 병목이 줄었는지 확인하고, 다음 계층의 조정 필요 여부를 판단한다. 결과가 개선될 때까지 이 과정을 반복한다.

ID — Active Directory Domain Services04-01

ID 개요와 솔루션 가이드

Windows Server의 ID·액세스 관리가 무엇인지, 그리고 동적 액세스 제어·파일 액세스 감사 같은 시나리오별 솔루션 가이드를 소개하는 개요.

#1문제 상황

ID와 접근 권한을 다루는 방식이 여러 갈래로 흩어져 있으면, 어떤 사용자가 어떤 데이터에 접근할 수 있는지 일관되게 통제하기 어렵다. 온프레미스에 있는 서비스와 클라우드에 있는 서비스가 섞이면 인증·권한 판단 기준이 서로 달라져 관리 부담이 커진다. 파일 접근 감사, 접근 거부 시 안내, 데이터 분류·보존 같은 요구는 각각 따로 구현하면 중복이 생기고 정책이 어긋난다. 그래서 ID·액세스 관리가 무엇인지 정리하고, 시나리오별 솔루션을 참고해 일관된 방식으로 구현할 필요가 있다.

#2핵심 질문

여러 환경에 흩어진 ID와 접근 권한을 일관된 하나의 방식으로 통제하려면 무엇을 기준으로 삼아야 하는가?

#3동작 예시

동적 액세스 제어 시나리오에서는 사용자·장치·데이터 분류 속성을 조건으로 삼아 접근 여부를 결정하는 중앙 액세스 정책을 세운다. 파일 접근 감사 시나리오에서는 같은 정책으로 접근 기록을 남기고, 접근이 거부될 때 이유를 알려주는 안내를 붙인다. 문서 분류·암호화·보존 시나리오에서는 분류 결과를 정책 판단에 그대로 연결해, 권한 통제와 데이터 관리가 같은 기준 위에서 돌아가게 한다.

#4동작 과정

  1. ID·액세스 관리 범위 정리온프레미스와 클라우드, 하이브리드 배포에서 인증과 권한을 어디까지 하나로 다룰지 정한다. 이 범위가 이후 정책 설계의 틀이 된다.
  2. 시나리오별 솔루션 선택중앙 액세스 정책, 파일 접근 감사, 접근 거부 안내, 분류 기반 암호화·보존 같은 시나리오 중 필요한 것을 고른다. 각 시나리오는 배포 단계가 정해져 있어 그 절차를 따른다.
  3. 정책·감사·분류 연결사용자·장치·데이터 속성을 조건으로 정책을 적용하고, 감사와 분류 결과를 같은 기준에 연결한다. 그래서 통제·기록·데이터 관리가 한 흐름으로 이어진다.

#5한 줄 요약

ID와 접근 권한을 사용자·장치·데이터 속성 기준으로 하나로 통제하고, 그 위에 감사·분류·보존 시나리오를 연결하는 것

ID — Active Directory Domain Services04-02

AD DS 관리 센터와 가상화

Active Directory Administrative Center로 AD DS를 관리하는 방법과, 가상 도메인 컨트롤러(AD DS 가상화)의 개념·배포·복원을 설명한다.

#1문제 상황

도메인 컨트롤러를 가상 머신으로 옮기면 물리 서버와 다른 문제가 생긴다. 가상 머신을 복사하거나 스냅샷으로 되돌리면 같은 도메인 데이터를 가진 컨트롤러가 여러 개 생길 수 있고, 시간이 어긋나면 복제(컨트롤러끼리 데이터를 맞추는 동작)가 꼬인다. 관리 면에서도 예전 도구는 휴지통 복원·세밀한 암호 정책·PowerShell 이력 확인 같은 작업을 하려면 여러 화면을 오가야 했다. 가상 컨트롤러를 안전하게 배포·복원하는 방법과, 한 화면에서 관리하는 도구가 함께 필요해졌다.

#2핵심 질문

가상 머신으로 돌아가는 도메인 컨트롤러를 복제·복원 사고 없이 안전하게 운영하려면 무엇을 지켜야 하는가?

#3동작 예시

Active Directory 관리 센터 한 화면에서 휴지통을 켜 삭제된 개체를 되살리고, 세밀한 암호 정책을 특정 사용자 집합에 적용하며, PowerShell 이력 뷰어로 실행한 명령을 확인한다. 가상화 쪽에서는 가상 도메인 컨트롤러 기술 참고에 따라 생성 식별자를 유지하고 시간 동기화를 바깥 원본과 맞춰, 스냅샷 복원 후에도 복제가 어긋나지 않게 배포·복원 절차를 따른다.

#4동작 과정

  1. 한 화면 관리 도구로 기본 작업Active Directory 관리 센터에서 휴지통 복원, 세밀한 암호 정책, PowerShell 이력 확인 같은 작업을 처리한다. 여러 도구를 오갈 필요가 줄어든다.
  2. 가상 컨트롤러 배포가상 도메인 컨트롤러 아키텍처와 배포·구성 지침에 따라 생성 식별자와 시간 동기화를 지키며 컨트롤러를 세운다. 복제가 꼬이지 않도록 하는 핵심 조건을 맞추는 단계다.
  3. 복제본·복원 관리복제된 컨트롤러나 복원한 컨트롤러를 다룰 때 지침에 따라 복제 상태를 점검하고, 문제가 있으면 문서화된 복원 절차로 되돌린다. 그래서 가상 환경에서도 도메인 데이터가 일관되게 유지된다.

#5한 줄 요약

가상 도메인 컨트롤러를 복제·시간 동기화 규칙에 따라 안전하게 배포·복원하면서 한 화면의 관리 도구로 AD DS를 다루는 것

AD DS 설계와 계획

AD DS를 도입하기 전에 포리스트·도메인·조직 구성 단위·사이트 토폴로지·DNS 구조와 요구사항을 설계하고 계획하는 방법.

→ 03-02 참조

#1문제 상황

AD DS를 도입할 때 설계 없이 서버부터 세우면, 나중에 도메인을 합치거나 나누는 일이 생기고 그때마다 계정과 정책을 다시 옮겨야 한다. 포리스트·도메인·조직 구성 단위를 나중에 바꾸는 작업은 서비스 중단과 대규모 마이그레이션을 부르며, 처음에 정한 이름과 DNS 구조가 이미 여러 시스템에 박혀 있으면 되돌리기 어렵다. 또 "도메인을 몇 개 만들 것인가", "DNS는 누가 관리할 것인가" 같은 결정이 각 부서에서 따로 내려지면, 권한 경계와 복제 범위가 뒤엉켜 운영 부담만 커진다. 그래서 실제 설치 전에 요구사항을 모으고 논리 구조와 사이트 토폴로지를 먼저 확정하는 단계가 필요하다.

#2핵심 질문

포리스트·도메인·사이트·DNS 구조를 어떤 기준으로 나누고 묶어야 이후 변경 없이 조직을 담아낼 수 있는가?

#3동작 예시

본사와 지사가 있고 각 지사가 자체 IT 인력을 둔 경우를 생각하자. 설계자는 먼저 "자율 운영이 필요한가, 완전히 격리해야 하는가"(Autonomy vs. Isolation)를 따진다. 자율 운영이면 하나의 포리스트 안에 도메인을 나누고, 법적으로 데이터를 분리해야 하면 별도 포리스트를 선택한다. 이 결정에 따라 사이트 링크와 DNS 영역 배치도 함께 정해진다.

#4동작 과정

  1. 요구사항 수집인원, 애플리케이션, 보안 규제, 기존 DNS·네트워크 구조를 조사하고 AD DS 최대 한도(maximum limits)에 걸리는 항목이 없는지 확인한다. 이 단계에서 나온 제약이 이후 모든 설계 결정의 근거가 된다.
  2. 논리 구조 설계수집한 요구사항을 포리스트·도메인·조직 구성 단위(OU, 사용자와 자원을 담는 폴더 같은 관리 경계)로 옮기고, 권한 위임 지점과 도메인 이름, 포리스트 루트 도메인을 정한다.
  3. 사이트·DNS 설계네트워크 대역과 연결 속도를 기준으로 사이트와 사이트 링크를 배치하고, AD DS 통합 DNS 영역(도메인 컨트롤러가 복제로 함께 나르는 DNS 데이터) 구조와 도메인 컨트롤러 위치를 확정한다.

#5한 줄 요약

설치 전에 요구사항을 포리스트·도메인·사이트·DNS 결정으로 미리 확정해, 이후 구조 변경 없이 조직을 담아내는 것

ID — Active Directory Domain Services04-04

AD DS 배포

새 포리스트·도메인·RODC 설치부터 도메인 컨트롤러 강등과 메타데이터 정리까지 AD DS를 실제로 배포하는 절차.

#1문제 상황

설계를 마쳤더라도 실제 설치는 단순히 역할 하나를 켜는 일이 아니다. 새 포리스트를 만들면 스키마가 확장되고, 기존 도메인에 도메인 컨트롤러를 추가하면 복제본이 생기며, 서버를 내릴 때는 그 서버가 맡던 역할과 데이터를 다른 서버로 넘겨야 한다. 이 과정을 순서 없이 진행하면 복제 불일치와 남은 메타데이터가 쌓인다. 또 서버 관리자로 역할을 설치하는 방식과 무인 설치용 응답 파일, 강등 절차가 각각 다르고, 기존 환경에 새 도메인 컨트롤러를 넣을 때는 adprep이 스키마와 도메인·포리스트 정보를 갱신한다. 어떤 순서로 무엇을 갱신하는지 알지 못하면 배포 도중 되돌리기 어려운 상태에 빠진다.

#2핵심 질문

새 포리스트 설치부터 도메인 컨트롤러 강등·정리까지, 복제와 스키마 갱신을 깨뜨리지 않고 어떤 순서로 배포해야 하는가?

#3동작 예시

기존 도메인에 도메인 컨트롤러를 하나 추가하는 상황을 보자. 관리자는 새 서버에 AD DS 역할을 설치하고, 설치 마법사에서 "기존 도메인에 도메인 컨트롤러 추가"를 선택한 뒤 대상 도메인 이름과 자격 증명, 사이트, DNS·글로벌 카탈로그 옵션을 지정한다. 설치가 끝나면 새 서버는 기존 도메인 컨트롤러로부터 데이터를 복제받아 같은 디렉터리를 제공하기 시작한다.

#4동작 과정

  1. 역할 설치와 사전 준비대상 서버에 AD DS 역할을 추가하고, 기존 환경이면 adprep의 스키마·도메인·포리스트 갱신(새 버전이 요구하는 속성과 구조를 미리 반영하는 작업)이 완료됐는지 확인한다.
  2. 승격 또는 새 포리스트 생성새 포리스트·도메인이면 루트 도메인 이름과 DNS 구성을 정해 처음 도메인 컨트롤러를 만들고, 기존 도메인·자식 도메인·RODC(읽기 전용 도메인 컨트롤러)면 대상과 옵션을 지정해 승격한다. 승격 시 지정한 사이트와 DNS 배치가 곧 복제 경로가 된다.
  3. 강등과 메타데이터 정리서버를 내릴 때는 먼저 FSMO 역할과 글로벌 카탈로그 등 맡은 기능을 넘기고 강등한 뒤, 남은 메타데이터(디렉터리에 남은 서버 흔적)를 정리해 복제가 깨끗하게 유지되도록 한다.

스키마 갱신과 승격·강등·정리 순서를 지켜 도메인 컨트롤러를 안전하게 늘리고 줄이는 것

ID — Active Directory Domain Services04-05

AD DS 운영 — 계정·그룹 정책·서비스 계정

사용자 계정·보안 그룹·그룹 정책·서비스 계정(gMSA/dMSA) 등 AD DS를 일상적으로 운영하고 관리하는 방법.

#1문제 상황

AD DS를 세운 뒤에는 사용자 계정, 보안 그룹, 그룹 정책, 서비스 계정을 매일 만들고 고쳐야 한다. 그런데 서비스 계정을 사람이 직접 암호를 정해 쓰면 암호가 바뀔 때마다 그 계정을 쓰는 서비스가 멈추고, 담당자가 퇴사하면 암호를 아는 사람이 그대로 남는다. 또 SPN(서비스 주체 이름, 서비스와 계정을 연결하는 식별자)이 중복되면 Kerberos 인증이 어긋난다. 여러 대의 서버에서 같은 서비스 계정을 돌리면 암호를 각 서버에 똑같이 배포해야 하는데, 이 배포와 교체를 자동화하지 않으면 운영자가 개입할 때마다 정지와 보안 노출이 함께 생긴다.

#2핵심 질문

계정·그룹 정책·서비스 계정을 사람 손을 줄이면서 안전하게 운영하려면 어떻게 관리해야 하는가?

#3동작 예시

여러 웹 서버가 같은 데이터베이스에 접속할 때 서비스 계정을 쓰는 상황을 보자. 관리자는 그룹 관리 서비스 계정(gMSA, 여러 서버가 함께 쓰도록 암호를 자동으로 돌려주는 계정)을 만들고, 먼저 키 배포 서비스(KDS) 루트 키를 생성한 뒤 그 계정을 쓸 서버들을 지정한다. 그러면 각 서버는 암호를 직접 입력하지 않고 AD DS가 주기적으로 갱신하는 암호를 받아 인증한다.

#4동작 과정

  1. 계정과 그룹 구성사용자 계정과 보안 그룹을 만들고, 위임(Delegation of Control)으로 관리자가 특정 OU의 계정만 다루도록 권한을 나눈다. 이렇게 하면 도메인 전체 권한을 넘기지 않고 업무를 분담할 수 있다.
  2. 정책 적용그룹 정책 개체(GPO)로 보안 설정과 환경을 지정하고, 적용 범위와 필터링으로 어느 사용자·컴퓨터에 내려갈지 정한다. 정책 결과와 모델링으로 실제 반영 상태를 확인한다.
  3. 서비스 계정 자동화gMSA나 dMSA(위임 관리 서비스 계정)를 도입하고 KDS 루트 키를 만들어 암호 교체를 AD DS에 맡긴다. 서버는 별도 암호 관리 없이 계정을 쓰고, 사람이 암호를 알 필요가 없어진다.

AD DS 보안과 재해 복구

AD DS를 공격으로부터 지키는 보안 모범 사례와, 장애·침해 상황에서 포리스트를 복구하는 재해 복구 절차.

#1문제 상황

AD DS는 인증과 권한의 중심이라 공격자가 여기를 장악하면 도메인 전체를 손에 넣는다. 도메인 관리자·엔터프라이즈 관리자 같은 강력한 계정과 도메인 컨트롤러는 자격 증명 탈취의 주요 표적이 되지만, 이런 계정을 일상 업무에 그대로 쓰거나 도메인 컨트롤러에 다른 소프트웨어를 함께 설치하면 공격 표면이 넓어진다. 또 침해가 이미 진행 중일 때 대응 계획 없이 복구부터 하면, 공격자가 심어둔 권한과 백도어가 그대로 남는다. 그래서 평상시의 최소 권한·보호 계정·감사 정책과, 침해를 전제로 한 격리·복구 계획을 함께 준비해야 한다.

#2핵심 질문

강력한 계정과 도메인 컨트롤러를 어떻게 보호하고, 침해가 확인됐을 때 어떻게 안전하게 복구하는가?

#3동작 예시

관리자가 도메인 관리자 계정으로 일상 업무를 보는 상황을 생각하자. 모범 사례는 이 계정을 보호된 계정 그룹에 넣고 대화형 로그온을 차단하며, 일반 업무는 별도의 관리 계정으로 나누어 하도록 만드는 것이다. 관리용 서버를 따로 두고 거기서만 관리 작업을 하면, 사용자 PC가 침해돼도 관리자 자격 증명이 새어 나가지 않는다.

#4동작 과정

  1. 공격 표면 축소와 최소 권한강력 계정을 일상 사용에서 분리하고 관리용 호스트에서만 관리 작업을 하도록 한다. 도메인 컨트롤러에는 필요한 역할만 남겨 다른 소프트웨어가 얹히지 않게 한다.
  2. 모니터링과 감사감사 정책과 고급 감사 설정으로 인증·계정 변경 같은 이벤트를 기록하고, 지정한 이벤트를 주기적으로 확인해 침해 징후를 조기에 발견한다.
  3. 침해 대응과 복구침해를 전제로 격리·자격 증명 재설정·신뢰 복구 순서를 미리 정해 둔다. FSMO 역할 이전과 기능 수준 관리 같은 정상 운영 절차를 함께 익혀 두어 복구 시점에 순서를 헤매지 않게 한다.

AD DS 문제 해결

AD DS 복제 오류와 LDAP 연결 등 도메인 서비스에서 발생하는 문제를 진단하고 해결하는 방법.

#1문제 상황

AD DS는 여러 도메인 컨트롤러가 복제로 데이터를 맞추기 때문에, 한 곳의 복제가 멈추거나 DNS·LDAP 연결이 어긋나면 사용자 로그인과 그룹 정책 적용이 조용히 실패한다. 문제는 증상이 "로그인이 가끔 안 된다"처럼 뭉뚱그려 나타나서, 원인 서버와 시점을 찾기 어렵다는 점이다. 복제 오류는 디렉터리 서비스 이벤트 로그와 Repadmin.exe, Dcdiag.exe 같은 도구가 남기지만, 이벤트를 읽고 도구 출력을 해석하지 못하면 어느 연결이 왜 실패했는지 판단할 수 없다. 진단 환경을 미리 갖춰 두지 않으면 장애 때마다 처음부터 추측하게 된다.

#2핵심 질문

복제와 LDAP 연결 문제를 어느 도구로 어떤 순서로 확인해 원인을 정확히 짚어내는가?

#3동작 예시

두 도메인 컨트롤러 사이 복제가 멈춘 상황을 보자. 관리자는 먼저 Dcdiag로 도메인 컨트롤러 상태와 연결을 점검하고, Repadmin으로 복제 실패 목록과 마지막 성공 시각을 확인한다. 특정 연결만 실패하면 그 연결의 DNS 이름 확인과 포트, 사이트 링크를 차례로 확인해 실패 지점을 좁힌다.

#4동작 과정

  1. 진단 환경 준비문제가 생기면 바로 쓸 수 있도록 도메인 컨트롤러에서 이벤트 로그와 Repadmin·Dcdiag 같은 도구를 사용할 수 있게 준비하고, 필요하면 ETW(Windows용 이벤트 추적)로 LDAP 연결 같은 세부 동작을 기록한다.
  2. 복제 상태 확인Repadmin과 Dcdiag로 실패한 복제와 이벤트 로그 항목을 확인해 원인 서버와 연결을 특정한다. 여기서 좁힌 범위가 다음 확인 대상을 정한다.
  3. 원인별 조치DNS 이름 확인, 연결, 사이트 구성 중 어긋난 지점을 바로잡고 복제를 다시 돌려 정상화됐는지 확인한다. 조치 후 다시 도구로 검증해 재발 여부를 남긴다.

AD FS 개요와 설계

AD FS는 온프레미스에서 사용자 인증과 SSO(웹 SSO·페더레이션)를 제공하는 페더레이션 서비스로, 배포 목표·토폴로지·인증서·용량 등 설계 요소를 먼저 정한다.

#1문제 상황

여러 웹 애플리케이션이 각자 로그인을 처리하면, 사용자는 앱마다 계정과 암호를 따로 관리하고 관리자는 인증 정책을 앱별로 반복 설정해야 한다. 회사 계정으로 외부 파트너의 애플리케이션에 접속하려면 계정을 상대 조직에 또 만들거나 신뢰 관계를 매번 새로 맺어야 해서, 경계를 넘는 인증이 번거롭고 관리 비용이 크다. 또 인증을 앱 안에 넣으면 사용자·암호 저장소가 앱마다 흩어져 보안 관리가 어려워진다. 그래서 인증을 앱에서 떼어내 한 곳에서 처리하고, 조직 경계를 넘는 신뢰를 표준 방식으로 맺는 구조가 필요하다.

#2핵심 질문

여러 애플리케이션과 다른 조직의 사용자까지 하나의 인증 흐름으로 묶어 SSO를 제공하려면 무엇을 먼저 설계해야 하는가?

#3동작 예시

본인 회사의 웹 애플리케이션과 파트너 회사의 애플리케이션에 같은 계정으로 접속하는 상황을 보자. 먼저 배포 목표를 정한다. 자사 사용자가 자사 앱에 접속하는 웹 SSO인지, 자사 사용자가 파트너 앱에 접속하는 페더레이션 웹 SSO인지에 따라 페더레이션 서버와 프록시를 어디에 두고 신뢰를 어떻게 맺을지가 갈린다. 목표가 정해지면 그에 맞는 토폴로지가 선택된다.

#4동작 과정

  1. 배포 목표 식별자사 사용자를 자사 앱에 연결할지, 다른 조직 사용자를 자사 앱에 받을지, 자사 사용자를 다른 조직 앱에 보낼지를 정한다. 이 분류가 이후 토폴로지와 신뢰 구성의 기준이 된다.
  2. 토폴로지 선택목표에 맞춰 독립 페더레이션 서버, WID(Windows 내부 데이터베이스) 기반 팜, WID와 페더레이션 서버 프록시 조합, SQL Server 기반 팜 중에서 규모와 가용성에 맞는 형태를 고른다. 여기서 인증서와 노출 위치가 함께 정해진다.
  3. 요구사항과 인증서·용량 계획서버 요구사항과 인증서, 페더레이션 서버 프록시 배치, 사용량을 점검해 실제 배포 가능한 구성인지 확인한다. 이 계획이 확정되면 설치와 신뢰 구성 단계로 넘어간다.

AD FS 배포

AD FS 서버 역할 설치, 페더레이션 서버 팜 구성, 페더레이션 서버 프록시 배치, 인증서·DNS 설정 등 실제 배포 절차를 수행한다.

#1문제 상황

예전에는 각 응용 프로그램이 사용자 이름과 암호를 직접 받아 자체적으로 로그인 처리를 했다. 이 방식에서는 앱마다 인증 코드와 계정 저장소가 따로 생기고, 사용자는 앱 개수만큼 자격 증명을 관리해야 했다.

앱이 늘어날수록 계정이 흩어져 관리가 어려워지고, 한 곳의 계정이 뚫리면 그 자격 증명이 다른 앱에도 그대로 통할 위험이 커진다. 그래서 인증을 한 곳에 모으고 각 앱은 그 결과만 신뢰하게 만드는 배포 절차가 필요해졌다.

#2핵심 질문

여러 응용 프로그램의 인증을 하나의 페더레이션 서비스로 모아 안전하게 배포하려면 무엇을 어떤 순서로 구성해야 하는가?

#3동작 예시

AD FS 배포는 서버 역할 설치로 시작해 인증서와 DNS를 준비하고, 페더레이션 서버 팜을 구성한 뒤, 외부 사용자용 페더레이션 서버 프록시를 배치하는 흐름으로 진행된다. 예를 들어 SSL 인증서를 발급받아 AD FS 서버에 등록하고, 페더레이션 서비스 이름에 대한 DNS 레코드를 회사 DNS에 만들면, 이후 클라이언트가 그 이름으로 인증 요청을 보낼 수 있게 된다.

#4동작 과정

  1. 역할 설치와 전제 준비Windows Server에 AD FS 서버 역할을 설치하고, 페더레이션 서비스에 쓸 SSL 인증서와 토큰 서명·암호 해독 인증서를 준비한다. 회사 DNS에 페더레이션 서비스 이름과 장치 등록 서비스(DRS, 장치를 AD FS에 등록·인증하는 서비스) 레코드를 만든다.
  2. 페더레이션 서버 팜 구성첫 페더레이션 서버를 만들어 팜을 초기화하고, 이후 서버를 팜에 추가해 여러 서버가 같은 인증을 나눠 처리하게 한다. 클레임 규칙(사용자 특성을 인증 판단에 쓰는 규칙)과 신뢰 당사자 트러스트(인증을 위임받는 앱 쪽 신뢰 관계)를 설정한다.
  3. 프록시 배치와 검증외부망에 페더레이션 서버 프록시(내부 AD FS로 요청을 중계하는 경계 서버)를 배치해 인터넷 사용자의 인증을 받아 넘긴다. 설정을 마친 뒤 페더레이션 서버가 정상 동작하는지 확인하고, 파트너 조직과의 계정·리소스 트러스트를 구성한다.

#5한 줄 요약

인증 정책·클레임 규칙·인증서 관리 같은 운영 작업과 클레임 파이프라인 등의 기술 개념, 로그·진단을 통한 장애 해결 방법을 함께 다룬다.

#1문제 상황

AD FS를 배포한 뒤에도 운영 작업은 계속 남는다. 인증 정책을 바꾸거나 클레임 규칙을 추가하고, 인증서가 만료되기 전에 갱신해야 하며, 로그인 문제가 생기면 원인을 찾아야 한다.

배포 절차만 알아서는 이런 일을 처리할 수 없다. 인증이 실패했을 때 어느 단계에서 규칙이 어긋났는지, 인증서 문제인지 정책 문제인지 구분하지 못하면 장애가 길어진다.

#2핵심 질문

AD FS를 안정적으로 운영하려면 인증 정책·클레임·인증서를 어떻게 관리하고, 문제가 생겼을 때 어디를 보고 원인을 찾아야 하는가?

#3동작 예시

AD FS는 요청이 들어오면 클레임 파이프라인이라는 단계별 처리 흐름을 거친다. 들어온 클레임을 수용하고, 클레임 규칙을 적용해 변환하며, 마지막에 토큰 발급 여부를 결정한다. 관리자는 이 파이프라인 단계를 기준으로 이벤트 로그와 진단 추적을 확인해 어느 규칙에서 클레임이 걸러졌는지 찾아낸다.

#4동작 과정

  1. 정책과 규칙 관리액세스 제어 정책(누가 어떤 조건에서 인증받을지 정하는 규칙)과 추가 인증 방법을 설정하고, 클레임 규칙을 만들어 들어온 클레임을 통과·필터·변환한다. 조직 요구에 맞춰 로그인 화면과 대체 로그인 ID 같은 사용자 환경도 조정한다.
  2. 인증서 관리토큰 서명 인증서와 암호 해독 인증서를 추적하고 만료 전에 갱신해 신뢰 사슬이 끊기지 않게 한다. 인증서 갱신 도구와 신뢰 당사자 트러스트 갱신을 함께 처리한다.
  3. 진단과 문제 해결이벤트 로그와 진단 추적으로 클레임이 어느 단계에서 처리·거부됐는지 확인한다. 필요하면 Rapid Restore Tool 같은 도구로 구성을 백업·복원하고, 로그인 실패 원인을 규칙·정책·인증서 관점에서 좁혀 해결한다.

AD CS — Active Directory Certificate Services

AD CS는 도메인 환경에서 인증서를 발급·관리·해지(CRL/OCSP)하는 PKI 서버 역할로, 인증서 템플릿과 신뢰 체계를 기반으로 동작한다.

#1문제 상황

도메인 환경에서 사용자와 서버를 인증하려면 서로를 신뢰할 수 있는 인증서가 필요하다. 인증서를 각자 손으로 만들면 발급자와 유효 기간, 서명이 제각각이 되어 상대가 진짜인지 확인할 방법이 없다.

인증서를 아무 곳에서나 발급하면 위조된 인증서를 구분할 수 없고, 만료되거나 유출된 인증서를 무효화할 통일된 절차도 없다. 신뢰의 기준이 되는 발급 기관과 그 발급·해지 체계가 필요하다.

#2핵심 질문

도메인 전체가 신뢰할 수 있는 인증서를 발급하고, 유효 기간과 해지 상태까지 일관되게 관리하려면 어떻게 해야 하는가?

#3동작 예시

AD CS는 인증 기관(CA, 인증서에 서명해 신뢰를 보증하는 서버)을 세우고 인증서 템플릿으로 발급 규격을 정한다. 사용자가 템플릿에 맞춰 인증서를 요청하면 CA가 서명해 발급하고, 해지된 인증서는 CRL(해지 목록)이나 OCSP(온라인 해지 확인 응답자)로 배포해 검증하는 쪽이 무효 여부를 확인하게 한다.

#4동작 과정

  1. 신뢰 체계 구성루트 CA를 세우고 하위 CA로 서명 권한을 위임해 인증서 사슬을 만든다. 루트 인증서를 신뢰할 수 있는 루트로 배포해 클라이언트가 발급자를 신뢰하게 한다.
  2. 발급 규격과 요청 처리인증서 템플릿으로 용도·주체·키 사용 규칙을 정의하고, 웹 등록·정책 웹 서비스·네트워크 장치 등록 서비스 같은 등록 채널로 들어온 요청에 서명해 발급하거나 보류·거부한다.
  3. 해지와 갱신 관리유출·만료된 인증서를 해지하고 CRL과 OCSP로 상태를 배포해 검증 시 무효 인증서가 걸러지게 한다. 인증서 갱신과 CA 마이그레이션, 상태 모니터링으로 PKI를 계속 유지한다.

#5한 줄 요약

인증 기관과 템플릿으로 도메인 인증서를 발급하고 CRL·OCSP로 해지까지 일관되게 관리해 신뢰의 기준을 세우는 것

자격 증명 보호 — 로그온 유형·SRP·LAPS

관리자 자격 증명 탈취를 막기 위한 보호 기법으로, 로그온 유형 구분, 소프트웨어 제한 정책(SRP), 로컬 관리자 암호 자동 관리(LAPS)를 포함한다.

#1문제 상황

공격자는 관리자 자격 증명을 탈취해 더 높은 권한으로 옮겨 다니는 것을 노린다. 관리자가 서버에 로그온할 때 자격 증명이 메모리에 남거나, 신뢰할 수 없는 프로그램이 실행되거나, 여러 장비의 로컬 관리자 암호가 같으면 한 곳이 뚫릴 때 피해가 넓어진다.

이런 경로를 막지 않으면 관리자 한 명의 자격 증명 유출이 도메인 전체 장악으로 이어질 수 있다. 로그온 방식과 프로그램 실행, 로컬 암호를 각각 통제하는 장치가 필요하다.

#2핵심 질문

관리자 자격 증명이 탈취되는 경로를 로그온 유형·프로그램 실행·로컬 암호 관리로 어떻게 줄일 수 있는가?

#3동작 예시

관리자가 원격 데스크톱으로 서버에 접속할 때 자격 증명을 대상 서버에 남기지 않는 제한된 관리자 모드(Restricted Admin mode)로 연결하면, 대상 서버에 관리자 암호가 노출되지 않는다. 또 관리 작업은 클라이언트에서 서버로 권한을 위임하는 방식으로 처리해 자격 증명을 서버에 두지 않는다.

#4동작 과정

  1. 로그온 유형 구분과 통제로그온 유형(대화형·네트워크·원격 등 자격 증명이 어디에 남는지를 나누는 구분)을 파악해, 관리자 계정이 자격 증명을 남기는 방식으로 로그온하지 않도록 제한한다. 자격 증명 위임을 꼭 필요한 경우로 좁힌다.
  2. 소프트웨어 제한 정책(SRP)소프트웨어 제한 정책으로 실행을 허용할 프로그램과 차단할 프로그램을 정해, 메일 첨부 등으로 들어온 신뢰할 수 없는 실행 파일이 관리자 권한으로 도는 것을 막는다.
  3. 로컬 관리자 암호 자동 관리LAPS(로컬 관리자 암호를 주기적으로 바꾸고 관리하는 기능)로 각 장비의 로컬 관리자 암호를 서로 다르게 자동 관리·교체해, 한 장비의 암호가 유출돼도 다른 장비로 번지지 않게 한다.

#5한 줄 요약

로그온 유형·프로그램 실행·로컬 암호를 각각 통제해 관리자 자격 증명 탈취가 도메인 전체로 번지는 것을 막는 것

코어 네트워크 가이드와 BranchCache

코어 네트워크 가이드는 Windows Server로 DNS·DHCP·NPS 등 핵심 네트워크 서비스를 갖춘 기본 네트워크를 단계별로 구축하는 안내이고, BranchCache는 지점 사무실에서 콘텐츠를 로컬에 캐시해 WAN 대역폭 사용을 줄이는 기능이다.

#1문제 상황

서버와 클라이언트가 통신하려면 이름 해석, 주소 할당, 네트워크 접근 제어 같은 핵심 서비스가 먼저 갖춰져야 한다. 이런 요소를 하나씩 따로 구성하면 서로 맞물리지 않아 인증이 안 되거나 이름이 풀리지 않는 문제가 생긴다.

또 지점 사무실에서 중앙의 파일이나 웹 콘텐츠를 쓸 때마다 매번 WAN(지점과 본사를 잇는 원거리 회선)을 건너야 하면 회선이 느려지고 대역폭이 낭비된다.

#2핵심 질문

DNS·DHCP·NPS 같은 핵심 네트워크 서비스를 갖춘 기본망을 어떻게 단계별로 구축하고, 지점의 반복 콘텐츠 다운로드는 어떻게 줄이는가?

#3동작 예시

코어 네트워크 가이드는 서버 인증서 배포부터 시작해 WEB1 같은 웹 서버를 세우고, DNS에 별칭(CNAME) 레코드를 만들며, NPS용 인증서 자동 등록과 802.1X 유선·무선 접속을 구성하는 순서로 기본망을 완성한다. 지점에서는 BranchCache 호스티드 캐시 서버를 두고 지점 클라이언트가 그 서버에서 콘텐츠를 받게 한다.

#4동작 과정

  1. 핵심 서비스 구축인증서 배포와 웹 서버 설치, DNS 별칭 레코드 생성, CRL 배포 등으로 이름 해석과 신뢰의 토대를 만든다. NPS(네트워크 정책 서버, 접속 허용·인증을 판단하는 서버)에 인증서 자동 등록을 설정한다.
  2. 접속 인증 구성802.1X(유선·무선 접속 시 인증을 요구하는 표준) 인증을 배포해 네트워크에 들어오는 장치를 NPS가 검증하게 한다. 이로써 주소 할당(DHCP)과 이름 해석(DNS)이 동작하는 기본망이 완성된다.
  3. 지점 콘텐츠 캐시지점에 BranchCache 호스티드 캐시 서버를 설치하고 서비스 연결 지점으로 자동 검색되게 설정한다. 지점 클라이언트가 같은 콘텐츠를 캐시에서 받아 WAN 대역폭 사용이 줄어든다.

#5한 줄 요약

DNS·DHCP·NPS로 기본망을 단계별로 세우고, BranchCache로 지점의 반복 콘텐츠를 로컬 캐시에서 제공해 WAN 부담을 줄이는 것

네트워킹 — DNS·DHCP·SDN·NPS·IPAM06-02

DNS Server

DNS Server는 도메인 이름을 IP 주소로(또는 그 반대로) 변환해 주는 서버 역할로, Windows Server에 설치해 존·리소스 레코드·동적 업데이트·DNSSEC 같은 기능을 제공한다.

#1문제 상황

사람은 서버를 이름으로 기억하지만 통신은 IP 주소로 이뤄진다. 이름과 주소를 연결해 주는 장치가 없으면 사용자는 숫자 주소를 외워야 하고, 서버 주소가 바뀔 때마다 각 클라이언트 설정을 고쳐야 한다.

이름 해석이 수동이라면 주소 변경이 곧 장애로 이어지고, 응답이 위조되면 사용자가 가짜 서버로 유도될 수 있다. 이름과 주소를 자동으로 관리하고 응답을 검증하는 서버가 필요하다.

#2핵심 질문

도메인 이름을 IP 주소로 안정적으로 변환하고, 주소 변경과 응답 위조까지 감당하려면 DNS를 어떻게 운영해야 하는가?

#3동작 예시

클라이언트가 어떤 이름을 조회하면 DNS Server는 자신이 관리하는 존과 리소스 레코드에서 해당 이름의 주소를 찾아 응답한다. 없으면 다른 DNS 서버로 질의를 넘기는 전달을 하고, 동적 업데이트가 켜져 있으면 클라이언트가 바뀐 주소를 스스로 등록하게 한다.

#4동작 과정

  1. 존과 레코드로 이름 관리DNS 존(특정 도메인의 이름 데이터 묶음)을 만들고 A·CNAME 같은 리소스 레코드로 이름과 주소를 연결한다. 동적 업데이트와 노화·정리로 오래된 레코드가 자동 갱신·삭제되게 한다.
  2. 질의 처리와 전달클라이언트 조회를 받아 존에서 답을 찾고, 없으면 다른 서버로 전달해 결과를 받아 응답한다. 역방향 조회와 캐시로 이름→주소, 주소→이름 양방향을 처리한다.
  3. 보안과 운영DNSSEC(응답에 서명해 위조를 검증하는 확장)로 응답 신뢰를 보장하고, DoH(DNS over HTTPS, 암호화된 채널로 질의하는 방식)로 질의를 보호한다. DNS 정책으로 조건에 따라 응답을 나누고 로깅·진단으로 장애를 추적한다.

네트워킹 — DNS·DHCP·SDN·NPS·IPAM06-03

DHCP·Network ATC·Network HUD

DHCP는 클라이언트에 IP 주소와 네트워크 설정을 자동으로 할당하는 서버 역할이고, Network ATC는 Hyper-V 호스트의 네트워크 구성을 의도(intent) 기반으로 단순화하며, Network HUD는 네트워크 문제를 진단·표시하는 도구다.

#1문제 상황

서버와 클라이언트가 늘어나면 각 장비의 IP 주소, 서브넷 마스크, 게이트웨이, DNS 주소를 사람이 직접 적어 넣어야 한다. 장비가 수십 대일 때는 버틸 만하지만 수백, 수천 대가 되면 주소가 겹치거나 빠뜨리는 실수가 반복되고, 새 장비를 꽂을 때마다 담당자가 일일이 설정해야 한다.

고정 IP를 손으로 관리하면 주소 자원이 어디까지 쓰였는지 파악하기 어렵고, 장비를 다른 망으로 옮길 때마다 설정을 다시 고쳐야 한다. Hyper-V 호스트의 네트워크 구성도 마찬가지여서, NIC·vSwitch·가상 어댑터 설정을 여러 호스트에 걸쳐 사람이 맞추다 보면 호스트마다 미묘하게 다른 상태가 된다. 문제가 생겼을 때 어느 계층에서 어긋났는지 확인할 도구도 마땅치 않다.

#2핵심 질문

장비마다 IP와 네트워크 설정을 사람이 직접 입력하고 호스트 네트워크를 손으로 맞추는 대신, 주소 할당과 네트워크 구성을 자동화하고 상태를 한눈에 진단할 수는 없을까?

#3동작 예시

관리자가 DHCP 서버 역할을 설치하고 192.168.1.0/24 대역에 대한 범위(scope, 할당할 주소 구간)를 정의하면, 같은 망에 새로 연결된 클라이언트가 부팅하며 DHCP 요청을 보낸다. 서버는 그 요청에 대해 아직 쓰이지 않은 주소 하나를 골라 임대(lease) 기간과 함께 돌려주고, 클라이언트는 그 주소와 서브넷·게이트웨이·DNS 정보를 자동으로 적용한다. 반대로 DHCP 요청을 직접 받을 수 없는 다른 서브넷에 클라이언트가 있으면, 그 망의 릴레이 에이전트(relay agent)가 요청을 DHCP 서버까지 전달해 준다.

#4동작 과정

  1. 주소 범위 정의관리자가 DHCP 콘솔이나 Windows PowerShell로 범위·제외 주소·임대 기간·서브넷 선택 옵션을 설정해 어떤 대역에서 어떤 주소를 나눠 줄지 정한다. 이렇게 해 두면 주소 할당 규칙이 서버 한 곳에 모여 장비별 수동 입력이 사라진다.
  2. 요청과 임대 부여클라이언트가 네트워크에 붙어 IP를 요청하면 DHCP 서버가 사용 가능한 주소를 골라 임대 정보와 함께 응답한다. 서버는 임대 상태와 이벤트 로그를 남기므로 어떤 주소가 누구에게 언제 나갔는지 추적할 수 있고, 두 대의 DHCP 서버를 페어로 묶는 장애 조치(failover, 한 대가 멈춰도 다른 대가 이어받는 구성)로 중단 없이 임대를 이어 갈 수 있다.
  3. 호스트 의도 적용과 진단Hyper-V 호스트에서는 Network ATC가 "이 호스트의 네트워크는 이렇게 구성한다"는 의도(intent)를 정의해 NIC·vSwitch·가상 어댑터 구성을 자동으로 맞추고, Network HUD가 그 결과를 시각적으로 보여 주며 문제 지점을 짚는다. 손으로 맞추던 호스트 간 차이가 줄고, 이상이 생기면 어디서 어긋났는지 바로 확인할 수 있다.

#5한 줄 요약

주소 할당(DHCP)과 호스트 네트워크 구성을 자동화하고 그 상태를 진단 가능하게 만들어, 네트워크 설정을 사람 손에서 서버와 의도 정의로 옮기는 것

네트워킹 — DNS·DHCP·SDN·NPS·IPAM06-04

SDN — Software Defined Networking

SDN(소프트웨어 정의 네트워킹)은 네트워크 제어를 소프트웨어로 중앙 집중화해 가상 네트워크·게이트웨이·부하 분산을 유연하게 구성하고 자동화하는 Windows Server의 기술 집합이다.

#1문제 상황

가상 머신과 테넌트(tenant, 같은 인프라를 나눠 쓰는 고객)가 늘어나면 각 VM이 쓸 가상 네트워크, 게이트웨이, 부하 분산, 방화벽 규칙을 장비별로 따로 설정해야 한다. 물리 스위치와 라우터에 하나씩 명령을 넣는 방식은 변경 하나에 여러 장비를 손대야 하고, 테넌트마다 같은 사설 IP 대역을 써도 서로 겹치지 않게 격리하려면 VLAN 같은 기존 수단으로는 규모를 감당하기 어렵다.

장비마다 설정이 흩어져 있으면 새 테넌트를 만들거나 정책을 바꿀 때마다 전체를 다시 맞춰야 하고, 어느 규칙이 어디에 적용됐는지 일관되게 관리하기 어렵다. 네트워크 상태를 사람이 머릿속으로 추적해야 하니 자동화도 어렵다.

#2핵심 질문

네트워크 제어를 장비별 수동 설정에서 중앙의 소프트웨어로 모아, 가상 네트워크·게이트웨이·부하 분산·정책을 일관되게 구성하고 자동화할 수는 없을까?

#3동작 예시

네트워크 컨트롤러(Network Controller, SDN의 중앙 제어 지점)에 "테넌트 A의 가상 네트워크를 만들고 가상 게이트웨이를 붙인다"는 요청을 한 번 보내면, 컨트롤러가 그 정책을 호스트의 가상 스위치와 필요한 구성 요소에 밀어 넣어 실제 통신 경로를 만든다. 관리자는 개별 호스트에 접속해 명령을 반복할 필요 없이 컨트롤러 한 곳에서 테넌트 가상 네트워크를 만들고, 가상 게이트웨이를 추가하고, 부하 분산과 NAT 규칙을 걸 수 있다. Hyper-V 네트워크 가상화는 이 위에서 테넌트마다 겹치는 IP 주소를 써도 서로 격리되게 해 준다.

#4동작 과정

  1. 중앙 제어 지점 구성네트워크 컨트롤러를 배포한다. 장애 조치 클러스터링(Failover Clustering)이나 Service Fabric 기반으로 구성해 컨트롤러 자체가 한 대 멈춰도 제어가 이어지게 만든다. 제어가 한 곳에 모이면서 정책을 한 번 정의해 여러 호스트에 일관되게 적용할 수 있게 된다.
  2. 가상 네트워크와 정책 배포테넌트 가상 네트워크, 가상 게이트웨이, 부하 분산(Software Load Balancer), QoS, 암호화 같은 요소를 컨트롤러를 통해 정의한다. Hyper-V 네트워크 가상화와 iDNS(내부 DNS 서비스)가 겹치는 주소 대역을 격리하고 이름 해석을 처리해, 테넌트가 자기 주소 체계를 그대로 쓸 수 있게 된다.
  3. 운영과 갱신SDN 인프라를 업데이트·백업·복원하고, 가상 네트워크 피어링이나 게이트웨이 대역 할당 같은 운영 작업을 컨트롤러에서 수행한다. 정책 변경이 중앙에서 반영되므로 테넌트 추가와 설정 변경이 자동화된 절차로 처리된다.

네트워킹 — DNS·DHCP·SDN·NPS·IPAM06-05

HPN·HCN·IPAM·NCSI·NLB

HPN은 RDMA·SMB Direct 같은 고성능 네트워킹 기능을, HCN은 컨테이너 네트워크를 관리하는 서비스 API를, IPAM은 IP 주소와 DNS·DHCP 자원을 통합 관리하는 도구를, NCSI는 네트워크 연결 상태 진단을, NLB는 여러 서버에 트래픽을 분산하는 기능을 말한다.

#1문제 상황

네트워크가 커지면 서로 다른 문제가 한꺼번에 생긴다. IP 주소·DNS 레코드·DHCP 범위가 여러 도구에 흩어져 있어 어느 주소가 쓰였고 어느 이름이 어디를 가리키는지 통합해 보기 어렵고, 컨테이너처럼 자주 생성·삭제되는 워크로드의 네트워크를 일일이 손으로 연결하기도 어렵다.

성능 쪽도 마찬가지여서 RDMA·SMB Direct 같은 고성능 네트워킹 기능과 각종 오프로드 기능을 어떤 조합으로 켜야 하는지 알기 어렵고, 연결이 안 될 때 원인이 케이블인지 설정인지 서버인지 판단할 근거가 없다. 트래픽이 몰리는 서비스는 서버 한 대로 감당이 안 되는데, 여러 서버로 나눠 보내는 구성도 별도로 만들어야 한다.

#2핵심 질문

주소·이름 자원 관리, 고성능·컨테이너 네트워킹, 연결 진단, 트래픽 분산을 각각 따로 붙이지 않고 한 환경에서 일관되게 다룰 수는 없을까?

#3동작 예시

IPAM(IP Address Management)을 배포하면 관리자는 하나의 콘솔에서 IP 주소 블록과 사용률을 보고, DNS 영역과 리소스 레코드를 만들고 지우고, DHCP 범위까지 함께 관리할 수 있다. 예를 들어 특정 IP 주소에 어떤 DNS 레코드가 걸려 있는지 조회하거나, DNS 영역을 만들어 레코드를 추가하는 작업을 IPAM 안에서 처리한다. 컨테이너 쪽에서는 HCN(Host Compute Network) 서비스 API가 컨테이너 엔드포인트를 가상 네트워크에 연결하는 요청을 처리하고, 연결에 문제가 생기면 NCSI가 네트워크 연결 상태를 진단해 어느 계층에서 끊겼는지 알려 준다.

#4동작 과정

  1. 자원 통합 관리IPAM으로 IP 주소 공간, DNS 영역·리소스 레코드, DHCP 범위를 한곳에서 관리한다. 역할 기반 액세스 제어(RBAC)와 액세스 범위로 누가 어떤 자원을 볼 수 있는지 나누고, 여러 Active Directory 포리스트의 자원도 함께 다룬다. 흩어져 있던 자원이 한 화면에 모여 중복·충돌을 줄일 수 있다.
  2. 워크로드 네트워킹과 성능HCN 서비스 API가 컨테이너 네트워크를 만들고 컨테이너 엔드포인트를 연결하며, Hyper-V 가상 스위치와 RSC 같은 오프로드 기능이 그 트래픽을 처리한다. HPN 계열 기능은 RDMA·SMB Direct처럼 성능을 끌어올리는 기술을 소프트웨어 전용·소프트웨어+하드웨어·하드웨어 전용으로 나눠 어떤 조건에서 쓸 수 있는지 정리해 준다.
  3. 진단과 분산NCSI가 인터넷 연결 여부와 네트워크 상태를 판단해 문제를 좁히고, NLB(Network Load Balancing)가 여러 서버에 들어오는 트래픽을 나눠 한 대에 부하가 몰리지 않게 한다. 관리자는 진단 결과로 원인을 좁힌 뒤 분산 구성을 적용해 가용성과 처리량을 함께 확보한다.

#5한 줄 요약

NPS — Network Policy Server

NPS(네트워크 정책 서버)는 RADIUS 서버·프록시로 동작하며 VPN·무선·802.1X 연결의 인증·권한 부여·계정 기록을 중앙에서 정책으로 제어하는 서버 역할이다.

#1문제 상황

VPN, 무선, 802.1X 스위치처럼 네트워크에 접속하는 경로가 늘어나면 각 장비가 접속자를 따로 인증하고 권한을 판단하게 된다. 장비마다 계정과 정책을 개별로 관리하면 같은 사용자가 경로에 따라 다르게 취급되고, 접속 기록도 흩어져 누가 언제 어디로 들어왔는지 한눈에 볼 수 없다.

정책을 바꿀 때도 장비를 하나씩 찾아가 설정을 고쳐야 하며, 접속이 실패할 때 인증 문제인지 권한 문제인지 구분하기 어렵다. 인증 서버의 인증서·포트·방화벽 설정까지 각각 맞춰야 하니 관리 부담이 커진다.

#2핵심 질문

VPN·무선·802.1X 접속의 인증과 권한 부여, 접속 기록을 장비별 설정이 아니라 중앙 정책으로 일관되게 제어할 수는 없을까?

#3동작 예시

VPN 서버나 무선 액세스 포인트 같은 접속 장치를 RADIUS 클라이언트로 NPS에 등록해 두면, 사용자가 접속을 시도할 때 그 장치가 접속 요청을 NPS로 넘긴다. NPS는 연결 요청 정책(connection request policy)으로 요청을 어디서 처리할지 정하고, 네트워크 정책(network policy)으로 조건에 맞는지 판단해 접속을 허용하거나 거부한다. 허용하면 그 결정을 접속 장치에 돌려주고, 접속 기록은 계정 기록(accounting)으로 남긴다. NPS를 RADIUS 프록시로 두면 요청을 다른 RADIUS 서버 그룹으로 넘겨 처리하게 할 수도 있다.

#4동작 과정

  1. NPS 배포와 등록NPS 역할을 설치하고 Active Directory 도메인에 등록해, 접속 장치(RADIUS 클라이언트)와 인증에 쓸 인증서를 준비한다. 인증서 템플릿과 방화벽, UDP 포트를 맞춰 두면 이후 정책만으로 접속 제어가 가능해진다.
  2. 정책으로 판단연결 요청 정책으로 요청을 받을지·넘길지 정하고, 네트워크 정책의 조건과 접속 권한(access permission)으로 허용·거부를 결정한다. 정책은 템플릿으로 재사용할 수 있어 여러 서버에 같은 규칙을 일관되게 적용할 수 있고, 접속 요청 처리 과정에서 영역 이름(realm name)이나 원격 RADIUS 서버 그룹을 활용해 요청을 알맞게 라우팅한다.
  3. 계정 기록과 관리허용·거부 결과를 접속 장치에 돌려주고 계정 기록 설정으로 접속 내역을 수집한다. 구성을 내보내 다른 서버에 가져오거나, 도메인 등록·해제, 프록시 부하 분산, 동시 인증 수 조정 같은 운영 작업을 수행하며, 변경 후에는 구성을 검증해 정책이 의도대로 동작하는지 확인한다.

진단·QoS·Windows Time·기타

패킷 모니터(Pktmon) 같은 네트워크 진단 도구, 트래픽 우선순위를 정하는 QoS 정책, 도메인 전체의 시각 동기화를 담당하는 Windows Time 서비스 등 네트워크 운영에 필요한 부가 기능들을 묶은 항목이다.

#1문제 상황

네트워크는 연결만 되면 끝이 아니라, 어디서 병목이 생겼는지 확인하고, 중요한 트래픽이 밀리지 않게 우선순위를 정하고, 여러 서버의 시각을 맞춰야 운영이 된다. 그런데 진단 도구·대역 관리·시간 동기화가 각각 따로 놀면 문제가 생겼을 때 어느 기능이 원인인지 가려내기 어렵다.

특히 대역폭을 서버마다 개별로 제한하면 정책이 흩어져 일관성이 없어지고, 서버 시각이 어긋나면 인증·로그·배포처럼 시간에 의존하는 작업이 조용히 틀어진다. 진단도 마찬가지여서 패킷을 뜨고 분석하는 절차가 번거로우면 문제 재현과 원인 파악이 늦어진다.

#2핵심 질문

패킷 진단, 트래픽 우선순위, 시각 동기화를 각 서버에 흩어진 설정이 아니라 중앙에서 일관되게 관리하고 확인할 수는 없을까?

#3동작 예시

관리자가 Active Directory 전체에 적용되는 QoS 프로필을 만들면, 그 설정이 그룹 정책으로 배포되어 여러 서버와 클라이언트에 같은 대역 관리 규칙이 적용된다. 예를 들어 특정 애플리케이션의 트래픽에 우선순위를 주거나 대역폭을 제한하는 규칙을 프로필 하나로 정의해 두면, 개별 서버를 찾아다니며 설정을 고칠 필요가 없다. 문제가 생기면 Pktmon 같은 패킷 모니터로 트래픽을 들여다보고, 시각이 의심되면 Windows Time 서비스로 도메인 전체의 시간 동기화 상태를 확인한다.

#4동작 과정

  1. 중앙 프로필 정의QoS 프로필을 만들어 그룹 정책으로 배포한다. 프로필의 설정이 도메인 전체에 퍼지므로 대역 관리 규칙이 서버마다 흩어지지 않고 한곳에서 일관되게 적용된다.
  2. 적용과 우선순위배포된 정책에 따라 특정 트래픽에 우선순위( DSCP 표시)를 붙이거나 대역폭을 제한해, 중요한 트래픽이 몰리는 상황에서도 밀리지 않게 한다. 이때 어떤 정책이 언제 적용됐고 오류가 났는지는 QoS 정책 이벤트와 오류 기록으로 확인할 수 있다.
  3. 진단과 시각 정렬Pktmon이나 Windows Admin Center의 패킷 모니터링 확장으로 트래픽을 캡처·분석해 원인을 좁히고, Windows Time 서비스로 도메인의 시각을 동기화한다. 정확한 시각 설정과 동기화 상태를 함께 관리하면 인증·로그·배포가 시간 어긋남 없이 동작한다.

DirectAccess·Always On VPN·RAS

DirectAccess, Always On VPN, RRAS/RAS 게이트웨이처럼 도메인·원격 클라이언트가 사내 네트워크에 안전하게 접속하도록 하는 Windows Server 원격 액세스 기술을 통칭한다.

#1문제 상황

재택·이동 근무가 늘면 사내 네트워크 밖에서 사내 자원에 접속해야 하는데, 예전 방식은 사용자가 VPN 연결을 직접 켜고 끄고 연결 여부를 스스로 관리해야 했다. 연결이 끊기면 사내 자원 접근도 끊기고, 사용자는 왜 안 되는지 알기 어렵다.

또 원격 클라이언트에게 무엇을 허용할지, 인증서를 어떻게 다룰지, 사내망과 어떻게 라우팅할지를 서버마다 따로 정하면 정책이 흩어진다. DirectAccess에서 Always On VPN으로 옮겨 가려는 조직은 기존 배포를 어떻게 마이그레이션할지, 인증서와 연결 프로필을 어떻게 맞출지도 정해야 한다.

#2핵심 질문

원격 클라이언트가 사내 네트워크에 안전하게 접속하도록, 연결 관리와 정책을 사용자 손이 아니라 중앙에서 일관되게 제공할 수는 없을까?

#3동작 예시

Always On VPN을 배포하면 관리자는 먼저 인프라를 세우고 인증서를 구성한 뒤 VPN 연결 프로필을 만들어 클라이언트에 배포한다. 그러면 사용자가 VPN을 따로 켜지 않아도 연결 프로필에 따라 사내 자원 접근이 이뤄지고, 관리자는 어떤 인증서와 어떤 터널을 쓸지 중앙에서 정한다. 기존에 DirectAccess를 쓰던 환경이라면 DirectAccess에서 Always On VPN으로 마이그레이션 계획을 세워, 인프라·인증서·연결을 단계적으로 옮긴다.

#4동작 과정

  1. 인프라와 인증서 준비Remote Access를 VPN 서버로 설치하거나 Always On VPN 인프라를 배포한다. 이어서 클라이언트와 서버가 서로를 신뢰하도록 Always On VPN 인증서를 구성하는데, 인증서가 준비되어야 연결이 성립하므로 먼저 처리한다.
  2. 연결 프로필 생성과 배포VPN 연결 프로필을 만들어 클라이언트에 배포한다. 프로필이 클라이언트에 적용되면 사용자가 수동으로 연결을 켜지 않아도 조건에 따라 사내 네트워크로 접속할 수 있게 된다.
  3. 마이그레이션과 검증DirectAccess를 쓰던 조직은 인프라·인증서·연결을 Always On VPN으로 옮기는 계획을 세워 단계적으로 마이그레이션하고, DirectAccess 오프라인 도메인 조인이나 RAS 게이트웨이 같은 요소를 함께 점검한다. 배포 후에는 클라이언트가 실제로 사내 자원에 접근되는지 검증한다.

#1문제 상황

DirectAccess와 원격 액세스 구성은 방화벽, 인증서, DNS, 네트워크 위치 등 여러 요소가 얽혀 있어, 실제 운영망에 적용하기 전에 어디서 잘못되는지 확인하기 어렵다. 문서만 읽고 구성을 바꾸면 클라이언트가 사내망에 붙지 못하거나 클러스터 노드가 트래픽을 나눠 받지 못하는 문제가 배포 후에야 드러난다. 그래서 각 구성 요소를 격리된 환경에서 단계별로 세워 검증할 절차가 필요하다.

#2핵심 질문

운영망을 건드리지 않고 DirectAccess와 WAP 구성을 단계별로 세워 정상 동작을 미리 확인하려면 어떻게 해야 하는가?

#3동작 예시

테스트 랩 가이드는 Hyper-V 가상 머신 여러 대로 사내망 서버와 인터넷 구간, 외부 클라이언트를 흉내 낸다. 이 가이드를 따라 DirectAccess를 NLB 클러스터로 묶으면, 외부 클라이언트가 인터넷 구간을 거쳐 클러스터 주소로 접속했을 때 어느 노드가 응답해도 사내 리소스에 도달하는지 확인할 수 있다.

#4동작 과정

  1. 사전 구성 완료먼저 기본 DirectAccess 구성을 끝내고 EDGE1 서버와 도메인 컨트롤러, 앱 서버를 세워 클라이언트 한 대가 정상 접속하는 상태를 만든다. 이 기준선이 있어야 이후 단계의 실패를 구분할 수 있다.
  2. 클러스터·멀티사이트 확장EDGE2를 설치해 두 노드를 네트워크 부하 분산(NLB, 여러 서버에 접속을 나눠 주는 방식) 클러스터로 묶거나, 2-DC1과 2-EDGE1을 추가해 멀티사이트 배포를 구성한다. 노드가 늘어도 같은 주소로 접속이 유지되는지 확인한다.
  3. 시나리오 검증과 스냅샷인터넷에서의 접속, NAT(주소를 바꿔 내보내는 장치) 뒤 클라이언트의 접속, 사내 복귀 시 접속을 차례로 시험하고 마지막에 구성을 스냅샷으로 저장한다. 검증된 상태를 다시 꺼내 반복 시험할 수 있게 된다.

RDS 계획과 아키텍처

세션 호스트·연결 브로커·RD 웹 액세스·RD 게이트웨이 등 RDS 역할 구성과 데스크톱 호스팅 참조 아키텍처를 미리 설계하는 단계다.

#1문제 상황

원격 데스크톱 서비스를 세션 호스트 몇 대로만 시작하면, 사용자가 늘고 접속 경로가 다양해질 때 어느 구성 요소를 어디에 둘지 다시 설계해야 한다. 연결 브로커, 웹 액세스, 게이트웨이 같은 역할을 나중에 덧붙이면 주소와 인증서, 고가용성 구성이 서로 어긋난다. 그래서 배포 전에 규모와 접속 방식, 보안 요구를 정해 역할 배치를 먼저 정해야 한다.

#2핵심 질문

사용자 수와 접속 방식이 커져도 흔들리지 않도록 RDS 역할을 어떻게 배치하고 설계할 것인가?

#3동작 예시

데스크톱 호스팅 참조 아키텍처는 세션 호스트(실제 데스크톱을 돌리는 서버), 연결 브로커(접속을 적절한 호스트로 배정하는 서버), RD 웹 액세스(브라우저로 접속하게 하는 웹), RD 게이트웨이(외부에서 사내로 들어오는 통로)를 각각 분리해 배치한다. 여기에 각 역할을 둘 이상 두어 한 대가 멈춰도 접속이 유지되게 만든다.

#4동작 과정

  1. 요구 정리사용자 수, 접속 위치(사내·외부), 사용할 앱, 보안 요구를 먼저 정한다. 이 값이 세션 호스트 대수와 역할 배치의 기준이 된다.
  2. 역할 배치 설계세션 호스트, 연결 브로커, 웹 액세스, 게이트웨이를 어느 서버에 둘지, 고가용성을 어디에 걸지 정한다. 네트워크와 저장소 요구도 여기서 함께 잡아 이후 재설계를 줄인다.
  3. 참조 아키텍처 확정데스크톱 호스팅 참조 아키텍처에 맞춰 최종 구성을 확정하고, 인증과 GPU, 요금 같은 선택지를 요구에 맞게 고른다. 확정된 설계가 배포 단계의 설치 목록이 된다.

RDS 배포와 라이선스

RDS 인프라를 설치·구성하고 세션 컬렉션을 배포하며 RDS CAL(클라이언트 액세스 라이선스)로 사용 권한을 부여하는 과정이다.

#1문제 상황

설계만 끝낸 상태에서는 실제 사용자가 접속할 수 없다. 세션 호스트와 컬렉션을 세우고 인증서를 붙이고, 라이선스 서버를 활성화해 RDS CAL(원격 데스크톱 접속 권한을 부여하는 라이선스)을 설치하지 않으면 평가 기간이 지난 뒤 접속이 끊긴다. 구성 요소를 각각 따로 배포하면 서로를 찾지 못해 컬렉션이 열리지 않는 문제도 생긴다.

#2핵심 질문

설계된 RDS 환경을 실제로 세우고 사용자에게 합법적인 접속 권한을 부여하려면 어떤 순서로 배포해야 하는가?

#3동작 예시

RDS 인프라를 배포하면 먼저 연결 브로커와 웹 액세스, 게이트웨이 같은 기반 역할을 세우고, 그 위에 세션 컬렉션(사용자에게 제공할 데스크톱과 앱의 묶음)을 만든다. 이어서 라이선스 서버를 활성화하고 RDS CAL을 설치해 세션 호스트가 그 라이선스를 받아 쓰게 연결한다.

#4동작 과정

  1. 인프라 역할 설치연결 브로커, RD 웹 액세스, RD 게이트웨이를 배포하고 인증서를 적용한다. 인증서가 맞아야 클라이언트가 경고 없이 접속한다.
  2. 컬렉션 생성세션 호스트를 컬렉션에 묶어 사용자에게 제공할 데스크톱과 앱 범위를 정한다. 이 단계에서 사용자가 실제로 접속할 대상이 정해진다.
  3. 라이선스 적용라이선스 서버를 활성화하고 RDS CAL을 설치한 뒤 세션 호스트를 라이선스 서버에 연결한다. 이로써 평가 기간 이후에도 접속이 계속 허용된다.

#5한 줄 요약

설계된 RDS 역할과 컬렉션을 세우고 RDS CAL로 사용 권한을 부여해 실제 접속이 가능하게 만드는 것

RDS 운영과 클라이언트 연결

배포된 RDS 환경에서 컬렉션·사용자를 관리하고 성능을 튜닝하며, 웹 클라이언트나 RDP 등으로 클라이언트가 세션에 접속하도록 연결하는 작업이다.

#1문제 상황

배포가 끝난 뒤에도 컬렉션에 사용자를 추가하고, 개인 데스크톱 컬렉션을 관리하고, 성능 저하 원인을 찾는 작업이 계속 필요하다. 또 사용자가 어떤 기기와 앱으로 접속할지 정해 주지 않으면 세션에 들어가지 못한다. 운영과 연결 방법을 따로 관리하면 사용자 문의마다 원인을 처음부터 다시 찾게 된다.

#2핵심 질문

배포된 RDS 환경에서 사용자와 컬렉션을 관리하고, 다양한 기기의 클라이언트가 세션에 안정적으로 접속하게 하려면 어떻게 해야 하는가?

#3동작 예시

사용자는 Windows App이나 원격 데스크톱 클라이언트, 또는 브라우저 기반 RDS 웹 클라이언트로 접속한다. 관리자는 컬렉션에 사용자를 추가하고, 성능 카운터로 앱 지연 원인을 확인하며, 필요하면 개인 데스크톱 세션 컬렉션을 따로 관리한다.

#4동작 과정

  1. 컬렉션·사용자 관리컬렉션에 사용자와 그룹을 추가하고 권한을 조정한다. 누가 어떤 데스크톱과 앱에 접속할 수 있는지가 여기서 정해진다.
  2. 성능 점검과 튜닝성능 카운터로 앱 성능 문제를 진단하고 VDI 데스크톱 설정을 최적화한다. 원인이 되는 구성을 바꿔 체감 지연을 줄인다.
  3. 클라이언트 연결사용자가 Windows App, 원격 데스크톱 클라이언트, 웹 클라이언트 중 하나로 접속하고, 필요하면 외부 접속을 열어 준다. 이로써 사용자가 자신의 기기에서 세션에 도달한다.

#5한 줄 요약

배포된 RDS 환경의 컬렉션과 사용자를 관리하고 클라이언트가 다양한 기기에서 세션에 접속하도록 연결하는 것

보안 기능과 가디드 패브릭

Secured-core·Credential Guard 같은 Windows Server의 보안 기능과, 호스트 관리자가 테넌트 VM의 데이터를 들여다볼 수 없도록 Hyper-V 호스트와 가상 머신을 암호학적으로 보증하는 가디드 패브릭(Guarded Fabric)·실드 VM 기술을 묶어 이르는 보안·보증 영역이다.

#1문제 상황

가상 머신을 호스트 위에서 돌리면, 그 호스트를 관리하는 사람은 가상 머신의 메모리와 디스크에 접근할 수 있다. 테넌트 입장에서는 자신의 데이터를 호스트 관리자가 들여다볼 수 있다는 뜻이고, 호스트가 악성 코드에 감염되면 가상 머신 전체가 노출된다. 기존에는 호스트를 신뢰하는 전제로만 운영되어 이런 내부자와 호스트 침해 위협을 막을 방법이 없었다.

#2핵심 질문

호스트 관리자조차 테넌트 가상 머신의 데이터를 볼 수 없도록 하려면 무엇을 어떻게 보증해야 하는가?

#3동작 예시

가디드 패브릭에서는 호스트가 정상 상태임을 증명해야만 실드 VM(암호화된 상태로 보호되는 가상 머신)을 실행할 수 있다. 호스트는 HGS(호스트 보증 서비스, 호스트의 상태를 확인해 주는 서버)에 자신의 상태를 보고하고, 통과하면 VM을 풀어 주는 키를 받는다.

#4동작 과정

  1. 호스트 증명호스트가 TPM(하드웨어에 심긴 보안 칩)이나 키 모드로 자신이 변조되지 않았음을 HGS에 증명한다. 통과하지 못한 호스트는 실드 VM을 실행하지 못한다.
  2. 키 해제HGS가 증명을 통과한 호스트에만 실드 VM을 여는 키를 내려 준다. 키가 없으면 VM 디스크는 암호화된 상태로 남아 읽을 수 없다.
  3. 실드 VM 실행키를 받은 호스트가 실드 VM을 시작하고, 관리자는 콘솔 접속과 같은 제어가 제한된다. 이로써 테넌트 데이터가 호스트 관리자에게서 보호된다.

Windows 인증·Kerberos·TLS

Windows Server가 사용자·서비스·장치의 신원을 확인하고 통신을 보호하는 인증 체계로, 도메인 로그온의 기본 프로토콜인 Kerberos와 자격 증명 처리 구조, 그리고 Schannel SSP 기반 TLS/SSL 암호화 통신을 아우른다.

#1문제 상황

사용자가 도메인에 로그온하려면 자격 증명을 검증할 방법이 필요하고, 서비스와 장치도 서로를 확인해야 한다. 인증 없이 통신하면 아무나 다른 사용자로 가장하거나 전송 중인 데이터를 가로챌 수 있다. 예전에는 자격 증명을 그대로 보내는 방식도 있었지만, 재사용 공격과 도청에 취약했다.

#2핵심 질문

Windows Server는 사용자·서비스·장치의 신원을 어떻게 확인하고 그 통신을 어떻게 보호하는가?

#3동작 예시

도메인 로그온에서는 Kerberos(티켓을 발급해 신원을 증명하는 인증 프로토콜)가 기본으로 쓰인다. 클라이언트는 KDC(티켓을 발급하는 도메인 컨트롤러 서비스)에서 티켓을 받고, 서비스는 그 티켓을 검사해 클라이언트를 확인한다. 통신 구간은 Schannel(SSL/TLS를 처리하는 Windows 보안 공급자)이 TLS로 암호화한다.

#4동작 과정

  1. 자격 증명 수집과 보호로그온 시 사용자의 자격 증명을 LSA(로컬 보안 기관, 인증을 담당하는 시스템)가 받아 보호된 형태로 다룬다. 보호 계층이 있어 평문 자격 증명이 노출되지 않는다.
  2. 티켓 기반 인증Kerberos가 KDC에서 티켓을 발급하고 클라이언트와 서비스가 그 티켓으로 서로를 확인한다. 자격 증명을 매번 보내지 않아 재사용 위험이 줄어든다.
  3. 전송 보호Schannel이 TLS/SSL로 통신을 암호화하고 무결성을 검사한다. 이로써 전송 중 데이터를 가로채도 내용을 읽거나 바꿀 수 없다.

Data Deduplication과 DFS

같은 데이터 블록을 한 번만 저장해 공간을 절약하는 Data Deduplication과, 여러 파일 서버의 공유 폴더를 하나의 논리 네임스페이스로 묶는 DFS(분산 파일 시스템)를 다루는 영역이다.

#1문제 상황

파일 서버에 같은 내용의 파일이 계속 쌓이면, 볼륨은 실제 데이터보다 훨씬 빠르게 소진된다. 백업 사본, 문서 초안, 여러 사용자가 복사한 동일 첨부 파일은 서로 조금씩만 다를 뿐 대부분의 바이트가 겹치는데, 기존 NTFS 저장 방식은 파일을 통째로 각각 기록하므로 겹치는 부분도 매번 새로 저장한다. 그 결과 같은 데이터를 몇 번이고 중복 저장하게 되어 디스크를 낭비한다.

또한 공유 폴더가 서버마다 흩어져 있으면, 사용자는 어떤 파일이 어느 서버에 있는지 서버 이름과 경로를 각각 기억해야 한다. 서버 한 대가 점검으로 내려가면 그 서버 경로를 쓰던 사용자는 접속이 끊기고, 관리자는 공유 폴더를 옮길 때마다 클라이언트 설정을 다시 안내해야 한다. 개별 공유를 하나로 묶어 주는 상위 계층이 없으면 이런 경로 관리가 서버 수만큼 늘어난다.

#2핵심 질문

같은 데이터를 한 번만 저장해 공간을 아끼고, 여러 서버의 공유 폴더를 하나의 경로로 묶어 안정적으로 제공하려면 어떻게 해야 하는가?

#3동작 예시

Data Deduplication은 볼륨에 저장된 파일들을 일정한 크기의 블록(데이터 조각)으로 나누고, 서로 같은 블록을 찾아 하나만 남긴다. 남은 고유 블록은 chunk store(고유 조각 창고)에 보관하고, 각 파일은 "이 파일은 어떤 고유 블록들로 이루어졌다"는 참조 정보만 갖는다. 예를 들어 10명이 복사한 100MB 문서는 내용이 같으므로 고유 블록이 한 벌만 저장되고, 10개 파일은 같은 블록을 가리킨다.

#4동작 과정

  1. 중복 제거 대상 지정과 초기 최적화관리자가 볼륨에서 Data Deduplication을 켜면, 이후 기록되는 새 데이터는 일정 시간이 지나 최적화 작업이 돌 때 블록 단위로 나뉘어 중복이 제거된다. 이때 물리적으로 쓰이는 공간이 줄어든다.
  2. 고유 블록 저장과 참조 기록같은 블록은 chunk store(고유 조각 창고)에 한 번만 저장하고, 원래 파일은 그 블록을 가리키는 정보로 대체된다. 사용자가 파일을 읽으면 시스템이 참조를 따라 원래 내용을 다시 조립해 돌려주므로, 응용 프로그램은 중복 제거 여부를 알 필요가 없다.
  3. DFS 네임스페이스로 공유 묶기DFS Namespaces(분산 파일 시스템 네임스페이스)에서 루트를 만들고, 각 공유 폴더를 폴더 대상(folder target, 실제 데이터가 있는 서버 경로)으로 등록한다. 사용자는 하나의 네임스페이스 경로로 접근하고, 대상 서버가 내려가면 클라이언트는 다른 대상으로 자동으로 넘어가므로 경로를 바꿀 필요가 없다.

#5한 줄 요약

같은 데이터 블록을 한 번만 저장해 공간을 절약하고, 여러 서버의 공유 폴더를 하나의 논리 네임스페이스로 묶어 안정적으로 제공하는 것

파일 서버·SMB·NFS·NTFS

파일 서버가 SMB·NFS 공유 프로토콜과 NTFS 파일 시스템을 통해 클라이언트에 파일과 폴더를 제공하는 핵심 구성 요소이다.

#1문제 상황

파일을 서버 한 대에만 두고 로컬 경로로만 읽고 쓴다면, 다른 컴퓨터에 있는 사용자는 그 파일에 접근할 방법이 없다. 여러 컴퓨터가 하나의 파일을 함께 쓰려면 파일이 어디에 있고 누가 어떤 권한으로 접근하는지를 정하는 규칙이 필요한데, 이런 규칙 없는 로컬 저장만으로는 공동 작업이 불가능하다. 또한 파일을 주고받을 때 인증 없이 아무나 읽고 쓸 수 있으면, 사내 문서가 그대로 노출된다.

저장 매체를 그대로 노출하는 방식도 한계가 있다. 파일 시스템마다 파일 이름 규칙, 권한 표현, 최대 크기 같은 제약이 다르고, 네트워크로 파일을 다룰 때 이 차이를 매번 애플리케이션이 직접 처리하면 호환성과 보안을 관리하기 어려워진다. 파일 하나를 여러 클라이언트가 동시에 열 때 누가 먼저 쓰는지, 잠금은 어떻게 할지도 정해진 규약이 있어야 한다.

#2핵심 질문

네트워크 너머의 파일과 폴더를 여러 클라이언트가 안전하고 일관되게 읽고 쓰게 하려면 어떤 계층이 필요하고, 그 위에서 파일 시스템은 무엇을 담당하는가?

#3동작 예시

SMB(Server Message Block, 네트워크 파일 공유 프로토콜)는 클라이언트가 서버의 파일을 열고, 읽고, 쓰고, 닫는 요청을 네트워크로 주고받는 규약이다. 클라이언트가 공유 폴더의 파일을 열면 SMB 요청이 TCP/IP(인터넷 표준 전송 규약) 위로 서버에 도착하고, 서버는 그 요청에 담긴 사용자 자격 증명을 확인한 뒤 NTFS(윈도우의 파일 시스템)의 권한 규칙에 따라 허용 여부를 판단한다. 허용되면 서버가 파일 데이터를 응답으로 돌려준다.

#4동작 과정

  1. 공유와 프로토콜 선택관리자가 폴더를 SMB 또는 NFS(Network File System, 유닉스 계열에서 쓰는 파일 공유 프로토콜)로 공유하면, 클라이언트는 그 프로토콜로 서버에 연결한다. 이 단계에서 어떤 방식으로 파일에 접근할 수 있는지가 정해진다.
  2. 인증과 권한 확인서버가 클라이언트의 자격 증명을 검증하고, NTFS 파일 시스템의 접근 제어 규칙(누가 어떤 파일에 어떤 작업을 할 수 있는지)으로 실제 허용 여부를 판단한다. 권한이 없으면 열기 요청이 거부되어 데이터가 노출되지 않는다.
  3. 읽기·쓰기 처리허용된 요청은 서버가 파일 데이터를 읽거나 기록해 응답한다. SMB는 서명(signing, 데이터가 위변조되지 않았음을 검증하는 표시)과 암호화(전송 중 데이터를 감추는 기능)를 지원하므로, 전송 구간에서 내용이 변조되거나 그대로 노출되는 것을 막을 수 있다.

파일 서버가 SMB·NFS 같은 공유 프로토콜로 네트워크 너머의 파일 접근을 중개하고, NTFS가 그 접근을 권한 규칙으로 통제하는 것

FSRM·Folder Redirection·iSCSI

FSRM으로 공유 폴더의 쿼터·파일 차단을 관리하고, Folder Redirection으로 사용자 데이터를 서버로 모으며, iSCSI Target Server로 네트워크 블록 스토리지를 제공하는 기능 묶음이다.

#1문제 상황

파일 서버를 운영하다 보면 사용자마다 저장 용량을 얼마나 쓸지, 어떤 종류의 파일을 올릴 수 있는지 관리할 규칙이 없다. 용량 제한이 없으면 한 사용자의 대용량 파일이 볼륨을 가득 채워 다른 사용자까지 저장하지 못하게 되고, 실행 파일이나 미디어 파일이 무분별하게 쌓이면 서버 용도가 흐려진다. 이런 규칙을 사람이 일일이 점검하는 것은 현실적이지 않다.

사용자 데이터가 각자 PC의 로컬 폴더에 흩어져 있으면, PC 고장·분실 시 데이터가 사라지고 관리자는 백업 대상을 파악하기 어렵다. 또한 서버가 제공하는 저장 공간이 파일 공유 형태뿐이라면, 운영체제나 데이터베이스처럼 블록 단위 저장을 요구하는 워크로드는 별도의 물리 스토리지를 따로 붙여야 하는 부담이 있다.

#2핵심 질문

공유 폴더의 용량과 파일 종류를 자동으로 통제하고, 사용자 데이터를 서버로 모으며, 네트워크로 블록 스토리지를 제공하려면 어떤 기능들을 조합해야 하는가?

#3동작 예시

FSRM(File Server Resource Manager, 파일 서버 리소스 관리자)에서 쿼터(quota, 폴더나 볼륨에 허용되는 저장 용량 한도)를 설정하면, 사용자 저장량이 한도에 도달할 때 경고가 기록되고 초과 시 저장이 차단된다. 같은 도구에서 파일 차단(file screen) 규칙을 만들면 지정한 파일 그룹(예: 실행 파일)이 공유 폴더에 기록되는 순간 차단되고, 어떤 파일이 걸렸는지 감사 기록에 남는다.

#4동작 과정

  1. 용량·파일 종류 통제FSRM에서 볼륨이나 폴더에 쿼터와 파일 차단 규칙을 적용한다. 한도 초과나 금지 파일 기록이 자동으로 걸러지므로 관리자가 상시 감시하지 않아도 서버 용도가 유지된다.
  2. 사용자 데이터 서버 집중Folder Redirection(폴더 리다이렉션)으로 문서·바탕 화면 같은 사용자 폴더를 서버 공유 폴더로 돌린다. 사용자는 평소처럼 로컬 폴더를 쓰지만 실제 데이터는 서버에 저장되므로, PC가 바뀌어도 같은 파일을 쓰고 백업 대상이 서버 한 곳으로 모인다.
  3. 네트워크 블록 스토리지 제공iSCSI Target Server로 네트워크를 통해 접근하는 블록 스토리지 대상을 만든다. 클라이언트는 그 대상을 로컬 디스크처럼 인식해 사용할 수 있으므로, 블록 저장이 필요한 워크로드도 별도 물리 장치 없이 구성할 수 있다.

#5한 줄 요약

파일 서버에서 저장 규칙을 자동으로 강제하고, 사용자 데이터를 서버로 모으고, 네트워크로 블록 스토리지를 제공하는 기능들을 함께 갖추는 것

ReFS·Storage Migration·Storage Replica

무결성과 복원력에 강한 ReFS 파일 시스템, 서버 데이터를 이전하는 Storage Migration Service, 재해 복구를 위한 Storage Replica 복제 기술을 다룬다.

#1문제 상황

기존 NTFS는 오랫동안 쓰였지만, 대용량 데이터와 대규모 볼륨을 다루는 현대 워크로드에서는 손상 감지·복구와 확장성에 한계가 드러난다. 저장 중 데이터가 조용히 손상되어도 즉시 알기 어렵고, 문제가 발견됐을 때 볼륨 전체를 검사하고 복구하는 데 오랜 시간이 걸린다. 데이터가 커질수록 이런 검사 비용은 더 커진다.

또한 서버 하드웨어나 운영체제를 교체할 때 기존 서버의 데이터와 설정을 새 서버로 옮기는 작업은 수작업이 많아 오류와 중단 위험이 크다. 재해로 서버 한 대가 통째로 사용할 수 없게 됐을 때, 미리 준비된 다른 위치의 복제본으로 신속히 전환할 수단이 없다면 복구 시간이 길어진다.

#2핵심 질문

손상에 강하고 큰 데이터를 효율적으로 다루는 파일 시스템, 서버를 옮기는 이전 도구, 재해 복구를 위한 복제를 어떻게 갖추는가?

#3동작 예시

ReFS(Resilient File System, 복원력 있는 파일 시스템)는 데이터를 쓸 때 무결성 스트림(integrity stream, 데이터의 올바름을 검증하는 별도 정보)을 함께 기록해, 읽을 때 값이 어긋났는지 검사한다. 만약 손상이 감지되고 해당 데이터의 복사본이 다른 디스크에 남아 있으면, ReFS는 그 복사본으로 원래 데이터를 자동으로 복구한다. 손상이 조용히 남는 대신 즉시 드러나고 복구되는 방식이다.

#4동작 과정

  1. 무결성 검사와 복구ReFS가 데이터를 기록할 때 무결성 정보를 함께 저장하고, 읽을 때 검증한다. 손상이 발견되면 복사본이 있는 경우 자동으로 복구하므로, 데이터 신뢰성이 유지된다.
  2. 서버 데이터 이전Storage Migration Service가 원본 서버의 데이터·공유·설정을 조사하고 새 서버로 옮긴 뒤, 전환(cutover)으로 클라이언트 접근을 새 서버로 넘긴다. 수작업 이전보다 중단과 오류가 줄어든다.
  3. 복제로 재해 복구 구성Storage Replica로 서버 간, 또는 클러스터 간에 볼륨 단위 복제를 설정한다. 원본에 문제가 생겼을 때 복제본으로 전환할 수 있어, 서버 손실 시에도 데이터를 이어 쓸 수 있다.

Storage Spaces Direct

여러 서버의 로컬 드라이브를 소프트웨어 정의 스토리지 풀로 묶어 고가용성 공유 볼륨을 구성하는 클러스터형 스토리지 기술이다.

#1문제 상황

고가용성 공유 스토리지를 만들려면 전통적으로 SAN(여러 서버가 함께 쓰는 전용 스토리지 장치) 같은 별도 하드웨어가 필요했다. SAN은 별도 구매·배선·관리 부담이 크고, 서버와 스토리지의 확장이 따로 움직여 비용과 복잡성이 늘어난다. 서버 한 대에 직접 꽂힌 로컬 디스크만으로는 다른 서버와 공유하거나 서버 장애를 견디는 구성이 되지 않는다.

서버 여러 대의 로컬 디스크를 묶어 하나의 저장소처럼 쓰려 해도, 어느 디스크에 데이터를 두고 어디에 복사본을 남길지, 디스크가 하나 빠졌을 때 무엇으로 복구할지를 각 서버가 따로 판단하면 일관성이 깨진다. 장애를 견디면서 용량과 성능을 함께 확보하는 규칙이 필요하다.

#2핵심 질문

여러 서버에 각각 꽂힌 로컬 드라이브를 하나의 소프트웨어 정의 스토리지로 묶어, 고가용성 공유 볼륨을 어떻게 구성하는가?

#3동작 예시

Storage Spaces Direct(직접 연결 스토리지 기반 소프트웨어 정의 스토리지)는 클러스터의 여러 서버에 있는 로컬 드라이브를 하나의 스토리지 풀로 모은다. 이 풀 위에 볼륨을 만들면, 데이터는 여러 서버의 드라이브에 나뉘어 저장되고 복사본도 서로 다른 위치에 남는다. 서버 한 대가 멈춰도 다른 서버가 남은 복사본으로 그 볼륨을 계속 제공하므로, 공유 볼륨이 끊기지 않는다.

#4동작 과정

  1. 드라이브를 풀로 묶기클러스터의 여러 서버가 가진 로컬 드라이브를 하나의 스토리지 풀로 모은다. 개별 서버의 디스크가 아니라 전체가 하나의 저장 용량으로 다뤄지므로, 서버와 무관하게 용량을 확장할 수 있다.
  2. 복원력 규칙 적용볼륨을 만들 때 데이터와 복사본을 몇 개 남길지 정하는 복원력 설정을 적용한다. 이 규칙에 따라 복사본이 서로 다른 서버·드라이브에 배치되므로, 디스크나 서버 하나가 빠져도 데이터가 유지된다.
  3. 공유 볼륨으로 제공만들어진 볼륨을 클러스터의 각 서버가 동시에 접근할 수 있는 공유 볼륨(CSV) 형태로 제공하고, 서버를 추가하거나 드라이브를 교체하며 확장·복구한다. 장애가 나면 복제된 데이터를 기준으로 볼륨을 다시 정상 상태로 맞춘다.

Work Folders·Storage QoS·디스크 관리

사용자 데이터를 서버로 동기화하는 Work Folders, 가상 디스크의 성능을 제한하는 Storage QoS, 디스크와 볼륨을 관리하는 디스크 관리 기능을 다룬다.

#1문제 상황

사용자가 개인 PC와 회사 PC를 함께 쓰면, 회사 파일을 개인 기기에도 두고 쓰고 싶어 한다. 그런데 회사 데이터를 개인 기기에 그대로 복사하면 통제를 벗어나고, 개인 기기를 잃어버렸을 때 파일 유출로 이어진다. 반대로 개인 기기 접근을 막으면 사용자는 파일을 옮기기 위해 메일이나 USB 같은 우회 수단을 쓰게 된다.

서버에서 여러 가상 디스크가 동시에 돌면, 한 워크로드가 저장소 대역을 독차지해 다른 워크로드의 응답이 느려질 수 있다. 우선순위나 상한 없이 자원을 나눠 쓰면 성능이 예측되지 않는다. 또 서버에 디스크를 추가하거나 교체할 때, 디스크 초기화·파티션 방식·볼륨 확장 같은 작업을 정해진 절차 없이 하면 데이터 손실과 호환 문제가 생긴다.

#2핵심 질문

사용자 데이터를 서버 통제 아래에서 여러 기기로 동기화하고, 저장소 성능을 제한하며, 디스크와 볼륨을 안전하게 관리하려면 무엇이 필요한가?

#3동작 예시

Work Folders(작업 폴더)는 서버의 파일 공유 폴더와 사용자 기기의 로컬 폴더를 연결해, 서버에 저장된 파일을 기기로 내려받아 쓰게 한다. 사용자는 평소 파일 탐색기 폴더처럼 작업하고, 변경 사항은 서버와 동기화된다. 파일 자체는 회사 서버에 남아 있어 관리자가 접근을 통제할 수 있고, 개인 기기는 그 사본을 필요할 때 받아 쓰는 위치가 된다.

#4동작 과정

  1. 서버 데이터 동기화Work Folders 서버가 사용자별 폴더를 두고, 사용자가 등록한 기기와 파일을 주고받는다. 파일이 중앙 서버에 남으므로 기기를 늘려도 같은 데이터를 쓰고 관리자가 통제할 수 있다.
  2. 성능 한도 지정Storage QoS(저장소 서비스 품질)로 가상 디스크마다 최대 대역과 최소 보장을 설정한다. 한 워크로드가 대역을 독차지하지 못하게 막으므로, 다른 워크로드의 성능이 예측 가능해진다.
  3. 디스크와 볼륨 관리디스크 관리를 통해 새 디스크를 초기화하고 파티션 방식과 볼륨을 정하며, 필요하면 볼륨을 확장하거나 드라이브 문자·탑재 지점을 지정한다. 정해진 절차로 처리하므로 데이터 손실과 호환 문제를 줄인다.

Hyper-V 개요와 호환성

Hyper-V는 Windows Server에 내장된 하드웨어 기반 가상화 기술로, 하나의 물리 서버에서 격리된 여러 가상 머신을 실행하며 게스트 OS·세대별 호환성을 함께 따진다.

#1문제 상황

과거에는 물리 서버 한 대에 운영체제를 하나만 설치했다. 이 방식은 서버 자원을 나눠 쓰기 어려워, 남는 CPU와 메모리가 있어도 다른 서비스에 돌려줄 수 없었다. 새 서비스를 올리려면 서버를 통째로 한 대 더 사야 했고, 서로 다른 프로그램이 같은 OS 위에서 충돌하는 문제도 있었다.

이를 해결하려고 등장한 소프트웨어 가상화는 OS 위에서 또 다른 OS를 흉내내는 방식이라 느렸다. 하드웨어를 직접 제어하지 못하고 중간 계층을 거쳐야 해서 성능 손실이 컸다. 서버 한 대에서 여러 개의 격리된 환경을 돌리면서도 성능을 거의 그대로 유지하는 방법이 필요했다.

#2핵심 질문

물리 서버 한 대에서 성능 손실 없이 서로 완전히 격리된 여러 운영체제를 동시에 돌릴 수 있을까?

#3동작 예시

Windows Server에 Hyper-V 역할을 설치하면, 하이퍼바이저가 하드웨어와 운영체제 사이에 직접 자리 잡는다. 관리 운영체제(호스트 OS)는 하나의 파티션으로 올라가고, 그 위에 만든 가상 머신(VM)들은 각자 독립된 파티션에서 실행된다. 예를 들어 물리 CPU 16코어, 메모리 64GB 서버에서 VM 두 개에 코어 4개·메모리 16GB씩 할당하면, 두 VM은 서로의 존재를 모른 채 자기 몫의 하드웨어를 가진 것처럼 동작한다.

#4동작 과정

  1. 역할 설치와 하이퍼바이저 기동서버 관리자나 Install-WindowsFeature cmdlet으로 Hyper-V 역할을 설치하면, 부팅 시 하이퍼바이저가 하드웨어를 먼저 점유한다. 이때 호스트 OS 자체도 하나의 파티션으로 격리되어, VM과 같은 수준에서 관리된다.
  2. VM 생성과 하드웨어 할당가상 스위치로 네트워크를 만들고 VM에 가상 CPU·메모리·디스크를 배정한다. 세대(Generation)를 1로 하면 BIOS 기반 레거시 부팅, 2로 하면 UEFI·보안 부팅 같은 최신 보안 기능을 쓴다. 게스트 OS가 지원 목록에 있는 Windows·Linux·FreeBSD 배포판인지 확인해 세대를 맞춘다.
  3. 격리 실행과 확장각 VM은 자기 파티션에서 게스트 OS를 부팅하고, 하이퍼바이저가 하드웨어 접근을 중재한다. 호스트가 감당하는 범위 안에서 VM 수를 늘려 서버 한 대의 자원을 최대한 쓴다.

Hyper-V 계획 — 보안·GPU·백업

Hyper-V를 도입하기 전에 호스트 보안 강화, GPU 가속 방식 선택, VM 백업·복구 전략을 미리 설계하는 계획 단계다.

#1문제 상황

Hyper-V를 설치한 뒤에 보안 설정을 뒤늦게 고민하면, 이미 열려 있는 공격 경로를 하나씩 막느라 애를 먹는다. 호스트 OS에 관리 도구를 많이 올려 두면 그만큼 공격 표면이 넓어지고, 호스트가 뚫리면 그 위의 모든 VM 설정 파일과 데이터가 함께 위험해진다.

여기에 GPU 가속과 백업 방식까지 즉흥적으로 정하면 나중에 되돌리기 어렵다. 예를 들어 여러 VM이 GPU를 나눠 쓰는 방식과 특정 VM에 통째로 넘기는 방식은 지원 조건이 달라서, 배포 뒤에 바꾸려면 VM을 다시 만들어야 할 수 있다. 그래서 도입 전에 보안·가속·복구를 한꺼번에 설계해 두어야 한다.

#2핵심 질문

Hyper-V를 도입할 때 호스트 보안과 GPU 가속, 백업·복구를 어떻게 미리 정해 두어야 재작업 없이 안전하게 운영할 수 있을까?

#3동작 예시

보안 계획은 호스트, VM, 설정 파일, VM 데이터 네 가지를 각각 잠그는 체크리스트로 세운다. 예를 들어 호스트에는 필요한 관리 도구만 남겨 공격 표면을 줄이고, VM 설정 파일과 가상 디스크는 접근 권한을 최소한으로 좁힌다. GPU가 필요하면 여러 VM이 나눠 쓰는 방식(GPU 파티셔닝)과 한 VM에 물리 GPU를 전용으로 붙이는 방식(DDA) 중 워크로드에 맞는 쪽을 고른다.

#4동작 과정

  1. 호스트 보안 강화관리 운영체제에 필요한 최소 설치 옵션을 쓰고, 펌웨어와 OS를 최신으로 유지한다. 생산 워크로드를 Windows 10·11 같은 클라이언트용 Hyper-V에 올리지 않는다.
  2. 가속·격리 방식 선택GPU는 파티셔닝과 DDA(Discrete Device Assignment, 물리 장치를 VM에 통째로 넘기는 방식) 중에서 고르고, 중첩 가상화(Nested Virtualization, VM 안에서 다시 VM을 돌리는 기능)와 가상 Fibre Channel 지원 여부를 워크로드에 맞춰 정한다.
  3. 백업·복구 전략 수립VM 데이터와 설정 파일을 어떤 주기로 어디에 복제·백업할지 정하고, 복구 시나리오까지 함께 정해 둔다. 이 전략이 정해져야 장애 때 되살릴 수 있다.

Hyper-V 배포

Hyper-V 역할을 설치하고 가상 스위치·가상 머신을 만들며 VLAN·NAT 네트워크까지 구성해 실제 가상화 환경을 구축하는 절차다.

#1문제 상황

Hyper-V를 쓰기로 정했어도 실제로 역할을 올리고 VM을 띄우기까지는 단계가 많다. 네트워크를 어떻게 붙일지, VM을 몇 세대로 만들지, 저장소를 어떻게 구성할지를 각각 따로 정하다 보면 설정이 서로 어긋나 VM이 부팅되지 않는다.

특히 네트워크 구성에서 VLAN을 지정하지 않으면 VM이 엉뚱한 대역으로 트래픽을 내보내거나 격리되지 않는다. 또 여러 호스트로 VM을 옮기려면 미리 마이그레이션 설정을 해 두어야 하고, GPU·저장소 같은 물리 장치를 VM에 직접 붙이려면 조건이 까다롭다. 배포 절차를 순서대로 밟지 않으면 나중에 다시 손봐야 한다.

#2핵심 질문

Hyper-V 역할 설치부터 네트워크·저장소·VM 구성까지, VM이 정상 부팅되고 확장 가능하도록 어떻게 순서대로 배포할까?

#3동작 예시

서버 관리자나 Install-WindowsFeature cmdlet으로 Hyper-V 역할을 설치하면 관리 도구와 가상 스위치 기능이 함께 들어온다. 이어서 가상 스위치를 만들고, VM을 만들어 게스트 OS를 설치한다. 예를 들어 NAT 네트워크를 구성하면 VM들이 호스트를 거쳐 외부로 나가되 서로 격리된 사설 대역을 쓸 수 있고, VLAN을 지정하면 스위치 포트별로 트래픽을 분리할 수 있다.

#4동작 과정

  1. 역할 설치와 스위치 구성Hyper-V 역할을 설치한 뒤 가상 스위치를 만든다. VM이 내부·외부·사설 네트워크 중 어디로 나갈지 정하고, 필요하면 VLAN과 NAT 네트워크를 설정해 트래픽을 분리한다.
  2. VM 생성과 세대·저장소 설정VM을 만들고 세대(1 또는 2)와 가상 디스크를 구성한다. 세대 2는 UEFI·보안 부팅 같은 최신 보안 기능을 쓰고, 저장소 구조를 정해 가상 디스크를 배치한다.
  3. 확장·이관 준비VM 내보내기·가져오기로 옮길 수 있게 하고, 라이브 마이그레이션을 쓸 호스트를 설정한다. GPU 파티셔닝이나 DDA, 중첩 가상화가 필요하면 해당 조건을 갖춰 VM에 장치를 붙인다.

Hyper-V 역할 설치부터 네트워크·저장소·VM 구성을 순서대로 밟아, 부팅되고 확장 가능한 가상화 환경을 실제로 세우는 것

Hyper-V 관리·복제

Hyper-V Manager·PowerShell로 호스트와 VM을 관리하고, Hyper-V Replica로 다른 호스트나 클러스터에 VM을 복제해 재해 복구를 구성하는 영역이다.

#1문제 상황

VM을 띄운 뒤에는 상태를 관리하고 장애에 대비해야 한다. 한 호스트에만 VM을 두면 그 서버가 죽는 순간 서비스가 멈추고, 백업이 있어도 마지막 백업 이후의 데이터는 잃는다. 서비스 중단 시간을 줄이려면 다른 위치에 VM을 계속 복제해 두어야 한다.

관리 면에서도 문제가 있다. CPU·메모리를 어느 VM에 얼마나 줄지, 스케줄러를 어떤 방식으로 돌릴지, NUMA(여러 CPU가 메모리를 나눠 쓰는 구조)를 어떻게 맞출지를 정하지 않으면 성능이 들쭉날쭉해진다. 체크포인트·동적 메모리·프로세서 호환성 같은 기능을 언제 쓰는지도 운영 중에 판단해야 한다.

#2핵심 질문

가동 중인 VM을 다른 호스트나 클러스터로 계속 복제해 두고, 자원도 안정적으로 관리하려면 어떻게 해야 할까?

#3동작 예시

Hyper-V Replica는 한 호스트의 VM을 다른 호스트나 클러스터로 복제한다. 원본 호스트에서 복제를 켜고 대상 호스트를 지정하면, 변경분이 주기적으로 전송돼 대상 쪽에 복제본이 유지된다. 원본 서버가 죽으면 관리자가 복제본을 페일오버(failover, 대기 중이던 복제본을 실제 서비스 인스턴스로 전환하는 것)해 서비스를 이어간다.

#4동작 과정

  1. 복제 설정과 초기 전송원본 호스트나 클러스터에서 Hyper-V Replica를 켜고 대상 호스트를 지정한다. 초기 복사본을 보낸 뒤, 이후에는 바뀐 부분(변경분)만 주기적으로 전송한다.
  2. 자원·호환성 관리체크포인트로 특정 시점 상태를 남기고, CPU 자원 제어·동적 메모리·NUMA 구성을 맞춘다. 프로세서 호환성 모드를 켜면 서로 다른 CPU 세대의 호스트로도 VM을 옮길 수 있다.
  3. 페일오버와 복구원본에 장애가 나면 복제본을 페일오버해 서비스를 이어받는다. CSV(클러스터 공유 볼륨)를 여러 개 두면 복제 대상을 나눠 관리할 수 있다.

#5한 줄 요약

VM을 다른 호스트에 계속 복제하고 자원을 안정적으로 관리해, 장애가 나도 서비스를 빠르게 이어가게 하는 것

장애 조치 클러스터링

여러 서버를 하나의 클러스터로 묶어 노드 장애 시 워크로드를 다른 노드로 자동 전환해 고가용성을 제공하는 Windows Server의 핵심 기능이다.

#1문제 상황

서버 한 대에 서비스를 올리면 그 서버의 하드웨어나 OS에 문제가 생기는 순간 서비스가 멈춘다. 사람이 수동으로 다른 서버에 옮기려 해도, 어느 서버가 살아 있고 데이터가 어디 있는지 확인하는 동안 중단이 길어진다. 대기 서버를 두더라도 자동으로 넘겨주는 장치가 없으면 무용지물이다.

여러 서버가 같은 데이터를 동시에 건드리면 데이터가 깨지는 문제도 있다. 또 클러스터를 이루는 노드들이 서로 연결이 끊겼을 때 양쪽이 각자 서비스한다고 착각하면 데이터가 갈라진다. 이 두 가지 문제를 함께 다루는 고가용성 구성이 필요하다.

#2핵심 질문

여러 서버를 하나로 묶어 노드에 장애가 나도 서비스가 자동으로 다른 노드에서 이어지게 하려면 어떻게 해야 할까?

#3동작 예시

파일 서버 두 대를 장애 조치 클러스터로 묶는다고 하자. 두 노드는 공유 저장소(또는 스토리지 공간 다이렉트)에 데이터를 두고, 한 노드만 그 데이터를 활성으로 소유한다. 활성 노드에 장애가 나면 클러스터가 이를 감지해 대기 노드에서 워크로드를 자동으로 시작한다. 이때 쿼럼 위트니스(quorum witness, 클러스터가 살아 있는 편을 판정하도록 돕는 투표 장치)가 어느 쪽이 정상인지 판단해 데이터 분열을 막는다.

#4동작 과정

  1. 클러스터 구성과 검증서버 노드들을 클러스터로 묶기 전에 하드웨어 요구 사항을 확인하고 검증한다. 클러스터 계정과 저장소 연결을 준비하고, 필요하면 AD DS에 미리 클러스터 개체를 만들어 둔다.
  2. 쿼럼과 위트니스 설정쿼럼 위트니스를 배치해 노드 간 연결이 끊겨도 어느 편이 살아남을지 정한다. 이 설정이 없으면 클러스터가 판단을 못 하고 멈출 수 있다.
  3. 워크로드 배치와 자동 전환CSV(클러스터 공유 볼륨)나 스토리지 공간 다이렉트에 데이터를 두고 VM·파일 서버 같은 워크로드를 올린다. 노드에 장애가 나면 클러스터가 워크로드를 다른 노드로 자동 전환해 서비스를 이어간다.

#5한 줄 요약

여러 서버를 하나의 클러스터로 묶고 노드 장애 시 워크로드를 자동 전환해 서비스 중단을 막는 것

로컬 AI 추론

Windows Server에서 로컬 GPU 등 하드웨어를 활용해 모델 추론 엔드포인트를 분산 구성하고 운영하는 기능

모델을 각자 PC에 따로 설치하면, 컴퓨팅 성능이 제각각이라 큰 모델을 못 돌리고 관리도 흩어진다. 여러 사용자가 같은 모델 컴퓨팅을 공유하면서 요청과 출력이 어디로 가는지 조직이 직접 통제할 방법이 필요하다.

#3동작 예시

#4동작 과정

  1. 추론 엔드포인트 준비Windows Server에 모델 서버를 올려 OpenAI 호환 엔드포인트를 만든다. 모델을 어디서 받아 어떻게 적재할지, 요청과 출력이 지나는 네트워크 경로를 함께 정한다.
  2. 클라이언트 연결Visual Studio Code, GitHub Copilot CLI, Intelligent Terminal 같은 클라이언트를 서버 엔드포인트에 연결한다. 로컬 엔드포인트와 원격 엔드포인트를 모두 가리킬 수 있어 용도에 따라 나눠 쓴다.
  3. 운영과 통제진단과 부가 서비스를 붙여 상태를 점검하고, 요청·출력이 어디로 흐르는지 통제한다. 이 통제 범위가 곧 이 구성의 목적이다.

로컬 AI 추론과 지원 솔루션11-02

지원 솔루션

Windows Server 로컬 추론 엔드포인트에 연결해 사용할 수 있는 GitHub Copilot CLI, Visual Studio Code, Intelligent Terminal 등 지원 클라이언트 솔루션

#1문제 상황

기존에는 개발자가 AI 모델을 쓰려면 도구마다 별도의 클라우드 서비스에 각각 접속하고 인증 정보를 따로 관리해야 했다. 로컬 서버에서 모델을 직접 돌리더라도, 그 엔드포인트(앱이 요청을 보내는 접속 주소)에 어떤 클라이언트를 어떻게 붙이는지가 도구마다 제각각이라 설정이 흩어졌다.

데이터가 외부로 나가면 안 되는 환경에서는 클라우드 연결 방식 자체를 쓸 수 없었고, 서버 안에서 돌아가는 모델에 개발 도구를 연결하려면 도구별로 각각 방법을 찾아야 했다.

#2핵심 질문

로컬에서 돌아가는 추론 엔드포인트 하나를 여러 개발 도구가 공통으로 붙어 쓸 수 있게 하려면 어떻게 연결해야 하는가?

#3동작 예시

Windows Server 에서 추론 런타임으로 모델 엔드포인트를 띄운다. GitHub Copilot CLI 에 그 엔드포인트 주소를 지정하고, Visual Studio Code 에도 같은 주소를 설정한다. 그러면 두 도구는 클라우드가 아니라 서버 내부의 같은 엔드포인트로 요청을 보내 결과를 받는다.

#4동작 과정

  1. 엔드포인트 준비서버에서 추론 런타임을 실행해 모델 엔드포인트를 연다. 이때 도구들이 접속할 주소가 정해진다.
  2. 클라이언트 연결GitHub Copilot CLI, Visual Studio Code, Intelligent Terminal 같은 지원 클라이언트에 그 엔드포인트 주소를 설정해 같은 모델을 가리키게 한다. 도구마다 따로 클라우드에 가입할 필요가 없어진다.
  3. 요청 처리각 도구가 보낸 요청이 로컬 엔드포인트에서 추론되고, 결과가 해당 도구로 돌아온다.

#5한 줄 요약

로컬 추론 엔드포인트 하나를 여러 지원 클라이언트가 공통으로 연결해 쓰게 하는 것
