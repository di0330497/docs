1ElastiCache가 무엇이고 어디에 놓이는가이 서비스가 무엇을 대신해 주는지, 어떤 엔진과 어떤 배포 형태를 고르는지가 정해져야 이후의 모든 설계·운영 선택이 의미를 가진다.62구성 요소의 어휘 — 노드·샤드·클러스터·복제 그룹콘솔·CLI·API·문서가 모두 이 단어들로 쓰여 있어서, 이 어휘가 잡히기 전에는 생성도 확장도 장애 대응도 읽히지 않는다.73처음 만들고 접속해 보기추상 개념을 손에 잡히는 리소스로 한 번 만들어 봐야 이후의 네트워크·보안·확장 이야기가 실제 화면과 연결된다.54네트워크와 접근 경로ElastiCache 는 VPC 안에서만 닿는 서비스여서, 접속 경로를 이해하지 못하면 보안 설정도 클라이언트 설정도 시작할 수 없다.65보안 — 암호화, 인증, 권한캐시에도 실제 사용자 데이터가 들어가므로, 운영에 넘기기 전에 누가 어떻게 닿을 수 있는지를 먼저 닫아 두어야 한다.66클라이언트에서 제대로 쓰기캐시의 체감 성능은 대부분 서버가 아니라 클라이언트 설정과 캐싱 전략에서 갈린다. 이 단계 없이는 뒤의 확장·모니터링이 엉뚱한 곳을 고치게 만든다.67엔진이 제공하는 데이터 기능단순 키-값을 넘어선 기능들이 캐시를 검색·AI 워크로드까지 끌어올린다. 앞의 어휘와 클라이언트 설정이 잡힌 뒤라야 이 기능들의 제약이 이해된다.78규모 조절 — 용량 산정과 확장캐시가 실제 트래픽을 받기 시작하면 가장 먼저 부딪히는 것이 용량이다. 앞의 노드·샤드 어휘가 여기서 실제 조작으로 바뀐다.69고가용성과 내구성확장이 되어도 장애가 나면 소용없다. 복제·Multi-AZ·트랜잭션 로그가 어디까지 지켜 주는지를 알아야 백업 정책도 정해진다.510백업·마이그레이션·버전 업그레이드데이터를 옮기고 되돌리고 엔진을 올리는 일은 모두 앞의 복제·내구성 구조 위에서 벌어진다. 여기까지 와야 실제 운영 이관이 가능해진다.611파라미터·모니터링·레퍼런스만들고 확장하고 지킨 캐시를 계속 들여다보고 조율하는 단계. 지표와 파라미터를 알아야 앞 단계의 선택이 맞았는지 확인할 수 있다.8

1ElastiCache가 무엇이고 어디에 놓이는가01-01

인메모리 캐시가 푸는 문제와 ElastiCache의 역할

디스크 기반 DB 조회의 지연과 부하를 메모리에 결과를 두어 마이크로초 응답으로 해결하는 완전관리형 인메모리 캐시 서비스다.

1상대의 출발점 확인

애플리케이션이 데이터를 조회할 때마다 데이터베이스 디스크에 접근합니다. 디스크 I/O는 메모리 접근보다 수천 배 느리므로, 같은 데이터를 반복 조회할 때마다 지연이 누적되고 데이터베이스에 부하가 걸립니다.

2질문 제기

자주 쓰는 데이터를 매번 디스크까지 가서 찾아오는 지연을 없앨 수 있을까요?

3구조적 핵심 예시

사용자의 프로필 정보를 조회하는 요청이 들어올 때, 먼저 메모리에 저장된 프로필 데이터(캐시)를 확인하고, 없으면 데이터베이스에서 가져온 후 메모리에 보관합니다. 다음 조회는 메모리에서만 응답하므로 마이크로초 단위의 답변이 가능합니다.

4단계별 동작 과정

  1. 요청 수신애플리케이션에서 데이터 조회 요청이 들어옵니다.
  2. 캐시 확인ElastiCache가 메모리에 해당 데이터가 있는지 찾습니다. 있으면 즉시 반환합니다.
  3. 데이터베이스 조회 및 저장캐시에 없으면 데이터베이스에서 가져와 ElastiCache 메모리에 저장한 후 애플리케이션에 반환합니다.

5본질 요약

ElastiCache는 데이터베이스 조회 결과를 메모리에 두어 응답 시간을 마이크로초 단위로 단축하고 데이터베이스 부하를 줄이는 완전관리형 인메모리 캐시 서비스입니다.

1ElastiCache가 무엇이고 어디에 놓이는가01-02

Valkey·Redis OSS·Memcached — 엔진 세 가지와 선택 기준

자료구조·복제·영속성이 필요하면 Valkey나 Redis OSS, 단순 키-값 캐시와 멀티스레드 확장이면 Memcached를 고른다.

1상대의 출발점 확인

캐시 서비스마다 지원하는 데이터 구조와 기능이 다릅니다. 어떤 엔진은 단순 키-값만 저장하고, 어떤 엔진은 리스트, 해시, 집합처럼 복잡한 자료구조를 지원하며, 일부는 디스크에 데이터를 영속적으로 저장할 수 있습니다.

2질문 제기

캐시가 필요한 상황에서 어떤 엔진을 선택해야 데이터 구조 요구사항과 성능을 모두 만족시킬 수 있을까요?

3구조적 핵심 예시

실시간 게임 리더보드를 만들 때, Valkey나 Redis OSS는 sorted set(정렬된 집합)이라는 자료구조로 점수 기준 순위를 효율적으로 계산합니다. Memcached는 단순 키-값만 지원하므로 순위 계산을 애플리케이션 코드에서 직접 해야 하고 속도가 떨어집니다.

4단계별 동작 과정

  1. 요구사항 분석데이터 구조(단순 키-값, 리스트, 해시 등)와 영속성 필요 여부를 파악합니다.
  2. 엔진 선택자료구조나 복제·영속성이 필요하면 Valkey나 Redis OSS를 선택하고, 순수 고속 캐싱만 필요하면 Memcached를 선택합니다.
  3. 클러스터 구성선택한 엔진으로 메모리 크기와 노드 개수를 설정합니다.

샤드(노드 그룹)와 데이터 파티셔닝

샤드는 전체 키 공간의 일부를 담당하는 노드 묶음으로, 데이터를 여러 조각으로 나눠 담는 파티셔닝 단위다.

1상대의 출발점 확인

캐시를 하나의 서버에서만 운영하면, 데이터량이 증가했을 때 그 서버의 메모리 크기가 저장 가능한 데이터의 상한이 된다. 또한 읽기와 쓰기 요청이 모두 그 하나의 서버로 몰려 병목이 생긴다. 만약 데이터를 여러 서버에 나눠 저장하면서도 각 서버가 전체 데이터 중 어느 부분을 책임지는지 혼란이 없어야 한다.

2질문 제기

데이터를 여러 노드에 자동으로 분산시키면서도, 각 노드가 어떤 데이터를 담당해야 하는지 어떻게 결정할까?

3구조적 핵심 예시

샤드는 키 공간(key space)을 16,384개의 해시 슬롯으로 나누고, 각 샤드가 그 중 일부 슬롯을 담당하는 구조다. 예를 들어 샤드 3개가 있으면 샤드 1은 0~5460번, 샤드 2는 5461~10921번, 샤드 3은 10922~16383번을 각각 담당한다. 클라이언트가 key를 저장하거나 조회할 때 그 key를 CRC16 해시 함수로 해싱해 0~16383 사이의 슬롯 번호를 구하고, 그 슬롯을 담당하는 샤드로 요청을 보낸다.

4단계별 동작 과정

  1. 해시 슬롯 계산클라이언트가 key를 해시하여 0~16383 범위의 슬롯 번호를 구한다. 이는 CRC16 알고리즘(데이터에 오류가 없는지 검사하는 방식)을 key에 적용해 일관된 번호를 얻는 것이다.
  2. 슬롯-샤드 매핑구한 슬롯 번호가 어느 샤드의 범위에 속하는지 확인해 대상 샤드를 결정한다.
  3. 데이터 처리해당 샤드의 노드로 읽기 또는 쓰기 요청을 전송하고, 그 노드가 실제 데이터를 저장하거나 반환한다.

5본질 요약

클러스터는 노드들의 집합이며, cluster mode를 켜면 샤드를 여러 개 두고 끄면 샤드 하나만 쓴다.

1상대의 출발점 확인

클러스터 모드를 끄면 샤드가 1개 고정이므로, 전체 캐시 용량이 그 1개 샤드의 노드 메모리 크기로 제한된다. 저장할 데이터가 계속 증가하면 캐시 크기를 키워야 하는데, 이는 같은 샤드 내에 더 큰 노드를 쓰는 수직 확장(scale-up)만 가능하다는 뜻이다. 반면 클러스터 모드를 켜면 여러 샤드를 동시에 운영할 수 있어 데이터를 여러 노드에 파티셔닝할 수 있다.

2질문 제기

캐시 데이터가 커질 때 여러 샤드를 동시에 두면서도 각 샤드를 어떻게 관리할 수 있을까?

3구조적 핵심 예시

클러스터는 노드들의 모음이며, cluster mode 설정에 따라 내부 구조가 달라진다. Cluster mode disabled: 샤드 1개(primary + replica 노드들)로 구성되며, 예를 들어 primary 1개 + replica 2개라면 총 3개 노드가 모두 같은 데이터를 복제하고 있다. Cluster mode enabled: 여러 샤드를 동시에 두며, 각 샤드마다 primary + replica 노드들이 있다. 예를 들어 샤드 3개, 각 샤드마다 primary 1개 + replica 2개라면 총 9개 노드가 데이터를 서로 다르게 분산 저장한다.

4단계별 동작 과정

  1. 클러스터 모드 선택ElastiCache 클러스터를 생성할 때 cluster mode를 활성화할지 비활성화할지 결정한다. 이는 생성 후 변경할 수 없으므로 사전에 데이터 규모를 예상해서 선택해야 한다.
  2. 샤드 개수 지정Disabled 모드일 때는 샤드가 자동으로 1개 고정되고, enabled 모드일 때는 1~500개 범위에서 샤드 개수를 직접 지정할 수 있다.
  3. 데이터 접근 방식 결정Disabled 모드에서는 클라이언트가 primary 엔드포인트 하나로 모든 요청을 보내면 되지만, enabled 모드에서는 클라이언트가 각 key의 슬롯 번호를 계산해 올바른 샤드로 요청을 라우팅해야 한다.

복제 그룹 — 프라이머리와 리드 레플리카

복제 그룹은 쓰기를 받는 프라이머리 노드와 그 사본을 유지하며 읽기를 나눠 받는 리드 레플리카로 이뤄진 묶음이다.

1상대의 출발점 확인

캐시 노드가 하나뿐이면 그 노드에 장애가 발생했을 때 캐시 전체가 다운되어 서비스 중단이 생긴다. 또한 모든 쓰기 요청과 모든 읽기 요청을 그 하나의 노드가 처리해야 하므로, 읽기 부하가 높을 때 성능 병목이 심해진다. 이를 해결하려면 데이터를 여러 노드에 복제하면서도 일관성을 유지해야 한다.

2질문 제기

쓰기는 한 곳에서만 받으면서도 읽기는 여러 노드에서 분산시키고, 장애 시 자동으로 다른 노드로 대체할 수 있을까?

3구조적 핵심 예시

복제 그룹은 primary(주 노드)와 replica(복제 노드) 노드로 이뤄진다. Primary 노드가 쓰기 요청을 받으면 데이터를 변경한 후 그 변경 내용을 모든 replica 노드에게 동기식으로 전송한다. 예를 들어 "SET key value" 명령이 primary에 도착하면 primary가 먼저 실행한 후 replica들이 같은 명령을 실행하도록 전파하여 모든 노드의 데이터를 동기화한다. 애플리케이션은 쓰기를 primary 엔드포인트로, 읽기를 reader 엔드포인트로 보내면 읽기가 여러 replica에 자동 분산된다. Primary가 다운되면 클러스터가 이를 감지하고 replica 중 하나를 새 primary로 승격하여 서비스가 계속되게 한다.

4단계별 동작 과정

  1. 쓰기 처리애플리케이션이 primary 엔드포인트로 쓰기 요청(예: SET, DEL)을 보내면 primary 노드가 즉시 실행하고, 그 내용을 replica들에게 복제 명령으로 전송한다.
  2. 읽기 분산애플리케이션이 reader 엔드포인트로 읽기 요청(예: GET)을 보내면 로드 밸런서(load balancer)가 그 요청을 여러 replica 노드 중 하나로 자동 분산한다.
  3. 자동 장애조치Primary 노드의 헬스 체크가 실패하면 클러스터가 이를 감지하고, 기존 replica 중 하나를 자동으로 새 primary로 승격시킨다. 승격된 노드가 쓰기를 받기 시작하고, 다른 노드들이 그것을 복제하는 새로운 복제 관계가 형성된다.

엔드포인트의 종류 — 프라이머리·리더·노드·구성 엔드포인트

엔드포인트는 애플리케이션이 접속할 주소로, 쓰기용 프라이머리·읽기 분산용 리더·개별 노드용·클러스터 전체 구조를 알려주는 구성 엔드포인트로 나뉜다.

1상대의 출발점 확인

클라이언트가 각 노드의 IP와 포트를 하드코딩해서 접속했다면, 노드가 장애나 교체로 새로 시작되면 그 IP가 변할 수 있고 클라이언트 코드를 다시 수정해야 한다. 또한 클러스터 모드를 켠 후 샤드를 추가하면 새 노드들의 주소와 데이터 위치를 클라이언트가 다시 배워야 하고, 라우팅 로직을 다시 짜야 한다. 이는 클라이언트 애플리케이션 개발을 복잡하게 만든다.

2질문 제기

클라이언트가 여러 노드 중 어디로 접속해야 하고, 어느 데이터가 어느 노드에 있는지 어떻게 알 수 있을까?

3구조적 핵심 예시

엔드포인트는 하나 이상의 노드에 접속하기 위한 DNS 이름이며, 용도별로 여러 종류가 있다. Primary endpoint: 쓰기를 받는 primary 노드의 주소이며, cluster mode 활성화 여부와 관계없이 항상 제공된다. Reader endpoint: 모든 replica 노드에 대해 라운드 로빈(순서대로 번갈아) 로드 밸런싱을 하는 주소이며, replica가 존재할 때만 제공되고 읽기 전용이다. Node endpoint: 개별 노드 하나씩의 주소이며, 클라이언트가 각 노드를 직접 제어해야 할 때 사용한다. Configuration endpoint: 클러스터 전체의 토폴로지 정보(각 해시 슬롯이 어느 노드에 위치하는지)를 제공하는 특수 엔드포인트이며, cluster mode enabled 상태에서만 제공되고 클라이언트가 스마트 라우팅을 구현할 때 필요하다.

4단계별 동작 과정

  1. 쓰기 요청애플리케이션이 primary endpoint의 DNS를 해석해 primary 노드의 IP를 얻고, 쓰기 요청을 보낸다. DNS는 장애 시 새 primary 노드의 IP로 자동 갱신되므로 클라이언트 코드 변경 불필요다.
  2. 읽기 요청애플리케이션이 reader endpoint로 읽기 요청을 보내면, AWS의 로드 밸런서가 그 요청을 여러 replica 노드 중 하나로 자동 분배한다.
  3. 클라이언트 라우팅 (cluster mode enabled)클라이언트가 configuration endpoint에 접속해 각 해시 슬롯이 어느 노드에 있는지 배우고, 이후 각 요청 시 key의 슬롯을 계산하여 직접 올바른 노드로 라우팅한다. 이는 한 번의 왕복(round-trip)만 필요로 하므로 성능이 더 좋다.

캐시 엔진(Redis 또는 Memcached)의 설정을 노드마다 수동으로 관리했다면, 모든 노드에 일관성 있게 같은 설정을 적용하기 어렵고, 설정을 변경할 때마다 각 노드에 일일이 명령을 전송해야 한다. 또한 노드들이 어느 VPC에 배치될지, 누가 접속할 수 있을지, 데이터 손실 시 복구는 어떻게 할지, 상태 변화는 어떻게 알 지 등을 별도로 관리해야 한다.

2질문 제기

캐시 클러스터를 일관성 있게 설정하고, 네트워크에 배치하고, 접근을 제어하고, 데이터와 상태를 관리하려면 어떤 요소들을 어떻게 준비해야 할까?

3구조적 핵심 예시

ElastiCache 클러스터는 여러 구성 요소로 둘러싸여 있다. 파라미터 그룹(parameter group): Redis의 maxmemory-policy, timeout, appendonly 같은 설정을 템플릿으로 정의해두고, 클러스터 생성 시 이 템플릿을 지정하면 모든 노드가 자동으로 같은 설정을 받는다. 서브넷 그룹(subnet group): 클러스터의 노드들을 배치할 VPC의 어떤 서브넷들인지를 미리 지정한다. 보안 그룹(security group): 어떤 IP나 포트에서의 접속을 허용할지를 방화벽 규칙으로 정의한다. 백업(snapshot): Redis의 경우 특정 시점의 데이터 스냅샷을 S3에 저장해 나중에 복구할 수 있게 한다. 이벤트(event): 노드 부팅, 자동 장애조치, 파라미터 그룹 변경 같은 중요한 사건이 발생하면 SNS(Simple Notification Service, 메시지 전송 서비스)로 알린다.

4단계별 동작 과정

  1. 사전 설정 정의클러스터 생성 전에 파라미터 그룹에 엔진 설정을, 서브넷 그룹에 배치 위치를, 보안 그룹에 네트워크 접근 규칙을 정의한다.
  2. 클러스터 배포생성 시 위의 구성 요소들을 지정하면, 노드들이 해당 서브넷에 배치되고 파라미터가 자동 적용되며 보안 그룹이 네트워크 접근을 제어한다.
  3. 운영 중 관리백업으로 정기적 또는 수동으로 데이터를 저장하고, 이벤트 알림으로 클러스터의 상태 변화를 추적한다.

ElastiCache 용어와 콘솔·CLI·API 용어 대응

콘솔의 '샤드'가 API에서는 node group, '클러스터'가 replication group으로 불리는 식의 용어 대응을 정리한다.

1상대의 출발점 확인

AWS ElastiCache 콘솔에서는 리소스를 "샤드", "클러스터", "노드"라고 부르는데, AWS CLI나 API 문서를 보면 같은 것을 "node group", "replication group", "cache node"라고 부른다. 이 용어들이 동일한 개념인지, 다른 수준의 개념인지 명확하지 않으면 API를 호출할 때 잘못된 파라미터를 사용하거나 문서를 잘못 이해하게 된다.

2질문 제기

콘솔의 용어와 CLI/API의 용어가 다르게 나타나는 이유가 뭐고, 콘솔에서 본 리소스를 API로 정확하게 표현하려면 어떻게 매핑해야 할까?

3구조적 핵심 예시

AWS 콘솔은 사용자 편의를 위해 직관적이고 단순한 용어를 쓰지만, CLI/API는 기술적 정확성을 위해 더 세분화된 용어를 쓴다. 콘솔의 "클러스터(Cluster)"는 API에서 "replication group"이라 불린다(복제 관계 있는 노드 묶음을 강조). 콘솔의 "샤드(Shard)"는 API에서 "node group"이라 불린다(노드들이 그룹을 이룬다는 의미). 콘솔의 "노드(Node)"는 API에서 "cache node"라 불린다(ElastiCache 전용 개념임을 명시). 콘솔의 계층은 cluster > shard > node이고, API 용어는 replication group > node group > cache node다.

4단계별 동작 과정

  1. 콘솔 UI 학습ElastiCache 콘솔에서 리소스를 탐색하며 cluster 목록에서 shard를, shard 내에서 node를 확인한다.
  2. API 문서와 매핑AWS API 공식 문서(예: DescribeReplicationGroups, DescribeCacheClusters)를 읽으며 각 콘솔 용어를 API 용어로 대응시킨다.
  3. CLI/API 호출AWS CLI나 boto3 같은 SDK로 리소스를 조작할 때는 API 용어를 파라미터로 사용한다. 예: aws elasticache describe-replication-groups, describe-cache-clusters --cache-cluster-id 등.

사전 설정 — 계정, IAM 사용자, AWS CLI, VPC 준비

ElastiCache 를 쓰기 전에 AWS 계정 가입, 권한 있는 IAM 사용자 생성, AWS CLI 설치, 캐시가 들어갈 VPC 확보까지 한 번만 해두는 준비 작업.

1상대의 출발점 확인

ElastiCache를 사용하려면 AWS 계정이 있어야 하는데, root 계정으로 직접 작업하는 것은 보안상 위험하다. 따라서 권한이 제한된 IAM(Identity and Access Management, 신원 관리) 사용자를 만들어서 그 계정으로 작업해야 한다. 또한 콘솔 UI가 아니라 자동화와 스크립팅을 위해 로컬 머신에 AWS CLI를 설치하고 인증 정보를 설정해야 한다. 마지막으로 캐시가 배치될 VPC와 그 내의 서브넷, 보안 그룹을 미리 준비해야 한다.

2질문 제기

ElastiCache를 실제로 만들고 조작하기 위해 먼저 갖춰야 할 기초 환경이 뭘까?

3구조적 핵심 예시

사전 설정은 일회성 준비 작업들의 모음이다. (1) AWS 계정 가입: AWS 웹사이트에서 신용카드를 등록하고 계정을 만든다. (2) IAM 사용자 생성: AWS 콘솔의 IAM 서비스에서 새 사용자를 만들고 "AmazonElastiCacheFullAccess" 권한을 부여한다. (3) 액세스 키 발급: 그 사용자의 액세스 키 ID와 시크릿 액세스 키를 발급받는다. (4) AWS CLI 설치: 로컬 머신에 AWS CLI를 설치하고, aws configure 명령으로 위의 액세스 키를 입력해 인증 정보를 저장한다. (5) VPC 준비: ElastiCache 클러스터가 배치될 VPC를 생성하거나 기본 VPC를 사용하고, 그 VPC 내의 서브넷 2개 이상을 확인한다. (6) 보안 그룹 생성: 캐시 포트(기본 6379)로의 접속을 허용하는 보안 그룹을 미리 만든다.

4단계별 동작 과정

  1. AWS 계정 및 권한 설정AWS에 가입하고 IAM 사용자를 만든 뒤 ElastiCache, EC2, VPC 관련 권한을 부여한다. Root 계정은 이후 사용하지 않는다.
  2. 로컬 개발 환경 준비로컬 머신에 AWS CLI를 설치하고, aws configure로 위의 IAM 사용자 액세스 키와 기본 AWS 리전(예: us-east-1)을 입력한다. 이로부터 AWS CLI는 모든 명령을 해당 계정과 리전으로 실행한다.
  3. 네트워크 리소스 확인ElastiCache 클러스터가 들어갈 VPC를 정하거나 생성하고, 그 VPC 내의 2개 이상 서브넷과 캐시 포트로의 접속을 허용하는 보안 그룹을 준비한다. 이 정보는 클러스터 생성 시 필수이다.

VPC 안의 ElastiCache와 접근 패턴

ElastiCache 캐시는 내 VPC 안 사설 IP로만 노출되며, 같은 VPC의 EC2·다른 VPC·온프레미스에서 각각 어떤 경로로 접근하는지가 접근 패턴이다.

1상대의 출발점 확인

캐시는 VPC 밖에 노출되면 보안 위험이 크므로 VPC 안에만 놔둡니다. 하지만 VPC 내에만 노출되면 같은 VPC의 리소스에서만 접근할 수 있고, 다른 VPC나 온프레미스 데이터센터에서 접근하는 경로가 복잡하거나 불가능해집니다.

2질문 제기

ElastiCache가 VPC 내 사설 IP에만 노출될 때, 같은 VPC, 다른 VPC, 온프레미스에서 각각 어떻게 접근할까요?

3구조적 핵심 예시

VPC-A의 EC2가 VPC-A 내 ElastiCache에 접근하려면 같은 네트워크이므로 사설 IP로 직접 통신합니다. VPC-B의 리소스가 접근하려면 VPC 피어링(두 VPC를 직접 연결) 또는 Transit Gateway(다른 네트워크들을 연결하는 중앙 허브)를 경유합니다. 온프레미스에서는 VPN 또는 Direct Connect(전용 네트워크 회선)를 거쳐 접근합니다.

4단계별 동작 과정

  1. 같은 VPC 접근클라이언트(EC2 등)가 캐시 사설 IP에 직접 연결, 보안 그룹으로 인입 트래픽 제어
  2. 다른 VPC 접근VPC 피어링 또는 Transit Gateway를 거쳐 네트워크 경로 설정 후 캐시 사설 IP에 도달
  3. 온프레미스 접근VPN/Direct Connect로 AWS VPC와 온프레미스를 연결, 그 경로를 통해 캐시 사설 IP 접근

서브넷과 서브넷 그룹, 그리고 IP 주소 용량

서브넷 그룹은 캐시 노드를 배치할 서브넷들의 묶음이며, 그 서브넷에 남은 IP 여유가 스케일링·장애 복구 성공 여부를 좌우한다.

1상대의 출발점 확인

VPC 안에서 캐시 노드를 어디에 배치할지, 몇 개의 서브넷에 분산할지 정하지 않으면 안 됩니다. IP 주소가 부족하면 스케일링(노드 추가)이나 장애 복구 시 새 노드를 배치할 수 없습니다.

2질문 제기

캐시 노드가 배치될 서브넷들을 미리 정해두고, 그 서브넷에 남은 IP가 충분할까요?

3구조적 핵심 예시

서브넷 그룹은 VPC 내 여러 서브넷을 하나의 묶음으로 등록하는 것입니다. 예를 들어 "cache-subnet-group"이라 이름 붙이고 서브넷-A, 서브넷-B, 서브넷-C를 포함시키면, 클러스터를 만들 때 그 그룹을 선택합니다. AWS는 자동으로 노드를 여러 서브넷에 분산시키는데, 각 서브넷에 남은 가용 IP가 스케일링·복구 성공 여부를 결정합니다.

4단계별 동작 과정

  1. 서브넷 그룹 정의VPC 내 여러 서브넷(보통 가용 영역마다 하나씩)을 묶어 서브넷 그룹 생성
  2. IP 용량 확인각 서브넷의 가용 IP 수를 확인해서, 현재 노드 수 + 장기간 스케일 여유를 고려
  3. 부족 시 조치만약 서브넷 IP가 부족하면, 새 서브넷을 서브넷 그룹에 추가하거나 기존 서브넷의 IP 범위를 확장

2질문 제기

3구조적 핵심 예시

클러스터 생성 시 "네트워크 유형" 옵션에서 IPv4(예: 10.0.1.50), IPv6(예: 2600:abcd::1), 또는 듀얼 스택(둘 다)을 선택합니다. 선택한 유형에 따라 VPC 내 엔드포인트가 해당 주소 체계로 노출됩니다.

  2. 네트워크 유형 선택클러스터 생성 폼에서 적절한 네트워크 유형 지정

1상대의 출발점 확인

기존에는 Memcached를 쓸 때 각 노드(서버)의 IP 주소와 포트를 클라이언트 코드에 직접 입력했다. 예를 들어 "192.168.1.1:11211, 192.168.1.2:11211, 192.168.1.3:11211" 이렇게 고정값으로 넣어야 했다.

한계는 노드가 추가되거나 제거되면 클라이언트 코드를 수정해야 한다는 것이다. 운영 중에 캐시 노드를 늘리려면 배포를 다시 해야 하고, 노드가 장애로 내려갔다가 복구되어도 수동으로 설정을 갱신해야 했다.

2질문 제기

클라이언트가 계속 모든 노드 주소를 알고 있어야 하는데, 노드가 변할 때마다 클라이언트 설정을 일일이 바꿀 수 있는 방법이 없을까?

3구조적 핵심 예시

Auto Discovery는 "설정 엔드포인트"라는 고정된 주소 하나를 놓고, 클라이언트가 처음 그 주소로 물어본다. 그러면 설정 엔드포인트가 "현재 살아있는 노드는 A, B, C입니다"라고 답해준다. 그 다음부터 클라이언트는 A, B, C로 요청을 보낸다. 나중에 D 노드가 추가되면, 클라이언트가 설정 엔드포인트에 다시 물어봤을 때 "이제 A, B, C, D입니다"라고 최신 목록을 받는다. 클라이언트 코드는 설정 엔드포인트만 알면 되고, 뒤의 노드 변화는 자동으로 따라간다.

4단계별 동작 과정

  1. 클라이언트 시작클라이언트가 설정 엔드포인트(Configuration Endpoint, 한 주소와 포트)에 연결하고 "지금 어떤 노드들이 있어?"라고 요청한다.
  2. 노드 목록 조회설정 엔드포인트가 현재 클러스터의 모든 활성 노드 목록(IP와 포트)을 돌려준다. 이 목록을 클라이언트가 메모리에 저장한다.
  3. 실제 캐시 접근 및 주기적 갱신클라이언트는 받은 노드 목록으로 직접 데이터를 조회하거나 저장하고, 주기적으로 설정 엔드포인트를 다시 물어서 노드 목록이 바뀌었는지 확인한다.

3구조적 핵심 예시

PrivateLink 인터페이스 엔드포인트는 VPC 내부에 가상의 대사관을 만드는 것과 같다. 클라이언트가 VPC 내부의 이 대사관 주소로 요청을 보내면, AWS 내부 네트워크를 통해 자동으로 elasticache.us-east-1.amazonaws.com으로 전달된다. 트래픽이 인터넷 게이트웨이나 NAT를 거치지 않는다.

  1. 인터페이스 엔드포인트 생성AWS 콘솔이나 CloudFormation으로 VPC 내에 ElastiCache용 PrivateLink 엔드포인트를 만든다. 이 엔드포인트는 VPC 내부의 비공개 IP 주소(예: 10.0.1.100)를 할당받는다.
  2. DNS 또는 IP로 접근클라이언트 코드에서 공개 ElastiCache API 엔드포인트 대신 PrivateLink 엔드포인트의 IP 주소나 DNS 이름을 사용한다. 같은 VPC 내의 EC2, Lambda 등에서 이 주소로 API를 호출한다.
  3. 연결 문제 해결연결이 안 되면 보안 그룹(Security Group)의 인바운드 규칙, 라우팅 테이블, 엔드포인트 정책(Resource Policy)을 점검한다. 특히 포트 443(HTTPS)이 열려 있는지, 엔드포인트가 속한 서브넷의 인터넷 연결 설정이 제대로 되어 있는지 확인한다.

5단계 보안 — 암호화, 인증, 권한

클라이언트와 캐시 사이를 오가는 데이터를 TLS로 감싸 네트워크 도청을 막는 기능으로, 켜면 클라이언트도 TLS 모드로 접속해야 한다.

1상대의 출발점 확인

Memcached와 Redis는 기본적으로 암호화 없이 평문(Plain Text)으로 데이터를 주고받는다. 클라이언트에서 "user_id:12345" 같은 데이터를 캐시에 저장하면, 네트워크에서 그 데이터를 그대로 볼 수 있다.

한계는 VPC 내부라고 해도, 권한 없는 EC2 인스턴스나 같은 네트워크의 공격자가 트래픽을 가로채고 캐시된 민감한 데이터(세션 토큰, API 키, 개인정보 등)를 읽을 수 있다는 것이다.

2질문 제기

클라이언트와 캐시 사이의 통신을 암호화해서 네트워크 도청을 막을 수 있을까?

3구조적 핵심 예시

TLS 암호화를 켜면, 클라이언트는 캐시 노드와 TLS 핸드셰이크를 먼저 수행해서 암호화된 채널을 만든다. 그 다음부터의 모든 통신("get key", "user_id:12345" 등)이 암호화 상태로 전송되고, 수신 쪽에서 복호화한다. 네트워크에서는 암호화된 바이너리만 보인다.

4단계별 동작 과정

  1. TLS 활성화ElastiCache 클러스터 또는 노드의 설정에서 "In-Transit Encryption"을 활성화한다. 캐시 노드가 TLS 서버로 작동하기 시작한다.

  3. 암호화된 통신연결이 확립되면, 모든 get/set 명령과 응답이 TLS로 감싼 상태로 전송된다. 평문으로는 절대 노출되지 않는다.

1상대의 출발점 확인

ElastiCache는 메모리 기반 데이터베이스지만, 클러스터 스냅샷(백업)을 S3에 저장하고, RDB(Redis Disk 백업)가 활성화되면 주기적으로 디스크에 쓴다. 이 경우 디스크나 S3에 평문 데이터가 저장될 수 있다.

한계는 저장소에 암호화가 없으면 백업 파일이 유출되거나 디스크가 도난당할 때 민감한 데이터가 노출된다는 것이다. 또한 암호화 키를 AWS가 관리하면 회사의 보안 정책상 키 통제권이 없을 수 있다.

2질문 제기

3구조적 핵심 예시

At-Rest Encryption을 켜면, ElastiCache가 데이터를 저장하기 전에 자동으로 암호화한다. KMS(Key Management Service)라는 AWS 암호화 서비스를 쓰는데, AWS 관리 키(aws/elasticache) 대신 "고객 관리 키(Customer-Managed Key)"를 지정할 수 있다. 고객 관리 키는 회사가 AWS KMS 콘솔에서 생성하고 통제하는 키로, 필요하면 키 접근을 제한하거나 감사 로그를 남길 수 있다.

4단계별 동작 과정

  1. KMS 고객 관리 키 생성AWS KMS 콘솔에서 대칭 암호화 키를 생성한다. 이 키는 회사만 관리 권한을 가지며, IAM 정책으로 누가 이 키를 쓸 수 있는지 제어한다.
  2. At-Rest Encryption 활성화ElastiCache 클러스터 생성 또는 수정 시 "At-Rest Encryption" 옵션을 켜고, 생성한 고객 관리 키를 지정한다.
  3. 자동 암호화 및 복호화이후 모든 데이터(메모리의 스냅샷, RDB 파일)가 저장될 때 자동으로 이 KMS 키로 암호화되고, 클라이언트가 읽을 때 자동으로 복호화된다. 애플리케이션은 암호화/복호화 과정을 신경 쓸 필요가 없다.

1상대의 출발점 확인

Memcached와 Redis는 기본적으로 인증 없이 네트워크만 연결되면 누구나 데이터에 접근할 수 있다. VPC 내부라고 가정하면, 같은 VPC의 어떤 EC2 인스턴스라도 캐시에 연결할 수 있다.

한계는 마이크로서비스 환경에서 특정 애플리케이션만 캐시에 접근하고 다른 애플리케이션은 차단하고 싶을 수 있다는 것이다. 하지만 인증이 없으면 이를 보장할 수 없다.

2질문 제기

캐시에 접근하기 전에 클라이언트가 올바른 암호를 제출하도록 강제할 수 있을까?

3구조적 핵심 예시

AUTH 토큰은 간단한 암호 문자열(예: "aB12!@cD34EfGhI5JkLmN6opqRst7uVwxYz")이다. ElastiCache에서 토큰을 설정하면, 클라이언트가 처음 접속할 때 이 토큰을 제출해야 한다. 토큰이 맞으면 접속이 허용되고, 틀리면 거부된다.

4단계별 동작 과정

  1. AUTH 토큰 설정ElastiCache 클러스터 또는 Replication Group(Redis) 또는 Parameter Group(Memcached) 설정에서 AUTH 토큰을 입력한다. 일반적으로 16자 이상의 무작위 문자열을 사용한다.
  2. 클라이언트 토큰 제출클라이언트 라이브러리에서 AUTH 토큰을 설정한다(예: Java에서 "new MemcachedClient(addr, token)"). 클라이언트가 캐시에 연결할 때 이 토큰을 함께 보낸다.
  3. 인증 검증캐시가 토큰을 검증한다. 일치하면 모든 명령을 실행 허용하고, 불일치하면 "AUTH failed" 에러를 돌려준다.

1상대의 출발점 확인

AUTH 토큰은 하나의 암호만 지원한다. 모든 클라이언트(웹 서버, 배치 작업, 모니터링 도구)가 같은 토큰을 써야 한다. 따라서 모든 클라이언트가 같은 권한을 가지며, 특정 클라이언트가 특정 키만 읽게 하거나 특정 명령만 쓰게 할 수 없다.

한계는 한 클라이언트가 토큰을 유출하면 모든 클라이언트의 접근이 위험해진다는 것이다. 또한 장기간 같은 토큰을 쓰면 보안 위험이 증가하며, 토큰을 수동으로 바꾸는 것은 번거롭고 실수하기 쉽다.

2질문 제기

사용자마다 다른 명령과 키에만 접근하게 제한하고, 토큰을 자동으로 주기적으로 바꿀 수 있을까?

3구조적 핵심 예시

RBAC를 쓰면, ElastiCache 내에 여러 사용자 계정을 만들고 각각 다른 권한을 부여한다. 예를 들어 웹 서버는 "app_user"(GET/SET 명령만, "session:*" 키만 접근), 배치 작업은 "batch_user"(DEL 명령 포함, "batch:*" 키만 접근), 모니터링은 "monitor_user"(INFO 명령만 실행)처럼 분리한다. 각 클라이언트는 자신의 사용자 계정과 암호로 로그인한다. AWS Secrets Manager를 연동하면, 각 사용자의 암호를 30일마다 자동으로 바꾸는 것도 가능하다.

4단계별 동작 과정

  1. 사용자와 권한 정의ElastiCache (Redis 6.0+)에서 새 사용자 계정을 만든다. 각 사용자마다 실행 가능한 명령(GET, SET, DEL, INFO 등)과 접근 가능한 키 패턴(예: "session:*", "cache:*")을 ACL(Access Control List)로 정의한다.
  2. 사용자 그룹화 및 정책 적용비슷한 권한을 가진 사용자들을 "사용자 그룹"으로 묶는다(선택사항). 각 클라이언트는 자신의 사용자 계정과 암호를 받는다.
  3. 자동 암호 회전 설정AWS Secrets Manager에서 ElastiCache 인증 정보를 저장하고 자동 회전을 설정한다. 예를 들어 30일마다 각 사용자의 암호를 새로 생성하고, Secrets Manager에 저장된 값을 자동으로 업데이트한다. 클라이언트는 Secrets Manager에서 최신 암호를 읽어서 사용한다.

4단계별 동작 과정

  3. 테스트 클러스터에서 검증배포 전에 스테이징 ElastiCache 클러스터에서 앱을 실행해 실제로 모든 명령이 작동하는지 확인한다.

캐싱 전략 — lazy loading, write-through, TTL

캐시에 데이터를 언제 채울지(요청 시점 vs 쓰기 시점)와 언제 버릴지(TTL)를 정하는 기본 설계 패턴이다.

1상대의 출발점 확인

캐시를 아무렇게나 쓰면 데이터가 일관성을 잃거나 오래된 값을 계속 반환할 수 있다. 캐시에 언제 데이터를 채울지, 언제 버릴지, 데이터가 정합성을 잃지 않으려면 어떻게 관리할지 정하는 규칙이 없으면 운영이 복잡해진다.

2질문 제기

데이터가 정확성을 잃지 않으면서 캐시를 효과적으로 활용하려면 언제 데이터를 넣고 빼야 할까?

3구조적 핵심 예시

Lazy Loading에서는 요청이 들어올 때만 캐시를 확인한다. 없으면 데이터베이스에서 읽어 캐시에 넣는다. Write-Through에서는 데이터를 쓸 때마다 동시에 캐시도 갱신한다. TTL(유효 기간)을 설정하면 일정 시간 후 자동으로 캐시에서 지워진다.

4단계별 동작 과정

  1. Lazy Loading 적용요청이 들어오면 먼저 캐시에서 찾는다. 없으면(캐시 미스) 데이터베이스에 쿼리하고 그 결과를 캐시에 저장한다. 다음 요청부터는 캐시에서 빠르게 반환된다.
  2. Write-Through 적용데이터를 쓸 때 캐시도 동시에 갱신한다. 읽기는 항상 최신 데이터를 얻지만, 쓰기 작업이 약간 느려진다.
  3. TTL로 만료 관리모든 캐시 아이템에 유효 기간을 설정해, 일정 시간 후 자동으로 삭제된다. 이렇게 하면 오래된 데이터가 계속 남아있지 않는다.

1상대의 출발점 확인

2질문 제기

  2. 토폴로지 탐색 활성화클라이언트가 주기적으로(보통 60초마다) CLUSTER NODES 명령이나 관리 API를 호출해 클러스터의 노드 목록과 슬롯 배치를 확인한다.
  3. 지수 백오프로 재시도토폴로지 갱신 중 실패하면 지수 백오프(처음엔 짧게, 실패할수록 대기 시간을 늘림)로 재시도해 클라이언트 부담을 줄인다.

  1. 해시와 배치클라이언트가 해시 함수로 키와 노드를 같은 범위의 숫자로 변환하고, 원형 공간에 배치한다.
  2. 키의 노드 결정키를 시계방향으로 탐색해 처음 만나는 노드를 찾고, 그 노드를 키의 저장소로 지정한다.

JSON 데이터 타입과 JSON 명령

JSON 문서를 통째로 문자열로 다루지 않고 경로 단위로 저장·조회·수정하는 네이티브 데이터 타입과 JSON.SET/GET 등 전용 명령이다.

1상대의 출발점 확인

기존에는 Redis에서 JSON 데이터를 저장하려면 전체 JSON 문서를 하나의 문자열 값으로 저장해야 했다. 특정 필드만 수정하려면 전체 문서를 꺼내 파싱하고, 해당 필드를 수정한 후 다시 저장하는 과정을 거쳐야 했으므로, 부분 조회나 부분 수정이 비효율적이었다.

2질문 제기

JSON 문서의 특정 경로만 효율적으로 저장하고 조회하고 수정할 수 있을까?

3구조적 핵심 예시

4단계별 동작 과정

2질문 제기

3구조적 핵심 예시

서버리스 캐시는 트래픽 패턴을 실시간으로 감시하다가, 요청이 많아지면 ECPU(탄력적 캐시 처리 단위)와 메모리 용량을 자동으로 증가시킵니다. 예를 들어 오전 10시에 요청량이 5배 급증하면, 캐시가 자동으로 메모리 스케일링에 들어갑니다.

4단계별 동작 과정

  1. 트래픽 모니터링CloudWatch 지표를 통해 초당 요청 수와 메모리 사용률을 실시간으로 확인합니다.
  2. 임계값 도달 시 자동 확장정의된 상한(예: ECPU 한도 100)에 도달하기 전에 미리 스케일링하는 프리스케일링이 작동합니다.
  3. 트래픽 감소 시 자동 축소요청이 줄어들면 불필요한 용량을 자동으로 반환해 비용을 절감합니다.

3구조적 핵심 예시

온라인 리샤딩(Online Resharding)을 사용하면, 기존 클러스터가 계속 요청을 받으면서 백그라운드에서 데이터를 새 노드로 이동합니다. 예를 들어 3개 샤드(각각 파티션)에서 4개 샤드로 확장할 때, 클라이언트는 평상시처럼 캐시에 접근하고, 데이터 재분배는 눈에 띄지 않게 진행됩니다.

4단계별 동작 과정

  1. 수직 확장기존 노드 타입을 더 큰 것으로 변경합니다(예: cache.r6g.large → cache.r6g.xlarge). 이 작업 중에도 기존 연결은 유지됩니다.
  2. 수평 확장샤드 개수를 늘립니다(예: 3개에서 4개로). 각 샤드의 키들이 새로운 배치로 재배분되고, 리샤딩이 진행되는 동안 캐시는 정상 작동합니다.
  3. 온라인 리샤딩위 두 작업이 백그라운드에서 병렬로 수행되며, 서비스 중단 시간은 0에 가깝습니다.

2질문 제기

3구조적 핵심 예시

  1. 핫 데이터 식별최근 N일간 접근했던 데이터를 메모리에 유지합니다.
  2. 콜드 데이터 이동접근이 없었던 데이터를 SSD로 내려 보냅니다.
  3. 접근 시 자동 복구콜드 데이터에 접근하면 즉시 메모리로 끌어올려 성능을 유지합니다.

프라이머리 노드가 죽으면 다른 가용영역의 복제본을 자동으로 승격시켜 다운타임을 최소화하는 기능이다.

1상대의 출발점 확인

단일 가용영역(AZ)에 캐시 클러스터를 두면, 노드의 네트워크 장애나 하드웨어 고장 시 캐시를 전부 다시 따뜻하게 데워야 하거나 복구를 기다려야 합니다. 그 사이에 캐시 미스로 인한 지연과 데이터베이스 부하가 급증합니다.

2질문 제기

프라이머리 노드가 장애를 일으키면 이미 데이터를 받아둔 다른 가용영역의 복제본을 즉시 프라이머리로 전환할 수 있을까요?

3구조적 핵심 예시

프라이머리-레플리카 구조에서 프라이머리는 쓰기를 받고 여러 AZ의 레플리카들로 복제하고 있습니다. 프라이머리가 응답 불능이 되면, 이미 최신 데이터를 가진 다른 AZ의 레플리카 중 하나가 즉시 새로운 프라이머리로 승격되고 쓰기를 받기 시작합니다.

4단계별 동작 과정

  1. 정상 상태 데이터 복제프라이머리 노드가 들어오는 쓰기를 메모리에 적용한 후, 다른 AZ에 있는 모든 레플리카 노드로 그 변경을 전파합니다.
  2. 장애 감지ElastiCache의 헬스 체크(정기적 핑)가 프라이머리 노드의 응답 실패를 감지하면, 클러스터 상태를 "장애" 상태로 표시합니다.
  3. 자동 승격즉시 레플리카 중 하나를 새 프라이머리로 선택해 승격시키고, 애플리케이션 연결은 자동으로 그 새 프라이머리로 리다이렉트됩니다.

글로벌 데이터스토어로 리전 간 복제

한 리전의 클러스터를 다른 리전으로 자동 복제해 지역 장애 대비와 저지연 읽기를 제공하는 기능이다.

1상대의 출발점 확인

한 AWS 리전의 캐시 클러스터는 그 리전 내에만 존재하므로, 다른 리전의 애플리케이션이 데이터에 접근하려면 네트워크를 건너서 지연이 발생합니다. 리전 간 거리가 멀수록 지연은 수십~수백 밀리초까지 증가합니다.

2질문 제기

여러 리전에 분산된 애플리케이션이 모두 저지연으로 같은 캐시 데이터에 접근할 수 있을까요?

3구조적 핵심 예시

글로벌 데이터스토어는 한 리전(프라이머리)의 캐시를 마스터로 삼고, 다른 리전들(세컨더리)로 그 데이터를 자동 복제합니다. 각 리전의 애플리케이션은 로컬 캐시에서 읽고, 쓰기는 프라이머리 리전으로만 전송되어 일관성을 유지합니다.

4단계별 동작 과정

  1. 프라이머리에서 쓰기한 리전(프라이머리)의 클러스터에만 쓰기가 들어옵니다. 이 쓰기는 메모리에 즉시 적용됩니다.
  2. 리전 간 복제쓰기 직후 프라이머리는 그 변경을 모든 세컨더리 리전으로 비동기 전파합니다. 네트워크 지연에도 불구하고 곧 각 세컨더리에 도착합니다.
  3. 세컨더리에서 읽기각 세컨더리 리전의 애플리케이션은 로컬 캐시에서 읽기만 수행하므로 극저지연으로 데이터를 얻습니다.

5본질 요약

한 프라이머리 리전의 캐시를 여러 세컨더리 리전으로 자동 동기화해, 각 리전의 애플리케이션이 로컬 캐시에서 저지연 읽기를 하고 동시에 리전 장애 시 다른 리전으로 장애 조치할 수 있는 글로벌 캐시 구조

리전·AZ 배치 선택과 로컬 존·Outposts

캐시를 어느 리전·가용영역에 둘지, 나아가 로컬 존이나 온프레미스 Outposts에 둘지 고르는 배치 전략이다.

1상대의 출발점 확인

캐시 클러스터를 만들 때 기본적으로 AWS 리전(지역)과 그 내부의 가용영역(AZ, 물리 데이터센터)을 선택합니다. 하지만 극저지연이 필요하거나 온프레미스 인프라와 통합해야 하는 경우, 이 기본 선택만으로는 부족할 수 있습니다.

2질문 제기

캐시를 어느 리전·AZ에, 나아가 로컬 존이나 온프레미스 Outposts에 배치해야 지연을 최소화하고 고가용성을 확보할 수 있을까요?

3구조적 핵심 예시

리전은 us-east-1 같은 지리적 지역이고, AZ는 그 지역 내 물리적 데이터센터(us-east-1a, us-east-1b 등)입니다. 여러 AZ에 노드를 분산하면 한 데이터센터의 장애에도 서비스가 지속됩니다. 필요하면 로컬 존(극저지연용)이나 Outposts(고객 온프레미스 데이터센터)에도 노드를 배치할 수 있습니다.

4단계별 동작 과정

  1. 리전 선택사용자와 가까운 리전을 고르거나(지연 최소화), 규제상 데이터 거주 요건을 만족하는 리전을 선택합니다.
  2. AZ 분산선택한 리전 내에서 여러 AZ에 노드를 배치해, 한 데이터센터 장애 시에도 다른 AZ의 레플리카가 살아 있도록 합니다.
  3. 로컬 존·Outposts 추가극저지연이 필수이거나 온프레미스 시스템과 일관성을 원하면, AWS 로컬 존이나 고객 Outposts에도 노드를 배치합니다.

5본질 요약

리전, 가용영역, 로컬 존, Outposts 중에서 적절한 배치 조합을 선택해 지연을 최소화하고 고가용성을 확보하는 캐시 인프라 배치 전략

Durability — 동기·비동기 쓰기와 Multi-AZ 트랜잭션 로그

쓰기를 여러 AZ의 트랜잭션 로그에 기록해 노드가 죽어도 데이터가 사라지지 않게 하는 내구성 옵션이다.

1상대의 출발점 확인

메모리 캐시는 기본적으로 휘발성이라, 노드가 전원 꺼짐이나 충돌로 죽으면 메모리의 모든 데이터가 사라집니다. 일반 캐시는 이것을 감수하지만, 어떤 애플리케이션은 캐시 데이터 손실을 용인할 수 없습니다.

2질문 제기

캐시 노드가 장애로 재시작되어도 데이터 손실 없이 복구할 수 있을까요?

3구조적 핵심 예시

Durability는 쓰기가 들어올 때마다 프라이머리 노드가 메모리에 쓴 직후, 그 쓰기를 여러 AZ의 디스크 기반 트랜잭션 로그(on-disk 저장소)에도 기록하는 방식입니다. 노드 재시작 시 메모리는 이 로그에서 데이터를 읽어 복구합니다.

4단계별 동작 과정

  1. 쓰기 수신 및 메모리 적용클라이언트의 쓰기가 프라이머리 노드에 도착하면, 즉시 메모리에 적용됩니다.
  2. 트랜잭션 로그에 기록메모리 쓰기 후, 그 변경을 여러 AZ의 디스크 로그에 동기 또는 비동기로 기록합니다. 동기 쓰기는 로그 기록 완료를 기다리고, 비동기는 기다리지 않습니다.
  3. 장애 복구노드가 재시작되면, 메모리를 로그에서 읽어 Durability가 켜진 마지막 상태로 데이터를 복구합니다.

5본질 요약

메모리에 쓴 데이터를 여러 AZ의 디스크 트랜잭션 로그에도 기록해, 노드 재시작 후에도 데이터 손실 없이 메모리를 복구할 수 있는 내구성 옵션

Durability의 일관성·장애 시나리오·제한과 모니터링

내구성을 켰을 때 읽기 일관성이 어떻게 보장되고 장애 시 무슨 일이 벌어지며 어떤 제한과 지표를 봐야 하는지다.

1상대의 출발점 확인

Durability를 켜면 내구성이 높아지지만, 각 쓰기마다 여러 AZ의 로그에 기록해야 하므로 쓰기 지연이 증가합니다. 또한 메모리와 디스크 로그 사이의 불일치, 노드 재시작 시의 동작, 리소스 소비 등 운영상 고려사항이 생깁니다.

2질문 제기

Durability를 켰을 때 읽기 쓰기의 일관성은 어떻게 보장되고, 장애 상황에서는 어떤 일이 벌어지며, 어떤 제한을 마주하고 모니터링해야 할까요?

3구조적 핵심 예시

Durability가 켜진 클러스터에서 읽기는 항상 메모리에서 이뤄져 최신 데이터를 반영하고, 쓰기는 메모리와 로그에 동시 기록되므로 지연이 증가합니다. 노드 재시작 시에도 로그에서 전체 데이터를 복구하므로 데이터 일관성은 보장되지만, 그 복구 시간 동안은 캐시가 응답할 수 없습니다.

4단계별 동작 과정

  1. 일관성 보장읽기는 항상 메모리의 최신 상태를 반영하고, 쓰기는 메모리와 여러 AZ의 로그에 동기/비동기로 기록되므로, 메모리 상태와 로그 상태 사이의 불일치는 발생하지 않습니다.
  2. 장애 복구 및 불가용 기간노드가 장애로 재시작되면, 메모리를 로그에서 읽어 복구하는 동안 캐시는 요청에 응답할 수 없습니다. 데이터 크기에 따라 복구에 수초~수분이 걸릴 수 있습니다.
  3. 리소스 모니터링Durability로 인해 디스크 I/O와 CPU 사용률이 증가하고, 로그 파일이 디스크 공간을 차지합니다. 정기적으로 쓰기 지연, 로그 파일 크기, 복구 시간을 모니터링해야 합니다.

5본질 요약

Durability를 통한 내구성이 메모리와 로그 간의 일관성은 보장하지만, 쓰기 지연과 복구 시간을 대가로 하며, 이들을 주기적으로 모니터링해 운영 영향을 제어해야 한다는 점

백업의 원리와 성능 영향, 예약 메모리

백업(스냅샷)은 특정 시점의 캐시 데이터를 .rdb 파일로 S3에 저장하는 것으로, 포크와 디스크 쓰기 때문에 메모리·CPU 여유가 필요하다.

→ 09-04 참조

1상대의 출발점 확인

캐시는 일시적 데이터 저장소지만, 매우 큰 데이터셋을 캐시했거나 중요 기능에 캐시가 깊게 결합되어 있으면 백업으로 보존하고 싶을 때가 있습니다. 하지만 메모리 데이터를 백업하는 것은 간단하지 않고 성능 영향이 큽니다.

2질문 제기

메모리 캐시 데이터의 백업은 어떻게 만들고, 그것이 실행 중인 캐시 성능에 어떤 영향을 미칠까요?

3구조적 핵심 예시

백업은 특정 시점의 메모리 스냅샷을 RDB 파일(Redis Database 파일)로 디스크에 직렬화(serialize)한 뒤, 그 파일을 S3에 업로드하는 방식입니다. 이 과정은 메모리 포크(Copy-on-Write, 메모리 복제), 디스크 쓰기, 네트워크 전송 등을 순차적으로 수행하므로 여유 메모리와 CPU가 필요합니다.

4단계별 동작 과정

  1. 메모리 포크 및 스냅샷 생성백업이 시작되면, 프로세스가 메모리를 포크(Copy-on-Write 방식)해 스냅샷을 생성합니다. 이 단계에서 메모리 사용량이 급증합니다.
  2. RDB 파일 직렬화포크된 메모리 스냅샷을 RDB 파일로 디스크에 써 내립니다. 이 I/O 작업이 메모리 I/O와 CPU를 꽤 소비합니다.
  3. S3 업로드완성된 RDB 파일을 S3에 업로드합니다. 파일 크기가 크면 업로드도 시간이 걸립니다.

1상대의 출발점 확인

백업을 만드는 방법은 여러 가지입니다. 언제 자동으로 만들지, 어떤 주기로 보존할지, 수동 백업은 언제 필요한지, 그리고 클러스터를 삭제할 때 데이터를 남길지 등을 미리 정해야 데이터 손실이나 규제 위반을 피할 수 있습니다.

2질문 제기

어떤 주기와 정책으로 자동 백업을 만들고, 수동 백업과 최종 백업을 어떻게 관리하며, 보존 기간은 어떻게 설정해야 할까요?

3구조적 핵심 예시

자동 백업은 매일 정한 시간에 자동으로 뜨고(예: 매일 오전 3시), 설정한 보존 기간 동안(예: 7일) 이전 백업들을 유지합니다. 수동 백업은 필요할 때 즉시 생성되고 보존 기간 제한이 없으므로 오래 보관할 수 있습니다. 클러스터를 삭제할 때는 최종 백업을 남길지 말지를 선택합니다.

4단계별 동작 과정

  1. 자동 백업 설정자동 백업을 활성화하고, 매일 백업할 시간(UTC)과 보존 기간(예: 1일~35일)을 지정합니다. 정한 시간이 되면 클러스터는 자동으로 백업을 생성합니다.
  2. 수동 백업 생성필요할 때(예: 주요 업데이트 전, 마이그레이션 직전) 수동으로 백업을 시작합니다. 수동 백업은 명시적으로 삭제할 때까지 유지됩니다.

백업에서 복원하고 새 캐시 시딩하기

저장된 백업으로 새 클러스터를 만들어 데이터를 되살리거나, 외부 .rdb 파일로 새 캐시를 미리 채우는 작업이다.

1상대의 출발점 확인

ElastiCache 클러스터의 데이터는 메모리에만 존재하기 때문에, 클러스터가 삭제되거나 장애가 나면 데이터를 되살릴 방법이 없다. 또한 외부에서 운영하던 Valkey/Redis OSS 환경의 대량 데이터를 새로운 ElastiCache 클러스터로 옮길 때도, 애플리케이션 코드로 하나씩 데이터를 입력해야 하므로 시간이 오래 걸리고 오류 가능성이 높다.

2질문 제기

저장된 백업 스냅숏으로 손실된 데이터를 되살리거나, 외부 환경의 데이터를 ElastiCache에 미리 채워 초기화 시간을 단축할 수 있을까?

3구조적 핵심 예시

ElastiCache는 클러스터가 보유한 메모리 내용을 .rdb 파일(Redis Database Snapshot)로 저장하고, 새 클러스터를 만들 때 이 파일을 시작점으로 지정해서 메모리 전체를 한 번에 복원하거나, 외부 Redis/Valkey에서 export한 .rdb 파일을 ElastiCache 클러스터의 초기 데이터로 로드할 수 있다.

4단계별 동작 과정

  1. 백업 생성실행 중인 ElastiCache 클러스터의 메모리 전체를 .rdb 파일로 저장해 S3에 보관.
  2. 복원용 클러스터 생성새 클러스터를 만들 때 백업 파일의 경로를 명시하면, 클러스터 시작 시 그 파일을 읽어 메모리에 데이터를 그대로 로드해 복원 완료.
  3. 시딩 동작외부 Redis/Valkey 환경에서 export한 .rdb 파일도 같은 방식으로 사용할 수 있어, ElastiCache 클러스터가 시작되면서 외부 데이터가 미리 채워진 상태로 서비스 가능.

온라인 마이그레이션 — 외부 클러스터를 ElastiCache로

EC2 등에서 직접 운영하던 Valkey/Redis OSS를 복제(replication)로 연결해 다운타임을 거의 없이 ElastiCache로 옮기는 방법이다.

1상대의 출발점 확인

EC2나 자체 운영 서버에서 Valkey/Redis OSS를 직접 운영하면, ElastiCache로 옮기려면 전체 서비스를 중단한 후 데이터를 복사하고 애플리케이션의 접속 대상을 변경해야 한다. 이 과정 중에 들어오는 새로운 데이터는 손실되고, 마이그레이션 시간이 길수록 사용자 영향이 심해진다.

2질문 제기

운영 중인 외부 Redis/Valkey 클러스터를 서비스 중단 없이 ElastiCache로 옮길 수 있을까?

3구조적 핵심 예시

ElastiCache는 외부 클러스터를 복제 소스로 등록하고 실시간 동기화를 시작한다. 외부 클러스터의 모든 쓰기 명령(SET, DEL, 만료 등)을 ElastiCache가 따라가면서 두 클러스터의 데이터를 같은 상태로 유지하다가, 동기화가 완료되면 애플리케이션의 접속만 ElastiCache로 바꾸는 방식이다.

4단계별 동작 과정

  1. 복제 연결 설정ElastiCache 콘솔에서 외부 클러스터의 주소를 복제 소스로 등록, 네트워크 연결 확인 후 실시간 동기화 시작.
  2. 데이터 동기화외부 클러스터에 들어오는 모든 쓰기, 삭제, 만료 이벤트를 ElastiCache에 실시간으로 반영해서 두 클러스터의 상태를 동일하게 유지.
  3. 전환동기화 상태가 "in sync"로 표시되고 지연이 거의 없음을 확인한 후, 애플리케이션 설정을 ElastiCache의 엔드포인트로 변경하고 외부 클러스터를 비활성화.

1상대의 출발점 확인

ElastiCache 클러스터의 Valkey/Redis OSS 엔진 버전이 오래되면 보안 패치나 성능 개선을 받지 못하고 메모리 누수나 취약점에 노출된다. 하지만 버전을 올리면 엔진의 내부 알고리즘, 인메모리 데이터 형식, 명령어 동작이 바뀔 수 있어서, 기존 데이터나 애플리케이션 코드가 깨질 수 있다.

2질문 제기

새 엔진 버전으로 업그레이드할 때 기존 데이터와 애플리케이션이 호환되도록 안전하게 진행할 수 있을까?

3구조적 핵심 예시

마이너 버전 업그레이드(예: 7.0.1 → 7.0.2)는 패치 수준이라 인메모리 형식이 그대로이고 호환성이 유지되지만, 메이저 버전 업그레이드(예: 6.x → 7.x)는 데이터 구조가 재설계되어 기존 백업에서 복원할 때 변환 절차가 필요하고 일부 명령어의 동작이 달라진다.

4단계별 동작 과정

  1. 호환성 검토업그레이드할 버전의 릴리스 노트와 마이그레이션 가이드를 읽고, 사용 중인 명령어·데이터 구조·설정값이 변경되었는지 확인.
  2. 테스트프로덕션 환경과 동일한 데이터와 설정으로 테스트 클러스터를 만들어 업그레이드를 수행한 후 애플리케이션 연결 테스트와 성능 검증.
  3. 프로덕션 적용마이너 버전은 기존 클러스터를 직접 업그레이드하고, 메이저 버전은 새 클러스터를 만들어 데이터를 마이그레이션한 후 전환.

1상대의 출발점 확인

AWS는 정기적으로 ElastiCache 클러스터에 보안 패치, 운영체제 업데이트, 인프라 유지보수를 자동으로 적용한다. 사용자가 통제하지 않으면 이런 업데이트가 예고 없이 업무 시간에 실행되어 클러스터가 멈추고, 읽기 복제본이나 다중 가용 영역 구성이 없으면 서비스 전체가 중단된다.

AWS의 정기 유지보수로 인한 예측 불가능한 서비스 중단을 줄이면서, 필수 보안 패치는 적시에 적용할 수 있을까?

3구조적 핵심 예시

ElastiCache는 주간 유지 관리 창(Maintenance Window)을 설정하면, AWS가 패치와 업데이트를 그 기간 내에만 자동으로 수행하고, 다중 가용 영역 구성의 경우 한쪽 프라이머리 노드를 먼저 업데이트한 후 자동으로 페일오버해서 중단 없이 완료한다.

4단계별 동작 과정

  1. 유지 관리 기간 설정사용자가 주 단위로 영향이 가장 적은 시간대(예: 일요일 03시~04시)를 선택해 설정.
  2. 자동 적용AWS가 그 기간에 보안 패치와 서비스 업데이트를 자동으로 실행하고, 다중 AZ 구성이면 프라이머리 업데이트 후 페일오버로 무중단 처리.
  3. 선택적 제어긴급 보안 패치는 기다리지 않고 즉시 적용할 수 있으며, 일반 업데이트는 미리 설정한 기간까지 연기할 수 있다.

1상대의 출발점 확인

ElastiCache 클러스터마다 Valkey/Redis OSS/Memcached의 엔진 설정값(maxmemory-policy, timeout, tcp-backlog 등)을 일일이 입력해야 하는데, 여러 클러스터가 같은 설정을 공유할 때 각각을 따로 수정해야 하고 설정 간 불일치가 발생하기 쉽다.

2질문 제기

엔진 설정값들을 하나의 템플릿으로 관리해서, 여러 클러스터에 일괄 적용하고 중앙에서 수정할 수 있을까?

3구조적 핵심 예시

파라미터 그룹은 Valkey/Redis OSS/Memcached 각각의 엔진 설정값들을 명명된 조합으로 저장해서, 클러스터 생성 시 이 그룹을 선택하면 그 안의 모든 파라미터가 한 번에 적용되고, 나중에 그룹의 값을 수정하면 연결된 모든 클러스터에 자동으로 반영된다.

4단계별 동작 과정

  3. 실제 파라미터 조정업무 특성에 맞게 maxmemory-policy, timeout, tcp-backlog, thread 관련 설정 등을 권장 범위 내에서 수정하고 테스트.

1상대의 출발점 확인

기존에는 팀이 ElastiCache를 필요한 대로 개별적으로 구성했습니다. 누군가는 보안을 중시하고, 누군가는 비용만 생각했으며, 누군가는 장애 대응을 간과했습니다. 이렇게 일관성 없이 구성하면 어느 부분은 탄탄하고 어느 부분은 허술한 아키텍처가 됩니다. 체계적인 점검 기준이 없어 무엇을 개선해야 할지 알기 어려웠습니다.

2질문 제기

캐시 아키텍처가 운영, 보안, 안정성, 성능, 비용 측면에서 균형 잡혀 있는지 어떻게 확인할까요?

3구조적 핵심 예시

AWS Well-Architected 프레임워크에서는 다섯 기둥(운영 탁월성, 보안, 신뢰성, 성능 효율성, 비용 최적화)의 관점으로 시스템을 평가합니다. ElastiCache Well-Architected Lens는 이 다섯 기둥에 따라 각각 "CloudWatch로 모니터링을 설정했는가?", "암호화와 접근 제어를 설정했는가?", "Multi-AZ와 자동 페일오버를 설정했는가?", "적절한 캐시 정책과 노드 크기를 선택했는가?", "리서브드 인스턴스나 절감 플랜은 고려했는가?" 같은 체크리스트 질문들을 제시합니다.

4단계별 동작 과정

  1. 기둥별 항목 확인다섯 기둥 각각에 대해 체크리스트 질문에 답합니다. 각 질문은 현재 아키텍처가 그 기둥의 원칙을 따르는지 판단하게 합니다.
  2. 미흡 영역 식별체크리스트를 통과하지 못한 항목들이 개선이 필요한 부분입니다. 예를 들어 "다중 가용 영역을 사용 중인가?"에 "아니오"라면 신뢰성을 높이려면 설정을 변경해야 합니다.
  3. 개선 계획 수립미흡 영역별로 개선 방안을 결정하고 우선순위를 정하여 단계적으로 적용합니다.

5본질 요약
