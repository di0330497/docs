SDLC

토픽 'SDLC'(소프트웨어 개발 생명주기)를 AWS 의 정품 문서로 학습할 수 있게 구성했다. 먼저 분명히 해야 할 사실이 하나 있다 — AWS 에는 SDLC 라는 이름의 독립 문서가 없다. 소프트웨어를 만들어 배포하고 고치는 과정을 AWS 는 Well-Architected Framework 안에서 '운영 탁월성' 기둥의 개선 사례로 서술한다. 그래서 목차는 SDLC 의 단계를 그대로 따르되, 각 단계의 근거는 그 단계에 해당하는 Well-Architected 최선실천 페이지로 붙였다. 단계 배열은 다음과 같다 — 무엇을 관찰할지 정하고(준비), 설계 표준을 세우고(요구·설계), 코드를 쓰고(구현), 시험하고(시험), 빌드 환경을 만들고(빌드), 자동화해 배포하고(배포), 준비도 판단을 거쳐(배포 판단), 관측하며 사건에 대응하고(운영), 피드백을 돌린다(개선). 즉 9단계가 SDLC 의 고리이고 10단계는 그 고리가 도는 방식이다. Prescriptive Guidance 디렉터리는 이 환경에서 전부 403 이라 근거로 쓸 수 없었고, Well-Architected Framework 색인 475쪽은 정상 접근된다.

1단계 1. 소프트웨어 생명주기란 무엇인가

소프트웨어 생명주기(SDLC)는 하나의 소프트웨어를 기획하고 설계하고 개발하고 시험하고 배포하고 운영하며 개선에 이르기까지 거치는 전체 과정의 단계를 가리키는 말이다.

#1문제 상황

소프트웨어는 한 번 만들어 끝나는 물건이 아니다. 만들고 나서도 고치고 다시 고치면서 오래 쓰인다. 그래서 소프트웨어 생명주기(SDLC)라는 전체 과정이 필요하다.

AWS Well-Architected Framework는 이 과정을 다섯 단계와 여섯 기둥으로 나눠 다룬다. 여기에는 abstract and introduction, 즉 전체 소개가 들어 있고, the pillars of the framework 라는 기둥 목록이 함께 제시된다.

#2핵심 질문

하나의 소프트웨어가 만들어지고 운영되기까지 전체 과정은 어떻게 구성되는가?

#3동작 예시

팀이 새 서비스를 만들기로 한다. 기획에서 요구사항을 정하고 설계하고 개발하고 시험한 뒤 배포한다. 배포 후 문제와 개선점을 고치며 다음 반복으로 넘어간다.

이 절차를 Framework 기준으로 점검하면 개선할 부분을 미리 찾을 수 있다.

#4동작 과정

5. 시험과 검증05-01

5단계 5. 시험과 검증

운영 중인 시스템에 바꿔 넣을 때 문제가 생기기 전에 그 변경이 안전한지 미리 확인하는 절차로, 시험한 결과를 근거로 배포를 진행할지 결정한다.

먼저 알아야 할 것 04-01

#1문제 상황

운영 중인 시스템에 코드를 바꿔 넣으면 사용자가 받는 서비스가 바로 그 영향을 받는다(→ 01-01). 그런데 이때 아무 확인 없이 배포하면 문제가 생겼을 때 원인을 되짚을 길이 사라진다.

변경을 시험하고 검증하는 것은, 바꾼 내용을 운영에 올리기 전에 임시 환경에서 미리 돌려 보고 문제가 없는지 확인하는 일이다. 그래서 실패는 운영에 닿기 전에 드러난다.

#2핵심 질문

바꾼 내용을 운영에 올리기 전에 어떻게 미리 확인하는가?

#3동작 예시

개발자가 주문 화면의 버튼 문구를 고쳐 배포를 요청한다. 담당자는 운영과 똑같은 조건을 낸 임시 환경에 그 변경을 올린다.

파일과 설정이 의도한 대로 반영됐는지 보고, 기능 시험과 부하 시험을 돌려 응답이 느려지지 않는지 본다. 여기서 멈췄다면 운영 배포는 진행하지 않는다.

  1. 임시 환경을 만든다운영 옆에 변경을 시험할 환경을 따로 세운다. IaC, 즉 코드로 인프라를 정의하는 방식으로 자동 생성하면 사람마다 다른 결과가 생기지 않는다(→ 03-02).

#2핵심 질문

코드를 고칠 때마다 빌드와 배포를 자동으로 시키려면 어떻게 해야 하는가?

#3동작 예시

개발자가 저장소에 새 기능을 올리면 파이프라인이 그 변경을 자동으로 빌드해 실행 파일을 만든다. 이어서 시험을 통과하면 운영 환경에 배포되고, 실패하면 배포는 진행되지 않는다.

운영자는 파이프라인 화면에서 어떤 변경이 통과했는지와 배포가 끝났는지를 본다.

#4동작 과정

  1. 빌드한다소스 코드를 컴파일해 실행 가능한 결과물을 만든다. 이 자동화된 흐름을 build and deployment management systems가 맡으며, AWS Developer Tools의 AWS CodeBuild가 그 역할을 한다.
  2. 시험하고 판정한다만들어진 결과물이 기준을 통과했는지 확인해 배포 여부를 정한다.
  3. 배포한다AWS CodePipeline이 단계 순서를 정하고 AWS CodeDeploy가 대상 환경에 결과를 올린다. 각 배포는 반드시 되돌릴 수 있어야 한다.
  4. 확인해 볼 것파이프라인 화면에서 마지막 변경이 어느 단계에서 끝났는지 본다.

#1문제 상황

#3동작 예시

#4동작 과정

  4. 확인해 볼 것각 환경의 접근 권한이 운영에 가까운 곳일수록 더 제한되어 있는지 본다.

#1문제 상황

분기마다 한 번, 정해진 변경 창에 코어 서비스를 멈추고 새 버전을 한 번에 올리면 문제가 생겼을 때 무엇이 잘못됐는지 찾기 어렵다. 되돌릴 계획도 없이 서버 설정을 직접 덮어쓰면 이전 상태로 돌아갈 길이 사라진다.

자주·작게·되돌릴 수 있게 바꾸기는 이 문제를 반대에서 푸는 방식이다. OPS05-BP09는 frequent, small, and reversible changes를 요구하고, change management·configuration management 시스템과 build and delivery 시스템이 함께 동작할 때 효과가 크다고 본다. 작은 변경일수록 부작용을 바로 알아채고 되돌릴 수 있다.

#2핵심 질문

#3동작 예시

#4동작 과정

먼저 알아야 할 것 06-03

#1문제 상황

실패를 전제로 배포를 계획한다는 태도는 이 빠진 계획을 미리 채운다. OPS06-BP01은 여러 팀이 실패에서 돌아올 전략을 세우게 하며, deployment와 rollback 단계, 변경 정책, feature flags, 트래픽 격리와 전환이 그 예다. 릴리스 크기를 줄여 영향 범위와 다운타임도 함께 줄인다.

#3동작 예시

#4동작 과정

  2. 작게 나눈다한 릴리스의 변경을 나누어 어떤 구성요소가 실패해도 다른 부분에 미칠 영향을 줄인다.

#1문제 상황

운영 중인 서버에 설정을 손으로 고치면 같은 설정이 다시 만들어지지 않는다. 무엇이 바뀌었는지 기록이 남지 않아 되돌릴 수 없다(→ 04-01).

불변 인프라로 배포한다는 방법은 이를 금지한다. REL08-BP04는 in-place 수정을 허용하지 않고, 변경이 필요하면 필요한 변경이 모두 들어 있는 새 infrastructure resource 묶음을 기존 자원에 나란히 배포하라고 정한다. 배포는 자동으로 검증되고 성공하면 트래픽을 새 자원에 점진적으로 옮긴다. 소프트웨어 업데이트, 보안 패치, 인프라·설정 변경이 모두 여기에 쓰인다.

#2핵심 질문

돌아가는 자산을 고치지 않고 변경을 반영하려면 어떻게 하는가?

#3동작 예시

보안 패치가 필요해 패치가 포함된 새 서버 묶음을 나란히 올린다. 자동 검증이 통과하면 트래픽을 새 묶음으로 옮기고 기존 묶음은 남겨 둔다.

검증에 실패하면 새 묶음을 버리고 기존 묶음이 그대로 사용자 요청을 받는다.

#4동작 과정

  1. 새 자원을 만든다모든 변경이 들어 있는 새 infrastructure resource를 만들어 기존 자원에 나란히 배포한다.
  2. 검증한다이 배포를 자동으로 검증해 성공 여부를 확인한다.
  3. 옮긴다성공하면 트래픽을 새 자원 쪽으로 점진적으로 이동한다. 그 결과를 reliability, consistency, reproducibility를 얻는다고 한다.

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 자동 도구로 올린다REL08-BP05 Deploy changes with automation 원칙에 따라 시험과 배포, 용량 증감, 데이터 이동을 도구가 수행한다. 비상용 수동 절차로 자동 절차를 건너뛰지 않게 한다.
  2. 안전장치를 끼운다사전 시험과 자동 롤백, 운영 환경에 나누어 배포하는 staggered production deployments를 릴리스 과정에 넣는다. 실패해도 개발자가 옆에서 지켜보지 않아 된다.
  3. 확인해 볼 것배포 기록에서 각 변경이 자동 승인 규칙을 거쳐 올라갔는지와 자동 롤백이 실제로 동작했는지 확인한다.

#1문제 상황

런북은 누가 봐도 같은 순서로 같은 결과를 얻게 해 주는 문서다. 여기서는 런북과 함께, 특정 사건에 대응해 원인을 찾는 절차인 플레이북까지 함께 다룬다.

#2핵심 질문

#3동작 예시

밤중 장애가 터지면 온콜 담당자는 알람을 보고 플레이북을 열어 확인 항목 순서대로 원인을 좁힌다.

#4동작 과정

  1. 절차를 적는다어떤 과제를 하기 위해 따라야 할 단계들을 문서로 남긴다. 이것이 OPS07-BP03 Use runbooks to perform procedures 다. 오류 처리·사용할 도구·권한·예외 상황과 에스컬레이션 경로까지 적어 둔다.
  2. 중앙에 둔다런북을 한곳에 모아 보고 절차가 바뀔 때마다 갱신한다. 신입 교육부터 큰 릴리스 배포까지 같은 문서를 따라가게 되고 갱신 자체가 변경 관리의 일부가 된다.
  3. 원인을 찾는 절차를 따로 둔다플레이북은 특정한 사건이 발생했을 때 원인을 조사하는 절차로, OPS07-BP04 Use playbooks to investigate issues 에 해당한다. 런북이 결과를 얻는 일이라면 플레이북은 원인을 찾는 일이다.
  4. 확인해 볼 것저장소의 문서 목록에서 런북 하나를 열어 단계가 번호 순서로 서 있고 오류 처리 항목이 들어 있는지 본다.

#4동작 과정

먼저 알아야 할 것 09-04

→ 09-04 참조

#1문제 상황

운영 중 벌어진 사건(events)을 팀마다 제각기 다르게 대응하면 같은 장애를 여러 번 반복해서 겪는다. 그래서 AWS Well-Architected Framework는 OPS10-BP01 Use a process for event, incident, and problem management처럼 사건·incident·problem을 나누고 각자 정해진 절차로 다루게 한다. 문서로 남겨 둔 절차가 있으면 대응과 학습이 이어진다.

#2핵심 질문

사건이 터졌을 때 정해진 절차로 빠르게 대응하고 같은 일을 반복하지 않게 하려면?

#3동작 예시

결제 서비스의 응답 시간이 급격히 오른다. 팀은 미리 정해 둔 절차에 따라 알람을 확인하고 영향받는 작업을 격리해 결과를 되돌린다. 처리가 끝나면 같은 원인으로 반복된 사건이 목록에 남아 문제로 등록된다.

#4동작 과정

  1. 사건을 감지한다알람이 울리면 사건으로 기록하고 영향도를 본다. 알람마다 OPS10-BP02 Have a process per alert처럼 알람별 대응 절차를 둬 판단을 통일한다.
  2. 우선순위를 정한다OPS10-BP03 Prioritize operational events based on business impact처럼 업무 영향이 큰 것을 먼저 처리한다.
  3. 문제를 남긴다반복된 사건의 근본 원인은 문제로 기록해 자원을 배정한다. 절차는 한곳에 저장하고 계속 고쳐 쓴다.
  4. 확인해 볼 것알람과 사건 목록에 각 사건의 상태와 담당자가 함께 표시되는지 화면에서 확인한다.

지속 개선 절차

운영 중 얻은 실제 경험을 근거로 반복해서 평가하고 수정하는, 반복적으로 돌리는 정해진 작업 순서.

먼저 알아야 할 것 09-04

#1문제 상황

운영이 오래 이어지면 아키텍처가 배포 당시의 모범 사례에서 뒤처진다. 그런데 개선 후보는 신제품 기능보다 우선순위가 낮아 백로그에 방치된다.

지속 개선 절차는 워크로드 검토와 개선 후보 우선순위 정하기를 정해진 주기로 반복해 운영 상태를 최신 상태로 붙잡는다. 운영 지표를 보고 개선 순서를 정하는 일(→ 09-04)이 이 절차의 입력이 된다.

#2핵심 질문

운영한 지 한참 지난 워크로드를 누가, 어떤 주기로 검토해 개선 과제를 뽑는가?

#3동작 예시

운영 담당자가 분기마다 워크로드 검토를 연다. 모은 지표와 아키텍처 모범 사례를 맞춰 보면 오래된 부분이 드러난다.

그 결과가 백로그에 별도 항목으로 등록되고, 새 기능과 같은 기준으로 우선순위를 매긴다.

#4동작 과정

  1. OPS 11. How do you evolve operations? 기준을 정한다 — 조직 안에서 워크로드를 무엇에 비추어 개선 여부를 판단할지 기준을 정한다. 기준이 있어야 여러 팀이 같은 판정을 내린다.
  2. OPS11-BP01 Have a process for continuous improvement 절차를 돌린다 — 워크로드 검토를 자주 의도적으로 열고 결과로 개선 후보를 뽑는다. 이 절차는 이름 그대로 정해진 업무 순서이며 가볍게 한 번 하는 활동이 아니다.
  3. 후보에 우선순위를 준다뽑은 후보를 소프트웨어 개발 과정 안에서 신제품 기능과 같은 무게로 다룬다. 후보는 산출물 a-evolve 로 관측 대상 업무 상태를 함께 적고, oe-evolve 로는 이 후보들이 다음 반복에서 무엇을 개선했는지 추적한다.
  4. 확인해 볼 것반복 검토 기록에서 이번에 뽑힌 개선 후보가 지난번 검토의 후보와 같은 목록에만 머물지 않고 실제 반영 항목으로 이어졌는지 본다.

먼저 알아야 할 것 10-01

→ 10-01 참조

#1문제 상황

장애가 끝나면 팀은 원인을 추측한 채 넘어가고 같은 문제가 되풀이된다. 네트워크 팀처럼 다른 팀의 도움 없이 원인 규명을 끝낼 수도 없다.

OPS11-BP02 Perform post-incident analysis는 사고가 끝난 뒤 원인 규명에 데이터를 붙이고 재발을 막는 완화 조치와 신속한 대응 절차를 함께 세우는 관행이다.

#2핵심 질문

끝난 사고에서 무엇이 기여했는지 데이터로 밝히고 어떻게 다시 막을 것인가?

#3동작 예시

어떤 서버의 활성 세션이 약 23시간 55분마다 끊긴다. 팀은 직접 추적해 봤지만 원인이 네트워크인지 애플리케이션 서버인지 판단하지 못하고 방치된다.

사후에 사고 분석을 붙여 관측 계획과 지표를 미리 마련해 두면, 다음번부터 같은 증상이 데이터로 남는다.

#4동작 과정

  1. 원인 규명에 쓸 데이터를 모은다사건 관측 계획과 지표를 먼저 세워 사건이 났을 때 쓸 데이터를 남긴다. 이 데이터가 사고 후 분석의 근거가 된다.
  2. 완화 조치와 대응 절차를 만든다확인된 원인에서 재발을 막거나 범위를 줄이는 완화 조치를 세우고, 다음 사건에 빠르게 대응할 절차를 함께 정한다.
  3. 기여 요인을 알린다무엇이 사고에 기여했는지와 시정한 내용을 대상 독자에 맞게 알린다. 의사결정자는 전체를, 담당자는 재현 가능한 절차만 받는다.
  4. 확인해 볼 것사고 분석 결과로 만든 완화 조치가 이후 같은 증상이 반복됐을 때 실제로 효과를 냈는지 확인한다.

#1문제 상황

피드백 루프는 운영 결과와 사용자 반응을 측정(Measurement)·검토(Review) 단계로 되돌려 다음 결정에 반영하는 되돌아가는 연결이다(→ 10-02). 여기서 다루는 개념은 OPS11-BP03 Implement feedback loops, 즉 이 되돌아가는 연결을 실제 절차와 워크로드에 넣어 두는 것이다.

#2핵심 질문

#3동작 예시

이 검토가 정기 회의와 큰 배포 직후에 반복되면서 개선이 쌓인다.

#4동작 과정

  1. 즉각 피드백을 모은다운영 활동의 결과와 수행 상황을 바로 확인한다. 팀원·고객·자동화 결과가 여기 해당하며, A/B 테스트와 새 기능 배포가 이 방식이다.
  2. 회고 분석을 한다일정 주기나 스프린트 끝, 큰 배포·사건 뒤에 운영 결과와 지표를 되돌아본다.
  3. 결정으로 돌린다모은 피드백을 다음 결정과 개선에 반영하고, 투자한 개선이 맞았는지도 확인한다.
  4. 확인해 볼 것팀 회의 안건에 회고 항목이 잡혀 있고 지난 회고의 개선 항목이 이번 결정으로 이어졌는지 확인한다.

#1문제 상황

#3동작 예시

#4동작 과정

  1. 정보를 한곳에 모은다팀이 만든 문서와 기록을 검색할 수 있는 위키 같은 중앙 저장소에 둔다. 정보가 정확하고 최신인지도 함께 살핀다.
  2. 찾고 고친다찾기 기능으로 필요한 정보를 꺼내고, 내용이 옛것이면 갱신하며, 쓸모가 사라진 것은 보관한다.
  3. 교훈을 나눈다사고와 실패에서 얻은 교훈을 문서로 남기고 팀 전체가 보게 한다. 없는 내용을 발견하면 추가 요청하는 절차도 함께 둔다. OPS11-BP08 Document and share lessons learned가 이 공유를 다룬다.
  4. 확인해 볼 것팀 위키에서 최근 문서를 찾아 올바른 문서가 표시되는지 보고, 내용이 오래됐으면 갱신 요청을 남긴다.

#1문제 상황

OPS11-BP05 Define drivers for improvement는 환경 여러 곳에서 모은 데이터를 사건·활동과 사업 결과에 연결해 개선 동인을 정하는 일이다. OPS11-BP06 Validate insights는 그 동인에서 나온 통찰이 실제로 맞는지 시험하는 일이다. 둘을 거치면 데이터가 근거가 된다.

어떤 데이터를 어떤 사업 결과와 이어야 개선할 곳이 보이는가?

#3동작 예시

팀은 이 통찰을 가정 순서로 시험해 원인이 맞는지를 확인하고 개선 대상으로 고른다.

#4동작 과정

  1. 동인을 정한다환경에서 모은 데이터를 사건·활동과 사업 결과에 맞춰 본다. 개발·테스트·프로덕션 환경을 서로 비교해 어디가 다른지 본다. 배포와 그 결과도 자세히 남겨 비교할 수 있게 하는데, 이 기록이 AWS CloudTrail 같은 활동 기록의 근거가 되고 보안 상태를 살피는 데도 쓴다.
  2. 통찰을 검증한다데이터에서 나온 판단을 작은 시험으로 확인해 맞는지 본다. 새 기능의 효과도 같은 방식으로 재서 효과 없는 수집은 줄이고 반복 작업은 자동화한다.
  3. 확인해 볼 것개선 후보 목록에 각 항목의 사업 결과와 근거 데이터가 함께 적혀 있는지 확인한다.

#2핵심 질문

#3동작 예시

#4동작 과정

  2. 환경을 함께 살핀다개발·테스트·프로덕션 어디에서도 개선할 곳이 있는지 확인한다. 한 환경의 위험을 다른 팀이 모르는 채 그대로 당하지 않게 공유한다.

  4. 확인해 볼 것검토 회 기록에 지표 이름과 도출된 개선 후보가 함께 남아 있는지 확인한다.
