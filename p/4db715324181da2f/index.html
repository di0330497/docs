1상대의 출발점 확인

모든 데이터를 동일한 형식으로 저장할 수 없습니다. 데이터의 특성과 사용 패턴에 따라 저장 방식이 달라집니다. CSV 형식은 읽기 쉽지만 용량이 크고, 다른 형식은 압축률이 좋지만 파싱이 복잡할 수 있습니다. 잘못된 형식을 선택하면 학습 속도가 느려지거나 메모리를 낭비하게 됩니다.

2질문 제기

ML 학습과 추론에 사용할 데이터를 어떤 파일 형식으로 저장해야 효율적인가?

3구조적 핵심 예시

행 기반 형식(CSV, JSON)은 한 건의 데이터 레코드를 순서대로 저장하므로, 특정 행을 빠르게 읽을 수 있습니다. 열 기반 형식(Parquet, ORC)은 각 열을 따로 저장해서 특정 열만 필요한 분석에서는 불필요한 데이터를 건너뛸 수 있습니다. SageMaker의 내장 알고리즘이 선호하는 RecordIO-protobuf는 이진 형식으로, 매우 빠른 처리를 위해 최적화되어 있습니다.

4단계별 동작 과정

  1. 데이터 특성 파악데이터셋의 크기, 행과 열의 개수, 자주 접근하는 패턴(특정 행 읽기 vs. 특정 열 읽기)을 분석합니다.
  2. 포맷 선택가독성이 중요하면 CSV/JSON, 속도와 용량이 중요하면 Parquet/ORC, SageMaker 내장 알고리즘 사용 시 RecordIO를 선택합니다.
  3. 변환 및 저장선택한 형식으로 데이터를 변환해서 S3나 다른 저장소에 올립니다.

3구조적 핵심 예시

3구조적 핵심 예시

고속 학습이 필요한 경우 FSx for Lustre(초고속 병렬 파일시스템)를 학습 작업에 붙여서 S3보다 훨씬 빠른 I/O를 얻습니다. 온프레미스 데이터센터의 파일을 AWS로 옮기려면 DataSync(자동화된 대용량 데이터 이동)나 Storage Gateway(온프레미스와 AWS를 연결하는 가상 게이트웨이)를 써서, 네트워크를 통해 안전하고 효율적으로 전송합니다.

4단계별 동작 과정

  1. 요구사항 파악학습 작업이 요구하는 I/O 속도, 기존 데이터의 위치(온프레미스 vs. AWS), 데이터 용량을 정리합니다.
  2. 적절한 서비스 선택속도가 최우선이면 FSx for Lustre 또는 EBS, 기존 온프레미스 데이터를 옮기면 DataSync 또는 Storage Gateway를 선택합니다.
  3. 연결 구성선택한 스토리지를 SageMaker의 학습 인스턴스나 추론 엔드포인트에 마운트하거나, 온프레미스 시스템과 동기화를 설정합니다.

운영 데이터베이스는 애플리케이션이 실시간으로 쿼리하는 데 최적화되어 있습니다. 한 건 또는 작은 범위의 데이터를 빠르게 읽기 위함입니다. 하지만 ML 학습에는 수백만 건의 전체 데이터가 필요합니다. 기존 방식처럼 애플리케이션 쿼리 API를 사용해 한 건씩 읽으면 네트워크 왕복이 수백만 번 발생하고, 시간이 엄청 걸립니다. 또한 DB 서버에 지속적인 부하가 걸려 운영 시스템에 영향을 줍니다.

4단계별 동작 과정

  1. 데이터 소스 연결SageMaker Canvas나 Glue가 RDS, DynamoDB, Redshift 같은 데이터베이스 연결 정보(호스트, 포트, 인증)를 받습니다.
  2. 배치 추출 실행선택한 테이블이나 SQL 쿼리에 대해 전체 데이터를 S3로 한 번에 내보냅니다. 이 과정에서 네트워크 왕복이 최소화되고 DB 스캔은 한 번만 일어납니다.

배치 방식의 데이터 추출은 정해진 시간에 한 번씩 전체 데이터를 옮기는 방식입니다. 이는 역사 데이터는 잘 처리하지만, 센서, 클릭, 구매 같은 실시간 이벤트 데이터를 다룰 수 없습니다. 배치 추출 시간 사이사이에 발생한 이벤트는 누락되거나 지연 처리되고, 실시간 모델(예: 사기 탐지)이 필요한 경우 전혀 쓸 수 없습니다.

2질문 제기

계속 발생하는 이벤트 데이터를 손실 없이 실시간으로 받아서 저장소나 모델로 전달하려면?

3구조적 핵심 예시

초당 수천 건의 센서 데이터가 쏟아져 들어올 때, Kinesis Data Streams가 이 데이터를 메모리 버퍼에 받은 후 순서를 지켜 실시간으로 Lambda, Redshift, 또는 학습 중인 모델로 흘려보냅니다.

4단계별 동작 과정

  1. 스트림 채널 설정Kinesis Data Streams, Kafka, 또는 관리형 Flink 같은 스트리밍 플랫폼이 이벤트를 받을 채널을 만들고 데이터 소스와 연결합니다.
  2. 실시간 데이터 수신 및 버퍼링데이터 생산자(센서, 애플리케이션)에서 이벤트가 계속 들어오면 플랫폼이 이를 메모리나 디스크에 버퍼링해서 순서를 유지합니다.
  3. 다운스트림 시스템으로 전달버퍼링된 데이터를 구독자(Firehose, Lambda, 실시간 모델)가 읽어가면서 저장소에 적재하거나 즉각 처리합니다.

3구조적 핵심 예시

SageMaker Processing Job은 변환 코드를 AWS가 준비한 여러 머신에 배분합니다. 예를 들어 100GB 데이터는 10개 머신에 10GB씩 나눠 동시에 처리하고 결과를 모읍니다. Lambda는 새로운 데이터가 S3에 도착하는 순간 자동으로 변환 함수를 실행합니다. Spark는 대규모 분산 처리 엔진으로 수 테라바이트 이상을 다룹니다.

4단계별 동작 과정

  1. 처리 방식 선택배치(주기적으로 한 번에), 스트리밍(계속 들어옴), 초대규모(수백GB 이상) 중 데이터 특성에 맞게 선택합니다. Processing Job은 배치용, Lambda는 스트리밍용, EMR과 Spark는 초대규모용입니다.
  2. 처리 실행SageMaker Processing은 여러 머신 클러스터를 임시로 켜서 병렬로 데이터를 처리하거나, Lambda 함수가 이벤트에 반응해 즉시 변환하거나, Spark 클러스터가 분산 처리합니다.
  3. 결과 저장처리된 데이터를 S3, 데이터베이스, 또는 데이터 레이크에 저장합니다.

학습 잡이 데이터를 어디서 어떤 방식으로 읽어올지(복사·스트리밍·파일시스템 마운트) 정하는 설정이다.

1상대의 출발점 확인

기존에는 학습 데이터를 직접 컴퓨터에 다운로드해서 로컬 드라이브에 저장한 후, 학습 프로그램이 그 파일을 읽어 실행했다. 하지만 데이터 크기가 커질수록 다운로드 시간이 오래 걸리고, 여러 사람이 같은 데이터로 학습하려면 각자 복사본을 가져야 해서 저장공간 낭비가 심했다.

2질문 제기

학습 데이터가 어디에 있든 효율적으로 접근하고, 학습 속도를 떨어뜨리지 않으면서도 저장공간을 낭비하지 않으려면 어떻게 해야 할까?

3구조적 핵심 예시

SageMaker 학습 잡은 세 가지 방식으로 데이터를 읽는다. File 모드는 학습 전에 S3에서 데이터를 모두 다운로드하는 방식이고, Pipe 모드는 학습 중에 필요한 부분만 S3에서 스트리밍(실시간으로 조금씩 받아오기)하는 방식이다. 또한 EFS나 FSx 같은 파일시스템에 데이터를 마운트(연결)해서 직접 읽을 수도 있다.

4단계별 동작 과정

  1. 데이터 소스 결정학습 데이터가 S3에 있는지, 파일시스템에 있는지 정한다.
  2. 접근 방식 선택File 모드로 사전 로드할지, Pipe 모드로 스트리밍할지, 혹은 마운트된 파일시스템에서 직접 읽을지 결정한다. 데이터가 크면 Pipe 모드가 초기 대기시간을 줄이고, 작으면 File 모드가 안정적이다.
  3. 학습 진행선택한 방식으로 컨테이너 내 /opt/ml/input/data 경로에 데이터가 도착하면, 학습 스크립트가 읽어 처리한다. 분할(샤드)과 셔플(무작위 섞기)도 이 단계에서 설정한다.

문제 유형별 알고리즘 적합성과 해석 가능성

풀려는 문제가 분류·회귀·군집·이상탐지 중 무엇인지에 따라 알고리즘을 고르고, 결과를 사람이 설명할 수 있는지(해석 가능성)까지 따져 선택하는 기준이다.

1상대의 출발점 확인

많은 신입 개발자가 어떤 알고리즘을 써야 할지 막힌다. 예를 들어 회사의 고객 신용도를 예측해야 하는데, 분류 문제인지 회귀 문제인지 구분하지 못하거나, 결과를 은행 심사팀에 설명할 수 없는 블랙박스 모델을 선택했다가 규제 때문에 문제가 생긴다.

2질문 제기

내가 풀려는 문제가 정확히 무엇인지(분류·회귀·군집·이상탐지) 파악하고, 그 문제에 맞는 알고리즘을 고르되 결과를 사람이 설명할 수 있어야 하는데 어떤 기준으로 선택할까?

3구조적 핵심 예시

고객을 '우량·일반·위험' 3가지로 분류하는 것(분류)과, 고객의 다음 해 매출을 750만 원 같은 숫자로 예측하는 것(회귀)은 다른 문제이고, 따라서 다른 알고리즘을 써야 한다. 또한 이상탐지는 정상 데이터의 패턴을 학습해 비정상을 찾는 문제고, 군집은 유사한 데이터끼리 그룹을 나누는 문제다. 금융 회사라면 의사결정 근거를 설명할 수 있는 선형 회귀나 의사결정 트리를 선택하는 게 낫고, 추천 시스템이면 블랙박스인 딥러닝 신경망도 괜찮다.

4단계별 동작 과정

  1. 문제 유형 정의예측할 값이 범주(category)인가, 숫자인가, 아니면 비정상을 탐지하거나 유사한 것끼리 묶는가를 판단한다.
  2. 적합한 알고리즘군 선택분류면 로지스틱 회귀·의사결정 트리·앙상블(여러 모델 조합), 회귀면 선형/비선형 회귀, 이상탐지면 Isolation Forest나 원클래스 SVM을 후보로 올린다.
  3. 해석 가능성 고려결과를 사람이 설명해야 하는 상황(금융·의료·법률)이면 의사결정 트리나 선형 모델처럼 투명한 알고리즘을 선택하고, 그렇지 않으면 복잡하지만 성능이 좋은 모델을 우선한다.

1상대의 출발점 확인

2질문 제기

3구조적 핵심 예시

JumpStart는 Hugging Face나 Papers with Code 같은 공개 저장소에서 가져온 미리 학습된 모델 수백 개를 SageMaker 콘솔에 통합해서 제공한다. 사용자는 클릭 몇 번으로 이 모델을 한 줄의 코드도 없이 배포하거나, 자신의 데이터로 미세조정(Fine-tuning, 마지막 층만 다시 학습)할 수 있다. Amazon Bedrock은 여기서 한 발 더 나아가 Claude, Llama, Mistral 같은 대규모 파운데이션 모델을 관리형 API로 제공하므로, 사용자는 학습이나 인프라 관리 없이 곧바로 생성형 AI 기능을 자신의 애플리케이션에 붙일 수 있다.

4단계별 동작 과정

  2. 배포 또는 미세조정바로 배포해 엔드포인트(API 접근점)로 만들거나, 자신의 데이터로 미세조정 잡을 실행해 성능을 개선한다.
  3. 추론 실행배포된 모델에 입력을 보내면 예측 결과가 돌아온다. Bedrock의 경우 API 호출만으로 충분하다.

4단계별 동작 과정

  2. 자동 탐색 실행Autopilot이 데이터 특성을 분석하고, 전처리 파이프라인과 여러 알고리즘을 시도해 모델 후보들을 생성한다. 이 과정은 보통 수십 분에서 몇 시간 걸린다.
  3. 모델 선택 및 배포제시된 모델 중 성능 또는 비용을 고려해 하나를 선택하고, 엔드포인트로 배포해 추론을 시작한다.

1상대의 출발점 확인

전통적인 데스크톱 개발에서는 코드를 작성하고 로컬 PC에서 바로 실행한다. 하지만 머신러닝 학습은 대용량 데이터와 높은 계산 성능이 필요하므로, 로컬 PC만으로는 불가능하고, 원격 서버에서 실행해야 한다. 동시에 데이터가 어디서 오는지, 결과가 어디로 가는지, 중간 체크포인트는 어떻게 저장되는지를 명확히 해야 한다.

3구조적 핵심 예시

SageMaker 학습 잡은 세 가지 통로를 오간다. 첫째, S3의 학습 데이터가 입력 채널(Input Channel)을 통해 컨테이너 내 /opt/ml/input/data 디렉토리로 수신된다. 둘째, 사용자가 JSON으로 지정한 하이퍼파라미터(학습률, 배치 크기, 에포크 수 등)가 환경 변수로 컨테이너에 전달된다. 셋째, 학습이 끝나면 모델 아티팩트(model.tar.gz)와 중간 체크포인트가 다시 S3로 저장되어, 나중에 가져올 수 있다.

4단계별 동작 과정

  1. 학습 잡 정의S3 경로(데이터, 산출물), 인스턴스 타입(ml.p3.8xlarge 같은 GPU), 하이퍼파라미터, 컨테이너 이미지(내장 알고리즘 또는 사용자 정의)를 JSON으로 작성한다.
  2. 데이터 수신 및 학습 실행SageMaker가 지정된 EC2 인스턴스를 띄우고, 입력 채널을 통해 S3의 데이터를 /opt/ml/input/data로 다운로드(또는 스트리밍)한다. 컨테이너 내 학습 스크립트가 이 데이터와 하이퍼파라미터로 모델을 학습시킨다.
  3. 모델 저장 및 체크포인트 관리학습이 완료되면 모델 파일을 /opt/ml/model에 저장하면, SageMaker가 자동으로 S3에 업로드한다. 중간 체크포인트도 활성화하면 학습 실패 시 그 지점부터 재개할 수 있다.

분류 평가 지표: 혼동 행렬, 정확도·정밀도·재현율·F1, ROC와 AUC

맞춘 것과 틀린 것을 표로 정리한 혼동 행렬에서 정확도·정밀도·재현율·F1을 계산하고, 임계값을 바꿔가며 그린 ROC 곡선의 면적(AUC)으로 분류 모델의 성능을 비교하는 방법이다.

1상대의 출발점 확인

분류 모델의 성능을 평가할 때 정확도(맞춘 비율)만 본다. 그런데 데이터가 불균형이면(예: 양성 샘플 5%, 음성 샘플 95%) 항상 음성으로 예측해도 95% 정확도가 나온다. 또한 정확도만으로는 모델이 어떤 방식으로 틀렸는지 알 수 없다. 양성을 음성으로 잘못 예측한 건지, 음성을 양성으로 잘못 예측한 건지 구분할 수 없고, 실무에서는 이 구분이 매우 중요하다.

2질문 제기

맞춘 것과 틀린 것의 종류까지 세어서 모델의 실제 성능을 정확히 파악할 수 있을까?

3구조적 핵심 예시

의료 진단 모델을 평가할 때, 실제값과 예측값의 조합별로 네 칸에 개수를 집계한다. 양성 맞춤(진짜 병자를 병자로 진단), 양성 틀림(건강한 사람을 병자로 오진), 음성 맞춤(건강한 사람을 건강하게 진단), 음성 틀림(병자를 건강하다고 놓침). 이 네 개의 숫자만 있으면 모델의 성능을 다각도로 평가할 수 있다.

4단계별 동작 과정

  1. 혼동 행렬 작성모든 예측을 실제값과 예측값의 조합(양성 맞춤, 양성 틀림, 음성 맞춤, 음성 틀림)별로 분류해 개수를 네 칸에 기록한다.
  2. 지표 계산혼동 행렬의 네 개 숫자로 네 가지를 계산한다. 정확도(전체 샘플 중 맞춘 비율), 정밀도(양성으로 예측한 것 중 실제 양성의 비율), 재현율(실제 양성 중 양성으로 예측한 비율), F1(정밀도와 재현율의 조화평균).
  3. ROC 곡선과 AUC모델의 분류 임계값을 0부터 1까지 바꿔가며 매번 재현율과 위양성율(음성을 양성으로 잘못 예측한 비율)을 계산해 그래프에 점들을 찍는다. 이 점들을 연결한 곡선 아래 면적이 AUC(Area Under Curve)이고, 1에 가까울수록 모델이 좋다.

2질문 제기

3구조적 핵심 예시

주택 가격 예측 모델의 성능 평가에서, 먼저 모든 샘플의 평균 가격만 예측하는 단순한 베이스라인 모델을 만들고 그 오차를 기록한다. 그 다음 특성(방 개수, 면적 등)을 사용하는 복잡한 모델을 만들어 오차를 측정하면, 베이스라인과의 차이로 진짜 개선을 판단할 수 있다.

4단계별 동작 과정

  1. 오차 지표 계산예측값과 실제값의 차이를 측정한다. RMSE(제곱 오차의 평균에 제곱근, 큰 오차에 더 민감), MAE(절댓값 오차의 평균, 전체 오차의 규모), R²(모델이 데이터 변동의 몇 퍼센트를 설명하는지, 0~1 범위).
  2. 베이스라인 모델 수립처음에 단순한 기준 모델(예: 항상 평균값만 예측, 또는 이전 값을 예측)을 만들어 그 오차 지표를 기록한다.
  3. 개선 비교더 복잡한 모델을 만들 때마다 베이스라인의 오차와 비교해, 오차가 실제로 줄었는지 확인한다. 오차가 줄지 않으면 모델의 복잡성만 늘어난 것이다.

학습이 제대로 수렴하는지·과적합인지를 학습 곡선과 SageMaker Debugger의 내장 규칙, 프로파일러의 자원 사용 지표로 자동 감지해 문제 있는 학습 잡을 조기에 잡아내는 것이다.

1상대의 출발점 확인

모델 학습이 끝난 후에 테스트 정확도만 본다. 그런데 학습 과정에서 무슨 일이 일어났는지 모른다. 학습이 제대로 수렴했는지, 가중치가 폭발적으로 커졌는지, 과적합으로 망가졌는지, 그래디언트가 0으로 사라졌는지를 뒤늦게 발견하게 되면 시간과 자원이 낭비된다. 또한 학습 잡이 실패했을 때 어디서 문제가 생겼는지 추적하기 어렵다.

2질문 제기

모델이 제대로 학습하고 있는지, 과적합이나 수렴 실패가 일어나는지를 학습 중에 실시간으로 감지할 수 있을까?

3구조적 핵심 예시

학습 과정에서 훈련 손실(training loss, 훈련 데이터에 대한 오차)과 검증 손실(validation loss, 검증 데이터에 대한 오차)을 매 에폭마다 기록해 그래프로 그린다. 두 곡선이 함께 내려가면 정상 학습, 훈련 손실은 내려가지만 검증 손실이 올라가면 과적합, 둘 다 올라가면 학습이 제대로 되지 않는 것이다.

4단계별 동작 과정

  1. 학습 곡선 추적매 에폭마다 훈련 손실과 검증 손실을 기록하고 시각화한다. 손실 값의 추이와 수렴 여부를 실시간으로 확인할 수 있다.
  2. SageMaker Debugger의 내장 규칙 적용Vanishing Gradient(그래디언트가 0으로 사라짐), Exploding Weight(가중치가 비정상적으로 커짐), Overfitting(과적합 감지), Overtraining(더 이상 개선이 없음) 같은 문제를 자동으로 감지해 경고한다.
  3. 프로파일러로 자원 모니터링CPU 사용률, GPU 메모리 사용률, 데이터 로딩 시간 등을 추적해 학습 잡의 병목을 찾고, 자원 사용 패턴의 이상을 감지한다.

SageMaker Clarify로 모델 편향과 설명 가능성 해석

Clarify가 학습 전후 데이터·모델의 편향 지표를 계산하고 SHAP 기반 특성 기여도를 내놓아, 모델이 왜 그렇게 예측했는지와 특정 집단에 불리하지 않은지를 확인하게 해준다.

1상대의 출발점 확인

모델이 예측을 내리면 그냥 받아들인다. 하지만 모델의 예측이 왜 나왔는지 알 수 없고, 특정 인구집단(성별, 나이, 인종 등)에 편향되지 않았는지 확인하기 어렵다. 신용 승인 모델이 여성 지원자에게만 불공정하게 거절한다면? 의료 진단 모델이 특정 인종의 데이터로 편향되어 있다면? 이를 발견하지 못하면 법적·윤리적 문제가 발생한다.

2질문 제기

모델이 왜 그런 예측을 했으며, 그 예측이 특정 집단에 편향되지는 않았을까?

3구조적 핵심 예시

신용 대출 모델이 신청자 1,000명을 심사했을 때, 남성의 승인율이 80%인데 여성은 40%라면 성별에 따른 편향이 있다. Clarify가 이 편향을 지표로 정량화하고, 개별 승인/거절 결정에서 소득, 신용점수, 나이 중 어느 요소가 얼마나 결정을 좌우했는지 SHAP 값으로 보여준다.

4단계별 동작 과정

  1. 편향 지표 계산Clarify가 학습 데이터와 모델의 편향을 여러 기준(성별, 나이, 인종 등)으로 측정한다. 예를 들어 특정 집단의 양성 예측율과 전체 양성 예측율의 차이를 계산해 편향 점수를 매긴다.
  2. SHAP 기반 특성 기여도 분석개별 예측에서 각 입력 특성(입력값)이 최종 예측에 얼마나 기여했는지를 계산한다. "소득이 +0.3 기여, 신용점수가 +0.5 기여해서 이 사람이 승인되었다"는 식으로 해석할 수 있다.
  3. 결과 해석 및 보고편향 지표와 특성 기여도를 함께 보며 모델의 공정성을 판단하고, 편향이 발견되면 학습 데이터 보정이나 모델 재조정을 검토한다.

트레이드오프 판단, 재현 가능한 실험, 섀도 변형 비교

정밀도와 재현율, 정확도와 비용·지연처럼 서로 맞바꾸는 관계를 요구사항에 맞게 고르고, 실험 추적으로 결과를 재현하며 섀도 테스트로 새 모델을 실제 트래픽 사본에 안전하게 견줘본다.

1상대의 출발점 확인

모델을 한 번 만들고 배포한다. 그런데 정밀도와 재현율, 속도와 정확도 같은 서로 맞바꾸는 관계(트레이드오프)에서 뭘 우선할지 명확하지 않다. 또한 같은 모델을 다시 만들 때 같은 결과가 나올지 보장할 수 없고, 새 모델을 배포했을 때 실제 트래픽에서 어떻게 작동하는지 배포 전에는 알 수 없다.

2질문 제기

여러 모델 후보 중에서 요구사항에 맞는 것을 선택하고, 실험을 재현하며, 새 모델을 안전하게 검증할 수 있을까?

3구조적 핵심 예시

암 진단 모델에서 임계값을 조정해 재현율(병자를 놓치지 않는 비율)과 위양성율(건강한 사람을 병자로 오진하는 비율)의 트레이드오프를 제어한다. 의료 요구사항이 "최소 95% 재현율 필요"이라면 그 기준에 맞는 임계값을 선택한다. 그 다음 섀도 테스트로 새 모델을 기존 모델과 나란히 실제 환자 데이터에 적용해서, 예측이 얼마나 달라지는지 확인한 후 배포 여부를 결정한다.

4단계별 동작 과정

  1. 트레이드오프 판단정밀도(오진 최소화)와 재현율(놓침 최소화), 정확도와 추론 지연시간 같은 상충 관계를 분석해, 요구사항(예: 의료 기준, 비즈니스 목표)에 우선순위를 정한다. 임계값 조정 같은 방법으로 양쪽의 균형을 맞춘다.
  2. 실험 추적과 재현 가능성MLflow 같은 도구로 모델 파라미터, 학습 환경, 랜덤 시드, 메트릭을 기록해, 언제든 같은 결과를 재현할 수 있도록 한다.
  3. 섀도 테스트로 안전한 검증실제 트래픽의 사본에 새 모델(섀도 변형)을 적용해 기존 모델의 예측과 비교한다. 성능이 확인되면 실제 트래픽의 일부를 새 모델로 처리한 후, 점진적으로 비율을 높여 배포한다.

학습이 끝나서 모델 파일(.pth, .pb 같은 가중치 파일)이 손에 있다. 하지만 이 파일만으로는 예측 서비스를 만들 수 없다. 모델을 실행하려면 프로그래밍 언어 런타임(Python, Java 등), 의존 라이브러리(TensorFlow, PyTorch 등), 입출력 처리 코드, 몇 개의 컴퓨터를 할당할지 정해야 한다. 이 모든 것을 수동으로 구성하면 복잡하고 오류가 나기 쉽다.

2질문 제기

학습한 모델을 실제 예측 서비스로 어떻게 변환하고 배포할까?

3구조적 핵심 예시

TensorFlow로 학습한 이미지 분류 모델을 배포할 때, 모델 파일 + TensorFlow 런타임 + 추론 코드를 Docker 컨테이너에 묶는다. 그 컨테이너를 SageMaker에 등록해 Model 객체를 만들고, 그 Model로 EndpointConfig를 작성해(ml.m5.large 인스턴스 2개) 마지막에 Endpoint를 배포하면 HTTPS 호출 주소가 생긴다.

4단계별 동작 과정

  1. Model 객체 생성학습된 모델 아티팩트(가중치·파라미터 파일)와 추론 컨테이너(런타임 환경, 라이브러리, 입출력 처리 코드를 담은 Docker 이미지)를 SageMaker에 등록해 Model 객체를 만든다.
  2. EndpointConfig 작성이 Model을 실행할 때 몇 개의 컴퓨팅 인스턴스를 쓸지, 어떤 사양(ml.m5.large 같은 인스턴스 타입)으로 운영할지, 여러 모델의 트래픽 배분 비율을 정의한다.
  3. Endpoint 배포EndpointConfig를 실제로 시작해 고정된 HTTPS 주소를 받고, 그 주소로 예측 요청을 보내면 학습된 모델이 실시간으로 응답한다.

실시간 엔드포인트와 프로덕션 변형

항상 켜져 있는 HTTPS 엔드포인트로 밀리초 단위 응답을 주는 방식이며, 한 엔드포인트 안에 여러 프로덕션 변형을 두고 트래픽 비율을 나눠 A/B 테스트나 점진 배포를 할 수 있다.

1상대의 출발점 확인

한 엔드포인트에 모델이 하나만 있다. 새로운 모델로 바꾸려면 기존 엔드포인트를 중단하고 새 모델로 재배포해야 하므로 서비스 중단 시간이 생긴다. 또한 새 모델이 정말 좋은지 배포 전에 검증할 수 없고, 천천히 전환할 수 없다. 위험한 배포는 장애를 초래할 수 있다.

2질문 제기

한 엔드포인트 안에서 여러 모델을 동시에 실행하고, 트래픽을 나눠서 안전하게 배포할 수 있을까?

3구조적 핵심 예시

주문 추천 엔드포인트에 모델 v1과 v2를 동시에 배포한다. 들어오는 예측 요청 100개 중 90개는 모델 v1로, 10개는 모델 v2로 처리한다. 모델 v2의 결과를 모니터링해 성능이 좋으면 점진적으로 트래픽 비율을 90:10에서 80:20, 50:50으로 늘려나가다가 최종적으로 100:0으로 전환한다.

4단계별 동작 과정

  1. 프로덕션 변형 설정한 Endpoint 안에 여러 모델을 등록하고 각각에 트래픽 가중치를 할당한다(예: 변형A 80%, 변형B 20%). 각 변형은 독립적인 인스턴스로 실행된다.
  2. 트래픽 분산 실행들어오는 예측 요청이 설정한 가중치 비율에 따라 각 모델로 배분되고, 각 모델은 병렬로 예측을 내놓는다.
  3. A/B 테스트 또는 점진 배포두 모델의 예측 결과와 성능을 비교해 더 좋은 모델을 확인한 후, 트래픽 비율을 천천히 조정하거나 빠르게 전환해 배포를 완료한다. 서비스 중단 없이 안전한 전환이 가능하다.

5본질 요약

한 엔드포인트에 여러 프로덕션 변형(모델)을 두고 트래픽 가중치를 조정해서 A/B 테스트와 점진 배포를 서비스 중단 없이 안전하게 실행하는 것

서버리스 추론과 비동기 추론

서버리스 추론은 인스턴스 관리 없이 요청량에 따라 자동으로 뜨고 내려가는 방식이고, 비동기 추론은 큰 페이로드·긴 처리 시간의 요청을 큐에 넣고 결과를 S3로 돌려주는 방식이다.

1상대의 출발점 확인

기존의 SageMaker 실시간 엔드포인트는 인스턴스를 계속 띄워 놔야 하기 때문에 요청이 없을 때도 비용이 나간다. 또한 크기가 큰 페이로드를 처리하거나 오래 걸리는 작업을 실시간 요청으로 처리할 수 없다.

2질문 제기

요청량에 따라 자동으로 인스턴스가 뜨고 내려가고, 동시에 큰 작업도 효율적으로 처리할 수 있는 방식은?

3구조적 핵심 예시

서버리스 추론 엔드포인트에 요청이 오면 필요한 인스턴스가 자동으로 시작되고 처리 후 곧 종료되며, 비동기 추론은 요청을 SQS 큐에 넣고 백그라운드에서 처리해 결과를 S3에 저장한다.

4단계별 동작 과정

  1. 요청 수신클라이언트가 요청을 보냄. 서버리스는 동기 방식이고 비동기는 비동기 큐에 요청을 넣는 방식이다.
  2. 리소스 할당 및 처리서버리스는 유휴 인스턴스가 있으면 재사용하고 없으면 새로 띄웠다가 처리 후 해제하며, 비동기는 워커가 큐에서 꺼내 처리한다.
  3. 결과 반환서버리스는 응답을 직접 보내고, 비동기는 S3에 저장한 후 알림(SNS/SQS)으로 완료를 알린다.

5본질 요약

인스턴스 관리의 복잡성을 제거하고, 사용 패턴에 따라 비용을 절감하면서도 다양한 처리 방식(실시간/배치)을 지원하는 것

공식 문서https://docs.aws.amazon.com/sagemaker/latest/dg/serverless-endpoints.html

배치 변환(Batch Transform)

엔드포인트를 계속 띄우지 않고 S3에 쌓인 대량 데이터를 한 번에 추론해 결과를 다시 S3에 저장하는 일회성 작업 방식이다.

1상대의 출발점 확인

기존 방식은 엔드포인트를 띄워서 개별 요청을 처리하는데, S3에 이미 쌓여 있는 대량의 데이터를 처리할 때는 하나씩 요청하느라 비효율적이다. 또한 엔드포인트를 계속 띄워야 하므로 불필요한 비용이 발생한다.

2질문 제기

S3에 있는 대량의 데이터를 엔드포인트 없이 한 번에 효율적으로 추론할 수 있는 방법은?

3구조적 핵심 예시

배치 변환은 S3 폴더에 있는 여러 파일을 읽어, 일회성 추론 작업으로 모든 데이터를 한 번에 처리한 후 결과를 다시 S3에 저장한다.

4단계별 동작 과정

  1. 입력 데이터 지정S3 경로를 지정해 처리할 데이터의 위치를 알린다.
  2. 배치 변환 작업 실행SageMaker가 임시 인스턴스를 띄워 데이터를 병렬로 처리하고, 처리가 끝나면 인스턴스를 자동 종료한다.
  3. 결과 저장추론 결과를 지정된 S3 경로에 저장한다.

5본질 요약

대량 데이터를 엔드포인트 없이 일회성 작업으로 처리해 비용을 절감하고 운영을 단순화하는 것

멀티 모델·멀티 컨테이너 엔드포인트와 직렬 추론 파이프라인

하나의 엔드포인트에 여러 모델을 올려 비용을 줄이거나(멀티 모델/멀티 컨테이너), 전처리-추론-후처리 컨테이너를 순서대로 연결해 하나의 요청으로 처리하는(추론 파이프라인) 호스팅 옵션이다.

1상대의 출발점 확인

기존 방식은 모델 하나마다 엔드포인트 하나를 띄워야 하기 때문에 여러 모델을 운영할 때 비용과 관리 복잡도가 급증한다. 또한 전처리와 추론, 후처리가 분리되어 여러 번 요청해야 한다.

2질문 제기

여러 모델이나 처리 단계를 하나의 엔드포인트에서 통합 관리하면서 비용과 지연 시간을 줄일 수 있는 방법은?

3구조적 핵심 예시

멀티 모델 엔드포인트는 여러 모델을 하나의 엔드포인트 안에 올려놓고 요청에 따라 필요한 모델만 로드해 처리하며, 추론 파이프라인은 전처리 컨테이너 → 추론 컨테이너 → 후처리 컨테이너를 순서대로 연결해 하나의 요청으로 처리한다.

4단계별 동작 과정

  1. 요청 수신 및 모델/경로 선택클라이언트가 요청 시 어느 모델을 쓸지 지정하거나, 파이프라인은 입력 데이터를 받는다.
  2. 순서대로 처리멀티 모델은 해당 모델을 메모리에 로드해 추론 수행하고, 파이프라인은 각 컨테이너를 거쳐 단계별 처리를 수행한다.
  3. 결과 반환최종 추론 결과나 처리 결과를 응답으로 보낸다.

5본질 요약

여러 모델이나 처리 단계를 하나의 리소스에서 관리하면서 비용을 줄이고 요청 처리를 단순화하는 것

컨테이너 선택: 사전 빌드 이미지, BYOC, Amazon ECR

추론은 항상 컨테이너 안에서 실행되므로 AWS가 제공하는 사전 빌드 이미지를 쓰거나, 직접 만든 이미지를 Amazon ECR에 올려 쓰는(BYOC) 선택을 한다.

1상대의 출발점 확인

SageMaker 추론은 항상 컨테이너(도커 이미지) 안에서 실행되는데, 직접 도커 이미지를 만들려면 복잡한 설정과 의존성 관리가 필요하고 실수하기 쉽다.

2질문 제기

추론을 실행할 컨테이너를 어떻게 준비할 것인가?

3구조적 핵심 예시

AWS가 제공하는 사전 빌드 이미지(TensorFlow, PyTorch 등 머신러닝 프레임워크가 이미 포함된 이미지)를 그대로 쓰거나, 특수한 요구사항이 있으면 직접 도커 이미지를 만들어 Amazon ECR(AWS의 이미지 저장소)에 올려 사용한다.

4단계별 동작 과정

  1. 사전 빌드 이미지 확인AWS가 제공하는 이미지 중 모델 프레임워크와 버전에 맞는 것이 있는지 확인한다.
  2. 선택 또는 직접 작성있으면 바로 그것을 쓰고, 없으면 Dockerfile을 작성해 도커 이미지를 빌드한다.
  3. ECR에 등록직접 만든 이미지를 Amazon ECR에 올려서 SageMaker 엔드포인트가 참조하도록 한다.

5본질 요약

추론 실행에 필요한 컨테이너를 기성품 또는 커스텀으로 선택해 사용 가능하게 하고, 이를 중앙 저장소(ECR)에서 관리하는 것

공식 문서https://docs.aws.amazon.com/sagemaker/latest/dg/docker-containers.html

컴퓨팅 선택과 엔드포인트 오토 스케일링

모델 크기와 지연 시간 요구에 맞는 인스턴스 종류를 고르고, 호출량 지표를 기준으로 인스턴스 수를 자동으로 늘리고 줄여 비용과 성능을 맞춘다.

1상대의 출발점 확인

기존은 엔드포인트에 고정된 수의 인스턴스를 할당해 놔야 하는데, 요청이 적을 때는 낭비적이고 요청이 많을 때는 지연이 발생한다.

2질문 제기

모델의 크기와 처리 요구, 그리고 실시간 요청량에 맞춰 인스턴스를 자동으로 늘렸다 줄일 수 있을까?

3구조적 핵심 예시

ml.m5.xlarge 같은 인스턴스 타입을 선택해 모델 크기와 지연 시간을 맞추고, 호출 수나 CPU 사용률 같은 지표를 기반으로 인스턴스 수를 자동 조절한다(예: 호출 수 100당 인스턴스 1개 할당).

4단계별 동작 과정

  1. 인스턴스 타입 선택모델 크기, 추론 속도 요구, 메모리 필요량을 고려해 적절한 인스턴스 타입(ml.m5.xlarge, ml.p3.2xlarge 등)을 선택한다.
  2. 오토 스케일링 정책 설정스케일링 지표(호출 수, CPU 사용률)와 목표치를 정한다(예: 평균 호출 수 100이면 인스턴스 1개).
  3. 지표 기반 자동 조절CloudWatch가 지표를 모니터링하고 정책에 따라 인스턴스를 자동으로 추가하거나 제거한다.

5본질 요약

모델 특성에 맞춘 인스턴스 선택과 실시간 요청량 지표를 통한 자동 스케일링으로 비용 효율과 성능을 동시에 달성하는 것

추론 최적화와 다른 배포 대상: Neo, 엣지, ECS·EKS·Lambda·API Gateway

Neo 컴파일이나 양자화 등으로 모델을 더 빠르고 가볍게 만들고, SageMaker 엔드포인트 대신 엣지 기기나 ECS·EKS·Lambda 같은 다른 실행 환경에 배포하는 선택지다.

1상대의 출발점 확인

SageMaker 엔드포인트는 안정적이지만 비용이 높고, 엣지 기기에서는 실행할 수 없으며, 고정된 지연 시간이 있다. 또한 모델 크기가 크면 엣지 환경이나 서버리스 환경(Lambda 등)에서 실행하기 어렵다.

2질문 제기

모델을 더 빠르고 가볍게 만들거나 다양한 실행 환경(엣지, 컨테이너, 서버리스)에 배포할 수 있을까?

3구조적 핵심 예시

SageMaker Neo가 모델을 컴파일해 특정 하드웨어(CPU, GPU, 모바일)에 최적화하고 크기를 줄이며, 최적화된 모델을 엣지 기기, ECS/EKS 클러스터, Lambda 함수, API Gateway 뒤의 서버리스 애플리케이션 등 다양한 환경에 배포한다.

4단계별 동작 과정

  3. 자동 빌드·테스트·배포코드가 main 브랜치로 병합되면 CI/CD 파이프라인이 자동으로 코드를 빌드하고 테스트한 후 배포 단계로 진행합니다.

1상대의 출발점 확인

기존 방식은 모델을 학습하고 배포한 뒤, 그 모델이 계속 같은 성능을 유지한다고 가정합니다. 하지만 실제로는 시간이 지나면서 모델이 받는 입력 데이터의 분포가 달라지거나, 세상의 변화로 인해 모델의 예측 정확도가 떨어집니다. 예를 들어 신용카드 사기 탐지 모델은 학습 시점의 사기 패턴을 학습했지만, 2년 뒤에는 사기 수법 자체가 완전히 달라져 모델의 성능이 급격히 떨어질 수 있습니다. 이런 현상을 발견하지 못하면 배포된 모델이 더 이상 쓸모없어도 계속 운영되는 상황이 발생합니다.

2질문 제기

3구조적 핵심 예시

금융 기관이 대출 승인 모델을 배포했다고 하겠습니다. 학습 데이터는 2023년 1월~6월 고객 신청 정보였고, 모델의 입력값은 나이, 소득, 신용점수, 근무 연수 등 5개 피처입니다. 2024년 9월이 되었을 때, 새로 들어오는 신청자의 평균 소득이 학습 시점보다 30% 높아졌다면, 모델이 보지 못한 새로운 데이터 분포에 직면한 것입니다. 동시에 모델의 예측 정확도도 85%에서 71%로 떨어졌습니다. 이처럼 입력 데이터의 특성이 변하는 현상(데이터 드리프트)과 그로 인한 모델 성능 저하(모델 드리프트)를 감지해야 합니다.

  2. 모니터링 설계 원칙무엇을 감시할지(어떤 지표를 추적), 언제 감시할지(실시간·일일·주간 단위), 어떤 수치 이상이면 경고할지를 미리 결정합니다. 이를 위해 모델을 배포하기 전 학습 데이터나 검증 데이터에서 정상 범위의 통계(평균, 표준편차, 이상치 비율 등)를 계산해 "베이스라인"으로 저장합니다.
  3. 경고와 대응배포된 모델이 받는 실시간 예측 입출력 데이터를 수집해 베이스라인과 정기적으로 비교합니다. 만약 입력값 분포가 베이스라인에서 벗어나거나 정확도가 떨어지면 알람을 보내 데이터 엔지니어나 ML 엔지니어가 원인을 조사하고 모델 재훈련 등 대응 조치를 취합니다.

SageMaker Clarify가 운영 중 예측의 공정성 지표 변화(편향 드리프트)와 각 피처의 중요도 순위 변화(피처 기여도 드리프트)를 베이스라인과 비교해 알려주는 기능이다.

1상대의 출발점 확인

기존의 일반적인 드리프트 모니터링은 데이터의 평균·분산 같은 통계와 모델의 정확도만 추적합니다. 하지만 두 가지 중요한 문제를 간과합니다. 첫째, 모델의 예측이 특정 그룹(나이대, 성별, 인종 등)에 대해 공정하지 않게 변할 수 있습니다. 둘째, 모델 학습 시점엔 중요했던 입력값(피처)이 시간이 지나면서 중요도를 잃고, 다른 피처가 더 중요해지는 현상을 알 수 없습니다.

2질문 제기

모델이 시간이 지나면서 특정 그룹에 대해 불공정해지거나, 중요도 있던 입력 값이 무시되는 현상을 감지할 수 있을까?

3구조적 핵심 예시

채용 추천 모델을 예로 들겠습니다. 학습 시점에는 남성과 여성의 통과율 차이가 2%p(공정함)였고, 회사경력 길이가 가장 중요한 피처였습니다. 하지만 1년 뒤, 최근 6개월 동안 모델의 예측을 분석하니 여성의 통과율이 남성 대비 15%p 떨어졌습니다(편향 드리프트). 동시에 피처 중요도 분석을 다시 하면 회사경력은 4위로 내려가고, 학위 종류와 특정 기술 자격이 더 중요해졌습니다(피처 기여도 드리프트). 이런 변화는 정확도 지표만으로는 감지되지 않지만, 공정성과 모델 신뢰도에 심각한 영향을 미칩니다.

4단계별 동작 과정

  1. 공정성 지표 베이스라인 생성학습/검증 데이터에서 보호 대상 그룹(예: 성별)별로 모델의 공정성을 나타내는 지표(선택률 차이, 거짓 양성률 차이, 거짓 음성률 차이 등)를 계산해 저장합니다.
  2. 피처 기여도 베이스라인 생성학습 시점에 각 입력 피처가 예측에 미치는 영향도(SHAP 값, permutation importance 같은 설명 가능성 도구)를 계산해 피처별 중요도 순위로 저장합니다.
  3. 운영 데이터 비교Model Monitor에서 수집된 최근 예측 데이터를 SageMaker Clarify(공정성 분석 도구)로 분석해서 공정성 지표와 피처 기여도를 다시 계산합니다. 베이스라인과의 변화(편향 드리프트, 피처 기여도 드리프트)를 계산해 리포트합니다.

A/B 테스트와 섀도 테스트로 프로덕션 성능 검증

한 엔드포인트의 프로덕션 변형들에 트래픽을 나눠 비교하는 A/B 테스트와, 실제 트래픽을 복제해 응답을 사용자에게 주지 않고 새 모델을 검증하는 섀도 테스트다.

1상대의 출발점 확인

기존 방식은 새 모델이 완성되면 기존 모델을 통째로 교체해서 배포합니다. 문제점은 새 모델이 실제 운영 환경에서 예상과 다르게 작동할 수 있다는 것입니다. 테스트 데이터에서는 정확도가 좋았지만, 실제 사용자의 다양한 입력값과 예측 패턴을 마주하면 성능이 떨어질 수 있습니다. 만약 이 사실을 모르고 배포했다면 모든 사용자에게 영향을 줍니다. 또한 모델의 성능을 실제 사용자 데이터와 비즈니스 지표(클릭율, 전환율 등)로 확인할 기회 자체가 없었습니다.

2질문 제기

새 모델이 실제 트래픽에서 기존 모델보다 나은지 확인하면서도 사용자 경험을 해치지 않을 수 있을까?

3구조적 핵심 예시

추천 시스템이 기존 모델 A를 사용 중이고, 새 모델 B를 개발했다고 하겠습니다. A/B 테스트를 하면, 같은 시간에 들어오는 사용자를 둘로 나눕니다. 절반은 모델 A의 추천을 받고, 절반은 모델 B의 추천을 받습니다. 1주일 뒤 결과를 비교하면 "모델 A는 클릭율 8%, 모델 B는 클릭율 9%"라는 비즈니스 지표를 얻습니다. 섀도 테스트를 하면, 모든 사용자가 모델 A의 추천만 받습니다. 동시에 백그라운드에서 모델 B도 같은 입력값으로 예측을 실행해 결과를 S3에 저장합니다. 사용자는 절대 B의 결과를 보지 못하므로, 만약 B가 망가져 있어도 사용자에게 영향을 주지 않습니다.

4단계별 동작 과정

  1. A/B 테스트SageMaker 엔드포인트의 "traffic distribution" 설정으로 여러 모델 버전(A, B)을 같은 엔드포인트에 배포합니다. 들어오는 요청의 일부는 모델 A로, 일부는 모델 B로 라우팅합니다. CloudWatch에서 양쪽의 정확도, 응답 시간, 비즈니스 지표(클릭율, 전환율 등)를 실시간으로 비교합니다.
  2. 섀도 테스트모든 사용자 트래픽을 기존 모델(프로덕션 모델)에만 보내서 응답을 생성하고 사용자에게 전달합니다. 동시에 새 모델도 같은 입력으로 실행해 그 결과를 S3에 기록하기만 합니다. 실제 사용자는 절대 새 모델의 출력을 받지 못하므로 위험이 없습니다.
  3. 결과 평가A/B 테스트와 섀도 테스트 각각을 충분한 기간(보통 1주~1개월) 실행한 뒤, 정확도·지연·비즈니스 지표를 통계적으로 비교해 새 모델이 기존 모델보다 나은지 판단합니다. 확신이 있으면 새 모델로 100% 트래픽을 옮깁니다.

SageMaker가 내보내는 호출·자원 지표와 컨테이너 로그를 CloudWatch에서 보고 알람·대시보드로 감시하며, CloudTrail로 누가 어떤 API를 호출했는지 감사하는 방법이다.

1상대의 출발점 확인

기존 방식은 SageMaker 모델을 배포한 뒤, 그 상태를 알기 위해 AWS 콘솔을 열고 수동으로 확인합니다. 문제점은 첫째, 수동 확인이 느리고 비효율적입니다. 둘째, 대량의 모델과 요청이 있을 때 모든 것을 놓치기 쉽습니다. 셋째, 문제가 발생했을 때 누가 언제 무엇을 수정했는지 추적할 수 없습니다. 넷째, 동시에 여러 팀이 같은 모델을 관리할 때 투명성이 부족합니다.

2질문 제기

SageMaker의 성능 지표와 로그를 한곳에서 자동으로 모니터링하고, 문제 발생 시 누가 언제 뭘 했는지 추적할 수 있을까?

3구조적 핵심 예시

금융사의 SageMaker 엔드포인트가 평상시 응답 시간 50ms에서 갑자기 1초로 느려졌습니다. CloudWatch 대시보드를 열면 지난 1시간 응답 시간 그래프가 가파르게 올라가는 것이 시각적으로 보입니다. 동시에 미리 설정한 알람이 "응답 시간 > 500ms"를 감지해서 이메일과 Slack으로 담당자에게 즉시 알립니다. 엔드포인트 로그를 CloudWatch Logs에서 검색하면 "GPU 메모리 부족" 에러가 대량 발생한 것을 발견합니다. 또한 CloudTrail 로그를 확인하면 1시간 전 다른 팀의 엔지니어가 배치 크기를 2배로 늘렸다는 API 호출 기록이 나타납니다.

4단계별 동작 과정

  1. 지표와 로그 수집SageMaker가 자동으로 호출 횟수, 응답 시간, 에러율, CPU/메모리 사용률, 모니터링 위반 개수 등의 지표를 CloudWatch로 전송합니다. 엔드포인트 컨테이너 내 애플리케이션이 출력하는 모든 로그(에러, 경고, 디버그 정보)도 CloudWatch Logs로 모입니다.
  2. 알람 설정CloudWatch에서 특정 지표가 임계값을 넘으면(예: 에러율 > 5%, 응답 시간 > 1초) SNS(알림 서비스)를 통해 이메일·Slack·전화·SMS로 알림을 자동 발송합니다. 여러 지표를 조합한 복합 알람(예: CPU > 80% AND 메모리 > 90%)도 설정 가능합니다.
  3. 대시보드와 감사CloudWatch 대시보드에 여러 지표를 시각화(그래프, 게이지)해서 한 화면에서 전체 상태를 파악합니다. CloudTrail은 SageMaker API 호출(엔드포인트 생성·수정·삭제·설정 변경 등)을 모두 기록해서 호출자·타임스탬프·IP·변경 내용을 추적할 수 있게 해줍니다.

1상대의 출발점 확인

기존 방식은 SageMaker 엔드포인트의 응답이 느리거나 요청이 거부될 때, 어디서 문제가 발생했는지 알기 어렵습니다. 문제점은 병목 지점이 많다는 것입니다. 네트워크 지연일 수도, 모델 추론 자체가 느린 것일 수도, 데이터 전처리 단계가 병목일 수도 있습니다. 또는 AWS 리소스 한도를 초과해서 새 요청이 거부되는 것일 수도 있습니다. 기존엔 이 모든 경우를 구분하기 위해 여러 도구를 번갈아가며 확인해야 했습니다.

2질문 제기

느린 응답이나 요청 거부의 원인(전처리·추론·네트워크·용량 등)을 빠르게 찾을 수 있을까?

3구조적 핵심 예시

사용자가 추천 시스템 API를 호출하는데, 평상시 200ms에 응답하던 것이 갑자기 5초가 걸리기 시작했습니다. X-Ray 분산 추적을 보면, 요청 흐름이 다음과 같습니다: 데이터 전처리 50ms → SageMaker 엔드포인트 대기 4초 → 모델 추론 100ms → 후처리 50ms. 병목은 "대기 4초"입니다. 이는 엔드포인트의 인스턴스가 들어오는 요청을 처리하지 못하고 대기열에 쌓여 있다는 뜻입니다. CloudWatch에서 "요청 동시성 1000개 초과" 로그를 찾고, AWS Service Quotas 콘솔에서 확인하니 이 리전의 ml.m5.large 인스턴스 한도가 100개인데 이미 100개를 다 썼다는 것을 알 수 있습니다. 한도를 1000으로 증설 요청을 AWS에 보내면 수분 내에 승인됩니다.

4단계별 동작 과정

  1. X-Ray 분산 추적API 요청이 엔드포인트에 도착해서 응답을 반환할 때까지 거치는 각 단계(전처리, 모델 호출, 후처리, 네트워크 대기 등)의 소요 시간을 기록합니다. 각 단계에 태그(segment)를 붙여서 어느 부분이 느린지 시각적으로 파악할 수 있습니다.
  2. CloudWatch Logs Insights로 로그 분석엔드포인트 로그와 모델 컨테이너 로그에서 특정 패턴이나 에러를 검색합니다. 예를 들어 "GPU 메모리 부족", "컨테이너 재시작 발생", "요청 스로틀링", "타임아웃" 같은 키워드를 집계해서 근본 원인을 식별합니다.
  3. 서비스 쿼터 확인 및 증설AWS Service Quotas 콘솔에서 현재 리소스 사용량과 리전별 한도(예: 리전당 ml.m5.large 인스턴스 100개, ml.g4dn.xlarge 50개)를 확인합니다. 한도에 근접하거나 초과하면 AWS에 증설 요청을 보냅니다. 일반적으로 사업 용도 요청은 수분~수시간 내 승인됩니다.

2질문 제기

3구조적 핵심 예시

  1. 구매 옵션 선택 및 조합온디맨드(언제든 쓸 수 있지만 비쌈, 개발·테스트용), Savings Plans(장기 약정 시 30~50% 할인, 안정적 워크로드용), 스팟 인스턴스(단기 할인 최대 70%, 중단 위험 있음, 배치 작업·개발용), 리저브드 인스턴스(폐기 예정, Savings Plans 권장) 중 워크로드와 용도에 맞는 조합을 선택합니다.
  2. 태그 기반 비용 추적모든 SageMaker 리소스(엔드포인트, 학습 작업, 노트북, 모니터링 규칙 등)에 비용 센터, 프로젝트명, 환경(프로덕션/개발/테스트) 태그를 붙입니다. AWS Cost Explorer에서 태그별로 비용을 그래프로 시각화해서 어느 프로젝트·팀이 얼마나 쓰는지 명확히 파악합니다.
  3. 예산 알람·권고·스케일링AWS Budgets에서 월간 예산 한도(예: $6000)를 설정해서 초과 시 알람을 발송합니다. AWS Trusted Advisor는 미사용 리소스(1주 이상 사용 안 한 엔드포인트, 높은 가용성이 필요 없는 인스턴스 타입 등)를 자동 탐지해 절감 권고를 보냅니다. Application Auto Scaling을 켜서 요청 부하에 따라 엔드포인트 인스턴스 수를 자동 조정합니다.

IAM 역할·정책·최소 권한과 SageMaker 실행 역할

누가 어떤 AWS 작업을 할 수 있는지 IAM 정책으로 정하고, SageMaker 작업이 대신 쓰는 실행 역할에는 꼭 필요한 권한만 주는 원칙이다.

1상대의 출발점 확인

AWS 초기 사용자들은 권한을 세분화하지 않고 한 사용자에게 모든 리소스 접근을 허용하거나, 역할 없이 접근 키를 직접 공유했습니다. 이는 한 사용자의 접근 키가 유출되면 전체 AWS 환경이 위험해지고, 어떤 사용자가 언제 무엇을 했는지 추적하기 어렵게 만듭니다.

2질문 제기

누가 어떤 AWS 작업을 정확히 할 수 있는지 제어하고, 각 사용자나 애플리케이션이 실제 필요한 권한만 갖도록 하려면?

3구조적 핵심 예시

SageMaker 학습 작업이 S3 특정 버킷에서만 데이터를 읽고, ECR 특정 리포지토리에서만 학습 이미지를 가져오고, CloudWatch에만 로그를 쓰는 IAM 정책을 만들어 SageMaker 작업이 사용할 역할에 할당합니다. 이렇게 하면 학습 작업의 접근 키가 유출되어도 그 세 가지 작업만 가능하고, 다른 리소스는 건드릴 수 없습니다.

4단계별 동작 과정

  1. IAM 정책 정의Action(예: s3:GetObject), Resource(예: arn:aws:s3:::my-bucket/train/*), Effect(Allow/Deny)로 정책 문서를 작성합니다.
  2. IAM 역할 생성정책을 역할에 할당합니다. SageMaker 서비스가 이 역할을 assume할 수 있게 신뢰 관계(Trust Relationship)를 설정합니다.
  3. SageMaker 작업에 역할 지정학습 작업 생성 시 이 역할의 ARN(리소스 고유명)을 지정하면, 작업은 역할의 권한으로만 실행됩니다.

리소스 정책과 교차 계정 접근

S3 버킷·KMS 키 같은 리소스 쪽에 붙이는 정책과 역할 위임으로 다른 AWS 계정이 내 데이터·모델에 안전하게 접근하게 하는 방법이다.

→ 11-01 참조

1상대의 출발점 확인

기존에는 같은 AWS 계정 내에서 역할과 정책으로 접근을 제어하기 쉬웠지만, 다른 계정의 리소스에 접근하려면 복잡한 설정이 필요했습니다. 조직이 여러 계정으로 나뉘거나 파트너사와 데이터를 공유하려면 이 문제가 심각해집니다.

2질문 제기

다른 AWS 계정이 내 S3 버킷이나 KMS 키 같은 리소스에 안전하게 접근하려면 어떻게 설정해야 할까?

3구조적 핵심 예시

Account A의 S3 버킷에 리소스 정책(버킷 정책)을 붙여서 Account B의 특정 IAM 역할 ARN이 s3:GetObject를 할 수 있다고 명시합니다. 동시에 Account B의 그 역할에는 sts:AssumeRole 권한(다른 역할로 전환할 수 있는 권한)을 추가합니다. 그러면 Account B의 사용자는 그 역할로 전환(assume)한 뒤 Account A의 S3 버킷에 접근할 수 있습니다.

4단계별 동작 과정

  1. 리소스 정책 설정S3 버킷에 정책을 붙여 다른 계정의 특정 역할 ARN이 특정 작업(예: GetObject)을 할 수 있도록 정의합니다.
  2. 교차 계정 역할 신뢰 설정다른 계정의 역할에 이 역할을 assume할 수 있는 권한을 신뢰 관계로 설정합니다.
  3. 계정 간 역할 전환 및 접근다른 계정의 사용자가 sts:AssumeRole을 호출해 역할을 전환한 뒤 리소스 정책이 허용하는 작업을 수행합니다.

암호화와 비밀 관리: AWS KMS, Secrets Manager, 데이터 프라이버시

저장 데이터와 전송 데이터를 KMS 키로 암호화하고 DB 자격 증명 같은 비밀은 코드가 아닌 Secrets Manager에 두는 것이다.

1상대의 출발점 확인

이전에는 민감한 데이터가 평문으로 저장되고, 데이터베이스 자격 증명(사용자명·비밀번호)이 애플리케이션 코드에 하드코딩되어 있었습니다. 저장소가 침입당하거나 소스 코드가 유출되면 모든 데이터가 노출됩니다.

2질문 제기

저장된 데이터와 전송되는 데이터를 모두 암호화하고, 민감한 정보는 코드 없이 안전하게 관리하려면?

3구조적 핵심 예시

학습 데이터를 S3에 저장할 때 KMS(Key Management Service) 키로 암호화하고, 데이터베이스 자격 증명은 AWS Secrets Manager에 저장한 뒤, SageMaker 학습 작업이 실행될 때 애플리케이션이 Secrets Manager API를 호출해 필요할 때마다 자격 증명을 조회합니다. 저장소와 코드가 동시에 유출되어도 암호화 키와 Secrets Manager 접근 권한이 없으면 데이터를 읽을 수 없습니다.

4단계별 동작 과정

  1. 데이터 암호화S3, EBS(학습 인스턴스 스토리지), RDS 같은 저장소에서 KMS 키로 저장 데이터를 암호화하고, SageMaker와 AWS 서비스 간 전송 데이터는 TLS(암호화된 통신)로 보호합니다.
  2. 민감한 정보 저장DB 자격 증명, API 키, 토큰 같은 비밀을 코드에 두지 않고 Secrets Manager에 저장합니다.
  3. 런타임에 조회애플리케이션이 실행될 때 Secrets Manager API를 호출해 필요한 자격 증명을 조회하고, 각 작업의 IAM 역할에 조회 권한만 부여합니다.

11보안과 거버넌스11-04

네트워크 격리: VPC, 서브넷, 보안 그룹, PrivateLink, Direct Connect

학습·추론 작업을 인터넷 없는 사설 VPC 안에서 돌리고 VPC 엔드포인트(PrivateLink)로만 AWS 서비스에 접속하게 막는 구성이다.

1상대의 출발점 확인

초기 SageMaker 설정에서 학습과 추론 인스턴스는 공개 인터넷(인터넷 게이트웨이)에 연결되어 있습니다. 이는 외부에서 인스턴스를 공격할 수 있는 경로가 열려 있고, 학습 데이터가 인터넷을 통해 이동할 때 중간에 도청당할 수 있다는 뜻입니다.

2질문 제기

학습과 추론 작업을 인터넷과 완전히 단절된 폐쇄된 네트워크 환경에서만 실행하려면?

3구조적 핵심 예시

SageMaker 학습 인스턴스를 VPC(Virtual Private Cloud, 사설 네트워크)의 프라이빗 서브넷(인터넷 게이트웨이가 없는 서브넷)에 배치하고, AWS 서비스(S3, ECR, CloudWatch)에는 VPC 엔드포인트(PrivateLink, AWS 서비스로 가는 사설 통로)를 통해서만 접속하게 합니다. 이렇게 하면 학습 데이터와 모델이 공개 인터넷을 거치지 않습니다.

4단계별 동작 과정

  1. VPC 및 프라이빗 서브넷 구성VPC를 만들고, 인터넷 게이트웨이가 없는 프라이빗 서브넷을 생성하며, SageMaker 인스턴스를 그곳에 배치합니다.
  2. 보안 그룹 및 네트워크 ACL 설정보안 그룹(인바운드/아웃바운드 트래픽 제어)과 네트워크 ACL(서브넷 수준 방화벽)로 필요한 트래픽만 허용합니다.
  3. VPC 엔드포인트 설정S3, ECR, CloudWatch, SageMaker API 같은 AWS 서비스에 VPC 엔드포인트(Interface 또는 Gateway)를 만들어, 프라이빗 서브넷에서 공개 인터넷을 거치지 않고 이들 서비스에 접속합니다.

감사·컴플라이언스와 CI/CD 보안, 보안 트러블슈팅

CloudTrail 로그로 누가 무엇을 했는지 남기고 규정 준수를 확인하며, 권한 오류 같은 보안 문제를 찾아 고치는 활동이다.

→ 11-01 참조

1상대의 출발점 확인

이전에는 누가 어떤 AWS API를 호출했는지, 언제 리소스가 변경되었는지 기록이 없었습니다. 보안 사건이 발생해도 어느 사용자의 접근 키가 유출되었는지, 어떤 데이터가 접근되었는지 추적할 수 없으며, 규정 준수(컴플라이언스) 감사도 불가능합니다.

2질문 제기

모든 AWS API 호출을 기록하고, 비정상 활동을 찾아내며, 규정 준수를 확인하고 보안 문제를 해결하려면?

3구조적 핵심 예시

CloudTrail에서 전체 AWS API 호출 로그를 수집하고, 특정 사용자의 권한 오류(UnauthorizedOperation)가 많다는 것을 발견했다면 그 사용자의 IAM 정책을 검토해 필요한 권한을 추가하거나 불필요한 권한을 제거합니다. 또한 일반적이지 않은 지역에서의 API 호출이나 대량의 DeleteObject 요청을 찾아 침입 시도나 데이터 삭제 공격을 조기에 탐지합니다.

4단계별 동작 과정

  1. CloudTrail 로깅 활성화CloudTrail을 설정해 모든 AWS API 호출(누가, 무엇을, 언제, 어디서)을 S3 버킷에 기록합니다.
  2. 로그 분석 및 모니터링CloudTrail 로그를 분석해 권한 오류, 비정상 활동(예: 야간 대량 데이터 접근), 규정 위반을 찾아냅니다.
  3. 문제 해결 및 정책 조정발견된 문제(권한 부족, 과도한 권한, 보안 사건)를 해결하고, IAM 정책과 네트워크 설정을 조정하며 CI/CD 파이프라인에 보안 검사를 추가합니다.

5본질 요약

CloudTrail 로그로 모든 AWS 작업을 기록하고 분석해 규정 준수를 확인하며 보안 문제를 조기에 탐지하고 해결하는 것입니다.
