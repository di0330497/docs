#1문제 상황

코드를 팀마다 다른 컴퓨터에서 돌리면 설치한 버전이 달라 결과가 갈립니다. Docker 는 애플리케이션을 다르게 만들어 어디서든 같은 코드를 같은 상태로 실행하게 하는 플랫폼입니다.

Docker 는 애플리케이션을 컨테이너라는 격리된 환경에 넣어 여러 개를 한 컴퓨터에서 함께 돌릴 수 있게 합니다. Docker Engine 이 그 안에서 컨테이너를 실제로 만들고 실행하는 엔진이고, Docker 는 공개된 오픈 소스 프로젝트입니다. 설치는 Docker Desktop 으로 한 번에 할 수 있습니다.

#2핵심 질문

여러 컨테이너를 한꺼번에 다루려면 Docker Compose(→ 01-05)를 쓴다.

#4동작 과정

  1. 나눈다client-server 구조로 CLI 로 명령을 보내면 Docker Engine 이 받아 컨테이너를 만든다. container runtime 이 그 컨테이너를 실제로 실행하는 부품이다.
  2. 돌린다만들어진 컨테이너는 host 의 커널을 나눠 써 자원 격리를 얻는다. 엔진이 같은 컴퓨터에서 여러 개를 동시에 붙들고 있다.
  3. 확인해 볼 것터미널에서 docker version 을 실행해 설치된 엔진과 클라이언트 버전 정보가 보이는지 확인한다.

Linux 는 패키지 관리 도구로 프로그램과 설정을 관리하는 운영체제다. 여기에 Docker Engine 을 설치하면 기본으로 root 만 컨테이너를 다룰 수 있습니다. post-installation steps 로 일반 계정에도 권한을 열어 줍니다.

설치는 apt repository 를 정해 두고 그곳에서 페이지를 받아 온다.

#2핵심 질문

설치한 뒤 일반 사용자도 sudo 없이 docker 명령을 쓸 수 있게 하려면?

#3동작 예시

데몬(→ 02-03)을 켠 상태에서 사용자 계정을 docker 그룹에 넣고 다시 로그인한다. 이제 docker ps 를 sudo 없이 그대로 쳐도 컨테이너 목록이 나온다.

#4동작 과정

  1. 설치한다Install Docker Engine 을 공식 절차대로 설치하고 데몬이 시작되도록 한다. 데몬은 Unix 소켓을 열어 둔다.
  2. 권한을 연다만든 docker 그룹에 사용자를 넣는다. 방화벽 규칙도 필요한 포트에 맞춰 손본다.
  3. 확인해 볼 것docker ps 를 sudo 없이 실행해 오류 없이 목록이 나오는지 확인한다.

Docker CLI — 명령의 모양과 필터링

터미널에서 컨테이너를 다루는 명령줄 도구로, docker [명령] [옵션] [인자] 형태로 동작하고 --filter 로 대상을 걸러 --format 으로 출력 형태를 바꾼다.

먼저 알아야 할 것 01-06

#1문제 상황

컨테이너가 몇 개씩 쌓이면 목록 출력이 길어져 원하는 대상을 찾기 어렵고, 같은 정보를 매번 다른 모양으로 뽑아 써야 한다. docker 명령을 직접 치는 방식(→ 02-06 에서 docker version 확인)은 익히기 어렵다.

Docker CLI 는 docker command 와 그 아래 subcommand 로 동작하는 명령줄 도구다. --filter 로 대상만 골라내고 --format 으로 출력 모양을 바꾼다.

#2핵심 질문

오래된 목록에서 필요한 대상만 골라 원하는 모양으로 볼 수 있을까?

#3동작 예시

이미지가 쌓인 컴퓨터에서 docker images 를 치면 목록이 전부 나온다. 여기에 --filter reference=alpine 를 붙이면 이름에 alpine 이 들어 있는 이미지만 남는다.

#4동작 과정

  1. 명령을 친다docker images 처럼 상위 docker command 다음에 subcommand 를 적어 엔진에 작업을 요청한다. 여기서 엔진은 요청을 처리하는 쪽이고 CLI 는 요청을 전달한다(→ 02-03).
  2. 걸러 낸다--filter "KEY=VALUE" 로 대상 필드와 값을 골라 일치하는 항목만 보여 준다. != 로 반대로 가져올 수도 있다.
  3. 모양을 정한다--format 으로 출력할 항목과 배치만 골라 낸다. tab completion 은 명령어 앞부분을 쳐 후보를 보여 주는 기능이다.
  4. 확인해 볼 것docker images --filter reference=alpine 를 친 뒤 목록에 alpine 계열 이미지만 남는지 본다.

Docker 데몬 — 엔진의 중심 프로세스

컨테이너를 실제로 만들고 관리하는 엔진의 중심 프로세스로, 커널 기능과 컨테이너 실행에 필요한 권한을 이 프로세스가 갖고 있어서 일반 계정에서는 조작할 수 없다.

먼저 알아야 할 것 02-01

#1문제 상황

CLI 로 명령을 보내도 그것을 실제로 수행할 프로그램이 필요하다(→ 02-02). 그 프로그램이 어디서 떠 있는지 모르면, 명령이 왜 안 먹는지, 왜 권한 오류가 나는지 알 수 없다.

Docker daemon 은 컨테이너를 만들고 관리하는 중심 프로세스이고, 실행 파일 이름은 dockerd 다. 이 프로세스를 어디서 띄웠는지 알면 문제를 좁힐 수 있다.

#2핵심 질문

Docker daemon 을 언제 어떻게 시작하고, 죽었을 때 어디서 로그를 볼까?

#3동작 예시

설치 직후 컨테이너가 안 잡힌다. sudo systemctl start docker 로 데몬을 띄우고, systemctl status docker 로 상태를 본다.

#4동작 과정

  1. 시작한다보통 운영 체계의 시스템 유틸리티가 Docker daemon 을 자동으로 띄운다. Ubuntu 계열에서는 sudo systemctl start docker 로 직접 시작하고, 부팅 시 자동 시작을 켜 둘 수도 있다.
  2. 수동으로 띄운다시스템 유틸리티를 쓰지 않을 때는 dockerd 명령으로 직접 실행한다. 이런 경우 실행 권한이 필요할 수 있다.
  3. 원인을 본다troubleshooting the Docker daemon 은 데몬이 왜 멈췄는지를 daemon logs 로 좁혀 보는 절차다.
  4. 확인해 볼 것데몬 상태를 묻는 명령으로 Docker daemon 이 실제로 떠 있는지 확인한다.

데몬이 시작될 때 읽는 설정 파일로, 로그 기록 방식이나 저장 드라이버 같은 엔진의 기본 동작을 여기 적힌 값으로 지정해 둔다.

먼저 알아야 할 것 02-03

→ 02-03 참조

#1문제 상황

설치 직후 docker 명령을 치면 권한 오류가 난다. 데몬은 root 로만 돌아가고 소켓에는 docker 그룹만 닿기 때문이다(→ 02-03).

이 그룹과 기본 동작은 daemon.json 에서 정한다. 파일 하나를 고쳐 데몬 기본값을 바꿀 수 있다.

#2핵심 질문

데몬의 기본 동작을 바꿀 때 무엇을 어디에 적는가?

#3동작 예시

설치 후 문서를 따라 daemon.json 을 열어 docker 그룹을 넣고 데몬을 다시 띄운다. 이제 같은 계정으로 sudo 없이 docker 명령이 된다.

#4동작 과정

  1. 접근을 연다데몬은 유닉스 소켓에 묶여 있고 root 소유다. 데몬 설정 파일에 docker 그룹을 넣어야 일반 계정이 소켓에 닿는다.
  2. 기본값을 적는다log driver 를 정하고, 데몬이 죽어도 실행 중인 컨테이너를 유지하는 live restore, containerd 를 Docker daemon 안에서 쓸지, default ulimits 를 여기 지정한다.
  3. 다시 띄운다바뀐 값을 데몬이 읽도록 재시작한다.
  4. 확인해 볼 것sudo 없이 컨테이너 목록 명령이 되는지 확인한다.

대체 컨테이너 런타임

기본 런타임 대신 runc 같은 다른 프로그램을 컨테이너 생성·실행 프로그램으로 지정해, 보안이나 성능 측면에서 다른 선택지를 쓰는 방법.

먼저 알아야 할 것 02-03

#1문제 상황

기본 런타임은 커널 기능에 직접 기대는 방식이라 일부 환경에서 격리 강도나 성능 문제가 드러난다(→ 02-03).

대체 컨테이너 런타임을 지정하면 그 자리를 다른 프로그램이 맡는다. 보안 모델을 바꾼 선택지가 생긴다.

#2핵심 질문

컨테이너를 실행하는 프로그램을 기본값 아닌 다른 것으로 바꿀 수 있을까?

#3동작 예시

격리를 더 강하게 하려 한다. 데몬 설정에 Wasmtime 같은 런타임을 이름으로 등록해 두고, docker run 시 그 이름을 지정한다.

#4동작 과정

  1. 알아본다containerd 는 기본으로 runc 를 컨테이너 런타임으로 쓴다. runc 는 컨테이너를 실제로 만들어 실행하는 프로그램이다.
  2. 고른다containerd shim API 를 구현한 Wasmtime·gVisor·Kata Containers 는 별도 설정 없이 쓸 수 있다. runc 를 대신하는 종류는 데몬 설정에 직접 등록해야 한다.
  3. 가리킨다containerd image store 를 함께 쓰면 이미지 보관 방식까지 바꿀 수 있다.
  4. 확인해 볼 것컨테이너 목록에서 등록한 이름으로 만든 항목이 실행 중인지 확인한다.

Dockerfile — 이미지 빌드 지시서

Dockerfile 이란 베이스 이미지에 어떤 프로그램과 설정을 얹어 새 이미지를 만들라고 나열한 텍스트 파일로, FROM·RUN·COPY 같은 명령 줄을 위에서 아래로 순서대로 실행해 이미지를 만든다.

먼저 알아야 할 것 02-02

#1문제 상황

컨테이너 하나를 이미지에 담는 방법을 매번 손으로 옮기면 무엇을 넣었는지 알 수 없다(→ 01-03).

Dockerfile 에 명령을 적어 두면 엔진이 그대로 따라 만든다. 같은 구성이 어디서든 재현된다.

#2핵심 질문

이미지에 어떤 파일과 명령을 넣는지 어디에 적어 둘까?

#3동작 예시

앱 코드를 담은 디렉터리에서 Dockerfile 에 FROM, COPY, RUN 을 적고 빌드를 돌린다. 엔진이 각 줄의 결과를 계층으로 쌓아 이미지를 만든다.

#4동작 과정

  1. 시작점을 고른다FROM 은 베이스 이미지를 골라 새 빌드 단계를 시작한다. 그 다음 RUN 으로 패키지 설치 같은 빌드 명령을 실행한다.
  2. 파일을 싣는다COPY 와 ADD 로 로컬 파일과 디렉터리를 이미지에 넣고, ENV·EXPOSE·LABEL·ARG 로 환경변수와 포트 설명, 메타데이터를 정한다.
  3. 실행 진입점을 정한다CMD 는 기본 실행 명령, ENTRYPOINT 는 기본 실행 파일을 지정한다. build context 는 빌드 때 보낼 소스 파일 묶음이다.
  4. 확인해 볼 것이미지를 만들어 실행한 뒤 CMD 나 ENTRYPOINT 에 적은 명령이 실제로 실행되는지 본다.

이미지 레이어란 이미지 한 장이 명령 실행 결과별로 여러 겹으로 쌓인 파일 묶음이고, 빌드 캐시는 그 레이어를 재사용해 다시 만들지 않고 즉시 가져오는 저장 장치다.

먼저 알아야 할 것 03-01

→ 03-01 참조

#1문제 상황

같은 명령 줄을 다시 빌드할 때마다 모든 파일을 새로 만들면 시간이 오래 걸린다(→ 03-01).

image layers 는 각 명령의 결과를 따로 저장해 재사용하게 해 준다. 바뀐 부분만 다시 만든다.

#2핵심 질문

바뀌지 않은 부분은 다시 만들지 않고 어떻게 재사용하는가?

#3동작 예시

의존성이 설치된 줄은 그대로 두고 소스 코드 줄만 고쳐 빌드한다. 앞 계층은 캐시에서 그대로 오고, 고친 줄만 새로 쌓인다.

#4동작 과정

  1. 쌓는다image layers 각각은 파일 추가·삭제·수정을 담은 변경 묶음이고, 만들어진 뒤에는 고칠 수 없다.
  2. 지킨다copy-on-write 는 파일을 바로 바꾸지 않고 사본을 떴다가 바꿔 쓰는 방식으로, 읽기 전용 레이어를 여러 컨테이너가 함께 쓸 수 있게 한다.
  3. 재쓴다layer caching 은 앞 단계가 그대로면 그 결과를 build cache 에서 가져온다. cache invalidation 은 앞 레이어가 바뀐 순간 뒤 단계의 캐시를 무효로 만드는 규칙이다.
  4. 확인해 볼 것같은 Dockerfile 을 두 번 돌렸을 때 두 번째 빌드에서 어느 계층이 캐시로 표시되는지 본다.

Multi-stage build — 빌드에 쓰던 도구를 넣지 않기

Multi-stage build 는 여러 단계로 나누어 앞 단계에서 컴파일한 결과만 골라 마지막 단계로 복사하고 컴파일 도구는 최종 이미지에 싣지 않는 Dockerfile 작성법이다.

먼저 알아야 할 것 03-02

→ 03-02 참조

#1문제 상황

Go 나 Rust 같은 앱은 실행 파일 하나면 되지만, 그것을 만들려면 컴파일러와 라이브러리가 필요하다(→ 03-01). 한 단계로 빌드하면 이 도구까지 이미지에 남아 이미지 크기가 커지고 보안 업데이트 대상도 늘어 난다.

Multi-stage build 는 Dockerfile 에 FROM 을 여러 번 적어 여러 build stage 로 나눈다. 각 단계는 다른 베이스 이미지에서 시작할 수 있고, 원하는 산출물만 다음 단계로 복사해 final stage 에 남긴다. 빌드 스크립트는 따로 필요 없고 docker build 한 번이면 된다.

#2핵심 질문

빌드에만 필요한 도구를 최종 이미지에서 빼고 크기와 보안을 함께 챙기는가?

#3동작 예시

Go 앱 Dockerfile 에 golang 베이스 이미지로 만든 첫 단계와 scratch 라는 빈 베이스 이미지로 만든 마지막 단계가 있다. docker build 를 치면 첫 단계에서 실행 파일이 만들어지고 마지막 단계에 그 파일만 복사된다.

결과 이미지에는 실행 파일과 지정한 실행 명령만 남는다. 컴파일러는 들어 있지 않다.

#4동작 과정

  1. 단계를 나눈다FROM 이 나올 때마다 새 build stage 가 시작된다. 각 단계는 베이스 이미지에서 시작하므로 앞 단계의 파일은 기본적으로 이어지지 않는다.
  2. 결과물만 복사한다COPY --from=0 처럼 어느 단계에서 가져올지 지정해 빌드 산출물만 옮긴다. 그 외 파일은 final stage 에 남지 않아 smaller image 가 된다.
  3. 확인해 볼 것빌드 뒤 docker image ls 를 실행해 만들어진 이미지의 크기가 이전보다 작아졌는지 본다.

빌드 인자와 시크릿

빌드 인자는 Dockerfile 안에 고정하지 않고 빌드 때 넘겨주는 설정값(ARG·ENV)이고, 빌드 시크릿은 비밀번호 같은 민감 값을 이미지 기록에 남기지 않고 빌드에만 임시로 제공하는 장치다.

먼저 알아야 할 것 03-01

#1문제 상황

Dockerfile 에 버전 번호나 서버 주소를 그대로 적으면 값이 바뀔 때마다 파일을 고쳐야 한다. 반대로 비밀번호까지 빌드 인자로 넘기면 그 값이 이미지 기록과 docker history 에 남아 이미지 밖으로 새어 나간다.

Build variables, 즉 ARG 은 Dockerfile 지시의 값을 바꿔 주는 변수이고, build secrets 는 비밀값을 빌드에만 붙여 주는 방식이다. ARG 과 ENV 는 둘 다 Dockerfile 에 선언하고 docker build 옵션으로 값을 주지만, 쓰임이 다르다.

#2핵심 질문

빌드마다 달라지는 값은 어떻게 넘기고 비밀값은 어떻게 이미지에 남기지 않겠는가?

#3동작 예시

의존성 버전을 ARG VERSION 으로 선언해 두고 빌드할 때 값을 지정한다. 이미지에는 그 값이 환경변수로 남지 않는다.

DB 비밀번호가 필요하다면 secret mount 로 빌드 중에만 파일로 붙인다. 빌드가 끝나면 붙였던 비밀 파일은 사라진다.

#4동작 과정

  1. ARG 을 선언한다Dockerfile 안에 ARG 로 빌드 변수를 선언한다. 빌드 명령에서 값을 주면 FROM 이나 RUN 같은 지시가 그 값을 쓴다. 빌드가 끝나면 빌드 인자 값은 최종 이미지에 남지 않는다.
  2. ENV 를 쓴다ENV 로 선언한 환경변수는 컨테이너가 실행될 때에도 남아 설정을 남기는 데 쓴다.
  3. 비밀은 build secrets 로 넘긴다빌드 시크릿은 빌드 단계에만 마운트되는 비밀 파일이다. RUN 중에만 읽히고 이미지 기록에는 값이 남지 않는다.
  4. 확인해 볼 것docker history 로 이미지를 열어 ARG 로 넘긴 값이 명령줄에 남았는지 확인한다.

#1문제 상황

컨테이너는 호스트의 커널을 함께 쓰기 때문에, 컨테이너화만으로는 서로 다른 기종을 해결하지 못한다. linux/amd64 용 컨테이너는 에뮬레이션 없이 arm64 호스트에서 돌지 않고, Windows 컨테이너는 Linux 호스트에서 돌지 않는다.

Multi-platform builds 는 같은 애플리케이션을 여러 아키텍처용으로 묶어 하나의 이미지 이름 뒤에 넣어, 사용하는 CPU 아키텍처에 맞는 variant 가 자동으로 고르게 한다.

#2핵심 질문

내 애플리케이션이 여러 CPU 아키텍처 기기에서 돌아가게 어떻게 만드겠는가?

#3동작 예시

팀에서 amd64 서버와 arm64 개발 노트를 함께 쓴다. 다중 플랫폼 빌드로 이미지 하나를 만들면 push 한 번으로 두 아키텍처용 variant 가 레지스트리에 올라간다.

어느 기기에서 pull 하든 그 기기의 아키텍처에 맞는 variant 가 나온다.

#4동작 과정

  1. platform 을 정한다빌드 대상 platform 을 정해 여러 base images 를 각 아키텍처에 맞는 버전으로 받는다.
  2. 각 아키텍처로 빌드한다같은 소스를 아키텍처별로 따로 빌드해 변형된 이미지를 만든다.
  3. manifest list 로 묶는다만들어진 변형들을 하나의 이미지 이름으로 묶어 레지스트리에 올린다. 같은 이름으로 pull 하면 맞는 것이 선택된다.
  4. 확인해 볼 것docker manifest inspect 로 올린 이미지에 어떤 아키텍처 variant 가 들어 있는지 확인한다.

4. 빌드를 돌리는 곳 — BuildKit 과 builder04-01

Docker 빌드 개요 — 빌드는 어떻게 도는지

Dockerfile 이라는 서술 파일에 이미지 구성(어떤 베이스 이미지 위에 어떤 파일과 명령을 얹는지)을 적어 두면 Docker 엔진이 그 지시를 따라 각 단계를 실행해 이미지 계층을 쌓아 올리는 전체 과정.

먼저 알아야 할 것 03-01

#1문제 상황

같은 앱을 팀마다 다른 컴퓨터에서 다른 순서로 설치하면 결과가 제각각이다. 설치 절차를 매번 손으로 따라 하기엔 느리고, 남는 것도 없다.

Docker Build Overview 는 Dockerfile 에 적은 지시를 기계가 그대로 실행하는 전체 과정이다. Buildx 가 명령을 해석해 요청을 보내고, 실제 실행은 BuildKit 이 맡는다.

#2핵심 질문

설치 절차를 글로 남겨 두고 그것을 자동으로 실행하려면 무엇이 필요한가?

#3동작 예시

개발자는 Dockerfile 에 베이스 이미지와 복사할 파일, 실행할 명령을 차례로 적는다. docker build 를 치면 각 줄이 순서대로 실행되고 결과가 이미지 계층으로 쌓인다.

완성된 이미지는 로컬 저장소에 들어가고, 레지스트리로 보내면 다른 팀도 그대로 받을 수 있다.

#4동작 과정

  1. frontend 가 해석한다frontend 는 Dockerfile 문법과 빌드 옵션을 읽어 지시 목록으로 바꿔 주는 앞부분이다. docker build 명령은 Buildx 를 감싼 껍데기이고 Buildx 가 이 역할을 맡는다.
  2. backend 가 실행한다BuildKit 은 builder 라고 부르는 서버로, 지시를 해석해 각 단계를 실행한다. 빌드 결과는 클라이언트로 돌아오거나 레지스트리에 올라간다.
  3. pipeline 을 따라 쌓는다build pipeline 이 정의한 각 단계가 순서대로 실행되며 각 단계의 출력물이 다음 단계의 입력이 되고 마지막에 이미지가 만들어진다.

BuildKit — 기본 빌드 엔진

Docker 의 기본 이미지 빌드 엔진으로, Dockerfile 각 지시를 병렬로 처리해 빠르고 효율적인 빌드를 수행하며 여러 단계를 서로 독립적으로 실행하는 현대적 빌드 백엔드.

먼저 알아야 할 것 04-01

#1문제 상황

기본 빌드 엔진은 Dockerfile 을 위에서 아래로 한 줄씩 처리해 속도가 느리고, 실행 환경마다 설정을 다시 맞춰야 한다(→ 04-01). 특히 네트워크가 필요한 단계가 얽히면 빌드가 길게 늘어진다.

BuildKit 은 이 문제를 풀기 위해 나온 빌드 백엔드다. 동작 방식은 buildkitd.toml 설정 파일로 바꾼다. rootful 모드에서는 /etc/buildkit/buildkitd.toml, rootless 모드에서는 ~/.config/buildkit/buildkitd.toml 을 읽고, Custom Dockerfile syntax 지시로 다른 파서도 쓸 수 있다.

#2핵심 질문

빌드 엔진의 동작을 설정 파일 하나로 어디까지 바꿀 수 있는가?

#3동작 예시

빌드가 외부 네트워크를 막힌 환경에서 돌아야 한다면 buildkitd.toml 에 proxyNetwork 를 켠다. 권한 없이 기기 접근이 필요한 경우에만 insecure-entitlements 목록에 device 를 넣고, 빌드 산출물의 출처 기록을 늘리고 싶으면 provenanceEnvDir 로 추가 설치를 읽게 한다.

이 파일을 고쳐 데몬을 다시 띄우면 이후 모든 빌드에 그 설정이 적용된다.

#4동작 과정

  1. 설정 파일을 둔다root 는 BuildKit 상태를 저장할 경로고, 그 외 항목은 buildkitd.toml 에서 켜고 끈다. configure BuildKit 은 이 파일을 편집해 기본값을 바꾸는 일이다.
  2. 데몬을 다시 시작한다BuildKit 데몬(buildkitd) 이 시작할 때 이 파일을 읽어 새 설정으로 빌드를 수행한다. rootless BuildKit 은 권한 없이 돌아가므로 사용자 홈 경로의 파일을 쓴다.
  3. 안전 항목을 조심한다insecure-entitlements 는 기본적으로 꺼져 있고, 켜면 빌드가 호스트 네트워크와 기기에 접근할 수 있게 된다.
  4. 확인해 볼 것데몬을 다시 띄운 뒤 같은 Dockerfile 을 빌드해 앞 단계가 재사용되는지 확인한다.

빌드 캐시 정리와 최적화

변경된 지시 이후 단계만 다시 실행해 빌드 속도를 높이는 캐시를, 더 이상 쓰이지 않는 캐시 항목을 정리하고(cache prune) 캐시가 잘_hit 되도록 Dockerfile 을 다듬는 일.

먼저 알아야 할 것 03-02

#1문제 상황

Docker 는 Dockerfile 의 지시마다 레이어(→ 03-02)를 쌓고, 앞 지시가 그대로면 그 레이어를 빌드 캐시에서 재사용한다. 문제는 순서를 잘못 잡으면 안 바뀐 부분까지 캐시가 깨져 매번 전체를 다시 만든다.

빌드 캐시 정리와 최적화는 레이어 순서를 고쳐 캐시 재사용률을 높이고, 쓰이지 않는 항목을 지우는 작업이다.

#2핵심 질문

빌드가 느릴 때 캐시가 덜 깨지게 Dockerfile 을 어떻게 정리하고 오래된 항목을 지울까?

#3동작 예시

체크아웃한 저장소에서 이미지 빌드를 걸었다. 위에서부터 6분이나 걸리고 CACHED 표시가 몇 개뿐이다. 명령 순서를 바꿔 다시 걸으니 대부분의 단계가 CACHED 로 나온다.

오래 쌓인 builder prune 을 한 번 돌리면 이후 빌드가 다시 빨라진다.

#4동작 과정

  1. 순서를 정한다자주 바뀌지 않는 명령을 위로, 자주 바뀌는 COPY 를 아래로 옮긴다. Optimize cache usage in builds 는 의존성 설치처럼 느린 단계를 앞쪽에 두어 반복 빌드를 줄이는 지침이다.
  2. 컨텍스트를 줄인다빌드에 보내는 파일 묶음(build context)에서 불필요한 파일을 빼면 전송과 캐시 무효화가 줄어든다.
  3. 캐시 항목을 정리한다build garbage collection 은 builder 가 든 빌드 캐시 기록을 되감는 일이고, docker buildx prune 은 쓰이지 않는 항목을 지운다.
  4. 확인해 볼 것빌드 출력에서 각 단계 앞에 CACHED 가 붙는지 보고, 지운 뒤 첫 빌드가 다시 만드는 단계가 무엇인지 확인한다.

이미지 pull 과 사용량 제한

pull(당겨오기)은 레지스트리 서버에서 이미지를 내려 받는 동작이고, pull 요청(usage) 횟수와 대역폭을 계정 단위로 세므로 조직 설정에서 한도와 유지 기간을 정해 둘 수 있다.

#1문제 상황

컨테이너를 띄울 때마다 이미지를 내려 받으면 Registry 서버로 요청이 반복된다(→ 05-02). 서버는 요청을 계정 단위로 세어 일정량을 넘으면 막는다.

pull usage and limits 는 받은 횟수와 대역폭을 세어 한도를 정해 두는 기능이다.

#2핵심 질문

Docker Hub pull 을 계속 반복할 때 어디까지 허락되고 남는 한도는 어떻게 보는가?

#3동작 예시

CI 파이프라인에서 빌드마다 base image 를 pull 하다 limit 에 걸려 pull 이 실패한다. 로그인한 상태로 바꾸고 rate limits 를 확인하니 여유가 늘어난다.

한도를 넘지 않게 pull 을 줄이려면 optimizing Docker Hub usage 를 검토한다.

#4동작 과정

  1. pull 을 센다Docker Hub pull 은 버전 확인과 실제 다운로드를 합친 동작으로 세며, 버전 확인만으로는 사용량이 늘지 않는다. 여러 아키텍처용 이미지는 아키텍처마다 한 번씩 센다.
  2. 한도를 정한다rate limits 는 로그인 여부와 구독에 따라 다르게 잡힌다. 이 값은 계정의 settings 에서 확인한다.
  3. 사용을 줄인다optimizing Docker Hub usage 는 이미지를 매번 받지 않도록 로컬에 캐시해 두고 필요한 것만 받는 쪽이다.
  4. 확인해 볼 것Docker Hub 계정 settings 화면의 사용량 표시와 남은 rate limit 을 본다.

다중 이미지(manifest list) 다룰 때

manifest list(매니페스트 리스트)는 하나의 이미지 이름 뒤에 여러 아키텍처용 variant 를 묶어 둔 참조 정보로, 이 이름을 pull 하면 사용 중인 CPU 아키텍처에 맞는 이미지가 자동으로 골라진다.

#1문제 상황

컨테이너는 호스트 커널을 나눠 써서 amd64 컨테이너를 arm64 컴퓨터에서 그대로 돌릴 수 없다(→ 01-02). 아키텍처마다 이미지를 따로 만들면 이름이 너무 많아진다.

manifest list 는 이 변형들을 하나의 이름 뒤에 묶어 두는 참조 정보다.

#2핵심 질문

하나의 이미지 이름으로 여러 CPU 아키텍처에서 돌릴 수 있게 묶어 두려면 어떻게 하는가?

#3동작 예시

amd64 와 arm64 용 이미지를 하나의 이름으로 묶어 Registry 에 올린다. amd64 컴퓨터에서 docker pull 을 하면 그 이름에 묶인 목록을 보고 이 컴퓨터에 맞는 amd64 이미지를 자동으로 고른다.

#4동작 과정

  1. 여러 판을 만든다다중 플랫폼 빌드로 각 아키텍처의 platform-specific image 를 따로 만들어 같은 repository name 의 tag 아래에 둔다.
  2. 목록으로 묶는다docker manifest 명령으로 여러 이미지를 하나의 manifest list(image index)로 묶어 push 한다. 그러면 한 이름만 알면 된다.
  3. 골라 받는다multi-platform image 이름을 pull 하면 클라이언트가 image index 를 보고 자기 CPU 에 맞는 variant 를 자동으로 받는다.
  4. 확인해 볼 것pull 후 이미지 목록에 들어 있는 항목의 아키텍처가 이 컴퓨터의 CPU 아키텍처와 같은지 본다.

비공개 registry 는 로그인한 계정에만 이미지를 push·pull 할 수 있게 잠근 이미지 저장소로, docker login 으로 받은 자격 증명(config.json)을 써서 인증한다.

먼저 알아야 할 것 05-02

→ 05-02 참조

#1문제 상황

Docker Hub 의 public 저장소는 누구나 이미지를 내려받을 수 있지만, 회사 내부 전용 이미지나 subscription 전용 기능을 쓰려면 읽을 수 없는 곳이어야 한다(→ 05-02).

private registry 는 로그인한 계정에만 push·pull 을 허용하는 이미지 저장소다. docker login 으로 통과한 뒤에야 push 도 되고, CA certificates 로 서명된 인증서를 쓰는 저장소라면 그 사양까지 지정해 준다.

#2핵심 질문

내 이미지 저장을 비공개로 걸어 두고, 내 계정으로만 push 하고 pull 하는 것은 어떻게 하는가?

#3동작 예시

팀 배포 스크립트에서 비공개 registry 주소 앞에 계정 이름을 붙여 docker login 으로 들어간다. Docker Desktop 이면 운영체제 키체인에 credentials 가 저장된다.

같은 스크립트가 곧바로 docker push 를 실행해 사내 저장소에 이미지를 올리고, 배포 서버는 그 계정으로 로그인한 뒤 pull 해서 컨테이너를 띄운다.

#4동작 과정

  1. 로그인한다registry 주소와 계정·비밀번호를 docker login 에 주면 서버가 자격을 확인한다. 통과한 credentials 는 설정된 credential store 에 저장되며, credential store 를 정하지 않으면 Docker 설정 파일인 config.json 에 base64 로 저장된다.
  2. 인증서를 지정한다CA certificates 를 요구하는 저장소는 docker login 에 CA 서명 파일을 함께 넘겨 그 인증서를 신뢰하도록 설정한다. Verify repository client with certificates 로 연결이 확인된다.
  3. 확인해 볼 것Docker Desktop 에서 Settings 의 credential store 항목에 계정이 저장되어 있는지 보고, docker login 에 사설 인증서를 준 뒤 push 가 되는지 확인한다.

이미지 서명은 제공자의 개인 키로 만든 도장이 이미지에 붙는 것으로, pull 할 때 Docker 가 해당 키로 도장을 풀어 출처와 무결성을 확인한다.

먼저 알아야 할 것 05-05

#1문제 상황

registry 에 올린 이미지가 정말 우리 조직이 만든 것인지, 중간에 파일이 바뀌지 않았는지는 pull 받는 쪽만으로 알 수 없다. tag 와 digest 로는 내용이 바뀌었는지 알 수 없다(→ 05-05).

이미지 서명은 제공자의 개인 키로 만든 도장이 이미지에 붙는 것이다. 서명자 Notary 와 trust data 를 함께 쓰면 push 와 pull 양쪽에서 확인을 자동화할 수 있고, 서명하지 않은 이미지는 Docker Scout 로 점검해 대신 확인한다.

#2핵심 질문

받은 이미지가 우리 것이고 변조되지 않았다는 것을 자동으로 확인하려면 어떻게 하는가?

#3동작 예시

빌드 파이프라인에서 tag 하나를 정해 sign an image 로 이미지 서명을 붙인 뒤 push 한다. 배포 서버는 같은 trust store를 쓰고 pull 하므로 서명이 없거나 다른 제공자의 이미지면 거부된다.

서명 키를 빌드마다 손으로 넣지 않으려면 환경 변수로 통제 도구에 전달하는 절차를 둔다.

#4동작 과정

  1. 키를 준비한다제공자 키와 delegation 키를 로컬 Docker trust store 로 불러온다. delegation 키에는 비공개 키를 두는 비밀번호를 함께 요구해 불러오기 때 쓴다.
  2. 이미지에 서명한다Notary 로 이미지와 tag 를 묶어 서명한다. DOCKER_CONTENT_TRUST_REPOSITORY_PASSPHRASE 같은 환경 변수를 클라이언트에 전달하면 이 서명을 자동으로 수행할 수 있고, trust data 를 로그인 쪽에서 함께 옮긴다.
  3. 확인해 볼 것서명된 tag 를 pull 한 결과에 표시되는 서명 상태를 보고, trust store에 들어 있는 키 이름을 확인한다.

먼저 알아야 할 것 01-06

#1문제 상황

컨테이너는 호스트에서 돌아가는 프로세스 하나다. 이 프로세스는 자기 파일 시스템·네트워크·프로세스 트리를 호스트와 분리해 갖는다(→ 01-02).

docker run 은 이 이미지를 받아 컨테이너를 만들어 실행하는 명령이다. 형태는 docker run [OPTIONS] IMAGE[:TAG|@DIGEST] [COMMAND] [ARG...] 이며, tag 를 생략하면 latest 로 간다(→ 01-03).

#2핵심 질문

이미지 하나를 골라 컨테이너로 실행하려면 어디서부터 시작하는가?

#3동작 예시

개발자는 터미널에서 docker run -d -it --rm ubuntu 를 친다. 이미지가 없으면 레지스트리에서 받아오고(→ 01-04), 컨테이너가 백그라운드로 떠 있는 채 셸에 붙어 명령을 받는다.

컨테이너 lifecycle 이 시작되고 바로 실행 상태가 된다. 종료하면 --rm 이 붙어 있어 컨테이너가 자동으로 지워진다.

#4동작 과정

  1. 실행한다docker run 이 이미지 참조로 컨테이너를 만들고 실행한다. Running containers 는 여기서 하나가 시작된다.
  2. 입력과 이름을 붙인다-d 로 백그라운드에 띄우고, -it 로 입출력을 붙여 대화형 셸을 쓴다. 끝에 실행할 명령을 덧붙이면 이미지에 박힌 실행 파일을 대신 쓴다(→ 06-02).
  3. 확인해 볼 것실행 직후 docker ps 를 치면 방금 만든 컨테이너가 실행 중으로 보이는지 확인한다.

#2핵심 질문

#3동작 예시

기존 데이터베이스 컨테이너가 표준 포트를 쓰고 있다. 새 인스턴스는 --name 으로 이름을 정하고 네트워크를 골라 다른 이름으로 붙인다.

#4동작 과정

  1. 어떤 기본값인지 본다컨테이너는 이미지 설정에 적힌 실행 파일을 그대로 가져온다. 여기서 시작하는 값을 기본값이라 부른다.

  3. 확인해 볼 것docker inspect 로 컨테이너를 열어 환경 변수와 이름이 어떤 값으로 들어갔는지 확인한다.

볼륨은 Docker 가 정한 자리에 숨어 있어 개발 중 코드를 바로 고쳐 반영하기 어렵다. 호스트의 설정을 컨테이너에 넣어 주는 것도 필요하다. Bind mounts는 사용자가 고른 호스트 경로의 actual directory 를 컨테이너에 그대로 붙인다. volume 과 달리 host path 를 내가 정하므로 편집과 백업을 직접 처리한다.

#2핵심 질문

호스트에 있는 특정 경로를 컨테이너에서 그대로 쓰려면 어떻게 하지?

#3동작 예시

개발 중 웹 컨테이너가 소스 코드를 읽어야 한다. 호스트 작업 폴더를 컨테이너의 소스 경로에 마운트해 실행한다. 호스트에서 저장한 코드가 다시 빌드 없이 반영된다.

#4동작 과정

  1. 경로를 고른다컨테이너에 붙일 호스트의 absolute path 를 정한다. 상대 경로도 쓸 수 있지만 기준이 달라지기 쉽다.
  2. 마운트 옵션을 준다docker run 의 mount option 으로 host path 와 컨테이너 경로를 대응시킨다. -v 뒤에 경로:경로 형태를 쓴다.
  3. 확인해 볼 것컨테이너 안에서 마운트 지점에 호스트에서 만든 파일이 보이는지 ls 로 확인한다.
  4. 읽기 전용으로 막는다설정을 넣어 줄 때는 read-only bind mount 로 지정해 컨테이너가 고치지 못하게 한다.

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 마운트를 요청한다docker run 에 --tmpfs 옵션을 주면 컨테이너에 tmpfs mounts 가 생긴다. ephemeral filesystem 이라 수명이 컨테이너와 같다.
  2. 크기를 정한다--tmpfs-size 로 최대 크기를 지정한다. 이 값은 --memory 상한을 넘어 추가 메모리를 주지 않는다.
  3. 확인해 볼 것컨테이너 안에서 마운트 지점의 파일이 컨테이너 종료 후에도 남아 있는지 확인한다.
  4. 사용처를 나눈다image mounts 는 빌드 단계에서 이미지와 소스를 함께 보는 다른 방식으로 쓰인다.

Bridge network driver — 기본 통로

컨테이너마다 별도의 가상 네트워크 장치를 만들고 호스트의 실제 인터페이스에 가상의 브리지(가상 교환기)를 씌워, 여러 컨테이너가 호스트를 모르면서 서로 통신하게 하는 Docker 기본 네트워크 드라이버.

먼저 알아야 할 것 06-06

#1문제 상황

컨테이너마다 네트워크 장치가 따로 있어도 서로를 모르고 바깥 통신 경로도 없다(→ 01-02, → 08-06). Bridge network driver 는 호스트의 실제 인터페이스 위에 가상의 브리지(컨테이너끼리 패킷을 중계하는 소프트웨어 스위치)를 만들어 이 문제를 푼다.

붙은 컨테이너는 host 와 같은 브리지 안의 컨테이너와 자유롭게 통신하고, 다른 네트워크와 Docker 호스트 바깥에서는 차단된다.

#2핵심 질문

여러 컨테이너를 한 곳에 연결하면서 바깥과는 막는 기본 통로를 무엇으로 만들까?

#3동작 예시

웹 앱 컨테이너와 DB 컨테이너를 함께 실행한다. 앱 컨테이너에서 DB 컨테이너의 IP 로 접속하면 둘이 붙어 있는 브리지 안에서만 오가는 트래픽이 그대로 전달된다.

같은 브리지에 붙은 컨테이너만 서로를 볼 수 있고, 다른 브리지의 컨테이너는 접근할 수 없다.

#4동작 과정

  1. 브리지를 띄운다Docker 엔진이 설치되면 default bridge 라 이름 붙은 브리지가 만들어진다. 이 기본 브리지는 Docker 엔진이 늘 써 온 docker0 이며 docker run 한 컨테이너는 여기에 자동으로 붙는다.
  2. 컨테이너를 붙인다붙은 컨테이너마다 네트워크 인터페이스가 생기고 subnet 안의 IP 주소를 받는다. 브리지 안의 컨테이너끼리는 서로 접근할 수 있고 다른 네트워크와 호스트 밖에서는 막힌다.
  3. 바깥으로 나가게 한다masquerading 으로 컨테이너가 바깥으로 나갈 때 호스트의 IP 주소를 대신 쓰게 한다. 그래서 바깥 장비는 컨테이너 IP가 아니라 Docker 호스트의 IP만 본다.
  4. 확인해 볼 것docker network inspect bridge 를 실행해 컨테이너가 붙은 subnet 과 gateway 가 어떻게 배정됐는지 확인한다.

docker run -p 8080:80 으로 컨테이너를 실행하면 호스트의 8080 포트로 들어온 요청이 컨테이너의 80 포트로 전달된다. 브라우저로 호스트 주소의 8080 에 접속하면 컨테이너 안의 웹 화면이 열린다.

#4동작 과정

  1. 짝을 정한다-p 또는 --publish 에 호스트 포트:컨테이너 포트 형태로 적는다. -P 를 쓰면 EXPOSE 로 선언해 둔 모든 포트를 임의 번호로 공개한다.
  2. 방화벽 규칙을 만든다Docker 가 NAT(네트워크 주소 변환)과 masquerading 규칙을 만들어 요청을 컨테이너로 넘긴다. 브리지 밖의 다른 네트워크에서도 이 공개 포트로 접근할 수 있다.
  3. 확인해 볼 것docker ps 의 PORTS 칸에 0.0.0.0:8080→80/tcp 같은 매핑이 보이는지 확인한다.

#1문제 상황

#2핵심 질문

네트워크 격리를 없애야 할 때, 그리고 통신을 완전히 막아야 할 때 무엇을 고르는가?

#3동작 예시

#1문제 상황

Overlay network driver 는 각 호스트의 브리지 위에 가상의 네트워크를 하나 더 얹어 이 일을 한다.

#2핵심 질문

#4동작 과정

  1. 겹친 네트워크를 만든다docker network create 로 만드는 overlay network 는 swarm overlay 로 각 호스트 위에 얹힌다. 브리지 드라이버와 같은 명령으로 만든다.
  2. 여러 개를 붙인다컨테이너와 서비스는 하나의 네트워크에만 그려 있지 않고 여러 네트워크에 동시에 붙을 수 있다. 서로 붙어 있는 네트워크끼리만 통신된다.
  3. 확인해 볼 것docker network inspect 결과의 Driver 가 overlay 인지 Scope 가 swarm 인지 확인한다.

방화벽 규칙과 패킷 필터링

Docker는 컨테이너가 오가는 패킷을 통과시키기 위해 iptables나 nftables(호스트의 패킷을 검사하고 허용·차단 규칙을 두는 커널 기능)에 규칙을 자동으로 넣어 다른 트래픽이 컨테이너로 새어 들어오지 않게 막는다.

→ 08-01 참조

#1문제 상황

Docker 는 iptables(호스트의 패킷을 검사하고 허용·차단 규칙을 두는 커널 기능)에 규칙을 자동으로 넣어 이 일을 한다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 규칙을 자동으로 넣는다Docker 는 브리지 네트워크를 위해 방화벽 규칙을 만든다. ipvlan·macvlan·host 네트워크에는 규칙을 만들지 않는다. 만들어진 규칙은 브리지 동작에 필요하므로 직접 바꾸지 않는다.
  2. 백엔드를 고른다기본은 iptables 이고 nftables 도 쓸 수 있다. 두 백엔드의 브리지 기능은 같으며 firewall-backend 엔진 설정으로 고른다.
  3. 직접 거를 때사용자가 만든 규칙은 DOCKER-USER 체인에 넣는다. 이 체인은 어떤 컨테이너로 출발하는지와 관계없이 컨테이너로 들어오는 트래픽을 먼저 검사한다.
  4. 확인해 볼 것iptables -L DOCKER-USER 을 실행해 그 체인에 어떤 규칙이 들어 있는지 확인한다.

Compose 파일의 services

#4동작 과정

Compose 파일의 volumes 와 networks

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

  2. 네트워크를 선언한다최상위 networks 에 네트워크 이름을 적고, 쓸 서비스의 networks 항목에서 그 이름을 가리킨다. Compose 가 그 안에서 전용 네트워크를 만들어 각 서비스 컨테이너를 붙인다.

여러 Compose 파일 합치기와 include

override 같은 여러 Compose 파일을 함께 읽어 설정을 덮어씌우거나, include 로 다른 파일의 일부를 가져와 재사용해 큰 설정을 나눠 관리하는 방법이다.

먼저 알아야 할 것 09-02

#1문제 상황

공통 설정을 모든 파일에 복사해 두면 수정할 때 여러 군데를 고쳐야 하고, Compose 파일이 수백 줄로 커진다.

여러 Compose 파일을 합치기와 include는 이 문제를 푼다. Merge Compose files 는 docker compose -f a.yml -f b.yml up 처럼 여러 파일을 함께 읽고 정해진 규칙으로 설정을 합친다. use include to modularize Compose files 는 다른 파일의 일부만 가져와 재사용하게 한다.

#2핵심 질문

공통 설정은 한 곳에 두고 환경별 차이만 다른 파일로 나눠 어떻게 관리하는가?

#3동작 예시

base.yml 에 공통 서비스 설정을 두고 override.yml 에 그 서비스의 포트와 환경변수만 바꾼다. 두 파일을 함께 실행하면 services.foo.key2 는 override.yml 의 값으로 덮이고, key3 은 base.yml 값만 남는다.

#4동작 과정

  1. 여러 파일을 합친다Merge Compose files 규칙대로 YAML 매핑은 없는 항목을 더하고 같은 키의 값을 뒤 파일이 덮는다. 시퀀스는 앞의 값에 뒤 파일의 값을 덧붙인다. Fragments 는 여러 YAML 조각을 한 파일로 미리 합쳐 두는 쪽이다. 단 command·entrypoint·healthcheck 같은 셸 명령 값은 예외 규칙이 따로 있다.
  2. 일부만 가져온다include 로 다른 파일을 불러와 공통 설정을 재사용하고, override 파일에는 그 중 바꿀 것만 남긴다. profiles 절은 특정 조건에서만 쓸 묶음을 지정한다.
  3. 확인해 볼 것두 파일을 함께 실행한 뒤 docker compose config 에서 어느 값이 남았는지 확인한다.

#1문제 상황

#2핵심 질문

비밀값을 파일에 남기지 않고 주입하면서 운영에서 잘 뜨게 하려면 어떻게 구성하는가?

#4동작 과정

  1. 비밀을 정의한다최상위 secrets 절에 비밀 이름과 제공 방법을 적는다. Compose 는 이 비밀 한 개짜리 파일을 컨테이너에 bind mount 한다. 이 방식은 Linux 컨테이너에서만 동작하며 Windows 컨테이너는 디렉터리 bind mount만 지원한다. services 절의 secrets 항목으로 권한을 명시적으로 준 서비스만 읽는다.

#2핵심 질문

#4동작 과정

  3. 확인해 볼 것prune 실행 전후로 docker images 목록에 있던 이름 없는 이미지가 사라졌는지 확인한다.

디스크을 차지하는 자원의 크기와 되찾을 수 있는 양을 어떻게 확인하는가?

#4동작 과정

  1. 요약을 본다docker system df 를 실행하면 종류별로 총 개수와 크기, reclaimable(되찾을 수 있는 양)이 표로 나온다. 이 값으로 어떤 종류를 정리할지 정한다.
  2. 자세히 내려다본다-v, --verbose 를 붙이면 이미지별로 REPOSITORY·TAG·IMAGE ID·CREATED·SIZE·SHARED SIZE·UNIQUE SIZE 가 펼쳐져 어떤 이미지가 큰지 보인다. 한 이미지 목록이 필요하면 docker images 로도 볼 수 있고, 전체 요약은 docker info 에서도 확인할 수 있다.
  3. 확인해 볼 것docker system df 실행 후 표에 네 줄(Images·Containers·Local Volumes)이 나오는지 확인한다.

먼저 알아야 할 것 10-02

#1문제 상황

container state 를 가진 컨테이너의 start·stop·die 같은 변화와 이미지의 pull·push·tag 가 이벤트 객체로 나타나면, 언제 무슨 일이 있었는지 추적이 된다.

#2핵심 질문

Docker 엔진에서 지금 무슨 일이 일어나고 있는 걸 어떻게 실시간으로 보나?

#3동작 예시

배포 직후 터미널에 docker system events 를 켜 둔다. 이미지 pull 이 시작되고 컨테이너가 start 된 줄이 시간과 함께 차례로 찍히고, health_status 이벤트가 올라온 것을 그 자리에서 확인한다.

#4동작 과정

  1. 이벤트를 켠다docker system events 명령이 엔진의 이벤트 스트림을 붙잡아 시간순으로 출력한다. 기본적으로 최근 256건만 남아 있고, 컨테이너·이미지·볼륨 등 오브젝트 종류마다 이벤트 종류가 다르다.
  2. 걸러 본다--filter 로 이벤트 종류나 대상을 지정해 관심 있는 줄만 남긴다. docker ps 로 지금 대상 목록을 확인해 두고 좁히면 좋다.
  3. 확인해 볼 것필터 없이 켠 뒤 이미지에 tag 를 하나 붙여, 그 줄이 목록에 뜨는지 본다.

Docker object label 로 메모 붙이기

컨테이너나 이미지 같은 Docker 오브젝트에 key=value 형태의 라벨(메타데이터)을 달아 두는 기능으로, 나중에 filter 로 해당 오브젝트만 골라 보거나 관리를 자동화할 수 있다.

먼저 알아야 할 것 10-02

#1문제 상황

여러 팀이 컨테이너를 함께 띄우면 어느 컨테이너가 누구 것인지 이름만으로는 알기 어렵다. Docker object labels 는 오브젝트에 직접 이름을 붙여 저장한다.

label 을 단 오브젝트만 filter by label 로 골라 낼 수 있어, 관리 정보를 코드와 함께 두고 자동화까지 잇는다.

#2핵심 질문

어떤 컨테이너가 어느 환경·어느 팀의 것인지 어떻게 표시하고 다시 찾아낼까?

#3동작 예시

개발용 DB 컨테이너를 띄우면서 환경과 소유자를 label 로 지정한다. 나중에 목록을 볼 때 그 label 값으로 거르면 개발용 컨테이너만 골라 낼 수 있다.

#4동작 과정

  1. 붙인다label 은 문자열로 저장되는 key-value 쌍의 metadata 다. 한 오브젝트 안에서 key 는 유일해야 하고, 같은 key 를 다시 쓰면 마지막 값이 앞의 값을 덮어쓴다.
  2. 찾는다filter by label 로 label 값이 일치하는 오브젝트만 골라 listing 한다. 서드파티 도구까지 쓸 계획이면 key 앞에 소유 도메인의 역순 표기(com.example.some-label)를 붙인다.
  3. 확인해 볼 것label 을 붙여 만든 컨테이너의 목록에 key=value 가 함께 보이는지 본다.

엔진 지표를 Prometheus 로

Docker 엔진이 기본으로 노출하는 메트릭 API(/metrics)를 Prometheus 같은 모니터링 도구가 주기적으로 긁어 가 CPU·메모리·I/O·네트워크 사용량과 이미지 pull 통계 등을 그래프로 모아 보는 방법이다.

먼저 알아야 할 것 10-03

#1문제 상황

Collect Docker metrics with Prometheus 는 그 metrics endpoint 를 Prometheus 가 긁어 가 CPU·메모리·I/O 같은 container metrics 를 시간별 그래프로 쌓는다.

#2핵심 질문

Docker 엔진이 만든 컨테이너들의 자원 사용량을 시간 흐름으로 보고 어떻게 남겨 둘까?

#3동작 예시

Prometheus 를 컨테이너로 띄워 Docker 를 대상으로 등록한다. 몇 분 지나면 컨테이너별 메모리 사용 그래프가 그려지고, 어느 컨테이너가 평소보다 많이 먹는지 화면에서 비교한다.

#4동작 과정

  1. 주소를 정한다daemon.json 에 metrics-address 를 적어 데몬이 metrics endpoint 를 열게 한다. Docker Desktop 에서는 설정 화면에서 이 값을 지정한다.
  2. 수집시킨다Prometheus 가 그 endpoint 를 주기적으로 긁어 daemon metrics 를 저장한다. 대상은 Docker 엔진 자체이며 애플리케이션 수치는 여기서 나오지 않는다.
  3. 확인해 볼 것브라우저에서 metrics endpoint 주소로 접속해 숫자가 나열된 페이지가 열리는지 본다.

#5한 줄 요약

#2핵심 질문

  3. 받는다만들어진 산출물은 지정한 곳으로 돌아온다. 로컬 엔진의 이미지 저장소나 레지스트리가 목적지가 된다.

Docker daemon socket 보호

dockerd 가 리슨하는 소켓(원격 API 엔드포인트)은:root 권한으로 컨테이너를 다루는 통로이므로, root 사용자만 접근하게 하고 Docker 그룹을 별도로 두며 TLS 로만 네트워크를 건 뒤 방화벽과 사용자 권한 제한으로 남는 접근 경로를 막아 두는 것.

먼저 알아야 할 것 02-04

#1문제 상황

Docker 데몬 소켓에 닿으면 root access to the host 가 가능하다. 그래도 기본 상태에서는 그 권한이 넓게 열려 있다.

Protect the Docker daemon socket 는 docker group 멤버만 다루게 하고, 다른 데몬에 붙을 때는 SSH 로만 나가게 해 root-equivalent 권한이 새어 나갈 통로를 막는다.

#2핵심 질문

호스트를 root 와 동등하게 다룰 수 있는 Docker 데몬 소켓에 어떤 통로로만 들어갈게 할까?

#3동작 예시

다른 컴퓨터에 원격으로 작업을 해야 해 docker context create 로 ssh://docker-user@host1.example.com 형태의 접속 정보를 만든다. docker context use 로 그 이름에 바꾸면 이후 명령이 그 데몬에 붙는다.

#4동작 과정

  1. 한정한다daemon socket 에는 root 와 docker 그룹에 속한 계정만 닿게 한다. 소켓 권한이 이 둘 외에는 닫혀 있어야 한다.
  2. 통로를 정한다로컬 데몬은 로컬에서만 쓰고, 다른 데몬에는 SSH 나 TLS(HTTPS) 소켓으로만 연결한다. 원격 계정에는 미리 소켓 권한을 부여한다.
  3. 확인해 볼 것docker context ls 목록에 새 컨텍스트 이름이 나오고 현재 표시가 그 이름으로 바뀌는지 본다.

11. 잠근다 — 보안 경계와 여러 대로 확장11-02

seccomp 프로필로 syscall 제한

허용된 시스템 콜 목록(허용 목록, allow list)만 컨테이너 안에서 실행 가능하게 만들어, 컨테이너가 커널에 요청할 수 있는 작업을 좁혀 탈출과 권한 남용을 막는 기본 보안 기능.

먼저 알아야 할 것 11-01

#1문제 상황

소켓 권한만 좁혀 두어도 컨테이너 안의 프로그램은 커널의 syscall 을 자유롭게 부를 수 있다(→ 11-01). seccomp 는 이 목록 자체를 좁힌다.

Seccomp security profiles 는 지정된 syscall 만 남기고 나머지를 막아, 컨테이너가 할 수 있는 작업을 한 목록으로 제한한다.

#2핵심 질문

컨테이너 안의 프로그램이 커널에 요구할 수 있는 작업 범위를 어디까지로 좁힐 수 있을까?

#3동작 예시

컨테이너를 실행한 뒤 그 안에서 기대 밖의 커널 작업을 시도해 본다. seccomp 프로필에 없는 요청은 실패로 돌아오고, 에러를 내지 않고 조용히 무시되는 security non-events 도 생긴다.

#4동작 과정

  1. 프로필을 받는다컨테이너를 만들 때 seccomp 프로필을 넘기면 그 목록만 쓸 수 있다. 커널이 seccomp 를 켜 두어야 동작한다.
  2. 막는다default seccomp 은 기본으로 syscall 을 거부하는 allowlist 형태로, 300여 개 중 약 44개를 꺼 둔다. 필요하면 AppArmor security profiles 를 함께 쓴다.
  3. 확인해 볼 것컨테이너 안에서 프로필이 허용하지 않은 명령을 쳐 보고 거부되는지 확인한다.

#5한 줄 요약

user namespace 로 컨테이너 격리

컨테이너 안의 root 를 호스트의 일반 사용자 신원(UID/GID)으로 매핑해, 컨테이너가 권한을 잘못 사용하더라도 호스트의 실제 root 권한에는 못 미치게 만드는 격리 방식.

먼저 알아야 할 것 11-02

#1문제 상황

syscall 을 좁혀도 컨테이너 안의 프로그램은 여전히 root 로 돈다(→ 11-02). 그 root 가 호스트의 실제 root 라면 탈출했을 때 권한이 그대로 따라온다.

user namespace 는 이 root 를 호스트의 덜 중요한 신원으로 다시 매핑해, 안에서 아무리 권한을 써도 호스트에는 못 미치게 만든다.

#2핵심 질문

컨테이너 안에서 root 로 보이는 사용자 신원을 호스트의 어떤 신원으로 바꿔야 권한 남용이 막히는가?

#3동작 예시

데몬을 userns-remap 으로 켠 뒤 컨테이너 안에서 uid 0 인 프로세스를 확인한다. 호스트에서 보면 그 프로세스는 일반 사용자 신원으로 매핑되어 루트 권한이 없다.

#4동작 과정

  1. 범위를 정한다userns-remap 으로 지정된 범위의 UID/GID 가 네임스페이스 안에서 0부터 65536까지의 일반 번호로 보인다. 호스트에서는 권한 없는 신원으로만 쓰인다.
  2. 여유분을 잡는다매핑은 /etc/subuid 와 /etc/subgid 두 파일에 적힌 범위를 쓴다. 이 파일이 실제 신원 부여의 재료가 된다.
  3. 알아 둔다이 설정에서도 데몬은 root 로 돈다. 데몬까지 root 없이 돌리려면 rootless mode 를 쓴다.
  4. 확인해 볼 것컨테이너 안에서 본 uid와 호스트에서 ps 로 본 그 프로세스의 사용자 이름이 다른지 확인한다.

#5한 줄 요약

user namespace 격리컨테이너 안의 root 를 호스트의 덜 중요한 신원으로 재매핑해 권한이 밖으로 못 나가게 하는 것

먼저 알아야 할 것 05-06

#1문제 상황

이미지를 만들면 그 안에 어떤 패키지가 어느 버전으로 들어 있는지 직접 알기 어렵다(→ 01-03). 그래서 배포 뒤에 이미 알려진 문제가 새로 드러나도 어디서 왔는지 찾느라 헤맨다.

Docker Scout 는 이미지 하나를 검사해 내부 패키지 버전과 알려진 취약점을 대조한다. 어떤 패키지가 문제인지와 고치는 방법을 함께 보여 준다.

#2핵심 질문

내 이미지에 이미 알려진 취약점이 들어 있는지 어떻게 확인하지?

#3동작 예시

취약한 의존성이 있는 Node.js 앱을 이미지로 빌드해 레지스트리에 올린다. Docker Scout 로 이 이미지를 열면 Image details view 에 패키지 목록과 각 항목의 심각도, 고치는 방법이 나온다.

같은 이미지를 v2 로 다시 올리면 지난번 결과와 비교해 문제 수가 줄었는지 볼 수 있다.

#4동작 과정

  1. 설치하고 켠다Docker Scout 는 Docker CLI 확장 기능으로 설치해 기능을 켠다. 계정에 로그인해 두면 레지스트리에 올린 이미지까지 검사할 수 있다.
  2. 분석한다이미지 안의 각 레이어를 훑어 패키지와 버전을 뽑아 알려진 취약점과 맞춘다. 결과에는 문제 심각도와 해결 제안이 붙는다(→ 11-05).
  3. 결과를 나눈다Image details view 를 열어 어떤 패키지가 문제인지 확인한다. SBOM, 즉 이미지 구성품 목록을 함께 뽑아 팀과 공유할 수 있다.
  4. 확인해 볼 것이미지 상세 화면에 패키지별 취약점 목록과 심각도 표시가 나타나는지 본다.

Scout SBOM 과 policy 평가

SBOM(이미지에 포함된 소프트웨어 구성품 목록)을 뽑아 가시성을 확보하고, policy(규칙)로 취약점 허용 기준을 정해 이미지나 CI 파이프라인이 그 기준을 통과하는지 자동 평가하는 것.

먼저 알아야 할 것 11-04

→ 11-04 참조

#1문제 상황

취약점을 하나씩 고치는 동안 새로운 취약점이 계속 쌓인다(→ 11-04). 무엇까지 허용하고 무엇은 막아야 하는지 기준을 정해 두지 않으면 통과 여부를 사람이 매번 판단해야 한다.

Scout SBOM 과 policy 평가는 이미지 구성품 목록인 SBOM 을 뽑고, 미리 정한 policy 로 통과 여부를 재는 기능이다.

#2핵심 질문

이 이미지가 우리 기준을 만족하는지 자동으로 판정할 수 있을까?

#3동작 예시

릴리스 파이프라인에서 이미지 하나를 검사한다. CLI 가 이미지를 SBOM 으로 색인하고 advisory database, 즉 권고 취약점 목록과 VEX(해당 취약점이 이 이미지에서 실제로 영향이 있는지 표기한 데이터)를 얹은 뒤 각 policy 를 평가한다.

결과에서 기준을 넘는 취약점이 나오면 빌드를 실패 처리한다. 검사는 로컬에서 돌아서 이미지 내용이 외부로 나가지 않는다.

#4동작 과정

  1. SBOM 을 만든다Docker Scout SBOMs 로 이미지의 구성품과 버전을 목록으로 뽑는다. 이 목록을 팀에 공유해 무엇이 들어 있는지 보이게 한다.
  2. policy 를 정한다Evaluate policies 로 기준을 정한다. 기본 제공 규칙을 쓰거나 임계값을 바꾸거나 Rego 라는 규칙 언어로 직접 쓴다.
  3. 예외를 남긴다Manage vulnerability exceptions 로 특정 취약점을 무시한다고 기록해 둘 수 있다. CI 에서는 Docker Scout GitHub Action 으로 같은 평가를 돌린다.
  4. 확인해 볼 것정책 평가 결과에서 통과·실패 항목과 예외 처리된 취약점이 어떻게 표시되는지 본다.

Scout SBOM 과 policy 평가이미지의 구성품 목록을 뽑고 정한 기준으로 통과 여부를 재는 것

Swarm mode — 여러 Docker Engine 을 한 덩어리로

여러 Docker Engine 을 manager 와 worker 노드로 묶어 오케스트레이션 계층으로 관리하는 클러스터 모드이며, 매니저가 선언한 스웜 단위의 복제 컨테이너 서비스와 비밀 값을 각 노드에 배치한다.

먼저 알아야 할 것 11-01

#1문제 상황

Docker Engine 여러 대에 컨테이너를 나눠 띄우면 어떤 컴퓨터가 죽었을 때 사람이 대신 옮기고, 어디가 몇 개 돌아야 하는지 외워 두어야 한다(→ 02-03).

Swarm mode 는 여러 Docker 호스트를 하나의 스웜으로 묶어, 선언한 상태를 Docker 가 계속 유지하게 하는 오케스트레이션 계층이다.

#2핵심 질문

여러 Docker Engine 에 서비스 복제본을 나눠 두고 자동으로 유지하려면 어떻게 하지?

#3동작 예시

서비스를 만들 때 원하는 상태인 desired state 를 복제 수와 노출 포트로 선언한다. 그러면 스웜이 그 수만큼 컨테이너를 각 노드에 띄운다.

worker node 하나가 죽으면 그 노드의 task 를 다른 노드로 옮긴다. task 는 스원 서비스에 속해 manager 가 관리하는 컨테이너 한 개다.

#4동작 과정

  1. 노드를 편 나눈다Swarm mode key concepts 에 따라 manager node 는 구성원 관리와 작업을 나눠 주는 역할, worker node 는 서비스를 실제로 실행하는 역할을 맡는다. 한 호스트가 둘 다 해도 된다.
  2. 서비스를 선언한다How services work 규칙에 따라 복제 수와 네트워크·저장 자원·공개 포트를 적으면 스원이 그 상태를 지킨다. 죽은 노드의 task 는 다른 곳에서 다시 뜬다.
  3. 비밀 값을 나눈다Manage sensitive data with Docker secrets 로 비밀 값을 manager 가 노드별로 전달해 마운트되게 한다. Orchestration 계층은 swarmkit 이며 Docker Engine 안에 들어 있다.
  4. 확인해 볼 것노드 목록에서 각 노드가 manager 와 worker 역할을 함께 맡는지 볼 수 있다.
