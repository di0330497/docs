Amazon API Gateway 란 무엇인가

Amazon API Gateway 는 AWS 에서 제공하는 관리형 서비스로, 인터넷이나 사설망에서 온 요청을 받아 보냈던 API 와 엔드포인트에 정리된 형태로 노출해 줘 HTTP 요청만으로 서비스를 쓰게 한다.

#1문제 상황

서버가 만든 기능은 사내망 안의 주소에만 있다. 외부에서 보이게 하려면 주소·인증·트래픽 처리를 직접 만들어 붙여야 한다. Amazon API Gateway는 그 일을 AWS가 맡는 fully managed, 즉 관리형 서비스다. 내부 데이터를 지킨 채 API front door를 세워 요청만 주고받게 해 준다. back end as a service라는 형태로 동작하므로 서버를 직접 만들지 않는다.

#2핵심 질문

내 백엔드 앞단에 외부용 API 주소를 어떻게 세우는가?

#3동작 예시

팀이 만든 주문 조회 기능을 모바일 앱에 연다. 앱은 AWS가 만든 엔드포인트 주소로 GET 요청을 보내고, 주문 목록을 JSON으로 받는다. 누가 호출했는지 확인하고 몇 건이 들어왔는지도 기록된다.

#4동작 과정

  1. 주소를 만든다REST, HTTP, WebSocket API 중 하나를 골라 리소스와 메서드를 붙인다. 이때 쓰이는 이름이 REST API다.
  2. 백엔드에 붙인다Lambda 함수나 다른 AWS 서비스, 외부 웹 서비스를 호출 대상으로 연결한다. stateless client-server communication, 즉 요청마다 상태를 들지 않는 통신을 쓴다.
  3. 보낸다표준 HTTP 메서드인 GET, POST, PUT, PATCH, DELETE를 그대로 노출해 클라이언트가 호출하게 한다. 외부 앱 개발자에게 공개해 여러 쪽에서 함께 쓰게 할 수도 있다.
  4. 확인해 볼 것콘솔에서 만든 API의 엔드포인트 주소로 요청을 보내 응답 본문이 오는지 확인한다.

API Gateway 의 기본 개념

API 를 구성하는 가장 작은 단위를 리소스(resource)라고 부르고, 각 리소스 아래에 메서드(GET·POST 등)를 붙여 하나의 요청 단위를 만들고, 호출 대상인 백엔드 연동을 통합 타입(integration)이라고 부른다.

먼저 알아야 할 것 01-01

#1문제 상황

주소 하나만으로는 기능을 표현할 수 없다. 몇 개의 묶음으로 관리하고 어디까지 배포했는지 알고어야 한다(→ 01-01). API Gateway는 요청 하나가 됩니다는 단위를 정해 이름 붙인다.

리소스(resource)는 API 구성의 가장 작은 단위고, 그 아래 메서드(method)가 붙어 하나의 요청 단위를 이룬다. 이 묶음을 한 번에 올리는 배포(deployment)와 환경별 그릇인 stage가 더해지고, API Gateway ARN이 이 구성을 가리키는 고유 이름이 된다.

API의 요청 단위와 배포 단위를 어떻게 나누고 부르는가?

#3동작 예시

주문 API에 /orders 리소스를 만들고 그 아래 GET 메서드를 둔다. 개발자가 만든 리소스 묶음을 하나의 stage에 배포해 실제 호출 가능한 상태로 만든다. 이 API는 API Gateway ARN으로 다른 AWS 서비스에서 찾아 쓴다.

#4동작 과정

  1. 리소스를 둔다애플리케이션 논리에 따라 REST API 안의 경로 묶음을 리소스 트리로 정리한다. 자식 리소스를 넣어 계층을 만든다.
  2. 메서드를 붙인다리소스 하나에 GET·POST 등 고유한 HTTP 메서드를 하나 이상 붙인다. 각 메서드가 요청 단위 하나가 된다.
  3. 배포한다이 리소스 묶음을 한 개 이상의 stage에 배포한다. stage는 같은 API의 버전과 환경을 나눠 담는다.
  4. 확인해 볼 것콘솔의 리소스 트리에서 /orders 아래 GET 메서드가 하나의 요청으로 보이는지 확인한다.

REST API 와 HTTP API 중 고르기

REST API 는 광범위한 기능과 VPC 링크·AWS IAM 같은 세밀한 제어를 제공하는 오래된 방식이고, HTTP API 는 더 단순하고 저렴하며 낮은 지연으로 동작해 REST 만큼 제어가 필요 없는 서비스에 알맞다.

먼저 알아야 할 것 01-02

#1문제 상황

HTTP로 노출되는 API는 형태가 두 가지다. 선택은 choose between REST APIs and HTTP APIs, 즉 어느 쪽을 쓸지 가리는 문제고 기준은 기능·가격·특성의 차이(feature comparison)에 있다.

REST API는 기능이 더 많고 가격은 높다. HTTP API는 기능을 최소로 두어 더 낮은 가격으로 설계됐다.

#2핵심 질문

내 서비스에는 어느 쪽의 기능이 필요한가?

#3동작 예시

팀이 내부 요청만 처리하는 경량 API를 만든다. API 키나 요청 검증이 필요 없으므로 HTTP API를 고르고, 리소스와 메서드를 몇 개만 등록해 배포한다.

#4동작 과정

  1. 필요 기능을 센다API 키, 클라이언트별 스로틀링, 요청 검증, AWS WAF 연동, private API endpoint가 필요하면 REST API가 답이다. 이 기능들 없으면 HTTP API로 충분하다.
  2. 엔드포인트 타입을 본다Edge-optimized와 Regional, Private는 REST API만 지원하고 HTTP API는 Regional만 지원한다.
  3. 비용과 지연을 본다feature comparison 표에서 latency와 price 차이를 확인해 트래픽 규모에 맞는 쪽을 고른다. HTTP API는 낮은 지연을 목표로 만들어졌다.
  4. 확인해 볼 것콘솔에서 두 API를 각각 만들고 리소스 목록에 차이 나는 설정 항목이 얼마나 되는지 비교한다.

네 가지 API 형태 — REST·HTTP·WebSocket·portals

한 서비스 안에서 REST API·HTTP API·WebSocket API·API Gateway portals 라는 기능이 서로 다른 네 가지 형태로 제공되며, portals 는 조직 내부의 API 묶음을 한 곳에서 찾아 쓰는 용도로 쓰인다.

먼저 알아야 할 것 01-02

#1문제 상황

요청을 한 번 보내고 한 번 받는 방식만으로는 실시간 알림을 전달할 수 없다. 유지되는 연결로 먼저 말을 거는 기능도 필요하다. 게다가 조직이 되면 여러 사람이 만든 API를 한곳에서 찾아야 한다.

API Gateway는 API Gateway REST APIs와 API Gateway HTTP APIs를 요청·응답 방식으로 제공하고, WebSocket APIs는 연결을 열어 둔 채 양방향 메시지를 주고받으며, API Gateway portals는 여러 API를 묶어 찾는 단위를 준다.

#2핵심 질문

내 서비스의 대화 방식에 맞는 API 형태는 무엇인가?

#3동작 예시

대시보드에 주문이 들어올 때마다 알림을 띄워야 한다. REST API로 주문을 받는 API를 두고, 알림은 WebSocket API의 유지 연결로 브라우저에 밀어 보낸다. 사내 다른 팀이 만든 API들은 portals에서 목록으로 찾아 연다.

#4동작 과정

  1. 요청 응답 방식을 고른다REST API는 클라이언트 요청에 서비스가 동기적으로 응답하는 방식을 쓴다. HTTP API는 같은 방식에 설정을 훨씬 적게 쓰는 형태다(→ 01-03).
  2. 지속 연결 방식을 고른다WebSocket API는 연결을 한 번 열어 둔 뒤 양방향으로 메시지를 주고받는 지속 연결을 제공한다. Lambda 함수나 다른 AWS 서비스를 연결 대상으로 둔다.
  3. 여러 API를 묶는다API Gateway portals는 여러 API를 한 단위로 묶어 관리하고 찾는 곳이다. 묶인 안에서 외부 공개용과 내부 전용을 나눠 본다.
  4. 확인해 볼 것콘솔에서 REST·HTTP·WebSocket 세 종류를 하나씩 만들고 각 API 화면의 동작 방식이 어떻게 다른지 본다.

할당량과 알아둘 것

API Gateway 에는 계정·리전스·API 단위로 정해진 사용량 한도(할당량)가 걸려 있어 한 번에 만들 수 있는 API 수나 요청 처리량, 리소스 수가 이 값을 넘으면 새 리전스를 쓰거나 한도를 올려야 한다.

먼저 알아야 할 것 01-01

#1문제 상황

모든 요청은 그저 통과하는 게 아니다. 앞단에서 걸러지는 양과 처리 속도에는 천장이 있다. 이 한도를 알아야 설계를 미리 깎을 수 있다(→ 01-01).

할당량은 계정·리전·API 단위로 정해지는 quotas다. API 종류마다 REST API quotas와 HTTP API quotas가 따로 있고, 새 API를 쓰기 전에 알아둘 점이 important notes로 정리되어 있다.

#2핵심 질문

한 계정과 리전에서 API Gateway가 어디까지 받아 주는가?

#3동작 예시

팀이 주문 API를 만들었는데 리소스를 막 추가하자 새 API 생성이 막힌다. 무엇이 부족한지 확인하니 계정·리전 단위 리소스 수에 닿은 것이었다. 새 리전에서 다시 만들거나 한도를 올려 해결했다.

#4동작 과정

  1. 한도 종류를 구분한다계정·리전 전체에 걸리는 양과 API 하나에만 걸리는 양이 따로 있다. throttle quota는 초당 요청 수로 정해지고 버스트 여유가 붙는다.
  2. 형태별로 확인한다REST API quotas와 HTTP API quotas를 나누어 보고, 같은 이름의 한도라도 어떤 형태에 붙었는지에 따라 값이 다르다.
  3. 한도를 올리거나 위치를 바꾼다올릴 수 있는 항목은 상격을 요청하고, 올릴 수 없는 항목이면 새 리전에서 API를 다시 만든다.
  4. 확인해 볼 것콘솔의 계정 한도 화면에서 자신의 리전에 적용된 항목 이름과 현재 사용량이 어떻게 보이는지 확인한다.

보안 정책과 IP 주소 타입

API 가 어떤 IP 주소(IPv4 와 IPv6 등)를 받을지 그리고 어떤 보안 수칙(예: IP 대역 차단, TLS 강제 등)을 REST API 수준에서 지정하는 설정.

먼저 알아야 할 것 02-01

#1문제 상황

API가 외부에 열리면 통신 도중 내용을 바꿔치거나 엿보는 공격이 들어온다. 어떤 암호 방식만 받을지 정하지 않으면 오래된 취약한 연결도 그대로 받아 준다(→ 02-01).

보안 정책은 이때 쓰이는 규칙이다. 클라이언트가 TLS handshake를 맺을 때 API Gateway가 받아들일 TLS version과 cipher suite를 정해 이 둘을 막는다. IPv4 and IPv6 어떤 주소로 들어올지도 함께 지정한다.

#2핵심 질문

이 API 는 어떤 암호 연결과 어떤 IP 주소만 받을 것인가?

#3동작 예시

규제 대상 서비스라 오래된 방식은 막아야 한다. 보안 정책에서 enhanced security policy를 고르고 TLS 1.0을 허용하지 않게 바꾼다. 이 정책은 이름이 SecurityPolicy_로 시작하는 규칙이며 포스트 양자 암호화 쓸 때 쓴다. 이때 endpoint access mode도 함께 지정한다.

#4동작 과정

  1. 정책 종류를 고른다TLS_1_0과 TLS_1_2는 supported security policies 가운데 레거시 계열이라 이전 동작과 맞출 때 쓴다. 이름이 SecurityPolicy_로 시작하는 것들은 enhanced security policy다.
  2. 강한 계열을 쓴다규제 대상이나 고급 거버넌스, 포스트 양자 암호화가 필요하면 enhanced security policy를 고르고 endpoint access mode를 함께 설정한다.
  3. 주소 타입을 정한다IPv4 and IPv6 가운데 받을 IP 주소 종류를 지정해 어떤 주소에서 오는 요청만 받는다.
  4. 확인해 볼 것콘솔에서 보안 정책을 바꾼 뒤 허용된 TLS 버전 목록이 어떻게 갱신되는지 확인한다.

메서드 요청과 메서드 응답

하나의 API 메서드(GET·POST 등)에 대해 호출자가 보내야 하는 요청 파라미터를 어떤 인증·검증 방식으로 요구할지, 그리고 백엔드가 돌려준 결과를 호출자에게 어떤 상태 코드와 헤더·본문 형식으로 내보낼지를 정하는 두 가지 설정.

먼저 알아야 할 것 01-02

#1문제 상황

리소스와 메서드만 있으면 API 는 뼈대만 있는 상태다(→ 01-02). 누가 보낸 값이 틀렸는지, 인증 없이 들어왔을 때를 어디서 막는지 정할 자리가 없다.

메서드 요청과 메서드 응답은 그 자리를 채운다. method request 는 요구 조건을 정하고, method response 는 되돌릴 모양을 정해 준다.

#2핵심 질문

각 메서드가 무엇을 요구하고 무엇을 돌려줄지 어떻게 고정해 놓을까?

#3동작 예시

주문 조회 메서드에 Authorization 헤더를 필수로 표시해 둔다. 토큰 없이 호출한 요청은 백엔드로 가지 않고 권한 오류로 끝난다.

조회가 끝나면 메서드 응답 설정대로 상태 코드 200과 주문 목록을 JSON 형태로 내보낸다.

#4동작 과정

  1. 메서드를 만든다리소스 아래에 GET 같은 HTTP 메서드를 붙인다. Methods는 이 요청 단위를 정하는 자리다.
  2. 요구 조건을 정한다method request 에 authorization 방식을 고르고 request parameters 로 어떤 값이 필수인지 표시한다. authorizer 를 붙이면 인증은 그 Lambda 나 Cognito 가 맡는다(→ 03-01).
  3. 돌려줄 모양을 정한다method response 에 상태 코드와 헤더·본문 형식을 지정한다. 규격은 API 문서 게시에 그대로 쓰인다(→ 07-03).
  4. 확인해 볼 것해당 메서드 화면에서 Authorization 값과 필수 파라미터 표시가 켜져 있는지 본다.

  2. 주체 범위를 좁힌다계정 ID, IP 대역, CIDR 블록, VPC 또는 VPC endpoint 중에서 쓸 조건을 고른다.
  3. 판정 순서를 따른다authorization workflow 는 resource policy 와 IAM 신분 기반 정책을 함께 보고 통과 여부를 정한다. private API 는 VPC endpoint 정책도 함께 쓴다.
  4. 확인해 볼 것API 정책 화면에 연결된 resource policy 문서와 허용된 주체가 보이는지 확인한다.

→ 02-04 참조

#1문제 상황

API 는 기본으로 누구나 부를 수 있다. 내부 주문 API 라면 사내 계정만 들어오게 해야 한다.

IAM 권한을 쓰면 호출자의 신원인 IAM principal 과 이 API 가 요구하는 작업이 일치할 때만 통과시킨다. control access for invoking an API 는 바로 이 통제다.

#2핵심 질문

#3동작 예시

사내 배포 서버의 IAM 역할에 이 API 를 부르는 권한을 넣는다. 서버는 AWS 자격 증명으로 요청에 서명해 보낸다.

권한이 없는 사용자 계정으로 같은 호출을 하면 권한 오류를 받는다.

#4동작 과정

  1. 메서드에 인증을 켠다해당 메서드의 authorization 을 IAM 으로 지정한다.
  2. 정책 문장을 적는다identity-based policy 에 execute-api:Invoke 와 API ARN 을 적어 호출 대상을 지정한다. 호출자는 SigV4 또는 SigV4a 로 요청에 서명한다.
  3. 다른 정책과 함께 본다authorization workflow 안에서 resource policy(→ 02-04)까지 함께 판정된다. private API 는 VPC endpoint 정책도 함께 쓴다.
  4. 확인해 볼 것권한 있는 자격 증명으로 호출했을 때 요청이 통과하고, 없는 자격 증명으로는 막히는지 본다.

Lambda authorizer 붙이는 방법

API 호출을 받을 때 AWS Lambda 함수를 먼저 실행해 신짜 신분인지 판별하고, 통과한 요청만 뒤쪽 API로 보내는 후처리(인증) 방식이다.

먼저 알아야 할 것 02-03

#1문제 상황

API 키나 IAM 인장만으로는 서버가 만든 여러 종류의 토큰을 전부 해석하기 어렵다. 회사 로그인이든 내부 티켓이든 직접 확인하는 코드가 필요하다.

Lambda authorizer 는 요청마다 이 코드를 대신 실행해 준다. Bearer 토큰나 요청 파라미터를 보고 통과 여부를 정한다.

#2핵심 질문

자기 방식의 인증을 API 앞단에 어떻게 붙일까?

#3동작 예시

클라이언트가 사내 로그인 토큰을 Authorization 헤더에 실어 주문 API 를 부른다. API Gateway 는 이 요청을 Lambda authorizer 에 먼저 넘긴다.

Lambda 가 토큰을 확인해 정책 문서를 돌려주면 원래 요청이 진행되고, 토큰이 오래됐으면 401 이 돌아간다.

#4동작 과정

  1. authorizer 를 만든다REST API 콘솔이나 CLI 로 Lambda authorizer 를 등록하고 실행할 Lambda 함수를 지정한다. 캐시 시간(authorizer caching)을 정하면 같은 결과가 일정 시간 재사용된다.
  2. 방식을 정한다REQUEST authorizer 는 요청 파라미터까지 보고 판별하고, TOKEN 방식은 지정한 헤더의 토큰만 본다.
  3. 판정 흐름을 따른다클라이언트가 메서드를 호출하면 API Gateway 가 authorizer 등록 여부를 확인해 Lambda 를 부르고, simple workflow 는 받은 정책만으로, full workflow 는 호출 대상 메서드까지 확인해 통과시킨다.
  4. 확인해 볼 것API의 authorizer 목록에 등록된 Lambda authorizer 이름과 연결된 메서드가 보이는지 확인한다.

이 규격을 지켜야 인증 결과가 API Gateway 에 실제로 반영된다.

#2핵심 질문

#3동작 예시

  2. 판단을 한다함수 안에서 토큰을 확인하고 통과 여부를 정한다.
  3. 응답을 돌려준다통과면 principalId 와 context, iam 같은 필드에 담은 policy document 를, 실패면 오류를 담은 JSON 을 돌려준다. 이것이 output from a Lambda authorizer 다.
  4. 확인해 볼 것Lambda 함수의 로그에서 이벤트와 응답 JSON 의 필드 이름이 규격과 맞게 찍히는지 본다.

#2핵심 질문

Cognito 가 발급한 토큰 검증을 Lambda 없이 API Gateway 에서 맡길 수 있을까?

#3동작 예시

사용자가 앱에서 Cognito 로 로그인해 access token 을 받는다. 앱은 그 토큰을 Authorization 헤더에 넣어 프로필 API 를 부른다.

API Gateway 가 서명과 만료를 확인해 유효하면 응답을 돌려주고, 로그인하지 않은 요청은 401 을 돌려준다.

#4동작 과정

  1. authorizer 를 만든다콘솔의 Authorizers 화면에서 Create authorizer 를 고르고 타입을 Cognito 로, 사용할 user pool 을 지정한다. 정식 이름은 COGNITO_USER_POOLS authorizer 다.
  2. 토큰 방식을 정한다OAuth 스코프 등 Cognito 가 정해 둔 범위(scope) 안에서만 토큰이 발급되도록 연결한다. 이 토큰은 JWT, 서명 정보를 담은 토큰이다.
  3. 반영시킨다authorizer 를 만든 뒤에는 API 를 다시 배포해야 변경이 실제 호출에 반영된다.
  4. 확인해 볼 것authorizer 목록에 타입이 Cognito 로 잡히고 사용할 user pool 이 선택되어 있는지 확인한다.

Verified Permissions 로 속성 기반 인가

사용자·리소스에 붙은 속성값을 정책으로 비교해 접근 허용 여부를 판단하는 AWS Verified Permissions 를 Lambda authorizer 안에서 호출해 인가를 수행하는 방법이다.

먼저 알아야 할 것 03-01

#1문제 상황

인증 통과와 인가는 다르다. 인증은 신원이 맞다는 확인이고, 인가는 그 신원이 이 리소스를 만질 자격이 있는지의 판단이다. Lambda authorizer(→ 03-01) 안에서 권한 조건을 손으로 짜면 리소스가 늘어날 때마다 조건도 같이 늘어난다.

Verified Permissions는 속성 기반 인가를 맡는다. control access based on an identity's attributes, 즉 신원의 속성값과 policies, 즉 허용 규칙을 비교해 authorization, 즉 허용 여부를 내린다. Cedar 정책 언어로 권한을 쓰고, 정책 저장소 스키마와 policies로 세밀하게 정한다.

#2핵심 질문

신원은 이미 확인했는데 이 요청을 통과시킬 자격이 있는지 어떻게 판단하는가?

#3동작 예시

직원 주말에 주문 문서를 읽는 요청이 들어온다. Verified Permissions가 Cognito user pool 신원의 부서 속성과 문서 소유자 속성을 정책과 맞춰 본다.

부서가 다르다는 조건에 걸려 인가 결과가 거부로 나온다.

#4동작 과정

  1. 정책을 둔다정책 저장소에 스키마를 만들고 Cedar 정책으로 허용 규칙을 적는다. Verified Permissions는 이 저장소를 API와 연결해 관리한다.
  2. authorizer를 만든다Verified Permissions가 이 정책을 판단하는 Lambda authorizer를 만들어 붙인다. 신원은 앞선 인증(→ 03-01)에서 이미 확인된 상태여야 하고, Cognito user pool이나 OpenID Connect(OIDC) 를 신원 공급원으로 쓴다.
  3. 결과를 적용한다authorizer가 내린 허용 또는 거부로 요청을 통과시키거나 거절한다. 이 방식은 Regional과 edge-optimized REST API에서만 동작한다.
  4. 확인해 볼 것해당 REST API의 메서드에 authorizer가 붙어 있고, 속성 값이 다른 요청이 실제로 거부되는지 콘솔에서 테스트 호출해 본다.

HTTP API 의 JWT authorizer

HTTP API 에서 JSON Web Token(JWT, 클레임을 서명해 넣은 토큰)의 서명과 만료 등을 직접 검사해 인가하는, Lambda 를 쓰지 않는 내장 인증 방식이다.

먼저 알아야 할 것 03-03

#1문제 상황

JWT authorizers를 쓰기 전에는 HTTP API마다 Lambda authorizer(→ 03-01)를 붙여 토큰을 검사했다. 인증 방식이 하나 늘어날 때마다 함수와 운영 부담이 함께 늘어난다.

HTTP API access control을 위한 JWT authorizers는 토큰 검사를 API가 직접 맡는다. identity source로 받은 토큰을 확인하고 claim, 즉 토큰 안의 항목을 보고 허용 여부를 가린다.

#2핵심 질문

Lambda 없이 토큰의 서명과 범위를 확인해 요청을 걸러낼 수 있는가?

#3동작 예시

브라우저에서 주문 목록을 호출하면 헤더에 identity source로 지정한 위치에서 JWT가 실려 온다. API가 서명과 만료를 확인하고 라우트에 설정한 범위 하나라도 토큰에 있으면 통과시킨다.

범위가 없으면 거부되고 401이 돌아간다.

#4동작 과정

  1. 발급자를 지정한다identity source와 발급자·audience를 정해 토큰을 받아낼 자리와 출처를 지정한다. 서명까지 확인해 조작된 토큰을 걸러 낸다.
  2. 범위를 정한다라우트마다 scopes를 지정한다. 범위를 준 라우트는 토큰이 그중 하나 이상을 포함해야 통과한다.
  3. 재사용한다라우트마다 서로 다른 authorizer를 쓰거나 하나의 authorizer를 여러 라우트에 공유한다.
  4. 확인해 볼 것토큰을 넣은 요청과 범위를 뺀 요청을 각각 호출해 허용과 거부가 갈리는지 본다.

#2핵심 질문

지속 연결을 열기 직전에 이 사용자를 걸러낼까?

#3동작 예시

  2. authorizer를 건다Lambda authorizer, 즉 Lambda 함수로 접근을 통제하는 방식을 $connect 라우트에 붙인다. 모든 WebSocket API에 붙이는 것이 권장된다.
  3. 연결을 열거나 거절한다authorizer가 통과시킨 요청에만 연결이 맺어진다. 이후 메시지는 이미 확립된 연결 위에서 오간다.
  4. 확인해 볼 것$connect 라우트에 authorizer가 붙어 있는지 보고, 토큰 없는 접속이 거부되는지 확인한다.

#4동작 과정

  2. 응답을 정한다응답을 직접 만들어 볼 때는 MOCK integration을 쓴다. API Gateway가 통합 끝점 역할로 메서드 요청에 응답한다.

  4. 확인해 볼 것메서드의 통합 설정에서 type 값을 확인해 어느 유형으로 붙어 있는지 본다.

#1문제 상황

먼저 알아야 할 것 04-02

→ 04-02 참조

#1문제 상황

Lambda proxy 통합(→ 04-02)이 함수 쪽에서 형식을 정하는 방식이면, 함수는 여러 다른 방법으로 호출받는 걸 감당해야 한다. 또한 응답이 필요 없는 작업을 API로 받았을 때 결과를 기다리면 시간만 쓴다.

Lambda custom integrations는 API Gateway가 함수를 직접 부르고, method mapping으로 무엇을 넘길지 정한다. asynchronous invocation을 쓰면 응답 없이 두는 것도 가능하다.

함수를 부르는 쪽과 기다리는 쪽을 나누어 각각 정할 수 있는가?

#3동작 예시

POST 메서드를 Lambda custom 통합으로 두고 요청의 이름과 도시를 함수에 넘긴다. 함수는 인사말을 만들어 응답하면 API Gateway가 그 값을 클라이언트에 돌려준다.

응답이 필요 없는 작업은 asynchronous invocation으로 보내 함수가 끝나기만 기다린다.

#4동작 과정

  1. method mapping을 정한다integration request에서 어떤 요청 값을 함수에 어떤 이름으로 넘길지 정한다. 함수 입력 형식에 맞춰 이름과 자리를 맞춘다.
  2. 응답을 돌려준다함수가 만든 응답을 integration response가 받아 메서드 응답으로 내보낸다. 여기서 상태 코드와 본문 형태를 고쳐 쓸 수 있다.
  3. 기다리지 않는다asynchronous invocation으로 보내면 함수가 끝난 뒤 결과를 담는 곳만 남고 HTTP 응답은 바로 돌아간다. Lambda errors는 이 방식에서 오류 처리 방식이 달라진다.
  4. 확인해 볼 것메서드의 integration request에서 넘기는 파라미터 이름이 함수 입력과 맞는지 본다.

HTTP 통합과 응답 스트리밍

API Gateway가 백엔드 서버로 직접 HTTP 요청을 보내는 방식이며, 응답 본문을 일부씩 먼저 보내는 스트리밍 설정으로 긴 응답을 기다리지 않고 내보낼 수 있다.

먼저 알아야 할 것 04-01

→ 04-01 참조

#1문제 상황

백엔드가 다른 팀이 운영하는 HTTP 서버인 경우가 많다. 함수를 사이에 넣지 않고 곧바로 호출하고 싶지만, 응답 본문이 크면 전체가 모일 때까지 클라이언트가 기다려야 한다.

HTTP integration은 API Gateway가 백엔드 서버로 직접 HTTP 요청을 보낸다. 여기에 stream the integration response, 즉 payload response streaming을 켜면 본문을 쪼개 보내고, response transfer mode로 스트리밍 여부를 정한다.

#2핵심 질문

외부 HTTP 서버로 곧바로 호출하면서 긴 응답을 기다리지 않게 할 수 있는가?

#3동작 예시

비디오 목록을 담은 GET 메서드를 HTTP proxy 통합으로 두고 백엔드 서버 주소를 넣는다. 요청이 그대로 서버로 전달되고 응답이 돌아온다.

스트리밍을 켜면 본문이 완성되기 전부터 조각으로 나뉘어 클라이언트에 도착한다.

#4동작 과정

  1. 연결을 정한다HTTP 통합은 포트 80, 443, 1024~65535를 지원한다. proxy 유형은 메서드와 엔드포인트 주소만 정하면 되고, custom 유형은 요청과 응답 매핑까지 적어야 한다.
  2. 요청을 보낸다메서드 요청은 매핑된 형태로 백엔드 서버에 직접 전달되고, 서버 응답이 통합 응답으로 들어온다.
  3. 본문을 나눠 보낸다response transfer mode를 스트리밍으로 두면 payload response streaming이 동작해 본문을 일부씩 먼저 내보낸다. 클라이언트는 전체를 기다리지 않고 읽기 시작한다.
  4. 확인해 볼 것메서드의 통합 설정에서 통합 유형과 transfer mode가 어떻게 되어 있는지 본다.

#2핵심 질문

  2. 동작을 고른다통합에서 Amazon S3 proxy 나 Amazon Kinesis proxy 같은 동작을 고른다. 통합 유형을 고르는 기준은 04-01 에 있다.
  3. 요청을 건넨다메서드 호출이 선택한 action 과 URI 에 맞춰 AWS 서비스가 요청을 처리한다. 응답은 매핑 템플릿으로 원하는 모양에 맞춰 돌려준다(→ 05-03).

먼저 알아야 할 것 04-01

→ 04-01 참조

#1문제 상황

HTTP 통합은 인터넷을 지나야 하므로 사설망 안의 백엔드에는 닿지 못한다(→ 04-01). private 통합과 VPC link 는 API Gateway 를 VPC 안으로 붙여 사설 자원에 요청을 전달하게 한다. 인터넷에서 보이는 엔드포인트는 그대로 두고 내부 자원만 연다.

#2핵심 질문

사설망 안의 백엔드에 API Gateway 요청을 어떻게 닿게 하나?

#3동작 예시

사설 subnet 에 있는 내부 주문 서비스가 있다. VPC link 로 그 자리에 연결한 뒤 API 를 호출하면 주문 목록이 돌아온다. 주문 서비스는 인터넷에 노출되지 않는다.

#4동작 과정

  1. VPC link 를 만든다VPC 안의 로드 밸런서와 API 를 묶는 연결을 먼저 만든다. REST API 에서는 VPC links V2 를 쓰며, Network Load Balancer 없이 Application Load Balancer 로도 연결할 수 있다.
  2. 통합을 붙인다private integration 으로 리소스·서브넷을 골라 요청을 내부로 보낸다. ACL 을 대면 로드 밸런서를 거치지 않고 지정한 프라이빗 IP 로 직접 간다.
  3. 범위를 정한다이 방식은 대상 자원이 모두 같은 AWS 계정에 있어야 한다. 계정을 넘겨 쓰려면 대상 쪽에도 권한을 준비해야 한다.
  4. 확인해 볼 것콘솔에서 VPC link 목록에 만든 링크가 활성 상태로 보이는지 확인한다.

#2핵심 질문

틀린 요청을 백엔드에 보내지 않고 앞에서 어떻게 거르나?

#3동작 예시

#4동작 과정

  1. 모델을 만든다data models for REST APIs 항목에서 본문 구조를 정의한다. 이 모델이 schema 역할을 해 필수 값과 자료형을 정한다.
  2. 검증기를 붙인다model 과 필수 파라미터 검사를 묶은 request validator 를 메서드 요청 설정에 연결한다. 실행은 메서드 응답 절차와 함께 정한다.
  3. 거부한다어긋난 요청은 그 자리에서 400 오류로 끝나고 백엔드에 전달되지 않는다. 뒤 stages 에선 애플리케이션 고유 검증만 하면 된다.
  4. 확인해 볼 것필수 파라미터를 뺀 요청을 보내 400 응답이 나는지 확인한다.

먼저 알아야 할 것 05-02

#1문제 상황

요청과 응답을 그대로 통과시키면 백엔드 규격이 그대로 노출된다(→ 05-02). mapping template transformations 는 미리 써 둔 문서에 값을 끼워 넣어 모양을 바꾼다. 통째로 넘기지 않으므로 그만큼 형태를 원하는 대로 만들 수 있다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 템플릿을 고른다통합 요청과 응답, VTL 이라는 Velocity Template Language 로 본문을 다시 쓰는 두 방식을 쓴다. 이 변환이 body mapping 이다.

5단계 5. 요청과 응답을 바꾼다

이미지나 동영상 같은 이진 데이터를 텍스트로 깨뜨리지 않고 통째로 통과시키는 Content-Type 처리와, 클라이언트가 받는 응답 본문을 자동으로 압축해서 전송량과 지연을 줄이는 기능이다.

먼저 알아야 할 것 05-03

#1문제 상황

API Gateway는 요청과 응답 본문을 기본적으로 UTF-8로 인코딩된 JSON 문자열인 텍스트 페이로드로 다룬다(→ 05-03). 그래서 JPEG 이미지나 GZip 파일 같은 이진 페이로드는 형태가 깨지거나 아예 전달되지 않는다.

binary media types는 이진 데이터로 취급할 Content-Type 목록이라, 이 값을 지정한 타입은 본문을 바꾸지 않고 통째로 넘긴다. 여기에 payload compression을 켜면 응답 크기를 줄여 전송량과 지연도 낮출 수 있다.

#2핵심 질문

텍스트가 아닌 데이터를 깨지 않고 넘기면서 응답 크기는 어떻게 줄일까?

#3동작 예시

업로드 API가 이미지를 받으려면 image/png를 binary media types에 넣어 둔다. 클라이언트가 PNG 파일을 POST하면 함수는 파일을 base64로 인코딩해 돌려주고, API Gateway는 그 값을 다시 원본 바이트로 풀어 응답한다.

같은 API에서 클라이언트가 gzip 압축을 요청하면 payload compression이 본문을 압축해 내보낸다.

#4동작 과정

  1. 이진 타입을 지정한다binary media types에 image/png 같은 Content-Type을 나열한다. 이 목록에 든 타입은 content type conversions를 거쳐 본문이 텍스트가 아닌 데이터로 전달된다. AWS Lambda proxy 통합에서는 함수가 응답을 base64로 인코딩해야 하고, 프록시 통합에 응답 스트리밍을 쓰면 이 설정이 필요 없다.
  2. 압축을 켠다메서드 응답에서 ContentHandling을 지정해 클라이언트가 받을 응답 본문을 payload compression으로 줄인다. 이때 클라이언트가 보내는 Accept 헤더 값에 따라 압축 여부가 달라진다.
  3. 확인해 볼 것API 콘솔의 이진 미디어 타입 목록에 image/png가 들어 있는지, 해당 메서드 응답의 ContentHandling 값이 어떻게 설정되어 있는지 확인한다.

먼저 알아야 할 것 06-02

#1문제 상황

새 버전을 바로 100%로 올리면 버그가 모든 사용자에게 그대로 드러난다. 그렇다고 시험 환경에서만 확인하면 실제 트래픽 조건을 볼 수 없다.

canary release deployment는 전체 요청을 무작위로 나눠 일정 비율만 새 버전으로 보낸다. 트래픽을 작게 무작위로 두면 버그가 있어도 대부분 사용자는 한 번도 건드리지 않는다.

#2핵심 질문

지표를 확인한 뒤 promote a canary로 비율을 키우고, 문제가 없으면 100%로 올려 완전히 전환한다.

#4동작 과정

  1. 비율을 정한다deploymentCanarySettings에 canary percentage를 넣는다. 전체 API 트래픽이 무작위로 나뉘어 카나리가 이 비율만큼 받고 나머지는 기존 버전이 받는다.

  4. 확인해 볼 것배포 목록에서 카나리 배포의 상태와 설정된 트래픽 비율이 어떻게 표시되는지 확인한다.

#2핵심 질문

#4동작 과정

  2. 인증서를 붙인다AWS Certificate Manager에서 받은 인증서를 이 도메인 이름에 연결해 HTTPS로 동작하게 한다. 프라이빗 API에 쓰는 도메인은 별도 방식으로 다룬다.
  3. DNS로 연결한다내 도메인의 DNS 기록을 가리켜 API가 이 도메인 이름으로 들어오게 만든다.
  4. 확인해 볼 것콘솔의 Custom domain names 목록에 등록된 도메인 이름과 API 매핑이 붙은 base path가 보이는지 확인한다.

#1문제 상황

routing rules는 조건을 보고 동작을 정하는 규칙이고, API mappings은 base path mapping으로 그 연결을 등록하는 구조다.

#2핵심 질문

도메인 하나에 들어온 요청을 조건에 따라 어느 API로 보낼지 어떻게 정할까?

#3동작 예시

routing mode를 ROUTING_RULE_THEN_API_MAPPING으로 두면 모든 라우팅 규칙을 먼저 평가하고 나서 API 매핑을 본다.

#4동작 과정

  1. 조건을 정한다규칙마다 header 조건 두 개와 path 조건 한 개까지 지정할 수 있다. 조건이 모두 맞으면 그 규칙의 동작을 수행하고, 조건 없이 만들면 항상 수행되는 catch-all 규칙이 된다.
  2. 동작을 정한다규칙의 action으로 요청을 특정 API의 stage로 보낸다. 규칙은 우선순위 순서로 평가된다.
  3. 매핑을 등록한다API mappings으로 base path를 어떤 API에 붙이는지 등록한다. routing mode가 ROUTING_RULE_THEN_API_MAPPING이면 모든 라우팅 규칙을 먼저 평가한 뒤 매핑을 평가한다.
  4. 확인해 볼 것사용자 지정 도메인 화면에서 라우팅 규칙의 조건과 우선순위, 그리고 등록된 base path 매핑이 보이는지 확인한다.

#1문제 상황

사용자 지정 도메인 인증서나 라우팅 규칙을 쓰지 않으면 API는 기본 엔드포인트 주소로만 열린다(→ 06-04). 이 주소에는 페일오버가 없고, 여러 경로로 열린 통로를 한곳에 모으는 방법도 없다.

DNS failover는 IP를 다른 리전으로 돌리는 방어 수단이고, disable the default endpoint는 기본 주소로 직접 오는 요청을 막는다.

#2핵심 질문

리전 장애 때 API 주소를 그대로 두고도 전환하고, 접근 통로도 하나로 모으려면 어떻게 할까?

#3동작 예시

Route 53 alias 기록에서 Evaluate Target Health를 켜고 health check를 붙인다. 기본 리전의 API Gateway를 쓸 수 없을 때 DNS가 보조 리전 API를 가리키는 IP로 바뀌어, 클라이언트는 같은 주소로 계속 호출된다.

기본 엔드포인트는 끄도록 설정해 모든 호출이 사용자 지정 도메인으로만 들어오게 한다.

#4동작 과정

  1. health check를 붙인다Amazon Route 53의 health check로 기본 리전과 보조 리전의 상태를 본다. alias 기록에서 Evaluate Target Health를 선택하면 이 API가 unavailable일 때만 전환된다. 자체 health check를 두면 그보다 먼저 끊기는 경우도 잡아낸다.
  2. 끄킨다disable the default endpoint로 기본 엔드포인트에 직접 들어오는 호출을 차단해 모든 접근을 사용자 지정 도메인 하나로 모은다.
  3. 확인해 볼 것도메인 설정에서 기본 엔드포인트 상태가 비활성화로 표시되고 Route 53 alias 기록에 health check가 연결돼 있는지 확인한다.

#1문제 상황

API keys는 API Gateway가 미리 발급한 비밀 문자열이다. 호출자가 이 값을 헤더나 쿼리 문자열로 보내면 API Gateway가 그것으로 호출자를 구분해 통과시킨다. 만든 값은 나중에 바꿀 수 없고, 사용량 계획(→ 07-02)에 붙여 할당량까지 통제한다.

#2핵심 질문

API를 부르는 상대가 누구인지 어떻게 구분할까?

#3동작 예시

모바일 앱이 주문 조회 API를 부를 때 헤더에 자기 앱용 API 키를 넣는다. API Gateway는 메서드에 API 키 요구가 켜져 있는지 보고 키가 없으면 즉시 거절하고, 있으면 통과시켜 백엔드 결과를 돌려준다.

키는 요청 헤더로도, 쿼리 문자열 값으로도 보낼 수 있고 어디서 읽을지는 API key source로 정한다.

#4동작 과정

  1. 키를 만든다리전의 API를 고르고 API keys 화면에서 값을 생성하거나 여러 개를 CSV로 가져온다. 이 값은 발급 후 변경할 수 없다.
  2. 메서드에 요구한다키가 필요한 메서드에 API key 요구를 켠다. 켜진 메서드에는 키가 붙지 않으면 요청이 전 단계로 돌아간다. 키는 API key source로 HEADER인지 쿼리 문자열인지 정한다.
  3. 호출로 시험한다키를 넣고 call a method using an API key 절차로 메서드를 직접 호출해 통과 여부를 본다. 키는 usage plan(→ 07-02)에 연결해 호출량 제한을 함께 건다.
  4. 확인해 볼 것API keys 목록에 만든 키가 보이고, 키 없는 요청이 403으로 떨어지는지 콘솔에서 확인한다.

#1문제 상황

usage plans는 하나의 사용량 계획을 만들어 여러 API와 메서드에 적용하고, 그 안에서 요청 속도와 총 사용량을 throttle로 제한한다. 계획은 API keys로 호출자를 알아보고, quota와 burst limit이 상한을 정한다.

#2핵심 질문

키를 가진 호출자가 한꺼번에 과하게 부르지 못하게 어떻게 제한할까?

#3동작 예시

#4동작 과정

  1. 계획을 만든다usage plans에서 하나의 사용량 계획을 만들고 묶을 API와 메서드를 고른다. plan은 API 단계와 메서드 단위로 나눠 지정할 수 있다.
  2. 한도를 정한다throttle 항목에서 목표 요청 속도를 정하고 quota로 총량과 기간을 정한다. burst limit은 순간적으로 허용되는 초과 폭이다.
  3. 키를 붙인다계획에 API keys를 연결한다. 키는 usage plans에서 직접 만들거나 CSV로 가져오고, 같은 키를 Lambda authorizer(→ 03-01)·IAM·Cognito와 나란히 쓸 수도 있다.
  4. 확인해 볼 것해당 키로 만든 사용량 계획 상세 화면에 연결된 API와 단계가 보이는지 확인한다.

API documentation은 각 리소스·메서드에 도움말을 붙이는 기능이다. representation of API documentation으로 본문을 저장하고, publish documentation으로 문서 버전을 스테이지에 묶어 배포 대상에 나눠 보인다.

#2핵심 질문

외부 개발자가 API 사용법을 어디서 읽게 할까?

#3동작 예시

결제 API의 문서 페이지에 POST /charges 메서드를 올린다. 필요한 헤더·본문 필드·응답 스키마·오류 메시지를 적어 두고 공개 URL로 배포한다. 개발자는 그 페이지를 보고 요청을 만든다.

#4동작 과정

  1. 내용을 적는다API Gateway REST API·AWS SDK·CLI·콘솔 중 하나로 documentation parts를 만든다. OpenAPI 파일의 문서 부분을 그대로 가져오거나 내보낼 수도 있다.
  2. 버전을 묶는다API Gateway가 원본 내용을 보관하므로 다른 시점의 문서도 버전으로 남는다. 문서 버전을 특정 스테이지에 연결하고 그 스테이지용 스냅숏을 내보낸다.
  3. 공개한다publish documentation으로 배포하면 외부에서 볼 수 있는 문서가 생긴다. 개발자 포털을 붙여 함께 제공할 수 있고 documentation access로 접근 경로를 관리한다.
  4. 확인해 볼 것콘솔의 Documentation 화면에 각 메서드의 설명과 response shape가 보이는지 확인한다.

#2핵심 질문

#4동작 과정

  3. 받아 쓴다만들어진 SDK는 메서드와 파라미터를 담은 client SDK 파일과 예제 코드로 구성된다. 예제 코드에서 실제 호출 흐름을 그대로 따라가면 된다.

캐시 설정

같은 요청에 대한 백엔드 응답을 API Gateway 가 잠시 저장해 두었다가 반복 요청에 그대로 돌려주어, 백엔드에 도달하는 횟수와 지연 시간을 줄이는 기능.

먼저 알아야 할 것 06-02

#1문제 상황

같은 주소로 반복되는 요청마다 백엔드로 나간다. 백엔드 부하가 커지고 응답 시간도 그대로 따라 오른다.

cache settings를 켜면 API Gateway가 백엔드 응답을 TTL 동안 저장한다. 같은 요청이 오면 백엔드로 가지 않고 저장된 값을 돌려준다.

#2핵심 질문

반복되는 요청의 부하를 어디에서 줄일까?

#3동작 예시

상품 목록 조회를 API Gateway로 반복 호출한다. 첫 요청은 백엔드까지 갔다가 캐시에 저장되고, 그 뒤 요청은 저장된 응답을 즉시 돌려준다. 캐시 대상은 cache key parameters로 정한 요청 값이 같은 경우다.

#4동작 과정

  1. 켜다스테이지 단위로 API caching을 켠다. 캐시가 켜진 동안 백엔드 응답이 지정된 시간 동안 저장된다.
  2. 지정한다TTL을 초 단위로 정한다. TTL이 0이면 캐시를 끈 상태이며, API Gateway는 응답을 저장하지 않고 매번 백엔드로 나간다.
  3. 맞춘다캐시 key parameters로 응답을 나눌 기준이 되는 쿼리·헤더 값을 고르고, 큰 본문은 enable payload compression으로 압축해 저장 공간과 전송량을 줄인다. 캐시는 최대한 best-effort로 동작한다.
  4. 확인해 볼 것캐시에서 응답한 요청 수와 백엔드로 나간 요청 수를 CloudWatch 지표로 나란히 볼 수 있는지 확인한다.

8. HTTP API — 더 가벼운 축08-01

HTTP API 라우트

HTTP API 는 메서드와 경로 조합(예: GET /orders)을 하나의 라우트로 등록하고, 그 요청이 오면 지정한 백엔드로 보내는 규칙으로, REST API 보다 설정 항목이 훨씬 적다.

먼저 알아야 할 것 01-03

#1문제 상황

REST API로 사소한 경로 하나를 받으려 해도 리소스와 메서드, 통합 설정을 모두 만들어야 한다(→ 01-02·01-03). 설정이 무거워 소규모 서비스에는 과하다.

Routes는 메서드와 경로를 묶은 주소표다. HTTP APIs에서 이 한 줄이 요청 처리 규칙 전체를 정해 REST API보다 설정 항목이 훨씬 적다.

#2핵심 질문

들어온 요청이 어느 백엔드로 갈지 어디서 정할까?

#3동작 예시

GET /pets 라우트를 만들어 pet 목록 Lambda 함수에 연결한다. 클라이언트가 그 경로를 부르면 해당 함수로 전달되고 응답이 그대로 돌아온다. 어느 route에도 걸리지 않으면 $default 라우트가 대신 받는다.

#4동작 과정

  1. 주소를 적는다하나의 route key로 메서드와 경로를 적는다. ANY 메서드는 그 경로에 따로 정의하지 않은 모든 메서드를 받는다.
  2. 변수를 쓴다GET /pets/{petID}처럼 경로 변수를 쓰면 그 자리의 값이 백엔드로 전달된다. 하위 경로를 전부 받는 {proxy+} 형태도 쓰며 경로 끝에만 둘 수 있다.
  3. 남는 것을 받는다어느 route와도 맞지 않는 요청은 $default 라우트가 처리한다. 경로와 쿼리 값은 백엔드로 넘기기 전에 URL 디코딩된다.
  4. 확인해 볼 것콘솔의 Routes 목록에 메서드와 경로가 나란히 보이는지 확인한다.

HTTP API 통합

통합(integration)은 라우트로 들어온 요청을 어떤 백엔드(Lambda 함수, AWS 서비스, 프라이빗 API 등)에 전달하고 응답을 되돌리는 설정이다.

먼저 알아야 할 것 08-01

#1문제 상황

라우트만으로는 요청을 처리할 곳이 정해지지 않는다. 라우트마다 어디로 넘길지 따로 묶어 줘야 한다.

HTTP API integrations는 라우트에 처리 대상을 붙인다. AWS Lambda integrations, HTTP integrations, AWS service integrations, private integrations 네 가지를 쓸 수 있고, 모두 proxy 형태로 요청과 응답을 그대로 통과시킨다.

#2핵심 질문

라우트로 들어온 요청을 실제 처리 대상에 어떻게 연결할까?

#3동작 예시

POST /signup 라우트를 만든 뒤 AWS Lambda proxy 통합으로 가입 처리 함수를 붙인다. signup 요청이 오면 함수로 그대로 넘어가고 함수가 돌려준 응답이 호출자에게 그대로 돌아간다.

#4동작 과정

  1. 대상을 고른다Lambda proxy, AWS service, HTTP proxy 중 하나를 고른다. 내부망에 있는 프라이빗 API에는 private integrations를 쓴다(→ 04-06).
  2. 연결한다통합을 만들 때 대상을 고르고 어느 경로를 넘길지 지정한다. Lambda proxy 통합은 Lambda 권한에 API를 등록하는 절차를 함께 밟는다.
  3. 보낸다요청과 응답은 변환 없이 대상에 전달되고 되돌아온다. 호출자는 Lambda 함수가 정한 상태 코드와 본문을 그대로 받는다.
  4. 확인해 볼 것라우트 상세에 붙은 통합의 종류가 Lambda proxy·HTTP·AWS service로 보이는지 확인한다.

8. HTTP API — 더 가벼운 축08-03

HTTP API 파라미터 매핑과 CORS

파라미터 매핑은 경로·쿼리·헤더·본문 값을 백엔드가 받을 형태로 이름과 형식을 바꿔 보내는 기능이고, CORS 설정은 브라우저가 다른 도메인의 API를 호출할 때 필요한 접근 허용 규칙이다.

먼저 알아야 할 것 08-02

#1문제 상황

프론트엔드가 보낸 요청을 Lambda 나 사내 서버가 바로 받으면 이름과 형태가 맞지 않아 코드를 다시 짜야 한다. 브라우저에서 다른 도메인의 API를 부르면 브라우저가 요청 자체를 막는다(→ 08-01).

HTTP API 파라미터 매핑은 요청을 백엔드에 닿기 전에 고치는 기능이다. CORS 는 브라우저가 허용해 줄 도메인과 헤더를 정해 준다. 그래서 백엔드는 자기 형식만 보면 되고 브라우저도 요청을 보낸다.

#2핵심 질문

브라우저가 보낸 요청을 백엔드가 원하는 형태로 바꿔 보내고 같은 도메인에서 호출도 허용하려면 어떻게 하는가?

#3동작 예시

브라우저가 주문 목록을 GET으로 부르며 헤더에 Authorization 을 보낸다. 파라미터 매핑이 그 헤더를 그대로 통과시키고 CORS 설정이 allow-origin 을 지정해 둔다.

브라우저 네트워크 창에 200 응답이 뜨고, CORS 오류가 없어진다.

#4동작 과정

  1. 요청 파라미터를 정한다parameter mapping 은 바꾸려는 위치와 새 값을 이름-값 쌍으로 적는 설정이다. 헤더·쿼리 문자열은 append·overwrite·remove, 경로는 overwrite 로 고친다.
  2. 응답을 먼저 고친다백엔드 응답이 그대로 클라이언트로 나가기 전에 같은 방식으로 본문을 바꿀 수 있다. OpenAPI 로 만든 정의를 배포할 때 함께 반영한다.
  3. 허용 규칙을 적는다CORS 설정으로 브라우저가 열어 볼 도메인·헤더·메서드를 지정한다. payload format 을 서로 다르게 맞추어도 브라우저가 읽을 형태로 본문이 나가게 된다.
  4. 확인해 볼 것브라우저 개발자 도구 콘솔에 CORS 오류가 남지 않고, 해당 도메인 요청에 Access-Control-Allow-Origin 헤더가 붙는지 본다.

HTTP API 스테이지와 사용자 지정 도메인

HTTP API 의 $default 스테이지는 기본 API를 담는 그릇이며, 사용자 지정 도메인 이름을 붙여 api.example.com 같은 자체 주소로 API를 공개할 수 있다.

먼저 알아야 할 것 08-03

#1문제 상황

배포하면 API Gateway가 만든 기본 주소로만 호출된다. 이 주소는 기억하기 어렵고 호출 쪽 코드에 그대로 박혀 있다.

HTTP API 스테이지와 사용자 지정 도메인 이름을 쓰면 이 주소를 own 도메인으로 바꿀 수 있다. Stages 는 코드를 올리는 단위이고, custom domain names 과 API mappings 은 그 주소를 내 것으로 등록하는 설정이다.

#2핵심 질문

기본 엔드포인트 주소 대신 내 도메인 주소로 HTTP API를 부르게 만들려면 어떻게 하는가?

#3동작 예시

주소로 https://api.example.com/myservice 를 쓴다. HTTPS 인증서를 붙인 뒤 그 주소로 GET을 보내면 해당 API가 응답한다.

기존 코드의 기본 엔드포인트가 그대로 동작하는지 콘솔에서 함께 본다.

#4동작 과정

  1. 스테이지를 정한다$default stage 는 별도 이름 없이 기본 API를 담는 그릇이다. 배포한 API는 이 스테이지 아래에 놓이고 기본 주소의 마지막 경로 자리가 된다.
  2. 도메인을 붙인다custom domain names 에 내 도메인과 기본 경로를 등록한다. 도메인 소유권을 확인하고 HTTPS 인증서를 연결한다.
  3. 연결을 매핑한다API mappings 으로 한 도메인 아래 여러 API를 경로별로 나눠 연결한다. 한 API 안에서 여러 경로를 쓰려면 경로별로 따로 등록한다.
  4. 확인해 볼 것콘솔의 사용자 지정 도메인 화면에 등록한 도메인 이름과 API 매핑 목록이 올라와 있는지 본다.

8. HTTP API — 더 가벼운 축08-05

HTTP API 보호와 관측

보호는 요청 속도 제한(throttling)·상호 TLS 같은 요청 방어 기능으로 트래픽을 막는 것이고, 관측은 CloudWatch 지표와 로그로 요청량·지연·오류를 숫자로 남기는 것이다.

먼저 알아야 할 것 08-04

#1문제 상황

외부에 공개된 API 는 누구나 부를 수 있고 한 사용자가 요청을 몰아 보내면 다른 사용자가 기다린다. 문제가 생겨도 숫자 없이 알기 어렵다(→ 08-01).

HTTP API 보호와 관측은 이 두 가지를 함께 다룬다. throttling 은 초당 허용량을 넘긴 요청을 늦추거나 막고, mutual TLS 는 양쪽 인증서로 상대 신분을 확인한다. metrics 와 logging 은 남은 요청을 숫자로 기록한다.

#2핵심 질문

공개된 API의 과도한 요청을 막고 실제로 얼마나 쓰였는지 숫자로 확인하려면 어떻게 하는가?

#3동작 예시

한 클라이언트가 짧은 시간에 수천 번 호출한다. throttling 설정에 닿은 요청은 대기시키거나 429로 거절된다.

같은 시간대 Count 지표가 CloudWatch 대시보드에 올라가고 4xx·5xx 카운터가 오류를 보여 준다.

#4동작 과정

  1. 속도를 제한한다throttling 은 라우트·스테이지 단위로 요청 속도와 요청 크기의 상한을 정한다. 넘은 요청은 지연되거나 거부되어 뒤의 요청을 지킨다.
  2. 상대 신분을 확인한다mutual TLS 를 켜면 클라이언트도 인증서를 제시해야 한다. 서로의 신분을 확인한 연결만 받아들이며 사설 인증서를 쓸 수 있다.
  3. 숫자로 남긴다metrics 로 Count·4xx·5xx·데이터 처리량·지연을 CloudWatch 로 보낸다. logging 을 켜면 요청·응답 기록을 남기고, 상세 지표로 라우트 단위 수치를 따로 볼 수 있다.
  4. 확인해 볼 것CloudWatch 대시보드에 API 별 Count 그래프가 시간대별로 올라오고 라우트별로 나뉘어 보이는지 본다.

WebSocket API 개요와 route key

WebSocket API는 클라이언트와 서버 사이에 연결을 한 번 열어 두고 양방향으로 메시지를 주고받는 지속 연결(두 컴퓨터가 계속 대화하는 통로)을 제공하며, API Gateway가 처음 연결할 때 받는 URL 경로 조각인 route key로 어떤 메시지를 어느 백엔드로 보낼지 구분한다.

먼저 알아야 할 것 01-04

#1문제 상황

REST API 는 요청이 올 때마다 답을 돌려주므로 채팅 알림처럼 서버가 먼저 말을 거는 일은 못 한다. 폴링으로 물어보면 필요 없는 통신이 계속 쌓인다(→ 01-04).

WebSocket API 는 클라이언트와 백엔드 사이에 계속 열린 통로를 만든다. Overview of WebSocket APIs 가 그 구조를 정의한다. 연결 순간 받은 경로 조각이 route key 다.

#2핵심 질문

클라이언트와 서버가 연결을 유지한 채 양방향으로 메시지를 주고받으려면 어떻게 하는가?

#3동작 예시

채팅 클라이언트가 wss://주소/{stage} 로 접속한다. 서버는 $connect 라우트를 실행해 접속을 기록하고 클라이언트에게 아이디를 돌려준다.

이후 접속자가 그대로 남아 있는 상태에서 서버가 먼저 알림 메시지를 보낸다.

#4동작 과정

  1. 연결을 받는다$connect 는 연결이 열릴 때 실행되는 라우트다. $disconnect 는 그 연결이 끊길 때 실행된다. 한 번 열린 통로는 요청-응답이 끝나도 유지된다.
  2. 경로를 읽는다처음 연결할 때 받은 경로 조각이 route key 다. routeSelectionExpression 이 메시지 안에서 route key 를 찾아낼 위치를 지정하고, 그 값에 맞는 라우트로 보낸다.
  3. 남아 있는 대상을 센다connected users 는 지금 연결되어 있는 클라이언트 목록이다. 서버는 이 목록을 보고 누구에게 보낼지 고른다. JSON 이 아닌 메시지는 $default 라우트로 간다.
  4. 확인해 볼 것API Gateway 콘솔에서 $connect·$disconnect 를 포함한 라우트 목록에 route key 가 어떻게 잡혔는지 본다.

라우트는 메시지를 받을 주소표이며, 통합(integration)은 그 라우트에 도착한 메시지를 Lambda 함수나 HTTP 백엔드 같은 실제 처리 대상에 연결해 주는 설정이다.

먼저 알아야 할 것 09-01

→ 09-01 참조

#1문제 상황

연결만 열어 두면 메시지마다 같은 백엔드가 뜬다(→ 09-01). 어느 처리를 맡길지 정해 둘 곳이 없다.

WebSocket 라우트와 통합은 그 분리 담당이다. Invoke your backend integration 으로 라우트마다 대상을 정하고, Integration request 로 보낼 형태를, Integration responses 로 돌아온 결과를 다룬다. two-way communication 은 연결된 클라이언트 쪽으로 되쏘는 통로다.

#2핵심 질문

받은 메시지를 라우트마다 다른 백엔드로 보내고 되돌아온 결과는 어떻게 처리하는가?

#3동작 예시

클라이언트가 {"action":"join","room":"lobby"} 를 보낸다. action 값에 맞는 라우트가 통합 대상 Lambda 함수를 실행한다.

함수가 처리한 뒤 Integration responses 가 호출자에게 acknowledgement 를 돌려보내고, 뒤이어 서버가 다른 접속자에게 알림을 보낸다.

#4동작 과정

  1. 경로를 정한다$default route 는 어떤 route key 매칭도 되지 않을 때 모든 메시지를 받는 기본 라우트다. Custom routes 는 지정한 값일 때만 그 라우트로 보낸다.
  2. 통합을 건다각 라우트에 Lambda 함수나 HTTP 백엔드 같은 실제 처리 대상을 묶는다. Invoke your backend integration 이 이 연결을 가리킨다.
  3. 형식을 정한다Integration request 로 보낼 본문·헤더를 만들고, Integration responses 로 돌아온 본문을 어느 상태 코드와 형식으로 내보낼지 정한다.
  4. 확인해 볼 것콘솔의 라우트 화면에서 각 라우트에 붙은 통합 대상과 Integration responses 항목이 어떻게 잡혔는지 본다.

선택 표현식(selection expression)은 메시지 본문에서 route key 값을 찾아낼 위치를 JSONPath 같은 규칙으로 지정하는 설정으로, 어디를 읽어 라우트를 결정할지 알려 준다.

먼저 알아야 할 것 09-02

→ 09-01 참조

#1문제 상황

메시지마다 어느 라우트로 갈지 정하려면 본문 안의 값을 읽어야 한다(→ 09-02). 읽을 자리와 읽은 값을 알려 주는 규칙이 없다.

선택 표현식이 그 자리다. WebSocket selection expressions 라고 부른다. route response selection expression 도 같은 방식으로 어느 라우트에 답을 보낼지 정한다.

#2핵심 질문

메시지 본문에서 어느 값을 읽어 라우트를 고르고 답은 어느 라우트로 보낼지 어떻게 정하는가?

#3동작 예시

본문이 {"action":"send","text":"hi"} 일 때 $request.body.action 이 route key 값이 되어 send 라우트로 간다.

값이 하나도 맞지 않으면 예약된 $default 로 넘어간다.

#4동작 과정

  1. 읽을 자리를 정한다WebSocket selection expressions 는 $request.body.action 처럼 $로 시작하는 변수를 쓴다. 중괄호로 경계를 묶어 '${request.body.version}-beta' 처럼 쓸 수 있고, 여러 변수도 나열한다.
  2. 한 번만 평가한다변수는 한 번만 계산되며 다시 재귀적으로 계산되지 않는다. $ 는 '\'로 이스케이프해 예약된 $default 를 그대로 쓸 수 있고, 패턴이 필요하면 '/2\d\d/' 처럼 슬래시로 감싸 2XX 같은 형태를 받는다.
  3. 답의 방향을 정한다route response selection expression 은 어떤 라우트로 되쏘아 보낼지 정한다. 이 둘로 message routing 이 완성된다.
  4. 확인해 볼 것콘솔의 라우트 선택 표현식 칸에 적힌 경로가 메시지 본문의 실제 필드명과 맞는지 본다.

#1문제 상황

프런트엔드가 보낸 메시지에는 프린트에 필요한 값이 섞여 있고, 백엔드가 돌려주는 응답은 자기 형식이라 그대로 클라이언트에 내보낼 수 없다. 라우트와 통합은 이미 정해졌으니(→ 09-02) 중간에 값을 고쳐 붙일 자리가 필요하다.

WebSocket 데이터 변환은 그 자리를 맡는다. data mapping 으로 라우트 요청을 백엔드 통합에 넘기고, binary media types 로 텍스트가 아닌 데이터를 해석해 전달한다.

#2핵심 질문

메시지를 백엔드 규격과 클라이언트 규격에 맞게 어떻게 바꿔 보내는가?

#3동작 예시

채팅 클라이언트가 주문 상태 JSON 을 보낸다. 연동해 둔 Lambda 함수는 주문 번호만 필요해 값을 추려 받고, 응답도 클라이언트 형식으로 잘라 돌려준다.

#4동작 과정

  1. 선택한다메시지 본문에서 매핑 템플릿을 고를 위치를 지정한다. binary media types 로 지정한 콘텐츠 타입의 메시지는 텍스트 대신 원본 그대로 통과시킨다.
  2. 변환한다mapping template 로 요청을 통합 요청에, 통합 응답을 메서드 응답에 대응시킨다. 템플릿은 Velocity Template Language 로 쓰고 JSONPath 표현식으로 값을 꺼내 쓴다.
  3. 확인해 볼 것WebSocket 연결을 열고, 라우트에 도착한 메시지가 어떤 형태로 백엔드에 들어갔는지 로그에서 확인한다.

#5한 줄 요약

WebSocket 데이터 변환은 메시지를 매핑 템플릿으로 필요한 값만 골라 바꾸고 이진 데이터는 통째로 넘기는 기능입니다.

상호 TLS와 백엔드 클라이언트 인증서

상호 TLS(mTLS)는 클라이언트와 API Gateway가 서로의 신분을 확인하기 위해 양쪽 모두 인증서를 제시하는 방식으로, API Gateway에서는 이 인증서를 활성화해 백엔드 호출도 인증된 클라이언트로 보이게 하여 암호화된 통신과 함께 상대방이 누구인지도 보장한다.

먼저 알아야 할 것 02-02

#1문제 상황

API 키나 서명(→ 07-01)만으로는 상대 클라이언트가 실제로 어떤 기기인지 알 수 없다. 사내 기기나 IoT 장비만 들어오게 하고 싶으면 연결 자체에서 신분을 확인해야 한다.

REST API 의 상호 TLS 는 클라이언트에게 X.509 인증서를 요구한다. certificate authority 에서 발급받은 인증서를 함께 쓰며, 이 인증서를 backend client certificates 로 Lambda authorizer 와 백엔드에 넘긴다.

#2핵심 질문

어떤 클라이언트만 API 에 들어오게 인증서로 어떻게 걸러내는가?

#3동작 예시

IoT 장비가 사용자 지정 도메인 주소(→ 06-04)의 API 로 요청을 보낸다. 장비가 심은 인증서를 함께 보내고, API Gateway 가 요구한 뒤에야 메서드가 실행된다.

#4동작 과정

  1. 요구한다API 또는 사용자 지정 도메인 수준에서 클라이언트 인증서를 필수로 요구한다. 요구되면 X.509 인증서를 제시하지 않은 요청은 통과하지 못한다.
  2. 넘긴다받아들인 인증서를 Lambda authorizer 와 백엔드 통합에 전달한다. 다른 인증 방식과 함께 쓸 수도 있다.
  3. 확인해 볼 것인증서를 첨부한 요청과 첨부하지 않은 요청을 각각 보내고, 둘째가 거부되는 것을 확인한다.

#5한 줄 요약

상호 TLS는 클라이언트와 서버가 인증서로 서로를 확인하게 하는 양방향 인증입니다.

AWS WAF 붙이기

AWS WAF(Web Application Firewall)는 웹 애플리케이션을 지나는 요청을 미리 검사해 악성 패턴에 해당하는 요청만 차단하거나 카운트하는 방화벽 규칙 집합으로, API Gateway REST API에 붙여 API 앞단에서 공격을 걸러낼 수 있다.

먼저 알아야 할 것 02-04

→ 10-01 참조

#1문제 상황

REST API 앞단에는 API Gateway 만 있다. 관용적인 웹 공격 요청이 그대로 백엔드까지 닿으면 API 가 느려지거나 응답이 막힌다. 라우팅과 권한은 정해져도(→ 02-04) 요청 자체를 걸러낼 자리가 없다.

AWS WAF 를 쓰면 web ACL 이 그 자리를 막는다. managed rule groups 로 정해진 패턴에 걸리는 요청을 차단하거나 카운트한다.

#2핵심 질문

공격 패턴에 해당하는 요청을 API 앞단에서 어떻게 걸러내는가?

#3동작 예시

스테이지에 붙인 web ACL 화면에서 SQL injection 규칙을 본다. 공격 문자열이 붙은 요청 수 카운트가 올라가고 있고, 차단으로 바꿨더니 같은 요청이 403 응답을 받는다.

#4동작 과정

  1. 만든다AWS WAF 에 web access control list 를 만들고 규칙과 조건을 넣는다. managed rule groups 를 함께 둘 수 있다.
  2. 붙인다web ACL 을 REST API 의 스테이지에 연결한다. 콘솔에서 고르거나 AWS CLI 로 지정한다.
  3. 확인해 볼 것WAF 대시보드에서 해당 규칙에 맞는 요청이 차단되었는지 확인한다.

#5한 줄 요약

스로틀링

스로틀링은 초당 허용하는 요청 수나 요청 크기 같은 사용량 한도를 설정해 그을 넘지 않는 요청은 거부하고 나머지는 필요한 대기로 지연시키는 방식으로, 하나의 API 계정이 소모할 수 있는 리소스의 양을 통제해 다른 사용자를 지키고 API의 과부하를 막는다.

먼저 알아야 할 것 07-02

#1문제 상황

한 호출자가 요청을 몰아 보내면 같은 계정의 다른 API 와 사용자까지 느려진다. 사용량 계획으로 클라이언트별 한도를 둘 수도 있지만(→ 07-02) API 자체에도 상한이 필요하다.

throttling 은 rate limit 와 burst limit 을 걸고, 계정 수준에서는 리전별로 계정의 모든 API 에 대해 검사한다. 이 한도는 목표치로.best-effort 로 동작한다.

#2핵심 질문

API 로 몰려드는 요청을 초당 허용량으로 어떻게 제한하는가?

#3동작 예시

_rate limit 를 초당 100건으로 둔 API 에 순간적으로 300건이 들어온다. 허용된 100건만 통과하고 나머지는 429 응답을 받는다.

#4동작 과정

  1. 정한다계정 수준과 API·스테이지·메서드 수준에서 rate limit 와 burst limit 을 지정한다.
  2. 자른다token bucket 알고리즘으로 요청 하나당 토큰 하나를 소모하게 해 한도를 넘은 요청은 거부한다. account level throttling 은 리전의 계정 안 모든 API 에 함께 적용된다.
  3. 확인해 볼 것한도를 넘긴 호출이 429 로 거절되는지 콘솔에서 확인한다.

#5한 줄 요약

스로틀링은 토큰 버킷 방식으로 초당 허용량을 정해 과한 요청을 제한하는 기능입니다.

10. API 를 지킨다10-04

private REST API

private API는 AWS 네트워크 안에서만 도달할 수 있도록 API Gateway의 엔드포인트에 사설 주소만 남기고 인터넷에서는 접근하지 못하게 만든 API로, 이 상태에서는 리소스 정책으로 접근 권한을 따로 지정해야 한다.

먼저 알아야 할 것 02-01

#1문제 상황

일반 엔드포인트는 전 세계에서 주소를 알면 호출할 수 있다(→ 02-01). 사내망에서만 쓸 API 라면 그 주소가 밖에 노출되지 않아야 하고, 대신 VPC 안에서만 들어오는 통로를 만들어야 한다.

Private REST API 가 그렇게 만든다. 트래픽은 공개 인터넷을 거치지 않고 AWS 네트워크 안에만 머문다. API providers 와 API consumers 를 나눈 뒤 VPC endpoint policy 로 어느 쪽이 붙을지 정한다.

#2핵심 질문

사설 API 를 VPC 안에서만 호출되게 어떻게 노출하는가?

#3동작 예시

사내 애플리케이션이 VPC 안에서 private endpoint 주소의 API 를 부른다. 같은 VPC 의 다른 서비스에서 external endpoint 주소로 부르면 연결되지 않는다.

#4동작 과정

  1. 만든다엔드포인트 타입을 PRIVATE 로 둔 REST API 를 배포한다. 사용자 지정 도메인에는 사설 인증서가 필요하고, VPC endpoint policy 로 접근을 지정한다.
  2. 연결한다VPC 에 interface VPC endpoint 를 만들고 private API 에 연다. AWS PrivateLink 사설 IP 로만 닿는다.
  3. 확인해 볼 것VPC 안에서는 private endpoint 주소로 부르고, 밖에서는 닿지 않는지 확인한다.

#5한 줄 요약

Private REST API는 사설 주소만 남겨 AWS 네트워크 안에서만 호출되게 만든 API입니다.

데이터 보호와 암호화

API Gateway의 데이터 보호는 주고받는 데이터의 암호화(전송 중 암호화로 통신 내용을 가리고, API 키·서명·인증으로 접근 권한을 확인하며, 자격 증명이 담긴 민감 정보는 로그에서 가리는 것)를 통해 API를 오가는 데이터를 안전하게 지키는 것.

먼저 알아야 할 것 10-01

#1문제 상황

API 앞뒤로 오가는 요청과 응답은 인증서를 타고 가지만, 그 내용은 중간에서 읽힐 여지가 있다. 저장된 데이터도 같은 문제다. 전송 구간마다 따로 손대야 하는 설정이 많다.

data protection 은 이 구간들을 나눠 다룬다. data encryption 에서 통신 중 암호화와 at rest 암호화를 각각 보고, 캐시를 켠 REST API 는 cache encryption 도 쓸 수 있다. private API 의 사용자 지정 도메인에서 만든 인증서와 개인 키는 AWS 관리 KMS 키로 암호화된다.

#2핵심 질문

API 를 오가는 데이터를 구간마다 어떻게 암호화해 지키는가?

#3동작 예시

캐시를 켠 REST API 로 같은 요청 두 번을 보낸다. 두 번째는 저장된 응답이 암호화 상태로 저장돼 그대로 돌아온다.

#4동작 과정

  1. 구간을 나눈다internetwork traffic privacy 로 네트워크를 오가는 구간을, at rest 로 저장되는 구간을 따로 본다.
  2. 암호화한다캐시를 사용하면 cache encryption 을 켜고, private API 의 사용자 지정 도메인 인증서 개인 키는 AWS 관리 키로 암호화해 AWS KMS 에서 확인할 수 있다.
  3. 확인해 볼 것캐시 설정을 열면 암호화 항목이 켜졌는지 확인한다.

#5한 줄 요약

IAM과 서비스 연결 역할

API Gateway는 IAM의 역할과 정책을 통해 누가 어떤 API를 호출할 수 있는지를 정하고, 다른 AWS 서비스를 대신 호출할 때 필요한 권한은 서비스 연결 역할(Service-linked role)이라는 전용 역할로 위임받아 관리한다.

먼저 알아야 할 것 02-05

#1문제 상황

API 를 만들 수 있는 사람, 호출할 수 있는 사람, API Gateway 가 다른 AWS 서비스를 대신 부를 때의 권한이 서로 다른 주체다. 이 셋을 각각의 권한 문서로 정의해야 한다.

이 정리는 IAM 이 맡는다. 서비스 사용자는 관리자에게 권한을 요청하고, 관리자는 접근을 정해 요청을 올리며, IAM 관리자는 정책을 직접 쓴다(→ 02-05).

#2핵심 질문

누가 어떤 API 를 만들고 호출할 수 있는지를 어떻게 정의하는가?

#3동작 예시

관리자가 identity-based policy 에서 특정 메서드에 대한 호출 권한만 허용한다. 그 밖의 메서드를 호출하려 한 사용자는 거절된다.

#4동작 과정

  1. 정한다how API Gateway works with IAM 에 따라 identity-based policy 로 사용자·역할의 권한을, resource-based policy 로 API 자체 권한을 선언한다.
  2. 위임한다API Gateway 가 다른 AWS 서비스를 대신 호출할 권한이 필요하면 service-linked role 로 위임받아 관리한다.
  3. 확인해 볼 것IAM 콘솔에서 해당 API 에 붙은 리소스 정책과 service-linked role 이 있는지 확인한다.

#5한 줄 요약

11. 지켜보고 정의로 쓴다11-01

CloudWatch 지표

API Gateway 가 요청 처리 중에 센 호출 건수·지연 시간·오류 수 같은 수치를 CloudWatch 에 지표(metric)로 보내 대시보드 그래프로 보여주는 것.

먼저 알아야 할 것 06-02

#1문제 상황

API 는 올라가 있지만 지금이 정상인지 비정상인지 알 길이 없다. 호출자가 겪는 실제 체감을 알아야 다음 고처 할 곳을 정한다.

CloudWatch 지표는 API Gateway 가 요청을 처리하면서 센 숫자를 CloudWatch 로 내보내는 기능이다. 이 지표는 지표(metric), 즉 이름과 단위와 값으로 된 시간별 수치로, 기본적으로 1분 단위로 쌓인다. 이제 호출 건수와 지연 시간을 그래프로 보고 이상이 생긴 자리를 짚는다.

#2핵심 질문

내 API 가 지금 어떤 상태인지 숫자로 어떻게 확인하는가?

#3동작 예시

운영자가 CloudWatch 콘솔에서 내 API 의 그래프를 연다. 어느 순간 호출 건수인 Count 가 평소보다 크게 뛰고, 같은 구간에 5xx 오류도 함께 오른다.

그래프 위 구간을 확대해 보면 지연 시간(Latency)이 같이 늘어난 걸 확인하고, 원인을 좁히러 백엔드 쪽을 본다.

#4동작 과정

  1. 수치로 남긴다요청 처리 중에 센 값을 지표로 만들어 CloudWatch 로 보낸다. 이때 API 이름·스테이지·-method 같은 구분값을 dimensions and metrics, 즉 지표를 잘게 쪼개는 기준으로 붙여 같은 이름의 다른 값과 섞이지 않게 한다.
  2. 항목별로 본다CloudWatch 지표에는 호출 건수를 세는 Count 와 API 호출 전체의 응답 시간을 잰 Latency, 백엔드가 얼마나 늦게 답했는지를 잰 IntegrationLatency 가 있다. 캐시로 얻은 적중률을 보려면 CacheHitCount 와 CacheMissCount 를 함께 본다.
  3. 그래프로 확인한다여러 지표를 한 화면에 놓아 보는 API dashboard 로 추이를 한 번에 훑는다.
  4. 확인해 볼 것CloudWatch 콘솔에서 해당 API 의 지표를 1분 단위로 열어 값이 쌓이는지 확인한다.

#4동작 과정

  2. 호출을 남긴다access logging 은 누가 API 를 어떻게 불었는지 기록한다. 직접 만든 로그 그룹에 정한 log format 으로 쓰고, 넣을 항목을 $context 변수로 고른다.
  3. 권한을 준다CloudWatch Logs 로 보내려면 API Gateway 가 로그를 읽고 쓸 권한을 가져야 하므로, 제공되는 AmazonAPIGatewayPushToCloudWatchLogs 관리 정책을 붙인다.
  4. 확인해 볼 것CloudWatch Logs 의 해당 로그 그룹에 최근 호출이 시간순으로 들어 있는지 확인한다.

AWS X-Ray 는 요청 하나가 지나가는 전체 길을 한 줄로 이어 붙여 보여 주는 추적 기능이다.

#2핵심 질문

느린 요청의 지연이 어느 구간에서 생기는가?

#3동작 예시

느린 호출 하나를 X-Ray 콘솔에서 열어 본다. 서비스맵(service maps) 그래프에서 API Gateway 다음에 있는 Lambda 구간의 막대가 길게 늘어져 있다.

#4동작 과정

  1. 추적을 잇는다X-Ray tracing 을 켜면 API Gateway 가 요청의 trace 식별자를 뒤따르는 서비스로 넘겨 연결을 이어 준다. 이미 추적 중인 서비스에서 이 API 를 불러도 식별자는 그대로 전달된다.
  2. 지연을 나눠 본다traces(추적) 하나에는 각 구간의 걸린 시간이 들어 있고, service maps 로는 요청 전체와 그 아래 서비스들의 지연을 한눈에 본다.
  3. 골라서 기록한다sampling rules 로 어떤 요청을 어떤 비율로 기록할지 정한다. 모든 요청을 남기면 비용과 저장량이 커진다.
  4. 확인해 볼 것해당 API 스테이지의 X-Ray 콘솔에서 트레이스 목록이 쌓이는지 확인한다.

OpenAPI 확장은 API 의 모양과 동작을 문서 하나에 적어 통째로 읽어들이게 하는 방법이다.

#2핵심 질문

API 의 구조와 인증·통합 설정을 코드로 한 번에 정의할 수 있는가?

#3동작 예시

#4동작 과정

  2. 통합을 적는다x-amazon-apigateway-integration 에 어디로 넘길지 지정한다. 인증이나 CORS 같은 설정도 각자 대응하는 확장 항목으로 함께 적는다.
  3. 읽어들인다이 정의 파일을 읽어 API 를 만든다. 같은 문서가 저장소에서 버전 관리되므로 바뀐 점을 되짚을 수 있다.
  4. 확인해 볼 것정의 파일을 넣은 뒤 콘솔의 리소스 목록에 메서드가 만들어져 있는지 확인한다.

API Gateway portals

여러 API 를 하나의 AWS 계정에 묶어 만드는 제품(portal) 단위 개념으로, 외부에 공개되는 API 와 내부 전용 API 를 나눠 관리하고 배포를 함께 올리는 방식.

#1문제 상황

여러 팀이 만든 API 가 여러 AWS 계정에 흩어져 있다. 어느 문서가 어떤 API 의 것인지 알기 어렵고, 쓸 수 있는 API 목록도 한곳에 없다.

API Gateway portals 는 여러 API 를 한 단위로 묶어 문서와 함께 관리하는 구조다.

#2핵심 질문

여러 AWS 계정에 흩어진 API 와 그 문서를 어디에 모아 함께 볼 수 있는가?

#3동작 예시

담당자가 포털을 열어 제품 목록을 훑는다. try it 으로 문서에 적힌 요청을 그대로 실행해 응답을 확인하고, 다른 계정의 사용자에게 제품 단위로 문서를 공유한다.

#4동작 과정

  1. 묶음을 만든다portal 은 portal product(제품) 여러 개를 담는다. 하나의 API 계정 안에서 만든 API 묶음이 바로 이 제품이다.
  2. 문서를 붙인다제품 페이지에는 사용자에게 보여 줄 설명을 두고, 그 아래 API 경로와 메서드와 스테이지별 페이지가 붙는다. 이 두 층이 합쳐져야 사용자에게 쓸 만한 문서가 된다.
  3. 공유한다제품 단위로 다른 AWS 계정에 나눠 공유할 수 있어 계정을 넘나드는 쓰임을 이어 간다.
  4. 확인해 볼 것포털을 열어 제품 목록과 각 제품 아래에 API 문서가 붙어 있는지 확인한다.
