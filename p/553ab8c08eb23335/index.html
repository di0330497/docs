WAF의 위치와 동작 원리01-01

웹 애플리케이션 방화벽의 역할

애플리케이션 계층(HTTP/HTTPS) 요청을 규칙 기반으로 검사해 악성 트래픽을 차단하거나 허용하는 AWS 관리형 웹 방화벽 서비스.

#1문제 상황

기존의 네트워크 방화벽(보안 그룹, NACL 등)은 IP 주소와 포트 번호 단위로 트래픽을 허용하거나 차단한다. 그런데 웹 요청은 거의 모두 80번(HTTP)과 443번(HTTPS) 포트로 들어오기 때문에, 이런 방화벽은 "웹 요청"이라는 트래픽 자체를 막지 못한다. 그리고 요청의 내용, 즉 URL 경로나 헤더, 본문이 악성인지 아닌지는 전혀 살피지 않는다. 그래서 SQL 삽입이나 XSS 같은 공격은 정상 요청처럼 보이는 채로 방화벽을 통과해 애플리케이션까지 도달한다. 이게 기존 방식의 명확한 한계다. 포트와 프로토콜 수준만 보고 애플리케이션(HTTP) 수준의 공격을 구분하지 못한다.

#2핵심 질문

웹 애플리케이션으로 들어오는 HTTP 요청을 내용까지 살펴서 악성 요청만 골라내 차단할 방법은 없을까?

#3동작 예시

AWS WAF는 각 웹 요청의 내용, 즉 URL 경로·쿼리 문자열·헤더·본문을 규칙(룰)과 대조해, 조건에 맞는 요청만 차단하고 나머지는 통과시킨다. 가장 직관적인 예는 로그인 URL의 파라미터에 SQL 명령 패턴이 들어 있는 요청이다. WAF는 그 요청을 규칙과 대조했을 때 SQL 삽입 패턴에 해당하면 해당 요청 하나만 차단하고, 같은 URL을 보낸 정상 사용자의 요청은 그대로 통과시킨다.

#4동작 과정

  1. 요청 도착사용자의 HTTP 요청이 WAF가 연결된 보호 대상(CloudFront, ALB 등)으로 들어온다. 이 시점에 WAF가 트래픽 경로에 끼어 있다.
  2. 규칙 평가WAF가 요청의 내용을 web ACL(웹 액세스 제어 목록, 규칙들의 묶음)에 등록된 규칙들과 차례대로 대조해 차단·허용·카운트 중 무엇에 해당하는지 판정한다.
  3. 결과 적용차단 판정이면 요청을 버리고 차단 응답을 돌려주며, 허용 판정이면 요청을 원래 대상 리소스로 전달해 정상 서비스를 받게 한다.

동작 원리: web ACL이 요청을 처리하는 흐름

web ACL(보호 팩)에 규칙과 규칙 그룹을 우선순위 순서대로 적용해 각 요청을 허용·차단·계수·챌린지 등으로 처리하는 흐름.

#1문제 상황

방화벽에 규칙이 여러 개 생기면 "어떤 순서로, 어떤 기준으로 적용할지"가 반드시 정해져야 실제 동작한다. 규칙마다 차단 조건과 허용 조건이 뒤섞여 있으면, 어느 규칙이 먼저 평가되는지와 차단·허용 중 무엇이 우선인지가 애매해져 요청마다 결과가 들쭉날쭉해진다. 또 요청 하나를 보고 규칙 전체를 매번 다시 판단하면 판단 기준 자체가 불안정해진다. 즉 검사할 규칙을 담는 "정해진 틀"이 없으면 규칙이 아무리 많아도 일관된 차단이 불가능하다.

#2핵심 질문

여러 규칙을 하나의 묶음으로 관리하면서 모든 요청에 같은 순서로 일관되게 적용하려면 어떻게 해야 할까?

#3동작 예시

web ACL(웹 액세스 제어 목록)은 규칙들을 우선순위 순서대로 나열한 하나의 검사 목록이다. 들어온 요청은 이 목록을 처음부터 순서대로 거치며, 규칙 하나에서 차단되지 않으면 다음 규칙으로 넘어가고, 마지막까지 차단되지 않은 요청만 통과한다. 예를 들어 첫 번째 규칙이 봇(자동 프로그램)의 요청을 차단하고, 두 번째 규칙이 과도한 요청(rate limit, 짧은 시간 안의 요청 수 제한)을 차단한다면, 두 조건을 모두 통과한 사람의 요청만 서버에 도착한다.

#4동작 과정

  1. 규칙 평가 순서web ACL 안에 규칙을 우선순위 순서대로 배치해 두고, 들어온 요청은 1번 규칙부터 차례로 평가된다. 차단 조건에 걸리면 즉시 평가가 끝난다.
  2. 기본 동작 적용모든 규칙을 통과한 요청에 무엇을 할지 web ACL의 기본 동작(기본 액션: 허용 또는 차단)이 한 번에 정한다.
  3. 대응 실행차단된 요청은 차단 응답(예: 403, 접근 거부)을 받고 종료되고, 허용된 요청만 보호 대상 리소스로 전달되어 정상 서비스를 받는다.

보호 대상 리소스와 CloudFront 연동

CloudFront 배포, ALB, API Gateway 등 AWS 리소스에 web ACL을 연결해 해당 리소스로 들어오는 요청을 보호하는 방식.

#1문제 상황

WAF는 독자적으로 트래픽을 받는 서버가 아니라, 다른 AWS 서비스의 트래픽 경로에 붙어서 요청을 검사하는 부가 서비스다. 어떤 서비스에 붙느냐에 따라 요청이 실제로 지나가는 경로가 달라지고, 그래서 보호할 대상을 정해 연결하지 않으면 WAF가 검사할 요청 자체가 생기지 않는다. 즉 WAF를 설치만 해서는 아무것도 보호되지 않고, "어느 리소스로 들어오는 요청을 검사할지"를 명시적으로 연결해 주는 설정이 반드시 선행되어야 한다.

#2핵심 질문

WAF가 요청을 검사하려면 트래픽이 흐르는 경로의 어느 지점에 연결해야 할까?

#3동작 예시

WAF를 CloudFront(전 세계 엣지 위치에서 콘텐츠를 사용자에게 전달하는 CDN 서비스)와 연결하면, 사용자가 CloudFront 주소로 보낸 모든 요청이 WAF를 먼저 거친 뒤에야 원본 서버로 전달된다. 예를 들어 사용자가 https://cdn.example.com 으로 요청을 보내면 요청은 CloudFront → WAF 검사 → 원본 서버 순서로 흐르고, WAF에서 차단된 요청은 원본 서버에 도달하지 못한다.

#4동작 과정

  1. 연결 설정보호할 리소스(CloudFront 배포, ALB, API Gateway 등)를 선택해 web ACL과 연결한다.
  2. 검사 지점 형성연결이 완료되는 순간부터 해당 리소스로 향하는 모든 요청이 web ACL을 통과하는 경로가 만들어진다.
  3. 요청 처리요청이 web ACL 규칙을 통과하면 리소스로 전달되고, 차단되면 응답을 받고 끝난다.

보호 팩 개념과 생성

보호 팩(web ACL)은 규칙·규칙 그룹·기본 액션을 한 단위로 묶어 특정 AWS 리소스의 트래픽을 검사하고 대응하는 컨테이너이며, 새 콘솔과 표준 콘솔에서 생성한다.

#1문제 상황

보호 규칙을 처음부터 직접 만들려면 조건 작성 방법을 배워야 하고, 잘못 지정하면 정상 사용자의 요청까지 차단하는 오탐이 생길 위험이 있다. 또 SQL 삽입이나 XSS처럼 널리 알려진 공격 패턴은 매번 새로 작성하기보다 검증된 묶음으로 바로 적용하는 편이 훨씬 빠르다. 규칙을 처음부터 일일이 쓰는 방식은 시간이 오래 걸리고 누락이 생기기 쉬워서, 방어에 구멍이 나거나 과한 차단이 발생하는 문제가 있다.

#2핵심 질문

검증된 공격 대응 규칙들을 한 번에 묶어 빠르게 그리고 안전하게 적용하려면 어떻게 해야 할까?

#3동작 예시

AWS WAF의 관리형 규칙 그룹(managed rule group, AWS가 유지 관리하는 규칙 묶음)은 잘 알려진 위협 패턴을 미리 담고 있어 web ACL에 몇 번의 클릭만으로 붙일 수 있다. 예를 들어 "AWSManagedRulesCommonRuleSet" 하나를 추가하면 SQL 삽입, XSS 등 주요 공격 대응 규칙이 한 번에 적용된다.

#4동작 과정

  1. 규칙 그룹 선택콘솔의 규칙 추가 화면에서 관리형 규칙 그룹(예: Common Rule Set)을 고른다.
  2. 동작 설정그 그룹에 대해 차단 또는 카운트(기록만 남기고 차단은 하지 않음) 중 무엇을 할지 지정한다.
  3. web ACL에 추가그룹을 web ACL에 넣고 저장하면 이후 모든 요청이 이 그룹의 규칙들로 평가된다.

#1문제 상황

한번 만든 web ACL과 규칙은 고정된 것이 아니라 운영 중에도 계속 바뀐다. 특정 규칙이 정상 사용자의 요청을 과도하게 차단하면 그 규칙만 동작을 바꿔야 하고, 더 이상 필요 없는 규칙이나 web ACL 자체는 지워야 한다. 이 수정·삭제 과정이 매끄럽지 않으면 오탐(정상 요청 차단)이 계속되거나, 쓰지 않는 규칙이 쌓여 검사 기준이 어지러워진다. 특히 연결된 리소스가 있는 채로 무작정 지우려 하면 실패하므로, 어떤 순서로 정리해야 하는지 정해져 있어야 한다.

#2핵심 질문

이미 적용 중인 규칙 묶음과 web ACL을 상황에 맞게 수정하거나 제거하려면 어떤 순서로 해야 할까?

#3동작 예시

콘솔의 web ACL 상세 화면에서 개별 규칙의 동작을 바꾸거나 규칙을 삭제할 수 있고, 더 이상 쓰지 않는 web ACL은 리소스 연결을 해제한 뒤 삭제한다. 예를 들어 로그인 관련 규칙이 정상 사용자를 오탐으로 차단하면, 그 규칙만 동작을 카운트(기록만 하고 차단 안 함)로 바꿔 차단을 멈추고 로그로 원인을 확인한다.

#4동작 과정

  1. 규칙 편집web ACL 상세 화면에서 대상 규칙을 선택해 동작(차단·카운트 등)이나 조건을 수정하고 저장한다.
  2. 규칙 삭제규칙 목록에서 제거할 규칙을 골라 삭제하면 평가 대상에서 빠진다.
  3. web ACL 삭제리소스와의 연결을 먼저 해제한 뒤에 web ACL 자체를 삭제한다. 연결이 남아 있으면 삭제할 수 없다.

보호 대상 리소스 연결·분리

CloudFront·API Gateway·ALB 등 보호 대상 AWS 리소스에 보호 팩을 연결해 검사를 적용하고, 해제하거나 다른 보호 팩으로 바꿀 때 쓰는 연결·분리 작업.

→ 01-03 참조

#1문제 상황

기존에는 보호 대상 리소스마다 보안 설정을 각각 따로 구성해야 했다. 웹 ACL(보호 규칙을 담는 꾸러미)을 아무리 정교하게 만들어도, 그것을 실제 AWS 리소스에 연결하지 않으면 요청 검사가 전혀 일어나지 않는다. 또 리소스별로 설정이 흩어져 있어 어떤 리소스가 어느 규칙을 받는지 파악하기 어렵고, 연결을 빼먹은 리소스는 보호 규칙을 하나도 거치지 않고 그대로 노출되는 문제가 생긴다.

#2핵심 질문

한 번 만들어 둔 웹 ACL을 어떤 AWS 리소스에 적용하고, 반대로 어떻게 떼어낼 것인가?

#3동작 예시

생성한 웹 ACL 하나를 CloudFront 배포(콘텐츠를 전 세계 엣지에서 서빙하는 서비스)에 연결하면, 그 배포로 들어오는 모든 요청이 웹 ACL의 규칙을 순서대로 거친 뒤에야 원본 서버로 전달된다. 연결만으로 보호가 시작되고, 분리하면 그 즉시 보호가 끝난다.

#4동작 과정

  1. 연결 대상 지정보호할 리소스(CloudFront 배포, Application Load Balancer, API Gateway 등)를 콘솔이나 API로 선택한다.
  2. 연결 실행웹 ACL을 해당 리소스에 연결하면 리소스에 도착하는 요청부터 웹 ACL 규칙 평가가 적용되기 시작한다.
  3. 분리로 해제더 이상 보호가 필요 없으면 웹 ACL과 리소스의 연결을 끊는다. 규칙은 그대로 유지되므로 나중에 다시 연결만 하면 보호가 복원된다.

#5한 줄 요약

웹 ACL을 보호 대상 AWS 리소스에 붙였다 떼는 연결·분리 관리로, 연결된 리소스의 트래픽에만 규칙 평가가 적용되는 것

규칙 우선순위와 처리 순서

보호 팩에 추가한 규칙이 낮은 우선순위 번호부터 차례로 평가되어 첫 번째 일치 규칙의 액션이 적용되고, 일치가 없으면 기본 액션을 따르는 처리 순서.

#1문제 상황

기존에는 웹 ACL 안에 규칙을 여러 개 넣을 수 있었지만, 규칙 사이의 실행 순서가 정해져 있지 않으면 같은 요청이라도 어떤 규칙을 먼저 보느냐에 따라 결과가 달라졌다. 예를 들어 "특정 IP 차단" 규칙과 "모든 요청 허용" 규칙이 동시에 조건에 맞을 때, 먼저 만난 규칙이 무엇이냐에 따라 차단과 허용이 뒤집힌다. 이런 충돌 때문에 규칙을 추가·변경할 때마다 전체 동작을 예측하기 어려운 상태가 된다.

#2핵심 질문

웹 ACL 안의 여러 규칙이 모두 조건에 맞을 때, 어느 규칙의 결과를 최종적으로 적용할 것인가?

#3동작 예시

각 규칙에 우선순위 숫자를 부여하고 작은 숫자부터 순서대로 평가하는 방식이다. 예를 들어 100번 규칙이 먼저 평가되고 200번 규칙이 나중에 평가되며, 먼저 조건에 맞아 확정된 규칙의 액션이 그 요청의 최종 처리로 결정된다.

#4동작 과정

  1. 우선순위 부여웹 ACL 안의 모든 규칙에 중복 없는 우선순위 숫자를 지정한다. 숫자가 작을수록 먼저 평가된다.
  2. 순서대로 평가들어온 요청을 우선순위 낮은 숫자부터 규칙에 대입해, 조건에 일치하는 규칙을 찾는다.
  3. 결과 확정조건에 맞는 규칙이 나오면 즉시 그 규칙의 액션이 적용되고 남은 규칙 평가는 중단된다. 어떤 규칙에도 안 걸리면 기본 액션이 적용된다.

#5한 줄 요약

규칙마다 우선순위를 매겨 정해진 순서로 평가하고, 처음 일치한 규칙의 액션을 최종 결과로 확정하는 것

보호 팩(web ACL) 구성02-05

기본 액션 설정

보호 팩의 규칙 중 어느 것도 일치하지 않은 요청에 대해 전체가 취할 액션(예: 허용·차단)을 기본값으로 정하는 설정.

#1문제 상황

기존에는 웹 ACL의 규칙이 조건에 맞는 요청만 처리하고, 어떤 규칙에도 걸리지 않는 요청은 별다른 처리 기준이 없어 관리자가 예측하기 어려운 방식으로 통과되거나 막혔다. 규칙을 아무리 잘 만들어도 "그 외 나머지 요청"을 어떻게 할지가 정해져 있지 않으면, 새로 유입되는 평범한 트래픽에 대해 일관된 정책을 적용할 수 없는 문제가 있다.

#2핵심 질문

웹 ACL의 모든 규칙을 통과한 요청을 기본적으로 허용할지 차단할지 어떻게 정할 것인가?

#3동작 예시

기본 액션(default action)을 Allow로 설정하면 어떤 규칙에도 걸리지 않은 요청은 그대로 통과하고, Block으로 설정하면 그런 요청은 전부 차단된다. 규칙이 하나도 없는 새 웹 ACL에서도 이 기본 액션이 모든 요청의 처리 기준이 된다.

#4동작 과정

  1. 기본 액션 선택웹 ACL 생성 시 Allow나 Block 중 하나를 기본 액션으로 지정한다.
  2. 규칙 평가도착한 요청을 우선순위 순서대로 규칙에 대입해 일치 여부를 확인한다.
  3. 기본 액션 적용모든 규칙에서 일치하지 않은 요청에만 선택한 기본 액션이 적용되어 통과 또는 차단이 결정된다.

#5한 줄 요약

어떤 규칙에도 일치하지 않는 요청에 대해 허용 또는 차단 중 하나를 기본값으로 미리 정해, 규칙의 사각지대까지 일관된 처리를 보장하는 것

규칙 그룹 동작과 오버라이드

보호 팩에 포함한 규칙 그룹의 동작(평가 여부·액션)을 그룹 단위로 관리하고, 그룹 안 개별 규칙의 액션을 기본값에서 다른 액션으로 바꾸는 오버라이드 동작.

→ 05-01 참조

#1문제 상황

기존에는 규칙을 묶어 둔 규칙 그룹을 웹 ACL에 통째로 추가하면, 그 안의 모든 규칙이 담긴 대로 실행되었다. 그런데 그룹 안의 개별 규칙 하나가 내 서비스 상황에 맞지 않을 때, 그 규칙을 빼려면 그룹 전체를 해체하거나 그룹에서 규칙을 직접 제거해야 했다. 이러면 나머지 정상 규칙들까지 같이 잃게 되고, 특히 AWS가 관리하는 규칙 그룹은 내가 수정할 수 없어서 개별 조정이 아예 불가능한 문제가 있다.

#2핵심 질문

규칙 그룹 전체를 쓰면서도, 그룹 안의 특정 규칙 동작만 따로 바꿀 수는 없을까?

#3동작 예시

관리형 규칙 그룹(시중의 공격 패턴 규칙 묶음)을 웹 ACL에 넣은 뒤, 그 안의 규칙 하나만 Count(차단하지 않고 세기만 하는 동작)로 오버라이드(덮어쓰기)한다. 그 규칙은 실제로는 차단하지 않고 지표에만 기록되므로, 나머지 규칙은 원래 동작을 그대로 수행한다.

#4동작 과정

  1. 그룹 추가규칙 그룹을 웹 ACL에 추가한다. 이때 그룹 전체의 동작(예: 그룹 안 요청을 전부 차단하는지)을 함께 지정할 수 있다.
  2. 개별 규칙 오버라이드콘솔에서 그룹 안의 특정 규칙을 선택해 액션을 다른 값(예: Block → Count)으로 덮어쓴다. 오버라이드한 규칙만 동작이 바뀐다.
  3. 그룹 동작과 오버라이드의 조합 적용웹 ACL 평가 시 그룹 안 규칙들은 각자의 최종 액션대로 실행되고, 오버라이드하지 않은 규칙은 원래 액션 그대로 실행된다.

#5한 줄 요약

규칙 그룹을 통째로 재사용하면서 개별 규칙 또는 그룹 전체의 액션을 덮어써서, 그룹을 해체하지 않고도 세부 동작을 조정하는 것

본문 검사 한계·토큰 도메인·트래픽 지표

보호 팩이 검사하는 요청 본문 크기의 한계와 검사 생략 옵션, CAPTCHA·챌린지·토큰에 쓰일 도메인 설정, 그리고 보호 팩의 트래픽 지표를 보는 방법을 아우르는 구성 항목.

→ 08-02 참조

#1문제 상황

기존에는 웹 ACL이 요청 본문을 검사한다고 생각하고 설정했지만, 본문 검사에는 크기 한계가 있어서 일정 크기(기본 8KB)를 넘는 요청의 본문은 검사되지 않는다는 점을 모르면 검사 누락 구간이 생긴다. 또 CAPTCHA·Challenge 같은 상호작용을 통과한 클라이언트가 받는 토큰의 신뢰 범위를 도메인으로 제한하지 않으면 다른 도메인에서 발급된 토큰까지 유효하게 받아들여질 수 있다. 마지막으로 실제 트래픽이 어떻게 허용·차단됐는지 지표로 확인하지 않으면 규칙이 제대로 동작하는지, 너무 많이 차단하고 있는지 판단할 수 없다.

#2핵심 질문

본문 검사의 크기 한계, 토큰을 신뢰할 도메인, 그리고 처리 결과 지표를 어떻게 함께 관리할 것인가?

#3동작 예시

본문 검사 한계를 8KB로 확인해 두고, 내 사이트 도메인만 토큰 도메인으로 등록한 뒤, 트래픽 지표에서 "차단된 요청 수"와 "허용된 요청 수"를 보는 방식이다. 이 세 가지를 한 세트로 파악하면 검사가 빠진 요청과 신뢰할 수 없는 토큰, 과도한 차단을 한 번에 잡아낼 수 있다.

#4동작 과정

  1. 본문 검사 한계 확인웹 ACL에 설정된 본문 검사 한계값을 확인하고, 그 크기를 넘는 요청은 본문 검사에서 제외됨을 인지한다.
  2. 토큰 도메인 지정CAPTCHA·Challenge 토큰을 신뢰할 도메인 목록을 등록해, 그 도메인에서 발급된 토큰만 유효하게 처리한다.
  3. 지표로 결과 확인웹 ACL이 처리한 트래픽의 허용·차단·카운트 지표를 보고 규칙의 동작과 오작동 여부를 점검한다.

#5한 줄 요약

본문 검사의 크기 한계, 토큰의 신뢰 도메인, 트래픽 처리 지표라는 세 가지 관점을 함께 확인해 검사 누락과 오동작 없이 보호가 실제로 작동하는지 유지하는 것

규칙: 문장(statement) 만들기03-01

규칙과 규칙 액션

AWS WAF 규칙은 검사 조건(문장)과 그 조건이 충족될 때 수행할 액션(허용·차단·카운트·캡차 등)을 묶은 보호의 기본 단위다.

#1문제 상황

기존에는 웹 ACL만 만들어 두면 요청이 전부 검사될 것이라고 생각하기 쉽지만, 웹 ACL 자체는 조건이 없으면 모든 요청에 기본 액션만 적용한다. 특정 공격 패턴이나 특정 IP 대역을 막으려면 "어떤 요청인지 판별하는 조건"과 "그 조건에 맞으면 무엇을 할지"를 담은 규칙이 반드시 필요하다. 규칙이 없으면 세밀한 차단은 아예 시작할 수 없는 상태다.

#2핵심 질문

요청이 어떤 조건에 맞는지 판단하는 규칙과, 그 조건에 맞았을 때 취할 액션은 어떻게 정의할 것인가?

#3동작 예시

"IP가 203.0.113.0/24 대역에 속하면 차단한다"는 규칙 하나가 전형적인 형태다. 조건(statement)은 "IP 집합에 포함되는지"를 판별하고, 액션(action)은 일치했을 때 Block을 실행한다. 이 둘이 짝을 이뤄 하나의 규칙이 된다.

#4동작 과정

  1. 조건(statement) 정의요청의 어떤 부분(IP, 헤더, 본문 문자열 등)을 어떤 방식(포함, 일치, 크기 등)으로 판별할지 조건을 만든다.
  2. 액션(action) 지정조건이 맞은 요청에 적용할 동작을 선택한다. Allow는 통과, Block은 차단, Count는 차단 없이 집계만 한다.
  3. 웹 ACL에 추가해 평가규칙에 우선순위를 붙여 웹 ACL에 넣으면, 이후 도착하는 요청마다 조건 평가와 액션 적용이 실행된다.

문장 설정: 요청 구성요소와 변환

검사할 요청 구성요소(헤더·쿼리 문자열·본문·쿠키 등)를 지정하고, 매치 전에 텍스트 변환(소문자화·디코딩 등)을 적용해 비교 기준을 통일하는 문장 설정이다.

#1문제 상황

웹 ACL(Web Access Control List, 요청 허용·차단 규칙 묶음)에 규칙을 넣을 때, 규칙은 "어떤 요청을 검사할지"와 "검사 결과가 맞으면 어떻게 할지"를 담아야 한다. 처음에는 이 조건을 IP 주소 대역 하나나 URL 경로 하나로만 표현했는데, 그 방식으로는 "헤더 값에 특정 문자열이 들어 있는 POST 요청"처럼 여러 요소를 조합하거나 검사 전에 값을 정제해야 하는 경우를 표현할 수 없었다. 또 요청 본문(body, 몸통에 해당하는 데이터 부분)을 그대로 검사하면 대소문자 차이, 인코딩된 특수문자 때문에 공격 패턴이 쉽게 회피되는 한계가 있었다.

#2핵심 질문

검사할 요청의 어느 부분을, 어떤 형태로 바꾼 뒤에, 무엇과 비교할지를 한 문장으로 정확히 지정할 수 없을까?

#3동작 예시

"User-Agent 헤더의 값에서 모든 공백을 제거한 결과가 'MyApp/1.0'과 같은 문자열인 요청"이라는 조건을 하나의 문장으로 만든다. 이 문장은 검사 대상(header, 헤더 — 요청의 머리 부분에 실리는 메타데이터), 대상 필드(User-Agent), 적용할 변환(공백 제거), 비교 값(MyApp/1.0)을 순서대로 담고 있어, WAF가 이 문장 하나만 보고 "무엇을 어떻게 검사할지"를 바로 알 수 있다.

#4동작 과정

  1. 구성요소 선택요청에서 어느 부분을 검사할지 정한다. origin(출발지 IP), header(요청의 특정 헤더), body(요청 본문), URI path(URL에서 경로 부분), query string(URL의 ? 뒤 파라미터) 등이 대상이 된다.
  2. 변환 적용비교 전에 텍스트 변환(transformation, 문자열을 정해진 규칙으로 바꾸는 처리)을 붙인다. 소문자화, 공백·HTML 태그 제거, URL 디코딩(인코딩된 %20 같은 표기를 실제 문자로 복원) 등을 순서대로 적용해 공격 패턴이 형태를 바꿔도 잡히게 한다.
  3. 문장 완성과 판정변환된 값을 지정한 비교 기준(문자열·정규식·크기 등)과 대조해 참/거짓을 만들고, 규칙이 이 문장의 결과에 따라 허용·차단·카운트 같은 동작을 수행한다.

문자열·크기·정규식 매치 문장

요청 구성요소가 특정 문자열을 포함하거나, 정해진 크기 범위를 넘거나, 정규식 패턴과 일치하는지 검사하는 문장이다.

#1문제 상황

초기 조건식에는 "IP가 이 대역에 속하는가" 같은 단순 비교만 있었고, 요청 내용 자체를 기준으로 삼는 방법이 없었다. 그래서 "본문에 특정 문구가 들어갔는지", "쿠키 값이 너무 긴지" 같은 세부 검사는 불가능했고, 여러 문자열 패턴을 묶어서 검사하려면 규칙을 여러 개 만들거나 와일드카드(*) 같은 단순 기호로 퉁쳐야 했다. 이런 방식은 조건마다 규칙이 늘어나고, 패턴 표현도 정밀하지 않아 정확한 판정이 어려웠다.

#2핵심 질문

문자열·크기·정규식처럼 요청 값의 구체적인 내용을 기준으로 참/거짓을 판별하는 문장을 어떻게 만들 수 있을까?

#3동작 예시

"쿼리 문자열에서 'admin'이라는 문자열이 정확히 포함된 요청"을 만들 때, 문자열 매치(string match) 문장에 검사 대상(쿼리 문자열), 비교 문자열(admin), 대소문자 무시 여부를 지정한다. 값이 하나의 패턴으로 고정된 이 예시는 문자열 매치의 가장 단순한 동작 방식을 그대로 보여준다.

#4동작 과정

  1. 검사 대상과 비교 값 지정문자열 매치(string match)는 대상 값이 지정한 문자열과 같은지, 크기 제약(size constraint)은 대상 값의 길이(바이트 단위)가 지정한 범위 안인지를 본다. 대상 값에는 요청 구성요소(헤더·본문·쿼리 문자열 등)와 텍스트 변환을 조합해 넣는다.
  2. 패턴 세트로 비교정규식 매치(regex match)는 대상 값을 정규식 패턴 세트(regex pattern set, 정규식 여러 개를 묶어 둔 재사용 목록)의 각 패턴과 대조한다. 대상이 패턴 중 하나라도 맞으면 문장은 참이 된다.
  3. 판정 반환비교 결과 참이면 규칙의 동작(허용·차단 등)이 실행되고, 거짓이면 다음 규칙으로 넘어간다.

#5한 줄 요약

요청의 특정 값을 문자열·크기·정규식 패턴과 대조해 일치 여부를 참/거짓으로 반환하는 매치 문장

IP·ASN·지리 매치 문장

요청이 온 IP 주소(IP set), 자치 시스템 번호(ASN), 또는 국가·지리적 위치가 설정한 조건에 맞는지 검사하는 문장이다.

#1문제 상황

초기 조건식은 요청을 보낸 IP 주소 하나만 출발지 판단의 근거로 삼았다. 그런데 IP만으로는 "어느 국가에서 왔는지", "어느 인터넷 사업자(네트워크 운영자)가 관리하는 주소인지"를 알 수 없었고, 요청이 프록시나 CDN을 거쳐 오면 실제 클라이언트 IP가 아니라 중간 서버의 IP가 조건식에 잡히는 문제도 있었다. IP 대역을 대량으로 등록해야 하는 경우 관리 부담도 커졌다.

#2핵심 질문

요청이 온 IP 주소를 국가·인터넷 사업자(ASN)·IP 집합 기준으로 비교하는 매치 문장은 어떻게 만들 수 있을까?

#3동작 예시

"요청이 한국(KR)에서 왔는가"를 판정하는 지리 매치(geo match) 문장을 만든다. WAF는 요청의 출발지 IP를 국가 코드로 변환해 두고, 문장에 지정한 국가 코드 목록(예: KR)과 대조해 참/거짓을 반환한다. IP 대역을 일일이 나열하지 않아도 국가 단위 차단이 성립한다.

#4동작 과정

  1. 출발지 IP 확정요청의 origin(실제 출발지) IP를 확인한다. 프록시·CDN 뒤에 있는 경우 forwarded IP(요청 헤더에 기록된 원래 클라이언트 IP)를 쓸지, 그 헤더의 신뢰도를 어떤 값으로 둘지 설정으로 정한다.
  2. 기준과 대조IP 집합 매치(IP set match)는 출발지 IP가 IP 집합(IP set, 등록해 둔 IP 대역들의 목록)에 속하는지, ASN 매치(ASN match)는 해당 IP를 관리하는 인터넷 사업자 번호(ASN)가 지정 목록에 속하는지, 지리 매치는 국가 코드가 지정 목록에 속하는지를 각각 비교한다.
  3. 판정 반환목록에 속하면 참, 아니면 거짓을 반환해 규칙 동작을 실행하거나 다음 규칙으로 넘긴다.

#5한 줄 요약

출발지 IP를 IP 집합·ASN·국가 코드 목록과 대조해 요청의 출처를 기준으로 판정하는 매치 문장

SQLi·XSS·라벨 매치 문장

요청에 SQL 인젝션·XSS 공격 패턴이 있는지, 또는 앞선 규칙이 부여한 라벨이 붙어 있는지 검사하는 문장이다.

#1문제 상황

처음에는 SQL 인젝션(SQLi, 입력 값에 SQL 명령을 끼워 넣는 공격)과 XSS(크로스 사이트 스크립팅, 악성 스크립트를 웹 페이지에 심는 공격) 같은 공격을 막기 위해 공격 패턴을 개발자가 직접 규칙으로 작성했다. 그러나 공격 구문은 대소문자, 주석, 인코딩 등으로 형태가 무한히 바뀌어 수동 패턴은 자꾸 빠뜨렸고, 그 때문에 "이 요청은 공격 후보인가"를 자동으로 판별해 주는 신뢰할 만한 기준이 필요해졌다. 또한 같은 요청을 여러 규칙에서 처리한 결과를 다음 규칙의 입력으로 넘겨주는 표시(라벨)도 없어 규칙 간 연계가 어려웠다.

#2핵심 질문

SQL 인젝션·XSS 의심 여부를 자동 판정하고, 앞선 규칙의 판정 결과를 라벨로 남겨 뒤의 규칙이 참조하게 하려면 어떻게 해야 할까?

#3동작 예시

"쿼리 문자열에서 SQL 인젝션으로 보이는 패턴을 찾으면"이라는 SQLi 매치 문장을 만든다. WAF가 내장한 공격 탐지 엔진이 대상 값을 스스로 분석해 "공격 의심이 있다/없다"를 참/거짓으로 반환하므로, 개발자가 공격 구문 목록을 직접 관리하지 않아도 된다.

#4동작 과정

  1. 공격 탐지 문장 구성SQLi 매치(SQL injection match)와 XSS 매치(XSS match) 문장에 검사 대상(헤더·본문·쿼리 문자열 등)과 텍스트 변환을 지정한다. WAF 내장 엔진이 대상 값을 여러 공격 형태로 해석해 의심 여부를 판정한다.
  2. 라벨 부착규칙의 동작에 라벨(문자열 표시, 예: awswaf:managed:aws:sqli)을 달아두면, 이 규칙이 요청을 처리할 때 그 라벨이 요청에 기록된다. 뒤의 라벨 매치(label match) 문장은 요청에 기록된 라벨 중 지정한 라벨이 있는지(네임스페이스 접두어로 무리 지어 비교 가능)를 확인해 판정한다.
  3. 판정 반환공격 의심이거나 라벨이 존재하면 참을 반환해 차단·카운트 등의 규칙 동작을 수행한다.

#5한 줄 요약

내장 엔진이 SQLi·XSS 의심 여부를 자동 판정하고, 규칙의 처리 결과를 라벨로 남겨 다른 규칙이 그 라벨을 조건으로 삼게 하는 매치 문장

논리 문장·스코프다운·재사용 엔티티

AND·OR·NOT 논리로 여러 문장을 조합하고, 스코프다운으로 검사 대상을 제한하며, IP set 등 재사용 엔티티로 공통 조건을 공유하는 문장 체계다.

#1문제 상황

하나의 문장은 "한 가지 조건"만 표현할 수 있어서, "이 헤더가 있고 AND 본문이 짧고"처럼 조건을 조합하거나 "이 조건이 아닌 경우"를 표현하려면 규칙을 여러 개 만들고 순서로 흉내 내야 했다. 조건이 늘어날수록 규칙 수가 늘고, 특정 요청에만 규칙을 적용하려면(예: 로그인 경로에만 검사 적용) 적용 범위를 좁힐 방법도 마땅치 않았다. 같은 패턴을 여러 규칙에서 쓰려면 매번 조건을 다시 작성해야 해서 수정 시 일관성을 잃기 쉬웠다.

#2핵심 질문

문장들을 AND·OR·NOT로 조합하고, 검사 범위를 좁히고, 공통 패턴을 한 번 정의해 여러 규칙에서 재사용하려면 어떻게 해야 할까?

#3동작 예시

AND 문장 안에 "헤더에 X-API-Key가 있다"와 "쿼리 문자열이 'user=admin'과 같다" 두 매치 문장을 넣고, 여기에 스코프다운(scope-down, 검사 적용 범위를 좁히는 문장)으로 "URI 경로가 /login으로 시작하는 요청만"이라는 제한을 걸어둔다. 이렇게 하면 로그인 요청 중 두 조건을 모두 만족할 때만 판정이 참이 되는 단일 규칙이 완성된다.

#4동작 과정

  1. 조합AND(모두 참), OR(하나라도 참), NOT(참을 거짓으로 뒤집음) 문장 안에 매치 문장들을 자식으로 넣어 하나의 참/거짓으로 수렴시킨다.
  2. 범위 제한과 재사용스코프다운 문장으로 해당 규칙이 검사할 요청 범위를 좁힌다. 재사용 엔티티(reusable entity, IP 집합·정규식 패턴 세트·규칙 그룹처럼 한 번 만들어 여러 곳에서 참조하는 객체)를 문장에 연결해 동일한 기준을 여러 규칙이 공유한다.
  3. 최종 판정조합·제한·재사용이 모두 반영된 최종 결과가 참이면 규칙 동작을 실행한다.

#5한 줄 요약

매치 문장들을 논리 연산으로 조합하고, 스코프다운으로 적용 범위를 좁히며, IP 집합·패턴 세트·규칙 그룹을 재사용해 하나의 규칙을 표현하는 문장 구조

rate-based 규칙 (속도 기반 차단)04-01

rate-based 규칙 개념과 설정

일정 시간 창 안에서 설정한 요청 수(임계값)를 넘기는 과도한 트래픽을 감지해 차단하는 속도 기반 규칙의 개념과 규칙 생성 시 필요한 설정.

#1문제 상황

일반 규칙은 요청 하나하나의 내용을 검사해 허용·차단을 정한다. 그런데 내용이 정상적인 요청을 비정상적으로 빠른 속도로 반복 보내는 공격(로그인 시도 반복, 데이터 크롤링, DDoS 폭주 등)은 개별 요청만 봐서는 정상과 구분이 안 되어 막을 수 없었다. 요청 수를 세려면 로그를 별도로 수집해 분석해야 했고, 실시간으로 차단까지 이어지는 자동 처리가 없었다.

#2핵심 질문

일정 시간 동안 들어온 요청 수가 기준을 넘는 클라이언트를 자동으로 차단하려면 어떻게 해야 할까?

#3동작 예시

"5분 동안 같은 IP에서 온 요청이 2,000건을 넘으면 차단"이라는 rate-based 문장을 만든다. WAF가 각 IP별로 5분 창(window, 집계 시간 구간) 안의 요청 수를 계속 세다가 2,000건을 넘는 순간 그 IP의 이후 요청은 기준(평가 키, aggregation key — 요청을 어떤 단위로 묶어 셀지 정하는 값)에 따라 차단된다. 이 하나의 문장으로 속도 기반 차단이 동작한다.

#4동작 과정

  1. 평가 키와 한도 지정요청을 묶는 단위인 평가 키(IP 주소, IP+세션, IP+쿠키 등으로 선택)와 평가 기간(1분 또는 5분) 및 한도(최대 허용 요청 수)를 문장에 설정한다.
  2. 요청 수 집계WAF가 평가 기간 동안 평가 키별로 요청 수를 실시간으로 누적한다. 그리고 특별한 설정을 하지 않으면 회귀 집계(regression aggregation, 한도를 넘은 이후에는 해당 요청을 항상 차단 대상으로 누적 유지)가 자동 적용되어 한 번 넘긴 클라이언트는 계속 집계된다.
  3. 한도 초과 시 차단평가 기간 내 요청 수가 한도를 넘으면 조건이 참이 되어 차단 등의 규칙 동작이 실행되고, 넘지 않으면 다음 규칙으로 넘어간다.

#5한 줄 요약

평가 키별로 단위 시간당 요청 수를 실시간 집계해, 설정한 한도를 넘는 클라이언트를 자동으로 차단하는 속도 기반 규칙

rate-based 규칙 (속도 기반 차단)04-02

집계 키와 요청 제한

요청을 묶어서 셀 기준인 집계 키(IP, 전달 IP, 라벨 네임스페이스 등)와 임계값 초과·평가 창 등 요청 제한 적용 방식을 정의한다.

#1문제 상황

기존 rate-based 규칙은 들어오는 요청 전체를 하나의 묶음으로 세어 "분당 N개를 넘으면 차단"하는 방식으로 작동했다. 이 방식은 공격자가 여러 IP로 요청을 나눠 보내면 각 IP의 요청 수는 적어 한도를 넘지 않으므로 감지하지 못한다. 또 단순히 전체 요청 수만 세다 보니, 정상 사용자가 갑자기 몰려든 경우(예: 이벤트로 인한 접속 급증)와 공격을 구분하지 못해 정상 트래픽까지 차단할 위험이 있다. 즉 "무엇을 기준으로 몇 개까지 세느냐"를 정할 수 없는 것이 기존 방식의 명확한 한계다.

#2핵심 질문

여러 IP에 분산된 공격과 정상적인 접속 급증을 구분하려면, 요청 수를 누구를 기준으로 세고 언제 차단해야 할까?

#3동작 예시

rate-based 규칙에 집계 키(요청을 묶어 셀 기준)를 "IP 주소와 사용자 에이전트의 쌍"으로 지정하고 요청 제한을 "5분에 2000건"으로 설정한다고 하자. 공격자가 어떤 IP 1개에서 5분 동안 3000건을 보내면 그 IP와 사용자 에이전트 쌍이 한도를 넘어 차단되지만, 정상 사용자는 5분에 2000건을 넘는 경우가 거의 없어 영향이 없다. 같은 IP라도 사용자 에이전트가 다르면 서로 다른 집계 키로 취급되어 따로 세어진다.

#4동작 과정

  1. 집계 키 지정요청을 묶어 셀 기준(IP 주소, IP+사용자 에이전트, 쿠키 값, 라벨, ASN 등)을 규칙에 설정한다. WAF는 이 기준으로 같은 묶음에 속하는 요청들을 한 개의 카운터로 합산한다.
  2. 요청 제한과 시간 창 설정집계 키 하나가 시간 창(예: 5분) 동안 보낼 수 있는 최대 요청 수를 지정한다. WAF가 각 집계 키의 요청 수를 시간 창 단위로 실시간 갱신하며 한도 초과 여부를 판정한다.
  3. 한도 초과 키만 차단요청 수가 제한을 넘은 집계 키에 속한 이후 요청에 규칙 액션(차단 등)을 적용한다. 초과하지 않은 키의 요청은 계속 통과시킨다.

#5한 줄 요약

요청을 집계 키(IP, IP+사용자 에이전트 등)로 묶어 시간 창 안의 허용 한도를 각각 세고, 한도를 넘긴 키의 요청만 골라 차단하는 것

rate-based 규칙 (속도 기반 차단)04-03

성공 사례 예제와 제한 IP 목록

로그인 페이지·헤더 누락·라벨 등 실제 시나리오에 rate-based 규칙을 적용한 예제와, 규칙이 차단한 IP 주소를 목록으로 확인하는 방법.

#1문제 상황

기존에는 rate-based 규칙이 모든 요청을 대상으로 "분당 N건"만 세는 단순한 형태였다. 그런데 실제 공격은 로그인 페이지의 무차별 대입(아이디·비밀번호를 계속 입력해 뚫는 시도)처럼 특정 경로에 집중되거나, 특정 헤더가 빠진 요청을 대량으로 보내는 방식으로 발생한다. 전부를 같은 기준으로 세는 규칙으로는 이런 특정 대상 공격을 정확히 잡을 수 없고, 반대로 정상 트래픽이 과도하게 차단될 수도 있다. 게다가 어떤 IP가 실제로 차단되었는지 확인할 방법이 없어 운영 대응이 어려운 것도 한계였다.

#2핵심 질문

공격이 집중되는 조건을 지정해 rate-based 규칙을 걸고, 차단된 IP 목록은 어디서 어떻게 확인할 수 있을까?

#3동작 예시

로그인 페이지(/login 경로)에 대해서만 "IP 주소와 사용자 에이전트 쌍 기준 5분에 100건"이라는 rate-based 규칙을 적용한다고 하자. 정상 사용자는 로그인 시도가 5분에 100건을 넘지 않아 아무 영향이 없다. 반면 무차별 대입 공격은 로그인 경로에 요청을 집중시키므로, 조건이 해당 요청들만 집계 대상으로 한정해 한도를 훨씬 넘겨 정확히 차단된다. 차단된 IP는 콘솔의 rate-based 규칙 상세 화면이나 API를 통해 목록으로 조회할 수 있다.

#4동작 과정

  1. 조건부 대상 한정규칙에 스코프다운 조건(경로가 /login인 요청, 특정 헤더가 없는 요청 등)을 붙여, 그 조건에 맞는 요청만 rate-based 집계 대상으로 한정한다.
  2. 집계와 한도 판정한정된 요청을 지정한 집계 키로 묶어 요청 제한과 비교하고, 한도를 넘긴 키의 요청에 차단 액션을 적용한다.
  3. 차단 IP 조회콘솔 또는 API로 rate-based 규칙이 차단한 IP 목록을 조회해 모니터링하고 운영에 대응한다.

#5한 줄 요약

경로·헤더 같은 조건으로 집계 대상을 한정해 rate-based 제한을 정확히 적용하고, 차단된 IP 목록을 콘솔·API로 조회해 운영 대응까지 가능하게 하는 것

규칙 그룹과 용량05-01

규칙 그룹 문장과 규칙 그룹 개념

여러 규칙을 하나로 묶은 재사용 컨테이너로, 보호 팩(web ACL) 안에서 하나의 문장(rule group statement)으로 참조해 일괄 적용한다.

#1문제 상황

기존에는 웹 ACL마다 규칙을 하나씩 직접 정의해 넣었다. 개발용 웹 ACL, 운영용 웹 ACL처럼 웹 ACL이 여러 개면 같은 공격 차단 규칙을 웹 ACL 수만큼 반복해서 만들어야 했다. 규칙 하나를 고치려면 그 규칙이 들어 있는 모든 웹 ACL을 찾아 일일이 수정해야 했고, 웹 ACL 하나의 규칙 수가 늘어나면 구성이 커져 읽고 관리하기 어려워졌다. 규칙이 재사용되지 않고 각 웹 ACL에 중복으로 박혀 있는 것이 기존 방식의 명확한 한계다.

#2핵심 질문

여러 웹 ACL에서 같은 규칙 묶음을 한 번만 만들고 일관되게 적용하려면 규칙을 어떤 단위로 묶어야 할까?

#3동작 예시

SQLi 차단 규칙, XSS 차단 규칙, 지리 차단 규칙 세 개를 "공통 보안 규칙 그룹"이라는 규칙 그룹 하나로 묶는다. 규칙 그룹은 웹 ACL과 별개로 존재하는 독립 리소스다. 개발용·운영용 웹 ACL 두 곳에 이 그룹을 참조하는 문장 하나씩만 추가하면 두 웹 ACL이 같은 규칙들을 함께 평가하게 된다. 그룹 안의 규칙을 한 번 고치면 그 그룹을 쓰는 모든 웹 ACL에 동일하게 반영된다.

#4동작 과정

  1. 규칙 그룹 생성여러 규칙을 하나의 규칙 그룹 리소스로 묶어 저장한다. 웹 ACL과 별개로 존재하므로 어디서든 참조할 수 있다.
  2. 웹 ACL에 규칙 그룹 문장 추가웹 ACL에 규칙 그룹 문장(그룹 전체를 호출하는 특수한 문장)을 추가한다. 그룹 안 개별 규칙의 액션을 오버라이드(그 웹 ACL에서만 다르게 조정)할 수도 있다.
  3. 우선순위에 따라 평가웹 ACL의 규칙 우선순위에 맞춰 규칙 그룹 문장이 실행되고, 그룹 안의 규칙들이 순서대로 요청을 검사해 각자 설정된 액션을 적용한다.

#5한 줄 요약

여러 규칙을 하나의 독립 리소스인 규칙 그룹으로 묶어, 웹 ACL에 참조 문장을 추가하는 것만으로 같은 규칙 묶음을 여러 웹 ACL에서 재사용하는 것

관리형 규칙 그룹과 버전 관리

AWS나 파트너가 운영·버전 관리하는 규칙 그룹으로, 버전 수명주기와 만료에 따라 최신 방어 규칙을 유지한다.

#1문제 상황

기존에는 보안 규칙을 사용자가 직접 작성해야 했다. 새로운 공격 패턴이 나올 때마다 규칙을 스스로 찾아 고쳐야 했고, 보안 지식이 없으면 누락되거나 뒤처지기 쉬웠다. 설령 AWS가 운영하는 규칙 그룹을 쓰더라도, 규칙이 바뀌면 동작이 달라져 갑자기 정상 트래픽이 차단되는 사고가 날 수 있었다. 규칙의 갱신을 누가 하느냐, 그리고 갱신으로 인한 변화를 어떻게 통제하느냐가 해결되지 않은 문제였다.

#2핵심 질문

누군가 지속적으로 갱신해 주는 규칙 그룹을 쓰면서도, 업데이트로 인한 동작 변화를 안전하게 통제할 수는 없을까?

#3동작 예시

관리형 규칙 그룹은 AWS(또는 AWS Marketplace 파트너)가 만들고 최신 공격 패턴에 맞춰 계속 갱신하는 규칙 그룹이다. 여기에 버전 관리 기능이 붙는다. 예를 들어 현재 버전 v1.0을 "정적 버전"으로 고정해 웹 ACL에 추가하면, AWS가 v1.1, v1.2를 출시해도 쓰고 있는 규칙의 동작은 전혀 바뀌지 않아 안전하다. 반대로 "기본 버전"을 지정하면 AWS가 새 기본 버전을 정할 때 자동으로 따라간다. 고정한 버전의 유효 기간이 끝나면(만료) 해당 버전을 더 이상 쓸 수 없게 된다.

#4동작 과정

  1. 그룹 선택과 버전 지정웹 ACL에 관리형 규칙 그룹을 추가할 때 사용할 버전(정적 버전 고정 또는 기본 버전 추적)을 지정한다. 미지정 시 그룹의 기본 버전이 적용된다.
  2. 요청 평가지정된 버전의 규칙들이 요청을 검사하고 설정된 액션을 적용한다. 버전을 고정했으면 AWS의 갱신과 무관하게 동작이 유지된다.
  3. 만료 통제와 갱신고정 버전에도 만료일이 있으므로 만료 전에 새 버전으로 갱신하고, 버전 변경으로 생긴 동작 변화는 테스트·모니터링을 거쳐 반영한다.

#5한 줄 요약

AWS가 유지보수하는 규칙 그룹을 웹 ACL에 추가하고, 정적 버전 고정·기본 버전 추적·버전 만료 통제로 규칙 갱신의 충격을 관리하며 쓰는 것

관리형 그룹 작업: 조회·추가·알림

관리형 규칙 그룹의 목록·규칙·버전을 조회하고 보호 팩에 추가하며, 새 버전·만료 변경을 SNS 알림으로 받는 작업 절차.

→ 05-02 참조

#1문제 상황

기존에는 사용할 수 있는 관리형 규칙 그룹이 어떤 것들이 있는지, 각 그룹에 어떤 규칙이 들어 있는지 확인할 방법이 명확하지 않아 문서를 찾아다니거나 콘솔을 뒤져야 했다. 웹 ACL에 그룹을 추가한 뒤에도 새 버전이 출시되었는지, 쓰던 버전의 만료가 얼마 남았는지를 직접 챙기지 않는 한 알 수 없었다. 버전 갱신을 놓치면 보안 규칙이 뒤처지고, 만료를 놓치면 그룹이 갑자기 동작하지 않게 되는 것이 기존 방식의 한계다.

#2핵심 질문

관리형 규칙 그룹을 목록에서 찾아 웹 ACL에 추가하고, 버전 출시·만료 소식을 챙기려면 어떤 작업이 필요할까?

#3동작 예시

콘솔이나 API로 계정에서 사용 가능한 관리형 규칙 그룹 목록을 조회하면 각 그룹의 용도(예: Core rule set은 SQLi·XSS 등 공통 위협 차단)와 규칙 수를 확인할 수 있다. 그중 Core rule set 그룹을 웹 ACL에 추가하면 즉시 그 규칙들이 평가에 포함된다. 마지막으로 SNS 주제(알림을 받을 채널)를 지정해 두면, AWS가 새 버전을 출시하거나 그룹 버전이 곧 만료된다는 알림이 이메일 등으로 전달된다.

#4동작 과정

  1. 그룹 조회API 또는 콘솔에서 계정에 사용 가능한 관리형 규칙 그룹 목록을 가져오고, 원하는 그룹의 규칙 내역과 사용 가능한 버전 목록을 확인한다.
  2. 웹 ACL에 추가선택한 그룹을 웹 ACL에 추가하고 버전과 오버라이드(개별 규칙 동작 조정) 설정을 지정해 평가 대상에 포함시킨다.
  3. 알림 설정그룹과 연결할 SNS 주제를 지정한다. 이후 새 버전 출시·만료 임박 알림을 받아 적절한 시점에 버전을 갱신한다.

#5한 줄 요약

관리형 규칙 그룹을 조회해서 웹 ACL에 추가하고, SNS 알림으로 버전 출시·만료 소식을 받아 최신 상태를 유지하는 작업 흐름을 제공하는 것

규칙 그룹과 용량05-04

AWS 관리형 규칙(AWS Managed Rules)

AWS가 직접 운영하는 관리형 규칙 그룹 세트로, 일반 위협·사용 사례·IP 평판·계정 사기(ACFP·ATP)·봇·DDoS 방어를 즉시 제공한다.

#1문제 상황

기존에는 SQLi(데이터베이스 명령 삽입), XSS(스크립트 삽입) 같은 흔한 웹 공격을 막으려면 규칙을 처음부터 직접 작성해야 했다. 이런 공격 패턴은 전 세계적으로 표준적이어서 매번 다시 만들어 쓰는 것은 비효율적이고, 직접 만든 규칙에는 누락된 패턴이 생기기 쉬워 가장 흔한 공격부터 뚫릴 위험이 있었다. 공격 유형별로 어떤 대비가 표준으로 제공되는지 한눈에 파악하기도 어려웠다.

#2핵심 질문

모든 고객이 공통으로 당하는 웹 공격을, AWS가 미리 만들어 갱신해 주는 표준 규칙으로 바로 막을 수는 없을까?

#3동작 예시

AWS Managed Rules는 AWS가 직접 운영하는 관리형 규칙 그룹의 모음이다. 대표적인 그룹으로 Core rule set(OWASP 기준의 공통 위협인 SQLi·XSS·파일 크기 초과 등을 차단), 관리형 IP 평판(악성 IP 목록 기반 차단), Bot Control(봇 트래픽 식별·관리), ATP(계정 탈취 방지), ACFP(계정 생성 사기 방지)가 있다. 웹 ACL에 이 그룹 중 필요한 것을 추가하기만 하면, 별도로 규칙을 작성하지 않아도 해당 공격에 대한 보호가 즉시 적용된다.

#4동작 과정

  1. 그룹 선택보호 목적에 맞는 AWS 관리형 그룹(공통 위협, IP 평판, 봇, 계정 탈취·생성 사기 방지 등)을 목록에서 고른다.
  2. 웹 ACL에 추가선택한 그룹을 웹 ACL에 추가하고 버전과 오버라이드 설정을 지정해 평가에 포함시킨다. 규칙 작성을 직접 하지 않아도 보호가 시작된다.
  3. 최신 상태 유지AWS가 규칙과 버전을 갱신하므로, 알림을 받아 새 버전을 반영해 규칙이 뒤처지지 않게 유지한다.

#5한 줄 요약

AWS가 만들고 지속 갱신하는 표준 관리형 규칙 그룹을 웹 ACL에 추가하는 것만으로 흔한 웹 공격에 대한 보호를 즉시 얻는 것

규칙 그룹과 용량05-05

자체 규칙 그룹 관리

사용자가 직접 규칙을 모아 규칙 그룹을 생성·편집하고 보호 팩에 적용하거나 삭제·공유하는 관리 절차.

#1문제 상황

기존에는 규칙을 만들 때마다 web ACL(보호 팩, 요청을 검사해 허용·차단을 결정하는 방화벽 구성 단위) 안에 직접 규칙을 넣어 사용했다. 같은 검사 규칙을 여러 web ACL에 적용해야 하면 규칙 내용을 web ACL마다 반복해서 만들어 넣어야 하고, 규칙 하나를 고치려면 그 규칙이 들어 있는 모든 web ACL을 하나씩 찾아 수정해야 한다. web ACL이 많아질수록 같은 규칙이 여러 곳에 중복 존재하게 되어, 어느 한 곳만 고치고 다른 곳을 놓치면 web ACL마다 보호 수준이 달라지는 것이 명확한 한계다.

#2핵심 질문

규칙을 한 번만 만들어 두고 여러 web ACL에서 재사용하면서, 수정도 한곳에서 할 수는 없을까?

#3동작 예시

"헤더 보호"라는 규칙 그룹(rule group, 규칙을 담아두는 재사용 가능한 묶음) 하나에 보안 헤더 검사 규칙 3개를 넣고, 세 개의 web ACL이 모두 이 그룹 하나를 참조하게 만든다. 그룹 안의 규칙 하나를 고치면 그 그룹을 참조하는 모든 web ACL에 변경이 한 번에 반영되므로, 규칙을 수백 번 복사해 넣을 필요가 없다.

#4동작 과정

  1. 규칙 그룹 생성이름과 규칙 목록, 그룹이 사용할 Web ACL 용량(WCU)을 정해 규칙 그룹 리소스를 만든다.
  2. web ACL에 연결web ACL을 편집해 규칙 그룹을 참조로 추가하면, 그룹 안의 규칙 전체가 하나의 단위로 해당 web ACL의 검사 순서에 들어간다.
  3. 그룹 단위로 관리그룹을 수정하면 참조하는 모든 web ACL에 동시 반영되고, 그룹을 삭제하려면 먼저 모든 web ACL에서 분리해야 한다.

#5한 줄 요약

규칙을 그룹으로 묶어 여러 web ACL에서 재사용하고 수정과 삭제를 그룹 단위로 한곳에서 처리해 규칙 관리를 중앙화하는 것

Marketplace·서비스 소유 그룹·WCU

AWS Marketplace에서 구독하는 타사 규칙 그룹, 다른 AWS 서비스가 소유한 규칙 그룹, 그리고 모든 규칙이 소비하는 용량 단위 WCU를 다룬다.

#1문제 상황

기존에는 규칙 그룹을 직접 만들거나 AWS 관리형 규칙 그룹을 추가하는 방식만 생각했다. 그런데 실제로는 자신이나 AWS가 아닌 제3자가 만든 규칙 그룹도 web ACL에 들어온다. AWS Marketplace(타사 벤더가 보안 규칙을 판매하는 장터)에서 구독한 규칙 그룹, 그리고 Shield Advanced 같은 다른 AWS 서비스가 자동으로 넣는 서비스 소유 규칙 그룹이 그것이다. 이런 그룹은 내가 만들지 않았으므로 콘솔 어디에서 왔는지 파악하기 어렵고 수정 권한도 없다. 또 규칙이 늘어나면 각 규칙이 차지하는 용량인 WCU(Web ACL capacity unit)가 합산되어 web ACL의 총 용량 한도를 초과할 수 있으며, 초과하면 규칙을 더 추가할 수 없게 된다.

#2핵심 질문

내가 만들지 않은 규칙 그룹은 어디서 오는지 구분하고, web ACL에 규칙을 얼마나 넣을 수 있는지는 무엇이 결정하는가?

#3동작 예시

Marketplace에서 구독한 타사 규칙 그룹을 web ACL에 추가하면 그룹이 사용하는 WCU 수치가 전체 용량에 합산된다. 예를 들어 어떤 규칙 그룹이 15 WCU를 차지하면, 리전 web ACL의 총 한도인 1,500 WCU 중 15가 이 그룹에 배정되는 식으로 모든 규칙의 용량을 합산해 web ACL이 한도를 넘지 않는지 계산한다.

#4동작 과정

  1. 규칙 그룹 추가·식별Marketplace 구독 그룹이나 서비스 소유 그룹을 web ACL에 추가하고, 그룹의 출처에 따라 수정 가능 여부가 달라짐을 확인한다.
  2. WCU 합산web ACL 안의 모든 규칙과 규칙 그룹이 쓰는 WCU를 각각 더해 총 사용량을 산정한다(복잡한 검사일수록 WCU가 크고, 그룹은 그룹 전체 값으로 계산).
  3. 한도 초과 처리합산 결과가 web ACL 용량 한도(리전 1,500, CloudFront 5,000 등)를 넘으면 규칙을 더 추가할 수 없으므로, 규칙을 단순화하거나 제거해 용량을 확보한다.

#5한 줄 요약

규칙 그룹의 출처(자체·Marketplace·서비스 소유)에 따라 관리 방식을 구분하고, 모든 규칙이 차지하는 계산 용량을 WCU로 합산·제한해 web ACL이 정해진 용량 안에서 동작하게 하는 것

IP 세트 생성·관리

차단·허용·검사할 IP 주소와 CIDR 범위를 하나로 묶어 규칙에서 재사용하는 리소스

#1문제 상황

기존에는 IP 주소를 검사 기준으로 쓰려면 규칙을 만들 때마다 차단하거나 허용할 IP 주소와 CIDR 범위(네트워크를 표현하는 주소 표기, 예: 203.0.113.0/24)를 규칙 안에 직접 입력했다. 같은 IP 목록을 여러 규칙에서 쓰려면 주소를 규칙마다 반복해서 적어야 하고, 목록이 바뀔 때마다(예: 차단할 IP가 하나 추가되면) 그 목록을 사용하는 규칙을 전부 찾아 일일이 고쳐야 한다. IP 목록이 여러 규칙에 흩어져 있어 한 규칙만 갱신하고 나머지를 놓치면 검사 결과가 일관되지 않게 되는 것이 명확한 한계다.

#2핵심 질문

여러 규칙이 같은 IP 주소 목록을 공유하면서, 목록을 한 번만 고치면 모든 규칙에 반영되게 할 수는 없을까?

#3동작 예시

"차단 목록"이라는 IP 세트(IP set) 리소스 하나에 차단할 IP 주소와 CIDR 범위를 모아 두고, 각 규칙의 IP 세트 매치 문장(요청의 출발 IP가 세트에 들어 있는지 검사하는 문장)에서 이 세트를 참조하게 만든다. 이후 세트에 IP를 하나 추가하면 그 세트를 검사 기준으로 쓰는 모든 규칙이 같은 갱신된 목록으로 요청을 검사하게 된다.

#4동작 과정

  1. IP 세트 생성이름, 주소 유형(IPv4 또는 IPv6), 포함할 IP 주소 목록을 지정해 세트 리소스를 만든다.
  2. 규칙에서 참조web ACL의 규칙에서 IP 세트 매치 문장을 추가하고 사용할 세트를 선택하면, 규칙이 세트 안의 모든 주소를 검사 기준으로 사용한다.
  3. 목록 갱신세트에 주소를 추가·삭제하면 세트를 참조하는 모든 규칙의 검사 기준에 변경이 즉시 반영된다.

#5한 줄 요약

IP 주소 목록을 규칙 밖의 공유 리소스로 분리해, 목록을 한 번만 관리하면 그 목록을 쓰는 모든 규칙이 함께 갱신되는 것

정규식 패턴 세트 관리

여러 정규식 패턴을 하나로 묶어 문자열 검사 규칙에서 재사용하는 리소스

#1문제 상황

기존에는 텍스트 패턴을 검사하는 규칙을 만들 때마다 정규식(문자열의 형식을 표현하는 검색 패턴 표기)을 규칙 안에 직접 작성했다. 예를 들어 이메일 형식 검사, 사용자 ID 형식 검사 등 규칙마다 패턴을 개별 입력해야 하고, 같은 패턴을 여러 규칙에서 쓰려면 복사해서 넣어야 한다. 패턴 하나를 고치려면 그 패턴을 사용하는 모든 규칙을 찾아 수정해야 하는데, 규칙마다 패턴이 조금씩 다르게 변형되어 있으면 검사 결과가 규칙별로 제각각이 되는 것이 명확한 한계다.

#2핵심 질문

같은 정규식 패턴을 한 번만 정의해 두고 여러 규칙이 공유할 수는 없을까?

#3동작 예시

"이메일 허용 패턴"이라는 정규식 패턴 세트(regex pattern set)에 이메일 형식을 검사하는 정규식 하나를 저장하고, 여러 문자열 매치 규칙이 이 세트를 참조하게 만든다. 이후 패턴을 수정하면 세트를 참조하는 모든 규칙이 수정된 패턴으로 검사하므로, 규칙마다 정규식을 반복 작성할 필요가 없다.

#4동작 과정

  1. 패턴 세트 생성이름과 정규식 패턴 목록을 지정해 세트 리소스를 만든다.
  2. 규칙에서 참조문자열 매치 문장의 정규식 패턴 세트 옵션에서 세트를 선택하면, 규칙이 세트 안의 모든 패턴을 검사 기준으로 사용한다.
  3. 패턴 갱신세트의 패턴을 수정하면 세트를 참조하는 모든 규칙에 변경이 즉시 반영된다.

#5한 줄 요약

정규식 패턴을 규칙 밖의 공유 리소스로 만들어 한 번만 정의·수정하고 여러 문자열 검사 규칙이 같은 패턴을 함께 쓰게 하는 것

커스텀 요청 헤더·응답·상태 코드

규칙 동작 시 들어오는 요청에 커스텀 헤더를 삽입하거나, 차단된 요청에 대해 사용자 지정 응답 본문·헤더·상태 코드를 내려보내는 기능.

#1문제 상황

기존에는 WAF 규칙이 요청을 허용하거나 차단할 때 요청 내용을 바꿀 수 없었고, 차단했을 때 내려주는 응답도 표준 상태 코드(주로 403)와 기본 차단 화면으로 고정되어 있었다. 그래서 차단된 사용자에게 왜 차단됐는지 안내 문구를 보여줄 수 없었고, 뒤의 오리진 서버(실제 콘텐츠를 만들어 응답하는 서버)도 "이 요청은 WAF 검사를 통과했다"는 사실을 알 방법이 없어 요청을 검증해야 하는 애플리케이션 로직을 별도로 만들어야 했다.

#2핵심 질문

WAF가 요청을 처리하면서 요청에 정보를 추가하고, 차단 응답의 본문·헤더·상태 코드를 원하는 대로 지정할 수는 없을까?

#3동작 예시

허용 규칙이 매치된 요청에 X-WAF-Test: true라는 커스텀 헤더(직접 이름과 값을 정해 요청에 추가하는 헤더)를 삽입하면, 오리진 서버가 이 헤더를 읽어 "이 요청은 WAF 검사를 통과했다"고 판단할 수 있다. 반대로 차단 규칙에는 429(요청이 너무 많음) 같은 커스텀 상태 코드와 "봇으로 판단되어 차단되었습니다"라는 응답 본문을 지정해, 차단된 클라이언트가 명확한 안내를 받게 한다.

#4동작 과정

  1. 요청에 헤더 삽입규칙의 액션 설정에서 커스텀 헤더 이름과 값을 지정하고, 규칙이 매치된 요청이 오리진으로 전달될 때 그 헤더를 요청에 추가한다.
  2. 차단 응답 구성차단·카운트(계수) 같은 액션에서 사용자 지정 응답 본문, 응답 헤더, HTTP 상태 코드를 지정한다.
  3. 전달과 응답헤더가 삽입된 요청은 오리진 서버에 도달해 처리되고, 차단된 요청을 보낸 클라이언트는 지정된 본문·상태 코드의 응답을 받는다.

#5한 줄 요약

WAF 규칙이 요청을 처리할 때 요청에 커스텀 헤더를 추가하거나 차단 응답의 본문·헤더·상태 코드를 자유롭게 지정해, 보호 기능과 애플리케이션이 서로 정보를 주고받게 하는 것

웹 요청 라벨링: 추가·매치

규칙이 매칭된 웹 요청에 라벨을 붙이고, 이후 규칙이 그 라벨을 조건으로 매칭해 뒤따르는 규칙의 동작을 제어하는 기능.

#1문제 상황

기존에는 각 규칙이 요청을 검사한 결과를 다음 규칙에게 전달할 수단이 없어서, 앞선 규칙의 판정 결과를 뒤따르는 규칙이 조건으로 사용하지 못했다. 예를 들어 봇 규칙이 "이 요청은 봇이다"라고 판정해도, rate-based 규칙(요청 빈도를 세는 규칙)이 그 판정을 조건으로 삼을 수 없어 봇 여부와 요청 횟수를 함께 다루려면 각 규칙이 동일한 검사를 처음부터 다시 수행해야 했다. 검사가 규칙마다 반복되면서 요청을 두 번 이상 분석하게 되고, 규칙 조합이 복잡해지는 것이 명확한 한계다.

#2핵심 질문

앞선 규칙이 내린 판정 결과를 요청에 표시로 남겨, 뒤따르는 규칙이 그 표시를 조건으로 쓸 수는 없을까?

#3동작 예시

관리형 봇 규칙이 봇으로 판정한 요청에 awswaf:managed:aws:bot:bot이라는 라벨(label, 규칙이 요청에 붙이는 분류 표시)을 추가하도록 설정해 둔다. 그다음 rate-based 규칙이 라벨 매치 문장(요청에 특정 라벨이 붙었는지 검사하는 문장)으로 이 라벨을 조건으로 지정하면, "봇으로 분류된 요청만 분당 100회로 제한"처럼 앞선 규칙의 판정 결과를 뒤 규칙이 그대로 재사용할 수 있다.

#4동작 과정

  1. 라벨 추가규칙의 라벨 추가 설정에서 라벨 이름을 지정하고, 규칙이 매치된 요청에 그 라벨을 붙인다.
  2. 라벨 매치뒤따르는 규칙의 라벨 매치 문장에서 라벨 이름(접두사 일치도 허용)을 조건으로 지정한다.
  3. 판정 재사용요청이 web ACL의 규칙들을 우선순위 순서대로 지나가며, 앞선 규칙이 붙인 라벨이 뒤 규칙의 조건으로 평가되어 최종 액션이 결정된다.

#5한 줄 요약

규칙이 매치된 요청에 라벨을 붙이고 뒤따르는 규칙이 그 라벨을 조건으로 삼아, 앞선 규칙의 판정 결과를 이후 규칙에서 재사용하게 하는 것

지능형 위협 완화 (Intelligent Threat Mitigation)08-01

지능형 위협 완화 개요와 옵션 비교

봇·자동화 공격을 막는 지능형 위협 완화 기능(토큰, CAPTCHA/챌린지, Bot Control, ACFP, ATP, Anti-DDoS)의 개요와 옵션별 용도·차이를 비교한 항목.

#1문제 상황

기존에는 웹 애플리케이션이 들어오는 요청 하나하나를 규칙으로 검사했다. IP 주소가 차단 목록에 있는지, URL에 공격 패턴이 들어있는지 같은 조건을 하나씩 비교해서 통과시키거나 막았다. 이 방식은 규칙을 잘 알고 있는 공격자가 쉽게 우회할 수 있었고, 봇이 사람인 척 보내는 요청은 어떤 규칙으로도 걸러낼 수 없었다. 요청의 내용이 아니라 "누가 보냈는지"를 판별할 수단이 없었기 때문이다. 또한 사기성 계정 생성이나 탈취 시도처럼 정상 요청과 구별이 거의 없는 위협은 기존 규칙 기반 검사로는 감지 자체가 불가능했다.

#2핵심 질문

요청의 내용만으로는 판별할 수 없는 봇·사기성 위협을, 어떻게 요청을 보낸 클라이언트 자체를 검증해서 막을 수 있을까?

#3동작 예시

방문자의 브라우저가 처음 요청을 보내면, AWS WAF는 브라우저에 자바스크립트 검증 과제를 내보내고 그것을 해결한 브라우저에만 토큰(암호화된 신원 확인 표시)을 발급한다. 이후 그 브라우저가 보내는 모든 요청에는 토큰이 함께 실린다. AWS WAF는 규칙 검사를 하기 전에 토큰이 유효한지 확인해서, 토큰이 없는 요청이나 토큰 검증에 실패한 요청은 봇으로 간주해 추가 검사를 하거나 차단한다. 이렇게 하면 평범한 방문자는 아무것도 모른 채 계속 이용하고, 검증을 통과하지 못한 자동화 프로그램만 걸러진다.

#4동작 과정

  1. 옵션 선택AWS WAF 콘솔에서 지능형 위협 완화 기능을 고른다. 토큰·CAPTCHA·챌린지 같은 기본 검증 기능과, Bot Control·ACFP·ATP 같은 관리형 규칙 그룹이 제공하는 기능을 조합해서 쓴다.
  2. 클라이언트 검증과 토큰 발급브라우저가 먼저 검증 과제를 해결하고 유효한 토큰을 받으면, 이후 요청마다 토큰이 자동으로 붙는다. AWS WAF는 각 요청에서 토큰의 유효성을 확인한다.
  3. 규칙 실행과 대응토큰 검증 결과를 기준으로 관리형 규칙이 봇 여부, 계정 생성 사기, 계정 탈취 시도를 판정하고, 설정한 액션(차단·카운트·검증 과제 재시도 등)을 적용해 위협을 완화한다.

#5한 줄 요약

요청 내용이 아니라 요청을 보낸 클라이언트를 검증하는 토큰 기반 판별을 공통 기반으로 삼아, 봇과 사기성 위협을 막는 여러 관리형 옵션을 한곳에서 제공하는 것

토큰: 획득·특성·면역 시간

AWS WAF가 클라이언트 검증 결과를 담아 발급하고 이후 요청에 실어 보내는 암호화된 토큰의 획득 방식, 특성, 만료·면역 시간 설정을 다루는 항목.

#1문제 상황

기존에는 클라이언트를 검증하려면 IP 주소나 User-Agent 헤더(요청을 보낸 프로그램의 이름이 담긴 헤더)를 확인했다. 하지만 공격자는 IP를 바꾸거나 헤더를 위조하는 일이 쉬워서, 이런 값은 클라이언트의 신원을 보장해 주지 못했다. 게다가 NAT(여러 기기가 하나의 공인 IP를 공유하는 환경)처럼 정상 사용자 여러 명이 같은 IP를 쓰는 경우에는 IP만으로 사용자를 구별할 수 없었다. 요청마다 매번 검증 과제를 내는 방법도 있었지만, 정상 사용자가 페이지를 열 때마다 검증을 반복해야 해서 사용성이 크게 떨어졌다.

#2핵심 질문

브라우저가 검증을 한 번 통과했다는 사실을 어떻게 하면 다음 요청에서도 반복 검증 없이 신뢰할 수 있는 방식으로 증명할 수 있을까?

#3동작 예시

브라우저가 웹사이트에 처음 접속하면 AWS WAF는 자바스크립트 과제를 내보내고, 브라우저가 이를 해결하면 AWS WAF가 그 브라우저 고유의 토큰(암호화된 자격 증명 표시)을 하나 만들어 돌려준다. 이후 브라우저가 보내는 모든 요청에는 이 토큰이 함께 실린다. AWS WAF는 토큰의 서명과 유효 기간을 확인해서 그 요청이 이전에 검증을 통과한 클라이언트에서 온 것임을 판단한다. 사용자는 두 번째 접속부터는 검증 과정을 거치지 않는다.

#4동작 과정

  1. 토큰 획득브라우저가 검증 과제를 해결하거나, 애플리케이션이 통합 SDK를 통해 요청하면 AWS WAF가 암호화된 토큰을 생성해 클라이언트에 저장한다.
  2. 요청에 토큰 포함이후 브라우저 또는 SDK는 모든 요청에 토큰을 자동으로 붙여 보내고, AWS WAF는 각 요청의 토큰 서명과 유효 기간을 검증한다.
  3. 면역 시간 적용토큰이 유효한 것으로 확인된 클라이언트는 면역 시간(immunity time) 동안에는 추가 검증 없이 통과한다. 면역 시간이 지나면 다시 검증을 요구할 수 있다.

#5한 줄 요약

검증을 통과한 클라이언트에게 암호화된 토큰을 발급하고, 면역 시간 동안 그 토큰을 신뢰해서 정상 사용자의 반복 검증 없이 클라이언트 신원을 판별하는 것

CAPTCHA와 챌린지 액션

사람임을 확인하는 CAPTCHA 퍼즐과 무중단 클라이언트 검증 챌린지, 그리고 이에 대응하는 규칙 액션의 동작을 다루는 항목.

#1문제 상황

기존에는 의심스러운 요청을 조건 기반 규칙으로 검사해서, 조건에 걸리면 바로 차단하거나 통과시켰다. 하지만 봇이 보내는 요청은 정상 요청과 형태가 같을 때가 많아서 "차단할지 통과시킬지" 이분법으로는 잘못 차단하거나 놓치는 경우가 생겼다. 게다가 정상 사용자의 요청을 토큰으로 검증한다 하더라도, 토큰이 아직 없는 첫 요청이나 토큰 검증에 실패한 요청을 어떻게 처리해야 할지가 남아 있었다. 이런 경계에 있는 요청을 단순 차단하면 정상 사용자를 내쫓고, 그냥 통과시키면 봇을 들여보내는 딜레마였다.

#2핵심 질문

차단도 통과도 확실하지 않은 애매한 요청에 대해, 정상 사용자는 지나가게 하면서 봇은 걸러낼 수 있는 중간 단계를 만들 수 없을까?

#3동작 예시

규칙이 CAPTCHA 액션을 발동하면 AWS WAF는 브라우저에 퍼즐 페이지를 보여주고, 사용자가 퍼즐을 풀면 그 브라우저에 유효한 토큰이 발급되어 이후 요청은 통과한다. 챌린지 액션은 퍼즐 대신 자바스크립트 검증 과제를 조용히 실행해서, 사람이 아무것도 하지 않아도 통과시킨다. 자동화 프로그램은 이 과제를 정상적으로 실행하지 못하므로 토큰을 얻지 못해 계속 검증 단계에 머문다.

#4동작 과정

  1. 액션 발동요청이 CAPTCHA 또는 챌린지 액션이 붙은 규칙에 걸리면, AWS WAF는 요청을 차단하거나 통과시키지 않고 검증 페이지로 응답한다.
  2. 검증 수행사용자가 CAPTCHA 퍼즐을 풀거나, 브라우저가 자바스크립트 챌린지를 무인으로 해결한다.
  3. 토큰 발급과 통과검증이 성공하면 브라우저에 토큰이 발급되고, 이후 해당 클라이언트의 요청은 규칙 검사를 통과해 애플리케이션에 도달한다.

#5한 줄 요약

판별이 애매한 요청에 대해 사람은 풀 수 있고 자동화 프로그램은 풀 수 없는 검증 과제를 중간에 끼워 넣어, 통과한 클라이언트에 토큰을 주고 통과하지 못한 요청을 제한하는 것

Bot Control 관리형 규칙

알려진 봇과 봇 트래픽 패턴을 신호로 식별해 허용·차단·계수·챌린지하는 AWS 관리형 Bot Control 규칙 그룹.

#1문제 상황

기존에는 봇을 막으려면 IP 차단 목록이나 User-Agent 헤더(요청을 보낸 프로그램 이름이 담긴 헤더) 검사 같은 수단을 썼다. 하지만 봇은 IP를 바꾸고 헤더를 정상 브라우저의 것으로 위조하는 일이 흔해서 이런 검사는 쉽게 우회됐다. 반대로, 검색 엔진 크롤러처럼 허용해야 하는 봇을 구별하지 못하면 정상적인 봇까지 차단하는 부작용이 생겼다. 봇인지 아닌지, 어떤 봇인지 판별하는 것이 규칙 기반 검사로는 불가능했다.

#2핵심 질문

헤더와 IP를 위조하는 봇을, 정상 사용자와 허용할 봇은 살려두면서 골라낼 수 있는 방법은 무엇일까?

#3동작 예시

Bot Control을 웹 ACL(요청 검사 규칙 묶음)에 추가하면, AWS WAF는 모든 요청에 대해 토큰 검증(클라이언트가 이전 검증을 통과했는지 확인)과 행동 분석을 결합해 그 요청이 봇인지 판정한다. 검색 엔진 크롤러처럼 AWS가 신원을 확인한 봇은 "확인된 봇"으로 분류되어 허용 정책을 적용할 수 있고, 신원이 불분명한 자동화 프로그램은 차단하거나 추가 검증으로 보낼 수 있다.

#4동작 과정

  1. 신원 판별각 요청에 대해 토큰 유무와 유효성, 클라이언트 행동 패턴을 분석해서 사람·확인된 봇·미확인 봇으로 분류하고 라벨을 붙인다.
  2. 분류별 규칙 적용관리형 규칙이 분류 결과에 따라 기본 액션(차단·카운트 등)을 적용하고, 사용자는 권장 조치를 보고 직접 규칙을 조정할 수 있다.
  3. 대응과 추적봇으로 판정된 요청은 차단되거나 검증 단계로 보내지고, 허용할 봇은 통과한다. 모든 판정은 로그와 지표로 남아 후속 조정에 쓰인다.

#5한 줄 요약

토큰 검증과 행동 분석으로 요청이 사람인지 봇인지, 어떤 봇인지를 판별해 봇에는 차단·검증을 적용하고 확인된 봇은 허용하는 관리형 규칙 그룹

계정 생성 사기 방지(ACFP)

가짜 계정 생성과 사기성 가입을 막기 위해 토큰, 봇 점수, 신호, 응답 검사 등을 조합해 판단하는 ACFP 관리형 규칙 그룹.

#1문제 상황

기존에는 계정 생성 요청을 검증할 때 같은 IP에서 너무 많이 가입하는지(속도 제한)나 특정 문자열 포함 여부 같은 단순 규칙을 확인했다. 하지만 공격자는 IP를 바꿔가며 가입 요청을 흩뿌리기 때문에 속도 제한을 쉽게 피했다. 또 사기성 계정 생성은 요청 형태가 정상 가입과 거의 같아서, 요청 내용만 보고 판별하는 것은 불가능했다. 그 결과 스팸 발송, 쿠폰 남용, 대량 계정 확보 같은 피해가 규칙 검사로는 막히지 않았다.

#2핵심 질문

정상 가입 요청과 형태가 같은 사기성 계정 생성을, 어떻게 클라이언트 검증과 응답 검사로 판별할 수 있을까?

#3동작 예시

ACFP를 웹 ACL에 추가하면 가입 페이지로 들어오는 모든 요청의 토큰 유효성을 먼저 확인한다. 토큰이 없는 요청이나 검증에 실패한 요청은 가입 처리를 시작하기 전에 차단하거나 추가 검증으로 보낸다. 그리고 실제로 가입 요청이 이뤄지면 응답까지 검사해서, 가입 성공 여부에 따라 위험 점수를 매기고 의심스러운 계정 생성을 차단한다.

#4동작 과정

  1. 사전 검증가입 요청이 오면 토큰 유효성을 확인하고, 검증되지 않은 클라이언트의 요청을 차단하거나 CAPTCHA·챌린지로 보낸다.
  2. 요청 검사와 라벨링가입 요청의 경로(페이지 주소)를 확인해 검증 대상을 정하고, 요청에 위험 라벨을 붙인다.
  3. 응답 검사와 차단서버가 내려준 가입 응답(성공·실패)을 검사해 공격 성공 여부까지 파악하고, 사기성 가입으로 판정된 요청을 차단한다.

계정 생성 요청에 대해 토큰 사전 검증과 가입 응답 검사를 결합해서, 정상 가입과 형태가 같은 사기성 계정 생성을 판별하고 차단하는 관리형 규칙 그룹

계정 탈취 방지(ATP)

탈취된 자격 증명과 자동화된 로그인 시도를 탐지해 계정 탈취를 막는 ATP 관리형 규칙 그룹.

#1문제 상황

기존에는 로그인 요청을 막으려면 실패 횟수 제한이나 IP 차단 같은 단순 규칙을 사용했다. 하지만 공격자는 IP를 바꿔가며 대량의 로그인 시도(크리덴셜 스터핑: 훔친 계정 정보를 대량으로 대입하는 공격)를 수행해서 속도 제한을 피했다. 거꾸로, 실제 사용자의 로그인 실패가 누적되면 정상 사용자까지 IP 차단에 걸리는 문제도 있었다. 로그인 요청 하나하나는 정상과 구별이 안 되므로 요청 내용만으로 탈취 시도를 알아채는 것이 불가능했다.

#2핵심 질문

정상 로그인과 형태가 같은 대량 계정 탈취 시도를, 어떻게 클라이언트 검증과 로그인 응답 검사로 판별할 수 있을까?

#3동작 예시

ATP를 웹 ACL에 추가하면 로그인 페이지로 들어오는 요청의 토큰 유효성을 먼저 확인한다. 토큰이 없거나 유효하지 않은 클라이언트의 로그인 시도는 차단되거나 추가 검증으로 보내진다. 그리고 로그인 요청의 응답을 검사해서, 로그인 성공 여부를 위협 점수에 반영하고 연속된 실패가 의심스러울 때 차단한다.

#4동작 과정

  1. 사전 검증로그인 요청의 토큰 유효성을 확인하고, 검증되지 않은 클라이언트의 요청은 차단하거나 CAPTCHA·챌린지로 보낸다.
  2. 로그인 요청 검사로그인 경로를 확인해 검사 대상을 정하고, 요청에서 위협 신호를 찾아 라벨을 붙인다.
  3. 응답 검사와 차단로그인 응답(성공·실패)을 검사해 탈취 시도의 성공 여부까지 파악하고, 위험 점수에 따라 공격을 차단하거나 로그로 남긴다.

DDoS 방지: anti-DDoS 규칙 그룹

대규모 트래픽 공격을 지능적으로 완화하는 AWS WAF의 DDoS 방지용 Anti-DDoS 관리형 규칙 그룹을 다루는 항목.

#1문제 상황

기존에는 대량 트래픽으로 서비스를 마비시키는 DDoS 공격을 막으려고 AWS Shield 같은 네트워크 계층 방어에 주로 의존했다. 그런데 이 방어는 거대한 트래픽 자체는 줄여주지만, 정상 요청처럼 보이면서 헤더·쿠키·경로를 조작한 애플리케이션 계층(웹 요청 내용을 다루는 계층) 공격은 구분하지 못한다. 또 관리형 봇 방어 규칙을 웹 ACL(요청 평가 규칙을 묶어 보호 대상을 지키는 단위)에 아무리 조합해도, 공격 트래픽이 커지기 전에 유입 초기부터 지능적으로 완화하는 단계가 없어서 규칙이 공격을 감당하는 사이 서비스 부하가 치솟는 문제가 남았다.

#2핵심 질문

애플리케이션 계층 DDoS 공격이 밀려올 때 서비스를 죽이지 않으면서 공격 요청만 골라 유입량부터 줄이려면 어떻게 해야 할까?

#3동작 예시

Anti-DDoS 관리형 규칙 그룹(여러 방어 규칙을 AWS가 묶어 관리하는 것)을 웹 ACL에 추가하면, 규칙이 들어오는 요청을 토큰(클라이언트 검증 결과를 담은 암호화된 표시)과 신호 점수로 판정해 공격자로 보이는 요청에는 차단·챌린지를 적용하고 정상 요청은 통과시킨다. 즉 "공격으로 보이는 요청의 유입량 자체를 줄이는" 방어가 규칙 한 덩어리로 동작한다.

#4동작 과정

  1. 규칙 그룹 추가웹 ACL에 Anti-DDoS 관리형 규칙 그룹을 추가해 방어를 켠다. 규칙 그룹은 AWS가 관리하는 여러 규칙의 묶음이다.
  2. 트래픽 검사와 판정들어오는 각 요청에 대해 토큰 보유 여부, 요청 패턴, 위협 신호 점수를 조합해 공격 여부를 판정한다.
  3. 완화 조치공격으로 판정된 요청은 차단하거나 챌린지(추가 검증 요구)로 돌려 유입을 줄이고, 정상 요청은 그대로 통과시킨다.

애플리케이션 계층 DDoS 공격을 관리형 규칙으로 조기에 감지해 공격 트래픽의 유입량 자체를 줄이는 방어 그룹

브라우저와 모바일 앱에서 토큰을 받아 지능형 위협 완화 기능과 연동하게 하는 JavaScript 및 모바일 SDK 통합을 다루는 항목.

#1문제 상황

기존에는 지능형 위협 완화(토큰, CAPTCHA, 챌린지)를 서버 쪽 규칙만으로 구성했다. 웹 ACL이 토큰을 요구해도 정작 브라우저와 모바일 앱 쪽에서 토큰을 받아 요청에 실어 보낼 방법이 없어서, 정상 사용자까지 차단되거나 개발자가 토큰 API를 직접 호출하는 코드를 각자 구현해야 했다. 연동 방식이 제각각이라 통합 비용이 크고, 오류가 나면 토큰 없는 요청이 대량으로 쌓여 앱 전체가 검증 단계에서 막히는 문제가 생겼다.

#2핵심 질문

브라우저와 모바일 앱이 토큰·CAPTCHA·챌린지 기능을 일관된 방식으로 사용하게 하려면 어떻게 연동해야 할까?

#3동작 예시

AWS WAF가 제공하는 JavaScript 통합 스크립트나 모바일 SDK(기능을 미리 구현해 둔 개발용 라이브러리)를 앱에 추가하면, 클라이언트가 자동으로 토큰을 받아 이후 모든 요청에 실어 보낸다. 페이지에 스크립트 한 줄을 넣으면 로드 시점에 토큰을 받아와 요청 헤더에 담아주는 식으로 동작한다.

#4동작 과정

  1. SDK 통합웹 페이지에는 JavaScript 스크립트를, 모바일 앱에는 토큰 획득용 SDK를 추가한다.
  2. 토큰 획득클라이언트가 AWS WAF 토큰 엔드포인트(토큰을 발급하는 서버 주소)에 요청해 암호화된 토큰을 받고, 이후 요청에 항상 담아 보낸다.
  3. 요청 검증웹 ACL 규칙이 토큰의 유효성을 검사해 유효하면 통과시키고, 없거나 무효하면 CAPTCHA나 챌린지로 연결한다.

클라이언트가 토큰을 표준적인 방식으로 획득·전송하게 만들어 서버의 위협 완화 규칙과 연동시키는 통합 라이브러리

#2핵심 질문

#4동작 과정

  1. 로그 목적지 설정콘솔에서 로그를 보낼 CloudWatch Logs 로그 그룹, S3 버킷, Firehose 중 하나를 지정하고 로깅을 활성화한다.

#1문제 상황

기존에는 규칙을 만들자마자 실서비스의 web ACL(웹 트래픽 보호 설정 묶음)에 그대로 적용했다. 그 결과 오탐(정상 요청을 공격으로 잘못 판단해 차단)이 발생해 실제 사용자의 접속이 막히는 사고가 잦았다. 또 수동으로 공격 요청을 흉내 내서 규칙을 확인하는 방식은 실제 트래픽의 분포와 달라서, 정작 운영 중인 트래픽에서 규칙이 어떻게 작동할지는 알 수 없었다. 규칙을 실전에 걸기 전에 실제 요청으로 검증할 절차가 없다는 것이 가장 큰 문제였다.

#2핵심 질문

실제 트래픽을 방해하지 않으면서, 새 규칙이 정상 요청과 공격을 올바르게 가르는지 확인하고 조정할 방법은 무엇일까?

#3동작 예시

새 규칙을 처음부터 차단(Block)으로 넣지 않고, 계수(Count) 동작으로 먼저 넣는다. 계수 동작은 요청을 막지 않고 규칙에 걸리는 요청 수만 집계한다. 이 상태로 실제 트래픽을 흘려보내며 며칠간 지표를 보고, 정상 요청이 규칙에 걸리는지(오탐) 확인한 뒤에만 차단으로 바꾼다. 이렇게 하면 실패해도 요청이 막히는 일 없이 규칙의 품질을 실전 트래픽으로 검증할 수 있다.

#4동작 과정

  1. 테스트 준비규칙을 계수(Count) 동작으로 web ACL에 넣고, 요청 샘플을 수집하도록 설정한다. 실제 요청 패턴 그대로 검증하기 위한 준비다.
  2. 모니터링과 조정CloudWatch 지표(규칙별로 걸린 요청 수)와 샘플 요청을 보며, 차단돼선 안 될 요청이 계수되는지 확인하고 규칙 조건을 다듬는다.
  3. 실전 전환오탐이 없다고 판단되면 규칙을 차단/허용 동작으로 바꾸고, 우선 일부 트래픽에 적용한 뒤 전체로 확대해 배포를 마친다.

#4동작 과정

  1. 지표 수집CloudWatch가 매 분마다 web ACL과 규칙별 요청 수(허용·차단·계수)를 지표로 기록하고 대시보드에 표시한다.
  2. 동작 분석샘플링된 요청의 세부 정보(어느 규칙에 걸렸고 왜 그런 판정인지)를 확인해 규칙이 의도대로 작동하는지 판단한다.
  3. 변경 감사AWS CloudTrail이 관리자가 내린 API 호출(설정 변경 등)을 이벤트로 저장해, 언제 누가 무엇을 바꿨는지 감사 로그로 확인한다.

#2핵심 질문

WAF 운영이 규정을 지키면서 장애와 인프라 위협에도 견딜 수 있다는 것을 어떻게 보장할까?

#3동작 예시

규정 준수·복원력·인프라 보안이라는 세 갈래로 점검한다. 규정 준수는 AWS Artifact에서 WAF 관련 규정 준수 보고서를 받아 요구 사항 충족을 확인하고, 복원력은 장애 시에도 보호가 유지되도록 설계를 점검하며, 인프라 보안은 전송 중·저장 중 암호화와 접근 통제를 적용하는 방식이다.

#4동작 과정

  1. 규정 준수 확인AWS Artifact의 규정 준수 보고서와 인증 목록에서 WAF가 해당 규정 요구 사항을 충족하는지 확인한다.
  2. 복원력 점검리전 장애나 재해 상황을 가정해, web ACL과 규칙이 보조 리전·백업 설정에서도 유지되는지 설계를 점검한다.
  3. 인프라 보안 적용데이터 암호화(전송 중 TLS, 저장 중 암호화)와 인프라 접근 통제를 적용해 보안 기준을 맞춘다.

WAF Classic에서 마이그레이션

기존 AWS WAF Classic의 규칙·웹 ACL을 새 AWS WAF로 옮기는 절차와 주의사항.

#1문제 상황

기존 AWS WAF Classic은 조건(Condition)·규칙(Rule)·web ACL 순서로 구성되는 옛 구조라서, 관리형 규칙 그룹, 레이블, 지능형 위협 완화 같은 새 WAF의 기능을 쓸 수 없었고 유지보수도 중단될 예정이었다. 그런데 Classic에 이미 구성된 차단 규칙을 새 WAF로 옮기는 과정에서 규칙 구조가 달라 판정 결과가 바뀌면, 서비스 장애나 보안 허점으로 이어질 수 있다는 것이 문제였다.

#2핵심 질문

기존 Classic 구성의 규칙과 web ACL을 새 WAF로 옮기면서도 차단 동작이 바뀌지 않게 하려면 어떻게 해야 할까?

#3동작 예시

AWS가 제공하는 마이그레이션 도구가 Classic web ACL의 조건과 규칙을 새 WAF의 규칙·규칙 그룹으로 자동 변환해 준다. 변환 결과를 새 web ACL에 넣어 차단 동작이 기존과 같은지 검증한 뒤, 트래픽을 하루에 한 번 새 web ACL로 전환하는 방식으로 진행한다.

#4동작 과정

  1. 사전 점검마이그레이션 지원 여부와 전환 시 영향(IP 주소, 레이블 등)을 확인하고 변환 계획을 세운다.
  2. 자동 변환과 보완도구가 Classic web ACL을 새 WAF 구성으로 변환하고, 자동으로 옮겨지지 않는 부분을 수동으로 보완한다.
  3. 트래픽 전환검증을 마친 뒤 보호 대상 리소스의 연결을 Classic에서 새 web ACL로 한 번에 바꿔(스위치오버) 무중단으로 전환을 완료한다.

#2핵심 질문

  2. 생성 시 검사자원을 생성할 때 WAF가 한도 초과 여부를 검사하고, 초과하면 요청을 거부한다.
  3. 증가 요청한도가 부족하면 Service Quotas에 증가를 요청해 승인받은 뒤 자원을 계속 생성한다.

AWS WAF API를 HTTPS 요청이나 AWS SDK로 호출해 보호 구성을 프로그래밍 방식으로 관리하는 방법.

#2핵심 질문

웹 ACL 생성부터 로그 확인까지의 모든 WAF 관리를 사람의 클릭 없이 코드로 수행할 수는 없을까?

  3. 응답 확인과 반복코드가 반환된 결과를 받아 성공 여부를 확인하고, 같은 코드를 CI/CD(코드 배포 자동화 파이프라인)에 넣어 환경마다 반복 실행한다.

AWS Shield 개요: Standard와 Advanced

AWS Shield는 AWS 리소스를 DDoS 공격으로부터 지키는 관리형 서비스로, 기본 제공되며 추가 요금이 없는 Standard와 유료 구독으로 고급 탐지·완화·비용 보호와 SRT 지원을 제공하는 Advanced로 나뉜다.

#1문제 상황

기존에는 공격 트래픽을 막기 위해 WAF의 규칙으로 요청을 필터링했다. 그런데 WAF는 들어온 요청 하나하나를 검사하는 방식이라, 네트워크·전송 계층에서 벌어지는 대규모 DDoS(분산 서비스 거부) 공격에는 대응할 수 없다. 수백 Gbps의 트래픽이 몰려오면 WAF가 검사할 여유조차 없어지고, 그보다 먼저 네트워크 대역폭과 서버 자체가 고갈되어 서비스 전체가 마비된다. 요청을 검사하는 계층이 아니라 그 앞 단계에서 막아야 하는 공격인 것이다.

#2핵심 질문

웹 ACL에 도달하기도 전에 인프라 전체를 마비시키는 대규모 DDoS 공격은 누가, 어떻게 막는가?

#3동작 예시

AWS는 전 세계 네트워크 경계에서 들어오는 트래픽을 항상 감시하고 있으며, 평소 패턴과 다른 대량 트래픽이 감지되면 그것이 대상 리소스에 도달하기 전에 탐지해 걸러낸다. 이 보호는 AWS Shield라는 서비스가 담당하는데, Standard는 아무 설정 없이 모든 AWS 고객에게 기본으로 무료 제공되고, Advanced는 유료로 더 정밀한 탐지·완화(공격 차단 처리)와 비용 보호를 추가로 제공한다.

#4동작 과정

  1. 트래픽 감시AWS 네트워크 경계가 모든 인바운드 트래픽을 상시 분석해 평소와 다른 급증 징후를 감지한다.
  2. 완화 적용공격으로 판단되면 대상 리소스에 도달하기 전 지점에서 공격 트래픽을 걸러내며, Advanced는 애플리케이션 계층 공격까지 자동 완화 규칙을 적용한다.
  3. 보고와 보호 유지감지·완화 결과를 보고하고, 공격이 끝날 때까지 보호를 계속 유지한다.

#5한 줄 요약

AWS 네트워크 경계에서 DDoS 공격을 자동으로 탐지·완화해 웹 애플리케이션이 공격 중에도 계속 동작하게 하는 것

AWS Firewall Manager 개요와 WAF 정책

AWS Firewall Manager는 AWS Organizations 전체 계정에 WAF 보호와 같은 방화벽 규칙을 한곳에서 중앙 관리하고 일괄 적용·감사하는 보안 관리 서비스다.

#1문제 상황

#2핵심 질문

여러 계정에 흩어진 WAF 웹 ACL과 보안 규칙을 한곳에서 정의해 모든 리소스에 빠짐없이 적용할 수는 없을까?

#3동작 예시

Firewall Manager에 "조직의 모든 계정에 있는 Application Load Balancer와 CloudFront에는 이 웹 ACL을 붙인다"는 정책 하나를 만들면, 현재 있는 리소스는 물론 이후 새로 생기는 계정과 리소스에도 그 정책이 자동으로 적용된다. 중앙에서 정책 하나를 고치면 조직 전체가 따라 바뀐다.

#4동작 과정

  1. 정책 정의중앙 관리 계정에서 적용 대상 리소스 유형과 적용할 규칙(웹 ACL, Shield Advanced 등)을 담은 정책을 만든다.
  2. 조직 전체 배포Firewall Manager가 AWS Organizations(계정 관리 체계)의 모든 계정을 조사해 정책에 어긋난 리소스를 찾아내고 정책 내용을 자동 적용한다.
  3. 지속 점검이후 새 계정·새 리소스가 생겨도 정책을 기준으로 계속 점검·보정해 비준수 상태가 남지 않게 유지한다.

#5한 줄 요약
