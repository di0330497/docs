1CloudWatch가 무엇을 하는 물건인가메트릭·로그·경보라는 세 축과 기능 지도를 먼저 잡아야 이후 모든 장이 '어디에 속한 이야기'인지 알 수 있다.32메트릭의 구조메트릭이 어떻게 식별되고 어떤 단위로 저장·집계되는지를 모르면 그래프도 경보도 해석할 수 없다. CloudWatch의 모든 수치 기능의 전제다.53내 데이터를 CloudWatch 메트릭으로 넣고 빼기AWS가 자동으로 주는 메트릭 다음 단계는 내가 만드는 메트릭이다. 게시 경로를 알아야 뒤의 조회·경보를 내 데이터에 적용할 수 있다.44메트릭 찾기·계산하기·질의하기저장된 메트릭을 꺼내 보는 방법이 있어야 그래프와 경보가 의미를 갖는다. 수식·검색·SQL 질의는 대시보드와 경보 양쪽에서 재사용된다.55보이게 만들기: 그래프와 대시보드조회 결과를 사람이 계속 보는 화면으로 고정하는 단계. 위젯 구조를 알아야 경보·로그 쿼리도 같은 화면에 모을 수 있다.56경보: 값이 넘으면 무슨 일이 일어나게 하기메트릭과 쿼리를 알아야 임계값을 정할 수 있고, 경보를 알아야 뒤의 자동 대응·조사 기능이 이해된다. 1CloudWatch가 무엇을 하는 물건인가01-01

CloudWatch가 푸는 문제와 관측 데이터의 세 축

AWS 위의 시스템이 지금 정상인지 알기 위해 숫자(메트릭)·텍스트(로그)·요청 흐름(트레이스)이라는 세 종류의 관측 데이터를 한곳에 모아 보고 알림까지 걸어주는 서비스다.

1상대의 출발점 확인

AWS 위에서 서버나 서비스를 운영할 때, 각 서비스마다 자신의 상태 정보를 따로 모아야 했다. EC2에서는 CPU 사용률을 확인하고, RDS에서는 데이터베이스 성능을 보고, Lambda에서는 함수 실행 로그를 따로 봤다. 이런 식으로 관측 데이터가 여기저기 흩어져 있으면, 전체 시스템이 정상인지 빠르게 파악할 수 없고, 문제가 어디서 나왔는지 추적하기도 어렵다.

2질문 제기

AWS 위의 수많은 서비스들이 지금 정상으로 작동하고 있는지, 그리고 문제가 있다면 어디서 발생했는지를 빠르게 알 수 있는 방법은 무엇인가?

3구조적 핵심 예시

CloudWatch는 메트릭(숫자 데이터, 예: CPU 사용률 80%), 로그(텍스트 기록, 예: "요청 처리 완료"), 트레이스(요청이 여러 서비스를 거치는 흐름, 예: 사용자 요청 → 웹서버 → 데이터베이스 → 응답)라는 세 종류의 관측 데이터를 AWS의 모든 서비스에서 자동으로 수집하여 한 곳에 모아둔다. 덕분에 개발자는 여러 곳을 돌아다니지 않아도 CloudWatch 콘솔 하나에서 전체 시스템의 건강 상태를 확인할 수 있다.

4단계별 동작 과정

  1. 데이터 수집각 AWS 서비스(EC2, RDS, Lambda, ECS 등)는 자동으로 자신의 메트릭과 로그를 CloudWatch로 전송한다.
  2. 데이터 통합CloudWatch는 이 모든 데이터를 타임스탬프(시간 기록)와 함께 저장하여 순시간 상태를 기록한다.
  3. 대시보드와 알림개발자는 대시보드에서 한눈에 전체 상태를 보고, 경보(알림 규칙)를 설정하여 문제 발생 시 즉시 통지받을 수 있다.

CloudWatch 기능 지도: 어떤 기능이 어떤 질문에 답하는가

메트릭·경보·대시보드·Logs·Logs Insights·Synthetics·RUM·Application Signals 등 CloudWatch의 각 기능이 "무엇이 이상한가/왜 그런가/사용자는 어떤가" 중 어느 질문에 대응하는지 한 장으로 정리한 지도다.

1상대의 출발점 확인

시스템에 문제가 생겼을 때, "지금 뭐가 이상한가?"를 파악하려면 메트릭(숫자)을 봐야 하고, "왜 그런가?"를 알려면 로그(텍스트)를 뒤져야 하고, "사용자는 어떤 경험을 했나?"를 알려면 또 다른 도구를 써야 했다. 각 질문에 맞는 도구를 찾아가며 사용해야 하는 번거로움이 있었다.

2질문 제기

발생한 문제의 "뭐가 이상한가/왜 그런가/사용자는 어떤가" 중 어느 것인지에 따라 CloudWatch의 어떤 기능을 사용해야 하는가?

3구조적 핵심 예시

웹 서비스의 응답 시간이 갑자기 느려졌다면, 먼저 메트릭(Metrics)으로 CPU나 메모리 사용률이 치솟았는지 확인하고, 경보(Alarms)가 울렸는지 본 뒤, 로그(Logs)를 보고 에러 메시지가 있는지 찾고, Logs Insights로 느린 쿼리를 분석하고, 마지막으로 RUM(Real User Monitoring)으로 실제 사용자들이 얼마나 느린 응답을 받았는지 확인한다.

4단계별 동작 과정

  1. "뭐가 이상한가?" 질문에 대답Metrics(메트릭)과 Alarms(경보)는 수치 데이터를 시간 순서로 그래프로 그려서 비정상 상태를 빠르게 인지하게 한다.
  2. "왜 그런가?" 질문에 대답Logs(로그)와 Logs Insights(로그 분석)는 시간대별 텍스트 기록을 수집하고 검색하여 근본 원인을 추적할 수 있게 한다.
  3. "사용자는 어떤가?" 질문에 대답RUM(실제 사용자 모니터링), Application Signals(애플리케이션 신호), Synthetics(합성 테스트)는 실제 사용자 경험이나 프로액티브한 장애 감지를 제공한다.

시작 준비: 리전, IAM 권한, 콘솔과 CLI/SDK, 자동 대시보드로 첫 확인

CloudWatch는 리전 단위로 데이터가 쌓이므로 올바른 리전 선택, 필요한 IAM 권한 부여, 콘솔·AWS CLI·SDK 접근 방법을 갖춘 뒤 자동 대시보드로 첫 지표를 확인하는 것이 출발점이다.

1상대의 출발점 확인

CloudWatch를 처음 사용하려고 하면, 어디서부터 시작해야 할지 명확하지 않다. 계정은 만들었지만, 어느 리전에서 데이터를 봐야 하는지, 권한은 어떻게 주는지, 데이터가 언제부터 보일지 알 수 없다. 특히 다중 리전 환경에서는 리전을 잘못 선택하면 아무 데이터도 안 보인다.

2질문 제기

CloudWatch를 처음 사용할 때 리전·권한·접근 방법을 어떻게 설정하고, 처음으로 데이터를 확인해야 하는가?

3구조적 핵심 예시

서울 리전(ap-northeast-2)에서 EC2 인스턴스를 운영 중이면, CloudWatch 콘솔도 서울 리전으로 선택해야 해당 EC2의 메트릭(CPU, 네트워크)이 보인다. 리전을 도쿄(ap-northeast-1)로 설정하면 서울의 데이터는 보이지 않는다. 또한 IAM 권한에서 CloudWatch 접근 권한을 부여해야 콘솔에 로그인했을 때 데이터를 볼 수 있다.

4단계별 동작 과정

  1. 올바른 리전 선택 및 권한 확인콘솔 우측 상단에서 리전을 선택하고(예: 서울), IAM에서 해당 계정/역할에 cloudwatch:GetMetricStatistics, logs:DescribeLogStreams 등의 권한이 있는지 확인한다.
  2. 접근 방법 선택웹 콘솔(클릭), AWS CLI(명령어), 또는 SDK(코드)로 접근할 수 있으며, 선호하는 방법을 준비한다.
  3. 자동 대시보드로 첫 확인CloudWatch는 EC2, RDS 등 주요 서비스를 자동으로 인지하고 기본 메트릭 대시보드를 만들어 제공하므로, 콘솔의 "대시보드" 탭을 열면 기본 지표를 즉시 볼 수 있다.

메트릭은 시간 순서로 쌓인 데이터 포인트의 집합이고, 네임스페이스는 그 메트릭들을 서비스별로 구분해 담는 이름 공간이며, 각 데이터 포인트는 값과 타임스탬프를 가진다.

1상대의 출발점 확인

시스템 모니터링에서 데이터를 저장하고 조회할 때, 시간 정보 없이 숫자만 저장하면 어떤 시점의 값인지 알 수 없다. 또한 같은 이름의 메트릭이 여러 개 있을 때(예: 여러 EC2 인스턴스의 CPU) 어느 인스턴스의 CPU 값인지 구분할 수 없다. 데이터 구조가 명확하지 않으면 조회와 분석이 복잡해진다.

2질문 제기

시간 순서로 쌓인 메트릭 데이터를 저장하고, 어느 리소스의 어느 값인지 정확히 식별하려면 어떤 정보 구조가 필요한가?

3구조적 핵심 예시

EC2 인스턴스 "web-server-1"의 CPU 사용률을 기록한다면, CloudWatch는 "메트릭 이름: CPUUtilization, 값: 75%, 타임스탬프: 2026-08-31 14:30:00 UTC, 네임스페이스: AWS/EC2"라는 식으로 저장한다. 타임스탬프가 있으므로 시간 순서를 추적할 수 있고, 네임스페이스는 어떤 종류의 서비스(EC2, RDS 등)인지 알려주며, 각 데이터 포인트(값)는 정확한 시점의 상태를 나타낸다.

4단계별 동작 과정

  1. 메트릭 정의메트릭(Metric)은 시간순 데이터 포인트(Data Point, 값+타임스탬프)의 모음이며, 각 데이터 포인트는 특정 시점의 측정값을 기록한다.
  2. 네임스페이스 분류네임스페이스(Namespace, 이름 공간)는 메트릭을 서비스별로 구분하여 담는 폴더 같은 역할을 한다(예: AWS/EC2, AWS/RDS, AWS/Lambda).
  3. 타임스탬프로 시계열 추적각 데이터 포인트는 타임스탐프(Timestamp, 기록 시간)를 가져서 시간 순서대로 정렬되며, 이를 통해 "지난 1시간 동안의 추이"처럼 시계열 분석이 가능하다.

디멘션: 메트릭의 정체성과 조합 규칙

디멘션은 메트릭에 붙는 이름/값 쌍으로, 같은 이름의 메트릭이라도 디멘션 조합이 다르면 서로 다른 메트릭으로 취급된다.

1상대의 출발점 확인

같은 이름의 메트릭이 여러 개 있을 때(예: 다섯 개의 EC2 인스턴스가 모두 CPUUtilization 메트릭을 보낸다), 어느 인스턴스의 CPU 값인지 구분하는 방법이 필요하다. 메트릭 이름만으로는 부족하고, 인스턴스 ID나 인스턴스 이름 같은 추가 정보가 필요하다.

2질문 제기

같은 이름의 메트릭이 여러 개일 때, 어떤 리소스의 어느 값인지 정확히 구분하려면 어떤 방식을 써야 하는가?

3구조적 핵심 예시

"CPUUtilization"이라는 메트릭 두 개가 있다고 하자. 하나는 인스턴스 ID가 "i-1234567"인 웹서버의 CPU이고, 다른 하나는 "i-7654321"인 데이터베이스 서버의 CPU다. CloudWatch는 각 메트릭에 "InstanceId=i-1234567"이라는 디멘션(Dimension, 이름/값 쌍)을 붙인다. 덕분에 같은 이름의 메트릭이라도 디멘션 조합이 다르면 완전히 다른 메트릭으로 취급된다.

4단계별 동작 과정

  1. 디멘션 정의디멘션(Dimension)은 메트릭에 붙는 이름/값 쌍으로(예: InstanceId/i-1234567, Environment/production), 그 메트릭의 정체를 명시한다.
  2. 조합으로 정체 결정같은 이름의 메트릭이라도 디멘션 조합이 다르면 서로 다른 메트릭이 된다(예: 메트릭 이름은 같지만 InstanceId가 다르면 다른 데이터).
  3. 필터링과 검색 가능대시보드나 쿼리에서 특정 디멘션 값으로 필터링하면 원하는 리소스의 메트릭만 골라 볼 수 있다.

해상도와 기간(period), 보존 기간과 롤업

메트릭은 표준(60초) 또는 고해상도(1초) 단위로 기록되며, 시간이 지나면 더 긴 기간으로 롤업되어 최대 15개월까지 보존된다.

1상대의 출발점 확인

모니터링 데이터를 원래 해상도(1초, 60초 등)로 영원히 보관하면 저장 공간이 무한정 필요하다. 또한 최근 데이터는 세밀한 해상도가 필요하지만, 1년 전 데이터는 대충 시간 단위의 요약만 있어도 충분하다. 해상도와 보존 기간을 효율적으로 관리하는 체계가 필요하다.

2질문 제기

최근의 세밀한 데이터는 유지하면서도 오래된 데이터는 효율적으로 압축하여, 저장 공간과 비용을 줄이려면 어떻게 해야 하는가?

3구조적 핵심 예시

어떤 메트릭이 매분(1분 = 60초 단위, 표준 해상도)으로 기록되다가 7일이 지나면 5분 단위로, 30일이 지나면 1시간 단위로, 최종적으로 15개월까지 저장된다. 이 과정을 "롤업(Rollup)"이라 한다. 덕분에 1분 단위 세밀한 데이터가 저장되는 비용은 1주일로 제한되고, 오래된 데이터는 자동으로 더 큰 시간 단위로 묶여 저장되므로 저장소를 효율적으로 쓸 수 있다.

4단계별 동작 과정

  1. 해상도 선택메트릭을 표준 해상도(60초 단위)로 기록하거나, 더 세밀하게 고해상도(1초 단위)로 기록할 수 있으며, 고해상도일수록 비용이 높다.
  2. 자동 롤업시간이 지나면서 CloudWatch가 자동으로 데이터를 집계하여(예: 1분 데이터 60개를 1시간 평균으로 묶어) 더 큰 단위로 저장한다.
  3. 기간 단위 보존표준 해상도 데이터는 15개월, 고해상도 데이터는 더 짧은 기간(설정에 따라) 보존되며, 그 이상 오래된 데이터는 자동 삭제된다.

통계·단위·백분위수와 집계가 일어나는 방식

통계는 지정한 기간 동안 데이터 포인트를 Sum·Average·Maximum·백분위수 등으로 묶어 계산한 값이며, 단위는 그 값이 무엇을 세는지 알려준다.

1상대의 출발점 확인

1분마다 기록되는 메트릭 데이터가 있다면, 1시간의 데이터는 60개의 개별 값이 쌓인다. 개발자가 "지난 1시간의 최대 CPU 사용률"을 알고 싶을 때, 60개 값을 모두 조회해서 직접 비교하는 것은 비효율적이다. 시간대별로 이미 계산된 요약 정보(평균, 최댓값 등)가 있으면 더 빠르다.

2질문 제기

시간대별로 데이터 포인트를 그룹화하여 평균, 최댓값, 합계 같은 요약 통계를 미리 계산하고 제공하려면 어떻게 하는가?

3구조적 핵심 예시

EC2 인스턴스의 CPU 사용률이 1분마다 기록된다면(75%, 80%, 78%, 85%, ...이라는 식의 개별 값), CloudWatch는 지난 1시간 동안의 이 값들을 자동으로 묶어서 "Average(평균): 79.5%, Maximum(최댓값): 90%, Minimum(최솟값): 70%, Sum(합계): 4770%"처럼 계산해서 저장한다. 대시보드에서는 이 요약된 통계를 그래프로 그리므로, 1시간 동안의 추이를 한눈에 볼 수 있다.

4단계별 동작 과정

  1. 통계 정의통계(Statistic)는 지정한 기간(예: 1시간) 동안의 데이터 포인트들을 Sum(합계), Average(평균), Maximum(최댓값), Minimum(최솟값), 또는 Percentile(백분위수, 예: 99번째 값)로 계산한 결과다.
  2. 집계 기간 설정대시보드나 경보에서 기간(Period)을 정하면(예: 5분), CloudWatch는 그 기간의 모든 데이터를 한데 모아 통계를 계산한다.
  3. 백분위수로 이상치 추출"지난 1시간에 사용자 요청 중 99%는 얼마나 빨리 처리되었는가"처럼 특정 백분위수를 지정하면, 일부 매우 느린 요청(이상치)을 제외한 대부분의 사용자 경험을 파악할 수 있다.

  2. 실시간 전송 시작새로 도착하는 메트릭이 거의 실시간(수초 단위)으로 Firehose로 흘러갑니다.
  3. 외부 저장 또는 처리Firehose가 메트릭을 S3, HTTP 엔드포인트, 또는 외부 모니터링 플랫폼으로 배송합니다.

2질문 제기

3구조적 핵심 예시

CloudWatch 콘솔의 메트릭 탐색 화면에서 먼저 "AWS/EC2"라는 네임스페이스를 선택하고, 그 안에서 "CPUUtilization" 같은 메트릭을 찾은 후, "인스턴스 ID=i-1234567890abcdef0" 같은 차원으로 필터링하면 그 특정 인스턴스의 CPU 메트릭만 표시됩니다. 이 과정을 API로 하려면 ListMetrics 호출로 조건에 맞는 메트릭 목록을 얻은 후, GetMetricData로 값을 조회합니다.

4단계별 동작 과정

  1. 네임스페이스와 차원으로 탐색콘솔에서 계층적으로 서비스(EC2, RDS 등) → 메트릭 → 구체적 대상(인스턴스 ID 등) 순으로 선택해 원하는 메트릭을 찾습니다.
  2. ListMetrics API로 조회프로그래매틱하게 네임스페이스, 메트릭 이름, 차원으로 조건을 지정해 ListMetrics API를 호출해 해당하는 메트릭 목록을 얻습니다.
  3. GetMetricData 또는 GetMetricStatistics API로 값 추출 — 찾은 메트릭에 대해 특정 시간대의 값, 평균, 최댓값 등의 통계를 조회합니다.

메트릭 수식(metric math)과 검색 표현식(SEARCH)

여러 메트릭을 사칙연산·통계 함수로 조합해 새 시계열을 만들고, SEARCH 표현식으로 조건에 맞는 메트릭을 자동으로 한 번에 그리는 기능이다.

1상대의 출발점 확인

원하는 지표를 만들기 위해 여러 메트릭을 조합해야 할 때, 각 메트릭을 따로 조회해서 스프레드시트나 코드에서 수동으로 계산해야 합니다. 또한 새로운 메트릭이 추가되거나 모니터링 대상이 늘어나면, 대시보드의 모든 차트를 수동으로 수정해야 해서 유지보수가 어렵습니다.

2질문 제기

여러 메트릭을 자동으로 계산해 새로운 지표를 만들고, 새 메트릭을 추가하면 자동으로 포함시킬 수 있을까요?

3구조적 핵심 예시

메트릭 수식으로 "m1 / m2 * 100"처럼 두 메트릭을 나누어 백분율을 계산하거나, "AVERAGE(m1, m2, m3)"로 여러 메트릭의 평균을 구할 수 있습니다. SEARCH 표현식으로 "namespace='AWS/EC2' AND metric_name='CPU*'"처럼 패턴을 지정하면, 그 조건에 맞는 모든 메트릭이 자동으로 검색되고 수식에 포함되어 갱신됩니다.

4단계별 동작 과정

  1. 메트릭 수식 정의대시보드 또는 알람 설정 화면에서 사칙연산과 통계 함수(AVERAGE, MAX, MIN, SUM 등)를 사용해 새 지표의 계산 방식을 정의합니다.
  2. SEARCH 표현식으로 동적 메트릭 선택조건을 지정하면 그 조건에 맞는 모든 메트릭이 자동으로 검색되고 수식에 적용됩니다.
  3. 대시보드에 실시간 표시계산된 결과가 그래프로 표시되고, 새 메트릭이 조건에 맞게 추가되면 자동으로 계산에 포함됩니다.

Metrics Insights: SQL로 메트릭 질의하기

SQL 문법으로 대량의 메트릭을 실시간 집계·그룹화·정렬해 조회하는 고성능 질의 엔진이다.

1상대의 출발점 확인

CloudWatch에서 메트릭을 조회할 때 기본 그래프 보기나 GetMetricStatistics API는 제한적인 집계만 제공합니다. 여러 리소스의 메트릭을 복잡하게 비교하거나, 특정 조건으로 필터링하거나, 여러 기준으로 그룹화하려면 데이터를 수동으로 처리해야 하고, 실시간으로 대량의 메트릭을 고성능으로 집계할 수 없습니다.

2질문 제기

500개의 인스턴스 중 CPU 사용률이 80% 이상인 것만 빠르게 찾아서 비교하려면?

3구조적 핵심 예시

Metrics Insights는 SQL 쿼리를 그대로 사용합니다. "SELECT avg(CPUUtilization) FROM SCHEMA("AWS/EC2", {InstanceId}) WHERE avg(CPUUtilization) > 80 GROUP BY InstanceId"처럼 작성하면, CloudWatch의 메트릭 저장소를 실시간으로 스캔해서 조건에 맞는 인스턴스들의 평균값만 뽑아 표로 반환합니다.

4단계별 동작 과정

이상 탐지(anomaly detection): 기대 밴드로 정상 범위 학습하기

과거 패턴을 머신러닝으로 학습해 기대 범위(밴드)를 만들고 거기서 벗어난 값을 이상으로 표시·경보하는 기능이다.

1상대의 출발점 확인

일정한 임계값(threshold) 하나만으로는 정상 범위를 설정할 수 없습니다. CPU 사용률이 시간대·요일·업무량에 따라 달라지면, 80%가 정상일 때도 있고 이상일 때도 있습니다. 임계값을 높게 설정하면 실제 문제를 놓치고, 낮게 설정하면 오경보가 계속 울립니다.

2질문 제기

과거 패턴을 학습해서 해당 시간대의 정상 범위를 자동으로 판단하고 진짜 이상만 감지하려면?

3구조적 핵심 예시

지난 2주의 CPU 데이터를 머신러닝으로 분석하면, 시스템이 "월요일 9~10시는 평균 60% 전후가 정상, 화요일 13~14시는 40% 전후가 정상"이라는 패턴을 학습합니다. 그다음 월요일 9시에 CPU가 90%면 빨강으로 표시되고 경보가 울리고, 화요일 13시에 70%이면 그 시간대의 패턴에 비해 높으니 역시 경보됩니다.

4단계별 동작 과정

  1. 과거 데이터 학습지난 14일(또는 사용자가 설정한 기간)의 메트릭 데이터를 수집해 시간대별·요일별 패턴을 분석합니다.
  2. 기대 밴드(Band) 생성각 시간대의 정상적인 범위(예: 평균 ± 2 표준편차)를 "밴드"로 계산하고, 이를 그래프 위에 띠 모양으로 표시합니다.
  3. 실시간 비교 및 경보새로운 메트릭이 들어오면 그 시간대의 밴드와 비교해 벗어나면 이상으로 표시하고 경보를 발동합니다.

2질문 제기

  2. 상태 변화 감지새로운 상태가 이전 상태와 다르면 변화가 감지된다.
  3. 액션 실행상태 변화가 감지되었을 때만 SNS 알림 전송, EC2 인스턴스 시작/중지, Auto Scaling 동작 같은 설정된 액션이 한 번 실행되고, 같은 상태가 지속되면 추가 액션은 실행되지 않는다.

평가 방식: 기간·평가 기간·M out of N·워밍업·결측 데이터

1상대의 출발점 확인

3구조적 핵심 예시

  2. M out of N 평가평가 기간 내 축적된 N개 포인트 중 M개 이상이 임계값을 넘는지 확인하며, 데이터가 부족한 경우(결측 데이터)는 설정된 정책(무시, 경보로 취급, 정상으로 취급)에 따라 처리된다.

  1. 데이터 보호 정책 정의정규식이나 AWS 사전정의 패턴으로 주민번호, 카드번호 등을 감지해 마스킹할 규칙을 세운다.
  2. 로그 그룹 암호화 설정로그 그룹을 KMS 마스터 키로 암호화하도록 설정해 저장소 수준의 보호를 추가한다.
  3. 저장 및 암호화로그가 들어올 때 민감 데이터는 마스킹되고, 전체 로그는 암호화된 형태로 저장된다.

로그 검색의 두 갈래: 필터 패턴과 Logs Insights

저장된 로그를 찾는 방법은 단순 문자열/JSON 조건으로 걸러내는 필터 패턴과, 쿼리문으로 집계·분석까지 하는 Logs Insights 두 가지다.

1상대의 출발점 확인

CloudWatch Logs에 저장된 로그는 텍스트 덩어리다. 기존에는 특정 로그를 찾으려면 전체 로그를 읽거나 간단한 문자열 검색만 가능했다. 특정 에러 코드를 조건으로 걸러내거나, 여러 필드를 조합해 조회·집계·분석하려면 복잡한 작업이 필요했다.

2질문 제기

저장된 로그에서 단순 검색과 복잡한 분석이 필요한 경우를 각각 어떻게 처리할까?

3구조적 핵심 예시

필터 패턴은 로그 한 줄을 문자열이나 JSON 구조로 조건 검사하는 것이다. 예를 들어 [... error="500" ...] 패턴은 JSON 형태의 로그에서 error 필드가 500인 것만 골라낸다. 반면 Logs Insights는 SQL처럼 쿼리를 짜서 로그 집합 전체를 분석한다. 예를 들어 지난 1시간 동안 5분 간격으로 에러 건수를 세는 복잡한 집계도 한 번의 쿼리로 처리한다.

4단계별 동작 과정

  1. 필터 패턴로그 텍스트나 JSON에 패턴을 적용해 조건에 맞는 로그만 추출한다.
  2. Logs Insights 쿼리fields(필드 추출) → filter(조건 필터) → stats(집계) → sort(정렬) 등의 명령을 파이프로 이어붙여 한 번에 조회·집계·분석을 처리한다.
  3. 결과 반환필터 패턴은 매칭된 로그 목록을, Logs Insights는 집계된 테이블 형태의 결과를 반환한다.

Logs Insights 쿼리 언어와 핵심 명령

fields·filter·stats·sort·limit·parse 같은 명령을 파이프로 이어 붙여 로그를 조회·집계하는 Logs Insights 전용 쿼리 문법이다(SQL·PPL도 선택 가능).

1상대의 출발점 확인

프로그래밍 없이는 로그 분석이 어려웠다. 특정 시간대의 에러를 세거나 특정 필드 값으로 그룹화하려면 로그를 다운받아 Python이나 SQL 같은 별도 도구로 처리해야 했다. CloudWatch 내에서는 단순 검색만 가능했다.

2질문 제기

CloudWatch에 저장된 로그를 SQL처럼 직접 쿼리해서 조회·집계·분석할 수 있을까?

3구조적 핵심 예시

fields timestamp, status | filter status="ERROR" | stats count() by timestamp 라는 쿼리는 timestamp와 status 필드를 뽑고, status가 ERROR인 것만 필터링한 뒤 시간대별로 에러 발생 건수를 센다. SQL의 SELECT → WHERE → GROUP BY와 같은 흐름을 직관적인 명령어로 표현한다.

4단계별 동작 과정

  1. 필드 추출fields 명령으로 필요한 컬럼만 선택해 쿼리할 데이터 크기를 미리 줄인다.
  2. 조건 필터·집계filter로 조건을 걸고, stats·count·avg·sum 같은 함수로 숫자를 계산하며 group by로 카테고리별 분석을 진행한다.
  3. 정렬·제한sort로 결과를 정렬하고 limit으로 행 수를 제한해 최종 결과를 반환한다.

3구조적 핵심 예시

필드 인덱스는 자주 쓰는 필드(예: status, user_id)를 미리 정렬해두는 것으로, 그 필드로 필터링할 때 전체 스캔 대신 인덱스만 읽으면 된다. 패싯은 특정 필드의 값이 각각 몇 개씩 있는지를 보여줘 문제의 범위를 시각적으로 파악하기 쉽게 한다. 예를 들어 status 필드의 패싯을 보면 OK는 1000만 건인데 ERROR는 100만 건이면, ERROR 쪽에 집중할 수 있다.

4단계별 동작 과정

  1. 필드 인덱스status 같은 자주 쓰는 필드를 인덱스로 등록하면, filter status="ERROR" 실행 시 전체 로그 대신 인덱스된 값만 검색해 속도 향상.
  2. 패싯·패턴 분석어떤 필드의 값이 가장 자주 나오는지(패싯) 또는 어떤 로그 패턴이 자주 반복되는지(패턴 분석)를 먼저 확인해 원인 범위를 파악.
  3. 주변 로그특정 로그 한 줄을 선택하면 그 전후 로그를 함께 보여줘 문제의 전후 상황과 문맥을 파악.

로그 이상 탐지와 Live Tail

로그 패턴을 학습해 평소와 다른 로그를 자동으로 짚어주는 이상 탐지와, 들어오는 로그를 실시간으로 흘려보며 보는 Live Tail이다.

1상대의 출발점 확인

문제가 발생해야 쿼리를 짜서 원인을 찾거나, 정해진 경보 규칙에만 의존한다. 이상한 로그 패턴이 들어와도 미리 알 수 없고, 새로운 종류의 문제에는 대응이 어렵다. 또한 실시간 로그 흐름을 보기 위해서는 콘솔에 계속 들어있어야 한다.

2질문 제기

평소 로그 패턴을 자동으로 학습해 예상과 다른 이상 징후를 미리 감지하고, 실시간 로그 흐름을 직관적으로 볼 수 있을까?

3구조적 핵심 예시

매일 오전 9~10시에 에러 로그가 보통 5건 들어온다는 패턴을 기계학습으로 학습하면, 갑자기 50건이 들어오는 날 자동으로 "이상 탐지됨"이라고 알려준다. Live Tail은 지금 이 순간 들어오는 로그를 실시간으로 흘려보면서 모니터링할 수 있게 한다.

4단계별 동작 과정

  1. 패턴 학습지난 2주~4주의 로그를 분석해 시간대·필드별 정상 범위(평균, 표준편차 등)를 기계학습으로 자동 학습.
  2. 이상 탐지새로 들어오는 로그가 학습된 패턴에서 벗어나면(급격한 증가, 새로운 에러 타입 등) 이상으로 판정하고 알림 발송.
  3. Live Tail 보기실시간으로 들어오는 로그를 필터 없이 또는 특정 조건으로만 흘려보며 현재 진행 중인 문제를 실시간 모니터링.

메트릭 필터로 로그를 메트릭으로 바꾸기

로그 그룹에 조건을 걸어 일치하는 로그 발생 횟수나 추출한 값을 CloudWatch 메트릭으로 만들어 경보까지 연결하는 기능이다.

→ 05-01 참조

1상대의 출발점 확인

로그와 메트릭은 분리된 시스템이다. 로그는 로그 그룹에 저장되고, 메트릭은 CloudWatch Agent 같은 별도 수집 장치로 만들어진다. 로그에 담긴 정보(에러 발생 횟수, 처리 시간 등)를 메트릭으로 활용하려면 복잡한 변환 작업이 필요했다.

2질문 제기

로그 그룹에 들어오는 로그 내용을 직접 메트릭으로 바꿔서 경보까지 연결할 수 있을까?

3구조적 핵심 예시

로그 그룹에 "ERROR: database timeout" 같은 로그가 1시간에 10번 들어오면, 메트릭 필터 규칙 "database timeout 포함"을 정의해두면 CloudWatch가 매분마다 해당 패턴의 로그 발생 횟수를 세어 ErrorCount라는 메트릭으로 만들고, 그 메트릭에 경보를 붙여서 10회 이상이면 SNS로 경고를 보낸다.

4단계별 동작 과정

  1. 필터 규칙 정의로그 그룹에 메트릭 필터를 생성하고, 특정 문자열이나 JSON 패턴이 나올 때마다 카운트하거나 특정 필드 값을 추출하도록 설정.
  2. 메트릭 생성필터가 매칭될 때마다 카운트값이나 추출값이 CloudWatch 메트릭에 기록되며(예: ErrorCount 메트릭에 +1), 이 메트릭이 시간대별로 누적.
  3. 경보 연결생성된 메트릭에 경보(Alarm)를 붙여 임계값 초과 시 SNS·Email·Slack·Lambda 등으로 자동 알림.

구독 필터로 로그를 실시간 전달하기

들어오는 로그를 조건에 맞춰 Lambda·Kinesis Data Streams·Firehose 등으로 거의 실시간 스트리밍해 다른 시스템에 넘기는 방법이다.

1상대의 출발점 확인

CloudWatch Logs에 저장된 로그는 CloudWatch 내에서만 조회·분석할 수 있다. 다른 시스템(Splunk, 데이터 웨어하우스, 실시간 처리 엔진)으로 로그를 보내려면 별도 배치 작업이나 SDK 통합이 필요했다. 로그를 다른 곳으로 실시간 전달하기 어렵고, 로그 기반 실시간 처리가 제한된다.

2질문 제기

CloudWatch Logs에 들어오는 로그를 거의 실시간으로 Lambda·Kinesis·S3 등 다른 AWS 서비스로 자동 전달할 수 있을까?

3구조적 핵심 예시

로그 그룹에 구독 필터를 설정해 "ERROR 또는 CRITICAL"을 포함하는 로그만 Lambda 함수로 보내면, Lambda가 그 로그를 받아 Slack에 알림을 보내거나 Kinesis에 넣어서 실시간 분석 엔진으로 흘릴 수 있다. 정상적인 INFO 로그는 필터링되어 Lambda로 가지 않는다.

4단계별 동작 과정

  1. 구독 필터 설정로그 그룹에서 특정 패턴(필터)을 정의해 그 패턴에 맞는 로그를 특정 대상(Lambda, Kinesis Streams, Kinesis Firehose, S3, OpenSearch 등)으로 전달하도록 등록.
  2. 로그 전달새 로그가 들어올 때마다 필터를 실시간 적용해 조건에 맞으면 선택된 대상으로 거의 실시간(보통 밀리초 단위)에 비동기 전송.
  3. 대상 처리받은 쪽에서 로그를 처리(Lambda는 커스텀 로직 실행, Kinesis Streams는 실시간 스트리밍 처리, Firehose는 배치 저장 또는 변환).

2질문 제기

3구조적 핵심 예시

CloudWatch Logs에 쌓인 로그를 S3에 한 번에 옮기면(Export), S3의 저렴한 스토리지에 영구 보관되고 Athena(SQL 쿼리 도구)에서 직접 분석할 수 있다. 또는 OpenSearch로 계속 스트리밍하면 실시간으로 로그를 색인하고 대시보드를 만들 수 있다.

4단계별 동작 과정

  1. 내보내기 요청CloudWatch 콘솔에서 특정 시간 범위의 로그를 S3 경로로 내보낼 것을 지정한다.
  2. 배경 작업 처리CloudWatch가 로그를 읽고 압축하여 S3에 파일 형태로 저장한다.
  3. 외부 도구 연계S3의 로그를 Athena(SQL 쿼리), EMR(대용량 처리), 데이터 웨어하우스에서 바로 읽어 분석한다.

1상대의 출발점 확인

2질문 제기

EC2 서버 내부의 메모리, 디스크, 로그 같은 정보를 CloudWatch에서 볼 수 있으려면?

3구조적 핵심 예시

CloudWatch 에이전트를 EC2 서버에 설치하면, 에이전트가 주기적으로 OS의 메트릭(메모리, 디스크)과 로그 파일을 읽어 CloudWatch로 보낸다. 온프레미스 서버에도 같은 에이전트를 설치할 수 있다.

4단계별 동작 과정

  1. 에이전트 다운로드 및 설치EC2에 IAM 역할을 부여한 후 AWS에서 제공하는 설치 명령(또는 Systems Manager)으로 에이전트 패키지를 다운로드하고 설치한다.
  2. 설정 파일 배치에이전트가 무엇을 수집할지 정의하는 JSON 설정 파일을 배치한다.
  3. 에이전트 시작 및 모니터링에이전트 프로세스를 실행하면, 주기적으로 메트릭과 로그를 수집해 CloudWatch로 전송한다.

1상대의 출발점 확인

시스템 메트릭(CPU, 메모리, 디스크)은 CloudWatch 에이전트가 기본으로 수집할 수 있다. 하지만 데이터베이스 연결 수, 캐시 히트율, 메시지 큐 길이 같은 애플리케이션 고유의 메트릭은 에이전트가 알 수 없다. 이런 것들을 수집하려면 별도의 수집 기법이 필요하다.

2질문 제기

호스트 메트릭과 애플리케이션 메트릭을 한 에이전트로 함께 수집할 수 있을까?

3구조적 핵심 예시

CloudWatch 에이전트는 설정에서 StatsD 리스너(포트 8125) 또는 collectd 소켓을 활성화하면, 애플리케이션이 그 포트로 보낸 커스텀 메트릭(StatsD 형식)을 수집해 CloudWatch로 함께 전송한다.

4단계별 동작 과정

  1. 시스템 메트릭 수집에이전트가 설정 파일에 명시된 CPU, 메모리, 디스크 메트릭을 OS에서 읽어 수집한다.
  2. 플러그인 리스너 활성화설정 파일에서 StatsD 또는 collectd 리스너 포트를 활성화하면, 에이전트가 그 포트를 열고 대기한다.
  3. 애플리케이션 메트릭 수신 및 전송애플리케이션이 해당 포트로 메트릭을 보내면 에이전트가 수신하고, 시스템 메트릭과 함께 CloudWatch로 전송한다.

OpenTelemetry 수집 경로: OTLP 엔드포인트·컬렉터·ADOT

표준 OpenTelemetry 형식(OTLP)으로 만든 신호를 컬렉터나 ADOT 배포판을 거쳐 CloudWatch 로 보내는 길이다.

1상대의 출발점 확인

CloudWatch는 CloudWatch 에이전트(StatsD, collectd), Prometheus, CloudWatch API 등 여러 형식의 메트릭을 받는다. 하지만 OpenTelemetry(OTLP)는 메트릭·로그·트레이스를 함께 표준화한 새로운 형식이다. 기존 에이전트만으로는 OTLP를 직접 수신할 수 없다.

2질문 제기

OpenTelemetry 표준 형식으로 보낸 메트릭, 로그, 트레이스를 CloudWatch에서 수집하려면?

3구조적 핵심 예시

1상대의 출발점 확인

1상대의 출발점 확인

  3. 메트릭 수집 및 전송선정된 팟의 /metrics 엔드포인트에서 Prometheus 형식 메트릭을 주기적으로 긁어서 CloudWatch로 전송한다.

1상대의 출발점 확인

일반적으로 각 서비스와 애플리케이션이 생성하는 로그와 메트릭은 자신이 실행되는 환경 내에 산재되어 있습니다. EC2의 로그는 EC2 인스턴스에, RDS의 메트릭은 RDS 대시보드에, 외부 모니터링 도구의 데이터는 그 도구의 저장소에 남아 있습니다. 이렇게 흩어진 데이터들은 한곳에서 전체 상황을 파악하기 어렵게 만듭니다.

2질문 제기

외부에 흩어져 있는 데이터 소스들을 CloudWatch로 가져오고, 반대로 CloudWatch의 데이터를 다른 시스템으로 보내려면 어떻게 할까요?

3구조적 핵심 예시

  3. 연속 흐름 유지설정된 경로에 따라 지속적으로 데이터가 양방향으로 이동하며, 필터나 규칙으로 필요한 데이터만 선택해 전달됩니다.

서비스 맵과 SLO 대시보드로 전체 상황을 파악할 수 있지만, "왜 특정 사용자의 요청이 갑자기 느려졌는가?" 또는 "어느 요청이 DB 타임아웃을 일으켰는가?"를 추적하려면 개별 요청의 전체 경로를 상세히 들여다봐야 합니다. 기존에는 로그를 수동으로 뒤져서 요청 ID를 추적하고 관련 로그들을 찾아야 했습니다.

3구조적 핵심 예시

1상대의 출발점 확인
