PostgreSQL 소개와 문서·버그 리포트 안내

PostgreSQL이 무엇인지, 그 역사와 문서 구성, 문제 발생 시 버그를 신고하는 방법을 안내하는 입문 장이다.

#1문제 상황

데이터를 여러 사람이 동시에 다루면서 값이 서로 어긋나지 않게 유지하려면, 단순한 파일 저장이나 표 계산 도구로는 한계가 금방 드러난다. 동시에 같은 데이터를 읽고 쓰는 순간 어떤 값이 진짜인지 보장할 방법이 없고, 여러 테이블에 나뉜 데이터를 관계로 묶어 조회하는 일도 어렵다.

그래서 예전부터 데이터베이스 관리 시스템이 쓰였지만, 초창기 상용 제품은 지금 당연하게 여기는 기능들이 한참 뒤에야 들어왔다. 복잡한 질의나 트리거, 갱신 가능한 뷰, 트랜잭션 무결성, 다중 버전 동시성 제어 같은 개념은 소수의 상용 시스템에서나 나중에 지원되었다.

또한 사용자가 데이터 타입이나 함수, 연산자 같은 것을 직접 늘려 쓸 수 없는 제품이 많았고, 라이선스 제약 때문에 소스를 고치거나 자유롭게 재배포하기도 어려웠다.

#2핵심 질문

여러 사용자가 동시에 쓰는 데이터의 무결성을 지키면서, 사용자가 기능을 직접 확장하고 자유롭게 쓸 수 있는 데이터베이스는 어떻게 만들 수 있을까?

#3동작 예시

PostgreSQL은 버클리 캘리포니아 대학 컴퓨터과학과에서 개발된 POSTGRES 4.2 버전을 계승한 객체-관계형 데이터베이스 관리 시스템(ORDBMS, 관계형 테이블에 객체 개념을 더한 DBMS)이다. 예를 들어 외래 키(다른 테이블의 행을 가리키는 제약)로 연결된 두 테이블에서, 한쪽 행을 지우는 순간 관련 행까지 정해진 규칙대로 처리되며 값의 일관성이 유지된다.

#4동작 과정

  1. 기반 계승PostgreSQL은 버클리에서 만든 POSTGRES 4.2의 오픈소스 후속 구현으로 출발해, 그때 실험되던 개념들을 기본으로 갖춘다.
  2. 표준과 기능 제공SQL 표준의 상당 부분을 지원하고 복잡한 질의, 외래 키, 트리거, 갱신 가능한 뷰, 트랜잭션 무결성, 다중 버전 동시성 제어 같은 기능을 제공한다.
  3. 확장과 배포새 데이터 타입, 함수, 연산자, 집계 함수, 인덱스 방식, 절차 언어를 사용자가 추가할 수 있고, 관대한 라이선스 덕분에 사용·수정·재배포가 자유롭다.

#5한 줄 요약

버클리 POSTGRES를 계승해 표준 SQL과 확장성을 함께 갖춘, 자유롭게 쓰고 고칠 수 있는 객체-관계형 데이터베이스 관리 시스템

튜토리얼 — 설치와 시작하기

PostgreSQL을 설치한 뒤 서버를 켜고 psql로 접속해 첫 데이터베이스와 테이블을 만들어 보는 실습 안내다.

#1문제 상황

데이터베이스를 처음 접하면 서버를 설치하고 켠 뒤 접속해서 데이터베이스와 테이블을 만드는 첫 단계에서 막히기 쉽다. 설치 자체보다, 서버가 어떤 구조로 돌아가는지와 어디에 어떻게 접속하는지를 모르면 첫 명령 한 줄을 어디에 넣어야 할지 알 수 없다.

이 안내는 그 진입 장벽을 없애기 위해 설치, 구조의 기본, 데이터베이스 생성, 데이터베이스 접속이라는 네 가지를 순서대로 밟게 한다. 컴퓨터를 다루는 일반적인 지식만 가정하고 특정 운영체제나 프로그래밍 경험을 요구하지 않기 때문에 초심자도 그대로 따라올 수 있다.

#2핵심 질문

PostgreSQL을 설치해 서버를 켜고, 첫 데이터베이스를 만들어 접속하기까지는 어떤 순서로 진행해야 할까?

#3동작 예시

이 장은 설치(Installation), 구조의 기본(Architectural Fundamentals), 데이터베이스 만들기(Creating a Database), 데이터베이스 접속하기(Accessing a Database) 네 절로 구성된다. 예를 들어 설치를 마친 뒤 서버를 기동하고 명령줄 도구로 접속해 CREATE DATABASE 문을 실행하면, 방금 만든 데이터베이스에 연결해 이후의 SQL 작업을 시작할 수 있다.

#4동작 과정

  1. 설치PostgreSQL을 설치하고 데이터베이스 서버가 실행되도록 준비한다.
  2. 구조 이해서버와 클라이언트가 어떻게 나뉘어 동작하는지 클라이언트-서버 구조의 기본을 익힌다.

SQL 문법

PostgreSQL SQL 문장을 이루는 어휘·식별자·상수·연산자·주석 등 표기 규칙과 표현식 작성법.

#1문제 상황

SQL 문장을 아무렇게나 적으면 데이터베이스가 의도와 다르게 해석한다. 식별자와 키워드는 대소문자 처리 규칙이 다르고, 상수와 연산자, 특수 문자, 주석이 각각 정해진 표기법을 따르기 때문에 이 규칙을 모르면 문법 오류가 나거나 다른 결과가 나온다.

또한 값을 계산하는 식(expression)을 쓸 때 열을 가리키는 방법, 함수를 호출하는 방식, 타입을 변환하는 표기, 연산자 우선순위를 제대로 알지 못하면 원하는 결과를 얻기 어렵다. 이런 표기 규칙이 SQL 전체의 바탕이 되기 때문에 여기서 어긋나면 이후 모든 문장이 흔들린다.

#2핵심 질문

SQL 문장을 이루는 어휘와 식은 어떤 표기 규칙에 따라 작성해야 할까?

#3동작 예시

SQL 문법 장은 어휘 구조(Lexical Structure)와 값 식(Value Expressions), 함수 호출(Calling Functions)로 나뉜다. 예를 들어 어느 테이블의 열을 참조하는 식을 쓰고 그 결과에 타입 캐스트(값의 데이터 타입을 바꾸는 표기)를 붙이면, 데이터베이스는 정해진 우선순위에 따라 식을 계산해 하나의 값으로 돌려준다.

#4동작 과정

  1. 어휘 구조 해석식별자와 키워드, 상수, 연산자, 특수 문자, 주석을 정해진 표기법으로 읽어 문장의 토큰을 나눈다.
  2. 값 식 구성열 참조, 위치 매개변수, 함수 호출, 집계·윈도 함수 호출, 타입 캐스트 등으로 계산할 식을 만든다.
  3. 우선순위 적용연산자 우선순위와 식 평가 규칙에 따라 값을 계산해 최종 결과를 낸다.

데이터 정의(DDL)

CREATE·ALTER·DROP 등으로 테이블, 스키마, 제약 조건, 권한 같은 데이터베이스 객체 구조를 만들고 바꾸는 명령.

#1문제 상황

데이터를 담을 구조를 잡지 않으면 아무것도 저장할 수 없다. 그런데 테이블을 한 번 만들고 나면 열을 더하거나 빼고, 제약 조건을 붙이거나 떼고, 열의 기본값이나 데이터 타입을 바꾸고, 이름을 고쳐야 하는 요구가 계속 생긴다.

이런 변경을 데이터가 들어 있는 상태에서 잘못하면 값이 깨지거나 제약이 어긋난다. 또한 누가 어떤 객체에 접근할 수 있는지 권한을 정하고, 스키마로 객체를 묶어 이름 충돌을 피하는 일까지 함께 관리해야 한다. 구조를 만드는 명령과 바꾸는 명령을 따로 익히지 않으면 유지보수 단계에서 계속 문제가 생긴다.

#2핵심 질문

테이블과 스키마, 제약 조건 같은 데이터베이스 객체의 구조는 어떻게 만들고 바꾸며 관리할까?

#3동작 예시

데이터 정의 장은 테이블 기본(Table Basics)에서 시작해 기본값, ID 열, 생성 열, 제약 조건(검사·NOT NULL·고유·기본 키·외래 키·배제)을 다루고, 이어서 테이블 수정과 권한, 스키마로 넘어간다. 예를 들어 이미 있는 테이블에 열을 하나 추가하고 그 열에 NOT NULL 제약을 붙이면, 새 구조가 즉시 적용되어 이후 들어오는 데이터부터 규칙이 강제된다.

#4동작 과정

  1. 객체 생성CREATE TABLE 등으로 테이블을 만들고 기본값·ID 열·생성 열 같은 열 속성을 지정한다.
  2. 제약과 수정기본 키·외래 키·고유·검사 제약을 붙이고, ALTER 명령으로 열을 더하거나 빼고 타입·기본값·이름을 바꾼다.
  3. 권한과 스키마객체별 권한을 부여하고 스키마로 묶어 검색 경로에 따라 객체를 찾도록 관리한다.

데이터 조작(DML)

INSERT·UPDATE·DELETE·MERGE 등으로 테이블의 실제 데이터 행을 넣고, 고치고, 지우는 명령.

#1문제 상황

테이블 구조만 만들어 두면 그 안은 비어 있다. 실제로 쓸모 있으려면 데이터를 넣고, 잘못된 값을 고치고, 필요 없어진 행을 지우는 작업이 계속 이어져야 한다. 구조를 정의하는 명령과 데이터를 다루는 명령은 목적이 달라서, 후자를 따로 익히지 않으면 테이블은 있어도 내용을 채우지 못한다.

또 데이터를 바꾸는 문장은 잘못 실행하면 여러 행을 한꺼번에 망가뜨릴 수 있어, 어떤 행이 바뀌는지를 정확히 지정하는 조건과 바꾼 결과를 확인하는 방법이 함께 필요하다.

#2핵심 질문

테이블에 데이터를 넣고, 고치고, 지우는 일은 어떤 명령으로 어떻게 하는가?

#3동작 예시

데이터 조작 장은 데이터 삽입(Inserting Data), 갱신(Updating Data), 삭제(Deleting Data)와 함께 수정된 행에서 데이터를 돌려받는 방법(Returning Data from Modified Rows)을 다룬다. 예를 들어 조건에 맞는 행의 열 값을 UPDATE로 바꾸면서 그 바뀐 행의 값을 같은 문장에서 바로 돌려받으면, 어떤 행이 어떻게 달라졌는지 실행 결과로 확인할 수 있다.

#4동작 과정

  1. 삽입INSERT로 테이블에 새 행을 넣어 저장할 데이터를 채운다.
  2. 갱신·삭제UPDATE로 조건에 맞는 행의 값을 바꾸고, DELETE로 필요 없어진 행을 지운다.
  3. 결과 확인수정된 행의 값을 RETURNING 같은 방법으로 돌려받아 어떤 행이 바뀌었는지 확인한다.

SQL 언어02-04

쿼리

SELECT 문으로 테이블 조인, 집계, 정렬, 서브쿼리, CTE 등을 사용해 원하는 데이터를 조회하는 방법.

#1문제 상황

테이블에 데이터를 넣고 나면 거기서 원하는 값만 골라내야 하는데, 저장된 행을 전부 읽어서 눈으로 걸러내는 방식은 데이터가 조금만 늘어도 감당이 안 됩니다. 여러 테이블에 나뉜 정보(주문과 고객, 상품과 재고)를 사람이 직접 맞춰 붙이는 것도 오류가 나기 쉽습니다.

PostgreSQL 이전의 단순 조회는 한 테이블에서 조건에 맞는 행을 꺼내는 정도에 머물렀고, 조인·집계·정렬·중첩 질의를 섞어 쓰려면 애플리케이션 코드에서 반복문을 돌려 처리해야 했습니다. 그 결과 네트워크로 불필요한 행을 실어 나르게 되고, 같은 계산을 여러 번 하게 되어 느려지고 결과도 흔들렸습니다.

#2핵심 질문

서버 안에서 여러 테이블을 붙이고, 조건으로 거르고, 묶어서 계산하고, 정렬·페이지 처리까지 한 번에 처리해 원하는 행만 받아오려면 어떻게 해야 할까요?

#3동작 예시

고객 테이블과 주문 테이블이 있고, "2024년 이후 주문 금액 합계가 큰 고객 상위 10명"을 뽑는다고 합시다. 애플리케이션으로 전부 가져오는 대신, FROM 으로 두 테이블을 조인하고 WHERE 로 기간을 거르고 GROUP BY 로 고객별로 묶어 SUM(금액) 을 계산한 뒤 ORDER BY 합계 DESC LIMIT 10 을 붙이면, PostgreSQL 이 이 계획을 한 번에 실행해 딱 10행만 돌려줍니다.

#4동작 과정

  1. 테이블 식 구성FROM 절에서 조인할 테이블을 나열하고 WHERE 로 행을 걸러 원하는 대상만 남깁니다. 조인 조건이 맞는 행끼리만 결합되어 불필요한 행이 결과에서 빠집니다.
  2. 집계와 그룹화GROUP BY 로 같은 기준의 행을 묶고 HAVING 으로 그룹 결과를 다시 거릅니다. 집계 함수(SUM, COUNT 등)가 그룹 단위 값을 계산해 요약된 행이 만들어집니다.
  3. 결과 다듬기SELECT 목록으로 출력 컬럼을 고르고 DISTINCT 로 중복을 제거하며, ORDER BY·LIMIT·OFFSET 으로 정렬과 페이지 처리를 적용합니다. WITH(CTE)나 서브쿼리로 중간 결과를 이름 붙여 재사용하면 최종적으로 원하는 행만 남습니다.

#1문제 상황

컬럼에 어떤 값이든 문자열로만 저장하면, 숫자 비교가 문자열 비교가 되어 "10" 이 "9" 보다 작게 취급되고 날짜 계산도 할 수 없습니다. 반대로 아무 타입이나 대충 지정하면 저장 공간을 낭비하거나 표현할 수 있는 범위를 넘는 값이 들어와 오류·정밀도 손실이 생깁니다.

초창기 방식은 숫자·문자·날짜 몇 가지 타입만 두고 나머지는 애플리케이션이 문자열을 파싱해 처리하게 했습니다. 그러면 타입이 어긋난 값이 조용히 들어가 잘못된 비교 결과를 낳고, 서버는 그 값이 유효한지 검증할 방법이 없었습니다.

#2핵심 질문

컬럼에 담을 값의 종류를 미리 정해 두고, 저장 크기와 표현 범위·연산 방식까지 서버가 일관되게 관리하게 하려면 어떻게 해야 할까요?

#3동작 예시

금액을 다루는 컬럼을 numeric(10,2) 로 선언하면 소수점 이하 두 자리를 정확히 보관하고 반올림 오차 없이 합계를 계산합니다. 반면 같은 값을 real 로 선언하면 부동소수점 근사값으로 저장되어 0.1 + 0.2 가 정확히 0.3 이 되지 않을 수 있습니다. 타입 선언 하나가 저장 방식과 연산 결과를 바꾸는 것입니다.

#4동작 과정

  1. 타입 선택값의 성격에 따라 정수(integer, bigint), 임의 정밀도 숫자(numeric), 문자(text, varchar), 날짜·시간(timestamp, date), 불리언, JSON, 배열 등에서 고릅니다. 각 타입은 저장 크기와 표현 범위가 정해져 있어 목적에 맞는 것이 선택됩니다.
  2. 값 저장과 검증INSERT·UPDATE 시 서버가 입력값을 해당 타입 규칙으로 해석해 저장하고, 범위를 벗어나거나 형식이 맞지 않으면 오류로 거부합니다. 잘못된 값이 테이블에 들어가는 것을 막아 데이터 일관성이 유지됩니다.
  3. 타입별 연산 적용저장된 값은 그 타입에 정의된 연산자·함수로 처리됩니다. 숫자는 산술, 날짜는 기간 연산, 문자는 패턴 검색이 가능해져 값의 성격에 맞는 계산이 이뤄집니다.

문자열·숫자·날짜 처리와 집계·윈도우·배열 연산 등 PostgreSQL이 기본 제공하는 내장 함수와 연산자.

#1문제 상황

문자열을 합치거나 날짜에서 연·월을 뽑아내는 일을 애플리케이션에서 처리하면, 테이블의 모든 행을 서버 밖으로 꺼내 각 언어의 라이브러리로 가공한 뒤 다시 계산해야 합니다. 행이 많아질수록 전송량이 폭증하고, 서버가 SQL 로 할 수 있는 일을 굳이 밖에서 반복하게 됩니다.

초기의 조회는 컬럼 값을 그대로 꺼내는 정도였고, 소문자 변환·부분 문자열·날짜 차이·그룹 합계 같은 계산은 전부 클라이언트 몫이었습니다. 그러면 같은 계산을 여러 곳에서 각자 구현하게 되어 결과가 어긋나고, 정렬·필터도 계산된 값이 아닌 원본 값 기준으로만 가능했습니다.

#2핵심 질문

문자열·숫자·날짜 가공과 집계·윈도우 계산을 데이터가 있는 서버 안에서 내장 함수와 연산자로 처리해 결과만 받아오려면 어떻게 해야 할까요?

#3동작 예시

이메일 컬럼에서 도메인별 가입자 수를 세려고 합니다. 애플리케이션으로 전부 가져와 파싱하는 대신, SELECT split_part(email, '@', 2) AS domain, count(*) FROM users GROUP BY domain 으로 서버 안에서 문자열을 잘라 그룹핑하면 도메인별 개수만 돌려받습니다. 문자열 함수와 집계 함수를 한 문장에 섞어 쓴 것입니다.

#4동작 과정

  1. 값 변환 함수 적용문자열 함수(||, substring, upper), 수학 함수, 날짜·시간 함수(EXTRACT, date_trunc)로 컬럼 값을 원하는 형태로 가공합니다. 원본을 그대로 꺼내지 않고 필요한 값만 계산해 내보낼 수 있게 됩니다.
  2. 집계·윈도우 계산SUM·COUNT·AVG 같은 집계 함수로 그룹별 요약을 만들거나, 윈도우 함수로 행을 유지한 채 순위·누적합을 계산합니다. 전체를 꺼내지 않고도 요약과 순위 정보가 결과에 담깁니다.
  3. 식 안에서 조합연산자와 함수를 식 안에 겹쳐 쓰고 결과를 WHERE·ORDER BY 에도 적용합니다. 계산된 값 기준으로 거르고 정렬할 수 있어 후처리 없이 최종 결과가 완성됩니다.

타입 변환

서로 다른 데이터 타입 사이에서 값이 자동 또는 명시적(CAST)으로 변환되는 규칙과 우선순위.

#1문제 상황

SQL 문은 의도하든 아니든 한 식 안에서 서로 다른 타입을 섞게 됩니다. 정수 컬럼과 문자열 리터럴을 비교하거나, 숫자와 문자를 UNION 으로 합치거나, 함수에 다른 타입 인자를 넘기는 상황이 그렇습니다. 이때 규칙 없이 변환이 이뤄지면 결과가 달라지거나 비교가 예상과 어긋납니다.

초기에는 이런 혼합 타입 식을 애플리케이션에서 미리 맞춰 넘기거나, 서버가 임의로 한쪽을 바꿔 비교하게 두었습니다. 그러면 같은 값이 문맥에 따라 다른 타입으로 해석되어 인덱스를 타지 못하거나, 조용히 잘려 나가 잘못된 결과가 나오는 문제가 있었습니다.

#2핵심 질문

서로 다른 타입이 한 식에 섞였을 때 어떤 값을 어떤 타입으로 바꿀지 규칙과 우선순위를 정해, 결과를 예측 가능하게 만들려면 어떻게 해야 할까요?

#3동작 예시

정수 컬럼 id 와 문자열 리터럴 '42' 를 WHERE id = '42' 로 비교하면, PostgreSQL 은 리터럴을 정수로 해석해 비교합니다. 반대로 id::text = '42' 처럼 명시적으로 문자로 바꾸면 문자 비교가 되어 인덱스 사용이 달라질 수 있습니다. 같은 값이라도 어느 쪽으로 변환하느냐에 따라 실행 방식과 결과가 갈립니다.

#4동작 과정

  1. 변환 지점 판별연산자·함수 호출·UNION·CASE·SELECT 출력 컬럼 등에서 서로 다른 타입이 만나는 지점을 찾습니다. 어디서 타입을 맞춰야 하는지가 먼저 정해집니다.
  2. 규칙에 따른 타입 결정후보 연산자와 함수 중 인자 타입이 맞는 것을 고르고, 암시적 변환(자동) 우선순위에 따라 공통 타입을 정합니다. 명확하지 않으면 명시적 캐스트(CAST, ::)로 사용자가 직접 지정합니다.
  3. 변환 실행과 결과 반영정해진 타입으로 값을 변환해 식을 평가합니다. 변환이 비교·정렬·인덱스 사용 방식에 반영되어 최종 결과가 결정됩니다.

B-tree, GiST, GIN 등 인덱스 종류와 생성·사용 방법으로 조회 성능을 높이는 구조.

#1문제 상황

인덱스가 없으면 특정 행 하나를 찾을 때도 테이블 전체를 처음부터 끝까지 읽어야 합니다. 행이 수백만 개로 늘면 조건에 맞는 한 건을 찾는 데도 매번 전부 스캔하게 되어 조회가 느려지고, 동시에 들어오는 요청이 밀리기 시작합니다.

초기의 조회는 테이블을 순차적으로 훑는 방식뿐이었고, 값이 어디 있는지 미리 알 방법이 없었습니다. 그래서 같은 조건의 검색을 반복해도 매번 전체를 다시 읽었고, 정렬된 결과를 얻으려면 읽은 뒤 다시 정렬하는 비용까지 붙었습니다.

#2핵심 질문

값의 위치를 미리 정리해 두어, 전체를 읽지 않고도 조건에 맞는 행만 빠르게 찾아내려면 어떻게 해야 할까요?

#3동작 예시

#4동작 과정

  1. 인덱스 생성컬럼에 맞는 인덱스 종류를 골라 만듭니다. B-tree 는 크기 비교·정렬, GIN 은 배열·전문 검색, GiST·SP-GiST 는 기하·공간, BRIN 은 큰 테이블의 범위 요약에 쓰입니다. 값과 위치의 대응이 별도 구조로 저장됩니다.
  2. 탐색에 활용조건이 인덱스 컬럼과 맞으면 서버가 인덱스를 먼저 뒤져 대상 행의 위치를 좁힙니다. 전체 스캔 대신 필요한 범위만 읽어 조회가 빨라지고, ORDER BY 도 정렬된 인덱스를 그대로 활용할 수 있습니다.
  3. 유지 비용 감수INSERT·UPDATE·DELETE 때마다 인덱스도 함께 갱신되어 쓰기 비용과 저장 공간이 늘어납니다. 그래서 정말 필요한 컬럼에만 만들고 주기적으로 사용 여부를 점검합니다.

#1문제 상황

초기의 문자열 검색은 원문을 통째로 비교하는 방식이었습니다. 그래서 "run" 을 찾으면 "running" 은 놓치고 "brunch" 의 일부는 걸리는 식으로 결과가 부정확했고, 어떤 단어가 얼마나 중요한지 순위를 매길 수도 없었습니다.

#2핵심 질문

#3동작 예시

문서 컬럼에 to_tsvector 로 색인을 만들고 to_tsquery 로 질의를 던지면, "The cats are running" 이라는 문장은 cat, run 같은 기본형 토큰으로 정규화되어 저장됩니다. 여기에 'run' 을 검색하면 시제 변형까지 같은 토큰으로 맞아떨어져 찾아지고, ts_rank 로 관련도 순으로 정렬할 수 있습니다.

#4동작 과정

  1. 문서 파싱과 정규화문서를 파서로 토큰(단어)으로 나누고, 불용어(stop words)를 제거한 뒤 사전으로 어간을 기본형으로 바꿉니다. 결과가 tsvector 라는 정규화된 토큰 목록으로 저장되어 변형된 단어도 같은 형태로 모입니다.
  2. 질의 변환검색어도 같은 규칙으로 파싱해 tsquery 로 만듭니다. AND·OR·NOT 과 구문 검색을 표현할 수 있고, 문서 토큰과 같은 기준으로 비교되어야 매칭이 정확해집니다.

동시성 제어(MVCC)

MVCC와 트랜잭션 격리 수준으로 여러 트랜잭션이 동시에 접근할 때 일관성과 동시성을 유지하는 방식.

#1문제 상황

예전 방식은 한 세션이 어떤 행을 수정하는 동안 다른 세션이 그 행을 건드리지 못하도록 락(잠금)을 걸어 막았다. 읽기 작업끼리도 서로 기다려야 했고, 긴 쓰기 트랜잭션이 끝날 때까지 조회가 멈춰 동시성이 크게 떨어졌다. 읽는 쪽과 쓰는 쪽이 같은 데이터를 두고 계속 줄을 서야 했던 구조다.

#2핵심 질문

읽기와 쓰기가 서로를 막지 않으면서도 각 트랜잭션이 일관된 데이터를 보게 하려면 어떻게 해야 하는가?

#3동작 예시

어떤 세션이 계좌 잔액 행을 100에서 200으로 바꾼다. 다른 세션이 같은 행을 조회할 때, 변경 세션이 아직 커밋하지 않았다면 조회는 여전히 100을 본다. 커밋이 끝난 뒤에 시작된 조회부터 새 값 200이 보인다.

#4동작 과정

  1. 변경본 기록행을 수정할 때 기존 행을 덮어쓰지 않고 변경된 새 버전의 행을 별도로 만든다. 그래서 원래 행은 그대로 남는다.
  2. 스냅샷 판정각 조회는 격리 수준(Read Committed, Repeatable Read, Serializable 같은 트랜잭션 간 약속)에 따른 자기 스냅샷을 기준으로, 자기에게 보여야 할 행 버전만 골라 읽고 커밋되지 않은 버전은 건너뛴다.
  3. 정리더 이상 어떤 트랜잭션도 볼 수 없는 오래된 행 버전은 나중에 청소 작업으로 회수된다.

#5한 줄 요약

행의 여러 버전을 유지해 읽기와 쓰기가 서로 기다리지 않게 하면서 트랜잭션마다 일관된 데이터를 보여주는 것

성능 팁과 병렬 쿼리

쿼리 튜닝과 서버 설정으로 성능을 높이는 방법 및 여러 워커가 쿼리를 나눠 처리하는 병렬 쿼리.

#1문제 상황

같은 결과를 내는 쿼리도 플래너가 고른 실행 계획에 따라 몇 배나 느려진다. 그런데 어떤 쿼리가 느린지, 어느 단계에서 시간을 쓰는지 확인하지 않고 설정값만 만지면 개선이 되지 않는다. 또 큰 테이블 하나를 처리할 때 서버가 코어 하나만 써서 나머지 CPU가 놀게 된다.

#2핵심 질문

느린 쿼리가 어디서 시간을 쓰는지 확인하고, 여러 CPU를 나눠 써서 더 빨리 처리할 수 있는가?

#3동작 예시

쿼리 앞에 EXPLAIN ANALYZE 를 붙여 실행하면, 플래너가 만든 계획 트리와 각 단계에서 실제로 걸린 시간이 줄 단위로 출력된다. 예를 들어 큰 테이블을 순차 스캔하는 단계가 전체 시간의 대부분이면 그 사실이 출력에 그대로 드러난다.

#4동작 과정

  1. 계획 확인EXPLAIN ANALYZE 로 실행 계획과 실제 소요 시간을 본다. 플래너가 쓰는 통계가 오래됐으면 ANALYZE 로 갱신한다.
  2. 튜닝 적용인덱스 추가, 조인 형태 조정, 서버 설정값 변경 등으로 병목 단계를 줄인다.
  3. 병렬 실행큰 스캔·조인·집계는 워커 프로세스 여러 개가 데이터를 나눠 처리한 뒤 결과를 합친다. 그래서 코어 여러 개를 함께 쓴다.

#5한 줄 요약

실행 계획과 통계를 근거로 병목을 찾아 고치고, 큰 쿼리는 여러 워커로 나눠 CPU를 함께 쓰게 하는 것

설치 — 바이너리 배포판

소스 코드를 직접 컴파일하지 않고, 각 운영체제용으로 미리 빌드된 패키지(인스톨러·패키지 관리자)로 PostgreSQL 서버를 설치하는 방법.

#1문제 상황

소스 코드를 직접 받아 컴파일하려면 컴파일러와 빌드 도구, 개발 라이브러리를 먼저 갖추고 빌드 단계를 거쳐야 한다. 이 과정은 오래 걸리고 의존성이 하나만 어긋나도 실패한다. 그래서 서버를 쓰려는 사람에게 설치 자체가 큰 진입 장벽이 된다.

#2핵심 질문

컴파일 과정을 직접 거치지 않고 PostgreSQL 서버를 빠르고 간단하게 설치할 수 있는가?

#3동작 예시

운영체제의 패키지 관리자나 인스톨러로 미리 빌드된 PostgreSQL 패키지를 내려받아 설치하면, 서버 실행 파일과 기본 클라이언트 도구가 정해진 위치에 배치된다. 공식 문서는 바이너리 패키지가 제공되는 플랫폼에서는 이 방식을 권장한다고 밝힌다.

#4동작 과정

  1. 패키지 확보공식 다운로드 페이지에서 자신의 플랫폼에 맞는 바이너리 패키지나 인스톨러를 받는다.
  2. 설치 실행패키지 관리자나 인스톨러가 서버 바이너리와 클라이언트 도구를 정해진 위치에 배치한다.
  3. 설치 확인설치가 끝나면 서버 실행 파일과 psql 같은 도구가 함께 들어와 바로 쓸 수 있다.

#2핵심 질문

#3동작 예시

  2. 빌드 설정configure(또는 Meson)로 설치 경로와 기능 옵션을 지정한다. 이 단계에서 필요한 개발 라이브러리가 있는지도 검사한다.
  3. 컴파일·설치빌드 도구로 컴파일하고 설치한다. 그 결과 원하는 옵션이 반영된 서버 실행 파일이 만들어진다.

서버 셋업과 운영

설치 후 데이터베이스 클러스터를 생성하고 서버를 시작·중지하며 정상적으로 운영하기 위한 기본 절차와 환경 설정.

#1문제 상황

패키지나 소스로 서버를 설치해도 그 직후에는 데이터를 담을 저장 영역이 없다. PostgreSQL 은 하나의 데이터 디렉터리(클러스터)를 중심으로 동작하기 때문에 이 영역을 만들지 않으면 서버를 시작할 수 없다. 시작·중지 방법과 자원 설정도 모르면 운영 중에 바로 문제가 생긴다.

#2핵심 질문

설치한 서버가 실제로 데이터를 담고 돌아가게 만들고 안정적으로 운영하려면 무엇을 해야 하는가?

#3동작 예시

클러스터 생성 도구(initdb)로 데이터 클러스터를 만들면 지정한 디렉터리에 설정 파일과 데이터 저장 구조가 생긴다. 그다음 서버를 시작하면 이 클러스터를 열고 클라이언트 연결을 받기 시작한다. 종료할 때는 정상 종료 절차를 거쳐 진행 중인 작업을 안전하게 마무리한다.

#4동작 과정

  1. 클러스터 생성initdb 로 데이터 디렉터리를 초기화한다. 이때 서버를 실행할 사용자 계정과 파일 시스템이 준비되어 있어야 한다.
  2. 서버 시작시작 명령으로 서버를 띄운다. 시작에 실패하면 로그와 커널 자원 설정(공유 메모리 등)을 확인한다.
  3. 운영·종료서버를 운영하면서 필요할 때 안전하게 종료하고, 클러스터 업그레이드 같은 유지 작업을 한다.

#5한 줄 요약

데이터 클러스터를 만들어 서버를 시작하고 안전하게 운영·종료하는 기본 절차를 세우는 것

서버 구성

postgresql.conf 등의 설정 파일에서 메모리·연결·로깅 등 서버 동작 전반을 제어하는 구성 매개변수를 지정하는 방법.

#1문제 상황

서버를 설치하고 시작하면 기본 설정값으로 동작한다. 그런데 기본값은 특정 서버의 자원과 사용 패턴에 맞춰진 것이 아니라서 메모리·연결 수·로깅 같은 항목이 실제 환경과 어긋날 수 있다. 그대로 두면 성능과 안정성이 떨어지고, 문제 원인도 로그에 남지 않아 파악하기 어렵다.

#2핵심 질문

서버의 메모리·연결·로깅 같은 동작을 실제 환경에 맞게 제어하려면 어떻게 설정하는가?

#3동작 예시

메모리 관련 매개변수의 값을 바꾸려면 postgresql.conf 파일에서 해당 항목을 수정하거나, SQL 로 매개변수를 지정하고 설정을 다시 읽게 하면 된다. 문서는 설정 파일, SQL, 셸 환경 변수 등 여러 경로로 매개변수를 지정할 수 있다고 설명한다.

#4동작 과정

  1. 매개변수 지정설정 파일에 값을 적거나 SQL·셸을 통해 매개변수를 지정한다. 이름과 값 형식이 정해져 있다.
  2. 적용설정 파일 변경은 다시 읽기로 반영되고, 서버 재시작이 필요한 항목도 있다. SQL 로 바꾼 값은 바로 반영된다.
  3. 영역별 조정연결과 인증, 자원 사용량, WAL(쓰기 전 로그), 로깅 등 영역별 매개변수를 워크로드에 맞게 조정한다.

클라이언트 인증

클라이언트가 서버에 접속할 때 신원을 확인하는 방식으로, pg_hba.conf 규칙과 비밀번호·인증서 등 다양한 인증 방법을 설정한다.

#1문제 상황

데이터베이스 서버는 네트워크에 열려 있어 아무 클라이언트나 접속을 시도할 수 있다. 접속을 그대로 허용하면 서버에 도달한 누구든 데이터를 읽고 바꿀 수 있고, 누가 어떤 이름으로 들어왔는지도 구분되지 않는다. 그래서 서버는 접속 요청마다 그 클라이언트가 정말 그 사용자가 맞는지 확인할 절차를 따로 가져야 한다.

#2핵심 질문

클라이언트가 서버에 접속할 때 그 신원을 어떤 규칙과 방법으로 확인할 것인가?

#3동작 예시

#4동작 과정

  1. 접속 요청 파싱클라이언트가 접속하려는 데이터베이스 이름과 사용자 이름, 접속 방식·출처 주소가 서버에 전달된다. 서버는 이 정보로 어떤 규칙을 적용할지 판단할 준비를 한다.
  2. 규칙 대조서버가 pg_hba.conf의 규칙을 위에서부터 순서대로 검사해 처음 맞는 줄을 고른다. 이 파일은 "어떤 클라이언트를 어떤 방법으로 인증할지"를 적는 접속 규칙 목록이다.
  3. 인증 방법 실행과 판정고른 규칙의 방법(예: 비밀번호 검증, 인증서 확인)으로 신원을 확인하고, 성공하면 SQL 환경에 그 사용자 신원이 설정되어 접속이 이어진다. 실패하면 접속이 끊긴다.

#1문제 상황

여러 사람과 프로그램이 하나의 데이터베이스에 접속하면, 각자가 어떤 객체에 접근하고 무엇을 할 수 있는지 구분해야 한다. 사용자마다 권한을 직접 하나하나 부여하면 대상이 늘수록 관리가 복잡해지고, 같은 권한을 여러 사람에게 반복 지정하다 보면 빠뜨리거나 잘못 주기 쉽다. 접속 주체와 권한을 묶어 관리할 공통 개념이 필요하다.

#2핵심 질문

접속 주체와 그 권한을 어떻게 하나의 개념으로 묶어 일관되게 관리할 것인가?

#3동작 예시

하나의 롤(role)을 만들어 데이터베이스 사용자로도, 여러 사용자를 묶는 그룹으로도 쓸 수 있다. 롤이 테이블 같은 객체를 소유하면 그 객체에 대한 권한을 가지며, 다른 롤에게 그 객체의 권한을 부여해 누가 어떤 객체에 접근할지 정한다. 또 한 롤에 다른 롤의 멤버십을 부여하면, 멤버 롤은 그 롤에 주어진 권한을 그대로 사용할 수 있다.

#4동작 과정

  1. 롤 생성과 속성 지정롤을 만들고 로그인 가능 여부, 슈퍼유저 여부 같은 속성을 정한다. 이 속성이 그 롤이 어떤 용도로 쓰일지를 결정한다.
  2. 객체 소유와 권한 부여롤이 테이블·함수 같은 객체를 소유하면 그 객체의 권한을 갖고, 다른 롤에게 GRANT로 접근 권한을 넘겨 준다. 권한을 받은 롤은 그 객체에 정해진 범위의 작업을 할 수 있다.
  3. 멤버십으로 권한 상속한 롤을 다른 롤의 멤버로 넣으면 멤버 롤이 상위 롤의 권한을 사용할 수 있다. 이로써 사용자와 그룹을 따로 두지 않고 하나의 롤 체계로 관리하게 된다.

#3동작 예시

#4동작 과정

  1. 템플릿 확인새 데이터베이스를 만들 때 기준이 되는 템플릿 데이터베이스를 정한다. 템플릿을 바꾸면 그 복사본으로 만들어지는 새 데이터베이스의 초기 내용이 달라진다.

  3. 삭제와 정리DROP DATABASE로 데이터베이스를 없애면 그 안의 모든 객체가 함께 제거된다. 이 작업은 되돌릴 수 없으므로 대상과 시점을 분명히 해 실행한다.

#4동작 과정

  1. 죽은 행 표시와 공간 회수VACUUM이 더 이상 쓰이지 않는 행이 쓰는 공간을 다시 쓸 수 있게 정리한다. 그래서 같은 데이터를 담은 테이블이 차지하는 공간 낭비가 줄어든다.

  3. 자동화된 반복 실행이 작업들은 주기적으로 반복해야 효과가 유지되므로 스크립트나 예약 도구로 정기 실행한다. 그 결과 성능 저하가 누적되지 않고 일정하게 유지된다.

데이터를 잃지 않도록 파일을 복사하거나 논리적으로 덤프해 두고, 장애 시 WAL을 재생해 일관된 시점으로 되돌리는 방법이다.

#1문제 상황

데이터베이스에 담긴 데이터는 장비 고장이나 잘못된 작업으로 한순간에 잃을 수 있다. 그래서 데이터를 따로 복사해 두는 백업이 필요한데, 백업을 뜨는 동안에도 데이터가 계속 바뀌기 때문에 단순히 파일만 복사하면 일관되지 않은 상태가 섞일 수 있다. 장애가 난 뒤에도 정확히 어느 시점 상태로 되돌릴 수 있어야 한다.

#2핵심 질문

데이터 변경이 계속되는 상황에서도 잃지 않고 정확한 시점으로 되돌릴 수 있게 어떻게 백업하고 복구할 것인가?

#3동작 예시

PostgreSQL은 데이터를 바꾸기 전에 그 변경 내용을 먼저 WAL(선행 기록 로그)에 기록한다. 그래서 백업 파일과 함께 그때까지 쌓인 WAL을 보관해 두면, 장애 후 백업을 복원한 뒤 WAL을 순서대로 재생해 특정 시점 상태까지 되돌릴 수 있다. 이렇게 연속 보관과 특정 시점 복구(PITR)를 조합하면 정확한 시점으로 복구할 수 있다.

#4동작 과정

  1. 변경 전 로그 기록데이터를 실제로 바꾸기 전에 변경 내용을 WAL에 먼저 적는다. 그래서 장애가 나도 로그를 근거로 변경을 다시 적용할 수 있다.
  2. 베이스 백업과 WAL 보관파일 시스템 수준으로 데이터베이스 전체를 복사한 베이스 백업을 만들고, 그 시점 이후의 WAL을 계속 모아 둔다. 이 둘을 합치면 백업 시점 이후의 모든 변경을 재현할 재료가 갖춰진다.
  3. 복구 시 재생장애 후 베이스 백업을 복원하고 보관한 WAL을 순서대로 재생해 원하는 시점까지 되돌린다. 그래서 백업 시점과 장애 시점 사이의 변경도 잃지 않고 복구된다.

#5한 줄 요약

변경을 미리 WAL에 기록하고 베이스 백업과 그 이후 로그를 함께 보관해, 장애가 나도 원하는 시점의 일관된 상태로 되돌리는 것

서버가 죽어도 서비스를 이어가도록 여러 대의 PostgreSQL을 복제·동기화하고 읽기 부하를 분산하는 구조를 설명한다.

#1문제 상황

PostgreSQL 서버 한 대만 띄워 두면 그 서버가 멈추거나 디스크가 고장 나는 순간 서비스 전체가 멈춘다. 데이터는 한 곳에만 있으므로 DB가 복구될 때까지 애플리케이션은 아무 요청도 처리하지 못한다.

동시에 사용자가 늘어 조회 요청이 몰리면, 쓰기와 읽기가 같은 서버의 같은 자원을 두고 경쟁한다. 결국 읽기 트래픽이 쓰기 성능까지 끌어내려 전체 응답이 느려진다. 서버 한 대로는 장애 대응과 부하 분산을 동시에 해결할 수 없다.

#2핵심 질문

서버 한 대가 죽어도 서비스를 이어가고 읽기 부하를 나눠 받으려면, 여러 PostgreSQL 인스턴스를 어떻게 함께 동작시켜야 하는가?

#3동작 예시

쓰기를 받는 주 서버(Primary) 한 대와, 그 서버의 변경 내용을 계속 복사받는 대기 서버(Standby) 한 대를 둔다. 대기 서버는 받은 변경을 자기 데이터에 계속 재적용하며 주 서버와 같은 상태를 유지한다.

평상시 애플리케이션은 쓰기를 주 서버로, 읽기를 대기 서버로 보내 부하를 나눈다. 주 서버가 멈추면 대기 서버를 주 서버로 승격해 이어받게 하고, 복구된 서버는 다시 대기 역할로 붙인다.

#4동작 과정

  1. 변경 스트리밍주 서버가 모든 데이터 변경을 WAL(미리 쓰기 로그, 데이터를 바꾸기 전에 기록해 두는 변경 일지)로 남긴다. 이 로그를 대기 서버가 실시간으로 전송받아, 같은 변경을 순서대로 자기 데이터에 적용한다.
  2. 읽기 분산대기 서버가 주 서버와 같은 데이터를 가지면 읽기 전용 질의를 받을 수 있다. 핫 스탠바이(Hot Standby, 대기 서버에서 읽기 질의를 허용하는 상태)를 켜면 조회 트래픽을 대기 서버로 돌려 주 서버의 부담이 줄어든다.
  3. 승격과 전환주 서버에 장애가 나면 대기 서버를 주 서버로 승격(failover, 장애 시 역할을 넘기는 것)한다. 서비스가 중단 시간을 최소화하며 새 주 서버로 이어지고, 복구된 서버를 새 대기로 재구성한다.

#5한 줄 요약

주 서버의 변경을 대기 서버로 계속 복제해 두었다가 장애 시 역할을 넘기고 읽기를 분산함으로써, 서버 한 대의 한계를 여러 대의 협력으로 넘어서는 것

데이터베이스 활동 모니터링

현재 실행 중인 쿼리, 잠금, 통계 뷰 등을 조회해 데이터베이스가 지금 무엇을 하고 있는지 관찰하는 방법이다.

#1문제 상황

데이터베이스가 느려졌을 때 서버에 접속해 로그만 보면, 지금 어떤 쿼리가 돌고 있는지, 어떤 잠금 때문에 대기 중인지 알 수 없다. 문제를 겪는 시점과 원인을 확인하는 시점이 어긋나면 재현도 어렵다.

또한 테이블과 인덱스가 얼마나 읽히고 쓰이는지, 디스크 입출력이 어디에 몰리는지 같은 누적 상태를 알 방법이 없으면, 어디를 손봐야 할지 판단할 근거가 없다. 운영 중인 DB에서는 문제가 터진 뒤에만 원인을 추측하게 된다.

#2핵심 질문

데이터베이스가 지금 무엇을 하고 있고 지금까지 무엇을 해 왔는지, 서버 안에서 직접 확인하려면 어떻게 해야 하는가?

#3동작 예시

pg_stat_activity 뷰를 조회하면 현재 연결된 세션마다 실행 중인 쿼리, 시작 시각, 대기 중인지 여부가 한눈에 나온다. 여기서 특정 쿼리가 오래 걸리는 것을 발견하고 그 쿼리를 실행한 세션을 확인할 수 있다.

같은 방식으로 pg_stat_all_tables에서는 테이블별로 순차 스캔과 인덱스 스캔이 몇 번 일어났는지 누적 수치를 본다. 값이 계속 쌓이므로 인덱스가 실제로 쓰이는지 여부를 근거로 판단할 수 있다.

#4동작 과정

  1. 통계 수집서버가 세션, 테이블, 인덱스, 입출력 등 각 동작을 실행할 때마다 그 횟수와 시간을 내부 통계로 누적한다. 이 수집은 통계 수집 설정(Statistics Collection Configuration)에 따라 켜지고 조정된다.
  2. 뷰로 노출누적된 통계와 현재 세션 정보를 pg_stat_activity, pg_stat_replication, pg_stat_io 같은 pg_stat_* 뷰로 조회할 수 있게 한다. 사용자는 SQL로 이 뷰들을 질의해 상태를 읽는다.
  3. 원인 판단조회한 값으로 오래 걸리는 쿼리, 잠금 대기, 복제 지연, 입출력 병목을 가려낸다. 그 결과로 쿼리나 설정을 고치고, 다시 뷰를 조회해 개선 여부를 확인한다.

#5한 줄 요약

서버가 스스로 누적한 실행 통계와 현재 세션 정보를 SQL 뷰로 보여 주어, 데이터베이스가 지금 무엇을 하고 있는지 관찰하고 판단할 수 있게 하는 것

논리 복제

WAL의 물리적 복사가 아니라 테이블·행 단위 변경을 발행/구독 방식으로 다른 데이터베이스에 전달하는 복제 방식이다.

→ 04-03 참조

#1문제 상황

물리적 복제는 주 서버의 디스크 내용을 바이트 단위로 그대로 복사하는 방식이라, 복제 대상이 서버 전체이고 두 서버가 사실상 같은 데이터베이스여야 한다. 그래서 특정 테이블 몇 개만, 또는 조건에 맞는 행만 다른 곳으로 보내고 싶어도 할 수 없다.

또한 복제본은 주 서버와 같은 PostgreSQL 버전과 같은 구조를 따라야 하고, 복제본 쪽에서 별도로 데이터를 가공하기도 어렵다. 서로 다른 시스템 사이에 변경분만 골라 전달하거나, 일부 데이터만 부분적으로 동기화하려는 요구는 물리적 복제로 충족되지 않는다.

#2핵심 질문

디스크 복사가 아니라 테이블과 행 단위의 변경만 골라, 다른 데이터베이스로 전달하려면 어떻게 해야 하는가?

#3동작 예시

발행 서버에서 특정 테이블을 담은 발행(Publication)을 하나 만든다. 구독 서버에서는 그 발행을 구독(Subscription)으로 등록한다. 그러면 발행 서버에서 그 테이블에 INSERT, UPDATE, DELETE가 일어날 때마다 변경 내용이 구독 서버로 전달되어 그대로 반영된다.

발행에는 행 필터(Row Filter)를 걸 수 있어, 예를 들어 특정 조건을 만족하는 행만 전달 대상으로 삼을 수 있다. 이렇게 하면 테이블 전체가 아니라 원하는 데이터만 골라 다른 데이터베이스로 흘려보낼 수 있다.

#4동작 과정

  1. 발행 정의발행 서버가 어떤 테이블과 어떤 행을 내보낼지 발행(Publication)으로 지정한다. 이 시점에 구독자가 참조할 복제 식별 기준(Replica Identity, 변경된 행을 찾아내는 키)도 정해진다.
  2. 구독 연결과 초기 동기화구독 서버가 구독(Subscription)을 등록해 발행 서버에 연결한다. 최초 한 번 기존 데이터를 초기 스냅샷(Initial Snapshot)으로 받아 채운 뒤, 이후의 변경을 이어서 받을 준비를 한다.
  3. 변경 전달과 반영이후 발행 서버에서 발생한 행 단위 변경이 구독 서버로 전달되어 순서대로 적용된다. 충돌(Conflicts)이 나면 정해진 규칙에 따라 처리되고, 서로 다른 데이터베이스 사이에서도 선택한 데이터만 동기화된다.

JIT 컴파일과 회귀 테스트

쿼리 실행 중 자주 쓰이는 표현식을 기계어로 컴파일해 속도를 높이는 JIT와, 기능 변경이 기존 동작을 깨지 않았는지 검사하는 회귀 테스트를 다룬다.

#1문제 상황

PostgreSQL은 쿼리를 실행할 때 각 표현식과 연산을 미리 정해진 방식으로 하나씩 해석하며 처리한다. 이 방식은 어떤 쿼리에도 안전하게 적용되지만, 같은 조건 비교나 함수 호출을 수백만 번 반복하는 무거운 쿼리에서는 해석에 드는 비용이 계속 누적된다.

한편 코드를 고쳐 기능을 바꿀 때마다, 그 변경이 기존에 잘 돌던 동작을 조용히 깨뜨릴 수 있다. 변경 하나하나를 사람이 손으로 확인하는 것은 한계가 있고, 눈에 띄지 않는 회귀(기존 동작이 망가지는 것)를 놓치면 나중에야 문제가 드러난다.

#2핵심 질문

같은 작업을 반복하는 무거운 쿼리의 실행 비용을 줄이면서, 동시에 기능 변경이 기존 동작을 깨뜨리지 않았음을 자동으로 확인하려면 어떻게 해야 하는가?

#3동작 예시

JIT(Just-in-Time compilation, 실행 직전에 기계어로 번역하는 것)를 켜면, 자주 실행되는 표현식과 조건이 실행 중에 기계어 코드로 컴파일된다. 인라이닝(Inlining)은 작은 함수 호출을 호출 없이 코드 안에 펼쳐 넣는 최적화로, 반복 호출의 부담을 줄인다. 무거운 쿼리에서 이런 부분이 실제로 빨라진다.

회귀 테스트는 준비된 입력과 그에 대한 기대 출력을 미리 정해 두고, 코드를 바꾼 뒤 실행 결과가 기대와 같은지 자동으로 대조한다. 결과가 다르면 어떤 테스트가 왜 달라졌는지가 드러나, 기존 동작을 깨뜨린 변경을 바로 찾아낸다.

#4동작 과정

  1. JIT 적용 판단쿼리의 예상 비용이 일정 수준을 넘으면 그 쿼리에 JIT를 적용한다. 적용 후 표현식 평가, 조건 비교 같은 연산이 기계어로 번역되어 반복 실행 비용이 줄어든다.
  2. 최적화 수행인라이닝과 최적화(Optimization)로 번역된 코드에서 불필요한 호출과 연산을 덜어 낸다. 그 결과 같은 결과를 내면서 더 적은 작업으로 처리한다.
  3. 회귀 테스트 검증기능을 바꾼 뒤 회귀 테스트가 미리 정한 기대 출력과 실제 출력을 대조한다. 차이가 있으면 그 지점이 보고되어, 기존 동작이 깨졌는지 자동으로 확인된다.

#5한 줄 요약

무거운 쿼리의 반복 연산을 실행 직전에 기계어로 번역해 비용을 줄이고, 기능 변경이 기존 동작을 깨뜨리지 않았는지를 회귀 테스트로 자동 확인하는 것

libpq C 라이브러리

C 프로그램이 PostgreSQL 서버에 접속해 SQL을 보내고 결과를 받도록 해 주는 공식 클라이언트 라이브러리다.

#1문제 상황

C 프로그램에서 PostgreSQL에 직접 연결해 SQL을 보내려면, 네트워크 연결을 열고 인증을 협상하고, 전송 형식에 맞춰 요청과 응답 바이트를 직접 조립하고 해석해야 한다. 이런 저수준 처리에는 프로토콜 세부 규칙이 얽혀 있어 애플리케이션마다 다시 구현하면 오류가 나기 쉽다.

연결이 끊기거나 쿼리가 오래 걸릴 때의 처리, 결과 집합을 하나씩 읽어 오는 방법, 요청 취소 같은 동작도 각각 규칙이 정해져 있다. 이 모든 것을 애플리케이션 코드가 직접 다루면 데이터베이스 접속 로직이 애플리케이션 곳곳에 흩어지고 유지보수가 어려워진다.

#2핵심 질문

C 프로그램이 PostgreSQL 서버 접속과 SQL 실행, 결과 수신을 저수준 프로토콜을 직접 다루지 않고 수행하려면 무엇을 쓰면 되는가?

#3동작 예시

프로그램이 먼저 PQconnectdb에 접속 문자열을 넘겨 서버에 연결하고, 연결이 성공했는지 상태 함수로 확인한다. 그다음 PQexec로 SQL 명령을 보내면, 서버가 돌려준 결과가 PGresult 구조체로 프로그램에 들어온다.

프로그램은 이 결과에서 행과 열 값을 읽어 처리하고, 다 쓰면 PQclear로 결과를 해제한다. 연결 설정 문자열에는 서버 주소, 포트, 사용자 같은 접속 정보를 담고, 파이프라인 모드처럼 여러 요청을 한 번에 흘려보내는 처리도 같은 라이브러리 안에서 제공된다.

#4동작 과정

  1. 연결 수립접속 제어 함수와 연결 문자열(Connection Strings)로 서버에 접속하고 인증을 마친다. 연결 상태 함수로 성공 여부를 확인해, 이후 명령을 보낼 준비가 되었는지 판단한다.
  2. 명령 실행과 결과 수신명령 실행 함수(Main Functions)가 SQL을 전송하고 결과를 PGresult로 받는다. 프로그램은 결과 정보 조회 함수로 행과 열, 값, 영향받은 행 수를 읽어 낸다.
  3. 정리와 종료처리한 결과를 해제하고 연결을 닫는다. 취소 함수로 진행 중인 긴 쿼리를 중단하거나, 파이프라인 모드로 여러 명령을 묶어 보내는 처리도 이 라이브러리 안에서 수행한다.

C 프로그램이 PostgreSQL 서버와의 접속, SQL 전송, 결과 수신을 저수준 프로토콜을 직접 구현하지 않고 공식 라이브러리 호출로 처리하게 해 주는 것

라지 오브젝트

이미지·문서처럼 큰 데이터를 여러 청크로 나눠 서버 안에 저장하고 스트리밍으로 읽고 쓰는 메커니즘이다.

#1문제 상황

일반적인 컬럼 값은 한 행 안에 담기는 크기로 제한되어, 이미지나 문서처럼 큰 데이터를 통째로 한 값에 넣기 어렵다. 큰 데이터를 여러 행으로 쪼개 저장하면 다시 읽을 때 순서와 조각을 애플리케이션이 직접 관리해야 하고, 조회할 때마다 전체를 한꺼번에 메모리에 올려야 하는 부담도 생긴다.

이렇게 되면 파일처럼 앞에서부터 조금씩 읽고 쓰는 처리가 어렵고, 큰 파일을 다루는 애플리케이션마다 저장 방식을 따로 구현하게 된다. 큰 데이터를 서버 안에서 일관되게 다룰 공통된 방법이 없다.

#2핵심 질문

이미지나 문서처럼 큰 데이터를 한 값에 담지 못하는 문제를 피하면서, 서버 안에서 조금씩 이어 읽고 쓰려면 어떻게 해야 하는가?

#3동작 예시

라지 오브젝트(Large Object)는 큰 데이터를 여러 청크로 나누어 특별한 구조에 저장하고, 파일처럼 스트림 방식으로 접근할 수 있게 한다. 프로그램은 먼저 라지 오브젝트를 만들고 디스크의 파일을 그 안으로 가져온다.

이후 라지 오브젝트를 열어 원하는 위치로 이동(seek)하고, 필요한 만큼만 읽거나 쓴다. 다 읽고 나면 닫고 제거한다. 큰 데이터를 한 번에 메모리에 올리지 않고 필요한 부분만 다룰 수 있다.

#4동작 과정

  1. 생성과 가져오기클라이언트 인터페이스로 라지 오브젝트를 만들고, 파일의 내용을 여러 청크로 나누어 서버로 가져와 저장한다. 큰 데이터가 서버 안의 전용 구조에 나뉘어 들어간다.
  2. 스트림 읽기와 쓰기라지 오브젝트를 열어 쓰기 함수로 데이터를 채우고, 읽기 함수로 조금씩 읽는다. seek로 읽기 위치를 옮겨 필요한 구간만 다루므로 전체를 한 번에 올리지 않는다.
  3. 정리와 제거다 쓴 라지 오브젝트의 열린 핸들을 닫고, 더 필요 없으면 제거한다. 서버 측 함수로도 같은 작업을 할 수 있어 큰 데이터가 일관된 방식으로 관리된다.

#5한 줄 요약

큰 데이터를 여러 청크로 나누어 서버 안에 저장하고 스트림 방식으로 조금씩 읽고 쓰게 함으로써, 한 값의 크기 제한을 넘어서는 데이터를 파일처럼 다루게 하는 것

ECPG — C 임베디드 SQL

C 소스 코드 안에 SQL 문을 직접 써 넣으면 전처리기가 이를 libpq 호출로 바꿔 주는 임베디드 SQL 도구다.

#1문제 상황

C 프로그램에서 데이터베이스를 쓰려면 libpq 같은 클라이언트 라이브러리 함수를 직접 호출해야 한다. SQL 문장을 문자열로 만들어 PQexec 같은 함수에 넘기고, 돌아온 결과도 문자열이나 바이너리 형태라 원하는 C 타입으로 손수 변환해야 한다. 쿼리와 C 코드가 문자열 경계로 분리돼 있어 코드가 길어지고, 값을 넘기고 받는 바인딩·타입 변환 코드가 호출마다 반복된다. SQL 문장이 문자열 안에 숨어 있으니 컴파일 시점에는 검증되지 않고 런타임에 가서야 오류가 드러난다.

#2핵심 질문

C 코드 안에 SQL 문을 그대로 써 넣으면, 그 문장을 알아서 안전한 라이브러리 호출로 바꿔 주는 방법은 없을까?

#3동작 예시

C 변수 앞에 콜론을 붙여 SQL 문 안에서 값을 주고받는다. EXEC SQL SELECT name INTO :user_name FROM users WHERE id = :user_id;라고 쓰면, 전처리기 ecpg가 이 문장을 libpq 호출 코드로 바꾸고 결과를 지정한 C 변수에 채워 준다.

#4동작 과정

  1. 전처리ecpg가 .pgc 소스에서 EXEC SQL로 시작하는 문장을 찾아 C 코드와 분리하고, 그 자리를 libpq를 호출하는 C 코드로 바꾼다.
  2. 컴파일·연결변환된 C 코드를 컴파일하고 ecpg 런타임 라이브러리와 연결해 실행 파일을 만든다.
  3. 실행프로그램이 돌 때 SQL 문이 서버로 전달되고, INTO로 지정한 호스트 변수(결과를 담는 C 변수)에 조회 결과가 채워진다.

#5한 줄 요약

C 소스에 SQL을 직접 써 넣으면 전처리기가 그 문장을 libpq 호출로 변환해 주는 임베디드 SQL 도구

정보 스키마

데이터베이스의 테이블·열·권한 등 구조 정보를 표준 SQL 뷰로 조회할 수 있게 제공하는 스키마다.

#1문제 상황

데이터베이스의 테이블·열·권한 같은 구조 정보를 알아내려면 각 제품의 내부 카탈로그 테이블을 직접 조회해야 한다. PostgreSQL이라면 pg_catalog의 고유한 테이블 구조에 의존해야 하고, 그 쿼리는 SQL 표준과 다르다. 그래서 다른 데이터베이스 제품으로 옮기면 구조 조회 쿼리를 제품마다 다시 써야 한다. 구조를 확인하는 코드가 특정 제품에 묶여 이식성이 떨어진다.

#2핵심 질문

데이터베이스 구조 정보를 특정 제품에 묶이지 않는 표준 SQL로 조회할 수는 없을까?

#3동작 예시

SELECT column_name, data_type FROM information_schema.columns WHERE table_name = 'users';처럼 표준 스키마의 뷰를 일반 SELECT로 조회한다. 결과는 열 이름과 데이터 타입이 담긴 행으로 돌아온다.

#4동작 과정

  1. 표준 뷰 제공information_schema가 내부 카탈로그 정보를 표준에서 정의한 형태의 뷰로 노출한다.
  2. 조회사용자가 뷰를 평범한 SELECT 문으로 읽으면 테이블·열·권한 같은 구조 정보가 행으로 나온다.
  3. 필터WHERE 절로 특정 테이블이나 스키마만 골라 필요한 정보만 받는다.

SQL 확장과 트리거(이벤트 트리거 포함)

SQL 함수·연산자·집계 등을 직접 정의해 데이터베이스 기능을 확장하고, 테이블 변경 시 자동 실행되는 트리거(이벤트 트리거 포함)로 동작을 자동화하는 서버 측 프로그래밍 기법.

#1문제 상황

데이터베이스에 기본으로 들어 있는 함수와 타입만으로는 업무 규칙을 표현하기 어렵다. 값이 바뀔 때 지켜야 할 조건을 애플리케이션이 매번 확인하고, 관련된 여러 쿼리를 순서대로 직접 호출해야 한다. 이 규칙을 각 애플리케이션마다 따로 구현하면 한 곳이라도 빠뜨리기 쉽고, 그때마다 데이터 불일치가 생긴다. 로직이 앱 여러 곳에 흩어져 관리도 어려워진다.

#2핵심 질문

업무 로직을 데이터베이스 안에서 직접 정의하고, 데이터가 바뀔 때 자동으로 실행되게 할 수는 없을까?

#3동작 예시

재고 합계를 갱신하는 함수를 CREATE FUNCTION으로 정의한 뒤, 주문 테이블에 CREATE TRIGGER로 연결한다. 주문 테이블에 INSERT가 일어나면 등록해 둔 함수가 자동으로 실행돼 합계가 갱신된다.

#4동작 과정

  1. 함수 정의SQL 함수나 절차적 언어로 새로운 함수·연산자·집계를 만들어 데이터베이스 기능을 확장한다.
  2. 트리거 등록특정 테이블의 INSERT·UPDATE·DELETE, 또는 스키마 변경 같은 이벤트에 실행할 함수를 연결한다.
  3. 자동 실행해당 이벤트가 발생하면 트리거가 발동해 연결된 함수가 실행되고, 애플리케이션이 신경 쓰지 않아도 규칙이 지켜진다.

규칙 시스템

쿼리 실행 시 규칙(rule)에 따라 원래 문장을 다른 문장들로 재작성해 뷰·갱신 등을 처리하는 PostgreSQL의 규칙 시스템.

#1문제 상황

뷰를 조회하면 저장해 둔 SELECT 문이 대신 실행되지만, 뷰에 대한 변경(INSERT·UPDATE·DELETE)을 원본 테이블에 어떻게 반영할지는 저절로 정해지지 않는다. 또 조건에 따라 질의를 다른 문장으로 바꾸고 싶어도 그 분기를 애플리케이션에서 처리해야 한다. 이런 재작성 로직을 앱에 두면 질의를 바꿀 때마다 앱 코드를 고쳐야 하고, 같은 규칙이 여러 클라이언트에 흩어진다.

#2핵심 질문

#3동작 예시

서버 프로그래밍 인터페이스(SPI)

C 함수나 내부 코드에서 SQL을 실행하고 결과 행을 주고받을 수 있게 해 주는 서버 프로그래밍 인터페이스(SPI).

#1문제 상황

C 언어로 작성한 함수가 이미 서버 안에 로드되어 실행되고 있다고 하자. 이 함수가 테이블에서 값을 읽거나 다른 테이블에 값을 쓰려면 SQL을 실행해야 하지만, 일반 클라이언트처럼 연결을 새로 열고 질의를 보내는 방식은 서버 내부 코드에는 맞지 않는다. 서버가 이미 트랜잭션과 스냅샷을 들고 있는데 그 안에서 다시 바깥 연결을 여는 것은 이중 구조가 되고, 이미 열려 있는 트랜잭션과 결과를 주고받을 방법도 없다.

그래서 C 함수가 서버 내부에서 직접 SQL을 실행하고 그 결과 행을 받아 쓸 수 있는 별도의 통로가 필요해진다. 이것이 없으면 서버 내부 코드는 데이터베이스에 접근할 수 없어 제 기능을 못 한다.

#2핵심 질문

서버 안에서 도는 C 함수가 별도 연결 없이 SQL을 실행하고 결과 행을 받아오려면 무엇이 필요한가?

#3동작 예시

C 함수가 SPI_connect로 SPI 관리자에 연결한 뒤, SPI_execute("INSERT INTO t VALUES (1)", ...)를 호출하면 서버 내부에서 그 SQL이 바로 실행된다. 실행 후 결과 행 개수는 전역 변수 SPI_processed에 담기고, SELECT였다면 SPI_tuptable에 결과 튜플(행 묶음)이 들어온다. 클라이언트와 서버 사이의 네트워크 왕복 없이, 지금 열려 있는 트랜잭션 컨텍스트 그대로 SQL이 처리되고 그 결과가 C 변수로 전달된다. 작업이 끝나면 SPI_finish로 연결을 닫는다.

#4동작 과정

  1. 연결C 함수가 SPI_connect를 호출해 SPI 관리자(서버 내부에서 SQL 실행을 중개하는 계층)에 연결한다. 이때부터 현재 트랜잭션 안에서 SQL을 실행할 수 있는 상태가 된다.
  2. 실행SPI_execute나 SPI_prepare로 SQL을 넘겨 실행한다. SPI_prepare는 문장을 미리 준비만 해 두고, SPI_execute_with_args처럼 인자를 밖에서 넘기는 함수는 반복 실행에 유리하다. 결과 행 수와 튜플 테이블이 전역 변수로 돌아온다.
  3. 정리SPI_finish를 호출해 SPI 관리자와의 연결을 끊고 자원을 반납한다. 이로써 C 함수는 SQL 실행 결과를 확보한 채 서버 프로세스로 복귀한다.

서버가 WAL 파일 보관과 OAuth 토큰 검증 같은 외부 작업을 안정적으로 위임하고 그 결과를 신뢰하려면 어떤 구조가 필요한가?

#3동작 예시

archive_library를 커스텀 모듈로 설정하면, PostgreSQL은 완료된 WAL 파일을 그 모듈에 넘기고 모듈이 성공적으로 보관했다고 알릴 때까지 해당 파일을 재활용하거나 지우지 않는다. 모듈은 초기화 함수로 시작해 시작·확인·보관·종료 콜백을 차례로 호출받으며, 각 WAL 파일을 어떻게 처리할지는 모듈이 정한다. OAuth 검증 모듈도 같은 구조로, 서버가 클라이언트의 토큰을 검증 모듈에 넘겨 유효 여부를 판단하게 한다.

#4동작 과정

  1. 초기화서버가 아카이브 모듈의 초기화 함수를 호출해 모듈을 준비시킨다. 이로써 서버는 어느 라이브러리가 보관 작업을 맡을지 알게 된다.
  2. 콜백 실행WAL 파일이 완료될 때마다 서버가 보관 콜백을 호출하고, 모듈은 파일을 보관한 뒤 성공 여부를 돌려준다. 성공 응답을 받기 전까지 서버는 그 파일을 지우지 않는다.
  3. 종료·검증작업이 끝나면 종료 콜백으로 자원을 정리한다. OAuth 검증 모듈은 같은 콜백 구조로 토큰을 검사해 인증 결과를 서버에 돌려준다.

서버가 WAL 보관과 OAuth 검증 같은 외부 작업을 정해진 콜백으로 모듈에 위임하고 그 결과를 신뢰해 처리하게 해 주는 것

레퍼런스07-01

SQL 명령어 레퍼런스

CREATE, SELECT, INSERT 등 PostgreSQL이 지원하는 모든 SQL 문의 문법과 옵션을 명령별로 정리한 공식 레퍼런스다.

#1문제 상황

개발자가 CREATE, SELECT, INSERT 같은 SQL 문을 쓰다가 문법과 옵션이 헷갈리면 여러 출처를 뒤지게 된다. 블로그나 예전 글은 버전에 따라 달라진 문법을 담고 있을 수 있어, 그대로 따라 했다가 오류를 만나거나 원하는 동작을 얻지 못한다. 어떤 명령이 어떤 옵션을 받고 어떤 표준과 호환되는지 한 곳에서 확인할 수 없다는 점이 문제다.

특히 명령마다 문법 형태와 허용 옵션이 제각각이라, 각 명령의 정확한 사용법을 버전에 맞게 확인할 단일 기준이 필요하다. 이 기준이 없으면 시행착오로 시간을 낭비하게 된다.

#2핵심 질문

PostgreSQL이 지원하는 모든 SQL 명령의 문법과 옵션을 버전에 맞게 정확히 확인할 단일 기준은 어디에 있는가?

#3동작 예시

SQL 명령어 레퍼런스는 ABORT부터 시작해 ALTER, CREATE, SELECT 등 모든 명령을 하나씩 나열한다. 각 명령마다 전용 페이지가 있어 그 명령의 문법, 파라미터, 예제, 그리고 표준 준수 여부와 호환성 정보를 담는다. 예를 들어 ALTER DATABASE 항목은 데이터베이스를 변경하는 명령의 문법과 옵션을 정리하고, ALTER DEFAULT PRIVILEGES 항목은 기본 접근 권한을 정의하는 방법을 설명한다. 개발자는 필요한 명령의 페이지를 찾아 그 버전에 맞는 정확한 사용법을 바로 확인할 수 있다.

#4동작 과정

  1. 명령 나열레퍼런스가 PostgreSQL이 지원하는 모든 SQL 명령을 알파벳 순으로 나열한다. ABORT처럼 트랜잭션을 중단하는 명령부터 ALTER 계열, CREATE 계열까지 빠짐없이 담긴다.
  2. 명령별 상세각 명령은 자신의 전용 페이지로 연결된다. 그 페이지에서 문법, 파라미터, 예제, 표준 준수와 호환성 정보를 확인한다.
  3. 기준 적용개발자가 이 레퍼런스를 기준으로 실제 SQL을 작성하고, 필요하면 전통적인 man 페이지 형태로도 같은 내용을 볼 수 있다.

PostgreSQL이 지원하는 모든 SQL 명령의 문법과 옵션을 명령별 공식 페이지로 정리해 버전에 맞는 정확한 사용법을 확인하게 해 주는 것

클라이언트·서버 애플리케이션 레퍼런스

psql 같은 클라이언트 도구와 postgres·pg_ctl 등 서버 애플리케이션의 사용법과 옵션을 정리한 공식 레퍼런스다.

#1문제 상황

PostgreSQL을 설치한 뒤 psql로 접속하거나 서버를 띄우고 멈추려면 각 도구가 어떤 옵션을 받는지 알아야 한다. 그런데 클라이언트 도구와 서버 애플리케이션은 종류가 많고 옵션 체계가 서로 달라, 필요할 때마다 명령줄 도움말을 하나씩 뒤지면 전체 그림을 잡기 어렵다. 서버를 운영하다 보면 시작·정지·제어 같은 작업을 반복하게 되는데, 그때마다 정확한 옵션을 몰라 헤매게 된다.

SQL 문법을 아는 것과 별개로, 이 도구들을 어떻게 실행하고 어떤 옵션을 주는지 버전에 맞게 정리된 기준이 필요하다. 이 기준이 없으면 실행 단계에서 불필요한 시행착오가 생긴다.

#2핵심 질문

psql 같은 클라이언트 도구와 postgres·pg_ctl 같은 서버 애플리케이션의 사용법과 옵션을 버전에 맞게 어디서 확인하는가?

#3동작 예시

레퍼런스는 SQL 명령어 파트와 나란히 클라이언트 애플리케이션, 서버 애플리케이션 파트를 둔다. 클라이언트 애플리케이션 파트에는 psql처럼 질의를 입력하고 결과를 보는 도구가, 서버 애플리케이션 파트에는 postgres처럼 서버를 직접 실행하거나 pg_ctl처럼 서버를 시작·정지·제어하는 도구가 정리된다. 각 도구는 전용 페이지를 가져 사용법과 옵션을 설명하며, 같은 내용을 전통적인 man 페이지 형태로도 제공한다.

#4동작 과정

  1. 파트 구분레퍼런스가 클라이언트 애플리케이션과 서버 애플리케이션을 각각 별도 파트로 나눈다. 대상에 따라 어느 도구를 봐야 하는지 빠르게 좁힐 수 있다.
  2. 도구별 상세각 도구는 자신의 전용 페이지에서 사용법과 옵션을 설명한다. psql의 접속·실행 옵션부터 서버 제어 도구의 시작·정지 옵션까지 확인한다.
  3. 버전 적용개발자와 운영자가 이 레퍼런스를 기준으로 도구를 실행하고, 필요하면 man 페이지 형태로도 같은 정보를 본다.

psql 같은 클라이언트 도구와 postgres·pg_ctl 같은 서버 애플리케이션의 사용법과 옵션을 도구별 공식 페이지로 정리해 버전에 맞게 확인하게 해 주는 것

내부 구조 개요

PostgreSQL 서버가 클라이언트 연결을 받아 파서·플래너·실행기·스토리지 계층을 거쳐 질의를 처리하는 전체 내부 흐름을 조망하는 장이다.

#1문제 상황

클라이언트가 SELECT 문을 보내면 서버는 결과를 돌려주지만, 그 사이 내부에서 무슨 일이 일어나는지는 겉으로 보이지 않는다. 그래서 질의가 느리거나 예상과 다르게 동작할 때 어느 단계에서 문제가 생겼는지 짐작하기 어렵다. 텍스트로 된 SQL 한 줄이 실제 데이터로 바뀌기까지 파서, 플래너, 실행기, 스토리지 계층을 거친다는 구조를 모르면 원인을 좁힐 수 없다.

튜닝이나 문제 해결을 하려면 이 처리 흐름을 단계별로 파악해야 한다. 연결이 어떻게 맺어지고 질의가 어떤 순서로 처리되는지에 대한 전체 조망이 먼저 필요하다.

#2핵심 질문

클라이언트가 보낸 SQL 한 줄이 파서·플래너·실행기를 거쳐 결과가 되기까지 서버 내부에서는 어떤 순서로 처리되는가?

#3동작 예시

이 장은 하나의 질의가 지나가는 경로를 순서대로 설명한다. 연결이 맺어지는 방식, 파서 단계에서 SQL 텍스트가 해석되는 과정, 규칙 시스템, 플래너/옵티마이저가 가능한 실행 계획들을 만들어 그중 하나를 고르는 과정, 그리고 실행기가 계획을 수행하는 단계가 이어진다. 파서 단계는 다시 파서와 변환 과정으로 나뉘고, 플래너 단계는 가능한 계획 생성으로 세분된다. 이 흐름을 따라가면 SQL 한 줄이 내부에서 어떤 변환을 거치는지 그림이 잡힌다.

#4동작 과정

  1. 연결과 파싱클라이언트 연결이 맺어지고, SQL 텍스트가 파서 단계에서 해석되어 내부 표현으로 바뀐다. 이때 규칙 시스템이 적용될 수 있다.
  2. 계획 수립플래너/옵티마이저가 가능한 실행 계획들을 만들어 그중 하나를 고른다. 같은 질의라도 어떤 계획을 고르느냐에 따라 실제 처리 방식이 달라진다.
  3. 실행실행기가 선택된 계획을 수행해 스토리지 계층의 데이터에 접근하고 결과를 만들어 클라이언트로 돌려준다. 이로써 SQL 한 줄의 처리 여정이 끝난다.

시스템 카탈로그와 시스템 뷰

테이블·컬럼·함수 같은 스키마 정보를 자기 자신이 관리하는 시스템 카탈로그 테이블과, 이를 사람이 읽기 쉽게 노출한 시스템 뷰의 구조를 설명한다.

→ 08-09 참조

#1문제 상황

데이터베이스가 테이블·컬럼·함수 같은 스키마 정보를 어디에도 저장하지 않으면, 그 정보를 관리하는 코드가 직접 파일이나 메모리에 들고 있어야 한다. 테이블 하나를 만들 때마다 그 사실을 별도 자료 구조에 반영하고 서버가 재시작하면 다시 채워 넣는 식이다. 이렇게 하면 스키마 변경과 조회가 코드 경로마다 흩어지고, 사용자가 자기 구조를 직접 확인할 방법도 마땅치 않다.

#2핵심 질문

스키마 정보를 코드가 아니라 데이터베이스 자신이 테이블로 저장하고 조회할 수는 없을까?

#3동작 예시

새 테이블을 만들면 그 정의가 일반 테이블에 행으로 기록된다. 테이블 자체의 정보는 pg_class에, 각 컬럼의 이름·타입·번호는 pg_attribute에 저장된다. 사용자가 이 두 카탈로그를 SELECT로 조회하면 방금 만든 테이블의 구조가 그대로 나온다.

#4동작 과정

  1. 카탈로그에 기록CREATE TABLE 같은 DDL 명령이 실행되면 서버는 그 정의를 시스템 카탈로그 테이블에 행으로 쓴다. 그래서 스키마 정보가 데이터와 같은 저장소에 남는다.
  2. 시스템 뷰로 노출카탈로그 원본은 내부 컬럼과 객체 식별 번호로 가득하다. 사람이 읽기 쉽도록 필요한 컬럼만 골라 이름 붙인 시스템 뷰가 그 위에 얹힌다.
  3. 조회와 재사용사용자나 서버가 시스템 뷰를 SELECT하면 현재 스키마 상태를 얻는다. 파서와 플래너도 이 정보를 참조해 다음 명령을 해석한다.

#5한 줄 요약

스키마 정보를 데이터베이스 자신의 테이블로 저장하고 읽기 쉬운 뷰로 노출해, 서버가 자기 구조를 스스로 관리하고 사용자도 확인할 수 있게 하는 것

프런트엔드/백엔드 프로토콜

클라이언트와 서버가 메시지 스트림으로 통신하며 연결 설정·질의·결과·확장 질의를 주고받는 와이어 프로토콜 규격이다.

#1문제 상황

클라이언트가 서버에 질의를 보내고 결과를 받으려면 양쪽이 같은 형식을 공유해야 한다. 형식이 정해져 있지 않으면 각 클라이언트가 서버 내부 함수를 직접 부르거나, 결과를 어떤 순서로 어떤 타입으로 보낼지 매번 맞춰야 한다. 이러면 서버 구조가 조금만 바뀌어도 모든 클라이언트가 깨진다.

#2핵심 질문

서버 내부 사정과 무관하게 모든 클라이언트가 같은 방식으로 연결하고 질의하고 결과를 받으려면 어떤 통신 규격이 필요할까?

#3동작 예시

psql이 서버에 접속하면 먼저 Start-up 메시지를 보내 사용자 이름과 데이터베이스 이름을 전달한다. 이후 주고받는 모든 메시지는 타입 문자와 길이가 앞에 붙은 스트림 형태다. 예를 들어 SELECT를 보내면 서버는 RowDescription으로 컬럼 정보를, DataRow로 각 행을, CommandComplete로 끝을 알린다.

#4동작 과정

  1. 연결 설정클라이언트가 Start-up 메시지를 보내고 인증을 거쳐 세션을 연다. 이때부터 모든 대화는 정해진 메시지 형식을 따른다.
  2. 질의 전송Simple Query로 SQL 문자열을 통째로 보내거나, Extended Query로 Parse·Bind·Execute를 나눠 보낸다. 후자는 준비된 문을 반복 실행할 때 쓴다.
  3. 결과 수신과 종료서버가 RowDescription·DataRow·CommandComplete 메시지를 순서대로 보내고, 클라이언트는 결과 집합을 조립한다. 작업이 끝나면 Terminate 메시지로 세션을 닫는다.

#5한 줄 요약

클라이언트와 서버가 정해진 메시지 스트림 규격으로만 대화하게 해, 어떤 언어와 도구로 만든 클라이언트든 같은 서버에 붙을 수 있게 하는 것

코딩 관례와 네이티브 언어 지원

PostgreSQL 소스 코드의 서식·명명 규칙과, 다국어 메시지·로케일에 대응하는 네이티브 언어 지원(NLS) 체계를 다룬다.

#1문제 상황

여러 사람이 오랜 기간 같은 서버 소스를 고치면 서식과 명명이 제각각이 되어 읽기 어려워지고, 오류 메시지도 매번 다른 형식으로 나온다. 같은 문제를 가리키는 메시지가 개발자마다 다르게 쓰이면 사용자는 원인을 파악하기 어렵다. 게다가 사용자에게 보이는 문자열이 한 언어로 고정되면 다른 언어를 쓰는 사용자에게 그대로 전달된다.

#2핵심 질문

서로 다른 사람이 만든 코드가 하나처럼 보이게 하고, 오류 메시지와 사용자 표기를 일관된 규칙으로 맞추려면 무엇을 정해야 할까?

#3동작 예시

서버 안에서 오류를 낼 때는 정해진 함수와 오류 수준으로 보고하고, 메시지 문장의 대소문자와 마침표 규칙을 통일한다. 이렇게 하면 psql로 보든 서버 로그로 남든 같은 오류가 같은 모양으로 보인다. 형식 규칙도 한 가지 스타일로 고정해, 변경 사항 비교에서 의미 있는 부분만 드러난다.

#4동작 과정

  1. 서식 통일들여쓰기·중괄호 위치·줄 길이 같은 형식을 한 가지 스타일로 고정한다. 그래야 변경 비교가 의미 있는 수정만 보여주고 리뷰가 빨라진다.
  2. 오류 보고 규칙서버 안에서 오류를 낼 때의 보고 방식과 메시지 문체·대소문자·마침표 규칙을 정한다. 그래서 사용자에게 나가는 메시지가 일관된다.
  3. 네이티브 언어 지원사용자에게 보이는 문자열을 코드에 직접 박지 않고 번역 대상으로 분리한다. 그래서 로케일 설정에 따라 해당 언어 메시지가 나온다.

#5한 줄 요약

소스 서식과 오류 메시지, 사용자 표기 문자열에 공통 규칙을 적용해, 여러 사람이 고쳐도 코드와 메시지가 하나의 일관된 모습을 유지하게 하는 것

확장 인터페이스 — 언어 핸들러와 FDW

새 절차적 언어를 서버에 붙이는 언어 핸들러 작성법과, 외부 데이터 소스를 SQL 테이블처럼 다루게 하는 외부 데이터 래퍼(FDW) 작성법을 설명한다.

#1문제 상황

사용자가 SQL이나 C가 아닌 새 언어로 함수를 쓰고 싶어도 서버는 그 언어의 소스 텍스트를 어떻게 실행할지 모른다. 서버가 지원하지 않는 언어를 붙이려면 실행 엔진 깊숙한 곳을 고쳐야 하고, 그러면 새 언어마다 코어를 수정해야 한다. 외부 데이터 소스도 마찬가지로, 매번 코어에 코드를 넣지 않고는 SQL 테이블처럼 다룰 수 없었다.

#2핵심 질문

서버 코어를 건드리지 않고 새 절차적 언어와 외부 데이터 소스를 기존 SQL 문법에 그대로 붙일 수는 없을까?

#3동작 예시

언어 핸들러는 평범한 C 함수 하나다. 사용자 함수가 호출되면 서버는 그 함수가 선언한 언어의 핸들러를 대신 부른다. 핸들러는 넘겨받은 소스 텍스트를 해석해 실행하고 결과를 돌려준다. 그래서 새 언어마다 코어를 고치는 대신 핸들러 함수 하나를 등록하면 된다.

#4동작 과정

  1. 핸들러 등록새 언어를 지원하려면 version 1 인터페이스를 따르는 C 함수를 작성해 그 언어와 연결한다. 이후 그 언어의 사용자 함수 호출이 이 핸들러로 전달된다.
  2. 호출 위임컴파일 언어의 version 1 인터페이스가 아닌 함수는 모두 해당 언어의 call handler를 거친다. 핸들러가 소스 텍스트 해석 등 실제 실행을 맡는다.
  3. FDW 연결외부 데이터 래퍼는 외부 소스를 SQL 테이블처럼 보이게 하는 루틴 집합을 제공한다. 등록하면 사용자는 일반 테이블과 같은 문법으로 외부 데이터를 조회한다.

#5한 줄 요약

실행 로직을 핸들러와 래퍼라는 교체 가능한 함수 집합으로 분리해, 코어 수정 없이 새 언어와 외부 데이터 소스를 기존 SQL에 붙이게 하는 것

테이블 샘플링과 커스텀 스캔 프로바이더

TABLESAMPLE 방식을 구현하는 샘플링 메서드와, 플래너가 선택할 수 있는 자체 스캔 경로를 제공하는 커스텀 스캔 프로바이더 작성법을 다룬다.

#1문제 상황

큰 테이블에서 전체를 다 읽지 않고 일부 행만 뽑아 보고 싶을 때, 매번 조건을 직접 만들어 거르는 방식은 느리고 결과가 한쪽으로 치우칠 수 있다. 게다가 표준이 요구하는 BERNOULLI·SYSTEM 외의 특별한 추출 방식이 필요하면 사용자가 손댈 방법이 없었다. 플래너도 기본 스캔 경로만 알 뿐 확장 모듈이 제공하는 특수한 스캔 방법을 선택할 수 없었다.

#2핵심 질문

TABLESAMPLE의 추출 방식과 플래너의 스캔 경로를 확장 모듈이 직접 정의해 끼워 넣을 수는 없을까?

#3동작 예시

새 샘플링 메서드는 SQL 함수 하나로 표현된다. 이름이 TABLESAMPLE 절에 쓰이는 메서드 이름과 같고, tsm_handler를 반환하는 시그니처를 가진다. 이 함수는 테이블에서 어떤 행을 고를지 결정하는 핸들러를 돌려주고, 서버는 그 핸들러를 호출해 행을 추출한다.

#4동작 과정

  1. 메서드 정의TABLESAMPLE 절에 쓸 이름으로, internal 인자를 받아 tsm_handler를 반환하는 함수를 만든다. 이 함수가 샘플링 방식의 진입점이 된다.
  2. 행 선택 위임서버는 TABLESAMPLE이 실행될 때 해당 핸들러를 불러 어떤 행을 고를지 결정하게 한다. 그래서 표준 방식 외의 추출도 같은 문법으로 쓸 수 있다.
  3. 스캔 경로 제공커스텀 스캔 프로바이더는 플래너가 선택할 수 있는 자체 스캔 경로를 등록한다. 플래너가 유리하다고 판단하면 그 경로를 실행 계획에 넣는다.

#5한 줄 요약

샘플링 방식과 스캔 경로를 확장 모듈이 정의한 함수와 경로로 등록하게 해, 코어 변경 없이 TABLESAMPLE과 실행 계획을 확장하는 것

GEQO·테이블/인덱스 접근 메서드·확장 WAL

조인 순서 탐색에 유전 알고리즘을 쓰는 GEQO, 테이블·인덱스 접근 메서드 인터페이스, 확장 모듈이 자체 WAL을 기록하는 방법을 묶어 설명한다.

#1문제 상황

조인이 여러 개인 질의에서 가능한 조인 순서는 조인 수가 늘수록 폭발적으로 증가한다. 플래너가 모든 순서를 비교하는 완전 탐색은 조인이 조금만 많아져도 감당할 수 없는 시간이 걸린다. 그래서 최적에 가까운 계획을 현실적인 시간 안에 찾는 다른 방법이 필요하다.

#2핵심 질문

조인 순서의 경우의 수가 너무 많을 때, 모든 조합을 다 따져보지 않고도 쓸 만한 실행 계획을 빠르게 찾을 수는 없을까?

#3동작 예시

조인 수가 임계값을 넘으면 플래너는 GEQO로 전환한다. 여러 조인 순서를 하나의 후보 해로 보고, 여러 후보를 만들어 교차와 변이를 거치며 점점 나은 순서를 고른다. 전부를 비교하지 않고도 비용이 낮은 순서에 수렴한다.

#4동작 과정

  1. 탐색 전환조인 개수가 일정 수를 넘으면 완전 탐색 대신 GEQO가 켜진다. 경우의 수가 감당 불가능해지는 지점에서 탐색 전략을 바꾸는 것이다.
  2. 유전 탐색조인 순서들을 후보 집합으로 두고 교차·변이·선택을 반복해 더 나은 순서를 만든다. 그래서 전수 비교 없이 근사 최적해를 얻는다.
  3. 인터페이스 확장테이블·인덱스 접근 메서드 인터페이스와 확장 WAL이 실행 계층을 확장 모듈이 대체·추가하게 한다. 접근 메서드는 저장 방식을, 확장 WAL은 자체 기록을 담당한다.

#5한 줄 요약

경우의 수가 폭발하는 조인 순서 탐색을 유전 알고리즘으로 근사하고, 접근 메서드와 WAL 같은 실행 계층을 확장 가능하게 열어 두는 것

내부 구조08-08

내장 인덱스 접근 메서드와 물리 저장 구조

B-tree·해시·GiST·SP-GiST·GIN·BRIN 등 내장 인덱스 접근 메서드와, 페이지·파일 세그먼트로 이루어진 데이터베이스 물리 저장 구조를 설명한다.

#1문제 상황

테이블에서 조건에 맞는 행을 찾을 때, 인덱스가 없으면 모든 행을 처음부터 끝까지 읽어야 한다. 데이터가 커질수록 이 전체 스캔은 느려지고, 값 하나를 찾는 데도 테이블 전체를 훑는 비용이 든다.

문제는 모든 검색이 같은 방식으로 빠를 수 없다는 점이다. 값의 대소 비교로 찾는 검색, 같은 값이 몇 번 나오는지 세는 검색, 좌표나 범위처럼 공간적인 검색은 각각 잘 맞는 자료 구조가 다르다. 하나의 정렬 구조만 제공하면 나머지 검색은 다시 느려진다.

또한 인덱스와 테이블 데이터가 실제로 디스크 어디에 어떤 단위로 저장되는지 정해져 있지 않으면, 읽기·쓰기 단위를 예측할 수 없어 성능이 흔들린다. 저장 구조와 접근 방식이 함께 정의되어야 검색 속도를 일관되게 유지할 수 있다.

#2핵심 질문

여러 종류의 검색을 데이터 물리 저장 구조 위에서 각각 빠르게 처리하려면 어떤 인덱스 접근 메서드가 필요한가?

#3동작 예시

B-tree 인덱스를 예로 들면, 정렬된 키 값을 리프 레벨에 순서대로 저장하고 그 위에 상위 레벨을 쌓아 트리를 만든다. 값 하나를 찾으면 루트에서 시작해 각 레벨에서 어느 가지로 내려갈지 비교 한 번으로 정하고, 리프까지 몇 단계 만에 도달해 해당 행의 위치를 얻는다.

반면 여러 값 목록을 담는 배열 컬럼에는 GIN 인덱스를 쓴다. 배열 안의 각 요소를 키로 등록해 두고, 특정 요소를 포함하는 행을 찾을 때 그 요소에 연결된 항목 목록을 바로 꺼낸다. 같은 테이블이라도 검색 종류에 따라 다른 접근 메서드를 붙이는 것이다.

#4동작 과정

  1. 접근 메서드 선택어떤 연산자와 데이터 타입 조합을 지원하는지에 따라 B-tree, Hash, GiST, SP-GiST, GIN, BRIN 중 하나를 인덱스 정의에 지정한다. 이 선택이 어떤 검색을 빠르게 만들지 결정한다.
  2. 물리 저장인덱스와 테이블은 고정 크기 페이지 단위로 저장되고, 큰 객체는 여러 파일 세그먼트로 나뉜다. 각 페이지 안에는 항목들이 채워지며, 이 단위가 디스크 읽기·쓰기의 기본 블록이 된다.
  3. 검색 실행질의가 오면 플래너가 맞는 인덱스를 고르고, 해당 접근 메서드가 페이지를 따라가며 조건에 맞는 항목의 위치를 찾아낸다. 그 결과로 전체 스캔 없이 필요한 행만 읽는다.

검색 종류마다 알맞은 인덱스 접근 메서드를 제공하고 이를 페이지·세그먼트 기반 물리 저장 구조 위에서 동작시켜, 전체 스캔 없이 필요한 데이터를 빠르게 찾는 것

#1문제 상황

또한 데이터베이스는 자신의 테이블·컬럼·타입 같은 구조 정보를 스스로 알고 있어야 한다. 이 정보를 사람이 손으로 채우면 버전마다 틀리고 누락되기 쉽다.

#2핵심 질문

트랜잭션의 경계와 동시성을 관리하면서 시스템 카탈로그 구조를 일관되게 선언·초기화하려면 어떻게 해야 하는가?

#3동작 예시

시스템 카탈로그는 별도의 선언 파일에 컬럼 구조와 초기 행을 정의해 두고, 데이터베이스 초기화 시점에 그 정의를 읽어 카탈로그 테이블을 만들고 내용을 채운다. 구조와 초기값이 한 곳에서 관리되는 것이다.

#4동작 과정

  1. 트랜잭션 식별과 경계트랜잭션이 시작되면 식별자(xid)를 부여받고, 커밋이나 롤백으로 경계가 닫힌다. 그 안의 변경은 확정 전까지 다른 세션에 반영되지 않아 일관성이 유지된다.
  2. 잠금과 하위 트랜잭션·2단계 커밋동시 접근을 조율하기 위해 잠금을 걸고, 하위 트랜잭션(중첩 작업 단위)이나 2단계 커밋(여러 자원에 걸친 확정 절차)으로 복잡한 확정을 다룬다. 실패 지점만 골라 되돌릴 수 있다.
  3. 카탈로그 선언과 초기 채움카탈로그 정의 파일이 테이블 구조와 초기 내용을 선언하고, 초기화 단계에서 이를 읽어 시스템 카탈로그를 구성한다. 구조 정보가 데이터베이스 스스로의 형태로 자리 잡는다.

#1문제 상황

질의를 실행하기 전에 플래너는 어떤 실행 계획이 가장 싼지 골라야 한다. 이때 각 단계가 몇 개의 행을 반환할지 예측하지 못하면 비용 계산의 근거가 없어, 좋지 않은 계획을 고를 수 있다.

예측은 수집된 통계에 의존한다. 통계가 값 분포와 선택도를 충분히 반영하지 못하면 추정이 빗나가고, 그 결과 조인이나 스캔 방식 선택이 어긋나 성능이 나빠진다.

한편 백업 도구가 만든 결과물이 무엇을 담고 있는지 표준 형식으로 남지 않으면, 백업의 내용과 무결성을 다른 도구가 검증하거나 이어받기 어렵다. 백업 산출물의 목록과 검증 정보를 담는 일관된 형식이 필요하다.

#2핵심 질문

#3동작 예시

백업 매니페스트는 백업에 포함된 각 파일의 이름과 크기·체크섬 같은 항목을 나열한 목록 파일이다. 백업을 복원하거나 검증하는 쪽은 이 목록을 읽어 무엇이 담겼고 제대로 전달됐는지 확인한다.

#4동작 과정

  1. 통계 수집각 컬럼의 값 분포, 서로 다른 값 개수, 가장 흔한 값 목록 같은 정보를 수집해 저장한다. 이것이 이후 추정의 원재료가 된다.
  2. 선택도·비용 추정플래너는 이 통계로 조건이 반환할 행 수(선택도)를 어림잡고, 그 추정치로 각 계획의 비용을 계산해 가장 싼 계획을 고른다. 추정이 정확할수록 계획 선택이 좋아진다.
  3. 매니페스트 기록백업 도구는 백업에 포함된 파일 목록과 크기·체크섬 정보를 매니페스트 파일에 기록한다. 이후 검증·복원 도구가 이 형식을 읽어 백업 내용과 무결성을 확인한다.

날짜·시간 값도 입력 표기법이 다양해, 어떤 문자열이 어떻게 해석되는지 규칙이 없으면 같은 입력이 환경에 따라 다르게 받아들여질 수 있다. 특히 애매한 표기는 해석 기준이 분명해야 한다.

#3동작 예시

날짜/시간 입력에서는 문자열을 받아들이는 형식과 해석 규칙이 정해져 있고, SQL 표준이 예약어로 지정한 단어 목록과 그 단어를 식별자로 쓸 수 있는지 여부가 함께 정리되어 있다.

#4동작 과정

  1. 오류 코드 확인서버가 반환하는 오류에는 다섯 글자 코드가 붙고, 앞부분이 오류 종류를 나타낸다. 애플리케이션은 메시지 문장 대신 이 코드로 오류 조건을 판별한다.
  2. 날짜/시간 입력 해석입력된 문자열은 정해진 형식과 규칙에 따라 날짜·시간 값으로 해석된다. 지역 설정과 무관하게 어떤 표기가 어떻게 읽히는지 기준이 제공된다.
  3. 예약어 구분SQL 표준 예약어 목록과 함께 각 단어가 식별자로 허용되는지가 정리되어 있어, 이름 충돌을 피하는 판단 근거가 된다.

#1문제 상황

PostgreSQL이 SQL 표준을 어느 범위까지 지원하는지 분명하지 않으면, 다른 데이터베이스에서 쓰던 SQL을 그대로 옮겨 쓸 수 있는지 판단하기 어렵다. 지원 여부를 실행해 봐야만 아는 상황은 이식 비용을 키운다.

표준에는 있지만 지원하지 않는 기능과, 표준을 넘어서 제공하는 기능이 뒤섞여 있으면 기대와 실제가 어긋난다. 어떤 기능이 표준에 근거한 것인지 구분할 기준이 필요하다.

또 기본 배포에 어떤 부가 모듈과 보조 프로그램이 함께 제공되는지 알지 못하면, 필요한 기능을 직접 만들거나 외부에서 찾아야 한다는 사실조차 놓치게 된다.

#2핵심 질문

PostgreSQL이 SQL 표준을 어디까지 지원하고 기본 배포에 어떤 부가 모듈·프로그램이 포함되는지 어떻게 확인할 수 있는가?

#3동작 예시

SQL 적합성 부록은 지원하는 기능과 지원하지 않는 기능을 나누어, 표준의 어떤 항목이 구현되어 있는지 항목별로 제시한다. 사용자는 옮기려는 SQL이 여기 있는지 확인해 이식 가능성을 가늠한다.

추가 모듈과 프로그램 부록은 기본 배포에 함께 오는 확장 모듈과 보조 실행 프로그램의 목록을 소개한다. 설치 후 어떤 도구와 기능을 바로 쓸 수 있는지 여기서 확인한다.

#4동작 과정

  1. 지원 기능 대조SQL 표준의 기능을 지원 항목과 미지원 항목으로 나누어 제시한다. 옮기려는 SQL이 어느 쪽에 속하는지 대조해 이식 가능성을 판단한다.
  2. 표준 범위 파악XML 관련 질의 제한 같은 구현상 한계를 함께 밝혀, 표준이라도 실제로 어디까지 동작하는지 알 수 있게 한다. 기대와 실제의 간극을 줄인다.
  3. 부가 모듈·프로그램 확인기본 배포에 포함된 확장 모듈과 보조 프로그램을 소개해, 별도로 만들지 않고 바로 쓸 수 있는 범위를 알려준다.

외부 프로젝트·소스 저장소·문서화 가이드

PostgreSQL과 연동되는 외부 프로젝트, 소스 코드 저장소 사용법, 공식 문서를 작성하는 규칙을 다루는 부록이다.

#1문제 상황

PostgreSQL은 하나의 프로그램으로 모든 요구를 감당하기 어렵다. 클라이언트 인터페이스, 관리 도구, 절차적 언어, 확장 기능 같은 필요가 계속 생기는데, 이것을 모두 핵심 프로젝트 안에서 개발하면 관리가 무거워지고 속도가 떨어진다.

또한 소스 코드가 어떤 저장소에서 어떻게 관리되고 변경이 어떻게 받아들여지는지 규칙이 없으면, 외부 기여자가 참여할 방법을 찾기 어렵다. 코드 변경의 흐름이 불투명해지면 기여가 줄어든다.

공식 문서 역시 작성 규칙 없이 아무렇게나 쓰이면 형식이 제각각이 되어 읽기 어려워진다. 문서를 일관되게 만드는 기준이 있어야 품질이 유지된다.

#2핵심 질문

핵심 밖의 기능을 외부 프로젝트로 분리하고, 소스 저장소와 문서 작성 규칙을 정해 기여를 일관되게 받아들이려면 어떻게 해야 하는가?

#3동작 예시

클라이언트 인터페이스, 관리 도구, 절차적 언어, 확장 기능처럼 핵심과 분리해 발전시키는 편이 나은 기능들은 외부 프로젝트로 개발된다. 이렇게 하면 각 기능이 자기 속도로 발전하면서 핵심 프로젝트는 관리 부담을 덜 수 있다.

소스 코드 저장소 부록은 코드가 어디에 있고 어떻게 사용하는지, 문서 부록은 공식 문서를 어떤 규칙으로 작성하는지 설명한다. 기여자는 이 두 안내를 따라 변경을 제출하고 문서를 쓴다.

#4동작 과정

  1. 외부 프로젝트 분리클라이언트 인터페이스·관리 도구·절차적 언어·확장 기능 같은 기능을 핵심과 분리해 별도 프로젝트로 개발한다. 각 기능이 독립적으로 발전하고 핵심은 가벼워진다.
  2. 소스 저장소 사용소스 코드가 위치한 저장소의 사용법을 안내해 기여자가 코드를 받고 변경을 올리는 경로를 알 수 있게 한다. 기여 흐름이 분명해진다.
  3. 문서 작성 규칙 적용공식 문서를 작성하는 규칙을 제시해 작성자가 같은 형식과 관행을 따른다. 문서가 일관되게 유지된다.

핵심 밖 기능을 외부 프로젝트로 분리해 발전시키고, 소스 저장소 사용법과 문서 작성 규칙을 제시해 기여와 문서화가 일관된 흐름을 갖게 하는 것

한계·약어·용어집

PostgreSQL의 각종 한계값과 문서에 쓰인 약어, 주요 용어의 뜻을 정리한 부록이다.

#1문제 상황

PostgreSQL을 쓰다 보면 테이블에 컬럼을 몇 개까지 넣을 수 있는지, 데이터베이스 크기에 상한이 있는지 같은 물음이 나온다. 이런 값을 문서 어디에서도 확인하지 못하면 개발자는 제한이 없다고 가정하거나 경험만으로 어림잡게 된다. 그 결과 스키마를 크게 설계해 두었다가 나중에 컬럼 수나 식별자 길이 같은 지점에서 막히는 일이 생긴다.

#2핵심 질문

PostgreSQL이 분명히 정해 둔 절대 한계와 문서에 쓰인 약어·용어는 어디에서 한눈에 확인할 수 있을까?

#3동작 예시

한 테이블에 컬럼을 계속 추가한다고 하자. 실제로 컬럼은 테이블당 1,600개까지 넣을 수 있지만, 그보다 먼저 튜플 크기가 한 페이지 안에 들어가야 하는 조건에 걸린다. 그래서 컬럼 수를 늘리기 전에 Appendix K의 한계 표를 열어 어느 값이 먼저 막히는지 확인한다.

#4동작 과정

  1. 한계값 확인Appendix K의 한계 표에서 데이터베이스 수(4,294,950,911), 데이터베이스당 관계 수, 관계 크기(기본 BLCKSZ 8192바이트에서 32TB), 테이블당 컬럼 수(1,600)처럼 항목별 상한을 본다.
  2. 약어·용어 해석Appendix L의 약어 목록과 Appendix M의 용어집에서 문서 곳곳에 나오는 줄임말과 주요 용어의 뜻을 확인한다.
  3. 절대 한계와 실제 한계 구분표에 적힌 값은 하드 리밋이고, 성능이나 사용 가능한 디스크 공간 같은 실제 제약이 그 전에 먼저 걸릴 수 있다는 주석을 함께 읽는다.

#1문제 상황

psql 같은 프로그램을 터미널에서 쓰면 결과가 흑백으로만 나와 표와 경고, 오류를 눈으로 구분하기 어렵다. 또 예전 문서를 보고 쓴 명령이 지금 버전에서도 그대로 통하는지, 이름이 바뀌지는 않았는지 판단할 근거가 없으면 오래된 사용법을 그대로 답습하게 된다. 그 결과 잘못된 명령을 계속 쓰거나, 개선된 대체 기능을 놓치게 된다.

#2핵심 질문

콘솔 출력에 색을 어떻게 켜고, 더 이상 권장되지 않거나 이름이 바뀐 기능은 어디에서 확인할까?

#3동작 예시

psql에서 쿼리 결과를 볼 때 색이 적용되면 오류 메시지와 일반 출력이 서로 다른 색으로 표시되어 한눈에 구분된다. 색을 쓸지 여부와 각 요소의 색은 설정으로 정하며, 색이 언제 쓰이는지는 Appendix N에서, 어떤 기능이 바뀌었는지는 폐기·개명 목록에서 확인한다.

#4동작 과정

  1. 색 사용 조건 확인Appendix N의 "When Color is Used"에서 색이 언제 적용되는지 조건을 확인한다.
  2. 색 직접 설정"Configuring the Colors"에서 각 출력 요소의 색을 어떻게 지정하는지 설정한다.
  3. 폐기·개명 확인더 이상 권장되지 않거나 이름이 바뀐 기능 목록을 확인해, 예전 명령을 지금 버전에 맞게 고쳐 쓴다.
