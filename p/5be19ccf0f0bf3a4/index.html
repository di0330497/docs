350-601 DCCOR

Cisco CCNP/CCIE Data Center 필수 시험 350-601 DCCOR(Implementing Cisco Data Center Core Technologies)의 공식 시험 청사진 5개 도메인(Network 25% / Compute 25% / Storage Network 20% / Automation 15% / Security 15%)을 처음 배우는 사람이 위에서 아래로 읽을 수 있게 재배열한 학습 목차. 시험이 특정 제품 하나가 아니라 Nexus/NX-OS, ACI, UCS, MDS, Intersight, Nexus Dashboard를 함께 묻기 때문에 '제품별 문서 목차'가 아니라 '선행 개념 순서'로 묶었다. cisco.com/c/en/us/td 아래 제품 컨피그 가이드는 WebFetch에서 전부 HTTP 403을 반환해 직접 열람하지 못했고, 인벤토리는 공식 시험 토픽 PDF 전문(텍스트 추출 성공)을 1차 근거로 삼았다.

이어서 읽기
1데이터센터와 NX-OS의 출발점이후 모든 항목이 '어떤 장비의 어떤 운영체제에서 무엇을 한다'는 문장이라, 그 장비·OS·토폴로지 어휘를 먼저 세운다.42데이터센터 L2 스위칭과 vPC라우팅·오버레이·UCS 업링크가 모두 L2 포트채널 위에 얹히므로, L2 루프 제어와 vPC를 먼저 이해해야 한다.53데이터센터 L3 라우팅과 멀티캐스트VXLAN 언더레이와 EVPN 컨트롤 플레인이 OSPF·BGP·PIM 위에서 돌기 때문에, 오버레이보다 먼저 와야 한다.44VXLAN EVPN 오버레이L2/L3와 멀티캐스트를 익힌 뒤라야 '터널로 L2를 늘리고 BGP로 학습한다'는 오버레이가 이해된다. ACI 이해의 전제이기도 하다.55Cisco ACIACI는 앞의 파브릭·오버레이를 컨트롤러가 정책으로 추상화한 형태다. VXLAN과 액세스 계층을 알고 봐야 객체 모델이 의미를 갖는다.56UCS 컴퓨트 인프라서버 정책·서비스 프로파일을 만들기 전에 '무엇이 물리적으로 무엇에 연결되는가'와 UCS 관리 평면 진입이 먼저다.67UCS 서비스 프로파일과 Intersight풀·정책·SAN 연결이 준비돼야 서비스 프로파일이라는 '스테이트리스 서버'가 조립된다. Intersight는 같은 모델의 클라우드판이다.58파이버 채널 SAN 파브릭 기초조닝·NPV·FCoE는 전부 FC 주소·로그인·파브릭 초기화 위에서 벌어지는 일이라, 그 밑바닥을 먼저 세운다.69FC 파브릭 서비스, FCoE와 이더넷 스토리지파브릭이 형성된 뒤 '누가 누구와 통신하게 할 것인가'를 정하는 계층. 마지막에 FC를 이더넷에 얹는 FCoE와 IP 스토리지로 확장한다.610자동화와 오케스트레이션앞에서 손으로 만든 구성 대상이 있어야 '그것을 코드로 만든다'가 성립한다. 온박스에서 시작해 오프박스 도구로 넓힌다.1011네트워크·컴퓨트·스토리지 보안보호할 대상(파브릭, 서버, SAN)을 전부 배운 뒤라야 접근 제어와 정책 보안이 '무엇을 어디에 거는지'로 읽힌다.712모니터링·어슈어런스와 수명주기 운영구축과 보안을 마친 시스템을 '보고, 증명하고, 바꾸는' 마지막 계층. 세 도메인의 모니터링·업그레이드 토픽을 한자리에 모은다.5

VLAN·트렁크와 데이터센터 L2 포트 설계

VLAN 은 하나의 물리 스위치를 여러 논리 브로드캐스트 도메인으로 나누는 방식이고, 트렁크(802.1Q)는 여러 VLAN 을 태그로 구분해 한 링크로 함께 실어 나르는 포트다.

#1문제 상황

초기 네트워크에서는 한 스위치의 모든 포트가 같은 브로드캐스트 도메인에 속했다. 이는 보안 분리가 없었고, 브로드캐스트 스톰 시 영향 범위가 커졌으며, 조직 내 여러 부서나 테넌트를 논리적으로 나눌 수 없었다. 대역폭도 모두가 공유하므로 한 부서의 트래픽 폭증이 다른 부서에 영향을 미쳤다.

#2핵심 질문

한 물리 스위치를 독립적인 여러 네트워크로 논리적으로 나누고, 그 여러 네트워크를 하나의 링크로 함께 실을 수 있으려면?

#3동작 예시

스위치의 포트를 VLAN ID 번호로 분류한다. 예를 들어 포트 1-10은 VLAN 10(개발팀), 포트 11-20은 VLAN 20(운영팀)으로 설정하면, 같은 물리 스위치 안에 두 개의 독립 브로드캐스트 도메인이 생긴다. 두 스위치 간 연결 포트는 트렁크로 설정해 VLAN 10·20 프레임을 모두 통과시키되, 프레임에 802.1Q 태그를 붙여 수신 쪽이 어느 VLAN인지 알 수 있게 한다.

#4동작 과정

  1. VLAN 설정스위치 각 포트에 VLAN ID를 할당해, 논리적으로 서로 다른 브로드캐스트 도메인을 만든다. 같은 VLAN 내의 호스트들은 별도 설정 없이 브로드캐스트로 도달할 수 있다.
  2. 트렁크 설정스위치 간 연결 포트는 트렁크(802.1Q)로 설정해, 여러 VLAN의 프레임을 한 링크로 전달하면서 각 프레임에 VLAN 태그를 붙인다. 수신 스위치는 태그를 읽어 어느 VLAN이 받을 프레임인지 구분한다.
  3. 기본 동작같은 VLAN 내 호스트는 브로드캐스트로 도달 가능하고, 다른 VLAN과의 통신은 L3(라우터)을 거쳐야 한다. 각 VLAN은 고유의 subnet을 가진다.

스패닝 트리는 L2 루프를 막기 위해 여분 경로를 차단 상태로 두는 프로토콜이고, BPDU Guard·Root Guard·Bridge Assurance 같은 보호 기능이 잘못된 스위치나 링크로 인한 토폴로지 붕괴를 예방한다.

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

  1. RSTP 동작스위치들이 BPDU를 주고받아 루트 스위치를 선출하고, 각 링크의 역할(루트 포트·지정 포트·백업 포트·대체 포트)을 정한다. 토폴로지 변화가 감지되면 영향받는 포트만 빠르게 재계산해 전체 재수렴을 피한다.
  2. 보호 기능BPDU Guard는 액세스 포트(서버가 붙는 포트)에서 BPDU가 들어오면 그 포트를 즉시 차단하고, Root Guard는 루트 선출 메시지의 이상을 감지해 포트를 차단하며, Bridge Assurance는 예상 없는 토폴로지 변화(링크 미러링 등)를 방지한다.
  3. 토폴로지 수렴수십 초 대기 없이 밀리초 단위로 재수렴하므로, 서비스 단절 시간이 거의 무시할 수 있는 수준이 된다.

#1문제 상황

#3동작 예시

#4동작 과정

  1. 링크 협상LACP(Link Aggregation Control Protocol)는 양단이 포트 채널을 형성할 조건(우선순위, 시스템 ID 등)을 주고받아 합의한다. 조건이 일치해야만 포트가 활성화된다.
  2. 트래픽 분산포트 채널에 들어온 프레임의 출발지·목적지 MAC 주소, 출발지·목적지 IP, 포트 등을 기반으로(해싱 알고리즘) 어느 물리 포트로 보낼지 결정한다. 특정 플로우는 항상 같은 포트로 가므로 패킷 순서가 뒤바뀌지 않는다.
  3. 자동 우회한 포트에 오류가 발생하면 LACP가 감지해 그 포트를 포트 채널에서 제거하고, 그 포트의 트래픽을 다른 활성 포트로 재계산한다.

OSPFv2 와 OSPFv3

링크 상태 정보를 영역(area) 단위로 공유해 최단 경로를 계산하는 내부 라우팅 프로토콜로, OSPFv2 는 IPv4, OSPFv3 는 IPv6(및 IPv4) 용이다.

#1문제 상황

고정 라우팅은 관리자가 손으로 모든 경로를 입력해야 하므로 네트워크가 커지면 관리 부담이 크다. RIP는 간단하지만 최대 15홉 제약이 있고 수렴이 느리다.

#2핵심 질문

자동으로 네트워크 토폴로지를 학습해 최단 경로를 계산하는 프로토콜이 있을까?

#3동작 예시

네 대의 라우터 A-B-C-D가 각 링크에 서로 다른 비용(대역폭이나 지연)을 가지고 연결되어 있을 때, OSPF는 각 라우터가 자신의 링크 정보(Link State)를 영역(area) 내 모든 라우터에 알린다. 그러면 각 라우터가 동일한 토폴로지 정보를 가지고 Dijkstra 알고리즘을 돌려 A→D의 최단 경로를 계산한다. IPv4는 OSPFv2, IPv6는 OSPFv3(또는 IPv4도 지원하는 OSPFv3)를 사용한다.

#4동작 과정

  1. 링크 상태 정보 수집각 라우터가 자신과 연결된 링크의 상태(비용, 인접 라우터)를 LSA(Link State Advertisement)로 작성해 영역 내 이웃들에게 전파한다.
  2. SPF 계산모든 라우터가 동일한 토폴로지 정보를 받으면, 각자 SPF(Shortest Path First) 트리를 계산해 최단 경로를 확정한다.
  3. 라우팅 테이블 갱신계산된 경로로 라우팅 테이블을 채우고, 링크 상태 변화가 발생하면 영역 내에 빠르게 전파되어 수렴한다.

BGP 와 MP-BGP 주소 패밀리

BGP 는 자율 시스템 간 경로를 정책으로 교환하는 프로토콜이고, MP-BGP 는 주소 패밀리(AFI/SAFI)를 추가해 IPv6·VPNv4·L2VPN EVPN 같은 여러 종류의 경로를 한 세션으로 나른다.

#1문제 상황

OSPF는 내부 네트워크(자율 시스템 내)에만 쓴다. 인터넷처럼 서로 다른 자율 시스템(AS)들 사이의 라우팅은 정책 기반 경로 교환이 필요한데, OSPF로는 정책 필터링이 약하다. 또한 IPv4만 지원하거나, 여러 주소 체계(IPv6, VPN)를 각각 따로 관리해야 한다.

#2핵심 질문

자율 시스템 간에 정책으로 경로를 선택해서 주고받고, 여러 주소 체계를 한 세션에서 관리할 수는 없을까?

#3동작 예시

ISP A와 ISP B가 BGP로 피어링한다. ISP A는 "내 고객 네트워크 10.0.0.0/8은 ISP B로 보내지 마"라는 정책을 BGP 필터에 설정하고, ISP B는 "ISP A의 경로는 다른 곳에 재배포하지 마"라는 정책을 적용한다. 이때 MP-BGP를 쓰면, IPv4 경로도 전달하고, VPNv4(고객별 격리 네트워크) 경로도 한 세션에서 전달한다.

#4동작 과정

  1. AS 간 경로 교환BGP 피어 두 개가 UPDATE 메시지를 주고받아, 각자 도달 가능한 네트워크 프리픽스와 경로 특성(AS path, 로컬 선호도 등)을 전달한다.
  2. 정책 기반 경로 선택수신한 경로에 정책(필터, 정책 기반 라우팅)을 적용해, 어떤 경로를 받을지, 어떤 경로를 보낼지 결정한다.
  3. 주소 패밀리 분리MP-BGP의 주소 패밀리(AFI/SAFI)를 이용해 IPv4 유니캐스트, IPv6 유니캐스트, VPNv4, L2VPN EVPN 같은 서로 다른 경로 종류를 구분해 한 세션에서 전달한다.

FHRP: HSRP·VRRP 와 vPC 상호작용

여러 스위치가 하나의 가상 게이트웨이 IP 를 공유해 기본 게이트웨이를 이중화하는 기술이며, vPC 환경에서는 두 피어가 모두 액티브처럼 트래픽을 포워딩한다.

#1문제 상황

한 대의 라우터나 스위치가 기본 게이트웨이로 작동하면, 그 장비가 다운되는 순간 모든 트래픽이 끊긴다. 두 대를 놓아도, 기본 게이트웨이가 고정되어 있으면 한쪽만 트래픽을 받는다.

#2핵심 질문

여러 라우터나 스위치가 하나의 게이트웨이 주소를 공유해, 하나가 다운되면 다른 것이 대체하도록 할 수는 없을까?

#3동작 예시

호스트들이 기본 게이트웨이 IP 192.168.1.254를 입력해 놨는데, 실제로는 스위치 A와 B가 그 주소를 공유하면서 HSRP나 VRRP로 주기적으로 "내가 액티브다"라고 신호를 주고받는다. A가 신호를 보내지 않으면 B가 액티브로 바뀌어 ARP 응답을 대신 한다. vPC 환경에서는 조금 다르게, A와 B가 동시에 액티브처럼 트래픽을 포워딩해 대역폭을 효율적으로 쓴다.

#4동작 과정

  1. 가상 IP 공유여러 피어 스위치가 같은 가상 게이트웨이 IP와 MAC 주소를 설정한다.
  2. 상태 경쟁HSRP/VRRP는 주기적 헬로 메시지로 우선도를 경쟁하는 반면, vPC 환경에서는 peer-link를 통해 합의해 두 피어가 동시에 액티브로 작동한다.
  3. 트래픽 처리호스트에서 온 ARP 요청이나 트래픽은 두 피어가 모두 응답하거나 포워딩해, 스위치 장애에도 투명하게 계속 처리된다.

#5한 줄 요약

여러 스위치가 하나의 가상 게이트웨이 주소를 공유해 기본 게이트웨이를 이중화하며, vPC 환경에서는 두 피어가 동시 액티브로 트래픽을 분산 처리하는 기술

IP 멀티캐스트와 PIM

하나의 패킷을 여러 수신자에게 그룹 주소로 한 번에 전달하는 방식이며, PIM 은 기존 유니캐스트 경로를 이용해 멀티캐스트 배포 트리를 만드는 프로토콜이다.

#1문제 상황

유니캐스트는 한 송신자가 각 수신자마다 별도의 복사본을 보내야 해, 수신자가 많으면 송신자의 부하와 네트워크 대역폭이 급증한다.

#2핵심 질문

한 송신자가 여러 수신자에게 패킷을 한 번만 보내고, 네트워크가 자동으로 필요한 곳에만 복사해 전달할 수는 없을까?

#3동작 예시

스포츠 중계 송신자가 멀티캐스트 주소 224.1.1.1로 패킷을 한 번 보낸다. 이 패킷이 라우터들을 통해 흘러가면서, 각 라우터가 "어느 인터페이스로 수신자가 있는가"를 판단해 필요한 쪽으로만 복사해 보낸다. 수신자는 224.1.1.1 그룹에 가입하면 패킷을 받는다.

#4동작 과정

  1. 그룹 가입수신자(호스트나 장비)가 IGMP(Internet Group Management Protocol)를 통해 멀티캐스트 그룹(예: 224.1.1.1)에 가입한다는 신호를 로컬 라우터에 보낸다.
  2. 배포 트리 구성PIM(Protocol Independent Multicast)이 기존 유니캐스트 라우팅 정보를 이용해 송신자에서 수신자들로 향하는 트리를 구성한다. 공유 트리(RP 중심) 또는 소스 트리(송신자 중심)를 선택한다.
  3. 패킷 포워딩송신자의 패킷이 트리를 따라 내려가면서 각 라우터가 필요한 인터페이스로만 복사해 전달한다.

4VXLAN EVPN 오버레이04-01

오버레이 개념: 언더레이·오버레이, VTEP, VNI

물리 IP 망(언더레이) 위에 가상 L2/L3 망(오버레이)을 얹고, 그 출입구 역할을 하는 스위치가 VTEP, 테넌트 구분 번호가 VNI다.

#1문제 상황

물리 네트워크는 스위칭·라우팅의 토폴로지가 정해져 있다. 테넌트별 격리, 라우팅 정책, 망 확장이 필요하면 물리 장비와 설정을 새로 깔아야 하고, VLAN 수 제약(4094개)과 망 경계의 L2 제약이 있다.

#2핵심 질문

물리 네트워크(데이터센터 코어 라우터·스위치)는 유지하면서, 그 위에 테넌트별 가상 L2/L3 네트워크를 자유롭게 올리고 내릴 수는 없을까?

#3동작 예시

데이터센터의 모든 서버가 연결된 물리 IP 망(언더레이, 보통 L3 기반)이 있고, 그 위에 테넌트 A의 가상 네트워크와 테넌트 B의 가상 네트워크를 각각 따로 구성한다. 각 서버 위의 리프 스위치(또는 하이퍼바이저)가 VTEP(VXLAN Tunnel Endpoint, 터널 출입구) 역할을 해서, 테넌트 A의 VM이 보낸 패킷을 VNI 5000(테넌트 A 구분 번호)으로 캡슐화해 언더레이 IP 망으로 터널링한다. 원격 데이터센터나 다른 리프로 도착하면, VTEP가 캡슐화를 풀어 원래 패킷을 복원한다.

#4동작 과정

  1. 언더레이 구성모든 VTEP 스위치가 IP 라우팅으로 서로 도달 가능하도록 물리 망을 설계해(보통 L3 기반), 언더레이 네트워크를 구성한다.
  2. VXLAN 캡슐화테넌트 VM이나 서버에서 온 패킷이 리프 스위치/VTEP에 도착하면, 테넌트별 VNI를 스탬핑해 VXLAN 헤더로 캡슐화하고, 목적지 VTEP의 IP로 UDP 터널(보통 포트 4789)을 통해 보낸다.
  3. 원격 VTEP 복원원격 VTEP가 패킷을 받으면 VXLAN 헤더를 풀어 원래 이더넷 프레임을 복원하고, 테넌트의 로컬 네트워크(VLAN)로 포워딩한다.

4VXLAN EVPN 오버레이04-02

VXLAN 캡슐화와 데이터 플레인 포워딩

원본 이더넷 프레임을 VXLAN 헤더와 UDP/IP 로 감싸 VTEP 간에 실어 나르는 방식과, 그 패킷이 언더레이에서 전달되는 과정이다.

→ 04-01 참조

#1문제 상황

기존에는 이더넷 프레임이 L2 스위치를 통해 같은 VLAN 내에서만 직접 전송됩니다. 그런데 데이터센터 규모가 커지면 물리적으로 떨어진 여러 장소에 같은 VLAN이 필요해집니다. 하지만 L2 프레임을 L3 네트워크(IP 네트워크) 위에서 그대로 보낼 수는 없습니다. 또한 기존 방식은 MAC 주소 플러딩(broadcasting)에 의존해 규모 확장에 한계가 있습니다.

#2핵심 질문

물리적으로 분산된 데이터센터나 클라우드 환경에서 L3 네트워크 위에 L2 세그먼트를 효율적으로 구성할 수 있는 방법이 있을까요?

#3동작 예시

원본 이더넷 프레임 앞에 VXLAN 헤더를 붙이고, 그 위에 다시 UDP와 IP 헤더를 감싸서 전송합니다. 수신 끝에서는 이 레이어들을 벗겨내 원본 프레임을 복원합니다. 이렇게 하면 일반적인 IP 라우터와 L3 네트워크를 통해 L2 프레임을 터널처럼 실어 나를 수 있습니다.

#4동작 과정

  1. 캡슐화원본 이더넷 프레임이 송신 VTEP(VXLAN Tunnel Endpoint, 터널 양 끝점)에 도착하면, 프레임 앞에 VXLAN 헤더(24비트 VNI, Virtual Network Identifier)를 붙이고, 그 위에 UDP 헤더와 송수신 IP 주소를 추가합니다.
  2. 언더레이 포워딩캡슐화된 패킷은 일반 IP 패킷처럼 물리 라우터들을 통해 목적지 VTEP로 전달됩니다.
  3. 역캡슐화수신 VTEP가 패킷을 받으면 IP/UDP 헤더를 벗겨내고 VXLAN 헤더도 제거해 원본 이더넷 프레임을 복원하고 인터페이스로 내보냅니다.

#5한 줄 요약

BGP EVPN 컨트롤 플레인과 route type

MP-BGP EVPN 이 MAC/IP 와 VTEP 정보를 route type(2·3·5 등)으로 광고해 플러딩 없이 오버레이 경로를 학습하게 하는 제어 평면이다.

#1문제 상황

전통적인 L2 네트워크에서는 MAC 주소를 배우기 위해 브리징 플러딩(flooding)을 사용합니다. 스위치가 도착 포트를 모르면 다른 모든 포트로 브로드캐스트합니다. 이 방식은 로컬 세그먼트에서는 작동하지만, VXLAN 같은 오버레이 환경에서 수천 개의 VTEP 사이에 모든 MAC을 플러딩하려면 불필요한 트래픽이 엄청나고 확장성이 떨어집니다.

#2핵심 질문

대규모 오버레이 네트워크에서 MAC/IP 주소와 VTEP 정보를 플러딩 없이 어떻게 효율적으로 배포할 수 있을까요?

#3동작 예시

VTEP는 로컬에서 학습한 MAC과 IP, 그리고 자신의 위치(VTEP IP)를 BGP의 특수 주소족인 EVPN(Ethernet VPN)으로 광고합니다. 이때 route type 2(MAC/IP 광고)나 type 3(멀티캐스트 그룹 멤버십) 같은 라우트 타입을 사용해 각 정보의 목적을 명확히 구분합니다.

#4동작 과정

  1. 로컬 정보 수집VTEP는 자신에게 연결된 엔드포인트(호스트, VM)로부터 패킷이 도착할 때 출발지 MAC과 IP를 학습합니다.
  2. EVPN 광고학습한 MAC/IP 정보를 MP-BGP(Multiprotocol BGP)를 통해 route type 2로 다른 VTEP들에게 광고합니다. 함께 광고되는 정보는 이 MAC/IP가 어느 VTEP에 있는지입니다.
  3. 포워딩 테이블 구성다른 VTEP가 이 정보를 수신하면 자신의 포워딩 테이블에 항목을 추가해, 특정 MAC/IP로 가는 패킷은 해당 VTEP로 터널링하도록 설정합니다.

#5한 줄 요약

EVPN은 BGP를 제어 평면으로 사용해 MAC/IP 정보를 route type으로 구분해 동적으로 배포하는 오버레이 라우팅 프로토콜입니다.

모든 리프가 동일한 게이트웨이 IP/MAC 을 공유해 어디서든 라우팅하고, L2VNI 는 세그먼트를 L3VNI 는 VRF 를 구분해 테넌트를 격리한다.

→ 04-03 참조

#1문제 상황

기존 방식에서는 라우팅을 위해 한두 개의 중앙 게이트웨이에만 모든 트래픽을 집중시킵니다. 이 구조는 게이트웨이가 병목이 되고, 지연이 발생하며, 게이트웨이 장애 시 전체 트래픽이 영향을 받습니다. 또한 여러 테넌트가 공존할 때 격리(isolation)를 효과적으로 구현하기 어렵습니다.

#2핵심 질문

모든 리프 스위치에서 라우팅을 동시에 처리하면서 테넌트별 트래픽을 어떻게 격리할 수 있을까요?

#3동작 예시

모든 리프 스위치가 동일한 가상 게이트웨이 IP와 MAC 주소를 공유하도록 설정합니다(애니캐스트). 각 리프는 VLAN별로 다른 L2VNI를 사용해 브로드캐스트 도메인을 분리하고, VRF별로 다른 L3VNI를 사용해 라우팅 공간을 분리합니다. 그러면 모든 리프가 라우팅을 할 수 있으면서도 테넌트 데이터는 격리됩니다.

#4동작 과정

  1. 게이트웨이 도달엔드포인트가 다른 서브넷의 대상으로 패킷을 보낼 때, ARP 또는 ND로 게이트웨이의 MAC을 요청하면 모든 리프가 동일한 가상 게이트웨이 MAC으로 응답합니다.
  2. 분산 라우팅그 패킷이 어느 리프에 도착하든 그 리프가 L3 룩업을 수행하고 다음 홉을 결정합니다. L3VNI는 각 VRF별 라우팅 테이블을 독립적으로 유지하므로 테넌트 간 격리가 유지됩니다.
  3. VNI 전환같은 VLAN 내의 트래픽은 L2VNI로 포워딩되고, 다른 VLAN으로 가는 트래픽은 L3VNI로 포워딩되며, 각 단계에서 테넌트/VRF 정보를 유지합니다.

VXLAN 파브릭의 패킷 흐름과 외부 연결

파브릭 내부 동서 트래픽의 경로와, 보더 리프/보더 게이트웨이를 통해 외부망·다른 사이트로 나가는 남북 트래픽 흐름이다.

→ 04-04 참조

#1문제 상황

VXLAN 파브릭 내부에서만 트래픽이 흐르면 유한합니다. 실무에서는 외부 네트워크(인터넷, 다른 데이터센터, 온프레미스 시스템)와 통신해야 합니다. 하지만 외부 네트워크는 VXLAN을 모르므로, 파브릭의 테넌트 트래픽이 외부로 나갈 때 캡슐화를 벗기고, 외부에서 들어온 패킷은 캡슐화해야 합니다.

#2핵심 질문

VXLAN 파브릭 내 트래픽(동서)과 외부로의 트래픽(남북)이 각각 어떻게 경로를 통과할까요?

#3동작 예시

파브릭 내 같은 오버레이 네트워크에 속한 엔드포인트들 사이의 트래픽은 분산 게이트웨이를 거쳐 L2VNI/L3VNI로 터널링됩니다. 외부 네트워크로 나가는 패킷은 보더 리프(border leaf) 또는 보더 게이트웨이라는 특수 엣지 노드를 통과해야 하는데, 이 노드가 VXLAN 캡슐화를 벗기고 외부 프로토콜(MPLS, BGP 등)로 포워딩합니다.

#4동작 과정

  1. 동서 트래픽 (E-W)같은 VNI 내 엔드포인트 간 트래픽은 리프가 직접 L2 포워딩하거나, 다른 VLAN에 있으면 분산 게이트웨이에서 L3 라우팅해 L3VNI 터널로 전달합니다.
  2. 남북 트래픽 출발 (N-S Egress)외부 네트워크로 나가는 패킷이 보더 리프에 도착하면, VXLAN 캡슐화를 제거하고 패킷의 출발지/목적지 IP를 기반으로 외부 라우팅 프로토콜(BGP, 정적 라우트 등)에 따라 포워딩합니다.
  3. 남북 트래픽 진입 (N-S Ingress)외부에서 들어온 패킷이 보더 리프에 도착하면, 목적지 IP를 기반으로 어느 테넌트/VRF에 속하는지 판단하고, 적절한 L3VNI로 캡슐화해 파브릭 내부로 라우팅합니다.

#5한 줄 요약

VXLAN 파브릭은 파브릭 내 동서 트래픽은 분산 게이트웨이와 L3VNI로 처리하고, 외부 연결 남북 트래픽은 보더 리프/보더 게이트웨이를 통해 캡슐화 변환을 거쳐 처리합니다.

ACI 액세스 정책 체인

서버가 붙는 리프 포트를 쓰려면 VLAN Pool→도메인→AEP→Interface Policy Group→Interface/Switch Profile로 이어지는 액세스 정책 체인을 만들어 논리 EPG와 물리 포트를 연결해야 한다.

→ 05-02 참조

#1문제 상황

논리 모델(EPG, Contract)로 애플리케이션 정책을 정의했어도, 실제 서버는 리프 스위치의 물리 포트에 연결됩니다. 이 두 계층 사이를 연결해야 하는데, 전통적 방식은 포트마다 VLAN을 개별 설정해 이 작업이 복잡하고 오류가 많습니다.

#2핵심 질문

논리적 EPG와 물리 포트를 체계적으로 연결할 수 있는 방법이 있을까요?

#3동작 예시

ACI는 VLAN Pool → Physical Domain → Attachable Access Entity Profile(AEP) → Interface Policy Group → Interface Profile/Switch Profile 이라는 다섯 단계의 액세스 정책 체인으로 논리와 물리를 연결합니다. 각 단계에서 사용 가능한 VLAN, 포트의 동작 방식, 특정 포트 그룹 등을 정의해 나갑니다.

#4동작 과정

  1. VLAN Pool과 Domain 설정먼저 사용할 VLAN 범위를 VLAN Pool로 정의하고, 이 VLAN들이 물리 네트워크에서 어떻게 동작할지를 Physical Domain으로 묶습니다.
  2. AEP와 Interface Policy GroupAEP(액세스 포트가 수행할 기본 동작 규칙)를 정의하고, Interface Policy Group에서 포트 속도, 흐름 제어, MTU 같은 세부 설정을 합니다. 이 정책 그룹을 도메인과 연결합니다.
  3. Interface/Switch Profile로 포트 할당Interface Profile에서 구체적인 포트(예: 리프 101의 포트 1/1~1/8)를 선택하고, Switch Profile에서 어느 리프 스위치에 이 정책을 적용할지를 지정하면, 서버가 연결된 포트가 적절한 VLAN/EPG로 자동 구성됩니다.

#5한 줄 요약

ACI 액세스 정책 체인은 VLAN Pool부터 포트까지의 다섯 단계 계층으로 논리 EPG를 물리 포트에 매핑하는 정책 프레임워크입니다.

5Cisco ACI05-04

VMM 도메인과 가상화 통합

VMM 도메인은 APIC가 vCenter 같은 하이퍼바이저 관리자와 연동해 EPG를 포트그룹으로 자동 생성·배포하게 하는 가상화 통합 기능이다.

→ 05-03 참조

#1문제 상황

APIC(ACI 컨트롤러)와 vCenter(또는 다른 하이퍼바이저 관리 플랫폼)가 분리된 상태에서, 네트워크 관리자가 APIC에서 EPG(End Point Group)를 수동으로 만든 뒤 vCenter의 포트그룹 설정과 일일이 맞춰야 합니다. 이 과정에서 동기화 오류가 발생하거나 네트워크 정책이 실제 가상화 환경과 맞지 않을 수 있습니다.

#2핵심 질문

APIC가 vCenter 같은 하이퍼바이저 관리자와 연동해서 포트그룹이 자동으로 ACI의 EPG가 될 수 있을까요?

#3동작 예시

APIC에 VMM 도메인 객체로 vCenter의 접속 정보를 등록하면, APIC가 vCenter의 API를 통해 포트그룹 목록을 지속적으로 감시합니다. vCenter에서 새 포트그룹이 만들어지거나 변경되면 APIC가 실시간으로 인지해 대응하는 EPG를 자동 생성·업데이트하고, 그 포트그룹에 속한 VM들이 APIC의 정책을 즉시 적용받습니다.

#4동작 과정

  1. VMM 도메인 등록관리자가 APIC의 VMMDomain 객체에 vCenter의 접속 자격증명과 연결 정보를 입력하면 APIC-vCenter 간 통신 채널 수립
  2. 포트그룹 감시 및 EPG 자동 생성APIC가 vCenter API를 폴링하거나 콜백을 받아 포트그룹 상태를 모니터링하고, 신규 또는 변경된 포트그룹에 대해 자동으로 대응하는 EPG 객체를 APIC 데이터 모델에 생성
  3. 정책 자동 적용포트그룹에 속한 VM의 MAC/IP가 발견되면 APIC 리프 스위치가 해당 EPG의 보안 정책·QoS·접근제어를 즉시 적용

#5한 줄 요약

VMM 도메인과 가상화 통합APIC와 vCenter 같은 하이퍼바이저 관리 플랫폼을 API로 연동해 포트그룹의 생성·변경을 자동으로 감지하고 EPG로 매핑한 뒤 네트워크 정책을 실시간으로 동기화하는 기능

ACI 엔드포인트 학습·포워딩과 외부 연결

ACI는 COOP 데이터베이스에 엔드포인트를 등록해 VXLAN으로 파브릭 내부를 포워딩하고, L3Out/L2Out으로 외부 네트워크와 연결한다.

#1문제 상황

일반 L2/L3 네트워크에서 MAC 주소 학습은 주로 플러딩(flooding)으로 이루어지고, 라우팅은 동적 경로 프로토콜에 의존합니다. 엔드포인트(호스트) 정보가 네트워크 곳곳에 분산되어 있어 중앙에서 추적·제어가 어렵고, 외부 네트워크와의 연결도 별도의 복잡한 구성이 필요합니다.

#2핵심 질문

ACI 파브릭이 모든 엔드포인트의 위치를 중앙에서 알고 있다가 VXLAN으로 파브릭 내부를 포워딩하면서 동시에 L3Out/L2Out으로 외부 네트워크와도 연결할 수 있을까요?

#3동작 예시

리프 스위치가 서버나 VM의 MAC/IP를 처음 발견하면 그 정보를 COOP(Cluster Objcet Oriented Policy) 중앙 데이터베이스에 등록하고, 다른 리프들이 그 정보를 쿼리할 수 있게 합니다. 다른 리프에 있는 엔드포인트로 가는 트래픽은 VXLAN 터널로 자동 캡슐화되어 전달되며, 외부 네트워크 향 트래픽은 L3Out/L2Out 객체가 정한 경계에서 처리됩니다.

#4동작 과정

  1. 엔드포인트 학습리프 스위치가 연결된 포트에서 MAC 프레임이나 ARP/ND를 수신하면 출발지 MAC/IP와 포트 정보를 로컬 메모리에 기록한 뒤 APIC(또는 COOP 데이터베이스)에 보고하고, 모든 리프가 이 정보에 접근 가능
  2. VXLAN 파브릭 포워딩목적지 엔드포인트가 다른 리프에 등록되어 있으면 송출 리프는 원본 L2 프레임을 VXLAN(Virtual Extensible LAN·L2 패킷을 L4 UDP로 캡슐화하는 프로토콜)으로 감싸서 목적지 리프의 VTEP(VXLAN Tunnel End Point)로 터널링
  3. 외부 네트워크 연결L3Out(외부 라우터와의 BGP/OSPF 연동) 또는 L2Out(레이어2 연장)을 통해 파브릭 경계에서 외부 서브넷으로의 트래픽을 APIC 정책에 따라 라우팅 또는 포워딩

#5한 줄 요약

ACI 엔드포인트 학습·포워딩과 외부 연결COOP 중앙 데이터베이스로 모든 엔드포인트를 추적하고, VXLAN 터널로 파브릭 내부의 분산된 리프 간 포워딩을 투명하게 처리한 뒤, L3Out/L2Out으로 외부 네트워크 경계를 명확히 제어하는 메커니즘

UCS 구성요소 - 랙 서버, 블레이드 섀시, X-Series, FI

UCS는 C-Series 랙 서버, B-Series 블레이드 섀시, 차세대 X-Series 모듈형 시스템을 Fabric Interconnect(FI)라는 단일 관리·전달 지점에 묶어 운영하는 통합 컴퓨팅 시스템이다.

#1문제 상황

기존 데이터센터는 서버(랙마운트 또는 블레이드)를 스토리지, 네트워크 스위치와 분리해서 각각 독립적으로 관리합니다. 서버별 관리 인터페이스가 다르고, 네트워크 설정과 전원 정책을 일관되게 배포하기 어려우며, 확장이나 문제 해결 시 여러 관리 도구를 오갈 수밖에 없습니다.

#2핵심 질문

다양한 형태의 서버(랙·블레이드·모듈)를 단 하나의 통합 관리 플랫폼에서 네트워크, 전원, 정책을 함께 제어할 수 있을까요?

#3동작 예시

Cisco UCS는 C-Series 랙 서버, B-Series 블레이드 섀시, 최신 X-Series 모듈형 시스템을 모두 Fabric Interconnect(FI)라는 중앙 관리 스위치에 연결합니다. FI에 연결된 모든 서버·섀시·포트가 UCS Manager라는 단일 관리 인터페이스에서 보이고, 템플릿 기반 정책으로 전체 컴퓨팅 자원을 일괄 구성·배포합니다.

#4동작 과정

  1. 물리 아키텍처C-Series(표준 랙마운트형)·B-Series(고밀도 블레이드 섀시)·X-Series(차세대 모듈형) 등 다양한 폼팩터의 서버들을 데이터센터 랙에 설치한 뒤 네트워크·전원 케이블을 FI에 연결
  2. 단일 관리 진입점UCS Manager(웹 UI 또는 CLI) 또는 Intersight 클라우드 관리 콘솔에 접속하면 FI를 통해 모든 섀시·슬롯·서버의 하드웨어 상태, 전원, BIOS, 부팅 순서, 네트워크 카드를 일관되게 조회·제어
  3. 정책 기반 배포서버 프로필(profile), 네트워크 정책, 부팅 정책, RAID 설정 등을 템플릿으로 정의한 뒤 여러 서버에 일괄 적용하거나 한 번에 업데이트

UCS 구성요소Fabric Interconnect를 중심으로 C-Series·B-Series·X-Series 등 다양한 서버 폼팩터를 하나의 통합 컴퓨팅 시스템으로 묶어 단일 관리 인터페이스에서 전체 자원의 전원, 네트워크, 정책을 일관되게 제어하는 것

C-Series 단독 운영과 CIMC

C-Series 랙 서버는 FI에 물리지 않고 단독(standalone)으로도 쓸 수 있으며, 이때 서버 내장 관리 컨트롤러인 CIMC의 웹/IPMI/Redfish 인터페이스로 전원·BIOS·RAID·KVM을 관리한다.

#1문제 상황

C-Series 랙 서버는 FI(Fabric Interconnect)에 연결해서 UCS Manager로 관리하는 것이 기본이지만, 어떤 환경에서는 FI 연결 없이 단독으로 운영해야 할 수도 있습니다. 단독 운영 시 서버의 전원, BIOS, 디스크 RAID, 원격 콘솔 같은 중요한 관리 기능을 수행할 방법이 필요합니다.

#2핵심 질문

C-Series 랙 서버가 Fabric Interconnect 없이 단독으로도 전원·BIOS·RAID·원격 관리를 할 수 있을까요?

#3동작 예시

각 C-Series 서버에는 CIMC(Cisco Integrated Management Controller)라는 작은 내장 마이크로컨트롤러가 있어서 서버의 마더보드와 독립적으로 작동합니다. CIMC는 서버의 전용 관리 이더넷 포트(LOM·Light On Motherboard)로 네트워크에 연결되어 웹 UI, SSH CLI, Redfish REST API 등으로 서버 전원, BIOS, RAID, 온도·팬 모니터링, 원격 콘솔(KVM)을 제어할 수 있습니다.

#4동작 과정

  1. 네트워크 연결C-Series 서버의 후면 패널에 있는 전용 관리 포트(보통 별도의 RJ45)를 LAN에 연결하거나, 마더보드 LOM이 있으면 그것을 활용해 CIMC 관리 트래픽을 라우팅
  2. 접속 방식 선택웹 브라우저로 CIMC IP에 접속하거나, SSH로 CLI에 진입하거나, Redfish API 클라이언트로 프로그래밍 방식 제어 중 선택
  3. 하드웨어 제어 수행전원 온/오프, BIOS 설정 변경, 디스크 핫스왑·RAID 생성, 원격 콘솔 오픈(KVM over IP), 펌웨어 업그레이드, 센서 모니터링 등을 개별 서버 단위로 직접 실행

#5한 줄 요약

C-Series 단독 운영과 CIMC서버에 내장된 독립적인 관리 마이크로컨트롤러(CIMC)로 FI 없이도 서버의 하드웨어 전원·구성·모니터링·원격 접근을 직접 제어할 수 있게 하는 것

FI 초기 셋업, 클러스터와 UCS Manager 진입

FI를 콘솔 초기 설정 마법사로 구성해 두 대를 L1/L2로 묶은 HA 클러스터와 가상 IP를 만들고, 그 VIP로 UCS Manager GUI/CLI에 접속해 도메인 전체를 관리한다.

Fabric Interconnect는 공장 기본값으로 출고되어 IP 주소, 관리자 계정, 클러스터 설정이 전혀 없는 상태입니다. 직렬 콘솔 케이블로 연결해야만 첫 설정을 시작할 수 있고, 이 과정 없이는 UCS Manager에 접근할 수 없어 어떤 서버도 관리할 수 없습니다.

#2핵심 질문

두 대의 Fabric Interconnect를 초기 설정으로 자동 클러스터화하고 가상 IP를 만들어 UCS Manager 단일 진입점을 제공할 수 있을까요?

#3동작 예시

직렬 콘솔 케이블로 두 대의 FI(A와 B)에 각각 접속 후 초기 설정 마법사(setup wizard)에서 호스트명, 관리 IP, 게이트웨이 등을 입력합니다. 그러면 한 FI는 Primary(L1), 다른 하나는 Secondary(L2) 역할로 자동 설정되고, 두 FI 사이의 클러스터 포트가 활성화되어 하트비트와 설정 동기화를 시작합니다. 클러스터 형성이 완료되면 가상 IP(VIP)가 자동 생성되고, 이 VIP로 UCS Manager에 접속할 수 있게 됩니다.

#4동작 과정

  1. 직렬 콘솔 접속 및 초기화FI-A의 콘솔 포트에 연결해 setup wizard 시작 후 호스트명, 관리 IP, 게이트웨이, DNS 입력 완료. 동일하게 FI-B도 구성 (단, IP는 다르게 할당)
  2. 클러스터 형성FI-A를 Primary(L1), FI-B를 Secondary(L2)로 지정하면 두 FI 사이의 전용 클러스터 포트를 통해 자동으로 HA 클러스터 상태 동기화 및 관리 데이터 복제 시작
  3. VIP 생성 및 UCS Manager 접속클러스터링이 완료되면 자동으로 가상 IP(VIP)가 할당되고, 이 VIP 또는 Primary FI IP로 웹 브라우저·CLI를 통해 UCS Manager에 진입해 도메인 전체(모든 서버, 섀시, 정책) 관리 시작

UCS LAN 연결: end-host 모드, VLAN, 핀닝, vNIC

FI는 기본적으로 end-host 모드로 동작해 STP 없이 서버 vNIC 트래픽을 업링크에 핀닝하며, VLAN과 vNIC 정의로 서버의 논리 네트워크 연결을 만든다.

→ 05-01 참조

#1문제 상황

일반 이더넷 스위치는 보통 "스위치 모드"에서 동작해 포트 간의 루프를 막기 위해 STP(Spanning Tree Protocol)를 실행합니다. STP는 루프 방지에는 효과적이지만 수렴 지연, 포트 차단, 대역폭 낭비 같은 문제를 야기하고, 데이터센터에서는 성능과 복잡성 면에서 불이익입니다.

#2핵심 질문

Fabric Interconnect가 STP 없이 서버 트래픽을 직접 업링크로 포워딩하고 VLAN과 가상 NIC(vNIC)로 논리 네트워크를 구성할 수 있을까요?

#3동작 예시

FI를 "end-host mode"로 구성하면 STP를 비활성화하고, 모든 서버 포트를 개별 호스트 엔드포인트로 취급합니다. 각 서버의 가상 NIC(vNIC)는 특정 VLAN에 할당되고, 그 vNIC의 트래픽은 고정된 업링크 포트(port pinning)로 직접 전송되어, 루프나 포트 차단 없이 빠르고 예측 가능한 경로로 외부 네트워크에 도달합니다.

#4동작 과정

  1. End-Host 모드 활성화UCS Manager에서 FI의 LAN 모드를 "End-Host Mode"로 설정하면 FI가 일반 스위치처럼 포트 간 포워딩을 하지 않고, 서버 포트의 트래픽을 바로 업링크로 단방향 전송하는 모드로 전환. STP는 자동으로 비활성화
  2. VLAN 정의 및 vNIC 생성관리자가 UCS Manager에서 VLAN(가상 LAN·논리적 네트워크 세그먼트)을 정의한 후, 서버 프로필 또는 개별 서버의 vNIC(가상 네트워크 카드)를 특정 VLAN에 연결. 각 vNIC는 고유한 MAC 주소를 받음
  3. 포트 핀닝과 트래픽 전달각 vNIC의 이그레스 트래픽이 사전 구성된 특정 업링크 포트(pinning)로 고정되어 전송되므로, 루프나 수렴 지연 없이 결정적이고 빠른 경로로 외부 스위치/라우터에 연결되고, 인그레스 트래픽도 업링크로부터 해당 서버 포트에 직접 전달

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 풀에서 아이디 예약UUID, MAC, WWN을 미리 풀(저장소)에 준비해두고 서버 배포 시 자동으로 할당받는다.

SAN은 서버(이니시에이터)가 네트워크 너머의 디스크 장치(타깃)가 노출한 논리 볼륨(LUN)을 마치 로컬 디스크처럼 블록 단위로 읽고 쓰게 해주는 전용 스토리지 네트워크다.

일반적으로 서버는 로컬 디스크(IDE, SATA, SAS)를 직접 물려 블록 단위로 읽고 쓴다. 하지만 로컬 디스크는 그 서버에만 연결되어 있어서 다른 서버와 공유할 수 없다. 여러 서버가 같은 스토리지를 사용하려면 공유 스토리지가 필요하다.

#2핵심 질문

네트워크 너머의 원격 스토리지를 마치 로컬 디스크처럼 블록 레벨에서 읽고 쓸 수 있을까?

#3동작 예시

서버(이니시에이터)가 FC 네트워크를 통해 스토리지 장치(타깃)에 연결된다. 타깃은 자신의 디스크를 여러 개의 LUN(Logical Unit Number, 논리 볼륨)으로 분할해서 노출한다. 서버는 조닝 규칙에 따라 허용된 LUN을 발견하고, 그걸 로컬 디스크처럼 마운트해서 블록 단위의 읽고 쓰기를 수행한다.

#4동작 과정

  1. FC 네트워크로 접속 확립이니시에이터(서버의 HBA)가 FC 스위치를 통해 타깃(스토리지)에 연결되고 SCSI 프로토콜 기반의 통신이 시작된다.
  2. LUN 발견 및 할당타깃이 LUN 목록을 이니시에이터에 노출하고, 조닝(접근 제어) 규칙에 따라 이니시에이터가 액세스 가능한 LUN만 발견한다.
  3. 블록 레벨 I/O 실행서버는 LUN을 로컬 디스크로 인식해 파일시스템을 만들고, 모든 읽고 쓰기를 FC 네트워크를 통해 스토리지로 전달한다.

FC 프로토콜 계층과 주소 체계: WWN, FCID

파이버 채널은 FC-0~FC-4 계층으로 나뉘며, 장비마다 영구 고유 이름인 WWN을 갖고 파브릭 로그인 시 라우팅에 쓰이는 24비트 주소 FCID를 할당받는다.

→ 08-04 참조

#1문제 상황

기존 이더넷에서 장치는 MAC 주소(고정, 네트워크마다 같음)로 식별되고, IP 주소(할당받음)로 라우팅된다. 파이버 채널 네트워크도 비슷한 방식이 필요한데, 이더넷과 달리 물리·링크·네트워크·프로토콜·애플리케이션 계층이 명확하게 분리되어 있어서 각 계층이 서로 다른 방식으로 주소를 지정해야 한다는 문제가 있다.

#2핵심 질문

파이버 채널 장비는 평생 갖는 고유 이름과, 파브릭 접속할 때마다 받는 동적 주소를 어떻게 다르게 관리할까?

#3동작 예시

서버가 처음 스토리지 네트워크에 접속하면, 서버의 파이버 채널 카드는 출장지에서 정부 발급 신분증(WWN)을 들고 가서 공항 보안(FC 스위치)에 등록하고, 그때마다 입국 번호표(FCID)를 받는다. 신분증은 영구적이고 고유하지만, 번호표는 접속할 때마다 새로 받고, 나라를 떠나면 반납된다.

#4동작 과정

  1. FC-0~FC-4 계층 정의FC 프로토콜은 물리 케이블(FC-0)에서 애플리케이션(FC-4, SCSI 등)까지 5개 계층으로 나뉘고, 각 계층은 그 계층에서 필요한 주소 지정과 제어를 담당한다.
  2. WWN 할당모든 FC 포트(포트는 통신 끝점)는 제조 단계에서 WWN(World Wide Name, 전 세계 고유 이름)을 받는다. 이 주소는 장비를 바꾸기 전까지 절대 바뀌지 않는다.
  3. FCID 동적 할당포트가 파브릭(FC 스위치 네트워크)에 로그인할 때, 스위치가 24비트 주소인 FCID를 할당한다. 이 주소는 라우팅에 사용되고, 로그아웃하면 회수된다.

FC 포트 타입과 링크·노드 로그인

FC 포트는 역할에 따라 N/F/E/TE/NP/TF 등으로 나뉘고, 링크가 올라오면 FLOGI(파브릭 로그인)·PLOGI(노드 로그인)·PRLI(프로세스 로그인) 순서로 통신 준비를 마친다.

→ 08-02 참조

#1문제 상황

이더넷에서는 케이블만 꽂으면 포트가 켜지지만, 파이버 채널은 포트마다 역할이 정해져 있다. N 포트는 서버, F 포트는 스위치와 연결되는 식인데, 역할이 맞지 않으면 통신이 안 된다. 또한 이더넷은 케이블이 올라오면 바로 데이터를 주고받지만, 파이버 채널은 장비가 파브릭에 "여기 있습니다" 등록하고 통신 준비를 거쳐야 한다는 복잡함이 있다.

#2핵심 질문

파이버 채널에서 물리 케이블이 올라왔을 때, 서버와 스위치가 통신 준비를 어떤 순서로 거쳐야 할까?

#3동작 예시

포트는 역할(N/F/E/TE/NP/TF)이 정해진 것이고, 링크가 올라오면 세 가지 "로그인" 단계를 거친다. 먼저 FLOGI(Fabric Login)로 스위치가 "너는 파브릭에 속하니?"를 묻고, 다음 PLOGI(Port Login)로 포트끼리 "우리 연결할 거니?"를 확인하고, 마지막 PRLI(Process Login)로 SCSI 같은 상위 프로토콜이 "나랑 데이터 주고받을 준비 됐니?"라고 확인한다.

#4동작 과정

  1. 포트 타입 설정N 포트(노드, 보통 서버), F 포트(패브릭, 스위치 다운링크), E 포트(익스팬션, 스위치 간), TE 포트(트렁크 포트로 여러 VSAN 실음), NP 포트(노드 포트인데 패스스루), TF 포트(트렁크 F 포트) 등 역할에 따라 포트가 나뉜다.
  2. FLOGI 수행서버가 스위치에 로그인 프레임을 보내면, 스위치가 FCID를 부여하고 FLOGI 응답을 되돌려준다. 이 단계에서 파브릭 승인이 난다.
  3. PLOGI, PRLI 순차 진행그 다음 포트-대-포트 로그인(PLOGI)을 거쳐 포트 간 통신 파라미터를 맞추고, 마지막으로 PRLI로 SCSI 같은 상위 프로토콜 준비를 완료하면 데이터 전송 가능 상태가 된다.

#5한 줄 요약

파이버 채널 포트가 역할을 미리 정하고, 링크 올라올 때마다 FLOGI·PLOGI·PRLI 세 단계의 "로그인"을 거침으로써 파브릭 멤버십과 통신 준비를 확인하는 것

스위치 파브릭 초기화: 도메인 ID와 principal switch

여러 FC 스위치가 연결되면 principal switch를 선출하고 각 스위치가 고유한 도메인 ID를 받아 FCID 주소 공간을 나눠 갖는 과정이 파브릭 초기화다.

#1문제 상황

이더넷 스위치 여러 개를 연결하면 스패닝 트리 프로토콜이 자동으로 루프를 제거한다. 하지만 파이버 채널은 각 스위치가 FCID를 나눠 갖는데, 누가 먼저 어떤 범위를 가질지 정하지 않으면 충돌이 난다. 파이버 채널은 분산 시스템이면서도 중앙 조정이 필요한데, 이를 동적으로 선출해야 한다는 복잡함이 있다.

#2핵심 질문

여러 FC 스위치가 연결되었을 때, 누가 주도권을 갖고 각 스위치가 몇 번대의 주소를 쓸지를 어떻게 결정할까?

#3동작 예시

파브릭 초기화 때, 모든 스위치가 자신의 우선순위(priority)를 비교한다. 우선순위가 가장 높은 스위치가 principal switch(주 스위치)로 선출되어, 각 스위치에 도메인 ID(Domain ID, 1~239)를 할당한다. 각 도메인 ID는 FCID의 앞 8비트를 차지하므로, 이 할당이 끝나면 파브릭 내 모든 장비의 주소 공간이 정해진다.

#4동작 과정

  1. 우선순위 비교ISL(스위치 간 링크)로 연결된 스위치들이 각자의 우선순위와 스위치 이름을 주고받으며, 가장 우선순위가 높은 스위치를 principal switch로 선출한다.
  2. 도메인 ID 할당Principal switch가 나머지 스위치에 도메인 ID를 할당한다. 이 ID는 FCID의 앞 8비트(Domain ID:Area ID:Port ID 형태)가 되어, 파브릭 내 라우팅을 가능하게 한다.
  3. 파브릭 안정화모든 스위치가 할당받은 도메인 ID를 받아들이고 저장하면, 파브릭이 안정화되고 VSAN 등 상위 기능이 동작 가능해진다.

#5한 줄 요약

파이버 채널 파브릭에서 principal switch를 동적으로 선출해 각 스위치에 도메인 ID를 할당함으로써, 파브릭 내 모든 주소 공간을 조정하고 라우팅 가능 상태로 만드는 것

VSAN 과 VSAN 트렁킹

VSAN은 하나의 물리 FC 파브릭을 서로 독립된 논리 파브릭으로 나누는 기술이고, 트렁킹(TE 포트)은 한 ISL로 여러 VSAN 트래픽을 함께 실어 나르는 방식이다.

#1문제 상황

파이버 채널 파브릭은 물리적으로 하나인데, 여러 부서나 고객의 스토리지를 연결할 때 서로 보이지 않게 격리해야 한다. 이더넷의 VLAN처럼 분할이 가능하다면, 하나의 파브릭 투자로 여러 독립된 네트워크를 만들 수 있다. 하지만 VLAN과 달리 파이버 채널은 스토리지 전용이고 상태를 많이 관리해야 하므로, 단순 포트 분할로는 부족하다.

#2핵심 질문

하나의 물리 파이버 채널 파브릭을 여러 독립된 논리 파브릭으로 나누면서, 일부 스위치 간에는 같은 VSAN 트래픽을 효율적으로 실을 수 있을까?

#3동작 예시

VSAN(Virtual SAN)은 파이버 채널 파브릭을 가상으로 분할해서, VSAN 1에 속한 서버와 스토리지는 VSAN 2에 속한 장비를 볼 수 없게 한다. 각 VSAN은 독립된 도메인 ID 공간을 가지므로, 같은 도메인 ID를 가진 스위치가 여러 VSAN에서 중복으로 존재할 수 있다. 트렁킹(TE 포트)은 한 ISL로 여러 VSAN 트래픽을 함께 실어 보내는 것으로, ISL 대역폭을 효율적으로 쓸 수 있게 한다.

#4동작 과정

  1. VSAN 생성 및 할당스위치에 VSAN을 정의(예: VSAN 1, VSAN 10)하고, 각 포트를 특정 VSAN에 할당한다. 같은 VSAN에 속한 장비만 통신 가능해진다.
  2. TE 포트 설정ISL에 TE(Trunking E) 포트를 설정하면, 그 ISL 하나로 여러 VSAN 트래픽을 태그(VSAN ID를 프레임에 붙임)를 붙여 함께 전송한다.
  3. VSAN 독립성 유지각 VSAN이 독립된 파브릭처럼 작동하므로, VSAN 1의 principal switch와 VSAN 10의 principal switch가 별개로 선출되고, 도메인 ID도 각각 할당된다.

#5한 줄 요약

물리 파이버 채널 파브릭을 VSAN으로 분할해 테넌트 격리를 이루면서, 트렁킹으로 스위치 간 ISL 대역폭을 공유하는 것

FC 포트 채널

여러 FC ISL을 하나의 논리 링크로 묶어 대역폭을 합치고 한 링크가 끊겨도 파브릭 재구성 없이 트래픽을 유지하는 링크 집성 기술이다.

→ 08-05 참조

#1문제 상황

두 FC 스위치를 ISL 하나로 연결하면, 그 링크가 끊기는 순간 파브릭이 분할되어 principal switch 선출을 다시 해야 하고, 타이밍에 따라 서로 다른 도메인 ID를 할당받을 수 있다. ISL 여러 개를 따로따로 운영하면 대역폭은 늘지만 링크 하나가 끊져도 파브릭이 재구성되는 문제가 그대로다. 스위치 간 연결을 더 견고하고 효율적으로 만들 방법이 필요하다.

#2핵심 질문

여러 FC ISL을 하나의 논리 링크처럼 묶어서, 개별 링크 손실 시에도 파브릭을 유지하면서 대역폭을 합칠 수 있을까?

#3동작 예시

ISL 포트 채널은 2~4개의 물리 ISL을 하나의 논리 포트 채널로 묶는다. 개별 ISL들은 각각 데이터를 실으면서도, 하나가 끊겨도 나머지들이 파브릭을 살려둔다. 이더넷의 LAG(Link Aggregation Group)과 원리는 비슷하지만, 파이버 채널에서는 이것이 파브릭 안정성에 직결된다.

#4동작 과정

  1. 포트 채널 구성스위치 쌍 사이의 ISL 포트(보통 E 포트나 TE 포트)를 같은 포트 채널 그룹 번호로 설정한다. 그러면 여러 포트가 하나의 논리 채널(포트 채널 인터페이스)로 통합된다.
  2. 트래픽 분산 및 보호트래픽이 포트 채널의 여러 물리 포트에 분산되어 대역폭을 합치고, 한 포트가 끊겨도 나머지 포트로 통신을 유지하므로 파브릭 재구성이 일어나지 않는다.
  3. 포트 채널 유지포트 채널 인터페이스의 상태는 모든 멤버 포트의 상태에 따라 결정되며, 모든 멤버가 다운되어야 포트 채널이 다운된다.

#5한 줄 요약

CFS 로 파브릭 설정 분산

CFS(Cisco Fabric Services)는 한 스위치에서 바꾼 설정(device alias, NTP, 조닝 등)을 파브릭 안의 모든 스위치에 자동으로 퍼뜨려 설정을 일치시키는 기능이다.

→ 09-02 참조

#1문제 상황

FC 파브릭에 스위치가 여러 개 있을 때, 한 스위치의 CLI에서 조닝(zoning) 설정을 바꾸어도 이웃 스위치는 모르고 있다. 관리자가 수동으로 각 스위치에 접속해서 같은 설정을 반복해야 하고, 실수로 빼먹으면 파브릭의 일부만 설정이 적용되어 일관성이 깨진다. 파브릭 규모가 커질수록 수동 작업은 불가능해진다.

#2핵심 질문

한 스위치에서 바꾼 설정을 파브릭 안의 모든 스위치에 자동으로 전파할 수 있을까?

#3동작 예시

CFS(Cisco Fabric Services)는 한 스위치에서 device alias, NTP, 시간 설정, 조닝 같은 설정을 바꾸면, 그것을 파브릭의 다른 모든 스위치에 자동으로 전파한다. 이것은 마치 한 컴퓨터가 클라우드 동기화 폴더에 파일을 저장하면, 다른 컴퓨터들이 자동으로 같은 파일을 받는 것처럼 작동한다.

#4동작 과정

  1. 설정 변경 감지관리자가 한 스위치(보통 principal switch)에서 설정(device alias, NTP, 조닝 등)을 바꾼다.

#1문제 상황

#3동작 예시

#4동작 과정

  3. 조닝 및 관리에서 사용조닝 규칙이나 CLI 명령에서 WWN 대신 device alias를 쓸 수 있으므로, 설정이 이해하기 쉽고 유지보수가 간단해진다.

NPV와 NPIV

NPIV 는 한 물리 FC 포트가 여러 개의 FCID(가상 N포트)로 로그인하게 해주고, NPV 는 엣지 스위치를 도메인 ID 없는 프록시로 만들어 코어 스위치에 호스트 로그인을 그대로 전달하게 하는 모드다.

#1문제 상황

FC 스위치는 각각 고유한 Domain ID를 가지고 파브릭을 구성합니다. 파브릭이 커질수록 더 많은 스위치가 필요하고, 각 스위치가 Domain ID를 소비하므로 결국 Domain ID 부족(최대 239개) 문제에 직면하게 됩니다. 또한 한 물리 FC 포트는 하나의 FCID(Fibre Channel ID)로만 로그인할 수 있어서 가상화 환경에서 여러 호스트가 같은 포트를 공유하기 어렵습니다.

#2핵심 질문

FC 스위치 수의 제약 없이 더 많은 호스트를 연결하고, 한 포트에서 여러 호스트를 동시에 지원할 수 있을까요?

#3동작 예시

NPIV(N Port ID Virtualization)는 호스트의 hypervisor가 한 물리 FC 포트로 여러 번 로그인하게 해서, 각 가상 머신이 고유한 FCID를 받도록 합니다. NPV(Fibre Channel Virtual Link Port Mode)는 엣지 스위치가 Domain ID를 갖지 않는 프록시 역할을 하면서, 연결된 호스트의 로그인 요청을 코어 스위치에 그대로 전달합니다.

#4동작 과정

  1. NPIV 로그인Hypervisor가 같은 물리 포트로 여러 번 FLOGI(Fabric Login) 요청을 보내면, 각각 다른 FCID를 할당받습니다.
  2. NPV 프록시 전달NPV 모드의 엣지 스위치는 호스트 로그인을 가로채지 않고 코어 스위치에 그대로 전달하며, 스위치 간 라우팅만 수행합니다.
  3. Domain ID 절약NPV는 엣지 스위치가 Domain ID를 사용하지 않으므로 제한된 Domain ID 풀을 효율적으로 사용하고, NPIV는 물리 포트를 여러 FCID로 나누어 포트 활용도를 높입니다.

#5한 줄 요약

FC 파브릭의 확장성으로, NPIV는 한 포트의 논리 분할을 통해 가상 호스트를 지원하고, NPV는 엣지-코어 스위치 구조로 Domain ID 제약을 우회하는 것

#2핵심 질문

#1문제 상황

접속 포트(호스트가 직접 연결되는 포트)는 기존에 어떤 패킷이든 검사 없이 받습니다. 공격자가 같은 포트에서 위조된 DHCP 응답을 보내거나, ARP를 조작하거나, 다른 IP로 위장해 보내면 그 공격 트래픽이 그대로 네트워크로 통과합니다.

#2핵심 질문

#3동작 예시

First-hop security는 접속 포트에서 세 가지 검사를 조합합니다. DHCP 스누핑은 정당한 DHCP 서버만 응답 허용, ARP Inspection은 존재하는 IP와 MAC 조합만 통과, IP Source Guard는 DHCP로 할당받은 IP와 MAC 쌍만 수용합니다.

#4동작 과정

  1. DHCP 스누핑스위치가 포트에서 오가는 DHCP 패킷을 가로채 신뢰할 수 있는 포트(신뢰 포트, 보통 업링크)에서만 DHCP 응답을 허용하고, 일반 포트에서의 DHCP 응답은 차단합니다.
  2. Dynamic ARP Inspection(DAI)ARP 요청과 응답을 검사해, DHCP 스누핑이 기록한 바인딩 테이블(IP-MAC 매핑)과 일치하는 ARP 패킷만 통과시킵니다.

MACsec 링크 암호화와 제어 평면 보호

MACsec 은 링크 구간 이더넷 프레임을 하드웨어로 암호화하고, CoPP 는 슈퍼바이저 CPU 로 올라오는 제어 트래픽을 속도 제한해 스위치 두뇌를 보호한다.

#1문제 상황

기존 이더넷 링크는 평문으로 프레임을 전송합니다. 같은 스위치 포트나 공유 링크에 접속한 공격자는 트래픽을 도청하거나 변조할 수 있습니다. 또한 스위치의 슈퍼바이저 CPU(스위치를 제어하는 중앙 처리 장치)로 올라오는 제어 트래픽(라우팅 업데이트, SNMP 쿼리 등)이 제한 없이 들어오면 CPU 자원이 고갈되어 스위치가 응답 불가 상태가 될 수 있습니다.

#2핵심 질문

링크 구간의 이더넷 프레임을 암호화해 도청을 방지하고, 스위치 CPU를 과부하로부터 보호할 수 있을까요?

#3동작 예시

MACsec은 두 인접 장비 간에 사전 협상된 키로 이더넷 프레임 자체를 암호화해 링크 도청과 변조를 방지합니다. CoPP(Control Plane Policing)는 CPU로 올라오는 제어 트래픽의 종류별 허용 속도를 정의해, 그 한계를 초과하는 트래픽은 폐기함으로써 CPU 과부하를 방지합니다.

#4동작 과정

  1. MACsec 암호화두 스위치 간에 키 교환을 통해 암호화 키를 공유한 후, 송신 측이 이더넷 프레임을 그 키로 암호화하고 수신 측이 복호화함으로써 링크 도청과 변조를 방지합니다.
  2. CoPP 정책 설정관리자가 스위치 CPU로 올라올 트래픽 종류(라우팅 프로토콜 헬로, SNMP, SSH, DHCP 등)마다 허용 대역폭(초당 패킷 수 또는 바이트 수)을 정의합니다.
  3. 제어 트래픽 필터링정의된 대역폭을 초과하는 제어 트래픽 패킷은 폐기하고, 정상 범위 내의 트래픽만 CPU에서 처리하도록 해 CPU 보호와 스위치의 안정성을 유지합니다.

MACsec으로 링크상 데이터 암호화를 통해 도청과 변조를 차단하고, CoPP로 제어 평면 트래픽의 속도를 제한해 스위치 CPU 리소스를 과부하로부터 방어하는 메커니즘

#2핵심 질문

각 엔드포인트 그룹(EPG) 간 통신을 기본적으로 차단하고, 필요한 경우만 명시적으로 허용할 수 있을까요?

#3동작 예시

#4동작 과정

  1. EPG 정의같은 보안 정책과 라이프사이클을 가진 엔드포인트들(서버, VM, 호스트)을 그룹으로 분류합니다.
  2. 계약 생성어느 EPG가 서비스를 제공(provider)하고 어느 EPG가 소비(consumer)할지 정의해 통신 방향을 명시합니다.
  3. 필터와 규칙 추가계약에 필터를 적용해 프로토콜(TCP, UDP 등), 포트(80, 443 등), 주소 범위 같은 구체적인 조건을 정의하면, 그 조건에 맞는 트래픽만 허용됩니다.

#3동작 예시

UCS는 역할 기반 권한(RBAC, 역할마다 실행 가능한 기능을 다르게 제한)으로 관리 접근을 통제하고, MDS는 AAA로 관리자를 인증한 후, 각 포트에 허용된 WWN(World Wide Name, SAN 장비의 고유 식별자) 목록을 설정하고 vHBA 파브릭 바인딩(서버 HBA와 SAN 포트의 연결 인증)으로 허가된 서버만 SAN에 붙게 합니다.

#1문제 상황

기존에는 네트워크 관리자가 주기적으로 장비에 접속해서 로그를 확인하거나 상태 명령어를 실행해야 했습니다. 이는 문제를 발견하기까지 시간이 오래 걸리고, 야간이나 주말에는 관리자가 대응하지 못한다는 한계가 있습니다. 특히 하드웨어 장애 같은 긴급 상황은 관리자가 직접 알아야 대응이 가능했습니다.

#2핵심 질문

장비의 문제나 상태 변화를 관리자가 직접 확인하지 않고도 자동으로 감지하고 즉시 알릴 수 있을까요?

#3동작 예시

장비에서 발생한 로그나 알림을 서버로 직접 전송하는 방식입니다. syslog 서버에는 모든 이벤트를 문자 메시지로 계속 기록하고, SNMP는 중요한 상황을 즉시 트랩(trap) 알림으로 보내며, Call Home은 하드웨어 이상을 벤더의 지원 시스템에 자동으로 신고합니다.

#4동작 과정

  1. 로그 및 이벤트 생성스위치의 인터페이스 상태 변화, CPU 사용률, 온도, 팬 고장 등 모든 상황이 발생하면 장비 내부에서 로그가 기록됩니다.
  2. 능동적 전송syslog 프로토콜(UDP 기반 로그 전송)로 로그 메시지를 수집 서버로 계속 전송하고, SNMP 트랩은 심각한 사건만 즉시 통보하며, Call Home은 하드웨어 결함을 벤더의 자동 신고 시스템에 알립니다.
  3. 중앙 수집 및 대응모니터링 서버에 모인 로그를 분석해서 패턴을 파악하거나, 트랩 알림이 오면 관리자에게 즉시 통지해 빠른 대응이 가능해집니다.

트래픽 가시성: SPAN, ERSPAN, NetFlow

실제 패킷을 복사해 분석기로 보내거나(SPAN/ERSPAN) 흐름 단위 통계로 요약해(NetFlow) 네트워크에서 무엇이 오가는지 들여다보는 기법이다.

#1문제 상황

기존에는 네트워크를 통과하는 실제 데이터의 흐름을 보기 어려웠습니다. 특정 포트의 트래픽을 분석하려면 포트에 직접 패킷 분석기를 연결해야 했고, 원격지의 트래픽을 분석할 수 없었으며, 네트워크 전체의 트래픽 패턴을 통계로 파악할 방법이 없었습니다.

#2핵심 질문

스위치 포트를 통과하는 실제 트래픽을 어떻게 분석 도구로 가져가서 문제를 찾을 수 있을까요?

#3동작 예시

스위치가 특정 포트의 트래픽을 그대로 또는 요약 형태로 분석 도구에 제공합니다. SPAN은 패킷을 복사해 분석기로 보내고, ERSPAN은 그 복사본을 원격 분석기로 터널링하며, NetFlow는 흐름 통계만 추출해서 경량으로 전송합니다.

#4동작 과정

  1. 트래픽 복사/수집SPAN(Switched Port Analyzer)은 지정된 포트의 모든 패킷을 분석 포트로 복사합니다. ERSPAN(Encapsulated Remote SPAN)은 그 복사본을 터널로 원격지의 분석기로 보냅니다. NetFlow는 패킷 흐름 정보(출발 IP/목적지 IP/프로토콜/포트/트래픽 볼륨)만 추출합니다.
  2. 분석기에서 처리SPAN/ERSPAN으로 받은 패킷들은 상세 분석 도구(IDS, 보안 검사)에서 검사되고, NetFlow 데이터는 수집기에서 요약 통계로 처리됩니다.
  3. 문제 파악비정상 트래픽(악성 연결), 대역폭 낭비(특정 애플리케이션의 과도한 사용), 응용 성능 저하의 원인을 특정할 수 있습니다.

모델 기반 스트리밍 텔레메트리와 네트워크 어슈어런스

YANG 데이터 모델을 기반으로 장비가 상태를 주기적으로 수집기에 밀어 보내고(push), 그 데이터로 의도대로 동작하는지 지속 검증하는 방식이다.

#1문제 상황

기존 모니터링(syslog와 SNMP)은 장비에 문제가 생겼을 때 알림을 보내므로 문제를 뒤늦게 감지합니다. 또한 각 장비 제조사마다 데이터 형식이 다르고, 어떤 상태가 정책과 일치하는지 확인할 수 없었습니다. 네트워크 설정이 관리자의 의도대로 실제로 동작하는지 검증하는 방법이 없었습니다.

#2핵심 질문

모든 장비의 상태 데이터를 표준화된 형식으로 실시간 수집하면서 설정이 의도한 정책대로 동작하는지 자동으로 검증할 수 있을까요?

#3동작 예시

YANG 데이터 모델이라는 표준 방식으로 모든 장비의 상태(인터페이스 정보, 라우팅 테이블, 온도, CPU 등)를 구조화합니다. 장비가 정해진 주기(1초마다 등)로 이 데이터를 수집 시스템에 능동적으로 전송하고, 수집 시스템이 받은 데이터와 기대하는 설정 정책을 비교해 일치하는지 검증합니다.

#4동작 과정

  1. YANG 모델 정의모든 네트워크 장비의 설정과 상태 정보(BGP 라우트, 인터페이스 상태, 서비스 수준 정책 등)를 표준화된 구조화 형식으로 정의합니다.
  2. 스트리밍 텔레메트리 수집각 장비가 지정된 주기로(초 단위) 상태 데이터를 YANG 형식으로 수집 시스템에 능동적으로 전송하므로 실시간 가시성을 얻습니다.
  3. 어슈어런스 검증수집 시스템이 실제 상태 데이터와 관리자가 정의한 의도(의도 기반 네트워킹, Intent-Based Networking)를 비교해서 네트워크가 정책대로 동작하는지 지속적으로 보증합니다.

수명주기 관리: 업그레이드 영향, 설정 관리와 백업

소프트웨어 업그레이드(ISSU 등)의 트래픽 영향 판단, 설정의 저장·복원·백업까지 장비를 도입부터 교체까지 안전하게 운영하는 절차다.

#1문제 상황

기존에 NX-OS를 업그레이드하려면 장비를 재부팅해야 했으므로 트래픽이 중단되었습니다. 잘못된 설정 변경을 되돌릴 방법이 없었고, 장비 장애 시 운영체제나 설정을 복원하기 어려웠습니다. 또한 언제, 누가, 무엇을 변경했는지 추적할 수 없었으므로 문제 원인 파악이 어려웠습니다.

#2핵심 질문

네트워크 서비스를 중단하지 않으면서 안전하게 소프트웨어를 업그레이드하고 설정 변경을 관리할 수 있을까요?

#3동작 예시

ISSU(In-Service Software Upgrade)로 장비의 한쪽 처리 부분을 먼저 업그레이드한 뒤 역할을 전환하는 방식으로 중단 없이 진행하고, 매 변경 시 설정을 백업해서 문제 발생 시 빠르게 롤백합니다.

#4동작 과정

  1. 무중단 업그레이드(ISSU)듀얼 프로세서 구조의 장비는 한쪽 프로세서의 소프트웨어를 먼저 업그레이드한 뒤, 다른 쪽 프로세서로 전환합니다. 전환 동안 데이터 트래픽은 계속 흐르므로 서비스 중단이 없습니다.
  2. 설정 버전 관리변경 전후의 설정을 자동으로 백업하고 타임스탬프 및 변경자 정보를 기록해서 변경 이력을 추적합니다.
  3. 빠른 복구업그레이드 후 예상치 못한 문제가 발생하면 이전 버전의 NX-OS로 즉시 롤백하거나, 설정 백업으로 빠르게 복원할 수 있습니다.
