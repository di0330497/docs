1부. 클라우드 네트워크와 로드 밸런싱 기초001

로드 밸런싱(Load Balancing)

여러 서버에 요청을 나눠 보내는 기본 개념

사용자가 몰리는 시간에 서버 한 대가 모든 요청을 받으면 응답이 눈에 띄게 느려지고, 심하면 서버가 멈춰서 서비스 전체가 마비됩니다. 로드 밸런싱(Load Balancing)은 이런 상황을 막기 위해 여러 서버에 요청을 나눠 보내는 기술입니다. 은행에 창구가 하나뿐이면 손님 줄이 금세 길어지고, 그 창구 직원이 자리를 비우면 업무가 통째로 멈춥니다. 로드 밸런싱은 은행 입구에서 손님을 빈 창구로 안내하는 직원과 같아서, 맨 앞에 선 서버(로드 밸런서, Load Balancer)가 요청을 받아 뒤에 있는 여러 서버 가운데 한 대에게 넘깁니다. 이때 각 창구가 얼마나 바쁜지, 고장 나지는 않았는지를 살펴 가장 여유 있는 곳으로 보내고, 한 창구가 문을 닫으면 나머지 창구로 자동으로 방향을 바꿉니다.

덕분에 손님은 창구가 몇 개인지 몰라도 되고, 창구를 하나 더 열거나 닫아도 줄이 끊기지 않습니다. 정리하면 로드 밸런싱은 클라이언트의 요청을 여러 대의 서버에 분산해 한 대에 부하가 몰리지 않게 하고, 일부 서버가 고장 나도 서비스가 계속되도록 만드는 구조입니다.

L4 로드 밸런싱과 L7 로드 밸런싱

전송 계층과 응용 계층에서 나누는 기준의 차이

웹 서비스가 커져 서버를 여러 대로 늘렸는데 순서대로 돌려 보내기만 하면, 이미지 요청과 로그인 요청이 뒤섞여 비효율이 생깁니다. 이때 요청을 어느 계층에서 들여다보고 나눌지를 정하는 것이 L4 로드 밸런싱과 L7 로드 밸런싱의 차이입니다. 택배 회사로 비유하면 L4는 겉봉투에 적힌 주소만 보고 분류하는 창고 직원과 같아서, IP 주소와 포트 같은 전송 계층(Transport Layer) 정보만으로 연결을 나눕니다. 반면 L7은 봉투를 열어 내용물까지 확인하는 담당자와 같아서, HTTP 주소(URL)나 쿠키처럼 응용 계층(Application Layer)의 내용을 읽고 요청을 구분합니다.

그래서 L7은 이미지 요청만 모아 특정 서버로 보내거나 로그인 요청을 별도 서버로 돌리는 세밀한 분기가 가능하고, L4는 내용을 들여다보지 않아 상대적으로 빠르고 단순합니다. 두 방식은 대체 관계가 아니라 앞단에서 L4로 크게 나누고 뒤에서 L7로 다시 나누는 식으로 함께 쓰이기도 합니다. 결국 L4 로드 밸런싱은 전송 계층의 주소 정보로 연결을 분산하고, L7 로드 밸런싱은 응용 계층의 요청 내용을 해석해 더 세밀하게 분산한다는 점이 두 방식의 핵심 차이입니다.

리버스 프록시(Reverse Proxy)

서버 앞에서 요청을 대신 받아 넘기는 중계자

서버를 인터넷에 그대로 노출하면 접속 폭주와 악의적인 요청을 서버가 혼자 감당해야 하고, 서버의 주소와 내부 구조까지 외부에 드러납니다. 리버스 프록시(Reverse Proxy)는 서버 앞에 서서 요청을 대신 받아 뒤쪽 서버로 넘기는 중계자입니다. 호텔로 비유하면 리버스 프록시는 정문 안내 데스크와 같아서, 손님은 객실이 몇 개인지 몰라도 데스크에만 용건을 말하면 됩니다. 데스크는 손님의 요청을 확인해 해당 업무를 맡은 부서로 전달하고, 답변은 다시 데스크를 거쳐 손님에게 돌아갑니다. 그래서 객실 배치나 부서 구성이 바뀌어도 손님은 알 필요가 없고, 신분 확인이나 출입 제한 같은 통제를 한 지점에서 할 수 있습니다.

실제로는 이런 위치 덕분에 여러 서버로 요청을 나누는 로드 밸런싱, HTTPS 암호화 처리, 캐싱 같은 일을 서버 대신 맡기도 합니다. 정리하면 리버스 프록시는 클라이언트와 서버 사이에서 요청과 응답을 중계하며, 서버를 외부로부터 감추고 공통 처리를 한 지점에 모으는 역할을 합니다.

포워드 프록시와 리버스 프록시

누구를 대신하느냐로 갈리는 두 프록시

사내에서 인터넷을 쓰는데 접속 기록도 남지 않고 직원 PC가 외부에 그대로 노출되는 것이 문제이고, 반대로 서비스 서버를 운영할 때는 서버 앞에서 들어오는 요청을 걸러 줄 무언가가 필요합니다. 이 두 상황에서 서로 다른 쪽을 대신 서는 포워드 프록시(Forward Proxy)와 리버스 프록시(Reverse Proxy)가 쓰입니다. 회사로 비유하면 포워드 프록시는 직원 편에서 외부에 전화를 걸고 받아 주는 비서와 같아서, 직원 대신 나서고 상대방에게는 비서의 번호만 보입니다. 리버스 프록시는 반대로 외부 손님을 맞는 안내 데스크와 같아서, 손님은 회사 내부 부서를 몰라도 데스크를 통해 용건을 전달합니다.

즉 누구를 대신하느냐가 갈림길인데, 포워드 프록시는 클라이언트를 대신하고 리버스 프록시는 서버를 대신합니다. 그래서 포워드 프록시는 사내 접속 통제와 익명성 확보에, 리버스 프록시는 서버 보호와 부하 분산에 주로 쓰입니다. 결국 두 프록시의 차이는 중계자가 어느 쪽 편에 서느냐이며, 포워드 프록시는 클라이언트의 대리인, 리버스 프록시는 서버의 대리인이라고 정리할 수 있습니다.

가상 IP(VIP)와 서비스 엔드포인트

클라이언트가 바라보는 하나의 주소

서버를 여러 대로 늘리면 클라이언트는 어느 주소로 요청을 보내야 할지 몰라 곤란해지고, 서버 한 대가 교체될 때마다 접속 설정을 바꿔야 합니다. 이때 클라이언트가 바라보는 하나의 고정된 주소를 가상 IP(VIP, Virtual IP)라 하고, 그 뒤에서 실제로 요청을 받는 서버들을 서비스 엔드포인트(Service Endpoint)라고 합니다. 콜센터로 비유하면 VIP는 안내문에 적힌 대표 전화번호와 같아서, 고객은 상담원 개개인의 번호를 알 필요가 없습니다. 대표번호로 걸면 교환기가 현재 통화가 가능한 상담원 회선, 즉 엔드포인트 가운데 하나로 연결해 줍니다. 상담원이 퇴근하거나 자리를 바꿔도 대표번호는 그대로여서 고객은 바뀐 것을 눈치채지 못하고, 새 상담원의 회선만 교환기 목록에서 갈아 끼우면 됩니다.

이 목록은 보통 상태 확인(헬스 체크, Health Check)을 거쳐 관리되어 응답하지 않는 회선은 자동으로 빠집니다. 정리하면 VIP는 클라이언트가 고정적으로 바라보는 대표 주소이고, 서비스 엔드포인트는 그 주소 뒤에서 실제 요청을 처리하는 서버들의 목록입니다. 이 둘을 분리해 두면 서버를 늘리거나 교체해도 클라이언트 설정은 그대로 둘 수 있습니다.

← 이전포워드 프록시와 리버스 프록시다음 →상태 비저장(Stateless)과 세션 선호도

1부. 클라우드 네트워크와 로드 밸런싱 기초006

상태 비저장(Stateless)과 세션 선호도

요청을 아무 서버에나 보내도 되는 조건

서버를 여러 대로 나눠 요청을 분산하면, 로그인한 사용자의 정보를 각 서버가 따로 들고 있어서 다음 요청이 다른 서버로 가면 로그인이 풀리는 일이 생깁니다. 상태 비저장(Stateless)과 세션 선호도(Session Affinity)는 이 문제를 서로 다른 방식으로 다루는 두 가지 접근입니다. 병원으로 비유하면 상태 비저장은 환자 기록을 의사 개인의 수첩이 아니라 병원 공용 전산에 두는 방식이라, 어느 진료실로 가도 같은 기록을 바로 꺼내 볼 수 있습니다. 세션 선호도는 반대로 특정 환자를 담당 의사에게 계속 붙여 두는 방식이라, 진료실이 여러 개여도 그 환자의 요청은 늘 같은 의사에게 갑니다.

전자는 서버가 요청마다 필요한 정보를 매번 받아 처리하므로 어느 서버로 보내도 결과가 같고, 그래서 아무 서버에나 자유롭게 분산할 수 있습니다. 후자는 서버가 사용자 상태를 메모리에 들고 있는 경우에 쓰이며, 대신 그 서버가 죽거나 트래픽이 몰리면 다른 서버로 옮겨 가기 어렵다는 제약이 따릅니다. 결국 상태 비저장은 서버가 사용자 상태를 들고 있지 않아 아무 서버에나 요청을 보내도 되는 조건을 말하고, 세션 선호도는 같은 사용자의 요청을 같은 서버로 묶어 보내는 방식입니다.

← 이전가상 IP(VIP)와 서비스 엔드포인트다음 →헬스 체크(Health Check)

1부. 클라우드 네트워크와 로드 밸런싱 기초007

헬스 체크(Health Check)

서버가 살아 있는지 주기적으로 확인하는 방법

서버 여러 대를 뒤에 두고 서비스를 운영할 때, 그중 한 대가 조용히 응답을 멈추면 사용자는 이유도 모른 채 오류 화면을 마주하게 됩니다. Application Gateway 같은 부하 분산 장치가 이런 서버로 계속 요청을 보내면 장애가 눈에 보이기 전까지 번지기 때문에, 서버가 살아 있는지 주기적으로 물어보는 헬스 체크(Health Check)가 필요합니다.

아파트 단지에 비유하면 경비원이 각 동의 소방 설비를 정해진 시간마다 순찰하는 것과 같습니다. 순찰은 문이 잠겨 있는지, 비상등이 켜지는지 같은 정해진 항목을 확인하는 일이고, 응답이 오지 않으면 그 동을 정상으로 보지 않습니다.

순찰 주기와 판정 기준을 미리 정해 두면, 문제가 생긴 동을 사람이 발견하기 전에 시스템이 먼저 알아챕니다. 여기서 정해진 항목을 확인하도록 보내는 요청을 프로브(probe), 결과를 정상과 비정상으로 나누는 판단을 상태 확인이라고 부릅니다.

정리하면 헬스 체크는 서버에 주기적으로 신호를 보내 응답 여부와 상태를 확인하는 장치이며, 부하 분산 장치는 이 결과를 근거로 요청을 보낼 서버를 고릅니다.

1부. 클라우드 네트워크와 로드 밸런싱 기초008

헬스 체크 실패와 서킷 브레이킹

죽은 서버를 목록에서 빼는 판단

헬스 체크가 실패한 서버로도 요청을 계속 보내면, 사용자 요청은 응답 없이 대기하다 시간 초과로 끝나고 정상 서버까지 함께 느려집니다. 그래서 실패를 감지한 뒤 목록에서 빼는 판단과, 뺀 서버를 곧바로 다시 넣지 않고 일정 시간 지켜보는 장치가 함께 필요하며, 이를 서킷 브레이킹(Circuit Breaking)이라고 합니다.

택배 회사에 비유하면 연락이 닿지 않는 기사에게 새 물건을 배정하지 않고 배차 목록에서 빼는 것이 첫 단계입니다. 곧바로 다시 배정하면 같은 실패가 반복되므로, 회사는 몇 분간 배정을 멈추고 상태를 확인한 뒤에 복귀시킵니다.

이렇게 실패가 정해진 횟수를 넘으면 회선을 끊듯 요청을 차단하고, 일정 시간이 지나면 일부만 흘려보내 정상 여부를 다시 확인합니다. 차단된 상태를 열린 상태(open), 회복을 시험하는 상태를 반쯤 열린 상태(half-open)라고 부릅니다.

정리하면 헬스 체크 실패는 서버를 목록에서 빼라는 신호이고, 서킷 브레이킹은 실패한 대상으로 가는 요청을 잠시 끊어 전체 시스템이 무너지지 않게 지키는 안전장치입니다.

수평 확장(Scale Out)

서버 수를 늘려 처리량을 키우는 방식

사용자가 몰리는 시간에 서버 한 대가 버티지 못하면 응답이 느려지고 결국 접속이 끊깁니다. 서버 한 대의 성능을 높이는 대신 서버 수를 늘려 처리량을 키우는 방식이 수평 확장(Scale Out)입니다.

식당에 비유하면 요리사 한 명의 실력을 높이는 대신 주방을 갖춘 지점을 여러 개 두고 손님을 나눠 보내는 것과 같습니다. 손님은 입구에서 어느 지점으로 갈지 안내받고, 각 지점은 같은 메뉴판을 씁니다.

지점이 늘어나도 주문 상태를 각자 따로 들고 있으면 혼선이 생기므로, 세션과 데이터를 공용 저장소에 두는 설계가 함께 필요합니다. 이때 지점을 늘리는 일은 서버를 추가하고 부하 분산 장치의 대상 목록에 넣는 작업으로 이뤄집니다.

정리하면 수평 확장은 서버 대수를 늘려 부하를 나누는 방식이고, 앞단의 부하 분산 장치와 공용 상태 저장소가 함께 갖춰져야 효과가 납니다.

← 이전헬스 체크 실패와 서킷 브레이킹다음 →고가용성(High Availability)과 단일 장애점

1부. 클라우드 네트워크와 로드 밸런싱 기초010

고가용성(High Availability)과 단일 장애점

하나가 죽어도 서비스가 유지되는 구조

구성 요소 중 하나만 멈춰도 서비스 전체가 멈춘다면, 그 하나가 회사에 치명적인 약점이 됩니다. 그 약점을 없애거나 예비를 두어 하나가 죽어도 서비스가 유지되는 구조를 고가용성(High Availability)이라 하고, 그런 약점을 단일 장애점(Single Point of Failure)이라고 부릅니다.

아파트에 비유하면 한 대뿐인 엘리베이터가 멈추면 고층 주민 전체가 계단을 써야 하는 상황과 같습니다. 엘리베이터를 두 대로 늘리면 하나가 점검 중이어도 다른 하나가 사람을 나르며, 두 대가 같은 전원을 쓰면 정전 한 번에 둘 다 멈추므로 전원도 나눠 받아야 합니다.

관리실이 한 곳뿐이면 그 방이 잠기는 순간 단지 전체가 마비되므로, 관리 업무도 여러 곳에서 나눠 볼 수 있어야 합니다. 이렇게 예비를 두는 것만으로는 부족하고, 예비가 정말 따로 동작하는지 주기적으로 확인하는 절차가 붙어야 합니다.

정리하면 고가용성은 같은 역할을 하는 요소를 둘 이상 두고 서로 다른 자원에 얹어, 하나가 죽어도 나머지가 역할을 이어받게 만드는 설계입니다.

← 이전수평 확장(Scale Out)다음 →Azure 가상 네트워크(VNet)

2부. Azure 네트워크 기초011

Azure 가상 네트워크(VNet)

Azure 리소스가 사는 사설 네트워크 공간

클라우드에 서버를 만들었는데 인터넷 어디서든 그 주소로 접근할 수 있다면, 관리용 포트까지 세상에 열려 있는 셈입니다. Azure에서 리소스가 사는 사설 네트워크 공간을 정하고 그 안에서만 통신하게 만드는 것이 가상 네트워크(VNet, Virtual Network)입니다.

회사 사옥에 비유하면 먼저 울타리로 둘러싸인 대지를 정하고 그 안에 주소를 매기는 것과 같습니다. 대지의 주소 범위를 정하면 그 안의 각 리소스가 사설 IP를 받고, 대지 밖에서는 이 주소로 직접 들어올 수 없습니다.

사옥 출입이 정해진 정문을 통해서만 가능하듯, 외부와의 연결도 게이트웨이나 방화벽 같은 출입구를 거치게 됩니다. 대지는 다른 회사 대지와 겹치지 않게 설계해야 하고, 필요하면 다른 대지와 전용선으로 이어 붙일 수 있습니다.

정리하면 VNet은 Azure 리소스에 사설 IP를 부여하고 외부와의 경계를 정하는 논리적 네트워크 단위이며, 주소 범위와 출입 경로를 먼저 설계하는 것이 핵심입니다.

← 이전고가용성(High Availability)과 단일 장애점다음 →서브넷(Subnet)

2부. Azure 네트워크 기초012

서브넷(Subnet)

VNet을 용도별로 쪼갠 구획

VNet 하나에 웹 서버, 데이터베이스, 관리용 서버를 모두 같은 구획에 두면 접근 규칙을 하나로만 정해야 해서 한 곳이 뚫리면 전부 위험해집니다. 그래서 VNet을 용도별로 쪼개는 구획인 서브넷(Subnet)을 두고, 구획마다 접근 규칙을 따로 겁니다.

사무실 건물에 비유하면 한 층을 통으로 쓰지 않고 회의실, 전산실, 창고로 벽을 세워 나누는 것과 같습니다. 층마다 출입 카드 권한을 다르게 주면 전산실은 담당자만 들어가고, 창고는 누구나 드나들 수 있습니다.

벽을 세울 때는 각 방의 크기를 미리 정해야 하고, 나중에 방을 늘릴 여유 공간을 남겨 두어야 합니다. 서브넷도 같은 원리로 주소 범위를 나누고, 서브넷 사이의 통신은 네트워크 보안 그룹 같은 규칙으로 통제합니다.

정리하면 서브넷은 VNet의 주소 범위를 용도별로 나눈 구획이고, 구획마다 별도의 접근 규칙을 적용해 피해 범위를 좁히는 장치입니다.

← 이전Azure 가상 네트워크(VNet)다음 →서브넷 위임(Subnet Delegation)

2부. Azure 네트워크 기초013

서브넷 위임(Subnet Delegation)

특정 서비스에 서브넷을 전용으로 맡기는 표시

가상 네트워크(Virtual Network) 안에 서브넷(Subnet, 주소 범위를 나눠 놓은 구획)을 만들어 두고 그 위에 데이터베이스 같은 관리형 서비스를 올리려 하면, 서비스가 자기 몫의 주소를 스스로 잡을 권한이 없어 배포가 중간에 멈춰 버립니다. 서브넷 위임(Subnet Delegation)은 이때 관리자가 이 서브넷은 해당 서비스 전용이라고 표시해 주는 기능으로, 가상 네트워크라는 더 큰 체계 안에서 서비스가 자기 구획을 정당하게 쓸 수 있게 해 줍니다.

아파트 한 동을 가상 네트워크, 그 안의 층별 구획을 서브넷이라고 생각해 보겠습니다. 관리사무소가 3층 전체는 택배 회사의 물류 거점으로 쓰겠다고 정하고 그 사실을 건물 대장에 적어 두면, 택배 회사는 3층의 현관과 우편함을 자기 방식대로 배치할 수 있지만 다른 층에는 손대지 않습니다.

서브넷 위임이 바로 그 대장 기록에 해당하며, 위임을 받은 서비스는 그 서브넷 안에 자기 자원을 만들고 주소를 나눠 쓸 수 있습니다. 대신 한 서브넷에는 한 서비스만 위임할 수 있어서, 이미 다른 서비스에 넘긴 구획은 새 서비스가 함께 쓰지 못합니다.

정리하면 서브넷 위임은 서브넷에 특정 서비스 이름을 지정해 그 서비스만 해당 주소 범위를 관리하도록 허용하는 표시입니다. 이 표시가 있어야 관리형 서비스가 가상 네트워크 안에서 주소 충돌 없이 안전하게 자리 잡습니다.

2부. Azure 네트워크 기초014

네트워크 보안 그룹(NSG)

서브넷과 NIC 앞에서 트래픽을 거르는 규칙

서브넷을 나눠 서비스를 배치했더라도 아무나 데이터베이스 통로로 접속할 수 있다면 그 구성은 사실상 무방비입니다. 네트워크 보안 그룹(Network Security Group, NSG)은 서브넷과 네트워크 인터페이스(NIC, 가상 컴퓨터가 네트워크에 연결되는 접점) 앞에서 오가는 트래픽을 규칙으로 걸러 내는 방화벽 역할을 합니다.

아파트 단지 정문에 경비실이 있어 방문자의 목적과 신분을 확인한 뒤 들여보내거나 돌려보내는 모습을 떠올리면 됩니다. 경비실이 세워 둔 출입 명단이 보안 규칙이고, 명단에는 어느 쪽에서 오는 트래픽인지, 어느 포트(port, 서비스가 쓰는 통로 번호)로 가는지, 허용인지 차단인지를 적습니다.

명단에 걸리지 않은 트래픽은 기본적으로 막히므로 필요한 통로만 명단에 올려 두는 방식으로 운영합니다. 이 그룹을 서브넷에 붙이면 그 안의 모든 자원에 한꺼번에 적용되고, 네트워크 인터페이스에 붙이면 그 가상 컴퓨터 하나에만 적용됩니다.

결국 NSG는 서브넷과 네트워크 인터페이스 앞에서 허용과 차단을 규칙으로 판정하는 트래픽 필터입니다. 어디에 붙이느냐에 따라 적용 범위가 달라진다는 점이 핵심입니다.

2부. Azure 네트워크 기초015

NSG 규칙 우선순위와 기본 규칙

규칙이 겹칠 때 무엇이 이기는가

규칙을 여러 개 만들어 두면 서로 허용과 차단이 겹치는 순간이 반드시 생기고, 그때 무엇이 이기는지 정해져 있지 않으면 같은 구성인데도 결과가 달라집니다. 네트워크 보안 그룹(NSG)은 규칙마다 우선순위 번호를 붙여 숫자가 낮은 규칙부터 먼저 평가하고, 처음으로 일치한 규칙의 판정으로 결론을 내립니다.

아파트 경비실 벽에 출입 지침이 여러 장 붙어 있고, 위에서부터 차례로 읽으며 해당되는 항목이 나오면 거기서 판단을 끝내는 상황과 같습니다. 지침 100번에 택배 기사는 정문 통과 허용, 200번에 야간에는 모든 외부인 차단이 적혀 있다면, 택배 기사가 낮에 오면 100번에서 허용으로 끝나고 200번은 읽지 않습니다.

100번부터 4096번까지가 관리자가 만드는 사용자 정의 규칙이고, 그 뒤에 65000번대의 기본 규칙이 자동으로 붙어 있습니다. 기본 규칙은 가상 네트워크 내부 통신과 부하 분산 장치의 상태 확인은 허용하고 나머지 인바운드는 모두 거부하며, 관리자가 임의로 지울 수는 없습니다.

정리하면 NSG는 낮은 번호의 규칙부터 평가해 처음 일치한 규칙에서 판정을 확정하고, 어떤 규칙에도 걸리지 않은 인바운드는 기본 규칙이 차단합니다. 그래서 새 규칙을 넣을 때는 기존 규칙과의 번호 순서를 반드시 함께 봐야 합니다.

2부. Azure 네트워크 기초016

사용자 정의 경로(UDR)

기본 라우팅을 관리자가 덮어쓰는 방법

가상 네트워크는 목적지 주소만 보고 알아서 길을 찾지만, 모든 트래픽을 방화벽 장비를 거쳐 보내야 하거나 외부와 연결된 회선 쪽으로 돌려야 하는 경우에는 그 자동 경로가 오히려 방해가 됩니다. 사용자 정의 경로(User Defined Route, UDR)는 관리자가 경로 표를 직접 만들어 기본 라우팅을 덮어쓰는 방법입니다.

아파트 단지로 들어오는 택배가 안내만 따르면 가장 가까운 길로 오지만, 단지 규정상 모든 택배는 먼저 중앙 물류 거점을 들러 검수를 받아야 한다면 안내를 무시하고 거점을 경유하도록 바꿔야 합니다. 경로 표의 각 줄에는 목적지 주소 범위, 다음 홉(Next Hop, 패킷을 넘겨줄 다음 지점)의 종류와 주소, 그리고 그 경로가 유효한지 여부가 적힙니다.

다음 홉으로는 가상 네트워크 게이트웨이, 가상 어플라이언스(방화벽처럼 트래픽을 검사하는 가상 장비), 인터넷, 없음(해당 목적지 차단) 등을 고를 수 있습니다. 같은 목적지에 대한 경로가 여럿이면 더 구체적인 주소 범위를 가진 경로가 이기고, 그것도 같으면 사용자 정의 경로가 시스템 기본 경로보다 우선합니다.

결국 UDR은 경로 표를 직접 작성해 트래픽이 지나갈 다음 지점을 관리자가 지정하는 수단입니다. 검사와 통제가 필요한 구간을 강제로 거치게 만들 때 씁니다.

2부. Azure 네트워크 기초017

Azure DNS와 프라이빗 DNS 영역

이름을 IP로 바꿔 주는 Azure의 이름 서비스

서버를 주소 숫자로만 부르면 사람이 외우기 어렵고, 서버가 늘거나 바뀔 때마다 접속 정보를 손봐야 합니다. Azure DNS는 이름을 주소로 바꿔 주는 이름 서비스(DNS, Domain Name System)를 Azure에서 운영하는 것이고, 프라이빗 DNS 영역(Private DNS Zone)은 그 이름 풀이를 가상 네트워크 안에서만 쓰도록 만든 구역입니다.

아파트 단지의 입주자 전화번호부를 생각해 보겠습니다. 이름으로 찾으면 번호가 나오고, 이사가 와서 번호가 바뀌면 전화번호부만 고치면 되므로 모든 세대가 각자 번호를 외울 필요가 없습니다.

Azure DNS의 공용 영역은 인터넷 전체가 보는 전화번호부라서 외부에 공개할 이름을 등록하고, 프라이빗 DNS 영역은 단지 내부용 전화번호부라서 가상 네트워크에 연결된 자원만 그 이름을 조회할 수 있습니다. 프라이빗 영역을 가상 네트워크에 연결하면 그 안의 가상 컴퓨터들이 이름으로 서로를 찾고, 이름과 주소의 대응은 자동 등록으로 관리할 수도 있습니다.

정리하면 Azure DNS는 이름과 주소의 대응을 관리하는 이름 서비스이고, 프라이빗 DNS 영역은 그 대응을 지정한 가상 네트워크 안으로 한정하는 도구입니다. 덕분에 서버 주소가 바뀌어도 접속하는 쪽의 설정을 고치지 않아도 됩니다.

공인 IP와 사설 IP

Azure에서 주소를 붙이는 두 가지 방식

같은 주소 체계를 쓰다 보면 사내 서버 여러 대가 같은 숫자를 주장하는 일이 생기고, 그 주소를 그대로 인터넷에 내보내면 남의 주소와 충돌합니다. Azure는 자원에 주소를 붙일 때 인터넷에서 직접 통하는 공인 IP(Public IP)와 가상 네트워크 안에서만 통하는 사설 IP(Private IP)를 나눠 씁니다.

아파트 단지의 동·호수와 도로명 주소를 떠올리면 이해가 쉽습니다. 101동 1203호는 단지 안에서만 통하는 사설 IP에 해당하고, 택배가 실제로 찾아오려면 필요한 ○○로 12 같은 도로명 주소가 공인 IP에 해당합니다.

사설 IP는 가상 네트워크의 주소 범위에서 자동으로 배정되든지 관리자가 직접 지정하든지 하며, 인터넷에서는 그 숫자만으로는 찾아갈 수 없습니다. 공인 IP는 인터넷으로 나가는 통로에 붙어 외부에서 접근할 수 있고, 계속 유지되는 고정 방식과 필요할 때만 잠깐 붙는 동적 방식이 있습니다.

결국 공인 IP는 인터넷에서 식별되는 대외 주소이고 사설 IP는 가상 네트워크 내부에서만 쓰이는 대내 주소입니다. 이 둘을 나눠 두면 주소 부족을 줄이면서도 바깥에 드러낼 자원만 골라 노출할 수 있습니다.

Azure는 이런 문제를 계층별로 나눠 해결하려고 Load Balancer, Application Gateway, Front Door, Traffic Manager라는 네 가지 부하 분산 서비스를 준비해 두었습니다. 아파트 단지로 비유하면 Traffic Manager는 어느 단지로 갈지 미리 정해 주는 안내 전화 교환원이고, Front Door는 단지 정문에서 가장 가까운 출입구로 길을 열어 주는 글로벌 안내데스크입니다. Application Gateway는 각 동 로비에서 방문 목적지인 호실 번호를 받아 알맞은 집으로 안내하는 경비원이며, Load Balancer는 층마다 놓인 배전반처럼 전기(연결)만 여러 회선으로 고르게 나눠 주는 장치입니다.

그래서 주소나 포트 수준에서 연결만 나누면 Load Balancer, 웹 주소와 경로를 보고 판단해야 하면 Application Gateway, 여러 지역에 걸친 전 세계 사용자 입구라면 Front Door, 지역 간 트래픽 방향만 정하고 싶다면 Traffic Manager를 고릅니다.

이 네 서비스는 서로 대체재가 아니라 필요하면 층층이 겹쳐 쓸 수 있는 도구입니다.

Azure 리소스 계층과 리소스 그룹

리소스를 묶어 관리하는 단위

클라우드에 가상 머신, 데이터베이스, 저장소를 마구 만들다 보면 무엇이 어느 서비스의 부품인지 알 수 없게 되고, 하나를 지우려다 엉뚱한 시스템까지 멈추는 사고가 납니다. Azure는 이 문제를 막으려고 모든 자원을 리소스 그룹(resource group)이라는 폴더로 묶고, 그 위에 구독(subscription)과 관리 그룹(management group)이라는 더 큰 단계를 두었습니다.

이 구조는 한 회사 건물의 서류 철과 같아서, 리소스는 개별 문서, 리소스 그룹은 부서별 서류철, 구독은 부서, 관리 그룹은 건물 전체의 캐비닛에 해당합니다. 문서를 찾을 때 부서 철을 펼치면 되듯이, Azure에서는 리소스 그룹 단위로 권한을 주고 비용을 집계하고 한꺼번에 삭제할 수 있습니다.

다만 서류철을 옮길 수 있어도 문서 하나는 반드시 철 하나에만 들어가야 하듯, 한 리소스는 동시에 여러 리소스 그룹에 속할 수 없습니다. 또한 리소스 그룹은 그 자체가 위치를 가지지만 그 안의 리소스는 각자 다른 지역에 둘 수 있습니다.

이 계층 덕분에 운영자는 자원을 이름 하나가 아니라 소속과 책임 단위로 관리하게 됩니다.

3부. Application Gateway 개요와 구조021

Azure Application Gateway

7계층 웹 트래픽 전용 관리형 로드 밸런서

웹 서비스를 운영하면 같은 서버 주소 하나로 여러 사이트와 여러 경로를 받아야 하는데, 단순히 연결만 나눠 주는 장비로는 특정 경로의 요청을 특정 서버로 보내지 못해 관리가 어려워집니다. Azure Application Gateway는 이런 요구를 위해 만들어진 7계층, 즉 웹 주소와 경로를 읽을 수 있는 계층에서 동작하는 관리형 로드 밸런서(load balancer)입니다.

아파트 정문의 안내데스크로 비유하면, 방문객의 이름표에 적힌 목적지(주소와 경로)를 읽고 해당 동의 해당 호실로 직접 안내하는 방식입니다. 일반 로드 밸런서가 순서대로 번호를 매겨 나눠 주는 것과 달리, Application Gateway는 요청 주소를 기준으로 어느 백엔드(backend) 서버 묶음으로 보낼지 규칙으로 정할 수 있습니다. 여기에 웹 애플리케이션 방화벽(Web Application Firewall)을 붙여 악성 요청을 걸러 내고, 보안 소켓 계층(SSL/TLS) 암호화를 대신 처리하는 기능도 함께 제공합니다.

실제 동작은 리스너(listener)가 요청을 받고, 규칙(rule)이 판단하고, 백엔드 풀(backend pool)이 처리하는 순서로 이어집니다.

3부. Application Gateway 개요와 구조022

Application Gateway v1과 v2

세대 차이와 v1을 더 쓰지 않는 이유

기존 v1 게이트웨이를 쓰던 조직이 보안 요구와 트래픽 증가를 만나면, 성능 상한과 기능 부재 때문에 구조를 뜯어고쳐야 하는 상황에 부딪힙니다. Azure는 이 한계를 넘으려고 Application Gateway v2 세대를 내놓았고, 지금은 새로 만드는 게이트웨이에 v1을 권하지 않습니다.

v1이 정해진 크기와 대수로 성능을 맞추는 고정 요금제 건물이라면, v2는 손님이 늘면 자동으로 창구를 늘리는 탄력형 건물에 가깝습니다. v2는 자동 확장(autoscaling)과 가용 영역(availability zone) 분산을 지원해 특정 구역 장애에도 견디고, 웹 애플리케이션 방화벽의 최신 규칙 집합과 더 강한 성능을 함께 제공합니다. 반면 v1은 확장에 수동 개입이 필요하고 일부 신규 기능이 제공되지 않아, 이미 운영 중인 환경도 v2로 옮기는 것이 일반적인 권장 방향입니다.

다만 세부 기능과 마이그레이션 제약은 시점과 환경에 따라 달라질 수 있으므로, 실제 전환 전에는 해당 지역과 요금제의 최신 문서를 확인해야 합니다.

3부. Application Gateway 개요와 구조023

Application Gateway의 구성 요소 지도

프런트엔드·리스너·규칙·백엔드가 맞물리는 관계

게이트웨이를 처음 설정하면 화면에 프런트엔드, 리스너, 규칙, 백엔드 같은 항목이 잔뜩 늘어서서 무엇이 무엇과 연결되는지 알기 어렵습니다. Application Gateway는 이 네 가지를 하나의 흐름으로 맞물리게 설계했고, 그 관계를 알면 설정이 훨씬 단순해집니다.

아파트 정문 안내 체계로 비유하면, 프런트엔드 IP 구성(frontend IP configuration)은 방문객이 도착하는 정문 주소이고, 리스너(listener)는 어느 문으로 온 몇 번 차량인지 확인하는 접수 창구입니다. 규칙(rule)은 접수된 목적지에 따라 어느 동으로 보낼지 정하는 안내 지침이고, 백엔드 풀(backend pool)은 실제로 손님을 맞이하는 각 동의 세대들이며, 상태 프로브(health probe)는 그 세대가 지금 응대 가능한지 수시로 확인하는 순찰입니다. 요청은 프런트엔드로 들어와 리스너가 받고, 규칙이 판단해 백엔드 풀로 넘기며, 응답은 같은 길을 되짚어 나갑니다.

이 사슬 중 하나만 비어 있어도 트래픽은 흐르지 않으므로, 설정 오류를 찾을 때는 이 순서대로 짚어 보는 것이 가장 빠릅니다.

3부. Application Gateway 개요와 구조024

프런트엔드 IP 구성(Frontend IP Configuration)

게이트웨이가 요청을 받는 입구

게이트웨이를 만들었는데 외부에서 접속할 주소가 정해지지 않으면 사용자는 어디로 요청을 보내야 할지 알 수 없고, 서비스는 문은 있는데 간판이 없는 셈이 됩니다. 프런트엔드 IP 구성(frontend IP configuration)은 Application Gateway가 요청을 받는 입구 주소를 정의하는 설정으로, 게이트웨이 구성의 출발점입니다.

아파트로 비유하면 단지 정문의 도로 주소와 같아서, 택배 기사가 그 주소를 보고 찾아오듯 사용자와 인터넷이 이 주소로 요청을 보냅니다. 여기에는 공인 IP(public IP)를 붙여 인터넷에 공개하거나, 가상 네트워크 내부 주소만 써서 내부 사용자 전용으로 둘 수 있고, 같은 게이트웨이에 여러 입구를 두는 것도 가능합니다. 이 입구는 리스너(listener)와 짝을 이루어 어느 포트와 프로토콜로 받을지를 정하게 됩니다.

즉 프런트엔드 IP 구성은 트래픽이 처음 닿는 지점을 선언하고, 그 뒤의 판단과 분배는 리스너와 규칙이 이어받는 구조입니다.

3부. Application Gateway 개요와 구조025

공인 프런트엔드와 사설 프런트엔드

인터넷 공개 입구와 내부 전용 입구의 차이

회사 내부 직원만 쓰는 업무 시스템을 인터넷에 그대로 열어 두면, 외부에서 로그인을 계속 시도하거나 빈틈을 찾아 두드리는 트래픽이 하루 종일 들어옵니다. Application Gateway는 이런 문제를 피하려고 트래픽을 받는 입구 자체를 인터넷에 공개하는 공인 프런트엔드(public frontend)와 내부에서만 닿는 사설 프런트엔드(private frontend)로 나눠 둡니다.

아파트 단지로 비유하면 공인 프런트엔드는 공용 도로에서 바로 보이는 정문이고, 사설 프런트엔드는 단지 안쪽 주민만 오가는 지하 주차장 통로입니다. 정문에는 도로명 주소와 간판이 붙어 있어 택배 기사도 주민도 쉽게 찾아오지만, 그만큼 누구나 문 앞까지 올 수 있습니다. 반대로 지하 통로는 단지 밖에서 주소를 알 수 없고 단지 경비를 통과해야 닿기 때문에 외부인의 출입 자체가 어렵습니다.

Application Gateway에서도 공인 프런트엔드는 공인 IP 주소와 공개 DNS 이름을 갖고 인터넷 어디서나 접속을 받으며, 사설 프런트엔드는 가상 네트워크 안쪽 주소만 가져 같은 가상 네트워크나 연결된 사설 회선에서만 접속을 받습니다. 결국 공인 프런트엔드는 불특정 다수에게 열린 대외 창구이고 사설 프런트엔드는 내부망으로 한정된 대내 창구이며, 두 입구는 같은 Application Gateway 안에서 서로 다른 주소 체계와 접근 범위를 가집니다.

어느 쪽을 쓸지는 서비스 대상이 인터넷 전체인지 회사 내부인지로 정하고, 둘을 함께 두어 외부 공개 서비스와 내부 관리 화면을 한 장비에서 분리해 운영하기도 합니다.

Application Gateway 서브넷 요구 사항

전용 서브넷과 최소 크기가 필요한 이유

Application Gateway를 다른 서비스와 같은 서브넷에 섞어 두면 주소가 부족해지거나 경로 설정이 엉켜 장애 원인을 찾기 어려워집니다. 그래서 Application Gateway는 자기 전용 서브넷(dedicated subnet)을 따로 갖고, 그 서브넷 안에는 다른 리소스를 두지 못하게 막으며 정해진 최소 크기 이상의 주소 공간이 필요합니다.

회사 건물에 방문객 접수 데스크를 둔다고 비유하면, 접수 데스크는 다른 부서 책상 사이에 끼워 넣는 것이 아니라 출입구 옆에 전용 공간을 따로 마련합니다. 그 공간에는 안내 직원이 앉을 자리와 방문객이 잠시 서 있을 자리가 여러 개 필요하고, 다른 부서가 그 자리를 창고로 쓰기 시작하면 접수 업무가 밀립니다.

Application Gateway도 마찬가지로 게이트웨이 인스턴스가 쓸 주소와 내부 관리용 주소를 넣을 자리가 필요해 서브넷을 전용으로 비워 둡니다. 최소 크기는 게이트웨이가 확장될 때 필요한 주소 수를 미리 넣어 둔 것으로, v2에서는 대체로 /24 정도를 권장하지만 구성과 환경에 따라 달라질 수 있습니다.

정리하면 Application Gateway 서브넷은 게이트웨이만 쓰는 빈 서브넷이어야 하고, 인스턴스 수와 향후 확장을 감당할 주소 공간을 확보해야 합니다. 이 조건을 미리 맞춰 두면 나중에 인스턴스를 늘리거나 가용 영역을 나눌 때 주소 부족으로 막히지 않습니다.

3부. Application Gateway 개요와 구조027

Application Gateway 인스턴스와 용량

처리 능력을 무엇으로 정하는가

트래픽이 갑자기 몰리는 순간에 게이트웨이가 처리 속도를 따라가지 못하면 사용자는 연결이 끊기거나 화면이 늦게 뜨는 경험을 합니다. Application Gateway는 처리를 맡는 인스턴스(instance) 수로 용량을 정하고, 그 수와 각 인스턴스의 처리 능력을 조합해 초당 처리량과 동시 연결 수를 확보합니다.

마트 계산대에 비유하면 인스턴스는 계산원이 서 있는 계산대 한 대이고, 용량은 계산대를 몇 대 열어 두느냐로 정해집니다. 손님이 적을 때는 한두 대로 충분하지만 점심시간처럼 손님이 몰리면 계산대를 더 열어야 줄이 줄어듭니다.

Application Gateway도 인스턴스 한 대가 감당하는 처리량을 기준으로 전체 용량을 계산하고, 트래픽이 늘면 인스턴스를 더해 처리 능력을 키웁니다. 용량을 정할 때는 평균 트래픽이 아니라 피크 시간대의 동시 연결과 초당 요청 수를 봐야 하며, SSL 처리처럼 부하가 큰 기능이 켜져 있으면 같은 인스턴스로 감당하는 양이 줄어듭니다.

결국 Application Gateway의 처리 능력은 인스턴스 수와 각 인스턴스가 감당하는 부하로 결정되며, 용량 산정은 최대 부하를 기준으로 여유를 두고 잡아야 합니다.

3부. Application Gateway 개요와 구조028

자동 크기 조정(Autoscale)

v2에서 트래픽에 따라 인스턴스를 늘리고 줄이는 방식

이벤트나 광고로 트래픽이 몇 배로 뛰는 날, 미리 정해 둔 인스턴스 수가 모자라면 응답이 밀리고 반대로 한산한 새벽에는 남는 인스턴스가 비용만 잡아먹습니다. v2 Application Gateway의 자동 크기 조정(Autoscale)은 트래픽 지표를 보고 인스턴스를 늘리거나 줄여 이 낭비와 부족을 함께 줄이는 기능입니다.

콜센터에 비유하면 자동 크기 조정은 대기 전화 수를 보면서 상담원을 부르고 돌려보내는 관리자입니다. 전화가 몰리면 대기 시간이 길어지기 전에 상담원을 더 투입하고, 전화가 끊기면 남는 상담원을 순차적으로 퇴근시킵니다.

Application Gateway도 처리 부하를 나타내는 지표를 주기적으로 확인해 인스턴스를 늘리고, 부하가 가라앉으면 최소 인스턴스 수까지 줄입니다. 이때 최소와 최대 인스턴스 수를 정해 두어 아무리 한산해도 최소만큼은 유지하고, 갑작스러운 폭주에도 최대를 넘지 않게 상한을 둡니다. 또한 늘어난 인스턴스는 준비 시간이 필요하므로 급격한 증가에는 즉시 반응하지 못할 수 있어, 중요한 행사 전에는 최소 수를 미리 올려 두는 편이 안전합니다.

정리하면 자동 크기 조정은 부하 지표에 따라 인스턴스를 자동으로 늘리고 줄여 성능과 비용의 균형을 맞추는 방식이며, 최소·최대 범위 설정이 그 안전장치입니다.

3부. Application Gateway 개요와 구조029

고정 크기(Manual Scale) 운영

인스턴스 수를 직접 정할 때의 판단

자동 크기 조정에 맡기면 예측하기 어려운 상황에서 인스턴스 수가 계속 바뀌어, 용량 계획이나 비용 예측이 어려워지는 경우가 있습니다. 고정 크기(Manual Scale) 운영은 인스턴스 수를 사람이 직접 정해 두고 그 수를 유지하는 방식으로, 트래픽 패턴이 일정하거나 변화를 미리 아는 환경에 어울립니다.

회사 셔틀버스로 비유하면 자동 크기 조정은 승객 수에 따라 버스를 계속 추가 투입하는 운영이고, 고정 크기는 출퇴근 시간대 승객이 늘 비슷하다는 것을 알고 매일 같은 대수를 배차하는 운영입니다. 배차 대수를 고정하면 기사와 주차 공간을 미리 확보할 수 있고 비용도 매달 같게 나옵니다. 대신 예상보다 승객이 몰리는 날에는 버스가 부족해지고, 한산한 날에는 빈 버스가 그대로 도는 낭비가 생깁니다.

Application Gateway에서도 고정 크기는 인스턴스 수가 변하지 않아 성능이 예측 가능하고 비용 계산이 쉽지만, 예상하지 못한 트래픽 급증에는 여유가 없습니다. 그래서 고정 크기는 트래픽이 안정적이고 최대 부하를 이미 아는 서비스에 적합하며, 피크를 넉넉히 덮는 수를 골라 두는 판단이 필요합니다.

가용 영역(Availability Zone) 구성

인스턴스를 여러 영역에 흩어 두는 설계

데이터센터 한 곳에만 게이트웨이를 두면 그 지역에 정전이나 냉각 장애가 생기는 순간 서비스 전체가 멈춥니다. 가용 영역(Availability Zone) 구성은 같은 리전 안의 물리적으로 분리된 여러 데이터센터에 인스턴스를 나눠 두어, 한 곳이 무너져도 나머지가 트래픽을 이어받게 하는 설계입니다.

은행 지점에 비유하면 가용 영역은 서로 다른 동네에 있는 지점들이고, 고객은 한 지점이 문을 닫아도 다른 지점에서 같은 업무를 볼 수 있습니다. 각 지점은 건물도 전력도 따로 쓰기 때문에 한 동네에 정전이 나도 다른 동네 지점은 정상으로 영업합니다.

Application Gateway도 인스턴스를 둘 이상의 가용 영역에 흩어 배치하면, 한 영역이 작동하지 않아도 다른 영역의 인스턴스가 계속 요청을 받습니다. 다만 이 구성이 의미를 가지려면 인스턴스가 최소 두 개 이상이어야 하고, 영역별로 나눠 배치되도록 설정해야 하며, 연결된 백엔드도 여러 영역에 퍼져 있어야 전체가 버팁니다.

정리하면 가용 영역 구성은 인스턴스를 물리적으로 분리된 여러 영역에 나눠, 한 영역의 장애가 서비스 중단으로 이어지지 않게 하는 고가용성 설계입니다.

3부. Application Gateway 개요와 구조031

관리형 서비스로서의 Application Gateway

사용자가 패치와 업그레이드를 하지 않는 이유

서버 소프트웨어를 직접 설치해 운영해 본 적이 없는 사람이라면, 장비 한 대를 세워 두고 몇 달 만에 보안 패치가 스무 개씩 쌓이는 상황을 상상하기 어려울 것입니다. 그 패치를 하나라도 빠뜨리면 취약점 공지가 나오고, 새 버전으로 올리는 날에는 설정이 초기화되거나 서비스가 잠깐 멈추는 일이 생깁니다. Application Gateway(Azure의 웹 트래픽 분산 서비스)는 바로 이 반복 작업을 사용자 대신 떠안는 관리형 서비스(managed service)라는 점이 출발점입니다.

이를 아파트 관리 사무소에 비유해 보면 이해가 쉽습니다. 세입자는 자기 집 안의 수도꼭지와 보일러만 신경 쓰면 되고, 건물 전체의 배관 교체나 소방 설비 점검은 관리 사무소가 알아서 합니다. 세입자가 관리 사무소에 "우리 집 배관 좀 새 버전으로 바꿔 주세요"라고 요청할 필요가 없는 것처럼, Application Gateway 사용자는 게이트웨이를 구성하는 가상 머신의 운영체제 패치나 서비스 엔진 업그레이드를 직접 하지 않습니다.

대신 리스너(listener)와 라우팅 규칙, 백엔드 풀(backend pool) 같은 "내가 원하는 동작"만 설정하고, 그 아래 계층의 유지보수는 플랫폼이 맡습니다. 물론 관리형이라고 해서 사용자가 아무것도 하지 않아도 되는 것은 아니며, 어떤 항목까지 플랫폼이 책임지는지는 서비스 등급과 배포 방식에 따라 달라질 수 있습니다.

정리하면 Application Gateway에서 사용자가 관리하는 것은 규칙과 설정이고, 패치·업그레이드·이중화 같은 운영 부담은 서비스 제공자 쪽으로 옮겨집니다. 그래서 조직은 게이트웨이 자체를 돌보는 일이 아니라 그 위에서 흐르는 트래픽 정책에 시간을 쓸 수 있습니다.

3부. Application Gateway 개요와 구조032

백엔드로 쓸 수 있는 대상들

VM·VMSS·App Service·AKS를 뒤에 두는 조합

웹 서비스를 운영하다 보면 요청을 처리하는 서버가 한 종류로 끝나는 경우가 드물어서, 어떤 요청은 가상 머신이 받고 어떤 요청은 앱 서비스가 받는 식으로 뒤섞입니다. 이때 앞단에 놓인 게이트웨이가 뒤쪽 서버들을 각각 따로 알아야 한다면, 서버를 하나 추가할 때마다 게이트웨이 설정을 손봐야 하는 번거로움이 생깁니다. Application Gateway는 이 뒤쪽 서버 묶음을 백엔드 풀(backend pool)이라는 하나의 단위로 다루면서, 성격이 다른 여러 종류의 대상을 같은 풀에 담을 수 있게 합니다.

이를 택배 물류센터에 비유하면, 집배원은 각 집의 사정을 몰라도 "이 구역 배송 목록"이라는 하나의 묶음만 보면 됩니다. 목록에 아파트도 있고 단독주택도 있고 상가도 있듯이, 백엔드 풀에는 가상 머신(VM), 가상 머신 확장 집합(VMSS, 같은 이미지의 서버를 여러 대로 늘려 주는 단위), App Service(Azure의 관리형 웹 앱 호스팅), AKS(Azure Kubernetes Service, 컨테이너를 묶어 운영하는 관리형 쿠버네티스)가 함께 들어갈 수 있습니다. 게이트웨이는 각 대상의 IP 주소나 내부 이름을 목록으로 들고 있다가, 앞에서 들어온 요청을 이 목록 안의 건강한 대상에게 넘깁니다.

서버를 늘릴 때는 풀에 주소를 추가하기만 하면 되고, 앞단의 입구 설정은 그대로 둘 수 있습니다. 다만 어떤 대상이 실제로 지원되는지, 상태 확인 방식이 무엇인지는 서비스 버전에 따라 다를 수 있으므로 구성 전에 확인이 필요합니다.

결국 백엔드 풀은 "요청을 처리할 서버들의 명단"이고, 그 명단에 VM·VMSS·App Service·AKS를 섞어 넣을 수 있다는 점이 이 서비스의 유연함입니다. 덕분에 기존 가상 머신과 새로 만든 컨테이너 서비스를 같은 입구 아래에서 함께 운영할 수 있습니다.

4부. 리스너와 라우팅033

리스너(Listener)

어떤 요청을 받아들일지 정하는 조건

게이트웨이를 세워 두었는데 아무 요청도 받지 못하는 상황이 실제로 있습니다. 입구는 열려 있지만 "어떤 주소로, 어떤 포트로, 암호화된 연결로 들어오는 요청을 받을지"를 아무도 정해 두지 않았기 때문입니다. 리스너(listener)는 바로 이 조건을 정하는 구성 요소로, 어떤 요청을 받아들일지 판단하는 문지기 역할을 합니다.

이를 회사 정문 경비실에 비유하면, 경비원은 출입증 종류와 방문 목적이 적힌 안내판을 보고 어떤 사람을 들일지 결정합니다. 리스너에서 그 안내판에 해당하는 것이 프로토콜(HTTP인지 HTTPS인지), 포트 번호, 그리고 요청의 도메인 이름입니다. 예를 들어 443번 포트로 오는 HTTPS 요청만 받겠다고 정하면, 80번 포트로 오는 요청은 그 리스너의 문 앞에서 걸러집니다.

리스너는 요청을 받아들이는 조건만 정하고, 받은 요청을 어디로 보낼지는 별도의 라우팅 규칙(rule)이 정합니다. 그래서 리스너 하나에 규칙 하나를 연결하는 식으로 입구와 목적지를 짝지어 구성합니다.

HTTPS 리스너라면 인증서가 필요하고, 이 인증서를 어디에 두고 어떻게 갱신하는지도 함께 설계해야 합니다.

정리하면 리스너는 게이트웨이가 요청을 받아들이기 위한 조건 묶음이며, 프로토콜·포트·도메인·인증서가 그 핵심입니다. 이 조건이 없으면 뒤쪽 백엔드가 아무리 잘 돌아가도 요청은 게이트웨이 앞에서 멈춥니다.

4부. 리스너와 라우팅034

기본 리스너와 다중 사이트 리스너

하나의 입구로 여러 도메인을 받는 방법

회사가 도메인을 여러 개 쓰기 시작하면 문제가 생깁니다. 쇼핑몰용 주소와 사내 업무용 주소를 따로 운영하려는데, 게이트웨이를 도메인 수만큼 새로 만들면 비용도 관리 부담도 배로 늘어납니다. 이때 하나의 게이트웨이 입구로 여러 도메인을 받아내는 방식이 다중 사이트 리스너(multi-site listener)이고, 도메인 구분 없이 하나의 입구만 쓰는 방식이 기본 리스너(basic listener)입니다.

이를 한 건물의 공동 현관에 비유하면, 기본 리스너는 현관이 하나뿐이라 들어오는 모든 사람을 같은 안내데스크로 보내는 구조입니다. 다중 사이트 리스너는 같은 현관이라도 방문객이 말한 회사 이름에 따라 안내데스크를 나눠 주는 구조이며, 여기서 회사 이름에 해당하는 것이 요청의 호스트 이름(host name)입니다.

다중 사이트 리스너를 쓰려면 각 도메인마다 리스너를 만들고 각각에 도메인 이름과 인증서를 지정한 뒤, 도메인별로 다른 백엔드 풀과 연결합니다. 이렇게 하면 IP 주소 하나에 여러 도메인을 얹을 수 있어 게이트웨이를 여러 개 두지 않아도 됩니다.

다만 같은 포트를 공유하는 구조이므로 도메인별 인증서 관리와SNI(서버 이름 표시, 접속한 도메인에 맞는 인증서를 골라 주는 방식) 지원 여부를 미리 확인해야 합니다.

정리하면 기본 리스너는 단일 입구·단일 목적지, 다중 사이트 리스너는 하나의 입구에서 도메인별로 목적지를 나누는 구성입니다. 도메인이 늘어날 때 게이트웨이를 증설하는 대신 리스너를 추가하는 쪽이 운영상 유리합니다.

4부. 리스너와 라우팅035

호스트 기반 라우팅

도메인 이름으로 백엔드를 가르는 규칙

서비스가 커지면 앞단 주소 하나로 모든 요청을 받으면서, 뒤에서는 쇼핑몰은 쇼핑몰 서버가, 블로그는 블로그 서버가 처리해야 하는 상황이 옵니다. 요청 자체에는 "어느 서비스로 가야 하는지"가 눈에 보이지 않으므로, 기준을 정해 주지 않으면 모든 요청이 한 곳으로 몰립니다. 호스트 기반 라우팅(host-based routing)은 요청에 담긴 도메인 이름을 기준으로 백엔드를 가르는 규칙입니다.

이를 아파트 우편물 분류에 비유하면, 배달원은 봉투에 적힌 동·호수를 보고 어느 우편함에 넣을지 정합니다. 여기서 봉투의 주소가 요청의 호스트 이름이고, 우편함이 백엔드 풀입니다. shop.example.com으로 온 요청은 쇼핑몰 서버 묶음으로, blog.example.com으로 온 요청은 블로그 서버 묶음으로 보내는 식이며, 두 규칙은 하나의 게이트웨이 안에서 나란히 존재합니다.

이 규칙이 동작하려면 앞단의 다중 사이트 리스너가 도메인별로 요청을 구분해 주어야 하고, 규칙에는 어떤 리스너의 요청을 어느 풀로 보낼지가 적힙니다. 도메인을 새로 추가할 때는 리스너와 규칙 한 쌍을 더하면 되므로 기존 서비스에는 손대지 않아도 됩니다.

정리하면 호스트 기반 라우팅은 URL의 도메인 부분을 보고 목적지 백엔드를 고르는 규칙입니다. 하나의 IP 주소와 하나의 게이트웨이로 여러 서비스를 운영하면서도 서로의 트래픽을 섞지 않을 수 있습니다.

4부. 리스너와 라우팅036

경로 기반 라우팅

URL 경로로 백엔드를 가르는 규칙

하나의 서비스 안에서도 성격이 다른 요청이 섞입니다. 상품 목록을 보여 주는 요청과 이미지를 내려받는 요청, 결제를 처리하는 요청은 뒤에서 처리하는 서버의 부하 특성이 전혀 다릅니다.

이걸 한 서버 묶음에 모두 맡기면 이미지 요청이 결제 요청을 밀어내는 일이 생깁니다. 경로 기반 라우팅(path-based routing)은 URL에서 도메인 뒤에 붙는 경로를 기준으로 백엔드를 가르는 규칙입니다.

이를 큰 병원의 진료 안내에 비유하면, 같은 건물에 들어온 환자라도 "내과"라고 말하면 내과 접수로, "정형외과"라고 말하면 정형외과 접수로 안내됩니다. 여기서 진료과 이름이 URL 경로이고, 각 접수처가 백엔드 풀입니다. /images/로 시작하는 요청은 이미지 전용 서버 묶음으로, /api/로 시작하는 요청은 응용 프로그램 서버 묶음으로 보내도록 규칙을 나눌 수 있습니다.

경로는 보통 앞부분이 일치하는지를 기준으로 판단하며, 여러 규칙이 겹칠 때 어느 것이 우선하는지는 규칙의 순서와 설정에 따릅니다. 이 방식은 호스트 기반 라우팅과 함께 쓸 수 있어서, 도메인으로 서비스를 나눈 뒤 그 안에서 다시 경로로 역할을 나누는 구성도 가능합니다.

정리하면 경로 기반 라우팅은 URL의 경로 부분을 보고 요청을 다른 백엔드로 흘려보내는 규칙입니다. 덕분에 하나의 도메인 아래에서도 정적 파일과 업무 처리를 분리해 각자에게 맞는 서버 구성으로 운영할 수 있습니다.

4부. 리스너와 라우팅037

요청 라우팅 규칙(Request Routing Rule)

리스너와 백엔드를 잇는 연결 규칙

수십 개 서비스가 한 주소 뒤에 모여 있는데 어느 요청을 어디로 보내야 하는지 정해 두지 않으면, 모든 요청이 엉뚱한 서버로 흩어져 장애가 납니다. 이 문제를 풀기 위해 리스너와 백엔드 사이에 연결 규칙을 미리 정해 두는 장치가 요청 라우팅 규칙(Request Routing Rule)입니다.

아파트 우편함을 떠올리면 이해가 쉽습니다. 경비실에 들어온 택배는 수령인 이름과 동, 호수가 적힌 규칙표를 보고 각 세대 앞으로 옮겨집니다. 요청 라우팅 규칙에서 리스너(Listener)는 택배를 처음 받는 경비실이고, 백엔드(Backend)는 실제 수령인인 각 세대이며, 규칙은 이름과 호수를 대조하는 규칙표에 해당합니다.

규칙은 보통 경로나 호스트 이름 같은 조건과 그에 대응하는 대상 백엔드를 한 쌍으로 묶어 정의하고, 조건이 맞는 첫 규칙에서 처리가 끝납니다. 즉 라우팅 규칙은 들어온 요청의 생김새를 읽어 알맞은 백엔드로 넘기는 판단 기준입니다.

4부. 리스너와 라우팅038

기본 규칙의 역할

어떤 규칙에도 걸리지 않은 요청의 처리

규칙을 아무리 촘촘히 짜 두어도 새로 생긴 경로나 예상하지 못한 요청은 반드시 나타나는데, 그때 처리 방침이 없으면 사용자는 이유를 알 수 없는 오류 화면만 보게 됩니다. 그래서 어떤 규칙에도 걸리지 않은 요청을 받아 줄 마지막 규칙을 따로 두는데, 이것이 기본 규칙(Default Rule)입니다.

택배 허브에 비유하면 이해가 쉽습니다. 분류 벨트를 따라가던 택배가 어느 지역 벨트에도 해당하지 않으면 마지막에 있는 기타 벨트로 떨어집니다. 기본 규칙은 이 기타 벨트처럼 모든 구체 규칙을 확인한 뒤에도 남은 요청을 맡아 정해진 백엔드로 보내거나 정중히 거절합니다.

규칙은 위에서부터 차례로 평가되므로 기본 규칙은 항상 목록의 맨 끝에 놓이고, 앞에 두면 뒤따르는 모든 규칙이 가려집니다. 결국 기본 규칙은 예외를 방치하지 않고 통제된 방식으로 처리하게 만드는 안전망입니다.

4부. 리스너와 라우팅039

URL 경로 맵(Path Map)

경로별 대상과 설정을 표로 정의하기

경로마다 담당 서버가 다른데 이 대응을 머릿속이나 문서 몇 장에만 적어 두면, 새 서비스를 붙일 때마다 누가 어디로 보내는지 확인하느라 시간이 새고 실수도 납니다. 이 대응 관계를 한눈에 보이도록 표로 정의한 것이 URL 경로 맵(Path Map)입니다.

큰 병원의 진료과 안내판을 떠올리면 됩니다. 안내판에는 층과 진료과 이름, 담당 접수처가 나란히 적혀 있어 환자가 자기 증상에 맞는 곳을 바로 찾습니다. 경로 맵에서 경로는 안내판의 진료과 항목이고, 대상 백엔드는 그 과가 있는 층과 접수처이며, 설정값은 운영 시간이나 담당자처럼 함께 적어 두는 부가 정보입니다.

요청이 들어오면 게이트웨이는 표에서 가장 잘 맞는 경로를 찾아 그 줄에 적힌 대상으로 넘깁니다. 표에 없는 경로가 들어오면 기본 규칙이 처리하므로, 표는 자주 쓰는 경로를 빠짐없이 채우는 것이 중요합니다. 즉 경로 맵은 흩어진 연결 정보를 표 하나로 모아 누구나 같은 판단을 하게 만드는 문서이자 설정입니다.

4부. 리스너와 라우팅040

URL 재작성(Rewrite)

들어온 URL을 다른 모양으로 바꿔 넘기기

백엔드 서버가 예전에 정해진 주소 체계를 그대로 기대하고 있어서, 게이트웨이가 받은 주소를 그대로 넘기면 페이지가 열리지 않는 경우가 흔합니다. 이때 겉으로 보이는 주소는 그대로 두고 안쪽으로 넘길 때만 주소 모양을 바꾸는 기능이 URL 재작성(URL Rewrite)입니다.

택배 송장에 비유할 수 있습니다. 고객이 적은 주소는 그대로 두고, 허브 직원이 그 위에 내부 배송 구역 코드를 덧붙여 자기 창고 체계에 맞게 만드는 것과 같습니다. 재작성 규칙은 어떤 주소를 어떤 모양으로 바꿀지 정하는 대응이며, 경로의 일부를 잘라내거나 앞에 접두어를 붙이는 식으로 동작합니다.

중요한 점은 재작성이 서버 안에서 일어나므로 사용자의 브라우저 주소창은 바뀌지 않는다는 것입니다. 정리하면 URL 재작성은 주소를 다른 주소로 안내하는 것이 아니라, 넘기는 순간에만 모양을 손질해 백엔드가 알아듣게 만드는 변환입니다.

4부. 리스너와 라우팅041

리디렉션(Redirect)

HTTP를 HTTPS로, 옛 주소를 새 주소로 돌리기

사용자가 예전에 즐겨찾기한 주소로 들어오거나 암호화되지 않은 주소로 접속하면, 그 요청을 그대로 처리할지 막을지 애매해져 보안 구멍과 불편이 함께 생깁니다. 이때 브라우저에게 다른 주소로 다시 가라고 알려 주는 응답이 리디렉션(Redirect)입니다.

이사를 간 집의 주소 안내를 떠올리면 쉽습니다. 새 집 주소를 적은 쪽지를 문에 붙여 두면, 옛 집을 찾아온 사람은 그 쪽지를 읽고 새 집으로 발길을 돌립니다. 리디렉션에서 옛 주소는 쪽지를 붙여 둔 집이고, 새 주소는 실제로 살고 있는 집이며, 응답 코드(Status Code)는 쪽지에 적힌 안내 문구에 해당합니다.

브라우저는 이 응답을 받으면 주소창을 새 주소로 바꾸고 그곳에 다시 요청을 보냅니다. 영구 이동과 일시 이동을 구분하는 코드를 쓰면 검색 엔진이 주소 변경을 제대로 반영하므로, HTTP를 HTTPS로 돌리거나 옛 주소를 새 주소로 옮길 때 널리 쓰입니다.

HTTP 헤더 재작성

요청·응답 헤더를 고쳐 백엔드에 전달하기

백엔드 서버가 클라이언트 정보를 헤더(Header)에서 읽는데, 게이트웨이를 거치면서 원래 값이 사라지거나 엉뚱한 값으로 남아 있으면 인증이 풀리거나 잘못된 접속 기록이 쌓입니다. 이 헤더 값을 넘기기 전에 고쳐 주는 기능이 HTTP 헤더 재작성(Header Rewrite)입니다.

택배 상자에 붙는 송장과 취급 주의 라벨을 떠올리면 됩니다. 허브 직원이 기존 라벨을 떼지 않고 필요한 정보를 덧붙이거나 잘못된 표기를 고쳐 다시 붙이듯이, 게이트웨이는 요청 헤더와 응답 헤더의 값을 추가하거나 바꾸거나 지웁니다.

예를 들어 실제 접속자의 주소를 별도 헤더에 담아 넘기면 백엔드는 게이트웨이 주소가 아닌 진짜 사용자를 알 수 있습니다. 반대로 내부 구조를 드러내는 헤더는 지워서 밖으로 새지 않게 합니다. 결국 헤더 재작성은 서버와 클라이언트 사이에서 주고받는 부가 정보를 상황에 맞게 정리해, 양쪽이 서로를 정확히 알아보게 만드는 손질입니다.

4부. 리스너와 라우팅043

다중 사이트 인증서 선택

여러 도메인에 각각 다른 인증서를 붙이는 법

한 게이트웨이 뒤에 회사 블로그, 쇼핑몰, 관리자 페이지를 각각 다른 도메인으로 운영한다고 해 봅시다. 인증서를 하나만 올려 두면 두 번째 도메인으로 접속한 방문자는 이름이 맞지 않는 인증서를 받게 되고, 브라우저는 곧바로 경고 화면을 띄워 신뢰를 잃게 만듭니다. 이 문제를 푸는 기능이 다중 사이트 인증서 선택, 다른 말로 서버 이름 표시(Server Name Indication, SNI) 기반 선택입니다.

아파트 로비의 안내데스크를 떠올리면 이해가 쉽습니다. 방문객은 데스크에 도착하자마자 자신이 찾는 세대의 이름을 먼저 말하고, 안내데스크는 그 이름에 맞는 출입증을 골라 건네줍니다. 웹에서도 암호화 연결을 시작할 때 접속하려는 도메인 이름을 먼저 알려 주는데 이것이 SNI이고, 게이트웨이는 그 이름에 묶여 등록된 인증서를 골라 제시합니다.

그래서 리스너(listener)마다 호스트 이름과 인증서를 한 쌍으로 등록해 두면 도메인별로 다른 인증서를 쓸 수 있고, 등록되지 않은 이름으로 들어오면 미리 정한 기본 인증서가 대신 나갑니다.

정리하면 다중 사이트 인증서 선택은 하나의 수신 지점에서 여러 도메인을 받으면서 SNI 값에 따라 알맞은 전송 계층 보안(Transport Layer Security, TLS) 인증서를 골라 주는 구성이고, 도메인마다 리스너와 인증서를 짝지어 관리하는 것이 핵심입니다.

4부. 리스너와 라우팅044

라우팅 규칙 디버깅

왜 다른 백엔드로 갔는지 추적하기

라우팅 규칙을 여러 개 걸어 두고 운영하다 보면 분명 A 서비스로 보낸 요청이 B 서비스에서 처리되는 일이 생깁니다. 원인을 모른 채 설정을 이것저것 바꾸면 증상만 옮겨 다니므로, 요청이 어느 규칙을 타고 어느 백엔드로 갔는지 역으로 추적하는 라우팅 규칙 디버깅이 필요합니다.

택배 분류센터를 떠올려 보면 구조가 잘 보입니다. 분류 담당자는 주소 라벨을 위에서부터 차례로 읽으며 처음으로 맞는 벨트에 상자를 올리고, 어느 벨트에도 해당하지 않으면 기본 벨트로 보냅니다. 게이트웨이도 리스너(listener)에서 요청을 받아 규칙 목록을 순서대로 검사하고, 호스트 이름과 경로 조건이 맞는 첫 규칙의 백엔드 풀(backend pool)로 요청을 넘깁니다.

그래서 디버깅은 어떤 리스너가 요청을 받았는지, 그 리스너에 붙은 규칙의 우선순위와 경로 패턴이 무엇인지, 대상 백엔드가 상태 프로브(health probe)에서 정상으로 판정되는지를 차례로 확인하는 일입니다.

정리하면 라우팅 디버깅은 리스너, 규칙 우선순위, 경로 조건, 백엔드 상태를 순서대로 좁혀 요청의 이동 경로를 복원하는 작업입니다.

5부. 백엔드 풀과 상태 프로브045

백엔드 풀(Backend Pool)

요청을 넘길 서버 목록을 만드는 일

요청을 넘길 서버가 한 대뿐이라면 주소 하나만 적어 두면 됩니다. 하지만 서비스가 커지면 여러 대의 서버에 요청을 나눠 보내야 하고, 서버를 늘리거나 뺄 때마다 설정을 고치는 일이 반복되면 실수가 쌓입니다. 이때 서버 목록을 한곳에 모아 관리하는 단위가 백엔드 풀(Backend Pool)입니다.

식당 홀 매니저가 주문을 넘길 주방 담당자 명단을 들고 있다고 생각해 봅시다. 매니저는 명단에 적힌 사람에게만 주문을 넘기고, 한 사람이 너무 바쁘면 다음 사람에게 돌리며, 새 직원이 들어오면 명단에 이름을 추가합니다. 백엔드 풀도 마찬가지로 요청을 받을 서버들의 주소를 항목으로 담고, 그 목록을 기준으로 부하 분산과 상태 확인이 이루어지며, 서버를 추가하거나 제거할 때는 목록의 항목만 바꾸면 됩니다.

즉 백엔드 풀은 요청을 넘길 서버 목록을 하나의 이름으로 묶어 관리하는 자원이고, 라우팅 규칙은 서버 하나가 아니라 이 풀을 가리킵니다.

5부. 백엔드 풀과 상태 프로브046

백엔드 대상 유형

IP·FQDN·App Service·VMSS를 지정하는 방법

백엔드 풀에 서버를 넣을 때는 무엇을 기준으로 주소를 적을지 정해야 하는데, 이 선택지를 백엔드 대상 유형이라고 합니다. 기준을 잘못 고르면 서버가 교체될 때마다 주소가 어긋나 요청이 실패합니다.

택배를 보낼 때 받는 곳을 적는 방법이 여러 가지인 것과 같습니다. 정확한 좌표를 적는 방식은 IP 주소 지정이고, 건물 이름과 호수를 적는 방식은 정규화된 도메인 이름(Fully Qualified Domain Name, FQDN) 지정입니다. 택배 대행 업체에 맡기듯 플랫폼이 관리하는 서비스를 그대로 가리키는 방식이 App Service 지정이고, 같은 모양의 집이 자동으로 늘어나는 단지를 가리키는 방식이 가상 머신 확장 집합(Virtual Machine Scale Set, VMSS) 지정입니다.

IP와 FQDN은 주소 자체를 적는 방식이라 유연하지만 서버가 바뀌면 손이 가고, App Service와 VMSS는 플랫폼이 대상을 관리하므로 확장과 교체가 잦은 환경에 어울립니다.

정리하면 백엔드 대상 유형은 서버를 주소로 가리킬지 플랫폼 자원으로 가리킬지 고르는 일이고, 운영 방식에 맞춰 선택해야 합니다.

5부. 백엔드 풀과 상태 프로브047

VM을 백엔드에 넣는 두 가지 방식

NIC 기준 지정과 IP 직접 지정의 차이

같은 가상 머신(Virtual Machine, VM)을 백엔드에 넣는 방법도 두 가지인데, 결과만 보면 비슷해 보여도 관리 방식이 크게 다릅니다. 차이를 모르고 고르면 VM을 다시 만들었을 때 백엔드가 조용히 비는 일이 생깁니다.

사람을 부를 때 명함을 주고받는 방식과 전화번호만 적어 두는 방식을 떠올려 보면 좋습니다. 명함에 적힌 신원 정보를 기준으로 부르면 그 사람이 부서를 옮겨도 명함 정보가 갱신되는 한 연락이 닿는데, 이것이 네트워크 인터페이스(Network Interface, NIC) 기준 지정입니다. 반대로 전화번호만 적어 두면 번호가 바뀌는 순간 연락이 끊기므로 직접 고쳐야 하고, 이것이 IP 주소 직접 지정입니다.

NIC 기준은 가상 머신의 네트워크 인터페이스 자원을 참조하므로 주소가 바뀌어도 따라가지만 같은 가상 네트워크 안의 자원이어야 하고, IP 직접 지정은 어디에나 쓸 수 있는 대신 변경을 사람이 관리해야 합니다.

결국 두 방식의 차이는 대상을 신원으로 묶느냐 주소로 묶느냐이며, 교체가 잦은 환경이라면 NIC 기준이 안전합니다.

5부. 백엔드 풀과 상태 프로브048

상태 프로브(Health Probe)

백엔드가 정상인지 판정하는 규칙

백엔드 서버 한 대가 조용히 멈춰도 게이트웨이는 그 사실을 모른 채 요청을 계속 보낼 수 있습니다. 사용자는 계속 오류를 받게 되므로, 서버가 정상인지 주기적으로 판정하는 규칙인 상태 프로브(Health Probe)가 필요합니다.

식당 매니저가 주문을 넘기기 전에 주방에 전화해 지금 받을 수 있는지 확인하는 모습과 같습니다. 전화를 받지 않거나 대답이 늦으면 그 담당자를 잠시 명단에서 빼고 다른 사람에게 주문을 넘깁니다. 상태 프로브도 정해진 주기로 백엔드에 요청을 보내 응답 코드와 응답 시간을 보고, 정해진 횟수만큼 실패하면 그 백엔드를 풀에서 빼며, 다시 정상 응답이 이어지면 복귀시킵니다.

이때 확인할 경로와 포트, 주기, 실패 판정 횟수를 함께 정해야 하며, 이 값이 백엔드의 실제 동작과 어긋나면 멀쩡한 서버가 계속 제외됩니다.

정리하면 상태 프로브는 백엔드가 요청을 받을 준비가 되었는지 규칙에 따라 판정해 트래픽 대상에서 넣고 빼는 장치입니다.

사용자 정의 프로브

경로·간격·임계값을 직접 정하기

서버가 살아 있는지만 확인하는 획일적인 점검으로는 서비스마다 다른 사정을 담아내지 못해, 트래픽이 몰리는 서버의 이상을 늦게 발견하거나 멀쩡한 서버를 성급히 빼는 일이 생깁니다. 그래서 Application Gateway에는 점검할 경로와 주기, 판정 기준을 운영자가 직접 정하는 사용자 정의 프로브(custom probe)가 있습니다.

아파트 경비원의 순찰에 비유하면, 먼저 어느 구역을 도는지 정하는 순찰 경로가 프로브 경로에 해당합니다. 몇 분마다 한 바퀴 도는지 정하는 순찰 주기가 프로브 간격이고, 이 간격이 짧으면 이상을 빨리 알 수 있지만 서버는 그만큼 자주 응답해야 합니다. 몇 번 연속으로 문제를 발견해야 보고할지를 정하는 기준이 임계값(threshold)이며, 한 번의 실수로 서버를 빼지 않도록 여유를 두는 장치입니다.

여기에 정상 판정을 위한 임계값을 따로 두어, 회복된 서버가 곧바로 복귀하지 않고 충분히 정상임을 확인한 뒤 돌아오게 할 수 있습니다.

정리하면 사용자 정의 프로브는 프로브 경로, 간격, 임계값을 서비스 특성에 맞게 조정해 백엔드의 건강 상태 판정을 운영자 손에 맡기는 기능입니다. 기본 점검으로 충분하지 않은 서비스일수록 이 세 가지 값을 자기 환경에 맞춰 정하는 일이 중요합니다.

프로브 실패 시 백엔드 제거와 복귀

서버를 언제 빼고 언제 되돌리는가

택배 회사의 배송 기사 배정에 비유하면, 배정 명단에 올라 있는 기사에게만 물량이 가고 연락이 닿지 않는 기사는 명단에서 빠집니다.

몇 번 연속 연락이 안 될 때 명단에서 뺄지를 정하는 것이 비정상 임계값(unhealthy threshold)이고, 몇 번 연속 정상 배송을 확인해야 다시 명단에 넣을지를 정하는 것이 정상 임계값(healthy threshold)입니다. 명단에서 빠진 동안에도 게이트웨이는 프로브를 계속 보내 회복 여부를 확인하며, 이 확인 주기가 곧 프로브 간격입니다. 이렇게 빼는 기준과 되돌리는 기준을 따로 두면 일시적인 지연과 실제 고장을 구분할 수 있습니다.

정리하면 프로브 실패 시 백엔드 제거와 복귀는 비정상 임계값과 정상 임계값, 프로브 간격으로 결정되는 상태 전환 절차입니다. 이 두 임계값을 서비스의 민감도에 맞게 조정하는 것이 오탐과 미탐 사이의 균형을 잡는 일입니다.

5부. 백엔드 풀과 상태 프로브051

세션 선호도(Session Affinity)

같은 사용자를 같은 서버로 보내는 쿠키 방식

로그인한 사용자가 다음 화면에서 갑자기 로그아웃되거나 장바구니가 비어 보이는 일은, 요청마다 다른 서버로 보내졌기 때문에 생깁니다. 세션 정보를 서버마다 따로 들고 있는 구조에서는 같은 사용자를 같은 서버로 붙여 주는 세션 선호도(session affinity)가 그 해결책이 됩니다.

단골 미용실에 비유하면, 접수할 때 담당 디자이너 이름을 적은 접수증을 손님에게 쥐여 주는 것이 쿠키(cookie) 방식입니다. 다음에 손님이 접수증을 내밀면 데스크가 그 이름을 보고 같은 디자이너에게 안내하듯, 게이트웨이는 쿠키에 담긴 표식을 읽어 같은 백엔드로 요청을 보냅니다.

이 표식은 게이트웨이가 직접 발급하는 경우와 백엔드가 심은 쿠키를 그대로 활용하는 경우가 있으며, 후자는 기존 애플리케이션을 크게 고치지 않아도 된다는 장점이 있습니다. 다만 담당 디자이너가 휴무이면 손님이 다른 사람에게 배정되듯, 해당 서버가 빠지면 선호도는 깨지고 세션도 새로 시작될 수 있습니다.

정리하면 세션 선호도는 쿠키에 남긴 표식을 근거로 같은 사용자의 요청을 같은 백엔드로 유지하는 방식입니다. 부하 분산과 세션 유지가 서로 당기는 지점을 이해하고, 쿠키 만료와 서버 이탈 상황까지 함께 설계해야 합니다.

백엔드 HTTP 설정(Backend Settings)

백엔드로 보낼 때의 프로토콜과 포트

백엔드가 443번 포트에서 암호화된 연결만 받는데 게이트웨이가 80번 포트로 평문 요청을 보내면, 목록에 서버가 멀쩡히 있어도 요청은 번번이 실패합니다. 그래서 Application Gateway는 백엔드로 나갈 때 쓸 프로토콜과 포트를 백엔드 HTTP 설정(backend settings)으로 따로 지정합니다.

회사 건물에 우편을 보내는 일에 비유하면, 봉투를 항공편으로 보낼지 육상으로 보낼지 고르는 것이 프로토콜(protocol) 선택입니다. 암호화된 HTTPS는 내용을 봉인해 보내는 방식이고 HTTP는 봉인 없이 보내는 방식이라, 어느 쪽으로 받도록 되어 있는지 서로 맞춰야 합니다.

건물의 어느 출입구로 들어갈지를 정하는 것이 포트(port)이며, 서버가 열어 둔 문과 다른 문을 두드리면 응답이 없습니다. 게이트웨이는 이 설정을 백엔드 풀 단위로 묶어 적용하므로, 같은 풀에 속한 서버들은 같은 프로토콜과 포트로 불러야 합니다.

정리하면 백엔드 HTTP 설정은 게이트웨이가 백엔드로 요청을 보낼 때 사용할 프로토콜과 포트를 정하는 구성입니다. 프런트엔드에서 받는 방식과 백엔드로 보내는 방식을 따로 둘 수 있다는 점이 이 설정의 핵심입니다.

5부. 백엔드 풀과 상태 프로브053

호스트 이름 재정의(Host Name Override)

백엔드에 넘길 Host 헤더 바꾸기

백엔드 서버 한 대가 여러 사이트를 함께 서비스하는데 요청의 Host 헤더가 게이트웨이 주소로 남아 있으면, 서버는 어느 사이트의 응답을 내야 할지 판단하지 못합니다. 이때 백엔드로 넘길 Host 헤더를 지정하는 호스트 이름 재정의(host name override)를 씁니다.

한 건물에 여러 회사가 입주한 오피스에 비유하면, 택배 기사는 건물 주소만 보고 들어오지만 실제로 물건을 전할 곳은 문패에 적힌 회사 이름으로 정해집니다.

게이트웨이가 요청을 보낼 때 붙이는 Host 헤더가 바로 그 문패이고, 재정의 설정은 택배 기사가 들고 간 문패 이름을 다른 이름으로 바꿔 다는 일입니다. 이 설정을 켜지 않으면 원래 요청에 실려 온 Host 값이 그대로 전달되고, 켜면 운영자가 지정한 이름으로 바뀌어 전달됩니다. 이름이 바뀌면 백엔드는 그 이름에 맞는 사이트 설정과 인증서를 고르게 되므로, 실제로 백엔드가 기대하는 이름을 정확히 적어야 합니다.

정리하면 호스트 이름 재정의는 게이트웨이가 백엔드로 전달하는 Host 헤더 값을 지정한 이름으로 바꾸는 설정입니다. 하나의 백엔드가 여러 이름을 받는 구조에서 특히 유용하지만, 백엔드가 기대하는 이름과 어긋나면 오히려 오류를 부릅니다.

연결 드레이닝(Connection Draining)

서버를 뺄 때 진행 중인 요청을 마저 처리하기

서버를 점검하거나 교체하려고 목록에서 빼는 순간 처리 중이던 요청까지 끊기면, 결제 도중이던 사용자는 오류 화면을 보게 됩니다. 그래서 새 연결은 받지 않으면서 이미 들어온 요청은 끝까지 처리하게 해 주는 연결 드레이닝(connection draining)을 함께 설정합니다.

식당 마감에 비유하면, 입구에 영업 종료를 알려 새 손님은 받지 않되 자리에 앉은 손님의 식사는 끝까지 마치게 하는 것과 같습니다.

게이트웨이는 해당 백엔드를 목록에서 빼고 새 요청을 다른 서버로 돌리면서, 이미 연결된 요청은 제한 시간 안에서 마저 처리되도록 기다립니다. 제한 시간이 너무 짧으면 마무리 중인 요청이 끊기고, 너무 길면 서버를 실제로 내리는 시점이 그만큼 늦어집니다. 그래서 서비스가 요청 하나를 처리하는 데 걸리는 시간을 기준으로 여유 있게 잡는 것이 보통입니다.

정리하면 연결 드레이닝은 백엔드를 제거할 때 신규 트래픽은 차단하고 진행 중인 요청은 제한 시간 안에서 완료시키는 절차입니다. 무중단 배포와 점검을 위해 제거 절차에 반드시 함께 설계해야 하는 요소입니다.

5부. 백엔드 풀과 상태 프로브055

백엔드 TLS

게이트웨이와 백엔드 사이 구간까지 암호화하기

게이트웨이가 외부와 주고받는 구간을 암호화해 두어도 게이트웨이에서 백엔드 서버로 이어지는 안쪽 구간이 평문으로 열려 있으면, 같은 망에 접근할 수 있는 사람은 요청과 응답을 그대로 들여다보거나 중간에서 내용을 바꿔치기할 수 있습니다. 백엔드 TLS(Backend TLS)는 이 마지막 구간까지 암호화해 게이트웨이와 백엔드 사이의 연결을 끝까지 닫아 두는 기능입니다.

회사 우편실을 떠올려 보면 이해가 쉽습니다. 외부에서 들어온 우편물은 봉인이 붙은 봉투로 오지만, 우편실에서 각 부서로 다시 배달할 때 내용물이 훤히 보이는 투명 봉투에 그대로 담아 보낸다면 사내를 오가는 사람 누구나 그 내용을 읽을 수 있습니다.

그래서 우편실 직원이 부서로 보내기 직전에 내용물을 새 봉투에 넣고 다시 봉인하는데, 이 두 번째 봉인이 백엔드 TLS에 해당합니다. 게이트웨이는 백엔드와 연결을 맺을 때 별도의 암호화 협상(TLS 핸드셰이크)을 하고, 그 협상으로 정한 열쇠로만 안쪽 구간의 대화를 주고받습니다.

정리하면 백엔드 TLS는 게이트웨이가 백엔드로 보내는 트래픽에 대해 별도의 TLS(Transport Layer Security) 연결을 맺어, 외부 구간과 내부 구간을 각각 독립적으로 암호화하는 구성입니다. 이때 백엔드 인증서를 검증하도록 설정해야 중간자 가장을 막을 수 있고, 인증서가 만료되면 연결이 끊기므로 만료 관리도 함께 필요합니다.

5부. 백엔드 풀과 상태 프로브056

백엔드 상태 화면 읽기

풀 화면에서 비정상 대상을 찾아내는 법

백엔드가 여러 대 묶인 풀(pool)에서 한 대가 조용히 응답을 멈추면, 게이트웨이는 겉으로는 정상처럼 보이는데 일부 사용자만 간헐적으로 오류를 겪는 상황이 생깁니다. 백엔드 상태 화면은 풀에 속한 대상 각각의 건강 상태를 한눈에 보여 주어, 어느 대상이 비정상인지 빠르게 찾아내게 해 주는 화면입니다.

아파트 경비실 벽에 세대별 상태 등을 켜 두는 판이 있다고 생각해 보십시오. 초록불은 정상, 빨간불은 고장, 노란불은 확인 중인데, 경비원은 이 판을 보고 어느 집에 문제가 생겼는지 바로 알 수 있습니다. 백엔드 상태 화면도 같은 방식으로 대상마다 정상(healthy), 비정상(unhealthy), 확인 중(unknown) 같은 상태를 표시하고 마지막 점검 시각과 실패 사유를 함께 보여 줍니다.

여기서 중요한 것은 게이트웨이가 주기적으로 각 대상에 상태 확인 요청(health check)을 보내 응답 코드와 응답 시간을 보고 판정한다는 점이며, 화면은 그 결과를 모아 보여 주는 창일 뿐입니다.

정리하면 백엔드 상태 화면은 상태 확인 결과를 대상 단위로 보여 주는 진단 도구이고, 비정상 표시가 뜬 대상은 풀에서 빠져 트래픽을 받지 않게 됩니다. 따라서 화면에서 빨간 상태가 늘어난다면 개별 서버의 자원이나 애플리케이션 응답을 먼저 확인하고, 특정 대상만 계속 실패하면 그 대상의 설정이나 네트워크 경로를 따로 점검해야 합니다.

6부. HTTP 설정과 트래픽 제어057

HTTP/1.1과 HTTP/2

게이트웨이가 말하는 두 프로토콜의 차이

웹 페이지 하나를 열어도 수십 개의 요청이 오가는데, 연결마다 요청을 하나씩 보내고 응답을 기다리는 방식으로는 앞선 요청이 끝나야 다음 요청을 보낼 수 있어 화면이 늦게 뜹니다. HTTP/1.1과 HTTP/2는 게이트웨이가 클라이언트와 대화할 때 쓸 수 있는 두 가지 프로토콜(protocol)로, 같은 요청을 어떻게 실어 나르느냐에서 차이가 납니다.

택배 창고를 비유로 들면 차이가 분명해집니다. HTTP/1.1이 트럭 한 대에 상자를 하나만 싣고 왕복하는 규칙이라면, HTTP/2는 여러 상자를 한 트럭에 함께 실어 보내고 도착하는 순서대로 내리는 규칙입니다. HTTP/2는 이렇게 하나의 연결 위에 여러 요청을 동시에 주고받는 다중화(multiplexing)를 하고, 헤더를 압축하며, 같은 연결을 계속 재사용합니다. 반면 HTTP/1.1은 연결을 여러 개 열어 병렬로 보내는 식으로 부족한 점을 메우지만, 연결 수가 늘어날수록 그만큼 부담도 커집니다.

정리하면 HTTP/1.1은 연결마다 요청과 응답을 순서대로 주고받는 텍스트 기반 규약이고, HTTP/2는 하나의 연결에서 여러 요청을 동시에 다루는 바이너리 기반 규약입니다. 게이트웨이는 클라이언트와는 HTTP/2로, 백엔드와는 HTTP/1.1로 대화하는 식으로 양쪽을 다르게 설정할 수 있으므로, 어느 구간이 어떤 프로토콜인지 확인해 두는 것이 좋습니다.

6부. HTTP 설정과 트래픽 제어058

WebSocket과 HTTP/2 스트리밍

실시간 연결을 중계하는 방식

채팅이나 주식 시세처럼 서버에서 먼저 알려 줘야 하는 데이터를 일반 HTTP 요청으로 받으려면 클라이언트가 짧은 간격으로 계속 물어봐야 하고, 그때마다 연결을 새로 맺느라 지연과 낭비가 쌓입니다. WebSocket과 HTTP/2 스트리밍은 이렇게 한 번 열어 둔 연결을 끊지 않고 계속 대화하는 방식이며, 게이트웨이는 그런 실시간 연결을 중계하는 역할을 맡습니다.

우체국 편지와 전화 통화의 차이를 떠올리면 이해가 쉽습니다. 편지는 한 번 보내면 끝나고 다시 받으려면 또 보내야 하지만, 전화는 한 번 연결되면 끊을 때까지 양쪽이 언제든 말할 수 있습니다. WebSocket(웹소켓)은 전화 통화처럼 한 번 협상으로 연결을 열고 나면 양방향으로 데이터를 계속 주고받는 방식이고, HTTP/2 스트리밍은 이미 열린 HTTP/2 연결 위에서 응답을 한 번에 다 보내지 않고 조각조각 흘려보내는 방식입니다. 게이트웨이는 이 연결을 백엔드까지 이어 주어야 하므로, 연결이 유지되는 동안 자원을 계속 붙잡고 있고 중간 장비가 오래된 연결을 끊지 않도록 시간 제한을 넉넉히 맞춰 두어야 합니다.

정리하면 WebSocket은 연결을 업그레이드(upgrade)해 양방향 통로를 만들고, HTTP/2 스트리밍은 하나의 연결 안에서 응답을 나눠 보내 실시간처럼 데이터를 전달합니다. 두 방식 모두 일반 요청보다 연결 수명이 길기 때문에, 게이트웨이의 유휴 시간 제한과 백엔드의 타임아웃을 서로 맞추지 않으면 연결이 예고 없이 끊기는 일이 생깁니다.

6부. HTTP 설정과 트래픽 제어059

연결 유지(Keep-Alive)와 유휴 시간 제한

연결을 얼마나 붙잡고 있을 것인가

요청이 올 때마다 연결을 새로 맺고 끊으면 그때마다 암호화 협상과 왕복 지연이 붙어, 트래픽이 많을수록 체감 속도가 눈에 띄게 느려집니다. 연결 유지(Keep-Alive)는 이 비용을 줄이려고 한 번 맺은 연결을 다음 요청을 위해 남겨 두는 기능이고, 유휴 시간 제한(idle timeout)은 그렇게 남겨 둔 연결을 언제 정리할지 정하는 값입니다.

카페 좌석을 떠올려 보면 두 설정의 관계가 잘 드러납니다. 손님이 올 때마다 자리를 새로 세팅하고 떠나면 바로 치우는 가게는 회전은 빠르지만 준비할 손이 많이 들고, 자리를 그대로 두는 가게는 다음 손님이 바로 앉을 수 있습니다. 다만 아무도 앉지 않는 자리를 한없이 그대로 두면 그 자리가 계속 묶여 다른 손님이 못 앉으므로, 일정 시간이 지나면 정리하는 규칙이 필요합니다.

Keep-Alive가 자리를 남겨 두는 규칙이라면 유휴 시간 제한은 그 자리를 비울 시점을 정하는 규칙이고, 게이트웨이는 이 시간 동안 요청이 없는 연결을 닫아 자원을 회수합니다.

정리하면 연결 유지(Keep-Alive)는 TCP 연결을 재사용해 핸드셰이크 비용을 줄이는 기능이고, 유휴 시간 제한은 재사용할 연결을 얼마나 보관할지 정하는 값입니다. 이 값이 백엔드나 중간 장비의 제한보다 길면 게이트웨이가 이미 닫힌 연결에 요청을 보내 실패할 수 있으므로, 구간마다 설정을 더 짧은 쪽에 맞추는 것이 안전합니다.

6부. HTTP 설정과 트래픽 제어060

요청 제한 시간과 응답 제한 시간

느린 백엔드를 언제 끊을 것인가

백엔드 한 대가 응답을 아주 느리게 주면 그 요청을 기다리는 연결이 계속 쌓이고, 결국 정상 백엔드까지 자원이 바닥나 전체가 함께 느려지거나 멈춥니다. 요청 제한 시간(request timeout)과 응답 제한 시간(response timeout)은 이런 느린 백엔드를 언제 포기하고 끊을지 정하는 두 개의 시간 값입니다.

식당에서 주문을 받는 상황을 비유로 들면 구분이 쉬워집니다. 손님이 주문서를 내는 데 시간이 오래 걸리면 홀 직원이 언제까지 기다릴지 정해야 하고, 주문을 받은 뒤 주방에서 음식이 언제 나올지 기다리는 시간도 따로 정해야 합니다. 요청 제한 시간은 클라이언트가 요청을 끝까지 보내는 데 걸리는 시간을 제한하는 값이고, 응답 제한 시간은 게이트웨이가 백엔드에 요청을 넘긴 뒤 응답이 시작되거나 완료되기를 기다리는 시간을 제한하는 값입니다.

기다리는 시간이 정해진 값을 넘으면 게이트웨이는 그 연결을 끊고 오류를 돌려주어, 느린 요청 하나가 전체 자원을 붙잡지 않게 합니다.

정리하면 요청 제한 시간은 들어오는 요청을 받아들이는 구간의 상한이고, 응답 제한 시간은 백엔드가 응답할 때까지 기다리는 구간의 상한입니다. 두 값은 백엔드의 실제 처리 시간과 재시도 정책을 함께 고려해 정해야 하며, 너무 짧으면 정상 요청이 잘리고 너무 길면 느린 백엔드가 자원을 오래 붙잡습니다.

최대 요청 본문 크기

파일 업로드가 갑자기 막히는 이유

서비스가 잘 돌아가던 어느 날, 사용자가 사진과 첨부 파일을 올리기 시작하면서 갑자기 업로드가 막히기 시작했습니다. 화면에는 아무 설명도 없이 실패만 뜨고, 개발자는 애플리케이션 로그에도 흔적이 없는 상황을 마주합니다.

이때 가장 먼저 의심해야 하는 것이 게이트웨이가 허용하는 요청 본문의 최대 크기(max request body size) 설정입니다. 애플리케이션 게이트웨이는 사용자와 서버 사이에서 요청을 대신 받아 넘기는 입구 역할을 하므로, 그 입구에 설치된 크기 제한이 본문이 서버에 닿기도 전에 요청을 잘라내기 때문입니다. 이를 아파트 택배로 비유해 보면 이해가 쉽습니다. 경비실에는 택배 보관함 크기가 정해져 있어서 그보다 큰 상자는 집 앞까지 올라가지 못하고 경비실에서 반송됩니다. 택배 기사가 아무리 큰 물건을 가져와도 경비실 규칙이 우선이고, 세대 안에서는 무슨 일이 있었는지조차 알 수 없습니다. 게이트웨이의 최대 본문 크기도 이 보관함과 똑같이 요청을 받아들이느냐 마느냐를 결정하는 문턱이고, 이 문턱은 애플리케이션 설정과 별개로 게이트웨이 쪽에서 먼저 적용됩니다.

그래서 업로드가 막힐 때는 애플리케이션 코드보다 게이트웨이의 크기 제한을 먼저 확인해야 합니다. 정리하면 최대 요청 본문 크기는 게이트웨이가 한 번에 받아들일 수 있는 요청 본문의 상한이며, 이 값을 넘는 요청은 업로드 단계에서 거부됩니다. 파일 업로드를 다루는 서비스라면 예상 최대 파일 크기와 인코딩으로 늘어나는 여유분을 함께 계산해 이 값을 조정해야 합니다.

선호도 쿠키 설정

쿠키 이름과 만료를 다루는 방법

여러 서버에 요청을 나눠 보내는 구조에서는 같은 사용자가 매번 다른 서버로 흩어지면서 장바구니가 비거나 로그인이 풀리는 일이 생깁니다. 앞단의 게이트웨이가 사용자를 어느 서버로 보낼지 기억하지 못하면, 세션 정보가 특정 서버에만 남아 있기 때문입니다. 이 문제를 풀기 위해 게이트웨이는 선호도 쿠키(affinity cookie)라는 작은 표식을 사용자의 브라우저에 심고, 그 표식을 보고 같은 사용자를 같은 서버로 계속 보내 줍니다. 이를 회사 건물의 담당 창구로 비유할 수 있습니다. 방문증에 담당자 이름과 유효기간이 적혀 있으면 안내데스크는 그 사람을 늘 같은 창구로 보내 주고, 방문증이 만료되면 새로 발급해 다시 배정합니다.

여기서 쿠키 이름은 방문증의 제목, 만료 시각은 방문증에 적힌 유효기간에 해당하며, 게이트웨이는 이 두 가지를 설정값으로 정합니다. 이름이 겹치면 다른 용도의 쿠키와 섞여 엉뚱한 서버로 보내질 수 있으므로 서비스마다 구분되는 이름을 쓰는 것이 좋고, 만료를 너무 짧게 두면 사용자가 조금만 자리를 비워도 선호도가 초기화됩니다. 반대로 너무 길게 두면 서버를 교체하거나 제거한 뒤에도 오래된 표식이 남아 오류를 일으킬 수 있습니다. 정리하면 선호도 쿠키는 게이트웨이가 사용자와 특정 백엔드 서버의 짝을 유지하려고 브라우저에 남기는 표식이며, 쿠키 이름과 만료 시간은 이 짝이 얼마나 오래 유지되는지를 정하는 핵심 설정입니다.

재작성 조건과 서버 변수

조건이 맞을 때만 재작성을 적용하기

서비스가 커지면 요청 주소나 헤더를 게이트웨이에서 한 번 손봐서 넘겨야 하는 경우가 많아집니다. 그런데 모든 요청에 같은 규칙을 적용하면 정상 동작하던 경로까지 바뀌어 버려 장애가 생깁니다.

그래서 게이트웨이는 재작성(rewrite) 규칙에 조건을 붙여, 조건이 맞는 요청에만 주소나 헤더를 바꾸도록 합니다. 이때 조건을 판단하는 재료로 쓰이는 것이 서버 변수(server variable)입니다. 이를 우편물 분류로 비유해 보면, 우체국에서는 모든 봉투를 뜯지 않고 겉면에 적힌 주소나 표식만 보고 분류합니다. 받는 사람 주소, 보낸 사람 지역, 우표 종류 같은 겉면 정보가 판단 재료가 되고, 이 정보가 특정 조건과 맞을 때만 다른 주소로 다시 써서 보냅니다.

게이트웨이의 서버 변수도 요청 경로, 호스트 이름, 쿼리 문자열, 헤더 값처럼 요청 겉면에 이미 적혀 있는 정보이며, 재작성 조건은 이 변수가 어떤 값일 때만 규칙을 적용할지 정합니다. 예를 들어 경로가 특정 접두사로 시작할 때만 뒷부분을 잘라내거나, 특정 호스트로 들어온 요청에만 헤더를 덧붙이는 식입니다. 조건을 좁게 잡을수록 의도한 요청만 바뀌고 나머지는 원래대로 흘러갑니다. 정리하면 재작성 조건은 서버 변수라는 요청의 겉면 정보를 검사해 규칙 적용 여부를 가리는 장치이고, 이를 통해 주소 변형이 필요한 요청에만 선별적으로 손을 댈 수 있습니다.

응답 압축과 콘텐츠 인코딩

응답 크기를 줄여 전송하기

응답이 커지면 사용자는 화면이 뜨기를 하염없이 기다리고, 회선 요금도 함께 늘어납니다. 같은 내용을 매번 그대로 보내는 것이 낭비라는 사실은 분명한데, 서버와 브라우저 사이의 약속이 맞지 않으면 압축을 켜 두어도 아무 효과가 없습니다. 이 약속을 다루는 개념이 콘텐츠 인코딩(content encoding)이고, 게이트웨이는 여기서 응답을 압축해 보내는 역할을 맡습니다. 이를 이삿짐 포장으로 비유할 수 있습니다. 짐을 진공 압축 팩에 넣으면 부피가 크게 줄어 트럭 한 대로 더 많이 나르지만, 받는 쪽에 압축 팩을 풀 도구가 없으면 짐을 꺼낼 수 없습니다. 그래서 보내는 쪽은 "이 짐은 압축해서 보냈다"는 표시를 붙이고, 받는 쪽은 그 표시를 보고 풀 방법을 고릅니다.

웹에서는 브라우저가 요청할 때 어떤 압축 방식을 풀 수 있는지 알려 주고, 게이트웨이는 그중 지원되는 방식을 골라 응답 본문을 압축한 뒤 응답 헤더에 어떤 방식으로 압축했는지 적습니다. 이미 압축된 이미지나 동영상처럼 더 줄일 여지가 없는 형식은 다시 압축해도 효과가 없고 오히려 시간만 쓰므로, 게이트웨이는 보통 응답의 형식과 크기를 보고 압축 대상인지 판단합니다. 정리하면 콘텐츠 인코딩은 응답 본문을 어떤 방식으로 압축했는지 알리는 표준 약속이고, 게이트웨이는 이 약속에 맞춰 압축 가능한 응답만 골라 압축함으로써 전송량을 줄입니다.

캐싱을 두지 않는 설계

게이트웨이가 캐시를 갖지 않을 때의 대안

게이트웨이가 응답을 저장해 두고 재사용하면 빠를 것 같지만, 실제 운영에서는 그 편리함이 독이 되는 순간이 있습니다. 사용자별로 내용이 달라지는 응답이나 매초 바뀌는 값이 캐시에 남으면, 다른 사용자에게 남의 데이터가 보이거나 오래된 값이 계속 나가는 사고가 생깁니다. 그래서 어떤 설계에서는 게이트웨이가 아예 캐시를 갖지 않도록 결정하고, 속도와 정확성 사이에서 정확성을 택합니다. 이를 은행 창구로 비유해 보면, 창구 직원이 어제 처리한 잔액을 적어 두었다가 오늘 그 종이를 그대로 읽어 주면 큰일이 납니다. 그래서 창구는 어떤 경우에도 원장을 직접 확인하고, 종이 메모는 아예 두지 않습니다. 캐시를 두지 않는 게이트웨이도 마찬가지로 모든 요청을 뒤쪽 서버까지 그대로 전달해 최신 값을 받아 옵니다.

대신 속도를 잃는 부분은 다른 수단으로 메웁니다. 뒤쪽 서버나 데이터베이스 쪽에 캐시를 두어 책임 범위를 좁히거나, 정적 파일은 별도의 배포 계층에서 처리하도록 나누고, 응답 헤더로 브라우저나 중간 계층에 캐시 가능 여부를 명시해 게이트웨이는 판단에서 빠지는 구조를 씁니다. 이렇게 하면 어떤 응답이 캐시되어도 되는지 아는 주체가 데이터의 성격을 가장 잘 아는 쪽으로 옮겨 갑니다. 정리하면 캐싱을 두지 않는 설계는 게이트웨이를 항상 최신 값을 전달하는 통로로 남기고, 캐시가 필요한 부분은 서버나 배포 계층, 혹은 명시적인 캐시 지시자로 분리하는 방식입니다.

Traffic Manager·Front Door와의 역할 분담

지역 간 분산은 무엇이 맡는가

서비스가 여러 지역에 배포되면 사용자는 어느 지역의 서버로 접속해야 가장 빠른지 알 수 없고, 한 지역이 멈추면 그 지역 사용자만 서비스를 못 쓰는 일이 생깁니다. 이 문제를 게이트웨이 하나에 모두 떠맡기면 설정이 복잡해지고 장애 지점도 한곳에 몰립니다. 그래서 지역 간 분산은 Traffic Manager나 Front Door 같은 별도의 앞단 서비스가 맡고, 애플리케이션 게이트웨이는 한 지역 안에서 요청을 정리하는 역할로 나누는 것이 일반적입니다. 이를 전국 물류로 비유해 보면, 어느 물류센터로 보낼지 정하는 전국 배차 시스템과, 센터 안에서 어느 하역장으로 물건을 보낼지 정하는 현장 안내가 따로 있습니다. 전국 배차는 지역 단위로 트래픽을 나누고 장애가 난 센터를 우회시키며, 현장 안내는 센터에 도착한 화물을 세부 규칙에 따라 나눕니다.

같은 원리로 지역 간 분산을 맡는 서비스는 사용자의 위치와 각 지역의 건강 상태를 보고 어느 지역으로 보낼지 결정하고, 게이트웨이는 넘겨받은 요청에 경로 규칙, 인증, 재작성 같은 세밀한 처리를 적용합니다. 이렇게 층을 나누면 지역 장애 대응은 앞단이, 요청 단위의 정책은 게이트웨이가 맡아 각자의 변경이 서로를 흔들지 않습니다. 정리하면 Traffic Manager나 Front Door는 지역 단위의 분산과 장애 우회를, 애플리케이션 게이트웨이는 한 지역 안의 요청 처리와 정책 적용을 담당하도록 역할을 나누는 것이 핵심입니다.

호스트와 경로를 함께 쓰는 설계

도메인과 URL 경로를 조합하는 방법

회사에 서비스가 하나둘 늘어나면 게이트웨이 앞으로 들어오는 요청의 목적지를 구분할 방법이 급히 필요해집니다. 주소만 보고 판단하면 같은 서버 주소를 쓰는 여러 서비스가 뒤섞이고, 경로만 보고 판단하면 여러 도메인을 함께 운영할 때 남의 서비스로 요청이 새어 들어갑니다.

호스트와 경로를 함께 쓰는 설계는 이 두 가지 단서를 조합해 요청을 정확히 나누는 방법입니다. 호스트는 요청이 어느 도메인으로 왔는지를 가리키는 이름이고, 경로는 그 도메인 안에서 어떤 자원을 원하는지를 가리키는 주소의 뒷부분입니다. 아파트 단지에 비유하면 이해가 쉽습니다. 단지에는 여러 동이 있고 각 동에는 호수가 붙어 있는데, 택배기사가 "3동 1201호"라는 표기를 보고 물건을 배달하듯 게이트웨이도 "쇼핑몰 도메인의 결제 경로"처럼 두 단서를 합쳐 목적지를 찾습니다. 동 번호만 보고 배달하면 같은 번호의 다른 동에 물건이 잘못 가고, 호수만 보고 배달하면 애초에 어느 단지인지 알 수 없습니다.

그래서 규칙을 세울 때는 호스트가 무엇인지 먼저 확정하고, 그다음 경로의 앞부분 단위로 담당 서비스를 정합니다. 이때 가장 구체적인 규칙을 먼저 검사하도록 순서를 정해 두어야, 넓은 규칙이 좁은 규칙을 가로채는 일이 생기지 않습니다. 정리하면 이 설계는 HTTP 요청의 호스트 헤더(host header)와 URL 경로(path)를 조건으로 삼아 라우팅 규칙을 만들고, 우선순위에 따라 가장 잘 맞는 규칙 하나를 고르는 방식입니다.

트래픽 분배 알고리즘

다섯 가지 분배 방식의 차이

서버를 여러 대 두었는데 한 대에만 요청이 몰리면 그 서버만 먼저 지쳐 응답이 느려지고, 결국 전체 서비스가 멈춘 것처럼 보입니다. 트래픽 분배 알고리즘은 들어오는 요청을 어느 백엔드로 보낼지 규칙으로 정해 부하를 고르게 나누는 장치입니다. 흔히 다섯 가지 방식이 비교되는데, 각각 무엇을 기준으로 삼는지가 다릅니다. 택배 회사 배차실에 비유해 보겠습니다. 순서대로 돌아가며 배정하는 방식은 기사 목록을 한 바퀴씩 돌면서 차례대로 일을 주는 것과 같고, 무작위 배정은 눈감고 뽑는 것과 같습니다.

기사마다 짐을 드는 힘이 다르다면 남은 여력이 많은 기사에게 먼저 주는 방식이 낫고, 이것이 연결 수가 적은 서버를 고르는 최소 연결(minimum connections) 방식입니다. 처리 능력이 큰 서버에 비례해서 더 많이 주는 가중치(weighted) 방식은 큰 트럭을 가진 기사에게 짐을 더 싣는 것과 같고, 접속을 계속 유지해야 하는 대화형 서비스에서는 같은 손님을 늘 같은 기사에게 붙이는 해시(hash) 방식이 쓰입니다.

가중치는 운영자가 직접 정하는 값이라 실제 성능이 바뀌면 다시 손봐야 한다는 점도 함께 기억해야 합니다. 결국 이 다섯 가지는 차례대로 돌리는 방식, 무작위 방식, 최소 연결 방식, 가중치 비례 방식, 해시 기반 고정 방식으로 정리되며, 서비스가 무엇을 우선하는지에 따라 골라 쓰면 됩니다.

TLS 핸드셰이크 기초

암호화 연결이 맺어지는 과정

인터넷에서 비밀번호를 입력하면 그 값이 여러 장비를 거쳐 서버까지 그대로 흘러갑니다. 아무런 보호 장치가 없다면 중간에서 몰래 들여다보거나 내용을 바꿔치기해도 사용자는 알아챌 방법이 없습니다. TLS 핸드셰이크(handshake)는 이 문제를 풀기 위해 두 컴퓨터가 대화를 시작하기 전에 서로를 확인하고 암호화 규칙을 맞추는 준비 과정이며, HTTPS라는 이름의 안전한 웹 통신도 이 과정 위에 서 있습니다. 모르는 사람에게 귀중품을 맡겨야 하는 상황에 비유할 수 있습니다. 먼저 상대가 정말 그 회사 직원인지 신분증을 확인하고, 그다음 둘만 아는 열쇠를 함께 만들어 냅니다.

이때 신분증 역할을 하는 것이 서버 인증서이고, 열쇠를 함께 만드는 절차는 상대만 풀 수 있는 자물쇠를 주고받는 방식으로 이루어져 실제 열쇠 자체가 회선 위를 그대로 지나가지 않습니다. 두 사람이 같은 열쇠를 갖게 되면 그 뒤의 대화는 모두 그 열쇠로 잠가서 주고받고, 대화가 길어져도 열쇠를 매번 다시 만들지 않습니다.

다만 어떤 암호 방식이 쓰이는지는 브라우저와 서버의 버전에 따라 달라질 수 있어 하나로 단정하기는 어렵습니다. 정리하면 TLS 핸드셰이크는 인증서로 상대를 확인하고, 안전하게 공유한 대화 키를 바탕으로 이후 통신을 암호화하는 사전 협상 절차입니다.

TLS 종료(TLS Termination)

게이트웨이에서 암호화를 풀고 백엔드로 넘기기

백엔드 서버마다 암호화 인증서를 심고 갱신하려면 서버 수만큼 작업이 늘어나고, 인증서 하나가 만료되는 것만으로도 장애가 납니다. TLS 종료(termination)는 이 부담을 게이트웨이 한 곳으로 모으는 구성입니다. 게이트웨이가 사용자와는 암호화로 대화하고, 뒤쪽 서버들과는 암호화를 벗긴 상태로 주고받는 방식입니다. 아파트 현관의 경비실을 떠올리면 됩니다. 방문객은 경비실에서 신분을 확인하고 출입증을 받지만, 일단 안으로 들어오면 각 세대 문 앞에서는 다시 신분증을 검사하지 않습니다.

게이트웨이가 경비실처럼 인증서를 들고 방문객과 암호화 연결을 맺고, 확인이 끝난 요청은 내부망의 서버들에게 평문(plaintext)으로 전달합니다. 인증서를 갱신할 곳이 한 군데로 줄고 서버들은 암호 연산을 하지 않아도 되어 처리 속도가 올라가는 대신, 경비실과 세대 사이 구간은 보호되지 않으므로 내부망을 신뢰할 수 있는 환경에서만 써야 합니다.

내부 구간까지 지켜야 하는 규제 환경이라면 이 구성은 적합하지 않습니다. 결국 TLS 종료는 암호화 연결의 끝점을 게이트웨이에 두어 인증서 관리와 연산 부담을 한 곳으로 모으는 방식이며, 내부망 신뢰를 전제로 합니다.

엔드투엔드 TLS

양 끝단까지 암호화를 유지하는 구성

게이트웨이에서 암호화를 풀면 내부망을 지나는 요청은 그대로 읽을 수 있는 상태가 됩니다. 내부망이 안전하다고 믿고 있었는데 그 안에 침입자가 있었다면, 사용자의 비밀번호와 개인정보가 아무 방어 없이 노출됩니다. 엔드투엔드 TLS(end-to-end TLS)는 게이트웨이에서 암호화를 풀지 않고, 사용자와 최종 서버 사이 구간 전체를 끝까지 암호화된 상태로 유지하는 구성입니다. 편지를 보낼 때 중간 우체국에서 내용을 확인하지 못하도록 봉투를 뜯지 않고 전달하는 것과 같습니다. 게이트웨이는 봉투 겉면의 주소만 보고 어디로 보낼지 판단하며, 내용을 확인할 필요가 있으면 서버가 직접 열어 봅니다.

그래서 게이트웨이는 암호를 풀지 않은 채 연결을 넘겨주는 통과 방식으로 동작하고, 서버는 자기 인증서를 따로 가져야 합니다. 인증서 관리 지점이 늘어나는 대신 내부 구간까지 보호되며, 게이트웨이가 요청 내용을 검사하거나 고치는 기능은 제한될 수 있습니다. 정리하면 엔드투엔드 TLS는 사용자부터 최종 서버까지 암호화를 끊지 않아 내부 구간의 도청과 변조를 막는 구성이고, 그만큼 인증서 운영 부담이 늘어납니다.

서버 인증서와 인증서 체인

인증서가 신뢰받기 위한 조건

브라우저가 아무 사이트나 믿고 암호화를 시작하면, 가짜 사이트가 만든 열쇠로 사용자의 정보를 가로채도 막을 방법이 없습니다. 서버 인증서(certificate)는 그 서버가 정말 그 도메인의 주인임을 증명하는 문서이며, 인증서 체인(chain)은 이 증명을 최상위 신뢰 지점까지 이어 붙인 연결 고리입니다. 여권과 비자에 비유할 수 있습니다. 내 여권만 보여 주면 그 나라가 발급했다는 사실을 상대가 확인할 수 없으므로, 여권을 발급한 기관의 도장과 그 기관을 인정하는 상위 기관의 근거가 함께 필요합니다.

인증서도 서버 인증서, 그것을 서명한 중간 인증서, 중간 인증서를 서명한 루트 인증서로 이어지고, 브라우저나 운영체제에는 루트 인증서가 미리 신뢰 목록으로 들어 있습니다. 브라우저는 이 사슬을 따라 올라가며 서명이 맞는지, 유효 기간이 지나지 않았는지, 요청한 도메인 이름과 일치하는지 확인하고, 하나라도 어긋나면 경고를 띄웁니다.

서버가 중간 인증서를 함께 보내지 않으면 사슬이 끊겨 정상 인증서인데도 신뢰받지 못하는 경우가 생깁니다. 결국 인증서는 도메인 소유를 증명하는 문서이고, 체인은 그 증명을 브라우저가 이미 신뢰하는 루트까지 연결해 주는 서명의 사슬이며, 이 사슬이 온전해야 암호화 연결이 신뢰 위에서 시작됩니다.

파일과 비밀번호로 인증서 등록하기

웹사이트에 암호화 통신을 붙이려면 서버가 인증서와 개인 키를 함께 들고 있어야 하는데, 이 둘을 따로 옮기다 보면 짝이 어긋나거나 키가 엉뚱한 곳에 남습니다. Application Gateway에서는 이 둘을 하나의 파일에 담고 비밀번호까지 걸어 올리는 PFX 형식을 씁니다.

회사 금고 열쇠를 맡기는 상황을 생각하면 됩니다. 열쇠(개인 키)와 그 열쇠가 맞는다는 것을 증명하는 등록 대장(서버 인증서)을 각각 들고 다니면 잃어버리기 쉬우니, 작은 상자(PFX 파일)에 둘을 같이 넣고 자물쇠(비밀번호)를 채워 한 번에 건넵니다.

게이트웨이는 상자를 받아 자물쇠를 풀고, 안의 대장이 열쇠와 짝이 맞는지 확인한 뒤에야 문을 엽니다. 그래서 등록 화면에서는 파일 하나와 비밀번호 한 칸만 채우면 되고, 짝이 맞지 않으면 그 자리에서 거부됩니다.

PFX는 인증서와 개인 키를 한데 담아 암호로 보호하는 컨테이너 형식이며, 게이트웨이는 이를 풀어 TLS 종료(termination)에 쓸 신원으로 등록합니다.

Key Vault 연동

비밀 저장소에서 인증서를 가져와 쓰기

인증서 파일을 게이트웨이 화면마다 직접 올리면, 갱신할 때 여러 곳을 손으로 고쳐야 하고 누가 어떤 파일을 올렸는지 흔적도 남지 않습니다. 그래서 인증서와 비밀을 한곳에 모아 두는 Key Vault(Azure의 비밀 저장소)와 게이트웨이를 연결해, 게이트웨이가 필요할 때 저장소에서 꺼내 쓰게 합니다.

게이트웨이는 자기에게 부여된 권한(관리 ID, managed identity)으로 금고에 접근해 인증서를 가져오고, 금고 쪽 항목이 갱신되면 다음에 꺼낼 때 새것을 받습니다. 게이트웨이 설정에는 파일이 아니라 금고 안의 항목 이름만 적히므로 인증서 내용이 설정 화면에 남지 않습니다. 다만 금고의 접근 권한 설정이 어긋나면 열쇠를 받지 못해 사이트가 뜨지 않으므로, 권한 범위를 최소로 두는 것이 중요합니다.

Key Vault 연동은 인증서의 보관과 접근 통제를 저장소에 맡기고 게이트웨이는 참조만 하게 만드는 구성이며, 갱신 지점을 한 곳으로 모으는 효과가 있습니다.

관리형 인증서(Managed Certificate)

Azure가 발급과 갱신을 맡는 인증서

도메인 하나에 인증서를 붙이려 해도 발급 신청, 도메인 소유 증명, 갱신 알림 대응까지 사람이 챙길 일이 적지 않고, 한 번 놓치면 사이트에 만료 경고가 뜹니다. 관리형 인증서(Managed Certificate)는 이 발급과 갱신을 Azure가 대신 맡는 방식입니다.

아파트 도어락 비밀번호를 관리사무소가 주기적으로 바꿔 주는 것과 같습니다. 입주민(도메인 소유자)은 도메인이 자기 것임을 한 번 확인해 주기만 하면, 사무소(Azure)가 정해진 주기마다 새 비밀번호(인증서)를 만들어 문에 반영하고 묵은 비밀번호는 폐기합니다.

입주민은 언제 바뀌는지 외울 필요 없이 문이 계속 열리기만 하면 됩니다. 다만 도메인이 게이트웨이를 가리키도록 설정되어 있어야 확인이 되므로, DNS 설정이 어긋나면 발급이 진행되지 않습니다.

관리형 인증서는 발급·검증·갱신의 반복 작업을 플랫폼에 위임하는 기능이며, 그 대가로 도메인 연결 상태를 플랫폼이 확인할 수 있어야 합니다.

인증서 만료와 갱신 절차

만료 전에 갈아 끼우는 순서

인증서에는 유효기간이 있어 기간이 끝나면 브라우저가 경고 화면을 띄우고, 사용자는 그 사이트를 신뢰하지 않게 됩니다. 만료일이 지나서야 알아차리면 이미 늦으므로, 만료 전에 새 인증서로 갈아 끼우는 순서를 미리 정해 둡니다.

여권 갱신과 비슷합니다. 여권 만료일이 다가오면 미리 새 여권을 발급받아 두고, 출국 당일에는 새 여권으로 바꿔 듭니다.

인증서도 새것을 먼저 발급받아 게이트웨이에 등록해 두면 이전 것과 새것이 잠시 함께 존재하는 상태가 됩니다. 그 뒤 수신기(listener)가 새 인증서를 가리키도록 바꾸고, 접속이 정상인지 확인한 다음에야 헌 것을 지웁니다. 순서를 뒤집어 헌 것을 먼저 지우면 그 사이 접속이 끊깁니다.

갱신은 새 인증서 등록, 수신기 전환, 구 인증서 제거의 세 단계로 진행하며, 전환 지점을 겹쳐 두는 것이 무중단의 핵심입니다.

SNI와 다중 도메인 TLS

서버 이름을 보고 인증서를 고르는 방식

서버 하나에 여러 도메인을 올리면, 접속하는 쪽은 어느 도메인으로 왔는지 알리지 않은 채 암호화 협상을 시작합니다. 그 상태에서는 서버가 어떤 인증서를 내밀어야 할지 몰라 엉뚱한 인증서가 나가고, 브라우저가 이름 불일치 경고를 띄웁니다.

한 건물에 여러 상호가 입주한 상가를 생각하면 됩니다. 방문객이 몇 층 몇 호가 아니라 상호 이름을 먼저 말하면(SNI, Server Name Indication), 안내데스크가 그 상호의 명패(인증서)를 골라 내밉니다.

이름은 암호화가 시작되기 전 협상 첫머리에 전달되기 때문에, 하나의 IP 주소와 포트로도 상호마다 다른 명패를 쓸 수 있습니다. 그래서 도메인마다 인증서를 따로 등록해 두고 이름에 따라 골라 쓰는 구성이 가능해집니다. 이름을 알려주지 않는 아주 오래된 클라이언트는 여전히 첫 번째 인증서를 받게 되므로, 그런 경우를 위해 기본 인증서를 하나 정해 두기도 합니다.

SNI는 TLS 협상 첫머리에 목적지 도메인 이름을 실어 보내는 확장이고, 다중 도메인 구성은 그 이름을 근거로 인증서를 선택하는 방식입니다.

7부. TLS와 인증서078

상호 TLS(mTLS)

클라이언트 인증서까지 검증하는 구성

보통의 TLS는 사용자가 서버가 진짜인지만 확인하고 끝나므로, 서버 입장에서는 접속한 쪽이 누구인지 알 수 없습니다. 사내 시스템처럼 허가된 상대만 받아야 하는 곳에서는 이것으로 부족해, 클라이언트도 인증서를 내밀어 서로를 확인하는 상호 TLS(mTLS, mutual TLS)를 씁니다.

택배 수령과 비슷합니다. 택배 기사가 신분증(클라이언트 인증서)을 보여 주고, 집주인도 문 안쪽에서 자기 신분을 확인시켜 주는 식입니다.

게이트웨이는 접속해 온 쪽의 인증서가 신뢰하는 발급 기관(CA)에서 나온 것인지, 유효기간이 남았는지, 폐기되지 않았는지 확인하고, 통과한 요청만 뒤쪽 서비스로 넘깁니다. 그래서 인증서가 없는 브라우저는 애초에 연결 단계에서 끊기고, 애플리케이션 코드는 상대 신원을 다시 확인할 필요가 줄어듭니다. 다만 클라이언트 인증서를 발급하고 배포하고 폐기하는 관리 부담이 따르므로, 대상 시스템의 범위를 좁게 정하는 편이 좋습니다.

mTLS는 서버와 클라이언트가 각각 인증서로 신원을 증명하는 양방향 검증이며, 게이트웨이에서 이 검증을 끝내면 뒤쪽 서비스는 검증된 요청만 받게 됩니다.

7부. TLS와 인증서079

TLS 정책과 암호 그룹

허용할 프로토콜과 암호를 제한하기

웹사이트와 브라우저가 암호화 통신을 시작할 때 어떤 암호 방식을 쓸지 서로 협상하는데, 여기서 아무 방식이나 허용하면 이미 뚫린 것으로 알려진 낡은 암호가 선택되어 대화 내용이 도청될 수 있습니다. 그래서 서버 쪽에서 허용할 프로토콜 버전과 암호 그룹(cipher suite)을 미리 목록으로 정해 두는 규칙이 필요한데, 이것이 TLS 정책입니다.

회사 정문 경비실을 떠올려 보면, 방문객이 신분증을 여러 장 내밀 때 경비원은 책상 위에 붙은 인정 신분증 목록과 하나씩 대조하고 목록에 있는 것과 일치할 때만 출입을 허락합니다.

TLS 연결도 마찬가지로, 브라우저가 쓸 수 있는 방식들의 후보를 먼저 내밀면 서버는 자기 정책 목록과 겹치는 것 중에서 하나를 골라 확정합니다. 이때 암호 그룹은 키를 교환하는 방식, 신분을 증명하는 방식, 내용을 암호화하는 방식, 변조를 막는 방식을 한 묶음으로 지정한 이름표라서 목록에는 이 이름표들이 올라갑니다. 정책에 없는 낡은 방식은 협상 테이블에 아예 오르지 못하므로 약한 암호가 선택될 여지가 사라집니다.

정리하면 TLS 정책은 허용할 프로토콜과 암호 그룹을 명시한 허용 목록이고, 실제 협상은 그 목록 안에서만 이뤄지도록 강제하는 장치입니다.

7부. TLS와 인증서080

SSL 프로파일

여러 리스너에 TLS 설정을 묶어 쓰기

웹 서버가 여러 개 있고 그중 몇십 개가 각자 TLS 설정을 따로 들고 있으면, 보안 담당자가 암호 방식을 바꿀 때마다 하나하나 찾아가 고쳐야 하고 한 곳만 빠뜨려도 낡은 설정이 그대로 남습니다. 이 반복과 누락을 없애기 위해 TLS 설정을 한 덩어리로 만들어 여러 리스너가 함께 참조하게 한 것이 SSL 프로파일(SSL profile)입니다.

아파트 관리사무소의 표준 계약서 양식을 떠올려 보면 비슷합니다. 관리사무소가 양식을 한 번 만들어 두면 각 동 대표가 그 양식을 복사해 쓰고, 조항을 고칠 일이 생기면 원본 한 장만 고쳐도 모든 동의 계약서가 같이 바뀝니다.

SSL 프로파일도 프로토콜 버전, 암호 그룹, 인증서 같은 항목을 담은 설정 묶음이고, 리스너는 값을 직접 적는 대신 이 묶음의 이름을 가리킵니다. 그래서 프로파일 하나를 고치면 그를 참조하는 리스너 전부에 같은 변경이 한꺼번에 적용됩니다. 반대로 특정 리스너만 다른 설정이 필요하면 그 리스너만 다른 프로파일을 가리키게 하면 됩니다.

정리하면 SSL 프로파일은 TLS 설정을 재사용 가능한 한 벌로 묶어 둔 것이고, 리스너가 그 묶음을 참조함으로써 설정의 일관성과 변경의 편의를 함께 얻습니다.

웹 애플리케이션 방화벽(WAF)

웹 공격을 요청 단계에서 걸러 내는 계층

서버 앞에 아무 방어도 없으면 공격자는 로그인 폼에 악성 코드를 넣은 요청을 보내거나 데이터베이스를 통째로 넘겨 달라는 요청을 마음껏 던질 수 있고, 서버는 그 요청을 정상 업무로 착각해 처리하다가 결국 뚫립니다. 이런 공격을 서버가 해석하기 전에 요청 단계에서 걸러 내는 계층이 웹 애플리케이션 방화벽(WAF, Web Application Firewall)입니다.

건물 로비의 보안 검색대를 떠올려 보면 구조가 그대로 겹칩니다. 방문객이 가방을 올리면 검색대가 내용물을 확인하고 위험한 물건이 나오면 사무실로 올라가지 못하게 막습니다.

WAF도 사용자가 보낸 HTTP 요청을 서버에 닿기 전에 받아서 주소, 머리말, 본문을 살펴보고 알려진 공격 모양과 맞으면 그 요청을 차단하거나 기록합니다. 검색대가 모든 물건을 압수하는 것이 아니라 정해진 금지 품목만 걸러 내듯, WAF도 규칙에 적힌 패턴에 해당할 때만 손을 댑니다. 그래서 서버 쪽 애플리케이션은 이미 걸러진 요청만 받게 되고, 코드에 구멍이 있어도 공격이 실제로 도달할 확률이 크게 줄어듭니다.

정리하면 WAF는 네트워크 방화벽이 포트와 주소를 보는 것과 달리 웹 요청의 내용 자체를 들여다보며, 애플리케이션 앞단에서 공격을 조기에 막는 계층입니다.

8부. 웹 애플리케이션 방화벽(WAF)082

WAF 정책과 연결 방식

정책을 게이트웨이·리스너·경로에 붙이기

WAF를 켜 두기만 하고 어디에 어떤 규칙을 적용할지 정하지 않으면, 중요한 결제 경로에는 느슨한 규칙이, 관리자 화면에는 아예 규칙이 없는 식으로 구멍이 생깁니다. 그래서 규칙 묶음을 정책(policy)이라는 단위로 만들고, 그것을 게이트웨이 전체나 특정 리스너, 특정 경로에 붙이는 연결 방식이 함께 쓰입니다.

학교의 생활 규칙을 떠올려 보면 이해가 쉽습니다. 교칙은 학교 전체에 적용되고, 학년 규칙은 해당 학년에만, 실험실 안전 수칙은 그 교실에 들어갈 때만 적용됩니다.

WAF 정책도 같은 방식으로, 게이트웨이에 붙이면 그 게이트웨이를 지나는 모든 트래픽에, 리스너에 붙이면 그 포트로 들어오는 트래픽에, 경로(path)에 붙이면 그 주소로 향하는 요청에만 적용됩니다. 더 좁은 범위에 붙인 정책이 더 구체적인 상황을 다루므로, 넓게는 기본 정책을 두고 좁게는 경로별 정책으로 예외를 주는 식으로 조합합니다.

정리하면 WAF 정책은 규칙 묶음에 이름을 붙인 것이고, 연결 방식은 그 정책을 게이트웨이, 리스너, 경로라는 적용 범위에 매다는 절차입니다.

8부. 웹 애플리케이션 방화벽(WAF)083

관리 규칙 집합(CRS)

알려진 공격 패턴을 모아 둔 규칙 묶음

WAF 규칙을 아무것도 없는 상태에서 직접 하나씩 쓰려 하면, 어떤 공격이 흔한지 매번 조사해야 하고 새로운 공격 기법이 나올 때마다 규칙을 새로 만들어야 합니다. 이 부담을 줄이려고 여러 기관과 전문가가 실제로 관측된 공격 패턴을 모아 공개한 규칙 묶음이 관리 규칙 집합(CRS, Core Rule Set)입니다.

공항 검색대의 금지 품목 안내서를 떠올려 보면 비슷합니다. 보안 요원이 모든 가방을 처음부터 끝까지 상상해서 뒤지는 대신, 그동안 문제가 된 물건들의 사진과 설명이 담긴 안내서를 기준으로 확인합니다.

CRS도 마찬가지로 SQL 삽입, 명령 실행, 경로 조작 같은 공격들이 남긴 특징적인 문자열과 구조를 규칙으로 적어 두고, 요청이 그 규칙에 걸리는지 검사합니다. 안내서가 개정되면 각 공항이 같은 기준으로 다시 맞추듯, CRS도 새 버전이 나오면 가져다 갱신하는 방식으로 운영합니다. 다만 안내서에 없는 물건은 걸러지지 않으므로, CRS만으로 모든 공격을 막을 수 있다고 단정하지는 않습니다.

정리하면 관리 규칙 집합은 검증된 공격 패턴을 한곳에 모아 둔 공용 규칙 묶음이고, WAF는 이 묶음을 자기 정책 안에 넣어 기본 방어선으로 사용합니다.

OWASP 핵심 규칙

SQL 삽입과 XSS 같은 대표 공격을 막는 규칙

웹 공격의 상당수는 겉보기에 평범한 입력창을 통해 들어오는데, 로그인 칸에 따옴표를 섞어 데이터베이스 명령을 바꾸거나 댓글에 스크립트를 심어 다른 사용자의 화면에서 실행되게 하면 개인정보가 그대로 새어 나갑니다. 그래서 OWASP라는 민간 보안 단체가 정리한 대표 공격 목록을 기준으로, SQL 삽입과 XSS처럼 빈번한 공격을 겨냥한 핵심 규칙들이 WAF에 기본으로 들어갑니다.

우편물 분류대를 떠올려 보면 이해가 쉽습니다. 분류 직원이 모든 봉투를 뜯어 보는 대신 우편물에 흔히 섞여 오는 위험 물질의 냄새와 무게를 기준으로 골라내듯이, 핵심 규칙은 입력값 안에서 따옴표, 세미콜론, 스크립트 태그처럼 공격에 자주 쓰이는 조각을 찾아냅니다.

SQL 삽입은 입력값이 데이터베이스 명령의 일부로 붙어 버리는 것을 노리고, XSS는 입력값이 다른 사용자의 브라우저에서 코드로 실행되는 것을 노리므로, 규칙은 각각 그 경계를 넘는 조합을 의심합니다. 다만 정상적인 문장에도 그런 글자가 들어갈 수 있어서, 규칙은 차단과 경고 사이의 강도를 조절해 운영합니다.

정리하면 OWASP 핵심 규칙은 대표적인 웹 공격 유형에 대응하는 기본 규칙 묶음이고, 그 위에 사이트 특성에 맞는 조정을 얹어 오탐과 미탐을 줄이는 것이 실무의 핵심입니다.

사용자 정의 규칙

IP·지역·헤더 조건으로 직접 차단하기

방화벽이 켜져 있어도 특정 주소에서만 들어오는 요청이나 이상한 헤더를 붙인 요청은 정상 트래픽과 똑같이 생겨서 그냥 지나갑니다. 그래서 관리자가 직접 조건을 적어 차단하는 사용자 정의 규칙(Custom Rule)이 필요합니다.

아파트 경비실을 떠올려 보면, 기본 출입 규칙은 '정문으로만 들어온다' 정도이고 그 밖의 판단은 경비원이 직접 적은 쪽지에 맡깁니다. 관리자는 쪽지에 '이 동 주소에서 오는 사람은 세워라', '이 지역에서 온 방문객은 따로 불러라', '방문증에 특정 글자가 찍혀 있으면 들이지 마라'처럼 조건을 한 줄씩 적습니다.

경비원은 문 앞에 선 사람의 주소와 방문증을 그 쪽지와 하나씩 맞춰 보고, 걸리는 항목이 있으면 출입을 막습니다. 이렇게 사람이 직접 쓴 조건 한 줄이 규칙 하나가 되고, 규칙이 여러 개면 적용 순서에 따라 판정이 달라집니다.

정리하면 사용자 정의 규칙은 IP 대역, 접속 지역, 요청 헤더 같은 값을 조건으로 삼아 관리자가 직접 차단 여부를 정하는 장치입니다. 기본 규칙이 잡지 못하는 예외 상황을 사람이 직접 메우는 마지막 손잡이입니다.

규칙 우선순위와 평가 순서

어떤 규칙이 먼저 판정하는가

규칙이 수십 개 쌓이면 같은 요청에 차단 규칙과 허용 규칙이 동시에 걸리는 상황이 생깁니다. 어느 쪽을 먼저 볼지 정해 두지 않으면 같은 요청의 판정이 매번 달라지므로, 규칙 우선순위와 평가 순서가 필요합니다.

회사 규정집을 떠올려 보면 취업규칙, 부서 지침, 팀 관행이 한 권에 함께 묶여 있고, 서로 부딪히면 위에 있는 규정이 이깁니다.

보안 장비도 규칙을 위에서 아래로 차례로 읽으면서 요청과 맞는지 확인하고, 처음 걸린 규칙에서 판정을 끝냅니다. 그래서 좁고 구체적인 예외 규칙을 위에 두고 넓은 차단 규칙을 아래에 두는 식으로 순서를 설계합니다. 같은 규칙 묶음이라도 순서를 바꾸면 결과가 달라지므로, 순서 자체가 하나의 설정값입니다.

정리하면 규칙 우선순위와 평가 순서는 여러 규칙이 겹칠 때 어느 판정을 채택할지 정하는 틀입니다. 위에서 아래로 한 번만 훑고 먼저 맞는 규칙에서 멈추는 방식이 일반적입니다.

탐지 모드와 방지 모드

기록만 할지 실제로 막을지 정하기

차단 규칙을 새로 만들면 대개 정상 업무까지 함께 막히고, 규칙을 잘못 세웠다는 사실을 장애가 터진 뒤에야 알게 됩니다. 그래서 규칙을 실제로 걸기 전에 위반으로 잡히는 요청만 기록해 보는 탐지 모드(Detect Mode)가 먼저 필요합니다.

과속 단속 카메라를 새로 세울 때를 떠올려 보면, 처음 몇 달은 딱지를 끊지 않고 어느 차가 몇 킬로로 지나갔는지만 기록합니다. 이때는 위반 표시만 남기고 실제 처분은 하지 않으므로, 카메라 위치가 잘못 잡혔는지 사람이 확인할 시간이 생깁니다. 기록을 충분히 살펴 기준을 고친 뒤에야 실제로 과태료를 매기는 단속이 시작됩니다.

보안 장비에서도 기록만 하는 탐지 모드와 실제로 막는 방지 모드(Prevent Mode)를 이렇게 나눠 두고, 검증이 끝난 규칙만 방지 모드로 올립니다.

정리하면 탐지 모드는 규칙에 걸린 요청을 로그로만 남기고, 방지 모드는 그 요청을 실제로 차단합니다. 새 규칙은 탐지 모드로 먼저 검증하고 방지 모드로 전환하는 순서가 안전합니다.

예외 목록(Exclusion)

정상 요청이 막히지 않도록 빼 주기

차단 규칙을 넓게 잡으면 정상 업무용 자동 호출까지 함께 막혀서, 담당자가 규칙을 통째로 꺼 버리는 일이 생깁니다. 그 대신 규칙은 그대로 두고 통과시켜야 할 대상만 따로 적어 두는 예외 목록(Exclusion)이 필요합니다.

공항 보안 검색의 신뢰 여행자 제도를 떠올려 보면, 사전에 신원이 확인된 사람은 이름이 명단에 올라 있어서 긴 검색 절차를 건너뜁니다. 검색 규칙 자체는 모든 승객에게 똑같이 적용되지만, 명단에 있는 사람만 별도 통로로 빠지는 구조입니다.

보안 장비의 예외 목록도 같은 방식으로, IP 주소나 요청 경로, 특정 헤더 값을 적어 두면 그 요청은 규칙 판정에서 빠집니다. 다만 예외는 규칙을 우회하는 구멍이므로, 누가 언제 왜 넣었는지 남겨 두고 주기적으로 다시 확인해야 합니다.

정리하면 예외 목록은 차단 규칙은 유지하면서 정상 요청만 골라 빼 주는 장치입니다. 규칙을 끄는 대신 예외를 좁게 적는 편이 훨씬 안전합니다.

요청 본문 검사 제한

검사할 크기와 파일 형식의 한계

파일 업로드나 대용량 API 호출이 섞인 서비스에서는 요청 본문을 전부 읽어 검사하는 것만으로도 장비 응답이 눈에 띄게 느려집니다. 그래서 검사할 크기와 형식에 한계를 두는 요청 본문 검사 제한(Request Body Inspection Limit)을 둡니다.

택배 물류센터를 떠올려 보면, 모든 상자를 다 열어 내용물을 확인하면 하루 만에 처리가 밀립니다. 그래서 일정 크기 이하의 상자만 표본으로 열어 보고, 액체나 위험물처럼 미리 정한 품목만 따로 검사합니다.

요청 본문 검사도 같아서 검사할 최대 크기를 몇 MB 수준으로 정하고, 검사할 수 있는 파일 형식 목록을 따로 둡니다. 그 범위를 넘는 본문은 검사 없이 통과시키거나 거부하는 식으로 미리 약속해 두고, 검사하지 못했다는 사실을 로그에 남깁니다.

정리하면 요청 본문 검사 제한은 검사 가능한 크기와 파일 형식의 범위를 미리 정해 두는 설정입니다. 검사하지 못한 요청을 어떻게 처리할지도 함께 정해야 규칙의 빈틈이 생기지 않습니다.

8부. 웹 애플리케이션 방화벽(WAF)090

봇 보호(Bot Protection)

자동화 트래픽을 구분해 다루기

쇼핑몰 가격을 긁어 가는 프로그램과 검색엔진의 정상 수집기는 겉으로 보이는 요청이 거의 같습니다. 둘을 구분하지 않고 자동화 트래픽을 통째로 막으면 검색 노출까지 함께 잃게 되므로, 봇 보호(Bot Protection)가 필요합니다.

회사 로비 안내데스크를 떠올려 보면, 매일 오는 택배기사는 정해진 시간에 물건만 놓고 가므로 굳이 막지 않고, 처음 보는 사람이 서류를 들고 사내를 돌아다니려 하면 안내를 받게 합니다. 안내데스크는 방문 목적과 신분을 확인해 통과, 대기, 퇴거를 나눠 판단합니다.

봇 보호도 같은 방식으로, 자동화 트래픽을 한 덩어리로 막지 않고 검색엔진 크롤러처럼 허용할 봇, 확인이 필요한 봇, 차단할 봇으로 나눕니다. 판단 근거로는 요청 빈도, 접속 경로, 브라우저 정보의 일관성 같은 신호를 함께 봅니다.

정리하면 봇 보호는 자동화 트래픽을 무조건 차단하는 대신 종류를 나눠 다루는 기능입니다. 허용할 봇과 막을 봇의 기준을 정하고, 판단 신호를 함께 보는 것이 핵심입니다.

8부. 웹 애플리케이션 방화벽(WAF)091

WAF 튜닝과 오탐 대응

막히는 정상 요청을 고쳐 나가는 절차

새 보안 규칙을 켠 다음 날, 결제 화면에서 정상 고객이 계속 오류를 만나고 문의가 쏟아지는 상황이 벌어질 수 있습니다. 이런 일을 막고자 웹 애플리케이션 방화벽(Web Application Firewall, WAF)은 미리 정한 공격 패턴을 걸러 내지만, 규칙이 촘촘할수록 정상 요청까지 막는 오탐(false positive)이 생기므로 켠 뒤에 조정하는 절차가 반드시 필요합니다.

아파트 정문 경비원이 금지 목록을 들고 출입자를 세는 모습을 떠올리면 이해가 쉽습니다.

경비원이 "이상한 사람은 막아라"는 지시만 받으면 사복을 입은 주민까지 붙잡게 되는데, 이것이 오탐입니다. 그래서 경비일지를 펼쳐 어느 주민이 어떤 이유로 붙잡혔는지 확인하고, 그 주민만 예외 명단에 올려 통과시키는 일이 튜닝입니다. 이때 명단 전체를 지우지 않고 걸린 항목 하나만 풀어야 다른 위험한 사람을 계속 막을 수 있습니다.

실제로는 WAF 로그에서 차단 규칙 번호와 요청 내용을 확인한 뒤 해당 규칙이나 매개변수만 예외(exclusion)로 빼고, 다시 검사해 정상 통과와 공격 차단이 함께 유지되는지 보는 절차를 반복합니다. 결국 WAF 튜닝은 보안을 끄는 일이 아니라 막힌 정상 요청을 근거를 갖고 하나씩 풀어 주는 일입니다.

차단 사유 확인

로그에서 왜 막혔는지 찾아내기

고객이 "페이지가 열리지 않는다"고 연락해 왔는데 서버 애플리케이션 로그에는 아무 흔적도 없어 원인을 못 찾는 일이 흔합니다. 요청이 서버에 닿기도 전에 게이트웨이에서 잘렸기 때문이며, 이때는 Application Gateway의 진단 로그와 WAF 로그에서 차단 사유를 확인해야 합니다.

택배가 돌아왔을 때 운송장에 반송 사유가 적혀 있으면 바로 알 수 있는 것과 같습니다.

로그에는 어느 규칙이 걸렸는지 알려 주는 규칙 식별자(rule ID)와, 요청의 어느 부분이 패턴과 일치했는지 알려 주는 일치 변수(matched variable)가 함께 남습니다. 이 두 가지를 보면 "쿠키의 어떤 값이 SQL 삽입(SQL injection) 패턴으로 보였다"처럼 막힌 지점을 짚을 수 있습니다. 여기에 클라이언트 IP와 요청 시각, 상태 코드를 붙여 보면 같은 사용자가 반복해서 막히는지도 판단할 수 있습니다.

정리하면 차단 사유 확인은 게이트웨이 로그에서 규칙 식별자와 일치 변수, 요청 맥락을 읽어 왜 막혔는지 재구성하는 작업입니다. 원인을 문장으로 설명할 수 있어야 예외를 줄지 규칙을 고칠지 결정할 수 있습니다.

Application Gateway Ingress Controller(AGIC)

AKS의 인그레스로 게이트웨이 쓰기

쿠버네티스 클러스터(AKS)에서 서비스를 외부에 공개할 때마다 클라우드 로드밸런서를 새로 만들면 공인 IP와 비용이 계속 늘고 관리할 대상도 함께 늘어납니다. 인그레스(ingress)는 "이 주소로 온 요청을 이 서비스로 보내라"는 선언인데, 이를 실제 Application Gateway 설정으로 옮겨 주는 것이 인그레스 컨트롤러(Ingress Controller)이고 AKS용 구현이 AGIC(Application Gateway Ingress Controller)입니다.

입주사가 바뀔 때마다 로비 안내판을 고쳐 붙이는 건물 관리인을 떠올리면 됩니다.

입주사는 "우리는 3층이고 간판은 이렇게 달아 달라"는 신청서만 내고, 관리인은 그 신청서를 읽어 안내판과 층별 표시를 실제로 바꿉니다. 여기서 신청서가 인그레스 리소스, 관리인이 AGIC, 안내판이 Application Gateway의 리스너와 백엔드 풀 설정입니다. 관리인은 주기적으로 신청서를 훑어 새로 들어오거나 사라진 입주사를 반영하므로, 사람이 포털에서 규칙을 손으로 고칠 필요가 없습니다.

정리하면 AGIC는 클러스터 안의 인그레스 선언을 감시하다가 게이트웨이의 라우팅 규칙으로 반영하는 컨트롤러입니다. 덕분에 게이트웨이 하나를 여러 서비스가 나눠 쓰면서도 배포는 쿠버네티스 선언만으로 끝납니다.

인그레스 규칙이 게이트웨이 설정이 되는 과정

쿠버네티스 선언이 실제 라우팅으로 바뀌는 흐름

쿠버네티스에 인그레스 규칙을 하나 추가했을 뿐인데 실제 사용자 트래픽 경로가 바뀌는 모습은 처음 보면 마법처럼 느껴집니다. 이 변화는 선언을 감시하는 컨트롤러가 게이트웨이의 설정을 대신 고쳐 주기 때문에 일어나며, 그 중간 단계를 알면 장애 때 어디를 봐야 할지가 분명해집니다.

식당에서 손님이 적은 주문서가 홀 매니저를 거쳐 주방의 조리 순서표로 바뀌는 과정과 같습니다.

먼저 인그레스 리소스에 "이 호스트와 경로는 이 서비스로"라는 규칙이 적히고, 컨트롤러는 API 서버를 통해 그 변경을 감지합니다. 다음으로 컨트롤러가 규칙을 게이트웨이가 이해하는 형태로 번역해 리스너, 라우팅 규칙, 백엔드 풀, 상태 프로브(health probe)를 만들거나 고칩니다. 게이트웨이는 바뀐 구성을 적용한 뒤 백엔드가 정상인지 확인하고, 그 결과를 다시 리소스의 상태(status)에 적어 알려 줍니다.

프라이빗 링크(Private Link)

게이트웨이를 사설 엔드포인트로 노출하기

게이트웨이를 공인 IP로 열어 두면 인터넷 어디서나 접근을 시도할 수 있어, 사내 시스템끼리만 통신하고 싶은 조직에는 부담이 됩니다. 이때 가상 네트워크(VNet) 안에 사설 주소만 가진 진입점을 만들어 인터넷을 거치지 않고 게이트웨이에 닿게 하는 기능이 프라이빗 링크(Private Link)입니다.

두 건물이 공용 도로를 건너지 않고 지하 연결 통로로 이어져 있는 모습을 생각하면 됩니다.

통로를 쓰려는 쪽 건물에는 전용 출입문이 생기는데, 이것이 프라이빗 엔드포인트(Private Endpoint)이고 그 문에 붙는 사설 IP로만 들어갈 수 있습니다. 연결을 받아 주는 쪽은 어떤 대상에 어떤 요청을 허용할지 정해 두는데, 이 승인 절차가 없으면 문이 있어도 열리지 않습니다. 그래서 트래픽은 공용 인터넷을 지나지 않고, 주소도 조직의 사설 대역 안에서만 유효합니다.

정리하면 프라이빗 링크는 게이트웨이 같은 서비스를 사설 엔드포인트로 노출해 가상 네트워크 안에서만 도달하게 하는 연결 방식입니다. 공인 노출을 줄이면서도 여러 네트워크의 서비스를 같은 사설 주소 체계로 부를 수 있다는 점이 핵심입니다.

프런트엔드 IP 설정을 사설로 두면 게이트웨이는 가상 네트워크 안쪽 주소로만 응답하고, 외부 사용자는 VPN이나 다른 진입 경로를 거쳐야 닿습니다. 백엔드는 사설 주소를 쓰는 서버나 내부 로드밸런서로 두고, 상태 프로브와 라우팅 규칙도 내부 경로 기준으로 맞춥니다. 이름 해석과 인증서, 방화벽 규칙까지 내부 기준으로 정리해 두어야 사설 주소로 접속했을 때 오류 없이 동작합니다.

정리하면 내부 전용 게이트웨이는 사설 프런트엔드와 사설 백엔드를 짝지어 가상 네트워크 경계 안에서만 트래픽을 처리하는 구조입니다. 외부 노출 지점을 따로 두고 그 지점에서만 보안을 강화하면 관리할 대상이 줄고 사고 범위도 좁아집니다.

허브 앤 스포크 구성

중앙 게이트웨이 하나로 여러 VNet을 받기

부서별로 가상 네트워크(VNet, Virtual Network)를 나눠 쓰는 회사가 네트워크마다 게이트웨이를 따로 두면 비용과 관리 부담이 빠르게 늘어납니다. 외부에 공개할 서비스는 몇 개 없는데 어느 네트워크의 어느 주소로 트래픽을 보낼지 매번 사람이 정해야 하니, 이 문제를 한 곳에서 풀도록 만든 구성이 허브 앤 스포크(Hub and Spoke)입니다.

회사 건물에 비유하면 본사 1층에 안내 데스크 하나를 두고 각 지사 건물이 그 데스크로만 이어진 통로를 갖는 구조와 같습니다.

안내 데스크가 있는 본사가 허브(Hub)이고, 데스크와 통로로 연결된 각 지사가 스포크(Spoke)입니다. 방문객은 어느 지사로 가든 먼저 데스크에서 목적지를 확인하고, 데스크는 정해진 통로로만 사람을 보냅니다. 그래서 출입 규칙과 보안 검색, 방문 기록을 데스크 한 곳에서 관리하면 되고 지사마다 경비실을 따로 둘 필요가 없습니다.

실제 구성에서는 공용 가상 네트워크를 허브로 두고 게이트웨이와 방화벽 같은 자원을 그곳에 모은 뒤, 나머지 네트워크를 피어링(peering)으로 연결합니다. 다만 허브가 멈추면 모든 연결이 함께 막히므로 허브 쪽 이중화를 반드시 같이 설계해야 합니다.

멀티 리전과 장애 조치 설계

지역 장애에 대비해 이중화하는 방법

게이트웨이와 서버를 한 지역(region)에만 두면 그 지역에 정전이나 네트워크 장애가 생기는 순간 서비스 전체가 멈춥니다. 그래서 서로 떨어진 두 지역에 같은 구성을 복제해 두고 한쪽이 죽으면 다른 쪽이 이어받게 하는 멀티 리전(multi-region) 설계와 장애 조치(failover)가 필요합니다.

택배 회사가 물류센터를 두 곳에 두는 방식에 비유할 수 있습니다. 평소에는 가까운 1센터가 모든 주문을 처리하고 2센터는 같은 재고와 배송 계획을 미리 받아 대기합니다.

본사 관제 시스템이 1센터의 상태를 계속 확인하다가 불이 나거나 길이 막히면 즉시 2센터로 주문을 돌립니다. 이때 2센터가 최신 주문을 알고 있어야 이어받을 수 있으므로 두 센터의 기록을 계속 맞춰 두는 작업이 함께 필요합니다.

실제로는 주 지역(primary region)과 보조 지역(secondary region)에 같은 게이트웨이 구성을 두고, 상태 검사(health probe)와 트래픽 관리자(traffic manager)가 장애를 감지해 트래픽을 넘깁니다. 넘기는 방식은 자동과 수동으로 나뉘고 데이터 복제 지연과 비용까지 감안해야 하므로, 무엇을 먼저 살릴지 순서를 정해 두는 것이 중요합니다.

Application Gateway for Containers

컨테이너용 후속 서비스와 기존 제품의 차이

쿠버네티스(Kubernetes)에서 컨테이너를 수백 개 띄우면 파드(pod)가 수시로 생기고 사라져서, 고정된 서버 주소를 전제로 만든 기존 게이트웨이는 설정을 따라가지 못합니다. 이런 환경을 위해 컨테이너와 쿠버네티스의 규칙을 직접 읽어 트래픽을 나눠 주는 Application Gateway for Containers가 나왔습니다.

좌석이 계속 바뀌는 대형 행사장에 비유할 수 있습니다. 기존 제품은 미리 짜 둔 좌석표를 들고 안내하는 방식이라 사람이 자리를 옮길 때마다 표를 다시 만들어야 합니다.

반면 새 서비스는 행사장의 좌석 변경 알림을 실시간으로 받아 안내 요원이 스스로 위치를 갱신합니다. 그래서 무대를 새로 세우거나 좌석 구역을 늘려도 사람이 게이트웨이 설정을 손으로 고칠 일이 거의 없습니다.

기술적으로는 쿠버네티스의 인그레스(Ingress)와 게이트웨이 API(Gateway API) 자원을 읽어 경로 규칙을 자동으로 만들고, 기존 Application Gateway와 달리 고정된 프런트엔드 구성에 덜 묶입니다. 다만 서비스마다 제공 기능과 지원 범위가 다르므로, 쓰려는 기능이 실제로 지원되는지 확인한 뒤 선택해야 합니다.

게이트웨이와 서비스 메시의 역할 경계

7계층 라우팅을 어디까지 맡길 것인가

마이크로서비스가 늘면 서비스 사이 통신까지 게이트웨이에 맡기려는 요구가 생기는데, 그렇게 하면 게이트웨이가 내부 통신 규칙까지 떠안아 설정이 걷잡을 수 없이 복잡해집니다. 외부에서 들어오는 트래픽은 게이트웨이가, 서비스 사이의 통신은 서비스 메시(service mesh)가 맡도록 경계를 나누는 이유가 여기에 있습니다.

호텔에 비유하면 정문 프런트 데스크와 객실 사이 내부 전화망의 역할 차이와 같습니다. 프런트 데스크는 건물 밖에서 온 손님의 신분을 확인하고 어느 객실로 보낼지 정하는 일을 맡습니다.

반면 객실과 주방, 세탁실 사이의 연락은 프런트를 거치지 않고 내부 전화망이 직접 처리합니다. 이 둘을 한 창구로 합치면 외부 손님 응대와 내부 업무 연락이 뒤섞여, 어느 규칙이 어디에 적용되는지 아무도 설명하지 못하게 됩니다.

실제로는 7계층(HTTP) 라우팅과 인증, 외부 노출을 게이트웨이가 담당하고, 서비스 간 통신의 암호화와 재시도, 추적은 서비스 메시의 사이드카(sidecar)가 담당하는 식으로 나눕니다. 경계를 정할 때는 트래픽이 어디서 시작하는지와 누가 정책을 소유하는지를 기준으로 삼으면 됩니다.

대용량 트래픽 대응 설계

동시 연결과 처리량 한계를 다루는 법

이벤트나 공지가 뜨는 순간 동시 접속이 몇 배로 뛰면, 게이트웨이 한 대의 연결 수와 처리량 한계에 먼저 부딪혀 정상 사용자까지 함께 느려지거나 끊깁니다. 그래서 미리 한계를 알고 늘리는 방법과 줄이는 방법을 함께 준비하는 용량 설계가 필요합니다.

고속도로 톨게이트에 비유하면 이해가 쉽습니다. 차가 몰릴 때 차로 수를 늘리는 것이 게이트웨이 인스턴스를 늘리는 일이고, 정산을 자동으로 바꿔 차마다 걸리던 시간을 줄이는 것이 연결 재사용(keep-alive)과 암호화 처리 부하를 줄이는 일입니다.

또한 모든 차를 같은 톨게이트로 보내지 않고 목적지별로 나눠 보내면 특정 차로에만 줄이 생기는 일을 막을 수 있습니다. 다만 차로를 무작정 늘리면 뒤쪽 도로가 먼저 막히므로, 게이트웨이 뒤의 서버와 데이터베이스 용량도 같이 키워야 합니다.

실제로는 인스턴스 수와 인스턴스당 연결 수를 기준으로 최대 동시 연결을 계산하고, 오토스케일(autoscale)과 캐싱, 압축, 연결 재사용으로 단위 시간당 부하를 낮춥니다. 한계 수치는 제품과 등급마다 다르므로 실제 트래픽으로 부하 테스트를 해 확인하는 것이 안전합니다.

v1에서 v2로 마이그레이션

기존 게이트웨이를 옮기는 절차

오래 쓴 v1 게이트웨이는 확장성과 배포 방식의 제약이 있어, 새 기능이 필요할 때 v2로 옮겨야 하는 상황이 옵니다. 그런데 주소와 설정 형식이 달라서 그냥 새로 만들면 서비스가 끊기므로, 순서를 정한 마이그레이션(migration) 절차가 필요합니다.

이사에 비유하면 순서가 분명합니다.

  • 먼저 새 집을 구해 가구를 들이고(새 v2 게이트웨이와 백엔드 연결), 기존 집과 새 집의 주소가 겹치지 않게 정리합니다.
  • 그다음 우편물을 새 집으로 돌리도록 안내하고(도메인의 DNS 레코드를 새 게이트웨이로 변경), 며칠 동안 두 집을 함께 유지하며 빠진 우편이 없는지 확인합니다.
  • 마지막으로 구 집 계약을 정리하듯 예전 게이트웨이와 남은 설정을 제거합니다.

실제로는 v2 게이트웨이를 병렬로 만들어 리스너와 규칙, 상태 검사, 인증서를 옮기고, 낮은 비중의 트래픽부터 새 쪽으로 보내 확인한 뒤 DNS 전환과 구 리소스 삭제 순으로 진행합니다. v1과 v2는 함께 존재할 수 없는 자원과 설정 항목이 있으므로, 옮기기 전에 두 버전의 차이를 목록으로 대조해 두는 것이 좋습니다.

Azure Monitor 메트릭

게이트웨이가 내보내는 수치 읽기

게이트웨이를 통해 서비스에 접속하는 사람들이 갑자기 느리다고 이야기하는데, 서버에 들어가 로그를 뒤져도 어디서 막히는지 알 수 없다면 원인을 찾는 데만 몇 시간이 걸립니다. Azure Monitor 메트릭(metric, 측정값)은 이런 상황에서 게이트웨이가 스스로 남기는 숫자 기록을 모아 보여 주는 관측 기능으로, Azure의 모니터링 서비스 안에서 게이트웨이 같은 자원의 상태를 수치로 확인하는 역할을 맡습니다.

회사 건물에 비유하면 각 사무실의 전기·수도 계량기가 일정 간격으로 사용량을 자동으로 기록하는 것과 같습니다. 게이트웨이도 같은 방식으로 초당 몇 건을 처리했는지, 응답에 몇 밀리초가 걸렸는지를 정해진 주기마다 숫자로 남깁니다.

관리자는 계량기 앞에 매번 서서 눈금을 읽는 대신 대시보드에서 그래프로 추이를 한눈에 봅니다. 여기서 메트릭은 사건의 내용을 문장으로 남기는 로그와 달리 양과 시간만 남긴다는 점이 다릅니다.

정리하면 Azure Monitor 메트릭은 게이트웨이가 주기적으로 내보내는 성능 수치를 모아 시계열 그래프로 보여 주는 기능이며, 문제의 규모와 시점을 가장 빠르게 파악하는 첫 단서가 됩니다.

핵심 메트릭 — 처리량·지연·실패

장애 때 무엇을 먼저 볼 것인가

장애가 터지면 화면에 빨간 경고만 잔뜩 뜨고 정작 무엇부터 확인해야 할지 몰라 시간을 흘려보내기 쉽습니다. 게이트웨이 모니터링에서는 처리량(throughput), 지연(latency), 실패(failure)라는 세 가지 수치를 먼저 보도록 정해 두는 것이 이런 혼란을 줄이는 기본입니다.

택배 물류센터에 비유하면 하루에 몇 상자를 처리했는지가 처리량이고, 주문에서 도착까지 몇 시간이 걸렸는지가 지연이며, 파손되거나 주소를 못 찾아 돌아온 상자 수가 실패입니다. 세 숫자는 서로 얽혀 있어서 처리량이 갑자기 늘면 지연이 같이 올라가고, 지연이 한계를 넘으면 실패가 튀어 오릅니다. 그래서 센터장은 상자 수만 보지 않고 세 계기판을 나란히 놓고 어느 것이 먼저 움직였는지 확인합니다.

여기서 처리량은 단위 시간당 처리한 요청 수, 지연은 요청이 들어와 응답이 나갈 때까지 걸린 시간, 실패는 오류로 끝난 요청의 비율을 뜻합니다.

결국 이 세 메트릭은 게이트웨이가 건강한지 판단하는 최소 조합이며, 장애 때는 처리량의 급변, 지연의 상승, 실패율의 증가 순서로 원인을 좁혀 가는 것이 좋습니다.

진단 로그(Diagnostic Log)

액세스·방화벽·성능 로그 켜기

메트릭만으로는 몇 건이 실패했다는 사실은 알 수 있어도 어떤 요청이 왜 실패했는지는 알 수 없습니다. 진단 로그(Diagnostic Log)는 게이트웨이가 처리한 요청 하나하나의 내용을 기록으로 남기는 기능으로, Azure Monitor에서 자원별로 켜고 끄는 선택 사항입니다.

아파트 경비실의 방문 기록부에 비유할 수 있습니다. 누가 몇 시에 들어왔고 어떤 목적으로 왔는지 줄줄이 적히는 방문 기록, 출입문 잠금장치가 누구를 막았는지 남기는 차단 기록, 엘리베이터가 몇 층에서 오래 멈췄는지 남기는 운행 기록이 각각 액세스 로그, 방화벽 로그, 성능 로그에 해당합니다. 기록부는 기본적으로 비어 있고 관리자가 이 기록을 남기겠다고 지정해야 비로소 쓰이기 시작합니다. 다만 기록을 남기면 저장 공간과 비용이 함께 늘어나므로 필요한 항목만 골라 켜는 것이 보통입니다.

정리하면 진단 로그는 요청 단위의 상세 기록을 저장소나 분석 도구로 흘려보내는 설정이며, 메트릭이 얼마나를 답한다면 로그는 무엇이 왜 일어났는지를 답합니다.

액세스 로그 분석

요청 한 건이 지나간 경로 따라가기

사용자가 특정 주소로 접속했는데 오류가 났다는 연락을 받고도, 그 요청이 어느 규칙을 거쳐 어느 백엔드로 갔는지 확인할 방법이 없다면 재현도 수정도 불가능합니다. 액세스 로그 분석은 진단 로그에 남은 요청 기록을 시간이나 주소, 상태 코드 같은 기준으로 걸러 요청 한 건의 이동 경로를 되짚는 작업입니다.

택배 송장 추적에 비유하면 이해가 쉽습니다. 송장 번호 하나를 넣으면 집하장, 간선 터미널, 배송 기사까지 어느 지점을 몇 시에 통과했는지 순서대로 나옵니다.

액세스 로그도 요청마다 붙는 추적 식별자와 시각, 라우팅된 규칙, 최종 백엔드 주소, 응답 코드를 함께 남기므로 같은 방식으로 한 건을 따라갈 수 있습니다. 여러 지점의 기록을 시각 순서로 이어 붙여야 하며, 응답 코드가 5로 시작하면 백엔드 쪽 문제, 4로 시작하면 요청이나 규칙 쪽 문제로 범위를 좁히는 식으로 읽습니다.

결국 액세스 로그 분석은 로그 한 줄을 요청의 여정으로 복원하는 일이며, 간헐적으로만 실패하는 문제를 잡을 때 가장 확실한 근거가 됩니다.

백엔드 상태와 프로브 메트릭

비정상 백엔드를 수치로 찾아내기

백엔드 서버 한 대가 조용히 응답을 멈췄는데 게이트웨이가 계속 그 서버로 요청을 보내고 있다면, 사용자는 다섯 번 중 한 번꼴로 오류를 겪게 됩니다. 백엔드 상태와 프로브(probe, 상태 확인) 메트릭은 게이트웨이가 각 백엔드에 주기적으로 신호를 보내 정상 여부를 수치로 드러내는 장치입니다.

아파트 관리사무소가 각 세대의 인터폰이 제대로 연결되는지 정해진 시간에 한 번씩 눌러 보는 것과 같습니다. 눌렀을 때 응답이 오면 정상, 일정 시간 안에 응답이 없으면 비정상으로 표시하고 그 세대는 잠시 방문자 연결 대상에서 빼 둡니다.

게이트웨이도 같은 방식으로 상태 프로브를 보내 응답 코드와 응답 시간을 기록하고, 비정상으로 판정된 백엔드는 요청 분배에서 제외합니다. 이때 프로브 성공과 실패 건수, 응답 시간이 메트릭으로 올라오므로 어느 백엔드가 언제부터 흔들렸는지 그래프로 확인할 수 있습니다.

정리하면 프로브 메트릭은 게이트웨이가 백엔드의 건강 상태를 스스로 점검해 남기는 수치이며, 장애를 사용자 신고보다 먼저 감지하는 조기 경보의 근거가 됩니다.

10부. 모니터링과 진단108

경고 규칙(Alert)

문제가 커지기 전에 알림 받기

새벽에 실패율이 서서히 올라가는데 아무도 대시보드를 보고 있지 않다면, 아침에 출근했을 때는 이미 사용자 항의가 쌓여 있는 뒤입니다. 경고 규칙(Alert rule)은 메트릭이나 로그가 정해 둔 조건을 넘으면 자동으로 알림을 보내는 기능으로, Azure Monitor 안에서 감시 조건과 알림 대상을 묶어 관리합니다.

건물 화재 경보기에 비유할 수 있습니다. 연기가 일정 농도를 넘으면 사이렌이 울리고, 울리는 대상은 경비실 전화와 관리자 휴대전화로 미리 정해 둡니다.

경고 규칙도 어떤 수치를 몇 분 동안 감시할지, 임계값을 얼마로 둘지, 울리면 누구에게 어떤 경로로 알릴지를 미리 정해 둡니다. 너무 예민하게 잡으면 사소한 흔들림에도 사이렌이 울려 아무도 믿지 않게 되고, 너무 둔하면 불이 번진 뒤에야 울리므로 임계값과 지속 시간을 함께 조정하는 것이 핵심입니다.

정리하면 Application Insights 연동은 게이트웨이에서 시작된 요청에 추적 식별자를 부여해 애플리케이션까지 한 줄로 연결하는 구성입니다. 게이트웨이 설정에서 연동을 켜고 연결 정보를 애플리케이션 쪽 계측 설정과 맞춰 두는 것이 출발점입니다.

로그 분석 쿼리(KQL) 활용

로그를 질문 형태로 조회하기

로그가 쌓이기만 하고 필요한 값을 찾지 못하면 저장 공간만 쓰는 기록이 됩니다. KQL(Kusto Query Language, 로그를 질문 형태로 조회하는 언어)은 표 형태로 쌓인 로그에 조건과 집계를 걸어 원하는 줄만 뽑아내는 도구입니다. 도서관 사서에게 말을 거는 상황과 비슷한데, 서가 이름을 대고, 원하는 조건을 말하고, 어떤 항목만 보여 달라고 하고, 몇 권인지 세어 달라고 하는 순서가 그대로 질의문이 됩니다.

서가 이름에 해당하는 것이 로그 테이블이고, 조건은 where 절, 보여 줄 항목은 project 절, 개수와 평균 같은 집계는 summarize 절로 표현합니다. 여기에 시간 범위를 함께 지정하면 최근 한 시간처럼 좁은 구간만 골라 볼 수 있어, 장애 시점 전후의 변화를 비교하기 좋습니다. 정리하면 KQL은 테이블 선택, 조건 필터, 항목 추출, 집계라는 네 단계를 질의문으로 적어 로그를 원하는 모양으로 바꾸는 방법입니다. 게이트웨이 로그에서는 응답 코드 분포나 구간별 지연 시간을 세는 질의가 가장 자주 쓰입니다.

흔한 오류 코드와 원인

502·504·403이 나오는 이유

사용자 화면에 502나 504, 403이 뜨면 원인이 게이트웨이에 있는지 뒤쪽 서버에 있는지부터 갈라야 합니다. 이 세 코드는 자주 보이지만 뜻이 전혀 다르고, 확인해야 할 지점도 서로 다릅니다. 식당으로 비유하면 403은 문 앞에서 신분 확인이 막힌 경우로, 주문 자체가 들어가지 못하고 출입이 거부된 상태입니다. 502는 주문은 들어갔는데 주방이 엉뚱한 응답을 돌려준 경우이고, 504는 주문을 넣고 기다렸지만 정해진 시간 안에 요리가 나오지 않아 기다림을 포기한 경우입니다.

그래서 403이면 인증 정보나 접근 규칙을, 502이면 뒤쪽 서버가 살아 있는지와 응답 형식을, 504이면 뒤쪽 처리 시간과 게이트웨이의 제한 시간 설정을 먼저 봅니다. 정리하면 403은 접근 권한 문제, 502는 뒤쪽 서버의 잘못된 응답, 504는 응답 지연으로 인한 시간 초과를 가리킵니다. 같은 화면 오류라도 이 구분을 먼저 하면 확인할 곳을 절반으로 줄일 수 있습니다.

코드로 배포하기

ARM·Bicep·Terraform으로 게이트웨이 정의하기

Terraform은 특정 클라우드에 매이지 않는 도구로, 선언한 구성과 실제 상태의 차이를 상태 파일에 기록해 두고 그 차이를 맞춰 갑니다. 정리하면 ARM과 Bicep은 해당 클라우드의 배포 형식에, Terraform은 여러 환경을 함께 다루는 데 강점이 있는 코드 기반 배포 방식입니다. 어떤 도구를 쓰든 구성 파일을 버전 관리에 넣어 두면 변경 이력과 재현이 함께 확보됩니다.

구성 변경의 적용과 전파 시간

설정을 바꿨을 때 언제 반영되는가

게이트웨이 설정을 바꾼 직후 확인했는데 예전 동작이 그대로여서 장애로 오인하는 일이 흔합니다. 구성 변경은 저장되는 시점과 실제 트래픽에 적용되는 시점이 다를 수 있기 때문입니다. 아파트 게시판에 공지를 붙이는 상황과 비슷한데, 관리사무소가 문서를 등록한 순간과 각 세대가 그 내용을 확인하는 순간 사이에는 시간차가 생깁니다. 게이트웨이도 설정을 받아들인 뒤 여러 인스턴스로 퍼뜨리는 과정을 거치므로, 그동안에는 일부 요청만 새 설정을 따르는 과도기(전파 중)가 나타날 수 있습니다.

라우팅 규칙이나 수신기처럼 구조를 바꾸는 변경은 새 구성의 배포가 필요해 전파보다 더 오래 걸리는 경우가 많고, 반영 시점은 제품과 배포 방식에 따라 다릅니다. 정리하면 구성 변경에는 저장, 전파, 적용이라는 단계가 있고 그 사이에 시차가 존재합니다. 변경 후에는 바로 판단하지 말고 해당 제품 문서의 반영 소요 시간을 확인한 뒤 충분히 기다려 검증하는 것이 안전합니다.

무중단 배포 전략

배포 중에도 연결을 끊지 않는 방법

서비스에 새 버전을 올릴 때마다 서버를 잠깐 내렸다가 다시 켜는 방식을 쓰면, 그 몇 분 사이에 접속해 있던 사용자는 연결이 끊기고 결제 도중이던 요청은 실패합니다. 이런 중단을 없애기 위해 등장한 것이 무중단 배포(Zero-downtime deployment) 전략이고, 여러 대의 서버를 부하 분산기(Load Balancer) 뒤에 두는 구조가 그 바탕이 됩니다.

비유하자면 24시간 여는 대형 마트의 진열대 교체와 같습니다. 매장 입구에 선 안내 직원이 손님을 아직 공사하지 않은 진열대로 보내 주듯, 부하 분산기는 새 버전으로 바꿀 서버를 목록에서 빼고 나머지 서버로 트래픽을 돌립니다. 진열대를 다 바꾼 뒤 상태를 확인하고 다시 영업에 투입하듯, 서버도 준비가 끝났는지 확인(Health check)한 다음에야 트래픽을 받게 합니다.

이때 한 대씩 순서대로 바꾸는 방식(Rolling)과 새 서버 무리를 따로 세워 두고 한 번에 갈아타는 방식(Blue-Green), 새 버전에 소량의 손님만 먼저 보내 보는 방식(Canary)이 대표적이며, 문제가 보이면 이전 진열대로 되돌리는 절차(Rollback)를 함께 준비합니다.

정리하면 무중단 배포는 서버를 한꺼번에 내리는 대신 트래픽을 옮겨 가며 버전을 교체하는 운영 방식이고, 부하 분산기와 상태 확인, 되돌리기가 그 세 기둥입니다.

장애 대응 런북

증상별로 무엇을 어떤 순서로 확인할지

장애가 터졌을 때 무엇부터 볼지 정해 두지 않으면, 담당자는 로그와 지표를 마구 열어 보며 시간을 흘려보내고 복구는 늦어집니다. 그래서 증상별로 확인 순서를 미리 적어 둔 문서를 장애 대응 런북(Runbook)이라 부르며, 이는 운영 절차 문서의 한 갈래입니다.

아파트 소방 점검 매뉴얼과 같습니다. 연기가 나면 먼저 어느 층인지 확인하고, 그다음 소화전 밸브를 잠그고, 마지막에 원인 설비를 세우는 식으로 순서가 정해져 있습니다.

런북도 증상(5xx 오류 급증, 응답 지연, 연결 실패 등)마다 첫 확인 항목과 다음 항목을 순서대로 적고, 각 단계에 "정상이면 다음으로, 아니면 누구에게 알린다"는 판단 기준을 붙입니다. 여기에 최근 변경 이력과 대시보드 링크, 되돌리는 절차를 함께 적어 두면 새로 온 당직자도 같은 순서로 움직일 수 있습니다.

장애가 끝난 뒤에는 런북에 빠져 있던 단계를 채워 넣는 것으로 마무리합니다.

결국 런북은 지표와 로그, 변경 이력을 정해진 순서로 훑게 만드는 문서이며, 핵심은 빠른 추측이 아니라 반복 가능한 절차입니다.

구성 백업과 복구

설정을 내보내고 같은 모양으로 다시 세우기

설정을 손으로 하나하나 다시 만들다 보면 빠뜨린 항목 하나 때문에 서비스가 절반만 살아나는 일이 생기고, 급할 때일수록 그 실수는 늘어납니다. 그래서 설정을 파일로 내보내 보관하고 그 파일로 같은 모양을 다시 세우는 구성 백업과 복구(Configuration backup and restore)가 필요합니다.

이삿짐 목록과 가구 배치 도면을 떠올리면 쉽습니다. 짐을 쌀 때 무엇이 어디에 있었는지 목록으로 적어 두면 새집에서 같은 배치를 그대로 만들 수 있고, 도면이 없으면 가구를 놓을 자리를 매번 새로 고민해야 합니다.

구성 내보내기(Export)는 이 도면을 뜨는 일이고, 복구(Import·Restore)는 도면을 보고 가구를 다시 놓는 일입니다. 도면은 버전 관리 저장소에 넣어 언제 무엇이 바뀌었는지 남기고, 복구한 뒤에는 실제 설정과 도면이 같은지 대조해 확인합니다.

도면만 있고 열쇠 같은 것(인증서와 비밀 값)이 없으면 집은 완성되지 않으므로, 그런 값은 별도 금고에 보관합니다.

정리하면 구성 백업은 설정 자체를 산출물로 만들어 보관하는 일이며, 복구는 그 산출물로 같은 환경을 재현하는 절차입니다.

업그레이드와 설정 드리프트 관리

서비스 업데이트와 구성 불일치 다루기

서비스를 업데이트할 때마다 사람이 화면에서 몇 개를 손으로 고치다 보면, 같은 역할의 서버들이 조금씩 다른 설정을 갖게 되고 어느 것이 맞는지 아무도 모르는 상태가 됩니다. 이렇게 시간이 지나며 기준에서 벗어나는 현상을 설정 드리프트(Configuration drift)라 하고, 이를 다루는 일이 업그레이드 관리와 함께 운영의 큰 축을 이룹니다.

여러 지점을 가진 프랜차이즈 카페를 생각해 봅시다. 본사가 정한 표준 레시피가 있는데 각 지점이 재료를 조금씩 바꿔 쓰면 손님은 지점마다 다른 맛을 받게 되고, 본사는 어느 지점이 어긋났는지 알 수 없습니다.

그래서 본사는 "이렇게 되어 있어야 한다"는 최종 상태를 문서로 정하고 각 지점이 스스로 그 상태에 맞추게 합니다. 설정도 마찬가지로 원하는 상태(Desired state)를 코드로 선언해 두고 실제 상태와 비교해 차이를 없애는 방식을 쓰며, 업그레이드는 한 번에 전체를 바꾸지 않고 일부부터 적용해 문제 범위를 좁힙니다.

차이를 발견했을 때 사람이 다시 손으로 맞추는 대신 도구가 자동으로 맞추게 하는 것이 핵심입니다.

결국 드리프트 관리는 설정의 기준 상태를 코드로 고정하고 실제와의 차이를 계속 되돌리는 일이며, 업그레이드는 그 기준을 한 단계씩 올리는 일입니다.

처리량 단위(Capacity Unit)와 비용

v2 과금 구조를 이해하고 비용 줄이기

사용한 만큼만 요금을 내는 방식에 익숙하면, 처리 능력을 미리 확보해 두는 과금 구조를 만났을 때 요금이 왜 이렇게 나왔는지 이해하기 어렵습니다. 처리량 단위(Capacity Unit)는 게이트웨이 같은 서비스에서 확보한 처리 능력을 세는 과금 기준이고, v2 과금 구조는 이 단위를 중심으로 비용이 계산되는 모델입니다.

식당 예약에 비유하면 이해가 빠릅니다. 손님이 올지 안 올지 모르지만 30명분 테이블을 예약해 두면, 실제로 10명만 와도 30명분 자리를 비용으로 치러야 합니다.

처리량 단위도 같은 성격이라, 미리 잡아 둔 단위가 많을수록 기본 비용이 올라가고 실제 트래픽이 그보다 적어도 줄어들지 않습니다. 그래서 비용을 줄이려면 실제 사용량 그래프를 보고 남는 단위를 줄이고, 몰리는 시간대를 따로 떼어 그때만 늘리며, 쓰지 않는 라우팅 규칙과 긴 로그 보관 기간을 정리하는 식으로 손봅니다.

정확한 단위 정의와 과금 비율은 버전과 리전에 따라 다를 수 있으므로 문서로 확인해야 합니다.

정리하면 처리량 단위는 확보한 처리 능력에 대한 요금 기준이고, 비용 관리의 핵심은 확보한 양과 실제 사용량의 간격을 줄이는 일입니다.

운영 체크리스트

실무에서 주기적으로 확인할 항목 정리

운영은 특별한 사건이 없을 때도 조용히 어긋나기 때문에, 무언가 터진 뒤에야 확인하면 이미 늦은 항목이 많습니다. 그래서 매일과 매주, 매월 확인할 항목과 담당자를 정해 둔 운영 체크리스트(Operational checklist)를 실무에서 상시로 돌립니다.

자동차 정기 점검표와 같습니다. 매일은 타이어 공기압과 계기판 경고등, 매주는 엔진오일, 매월은 정비소 점검처럼 주기를 나눠 두면 작은 이상을 큰 고장 전에 잡습니다.

체크리스트도 같은 방식으로 나누어, 매일은 오류율과 지연, 인증서 만료일, 백업 성공 여부를 보고, 매주는 설정이 기준과 같은지와 비용 추이를, 매월은 접근 권한과 로그 보관, 업그레이드 계획을 확인합니다. 각 항목에는 "무엇을 보고, 어떤 값이면 이상인지"를 숫자로 적어 두어야 담당자가 바뀌어도 같은 판단이 나옵니다.

확인만 하고 끝내지 않고, 걸린 항목은 담당자와 기한을 정해 처리 목록으로 넘깁니다.

결국 체크리스트는 지표와 설정, 권한, 비용을 주기와 기준값으로 묶어 놓은 점검표이며, 확인한 기록이 남을 때 비로소 운영의 근거가 됩니다.
