Harness Engineering

하네스 엔지니어링(Harness Engineering)은 LLM을 신뢰할 수 있는 에이전트로 만드는 실행 계층(하네스) — 도구·컨텍스트/메모리·가드레일·샌드박스·오케스트레이션·관측/평가·피드백 루프 — 을 설계·구축·운영·반복하는 엔지니어링 분야다. '에이전트 = 모델 + 하네스'라는 등식 위에서, 하네스 엔지니어링은 특정 벤더 제품이 아니라 코딩 에이전트 일반의 스캐폴딩을 다룬다. 단일 제품이 없으므로 근거는 공식 문서를 제공하는 주류 하네스 구현체들 — OpenAI(Codex·Agents SDK·Agents API·'Harness engineering' 공식 엔지니어링 글), Anthropic(Claude·Claude Agent SDK·Managed Agents·'Building effective agents'), MCP(Model Context Protocol 공식 사양) — 로 삼았다.

1단계 하네스 엔지니어링의 기초

에이전트는 추론하는 모델과 그 모델을 둘러싼 실행 인프라(하네스)의 결합이며, 하네스가 도구 실행·샌드박스·수명주기를 관리한다.

#1문제 상황

LLM을 단독으로 쓰는 방식은 모델에 프롬프트를 한 번 보내고 답 하나를 받는 데서 끝난다. 이 방식은 대화 한 턴 안에서 답을 내야 하므로 파일을 읽고, 계산기를 두드리고, 코드를 실행하는 같은 실제 행동은 전혀 할 수 없다. 모델이 아무리 뛰어나도 답변을 생성하는 것 외에는 아무것도 할 수 없고, 그 답변도 학습된 지식 범위를 벗어나지 못한다. 즉 모델 하나만으로는 어떤 작업도 직접 완료할 수 없다는 것이 기존 방식의 명확한 한계다.

#2핵심 질문

모델이 스스로 도구를 쓰고 여러 단계를 거쳐 작업을 끝까지 수행하게 하려면 그 모델을 어떻게 둘러싸고 운영해야 하는가?

#3동작 예시

#4동작 과정

  1. 모델 호출하네스가 사용자 요청과 사용 가능한 도구 목록을 모델에 보내고, 모델이 다음 행동(어떤 도구를 어떤 인자로 부를지)을 결정해 응답한다.
  2. 도구 실행하네스가 모델이 고른 도구를 실제 환경에서 실행하고, 그 결과(성공·실패·출력)를 모델에게 돌려준다.
  3. 반복과 종료하네스가 위 두 단계를 목표 달성 또는 최대 반복 횟수에 도달할 때까지 반복하고, 마지막 응답을 사용자에게 전달한다.

#1문제 상황

#2핵심 질문

#4동작 과정

#1문제 상황

모든 작업을 에이전트로 만들면 실제로는 필요 없는 복잡성이 생긴다. 에이전트는 매 단계마다 모델이 다음 행동을 결정하므로 호출 횟수가 늘고, 그만큼 비용과 지연이 증가하며, 모델이 경로를 잘못 선택하면 오류가 발생할 가능성도 커진다. 결과가 이미 정해져 있는 작업에 에이전트를 쓰면 단순한 API 호출과 비교해 이득 없이 오버헤드와 실패 리스크만 커진다는 것이 문제다.

#2핵심 질문

#4동작 과정

  1. 작업 성격 판별결과가 정해져 있고 오류 허용이 낮은지, 경로 탐색과 반복이 필요한지를 판단한다.

  3. 복잡 작업만 에이전트로경로 탐색이 필요한 작업만 에이전트 구조로 실행한다.

#1문제 상황

에이전트를 만들 때 처음 맞닥뜨리는 선택은 프레임워크를 쓰느냐, 직접 구현하느냐다. 프레임워크를 쓰지 않고 직접 구현하는 방식은 루프(모델 호출 → 결과 처리 → 다시 모델 호출), 도구 호출 파싱, 상태 저장, 오류 재시도 같은 반복적인 코드를 매번 손으로 작성하게 만든다. 이 방식은 각 부분을 완전히 통제할 수 있다는 장점이 있지만, 프로젝트마다 같은 기반 구조를 다시 짜야 하고 초기 진입 장벽이 높다.

#2핵심 질문

#4동작 과정

  1. 에이전트와 도구 정의실행기(루프를 대신 돌려 주는 프레임워크 구성 요소)에 역할 지시문과 사용할 도구 목록을 등록한다. 직접 구현이라면 이 단계에서부터 루프 코드를 설계해야 한다.
  2. 루프 실행실행기가 모델 호출, 도구 호출 요청 감지, 도구 실행, 결과를 메시지로 다시 넣기를 반복하며 최종 응답이 나올 때까지 돌린다. 직접 구현은 이 반복을 while 문 등으로 직접 작성한다.
  3. 결과 반환루프가 끝나면 최종 답변이 완성되어 사용자에게 전달된다.

#1문제 상황

도구 호출이 없던 기존 방식에서는 모델이 텍스트 응답만 생성했다. 사용자가 "지금 서울 날씨 알려줘"라고 물어도 모델은 학습된 지식으로만 답하거나, 실제 데이터가 필요한 작업은 아예 수행할 수 없었다. 시스템 외부 상태를 읽거나 변경하는 일은 모델의 출력 범위 밖이라, 날씨 조회·데이터베이스 변경·파일 처리 같은 작업은 전부 별도의 코드로 사용자 요청을 분석해 수동으로 연결해야 했다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 도구 정의 전달응용 프로그램이 함수 이름·설명·파라미터 형식을 모델 호출에 함께 실어 보낸다. 모델은 이 정보를 보고 함수 호출 요청을 만들 수 있게 된다.
  2. 함수 호출 요청 수신 및 실행모델이 정해진 형식의 함수 호출 출력을 내면 호스트 코드가 그 요청을 파싱해 실제 함수를 대신 실행한다.
  3. 결과 반환 및 최종 응답실행 결과를 모델에게 다시 넣으면 모델이 그 결과를 반영한 최종 답변을 사용자에게 생성한다.

#2핵심 질문

#4동작 과정

  1. 스키마 작성도구의 이름과 설명, 입력 파라미터 각각의 이름·타입·필수 여부를 JSON 스키마로 기술한다. 설명이 구체적일수록 모델이 언제 그 도구를 쓸지 정확히 판단한다.
  2. 모델에 등록작성한 스키마를 모델 호출에 실어 보내 모델이 도구의 존재와 입력 형식을 학습하도록 한다. 모델은 응답에서 이 스키마에 맞는 호출만 생성한다.
  3. 호출 검증과 실행호스트가 스키마와 일치하는지 검증한 뒤 실제 함수를 실행한다. 형식이 미리 고정되어 있어 검증과 오류 처리가 단순해진다.

#2핵심 질문

모델 응답 형식이 매번 달라져도 되는 불안정함을 없애려면 어떻게 해야 하는가?

#4동작 과정

  1. 검색 쿼리 생성모델이 사용자 질문을 분석해 검색할 키워드를 정하고 파일 검색 또는 웹 검색 도구를 호출한다.

#1문제 상황

모델이 코드를 만들어 내는 방식은 처음에는 파일 전체를 통째로 다시 생성하는 방식이었다. 프롬프트 하나에 원하는 결과를 적으면 모델이 관련 파일을 처음부터 끝까지 새로 써서 반환했고, 사람이 그 내용을 복사해 파일에 붙여넣어야 했다. 이 방식은 파일이 커질수록 토큰 비용이 늘고, 긴 파일에서 한 줄만 고치려 해도 나머지 전체를 다시 생성해야 해서 느리고 값비싸며, 잘못된 부분이 섞여 들어가면 어디가 고쳐진 것인지 확인하기도 어려웠다. 이런 이유로 파일 단위 재생성은 실제 코드 작업에 쓰기 어려운 방식이었다.

#2핵심 질문

전체 파일을 다시 쓰지 않고, 기존 코드를 지키면서 원하는 부분만 정확히 고치는 안전한 파일 조작은 어떻게 할 수 있을까?

#3동작 예시

파일 편집 도구는 기존 파일에서 바꾸고 싶은 정확한 조각(문자열)과 그 조각을 대체할 새 내용을 도구에 넘긴다. 도구는 파일 전체에서 그 조각이 정확히 한 곳에만 있는지 확인한 뒤, 그 위치만 새 내용으로 바꾼 결과를 파일에 반영한다. 예를 들어 함수 이름을 바꿀 때 전체 파일을 다시 쓰는 대신 "옛 이름"을 "새 이름"으로 치환하는 편집 요청 하나가 파일에 바로 적용된다.

#4동작 과정

  1. 탐색과 선택모델이 읽기 도구로 파일을 열어 바꿀 위치와 기존 내용을 확인하고, 유일하게 매칭되는 조각을 정한다.
  2. 편집 실행바꿀 원문(문자열)과 새 내용을 편집 도구에 넘기면, 도구가 원문과 정확히 일치하는 위치를 찾아 새 내용으로 치환한다. 일치하는 곳이 두 군데 이상이거나 없으면 적용하지 않고 오류를 돌려준다.
  3. 결과 확인편집이 끝난 뒤 해당 부분을 다시 읽어 바뀐 내용을 확인하고, 필요하면 이어서 다음 편집을 진행한다. 결과로 파일이 의도한 상태로 갱신된다.

2단계 도구 사용 — 에이전트가 세상과 연결되는 방식

한 턴에서 여러 도구를 동시에 호출하고, 도구가 많을 때는 관련 도구만 골라 런타임에 로드하게 하는 메커니즘이다.

#1문제 상황

처음에는 도구 호출이 한 턴에 하나씩 순차적으로만 실행되었다. 여러 파일을 읽거나 여러 검색을 해야 하는 작업이면 모델은 도구 하나의 결과를 기다렸다가 다음 도구를 호출해야 했고, 그 결과를 다시 기다려야 했다. 결과를 기다리는 동안 모델은 멈춰 있고, 호출 횟수만큼 왕복 지연이 쌓여 전체 실행이 느려졌다. 도구 목록이 길어질수록 모델이 매 턴 모든 도구의 이름과 설명을 다시 읽어야 해서 토큰도 낭비되었다.

#2핵심 질문

여러 도구 호출을 한 턴에 묶어 왕복 지연을 줄이고, 수백 개가 넘는 도구 중 필요한 것만 골라 쓸 수는 없을까?

#3동작 예시

모델이 "세 파일을 각각 읽어라"라는 작업을 받으면 세 파일 읽기를 하나의 응답에 담아 도구 호출 세 개를 한 번에 보낸다. 런타임이 이 셋을 동시에 실행해 결과를 모아 한 턴에 돌려준다. 호출이 따로 일어나는 게 아니라 묶음으로 처리되므로 왕복이 세 번이 아니라 한 번이 된다.

#4동작 과정

  1. 병렬 호출모델이 하나의 응답 안에 서로 의존하지 않는 도구 호출 여러 개를 담아 보내면, 런타임이 그것들을 동시에 실행하고 결과를 모두 모은다.
  2. 도구 검색도구가 많을 때는 모델이 먼저 짧은 검색 쿼리로 관련 도구만 목록에서 찾고, 그 결과로 얻은 도구 정의만 실제 컨텍스트에 로드한다. 전체 도구 목록을 매번 읽지 않아도 된다.
  3. 결과 통합실행된 각 도구의 결과가 한 턴의 입력으로 합쳐져 모델이 다음 행동을 결정한다. 묶음 처리 덕분에 하나씩 기다리던 지연이 사라진다.

#5한 줄 요약

독립적인 도구 호출을 한 턴에 묶어 동시 실행하고, 검색으로 필요한 도구만 로드해 지연과 토큰 비용을 줄이는 메커니즘

명확한 이름·설명·스키마와 입력 검증을 갖춰 도구가 실패하거나 오용되기 어렵게(포카요케) 설계하는 원칙이다.

#1문제 상황

도구가 처음 추가될 때는 이름과 설명이 모호하고 입력 형식도 느슨한 경우가 많았다. 도구 이름이 "처리"처럼 추상적이면 모델이 언제 이 도구를 써야 하는지 판단하지 못했고, 입력에 숫자 형식이나 필수 값이 제대로 정의되어 있지 않으면 모델이 잘못된 값을 넣어 런타임 오류를 일으켰다. 도구가 실패할 때마다 호출이 낭비되고, 오류를 보고받은 모델이 다시 시도하는 과정이 반복되어 전체 실행이 불안정해졌다.

#2핵심 질문

도구가 처음부터 오용되기 어렵게 만들어 실패 자체가 잘 일어나지 않게 하려면 어떻게 설계해야 할까?

#3동작 예시

파일 편집 도구를 만들 때 "편집"이라는 짧은 이름 대신 "파일_편집"처럼 동작이 드러나는 이름과, "기존 문자열을 새 문자열로 치환한다"는 구체적인 설명, 그리고 치환할 원문(필수, 문자열)과 새 내용(필수, 문자열)을 명시하는 스키마를 함께 정의한다. 필수 필드가 빠지거나 형식이 틀린 입력이 오면 도구가 실행 전에 거부하므로 잘못된 호출이 파일을 망칠 수 없다.

#4동작 과정

  1. 명확한 정의도구마다 동사 중심의 구체적인 이름과 "언제, 무엇을 하는지"를 설명하는 설명, 그리고 각 입력 필드의 이름·형식·필수 여부를 담은 스키마를 작성한다.
  2. 입력 검증(포카요케)호출이 들어오면 스키마에 따라 필수 필드 누락과 타입 불일치를 먼저 검사한다. 기준에 맞지 않는 입력은 실행하지 않고 즉시 오류로 돌려보내 오용을 막는다.
  3. 안전한 실행과 결과 반환검증을 통과한 호출만 실제 작업을 수행하고, 성공 여부를 명확한 형식으로 돌려준다. 모델이 결과를 읽고 다음 행동을 결정한다.

#5한 줄 요약

명확한 이름·설명·스키마와 입력 검증으로 도구가 실패하거나 오용되기 어렵게(포카요케) 설계해 호출 품질을 높이는 원칙

#1문제 상황

모델을 쓸 때는 프롬프트에 모든 필요한 정보를 한꺼번에 넣는 것이 일반적인 방식이었다. 그런데 모델이 한 번에 받을 수 있는 입력에는 상한이 있고, 이 상한을 넘는 정보는 잘리거나 아예 처리가 거부되었다. 대화가 길어지면 이전 대화 내용이 계속 쌓여 금방 상한에 닿았고, 도구 결과나 파일 내용을 추가하면 한참 전에 쓴 지시가 밀려나 소실되기 일쑤였다.

#2핵심 질문

한 번에 넣을 수 있는 입력 범위가 정해져 있는데, 그 범위 안에서 프롬프트와 도구 결과와 대화 이력을 어떻게 배분해야 할까?

#3동작 예시

컨텍스트 윈도가 10만 토큰인 모델이 있고, 현재 대화 이력이 6만 토큰, 도구 결과가 3만 토큰이라면 남는 공간은 1만 토큰이다. 새 작업 지시를 이 1만 토큰 안에 넣어야 하므로, 큰 파일 전체를 붙이는 대신 필요한 부분만 요약해서 넣는 식으로 예산을 짠다.

#4동작 과정

  1. 예산 파악먼저 컨텍스트 윈도의 총 크기를 확인하고, 현재 대화 이력과 도구 결과, 시스템 지시가 각각 얼마나 차지하는지 토큰 수로 센다.
  2. 배분 결정남은 공간 안에서 새 프롬프트·파일 내용·검색 결과 중 무엇을 얼마나 넣을지 우선순위대로 정한다. 중요도가 낮은 정보는 요약하거나 생략한다.
  3. 한도 내 실행정해진 예산 안에서 작업을 수행한다. 도중에 입력이 한도를 넘으려 하면 이전 내용을 줄이거나 정리해 항상 윈도 안에서 처리한다.

#5한 줄 요약

한정된 컨텍스트 윈도 안에서 프롬프트·도구 결과·대화 이력이 차지하는 토큰을 관리해 처리 범위를 넘지 않게 하는 예산 개념

반복 호출에서 동일한 프롬프트 앞부분을 서버에 캐시해 레이턴시와 비용을 줄이는 기능.

#1문제 상황

에이전트가 여러 차례 모델을 호출할 때, 매 호출마다 같은 프롬프트 앞부분(시스템 지시문, 긴 문서, 대화의 앞부분)을 처음부터 다시 전송하고 다시 처리해야 했다. 호출이 반복될수록 같은 내용을 계속 재계산하느라 응답이 느려지고, 그만큼 처리 비용이 반복해서 청구되었다. 내용이 같다는 사실은 알지만 재사용할 방법이 없어 매번 처음처럼 비싸게 처리하는 비효율이 남아 있었다.

#2핵심 질문

호출마다 반복해서 들어오는 동일한 프롬프트 앞부분을 다시 계산하지 않고 재사용하면 레이턴시와 비용을 줄일 수는 없을까?

#3동작 예시

동일한 시스템 지시문과 2만 토큰짜리 규칙 문서가 매 호출 앞부분에 붙는 상황에서, 첫 호출이 그 앞부분을 처리한 뒤 서버에 저장해 둔다. 두 번째 호출부터는 캐시된 앞부분을 그대로 재사용하고 새로 달라진 뒷부분만 처리한다. 긴 앞부분의 계산이 반복되지 않아 응답이 빨라지고 비용이 줄어든다.

#4동작 과정

  1. 캐시 저장첫 호출에서 프롬프트 앞부분이 처리될 때 그 내용이 서버에 캐시로 저장된다. 이때 캐시 저장 비용이 한 번 발생한다.
  2. 캐시 재사용이후 호출에서 프롬프트 앞부분이 캐시된 내용과 정확히 일치하면 새로 계산하지 않고 저장된 값을 읽어 사용한다. 앞부분이 바뀌면 캐시는 다시 저장된다.
  3. 응답과 비용 정산모델은 이어지는 뒷부분만 추가로 처리해 응답을 만들고, 캐시를 읽은 앞부분은 더 낮은 비용으로 계산된다.

반복 호출에서 동일한 프롬프트 앞부분을 서버에 캐시해 재계산을 없애고 레이턴시와 비용을 줄이는 기능

길어진 대화를 요약·압축해 컨텍스트 윈도에 다시 담아 오래된 토큰을 절약하며 세션을 이어가는 기법.

#1문제 상황

긴 대화를 이어가면 이전 메시지가 계속 쌓여 컨텍스트 윈도를 금방 가득 채웠다. 윈도가 꽉 차면 윗부분부터 밀려나 오래된 대화 내용과 초기 지시가 통째로 사라졌고, 그 결과 모델이 앞서 정한 방향이나 결정을 잊어버리는 문제가 생겼다. 단순히 오래된 토큰을 지우는 방식은 필요한 정보까지 함께 잃는 손실이 컸다.

#2핵심 질문

컨텍스트가 가득 찼을 때 중요한 정보는 남기고 오래된 토큰만 압축해 세션을 이어가려면 어떻게 해야 할까?

#3동작 예시

대화가 15만 토큰에 이르러 윈도 한도에 닿으면, 시스템이 지금까지의 대화 전체를 요약한다. "사용자가 X 요구사항을 정했고, 이미 A·B 기능을 구현했으며, 현재 C 문제를 해결 중이다" 같은 핵심만 추린 5천 토큰짜리 압축본을 만들어 새 컨텍스트에 넣는다. 원래 대화는 사라지지만 필수 정보는 요약 안에 남아 다음 작업을 계속할 수 있다.

#4동작 과정

  1. 압축 시점 판단컨텍스트가 한도에 가까워지면 시스템이 이전 대화를 요약본으로 압축할지 판단한다.
  2. 요약 생성지금까지의 대화에서 결정된 사항·진행 상태·남은 과제 같은 핵심 정보를 추려 짧은 요약을 만든다.
  3. 세션 재구성요약본과 최근 메시지를 새 컨텍스트에 담아 모델이 이어서 작업한다. 새 호출은 줄어든 토큰으로 동일한 작업 맥락을 유지한다.

#1문제 상황

모델 호출은 기본적으로 상태가 없는 방식이었다. 호출 하나가 끝나면 그 응답은 다음 호출로 자동 이어지지 않아서, 매 호출마다 지금까지의 대화 전체를 프롬프트에 다시 실어 보내야 했다. 대화가 길어질수록 매번 전체 이력을 재전송하느라 토큰이 중복 사용되었고, 전달을 빠뜨리면 모델이 아까 한 결정을 모르는 상태로 작업이 꼬였다.

#2핵심 질문

호출 사이에 대화 이력과 진행 상태를 보관해서, 다음 호출이 이전 내용을 이어받아 일관되게 작업하게 하려면 어떻게 해야 할까?

#3동작 예시

한 세션에서 사용자가 "로그인 기능을 만들어줘"라고 지시하고, 모델이 파일을 만들고 답변했다. 이때 이 메시지들이 세션 상태로 저장되고, 다음 호출에는 이전 대화 전체가 메시지 목록으로 다시 전달된다. 사용자가 "이제 에러 처리를 추가해줘"라고만 해도 모델은 앞선 대화를 읽고 로그인 기능에 에러 처리를 덧붙인다.

#4동작 과정

  1. 상태 기록한 번의 에이전트 실행(세션)에서 사용자 메시지와 모델 응답·도구 결과가 순서대로 대화 이력에 쌓인다.
  2. 이력 전달다음 호출을 보낼 때 저장된 이력이 메시지 목록으로 프롬프트에 포함되어 모델이 전체 맥락을 보게 된다.
  3. 상태 갱신과 계속새 응답이 다시 이력에 추가되어 세션이 끝날 때까지 상태가 계속 이어진다. 세션을 재개하면 저장된 상태부터 작업을 계속한다.

#4동작 과정

  1. 기록대화나 작업에서 남길 가치가 있는 정보(규칙, 선호, 결정, 진행 상태)를 영속 메모리에 저장한다.
  2. 보존세션이 종료되어 대화 히스토리가 사라져도 메모리 저장소의 내용은 그대로 유지된다.
  3. 재사용다음 세션이 시작될 때 저장된 메모리를 컨텍스트로 읽어들여, 사용자가 다시 말하지 않아도 그 정보를 바탕으로 작업을 시작한다.

#1문제 상황

#2핵심 질문

  1. 권한 산정작업 내용을 분석해 꼭 필요한 도구와 권한 범위만 목록으로 정합니다.

  3. 작업 실행과 회수부여된 권한 안에서 작업이 실행되고, 종료 시점에 권한이 해제되어 다음 작업에 남지 않습니다.

#1문제 상황

여러 에이전트가 한 저장소에서 동시에 작업하려면 기존 방식은 브랜치를 나누거나 작업 폴더를 따로 복사하는 방법을 썼다. 브랜치를 나누면 커밋을 만들고 병합(merge)할 때마다 충돌이 나고, 작업 폴더를 복사하면 저장소 전체 히스토리를 매번 새로 받아야 해서 시간과 디스크가 낭비된다. 같은 브랜치에서 동시에 작업하면 한쪽이 만든 변경이 다른쪽 작업 공간에 바로 보여 서로 격리되지 않는다.

#2핵심 질문

여러 에이전트가 같은 저장소를 쓰면서도 서로의 작업을 건드리지 않고 동시에 일하려면 어떻게 해야 할까?

#3동작 예시

Git 워크트리는 하나의 저장소에서 여러 개의 작업 폴더를 만들어 주는 기능이다. 각 작업 폴더는 서로 다른 브랜치를 체크아웃한 상태로 존재해서, 에이전트 A는 main 브랜치 작업 폴더에서, 에이전트 B는 feature 브랜치 작업 폴더에서 동시에 각자의 파일을 편집한다. 두 폴더는 같은 저장소의 객체 데이터를 공유하므로 저장소를 복사할 필요가 없고, 각자 커밋을 만들어도 상대 작업 폴더에는 영향이 없다.

#4동작 과정

  1. 워크트리 생성에이전트별로 git worktree add로 독립된 작업 폴더를 만들고 각자 다른 브랜치를 거기에 연결한다.
  2. 동시 작업과 커밋각 에이전트는 자기 폴더에서 파일을 편집·커밋한다. 커밋은 같은 저장소 객체 데이터에 쌓여도 작업 폴더끼리는 서로 보이지 않는다.
  3. 병합과 정리작업이 끝나면 각 브랜치를 main에 병합하고 사용이 끝난 워크트리를 git worktree remove로 제거해 정리한다.

#2핵심 질문

에이전트가 샌드박스 안에서 만든 파일과 산출물을 어떻게 밖으로 꺼내 보존하고 공유할 수 있을까?

#3동작 예시

에이전트 실행이 끝나면 샌드박스에 남아 있던 파일들을 환경에서 찾을 수 있고, 그 파일을 다운로드하거나 다음 실행의 입력으로 다시 넣을 수 있다. 예를 들어 에이전트가 분석 결과를 CSV 파일로 만들어 샌드박스에 저장했다면, 실행 종료 후 그 경로의 파일을 다운로드해서 사용자가 받아 보거나 다른 에이전트 실행에 그 파일을 초기 파일(아티팩트)로 넘겨줄 수 있다.

#4동작 과정

여러 작업을 하나의 에이전트에게 모두 맡기는 기존 방식은 모든 입력이 같은 처리 경로를 지난다. 단순한 질문도 복잡한 추론 경로를 거쳐 답이 느려지고, 작업 유형에 따라 요구되는 도구·문맥·모델 특성이 달라도 하나의 에이전트가 전부 소화해야 하므로 전문성이 떨어지며 응답 품질이 평균에 머문다.

#2핵심 질문

입력을 하나의 에이전트가 전부 처리하는 대신, 작업 유형에 맞는 전문화된 에이전트에게 먼저 보내면 더 정확하고 빠르게 답할 수 없는가?

#3동작 예시

사용자가 "오늘 날씨 알려줘"라고 입력하면 라우터 역할의 에이전트가 이 입력을 단순 질의로 분류해 날씨 도구를 가진 가벼운 에이전트로 보낸다. 반면 "이 데이터 분석해서 보고서 작성해줘"라는 입력은 복잡 작업으로 분류해 데이터 분석·도구 작성 능력을 갖춘 무거운 에이전트로 보낸다. 입력을 먼저 분류하는 것이 라우팅 패턴의 핵심 동작이다.

#4동작 과정

  1. 입력 수신 및 분류라우팅 에이전트가 들어온 입력을 보고 단순 작업인지 복합 작업인지 판정한다.
  2. 에이전트 선택분류 결과에 따라 해당 작업 유형을 전담하는 에이전트를 하나 고른다.
  3. 전달 및 실행원본 입력을 선택된 에이전트에게 넘겨 처리하게 하고, 그 결과를 사용자에게 돌려준다.

입력을 먼저 분류해 작업 유형에 맞는 전문화된 에이전트로 보내는 것으로, 단순·복합 입력을 구분해 각각에게 적합한 처리 경로를 태워 주는 것

#2핵심 질문

#3동작 예시

  2. 표준 인터페이스 통한 통신호스트는 클라이언트가 제공하는 표준 메시지 형식으로 서버의 기능을 요청하고 응답을 받는다.

#3동작 예시

파일 서버가 호스트에 세 가지를 노출한다고 하자. 리소스는 "특정 프로젝트 문서"처럼 호스트가 읽을 수 있는 데이터이고, 도구는 "파일 검색"처럼 호스트가 실행을 요청할 수 있는 함수이며, 프롬프트는 "코드 리뷰"처럼 재사용 가능한 입력 템플릿이다. 호스트는 이 세 종류를 각각의 표준 방식으로 조회하고 사용한다.

#4동작 과정

  1. 기능 노출서버가 제공하는 기능을 리소스·도구·프롬프트 세 종류로 구분해 호스트가 볼 수 있게 목록을 제공한다.
  2. 기능 선택호스트가 모델의 요청에 따라 읽을 리소스, 실행할 도구, 적용할 프롬프트를 골라 서버에 요청한다.
  3. 결과 수신서버가 요청한 데이터를 돌려주거나 도구 실행 결과를 반환하고, 호스트는 이를 모델의 응답에 반영한다.

#5한 줄 요약

MCP 서버가 호스트에 읽을 수 있는 데이터(리소스), 실행 가능한 함수(도구), 재사용 가능한 프롬프트라는 세 가지 기본 요소를 표준화된 형태로 노출하는 것

클라이언트와 서버가 메시지를 주고받는 통신 방식 — 로컬 프로세스의 stdio와 HTTP 기반의 스트리머블 HTTP.

#1문제 상황

MCP 클라이언트와 서버가 메시지를 주고받으려면 둘 사이에 통신 경로가 필요하다. 전송 방식이 정해져 있지 않으면 클라이언트는 서버가 로컬 프로세스인지 원격 서비스인지에 따라 각각 다른 방식으로 연결을 구현해야 하고, 연결 설정과 메시지 인코딩이 서버마다 달라져 표준화가 깨진다.

#2핵심 질문

클라이언트와 서버가 주고받는 메시지를 어떤 실행 환경에서도 동일하게 전달할 수 있는 표준 전송 방식이 필요한 것이 아닌가?

#3동작 예시

로컬에서 실행되는 파일 서버는 클라이언트 프로세스가 자식 프로세스로 띄우고 표준 입력·표준 출력(stdio)을 통해 메시지를 주고받는다. 반면 원격에 있는 데이터베이스 서버는 클라이언트가 HTTP 연결을 열어 스트리머블 HTTP 방식으로 메시지를 주고받는다. 어느 쪽이든 메시지 내용과 형식은 같고, 운반하는 통로만 다르다.

#4동작 과정

  1. 연결 수립로컬 서버는 클라이언트가 자식 프로세스로 실행해 stdio 파이프를 열고, 원격 서버는 HTTP 엔드포인트에 연결한다.
  2. 메시지 교환클라이언트와 서버가 양방향으로 JSON 메시지를 주고받으며 요청과 응답을 처리한다.
  3. 세션 유지 및 종료스트리머블 HTTP는 연결 안에서 서버가 여러 응답을 이어 보낼 수 있고, 작업이 끝나면 연결을 닫는다.

#5한 줄 요약

클라이언트와 서버가 로컬 프로세스에서는 stdio, 원격에서는 HTTP 기반의 스트리머블 HTTP로 메시지를 주고받는 표준 전송 방식을 제공하는 것

MCP 인가와 OAuth

MCP 서버가 보호된 리소스에 접근할 때 OAuth 2.1 기반으로 클라이언트를 인가하고 토큰을 발급·갱신하는 절차.

#1문제 상황

MCP 서버가 보호된 리소스(사용자의 파일, 메일, 저장소 등)에 접근하려면 누가 접근해도 되는지 확인하는 과정이 필요하다. 기존에는 클라이언트가 서버에 직접 API 키나 비밀번호를 보내는 방식이 흔했다. 이 방식은 키가 코드나 설정 파일에 남아 유출되기 쉽고, 키 하나가 만료되면 사용자가 직접 새 키를 발급받아 다시 넣어야 했다. 또한 키만 알면 어떤 작업이든 가능해져 접근 범위를 좁게 제한하기 어렵다는 한계가 있었다.

#2핵심 질문

사용자가 매번 비밀번호를 노출하지 않으면서, MCP 서버가 사용자를 대신해 보호된 리소스에 최소한의 범위로만 접근하게 하려면 어떻게 해야 하는가?

#3동작 예시

사용자가 MCP 클라이언트(채팅 에이전트)에서 "내 캘린더에 일정을 추가해 줘"라고 요청한다. 클라이언트는 MCP 서버(캘린더 서버)에 접근이 필요하다는 신호를 보내고, 서버는 브라우저에서 사용자에게 OAuth 2.1 인가 화면을 띄운다. 사용자가 "허용"을 누르면 서버는 사용자를 확인하는 대신 클라이언트에게 일정 읽기·쓰기 범위만 담긴 토큰을 발급한다. 이후 클라이언트는 그 토큰만 들고 캘린더에 접근하며, 비밀번호는 어디에도 전달되지 않는다.

#4동작 과정

  1. 인가 요청과 사용자 승인MCP 서버가 클라이언트의 접근 요청을 받으면 사용자에게 인가 화면(어떤 리소스를 어떤 범위로 쓸지 묻는 화면)을 보여주고, 사용자가 허용하면 서버는 짧은 수명의 임시 코드를 클라이언트에 넘긴다.
  2. 토큰 발급과 접근클라이언트가 임시 코드를 서버의 토큰 엔드포인트(토큰을 발급하는 주소)에 보내면, 서버는 접근 토큰(보호된 리소스에 접근할 때 제시하는 자격 증명)과 갱신 토큰(접근 토큰이 만료됐을 때 새로 받기 위한 토큰)을 발급한다. 클라이언트는 접근 토큰으로 리소스에 접근한다.
  3. 토큰 갱신과 종료접근 토큰이 만료되면 클라이언트가 갱신 토큰을 사용해 새 접근 토큰을 받는다. 사용자가 권한을 취소하거나 클라이언트가 세션을 끝내면 토큰은 폐기되어 더 이상 접근할 수 없다.

#5한 줄 요약

사용자가 직접 비밀번호를 노출하지 않고, 사용자의 승인 아래 발급된 범위 제한 토큰으로 MCP 클라이언트가 서버 리소스에 접근하게 하는 인가 절차

MCP 보안 모범 사례

MCP 서버를 안전하게 설계·운영하기 위한 공격 벡터 분석과 보안 권장 사례 모음.

#1문제 상황

MCP 서버는 파일 시스템, 데이터베이스, 외부 API 같은 민감한 리소스에 붙는다. 기존에는 서버 하나가 모든 기능을 열어두고 클라이언트를 신뢰하는 방식이 많았다. 이 방식은 악성 프롬프트 주입(사용자 입력에 숨긴 지시문이 모델을 조종하는 공격)이나 과도한 권한으로 인해 서버가 의도하지 않은 작업을 수행하게 되는 문제가 생긴다. 또한 서버가 어떤 도구를 어떤 범위로 허용하는지 명시하지 않으면 클라이언트는 모든 기능을 쓸 수 있게 되어 공격 표면이 커진다.

#2핵심 질문

MCP 서버가 악성 입력과 과도한 권한으로부터 안전하게 동작하도록 하려면 어떤 기준으로 설계하고 운영해야 하는가?

#3동작 예시

파일 접근 서버 하나가 있다고 하자. 이 서버는 시스템 전체 경로를 허용하지 않고 특정 작업 폴더 하나만 읽고 쓰도록 구성한다. 클라이언트가 ../../../etc/passwd처럼 폴더 밖으로 벗어나는 경로를 요청하면 서버는 경로를 정규화(실제 경로로 변환)한 뒤 허용 범위를 벗어났다는 것을 감지하고 요청을 거부한다. 이렇게 "기본 거부, 명시적 허용" 방식이 서버 보안의 출발점이다.

#4동작 과정

  1. 공격 표면 줄이기서버가 노출하는 도구를 필요한 것만 최소로 선언하고, 각 도구에 최소 권한(작업을 수행하는 데 필요한 가장 좁은 권한)을 부여한다. 입력 검증(형식·길이·허용 값 확인)과 샌드박싱(격리된 실행 환경)을 적용해 예상 밖의 입력을 차단한다.
  2. 위협 모델링과 모니터링프롬프트 주입, 경로 탐색, DoS(서비스 거부 공격) 같은 공격 벡터를 목록화하고, 서버 로그와 감사 기록(누가 언제 무엇을 했는지 남기는 기록)을 활성화해 이상 접근을 추적한다.
  3. 인가와 배포 검증민감한 도구 앞에 사용자 확인 단계를 두고, 배포 전에 종속성 취약점을 스캔하며 패키지 서명(게시자가 만든 것을 확인하는 서명)을 검증한다.

#5한 줄 요약

공격 벡터를 분석해 도구와 권한을 최소화하고 입력 검증·모니터링을 적용해 MCP 서버를 안전하게 설계·운영하는 보안 기준

원격 MCP 서버·터널·커넥터

인터넷에 호스팅된 MCP 서버에 연결하거나, 방화벽 안의 로컬 서버를 터널·커넥터로 안전하게 노출하는 방법.

#1문제 상황

MCP 서버는 보통 같은 컴퓨터에서 실행되는 로컬 프로세스(현재 실행 중인 프로그램)로 시작했다. 그러나 팀이 공유하는 서버나 회사 내부 시스템에 붙는 서버는 인터넷을 통해 여러 클라이언트가 사용해야 한다. 이때 문제는 로컬 서버가 방화벽 뒤에 있어 외부에서 직접 접근할 수 없고, URL과 인증 방식을 수동으로 관리하면 서버가 노출되거나 연결 정보가 흩어진다는 점이다. 서버가 바뀔 때마다 모든 클라이언트 설정을 고쳐야 하는 유지보수 부담도 컸다.

#2핵심 질문

방화벽 안에 있는 MCP 서버를 인터넷의 클라이언트가 안전하고 일관된 방법으로 연결하려면 어떻게 해야 하는가?

#3동작 예시

개발자의 컴퓨터에 있는 MCP 서버를 외부 에이전트가 사용해야 한다고 하자. 서버는 연결 URL(접속 주소)을 커넥터 플랫폼에 등록하고, 클라이언트는 그 커넥터 주소로 요청을 보낸다. 커넥터는 요청을 받아 터널(외부 요청을 방화벽 안 서버로 전달하는 통로)을 통해 로컬 서버에 전달하고, 응답을 다시 클라이언트에 돌려준다. 개발자는 방화벽 설정을 바꾸지 않아도 외부에서 자기 서버를 쓸 수 있게 된다.

#4동작 과정

  1. 서버 노출 구성로컬 MCP 서버에 인증(접근 자격 확인)과 URL을 붙이고, 터널링 도구나 커넥터 플랫폼에 서버를 등록해 외부에서 접근 가능한 엔드포인트(접속 지점)를 만든다.
  2. 클라이언트 연결클라이언트가 커넥터나 원격 서버의 URL과 인증 정보를 설정에 담아 연결한다. 커넥터를 쓰면 여러 서버를 한 곳에서 관리하고 인증·라우팅(요청을 알맞은 서버로 보내는 일)이 커넥터에서 처리된다.
  3. 요청 전달과 응답클라이언트 요청이 터널 또는 커넥터를 거쳐 로컬 서버에 도달하고, 서버가 도구를 실행한 결과가 같은 경로로 클라이언트에 돌아간다. 연결 정보 변경 시 커넥터 설정만 갱신하면 된다.

#5한 줄 요약

터널과 커넥터를 통해 방화벽 안의 MCP 서버를 외부에서 안전하게 호출할 수 있게 하여, 서버 배포와 인증·연결 관리를 한 곳에서 처리하는 것

에이전트 스킬

지시문과 예시·자산을 묶어 모델에 재사용 가능한 전문 능력으로 주입하는 패키지.

#1문제 상황

모델에게 특정 작업을 잘 시키려면 이전에는 시스템 프롬프트(모델의 기본 지시문)에 지시문과 예시를 직접 붙여 넣었다. 이 방식은 프롬프트가 길어질수록 매번 붙여 넣어야 하고, 파일을 읽는 방법이나 실행 절차 같은 절차적 지식(순서대로 따라야 하는 방법)을 문장으로 표현하기 어렵다. 또한 같은 능력을 여러 세션이나 다른 프로젝트에서 재사용하려면 매번 같은 내용을 복사해 넣어야 하는 비효율이 있었다.

#2핵심 질문

절차와 예시, 참고 자산을 하나의 패키지로 묶어 모델이 재사용할 수 있는 전문 능력으로 만드는 방법은 무엇인가?

#3동작 예시

"PDF에서 표를 추출하는" 스킬이 있다고 하자. 이 스킬은 SKILL.md라는 지시문 파일(작업 방법과 순서를 적은 파일)과 표 추출을 위한 예시 코드, 참고 문서를 폴더 하나에 담고 있다. 모델이 PDF 표 추출이 필요할 때 이 스킬을 불러오면 지시문에 따라 라이브러리를 설치하고 코드를 작성해 표를 뽑아낸다. 스킬은 마치 모델이 즉시 참조할 수 있는 작업 매뉴얼처럼 동작한다.

#4동작 과정

  1. 스킬 구성SKILL.md 지시문, 예시, 필요한 자산(코드·데이터 파일)을 폴더 구조로 묶고 스킬 이름과 설명을 정의한다.
  2. 스킬 호출모델이 작업을 만나면 스킬 설명을 보고 필요한 스킬을 선택해 해당 폴더를 읽는다. 설명이 작업과 맞는지 판단해 스킬이 활성화된다.
  3. 지시문 실행모델이 SKILL.md에 적힌 절차를 단계대로 따라가며 자산을 활용해 작업을 수행하고 결과를 낸다.

#5한 줄 요약

지시문·예시·자산을 한 패키지로 묶어 모델이 필요할 때 불러와 사용하는 재사용 가능한 전문 능력 주입 방식

플러그인

스킬과 MCP 서버 구성 등을 하나로 묶어 여러 에이전트 세션·환경에서 재사용할 수 있게 만든 패키지.

#1문제 상황

에이전트 하나를 구성하려면 스킬(작업 절차 패키지), MCP 서버 연결 정보, 도구 설정을 각각 따로 만들어 에이전트마다 붙여야 했다. 이 방식은 같은 조합을 다시 쓰려면 JSON 설정을 복사해 붙여 넣고 URL이나 키 값을 일일이 다시 지정해야 했다. 구성이 늘어날수록 설정이 흩어져 어떤 에이전트에 무엇이 붙어 있는지 파악하기 어렵고, 여러 환경(개발·운영)에서 동일한 구성을 유지하기 힘들다는 문제가 있었다.

#2핵심 질문

스킬과 MCP 서버 구성 같은 도구 묶음을 하나로 만들고 여러 에이전트 세션·환경에서 그대로 재사용하는 방법은 무엇인가?

#3동작 예시

"도록 조회 플러그인"이 있다고 하자. 이 플러그인 안에는 도록 MCP 서버의 URL과 인증 정보, 그리고 조회 절차 스킬이 들어 있다. 에이전트 설정에 플러그인 이름을 지정하기만 하면 도록 조회 기능과 서버 연결이 한 번에 활성화된다. 다른 에이전트나 다른 환경에서도 같은 플러그인 이름만 지정하면 동일한 구성이 재현된다.

#4동작 과정

  1. 플러그인 패키징스킬 파일, MCP 서버 구성, 도구 정의를 하나의 플러그인 구조로 묶고 이름·버전·설명을 정의한다.
  2. 플러그인 등록·설치플러그인을 에이전트나 환경에 등록하면 플러그인 내부의 서버 연결과 스킬이 함께 사용 가능한 상태로 로드된다.
  3. 실행과 재사용에이전트가 플러그인에 포함된 도구와 스킬을 사용해 작업을 수행한다. 다른 세션·환경에서도 같은 플러그인을 참조해 동일한 구성을 사용한다.

#5한 줄 요약

스킬과 MCP 서버 구성 등을 하나의 패키지로 묶어 이름으로 참조하는 것만으로 여러 에이전트 세션·환경에서 재사용하게 하는 것

MCP 디버깅과 인스펙터

MCP 서버와 클라이언트 통합을 대화형으로 테스트·디버깅하는 인스펙터 도구와 문제 해결 절차.

#1문제 상황

MCP 서버를 만들고 클라이언트와 연결하면 서버가 요청에 응답하지 않거나, 도구가 호출돼도 결과가 이상한 경우가 많다. 기존에는 로그 파일에 출력된 내용을 뒤져 원인을 추측하고, 코드에 임시 출력문을 넣어 다시 실행하는 식으로 문제를 찾아야 했다. 이 방식은 서버-클라이언트 사이에 오고 가는 메시지(요청·응답)가 어떤 순서와 내용으로 흐르는지 보이지 않아, 연결 실패인지 서버 오류인지 인증 문제인지 구분하기 어렵다는 한계가 있었다.

#2핵심 질문

MCP 서버와 클라이언트 사이의 메시지 흐름을 직접 보고 도구 호출을 시험하면서 문제를 찾으려면 어떻게 해야 하는가?

#3동작 예시

MCP 인스펙터라는 웹 도구에 로컬 MCP 서버 주소를 입력하면, 서버가 선언한 도구 목록이 화면에 나타난다. 개발자가 화면에서 도구 하나를 골라 예시 인자를 넣고 호출 버튼을 누르면, 클라이언트가 보낸 요청과 서버가 돌려준 응답 메시지가 원문 그대로 옆 패널에 표시된다. 이로써 서버가 정상 응답을 주는지, 에러를 돌려주는지 한눈에 확인할 수 있다.

#4동작 과정

  1. 서버 연결과 목록 확인인스펙터에 서버 주소를 입력해 연결하고, 서버가 노출한 도구 목록과 각 도구의 입력 스키마(받는 인자 형식 정의)를 확인한다.
  2. 대화형 도구 호출화면에서 도구를 선택해 인자를 넣고 직접 호출해 본다. 이때 서버-클라이언트 간 JSON-RPC 메시지(구조화된 요청·응답 형식)가 로그로 표시되어 연결·요청·응답 단계를 추적한다.
  3. 문제 격리와 수정응답 메시지의 에러 코드와 내용을 보고 서버 코드나 구성의 문제를 찾아 수정한 뒤 인스펙터에서 다시 호출해 정상 동작을 확인한다.

#5한 줄 요약

인스펙터로 MCP 서버와 클라이언트 사이의 메시지를 대화형으로 보고 도구 호출을 직접 시험하며 통합 문제를 찾아 해결하는 디버깅 도구

MCP 레지스트리와 배포

MCP 서버를 공개 레지스트리에 게시·버저닝하고 배포하는 절차와 정책.

#1문제 상황

MCP 서버를 다른 사람이나 팀이 쓰게 하려면 서버 코드를 공유하고 실행 방법을 문서로 알려 주는 수준에 그쳤다. 사용자는 저장소를 직접 찾아 설치하고, 서버가 업데이트되면 버전이 몇인지 어떤 변경이 있었는지 알기 어려웠다. 서버마다 배포 방식이 제각각이어서 보안 점검을 거친 서버인지, 유지 관리가 되는 서버인지 판단할 기준이 없었다. 이는 서버를 신뢰하고 설치하기 어렵게 만드는 문제였다.

#2핵심 질문

MCP 서버를 누구나 찾아 설치할 수 있고 버전과 정책이 관리되도록 공개적으로 게시·배포하려면 어떤 절차가 필요한가?

#3동작 예시

개발자가 만든 시간 추적 MCP 서버를 레지스트리(공개 서버 목록 저장소)에 등록한다고 하자. 서버 설명과 설치 명령, 버전을 담은 메타데이터와 함께 서버를 게시하면, 다른 사용자는 레지스트리에서 "시간 추적"을 검색해 설치 명령을 그대로 실행해 쓴다. 새 버전을 올리면 레지스트리에 버전 기록이 남고, 기존 사용자는 업데이트 가능 여부를 확인할 수 있다.

#4동작 과정

  1. 게시 준비서버에 이름·설명·버전·연결 정보를 담은 메타데이터를 작성하고, 배포할 서버 코드와 설정을 묶는다.
  2. 레지스트리 게시·버저닝서버를 레지스트리에 등록하고 버전을 부여한다. 버전은 시맨틱 버저닝(주·부·수 버전 번호 규칙)으로 관리해 변경 크기와 호환성을 나타낸다.
  3. 검색·설치·배포사용자가 레지스트리에서 서버를 검색해 설치 명령을 실행하거나, 배포 플랫폼을 통해 실행 환경에 배포한다. 이후 관리자가 새 버전을 게시하면 사용자는 버전 기록을 보고 갱신한다.

#5한 줄 요약

MCP 서버를 공개 레지스트리에 버전·정책과 함께 게시해 누구나 검색·설치하고 갱신할 수 있게 하는 배포 절차

8단계 관측·평가·운영 반복

에이전트 실행의 모든 단계를 기록해 대시보드에서 검사하고 OTLP JSON으로 내보낼 수 있게 하는 관측의 기본 수단.

#1문제 상황

에이전트를 실행할 때 결과만 보고 성공인지 실패인지 판단하던 기존 방식은, 어느 단계에서 답이 틀어졌는지 알 수 없다는 명확한 한계가 있다. 여러 도구 호출과 긴 추론이 섞인 실행이라면 어느 호출이 잘못된 입력을 받았는지, 어느 단계에서 시간이 오래 걸렸는지 전혀 추적할 수 없다.

#2핵심 질문

에이전트 실행의 각 단계를 기록해 두고 나중에 검사할 수 있게 하려면 어떻게 해야 할까?

#3동작 예시

에이전트가 한 번 실행되면 하나의 트레이스가 만들어진다. 트레이스 안에는 에이전트가 받은 입력, 생성한 응답, 호출한 도구 각각과 그 결과가 순서대로 스팬(span, 실행 구간 하나하나)으로 쌓인다. 이 스팬들이 대시보드에서 위에서 아래로 펼쳐져 보이므로, 어떤 단계가 실행됐고 각 단계가 얼마나 걸렸는지 한눈에 검사할 수 있다.

#4동작 과정

  1. 실행 기록 생성에이전트 API가 실행될 때 입력·출력·도구 호출·지연 시간을 담은 트레이스를 시각화 도구로 전송한다.
  2. 대시보드 검사트레이스 목록에서 실행 하나를 열어 스팬 트리로 진행 경로와 각 단계의 수행 시간, 생성 토큰 수를 본다.
  3. 데이터 내보내기트레이스를 OTLP(OpenTelemetry 프로토콜, 관측 데이터 전송 표준) JSON으로 내보내 자체 모니터링 시스템에 연결한다.

#5한 줄 요약

에이전트 실행의 모든 단계를 기록해 대시보드에서 검사하고 OTLP JSON으로 내보낼 수 있게 하는 관측의 기본 수단

8관측·평가·운영 반복08-02

8단계 관측·평가·운영 반복

에이전트에게 작업을 맡길 때 사람은 매번 요청문에 필요한 규칙을 다시 적어 넣거나, 같은 지침을 여러 채팅 세션에 반복해서 붙여 넣는다. 이 방식은 규칙이 늘어날수록 요청문이 길어지고, 세션마다 표현이 달라져 에이전트가 아키텍처나 코딩 스타일을 제각각으로 적용한다. 규칙과 실제 결과가 어긋나도 어디서 어긋났는지 찾기 어렵다.

#2핵심 질문

에이전트가 프로젝트마다 매번 같은 아키텍처 규칙과 개발 취향을 따르게 하려면 어떻게 해야 하는가?

#3동작 예시

AGENTS.md 파일 하나를 프로젝트 루트에 두고 그 안에 "DB 접근은 반드시 리포지토리 계층을 거친다", "에러는 커스텀 예외로 던진다" 같은 규칙을 적는다. 에이전트는 세션을 시작할 때 이 파일을 읽어 지침으로 삼고, 이후 모든 응답이 그 규칙 아래에서 생성된다. 규칙이 파일 하나에 모여 있으므로 수정도 한 곳에서만 하면 된다.

#4동작 과정

  1. 지침 작성프로젝트 루트의 AGENTS.md에 아키텍처 규칙, 개발 취향, 금지 사항을 문장으로 정리해 저장한다.
  2. 자동 로드에이전트가 해당 프로젝트에서 작업을 시작하면 이 파일을 자동으로 읽고 지침으로 적용한다.
  3. 일관된 생성이후의 모든 계획·코드·답변이 그 지침을 기준으로 생성되어 프로젝트 단위로 결과가 통일된다.

#5한 줄 요약

프로젝트 단위 지침 파일 하나로 에이전트의 아키텍처 규칙과 개발 취향을 주입해 일관된 결과를 강제하는 것

#1문제 상황

대화가 길어지면 에이전트가 처리해야 하는 컨텍스트(대화 이력 전체)가 계속 쌓인다. 기존 방식은 오래된 메시지를 그대로 유지하거나 반대로 너무 많이 잘라내는 식이었는데, 전자는 컨텍스트가 비대해져 처리 속도가 느려지고 비용이 커지며, 후자는 중요한 합의나 결정이 사라져 에이전트가 같은 질문을 반복하거나 앞선 결정과 어긋난 결과를 낸다.

#2핵심 질문

길어진 대화가 쌓은 정보를 잃지 않으면서도 컨텍스트를 다시 가볍게 만들 수 있는 방법은 무엇인가?

#3동작 예시

에이전트가 1시간 동안 대화하며 100개의 메시지를 교환했다고 하자. 이 상태에서 컴팩션(대화 요약 압축)이 실행되면, 100개 메시지의 핵심 내용 — 정한 목표, 확정한 결정, 진행 중인 작업 상태 — 을 몇 개의 요약 메시지로 압축하고 나머지 원문을 정리한다. 에이전트는 이후 요약 메시지로 작업을 이어가므로 정보는 남고 컨텍스트는 줄어든다.

#4동작 과정

  1. 비대화 감지컨텍스트가 설정한 한계에 가까워지면 시스템이 컴팩션 조건을 확인한다.
  2. 요약 압축기존 대화를 읽고 목표·결정·진행 상태 같은 핵심만 뽑아 짧은 요약 메시지로 재구성한다.
  3. 정리 후 재개원문 대신 요약을 새 컨텍스트로 삼아 에이전트가 작업을 계속하고, 이후 대화 흐름도 정돈된 상태로 유지된다.

쌓인 컨텍스트를 핵심 요약으로 압축해 정보 손실 없이 상태를 유지하는 가비지 컬렉션

가드레일과 인간 검토로 에이전트의 자율적 실행 수준을 정하고 위험 지점에서 사람에게 승인을 요청하는 제어 구조.

#1문제 상황

에이전트에게 자율성을 주지 않으면 모든 단계에서 사람이 개입해 자동화의 의미가 줄고, 반대로 모든 것을 맡기면 잘못된 도구 실행이나 예상 밖의 부작용을 사람이 알지 못한 채 지나간다. 기존 방식은 자동화를 켜거나 끄는 이분법이라서, 일은 자동으로 하고 위험한 순간만 사람이 확인하는 중간 지점을 설정할 수 없었다.

#2핵심 질문

에이전트가 스스로 일을 진행하면서도 위험한 지점에서만 사람의 승인을 받게 하려면 어떻게 해야 하는가?

#3동작 예시

에이전트가 개발 서버에 배포하는 워크플로를 돌릴 때, 가드레일(제약 규칙)에 따라 코드 변경 같은 일반 작업은 자동으로 실행하지만 "프로덕션 서버 접근"은 실행 전에 사람의 승인을 요청하도록 설정한다. 에이전트는 승인 요청을 던지고 사람이 확인 버튼을 누르기 전까지 그 단계를 진행하지 않는다.

#4동작 과정

  1. 자율 수준 설정가드레일로 어떤 작업은 자동 실행, 어떤 작업은 승인 필요로 분류해 자율성 수준을 정한다.
  2. 실행 중 판단에이전트가 작업을 진행하며 각 단계가 승인 필요 분류에 걸리는지 확인한다.
  3. 승인 후 계속승인 필요 단계에서는 사람의 허가를 기다렸다가 승인이 오면 이어서 실행하고, 거부되면 해당 동작을 중단한다.

가드레일과 승인 지점으로 에이전트 자율성의 수준을 정해 위험한 순간에만 사람이 개입하는 제어 구조

#1문제 상황

한 번 잘 돌아간 워크플로를 다시 쓰려면 사람이 그 과정을 기억해서 요청문을 처음부터 다시 조립한다. 이 방식은 같은 작업을 반복할 때마다 동일한 시간과 노력이 들고, 처음 성공했을 때의 프롬프트 구성·도구 사용 순서·중간 판단이 기록으로 남지 않아 성공 조건이 팀 내 경험으로만 전해진다.

#2핵심 질문

한 번 성공한 워크플로를 기록해 두고 다음에는 버튼 하나로 재현하려면 어떻게 해야 하는가?

#3동작 예시

에이전트와 함께 버그 수정 후 테스트 실행까지 완료한 세션이 있다고 하자. 이 세션의 실행 과정을 "버그 수정"이라는 스킬로 기록하면, 다음에 같은 유형의 버그가 들어왔을 때 사람이 긴 요청문을 새로 쓰는 대신 그 스킬을 호출한다. 에이전트는 기록된 단계 — 원인 파악, 수정, 테스트 — 를 그대로 재생한다.

#4동작 과정

  1. 관찰과 기록에이전트가 작업을 수행하는 과정에서 실행한 도구 호출과 결정을 세션 단위로 저장한다.
  2. 스킬로 변환저장된 실행 흐름을 이름 붙은 재사용 가능한 스킬 형태로 정리한다.
  3. 재생과 개선이후 작업에서 그 스킬을 호출해 같은 흐름을 재현하고, 새로 얻은 교훈을 반영해 스킬을 갱신한다.

#5한 줄 요약
