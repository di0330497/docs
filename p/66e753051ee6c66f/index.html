1부. 컨테이너와 이미지 기초001

컨테이너 이해

가상머신과 비교해 컨테이너(Container)가 가볍고 빨리 뜨는 이유를 설명한다

#1왜 필요한가

예전에는 앱을 서버에 직접 설치했는데, 개발자 PC에서는 되던 앱이 운영 서버에서는 라이브러리 버전이 달라 터지는 일이 흔했다. 이사할 때마다 짐이 안 맞는 상자에 억지로 쑤셔 넣는 셈이었다.

#2비유로 설명

항만 터미널에 규격이 제각각인 자루와 박스가 쌓인다고 상상해보자. 크레인마다 따로 장비가 필요하고 적재도 느리다. 그러다 표준 화물 컨테이너가 등장했다. 크기·잠금장치가 통일되니 어느 크레인·배에서도 똑같이 다룰 수 있고 하역 속도가 빨라졌다. 컨테이너 기술이 앱에 한 일이 바로 이것이다. 앱과 실행 환경을 표준 상자에 함께 포장한다.

#3진짜로는

컨테이너(Container)는 호스트 운영체제의 커널을 공유하면서 프로세스를 격리해 실행하는 방식이다. 가상머신(VM, 물리 서버 위에 가상 하드웨어를 통째로 흉내 내는 기술)이 게스트 OS까지 통째로 띄우는 것과 달리, 컨테이너는 OS 커널 위에서 네임스페이스(격리된 시야)와 cgroup(자원 한도) 같은 커널 기능으로 격리만 한다. 그래서 이미지가 수백 MB 수준으로 가볍고 시작이 초 단위다.

#4비유 ↔ 실제 대응

표준 화물 컨테이너=컨테이너 실행 단위, 통일된 잠금장치=표준 이미지 규격(OCI), 크레인=컨테이너 런타임, 화물 내용물=앱과 라이브러리.

#5비유의 한계

진짜 화물 컨테이너는 텅 빈 강철 상자지만, 소프트웨어 컨테이너는 실행 가능한 파일과 설정을 포함한 살아 있는 실행 환경이라는 점이 다르다.

#6아주 작은 예시

docker run nginx 는 nginx 이미지로 컨테이너 한 개를 띄우라는 뜻이다. run=띄우기, nginx=쓸 설계도 이름이다.

#7흔한 오해

컨테이너가 가상머신보다 보안상 완전히 안전하다고 생각하는 것이다. 커널을 공유하므로 커널 취약점의 영향 범위가 넓을 수 있어 이미지 관리와 권한 최소화가 중요하다.

#8한 줄 요약

컨테이너는 OS 커널을 공유해 가볍고 빠르게 뜨는 표준화된 앱 실행 상자다.

Docker 구조

도커 엔진(Engine)과 데몬(Daemon)이 컨테이너를 띄우는 구조를 설명한다

#1왜 필요한가

컨테이너 개념만 알고 실제 도구가 없으면 매번 격리 환경을 손으로 조립해야 한다. 개발자마다 다른 스크립트를 쓰면 재현이 안 된다.

#2비유로 설명

항만에서 크레인 기사에게 매번 구두로 지시하면 실수가 난다. 그래서 관제실(지시를 받는 곳), 크레인 본체(실제 작업), 설계도 창고가 하나로 묶인 표준 하역 시스템이 생겼다. Docker가 그 시스템이다.

#3진짜로는

Docker 구조의 중심은 도커 데몬(Daemon, 백그라운드에서 컨테이너를 관리하는 상주 프로세스)이다. 사용자가 도커 클라이언트(Client, docker 명령어 도구)로 요청하면 데몬이 이미지 관리, 컨테이너 생성·실행, 네트워크·볼륨을 처리한다. 데몬과 클라이언트는 REST API로 대화하며, 실제 컨테이너 실행은 containerd와 runc 같은 하위 런타임이 맡는다. 도커 엔진(Engine)은 이 전체 묶음을 가리킨다.

#4비유 ↔ 실제 대응

관제실 접수창구=도커 클라이언트, 하역 지휘소=도커 데몬, 크레인 팔=containerd·runc, 설계도 창고=이미지 저장소.

#5비유의 한계

항만 크레인은 물리 장비를 직접 움직이지만, 데몬은 커널 기능을 호출하는 소프트웨어라서 하드웨어를 직접 만지지 않는다.

#6아주 작은 예시

docker ps 는 실행 중인 컨테이너 목록을 보여달라는 뜻이다. ps=행렬 목록 보기, docker stop mybox 는 mybox라는 컨테이너를 정지시킨다.

#7흔한 오해

docker 명령어 자체가 컨테이너를 띄운다고 생각하는 것이다. 실제 작업은 항상 데몬이 하고, 클라이언트는 주문서만 전달한다. 데몬이 죽으면 명령이 안 먹는다.

#8한 줄 요약

Docker는 클라이언트의 주문을 데몬이 받아 하위 런타임으로 컨테이너를 띄우는 구조다.

이미지와 레이어

이미지(Image)와 레이어(Layer)가 쌓여 재사용되는 원리를 설명한다

#1왜 필요한가

앱을 매번 처음부터 통째로 복사하면 용량이 크고 배포가 느리다. OS부터 앱까지 매번 새로 받으면 네트워크도 시간도 낭비다.

#2비유로 설명

항만에서 화물 설계도를 매번 통째로 다시 그리지 않는다. 표준 팔레트 위에 상자를 한 층씩 쌓듯, 기본 틀 위에 추가분만 얹는다. 같은 밑바탕을 쓰는 화물은 밑부분을 공유한다. 이미지 레이어가 exactly 이 방식이다.

#3진짜로는

이미지(Image, 컨테이너를 찍어내는 읽기 전용 틀)는 여러 레이어(Layer, 변경분을 쌓는 얇은 막)의 합이다. Dockerfile의 지시문 한 줄이 레이어 한 개를 만든다. 레이어는 내용이 같으면 캐시(Hash 값으로 식별되는 재사용 저장분)로 공유된다. 컨테이너가 실행될 때는 이미지 위에 쓰기 가능한 얇은 층이 얹히고, 컨테이너 안의 변경은 그 층에만 남는다.

#4비유 ↔ 실제 대응

팔레트 밑판=베이스 이미지, 쌓는 상자 층=각 레이어, 공유 밑판=레이어 캐시, 화물 꺼낼 때 깔개=쓰기 가능 층.

#5비유의 한계

진짜 상자는 위층을 치워도 아래층이 그대로지만, 이미지 레이어는 한 번 쌓이면 수정이 안 되고(불변) 새 레이어로만 덮는다.

#6아주 작은 예시

FROM node:20 은 node 20이 깔린 밑판을 쓰겠다는 뜻이다. FROM=밑판 지정이다.

#7흔한 오해

컨테이너 안 파일을 고치면 이미지가 바뀐다고 생각하는 것이다. 그 변경은 컨테이너의 쓰기 층에만 있고 이미지는 그대로다. 저장하려면 새 이미지로 만들어야 한다.

#8한 줄 요약

도커파일(Dockerfile) 지시문으로 이미지를 만드는 법을 설명한다

#1왜 필요한가

이미지를 손으로 조립하면 과정이 기록에 안 남아 다음 사람이 똑같이 못 만든다. 클릭 몇 번으로 만든 서버가 대표적 예다.

#2비유로 설명

항만 적재 명세서는 "밑판은 A형, 2층에 냉장박스, 문에 자물쇠"처럼 순서대로 적힌다. 누구나 같은 문서를 보면 같은 화물이 나온다. Dockerfile(도커파일, 이미지를 만드는 순서서)이 그 명세서다.

#3진짜로는

Dockerfile은 FROM(기반 이미지), COPY(파일 복사), RUN(실행 명령), CMD(기본 실행 명령) 같은 지시문(Instruction, 한 줄 명령)의 목록이다. docker build가 위에서 아래로 실행하며 레이어를 쌓는다. 자주 바뀌는 내용(앱 코드)은 아래쪽에 두면 캐시가 잘 살아 빌드가 빨라진다. .dockerignore로 불필요한 파일을 빼는 것도 기본이다.

#4비유 ↔ 실제 대응

적재 명세서=Dockerfile, 명세서 한 줄=지시문 한 개, 완성된 묶음=이미지, 조립 크레인=docker build.

#5비유의 한계

화물 명세서는 사람이 읽고 손으로 쌓지만, Dockerfile은 빌드 도구가 자동으로 기계적으로 실행한다는 점이 다르다.

#6아주 작은 예시

FROM node:20 밑판으로 node 20 이미지를 쓴다. COPY . /app 현재 폴더 파일을 /app에 복사한다. CMD ["node", "app.js"] 컨테이너가 뜰 때 app.js를 실행한다.

#7흔한 오해

CMD에 적으면 이미지에 박힌 고정값이라 못 바꾼다고 생각하는 것이다. 실행 시 인자로 덮어쓸 수 있다.

Dockerfile은 이미지를 재현 가능하게 쌓는 순서서다.

컨테이너 실행과 관리

실행(Run)·정지(Stop)·삭제(Remove)로 컨테이너를 다루는 법을 설명한다

#1왜 필요한가

이미지만 있고 띄우고 끄는 법을 모르면 설계도만 있고 배는 못 띄우는 항만과 같다. 테스트하다 남은 좀비 컨테이너가 자원을 먹는 일도 생긴다.

#2비유로 설명

항만에서 화물 묶음마다 출항·대기·폐기 상태판을 붙인다. 뜨는 묶음(run), 잠시 멈춘 묶음(stop), 기록까지 지우는 폐기(remove)가 구분된다. Docker의 run·stop·rm도 같은 상태판이다.

#3진짜로는

실행(Run)은 이미지에서 컨테이너를 만들어 시작시키는 것이고, 정지(Stop)는 프로세스에 종료 신호를 보내 멈추는 것, 삭제(Remove)는 정지된 컨테이너의 기록과 쓰기 층을 지우는 것이다. run은 pull(받기)+create(만들기)+start(시작)를 한 번에 한다. -d(백그라운드), --name(이름 붙이기), -p(포트 연결) 옵션을 붙여 쓴다. 컨테이너는 기본적으로 일회성이라 지우면 안의 변경도 사라진다.

#4비유 ↔ 실제 대응

출항 상태판=실행 중, 대기 상태판=정지, 폐기 도장=삭제, 화물 식별 꼬리표=컨테이너 이름.

#5비유의 한계

화물은 멈춰 있어도 내용물이 남지만, 컨테이너를 삭제하면 쓰기 층 변경분은 기본적으로 함께 사라진다.

#6아주 작은 예시

docker run -d --name web -p 8080:80 nginx 는 nginx를 백그라운드(-d)로 web이라는 이름으로 띄우고 PC의 8080번을 컨테이너 80번에 연결(-p)한다는 뜻이다.

#7흔한 오해

stop하면 데이터가 다 지워진다고 생각하는 것이다. stop은 멈춤일 뿐이고, rm을 해야 기록이 지워진다.

#8한 줄 요약

꺼져도 남는 저장소인 볼륨(Volume)의 쓰임을 설명한다

#1왜 필요한가

컨테이너를 지우면 안의 데이터가 함께 사라진다. DB 컨테이너를 업데이트했다가 자료가 날아가면 큰일이다.

#2비유로 설명

#3진짜로는

볼륨(Volume, 컨테이너 밖에 있는 오래가는 저장 공간)은 컨테이너의 쓰기 층과 분리된 저장소다. 컨테이너를 지워도 볼륨 내용은 남고 다른 컨테이너에 붙일 수 있다. 도커가 관리하는 이름 있는 볼륨과 호스트 폴더를 직접 연결하는 바인드 마운트(Bind Mount, 호스트 경로를 그대로 꽂는 방식)가 있다. DB처럼 상태가 있는 용도에 쓴다.

#4비유 ↔ 실제 대응

오가는 배=컨테이너, 항구 창고=볼륨, 창고 대여증=볼륨 이름, 창고 문 연결=마운트.

#5비유의 한계

항구 창고는 사람이 걸어 들어가지만, 볼륨은 컨테이너 안의 특정 경로에 가려진 채 붙는다는 점이 다르다.

#6아주 작은 예시

#7흔한 오해

#8한 줄 요약

컨테이너끼리 대화하는 네트워크(Network) 기초를 설명한다

#1왜 필요한가

#2비유로 설명

항만 안에서 트럭끼리 무전기로 부를 때 차량 번호가 아니라 "냉동 3호" 같은 이름으로 부른다. 배가 바뀌어도 이름은 그대로라 찾을 수 있다. 컨테이너 네트워크도 이름으로 찾는 구조다.

#3진짜로는

컨테이너 네트워크(Network, 컨테이너끼리 통신하는 가상 길)는 기본적으로 도커가 만든 가상 다리(브리지)를 통해 연결된다. 같은 네트워크에 붙은 컨테이너는 컨테이너 이름으로 서로 찾을 수 있다(내장 DNS가 이름→IP를 풀어준다). 외부 공개는 포트 매핑(-p)으로 한다. 격리가 필요하면 네트워크를 나눠 서로 못 보게 한다.

#4비유 ↔ 실제 대응

항만 내 무전기망=컨테이너 네트워크, 별명 호출=이름 기반 DNS, 바깥 게이트=포트 매핑, 분리된 부두=별도 네트워크.

#5비유의 한계

무전기는 사람이 알아듣지만, 컨테이너 통신은 정해진 포트와 규약(TCP/UDP)이 맞아야 한다는 점이 다르다.

#6아주 작은 예시

#7흔한 오해

#8한 줄 요약

#2비유로 설명

#3진짜로는

컨테이너 로그(Logs, 표준 출력·표준 에러로 나온 글)는 앱이 표준 출력(stdout)과 표준 에러(stderr)에 찍은 내용이 도커에 의해 모인 것이다. docker logs로 본다. 파일에 직접 쓰는 로그는 컨테이너를 지우면 사라지므로 표준 출력으로 내보내는 것이 원칙(12-Factor 방식)이다. 이 로그가 나중에 CloudWatch 같은 곳으로 모이는 출발점이 된다.

#4비유 ↔ 실제 대응

배의 항해 일지=표준 출력 로그, 관제탑 기록실=로그 수집기, 배에 타서 보기=컨테이너 접속, 무전 녹취=docker logs.

#5비유의 한계

항해 일지는 사람이 정리하지만, 컨테이너 로그는 앱이 찍은 그대로 쌓여 양이 많고 정리가 안 돼 있다.

#6아주 작은 예시

#7흔한 오해

레지스트리 이해

이미지를 보관하는 창고인 레지스트리(Registry) 역할을 설명한다

#1왜 필요한가

만든 이미지를 USB로 돌리면 버전이 꼬이고 누가 최신인지 모른다. 서버마다 다른 이미지를 쓰면 장애 원인이 된다.

#3진짜로는

레지스트리(Registry, 이미지를 저장·배포하는 창고 서버)는 이미지를 이름:태그(Tag, 버전 꼬리표) 형태로 보관한다. push(올리기)와 pull(받기)로 주고받는다. 공개 창고(Docker Hub)와 사설 창고(ECR 등)가 있다. 같은 태그라도 내용은 달라질 수 있어 중요한 배포에는 고유 식별자(digest)를 쓰기도 한다.

#4비유 ↔ 실제 대응

설계도 창고=레지스트리, 설계도 번호=이미지 태그, 창고에 맡기기=push, 창고에서 꺼내기=pull.

#5비유의 한계

진짜 창고는 설계도를 복사해 주지만, 레지스트리는 레이어 단위로 필요한 조각만 주고받는다는 점이 다르다.

#6아주 작은 예시

docker push myapp:v1 은 myapp의 v1판을 창고에 올린다는 뜻이다. push=올리기, v1=버전 꼬리표다.

#7흔한 오해

latest 태그가 항상 최신 안전한 버전이라고 생각하는 것이다. latest는 그냥 이름일 뿐 덮어씌워질 수 있어 운영에서는 고정 태그가 안전하다.

AWS 전용 창고인 ECR(Elastic Container Registry)에 이미지를 올리는 법을 설명한다

#1왜 필요한가

외부 공개 창고에 회사 이미지를 올리면 코드와 비밀이 샐 수 있다. 사내망에서 빠르고 권한 있게 쓸 창고가 필요하다.

#2비유로 설명

항만 회사가 외부 공용 창고 대신 자기 부두 안에 자물쇠 달린 전용 창고를 짓는다. 출입증 있는 직원만 드나들고 요금도 자기 회사 체계로 낸다. ECR이 그 전용 창고다.

#3진짜로는

ECR(Elastic Container Registry, AWS가 관리하는 사설 이미지 창고)은 리포지토리(Repository, 이미지 종류별 보관함) 단위로 이미지를 보관한다. AWS IAM 권한으로 push·pull을 통제하고, 같은 리전 안에서는 빠르고 안정적으로 받을 수 있다. aws ecr get-login-password 로 로그인한 뒤 docker push·pull을 쓴다. 이미지는 리전별 주소(계정ID.dkr.ecr.리전.amazonaws.com/이름)로 구분된다.

#4비유 ↔ 실제 대응

전용 창고 건물=ECR, 품목별 선반=리포지토리, 출입증 검사=IAM 인증, 창고 주소판=레지스트리 URI.

#5비유의 한계

진짜 창고는 물건을 직접 들고 가지만, ECR은 네트워크로 레이어를 전송하고 보관료·전송료를 낸다.

#6아주 작은 예시

aws ecr create-repository --repository-name myapp 은 myapp 보관함을 만든다는 뜻이다. create-repository=보관함 만들기다.

#7흔한 오해

ECR에 올리면 자동으로 ECS에서 쓸 수 있다고 생각하는 것이다. ECS 쪽 실행 역할에 ECR 읽기 권한을 따로 줘야 한다.

#8한 줄 요약

ECR은 IAM으로 잠그고 리전 안에서 쓰는 AWS 전용 이미지 창고다.

ECS란

오케스트레이션(Orchestration) 관점에서 ECS(Elastic Container Service)가 하는 일을 설명한다

#1왜 필요한가

컨테이너가 수십 개가 되면 사람이 손으로 띄우고 죽은 것을 살리는 일을 못 한다. 서버가 죽으면 그 위 컨테이너도 함께 죽는다.

#2비유로 설명

항만에 배가 수백 척이면 항만 회사가 운항 스케줄을 짠다. 비는 자리 메우기, 고장 배 교체, 정기 노선 유지를 회사가 알아서 한다. ECS가 그 항만 회사다.

#3진짜로는

ECS(Elastic Container Service, AWS의 컨테이너 지휘 서비스)는 오케스트레이션(Orchestration, 여러 컨테이너의 배치·복구·확장을 자동 지휘하는 일)을 대신 해준다. 원하는 상태(몇 개를 띄울지)를 선언하면 ECS가 빈 자리에 컨테이너를 배치하고, 죽으면 다시 띄우고, 부하에 따라 늘린다. 서버 관리를 AWS에 맡기는 Fargate 방식과 직접 서버를 굴리는 EC2 방식이 있다.

#4비유 ↔ 실제 대응

항만 회사=ECS 제어부, 운항 스케줄=원하는 상태, 빈 선석=용량, 고장 배 교체=자동 복구.

#5비유의 한계

항만 회사는 사람과 협상하지만, ECS는 선언된 숫자와 규칙대로 기계적으로 움직인다.

#6아주 작은 예시

서비스에서 desiredCount=3 은 같은 화물 묶음을 항상 3개 유지하라는 뜻이다. desiredCount=원하는 개수다.

#7흔한 오해

ECS가 앱 코드를 고쳐준다고 생각하는 것이다. ECS는 배치·유지만 하고 앱 로직은 이미지에 담겨 있어야 한다.

#8한 줄 요약

ECS는 원하는 개수를 선언하면 배치와 복구를 대신하는 지휘자다.

ECS 핵심 4요소

클러스터(Cluster)·작업 정의·태스크·서비스 관계를 한 그림으로 설명한다

#1왜 필요한가

클러스터·작업 정의·태스크·서비스가 뒤섞이면 설정을 어디에 적어야 할지 모른다. 이미지 지정과 개수 유지를 한 곳에 몰아넣어 혼란이 생긴다.

#2비유로 설명

항만에 부지(항만 전체), 적재 명세서(화물 설계), 실제 출항 묶음(오늘 뜨는 배), 정기 노선(매일 뜨는 항로)이 있다. 부지에 명세서대로 묶음을 띄우고 노선이 묶음을 유지한다. ECS 4요소가 똑같다.

#3진짜로는

클러스터(Cluster, 일터 묶음)는 태스크가 뛰노는 논리적 일터다. 작업 정의(Task Definition, 설계도)는 이미지·CPU·메모리·환경변수를 적은 문서다. 태스크(Task, 실행 단위)는 작업 정의대로 실제 뜬 컨테이너 묶음이다. 서비스(Service, 개수 지킴이)는 태스크를 원하는 개수만큼 유지하는 관리자다. 관계는 클러스터 안에 서비스가 있고 서비스가 태스크를 낳고 태스크는 작업 정의를 따른다.

#4비유 ↔ 실제 대응

항만 부지=클러스터, 적재 명세서=작업 정의, 출항 묶음=태스크, 정기 노선=서비스.

#5비유의 한계

항만 노선은 사람이 운항하지만, 서비스는 숫자가 모자라면 즉시 새 태스크를 기계적으로 띄운다.

#6아주 작은 예시

작업 정의에 image: nginx, memory: 512 를 적으면 nginx를 메모리 512MB로 띄우는 설계도가 된다.

#7흔한 오해

태스크와 서비스를 같은 것으로 보는 것이다. 태스크는 한 번 뜬 실체이고 서비스는 그 개수를 지키는 관리자다.

#8한 줄 요약

작업 정의대로 태스크를 띄우고 서비스가 개수를 지키는 일터가 클러스터다.

시작 유형 고르기

EC2·Fargate·외부 시작 유형(Launch Type)의 차이를 설명한다

#1왜 필요한가

서버를 직접 굴릴지 말지 정하지 않으면 요금과 운영 부담 계산이 안 된다. 트래픽이 들쭉날쭉한데 서버를 사두면 돈이 샌다.

#2비유로 설명

항만이 화물 운송을 외주 운송사에 맡길지(Fargate), 자기 트럭 부대를 둘지(EC2), 먼 섬 선착장을 붙일지(외부)에 따라 비용과 손이 다르다. 시작 유형(Launch Type, 태스크를 어디에 띄울지 정하는 선택지)이 그 결정이다.

#3진짜로는

EC2 시작 유형은 직접 EC2 인스턴스를 굴리고 ECS 에이전트를 올려 태스크를 얹는 방식이다. 제어 폭이 넓지만 패치·확장을 직접 한다. Fargate는 서버 없이 CPU·메모리만 지정하면 AWS가 자리를 내주는 서버리스 방식이다. 외부(External)는 온프레미스 기계를 ECS에 붙이는 방식(ECS Anywhere)이다. 짧고 변동 큰 일은 Fargate, 오래 돌며 튜닝이 필요하면 EC2가 흔한 선택이다.

#4비유 ↔ 실제 대응

외주 운송사=Fargate, 자가 트럭 부대=EC2 시작 유형, 먼 섬 선착장=외부 유형, 배차표=용량 계획.

#5비유의 한계

외주 트럭도 실물은 있지만, Fargate는 서버를 볼 수도 만질 수도 없이 규격만 지정한다.

#6아주 작은 예시

작업 정의의 launchType: FARGATE 는 서버 지정 없이 AWS에 맡긴다는 뜻이다.

#7흔한 오해

Fargate가 항상 싸다고 생각하는 것이다. 상시 가동 대용량은 EC2가 쌀 수 있어 계산이 필요하다.

Fargate 이해

서버 관리 없는 매니지드 실행인 Fargate(Fargate)의 원리를 설명한다

#1왜 필요한가

서버 패치·용량 계산에 시간을 쓰면 정작 앱 개발을 못 한다. 트래픽이 튈 때마다 서버를 사는 것도 느리다.

#2비유로 설명

항만이 외주 운송사에 "냉동 2톤짜리 세 대"라고만 말하면 차종·기사·정비는 운송사가 알아서 한다. 쓰는 만큼만 낸다. Fargate(Fargate, 서버 관리 없는 실행 방식)가 그 외주 계약이다.

#3진짜로는

Fargate는 CPU와 메모리 조합(예: 0.25 vCPU + 0.5GB 같은 규격, 값은 바뀔 수 있음)만 지정하면 AWS가 격리된 공간에 태스크를 띄워준다. 패치·확장·격리를 AWS가 맡고 사용자는 vCPU·메모리 사용량과 비례해 낸다. 태스크마다 전용 커널 격리가 되어 이웃 간섭이 적다. 서버 접속(SSH)이 필요 없는 구조다.

#4비유 ↔ 실제 대응

외주 계약서=작업 정의의 CPU·메모리 지정, 운송사 차고=AWS 용량 풀, 운행료=vCPU·메모리 요금, 기사 교체=자동 패치.

#5비유의 한계

외주 트럭은 기사와 대화할 수 있지만, Fargate 태스크의 밑바탕 서버에는 접속할 수 없다.

#6아주 작은 예시

cpu: "256", memory: "512" 는 0.25 vCPU와 512MB짜리 자리를 달라는 뜻이다.

#7흔한 오해

Fargate에서는 아무 제약이 없다고 생각하는 것이다. 저장소·실행 시간·네트워크 모드(awsvpc 필수) 같은 규격 제약이 있다.

#8한 줄 요약

Fargate는 CPU·메모리만 말하면 서버 걱정 없이 띄워주는 외주 실행이다.

EC2 실행 이해

직접 서버를 굴리는 EC2 실행(EC2 Launch Type)의 원리를 설명한다

#1왜 필요한가

특수 하드웨어(GPU)나 고정 IP·로컬 디스크가 필요하면 외주 규격에 안 맞는다. 비용을 깎기 위해 예약 서버를 써야 할 때도 있다.

#2비유로 설명

항만이 자기 트럭 부대를 두면 차종 개조·야간 대기·연료 공동구매가 자유롭다. 대신 정비·기사 관리는 자기 몫이다. EC2 실행(EC2 Launch Type, 직접 서버 위에 태스크를 얹는 방식)이 그렇다.

#3진짜로는

EC2 실행은 사용자가 EC2 인스턴스를 만들고 ECS 에이전트(Agent, 클러스터와 연락하는 상주 프로그램)가 깔린 상태로 클러스터에 등록한다. 태스크는 남은 CPU·메모리·포트에 배치된다. 인스턴스 종류 선택, AMI 패치, 오토스케일링은 사용자가 한다. 예약·스팟 요금으로 아낄 수 있고 특정 포트·볼륨 제어가 자유롭다.

#4비유 ↔ 실제 대응

자가 트럭=EC2 인스턴스, 배차 연락병=ECS 에이전트, 차고 확장=Auto Scaling, 연료 할인=예약·스팟 요금.

#5비유의 한계

트럭은 한 번에 한 짐이지만, EC2 한 대에는 여러 태스크가 나눠 탈 수 있다.

#6아주 작은 예시

에이전트가 살아 있으면 ECS 콘솔의 컨테이너 인스턴스 목록에 서버가 뜬다. 안 뜨면 에이전트·IAM 역할을 의심한다.

#7흔한 오해

EC2면 Fargate 설정을 그대로 쓰면 된다고 생각하는 것이다. 네트워크 모드·배치 제약 등 일부 설정이 다르다.

#8한 줄 요약

EC2 실행은 서버를 직접 굴리는 대신 자유와 할인을 얻는 방식이다.

ECS Anywhere 맛보기

온프레미스 서버를 붙이는 ECS Anywhere(Anywhere)의 쓰임을 설명한다

#1왜 필요한가

공장·매장 서버처럼 AWS 바깥에 있는 기계를 클라우드 방식으로 다루고 싶을 때가 있다. 다 옮기기에는 회선·법규가 막힌다.

#2비유로 설명

#2비유로 설명

#3진짜로는

#5비유의 한계

#6아주 작은 예시

같은 1vCPU라도 상시 가동이면 EC2 예약이, 하루 몇 시간만이면 Fargate가 쌀 수 있다. 조건별로 계산한다.

ECS와 EKS(Kubernetes)·Lambda(Functions)의 고르는 기준을 설명한다

#1왜 필요한가

#2비유로 설명

항만 회사의 정기 노선(ECS), 전 세계 선사 연합 표준(EKS, Kubernetes 방식), 택배 오토바이(Lambda, 함수 실행)가 있다. 매일 같은 항로면 정기 노선, 연합 규격이 필요하면 연합, 가벼운 심부름은 오토바이다.

#3진짜로는

ECS는 AWS 밀착 단순 운영이 강점이다. EKS(Kubernetes, 컨테이너 표준 지휘 체계)는 이식성과 생태계가 강하지만 학습·운영 부담이 크다. Lambda(Functions, 요청당 실행되는 조각 코드)는 서버가 전혀 없고 짧은 일에 싸지만 실행 시간·상태 유지에 제약이 있다. 오래 도는 웹·API는 ECS, 표준·멀티클라우드면 EKS, 간헐적 작업이면 Lambda가 흔한 답이다.

#4비유 ↔ 실제 대응

정기 노선=ECS 서비스, 연합 규격=EKS, 오토바이 심부름=Lambda 함수, 항로표=아키텍처 결정.

#5비유의 한계

진짜 운송 수단은 바꿔 타기 어렵지만, 셋은 같은 이미지·코드를 나눠 쓰는 혼합도 흔하다.

#6아주 작은 예시

하루 몇 번 도는 이미지 변환이면 Lambda+이벤트가, 24시간 API면 ECS 서비스가 어울린다.

#7흔한 오해

#8한 줄 요약

격리된 네트워크 땅인 VPC(Virtual Private Cloud)를 설명한다

#3진짜로는

VPC는 리전 안에 만드는 비공개 주소 공간(예: 10.0.0.0/16 같은 범위, 값은 예시)이다. 안에 서브넷을 나누고 라우팅·방화벽을 건다. ECS 태스크는 VPC 안 서브넷에서 IP를 받고 보안 그룹 통제를 받는다. 리전마다 기본 VPC가 있지만 실무에서는 용도별 VPC를 새로 만든다.

#4비유 ↔ 실제 대응

울타리 친 부지=VPC, 부지 주소 체계=CIDR 범위, 구역 나누기=서브넷, 정문 경비=보안 그룹.

#5비유의 한계

서브넷(Subnet, VPC를 자른 작은 구역)은 퍼블릭(인터넷 길 있음)과 프라이빗(인터넷 길 없음)으로 나뉜다. ECS 태스크는 보통 프라이빗에 두고 로드밸런서만 퍼블릭에 둔다. 가용영역(AZ, 독립 전원·망의 건물군)은 리전 안 2곳 이상에 나눠야 한 곳 장애를 버틴다.

#4비유 ↔ 실제 대응

#5비유의 한계

진짜 부두는 배가 직접 오가지만, 서브넷 사이 이동은 라우팅 규칙을 따른다.

보안 그룹과 NACL

방화벽인 보안 그룹(Security Group)의 허용 규칙을 설명한다

#1왜 필요한가

문을 다 열어두면 누구나 DB에 붙는다. 반대로 다 닫으면 앱도 안 돈다. 허용 목록이 필요하다.

#2비유로 설명

항만 정문에 "냉동창고는 3번 게이트에서만" 같은 출입판을 붙인다. 특정 문·특정 상대만 통과다. 보안 그룹(Security Group, 가상 방화벽)이 그 출입판이다.

#3진짜로는

보안 그룹은 인스턴스·태스크에 붙는 허용 전용 방화벽이다. 인바운드(들어오는 길)와 아웃바운드(나가는 길)를 포트·상대별로 적는다. 기본은 다 막고 적힌 것만 연다. NACL(서브넷 단위 필터)은 서브넷 경계의 1차 검문으로 허용·거부를 함께 적는다. 실무는 보안 그룹을 주로 쓰고 NACL은 기본으로 둔다.

#4비유 ↔ 실제 대응

출입판=보안 그룹 규칙, 정문 경비=보안 그룹, 외곽 검문소=NACL, 통행증=포트·프로토콜 조건.

#5비유의 한계

진짜 경비는 사람을 기억하지만, 보안 그룹은 상태를 기억하는 Stateful이라 나가는 답신은 자동 허용된다.

#6아주 작은 예시

#7흔한 오해

#8한 줄 요약

라우팅과 NAT

라우트 테이블(Route Table)과 NAT 게이트웨이(Gateway)의 길을 설명한다

#1왜 필요한가

#3진짜로는

라우트 테이블(Route Table, 목적지별 길 안내판)은 서브넷마다 붙어 패킷의 다음 목적지를 정한다. NAT 게이트웨이(Gateway, 안→밖 전용 대리문)는 프라이빗 서브넷의 태스크가 바깥(ECR·패키지)을 부를 때 쓴다. 바깥→안은 못 들어온다. 인바운드는 로드밸런서가 맡는다.

#4비유 ↔ 실제 대응

길 안내판=라우트 테이블, 대리 수령 창구=NAT 게이트웨이, 정문=인터넷 게이트웨이, 창구 이용료=NAT 요금.

#5비유의 한계

진짜 창구는 사람이 물건을 들고 오지만, NAT는 주소만 바꿔주는 통과 장치다.

#6아주 작은 예시

#7흔한 오해

NAT가 있으면 바깥에서 안으로 들어올 수 있다고 생각하는 것이다. NAT는 안→밖 전용이다.

#8한 줄 요약

취약점을 거르는 이미지 스캔(Scanning) 설정을 설명한다

#1왜 필요한가

남이 만든 밑판에 구멍이 있으면 그대로 배포된다. 터진 뒤에 알면 늦다.

#2비유로 설명

창고에 들어오는 화물을 X-ray로 훑는다. 위험물 표시가 뜨면 반입을 막는다. 이미지 스캔(Scanning, 알려진 취약점 검사)이 그 검색대다.

#3진짜로는

ECR 스캔은 이미지의 OS·라이브러리에서 알려진 취약점(CVE)을 찾아 심각도(Critical·High 등)로 알려준다. push 때 자동 스캔을 켤 수 있다. 결과가 나쁘면 배포를 멈추는 게 원칙이다. 스캔은 알려진 병만 찾으니 최신 밑판 유지와 함께 쓴다.

#4비유 ↔ 실제 대응

X-ray 검색대=이미지 스캔, 위험물 표시=심각도 등급, 반입 금지=배포 차단, 새 포장=밑판 업데이트.

#5비유의 한계

진짜 X-ray는 실물을 보지만, 스캔은 목록 대조라 모르는 병은 못 찾는다.

#6아주 작은 예시

scanOnPush=true 는 올릴 때마다 자동 검사한다는 뜻이다.

#7흔한 오해

스캔 통과면 안전하다고 생각하는 것이다. 알려진 취약점만 본 것이니 최소 권한·업데이트가 함께 가야 한다.

#8한 줄 요약

이미지 스캔은 알려진 구멍을 미리 찾는 검색대다.

한국 망분리 기초

망분리망(Isolated Network)에서 엔드포인트로 이미지를 받는 발상을 설명한다

#1왜 필요한가

금융·공공 망분리망(Isolated Network, 인터넷 차단망)에서는 docker pull이 안 된다. 바깥에서 바로 받으려 하면 보안 심사에서 막힌다.

#2비유로 설명

외딴 섬 항만에 화물을 넣을 때 본토에서 검역·소독을 마친 것만 반출입 절차로 들인다. 그날그날 바로 사들이는 방식이 안 된다. 망분리 대응이 같다.

#3진짜로는

망분리망에서는 인터넷 호출을 막고 VPC 엔드포인트로 AWS 안 통로만 쓴다. 이미지는 바깥에서 스캔·승인 후 반입용 저장소로 옮겨(에어갭 반입) 쓴다. NAT·외부 레지스트리 접근은 원칙적으로 막는다. 절차가 길어 이미지·태그 관리가 더 엄격해진다.

#4비유 ↔ 실제 대응

외딴 섬=망분리 VPC, 검역소=반출입 심사, 소독필 화물=승인된 이미지, 전용선=엔드포인트.

#5비유의 한계

진짜 섬은 배가 가지만, 망분리 반입은 매체·전용 파이프라인 같은 정해진 길로만 간다.

#6아주 작은 예시

#7흔한 오해

망분리에서도 NAT만 열면 된다고 생각하는 것이다. 정책상 안 되는 경우가 많아 엔드포인트·반입이 정답이다.

작업·컨테이너 단위 CPU·메모리(Resource) 배분을 설명한다

#1왜 필요한가

#2비유로 설명

#3진짜로는

#4비유 ↔ 실제 대응

바닥 면적=CPU, 높이=메모리, 규격표=Fargate 조합표, 문 안 닫힘=OOM 종료.

#5비유의 한계

진짜 상자는 크기가 고정되지만, CPU는 남으면 나눠 쓰고 모자라면 기다리는 유연함이 있다.

#3진짜로는

검사소=443 리스너, 신분증=인증서, 대행=ACM 갱신.

#5비유의 한계

검사소는 사람이 보지만 TLS는 수학으로 증명한다.

#6아주 작은 예시

#2비유로 설명

옆칸(Sidecar, 본칸 돕는 작은 칸) 직원이 대형 창고(S3, Simple Storage Service, 큰 물건 창고)에 다녀온다. 본칸은 일만 한다.

#4비유 ↔ 실제 대응

대형 창고=S3, 심부름꾼=사이드카, 심부름 목록=작업 역할 권한.

#5비유의 한계

심부름은 사람이 뛰지만 사이드카는 API로 오간다.

#6아주 작은 예시

#4비유 ↔ 실제 대응

단골 수첩=세션·상태, 사무동=외부 저장소, 배 갈아타기=태스크 교체.
