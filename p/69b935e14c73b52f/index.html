1SQS의 위치와 메시지 수명주기01-01

분산 시스템을 잇는 큐의 역할

분산 시스템 구성 요소 사이에서 메시지를 잠시 저장했다가 전달해 서로의 결합도를 낮추는 완전관리형 메시지 큐 서비스

1상대의 출발점 확인

여러 프로그램이 서로 통신할 때, 보통 한 프로그램이 다른 프로그램을 직접 호출한다. 주문 처리 서비스가 결제 서비스를 직접 부르고, 결제 서비스가 재고 서비스를 직접 부르는 방식이다. 이렇게 직접 연결하면 상대가 느리거나 잠시 멈추면 호출한 쪽도 함께 기다려야 하고, 상대가 죽어 있으면 요청이 그대로 실패한다. 프로그램 개수가 늘어나고 서로의 장애가 전파될수록 시스템 전체가 불안정해진다. 게다가 각 프로그램이 처리할 수 있는 속도가 다르기 때문에, 빠른 쪽이 느린 쪽을 기다리느라 전체 성능이 느린 구성 요소에 맞춰진다.

2질문 제기

프로그램들이 서로 직접 붙어 있지 않아도, 누군가의 장애나 느린 처리 속도에 흔들리지 않게 메시지를 안전하게 주고받으려면 어떻게 해야 할까?

3구조적 핵심 예시

중간에 큐(queue, 줄)라는 저장 공간을 하나 두는 것이 해법이다. 주문 처리 서비스는 결제 서비스를 직접 부르는 대신 "결제 요청"이라는 메시지를 큐에 넣고 즉시 자기 일로 돌아간다. 결제 서비스는 자기 속도에 맞춰 큐에서 메시지를 하나씩 꺼내 처리한다. 결제 서비스가 잠시 멈춰 있어도 메시지는 큐에 그대로 보관되어 유실되지 않고, 주문 처리 서비스는 기다리지 않는다.

4단계별 동작 과정

  1. 생산자가 메시지를 보낸다보내는 쪽 프로그램이 큐에 메시지를 넣는다. 이 시점에 메시지는 큐에 저장되므로 보내는 쪽은 바로 다음 작업을 진행할 수 있다.
  2. 소비자가 메시지를 가져간다받는 쪽 프로그램이 큐에서 메시지를 꺼내 처리한다. 소비자는 자기 여유에 맞춰 가져가므로 서로의 속도 차이가 문제 되지 않는다.
  3. 처리가 끝나면 삭제한다처리가 완료된 메시지를 큐에서 지워야 다음에 다시 꺼내지 않는다. 이렇게 하면 두 프로그램 모두 각자의 속도로 안정적으로 동작한다.

큐를 단순한 저장소로만 생각하면, 메시지를 넣고 꺼내는 것이 전부라고 오해하기 쉽다. 그런데 실제 운용에서는 메시지가 어떤 상태를 거쳐 사라지는지 정확히 알아야 한다. 넣은 메시지가 왜 소비자에게 보이지 않는지, 같은 메시지가 왜 두 번 보이는지, 그리고 언제 큐에서 완전히 사라지는지 모르면 메시지를 잃거나 중복 처리하는 사고가 난다. 특히 여러 소비자가 동시에 큐에서 메시지를 꺼내는 환경에서는, 누가 그 메시지를 처리 중인지가 명확하지 않으면 같은 메시지를 여러 소비자가 동시에 가져가 버린다.

3구조적 핵심 예시

  2. 수신(receive)소비자가 ReceiveMessage 로 메시지를 가져간다. 이 순간 메시지가 숨겨져서 다른 소비자는 같은 메시지를 가져갈 수 없다.
  3. 삭제(delete)소비자가 처리를 마치고 DeleteMessage 로 메시지를 지워 수명주기가 끝난다. 삭제 전에 실패하면 메시지는 숨김 만료 후 다시 보여 재처리된다.

SQS·SNS·Amazon MQ의 역할 구분

SQS는 소비자가 직접 가져가는 큐, SNS는 구독자에게 밀어 보내는 퍼블리시·서브스크라이브, Amazon MQ는 관리형 브로커 기반의 메시지 서비스

1상대의 출발점 확인

AWS에는 비슷해 보이는 메시지 서비스가 여러 개 있어서 처음 접하면 무엇을 써야 할지 헷갈린다. 메시지를 저장해 주는 SQS, 메시지를 여러 곳에 복사해 보내는 SNS, 기존 메시지 브로커(중개자)를 그대로 옮겨 온 Amazon MQ까지, 이름만 보면 모두 "메시지를 전달하는 것" 같다. 이들을 같은 것으로 취급해 아무거나 고르면, 원하는 전달 방식과 맞지 않아 메시지가 유실되거나 불필요하게 비싼 구성을 쓰게 된다. 세 서비스는 전달 방식이 서로 다르기 때문에 목적에 맞게 골라야 한다.

2질문 제기

메시지를 "한 곳에 쌓아두고 소비자가 가져가는 것"과 "여러 곳에 한 번에 밀어 보내는 것", 그리고 "기존 브로커의 표준 방식을 유지하는 것"은 어떻게 다른 걸까?

3구조적 핵심 예시

세 서비스의 차이는 "누가 메시지를 가져가느냐"에 있다. SQS는 소비자가 큐에서 메시지를 꺼내 가는 방식이라, 보낸 쪽과 받는 쪽이 1:1로 연결된다. SNS는 토픽(주제)에 메시지를 올리면 구독해 둔 여러 대상이 각자 같은 메시지를 받는 방식이라, 1:N 전파에 쓰인다. Amazon MQ는 Apache ActiveMQ 같은 기존 브로커를 AWS에서 관리해 주는 서비스라, 이미 브로커 기반 표준 프로토콜(JMS 등)로 만들어진 시스템을 그대로 옮길 때 사용한다.

4단계별 동작 과정

  1. 전달 대상 결정메시지를 받을 대상이 하나면 SQS, 여러 개면 SNS, 기존 브로커 표준 방식을 써야 하면 Amazon MQ를 고른다.
  2. 전달 방식 선택SQS는 소비자가 직접 꺼내 가고, SNS는 서비스가 구독자에게 밀어 보내며, Amazon MQ는 중앙 브로커가 소비자에게 전달을 조율한다.
  3. 기존 시스템 연동 확인AWS에 새로 짓는 시스템은 SQS나 SNS가 간단하고, 온프레미스(자체 서버)에서 쓰던 브로커 기반 시스템을 옮기는 경우 Amazon MQ가 적합하다.

5본질 요약

SQS는 소비자가 꺼내 가는 큐, SNS는 구독자에게 밀어 보내는 퍼블리시·서브스크라이브, Amazon MQ는 기존 브로커 표준을 유지하는 관리형 서비스로, 메시지 전달 방식과 기존 시스템 호환성에 따라 선택하는 것

표준 큐와 FIFO 큐의 선택 기준

표준 큐는 최대 처리량과 순서 무관 처리를, FIFO 큐는 정확한 순서와 정확히 1회 처리를 보장하므로 애플리케이션의 순서 요구사항으로 큐 유형을 결정한다.

1상대의 출발점 확인

큐를 처음 쓸 때 많은 개발자가 큐 유형을 고민하지 않고 기본값을 그대로 쓴다. 그런데 SQS에는 표준 큐와 FIFO 큐라는 두 가지 유형이 있고, 전달 보장이 근본적으로 다르다. 표준 큐는 처리량이 높고 순서를 보장하지 않으며, FIFO 큐는 순서와 정확히 1회 처리를 보장하지만 처리량에 제약이 있다. 이 차이를 모르고 표준 큐를 썼다가 주문 번호가 뒤바뀌어 오는 문제를 겪거나, FIFO 큐를 썼다가 필요한 처리량이 안 나와 애를 먹는 일이 생긴다. 서비스를 설계할 때 "순서가 중요하냐"는 질문에 답할 수 있어야 한다.

2질문 제기

메시지를 보낸 순서와 중복 처리 여부가 중요한 애플리케이션인가, 아니면 최대 처리량이 더 중요한 애플리케이션인가?

3구조적 핵심 예시

은행의 계좌 입출금 처리 같은 시스템은 순서가 생명이다. "입금" 메시지가 "출금" 메시지보다 늦게 도착하면 잔액 계산이 틀어진다. 이런 경우 FIFO 큐를 써서 메시지가 보내진 순서 그대로 처리되게 한다. 반면 로그 수집처럼 메시지 순서가 크게 상관없고 대량을 빠르게 처리해야 하는 경우에는 표준 큐가 적합하다. 순서 요구사항이 곧 큐 유형 선택의 기준이다.

4단계별 동작 과정

  1. 순서 요구 확인메시지를 보낸 순서대로 소비자가 처리해야 하는지 판단한다. 처리 순서가 결과에 영향을 주면 FIFO, 그렇지 않으면 표준 큐가 후보다.
  2. 중복 허용 확인정확히 1회 처리가 필수인지 확인한다. FIFO는 중복을 제거하고, 표준 큐는 드물게 중복 전달이 일어날 수 있다.
  3. 처리량 확인FIFO 큐는 초당 수백 건 수준의 처리량 제한이 있고, 표준 큐는 무제한에 가까운 처리량을 지원한다. 필요한 처리량이 FIFO 한도를 넘는지 점검한다.

표준 큐는 메시지를 최소 1회 전달하므로 드물게 중복 전달이 발생할 수 있다는 전달 보장을 뜻한다.

1상대의 출발점 확인

메시지 큐를 쓸 때 "메시지가 한 번만 전달될 것"이라고 당연히 생각하기 쉽다. 그런데 표준 큐는 이런 전제가 성립하지 않는다. SQS의 표준 큐는 여러 대의 서버가 메시지를 분산 저장하는 구조라서, 메시지를 꺼내 간 소비자가 처리 완료를 알리기 전에 통신이 끊기면, 같은 메시지가 큐에 다시 나타나 다른 소비자에게 전달될 수 있다. 이 사실을 모르고 "메시지는 반드시 한 번만 처리된다"고 가정하고 코드를 짜면, 결제나 포인트 적립 같은 민감한 처리에서 중복 실행이라는 치명적인 문제가 생긴다.

2질문 제기

표준 큐가 보장하는 것은 "메시지가 반드시 한 번만"이 아니라 무엇인가, 그리고 그 보장 아래에서 중복 처리를 막으려면 어떻게 해야 할까?

3구조적 핵심 예시

표준 큐가 보장하는 것은 "최소 1회 전달(at-least-once)"이다. 메시지는 최소한 한 번은 반드시 전달되지만, 드물게 두 번 이상 전달될 수 있다. 예를 들어 소비자가 메시지를 받아 처리하는 도중 전송이 끊겨 삭제 요청을 못 보내면, SQS는 숨김 시간이 끝난 후 그 메시지를 다시 보여 준다. 이때 처리 로직이 "한 번만 실행된다"고 가정하면 중복 실행이 일어난다. 따라서 소비자 쪽에서 메시지 ID나 업무 키를 기준으로 중복을 걸러내는 처리를 함께 만들어야 한다.

4단계별 동작 과정

  1. 메시지 전달SQS가 메시지를 소비자에게 전달한다. 이때까지는 메시지가 큐에 남아 있고, 소비자가 삭제하지 않으면 다시 전달될 수 있다.
  2. 처리와 삭제 사이의 실패 가능성소비자가 처리를 마친 뒤 삭제 요청이 유실되면, SQS는 메시지가 처리되지 않은 것으로 보고 일정 시간 후 다시 전달한다. 이것이 중복 전달의 원인이다.
  3. 소비자 측 중복 방어소비자는 메시지의 고유 식별자나 업무 키를 저장해 두고, 이미 처리한 키면 건너뛰는 방식으로 같은 메시지의 재처리를 막는다.

FIFO 큐의 개념과 핵심 용어

FIFO 큐는 메시지가 보내진 순서대로 정확히 한 번 처리됨을 보장하는 큐로, 메시지 그룹 ID와 중복 제거 ID가 핵심 개념이다.

1상대의 출발점 확인

표준 큐를 쓰던 기존 방식을 보면, 메시지는 최소 1회 전달된다는 보장만 있고 보낸 순서대로 도착하지 않으며 같은 메시지가 두 번 전달될 수도 있습니다. 그 때문에 주문 처리나 결제처럼 처리 순서가 결과를 바꾸는 작업에서는 소비자(메시지를 꺼내 가는 프로그램)가 순서를 다시 맞추고 중복을 직접 걸러야 했고, 그렇지 않으면 데이터가 어긋나는 문제가 발생했습니다.

2질문 제기

보낸 순서대로 정확히 한 번만 처리되도록 보장하려면 큐가 어떤 방식으로 메시지를 관리해야 하는가?

3구조적 핵심 예시

은행의 이체 요청 메시지들이 한 계좌에 대해 여러 건이 들어올 때, 같은 계좌의 메시지들에는 같은 메시지 그룹 ID(MessageGroupId)를 붙이고 각 메시지에는 중복 제거 ID(MessageDeduplicationId)를 붙입니다. 그러면 큐는 그룹 안에서 메시지를 보낸 순서대로 꺼내 주고, 같은 중복 제거 ID를 가진 메시지는 다시 들어와도 버립니다.

4단계별 동작 과정

  1. 메시지 그룹 ID 부여생산자(메시지를 넣는 프로그램)가 순서를 지켜야 하는 메시지들에 같은 메시지 그룹 ID를 붙여 하나의 그룹으로 묶습니다.
  2. 그룹 단위 순서 보장과 중복 제거 ID 대조큐는 그룹 안에서 메시지를 보낸 순서대로 전달하고, 5분 중복 제거 창 안에 같은 중복 제거 ID가 다시 들어오면 같은 메시지로 보고 폐기합니다.
  3. 소비자 전달소비자가 그룹 순서대로 메시지를 하나씩 받아 처리하고, 처리한 메시지를 큐에서 삭제합니다.

1상대의 출발점 확인

표준 큐에서는 생산자가 보낸 여러 메시지가 도착하는 순서가 뒤섞일 수 있고, 소비자가 어떤 순서로든 꺼내 갑니다. 또 메시지마다 그것을 구분할 수 있는 식별자가 명확하지 않아서, 받은 메시지가 어떤 요청인지, 어느 큐에서 온 것인지 추적하기 어려웠습니다.

2질문 제기

여러 생산자가 보낸 메시지가 뒤섞여도 순서를 지키고 각 메시지를 정확히 구분하려면 큐는 무엇을 기준으로 삼아야 하는가?

3구조적 핵심 예시

4단계별 동작 과정

  2. 그룹 안에서 순서대로 전달큐는 그룹별로 메시지를 보낸 순서대로 전달하고, 서로 다른 그룹의 메시지들만 뒤섞어 전달합니다.
  3. 식별자로 구분각 메시지에 부여된 메시지 식별자(Message ID)와 큐 식별자(큐 URL)로 메시지를 구분하고, 소비자가 받은 메시지를 확인·삭제합니다.

FIFO 큐는 중복 제거 ID와 5분 중복 제거 창을 이용해 메시지가 정확히 한 번 처리되도록 중복 전송을 제거한다.

1상대의 출발점 확인

표준 큐는 최소 1회 전달이라서 네트워크 오류나 타임아웃 때문에 생산자가 같은 메시지를 다시 보내면 소비자는 같은 메시지를 두 번 받을 수 있습니다. 기존 방식에서는 소비자 쪽에서 처리 결과를 저장할 때 이미 처리한 메시지인지 미리 확인하는 멱등(같은 요청을 여러 번 처리해도 결과가 같게 만드는) 로직을 직접 구현해야 했습니다.

2질문 제기

재시도로 같은 메시지가 다시 전송되어도 한 번만 처리되게 하려면 큐가 무엇을 제거해야 하는가?

3구조적 핵심 예시

결제 승인 메시지를 보낼 때 같은 내용의 메시지에는 같은 중복 제거 ID(MessageDeduplicationId)를 붙입니다. 큐는 5분 동안 중복 제거 ID를 기억했다가, 같은 ID의 메시지가 다시 들어오면 처리 대상에 넣지 않고 바로 버립니다. 그래서 소비자는 같은 결제를 두 번 승인하지 않습니다.

4단계별 동작 과정

  1. 중복 제거 ID 부여생산자가 각 메시지에 중복 제거 ID를 붙이고, 생산자 측 중복 제거 기능을 쓰지 않는다면 큐가 메시지 본문의 해시(내용을 고정 길이 값으로 바꾼 것)로 ID를 자동 생성합니다.
  2. 중복 제거 창에서 대조큐는 5분 동안 들어온 중복 제거 ID를 유지하며 새 메시지의 ID와 비교합니다.
  3. 중복 폐기 또는 정상 처리같은 ID가 창 안에 있으면 메시지를 폐기하고, 처음 보는 ID면 소비자에게 전달하여 처리되게 합니다.

  3. 표준에서 FIFO로 전환순서와 중복 제거가 필요한 시점에 표준 큐를 FIFO 큐로 전환하면, 같은 메시지를 유지한 채 FIFO의 순서 보장과 정확히 1회 처리를 사용하게 됩니다.

메시지 순서와 정확히 한 번 처리를 보장하는 FIFO 큐를 만들며, 큐 이름이 반드시 .fifo 로 끝나야 하는 규칙을 다루는 항목.

1상대의 출발점 확인

표준 큐처럼 이름을 아무렇게나 지어 FIFO 큐를 만들려고 하면, SQS는 이름 끝이 .fifo 로 끝나지 않는 큐를 FIFO 큐로 만들어 주지 않아 생성이 거부됩니다. 기존 방식에서는 이름 규칙을 몰라서 무엇이 잘못됐는지 찾느라 시간을 보냈고, 결국 만들어도 표준 큐처럼 동작하는 실수가 있었습니다.

2질문 제기

FIFO 큐가 가진 순서와 중복 제거 기능을 그대로 쓰려면 이름과 구성을 어떻게 정해야 생성이 허용되는가?

3구조적 핵심 예시

"order-queue.fifo"처럼 이름 끝에 반드시 .fifo 를 붙이고, 큐 유형에서 FIFO를 선택한 뒤 생성하면 SQS가 이 큐를 FIFO 큐로 인식합니다. 이후에는 중복 제거 설정을 따로 선택해 같은 내용의 메시지가 중복 전송돼도 걸러집니다.

4단계별 동작 과정

  1. 이름 규칙 적용큐 이름을 .fifo 로 끝나게 지어 FIFO 큐임을 이름만으로도 구분되게 합니다.
  2. 유형과 중복 제거 설정 선택큐 유형으로 FIFO를 선택하고, 중복 제거를 활성화하거나 생산자 측 중복 제거 방식을 정합니다.
  3. 생성 완료와 FIFO 동작 적용큐가 생성된 뒤부터 메시지 그룹 ID 단위 순서 보장과 정확히 1회 처리가 동작합니다.

5본질 요약

큐 이름을 .fifo 로 끝내고 FIFO 유형을 선택해, 순서 보장과 중복 제거가 기본으로 동작하는 큐를 만드는 것

3큐 만들고 관리하기03-03

큐 운영: 편집·메시지 수신·삭제·퍼지

이미 만든 큐를 편집하고, 메시지를 수신·삭제하며, 큐를 비우거나 삭제하는 일상 운영 작업을 다루는 항목.

1상대의 출발점 확인

큐를 한 번 만들면 끝이 아니라, 이후에도 설정을 고치고 메시지가 제대로 쌓이고 처리되는지 확인하고, 불필요해진 큐나 메시지를 정리하는 운영 작업이 계속 필요하다. 기존 방식은 큐 설정을 바꾸려고 콘솔에서 큐를 하나하나 열어 값을 고치고, 메시지를 확인하려고 직접 꺼내 본 뒤 삭제해야 했다. 이 과정은 반복적이고, 실수로 메시지를 지우면 복구할 수 없으며, 큐를 비울 때도 메시지를 일일이 삭제하거나 큐 자체를 없애야 해서 번거롭고 위험했다.

2질문 제기

만들어진 큐를 멈추지 않고 설정을 고치고, 메시지를 안전하게 확인하고 삭제하며, 큐 전체를 한 번에 비우려면 어떻게 해야 할까?

3구조적 핵심 예시

SQS 콘솔에서 큐를 하나 선택하면 편집(Edit), 메시지 송수신(Send and receive messages), 삭제(Delete), 퍼지(Purge) 버튼이 함께 제공된다. 예를 들어 메시지가 계속 쌓여 더 오래 보관하고 싶다면 편집 화면에서 메시지 보존 기간만 바꿔 저장하면 그 자리에서 적용되고, 큐에 쌓인 메시지가 무엇인지 확인하고 싶다면 메시지 송수신 화면에서 메시지를 꺼내 내용을 본 뒤 삭제할 수 있다.

4단계별 동작 과정

  1. 편집(Edit)큐를 선택하고 편집을 누르면 보존 기간, 가시성 타임아웃(메시지가 다른 소비자에게 보이지 않는 시간) 등 파라미터를 수정할 수 있고, 저장하면 새 설정이 즉시 적용된다.
  2. 메시지 수신·삭제메시지 송수신 화면에서 Poll for messages로 메시지를 꺼내 내용을 확인한 뒤 Delete로 삭제한다. 수신된 메시지는 가시성 타임아웃 동안 다른 소비자에게 보이지 않고, 삭제하지 않으면 시간이 지나 다시 보인다.
  3. 삭제·퍼지Delete Queue는 큐 자체를 제거하고, Purge는 큐는 그대로 두고 안에 있는 메시지만 모두 지운다. 퍼지는 되돌릴 수 없고 최대 60초가 걸린다.

5본질 요약

큐를 삭제하지 않고 파라미터를 편집하고, 메시지를 수신·확인·삭제하며, 필요할 때 큐 전체의 메시지를 퍼지하는 운영 동작을 콘솔에서 지원하는 것

큐 파라미터 구성

메시지 보존 기간, 가시성 제한 시간, 폴링 방식, 지연 시간 등 큐 동작을 결정하는 파라미터를 설정하는 항목.

1상대의 출발점 확인

큐를 만들면 메시지 보존 기간 4일, 가시성 타임아웃 30초, 지연 0초 같은 기본값이 그대로 적용된다. 기존 방식은 이 기본값을 놔두고 쓰다 보니 문제가 생겼다. 메시지가 4일 안에 소비되지 않으면 사라져버리고, 소비자가 메시지 하나를 처리하는 데 2분이 걸리는데 타임아웃이 30초라서 처리 중에 같은 메시지가 다른 소비자에게 다시 전달되어 중복 처리되는 일이 벌어졌다.

2질문 제기

큐의 동작을 결정하는 파라미터(보존 기간, 지연, 가시성 타임아웃, 수신 대기 등)를 서비스 요구 사항에 맞게 어떻게 구성할까?

3구조적 핵심 예시

소비자가 메시지 하나를 처리하는 데 평균 2분이 걸리는 서비스라면, 가시성 타임아웃을 기본값 30초에서 2분 이상(예: 150초)으로 올린다. 이렇게 하면 메시지를 받은 소비자가 처리하는 동안 그 메시지가 다른 소비자에게 다시 보이지 않아 중복 처리가 막힌다.

4단계별 동작 과정

  1. 보존 기간 설정큐에 쌓인 메시지를 며칠 동안 보관할지 설정한다. 기본값은 4일이고 1분부터 14일까지 지정할 수 있으며, 기간이 지나면 메시지는 자동으로 삭제된다.
  2. 지연 시간 설정새로 전송된 메시지가 바로 보이지 않고 정해진 시간(0초부터 900초, FIFO 큐는 0~15분) 동안 숨겨졌다가 나타나도록 설정한다. 지정된 시간 동안 아무 소비자도 그 메시지를 받을 수 없다.
  3. 가시성 타임아웃 설정소비자가 메시지를 수신한 뒤 다른 소비자에게 보이지 않게 숨겨지는 시간을 설정한다. 기본값은 30초이고 최대 12시간까지 지정할 수 있으며, 소비자의 실제 처리 시간보다 길게 잡아야 중복 수신을 피할 수 있다.

5본질 요약

보존 기간·지연·가시성 타임아웃 같은 파라미터로 큐가 메시지를 얼마나 오래 보관하고, 언제부터 보이게 하고, 처리 중 얼마나 숨길지를 애플리케이션의 요구에 맞추는 것

비용 할당 태그

큐에 태그를 붙여 프로젝트나 팀 단위로 비용을 나누어 추적할 수 있게 하는 항목.

1상대의 출발점 확인

여러 팀이나 프로젝트가 같은 AWS 계정 안에서 큐를 나눠 쓰는 경우가 많다. 기존 방식은 큐에 어떤 소속 정보도 없어서, AWS 비용 보고서에는 큐별 요금만 나오고 그 비용이 어느 팀의 것인지, 어느 프로젝트에서 발생했는지 전혀 구분되지 않았다. 그래서 월말에 SQS 비용 전체는 보이지만 팀별로 정산하거나 프로젝트 예산을 점검하는 것이 불가능했다.

2질문 제기

많은 큐에서 발생한 비용을 팀·프로젝트 단위로 구분해서 추적하려면 큐에 무엇을 표시해야 할까?

3구조적 핵심 예시

각 큐에 Team=Checkout 또는 CostCenter=12345 같은 키-값 형태의 태그를 붙인다. 예를 들어 결제 팀이 쓰는 큐에는 Team=payment, 검색 팀이 쓰는 큐에는 Team=search라고 태그를 달면, AWS 비용 보고서에서 이 태그별로 요금을 집계할 수 있어 팀마다 큐 비용을 나눠 볼 수 있다.

4단계별 동작 과정

  1. 태그 추가큐를 만들 때나 만든 뒤 편집 화면에서 키-값 형태의 태그를 붙인다. 예를 들어 Department=Operations처럼 원하는 키와 값을 한 쌍씩 추가한다.
  2. 태그 활성화AWS Billing 콘솔의 Cost allocation tags 메뉴에서 해당 태그 키를 활성화해야 비용 보고서에 태그가 나타난다. 활성화 전까지는 태그가 붙어 있어도 비용 집계에 쓰이지 않는다.
  3. 비용 집계활성화 후 Cost Explorer나 비용 보고서에서 태그 값별로 큐 비용을 조회해 팀·프로젝트 단위로 비용을 확인하고 정산한다.

5본질 요약

3큐 만들고 관리하기03-06

큐 목록 조회와 페이지네이션

계정의 큐 목록을 조회하고 결과가 많을 때 페이지 단위로 나누어 가져오는 방법을 다루는 항목.

1상대의 출발점 확인

계정 안에 큐가 몇 개 없을 때는 ListQueues(큐 목록 조회) 호출 한 번으로 전체 목록을 받아볼 수 있었다. 기존 방식은 이 한 번의 응답만 믿고 큐 목록을 사용했다. 그런데 큐가 많아지면 응답이 끊긴다. 한 번의 ListQueues 응답에는 최대 1,000개(표준 큐 기준)만 담기고, 그 뒤에 있는 큐는 다음 페이지를 가져오지 않으면 영영 목록에 나타나지 않는다. 큐가 수천 개인 계정에서는 실제로 존재하는 큐를 빠뜨린 채 일부만 보고 운영하게 되는 문제가 생긴다.

2질문 제기

한 번의 응답으로 다 담기지 않는 수많은 큐를 빠뜨리지 않고 전부 조회하려면 어떻게 해야 할까?

3구조적 핵심 예시

ListQueues 응답에 NextToken(다음 페이지의 위치를 가리키는 표시자)이 포함되면, 그 토큰을 다음 ListQueues 호출에 그대로 넣어 다음 페이지를 받아온다. 받은 응답에 또 NextToken이 있으면 다시 그 토큰으로 다음 페이지를 요청하는 식으로, NextToken이 사라질 때까지 반복하면 큐가 아무리 많아도 전체 목록을 빠뜨리지 않고 모을 수 있다.

4단계별 동작 과정

  1. 첫 페이지 조회ListQueues를 호출해 큐 목록과 함께 NextToken을 받는다. 큐가 많아 응답이 잘렸다면 NextToken이 응답에 포함된다.
  2. 다음 페이지 조회받은 NextToken을 다음 ListQueues 호출 파라미터에 넣어 이어지는 큐 목록을 조회한다. 토큰은 이전 응답이 끝난 지점부터 다시 시작한다는 뜻이다.
  3. 반복NextToken이 더 이상 없을 때까지 같은 과정을 반복해 전체 큐 목록을 누락 없이 모은 뒤 활용한다.

5본질 요약

ListQueues의 NextToken으로 여러 응답을 이어 가며 큐 목록을 페이지 단위로 전부 조회하는 것

4메시지 송수신 동작04-01

큐와 메시지 식별자

SQS가 큐를 가리키는 큐 URL과, 메시지마다 부여되는 메시지 ID·수신 처리에 쓰이는 receipt handle 등 식별자의 종류와 역할을 설명한다.

1상대의 출발점 확인

큐와 메시지를 다룰 때 이름만으로 구분하면 충분하다고 생각하기 쉽다. 그런데 기존 방식에는 구멍이 있다. 큐 이름은 계정 안에서만 고유하고, 계정이나 리전이 다르면 같은 이름의 큐가 따로 존재할 수 있어 이름만으로는 어느 큐인지 특정할 수 없다. 메시지는 더 곤란하다. 내용이 같은 메시지가 여러 개 있어도 구분할 수단이 없고, 특히 메시지를 수신한 뒤 그 "특정 수신"만 가리켜 삭제하거나 처리 상태를 바꾸려면 이름으로는 도저히 정확히 지목할 수 없다.

2질문 제기

큐와 메시지, 특히 방금 수신한 그 메시지를 정확히 가리키는 식별자는 무엇이고 각각 언제 쓰일까?

3구조적 핵심 예시

큐는 큐 URL로, 전송된 메시지는 MessageId로, 수신된 메시지는 ReceiptHandle(수신 영수증 핸들)로 식별된다. 예를 들어 메시지를 수신하면 SQS는 그 메시지뿐 아니라 "이번에 내가 받은 그 수신"만 가리키는 ReceiptHandle을 함께 돌려주고, 삭제할 때 이 핸들을 그대로 넘겨야 내가 받은 그 메시지가 정확히 삭제된다.

4단계별 동작 과정

  1. 큐 URL로 큐 지정계정 ID, 리전, 큐 이름으로 구성된 큐 URL이 큐 하나를 유일하게 가리킨다. 대부분의 API 호출에서 이 URL로 어느 큐를 대상으로 할지 지정한다.
  2. MessageId로 메시지 구분SendMessage(메시지 전송)가 성공하면 반환되는 MessageId가 그 큐 안에서 메시지를 유일하게 식별한다. 다만 수신한 메시지를 삭제할 때는 이 ID가 쓰이지 않는다.
  3. ReceiptHandle로 수신 지목ReceiveMessage(메시지 수신)가 반환하는 ReceiptHandle은 "이번에 내가 수신한 그 메시지"를 가리킨다. 삭제하거나 가시성 타임아웃(다른 소비자에게 보이지 않는 시간)을 변경할 때 이 핸들을 사용해야 정확한 메시지에 적용된다.

5본질 요약

큐 URL, MessageId, ReceiptHandle이라는 세 식별자로 큐와 메시지, 그리고 방금 수신한 특정 수신 인스턴스까지 정확히 지목해 송수신·삭제 동작을 가능하게 하는 것

메시지 전송과 메시지 속성

SendMessage로 메시지를 보낼 때 본문과 함께 붙이는 메시지 속성(attribute)과 메타데이터의 종류와 쓰임을 다룬다.

1상대의 출발점 확인

메시지를 보낼 때 본문(Body)만 담아 보내는 것이 기본적인 방식이었다. 그런데 받는 쪽은 본문을 열어봐야 그 메시지가 어떤 종류인지, 어느 처리 경로로 보내야 하는지 알 수 있었다. 또한 보낸 시각, 수신 횟수 같은 메시지에 딸린 정보(메타데이터)를 함께 확인하려면 큐 속성을 다시 조회해야 했다. 메시지 종류가 많은 시스템에서는 모든 수신자가 본문을 매번 파싱(구조를 해석)해야 해서 비효율적이고, 본문 구조가 바뀌면 이를 읽는 모든 부분이 함께 고쳐져야 했다.

2질문 제기

메시지 본문과 함께, 받는 쪽이 본문을 열지 않고도 활용할 수 있는 부가 정보를 어떻게 실어 보낼까?

3구조적 핵심 예시

SendMessage(메시지 전송) 호출에 MessageAttribute(메시지 속성)를 키-값으로 덧붙여 보낸다. 예를 들어 주문 이벤트라면 event_type=order_placed 같은 속성을 본문과 함께 실어 보내면, 받는 쪽은 본문을 읽지 않고 속성만 보고도 이 메시지가 주문 생성 이벤트임을 알 수 있어 바로 적절한 처리 경로로 보낼 수 있다.

4단계별 동작 과정

  1. 속성 정의와 전송SendMessage로 본문과 함께 메시지 속성을 전송한다. 속성은 문자열, 숫자, 바이너리 타입을 지원하며 사용자 지정 속성과 AWS 예약 속성으로 나뉜다.
  2. 저장과 메타데이터 기록SQS가 메시지를 큐에 저장하면서 본문·속성과 함께 보낸 시각, 수신 횟수 같은 메타데이터를 기록한다. 속성을 포함한 메시지 전체 크기가 한도(1MB)를 넘지 않아야 한다.
  3. 수신 측 활용ReceiveMessage(메시지 수신) 응답에 속성과 메타데이터가 함께 내려와, 받는 쪽은 본문을 열지 않고 속성 값으로 메시지를 분류·라우팅하고 메타데이터로 상태를 판단한다.

5본질 요약

SendMessage가 본문에 더해 메시지 속성과 메타데이터를 함께 전달해 받는 쪽이 본문을 열지 않고도 메시지를 분류하고 처리할 수 있게 하는 것

숏 폴링과 롱 폴링

ReceiveMessage 호출 시 대기하지 않고 즉시 응답하는 숏 폴링과, 메시지가 도착할 때까지 정해진 시간 동안 기다리는 롱 폴링의 동작 차이를 설명한다.

1상대의 출발점 확인

소비자가 큐에서 메시지를 가져올 때 쓰는 기본 호출은 ReceiveMessage입니다. 숏 폴링 방식에서는 이 호출을 하면 서버가 큐에 메시지가 있는지 그 순간만 확인하고, 없으면 빈 응답을 즉시 돌려줍니다. 따라서 메시지가 아직 도착하지 않았는데 소비자가 계속 호출하면 빈 응답을 받는 호출이 반복되고, 그 사이에 메시지가 도착했다면 다음 호출까지 처리 시작이 늦어집니다. 즉 메시지가 자주 오지 않는 큐일수록 쓸데없는 API 호출이 늘고, 메시지 도착을 알아차리는 시점도 매번 미뤄집니다.

2질문 제기

큐에 메시지가 없을 때 빈 응답을 받고 다시 호출하는 낭비와 지연을 어떻게 줄일 수 있을까?

3구조적 핵심 예시

대기 시간을 20초로 설정한 롱 폴링을 사용한다고 가정합니다. 소비자가 ReceiveMessage를 호출하면 큐에 메시지가 없다면 서버가 빈 응답을 바로 주지 않고 최대 20초 동안 기다렸다가, 그 사이 메시지가 들어오면 즉시 그 메시지를 돌려주고, 20초가 지나도 없으면 그때 빈 응답을 줍니다. 소비자 입장에서는 호출 한 번에 메시지 도착을 최대 20초간 기다릴 수 있으므로 호출 횟수가 크게 줄어듭니다.

4단계별 동작 과정

  1. ReceiveMessage 호출소비자가 ReceiveMessage 호출 시 WaitTimeSeconds 값(롱 폴링 대기 시간)을 지정해 보냅니다.
  2. 대기큐에 메시지가 없으면 서버가 지정된 시간(최대 20초) 동안 응답을 보류하고, 메시지가 도착하면 대기를 멈춥니다.
  3. 응답 반환메시지가 도착했으면 그 메시지를, 대기 시간이 끝났는데도 없으면 빈 응답을 돌려받습니다.

5본질 요약

가시성 타임아웃

수신된 메시지가 다른 소비자에게 보이지 않게 잠기는 시간으로, 처리 완료 전에 실패하면 메시지가 다시 큐에 보이게 되는 메커니즘이다.

1상대의 출발점 확인

큐에서 메시지를 수신한 소비자가 처리하는 동안, 같은 메시지를 다른 소비자가 또 가져가 버리면 같은 작업이 두 번 실행되어 중복 처리가 생깁니다. 그래서 가시성 타임아웃이 없는 단순한 구조에서는 소비자가 메시지를 받자마자 즉시 삭제해야 중복을 피할 수 있었습니다. 하지만 그렇게 하면 처리 도중 실패했을 때 이미 메시지가 삭제되어 재처리할 방법이 없어지고, 메시지가 영구적으로 유실되는 문제가 남습니다.

2질문 제기

한 소비자가 처리하는 동안 다른 소비자가 같은 메시지를 가져가지 못하게 하면서도, 처리에 실패하면 다시 시도할 기회를 주려면 어떻게 해야 할까?

3구조적 핵심 예시

가시성 타임아웃을 30초로 설정한 큐를 예로 듭니다. 소비자가 메시지를 수신하면 그 메시지는 30초 동안 다른 소비자에게 보이지 않게 잠깁니다. 소비자가 30초 안에 처리를 끝내고 메시지를 삭제하면 그대로 끝나고, 처리에 실패해 삭제하지 못하면 30초가 지난 뒤 메시지가 다시 눈에 보여 다른 소비자가 다시 받아 처리할 수 있습니다.

4단계별 동작 과정

  1. 수신과 잠금소비자가 ReceiveMessage로 메시지를 가져오면 SQS가 그 메시지를 가시성 타임아웃 시간 동안 다른 소비자에게 보이지 않게 잠급니다.
  2. 처리와 삭제소비자가 메시지 처리를 끝내고 DeleteMessage로 삭제하면 잠금은 그대로 종료됩니다.
  3. 타임아웃 해제처리가 끝나기 전에 시간이 지나면 잠금이 풀리고, 실패한 메시지가 다시 큐에 보여 다른 소비자가 재처리할 수 있습니다.

5본질 요약

수신한 메시지를 일정 시간 동안 다른 소비자에게 숨겨 중복 처리를 막고, 그 시간 안에 삭제되지 않은 메시지는 다시 보이게 하여 실패한 작업을 재시도할 수 있게 하는 것

지연 큐와 메시지 타이머

큐 수준에서 모든 메시지를 일정 시간 보이지 않게 하는 지연 큐와, 메시지 수준에서 개별적으로 지연을 주는 메시지 타이머를 설명한다.

1상대의 출발점 확인

기본 큐는 메시지가 도착하면 즉시 소비자가 받을 수 있습니다. 그런데 주문 후 일정 시간이 지나야 확정되는 작업처럼 "나중에 처리해야 하는 메시지"가 있으면, 기존 방식에서는 애플리케이션 코드 안에서 직접 잠시 대기하거나 별도의 예약 처리 로직을 만들어야 했습니다. 이렇게 하면 코드가 복잡해지고, 대기하는 동안 서버 자원이 붙잡히며, 정확한 시간에 맞춰 실행되도록 보장하기도 어렵습니다.

2질문 제기

보낸 메시지를 특정 시간 동안 소비자에게 보이지 않게 숨겨 두고 시간이 지난 뒤에 처리되도록 하려면 어떻게 해야 할까?

3구조적 핵심 예시

전송 시점부터 5분간 숨겨 두는 지연 큐 하나를 예로 듭니다. 보낸 메시지는 큐에 들어가도 5분 동안 소비자에게 보이지 않고, 5분이 지나야 비로소 소비자가 받아 처리할 수 있습니다. 같은 방식으로 메시지 타이머를 쓰면 메시지마다 개별적으로 0~15분 사이의 지연 시간을 초 단위로 지정할 수 있습니다.

4단계별 동작 과정

  1. 지연 시간 설정큐 자체에 지연 시간을 두는 지연 큐, 또는 메시지마다 따로 시간을 두는 메시지 타이머로 지연을 지정합니다.
  2. 메시지 숨김전송된 메시지가 지연 시간 동안 소비자에게 보이지 않는 상태로 큐 안에 유지됩니다.
  3. 시간 경과 후 노출지연 시간이 지나면 메시지가 소비자에게 보이게 되어 평소처럼 수신해 처리합니다.

임시 큐와 요청-응답 패턴

임시 큐를 만들어 요청-응답 패턴을 구현하는 방식으로, 요청 메시지에 회신용 임시 큐 주소를 담아 응답을 되돌려 받는다.

1상대의 출발점 확인

큐는 기본적으로 보내는 쪽과 받는 쪽이 서로 모르는 비동기 전달에 적합하지만, 요청을 보내고 응답을 기다려야 하는 통신에는 맞지 않습니다. 기존 방식에서는 응답을 받을 전용 큐를 미리 만들어 두고, 요청자는 응답이 올 때까지 그 큐를 계속 확인해야 했습니다. 응답 큐를 상시로 만들어 두면 큐 관리 비용이 계속 들고, 여러 요청이 섞이지 않도록 응답을 요청별로 구분하는 부가 정보도 매번 담아야 했습니다.

2질문 제기

요청마다 전용 응답 큐를 만들고 응답을 받은 뒤 바로 정리하는 방식으로 요청-응답 통신을 간단하게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

요청자가 쓰고 버릴 짧은 수명의 임시 큐를 하나 만들고, 그 큐의 주소를 요청 메시지에 담아 보냅니다. 처리자는 요청을 처리한 뒤 그 주소로 응답을 보내고, 요청자는 자신의 임시 큐에서 응답을 받아 처리한 다음 그 자리에서 임시 큐를 삭제합니다.

4단계별 동작 과정

  1. 임시 큐 생성과 요청 전송요청자가 임시 큐를 만들고, 회신 주소로 그 큐의 URL을 담은 요청 메시지를 큐에 보냅니다.
  2. 요청 처리와 응답 전송처리자가 요청을 처리한 뒤 요청에 담긴 회신 주소를 보고 응답 메시지를 임시 큐에 보냅니다.
  3. 응답 수신과 큐 정리요청자가 임시 큐에서 응답을 받아 처리하고, 사용이 끝난 임시 큐를 삭제합니다.

1상대의 출발점 확인

Amazon SQS 메시지 본문에는 256KB라는 크기 한도가 있습니다. 그런데 이미지, 큰 로그, 파일 조각 같은 데이터는 256KB를 훌쩍 넘는 경우가 많습니다. 기존 방식에서는 이런 큰 데이터를 큐로 보내려면 애플리케이션 코드에서 직접 Amazon S3에 파일을 올리고, 그 주소를 메시지에 넣고, 받는 쪽에서는 주소로 다시 파일을 내려받는 로직을 매번 작성해야 했습니다. 직렬화와 주소 관리, 사용 후 파일 정리까지 모두 손으로 처리해야 해서 코드가 복잡해지고 실수가 잦았습니다.

2질문 제기

256KB를 넘는 대용량 데이터를 메시지 크기 한도에 걸리지 않고 안전하게 주고받으려면 어떻게 해야 할까?

3구조적 핵심 예시

확장 클라이언트(Extended Client)를 예로 듭니다. 보내는 쪽 SDK가 큰 본문을 Amazon S3 버킷에 저장하고, 큐에는 그 객체의 위치를 가리키는 작은 포인터 메시지만 보냅니다. 받는 쪽 SDK는 이 작은 포인터 메시지를 받은 뒤 S3에서 원본 데이터를 꺼내 다시 메시지 본문 형태로 복원합니다. 사용자 코드는 평소처럼 작은 메시지를 주고받는 것과 같은 모습으로 작성합니다.

4단계별 동작 과정

  1. S3 저장과 포인터 생성보내는 쪽 확장 클라이언트가 큰 본문을 S3 버킷에 업로드하고, 객체 위치를 담은 작은 포인터 메시지를 만듭니다.
  2. 큐 전송한도를 넘지 않는 포인터 메시지만 큐를 통해 소비자에게 전달됩니다.
  3. 본문 복원받는 쪽 확장 클라이언트가 포인터를 보고 S3에서 원본을 내려받아 메시지 본문으로 되돌립니다.

데드레터 큐 개념과 redrive 정책

소비자가 계속 처리에 실패한 메시지를 원본 큐에서 옮겨 쌓아두는 별도의 격리 큐로, redrive 정책의 maxReceiveCount만큼 재시도한 뒤에도 실패한 메시지가 이동해 디버깅할 수 있게 한다.

1상대의 출발점 확인

소비자가 메시지를 받아 처리하는데 계속 실패하면, 가시성 타임아웃이 지날 때마다 그 메시지가 다시 큐에 보입니다. 이런 메시지가 많아지면 소비자는 같은 메시지만 반복해서 받느라 새 메시지를 처리하지 못하고, 실패한 메시지와 정상 메시지가 큐 안에 뒤섞여 무엇이 문제인지 원인을 찾기 어려워집니다. 기존 방식에서는 실패한 메시지를 계속 큐에 남겨 두거나 직접 골라내 삭제해야 했고, 실패 원인을 분석할 수 있는 흔적도 남지 않았습니다.

2질문 제기

계속 처리에 실패한 메시지를 정상 메시지 흐름에서 분리해 두고 나중에 원인을 분석하려면 어떻게 해야 할까?

3구조적 핵심 예시

redrive 정책에 최대 수신 횟수(maxReceiveCount)를 3으로 설정한 큐를 예로 듭니다. 메시지가 수신되고 삭제되지 않은 횟수가 3회에 이르면, SQS가 그 메시지를 원본 큐에서 데드레터 큐로 자동 이동시킵니다. 이후 소비자는 정상 메시지만 받아 처리하고, 실패한 메시지는 데드레터 큐에 따로 쌓여 있어 언제든 꺼내 원인을 확인하거나 다시 처리할 수 있습니다.

4단계별 동작 과정

  1. 재시도 반복소비자가 메시지를 받았지만 삭제하지 못하면, 가시성 타임아웃이 지날 때마다 메시지가 다시 큐에 보이고 수신 횟수가 늘어납니다.
  2. redrive 정책 적용수신 횟수가 redrive 정책의 maxReceiveCount에 도달하면 SQS가 그 메시지를 데드레터 큐로 이동시킵니다.
  3. 격리와 분석실패한 메시지는 원본 큐에서 빠져 데드레터 큐에 남고, 소비자는 정상 흐름을 이어가며 나중에 데드레터 큐에서 실패 메시지를 꺼내 원인을 분석합니다.

DLQ 구성과 redrive allow 정책

원본 큐에 redrive 정책을 설정해 대상 DLQ와 재시도 횟수를 지정하고, redrive allow 정책으로 소스 큐가 DLQ에 메시지를 보낼 수 있는 권한을 허용하는 구성 절차다.

1상대의 출발점 확인

소비자가 계속 실패하는 메시지를 원본 큐에 그대로 두면, 그 메시지가 앞을 막고 같은 메시지를 계속 받아 처리하는 반복이 이어집니다. 기존 방식은 소비자 쪽에서 실패를 직접 잡아내거나 로그로 남기는 것뿐이라, 큐 안에 쌓인 실패 메시지를 구조적으로 분리할 방법이 없었습니다. 그래서 SQS는 redrive 정책(redrive policy)으로 재시도 횟수를 정하고, 그 횟수를 넘긴 메시지를 별도 DLQ(데드레터 큐)로 자동 이동시킵니다. 다만 redrive 정책만으로는 부족합니다. 원본 큐가 DLQ에 메시지를 보낼 권한이 없으면 이동이 거부되므로, DLQ 쪽에 redrive allow 정책(redrive allow policy)으로 어떤 소스 큐가 보낼 수 있는지 명시해야 합니다.

2질문 제기

실패 메시지를 DLQ로 자동 이동시키기 위해, 원본 큐에는 재시도 기준을, DLQ에는 보내는 쪽의 권한을 어떻게 설정할까요?

3구조적 핵심 예시

주문 처리 큐 orders와 격리 큐 orders-dlq를 만드는 예시입니다. orders에 redrive 정책으로 deadLetterTargetArn(메시지를 옮길 DLQ의 ARN)에 orders-dlq를 지정하고 maxReceiveCount를 5로 둡니다. 그다음 orders-dlq에 redrive allow 정책을 붙여, 소스 큐 ARN이 orders인 경우만 해당 DLQ로 메시지를 보낼 수 있게 허용합니다. 이렇게 양쪽 설정이 갖춰지면 소비자가 5번 연속으로 실패한 메시지만 orders-dlq로 이동합니다.

4단계별 동작 과정

  1. DLQ와 redrive 정책 구성이동 대상 DLQ(표준 큐는 표준 DLQ, FIFO 큐는 FIFO DLQ)를 만들고, 원본 큐의 redrive 정책에 DLQ ARN과 최대 재시도 횟수(maxReceiveCount)를 지정합니다.
  2. redrive allow 정책 부여DLQ에 리소스 기반 정책을 작성해, 허용할 소스 큐(ARN 조건)만 해당 DLQ로 SendMessage 할 수 있게 권한을 줍니다.
  3. 실패 메시지 자동 이동소비자가 최대 재시도 횟수를 넘긴 메시지를 SQS가 DLQ로 이동시키고, 원본 큐에서는 사라집니다.

DLQ로의 메시지 이동과 빈 큐 redrive·제거 동작을 CloudTrail로 감사하고, DLQ 적체를 CloudWatch 알람으로 감지하며, DLQ의 메시지 보존 기간을 설정해 운영하는 방법이다.

1상대의 출발점 확인

DLQ를 구성해도 메시지가 DLQ에 쌓이는 것 자체로는 운영이 되지 않습니다. 누가 언제 DLQ로 보냈는지 감사 기록이 없으면 원인 추적이 막히고, DLQ가 차오르는 것을 아무도 알아채지 못하면 실패가 방치됩니다. 또한 DLQ에 옮겨진 메시지는 원본 큐의 보존 기간과 별개로 관리해야 하는데, 보존 기간을 따로 정하지 않으면 기본값(4일)만 적용되어 디버깅 시간이 부족해질 수 있습니다.

2질문 제기

DLQ로 이동한 실패 메시지를 감사하고, 적체를 경고하고, 적절한 기간만 보관하려면 어떻게 운영할까요?

3구조적 핵심 예시

orders-dlq가 운영되는 모습의 예시입니다. CloudTrail이 해당 큐에 대한 SendMessage와 redrive 동작을 API 호출 이벤트로 기록해 나중에 누가 보냈는지 추적할 수 있게 합니다. CloudWatch 알람이 ApproximateNumberOfMessagesVisible 지표(큐에 보이는 메시지 수)가 100을 넘으면 알림을 보냅니다. 그리고 DLQ의 메시지 보존 기간을 14일로 설정해, 2주가 지난 실패 메시지는 자동 삭제되도록 합니다.

4단계별 동작 과정

  1. CloudTrail 감사 기록큐에 대한 API 호출과 DLQ 이동(redrive) 이벤트가 CloudTrail에 기록되는지 확인하고, 필요한 권한을 갖춰 감사 로그를 남깁니다.
  2. CloudWatch 알람 설정DLQ의 메시지 수 지표에 임계값을 걸고, 초과 시 알림이 가도록 알람을 구성해 적체를 빠르게 감지합니다.
  3. 보존 기간 설정DLQ의 메시지 보존 기간을 1일~14일 범위에서 정해, 디버깅에 필요한 기간만 메시지를 보관하고 오래된 실패 메시지를 정리합니다.

3구조적 핵심 예시

주문 생성 요청을 보내는 예시입니다. 프로듀서가 SendMessage 요청에 MessageDeduplicationId로 "order-20260926-0001"을 붙여 보냅니다. 같은 요청이 네트워크 재시도로 5분 안에 두 번 전송되어도 SQS는 동일한 중복 제거 ID를 보고 첫 메시지만 큐에 유지하고 두 번째는 중복으로 판별해 무시합니다.

4단계별 동작 과정

  1. 중복 제거 ID 결정프로듀서가 메시지마다 고유한 MessageDeduplicationId를 정합니다. 지정하지 않으면 SQS가 메시지 내용으로 계산한 해시를 사용합니다.
  2. 전송 시 ID 포함SendMessage 요청에 그 ID를 실어 보내고, SQS는 이 ID를 5분 중복 제거 창(window) 동안 기억합니다.
  3. 중복 판별과 폐기같은 ID의 메시지가 창 안에 다시 도착하면 SQS가 중복으로 판별해 큐에 넣지 않고, 첫 전송의 메시지만 소비자에게 전달됩니다.

1상대의 출발점 확인

중복 제거 ID를 쓰면 되지만, 프로듀서가 여러 대이거나 컨슈머가 여러 대인 시스템에서는 단순히 ID를 붙이는 것만으로는 중복이 남습니다. 프로듀서가 하나면 ID를 순번처럼 스스로 관리할 수 있지만, 프로듀서가 여럿이면 서로 다른 장비에서 같은 ID를 만들 위험이 있어 발급 전략이 달라집니다. 반대로 컨슈머가 여럿이면 큐에 중복이 없어도 같은 메시지를 두 컨슈머가 받아 중복 처리할 수 있고, 이는 결과(예: 결제, 재고 차감)에 그대로 반영됩니다.

2질문 제기

프로듀서가 하나든 여럿이든, 컨슈머가 여럿이든 중복이 결과에 반영되지 않게 하려면 어떻게 설계할까요?

3구조적 핵심 예시

이벤트 로그를 수집하는 시스템의 예시입니다. 프로듀서가 하나면 중복 제거 ID를 일련번호로 직접 발급합니다. 프로듀서가 여럿이면 UUID처럼 서로 충돌하지 않는 고유 ID를 각자 생성해 붙입니다. 컨슈머 측에서는 같은 ID를 가진 처리를 이미 했는지 저장소(예: 처리 ID 기록 테이블)에서 확인한 뒤에만 작업을 반영하는 멱등(결과가 한 번만 반영되는) 처리를 합니다.

4단계별 동작 과정

  1. 프로듀서 수에 맞는 ID 전략 선택프로듀서가 하나면 순번 기반, 여럿이면 UUID처럼 전역 고유한 MessageDeduplicationId를 만들어 같은 논리 메시지에는 항상 같은 ID를 붙입니다.
  2. 큐의 중복 제거FIFO 큐가 중복 제거 창 안에서 같은 ID를 걸러내 큐에 한 번만 남깁니다.
  3. 컨슈머 멱등 처리여러 컨슈머가 같은 메시지를 받아도 처리 ID를 먼저 확인해 이미 처리된 작업이면 건너뛰고, 결과가 한 번만 반영되게 합니다.

5본질 요약

메시지 그룹 ID와 인터리빙

FIFO 큐에서 메시지에 붙이는 그룹 식별자로, 같은 그룹 ID 안에서는 순서가 보장되고 서로 다른 그룹은 번갈아(인터리빙) 처리되어 병렬성을 높이는 속성.

→ 06-04 참조

1상대의 출발점 확인

FIFO 큐는 메시지 순서를 보장하지만, 그 순서 보장이 곧 제약이 됩니다. 모든 메시지가 순서대로만 처리되면 처리량이 하나의 흐름에 묶이고, 앞 메시지가 오래 걸리면 뒤 메시지가 전부 대기합니다. 그런데 실제 시스템에서는 주문별, 사용자별처럼 서로 독립인 여러 흐름이 섞여 있는 경우가 대부분입니다. 독립인 흐름까지 하나의 순서로 묶는 것은 불필요한 병목입니다.

2질문 제기

서로 독립인 메시지 흐름들의 순서는 각자 지키면서, 여러 흐름을 동시에 처리하려면 어떻게 해야 할까요?

3구조적 핵심 예시

알림 발송 큐의 예시입니다. 각 주문마다 MessageGroupId(메시지 그룹 ID)를 다르게, 예를 들어 주문 A 그룹과 주문 B 그룹으로 나눠 보냅니다. 컨슈머가 두 그룹에서 동시에 메시지를 받아 처리하므로 주문 A 알림 처리와 주문 B 알림 처리가 병렬로 진행되고, 각 그룹 안에서는 보낸 순서대로만 소비됩니다.

4단계별 동작 과정

  1. 그룹 ID 지정프로듀서가 메시지마다 MessageGroupId를 붙입니다. 같은 그룹 ID의 메시지는 하나의 가상 큐처럼 순서대로 처리됩니다.
  2. 독립 가상 큐 분리SQS가 그룹 ID별로 메시지를 독립된 가상 큐로 나눠, 서로 다른 그룹 사이에는 순서를 보장하지 않습니다.
  3. 인터리빙 처리여러 컨슈머 인스턴스가 서로 다른 그룹의 메시지를 동시에 받아 처리해, 그룹 하나가 막혀도 다른 그룹의 처리는 진행됩니다.

→ 06-03 참조

1상대의 출발점 확인

메시지 그룹 ID는 순서를 지켜 주지만, 그 대가로 그룹 하나가 병목이 될 수 있습니다. 같은 그룹 ID에 메시지가 대량으로 쌓이면(백로그) 뒤쪽 메시지는 선두 메시지가 처리될 때까지 모두 대기하고, FIFO 큐 처리량이 그 그룹 하나에 묶입니다. 또한 가상 큐처럼 쓰는 고유 그룹 ID를 재사용하면, 이전 사용에서 남은 지연이나 대기 메시지가 새 작업의 순서와 처리에 그대로 영향을 줍니다. 이런 상황은 그룹 ID를 무심코 고정하거나 재사용할 때 흔히 생깁니다.

2질문 제기

그룹 하나에 메시지가 몰리는 백로그와 가상 큐의 그룹 ID 재사용이 병목을 만들지 않으려면 어떻게 해야 할까요?

3구조적 핵심 예시

알림 발송을 그룹 ID "notifications" 하나로 몰아보내는 예시입니다. 이전 알림 10만 건이 쌓여 있는데 새 알림 메시지가 같은 그룹에 붙으면, 선두 10만 건이 처리되기 전까지 새 알림은 꼼짝없이 대기합니다. 이를 피하려면 각 논리 작업에 고유한 그룹 ID를 부여해 흐름을 분리하고, 재사용할 그룹 ID는 이전 메시지가 모두 소진된 뒤에만 다시 쓰는 방식으로 운영합니다.

4단계별 동작 과정

  1. 백로그 위험 인지같은 그룹 ID에 메시지가 계속 쌓이는지 확인합니다. 쌓이면 선두 메시지 처리 전까지 그룹 전체가 대기한다는 점을 전제로 설계합니다.
  2. 가상 큐 재사용 회피직전 작업의 메시지가 아직 남아 있는 그룹 ID를 다시 쓰지 않고, 수명이 끝난 소비 흐름은 고유 ID를 폐기합니다.
  3. 백로그 근본 제거한 그룹에 몰리지 않도록 그룹 ID를 세분화하고, 컨슈머를 늘려 그룹의 선두 메시지가 빨리 소진되게 합니다.

수신 재시도 ID와 장애 복구 설계

수신(ReceiveMessage) 재시도 때 같은 시도 ID를 보내 중복 수신을 막고, 장애 상황에서도 메시지가 유실·중복되지 않도록 큐를 설계하는 복구 전략.

→ 06-01 참조

1상대의 출발점 확인

기존 방식에서는 소비자가 ReceiveMessage 호출로 큐에서 메시지를 받아낸다. 네트워크 오류나 타임아웃으로 요청이 실패하면 소비자는 같은 요청을 다시 보내는데, 기존 API에는 "이번 요청이 방금 실패한 요청의 재시도다"라고 서버에 알려줄 수단이 없었다. 그래서 재시도는 언제나 완전히 새로운 수신 요청으로 취급되었고, 장애 복구 상황에서 소비자가 같은 메시지를 중복으로 받아가거나 수신 흐름이 어긋나는 문제가 생겼다. 또한 여러 소비자가 동시에 재시도를 하면 누가 어떤 메시지를 처리 중인지 서버가 구분할 방법이 없어져, 복구 후 처리 결과가 뒤섞이는 위험이 컸다.

2질문 제기

장애로 실패한 수신 요청을 다시 보낼 때, 서버가 그것을 "같은 요청의 재시도"로 알아채게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

ReceiveMessage 호출에 receiveRequestAttemptId(수신 시도 ID)라는 값을 실어 보내면, SQS는 같은 ID가 달린 여러 요청을 하나의 재시도 묶음으로 인식한다. 예를 들어 소비자가 "receipt-attempt-20260926-001"이라는 ID로 요청을 보냈는데 응답을 못 받았다면, 같은 ID로 다시 호출한다. SQS는 이 두 요청이 같은 시도의 연속임을 알고 중복 수신을 만들지 않는다.

4단계별 동작 과정

  1. 시도 ID 생성해 전송소비자가 ReceiveMessage 요청에 receiveRequestAttemptId 파라미터를 채워 보낸다. 이 ID는 수신 시도 하나를 대표하는 값이다.
  2. 실패 시 같은 ID로 재시도응답을 받지 못하거나 오류가 나면, 소비자는 같은 ID를 그대로 써서 다시 호출한다. SQS는 ID가 같은 요청들을 중복으로 보지 않고 하나의 시도로 처리한다.
  3. ID가 다른 요청은 별개 처리ID가 다르면 각각 독립된 수신으로 취급되어, 서로 다른 소비자나 서로 다른 시도는 같은 메시지를 중복으로 받아갈 수 있음을 설계에 반영해야 한다.

fair queues: 다중 테넌트 큐의 이웃 소음 완화

다중 테넌트가 메시지 그룹 ID로 공유하는 표준 큐에서, 대량 생산자의 메시지가 다른 테넌트의 처리를 밀어내는 이웃 소음(noisy neighbor) 문제를 완화하는 SQS 기능이다.

→ 06-03 참조

1상대의 출발점 확인

기존 방식에서는 표준 큐가 메시지를 받아간 순서대로 소비자에게 건네주고, 한 번에 가져갈 수 있는 메시지 수(in-flight)에 특별한 제한을 두지 않았다. 여러 테넌트(고객이나 팀)가 메시지 그룹 ID를 자기 테넌트의 식별자로 쓰면서 하나의 표준 큐를 공유한다고 하면, 메시지를 아주 많이 보내는 테넌트가 큐 앞부분을 계속 채워 다른 테넌트의 메시지는 끝까지 도달하지 못한다. 이렇게 한 테넌트의 대량 생산이 이웃 테넌트의 처리를 밀어내는 문제를 이웃 소음(noisy neighbor)이라고 하며, 기존 방식으로는 이를 막을 수단이 없었다.

2질문 제기

한 테넌트가 메시지를 대량으로 보낼 때, 어떻게 다른 테넌트의 메시지도 계속 처리되게 할 수 있을까?

3구조적 핵심 예시

fair queues 기능은 큐 안의 메시지를 메시지 그룹 ID별로 나누어, 어느 그룹이 in-flight(소비자가 받아 아직 삭제하지 않은) 메시지를 많이 쥐고 있는지 감시한다. 어떤 그룹이 지나치게 몰려 있으면, SQS는 소비자의 수신 요청에 대해 상대적으로 조용한 그룹(quiet groups)의 메시지를 먼저 건네준다.

4단계별 동작 과정

  1. 그룹별 분포 감지SQS가 큐의 메시지를 그룹 ID별로 집계해, in-flight 메시지가 어느 그룹에 몰려 있는지 분포를 본다.
  2. 조용한 그룹 우선 공급대량 생산 그룹이 감지되면, 소비자가 메시지를 요청할 때 조용한 그룹의 메시지를 우선해 준다. 이 중재는 대량 생산 그룹의 메시지를 받아가던 소비자에게만 적용되어, 전체 처리량에는 큰 손실을 주지 않는다.
  3. 평상시로 복귀대량 생산 그룹의 in-flight 수가 줄어들면 중재를 멈추고 모든 그룹의 메시지를 평소처럼 공급한다.

fair queues의 동작 원리와 지표

같은 그룹 ID의 대량 in-flight 메시지를 감지하면 소비자에게 잠시 조용한 그룹(quiet groups)을 우선 제공하고, 이 동작을 fair-queue 관련 CloudWatch 지표로 관찰할 수 있게 하는 동작 원리다.

1상대의 출발점 확인

기존 방식에서는 fair queues 기능이 꺼져 있는 표준 큐가 수신 요청이 올 때마다 큐 앞에 있는 메시지를 그대로 건네주었다. 대량 생산 그룹의 메시지가 계속 앞에 쌓여 있으면 소비자는 항상 그 메시지들만 받아가고, 다른 그룹의 메시지는 꺼내지지 않았다. 게다가 "지금 각 그룹이 얼마나 많은 메시지를 쥐고 있는지"를 볼 수 있는 지표가 없어서, 특정 테넌트의 처리가 밀리고 있는 상황을 운영자가 관찰하거나 원인을 판단하기 어려웠다.

2질문 제기

fair queues는 어떤 기준으로 대량 생산 그룹을 감지해 중재하고, 그 동작을 운영자가 어떤 지표로 확인할 수 있을까?

3구조적 핵심 예시

SQS가 메시지 그룹 ID별로 in-flight 메시지 수를 계속 계산한다. 어느 그룹의 in-flight 수가 다른 그룹에 비해 갑자기 크게 늘면 그 그룹을 대량 생산으로 판정하고, 오래 기다린 조용한 그룹의 메시지를 소비자에게 우선 반환한다.

4단계별 동작 과정

  1. in-flight 분포 계산SQS가 ReceiveMessage로 나간 메시지를 그룹 ID별로 집계해, 각 그룹이 보유한 in-flight 메시지 수를 지속적으로 파악한다.
  2. 공정성 중재 적용분포를 바탕으로 대량 생산 그룹을 판정하고, 조용한 그룹의 메시지를 원하는 소비자에게 해당 메시지를 우선 공급한다. 중재는 대량 생산 그룹에서 계속 받아가던 소비자에 대해서만 적용해 전체 처리량을 보존한다.
  3. 지표로 관찰CloudWatch의 InFlightMessagePerMessageGroup 지표로 그룹별 in-flight 수를 실시간으로 보면서 중재가 일어나는 상황을 확인하고, 큐 설계를 조정한다.

5본질 요약

→ 01-03 참조

1상대의 출발점 확인

기존 방식에서는 하나의 메시지를 여러 처리 시스템에 전달하려면 생산자 쪽 코드가 각 대상 큐에 일일이 메시지를 보내야 했다. 처리 대상을 하나 추가할 때마다 생산자 코드를 고쳐야 하고, 대상 중 하나가 실패하면 그 영향이 생산자의 발송 흐름까지 퍼졌다. 생산자가 알아야 하는 큐의 목록이 늘어날수록 생산자와 소비자 구조가 단단하게 결합되어, 시스템 전체를 유연하게 바꾸기 어려운 것이 기존 방식의 명확한 한계였다.

2질문 제기

생산자가 메시지를 한 번만 보내도 여러 큐가 각자 독립적으로 같은 메시지를 받아 처리하게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

SNS 주제(topic)에 SQS 큐를 구독시킨다. 생산자는 주제에 메시지를 한 번 발행하고, SNS가 구독된 모든 큐에 메시지를 복제해 전달한다. 메시지가 여러 대상으로 퍼져 나간다고 하여 팬아웃(fan-out) 패턴이라고 부른다.

4단계별 동작 과정

  1. 큐를 주제에 구독SQS 큐를 SNS 주제의 구독자로 등록하고, 주제가 이 큐에 메시지를 보낼 수 있도록 큐의 권한 정책을 설정한다.
  2. 주제에 한 번 발행생산자가 주제에 메시지를 보낸다. SNS는 메시지를 받아 그 순간 구독 중인 모든 큐에 복사본을 전달한다.
  3. 각 큐에서 독립 수신각 큐의 소비자들이 자기 큐에서 메시지를 따로 꺼내 처리한다. 어느 한 큐의 처리가 실패하거나 느려져도 다른 큐의 처리는 영향을 받지 않는다.

Lambda 트리거와 FIFO 동시성 동작

큐에 도착한 메시지가 Lambda 함수를 자동으로 실행하며, FIFO 큐에서는 메시지 그룹당 한 번에 하나만 실행되어 순서가 보장되는 동시성 동작.

1상대의 출발점 확인

기존 방식에서는 메시지가 큐에 도착해도 처리가 시작되지 않았고, 소비자 프로그램이 ReceiveMessage를 직접 호출해 폴링해야 했다. 처리를 항상 준비하려면 서버를 계속 띄워 두어야 하고, 메시지가 없는 동안에도 폴링 요청이 반복적으로 발생했다. 메시지가 갑자기 몰리는 상황에서는 서버를 미리 늘려 두지 않으면 처리가 밀렸고, 줄어들면 놀고 있는 자원 비용이 그대로 남았다. 처리량이 급변하는 워크로드에 인프라 규모를 맞추기 어려운 것이 한계였다.

2질문 제기

메시지가 큐에 도착하면 자동으로 처리 함수가 실행되게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

큐에 Lambda 함수를 트리거로 연결한다. 메시지가 큐에 도착하면 Lambda 서비스가 큐를 폴링해 메시지를 꺼내 함수를 실행한다. FIFO 큐에서는 같은 메시지 그룹 ID의 메시지가 순서대로, 그룹당 한 번에 하나씩만 처리되도록 동시성이 제어된다.

4단계별 동작 과정

  1. 트리거 연결과 폴링소비자 코드 대신 Lambda 함수를 큐의 트리거로 연결한다. Lambda 서비스가 주기적으로 큐를 폴링해 메시지를 배치 단위로 꺼내 함수를 호출한다.
  2. 동시성 조절표준 큐에서는 여러 배치가 함수의 여러 동시 실행으로 병렬 처리된다. FIFO 큐에서는 메시지 그룹 ID별로 동시 실행 수가 1로 제한되어 같은 그룹 안의 메시지 순서가 보장되고, 다른 그룹끼리는 병렬로 처리된다.
  3. 실패 처리함수 실행이 실패한 메시지는 다음 폴링에서 다시 꺼내져 재시도되고, 설정한 최대 수신 횟수를 넘기면 데드레터 큐로 이동해 격리된다.

5본질 요약

큐를 Lambda의 트리거로 연결해 서버 관리 없이 메시지 도착에 맞춰 함수를 자동 실행하고, FIFO 큐에서는 그룹별 동시성을 1로 제한해 순서를 보장하는 것

EventBridge 자동화와 Pipes 연동

큐 이벤트를 EventBridge 규칙으로 다른 AWS 서비스에 알리거나 EventBridge Pipes로 메시지를 변환·전달하는 서비스 간 자동화 연동.

1상대의 출발점 확인

기존 방식에서는 큐의 상태 변화(메시지 도착, 큐 생성·삭제 등)를 다른 AWS 서비스에 알리려면 알림을 받는 쪽이 직접 폴링하거나 별도의 감시 코드를 작성해야 했다. 또한 큐의 메시지를 받아 다른 서비스가 요구하는 형태로 변환해서 전달하려면 변환·전송 로직을 직접 구현하고 관리해야 했다. 연동 대상이 늘어날수록 관리할 코드와 장애 지점이 함께 늘어나는 것이 기존 방식의 한계였다.

2질문 제기

큐에서 일어난 이벤트를 다른 AWS 서비스가 자동으로 받아가게 하고, 메시지를 변환해 전달하는 연결을 별도 코드 없이 만들 수 없을까?

3구조적 핵심 예시

EventBridge 규칙이 SQS 큐의 이벤트를 감지해 다른 AWS 서비스에 알리고, EventBridge Pipes가 소스 큐에서 메시지를 읽어 필터·변환을 적용한 뒤 대상 서비스로 전달한다. 둘 다 코드 대신 설정으로 구성하는 무코드 연동 파이프라인이다.

4단계별 동작 과정

  1. 이벤트 발생과 규칙 매칭큐에 메시지가 도착하거나 자원 상태가 바뀌면 SQS가 이벤트를 EventBridge에 보낸다. 규칙의 이벤트 패턴과 일치하면 규칙이 대상을 호출해 알림을 전달한다.
  2. Pipes로 메시지 흐름 구성EventBridge Pipes에서 소스로 SQS 큐를 지정하면, 파이프가 메시지를 읽어 필터(조건으로 거르기)와 변환(매핑으로 형태 바꾸기)을 적용한다.
  3. 대상으로 전달과 실패 처리변환된 메시지를 지정한 대상(예: 다른 큐, Lambda 함수, API 대상 등)으로 보낸다. 전달이 실패하면 재시도하거나 대상 실패 큐로 보내 격리한다.

VPC 내부에서 메시지 전송

인터넷을 거치지 않고 VPC 엔드포인트를 통해 VPC 내부 리소스가 SQS 큐에 메시지를 안전하게 전송하는 방법.

1상대의 출발점 확인

기존에 VPC(가상 사설 클라우드. AWS 계정 안에 만드는 격리된 네트워크 공간) 안의 EC2 인스턴스가 SQS를 사용하려면 공용 인터넷 경로가 필요했다. 프라이빗 서브넷(외부에 직접 노출되지 않는 네트워크 구역)에 둔 인스턴스는 인터넷 게이트웨이가 없어서 SQS API에 도달하지 못했고, 그 때문에 NAT 게이트웨이(프라이빗 인스턴스가 인터넷으로 나갈 때 IP 주소를 바꿔주는 장치)를 추가하거나 퍼블릭 IP를 붙여야 했다. 이 방식은 부가 장치 비용이 들고, 트래픽이 공용 인터넷을 지나가므로 보안 통제를 별도로 강화해야 하는 문제가 있었다.

2질문 제기

인터넷 경유 없이 VPC 안에서만 SQS로 메시지를 주고받을 수는 없을까?

3구조적 핵심 예시

VPC 엔드포인트(interface endpoint)를 만들면, VPC 안의 EC2 인스턴스가 공용 IP가 아닌 사설 IP 주소로 SQS API에 접속한다. 요청은 AWS의 사설 네트워크 안에서만 이동하므로 인터넷 게이트웨이도 NAT도 필요 없어진다. 큐에 메시지를 보내는 동작 자체는 평소와 똑같은 SendMessage 호출이며, 도달 경로만 VPC 안으로 바뀐다.

4단계별 동작 과정

  1. VPC 엔드포인트 생성SQS용 interface 엔드포인트를 만들고, 연결할 서브넷과 보안 그룹을 지정한다. 엔드포인트는 선택한 서브넷 안에 사설 IP 주소를 가진 진입점을 만들어 준다.
  2. DNS 경로 전환SQS 도메인에 대한 DNS 해석이 엔드포인트의 사설 IP를 가리키게 된다. 요청이 인터넷 게이트웨이로 나가지 않으므로 별도 라우팅 테이블 수정 없이도 대부분의 구성에서 바로 동작한다.
  3. 메시지 전송·수신VPC 안의 인스턴스가 기존과 같은 SQS API(SendMessage, ReceiveMessage 등)를 호출하고, 응답도 같은 사설 경로로 돌아온다. 큐가 있는 리전과 VPC가 다르면 엔드포인트 정책이나 IAM 조건으로 접근을 제한할 수 있다.

5본질 요약

1상대의 출발점 확인

기존에는 콘솔 화면에서 큐를 만들거나 AWS CLI 명령을 하나씩 실행해 큐를 생성했다. 개발·스테이징·프로덕션처럼 환경이 여러 개면 같은 설정을 반복해서 입력해야 했고, 누가 언제 어떤 속성으로 큐를 바꿨는지 기록이 남지 않아 변경 이력을 추적하기 어려웠다. 실수로 다른 속성값을 입력하면 환경마다 큐 설정이 달라져 운영 때 문제가 되기도 했다.

2질문 제기

큐 구성을 코드로 선언해 한 번에, 반복 가능하게 만들 수는 없을까?

3구조적 핵심 예시

CloudFormation 템플릿(YAML 또는 JSON으로 작성하는 인프라 정의 파일)에 AWS::SQS::Queue 리소스를 선언하고 스택(템플릿에 적힌 리소스 묶음)으로 배포하면, 같은 정의가 그대로 여러 환경에 동일한 큐를 만든다. 콘솔 조작 없이 파일 하나로 큐 생성·갱신·삭제가 전부 관리된다.

4단계별 동작 과정

  1. 템플릿 작성AWS::SQS::Queue 리소스에 QueueName, MessageRetentionPeriod(메시지 보존 기간), VisibilityTimeout(수신된 메시지가 다른 수신자에게 숨겨지는 시간) 같은 속성을 선언한다. FIFO 큐라면 FifoQueue 속성과 ContentBasedDeduplication 등을 함께 지정한다.
  2. 스택 배포템플릿을 CloudFormation에 제출하면 서비스가 선언된 리소스를 순서대로 생성한다. 다른 스택에서 만든 리소스와 연결해야 하면 Ref나 Outputs로 큐 URL·ARN을 전달할 수 있다.
  3. 재사용과 갱신같은 템플릿을 다른 리전·계정에 다시 배포하고, 이후 설정 변경은 템플릿을 수정한 뒤 스택 업데이트로 적용한다. 변경 내역은 CloudFormation이 기록하므로 추적이 가능하다.

SQS API와 AWS JSON·쿼리 프로토콜

SQS를 조작하는 모든 동작은 HTTP API 요청으로 이뤄지며, 이 요청은 AWS JSON 프로토콜과 AWS 쿼리(Query) 프로토콜이라는 두 가지 형식으로 주고받는다.

1상대의 출발점 확인

기존에 SQS는 AWS 쿼리 프로토콜(query protocol)이라는 오래된 방식으로만 API를 제공했다. 이 방식은 요청에 Action 파라미터로 액션 이름을 넣고 폼 인코딩 방식으로 보내며, 응답은 XML로 돌아온다. 반면 AWS의 최신 서비스들은 JSON 기반의 표준 프로토콜을 쓰기 때문에, SQS만 따로 다루는 클라이언트 코드는 XML 파싱과 구식 요청 형식을 지원하기 위해 별도로 구현해야 했다.

2질문 제기

같은 큐 동작을 AWS 표준인 JSON 프로토콜로도 요청·응답할 수는 없을까?

3구조적 핵심 예시

SQS는 동일한 액션(SendMessage, ReceiveMessage 등)을 두 가지 방식으로 제공한다. 하나는 기존의 쿼리 프로토콜로 응답이 XML이고, 다른 하나는 AWS JSON 프로토콜로 응답이 JSON이다. 클라이언트가 사용할 방식을 골라 호출하면 되고, 액션의 의미는 같다.

4단계별 동작 과정

  1. 호출 방식 선택요청 헤더로 프로토콜이 결정된다. AWS JSON 프로토콜은 Content-Type을 application/x-amz-json-1.0으로 쓰고 X-Amz-Target 헤더에 "AmazonSQS.SendMessage"처럼 액션 이름을 넣는다. 쿼리 프로토콜은 Action 파라미터에 액션을 지정한다.
  2. 본문 작성과 인증JSON 프로토콜은 액션별 파라미터를 JSON 본문으로 실어 보내고, 쿼리 프로토콜은 파라미터를 폼 인코딩으로 보낸다. 두 방식 모두 SigV4(요청 내용을 기반으로 서명 값을 만들어 호출자를 검증하는 방식) 서명이 필요하다.
  3. 응답 해석JSON 프로토콜은 JSON 객체를, 쿼리 프로토콜은 XML 문서를 받는다. 각 프로토콜의 레이아웃에 맞춰 결과 필드(예: MessageId, MD5OfMessageBody)를 읽으면 된다.

요청 인증과 AWS SDK 사용

모든 SQS API 요청은 AWS 자격 증명으로 서명해야 하며, AWS SDK가 이 서명과 요청 구성을 대신 처리해 준다.

1상대의 출발점 확인

기존에 SQS API를 호출할 때 인증이 없거나 약하면, 자기 계정이 아닌 사용자가 큐의 메시지를 읽거나 지울 수 있었다. 또 HTTP 요청을 직접 만들려면 서명 계산, 만료된 자격 증명 처리, 일시적 오류 재시도, 응답 파싱을 매번 손으로 구현해야 해서 코드가 길어지고 실수가 잦았다.

2질문 제기

모든 SQS 요청이 호출자 신원을 검증받으면서, 번거로운 서명·재시도 작업은 자동으로 처리할 수는 없을까?

3구조적 핵심 예시

모든 SQS 요청은 SigV4로 서명되어 호출자의 자격 증명이 검증된다. 그리고 AWS SDK(각 프로그래밍 언어용 AWS 라이브러리)가 자격 증명을 읽어 서명을 붙이고, 일시적 오류를 재시도하며, 응답을 객체로 변환하는 일을 대신 처리한다. 개발자는 클라이언트를 만들고 메서드를 호출하기만 하면 된다.

4단계별 동작 과정

  1. 자격 증명 준비IAM 사용자·역할, 또는 임시 보안 자격 증명(예: EC2 인스턴스 프로파일, STS로 발급받은 토큰)에서 액세스 키와 시크릿 키를 얻는다. SDK는 환경 변수·설정 파일·메타데이터 서비스 등 다양한 위치에서 자격 증명을 찾는다.
  2. 요청 서명SDK 또는 직접 구현한 코드가 요청의 액션·헤더·본문을 기반으로 SigV4 서명 값을 계산해 Authorization 헤더에 넣는다. 이 서명이 호출자가 유효한 자격 증명을 가졌다는 증거가 된다.
  3. API 호출과 응답 처리SendMessage 같은 메서드를 호출하면 SDK가 서명을 붙여 요청을 보내고, 응답을 언어별 객체(예: 메시지 ID, 메시지 본문)로 변환해 준다. 실패하면 재시도 정책에 따라 다시 시도한다.

배치 액션과 클라이언트 측 버퍼링

여러 메시지 작업(전송·삭제·가시성 변경)을 하나의 API 호출로 묶는 배치 액션과, 클라이언트가 요청을 모아 보내는 버퍼링으로 API 호출 수를 줄이는 기법이다.

1상대의 출발점 확인

기존에는 메시지를 보낼 때마다 SendMessage 요청을 한 번씩 보냈다. 메시지 수가 많아질수록 HTTP 요청의 왕복(요청을 보내고 응답을 받는 전체 시간) 횟수가 그대로 늘어나 지연이 커졌고, SQS 요금은 요청 개수 기준이므로 비용도 요청 수에 비례해 증가했다. 수신(ReceiveMessage)과 삭제(DeleteMessage)도 마찬가지였다.

2질문 제기

여러 메시지를 한 번의 요청으로 묶어 왕복 횟수와 비용을 줄일 수는 없을까?

3구조적 핵심 예시

SendMessageBatch로 최대 10개의 메시지를 한 요청에 실어 보낸다. 요청이 하나이므로 왕복이 한 번이고, 실패한 항목은 응답의 개별 실패 목록으로 돌아와서 그 항목만 다시 보내면 된다. 수신과 삭제에도 ReceiveMessageBatch, DeleteMessageBatch가 같은 방식으로 존재한다.

4단계별 동작 과정

  1. 배치 요청 구성SendMessageBatch 호출에 메시지별 Id(응답에서 어느 항목의 결과인지 구분하는 식별자), 본문, 속성을 최대 10건까지 담는다. FIFO 큐에서는 같은 MessageGroupId로 묶은 메시지만 배치에 포함한다.
  2. 부분 성공 처리요청을 한 번 보내면 응답에 Successful 배열과 Failed 배열이 온다. 실패 항목의 Id와 오류 코드(예: MessageTooLong, ThrottlingException)를 확인해 해당 항목만 골라 재시도한다.
  3. SDK 버퍼링 활용SDK의 클라이언트 측 버퍼링을 켜면, 보낼 메시지를 클라이언트 내부 버퍼에 모았다가 배치 크기에 도달하거나 설정한 시간이 지나면 자동으로 배치 요청을 보낸다. 개발자가 배치 로직을 직접 짤 필요가 없다.

수평 확장과 배치로 처리량 높이기

처리하는 소비자 수를 늘리는 수평 확장과 배치 액션을 함께 쓰면 초당 처리 메시지 수를 크게 끌어올릴 수 있다.

1상대의 출발점 확인

기존에 메시지 처리가 느리면 인스턴스 하나의 CPU·메모리를 키우는 수직 확장을 시도했지만, 비용이 급격히 늘고 단일 서버 능력에는 한계가 있었다. 또한 메시지 하나씩 요청을 보내는 방식은 요청 수가 늘어 비용이 커지고, 요청당 처리량(단위 시간당 처리하는 메시지 수)이 작아 병목이 되었다.

2질문 제기

개별 서버를 키우지 않고, 서버 수와 요청당 메시지 수를 늘려 처리량을 높일 수는 없을까?

3구조적 핵심 예시

큐를 소비하는 인스턴스(컨슈머)를 여러 대로 늘려 동시에 ReceiveMessage를 호출하게 하고, 각 인스턴스는 배치 액션으로 요청 하나에 여러 메시지를 처리한다. SQS는 분산 서비스라서 컨슈머가 많을수록 병렬 처리량이 늘고, 배치를 쓸수록 요청 수는 줄어든다.

4단계별 동작 과정

  1. 수평 확장큐를 소비하는 인스턴스 수를 늘린다. 각 인스턴스가 큐에서 메시지를 가져가므로 컨슈머가 많을수록 전체 처리 속도가 올라간다(메시지 그룹 ID에 따라 순서가 보장되는 FIFO 큐는 그룹 수와 동시성에 제약이 있다).
  2. 배치 사용각 인스턴스는 ReceiveMessage로 최대 10개 메시지를 한 번에 받고, 처리 후 DeleteMessageBatch로 한 번에 삭제한다. 같은 수의 메시지를 처리하면서 요청 수는 최대 10분의 1로 줄어든다.
  3. 지표 기반 조정큐의 가시 메시지 수(ApprroximateNumberOfMessages, 대략적으로 대기 중인 메시지 개수) 같은 CloudWatch 지표를 보고 컨슈머 수를 늘리거나 줄여, 목표 지연 시간 안에서 비용과 처리량의 균형을 맞춘다.

JMS 클라이언트로 SQS 사용

JMS(Java Message Service) 표준 인터페이스를 통해 SQS를 메시지 브로커처럼 사용할 수 있게 해 주는 클라이언트 라이브러리다.

1상대의 출발점 확인

기존 방식에서는 애플리케이션이 큐에 메시지를 넣고 빼려면 SQS 전용 API(SendMessage, ReceiveMessage 등)를 직접 호출해야 했다. 그런데 자바 진영에는 예전부터 JMS(Java Message Service, 자바 애플리케이션끼리 메시지를 주고받기 위한 표준 인터페이스)가 널리 쓰여 왔다. JMS를 쓰던 기존 코드는 사용하는 큐 제품이 바뀌면 그 제품에 맞춰 다시 작성해야 했고, SQS 전용 API는 그 표준과 달라서 JMS 기반 코드를 그대로 옮겨 쓸 수 없었다. 결과적으로 자바 애플리케이션마다 SQS 방식으로 코드를 새로 짜야 하는 부담이 있었다.

2질문 제기

JMS 표준을 쓰는 기존 자바 코드를 거의 바꾸지 않고 Amazon SQS를 사용할 수 없을까?

3구조적 핵심 예시

Amazon SQS Java Messaging Library는 JMS 표준 인터페이스(javax.jms 패키지)의 실제 구현체다. 애플리케이션은 JMS의 ConnectionFactory, Queue, MessageProducer, MessageConsumer 같은 표준 객체만 사용하고, 그 객체의 내부 구현이 SQS API 호출로 바뀌는 구조다. 예를 들어 JMS의 send()를 호출하면 그 뒤에서 실제로는 SQS의 SendMessage 요청이 나간다.

4단계별 동작 과정

  1. 연결과 큐 준비JMS ConnectionFactory를 만들 때 SQS 자격 증명(접근 키 정보)과 엔드포인트(요청을 보낼 AWS 주소)를 설정하고, JMS Connection과 Session(메시지를 주고받는 작업 단위)을 연 뒤 대상 큐를 JMS Queue 객체로 만든다.
  2. 메시지 송수신MessageProducer.send()를 호출하면 내부적으로 SQS SendMessage API가 실행되어 큐에 메시지가 저장되고, MessageConsumer.receive()를 호출하면 SQS ReceiveMessage API가 실행되어 큐에서 메시지를 가져온다.
  3. 세션 정리작업이 끝나면 Connection을 닫아 내부 SQS 클라이언트와의 네트워크 연결을 정리한다.

SQS와 IAM의 동작 방식

Amazon SQS가 IAM과 연동해 사용자·역할 같은 신원을 인증하고 권한으로 API 작업을 허용·거부하는 동작 방식

1상대의 출발점 확인

AWS 계정에는 여러 사용자와 애플리케이션이 함께 일하기 때문에, 권한이 없는 대상이 큐를 읽으면 메시지 내용이 그대로 노출된다. 그래서 SQS는 요청을 처리하기 전에 "이 요청을 보낸 대상이 이 큐에서 이 작업을 할 수 있는가"를 검사해야 한다. SQS는 큐 자체에 접근 규칙을 붙이는 방식을 제공했지만, 사용자·그룹·역할 단위로 권한을 세밀하게 통제하고 다른 AWS 서비스와 같은 방식으로 관리하려면 AWS 전체의 IAM(Identity and Access Management, 사용자와 권한을 관리하는 AWS의 공통 서비스) 체계와 연결될 필요가 있었다.

2질문 제기

누가 어떤 SQS 큐에서 어떤 작업을 할 수 있는지를 AWS 전체에서 일관된 방식으로 어떻게 결정할까?

3구조적 핵심 예시

IAM은 요청을 보낸 주체(사용자나 역할)가 가진 자격 기반 정책과, 큐에 붙은 리소스 기반 정책 두 종류의 권한을 모두 확인해서 허용 여부를 정한다. 예를 들어 어떤 IAM 사용자가 특정 큐에서 ReceiveMessage(메시지 가져오기)를 호출하면, 그 사용자의 정책과 그 큐의 접근 정책에서 모두 허용해야 작업이 성공한다.

4단계별 동작 과정

  1. 요청 접수와 주체 확인SQS API 요청이 오면 AWS가 요청을 보낸 사용자나 역할이 진짜인지 인증한 뒤, 그 주체에게 연결된 IAM 정책들을 모은다.
  2. 정책 평가권한 경계(주체가 가질 수 있는 최대 권한의 상한), 주체의 자격 기반 정책, 큐의 리소스 기반 정책, 조직 단위의 서비스 제어 정책을 모두 대조해 명시적 허용(분명히 허락하는 규칙)이 있는지 확인한다.
  3. 허용 판정과 실행어느 정책에서도 명시적 허용이 없거나 어디선가 명시적 거부가 있으면 요청을 거부하고, 명시적 허용이 확인되면 작업을 실행한다.

큐 접근 정책(리소스 기반)

큐 자체에 붙는 리소스 기반 정책으로 다른 계정이나 AWS 서비스에 큐 접근 권한을 부여하는 방법

1상대의 출발점 확인

IAM의 자격 기반 정책은 "이 사용자가 무엇을 할 수 있는가"를 사용자 쪽에 붙이는 방식이다. 그런데 SQS 큐는 다른 AWS 계정이나 다른 서비스(Lambda, SNS 등)가 접근해야 하는 경우가 있다. 사용자 쪽에서 접근 대상을 일일이 열거하기 어렵고, 큐에 접근하는 외부 주체가 내가 관리하는 대상이 아닐 수도 있다. 그래서 권한 규칙을 사용자가 아니라 큐 자체에 붙여서, 큐가 접근 가능한 대상을 직접 정하는 방식이 필요했다.

2질문 제기

큐에 접근하는 주체가 내가 관리하지 않는 다른 계정이나 서비스일 때, 그 접근을 큐 쪽에서 어떻게 허용할까?

3구조적 핵심 예시

큐 접근 정책은 큐에 첨부하는 JSON(키-값 쌍으로 데이터를 적는 형식) 문서다. 문서에 Principal(누구에게), Action(무엇을 허용할지), Resource(어느 큐인지)를 적는다. 예를 들어 특정 AWS 계정에 대해 SendMessage(메시지 보내기)를 허용하는 정책 조각을 큐에 붙이면, 그 계정이 이 큐에 메시지를 보낼 수 있게 된다.

4단계별 동작 과정

  1. 정책 작성JSON 문서에 허용할 주체(Principal), 허용할 작업(Action), 대상 큐(Resource)를 채워 만든다.
  2. 큐에 첨부콘솔의 접근 정책 편집 화면이나 SetQueueAttributes API(큐의 속성을 설정하는 API)로 그 문서를 큐 속성에 저장한다.
  3. 평가와 적용이후 그 큐로 들어오는 요청마다 IAM이 이 문서를 정책으로 읽어, 적힌 조건에 맞는 요청에만 권한을 준다.

자격 기반 정책과 예제

IAM 사용자·역할·그룹에 붙이는 자격 기반 정책으로 SQS 작업을 제어하는 방법과 실제 정책 예제

1상대의 출발점 확인

큐 접근 정책은 큐마다 규칙을 따로 붙여야 해서, 큐가 많아지면 관리할 규칙도 그만큼 늘어난다. 하지만 회사에서는 "개발자 그룹은 모든 큐에서 메시지를 읽는다"처럼 역할 단위로 권한을 관리하고 싶은 경우가 더 많다. 큐마다 규칙을 적는 방식으로는 그룹 구성원이 새로 바뀌거나 큐가 추가될 때마다 정책을 고쳐야 하므로, 권한을 주체(사용자·그룹·역할) 쪽에 붙여 한 번에 통제할 방법이 필요했다.

2질문 제기

큐가 아니라 사용자나 역할 쪽에 권한을 붙여서 여러 큐를 한 번에 통제할 수는 없을까?

3구조적 핵심 예시

자격 기반 정책은 IAM 사용자·그룹·역할에 첨부하는 JSON 문서다. 예를 들어 "sqs:ReceiveMessage(메시지 가져오기)"와 "sqs:DeleteMessage(메시지 삭제하기)"를 특정 큐 ARN(큐를 가리키는 고유 주소)에 대해 허용하는 정책을 개발자 그룹에 붙이면, 그 그룹의 모든 구성원이 해당 큐에서 메시지를 받아 지울 수 있다.

4단계별 동작 과정

  1. 정책 작성Effect(허용할지 거부할지), Action(작업), Resource(대상 큐의 ARN)를 담은 JSON 문서를 만든다.
  2. 주체에 첨부만든 정책을 IAM 콘솔에서 대상 사용자·그룹·역할에 연결한다.
  3. 요청 시 평가그 주체가 큐 API를 호출하면 IAM이 첨부된 정책을 확인해, 허용 범위 안의 작업만 통과시킨다.

사용자 지정 정책과 평가 논리

Access Policy Language로 사용자 지정 정책을 만들고 명시적 허용·명시적 거부·기본 거부의 우선순위로 접근을 평가하는 논리

1상대의 출발점 확인

기본적인 허용 정책만으로는 "특정 시간대에만", "특정 태그가 붙은 큐만" 같은 조건이 있는 권한을 표현할 수 없다. 또 하나의 SQS 요청이 여러 정책과 여러 규칙에 동시에 걸릴 수 있는데, 허용 규칙과 거부 규칙이 섞여 있을 때 어느 쪽이 이기는지 기준이 없으면 보안 관리가 불안정해진다. 그래서 조건을 적을 수 있는 정책 문법과, 정책들이 충돌할 때의 최종 판정 규칙이 필요했다.

2질문 제기

여러 정책에 허용과 거부가 섞여 있을 때, SQS 요청의 최종 허용 여부는 어떤 기준으로 결정될까?

3구조적 핵심 예시

사용자 지정 정책은 IAM의 Access Policy Language라는 정책 문법으로 조건(Condition)까지 적을 수 있는 JSON 문서다. 평가 규칙은 명시적 거부(분명히 거절하는 규칙)가 최우선이고, 명시적 거부가 없으면 명시적 허용(분명히 허락하는 규칙)이 있는지 보며, 명시적 허용도 없으면 기본적으로 거부하는 방식으로 정해져 있다.

4단계별 동작 과정

  1. 명시적 거부 확인요청에 걸린 어떤 정책 규칙에서든 명시적 Deny가 있으면 그 즉시 거부로 판정한다.
  2. 명시적 허용 확인명시적 거부가 없으면 주체 정책, 리소스 정책, 권한 경계 등에서 명시적 Allow가 하나라도 있는지 확인한다.
  3. 기본값 적용명시적 허용이 하나도 없으면 기본적으로 거부로 처리하고, 허용이 확인되면 요청을 실행한다.

속성 기반 접근 제어(ABAC)

큐 태그를 IAM 정책의 조건으로 사용해 태그 일치에 따라 접근을 제어하는 속성 기반 접근 제어(ABAC)

1상대의 출발점 확인

기존 방식에서는 큐에 접근할 수 있는 대상을 정책에 큐 목록으로 일일이 적었다. 큐가 수백 개로 늘어나면 정책 문서가 방대해지고, 큐가 새로 생길 때마다 관련 정책을 찾아 고쳐야 했다. 사용자가 바뀔 때도 사용자마다 개별 정책을 다르게 만들어 주어야 하는 부담이 있었다. 그래서 정책에 구체적인 큐 이름을 나열하는 대신, 사용자와 큐에 붙은 속성(태그)이 서로 맞는지 보는 방식이 필요했다.

2질문 제기

큐가 많아져도 정책에 큐 목록을 일일이 적지 않고 권한을 관리할 수는 없을까?

3구조적 핵심 예시

ABAC(Attribute-Based Access Control, 속성 기반 접근 제어)는 사용자와 큐에 붙은 태그(key-value 쌍)를 정책의 조건으로 쓰는 방식이다. 예를 들어 사용자에게 "project=alpha" 태그를, 큐에도 "project=alpha" 태그를 붙여 두고 "요청한 큐의 project 태그가 내 project 태그와 같으면 허용"이라는 조건 하나를 정책에 적는다. 그러면 큐가 새로 추가되어도 같은 태그만 붙이면 자동으로 권한이 적용된다.

4단계별 동작 과정

  1. 태그 부여IAM 사용자·역할과 SQS 큐에 동일한 의미의 태그(예: project=alpha)를 각각 붙인다.
  2. 조건식 정책 작성정책의 Condition에 "aws:ResourceTag/project와 aws:PrincipalTag/project가 일치하면" 같은 조건을 적어 큐 작업을 허용한다.
  3. 일치 판정큐 API 요청 시 IAM이 요청자의 태그와 대상 큐의 태그를 비교해, 조건이 맞는 큐에만 권한을 부여한다.

5본질 요약

정책에 큐 이름 대신 태그 일치 조건을 적어서, 같은 태그를 가진 사용자와 큐 사이에 권한이 자동으로 성립하게 만드는 것

저장·전송 중 데이터 암호화

SSE-SQS나 SSE-KMS로 저장 데이터를 암호화하고 HTTPS/TLS로 전송 중 데이터를 보호하는 암호화 체계

1상대의 출발점 확인

기본 상태의 SQS 큐는 메시지를 받아 저장하고, 소비자가 요청하면 그 메시지를 전달한다. 여기서 암호화 설정을 하지 않으면 메시지 본문은 큐 저장 공간에 평문(원래 내용 그대로)으로 남고, 송수신 구간에서도 특별한 보호 없이 네트워크를 통해 이동한다. 금융 정보나 개인정보처럼 민감한 데이터를 다루는 조직은 이 상태로는 규정 요구를 충족할 수 없고, 저장 매체나 네트워크 구간에서 내용이 노출되면 그대로 유출로 이어진다.

2질문 제기

메시지가 큐에 저장되는 동안과 네트워크로 이동하는 동안, 그 내용을 안전하게 숨기려면 어떻게 해야 하는가?

3구조적 핵심 예시

큐에 SSE-KMS(서버 측 암호화 방식을 KMS 키로 쓰는 설정)를 켜두면, 메시지가 큐에 도착하는 순간 AWS KMS(암호화 키를 관리하는 서비스)가 가진 키로 메시지 본문을 자동으로 암호화해 저장한다. 저장 공간에는 암호문만 남고, 소비자가 메시지를 받을 때 같은 키로 복호화되어 원래 내용이 돌아온다. 전송 구간은 HTTPS(TLS) 연결을 사용하면 메시지가 네트워크 위에서 암호화된 채로 이동하므로, 큐에 도착하기 전이나 나간 후에 가로채여도 내용이 드러나지 않는다.

4단계별 동작 과정

  1. 저장 시 암호화전송자가 메시지를 보내면 큐 서버가 저장 지점에서 KMS 키로 메시지 본문을 암호화해 디스크에 기록한다.
  2. 수신 시 복호화소비자가 메시지를 받아가면 서버가 KMS 키로 복호화해 원문을 전달하므로, 애플리케이션 코드는 암호화 여부를 의식하지 않아도 된다.
  3. 키 관리KMS가 암호화 키의 생성·교체·회전을 대신 관리해, 개발자가 키를 직접 다루거나 저장하지 않아도 키 노출 위험이 줄어든다.

2질문 제기

3구조적 핵심 예시

  2. 규정 준수 확인SQS가 지원하는 규정 준수 프로그램(예: SOC, PCI DSS) 목록을 확인해 조직 요구에 맞는 보호 조치(암호화, 로깅, 접근 통제)를 적용하고 감사 증빙으로 남긴다.
  3. 복원력 설계리전별 큐 운영과 함께 재시도·재전송 전략을 세워 한 리전에 장애가 나도 다른 경로나 재시도로 메시지 처리가 이어지도록 한다.

CloudWatch 메트릭과 알람

Amazon SQS가 큐별로 노출하는 CloudWatch 메트릭(예: ApproximateNumberOfMessagesVisible, SentMessageSize)을 조회하고 임계값 기반 알람을 설정해 큐 상태를 지속적으로 감시하는 방법.

1상대의 출발점 확인

큐에 메시지를 넣고 소비자가 처리하는 동안, 큐에 메시지가 얼마나 쌓였는지·메시지가 얼마나 자주 도착하는지·처리가 얼마나 걸리는지를 아무도 보지 않으면, 어느 순간 메시지가 급증해 대기 시간이 길어져도 알아채지 못한다. 문제가 커진 뒤에야 로그를 뒤져 원인을 찾는 식의 대응이 반복되고, 정상일 때와 이상일 때의 차이를 판단할 기준(임계값)조차 없다.

2질문 제기

큐의 상태(쌓인 메시지 수, 메시지 크기, 처리 지연)를 계속 관찰하고, 이상이 생기면 바로 알려주려면 어떻게 해야 하는가?

3구조적 핵심 예시

SQS는 큐마다 ApproximateNumberOfMessagesVisible(현재 소비자에게 보이는 대기 메시지 수) 같은 메트릭을 CloudWatch에 자동으로 보낸다. 여기에 CloudWatch 알람을 연결해 "대기 메시지 수가 10,000개를 넘으면 알림"으로 설정해두면, 평소에는 아무도 모니터링 화면을 보지 않아도 임계값을 넘는 순간 담당자에게 통보가 간다.

4단계별 동작 과정

  1. 메트릭 발행SQS가 큐별 메트릭(대기 메시지 수, 메시지 크기, 처리 시간 등)을 CloudWatch에 정해진 주기로 자동 전송한다.
  2. 알람 설정CloudWatch 알람이 특정 메트릭의 임계값(예: 대기 메시지 10,000개)을 연속으로 초과하면 알람 상태로 전환한다.
  3. 통보와 후속 조치알람이 울리면 SNS(알림 서비스)를 통해 이메일·문자로 담당자에게 알리고, 필요하면 소비자 인스턴스를 늘리는 등의 자동 조치에 연결한다.

5본질 요약

2질문 제기

큐에 대한 모든 API 호출이 누구의 어떤 자격으로 언제 일어났는지 기록으로 남기려면 어떻게 해야 하는가?

3구조적 핵심 예시

CloudTrail을 활성화하면 모든 SQS API 호출이 이벤트로 기록된다. 예를 들어 어떤 IAM 사용자가 SendMessage를 호출하면 CloudTrail 이벤트에 "누가(호출 주체), 언제(시간), 무엇을(API 동작), 어디에(대상 큐), 결과(성공·실패)"가 남아, 나중에 감사 로그에서 그 호출을 그대로 재구성할 수 있다.

4단계별 동작 과정

  1. 이벤트 기록사용자나 서비스가 SQS API를 호출하는 순간 CloudTrail이 호출 정보(주체, 동작, 대상, 결과)를 이벤트로 캡처한다.
  2. 로그 저장캡처된 이벤트는 S3 버킷에 로그 파일로 쌓여 오래 보관되며, 필요할 때 꺼내 검색할 수 있다.
  3. 감사·조사보안 담당자가 저장된 로그를 검색해 특정 시간대의 특정 큐에 대한 모든 API 호출을 재구성하고, 이상 호출 여부를 판단해 조사에 사용한다.

오류 처리와 문제 메시지 포착

API 요청 오류(일시적 오류 포함)를 재시도로 처리하고, 연속 실패한 메시지를 문제 원인 분석용으로 별도 보관해 포착하는 방법.

1상대의 출발점 확인

메시지를 보내거나 받을 때 네트워크 끊김이나 서버 과부하 같은 일시적 오류가 나면 그 호출은 그냥 실패로 끝난다. 실패한 호출을 재시도하지 않으면 메시지가 유실되고, 소비자가 처리에 실패한 메시지를 삭제해버리면 그 메시지는 영영 사라진다. 반대로 실패한 메시지를 계속 큐에 남겨두면 같은 메시지가 반복해서 실패하며 정상 메시지 처리를 막는다. 오류를 별도로 모아두지 않으면 어디서 무엇이 실패했는지도 알 수 없다.

2질문 제기

일시적 오류로 실패한 처리를 안전하게 재시도하고, 계속 실패하는 메시지를 찾아 원인을 분석하려면 어떻게 해야 하는가?

3구조적 핵심 예시

소비자가 메시지를 처리하다 예외가 나면 메시지를 삭제하지 않고 그대로 둔다. 가시성 제한 시간(메시지가 다른 소비자에게 잠시 보이지 않는 시간)이 지나면 같은 메시지가 큐에 다시 나타나므로 재시도가 된다. 그런데도 정해진 최대 수신 횟수를 넘기면 그 메시지는 데드레터 큐(처리 실패 메시지를 모아두는 별도 큐)로 이동한다. 정상 큐는 계속 돌아가고, 실패 메시지는 따로 모여 원인 분석 대상이 된다.

4단계별 동작 과정

  1. 실패 인지와 재시도소비자가 처리를 마치기 전에 오류가 나면 메시지를 삭제하지 않아, 가시성 제한 시간 후 같은 메시지가 큐에 다시 나타나 재시도된다.
  2. 임계 초과 시 이관재시도 횟수가 큐에 설정된 최대 수신 횟수를 넘으면 메시지가 데드레터 큐로 이동해 정상 메시지 처리를 방해하지 않는다.
  3. 분석과 복구데드레터 큐에 쌓인 메시지를 조사해 원인(메시지 형식 오류, 종속 서비스 장애 등)을 찾아 고치고, 복구 가능한 메시지는 다시 원래 큐로 되돌려 처리한다.

5본질 요약

문제 증상별 트러블슈팅

Access denied, API 오류, DLQ redrive, FIFO 스로틀링, ReceiveMessage 미반환, 네트워크 오류 등 증상별 원인과 해결 절차를 안내하는 공식 트러블슈팅 가이드.

1상대의 출발점 확인

큐를 쓰다 문제가 생기면(접근 거부, API 오류, 메시지가 안 보임, 처리 지연 등) 어디서부터 확인해야 할지 막막하다. 관련 설정이 권한, 정책, 암호화 키, 네트워크, 소비자 코드 등 여러 곳에 흩어져 있어, 증상만으로 원인을 찾으려면 로그와 설정을 하나씩 뒤져야 하고, 우선순위가 없어 같은 조사를 반복하게 된다.

2질문 제기

특정 증상(예: AccessDenied, ReceiveMessage가 메시지를 주지 않음, FIFO 지연)이 나타났을 때 가장 빠르게 원인을 좁히려면 무엇부터 확인해야 하는가?

3구조적 핵심 예시

"AccessDenied" 오류가 나면 공식 트러블슈팅 절차는 먼저 접근 정책에 허용이 명시되어 있는지, IAM 정책과 큐 정책이 겹치면서 명시적 거부가 없는지, 큐에 암호화를 켰다면 KMS 키 정책에서 그 키 사용이 허용되었는지를 순서대로 확인하라고 안내한다. 이렇게 증상별 확인 순서가 정리되어 있어, 처음 마주한 문제라도 조사 지점을 곧바로 찾을 수 있다.

4단계별 동작 과정

  1. 증상 분류발생한 문제(권한 오류, API 오류, 메시지 미반환, 대기 시간 증가 등)를 증상 그룹으로 구분해 어느 절차를 따를지 정한다.
  2. 원인 후보 확인증상별 체크리스트를 따라 정책·설정·네트워크·소비자 코드 순서로 원인 후보를 하나씩 점검해 실제 원인을 좁힌다.
  3. 조치와 검증발견된 원인(정책 수정, 엔드포인트 변경, 소비자 재시도 로직 수정 등)을 고친 뒤 동일 증상이 재현되지 않는지 확인하고 정상 동작을 검증한다.

기능·역량 총람

SQS 가 제공하는 큐 유형, 전달 보장, 암호화, DLQ, 폴링, 가시성 제한 시간 등 기능 전체를 한눈에 정리한 개요.

1상대의 출발점 확인

기존 방식에서 애플리케이션끼리는 직접 통신했다. 보내는 쪽이 받는 쪽에 요청을 보내고 응답을 기다렸다. 이 방식은 받는 쪽이 느려지거나 잠시 다운되면 보내는 쪽도 함께 기다려야 하고, 트래픽이 몰리면 처리가 밀려 전체 응답 속도가 느려졌다. 게다가 두 애플리케이션이 같은 시간에 모두 살아 있어야 통신이 성립했다. 한쪽이 꺼져 있으면 메시지는 그냥 유실되었다. 이런 구조에서는 서로의 장애가 그대로 전파되고, 처리 속도가 다른 두 시스템을 자연스럽게 잇기 어렵다.

2질문 제기

보내는 쪽과 받는 쪽이 서로의 상태와 관계없이 메시지를 주고받으려면 무엇이 필요한가?

3구조적 핵심 예시

실제 동작 방식은 큐라는 중간 저장소를 두는 것이다. 보내는 애플리케이션은 메시지를 큐에 넣고 즉시 자기 일로 돌아간다. 받는 애플리케이션은 자기 페이스대로 큐에서 메시지를 꺼내 처리한다. 받는 쪽이 잠시 꺼져 있어도 메시지는 큐에 그대로 보관되고, 복귀한 뒤 꺼내면 된다. 연결 상태를 유지하는 일도, 두 쪽이 동시에 켜져 있을 필요도 없다.

4단계별 동작 과정

  1. 전송생산자(메시지를 보내는 애플리케이션)가 메시지 하나를 큐로 보낸다. 큐는 그 메시지를 저장한다.
  2. 보관큐는 소비자(메시지를 받는 애플리케이션)가 꺼낼 때까지 메시지를 보관한다. 기본 보관 기간은 4일이고 최대 14일까지 늘릴 수 있다.
  3. 수신·삭제소비자가 큐에서 메시지를 꺼내 처리하고, 처리가 끝나면 삭제 요청을 보낸다. 삭제가 완료되어야 큐에서 빠진다.

메시지 처리 타이밍과 필요 리소스

메시지를 보낸 뒤 실제로 꺼내 처리할 수 있게 되는 타이밍과 처리에 필요한 소비자·큐 같은 리소스를 설명하는 원칙.

1상대의 출발점 확인

기존 방식에서 소비자는 큐를 확인할 때마다 요청을 보냈고, 큐가 비어 있으면 빈 응답만 받고 끝났다. 이렇게 메시지 존재 여부와 상관없이 짧게 반복 조회하는 방식(short polling)은 요청 수가 많아지고, 메시지가 도착했는지 확인하기 위해 계속 호출해야 했다. 또 메시지가 언제 들어올지 모르는 상태에서는 소비자 리소스를 몇 개나 준비해야 할지 정하기 어려웠고, 너무 적게 두면 메시지가 쌓이고 너무 많이 두면 리소스가 낭비됐다.

2질문 제기

메시지가 언제 도착할지 모르는 상황에서 쌓임 없이 제때 처리하려면 언제, 얼마나 많은 리소스로 큐를 조회해야 하는가?

3구조적 핵심 예시

실제 동작 방식은 long polling(대기 조회)이다. 소비자가 큐를 조회할 때 대기 시간을 함께 지정하면, 큐가 비어 있어도 즉시 빈 응답을 주지 않고 그 시간 동안 기다렸다가 메시지가 도착하는 순간 그 메시지를 내려준다. 빈 응답이 줄어들고, 메시지는 도착 즉시 꺼낼 수 있게 된다.

4단계별 동작 과정

  1. 대기 조회소비자가 ReceiveMessage 요청을 보낼 때 대기 시간(WaitTimeSeconds)을 지정한다. 큐에 메시지가 없으면 지정한 시간만큼 응답을 미룬다.
  2. 도착·전달대기 중 메시지가 큐에 들어오면 즉시 그 메시지를 소비자에게 전달한다. 대기 시간이 끝나도 없으면 빈 응답을 준다.
  3. 리소스 조정유입 속도가 처리 속도를 앞서면 소비자(메시지를 처리하는 작업자) 개수를 늘린다. 폴링 자체의 부담이 낮아서, 소비자가 많아지는 비용보다 메시지가 쌓여 지연되는 문제를 막는 것이 우선이다.

큐·메시지·정책 한도(Quotas)

큐 수, 메시지 크기·보존 기간, 정책 크기 등 SQS 사용 시 지켜야 하는 서비스 한도를 모아둔 규격.

1상대의 출발점 확인

기존 방식에서는 한도를 생각하지 않고 시스템을 설계하는 경우가 많았다. 큐를 몇 개든 만들 수 있고, 메시지도 원하는 크기로 보낼 수 있다고 가정했다. 그런데 SQS에는 리전별 큐 개수, 메시지 최대 크기, 정책 최대 크기 같은 고정된 한도가 있고, 이를 넘기는 요청은 거부된다. 설계 단계에서 이 한도를 모르면 운영 중에 예기치 않게 메시지 전송이 실패하거나 큐를 더 만들 수 없는 상황에 부딪힌다.

2질문 제기

하나의 계정과 리전에서 큐와 메시지를 실제로 얼마나 만들고, 얼마나 크게 보낼 수 있는가?

3구조적 핵심 예시

실제 한도 하나만 보면, 메시지 하나는 최대 256KB까지만 보낼 수 있다. 그보다 큰 페이로드(실제 데이터)를 전달해야 하면 메시지에 큰 데이터를 직접 넣지 않고, 별도 저장소에 데이터를 두고 그 위치를 가리키는 참조만 메시지에 담아 보낸다. 큐 개수도 리전당 기본 10,000개까지 만들 수 있고, 이는 요청하면 늘릴 수 있다.

4단계별 동작 과정

  1. 한도 확인설계 시점에 리전별 큐 개수, 메시지 최대 크기(256KB), 보관 기간(1~14일, 기본 4일), 정책 최대 크기(32KB) 같은 한도를 문서에서 확인한다.
  2. 초과 시도한도를 넘는 요청(예: 300KB 메시지 전송)은 거부되어 오류를 돌려받는다. 이 경우 재시도로 해결되지 않으므로 설계를 바꿔야 한다.
  3. 조정 요청큐 개수 같은 일부 한도는 AWS에 증가를 요청하면 늘어난다. Service Quotas 콘솔에서 현재 한도와 사용량을 확인하고 조정할 수 있다.
