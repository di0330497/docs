1DynamoDB라는 물건의 정체테이블·항목·키가 무엇인지 모르면 이후의 모든 조작·설계 이야기가 성립하지 않는다.62내부에서 무슨 일이 일어나는가파티션과 일관성 모델을 알아야 용량·인덱스·모델링의 이유가 설명된다.43처리 용량과 요금 모델모든 읽기·쓰기가 용량 단위로 환산되므로, 조작을 배우기 전에 비용·스로틀의 단위를 먼저 잡아야 한다.54테이블과 항목 조작하기대상(테이블·항목)을 먼저 정의했으니, 이제 그 대상을 만들고 읽고 쓰는 기본 API를 익힌다.75데이터 조회하기항목 단위 조작 다음 단계로, 여러 항목을 한 번에 찾아오는 방법과 그 비용 구조를 다룬다.56보조 인덱스로 조회 경로 넓히기기본 키만으로 답할 수 없는 질의가 나오는 시점이 인덱스를 배울 시점이다.67트랜잭션·TTL·변경 데이터 캡처단일 항목 조작을 넘어서는 원자성·수명·이벤트 전파를 다룬다. 앞의 API와 용량 개념이 전제된다.78데이터 모델링API를 다 익힌 다음에야, 그 API로 무엇을 어떻게 담을지 설계할 수 있다.89애플리케이션에서 쓰기와 캐싱설계가 끝난 모델을 실제 코드로 옮기고, 읽기 지연을 더 줄여야 할 때 캐시를 붙인다.410다중 리전과 백업·복구단일 리전 운영이 손에 익은 뒤라야 복제·복구의 트레이드오프가 이해된다.511보안동작하는 시스템이 생긴 다음에 누가 무엇을 할 수 있는지를 잠근다.512운영·통합·한계만들고 지킨 시스템을 관측하고, 다른 서비스와 잇고, 한계와 비용을 관리하는 마지막 층.8

1DynamoDB라는 물건의 정체01-01

DynamoDB란 무엇인가: 서버리스 완전관리형 NoSQL

AWS가 서버 관리 없이 어떤 규모에서도 한 자릿수 밀리초 성능을 내주는 완전관리형 서버리스 NoSQL 키-값/문서 데이터베이스다.

1상대의 출발점 확인

전통적인 애플리케이션 개발에서는 서버 인프라를 구성하고, 데이터베이스를 설치·관리하며, 미래 트래픽에 대비해 용량을 미리 계획해야 한다. 성능 튜닝, 백업, 보안 설정 등 운영 작업도 개발팀의 책임이다. 이렇게 되면 트래픽 증가 예측이 어려워 용량 부족이나 과다 할당이 발생하고, 인프라 확장 시간이 걸리며, 관리 작업으로 개발 속도가 떨어진다.

2질문 제기

서버 관리 책임을 완전히 없애면서도 어떤 규모의 트래픽에서도 일정한 성능을 낼 수 있는 데이터베이스는 없을까?

3구조적 핵심 예시

데이터를 파티션 키라는 식별자로 구조화하면, AWS가 그 구조에 따라 인프라를 자동으로 확장하고 관리해준다. 예를 들어 사용자 ID를 파티션 키로 설정하면, AWS가 사용자 ID별로 데이터를 여러 서버에 나눠 저장하고, 사용자가 증가하면 자동으로 서버를 추가한다.

4단계별 동작 과정

  1. AWS 관리 책임 이전서버 구매·설정, 데이터베이스 설치, 용량 계획, 백업, 보안 패치를 AWS가 완전히 관리
  2. 성능 보장테이블의 파티션 키 설계에 따라 한 자릿수 밀리초(밀리초는 1000분의 1초) 응답 시간을 일관되게 제공
  3. 자동 확장데이터 용량이 늘거나 요청이 증가하면 AWS가 자동으로 인프라를 확장해 성능 유지

5본질 요약

1DynamoDB라는 물건의 정체01-02

관계형 데이터베이스와 무엇이 다른가

미리 정한 접근 패턴에 맞춰 데이터를 배치하고 조인·정규화 대신 키 기반 조회로 예측 가능한 성능을 얻는 것이 SQL과의 근본 차이다.

1상대의 출발점 확인

SQL 데이터베이스는 데이터 중복을 제거하기 위해 테이블을 정규화하고, 필요할 때 여러 테이블을 조인해서 정보를 조합한다. 이 방식은 매우 유연해서 미리 예상하지 못한 다양한 쿼리도 처리할 수 있다. 하지만 조인이 많아질수록 성능이 떨어지고, 응답 시간을 정확히 예측하기 어려우며, 대규모 트래픽에서 성능 최적화가 복잡하다.

2질문 제기

성능을 완벽하게 예측하면서도 필요한 모든 조회를 빠르게 처리할 수 있을까?

3구조적 핵심 예시

  2. 데이터 구조 결정각 조회 패턴에 최적화된 키 구조(파티션 키와 정렬 키)로 데이터 배치 (조인 불필요, 중복 허용)
  3. 성능 보증키 기반 조회는 항상 일정한 시간에 완료되므로 응답 시간을 정확히 예측 가능

  2. 파티션 내 정렬정렬 키가 있으면 같은 파티션 내에서 정렬 키 값 순서대로 항목 배열 (범위 쿼리 시 연속된 항목들을 빠르게 검색 가능)

DynamoDB는 파티션 키를 해싱해 데이터를 여러 파티션(저장 단위)에 나눠 저장하고, 데이터가 늘거나 트래픽이 몰리면 파티션을 자동으로 분할·확장한다.

1상대의 출발점 확인

SQL 데이터베이스는 일반적으로 한 대 또는 몇 대 서버에 전체 데이터를 저장하고, 용량 부족이나 성능 저하가 발생하면 데이터를 여러 서버에 나누는 샤딩(분할)을 수동으로 설계하고 구현해야 한다. 샤딩 키 선택, 데이터 재분배, 일관성 유지 등 복잡한 로직을 개발팀이 직접 관리해야 하고, 초기 샤딩 계획이 맞지 않으면 재설계가 어렵다.

2질문 제기

3구조적 핵심 예시

  3. 자동 분할 및 확장병목 파티션이 감지되면 두 개로 분할하고 데이터를 자동 재배치해 부하 분산 (사용자는 중단 없이 계속 접근 가능)

3구조적 핵심 예시

사용자의 주문 정보를 저장한다고 하자. 파티션 키는 user_id='user123'이고, 각 주문마다 order_id와 items 목록을 저장한다. 항목 크기는 속성 이름 "user_id"(7바이트) + "123"(3바이트) + "order_id"(8바이트) + "001"(3바이트) + "items"(5바이트) + 실제 items 데이터의 바이트 합으로 계산된다.

4단계별 동작 과정

  1. 속성 이름 길이 측정모든 속성 이름의 바이트 길이를 더함 (예: "order_id" = 8바이트)
  2. 속성 값 길이 측정각 속성의 값을 바이트로 인코딩한 길이를 더함 (문자열, 숫자, 바이너리 등 각 타입별로 계산)
  3. 총합 = 항목 크기속성 이름과 값의 바이트 합이 그 항목의 크기가 되며, 이 값이 400KB를 넘으면 저장 불가

읽기 일관성 - 최종 일관성과 강한 일관성

기본 읽기는 복제 지연으로 방금 쓴 값이 안 보일 수 있는 최종 일관성이고, 강한 일관성 읽기는 최신 값을 보장하지만 비용과 지연이 더 크다.

1상대의 출발점 확인

전통 데이터베이스는 쓰기가 완료되면 모든 읽기가 즉시 최신 값을 본다. DynamoDB는 데이터를 여러 서버에 복제해 저장하는데, 복제에 시간이 걸린다. 기본 읽기 요청은 가장 가까운 서버에서만 읽으므로 복제되지 않은 이전 값을 볼 수 있다.

2질문 제기

방금 쓴 데이터를 읽을 때 항상 최신 값을 봐야 하는가, 아니면 약간 지난 값을 봐도 괜찮은가?

3구조적 핵심 예시

user_id='john'의 balance를 100에서 150으로 업데이트했다. 기본 읽기 요청이 오면 아직 100이 적힌 서버에서 읽을 수 있다. 강한 일관성 읽기를 요청하면 모든 서버가 150으로 업데이트될 때까지 기다렸다가 읽는다.

4단계별 동작 과정

  1. 최종 일관성 읽기(기본값)가장 빠른 서버에서 즉시 읽고 반환하며, 만약 그 서버가 아직 업데이트되지 않았으면 이전 값을 반환할 수 있음
  2. 강한 일관성 읽기모든 복제본(replica)이 같은 값을 가질 때까지 기다렸다가 읽으므로 항상 최신 값을 보장하지만, 응답 시간이 더 길고 비용이 2배 더 듦
  3. 선택 기준금융 거래처럼 정확성이 중요하면 강한 일관성, 조회·추천처럼 약간 지난 데이터 괜찮으면 최종 일관성 선택

DynamoDB API 지형도

제어 플레인(테이블 생성·변경), 데이터 플레인(항목 CRUD·Query·Scan), 스트림·트랜잭션 API로 나뉘는 DynamoDB 작업 전체 지도.

1상대의 출발점 확인

데이터베이스 API는 보통 "쿼리 실행"이라는 단순한 개념으로 통일된다. DynamoDB는 데이터 저장·조회 외에도 테이블 생성·확장, 스트림 모니터링, 다중 항목 트랜잭션 등 다양한 작업을 지원하므로, 각 작업이 어떤 API 카테고리에 속하는지 이해해야 효율적으로 사용할 수 있다.

2질문 제기

DynamoDB에서 테이블 관리, 데이터 읽기·쓰기, 실시간 모니터링, 다중 항목 보장을 각각 어떻게 수행하는가?

3구조적 핵심 예시

애플리케이션이 처음 시작될 때 CreateTable 같은 제어 플레인 API로 테이블을 만든다. 실행 중에는 PutItem/GetItem 같은 데이터 플레인 API로 항목을 저장·조회한다. 여러 항목을 동시에 변경해야 할 때는 TransactWriteItems 트랜잭션 API를 쓴다. 항목이 바뀔 때마다 감지하려면 DynamoDB Streams 스트림 API를 활성화한다.

4단계별 동작 과정

  1. 제어 플레인(Control Plane)CreateTable, UpdateTable, DeleteTable 등으로 테이블 생성·스키마 변경·삭제를 담당
  2. 데이터 플레인(Data Plane)PutItem, GetItem, UpdateItem, Query, Scan 등으로 항목의 CRUD(생성·읽기·변경·삭제) 작업을 담당
  3. 스트림·트랜잭션 APIStreams로 항목 변경을 실시간 감지하고, TransactWriteItems/TransactGetItems로 여러 항목에 걸친 원자적(all-or-nothing) 변경을 보장

읽기·쓰기 용량 단위(RCU/WCU) 소비 규칙

DynamoDB가 요청을 처리할 때 쓰는 계량 단위로, 읽기는 4KB·쓰기는 1KB 단위로 반올림해 계산하며 강력한 일관성 읽기나 트랜잭션은 더 많이 소비한다.

1상대의 출발점 확인

전통 데이터베이스는 보통 "서버 몇 대를 구입하면 처리 가능한 요청이 정해진다"는 고정 개념이다. DynamoDB는 모든 요청이 같은 비용이 아니다. 4KB를 읽는 것과 1KB를 쓰는 것이 다른 비용을 소비하고, 강한 일관성 읽기는 최종 일관성 읽기의 2배 용량을 소비한다.

2질문 제기

DynamoDB에서 한 번의 읽기나 쓰기 요청이 실제로 얼마나 많은 용량 단위를 소비하는가?

3구조적 핵심 예시

3KB 크기의 항목을 1회 읽으면 RCU 1개를 소비한다. 5KB 항목을 읽으면 올림하여 RCU 2개 소비한다. 800바이트 항목을 1회 쓰면 WCU 1개를 소비한다. 강한 일관성 읽기는 이 수치를 2배로 만든다.

4단계별 동작 과정

  1. 읽기 단위 계산요청한 항목 크기를 4KB 단위로 올림 (예: 3KB = 1 RCU, 5KB = 2 RCU)
  2. 쓰기 단위 계산요청한 항목 크기를 1KB 단위로 올림 (예: 800B = 1 WCU, 1.5KB = 2 WCU)
  3. 일관성 수준 가중치강한 일관성 읽기는 최종 일관성 읽기의 2배 RCU 소비, 트랜잭션 요청은 각각 2배 소비

프로비저닝 모드는 미리 "초당 읽기 100개, 쓰기 50개"라고 지정해놓고 그만큼 매달 과금한다. 트래픽이 변동이 큰 서비스는 피크 시간을 대비해 과량 프로비저닝해야 하거나, 트래픽이 적을 때는 낭비가 발생한다.

2질문 제기

사용 패턴을 미리 알 수 없거나 트래픽이 불규칙할 때 DynamoDB 비용을 최소화하려면 어떻게 해야 하는가?

3구조적 핵심 예시

온디맨드 모드 테이블에서 어느 시간대에는 읽기 요청 10개, 어느 시간대에는 1000개가 올 수 있다. 각 시간 실제로 처리한 요청 건수만큼만 과금된다. 읽기 1건에 0.25달러/백만 건, 쓰기 1건에 1.25달러/백만 건 정도의 요금이 청구된다.

4단계별 동작 과정

  1. 용량 미리 지정 안 함테이블 생성 시 초당 처리량 수치를 정하지 않음
  2. 요청 도착 시마다 계량각 요청이 들어올 때마다 RCU/WCU를 소비하고, AWS가 자동으로 필요한 만큼 리소스를 할당함
  3. 실제 사용량 기준 과금매월 청구 시 실제로 처리한 읽기·쓰기 요청 건수만 과금

프로비저닝 모드와 Auto Scaling·예약 용량

초당 처리량(RCU/WCU)을 미리 정해두고 그만큼 과금하는 모드로, Auto Scaling으로 사용률에 따라 자동 조정하고 예약 용량으로 장기 할인받을 수 있다.

1상대의 출발점 확인

온디맨드는 유연하지만 고정 트래픽이 많을 때는 비쌀 수 있다. 트래픽을 예측할 수 있고 안정적이면 미리 용량을 정해두고 할인받는 게 낫지만, 그럼 트래픽 스파이크나 감소에 대응하려면 수동으로 조정해야 한다.

2질문 제기

예측 가능한 트래픽을 가진 서비스에서 온디맨드보다 저렴하면서도 갑작스런 증가에 대응하려면?

3구조적 핵심 예시

소셜 미디어 앱이 매일 10시~20시에 읽기 1000 RCU, 쓰기 200 WCU가 필요하고, 야간에는 읽기 100 RCU, 쓰기 20 WCU면 충분하다. 프로비저닝 모드로 이를 설정한 후, Auto Scaling 규칙을 "사용률 70%를 넘으면 용량을 15% 증가, 30% 이하로 내려가면 30% 감소"로 설정한다.

4단계별 동작 과정

  1. 용량 사전 지정테이블 생성 시 초당 읽기·쓰기 용량(RCU/WCU)을 명시적으로 정함 (예: 읽기 100, 쓰기 50)
  2. Auto Scaling 규칙 적용CloudWatch 메트릭을 모니터링해 사용률이 임계값을 벗어나면 자동으로 용량을 추가하거나 감소
  3. 예약 용량(선택)1년 또는 3년 약정으로 기본 용량을 미리 구입하면 30~65% 할인받고, 초과분은 온디맨드 가격으로 과금

3처리 용량과 요금 모델03-04

웜 처리량·버스트·적응 용량

테이블이 즉시 감당 가능한 처리량 기준선(웜 처리량)과, 남은 용량을 모아 순간 초과분을 흡수하는 버스트, 뜨거운 파티션에 용량을 재배분하는 적응 용량.

1상대의 출발점 확인

프로비저닝 용량을 정하면 그 수준까지만 처리하고, 초과 요청은 버려진다(throttling). 일시적인 스파이크(예: 마케팅 캠페인 시작, 유명인 언급)에 대응하지 못하고, 데이터가 일부 파티션에만 몰려 있으면(핫 파티션) 프로비저닝 용량을 제대로 쓰지 못한다.

2질문 제기

프로비저닝한 용량 내에서 순간 스파이크와 파티션 불균형을 어떻게 흡수하는가?

3구조적 핵심 예시

테이블의 기본 프로비저닝이 읽기 1000 RCU라고 하자. 보통 때는 800 RCU 정도만 쓰고 200 RCU가 남는다. 갑자기 1100 RCU가 필요하면, 남은 200 RCU를 즉시 사용하고 버스트 용량(이전 5분간 미사용분을 누적)을 추가로 흡수한다. 또한 user_id='popular_user'로 쏠린 요청이 있으면, 적응 용량(adaptive capacity)이 자동으로 그 파티션에 여유 용량을 재배분한다.

4단계별 동작 과정

  1. 웜 처리량(Warm Throughput)테이블이 프로비저닝된 기본 RCU/WCU 수준을 언제든 처리할 준비가 되어 있는 상태
  2. 버스트최근 5분간 사용하지 않은 용량을 누적해뒀다가, 순간적인 초과 요청에 즉시 사용해 일시적 스파이크 흡수
  3. 적응 용량(Adaptive Capacity)특정 파티션이 자주 핫스팟이 되면 DynamoDB가 자동으로 그 파티션의 처리 용량을 높여 불균형 해소

5본질 요약

3처리 용량과 요금 모델03-05

용량 모드 전환과 테이블 클래스

온디맨드와 프로비저닝 모드를 언제 어떻게 바꿀 수 있는지의 규칙과, 스토리지 대비 요청 비용 균형이 다른 Standard·Standard-IA 테이블 클래스 선택.

→ 03-02 참조

1상대의 출발점 확인

DynamoDB는 두 가지 용량 모드로 요금을 청구한다. 프로비저닝 모드는 미리 정한 읽기/쓰기 처리 용량만큼만 지불하고, 초과하면 요청이 막힌다. 온디맨드 모드는 실제 사용량에 따라 요청당 비용을 지불한다. 각 모드는 트레이드오프가 있다. 프로비저닝은 예측 가능한 트래픽에는 저렴하지만 용량을 미리 정해야 하고, 온디맨드는 트래픽이 불규칙하면 유리하지만 비용이 비싸다. 또한 테이블 클래스도 두 가지인데, Standard는 모든 요청에 최적화되고 Standard-IA는 액세스가 적은 데이터에 저렴한 스토리지 요금을 제공한다.

2질문 제기

프로비저닝과 온디맨드 중 어느 것을 선택해야 하고, 필요하면 언제 바꿀 수 있으며, 테이블 클래스는 어떻게 결정할까?

3구조적 핵심 예시

트래픽 패턴이 안정적인 웹사이트는 프로비저닝 모드로 하루 종일 필요한 용량을 정하면 된다. 하지만 소셜 미디어의 급변하는 핫콘텐츠처럼 순간적으로 트래픽이 폭증하는 애플리케이션은 온디맨드 모드로 자동으로 스케일링하는 것이 더 낫다. 그런데 6개월 후에 온디맨드에서 프로비저닝으로 바꿀 수 있으려면 마지막 전환 이후 24시간이 지나야 한다.

4단계별 동작 과정

  1. 용량 모드 선택 및 전환 규칙테이블을 생성할 때 모드를 정한다. 프로비저닝 또는 온디맨드로 시작하면, 그 이후로 모드를 바꾸려면 24시간 대기 기간이 있다. 같은 모드로 다시 전환하려면 또 다른 24시간을 기다려야 하므로 빈번한 전환은 피해야 한다.
  2. 테이블 클래스 결정Standard는 자주 액세스하는 데이터용이고, Standard-IA는 액세스 패턴이 명확히 적은 데이터(예: 아카이빙, 로그)용이다. 스토리지 요금은 Standard-IA가 훨씬 저렴하지만, 읽기/쓰기 요청 단가는 더 비싸다.
  3. 비용 구조 비교와 선택워크로드를 분석해 비용을 예측한 후 결정한다. 초기에는 온디맨드로 트래픽 패턴을 파악하고, 안정화되면 프로비저닝으로 전환하는 전략도 가능하다.

5본질 요약

사용 패턴에 따라 비용 청구 방식(프로비저닝 대 온디맨드)과 스토리지 최적화(Standard 대 Standard-IA)를 선택해 비용을 최소화하는 의사결정 체계

4테이블과 항목 조작하기04-01

테이블 기본 조작과 삭제 보호·태그

CreateTable·DescribeTable·UpdateTable·DeleteTable 로 테이블을 만들고 바꾸고 지우며, 삭제 보호와 태그로 관리하는 기본 작업이다.

1상대의 출발점 확인

데이터베이스 테이블을 다루려면 생성, 조회, 수정, 삭제라는 기본 작업이 필요하다. DynamoDB는 CreateTable, DescribeTable, UpdateTable, DeleteTable이라는 네 가지 API로 이를 처리한다. 하지만 테이블은 한번 만들면 데이터베이스의 컨테이너 역할을 하므로, 실수로 삭제하면 내부의 모든 데이터가 사라진다. 또한 테이블에 메타데이터를 붙여 관리를 편하게 할 필요가 있다.

2질문 제기

테이블을 만들고 설정을 바꾸고 지울 때 삭제 실수를 어떻게 방지할 수 있을까?

3구조적 핵심 예시

프로덕션 환경의 중요한 테이블은 삭제 보호(Deletion Protection) 플래그를 켜두면, DeleteTable 호출이 와도 실제 삭제는 막힌다. 관리자가 먼저 이 플래그를 끄고 명시적으로 재확인해야만 테이블이 지워진다.

4단계별 동작 과정

  1. 테이블 생성CreateTable로 파티션 키, 정렬 키, 용량 모드, 속성 정의를 담아 테이블을 만든다.
  2. 테이블 속성 조회 및 수정DescribeTable로 현재 상태를 확인하고, UpdateTable로 용량, 인덱스, 스트림 설정 등을 바꾼다.
  3. 삭제 보호와 태그 관리중요한 테이블은 삭제 보호를 켜고, 비용 추적이나 환경 구분을 위해 태그(예: Environment=Production, Owner=TeamA)를 붙인 뒤 DeleteTable을 호출한다.

5본질 요약

CreateTable·UpdateTable·DeleteTable로 테이블의 생명 주기를 관리하고, 삭제 보호와 태그로 중요한 테이블을 실수로 지우는 것을 방지하는 안전장치

4테이블과 항목 조작하기04-02

항목 쓰기: PutItem·UpdateItem·DeleteItem

항목 하나를 통째로 넣거나(PutItem), 일부 속성만 바꾸거나(UpdateItem), 키로 지우는(DeleteItem) 세 가지 쓰기 방식이다.

1상대의 출발점 확인

데이터를 저장하려면 항목(행)을 테이블에 넣어야 한다. 가장 단순한 방법은 전체 항목을 새로 쓰는 것이다. 하지만 기존 항목의 일부 속성만 바꾸고 싶다면, 전체를 다시 쓰면 다른 속성들까지 새로 정의해야 하므로 번거롭다. 또한 항목을 지울 때도 키로 대상을 찾아 삭제해야 한다.

2질문 제기

항목을 넣을 때 전체를 덮어쓸 것인지, 기존 항목의 일부만 수정할 것인지 어떻게 구분해서 실행할까?

3구조적 핵심 예시

사용자 항목에 이름, 이메일, 가입일이 있을 때, PutItem은 세 속성을 다시 정의해 통째로 바꾸고, UpdateItem은 이메일 속성만 새 값으로 수정한다. DeleteItem은 사용자 ID(키)로 찾아 항목 전체를 지운다.

4단계별 동작 과정

  1. PutItem항목 통째로 쓰기** — 항목의 모든 속성을 정의해서 보낸다. 같은 키가 이미 존재하면 덮어쓴다.
  2. UpdateItem항목 일부만 수정** — 키로 항목을 찾고 특정 속성만 변경한다. 기존의 다른 속성은 그대로 유지된다.
  3. DeleteItem항목 삭제** — 키로 항목을 찾아 통째로 지운다.

5본질 요약

PutItem으로 전체 항목을 새로 쓰고, UpdateItem으로 필요한 속성만 수정하며, DeleteItem으로 키를 기준으로 항목을 지우는 세 가지 쓰기 연산

항목 읽기와 배치 연산

GetItem 으로 키 하나를 읽고, BatchGetItem·BatchWriteItem 으로 여러 항목을 한 번의 호출에 모아 읽고 쓰는 방법이다.

1상대의 출발점 확인

항목을 읽으려면 GetItem으로 키를 넘겨 조회한다. 하지만 100개의 항목을 읽어야 한다면 GetItem을 100번 호출해야 하고, 네트워크 왕복과 API 요청 오버헤드가 커진다. 이는 성능을 떨어뜨리고 비용도 증가시킨다.

2질문 제기

여러 항목을 읽을 때 API 호출 횟수를 줄이고 성능을 높일 수 있을까?

3구조적 핵심 예시

사용자 ID 100개의 사용자 정보를 모두 가져오려면, GetItem 호출 100번 대신 BatchGetItem 하나에 100개의 키를 모아 보낸다. 서버는 한 번의 배치 요청으로 모든 항목을 조회해 응답한다.

4단계별 동작 과정

  1. 단일 읽기GetItem** — 키 하나를 지정해 해당 항목을 조회한다. 빠르지만 항목당 API 호출 하나씩이다.
  2. 배치 읽기BatchGetItem** — 최대 100개의 키를 한 요청에 담아 보낸다. 서버는 한 번에 여러 항목을 반환한다.
  3. 배치 쓰기BatchWriteItem** — PutItem과 DeleteItem을 최대 25개까지 묶어 한 요청으로 실행한다.

5본질 요약

GetItem 대신 BatchGetItem으로, 여러 PutItem·DeleteItem 대신 BatchWriteItem으로 API 호출 횟수를 줄여 네트워크 오버헤드와 비용을 절감하는 것

표현식 기본: 속성 이름·값 플레이스홀더와 프로젝션

#name·:value 플레이스홀더로 예약어와 값을 안전하게 넘기고, 프로젝션 표현식으로 필요한 속성만 받아오는 문법이다.

1상대의 출발점 확인

쿼리 문자열에 속성명을 직접 넣으면 'name'처럼 SQL 예약어와 충돌할 수 있다. 값을 문자열 그대로 연결하면 문자열 삽입 공격에 노출된다. 또한 항목에서 모든 속성을 받아오면 대역폭이 낭비되고, 민감한 정보(예: 내부 조회 통계)를 불필요하게 노출할 수 있다.

2질문 제기

속성명과 값을 안전하게 쿼리에 포함하고, 필요한 속성만 선택적으로 받아올 수 있을까?

3구조적 핵심 예시

UPDATE 요청에서 "name = 'Alice'"라고 직접 쓰는 대신, name 속성을 #n 플레이스홀더로, 값 'Alice'를 :val 플레이스홀더로 치환한다. 서버는 실제 속성명과 값을 따로 받아 안전하게 처리한다.

4단계별 동작 과정

  1. 속성명 플레이스홀더#name, #timestamp 같은 형식으로 속성명을 정의한다. 예약어와 특수 문자를 안전하게 처리한다.
  2. 값 플레이스홀더:value, :id 같은 형식으로 데이터 값을 정의한다. 문자열 주입을 방지한다.
  3. 프로젝션 표현식필요한 속성만 지정(예: '#n, #age')해서 응답에 포함할 속성을 제한한다.

5본질 요약

#name으로 속성명을, :value로 값을 플레이스홀더로 치환해 쿼리 주입을 방지하고, 프로젝션으로 필요한 속성만 전송해 보안과 효율성을 확보하는 것

업데이트 표현식과 원자적 카운터

SET·REMOVE·ADD·DELETE 절로 항목의 일부만 고치고, ADD 로 경합 없이 숫자를 증감하는 원자적 카운터를 만든다.

→ 04-02 참조

1상대의 출발점 확인

항목을 수정할 때 여러 가지 작업이 필요하다. 어떤 속성은 새 값으로 대체하고, 어떤 속성은 삭제하고, 숫자 속성은 증감해야 한다. 특히 방문 카운트나 재시도 횟수처럼 숫자를 증감할 때, 여러 클라이언트가 동시에 접근하면 값이 꼬일 수 있다. 일반적인 읽기-수정-쓰기 방식(read-modify-write)으로는 경합(race condition)을 피할 수 없다.

2질문 제기

UpdateItem에서 속성을 설정하고 삭제하고 숫자를 증감할 때, 동시 접근에서도 데이터 정합성을 유지하려면 어떻게 할까?

3구조적 핵심 예시

페이지 조회 카운트를 증가시킬 때, ADD viewCount :inc를 한 번 보내면 DynamoDB 서버가 내부적으로 기존 값을 읽고 증가량을 더한 후 다시 쓴다. 다른 클라이언트가 동시에 같은 요청을 해도 서버는 순서대로 원자적으로 처리해 값 손실이 없다.

4단계별 동작 과정

  1. SET 절속성 설정** — 새로운 값으로 속성을 설정한다. 예: SET #name = :name, #age = :age
  2. ADD 절원자적 증감** — 숫자 속성을 증감한다. 서버가 원자적으로(한 번에, 중단 없이) 처리해 경합을 방지한다. 예: ADD viewCount :one
  3. REMOVE와 DELETE 절속성을 삭제하거나(REMOVE), 집합 내 원소를 제거한다(DELETE).

5본질 요약

SET으로 속성을 수정하고 ADD로 숫자를 원자적으로 증감해, 동시 요청에서도 데이터 정합성을 보장하고 경합을 방지하는 것

조건 표현식과 조건부 쓰기

attribute_not_exists 같은 조건이 참일 때만 쓰기를 수행해 덮어쓰기와 경합을 막는 장치다.

→ 04-05 참조

1상대의 출발점 확인

쓰기 연산(PutItem, UpdateItem, DeleteItem)은 기본적으로 무조건 실행된다. 프로세스 A가 항목의 버전을 1에서 2로 바꾸려고 할 때, 다른 프로세스 B가 동시에 같은 항목을 수정하면 A의 변경사항이 B의 변경사항을 덮어쓸 수 있다. 이를 방지하려면 쓰기를 실행하기 전에 조건을 확인해야 한다.

2질문 제기

쓰기 연산을 실행하기 전에 특정 조건이 참인지 확인한 후 조건부로 실행하려면 어떻게 할까?

3구조적 핵심 예시

항목의 버전이 1일 때만 업데이트를 수행하려면, 조건 표현식 "#version = :oldVersion"을 넣는다. 서버가 조건을 검사해 참이면 UpdateItem을 실행하고, 거짓이면 연산을 취소한다. 응답에서 조건 실패 여부를 반환한다.

4단계별 동작 과정

  1. 조건 표현식 정의attribute_exists, attribute_not_exists 같은 함수나 비교 연산자(=, <>, <, >, <=, >=)로 조건을 작성한다.
  2. 쓰기 요청에 조건 포함PutItem, UpdateItem, DeleteItem 호출 시 ConditionExpression 파라미터에 조건을 담는다.
  3. 조건 검사 및 실행서버가 조건을 평가해 참이면 쓰기를 수행하고, 거짓이면 ConditionalCheckFailedException 예외를 반환한다.

5본질 요약

ConditionExpression으로 쓰기 전에 조건을 검사해, 조건이 참일 때만 연산을 수행해 동시 접근에서 의도하지 않은 덮어쓰기를 방지하는 것

오류 처리와 재시도 전략

스로틀링·조건 실패 등 오류를 구분하고, 재시도 가능한 오류에만 지수 백오프로 다시 시도하는 방법이다.

1상대의 출발점 확인

DynamoDB 요청이 실패하면 기존에는 모든 오류를 같은 방식으로 처리하거나 무조건 다시 시도했습니다. 하지만 이는 두 가지 문제를 낳습니다. 첫째, 일시적 오류(스로틀링으로 인한 처리량 초과)와 구조적 오류(권한 없음, 잘못된 요청)를 구분하지 않으면, 다시 시도할 수 없는 오류도 계속 재시도해 시간만 낭비합니다. 둘째, 무조건 즉시 재시도하면 오류가 반복되거나 서버 부하를 더합니다.

2질문 제기

DynamoDB 요청이 실패했을 때, 다시 시도할 수 있는 오류와 할 수 없는 오류를 어떻게 구분하고 효율적으로 대응할 것인가?

3구조적 핵심 예시

요청이 실패하면 HTTP 상태 코드와 오류 유형을 확인합니다. ProvisionedThroughputExceededException(상태 400)은 처리량 제한으로 인한 일시적 오류이므로 나중에 다시 시도하면 성공할 수 있습니다. ValidationException(상태 400)은 요청 자체가 잘못됐으므로 아무리 재시도해도 실패합니다. 이렇게 오류 종류를 보고 대응을 나눕니다.

4단계별 동작 과정

  1. 오류 분류요청이 실패하면 반환된 오류 코드를 확인해 재시도 가능 여부를 판단합니다. 일시적 오류(Throttling, ServiceUnavailable) 목록에 속하면 재시도 가능, 그 외는 최종 실패로 간주합니다.
  2. 지수 백오프로 재시도재시도 가능한 오류면 대기 시간을 늘려가며 다시 시도합니다. 첫 재시도는 1초 후, 두 번째는 2초 후, 세 번째는 4초 후처럼 기다리는 시간을 지수적으로 늘립니다(중복 요청 방지).
  3. 최대 재시도 초과 또는 구조적 오류 시 최종 실패지정된 최대 재시도 횟수(예: 3회)를 넘거나, 처음부터 재시도 불가 오류면 오류를 그대로 반환합니다.

5본질 요약

오류를 재시도 가능 여부로 분류해 일시적 문제만 지수 백오프로 자동 복구하고, 구조적 문제는 즉시 실패로 처리하는 효율적인 재시도 전략

Query와 키 조건 표현식

Query는 파티션 키를 지정하고 정렬 키 조건을 더해 원하는 아이템 묶음만 효율적으로 읽어오는 조회 방식이다.

1상대의 출발점 확인

기존에는 Scan으로 테이블 전체를 훑으며 원하는 아이템을 찾거나, 파티션 키만으로 단일 아이템을 조회(GetItem)했습니다. Scan은 모든 아이템을 읽어야 하므로 느리고 비싸며, GetItem은 정렬 키 조건을 지정할 수 없어 범위 조회가 불가능했습니다.

2질문 제기

파티션 키와 정렬 키를 조합해 특정 범위의 아이템만 빠르게 찾을 수는 없을까?

3구조적 핵심 예시

테이블 구조가 (user_id=파티션 키, timestamp=정렬 키)일 때, Query로 user_id='alice'이고 timestamp>=2025-01-01 AND timestamp<2025-02-01인 조건을 지정하면 alice의 1월 기록만 빠르게 추출됩니다. 다른 사용자나 다른 기간의 아이템은 읽지 않습니다.

4단계별 동작 과정

  1. 파티션 찾기파티션 키를 지정해 해시 함수로 그 파티션의 위치를 찾고 접근합니다.
  2. 정렬 키 필터 적용그 파티션 내에서 정렬 키 조건(초과, 미만, 범위, 문자열 시작 등)을 적용해 범위를 좁힙니다.
  3. 결과 반환조건을 만족하는 아이템들을 정렬 순서대로 반환합니다.

5본질 요약

필터 표현식과 결과 페이지네이션

필터 표현식은 읽은 뒤 결과만 걸러내는 것이라 비용은 그대로이며, 결과가 1MB를 넘으면 LastEvaluatedKey로 다음 페이지를 이어 받는다.

1상대의 출발점 확인

기존에는 Query나 Scan으로 아이템을 모두 가져온 후 애플리케이션 코드에서 필터링했습니다. 이 방식은 조건을 만족하지 않는 아이템도 읽어야 하므로 불필요한 용량 소비와 네트워크 전송량 증가를 초래했습니다.

2질문 제기

조회 결과를 서버 쪽에서 먼저 필터링하면 불필요한 데이터 전송을 줄일 수 있지 않을까?

3구조적 핵심 예시

Query로 user_id='alice'의 모든 기록 1000개를 읽어 1MB 용량을 소비하지만, 필터 표현식으로 status='completed'인 것만 결과에 담으면 네트워크에는 100개만 전송됩니다. 용량 소비는 여전히 1000개를 읽었으므로 1MB지만, 실제 전송량은 줄어듭니다.

4단계별 동작 과정

  1. 조회 실행Query나 Scan으로 키 조건을 만족하는 모든 아이템을 읽으며 용량 소비가 발생합니다.
  2. 필터 표현식 적용그 아이템들 중 필터 조건을 만족하는 것만 선별합니다(용량 추가 소비 없음).
  3. 페이지네이션결과가 1MB를 넘으면 LastEvaluatedKey(마지막 아이템의 키)를 반환하고, 클라이언트는 이 키를 다음 요청에 담아 이어서 받습니다.

Scan과 병렬 Scan

Scan은 테이블 전체를 훑는 조회로, 세그먼트를 나눠 여러 워커가 동시에 읽는 병렬 Scan으로 속도를 높일 수 있다.

1상대의 출발점 확인

Query는 파티션 키 조건이 필수이므로, 기본 키에 포함되지 않은 속성(예: age, country, status)으로 찾으려면 Scan으로 테이블 전체를 훑어야 했습니다. 아이템 수가 많으면 Scan은 오래 걸리고 많은 용량을 소비합니다.

2질문 제기

테이블 전체를 훑을 때 여러 워커가 동시에 읽으면 시간을 줄일 수 있지 않을까?

3구조적 핵심 예시

단일 워커가 Scan을 실행하면 처음부터 끝까지 순서대로 읽어 10초가 걸립니다. 같은 테이블을 4개 세그먼트로 나누고 워커 4개가 각각 자신의 세그먼트를 동시에 읽으면 약 3초에 완료됩니다. 병렬 처리로 네트워크와 I/O 대역폭을 활용합니다.

4단계별 동작 과정

  1. 세그먼트 분할테이블 전체를 동일 크기의 논리적 세그먼트로 나눕니다(예: 4개 세그먼트).
  2. 병렬 요청 전송각 워커가 자신의 세그먼트만 Scan하는 요청을 동시에 전송합니다.
  3. 결과 수집 및 병합각 워커의 결과를 수집해 하나의 결과 집합으로 병합합니다.

PartiQL로 SQL처럼 다루기

PartiQL은 DynamoDB 데이터를 SELECT·INSERT 같은 SQL 호환 문법으로 읽고 쓰게 해주는 질의 언어다.

1상대의 출발점 확인

DynamoDB는 기존에 Query, Scan, GetItem 같은 SDK 함수로만 사용했습니다. 관계형 데이터베이스 경험이 있는 개발자는 SQL 문법에 익숙하므로, 새로운 함수 문법을 배워야 하는 것이 불편했고 진입 장벽이 높았습니다.

2질문 제기

SQL 문법으로 DynamoDB를 조회하고 수정할 수 있다면, 기존 SQL 경험을 바로 활용할 수 있지 않을까?

3구조적 핵심 예시

SDK 방식: dynamodb.Query({TableName: 'Users', KeyConditionExpression: 'user_id = ?', ...}) PartiQL 방식: SELECT * FROM Users WHERE user_id = 'alice' 같은 조회를 SQL처럼 쓸 수 있으므로, SQL 배경의 개발자가 추가 학습 없이 사용할 수 있습니다.

4단계별 동작 과정

  1. PartiQL 쿼리 작성SELECT, INSERT, UPDATE, DELETE 등 표준 SQL 문법으로 쿼리를 작성합니다.
  2. DynamoDB API로 변환DynamoDB는 이 쿼리를 내부적으로 Query, PutItem, UpdateItem 등의 API 호출로 변환합니다.
  3. 결과 반환일반 SQL처럼 결과 행을 반환합니다.

보조 인덱스의 필요성과 두 종류

기본 키가 아닌 속성으로도 Query 하려고 테이블에 덧붙이는 조회용 구조로, 글로벌(GSI)과 로컬(LSI) 두 종류가 있다.

1상대의 출발점 확인

DynamoDB에서는 기본 키(파티션 키와 정렬 키)로만 Query가 가능했습니다. 기본 키에 포함되지 않은 다른 속성으로 찾으려면 Scan으로 전체 테이블을 훑어야 했는데, 이는 느리고 비싸다는 근본적인 한계가 있었습니다.

2질문 제기

기본 키가 아닌 다른 속성으로도 Query처럼 빠르게 조회할 수 있을까?

3구조적 핵심 예시

원본 테이블: (user_id 파티션, timestamp 정렬)로 사용자별 활동 기록 저장. 글로벌 보조 인덱스(GSI) 추가: (status 파티션, created_at 정렬)로 만들면 status='active'인 모든 사용자의 활동을 Query로 빠르게 찾을 수 있습니다. 로컬 보조 인덱스(LSI) 추가: (user_id 파티션, status 정렬)로 만들면 특정 user_id 내에서만 status별로 빠르게 찾을 수 있습니다(파티션 키는 고정).

4단계별 동작 과정

  1. 인덱스 생성원본 테이블의 데이터를 복사하되, 파티션 키와 정렬 키를 원하는 속성으로 재구성합니다. 글로벌 인덱스는 독립적인 파티션 키를 가지고, 로컬 인덱스는 원본의 파티션 키를 유지합니다.
  2. 데이터 자동 동기화원본 테이블이 업데이트되면 인덱스도 자동으로 동기화됩니다(원본과 인덱스 양쪽에 용량 소비).
  3. 인덱스로 Query 실행보조 인덱스에서 Query를 실행해 빠르게 결과를 얻습니다.

GSI: 구조·프로젝션·전용 용량

테이블과 완전히 다른 파티션/정렬 키를 갖고, 프로젝션한 속성만 복사해 자체 읽기·쓰기 용량으로 동작하는 별도 인덱스다.

1상대의 출발점 확인

테이블의 기본 인덱스(파티션 키, 정렬 키)만으로는 모든 조회 패턴을 효율적으로 처리할 수 없다. 예를 들어 파티션 키가 사용자ID이고 정렬 키가 생성일인 테이블에서 "특정 조직의 모든 항목"을 찾으려면 전체 테이블을 스캔해야 한다. 이는 비용이 크고 속도가 느리다.

2질문 제기

테이블의 기본 키와 완전히 다른 관점으로 데이터를 조회할 수 있는 별도의 인덱스를 만들 수 있는가?

3구조적 핵심 예시

GSI는 테이블의 기본 키와 독립적으로 파티션 키와 정렬 키를 설정해 운영한다. 같은 테이블의 데이터가 쓰여질 때 자동으로 GSI에도 복사되며, 선택한 속성만 저장되므로 저장 공간을 절약할 수 있다.

4단계별 동작 과정

  1. 프로젝션 속성 선택인덱스에 포함할 속성을 정한다. ALL(모든 속성 복사), KEYS_ONLY(기본 키만), INCLUDE(선택한 속성들)의 세 가지 모드가 있다.
  2. 별도 저장소에 자동 복사테이블에 데이터가 쓰여질 때마다 DynamoDB가 GSI에도 자동으로 복사하고 정렬 키 순서대로 저장한다.
  3. GSI로 조회 실행GSI의 파티션 키와 정렬 키를 사용해 쿼리를 실행하면 프로젝션된 속성이 빠르게 반환된다. 나머지 속성이 필요하면 기본 테이블에서 추가 조회한다.

GSI 온라인 관리와 키 위반 탐지

운영 중인 테이블에 GSI를 추가·삭제하며 백필 진행 상황을 보고, 키 타입에 맞지 않는 항목(키 위반)을 찾아 고치는 작업이다.

1상대의 출발점 확인

테이블을 만든 후 인덱스 설계를 변경하려면 서비스를 멈추고 모든 데이터를 새 구조로 마이그레이션해야 했다. 운영 중인 시스템에서는 인덱스를 추가하거나 제거할 수 없었다.

2질문 제기

운영 중인 테이블에 GSI를 동적으로 추가하거나 제거하면서 기존 데이터의 무결성을 어떻게 보장할 수 있는가?

3구조적 핵심 예시

DynamoDB는 GSI를 온라인으로 추가할 때 백필(backfill) 과정을 거친다. 테이블의 모든 기존 항목을 스캔해 새 인덱스의 키 형식으로 변환하고 복사하며, 진행 상황을 추적하고 키 타입 불일치(키 위반)를 감지한다.

4단계별 동작 과정

  1. 백필 시작새 GSI를 추가하면 DynamoDB가 테이블의 모든 항목을 스캔해 새 인덱스 키 형식으로 변환하고 복사한다. 이 작업은 백그라운드에서 진행되며 테이블 쓰기는 즉시 인덱스에도 반영된다.
  2. 진행 상황 모니터링CloudWatch 메트릭이나 DescribeTable API로 백필 진행률을 확인할 수 있다. 완료 전까지는 인덱스가 쿼리 트래픽을 받지 않는다.
  3. 키 위반 감지 및 수정키 값이 기대 타입(예: 문자열)과 맞지 않는 항목들을 찾아 애플리케이션에서 스키마 마이그레이션하거나 데이터를 정제한다.

LSI와 그 제약

파티션 키는 그대로 두고 정렬 키만 바꾸는 인덱스로, 테이블 생성 시에만 만들 수 있고 항목 컬렉션 10GB 제한을 받는다.

1상대의 출발점 확인

테이블의 기본 파티션 키만으로는 데이터를 다양한 정렬 순서로 조회할 수 없다. 파티션 키는 유지하되 정렬 키만 다르게 사용하는 경우 GSI를 만들어야 하는데, 이는 추가 비용과 일관성 문제를 야기한다.

2질문 제기

같은 파티션 키로 여러 정렬 키 관점을 효율적으로 제공할 수 있는가?

3구조적 핵심 예시

LSI(Local Secondary Index)는 파티션 키는 테이블과 동일하게 두고 정렬 키만 바꾸는 인덱스다. 같은 파티션 내에서만 동작하므로 GSI보다 강한 일관성을 보장하고 조회 지연이 적다.

4단계별 동작 과정

  1. 테이블 생성 시에만 정의LSI는 테이블을 만들 때만 추가할 수 있으며, 생성 후에는 추가하거나 삭제할 수 없다.
  2. 파티션 내 10GB 제약같은 파티션 키를 가진 모든 항목(LSI 포함)의 총 크기가 10GB를 넘을 수 없어, 대용량 파티션 설계에 제약을 준다.
  3. 강한 일관성 제공LSI는 같은 파티션 내의 데이터이므로 강한 일관성 읽기가 가능하고, GSI보다 쿼리 지연이 적다.

4단계별 동작 과정

  1. 스파스 인덱싱특정 속성이 있는 항목에만 인덱스 키를 부여해 불필요한 항목 저장을 피한다. 예: 프리미엄 회원만 인덱싱하거나, 특정 상태의 항목만 포함한다.
  2. 오버로딩과 샤딩GSI의 파티션 키와 정렬 키를 다양한 엔티티나 조회 패턴에 재사용하거나, 파티션을 여러 개로 나눠 조회 부하를 분산하고 핫스팟을 피한다.
  3. 집계 키 생성요약 데이터(예: 월별 판매량)를 별도의 집계 키로 만들어 저장해 복잡한 집계 쿼리를 단순화하고 성능을 향상한다.

2질문 제기

3구조적 핵심 예시

  2. 조건 평가각 작업의 ConditionExpression(예: 계좌 잔액 >= 출금액)을 평가해 모든 조건이 참인지 확인한다.
  3. 모두 커밋 또는 모두 롤백모든 조건을 만족하면 트랜잭션의 모든 작업을 커밋하고, 하나라도 조건을 만족하지 않으면 전체 트랜잭션을 롤백해 부분 업데이트를 방지한다.

관계형처럼 정규화부터 하지 않고, 앱이 어떤 질의를 할지(액세스 패턴)를 먼저 적어두고 그에 맞춰 테이블과 키를 정하는 DynamoDB 설계의 출발점이다.

1상대의 출발점 확인

관계형 데이터베이스는 정규화(중복을 제거하고 테이블을 분할하는 설계)를 먼저 한 후, 복잡한 조인으로 데이터를 조회합니다. 하지만 DynamoDB는 조인이 없고 파티션 키로만 빠르게 조회하는 방식이므로, 처음부터 설계 원칙이 완전히 다릅니다.

2질문 제기

DynamoDB 테이블을 어떻게 설계하면 실제 애플리케이션이 필요로 하는 질의들을 효율적으로 처리할 수 있을까요?

3구조적 핵심 예시

애플리케이션이 "사용자 ID로 프로필 조회", "주문 ID로 주문 내역 조회", "사용자별 최근 주문 10개 조회" 같은 질의를 한다고 하면, 이 질의 목록을 먼저 적어두고, 각 질의가 빠르게 처리되도록 파티션 키와 정렬 키를 설계합니다.

4단계별 동작 과정

  1. 액세스 패턴 정리애플리케이션에서 필요한 모든 질의를 목록화합니다 (누가, 무엇을, 어떤 순서로 읽을지).
  2. 테이블 구조 설계각 패턴에 최적화된 파티션 키, 정렬 키, GSI(보조 인덱스)를 결정합니다.
  3. 검증정한 테이블 구조로 모든 액세스 패턴을 효율적으로(한 번의 쿼리로) 처리할 수 있는지 확인합니다.

파티션 키 설계와 쓰기 샤딩

파티션 키 값을 고르게 퍼뜨려 핫 파티션을 막고, 값이 몰릴 때는 임의 접미사를 붙여 여러 파티션으로 쓰기를 나누는(쓰기 샤딩) 기법이다.

1상대의 출발점 확인

DynamoDB는 파티션 키 값별로 데이터를 여러 파티션(물리적 저장소)에 나눠서 저장합니다. 하지만 파티션 키 값이 한두 개에 집중되면 그 파티션에만 요청이 몰려서 읽기/쓰기 성능이 급격히 떨어집니다. 이를 핫 파티션 문제라고 합니다.

2질문 제기

특정 파티션 키 값에 쓰기 요청이 집중될 때, 그 부하를 여러 파티션에 분산시킬 수 있을까요?

3구조적 핵심 예시

실시간 게임 점수를 기록할 때, 파티션 키를 단순히 game_id로 하면 인기 있는 게임에 쓰기가 몰립니다. 대신 파티션 키를 game_id#0, game_id#1, game_id#2 같은 형태로 바꿔서 같은 게임의 데이터를 여러 파티션에 분산 저장합니다.

4단계별 동작 과정

  1. 문제 파악모니터링 결과 특정 파티션 키 값에 요청이 집중되어 쓰기 속도 저하가 발생합니다.
  2. 샤딩 적용파티션 키에 임의의 접미사(0~N 범위의 번호, 또는 UUID 일부)를 붙여서 같은 논리 데이터를 여러 항목(샤드)으로 분산 저장합니다.
  3. 읽기 통합해당 데이터를 조회할 때는 모든 샤드를 병렬로 읽어 결과를 통합합니다.

5본질 요약

파티션 키에 접미사를 붙여 같은 데이터를 여러 파티션에 분산 저장함으로써, 핫 파티션으로 인한 쓰기 병목을 해소하는 것

정렬 키 설계

같은 파티션 안에서 항목을 정렬·범위 조회하도록 정렬 키를 계층적 복합 값으로 구성하는 설계 기법이다.

1상대의 출발점 확인

DynamoDB의 기본 쿼리는 파티션 키로만 항목을 찾습니다. 같은 파티션 키를 가진 여러 항목들은 저장 순서가 무질서하므로, 그 안에서 특정 범위의 항목만 빠르게 가져올 방법이 없습니다. 모든 항목을 스캔해야 하므로 비효율적입니다.

2질문 제기

같은 파티션 안의 항목들 중에서 특정 범위만 효율적으로 조회하려면 어떻게 해야 할까요?

3구조적 핵심 예시

사용자별 주문 데이터에서 파티션 키를 사용자 ID로 설정하고, 정렬 키를 주문날짜#주문시간#주문ID 형태로 설정합니다. 그러면 "특정 기간 주문 조회" 또는 "최신 주문 10개 조회" 같은 쿼리를 이진 탐색으로 빠르게 처리할 수 있습니다.

4단계별 동작 과정

  1. 파티션 검색파티션 키(사용자 ID)로 데이터가 저장된 파티션을 찾습니다.
  2. 정렬 키 범위 탐색파티션 내 항목들이 정렬 키로 이미 정렬되어 있으므로, 이진 탐색으로 원하는 범위(예: 2024-01-01부터 2024-01-31까지)의 시작점과 끝점을 찾습니다.
  3. 결과 반환해당 범위의 항목들을 효율적으로 반환합니다.

단일 테이블 설계 빌딩 블록과 스키마 패키지

한 테이블에 여러 엔터티를 담는 설계를 재사용 가능한 기본 패턴(빌딩 블록)과 완성된 예제 스키마 패키지로 익히는 방법이다.

1상대의 출발점 확인

관계형 데이터베이스는 엔터티 타입당 테이블을 분리합니다. DynamoDB에서도 같은 방식으로 User 테이블, Order 테이블, Product 테이블을 따로 만들면, 관련 데이터를 조회할 때마다 여러 번의 네트워크 호출이 필요합니다. 트랜잭션(atomicity, consistency) 범위도 제한됩니다.

2질문 제기

여러 엔터티 타입의 데이터를 한 테이블에 담으면서도 각 엔터티별로 효율적으로 접근할 수 있을까요?

3구조적 핵심 예시

한 테이블에 User, Order, Product 데이터를 모두 저장하되, 파티션 키와 정렬 키를 엔터티 타입에 따라 다르게 설정합니다. 예를 들어 파티션 키를 "User#123" 형태로, 정렬 키를 "metadata" 또는 "Order#456" 형태로 하면, 같은 항목 집합으로 여러 접근 패턴을 만족할 수 있습니다.

4단계별 동작 과정

  1. 엔터티 패턴 정의각 엔터티(User, Order, Product)에 대해 PK(파티션 키#정렬 키) 구조를 설계합니다. 같은 테이블에서도 엔터티마다 다른 키 형식을 가질 수 있습니다.
  2. 보조 인덱스(GSI) 설정Global Secondary Index를 추가하여 기본 PK와 다른 방식의 조회 경로를 제공합니다. 예를 들어 "주문 날짜로 모든 주문 조회" 같은 쿼리를 지원합니다.
  3. 빌딩 블록 문서화자주 쓰는 패턴들을 재사용 가능한 블록으로 정리하고, 완성된 스키마 패키지로 공개하여 팀이 일관된 설계를 따르도록 합니다.

관계형 스키마 이전과 다대다 관계

RDBMS 테이블·조인을 DynamoDB로 옮길 때 인접 리스트(adjacency list) 같은 패턴으로 다대다 관계를 표현하는 방법이다.

1상대의 출발점 확인

관계형 데이터베이스에서 다대다 관계(예: 학생과 수강 과목)는 조인 테이블(junction table)로 표현합니다. DynamoDB는 조인 기능이 없으므로 관계를 직접 코딩으로 해결해야 합니다. 기존 설계를 그대로 옮기면 쿼리 복잡도가 높아집니다.

2질문 제기

DynamoDB에서 다대다 관계를 한 테이블 안에서 양방향으로 효율적으로 조회하려면?

3구조적 핵심 예시

학생(student001)과 과목(course A, course B) 관계를 저장할 때, 파티션 키를 "student#001", 정렬 키를 "course#A" 형태로 하는 항목과, 역으로 파티션 키를 "course#A", 정렬 키를 "student#001" 형태로 하는 항목을 모두 저장합니다. 이 방식을 인접 리스트(adjacency list) 패턴이라 합니다.

4단계별 동작 과정

  1. 조인 테이블 구조 파악원본 관계형 DB에서 다대다 관계를 정의하는 조인 테이블의 구조와 쿼리 패턴을 확인합니다.
  2. 양방향 항목 저장DynamoDB에서는 같은 관계를 두 방향으로 저장합니다. A→B 관계와 B→A 관계를 모두 항목으로 만들어 저장하므로, 어느 방향으로든 신속하게 조회할 수 있습니다.
  3. GSI 또는 스캔으로 조회 지원특정 학생의 모든 과목을 조회하거나, 특정 과목의 모든 학생을 조회할 때 각각 파티션 키로 효율적으로 검색합니다.

5본질 요약

시계열 데이터와 큰 항목 처리

기간별 테이블 분리로 시계열 데이터를 다루고, 400KB 제한을 넘거나 큰 값은 S3에 두고 포인터만 저장하는 설계다.

1상대의 출발점 확인

센서 데이터, 로그, 이벤트 기록 같은 시계열 데이터는 시간이 지남에 따라 계속 쌓입니다. 모든 데이터를 한 테이블에 저장하면 용량이 계속 증가하고, 관리 복잡도가 높아집니다. 또한 DynamoDB 항목의 크기는 400KB 제한이 있으므로, 대용량 파일이나 이미지 데이터는 직접 저장할 수 없습니다.

2질문 제기

시간이 지남에 따라 계속 증가하는 데이터와 400KB를 초과하는 데이터를 효율적으로 저장하고 조회하려면?

3구조적 핵심 예시

일별(또는 월별)로 다른 테이블을 만들어 시계열 데이터를 분산 저장합니다(예: events-2024-01, events-2024-02). 400KB 초과 항목(예: 대형 이미지)은 Amazon S3에 업로드하고, DynamoDB에는 그 파일의 S3 경로와 메타데이터(파일명, 크기, 업로드 시간)만 기록합니다.

4단계별 동작 과정

  1. 시간 기반 테이블 분산일(day), 주(week), 월(month) 단위로 테이블을 분리하여 각 테이블의 용량 증가를 제한합니다. 오래된 테이블은 필요시 백업 또는 삭제할 수 있습니다.
  2. 대용량 항목 감지 및 이전항목 크기가 400KB에 가까우면 DynamoDB 저장 대신 S3로 업로드합니다.
  3. 참조 정보 저장DynamoDB 항목에는 S3 파일 위치, 메타데이터, 접근 권한 정보 등만 저장하여 필요할 때 S3에서 조회할 수 있도록 합니다.

대량 데이터 작업과 효율적 업로드

초기 적재 시 파티션 키를 번갈아 가며 병렬로 올려 스로틀링 없이 처리량을 고르게 쓰는 업로드 요령이다.

1상대의 출발점 확인

DynamoDB는 파티션당 일정한 처리량(provisioned throughput)을 할당합니다. 순차적으로 데이터를 업로드하거나 파티션 키가 편중되면 특정 파티션에 부하가 집중되어 스로틀링(throttling, 처리 거부)이 발생합니다. 초기 대량 적재 시 이는 시간을 크게 낭비합니다.

3구조적 핵심 예시

  3. 쓰기와 무효화쓰기 요청은 DAX를 거쳐 DynamoDB로 간다. 관련 캐시 항목을 무효화하거나 업데이트해 캐시와 저장소 사이의 일관성을 유지한다.

DynamoDB 테이블은 한 AWS 리전(지역)에만 존재한다. 다른 리전의 애플리케이션이 데이터에 접근하려면 원본 테이블이 있는 리전까지 네트워크 요청을 보내야 하고, 네트워크 지연이 크다. 한 리전이 장애나면 다른 리전의 애플리케이션은 데이터에 접근할 수 없다.

2질문 제기

같은 DynamoDB 테이블을 여러 리전에 복제하면서 자동으로 동기화할 수 있을까?

3구조적 핵심 예시

글로벌 테이블을 설정하면 us-east-1, eu-west-1, ap-southeast-1 같은 여러 리전에 같은 테이블의 복제본(레플리카)이 생긴다. 어느 리전의 애플리케이션이 항목을 쓰면, DynamoDB가 다른 모든 리전 복제본으로 그 변경을 자동 전파한다.

4단계별 동작 과정

  1. 복제본 생성원본 테이블이 있는 리전에서 글로벌 테이블을 활성화하면, 지정한 다른 리전들에 복제본이 자동 생성된다. 각 복제본은 원본과 같은 스키마, 인덱스, 설정을 갖는다.
  2. 양방향 동기화어느 리전의 복제본에 쓰기가 일어나도, DynamoDB가 자동으로 다른 모든 리전 복제본으로 전파한다. 각 리전이 독립적으로 쓰기를 받아 처리할 수 있다(다중 활성화 모드).
  3. 데이터 일관성 유지복제본 간 복제 지연(보통 수백 밀리초)이 있을 수 있으므로, 일관성 보장 수준을 선택할 수 있다(다음 id=10-02 참고).

MREC와 MRSC (다중 리전 일관성 선택)

MREC는 리전마다 쓰기를 받고 최종적으로 수렴하는 방식, MRSC는 리전 간 강한 일관성을 보장하는 방식으로, 글로벌 테이블의 일관성 모델 선택지다.

1상대의 출발점 확인

단일 리전 테이블에서는 쓰기 후 즉시 강한 일관성 읽기(쓴 것을 바로 읽음)를 보장할 수 있다. 글로벌 테이블에서는 여러 리전 복제본이 있어서 이를 보장하기 어렵다. 모든 복제본이 동기화될 때까지 기다리면 응답이 느려지고, 동기화를 기다리지 않으면 다른 리전에서 아직 업데이트된 데이터를 읽을 수 없다.

2질문 제기

글로벌 테이블에서 각 리전이 독립적으로 쓰기를 받으면서도 데이터 일관성을 어떻게 선택할까?

3구조적 핵심 예시

미국 리전에서 계정 잔액을 업데이트할 때, MREC를 쓰면 유럽 리전에서 바로 새 잔액을 읽을 수 있다(업데이트가 동기화되는 짧은 시간 동안은 두 리전이 다른 값을 볼 수 있음). MRSC를 쓰면 유럽 리전은 미국의 업데이트가 유럽 복제본에 도착할 때까지 기다린 뒤 읽어야 한다(모든 리전이 같은 값을 봄).

4단계별 동작 과정

  1. MREC 선택Multi-Region Eventual Consistency의 약자다. 각 리전 복제본이 독립적으로 쓰기를 받는다(그래서 응답이 빠르다). 다른 리전의 업데이트는 비동기로 전파되므로, 복제본 간 일시적 차이가 생긴다. 높은 가용성과 응답 속도가 우선일 때 선택한다.
  2. MRSC 선택Multi-Region Strong Consistency의 약자다. 쓰기 요청이 모든 리전 복제본에 동기적으로 동기화될 때까지 기다린다(응답이 느리다). 모든 리전에서 같은 데이터를 항상 읽을 수 있다(강한 일관성). 금융·거래 같이 데이터 일관성이 매우 중요할 때 선택한다.
  3. 일관성 선택의 영향글로벌 테이블 생성 시 MREC 또는 MRSC를 선택한다. 이 선택이 응답 지연 시간, 데이터 일관성 수준, 비용에 직접 영향을 미친다.

복제본 추가·다중 계정 구성·과금·버전 차이를 이해하고 충돌과 지연을 줄이도록 설계하는 운영 모범 사례다.

1상대의 출발점 확인

각 리전에 테이블을 수동으로 만들고 복제 로직을 짜서 운영하면, 리전 추가·제거, 다중 AWS 계정 관리, 비용 추적, 버전 관리가 복잡하다. 특히 여러 리전에서 동시에 같은 항목을 수정할 때 충돌이 생기고, 리전 간 네트워크 지연으로 인한 일관성 문제를 직접 해결해야 한다.

2질문 제기

글로벌 테이블을 운영할 때 다중 리전·다중 계정 환경에서 충돌과 지연을 어떻게 줄일까?

3구조적 핵심 예시

글로벌 테이블에 새 리전을 추가할 때 같은 AWS 계정이면 콘솔에서 한 번에 처리되지만, 다른 계정에 추가하려면 각 계정의 IAM 역할(권한 정의)을 설정해야 한다. 또한 계정별로 비용이 청구되므로, 과금 구조를 이해하고 결산할 때 각 계정의 사용량을 추적해야 한다.

4단계별 동작 과정

  1. 복제본 추가·제거와 버전 관리글로벌 테이블에서 리전을 추가하거나 제거할 때, DynamoDB 글로벌 테이블 버전(v2018.04 vs v2019.11)에 따라 처리 방식이 다르다. 모든 리전의 버전을 같게 유지해야 호환성 문제를 피한다.
  2. 다중 계정 구성과 권한 설정여러 AWS 계정에 복제본을 두려면, 각 계정의 IAM 역할을 설정해 글로벌 테이블 접근을 허용해야 한다. 계정 간 신뢰 관계를 정확히 구성해야 권한 오류와 접근 거부가 줄어든다.
  3. 충돌 해결과 지연 최소화여러 리전에서 동시에 같은 항목을 수정하면 충돌이 생긴다. DynamoDB는 마지막 쓰기 승리(Last Write Wins) 규칙을 쓰거나, 애플리케이션 로직으로 충돌을 감지해 처리한다. 지연을 줄이려면 지리적으로 가까운 리전을 선택하고, MREC 모드에서는 읽기를 로컬 리전에만 하도록 아키텍처를 설계한다.

PITR (특정 시점 복구)

PITR을 켜두면 최근 35일 이내의 임의 시점 상태로 테이블을 새 테이블에 복원할 수 있다.

1상대의 출발점 확인

DynamoDB 테이블이 실수로 삭제되거나 손상되면, 수동으로 만든 백업이 없으면 데이터를 복구할 수 없다. 수동 백업도 언제 만들지 예측하기 어렵고, 백업 사이의 기간 동안 일어난 데이터 변경은 모두 잃어버린다.

2질문 제기

DynamoDB 테이블의 상태를 과거의 어느 시점으로 복원할 수 있을까?

3구조적 핵심 예시

PITR을 켜두면, DynamoDB가 자동으로 최근 35일간의 모든 변경사항을 기록한다. 데이터 손상을 발견했을 때 "3시간 전 상태로 복구해 달라"는 요청을 하면, DynamoDB가 그 시점의 스냅샷을 바탕으로 새로운 테이블을 만든다. 원본 테이블은 그대로 두고 복구본만 생기므로 검증 후 전환할 수 있다.

4단계별 동작 과정

  1. PITR 활성화테이블의 설정에서 PITR을 켜면, DynamoDB가 모든 변경사항(쓰기·삭제)을 최근 35일간 자동 기록한다. 이를 위한 추가 저장소 비용이 발생한다.
  2. 복구 시점 선택과 스냅샷 생성데이터 손상을 발견하면 AWS 콘솔이나 API에서 복구할 시점을 지정한다(예: 정확히 2시간 전). DynamoDB가 그 시점의 데이터 스냅샷을 바탕으로 새로운 테이블을 생성한다.
  3. 검증 후 전환복구된 테이블에서 데이터가 정상인지 확인한 후, 애플리케이션이 원본 테이블 대신 복구 테이블을 가리키도록 연결 설정을 바꿔 전환한다.

1상대의 출발점 확인

기존 방식에서는 테이블의 데이터를 보호하기 위해 별도로 데이터를 추출해 S3에 저장하거나, 데이터베이스 전체를 수동으로 복사하는 작업이 필요했다. 이 방식은 복구 시점(RPO, Recovery Point Objective)이 길어지고, 복구 시간(RTO, Recovery Time Objective)도 오래 걸린다. 또한 여러 리전에 걸친 재해 복구를 설정하려면 복잡한 자동화 스크립트를 직접 관리해야 한다.

3구조적 핵심 예시

온디맨드 백업은 DynamoDB 테이블의 전체 상태를 그 순간에 스냅샷으로 저장한 후, 이 스냅샷으로부터 새로운 테이블을 만든다. 예를 들어 오전 10시에 Orders 테이블을 백업하면, 그 시점의 모든 아이템이 별도 스냅샷에 저장되고, 언제든 이 스냅샷으로부터 Orders_Restored 같은 새 테이블을 생성할 수 있다.

4단계별 동작 과정

  1. 백업 트리거AWS 콘솔이나 API로 특정 테이블에 대해 백업을 시작하면, DynamoDB가 그 순간의 테이블 스냅샷을 생성하고 AWS 관리 스토리지에 저장한다.
  2. 복원 요청백업이 완료된 후 언제든 그 백업으로부터 새 테이블을 만들 수 있다. 원본 테이블과 독립적인 새 테이블이 생성되므로 원본 데이터에 영향을 주지 않는다.
  3. AWS Backup 정책 적용AWS Backup 서비스를 연동하면 일일/주간/월간 같은 스케줄에 따라 백업을 자동 실행하고, 여러 리전으로 복사해 저장하는 정책을 한 번에 설정할 수 있다.

IAM으로 DynamoDB 접근 제어

누가 어떤 테이블·API 작업을 할 수 있는지 IAM 자격 증명 기반 정책으로 허용/거부하는 기본 권한 체계.

1상대의 출발점 확인

기존 방식에서는 AWS 계정 내의 모든 사용자나 애플리케이션이 같은 수준의 권한을 갖거나, 수동으로 공유 자격증명(Access Key)을 배포해 관리했다. 이는 실수로 인한 데이터 삭제나 무단 접근 시 제어할 방법이 없고, 권한이 필요 이상 넓어지는 보안 위험이 있다.

2질문 제기

AWS 자격 증명(IAM 사용자, 역할, 임시 보안 자격증명)마다 DynamoDB의 어떤 테이블, 어떤 작업(읽기, 쓰기, 삭제)만 허용할지 세밀하게 정의할 수 있을까?

3구조적 핵심 예시

IAM 정책은 JSON 형식의 허용/거부 규칙 집합이다. 예를 들어 개발팀 IAM 역할에는 Orders 테이블의 GetItem과 Query 작업만 허용하고, DeleteTable 같은 삭제 작업은 거부하는 정책을 붙인다. 이렇게 하면 그 역할을 쓰는 애플리케이션은 자동으로 테이블 구조를 건드릴 수 없다.

4단계별 동작 과정

  2. IAM 사용자/역할에 정책 첨부정의한 정책을 특정 IAM 사용자, 역할, 그룹에 붙인다.
  3. 요청 시 평가DynamoDB로 가는 API 호출마다 AWS는 요청자의 IAM 자격증명을 확인해 정책을 적용하고, 허용된 작업만 실행하거나 거부한다.

요청이 용량을 넘어 거부될 때 그 원인이 핫 파티션인지, 프로비저닝 부족인지, 계정 한도인지, 온디맨드 최대 처리량 초과인지를 가려내고 각각에 맞게 푸는 절차다.

1상대의 출발점 확인

DynamoDB에 요청을 보냈을 때 거부 응답(429 에러)이 오면 "요청이 너무 많다"는 것만 알 수 있었습니다. 거부의 정확한 원인이 무엇인지는 모를 수밖에 없었습니다. 데이터가 한 파티션에 몰려 있어서인지(핫 파티션), 전체 테이블의 처리량이 부족한 것인지, 계정 전체 한도를 초과했는지, 온디맨드 모드의 최대 처리량을 넘었는지 구분이 필요합니다.

2질문 제기

3구조적 핵심 예시

CloudWatch 메트릭에서 UserErrors(클라이언트 요청 오류) 값과 시간 그래프를 보면, 특정 파티션의 처리량만 높은지(핫 파티션 신호), 테이블 전체가 높은지(용량 부족), 아니면 특정 시각에만 집중되는지(일시적 스파이크) 한눈에 드러납니다. 동시에 에러 로그의 에러 코드(ProvisionedThroughputExceededException, ValidationException 등)를 확인하면 원인이 명확해집니다.

4단계별 동작 과정

  1. 에러 로그 확인클라이언트가 받은 HTTP 상태 코드와 DynamoDB 에러 코드(ProvisionedThroughputExceededException, RequestLimitExceeded 등)를 기록하고 분류합니다.
  2. CloudWatch 메트릭 분석UserErrors, ConsumedWriteCapacityUnits, ConsumedReadCapacityUnits 추이를 시간별로 보면서, 특정 파티션 키 값이 비정상적으로 높은 사용률을 보이는지 확인합니다.
  3. 원인별 해결책 적용핫 파티션이면 파티션 키를 재설계하거나 정렬 키를 추가하고, 용량 부족이면 프로비저닝 용량을 늘리거나 온디맨드 모드로 전환합니다.

코드나 용량 소비 없이 S3의 데이터를 새 테이블로 불러오거나(Import), 테이블 데이터를 S3로 내보내(Export) 분석·백업·이전에 쓰는 기능이다.

2질문 제기

3구조적 핵심 예시

4단계별 동작 과정

  1. Import (S3에서 DynamoDB로)S3에 준비된 Parquet 또는 CSV 파일을 지정하면 DynamoDB가 스키마 검증과 데이터 타입 변환을 처리합니다.
  2. 병렬 적재AWS 내부에서 파일을 여러 파티션에 분산하여 병렬로 읽고 테이블에 기록하므로 대용량도 빠르게 처리됩니다.
  3. Export (DynamoDB에서 S3로)테이블의 모든 항목을 S3로 내보낼 때 AWS가 병렬 스캔으로 데이터를 추출하고 Parquet 파일로 변환하여 저장합니다.

DynamoDB로의 마이그레이션과 계정 간 이동

2질문 제기

기존 데이터베이스의 데이터를 DynamoDB로, 또는 DynamoDB 테이블을 다른 AWS 계정으로 효율적으로 이동할 수 있을까?

3구조적 핵심 예시

기존 RDS 데이터베이스를 S3로 내보낸 후 DynamoDB의 Import 기능으로 새 테이블에 직접 적재하거나, AWS Database Migration Service를 사용해 테이블 스키마와 데이터를 자동 변환하면서 옮길 수 있습니다. 계정 간 이동은 DynamoDB 테이블을 S3로 Export한 후 다른 계정에서 Import하거나 AWS Backup으로 복원합니다.

4단계별 동작 과정

  1. 원본 데이터 추출기존 데이터베이스(RDS, MongoDB 등)를 S3, CSV 또는 Parquet 형식으로 내보내거나, Database Migration Service로 데이터를 실시간 동기화합니다.
  2. 스키마 변환 및 설계기존의 정규화된 관계형 스키마를 DynamoDB의 비정규화 구조(파티션 키, 정렬 키, GSI)로 매핑하고 테이블을 생성합니다.
  3. 계정 간 이동기존 계정의 DynamoDB 테이블을 S3로 내보낸 후 대상 계정에서 Import하거나, AWS Backup으로 스냅숏을 만들어 다른 계정으로 복원합니다.

5본질 요약

기존 데이터베이스와 DynamoDB 간의 스키마 변환과 데이터 마이그레이션, 그리고 AWS 계정 간 테이블 이전을 관리형 도구와 서비스로 단순화하고 자동화하는 방법
