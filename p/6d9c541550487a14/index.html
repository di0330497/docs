1단계 기초 — 서비스 이해

AWS가 인프라를 관리하는 검색·분석 관리형 서비스로, OpenSearch 엔진 기반 도메인을 만들어 검색·로그 분석·벡터 검색을 실행한다.

1상대의 출발점 확인

검색 기능을 서비스에 넣으려면 예전에는 직접 검색 엔진을 설치하고 운영해야 했다. 오픈소스 검색 엔진(Elasticsearch, OpenSearch) 서버를 직접 골라 설치하고, 메모리와 디스크를 설정하고, 노드가 여럿일 때 클러스터로 묶고, 장애가 나면 직접 복구해야 했다. 이 과정은 검색 기능 자체를 만드는 일보다 서버를 관리하는 일이 더 큰 부담이 되는 구조였다. 트래픽이 늘면 노드를 추가해 용량을 늘리는 작업도 운영자가 직접 해야 했고, 버전 업그레이드나 보안 패치도 누락되기 쉬웠다.

2질문 제기

검색 엔진의 기능은 그대로 쓰면서 서버 설치·운영·확장의 부담은 AWS에 맡길 수는 없을까?

3구조적 핵심 예시

AWS 콘솔에서 "도메인 생성" 화면에 엔진 버전과 인스턴스 개수만 골라 만들기 버튼을 누르면, AWS가 OpenSearch 엔진이 실행 중인 서버 그룹(클러스터)을 통째로 만들어 준다. 생성된 도메인에는 전용 URL(엔드포인트)이 붙고, 이후에는 그 URL로 문서를 넣고 검색만 하면 된다. 서버의 설치, 네트워크 구성, 백업, 장애 대응은 AWS가 관리한다.

4단계별 동작 과정

  1. 도메인 생성AWS가 OpenSearch 엔진이 설치된 서버들을 클러스터로 묶어 준비하고, 접속용 URL과 인증 정보를 만들어 준다.
  2. 데이터 입력만든 URL로 문서(JSON)를 보내면 OpenSearch가 문서를 검색 가능한 구조(인덱스)에 저장한다.
  3. 검색과 분석같은 URL로 검색 질의를 보내면 OpenSearch가 저장된 문서에서 결과를 찾아 응답하고, 로그 분석이나 벡터 검색 같은 분석 작업도 그 위에서 실행한다.

1기초 — 서비스 이해01-02

1단계 기초 — 서비스 이해

오픈소스 OpenSearch를 직접 운영할지 AWS 관리형 OpenSearch Service를 쓸지 결정하는 기준으로, 운영 부담·확장성·비용·기능 차이를 비교한다.

1상대의 출발점 확인

OpenSearch는 오픈소스 검색 엔진이라 누구나 내려받아 자기 서버에 설치할 수 있다. 직접 설치하면 소프트웨어 비용은 없지만, 운영자가 서버 준비, 노드 구성, 보안 설정, 백업, 버전 업그레이드, 장애 복구를 전부 책임져야 한다. 반면 AWS의 OpenSearch Service는 이런 운영 작업을 AWS가 대신 처리하는 대신 인스턴스 사용료가 발생한다. 선택의 핵심은 같은 엔진을 "내가 관리할지" 아니면 "AWS가 관리하게 할지"다.

2질문 제기

같은 OpenSearch 엔진을 쓸 때, 운영 부담과 비용 중 어느 쪽을 선택 기준으로 삼아야 할까?

3구조적 핵심 예시

팀에 서버 운영 인력이 없고 검색 기능을 빠르게 서비스에 붙여야 하는 상황이라면 OpenSearch Service가 맞다. 클러스터 생성부터 확장, 백업, 보안 패치까지 AWS가 처리하므로 검색 기능 개발에만 집중할 수 있다. 반대로 이미 인프라 운영 노하우가 있고 엔진 버전이나 플러그인을 자유롭게 통제해야 하거나 장기 운영 비용을 최소화해야 한다면 직접 설치가 유리할 수 있다.

4단계별 동작 과정

  1. 운영 부담 비교직접 운영은 설치·보안·패치·장애 복구를 모두 수행해야 하고, Service를 쓰면 이 작업이 AWS 책임이 된다.
  2. 확장성과 기능 비교Service는 콘솔 조작이나 API 호출로 노드를 늘리면 되고, 직접 운영은 노드 추가와 재구성을 수동으로 해야 한다. 직접 운영은 플러그인과 설정을 제한 없이 바꿀 수 있는 자유도가 있다.
  3. 비용 비교Service는 인스턴스·스토리지 사용량에 따라 요금이 나오고, 직접 운영은 EC2 비용에 운영 인건비가 더해진다. 규모가 커질수록 직접 운영의 총비용이 낮아질 수 있다.

5본질 요약

OpenSearch Service가 지원하는 엔진 버전(OpenSearch 및 레거시 Elasticsearch OSS)과 버전별 표준·확장 지원 정책을 설명한다.

1상대의 출발점 확인

소프트웨어는 버전마다 기능과 지원 기간이 다르다. OpenSearch Service는 OpenSearch 엔진과 레거시 Elasticsearch OSS(오픈소스 버전) 엔진을 모두 지원하는데, 도메인을 만들 때 어느 버전을 고르느냐에 따라 쓸 수 있는 기능이 달라진다. 버전 선택을 신경 쓰지 않으면 나중에 특정 기능을 쓰려다 지원되지 않는 버전이라 되돌릴 수 없거나, 지원이 끝난 버전을 계속 운영하게 되는 문제가 생긴다.

2질문 제기

도메인을 만들 때 어떤 엔진 버전을 골라야 원하는 기능을 쓰면서 오래 안정적으로 운영할 수 있을까?

3구조적 핵심 예시

새로 시작하는 프로젝트라면 최신 OpenSearch 주 버전을 고르는 것이 기본 선택이다. 각 OpenSearch 버전은 주 버전별로 지원 시작 시점과 표준 지원 기간이 정해져 있고, 표준 지원이 끝난 버전은 별도의 확장 지원(Extended Support) 기간 동안만 패치와 지원을 받는다. 레거시 Elasticsearch OSS 버전은 이전에 Elasticsearch로 쓰던 시스템을 유지해야 하는 경우에만 선택한다.

4단계별 동작 과정

  1. 버전 확인도메인 생성 화면과 공식 문서의 기능·버전 표에서 지원 중인 OpenSearch 버전 목록과 Elasticsearch OSS 버전 목록을 확인한다.
  2. 지원 기간 확인선택한 버전의 표준 지원 종료일을 보고, 종료가 가까우면 확장 지원 기간이나 상위 버전으로의 업그레이드 경로를 확인한다.
  3. 버전 선택과 업그레이드원하는 기능이 지원되는 버전으로 도메인을 만들고, 이후 버전이 나오면 호환성을 확인해 상위 버전으로 업그레이드한다.

5본질 요약

도메인 생성 시 OpenSearch 또는 레거시 Elasticsearch OSS 엔진 버전을 고르고, 버전별 기능과 표준·확장 지원 기간을 기준으로 운영 계획을 세우는 것

Elasticsearch에서 OpenSearch로의 서비스 명칭 변경(rename) 배경과 그 영향·호환성을 다룬다.

1상대의 출발점 확인

이 서비스는 원래 Amazon Elasticsearch Service라는 이름으로 제공됐다. Elasticsearch는 특정 회사가 상표권을 가진 상용 제품명이었고, AWS는 오픈소스 프로젝트를 기반으로 서비스를 운영하다가 해당 프로젝트가 새 이름(OpenSearch)으로 갈라지면서 서비스 이름도 함께 바뀌어야 했다. 이름이 바뀌면 기존 사용자는 자신이 쓰던 기능이 그대로 유지되는지, 접속 주소나 설정이 바뀌지는 않는지 확인이 필요했다.

2질문 제기

서비스 이름이 Elasticsearch에서 OpenSearch로 바뀌었을 때, 기존에 쓰던 기능과 접속 방식은 그대로 유지될까?

3구조적 핵심 예시

이미 생성해 쓰고 있던 도메인(클러스터)은 이름 변경의 영향을 받지 않는다. 접속에 쓰는 엔드포인트 URL, 인증 방식, REST API 호출 방식이 그대로 유지되므로, 기존 애플리케이션 코드를 바꾸지 않고도 계속 사용할 수 있다. 이름이 바뀐 것은 콘솔의 서비스 명칭과 새로 만들어지는 리소스의 표기일 뿐이다.

4단계별 동작 과정

  1. 명칭 변경AWS가 서비스 이름을 Amazon Elasticsearch Service에서 Amazon OpenSearch Service로 바꾸고, 새로 생성되는 리소스와 문서의 표기를 OpenSearch로 통일한다.
  2. 호환성 유지기존 도메인의 엔드포인트와 REST API를 그대로 두어 기존 애플리케이션이 코드 수정 없이 계속 동작하게 한다.
  3. 레거시 지원이전 Elasticsearch 버전으로 만든 도메인은 레거시 엔진으로 계속 지원하고, OpenSearch 버전이 새 기본 선택이 된다.

5본질 요약

인스턴스 유형·스토리지·데이터 전송 등 구성 요소에 따른 요금 구조와 비용을 줄이는 방법을 설명한다.

1상대의 출발점 확인

관리형 서비스는 편리한 대신 사용량에 따라 비용이 계속 발생한다. OpenSearch Service 요금은 도메인을 구성하는 인스턴스의 종류와 개수, 스토리지 용량, 데이터 전송량 등 여러 요소가 결합되어 정해진다. 별 생각 없이 기본값으로 도메인을 만들면 필요보다 큰 인스턴스와 스토리지를 계속 사용해 불필요한 비용이 매달 나간다.

2질문 제기

필요한 성능은 유지하면서 OpenSearch Service의 월 비용을 어떻게 줄일 수 있을까?

3구조적 핵심 예시

처리할 데이터가 적은데 인스턴스를 여러 개 크게 잡으면 비용이 낭비된다. 대신 검색 부하가 낮은 시간대에는 인스턴스를 줄이고, 오래된 로그 인덱스는 자주 접근하지 않으므로 저비용 스토리지(UltraWarm)로 옮기거나 삭제한다. 이렇게 리소스를 실제 사용 패턴에 맞추는 것만으로도 상당한 비용을 줄일 수 있다.

4단계별 동작 과정

  1. 인스턴스 최적화현재 CPU·메모리 사용률을 확인해 과하게 지정된 인스턴스 유형과 개수를 줄이고, UltraWarm 노드(저비용 스토리지 계층)로 자주 안 쓰는 데이터를 옮긴다.
  2. 스토리지 최적화오래된 인덱스는 접근이 적으므로 저비용 스토리지로 이동하거나 보존 기간 정책(Index State Management)을 정해 자동 삭제한다.
  3. 요금 구조 활용예약 인스턴스나 Savings Plans(장기 사용 시 할인받는 요금제)를 적용하고, 필요 없는 데이터 전송이나 백업 보존 일수를 줄여 고정 지출을 낮춘다.

검색 엔진을 직접 설치하지 않고, 데이터를 담을 클러스터를 가장 간단하게 만드는 방법은 무엇일까?

1상대의 출발점 확인

도메인만 만들었다고 검색이 되는 것은 아니다. 검색 엔진은 데이터를 넣기 전까지는 빈 클러스터일 뿐이다. 일반 데이터베이스처럼 값을 저장하면 되지 않을까 생각할 수 있지만, OpenSearch는 문서를 저장할 때 나중에 빠르게 찾을 수 있도록 역색인(단어와 그 단어가 들어 있는 문서의 위치를 미리 연결해 두는 구조)을 만들어야 한다. 이 과정이 색인(indexing)이다.

2질문 제기

문서를 도메인에 넣었을 때, 검색 요청이 올 때마다 전체를 뒤지는 대신 빠르게 찾도록 하려면 어떻게 저장해야 할까?

3구조적 핵심 예시

문서 한 개를 저장하는 것은 "인덱스(문서들을 담는 저장 공간)에 문서를 추가한다"는 REST API 요청 한 번으로 끝난다. 예를 들어 PUT 요청으로 인덱스 이름과 문서 ID를 지정하면, OpenSearch가 문서의 각 단어를 분석해 역색인을 만들고 저장한다. 이후 같은 단어로 검색하면 전체 문서를 훑지 않고 역색인만 보고 해당 문서를 바로 찾는다.

4단계별 동작 과정

  1. 인덱스 준비검색 대상 문서들을 담을 인덱스(문서 묶음 단위)를 만들고, 필요하면 필드별 데이터 형식과 분석 방식을 정의한다.
  2. 문서 업로드REST API로 문서(JSON)를 인덱스에 보내면 OpenSearch가 문서를 단어 단위로 쪼개 분석해 역색인을 구성하고 저장한다.
  3. 검색 실행검색 API로 질의를 보내면 역색인을 이용해 해당 문서를 빠르게 찾아 점수순으로 결과를 돌려준다.

도메인에 저장된 인덱스에 질의를 보내 일치하는 문서를 찾아 결과로 돌려받는 작업.

1상대의 출발점 확인

도메인에 데이터를 넣기 전까지는 검색도 할 수 없다. 기존 방식(시작하기 가이드의 앞 단계)에서는 HTTP 요청을 보내 단일 문서나 여러 문서를 도메인에 저장했고, 그 결과로 단순한 확인 응답만 받았을 뿐이다. 저장된 데이터가 실제로 원하는 조건에 맞는 문서를 찾아내는지, 여러 문서 중에서 무엇이 나오는지는 확인할 수 없었다. 즉 데이터를 넣는 것과 데이터에서 값을 끄집어내는 것은 별개의 작업인데, 초보자는 데이터를 넣은 뒤 그 데이터를 어떻게 꺼내 보는지 모르는 상태에 머문다.

2질문 제기

저장한 문서를 원하는 조건으로 찾아 돌려받으려면 어떻게 해야 할까?

3구조적 핵심 예시

sample-index라는 인덱스에 넣어 둔 여러 문서를 검색하려면, 도메인 엔드포인트에 GET sample-index/_search 요청을 보내고 요청 본문에 query를 적는다. 예를 들어 match_all 쿼리를 보내면 인덱스에 저장된 모든 문서가 결과로 돌아온다. 여기서 핵심은 검색 대상이 "인덱스"라는 저장 공간이고, 요청 본문에 적는 쿼리 내용이 "무엇을 찾을지"를 결정한다는 점이다.

4단계별 동작 과정

Logstash 파이프라인을 사용해 다양한 소스의 데이터를 OpenSearch Service 도메인으로 로딩하는 방법.

1상대의 출발점 확인

여러 소스(로그 파일, 메시지 큐, 데이터베이스 등)에서 데이터를 모아 도메인에 넣으려면 소스마다 전송 방법을 구현해야 했다. 소스 형식이 서로 다르면 맞춤 코드를 작성해야 하고, 전송 중 데이터를 정리하거나 변환하는 작업도 코드 안에 섞여 관리가 어려웠다. 문제는 소스가 늘거나 형식이 바뀔 때마다 그 코드를 고쳐야 한다는 점이다.

2질문 제기

다양한 소스의 데이터를 하나의 파이프라인으로 모아 가공한 뒤 도메인에 로딩할 수는 없을까?

3구조적 핵심 예시

Logstash 파이프라인은 입력 부분에서 여러 소스의 데이터를 받아들이고, 필터 부분에서 데이터를 정리·변환한 뒤, 출력 부분에서 도메인으로 보내는 세 구간으로 이루어진다. 예를 들어 두 종류의 로그 파일이 입력으로 들어오면 형식을 맞춰 도메인에 전달된다.

4단계별 동작 과정

  1. 입력 수집파이프라인의 입력 설정에 정의된 소스들(로그 파일, 메시지 큐 등)에서 데이터를 받아들인다.
  2. 필터 가공받은 데이터에 필터를 적용해 형식을 정리하고 불필요한 부분을 제거하거나 값을 변환한다.
  3. 출력 전송가공된 데이터를 OpenSearch Service 도메인으로 전송해 색인한다. 이후에도 새 데이터가 들어올 때마다 입력-필터-출력 흐름이 반복된다.

5본질 요약

Logstash 파이프라인의 입력-필터-출력 구조로 다양한 소스의 데이터를 모아 가공한 뒤 도메인으로 로딩하는 것

5단계 검색 — 질의와 관련성

OpenSearch 도메인에 저장된 문서를 질의로 찾아내는 검색의 기본 개념과 함께 제공되는 검색 기능들을 한눈에 보여주는 입문 문서다.

1상대의 출발점 확인

데이터를 색인한 뒤에는 원하는 문서를 찾아내는 검색이 필요한데, 기존 데이터베이스의 조회 방식은 정확히 일치하는 값을 찾는 데 특화되어 있다. 문제는 문서의 일부 단어만 알고 있거나, 같은 뜻을 가진 다른 표현으로 찾으려 하면 결과가 나오지 않거나 원하는 문서가 뒤로 밀린다는 점이다. 또 검색 결과의 어떤 문서가 더 관련성이 높은지 판단하는 기준도 제공되지 않았다.

2질문 제기

저장된 문서를 단어 일치를 넘어 관련성까지 따져 원하는 결과를 찾아낼 수는 없을까?

3구조적 핵심 예시

검색은 질의로 받은 단어를 문서와 대조해 각 문서에 점수를 매기는 방식이다. 예를 들어 "검색 엔진"이라는 질의를 보내면 문서마다 그 단어가 얼마나 자주 나오고 어디에 있는지에 따라 관련성 점수가 계산되고, 점수가 높은 문서부터 목록으로 나온다.

4단계별 동작 과정

  1. 질의 전송사용자가 검색 조건(단어, 문장, 필드 지정 등)을 담은 질의를 도메인에 보낸다.
  2. 문서 대조와 점수 계산도메인이 저장된 문서들과 질의를 대조해 각 문서의 관련성 점수를 계산한다.
  3. 결과 정렬과 반환점수가 높은 문서부터 순서대로 정렬해 결과로 돌려준다. 필요에 따라 집계·강조 같은 추가 기능이 함께 적용된다.

5본질 요약

질의와 문서를 대조해 관련성 점수를 계산하고 점수가 높은 문서부터 반환함으로써 저장된 데이터에서 원하는 문서를 찾아내는 것

패키지와 커스텀 플러그인

도메인에 사전·플러그인 같은 커스텀 패키지를 업로드해 검색 기능을 확장하는 방법을 다루는 문서다.

1상대의 출발점 확인

기존에는 OpenSearch 도메인에 검색 기능을 확장하려면 기본 제공되는 기능만 사용해야 했다. 사전(동의어·형태소 분석용)이나 커스텀 플러그인 같은 부가 구성 요소를 넣고 싶어도, 인스턴스 내부 파일을 직접 바꾸는 것은 관리형 서비스인 OpenSearch Service에서는 허용되지 않았다. 그래서 검색어 처리 방식을 세밀하게 조정하거나 특수 플러그인을 쓰는 작업은 사실상 불가능했고, 기능 확장이 필요한 경우 아예 자체 클러스터를 운영해야 하는 부담이 있었다.

2질문 제기

도메인을 재구성하지 않고도 검색 기능을 확장하는 커스텀 패키지를 안전하게 올릴 수는 없을까?

3구조적 핵심 예시

동의어 사전 패키지를 하나 업로드한다고 해 보자. 사용자가 "노트북"을 검색할 때 "laptop"도 함께 검색되도록 하려면, 동의어 매핑이 담긴 텍스트 파일을 S3에 올려 두고, OpenSearch Service 콘솔에서 그 파일 경로를 지정해 패키지로 등록하면 된다. 그러면 해당 도메인의 인덱스가 이 패키지를 참조해 검색 시 동의어가 자동으로 확장된다.

4단계별 동작 과정

  1. 패키지 등록S3에 올린 파일을 OpenSearch Service 콘솔이나 API를 통해 패키지로 등록한다. 이때 파일 형식은 OpenSearch가 정해 둔 형식(예: 동의어 텍스트 파일, ICU 분석기 zip)을 따라야 한다.
  2. 도메인 연결등록한 패키지를 대상 도메인에 연결(associate)한다. 연결 요청이 처리되는 동안 도메인이 잠시 재시작될 수 있으며, 플러그인 패키지라면 클러스터가 해당 플러그인을 로드한다.
  3. 설정 반영연결이 끝나면 인덱스 매핑이나 분석기 설정에서 패키지가 제공하는 리소스(예: 동의어 필터)를 사용할 수 있게 되고, 이후 검색 질의에 그 설정이 그대로 적용된다.

5본질 요약

사전·플러그인 같은 커스텀 패키지를 S3에서 도메인으로 업로드·연결해 검색 기능을 확장하는 것

SQL 지원

OpenSearch 데이터를 익숙한 SQL 문법으로 질의할 수 있게 해주는 기능으로, SQL을 REST API·도구를 통해 실행한다.

1상대의 출발점 확인

기존에 OpenSearch 데이터를 조회하려면 DSL(Domain Specific Language)이라는 JSON 기반 질의 형식을 알아야 했다. 필드 조건, 정렬, 집계를 모두 중첩된 JSON 구조로 조합해야 해서, SQL에 익숙한 개발자나 데이터 분석가에게는 진입 장벽이 높았다. 특히 간단한 조건 검색조차 JSON 괄호를 여러 겹 써야 했고, 기존 데이터베이스 쿼리를 그대로 옮겨 쓰는 것도 불가능했다.

2질문 제기

SQL에 익숙한 사용자가 OpenSearch에 저장된 데이터를 기존 질의 문법 그대로 꺼내 쓸 수는 없을까?

3구조적 핵심 예시

SELECT product_name, price FROM products WHERE price > 100 ORDER BY price DESC LIMIT 10 같은 쿼리를 OpenSearch의 SQL 엔드포인트에 보내면, 이 문장이 내부적으로 OpenSearch의 검색 요청으로 변환되어 실행되고 결과가 표 형태로 돌아온다. 사용자는 JSON DSL을 전혀 몰라도 된다.

4단계별 동작 과정

  1. SQL 제출사용자가 SQL 쿼리를 REST API의 SQL 엔드포인트나 SELECT 문을 지원하는 도구(예: Query Workbench)를 통해 제출한다.
  2. 번역 실행OpenSearch가 SQL 문장을 파싱해 내부의 검색 질의(DSL)로 변환하고, 해당 인덱스에서 데이터를 검색한다. 표준 SQL 외에도 전체 텍스트 검색 같은 OpenSearch 고유 기능은 함수나 문법 형태로 확장되어 있다.
  3. 결과 반환변환된 질의의 실행 결과를 행·열 구조의 표나 JSON으로 반환하며, 집계(aggregation) 결과 역시 별도 필드로 함께 돌려준다.

5본질 요약

OpenSearch 데이터를 SQL 문법으로 질의할 수 있게 해서, JSON DSL 없이도 기존 데이터베이스 지식으로 검색·집계를 수행하는 것

크로스 클러스터 검색

여러 OpenSearch 클러스터(도메인)에 흩어진 인덱스를 하나의 질의로 함께 검색할 수 있게 하는 기능이다.

1상대의 출발점 확인

기존에는 하나의 OpenSearch 도메인(클러스터)에 저장된 데이터만 그 도메인의 검색 API로 조회할 수 있었다. 운영 환경별로 도메인을 분리해 두면(예: 지역별·계정별·용도별) 데이터가 여러 곳에 흩어지는데, 이를 한 번에 검색하려면 각 도메인에 따로 질의를 보내고 애플리케이션 쪽에서 결과를 직접 합쳐야 했다. 그 방식은 코드가 복잡해지고, 전체 결과를 정렬·집계하기도 어려웠다.

2질문 제기

여러 도메인에 흩어진 인덱스를 하나의 질의로 한 번에 검색할 수는 없을까?

3구조적 핵심 예시

"주문" 인덱스가 한국 리전의 도메인 A에, "상품" 인덱스가 다른 리전의 도메인 B에 있다고 하자. 한쪽 도메인에 크로스 클러스터 검색 연결을 만들어 두면, A 도메인의 검색 API에 A의 주문 인덱스와 B의 상품 인덱스를 함께 조건으로 건 질의를 보내는 것만으로 두 도메인의 결과가 하나의 응답으로 합쳐져 돌아온다.

4단계별 동작 과정

  1. 연결 생성한 도메인에서 다른 도메인(원격 클러스터)을 연결 대상으로 등록한다. 연결 시 원격 도메인의 엔드포인트 정보와 인증 자격이 필요하다.
  2. 인덱스 매핑연결된 원격 클러스터의 인덱스에 별칭(alias)을 붙여 로컬 인덱스처럼 참조할 수 있게 만든다.
  3. 통합 검색로컬·원격 인덱스를 함께 지정해 질의를 보내면, 로컬 도메인이 원격 도메인으로 질의를 전달하고 받은 결과를 합쳐 하나의 응답으로 반환한다.

학습 기반 순위

검색 결과의 순위를 사용자 상호작용·피드백 데이터로 기계학습 모델을 학습시켜 개선하는 기능이다.

1상대의 출발점 확인

기존 검색 결과의 순위는 질의와 문서 사이의 통계적 유사도 점수(예: BM25)로만 결정되었다. 점수는 키워드 빈도 같은 정적인 지표만 보기 때문에, 실제로 사용자가 어떤 결과를 더 많이 클릭하는지, 어떤 문서가 더 유용했는지는 전혀 반영하지 못했다. 그래서 문서 내용상 관련성이 높아 보여도 실제 사용자에게는 덜 유용한 결과가 상위에 오르는 일이 계속 발생했다.

2질문 제기

사용자들의 실제 클릭·선호 데이터를 학습에 반영해 검색 결과의 순위 자체를 개선할 수는 없을까?

3구조적 핵심 예시

쇼핑몰 검색 로그에서 "노트북" 질의에 대해 사용자가 클릭한 상품과 클릭하지 않은 상품을 수집했다고 하자. 이 데이터를 기계학습 모델의 학습용 정답(레이블)으로 만들어 OpenSearch의 Learning to Rank 플러그인에 등록하면, 이후 "노트북" 검색 시 기존 유사도 점수와 모델 점수를 함께 계산해 사용자 선호가 반영된 순서로 결과를 돌려준다.

4단계별 동작 과정

  1. 학습 데이터 준비질의-문서 쌍마다 사용자 상호작용(클릭, 구매 등)을 바탕으로 관련성 등급을 붙여 학습 데이터를 만든다.
  2. 모델 학습·업로드이 데이터로 순위 학습 모델(XGBoost 계열 등)을 훈련시키고, 학습된 모델 파일을 OpenSearch에 업로드해 색인에 등록한다.

비동기 검색과 Point in time

큰 질의를 백그라운드에서 처리하는 비동기 검색과, 특정 시점의 일관된 인덱스 상태(PIT) 위에서 페이징 검색을 가능하게 하는 기능이다.

1상대의 출발점 확인

기존에는 검색 질의를 보내면 그 요청이 끝날 때까지 클라이언트가 계속 기다려야 했다(sync, 동기 방식). 데이터가 많거나 집계가 무거운 질의는 실행에 수십 초가 걸릴 수 있어, 그동안 연결을 붙잡아 두어야 했고 요청이 중간에 끊기면 실행 결과도 함께 사라졌다. 또 페이지를 넘기며 많은 결과를 읽는 페이징 검색은, 페이지를 넘기는 사이에 데이터가 바뀌면 중복되거나 누락되는 결과가 생기는 문제도 있었다.

2질문 제기

무거운 질의를 백그라운드로 처리하면서도, 일관된 시점의 데이터 위에서 안정적으로 페이지를 넘기며 결과를 읽을 수는 없을까?

3구조적 핵심 예시

수백만 문서를 대상으로 한 집계 질의를 보낸다고 하자. 비동기 검색을 쓰면 요청은 즉시 작업 ID를 돌려주고, 사용자는 그 ID로 나중에 상태를 확인해 완료된 결과만 받아 간다. 동시에 Point in time(PIT)을 열어 두면 검색 시작 시점의 인덱스 상태가 고정되어, 페이지를 넘겨도 그 시점 기준의 결과가 계속 일관되게 나온다.

4단계별 동작 과정

  1. 비동기 작업 등록클라이언트가 비동기 검색 요청을 보내면 서버가 작업을 등록하고 즉시 작업 ID를 반환한다. 질의는 백그라운드에서 계속 실행된다.
  2. 결과 확인·수신사용자가 작업 ID로 상태를 조회해 실행이 끝났는지 확인하고, 완료되면 저장된 전체 결과를 한 번에 받아 간다.
  3. PIT 기반 페이징검색 시작 시 PIT 모드로 열어 둔 일관된 스냅샷(고정된 시점의 인덱스 상태) 위에서 페이지를 넘기며 추가 결과를 읽는다. PIT를 닫으면 그 고정 상태도 해제된다.

무거운 질의를 백그라운드로 돌려 클라이언트를 기다리게 하지 않고, PIT로 고정된 시점의 데이터 위에서 일관된 페이징 검색을 가능하게 하는 것

2질문 제기

단어 일치가 아니라 의미가 비슷한 문서를 찾고, 에이전트가 질의를 구성해주는 검색도 가능할까?

3구조적 핵심 예시

4단계별 동작 과정

  1. 벡터 저장신경망 모델(임베딩 모델)로 각 문서를 임베딩 벡터로 변환하고, 인덱스에 벡터 필드로 함께 저장한다.
  2. 질의 변환·검색사용자의 질의를 같은 모델로 벡터화한 뒤, 저장된 문서 벡터들과의 거리(유사도)를 계산해 가까운 순서로 결과를 뽑는다. 자연어 질의를 받는 방식·에이전트가 여러 질의를 스스로 구성하는 방식도 이 파이프라인 위에서 동작한다.
  3. 결과 반환유사도 순으로 정렬된 문서 목록(필요하면 기존 키워드 검색 결과와 결합)을 하나의 응답으로 돌려준다.

직접 질의(Direct Queries)

도메인에 데이터를 저장하지 않고 S3·CloudWatch Logs·Security Lake·Managed Prometheus 같은 외부 데이터 소스를 SQL·PPL로 직접 질의하는 기능이다.

1상대의 출발점 확인

기존에는 OpenSearch에서 데이터를 검색하려면 먼저 그 데이터를 OpenSearch 도메인 안의 인덱스로 색인(적재)해야 했다. S3 버킷의 로그, CloudWatch Logs, Security Lake 같은 곳에 이미 데이터가 있는 경우에도, 질의하려면 파이프라인으로 데이터를 복사해 도메인에 넣고 색인을 만들어야 했다. 데이터가 계속 늘어나는 환경에서는 복사 비용과 지연이 계속 발생했다.

2질문 제기

데이터를 도메인 안으로 복사하지 않고, 외부 데이터 소스에 있는 그대로 질의할 수는 없을까?

3구조적 핵심 예시

S3 버킷에 저장된 접속 로그를 분석한다고 하자. OpenSearch에 인덱스를 만들지 않고, 질의 대상으로 S3 위치와 형식(예: Parquet, CSV)만 등록한 뒤 SQL이나 PPL(파이프라인 처리 언어) 질의를 보내면, OpenSearch가 외부 소스에 직접 질의해 결과를 돌려준다. 데이터는 원래 있던 곳에 그대로 남는다.

4단계별 동작 과정

  1. 데이터 소스 등록질의하려는 외부 소스(S3, CloudWatch Logs, Security Lake, Managed Prometheus 등)의 위치와 접근 자격을 OpenSearch에 데이터 소스로 등록한다.
  2. 질의 실행사용자가 SQL·PPL로 작성한 질의를 보내면, OpenSearch가 이를 외부 소스의 질의 엔진(예: 데이터 카탈로그·쿼리 엔진)으로 전달해 실행한다.
  3. 결과 반환외부 소스에서 실행된 질의 결과를 OpenSearch 응답 형태로 돌려준다. 도메인 안에 데이터가 복사되지는 않는다.

5본질 요약

데이터를 OpenSearch 인덱스로 복사하지 않고, S3·CloudWatch Logs 등 외부 데이터 소스를 SQL·PPL로 직접 질의해 결과를 받아오는 것

1상대의 출발점 확인

기존 검색은 키워드 일치 방식을 쓴다. 문서와 질의를 텍스트 문자열로 비교해 같은 단어가 몇 번 등장하는지, 얼마나 정확히 맞는지로 결과를 정렬한다. 이 방식은 철자가 다르거나 같은 뜻의 다른 표현(동의어)을 쓰면 제대로 찾지 못하고, "비슷한 의미"라는 것을 전혀 알지 못한다. 예를 들어 "고양이"로 검색하면 "냥이" 또는 "A cat" 같은 문장은 같은 대상이라도 키워드가 안 맞아 결과에서 빠진다. 의미는 같아도 형태가 다르면 검색이 실패하는 것이 키워드 검색의 명확한 한계다.

2질문 제기

형태가 아니라 의미가 같은 문서를 어떻게 찾아낼 수 있을까?

3구조적 핵심 예시

각 문서를 숫자 벡터(방향과 길이를 가진 좌표값 목록)로 바꾼다. "고양이"는 어느 벡터 공간에서 [0.2, 0.8, 0.5] 같은 좌표로, "냥이"는 거의 같은 방향의 [0.25, 0.79, 0.48] 좌표로 매핑된다. 검색 질의도 같은 공간의 벡터로 바꾼 뒤, 저장된 모든 벡터와의 거리를 계산해 가장 가까운 k개를 결과로 돌려준다. 단어 표기가 달라도 의미가 같으면 벡터 좌표가 가까워지므로 같은 문서로 찾아진다.

4단계별 동작 과정

  1. 벡터 임베딩 생성문서의 텍스트를 머신러닝 모델로 통과시켜 각 문서를 고정 길이의 숫자 벡터로 변환하고, 이 벡터를 인덱스에 저장한다.
  2. 질의 벡터화와 거리 계산검색 질의도 같은 모델로 벡터로 바꾸고, 저장된 모든 벡터와의 유사도(벡터 간 거리)를 k-NN 방식으로 계산해 가까운 순서로 정렬한다.
  3. 상위 k개 반환거리가 가장 가까운 상위 k개 문서를 검색 결과로 돌려주고, 벡터 검색을 위해 별도로 구성한 k-NN 인덱스를 최신 상태로 유지해 검색 정확도를 보장한다.

GPU 지원 인스턴스에서 벡터 인덱스 생성·병합 작업을 가속화해 대규모 벡터 데이터를 빠르게 처리하는 기능.

1상대의 출발점 확인

벡터 검색은 문서마다 수백 차원의 숫자 벡터를 만들고, 검색할 때마다 저장된 모든 벡터의 거리를 계산한다. 데이터가 수억 건 수준으로 커지면 이 거리 계산량이 폭증해 CPU 기반 인스턴스에서는 인덱스 생성과 병합(작은 세그먼트들을 합치는 작업)에 수 시간이 걸릴 수 있다. 벡터 데이터가 많아질수록 CPU 처리 속도가 병목이 되어 색인 시간이 길어지고, 새 데이터가 검색에 반영되기까지 지연이 커지는 것이 기존 방식의 한계다.

2질문 제기

대규모 벡터 데이터의 색인 작업을 어떻게 실용적인 시간 안에 끝낼 수 있을까?

3구조적 핵심 예시

벡터의 거리 계산은 행렬 연산(여러 숫자 묶음에 같은 계산을 동시에 적용하는 연산)이다. GPU 인스턴스는 수천 개의 코어로 이 행렬 연산을 동시에 처리한다. 예를 들어 CPU가 1천 개 벡터의 거리를 순서대로 계산하는 동안 GPU는 1천 개를 한 번에 계산해 완료 시간을 크게 줄인다. 인덱스 생성·병합 같은 병렬화 가능한 단계만 GPU로 보내 처리한다.

4단계별 동작 과정

  1. GPU 지원 인스턴스 선택벡터 인덱스 생성·병합 전용 GPU 인스턴스 유형을 도메인에 구성하고, 도메인 엔드포인트에 GPU 인덱스 생성 요청을 보낸다.
  2. GPU 병렬 처리요청받은 벡터 인덱스의 생성·병합 작업을 GPU 코어에서 병렬로 수행해 CPU보다 훨씬 빠르게 벡터 간 거리 계산과 인덱스 구축을 끝낸다.
  3. 결과 반영과 비용 절감생성된 인덱스를 검색에 사용하고, 작업이 끝난 GPU 인스턴스는 필요할 때만 켜두는 방식으로 비용을 관리한다.

OpenSearch Serverless가 벡터 인덱스의 세그먼트를 자동으로 최적화하는 기능과, Amazon S3에 보관한 대용량 벡터를 서비스로 가져와 검색에 활용하는 통합 기능.

1상대의 출발점 확인

OpenSearch Serverless는 서버 관리 없이 검색 기능을 제공하지만, 벡터 인덱스는 데이터가 추가·삭제될 때마다 작은 세그먼트(인덱스의 저장 단위)가 계속 생긴다. 세그먼트가 쌓이면 검색할 때 여러 세그먼트를 모두 뒤져야 해서 속도가 느려지고 저장 공간도 낭비된다. 사용자가 직접 세그먼트를 병합하거나 관리하는 것은 서버리스 환경에서 할 수 없고, 대용량 벡터를 미리 S3에 보관해도 서비스에 올려 검색에 쓰려면 수동 가져오기 절차가 필요했던 것이 기존 방식의 한계다.

2질문 제기

서버 관리 없이 벡터 인덱스의 성능을 자동으로 유지하고, S3의 대용량 벡터를 어떻게 검색에 활용할 수 있을까?

3구조적 핵심 예시

서비스가 인덱스의 세그먼트 수와 크기를 계속 감시하다가, 세그먼트가 일정 개수 이상 쌓이면 서비스 내부에서 알아서 병합한다. 사용자는 병합 시점이나 방식을 정하지 않는다. 동시에 S3에 보관해 둔 벡터 데이터는 서비스가 읽어 자동으로 인덱스에 반영한다. 예를 들어 수십억 건의 벡터가 들어 있는 파일을 S3에 올려 두면, 사용자는 한 번의 구성만으로 그 벡터를 검색 대상에 포함시킨다.

4단계별 동작 과정

  1. 자동 병합서비스가 벡터 인덱스의 세그먼트 상태를 감시하고, 기준을 넘으면 세그먼트를 자동 병합해 검색 성능과 저장 효율을 유지한다.
  2. S3 벡터 가져오기Amazon S3에 저장된 대용량 벡터 데이터를 서비스가 읽어 벡터 인덱스로 적재하고, 이후 검색 질의의 대상에 포함시킨다.
  3. 지속 최적화데이터가 계속 추가되어도 병합과 정리가 반복 실행되어 별도 운영 조작 없이 인덱스가 최적 상태를 유지한다.

5본질 요약

OpenSearch Serverless가 벡터 인덱스의 세그먼트를 자동 병합해 성능을 유지하고, S3에 보관한 대용량 벡터를 서비스로 가져와 검색에 활용하게 하는 통합 기능

1상대의 출발점 확인

검색 서비스에 데이터를 넣으면 그 데이터는 인덱스(검색 가능한 저장 단위)로 만들어져 보관된다. 도메인을 운영할 때는 인덱스를 만들고, 설정을 바꾸고, 필요 없어진 인덱스를 지우는 작업이 반복된다. 이러한 작업을 인덱스별로 수동으로 하다 보면 잘못된 설정이 그대로 남아 검색 성능이 떨어지고, 오래된 인덱스가 계속 쌓여 저장 비용이 늘어난다. 각 인덱스를 언제 만들고 어떻게 설정하며 언제 없앨지가 관리되지 않는 것이 기존 방식의 한계다.

2질문 제기

도메인 안의 인덱스들을 생성부터 삭제까지 어떻게 체계적으로 관리할 수 있을까?

3구조적 핵심 예시

도메인은 인덱스 관리를 위한 REST API(HTTP 요청으로 기능을 호출하는 인터페이스)를 제공한다. 운영자는 한 번의 API 호출로 인덱스를 만들고, 샤드(인덱스를 나눈 저장 조각) 수 같은 설정을 지정한다. 데이터가 자라면 설정을 바꾸거나 새 인덱스로 교체하고, 오래된 인덱스는 삭제 API로 제거한다. 모든 작업이 명령 하나로 끝나고, 각 인덱스의 상태는 언제든 조회할 수 있다.

4단계별 동작 과정

  1. 인덱스 생성과 설정인덱스 생성 API로 새 인덱스를 만들고 샤드 수, 복제본 수 등 저장과 검색에 영향을 주는 설정을 함께 지정한다.
  2. 인덱스 운영과 갱신데이터 증가에 맞춰 인덱스 설정을 변경하거나 새 인덱스로 전환하고, 상태 조회로 크기와 검색 성능을 확인한다.
  3. 인덱스 삭제더 이상 필요 없는 인덱스를 삭제 API로 제거해 저장 공간과 비용을 회수하고, 삭제 전에 인덱스를 닫아 두어 접근을 차단하는 방식도 사용한다.

데이터 접근 빈도와 비용에 따라 핫(OR1)·웜(UltraWarm)·콜드(Cold) 저장소 계층으로 나눠 인덱스를 옮겨 저장 비용을 줄이는 기능.

1상대의 출발점 확인

기본적으로 모든 인덱스는 빠른 저장소(OR1)에 저장되어 언제든 빠르게 검색된다. 하지만 시계열 로그처럼 시간이 지나면 조회 빈도가 급격히 떨어지는 데이터도 똑같은 비싼 저장소에 계속 두면, 거의 읽지 않는 데이터 때문에 저장 비용이 계속 발생한다. 모든 데이터를 같은 저장소에 두는 방식은 데이터의 접근 빈도와 비용을 전혀 고려하지 않는다는 것이 한계다.

2질문 제기

자주 사용하지 않는 데이터의 저장 비용을 검색 속도를 유지하면서 어떻게 줄일 수 있을까?

3구조적 핵심 예시

인덱스를 접근 빈도에 따라 세 계층에 나눠 저장한다. 최근 데이터는 빠른 OR1(핫)에 두어 즉시 검색하고, 한 달쯤 지난 데이터는 UltraWarm(웜)으로 옮겨 비용을 줄이면서도 검색은 가능하게 한다. 더 오래된 데이터는 Cold(콜드) 계층으로 내려 거의 비용 없이 보관하고 필요할 때만 검색에 불러온다. 운영자는 인덱스마다 "언제 웜으로 옮길지" 같은 규칙만 정하면 된다.

4단계별 동작 과정

  1. 핫 계층 저장생성된 인덱스를 OR1 인스턴스(고성능 SSD 기반)에 저장해 가장 빠른 검색 성능을 제공한다.
  2. 웜 계층 이동접근 빈도가 낮아진 인덱스를 UltraWarm 노드로 옮겨 저비용 저장에 싣되 검색은 계속 지원한다.
  3. 콜드 계층 보관더 오래된 인덱스를 Cold 계층에 보관해 저장 비용을 최소화하고, 필요할 때만 검색 가능 상태로 활성화한다.

인덱스는 생성된 뒤에도 관리할 일이 계속 생긴다. 일정 크기 이상이 되면 새 인덱스로 전환(롤오버)해야 하고, 오래되면 축소하거나 삭제해야 한다. 이런 작업을 운영자가 시점마다 직접 API로 실행하면, 잊거나 놓친 경우 인덱스가 무한정 커져 검색이 느려지고 비용이 늘어난다. 수명주기 작업이 사람의 기억과 수작업에 의존하는 것이 기존 방식의 한계다.

2질문 제기

인덱스의 수명주기 작업을 사람 대신 규칙으로 자동 실행할 수 없을까?

3구조적 핵심 예시

운영자는 인덱스 패턴에 정책을 하나 붙인다. 정책은 "이 인덱스가 30GB를 넘으면 새 인덱스로 바꾸고, 30일이 지나면 웜 계층으로 옮기고, 90일이 지나면 삭제한다" 같은 상태 전이 규칙들의 묶음이다. 보통 10분 간격으로 실행되는 ISM이 인덱스 상태를 확인하다가 조건이 맞으면 해당 작업을 자동으로 수행한다. 사람이 개입할 필요가 없다.

4단계별 동작 과정

  1. 정책 정의와 적용상태별 수행할 작업(롤오버, 축소, 삭제 등)과 전이 조건을 담은 정책을 만들고 대상 인덱스에 적용한다.
  2. 주기적 상태 확인ISM이 주기마다 정책이 붙은 인덱스들을 점검해 조건(크기, 나이 등)이 충족됐는지 판단한다.
  3. 자동 작업 실행조건이 충족된 인덱스에 정책의 작업을 자동 수행하고 다음 상태로 전이시켜 수명주기를 끝까지 진행한다.

인덱스 데이터를 다른 환경으로 옮길 때 기존에는 스냅샷을 떠서 새 클러스터에 복원하거나, 검색 API로 문서를 읽어 다시 색인하는 방식을 썼습니다. 스냅샷 복원은 주기적으로만 실행되므로 그 사이에 생긴 데이터가 빠지고, 복원이 끝나기 전까지 대상 클러스터는 서비스할 수 없습니다. 검색으로 다시 색인하는 방식은 인덱스가 클수록 시간이 오래 걸리고 인덱스를 읽는 동안 원본 클러스터에 부하가 걸립니다. 두 방식 모두 데이터가 계속 쌓이는 운영 환경에서는 지연과 중단이 생깁니다.

2질문 제기

인덱스를 운영을 멈추지 않으면서 거의 실시간으로 다른 클러스터나 리전에 복제하거나 옮길 수는 없을까?

3구조적 핵심 예시

교차 클러스터 복제(cross-cluster replication, 서로 다른 클러스터 간에 인덱스를 복제하는 기능)는 원본 인덱스의 변경 로그를 계속 따라가며 대상 인덱스에 같은 문서를 똑같이 적용합니다. 원본과 대상 클러스터는 각자 독립적으로 검색을 처리하므로, 원본에 쓰는 트래픽과 대상에서 읽는 트래픽이 서로 간섭하지 않습니다. 데이터 센터 하나에 장애가 나도 다른 리전의 복제본으로 서비스를 이어갈 수 있습니다.

4단계별 동작 과정

  1. 리더 인덱스 구성대상 클러스터의 Kibana에서 복제하려는 원본 인덱스를 리더(leader, 복제의 원본이 되는 인덱스)로 지정하고 팔로워 인덱스(follower, 리더를 따라가는 인덱스)를 만든다. 지정 즉시 리더의 기존 데이터가 팔로워로 복사된다.
  2. 변경 사항 계속 반영이후 원본에 문서가 추가·수정·삭제될 때마다 해당 변경 내용을 팔로워가 실시간으로 받아 같은 순서로 적용한다. 원본을 읽지 않아도 되므로 원본 성능에 영향이 없다.
  3. 전환과 활용복제가 따라잡은 상태에서 필요하면 팔로워를 독립 클러스터로 전환(promote)하거나, 재해 복구 시 팔로워의 인덱스를 주 서비스로 승격한다. 리모트 리인덱스(remote reindex)도 같은 원리로 다른 클러스터의 인덱스를 대상 클러스터로 옮겨 새 인덱스로 다시 색인한다.

5본질 요약

원본 인덱스의 변경 내용을 계속 전달받아 대상 클러스터에 동일한 인덱스를 유지함으로써 운영 중단 없이 실시간 복제와 데이터 이동을 가능하게 하는 것

도메인의 상태·성능·보안을 CloudWatch 지표, 로그, 이벤트, CloudTrail 감사라는 AWS 모니터링 도구 묶음으로 종합적으로 살펴보는 방법의 개요.

1상대의 출발점 확인

도메인(OpenSearch 클러스터를 AWS에서 관리하는 단위)이 커지면 노드 수와 데이터 양이 늘어나고, 그만큼 어떤 지표를 봐야 하는지도 다양해집니다. 기존에는 서버에 직접 접속해 로그 파일을 열거나 상태 API를 호출해 일일이 확인해야 했고, 문제가 생겨도 "언제부터, 무엇 때문에" 악화됐는지 사후에 추적하기 어려웠습니다. 단일 도구로 상태·성능·보안·감사 기록을 한곳에서 보지 못하면 장애 원인을 찾는 데 오래 걸립니다.

2질문 제기

도메인의 상태와 성능, 그리고 보안 관련 기록을 한곳에서 종합적으로 추적할 방법은 없을까?

3구조적 핵심 예시

Amazon OpenSearch Service는 도메인을 만들면 CloudWatch 지표, CloudWatch Logs, EventBridge 이벤트, CloudTrail 기록을 자동으로 연결하는 모니터링 묶음을 제공합니다. CPU 사용률 같은 성능 지표는 CloudWatch에 쌓이고, 느린 검색 로그는 CloudWatch Logs에 전달되며, 도메인 생성 같은 상태 변화는 EventBridge 이벤트로 나가고, API 호출 기록은 CloudTrail에 남습니다. 콘솔의 모니터링 탭 하나에서 이 네 경로를 모두 열어볼 수 있습니다.

4단계별 동작 과정

  1. 지표 수집도메인이 건강 상태, CPU·메모리·디스크 사용률, 검색 처리량 등의 지표를 CloudWatch에 자동 게시한다. 별도 설정 없이 콘솔에서 그래프로 확인된다.
  2. 로그 게시느린 검색·느린 인덱싱·오류·애플리케이션 로그를 사용자가 켜면 CloudWatch Logs로 전달되어 도메인 내부 활동을 검색할 수 있다.
  3. 이벤트와 감사 기록 확인상태 변화는 EventBridge 이벤트로, API 호출은 CloudTrail로 각각 수집되어 자동화 트리거와 보안 감사에 쓰인다. 네 채널을 함께 보면 상태·성능·보안을 종합적으로 진단할 수 있다.

1상대의 출발점 확인

도메인의 노드가 몇 개인지, CPU가 얼마나 쓰이는지, 검색이 얼마나 느려졌는지는 서버에 직접 들어가 봐야 알 수 있었습니다. 그러나 OpenSearch Service는 클러스터를 AWS가 관리하므로 노드에 직접 접속할 수 없고, 상태를 확인할 통로가 제한적입니다. 이 때문에 문제가 생겨도 "지금 어느 자원이 부족한지"를 실시간으로 판단하기 어렵고, 장애가 나고 나서야 원인을 뒤늦게 추적해야 했습니다.

2질문 제기

노드에 직접 접속하지 않고도 도메인의 CPU·메모리·디스크·처리량을 실시간으로 추적할 수는 없을까?

3구조적 핵심 예시

OpenSearch Service는 클러스터의 각 지표를 CloudWatch로 자동 게시합니다. 예를 들어 CPUUtilization(CPU 사용률)과 FreeStorageSpace(남은 저장 공간)는 노드별·클러스터 전체별로 지표가 쌓이고, 콘솔의 모니터링 그래프에서 기간을 정해 바로 확인할 수 있습니다. 이 지표를 바탕으로 CloudWatch 알람을 설정하면 임계값을 넘었을 때 이메일 등으로 통지도 받습니다.

4단계별 동작 과정

  1. 지표 자동 게시도메인이 클러스터와 노드 단위의 지표(CPU, 메모리, 디스크 사용률, 검색·인덱싱 처리량, 노드 상태 등)를 CloudWatch에 자동으로 보낸다. 유휴 여유 공간은 데이터 노드와 초과 스토리지(ultra-warm, 자주 접근하지 않는 데이터를 저비용으로 저장하는 계층)로 나뉘어 게시된다.
  2. 모니터링 그래프 확인OpenSearch Service 콘솔의 모니터링 탭에서 지표를 선택해 기간별 추이를 그래프로 본다. 여러 지표를 한 그래프에 겹쳐 상관관계를 파악할 수 있다.
  3. 알람 설정CloudWatch 알람으로 지표가 임계값을 넘거나 일정 시간 아래로 내려가면 알림을 받는다. 이를 통해 장애 전에 자원 부족을 감지하고 인스턴스 확장을 계획한다.

5본질 요약

1상대의 출발점 확인

지표만으로는 "어떤 검색 요청이 느린지", "어떤 문서가 색인될 때 오류가 났는지" 같은 구체적인 내용은 알 수 없습니다. 기존에는 로그를 보려면 노드 안에서 로그 파일을 직접 열어야 했지만, OpenSearch Service는 관리형 서비스라 그 경로가 막혀 있습니다. 검색이 전체적으로 느려졌을 때 원인이 특정 쿼리인지, 색인이 밀린 것인지 판단할 방법이 없었습니다.

2질문 제기

도메인 안에서 어떤 검색·인덱싱·오류·보안 활동이 일어나고 있는지 로그로 들여다볼 수는 없을까?

3구조적 핵심 예시

OpenSearch Service는 검색 요청 중 임계값보다 오래 걸린 것들을 "느린 검색 로그(slow search log)"로, 색인 작업 중 느린 것들을 "느린 인덱싱 로그(slow index log)"로 남깁니다. 예를 들어 5초를 넘긴 검색 쿼리와 그 소요 시간이 로그 항목으로 기록됩니다. 이 로그를 CloudWatch Logs에 게시하도록 설정하면 콘솔과 로그 검색에서 원인 쿼리를 찾아낼 수 있습니다.

4단계별 동작 과정

  1. 로그 선택과 게시 설정콘솔에서 느린 검색·느린 인덱싱·오류·애플리케이션 로그 중 필요한 것을 켜고, 전달받을 CloudWatch Logs 로그 그룹을 지정한다. 로그는 index(문서를 저장하는 구조) 또는 클러스터 수준에서 세분화해 남길 수 있다.
  2. 임계값에 따라 기록설정한 시간 임계값을 넘는 검색·인덱싱 작업이 발생하면 해당 요청의 내용과 소요 시간이 로그로 기록된다. 보안 감사 로그를 켜면 인증·권한·자료 접근 시도가 함께 남는다.
  3. CloudWatch Logs에서 분석게시된 로그를 CloudWatch Logs 콘솔에서 검색하거나 Logs Insights로 질의해 느린 쿼리의 패턴을 찾는다. 이를 통해 성능 저하의 원인과 보안 위협 시도를 진단한다.

1상대의 출발점 확인

도메인에 무슨 일이 생겼는지 알려면 콘솔에 들어가 상태를 직접 확인하거나, 지표 알람이 울리기를 기다려야 했습니다. 그러나 인스턴스 유형 변경이 끝났는지, 도메인이 삭제됐는지, 구성 오류가 났는지 같은 상태 변화는 지표 그래프에 바로 잡히지 않아 놓치기 쉽습니다. 이런 변화를 눈치채지 못하면 자동화 작업이 실패했거나 도메인이 의도치 않게 바뀌어도 뒤늦게야 알게 됩니다.

2질문 제기

도메인의 상태가 바뀌는 순간을 놓치지 않고 자동으로 감지해 다른 시스템에 전달할 수는 없을까?

3구조적 핵심 예시

OpenSearch Service는 도메인 상태가 바뀔 때마다 이벤트를 Amazon EventBridge(이벤트를 받아 규칙에 따라 대상으로 전달하는 서비스)에 게시합니다. 예를 들어 도메인이 생성되거나 삭제될 때, 구성 변경이 시작되거나 끝날 때, 오류 알림이 발생할 때 이벤트가 생성됩니다. 이 이벤트에 규칙을 연결하면 Lambda 함수나 SNS 알림 같은 대상을 자동으로 실행시킬 수 있습니다.

4단계별 동작 과정

  1. 이벤트 생성도메인 생성·삭제·구성 변경·오류 알림 등 상태 변화가 발생하면 OpenSearch Service가 해당 이벤트를 EventBridge로 보낸다. 이벤트에는 도메인 이름과 변경 내용이 담긴 세부 정보가 포함된다.
  2. 규칙 매칭EventBridge에 미리 만든 규칙이 이벤트의 유형과 소스를 조건에 맞춰 매칭한다. 조건에 맞는 이벤트만 다음 단계로 전달된다.
  3. 대상 실행규칙에 연결된 대상(예: Lambda 함수로 알림 발송, SNS로 이메일 전송, 다른 워크플로 시작)이 이벤트에 따라 자동으로 실행된다. 시스템이 사람 개입 없이 상태 변화에 반응한다.

Serverless 개요와 비교

클러스터 관리 없이 검색·분석 용량을 자동으로 조정하는 서버리스형 OpenSearch 로, 관리형 도메인과의 차이를 이해하는 출발점

1상대의 출발점 확인

기존 OpenSearch Service는 관리형 도메인(managed domain)이라 해도 인스턴스 유형과 개수를 직접 골라야 했다. 사용량이 적을 때는 자는 컴퓨팅 자원에 비용을 계속 내야 했고, 검색량이 갑자기 늘면 인스턴스를 추가하는 작업을 미리 해 두지 않으면 응답이 느려졌다. 클러스터 상태를 보고 용량을 키우고 줄이는 일이 운영자의 상시 작업이었다.

2질문 제기

클러스터 크기를 누가 언제 정할지 고민하지 않고, 사용량에 따라 비용과 성능이 자동으로 맞춰지게 할 수 없을까?

3구조적 핵심 예시

OpenSearch Serverless는 도메인 대신 컬렉션(collection)이라는 검색·분석 단위를 만들고, 그 안에서 컴퓨팅 유닛(OCU, OpenSearch Compute Unit)이 배치 단위로 자동 증감한다. 사용자가 없으면 컴퓨팅 유닛이 0으로 내려가 비용이 발생하지 않고, 검색 요청이 들어오면 자동으로 늘어난다. 관리형 도메인처럼 인스턴스 유형을 고르는 화면 자체가 없다.

4단계별 동작 과정

  1. 컬렉션 생성관리형 도메인 대신 컬렉션을 만들고, 검색용인지 분석용인지 용도를 지정한다.
  2. 자동 확장·축소시스템이 컴퓨팅 유닛을 사용량에 맞춰 늘리고 줄이며, 유휴 상태에서는 0까지 내려간다.
  3. 비용·성능 정산실제로 사용된 컴퓨팅 유닛 시간과 저장 용량만큼만 과금되어, 놀고 있는 자원에 대한 비용이 사라진다.

5본질 요약

클러스터를 직접 관리하는 대신 검색·분석 용량을 사용량에 따라 0부터 자동으로 조정해 비용과 운영 부담을 없애는 것

Serverless 의 기본 단위인 컬렉션과, 벡터 임베딩을 저장·검색하는 벡터 검색 컬렉션을 만들고 다루는 방법

2질문 제기

3구조적 핵심 예시

4단계별 동작 과정

  1. 벡터 검색 컬렉션 생성AWS 콘솔에서 벡터 검색용 컬렉션을 만들고, 임베딩 모델을 지정해 벡터 생성을 맡긴다.
  2. 문서와 벡터 저장데이터를 넣을 때 임베딩이 함께 생성되어 문서 필드에 벡터가 저장된다.
  3. 근접 검색 수행검색어를 같은 방식으로 벡터로 바꾼 뒤 저장된 벡터들과의 거리를 계산해 가까운 순서로 결과를 돌려준다.

Serverless 보안

IAM·데이터 접근 제어·암호화·네트워크 접근·SAML 등 Serverless 컬렉션을 보호하는 보안 체계

1상대의 출발점 확인

기존 관리형 도메인에서는 보안을 설정하려면 클러스터 안의 사용자 계정, 도메인 정책, IAM 역할, 네트워크 접근 규칙을 각각 만들어 서로 연결해야 했다. 설정 위치가 여러 곳으로 나뉘어 있어 어디서 접근을 막아야 하는지 헷갈렸고, 누락된 설정 하나가 데이터 노출로 이어지기 쉬웠다.

2질문 제기

컬렉션에 누가 어떤 데이터를 읽고 쓸 수 있는지, 네트워크와 암호화는 어떻게 한곳에서 제어할 것인가?

3구조적 핵심 예시

Serverless의 보안은 데이터 접근 제어(data access control)를 IAM 정책으로 통일한 것이 핵심이다. 컬렉션을 만들 때 IAM 역할이 그 컬렉션의 인덱스와 특정 필드까지 읽고 쓸 수 있는지 정책으로 정하면, 사용자는 AWS 자격 증명으로 그 권한 범위 안에서만 접근한다. 여기에 KMS로 암호화, VPC(가상 사설망)로 네트워크 접근 제한, SAML로 기업 자격 증명 연동을 덧붙인다.

4단계별 동작 과정

  1. IAM 정책 작성어떤 IAM 역할이 어떤 컬렉션·인덱스·필드에 접근할 수 있는지 권한을 정책으로 정의한다.
  2. 네트워크·암호화 설정VPC 안에서만 접근을 허용하고, KMS 키로 저장 데이터를 암호화한다.
  3. 자격 증명 연동SAML(보안 자격 증명을 외부 인증 서버와 교환하는 표준)로 기업의 기존 인증 체계와 연결해 로그인을 통일한다.

Serverless 용량·스케일·모니터링

용량 한도 관리와 scale-to-zero 로 비용을 조절하고, CloudWatch·CloudTrail·EventBridge 로 상태를 모니터링하는 방법

1상대의 출발점 확인

클러스터를 직접 관리하는 기존 방식에서는 용량이 부족해지기 전에 운영자가 인스턴스를 추가하고, 놀 때는 줄여야 했다. 용량 한도를 초과하면 요청이 실패하거나 성능이 떨어졌고, 오늘 얼마나 쓸지 예측이 틀리면 비용 낭비나 장애가 그대로 나타났다. 상태를 알려면 각종 지표를 대시보드에서 직접 조합해 확인해야 했다.

2질문 제기

용량이 자동으로 조정되는 환경에서 한도를 초과하지 않게 통제하고, 상태를 어디서 어떻게 관찰할 것인가?

3구조적 핵심 예시

Serverless는 컴퓨팅 유닛(OCU)과 저장 용량에 각각 한도가 있고, 이 한도를 계정별로 설정할 수 있다. 사용량이 늘면 컴퓨팅 유닛이 자동으로 늘어나지만 설정한 한도에서 멈추고, 유휴 상태에서는 scale-to-zero로 0까지 줄어 비용이 멈춘다. 이런 증감과 오류 상황은 CloudWatch 지표에 자동으로 쌓여 대시보드에서 한눈에 보인다.

4단계별 동작 과정

  1. 한도 설정계정과 컬렉션에 컴퓨팅 유닛·저장 용량의 최대 한도를 지정해 자동 확장이 끝없이 커지는 것을 막는다.
  2. 자동 확장·축소부하에 따라 컴퓨팅 유닛이 늘고 줄며, 요청이 없는 시간에는 0으로 내려간다.
  3. 모니터링 구성CloudWatch 지표로 사용량과 오류를 보고, CloudTrail로 API 호출 기록을, EventBridge로 특정 이벤트 발생 시 알림을 받는다.

5본질 요약

컴퓨팅 유닛과 저장 용량이 자동으로 조정되되 계정이 정한 한도를 넘지 않게 하고, CloudWatch·CloudTrail·EventBridge로 그 상태를 관찰·통제하는 것

Ingestion 개요와 핵심 개념

Amazon OpenSearch Ingestion은 소스에서 OpenSearch Service 도메인이나 Serverless 컬렉션으로 데이터를 실시간 수집·변환하는 완전관리형 파이프라인 서비스다.

1상대의 출발점 확인

기존 방식에서는 로그나 애플리케이션 데이터를 검색 엔진에 넣으려면 파이프라인을 직접 만들어 운영해야 했다. 데이터를 보내는 스크립트, 버퍼 역할을 하는 큐, 변환 규칙, 실패한 데이터의 재처리를 전부 개발자가 조립하고 서버에 띄워 두어야 했다. 파이프라인이 죽으면 데이터가 쌓이기만 하고 검색에는 반영되지 않았으며, 트래픽이 늘면 파이프라인 용량도 직접 키워야 했다.

2질문 제기

여러 소스에서 오는 데이터를 변환·가공해 도메인이나 컬렉션까지 실시간으로 밀어 넣는 파이프라인을 직접 운영하지 않고 쓸 수 없을까?

3구조적 핵심 예시

Amazon OpenSearch Ingestion은 완전관리형 파이프라인 서비스로, Data Prepper(오픈소스 데이터 수집기) 기반 파이프라인을 정의하면 AWS가 그 파이프라인을 실행해 준다. 파이프라인 설정은 소스(어디서 데이터를 받는지), 프로세서(어떻게 변형하는지), 싱크(어디로 보내는지) 세 부분으로 작성하며, 이를 적용하면 S3나 Amazon Managed Streaming for Apache Kafka(MSK) 같은 소스에서 OpenSearch Service 도메인 또는 Serverless 컬렉션으로 데이터가 실시간 흘러간다.

4단계별 동작 과정

  1. 파이프라인 정의소스·프로세서·싱크를 포함한 파이프라인 설정 파일을 작성한다.
  2. 파이프라인 실행설정을 Ingestion에 배포하면 AWS가 파이프라인을 프로비저닝(자원을 준비해 실행하는 것)하고 시작한다.
  3. 데이터 전달파이프라인이 소스의 데이터를 읽어 변환 규칙을 적용하고, 지정된 도메인이나 컬렉션에 실시간으로 인덱싱(검색 가능하게 저장하는 것)한다.

5본질 요약

데이터 수집·변환·전달 파이프라인을 완전관리형으로 실행해, 직접 운영 없이 소스에서 OpenSearch 검색 엔진까지 데이터를 실시간으로 흘려보내는 것

4단계별 동작 과정

  1. 블루프린트 선택파이프라인 생성 시 사용 사례에 맞는 블루프린트를 고르면 소스와 싱크가 미리 연결된 YAML 구성이 만들어진다.
  2. YAML 설정 조정엔드포인트, 인증 정보, 인덱스 이름 등 필요한 값을 채워 파이프라인 구성을 완성하고 생성한다. 설정 문법이 틀리면 생성 시점에 오류로 알려준다.
  3. 파이프라인 실행과 데이터 유입파이프라인이 시작되면 설정된 소스에서 데이터를 읽어 처리한 뒤 OpenSearch 도메인에 넣고, 상태를 확인하며 동작한다.

3구조적 핵심 예시

OpenSearch는 MCP(Model Context Protocol) 서버를 제공한다. MCP는 AI 에이전트가 외부 도구와 통신할 때 쓰는 표준 프로토콜로, 에이전트가 이 서버에 연결하면 OpenSearch의 인덱스 검색, 문서 조회, 데이터 분석 같은 작업이 도구(툴) 형태로 노출된다. 여기에 에이전트 스킬을 함께 제공하면 에이전트는 어떤 작업을 어떤 순서로 수행할 수 있는지 정의된 스킬을 따라 OpenSearch 데이터를 활용한다. 에이전트 쪽은 표준 프로토콜만 지원하면 되므로 개별 인테그레이션 코드가 필요 없다.

4단계별 동작 과정

  1. MCP 서버 연결에이전트가 OpenSearch가 제공하는 MCP 서버에 표준 프로토콜로 연결한다.
  2. 도구와 스킬 노출서버가 OpenSearch에서 수행 가능한 작업(검색, 인덱스 정보 조회, 분석 등)을 도구로 노출하고, 에이전트가 활용할 수 있는 스킬 정의를 제공한다.
  3. 에이전트 실행에이전트가 사용자 요청에 맞는 스킬을 선택해 노출된 도구를 순서대로 호출하고, OpenSearch 데이터의 조회·분석 결과를 응답으로 만든다.

보안 분석

보안 로그에서 위협을 탐지·조사하고 대응 흐름을 자동화하도록 돕는 보안 분석 기능.

1상대의 출발점 확인

기존에는 보안 로그를 별도의 로그 수집 파이프라인으로 모아 두고, 위협 탐지는 사람이 쿼리를 직접 작성해 로그를 뒤지며 수동으로 했다. 그 방식은 위협이 실제로 발생했을 때 관련 로그를 찾아 연결하는 데 오랜 시간이 걸렸고, 탐지 규칙을 만들어도 운영 환경의 변화에 맞춰 갱신하지 않으면 금방 낡았다. 또 공격이 여러 로그 원본에 흩어져 남으면 한 곳에서 전체 흐름을 보기 어려워 탐지와 대응이 늦어지는 한계가 명확했다.

2질문 제기

흩어져 있는 보안 로그에서 위협을 자동으로 찾아내고, 발견된 위협에 대한 대응까지 한 흐름으로 이어가려면 어떻게 해야 할까?

3구조적 핵심 예시

보안 분석 기능은 탐지 규칙(detector rule)을 하나 등록해 두면, 도메인에 수집된 보안 로그가 들어올 때마다 그 규칙과 대조해 위협 의심 신호를 찾아낸다. 규칙에 걸린 로그는 알림으로 만들어지고, 같은 로그를 둘러싼 연관 기록까지 묶어 조사 화면에 보여준다. 사람은 쿼리를 짜는 대신 화면에서 탐지 결과를 확인하고 대응 여부를 정하기만 하면 된다.

4단계별 동작 과정

  1. 탐지 규칙 등록위협으로 판단할 조건(예: 특정 IP의 비정상 로그인 시도)을 규칙으로 도메인에 등록한다. 규칙은 서비스가 기본 제공하는 템플릿을 그대로 쓸 수도 있다.
  2. 로그 대조와 알림 생성수집된 보안 로그가 규칙 조건과 일치하면 서비스가 탐지 결과를 만들고, 설정된 알림 채널로 통보한다.
  3. 조사와 대응탐지 결과에 연관된 로그를 한 화면에서 확인하고, 심각도를 매기거나 대응 작업으로 넘겨 흐름을 이어간다.

모범 사례와 사이징

도메인의 저장 용량·샤드 수·인스턴스 유형을 산정하고 안정적으로 운영하기 위한 공식 모범 사례 지침.

1상대의 출발점 확인

도메인을 만들 때 인스턴스 유형과 개수, 저장 용량, 샤드 수를 정하는 기준이 없으면 사람마다 다르게 잡았다. 그 결과 저장 공간이 부족해 데이터가 쌓이지 못하거나, 샤드가 너무 많아 관리 부담만 커지고, 인스턴스가 과하게 커서 비용만 늘어나는 문제가 반복됐다. 운영 중에 도메인 구조를 바꾸는 것은 인덱스 재생성 같은 큰 작업이 필요해 나중에 바로잡기도 어려웠다.

2질문 제기

도메인을 처음 설계할 때 저장 용량과 샤드 수, 인스턴스 유형을 어떤 기준으로 정해야 안정적이면서도 낭비 없이 운영할 수 있을까?

3구조적 핵심 예시

들어올 데이터의 양과 보관 기간으로 저장 용량을 먼저 계산하고, 그 용량을 감당할 수 있게 샤드 개수를 정하는 방식이 가장 기본적인 설계 흐름이다. 예를 들어 하루 100GB가 들어오고 30일 보관해야 한다면 원본 보관분과 후처리(복제본 등)를 합쳐 필요한 총 용량이 나오고, 샤드 하나가 감당할 크기를 고려해 샤드 수를 산정한다. 인스턴스 유형과 개수는 그 계산된 용량과 CPU·메모리 요구를 함께 보고 고른다.

4단계별 동작 과정

  1. 용량 계산하루 수집량과 보관 기간, 복제본 비율을 곱해 도메인에 필요한 총 저장 용량을 구한다.
  2. 샤드 수 산정샤드 하나당 적정 크기를 기준으로 전체 용량을 나누어 샤드 개수를 정한다. 노드당 샤드 수 상한도 함께 확인한다.
  3. 인스턴스 선택계산된 용량과 처리 요구에 맞는 인스턴스 유형과 개수를 고르고, 필요에 따라 전용 마스터 노드 등을 추가해 구성을 확정한다.

비용 최적화와 전용 노드

Reserved Instance·UltraWarm 같은 비용 절감 방안과 전용 코디네이터·마스터 노드 배치를 다루는 비용·아키텍처 지침.

1상대의 출발점 확인

기본 구성으로 도메인을 만들면 전체 데이터를 실시간 검색 가능한 인스턴스에 계속 올려 두므로, 오래된 데이터가 쌓일수록 저장 비용과 인스턴스 운영 비용이 함께 계속 올라갔다. 또 모든 노드에 같은 역할을 맡기면 클라이언트 연결 처리와 인덱스 상태 관리가 데이터 노드의 자원을 나눠 쓰게 되어, 데이터량이 늘면 성능이 먼저 흔들리고 그걸 막으려고 인스턴스를 키우는 비용 낭비가 생겼다.

2질문 제기

자주 조회하지 않는 오래된 데이터와 클러스터 관리 부담 때문에 불어나는 비용을 줄이면서도 운영 안정성은 유지하려면 어떻게 해야 할까?

3구조적 핵심 예시

자주 쓰지 않는 데이터를 UltraWarm 계층으로 옮기고, 예약 인스턴스(Reserved Instance)로 장기간 쓸 인스턴스 비용을 미리 할인받는 방식이 대표적인 비용 절감 구조다. 자주 검색하는 최근 데이터는 일반 인스턴스에, 오래된 데이터는 저비용 스토리지에 두어 검색 성능은 유지하면서 저장 비용을 크게 줄인다. 전용 마스터·코디네이터 노드는 클러스터 관리와 연결 처리를 데이터 노드와 분리해, 성능을 위해서 비싼 인스턴스를 키우지 않아도 되게 돕는다.

4단계별 동작 과정

  1. 데이터 계층 분리자주 조회하는 데이터와 그렇지 않은 데이터를 나누고, 오래된 데이터를 UltraWarm 같은 저비용 스토리지 계층으로 옮긴다.
  2. 비용 선결제 적용장기간 운영할 인스턴스 크기를 예측해 Reserved Instance로 구매하고, 온디맨드(on-demand, 쓴 만큼 지불) 요금 대신 할인된 요금으로 인스턴스 비용을 낮춘다.
  3. 역할별 노드 배치마스터 노드(클러스터 상태 관리)와 코디네이터 노드(요청 분산)를 데이터 노드와 분리 배치해, 데이터 증가에 따라 성능 저하가 먼저 오지 않도록 구성한다.

5본질 요약

오래된 데이터를 저비용 계층으로 옮기고 예약 구매로 인스턴스 비용을 줄이며, 관리·연결 역할을 전용 노드로 분리해 성능 때문에 불필요하게 인스턴스를 키우지 않게 하는 비용·아키텍처 최적화 지침
