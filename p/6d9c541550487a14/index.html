1서비스의 정체와 첫 도메인도메인·컬렉션·파이프라인이라는 세 가지 대상을 먼저 구분해야 이후 모든 설정 화면과 요금이 무슨 이야기인지 알 수 있다.52도메인 설계 — 클러스터를 이루는 것들노드·인스턴스·스토리지·AZ 를 정하지 않으면 도메인을 만들 수 없고, 뒤의 성능·비용·가용성 이야기가 전부 이 선택 위에 얹힌다.63네트워크와 접근 통제도메인은 만들자마자 닫혀 있다. 데이터를 넣거나 검색하려면 먼저 어디서 어떻게 들어갈지와 누가 무엇을 할 수 있는지를 정해야 한다.64데이터 넣기검색할 것이 있어야 검색을 배운다. 인덱싱 경로를 먼저 열어야 이후 검색·수명주기·시각화가 실제 데이터 위에서 이해된다.45OpenSearch Ingestion 파이프라인직접 만든 적재 코드의 한계를 본 다음에야 관리형 수집기가 무엇을 대신해 주는지가 보인다. 파이프라인은 도메인과 컬렉션 모두의 입력구다.56검색하기데이터가 들어왔으니 이제 꺼낸다. 기본 검색을 먼저 알아야 벡터 검색·직접 질의 같은 변형이 무엇의 변형인지 알 수 있다.67벡터 검색과 머신러닝키워드 검색을 알고 나면 의미 기반 검색이 무엇을 대체하는지 이해된다. 이후 에이전틱 기능과 Serverless 벡터 컬렉션이 전부 여기에 기댄다.78인덱스 수명주기와 스토리지 계층데이터가 쌓이면 비용과 성능이 갈린다. 어떤 인덱스를 어디에 두고 언제 옮길지는 도메인 설계와 검색을 모두 알아야 판단할 수 있다.69시각화와 관측검색 API 를 알고 나야 대시보드가 뒤에서 무엇을 부르는지 보인다. 관측 기능은 앞의 적재·인덱스 설계 위에서만 의미가 있다.510모니터링·경보·탐지운영 판단의 근거가 되는 신호를 먼저 확보해야, 다음 단계의 업그레이드·스케일 변경이 안전한지 판별할 수 있다.611도메인 운영신호를 읽을 줄 알게 된 뒤에 변경을 가한다. 구성 변경·업그레이드·백업은 모두 앞 단계의 설계와 지표 위에서 판단된다.612Amazon OpenSearch Serverless도메인 운영의 부담을 전부 겪은 뒤에야 서버리스가 무엇을 없애 주고 무엇을 포기하게 하는지가 비교 가능해진다.7

도메인을 만들 때 고르는 이름·엔진 버전·노드 구성·네트워크·보안 옵션과 생성 후 바꿀 수 있는 구성 변경 항목 전체.

1문제 상황

도메인을 생성할 때 단순히 이름과 노드 몇 개만 고르는 것이 아니라, 엔진 버전, 보안 설정, 네트워크 환경, 암호화, 로깅 등 많은 선택지가 있습니다. 초기 설정을 놓치면 나중에 보안이 허술해지거나, 필요한 기능을 쓸 수 없거나, 성능 문제가 생길 수 있습니다. 또한 도메인을 만든 뒤에도 일부 설정은 바꿀 수 없는 경우가 있어서 신중한 계획이 필요합니다.

2핵심 질문

도메인 생성 시 어떤 옵션들을 선택해야 하고, 생성 후에 어떤 구성은 바꿀 수 있고 바꿀 수 없을까?

3동작 예시

도메인을 만들 때 "도메인 이름", "엔진 버전 (OpenSearch 2.13 vs Elasticsearch)", "배포 유형 (관리형 vs Serverless)", "인스턴스 타입과 개수", "VPC 설정", "보안 플러그인 활성화", "암호화 (전송 중·저장)", "로깅 (애플리케이션 로그·인덱스 로그)" 등을 결정합니다. 도메인 생성 후에는 노드 개수, 스토리지 크기, 보안 정책은 바꿀 수 있지만, 도메인 이름과 VPC 설정은 변경 불가능합니다.

4동작 과정

  1. 기본 설정 선택도메인 이름, 엔진 버전, 배포 형태(관리형 vs Serverless)를 결정합니다.
  2. 클러스터와 네트워크 구성인스턴스 타입과 개수, VPC 내 서브넷과 보안 그룹, EBS 스토리지 크기를 지정합니다.
  3. 고급 설정암호화(인증서 기반 통신, KMS 저장암호화), Fine-Grained Access Control(권한 관리), 로깅(CloudWatch, 인덱스), 스냅샷 자동 백업을 활성화하고 설정합니다.

데이터 노드는 저장·검색을, 전용 마스터는 클러스터 상태 관리를, 전용 코디네이터는 요청 분배와 결과 취합을 나눠 맡는다.

1문제 상황

OpenSearch 클러스터의 모든 노드가 동일한 역할을 한다면, 한 노드가 검색 요청을 처리하다가 과부하가 걸리면 다른 업무(클러스터 상태 관리, 요청 분배)까지 느려집니다. 또한 한 노드에서 대량의 데이터를 저장하면서 동시에 복잡한 검색 쿼리를 처리하려니 병목이 생깁니다. 효율적으로 운영하려면 역할을 나누어서 각 노드가 자신의 일에 집중해야 합니다.

2핵심 질문

클러스터 내에서 데이터 저장, 클러스터 관리, 요청 분배를 담당하는 노드들을 역할별로 나누면, 각자 자신의 일에 집중해서 전체 성능과 안정성을 높일 수 있지 않을까?

3동작 예시

도메인에 4개의 노드가 있다면, 1개를 전용 마스터 노드로, 1개를 전용 코디네이터 노드로, 2개를 데이터 노드로 구성할 수 있습니다. 마스터는 클러스터의 상태(어떤 샤드가 어디에 있는지)만 관리하고, 코디네이터는 들어오는 요청을 받아 적절한 데이터 노드들에게 분배하고 결과를 합쳐 돌려주며, 데이터 노드는 문서를 저장하고 검색만 합니다.

4동작 과정

  1. 데이터 노드실제 문서(인덱스, 샤드)를 저장하고, 들어오는 검색 요청을 처리해 결과를 반환합니다.
  2. 전용 마스터 노드클러스터 전체의 상태(메타데이터)를 관리하고, 노드 추가·제거, 샤드 재배치 같은 클러스터 유지 작업을 담당합니다.
  3. 전용 코디네이터 노드클라이언트의 요청을 받아 관련 데이터 노드들에게 병렬로 보내고, 각 노드의 검색 결과를 취합해 클라이언트에게 최종 응답을 돌려줍니다.

2핵심 질문

3동작 예시

4동작 과정

  2. 인스턴스 타입 선택AWS가 제공하는 지원 인스턴스 타입 중에서 해당 규모에 맞는 것을 선택합니다. 예를 들어 검색량이 적으면 t4g 계열, 많으면 c6g나 r6g 계열을 씁니다.

1문제 상황

기존에 스토리지 공간을 늘릴 때, 단순히 용량(GB)만 정해서 구성했습니다. 하지만 검색 엔진의 성능은 저장 용량뿐만 아니라 초당 얼마나 많은 쓰기·읽기를 처리할 수 있는지(IOPS, 입출력 작업 수)와 초당 몇 MB의 데이터를 옮길 수 있는지(처리량)에도 영향을 받습니다.

2핵심 질문

데이터 노드에 붙는 EBS 볼륨에서 저장 용량과 성능(IOPS·처리량)을 어떻게 설정해야 색인·검색 속도 저하 없이 안정적으로 운영할 수 있는가?

3동작 예시

gp3 볼륨은 기본 IOPS가 3000, 처리량이 125 MB/s로 설정되는데, 색인이 자주 일어나면 IOPS를 16000까지, 처리량을 1000 MB/s까지 따로 올릴 수 있습니다. 용량을 100GB에서 500GB로 늘릴 때 성능을 함께 올리지 않으면 색인 속도가 떨어집니다.

4동작 과정

  1. 스토리지 유형 선택gp3(범용), io2 블록 익스프레스(매우 높은 성능 필요할 때) 중 선택합니다. OpenSearch는 주로 gp3를 권장합니다.
  2. 기본 설정용량(GB), 기본 IOPS(3000~16000), 처리량(125~1000 MB/s)을 설정합니다. 데이터 로딩 속도가 높을수록 IOPS와 처리량을 크게 설정합니다.

Multi-AZ 와 대기 노드 배치

노드와 샤드 복제본을 여러 가용 영역에 나눠 두어 한 AZ 가 죽어도 도메인이 살아 있게 하는 구성.

1문제 상황

기존에는 한 가용 영역(AZ)에 모든 노드를 배치했으므로, 그 AZ의 전체 장애(정전, 네트워크 끊김)가 발생하면 도메인 전체가 다운되었습니다. 도메인을 재생성하거나 백업에서 복구하기까지 시간이 걸렸습니다.

2핵심 질문

한 가용 영역이 먹통이 되어도 도메인이 계속 작동하려면 어떻게 노드를 배치해야 하는가?

3동작 예시

도메인에 데이터 노드 6개가 있을 때, 2개씩 AZ-1, AZ-2, AZ-3에 배치합니다. 그러면 AZ-1이 죽어도 나머지 4개 노드(AZ-2, AZ-3에 있는 것들)가 살아서 도메인이 계속 검색을 처리합니다.

4동작 과정

  1. Multi-AZ 활성화도메인 생성 또는 업데이트 시 Multi-AZ를 켜면 노드가 여러 가용 영역에 자동으로 분산됩니다.
  2. 대기 노드 배치마스터 노드(클러스터 상태를 관리하는 노드)를 세 곳(AZ-1, AZ-2, AZ-3)에 각 1개씩 배치하면, 한 곳이 죽어도 나머지 둘이 마스터 기능을 유지합니다.
  3. 복제본 전략각 샤드(데이터 조각)의 복제본도 다른 AZ에 배치되므로, 한 AZ 노드의 데이터가 다른 곳에 백업되어 있는 상태입니다.

필요한 저장 용량을 계산하고 샤드 수와 인스턴스 수를 정하는 절차, 그리고 페타바이트급으로 키울 때의 설계 지침.

1문제 상황

기존에는 "저장 공간 100GB가 필요하다"고만 정하고 도메인을 만들었는데, 시간이 지나면서 용량이 부족하거나 성능이 떨어졌습니다. 샤드(데이터를 여러 조각으로 나누는 것) 개수가 너무 적으면 병렬 처리가 안 되고, 너무 많으면 관리 부하가 커집니다.

2핵심 질문

저장할 데이터 양과 검색 성능을 고려할 때, 샤드는 몇 개로 만들고, 노드는 몇 개가 필요하며, 페타바이트급 규모로 자랄 때는 어떻게 설계해야 하는가?

3동작 예시

매달 1GB씩 100개월 데이터를 보관할 예정(총 100GB)이면, 한 샤드당 최대 50GB 정도를 두는 것이 성능 상 좋으므로 2~3개 샤드가 필요합니다. 복제본 1개를 두면 데이터 노드 2개가 필요합니다. 페타바이트급(1000배 커짐)이면 같은 비율로 노드도 2000개가 필요해집니다.

4동작 과정

JSON 문서를 인덱스에 넣는 기본 방법으로, 단건 인덱싱 API 와 여러 건을 한 번에 밀어넣는 _bulk 요청으로 데이터를 검색 가능한 상태로 만드는 과정이다.

1문제 상황

데이터베이스나 파일에 있는 데이터는 그대로는 검색할 수 없다. JSON 형식의 문서를 OpenSearch 인덱스에 저장(인덱싱)해야 검색 쿼리가 그 데이터를 찾을 수 있다. 단건씩 API를 호출하면 네트워크 왕복이 많아져 느리다.

2핵심 질문

수백만 건의 데이터를 빠르게 OpenSearch에 넣고 검색 가능하게 하려면?

3동작 예시

단건 인덱싱은 API를 한 번 호출해 문서 한 개를 넣는다. _bulk 요청은 JSON Lines 형식(한 줄당 하나의 요청 명령)으로 수천 개의 문서 적재 명령을 묶어 한 번의 HTTP 요청으로 보낸다.

4동작 과정

  1. 문서 포맷 준비데이터를 JSON 형식으로 변환해 각 문서에 고유 ID를 지정한다.
  2. _bulk API로 대량 전송문서들을 JSON Lines 형식으로 묶고 한 번에 OpenSearch로 보낸다.
  3. 인덱싱 및 검색 활성화OpenSearch가 받은 문서들을 인덱스 구조에 저장하고, 검색 쿼리가 이 데이터를 즉시 찾을 수 있게 한다.

5한 줄 요약

JSON 문서를 단건 또는 _bulk API로 인덱스에 저장해 검색 가능하게 하는 기초 작업

Lambda로 스트리밍 적재 — S3 · Kinesis · DynamoDB

S3 업로드, Kinesis Data Streams 레코드, DynamoDB 변경 이벤트를 트리거로 Lambda 함수를 실행해 데이터를 실시간으로 OpenSearch 도메인에 넣는 방식이다.

1문제 상황

데이터가 S3, Kinesis, DynamoDB 같은 AWS 서비스에서 계속 생겨난다. 수동으로 주기적으로 배치 작업을 실행해 적재하면 지연이 길어진다. 또한 배치 작업의 실패 처리, 크기 조정 등이 복잡하다.

2핵심 질문

S3 업로드나 Kinesis 레코드 같은 이벤트를 감지해 자동으로 데이터를 실시간으로 OpenSearch에 넣을 수 있을까?

3동작 예시

S3에 파일이 업로드되면 S3 이벤트 알림이 Lambda 함수를 트리거한다. Lambda가 파일을 읽고 JSON으로 변환해 OpenSearch로 전송한다. Kinesis에 데이터가 들어오면 Kinesis 트리거가 Lambda를 실행해 OpenSearch에 저장한다.

4동작 과정

  1. 이벤트 발생 및 Lambda 트리거S3 업로드, Kinesis 레코드 도착, DynamoDB 쓰기 같은 이벤트가 Lambda 함수를 자동 실행한다.
  2. 데이터 변환 및 정제Lambda가 이벤트 데이터를 읽고 필요하면 형식을 변환·정제한다.
  3. OpenSearch로 전송처리된 데이터를 OpenSearch API로 인덱싱한다.

5한 줄 요약

S3, Kinesis, DynamoDB의 이벤트를 Lambda로 감지해 자동 실행하고 데이터를 실시간으로 OpenSearch에 적재하는 것

Data Firehose와 CloudWatch Logs로부터 적재

코드를 거의 쓰지 않고 관리형 전송 서비스인 Amazon Data Firehose 나 CloudWatch Logs 구독으로 로그·스트림 데이터를 OpenSearch 로 자동 전달하는 경로다.

1문제 상황

람다 함수로 스트리밍 적재를 구성하려면 코드를 작성하고 배포·운영해야 한다. 하지만 로그나 이벤트 스트림을 OpenSearch로 보내는 작업은 매우 흔해서 코드를 짤 필요 없이 관리형 서비스로 처리할 수 있다.

2핵심 질문

로그와 스트림 데이터를 코드 거의 없이 OpenSearch로 자동 전달할 수 있을까?

3동작 예시

CloudWatch Logs 구독 필터를 설정하면 로그 그룹의 모든 새 로그가 자동으로 Firehose 배송 스트림(또는 Lambda)으로 전달된다. Firehose는 배송 대상으로 OpenSearch를 지정받고 배치로 묶어 정기적으로(몇 초마다) OpenSearch에 전송한다.

4동작 과정

  1. CloudWatch Logs 또는 Firehose 설정CloudWatch Logs 구독 필터 또는 Firehose 배송 스트림을 만들고 OpenSearch를 대상으로 지정한다.
  2. 로그·데이터 수집 및 버퍼링CloudWatch Logs의 새 로그나 Firehose로 들어오는 데이터가 버퍼에 모인다.
  3. 자동 배송버퍼 크기나 시간 조건(예: 5MB 또는 60초)을 만족하면 Firehose가 자동으로 배치를 OpenSearch로 전송한다.

5한 줄 요약

CloudWatch Logs 구독 필터나 Data Firehose 배송 스트림으로 로그와 데이터를 자동 수집해 코드 없이 OpenSearch로 전달하는 것

Logstash와 서드파티 수집기

Logstash 의 OpenSearch 출력 플러그인이나 Fluent Bit·Fluentd·OpenTelemetry 같은 외부 수집기를 써서 다양한 소스의 데이터를 변환해 적재하는 방법이다.

1문제 상황

데이터가 여러 다양한 소스(애플리케이션 로그, 시스템 메트릭, 데이터베이스 변경 로그 등)에서 여러 형식(텍스트, CSV, 바이너리)으로 생겨난다. AWS 서비스만으로 모든 소스를 OpenSearch에 연결하기는 어렵고, 데이터를 전처리하거나 필터링·변환(parsing, enrichment)해야 할 수도 있다.

2핵심 질문

다양한 소스의 데이터를 변환하고 필터링한 후 OpenSearch에 넣는 통합 도구가 있을까?

3동작 예시

Logstash는 수집(input) → 필터링 및 변환(filter) → 전송(output) 파이프라인으로 작동한다. 예를 들어 로그 파일을 읽고(input), grok 필터로 텍스트를 필드로 파싱하고(filter), OpenSearch output 플러그인으로 인덱싱(output)한다. Fluent Bit나 OpenTelemetry 같은 경량 수집기도 같은 패턴으로 작동한다.

4동작 과정

  1. 소스에서 데이터 수집Logstash input 플러그인(파일, 네트워크 소켓, 데이터베이스 등)이 다양한 소스에서 데이터를 읽는다.
  2. 데이터 변환 및 정제filter 플러그인으로 텍스트 파싱, 필드 추출, 조건부 필터링, 데이터 보강(enrichment)을 한다.
  3. OpenSearch로 전송OpenSearch output 플러그인이 변환된 데이터를 인덱싱한다.

5한 줄 요약

Logstash나 Fluent Bit·Fluentd·OpenTelemetry 같은 수집기로 다양한 소스의 데이터를 읽고 변환·필터링한 후 OpenSearch에 적재하는 것

OpenSearch Ingestion이란 — 관리형 Data Prepper와 Ingestion OCU

오픈소스 Data Prepper 를 AWS 가 대신 운영해 주는 서버리스 수집 서비스로, 용량은 Ingestion OCU 단위로 자동 확장된다.

1문제 상황

기존에는 Data Prepper(오픈소스 데이터 수집 소프트웨어)를 직접 설치하고 운영해야 했습니다. EC2 인스턴스를 구성하고, 소프트웨어 패치를 적용하고, 장애가 발생하면 대응하는 운영 부담이 모두 개발팀에게 있었습니다.

2핵심 질문

데이터 수집 파이프라인을 자동으로 확장되는 관리형 서비스로 쓸 수 있을까?

3동작 예시

AWS가 Data Prepper 소프트웨어를 대신 실행해 주고, 들어오는 데이터량에 따라 Ingestion OCU(처리 용량 단위)라는 측정 단위로 자동으로 확장되는 서버리스 서비스입니다.

4동작 과정

  1. 설정YAML 파일로 수집·가공·저장 규칙을 정의하고 AWS에 업로드합니다.
  2. 자동 확장들어오는 데이터량에 따라 Ingestion OCU(오퍼레이셔널 용량 단위)가 자동으로 증가하거나 감소합니다.
  3. 관리 책임 감소AWS가 소프트웨어 운영, 보안 패치, 장애 대응을 담당하므로 사용자는 파이프라인 로직만 관리하면 됩니다.

5한 줄 요약

Data Prepper 소프트웨어의 운영 부담을 AWS에 넘기고, 용량을 자동 확장하며 실제 사용한 OCU만큼만 비용을 내는 서버리스 데이터 수집 서비스

파이프라인 구조 — 서브파이프라인·source·processor·sink·buffer·route

파이프라인은 YAML 로 source(입력) → buffer → processor(가공) → route/sink(출력) 을 잇는 서브파이프라인들의 조합이다.

1문제 상황

데이터 수집은 단순해 보이지만, 실제로는 여러 단계를 거칩니다. 어디서 받을지(source), 어떻게 변환할지(processor), 어디로 보낼지(sink)를 정해야 하고, 그 사이에서 데이터가 임시로 쌓였다가(buffer) 처리되는 과정을 구조적으로 조직해야 합니다.

2핵심 질문

서로 다른 데이터 소스와 처리 규칙을 어떻게 구조적으로 연결할 것인가?

3동작 예시

각 파이프라인은 source(입력 지점) → buffer(임시 저장소) → processor(변환 로직) → sink(출력 지점)의 순서로 데이터가 흐르며, 여러 개의 이 경로(서브파이프라인)를 조합해서 만듭니다. route(경로 분배)를 쓰면 한 source에서 온 데이터를 여러 processor로 동시에 보낼 수도 있습니다.

4동작 과정

  1. source 정의Kinesis, S3, HTTP 같은 입력 지점을 선언합니다.
  2. 변환 체인buffer에 데이터가 쌓이다가 processor가 필터링, 포맷 변환, 필드 추가 같은 작업을 수행합니다.
  3. sink 선택처리된 데이터를 OpenSearch 도메인, 다른 S3 버킷, 외부 서비스로 보냅니다.

5한 줄 요약

오래 걸리는 검색을 백그라운드로 돌려 부분 결과를 받고, 특정 시점의 데이터 상태를 고정해 일관되게 페이지를 넘기는 기능이다.

3동작 예시

4동작 과정

  1. 비동기 검색 요청검색 쿼리를 제출하되, 결과를 모두 기다리지 않고 즉시 검색 ID를 받습니다.

  3. Point in Time으로 일관성 보장검색 시작 시점의 데이터 스냅샷을 고정해서, 검색 진행 중 새로운 변경사항에 영향받지 않습니다.

2핵심 질문

3동작 예시

스냅샷(snapshot)은 특정 시점의 인덱스 데이터를 S3(AWS의 객체 스토리지)에 백업한 것이다. 자동 스냅샷은 AWS가 정기적으로 생성하고, 수동 스냅샷은 관리자가 필요할 때마다 생성할 수 있으며, 언제든 해당 스냅샷으로부터 인덱스를 복원할 수 있다.

4동작 과정

  1. 스냅샷 생성자동 또는 수동으로 현재 인덱스 데이터를 S3에 백업 저장한다.
  2. 스냅샷 관리Snapshot Management(일정 자동화 도구)로 백업 주기와 보존 기간을 설정해 자동화한다.
  3. 데이터 복원필요시 S3에 저장된 스냅샷을 선택해 도메인의 인덱스로 복원한다.

5한 줄 요약

Auto-Tune 과 관리 작업

Auto-Tune은 사용 패턴을 보고 JVM 등 클러스터 설정을 자동 조정하며, 노드 재시작 같은 관리 작업은 콘솔에서 직접 수행할 수 있다.

1문제 상황

2핵심 질문

3동작 예시

Auto-Tune은 클러스터의 쿼리 응답 시간, CPU 사용률, 힙 메모리 사용량 등을 실시간으로 모니터링하고, 그 데이터를 기반으로 JVM 힙 크기와 쓰레드 풀 같은 설정을 자동으로 조정한다.

4동작 과정

  1. 성능 지표 수집클러스터의 응답 시간, CPU, 메모리 같은 실시간 메트릭을 기록한다.
  2. 설정 분석 및 추천수집된 데이터를 분석해 성능을 개선할 설정 변경을 자동으로 결정한다.
  3. 설정 자동 적용추천된 설정을 클러스터에 적용하고, 필요하면 노드를 재시작한다.

5한 줄 요약

Serverless 아키텍처 — 인덱싱·검색 분리와 OCU

클러스터를 직접 운영하지 않고 AWS가 인덱싱과 검색 컴퓨트를 따로 자동 확장해 주며, 사용량은 OCU(OpenSearch Compute Unit) 단위로 계산되는 구조다.

1문제 상황

OpenSearch의 전통적인 운영 모델은 인덱싱과 검색을 모두 같은 클러스터에서 처리한다. 그런데 인덱싱 량이 갑자기 늘어나거나 검색 쿼리가 폭증하면 클러스터 전체를 확장해야 하고, 피크 시간 후 다시 축소해야 하는 오버헤드가 생긴다. 또한 용량 계획이 어렵다.

2핵심 질문

인덱싱과 검색의 컴퓨트를 분리하고, 각각 독립적으로 자동 확장하면서 사용한 만큼만 요금을 낼 수 있을까?

3동작 예시

Serverless는 인덱싱 전담 컴퓨트와 검색 전담 컴퓨트를 분리한다. 데이터 수집 속도가 늘어나면 인덱싱 컴퓨트만 확장하고, 검색 요청이 많아지면 검색 컴퓨트만 확장한다. 사용량은 OCU(OpenSearch Compute Unit, 워크로드 단위 컴퓨트)로 측정되고, 차단 없이 필요한 만큼만 과금한다.

4동작 과정

  1. Serverless 도메인 생성전통적인 클러스터 대신 Serverless 모드로 도메인을 만든다.
  2. 인덱싱과 검색 컴퓨트 배치인덱싱 OCU와 검색 OCU의 초기값(예: 각 2 OCU)을 설정한다.
  3. 자동 스케일링인덱싱 부하와 검색 부하가 실시간으로 모니터링되고, 각각 독립적으로 OCU가 자동 확장·축소된다.

5한 줄 요약

클러스터 운영 부담을 없애고 인덱싱과 검색 워크로드를 분리한 뒤 각각 독립적으로 자동 확장하며, 사용한 OCU만큼 과금하는 완전 관리형 Serverless 아키텍처

컬렉션은 용도에 맞춘 인덱스 묶음으로, 로그 분석용 시계열·전문 검색용 검색·임베딩 유사도용 벡터 검색 세 가지 유형 중 하나를 고른다.

1문제 상황

기존의 단일 인덱스는 어떤 종류의 데이터든 한 가지 방식으로만 저장하고 검색합니다. 로그, 문서, 이미지 임베딩 등 다양한 목적의 데이터를 모두 같은 구조로 관리해야 하므로, 검색 성능이나 분석 기능이 각 목적에 최적화되지 않습니다.

2핵심 질문

데이터의 용도에 따라 저장 구조와 검색 방식을 달리할 수 있다면 어떨까요?

3동작 예시

AWS의 컬렉션 유형은 세 가지입니다. 시계열 데이터(타임스탬프 포함 로그, 메트릭)는 시간 순서로 정렬하고 압축에 유리한 구조로 저장합니다. 검색 데이터(문서, 기사)는 역인덱스(단어별로 문서 목록을 역으로 정렬한 구조)를 만들어 텍스트 검색에 최적화합니다. 벡터 검색 데이터(사진, 텍스트 임베딩)는 벡터 공간에서 유사도를 빠르게 계산하는 구조를 씁니다.

4동작 과정

  1. 용도 결정데이터가 시계열인지, 텍스트 검색인지, 벡터 유사도 검색인지 판단합니다.
  2. 유형 선택각 용도에 최적화된 컬렉션 유형(Time Series, Search, Vectorsearch)을 선택합니다.
  3. 인덱스 구성선택한 유형에 맞춰 인덱스 매핑(필드 이름, 데이터 타입, 검색 옵션)이 자동으로 최적화되고, 데이터를 저장할 준비가 됩니다.

Serverless 보안 정책과 인증

IAM 권한 위에 암호화·네트워크·데이터 액세스 정책과 SAML 인증을 조합해 컬렉션 접근을 통제한다.

1문제 상황

기존의 자체 서버나 기본 OpenSearch는 IAM(Identity and Access Management, 신원 및 접근 권한 관리)만으로 접근을 제어했습니다. 하지만 누가 어떤 데이터에 접근할 수 있는지 세세하게 통제하려면 여러 보안 계층이 필요합니다.

2핵심 질문

IAM 권한만으로는 부족할 때, 암호화·네트워크·데이터 액세스를 함께 제어할 수 있을까요?

3동작 예시

Serverless는 IAM을 기반으로 네 겹의 보안을 추가합니다. 첫째, 전송 중 데이터를 TLS로 암호화합니다. 둘째, VPC 내부 네트워크에서만 접근하도록 제한합니다(네트워크 보안 정책). 셋째, 데이터 액세스 정책으로 특정 사용자는 특정 인덱스만 읽게 제한합니다. 넷째, SAML(Security Assertion Markup Language)로 회사의 기존 로그인 시스템(예: Active Directory)과 연동합니다.

4동작 과정

  1. IAM 설정AWS 계정의 IAM 정책으로 누가 컬렉션에 접근할 수 있는 기본 권한을 정합니다.
  2. 추가 정책 적용암호화(TLS), 네트워크 제한(VPC), 데이터 액세스 정책(인덱스별 권한)을 컬렉션에 할당합니다.
  3. 인증 연동SAML 인증을 활성화하면 회사의 기존 사용자 디렉토리와 연동되어, 회사 계정으로만 로그인할 수 있습니다.

5한 줄 요약

IAM 위에 암호화·네트워크·데이터 액세스 정책을 여러 겹 추가해 권한과 접근을 세밀하게 통제하는 것

용량 한도, Scale to zero, 컬렉션 그룹

계정별 최대·최소 OCU 한도를 정하고, 유휴 시 0까지 줄이는 Scale to zero와 여러 컬렉션이 용량을 공유하는 컬렉션 그룹으로 비용을 조절한다.

1문제 상황

전통적인 데이터베이스나 검색 엔진은 미리 서버를 구매하고 전원을 켜두기만 해도 매달 비용이 발생합니다. 데이터를 쓰지 않는 시간에도 유휴 자원에 대한 요금을 내야 했고, 여러 서비스가 용량을 나누면 어느 쪽이 얼마나 썼는지 추적하기 어려웠습니다.

2핵심 질문

업무 시간에만 서버를 쓰고 야간에는 비용을 0으로 줄일 수 있을까요?

3동작 예시

Serverless는 OCU(OpenSearch Compute Unit, 일종의 계산 단위)로 용량을 측정하고, 계정별 최소·최대 OCU 한도를 정해 놓습니다. 데이터를 쓰지 않으면 자동으로 0까지 축소되며, 다시 요청이 들어오면 즉시 복구됩니다. 여러 컬렉션이 한 풀에서 OCU를 나눠 쓰는 "컬렉션 그룹"을 만들면 서로 간에 용량을 동적으로 조정할 수 있습니다.

4동작 과정

  1. 계정 한도 설정계정 전체에서 쓸 수 있는 최대 OCU와 항상 최소한 유지할 OCU를 정합니다.
  2. Scale to zero 활성화유휴 상태가 일정 시간 이상 지속되면 용량이 0까지 자동으로 줄어들고, 다음 요청이 오면 다시 필요한 용량으로 복구됩니다.
  3. 컬렉션 그룹 구성여러 컬렉션을 하나의 그룹으로 묶으면 그룹 내 모든 컬렉션이 할당된 OCU 풀을 나눠 쓰므로, 어느 컬렉션이 갑자기 많이 써도 그룹 내에서 동적으로 조정됩니다.

컬렉션에 데이터 넣기와 벡터·ML·워크플로 설정

Ingestion 파이프라인이나 클라이언트로 문서를 적재하고, 머신러닝·신경/하이브리드 검색·워크플로를 컬렉션에 설정한다.

1문제 상황

기존에는 데이터를 OpenSearch에 넣기 위해 직접 HTTP 요청을 작성하고, 임베딩(텍스트를 벡터로 변환하는 작업)·머신러닝·검색 자동화를 따로 구축해야 했습니다. 각 기능을 연결하려면 여러 서비스를 조작해야 했고, 설정이 복잡했습니다.

2핵심 질문

다양한 데이터 소스에서 자동으로 데이터를 수집하고, 임베딩·검색·분석을 한 곳에서 설정할 수 있을까요?

3동작 예시

Serverless는 Ingestion 파이프라인(Logstash라는 데이터 수집 도구)으로 S3, Kinesis, HTTP 등 여러 소스에서 자동 수집하고, 내장 신경 검색(Neural Search, 텍스트를 벡터로 바꿔 의미 기반 검색)이나 하이브리드 검색(키워드+벡터 동시 검색)을 설정할 수 있습니다. 또한 워크플로를 정의하면 문서 수신 후 자동으로 변환·필터링·알림을 실행할 수 있습니다.

4동작 과정

  1. 데이터 적재Ingestion 파이프라인으로 원본 데이터 위치(S3, Kinesis, API)를 지정하면 자동으로 문서가 수집되고 컬렉션의 인덱스에 저장됩니다.
  2. 검색 기능 설정신경 검색을 활성화하면 저장된 문서가 자동으로 임베딩되고, 사용자의 질문도 같은 방식으로 벡터화한 후 의미가 비슷한 문서를 찾습니다.
  3. 워크플로 구성문서가 들어올 때마다 실행할 자동 작업(전처리, 필터링, 알림)을 정의해 두면 수동 개입 없이 진행됩니다.

스냅샷·수명주기·저장 절감과 모니터링

스냅샷 백업과 데이터 수명주기 정책, Zstandard 압축·Derived Source 같은 저장 절감 기능을 쓰고 CloudWatch·CloudTrail·EventBridge로 상태를 감시한다.

1문제 상황

전통적인 데이터 관리에서 백업과 저장 용량은 분리된 문제였습니다. 백업을 자동화하지 않으면 데이터 손실 위험이 있었고, 저장 용량이 늘어나면 비용이 선형으로 증가했으며, 무엇을 저장하는지 감시하려면 별도의 모니터링 도구가 필요했습니다.

2핵심 질문

오래된 데이터는 저장 비용을 줄이면서도, 실시간으로 전체 상태를 감시할 수 있을까요?

3동작 예시

Serverless는 스냅샷(특정 시점의 데이터 전체 사본)을 자동으로 주기적으로 백업하고, 데이터 수명주기 정책(오래된 인덱스는 읽기 전용으로 만들거나 삭제)을 정할 수 있습니다. Zstandard 압축으로 저장 크기를 30~50% 줄일 수 있고, Derived Source 기능으로 필요 없는 필드를 저장하지 않습니다. CloudWatch·CloudTrail·EventBridge로 수집량, 검색 횟수, 에러 등을 실시간으로 감시합니다.

4동작 과정

  1. 백업 설정스냅샷을 생성할 시간과 주기를 정하면 AWS가 자동으로 백업을 하고, 장애 시 특정 스냅샷으로 복구할 수 있습니다.
  2. 저장 절감데이터 수명주기 정책으로 30일 이상 된 인덱스는 읽기 전용으로 변경하고, Zstandard 압축과 Derived Source 설정으로 저장 크기를 줄입니다.
  3. 상태 감시CloudWatch, CloudTrail, EventBridge를 연동해 실시간으로 용량 사용량, 쿼리 성능, 접근 이력, 에러를 수집하고 대시보드에 표시합니다.

5한 줄 요약

자동 백업, 수명주기 관리, 압축을 통해 데이터 손실을 막으면서도 저장 비용을 줄이고, 통합 모니터링으로 전체 상태를 실시간으로 파악하는 것
