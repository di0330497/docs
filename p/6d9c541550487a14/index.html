'Amazon Opensearch'는 AWS 관리형 검색·분석 서비스 'Amazon OpenSearch Service'를 뜻한다. 도메인(프로비저닝 클러스터)·Serverless(컬렉션)·Ingestion(파이프라인)·Dashboards/UI 를 하나의 제품군으로 보고, 대상을 먼저 다루고 그 대상을 다루는 법을 뒤에 놓는다.

1서비스를 이해하고 고르기무엇을 다룰지, 무엇이 무엇보다 먼저여야 하는지 알아야 뒤 단계의 선택이 성립한다.42도메인을 세우고 첫 질의를 한다대상(도메인)이 실제로 어떤 것인지 손으로 한 번 만들어야 이후의 모든 설정·보안이 의미를 갖는다.43도메인을 운영·복구·확장한다한 번 만든 도메인은 계속 살아 있어야 하므로 배치·백업·용량·비용이라는 운영 수명주기를 다룬다.84데이터를 흘려보낸다색인할 문서가 어디에서 오는지 알아야 검색·분석 기능이 실제 데이터 위에서 의미가 있다.55무엇이든 찾아본다적재된 문서를 질의하는 기본 수단이며, 여기서 질의 언어·확장 지점이 나머지 기능의 전제가 된다.66의미를 벡터로 찾는다색인이 쌓인 뒤에야 가능한 검색 질의 확장으로, 전통적 키워드 검색의 한계를 여는 층이다.67모델을 붙이고 에이전트를 연다벡터·의미 검색이 임베딩을 필요로 하므로, 모델 연결과 그 위에 올라가는 도구를 한 묶음으로 다룬다.58인덱스의 수명과 저장 계층을 정한다검색 품질·성능·비용은 인덱스의 크기와 위치에서 결정되므로, 검색 다음에 배치한다.69돌아보며 본다운영 중인 도메인이 어떤 상태인지 확인하는 유일한 수단이며, 앞 단계의 설정 결과가 여기서 드러난다.710문과 잠금데이터가 쌓이고 다뤄질수록 접근 통제가 유일한 방어선이므로, 운영·검색 뒤에 놓아도 기능 이해를 방해하지 않는다.711서버리스(컬렉션)로 바꾸기도메인(클러스터)을 그대로 쓰지 않고 OCU 로 계산하는 대안 모델이므로, 프로비저닝 쪽을 끝내 본 뒤 비교하는 것이 맞다.612적재를 파이프라인으로 자동화한다앞 단계의 적재는 직접 연결했지만 파이프라인은 그 연결을 관리 가능한 운영 자산으로 만드는 마지막 층이다.6

Amazon OpenSearch Service 의 정체와 선택 기준

검색·로그 분석·벡터 검색용 오픈소스 OpenSearch 를 AWS 가 관리형으로 제공하는 서비스로, 인프라 운영 대신 사용량에 집중하려는 경우 고른다.

#1문제 상황

검색 기능이 필요한 곳에 오픈소스 OpenSearch 를 직접 설치해 쓰는 방식이 있다. 그러려면 서버를 준비하고, 소프트웨어를 설치하고, 여러 대의 노드를 묶어 클러스터를 구성하고, 버전 업그레이드와 보안 패치를 직접 해야 한다. 서버가 죽으면 복구도 스스로 해야 한다. 이 모든 운영 업무가 검색 기능을 만들고 다듬는 시간을 계속 빼앗는다.

#2핵심 질문

클러스터를 직접 설치하고 운영하는 수고 없이, 검색 기능 사용에만 집중할 수는 없을까?

#3동작 예시

AWS 이름을 붙여 관리형으로 제공하는 OpenSearch Service 는 시키는 대로 처리한다. 사용자가 인스턴스 유형과 노드 수, 접근 정책을 정해서 도메인을 만들면, AWS 가 그 설정대로 OpenSearch 클러스터를 구성해 검색 요청을 보낼 수 있는 엔드포인트 URL 을 알려준다. 이후 문서를 올리고 검색하는 일은 모두 그 URL 하나로 처리된다.

#4동작 과정

  1. 사용 시나리오 확인검색, 로그 분석, 벡터 검색(문장이나 이미지를 수치 벡터로 바꿔 유사한 것을 찾는 검색) 중 어느 용도인지에 따라 서비스 구성이 달라지므로 먼저 용도를 고른다.
  2. 도메인 생성인스턴스 유형, 노드 수, 스토리지, 접근 정책을 정하면 AWS 가 관리형 클러스터를 자동으로 만든다.
  3. 사용과 운영 위임발급된 엔드포인트로 데이터를 넣고 검색하며, 패치·백업·장애 복구는 AWS 가 담당한다.

#5한 줄 요약

오픈소스 OpenSearch 의 설치·운영 부담을 AWS 에 맡기고, 사용자는 검색 기능 사용에만 집중할 수 있게 하는 관리형 검색 서비스

지원 엔진 버전과 표준·확장 지원

OpenSearch 3.5 를 최신 지원 버전으로 두고, 엔진 버전별 제공 기능·플러그인이 달라지며 표준 지원과 확장 지원 기간이 적용되는 버전 관리 체계다.

#1문제 상황

OpenSearch 엔진은 버전이 올라갈 때마다 기능과 플러그인이 조금씩 달라진다. 직접 운영할 때는 어떤 버전이 어떤 기능을 지원하는지 문서를 뒤져 스스로 확인해야 하고, 지원이 끝난 버전을 계속 쓰면 보안 문제가 생겨도 대응하지 못하는 상태가 된다. 버전마다 지원 기간이 제각각이어서 언제 업그레이드해야 하는지 판단하기도 어렵다.

#2핵심 질문

버전별로 어떤 기능이 지원되고 언제까지 안전하게 쓸 수 있는지를 어떻게 명확히 알 수 있을까?

#3동작 예시

OpenSearch 3.5 가 현재 최신 지원 버전이다. 사용자가 도메인을 만들 때 지원 중인 버전 중 하나를 고르면, 그 버전에 정해진 표준 지원과 확장 지원 기간이 함께 적용된다. 표준 지원 기간에는 기능과 보안 업데이트가 제공되고, 확장 지원 기간에는 보안 패치만 제공된다.

#4동작 과정

  1. 버전 선택도메인 생성 시 지원 중인 엔진 버전 목록에서 하나를 고른다.
  2. 지원 기간 확인선택한 버전에 표준 지원(기능·보안 업데이트)과 확장 지원(보안 패치만)이 각각 언제까지 적용되는지 확인한다.
  3. 업그레이드 계획지원이 끝나기 전에 더 새로운 버전으로 도메인을 올려 지원 기간을 연장한다.

#5한 줄 요약

엔진 버전별 지원 기능과 표준·확장 지원 기간을 명확히 정해, 사용자가 어느 버전을 골라 언제 업그레이드할지 판단할 근거를 주는 버전 관리 체계

Elasticsearch 에서 OpenSearch 로 넘어온 이름 변경

2021년 라이선스 변경을 계기로 Elasticsearch 와 Kibana 가 각각 OpenSearch 와 OpenSearch Dashboards 라는 이름으로 바뀐 리브랜딩 과정이다.

#1문제 상황

검색 엔진으로 Elasticsearch 와, 그 데이터를 시각화하는 Kibana 를 함께 쓰는 것이 일반적이었다. 그런데 2021년 원 제작사의 라이선스 정책이 바뀌면서, 기존 방식대로 같은 이름으로 계속 무료 오픈소스로 배포하고 발전시키기가 어려워졌다. 이 라이선스를 유지한 채 기능을 추가하거나 보안 문제를 고치기도 제약이 커졌다.

#2핵심 질문

라이선스 정책 변경으로 같은 이름으로는 더 이상 배포할 수 없게 된 검색 엔진을, 어떻게 무료 오픈소스로 계속 이어갈 수 있을까?

#3동작 예시

Elasticsearch 는 OpenSearch 로, Kibana 는 OpenSearch Dashboards 라는 이름으로 바뀌었다. 이름과 로고가 달라졌을 뿐, 문서를 색인하고 검색하고 대시보드로 보여주는 핵심 기능과 사용 방식은 그대로 이어진다. 기존에 Elasticsearch API 로 작성한 코드도 대부분 그대로 OpenSearch 에서 동작한다.

#4동작 과정

  1. 포크라이선스 변경 전 마지막 오픈소스 버전을 기준으로 코드를 갈라내 포크(fork)한 OpenSearch 프로젝트를 시작한다.
  2. 이름 변경Elasticsearch 와 Kibana 를 각각 OpenSearch 와 OpenSearch Dashboards 로 바꿔 새 이름으로 배포한다.
  3. AWS 관리형 제공AWS 가 OpenSearch 프로젝트를 관리형 서비스로 올려 지속적으로 개발하고 지원한다.

인스턴스·스토리지·데이터 전송 등 사용량에 따라 과금되며, 비용 최적화와 예약 인스턴스 할인으로 지출을 줄일 수 있는 비용 구조다.

#1문제 상황

검색 서버를 직접 운영하면 서버를 빌리거나 사는 비용이 고정으로 잡힌다. 사용량이 적은 새벽에도, 기능을 아직 못 만든 개발 초기에도 같은 비용을 계속 내야 한다. 사용량이 늘어날 것을 예상해 미리 큰 인프라를 잡아두면 안 쓰는 용량의 비용까지 부담하게 된다.

#2핵심 질문

검색 서비스 비용을 실제 사용량에 맞춰 유연하게 늘었다 줄었다 하려면 어떻게 과금해야 할까?

#3동작 예시

인스턴스 하나를 쓰는 시간, 스토리지에 저장한 데이터 양, 다른 서비스로 나가는 데이터 전송량이 각각 별도의 비용 항목으로 집계된다. 이 항목들을 합산한 값이 그 달의 비용이며, 사용량이 줄면 비용도 함께 줄어든다.

#4동작 과정

  1. 사용량 집계인스턴스 실행 시간, 스토리지 사용량, 데이터 전송량을 시간 단위로 집계한다.
  2. 항목별 과금집계된 사용량에 각 항목의 단가를 곱해 합산하고, 인스턴스 유형과 스토리지 구성을 조정해 비용을 최적화한다.
  3. 할인 적용예약 인스턴스(일정 기간을 미리 약정하고 할인받는 요금제)를 적용해 장기 사용 비용을 낮춘다.

#5한 줄 요약

인스턴스·스토리지·데이터 전송 등 쓴 만큼만 과금하고, 예약 인스턴스 할인과 비용 최적화 옵션으로 지출을 조절할 수 있게 하는 사용량 기반 비용 구조

#2핵심 질문

#1문제 상황

AWS는 OpenSearch 서비스 소프트웨어를 보안 패치와 기능 개선을 위해 주기적으로 업데이트한다. 업데이트를 적용하는 동안에는 인스턴스 재시작이 일어나 성능이 떨어질 수 있다.

트래픽이 많은 시간에 업데이트가 적용되면 사용자가 체감하는 지연이 커진다. 언제 업데이트가 오는지 모르고 알림도 놓치면, 원치 않는 시간에 가동 중단 영향을 맞게 된다.

#2핵심 질문

서비스 소프트웨어 업데이트를 내가 정한 시간대에만 적용하고, 그 일정을 미리 알 수는 없을까?

#3동작 예시

도메인에 오프피크 창(업데이트를 적용해도 되는 시간대)을 지정해 두면, AWS는 그 시간대 안에서만 서비스 소프트웨어 업데이트를 진행한다. 업데이트가 준비되면 콘솔과 이메일로 알림이 오고, 원하면 즉시 적용하거나 다음 오프피크 창까지 미룰 수 있다.

#4동작 과정

  1. 오프피크 창 지정도메인 설정에서 업데이트를 허용할 요일과 시작 시각을 정한다. 지정하지 않으면 AWS가 임의의 시간대를 잡는다.
  2. 업데이트 통지AWS가 새 서비스 소프트웨어를 적용할 준비를 마치면 콘솔에 상태가 표시되고 이메일 알림이 발송된다.

워크로드에 맞는 인스턴스·스토리지·샤드 용량을 설계하고 비용을 최적화하며, 쿼터와 모범 사례를 적용하는 것이다.

#1문제 상황

도메인을 만들 때 인스턴스 수, 인스턴스 유형, 스토리지 크기를 정해야 한다. 인스턴스를 작게 잡으면 검색과 색인 속도가 느려지고 저장 공간이 금방 차서 쓰기 요청이 거부된다. 반대로 크게 잡으면 유휴 리소스에 대한 비용이 계속 나간다. Amazon OpenSearch Service는 실행 중인 인스턴스 수와 스토리지 기준으로 과금되기 때문에, 남는 용량은 그대로 비용이 된다. 샤드 개수 배치도 실수하기 쉽다. 샤드를 너무 많이 만들면 오버헤드가 커지고, 너무 적게 만들면 하나의 샤드가 지나치게 커져 검색이 느려진다. 용량과 비용은 이렇게 서로 맞물려 있어서 사전 설계가 필요하다.

#2핵심 질문

워크로드에 맞는 인스턴스·스토리지·샤드 용량을 정해 성능을 유지하면서 비용을 최소로 하려면 어떻게 해야 하는가?

#3동작 예시

일 1천만 건의 로그 문서를 30일 보관하는 도메인을 설계한다고 하자. 문서 하나의 평균 크기와 일별 증가량으로 총 저장 용량을 먼저 계산한다. 그다음 메모리와 CPU 요구를 본다. 보관하는 30일 치를 모두 메모리에 올리지 않으므로, 검색 QPS(초당 요청 수)와 색인 처리량에 맞는 인스턴스 유형과 개수를 고른다. 총 데이터 크기를 샤드 하나의 권장 크기로 나눠 샤드 수를 정하고, 샤드 수가 인스턴스 수와 어긋나지 않게 배치한다.

#4동작 과정

  1. 수요 계산일별 문서 수와 문서 크기, 보관 기간으로 총 스토리지 용량을, 예상 검색·색인 요청량으로 CPU와 메모리 요구치를 산정한다.
  2. 인스턴스·샤드 결정산정된 용량을 기준으로 인스턴스 유형과 개수, 샤드 수와 각 샤드 크기(권장 수 GB 이내)를 정한다.
  3. 쿼터와 모범 사례 적용도메인별 인덱스·샤드 수 제한 같은 쿼터를 확인하고, 모범 사례(핫 인덱스에만 빠른 스토리지, 오래된 데이터는 저비용 계층으로)를 적용해 비용을 최적화한다.

#5한 줄 요약

워크로드의 저장·처리 요구를 먼저 계산하고 그에 맞는 인스턴스·샤드 구성과 쿼터·모범 사례로 성능과 비용의 균형을 잡는 것

스트리밍 적재의 전체 그림

S3·Kinesis·DynamoDB·Firehose·CloudWatch 같은 AWS 소스와 Logstash·OpenSearch Ingestion 파이프라인에서 도메인·컬렉션으로 데이터가 흘러 들어오는 적재 경로 전체를 한눈에 보여주는 그림.

→ 12-01 참조

#1문제 상황

검색하려면 먼저 데이터가 도메인 안에 있어야 한다. 기존에는 데이터를 파일이나 프로그램으로 한 번에 밀어 넣는 배치 방식이 흔했다. 배치 방식은 일정 주기가 지나야 새 데이터가 검색에 나타나서, 로그·센서·사용자 행동처럼 끊임없이 생기는 실시간성 데이터에는 맞지 않았다. 데이터를 기다렸다가 묶어 보내는 동안 최신 사건이 검색에서 빠져 있었다. 게다가 데이터는 S3, Kinesis, DynamoDB, CloudWatch 등 여러 AWS 서비스에 다른 형태로 흩어져 있어서, 소스마다 적재 경로를 따로 만들면 중복 작업이 생기고 관리가 어렵다.

#2핵심 질문

여러 AWS 소스와 파이프라인에서 끊임없이 생기는 데이터를 하나의 도메인·컬렉션으로 지속해서 흘려보내려면 어떤 경로들이 있는가?

#3동작 예시

우선 전체 그림을 큰 흐름으로 본다. 소스(S3, Kinesis, DynamoDB, Firehose, CloudWatch, Logstash, OpenSearch Ingestion) → 파이프라인(전송·변환) → 대상(도메인·컬렉션) 순서다. 예를 들어 Kinesis Data Streams에 로그가 쌓이면, OpenSearch Ingestion 파이프라인이 그 스트림을 읽어 변환하고 도메인에 연속으로 색인한다. S3의 파일은 파이프라인이나 Lambda 중계를 통해 적재되고, CloudWatch 로그도 전용 전송 기능으로 도메인에 들어온다.

#4동작 과정

  1. 소스에서 데이터 생성S3, Kinesis, DynamoDB, Firehose, CloudWatch 같은 AWS 서비스나 Logstash, OpenSearch Ingestion 파이프라인이 데이터를 내보낸다.
  2. 파이프라인 전송·변환OpenSearch Ingestion이나 Lambda가 데이터를 읽어 형태를 정리하고 벌크 단위로 묶는다.
  3. 도메인·컬렉션 적재정리된 데이터가 도메인 또는 컬렉션에 지속해서 색인되어 검색 가능한 상태가 된다.

#5한 줄 요약

S3·Kinesis·DynamoDB·Firehose·CloudWatch·Logstash·OpenSearch Ingestion 같은 소스들을 파이프라인으로 묶어 도메인·컬렉션으로 실시간 적재하는 전체 경로를 제공하는 것

S3·Kinesis·DynamoDB·Firehose·CloudWatch 적재

Lambda 중계 등과 함께 S3·Kinesis Data Streams·DynamoDB·Data Firehose·CloudWatch 다섯 AWS 소스에서 스트리밍 데이터를 도메인으로 지속해서 적재하는 방법 모음.

#1문제 상황

AWS에서 운영되는 서비스들은 각자 자기만의 장소에 데이터를 쌓는다. S3에는 파일·백업이, Kinesis Data Streams에는 실시간 이벤트가, DynamoDB에는 테이블 변경 기록이, CloudWatch에는 로그와 지표가 저장된다. 이 데이터를 검색하려면 전부 OpenSearch 도메인으로 옮겨야 한다. 소스마다 전송 방식이 달라서, 콘솔에서 여러 번 설정하거나 별도 전송 코드를 작성해야 했다. 일회성으로 파일을 올리는 방식은 계속 쌓이는 스트리밍 데이터에 맞지 않고, Lambda 같은 중계를 직접 만들면 실패 처리와 재시도까지 운영자가 관리해야 하는 부담이 생긴다.

#2핵심 질문

다섯 AWS 소스(S3, Kinesis, DynamoDB, Firehose, CloudWatch)의 데이터를 도메인으로 계속해서 밀어 넣으려면 각각 어떤 경로를 쓰는가?

#3동작 예시

Amazon Kinesis Data Firehose를 보자. Firehose는 전송 스트림으로 들어오는 데이터를 배치로 모아 변환하고, 대상으로 Amazon OpenSearch Service 도메인을 지정할 수 있다. Lambda가 전달한 데이터는 Firehose가 일정 크기나 시간마다 묶어 도메인에 벌크로 색인한다. S3는 파이프라인 또는 Lambda 이벤트가 객체 생성 시점에 받아 적재하고, CloudWatch는 서브스크립션 필터로 로그 그룹의 새 로그를 실시간 전달한다.

#4동작 과정

  1. 소스별 전송 설정S3는 버킷 이벤트나 파이프라인, Kinesis·DynamoDB는 스트림, Firehose는 전송 스트림, CloudWatch는 로그 그룹 필터로 각각 도메인을 대상으로 지정한다.
  2. 중계·변환Lambda나 Firehose가 소스 데이터를 읽어 JSON 형태로 정리하고 색인에 필요한 메타데이터(인덱스 이름, 타임스탬프)를 붙인다.
  3. 도메인으로 벌크 색인변환된 데이터가 묶음 단위로 도메인에 전달되어 색인되고, 이후 검색 쿼리로 바로 조회할 수 있다.

#5한 줄 요약

S3·Kinesis·DynamoDB·Firehose·CloudWatch 다섯 AWS 소스가 Lambda나 파이프라인 중계를 거쳐 데이터를 도메인으로 지속해서 벌크 색인하는 적재 경로들을 제공하는 것

Logstash 적재

자체 관리 Logstash 파이프라인을 도메인 엔드포인트에 연결해 로그·문서를 벌크로 색인하는 적재 방법.

#1문제 상황

Elasticsearch를 쓰던 환경에서는 로그 수집과 전송에 Logstash가 널리 쓰였다. Logstash는 입력, 필터, 출력 단계로 구성된 파이프라인으로 데이터를 읽고 가공해 검색 엔진에 보낸다. Amazon OpenSearch Service만으로는 Logstash가 없다. 자체 관리 Logstash 서버를 이전에 쓰던 그대로 두고, 출력 대상만 OpenSearch 도메인으로 바꿔야 하는 상황이 흔하다. 도메인과 Logstash 사이 인증 방식이나 엔드포인트 설정을 잘못 맞추면 연결이 계속 실패하고, 포트 접근이 막혀 있으면 파이프라인이 멈춘 채 로그가 쌓이기만 한다.

#2핵심 질문

자체 관리 Logstash 파이프라인을 Amazon OpenSearch Service 도메인에 연결해 로그를 계속 색인하려면 어떻게 해야 하는가?

#3동작 예시

운영 중인 Logstash가 애플리케이션 로그를 읽어 도메인으로 보낸다고 하자. Logstash 설정 파일의 output 섹션에 도메인 엔드포인트와 포트 443을 적는다. 인증은 IAM 자격 증명 기반으로 한다. Logstash가 서명한 요청을 보낼 수 있게 IAM 역할을 만들고 그 역할을 도메인 접근 정책에 허용한다. 클러스터가 다중 AZ(가용 영역)로 운영되면 연결의 절반이 정상적으로 동작하려면 node-to-node 암호화 사용이 권장된다.

#4동작 과정

  1. 도메인 접근 준비도메인 엔드포인트와 포트, 접근 정책을 확인하고 Logstash가 사용할 IAM 역할에 도메인 접근 권한을 부여한다.
  2. Logstash 출력 설정logstash.yml 또는 파이프라인 설정의 output에 도메인 URL과 인증(사용자/비밀번호 또는 IAM 서명)을 지정하고 필요한 포트를 연다.
  3. 벌크 색인 실행Logstash가 읽은 로그를 묶음 단위로 도메인에 보내 색인하고, 실패한 배치는 재시도하며 계속 전송한다.

#5한 줄 요약

기존 Logstash 파이프라인의 출력 대상을 도메인 엔드포인트와 IAM 인증으로 연결해 로그를 벌크 색인하는 것

도메인·컬렉션 사이 데이터 이동

OpenSearch Ingestion 파이프라인을 이용해 도메인 간 또는 도메인과 컬렉션 사이에 데이터를 마이그레이션하는 방법.

#1문제 상황

데이터는 한 도메인에 계속 쌓이다 보니, 도메인을 통합하거나 기능이 다른 새 도메인·컬렉션으로 옮겨야 할 때가 생긴다. 버전이 다른 도메인으로 이전하거나, 벡터 검색 전용 컬렉션으로 보내는 경우가 그렇다. 수동으로 데이터를 내보내고 다시 넣으면 중단 시간과 데이터 어긋남이 생긴다. 색인을 통째로 옮기는 것도 대상 도메인의 버전과 설정이 맞아야 해서 쉽지 않다. 소스에서 대상으로 직접 전송하는 단순 복사 방식은 데이터가 커지면 단일 전송이 병목이 되고, 진행 상황을 관리하는 것도 어렵다.

#2핵심 질문

도메인 간, 또는 도메인과 컬렉션 사이에 데이터를 안정적으로 옮기려면 어떤 파이프라인을 쓰는가?

#3동작 예시

OpenSearch Ingestion 파이프라인으로 기존 도메인의 인덱스를 새 도메인으로 옮긴다고 하자. 파이프라인 설정에 소스(기존 도메인)와 싱크(대상 도메인·컬렉션)를 각각 지정한다. 파이프라인이 소스 도메인에서 문서를 읽어 대상으로 보낸다. 소스와 대상 버전·인증 정보가 설정에 맞으면 파이프라인 인프라가 AWS에 생성되고, 데이터가 스트리밍으로 계속 이동한다.

#4동작 과정

  1. 파이프라인 정의소스(도메인)와 싱크(대상 도메인·컬렉션), 인증 정보를 담은 OpenSearch Ingestion 파이프라인 설정을 작성한다.
  2. 파이프라인 실행설정을 제출하면 파이프라인이 생성되어 소스 도메인에서 데이터를 읽기 시작한다.
  3. 데이터 이동 완료문서가 대상 도메인·컬렉션에 색인되어 전체 이전이 끝나고, 이후 소스의 새 데이터도 정책에 따라 계속 이동시킬 수 있다.

SQL 질의

OpenSearch 데이터를 REST API 대신 SQL 문법으로 질의하고 결과를 표 형태로 받을 수 있게 해주는 기능이다.

#1문제 상황

OpenSearch의 기본 검색은 쿼리 DSL이라고 하는 JSON 구조로 요청을 보낸다. 필드 이름과 중첩 구조를 정확히 알아야 하고 조건이 조금만 복잡해져도 JSON이 길고 읽기 어려워진다. SQL에 익숙한 개발자는 매번 새 문법을 익혀야 하므로 진입 장벽이 된다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. SQL 수신과 파싱클라이언트가 SQL 질의를 _plugins/_sql 엔드포인트로 보내면 서버가 문장을 분석해 어떤 필드를 어떻게 검색·정렬·집계할지 해석한다.

  3. 표 형태 반환집계·정렬이 끝난 결과를 컬럼 이름과 행 데이터로 구성된 표 형식의 JSON 응답으로 돌려준다.

Learning to Rank

검색 결과의 상위 순위를 사용자 피드백으로 학습된 머신러닝 모델이 다시 매겨 검색 정확도를 높이는 기능이다.

#2핵심 질문

#3동작 예시

비동기 검색과 Point in time

오래 걸리는 검색을 백그라운드에서 실행해 나중에 결과를 가져오는 비동기 검색과, 검색 시점의 인덱스 상태를 고정하는 Point in time 기능이다.

#1문제 상황

일반 검색은 요청을 보내면 결과가 나올 때까지 연결을 계속 붙잡고 기다린다. 집계가 무겁거나 데이터가 많은 검색은 몇 초 이상 걸리는데, 그동안 클라이언트 연결이 끊기면 검색 결과가 통째로 사라진다. 또 긴 검색이 실행되는 사이에 문서가 추가·삭제되면 시작 시점과 끝 시점의 데이터 상태가 달라져 일관된 결과를 보장할 수 없다.

#2핵심 질문

오래 걸리는 검색을 백그라운드에서 돌려 연결이 끊겨도 결과를 나중에 가져오고, 검색 중 데이터가 바뀌어도 일관된 스냅샷을 유지할 수는 없을까?

#3동작 예시

수억 건 로그에 대한 집계 검색을 요청하면 서버가 즉시 작업 ID를 돌려주고, 검색은 백그라운드에서 계속 진행된다. 클라이언트는 연결을 끊었다가 몇 초 뒤 작업 ID로 상태를 물어 완료된 결과만 받아가면 된다. Point in time을 지정하면 검색이 시작된 시점의 인덱스 상태가 고정되어 그 스냅샷 기준으로 결과가 나온다.

#4동작 과정

  1. 비동기 검색 시작클라이언트가 비동기 검색 요청을 보내면 서버가 작업을 등록하고 즉시 작업 ID를 반환하며, 검색은 백그라운드에서 실행된다.
  2. 결과 폴링클라이언트가 작업 ID로 완료 여부를 물어보고, 진행 중에는 부분 결과나 진행률을 받는다.
  3. 완료 결과 수령검색이 끝나면 전체 결과를 한 번에 받아가고, Point in time이 설정된 경우 시작 시점의 고정된 스냅샷 데이터 기준으로 결과가 유지된다.

#5한 줄 요약

#1문제 상황

#2핵심 질문

단어 일치가 아니라 의미의 유사성으로 문서를 찾고, 대화형 질의를 검색 쿼리로 자동 만들며, 검색 속도까지 높일 수는 없을까?

#3동작 예시

#4동작 과정

  3. 세그먼트 병렬 검색과 반환인덱스의 세그먼트(문서가 저장된 조각)를 여러 스레드로 동시에 검색해 결과를 모은 뒤, 유사도 순으로 정렬된 문서 목록을 돌려준다.

S3에 보관된 대규모 벡터 데이터를 OpenSearch 벡터 엔진으로 가져오고, 자동 최적화가 인덱스 성능과 저장 효율을 관리하는 기능.

#1문제 상황

규모가 큰 벡터 데이터를 OpenSearch 로 옮길 때 전체를 한 번에 클러스터로 밀어 넣으면 시간과 비용이 크게 든다. 또한 벡터가 계속 늘어나면 저장 공간과 검색 성능이 어떤 인덱스 설정이 유리한지 관리자가 일일이 판단해야 했다.

#2핵심 질문

이미 S3 에 보관된 대규모 벡터 데이터를 효율적으로 가져오고 인덱스 상태를 자동으로 관리하려면 어떻게 해야 할까?

#3동작 예시

수억 건의 벡터가 S3 에 저장돼 있다면, 이 데이터를 OpenSearch 로 복사해 넣는 대신 S3 를 원본으로 인식하고 필요한 부분만 읽어 벡터 엔진으로 유입시킨다. 인덱스는 자동 최적화 기능이 분할과 병합을 스스로 조절한다.

#4동작 과정

  1. S3 데이터 연결S3 의 벡터 데이터 경로를 OpenSearch 벡터 엔진에 등록해 원본 저장소로 인식시킨다.
  2. 벡터 유입S3 데이터를 읽어 벡터 인덱스에 반영하고, 새 데이터는 계속 증분으로 동기화한다.
  3. 자동 최적화자동 최적화가 인덱스 분할·병합·압축을 상황에 맞춰 조절해 성능과 저장 효율을 관리한다.

#5한 줄 요약

S3 에 있는 대규모 벡터 데이터를 벡터 엔진에 끌어와 검색 가능하게 만들고, 자동 최적화가 인덱스 성능과 저장 효율을 관리하는 것

파생 소스와 Zstandard 압축

원본에서 파생 소스 필드를 생성해 저장 공간을 절약하고, Zstandard 코덱으로 더 높은 압축률과 처리 성능을 얻는 저장 최적화 기능.

#1문제 상황

벡터 검색을 쓰려면 원본 문서와 벡터를 함께 보관해야 하는데, 원본을 그대로 저장하면 공간을 많이 차지하고 벡터와 함께 복사본까지 늘어나 저장 비용이 커졌다. 또한 저장 압축에 오래 걸리는 코덱을 쓰면 공간은 줄지만 처리 속도가 느려지는 트레이드오프가 있었다.

#2핵심 질문

벡터 검색에 필요한 정보를 유지하면서 저장 공간을 줄이고 처리도 빠르게 하려면 어떻게 해야 할까?

#3동작 예시

원본 문서 전체를 저장하는 대신 검색에 필요한 필드들만 모아 만든 축약 버전을 "파생 소스"로 저장하고, 이 파생 소스를 Zstandard 코덱으로 압축해 보관한다. 문서를 다시 불러올 때는 압축을 풀어 원래 필드를 복원한다.

#4동작 과정

  1. 파생 소스 생성원본 문서에서 필요한 필드를 추려 별도의 파생 소스 필드를 만들고 원본 저장을 생략한다.
  2. Zstandard 압축파생 소스를 Zstandard 코덱으로 압축해 저장해 공간 사용을 줄인다.
  3. 복원 및 반환조회 시 압축을 풀어 원본 필드를 복원하고 검색 결과로 반환한다.

#5한 줄 요약

원본 대신 파생 소스 필드를 만들고 Zstandard 코덱으로 압축해 저장하여 공간을 줄이면서도 처리 성능을 유지하는 저장 최적화

머신 러닝 커넥터

OpenSearch 도메인을 Amazon Bedrock, Amazon SageMaker 등 AWS 및 외부 플랫폼의 ML 모델에 연결해 임베딩 생성·추론을 수행하게 하는 통합 기능.

#1문제 상황

벡터 검색이나 에이전트 기능을 쓰려면 문서를 벡터로 바꾸고 질문을 해석할 머신 러닝 모델이 필요하다. 하지만 모델을 직접 도메인 안에 띄우려면 GPU 자원과 모델 관리 비용이 들었고, 모델마다 호출 방식이 달라 연결할 때마다 별도 구현이 필요했다.

#2핵심 질문

외부 머신 러닝 모델을 OpenSearch 에 쉽게 연결해 임베딩과 추론을 쓰려면 어떻게 해야 할까?

#3동작 예시

OpenSearch 도메인에 ML 커넥터 하나를 등록하면 Amazon Bedrock 이나 Amazon SageMaker 의 모델을 도메인 밖에서 호출할 수 있다. 문서가 들어오면 커넥터가 그 모델을 불러 벡터를 만들고, 검색 시에도 같은 경로로 질문을 벡터로 바꾼다.

#4동작 과정

  1. 커넥터 등록연결할 모델 서비스(AWS 또는 외부 플랫폼)의 접속 정보와 호출 방식을 담은 커넥터를 등록한다.
  2. 모델 연결커넥터를 통해 모델을 OpenSearch 내부 리소스로 등록해 검색 파이프라인에서 호출 가능하게 만든다.
  3. 임베딩·추론 수행인덱싱과 검색 과정에서 모델을 호출해 임베딩 생성이나 추론 결과를 얻어 사용한다.

#5한 줄 요약

OpenSearch 도메인을 외부 ML 모델과 연결하는 커넥터를 제공하여 도메인을 떠나지 않고 임베딩 생성과 추론을 수행하게 하는 통합 기능

CloudFormation 템플릿 통합

ML 커넥터, 에이전트 등 머신 러닝 리소스를 AWS CloudFormation 템플릿으로 선언해 일관되게 배포하고 관리하는 방법.

#1문제 상황

ML 커넥터와 에이전트 같은 머신 러닝 리소스는 콘솔에서 클릭으로 만들다 보면 설정이 누락되거나 환경마다 모양이 달라지기 쉽다. 리소스가 늘어날수록 재현 가능한 배포가 어려워지고, 장애 시 같은 구성을 다시 만드는 데 시간이 걸렸다.

#2핵심 질문

ML 커넥터와 에이전트 리소스를 같은 설정으로 반복해서 배포하고 관리하려면 어떻게 해야 할까?

#3동작 예시

ML 커넥터, 모델, 에이전트의 설정을 코드로 작성해 CloudFormation 템플릿으로 묶어 둔다. 템플릿 한 번 실행으로 여러 AWS 리소스가 정의된 순서대로 생성되고, 다른 리전이나 계정에 같은 템플릿을 적용하면 동일한 구성이 그대로 재현된다.

#4동작 과정

  1. 템플릿 작성ML 커넥터와 에이전트에 필요한 리소스와 속성, 의존 관계를 YAML 이나 JSON 으로 선언한다.
  2. 스택 배포템플릿을 CloudFormation 스택으로 실행해 리소스가 순서에 맞춰 생성되고 연결된다.
  3. 일관 관리템플릿만 갱신해 다시 배포하면 변경 사항이 같은 방식으로 모든 환경에 적용된다.

#5한 줄 요약

Flow framework 플러그인

커넥터·모델·프롬프트를 조합해 검색, 요약, 질의응답 같은 ML 워크플로(에이전트)를 구성하고 실행하는 프레임워크 플러그인.

#1문제 상황

기존에는 OpenSearch에서 ML 작업을 하려면 커넥터를 붙이고 모델을 배포한 뒤 각 API를 직접 호출해 결과를 조합해야 했다. 검색-요약-질의응답처럼 여러 단계를 잇는 로직이 스크립트로 흩어져 있어 관리가 어렵고 재사용도 힘들었다.

#2핵심 질문

커넥터·모델·프롬프트를 한데 묶어 검색, 요약, 질의응답 같은 ML 워크플로를 OpenSearch 안에서 손쉽게 구성하고 실행할 수 없을까?

#3동작 예시

검색 요청 하나를 받으면 "문서를 검색하고 → 검색 결과를 LLM에 넘겨 요약하고 → 요약 텍스트를 응답으로 돌려주는" 일련의 단계를 하나의 워크플로 정의로 실행하는 경우다.

#4동작 과정

  1. 워크플로 정의 등록사용할 커넥터(외부 ML 제공자 연결 정보)와 모델, 프롬프트, 실행 순서를 하나의 템플릿으로 등록한다.
  2. 실행 요청등록된 워크플로를 워크플로 API로 호출하면 정의된 순서에 따라 단계가 시작된다.
  3. 단계 실행과 응답 반환각 단계가 차례로 실행되고 최종 결과(요약·검색 결과 등)가 요청자에게 돌아간다.

MCP 서버와 Agent Skills

에이전트가 OpenSearch 데이터를 도구로 조회·분석할 수 있게 해주는 Model Context Protocol(MCP) 서버와 전용 에이전트 스킬.

#1문제 상황

기존에는 LLM 에이전트가 OpenSearch 데이터에 접근하려면 별도 코드로 REST API를 호출하고 인증, 쿼리 작성, 결과 파싱을 직접 처리해야 했다. 에이전트마다 이 작업을 반복 구현하다 보니 연결이 복잡해지고 관리 부담이 커졌다.

#2핵심 질문

에이전트가 표준화된 방식으로 OpenSearch 데이터를 도구처럼 조회하고 분석하게 하려면 어떻게 해야 할까?

#3동작 예시

MCP 서버가 "인덱스 검색, 문서 조회, 집계" 같은 도구 목록을 에이전트에 제공하고, 에이전트가 자연어 요청을 도구 호출로 바꿔 OpenSearch에 질의한 뒤 그 결과를 답변 생성에 활용하는 흐름이다.

#4동작 과정

  1. 도구 노출OpenSearch MCP 서버가 인덱스 검색·분석용 도구를 표준 프로토콜(Model Context Protocol)로 에이전트에 제공한다.
  2. 도구 선택과 호출에이전트가 사용자 질문에 맞는 도구를 골라 파라미터와 함께 호출하고, Agent Skills로 정해진 분석 절차를 재사용한다.
  3. 결과 반환조회 결과가 에이전트로 돌아와 답변 생성에 사용된다.

Security Analytics

도메인에 수집된 로그를 탐지 규칙과 위협 인텔리전스 피드로 분석해 보안 위협과 이상 징후를 찾아내는 통합 보안 기능.

#1문제 상황

기존에는 보안 로그를 수집해 두어도 위협을 찾으려면 별도 SIEM 도구를 운영하거나 탐지 규칙을 일일이 작성해 검색해야 했다. 위협 인텔리전스 정보를 최신으로 유지하는 것도 별도 프로세스가 필요해 탐지가 늦어지기 쉬웠다.

#2핵심 질문

OpenSearch에 쌓인 로그에서 보안 위협과 이상 징후를 탐지 규칙과 위협 인텔리전스 피드만으로 자동으로 찾아낼 수 없을까?

#3동작 예시

수집된 로그에 "실패한 로그인 반복" 탐지 규칙을 적용하고, 외부 위협 인텔리전스 피드에 있는 악성 IP·도메인과 로그를 대조해 의심 행위를 보안 파인딩으로 만드는 경우다.

#4동작 과정

롤업·트랜스폼·데이터 스트림·star-tree

시계열 데이터를 압축·집계하거나 스트림으로 나눠 저장량을 줄이는 롤업·트랜스폼·데이터 스트림·star-tree 색인 기법들이다.

#1문제 상황

시계열 데이터(시간순으로 쌓이는 로그·메트릭)를 원본 그대로 색인에 보관하면 저장 용량과 비용이 계속 늘어난다. 오래된 데이터는 조회 빈도가 낮은데도 상세 그대로 공간을 차지하고, 색인이 커질수록 쿼리도 느려진다. 기존 방식은 데이터를 나누거나 요약하지 않고 한 색인에 전부 쌓아 두는 방식이라 이 문제를 피할 수 없었다.

#2핵심 질문

시간이 지나면 잘 안 쓰이는 시계열 데이터를, 상세함은 줄이고 저장량은 줄여 어떻게 계속 저렴하게 관리할까?

#3동작 예시

데이터 스트림(data stream, 날짜별 새 색인을 자동 생성해 시계열 데이터를 나눠 받는 저장 방식)으로 데이터를 백업 색인(뒤에서 실제 저장을 담당하는 색인)에 나눠 쌓으면, 오래된 색인만 골라 보존 정책을 적용할 수 있다. 롤업(rollup)은 1분 단위 원본을 1시간 단위 요약본으로 미리 집계해 작은 인덱스로 저장하므로, 원본을 지워도 과거 추세 조회는 계속 가능하다.

#4동작 과정

  1. 데이터 스트림으로 나눠 받기시계열 데이터를 날짜별 새 백업 색인에 자동 분산해 쌓고, 오래된 색인만 따로 관리 대상으로 분리한다.
  2. 롤업·트랜스폼으로 요약본 만들기원본을 시간 단위·필드별로 미리 집계(합계·평균 등)해 작은 인덱스로 만들고, 보존 기간이 지난 원본은 삭제해 공간을 되돌린다.
  3. star-tree 로 조회 가속화자주 쓰는 집계 조합을 미리 계산한 압축 색인 구조를 활용해, 큰 데이터를 전부 뒤지지 않고도 집계·조회를 빠르게 끝낸다.

크로스 클러스터 복제와 원격 재색인

인덱스를 다른 도메인에 실시간 복제하거나 원격 클러스터의 데이터를 다시 색인해 재해 복구와 마이그레이션을 지원하는 기능이다.

#1문제 상황

도메인 하나에 데이터와 서비스가 전부 몰려 있으면, 그 도메인이 장애로 죽었을 때 데이터와 서비스를 함께 잃는다. 같은 데이터를 다른 리전의 도메인에 미리 복제해 두면 장애에 대비할 수 있지만, 기존 방식은 스냅샷(지정 시점의 데이터 사본)을 떠서 수동으로 복원하는 방식이라 복제 시점 이후의 데이터가 유실되고 복원하는 데도 오랜 시간이 걸린다.

#2핵심 질문

도메인이 장애로 죽어도 서비스를 이어가도록, 데이터를 다른 도메인으로 실시간에 가깝게 복제하는 방법은?

#3동작 예시

크로스 클러스터 복제(cross-cluster replication, 다른 도메인으로 인덱스를 복제하는 기능)는 원본 도메인의 리더(원본 인덱스)와 대상 도메인의 팔로워(복제 인덱스)를 연결한다. 원본에 문서가 추가·수정·삭제될 때마다 그 변경이 대상 인덱스에 그대로 따라 적용되므로, 원본이 죽어도 대상 도메인으로 곧바로 서비스를 전환할 수 있다.

#4동작 과정

  1. 복제 연결 설정원본 도메인과 대상 도메인을 연결하고, 복제할 인덱스를 리더와 팔로워 쌍으로 지정한다.
  2. 변경 사항 동기화리더 인덱스에 문서 변경이 생길 때마다 대상 도메인이 변경 기록을 가져와 팔로워 인덱스에 적용해 계속 따라간다.
  3. 장애 시 전환·이관원본이 죽으면 대상 도메인으로 읽기·쓰기를 전환하고, 원격 재색인(원격 도메인의 데이터를 다시 색인해 옮기는 기능)으로 데이터를 새 도메인으로 이관한다.

#4동작 과정

#4동작 과정

#2핵심 질문

#2핵심 질문

#3동작 예시

#4동작 과정

  2. 공유 한도 적용그룹 안의 모든 컬렉션이 같은 용량 풀을 공유하므로, 어떤 컬렉션이 몰려도 그룹 한도 안에서 조정된다.
  3. scale to zero 실행사용량이 없으면 그룹의 용량이 0까지 줄고 요청이 오면 다시 올라가며, 0인 동안에는 컴퓨팅 비용이 나가지 않는다.

OpenSearch Ingestion 개념과 한계

Amazon OpenSearch Ingestion은 데이터를 OpenSearch Service 도메인이나 Serverless 컬렉션으로 실시간 수집·변환해 전달하는 완전관리형 파이프라인 서비스로, 지원 기능과 제약(리전·한도 등)을 함께 알아야 한다.

#1문제 상황

데이터를 OpenSearch로 보내는 기존 방식은 애플리케이션에서 수집 에이전트를 직접 띄우거나, 전송 파이프라인을 자체 서버에 설치해 운영해야 했다. 이렇게 하면 파이프라인 서버의 크기 조정, 장애 복구, 버전 관리까지 모두 사용자가 책임져야 한다. 데이터 양이 늘어날 때마다 인프라를 손봐야 하는 부담이 컸다.

#2핵심 질문

수집부터 변환·전달까지의 데이터 파이프라인을 직접 관리하지 않고도 실시간으로 OpenSearch에 넣을 수 없을까?

#3동작 예시

S3에 파일이 올라오면 OpenSearch Ingestion 파이프라인이 그 이벤트를 감지해 파일을 읽고, JSON으로 변환한 뒤 대상 도메인 인덱스에 실시간으로 넣는다. 파이프라인 용량은 설정한 단위에 따라 AWS가 자동으로 확장하므로 사용자는 파이프라인 정의만 작성하면 된다.

#4동작 과정

  1. 파이프라인 정의 작성YAML 형식으로 소스(어디서 데이터를 받을지)와 프로세서(어떻게 변환할지), 싱크(어디로 보낼지)를 지정해 파이프라인 구성을 만든다.
  2. 실시간 수집·변환소스에서 들어온 데이터를 정의된 프로세서로 필터링·변환하며 대상 형식에 맞춘다.
  3. 대상으로 전달변환된 데이터를 서버리스 컬렉션이나 도메인에 실시간으로 전송한다. 단, 지원 리전과 파이프라인당 처리 한도 같은 제약이 있어 사용 전에 확인해야 한다.

파이프라인 비용 관리

파이프라인은 실행 중일 때만 과금되므로, 사용하지 않을 때는 중지하고 필요할 때 다시 시작해 비용을 관리하는 방법을 말한다.

#1문제 상황

파이프라인은 구성된 용량만큼 계속 실행되는 컴퓨팅 리소스라서, 데이터가 들어오지 않아도 켜져 있으면 비용이 발생한다. 기존에는 파이프라인을 만들면 중지 기능이 명확하지 않아, 잠시 쓰지 않는 동안에도 과금이 이어지거나 운영을 멈추기 위해 통째로 삭제해야 했다. 사용량과 비용을 맞추는 관리 수단이 필요했다.

#2핵심 질문

데이터를 보내지 않는 동안에도 파이프라인 비용이 계속 청구되는 문제를 어떻게 막을 수 있을까?

#3동작 예시

배치 처리가 끝나 다음 배치까지 시간이 남은 주말 동안 파이프라인을 중지(stop)해 두면 실행 컴퓨팅 비용이 발생하지 않는다. 월요일에 파이프라인을 다시 시작(start)하면 이전 구성을 그대로 유지한 채 수집이 재개된다.

#4동작 과정

  1. 중지파이프라인을 stop 상태로 전환하면 실행 중이던 컴퓨팅 리소스가 내려가고 이후로는 과금이 중단된다. 중지 시점에 버퍼에 남은 데이터는 대상으로 마저 전달되고 수집은 멈춘다.
  2. 대기중지된 동안 파이프라인 정의와 설정은 그대로 보존되며 비용은 발생하지 않는다.
  3. 시작필요할 때 start로 다시 켜면 보존된 구성을 그대로 사용해 수집이 재개되고 과금도 다시 시작된다.

#5한 줄 요약

실행 중일 때만 과금되는 특성을 활용해, 사용하지 않을 때는 중지하고 필요할 때 다시 시작함으로써 파이프라인 비용을 통제하는 것

소스 커넥터

S3, DynamoDB, Kafka(MSK·Confluent), Kinesis, Lambda 등 다양한 AWS·타사 소스에서 파이프라인으로 데이터를 받아들이는 커넥터 구성을 말한다.

#1문제 상황

데이터는 S3, DynamoDB, Kafka, Kinesis, Lambda 등 제각각 다른 형태의 소스에 흩어져 있다. 기존에는 소스마다 전용 수집 코드와 전송 프로그램을 따로 만들어 파이프라인에 연결해야 했고, 소스가 늘어날 때마다 통합 작업이 반복됐다. 소스별 연결 방식을 표준화하지 않으면 수집 구축 비용이 계속 커진다.

#2핵심 질문

형태가 서로 다른 여러 데이터 소스를 하나의 파이프라인에 표준화된 방식으로 연결할 수 없을까?

#3동작 예시

파이프라인 정의의 소스 부분에 s3 소스와 버킷 이름, 이벤트 알림 설정을 적으면 S3에 객체가 올라올 때마다 자동으로 수집이 시작된다. 같은 방식으로 소스 이름만 dynamodb, kafka, kinesis로 바꾸면 각 소스가 파이프라인으로 데이터를 보낸다.

#4동작 과정

  1. 소스 선택과 권한 부여수집할 소스 유형(S3, DynamoDB, MSK, Kinesis 등)을 파이프라인 정의에 지정하고, 파이프라인 역할에 해당 소스를 읽을 IAM 권한을 부여한다.
  2. 이벤트 수신소스에서 생성된 데이터 변경 이벤트나 레코드를 파이프라인이 수신한다. S3는 객체 생성 알림을, Kafka·Kinesis는 스트림 레코드를, DynamoDB는 변경 사항을 받는다.
  3. 후속 처리로 연결받은 데이터를 이후 프로세서·싱크 단계로 넘긴다. Lambda는 사용자 지정 소스로 파이프라인에 직접 데이터를 넣는 데 쓴다.

#5한 줄 요약

S3·DynamoDB·Kafka·Kinesis 등 다양한 소스를 파이프라인 정의의 표준화된 소스 구성으로 연결해 수집을 자동화하는 것

파이프라인 보안과 네트워크

파이프라인에 IAM 역할·권한을 부여하고 VPC 접근, 교차 계정 수집, PrivateLink 등을 설정해 데이터 전송을 안전하게 보호하는 방법을 말한다.

#1문제 상황

파이프라인은 소스의 데이터를 읽어 대상으로 전달하는 동안 여러 계정과 네트워크를 거쳐 이동한다. 기존에는 전송 목적지인 도메인의 보안만 신경 쓰고, 파이프라인 자체가 어떤 권한으로 어느 네트워크에서 데이터를 주고받는지는 간과하기 쉬웠다. 권한이 과하거나 네트워크가 열려 있으면 데이터가 노출될 위험이 있다.

#2핵심 질문

파이프라인이 데이터를 읽고 전달하는 전 구간에서 권한과 네트워크 접근을 어떻게 안전하게 통제할 수 있을까?

#3동작 예시

파이프라인에 소스 읽기와 대상 쓰기 권한만 들어 있는 최소 권한 IAM 역할을 부여하고, 대상 도메인 쪽에는 이 역할만 접근하도록 리소스 정책을 건다. VPC 내부에 파이프라인을 두면 인터넷을 거치지 않고 사설 네트워크로만 데이터가 이동한다.

#4동작 과정

  1. IAM 역할과 권한 부여파이프라인에 소스를 읽고 대상에 쓸 수 있는 최소 권한의 IAM 역할을 연결한다. 교차 계정 수집이면 대상 계정이 파이프라인 역할을 신뢰하도록 설정한다.
  2. 네트워크 접근 구성파이프라인을 VPC 안에 배치해 사설망으로 통신하거나, PrivateLink로 특정 VPC에서만 접근할 수 있게 한다. 기본값은 AWS 네트워크를 통한 안전한 전송이다.
  3. 대상 측 정책과 암호화 적용대상 도메인·컬렉션의 접근 정책에 파이프라인 역할을 허용하고, 전송 구간과 저장 데이터가 각각 암호화되도록 설정해 전 구간을 보호한다.

#5한 줄 요약

IAM 최소 권한 역할, VPC·PrivateLink 기반 네트워크 제어, 대상 접근 정책을 조합해 파이프라인의 데이터 수집·전송 구간을 안전하게 보호하는 것

파이프라인 모니터링과 모범 사례

파이프라인의 로그와 지표를 CloudWatch 등으로 모니터링하고, 공식 모범 사례를 따라 안정적으로 운영하는 방법을 말한다.

#1문제 상황

파이프라인이 데이터를 처리하다가 지연되거나 실패해도, 이를 감지하는 장치가 없으면 데이터가 조용히 유실된다. 기존에는 파이프라인 로그를 수동으로 뒤져 문제를 파악해야 했고, 처리량이 한도에 도달했는지도 알기 어려웠다. 운영 안정성을 확보하려면 상태를 자동으로 관찰할 수단과 그에 따른 운영 기준이 필요했다.

#2핵심 질문

파이프라인이 실시간으로 데이터를 잘 처리하고 있는지, 문제가 생기면 어떻게 알 수 있을까?

#3동작 예시

CloudWatch에 파이프라인의 처리 지연 지표를 보내고, 지연 시간이 기준을 넘으면 알림이 울리도록 경보를 설정한다. 운영자는 콘솔의 파이프라인 대시보드에서 수신·전송 건수와 오류 수를 한눈에 보고, 필요하면 파이프라인 구성을 고친다.

#4동작 과정

  1. 지표 수집파이프라인 실행과 관련한 처리량, 지연, 오류 등의 지표를 CloudWatch로 전송한다. 파이프라인별 상태와 수집 경로 구성은 콘솔에서 확인한다.
  2. 로그와 경보 설정파이프라인의 애플리케이션 로그를 CloudWatch Logs에 남기고, 지표가 임계값을 넘으면 알림을 보내는 경보를 만든다.
  3. 모범 사례 적용으로 운영실패 데이터를 재시도하거나 DLQ(처리 실패 메시지를 모아두는 대기열)로 보내는 구성, 최소 권한 IAM, 적정 용량 산정 등을 적용해 파이프라인을 안정적으로 유지한다.

#5한 줄 요약

CloudWatch 지표·로그·경보로 파이프라인 상태를 자동 관찰하고, 공식 모범 사례에 따라 안정적으로 운영하는 것
