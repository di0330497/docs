Amazon VPC란 무엇인가 — 논리적으로 격리된 가상 네트워크

Amazon VPC(가상 프라이빗 클라우드)는 물리적 하드웨어가 아니라 클라우드 안의 설정으로 그어진 가상의 사설 네트워크 경계로, 그 안에서 IP 주소 범위와 서브넷·라우팅 테이블 등의 네트워크 자원을 원하는 대로 조합해 격리된 환경을 만든다.

#1문제 상황

AWS에서 인스턴스를 만들면 다른 사람이 만든 네트워크에 같이 놓인다. 그래서 보안 그룹 규칙을 일일이 좁혀야 하고, 다른 고객의 주소와 겹칠까 봐 신경 쓴다.

Amazon VPC는 사용자가 정의한 논리적으로 격리된 virtual network 안에서 AWS 리소스를 실행하게 한다. 직접 관리하는 데이터 센터의 네트워크와 닮았고, 그 안에 subnet과 internet gateway를 조합해 나만의 통신 구조를 세운다.

#2핵심 질문

내 리소스만 들어 있는 격리된 네트워크를 어떻게 만드는가?

#3동작 예시

콘솔에서 VPC를 만들고 그 안의 각 가용 영역마다 subnet을 하나씩 만든다. subnet 안에 EC2 인스턴스를 띄우면 서로 다른 주소로 나뉘어 배치된다. internet gateway를 붙이면 그 안에서 외부 통신이 필요한 subnet이 인터넷으로 나갈 수 있다.

#4동작 과정

  1. 범위를 그린다VPC에 IPv4 CIDR 블록을 정해 사용할 IP 주소 범위를 정한다. 이 안에서만 뒤 단계의 자원이 만들어진다.
  2. 나눈다subnet은 가용 영역마다 하나씩 만든다. subnet은 VPC의 주소 범위를 쪼갠 구간이다.
  3. 연결한다internet gateway를 붙여 필요한 subnet의 트래픽을 인터넷으로 내보낸다.
  4. 확인해 볼 것VPC를 선택해 리소스 맵에서 subnet이 가용 영역별로 나뉘어 있는지와 각 subnet의 공용·프라이빗 표시를 확인한다.

VPC 가 들어갈 수 있는 자리 — 리전과 가용 영역

VPC는 특정 리전 하나를 골라 그 안에서 만드는 네트워크이고, 리전은 물리적으로 떨어진 여러 데이터 센터를 묶는 단위이며, 가용 영역은 리전 안에서 서로 독립된 데이터 센터 하나를 뜻해 서로 다른 가용 영역에 리소스를 분산해 장애에 대비하게 된다.

먼저 알아야 할 것 01-01

#1문제 상황

VPC를 어디에 둘지 정하지 않으면 리소스가 한 곳에 몰린다. 그 한 곳이 점검이나 장애를 겪으면 다 같이 멈춘다.

AWS Region은 물리적으로 떨어진 여러 데이터 센터를 묶은 단위이고, Availability Zone은 그 리전 안에서 전원·네트워크가 독립된 데이터 센터 하나다. VPC는 리전 하나를 고르고, 그 안의 여러 Availability Zone에 subnet을 나눠 놓는다.

#2핵심 질문

한 리전 안에 여러 Availability Zone에 나눠 놓으면 무엇이 달라지는가?

#3동작 예시

VPC를 서울 리전에 만들고 가용 영역 두 곳에 subnet을 하나씩 만든다. 애플리케이션 서버는 한쪽에, 데이터베이스는 다른 쪽에 두어 한 곳이 끊겨도 나머지가 계속 받는다.

#4동작 과정

  1. 리전을 고른다Region을 정하면 VPC가 그 리전 안에서만 만들어진다.
  2. 영역을 나른다Availability Zone별로 subnet을 하나씩 배치한다. 리전은 Zonal, 즉 각 영역 단위의 구분이 있고 subnet도 여기에 묶인다.
  3. 분산한다같은 애플리케이션을 여러 영역에 나눠 두어 한 곳의 정전이나 천둥 같은 문제를 피한다. subnet 단위로 분리하면 격리 효과가 커진다.
  4. 확인해 볼 것subnet 목록에서 각 subnet이 어느 Availability Zone에 속하는지 다른지 확인한다.

#2핵심 질문

VPC를 만들 때 어떤 값을 미리 골라 두어야 나중에 고치지 않는가?

#3동작 예시

#4동작 과정

  1. 범위를 정한다IPv4 CIDR 블록으로 VPC 안에서 쓸 IP 주소 범위를 정한다. subnet도 이 범위 안에서만 쪼갤 수 있다.
  2. DNS를 켠다DNS support를 켜면 VPC 안의 이름 조회가 되고, DNS hostnames까지 켜면 그 subnet에서 만들어진 EC2 인스턴스가 공개 DNS 이름을 받는다.

  4. 확인해 볼 것VPC의 DNS 정보에서 DNS support와 DNS hostnames가 켜져 있는지 확인한다.

기본 VPC 와 기본 서브넷

기본 VPC는 AWS 계정을 처음 만들 때 해당 리전에 자동으로 만들어져 바로 쓸 수 있게 주는 VPC이고, 기본 서브넷은 그 안에 프리빗 라우팅 테이블과 라우팅 규칙이 미리 갖춰져 있어 IP 대역을 나눈 기본 영역을 가리킨다.

먼저 알아야 할 것 01-03

#1문제 상황

VPC를 하나도 안 만들고 인스턴스를 띄우면 어디에 들어가는지 모른다. 사실 AWS는 계정을 만들 때 기본 네트워크를 이미 만들어 둔 상태다.

default VPC는 각 가용 영역에 public subnet, internet gateway, DNS 해석 켜기를 이미 갖춰 둔 VPC여서 곧바로 EC2 인스턴스를 올릴 수 있다. 여기 붙은 default subnet과 default route table, default security group, default network ACL이 기본 구성을 이룬다.

#2핵심 질문

VPC를 만들지 않고 처음 테스트하려면 어디에 인스턴스를 올리는가?

#3동작 예시

새 AWS 계정으로 EC2 인스턴스를 만들면 subnet 목록에 이미 채워진 default subnet이 보인다. 거기에 그대로 올리면 별도 설정 없이 인터넷 통신이 된다.

#4동작 과정

  1. 자동으로 온다계정 만들 때 해당 리전에 default VPC가 생긴다. subnet·internet gateway·DNS 해석이 이미 설정돼 있다.
  2. 문법을 먼저 익힌다기본 구성은 EC2 인스턴스뿐 아니라 Elastic Load Balancing, Amazon RDS 같은 서비스에도 그대로 쓴다.
  3. 나중에 바꾼다다 쓴 뒤에는 subnet을 더 만들거나 설정을 고쳐 실제 환경에 맞춘다. 시험 삼이 만든 default VPC는 결국 지운다.
  4. 확인해 볼 것VPC 목록에서 default로 표시된 VPC를 고르고 그 안의 subnet과 internet gateway가 미리 채워져 있는지 본다.

  4. 확인해 볼 것삭제 시 서브넷 목록에 비어 있는 서브넷이 남아 있지 않은지 먼저 확인한다.

VPC CIDR 블록 — VPC 전체의 주소 범위

VPC 의 CIDR 블록은 그 VPC 안에 만들 수 있는 모든 IP 주소의 시작 범위(예: 10.0.0.0/16)로, VPC 를 만들 때 지정하고 나중에 최대 5개까지 추가할 수 있습니다.

먼저 알아야 할 것 01-03

#1문제 상황

VPC를 만들면 인스턴스에 붙일 사설 주소가 몇 개 필요한지부터 정해야 한다. 어떤 주소 범위를 쓸지 미리 정하지 않으면 서브넷을 나눌 때마다 범위가 겹친다.

VPC CIDR 블록은 그 VPC에서 쓸 수 있는 모든 IP 주소의 시작 범위를 정한다. CIDR notation은 10.0.0.0/16처럼 주소와 접두사 길이로 범위를 적는 표기법이고, private IPv4 address는 사설망에서 쓰는 비공개 주소다.

VPC를 만들 때 하나의 IPv4 CIDR 블록을 필수로 지정하고, 사후에 secondary CIDR block를 최대 5개까지 더 붙일 수 있다. 지정하는 범위는 /16에서 /28 사이여야 한다.

#2핵심 질문

#3동작 예시

어플리케이션용 VPC를 만들면서 주소 범위를 10.0.0.0/16으로 정한다. 그러면 이 VPC 아래 모든 서브넷의 주소가 이 범위 안에서만 나뉜다.

이후 다른 환경의 주소와 겹치지 않게 하려고 10.1.0.0/16을 secondary CIDR block로 추가한다.

#4동작 과정

  1. 범위를 정한다VPC를 만들 때 primary CIDR block로 첫 주소 범위를 지정한다. AWS는 RFC 1918에 적힌 private IPv4 address 범위를 고를 것을 권한다.
  2. 범위를 더 붙인다필요하면 secondary CIDR block로 IPv4 CIDR 블록을 최대 5개까지 추가한다. 추가할 때는 기존 범위와 겹치지 않아야 한다.
  3. 확인해 볼 것VPC 콘솔의 CIDR 블록 항목에서 지정한 범위와 추가된 범위가 어떻게 보이는지 확인한다.

#4동작 과정

  2. 남는 주소를 센다usable IP addresses는 실제로 인스턴스에 붙일 수 있는 주소 수다. AWS reserves five IP addresses, 즉 주소 다섯 개를 미리 빼 두므로 available IP addresses가 줄어든다.
  3. 확인해 볼 것서브enet 목록에서 해당 서브넷의 CIDR 블록과 사용 가능한 주소 수가 어떻게 표시되는지 확인한다.

IPv4 와 IPv6 의 차이 — 무엇을 선택하고 무엇이 다른가

IPv4 는 32비트 주소로 유한한 개수만 있어 부족해지는 반면 IPv6 는 128비트 주소로 사실상 무한에 가깝고, IPv6 VPC 에는 서브넷마다 /64 고정 크기를 사용한다는 등 두 체계의 규칙이 다릅니다.

먼저 알아야 할 것 02-01

#1문제 상황

IPv4만 쓰면 주소가 32비트라 개수가 유한해 언젠가 모자란다. IPv6는 128비트라 사실상 무한에 가깝지만, VPC 크기와 서브넷 크기를 정하는 규칙이 IPv4와 다르다.

dual-stack는 한 환경에서 IPv4와 IPv6를 함께 쓰는 구성이고, IPv6 GUA address는 외부에서 라우팅되는 IPv6 주소다(→ 02-01).

#2핵심 질문

VPC와 서브넷의 주소 체계를 IPv4로 갈지 IPv6로 갈지 무엇이 다른가?

#3동작 예시

새 VPC의 범위를 정한다. IPv4면 /16~/28 중 하나를 고르고, IPv6면 /44~/60을 4씩 증가시키며 고른다.

서브넷 크기도 달라진다. IPv4는 /16~/28, IPv6는 /44~/64다.

#4동작 과정

  1. 체계를 고른다IPv4는 VPC당 최대 5개 CIDR을 /16~/28 범위에서 고르고, IPv6는 /44~/60을 4 단위 간격으로 고른다. 어느 쪽이든 할당량을 조정할 수 있다.
  2. 서브넷 크기를 정한다subnet size는 IPv4에서 /16~/28, IPv6에서 /44~/64를 4 단위 간격으로 고른다.
  3. 주소를 나눠 쓴다dual-stack로 두 체계를 함께 쓰면 AWS가 주는 IPv6 CIDR block를 쓸 수 있고, 직접 가져온 범위는 BYOIP 형태로 쓴다.
  4. 확인해 볼 것VPC 설정에서 연결된 IPv4 CIDR 블록과 IPv6 CIDR 블록이 각각 몇 개로 보이는지 확인한다.

  1. 범위를 붙인다VPC와 각 서브넷에 Amazon-provided IPv6 CIDR block를 연결한다. 직접 가진 범위는 BYOIP로 가져올 수 있고, 서브넷 쪽 값은 subnet IPv6 CIDR로 관리한다.
  2. 경로를 연다공개 서브넷은 모든 IPv6 트래픽을 인터넷 게이트웨이로 보내는 라우트를 만든다. 프라이빗 서브넷은 egress-only internet gateway로 나가는 라우트를 만든다.

같은 서브넷에서도 어떤 인스턴스는 인터넷에 노출되어야 하고 어떤 인스턴스는 노출되면 안 된다. IP 주소(인터넷에서 각 장소를 찾게 하는 숫자 번호) 설정을 안 하면 나중에 인스턴스마다 따로 처리해야 한다.

이 스위치는 기본 동작을 정한다. 켜 두면 서브넷에서 새로 만들어지는 인스턴스가 자동으로 공개 IP 주소를 받는다.

#2핵심 질문

공개 IP 주소를 인스턴스마다 손대지 않고 자동으로 받게 하려면 어떻게 하나?

#3동작 예시

공개 서브넷의 설정을 켜 둔 상태에서 인스턴스를 새로 만든다. 인스턴스의 network interface에 자동 배정된 public IPv4 address가 붙어 외부에서 바로 접근된다.

설정을 끄고 만든 인스턴스에는 공개 주소가 붙지 않는다.

#4동작 과정

  1. 스위치를 정한다서브넷에서 auto-assign public IPv4 address 기능을 켜거나 끈다. 이 설정은 MapPublicIpOnLaunch 속성으로 관리되며 VPC 콘솔에서 고칠 수 있다.
  2. 주소를 배정받는다켜 둔 서브넷에서 만들어진 network interface에는 공개 IPv4 주소가 자동으로 붙는다. 예외로 EC2 실행 위저드에서 만든 비기본 서브넷은 이 속성이 켜진 채로 만들어진다.
  3. IPv6 속성도 본다IPv6 addressing 속성은 기본이 꺼짐이다. 켜면 서브넷에 IPv6 CIDR 블록이 있을 때 인스턴스가 network interface에서 IPv6 주소를 받는다.
  4. 확인해 볼 것서브넷 상세에서 공개 IPv4 자동 배정 항목이 켜짐인지 꺼짐인지 확인한다.

Amazon DNS 와 Route 53 Resolver

VPC 안에서 인스턴스가 다른 리소스를 이름으로 찾을 수 있게 해 주는 Amazon Provided DNS 와, 온프레미스와 여러 VPC 사이의 도메인 이름을 양방향으로 조회·전달하는 Route 53 Resolver 라는 DNS 서비스의 두 가지를 아우르는 DNS 구성 요소.

먼저 알아야 할 것 01-04

#1문제 상황

VPC 안의 인스턴스는 사설 IP 주소로 서로 통신한다. 그런데 IP 주소를 그대로 쓰면 주소를 바꿀 때마다 설정을 고쳐야 한다. 사람이 읽고 외울 수 있는 domain name 으로 리소스를 찾게 해 주는 DNS server 가 필요하다.

Amazon DNS 와 Route 53 Resolver 는 리전의 각 가용 영역에 내장된 DNS 서버다. 인스턴스는 별도 서버를 세우지 않고 사설 이름으로 다른 리소스를 찾을 수 있다.

#2핵심 질문

VPC 안에서 이름으로 리소스를 찾으려면 어디에 물어봐야 하는가?

#3동작 예시

앱 서버가_orders 라는 이름으로 데이터베이스에 접속한다. 인스턴스는 VPC 안의 Amazon DNS 서버에 이 이름을 물어보고 사설 IP 주소를 받아 접속한다.

외부 공개 주소는 그대로 노출되지 않고 사설 이름만 쓰게 된다.

#4동작 과정

  1. 물어본다인스턴스가 등록된 도메인 이름을 DNS server 로 보낸다. Amazon DNS server 는 VPC CIDR 기본 프라이빗 IPv4 범위에 2를 더한 주소와 169.254.169.253 에 있다.
  2. 프라이빗 이름으로 답한다private DNS 는 VPC 안에서만 해석되는 이름이다. 같은 이름이 외부 공개 DNS hostnames 로도 쓰이는지 03-02 에서 정한다.
  3. resolver endpoint 로 넓힌다온프레미스와의 질의를 주고받으려면 VPC 밖으로 나가는 resolver endpoint 를 만든다. 다른 리전과 공유되는 프라이빗 영역(private hosted zone)의 이름도 여기서 조회된다.
  4. 확인해 볼 것EC2 인스턴스에 접속해 VPC CIDR 기본 주소에 2를 더한 값으로 DNS 서버가 배정되어 있는지 본다.

#1문제 상황

VPC를 만들면 이름 조회가 기본값으로 맞춰진다. 하지만 프라이빗 이름을 쓰고 싶거나, 자기 계정의 DNS 서버로 바꾸고 싶을 수 있다.

VPC DNS 속성(DNS attributes)은 이런 선택을 VPC마다 정한다. enableDnsSupport 와 enableDnsHostnames 를 켜고 끄면 그 VPC의 인스턴스가 어떤 이름 규칙을 따를지 달라진다.

#2핵심 질문

이 VPC의 인스턴스는 어떤 이름으로 어떻게 조회해야 하는가?

#3동작 예시

인스턴스에 부여된 사설 호스트 이름을 외부에서 DNS로 조회한다. enableDnsHostnames 를 꺼 둔 VPC라면 그 이름은 프라이빗 DNS hostnames 로만 남고 공개 이름으로는 나타나지 않는다.

#4동작 과정

  1. DNS server 주소를 정한다enableDnsSupport 를 켜면 VPC가 DNS server 주소를 자동 지정한다. 끄면 이 VPC는 Route 53 Resolver 기본 주소가 아니라 새 DHCP option sets 로 준 서버를 쓴다(→ 03-03).
  2. 이름 해석을 켜는지 정한다도메인 이름 해석 사용 여부를 정한다. 끄면 이름 조회로 다른 곳에 가지 못한다.
  3. 프라이빗 이름을 노출한다enableDnsHostnames 를 켜면 인스턴스의 public DNS hostnames 대신 private DNS hostnames 를 다른 리소스가 참조할 수 있다.
  4. 확인해 볼 것VPC 콘솔의 DNS attributes 항목에서 세 스위치의 켜짐 상태를 확인한다.

Managed prefix list — AWS 가 관리하는 주소 목록

IP 주소 범위를 하나의 목록 이름으로 묶어 보안 그룹 규칙이나 라우트 테이블에서 참조하게 해 주는 기능으로, AWS 서비스의 주소 범위는 AWS 가 직접 관리하는 managed 유형으로 제공된다.

먼저 알아야 할 것 03-01

#1문제 상황

보안 그룹 규칙에 주소 범위를 하나씩 적으면 같은 포트와 프로토콜을 다루는 규칙이 자꾸 늘어난다. 다른 CIDR 블록 하나가 늘 때마다 규칙도 고쳐야 한다.

prefix list 는 자주 쓰는 IP 주소 범위를 한 묶음으로 두고 이름으로 참조하게 한다. 이 중 AWS 서비스의 범위를 AWS가 관리하는 유형이 AWS-managed prefix list 다.

#2핵심 질문

여러 주소 범위를 규칙 한 줄로 어떻게 묶는가?

#3동작 예시

같은 포트와 프로토콜을 쓰면서 CIDR 블록만 다른 규칙 세 개가 있다. 이를 AWS-managed prefix list 하나를 참조하는 규칙 한 개로 합친다.

#4동작 과정

  1. 묶음을 정한다prefix list 에 담을 IP 주소 범위를 정하고 이름과 max entries 를 정해 만든다. max entries 는 목록이 가질 수 있는 범위 수의 상한이다.
  2. 규칙에서 참조한다보안 그룹 규칙과 라우트에서 주소 대신 목록 이름을 넣는다. 다른 계정에서는 Resource Access Manager 를 거쳐 reference prefix list 로 쓸 수 있다.
  3. 확인해 볼 것보안 그룹 인바운드 규칙에서 출발지 항목이 CIDR 블록이 아니라 prefix list 이름으로 적혀 있는지 확인한다.

#1문제 상황

내 VPC에서 나가는 트래픽이 AWS 서비스 주소인지 확인해야 한다. 서비스마다 어디에 붙어 있는지 매번 따로 알기 어렵다.

AWS IP address ranges 는 AWS가 배포하는 공개 목록이다. ip-ranges.json 을 내려받아 라우팅 테이블이나 보안 그룹의 허용 대상 주소로 쓴다.

#2핵심 질문

AWS 가 어느 서비스와 어느 리전에서 어느 주소 범위를 쓰는지는 어떻게 아는가?

#3동작 예시

어떤 AWS 서비스로 나가는 트래픽만 허용하려 한다. ip-ranges.json 에서 service 와 region 을 골라 주소 범위를 뽑아 라우트에 넣는다.

#4동작 과정

  1. 내려받는다ip-ranges.json 을 받아 service 와 region 기준으로 address ranges 를 뽑는다. 일부 서비스의 범위는 AWS-managed prefix list 로도 공개된다.
  2. 필터에 쓴다뽑은 범위를 egress control 과 라우팅 테이블의 허용 대상 주소로 넣는다. BYOIP 로bring한 주소는 이 파일에 들어 있지 않다.
  3. 변화를 좇는다subscribe to notifications 로 새 범위가 추가될 때 알림을 받아 목록을 다시 받는다.
  4. 확인해 볼 것json 안에서 원하는 service 항목의 region 과 ip_prefix 가 들어 있는 자리를 찾아 본다.

Internet gateway — VPC 와 인터넷 사이의 문

VPC 서브넷에서 외부 인터넷으로 나가고 외부에서 들어오는 트래픽을 중개하는, VPC 에 붙는 가상의 라우팅 장치다.

먼저 알아야 할 것 01-03

#1문제 상황

VPC 안의 인스턴스는 기본적으로 외부와 통신할 길이 없다(→ 01-03). 그래서 외부에서 어떤 자원을 붙잡을지, 그 자원이 어디로 나가는지 정할 곳이 필요하다.

Internet gateway는 VPC에 붙는 가상의 라우팅 장치다. VPC 안에서 라우팅 테이블의 목적지로 internet gateway를 지목하면 그쪽으로 트래픽이 나가고, internet gateway route를 서브넷의 라우팅 테이블에 두면 그 public subnet의 인스턴스가 외부와 통신한다(→ 05-02). IPv4에서는 network address translation도 이 장치가 맡는다.

#2핵심 질문

VPC 안의 자원이 외부 인터넷과 통신할 길을 어떻게 만들까?

#3동작 예시

내 컴퓨터에서 VPC 안의 EC2 인스턴스에 접속한다. 그 인스턴스의 서브넷은 public subnet이고 공개 IPv4 주소를 갖고 있다.

인스턴스의 보안 그룹이 22번 포트에서 내 주소를 허용하니, internet gateway를 거쳐 세션이 열린다. 이 장치는 대역폭 제한을 만들지 않고 IPv4와 IPv6를 함께 다룬다.

#4동작 과정

  1. 연결한다VPC에 internet gateway를 붙인다. CreateInternetGateway로 만든 뒤 VPC에 연결하고, 연결되면 delete internet gateway가 뜬다.
  2. 길을 만든다public subnet의 라우팅 테이블에 internet gateway로 가는 internet gateway route를 추가한다. 이제 해당 서브넷에서 외부로 나가는 트래픽이 이 장치를 지난다.
  3. 떼어낸다쓰지 않게 되면 VPC에서 internet gateway를 분리한다. 분리 후에는 이 경로가 사라진다.
  4. 확인해 볼 것VPC 콘솔의 라우팅 테이블에서 0.0.0.0/0 목적지가 internet gateway로 되어 있는지 확인한다.

Elastic IP 주소 — 인스턴스에 붙이는 고정 공개 주소

인스턴스를 중지·재시작해도 변하지 않는 고정 공개 IPv4 주소로, 계정 안에서 직접 반납하거나 다른 리소스에 다시 붙일 수 있다.

먼저 알아야 할 것 04-01

#1문제 상황

인스턴스에 자동으로 붙는 공개 IPv4 주소는 인스턴스를 중지하고 다시 시작하면 바뀐다(→ 02-06). 외부에 서비스 주소를 알려 둔 곳에서는 주소가 바뀔 때마다 연결을 고쳐 줘야 한다.

Elastic IP address는 계정 안에서 미리 확보해 두고 인스턴스에 붙여 두는 고정 공개 IPv4 주소다. 인스턴스가 바뀌어도 주소는 그대로 남는다. BYOIPv4를 쓰면 직접 가져온 주소를 함께 쓸 수도 있다.

#2핵심 질문

인스턴스를 바꿔도 변하지 않는 공개 주소를 어떻게 유지할까?

#3동작 예시

운영 중인 웹 서버가 있다. 유지보수로 인스턴스를 새 것으로 바꿔야 한다.

Elastic IP address를 기존 인스턴스의 elastic network interface에 붙여 둔 상태였으므로, 인스턴스만 교체해 AssociateAddress를 다시 걸면 외부에 알려 준 주소로 그대로 서비스가 이어진다.

#4동작 과정

  1. 확보한다AllocateAddress로 계정에서 Elastic IP address 하나를 할당받는다. 이 주소는 명시적으로 반납하기 전까지 계정에 남는다.
  2. 붙인다AssociateAddress로 인스턴스나 elastic network interface에 연결한다. Elastic IP address는 인스턴스 자체가 아니라 elastic network interface의 속성이라, 한 번에 다른 인스턴스로 옮길 수 있다.
  3. 확인해 볼 것EC2 콘솔에서 해당 인스턴스의 주소가 Elastic IP로 표시되고, 인스턴스를 재시작해도 같은 주소가 유지되는지 본다.

NAT gateway — 프라이빗 서브넷이 나가는 길

프라이빗 서브넷의 인스턴스가 인터넷으로 나갈 때 그 주소를 대신 translate 해 주는, AWS 가 관리하는 단일 방향 통신 장치다.

먼저 알아야 할 것 04-02

#1문제 상황

public subnet을 internet gateway에 직접 연결하면 외부에서 그 인스턴스로 언제든 연결을 시작할 수 있다(→ 04-01). 인터넷에서 나가는 데만 쓸 인스턴스에는 그 연결을 막고 싶지만, 응답을 받아야 하니 아웃바운드 길은 남겨 둬야 한다.

NAT gateway는 AWS가 관리하는 단일 방향 장치다. 프라이빗 서브넷이 internet gateway 대신 이 장치를 거쳐 나갈 수 있게 해 주면서 외부에서 들어오는 연결은 전부 막는다. IPv6 트래픽에서는 NAT64를 수행해 IPv4 자원과 통신하게 할 수도 있다.

#2핵심 질문

프라이빗 서브넷이 외부로만 나갈 수 있는 길을 어떻게 만들까?

#3동작 예시

프라이빗 서브넷의 서버가 외부 API를 호출한다. 서브넷에는 internet gateway로 가는 route가 없어 직접 나갈 수 없다.

대신 NAT gateway로 가는 route를 둔다. NAT gateway는 Elastic IP address를 붙인 채 서브넷 경로에 놓이고, 그 주소를 대신 달아나갔다 돌아온 응답만 서버로 넘겨 준다.

#4동작 과정

  1. 세운다CreateNatGateway로 NAT gateway를 만들고 서브넷에 Elastic IP address를 지정한다. 서브넷은 private subnet이 public subnet이어야 한다(→ 05-01).
  2. 길을 건다프라이빗 서브넷의 라우팅 테이블에서 internet gateway 대신 NAT gateway를 목적지로 둔다. 이제 나가는 트래픽만 이 장치를 지난다.
  3. 넓힌다NAT gateway는 하나만 두면 그 가용 영역 장애 시 다른 영역의 통신이 끊긴다. per-AZ NAT gateway로 가용 영역마다 두고 같은 영역의 NAT gateway로 가게 하거나, 여러 영역을 묶는 regional NAT gateway를 쓸 수 있다.
  4. 확인해 볼 것NAT gateway 콘솔에서 상태가 available인지, 프라이빗 서브넷의 라우팅 테이블에서 0.0.0.0/0이 NAT gateway를 가리키는지 확인한다.

NAT gateway 의 쓰임과 비용 — 언제 하나를 더 세울까

아웃바운드를 허용하면서 외부에서 들어오는 연결은 막는 구조를 유지하려면 가용 영역마다 NAT gateway 를 두어야 하므로, 필요한 통신 방향과 아웃바운드 요구량에 따라 배치 수와 비용이 결정된다.

먼저 알아야 할 것 04-03

#1문제 상황

NAT gateway를 하나만 세우면 그것이 속한 가용 영역이 멈출 때 다른 영역의 프라이빗 서브넷은 인터넷을 잃는다(→ 04-03). 그런데 가용 영역마다 하나씩 세우면 그만큼 요금이 붙는다.

NAT gateway는 무엇을 얼마나 통과시키느냐에 따라 요금이 정해진다. 그래서 아웃바운드를 어디까지 허용할지, 어느 방향의 통신이 필요한지에 따라 배치 수가 갈린다.

#2핵심 질문

NAT gateway를 몇 개 어디에 세워야 통신과 비용을 함께 맞출까?

#3동작 예시

서로 다른 가용 영역에 프라이빗 서브넷이 있고, 모든 서브넷이 같은 외부 서비스로 나간다.

공통으로 쓰는 NAT gateway가 든 가용 영역 장애로 두 번째 영역의 아웃바운드가 전부 막힌다. 각 가용 영역에 NAT gateway를 하나씩 두고 같은 영역의 인스턴스가 같은 영역의 NAT gateway로 가게 하자.

#4동작 과정

  1. 쓰임을 정한다NAT gateway use cases 로 방향을 고른다. 프라이빗 서브넷의 아웃바운드만 허용하거나, 허용 목록에 있는 주소만 열고 싶으면 해당 시나리오를 고른다.
  2. 수를 정한다장애에 대응하려면 가용 영역마다 하나씩 둔다. 대신 한 영역 안의 여러 영역을 묶는 regional NAT gateway 하나로 아웃바운드 요구량을 모을 수도 있다.
  3. 요금을 살피다NAT gateway pricing 은 NAT gateway 개수와 사용 시간, 그리고 보낸 데이터 양에 data processing charge 가 붙는 구조다. 가용 영역이 다른 NAT gateway를 지나는 traffic 은 cross-AZ data transfer 로 따로 계산된다.
  4. 확인해 볼 것NAT gateway 콘솔에서 만든 게이트웨이 수와 어느 가용 영역에 있는지, 각 프라이빗 서브넷의 라우팅 테이블이 어디를 가리키는지 확인한다.

Egress-only internet gateway — 나가는 것만 허용하는 문

IPv6 주소가 있는 서브넷이 외부로 나갈 때만 경로를 제공해, 외부에서 인바운드로 들어오는 연결은 전부 차단하는 게이트웨이다.

먼저 알아야 할 것 04-01

#1문제 상황

IPv6 주소는 사실상 무한하므로 프라이빗 서브넷의 IPv6 주소까지 외부에 그대로 노출할 이유가 없다(→ 02-03). 그런데 응답을 받아야 하는 자원은 나가게 두고 들어오는 연결은 막아야 한다.

Egress-only internet gateway는 IPv6 트래픽에만 쓰이는 게이트웨이다. 서브넷에 IPv6 outbound 경로만 열어 주면서 internet gateway처럼 외부 연결을 받아들이는 일은 하지 않는다.

#2핵심 질문

IPv6 서브넷에 나가는 길만 어떻게 열어 줄까?

#3동작 예시

IPv6 주소만 있는 프라이빗 서브넷의 서버가 외부 소프트웨어 저장소를 접촉한다.

서브넷의 라우팅 테이블에 egress-only internet gateway를 목적지로 둔 route가 있어 나가는 요청은 닿는다. 외부에서 이 서버로 직접 연결을 시작하려 하면 차단된다.

#4동작 과정

  1. 만든다VPC에 egress-only internet gateway를 추가한다. 이 구성 요소는 가로로 확장되고 중복된 구조라 ipv6 트래픽만 다룬다.
  2. 길을 연다IPv6 서브넷의 라우팅 테이블에서 외부로 향하는 목적지를 이 게이트웨이로 지정한다. 이제 서브넷의 outbound traffic 만 외부로 나간다.
  3. IPv4 는 다른 길로IPv4 에서 나가는 것만 허용하려면 이 장치가 아니라 NAT gateway 를 쓴다(→ 04-03). internet gateway 와 달리 외부에서 먼저 들어오는 연결을 받아 주지 않는다.
  4. 확인해 볼 것해당 서브넷의 라우팅 테이블에 ::/0 목적지가 egress-only internet gateway를 가리키는 항목이 있는지 확인한다.

NAT device 비교 — NAT gateway 와 NAT instance

프라이빗 서브넷의 아웃바운드를 처리하는 두 방식인, AWS 관리형 NAT gateway 와 사용자가 직접 인스턴스로 구성한 NAT instance 를 관리·성능·비용·고가용성 측면에서 비교한다.

먼저 알아야 할 것 04-03

#1문제 상황

프라이빗 서브넷의 아웃바운드를 처리하는 방법은 둘이다. AWS가 맡아 주는 NAT gateway를 쓰거나, 직접 EC2 인스턴스를 세워 NAT 동작을 시키는 NAT instance를 쓴다(→ 04-03).

어느 쪽이 나은지는 유지보수 부담, 대역폭, 장애 대응, 요금으로 갈린다. 고를 때 무엇을 비교해야 하는지 알아야 한다.

#2핵심 질문

프라이빗 서브넷의 아웃바운드를 AWS가 맡게 할까 직접 운영할까?

#3동작 예시

장애가 잦은 서비스에서 프라이빗 서브넷을 나가는 경로를 새로 잡는다.

NAT gateway를 고르면 가용 영역마다 중복 구성으로 만들어 장애 시 자동으로 넘어가고, 유지보수는 AWS가 한다. NAT instance를 고르면 같은 처리를 직접 하고 운영체제 패치까지 맡아야 한다.

#4동작 과정

  1. 구분한다NAT device 는 프라이빗 서브넷의 아웃바운드를 대신 처리하는 어느 쪽 장치인지를 가리키는 말이다. AWS가 관리하는 managed NAT gateway와, 인스턴스에 NAT 설정을 직접 한 self-managed NAT instance로 나뉜다.
  2. 고장 난리를 본다NAT gateway는 가용 영역 안에서 중복 구현이라 자체 가용성이 높다. NAT instance는 failover를 스크립트로 직접 관리해야 한다.
  3. 속도와 손을 본다NAT gateway는 최대 100 Gbps로 NAT 트래픽에 맞춰 최적화돼 있고 유지보수는 AWS 몫이다. NAT instance는 인스턴스 타입 대역폭에 묶이고 패치와 운영을 사용자가 한다.
  4. 확인해 볼 것VPC 콘솔에서 프라이빗 서브넷의 라우팅 테이블이 NAT gateway를 가리키는지, EC2 목록에 NAT 용 인스턴스가 남아 있지 않은지 비교해 본다.

먼저 알아야 할 것 02-02

#1문제 상황

VPC 하나에는 사설 IP 주소가 아주 큰 덩어리로 들어 있다(→ 02-01). 이를 쪼개지 않으면 모든 리소스가 한 가용 영역에 몰리고 가용 영역 하나가 죽으면 함께 멈춘다.

CreateSubnet은 VPC CIDR 블록에서 구간을 하나 잘라 subnet을 만드는 동작이다. 만들어진 subnet은 subnet resides in a single Availability Zone, 즉 가용 영역 하나에만 앉는다.

#2핵심 질문

VPC의 주소 범위를 리소스마다 나눠 배치하려면 어떻게 해야 할까?

#3동작 예시

VPC 콘솔에서 서브nets 화면을 열고 Create subnet을 누른다. 이름과 CIDR 블록을 적은 뒤 가용 영역을 하나 고르면 서브넷이 그 영역 안에 만들어진다.

#4동작 과정

  1. 범위를 고른다VPC CIDR 블록에서 서브넷에 쓸 구간을 CIDR로 정한다(→ 02-02). IPv6 CIDR 블록이 있으면 서브넷에 추가로 지정할 수 있다.
  2. 영역을 고른다subnet이 앉을 가용 영역을 하나 지정한다. 한 subnet은 한 가용 영역에만 들어가므로 리소스를 여러 영역에 나누려면 subnet을 여러 개 만든다.
  3. 연결을 정한다만든 subnet에는 route table이 붙는다. 그 길에 따라 internet gateway로 나가는 public subnet과, NAT gateway로 나가는 private subnet이 갈린다(→ 05-02).
  4. 확인해 볼 것서브nets 목록에서 방금 만든 서브넷의 Available Zone 열에 가용 영역이 하나 적혀 있는지 확인한다.

라우팅 테이블의 개념 — 목적지마다 어디로 보내는지

서브넷 밖으로 나가는 트래픽이 목적지 주소에 따라 어느 경로(다음 홉)로 전달될지를 규칙(라우트) 목록으로 정해 둔 표를 말하며, 한 서브넷은 하나의 라우팅 테이블에 연결된다.

먼저 알아야 할 것 05-01

#1문제 상황

서브넷(→ 05-01)만으로는 인스턴스가 밖으로 나가는 방법을 알 수 없다. 목적지가 어디든 같은 곳으로 보내면 되지만, 그것만으로는 원하는 서비스에 닿지 못한다.

route table은 이 판단을 맡는다. 한 줄이 destination과 target으로 이루어져 있고, 직접 연결하지 않은 서브넷은 main route table이 대신 처리한다.

#2핵심 질문

서브넷 밖으로 나가는 트래픽을 목적지마다 어디로 보낼까?

#3동작 예시

public subnet의 인스턴스가 외부 API를 호출한다. subnet route table의 0.0.0.0/0 목적지가 internet gateway를 가리키므로 요청이 그쪽으로 나간다.

#4동작 과정

  1. 목적지를 읽는다route table은 destination, 즉 어디로 갈지 정한 IP 주소 범위로 행을 나눈다.
  2. 다음 홉을 고른다각 행의 target은 그 트래픽을 넘길 gateway나 network interface 같은 연결 지점이다. local route는 VPC 내부 통신을 위한 기본 경로로 IPv4와 IPv6에 각각 있다.
  3. 서브넷에 붙인다route table association이 서브넷과의 연결이며, 붙은 것이 subnet route table이다. 이 연결이 없는 서브넷은 main route table을 쓴다.
  4. 확인해 볼 것서브넷의 Details 탭에서 Route table 항목을 열어 어떤 라우팅 테이블이 붙어 있는지 확인한다.

먼저 알아야 할 것 05-02

#1문제 상황

라우팅 테이블이 없으면 서브넷은 VPC 안에서의 통신만 가능하다. 외부로 나가고 받아들이는 길을 새로 만들어야 그 길이 열린다.

CreateRouteTable과 CreateRoute로 표를 만들고 채운다. 만들어진 표는 어떤 서브넷에 붙였는지에 따라 효력이 생긴다.

#2핵심 질문

새로운 길이 필요한 라우팅 테이블을 만들고 서브넷에 적용하려면 어떻게 해야 할까?

#3동작 예시

운영 팀이 private subnet에 인터넷 아웃바운드를 연다. 라우팅 테이블을 새로 만들고 internet gateway를 가리키는 기본 라우트를 넣은 뒤 해당 서브넷에 연결한다.

#4동작 과정

  1. 표를 만든다CreateRouteTable을 호출하면 local route target을 가진 VPC 내부 통신용 local route가 들어 있는 새 표가 생긴다.
  2. 길을 넣는다CreateRoute로 목적지 CIDR와 target을 적어 route를 추가한다. 기존 목적지의 경로를 바꿀 때는 ReplaceRoute로 교체한다. VPN 같은 외부 연결이 붙어 있으면 propagated route가 자동으로 들어올 수 있다.
  3. 서브넷에 붙인다associate route table로 서브넷과 연결한다. 한 표는 여러 서브넷에 붙지만 한 서브넷에는 한 표만 붙는다. 연결을 해제하면 그 서브넷은 다시 main route table을 쓴다.
  4. 확인해 볼 것라우팅 테이블의 Routes 탭에서 local 항목과 내가 추가한 목적지가 함께 보이는지 확인한다.

먼저 알아야 할 것 05-03

#1문제 상황

한 표에 0.0.0.0/0과 10.10.2.0/24처럼 범위가 겹치는 route가 들어간다. 어느 쪽으로 실제 트래픽이 갈지 알려 주는 규칙이 없다면 결과를 예측할 수 없다.

이 판단 규칙이 route priority이며, VPC는 longest prefix match를 적용한다. 같은 접두사 길이일 때는 route priority 목록으로 넘어간다.

#2핵심 질문

겹치는 목적지 주소가 많을 때 어느 route가 이기는가?

#3동작 예시

표에 0.0.0.0/0 internet gateway와 10.10.2.0/24 사내망 경로가 함께 있다. 사내 주소로 가는 패킷은 더 구체적인 10.10.2.0/24 쪽으로 나간다.

#4동작 과정

  1. 접두사 길이를 본다longest prefix match가 가장 긴 접두사의 route를 먼저 고른다. 10.10.2.15/32가 10.10.2.0/24보다 앞선다.
  2. prefix list route를 살핀다prefix list는 주소 묶음을 목적지로 삼는 route로, 같은 접두사를 쓰는 일반 route보다 먼저 적용된다.
  3. 나머지를 순서대로 본다겹침이 남으면 static route가 propagated route보다 앞선다. propagated route는 VPN static route보다, Direct Connect BGP route 같은 동적 route보다 앞선다.
  4. 확인해 볼 것같은 목적지를 가리키는 행이 몇 개 있는지 Routes 탭에서 세어 본다.

게이트웨이 route table 과 main route table 교체

인터넷 게이트웨이를 통해 들어온 트래픽이 특정 라우팅 테이블(게이트웨이 route table)을 쓰도록 지정할 수 있고, 그 서브넷의 main route table을 다른 라우팅 테이블로 교체할 수 있다는 두 가지 방법을 설명한다.

먼저 알아야 할 것 05-03

#1문제 상황

internet gateway로 들어온 트래픽(→ 04-01)은 VPC 안으로 들어오면 서브넷의 표를 따른다. 서브넷이 따로 지정한 표가 없으면 VPC의 기본 표인 main route table을 쓴다. 표가 하나뿐이면 곧바로 보안 장비로 돌리고 싶어도 그렇게 할 수 없다.

gateway route table을 붙이면 들어오는 경로를 따로 조종할 수 있다. 여기에는 트래픽을 Gateway Load Balancer endpoint이나 middlebox 장비로 넘길 수 있다.

#2핵심 질문

VPC로 들어오는 트래픽의 경로를 서브넷의 표와 따로 정할 수 있는가?

#3동작 예시

외부에서 들어오는 트래픽을 그대로 서비스가 아니라 보안 장비로 먼저 보낸다. 게이트웨이에 라우팅 테이블을 연결하고 목적지를 그 장비의 네트워크 인터페이스로 지정한다.

#4동작 과정

  1. 표를 만든다인터넷 게이트웨이나 virtual private gateway에 associate route table로 라우팅 테이블을 연결하면 gateway route table이 된다.
  2. 목적지를 정한다게이트웨이 표는 default local route, Gateway Load Balancer endpoint, middlebox 장비의 network interface를 대상으로 한 route를 담을 수 있다.
  3. main route table을 바꾼다replace the main route table로 해당 서브넷이 가리키는 기본 표를 다른 라우팅 테이블로 교체한다. 실제 subnet route table이 없을 때 쓰이는 기본값이다.
  4. 확인해 볼 것게이트웨이의 Routes 탭에서 게이트웨이에 붙은 표가 보이는지 확인한다.

VPC peering connection — 두 VPC 를 직접 잇기

같은 리전(또는 리전 간 지원 조합)의 두 VPC 를 내부망처럼 직접 연결해 서로의 사설 IP 로 통신하게 해주는 기능으로, 두 VPC 의 라우팅 테이블을 서로의 통신에 맞게 손봐야 한다.

먼저 알아야 할 것 05-04

#1문제 상황

VPC가 여러 개로 나뉘면(→ 01-01) 사설 IP로 서로 통신할 방법이 없다. 인터넷 게이트웨이(→ 04-01)로 나가면 트래픽이 외부에 노출된다.

VPC peering connection은 두 VPC를 게이트웨이 없이 내부망처럼 직접 잇는다. 계정과 리전이 달라도 연결하며 단일 장애 지점과 대역폭 병목이 없다.

#2핵심 질문

두 VPC의 사설 IP를 직접 왕복하게 어떻게 잇는가?

#3동작 예시

운영 계정의 VPC와 개발 계정의 VPC를 잇는다. CreateVpcPeeringConnection API로 연결 요청을 만들고 승인한다. 두 쪽에서 상대 VPC의 사설 대역으로 향하는 라우트가 붙어 표면은 하나의 네트워크처럼 동작한다.

#4동작 과정

  1. 연결을 만든다VPC peering connection을 요청하고 상대 계정이 승인한다. VPC가 같은 리전이어도, 서로 다른 계정이어도 가능하며 AWS Site-to-Site VPN은 필요 없다.
  2. 양쪽에 경로를 연다peering connection route를 양쪽 VPC의 route table(→ 05-02)에 각각 추가한다. 이 경로 없이는 연결이 있어도 트래픽이 오가지 않는다.
  3. 중계는 못 한다transitive peering은 지원되지 않아 A-B, B-C를 이으면 A와 C는 직접 연결해야 한다. 한쪽으로 몰아 쓰는 구성은 Transit Gateway(→ 06-02)를 쓴다.
  4. 확인해 볼 것VPC 콘솔의 Peering Connections 화면에서 연결 상태가 active인지 보고, 각 VPC 라우팅 테이블에 상대 VPC 대역의 경로가 있는지 본다.

Transit Gateway — 여러 VPC 와 온프레미스의 중앙 허브

여러 VPC 와 VPN 연결, Site-to-Site VPN 까지 하나의 허브 장비에 붙여 중앙 허브 한 대를 경유하는 경로로 묶는 기능으로, 연결된 곳들끼리 서로 통신하려면 허브와의 경로를 어트래픽 라우터에 등록해야 한다.

먼저 알아야 할 것 06-01

#1문제 상황

VPC가 늘면 VPC peering connection(→ 06-01)을 둘마다 따로 만들어 양쪽 라우팅 테이블을 손봐야 한다. 수십 개가 되면 관리가 불가능해진다.

Transit Gateway는 VPC 하나를 central router hub로 두고 그에 붙은 곳끼리만 통신하게 한다. VPN 연결이나 AWS Direct Connect도 같은 허브에 붙인다.

#2핵심 질문

VPC가 많은데 중앙 한 곳만 경유하게 어떻게 잇는가?

#3동작 예시

세 개의 VPC와 사설 datacenter를 Transit Gateway에 모두 붙인다. 각 VPC의 라우팅 테이블에는 허브로 향하는 경로 하나만 추가한다. 결과적으로 모든 곳이 허브를 거쳐 서로 통신한다.

#4동작 과정

  1. 허브를 만든다리전에 Transit Gateway를 하나 만든다. 이 장비가 연결된 모든 곳의 경로를 한곳에서 나눠주는 중앙 라우터다.
  2. 붙인다각 VPC와 VPN 연결, Direct Connect를 attachment로 허브에 연결한다. Direct Connect는 물리 회선 방식으로 사무실과 AWS 사이를 직접 잇는 연결이다.
  3. 경로를 등록한다연결된 곳끼리 통신하려면 각 VPC의 라우팅 테이블에 transit gateway route를 등록한다. 같은 attachment 두 곳끼리는 통신되지 않는다.
  4. 확인해 볼 것Transit Gateway 콘솔의 Attachments 화면에서 붙은 VPC 목록과 상태를 확인한다.

#2핵심 질문

전용 회선 없이 온프레미스와 VPC를 암호화된 경로로 어떻게 잇는가?

#3동작 예시

#4동작 과정

  1. 양쪽 끝을 세운다AWS에 virtual private gateway, 사내 장비에 customer gateway를 만들어 서로를 가리키게 한다. Site-to-Site VPN은 IPsec 터널을 두 개 열어 한쪽이 끊겨도 나머지로 넘어간다.
  2. 암호를 맞춘다같은 사전 공유 키와 암호 알고리즘을 양쪽에 동일하게 넣는다. 틀리면 터널이 올라오지 않는다.
  3. 경로를 정한다사내 장비에 VPN static route로 VPC CIDR(→ 02-01)을 알려 준다. AWS 쪽에 별도 라우트를 넣는 방법인 VPN BGP route도 있다.

VPC Route Server — BGP 로 경로를 자동 배분

BGP 라우팅 프로토콜을 써서 라우팅 테이블에 경로를 직접 손대지 않고 자동 배포·학습하게 해주는 VPC 안의 구성 요소로, 허브로 선택하면 여러 VPC 의 경로를 한 곳에서 나눠준다.

먼저 알아야 할 것 05-04

#1문제 상황

방화벽 같은 외부 장비가 자신을 상대로 삼는 경로(→ 05-06)는 장비 상태가 바뀔 때마다 라우팅 테이블을 손으로 고쳐야 한다. 이때 실수로 기본 경로까지 사라지면 통신이 끊긴다.

VPC Route Server는 BGP로 외부 장비와 경로를 주고받으며 VPC 라우팅 테이블과 인터넷 게이트웨이 route table(→ 05-05)을 자동으로 고친다. 이 방식을 dynamic routing이라 부른다.

#2핵심 질문

외부 장비의 경로 변화를 VPC 라우팅 테이블에 자동으로 반영하려면?

#3동작 예시

서로 다른 두 방화벽을 각 VPC의 route server endpoint에 peer로 등록한다. 한 장비의 장애를 VPC Route Server가 감지해 그 장비로 가는 경로를 남은 장비로 자동 전환한다. VPN 게이트웨이에 붙은 라우팅 테이블은 지원하지 않는다.

#4동작 과정

  1. 구성 요소를 둔다VPC 안에 Amazon VPC Route Server를 만들고 그 주소가 route server endpoint가 된다.
  2. 피어를 붙인다각 방화벽을 route server peer로 등록하고 BGP 세션을 올린다. 이 세션으로 경로가 오간다.
  3. 경로를 전파한다route propagation으로 학습한 경로를 VPC 라우팅 테이블과 인터넷 게이트웨이 라우팅 테이블에 밀어 넣는다. 서브넷 라우팅 테이블도 지원한다.
  4. 확인해 볼 것VPC 콘솔의 Route servers에서 peer 상태가 active인지 보고, 대상 라우팅 테이블에 새 경로가 생겼는지 본다.

먼저 알아야 할 것 06-03

#1문제 상황

프라이빗 서브넷(→ 04-03)에서 S3 같은 AWS 서비스로 가려면 NAT gateway를 거쳐 인터넷으로 나가야 한다. 내려가는 데이터가 밖으로 나가고, 경유 비용도 붙는다.

VPC endpoint를 만들면 해당 서비스로 가는 경로가 VPC 안에서 끝난다. 이 방식의 이름이 AWS PrivateLink이다.

#2핵심 질문

인터넷을 거치지 않고 AWS 서비스에 프라이빗으로 닿으려면?

#3동작 예시

S3용 gateway endpoint를 만든다. VPC의 DNS 서버 주소가 자동 지정되어 있어야 S3 도메인 이름이 이 경로로 풀린다. 앞 단계에서 만든 VPN(→ 06-03)과 VPC peering(→ 06-01) 사이에도 VPC endpoint를 두어 사설 통신만 남긴다.

#4동작 과정

  1. 엔드포인트를 만든다VPC 안에서 서비스별 VPC endpoint를 만든다. 지정한 서브넷에 elastic network interface가 생성되어 그 서비스로 들어가는 입구가 된다. gateway endpoint와 interface endpoint로 나뉜다.
  2. 경로를 붙인다gateway endpoint는 S3와 DynamoDB 용이고, interface endpoint는 그 밖의 서비스와 VPC endpoint service를 쓰는데 프라이빗 DNS 이름으로 연결된다.
  3. 허용 대상을 좁힌다VPC의 route table 대신 endpoint-specific prefix list로 대상을 정리할 수 있다. 내 서비스를 다른 계정에 노출하려면 endpoint service를 만든다.

#1문제 상황

#4동작 과정

  2. 서브넷을 공유한다owner가 서브넷을 골라 participant와 공유한다. participant는 공유된 서브넷에서 리소스를 만들고 지울 수 있다.
  3. 권한과 비용을 나눈다responsibilities and permissions 규칙으로 각 역할이 할 수 있는 동작을 정하고, billing and metering로 사용량과 요금을 계정별로 나눠 부과한다.

  2. 넘긴다Firehose 가 record 를 수집해 지정된 저장소로 전달한다. 여러 목적지에 나눠 보내는 것도 Firehose 안에서 정한다.
  3. 질의한다Amazon Athena 로 저장된 기록에 표준 SQL 을 돌린다. query flow log records 는 이 단계에서 쓰이는 질의 방식이다.
  4. 확인해 볼 것delivery stream 목록에서 VPC Flow Logs 로부터 들어오는 데이터가 정상적으로 흐르는지 본다.

7단계 7. 트래픽 관측 — 누가 무엇을 주고받았는지 기록한다

CloudWatch 로 VPC 의 서브넷·게이트웨이·VPC 전체 처리량 지표를 확인하고, Reachability Analyzer 로 두 리소스 사이를 지나는 경로와 각 구간의 상태를 시각화해 통신이 어디서 막혔는지 찾을 수 있다.

먼저 알아야 할 것 07-01

#1문제 상황

VPC는 클라우드 안의 설정으로 그어진 가상의 사설 네트워크로, 그 안에서通信이 오간다(→ 01-01). Flow Logs 로는 흐름 하나하나의 기록은 남지만(→ 07-01) 전체 통신량이 얼마나 되는지, 어떤 경로가 막혔는지는 한눈에 안 보인다.

CloudWatch metrics 는 시간에 따른 값의 계열로 서브넷·게이트웨이 처리량과 NAU 를 보여 준다. Reachability Analyzer 는 두 리소스 사이 경로(network path)를 그려 각 구간이 도달 가능한지 알려 주는 reachability analysis 를 한다.

#2핵심 질문

VPC의 트래픽 양과 통신이 막힌 지점은 어떻게 함께 보는가?

#3동작 예시

A 인스턴스에서 B 인스턴스로 연결이 되지 않는다고 보고를 받는다. CloudWatch 지표에서 처리량이 0인 서브넷을 찾고, Reachability Analyzer로 두 인스턴스 사이 경로의 어느 구간에서 실패하는지 확인해 설정 원인을 좁힌다.

#4동작 과정

  1. 지표를 본다CloudWatch 지표에서 서브넷과 게이트웨이의 처리량, 그리고 네트워크 주소 사용량인 NAU를 시간별 값으로 확인한다. 어느 정도 규모까지 쓰는지 미리 재려면 Network Access Analyzer는 더 넓게 볼 수 있고, 비용은 billing and usage reports에서 친다.
  2. 경로를 그린다Reachability Analyzer에 출발점과 도착점 리소스를 넣으면 그 사이 network path를 구간별로 나누어 도달 가능 여부를 보여 준다.
  3. 막힌 곳을 찾는다경로 구간이 어긋난 지점을 보안 그룹(→ 08-01)이나 라우팅 규칙과 대조해 원인을 좁힌다.
  4. 확인해 볼 것CloudWatch 콘솔에서 해당 VPC의 서브넷 처리량 그래프가 시간에 따라 그려지는지 확인한다.

보안 그룹 — 리소스에 붙는 통과 규칙

보안 그룹은 EC2 인스턴스 같은 VPC 리소스마다 붙이고, 어떤 출발지에서 어느 포트로 들어오는 트래픽과 어느 목적지로 나가는 트래픽을 허용할지 정해 두는 상태 기반 방화벽 규칙 묶음이다.

먼저 알아야 할 것 05-01

#1문제 상황

VPC 안의 인스턴스는 서브넷을 통해 서로 통신하고 인터넷에도 나간다(→ 05-01). 하지만 무엇이 들어오는 트래픽을 받아줄지 정하는 곳이 없다.

보안 그룹(security group)은 인스턴스마다 붙이는 규칙 묶음이다. 규칙으로 허용된 트래픽만 인스턴스에 닿으므로, 가상의 방화벽(virtual firewall) 역할을 한다. VPC를 만들면 기본 보안 그룹이 함께 생긴다.

#2핵심 질문

내 인스턴스에 어떤 트래픽만 들어오게 제한할 수 있을까?

#3동작 예시

새 인스턴스를 만들면서 보안 그룹을 고른다. 22번 포트로 들어오는 트래픽은 사내 주소 대역에서만 받도록 한다.

그 인스턴스에 다른 곳에서 포트 접속을 시도하면 연결이 되지 않는다. 보안 그룹 규칙에 없는 트래픽은 인스턴스에 닿기 전에 막힌다.

#4동작 과정

  1. 보안 그룹을 만든다VPC 안에 이름과 설명을 가진 규칙 묶음을 만든다. CreateSecurityGroup로 만들 수 있으며, VPC를 만들 때 생기는 기본 보안 그룹 외에 원하는 만큼 추가한다.
  2. 규칙을 적는다인바운드 규칙은 출발지·포트·프로토콜을, 아웃바운드 규칙은 목적지·포트·프로토콜을 적는다. 이 결합이 허용 조건이 된다.
  3. 리소스에 붙인다보안 그룹은 네트워크 인터페이스(network interface) 단위로 인스턴스에 연결된다. 붙어 있는 동안 그 인스턴스를 지나는 트래픽만 이 규칙이 지킨다.
  4. 확인해 볼 것인스턴스의 보안 그룹 화면에서 붙어 있는 그룹 목록과 인바운드 규칙의 출발지가 사설 CIDR로 되어 있는지 확인한다.

#1문제 상황

보안 그룹이 리소스를 지나는 트래픽을 가른다고 했다(→ 08-01). 그런데 어떤 트래픽을 가를지는 그룹에 붙은 규칙이 정한다.

보안 그룹 규칙(security group rule)은 방향과 대상을 한 줄로 적는 조건이다. 허용(allow) 규칙만 만들 수 있고 거부 규칙은 없다.

#2핵심 질문

들어오는 트래픽과 나가는 트래픽을 한 줄 조건으로 어떻게 적는가?

#3동작 예시

웹 서버용 인스턴스에 인바운드(inbound rule) 규칙을 하나 추가한다. TCP, 443번 포트, 출발지는 0.0.0.0/0이다.

규칙을 저장하자마자 외부에서도 해당 포트로 접속할 수 있게 된다. 새로 만든 그룹에는 아웃바운드(outbound rule) 규칙이 따로 들어 있다.

#4동작 과정

  1. 방향을 고른다들어오는 트래픽은 인바운드, 나가는 트래픽은 아웃바운드 규칙으로 쓴다. 규칙 하나는 한쪽 방향만 다룬다.
  2. 프로토콜과 포트를 정한다protocol에 TCP나 UDP 같은 이름을 쓰고 port range에 80처럼 포트나 범위를 적는다.
  3. 상대를 정한다인바운드는 CIDR source로 출발지 주소 범위를, 아웃바운드는 목적지 주소 범위를 적는다. 하나의 security group을 상대로 지정할 수도 있다.
  4. 확인해 볼 것보안 그룹의 인바운드 규칙 목록에서 방향 표시에 Inbound가 붙고 출발지 주소가 입력되어 있는지 확인한다.

먼저 알아야 할 것 08-02

#1문제 상황

리소스를 만들 때 보안 그룹을 하나도 고르지 않으면 AWS가 대신 골라 붙여 준다(→ 08-01). 그 기본값이 모든 리소스에 같은 규칙을 적용해 버린다.

기본 보안 그룹(default security group)은 VPC를 만들 때 이름이 default로 생기는 보안 그룹이다. 규칙은 고칠 수 있지만 삭제할 수는 없다.

#2핵심 질문

같은 허용 규칙을 여러 VPC의 리소스에 한 번에 적용할 수 있을까?

#3동작 예시

운영 VPC에서 만든 보안 그룹에 웹 포트 허용 규칙을 넣는다. 이 그룹을 다른 계정의 내부 서비스에도 공유해 붙였다.

두 환경 어디서든 같은 규칙으로 트래픽이 걸러진다. 규칙은 하나만 고치면 두 곳이 함께 따라온다.

#4동작 과정

  1. 기본값을 좁힌다인스턴스 생성 시 그룹을 생략하면 그 VPC의 default 그룹이 붙는다. 이 그룹의 인바운드 규칙은 보안 그룹 자기 자신만 허용하는 형태라 외부 트래픽은 기본적으로 막힌다. 필요한 포트만 추가하고 전용 그룹을 따로 만들어 붙이는 편을 권장한다.
  2. 다른 VPC에 붙인다associate security groups with multiple VPCs 방식으로 다른 VPC의 리소스에도 같은 그룹을 연결할 수 있다.
  3. 계정 간에 공유한다AWS Organizations 안에서 share security groups를 쓰면 정책이 허용하는 다른 계정의 리소스에도 같은 규칙 묶음을 붙일 수 있다.
  4. 확인해 볼 것VPC 콘솔의 보안 그룹 화면에서 이름이 default인 그룹이 있는지, 그 그룹의 인바운드 규칙이 자기 그룹만 허용하는지 확인한다.

네트워크 ACL — 서브넷 경계의 통과 규칙

네트워크 ACL은 서브넷 하나에 붙는 상태 비저장(stateless) 방식의 방화벽으로, 패킷을 양방향에서 각각 따로 검사해 허용 또는 명시적 차단을 규칙 번호 순서로 적용한다.

먼저 알아야 할 것 08-01

→ 08-01 참조

#1문제 상황

보안 그룹은 리소스마다 붙는 규칙이라(→ 08-01), 서브넷 전체를 한 번에 막고 싶을 때는 쓸 곳이 없다.

네트워크 ACL(network ACL)은 서브넷 한 개의 경계에 붙는 규칙집이다. 서브넷으로 들어오는 패킷과 나가는 패킷을 서로 따로 검사하는 stateless 방식이다.

#2핵심 질문

서브넷 경계에서 들어오고 나가는 패킷을 따로 거를 수 있을까?

#3동작 예시

두 서브넷이 있는 VPC에 네트워크 ACL을 각 서브넷에 하나씩 붙인다. 첫 번째 서브넷에는 사내 대역에서 들어오는 트래픽만 통과시키는 규칙을 둔다.

Peered VPC에서 들어온 트래픽은 라우터가 서브넷으로 넘기려 해도 ACL이 막는다.

#4동작 과정

  1. ACL을 고른다VPC에는 기본 네트워크 ACL(default network ACL)이 이미 있고, 보안 그룹과 비슷한 규칙으로 직접 만드는 custom network ACL도 둘 수 있다.
  2. 서브넷 경계에 붙인다서브넷마다 ACL 하나가 붙어, 들어올 때와 나갈 때 이 규칙집을 각각 한 번 지난다.
  3. 양방향을 따로 정한다패킷은 상태를 기억하지 못하므로 들어오는 쪽과 나가는 쪽 규칙을 짝으로 만들어야 한다.

네트워크 ACL 규칙은 허용·차단·거부 규칙을 번호가 작은 순서대로 평가하고, 모든 규칙을 걸친 패킷은 서브넷 앞뒤에서 각각 한 번씩 이 규칙 집합을 통과해야 서브넷 안으로 들어가거나 나갈 수 있다.

#1문제 상황

네트워크 ACL이 서브넷 경계에서 동작한다고 했다(→ 08-04). 그런데 보안 그룹과 달리 이쪽은 명시적인 거부 규칙을 적고 번호 순서로 판단한다.

네트워크 ACL 규칙(network ACL rule)은 번호를 붙인 조건 목록이다. 규칙을 바꾸면 붙어 있는 서브넷에 곧바로 반영된다.

#2핵심 질문

서브넷 앞뒤를 통과할 패킷을 번호 순서로 어떻게 정할까?

#3동작 예시

ACL에 100번 허용 규칙과 200번 차단 규칙을 넣는다. 100번 조건에 맞는 패킷은 그대로 통과하고, 나머지는 200번에서 막힌다.

규칙 번호를 수정하자마자 해당 서브넷의 통신이 바뀐다.

#4동작 과정

  1. 번호를 붙인다rule number가 작은 규칙부터 평가해, 처음 맞은 규칙이 그 뒤 번호와 상관없이 그대로 적용된다.
  2. 종류와 대상을 적는다Type에 특정 프로토콜(예: SSH)이나 전체 트래픽을 고르고, protocol, port range, 그리고 인바운드면 출발지 CIDR을 채운다. outbound인 egress rule는 목적지를 적는다.
  3. 허용과 거부를 함께 둔다allow rule로 필요한 통로만 열어 두고 deny rule로 나머지를 막는다. 서브넷에 들어가면 다시 나갈 때도 같은 규칙집을 한 번 더 지난다.
  4. 확인해 볼 것ACL 규칙 화면에서 규칙 번호가 작은 순서로 나열되고, 인바운드와 아웃바운드가 따로 묶여 있는지 확인한다.

Path MTU Discovery — 패킷이 큰 이유로 못 갈 때

Path MTU Discovery는 경로 중간에서 가장 작은 MTU 값을 ICMP 메시지로 알려주는 기능으로, 이 값을 라우팅 설정에 반영하지 않으면 큰 패킷이 조용히 버려져 연결이 지연되거나 끊긴 것처럼 보인다.

먼저 알아야 할 것 08-04

#1문제 상황

네트워크 ACL이 패킷 크기까지 검사하지 않더라도(→ 08-04), 패킷이 목적지에 닿지 못하는 경우가 있다. 경로 중간 장비가 큰 패킷을 조용히 버리는 경우다.

경로 MTU(path MTU)는 출발 호스트와 수신 호스트 사이에서 처리할 수 있는 최대 전송 단위(maximum transmission unit)다. IPv4에서는 이를 넘는 패킷을 장비가 버리고 fragmentation이 필요하다고 알린다. Path MTU Discovery는 그 알림을 경로의 MTU 값으로 받아 적어 두는 기능이다.

#2핵심 질문

경로가 감당하지 못하는 큰 패킷을 어떻게 알아내게 할까?

#3동작 예시

ICMP Path MTU Discovery를 켠 호스트가 큰 패킷을 보낸다. 중간 장비가 그 패킷을 버리고 ICMP 메시지로 더 작게 나누어 보내라고 알린다.

보낸 쪽이 그 크기에 맞춰 나눠 다시 보내면 통신이 이어진다. IPv6는 경로에서 분할을 하지 않아 크기 초과를 ICMPv6 Packet Too Big으로 알린다.

#4동작 과정

  1. 경로의 한계를 잰다수신 호스트나 경로 장비가 MTU를 넘은 패킷을 버리고 ICMP 메시지로 필요한 분할(fracturing)을 알린다.
  2. 보낸 쪽이 나눈다그 알림을 받은 송신 호스트가 내용을 여러 작은 패킷으로 나눠 다시 보낸다.
  3. 값을 설정에 반영한다나눠 보낸 패킷이 통과하면 정상 통신이 되고, 여전히 크기 문제로 끊기면 MTU 관련 설정을 다시 확인한다.
  4. 확인해 볼 것VPC 안에서 인스턴스까지 보낸 큰 패킷에 대해 응답이 돌아오는지 테스트 도구로 확인한다.

계정 안의 모든 VPC 와 그 안의 모든 리소스가 인터넷에 공개되지 않도록 강제하는 계정 단위 설정으로, 관리자가 직접 연 통로를 통째로 막아 줍니다.

#1문제 상황

보안 그룹에서 인바운드 포트를 열어 두면(→ 08-02) 그 규칙을 가진 리소스만 인터넷에 닿는다. 그런데 리소스를 여러 팀이 만들고 계정이 크면 어디 하나에서 자꾸 0.0.0.0/0 이 붙는다.

VPC Block Public Access, 줄여서 VPC BPA는 계정 단위로 모든 VPC의 공개 노출을 막는다. internet gateway로 나가는 길 자체를 통째로 잠근다.

#2핵심 질문

설정 실수로 어떤 VPC가 인터넷에 열리면 그것을 계정 전체에서 막을 수 있을까?

#3동작 예시

운영 계정의 VPC를 막아 둔 상태에서 개발자가 공개 웹 서버를 만들려고 internet gateway를 붙인다. 저장은 되지만 외부에서 접속하는 연결이 차단되고, 콘솔에 차단 사유가 함께 보인다.

#4동작 과정

  1. 모드를 고른다계정 또는 리전 단위로 VPC BPA를 켜고 internet gateway block mode를 고른다. block-bidirectional는 들어오고 나가는 트래픽을 모두 막고, block-ingress는 들어오는 쪽만 막아 NAT gateway로 나가는 길은 남긴다.
  2. 예외를 정한다완전히 막히면 안 되는 곳은 exclusion으로 둔다. exclusion은 VPC나 서브넷 단위에 걸어 계정 모드에서 빼고 양방향 접근을 허용한다.
  3. 확인해 볼 것VPC BPA 상태를 확인하는 화면에서 켜진 계정 단위 모드와 제외된 VPC 목록이 함께 보이는지 본다.

  2. 예외를 표시한다강제에서 빼야 하는 자리는 VPC Encryption Controls Exclusions로 따로 남긴다. 트래픽 확인은 AWS Network Firewall 같은 계층 보안 도구를 함께 쓸 수 있다.

VPC가 다른 서비스를 대신 만들도록 설정하면 AWSServiceRoleForVPC 라는 이름의 역할이 계정에 만들어진다. VPC 콘솔에서 VPC가 어떤 역할을 쓰는지 목록에서 볼 수 있다.

#4동작 과정

  1. 역할이 만들어진다VPC를 쓰면 VPC가 정해 둔 이름의 service-linked role이 만들어진다. 이 역할의 권한은 VPC만 대신 사용할 수 있고 trust policy와 permissions policy로 정해진다.
  2. 관계를 끊는다permissions policy를 다른 IAM 대상에 붙여 옮겨 쓸 수는 없다. 관련 리소스를 먼저 지운 뒤에야 service-linked role을 삭제할 수 있다.
  3. 확인해 볼 것IAM 역할 목록에서 VPC 이름이 들어간 service-linked role이 따로 표시되는지 확인한다.

VPC 를 다른 종류의 영역으로 넓히기

하나의 VPC 를 같은 리전 안에서도 일반 리전 밖의 특수한 확장 영역(로컬 존, Outposts, Wavelength)까지 자리까지 함께 늘려 쓸 수 있게 해, 가까운 곳에서 지연 없이 서비스가 오게 만드는 방법.

먼저 알아야 할 것 01-02

#1문제 상황

리전은 지역 단위이고 리전 안에는 가용 영역이 여러 개 있다(→ 01-02). 그런데 사용자가 큰 도시에 사 residing 해 있거나 자체 데이터 센터가 있으면 리전의 가용 영역은 그곳에서 멀다.

Extend a VPC to other Zones는 그 VPC를 늘려서 리전 안의 AWS Local Zones, AWS Outposts, AWS Wavelength 같은 특수한 위치에도 자리를 두게 한다. 서브넷을 그 자리에 두면 사용자와 가까운 곳에서 서비스가 서게 된다.

#2핵심 질문

리전 밖의 가까운 자리까지 하나의 VPC로 확장하려면 어떻게 하지?

#3동작 예시

서울에 있는 앱을 미국tegergement 도시에 가까운 곳에서 빠르게 응답하게 하려고 한다. 같은 VPC 안에 Wavelength 위치의 서브넷을 하나 더 만들고 그 안에 인스턴스를 띄운다. 사용자 요청이 가까운 위치의 인스턴스로 바로 닿아 응답이 빨라진다.

#4동작 과정

  1. 위치를 정한다리전 안에서 가까운 쪽인 AWS Local Zones, 자체 데이터 센터에 두는 AWS Outposts, 통신사 5G망 끝에 두는 AWS Wavelength 중 하나를 고른다. 각 위치는 리전과 별개로 물리적으로 떨어진 곳이다.
  2. 서브넷을 붙인다고른 위치마다 subnet을 하나씩 만들어 그 위치로 지정한다. outpost subnet은 이렇게 만든 서브넷으로, 이후 설정에도 계속 AWS Outposts에 쓰인다.
  3. 확인해 볼 것VPC 콘솔의 서브넷 목록에서 각 서브넷의 가용 영역 이름이 Local Zone·Outpost·Wavelength로 따로 표시되는지 본다.

VPC 할당량 — 계정마다 정해진 한계

한 AWS 계정에서 VPC 를 몇 개까지 만들고 VPC 안의 리소스를 몇 개까지 둘 수 있는지에 대한 AWS 가 정해 둔 상한이며, 필요한 경우 할당량 증가를 요청해 올릴 수 있다.

먼저 알아야 할 것 01-03

#1문제 상황

환경을 나누다 보니 VPC와 서브넷이 자꾸 늘어난다. VPC를 몇 개까지 더 만들고 거기에 리소스를 몇 개까지 둘 수 있는지가 정해져 있지 않으면 필요한 시점에 구성이 막힌다.

Quotas는 계정 단위로 정해진 사용 상한이다. 넘으려 하면 request quota increase로 상한을 올려야 한다.

#2핵심 질문

계정에서 VPC와 서브넷을 몇 개까지 만들 수 있고 넘으면 어떻게 하나?

#3동작 예시

개발·스테이징·프로덕션용으로 VPC를 이미 다섯 개 썼다. 새 서비스용 VPC를 하나 더 만들려니 거절된다. 콘솔의 할당량 화면에서 VPCs per Region의 현재 사용량 5/5를 보고 상한을 올려 달라고 요청한다.

#4동작 과정

  1. 한도를 확인한다할당량은 별도 언급이 없으면 리전 단위로 적용된다. VPCs per Region의 기본값은 5이고 subnets per VPC와 security groups per VPC도 정해진 상한이 있다(→ 08-01).
  2. 사용량을 비교한다콘솔의 할당량 화면에서 각 항목의 현재 값과 한도를 나란히 보고 어디서 걸렸는지 본다. IPv4 CIDR blocks per VPC 같은 항목은 상한을 더 올릴 수 있다.
  3. 상한을 요청한다request quota increase로 올려 달라고 요청한다. 리소스별 할당량을 올리면 그 리전의 해당 리소스 전체에 함께 반영된다.
  4. 확인해 볼 것할당량 화면에서 한 항목의 현재 사용량이 한도를 넘지 않게 표시되는지 본다.

AWS Network Firewall — VPC 안의 트래픽을 거르는 벽

VPC 를 오가는 트래픽을 서브넷 단위로 가로질러 확인하고, 규칙에 어긋나면 차단하는 상태 저장 방화벽 서비스다.

먼저 알아야 할 것 09-02

#1문제 상황

보안 그룹은 인스턴스마다 붙는 통과 규칙이라(→ 08-01) 서브넷 사이를 오가는 트래픽 전체를 보는 곳이 없다. 침입 시도가 들어오는지 한 곳에서 막으려면 별도 장비를 관리해야 한다.

AWS Network Firewall은 VPC 안에 두는 상태 저장(stateful) 방화벽이다. 패킷 흐름을 기억해 양방향을 함께 판정하며 intrusion prevention 기능으로 intrusion detection와 방어를 함께 수행한다.

#2핵심 질문

서브넷 사이를 오가는 트래픽을 규칙대로 거르고 위반을 막으려면 어디서 처리하지?

#3동작 예시

#4동작 과정

  1. 방화벽을 만든다AWS Network Firewall 리소스인 firewall를 만들고 보호할 VPC와 방화벽 endpoint를 놓을 가용 영역과 서브넷을 지정한다.
  2. 정책을 붙인다firewall policy에 규칙 그룹을 넣어 검사 기준을 정한다. 이 정책이 트래픽 필터링 동작을 정의하고 규칙 그룹이 세부 기준을 담는다.
  3. 확인해 볼 것방화벽 상태 화면에서 endpoint가 각 가용 영역에 정상으로 살아 있는지 확인한다.

먼저 알아야 할 것 03-01

#1문제 상황

#2핵심 질문

VPC에서 나가는 이름 질의가 닿아도 되는 도메인을 어떻게 정하지?

#3동작 예시

어플리케이션이 의도치 않은 도메인으로 이름을 질의한다. 해당 도메인이 차단 목록에 있어 resolver가 해석을 진행하지 않고 정해진 응답으로 대체한다. 콘솔에 차단된 질의가 기록으로 남는다.

#4동작 과정

  1. 도메인 목록을 만든다허용할 도메인과 차단할 도메인을 domain list로 정리한다. 차단된 질의에는 원하는 응답을 지정할 수도 있다.
  2. 규칙 그룹을 만든다DNS Firewall rule group은 DNS queries를 걸러 내는 규칙의 묶음이다. 각 규칙은 domain list 하나와 그 목록에 해당하는 질의에 할 동작을 함께 지정한다.
  3. VPC에 연결한다rule group을 하나 이상의 VPC와 연결하면 그 VPC에서 DNS Firewall 필터링이 켜진다. resolver가 받는 질의를 DNS Firewall로 넘겨 검사를 받게 한다.
  4. 확인해 볼 것해당 VPC에서 차단 목록의 도메인을 조회했을 때 이름이 풀리지 않는지 본다.

Network Access Analyzer — 어떤 통신이 실제로 가능한지

VPC 의 라우팅 규칙을 실제로 계산해, 어떤 두 대상(리소스나 사용자) 사이에서 통신이 성립하는지, 어떤 보안 그룹 규칙이 그 통신을 허용하는지를 찾아 주는 분석 기능이다.

먼저 알아야 할 것 07-06

#1문제 상황

보안 그룹 규칙이 여러 겹이고(→ 08-02) 라우팅 테이블도 서브넷마다 다르다(→ 05-02). 두 서버가 말 안 통할 때 어느 규칙이 막고 있는지 눈으로 다 헤아리기 어렵다.

Network Access Analyzer는 이 구성을 직접 계산해 답을 낸다. Reachability Analyzer는 여기서 두 대상 사이의 도달 가능성을 따로 다루는 기능이다(→ 07-06).

#2핵심 질문

두 리소스 사이에서 통신이 실제로 성립하는지 어떤 규칙이 막는지 어떻게 아는가?

#3동작 예시

프라이빗 서브넷의 인스턴스가 다른 인스턴스에 붙지 않는다. Network Access Analyzer로 두 인스턴스를 지정하니 통신은 성립하지 않으며, 허용 규칙을 좁혀 본 보안 그룹 규칙이 원인으로 표시된다. 그 규칙을 고치자 reachability analysis 결과가 성립으로 바뀐다.

#4동작 과정

  1. 두 대상을 고른다인스턴스, VPC endpoint, Transit gateway, VPN gateway, internet gateway 같은 VPC 안의 리소스 두 개를 지정한다. 대상 종류가 늘어 있어 조합을 넓게 볼 수 있다.
  2. 경로를 계산한다reachability analysis를 돌려 통신되면 network paths를 홉 단위로 보여 주고, 안 되면 막고 있는 구성 요소를 지목한다.
  3. 반영한다Resource Control Policy로 태김이 붙은 리소스 묶음에 대한 접근을 통제해 확인한 구조를 정책으로 남긴다.
  4. 확인해 볼 것분석 결과에서 두 대상이 통신 가능인지, 불가능하면 차단 지점으로 어느 구성 요소가 표시되는지 본다.

#1문제 상황

#2핵심 질문

익힌 구성을 AWS CLI로 직접 만들어 보고 맞는지 어떻게 확인하지?

#3동작 예시

프라이빗 서브넷 안에만 인스턴스를 두고 외부로 나갈 때만 NAT gateway를 쓰도록 제한하고 싶어, private servers with NAT gateways 예제를 따라 CLI로 만든다. 생성된 VPC에 나가는 길이 있는지와 각 인스턴스가 프라이빗 서브넷에 놓였는지를 콘솔에서 본다.

#4동작 과정

  1. 예제를 고른다test environment처럼 개발·테스트용 VPC부터 시작하거나, web·database 서버용 구성, 프라이빗 서브넷과 NAT 조합처럼 더 복잡한 구성까지 고른다. 모두 동일한 VPC를 직접 만들어 세밀한 통제를 얻는 전제다.
  2. CLI로 만든다AWS CLI 명령을 순서대로 실행해 VPC와 서브넷, 라우팅 테이블, NAT gateway를 생성한다.
  3. 확인해 볼 것생성된 서브넷 목록에서 각 인스턴스가 프라이빗 서브넷에 있고 NAT gateway 경로가 붙어 있는지 본다.
