1HAProxy 가 무엇인가: 역할과 아키텍처01-01

로드 밸런싱의 단계와 로드 밸런서의 배치 방식

여러 서버로 요청을 분산하는 로드 밸런싱은 DNS·네트워크 4층·응답 7층으로 단계가 나뉘며, 그 장치는 전용 하드웨어나 일반 서버에 설치한 소프트웨어, 클라우드 서비스로 배치된다.

1문제 상황

요청이 하나인 서버에 몰리면 그 서버만 느려지고 나머지는 놀게 된다. 그래서 여러 대를 준비해 요청을 나눠 받으려 한다. 근데 나눌 대상과 나눌 수단이 어디부터인지가 갈린다. 도메인 이름 자체를 여러 IP 로 나누는 DNS 방식, TCP 패킷의 목적지 주소·포트만 보고 나누는 네트워크 4층 방식, HTTP 요청 내용까지 보고 나누는 응답 7층 방식으로 단계가 나뉜다. 무엇을 나눌지 정해야 로드 밸런서를 어디에 두고 어떻게 고르는지가 결정된다.

2핵심 질문

들어온 요청을 어떤 기준과 어느 시점에 판단해 여러 서버 중 하나로 보내는가?

3동작 예시

예를 들어 주소가 shop.example.com 이고 서버가 3대일 때, DNS 방식으로 가면 도메인 이름 자체를 3개 IP 로 돌려주고 접속을 분산한다. 4층 방식으로 가면 로드 밸런서는 TCP 연결의 목적지 주소와 포트를 보고 서버를 하나 골라 연결을 넘긴다. 7층 방식으로 가면 이미 연결된 상태에서 HTTP 요청 줄의 Host 와 URI 를 읽고, Host: shop.example.com 과 경로가 /cart 인 요청이면 결제용 서버로, 경로가 /img 인 요청이면 이미지 서버로 보낸다. 7층은 요청 내용을 봐야 하므로 연결을 열고 그 안에서 판단하고 다시 응답을 돌려주는 방식이 된다.

4동작 과정

  1. 판단 기준 정하기DNS 는 도메인 이름 해석 단계에서, 4층 은 TCP·IP 헤더의 주소와 포트만 보고, 7층 은 HTTP 요청 본문까지 해석해 판단한다. 판단이 얕을수록 빠르고, 깊을수록 경로·헤더 같은 조건으로 나눌 수 있다.
  2. 배치 방식 정하기전용 하드웨어 장비에 구현된 로드 밸런서, 일반 서버에 소프트웨어로 설치한 로드 밸런서, 클라우드 제공 서비스로 구성한 로드 밸런서가 있다. 어느 쪽이든 클라이언트에게 하나의 진입점을 보여 준다는 기능은 같고, 설치·운영 주체와 비용 구조가 다르다.
  3. 요청 넘기기HAProxy 는 소프트웨어로 설치해 쓰는 쪽에 해당한다. 클라이언트로부터 받은 트래픽을 자신이 받아 목적지 서버로 넘기고, 서버가 돌려준 응답을 다시 클라이언트에게 전달한다.

HAProxy 는 클라이언트 대신 트래픽을 받아 지정된 서버로 넘기고 연결을 정리하는 역방향 프록시이자 로드 밸런서이며, 웹 서버 본체의 업무나 애플리케이션 로직 자체는 대신하지 않는다.

1문제 상황

서버를 여러 대로 늘린 뒤에는 클라이언트마다 어느 서버로 갈지 알려야 하고, 그 서버가 응답하는 동안 연결을 붙잡고 있어야 하며, 어떤 서버가 죽었는지 알아야 한다. 이 일을 애플리케이션 코드로 하면 모든 서버에 같은 분배 로직을 넣어야 하고, 서버가 늘어날 때마다 고쳐야 한다. 애플리케이션은 데이터 처리와 응답 내용 생성만 맡길 수 있고, 연결과 분배는 그 밖의 계층이 맡아야 한다.

2핵심 질문

애플리케이션 코드를 건드리지 않고 클라이언트와 여러 서버 사이에서 트래픽을 나눠 주고 연결을 관리할 수 있는가?

3동작 예시

GET /orders 요청이 들어오면 HAProxy 는 클라이언트와의 연결을 먼저 받고, 목적지 후보 목록에서 살아 있는 서버 하나를 골라 그 서버로 새 연결을 연 뒤 요청 줄을 그대로 전달한다. 서버가 200 OK 와 주문 목록을 돌려주면 HAProxy 는 그 응답 바이트를 클라이언트에게 되돌려 보내고, 다 쓰면 양쪽 연결을 정리해 닫는다. 서버가 응답하지 않으면 그 서버를 후보에서 빼고 다른 곳으로 보내며, 주문 목록을 만드는 일은 전혀 하지 않는다.

4동작 과정

  1. 역방향 프록시로 받기HAProxy 는 클라이언트 대신 서버 쪽에 서서 트래픽을 먼저 받는다. 클라이언트는 HAProxy 만 알고 있고, 그 뒤에 몇 대가 있는지와 어디가 어떤 역할인지는 HAProxy 설정에 정의한다.
  2. 로드 밸런서로 나누기받은 요청을 조건에 맞는 서버로 보내고, 응답도 같은 경로로 되돌린다. 이 분배와 서버 상태 확인은 설정에 적은 규칙대로 알아서 반복된다.
  3. 연결 관리로 끝맺기클라이언트 쪽 연결과 서버 쪽 연결을 각각 열기·유지하기·닫기의 순서로 정리하고, 버퍼와 재사용을 관리한다. 애플리케이션 로직은 이 과정 바깥에 그대로 두고 HAProxy 는 그 흐름만 전달한다.

1문제 상황

연결이 많을 때 스레드마다 요청 하나를 끝까지 처리하는 방식은thread-per-request 라서, 연결 수가 스레드 수를 넘어가면 스레드를 늘리거나 대기 상태로 둘 수밖에 없다. 스레드를 늘리면 문맥 전환 비용이 커지고, 대기 중인 스레드는 CPU 를 잡고 있지 않아도 자원 자리를 차지한다. 큰 처리량 환경에서 이러한 낭비를 줄여야 한다.

2핵심 질문

연결 수가 스레드 수보다 훨씬 많아도 CPU 를 낭비하지 않으면서 모든 연결을 동시에 처리하려면 어떻게 해야 하는가?

3동작 예시

8만 개의 클라이언트 연결이 열려 있고 서버가 4대인 상황을 보자. 스레드-per-request 방식이라면 8만 개 요청을 위해 스레드가 수만 개 생겨야 한다. 이벤트 기반 방식이라면 스레드는 CPU 코어 수만큼만 두고 각 스레드가 커널로부터 어느 준비 완료 통지를 나눠 받는다. 읽을 데이터가 도착한 소켓 번호만 그 스레드에 알리면 그 스레드가 그 연결 한 건만 처리하고, 나머지 스레드는 자기 대기열로 돌아간다.

4동작 과정

  1. 준비 완료 통지를 나눠 받기커널이 "이 소켓에 읽을 데이터가 있다"는 신호를 보낼 때 여러 스레드가 그 신호를 나눠 맡는다. 한 스레드가 통지를 하나씩 집어 처리하므로 연결이 많아도 스레드 수는 늘지 않는다.
  2. 연결을 스레드에 고정하기각 스레드는 처음 맡은 연결만 계속 처리한다. 스레드 안에서 처리 중인 연결들의 자료구조를 붙여 두어, 다른 스레드의 자료구조를 건드리지 않게 한다.
  3. CPU 를 붙여 캐시 적중시키기각 스레드가 실제 CPU 코어 하나에 고정되도록 설정해, 그 스레드가 쓰는 메모리가 그 코어의 캐시에 남게 한다. 같은 스레드가 다시 자기 연결 자료구조를 읽을 때 메모리를 바깥에서 다시 가져오지 않아도 되어 처리 시간이 짧아진다.

1문제 상황

3동작 예시

  1. 프런트엔드와 백엔드를 나누어 정의하기프런트엔드는 클라이언트 연결이 붙는 지점이고, listen 이나 bind 로 주소와 포트를 지정한다. 백엔드는 그 요청을 보낼 목적지 서버들의 집합으로, 여러 대를 나열해 묶고 각 서버의 상태와 가중치를 적는다.

2핵심 질문

3동작 예시

4동작 과정

  2. 연결 재사용keepalive 를 켜 두면 같은 연결로 연속 요청을 주고받고, 정해진 대기 시간 동안 연결을 열어 둔다.
  3. 연합 정리와 제한대기 시간 초과나 연결 용량 초과, 상태 변경 같은 조건에서 연결을 정리하고 maxconn 과 server 지연 설정으로 전체 동시 수를 통제한다.

3동작 예시

  3. 트래픽 반영상태가 바뀐 서버를 라우팅 대상에 넣거나 빼고, 그 시점 이후 들어오는 요청을 살아 있는 서버로 보낸다.

고가용성과 우아한 전환

고가용성은 HAProxy가 죽어도 서비스를 계속 제공하도록 여러 인스턴스를 함께 운영하는 것이고, 우아한 전환은 기존 연결을 끊지 않은 채 설정 변경을 반영하는 방식이다.

1문제 상황

HAProxy 도 결국 하나의 프로세스로 동작하므로, 그 프로세스나 프로세스가 올라간 장비가 멈추면 서비스가 끊긴다. 그런데 설정을 바꿨다고 곧바로 새 설정으로 갈아타면 처리 중인 요청이나 아직传输이 끝나지 않은 응답이 중간에서 끊긴다. 배치는 임의로 뽑은 프로세스를 여러 개 띄우고 그 앞에 로드밸런서를 두는 방식으로 구성한다.

2핵심 질문

3동작 예시

4동작 과정

  1. 이중화 구성같은 설정으로 프로세스를 여러 개 띄우고 장비 장애나 복구에 대응하며, 각 프로세스를 관리 포트에 연결해 상태를 조회한다.
  2. 새 프로세스 기동관리 명령으로 설정을 다시 읽어 새 프로세스를 띄우고, 새로 들어오는 연결은 이 프로세스가 받게 한다.
  3. 기존 프로세스 정리기존 프로세스는 진행 중 커넥션을 마친 뒤 종료하도록 기다림 시간을 주고, 리스너를 넘긴 상태에서 내려가게 한다.

2핵심 질문

3동작 예시

  2. 서버에 태그 부여server 줄에 cookie srv1 처럼 서버마다 이름표를 붙인다. 이 이름표가 쿠키에 담겨 기준 값이 된다.

  3. 하위 섹션 연결frontend 는 들어오는 요청의 처리 방식을, backend 는 나가는 요청을 보낼 서버와 방식을 정한다. listen 은 두 가지를 한 섹션에 합친 형태다.

같은 값을 매번 손으로 변환해서 적어야 하는 것도 번거롭고, 실수로 다른 단위를 섞으면 설정이 의도대로 동작하지 않습니다.

또한 조건을 조합해 만든 규칙들이 많아지면 어떤 조건이 어디에 쓰이는지 추적이 어렵습니다. 조건에 이름을 붙여 재사용할 방법이 필요합니다.

2핵심 질문

3동작 예시

4동작 과정

  1. ACL 로 조건 정의acl <이름> <criterion> [인자] 형식으로 조건 하나를 이름 붙인 규칙으로 만든다. 이 이름 하나가 참 또는 거짓 값 하나를 갖는다.

변수와 주소·프로토콜 접두사 표기

${var} 로 런타임 변수를 참조하고, bind·server 주소에는 ipv4·ipv6·unix 같은 주소 계열 접두사와 tcp·udp·http 같은 프로토콜 접두사를 붙여 지정한다.

1문제 상황

HAProxy 설정에는 동일한 IP·포트·경로·타임아웃 값이 여기저기 반복해서 등장한다. 서버를 추가할 때마다 같은 값을 다시 적어야 하고, 설정을 고치면 파일 전체를 손봐야 한다.

주소도 일관되지 않다. IPv4 주소인지 IPv6 주소인지, 유닉스 소켓 경로인지, TCP인지 UDP인지가 문장 어디에 붙는지 정해져 있지 않으면 읽는 사람이 매번 해석해야 한다. 값이 늘어날수록 설정 파일은 길어지고 오타가 숨기 쉬워진다.

2핵심 질문

반복되는 값을 한 번만 정의해 재사용하고, 주소와 프로토콜의 종류를 같은 표기 규칙으로 명시할 수 있는가?

3동작 예시

${API_PORT} 라는 변수를 env API_PORT=8080 처럼 환경에서 주입하면 bind :${API_PORT} 와 server web1 :${API_PORT} 에 같은 8080 이 들어간다. 포트를 바꾸려면 API_PORT 값 하나만 고치면 되고, 설정 파일 안의 숫자는 손대지 않는다.

주소도 접두사로 종류가 드러난다. bind 127.0.0.1:80 은 IPv4 루프백이고, bind [::1]:80 은 IPv6 루패스고, bind /run/haproxy.sock 은 유닉스 소켓이다. bind :53 udp 는 TCP 가 아니라 UDP 53번 포트를 연다는 뜻이다.

4동작 과정

  1. 변수 정의와 참조env 지시문으로 환경 변수 값을 이름에 묶어 두고, ${이름} 형식으로 다른 지시문 어디에서든 불러 쓴다. 값이 바인딩되는 시점에 치환되므로 실행 환경마다 다른 설정을 같은 파일로 쓸 수 있다.
  2. 주소 계열 접두사ipv4@ , ipv6@ , unix@ , sock 같은 접두사를 주소 앞에 붙여 주소가 어느 계열인지 명시한다. 명시하지 않으면 IPv4와 IPv6를 모두 시도하는 v4v6 이 기본값이 되어, 의도치 않은 주소로 연결될 수 있다.
  3. 프로토콜 접두사tcp@ , udp@ , ssl@ , fcgi@ , sock@ 같은 접두사를 주소 뒤에 붙여 어떤 프로토콜로 통신할지 정한다. 서버 줄에서는 보통 생략하며, 이 경우 프론트엔드의 mode 값이 그대로 적용된다.

3동작 예시

frontend fe_http 에 bind *:80 을 두면 80번 포트로 들어오는 연결을 이 프록시가 받는다. 그 안에 mode http 라고 적으면 도착한 바이트를 HTTP 요청으로 해석하고, default_backend be_app 으로 보내 Backend 처리 위치를 정한다. listen stats 처럼 프론트엔드와 백엔드를 한 블록에 같이 적는 형태도 가능하다.

4동작 과정

  1. 프록시 섹션 선언frontend , backend , listen 중 하나로 시작하는 블록 하나가 프록시 섹션이다. frontend 는 클라이언트를 받는 쪽, backend 는 실제 서버가 있는 쪽, listen 은 둘을 합친 형태로 상태 확인용 포트나 로드밸런서 통계 페이지에 쓴다.
  2. mode 로 처리 방식 고정http 는 바이트를 HTTP 요청·응답으로 파싱해 헤더를 읽고 경로별로 규칙을 나눈다. tcp 는 바이트를 그대로 스트리밍해 앞뒤 판단 없이 통과시킨다. 그 밖에 udp 가 있으며, 섹션이 처음 등장할 때마다 mode 를 다시 쓰면 이후 지시문은 그 모드를 기준으로 해석된다.
  3. 섹션 간 연결프론트엔드 안에서 default_backend 로 백엔드를 지정하면, 모든 요청이 조건에 걸리지 않았을 때 그 백엔드로 넘어간다. 백엔드 안에서 server 로 나열한 서버들 중 하나를 골라 연결하고, 응답은 왔던 경로 그대로 클라이언트에게 돌아간다.

리스닝 주소와 소켓 지정

bind 지시문으로 클라이언트를 받을 IP 주소·포트·인터페이스(유닉스 소켓 포함)를 지정해 리스닝 포트를 여는 설정.

1문제 상황

프록시가 클라이언트 요청을 받으려면 먼저 포트를 열어 두고在那里 대기해야 한다. 그런데 어떤 주소를 열어야 하는지가 정해져 있지 않다. 모든 인터페이스에 열면 원치 않는 곳까지 노출되고, 특정 주소에 열면 내부 통신이 차단된다.

같은 컴퓨터 안에서만 통신하는 경우도 있다. 이때는 포트 번호가 아니라 파일 경로 하나로 소켓을 식별하며, 이 방식을 TCP·UDP 포트와 섞어 쓰는 설정도 흔하다.

2핵심 질문

3동작 예시

bind 10.0.0.5:8080 라고 쓰면 내부망 주소 10.0.0.5 의 8080 포트만 열어 두므로 외부에서 직접 붙는 시도가 막힌다. 같은 컴퓨터의 백엔드만 붙이려면 bind /run/haproxy/app.sock 처럼 경로를 적고, 백엔드 줄에서도 server b1 /run/haproxy/app.sock 로 같은 경로를 가리킨다.

4동작 과정

  1. 바인드 지시문으로 대기 지점 등록bind 주소:포트 를 쓰면 HAProxy 가 그 주소를 독점하고 클라이언트 연결을 받을 준비를 한다. 주소가 빈 bind :80 이면 모든 인터페이스를 뜻한다. 주소 앞에 인터페이스 이름을 붙이면 eth0:80 처럼 특정 NIC(네트워크 인터페이스 카드) 로 좁힐 수 있다.
  2. 소켓 경로 지정bind /path/name.sock 은 포트 대신 유닉스 도메인 소켓 파일을 연다. 커널이 파일을 통해 데이터를 넘기므로 패킷 처리와 권한 제어가 포트 방식과 다르며, 여러 인스턴스를 같은 머신에서 나눠 쓸 때 유용하다.
  3. 추가 옵션으로 대기 방식 조정같은 bind 줄에 v6transparent , interface , deferred 같은 값을 붙일 수 있고, 여러 주소를 여러 bind 줄로 나열하면 한 프록시가 여러 포트와 주소를 동시에 받을 수 있다.

server 지시문으로 백엔드 서버를 등록하고, check·rise·fall·fastinter·downinter 같은 값으로 상태 판정 주기와 UP/DOWN 전이를 정하는 설정.

1문제 상황

백엔드 서버가 여러 대라면 HAProxy 는 그중 하나를 골라 연결해야 한다. 그런데 서버는 언제든 내려가거나 응답이 느려진다. 접속 시점에 살아 있는지 미리 알 수 없어, 요청을 이미 죽은 서버로 보내 타임아웃까지 기다리는 일이 생긴다.

또한 상태를 한 번 판정하면 안 된다. 응답이 잠깐 지연된 서버를 곧바로 제외하면 용량을 잃고, 망가진 서버를 오래 붙잡으면 응답이 느려진다. 어느 정도 성공하고 실패해야 상태를 바꾸는지 기준이 필요하다.

2핵심 질문

백엔드 서버를 등록하고,健康 상태를 어떤 기준으로 주기마다 판정해 트래픽을 보낼지 결정하는가?

3동작 예시

server s1 10.0.0.11:8080 check port 8080 rise 2 fall 3 inter 1s 라면 HAProxy 는 1초마다 상태 확인을 보내고, 연속 2회 성공하면 UP, 연속 3회 실패하면 DOWN 으로 바꾼다. DOWN 인 s1 은 새 요청을 받지 않고, 이미 붙어 있던 연결만 정리된다.

4동작 과정

  1. 서버 등록과 확인 주기 설정server 이름 주소 [check] 로 서버를 나열하고, inter 2s 로 확인 주기를, fastinter 1s 로 실패 중에는 더 자주 확인하도록, downinter 5s 로 DOWN 상태일 때는 간격을 늘리도록 정한다. 확인 주기를 바꾸면 장애가 나도 그만큼 늦게야 상태가 바뀐다.
  2. UP·DOWN 전이 기준 지정rise 3 은 연속 3회 성공을, fall 3 은 연속 3회 실패를 기준 삼는다. on-marked-down shutdown-session 을 함께 쓰면 DOWN 이 되는 순간 그 서버에 붙어 있던 세션까지 끊어 버린다.
  3. 수동 제어와 하위 서버 그룹disabled 로 처음부터 트래픽을 막고, backup 으로 유지보수 중인 서버를 대기군으로 두며, server s1 아래에 server-template 로 여러 대를 한꺼번에 등록해 두면 같은 설정을 반복하지 않아도 된다.

1문제 상황

백엔드 서버가 특정 인터페이스의 주소만 바인딩하거나 방화벽이 특정 출발지만 허용하면, HAProxy 가 아무 주소로 연결을 시도해도 실패한다. 이때 어느 주소를 출발지로 쓸지 설정으로 지정하지 않으면 연결 단계에서 자꾸 끊긴다.

한편 여러 프록시가 같은 서버를 공유할 때는 각 프록시가 서로 다른 출발 포트 범위를 써야 한다. 출발 주소를 고정해 두면 같은 서버에서 어떤 클라이언트 요청이 어디로 들어왔는지 알 수도 없다.

2핵심 질문

3동작 예시

server s1 10.0.0.11:8080 check send-proxy 라고 두면 8000~8100 범위의 출발 포트에서만 서버로 나간다. http-request set-header X-Forwarded-For %[src] 를 추가하면 서버는 연결 출발지 대신 원래 클라이언트 주소를 받는 헤더를 얻게 되고, 접근 로그에 그대로 남는다.

4동작 과정

  1. 연결 방식과 출발 주소 지정connect 지시문으로 TCP 연결을 직접 만들어 서버로 보내고, source 로 서버가 보는 출발 IP·포트를 다시 쓴다. 주소가 여러 개면 공백으로 나열해 회전 선택되며, 주소 앞에 usesrc 를 붙이면 클라이언트 원래 주소를 출발 주소로 물려줄 수 있다.
  2. 포트 범위 분산과 프로토콜 전달send-proxy 는 서버에 연결 정보를 먼저 한 줄 보내는 PROXY 프로토콜을 써서 여러 프록시가 같은 서버·같은 포트를 공유할 수 있게 한다. send-proxy-v2 를 쓰면 같은 정보를 2번 형식으로 보낸다.
  3. 클라이언트 정보 상속option forwardfor 를 켜면 클라이언트 주소를 X-Forwarded-For 헤더에 이어 붙여 보내고, http-request set-header 로 원하는 이름의 헤더를 직접 만들어 서버에 넘길 수 있다. 이 정보는 접속 로깅과 권한 판정에 그대로 쓰인다.

SSL/TLS 연결과 암호화 정책

bind·server 줄의 ssl·crt·ca-file·verify·ciphers·alpn 같은 지시문으로 암호화 연결을 활성화하고 허용할 암호 스위트와 인증서를 정하는 설정.

1문제 상황

클라이언트와 백엔드 사이를 평문으로 두면, 그 구간을 지나는 데이터는 아무도 못 읽을 수 없다. HTTP 는 요청 내용과 인증 정보가 그대로 드러나기 때문에 그대로 노출하면 안 된다. 그렇다고 종단 간 암호화를 각 연결에 직접 적용할 수는 없고, 중간에서 종료하는 지점이 따로 필요하다.

암호를 쓴다고 안전하지 않다. 약한 암호 스위트를 허용하면 강제 해독이 가능하고, 클라이언트가 보낸 인증서를 아무것도 확인하지 않고 받으면 상대가 누구인지 검증할 수 없다. 어떤 인증서를 어디에 쓰고 무엇을 허용할지 정하는 구성이 필요하다.

2핵심 질문

어느 구간을 암호화하고, 어떤 인증서를 어떤 역할로 쓰며, 어떤 암호 스위트와 클라이언트 인증 수준을 허용할 것인가?

3동작 예시

프론트엔드에 bind :443 ssl crt /etc/ssl/certs/site.pem alpn h2,http/1.1 을 두면 해당 인증서로 TLS(전송 계층 보안) 연결을 받고, 협상된 ALPN 값에 따라 HTTP/2 와 HTTP/1.1 을 함께 처리한다. 백엔드에는 server s1 10.0.0.11:443 ssl verify required ca-file /etc/ssl/certs/ca.pem 을 두어 클라이언트 인증서와 서버 인증서를 모두 확인한 연결만 쓴다.

4동작 과정

  1. 암호화 구간 활성화bind 와 server 줄에 ssl 을 붙이면 그 구간이 TLS 로 암호화된다. 프런트엔드에서는 crt 로 서버 인증서를, ca-file 로 상대 인증서를 확인할 CA 번들(인증서를 서명한 기관 목록 파일) 을 준다.
  2. 신뢰 수준 지정verify none 은 상대 인증서를 보지 않아 기본값이고, verify optional 은证书이 있으면 확인만, verify required 는 인증서가 없으면 연결을 거부한다. 백엔드 인증서를 고정하려면 ca-file 에 더해 verifyhost 로 호스트명을 확인한다.
  3. 암호 스위트와 프로토콜 조정ciphers 로 허용할 암호 스위트를, ssl-min-ver TLSv1.2 로 최소 버전을, alpn 로 HTTP/2 등 응용 계층 프로토콜 협상을 정한다. 클라이언트 인증을 강제하려면 ssl-client-verify 에 required 를 쓴다.

DNS 리졸버와 서버 이름 해석

resolvers 섹션에 DNS 서버를 등록하고 init-addr·check resolvers 같은 지시문으로 백엔드 서버 이름을 주기적으로 재해석하게 하는 설정.

1문제 상황

백엔드 서버를 IP 주소로만 적으면, 주소를 바꾼 서버마다 설정을 손봐야 한다. 서버 이름으로 적어도 문제는 남는다. 이름은 HAProxy 가 시작할 때 한 번만 해석하면 되므로, 이후 IP 가 바뀐 사실을 모르는 채로 오래된 주소로 트래픽을 보낸다.

새로 추가된 서버나 빠진 서버의 IP 목록이 바뀌어도 마찬가지다. DNS 서버 목록을 설정하지 않으면 외부 도메인 이름을 해석할 수 없어 서버를 이름으로 등록하는 방식 자체가 불가능하다.

2핵심 질문

3동작 예시

resolvers dns 섹션에 nameserver ns1 10.0.0.2:53 을 등록해 두면, server s1 app.internal:8080 check resolvers dns init-addr none 을 읽은 HAProxy 는 app.internal 의 IP 목록을 주기적으로 다시 조회해 새 IP 를 서버 줄에 반영한다. none 이 없으면 A 레코드가 없었을 때 컴파일 단계에서 오류가 나고, last,libc,none 을 주면 기존 해석 결과를 쓰다가 없으면 libc 방식, 그것도 없으면 실패로 처리한다.

4동작 과정

  1. 리졸버 섹션 등록resolvers 이름 블록에 nameserver 로 DNS 서버 IP·포트를 나열하고, resolve_retries 와 timeout 으로 질의 실패 시 재시도 횟수와 대기 시간을 정한다. 이 이름은 서버 줄에서 resolvers 값으로 참조한다.
  2. 재해석 주기와 주소 확보 방식 지정check resolvers dns resolve_interval 10s 로 DNS 조회 전용 주기를 따로 두거나, hold 로 새 결과가 나올 때까지 남겨 두는 방식을 고른다. init-addr 는 시작 시 이름을 못 찾았을 때 어떤 IP 를 쓸지 정한다.
  3. 백엔드에 적용server 이름 도메인:포트 check resolvers dns 처럼 서버 줄에 resolvers 를 붙여야 백엔드가 등록된 DNS 로 이름을 조회한다. fqdns 를 함께 쓰면 IP 목록의 순서를 유지한 채 사용하기 위해 완전한 이름을 매번 질의한다.

1문제 상황

2핵심 질문

3동작 예시

4동작 과정

  1. inspect-delay 로 검사 시점 지정tcp-request inspect-delay 5s 는 요청이 도착한 뒤 5초까지만 기다리며 그때의 데이터만 대상으로 삼으라고 정합니다. 이 시간이 지나면 남은 지시문을 강제로 실행하고 뒤쪽 연결을 진행합니다. tcp-response inspect-delay 는 같은 방식으로 백엔드 응답을 기다렸다 검사합니다.

  3. analyze 단계에서 상태 변경tcp-request content set-var(txn.marker) str(...) 처럼 검사한 결과에 따라 샘플 값이나 변수에 상태를 남길 수 있습니다. 그 값을 뒤의 ACL 이나 백엔드 선택 조건에서 이어서 쓰면, 같은 흐름 안에서 한 번 읽고 결정한 정보를 재사용할 수 있습니다.

ACL 기본과 자료형별 매칭

ACL은 요청에서 가져온 값을 정해진 기준과 비교해 참·거짓을 내려 주는 조건 하나이고, 비교하는 값의 자료형에 따라 불리언·정수·문자열·정규식·데이터 블록·IP 주소용 매칭 방식을 각각 골라 쓴다.

1문제 상황

프런트엔드가 받은 요청마다 백엔드를 다르게 골라야 할 때, 예전에는 요청을 여러 규칙에 걸어 직접 하나씩 비교하는 방식으로 조건을 나눴습니다. 조건이 늘어날수록 설정이 길어지고, 같은 값을 규칙마다 다시 꺼내야 해서 유지하기 어려웠습니다. 어떤 값이 어떤 기준을 넘어야 하는지도 일일이 적어야 했습니다.

2핵심 질문

요청에서 꺼낸 값이 기준에 맞는지 참·거짓으로만 판정해 주는 통짜 조건을 어떻게 정의하는가?

3동작 예시

요청 경로가 /api/orders 라면 acl is_api path_beg /api 라고 정의합니다. 이 조건은 path_beg 라는 비교 방식(경로가 이 문자열로 시작하는가)으로 경로를 대조해 참·거짓만 돌려줍니다. 다른 지시문에서는 is_api 라는 조건 이름만 부르면 되므로 비교 방법을 다시 쓰지 않습니다.

4동작 과정

  1. 값을 먼저 꺼내고 기준을 나중에 비교path hdr method src 같은 fetch 지시문으로 값을 이름 붙은 샘플로 꺼냅니다. 그 다음 acl <이름> <비교 방식> <기준값> 형태로 조건 하나를 정의합니다. 조건 자체는 요청마다 실행되는 코드라기보다 설정에 미리 적어 둔 판정 규칙입니다.
  2. 자료형에 맞는 비교 방식 선택불리언은 참·거짓을, 정수는 수치 범위(src_port, hdr_len, req_size)를, 문자열은 완전 일치·접두사·접미사·부분 포함·정규식을 씁니다. 바이트 블록 비교(req_sha1, path_sub)와 IP 대역 비교(src, dst)도 같은 방식으로 붙습니다.
  3. 이름만 참조해 재사용정의한 조건 이름은 use_backend http_request deny http-request set-header 같은 어떤 지시문에서도 그대로 부를 수 있습니다. 여러 프런트엔드나 여러 규칙이 같은 기준을 공유하면 조건 정의를 한 곳에서만 고치면 됩니다.

여러 ACL 을 and·or·unless 같은 조건문으로 이어 붙여 하나의 복합 조건으로 만든 뒤, 그 참·거짓에 따라 라우팅이나 처리를 나누는 방법이다.

1문제 상황

2핵심 질문

3동작 예시

4동작 과정

  1. 비교 방식 그대로 이어 붙이기if 뒤에 조건 이름과 AND OR XOR EXCL 같은 연산자를 이어 씁니다. 각 피연산자는 조건 이름이거나 괄호로 묶은 하위 조건문이라서, (a OR b) AND c 처럼 우선순위를 지정할 수 있습니다.
  2. 부정과 기본값으로 반대쪽도 함께 정의unless 는 조건이 거짓일 때 참이 되는 연산자입니다. 예외 경로를 허용할 때 if !is_banned 나 unless is_blocked 라고 적어, 참인 경우만 따로 다루지 않아도 되게 합니다.
  3. 결과에 따라 처리 갈라내기복합 조건 하나를 use_backend 에 넘기면 참일 때만 그 백엔드로 보내고, 거짓이면 다음 지시문으로 넘어가 기본 경로를 따릅니다. http_request deny redirect set-header 같은 지시문에도 같은 방식으로 붙습니다. 조건문을 여러 개 나열하면 위에서부터 처음 참인 지시문이 적용됩니다.

1문제 상황

조건에 쓸 수 있는 값은 연결의 어느 깊이까지 파고들었느냐에 따라 달라집니다. TCP 헤더까지만 읽은 시점에는 클라이언트 주소와 포트 정도밖에 없고, 암호화가 걸려 있으면 그 위의 내용은 아예 볼 수 없습니다. 그런데 설정에서는 아무 구분 없이 샘플 이름을 쓰기 때문에, 그 값이 언제부터 존재하는지 모르고 쓰면 아무 조건도 참이 되지 않는 설정이 조용히 통과합니다.

2핵심 질문

어느 시점까지 데이터를 읽었는지에 따라 샘플을 계층별로 나누어, 얻을 수 있는 정보가 없는 잘못된 참조를 피하려면 어떻게 해야 하는가?

3동작 예시

src 는 가장 먼저 얻을 수 있는 값이라 tcp-request content 단계나 tcp-request inspect-delay 로 기다린 뒤에도 항상 쓸 수 있습니다. 반면 HTTP 요청 첫 줄을 파싱해야 얻는 req 샘플은 스트림 모드에서 처음 몇 바이트가 이미 지나간 뒤라면 비어 있습니다. 그래서 L6 샘플은 반드시 http-request 규칙 안에서만 씁니다.

4동작 과정

  1. L4TCP 와 IP 헤더에서 얻는 값** — src dst src_port dst_port req_ssl_hs_type 은 IP 헤더와 TCP 헤더에 들어 있는 값입니다. 연결이 성립한 순간부터 있으므로 가장 이른 단계의 조건에 씁니다. TLS 를 쓰면 암호화 때문에 그 위의 내용은 읽을 수 없습니다.
  2. L5세션과 방화벽에서 얻는 값** — sess 와 fc_* 계열 샘플은 커넥션 단위 상태를 나타냅니다. sess_shutdown 처럼 종료 중인지로 조건을 만들거나, 프런트엔드나 백엔드 측의 방화벽에서 추가한 정보를 꺼내 쓸 수 있습니다. 계층이 올라갈수록 값이 늘고, 그만큼 준비가 늦어집니다.
  3. L6버퍼에 실제로 담긴 데이터** — req.payload res.payload req_size res_size 는 읽어 들인 버퍼의 내용을 꺼냅니다. 일반 모드에서는 HTTP 헤더까지 파싱된 뒤에야 의미가 있고, 스트림 모드에서는 tcp-request content 나 inspect-delay 로 읽기를 멈춰 둔 만큼만 담겨 있습니다.

4동작 과정

키-값 쌍을 담은 맵 파일을 읽어 요청에서 뽑은 값을 다른 문자열이나 주소로 바꿔 내보내는 변환 표.

요청에서 뽑은 값에 따라 다른 문자열을 붙여 보내고 싶을 때가 있다. 여러 값을 나열하면 http-request set-header 안에 조건이 계속 쌓여 설정이 한 덩어리로 길어진다. 값이 바뀔 때마다 설정을 고쳐야 하고, 조건이 많아지면 어느 분기가 쓰이는지 파악하기 어렵다.

2핵심 질문

키와 값의 대응표를 따로 만들어 두고, 요청에서 얻은 키로 값만 골라서 치환할 수 있을까?

3동작 예시

convert_colour 이라는 맵 파일에 red 01ff00ff, green 00ff00ff, blue 0000ffff 세 줄을 넣어 둔다. 요청 쿼리의 colour 값이 blue 면 HAProxy는 세 줄 중 두 번째 필드인 0000ffff 를 꺼내 헤더 값으로 넣는다. 일치하는 키가 없으면 map_beg 기본값이 쓰인다.

4동작 과정

  1. 맵 파일 정의map_beg(접두사 일치), map_exact(완전 일치), map_ip(키가 IP) 같은 지시자로 키-값 쌍을 담은 파일을 지정하고, map_dom 등 다른 입력 형식도 고른다.
  2. 키 추출http-request 지시자 안에서 샘플 페치로 요청의 일부를 변수로 저장한다. 경로·쿼리·헤더·쿠키에서 값을 꺼내 온다.
  3. 값 치환set-var 로 맵을 참조해 대응되는 값을 변수에 담고, set-header 같은 지시자로 요청이나 응답에 반영한다. 없는 키는 맵의 기본값 지시자로 처리된다.

4동작 과정

  1. 필드 선택%ci, %si, %b, %s, %t 같은 로그 변수로 필요한 값만 골라 나열한다. 없는 값은 - 로 채워져 나올 수 있다.
  2. 포맷 지정자 적용%[req.hdr(host)] 로 헤더를, %{+Q}o 로 인용 표시를, %b 와 %B 로 바이트 수를 원하는 형태로 조립한다. +Q 처럼 부호를 붙이지 않으면 원본 문자열이 그대로 들어간다.
  3. 전역 또는 프록시별 적용global 섹션의 log-format 은 전체에, proxy 섹션의 log-format 은 그 프록시에만 적용된다. no-log 를 주면 상위 설정을 덮어 로그를 끌 수 있다.

같은 클라이언트의 요청을 항상 같은 백엔드 서버로 보내려면, 매 요청마다 클라이언트 정보를 서버 목록과 비교해 어느 서버에 붙을지 직접 계산해야 한다. 이 계산에 드는 CPU 비용을 매번 감당하기 어렵고, 설정을 바꿀 때마다 매핑 방식을 손봐야 한다. 이 대응 결과를 어디에 저장할지 지정할 수단도 없다.

2핵심 질문

클라이언트 키와 서버 번호를 미리 계산된 대응표에 저장하고, 이 대응표를 메모리 안에서 직접 관리할 수 있을까?

3동작 예시

4동작 과정

  1. 테이블 선언프로시 섹션에서 stick on-table 로 스틱 테이블을 선언한다. size 로 가용 메모리 크기를 정하고, 카운터를 같이 쓰려면 tablesize 와 카운터 이름, 주기를 나열한다.

1문제 상황

접속자 수를 제한하거나 같은 사용자를 같은 서버로 모으려면, 지금 몇 명이 붙어 있는지와 누구인지 알아야 한다. 하지만 커넥션은 들어왔다가 나가고, 사용자는 IP도 바뀌고 브라우저 탭도 여러 개라 한 사람이 몇 번인지 세기 어렵다. 요청을 보낼 때마다 숫자를 다시 세는 것도 부담이다.

그래서 요청을 하나씩 전부 기록해 두면 저장 공간과 처리 시간이 함께 커진다. HAProxy는 모든 요청 목록을 남기는 대신, 요청마다 몇 개의 숫자만 올려 두는 방법을 택한다.

2핵심 질문

3동작 예시

스픽 테이블 엔트리에 http_req_cnt 같은 카운터 필드를 붙여 두고, IP 하나에 해당하는 엔트리 값에 1을 계속 더한다. 3초 뒤 그 값을 3으로 나누면 그 IP의 초당 요청 수가 나오고, 세션 번호만 비교하면 지금 열려 있는 연결 수를 바로 알 수 있다.

4동작 과정

  1. 엔트리 생성접속 기준으로 삼을 값(소스 IP, 주소와 포트 조합 등)을 해시해 스틱 테이블의 해당 슬롯에 엔트리를 만든다. 같은 값은 항상 같은 슬롯으로 가고, 슬롯 수를 정해 두면 메모리가 무한정 늘어나지 않는다.
  2. 카운터 누적http_req_cnt(요청 수), conn_cnt(누적 연결 수), bytes_in·bytes_out(왕복 바이트) 같은 필드에 요청마다 값을 더한다. 트래커 키(sc0_get_gpt0 등)에는 조회 대상인 접속 기준을 담고, 그 안에 http_req_rate(최근 시간대 요청 수) 같은 rate 필드가 계산되어 들어간다.
  3. 조건 판단과 회전track-sc로 커넥션 단계에서만 세거나, http-request track-sc로 요청을 세는 지점을 정한다. table 크기를 expire 시간만큼씩 잘라내 오래된 엔트리를 지우고, store-rate 설정으로 rate 값이 몇 초 단위 평균으로 계산되는지 정한다.

4동작 과정

  1. 학습(기록)track-sc를 지시문에 붙이면 해당 연결을 닫을 때까지 스틱 테이블에 누적된다. track-count는 카운터만 올리고, http-request track-sc는 매 요청마다 deny_status나 maxconn 같은 상한에 걸리면 http-request deny로 즉시 거절한다.
  2. 검사(조회)stick-table type_ip table size로 선언한 테이블을 stick match나 stick on 뒤에 써서 현재 엔트리를 찾는다. track-sc가 만든 값은 그 안에서 track.count(지금까지 세어진 횟수)와 track.gpt(연결 ID 목록)으로 읽힌다.
  3. 참조로 공유stick on은 브라우저 쿠키나 URL 쿼리에 테이블 ID를 심어, 첫 요청이 만든 ID를 클라이언트가 다시 들고 오는 방식이다. 서버를 늘릴 때도 같은 ID를 쓰므로 사용자가 서버를 옮겨 다닐 필요가 없다.

파일 경로만 적으면 그 경로의 파일을 그대로 쓰고, 여러 인증서를 손대야 할 때 그 묶음을 손보지 않게 관리할 방법이 필요했다.

2핵심 질문

3동작 예시

4동작 과정

  1. 파일 읽기와 파싱crt 가 가리키는 파일을 열어 PEM 형식의 인증서 체인과 개인키를 분리한다. 읽은 키 쌍은 비밀키 파일 경로 순으로 정렬해 같은 파일이 중복 지정돼도 한 번만 로드한다.

1문제 상황

443 포트 하나로는 여러 도메인을 동시에 받을 수 없다. 그런데 IP 주소를 기준으로 인증서를 나누면 같은 IP에 여러 도메인이 있을 때 어느 것을 내줄지 알 수 없다. 인증서를 도메인마다 bind 를 여러 개 파서 나눠 받으면 같은 포트와 IP 가点上에서 겹쳐 하나의 어댑터로는 불가능하다.

그래서 한 소켓에서 어떤 인증서를 낼지 골라야했고, 인증서를 갈아꿀 때 그때마다 서비스를 내리는 방법밖에 없었다.

2핵심 질문

3동작 예시

4동작 과정

  1. 인증서 목록 등록bind 에 crt 를 여러 번 나열하면 하나의 포트에서 여러 인증서를 제공할 수 있다. crt-list 로 묶은 목록을 대신 심어도 같은 결과가 된다.
  2. SNI 로 선택클라이언트가 준 이름을 해시해 등록된 인증서의 subjectAltName(인증서가 다룰 수 있는 도메인 목록)과 대조해 대응되는 인증서를 고른다. 일치하는 이름이 없으면 기본 인증서를 내고, 지원하지 않는 버전이면 알림 없이 연결을 끊는다.
  3. 반영과 교체파일을 새 인증서로 덮어쓴 뒤 reload 하면 새 프로세스가 그 파일을 다시 읽어 새 인증서를 미리 올린다. 기존 프로세스는 열려 있는 연결을 마친 뒤 교체되고, SNI 캐시를 갱신한 신호가 들어오면 세션 재사용 동안에도 새 인증서가 쓰인다.

상대가 낼 만한 인증서를 어디까지 믿을지 정하지 않으면, 아무 인증서나 하나 내는 것으로 인증이 끝나고 말았다.

3동작 예시

인증서에 CA 의 OCSP 응답을 미리 끼워 넣어 클라이언트가 폐기 여부를 즉시 확인하게 하고, 주기가 되면 새 응답을 받아 교체하는 것.

1문제 상황

인증서를 받은 클라이언트는 그 인증서가 폐기되었는지 CA 에 직접 물어보지 않는다. 대부분 확인을 생략하거나 브라우저로만 확인한다. 그래서 누군가 인증서를 빼돌려 폐기했어도, 그동안 클라이언트는 그대로 신뢰하고 계속 접속한다.

한편 HAProxy가 이 확인을 대신 하려면 매 연결마다 CA 에 요청을 보내야 해서 느려지고, CA 부하도 커진다.

2핵심 질문

3동작 예시

기존의 응답 본문 저장 기능은 저장과 만료를 HAProxy 밖에서 관리해야 했습니다. 그 사이 생긴 파일이 최신 데이터인지, 어디까지 유효한지 HAProxy는 알지 못했고, 곧바로 활용하기 어렵습니다.

3동작 예시

4동작 과정

  1. 저장 대상 결정http-request cache 지점에서 cache 이름을 지정하고, 어떤 응답을 저장할지 조건으로 정합니다. 응답의 HTTP 상태 코드, 헤더 값, 본문 길이, 특정 요청 헤더 존재 여부, URL 일치 여부 등을 조건으로 씁니다. 이 조건을 통과한 요청만 캐시 후보가 됩니다.
  2. 메모리에 저장요청이 http-response cache 지점을 통과하면 HAProxy는 응답 본문과 헤더를 메모리에 저장합니다. 저장 용량과 최대 저장 개수를 넘으면 지정된 방향(가장 오래된 것부터 또는 가장 적게 쓰인 것부터)으로 밀어내며, 각 항목에 수명 시간을 함께 두어 시간이 지나면 사용되지 않고 정리됩니다.

3동작 예시

4동작 과정

  1. FastCGI 요청 생성fcgi-app 백엔드로 지정된 요청은 HTTP를 FastCGI 규약으로 바꿉니다. 헤더는 PARAMS 스트림에 바이트 길이-값 쌍으로 이어 붙이고, 요청 본문이 있으면 그 뒤에 STDIN 스트림으로 붙여 같은 연결로 보냅니다. PARAMS와 STDIN을 하나의 record로 합칠지 여부는 set-param 지시자로 정합니다.
  2. 응답 record 해석애플리케이션이 돌려준 record를 차례대로 읽습니다. FCGI_STDOUT(애플리케이션이 보낸 응답 내용), FCGI_STDERR(오류 메시지), FCGI_END_REQUEST(처리 완료 표시)를 구분해 처리하고, 오류 메시지는 HAProxy 로그로 남깁니다.
  3. HTTP 응답으로 복원 후 회신첫 STDOUT record에 들어 있는 HTTP 상태 줄과 헤더를 분리해 응답 헤더로 만들고, 이어지는 STDOUT 내용은 그대로 응답 본문으로 붙입니다. 뒤이어 나온 다른 백엔드의 STDOUT은 대기 중인 다른 클라이언트 요청의 응답으로 전달해 하나의 소켓으로 여러 요청을 처리합니다.

tune.bufsize, tune.maxconn 등 tune.* 지시문으로 버퍼 크기·연결 한도·스레드·타임아웃 등 전역 기본값을 정해 성능을 끌어올리는 영역이다.

1문제 상황

기본 설정으로 돌아간 HAProxy는 문서화된 기본값을 그대로 사용한다. 그래서 두 가지가 동시에 나타난다. 버퍼가 작아서 큰 요청이나 큰 응답이 들어오면 잘려 나가거나 재전송이 반복되고, 연결 한도가 낮게 잡혀 있어 피크 시간대 동시 요청이 많으면 대기열이 넘치고 연결이 거부된다.

frontends와 backends에 나열한 설정은 특정 경로의 동작만 바꾼다. 반면 모든 프런트엔드와 백엔드에 공통으로 적용되는 기본값을 한 번에 올리고 내릴 방법이 없다. 그래서 tune.* 지시문을 사용한다.

  3. 타임아웃 기본값 정하기tune.http.* , tune.ssl.* , tune.rcvbuf.client·server 로 대기 시간과 소켓 버퍼 크기의 기본값을 정한다. 이 값들이 모든 리스너와 서버 연결에 시작값으로 적용되어 별도 지정이 없는 경로의 동작을 통일한다.

동시 처리할 스트림 수를 제한해 성능을 지키면서, 위조·비정상 HTTP 요청을 거부해 DoS성 공격을 막는 지시문을 다루는 영역이다.

1문제 상황

HTTP/2와 HTTP/3은 하나의 TCP 연결 안에 여러 요청을 동시에 흘려보내는 방식이다. 이 구조 덕분에 연결을 새로 여는 비용이 줄고 응답이 빨라진다. 그런데 상대는 요청 개수를 제한해 주지 않는다. 아주 적은 수의 연결로 수만 개 요청을 한꺼번에 밀어넣으면 HAProxy는 요청 처리에 쓸 메모리와 CPU를 그만큼 소모한다.

이전 방식인 HTTP/1.1에서는 한 연결당 동시 요청이 사실상 하나였기 때문에 이런 압박이 생기지 않았다. 다중 요청이 가능해지면서 나타난 한계이므로, 스트림 수를 제한하는 지시문과 비정상 요청을 거부하는 지시문이 따로 필요하다.

2핵심 질문

연결 하나에 몰려드는 요청을 제한하고 위조된 비정상 요청을 거부해 다른 사용자의 요청까지 막히는 상황을 어떻게 막을 수 있을까?

3동작 예시

http-request deny deny_status 400 if { req_ssl_sni -i attacker.example }을 프런트엔드에 두면, TLS 협상 때 클라이언트가 보낸 서버 이름이 attacker.example와 정확히 같을 때 그 요청을 처리하지 않고 400으로 즉시 돌려준다. 백엔드로는 한 바이트도 전달되지 않는다.

프런트엔드에 http-request deny if { req.ssl_hello_type 1 } !{ src_port 443 }처럼 두면 TLS hello를 보냈는데 소스 포트가 443이 아닌 연결, 즉 프록시 서버로는 정상적인 경로가 아닌 요청을 같은 방식으로 거른다.

4동작 과정

  1. 동시 스트림 수 제한tune.http.maxhdr, http-request deny 위에 http_max_conn·http-request set-conn 계열로 적용되는 스트림 한도나 tune.h2.max-concurrent-streams, tune.h2.max-frames, tune.h2.max-header-list-size 같은 tune.h2.* / tune.h3.* 지시문으로, 한 연결에서 동시에 처리할 스트림 수와 프레임·헤더 크기를 상한으로 정한다.
  2. 요청 조건 거부http-request deny (무조건 거부), http-request reject (지정한 오류로 거절), http-request set-conn (연결에 값을 표시) 같은 지시문으로 조건에 맞는 요청을 프록시 라인에서 끊는다. req.ssl_sni, src_port, req.hdr(host) 같은 페치(요청에서 뽑아 낸 값)를 조건으로 쓴다.
  3. 시도 횟수 제한http-request deny 위에 설정하는 http-request track-sc0 와 track-sc0 table 을 함께 쓰면, 동일 출처에서 일정 횟수 이상 규칙에 걸린 요청을 누적해 세어 일정 임계치를 넘긴 출처 전체를 차단 상태로 올린다. 앞서 개별 요청을 걸어 낸 것과 별개로, 소스 단위의 무차별 대입과 변조된 요청을 막는다.

그 밖에 리눅스에서는 클라이언트와 서버가 같은 장비에 붙어 있을 때 원래 목적지 주소로 직접 패킷을 보내게 만드는 기술, 여러 코어를 어떻게 나눠 쓸지 정하는 기술이 OS에 있다. HAProxy는 이 커널 기능에 연결되는 지시문을 따로 모아서 제공한다.

  3. 코어 배정 고정nbproc, nbthread , cpu-map/thread-option 계열로 프로세스·스레드 수를 정하고 어떤 스레드가 어떤 CPU 코어를 쓰는지 지정해, 커널 스케줄러가 옮겨 타는 것을 막고 캐시 지역성을 유지한다.

  2. 스크립트 안에서 요청·응답 다루기스크립트는 리퀘스트·리스폰스 객체에서 소스 주소, HTTP 헤더, 쿠키, 샘플 데이터를 읽고 헤더를 추가하거나 상태를 바꾸는 작업을 수행한다. 이 작업이 끝나면 HAProxy가 같은 파이프라인을 이어서 진행한다.

HAProxy 구동과 기동 검증

haproxy 바이너리를 데몬/포그라운드로 띄우고 설정 파일 검증(-c)을 통과시킨 뒤 정상 기동과 리스닝 상태를 확인하는 일련의 절차.

1문제 상황

설정 파일만 작성해서는 HAProxy가 동작한다고 볼 수 없다. 문법 오류, 참조한 백엔드 이름 없음, 파일 권한 문제 중 무엇이든 한 곳만 틀려도 프로세스가 아예 뜨지 않거나, 뜨더라도 리스닝 포트를 열지 않는다. 특히 global 섹션의 chroot나 user 설정이 잘못되면 검증 단계에서 파일을 찾지 못한다는 형태로 드러난다.

게다가 이미 서비스 중인 서버에서 설정만 바꿨다면, 올바른 설정인지 먼저 확인하지 않고 재시작하면 그 순간부터 트래픽이 끊긴다. 그래서 실행 전에 검증을 통과시키는 과정이 반드시 앞에 온다.

2핵심 질문

설정 파일을 실제로 띄우기 전에 문법과 참조 오류를 찾아내고, 띄운 뒤 리스닝 상태까지 확인하는 절차는 어떻게 되나?

3동작 예시

haproxy -c -f /etc/haproxy/haproxy.cfg를 실행하면 HAProxy는 설정을 읽고 검증만 한 뒤 종료한다. 출력에 Configuration file is valid이 뜨면 문법과 참조에 문제가 없다는 뜻이고, 오류가 있으면 어느 줄의 어떤 지시문이 문제인지 line 42- 같은 위치와 함께 표시된다.

검증을 통과했다면 haproxy -Ws -f /etc/haproxy/haproxy.cfg -p /run/haproxy.pid & 로 기동한다. 이후 ss -lntp 로 확인하면 0.0.0.0:80 이나 0.0.0.0:443 리스닝이プロセス 번호와 함께 보인다.

4동작 과정

  1. 설정 검증haproxy -c (check 전용 모드)에 설정 파일 경로를 줘 읽기만 하고 종료하게 한다. -f 가 파일, -C <file> 가 커스텀 디렉터리 안의 기본 파일, -V 가 상세 출력, -q 가 경고 숨김이다. 검증 출력에 Configuration file is valid 가 떠야 다음으로 넘어간다.
  2. 기동haproxy -f <cfg> 로 실행한다. -D (daemon, 백그라운드로 전환), -Ws (master-worker 구조와 다중 스레드로 기동, 재적재 시 마스터가 워커를 교체하며 기존 연결을 이어받음), -p <file> (PID 파일 경로), -db (디버그 모드, 백그라운드 전환 없이 포그라운드로 실행하며 로그를 바로 확인) 중 운영 방식에 맞는 옵션을 함께 준다.

1문제 상황

HAProxy는 서비스 중인 상태에서 설정 파일을 바꿔도 아무 일도 일어나지 않는다. 프로세스는 이미 읽어 둔 설정으로 계속 동작하기 때문에, 파일을 편집했다고 가정하고 기다리면 반영되지 않는다. 반영하려면 프로세스를 다시 띄워야 하는데, 이때는 진행 중인 연결이 끊어진다.

long-lived 연결(장시간 유지되는 연결)은 끊어진다는 사실이 특히 문제다. 짧은 요청은 끊겨도 사용자가 체감을 거의 못하지만, 이미 올라간 세션이나 지속 중인 다운로드, 웹소켓은 중간에 잘리면 복구되지 않는다. 설정 변경을 적용하면서 기존 연결을 끝까지 살려 두는 방법이 필요하다.

2핵심 질문

기존에 처리 중인 연결을 하나도 끊지 않으면서 새 설정으로 교체하고, 필요하면 정상적으로 종료까지 시킬 수 있는가?

3동작 예시

kill -USR1 $(cat /run/haproxy.pid)을 보내면 그 반대 동작이 일어난다. 새 연결을 받을 워커를 즉시 내리고, 기존 워커들은 남아 있는 연결을 마저 처리한 다음 종료한다. 검증을 통과시킨 haproxy -c 결과를 파일로 받아 -f 에 넘기면 검증 없는 재적재가 되지 않는다.

4동작 과정

  1. 재적재(reload)kill -USR2 <pid> (master-worker 기동 시) 또는 haproxy -sf <pid> 로 기존 프로세스에 새 설정을 넘긴다. 먼저 haproxy -c -f <cfg> 로 검증을 통과시킨 설정을 넘기고, 새 워커가 리스닝을 넘겨받은 뒤 기존 워커는 대기 중인 연결을 마저 처리하고 종료한다.
  2. 소프트 스톱(soft stop)kill -USR1 <pid> (master-worker 기동 시) 또는 haproxy -W -b <pid> -p <pidfile> 로 실행한다. 새로운 워커를 띄우지 않고 리스닝만 닫아, 이미 들어온 연결만 끝낸 뒤 프로세스를 내린다. 핫스텝을 없앨 때 쓴다.
  3. 즉시 종료와 상태 확인kill -TERM <pid> (빠르고 매끄러운 종료, 마스터는 워커 종료 완료를 기다림), kill -USR1 와 kill -QUIT <pid> (즉시 중단) 로 강제 종료할 수 있다. graceful shutdown state(정상 종료 상태)에서는 중계 중인 데이터를 ��로 내보내고 연결을 닫은 다음, timeout seconds(종료 대기 시간) 동안만 유지된다. 종료 후 프로세스와 리스닝 포트가 모두 사라졌는지 확인한다.

1문제 상황

HAProxy는 클라이언트 연결 하나마다 소켓을 열고, 그 소켓마다 버퍼와 상태 정보를 메모리에 붙들고 있어야 합니다. 그런데 OS가 프로세스에 열어 주는 파일 디스크립터 수에는 기본 한계가 있고, 버퍼와 stick table(연결·요청 기록을 저장하는 해시 테이블)의 크기는 설정한 값만큼 실제로 점유됩니다.

쓰레드 수를 늘리면 CPU는 더 쓰지만 한 프로세스가 요구하는 메모리 총량도 함께 올라갑니다. 결국 서버를 준비할 때 미리 정해 둔 값이 실제 부하와 어긋나면, HAProxy는 예상치 못한 지점에서 연결을 거부하거나 메모리 부족으로 죽습니다.

2핵심 질문

3동작 예시

동시 연결이 20만 개인 서비스를 운영한다고 합시다. 설정에 ulimit-n 300000을 걸면 OS가 열어 둔 파일 디스크립터 상한이 30만으로 올라가, 20만 개의 클라이언트 소켓과 20만 개의 백엔드 소켓이 부족 없이 할당됩니다. 여기에 maxconn 250000을 두면 HAProxy는 동시 클라이언트 수가 25만 자리를 넘어가면 새 연결을 더 받지 않습니다.

4동작 과정

  1. 한계 설정ulimit-n으로 프로세스가 열 수 있는 소켓 수를 정하고, maxconn으로 동시 클라이언트 수 상한을 정합니다. 이 두 값이 실제 열릴 소켓 수의 기준선이 됩니다.
  2. 메모리 산정소켓마다 붙는 버퍼 크기와 stick-table size에 저장되는 엔트리당 메모리를 곱해 총 점유량을 계산합니다. nbthread를 늘리면 쓰레드별로 버퍼 사본이 생기므로 그 배수까지 더합니다.
  3. CPU 배분nbthread로 스레드 수를 정하고, nice로 프로세스 우선순위를 조정해 OS 스케줄러가 HAProxy에 CPU를 얼마나 먼저 주는지 제어합니다. 이 세 값이 서버 스펙과 맞아야 안정적으로 동작합니다.

5한 줄 요약

3동작 예시

  2. 안전한 전달log-forward로 로컬에 받은 로그를 다시 지정한 주소로 넘깁니다. HAProxy 자신이 로그를 받아 경유시키는 형태이므로, 다른 데이몬이 514 포트를 이미 쓰고 있어도 충돌하지 않습니다.
  3. 리모트 로그 파이프라인 연결log-forward len으로 넘길 수신 버퍼 크기를 정해 주고, 넘긴 뒤 syslog 데이몬이 중앙 수집기로 보내므로 서버가 여러 대여도 로그가 한 경로로 모입니다.

1문제 상황

서버 하나를 통째로 중지해서 빼내서 설정만 고치고 다시 올리는 방식으로 운영하면, 그 순간 그 서버로 오던 연결은 전부 끊어집니다. 게다가 설정 파일에 적힌 서버 목록을 바꾸려면 전체 재시작 없이는 반영되지 않으므로, 장애난 서버 하나만 즉시 격리하고 되돌리는 작업이 어렵습니다.

또한 어떤 서버가 왜 응답을 안 하는지, 현재 설정이 런타임에 어떤 값으로 읽히고 있는지, 커넥션은 어디에 붙어 있는지를 살아 있는 프로세스 안에서 직접 확인할 방법이 필요해졌습니다.

2핵심 질문

재시작 없이 살아 있는 HAProxy에 명령을 넣어 서버 상태를 바꾸고, 현재 설정을 조회할 수 있는가?

3동작 예시

unix socket에 접속해 set server bk1/srv1 state drain을 보내면 설정 변경 없이 그 서버로 새 요청이 더 이상 배정되지 않고 기존 세션만 자연스럽게 끝납니다. 이어서 show stat를 입력하면 방금 바꾼 서버 상태가 통계 화면에 즉시 반영된 것이 보입니다.

4동작 과정

  1. 제어 채널 개설전역 섹션에서 stats socket /run/haproxy.sock mode 660 level admin처럼 unix socket을 열어 두면, 별도 소켓 클라이언트나 socat으로 그 경로에 명령을 보낼 수 있습니다. 필요하면 TCP 소켓과 ACL로 접속 대상을 제한합니다.
  2. 명령으로 상태와 설정 변경set server <백엔드>/<서버> state ready|maint|drain, set weight, shutdown sessions 등을 넣어 서버를 우아하게 빼내거나 되돌립니다. enable/disable을 쓰면 listen 상태를 켜고 끌 수 있어 설정 파일을 건드리지 않고 ACL을 즉시 반영합니다.
  3. Master CLI로 프로세스 제어master-worker로 실행 중이면 master-socket을 통해 show info, show stat, show proc, reload 등 명령을 보냅니다. Master CLI에는 자동 reload과 재시작 시 이전 세션을 자연스럽게 마치는 hard-stop-after(즉시 종료 시점)이 있어, 설정만 바꾸고 안전하게 재적용할 수 있습니다.

5한 줄 요약

unix socket이나 Master CLI에 show stat·set server disable 같은 명령을 넣어 재시작 없이 설정과 서버 상태를 바꾸는 런타임 제어 수단

보안 격리와 설정 관리 실무

chroot·user·group·Linux capabilities로 권한을 낮추고, 설정 파일을 include와 환경변수로 분리해 관리하는 실무 수칙.

1문제 상황

HAProxy는 클라이언트 요청을 열고, 요청 본문을 읽고, 백엔드 쪽에 다시 연결하며, 관리용 소켓으로 명령도 받는 등 커널 주변의 권한을 상당수 건드립니다. 그래서 기본 상태로 띄우면 root로 실행되며, 설정 실수로 임의 명령이 열리면 그 권한이 그대로 노출됩니다.

한편 설정 파일이 수백 줄씩 한 덩어리로 커지면 프론트엔드 하나를 수정하려고 파일 전체를 열고 찾아야 하고, 환경마다 다른 값(인증 정보, 포트, 서버 주소)을 매번 손으로 고쳐 넣게 됩니다.

2핵심 질문

HAProxy가 꼭 필요로 하는 최소한의 권한만 남기면서, 하나의 설정 파일을 환경별로 갈라 관리할 수 있는가?

3동작 예시

전역 섹션에 chroot /var/lib/haproxy, user haproxy, group haproxy를 두면 시작할 때만 root로 필요한 위치를 잡고, 이후 모든 처리는 haproxy 계정으로 수행됩니다. 또 stats socket ... level admin을 빼고 level user로 두면 소켓 명령도 read 상태 확인 같은 제한된 명령만 동작합니다.

4동작 과정

  1. 권한 축소chroot로 루트 디렉터리를 가두고, user·group으로 실행 계정을 내립니다. 더 줄여야 하면 cap-drop으로 바인딩·파일 잠금 등 필요 없는 Linux capabilities를 버립니다.
  2. 노출 면 제어stats bind 주소와 monitor 권한, stats socket의 level(read/user/admin)과 expose-fd, acl 조합으로 관리 명령이 닿는 범위를 필요한 만큼만 연 뒤 모두 닫습니다.
  3. 설정 분리와 주입include로 공통 섹션(프론트엔드 정의 등)을 밖으로 빼고, environment로 주입한 변수를 $(ENV_VAR) 형태로 참조해 환경별 차이 값만 바꿔 넣습니다. -f로 여러 설정 파일을 함께 로드하는 방법도 함께 씁니다.

알림·오류 응답·링 버퍼 섹션

mailers로 메일 알림을 보내고, http-errors/errorfile로 오류 응답 본문을 교체하며, rings 섹션으로 하위 프로세스 로그를 수집하는 구성.

1문제 상황

백엔드 서버가 모두 응답하지 않으면 HAProxy는 클라이언트에게 기본 오류 페이지를 돌려줍니다. 이 기본 페이지는 내용이 비어 있고 상태 표시도 없어서, 사용자는 단순히 "잠깐 문제가 있어요" 수준만 보고 넘어가며, 운영자 입장에서도 장애가 일어난 사실이 자동으로 알려지지 않습니다.

또한 여러 대의 HAProxy를 함께 굴리면 각 프로세스가 남기는 로그가 어디로 모였는지, 어디까지 기록됐는지 추적하기 어렵습니다.

2핵심 질문

서버 장애가 발생했을 때 운영자에게 알림이 자동으로 가고, 사용자에게는 원인이 분명한 오류 응답이 나가도록 하려면 어떻게 하는가?

3동작 예시

메일을 보낼 SMTP 서버와 메일 형식을 mailers 섹션에서 정의하고, 프론트엔드에 email alerts mymailers를 두면 백엔드가 down/drain 상태로 바뀔 때 등록된 주소로 알림이 갑니다. 같은 프론트엔드에 http-request deny deny_status 503 if { !{ srv_conn health-check } }와 errorfile로 지정한 503 본문을 두면, 사용자에게는 그 본문이 그대로 반환됩니다.

4동작 과정

  1. 알림 발송mailers 섹션에서 email myalert from <발신자> to <수신자> via smtp <SMTP서버>를 정의해 두고, 프론트엔드에 email alerts myalert를 붙입니다. 그러면 서버 상태가 down/up으로 바뀌고 watch-port 상태가 변할 때 설정한 수신자에게 메일이 나갑니다.
  2. 오류 응답 교체http-request deny나 http-error 계열 지시자로 errorfile(외부 파일) 또는 errorfiles/errorfile 문자열로 상태 코드별 본문을 지정합니다. status 503 등 어떤 상태를 어떤 본문으로 바꿀지 정하면 사용자가 원인을 알 수 있는 문구를 받습니다.
  3. 하위 프로세스 로그 모으기rings 섹션에서 rings myring len 0 size 1024 forward <다른 HAProxy 주소> "<표현식> info"처럼, 하위 프로세스의 로그를 모아 앞단 HAProxy가 받아 기록하게 합니다. 개별 프로세스 로그가 흩어지지 않고 한 경로로 합쳐집니다.

5한 줄 요약

mailers로 메일 알림을 보내고, http-errors/errorfile로 오류 응답 본문을 교체하며, rings 섹션으로 하위 프로세스 로그를 수집하는 것

장애 진단과 성능 문제 추적

show info·show stat·profiling 같은 내장 진단 수단으로 병목과 비정상 동작의 원인을 좁히고 해결하는 절차.

1문제 상황

"느려졌다"는 말만으로는 어디가 문제인지 알 수 없습니다. 접속 자체가 안 되는지, 응답이 늦게 돌아오는지, 특정 서버만 느린지, 아니면 HAProxy 자체가 CPU를 다 쓰고 있는지를 구분하려면 각각의 지표를 따로 봐야 합니다.

가짜 서버로 테스트하면 네트워크와 실제 서버 상태를 함께 오염시켜 상황을 더 어렵게 만들기도 합니다. 원인을 좁히려면 실제 환경에서 남는 내장 수치를 순서대로 확인하는 절차가 필요합니다.

2핵심 질문

느려지거나 끊기는 상황에서, 내장 진단 수단만으로 병목이 어디인지 어떤 단계에서 문제가 생기는지를 어떻게 좁혀 나가는가?

3동작 예시

먼저 show info로 현재 CPU 사용률과 실행 시간을 확인하고, 이어 show stat에서 응답 시간 분포와 큐 길이를 봅니다. 클라이언트가 몰릴 때 queue가 0인데 connect만 늘었다면 백엔드가 느려 연결이 쌓인 것이고, 여기에 profiling을 켜고 하위 시스템 호출 지연 시간을 다시 확인해 어느 호출이 시간을 잡아먹는지 좁힙니다.

4동작 과정

  1. 기본 상태 확인런타임 CLI에 show info를 넣어 pid, uptime, 현재 커널 스택 크기, CPU 사용률, 재시작 횟수 같은 값을 봅니다. 재시작이 반복되는지, CPU가 한 코어에 몰려 있는지가 첫 갈림길입니다.
  2. 통계로 위치 좁히기show stat와 show servers state로 프론트엔드·백엔드·서버별 현재 세션, 큐, 대기 중인 요청, 응답 시간 분포를 비교합니다. 대기열이 있는 쪽이 병목이며, 어느 서버가 다른 서버보다 느린지도 바로 드러납니다.
  3. 고급 진단profiling을 전역에 켜면 하위 시스템 호출(에픽 api를 포함한 함수 호출)별 지연 시간이 쌓입니다. 이것을 해석해 어느 호출이 시간을 소모하는지 좁히고, 필요하다면 HAProxy 앞에 가짜 서버를 두는 식으로 한 요소씩 바꿔 붙여 원인을 분리해 냅니다.

5한 줄 요약

show info·show stat·profiling 같은 내장 진단 수단으로 병목과 비정상 동작의 원인을 좁히고 해결하는 것
