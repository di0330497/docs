AWS CodeDeploy

AWS의 관리형 배포 서비스인 AWS CodeDeploy를, 세 컴퓨팅 플랫폼(EC2/온프레미스·AWS Lambda·Amazon ECS)에 대한 애플리케이션 배포 자동화 도구로 해석하고 처음 배우는 사람이 위에서 아래로 읽는 순서로 재배열했다.

이어서 읽기
1CodeDeploy가 대신해 주는 일무엇을 자동화하는 서비스인지와 배포가 어떤 모양으로 진행되는지를 먼저 잡아야, 뒤의 모든 구성요소 이름이 자리에 들어간다.62핵심 구성요소의 이름과 관계애플리케이션·리비전·배포 그룹·배포 구성이라는 네 단어의 관계를 먼저 못 박아야, 이후 모든 설정 화면과 CLI 인자를 해석할 수 있다.73배포 속도와 안전선 정하기 — 배포 구성배포 구성은 배포 그룹을 만들 때 반드시 고르는 값이므로, 리소스를 만들기 전에 그 선택지가 무엇을 바꾸는지 알아야 한다.74AppSpec 파일 — 배포 지시서 쓰기리비전의 심장이자 배포 동작을 실제로 결정하는 파일이라, 리소스를 만들기 전에 문법과 수명 주기 이벤트를 손에 익혀야 한다.95배포 대상 준비하기 — 인스턴스와 에이전트EC2/온프레미스 배포는 대상이 준비되어 있지 않으면 아예 시작되지 않으므로, 리소스를 만들기 전에 대상 쪽을 먼저 세운다.96배포할 것과 받을 곳 만들기대상과 규칙을 알고 난 뒤라야 애플리케이션·리비전·배포 그룹을 각각 어떤 값으로 채워야 하는지 판단할 수 있다.87배포 실행하고 결과 다루기만들어 둔 리소스를 실제로 굴리는 단계이자, 실패했을 때 되돌리는 방법까지가 한 묶음이다.78자동 확장·로드 밸런싱과 감시 장치 붙이기기본 배포가 도는 것을 본 뒤라야, 트래픽 제어와 자동 롤백 같은 안전장치를 왜 붙이는지가 이해된다.79보안·한도·문제 해결동작하는 배포를 손에 넣은 뒤 운영에서 마주치는 권한·네트워크·한도·장애를 마지막에 정리한다.7

CodeDeploy가 하는 일과 수동 배포의 위험

CodeDeploy는 새 버전의 애플리케이션을 여러 서버·서비스에 자동으로 배포해 주는 AWS 관리형 서비스로, 사람이 일일이 파일을 복사하고 서비스를 재시작하다 생기는 누락·중단 위험을 없애 준다.

#1문제 상황

기존의 수동 배포는 개발자나 운영자가 직접 서버에 접속해서 애플리케이션 파일을 복사하고, 관련된 서비스를 멈췄다가 다시 시작하는 방식입니다. 이 과정에서 파일 누락, 서버 간 버전 불일치, 배포 중 서비스 중단 등의 문제가 쉽게 발생하고, 서버가 10개·100개가 되면 일관성 있게 관리하기가 거의 불가능해집니다.

#2핵심 질문

새 애플리케이션을 여러 서버에 동시에, 안전하게, 일관되게 배포하려면 어떻게 해야 할까요?

#3동작 예시

CodeDeploy는 당신이 S3 버킷에 올려 놓은 애플리케이션 번들(파일 모음)을 읽어서, 지정된 모든 서버에 자동으로 다운로드하고 설정에 따라 설치 및 재시작까지 해 줍니다. 당신은 "어떤 파일을 배포할지", "어떤 서버들에 배포할지", "배포 중에 어떤 스크립트를 실행할지"만 정의하면 됩니다.

#4동작 과정

  1. 배포 생성당신이 정의한 애플리케이션, 대상 서버 그룹(배포 그룹), 새 버전 파일(리비전)을 명시해 배포를 시작합니다.
  2. 자동 수행CodeDeploy는 각 서버에서 파일을 받고, appspec.yml 파일(설치 및 실행 지시서)에 정의된 명령어들을 순서대로 실행합니다.
  3. 상태 관리성공·실패 여부를 추적하고, 실패한 서버가 있으면 롤백(이전 버전으로 되돌리기)을 수행합니다.

CodeDeploy는 배포 대상 환경을 EC2/온프레미스 인스턴스, Lambda 함수, ECS 서비스 세 가지 컴퓨팅 플랫폼으로 나누며 플랫폼에 따라 쓸 수 있는 배포 방식과 설정이 달라진다.

#1문제 상황

애플리케이션은 실행되는 환경이 다릅니다. 물리 서버나 EC2 인스턴스 위에서 장시간 실행되는 경우가 있고, 요청이 들어올 때만 잠깐 실행되는 함수형 환경이 있고, 컨테이너 기반 서비스로 관리되는 경우도 있습니다. 각 환경은 애플리케이션을 설치하고 실행하는 방식이 완전히 다릅니다.

#2핵심 질문

CodeDeploy는 어떻게 이렇게 다른 여러 환경 유형을 모두 지원할까요?

#3동작 예시

CodeDeploy는 배포 대상을 세 가지 카테고리로 나누고, 각 카테고리마다 맞는 배포 방식과 설정을 달리 적용합니다. EC2나 온프레미스 서버는 CodeDeploy Agent라는 프로그램을 설치하고, Lambda는 함수 코드를 직접 업로드하고, ECS는 컨테이너 이미지를 업데이트하는 방식으로 각각 다르게 배포됩니다.

#4동작 과정

  1. 플랫폼 선택애플리케이션을 생성할 때 EC2/온프레미스, Lambda, ECS 중 하나를 선택합니다.
  2. 플랫폼별 배포 설정각 플랫폼에 맞는 배포 방식(인플레이스·블루/그린 등)과 설정이 활성화됩니다.
  3. 맞춤형 배포 실행선택한 플랫폼의 특성에 맞게 파일 복사, 함수 업로드, 컨테이너 업데이트 등이 진행됩니다.

#2핵심 질문

새 버전을 배포하되, 현재 서비스 중단을 최소화하면서도 문제 발생 시 빠르게 되돌릴 수 있는 방식은 무엇일까요?

#3동작 예시

#4동작 과정

  1. 인플레이스 배포각 서버를 하나씩 트래픽에서 제거하고 새 버전을 설치한 다음 다시 투입합니다.

인플레이스 배포는 어떻게 진행되는가

인플레이스 배포는 각 인스턴스를 순서대로 서비스에서 빼고 새 버전을 설치한 뒤 다시 트래픽에 넣는 방식이며, EC2/온프레미스 플랫폼에서만 쓸 수 있다.

#1문제 상황

여러 서버가 함께 서비스를 제공할 때, 모든 서버를 동시에 멈춰서 새 버전으로 바꿀 수는 없습니다. 일부 서버가 중단되더라도 나머지가 계속 요청을 처리해야 합니다. 그렇다고 서버를 하나씩 수작업으로 관리하면 시간이 오래 걸리고 누락이 생기기 쉽습니다.

#2핵심 질문

여러 서버가 함께 실행되는 상황에서 각 서버를 차례차례 새 버전으로 바꾸되, 다른 서버들의 서비스는 중단되지 않게 하려면 어떻게 할까요?

#3동작 예시

인플레이스 배포는 로드 밸런서 앞에 5대의 서버가 있을 때, 첫 번째 서버를 로드 밸런서에서 빼고(Deregister) 새 버전을 설치한 후 다시 넣고(Register), 두 번째 서버로 똑같이 반복하는 방식입니다. 배포 정책에서 한 번에 몇 대씩 처리할지를 결정합니다.

#4동작 과정

#1문제 상황

CodeDeploy 에이전트는 배포할 때마다 설치, 다운로드, 검증, 실행 단계마다 로그를 기록합니다. 이런 로그는 기본적으로 각 인스턴스에만 남습니다. 문제는 10개, 100개의 인스턴스가 배포되면 각각 다른 서버에 로그가 흩어져 있어서, 배포 상황을 전체적으로 확인하려면 일일이 인스턴스에 접속해야 한다는 점입니다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 로그 파일 생성 및 관리에이전트가 배포할 때 고유한 디렉토리를 만들고 배포 로그를 저장합니다. 인스턴스의 디스크를 낭비하지 않기 위해 기본적으로 오래된 배포 로그와 리비전(배포했던 파일 묶음)은 자동으로 정리됩니다.

  3. 중앙에서 조회CloudWatch 콘솔이나 CloudWatch Insights 쿼리로 모든 인스턴스의 배포 로그를 실시간으로 검색, 필터링, 분석할 수 있습니다.

  1. 폴더 구조 설계appspec.yml을 리비전 폴더의 최상위에 배치하고, 배포할 애플리케이션 코드, 설정 파일, 스크립트들을 하위 폴더에 정리합니다.

#3동작 예시

S3를 선택하면 zip 파일을 S3 버킷에 업로드하고, CodeDeploy가 버킷 이름과 키(파일 경로)를 보고 다운로드합니다. GitHub나 Bitbucket을 선택하면 리포지토리 URL과 커밋 해시를 전달해서, CodeDeploy가 그 커밋의 코드를 가져옵니다.

#1문제 상황

배포 대상 위치에 이전 버전의 파일이 이미 있을 때, 그것을 어떻게 처리할지 정해야 한다. 기존에는 배포 중 파일 충돌이 발생하면 배포가 실패하거나, 무조건 덮어씌웠다. 어떤 파일은 유지해야 하고 어떤 파일은 덮어씌워야 하는지를 배포 시마다 일일이 조정해야 했다.

#2핵심 질문

배포 대상에 이미 있는 파일을 유지할지, 덮어씌울지, 아니면 파일 충돌을 이유로 배포를 멈출지를 어떻게 정할까?

#3동작 예시

#4동작 과정

  1. FAIL배포 대상에 같은 이름의 파일이 이미 있으면 배포를 중단한다. 파일 충돌을 피하고 싶을 때 사용한다.
  2. OVERWRITE배포 대상에 같은 이름의 파일이 있어도 새로운 파일로 덮어씌운다. 모든 파일을 새 버전으로 강제 업데이트할 때 사용한다.
  3. RETAIN배포 대상에 같은 이름의 파일이 있으면 그것을 유지하고, 없는 파일만 새로 생성한다. 사용자 데이터나 설정 파일처럼 유지해야 할 파일이 있을 때 사용한다.

배포 중인 인스턴스를 로드 밸런서에서 잠시 빼고(등록 해제) 배포가 끝나면 다시 넣어, 사용자가 배포 중인 서버로 흘러들어가지 않게 하는 장치다.

#1문제 상황

배포 중인 인스턴스도 로드 밸런서가 트래픽을 보낸다. 배포 스크립트가 실행 중인 불안정한 상태에서도 사용자 요청이 들어온다.

#2핵심 질문

배포 중인 인스턴스는 트래픽을 받지 않게 하면서 배포를 진행할 수 없을까?

#3동작 예시

CodeDeploy가 배포를 시작할 때 로드 밸런서에서 그 인스턴스를 등록 해제하고, 배포가 끝나면 다시 등록하는 방식이다. CLB(Classic Load Balancer), ALB(Application Load Balancer), NLB(Network Load Balancer) 모두 이를 지원한다.

#4동작 과정

  1. 배포 전 인스턴스 등록 해제CodeDeploy가 로드 밸런서에 해당 인스턴스를 등록 해제 요청을 보내면 로드 밸런서는 즉시 그 인스턴스로의 트래픽 전송을 중단한다.
  2. 배포 진행인스턴스가 로드 밸런서에서 빠져 있는 동안 배포 작업을 수행한다.
  3. 배포 후 인스턴스 등록배포가 완료되면 인스턴스를 다시 로드 밸런서에 등록하여 사용자 트래픽 수신을 재개한다.

#5한 줄 요약

배포 중에 인스턴스를 로드 밸런서에서 일시 제거하여 불안정한 상태의 서버가 사용자 요청을 받지 않게 하는 보호 메커니즘

EC2 Auto Scaling 연동과 시작 배포(launch deployment)

Auto Scaling 그룹에 새 인스턴스가 뜨면 CodeDeploy 가 자동으로 최신 리비전을 그 인스턴스에 배포해 주는 연동이다.

#1문제 상황

Auto Scaling 그룹에서 새 인스턴스가 자동으로 생성되면 기본 이미지(AMI)로만 구동된다. 새로운 코드를 배포하려면 별도의 배포 명령을 수동으로 실행해야 한다.

#2핵심 질문

Auto Scaling으로 새 인스턴스가 자동 생성될 때 최신 애플리케이션 코드를 자동으로 배포할 수 없을까?

#3동작 예시

CodeDeploy는 Auto Scaling 그룹에 연동되어, Auto Scaling이 새 인스턴스를 시작할 때 CloudWatch 이벤트(AWS의 감시 시스템이 보내는 알림)를 통해 자동으로 통지받고, 바로 최신 리비전을 그 인스턴스에 배포한다.

#4동작 과정

  1. Auto Scaling 그룹 설정Auto Scaling 그룹을 CodeDeploy 애플리케이션과 연동하도록 설정한다.
  2. 인스턴스 시작 감지 및 자동 배포새 인스턴스가 시작되면 CloudWatch가 이를 감지하여 CodeDeploy에 신호를 보내고, CodeDeploy가 자동으로 최신 코드를 배포하기 시작한다.
  3. 배포 완료 후 서비스 투입배포가 완료되면 인스턴스가 로드 밸런서에 자동으로 등록되어 실제 트래픽 처리를 시작한다.

#5한 줄 요약

Auto Scaling의 자동 확장과 CodeDeploy의 자동 배포를 연결하여 새로운 인스턴스가 최신 코드 상태로 즉시 서비스 투입되게 하는 통합 메커니즘

종료 훅과 종료 배포(termination deployment)

#1문제 상황

Auto Scaling 그룹에서 인스턴스를 축소할 때, 실행 중인 작업을 마치지 못한 채 즉시 인스턴스가 종료된다. 데이터베이스 연결이나 큐의 메시지 처리 같은 정리 작업이 실행되지 않는다.

#2핵심 질문

인스턴스가 종료되기 전에 정리 작업(연결 종료, 메시지 처리 완료 등)을 미리 실행할 수 없을까?

#3동작 예시

Auto Scaling은 종료 수명주기 훅(인스턴스 종료 직전에 특정 작업을 실행하는 일시 중단 기능)을 CodeDeploy와 연동하여, 인스턴스가 사라지기 직전에 ApplicationStop 같은 정리 스크립트를 자동으로 실행한다.

#4동작 과정

  1. 종료 신호 감지 및 일시 중단Auto Scaling이 인스턴스 축소를 시작할 때 종료 수명주기 훅이 인스턴스 종료를 일시 중단한다.
  2. 종료 배포 실행CodeDeploy가 ApplicationStop, BeforeTerminate 같은 정리 라이프사이클 이벤트를 실행하여 열린 연결을 종료하고 처리 중인 작업을 완료한다.
  3. 인스턴스 종료 재개정리 작업이 완료되면 인스턴스가 정상적으로 종료된다.

#5한 줄 요약

#1문제 상황

기존에는 배포가 진행 중일 때 트래픽 증감에 따라 Auto Scaling이 자동으로 인스턴스를 늘리거나 줄 수 있었습니다. 하지만 이 과정에서 문제가 발생합니다. 새로운 버전으로 배포 중인데 오토 스케일이 작동되면, 새 인스턴스는 아직 배포되지 않은 상태로 추가되거나, 배포 중간에 인스턴스가 제거될 수 있어서 배포 상태가 불일치하게 됩니다.

#2핵심 질문

배포 과정 중에 인스턴스가 동적으로 추가되거나 제거되는데, CodeDeploy는 어떻게 이를 감지하고 일관된 배포 상태를 유지할까요?

#3동작 예시

배포 명령이 내려진 후 3개 인스턴스에 배포 중입니다. 이때 트래픽이 급증해서 Auto Scaling이 새 인스턴스 2개를 자동으로 추가합니다. CodeDeploy는 이 새 인스턴스들을 감지하고, 아직 배포되지 않은 상태로 들어온 인스턴스에 대해 현재 진행 중인 배포 명령을 즉시 적용하거나, 배포 규칙에 따라 배포를 실패 처리합니다.

#4동작 과정

  1. 배포 시작 후 인스턴스 변화 감지CodeDeploy는 배포 명령이 실행되는 동안 대상 그룹의 인스턴스 목록을 지속적으로 모니터링합니다. Auto Scaling이 새로운 인스턴스를 추가하거나 기존 인스턴스를 제거하는 변화를 감지합니다.
  2. 배포 규칙에 따른 대응CodeDeploy의 배포 구성에 따라 동작이 결정됩니다. 일부는 새 인스턴스에 즉시 배포를 재적용하고, 일부는 배포를 중단하거나 실패로 표시합니다.
  3. 배포 상태 최종 결정모든 인스턴스의 배포 상태가 통일되거나 실패 조건을 만족하면 배포가 종료됩니다.

#3동작 예시

#4동작 과정

  2. 경보 발동 및 신호 전송메트릭이 임계값을 초과하면 경보가 트리거되고, 이 신호가 CodeDeploy에 전달됩니다.

Amazon SNS 트리거와 알림 규칙

#3동작 예시

CodeDeploy 할당량과 참조 자료

애플리케이션 수·동시 배포 수 등 서비스 한도와 AppSpec·CLI 같은 참조 문서를 모아 본다.

#1문제 상황

개발자가 CodeDeploy를 사용하다 보면 예상치 못한 제약에 부딪힐 수 있다. 한 번에 배포할 수 있는 인스턴스 수가 제한되어 있고, 만들 수 있는 애플리케이션 개수나 배포 그룹의 개수도 정해져 있다. 리비전 파일의 크기 제한, API 호출 속도 제한(쓰로틀링) 등도 있다. 또한 AppSpec 파일의 정확한 문법이나 CLI 명령어의 옵션을 찾아야 할 때, 공식 문서의 어느 부분을 봐야 하는지 혼란스럽다.

#2핵심 질문

CodeDeploy의 한도를 미리 알고 있고, 필요한 API 문서와 설정 파일 참조를 어디서 찾을 수 있을까?

#3동작 예시

AWS 공식 문서는 몇 가지 명확한 카테고리로 나뉜다. 할당량 페이지에는 각 리소스별 한도(예: 애플리케이션당 최대 배포 그룹 수 100개)가 표로 정리되어 있고, AppSpec 참조 문서는 배포 설정 파일에서 각 섹션(hooks, permissions, files 등)의 필드를 어떻게 입력하는지 정의한다. CLI 참조는 각 명령어(create-deployment, get-deployment 등)의 매개변수와 출력 형식을 나열한다.

#4동작 과정

  1. 할당량 확인프로젝트 규모에 맞게 동시 배포 수나 리비전 크기 같은 한도를 미리 읽고, 필요하면 AWS 지원팀에 상향 요청(Limit Increase Request)을 제출한다.
  2. AppSpec 구조 파악배포할 애플리케이션의 설정 파일을 작성할 때, 공식 AppSpec 참조에서 버전, hooks(설치 전후 실행할 명령), permissions(파일 소유권과 권한) 같은 필드의 형식을 확인한다.
  3. CLI 명령어 학습배포를 자동화하는 스크립트나 파이프라인을 짤 때, CLI 참조에서 명령어의 매개변수와 반환값을 확인하고 복사·붙여넣기한다.

#5한 줄 요약

CodeDeploy의 서비스 한도를 투명하게 공개하고, AppSpec과 CLI 같은 핵심 도구의 문법과 옵션을 한 곳에 정리해 개발자가 올바르게 사용하도록 돕는 것

문제 해결: 실패 원인과 오류 코드 읽기

배포 실패 시 오류 코드와 로그를 단서로 원인을 좁혀 가는 진단 절차다.

#1문제 상황

배포가 실패하면 개발자는 당황한다. CodeDeploy 콘솔에 "배포 실패"라고만 표시되거나, 오류 메시지가 너무 길고 어떤 부분이 문제인지 모를 때가 많다. EC2 인스턴스와 CodeDeploy 에이전트(배포를 수행하는 프로그램) 사이의 통신 오류일 수도 있고, AppSpec 파일 문법 오류, IAM 권한 부족, 또는 인스턴스에서 실행하는 배포 스크립트의 오류일 수도 있다. 각 원인마다 해결 방법이 다르므로, 실패 원인을 체계적으로 좁혀가야 한다.

#2핵심 질문

배포 실패 시 원인을 빠르게 파악하고 단계적으로 문제를 해결할 수 있을까?

#3동작 예시

CodeDeploy 오류 코드는 대략 5가지 범주로 나뉜다. 1) Agent 연결 오류(에이전트가 CodeDeploy와 통신 불가), 2) 리비전 다운로드 오류(S3에서 코드를 못 가져옴), 3) 권한 오류(IAM 정책 부족), 4) 배포 스크립트 오류(install/start 훅에서 명령 실패), 5) 인스턴스 상태 오류(인스턴스가 실행 중이 아님). 각 범주는 해당 로그 위치가 다르다.

#4동작 과정

  1. 배포 상태 확인CodeDeploy 콘솔의 배포 상세 화면에서 각 인스턴스별 상태(성공/실패/중단)를 확인하고, 실패한 인스턴스의 오류 코드와 메시지를 기록한다.
  2. 로그 수집EC2 인스턴스에 SSH나 Systems Manager Session Manager(보안 셸 접근 도구)로 접속해 /var/log/codedeploy-agent/codedeploy-agent.log에서 에이전트 로그, /var/log/codedeploy-agent/deployments/에서 배포별 로그를 확인한다. 오류 코드가 어느 단계에서 발생했는지 추적한다.
  3. 원인별 해결오류가 AgentConnectionError(에이전트 연결 오류)면 인스턴스의 보안 그룹과 라우팅을 확인하고, DownloadFailure(다운로드 실패)면 S3 버킷 정책과 IAM 역할을 확인하며, ScriptFailure(스크립트 오류)면 AppSpec의 배포 스크립트를 직접 인스턴스에서 실행해 어느 명령이 실패하는지 확인한다.

#5한 줄 요약

배포 실패를 여러 단계(에이전트 연결, 리비전 다운로드, 권한, 스크립트, 인스턴스 상태)로 분류하고 각 단계별 로그를 읽는 체계적인 진단 절차를 제공하는 것
