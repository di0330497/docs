GuardDuty 란 무엇인가

AWS 계정 안의 EC2·EKS·S3 같은 자산을 누가 침범했는지, 어떤 악성 행위가 있었는지를 자동으로 찾아 경고해 주는 AWS 관리형 위협 탐지 서비스다.

#1문제 상황

EC2 인스턴스에 침입자가 들어와 Miner를 돌리거나 자격 증명을 빼돌릴 때, 누가 무엇을 했는지는 남은 로그를 직접 뒤져야 알 수 있었다. Amazon GuardDuty는 이런 AWS 환경의 활동 기록을 계속 감시하고 분석해 이상 징후를 자동으로 알려 주는 위협 탐지 서비스다. 관리형 서비스라 서버를 직접 운영하지 않는다.

#2핵심 질문

AWS 계정 안에서 누가 무엇을 했는지 사람이 뒤지지 않고도 알 수 있을까?

#3동작 예시

심야에 EC2 인스턴스가 평소보다 많은 CPU를 쓴다. GuardDuty 콘솔을 열어 보면 해당 인스턴스에 권한 남용 유형의 finding(탐지 결과, → 01-02)이 이미 올라와 있고 어느 API가 어느 자격 증명으로 호출됐는지 적혀 있다.

#4동작 과정

  1. 수집한다AWS CloudTrail 기록과 네트워크 흐름 로그 같은 데이터 소스를 읽어 온다. 데이터 소스는 GuardDuty가 지켜보는 원천 기록이다.
  2. 분석한다threat intelligence feed(악성 IP·파일 해시 목록)와 머신러닝 모델로 정상에서 벗어난 동작을 찾아 낸다. 이 분석을 intelligent threat detection이라 부른다.

#1문제 상황

클라우드 전반의 활동 기록만 보면 서비스마다 위험한 행동의 모습이 다르다. 어떤 버킷에서 대량 삭제가 일어나는지, 어느 함수에서 이상한 호출이 나가는지는 일반 신호만으로 드러나지 않는다.

그래서 S3 Protection·EKS Protection·RDS Protection·Lambda Protection처럼 서비스마다 보호 계획을 두고(→ 01-04) 그 서비스에 맞는 데이터 소스를 붙인다. 켠 계획의 범위만 따로 감시하게 되는 것이다.

#2핵심 질문

서비스마다 어떤 기록을 붙여야 그 서비스의 위험을 볼 수 있는가?

#3동작 예시

S3 Protection이 켜진 계정에서 버킷의 객체가 대량 삭제된다. GuardDuty가 S3의 CloudTrail 데이터 이벤트를 보고 위험을 판단해 finding 하나를 띄운다. 사용자는 콘솔에서 그 버킷과 삭제된 객체 수를 확인한다.

#4동작 과정

  1. 계획을 켠다보호 계획은 기능이 묶이는 단위다(→ 01-04). 계정에 필요한 계획만 켜면 그 계획의 데이터 소스 연결 권한이 함께 생긴다.
  2. 서비스 기록을 붙인다계획마다 전용 데이터 소스를 연결한다. S3는 객체 단위 API 작업이 담긴 CloudTrail 데이터 이벤트를 보고, 다른 서비스는 각자의 audit logs를 본다.
  3. 판단해 경고한다붙은 데이터에서 위험을 찾으면 그 서비스의 finding type으로 경고를 만든다(→ 03-06). 계획이 꺼진 서비스의 탐지 항목은 만들어지지 않는다.
  4. 확인해 볼 것보호 계획 화면에서 켜진 계획과 그 계획에 연결된 데이터 소스 이름이 함께 보이는지 확인한다.

그래서 GuardDuty는 기대와 어긋나는 잠재적 악성 활동을 발견할 때마다 finding(탐지 결과)을 만들어 낸다(→ 01-02). 사용자는 콘솔의 Findings 페이지나 AWS CLI·API 연산으로 이 기록을 보고 관리한다.

#2핵심 질문

발생한 의심스러운 활동을 무엇이 어떤 형태로 남겨 주는가?

#4동작 과정

  1. 모든 서비스에서 만들어 낸다EC2·S3·EKS 등 각 서비스의 데이터 소스에서 의심 활동이 나오면 공통 형식의 finding으로 정리한다(→ 02-03). 콘솔에서는 테스트용 샘플 finding도 직접 생성해 볼 수 있다.
  2. 유형으로 이름을 붙인다finding type이 그 위험을 짧고 읽기 쉽게 설명한다. attack types와 malware 관련 판정은 내부의 GuardDuty malware detection scan engine이 맡는다.
  3. 목록에서 다룬다생성된 finding은 콘솔 Findings 페이지에서 조회·관리하거나 CLI와 API로 가져온다.
  4. 확인해 볼 것Findings 페이지 목록에 finding 유형·심각도·발생 시각·대상 리소스가 모두 차 있는지 확인한다.

그래서 GuardDuty finding format이 고정되어 있다. 공통 필드와 유형별 추가 속성으로 나뉘며 어느 쪽이든 같은 자리를 읽는다.

  4. 확인해 볼 것상세 화면에서 resource·action·발생 시각이 고정된 위치에 모두 표시되는지 확인한다.

findings severity levels는 이 기준을 만든다. severity score를 1.0에서 10.0까지 매기고 이를 Critical·High·Medium·Low 네 등급으로 나눈다. 같은 유형이라도 상황에 따라 등급이 달라질 수 있다.

#4동작 과정

  1. 점수를 붙인다GuardDuty 가 해당 항목의 위험을 severity score로 1.0~10.0 사이에서 매긴다. 값이 클수록 위험이 크다.
  2. 등급으로 나눈다이 범위를 Critical·High·Medium·Low로 쪼갠다. Critical은 9.0~10.0 구간이다.
  3. 판단 근거를 함께 준다등급이 붙는 이유가 항목의 설명란에 함께 적힌다. 공격 시퀀스가 진행 중일 수 있다는 문구처럼 상황별로 달라진다.

#1문제 상황

EC2 인스턴스에서 이상한 일이 벌어졌다는 사실만으로는 무엇을 해야 할지 정하기 어렵다. 같은 침해라도 백도어인지 자원 고갈인지에 대응이 갈린다.

EC2 finding types는 이 상황을 유형별로 나눠 놓은 목록이다. Backdoor·CryptoCurrency·BruteForce·MaliciousFile 같은 이름이 각각 정해진 이상 징후를 가리킨다.

#2핵심 질문

EC2 인스턴스에서 일어난 의심스러운 행동을 유형별로 어떻게 구분해 알 수 있을까?

#3동작 예시

운영자가 인스턴스 하나의 항목 이름을 열어 본다. Backdoor:EC2/DnsBackdoor로 표시되어 있다.

DNS질의를 되돌아가는 백도어 징후라는 뜻이므로, 해당 인스턴스의 네트워크를 격리하는 조치(→ 09-01)로 넘어간다.

#4동작 과정

  1. 관찰 값을 모은다인스턴스의 통신·프로세스·파일 활동을 분석해 일반적인 패턴과 어긋나는 점을 찾는다(→ 02-01).
  2. 유형 이름을 붙인다찾은 이상이 EC2 finding types 목록의 이름으로 표기된다. 발견 유형별로 종류가 다르다.
  3. 받은 걸로 판정한다각 유형은 서로 다른 근거를 쓴다. CryptoCurrency는 비트코인 도구 흔적, BruteForce는 로그인 실패 폭주를 보고한다.
  4. 확인해 볼 것인스턴스의 항목 상세에서 finding type 이름과 발생 시각이 함께 표시되는지 본다.

IAM 탐지 유형과 침투 공격 시퀀스

누가 어떤 IAM 권한으로 무엇을 했는지 추적하는 탐지 유형과, 여러 공격 단계를 시간순으로 이어 붙여 한 번의 침투 시도로 보여 주는 시퀀스 탐지를 묶은 개념이다.

먼저 알아야 할 것 03-01

#1문제 상황

IAM 권한이 정상 동작인지 남용인지 구분하려면 권한 목록만으로는 부족하다. 콘솔 접근, 키 탈취, 로그 끄기처럼 흔한 동선을 따로 봐야 한다(→ 10-01).

IAM finding types가 그 동선을 유형으로 정리한다. 권한 남용은 IAMUser/AnomalousBehavior로 묶이고, 여러 단계를 이은 공격은 attack sequence finding types로 따로 나온다.

#2핵심 질문

누가 어떤 IAM 권한으로 무엇을 했는지 단계별로 추적할 수 있을까?

#3동작 예시

한 IAM 사용자의 키가 평소 쓰지 않던 리전에서 여러 번 쓰였다. ConsoleLoginSuccess와 CloudTrailLoggingDisabled가 같은 시간대에 이어진다.

이들을 합친 침투 시퀀스 항목 하나로, 키를 비활성화하는 조치(→ 09-04) 대상으로 넘긴다.

#4동작 과정

  1. 사용 기록을 모은다CloudTrail 기록에서 누가 어떤 권한으로 무엇을 했는지 뽑는다.
  2. 단계 이름을 붙인다공격 목적에 따라 Discovery·Exfiltration·Impact 같은 이름이 붙는다. 로그를 끊은 흔적은 DefenseEvasion, 키 탈취 흔적은 CredentialAccess로 분류된다.
  3. 순서를 이어 붙인다여러 단계를 시간순으로 묶어 한 번의 침투 시도로 보여 준다. 이런 것이 attack sequence finding types다.
  4. 확인해 볼 것항목 상세에서 시퀀스에 포함된 단계 목록이 시간순으로 보이는지 본다.

서비스별 탐지 유형

S3·EKS·RDS·Lambda 같은 서비스마다 그 서비스에 어울리는 의심 활동 목록을 따로 정의해, 어느 계획이 켜져 있느냐에 따라 해당 서비스의 탐지 항목이 만들어지는 방식이다.

먼저 알아야 할 것 03-04

#1문제 상황

EC2에 어울리는 의심 징후를 모든 서비스에 그대로 쓰면 맞지 않는다(→ 03-04). 버킷 공개 설정과 컨테이너 권한 상승은 전혀 다른 신호다.

서비스별 탐지 유형은 각 서비스에 맞는 의심 활동 목록을 따로 정의한다.

#2핵심 질문

각 서비스에서 무엇을 이상 징후로 볼지 어떻게 나누어 정의할 수 있을까?

#3동작 예시

S3 Protection finding types에 속하는 BucketPublicAccessGranted 항목이 올라온다. 버킷 정책이 공개로 바뀌었다는 뜻이다(→ 09-02).

같은 기간 RDS Protection finding types나 Lambda Protection finding types가 만드는 항목도 같은 목록에 모인다.

#4동작 과정

  1. 서비스를 고른다볼 대상 자원이 속한 서비스를 정한다. 데이터 소스도 그 서비스 전용이다.
  2. 전용 목록을 적용한다해당 서비스의 finding types 목록만 골라 판정한다. S3는 버킷 정책과 익명 접근을 보고하고, EKS와 컨테이너 런타임은 Runtime Monitoring finding types로 프로세스와 파일을 본다.
  3. 같은 형식으로 묶는다어느 목록에서 나온 항목이든 finding의 공통 형식(→ 03-02)에 맞춰 Findings 화면에 함께 모은다.
  4. 확인해 볼 것Findings 목록에서 resource type을 S3Bucket처럼 서비스별로 나눠 골라 볼 수 있는지 본다.

4단계 4. 실행 중인 것을 지켜본다 — Runtime Monitoring

실행 중인 EC2·EKS·ECS 워크로드에 경량 보안 에이전트를 붙여 커널 수준에서 일어나는 프로세스 실행과 파일·네트워크 접근을 실시간으로 지켜보고, 그 안에서 이상 징후를 찾아 경고로 내는 기능이다.

먼저 알아야 할 것 03-01

#1문제 상황

GuardDuty의 기본 탐지는 API 호출 기록을 분석하는 방식이라(→ 02-01), 서버 안에서 실제로 실행된 프로그램이 무엇을 했는지는 보이지 않는다.

Runtime Monitoring은 실행 중인 EC2 인스턴스·EKS 노드·ECS 태스크에 security agent를 붙여 그 안의 활동을 실시간으로 본다. security agent는 프로세스 실행과 file and network activity, 즉 파일 접근과 네트워크 연결을 관찰해 AWS로 보낸다.

#2핵심 질문

실행 중인 서버 안에서 일어나는 일을 어떻게 실시간으로 알 수 있을까?

#3동작 예시

리눅스 EC2 인스턴스 하나에서 알 수 없는 프로세스가 시작되고 이상한 외부 주소로 연결이 나간다. GuardDuty 콘솔의 Findings 목록에 해당 인스턴스의 경고가 새로 올라온다.

누가 침입한 게 아니라 서버 안에서 무슨 일이 벌어졌는지부터 알 수 있다.

#4동작 과정

  1. 붙인다관리 대상 자원에 security agent를 배포한다. GuardDuty가 대신 배포하고 갱신하거나 사용자가 직접 배포해 관리한다. 자식 자원 타입마다 방법이 다르다.
  2. 보낸다에이전트가 운영체제 수준의 프로세스 실행·파일 접근·네트워크 연결을 이벤트로 모아 GuardDuty로 보낸다. 데이터는 AWS 내부망 안에서만 오간다.
  3. 판단한다GuardDuty가 이벤트를 분석해 threat detection on hosts, 즉 호스트 단위 위협 탐지를 수행하고 이상 행동이 보이면 경고를 만든다. 권한 상승 같은 행위가 이에 해당한다.
  4. 확인해 볼 것콘솔의 Findings 목록에서 새로 생긴 호스트 관련 경고의 발생 시각과 대상 자원을 본다.

보안 에이전트를 EC2 인스턴스, EKS 클러스터의 노드, ECS 태스크(작업 단위) 등 실제 코드가 도는 컴퓨팅 자원에 설치하는 것을 뜻하며, 각 환경마다 자동으로 붙이는 방법과 수동으로 붙이는 방법이 따로 있다.

먼저 알아야 할 것 04-01

→ 04-03 참조

#1문제 상황

에이전트는 실제 코드가 도는 자원에 붙어야 관찰이 된다(→ 04-01). EC2 인스턴스, EKS 클러스터 노드, ECS 태스크처럼 자식 자원 유형마다 붙이는 방법이 달라 어디까지 사용자가 손대야 하는지 알기 어렵다.

이 차이를 automated agent on Amazon EC2, automated agent on Amazon EKS, automated agent on Amazon Fargate로 나눈다. 관리 대상은 managed-gdu-agent로 표시된다.

#2핵심 질문

내 환경에서 에이전트를 어디에 어떻게 붙여야 하는가?

#3동작 예시

신규 계정에서 EC2 인스턴스를 켠 뒤 해당 리전의 보호 계획을 확인한다. 인스턴스가 관찰 대상 목록에 자동 표시된다.

별도 설치 없이도 에이전트가 붙어 있었음을 알 수 있다.

#4동작 과정

  1. 자격 조건을 확인한다EC2는 지원 목록에 있는 CPU 아키텍처·운영체제·커널 버전이어야 붙는다(→ 04-03).
  2. 자동 배포를 켠다해당 리전의 보호 계획에서 자동 배포를 켠다. 신규·기존 인스턴스가 관리 대상 목록에 오른다.
  3. 직접 붙이는 경우를 안다다중 계정 환경이나 이전 수동 관리에서 쓰는 방법이 따로 있다. 여러 계정의 에이전트를 한데서 켜는 절차를 쓴다.
  4. 확인해 볼 것콘솔의 관리 대상 목록에 인스턴스·노드가 뜨고 상태가 표시되는지 본다.

붙이기 전에 맞아야 할 조건

에이전트를 설치하기 전에 워크로드가 GuardDuty 를 쓸 수 있는 리전 안에 있어야 하고, CPU 아키텍처·운영체제·커널 버전이 지원 목록에 속하며, 필요한 권한과 설정(예: 클러스터 보안 설정)이 갖춰져 있어야 한다는 전제 목록이다.

먼저 알아야 할 것 04-02

#1문제 상황

Runtime Monitoring은 실행 중인 워크로드에 보안 에이전트를 붙여 커널 수준을 지켜본다(→ 04-01). 그런데 어디에 어떻게 붙이는지는 앞에서 다루었고(→ 04-02), 붙이기 전에 맞아야 할 조건은 자원 종류마다 다르다.

이 조건은 prerequisites, 즉 에이전트를 붙이기 전에 미리 충족시켜야 할 전제 목록이다. 여기서 말하는 supported CPU architectures, operating systems, kernel versions 는 에이전트가 돌아갈 수 있는 CPU 구조·운영체제·커널 버전의 지원 목록이고, EKS add-on 은 클러스터 보안 설정 한 켤기를 뜻한다.

#2핵심 질문

에이전트를 붙이기 전에 어떤 조건을 미리 충족해야 하는가?

#3동작 예시

EC2만 지켜보다가 EKS 클러스터까지 보기로 한 팀을 든다. EC2용 조건만 맞췄으므로 클러스터 쪽 조건도 따로 확인한다. 아키텍처와 운영체제 버전이 목록에 있는지와 클러스터 보안 설정이 켜져 있는지를 차례로 살핀다.

조건 하나라도 어긋나면 그 자원에는 에이전트가 붙지 않는다.

#4동작 과정

  1. 조건 목록을 고른다지켜볼 자원 종류마다 다른 prerequisites를 쓴다. EC2 인스턴스, ECS-EC2, Fargate, EKS 클러스터가 각각 별도 조건을 가진다.
  2. 지원 목록과 대조한다그 안에서 supported CPU architectures, operating systems, kernel versions 를 확인한다. 지원하지 않는 조합이면 에이전트가 붙지 않는다. EKS라면 EKS add-on 이라는 클러스터 보안 설정도 켠다.
  3. 권한을 맞춘다EKS는 클러스터 보안 설정이 먼저 켜져 있어야 한다. 이 선행 조건은 03-03 의 권한 틀을 함께 쓴다.
  4. 확인해 볼 것콘솔의 Runtime Monitoring 설정 화면에 대상 리소스의 상태가 정상으로 보이는지 확인한다.

수집되는 런타임 이벤트 종류

에이전트가 워크로드 안에서 포착해 보내는 기록의 종류로, 실행된 프로그램과 실행 인자, 읽고 쓴 파일, 연결한 네트워크 통신, 로드된 라이브러리 같은 관찰 결과가 여기에 해당한다.

먼저 알아야 할 것 04-01

#1문제 상황

Runtime Monitoring은 에이전트를 붙인 워크로드 안에서 일어나는 일을 실시간으로 본다(→ 04-01). 그 근거가 되는 것이 collected runtime event types 다. 이 목록이 있어야 탐지가 무엇에 근거했는지 설명할 수 있다.

그 안에 file operations, network connections, process execution, dns queries 가 있다. 각각 파일을 읽고 쓴 기록, 네트워크로 이어진 기록, 실행된 프로그램과 인자 기록, 이름으로 주소를 물은 기록을 뜻한다.

#2핵심 질문

에이전트는 워크로드 안에서 무엇을 관찰해 보내는가?

#3동작 예시

컨테이너 안의 프로세스가 이상한 파일을 읽고 외부 주소에 연결한 정황이 잡힌다. 에이전트가 실행된 프로그램과 인자, 읽은 파일, 연결한 곳을 각각 보낸다. GuardDuty는 이 기록을 묶어 해당 리소스의 경고를 만든다.

기록 자체는 사용자에게 열려 있지 않고, 경고의 상세로만 볼 수 있다.

#4동작 과정

  1. 관찰한다에이전트가 워크로드 안에서 다음을 포착한다. process execution 은 실행된 프로그램과 실행 인자, file operations 은 읽고 쓴 파일과 권한 변경, network connections 은 연결·소켓·_BIND , dns queries 는 이름으로 주소를 물은 요청이다.
  2. 보낸다수집한 이벤트를 GuardDuty 백엔드로 넘겨 위협 탐지와 분석에 쓴다. 컨테이너·Fargate 태스크·Kubernetes Pod별로 같은 목록을 쓰고, 라이브러리 로드나 프로세스 추적 같은 기록도 여기에 든다.
  3. 결과로 알린다분석 결과가 이상 징후면 Runtime Monitoring finding 이 만들어진다. 이벤트는 그 밖의 purposes 로 쓰지 않는다.
  4. 확인해 볼 것경고 상세에서 실행된 프로그램과 파일·연결 기록이 함께 보이는지 확인한다.

에이전트의 네트워크 연결

에이전트가 관찰한 데이터를 AWS 로 보내고 구성 지시를 받을 때 어떤 통신 경로를 쓰는지, 그리고 그 통신이 VPC 엔드포인트(인터넷을 거치지 않고 AWS 서비스로 직접 이어지는 전용 연결) 같은 네트워크 요건을 어떻게 요구하는지를 다룬다.

먼저 알아야 할 것 04-02

#1문제 상황

에이전트가 붙은 워크로드에서 이벤트 전송이 안 되면 탐지 자체가 멈춘다(→ 04-02). 그래서 에이전트가 AWS로 데이터를 올리는 길이 정해져 있고, agent connectivity 가 그 경로를 가리킨다.

지정된 대상은 VPC endpoint 다. AWS PrivateLink 로 만든, 인터넷을 거치지 않고 GuardDuty 백엔드로 바로 이어지는 전용 연결 지점이며(→ 10-04), outbound connectivity 는 워크로드 밖으로 나가는 통신 그 자체를 뜻한다.

#2핵심 질문

에이전트는 어떤 경로로 GuardDuty에 데이터를 보내는가?

#3동작 예시

에이전트를 수동 설치한 팀이 이벤트가 올라가지 않는 것을 확인한다. 원인은 VPC endpoint 가 없다는 점이었다. AWS PrivateLink 로 GuardDuty용 엔드포인트를 만들자 이벤트가 전달되기 시작하고 탐지가 돌아온다.

데이터는 AWS 네트워크 안에서만 오간다.

#4동작 과정

  1. 연결 방법을 고른다GuardDuty는 두 가지 connectivity methods를 지원한다. 하나는 link-local 방식이고 다른 하나는 Amazon VPC endpoint 방식이다. 에이전트는 둘 중 가능한 쪽으로 먼저 붙으려 한다.
  2. 자동 또는 수동으로 붙인다자동 에이전트 구성이면 GuardDuty가 연결을 스스로 만든다. 수동 설치면 VPC endpoint 를 직접 만들어야 한다. link-local 방식은 리전에 따라 바뀌는 전용 주소로 접속하며 사설 DNS 를 쓰지 않는다.
  3. 신원을 대조한다GuardDuty는 instance identity roles 로 에이전트를 인증한다. Fargate 태스크는 task execution role 을 쓴다.
  4. 확인해 볼 것VPC 콘솔에서 GuardDuty 용 엔드포인트가 Available 상태인지 확인한다.

커버리지 문제와 해결

에이전트가 붙지 않은 워크로드나 예외로 제외된 통신이 어디인지 확인해 관찰 공백을 찾아내는 절차로, 현재 커버리지 상태를 확인하고 빠진 자원을 찾아 보완하는 방법이다.

먼저 알아야 할 것 04-02

→ 04-02 참조

#1문제 상황

에이전트를 붙였다고 해서 모든 워크로드가 지켜지는 것은 아니다(→ 04-02). 설정이 어긋난 자원은 조용히 데이터가 올라오지 않아 경고가 나오지 않는다. 이 공백을 찾는 것이 runtime coverage issues 다.

여기 다루는 것은 coverage and troubleshooting, 즉 커버리지 상태를 확인하고 빠진 자원을 찾아 고치는 절차이고, unhealthy instances 는 상태가 unhealthy 로 찍힌 자원을, partial coverage 는 일부만 지켜지는 상태를 가리킨다.

#2핵심 질문

내 자원이 실제로 지켜지고 있는지 어떻게 확인하는가?

#3동작 예시

온통 조용한 클러스터를 살펴보다 커버리지 통계를 연다. 몇 대가 unhealthy 로 떠 있다. 원인은 배포 도중 에이전트 설치가 중단된 것이라, 해당 인스턴스를 다시 배포하고 나서 상태가 Healthy 로 돌아오는 것을 본다.

상태가 unhealthy 인 동안은 그 자원의 런타임 동작을 전혀 보지 못한다.

#4동작 과정

  1. 세 가지를 확인한다커버리지 상태는 Runtime Monitoring 활성화, Amazon VPC endpoint 생성, 해당 자원에 대한 GuardDuty 보안 에이전트 배포로 결정된다. 셋 중 하나라도 어긋나면 unhealthy 이다.
  2. 빈틈을 찾는다커버리지 통계를 열어 unhealthy 인 자원과 partial coverage 인 자원을 찾는다. 관찰되지 않은 자원은 경고가 나올 수 없는 상태다.
  3. 알림을 건다EventBridge 알림을 구성해 상태가 바뀌면 바로 알 수 있게 한다. troubleshooting 문서를 따라 복구한다.
  4. 확인해 볼 것커버리지 화면에서 모든 대상 자원이 Healthy 로 표시되는지 확인한다.

5. 파일 안의 악성코드 — Malware Protection05-01

EC2 악성코드 보호가 도는 방식

GuardDuty Malware Protection for EC2가 EBS 볼륨의 스냅샷을 임시 볼륨에 복제해 그 안의 실행 파일을 분석해 악성코드 여부를 판정하고, 감염 시 계정을 격리하고 객체 스토리지로 증거를 남기는 자동 검사 방식이다.

먼저 알아야 할 것 03-06

#1문제 상황

기본 탐지는 API 호출 기록과 인스턴스의 가상화 수준 로그를 본다(→ 02-01). 그래서 인스턴스 안의 실행 파일이 이미 변조된 뒤에야 알아챌 수 있다.

Malware Protection for EC2 는 저장 영역을 직접 훑는다. 대상은 EBS volumes, 즉 인스턴스에 붙어 있는 블록 저장 볼륨이고, 이 안의 파일을 scanning volumes 과정에서 뒤져 악성코드 여부를 판정한다.

#2핵심 질문

인스턴스 안의 파일에서 악성코드를 어떻게 찾아내는가?

#3동작 예시

운영 중인 웹 서버 인스턴스의 볼륨을 검사한다. GuardDuty는 볼륨 스냅샷을 임시 볼륨으로 복제해 실행 파일을 분석한다. 악성코드가 나오면 경고를 만들고, 운영자 요청에 따라 볼륨을 격리하고 증거를 남긴다.

검사 과정은 인스턴스 성능에 영향을 주지 않는다.

#4동작 과정

  1. 검사 대상을 고른다스캔 시점에 특정 EC2 인스턴스를 포함하거나 제외할 수 있다. 컨테이너 워크로드의 볼륨도 대상이 된다.
  2. 볼륨을 복제해 훑는다연결된 EBS 볼륨의 스냅샷을 임시 볼륨으로 만들고 안의 파일을 분석한다. 이렇게 하는 이유는 실행 중인 인스턴스에 직접 손대지 않기 위해서다.
  3. 증거를 정한다Malware Protection for EC2 finding 이 생겼을 때만 스냅샷을 계정에 남길지 정할 수 있다. 보존된 스냅샷 이름은 guardduty-scanned-volume 으로 구분된다.
  4. 확인해 볼 것콘솔의 Protection 설정에서 스캔에 포함할 인스턴스 태그와 스냅샷 보존 여부가 보이는지 확인한다.

GuardDuty 가 스스로 시작하는 스캔

신규 또는 변경된 EC2 인스턴스를 GuardDuty 가 자동 감지해 EBS 볼륨 스냅샷을 대상으로 악성코드 스캔을 자동 실행하는 동작으로, 사용자가 스캔을 요청하지 않아도 작동한다.

먼저 알아야 할 것 05-01

#1문제 상황

EC2 악성코드 보호는 사용자가 시점을 골라 스캔을 돌릴 수도 있다(→ 05-01). 하지만 새 인스턴스가 계속 생기므로 기다릴 수는 없다.

그때 자동으로 도는 것이 GuardDuty-initiated malware scan 이다. 사용자가 스캔을 요청하지 않아도 GuardDuty가 scan trigger 를 만들어 시작한다. 계정에는 free trial 로 이 스캔이 제공되는 기간이 정해져 있다.

#2핵심 질문

새 인스턴스가 생길 때 스캔은 언제 시작되는가?

#3동작 예시

배포 파이프라인이 새 인스턴스 여섯 대를 새로 띄운다. 시간이 지나자 GuardDuty가 스스로 스캔을 시작하고, 그중 두 대에서 경고가 남는다. 사용자는 어떤 스캔을 돌릴지 정한 적이 없다.

이 스캔은 사용자가 적은 검사 대상 조건도 함께 지킨다.

#4동작 과정

  1. 사전 정리를 한다계정에 검사 대상 지정(customizations)을 해 둔다. 포함 태그로 볼 대상을 고르고 제외 태그로 건너뛸 대상을 정한다. 자동 스캔은 이 설정을 항상 지킨다.
  2. 건너뛸 방법을 정한다GuardDutyExcluded:true 태그를 EC2 자원에 붙이면 스캔은 시작된 뒤 바로 건너뛴다.
  3. 스캔을 시작한다findings that invoke malware scan 이 나타나면 GuardDuty가 스캔을 스스로 시작한다. 무료 제공 기간이 지난 뒤에는 이 자동 스캔이 요금으로 이어진다.
  4. 확인해 볼 것스캔 이력에서 GuardDuty가 시작한 항목이 사용자 요청 항목과 따로 표시되는지 확인한다.

직접 시키는 온디맨드 스캔

먼저 알아야 할 것 05-02

#1문제 상황

GuardDuty가 스스로 시작하는 스캔(→ 05-02)은 인스턴스가 새로 생기거나 바뀔 때만 돈다. 수동 스캔을 켜지 않은 계정이라면 아무 변화가 없어 내버려 둔 인스턴스를 직접 지목해 검사할 방법이 없다.

on-demand malware scan은 사용자가 직접 지목해 검사하는 방식이다. 설정 없이 인스턴트의 ARN만 주면 시작한다.

#2핵심 질문

내 원하지 않는 시점이든 골라 인스턴스 안의 악성코드를 어떻게 찾아낼까?

#3동작 예시

점검 대상 인스턴트를 정해 콘솔에서 on-demand malware scan을 요청한다. 곧 인스턴스의 볼륨 스냅샷이 복제되어 그 안의 실행 파일이 검사되고, 결과가 finding으로 남는다.

#4동작 과정

  1. 스캔을 시작한다검사할 EC2 인스턴트의 ARN을 콘솔이나 API로 넘긴다. 시작 전에 스냅샷 보관 설정을 정해 둘 수 있으며, 이 방식을 starting a scan라 부른다.
  2. 태그로 대상을 정한다인스턴스를 하나씩 나열하는 대신 태그 조건으로 대상 묶음을 지정할 수 있다. 이것이 scanning tags다.
  3. 같은 자원을 다시 본다finding에 나온 권고 조치를 수행한 뒤 같은 인스턴스를 다시 검사하려면 이전 스캔 이후 시간이 지나야 한다. 그 뒤에는 re-scanning이 가능하다.
  4. 확인해 볼 것Console의 Malware Protection for EC2 화면에서 지정한 인스턴스의 스캔 상태가 진행 중에서 완료로 바뀌는지 본다.

Malware Protection for S3는 업로드된 객체를 자동으로 검사한다. 위험 등급과 신뢰도 지표를 붙여 문제 객체를 골라낼 수 있다.

#2핵심 질문

버킷에 올라온 객체 중에 악성코드가 섞인 것은 어떻게 알아낼까?

#3동작 예시

#4동작 과정

  1. 보호를 켠다Malware Protection for S3를 GuardDuty의 일부로 쓰거나 단독 기능으로 켠다. 단독으로 켜면 별도 detector ID가 붙는다.
  2. 스캔이 돌아간다객체나 새 버전이 업로드되면 GuardDuty가 자동으로 스캔한다. 결과 상태는 S3 Object scan status로 확인한다.
  3. 태그로 막는다S3 Object scan status 값을 읽는 tag-based access control 규칙을 걸어, 위험 등급이 높은 객체만 다른 계정에 노출되지 않게 할 수 있다.
  4. 확인해 볼 것버킷 콘솔에서 객체에 붙은 S3 Object scan status 태그 값이 정상 판정으로 기록되는지 본다.

Malware Protection for AWS Backup은 AWS Backup이 만든 백업 자산을 검사한다. 복원하기 전에 위험을 알 수 있다.

#2핵심 질문

아직 되돌리지 않은 백업본 안의 악성코드를 어떻게 미리 찾아낼까?

#3동작 예시

#4동작 과정

  2. 자동으로 스캔한다AWS Backup이 보호 대상 자산을 만들거나 바꾸면 GuardDuty가 그 백업을 검사한다. 여기서 만들어진 결과가 recovery point scan이다.
  3. 원하는 때에 스캔한다지금 즉시 확인하려면 on-demand backup scan을 직접 실행한다. 진행 상황은 backup scan status로 본다.
  4. 확인해 볼 것Console의 백업 스캔 목록에서 대상 백업 자산을 고르면 결과 등급과 상태가 보인다.

관리자 계정과 멤버 계정의 관계

GuardDuty를 조직 전체에 걸칠 때 조직의 대표 계정을 관리자 계정(del administrator account), 그 아래 붙는 개별 AWS 계정을 멤버 계정(member account)이라고 부르며, 멤버 계정은 Findings 데이터만 관리자 계정으로 보내고 설정 변경은 관리자 계정 쪽에서만 이뤄진다.

administrator account and member account relationships는 계정들을 관리자 계정과 멤버 계정으로 묶는다. 멤버 계정은 aggregated findings만 올리고 설정은 관리자 계정에서만 바뀐다.

#2핵심 질문

여러 AWS 계정의 GuardDuty 설정을 한곳에서 통제하려면 어떻게 해야 하는가?

먼저 알아야 할 것 06-01

→ 06-01 참조

#1문제 상황

AWS Organizations로 여러 계정을 묶는 방법(→ 06-02) 대신, 초대를 주고받는 방식으로도 GuardDuty 조직을 만들 수 있다. 관리자 계정이 다른 계정에 초대장을 보내고, 초대받은 계정이 수락하면 그 계정은 멤버 계정(member account)이 된다. invited account는 아직 수락하기 전 상태의 계정이다. 한 계정은 관리자 계정과 멤버 계정을 동시에 맡을 수 없다.

#2핵심 질문

#3동작 예시

Custom Detection Rules 가 동작하는 방식

IAM 권한으로 클라우드 로그(CWL) 데이터를 대상으로 사용자가 직접 SQL 형식의 조건을 적어 만들어 두면, GuardDuty 가 그 로그를 주기적으로 스캔해 조건에 맞는 활동을 Finding(탐지된 의심 활동)으로 띄워 주는 사용자 정의 탐지 규칙 기능.

먼저 알아야 할 것 03-02

#1문제 상황

기본 탐지는 AWS 가 정해 둔 유형만 본다(→ 01-02). 조직마다 이상한 활동의 기준이 달라 그걸 직접 알릴 방법이 없다. Custom Detection Rules는 사용자가 만든 rule을 등록해 두고 GuardDuty 가 대신 검사하게 한다. GuardDuty managed rule는 AWS 가 직접 배포하는 기본 제공 rule이다.

#2핵심 질문

내 기준에 맞는 이상 활동이 로그에 나오면 어떻게 자동으로 알아채는가?

#3동작 예시

배포 계정에서 운영 계정으로AssumeRole 호출이 평소보다 많이 되는 것을 눈치챈다. 그 활동이 예상되지 않는 계정 목록에 맞으면 제한적인 rule을 하나 만들어 연관 계정과 연결한다. 이후 해당 활동이 보이면 GuardDuty 가 signal을 세고 finding을 띄운다.

#4동작 과정

  1. rule을 만든다데이터 소스와 조건을 적은 rule을 만들고, 의도하지 않은 활동이 일어날 계정과 연결한다. 연결마다 모드가 정해진다.
  2. 로그를 검사한다GuardDuty 가 그 rule이 의존하는 데이터 소스를 지켜보다가 들어오는 로그를 조건과 대조한다. AWS CloudTrail 관리 이벤트를 지원하며, frequency는 검사 주기 설정이다.
  3. 결과를 낸다일치하면 signal이 쌓이고 finding이 만들어진다. 모드를 Dry run으로 두면 finding 대신 CloudWatch 지표로 횟수만 셀 수 있다.
  4. 확인해 볼 것rule 목록에서 만든 rule의 연결 상태가 Live로 표시되는지 확인한다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 목록을 본다콘솔이나 ListCustomDetectionRules로 지금 쓸 수 있는 rule을 확인한다. 이 API 목록이 현재 기준으로 가장 정확하다.
  2. 지원 범위를 잰다규칙이 겨냥하는 AWS 서비스와 기능이 그 리전에 있어야 쓸 수 있다. 그래서 리전마다 보이는 rule이 다르다.
  3. 갱신을 함께 안다AWS 는 새 rule을 더하고 기존 rule을 다듬으며, 갱신마다 version이 붙는다. 그래서 rule 변경을 추적할 때 version을 본다.
  4. 확인해 볼 것rule 목록에서 이름으로 검색해 해당 rule이 활성화 가능한 상태로 뜨는지 확인한다.

먼저 알아야 할 것 07-01

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

  1. rule을 관리한다콘솔이나 API로 rule을 조회하고 수정하며 필요 없으면 삭제한다. 연결(association)은 rule과 계정을 잇고 그 연결의 모드를 live 또는 dry run으로 기록한다.
  2. 조직에 한 번에 건다delegated administrator for rules, 즉 규칙을 관리할 위임 관리자 계정이 조직 설정을 쓴다. 포함·제외 목록으로 어느 계정에 적용될지 정한다.
  3. 목록을 좁힌다콘솔의 규칙 목록은 이름·심각도·데이터 소스·전술·서비스 등의 필터로 줄일 수 있다. API로는 ListCustomDetectionRules를 쓴다.
  4. 확인해 볼 것rule 목록에서 만들고 싶은 rule이 검색되는지, 그 rule의 상태가 rule status에 어떻게 표시되는지 확인한다.

콘솔의 Findings 페이지

GuardDuty가 탐지한 모든 경고를 목록으로 모아 놓은 콘솔 화면으로, 각 행을 선택하면 해당 경고의 상세 정보·관련 리소스·조사(Investigation) 탭이 열린다.

먼저 알아야 할 것 08-01

#1문제 상황

탐지가 일어나면 알림만 오고 그 내용을 볼 자리는 콘솔 안에 흩어져 있었다. GuardDuty 콘솔의 Findings 페이지(경고 목록 화면)는 탐지된 모든 경고를 표로 모아 한곳에 보여 준다.

그래서 경고의 상세 정보와 그 경고가 얹힌 리소스 목록까지 한 화면에서 확인해 조사를 시작할 수 있다.

#2핵심 질문

탐지된 경고를 한곳에 모아 보고 그 안의 리소스까지 어떻게 확인하는가?

#3동작 예시

심각도 높은 EC2 경고가 새로 떴다. 운영자가 Findings 페이지로 가서 목록 맨 위에 있는 행을 고른다.

경고의 발생 시각, 관련 리소스, 그리고 조사(Investigation) 탭이 열린다.

#4동작 과정

  1. 목록을 연다콘솔 왼쪽 탐색 창에서 Findings를 고르면 경고가 표로 나온다. 기본 정렬은 마지막 확인 시각 내림차순이라 최근 경고가 위에 뜬다.
  2. 행을 고른다각 행을 누르면 finding details, 즉 그 경고의 상세 정보가 열린다. 칼 아이콘이 붙은 행은 여러 단계를 잇는 공격 시퀀스 경고다.

먼저 알아야 할 것 08-02

#1문제 상황

경고가 쌓일수록 목록 전체를 훑어야 한다. filtering GuardDuty findings는 기준을 골라 조건에 맞는 경고만 남기는 기능이다.

집계로 묶어 건수를 세면 어떤 출처가 문제인지 바로 드러난다.

#2핵심 질문

수많은 경고 중 조건에 맞는 것만 좁혀서 보여 주려면?

#3동작 예시

심각 등급 경고가 갑자기 늘었다. 운영자가 필터에서 계정 ID와 Findings 그룹을 골라 목록을 줄인다.

남은 경고를 finding aggregation으로 묶어 어느 그룹이 몇 건인지 본다.

#4동작 과정

  1. 기준을 고른다콘솔이나 CreateFilter API로 필터를 만든다. 기준 속성은 최소 1개 최대 50개까지 담을 수 있고, 서로 다른 속성은 AND로 묶인다.
  2. 값을 좁힌다계정 ID 같은 값에 Equals나 Does not equals를 쓰면 값은 최대 50개까지 넣는다. 같은 속성에 여러 값을 넣으면 그 안에서는 AND와 OR로 판정된다.
  3. 묶어 센다grouping findings로 묶어 건수를 낸다. 경고에는 확인하지 않은 새 경고와 이미 본 경고를 구분하는 lifecycle metadata가 함께 붙어 있어 필터 조건으로 쓸 수 있다.
  4. 확인해 볼 것필터를 적용한 뒤 목록 건수가 줄어들고, 조건을 지우면 원래 목록으로 돌아오는지 본다.

먼저 알아야 할 것 08-03

#1문제 상황

규칙에 맞는 새 경고는 목록에서 사라져 주의할 것만 남는다.

#2핵심 질문

무시해도 되는 경고를 자동으로 숨겨 두려면?

#3동작 예시

내부 점검 도구가 매시간 특정 IP를 호출해 같은 경고가 반복된다. 운영자가 그 IP를 조건으로 넣은 억제 규칙을 만든다.

이후 같은 IP에서 온 경고는 새로 뜨지 않는다.

#4동작 과정

  1. 규칙을 만든다creating suppression rules는 기존 필터에서 만들거나 새 필터를 정의해 시작한다. filter criteria로 경고 유형 전체를 무효화할 수도, 유형 안에서 특정 경우만 좁혀 무효화할 수도 있다.
  2. 저장한다규칙은 언제든 고칠 수 있다. 조건에 맞는 새 경고는 규칙이 있는 동안 자동으로 보관된다.
  3. 지표를 본다suppression rule metrics로 어떤 경고가 얼마나 억제됐는지 확인한다. 공용 알림 체계의 오탐도 줄이는 효과가 있다.
  4. 확인해 볼 것규칙을 만든 뒤 해당 IP에서 나는 새 경고가 목록에 뜨지 않는지 본다.

먼저 알아야 할 것 08-04

#1문제 상황

내 소유 도구에서 오는 활동은 위험하지 않은데 경고로 잡힌다. entity lists와 IP address lists는 신뢰 목록과 위협 목록을 미리 등록해 탐지 범위를 조정하게 해 준다.

등록 대상의 경고는 아예 생성되지 않아 목록이 조용해진다.

#2핵심 질문

신뢰하는 대상과 알려진 악성 대상을 미리 등록해 탐지를 조정하려면?

#3동작 예시

보안팀이 사내 스캐너의 IP 대역을 신뢰 목록에 넣고, 특정 도메인을 위협 목록에 올린다.

이후 그 IP의 경고는 뜨지 않고, 위협 목록의 통신은 경고로 남는다.

#4동작 과정

  1. 목록을 정한다entity lists는 IP 주소, 도메인, 알려진 도구·악성코드 식별자를 담을 수 있는 목록이다. 기존의 IP address lists도 계속 지원되지만 entity lists가 권장 방식이다.
  2. 올리고 켠다adding and activating a list로 S3 bucket for lists에 목록을 올려 등록한다. 목록 상태를 확인해 활성 여부를 본다.
  3. 탐지 범위를 정한다신뢰 목록에 든 출처에서는 경고를 만들지 않고, 위협 목록에 든 출처에서는 경고를 만들도록 GuardDuty가 판단한다.
  4. 확인해 볼 것목록을 등록한 뒤 신뢰 IP에서 온 경고가 더 이상 생성되지 않는지 본다.

  3. 복구 지점을 만든다take EBS snapshot으로 증거와 복구용 사본을 남긴 뒤 깨끗한 이미지로 교체한다.

S3 버킷과 오브젝트 조치

S3 Protection 이 버킷 정책 변경이나 오브젝트 웹 접근성 악용 같은 위험 탐지를 발견했을 때, 공개 노출된 접근 정책을 되돌리고 악성코드가 붙은 오브젝트를 격리·삭제하며 VPC 엔드포인트 방식 복구 지점을 만드는 절차.

먼저 알아야 할 것 08-02

#1문제 상황

버킷 정책이 몰래 느슨해지거나 오브젝트가 웹에 그대로 열리면(→ 08-02) 버킷 전체가 노출될 수 있다. GuardDuty 는 그 사실을 알려 주기까지가 끝이고, 실제로 막는 일은 사람이 한다.

S3 버킷과 오브젝트 조치는 그 막는 순서를 정해 준다. 공개를 되돌리고 문제를 좁힌 뒤 복구 지점을 남긴다.

#2핵심 질문

침해가 의심되는 S3 버킷과 오브젝트를 어떤 순서로 닫고 복구하는가?

#3동작 예시

Findings 목록에서 버킷 정책가 바뀐 탐지 항목을 연다. 상세에 버킷 이름·ARN·바뀐 API 호출·출처 IAM 주체가 함께 나온다. 운영자는 그 주체부터 지우고 정책 변경 이력을 되돌린다.

다음으로 같은 계정이 올린 오브젝트에 악성코드가 붙은 경우를 확인하고 해당 오브젝트만 격리한다.

#4동작 과정

  1. 지점을 좁힌다remediating a potentially compromised S3 bucket 절차로 버킷 ARN과 쓰인 API 호출, IAM 주체와 원격 IP를 읽어 어디서 들어왔는지 본다. 이 값들이 finding 상세에 함께 나온다.
  2. 공개를 닫는다Block Public Access 설정을 켜고 바뀐 버킷 정책 항목을 지운다. remediating a potentially malicious S3 object 절차로 악성코드가 붙은 오브젝트만 복사해 격리 태그를 단다.
  3. 되돌릴 지점을 남긴다recovery point, 즉 되돌릴 수 있는 사본을 남겨 두고 그 뒤 경고를 확인한다. 이 동작이 환경에서 원래 기대된 일이라면 Suppression rules(→ 08-04)로 이후 경고를 숨긴다.
  4. 확인해 볼 것Findings 상세에서 버킷 ARN과 사용된 API 호출이 보이는지 확인한다.

EBS 스냅샷과 AMI 조치

EC2 가 침해되어 EBS 볼륨 스냅샷이나 AMI 이미지가 감염될 수 있을 때, 스냅샷과 이미지를 신뢰할 수 없는 상태로 취급해 격리하고 새로 만든 깨끗한 이미지로 교체하는 절차.

먼저 알아야 할 것 09-01

#1문제 상황

인스턴스가 해킹당하면 그 인스턴스를 떠서 만든 EBS 스냅샷과 AMI 이미지도 그대로 복제된다(→ 09-01). 이미지에 악성코드가 남아 있으면 나중에 그 이미지로 다시 띄운 모든 인스턴스가 감염된다.

EBS 스냅샷과 AMI 조치는 복제본을 신뢰하지 못하게 취급하고 새로 만든 깨끗한 이미지로 바꾸는 순서를 정한다.

#2핵심 질문

감염될 수 있는 스냅샷과 이미지를 어떻게 격리하고 교체하는가?

#3동작 예시

악성코드 스캔이 걸린 스냅샷이 담긴 AWS Backup 복구 지점 경고가 Findings 에 뜬다. 운영자는 스냅샷 ID와 ARN, 스캔 결과를 확인한 뒤 그 스냅샷을 쓰는 자동 복원 작업을 멈춘다.

그다음 스냅샷의 공유 권한에서 다른 계정 접근을 떼고, 해당 스냅샷으로 만든 AMI 를 등록 해제한다.

#4동작 과정

  1. 복제본과 사용처를 확인한다탐지 항목에서 스냅샷 ID·ARN과 악성코드 스캔 결과를 읽고 AWS Backup 의 recovery point 접근을 제한한 뒤 이 스냅샷을 쓰는 자동 복원 작업을 일시 정지한다. remediation 은 사실 확인에서 출발한다.
  2. 공유를 끊는다스냅샷의 공유 권한에서 특정 계정 항목을 제거한다. 스냅샷과 AMI 가 다른 계정에 넘쳐 있으면 그 자리에서 더 퍼진다.
  3. 이미지를 갈아 끼운다해당 스냅샷으로 만든 AMI 를 deregister AMI 로 등록을 해제하고 깨끗한 것으로 만든다. 이미지를 못 쓰게 하려면 그 AMI 에서 뜬 인스턴스도 함께 정리한다.
  4. 확인해 볼 것스냅샷의 공유 권한 목록에 남은 계정이 없는지 확인한다.

자격 증명 조치

GuardDuty 가 노출되거나 악용된 IAM 자격 증명(액세스 키·사용자)을 찾아내면 해당 자격 증명을 비활성화하고 대신 사용할 신원(users)을 지시하며, 침해 계정이 접근한 리소스 목록까지 함께 제시하는 절차.

먼저 알아야 할 것 09-01

#1문제 상황

키가 새 코드에 박히면 그대로 넘어가서 아무도 모르게 쓰인다(→ 10-01). 키를 지워도 이미 그 키로 들어간 리소스에는 흔적이 남는다.

자격 증명 조치는 키를 막는 일과, 그 키로 어디까지 들어갔는지 확인하는 일을 한 번에 제시한다.

#2핵심 질문

잘못 쓰인 자격 증명을 어떻게 닫고 그 영향 범위를 어디까지 확인할까?

#3동작 예시

Findings 를 열어 악용된 자격 증명 항목을 선택한다. Resource 유형이 AccessKey 로 뜨고, 어디서 쓰였는지와 사용된 API 호출이 함께 나온다. 운영자는 해당 키를 바로 비활성화하고, 키를 어디다 새 파일에 넣었는지 찾아 지운다.

#4동작 과정

  1. 키를 특정한다탐지 항목의 Resource 영역에서 IAM 역할 또는 사용자를, User Type·User name·Access key ID 로 구분한다. AKIA 로 시작하는 키는 사용자나 루트 계정에 묶인 장기 키다.
  2. 키를 닫는다deactivate access keys 로 그 키를 비활성화한다. IAM 역할이 원인이라면 역할을 쓰는 곳까지 좁혀지고, 같은 유형이 계속 뜨면 원인을 더 찾아야 한다.
  3. 넘어간 곳을 본다키로 접근한 계정과 리소스 목록을 확인해 아직 남은 자산을 훑는다. 대상은 자격 증명이 붙은 종류에 따라 달라진다. standalone container 처럼 자격 증명이 따로 붙지 않은 곳은 로그를 보고 수동으로 막아야 한다.
  4. 확인해 볼 것탐지 항목에서 Resource 유형이 AccessKey 로 표시되는지 확인한다.

데이터베이스와 Lambda 조치

RDS Protection 과 Lambda Protection 이 각각 데이터베이스 로그와 함수 로그에서 위험 동작을 탐지했을 때, 연결을 차단하거나 함수를 격리하고 코드·권한을 점검해 다시 안전하게 돌릴 수 있게 하는 절차.

먼저 알아야 할 것 09-04

#1문제 상황

데이터베이스 로그에서 비정상 로그인이 잡히고 함수 로그에서 의심스러운 실행이 잡힌다(→ 06-06 에서 다룬 RDS Protection 과 Lambda Protection). 둘 다 로그만으로 결정이 나지 않는다.

데이터베이스와 Lambda 조치는 로그를 근거로 연결을 끊고 함수와 권한을 점검하는 순서를 각각 제시한다.

#2핵심 질문

비정상 로그인과 의심 함수 실행을 각각 어디서부터 막는가?

#3동작 예시

RDS Protection 이 존재하지 않는 자격으로 반복 로그인을 시도해 경고를 낸다. 운영자는 로그인 성공 기록과 실패 기록 중 어느 쪽인지 경고 종류로 구분해 본다.

Lambda 쪽에서도 의심 경고가 올라와 어느 함수에서 실행됐는지 함수 이름으로 좁힌 뒤 코드를 다시 본다.

#4동작 과정

  1. 문제를 나눈다경고 종류가 로그인 성공인지 실패인지, 데이터베이스인지 함수인지부터 갈라 본다. RDS Protection remediation 은 성공 로그인과 실패 로그인에 대해 따로 권장 절차를 낸다.
  2. 네트워크를 좁힌다데이터베이스 쪽은 RDS Protection remediation 절차로 네트워크 접근을 제한해 그 경로의 접속을 막고, 의심 함수는 격리해 호출되지 않게 한다. Lambda 는 코드째 배포되므로 함수만 막아도 같은 코드가 다시 돌아오지 않는다.
  3. 코드를 다시 본다막고 나면 함수의 코드와 실행 권한, 데이터베이스에 쓰이는 자격 증명을 점검해 되돌린다. 자격 증명은 → 09-04 절차로 처리한다.
  4. 확인해 볼 것Findings 상세에 사용된 API 호출과 대상 리소스가 함께 보이는지 확인한다.

EKS Protection 과 Runtime Monitoring 조치

Kubernetes Protection 과 Runtime Monitoring 이 클러스터와 컨테이너 런타임에서 의심스러운 동작(비루트 실행, 비정상 드로잉 등)을 잡아내면, 워크로드 실행 권한을 차단하고 클러스터·노드를 격리해 멈추게 하는 절차.

먼저 알아야 할 것 09-01

#1문제 상황

클러스터 설정이 느슨하거나 컨테이너가 권한을 남용하면 워크로드 하나가 풀 접근을 얻는다(→ 04-01). 컨테이너 안의 의심 동작은 바깥 로그로는 잘 안 드러난다.

EKS Protection 과 Runtime Monitoring 조치는 사용자·파드·컨테이너 이미지·노드별로 막는 순서를 따로 나눠 둔다.

#2핵심 질문

클러스터에서 의심 동작이 나오면 무엇을 먼저 막고 무엇을 격리하는가?

#3동작 예시

EKS audit log findings 가 올라와 어떤 사용자가 kubectl 명령으로 권한을 넓혔는지 보인다. 운영자는 그 사용자와 파드를 좁힌 뒤 클러스터 접근 권한을 먼저 거둔다.

Runtime Monitoring 경고에서는 어떤 컨테이너가 비루트로 실행됐는지 보고 그 워크로드의 실행을 멈춘다.

#4동작 과정

  1. 문제를 나눈다EKS Protection 과 Runtime Monitoring 경고는 성격이 달라 따로 본다. 클러스터 쪽은 EKS audit log findings 로 사용자·파드·노드·이미지를 보고, 런타임 쪽은 실행 중인 컨테이너 안을 본다.
  2. 권한을 거둔다워크로드가 실행되거나 클러스터에 접근할 권한을 먼저 차단한다. 실행을 멈추면 뒤따르는 피해가 같이 끊긴다.
  3. 격리한다문제가 된 파드와 노드를 클러스터에서 떼어 내 멈추고, 오염된 컨테이너 이미지로 다시 뜨지 않게 한다. 원래 기대된 동작이면 Suppression rules 로 경고를 숨긴다(→ 08-04).
  4. 확인해 볼 것탐지 항목에서 오염된 리소스의 이름과 사용된 API 호출이 보이는지 확인한다.

10. 권한과 감사 — 기록이 남는 자리10-01

GuardDuty 와 IAM 의 관계

IAM(누가 어떤 AWS 자원에 무엇을 할 수 있는지 정하는 권한 관리 서비스) 정책으로 GuardDuty 가 볼 수 있는 데이터와 켤 수 있는 기능을 통제하며, 서비스 전체를 하나의 IAM 서비스로 다룰 때는 별도의 권한 문서를 함께 봐야 한다.

먼저 알아야 할 것 06-01

#1문제 상황

GuardDuty 를 켤 수 있는 사람과 볼 수 있는 사람이 아무 제한 없이 같으면, 경고 내용을 잘못 본 사람이 조직 전체의 보안 상황을 알게 된다(→ 06-01 에서 다룬 계정 구조 위에서).

GuardDuty 는 자체 권한 문서를 따로 두고, 실제로 지켜지는 권한은 IAM 이 정한다.

#2핵심 질문

누가 GuardDuty 를 켜고 볼 수 있는지를 어떻게 정하고 관리하는가?

#3동작 예시

신입이 GuardDuty 콘솔을 열자 목록 조회는 되지만 보호 계획을 켜는 버튼이 비어 있다. 관리자가 IAM 정책에 켜기 권한을 붙여 준 뒤에야 그 버튼이 눌린다.

관리자가 다른 계정의 경고를 대신 관리하려 할 때는 위임 관리자 권한을 따로 줘야 한다.

#4동작 과정

  1. 사람을 나눈다GuardDuty 의 사용자는 세 갈래로 나뉜다. 서비스 사용자는 권한을 요청하고, 서비스 관리자는 접근을 정해 요청을 올리고, IAM 관리자는 정책 문서를 직접 쓴다.
  2. 정책으로 막는다identity-based policies 를 iam policy 로 붙여 누가 켤 수 있고 볼 수 있는지를 정한다. 아무 정책도 없으면 아무도 권한을 갖지 못한다.
  3. 권한을 나눠 준다몇몇 조회는 읽기 권한만 요구한다. Findings 를 보는 권한은 guardduty:ListFindings 같은 API 동작 단위로 요구되며, 어떤 주체가 통과하는지는 IAM policy simulator 에서 확인한다. 막히면 Troubleshooting Amazon GuardDuty identity and access 항목을 따라간다.
  4. 확인해 볼 것policy simulator 에서 guardduty:ListFindings 권한을 넣고 어떤 주체가 통과하는지 확인한다.

10. 권한과 감사 — 기록이 남는 자리10-02

서비스 연결 역할

서비스 연결 역할은 AWS 서비스가 사용자를 대신해 리소스에 접근할 때 자동 생성되는 전용 IAM 역할로, GuardDuty 는 이 역할이 맡는 권한 범위를 정해 어느 리소스를 대신 감시할지 결정한다.

먼저 알아야 할 것 10-01

#1문제 상황

GuardDuty는 사용자를 대신해 다른 AWS 서비스에 접근해 데이터를 모아야 한다(→ 10-01). 이때 필요한 권한을 하나씩 손으로 붙이면 빠뜨린 권한 때문에 탐지가 중간에 막힌다.

service-linked roles는 AWS 서비스가 사용자를 대신해 자원에 접근할 때 자동으로 만들어지는 전용 IAM 역할이다. GuardDuty service-linked role은 GuardDuty가 필요로 하는 permissions를 모두 담고 있으며, 이름은 AWSServiceRoleForAmazonGuardDuty다.

#2핵심 질문

GuardDuty가 대신 자원에 접근할 권한을 어디서 얻는가?

#3동작 예시

관리자가 GuardDuty를 켠다. 콘솔에서 별도 권한 요청 없이 탐지가 시작되고, IAM 콘솔에는 AWSServiceRoleForAmazonGuardDuty 이름의 역할이 이미 보인다.

이 역할을 누가 만들었는지, 어떤 권한이 들어 있는지 그 자리에서 확인한다.

#4동작 과정

  1. 자동으로 만들어진다GuardDuty를 켜면 서비스 연결 역할이 만들어진다. permissions는 GuardDuty가 미리 정해 둔 것이며 이 역할은 GuardDuty만 사용할 수 있다.
  2. 다른 곳에 붙이지 못한다이 역할의 권한은 trust policy와 permissions policy로 나뉘어 있다. permissions policy는 다른 IAM 주체에 붙일 수 없다.
  3. 삭제는 끄고 나서모든 리전에서 GuardDuty를 먼저 끈 뒤에야 이 역할을 지울 수 있다.
  4. 확인해 볼 것IAM 콘솔에서 AWSServiceRoleForAmazonGuardDuty 역할을 열어 신뢰 관계가 GuardDuty로 되어 있는지 본다.

CloudTrail 로 남기는 기록

GuardDuty 는 누가 어떤 설정을 바꾸었는지 AWS CloudTrail 이라는 서비스 감사 로그에 API 호출 형태로 남기므로, 권한 변경이나 탐지 결과 설정을 사후에 확인할 수 있다.

먼저 알아야 할 것 10-01

#1문제 상황

보호 계획을 켜고 끄고 권한을 바꾼 사람이 누구인지 사후에 알 수단이 없다. 설정이 틀어져도 언제 어떻게 바뀌었는지 찾지 못한다.

logging with CloudTrail은 GuardDuty 콘솔 화면에서 한 요청과 GuardDuty API를 코드에서 호출한 것까지 모두 잡아 기록한다. 누가 언제 어느 IP에서 무엇을 요청했는지 남는다.

#2핵심 질문

누가 언제 GuardDuty 설정을 바꿨는지 어떻게 확인하는가?

#3동작 예시

담당자가 전환기에 몰린 권한을 정리하려고 IAM 권한을 여러 개 지웠다. 며칠 뒤 그 변경이 사고에 관련됐는지 확인해야 한다.

CloudTrail 이벤트 히스토리에서 그 시간대 GuardDuty API 호출을 찾아 요청자와 IP를 확인한다.

#4동작 과정

  1. API 호출을 잡는다콘솔 조작과 API 호출이 모두 이벤트가 되어 남는다. audit trail로 어떤 요청이 있었는지 확인할 수 있다.
  2. management events로 묶어 본다계정이 만들어질 때 CloudTrail이 켜지므로 관리자 계정 변경 같은 기록은 별도 설정 없이 볼 수 있다.
  3. 오래 보관하려면 트레일을 만든다트레일을 만들면 이벤트를 S3 버킷에 계속 전달해 두어 오래 남길 수 있다. 트레일이 없으면 Event history에서 최근 이벤트만 본다.
  4. 확인해 볼 것CloudTrail 콘솔의 Event history에서 GuardDuty 관련 이벤트를 시간순으로 찾아 본다.

VPC 엔드포인트로 사설 연결

VPC 엔드포인트는 인터넷을 거치지 않고 AWS 내부망만 통해 GuardDuty 같은 서비스로 안전하게 통신하게 해 주는 연결 지점으로, 이렇게 하면 트래픽이 외부로 나가지 않아 데이터 보호 요건을 맞출 수 있다.

먼저 알아야 할 것 10-03

#1문제 상황

VPC 안의 서버가 GuardDuty API를 호출하려면 인터넷 게이트웨이나 NAT 장치를 거쳐야 한다. 트래픽이 밖으로 나가는 순간 데이터 보호 요건을 어기게 된다.

VPC endpoints (AWS PrivateLink)를 쓰면 그 연결을 없앨 수 있다. GuardDuty는 S3 findings도 이 경로로 받아 볼 수 있다.

#2핵심 질문

GuardDuty API를 인터넷을 거치지 않고 사설로 호출하려면?

#3동작 예시

공개 IP를 배정받지 못해 외부로 나갈 수 없는 서브넷의 인스턴스에서 GuardDuty 콘솔을 연다. 탐지 결과가 정상적으로 보인다.

이때 outbound 통신이 AWS 내부망 안에서만 오간 것을 VPC 흐름 로그에서 확인한다.

#4동작 과정

  1. 엔드포인트를 만든다interface VPC endpoint를 만들어 서브넷에 Elastic Network Interface가 붙는다. 인스턴스는 Public IP가 없어도 GuardDuty API와 통신한다.
  2. 경로를 내부망으로 묶는다VPC와 GuardDuty 사이 트래픽이 Amazon network 안에서만 오간다. PrivateLink는 GuardDuty가 쓸 수 있는 리전에서 모두 동작한다.
  3. S3 findings도 이 길로 받는다GuardDuty가 만든 S3 findings 버킷을 쓸 때도 사설 경로를 통해 findings를 읽어 온다.
  4. 확인해 볼 것VPC 콘솔에서 엔드포인트 목록에 GuardDuty 항목이 있는지 확인한다.

컴플라이언스 검증과 데이터 보호

컴플라이언스 검증은 GuardDuty 가 여러 산업 규제 기준에 맞는 보안 상태인지 확인하는 절차이고, 데이터 보호는 탐지한 threat 를 어디에 저장하고 얼마나 보관할지 정해 개인정보와 기업 데이터 노출을 막는 수단이다.

먼저 알아야 할 것 10-03

#1문제 상황

규제 대상 업무에 GuardDuty를 쓰려면 이 서비스가 검사 대상 범위에 들어오는지 먼저 확인해야 한다. 확인 없이 켜면 데이터가 어디에 저장되는지 모른 채로 운영하게 된다.

data protection는 탐지한 데이터를 어디에 두고 얼마나 오랫동안 지킬지 정해 노출을 막는 수단이다. complying 범위는 AWS Artifact에서 받는 제3자 감사 보고서로도 확인한다.

#2핵심 질문

규제 요건을 만족하는지, 내 데이터는 어디에 저장되는가?

#3동작 예시

회사가 의료 규제 대상 서비스에 GuardDuty를 도입한다. AWS Artifact에서 해당 서비스의 감사 보고서를 받아 범위를 확인하고, 저장 위치와 보관 기간을 팀 정책에 맞춰 설정한다.

#4동작 과정

  1. 범위부터 확인한다compliance validation은 어떤 서비스가 어떤 컴플라이언스 프로그램에 들어 있는지 대조해 본다. 프로그램 목록과 범위 문서를 함께 본다.
  2. 책임 지점을 정한다데이터 민감도와 회사 목표, 적용 법규에 따라 고객과 AWS가 각각 맡는 책임이 나뉜다.
  3. 데이터 사용을 정한다data protection은 탐지 데이터를 저장할 위치와 보관 기간을 정한다. 사용자의 데이터 활용에서 빠지려면 opting out of using your data를 선택할 수 있고, GuardDuty는 service improvement을 위해 익명 통계에 참여한다.
  4. 확인해 볼 것AWS Artifact에서 GuardDuty가 포함된 감사 보고서 목록을 열어 본다.

Security Hub 통합

GuardDuty 가 찾아낸 보안 위협(security finding)을 Amazon Security Hub 이 여러 서비스의 경보를 한곳에 모으는 허브로 자동 전송해, 다른 서비스의 경보와 함께 한 화면에서 대응할 수 있게 하는 기능이다.

먼저 알아야 할 것 08-06

#1문제 상황

탐지 결과가 GuardDuty 콘솔에만 있으면 다른 서비스가 알려 주는 경보와 나란히 비교할 수 없다(→ 08-06). 여러 콘솔을 번갈아 열어야 어느 문제가 급한지 판단한다.

AWS Security Hub CSPM integration은 GuardDuty의 findings를 Security Hub로 보내 findings aggregation이 한 목록에 모이게 한다.

#2핵심 질문

GuardDuty의 경보를 다른 보안 경보와 한곳에서 같이 볼 수 있는가?

#3동작 예시

GuardDuty가 EC2 인스턴스에서 이상 행동을 찾아 finding을 만든다. 같은 시간에 Security Hub의 다른 검사 결과도 올라온다.

한 화면에서 두 경보를 나란히 보고 어느 쪽을 먼저 처리할지 정한다.

#4동작 과정

  1. 연동을 켠다GuardDuty 콘솔에서 Security Hub CSPM으로 findings를 보내도록 연동을 활성화하고 설정한다.
  2. 보낸다findings aggregation을 통해 GuardDuty의 finding이 Security Hub가 여러 계정·서비스에서 모은 보안 상태 분석에 포함된다.
  3. 사용자가 정한다내보내기 대상에서 Security Hub를 빼거나 다시 붙일 수 있다. 내보내기 자체는 EventBridge 규칙으로 관리된다(→ 08-06).
  4. 확인해 볼 것Security Hub CSPM 콘솔의 목록에서 GuardDuty에서 온 finding이 함께 뜨는지 본다.

Detective 통합

GuardDuty 가 생성한 위협Finding의 관계를 Amazon Detective 로 보내 조사 그래프를 만들게 하여, 한 finding 에 연관된 아이콘·사용자·IP 같은 범위까지 함께 살펴볼 수 있게 하는 연동이다.

먼저 알아야 할 것 08-06

#1문제 상황

finding 하나가 계정, IAM role, EC2 인스턴스, 외부 IP 여러 대상을 엮고 있다. 각각을 다른 화면에서 하나씩 찾아보면 한 번의 공격이 어디까지 이어졌는지 알기 어렵다.

Amazon Detective integration은 finding의 관계를 investigation graph로 그려 한 화면에서 추적하게 한다.

#2핵심 질문

finding 하나에 얽힌 여러 대상의 관계를 어떻게 한 번에 살펴보는가?

#3동작 예시

GuardDuty 콘솔에서 finding 하나를 열어 related entities를 따라 Amazon Detective로 넘어간다. investigation 그래프에 계정과 IP 주소가 시간순으로 연결되어 있다.

같은 finding 안에서 어느 IP가 먼저 들어와 무엇을 건드렸는지 investigation을 이어 간다.

#4동작 과정

  1. 먼저 Detective를 켠다enable Detective를 먼저 끝내야 GuardDuty와 연동된다.
  2. finding 상세를 받는다Detective는 모든 finding type의 상세를 받아 entity profile로 보여 준다. entity는 계정, 계정 안 리소스, 외부 IP 주소가 될 수 있다.
  3. 그래프에서 훑는다콘솔에서 계정·IAM role·사용자·세션·사용자 에이전트·federated user·EC2 인스턴스·IP 주소 중 해당하는 entity에서 Detective로 넘어갈 수 있다.
  4. 확인해 볼 것finding 상세에서 Amazon Detective로 넘어가면 investigation 그래프가 뜨는지 본다.

Managed Instances 지원

GuardDuty 를 조직이나 엔터프라이즈 라이선스가 있는 계정에서 AWS 가 대신 설치·관리하게 해, 고객이 에이전트를 직접 배포하지 않고도 여러 계정에 threat detection 을 적용할 수 있게 하는 지원 기능이다.

먼저 알아야 할 것 04-02

#1문제 상황

Runtime Monitoring은 EC2·EKS·ECS 워크로드마다 보안 에이전트를 직접 붙여야 한다(→ 04-02). 계정이 많으면 설치와 갱신을 누락되고, 붙은 곳과 빠진 곳을 따로 관리해야 한다.

Managed Instances Support은 그 설치와 관리를 AWS가 맡는 방식이다. Managed Instances는 AWS가 대신 관리하는 컴퓨팅 환경 하나로, Lambda 실행 환경처럼 직접 에이전트를 붙일 수 없는 곳에도 protection plan coverage를 넓힌다.

#2핵심 질문

에이전트를 직접 배포하지 않고 여러 계정에 threat detection을 적용하려면?

#3동작 예시

조직 아래 계정들의 EC2 인스턴스를 GuardDuty 대시보드에서 본다. 계정마다 에이전트 설치 작업을 지시하지 않았는데도 인스턴스가 관리 대상 목록에 올라와 있다.

인스턴스 하나를 열어 어떤 컴퓨팅 환경에서 관리되는지 확인한다.

#4동작 과정

  1. 활성화한다조직이나 엔터프라이즈 라이선스가 있는 계정에서 Managed Instances Support을 켠다. 켜는 작업은 관리자 계정 쪽에서 한다.
  2. 관리 대상이 된다대상 컴퓨팅 환경이 Managed Instances로 등록되어 AWS가 에이전트 설치를 대신한다. 등록된 환경 안에서 protection plan coverage가 적용되는 범위를 본다.
  3. 범위를 확인한다지원 조합을 표에서 본다. Runtime Monitoring은 Amazon ECS와 AWS Fargate의 Managed Instance에서 지원되지 않지만 Malware Protection for EC2는 지원되며, Lambda Managed Instance는 두 기능 모두 지원되지 않는다. Javascript 코드가 꺼져 있어 이 표는 웹 문서에서 직접 확인해야 한다.
  4. 확인해 볼 것GuardDuty 콘솔에서 관리 중인 인스턴트 목록을 열어 어떤 컴퓨팅 환경으로 분류되는지 확인한다.

멈추는 법과 운영 경계

보호 계획(protection plan)을 일시 중지(suspend)하거나 완전히 비활성화(disable)하는 방법과, GuardDuty 가 지원하지 않는 리전·리소스 종류·사용량 한계 같은 운영상의 경계를 정리한 내용이다.

먼저 알아야 할 것 11-01

#1문제 상황

탐지 비용이 늘거나 계정 구조가 바뀌어 GuardDuty를 멈춰야 할 때가 온다. 멈추는 방법은 두 가지라 어떤 쪽을 골라도 결과가 달라진다.

Suspending or disabling은 각각 일시 정지와 완전 비활성화다. Regions and endpoints가 지원되지 않는 곳에서는 계정을 그대로 둘 수 없고, GuardDuty quotas와 troubleshooting 항목이 따로 있어 그 경계를 미리 알아야 한다.

#2핵심 질문

탐지를 잠시 멈추거나 완전히 끄려면 어떻게 하고 무엇을 먼저 확인해야 할까?

#3동작 예시

테스트 계정의 GuardDuty를 정리하려고 콘솔에서 보호 계획을 정지한다. 이후 며칠 뒤 다시 켜려 같은 화면을 연다.

기존 탐지 항목이 그대로 남아 있는 것을 보고 결정이 왜 달라졌는지 확인한다.

#4동작 과정

  1. 멈춘다정지(suspend)하면 요금이 붙지 않고 새 finding도 생성되지 않지만 기존 finding은 남는다. 나중에 다시 켤 수 있다.
  2. 끈다비활성화(disable)는 선택한 리전에서만 적용된다. 완전히 끄려면 켜진 모든 리전에서 각각 반복해야 하며, 기존 finding과 설정은 사라지고 복구되지 않는다.
  3. 사전 준비한다계정 조직에 멤버 계정이 남아 있으면 정지와 비활성화가 막히므로 먼저 분리하거나 삭제해야 한다. 남길 finding은 비활성화 전에 내보내고, Regions and endpoints 목록에서 지원 여부를 본다. 한계는 GuardDuty quotas 문서에서, 남은 문제는 troubleshooting 절차로 처리한다.
  4. 확인해 볼 것콘솔의 보호 계획 화면에서 상태가 정지인지 비활성화인지 표시되는지 확인한다.
