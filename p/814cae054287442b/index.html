이어서 읽기
1GitOps와 Argo CD 첫걸음뒤의 모든 설정이 무엇을 위한 것인지 알려면 GitOps 모델과 핵심 용어, 동작하는 설치 한 벌이 먼저 있어야 한다.42시스템 구조어떤 프로세스가 무엇을 책임지는지 알아야 뒤에 나오는 설정 키와 장애 증상이 어디에 속하는지 판단할 수 있다.53Application 리소스Argo CD가 다루는 대상 자체를 정확히 알아야 이후의 소스 도구·동기화 옵션이 어느 필드에 붙는지 이해된다.64매니페스트 생성 도구target state는 저장소 파일에서 만들어진다. 어떤 도구가 어떤 입력을 받아 매니페스트를 뽑는지가 이후 diff의 근원이다.75소스 접근과 무결성매니페스트를 어디서 어떻게 가져오는지가 안전하게 정해져야 실제 운영 저장소를 붙일 수 있다.56비교와 상태 판정sync를 배우기 전에 무엇이 OutOfSync·Degraded로 판정되는지를 알아야 동기화 옵션의 목적이 보인다.57동기화 제어비교 결과를 실제 클러스터 변경으로 옮기는 규칙이다. 배포 안전성의 대부분이 여기서 결정된다.78프로젝트와 접근 제어여러 팀이 한 Argo CD를 쓰기 시작하면 경계와 권한이 필요하다. 앞에서 배운 Application·sync를 대상으로 제한을 건다.79ApplicationSetApplication 하나를 다 이해한 다음에야 그것을 대량 생성하는 템플릿 엔진이 의미를 갖는다.710선언적 운영 설정여기까지의 기능을 UI 클릭이 아니라 Git으로 관리하려면 Argo CD 자신의 ConfigMap·Secret 규약을 알아야 한다.611관측·확장·운영기능이 다 갖춰진 뒤에는 상태를 보고, 알리고, 늘리고, 고치는 일이 남는다.612보안과 수명 주기운영에 들어간 Argo CD를 지키고 다음 버전으로 넘기는 일. 앞의 모든 설정이 이 판단의 입력이 된다.4

1GitOps와 Argo CD 첫걸음01-01

GitOps 원칙과 pull 기반 배포 모델

Git 저장소를 유일한 진실의 원천으로 삼고, 클러스터 안의 에이전트가 그 선언을 스스로 끌어와 반영하는 배포 방식.

#1문제 상황

전통적인 배포는 배포 엔지니어나 CI/CD 파이프라인이 클러스터에 직접 리소스를 push하는 방식, 즉 외부에서 클러스터로 변경사항을 밀어 넣는다. 이 방식의 한계는 Git 저장소와 클러스터의 상태가 불일치할 수 있고, 누가 언제 무엇을 배포했는지 감시하기 어렵고, 클러스터 문제 발생 시 Git에는 기록이 없을 수 있다는 점이다.

#2핵심 질문

만약 클러스터가 Git 저장소에서 스스로 변경사항을 주기적으로 확인해 끌어온다면 어떨까?

#3동작 예시

Argo CD는 Git 저장소를 유일한 진실의 원천으로 보고, 클러스터 안의 에이전트가 지정된 Git 경로를 주기적으로 조회해 그 선언 상태와 실제 클러스터 상태를 비교한 후 자동으로 일치시킨다. 예를 들어 Git의 nginx deployment 매니페스트가 replicas: 3으로 정의되어 있는데 클러스터에는 현재 1개 파드만 실행 중이면, Argo CD는 이를 감지해 2개 파드를 추가로 생성해 일치시킨다.

#4동작 과정

  1. Git을 단일 출처로 선언클러스터 관리자가 Git 저장소의 경로를 지정하고 "이 저장소가 우리 클러스터의 진실"이라고 선언.
  2. 클러스터 에이전트가 주기적으로 Git 확인Argo CD 컨트롤러가 일정 간격으로 해당 Git 경로의 매니페스트를 조회해 다운로드.
  3. 차이를 감지하고 맞추기다운로드한 매니페스트와 클러스터 실제 상태를 비교해 차이가 있으면 클러스터 리소스를 Git 상태로 변경.

#5한 줄 요약

Git을 배포의 유일한 기록으로 삼고, 클러스터가 Git을 주기적으로 당겨서 스스로 자동으로 동기화하는 pull 기반 배포 모델

Argo CD 핵심 용어와 조정 루프

Application·소스·대상 클러스터 같은 기본 용어와, 원하는 상태와 실제 상태를 계속 비교해 Synced/OutOfSync를 판단하는 반복 루프.

#1문제 상황

Argo CD를 처음 배우면 Application, destination, source, revision, sync status 같은 용어들이 나오는데, 이 용어들이 정확히 무엇을 의미하는지 모르면 설정 파일을 이해하기 어렵다. 또한 Argo CD가 "지금 뭘 하는 중인가"를 알기 위해서는 원하는 상태(desired state)와 실제 상태(actual state)를 비교해 지속적으로 조정하는 루프의 흐름을 이해해야 한다.

#2핵심 질문

Argo CD가 어떤 대상에 어떤 상태를 계속 확인해서 동기화 여부를 판단하는가?

#3동작 예시

Application 리소스는 세 가지를 지정한다: (1) source — Git 저장소의 어느 경로에서 매니페스트를 가져올 것인가, (2) destination — 어느 클러스터의 어느 네임스페이스에 배포할 것인가, (3) sync policy — 자동 동기화할 것인가 수동인가. 컨트롤러는 이 Application을 읽어 지정된 source의 최신 커밋 상태와 destination 클러스터의 실제 리소스들을 계속 비교해 Synced(일치) 또는 OutOfSync(불일치)를 판단한다.

#4동작 과정

  1. Application 정의 읽기Argo CD는 Application 리소스에서 source(Git 경로), destination(대상 클러스터), sync policy를 읽음.
  2. 원하는 상태와 실제 상태 비교Git의 최신 매니페스트를 다운로드해 원하는 상태로 보고, 클러스터 리소스의 현재 spec/status를 실제 상태로 읽어 둘을 비교.
  3. 상태 판정 및 반복차이가 없으면 Synced, 있으면 OutOfSync로 표시하고, 이 비교를 주기적으로 반복 (sync policy가 자동이면 OutOfSync 감지 시 자동 동기화).

2시스템 구조02-03

조정 한 사이클: refresh에서 sync까지

Git을 다시 읽어 원하는 상태를 만들고(refresh), 클러스터 실제 상태와 비교해 차이를 내고(diff), 그 차이를 클러스터에 적용하는(sync) 반복 루프가 Argo CD 동작의 전부다.

#1문제 상황

Argo CD가 실제로 "언제, 어디서, 어떤 순서로" 동작하는지 알아야 운영 중 문제를 진단하고 성능을 튜닝할 수 있다. Application 상태가 OutOfSync로 표시되고 나서 Synced가 되는 과정 사이에 정확히 무엇이 일어나는지, 그리고 그 과정이 몇 가지 단계로 나뉘는지 이해하는 것이 중요하다.

#2핵심 질문

Argo CD가 Git을 확인한 후 클러스터를 동기화하기까지 정확히 어떤 순서의 작업을 수행하는가?

#3동작 예시

한 번의 동기화 사이클은 세 단계로 나뉜다: refresh(Git 읽기) → diff(비교) → sync(적용). application controller가 주기적으로(기본 3분마다) 이 사이클을 반복한다. refresh 단계에서 repo-server에 "이 Application의 source 경로를 렌더링해달라"고 요청하고 최신 매니페스트를 받고, diff 단계에서 그것과 클러스터 현재 상태를 바이너리 비교해 차이를 계산하고, sync 단계에서 차이가 있으면 kubectl apply로 클러스터 업데이트를 진행한다.

#4동작 과정

  1. RefreshGit 상태 새로 읽기** — application controller가 repo-server에 "최신 Git 커밋 상태를 기준으로 매니페스트를 렌더링해달라"고 요청해 최신 desired state를 획득.
  2. Diff원하는 상태와 실제 상태 비교** — 렌더링된 매니페스트와 클러스터의 현재 리소스들(Deployment, Service, ConfigMap 등)을 세부 필드까지 비교해 추가/변경/삭제할 것들 목록 작성.
  3. Sync차이를 클러스터에 적용** — diff에서 나온 리소스들을 kubectl apply(또는 kubectl patch, kubectl delete)로 클러스터에 반영해 actual state를 desired state와 일치시킨 후 상태를 Synced로 변경.

#5한 줄 요약

refresh에서 Git을 새로 읽고, diff에서 원하는 상태와 실제 상태를 비교하며, sync에서 그 차이를 클러스터에 적용하는 세 단계 반복 루프가 Argo CD 동작의 모든 것

#1문제 상황

기존의 전체 Argo CD 설치는 웹 UI 서버, API 서버, 인증 시스템(Dex), 캐시(Redis) 등 모든 컴포넌트를 포함한다. 하지만 이렇게 설치하면 자동화 파이프라인이나 작은 환경에서는 필요 없는 컴포넌트에 리소스가 소비되고, 운영이 복잡해진다.

#2핵심 질문

UI와 API 없이 Application 리소스와 CLI만으로 배포 자동화를 수행할 수는 없을까?

#3동작 예시

Argo CD Core는 Application 리소스를 감시하는 argocd-application-controller와 Git에서 매니페스트를 가져오는 argocd-repo-server 두 개 컴포넌트만 배포한 형태다. kubectl apply로 Application YAML을 클러스터에 적용하면 컨트롤러가 이를 감지해 배포를 실행한다.

#4동작 과정

  1. 컴포넌트 최소화UI·API·Dex·Redis를 모두 제거하고 argocd-application-controller와 argocd-repo-server만 설치해 파드 개수와 리소스 사용량을 줄인다.
  2. Application 모니터링컨트롤러가 클러스터 내 Application 커스텀 리소스를 지속 감시하다가 생성·수정·삭제를 감지한다.
  3. 배포 실행repo-server가 Git 저장소에서 매니페스트를 가져와 클러스터에 배포하고, 컨트롤러가 상태를 추적한다.

  3. 배포 대상 명시spec.destination으로 실제 배포할 쿠버네티스 클러스터와 네임스페이스를 지정한다.

소스 지정: repoURL·path·targetRevision

source 블록은 매니페스트가 있는 저장소 주소(repoURL), 그 안의 디렉터리(path), 사용할 브랜치·태그·커밋(targetRevision)으로 배포할 원본을 정확히 가리킨다.

#1문제 상황

어느 저장소에서 어느 파일을 가져올지를 배포할 때마다 지정해야 한다. 같은 저장소와 경로를 반복 지정하는 수고가 생기고, 어느 브랜치·태그·커밋을 사용하는지 추적하기 어렵다. 시간이 지나면 배포된 파일의 버전이 불명확해진다.

#2핵심 질문

어느 Git 저장소의 어느 경로에서 어느 버전의 매니페스트를 배포할지를 한 번에 명확하게 기록할 수는 없을까?

#3동작 예시

Application의 source 블록에서 repoURL은 저장소 주소(예: https://github.com/myorg/manifests), path는 그 저장소 안의 디렉터리(예: prod/app), targetRevision은 사용할 브랜치·태그·커밋(예: main, v1.0.0, abc123d)을 각각 명시한다.

#4동작 과정

  1. 저장소 주소 기록spec.source.repoURL로 매니페스트를 보관한 Git 저장소의 HTTPS 또는 SSH 주소를 명시한다.
  2. 경로 지정spec.source.path로 저장소 내에서 배포에 사용할 YAML 파일이 위치한 디렉터리를 지정한다.
  3. 버전 결정spec.source.targetRevision으로 어느 브랜치·태그·커밋을 사용할지 명시해서 배포 시점의 스냅샷을 보장한다.

3Application 리소스03-05

애플리케이션 삭제·finalizer·cascade

Application을 지울 때 배포된 리소스까지 함께 지울지(cascade)를 finalizer 유무로 정하는 규칙이다.

#1문제 상황

Application을 kubectl delete 명령으로 지우면 Application 리소스만 삭제되고, 클러스터에 배포된 Pod·Service·Deployment 등은 남아 있다. 이렇게 되면 배포된 리소스가 고아(orphan) 상태로 남아 수동으로 정리해야 하거나, 의도하지 않게 애플리케이션이 계속 실행되는 문제가 발생한다.

#2핵심 질문

Application을 지울 때 배포된 리소스까지 함께 정리할지, 남길지를 명시적으로 선택할 수는 없을까?

#3동작 예시

Application에 spec.finalizers를 설정하면 삭제 시 Argo CD가 cascade 정책을 확인한다. spec.cascadeDelete.foreground를 true(기본값)로 설정하면 배포된 모든 리소스를 먼저 삭제한 후 Application을 지우고, false로 설정하면 Application을 먼저 지운 후 리소스는 비동기로 정리하거나 보존한다.

#4동작 과정

  1. Finalizer 설정spec.finalizers에 argo 값을 붙이면 쿠버네티스가 Application 삭제 요청을 일시 중단하고 Argo CD에 정리 기회를 준다.
  2. Cascade 정책 선택spec.cascadeDelete.foreground를 true로 설정하면 전경(foreground) 모드로 배포된 리소스부터 순차적으로 삭제하고, false로 설정하면 배경(background) 모드로 Application만 지운 후 리소스는 비동기로 정리한다.

4매니페스트 생성 도구04-06

파라미터 오버라이드와 빌드 환경 변수

Application 수준에서 Helm/Kustomize 파라미터를 덮어쓰고, 매니페스트 생성 시점에 앱 이름·네임스페이스·리비전 같은 빌드 환경 변수를 주입하는 기능이다.

→ 04-03 참조

#1문제 상황

저장소에 저장된 Helm values나 Kustomize 파라미터는 고정되어 있습니다. 같은 차트나 kustomization을 여러 환경에서 다른 값으로 쓰려면 저장소 파일을 직접 수정하거나, 저장소마다 Application을 여러 개 만들어야 합니다. 또한 배포 시점에 앱 이름, 네임스페이스, 리비전 같은 컨텍스트 정보를 동적으로 주입할 방법이 없습니다.

#2핵심 질문

Application 수준에서 저장소의 파라미터를 덮어쓰고, 배포 시점의 빌드 컨텍스트 정보를 매니페스트에 주입할 수 있을까요?

#3동작 예시

저장소의 values.yaml에 replicaCount: 3이라고 정의되어 있어도, Application의 .spec.source.helm.parameters에서 {name: "replicaCount", value: "5"}로 오버라이드할 수 있습니다. 또한 Argo CD는 배포할 때 ARGOCD_APP_NAME, ARGOCD_APP_NAMESPACE, ARGOCD_APP_REVISION 같은 환경 변수를 자동으로 주입하므로, 매니페스트가 이들을 참조해 동적 값을 만들 수 있습니다.

#4동작 과정

  1. 파라미터 오버라이드 정의Application의 spec.source.helm.parameters 또는 spec.source.kustomize.patches에서 저장소 파라미터를 다른 값으로 재정의합니다.
  2. 환경 변수 준비Argo CD가 내부 빌드 환경 변수(ARGOCD_APP_NAME, ARGOCD_APP_NAMESPACE 등)를 준비합니다.
  3. 매니페스트 생성오버라이드된 파라미터와 환경 변수가 적용된 상태에서 Helm template이나 kustomize 명령어를 실행해 최종 매니페스트를 생성합니다.

#5한 줄 요약

Application에서 저장소의 파라미터를 선택적으로 덮어쓰고, 배포 시점의 빌드 컨텍스트를 환경 변수로 주입해 동적이고 유연한 매니페스트 관리를 가능하게 하는 것

4매니페스트 생성 도구04-07

Config Management Plugin과 커스텀 도구 이미지

기본 지원 도구로 부족할 때 직접 만든 명령으로 매니페스트를 생성하도록 플러그인을 등록하고, 필요한 바이너리를 담은 커스텀 repo-server 이미지를 쓰는 확장 방식이다.

#1문제 상황

Argo CD는 기본적으로 Kustomize, Helm, kubectl 등 제한된 수의 도구만 지원합니다. 조직 내부의 특수한 매니페스트 생성 도구나 커스텀 렌더링 로직이 있다면, 기본 도구 목록에 없으므로 사용할 수 없습니다.

#2핵심 질문

Argo CD가 지원하지 않는 커스텀 도구나 명령으로 매니페스트를 생성해야 한다면 어떻게 할까요?

#3동작 예시

Argo CD의 repo-server라는 컴포넌트가 Git 저장소에서 매니페스트를 가져올 때 실행할 플러그인(plugin)을 ConfigMap에 등록할 수 있습니다. 이 플러그인이 실행될 때 필요한 바이너리(명령어 도구)를 담은 커스텀 Docker 이미지를 repo-server로 사용하면, 기본 도구에 의존하지 않고 자신의 렌더링 로직을 실행할 수 있습니다.

#4동작 과정

  1. 플러그인 정의 및 등록ConfigMap에 플러그인 이름, 실행할 명령어, 입출력 형식을 정의하고 Argo CD에 등록합니다.
  2. 커스텀 이미지 빌드플러그인이 사용할 바이너리나 스크립트를 Dockerfile에 포함시켜 Docker 이미지로 빌드합니다.
  3. repo-server 재배포커스텀 이미지를 사용하도록 repo-server를 다시 배포하면, Argo CD가 매니페스트를 렌더링할 때 새로 등록된 플러그인을 사용합니다.

#5한 줄 요약

Config Management Plugin과 커스텀 Docker 이미지를 통해 기본 도구로 처리할 수 없는 특수한 매니페스트 생성 요구사항을 충족하고 Argo CD의 기능을 확장하는 것

5소스 접근과 무결성05-01

프라이빗 저장소 인증

비공개 Git·Helm 저장소에 접근하기 위해 HTTPS 사용자명/토큰, SSH 키, GitHub App 같은 자격증명을 Argo CD 에 등록하는 방법.

#1문제 상황

공개 Git 저장소는 URL만으로 누구나 접근할 수 있지만, 비공개 저장소는 인증 없이 접근이 불가능합니다. Argo CD가 비공개 저장소에서 매니페스트를 가져오려면 사전에 자격증명(접근 권한을 증명하는 정보)이 필요합니다.

#2핵심 질문

Argo CD가 비공개 Git 또는 Helm 저장소에 접근하려면 어떤 자격증명을 어디에 등록해야 할까요?

#3동작 예시

Git 저장소의 프로토콜에 따라 필요한 자격증명이 다릅니다. HTTPS 프로토콜을 사용하면 사용자명과 개인 액세스 토큰이 필요하고, SSH 프로토콜을 사용하면 SSH 개인 키가 필요합니다. 또는 GitHub App처럼 발급된 자격증명을 사용할 수도 있습니다. 이런 자격증명들을 Kubernetes Secret(비밀번호를 저장하는 Kubernetes 객체)으로 Argo CD 네임스페이스에 사전 등록해두면, 저장소 동기화 시 자동으로 인증됩니다.

#4동작 과정

  1. 필요한 자격증명 결정HTTPS 토큰, SSH 키, GitHub App 중 저장소의 접근 방식에 맞는 것을 선택합니다.
  2. Kubernetes Secret으로 등록선택한 자격증명을 Secret 리소스 형태로 Argo CD의 네임스페이스에 저장합니다.
  3. 저장소 동기화 시 자동 인증Argo CD가 저장소에 접근할 때 등록된 Secret에서 자격증명을 읽어 자동으로 인증합니다.

#5한 줄 요약

비공개 저장소 접근에 필요한 자격증명을 Kubernetes Secret으로 미리 등록해두고 동기화 시 자동 인증하는 것

5소스 접근과 무결성05-02

저장소 등록과 자격증명 템플릿

저장소를 선언적 Secret 으로 등록하고, URL 접두어가 같은 여러 저장소가 자격증명 하나를 공유하도록 템플릿(repo-creds)을 정의하는 방식.

#1문제 상황

비공개 저장소마다 개별 자격증명을 등록해야 한다면, 저장소가 많을수록 관리 부담이 증가합니다. 같은 조직의 저장소 수십 개가 모두 같은 자격증명을 사용해도, 각각에 대해 자격증명을 반복해서 등록해야 하며, 나중에 자격증명이 변경되면 모든 등록을 수정해야 합니다.

#2핵심 질문

URL 패턴이 같은 여러 저장소가 단 하나의 자격증명을 공유하려면 어떻게 할까요?

#3동작 예시

Argo CD의 repo-creds(저장소 자격증명) 템플릿을 사용하면, URL 접두어 패턴(예: https://github.com/mycompany/*)을 정의하고 그에 해당하는 자격증명을 한 번만 등록할 수 있습니다. 이후 같은 패턴에 속하는 저장소들은 모두 이 자격증명을 자동으로 공유합니다.

#4동작 과정

  1. repo-creds 템플릿 정의Secret에 URL 패턴과 자격증명을 선언적으로 정의합니다.
  2. 개별 저장소 등록저장소들을 Application이나 Repository로 등록하되, 자격증명을 직접 지정하지 않습니다.
  3. 패턴 매칭으로 자동 적용Argo CD가 저장소 URL을 패턴과 비교해 매칭되면 해당 자격증명을 자동으로 사용합니다.

#5한 줄 요약

URL 패턴 기반의 repo-creds 템플릿을 정의해 같은 조직의 여러 저장소가 하나의 자격증명을 공유하고 관리 오버헤드를 줄이는 것

5소스 접근과 무결성05-03

SSH known hosts·TLS 인증서·Git 클라이언트 설정

Argo CD 가 Git 서버를 신뢰할 수 있도록 SSH 호스트 키와 TLS 인증서를 ConfigMap 에 등록하고 Git 클라이언트 동작을 조정하는 설정.

#1문제 상황

SSH 클라이언트는 처음 호스트에 연결할 때 호스트 키를 확인하도록 요구합니다. TLS 연결도 서버 인증서를 검증합니다. 하지만 Argo CD 같은 자동화 도구는 대화형 프롬프트에 응답할 수 없으므로, 신뢰할 호스트나 인증서를 미리 설정해야 합니다.

#2핵심 질문

Argo CD가 Git 서버와의 연결을 자동으로 신뢰하고 설정하려면 어떻게 해야 할까요?

#3동작 예시

Git 서버의 SSH 호스트 키와 TLS 인증서를 ConfigMap(설정값을 저장하는 Kubernetes 객체)에 미리 등록하면, Argo CD의 Git 클라이언트가 연결 시 이를 참조해 호스트 키 검증을 생략하고 인증서를 검증할 수 있습니다. 또한 Git 클라이언트의 동작(압축, 타임아웃, 암호화 설정 등)도 이 ConfigMap을 통해 조정할 수 있습니다.

#4동작 과정

  1. 호스트 키와 인증서 수집Git 서버의 SSH 호스트 키와 TLS 인증서를 수집합니다.
  2. argocd-ssh-known-hosts-cm ConfigMap 등록수집한 호스트 키와 인증서, Git 클라이언트 설정을 ConfigMap에 저장합니다.
  3. Git 클라이언트가 참조해 연결Argo CD의 Git 클라이언트가 연결 시 이 ConfigMap의 정보를 신뢰할 수 있는 호스트로 인식하고 자동으로 연결합니다.

#5한 줄 요약

SSH 호스트 키와 TLS 인증서를 ConfigMap에 미리 등록해 Argo CD가 Git 서버를 자동으로 신뢰하고 문제 없이 연결하도록 하는 것

5소스 접근과 무결성05-04

소스 무결성 검증과 GnuPG 서명

배포 대상 커밋이 신뢰된 GnuPG 키로 서명됐는지 검사해 검증되지 않은 소스의 동기화를 막는 기능.

#1문제 상황

Argo CD가 Git 저장소에서 매니페스트를 가져와 클러스터에 배포할 때, 가져온 내용이 정말 신뢰된 사람이 작성했는지 검증하지 않습니다. 저장소가 해킹되거나 악의적인 커밋이 주입된다면, Argo CD는 검증 없이 이를 배포하게 됩니다.

#2핵심 질문

배포할 커밋이 진짜 신뢰된 개발자가 작성한 것임을 어떻게 보장할 수 있을까요?

#3동작 예시

GnuPG(GNU 암호화 도구)를 사용하면 개발자가 커밋에 디지털 서명(개인 키로 생성한 암호화된 확인 도장)을 할 수 있습니다. Argo CD에 신뢰된 개발자들의 GnuPG 공개 키를 등록해두면, 배포 전에 커밋의 서명을 검증하고, 서명이 유효하지 않거나 신뢰되지 않는 키로 서명된 커밋은 배포하지 않습니다.

#4동작 과정

  1. 커밋에 GnuPG 서명개발자가 커밋 시 자신의 GnuPG 개인 키로 서명합니다.
  2. 신뢰된 공개 키 등록Argo CD에 신뢰된 개발자들의 GnuPG 공개 키를 등록합니다.
  3. 배포 전 서명 검증Argo CD가 동기화 전에 커밋 서명을 검증하고, 유효하지 않으면 동기화를 차단합니다.

#5한 줄 요약

GnuPG 디지털 서명으로 커밋의 진정성을 검증해 신뢰되지 않은 소스의 배포를 방지하는 것

5소스 접근과 무결성05-05

Source Hydrator: 렌더링 결과를 Git에 커밋

Helm·Kustomize 로 렌더링한 최종 매니페스트를 Argo CD 가 별도 브랜치에 커밋해 두고 그 브랜치를 배포 소스로 삼는 기능.

#1문제 상황

#2핵심 질문

#3동작 예시

자동 동기화·self-heal·재시도

Git 변경을 감지하면 Argo CD가 알아서 sync하고, 클러스터가 임의로 바뀌면 self-heal로 되돌리며, 실패 시 재시도한다.

#1문제 상황

수동 sync는 사용자가 명시적으로 sync 버튼을 눌러야 합니다. 하지만 실제 운영 환경에서는 Git이 변경될 때마다 매번 사용자가 버튼을 누르기는 불가능합니다. 또한 sync에 실패했을 때 자동으로 재시도하지 않으면 리소스가 삐뚤어진 상태로 남아 있을 수 있습니다. 그리고 누군가 클러스터를 직접 편집해버리면 Git과 다시 달라져서 그걸 다시 맞춰야 합니다.

#2핵심 질문

Git 변경이나 클러스터 변경을 감지해서 자동으로 대응하고, 실패했을 때 자동으로 재시도하려면 어떻게 할까요?

#3동작 예시

개발자가 git push로 매니페스트를 변경하면 Argo CD는 Webhook이나 주기적 폴링으로 이를 감지합니다. autoSync가 활성화되면 Argo CD는 자동으로 sync를 실행합니다. 누군가 kubectl을 직접 쓰거나 다른 도구가 클러스터의 Pod를 삭제하면, self-heal 기능이 이를 감지해서 자동으로 원래 상태로 되돌립니다. Sync 과정에서 일시적 네트워크 오류가 나면 retryStrategy에 따라 자동으로 재시도합니다.

#4동작 과정

  1. 변경 감지Webhook 또는 주기적 git fetch로 Git이 변경되었는지 확인하고, 변경이 있으면 Application을 OutOfSync 상태로 표시합니다.
  2. 자동 sync 실행과 재시도autoSync가 활성화되면 OutOfSync를 감지한 즉시 자동으로 sync를 시작합니다. Sync 도중 임시 오류가 발생하면 retryStrategy에 정의된 간격과 횟수만큼 자동으로 재시도합니다.
  3. Self-heal로 클러스터 보정Application 상태를 주기적으로 검사해서 클러스터가 Git과 달라졌으면 즉시 다시 적용합니다. 이렇게 하면 누군가 직접 수정한 내용도 자동으로 원래대로 돌려집니다.

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

  1. Git과 클러스터 비교Sync할 때 Argo CD가 "Git에는 없는데 클러스터에는 있는" 리소스를 찾습니다.

#1문제 상황

#3동작 예시

RBAC는 규칙 줄을 argocd-rbac-cm ConfigMap에 적어서 권한을 정의합니다. "p" 줄(정책)은 누가, 어디의 어떤 것을, 무슨 동작을 할 수 있는지를 적습니다. 예: p, developers, applications, get, frontend-* 는 developers 그룹이 frontend로 시작하는 모든 애플리케이션을 조회할 수 있다는 뜻입니다. "g" 줄(그룹)은 누가 어느 롤에 속하는지를 적어 정책을 사용자/그룹에 연결합니다.

#4동작 과정

  3. 권한 적용사용자가 API를 호출하거나 UI에서 작업할 때, Argo CD가 그 사용자의 롤과 정책을 조회해 동작을 허용하거나 거부합니다. 기본 제공되는 role:admin(모든 권한)과 role:readonly(조회만 가능)를 바로 사용하거나 커스텀 롤을 만들 수 있습니다.

ApplicationSet이 자동으로 Application을 생성하는 것은 좋지만, 운영 중에 ApplicationSet 설정을 바꾸면 기존 Application이 자동으로 삭제된다. 또한 누군가 Argo CD UI에서 Application의 필드를 직접 수정했는데, GitOps 컨트롤러가 매번 다시 덮어쓸 수 있다. 이런 동작은 운영 중 의도하지 않은 데이터 손실이나 설정 변경을 초래한다.

#2핵심 질문

ApplicationSet이 지운 Application이 실제 배포 자원까지 함께 삭제하지 않으면서, 동시에 사람이 수정한 필드를 컨트롤러가 덮어쓰지 않으려면 어떻게 해야 할까?

#3동작 예시

삭제 정책에서 finalizers를 orphan으로 설정하면 Application은 삭제되지만 Pod, Service 같은 쿠버네티스 리소스는 클러스터에 남는다. 수정 통제에서 특정 필드에 라벨을 붙이면 컨트롤러가 그 필드만 Git 값으로 갱신하고 나머지는 유지한다.

#4동작 과정

  1. 삭제 정책 지정ApplicationSet 설정에서 finalizers 값으로 orphan(리소스 유지), foreground(우아한 삭제), background(빠른 삭제) 중 하나를 선택한다.
  2. 수정 통제 마크 설정템플릿의 각 필드에 어노테이션을 붙여 이 필드는 GitOps 제어 대상인지, 사람이 수정해야 하는 영역인지를 구분한다.
  3. 컨트롤러의 선택적 갱신Argo CD 컨트롤러가 Application을 재조정할 때 표시된 필드만 Git 값으로 갱신하고, 나머지 필드는 기존 상태를 유지한다.

#5한 줄 요약

ApplicationSet의 자동 생성과 삭제 과정에서 배포된 실제 리소스를 보호하고, GitOps의 자동 제어 영역과 사람의 수동 수정 영역을 명시적으로 분리하는 것

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 로컬에서 암호화개발자가 로컬 환경에서 sealedsecrets 같은 도구로 평문 시크릿을 암호화한다. 이때 클러스터의 공개 키를 사용한다.
  2. 암호화된 상태로 Git에 커밋암호화된 시크릿 데이터를 YAML 파일에 넣어 Git에 푸시한다. 이 상태에선 내용이 읽혀 나오지 않는다.
  3. 배포 시 복호화Argo CD가 클러스터에 배포할 때 컨트롤러(Sealed Secrets 컨트롤러 같은 오퍼레이터)가 클러스터의 개인 키로 암호화된 데이터를 풀어서 실제 쿠버네티스 Secret으로 만든다.

#1문제 상황

Argo CD가 장애 상태에 빠지면 기존 방식에서는 etcd 데이터베이스나 설정이 손상되었을 때 전체 클러스터를 처음부터 재구성해야 합니다. 인증 토큰, 연결된 저장소 주소, 애플리케이션 배포 상태 등 모든 설정이 사라지거나 부분적으로 손상되면 복구 방법이 불명확하고 시간이 오래 걸립니다.

#2핵심 질문

Argo CD의 설정과 배포 상태를 백업했다가, 장애 이후 빠르게 복구할 수 있는 방법이 있을까요?

#3동작 예시

argocd admin export 명령어를 실행하면 Argo CD의 모든 설정(저장소, 인증, 애플리케이션 정의)을 YAML 파일로 추출할 수 있고, 나중에 argocd admin import로 다시 적용하면 이전 상태로 되돌릴 수 있습니다. 마치 전체 데이터베이스를 파일로 저장했다가 필요할 때 복원하는 것과 같습니다.

#4동작 과정

  1. 진단 단계비정상 Pod, 높은 CPU/메모리 사용, 동기화 불가 등 증상을 확인하고, 로그에서 근본 원인(데이터베이스 연결 끊김, 권한 부족 등)을 찾습니다.
  2. 백업 추출argocd admin export로 현재 설정을 파일로 추출하거나, etcd 스냅샷을 저장합니다.
  3. 복구 적용새로운 Argo CD 환경에 argocd admin import로 설정을 복원하거나, etcd 스냅샷을 복원해 이전 상태로 돌립니다.

#5한 줄 요약

Argo CD의 설정과 상태를 파일로 내보내고 가져올 수 있도록 제공하여, 장애 상황에서 전체 설정을 빠르게 복구할 수 있게 하는 것

#2핵심 질문

#3동작 예시

#4동작 과정

  3. 레이트 리밋 설정Git 폴링 주기, Kubernetes API 요청 간격, webhook 처리 큐 크기 등을 조절해 외부 서비스 부하를 제어합니다.

TLS와 mTLS 구성

argocd-server 와 내부 컴포넌트 사이 통신을 인증서로 암호화하고 서로 신원을 검증하도록 설정하는 방법.

#1문제 상황

Argo CD 컴포넌트들(argocd-server, argocd-repo-server, argocd-controller) 사이의 통신이 암호화되지 않으면, 같은 네트워크 상의 공격자가 통신을 가로채 토큰, 설정, 배포 명령을 탈취할 수 있습니다. 또한 클라이언트가 서버의 신원을 검증하지 않으면 위장된 서버에 접속할 수도 있습니다.

#2핵심 질문

Argo CD 컴포넌트 간 통신을 암호화하고, 서로의 신원을 상호 검증할 수 있을까요?

#3동작 예시

TLS는 argocd-server와 클라이언트 사이 통신을 암호화하는 것이고, mTLS(상호 TLS)는 argocd-repo-server와 argocd-controller 같은 내부 컴포넌트 사이에서 클라이언트도 인증서로 신원을 증명하도록 추가로 요구합니다. 각 컴포넌트가 상대방의 인증서를 검증해야 통신이 성립합니다.

#4동작 과정

  1. 인증서 발급 및 설정CA(인증 기관) 인증서를 생성하고, 각 컴포넌트마다 고유 인증서와 개인 키를 발급한 후, ConfigMap 또는 Secret으로 저장합니다.
  2. TLS 활성화argocd-server에 서버 인증서와 개인 키를 제공하여, HTTPS 포트에서 클라이언트 연결을 받도록 설정합니다.
  3. mTLS 활성화컴포넌트 간 통신 설정에서 상호 인증을 요구하고, 각 컴포넌트가 상대방의 인증서를 검증하도록 구성합니다.

#5한 줄 요약

TLS 인증서를 사용해 Argo CD 모든 계층의 통신을 암호화하고, mTLS로 내부 컴포넌트 간 상호 신원 검증을 강제하여 중간자 공격을 방어하는 것

#2핵심 질문

#3동작 예시

Argo CD 릴리스 노트에 각 기능이 알파·베타·안정으로 분류되어 있고, 버전 간에 파괴적 변경(Breaking Changes)이 명시되어 있습니다. 예를 들어 과거에 리소스 필터 문법이 바뀌었다면, 업그레이드 전에 기존 필터를 새 문법으로 수정해야 합니다.

  2. 사전 준비필요한 설정 변경을 테스트 환경에서 먼저 적용하고, 백업을 수행합니다.
  3. 버전 업그레이드Helm 차트나 Kustomize를 사용해 단계별로 버전을 올리고, 각 단계에서 애플리케이션 동기화 상태와 컴포넌트 상태를 확인합니다.

#3동작 예시

Git 저장소를 환경(dev, staging, prod)별로 분리하면, 각 환경이 서로 다른 Argo CD 인스턴스로 배포되어 한쪽 장애가 다른 쪽에 영향을 주지 않습니다. Argo CD 릴리스 자산이 GPG 서명되어 있으면, 다운로드한 이미지를 서명으로 검증해 진위를 확인할 수 있습니다.

#4동작 과정

  1. 저장소 구조 설계애플리케이션 리포지토리와 Argo CD 구성 리포지토리를 분리하고, 환경별 브랜치나 디렉터리로 관리하여 권한과 변경 추적을 용이하게 합니다.
  2. 릴리스 자산 검증공식 GitHub 릴리스에서 서명(GPG 또는 cosign)이 있는지 확인하고, 다운로드한 이미지 다이제스트를 공식 목록과 비교합니다.
  3. 지원 범위 확인현재 실행 중인 Argo CD 버전이 프로젝트의 지원 범위(LTS, 최신 안정 등)에 있는지 확인하고, 지원이 끝나는 버전은 계획된 시간에 업그레이드합니다.
