CICD

CICD = CI/CD(지속적 통합·지속적 전달/배포) 파이프라인을 설계·구축·운영하는 법. 가장 일반적인 해석인 '코드 커밋부터 배포까지를 자동화하는 파이프라인' 전반으로 잡고, 개념을 실물로 확인할 기준 구현체는 현재 가장 널리 쓰이는 GitHub Actions 공식 문서로 삼는다. 플랫폼 중립 개념(파이프라인·스테이지·잡·러너·환경)은 GitLab CI/CD 공식 문서로 교차 확인했다.

이어서 읽기
1CI/CD가 무엇을 해결하는가도구를 배우기 전에 '무엇이 아파서 이 자동화를 하는가'를 알아야 뒤의 모든 선택(트리거·게이트·환경)이 이유 있는 선택으로 읽힌다.42파이프라인의 구성 단위워크플로·잡·스텝·액션·러너라는 다섯 단어의 관계를 먼저 못 박아야 이후 문법과 옵션이 어디에 붙는 것인지 알 수 있다.63언제 도는가: 트리거파이프라인은 '언제 도는가'로 성격이 정해진다. 트리거를 알아야 CI용 워크플로와 배포용 워크플로를 갈라 설계할 수 있다.64실행 흐름 제어같은 워크플로라도 조건·매트릭스·동시성을 어떻게 거느냐로 비용과 신뢰도가 갈린다. 트리거 다음에 오는 두 번째 제어면이다.45실행 환경 고르기: 러너여기서부터 '어디서 도는가'를 정한다. 러너 선택이 속도·비용·보안 경계를 동시에 결정하므로 빌드 내용을 짜기 전에 정리한다.66파이프라인이 다루는 데이터변수·컨텍스트·표현식·시크릿은 이후 모든 스텝이 값을 주고받는 배관이다. 빌드 스크립트를 쓰기 직전에 알아야 한다.77빌드와 테스트를 파이프라인에 태운다(CI)여기가 CI의 본체다. 앞의 구성 단위와 데이터 배관을 실제 빌드·테스트·캐시·산출물로 조립한다.68배포(CD)검증을 통과한 산출물을 실제 환경으로 옮기는 단계. 승인·이력·롤백까지 포함해야 CD라 부를 수 있다.79재사용과 자체 액션 제작파이프라인이 여러 저장소로 늘어나면 복붙이 부채가 된다. 실전 규모로 넘어가기 위한 추상화 수단이다.610파이프라인 보안CI/CD는 저장소 권한과 프로덕션 자격증명을 동시에 쥔 실행 환경이다. 기능을 다 익힌 뒤 반드시 되짚어야 할 층이다.811운영·관측·거버넌스돌아가는 파이프라인을 계속 신뢰하려면 로그·지표·한도·정책·이행 경로가 필요하다. 마지막에 와야 앞의 모든 요소를 대상으로 삼을 수 있다.8

#2핵심 질문

  2. 자동 검증최신 코드를 받아 빌드하고, 작성된 모든 테스트를 자동으로 실행합니다.

#2핵심 질문

검증을 통과한 산출물을 자동으로 내보낼 준비를 해두고, 사람이 승인만 하면 배포하게 하거나 아예 사람 개입 없이 배포할 수는 없을까?

#4동작 과정

  1. 준비 환경 배포CI를 통과한 산출물이 자동으로 테스트용 환경에 배포됩니다.

  3. 운영 배포사람의 승인(지속적 전달) 또는 자동 규칙(지속적 배포)에 따라 실제 운영 환경으로 배포합니다.

#3동작 예시

  3. 순차 실행각 단계가 정해진 순서대로 실행되고, 실패하면 거기서 중단됩니다.

워크플로는 여러 잡으로 나뉘고 각 잡은 순서대로 실행되는 스텝(명령 한 줄 또는 액션 하나)들로 이루어지며, 기본적으로 잡끼리는 병렬로 돈다.

#1문제 상황

#2핵심 질문

실행해야 할 작업들을 의미 있는 단위로 나누되, 동시에 실행할 수 있는 것은 병렬로 돌릴 수는 없을까?

#3동작 예시

"테스트" 잡은 테스트 실행에 필요한 모든 스텝(의존성 설치, 테스트 실행, 결과 보고)을 담고, "배포" 잡은 배포에 필요한 스텝들을 따로 담습니다. 두 잡이 독립적이면 동시에 돌고, 한 잡이 끝나야 다음 잡이 시작되도록 의존성을 설정할 수 있습니다.

#4동작 과정

  1. 잡으로 분류워크플로 안에 여러 잡을 정의하고, 각 잡에 필요한 스텝들을 나열합니다.

  3. 상세한 결과각 잡의 성공·실패를 따로 추적할 수 있어 문제 원인을 빨리 찾을 수 있습니다.

#3동작 예시

#1문제 상황

기존에는 스텝이 실패하면 그 스텝 직후의 모든 스텝이 자동으로 건너뛰어졌고, 실패한 경우와 성공한 경우를 구분해 다르게 처리할 방법이 없었습니다. 또한 무한 대기 상황이나 예상 밖의 오래 걸리는 작업으로 인한 시간 낭비도 제어하기 어려웠습니다.

#2핵심 질문

스텝이나 잡이 실패했을 때도 계속 진행하거나, 실패 상황에 맞춰 따로 처리하고, 실행 시간을 제한할 방법이 있을까?

#3동작 예시

#4동작 과정

  1. 상태 평가각 스텝이 끝나면 성공/실패 상태가 기록되고, success()/failure()/always() 함수로 이전 스텝의 상태를 조회할 수 있습니다.
  2. 조건부 실행 및 계속 진행if 키로 상태 함수를 사용하거나, continue-on-error로 실패해도 다음 스텝이 진행되게 설정합니다.

github, env, job, steps, runner 등 현재 실행에 관한 정보를 담은 객체로, ${{ }} 안에서 점 표기로 값을 꺼내 쓴다.

#1문제 상황

워크플로가 실행될 때 러너는 아무 정보도 가지고 시작한다. 어떤 브랜치에서 실행되는지, 누가 커밋을 밀었는지, 어떤 이벤트로 트리거되었는지 전혀 모른다. 그래서 같은 워크플로가 다양한 상황에서 다르게 동작해야 할 때, 그 정보를 어디서도 꺼낼 수 없다.

#2핵심 질문

현재 실행하는 파이프라인이 어떤 상황에서 동작하는지 알아야 하는데, 그 정보를 어디서 꺼낼까?

#3동작 예시

GitHub Actions는 실행 시점에 현재 환경과 이벤트 정보를 담은 여러 객체를 자동으로 제공한다. 워크플로 YAML에서 ${{ github.ref_name }} 으로 현재 브랜치명을, ${{ github.actor }} 로 커밋 작성자를, ${{ runner.os }} 로 러너의 운영체제를 그대로 꺼낼 수 있다.

#4동작 과정

  1. 컨텍스트 객체 주입워크플로 실행을 시작할 때 GitHub가 github, env, job, steps, runner, secrets 등 6개 컨텍스트 객체를 자동으로 마련한다.
  2. ${{ }} 문법으로 접근YAML의 조건식이나 변수 자리에 ${{ 컨텍스트명.속성명 }} 형태로 점 표기를 써서 값을 추출한다.
  3. 스텝과 조건에 활용추출한 값을 다음 스텝의 입력, 환경 변수, if 조건으로 전달하거나 직접 명령에 끼워 넣는다.

#5한 줄 요약

파이프라인이 현재 실행 환경과 상황(브랜치, 이벤트, 러너 정보 등)에 관한 정보에 접근하는 수단

표현식과 내장 함수

${{ }} 안에서 비교·논리 연산과 contains, startsWith, success, failure 같은 내장 함수를 써서 값을 계산하거나 실행 조건을 판단하는 문법이다.

#1문제 상황

컨텍스트에서 값을 꺼내기만 해서는 모자란다. 예를 들어 특정 브랜치에서만 배포하거나, 커밋 메시지에 특정 단어가 들어 있으면 다르게 동작해야 할 때 값을 비교하거나 변형할 수 없다.

#2핵심 질문

조건에 따라 다르게 동작하거나 값을 계산해서 써야 할 때 어떻게 할까?

#3동작 예시

${{ contains(github.event.commits.*.message, 'urgent') }} 는 모든 커밋 메시지에서 'urgent' 문자열을 찾고, 발견하면 참을 반환한다. 이처럼 표현식 안에서 값을 직접 검사하고 결과를 얻을 수 있다.

#4동작 과정

  1. 비교·논리 연산${{ }} 안에서 ==, !=, &&, ||, !, <, >, <= 등 연산자를 써서 두 값을 비교하거나 논리식을 조합한다.
  2. 내장 함수 호출contains(문자열, 패턴), startsWith, endsWith, success, failure, always 같은 내장 함수를 호출해 특정 조건을 판단한다.
  3. 계산 결과 전달연산과 함수의 결과(참/거짓 또는 변환된 값)를 다음 스텝의 if 조건이나 변수로 전달한다.

  3. 다음 스텝이 값 접근다음 스텝이 steps 컨텍스트, env 컨텍스트 또는 로그를 통해 그 값을 참조한다.

잡 사이로 값 넘기기: outputs와 needs

한 잡이 jobs.<id>.outputs로 내놓은 값을 다른 잡이 needs 컨텍스트로 받아 쓰는, 잡 간 데이터 전달 방식이다.

→ 06-05 참조

#1문제 상황

워크플로의 여러 잡이 병렬로 실행될 때, 한 잡이 완료한 결과를 다른 잡이 알아야 하는 경우가 있다. 하지만 잡들은 독립적으로 격리되어 실행되므로 한 잡의 출력이나 변수를 다른 잡이 직접 접근할 수 없다.

#2핵심 질문

앞의 잡이 실행한 결과를 뒤의 잡이 어떻게 받아서 쓸까?

#3동작 예시

build 잡이 버전을 계산해서 GITHUB_OUTPUT에 쓰고, deploy 잡이 needs.build.outputs.version 으로 그 값을 받아서 배포 시 사용한다. needs는 이전 잡을 명시적으로 등록한 것이고, outputs는 그 잡이 내놓은 값들이다.

#4동작 과정

  1. 선행 잡이 outputs 정의잡 내 스텝에서 GITHUB_OUTPUT에 값을 쓰고, jobs.잡ID.outputs 아래에 그 KEY를 명시한다.
  2. 후속 잡이 needs 등록후속 잡의 needs 섹션에 선행 잡의 ID를 문자열이나 배열로 등록한다.
  3. 후속 잡이 값 접근후속 잡 내에서 needs.선행잡ID.outputs.KEY 형태로 그 값에 접근한다.

#5한 줄 요약

잡 간 데이터를 주고받기 위해 선행 잡이 outputs로 값을 내놓고 후속 잡이 needs로 명시적으로 받는 구조다

체크아웃과 언어 런타임 준비

actions/checkout 으로 저장소 코드를 러너에 내려받고 setup-node·setup-python 같은 셋업 액션으로 빌드에 필요한 언어 런타임 버전을 고정해 두는 첫 단계다.

#1문제 상황

워크플로 실행이 시작되면 러너는 빈 상태에서 출발한다. 저장소의 소스 코드도 없고, 빌드에 필요한 Node.js, Python, Go 같은 런타임도 설치되지 않았다. 이 상태에선 빌드나 테스트를 실행할 수 없다.

#2핵심 질문

#3동작 예시

먼저 actions/checkout 으로 저장소를 러너 로컬에 복제하고, 그 후 actions/setup-node@v3 으로 Node.js 버전을 고정하면, 이후 run 스텝에서 npm 명령을 곧바로 실행할 수 있다.

#4동작 과정

  1. 체크아웃actions/checkout 액션이 GitHub 저장소를 현재 분기 상태 그대로 러너의 작업 디렉터리에 복제한다.
  2. 런타임 설정setup-node, setup-python 같은 셋업 액션이 필요한 언어 런타임을 설치하고 버전을 고정한다.
  3. 빌드 준비 완료이후 run 스텝에서 npm install, python build.py 같은 명령을 바로 실행할 수 있다.

#5한 줄 요약

코드와 빌드 환경을 러너에 준비하는 첫 단계로, 체크아웃과 런타임 설정을 모두 포함한다

#2핵심 질문

#3동작 예시

#4동작 과정

  2. 워크플로 실행 시 토큰 요청GitHub Actions 워크플로가 실행되면 GitHub이 OIDC 토큰(JWT)을 발급하고, 액션이 그 토큰을 AWS로 전송한다.
  3. 임시 자격증명 발급AWS는 OIDC 토큰을 검증하고 유효 기간이 제한된 STS 자격증명(temporary credentials)을 반환하면, 액션이 그것으로 AWS 리소스에 접근한다.

액션의 릴리스와 버전 관리

액션을 태그·릴리스·커밋 SHA 로 버전 지어 배포하고, 사용자는 uses: 뒤의 참조로 원하는 버전을 고정해 쓴다.

#1문제 상황

액션 저장소에 버그 수정이나 기능 추가로 코드가 변경될 때마다, 그 액션을 사용하는 모든 워크플로가 즉시 새 버전의 영향을 받습니다. 새 버전에서 뭔가 깨지면 모든 사용자가 예고 없이 장애를 겪을 수 있습니다.

#2핵심 질문

액션의 버전을 명확하게 관리해서 사용자가 원하는 안정적인 버전으로 고정해 쓸 수 있도록 하려면 어떻게 해야 할까?

#3동작 예시

액션 저장소에 v1.0.0, v1.1.0, v2.0.0 같은 세마틱 버전 태그를 생성해 배포하고, 동시에 v1, v2 같은 주요 버전 태그도 유지해둡니다. 사용하는 워크플로에서 uses: owner/action@v1.0.0 (정확한 버전 고정) 또는 uses: owner/action@v1 (주요 버전, 마이너 업데이트는 자동)로 명시적으로 참조하면, 그 시점의 액션 코드가 실행됩니다.

#4동작 과정

  1. 액션 저장소에 릴리스 태그 생성배포할 때마다 세마틱 버저닝(v1.0.0, v1.2.3 등)을 따라 Git 태그를 생성하고 GitHub 릴리스 페이지에 그 태그의 변경 사항을 기록합니다.
  2. 사용자가 uses에서 버전 명시워크플로 파일에서 uses: owner/action@v1.2.3 (정확한 커밋 SHA나 태그)로 지정하면 그 버전의 액션 코드만 실행됩니다.
  3. 주요 버전 태그로 자동 업데이트 관리v1 같은 주요 버전 태그는 마이너·패치 업데이트가 나올 때마다 최신 커밋을 가리키도록 업데이트해서, @v1로 참조하는 사용자들이 하위 호환성이 있는 업데이트는 자동으로 받게 합니다.

#1문제 상황

워크플로가 GitHub의 저장소, 이슈, PR 등에 접근할 때 모든 권한을 가진 토큰을 사용하면, 토큰이 탈취되었을 때 공격자가 저장소를 지우거나, 팀 멤버를 추가/제거하거나, 조직 전체를 장악할 수 있는 위험에 노출됩니다.

#2핵심 질문

워크플로가 필요한 것만 할 수 있는 최소한의 권한으로 GitHub에 접근하게 하려면 어떻게 해야 할까?

#3동작 예시

워크플로 파일의 최상단에 permissions 블록을 추가해 각 작업(pull-requests, issues, contents, deployments 등)마다 read 또는 write 권한만 명시해두면, 그 외의 모든 권한은 자동으로 차단됩니다. 예를 들어 PR에 코멘트만 달아야 한다면 permissions: pull-requests: write만 주고 다른 권한(contents 쓰기, 저장소 설정 변경 등)은 모두 차단되는 식입니다.

#4동작 과정

  1. GITHUB_TOKEN 자동 발급매 워크플로 실행 시 GitHub이 일시적인 토큰을 자동으로 생성하고 GITHUB_TOKEN 환경 변수로 제공합니다.
  2. permissions 블록으로 범위 제한워크플로 정의 최상단에서 필요한 각 권한만 명시하고(예: pull-requests: write), 선언하지 않은 권한은 거부 상태가 됩니다.
  3. 실행 중 제한된 토큰 사용각 스텝이 그 토큰을 사용해 GitHub API를 호출할 때 선언된 범위 내에서만 동작하므로, 실수나 악의적 코드도 불가능한 작업은 수행할 수 없습니다.

OIDC로 시크릿 없는 클라우드 인증

장기 클라우드 키를 저장하는 대신 워크플로가 발급받은 신원 토큰으로 그때그때 짧은 자격증명을 받는 방식이다.

#1문제 상황

AWS, GCP, Azure 같은 클라우드 서비스에 접근하려면 장기간 유효한 API 키나 액세스 키를 저장소 시크릿으로 보관해야 합니다. 그 키가 탈취되면 공격자가 장시간 클라우드 자원에 직접 접근할 수 있고, 조직의 모든 서비스를 장악할 위험이 있습니다.

#2핵심 질문

장기 유효한 클라우드 키를 저장소에 보관하지 않으면서도 워크플로에서 클라우드 서비스에 안전하게 인증할 수 있을까?

#3동작 예시

GitHub이 워크플로 실행마다 OIDC(OpenID Connect) 표준을 따라 서명된 신원 토큰을 발급하고, AWS 같은 클라우드 제공자가 그 토큰의 진위를 검증한 뒤 유효 시간이 짧은(보통 1시간) 임시 자격증명(Temporary Security Credentials)을 생성해줍니다. 워크플로는 API 키를 저장할 필요가 없고, 토큰을 받아 임시 자격증명으로 작업하는 것입니다.

#4동작 과정

  1. 클라우드 제공자에서 OIDC 신뢰 관계 설정AWS IAM, GCP, Azure 등에서 GitHub을 신뢰할 수 있는 외부 OIDC 제공자로 등록하고, 어떤 GitHub 조직·저장소·워크플로로부터의 토큰을 수용할지 정책으로 정의합니다.
  2. 워크플로 실행 시 토큰 발급 및 교환워크플로 실행이 시작되면 GitHub이 서명된 OIDC 토큰을 생성하고, 워크플로 스텝에서 그 토큰을 클라우드 제공자에게 제시합니다.
  3. 토큰 검증 후 임시 자격증명 발급클라우드 제공자가 토큰의 서명과 클레임(발급자, 저장소, 워크플로 정보 등)을 확인한 뒤, 정책에 맞으면 임시 접근 키를 발급하고, 워크플로가 그것으로 인증해 작업합니다.

#5한 줄 요약

신원 토큰으로 일회성 임시 자격증명을 교환해 장기 키를 저장소에 보관하지 않으면서도 클라우드에 안전하게 인증하는 것

신뢰할 수 없는 입력과 스크립트 인젝션

PR 제목·이슈 본문 같은 사용자 입력을 run 스크립트에 직접 끼워 넣으면 임의 명령이 실행될 수 있다는 위험이다.

#1문제 상황

PR 제목, 이슈 본문, 커밋 메시지, 사용자 이름처럼 사용자가 직접 입력한 정보를 워크플로의 run 스크립트에 직접 끼워 넣으면, 악의적인 사용자가 거기에 셸 명령을 주입해 워크플로가 공격자가 원하는 임의 명령을 실행하게 될 수 있습니다.

#2핵심 질문

사용자로부터 받은 신뢰할 수 없는 입력을 워크플로의 run 스크립트에 안전하게 포함시키려면 어떻게 해야 할까?

#3동작 예시

PR 제목이 $(rm -rf /) 같은 셸 명령이면, run: echo "${{ github.event.pull_request.title }}" 식으로 직접 끼워 넣으면 bash가 $() 구문을 명령 치환으로 해석해 의도하지 않은 명령이 실행됩니다. 이를 막으려면 입력값을 env 블록의 환경 변수에 먼저 할당한 뒤 스크립트에서 참조하거나, JavaScript 액션 안에서만 입력을 다루는 방법을 써야 합니다.

#4동작 과정

  1. 신뢰할 수 없는 입력 출처 식별PR 제목, 이슈 본문, 커밋 메시지, 사용자 이름, webhook payload 등 외부에서 입력되는 모든 데이터를 구분합니다.
  2. 환경 변수를 통한 안전한 전달그 입력을 직접 run 셸 스크립트에 문자열 보간(${{ }})으로 끼워 넣지 말고, 먼저 env 블록에서 환경 변수에 할당한 뒤 스크립트에서 사용하거나, JavaScript 액션 안에서만 처리합니다.
  3. 입력값 검증 또는 이스케이프(선택)필요한 경우 정규표현식으로 입력 형식을 검증하거나, 특수 문자를 이스케이프 처리해 셸 명령 실행을 방지합니다.

사용자 입력을 run 셸 스크립트에 직접 포함시키지 않고 환경 변수나 액션 내부로 격리해 셸 명령 인젝션 공격을 방지하는 것

포크 PR과 pull_request_target의 함정

포크에서 온 PR은 권한이 제한되며, pull_request_target 은 신뢰된 컨텍스트라 외부 코드를 체크아웃하면 위험하다.

→ 10-04 참조

#1문제 상황

일반적으로 PR이 들어오면 GitHub Actions는 그 PR의 코드를 체크아웃해서 테스트를 실행합니다. 포크에서 온 PR의 경우 보안상 제한된 권한으로 실행되어 저장소에 쓰거나 보안 비밀에 접근할 수 없습니다. 하지만 pull_request_target 이벤트를 사용하면 base 브랜치(통상 main)의 코드를 기준으로 신뢰된 컨텍스트에서 실행되어 쓰기 권한과 비밀 접근이 가능해집니다. 이것이 외부 코드를 실행하는 상황에서 위험을 만듭니다.

#2핵심 질문

포크에서 온 PR에서 저장소에 쓸 수 있는 권한이 필요하다면, 외부 코드 실행의 위험을 어떻게 막을까?

#3동작 예시

pull_request 이벤트: PR의 코드를 체크아웃하고 격리된 권한에서 실행 (읽기 전용, 비밀 없음, 안전하지만 권한 제한)

pull_request_target 이벤트: base 브랜치의 코드를 체크아웃하고 신뢰된 권한에서 실행 (쓰기 권한, 비밀 접근, 권한은 있지만 악성 코드 실행 위험)

#4동작 과정

  1. 포크 PR 도착기본적으로 PR의 코드를 격리된 권한에서 실행하므로 저장소 수정이나 배포가 불가능합니다.
  2. pull_request_target 사용 시base 브랜치의 신뢰된 코드는 체크아웃하지만, 워크플로 파일 자체는 PR의 코드를 읽으므로 악성 스크립트가 실행될 수 있습니다.
  3. 안전한 운영pull_request_target을 써야 한다면 base의 검증된 코드만 실행하고, PR의 수정 내용은 직접 쓰기 권한 있는 단계에서 사용하지 않아야 합니다.

서드파티 액션을 신뢰하는 방법

남이 만든 액션은 커밋 SHA로 고정하고 소스를 검토해 공급망 위험을 줄인다.

#1문제 상황

워크플로에서 다른 사람이 만든 액션(예: actions/checkout@v4)을 사용할 때 보통 버전 태그로 지정합니다. 하지만 액션의 저장소 소유자 계정이 해킹되거나, 액션 코드 자체가 변조되면 악성 코드가 당신의 워크플로에서 실행될 수 있습니다. 또한 버전 태그는 나중에 다시 가리킬 수 있어 불변성이 보장되지 않습니다.

#2핵심 질문

내가 지정한 액션이 내가 검토한 그 정확한 코드를 실행한다는 보장이 있을까?

#3동작 예시

버전 태그로 지정: owner/repo@v1.0.0 — 언제든 태그가 다른 커밋을 가리킬 수 있습니다.

커밋 SHA로 지정: owner/repo@abc123def456... — 해당 커밋의 정확한 코드만 실행되고 나중에 변경되지 않습니다.

#4동작 과정

  1. 액션 선택필요한 기능을 제공하는 액션을 찾습니다.
  2. 소스 코드 검토액션의 GitHub 저장소에 가서 실제로 어떤 일을 하는 코드를 읽어봅니다.
  3. SHA로 고정확인한 버전의 정확한 커밋 SHA를 복사해 워크플로에 지정하고, 정기적으로 업데이트합니다.

#5한 줄 요약

셀프호스티드 러너의 위험과 격리

직접 운영하는 러너는 상태가 남고 내부망에 붙어 있어 공개 저장소에서 쓰면 위험하므로 격리·일회성 운영이 필요하다.

→ 09-01 참조

#1문제 상황

GitHub이 제공하는 호스팅 러너를 사용하면 매번 깨끗한 임시 머신에서 잡이 실행되어 상태가 남지 않습니다. 하지만 자신의 하드웨어나 회사 내부 서버에서 러너를 직접 운영하면 이전 잡이 남긴 파일, 환경 변수, 실행 중인 서비스가 다음 잡에 영향을 줄 수 있습니다. 더 위험하게, 공개 저장소의 PR이라면 악의 있는 코드가 내부망에 연결된 머신에 접근할 수 있습니다.

#2핵심 질문

자신의 인프라에서 러너를 운영하면서 공개 저장소의 코드를 실행할 때 내부 시스템을 어떻게 보호할까?

#3동작 예시

호스팅 러너: 각 잡마다 새 VM 생성 → 실행 → 폐기 (상태 제거, 안전)

셀프호스팅 러너 (부주의한 운영): 같은 머신에서 계속 실행 → 이전 상태 남음 → 악성 코드 실행 시 내부망 노출

#4동작 과정

  1. 레이블 제한셀프호스팅 러너에 고유한 레이블을 지정하고, 신뢰하는 워크플로만 그 러너를 명시적으로 선택하도록 제한합니다.
  2. 일회용 환경공개 저장소의 잡이 들어올 때마다 임시 컨테이너나 VM을 새로 만들어 실행하고 끝나면 폐기합니다.
  3. 상태 정리각 잡 실행 후 환경 변수, 임시 파일, 설치된 패키지를 정리하거나 머신을 리셋합니다.

아티팩트 어테스테이션과 공급망 신뢰

빌드 산출물이 어떤 워크플로에서 나왔는지 서명된 증명으로 남겨 출처를 검증하는 기능이다.

#1문제 상황

CI/CD 파이프라인에서 빌드된 파일(jar, exe, Docker 이미지 등)을 아티팩트로 저장하고 사용자가 다운로드합니다. 하지만 그 파일이 정말 당신의 파이프라인에서 나왔는지, 언제 어떤 코드로부터 빌드됐는지 검증할 방법이 없습니다. 리포지토리나 배포 환경이 해킹되면 악의 있는 바이너리가 배포될 수 있고, 사용자는 출처를 알 수 없습니다.

#2핵심 질문

이 바이너리가 정말 내 신뢰할 수 있는 CI/CD 파이프라인에서 생성됐다는 증명이 있을까?

#3동작 예시

어테스테이션 없음: 빌드 → 파일 업로드 → 사용자 다운로드 (출처 검증 불가)

어테스테이션 있음: 빌드 → 파일 업로드 + 서명된 증명서 발행 → 사용자가 증명서로 검증 (출처 확인 가능)

#4동작 과정

  1. 파이프라인에서 빌드GitHub Actions 워크플로에서 아티팩트를 생성합니다.
  2. 어테스테이션 발행GitHub이 해당 빌드의 메타데이터(저장소, 분기, 커밋, 워크플로 ID)를 암호화해 서명된 증명서를 발행합니다.
  3. 사용자가 검증아티팩트를 다운로드받을 때 증명서를 검사해 출처와 빌드 조건이 맞는지 확인합니다.

  1. 정책 정의조직 관리자가 GitHub 설정에서 어떤 액션은 금지할지, 어떤 러너는 허용할지, 승인 프로세스가 필요한지 정합니다.
  2. 권한 설정팀별로 어느 권한을 가질지 결정합니다. 예를 들어 새로운 Secrets를 추가할 수 있는 권한, 또는 프로덕션 배포 워크플로를 변경할 수 있는 권한을 제한합니다.
  3. 적용 및 감시정책이 모든 새 워크플로에 적용되고, 정책 위반이 발생하면 로그에 기록됩니다.

다른 CI에서 옮겨오기

Jenkins·GitLab CI·CircleCI 등 기존 CI 설정을 GitHub Actions 워크플로 문법으로 옮기는 매핑과 마이그레이션 도구다.

#1문제 상황

Jenkins, GitLab CI, CircleCI, Travis CI 같은 다른 CI 시스템을 사용하고 있으면, 그 시스템의 설정 파일(Jenkinsfile, .gitlab-ci.yml, .circleci/config.yml 등)이 이미 있습니다. GitHub Actions로 옮기려면 이 설정들을 GitHub Actions 문법으로 새로 작성해야 합니다. 수동으로 하나하나 옮기는 것은 시간이 많이 걸리고 실수하기 쉽습니다.

#2핵심 질문

기존 CI 설정을 어떻게 GitHub Actions로 빠르고 정확하게 변환할 수 있나요?

#3동작 예시

기존 CI 설정에서 "우분투 이미지에서 npm install 실행, npm test 실행, 성공하면 배포 서버에 ssh로 접속해서 배포" 같은 단계들이 있다면, 이를 GitHub Actions 문법의 "jobs → steps → run" 구조로 맞춰서 다시 쓰는 것입니다. 같은 의미의 작업도 문법만 다르므로, 개념을 이해하면 변환할 수 있습니다.

#4동작 과정

  1. 기존 설정 분석기존 CI에서 각 단계가 무엇을 하는지, 어떤 환경에서 실행되는지, 어디로 배포하는지 파악합니다.
  2. GitHub Actions 문법으로 매핑각 단계를 GitHub Actions의 잡, 스텝(step), 액션(action)으로 대응시킵니다. 예를 들어 "npm install"은 "run: npm install" 스텝이 되고, "ssh 배포"는 배포 액션 또는 커스텀 스크립트로 구현합니다.
  3. 마이그레이션 도구 또는 수동 변환GitHub은 Jenkins와 GitLab CI용 변환 가이드와 도구를 제공하므로, 이를 참고하거나 도구로 자동 변환한 후 조정합니다.

좋은 파이프라인의 판단 기준

빠르고, 결과가 늘 같고, 실패 원인이 바로 보이고, 안전하며, 읽고 고치기 쉬운가 - 이 다섯을 기준으로 파이프라인을 평가한다.

#1문제 상황

파이프라인이 작동하기만 하면 충분하다고 생각하기 쉽습니다. 하지만 실제로는 파이프라인이 느리면 배포가 지연되고, 불안정하면 실패했을 때 원인을 모르고, 복잡하면 유지보수가 어렵고, 보안이 허술하면 악의적인 코드가 프로덕션에 들어갑니다. 따라서 단순히 "작동한다"는 것만으로는 부족합니다.

#2핵심 질문

파이프라인이 정말 좋다는 것을 어떤 기준으로 판단할 수 있나요?

#3동작 예시

좋은 파이프라인은 빠르게 실행되고(같은 코드를 다시 실행해도 시간이 같음), 결과가 항상 일관성 있고(무작위 실패가 없음), 실패하면 어디가 문제인지 명확하고(로그가 읽기 쉬움), 외부 공격으로부터 안전하며(Secrets 누출 없음), 팀원들이 읽고 수정하기 쉬운(문법과 구조가 명확함) 다섯 가지 조건을 만족합니다.

#4동작 과정

  1. 성능과 안정성 평가파이프라인의 평균 실행 시간이 얼마나 되는지, 실패율은 얼마나 되는지, 불필요한 단계가 없는지 확인합니다.
  2. 명확성과 디버깅 용이성 평가실패했을 때 로그에서 원인을 빠르게 찾을 수 있는지, 각 단계의 목적이 명확한지 봅니다.
  3. 보안과 유지보수성 평가민감한 정보(API 키, 비밀번호)가 Secrets로 관리되는지, 워크플로 코드가 너무 복잡하지 않은지, 팀원이 이해하고 수정할 수 있는지 확인합니다.

#5한 줄 요약
