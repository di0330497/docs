1단계 아키텍처 (Architecture)

기업 네트워크를 계층형(코어·배포·액세스) 구조로 나누고 확장성·가용성·보안·관리 용이성을 함께 고려해 설계하는 기본 원칙이다.

#1문제 상황

기업 네트워크를 설계할 때 기존에는 각 부서나 건물 단위로 스위치를 두고 필요할 때마다 연결을 추가하는 방식이 일반적이었다. 이 방식은 규모가 작을 때는 단순해서 관리가 쉬웠지만, 조직이 커지면서 문제가 드러난다. 장비가 늘어나면 서로 연결되는 경로가 기하급수적으로 늘어나고, 어떤 장비가 어느 역할을 하는지가 흐려져서 장애가 났을 때 원인을 찾기 어렵다. 또 한 곳에 트래픽이 몰리면 나머지 네트워크 전체가 느려지는 현상도 막을 수 없다. 확장하거나 보안 정책을 적용하려면 일일이 장비 단위로 설정을 바꿔야 해서 비용과 인력이 계속 늘어난다.

#2핵심 질문

네트워크가 커지고 장비가 많아져도 일관된 규칙으로 설계하고 관리할 수는 없을까?

#3동작 예시

네트워크를 세 층으로 나누는 것이 대표적인 예시다. 가장 아래 액세스 층은 직원의 PC나 무선 AP가 직접 연결되는 스위치들이 모인 곳이고, 가운데 배포 층은 액세스 층의 트래픽을 모아 정책과 라우팅을 적용하는 곳이며, 가장 위 코어 층은 배포 층들을 서로 빠르게 연결해 사내 전체 트래픽의 백본 역할을 하는 곳이다. 각 장비는 자기 층의 역할만 수행하므로, 새 건물이 생기면 액세스 스위치를 배포 층에 연결하기만 하면 되고, 코어 층은 그대로 유지된다.

#4동작 과정

  1. 계층 분리네트워크를 코어·배포·액세스 세 층으로 나누고, 각 층에 수행할 역할(빠른 전달·정책 적용·사용자 연결)을 하나씩 할당한다.
  2. 계층 간 표준 연결각 층은 위아래 이웃 층에만 표준 방식으로 연결된다. 장비가 늘어도 연결 규칙이 일정하므로 추가 작업이 단순해진다.
  3. 정책·보안의 중앙 적용보안 필터와 접근 제어는 배포 층에서 한 번에 적용되고, 코어 층은 단순히 빠르게 전달하는 일에 집중한다. 그 결과 확장성·가용성·보안·관리 용이성이 함께 유지된다.

#5한 줄 요약

네트워크를 코어·배포·액세스 세 층으로 나누어 각 층에 역할을 명확히 부여함으로써 확장·보안·장애 대응을 일관된 규칙 아래 가능하게 만드는 설계 원칙

장비나 링크가 고장 나도 서비스가 끊기지 않도록 이중화·장애조치·로드밸런싱 등으로 시스템 가용성을 높이는 기법이다.

#1문제 상황

기존에는 네트워크 장비 한 대가 자신에게 연결된 모든 트래픽을 처리했다. 장비 한 대로 충분하다는 전제 아래 단순하게 구성했기 때문에, 그 장비가 고장 나거나 펌웨어 업그레이드로 재부팅되는 동안 연결된 사용자 전부가 서비스를 이용할 수 없었다. 전원 공급 장치나 링크가 하나뿐이라서 작은 고장 하나가 전체 서비스 중단으로 이어졌고, 장애 발생 시 대체 경로나 예비 장비가 없어서 수리하는 동안 계속 정지 상태가 유지됐다. 이런 구조에서는 가용성, 즉 실제로 서비스가 살아 있는 시간의 비율을 높이는 데 한계가 명확했다.

#2핵심 질문

장비나 링크 하나가 고장 나도 서비스가 끊기지 않게 하려면 어떻게 해야 할까?

#3동작 예시

게이트웨이 역할을 하는 라우터 두 대를 같은 그룹으로 묶는 방식이 대표적이다. 두 라우터는 하나의 가상 IP 주소를 공유하고, 평소에는 한 대가 주 역할로 모든 트래픽을 처리한다. 나머지 한 대는 대기 상태로 있다가, 주 역할 라우터가 고장 나거나 응답하지 않으면 수 초 안에 가상 IP 주소를 이어받아 동일한 서비스를 계속 제공한다. 사용자 입장에서는 연결 대상 주소가 바뀌지 않으므로 끊김을 느끼지 못한다.

#4동작 과정

  1. 이중화 구성동일한 역할을 하는 장비나 링크를 두 벌 준비하고, 한쪽을 주 역할, 다른 쪽을 대기 역할로 지정한다. 두 장비는 주기적으로 상태를 주고받는다.
  2. 장애 감지대기 장비가 주 장비로부터 일정 시간 응답을 받지 못하면 고장으로 판단하고 즉시 활성화를 결정한다.
  3. 장애조치대기 장비가 가상 IP 주소와 서비스 역할을 이어받아 트래픽 처리를 시작한다. 로드밸런싱을 함께 쓰면 평소에도 두 장비가 작업을 나눠 처리해 부하를 분산한다.

#5한 줄 요약

장비·링크·전원 등을 이중화하고 장애를 감지해 예비 자원이 역할을 이어받게 함으로써 단일 고장이 서비스 중단으로 이어지지 않게 하는 것

#1문제 상황

무선 네트워크를 처음 도입할 때는 AP 하나가 자체적으로 무선 설정과 인증을 모두 처리하는 독립형 방식이 흔했다. 이 방식은 소규모 사무실에서는 설정이 간단했지만, AP가 수십 대로 늘어나면 문제가 생긴다. 채널과 주파수를 AP마다 개별적으로 관리하다 보니 서로 간섭이 일어나고, 모든 AP에 동일한 설정을 일일이 반영해야 해서 오류가 잦았다. 사용자가 이동할 때 다른 AP로 넘어가는 로밍도 AP끼리 협력하지 않아 끊김 없이 처리하기 어려웠고, 보안 정책과 무선 감시를 중앙에서 일관되게 적용할 방법이 없었다.

#2핵심 질문

수십·수백 대의 AP를 일관된 정책 아래 중앙에서 관리하려면 무선 네트워크를 어떤 방식으로 배포해야 할까?

#3동작 예시

중앙 집중형 모델이 대표적이다. 모든 AP는 컨트롤러라는 중앙 장비에 등록되고, 무선 설정·인증·보안 정책은 컨트롤러에서 한 번 정해져 AP에 내려간다. 그 옆에는 소규모 단독 AP형인 자율형, 인터넷을 통해 관리 서비스로 제공되는 클라우드형, AP끼리 서로 연결해 백본을 구성하는 메시형, 그리고 정책을 소프트웨어로 정의하는 SD-Access 무선 방식이 있어 배포 규모와 관리 주체에 따라 선택된다.

#4동작 과정

  1. 방식 선택배포 규모와 관리 주체에 따라 자율형(AP 단독), 중앙 집중형(컨트롤러 관리), 클라우드형(인터넷 관리 서비스), 메시형(AP 간 연결), SD-Access 무선(소프트웨어 정의 정책) 중 하나를 고른다.
  2. AP 등록과 설정 배포중앙 집중형에서는 AP가 부팅되면 컨트롤러를 찾아 등록하고, 컨트롤러가 채널·보안·SSID 설정을 내려준다. AP는 수신한 설정 그대로 동작한다.
  3. 중앙 운영컨트롤러가 모든 AP의 상태를 모아 한 화면에 보여주고, 설정 변경은 중앙에서 한 번만 해도 전체 AP에 적용된다. 로밍도 컨트롤러가 좌표를 잡아주어 끊김을 줄인다.

#5한 줄 요약

AP가 무선 기능을 스스로 처리하는지, 컨트롤러나 클라우드가 중앙에서 일괄 관리하는지에 따라 자율형·중앙 집중형·클라우드형·메시형·SD-Access 무선으로 배포 방식을 구분 짓는 것

#3동작 예시

신호 세기 기반 측위가 대표적이다. 한 건물 안에 AP 여러 대가 이미 배치되어 있고, 각 AP는 클라이언트 장치가 보내는 무선 신호의 세기를 측정한다. 신호가 강하면 가깝고 약하면 멀다는 원리로, 여러 AP가 측정한 거리 정보가 겹쳐지면 클라이언트가 놓인 지점이 계산된다. 이렇게 얻은 위치는 자산 추적, 방문자 흐름 분석, 위치 기반 알림 같은 서비스에 활용된다.

#4동작 과정

  1. 신호 측정주변 AP들이 클라이언트 장치의 무선 신호 세기를 각자 측정한다. 세기는 신호가 도달한 강도로, 거리와 반비례한다.
  2. 위치 계산측정된 여러 신호 세기 정보가 위치 서버에 모이고, 각 AP와의 거리를 반지름으로 한 원들이 교차하는 지점이 클라이언트의 위치로 산출된다.
  3. 서비스 활용산출된 좌표와 시간 정보가 추적·분석 기능으로 전달되어 자산 위치 확인, 이동 흐름 통계, 위치 기반 서비스 제공에 사용된다.

#5한 줄 요약

#1문제 상황

무선 네트워크를 설계할 때 기존에는 AP를 일정한 간격으로 배치하고 대역폭만 넉넉히 잡으면 된다고 보는 경우가 많았다. 하지만 실제 환경에서는 한 회의실이나 강당에 수십 명이 동시에 접속하는 상황이 생기고, 이때 문제가 드러난다. 하나의 채널은 한 번에 하나의 클라이언트와 통신할 수 있어서, 접속자가 많아질수록 각자에게 돌아가는 전송 시간이 줄어든다. AP의 최대 전송 속도가 아무리 빨라도 클라이언트 수가 많아지면 한 명당 속도가 급격히 떨어지고, 간섭까지 겹치면 실제 체감 속도는 더 나빠진다.

#2핵심 질문

한 AP에 동시에 접속하는 클라이언트 수를 고려하지 않으면 무선 설계가 실패하는 이유는 무엇일까?

#3동작 예시

하나의 AP가 단일 채널에서 한 번에 한 클라이언트와만 데이터를 주고받는 방식이 핵심 예시다. AP의 전송 속도가 1Gbps라고 해도, 100명이 동시에 접속하면 통신 시간을 나눠 쓰므로 한 명이 받는 실제 속도는 그 일부에 지나지 않는다. 따라서 클라이언트 밀도가 높은 공간에서는 AP를 더 촘촘히 배치하거나 무선 주파수 대역을 더 많이 확보하고 전송률을 조정해, 한 셀에 머무는 접속자 수를 관리 가능한 수준으로 유지한다.

#4동작 과정

  1. 밀도 파악목표 공간에서 동시에 접속할 것으로 예상되는 최대 클라이언트 수를 산정하고, 한 AP(셀)가 감당해야 할 인원을 정한다.
  2. 용량 계획채널 수와 주파수 대역을 기준으로 한 AP당 처리 가능한 동시 접속 수를 계산하고, 이를 초과하지 않도록 AP 배치 간격과 수를 조정한다.
  3. 운영 조정전송률과 부하 분산 설정을 조정해 특정 AP로 접속자가 몰리지 않게 하고, 실제 사용량을 관찰해 필요한 곳에 AP를 추가한다.

#1문제 상황

네트워크 장비를 도입할 때 기존에는 컨트롤러와 관리 장비를 사내 데이터 센터에 설치하고, 회사가 직접 전원·냉각·보안·펌웨어 업데이트를 관리하는 방식이 표준이었다. 이 방식은 데이터가 회사 안에 머물고 장비를 직접 통제할 수 있다는 장점이 있지만, 초기 투자 비용이 크고 사내 전담 인력이 항상 필요하며, 지점이 늘어날 때마다 현장에 장비를 설치하고 유지보수해야 했다. 반대로 모든 것을 클라우드에 맡기면 관리 부담은 줄지만, 인터넷이 끊기면 관리 기능까지 멈추고 데이터가 외부 서버로 나가는 것에 대한 부담이 생긴다.

#3동작 예시

#4동작 과정

  1. 요구 조건 정리초기 비용, 운영 인력, 데이터 보안 요구, 지점 수, 인터넷 단절 허용도를 기준으로 배포 방식을 후보에 올린다.
  2. 방식 선택과 구축온프레미스를 선택하면 사내에 컨트롤러를 설치하고, 클라우드를 선택하면 클라우드 관리 서비스에 계약하고 AP를 등록한다.
  3. 운영 비교온프레미스는 사내 인력이 장비를 직접 관리하고, 클라우드는 공급자가 업데이트와 장애 처리를 맡는다. 장애와 비용이 발생하는 위치에 따라 선택이 실효성을 가진다.

#1문제 상황

여러 종류의 전송망을 상황에 맞게 골라 쓰면서도 중앙에서 일관된 정책으로 WAN을 관리할 수는 없을까?

#3동작 예시

중앙 컨트롤러가 모든 지사의 WAN 경로를 관리하는 방식이 대표적이다. 각 지사에는 가벼운 장비가 설치되고, 컨트롤러는 MPLS·인터넷·5G 같은 여러 전송망의 상태를 실시간으로 파악하고 있다가 트래픽 종류에 따라 어느 망으로 보낼지 정책을 내려준다. 예를 들어 중요 업무 트래픽은 MPLS로, 일반 웹 트래픽은 인터넷으로 보내고, 한 회선이 끊기면 다른 회선으로 자동 전환한다. 정책 변경은 컨트롤러에서 한 번만 하면 모든 지사에 적용된다.

#4동작 과정

  1. 중앙 정책 수립컨트롤러에서 트래픽 종류별 우선순위와 사용할 전송망 규칙을 정의하고, 이를 자동으로 각 지사 장비에 배포한다.
  2. 경로 모니터링과 선택지사 장비가 회선 상태 정보를 컨트롤러에 보내고, 컨트롤러는 현재 상황과 정책을 비교해 각 트래픽이 갈 전송망을 결정한다.
  3. 전달과 장애 전환결정된 전송망으로 트래픽이 전달되고, 사용 중인 회선이 끊기면 감지 즉시 다른 가용 회선으로 경로가 전환되어 서비스가 이어진다.

#5한 줄 요약

컨트롤러가 중앙에서 WAN 경로와 정책을 정의하고, MPLS·인터넷·5G 등 여러 전송망을 실시간 상태에 따라 선택·전환하며 트래픽을 전달하는 소프트웨어 정의 WAN 방식

SD-Access 작동 원리

컨트롤러가 LISP·VXLAN 기반 페브릭(Underlay/Overlay)을 엔드투엔드로 구성해 정책 기반 접근 제어와 자동화를 제공하는 소프트웨어 정의 액세스 방식이다.

#1문제 상황

기존의 캠퍼스 네트워크에서는 스위치 한 대씩 VLAN, VRF, ACL, 802.1X 설정을 일일이 넣어야 했다. 스위치가 수십 대로 늘면 같은 설정을 장비마다 반복해서 넣어야 하고, 사용자가 다른 건물로 옮겨가면 해당 스위치 포트의 VLAN을 관리자가 다시 맞춰야 했다. 이런 수동 구성은 장비마다 설정이 조금씩 달라져서 정책이 어디서 어떻게 적용되는지 파악하기 어렵고, 네트워크 확장과 변경에 많은 시간이 걸리는 한계가 있었다.

#2핵심 질문

네트워크 전체를 한 곳에서 정의하고, 사용자가 어디에 붙든 그 사용자에게 같은 정책을 자동으로 적용하려면 어떻게 해야 할까?

#3동작 예시

SD-Access에서는 네트워크를 물리적 토폴로지(Underlay)와 논리적 토폴로지(Overlay)로 분리한다. Underlay는 스위치와 라우터를 서로 연결하는 실제 전송망이고, Overlay는 그 위에 VXLAN 터널을 만들어 사용자·장치가 속한 가상 네트워크다. 컨트롤러가 이 두 계층을 모두 관리하므로, 관리자가 컨트롤러에서 "이 사용자는 이 가상 네트워크에 속하고 이 정책을 받는다"고 한 번 정의하면 스위치에 일일이 명령을 넣지 않아도 실제 장비들이 자동으로 그 구성대로 동작한다.

#4동작 과정

  1. 패브릭 준비컨트롤러가 각 스위치를 패브릭 역할(엣지, 본더, 컨트롤 플레인)로 지정하고, 스위치 사이에 LISP와 VXLAN 기반의 Overlay 터널을 만든다.
  2. 장치 등록과 정책 매핑사용자나 장치가 엣지 스위치에 연결되면 컨트롤러의 인증 절차를 거쳐 그 장치가 속할 가상 네트워크(VN)와 적용할 접근 정책이 결정된다. 이때 LISP가 "이 장치는 어느 가상 네트워크에 있는가"라는 위치 정보를 관리한다.
  3. 엔드투엔드 통신패킷이 출발지 엣지 스위치에서 VXLAN 터널로 캡슐화되어 목적지 엣지 스위치까지 전달되고, 목적지에서 원래 패킷으로 풀려 사용자에게 전달된다. 출발지와 목적지가 다른 물리 위치여도 정책과 가상 네트워크 구성은 그대로 유지된다.

#5한 줄 요약

컨트롤러가 Underlay와 Overlay를 통째로 구성·관리해서 장비별 수동 설정 없이 정책 기반 접근 제어와 자동화를 제공하는 것

QoS 구성 요소

분류·마킹, 폴리싱·셰이핑, 큐잉·스케줄링, 혼잡 회피 등 트래픽을 우선순위에 따라 처리하기 위한 QoS의 기본 구성 요소들이다.

#1문제 상황

기존 네트워크에서는 모든 패킷을 동등하게 취급했다. 스위치나 라우터는 도착한 패킷을 버퍼에 쌓아두고 도착한 순서대로 전송하므로, 대량의 파일 전송이나 다운로드 트래픽이 선로를 가득 채우면 음성 통화나 화상 회의 패킷이 뒤로 밀려 지연되고 끊겼다. 대역폭이 충분하면 문제가 드러나지 않지만, 링크가 혼잡해지는 순간 어떤 트래픽이 중요한지 구분할 방법이 없는 것이 근본적인 한계였다.

#2핵심 질문

혼잡한 링크에서 중요한 트래픽을 먼저 보내고 덜 중요한 트래픽을 나중에 보내려면 패킷을 어떻게 골라내고 순서를 정해야 할까?

#3동작 예시

QoS는 트래픽을 처리하는 여러 단계의 구성 요소로 이루어진다. 스위치에 들어온 패킷에 "음성" 또는 "데이터"라는 표시(마킹)를 붙이고, 표시된 등급에 따라 이 패킷은 받아들이거나(폴리싱) 일정 속도로 늦춰 보내고(셰이핑), 송신 큐에서 우선순위가 높은 등급을 먼저 꺼내 보내며, 큐가 가득 차기 전에 낮은 등급의 패킷을 먼저 버려서(혼잡 회피) 높은 등급의 지연을 보호한다. 예컨대 음성과 데이터가 섞여 들어와도 음성 패킷이 항상 앞선 큐를 통해 나간다.

#4동작 과정

  1. 분류·마킹패킷이 들어오면 어떤 트래픽인지 분류하고, 패킷 헤더의 QoS 표시 필드에 등급 값을 기록한다.
  2. 폴리싱·셰이핑등급마다 허용된 대역폭을 넘는 트래픽은 버리거나(폴리싱) 버퍼에 모아 천천히 보내 속도를 제한한다.
  3. 큐잉·스케줄링과 혼잡 회피송신 포트의 여러 큐에 등급별로 패킷을 넣고, 우선순위 높은 큐를 먼저 전송하며, 큐가 차오르면 낮은 등급의 패킷을 먼저 버려 지연을 관리한다.

#5한 줄 요약

분류, 마킹, 속도 제어, 큐잉, 혼잡 회피라는 구성 요소들을 순서대로 적용해 혼잡 상황에서도 트래픽 우선순위대로 처리하는 것

QoS 정책

음성·영상·데이터 등 트래픽 유형에 서비스 클래스를 지정하고 대역폭·대기열을 배분해 서비스 품질을 보장하는 규칙이다.

#1문제 상황

QoS 구성 요소를 장비에 하나씩 설정한다고 해서 품질이 보장되지는 않았다. 스위치마다 "어떤 트래픽을 몇 등급으로 나누고, 각 등급에 대역폭을 얼마씩 줄지"를 관리자가 임의로 정하다 보니, 한 장비에서는 음성이 높은 우선순위인데 다른 장비에서는 데이터가 높은 우선순위로 표시되는 등 네트워크 전체에서 일관된 서비스 품질을 만들 수 없었다. 트래픽 유형별로 어떤 처리를 받을지가 각 장비마다 제각각이라는 것이 한계였다.

#2핵심 질문

네트워크 전체에서 트래픽 유형별로 일관된 서비스 품질을 보장하려면 각 등급에 어떤 자원을 얼마나 배분할지 어떻게 정해야 할까?

#3동작 예시

QoS 정책은 "음성 트래픽은 EF(높은 우선순위) 서비스 클래스를 주고 대역폭 1Mbps를 보장하며, 데이터 트래픽은 기본 클래스를 주고 남는 대역폭을 나눠 쓴다"처럼 트래픽 유형에 서비스 클래스(class)를 지정하고 클래스마다 대역폭과 대기열을 배분하는 규칙이다. 관리자가 이 정책을 스위치의 입구(인그레스)에서는 마킹·폴리싱으로, 출구(이그레스)에서는 클래스별 큐와 대역폭 비율로 적용하면, 트래픽이 여러 장비를 지나도 같은 클래스가 같은 대우를 받는다.

#4동작 과정

  1. 클래스 정의와 분류음성, 영상, 데이터 등 트래픽 유형을 식별 조건으로 묶어 클래스를 만들고, 도착한 패킷이 어느 클래스인지 판별한다.
  2. 서비스 클래스 지정과 마킹판별된 클래스에 따라 패킷의 QoS 표시 값을 정하고, 필요한 경우 대역폭 제한(폴리싱) 조건을 적용한다.
  3. 대역폭·대기열 배분송신 포트에서 클래스마다 보장 대역폭과 큐 점유 비율을 지정해, 음성처럼 지연에 민감한 클래스는 항상 먼저 전송되고 데이터 클래스는 남는 대역폭을 나눠 쓴다.

#5한 줄 요약

트래픽 유형에 서비스 클래스를 지정하고 클래스마다 대역폭과 대기열을 배분하는 규칙을 정해, 혼잡 상황에서도 유형별로 일관된 서비스 품질을 보장하는 것

프로세스 스위칭 vs CEF

패킷마다 CPU가 라우팅을 계산하는 프로세스 스위칭과, FIB·인접 테이블을 미리 만들어 하드웨어가 고속 전달하는 CEF를 비교하는 주제다.

#1문제 상황

초기 라우터는 패킷이 도착할 때마다 CPU가 라우팅 테이블을 뒤져서 목적지 경로를 계산하고 패킷을 보냈다. 이 방식을 프로세스 스위칭이라 하는데, 패킷 하나를 처리할 때마다 테이블 조회와 계산을 처음부터 다시 해야 하므로 트래픽이 많아지면 CPU가 곧바로 포화되어 전송 속도가 급격히 떨어졌다. 개별 패킷 처리는 정확하지만 처리량을 늘릴 수 없는 것이 명확한 한계였다.

#2핵심 질문

패킷이 올 때마다 경로를 다시 계산하지 않고도 고속으로 패킷을 전달하려면 라우팅 정보를 어떻게 재사용해야 할까?

#3동작 예시

CEF(Cisco Express Forwarding)는 경로 계산 결과를 미리 테이블로 만들어 두고 패킷 전달은 하드웨어가 담당하는 방식이다. 라우팅 프로토콜이 만든 경로 정보에서 최적 경로만 골라 FIB(전달 정보 베이스)를 만들고, 목적지 MAC을 찾을 수 있도록 인접 테이블(adjacency table)을 미리 채워 둔다. 패킷이 도착하면 CPU를 거치지 않고 하드웨어가 FIB와 인접 테이블을 조회해 바로 다음 홉으로 보내므로, 같은 목적지가 반복돼도 매번 계산하지 않는다.

#4동작 과정

  1. 테이블 구축라우팅 프로토콜이나 정적 경로가 RIB(라우팅 정보 베이스)를 만들고, 그중 최적 경로만 뽑아 FIB와 인접 테이블을 하드웨어 메모리에 미리 채운다.
  2. 패킷 수신과 조회패킷이 들어오면 CPU 개입 없이 하드웨어가 FIB에서 목적지에 맞는 경로 항목과 인접 테이블의 2계층 정보를 찾는다.
  3. 하드웨어 전달찾은 정보로 패킷에 새 2계층 헤더를 붙여 다음 홉으로 보낸다. 경로가 바뀌지 않는 한 이후 패킷도 같은 테이블로 즉시 전달된다.

#5한 줄 요약

프로세스 스위칭이 패킷마다 CPU로 경로를 계산하던 것을, FIB와 인접 테이블을 미리 만들어 하드웨어가 바로 조회·전달하는 CEF로 대체해 처리량을 높이는 것

MAC 주소 테이블 vs TCAM

MAC 주소 테이블은 수신지 MAC 기준 2계층 전달에 쓰이고, TCAM은 병렬 검색으로 ACL·QoS 등 정책 매칭을 고속 처리하는 특수 메모리다.

#1문제 상황

스위치는 수신지 MAC 주소로 어느 포트로 보낼지 정하기 위해 MAC 주소 테이블을 사용했고, 이 테이블을 찾는 데는 일반 메모리(RAM)처럼 주소를 하나씩 순차 검색하는 방식을 썼다. 그런데 ACL(접근 제어 목록)이나 QoS 같은 정책은 "이 패킷은 차단, 저 패킷은 우선 처리"처럼 여러 조건을 각각 비교해야 하고, 정책 수가 늘어나면 순차 검색으로는 패킷마다 비교 횟수가 늘어나 전송 속도를 따라갈 수 없었다. 조건 매칭에 순차 검색을 쓰는 것이 한계였다.

#2핵심 질문

수많은 정책 조건을 패킷마다 빠짐없이 비교하면서도 전송 속도를 유지하려면 어떤 메모리 구조가 필요할까?

#3동작 예시

MAC 주소 테이블은 "수신지 MAC → 출력 포트" 매핑을 저장해 정확히 하나의 항목을 찾는 용도이고, TCAM(Ternary Content-Addressable Memory)은 모든 항목을 동시에 비교해 조건에 맞는 항목을 한 번에 찾는 특수 메모리다. 예를 들어 ACL에 1,000개의 차단 규칙이 있어도 패킷이 들어오면 TCAM이 1,000개 규칙을 병렬로 비교해 일치하는 규칙을 순차 검색 없이 즉시 찾아낸다. TCAM은 0, 1뿐 아니라 "아무 값이나 허용"이라는 와일드카드 상태를 저장할 수 있어서 서브넷 범위 같은 조건도 한 항목으로 매칭한다.

#4동작 과정

  1. 항목 저장MAC 주소 테이블은 수신지 MAC과 포트 쌍을 일반 메모리에 저장하고, TCAM에는 ACL·QoS 정책 조건을 와일드카드 포함 3진 상태로 저장해 둔다.
  2. 패킷 도착 시 매칭2계층 전달은 MAC 주소 테이블에서 수신지 MAC 항목을 찾아 해당 포트로 보내고, 정책 검사는 TCAM이 모든 규칙을 동시에 비교해 첫 일치 규칙을 반환한다.
  3. 처리 결과 적용MAC 테이블 조회 결과로 패킷을 전달하고, TCAM 일치 결과로 차단·허용·큐 지정 같은 정책을 적용한다. 두 검색 모두 하드웨어가 병렬로 처리해 속도 저하 없이 수행된다.

#5한 줄 요약

MAC 주소 테이블이 수신지 MAC 기준 2계층 전달을 담당하고, TCAM이 병렬 검색으로 ACL·QoS 등 정책 조건을 고속 매칭하는 특수 메모리라는 점에 있습니다

FIB vs RIB

RIB는 라우팅 프로토콜이 만든 전체 경로 정보(제어 플레인)이고, FIB는 그중 최적 경로를 패킷 전달에 바로 쓰도록 정리한 테이블(데이터 플레인)이다.

#1문제 상황

라우터에는 라우팅 프로토콜이 수집한 경로 정보가 많았다. OSPF, EIGRP, 정적 경로 등이 각자 알고 있는 목적지 경로를 모두 모아 두는데, 같은 목적지에 여러 경로가 있으면 어느 것을 실제 패킷 전달에 쓸지 결정해야 했다. 모든 경로 정보를 그대로 매번 뒤져서 패킷을 보내면 우선순위 비교와 중복 제거를 반복해야 하고, 하드웨어가 바로 쓸 수 있는 형태가 아니어서 고속 전달이 어려웠다. 각 프로토콜이 만든 원시 경로 정보를 그대로 쓰는 것이 한계였다.

#2핵심 질문

여러 라우팅 프로토콜이 만든 수많은 후보 경로를, 패킷 전달에 바로 쓸 수 있는 단 하나의 테이블로 정리하려면 어떻게 해야 할까?

#3동작 예시

RIB(Routing Information Base)는 라우팅 프로토콜들이 만든 전체 경로 정보를 모아 둔 "후보 목록"이고, FIB(Forwarding Information Base)는 그중에서 관리 거리와 메트릭을 따져 가장 좋다고 판정된 최적 경로만 뽑아 패킷 전달용으로 정리한 테이블이다. 예를 들어 RIB에 목적지 10.0.0.0/8로 가는 경로가 OSPF와 정적 경로 두 개 있어도, 우선순위(관리 거리)를 비교해 정적 경로 하나만 FIB에 들어간다. 패킷이 도착하면 라우팅 프로토콜 계산 없이 하드웨어가 FIB만 조회해 다음 홉으로 보낸다.

#4동작 과정

  1. RIB 구축OSPF, EIGRP, 정적 경로 등 각 라우팅 프로토콜이 알고 있는 경로를 모두 RIB에 등록하고, 같은 목적지의 후보 경로들을 우선순위와 메트릭을 기준으로 정렬해 둔다.
  2. 최적 경로 선택RIB에서 목적지별로 관리 거리가 가장 낮은 최적 경로를 하나 선택하고, 필요한 경우 재귀 조회로 실제 출력 인터페이스와 다음 홉까지 결정한다.
  3. FIB 생성과 전달선택된 최적 경로만 하드웨어 메모리의 FIB로 내려 보낸다. 패킷이 도착하면 CPU 계산 없이 FIB를 조회해 다음 홉으로 즉시 전달한다.

#5한 줄 요약

RIB가 라우팅 프로토콜이 만든 전체 경로 정보(제어 플레인)를 담고, FIB가 그중 최적 경로만 뽑아 패킷 전달에 바로 쓰는 테이블(데이터 플레인)이라는 점

하이퍼바이저는 물리 서버에서 여러 가상 머신을 실행하게 해주는 소프트웨어 계층으로, 유형 1은 하드웨어 위에 직접(베어메탈) 실행되고 유형 2는 호스트 OS 위에서 실행된다.

#1문제 상황

물리 서버 한 대에 운영체제 하나만 설치해 사용하는 기존 방식에서는 서버가 늘어날 때마다 새 하드웨어를 사야 했고, CPU·메모리 사용률이 낮은 서버도 하드웨어 하나를 계속 점유했다. 서로 다른 운영체제나 애플리케이션을 같은 장비에서 격리해 돌리려면 물리 장비를 나누는 방법밖에 없어 자원 활용과 확장에 한계가 있었다. 하나의 물리 서버를 여러 운영체제가 나눠 쓰는 방법이 없다는 것이 문제였다.

#2핵심 질문

물리 서버 한 대에서 여러 운영체제를 서로 간섭하지 않게 동시에 실행하려면 하드웨어와 운영체제 사이에 무엇을 두어야 할까?

#3동작 예시

하이퍼바이저는 물리 서버의 CPU, 메모리, 저장 장치를 여러 가상 머신에 나눠 주고 각 가상 머신의 운영체제가 하드웨어에 직접 접근한 것처럼 보이게 만드는 소프트웨어 계층이다. 유형 1(베어메탈) 하이퍼바이저는 물리 하드웨어 위에 바로 설치되어 호스트 OS 없이 가상 머신만 관리하므로 성능과 안정성이 높고, 유형 2는 일반 운영체제 위에서 응용 프로그램처럼 실행되므로 설치가 쉽지만 그 운영체제를 거쳐야 해서 성능과 격리가 상대적으로 약하다.

#4동작 과정

  1. 가상 머신 생성하이퍼바이저가 물리 자원(CPU 코어, 메모리, 디스크)을 나눠 각 가상 머신에 할당하고, 가상 장치(가상 NIC, 가상 디스크)를 만들어 준다.
  2. 스케줄링과 자원 배분유형 1은 하드웨어에 직접 접근해 가상 머신들의 CPU 실행 순서를 정하고 메모리를 격리해 관리하며, 유형 2는 호스트 OS의 프로세스로 실행되어 호스트 OS의 자원 관리 아래에서 동작한다.
  3. 가상 머신 실행각 가상 머신에 운영체제가 부팅되어 가상 장치를 실제 하드웨어처럼 사용하고, 하이퍼바이저는 가상 머신들이 서로 간섭하지 않도록 하드웨어 접근을 중재한다.

#5한 줄 요약

하이퍼바이저가 물리 서버의 자원을 가상 머신들에 분배·격리해 주는 계층이며, 유형 1은 하드웨어 위에 직접 실행되어 성능이 높고 유형 2는 호스트 OS 위에서 실행되어 설치가 쉬운 대신 성능과 격리가 약하다는 것

가상 머신은 하이퍼바이저가 물리 하드웨어 자원(CPU, 메모리, 스토리지, NIC)을 분할해 만든, 자체 OS와 가상 하드웨어를 가진 소프트웨어 기반 컴퓨터이다.

#1문제 상황

기존에는 서버 한 대에 운영체제 하나와 응용 프로그램 하나만 설치해서 썼다. 물리 하드웨어를 통째로 한 용도에만 할당하므로 CPU, 메모리, 디스크가 남는 시간이 많다. 다른 작업을 추가로 돌리려면 서버를 또 사야 해서 비용이 늘고, 각 서버의 자원 활용률은 낮게 머문다. 여러 서버를 두면 관리할 기기도 늘어나고 장애가 나면 그 기계 하나가 통째로 멈춘다.

#2핵심 질문

한 대의 물리 서버에서 여러 대의 독립된 컴퓨터를 안전하게 동시에 돌릴 수는 없을까?

#3동작 예시

물리 서버 한 대에 하이퍼바이저(가상화 소프트웨어)를 설치한다. 하이퍼바이저는 CPU, 메모리, 스토리지, NIC(네트워크 카드) 같은 물리 자원을 쪼개 각 가상 머신에 할당한다. 각 가상 머신은 자체 OS(운영체제)와 가상 하드웨어를 갖춘 하나의 완전한 컴퓨터로 보인다. 같은 물리 서버 위에서 Windows 가상 머신과 Linux 가상 머신이 서로 간섭 없이 따로 부팅되고 따로 동작한다.

#4동작 과정

  1. 자원 분할하이퍼바이저가 물리 CPU 코어, 메모리, 디스크 용량, NIC를 여러 조각으로 나누고 각 가상 머신에 지정된 양을 배정한다.
  2. 가상 하드웨어 제공각 가상 머신에 가상 CPU, 가상 메모리, 가상 디스크, 가상 NIC를 만들어 OS가 마치 실제 하드웨어인 것처럼 사용하게 한다.
  3. 독립 실행각 가상 머신이 자기 OS를 부팅하고 응용 프로그램을 돌린다. 하이퍼바이저는 각 머신이 맡은 자원 범위를 벗어나지 않게 격리해 한 머신의 장애가 다른 머신으로 번지지 못하게 한다.

#5한 줄 요약

가상 스위칭은 하이퍼바이저 내부에서 가상 NIC와 물리 NIC 사이 프레임을 전달하는 소프트웨어 스위치로, VM 간 및 외부 네트워크와의 통신 경로를 제공한다.

#1문제 상황

물리 서버에서는 NIC(네트워크 카드) 포트에 케이블을 꽂고 스위치로 프레임을 보내 VM이 아닌 실제 장비들이 서로 통신했다. 가상 머신이 생기면서 NIC 포트 수가 물리 한계를 갖게 되었고, 같은 물리 서버 안의 VM들끼리 통신하려면 트래픽이 밖의 실제 스위치까지 나갔다가 다시 돌아와야 했다. VM마다 NIC를 물리적으로 추가하는 방식은 포트 수와 배선 때문에 확장이 불가능했다.

#2핵심 질문

물리 포트와 케이블을 더 늘리지 않고 하이퍼바이저 안에서 가상 머신들을 서로, 그리고 외부 네트워크와 연결할 수는 없을까?

#3동작 예시

하이퍼바이저 내부에 소프트웨어 스위치(가상 스위치)를 만든다. 각 VM의 가상 NIC를 이 스위치의 포트에 연결하고, 스위치의 업링크 포트를 물리 NIC에 연결한다. 두 VM이 통신할 때 프레임은 가상 스위치가 내부에서 바로 전달해 밖으로 나가지 않는다. 외부와 통신할 때는 프레임이 가상 스위치를 지나 물리 NIC로 나간다.

#4동작 과정

  1. 가상 NIC 연결각 VM에 만들어진 가상 NIC를 하이퍼바이저의 가상 스위치 포트에 연결한다.
  2. 내부 전달같은 하이퍼바이저 안 VM 사이 트래픽은 가상 스위치가 MAC 주소(하드웨어 식별 주소)를 보고 내부에서 바로 전달한다.
  3. 외부 연결외부 네트워크로 가는 프레임은 가상 스위치가 물리 NIC로 보내 밖의 실제 스위치에 전달한다.

#2핵심 질문

#3동작 예시

#4동작 과정

3인프라 (Infrastructure)03-02

EtherChannel 트러블슈팅

여러 물리 링크를 하나의 논리 링크로 묶는 EtherChannel의 프로토콜 불일치·로드 밸런싱 문제를 진단하고 해결하는 과정.

→ 03-01 참조

#1문제 상황

EtherChannel 없이 스위치를 연결할 때는 물리 링크가 여러 개여도 스패닝 트리가 그중 하나만 활성화 상태로 쓰고 나머지는 차단해 버린다. 그래서 대역폭을 늘리려고 링크를 여러 개 깔아도 실제로는 하나만 사용되고, 링크 하나가 끊기면 그때 다른 링크가 활성화될 때까지 트래픽이 멈춘다. 또 링크를 강제로 모두 살리면 브리지 루프가 생겨 프레임이 무한히 돌 수 있다. 트러블슈팅이 필요한 상황은 EtherChannel을 구성했는데도 논리 링크가 올라오지 않거나, 올라와도 트래픽이 한쪽 링크로 몰리는 식이다.

#2핵심 질문

EtherChannel이 맺어지지 않거나 로드 밸런싱이 한쪽으로 쏠릴 때, 어디서부터 원인을 분리해서 찾아내야 하는가?

#3동작 예시

두 스위치를 네 개의 물리 링크로 묶으려 할 때, 양쪽 스위치의 EtherChannel 설정이 정확히 같은 조건이어야 논리 링크 하나로 합쳐진다. 양쪽의 채널 모드가 같은지, 양쪽이 인식하는 링크 개수가 같은지가 가장 먼저 보는 지점이다. 예를 들어 한쪽은 on 모드(협상 없이 강제로 채널링)로 설정했는데 다른쪽은 auto 모드(상대가 먼저 협상을 걸어올 때만 응답)로 설정하면, 협상을 건 쪽이 없으므로 두 링크는 EtherChannel로 합쳐지지 않고 각자 독립 링크로 살아남아 스패닝 트리가 하나만 활성화시킨다.

#4동작 과정

  1. 협상 상태 확인show etherchannel summary로 논리 채널이 올라왔는지, 각 물리 링크가 채널에 포함됐는지 확인한다. 링크가 채널에 안 들었으면 양쪽의 채널 모드(active·passive·on)와 협상 프로토콜(LACP·PAgP)이 일치하는지 본다.
  2. 조건 대조채널에 포함된 링크들의 속도·듀플렉스·VLAN 설정이 양쪽 스위치에서 동일한지 확인한다. 한 링크만 스위치포트 모드나 트렁크 허용 VLAN이 다르면 그 링크는 채널에서 빠진다.
  3. 로드 밸런싱 검증show etherchannel load-balance로 해시 기준을 확인하고, 트래픽이 한 링크로 몰리는지 본다. 기준이 목적지 MAC만 쓰면 같은 목적지로 가는 흐름이 전부 한 링크에 실리므로, 해시 기준을 바꿔 분산되게 한다.

#5한 줄 요약

여러 물리 링크를 하나의 논리 링크로 합치려면 양쪽 스위치의 모드·속도·VLAN 조건이 일치해야 하고, 트래픽 분산은 해시 기준의 선택에 달려 있다는 사실을 기준으로 원인을 분리해 확인하는 것

스패닝 트리(RSTP·MST)와 확장

RSTP와 MST가 브리지 루프를 막는 동작 원리와 보호·확장 기능을 다루는 개념.

#1문제 상황

스위치를 여러 대로 연결한 네트워크는 물리적으로 루프가 생기기 쉽고, 루프가 있으면 브로드캐스트 프레임이 스위치 사이를 계속 돌며 네트워크를 마비시킨다. 기존 STP(스패닝 트리 프로토콜)는 이 루프를 막기 위해 루트 브리지를 정하고 루프가 되는 링크를 차단하지만, 토폴로지가 바뀌면 수렴(새 경로로 전환)하는 데 수십 초가 걸려 그동안 트래픽이 끊긴다. 또 스위치 수가 많아지면 STP 하나로는 전체 네트워크를 하나의 트리로 관리해야 해서 차단되는 링크가 많아진다.

#2핵심 질문

브리지 루프를 막으면서도 기존 STP보다 훨씬 빠르게 재구성하고, 큰 네트워크에서도 불필요한 차단을 줄일 수는 없을까?

#3동작 예시

RSTP는 링크가 끊기는 즉시 수렴하는 방식을 쓴다. 기존 STP가 링크가 끊기면 새 BPDU(브리지 정보를 담는 제어 프레임)가 루트에서부터 다시 전파될 때까지 기다렸지만, RSTP는 대체 포트를 미리 활성 대기 상태로 준비해 두고 루트 링크가 끊기면 자기가 곧바로 포워딩으로 전환한다. 그래서 링크 하나가 끊겨도 1초 안에 트래픽이 새 경로로 옮겨 간다.

#4동작 과정

  1. 루트·포트 역할 선출RSTP도 STP처럼 브리지 ID(우선순위·MAC)를 비교해 루트 브리지를 정하고, 각 스위치에서 루트로 가는 최단 경로의 포트를 루트 포트로 지정한다.
  2. 대체 포트 준비루트로 가는 경로가 두 개 이상인 포트는 디스카딩 상태로 두되 대체 포트로 등록해 둔다. 이 포트는 루트 링크가 끊기는 순간 즉시 포워딩이 될 수 있는 후보다.
  3. MST로 영역 분할MST는 여러 VLAN을 몇 개의 인스턴스로 묶어 인스턴스마다 트리를 하나씩 만들고, 이를 통해 VLAN별로 다른 경로를 쓰게 해서 평소에는 차단돼 있던 링크도 다른 인스턴스에서는 활성화시킨다.

#5한 줄 요약

대체 포트를 미리 준비해 두고 수렴을 1초대로 줄인 RSTP와, VLAN을 인스턴스로 묶어 트리 개수를 줄이고 링크 활용도를 높이는 MST로 루프 방지와 빠른 재구성을 동시에 얻는 것

EIGRP vs OSPF 비교

EIGRP와 OSPF 두 다이내믹 라우팅 프로토콜의 동작 방식·수렴 특성·사용 환경을 비교하는 주제.

#1문제 상황

라우터가 네트워크 경로를 서로에게 알리지 않으면, 각 라우터는 자신과 직접 연결된 링크의 경로만 알고 그 너머의 네트워크로는 패킷을 보낼 수 없다. 그래서 다이내믹 라우팅 프로토콜이 필요한데, 프로토콜마다 경로를 계산하는 방식과 수렴 속도가 다르다. 초기 네트워크에서는 RIP처럼 단순히 홉 수만 세는 프로토콜이 쓰였지만, 경로가 많아지고 링크 속도가 제각각이 되면서 홉 수만으로는 최적 경로를 고르지 못하는 한계가 드러났다.

#2핵심 질문

규모와 환경이 다른 네트워크에서, 최적 경로를 빠르게 찾고 링크 변화에 신속히 대응하려면 어떤 라우팅 프로토콜을 골라야 하는가?

#3동작 예시

두 프로토콜은 경로를 고르는 기준부터 다르다. OSPF는 링크 비용(기본적으로 링크 속도에 반비례하는 값)의 합이 가장 작은 경로를 최단 경로로 고른다. EIGRP는 대역폭과 지연(및 필요 시 신뢰성·부하)을 조합한 메트릭 값을 계산해 그 값이 가장 작은 경로를 고른다. 같은 네트워크에서 두 프로토콜이 서로 다른 경로를 선택하는 경우가 생기는 이유가 바로 이 메트릭 계산 방식의 차이다.

#4동작 과정

  1. 경로 학습 방식 차이OSPF는 전체 네트워크의 링크 상태 정보를 모든 라우터가 공유하고 각자 SPF(최단 경로 우선) 계산을 해 경로를 만든다. EIGRP는 인접 라우터와만 경로 정보를 교환하고 각 라우터가 DUAL 알고리즘으로 최적 경로와 대체 경로를 정한다.
  2. 수렴 특성 차이링크가 끊기면 EIGRP는 미리 계산해 둔 대체 경로(feasible successor)가 있으면 즉시 그쪽으로 바꾼다. OSPF는 링크 상태 변화를 플러딩(모든 라우터에 전파)한 뒤 SPF를 다시 계산해야 하므로 재계산 시간이 걸린다.
  3. 사용 환경 선택OSPF는 벤더와 무관하게 표준으로 쓰이고 대규모 네트워크에서 널리 도입된다. EIGRP는 시스코 환경에서 설정이 간단하고 수렴이 빠르지만 표준이 아니어서 다중 벤더 환경에서는 적용이 어렵다.

#5한 줄 요약

링크 상태를 전체가 공유하고 SPF로 계산하는 OSPF와, 인접 라우터 간 교환과 DUAL 알고리즘으로 대체 경로를 미리 확보하는 EIGRP라는 서로 다른 경로 계산·수렴 방식을 환경에 맞게 선택하는 것

OSPFv2/v3 구성·검증

IPv4용 OSPFv2와 IPv6용 OSPFv3를 구성하고 상태를 검증하는 과정.

#1문제 상황

라우터가 수동으로 경로를 하나씩 입력받는 정적 라우팅은 네트워크가 조금만 커져도 경로가 수십 개로 늘고, 링크가 끊기면 사람이 직접 경로를 바꿔줘야 해서 유지보수가 감당하기 어려워진다. OSPF는 라우터들이 서로 링크 상태를 주고받아 변화에 스스로 대응하게 만드는 다이내믹 라우팅 프로토콜이다. 그런데 IPv4와 IPv6는 주소 체계가 달라서, OSPF도 IPv4용(OSPFv2)과 IPv6용(OSPFv3)으로 나뉘고 구성 방식에도 차이가 있다. OSPFv2는 네트워크 문에 IP 주소를 직접 넣어 광고 범위를 정하지만, OSPFv3는 링크 상태를 알리는 방식이라 구성 문법이 다르다.

#2핵심 질문

IPv4와 IPv6 어느 쪽이든, 라우터들이 링크 상태를 교환해 변화에 스스로 대응하게 하려면 OSPF를 어떻게 구성하고 검증해야 하는가?

#3동작 예시

OSPF의 핵심 동작은 인접 관계를 맺은 라우터끼리 LSA(링크 상태 광고, 자신이 아는 링크 정보를 담은 메시지)를 주고받고, 각 라우터가 모은 링크 상태 데이터베이스로 SPF 계산을 해 라우팅 테이블을 만드는 것이다. 예를 들어 세 라우터가 연쇄로 연결된 네트워크에서 한쪽 링크가 끊기면, 끊긴 라우터가 새 LSA를 보내고 나머지 라우터가 데이터베이스를 갱신한 뒤 SPF를 다시 계산해 새로운 경로로 패킷을 보낸다.

#4동작 과정

  1. OSPF 프로세스 활성화router ospf로 프로세스를 만들고, OSPFv2는 network 문으로 IP 주소가 포함된 인터페이스를 광고에 포함시키며, OSPFv3는 ipv6 router ospf로 프로세스를 만든 뒤 인터페이스에서 ipv6 ospf 명령으로 해당 인터페이스를 프로세스에 참여시킨다.
  2. 인접 관계 형성이웃 라우터가 hello 패킷을 주고받아 인접 관계를 맺고, hello 주기·데드 주기·영역(area) ID가 같아야 관계가 성립한다. 인접 관계가 완성되면 링크 상태 데이터베이스를 동기화한다.
  3. 검증 명령 실행show ip ospf neighbor로 인접 상태가 full인지 확인하고, show ip ospf로 프로세스 상태를, show ip route ospf로 OSPF가 만든 경로가 실제 라우팅 테이블에 들어갔는지 확인한다.

#5한 줄 요약

프로토콜 버전에 맞는 문법으로 OSPF 프로세스를 활성화하고 인접 관계를 맺어 링크 상태를 동기화한 뒤, 그 상태를 검증 명령으로 확인해 네트워크 변화에 스스로 대응하는 라우팅을 만드는 것

eBGP 구성·검증

자율시스템 간 경로 교환에 쓰는 eBGP를 구성하고 검증하는 과정.

#1문제 상황

인터넷은 수많은 자율시스템(AS, 한 조직이 운영하는 네트워크 단위)이 서로 연결된 구조다. AS 내부의 경로는 OSPF나 EIGRP 같은 내부 프로토콜이 처리하지만, 다른 AS로 나가는 경로는 어느 프로토콜도 자동으로 알려주지 않는다. 외부 연결은 정적 경로로 처리할 수도 있지만, 경로가 하나가 아니라 여러 개가 되고 상대 AS의 경로가 바뀌면 정적으로는 따라갈 수 없다. 그래서 AS와 AS 사이의 경로 교환 전용 프로토콜인 BGP가 필요하다. BGP는 경로를 고르는 기준도 속도가 아니라 정책(어느 AS를 거칠지, 어떤 경로를 선호할지)이다.

#2핵심 질문

서로 다른 자율시스템끼리 경로를 주고받고, 정책에 따라 그중 하나를 선택하려면 eBGP를 어떻게 구성해야 하는가?

#3동작 예시

eBGP의 핵심은 인접 라우터와 TCP(포트 179)로 연결을 맺고, 서로가 아는 경로를 NLRI(경로 정보)와 함께 광고하는 것이다. 예를 들어 내 AS가 상대 AS에게 192.0.2.0/24 네트워크를 광고하면, 상대는 그 경로를 받아 자신의 BGP 테이블에 넣고, 그 경로가 최적 경로로 선택되면 라우팅 테이블에 반영해 트래픽을 보낸다.

#4동작 과정

  1. 피어 구성router bgp <AS 번호>로 BGP 프로세스를 만들고 neighbor 명령으로 상대 라우터의 IP와 상대 AS 번호를 지정한다. eBGP는 서로 다른 AS끼리 하므로 각자 상대의 AS 번호를 적는다.
  2. 경로 광고network 명령으로 내 AS가 보유한 네트워크를 BGP에 광고한다. 이때 network 명령의 주소는 라우팅 테이블에 실제로 존재해야 광고된다.
  3. 검증 명령 실행show ip bgp summary로 피어 상태가 established인지 확인하고, show ip bgp로 받은 경로와 최적 경로 선택 상태를, show ip route bgp로 BGP 경로가 라우팅 테이블에 반영됐는지 확인한다.

정책 기반 라우팅(PBR)

라우팅 테이블이 아닌 정책에 따라 패킷의 경로를 결정하는 라우팅 기법.

#1문제 상황

일반적인 라우팅은 라우팅 테이블에 들어 있는 최적 경로를 따라 패킷을 보낸다. 라우팅 테이블의 경로는 목적지 주소 기준으로만 정렬되어 있어서, 목적지가 같으면 어떤 트래픽이든 같은 경로를 탄다. 하지만 실제 운영에서는 목적지가 같아도 출발지가 다르면 다른 경로로 보내야 하는 경우가 있다. 예를 들어 특정 고객망에서 온 트래픽만 전용 회선으로 보내고 나머지는 인터넷 회선으로 보내야 하는 상황은 목적지 주소만으로는 표현할 수 없다. 그래서 목적지가 아닌 트래픽 특성(출발지 주소, 프로토콜, 포트 등)에 따라 경로를 강제로 지정하는 방법이 필요해졌다.

#2핵심 질문

목적지가 같아도 트래픽의 출발지나 종류에 따라 서로 다른 경로로 보내려면 어떻게 해야 하는가?

#3동작 예시

PBR은 라우팅 테이블을 거치지 않고, route-map(일치 조건과 행동을 묶은 설정 블록)이 먼저 패킷을 검사해 경로를 정한다. 예를 들어 "출발지가 10.1.1.0/24인 패킷은 next-hop 192.168.1.1로 보낸다"는 route-map을 인터페이스에 적용하면, 해당 출발지의 패킷은 목적지와 무관하게 전용 경로로 보내진다. 조건에 맞지 않는 패킷은 원래대로 라우팅 테이블을 따라 간다.

#4동작 과정

  1. route-map 정의route-map 이름과 순서 번호를 만들고, match 문으로 일치 조건(출발지·목적지 주소, 프로토콜, 포트 등)을 지정하고 set 문으로 행동(보낼 next-hop, 보낼 인터페이스, DSCP 값 등)을 지정한다.
  2. 인터페이스 적용ip policy route-map <이름> 명령으로 해당 route-map을 패킷이 들어오는 인터페이스에 적용한다. PBR은 인터페이스로 들어오는 패킷부터 검사한다.
  3. 검증 명령 실행show route-map으로 route-map의 일치 카운터가 증가하는지 확인하고, show ip policy로 어떤 인터페이스에 정책이 적용됐는지 확인한다.

#5한 줄 요약

라우팅 테이블 대신 route-map의 일치 조건과 행동으로 패킷의 경로를 결정해, 목적지가 아닌 트래픽 특성에 기반한 경로 제어를 하는 것

무선 Layer 1 개념

무선 신호의 주파수 대역·채널·변조 등 물리 계층의 동작 원리를 다루는 개념.

#1문제 상황

유선 네트워크는 케이블이라는 물리적 매체가 정해져 있어서 신호가 흐르는 길이 고정되어 있고, 신호 간섭도 케이블 차폐로 어느 정도 막을 수 있다. 하지만 무선은 매체가 공기라서 신호가 사방으로 퍼지고, 같은 공간을 쓰는 다른 무선 기기와 전자기기까지 모두 간섭의 대상이 된다. 그래서 무선 네트워크는 물리 계층에서부터 주파수 대역을 나누고 채널을 구분해 신호가 서로 부딪히지 않게 관리해야 한다. 무선 신호는 유선과 달리 거리가 멀어질수록 약해지고, 벽 같은 장애물을 만나면 급격히 감쇠(신호 세기가 줄어듦)한다.

#2핵심 질문

케이블이 없는 공기라는 매체에서, 여러 기기가 동시에 신호를 주고받아도 서로 간섭하지 않게 하려면 물리 계층에서 무엇을 정해야 하는가?

#3동작 예시

무선 물리 계층의 핵심은 주파수 대역과 채널의 구분이다. 예를 들어 2.4GHz 대역은 채널 1, 6, 11처럼 서로 겹치지 않는 채널로 나뉘어 있고, AP(무선 액세스 포인트)는 이 채널 중 하나를 골라 신호를 보낸다. 옆 AP가 같은 채널을 쓰면 신호가 겹쳐 간섭이 생기므로, 인접 AP에는 겹치지 않는 다른 채널을 배정해서 각자 독립된 주파수 공간에서 통신하게 한다. 신호를 실어 보내는 방식은 변조(주파수·위상에 정보를 새기는 방법)로 정해지고, 변조 방식에 따라 한 번에 보내는 데이터 양이 달라진다.

#4동작 과정

  1. 대역과 채널 선택2.4GHz 또는 5GHz(또는 6GHz) 대역을 정하고, 해당 대역 안에서 겹치지 않는 채널을 골라 AP에 배정한다. 채널이 겹치면 같은 주파수 자원을 두 AP가 나눠 쓰게 되어 처리량이 떨어진다.
  2. 신호 송출과 변조AP가 정해진 채널의 주파수로 전파를 송출하고, 데이터를 실을 때 변조 방식을 적용해 주파수·위상에 비트를 새긴다. 신호가 강할수록 더 효율이 높은 변조 방식을 쓸 수 있고, 약해지면 낮은 변조 방식으로 내려간다.
  3. 수신과 재구성클라이언트가 받은 전파에서 변조된 신호를 복조해 데이터를 되살린다. 이 과정에서 수신 신호가 약하거나 간섭이 크면 오류가 생기므로, 신호 품질에 맞춰 변조 방식을 조정하면서 통신을 유지한다.

#5한 줄 요약

#2핵심 질문

동일한 무선 장비 하나를 어떤 모드로, 어떤 안테나와 함께 배치해야 상황에 맞는 무선 커버리지를 만들 수 있을까?

#3동작 예시

사무실 한 층 전체에 무선을 제공하려는 관리자가 있다고 하자. AP(액세스 포인트, 무선 신호를 내보내는 장치)를 로컬 모드로 설정하면 모든 무선 프레임이 CAPWAP 터널(무선 트래픽을 컨트롤러까지 감싸 보내는 경로)을 통해 컨트롤러로 전달되고, 중앙 집중식 정책이 그대로 적용된다. 여기에 실내 전방향 안테나(옴니 안테나)를 장착하면 신호가 360도로 퍼지므로 한 대의 AP로 사무실 중앙 천장 부근에 두고 넓게 서빙하는 구성이 된다. 이렇게 모드가 정책의 적용 지점을 정하고, 안테나가 신호가 퍼지는 모양을 정한다.

#4동작 과정

  1. 모드 선택AP를 로컬 모드(모든 트래픽을 컨트롤러로 보내는 기본 모드)나 플렉스 모드(컨트롤러 연결이 끊겨도 로컬에서 스위칭을 계속하는 모드) 중 하나로 설정한다. 모드에 따라 프레임이 어디서 처리되는지가 달라진다.
  2. 안테나 선정·장착전방향 안테나(옴니, 주변 전체로 퍼짐)와 지향성 안테나(패치·Yagi, 특정 방향으로 집중) 중 커버해야 할 영역에 맞는 것을 고른다.
  3. 배치와 출력 조정AP를 설치하고 전송 출력을 조절해 인접 AP 간 채널 간섭은 줄이면서 목표 영역 전체가 신호로 덮이도록 맞춘다.

AP가 컨트롤러를 발견하고 CAPWAP으로 등록·조인하기까지의 과정.

→ 03-09 참조

#1문제 상황

소규모 무선망에서는 AP 하나하나에 관리자가 직접 가서 IP 주소와 채널, 보안 설정을 입력했다. AP 수가 늘어나면 이런 수동 설정을 반복해야 하고, 설정이 서로 어긋나면 채널 간섭이나 정책 불일치가 발생한다. 중앙 컨트롤러가 모든 AP를 관리하는 구조에서는 AP가 부팅된 뒤 자동으로 컨트롤러를 찾아가 등록하는 절차가 필요하다. 이 절차가 없다면 AP는 아무 컨트롤러에도 연결되지 못하고, 관리망 밖에 떠 있는 상태가 된다.

#2핵심 질문

전원이 켜진 AP가 아무 설정도 받지 않은 상태에서 어떻게 자신을 관리할 컨트롤러를 스스로 찾아 등록할 수 있을까?

#3동작 예시

새 AP 한 대를 사무실에 설치한다고 하자. AP는 부팅 직후 DHCP를 통해 IP 주소를 받고, 그다음 자신이 가진 컨트롤러 후보 목록(로컬 설정, DNS 이름, DHCP 옵션 등으로 알게 된 컨트롤러 주소들)을 순서대로 시도한다. 목록에 있는 컨트롤러 중 응답하는 컨트롤러가 있으면 AP는 CAPWAP 터널(AP와 컨트롤러 사이의 제어·데이터 연결)을 맺고 조인 요청을 보낸다. 컨트롤러가 AP의 인증서와 펌웨어 버전을 확인한 뒤 이미지를 내려주고 설정을 적용하면, AP는 완전한 상태로 무선 서비스를 시작한다.

#4동작 과정

  1. 디스커버리AP가 DHCP로 IP를 받은 뒤, 로컬 저장된 컨트롤러 주소, DNS 조회, DHCP 옵션 순으로 컨트롤러 후보를 찾아간다. 응답한 컨트롤러가 있으면 AP는 그 컨트롤러를 선택한다.
  2. 조인AP가 CAPWAP 제어 터널(설정과 관리를 주고받는 연결)을 맺고 컨트롤러에 조인 요청을 보낸다. 컨트롤러는 장비 인증을 거쳐 펌웨어 버전을 확인한다.
  3. 설정 적용·서비스 시작버전이 다르면 컨트롤러가 AP에 이미지를 내려주고, 이어서 SSID·보안·채널 같은 설정을 전달한다. 설정이 끝난 AP는 데이터 터널을 맺고 무선 서비스를 시작한다.

#5한 줄 요약

무선 클라이언트가 AP를 옮길 때 L2 또는 L3 경계를 넘는 핸드오프 동작.

#1문제 상황

무선 클라이언트(노트북·폰)는 이동하면서 신호가 강한 AP로 연결을 옮긴다. 이때 같은 서브넷 안에 있는 다른 AP로 옮기면 기존 IP 주소를 그대로 쓰므로 통신이 끊기지 않는다. 하지만 서브넷이 다른 AP로 옮기면, 기존 서브넷의 IP 주소로는 새 네트워크에 도달할 수 없어서 클라이언트는 새 IP를 받아야 하고 연결이 끊긴 것처럼 보이는 순간이 생긴다. AP를 옮기는 핸드오프는 무조건 끊김 없이 되는 것이 아니라, L2인지 L3인지에 따라 처리 방식이 완전히 달라진다.

#2핵심 질문

무선 클라이언트가 AP를 옮길 때, 같은 네트워크( L2)와 다른 네트워크(L3) 경계를 넘는 경우 각각 연결을 어떻게 이어줄 수 있을까?

#3동작 예시

건물 1층과 2층에 있는 두 AP가 모두 같은 VLAN과 서브넷을 쓰는 구성이 있다고 하자. 클라이언트가 1층 AP에서 2층 AP로 이동하면, 새 AP로의 재인증과 함께 클라이언트가 쓰던 IP 주소와 연결 정보가 새 AP에 그대로 이어지므로(L2 로밍) 패킷 흐름이 중단되지 않는다. 반대로 2층이 완전히 다른 서브넷이라면, 클라이언트는 기존 IP를 유지한 채 컨트롤러가 만든 캡슐화 터널(무선 프레임을 그대로 감싸 원래 서브넷으로 보내는 경로)을 통해 이전 네트워크로 계속 통신한다. 이것이 L3 로밍의 핵심이다.

#4동작 과정

  1. 로밍 시작클라이언트가 새 AP의 신호로 접속을 옮기며, 새 AP가 클라이언트를 인증하고 기존 세션 정보를 확인한다.
  2. 경로 유지같은 서브넷이면 새 AP가 데이터 경로를 그대로 이어받고(L2 로밍), 다른 서브넷이면 컨트롤러가 터널로 원래 서브넷에 트래픽을 돌려준다(L3 로밍).
  3. 연결 완료클라이언트의 IP와 세션이 유지된 채 새 AP를 통한 통신이 이어지고, 옛 AP는 해당 클라이언트 연결을 정리한다.

#5한 줄 요약

클라이언트가 AP를 옮길 때, L2 로밍은 같은 서브넷 안에서 연결을 그대로 이어주고 L3 로밍은 터널로 원래 서브넷에 트래픽을 돌려줘서 IP가 바뀌는 끊김을 막는 것

#1문제 상황

무선 연결 문제는 유선과 달리 눈으로 확인할 수 있는 단절점이 없다. 클라이언트가 "와이파이에 연결 안 됨"이라고 하면, 원인이 클라이언트의 신호 강도인지, AP와 컨트롤러 사이인지, 인증 서버인지, DHCP인지 알 수 없다. 원인을 짐작하지 않고 임의로 AP를 재부팅하거나 설정을 바꾸면 증상만 일시적으로 사라지고 재발한다. 무선망은 여러 계층(무선 신호, AP, 컨트롤러, 인증, IP 할당)이 이어져 있어서, 각 계층을 순서대로 확인하지 않으면 실제 원인을 찾을 수 없다.

#2핵심 질문

연결·인증·성능 문제가 무선망의 어느 계층에서 발생했는지를 어떻게 체계적으로 좁혀서 찾을 수 있을까?

#3동작 예시

한 직원이 특정 위치에서만 와이파이 연결이 자주 끊긴다고 보고했다고 하자. 먼저 클라이언트 측에서 신호 강도와 채널 사용률을 확인해 그 위치의 무선 신호 품질이 나쁜지 본다. 신호 자체가 좋다면, 클라이언트의 인증 로그에서 인증 서버 응답이 정상인지 확인하고, 인증이 통과됐다면 DHCP로 IP를 받았는지 본다. 이렇게 "신호 → 인증 → IP 할당" 순서로 한 계층씩 검증해 나가면, 문제가 그 위치의 채널 간섭인지 인증 서버인지가 명확해진다.

#4동작 과정

  1. 신호 계층 확인클라이언트 위치의 신호 강도와 채널 간섭, AP 상태를 확인해 무선 전송 자체의 문제를 판별한다.
  2. 인증·연결 확인클라이언트가 AP에 조인하고 인증 서버를 통과했는지 로그로 확인하고, 실패 지점(클라이언트·AP·서버)을 찾는다.
  3. IP·성능 확인DHCP로 IP를 받았는지, 트래픽 속도와 지연이 정상인지 확인해 최종 원인을 확정하고 AP 채널·출력·정책을 조정해 해결한다.

여러 SSID·VLAN·ACL로 무선 트래픽을 분리하는 기법.

#1문제 상황

무선망 하나에 모든 사용자와 기기가 연결되면, 게스트 방문객이 내부 서버에 접근할 수 있고, 사물인터넷 기기와 직원 노트북이 같은 네트워크에 섞여 있어 한 기기가 감염되면 전체가 위험해진다. 유선망에서는 포트 단위로 VLAN(가상 네트워크 구획)과 ACL(접근 제어 목록)을 적용해 트래픽을 분리하지만, 무선에서는 여러 사용자가 같은 AP와 주파수를 공유하므로 이 분리 기준을 무선 단위로 다시 적용해야 한다. 분리 없이 무선망을 운영하면 보안 정책 하나를 바꿀 때마다 모든 사용자가 같은 영향을 받는 문제가 생긴다.

#2핵심 질문

한 대의 AP가 서비스하는 공간에서 사용자 그룹별로 트래픽을 어떻게 서로 다른 네트워크로 분리할 수 있을까?

#3동작 예시

한 사무실 AP에 "직원용", "게스트용", "사물인터넷용" SSID(무선 네트워크 이름) 세 개를 만들었다고 하자. 직원용 SSID는 내부 VLAN 100에 매핑되어 인트라넷 접근이 허용되고, 게스트용 SSID는 VLAN 200에 매핑되어 인터넷만 나가도록 ACL(어떤 트래픽을 허용·차단할지 정한 목록)로 제한된다. 클라이언트가 어떤 SSID로 접속하느냐에 따라 프레임이 해당 VLAN으로 분류되고, VLAN 간 트래픽은 라우팅·방화벽 정책을 거치므로 서로 다른 그룹이 같은 공간에 있어도 통신 경로가 완전히 분리된다.

#4동작 과정

  1. SSID·VLAN 매핑AP에 여러 SSID를 만들고 각 SSID를 서로 다른 VLAN에 연결한다. 클라이언트가 접속한 SSID가 곧 트래픽의 분류 기준이 된다.
  2. 정책 적용VLAN 사이를 지나는 트래픽에 ACL이나 방화벽 규칙을 적용해 게스트는 인터넷만, 직원은 내부망까지 허용하는 식으로 접근 범위를 제한한다.
  3. 트래픽 분리 동작클라이언트의 프레임이 자신의 SSID에 해당하는 VLAN으로 전달되고, 다른 VLAN으로의 접근은 정책에 따라 허용·차단되며 분리가 유지된다.

네트워크 장비의 시간 동기화를 위한 NTP와 PTP의 동작 방식과 차이를 해석하는 주제.

#1문제 상황

네트워크 장비들은 각자 자신의 내부 시계를 갖고 있지만, 장비마다 시계의 오차가 조금씩 다르고 시간이 지나면서 더 벌어진다. 로그와 인증, 보안 인증서 유효성 검사는 시간을 기준으로 동작하므로 장비들 사이의 시각이 어긋나면 사건 발생 순서가 뒤섞이고, 인증서가 "만료"된 것처럼 오판되기도 한다. 관리자가 모든 장비에 수동으로 시간을 맞추는 것도 가능하지만, 수십 대의 장비를 일일이 맞추는 것은 불가능하다. 그래서 장비들이 네트워크를 통해 자동으로 시간을 동기화하는 프로토콜이 필요하다.

#2핵심 질문

수많은 네트워크 장비가 각자 조금씩 다른 시계를 갖고 있을 때, 이들을 어떻게 한 기준 시간으로 맞출 수 있을까?

#3동작 예시

사내 네트워크의 모든 스위치와 라우터가 NTP(네트워크 시간 프로토콜, UDP 포트 123로 시간을 주고받는 표준)를 사용한다고 하자. 상위 계층 장비는 외부의 정확한 시간 서버에서 시간을 받고, 하위 장비들은 그 상위 장비를 시간 서버로 삼아 계층적으로 시간을 받아간다. 장비는 시간을 받으면 즉시 시계를 바꾸지 않고, 받은 시간과 자기 시계의 오차를 계산해 서서히 조정하므로 급격한 시간 점프 없이 일정한 오차 안으로 수렴한다. 반면 PTP(정밀 시간 프로토콜)는 하드웨어 타임스탬프(패킷이 들어오는 순간의 정확한 시각 기록)를 이용해 마이크로초 이하 수준으로 맞춘다.

#4동작 과정

  1. 시간 서버 확인장비가 NTP 서버 주소를 받아 시간 요청 패킷을 보내고, 서버의 시간과 왕복 지연을 바탕으로 현재 기준 시간을 계산한다.
  2. 오차 보정장비가 받은 시간과 자기 시계의 오차를 계산하고, 한 번에 크게 바꾸지 않고 오차가 줄어들도록 시계를 서서히 조정한다.
  3. 주기적 동기화장비가 주기적으로 다시 시간을 요청해 오차를 계속 점검하며, PTP가 필요한 환경에서는 하드웨어 타임스탬프로 더 정밀한 동기화를 유지한다.

#5한 줄 요약

NTP가 계층적 서버 구조와 서서히 조정하는 보정으로 장비 시계를 일정한 오차 안에 맞추고, PTP가 하드웨어 타임스탬프로 더 높은 정밀도를 제공해 시간 동기화 요구 수준에 따라 선택해 해석하는 것

내부 주소를 공인 주소로 변환하는 NAT와 포트 기반 PAT을 구성하는 방법.

#1문제 상황

사내 네트워크의 장비들은 사설 IP 주소(내부에서만 쓰는 주소)를 사용한다. 그런데 인터넷은 공인 IP 주소(전 세계에서 유일한 주소)로만 통신하므로, 사설 주소만으로는 외부와 직접 통신할 수 없다. 모든 내부 장비에 공인 주소를 하나씩 할당하면 주소가 부족해지고 보안상으로도 내부 구조가 그대로 드러난다. 내부 장비가 인터넷에 접속할 때마다 주소를 관리자가 수동으로 매핑해 주는 것도 불가능하다. 그래서 내부 트래픽이 나갈 때 주소를 자동으로 변환하는 장치가 필요하다.

#2핵심 질문

공인 주소가 부족한 상황에서, 사설 주소를 쓰는 수많은 내부 장비가 어떻게 하나의 공인 주소로 인터넷을 사용할 수 있을까?

#3동작 예시

사내 200대의 PC가 라우터 한 대를 통해 인터넷에 접속한다고 하자. 라우터에는 공인 주소가 하나만 있고, 내부 PC들은 각자 다른 사설 주소를 쓴다. PC가 인터넷으로 패킷을 보내면 NAT(네트워크 주소 변환, 주소를 바꿔 전달하는 기능)가 출발지 주소를 그 PC의 사설 주소에서 라우터의 공인 주소로 바꾸고, 어떤 PC의 어떤 포트였는지를 별도 표에 기록해 둔다. 응답 패킷이 돌아오면 그 표를 보고 다시 원래 PC의 사설 주소와 포트로 되돌려 보낸다. 이때 여러 PC가 같은 공인 주소를 공유하므로, 출발지 포트 번호까지 함께 바꿔 구분하는 방식이 PAT(포트 주소 변환)이다.

#4동작 과정

  1. 변환 테이블 등록내부 장비가 외부로 보내는 패킷이 라우터를 지날 때, 출발지 주소·포트와 변환된 공인 주소·포트의 대응을 변환 테이블에 기록한다.
  2. 주소·포트 변환NAT/PAT는 패킷의 출발지 주소(및 포트)를 공인 주소(및 새 포트)로 바꿔 외부로 내보내고, 여러 내부 장비가 하나의 공인 주소와 서로 다른 포트로 구분된다.
  3. 응답 역변환외부에서 돌아온 패킷을 변환 테이블과 대조해 원래 내부 장비의 사설 주소와 포트로 되돌려 보낸다. 테이블 항목은 통신이 끝난 뒤 정리된다.

#5한 줄 요약

NAT가 내부 사설 주소를 공인 주소로 바꿔 외부 통신을 가능하게 하고, PAT이 포트 번호까지 변환해 여러 내부 장비가 하나의 공인 주소를 공유하게 하는 것

FHRP(HSRP·VRRP·GLBP)

게이트웨이 이중화를 제공하는 HSRP·VRRP·GLBP의 동작 방식과 차이.

#1문제 상황

게이트웨이가 하나뿐인 네트워크에서는 호스트가 기본 게이트웨이 주소를 정적으로 설정하고 그 주소로 모든 외부 트래픽을 보낸다. 이 방식은 게이트웨이 장비가 고장나면 호스트가 가진 주소는 그대로인데 그 주소로 응답하는 장비가 사라지므로, 네트워크 전체가 외부로 나가는 길을 잃는다. 호스트가 다른 게이트웨이 주소를 자동으로 배우는 기능이 없기 때문에 관리자가 일일이 호스트 설정을 바꾸기 전까지 통신이 중단된다. 즉 단일 게이트웨이는 장애 시 복구까지 사람의 개입이 필요하다는 명확한 한계가 있다.

#2핵심 질문

호스트의 설정을 바꾸지 않고도 게이트웨이가 죽었을 때 다른 장비가 그 역할을 이어받게 하려면 어떻게 해야 하는가?

#3동작 예시

여러 라우터가 하나의 가상 IP 주소를 공유하고, 호스트는 그 가상 IP를 기본 게이트웨이로 설정한다. 평소에는 그중 한 대(Active)만 가상 IP로 들어온 트래픽을 처리하고 나머지는 대기(Standby)한다. Active 장비가 죽으면 Standby 장비가 가상 IP를 인계받아 호스트가 쓰는 주소는 그대로인 채 게이트웨이 역할만 옮겨간다. 호스트 입장에서는 게이트웨이 주소가 전혀 변하지 않으므로 설정 변경 없이 장애가 흡수된다.

#4동작 과정

  1. 가상 IP 공유라우터 여러 대가 하나의 가상 IP와 가상 MAC 주소를 갖도록 설정하고, 호스트는 그 가상 IP를 기본 게이트웨이로 쓴다.
  2. 활성 장비 선출프로토콜이 우선순위를 비교해 한 대를 Active로, 나머지를 Standby로 정하고, Active만 ARP(주소를 MAC 주소로 변환해 주는 프로토콜) 응답 등 가상 IP에 대한 실제 처리를 담당한다.
  3. 장애 시 인계Active가 Hello 메시지를 보내지 못하면 Standby가 이를 감지하고 가상 IP·가상 MAC을 자신이 갖고 Active로 승격한다. 결과적으로 호스트는 아무 변경 없이 새 게이트웨이와 계속 통신한다. HSRP는 Cisco 전용으로 한 번에 한 대만 활성이고, VRRP는 표준 프로토콜이며, GLBP는 여러 대가 동시에 부하를 분산한다는 차이가 있다.

#5한 줄 요약

여러 라우터가 하나의 가상 게이트웨이 주소를 공유해 호스트 설정 변경 없이 장애를 자동 인계하는 게이트웨이 이중화

멀티캐스트(PIM·IGMP·RPF)

PIM과 IGMP가 멀티캐스트 트래픽을 전달하고 RPF가 루프를 막는 원리.

#1문제 상황

유니캐스트는 송신자가 수신자마다 패킷을 하나씩 따로 보내고, 브로드캐스트는 송신자가 모든 호스트에 패킷을 보낸다. 유니캐스트는 같은 내용을 많은 수신자에게 보낼 때 같은 패킷을 수신자 수만큼 복제해 보내므로 링크 대역폭과 송신자 부하가 수신자 수에 비례해 커진다. 브로드캐스트는 관심 없는 호스트까지 모두 받게 되어 불필요한 트래픽이 네트워크 전체로 퍼진다. 즉 "여러 수신자에게 같은 데이터를 보내되, 원하는 호스트에게만 효율적으로 보내는" 방법이 기존 방식에는 없었다.

#2핵심 질문

같은 데이터를 여러 수신자에게 보내면서도 각 링크에 중복 없이 한 번만, 원하는 호스트에게만 전달하려면 어떻게 해야 하는가?

#3동작 예시

수신자가 방송(IPTV)을 보고 싶다고 그룹에 가입하면, 라우터들이 그 그룹을 향하는 트리(나무 형태의 전달 경로)를 만들고 송신자는 패킷을 한 번만 보낸다. 중간 라우터는 트리 분기점에서 패킷을 복제해 여러 갈래로 보낸다. 이때 RPF(역경로 확인)라는 검사로 패킷이 진짜 송신자 쪽 인터페이스에서 들어왔는지 확인해, 그렇지 않은 패킷은 버림으로써 루프(패킷이 빙빙 도는 현상)를 막는다.

#4동작 과정

  1. 그룹 가입수신자 호스트가 IGMP(가입 여부를 알리는 프로토콜)로 라우터에게 "나는 이 멀티캐스트 그룹을 받겠다"고 알리고, 라우터는 가입한 인터페이스를 기록한다.
  2. 트리 구성·전달라우터가 PIM(멀티캐스트 전달 경로를 만드는 프로토콜)으로 송신자에서 가입자까지의 트리를 만들고, 송신자가 보낸 패킷을 트리를 따라 복제·전달한다.
  3. RPF 검사각 라우터는 패킷이 유니캐스트 라우팅 테이블상 송신자로 가는 정상 경로의 인터페이스에서 들어왔는지 확인해, 엉뚱한 인터페이스에서 들어온 패킷은 버려 루프를 차단한다. 결과적으로 각 링크에는 같은 패킷이 한 번만 지나간다.

QoS 트러블슈팅

분류·마킹·큐잉·폴리싱 등 QoS 정책 적용상의 문제를 진단하고 해결하는 과정.

#1문제 상황

QoS 없이 모든 트래픽을 같은 대우로 보내면 링크가 혼잡해질 때 선입선출 방식으로 패킷이 쌓이고, 음성·화상 같은 지연에 민감한 트래픽이 대용량 파일 전송과 같은 큐에서 뒤로 밀려 품질이 떨어진다. 그래서 장비에 분류·마킹·큐잉·폴리싱 등 QoS 정책을 적용하는데, 정책이 의도대로 동작하지 않으면 음성 품질 저하, 특정 트래픽만 느려짐, 정책 미적용 등 증상이 나타난다. 문제는 정책이 여러 장비에 단계적으로 걸쳐 있어서 어느 단계에서 잘못됐는지 한눈에 보이지 않는다는 점이다.

#2핵심 질문

QoS 정책이 설정대로 동작하지 않을 때, 어느 장비의 어느 단계에서 트래픽 처리가 어긋났는지를 어떻게 찾아낼 수 있는가?

#3동작 예시

트래픽이 들어오는 인터페이스부터 나가는 인터페이스까지 QoS 파이프라인(분류 → 마킹 → 큐잉 → 스케줄링)을 순서대로 따라가며 각 단계의 카운터를 확인한다. 예를 들어 분류 단계의 카운터는 0인데 마킹 단계 카운터는 늘어난다면, 트래픽이 분류 기준에 매칭되지 않고 기본 클래스로 빠지고 있다는 사실이 드러난다. 이렇게 단계별 통계를 하나씩 대조하면 정책이 실제로 적용된 지점을 특정할 수 있다.

#4동작 과정

  1. 정책 적용 위치 확인show 명령으로 각 인터페이스에 정책이 적용됐는지와 적용 방향(입력/출력)을 확인한다. 인터페이스에 정책이 없으면 이후 단계는 전부 의미가 없다.
  2. 단계별 통계 대조분류·마킹·폴리싱·큐잉 각 단계의 매칭 카운터와 폴리싱에서 버려진 패킷 수를 확인해, 예상 트래픽 양과 실제 통계가 어긋난 단계를 찾는다.
  3. 큐와 스케줄링 확인출력 큐의 깊이와 드롭 카운터를 보고 어떤 클래스가 버려지고 있는지 확인해, 대역폭 할당이나 큐 가중치 설정 문제를 수정한다. 결과적으로 설계된 QoS 의도와 실제 처리 사이의 불일치 지점이 드러나고 수정 대상이 정해진다.

4네트워크 어슈어런스 (Network Assurance)04-01

네트워크 문제 진단 도구

ping, traceroute, telnet, SSH 등으로 연결성과 경로 상태를 확인해 네트워크 문제를 국소화하는 명령 도구 모음.

#1문제 상황

장애가 나면 관리자는 화면에 보이는 증상(인터넷 안 됨, 특정 서버 접속 불가)만 알고, 네트워크가 여러 구간(호스트, 스위치, 라우터, 서버)으로 나뉘어 있어 어느 구간이 문제인지 알 수 없다. 아무 정보 없이 장비 설정을 하나씩 뒤지면 시간이 오래 걸리고 원인을 놓치기 쉽다. 즉 장애의 위치(국소화)와 원인을 빠르게 좁히는 방법이 없으면 문제 해결이 운에 맡겨진다.

#2핵심 질문

네트워크 장애가 났을 때, 전체 구간 중 어디서부터 어디까지가 정상이고 어디서 끊겼는지를 가장 빠르게 좁히려면 어떻게 해야 하는가?

#3동작 예시

출발 호스트에서 목적지 서버까지 ping(ICMP 패킷을 보내 응답을 확인하는 도구)과 traceroute(경유하는 라우터를 홉 단위로 표시하는 도구)를 순서대로 실행한다. ping이 성공하면 IP 연결 자체는 살아있는 것이고, 특정 지점까지만 응답이 오는 traceroute 결과를 보면 끊긴 구간이 "응답한 마지막 라우터와 응답하지 않은 다음 라우터 사이"라는 구간 단위로 좁혀진다. 마지막으로 그 구간의 장비에 SSH(암호화된 원격 접속)나 telnet(원격 터미널 접속)으로 들어가 인터페이스 상태와 설정을 확인한다.

#4동작 과정

  1. 연결성 검사출발지에서 목적지 IP로 ping을 보내 응답 유무로 IP 연결 자체의 정상 여부를 판단한다.
  2. 경로 추적traceroute로 패킷이 지나는 각 라우터의 응답을 홉마다 확인해, 응답이 끊긴 지점으로 문제 구간을 좁힌다.
  3. 장비 확인문제 구간 장비에 SSH/telnet으로 접속해 인터페이스 상태(up/down), 라우팅 테이블, 트래픽 카운터를 확인해 원인을 확인한다. 결과적으로 문제가 물리 링크인지, 라우팅인지, 필터링인지가 구분된다.

syslog 원격 로깅

장비가 생성한 시스템 로그 메시지를 원격 로그 서버로 전송해 중앙에서 보관·분석하게 하는 로깅 방식.

#1문제 상황

장비는 부팅, 인터페이스 상태 변화, 인증 실패, 설정 변경 등의 사건이 발생할 때마다 시스템 로그 메시지를 생성한다. 이 로그를 장비 내부 버퍼에만 쌓아 두면, 재부팅하면 사라지고, 여러 장비의 로그를 한곳에서 비교할 수 없으며, 장애가 났을 때 그 장비에 직접 접속해야만 확인할 수 있다. 장비가 수십 대인 환경에서는 사건 발생 시점과 장비 간 인과 관계를 파악하기 어렵다는 명확한 한계가 있다.

#2핵심 질문

여러 장비가 생성하는 시스템 로그를 장비가 죽거나 재부팅되어도 잃지 않고 한곳에서 모아 보려면 어떻게 해야 하는가?

#3동작 예시

각 장비가 syslog 프로토콜로 로그 메시지를 UDP 포트 514를 통해 중앙 로그 서버로 보내고, 로그 서버는 장비별·심각도별로 파일에 저장한다. 장비 설정에서 "어떤 심각도 이상의 로그를 어느 서버로 보낼지"만 지정하면, 이후 발생하는 모든 사건이 실시간으로 중앙 서버에 쌓인다. 시간 동기화(NTP)가 되어 있으면 여러 장비의 로그를 같은 시각축 위에서 순서대로 재구성할 수 있다.

#4동작 과정

  1. 대상 설정각 장비에 로깅 서버의 IP 주소와 보낼 로그의 최소 심각도(예: informational 이상)를 지정한다.
  2. 메시지 전송장비에서 사건이 발생하면 심각도·시각(타임스탬프)·장비명이 붙은 로그 메시지를 syslog 프로토콜로 로그 서버에 보낸다.
  3. 중앙 보관·분석로그 서버가 장비별 파일에 메시지를 저장하고, 관리자는 한 화면에서 여러 장비의 로그를 시간순으로 조회해 장애 전후 상황을 재구성한다. 결과적으로 장비가 죽어도 로그는 서버에 남아 원인 분석이 가능하다.

#5한 줄 요약

각 장비의 시스템 로그 메시지를 실시간으로 중앙 로그 서버에 전송해, 장비 생존 여부와 관계없이 여러 장비의 사건을 한곳에서 시각축 기준으로 보관·분석하는 것

Flexible NetFlow

플로우 레코드·캐시·모니터를 자유롭게 조합해 트래픽을 측정·분석하는 유연한 NetFlow 구현 방식.

#1문제 상황

기존 NetFlow는 "어떤 필드를 기준으로 트래픽을 묶어서 셀 것인지"가 장비 제조사에 의해 고정되어 있어서, 관리자가 원하는 측정 기준(예: 특정 애플리케이션 포트, 특정 주소 조합)으로 유연하게 바꿀 수 없었다. 측정 항목을 바꾸려면 다른 버전이나 다른 장비를 써야 하고, 원하는 정보가 기본 필드에 없으면 아예 측정할 수 없는 경우도 있었다. 즉 트래픽 분석 요구가 다양해지는 환경에서 고정된 필드 구조가 큰 제약이었다.

#2핵심 질문

측정하고 싶은 트래픽의 기준 필드와 저장할 정보를 관리자가 직접 골라 정의하려면 어떻게 해야 하는가?

#3동작 예시

관리자가 플로우 레코드(flow record)에서 "출발 IP, 목적 IP, 목적 포트"를 측정 기준으로, "바이트 수, 패킷 수, 시각"을 저장 필드로 정의하고, 이 레코드를 캐시(트래픽을 임시로 모아 세는 메모리 공간)에 연결하고, 캐시에 쌓인 결과를 내보낼 모니터(flow monitor)를 인터페이스에 적용한다. 이 세 요소(레코드·캐시·모니터)를 조합하면 같은 장비에서 분석 목적별로 서로 다른 기준의 측정을 동시에 운영할 수 있다.

#4동작 과정

  1. 레코드 정의flow record로 매칭 기준 필드(어떤 값이 같으면 같은 플로우로 볼지)와 수집 필드(무엇을 셀지)를 정의한다.
  2. 캐시·모니터 구성정의한 레코드를 캐시에 연결하고, 유효 시간과 만료 조건을 정한 뒤 flow monitor로 묶는다.
  3. 적용·수출flow monitor를 인터페이스에 적용해 트래픽을 실시간으로 측정하고, 캐시가 차거나 일정 시간이 지나면 플로우 기록을 NetFlow 수집기(export)로 보낸다. 결과적으로 관리자가 정의한 기준 대로 트래픽 통계가 수집된다.

#5한 줄 요약

플로우 레코드·캐시·모니터를 관리자가 자유롭게 조합해, 측정 기준과 저장 필드를 직접 정의하고 인터페이스에 적용해 트래픽을 분석하는 유연한 NetFlow 구현 방식

SPAN/RSPAN/ERSPAN

스위치 포트나 VLAN의 트래픽을 복제해 다른 포트로 보내는 포트 미러링 기술로, RSPAN은 원격 VLAN으로, ERSPAN은 IP 네트워크를 통해 전송한다.

#1문제 상황

장애 분석이나 보안 감시를 위해 어떤 포트에 오가는 트래픽의 실제 내용을 봐야 할 때, 스위치는 기본적으로 목적지가 아닌 포트에는 프레임을 보내지 않으므로 탭(패킷을 복제하는 별도 하드웨어)을 물리적으로 꽂거나 장비에 직접 붙어 있어야만 트래픽을 볼 수 있었다. 감시 장비가 대상 포트와 같은 스위치에 없으면 케이블을 다시 깔아야 하고, 감시 대상이 여러 층·여러 건물에 퍼져 있으면 물리적 회선만으로는 한곳에서 전부 볼 수 없는 한계가 있다.

#2핵심 질문

스위치의 특정 포트나 VLAN 트래픽을, 그 스위치에 물리적으로 붙어 있지 않은 감시 장비까지도 복제해 보내려면 어떻게 해야 하는가?

#3동작 예시

스위치가 대상 포트의 트래픽을 복제해 감시 장비가 연결된 다른 포트로 보내는 것이 SPAN(포트 미러링)이다. 감시 장비가 다른 스위치에 있을 때는 그 스위치의 특정 VLAN을 감시 VLAN으로 지정하고, 출발 스위치가 복제본을 그 VLAN으로 태그를 붙여 보내면 중간 스위치들이 감시 VLAN으로 받아 목적 스위치에서 감시 포트로 내보내는 것이 RSPAN이다. 더 멀리 떨어져 있어 라우팅이 필요하면 복제본을 IP 패킷에 캡슐화(그대로 싸서)해 보내는 ERSPAN을 쓴다.

#4동작 과정

  1. 복제 설정SPAN은 출발 스위치에서 감시 대상(포트 또는 VLAN)과 목적지 포트를 지정하면, 대상 포트를 지나는 프레임이 복제되어 목적지 포트로 나간다.
  2. 원격 전달감시 장비가 다른 스위치에 있으면 RSPAN으로 복제 트래픽을 전용 감시 VLAN에 실어 스위치 간에 전달하고, 라우팅을 넘어야 하면 ERSPAN으로 IP 패킷 안에 캡슐화해 보낸다.
  3. 감시 장비 수신목적 스위치가 복제 트래픽을 감시 포트로 내보내고, 감시 장비(패킷 분석기)가 실제 트래픽과 동일한 내용을 분석한다. 결과적으로 감시 장비 위치와 무관하게 대상 트래픽 내용을 한곳에서 볼 수 있다.

#5한 줄 요약

#2핵심 질문

장애가 발생하기 전에, 그리고 관리자가 직접 명령을 내리지 않아도 네트워크 성능 변화를 계속 측정해 둘 수는 없을까?

#3동작 예시

#4동작 과정

  1. 테스트 정의관리자가 IP SLA 작업 하나를 만들어 측정 대상(예: 10.1.1.1 서버), 측정 항목(지연·지터·패킷 손실), 측정 주기(예: 30초)를 지정한다.
  2. 주기적 측정라우터가 정해진 주기마다 테스트 트래픽을 생성해 대상으로 보내고, 응답 시간과 도착 여부를 측정해 결과를 저장한다.
  3. 결과 활용라우터가 저장된 수치를 임계값(예: 지연 200ms 초과)과 비교해 초과 시 로그·SNMP 트랩으로 관리 시스템에 알리고, 필요하면 통계를 그래프로 뽑는다.

네트워크 설계·프로비저닝·정책·보증·자동화를 하나의 컨트롤러에서 수행하는 Cisco DNA Center의 통합 운영 절차.

#1문제 상황

기존에는 네트워크 장비 한 대를 구성할 때마다 관리자가 SSH나 콘솔로 직접 접속해 CLI(Command Line Interface, 명령 줄) 명령을 일일이 입력했다. 새 사이트를 추가하면 스위치·라우터별로 IP 설정, VLAN(가상 LAN) 구성, 보안 정책을 장비마다 반복해서 넣어야 했고, 이후 상태 확인도 장비마다 따로 접속해 점검해야 했다. 이 방식은 장비 수가 늘수록 작업량이 선형으로 늘고, 장비마다 설정이 조금씩 달라져 일관성을 유지하기 어렵다는 한계가 있다.

#2핵심 질문

#3동작 예시

기존에는 장비 접근 인증과 권한을 라우터·스위치마다 각자 로컬에 사용자명과 비밀번호로 저장하고 관리했다. 장비가 많아지면 장비마다 사용자 계정을 따로 만들고, 누가 어떤 명령을 쓸 수 있는지도 장비별로 설정해야 했다. 한 직원이 퇴사해도 모든 장비에서 계정을 일일이 지워야 했고, 누가 언제 어떤 명령을 실행했는지는 기록이 남지 않아 관리가 어렵다는 한계가 있다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 인증(Authentication)사용자가 장비에 접속을 시도하면 장비가 사용자명·비밀번호를 중앙 AAA 서버로 보내 신원 확인을 요청한다.

Control Plane Policing — CPU로 향하는 제어 플레인 트래픽에 정책을 적용해 과도한 트래픽으로부터 장비를 보호하는 기능.

#1문제 상황

라우터·스위치는 데이터 트래픽을 전달하는 일과 별개로, 라우팅 업데이트·ARP 요청·SSH 접속 같은 제어 트래픽을 처리하기 위해 CPU를 사용한다. 기존에는 이 제어 트래픽에 별다른 제한이 없어서, 공격자가 장비의 CPU가 처리해야 하는 요청(예: 대량의 ARP 요청이나 관리 접속 시도)을 폭주시키면 장비의 CPU가 고갈되어 라우팅 처리나 정상 트래픽 전달까지 마비될 수 있다는 명확한 문제점이 있다.

#2핵심 질문

CPU가 감당해야 하는 제어 트래픽이 폭주해도 장비가 정상 동작을 유지하려면 어떻게 해야 할까?

#3동작 예시

CoPP(Control Plane Policing)는 "CPU로 가는 트래픽"을 별도의 큐로 모아 보고, 그 큐에 허용량을 정해 두는 것이 실제 동작 방식이다. 예를 들어 "초당 100개까지만 라우팅 업데이트를 처리하고 초과분은 버린다"는 정책을 걸어 두면, 공격 트래픽이 몰려와도 CPU가 일정량 이상은 처리하지 않으므로 정상 제어 트래픽 처리가 보호된다.

#4동작 과정

  1. 정책 정의관리자가 제어 플레인(CPU가 처리하는 트래픽 경로)에 들어오는 트래픽 종류별(라우팅 프로토콜, SSH, ICMP 등) 허용/거부 규칙과 전송 속도 제한을 정한다.
  2. 분류와 제한장비가 CPU로 향하는 트래픽을 정책 규칙에 따라 분류하고, 정해진 속도(rate)를 넘는 트래픽은 폐기한다.
  3. 보호 실행제한 안의 정상 트래픽만 CPU에 전달되어 라우팅·관리 기능이 계속 동작하고, 과도한 트래픽은 CPU에 도달하기 전에 버려진다.

#1문제 상황

전통적인 네트워크 보안은 IP 주소와 VLAN 같은 네트워크 위치를 기준으로 접근을 통제했다. 방화벽은 "어느 IP 대역에서 오는 트래픽을 허용할지"를 보고 결정했고, 같은 VLAN 안에 있는 단말은 위치가 같다는 이유로 서로를 신뢰했다. 이 방식은 사용자가 다른 서브넷으로 옮겨 가면 정책이 따라가지 못하고, 내부에서 이동하며 공격하는 위협이나 도청을 막지 못하는 명확한 한계가 있었다. 링크를 지나는 데이터는 암호화되지 않은 채 이동했고, 네트워크에 물리적으로 연결되는 순간 아무 검증 없이 내부 자원에 접근할 수 있었다.

#2핵심 질문

신뢰를 "네트워크의 어느 위치에 있느냐"가 아니라 "누구이며 어떤 자격을 가졌느냐"를 기준으로 판단하려면 어떻게 해야 할까?

#3동작 예시

TrustSec 에서는 사용자나 장비에 SGT(Security Group Tag, 보안 그룹 태그)라는 숫자 꼬리표를 붙이고, 스위치가 이 꼬리표를 보고 통과를 결정한다. 같은 스위치에 연결된 두 단말이라도 SGT 가 서로 다르면 그 사이의 통신이 차단될 수 있고, 반대로 서로 멀리 떨어진 단말이라도 같은 SGT 를 가지면 동일한 정책이 적용된다. 정책 판단의 기준이 IP 주소에서 그룹 멤버십으로 바뀌는 것이 이 기술 묶음의 핵심이다.

#4동작 과정

  1. 신원 확인과 태그 부여단말이 네트워크에 접속하면 인증(802.1X 등)을 거쳐 어떤 보안 그룹(예: 직원, 임원, 게스트)에 속하는지 결정되고, 그에 맞는 SGT 가 트래픽에 붙는다.
  2. MACsec 으로 링크 보호인접한 두 장비 사이의 물리 링크를 MACsec(링크 계층 암호화)으로 암호화해, 중간에서 패킷을 도청하거나 변조하는 것을 막는다.
  3. NAC 로 접속 시점 통제NAC(네트워크 접근 제어)가 접속 전에 단말의 자격과 상태(백신, OS 패치 등)를 검사하고, 기준을 통과하지 못하면 네트워크 사용을 제한하거나 격리한다.

기존에는 장비 한 대를 바꾸려면 관리자가 그 장비에 직접 접속해 CLI 로 설정을 바꿨다. 네트워크 전체의 정책을 바꾸거나 수백 대 장비의 상태를 한눈에 보려면 장비를 하나씩 돌며 확인해야 했다. 장비를 개별적으로 다루는 방식은 규모가 커질수록 작업량이 늘고, 전체 네트워크의 일관성을 유지하기 어렵다는 명확한 한계가 있었다.

#2핵심 질문

수백 대의 장비를 개별 접속 없이 한곳에서 프로그래밍 방식으로 관리하려면 어떤 인터페이스가 필요할까?

#3동작 예시

Cisco DNA Center 는 네트워크 전체 장비를 하나의 제어 지점으로 묶고, REST API 를 통해 "이 어플라이언스에 이 정책을 적용하라"는 요청을 보내면 중앙 컨트롤러가 해당하는 장비들에 설정을 내려 보낸다. 관리자는 장비 IP 를 몰라도 원하는 결과만 API 로 주문하면 되고, vManage 도 SD-WAN 환경에서 같은 방식으로 브랜치 장비들을 관리한다.

#4동작 과정

  1. 요청 작성관리자가 HTTP 요청(예: 특정 사이트에 새 네트워크 프로필 생성)을 REST API 엔드포인트(기능별 주소)에 보낸다.
  2. 중앙 컨트롤러가 중개DNA Center 나 vManage 가 요청을 해석해 관련 장비 목록을 결정하고, 각 장비가 이해하는 설정 형태로 변환해 전달한다.
  3. 장비 반영과 응답장비들이 설정을 적용하고 결과를 중앙으로 보고하면, API 응답으로 전체 결과가 프로그래머에게 돌아온다.

#5한 줄 요약

DNA Center 와 vManage 가 제공하는 REST API 를 통해 장비를 개별 접속하지 않고도 네트워크 전체를 중앙에서 프로그래밍 방식으로 구성하고 관리하는 것

6자동화 (Automation)06-05

6단계 자동화 (Automation)

HTTP 응답의 상태 코드(2xx 성공, 4xx 클라이언트 오류, 5xx 서버 오류 등)를 보고 API 요청 결과를 판별하는 방법.

#1문제 상황

기존에는 API 에 요청을 보낸 뒤 성공 여부를 응답 본문 안의 메시지를 사람이 읽어 판단했다. 요청이 실패해도 장비가 응답을 아예 주지 않거나, 각 제조사가 다른 표현으로 오류를 돌려주면 결과 판별이 일관되지 않았다. 프로그램은 "이 요청이 실제로 성공했는지"를 신속하고 표준적으로 알 수단이 필요한 상황이었다.

#2핵심 질문

API 요청이 성공했는지 실패했는지를 요청마다 표준화된 방법으로 즉시 판별하려면 어떻게 해야 할까?

#3동작 예시

HTTP 응답은 세 자리 상태 코드를 항상 함께 돌려준다. 이 코드만 보고 판단하면 되는데, 200 시리즈(2xx)는 성공, 400 시리즈(4xx)는 잘못된 요청(클라이언트 문제), 500 시리즈(5xx)는 서버 문제를 뜻한다. 예를 들어 요청을 보냈는데 200 OK 가 오면 설정이 적용된 것이고, 404 Not Found 가 오면 요청한 경로가 틀렸다는 뜻이다.

#4동작 과정

  1. 응답 수신API 호출 결과로 상태 코드와 응답 본문이 함께 돌아온다.
  2. 코드 분류2xx(성공), 4xx(클라이언트 오류: 요청 형식·인증·경로 문제), 5xx(서버 오류: 장비 내부 문제)로 결과를 나눈다.
  3. 분기에 따른 처리프로그램이 코드 계열에 따라 성공 시 다음 작업을 진행하고, 오류 시 에러 로그를 남기거나 재시도·중단을 결정한다.

#5한 줄 요약

HTTP 상태 코드의 계열(2xx 성공, 4xx 클라이언트 오류, 5xx 서버 오류)을 보고 API 요청 결과를 표준적으로 판별해 다음 동작을 결정하는 것

6자동화 (Automation)06-06

6단계 자동화 (Automation)

장비에서 특정 이벤트(시스템 메시지, CLI 명령, 카운터 임계값 등)가 발생하면 미리 정의된 동작을 자동 실행하게 하는 Cisco IOS 내장 자동화 기능.

#1문제 상황

기존에는 네트워크에서 문제가 생기면 관리자가 로그를 보고 나서야 알아차리고, CLI 에 접속해 수동으로 명령을 내려 대응했다. 인터페이스가 다운되는 순간부터 사람이 개입하기까지 시간이 걸리므로 그 사이 장애가 커질 수 있었고, 각 장비에 사람이 상주할 수 없어 "어떤 이벤트가 났을 때 즉시 어떤 동작을 하라"는 반응을 장비 스스로 하게 만드는 수단이 부족한 한계가 있었다.

#2핵심 질문

사람이 개입하기 전에 장비가 특정 사건을 감지하고 미리 정해진 동작을 스스로 실행하게 하려면 어떻게 해야 할까?

#3동작 예시

EEM(Embedded Event Manager) 애플릿은 "이벤트(언제)"와 "동작(무엇을)"을 묶은 작은 프로그램이다. 예를 들어 인터페이스가 다운되는 이벤트(syslog 메시지 발생)를 감지하면 미리 등록해 둔 CLI 명령이나 Python 스크립트를 장비가 즉시 실행한다. 사람이 로그를 보고 접속하기 전에 이미 대응이 시작되는 방식이다.

#4동작 과정

  1. 이벤트 등록장비에서 추적할 조건(시스템 로그 메시지, CLI 명령 입력, 카운터 임계값 초과 등)을 애플릿의 이벤트로 정의한다.
  2. 감지장비가 동작 중 해당 조건이 발생하면 EEM 엔진이 이를 감지하고 애플릿을 활성화한다.
  3. 자동 실행애플릿에 등록된 동작(명령 실행, 스크립트 호출, 메시지 발송 등)이 장비 내부에서 즉시 수행되어 문제 대응이 끝난다.

#5한 줄 요약

장비 내부에서 특정 이벤트 발생을 자율 감지해 미리 정의된 동작을 사람의 개입 없이 즉시 실행하게 하는 Cisco IOS 내장 자동화 기능

6자동화 (Automation)06-07

6단계 자동화 (Automation)

여러 네트워크 장비·서비스의 배포와 운영을 자동화하는 도구(Ansible, Puppet, Chef 등)들의 동작 방식과 용도를 비교하는 내용.

#1문제 상황

네트워크를 운영할 때 장비 한 대를 설정하려면 관리자가 해당 장비에 직접 접속해 CLI(명령줄 인터페이스)로 명령을 하나씩 입력했다. 장비가 몇 대 안 되면 이 방식으로도 감당할 수 있지만, 수십~수백 대의 스위치와 라우터를 같은 설정으로 배포하거나 전체 구성을 일괄 변경해야 하는 순간 문제가 생긴다. 사람이 장비마다 직접 명령을 입력하는 방식은 시간이 오래 걸리고, 장비마다 명령을 빠뜨리거나 다르게 입력하는 실수가 나오며, 어떤 장비에 어떤 설정이 들어갔는지 기록이 남지 않아 나중에 문제가 생겼을 때 원인을 찾기 어렵다. 이 한계 때문에 여러 장비를 한 번에, 반복 가능한 방식으로 다루는 자동화 도구가 필요해졌다.

#2핵심 질문

수백 대의 네트워크 장비를 사람이 일일이 건드리지 않고도 동일한 설정으로 배포하고 운영할 수는 없을까?

#3동작 예시

Ansible이 동작하는 방식을 보면 오케스트레이션 도구의 핵심이 바로 보인다. 관리자는 "이 스위치들에 이 VLAN을 만들고 이 IP를 할당하라"는 내용을 YAML(들여쓰기로 구조를 표현하는 텍스트 형식)로 작성한 플레이북(실행할 작업 목록 파일)에 적어 둔다. 그러면 Ansible 컨트롤 노드(중앙에서 명령을 내리는 관리 장비)가 SSH(장비에 안전하게 원격 접속하는 프로토콜)로 대상 장비에 접속해 플레이북의 내용을 그대로 실행한다. 장비에 별도 에이전트 프로그램을 설치할 필요가 없고, 같은 플레이북을 다시 실행하면 항상 같은 결과가 나오므로 수백 대를 대상으로 해도 설정 내용과 결과가 동일하다.

#4동작 과정

  1. 설정 작성관리자가 플레이북에 원하는 최종 상태(어떤 VLAN, 어떤 IP, 어떤 라우팅 설정)를 선언적으로 적는다. 대상 장비 목록도 인벤토리(관리할 장비들을 모아 둔 목록)에 함께 기록한다.
  2. 자동화 도구가 장비에 접속해 실행Ansible 같은 도구가 컨트롤 노드에서 대상 장비마다 SSH로 접속해 플레이북의 작업을 순서대로 적용한다. 장비가 많아도 같은 작업이 병렬로 진행되므로 전체 시간이 짧아진다.
  3. 결과 확인과 재실행각 장비에서 작업이 성공했는지 실패했는지가 결과로 수집되어 관리자에게 보고된다. 설정을 바꾸고 싶으면 플레이북만 고쳐 다시 실행하면 되고, 이미 원하는 상태인 장비는 건너뛰므로 반복 실행해도 안전하다.

#5한 줄 요약

네트워크 장비 배포와 운영을 사람의 수동 명령이 아니라, 한 번 작성한 재사용 가능한 설정 정의로 자동 수행하고 그 결과를 일관되게 만드는 것
