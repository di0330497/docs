#1문제 상황

HTTP는 평문으로 데이터를 보낸다. 브라우저에서 웹서버로 요청을 보낼 때, 중간에 네트워크 경로상의 누구나 그 내용을 볼 수 있다. 개인정보, 비밀번호, 신용카드 번호 같은 민감한 데이터가 노출될 수 있다.

#2핵심 질문

웹 통신에서 중간에 누군가 데이터를 훔쳐보거나 변조하지 못하게 하려면 어떻게 해야 할까?

#3동작 예시

HTTPS는 HTTP 통신을 TLS(Transport Layer Security)라는 암호화 프로토콜로 감싸는 방식이다. 브라우저와 서버가 먼저 TLS 핸드셰이크를 통해 암호화 키를 공유한 다음, 그 키로 이후의 모든 데이터를 암호화해서 주고받는다. 중간에 누군가 패킷을 가로채도 그것은 암호화된 바이트 값일 뿐 원래 내용을 알 수 없다.

#4동작 과정

  1. TLS 핸드셰이크브라우저와 서버가 어떤 암호화 방식을 쓸지 협상하고, 서로 키를 교환해 양쪽이 같은 암호화 키를 갖도록 만든다.
  2. 암호화이후 브라우저와 서버가 주고받는 모든 데이터(요청, 응답, 헤더, 본문)는 그 키로 암호화되어 전송된다.
  3. 복호화받는 쪽이 암호화된 데이터를 받으면 같은 키로 복호화해 원래 평문을 읽는다.

비대칭 키와 X.509 SSL/TLS 서버 인증서

공개키와 개인키 한 쌍을 쓰는 비대칭 암호에서, 공개키와 도메인 정보를 담아 CA가 서명한 표준 파일이 X.509 SSL/TLS 서버 인증서다.

#1문제 상황

대칭 암호(한 개의 키로 암호화와 복호화 모두 함)를 쓰려면 통신 시작 전에 양쪽이 미리 같은 키를 나눠가져야 한다. 하지만 인터넷에서는 처음 만나는 낯선 서버와 안전하게 키를 주고받기가 어렵다. 서버는 수백만 개의 클라이언트와 통신해야 하는데, 각각과 미리 키를 교환할 수 없다.

#2핵심 질문

낯선 서버와 만날 때, 처음 통신부터 안전하게 암호화 키를 주고받으려면 어떻게 해야 할까?

#3동작 예시

비대칭 암호는 공개키와 개인키 한 쌍을 쓴다. 공개키는 누구나 알아도 되고(공개키로 암호화한 데이터는 개인키로만 복호화 가능), 개인키는 서버만 보관한다. 클라이언트는 서버의 공개키를 미리 알고 있으므로(또는 처음 연결할 때 서버로부터 받음), 서버와 암호화된 통신을 시작할 수 있다. 이것이 TLS 핸드셰이크의 기초다.

#4동작 과정

  1. 공개키 배포서버가 자신의 공개키를 X.509 SSL/TLS 서버 인증서 안에 담아 클라이언트에게 제시한다. 이 인증서는 인증 기관(CA)이 서명했으므로 신뢰할 수 있다.
  2. 공개키로 암호화클라이언트가 서버의 공개키를 받아서, 대칭 암호화 세션에서 쓸 일회용 키를 공개키로 암호화해 서버에 보낸다.
  3. 개인키로 복호화서버가 자신의 개인키로 그 메시지를 복호화해 일회용 키를 알아낸다. 양쪽이 이제 같은 일회용 키를 가졌으므로 이후 대칭 암호로 데이터를 주고받는다.

인증 기관(CA)·루트 인증서·신뢰 체인

CA는 인증서에 서명해주는 기관이고, 브라우저에 미리 내장된 루트 인증서에서 중간 CA를 거쳐 서버 인증서까지 이어지는 서명의 사슬이 신뢰 체인이다.

→ 03-01 참조

#1문제 상황

서버가 자신의 공개키를 가진 인증서를 제시한다고 해도, 클라이언트는 그것을 믿을 수 없다. 악의적인 사람도 자신이 만든 인증서를 내밀 수 있기 때문이다. "나는 구글입니다"라고 말하는 것만으로는 증명이 안 된다. 이 인증서가 정말 구글이 소유한 것인지, 중간에 누군가 바꿔치지 않았는지 확인할 방법이 필요하다.

#2핵심 질문

서버의 인증서가 정말 신뢰할 만한 것인지, 그리고 그 서버가 정말 자신이 주장하는 기관인지를 어떻게 검증할까?

#3동작 예시

인증 기관(CA, Certificate Authority)이 서버의 인증서에 디지털 서명을 한다. 그 CA 자신도 상위 CA로부터 인증을 받았고, 그 위에 또 상위 CA가 있으며, 최상단에는 브라우저에 미리 내장된 루트 CA가 있다. 클라이언트는 루트 CA를 믿고, 서버 인증서부터 루트 CA까지 거꾸로 올라가며 각 단계의 서명을 확인(신뢰 체인)해서 그 인증서가 신뢰할 만한지 판단한다.

#4동작 과정

  1. 루트 CA 신뢰브라우저에는 몇십 개의 루트 CA 인증서가 미리 내장되어 있다. 클라이언트는 이들을 자동으로 신뢰한다.
  2. 서명 검증 체인클라이언트가 서버 인증서를 받으면, 그것이 어느 중간 CA로부터 서명받았는지 확인한다. 그 중간 CA는 또 상위 CA로부터, 그리고 최종적으로 루트 CA로부터 서명을 받았는지 확인한다.
  3. 신뢰 결정루트 CA까지 연결되는 서명의 사슬(신뢰 체인)이 끊기지 않고 모두 유효하면, 그 서버 인증서는 신뢰할 수 있는 것으로 판단한다.

#5한 줄 요약

브라우저에 내장된 루트 CA를 신뢰의 출발점으로 삼아, 그로부터 서버 인증서까지 이어지는 서명의 사슬(신뢰 체인)을 검증함으로써 서버의 정체성을 확인하는 것

도메인 이름의 구조: TLD·아펙스·서브도메인·FQDN

도메인 이름은 .com 같은 최상위 도메인(TLD), 그 아래 등록한 아펙스(example.com), 앞에 붙는 서브도메인(www)으로 이루어지며 전체를 다 쓴 이름이 FQDN이다.

#1문제 상황

인증서는 특정 도메인 이름에 대해서만 유효하다. example.com용 인증서로는 example.org에 접속할 수 없다. 또한 www.example.com과 mail.example.com은 다른 도메인으로 취급될 수 있으므로, 어떤 인증서를 어떤 도메인에 붙일지 명확히 해야 한다. 도메인 이름이 어떤 구조를 가지고 있는지, 그리고 인증서가 어떤 부분을 검증하는지 알아야 한다.

#2핵심 질문

웹 사이트의 인증서는 정확히 어떤 도메인 이름에 대해 유효한가?

#3동작 예시

www.example.com이라는 도메인 이름은 네 부분으로 이루어진다. 맨 오른쪽 .com이 최상위 도메인(TLD, Top-Level Domain)이고, 그 앞의 example이 등록한 기본 도메인(아펙스, apex)이다. 앞의 www는 서브도메인이다. 이 네 부분을 모두 합쳐 쓴 www.example.com을 FQDN(Fully Qualified Domain Name)이라 한다. 인증서는 이 FQDN 전체 또는 일부를 지정해 발급된다.

#4동작 과정

  1. 도메인 계층 구분도메인 이름을 오른쪽에서 왼쪽으로 읽으면, TLD(.com) → 아펙스(example.com) → 서브도메인(www.example.com)으로 계층이 나뉜다.
  2. FQDN 확인브라우저 주소 표시줄에 입력한 전체 도메인 이름(예: www.example.com)을 FQDN이라 한다.
  3. 인증서 도메인 검증서버의 인증서가 그 FQDN 또는 그것과 일치하는 도메인 이름을 보유하고 있는지 확인한다.

와일드카드 인증서와 여러 도메인 이름(SAN)

*.example.com처럼 한 단계 서브도메인 전체를 덮는 것이 와일드카드 인증서이고, 여러 도메인 이름을 한 인증서에 함께 담는 필드가 SAN(추가 이름)이다.

#1문제 상황

회사가 운영하는 웹 서비스가 여러 도메인이나 여러 서브도메인을 사용할 수 있다. 예를 들어 www.example.com, api.example.com, mail.example.com, docs.example.com 등이 모두 같은 서버에서 호스팅될 수 있다. 각 도메인마다 따로 인증서를 발급받으면 관리 비용이 증가하고, 인증서 갱신도 여러 번 해야 한다.

#2핵심 질문

여러 도메인이나 서브도메인을 한 인증서로 커버할 수 있을까?

#3동작 예시

두 가지 방식이 있다. 첫째, *.example.com이라는 와일드카드 인증서는 www.example.com, api.example.com, mail.example.com 등 한 단계 아래의 모든 서브도메인을 자동으로 보호한다. 둘째, SAN(Subject Alternative Name, 추가 이름)은 한 인증서 안에 여러 도메인을 명시적으로 나열하는 필드다. 예를 들어 www.example.com과 www.example.org를 한 인증서에 담을 수 있다.

#4동작 과정

  1. 와일드카드 방식*.example.com을 등록한 인증서는 *.example.com과 일치하는 모든 도메인을 검증한다. 단, 한 단계 아래만 포함되므로(www.example.com, api.example.com 가능; a.b.example.com 불가능).
  2. SAN 방식인증서 내부의 SAN 필드에 여러 도메인을 명시적으로 입력한다. 브라우저가 접속한 도메인이 SAN 목록에 있으면 유효한 것으로 판단한다.

ACM이라는 서비스의 좌표02-01

AWS Certificate Manager가 대신하는 일과 요금 모델

ACM은 SSL/TLS 인증서의 발급·저장·갱신·배포를 AWS가 대신 처리해 주는 서비스이며, AWS 서비스에 붙이는 퍼블릭 인증서 자체는 무료다.

#1문제 상황

서버에서 인증서를 직접 관리하려면, 인증서 발급 신청, 파일 관리, 배포, 갱신(보통 3개월마다) 등을 모두 수동으로 처리해야 한다. 인증서가 만료되기 전에 갱신하지 못하면 서비스가 중단된다. 또한 여러 서버나 리전에 같은 인증서를 배포하려면 파일을 각각 복사해야 한다.

#2핵심 질문

SSL/TLS 인증서의 발급부터 갱신, 배포까지의 복잡한 과정을 자동화할 수 있을까?

#3동작 예시

AWS Certificate Manager(ACM)는 AWS가 인증서의 전체 생명주기를 대신 관리해주는 서비스다. 사용자는 ACM 콘솔이나 API에서 도메인 이름과 검증 방식을 지정하면, ACM이 인증서를 발급하고 저장한다. 그리고 만료 3개월 전부터 자동으로 갱신 프로세스를 시작한다. 또한 ACM에서 발급한 인증서는 AWS 서비스(ALB, NLB, CloudFront, API Gateway 등)에 바로 붙일 수 있다.

#4동작 과정

  1. 인증서 발급 요청사용자가 ACM 콘솔에서 도메인 이름을 입력하고 검증 방식(DNS 또는 이메일)을 선택한 후 발급을 요청한다. ACM이 CA와 협력해 인증서를 취득한다.
  2. 자동 갱신 관리ACM이 인증서의 유효 기간을 추적하고, 만료 3개월 전부터 자동으로 갱신 프로세스를 진행한다. 사용자는 별도의 개입 없이도 서비스가 항상 유효한 인증서를 사용하도록 보장된다.

#1문제 상황

AWS 리소스 중 일부는 글로벌하게(모든 리전에서) 사용할 수 있지만, ACM 인증서는 그렇지 않다. 인증서를 발급한 리전(예: us-west-2) 안에서만 그 인증서를 사용할 수 있다. 만약 다른 리전의 서비스(예: ap-northeast-1의 ALB)에 같은 도메인 인증서를 붙이려면, 그 리전에서 별도로 발급해야 한다. 리전 간에 인증서를 복사하거나 이동할 방법이 없다. 이것이 아키텍처 설계에 영향을 미친다.

#3동작 예시

#4동작 과정

ACM 인증서의 신뢰 체인은 세 층입니다. 최상단(루트 CA)은 Amazon Trust Services의 루트 인증 기관이며 브라우저가 신뢰합니다. 중간(중간 CA)은 Amazon Trust Services의 중간 인증 기관이며 주기적으로 교체됩니다(로테이션). 발급은 ACM이 실제 서버 인증서를 중간 기관으로 서명합니다. 투명성은 발급된 모든 인증서가 공개 로그(CT 로그)에 기록되며 누구나 조회 가능합니다. 이렇게 체인·로테이션·로깅을 통해 신뢰와 투명성을 유지합니다.

#4동작 과정

  1. 루트 CA 신뢰 설정브라우저와 운영 체제에는 Amazon Trust Services의 루트 CA가 미리 등재되어 있어 신뢰합니다.
  2. 중간 CA 로테이션ACM이 발급하는 인증서는 중간 CA로 서명되는데, 이 중간 CA는 보안상 주기적으로 새로운 것으로 교체됩니다.
  3. CT 로깅발급된 모든 인증서의 정보(도메인, 발급 시간 등)는 공개 CT(Certificate Transparency) 로그에 자동 기록되어 감시와 검증이 가능합니다.

#5한 줄 요약

ACM 인증서가 브라우저가 신뢰하는 Amazon Trust Services 루트 CA를 거쳐 발급되며, 중간 CA의 주기적 교체와 공개 로깅으로 신뢰와 투명성을 보장하는 것

ACM 콘솔에서 인증서를 신청하면 각 도메인마다 고유한 CNAME 레코드(이름과 값)를 생성합니다. 예를 들어 _12345abc.example.com CNAME _token.acm-validations.aws. 같은 형태입니다. 이 CNAME을 도메인의 DNS 설정에 추가하면, ACM은 이 정확한 레코드가 있는지 확인해서 소유권을 증명합니다.

#4동작 과정

  1. 토큰 생성인증서 신청 시 ACM이 도메인마다 고유한 레코드 이름(호스트)과 값(CNAME 대상)을 생성합니다.
  2. DNS 레코드 등록도메인 관리자가 이 CNAME을 DNS 설정에 추가합니다(Route 53, 호스팅 서비스 등).
  3. 검증 확인ACM이 정기적으로 이 레코드의 존재 여부를 확인하고, 발견되면 도메인 소유권을 확인합니다.

#5한 줄 요약

ACM이 각 도메인마다 고유한 CNAME 토큰을 생성해서 DNS에 등록하도록 하고, 그 레코드의 존재를 확인해 도메인 소유권을 검증하는 것

#2핵심 질문

  3. 검증 대기DNS가 업데이트되면 ACM이 자동으로 확인해서 도메인을 검증합니다(보통 몇 분에서 몇 시간).

HTTP 검증: CloudFront 리디렉션 방식

#1문제 상황

DNS 검증과 이메일 검증이 모두 불가능한 경우도 있습니다. 도메인이 제3자의 DNS에 있고, 관리자 이메일도 접근할 수 없을 때입니다. 이 경우 인증서를 발급받을 수 있는 방법이 없었습니다.

#2핵심 질문

도메인의 웹 서버에 접근할 수 있으면, 그걸 이용해 인증서 소유권을 검증할 수는 없을까요?

#3동작 예시

ACM은 도메인의 http://domain.com/.well-known/acm-challenge/ 경로에 특정 파일이 있는지 HTTP로 요청해서 확인합니다. 예를 들어 ACM이 지정한 token12345 파일이 그 경로에 있으면 리디렉션하도록 설정해 두면, ACM이 파일을 읽어서 소유권을 확인합니다.

#4동작 과정

  2. 리디렉션 설정웹 서버나 CDN(예: CloudFront)에서 /.well-known/acm-challenge/토큰 경로를 ACM이 지정한 위치로 리디렉션하도록 설정합니다.
  3. HTTP 요청으로 검증ACM이 정기적으로 그 경로에 HTTP 요청을 보내고, 파일을 읽거나 올바른 리디렉션을 받으면 소유권을 확인합니다.

#5한 줄 요약

레코드 전파 지연, CAA 레코드가 Amazon CA 를 막는 경우, 잘못된 리디렉션 등이 검증 실패의 주된 원인이다.

#1문제 상황

도메인 소유권 검증(DNS, 이메일)을 요청했지만 ACM이 실패했을 때, 단순히 "검증 실패" 메시지만 받습니다. 어느 단계에서 막혔는지, 내가 뭘 놓쳤는지 파악하기 어렵습니다. 검증 요청을 다시 보내도 같은 지점에서 계속 실패하면 원인을 진단할 수단이 필요합니다.

#2핵심 질문

ACM이 검증 실패를 보고했을 때 그 원인이 DNS 전파 지연인지, CAA 레코드 충돌인지, 리디렉션 오류인지 어떻게 구분하는가?

#3동작 예시

DNS 검증을 요청한 뒤 ACM이 제시한 CNAME 레코드(_xxx.example.com)를 Route 53에 추가했는데 검증이 실패했다고 나옵니다. 이때 ACM의 검증 상태 페이지에서 "타임아웃" 또는 "검증할 수 없음"이라는 상세 메시지를 확인하고, DNS 레코드가 정말 전파됐는지 nslookup 또는 Route 53 콘솔에서 확인합니다.

#4동작 과정

  1. 원인 분류 및 확인ACM 콘솔의 인증서 상세 페이지에서 각 도메인의 검증 상태 메시지를 읽어 "레코드 미전파", "CAA 정책 거부", "리디렉션 오류" 등 대략적인 원인을 판단합니다.
  2. DNS 또는 이메일 경로 점검DNS 검증이라면 레코드가 실제로 모든 네임서버에 전파됐는지 확인하고, 이메일 검증이라면 도메인 관리자 이메일로 ACM이 보낸 승인 링크가 도착했는지 확인합니다.
  3. 정책 및 설정 재검토CAA 레코드가 amazon 을 명시적으로 허용하는지, CNAME이 리다이렉트 체인을 만들지 않는지 확인한 뒤 필요시 수정하고 재검증을 요청합니다.

#5한 줄 요약

검증 실패 시 ACM이 제시하는 상태 메시지와 수동 점검(DNS 전파, CAA 정책, 리디렉션)을 조합해 실패 원인을 진단하고 제거하는 과정

통합 서비스 모델: ACM이 인증서를 대신 배치한다

ACM 인증서는 private key를 내려받지 않고 지원되는 AWS 서비스에 연결만 하면 ACM이 배포와 갱신까지 관리해 준다.

#1문제 상황

일반적인 인증서는 발급받은 뒤 개인 키(private key)와 인증서 파일을 직접 다운받아서 각 서버에 배포해야 합니다. 갱신 시점이 되면 새로운 인증서 파일을 다시 다운받고 모든 서버에 재배포해야 하는 수동 작업이 반복됩니다.

#2핵심 질문

ACM 인증서를 지원하는 AWS 서비스(ALB, CloudFront 등)에 직접 연결하면 인증서 갱신은 ACM이 자동으로 처리해 주는가?

#3동작 예시

ALB(Application Load Balancer)의 HTTPS 리스너를 설정할 때 ACM 인증서를 지정하는 순간, ACM은 그 인증서가 자신이 관리하는 것임을 알게 됩니다. 갱신 시점이 되면 ACM이 자동으로 새 인증서를 발급받고 ALB가 이를 즉시 사용하도록 업데이트합니다. 별도의 파일 다운로드나 서버 재배포 없이 진행됩니다.

#4동작 과정

  1. ACM 인증서 선택ALB, CloudFront, API Gateway 등 지원 서비스를 설정할 때 "인증서 선택" 항목에서 ACM 인증서를 지정합니다.
  2. ACM과 서비스 연결AWS 백엔드가 "이 서비스는 ACM 인증서 ID 00x를 사용한다"는 매핑 정보를 저장해 둡니다.
  3. 자동 배포 및 갱신인증서가 갱신될 때마다 ACM이 그 인증서를 사용하는 모든 서비스에 자동으로 새 인증서를 배포해 중단 없이 전환합니다.

Elastic Load Balancing과 CloudFront

ALB/NLB 리스너와 CloudFront 배포에 ACM 인증서를 붙여 HTTPS를 종료하는 가장 대표적인 통합 방식이다.

#1문제 상황

HTTPS 트래픽을 처리하려면 로드 밸런서나 CDN이 클라이언트와의 TLS 핸드셰이크를 완료해야 하는데, 이때 인증서 파일이 필요합니다. 여러 서비스에서 HTTPS를 쓰면 각각 인증서를 관리하고 갱신할 때마다 각 서비스에 따로 배포해야 합니다.

#2핵심 질문

ALB, NLB, CloudFront 같은 주요 로드 밸런싱·CDN 서비스에서는 ACM 인증서를 어떻게 활용하는가?

#3동작 예시

ALB의 443 포트(HTTPS) 리스너를 설정할 때 ACM 인증서를 지정하면, 클라이언트가 ALB에 연결할 때 ACM이 제공한 인증서로 TLS 핸드셰이크가 즉시 이루어집니다. CloudFront 배포의 "SSL 인증서" 항목에서도 ACM 인증서를 직접 선택할 수 있습니다.

#4동작 과정

  1. 리스너 또는 배포 설정ALB/NLB의 HTTPS 리스너나 CloudFront 배포의 SSL/TLS 설정에서 ACM 인증서를 선택합니다.
  2. HTTPS 종료 처리클라이언트 요청이 들어올 때 리스너/배포가 ACM 인증서를 사용해 TLS 핸드셰이크를 수행합니다.
  3. 내부 통신TLS가 종료된 뒤 백엔드 대상(EC2 인스턴스, S3 버킷 등)으로는 필요에 따라 HTTP 또는 HTTPS로 전달합니다.

#5한 줄 요약

#1문제 상황

#2핵심 질문

#4동작 과정

#2핵심 질문

CloudFormation 스택이 ACM 인증서 검증 완료를 무한정 기다리지 않게 하면서도 자동 프로비저닝을 보장하려면?

#3동작 예시

#4동작 과정

  1. 인증서와 검증 레코드를 템플릿에 정의AWS::CertificateManager::Certificate에서 DNS 검증을 선택하고, DomainValidationOptions 섹션의 검증용 CNAME 정보를 Route 53 레코드로 자동 생성하도록 설정합니다.
  2. 스택 실행CloudFormation 스택을 생성하면 인증서와 검증 레코드가 동시에 배포됩니다.
  3. 검증 자동 완료 및 후속 리소스 배포검증이 완료되면 스택이 나머지 리소스(ALB, CloudFront 등)를 계속 배포합니다.

#4동작 과정

  1. 내보내기 가능한 ACM 인증서 구매ACM에서 새 인증서를 요청할 때 또는 기존 퍼블릭 인증서에서 "내보내기 가능" 옵션을 선택합니다. (유료 옵션)

#3동작 예시

온프레미스 데이터센터의 웹 서버가 ACM 인증서를 사용해야 할 때, ExportCertificate API를 호출하면 인증서 체인(중간 CA 포함)과 패스프레이즈로 암호화된 개인 키를 PEM 형식으로 받을 수 있습니다. 개인 키는 암호화되어 있으므로 인증서를 가지고만으로는 개인 키를 복호화할 수 없고, 패스프레이즈를 알아야만 사용할 수 있습니다.

  2. 암호화와 생성ACM이 인증서, 중간 인증서 체인, 패스프레이즈로 암호화된 개인 키를 PEM 형식으로 생성합니다.

내보낸 인증서 폐기(Revoke)와 OCSP·CRL

개인 키가 유출됐을 때 인증서를 폐기해 OCSP·CRL 을 통해 브라우저가 더는 신뢰하지 않게 만드는 조치다.

#1문제 상황

한 번 발급된 인증서는 만료 날짜까지 유효하며, 개인 키가 유출되거나 손상되어도 인증서 자체는 계속 유효합니다. 브라우저와 클라이언트는 만료 날짜만 확인하지 중간에 폐기됐는지는 확인할 방법이 없어서, 악의적인 사용자가 유출된 개인 키로 서버를 사칭할 수 있습니다.

#2핵심 질문

개인 키가 유출되었을 때 인증서를 즉시 신뢰할 수 없는 상태로 만들 수 있는 방법이 있을까요?

#3동작 예시

ACM에서 내보낸 인증서를 사용하던 서버에서 개인 키가 도용되었다면, RevokeClientCertificate API를 호출하여 그 인증서를 폐기할 수 있습니다. 폐기 후 ACM은 OCSP(Online Certificate Status Protocol, 실시간 인증서 상태 조회 프로토콜) 응답기와 CRL(Certificate Revocation List, 폐기된 인증서 목록)을 즉시 업데이트하여, 브라우저가 그 인증서를 검증할 때 폐기 상태를 확인하고 연결을 거부하게 합니다.

#4동작 과정

  1. 폐기 요청개인 키 유출을 감지한 관리자가 폐기할 인증서의 ARN을 지정하여 API를 호출합니다.
  2. 상태 업데이트ACM이 OCSP 응답기의 데이터와 CRL 배포 지점(Distribution Point)을 실시간으로 업데이트합니다.
  3. 클라이언트 검증이후 브라우저는 인증서를 검증할 때 OCSP 쿼리나 CRL을 확인하고 폐기 상태를 발견하여 연결을 차단합니다.

  1. 에이전트 배포Kubernetes 클러스터에 ACM 인증서 동기화 에이전트를 배포하고 IAM 역할을 부여하여 ACM API 접근 권한을 설정합니다.

ACME 프로토콜과 ACM 관리형 ACME 서버

ACME는 인증서 발급·갱신을 자동화하는 표준 프로토콜이고, ACM은 이를 말하는 관리형 ACME 서버를 제공해 표준 클라이언트로 인증서를 받게 해준다.

#1문제 상황

ACM의 RequestCertificate API로 인증서를 발급받으려면 개발자가 AWS 계정 접근 권한과 AWS SDK 사용 방법을 알아야 합니다. 또한 검증 방식(DNS 검증 또는 이메일 검증)의 세부 설정도 RequestCertificate 호출 시점에 지정해야 하므로, 개발 팀과 인프라 팀 간에 요청-승인 절차가 복잡합니다.

#2핵심 질문

#3동작 예시

ACME(Automated Certificate Management Environment)는 Let's Encrypt에서 주도한 표준 프로토콜로, 클라이언트가 서버에 인증서 발급을 요청하고 도메인 소유권을 검증한 후 인증서를 받는 전체 과정을 자동화합니다. ACM은 ACME 호환 서버를 제공하므로, Certbot, cert-manager, acme.sh 등 표준 ACME 클라이언트를 사용하는 어떤 시스템이든 ACM에 인증서를 요청하고 받을 수 있습니다.

#4동작 과정

  1. ACME 엔드포인트 설정ACM 관리자가 ACM의 ACME 서버 엔드포인트를 활성화하고 External Account Binding(EAB, 외부 계정 바인딩으로 ACME 클라이언트의 신원을 확인하는 방식) 키를 생성합니다.
  2. 클라이언트 인증개발 팀이 표준 ACME 클라이언트에 엔드포인트와 EAB 키를 설정하고 도메인 소유권 검증(DNS 레코드 또는 HTTP 챌린지)을 수행합니다.
  3. 자동 발급 및 갱신클라이언트가 ACME 프로토콜로 인증서를 요청하면 ACM이 검증을 완료한 후 인증서를 발급하고, 만료 30일 전부터 자동으로 갱신합니다.

#1문제 상황

ACM에서 인증서를 얻는 방법은 두 가지입니다. 첫 번째는 RequestCertificate API를 직접 호출하는 것인데, 이 방식은 AWS 계정 접근 권한이 필요하고 API 호출 시마다 검증 방식을 지정해야 합니다. 두 번째는 ACME 클라이언트를 사용하는 것인데, 이 방식은 표준 프로토콜을 사용하지만 관리자가 먼저 ACME 서버 설정과 EAB를 구성해야 합니다.

#2핵심 질문

상황에 따라 어느 방식을 선택해야 하고, 두 방식이 어떻게 다르게 흐를까요?

#3동작 예시

소규모 팀에서 ACM 콘솔이나 AWS CLI로 몇 개의 인증서만 관리한다면 RequestCertificate API를 직접 사용하는 것이 간단합니다. 반면 마이크로서비스 아키텍처에서 수백 개의 파드와 서버가 각각 인증서를 필요로 한다면, 관리자가 ACME 서버를 미리 활성화한 후 개발자는 표준 ACME 클라이언트만 사용하는 분리형 흐름이 훨씬 효율적입니다.

#4동작 과정

  1. RequestCertificate 흐름개발자가 AWS 계정 권한으로 직접 RequestCertificate API를 호출하고, 검증 방식을 지정하며, 검증 완료 후 인증서를 받습니다. (개발자가 모든 권한과 절차를 직접 처리)
  2. ACME 흐름관리자가 ACME 엔드포인트와 EAB를 설정한 후, 개발자는 표준 ACME 클라이언트만 사용하여 도메인 검증 후 인증서를 받습니다. (권한과 절차가 분리됨)
  3. 선택 기준RequestCertificate는 빠르고 간단하지만 각 요청마다 API 호출이 필요하고, ACME는 초기 설정 후 표준 클라이언트로 자유롭게 발급받을 수 있습니다.

#5한 줄 요약

#1문제 상황

인증서를 수동으로 발급받아서 ACM에 업로드하거나, ACM의 DNS 검증을 거쳐 발급받는 방식은 각 클라이언트에서 발급 과정을 개별적으로 진행해야 합니다. 게다가 ACME 클라이언트(예: certbot)가 AWS 계정과 연결되려면 AWS 계정 정보와 권한을 어떻게 매핑할지 명확한 진입점이 없습니다.

#2핵심 질문

표준 ACME 클라이언트 도구들이 AWS 계정으로 연결되어 자동화된 인증서 발급을 받을 수 있도록 하려면 어떻게 해야 할까요?

#3동작 예시

ACME 엔드포인트는 각 AWS 계정과 리전별로 고유한 디렉터리 URL을 제공하는 진입점입니다. certbot 같은 표준 ACME 클라이언트가 이 URL에 접속하면, AWS ACM의 인증서 발급 시스템과 ACME 프로토콜로 통신할 수 있게 됩니다.

#4동작 과정

#4동작 과정

  1. 지원 키 알고리즘 제약Private CA로부터 발급받는 인증서의 공개 키 알고리즘(RSA, ECC)은 CA 생성 시 결정되며, 인증서별로 선택할 수 없습니다. 조직의 보안 정책에 맞춰 Private CA를 만들 때 미리 결정해야 합니다.
  2. 395일 최대 유효기간ACM 프라이빗 인증서의 최대 유효기간은 395일(약 13개월)로 고정됩니다. 공인 인증서(1년)보다 약간 길지만, 1년 이상을 요청할 수 없습니다.
  3. 발급 약 11개월 후 자동 갱신인증서 발급 후 약 11개월이 지나면 ACM이 자동으로 갱신 절차를 시작합니다. 인증서 유효기간이 남아있어도 미리 갱신해서 끊김 없이 유지하려는 의도입니다.

#4동작 과정

#1문제 상황

ACM에서는 AWS의 퍼블릭 CA 파트너를 통해 주로 인증서를 발급받는다. 하지만 기존에 외부 CA(예: Let's Encrypt, DigiCert)에서 발급한 인증서를 이미 가진 경우나, 특정 요구사항 때문에 다른 CA를 써야 하는 경우, 그 인증서를 ACM에 등록해 AWS 서비스에 연결해야 했다.

#2핵심 질문

외부 CA에서 받은 인증서를 ACM에 가져올 때 필요한 형식과 조건은 무엇인가?

#3동작 예시

외부 CA에서 받은 인증서 파일(예: example.crt), 개인 키 파일(example.key), 인증서 체인 파일(chain.crt)을 모두 텍스트 형식(PEM)으로 맞추고, Import certificate 페이지에 각각 붙여넣으면 ACM이 검증한 뒤 가져온다.

#4동작 과정

  2. 전제 조건 확인인증서의 도메인이 사용하려는 도메인과 정확히 일치하고, 유효 기간이 아직 시작되지 않았거나 만료되지 않았으며, 개인 키가 인증서와 쌍을 이루는지 확인한다.

기존 IAM 정책은 "이 역할은 ACM RequestCertificate을 할 수 있다"만 명시할 수 있었고, "하지만 example.com 도메인에만" 또는 "하지만 특정 태그가 붙은 인증서에만"처럼 세밀한 조건을 붙일 수 없었습니다. 그래서 모든 도메인의 인증서를 발급할 수 있는 권한을 주거나, 아무것도 못하게 막는 둘 중 하나만 가능했습니다.

#2핵심 질문

IAM 정책에 특정 도메인이나 태그 같은 조건을 붙여서 권한의 범위를 더 좁게 제한할 수 있을까요?

#3동작 예시

IAM 정책에 "Condition" 절을 추가하면, 예를 들어 "acm:domainName이 *.example.com일 때만" 또는 "리소스의 태그에 env=production이 있을 때만" RequestCertificate을 허용하는 식으로 작성할 수 있습니다. 이렇게 하면 같은 역할도 도메인별, 태그별로 다른 권한을 가질 수 있습니다.

#4동작 과정

  1. 조건 키 선택ACM 전용 조건 키(acm:domainName, acm:certificateAuthority 등)나 표준 태그 조건 키(aws:PrincipalTag, aws:ResourceTag 등) 중 적용할 것을 선택합니다.
  2. 정책에 조건 추가IAM 정책의 "Condition" 절에 키-연산자-값을 명시합니다. 예를 들어 "acm:domainName": {"StringLike": "*.example.com"} 같은 형태입니다.
  3. API 호출 시 평가사용자가 API를 호출하면 IAM이 그 요청의 컨텍스트(도메인 이름, 리소스 태그 등)와 정책의 조건을 비교해, 조건이 맞아야만 "허용됨" 판정을 내립니다.

IAM 정책의 Condition 절에 도메인, 태그, 인증서 속성 같은 컨텍스트 조건을 붙여, 같은 IAM 액션도 상황에 따라 다르게 허용/거부함으로써 권한의 세밀한 제어를 구현하는 방식

#1문제 상황

기존에는 ACM이 인증서를 갱신하거나 검증 상태를 확인하는 내부 작업을 할 때, 누가 그 작업을 수행하는지 명확하지 않았습니다. AWS 서비스가 사용자 대신 일을 하려면 어딘가 권한이 있어야 하는데, 그 권한 구조가 일관되지 않으면 감사나 문제 추적이 어렵습니다.

#2핵심 질문

ACM이 사용자를 대신해 인증서 갱신 같은 백그라운드 작업을 할 때, 어떤 IAM 역할로 그 작업을 수행해야 할까요?

#3동작 예시

AWS는 ACM 전용 서비스 연결 역할(AWSServiceRoleForCertificateManager)을 미리 정의해뒀습니다. 이 역할은 AWS가 자동으로 생성하고, 오직 ACM만 이 역할을 쓸 수 있으며, 인증서 갱신에 필요한 최소 권한만 가지고 있습니다. 또한 ACME 자동화(DNS 검증 자동화 등)를 하려면 그 서비스 연결 역할 외에 별도의 IAM 권한을 추가로 구성해야 합니다.

#4동작 과정

  1. 서비스 연결 역할 생성사용자가 첫 번째로 ACM을 사용할 때 AWS가 자동으로 AWSServiceRoleForCertificateManager를 생성하고, 그 역할을 ACM에 신뢰(trust)합니다. 이제 ACM이 사용자를 대신해 작업할 기반이 마련됩니다.
  2. 기본 갱신 권한서비스 연결 역할에는 인증서 갱신을 위한 기본 권한(Route 53, CloudFront 같은 연동 서비스 조회 권한 등)이 미리 포함됩니다.
  3. ACME 확장 권한 구성DNS 검증을 완전히 자동화하려면, 사용자가 별도로 ACME 자동화용 IAM 정책을 작성해 서비스 연결 역할에 추가해야 합니다(또는 별개의 ACME 전용 역할을 만들어 권한을 세분화할 수 있습니다).

#5한 줄 요약

AWS 서비스에 전용 서비스 연결 역할을 제공해 그 서비스의 백그라운드 작업을 명확하게 추적 가능하게 하고, 추가 자동화 필요 시 별도 IAM 권한을 레이어처럼 추가할 수 있게 하는 권한 구조

복원력과 인프라 보안

ACM이 리전·가용 영역 기반으로 확보하는 가용성과, TLS 및 서명된 API 요청으로 보호되는 네트워크 계층 보안.

#1문제 상황

기존에는 API 서비스가 한 곳에만 있거나, 네트워크 요청이 암호화되지 않으면 누구나 중간에서 통신을 가로챘습니다. 또한 서비스 장애 시 복구 절차가 명확하지 않으면 인증서 발급이나 갱신이 오랫동안 불가능할 수 있었습니다.

#2핵심 질문

ACM이 리전과 가용 영역에 걸쳐 안정적으로 작동하고, 네트워크 공격으로부터 보호받으려면 어떤 구조가 필요할까요?

#3동작 예시

ACM은 각 AWS 리전에서 여러 가용 영역(서로 다른 데이터센터)에 걸쳐 배포됩니다. 한 가용 영역이 장애를 일으키면 다른 가용 영역이 요청을 받고, 모든 API 요청은 TLS(HTTP 위의 암호화 프로토콜)로 암호화되며, 서명된 API 요청(AWS Signature Version 4)으로만 ACM과 통신할 수 있습니다.

#4동작 과정

  1. 다중 가용 영역 배포ACM의 데이터와 API 엔드포인트가 한 리전 내 여러 가용 영역에 복제되므로, 한 곳의 장애가 전체 서비스를 내려놓지 않습니다.
  2. 네트워크 계층 보안모든 API 통신이 TLS로 암호화되고, 또한 AWS SDK나 CLI를 통한 모든 요청이 AWS Signature Version 4로 서명되어야 하므로, 위변조되거나 무단으로 위장한 요청은 ACM에 도달하지 못합니다.
  3. 백업 및 복구ACM이 인증서 데이터를 자동으로 여러 가용 영역에 복제하므로, 갑작스런 데이터 손실 시에도 복구 절차를 통해 복원할 수 있습니다.

#5한 줄 요약

ACM을 다중 가용 영역에 걸쳐 배포하고, 모든 통신을 TLS 암호화와 요청 서명으로 보호해, 장애 상황에서도 서비스 연속성을 유지하고 네트워크 공격으로부터 안전하게 하는 인프라 설계

API 요청 속도 제한과 스로틀링

ACM API를 너무 빠르게 연속 호출하면 초당 요청 수 상한에 걸려 요청이 거부되므로, 재시도와 간격 조절이 필요하다는 규칙이다.

#1문제 상황

보통 프로그램에서 API를 호출할 때는 필요한 만큼 빠르게 연속으로 요청할 수 있다고 생각합니다. 하지만 AWS는 API 호출이 너무 많아지면 서버 부하를 피하기 위해 초과 요청을 거부합니다. ACM API도 초당 최대 호출 횟수 제한이 있어서 한계를 넘으면 요청이 실패합니다.

#2핵심 질문

ACM API를 연속으로 빠르게 호출하면 어떻게 되고, 어떻게 대처해야 하는가?

#3동작 예시

초당 X번 이상 API를 호출하면 "ThrottlingException"(조절 예외) 오류가 돌아오고 요청이 거부됩니다. 그러면 프로그램은 일정 시간 기다렸다가 다시 요청해야 합니다.

#4동작 과정

  1. 요청 전송프로그램이 ACM API를 호출합니다.
  2. 한계 도달 시 거부초당 한계를 초과하면 AWS가 요청을 받지 않고 ThrottlingException을 돌려줍니다.
  3. 재시도 및 간격 조절프로그램은 오류를 받으면 정해진 시간(예: 1초) 기다렸다가 다시 요청하거나, 요청 간격을 미리 늘려서 보냅니다.

자주 겪는 문제와 해결: 가져오기·피닝·API Gateway·ACME

인증서 가져오기 실패, 인증서 피닝으로 인한 갱신 장애, API Gateway 연동 오류, ACME 자동화 오류 같은 흔한 증상의 원인과 해결 절차다.

#1문제 상황

ACM을 처음 써보면 순조롭게 작동할 것 같지만, 실제로는 인증서를 가져올 때 실패하거나, 오래된 인증서를 계속 쓰는 바람에 갱신이 안 되거나, API Gateway 연동이 먹지 않거나, ACME 자동화 설정이 틀어지는 등 여러 오류가 생깁니다. 이때 원인을 알 수 없으면 손쓸 방법이 없습니다.

#2핵심 질문

ACM을 쓰면서 인증서 가져오기, 갱신, 피닝, API Gateway 연동에서 흔히 마주치는 오류와 해결법은 무엇인가?

#3동작 예시

인증서 가져오기가 실패하면 인증서 파일 형식이나 키 매칭을 확인하는 식으로, 각 오류 상황마다 정해진 진단 절차와 해결 순서가 있다는 뜻입니다.

#4동작 과정

  1. 증상 파악오류 메시지와 로그에서 어디서 문제가 생겼는지 확인합니다(가져오기 실패, 갱신 안 됨, 연동 오류 등).
  2. 원인 규명각 증상별 체크리스트(인증서 형식, 도메인 검증 상태, 권한, 피닝 설정 등)를 따라 원인을 찾습니다.
  3. 해결 절차 적용원인에 맞는 조치를 취합니다(인증서 재형식화, 도메인 재검증, 권한 설정 수정, 피닝 해제 등).

API 예외 처리와 SDK로 ACM 다루기

ACM API가 돌려주는 예외 유형을 이해해 코드에서 처리하고, AWS SDK로 인증서 요청·조회·태깅 등을 프로그래밍하는 방법이다.

#1문제 상황

프로그램에서 ACM API를 호출할 때 성공하는 경우만 생각하고, 오류가 나면 그냥 중단하거나 무시합니다. 하지만 네트워크 문제, 권한 부족, 잘못된 입력 등 여러 이유로 API 호출이 실패할 수 있고, 각 실패 원인을 구별해서 적절히 처리해야 안정적인 프로그램이 됩니다.

#2핵심 질문

ACM API를 코드에서 호출할 때 어떤 오류 종류가 있고, 각 오류를 어떻게 처리해야 하는가?

#3동작 예시

AWS SDK(소프트웨어 개발 키트)로 ACM을 호출하면 성공 또는 구체적인 예외(Exception) 객체가 돌아오는데, 예외에는 type("InvalidParameterException" 등)이 있어서 type별로 다르게 처리할 수 있다는 의미입니다.

#4동작 과정

  1. SDK로 API 호출AWS SDK(Python boto3, JavaScript SDK 등)를 써서 인증서 요청, 조회, 태깅 같은 작업을 코드로 수행합니다.
  2. 예외 발생 감지호출이 실패하면 AWS는 type과 message를 담은 예외 객체를 돌려줍니다.
  3. 예외 type별 처리코드에서 try-catch(또는 try-except) 블록으로 예외를 잡고, type을 확인해서 재시도(throttle), 재입력 요청(invalid input), 권한 확인(access denied) 등 적절한 대응을 합니다.

#5한 줄 요약

ACM SDK를 프로그래밍할 때 발생할 수 있는 각 예외 type의 의미를 이해하고, 각각에 맞는 오류 처리 로직을 코드에 작성하는 것
