1단계 기초 — Podman이란 무엇인가

컨테이너를 만들고 관리하는 오픈소스 엔진으로, 데몬 없이 사용자 권한으로 동작하는 것이 핵심 특징이다.

1상대의 출발점 확인

전통적인 컨테이너 도구는 중앙의 데몬(백그라운드에서 항상 떠 있는 관리 프로세스)이 컨테이너를 만들고 실행하는 모든 요청을 받아 처리했다. 사용자가 명령을 내리면 그 명령은 데몬에게 전달되고, 데몬이 실제 작업을 수행했다. 이 구조는 관리가 편하다는 장점이 있었지만, 데몬 하나가 모든 컨테이너를 책임지기 때문에 데몬이 죽으면 실행 중인 컨테이너 전체가 영향받고, 데몬을 루트 권한(관리자 권한)으로 실행해야 해서 보안 취약점이 생기면 전체 시스템이 위험해지는 문제가 있었다.

2질문 제기

컨테이너를 관리하는 중앙 데몬 없이도 안전하게 컨테이너를 만들고 실행할 수는 없을까?

3구조적 핵심 예시

Podman 은 데몬을 두지 않는 대신, podman run 같은 명령을 내리면 그 명령을 실행한 사용자 프로세스가 곧바로 컨테이너 생성을 직접 처리한다. 즉 명령 하나가 요청과 실행을 모두 맡는 셈이다. 그래서 컨테이너는 일반 사용자 권한으로도 실행할 수 있고, 각 컨테이너는 별도의 모니터 프로세스가 관리하면서 데몬이 죽을 일 자체가 없다.

4단계별 동작 과정

  1. 명령 실행사용자가 podman run 같은 명령을 내리면, 데몬을 거치지 않고 명령을 실행한 Podman 프로세스가 직접 작업을 시작한다.
  2. 컨테이너 생성과 모니터 배치Podman 이 컨테이너를 만들고, conmon 이라는 작은 모니터 프로세스를 붙여 컨테이너의 상태를 감시하게 한다. 데몬이 없어도 컨테이너 하나당 모니터가 따로 있으므로 관리가 끊기지 않는다.
  3. 실행 지속명령을 내린 프로세스가 끝나도 conmon 과 컨테이너는 남아 계속 실행되며, 컨테이너는 사용자 권한으로 돌아간다.

5본질 요약

데몬 없이 사용자 권한으로 컨테이너를 만들고 관리하게 만들어 보안과 안정성을 높이는 컨테이너 엔진

컨테이너 실행 형식과 이미지 형식의 공개 표준(OCI) 및 이미지를 저장·배포하는 레지스트리의 기본 개념이다.

1상대의 출발점 확인

컨테이너를 다루는 도구마다 실행 방식과 이미지 형식이 제각각이면, 한 도구로 만든 컨테이너는 다른 도구에서 실행되지 못하고, 이미지를 주고받을 때도 서로 호환되지 않아 사실상 도구 하나에 묶이게 된다. 초기 컨테이너 생태계는 이러한 비호환 때문에 사용자가 특정 회사의 도구에 종속되는 폐쇄적인 구조였다.

2질문 제기

도구와 회사가 달라도 누구나 동일하게 만들고 실행할 수 있는 컨테이너의 공통 기준은 무엇일까?

3구조적 핵심 예시

OCI(Open Container Initiative)는 컨테이너의 공개 표준을 정한 단체다. 이 표준은 크게 두 가지를 정의한다: 이미지 표준(컨테이너 이미지를 어떤 형식으로 저장하고 주고받을지)과 런타임 표준(이미지를 어떤 방식으로 실행할지). Podman 은 이 OCI 표준을 그대로 따르므로, 표준을 지키는 어느 도구로 만든 이미지든 Podman 으로 실행할 수 있고 그 반대도 성립한다.

4단계별 동작 과정

  1. 이미지 내려받기사용자가 podman pull 로 레지스트리(이미지를 저장하고 배포하는 서버)에서 OCI 표준 형식의 이미지를 내려받는다.
  2. 표준 형식 해석Podman 은 내려받은 이미지를 OCI 이미지 표준에 맞춰 해석하고, OCI 런타임 표준에 맞춰 컨테이너를 구성한다.
  3. 실행표준을 지키는 런타임(crun 같은 실행기)이 이미지를 컨테이너로 실행하므로, 어느 환경에서 만들어진 표준 이미지든 동일하게 동작한다.

5본질 요약

이미지와 실행 방식의 공개 표준(OCI)을 지켜 컨테이너가 도구와 회사에 관계없이 서로 호환되게 만드는 것

Docker CLI 와 문법이 호환되면서도 데몬이 없는 구조라 생기는 차이와 이식성을 이해하는 주제다.

1상대의 출발점 확인

Docker 는 데몬이 모든 컨테이너 요청을 받아 처리하는 구조로 널리 쓰였다. 사용자들은 데몬 없이도 컨테이너를 쓰고 싶지만 기존 명령어와 습관은 유지하고 싶어 했다. 데몬 구조를 벗어나는 도구가 등장했을 때 명령어가 완전히 다르면 사용자가 다시 배워야 하는 부담이 생기므로, 기존 방식과의 호환성이 곧 이식의 관건이 되었다.

2질문 제기

데몬 없는 구조를 쓰면서도 기존 Docker 명령어를 그대로 사용할 수는 없을까?

3구조적 핵심 예시

Podman 의 명령어는 Docker CLI(커맨드라인 도구)와 문법이 거의 동일하다. docker run, docker build, docker ps 에 쓰던 옵션과 흐름을 그대로 podman run, podman build, podman ps 로 바꿔 쓰면 된다. 심지어 alias docker=podman 같은 별칭(alias)을 지정하면 기존 스크립트를 거의 수정 없이 그대로 돌릴 수 있다.

4단계별 동작 과정

  1. 명령어 대응사용자가 Docker 에서 쓰던 명령을 Podman 명령으로 그대로 입력한다. 명령 이름만 바뀌고 옵션과 인자 형태는 같다.
  2. 내부 처리 차이Docker 명령은 데몬이 처리하지만 Podman 명령은 사용자 프로세스가 직접 처리한다. 겉보기 결과는 같고 실행 주체만 다르다.
  3. 호환 확인docker info 의 자리에 podman info 를 쓰는 식으로, 기존 워크플로를 그대로 이식해 사용한다.

5본질 요약

데몬 없는 구조를 가지면서도 Docker 명령어와 호환되어 기존 사용자와 스크립트가 그대로 이식되게 하는 것

1상대의 출발점 확인

  3. 사용자 환경 준비컨테이너를 실행할 사용자 계정에서 바로 podman 명령을 실행할 수 있는지 확인한다. 권한이 부족한 환경이면 구성 파일에서 사용자별 설정을 마친다.

이미지를 받으면 그 이미지에 붙은 이름과 버전 표시가 그대로 따라온다. 기존 방식은 이미지를 그 이름 그대로만 쓰기 때문에, 같은 이미지를 "운영용", "테스트용"처럼 목적별로 구분하거나 특정 빌드에 별칭을 붙여 편하게 실행할 방법이 마땅치 않다. 또한 이미지 이름에 버전을 잘못 붙여두면 나중에 어떤 이미지가 어느 시점의 것인지 혼란스러워지고, 같은 내용을 다른 이름으로 관리하게 되어 정리가 어려워지는 문제가 생긴다.

2질문 제기

하나의 이미지에 여러 이름과 버전 표시를 붙였다 떼어내어 목적에 맞게 구분하려면 어떻게 해야 할까?

3구조적 핵심 예시

podman tag myapp:1.0 myapp:latest는 myapp:1.0 이미지에 latest라는 태그를 하나 더 붙인다. 태그를 붙여도 이미지 내용은 그대로이고, 같은 이미지를 가리키는 이름이 하나 늘어날 뿐이다. podman untag myapp:latest는 그 태그만 떼어내고, 태그가 모두 사라지면 해당 이미지는 목록에서 none 태그로 남는다. 예를 들어 배포 직전에 빌드된 이미지에 latest 태그를 붙여 항상 최신 버전을 latest로 실행할 수 있게 된다.

4단계별 동작 과정

  1. 태그 붙이기podman tag 원본이름 새이름은 원본 이미지에 새 이름과 태그 쌍을 추가한다. 원본은 그대로 유지된다.
  2. 태그 떼기podman untag 이미지 태그는 지정한 태그만 제거한다. 다른 태그가 남아 있으면 이미지 자체는 삭제되지 않는다.
  3. 태그 활용실행할 때 태그로 구분된 이름을 그대로 사용한다. 예를 들어 myapp:latest는 항상 최신 빌드를 가리키도록 유지하면 명령을 바꾸지 않고도 최신 이미지를 실행할 수 있다.

5본질 요약

이미지에 이름과 버전 태그를 붙이고(tag) 떼어내어(untag), 같은 이미지를 여러 이름으로 구분하거나 특정 버전을 편리하게 가리키도록 관리하는 것

1상대의 출발점 확인

이미지를 쓸 때는 보통 레지스트리에서 이미 만들어진 것을 받아온다. 기존 방식은 직접 만든 애플리케이션을 이미지로 만들어야 할 때, 어떤 규칙으로 이미지를 구성해야 하는지 정해진 방법이 없어서 사람마다 제각각으로 만들고, 그 과정을 기록으로 남기지 않으면 나중에 같은 이미지를 다시 만들 수 없다. 이렇게 되면 이미지 구성이 불투명해져서 어느 시점에 무슨 내용이 들어갔는지 추적할 수 없고, 팀원이 서로 다른 이미지를 만들게 되는 문제가 생긴다.

2질문 제기

내 애플리케이션을 담은 컨테이너 이미지를 문법이 정해진 파일을 기준으로 재현 가능하게 만들려면 어떻게 해야 할까?

3구조적 핵심 예시

Containerfile에 FROM, COPY, RUN, CMD 같은 지시문을 순서대로 적어두고 podman build -t myapp .을 실행하면, 현재 디렉터리의 Containerfile을 읽어 그 지시문대로 이미지가 만들어진다. 예를 들어 FROM node:20, COPY . /app, RUN npm install, CMD ["npm", "start"]라는 Containerfile이 있으면, podman이 이 순서를 그대로 실행해 node 기반 이미지 위에 내 코드와 의존성을 얹은 myapp 이미지를 만들어낸다.

4단계별 동작 과정

  1. 설계 작성Containerfile에 밑바탕이 될 이미지(FROM), 복사할 파일(COPY), 실행할 설치 명령(RUN), 컨테이너 시작 시 실행할 명령(CMD)을 순서대로 적는다.
  2. 빌드 실행podman build -t 이름 .을 실행하면 podman이 Containerfile을 한 줄씩 읽어 각 지시문을 수행하고, 각 단계의 결과를 레이어로 쌓아 이미지를 만든다.
  3. 빌드 결과 사용만들어진 이미지는 로컬 목록에 등록되고, 그 이름으로 podman run 하면 Containerfile의 CMD가 기본 명령으로 실행된다.

1상대의 출발점 확인

이미지를 빌드할 때는 소스 코드를 컴파일하거나 의존성을 설치하는 과정이 필요하고, 그 과정에서 생기는 중간 산출물은 최종 이미지에는 필요 없는 경우가 많다. 기존 방식은 하나의 FROM으로 이미지를 만들기 때문에, 빌드에 필요한 도구와 실행에 필요한 도구가 같은 이미지에 모두 남아 이미지가 불필요하게 커진다. 또한 빌드할 때마다 같은 설치 작업을 처음부터 반복하면 시간이 오래 걸리고, 네트워크나 디스크 자원이 낭비되는 문제가 생긴다.

2질문 제기

빌드에만 필요한 중간 산출물은 버리고 실행에 필요한 것만 남기면서, 반복 빌드는 빠르게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

Containerfile에 FROM을 두 번 이상 적으면 다단계 빌드가 된다. 첫 번째 단계에서 컴파일러와 소스 코드로 빌드 산출물을 만들고, 두 번째 단계에서는 실행에 필요한 최소 이미지를 FROM으로 받은 뒤 COPY --from=첫단계이름으로 그 산출물만 가져와 복사한다. 예를 들어 Go 소스를 첫 단계에서 컴파일한 뒤, 두 번째 단계에서 작은 실행 이미지에 컴파일된 바이너리만 복사하면, 컴파일러가 포함되지 않은 가벼운 최종 이미지가 만들어진다.

4단계별 동작 과정

  1. 빌드 단계 정의Containerfile에 첫 FROM으로 빌드 도구가 있는 이미지를 지정하고, 그 단계에서 소스 빌드에 필요한 명령을 수행해 산출물을 만든다.
  2. 결과물만 복사두 번째 FROM으로 실행용 작은 이미지를 지정하고, COPY --from=빌드단계이름으로 앞 단계에서 만들어진 산출물만 새 이미지로 옮긴다.
  3. 캐시 활용빌드 시 각 지시문 단계의 결과가 레이어로 캐시되어, 변경되지 않은 단계는 다시 실행하지 않고 재사용한다. 변경된 줄 이후의 단계만 다시 실행되므로 반복 빌드가 빨라진다.

  1. 변경 상태 확인실행 중인 컨테이너에서 작업(패키지 설치, 파일 수정 등)을 마치고, 저장하기 전에 현재 상태가 원하는 상태인지 확인한다.
  2. commit 실행podman commit으로 해당 컨테이너의 변경된 파일시스템과 실행 설정을 스냅샷처럼 새 이미지 레이어로 저장한다. 이미지에는 이름과 태그를 붙인다.

2질문 제기

목적에 따라 호스트 폴더, 임시 공간, 메모리 중 어떤 저장소를 컨테이너 경로에 어떤 방식으로 연결할까?

3구조적 핵심 예시

설정 파일처럼 호스트에 이미 있는 파일은 podman run -v /호스트/경로:/컨테이너/경로 로 바인드 마운트(호스트 폴더를 그대로 연결)하고, 컨테이너가 지워져도 상관없는 임시 데이터는 이름 없는 익명 볼륨이나 메모리 위에만 사는 tmpfs 를 사용한다.

4단계별 동작 과정

  1. 바인드 마운트-v /호스트/경로:/컨테이너/경로 형태로 호스트의 특정 폴더를 컨테이너 경로에 그대로 연결한다. 호스트 파일을 컨테이너가 그대로 읽고 쓰며, 컨테이너가 지워져도 호스트 폴더는 그대로 남는다.
  2. 익명 볼륨이름 없는 볼륨을 컨테이너 경로에 연결한다. podman 이 자동으로 공간을 만들어 관리하며, 삭제 시점에 함께 정리되는 임시 데이터용으로 쓰인다.

2질문 제기

사용하지 않는 이미지·컨테이너·볼륨을 한 번에 안전하게 정리하고, 디스크가 실제로 어떻게 쓰이고 있는지 한눈에 파악할 수는 없을까?

3구조적 핵심 예시

podman system prune 은 사용하지 않는 대상만 골라 지운다. 예를 들어 중지된 컨테이너가 있고, 그 컨테이너가 쓰던 이미지가 다른 어떤 컨테이너에서도 참조되지 않는다면, prune 한 번에 컨테이너와 그 이미지를 함께 정리한다. 반대로 아직 실행 중이거나 곧 다시 사용할 컨테이너가 참조하는 이미지는 건드리지 않는다. podman system df 는 이와 달리 지우지 않고, 이미지·컨테이너·볼륨·캐시가 각각 몇 개이고 얼마나 많은 공간을 차지하는지를 표로 보여준다.

4단계별 동작 과정

  1. 현황 조회podman system df 로 이미지·컨테이너·볼륨별 개수와 사용 공간을 확인해 무엇이 쌓여 있는지 파악한다. 각 항목 옆의 REclaimable(회수 가능) 값이 지워도 되는 대상의 크기를 알려준다.
  2. 정리 대상을 결정podman system prune 을 실행하면 중지된 컨테이너, 그 컨테이너만이 쓰던 이미지, 사용하지 않는 네트워크와 볼륨, 빌드 캐시 중에서 회수 가능한 것들이 정리 목록으로 제안된다. --volumes 와 같은 옵션을 붙이면 볼륨까지 포함 범위를 넓힌다.

6단계 네트워킹

Podman의 기본 네트워크 스택 netavark가 컨테이너 네트워크를 구성·관리하는 방식의 개요.

1상대의 출발점 확인

컨테이너는 각자 격리된 환경에서 실행되므로, 기본 상태로는 다른 컨테이너와 통신할 방법이 없다. 과거에는 도커 같은 도구가 자체 네트워크 스택을 루트 권한으로 올려 컨테이너마다 가상 인터페이스와 브리지를 만들고 iptables 규칙으로 통신을 꾸몄다. 하지만 이 방식은 루트 권한이 필요해 일반 사용자가 컨테이너를 실행하기 어렵고, 네트워크 구성 요소가 커널과 호스트의 네트워크 설정에 깊이 의존해 관리가 복잡해지는 한계가 있다.

2질문 제기

루트 권한 없이도 여러 컨테이너가 서로 통신하고 외부와 연결되는 네트워크를 간단하고 안정적으로 만들 수는 없을까?

3구조적 핵심 예시

netavark 는 Podman 이 컨테이너를 실행할 때마다 호출하는 작은 네트워크 설정 프로그램이다. 컨테이너를 시작하면 netavark 가 호스트에 가상 브리지(virtual bridge, 여러 컨테이너가 같은 네트워크에 붙을 수 있게 하는 소프트웨어 스위치)를 만들고, 그 컨테이너 전용 가상 인터페이스인 veth(가상 이더넷 케이블) 한 쌍의 한쪽 끝을 브리지에 연결한다. 이렇게 되면 같은 브리지에 붙은 컨테이너들은 각자 받은 IP 주소로 서로 직접 통신할 수 있다.

4단계별 동작 과정

  1. 네트워크 자동 생성컨테이너를 실행할 때 --network 옵션을 주지 않으면 podman 이 기본 네트워크를 만들고, netavark 가 그 네트워크를 위한 브리지와 IP 대역을 준비한다.
  2. 인터페이스 연결netavark 가 컨테이너에 veth 가상 인터페이스를 만들고 한쪽 끝을 브리지에 꽂은 뒤, 그 네트워크 대역에서 IP 주소를 할당해 컨테이너에 부여한다.
  3. 통신 시작같은 네트워크에 붙은 컨테이너끼리는 할당된 IP로 서로 통신하고, 호스트의 라우팅 규칙을 통해 외부 네트워크와도 연결된다.

5본질 요약

  3. 격리된 통신같은 네트워크에 붙은 컨테이너끼리만 IP로 통신하고, 다른 네트워크의 컨테이너는 서로 볼 수 없어 네트워크 단위로 접근 범위가 나뉜다.

같은 네트워크에 붙은 컨테이너는 IP 주소로 통신하지만, IP 주소는 컨테이너가 실행될 때마다 바뀔 수 있고 사람이 기억하기도 어렵다. 또 컨테이너 안의 서비스는 호스트 바깥에서 직접 접근할 수 없어, 호스트의 포트와 컨테이너의 포트를 이어주는 작업이 필요하다. IP가 바뀌는 문제 때문에 다른 컨테이너를 가리키는 설정이 깨지고, 바깥 접근을 위해 어떤 포트가 어디로 연결됐는지 일일이 기억해야 하는 불편함이 생긴다.

2질문 제기

변경되는 IP 대신 이름으로 컨테이너를 찾게 하고, 컨테이너 안의 서비스를 호스트의 포트로 노출하려면 어떻게 해야 할까?

3구조적 핵심 예시

podman run -p 8080:80 웹서버 처럼 실행하면 호스트의 8080 포트로 들어온 요청이 컨테이너의 80 포트로 전달된다. 그러면 바깥 사용자는 호스트 주소와 8080 포트만 알면 컨테이너 안의 서비스에 접근할 수 있다. 동시에 aardvark-dns(컨테이너 이름을 IP로 바꿔주는 Podman 전용 DNS 서버)가 같은 네트워크 안에서 컨테이너 이름을 IP로 해석해 주므로, 다른 컨테이너는 IP 대신 이름으로 이 컨테이너를 찾을 수 있다.

4단계별 동작 과정

  1. 포트 매핑컨테이너 실행 때 -p 호스트포트:컨테이너포트 로 지정하면 netavark 와 포트 포워딩 규칙이 호스트 포트로 들어온 트래픽을 해당 컨테이너 포트로 전달한다.
  2. 이름 등록컨테이너가 네트워크에 붙으면 aardvark-dns 가 그 네트워크의 DNS(도메인 이름을 IP 주소로 바꿔주는 서비스)에 컨테이너 이름과 IP를 등록한다.
  3. 이름 기반 통신같은 네트워크의 다른 컨테이너가 그 이름을 요청하면 aardvark-dns 가 현재 IP를 돌려주어, IP가 바뀌어도 이름으로 통신이 유지된다.

5본질 요약

7단계 파드·쿠버네티스·매니페스트

1상대의 출발점 확인

컨테이너 하나만으로 서비스를 구성하지 않고, 여러 컨테이너가 함께 동작해야 하는 경우가 많다. 예를 들어 앱 컨테이너와 로그를 수집하는 컨테이너, 설정을 주기적으로 갱신하는 컨테이너가 한 세트로 움직여야 할 때, 각각을 따로 실행하면 네트워크도 따로 배정되어 서로를 어떻게 찾을지, 함께 시작하고 함께 멈추게 하려면 어떻게 할지 매번 관리해야 한다. 컨테이너 수가 늘수록 이 묶음 관리가 반복적인 수작업이 되어 실수가 나기 쉽다.

2질문 제기

여러 컨테이너를 하나의 단위로 묶어 네트워크와 IP를 공유하고 함께 관리하는 방법은 없을까?

3구조적 핵심 예시

podman pod create 로 파드를 만들고, podman run --pod 파드이름 으로 컨테이너를 그 파드에 넣어 실행한다. 같은 파드에 들어간 컨테이너들은 네트워크 네임스페이스(네트워크 구성이 격리되는 공간)를 공유하므로 하나의 IP와 포트 공간을 함께 쓴다. 즉 파드에 할당된 IP 하나로 모든 컨테이너에 접근할 수 있고, 파드를 중지하면 그 안의 컨테이너가 함께 중지된다. 이 구조는 쿠버네티스에서 파드를 다루는 방식과 같은 형태여서 나중에 쿠버네티스로 옮겨갈 때 개념이 그대로 이어진다.

4단계별 동작 과정

  1. 파드 생성podman pod create 로 이름 있는 파드를 만든다. 이때 파드의 네트워크와 IP 대역이 준비된다.
  2. 컨테이너 추가podman run --pod 파드이름 으로 실행하면 컨테이너가 그 파드의 네트워크 네임스페이스에 들어가 파드의 IP를 공유한다.
  3. 파드 단위 관리podman pod start/stop 으로 파드 안의 컨테이너들이 함께 시작·중지되고, podman pod ps 로 파드의 상태를 한눈에 조회한다.

여러 컨테이너가 네트워크와 IP를 공유하는 하나의 논리적 단위인 파드로 묶여 함께 생성·관리·삭제되는 것

7단계 파드·쿠버네티스·매니페스트

컨테이너·파드를 쿠버네티스 YAML로 내보내고(generate kube), 그 YAML을 다시 실행(play kube)해 쿠버네티스로 옮겨 가는 다리 역할을 하는 기능.

1상대의 출발점 확인

Podman 으로 컨테이너와 파드를 실행하면 그 상태는 Podman 만의 저장소에 남는다. 하지만 운영 환경이 쿠버네티스 클러스터라면, Podman 에서 실행 중인 구성을 그대로 쿠버네티스에 옮기려면 파드 정의를 쿠버네티스가 읽는 YAML 형식으로 다시 손으로 작성해야 했다. 같은 구성을 두 형식으로 관리하다 보면 둘 사이가 어긋나고, 옮길 때마다 다시 쓰는 비용이 든다는 한계가 있다.

2질문 제기

실행 중인 Podman 파드 구성에서 쿠버네티스가 바로 실행할 수 있는 YAML 을 만들고, 그 YAML 로 다시 파드를 띄울 수는 없을까?

3구조적 핵심 예시

podman generate kube 명령은 실행 중인 컨테이너나 파드 하나를 지정하면, 그 컨테이너의 이미지·포트·환경변수·볼륨·리소스 설정을 담은 쿠버네티스 Pod YAML 파일을 생성해 출력한다. 그리고 그 파일을 받은 podman play kube 는 YAML 에 적힌 정의를 그대로 읽어 Podman 위에 파드를 생성·실행한다. 즉 한 번의 YAML 이 두 실행 환경 사이를 오가는 공통 형식이다.

4단계별 동작 과정

  1. generate kube 로 내보내기실행 중인 컨테이너나 파드의 설정을 쿠버네티스 Pod YAML 로 변환해 파일로 저장한다.

컨테이너를 실행하려면 podman run 같은 명령을 사람이 직접 입력해야 한다. 이 방식은 터미널이 닫히거나 시스템이 재부팅되면 컨테이너가 다시 실행되지 않고, 컨테이너가 죽었을 때 아무도 자동으로 재시작해 주지 않는다. 서버에서 항상 떠 있어야 하는 서비스라면 매번 수동으로 켜고 끄고 확인하는 일이 반복되며, 재부팅 후 잊어버리면 서비스가 꺼진 채로 방치된다.

2질문 제기

컨테이너를 시스템 부팅 시 자동으로 시작하고, 죽으면 자동으로 재시작하게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

podman generate systemd --new --name myapp 명령을 실행하면 실행 중인 컨테이너의 설정이 담긴 systemd 유닛 파일(시스템이 서비스를 정의하는 설정 파일)이 출력된다. 그 내용을 /etc/systemd/system/myapp-container.service에 저장하고 systemctl enable --now myapp-container로 활성화하면, 이후부터는 리눅스가 부팅할 때 systemd가 이 컨테이너를 자동으로 띄우고, 프로세스가 죽으면 자동으로 다시 시작한다. 컨테이너를 운영체제의 일반 서비스처럼 다루는 것이 핵심이다.

4단계별 동작 과정

  1. 유닛 파일 생성podman generate systemd로 실행 중인 컨테이너의 실행 옵션을 그대로 담은 systemd 유닛 파일을 만든다. --new 옵션을 붙이면 정지된 컨테이너 대신 새 컨테이너를 만들도록 정의되어 재시작이 항상 깨끗한 상태에서 시작한다.
  2. systemd에 등록생성한 유닛 파일을 systemd 디렉터리(예: /etc/systemd/system/)에 두고 systemctl enable --now로 실행한다. enable은 부팅 시 자동 시작을 등록하고 --now는 즉시 시작한다.
  3. 자동 관리이후 systemd가 이 컨테이너의 생명주기를 전부 맡는다. 부팅 시 시작, 종료 시 정리, 크래시 시 재시작, systemctl status로 상태 확인까지 일반 서비스와 동일하게 동작한다.

5본질 요약

컨테이너 실행 명령을 시스템 표준 서비스 정의로 변환해 시작·재시작·상태 관리를 운영체제의 systemd에 위임하는 것

Quadlet

Quadlet은 컨테이너·이미지·볼륨 등을 systemd가 관리하는 선언적 유닛 파일(확장자 .container 등)로 정의해 자동 실행하게 하는 단위 파일 형식이다.

1상대의 출발점 확인

podman generate systemd로 만든 유닛 파일은 실행 명령을 텍스트로 변환한 것이라, 컨테이너 설정을 바꾸려면 유닛 파일을 직접 편집해야 하고 오타가 나면 서비스가 시작되지 않는다. 또한 시스템 디렉터리에 유닛 파일을 직접 복사해야 해서 배포와 버전 관리가 번거롭다. 컨테이너 설정과 systemd 설정이 한 파일에 뒤섞여 있어, 컨테이너만 이해하는 사람이 보기에는 복잡하다.

2질문 제기

복잡한 systemd 유닛 파일을 직접 다루지 않고, 컨테이너 설정만 간단히 적어도 systemd가 자동으로 관리해 주게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

myapp.container라는 파일 하나에 [Container] 섹션에 이미지와 포트, [Service] 섹션에 재시작 정책 정도만 적어 /etc/containers/systemd/에 둔다. 그러면 systemd가 부팅 시 이 파일을 자동으로 읽어 똑같은 내용의 유닛 파일로 변환해 컨테이너 서비스를 시작한다. 설정 파일을 선언적으로(원하는 상태만 적는 방식) 작성하면 systemd가 실행 세부를 채워 넣는 것이 핵심이다.

4단계별 동작 과정

  1. 선언적 파일 작성.container(컨테이너), .image(이미지 빌드), .volume(볼륨) 같은 확장자의 Quadlet 파일에 원하는 상태만 적는다. 예: [Container] Image=quay.io/podman/hello.
  2. 폴더에 배치작성한 파일을 /etc/containers/systemd/(전체 시스템용) 또는 ~/.config/containers/systemd/(사용자용)에 둔다. systemd가 이 디렉터리의 *.container 파일들을 유닛 정의로 인식한다.
  3. 자동 변환 및 관리systemd가 파일들을 유닛 파일로 변환해 등록하고 부팅 시 컨테이너를 시작한다. systemctl start, systemctl enable 같은 표준 systemd 명령으로 그대로 관리할 수 있다.

5본질 요약

컨테이너·볼륨·이미지의 원하는 상태를 짧은 선언적 파일로 적으면 systemd가 자동으로 유닛 파일로 변환해 생명주기를 관리하게 하는 것

자동 업데이트(auto-update)

auto-update는 실행 중인 컨테이너의 이미지를 최신 버전으로 자동 갱신하고 재시작해 주는 기능이다.

1상대의 출발점 확인

컨테이너를 오래 실행하면 이미지에 보안 패치가 나와도 실행 중인 컨테이너는 예전 이미지의 레이어(파일 시스템 변경분)를 계속 쓴다. 새 이미지를 받으려면 사람이 podman pull로 이미지를 내려받고, podman stop과 podman start로 컨테이너를 재시작해야 한다. 서버가 많아지거나 이미지가 자주 갱신되면 이 반복 작업이 누락되기 쉽고, 보안 패치가 적용 안 된 컨테이너가 오래 방치되는 문제가 생긴다.

2질문 제기

실행 중인 컨테이너가 사용하는 이미지를 최신 버전으로 자동으로 바꾸고 재시작까지 하게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

이미지가 갱신될 때 컨테이너도 함께 재시작되도록 컨테이너를 만들 때 --label io.containers.autoupdate=registry 옵션을 붙인다. 그 뒤 podman auto-update 명령을 실행하면 Podman이 등록된 컨테이너들의 이미지를 레지스트리(이미지 저장소)와 비교해 새 버전이 있으면 새 이미지를 받아 그 이미지로 컨테이너를 재시작한다. 이 명령을 systemd 타이머나 크론잡에 걸어 두면 주기적으로 자동 갱신이 일어난다.

4단계별 동작 과정

  1. 자동 업데이트 등록컨테이너를 만들 때 io.containers.autoupdate 레이블(이름표)을 붙여 "이 컨테이너는 업데이트 대상"임을 표시한다. 레이블 값으로 갱신 방식을 지정한다(예: registry는 레지스트리 확인).
  2. 이미지 비교 및 갱신podman auto-update가 업데이트 대상 컨테이너의 이미지와 레지스트리의 최신 이미지를 비교해, 버전이 다르면 새 이미지를 내려받는다.
  3. 컨테이너 재시작새 이미지로 기존 컨테이너를 교체해 재시작한다. 종료된 컨테이너만 대상이 되며, podman auto-update를 주기적으로 실행시키는 스케줄러(예: systemd 타이머)와 함께 쓰면 갱신이 완전히 자동화된다.

5본질 요약

컨테이너에 업데이트 대상 표시를 달아 두고, 명령 한 번으로 최신 이미지를 받아 컨테이너를 재시작해 이미지 갱신 작업을 자동화하는 것

이벤트(events)

events는 컨테이너·이미지·볼륨 등에서 발생한 상태 변화를 실시간으로 스트림으로 내보내는 하위 명령이다.

1상대의 출발점 확인

컨테이너가 언제 시작되고, 죽고, 이미지가 삭제됐는지 확인하려면 podman ps, podman images 같은 명령을 그때그때 실행해 상태를 찍어 봐야 한다. 이런 방식은 지금 순간의 상태만 보여줄 뿐 "언제 어떤 변화가 일어났는지"에 대한 기록은 남지 않는다. 여러 컨테이너를 운영하는 환경에서는 어떤 사건이 어떤 순서로 발생했는지 파악해야 문제 원인을 찾을 수 있는데, 수시로 폴링(주기적으로 상태를 확인하는 방식)하는 것은 늦고 불완전하다.

2질문 제기

컨테이너와 이미지 등에서 발생하는 상태 변화를 놓치지 않고 실시간으로 연속적으로 받아보려면 어떻게 해야 할까?

3구조적 핵심 예시

podman events --filter event=start를 실행하면 그 순간부터 컨테이너가 시작될 때마다 "시간, 컨테이너 이름, event=start" 형식의 이벤트 한 줄이 즉시 출력된다. 다른 터미널에서 podman start web을 실행하면 실시간으로 그 이벤트가 흘러나온다. 터미널에 이어지는 흐름(스트림)으로 출력되므로, 그 출력을 파일로 저장하거나 다른 프로그램에 전달해 기록과 모니터링을 만들 수 있다.

4단계별 동작 과정

  1. 이벤트 수신 시작podman events를 실행하면 Podman이 이벤트 스트림을 연다. --filter로 특정 종류(예: event=start, container=web)만 골라 받을 수 있다.
  2. 사건 발생 시 실시간 전달컨테이너 시작·정지, 이미지 생성·삭제, 볼륨 변경 등 상태 변화가 일어나는 즉시 해당 내용이 시간 순서대로 한 줄씩 출력된다.
  3. 기록·연동출력된 이벤트를 로그 파일에 저장하거나 외부 모니터링 도구로 보내 과거 이력 조회와 실시간 알림에 사용한다. --since 옵션으로 과거 일정 시점부터의 이벤트도 다시 받을 수 있다.

5본질 요약

컨테이너·이미지·볼륨의 모든 상태 변화를 실시간 스트림으로 내보내 운영자는 사건 발생을 즉시 보고 기록할 수 있게 하는 것

머신(machine)

Podman이 관리형 가상머신(Linux VM) 안에서 컨테이너를 실행하게 해주는 기능으로, macOS·Windows에서도 리눅스 컨테이너를 돌릴 수 있게 한다.

1상대의 출발점 확인

컨테이너는 리눅스 커널 기능(네임스페이스, cgroup 등) 위에서 돌아가므로, 리눅스가 아닌 macOS나 Windows에서는 컨테이너를 직접 실행할 수 없다. 그동안은 Docker Desktop 같은 별도 도구가 내부적으로 가상머신을 숨겨서 실행해 주었는데, 이 도구에 종속되면 라이선스·설정·동작 방식이 제조사 정책을 따라야 한다. 개발 환경과 운영 환경의 도구가 달라지면 동작이 달라지는 문제도 생긴다.

2질문 제기

리눅스가 아닌 운영체제에서도 동일한 Podman 명령으로 리눅스 컨테이너를 돌리려면 어떻게 해야 할까?

3구조적 핵심 예시

macOS에서 podman machine init으로 가상머신을 하나 만들고 podman machine start로 켠 뒤, 그냥 평소처럼 podman run을 실행하면 컨테이너가 그 가상머신 안의 리눅스에서 실행된다. 사용자는 가상머신의 존재를 거의 의식하지 않고 로컬에서 podman 명령을 쓰는 것과 똑같이 작업한다. Podman이 가상머신을 하나의 "머신"으로 등록해 두고 모든 명령을 그 머신에 전달하는 것이 핵심이다.

4단계별 동작 과정

  1. 머신 생성podman machine init으로 리눅스 가상머신(예: Fedora 기반 VM)을 생성한다. 이름·CPU·메모리·디스크 크기를 지정할 수 있다.
  2. 머신 시작podman machine start로 가상머신을 부팅하면 Podman이 그 안의 리눅스와 통신 경로를 자동으로 연결한다.
  3. 명령 실행이후의 podman run, podman ps 등 모든 명령이 로컬처럼 동작하되 실제 실행은 가상머신 안에서 일어난다. podman machine list로 여러 머신을 확인하고 전환할 수 있고, podman machine stop으로 끌 수 있다.

5본질 요약

사용자 대신 리눅스 가상머신을 만들어 관리하고 모든 Podman 명령을 그 안에서 실행되게 함으로써, macOS·Windows에서도 동일한 명령으로 리눅스 컨테이너를 다루게 하는 것

팜(farm)

여러 원격 Podman 머신을 하나의 팜으로 묶어 한 번에 빌드·새로고침하는 기능으로, 멀티 아키텍처 이미지 생성을 단순화한다.

1상대의 출발점 확인

여러 CPU 아키텍처(예: amd64와 arm64)를 지원하는 이미지를 만들려면 각 아키텍처용 빌드를 각각 실행해야 한다. 아키텍처별 머신이 따로 있다면 그 머신마다 접속해 빌드 명령을 반복 실행하고, 그 결과물을 레지스트리(이미지 저장소)에 하나의 이미지 태그로 묶어 올려야 한다. 머신 수만큼 명령을 반복하고 결과를 수동으로 합쳐야 해서 누락이나 실수 가능성이 크고, 과정이 길어진다.

2질문 제기

여러 원격 빌드 머신에 일일이 접속하지 않고, 한 번의 명령으로 모든 아키텍처의 이미지를 함께 만들려면 어떻게 해야 할까?

3구조적 핵심 예시

podman farm create buildfarm amd64-host arm64-host로 두 원격 머신을 "팜"으로 묶는다. 그 다음 podman farm build -f Containerfile .을 실행하면 팜에 속한 두 머신에서 동시에 빌드가 일어나고, 각 머신의 결과물이 하나의 매니페스트 리스트(여러 아키텍처 이미지를 한 태그로 묶는 목록)로 합쳐진다. 사용자가 보기에는 명령 한 번으로 멀티 아키텍처 이미지가 완성된다.

4단계별 동작 과정

  2. 팜에서 빌드podman farm build로 팜 안의 모든 머신에 빌드 작업을 분배해 동시에 실행한다.
  3. 결과 병합·푸시각 머신에서 만들어진 아키텍처별 이미지를 하나의 매니페스트 리스트로 결합하고 --push 옵션으로 레지스트리에 한 번에 올려 멀티 아키텍처 이미지를 완성한다.

1상대의 출발점 확인

컨테이너 레지스트리는 원래 컨테이너 이미지만 저장하도록 설계된 저장소다. 이미지 외의 파일(문서, 바이너리, 설정 파일 등)을 팀원끼리 공유하려면 별도의 파일 서버나 스토리지 서비스를 따로 운영해야 했고, 그러면 인증·접근 권한·버전 관리가 이미지와 이중으로 관리되는 문제가 생겼다. 레지스트리에 임의 파일을 넣으려 해도 이미지 형식이 아니라서 표준 도구로는 업로드·다운로드할 방법이 없었다.

2질문 제기

컨테이너 이미지가 아닌 임의의 파일도 컨테이너 레지스트리에 저장하고 내려받게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

OCI 아티팩트는 "임의의 파일을 OCI(Open Container Initiative, 컨테이너 포맷 표준) 아티팩트 형식으로 감싸 레지스트리에 올리는" 기능이다. 예를 들어 배포용 바이너리 파일 하나를 podman artifact add registry.example.com/team/config.tar.gz 같은 명령으로 레지스트리에 올리면, 그 파일은 이미지처럼 레이어로 저장되고 podman artifact pull로 같은 레지스트리 인증을 통해 내려받을 수 있다. 파일 내용이 이미지가 아니어도 저장·조회·삭제가 모두 표준 레지스트리 흐름 안에서 일어난다.

4단계별 동작 과정

  1. 아티팩트 추가(저장)podman artifact add <레지스트리>/<이름>으로 임의 파일을 OCI 아티팩트 형식으로 감싸 레지스트리에 업로드한다.
  2. 아티팩트 조회·내려받기podman artifact list로 저장된 아티팩트를 확인하고, podman artifact pull <레지스트리>/<이름>으로 원하는 파일을 로컬에 내려받는다.
  3. 아티팩트 삭제podman artifact rm <레지스트리>/<이름>으로 더 이상 필요 없는 아티팩트를 레지스트리에서 제거한다.

Podman이 노출하는 REST API(podman system service)와 원격 클라이언트(podman system connection)로, 네트워크 너머의 컨테이너를 제어하는 방법이다.

1상대의 출발점 확인

기존 CLI 방식의 컨테이너 관리는 podman 명령이 실행되는 그 로컬 머신에서만 동작했다. 다른 서버에 떠 있는 컨테이너를 제어하려면 그 서버에 직접 SSH로 접속해 명령을 내리는 수밖에 없었고, 여러 서버를 오가며 관리하는 것은 명령마다 접속 대상이 달라져 혼란스러웠다. 관리 대상이 늘어날수록 접속 방법과 인증 정보가 분산되어 유지보수가 어려웠다.

2질문 제기

한 로컬 명령만으로 네트워크 너머에 있는 컨테이너 엔진을 제어하려면 어떻게 해야 할까?

3구조적 핵심 예시

Podman은 서버 쪽에서 podman system service로 REST API 서버를 띄우고, 클라이언트 쪽에서 podman system connection add로 그 API 주소를 등록하면, 이후 로컬에서 내리는 podman 명령이 SSH나 유닉스 소켓을 통해 원격 서버의 podman으로 전달되어 그쪽 컨테이너를 제어한다. 예를 들어 podman system connection add office-server --host unix:///run/podman/podman.sock으로 연결을 등록하고 podman --connection office-server ps를 실행하면, 로컬에서 입력한 명령 하나가 원격 서버의 컨테이너 목록을 돌려준다.

4단계별 동작 과정

  1. 서비스 노출서버에서 podman system service를 실행해 REST API(HTTP 기반 인터페이스)를 유닉스 소켓이나 TCP 포트로 연다.
  2. 연결 등록클라이언트에서 podman system connection add로 서비스 주소와 접속 방식을 이름 붙여 저장한다.
  3. 원격 명령 실행podman --connection <이름> <명령>으로 로컬 CLI를 그대로 사용하면서 네트워크 너머의 컨테이너를 조작하고 결과를 받아 본다.

5본질 요약

컨테이너 실행 시 SELinux 레이블·seccomp 프로필·리눅스 capabilities로 권한을 제한해 호스트를 보호하는 보안 기법이다.

1상대의 출발점 확인

컨테이너는 프로세스를 격리해 실행하지만, 기본적으로 리눅스 커널의 기능을 그대로 쓸 수 있는 환경을 제공했다. 컨테이너 안에서 실행되는 프로세스에 특별한 제한이 없으면, 호스트의 민감한 기능(파일 접근, 네트워크 조작, 커널 호출)까지 손댈 수 있어 악성 코드나 버그가 호스트 전체를 위험에 빠뜨릴 수 있었다. 격리만으로는 부족하고, 컨테이너 프로세스의 권한 자체를 줄여야 했다.

2질문 제기

컨테이너 안에서 실행되는 프로세스의 권한을 어떻게 제한해 호스트를 보호할 수 있을까?

3구조적 핵심 예시

Podman은 컨테이너 실행 시 세 가지 권한 제한 장치를 함께 적용한다. SELinux(Security-Enhanced Linux, 커널 수준의 강제 접근 제어)는 컨테이너 프로세스에 레이블을 붙여 접근할 수 있는 파일 범위를 좁히고, seccomp(Secure Computing, 시스템 호출 허용 목록)는 컨테이너가 호출할 수 있는 커널 함수를 기본 목록으로 제한하며, capabilities(리눅스 권한 기능)는 root여도 쓸 수 있는 특권(네트워크 원시 소켓, 파일 소유권 변경 등)을 일부만 부여한다. 이 셋이 겹겹이 적용되어 컨테이너가 탈출하거나 남용해도 호스트 쪽 피해가 줄어든다.

4단계별 동작 과정

  1. 레벨 설정podman run --security-opt label=level:...처럼 SELinux 레이블을 지정해 컨테이너 프로세스가 접근 가능한 파일 범위를 제한한다.
  2. 프로필 적용--security-opt seccomp=profile.json로 시스템 호출 허용 목록을 지정하거나 기본 seccomp 프로필을 적용해 커널 호출을 제한한다.
  3. 권한 축소 실행--cap-drop로 불필요한 capabilities를 제거한 상태로 컨테이너를 실행해, root로 돌아도 갖지 못하는 특권이 생기게 한다.
