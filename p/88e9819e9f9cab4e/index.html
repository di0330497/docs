1S3라는 대상 이해하기01-01

Amazon S3란 무엇인가 — 객체 스토리지와 대표 사용 사례

S3는 파일을 '객체' 단위로 인터넷 상에 무제한 저장하고 꺼내 쓰는 AWS의 객체 스토리지 서비스로, 백업·데이터 레이크·정적 웹사이트 호스팅 등에 쓰인다.

1상대의 출발점 확인

기존에는 파일을 저장할 때 서버의 하드 드라이브에 폴더 구조로 정렬해서 보관했습니다. 폴더가 깊어지고 파일이 많아질수록 관리가 복잡해지고, 저장 공간을 늘리려면 물리적인 서버를 추가해야 했습니다. 또한 파일에 접근할 때마다 서버 위치에 따라 속도가 달라지는 문제가 있었습니다.

2질문 제기

폴더 구조 없이 인터넷 어디에서나 같은 속도로 수조 개의 파일을 저장하고 꺼낼 수 있는 방법이 있을까요?

3구조적 핵심 예시

S3에서는 파일을 버킷(bucket)이라는 독립적인 상자에 객체(object)라는 단위로 넣고, 이 객체를 고유한 이름(키)으로 지목해서 꺼냅니다. 폴더 구조가 없어도 키 이름 안에 슬래시를 넣으면 마치 폴더처럼 보입니다. 예를 들어 "images/photo/sunset.jpg"와 "documents/report/2024.pdf"는 실제로는 같은 버킷 안의 두 객체일 뿐이고, S3가 이들을 바로 찾아냅니다.

4단계별 동작 과정

  1. 객체 저장파일과 메타데이터(파일 크기, 생성 시간 등)를 객체로 만들어 버킷에 업로드하면 S3가 전 세계 여러 데이터센터에 복제본을 자동으로 보관합니다.

3구조적 핵심 예시

  2. 즉시 일관성 보장성공 응답을 받은 직후에 다른 클라이언트가 그 객체를 읽거나 목록을 조회하면 항상 최신 결과를 얻습니다.
  3. 복제본 투명성클라이언트는 백그라운드의 복제 상황을 신경 쓸 필요 없이 하나의 S3 서비스와 상호작용하는 것처럼 동작합니다.

2질문 제기

  2. S3로 전송요청을 S3로 보낸다. 다중 삭제면 한 번의 HTTP 요청으로 여러 객체 삭제 명령이 전달된다.

3구조적 핵심 예시

  2. 태그 적용객체 생성 후 별도 요청으로 태그를 붙인다. 같은 객체에 최대 10개의 키-값 쌍을 달 수 있다.

1상대의 출발점 확인

2질문 제기

3구조적 핵심 예시

조건부 요청은 요청에 "이 ETag를 가진 객체에만 쓰기" 같은 조건을 담아서 그 조건이 맞지 않으면 S3가 요청을 거부하는 방식이고, 프리사인 URL은 서버가 미리 서명한 URL을 클라이언트에게 주어서 그 URL이 유효한 시간 동안만 자격 증명 없이 접근할 수 있게 하는 방식이다.

4단계별 동작 과정

  1. 조건부 요청 작성클라이언트가 요청에 If-Match(특정 ETag일 때만), If-None-Match(ETag가 다를 때만) 같은 조건을 포함시킨다.
  2. S3가 조건 평가S3가 요청 조건을 확인하고, 맞지 않으면 412 Precondition Failed 오류를 반환한다.
  3. 프리사인 URL 생성 및 사용서버가 미리 요청을 서명해서 URL을 만들고, 클라이언트가 일정 시간(예: 1시간) 동안 그 URL로 인증 없이 접근한다.

S3가 수많은 권한 규칙 중에서 어떤 순서로 확인해 요청을 최종 허용하거나 거부할까?

3구조적 핵심 예시

S3는 요청이 들어오면 먼저 계정 소유자인지 확인하고, 다음으로 IAM 정책으로 명시적 거부가 있는지 확인한다. 거부가 없으면 버킷 정책과 객체 ACL을 함께 평가해서 명시적 허용이 있으면 통과시킨다.

4단계별 동작 과정

  1. 계정 소유자 확인요청이 AWS 계정에 속하는지, 루트 계정인지, IAM 사용자인지, 외부인지를 먼저 확인한다.
  2. 명시적 거부 우선 평가어떤 정책이든 명시적으로 거부(Deny)가 있으면 그 단계에서 즉시 거부한다. 따라서 거부 정책이 다른 모든 허용(Allow)보다 우선된다.
  3. 허용 정책 평가명시적 거부가 없으면 IAM 정책, 버킷 정책, 객체 ACL을 모두 합쳐서 하나라도 명시적 허용(Allow)이 있으면 요청을 통과시킨다.

2질문 제기

3구조적 핵심 예시

IAM 정책 문서는 JSON 형식으로 작성되며, 주요 필드는 Effect(Allow/Deny), Principal(누가), Action(무엇을 하는가), Resource(어디에서)이다. 예를 들어 특정 IAM 사용자에게만 s3:GetObject와 s3:PutObject 권한을 주려면, 정책의 Action 배열에 이 두 작업을 명시하고 Resource에 특정 버킷과 객체 경로를 지정한다.

  3. 요청 시 권한 검증클라이언트가 S3에 요청을 보낼 때 AWS는 요청자의 신원(사용자/역할)과 요청한 작업(Action)이 연결된 정책에 있는지 확인하고, 없으면 거부한다.

버킷 정책 작성과 대표 예제

버킷 자체에 붙이는 JSON 리소스 정책으로 누가 어떤 작업을 할 수 있는지 선언하는 방법과 자주 쓰는 예제들

1상대의 출발점 확인

IAM 정책은 사용자나 역할에 붙이는 방식이므로, 각 사용자별로 정책을 관리해야 한다. 하지만 버킷 자체에 접근하는 모든 요청에 대해 공통 규칙을 적용하려면 (예: 특정 IP 대역만 허용, 특정 AWS 계정만 접근 허용) 모든 사용자의 정책을 수정해야 한다. 이는 유지 보수가 어렵고 불일치가 발생하기 쉽다.

2질문 제기

버킷에 접근하는 모든 요청에 대해 일괄적으로 규칙을 적용하고 한 곳에서만 관리할 수 있을까?

3구조적 핵심 예시

버킷 정책은 버킷 자체에 붙는 JSON 형식의 리소스 정책(Resource Policy)로, Principal 필드에서 접근을 허용할 AWS 계정·IAM 사용자·역할을 지정하고, Action에서 허용할 S3 작업을 명시한다. 예를 들어 "AWS 계정 123456789012의 모든 사용자에게만 s3:GetObject를 허용한다"는 규칙을 버킷 정책에 적으면, 그 계정의 누구든 GetObject 요청을 하면 정책에서 먼저 검증된다.

4단계별 동작 과정

  1. 버킷 정책 JSON 작성Principal에서 누가(AWS 계정, IAM 사용자, 역할, *는 모두)를 지정하고, Action에서 무엇을 허용할지(s3:GetObject, s3:PutObject 등), Resource에서 어느 버킷과 객체를 대상으로 할지 선언한다.
  2. 버킷에 정책 연결작성한 정책을 버킷의 Bucket Policy 설정에 저장하면, 그 정책이 버킷에 적용된다.
  3. 모든 요청에 정책 적용클라이언트가 버킷에 접근할 때마다 AWS는 버킷 정책을 먼저 확인하고, 요청자와 요청 작업이 정책에 일치하면 허용, 아니면 거부한다.

4단계별 동작 과정

  2. 조건 연산자 지정StringEquals, IpAddress, Bool 같은 연산자로 조건 키 값이 일치하는지 판단한다.
  3. 조건 검증 후 권한 적용클라이언트 요청이 들어올 때 Principal과 Action이 맞더라도 Condition의 모든 조건이 참이어야만 최종적으로 권한이 허용된다.

퍼블릭 액세스 차단(Block Public Access) 설정

실수로 공개된 정책이나 ACL이 있어도 버킷·계정 수준에서 퍼블릭 접근을 일괄로 막아주는 안전장치

1상대의 출발점 확인

정책과 ACL(접근 제어 목록)이 올바르게 설정되지 않으면 실수로 버킷이나 객체가 공개되는 경우가 생긴다. 이런 실수를 사후에 발견하고 수정하는 것은 어려울 수 있고, 그 사이 민감한 데이터가 노출될 수 있다.

2질문 제기

정책이나 ACL 설정 실수로 공개 접근이 허용되더라도 이를 막을 수 있을까?

3구조적 핵심 예시

Block Public Access 기능은 AWS 계정 전체 또는 특정 버킷 수준에서 네 가지 플래그(BlockPublicAcls, IgnorePublicAcls, BlockPublicPolicy, RestrictPublicBuckets)를 켤 수 있다. 이 중 하나라도 활성화되면 정책이나 ACL에서 공개 권한이 있어도 AWS가 이를 무시하고 공개 접근을 차단한다.

4단계별 동작 과정

  1. Block Public Access 설정 활성화계정 또는 버킷의 Block Public Access 설정에서 필요한 플래그를 켠다.
  2. 공개 정책·ACL 자동 차단이후 어떤 정책이나 ACL이 공개 권한을 주더라도 AWS는 이를 무시하고 실제 공개 접근을 차단한다.
  3. 결과적으로 버킷 내 모든 객체 비공개플래그가 켜져 있는 한, 정책·ACL과 무관하게 버킷과 그 안의 객체는 항상 프라이빗이다.

객체 소유권과 ACL 비활성화

→ 04-07 참조

1상대의 출발점 확인

여러 AWS 계정의 사용자나 애플리케이션이 하나의 버킷에 파일을 업로드할 때, 기본적으로는 업로드한 사용자의 계정이 그 객체의 소유자가 된다. 이렇게 되면 객체마다 소유자가 다르고, ACL을 통해 소유자별로 권한을 관리해야 하므로 복잡해진다.

2질문 제기

버킷에 여러 계정이 업로드할 때 모든 객체의 소유권을 버킷 소유 계정으로 통일하고 정책만으로 권한을 관리할 수 있을까?

3구조적 핵심 예시

4단계별 동작 과정

  1. ObjectOwnership 설정 활성화버킷의 Object Ownership을 BucketOwnerEnforced로 설정한다.
  2. 업로드 객체의 소유권 강제이후 모든 업로드된 객체의 소유자가 버킷 소유 계정으로 통일되고, 객체별 ACL은 자동으로 무시된다.
  3. 정책만으로 접근 제어이제 객체 접근은 IAM 정책과 버킷 정책으로만 제어되므로, 권한 관리가 일원화되고 단순해진다.

ACL 개요와 구성 — 언제만 쓰는가

버킷·객체마다 붙는 옛 방식의 접근 목록으로, 지금은 특수한 경우에만 권장되는 권한 수단

→ 04-06 참조

1상대의 출발점 확인

초기 S3에서는 ACL만으로 권한을 관리했다. 나중에 IAM 정책과 버킷 정책이 추가되면서 더 유연한 권한 관리가 가능해졌지만, 하위 호환성을 위해 ACL도 여전히 지원된다. 이제는 두 방식이 함께 존재하므로 혼동이 생기고, 언제 ACL을 써야 하는지 불명확하다.

2질문 제기

ACL은 정책과 어떻게 다르고, 언제 여전히 필요한가?

3구조적 핵심 예시

ACL은 버킷 또는 객체마다 Grantee(권한을 받는 대상)별로 READ, WRITE, FULL_CONTROL을 직접 지정하는 옛 방식이다. 반면 정책은 Principal(누가)과 Action(무엇)을 나열하는 선언적 방식이다. ACL은 대상당 권한이 세 가지로만 한정되지만 정책은 수십 개의 세부 작업을 제어할 수 있다.

4단계별 동작 과정

  1. ACL 권한 유형 이해ACL에서는 각 Grantee에게 READ(읽기), WRITE(쓰기), FULL_CONTROL(전체)만 할당 가능하다.
  2. 정책 기반과의 차이 확인정책은 더 세밀한 작업 제어가 가능하고 조건도 추가할 수 있으므로 대부분의 경우 정책이 선호된다.
  3. 필요시만 ACL 활성화여러 계정의 업로드자가 각각의 객체를 소유하고 소유자가 자신의 객체에 대해서만 권한을 관리해야 하는 멀티테넌시 시나리오나 로깅 버킷 설정 같은 특수한 경우에만 ACL을 활성화한다.

3구조적 핵심 예시

  2. 암호화와 버전 관리저장된 데이터는 암호화 키로 암호화하고, 객체 버전 관리를 켜 의도하지 않은 삭제·덮어쓰기로부터 복구한다.

1상대의 출발점 확인

기존에는 데이터를 S3에 올릴 때 암호화를 하지 않으면 평문으로 저장되었다. 암호화를 적용하려면 매번 업로드 요청 때마다 암호화 옵션을 지정해야 했고, 실수로 빼먹으면 보안이 약해진다. 조직 규모가 커지면서 모든 업로드에서 암호화를 빠짐없이 강제하기가 어려워진다.

2질문 제기

S3에 올라간 데이터를 자동으로 암호화해 저장하고, 관리 부담을 줄일 수 있을까?

3구조적 핵심 예시

S3 기본 암호화(Default Encryption)는 버킷에 "새로 올라오는 모든 객체는 이 암호화 방식으로 암호화하라"고 한 번 설정해두는 것이다. 그러면 사용자가 요청 때 암호화 옵션을 지정하지 않아도 자동으로 S3 서버가 저장 전에 암호화한다.

4단계별 동작 과정

  1. 버킷 기본 암호화 설정버킷의 속성에서 암호화 방식(SSE-S3, SSE-KMS, DSSE-KMS 등)을 선택해 저장한다.
  2. 업로드 시 자동 암호화사용자가 데이터를 업로드할 때, 요청에 암호화 옵션이 없으면 버킷의 기본 설정이 자동으로 적용된다.
  3. 저장된 데이터 암호화S3는 데이터를 디스크에 쓰기 전에 선택된 암호화 키로 암호화해 저장한다.

SSE-S3와 SSE-KMS 지정하기

S3 관리 키(SSE-S3)와 AWS KMS 키(SSE-KMS) 중 무엇으로 암호화할지 요청·버킷 설정에서 지정하는 방법.

1상대의 출발점 확인

S3 암호화는 여러 방식이 있다. 암호화 키를 누가 관리하느냐에 따라 보안 수준과 관리 복잡도, 비용이 달라진다. 단순히 "암호화하기"만으로는 부족하고, 어떤 방식으로 암호화할지 선택해야 한다. 조직마다 데이터 분류와 보안 정책이 다르기 때문에 선택지가 필요하다.

2질문 제기

S3에서 암호화할 때, 암호화 키를 S3가 관리하게 할지 아니면 내 조직의 AWS KMS(Key Management Service)로 관리할지 어떻게 선택할까?

3구조적 핵심 예시

SSE-S3(S3 관리형 암호화)는 S3가 모든 암호화 키를 자동으로 만들고 관리하기 때문에 간단하고 추가 비용이 없지만, 내가 암호화 키를 제어할 수 없다. SSE-KMS(KMS 관리형 암호화)는 내가 AWS KMS에서 암호화 키를 만들고 관리하기 때문에 누가 데이터를 접근할 수 있는지 더 세밀하게 제어할 수 있지만, KMS 사용 비용이 발생한다.

4단계별 동작 과정

  1. 암호화 방식 선택버킷 기본 암호화 설정에서 SSE-S3 또는 SSE-KMS 중 하나를 선택한다.
  2. 암호화 키 준비SSE-S3는 S3가 자동 관리하고, SSE-KMS는 먼저 KMS에서 마스터 암호화 키를 만들어둔다.
  3. 데이터 암호화업로드 또는 버킷 기본 설정이 적용될 때, 선택된 방식으로 데이터가 암호화되어 저장된다.

5본질 요약

SSE-S3로 간편함을 택하거나 SSE-KMS로 세밀한 키 관리와 접근 제어를 택하는 선택지를 제공해, 보안 요구와 비용·관리 부담의 균형을 맞추게 하는 것

S3 버킷 키와 DSSE-KMS

KMS 호출 비용을 줄여주는 S3 버킷 키와, 두 겹으로 암호화하는 DSSE-KMS 옵션.

1상대의 출발점 확인

SSE-KMS로 암호화할 때, 매번 데이터를 암호화·복호화할 때마다 KMS 서비스를 호출해야 한다. KMS 호출에는 비용이 들고, 호출 빈도가 높으면 API 레이트 제한에 걸릴 수 있다. 또한 데이터 보안이 매우 중요한 경우 암호화 계층을 여러 겹으로 해야 할 필요도 있다.

2질문 제기

KMS 호출 비용을 줄이면서도, 더 높은 보안이 필요한 경우 추가 암호화 계층을 어떻게 적용할까?

3구조적 핵심 예시

S3 버킷 키(S3 Bucket Key)는 KMS 마스터 키에서 임시로 생성된 단기 키를 각 버킷별로 유지해, 매번 KMS를 호출하지 않고도 S3 내부에서 빠르게 데이터를 암호화·복호화한다. DSSE-KMS(Double-Layer Server-Side Encryption with KMS)는 KMS 키로 한 번 암호화한 후, S3 관리형 키로 다시 한 번 더 암호화해 두 계층의 보호를 제공한다.

4단계별 동작 과정

  1. S3 버킷 키 활성화버킷 기본 암호화에서 S3 버킷 키 옵션을 켜면, S3가 KMS 마스터 키로부터 단기 버킷 키를 만들어 재사용한다.
  2. DSSE-KMS 선택추가 보안이 필요하면 암호화 방식을 DSSE-KMS로 설정해, KMS 키로 먼저 암호화한 후 S3 관리형 키로 다시 암호화한다.
  3. 비용 절감과 보안 강화버킷 키로 KMS 호출 횟수를 줄여 비용을 절감하고, DSSE-KMS로 추가 보호를 동시에 달성한다.

SSE-C와 클라이언트 측·전송 중 암호화

내가 제공한 키로 암호화하는 SSE-C, 업로드 전에 직접 암호화하는 클라이언트 측 암호화, 그리고 HTTPS/TLS로 지키는 전송 중 암호화.

1상대의 출발점 확인

기존의 서버 측 암호화(SSE-S3, SSE-KMS)는 S3 서버가 암호화를 담당하기 때문에, 내 조직이 암호화 키를 완전히 제어할 수 없다. S3가 키를 보관하고 있으므로 만약 AWS 인프라가 침해되면 키가 노출될 위험이 있다. 또한 데이터 업로드 과정에서 인터넷을 거칠 때 암호화되지 않은 상태로 전송되면 중간에 탈취될 수 있다.

2질문 제기

암호화 키를 완전히 내가 관리하고, 업로드 과정에서도 데이터를 암호화해 보호할 수 있을까?

3구조적 핵심 예시

SSE-C(고객 제공 키)는 내가 제공한 암호화 키를 S3에 전달해, S3 서버가 그 키로만 데이터를 암호화해 저장하고, S3 자신도 그 키를 보관하지 않는다. 클라이언트 측 암호화는 데이터를 S3로 보내기 전에 내 애플리케이션에서 먼저 암호화한다. 전송 중 암호화는 HTTPS/TLS 프로토콜로 업로드·다운로드 과정 전체를 암호화한다.

4단계별 동작 과정

  1. SSE-C 사용키 제공** — 내가 생성한 암호화 키를 HTTPS를 통해 S3로 전달하고, S3는 그 키로만 데이터를 암호화해 저장한다. 이후 복호화할 때도 동일한 키를 제공해야만 접근 가능하다.
  2. 클라이언트 측 암호화업로드 전 암호화** — 내 애플리케이션이 데이터를 먼저 암호화한 후, 암호화된 상태로 S3로 전송한다.
  3. 전송 중 암호화HTTPS/TLS 적용** — 업로드·다운로드 시 HTTPS를 사용해 인터넷 구간에서 데이터가 암호화된 상태로 전달된다.

S3 버전 관리 — 버전·삭제 마커·MFA 삭제

같은 키의 객체를 여러 버전으로 보관해 덮어쓰기·삭제로부터 복구하게 해주는 기능과 삭제 마커·MFA 삭제 보호.

1상대의 출발점 확인

기존에는 같은 이름의 파일을 S3에 올리면 덮어써진다. 실수로 잘못된 파일을 올리거나 누군가 파일을 삭제해도 복구할 수 없다. 또한 데이터 규정 준수를 위해 의도하지 않은 변경·삭제로부터 보호가 필요하지만, 기본 S3만으로는 불가능하다. 특히 중요한 데이터의 경우 실수로 인한 영구 삭제로부터 보호하려면 별도의 메커니즘이 필요하다.

2질문 제기

같은 이름의 파일을 여러 번 올릴 때 이전 버전을 보관했다가 필요하면 복구할 수 있을까?

3구조적 핵심 예시

S3 버전 관리(Versioning)를 켜면, 같은 키(파일 이름)로 여러 번 올린 객체가 각각 다른 버전 ID를 받아 모두 보관된다. 파일을 삭제하면 "삭제 마커(Delete Marker)"가 붙어 최신 상태를 "삭제됨"으로 표시하지만, 이전 버전은 남아있다. MFA 삭제(MFA Delete)는 버킷 소유자의 계정에 MFA 인증을 요구해서만 객체를 영구 삭제하게 하는 보호 기능이다.

4단계별 동작 과정

  1. 버전 관리 활성화버킷의 버전 관리 속성을 켜면, 이후 올라오는 모든 객체가 고유한 버전 ID를 받고, 같은 키로 다시 올려도 덮어쓰지 않고 새 버전으로 저장된다.
  2. 삭제 마커와 복구객체를 삭제하면 삭제 마커가 생겨 최신 상태가 "삭제됨"이 되지만, 이전 버전들은 S3에 남아있어 필요시 특정 버전을 다시 활성화해 복구할 수 있다.
  3. MFA 삭제 설정우발적이거나 악의적인 영구 삭제를 방지하기 위해 버킷 소유자의 MFA 인증 없이는 버전을 삭제할 수 없게 설정한다.

3구조적 핵심 예시

S3는 접근 빈도별로 여러 클래스를 제공합니다. Standard는 즉시 접근(비쌈), IA(Infrequent Access)는 한 달에 몇 번 정도(더 싸지만 조회 비용 발생), Glacier는 거의 안 쓰는 장기 보관(아주 싸지만 복원 시간 필요)처럼, 사용 패턴에 맞춰 고르면 됩니다.

4단계별 동작 과정

  1. 각 클래스의 비용 구조 이해저장료(1GB당 월 비용), 최소 저장 기간(IA는 30일, Glacier는 90일 이상), 조회 비용(검색/다운로드 시 추가 요금)을 비교합니다.
  2. 데이터 접근 패턴 분석데이터마다 월 접근 빈도, 접근 예정 기간, 언제부터 보관용이 되는지를 파악합니다.
  3. 적절한 클래스 선택자주 쓰는 데이터는 Standard, 가끔 쓰는 것은 IA, 거의 안 쓰는 것은 Glacier로 저장해 총 비용을 최적화합니다.

→ 06-01 참조

1상대의 출발점 확인

여러 스토리지 클래스 중 하나를 선택해 저장하면, 그 이후 접근 패턴이 바뀌어도 클래스는 바뀌지 않습니다. 처음에는 자주 쓰던 데이터가 시간이 지나 거의 안 쓰게 되어도 여전히 Standard 요금을 내야 합니다. 접근 패턴 변화에 맞춰 수동으로 클래스를 옮기는 것은 번거롭습니다.

2질문 제기

3구조적 핵심 예시

Intelligent-Tiering으로 저장한 객체는 내부적으로 여러 계층을 가지고 있습니다. S3가 매일 접근 횟수를 세다가, 자주 쓰면 Frequent 계층에 유지하고, 30일간 안 쓰면 Infrequent 계층으로 자동 이동, 90일을 넘으면 Archive 계층으로 옮깁니다. 사람이 손을 댈 필요가 없습니다.

4단계별 동작 과정

  1. 객체 클래스를 Intelligent-Tiering으로 설정업로드하거나 기존 객체를 복사할 때 스토리지 클래스로 Intelligent-Tiering을 지정합니다.
  2. S3가 자동으로 접근 패턴 모니터링S3가 객체마다의 최종 접근 일시를 추적하고, 설정된 주기(기본 30일, 90일 등)를 기준으로 계층 이동 판단을 매일 수행합니다.
  3. 빈도에 따라 계층 자동 전환조건을 충족하면 객체는 투명하게 다음 계층으로 이동하고, 다시 접근되면 Frequent 계층으로 복귀합니다.

1상대의 출발점 확인

2질문 제기

거의 꺼내지 않을 데이터를 아주 저렴하게 저장했다가 필요할 때 꺼낼 수 있을까요?

3구조적 핵심 예시

Glacier는 장기 보관 전용 저장소입니다. 월 저장료가 Standard의 1/10 수준으로 아주 싸지만, 저장된 객체를 다시 읽으려면 먼저 "복원(restore)" 요청을 해서 몇 분~몇 시간 동안 데이터를 활성화한 후 접근합니다.

  2. 필요하면 복원 요청Glacier에 저장된 객체가 필요해지면 복원 요청을 하고, 복원 속도(표준 3~5시간, 신속 1분 등)를 선택합니다.
  3. 복원 완료 후 임시 접근요청한 복원 속도만큼 기다리면 객체가 임시로 활성화되어 다운로드할 수 있으며, 설정된 기간 후 다시 아카이브됩니다.

1상대의 출발점 확인

2질문 제기

1상대의 출발점 확인

3구조적 핵심 예시

3구조적 핵심 예시

  2. 이벤트 발생 시 자동 전달객체가 업로드되거나 삭제되는 순간 S3이 그 이벤트를 정의된 목적지로 즉시 보냅니다.

S3 버킷이 많아지면 각 버킷마다 얼마나 저장 공간을 쓰는지, 어느 객체가 자주 접근되는지를 파악하기 어렵다. CloudWatch 메트릭을 보려면 기본 메트릭(버킷당 저장 크기, 객체 수)만 나오고, 버킷별·프리픽스별·스토리지 클래스별 상세 비교와 비용 분석이 곤란하다. 특히 조직 전체의 리소스 사용 현황을 한눈에 보고 어디가 낭비되는지 찾기 어렵다.

3구조적 핵심 예시

  2. 그룹별 집계수집한 메트릭을 Storage Lens 그룹(계정, 리전, 버킷 이름 패턴, 스토리지 클래스, 태그 등)으로 분류해서 각 그룹의 합계를 계산한다.
  3. 대시보드 시각화각 그룹의 합계, 추이, 이상 징후를 그래프와 수치로 표시해서 버킷 간 비교와 의사결정을 가능하게 한다.

  2. 병렬 전송과 바이트 범위Multipart Upload로 한 파일을 여러 청크로 나눠 동시에 올린다. 다운로드 때도 바이트 범위 요청(HTTP Range 헤더)으로 일부만 받아 병렬 다운로드를 한다.
  3. 재시도 조정실패한 요청의 재시도 간격을 지수 백오프(점점 더 오래 기다렸다 다시 시도하는 알고리즘)로 조정해서 S3 과부하를 피한다.

Mountpoint for S3와 Storage Browser for S3

S3 버킷을 로컬 파일 시스템처럼 마운트해 읽고 쓰는 Mountpoint와, 웹 앱에 끼워 넣는 S3 데이터 탐색 UI 컴포넌트인 Storage Browser다.

1상대의 출발점 확인

개발자가 S3 데이터를 쓰려면 AWS SDK나 CLI로 명령을 입력해야 한다. S3는 객체 스토리지이지 파일 시스템이 아니라서, 일반 파일 탐색 프로그램(Windows 탐색기, Mac Finder)에서 직접 폴더를 열고 드래그 앤 드롭으로 저장할 수 없다. 웹 애플리케이션에 S3 데이터를 탐색할 UI를 넣으려면 프론트엔드를 직접 만들어야 한다.

2질문 제기

S3 데이터를 파일 시스템처럼 사용하거나 웹 앱에서 쉽게 탐색할 수 있는가?

3구조적 핵심 예시

Mountpoint for S3로 리눅스 서버에 S3 버킷을 로컬 경로("/mnt/mybucket/")로 마운트한다. 그러면 find, cp, cat 같은 일반 리눅스 명령어로 S3 데이터를 다룬다. Storage Browser for S3는 리액트 라이브러리로, 웹앱에 S3 파일 탐색 UI(폴더 구조, 미리보기, 업로드 버튼)를 내장한다.

4단계별 동작 과정

  1. 마운트 설정Mountpoint for S3 에이전트를 EC2나 온프레미스 서버에 설치하고 S3 버킷을 로컬 파일 시스템 경로로 마운트한다.
  2. 파일 시스템 인터페이스 제공마운트된 경로에서 표준 파일 명령(ls, cp, rm, cat)과 POSIX 권한 모델을 사용한다. 데이터는 여전히 S3에 저장되어 있다.
  3. 웹 앱 UI 통합Storage Browser 컴포넌트를 리액트 앱에 임포트하고 버킷 정보를 설정하면, 사용자가 웹에서 S3 파일을 탐색·다운로드·업로드할 수 있는 UI가 자동으로 나타난다.

5본질 요약

Mountpoint for S3가 S3 버킷을 로컬 파일 시스템처럼 마운트해 표준 파일 명령을 쓸 수 있게 하고, Storage Browser for S3는 웹 앱에 끼워 넣을 수 있는 S3 데이터 탐색 UI 컴포넌트로, 둘 다 S3의 객체 스토리지 특성을 파일 시스템처럼 쉽게 사용하도록 추상화하는 도구다

기존 S3 범용 버킷은 객체를 여러 가용 영역(데이터 센터)에 자동으로 분산 저장하고, 모든 객체를 평면 네임스페이스(flat namespace)로 관리합니다. "folder/" 같은 폴더 구조는 실제로는 키 이름의 접두사일 뿐, 데이터 저장 구조와는 무관합니다. 이 방식은 높은 내구성과 가용성을 제공하지만, 단일 데이터 센터 내에서의 초저지연 접근이나 실제 디렉터리 기반 계층 구조가 필요한 경우에는 최적화되지 않습니다.

2질문 제기

한 가용 영역 내에서 밀리초 단위 초저지연 접근을 하면서 동시에 실제 계층형 디렉터리 구조를 사용하려면 어떻게 해야 할까요?

3구조적 핵심 예시

디렉터리 버킷은 단일 가용 영역에만 데이터를 저장하고, 객체 키를 실제 디렉터리 경로로 처리합니다. 예를 들어 "logs/2024/january/app.log"라는 키를 저장하면, S3가 내부적으로 이 경로를 실제 디렉터리 구조로 관리하므로 경로 기반의 작업이 더 효율적입니다.

4단계별 동작 과정

  1. 저장 위치 제약디렉터리 버킷의 모든 데이터는 지정한 한 가용 영역이나 Local Zone(일부 리전의 엣지 로케이션)에만 저장되어 지연 시간이 크게 줄어듭니다.
  2. 계층형 키 구조객체 키를 디렉터리 경로처럼 처리하므로, 경로 기반의 작업(예: "logs/" 아래 모든 객체 조회)이 범용 버킷보다 빠르고 효율적입니다.
  3. API와 기능의 차이디렉터리 버킷은 CreateSession 인증, RenameObject(이름 변경), AppendObject(객체에 추가) 같은 확장 API를 지원하지만, 버킷 정책이나 일부 복제 기능은 제한됩니다.

CORS 구성과 문제 해결

다른 도메인의 웹 페이지에서 내 버킷 리소스를 브라우저로 호출할 수 있게 허용 규칙(CORS)을 정의하고 차단 문제를 진단하는 방법.

1상대의 출발점 확인

브라우저는 보안상 다른 도메인으로의 요청을 기본 차단합니다(Same-Origin Policy). 내 웹사이트(예: example.com)가 호스팅된 HTML 페이지에서 JavaScript로 S3 버킷(s3.amazonaws.com)의 이미지나 파일을 직접 호출하려고 하면 브라우저가 차단합니다.

2질문 제기

다른 도메인의 웹 페이지에서 S3 리소스를 안전하게 접근하게 하려면?

3구조적 핵심 예시

S3 버킷에 CORS 규칙을 설정하면, 특정 도메인(예: example.com)의 브라우저 요청을 허용합니다. CORS 규칙에는 어느 도메인에서 요청이 올 수 있는지(AllowedOrigins), 어떤 HTTP 메서드를 허용할지(AllowedMethods), 어떤 헤더를 포함할 수 있는지(AllowedHeaders) 등을 명시합니다.

4단계별 동작 과정

  1. CORS 규칙 정의버킷의 CORS 구성에 허용할 도메인, HTTP 메서드(GET, PUT 등), 요청/응답 헤더를 명시합니다.
  2. 브라우저의 사전 요청(Preflight)브라우저가 실제 요청 전에 OPTIONS 메서드로 해당 도메인이 허용 목록에 있는지 S3에 확인합니다.
  3. 요청 처리S3가 CORS 규칙에서 요청 도메인을 찾으면 Access-Control-Allow-* 헤더를 응답에 포함해 브라우저가 요청을 완료하도록 허용합니다.

1상대의 출발점 확인

2질문 제기

4단계별 동작 과정

  1. Multi-Region Access Point 설정여러 리전의 S3 버킷을 하나의 Multi-Region Access Point로 등록합니다.
  2. 요청 라우팅클라이언트가 전역 엔드포인트로 요청을 보내면, S3 인프라가 클라이언트의 위치와 각 리전의 네트워크 지연시간을 측정해 가장 최적의 리전으로 요청을 라우팅합니다.
  3. 장애 자동 전환선택된 리전에 문제가 발생하면 S3가 자동으로 다른 정상 리전으로 요청을 재라우팅합니다.

5본질 요약

여러 리전의 버킷을 하나의 전역 엔드포인트로 통합하고 지연시간 최소화 및 장애 자동 전환을 제공하는 것
