Docker의 정의와 아키텍처

Docker는 애플리케이션을 컨테이너로 패키징·배포·실행하는 개방형 플랫폼으로, 클라이언트·데몬·레지스트리 등의 구성요소가 협력해 동작한다.

#1문제 상황

애플리케이션을 실행하려면 그 앱이 필요로 하는 런타임, 라이브러리, 설정을 실행할 컴퓨터마다 직접 준비해야 한다. 개발자 컴퓨터와 서버의 설치 상태가 조금만 달라도 앱은 다르게 동작하고, 코드를 작성한 시점과 실제로 돌아가는 시점 사이에는 긴 지연이 생긴다.

#2핵심 질문

애플리케이션과 그것이 실행되는 인프라를 분리해, 어디서든 같은 방식으로 실행하려면 어떻게 해야 하는가?

#3동작 예시

컨테이너는 앱과 그 실행에 필요한 것들을 함께 담은 가볍고 격리된 환경이다. 이 격리 덕분에 한 호스트 위에서 여러 컨테이너를 동시에 돌릴 수 있고, 컨테이너를 공유하면 받은 쪽도 같은 방식으로 동작하는 같은 컨테이너를 얻는다. 실행에 필요한 것이 컨테이너 안에 들어 있으므로 호스트에 무엇이 설치돼 있는지에 의존하지 않는다.

#4동작 과정

  1. 격리 실행Docker는 애플리케이션을 컨테이너라는 느슨하게 격리된 환경에 패키징해 실행한다. 격리와 보안 덕분에 한 호스트에서 여러 컨테이너를 동시에 돌릴 수 있다.
  2. 인프라와 분리앱을 인프라로부터 분리해 소프트웨어를 빠르게 전달한다. 인프라를 앱을 다루듯 같은 방식으로 관리할 수 있게 된다.
  3. 수명주기 관리개발·테스트·배포로 이어지는 방법론을 적용해 코드를 작성한 시점과 프로덕션에서 실행하는 시점 사이의 지연을 크게 줄인다.

#5한 줄 요약

애플리케이션과 인프라를 분리해, 앱을 컨테이너로 패키징·배포·실행함으로써 어디서든 일관되게 돌아가게 하는 개방형 플랫폼

컨테이너와 이미지

이미지는 실행에 필요한 파일 시스템과 설정을 담은 읽기 전용 템플릿이고, 컨테이너는 그 이미지를 격리된 환경에서 실행한 살아있는 프로세스다.

#1문제 상황

React 프런트엔드, Python API, PostgreSQL 데이터베이스로 이루어진 앱을 개발한다고 하자. 이 프로젝트를 하려면 Node와 Python, PostgreSQL을 각각 설치해야 하고, 팀의 다른 개발자나 CI/CD 시스템, 프로덕션과 같은 버전을 쓰고 있는지 확인해야 한다. 이미 내 컴퓨터에 깔린 다른 버전이 앱이 필요로 하는 버전에 영향을 주지 않는지, 충돌은 어떻게 관리할지도 각자 해결해야 한다.

#2핵심 질문

앱의 각 구성요소가 서로 간섭하지 않고, 어느 컴퓨터에서든 같은 버전으로 실행되게 하려면 어떻게 해야 하는가?

#3동작 예시

컨테이너는 앱 구성요소마다 하나씩 두는 격리된 프로세스다. 앞의 예라면 React 앱, Python API, 데이터베이스가 각각 별도의 격리된 환경에서 실행된다. 각 컨테이너는 호스트에 미리 설치된 의존성에 기대지 않고 스스로 필요한 것을 갖추며, 서로 완전히 격리돼 있다.

#4동작 과정

  1. 이미지 준비이미지는 실행에 필요한 파일 시스템과 설정을 담은 읽기 전용 템플릿이다. 여러 겹의 레이어로 구성되며, 이 레이어들을 바탕으로 실행 환경이 만들어진다.
  2. 컨테이너 생성이미지를 바탕으로 컨테이너를 만든다. 컨테이너는 이미지를 격리된 환경에서 실행한 살아있는 프로세스로, 호스트의 사전 설치 의존성에 기대지 않는다.
  3. 격리 실행만들어진 컨테이너가 다른 컨테이너 및 호스트와 격리된 채 실행된다. 그래서 같은 머신에서 여러 구성요소를 동시에 돌려도 서로 영향을 주지 않는다.

#5한 줄 요약

이미지라는 읽기 전용 템플릿을 바탕으로, 필요한 것을 스스로 갖춘 격리된 프로세스인 컨테이너를 실행해 구성요소 간 간섭 없이 같은 환경을 재현하는 것

레지스트리와 설치 개요

레지스트리는 이미지를 저장하고 내려받을 수 있게 하는 원격 저장소(Docker Hub 등)이며, Docker 사용은 운영체제에 맞는 Docker Desktop 또는 Docker Engine을 설치하는 것으로 시작한다.

#1문제 상황

컨테이너 이미지는 내 컴퓨터에 저장할 수 있지만, 그것만으로는 친구에게 공유하거나 다른 머신에서 쓰기가 어렵다. 이미지를 주고받을 공통된 장소가 없으면 각자 이미지를 다시 만들거나 파일을 직접 옮겨야 한다. Docker를 쓰려면 먼저 운영체제에 맞는 실행 환경을 설치해야 한다는 점도 출발점의 부담이다.

#2핵심 질문

만든 이미지를 여러 사람과 여러 머신에서 함께 쓰려면 어디에 두고 어떻게 주고받아야 하는가?

#3동작 예시

이미지 레지스트리는 컨테이너 이미지를 저장하고 공유하는 중앙 위치다. 공개일 수도 비공개일 수도 있다. Docker Hub는 누구나 쓸 수 있는 공개 레지스트리이자 기본 레지스트리이며, 그 밖에 Amazon ECR, Azure ACR, Google GCR 같은 레지스트리도 있다. 조직 내부나 로컬에 사설 레지스트리(Harbor, JFrog Artifactory, GitLab Container registry 등)를 직접 운영할 수도 있다.

#4동작 과정

  1. 레지스트리 선택이미지를 올리고 내려받을 레지스트리를 정한다. 기본값은 Docker Hub이고, 공개·비공개 사설 레지스트리도 선택할 수 있다.
  2. 저장과 공유이미지를 레지스트리에 올려 여러 머신과 사람이 같은 이미지를 내려받아 쓸 수 있게 한다. 레지스트리와 그 안의 저장 단위인 리포지터리는 구분되는 개념이다.
  3. 설치로 시작운영체제에 맞는 Docker Desktop 또는 Docker Engine을 설치하고 시작한다. 설치가 끝나면 이미지를 가져와 컨테이너로 실행하는 흐름을 바로 시작할 수 있다.

#5한 줄 요약

이미지를 중앙 레지스트리에 두고 저장·공유하며, 설치된 Docker 실행 환경을 통해 어디서든 같은 이미지를 내려받아 쓰게 하는 것

컨테이너 실행 기본

이미지를 바탕으로 컨테이너를 만들어 실행하고, 목록·중지·삭제 등 기본 명령으로 다루는 방법

#1문제 상황

프로세스를 그냥 실행하면 호스트의 파일 시스템과 네트워크, 프로세스 트리를 그대로 공유한다. 그래서 앱이 필요로 하는 환경을 매번 호스트에 맞춰 준비해야 하고, 한 앱이 다른 앱이나 시스템에 영향을 줄 수 있다. 실행할 이미지의 버전도 명시하지 않으면 원하는 버전을 재현하기 어렵다.

#2핵심 질문

이미지를 바탕으로 컨테이너를 만들어, 격리된 환경에서 원하는 버전으로 실행하고 다루려면 어떻게 해야 하는가?

#3동작 예시

docker run ubuntu:24.04처럼 이미지 참조에 태그를 붙여 실행하면, 우분투 24.04 버전으로 컨테이너가 만들어진다. 태그는 이미지 버전이며 생략하면 latest가 기본이 된다. 이렇게 실행된 컨테이너 프로세스는 호스트와 분리된 자신만의 파일 시스템, 네트워크, 프로세스 트리를 가진다.

#4동작 과정

  1. 이미지 지정docker run [OPTIONS] IMAGE[:TAG|@DIGEST] [COMMAND] [ARG...] 형태로 실행할 이미지 참조를 지정한다. 이미지 참조는 이미지의 이름과 버전이며, 태그 대신 다이제스트로 특정 이미지를 가리킬 수도 있다.
  2. 컨테이너 생성·실행지정한 이미지로 컨테이너를 만들어 실행한다. Docker는 컨테이너 안에서 프로세스를 격리 실행하며, 호스트는 로컬일 수도 원격일 수도 있다.
  3. 옵션으로 동작 조정포트 공개, 로컬 파일 공유, 데이터 유지, 여러 컨테이너로 구성된 앱 실행 등 옵션으로 기본 동작을 바꾼다. 실행한 뒤에는 목록·중지·삭제 같은 기본 명령으로 컨테이너를 다룬다.

#5한 줄 요약

이미지 참조로 컨테이너를 만들어, 호스트와 분리된 고유한 파일 시스템·네트워크·프로세스 트리 안에서 프로세스를 격리 실행하는 것

이미지 빌드와 게시

Dockerfile 로 이미지를 빌드하고 태그를 붙여 레지스트리(Docker Hub)에 올려 공유하는 과정

#1문제 상황

이미지를 매번 손으로 준비하거나 다른 사람이 만든 것에만 의존하면, 내 앱에 맞는 실행 환경을 재현하기 어렵다. 또한 이미지에 이름을 붙이지 않으면 어디로 배포할지 정해지지 않고, 만든 이미지를 다른 사람과 공유할 방법도 없다.

#2핵심 질문

내 애플리케이션에 맞는 이미지를 어떻게 만들고, 이름을 붙여 남에게 공유할 수 있는가?

#3동작 예시

이미지는 대개 Dockerfile로 빌드한다. 가장 기본적인 명령은 docker build .이며, 끝의 .는 빌드 컨텍스트의 경로를 가리킨다. 빌더는 이 위치에서 Dockerfile과 참조된 파일들을 찾고, 필요하면 베이스 이미지를 가져온 뒤 Dockerfile에 적힌 지시를 차례로 실행한다. 이 명령으로 만든 이미지에는 이름이 없고 이미지 ID만 출력된다.

#4동작 과정

  1. 빌드Dockerfile을 바탕으로 이미지를 만든다. docker build .처럼 빌드 컨텍스트를 지정하면 빌더가 그 위치에서 Dockerfile과 참조 파일을 찾아 지시를 실행하고, 필요하면 베이스 이미지를 내려받는다.
  2. 태그이미지에 이름을 붙인다. 태그는 이름을 정할 뿐 아니라 그 이미지가 어디로 배포될 수 있는지도 결정한다.
  3. 게시컨테이너 레지스트리를 통해 새로 만든 이미지를 배포·공유한다. 빌드 캐시를 활용하면 다시 빌드할 때 반복 작업을 줄일 수 있고, 멀티스테이지 빌드로 여러 단계를 거쳐 이미지를 만들 수도 있다.

#5한 줄 요약

Dockerfile로 이미지를 빌드하고 이름을 붙여 레지스트리에 게시함으로써, 만든 이미지를 남과 공유하고 배포하는 것

시작 자습서

샘플 애플리케이션을 컨테이너로 빌드·실행·공유하며 Docker 사용 흐름을 처음부터 따라 하는 공식 입문 자습서

#1문제 상황

애플리케이션은 특정 런타임과 라이브러리, 데이터베이스, 지원 도구에 의존한다. 이런 의존성을 컴퓨터마다 손으로 준비하면 실행 환경이 제각각이 되고, 같은 앱을 여러 머신에서 일관되게 돌리기 어렵다.

#2핵심 질문

의존성을 앱과 함께 묶어, 준비 작업 없이 같은 방식으로 실행하고 공유하려면 어떻게 해야 하는가?

#3동작 예시

Docker는 의존성을 애플리케이션과 함께 패키징해 머신마다 손으로 준비하지 않아도 일관되게 실행되게 한다. 입문 자습서에서는 docker pull docker/welcome-to-docker로 이미지를 내려받고, docker run --detach --name welcome --publish 8080:80 docker/welcome-to-docker로 컨테이너를 실행한다. 이 명령은 컨테이너를 백그라운드로 돌리고 이름을 welcome으로 정하며 웹 서버를 8080 포트로 노출한다.

#4동작 과정

  1. 이미지로 내려받기Docker는 애플리케이션을 이미지로 배포하며, 이미지는 앱과 그 실행에 필요한 것을 담은 바로 실행 가능한 패키지다. 자습서에서는 누군가 Docker용으로 패키징해 둔 이미지를 Docker Hub에서 내려받는 것으로 시작한다.
  2. 컨테이너 실행이미지의 실행 인스턴스가 컨테이너다. 내려받은 이미지로 단일 컨테이너를 실행하고, 이어서 여러 컨테이너로 구성된 애플리케이션도 시작해 본다.
  3. 이미지로 만들어 공유애플리케이션을 이미지로 패키징하고 Docker Hub를 통해 공유한다. 이 흐름으로 실행·구성·패키징·공유까지 Docker 사용의 기본 과정을 한 번에 따라 해 본다.

#5한 줄 요약

앱과 의존성을 함께 담은 이미지를 내려받아 컨테이너로 실행하고, 다시 이미지로 만들어 공유하는 전체 흐름을 익히게 하는 것

빌드 개요와 컨텍스트

Docker 이미지 빌드가 무엇인지, 그리고 빌드에 필요한 파일들이 모이는 빌드 컨텍스트가 어떻게 빌더로 전달되는지 설명하는 개요.

#1문제 상황

이미지를 빌드할 때 어떤 도구가 어떤 역할을 맡는지, 빌드에 필요한 파일들이 어디서 어떻게 전달되는지 알기 어렵다. 이 구조를 모르면 빌드는 그냥 명령 한 줄로만 보이고, 빌드에 어떤 파일이 포함되는지도 파악하기 어렵다.

#2핵심 질문

빌드 요청이 어떤 구성요소를 거쳐 처리되고, 빌드에 필요한 파일들은 어떻게 빌더로 전달되는가?

#3동작 예시

Docker Build는 클라이언트-서버 구조로 동작한다. 클라이언트인 Buildx가 빌드를 실행·관리하는 사용자 인터페이스이고, 서버인 BuildKit가 빌드 실행을 맡는 빌더다. 빌드를 호출하면 Buildx 클라이언트가 BuildKit 백엔드로 빌드 요청을 보내고, BuildKit가 빌드 지시를 해석해 빌드 단계를 실행한다. 빌드 결과는 클라이언트로 돌아오거나 Docker Hub 같은 레지스트리로 업로드된다.

#4동작 과정

  1. 요청 전달docker build를 호출하면 Buildx가 빌드 옵션을 해석해 BuildKit 백엔드로 빌드 요청을 보낸다. 이때 빌더는 빌드 컨텍스트의 파일들을 받는다.
  2. 빌드 실행BuildKit가 빌드 지시를 해석하고 빌드 단계를 차례로 실행한다. 빌드 컨텍스트에서 Dockerfile과 참조된 파일을 찾아 사용한다.
  3. 결과 반환·업로드만들어진 빌드 출력을 클라이언트로 돌려보내거나 레지스트리에 업로드한다. Buildx는 빌드를 실행하는 것 외에 빌더라 부르는 BuildKit 백엔드도 만들고 관리한다.

#5한 줄 요약

Buildx 클라이언트가 빌드 요청을 BuildKit 빌더로 보내고, 컨텍스트의 파일을 근거로 빌드를 실행해 그 결과를 클라이언트나 레지스트리로 내보내는 것

이미지 빌드 — Dockerfile·BuildKit·Bake03-02

Dockerfile과 빌드 검사

Dockerfile은 이미지를 만드는 명령을 순서대로 적은 텍스트 파일이며, 빌드 검사는 그 작성 오류를 미리 잡아준다.

→ 03-01 참조

#1문제 상황

이미지를 만들려면 기반 이미지 선택부터 파일 복사, 의존성 설치, 실행 명령 지정까지 여러 단계를 정해진 순서로 실행해야 한다. 이 과정을 매번 손으로 반복하면 같은 이미지를 다시 만들기 어렵고, 누가 언제 어떤 순서로 실행했는지 기록도 남지 않는다.

게다가 명령 순서가 조금만 어긋나도 빌드가 중간에 실패하거나 의도와 다른 이미지가 만들어진다. 잘못 적은 지시자를 빌드를 끝까지 돌린 뒤에야 발견하는 일이 많아, 원인을 찾는 데 시간이 오래 걸린다.

#2핵심 질문

이미지를 만드는 명령을 어떤 형식으로 적어 두고, 그 작성 오류는 빌드 전에 어떻게 잡아낼 수 있을까?

#3동작 예시

Dockerfile 맨 위에 FROM ubuntu:24.04를 적고 그 아래 RUN apt-get update를 쓴 뒤 다시 FROM alpine:3.20을 적으면, 두 번째 FROM이 새 단계를 시작한다는 점을 빌드 검사가 FromAsCasing 같은 규칙으로 확인해 준다. 이처럼 각 줄이 어떤 지시자인지, 표기가 규칙에 맞는지를 빌드 전에 검사한다.

#4동작 과정

  1. 지시자 읽기Docker는 Dockerfile을 위에서 아래로 읽으며 FROM, RUN, WORKDIR, COPY, CMD 같은 지시자를 하나씩 실행한다. 각 지시자는 앞선 결과 위에 쌓이므로 순서가 곧 결과가 된다.
  2. 단계 구분FROM을 다시 만나면 지금까지 쌓은 것을 하나의 빌드 단계로 확정하고 새 단계를 연다. 그래서 어느 FROM이 어떤 단계인지, 이름이 겹치지 않는지가 중요해진다.
  3. 빌드 검사빌드 검사 도구가 Dockerfile을 실행하지 않고 정적으로 훑어 인자 표기, 대소문자, 형식 오류를 미리 알려준다. 오류를 빌드 전에 고칠 수 있어 실패한 빌드를 반복하지 않게 된다.

#1문제 상황

Dockerfile을 한 단계로만 작성하면 컴파일 도구, 소스 코드, 임시 파일까지 최종 이미지에 그대로 남는다. 그 결과 이미지가 불필요하게 커지고, 전송과 실행에 시간이 더 걸린다.

또 여러 이미지가 같은 기반 설정을 각자 따로 작성하면 같은 작업을 반복하고, 한쪽만 고쳐져서 서로 어긋나기 쉽다. 기반 이미지도 아무거나 고르면 보안 취약점이 많은 큰 이미지부터 시작하게 된다.

#2핵심 질문

더 작고 안전하고 빨리 만들어지는 이미지를 얻으려면 빌드를 어떻게 나누고 골라야 할까?

#3동작 예시

빌드 단계에서 컴파일을 끝낸 실행 파일만 최종 단계로 복사하면, 컴파일러와 소스 코드는 최종 이미지에 들어가지 않는다. 이렇게 빌드용 단계와 결과물만 담는 최종 단계를 분리하면 이미지 크기가 줄고 실행에 필요한 파일만 남는다.

#4동작 과정

  1. 단계 분리Dockerfile 지시자를 빌드용 단계와 최종 출력용 단계로 나눈다. 중간 단계의 결과 중 꼭 필요한 파일만 최종 단계로 복사되어 결과물이 가벼워진다.
  2. 공통 단계 재사용공통 부분이 많은 이미지들은 그 부분을 담은 재사용 단계를 하나 만들고 개별 단계가 이를 기반으로 삼는다. 공통 단계는 한 번만 빌드되므로 호스트 메모리를 아끼고 로드도 빨라진다.
  3. 기반 이미지 선택시작점이 되는 기반 이미지를 신중히 고른다. 안전한 이미지를 고르는 것이 보안 확보의 첫걸음이 되고, 이후 단계들이 그 위에서 일관되게 쌓인다.

멀티플랫폼·시크릿·CDI

여러 CPU 아키텍처용 이미지를 한 번에 빌드하고, 빌드 시크릿과 CDI로 비밀정보와 장치를 안전하게 다루는 기능.

#1문제 상황

컨테이너는 호스트의 커널을 공유하므로 컨테이너 안에서 도는 코드가 호스트의 CPU 아키텍처와 맞아야 한다. 그래서 arm64 컴퓨터에서는 linux/amd64 컨테이너를 그냥 실행할 수 없고, 리눅스 호스트에서는 윈도우 컨테이너를 실행할 수 없다.

개발자마다 CPU 아키텍처가 다른 장비를 쓰면 한 사람은 되고 다른 사람은 안 되는 상황이 생긴다. 또한 빌드 중에 비밀 토큰이 필요할 때 환경 변수나 인자에 넣으면 그 값이 이미지 레이어에 남아 유출될 수 있다.

#2핵심 질문

여러 운영체제와 CPU 아키텍처를 한 번에 지원하는 이미지를 어떻게 만들고, 비밀정보와 장치는 안전하게 다룰 수 있을까?

#3동작 예시

linux/amd64, linux/arm64, windows/amd64용 변형을 한 번의 빌드 명령으로 함께 만들어 하나의 이미지로 묶으면, 같은 이미지를 서로 다른 하드웨어에서 각각 실행할 수 있다. 어느 장비에서든 해당 아키텍처에 맞는 변형이 선택되어 실행된다.

#4동작 과정

  1. 다중 대상 지정한 번의 빌드 호출에 여러 운영체제·아키텍처 조합을 지정한다. 각 조합마다 그 환경에 맞는 이미지 변형이 만들어진다.
  2. 단일 이미지로 묶기만들어진 변형들을 하나의 이미지로 묶는다. 실행하는 쪽은 하드웨어에 맞는 변형을 자동으로 받아 쓰므로 환경별로 이미지를 따로 고르지 않아도 된다.
  3. 비밀정보와 장치 분리빌드 시크릿으로 비밀값을 이미지에 남기지 않고 빌드 중에만 쓴다. 장치는 CDI(컨테이너가 호스트 장치를 안전하게 쓸 수 있게 해 주는 규격)로 연결해 컨테이너가 필요한 하드웨어를 사용하게 한다.

#5한 줄 요약

하나의 이미지로 여러 플랫폼을 지원하고, 비밀정보와 장치를 이미지에 남기지 않고 안전하게 다루는 기능

빌드 캐시

이전 빌드 결과(레이어)를 재사용해 다시 빌드할 때 시간을 줄이는 빌드 캐시의 동작과 무효화 규칙.

→ 03-03 참조

#1문제 상황

Docker는 지시자와 그 지시자가 의존하는 파일이 이전 빌드 이후 바뀌지 않았으면 그 레이어를 캐시에서 재사용한다. 그런데 Dockerfile 명령 순서가 뒤죽박죽이면 자주 안 바뀌는 것까지 매번 다시 빌드하게 되어 캐시가 쉽게 무효화된다.

빌드에 보내는 파일 범위가 크면 그만큼 전송할 데이터가 많아지고, 그중 하나만 바뀌어도 캐시가 깨질 가능성이 커진다. 캐시를 어떻게 관리하느냐에 따라 빌드 시간이 크게 달라진다.

#2핵심 질문

바뀌지 않은 부분은 다시 만들지 않고 재사용하도록 빌드 순서와 범위를 어떻게 잡아야 할까?

#3동작 예시

소스 코드를 복사하는 COPY보다 의존성 설치 명령을 Dockerfile 앞쪽에 두면, 소스만 수정했을 때 의존성 설치 레이어는 캐시에서 그대로 재사용된다. 그래서 소스를 고칠 때마다 의존성을 다시 설치하지 않아도 된다.

#4동작 과정

  1. 레이어 순서 정리잘 바뀌지 않는 명령을 앞에, 자주 바뀌는 명령을 뒤에 둔다. 앞쪽 레이어가 바뀌지 않으면 뒤에서 아무리 고쳐도 앞부분은 재사용된다.
  2. 범위 좁히기빌드에 보내는 파일과 디렉터리 집합인 컨텍스트를 최소로 유지한다. 보내는 데이터가 줄면 캐시가 깨질 가능성도 줄어든다.
  3. 마운트와 캐시 공유바인드 마운트로 호스트의 파일을 빌드 중에 잠깐 끼워 넣어 불필요한 레이어를 줄이고, 캐시 마운트로 의존성 캐시를 빌드 사이에 유지한다. 캐시는 로컬·인라인·레지스트리 등 여러 방식으로 다른 환경과 공유할 수 있다.

#5한 줄 요약

바뀌지 않은 레이어를 재사용해 다시 빌드할 때 걸리는 시간과 데이터를 줄이는 캐시 동작

Bake로 선언적 빌드

여러 대상과 플랫폼 빌드를 HCL/JSON 파일로 선언해 docker buildx bake 한 번으로 실행하는 도구.

#1문제 상황

빌드 설정이 복잡해지면 docker build 명령에 붙이는 옵션 플래그와 환경 변수가 계속 늘어난다. 이런 긴 명령을 사람마다 다르게 입력하면 같은 프로젝트인데도 빌드 결과가 조금씩 달라진다.

플래그를 외우거나 매번 복사해 붙여야 하므로 실수도 잦고, 팀원 모두가 같은 방식으로 빌드한다는 보장이 없다. 여러 대상과 플랫폼을 한꺼번에 빌드하려면 명령이 더 길어지고 관리가 어려워진다.

#2핵심 질문

빌드 설정을 매번 긴 명령이 아니라 파일에 한 번 적어 두고 누구나 같게 실행하려면 어떻게 해야 할까?

#3동작 예시

docker build -f Dockerfile -t myapp:latest . 같은 명령을, 대상 이름과 컨텍스트, Dockerfile, 태그를 적은 HCL 파일 하나로 표현해 두면 docker buildx bake myapp 한 줄로 같은 빌드를 실행할 수 있다. 설정은 파일에 남고 명령은 짧아진다.

#4동작 과정

  1. 설정 파일 작성대상(target)마다 컨텍스트, Dockerfile, 태그 같은 빌드 설정을 HCL 또는 JSON 파일에 적는다. 명령줄에 흩어져 있던 플래그가 파일 안에 정리된다.
  2. 대상 해석Bake가 파일을 읽어 어떤 대상들을 어떤 설정으로 빌드할지 해석한다. 상속과 변수, 행렬 대상으로 여러 대상의 공통 설정을 한 번에 정의할 수 있다.
  3. 한 번에 실행docker buildx bake 명령으로 대상들을 실행한다. Bake는 Buildx CLI에 내장되어 있어 Buildx가 있으면 바로 쓸 수 있고, 파일에 적힌 대로 누구나 같은 설정으로 빌드하게 된다.

#5한 줄 요약

빌드 설정을 HCL·JSON 파일로 선언해 두고 한 번의 명령으로 팀 모두가 같게 실행하는 도구

빌더와 BuildKit

BuildKit은 Docker의 빌드 엔진이고, 빌더는 그 엔진을 실행하는 인스턴스로 드라이버를 통해 구성·관리한다.

#1문제 상황

빌드를 처리하는 엔진과 그 엔진이 실제로 도는 실행 환경을 구분하지 않고 쓰면, 어떤 빌드가 어디서 돌았는지 파악하기 어렵다. 기본 설정만 쓰면 여러 플랫폼 빌드나 캐시 공유 같은 기능의 제약을 그대로 안고 가게 된다.

여러 빌더를 함께 쓰려면 각 빌더가 어떤 드라이버로 만들어졌고 어떤 BuildKit 버전을 쓰는지 알아야 한다. 이 정보를 모르면 빌드가 실패해도 원인을 좁히기 어렵다.

#2핵심 질문

빌드 엔진과 그 실행 환경을 어떻게 구분하고 골라서 관리해야 할까?

#3동작 예시

docker buildx ls를 실행하면 시스템에 있는 빌더 인스턴스와 각각이 쓰는 드라이버, 상태, BuildKit 버전, 지원 플랫폼이 표로 나온다. 이름 옆의 별표(*)는 현재 선택된 빌더를 뜻하므로, 어느 빌더가 실제로 쓰이는지 한눈에 확인할 수 있다.

#4동작 과정

  1. 엔진과 실행 환경 구분BuildKit은 빌드를 실제로 수행하는 엔진이고, 빌더는 그 엔진을 실행하는 인스턴스다. 같은 엔진을 여러 실행 환경에서 따로 띄워 쓸 수 있다.
  2. 드라이버로 만들기docker buildx create 명령으로 빌더를 만든다. --driver를 생략하면 컨테이너 안에서 BuildKit 데몬을 돌리는 docker-container 드라이버가 쓰이고, 기본 빌더는 docker 드라이버를 쓰므로 직접 새로 만들 수는 없다.
  3. 점검과 관리docker buildx ls로 빌더 목록과 드라이버, BuildKit 버전, 플랫폼을 확인하고 원하는 빌더를 선택한다. 필요하면 buildkitd.toml 같은 설정으로 BuildKit 동작을 조정한다.

#5한 줄 요약

BuildKit이라는 빌드 엔진을 여러 빌더 인스턴스로 나누어 드라이버로 구성하고 골라 쓰는 구조

내보내기와 메타데이터

빌드 산출물을 이미지·레지스트리·로컬 tar 등 원하는 형태로 내보내고, 주석·SBOM 같은 메타데이터를 붙이는 기능.

#1문제 상황

빌드가 끝나면 그 산출물을 어디에 어떤 형태로 둘지 정해야 한다. 그런데 기본 동작만 쓰면 결과물이 로컬 이미지로만 남아 레지스트리에 올리려면 별도로 다시 푸시해야 한다.

또 이미지가 어떻게 만들어졌는지, 무엇이 들어 있는지에 대한 정보가 이미지와 함께 따라다니지 않으면 나중에 출처를 확인하기 어렵다. 보안 검사에 필요한 재료 정보도 함께 저장되어야 한다.

#2핵심 질문

빌드 산출물을 원하는 형태로 내보내고, 그 이미지에 대한 정보까지 함께 붙이려면 어떻게 해야 할까?

#3동작 예시

docker buildx build --output type=image .는 결과를 컨테이너 이미지 형식으로 내보내고, 여기에 push=true를 더하면 만든 이미지를 자동으로 밀어 올린다. 즉 output 옵션의 종류만 바꿔서 같은 빌드 결과를 이미지, 레지스트리, 로컬 파일 등 원하는 곳으로 보낼 수 있다.

#4동작 과정

  1. 내보내기 대상 선택output 옵션으로 결과를 이미지·레지스트리·로컬 tar 등 원하는 형태와 위치로 내보낸다. 레지스트리 내보내기는 push=true를 자동으로 설정해 푸시까지 처리한다.
  2. 압축과 이름 지정이미지 내보내기에서는 압축 방식과 여러 이름, 다이제스트 표기 같은 세부를 파라미터로 정한다. 결과물의 이름과 전송 방식을 한 곳에서 지정할 수 있다.
  3. 메타데이터 첨부주석과 함께 SBOM(이미지에 들어간 구성 요소 목록), 출처 정보 같은 증명 자료를 이미지에 붙여 저장한다. 이미지와 함께 이 정보가 따라다녀 나중에 구성과 출처를 확인할 수 있다.

#5한 줄 요약

빌드 산출물을 이미지·레지스트리·로컬 파일 등 원하는 형태로 내보내고 주석·SBOM 같은 메타데이터를 함께 붙이는 기능

GitHub Actions 빌드

GitHub Actions 워크플로에서 build-push-action 등으로 이미지를 빌드하고 레지스트리에 푸시하는 CI 구성.

#1문제 상황

기존에는 개발자가 각자 로컬에서 docker build 로 이미지를 만든 뒤 손으로 레지스트리에 docker push 하는 방식이었다. 이 방식은 빌드에 쓰인 환경과 순서가 사람마다 달라, 같은 소스인데도 결과 이미지가 조금씩 달라지거나 푸시를 빠뜨리는 일이 생긴다. 또 반복 작업을 매번 사람이 해야 하므로 코드가 바뀔 때마다 일관된 이미지를 보장하기 어렵다.

#2핵심 질문

코드가 바뀌는 순간 이미지 빌드와 레지스트리 푸시를 사람 손이 아니라 정해진 워크플로로 자동 실행하려면 어떻게 해야 할까?

#3동작 예시

저장소에 .github/workflows/build.yml 파일을 두고, main 브랜치에 push 가 들어오면 Docker의 docker/build-push-action 스텝이 이미지를 빌드하고 Docker Hub 로 푸시하도록 적는다. 이때 로그인 정보는 리포지터리 시크릿에서 읽고, 태그·라벨도 워크플로에서 지정한다.

#4동작 과정

  1. 워크플로 트리거push 같은 이벤트가 발생하면 GitHub Actions 러너가 워크플로를 시작한다. 사람이 명령을 치지 않아도 코드 변경이 곧 빌드 시작점이 된다.
  2. 빌더 준비와 로그인docker/setup-buildx-action 같은 스텝으로 BuildKit 기반 빌더를 구성하고, 시크릿으로 레지스트리에 로그인한다. 여기서 빌드 환경이 매번 동일하게 맞춰진다.
  3. 빌드·푸시·산출build-push-action 이 이미지를 만들어 레지스트리로 푸시하고, 필요하면 태그·라벨과 SBOM·provenance 증명(attestation)을 함께 붙인다. 결과 이미지와 그 출처가 워크플로 기록으로 남는다.

#5한 줄 요약

코드 변경을 신호로 이미지 빌드와 레지스트리 푸시를 자동화해, 누가 하든 같은 결과가 나오도록 만드는 것

빌드 정책

이미지에 적용할 규칙을 코드로 정의해 빌드 입력을 검증하고 조건에 맞지 않으면 차단하는 빌드 정책.

#1문제 상황

기존 빌드는 Dockerfile이 참조하는 것을 그대로 받아들여 진행했다. FROM 이 가리키는 base image, ADD 나 COPY 가 가져오는 원격 URL과 체크섬, Git 저장소 입력이 검증 없이 빌드에 쓰인다. 그래서 허용하지 않은 이미지나 변조된 파일이 들어와도 빌드는 그대로 끝까지 실행되고, 문제는 이미지만 만들어진 뒤에야 드러난다.

#2핵심 질문

빌드가 실행되기 전에 입력이 정한 규칙에 맞는지 검증해, 어긋나는 입력을 미리 차단하려면 어떻게 해야 할까?

#3동작 예시

정책을 Rego 라는 규칙 표현 언어로 적어 두고, 어느 Dockerfile의 base image 가 허용 목록에 없거나 ADD 로 받는 파일의 체크섬이 맞지 않으면 그 입력을 위반으로 판정한다. 위반이 하나라도 있으면 이미지 명령이 한 줄도 실행되기 전에 빌드가 실패한다.

#4동작 과정

  1. 입력 해석Buildx 가 Dockerfile 의 FROM, ADD·COPY, 빌드 컨텍스트, Git 저장소처럼 빌드가 참조하는 모든 입력을 확인한다. 무엇이 빌드에 들어오는지 먼저 목록으로 잡는다.
  2. 정책 평가실행 전에 그 입력들에 Rego 정책을 적용해 규칙 위반 여부를 판단한다. 검증이 빌드 실행보다 앞서 일어난다.
  3. 차단 또는 진행위반 입력이 있으면 명령 실행 전에 빌드를 실패시키고, 없으면 다음 단계로 넘어간다. 통과한 입력만 이미지에 반영된다.

#5한 줄 요약

빌드 실행 전에 입력을 규칙으로 검증해, 조건에 맞지 않는 입력을 결과물이 만들어지기 전에 막는 것

컨테이너 실행과 리소스

docker run 으로 컨테이너를 실행하고 CPU·메모리 등 자원 한도를 지정해 격리된 프로세스를 운영하는 방법.

#1문제 상황

호스트에서 프로세스를 그냥 실행하면 파일 시스템과 네트워크, 프로세스 트리를 호스트와 똑같이 공유한다. 그래서 한 프로세스가 다른 프로세스의 파일을 건드리거나 포트를 차지할 수 있고, 자원 한도가 없으면 하나가 CPU 와 메모리를 독점해 나머지가 밀린다. 실행 환경을 격리하고 자원을 제한하지 않으면 같은 호스트의 여러 작업이 서로 간섭한다.

#2핵심 질문

프로세스를 호스트로부터 격리하고 자원을 제한한 채 안정적으로 실행하려면 어떻게 해야 할까?

#3동작 예시

docker run ubuntu:24.04 로 컨테이너를 시작하면 그 안의 프로세스는 자체 파일 시스템과 자체 네트워크, 호스트와 분리된 프로세스 트리를 가진다. 여기에 --memory, --cpus 같은 옵션을 주면 이 컨테이너가 쓸 수 있는 메모리와 CPU 를 정해진 범위로 묶을 수 있다.

#4동작 과정

  1. 이미지 참조 지정docker run [OPTIONS] IMAGE[:TAG|@DIGEST] [COMMAND] [ARG...] 형태로 어떤 이미지로 컨테이너를 만들지 정한다. 태그나 다이제스트로 버전을 고정할 수 있다.
  2. 격리 환경 생성컨테이너 프로세스가 자체 파일 시스템·네트워크·프로세스 트리를 가진 상태로 시작한다. 호스트와 분리되므로 다른 작업과 간섭하지 않는다.
  3. 자원 한도 적용CPU·메모리·GPU 같은 자원 한도를 지정해 격리된 프로세스가 정해진 범위 안에서만 실행되게 한다. 한도를 넘지 않으므로 호스트 전체가 안정적으로 유지된다.

#5한 줄 요약

프로세스를 격리된 환경에서 실행하면서 자원 한도를 함께 지정해, 서로 간섭 없이 안정적으로 돌리는 것

Docker CLI 활용

docker 명령줄 도구에서 출력 형식·필터·자동완성·프록시 같은 옵션을 활용해 명령을 효율적으로 다루는 방법.

#1문제 상황

docker 명령의 기본 출력은 사람이 읽기 좋게 맞춰져 있어, 필요한 필드만 뽑거나 스크립트로 파싱하기 어렵다. 명령과 옵션이 많아 원하는 객체만 골라내기도 번거롭고, 프록시·컨텍스트처럼 환경에 따라 달라지는 설정을 매번 손으로 맞춰야 한다. 이 때문에 자동화 스크립트가 출력 형식 변화에 쉽게 깨진다.

#2핵심 질문

명령의 출력 형식과 실행 환경을 원하는 대로 제어해 CLI 를 효율적으로 다루려면 어떻게 해야 할까?

#3동작 예시

docker inspect --format '{{join .Args " , "}}' 컨테이너 처럼 --format 과 Go 템플릿 함수를 쓰면 컨테이너 정보 전체가 아니라 Args 필드만 골라 원하는 구분자로 이어 붙여 출력할 수 있다. 이런 방식으로 여러 명령의 출력을 필요한 값만 남겨 뽑아낼 수 있다.

#4동작 과정

  1. 출력 형식 지정--format 과 Go 템플릿 함수를 써서 명령이 내놓는 값 중 필요한 필드만 원하는 형태로 바꾼다. inspect 뿐 아니라 --format 을 지원하는 여러 명령에 같은 방식이 적용된다.
  2. 대상 필터링--filter 로 원하는 조건의 객체만 골라 명령 대상의 범위를 좁힌다. 다룰 대상이 줄어 명령 결과가 명확해진다.
  3. 환경 정리자동완성, 프록시, 컨텍스트, 라벨, 사용하지 않는 객체 정리 같은 옵션으로 실행 환경과 대상을 관리한다. 환경이 정돈되면 같은 명령이 어디서든 같은 방식으로 동작한다.

#5한 줄 요약

출력 형식·필터·환경 설정을 옵션으로 제어해, docker 명령을 사람 손과 스크립트 양쪽에서 일관되게 다루게 하는 것

데몬 운영

컨테이너를 실제로 만들고 돌리는 백그라운드 프로세스인 dockerd 를 시작하고 설정·운영하는 방법.

#1문제 상황

컨테이너를 실제로 만들고 돌리는 것은 백그라운드에서 도는 dockerd 라는 프로세스다. 이 프로세스를 손으로 띄우면 재부팅 뒤에 자동으로 올라오지 않고, 로그 확인·원격 접근·프록시 같은 설정도 매번 사람이 맞춰야 한다. 데몬이 멈추거나 설정이 어긋나면 원인을 찾기 어렵고 컨테이너 전체가 영향을 받는다.

#2핵심 질문

컨테이너를 실제로 만드는 백그라운드 프로세스를 안정적으로 시작하고 설정하며 운영하려면 어떻게 해야 할까?

#3동작 예시

보통 설치는 OS 유틸리티가 데몬을 관리하므로, Ubuntu·Debian 계열에서는 sudo systemctl start docker 로 시작하고 부팅 시 자동 시작도 함께 설정한다. 유틸리티를 쓰지 않고 시험할 때는 dockerd 명령을 직접 실행하며, 이때는 포그라운드에서 돌고 로그가 터미널로 바로 나온다.

#4동작 과정

  1. 시작systemd 같은 OS 유틸리티가 부팅 시 데몬을 자동 실행하거나, 사람이 직접 명령으로 띄운다. 자동 시작을 걸어 두면 재부팅 뒤에도 컨테이너 기반이 유지된다.
  2. 설정프록시, 원격 접근, IPv6 네트워킹, 대체 러너타임, live restore(데몬 재시작 중에도 컨테이너를 유지하는 기능) 같은 항목을 데몬 설정으로 지정한다. 설정이 한곳에 모여 환경이 일관된다.
  3. 관찰과 복구데몬 로그와 Prometheus 같은 메트릭으로 상태를 보고 문제를 진단한다. 이상이 있으면 설정이나 실행 상태를 고쳐 데몬을 정상으로 되돌린다.

컨테이너의 표준 출력 로그를 json-file·syslog·journald 등 어디로 어떤 형식으로 보낼지 정하는 로깅 드라이버 설정.

#1문제 상황

Docker 는 기본으로 json-file 로깅 드라이버를 쓰는데, 기본 상태에서는 로그 회전을 하지 않는다. 그래서 출력이 많은 컨테이너는 로그 파일이 계속 커져 디스크 공간을 채우고, 결국 디스크가 꽉 차는 문제로 이어진다. 또 로그가 로컬에만 쌓이면 여러 호스트의 로그를 한곳에서 모아 검색하기 어렵다.

#2핵심 질문

컨테이너의 표준 출력 로그를 어디로 어떤 형식으로 보낼지 정해, 로그를 관리 가능한 상태로 두려면 어떻게 해야 할까?

#3동작 예시

컨테이너를 띄울 때 --log-driver=local 이나 --log-driver=syslog, --log-driver=journald 처럼 드라이버를 지정하면, 표준 출력 로그가 JSON 파일 대신 정한 대상으로 전달된다. 데몬 수준에서 기본 드라이버를 바꾸면 그 이후 만들어지는 컨테이너에 같은 설정이 적용된다.

#4동작 과정

  1. 드라이버 선택데몬의 기본 로깅 드라이버를 정하거나 컨테이너마다 다른 드라이버를 지정한다. 컨테이너는 별도 설정이 없으면 데몬 기본값을 따른다.
  2. 로그 수집컨테이너의 표준 출력과 표준 에러가 선택한 드라이버를 통해 정해진 대상(JSON 파일, syslog, journald, 외부 로그 서비스 등)으로 전달된다. 형식과 목적지가 드라이버에 따라 달라진다.
  3. 보존과 조회로컬 회전을 걸거나 원격으로 보내 로그를 보존하고, docker logs 같은 수단으로 확인한다. 회전 설정으로 디스크가 차는 문제를 줄인다.

Docker Engine 설치

리눅스 배포판이나 바이너리 패키지로 Docker Engine(서버 데몬과 CLI)을 설치하고 초기 설정하는 절차.

#1문제 상황

Docker Engine 을 패키지 저장소 없이 손으로 올리면 업그레이드와 의존성 관리가 어렵고, 설치 후 설정을 빠뜨리기 쉽다. 특히 ufw 나 firewalld 로 방화벽을 쓰는 환경에서는 컨테이너가 노출한 포트가 방화벽 규칙을 우회할 수 있고, Docker 는 nft 로 만든 규칙을 지원하지 않아 iptables 계열 규칙과의 호환성도 따져야 한다. 설치 후 권한 설정을 안 하면 매번 sudo 를 붙여야 한다.

#2핵심 질문

리눅스 배포판에 데몬과 CLI 를 올바른 절차로 설치하고 초기 설정까지 마치려면 어떻게 해야 할까?

#3동작 예시

Ubuntu 에서는 배포판 버전 요건을 확인한 뒤 Docker 의 패키지 저장소를 추가하고, apt 로 서버 데몬과 CLI 패키지를 설치한다. 설치가 끝나면 서비스가 정상 동작하는지 확인하고, 사용자 그룹 설정으로 sudo 없이 명령을 쓸 수 있게 한다.

#4동작 과정

  1. 사전 확인대상 OS 버전과 방화벽 설정, iptables 호환성을 먼저 점검한다. 방화벽과의 충돌 가능성을 미리 걸러낸다.
  2. 저장소 등록과 설치배포판에 맞는 패키지 저장소를 추가하고 서버 데몬과 CLI 를 설치한다. 저장소를 통해 설치하면 이후 업그레이드도 같은 경로로 관리된다.
  3. 초기 설정sudo 없이 쓰도록 사용자 그룹을 설정하고 서비스 시작을 확인한다. 여기까지 마치면 데몬과 CLI 가 함께 동작할 준비가 끝난다.

엔진 플러그인

볼륨·네트워크·로깅·인가 같은 기능을 확장하도록 Docker Engine 에 끼워 넣는 플러그인의 개념과 사용법.

#1문제 상황

Docker Engine 은 컨테이너 실행, 이미지 관리, 기본 네트워크와 볼륨 같은 핵심 기능만 자체적으로 제공한다. 그래서 저장소를 여러 호스트에 걸쳐 공유하거나, 특정 로깅 시스템으로 로그를 보내거나, 별도 인증 체계로 접근을 통제하려면 기능을 직접 구현하거나 Engine 을 고쳐야 했다. 핵심 코드를 건드리지 않고 이런 기능을 추가할 통로가 없었던 것이 한계였다.

#2핵심 질문

Engine 의 핵심 코드를 수정하지 않고 볼륨·네트워크·인가·로깅 같은 기능을 끼워 넣어 확장하려면 어떻게 해야 하는가?

#3동작 예시

볼륨 플러그인이 "볼륨을 만들고, 컨테이너에 붙이고, 지운다"는 정해진 호출을 받아 처리하는 서버로 동작한다고 하자. docker volume create 로 볼륨을 만들면 Engine 은 그 요청을 플러그인에 넘기고, 플러그인은 실제 저장 위치를 준비한 뒤 그 이름을 돌려준다. 컨테이너를 시작하면 Engine 이 다시 플러그인에 "이 볼륨을 붙여라"라고 요청하고, 플러그인이 파일 시스템 경로를 마운트한다.

#4동작 과정

  1. 플러그인 등록관리형 플러그인은 docker plugin install 로 설치되며, Engine 이 플러그인 목록에 등록하고 이후 그 기능을 쓸 수 있게 된다.
  2. 기능 위임볼륨·네트워크·인가·로깅 같은 작업이 발생하면 Engine 은 해당 유형의 플러그인에게 실제 처리를 넘긴다. 예를 들어 로그 드라이버 플러그인이면 컨테이너 로그 전달을 플러그인이 맡는다.
  3. 결과 반영플러그인이 돌려준 결과를 Engine 이 컨테이너·서비스 동작에 반영한다. 볼륨이면 저장 경로가 붙고, 인가 플러그인이면 접근 허용 여부가 최종 결정된다.

→ 04-08 참조

#1문제 상황

컨테이너는 기본적으로 격리된 네트워크 네임스페이스를 갖기 때문에, 그대로 두면 호스트나 다른 컨테이너와 통신할 수 없다. 반대로 모든 컨테이너를 호스트 네트워크에 그대로 노출하면 격리가 사라지고 포트가 충돌한다. 컨테이너 간·외부 통신을 어떤 방식으로 열고 막을지 정하는 규칙이 필요했다.

#2핵심 질문

컨테이너마다 어떤 방식으로 IP 와 통신 경로를 부여해, 격리와 연결을 동시에 만족시킬 것인가?

#3동작 예시

bridge 드라이버로 네트워크를 만들면 IPv4 서브넷이 하나 생긴다. 이 네트워크에 연결한 컨테이너는 그 서브넷 주소를 가진 네트워크 인터페이스를 갖고, 같은 브리지에 연결된 컨테이너끼리 이름으로 통신할 수 있다. 반면 다른 네트워크에 있는 컨테이너나 외부에서의 접근은 기본적으로 막히고, 호스트 밖으로 나가는 트래픽은 마스커레이딩을 거쳐 호스트 IP 로 보인다.

#4동작 과정

  1. 드라이버 선택용도에 따라 드라이버를 고른다. bridge 는 기본 격리 통신, host 는 호스트 네트워크를 그대로 사용, overlay 는 여러 호스트에 걸친 통신, macvlan·ipvlan 은 컨테이너에 실제 네트워크 주소를 부여, none 은 네트워크를 주지 않는다.
  2. 네트워크 생성과 연결선택한 드라이버로 네트워크를 만들고 컨테이너를 연결하면, 그 드라이버 방식대로 인터페이스와 라우팅 규칙이 배치된다. bridge 는 호스트에 소프트웨어 브리지와 방화벽 규칙을 설치한다.
  3. 격리와 통신 적용같은 네트워크에 연결된 컨테이너끼리만 통신이 열리고, 나머지는 차단되며, 외부와의 연결은 포트 게시나 라우팅 규칙을 통해 이루어진다.

포트 게시와 방화벽

컨테이너 포트를 호스트로 노출하는 포트 게시(-p)와, 그 트래픽이 호스트 방화벽(iptables/nftables)과 상호작용하는 방식.

→ 04-07 참조

#1문제 상황

bridge 네트워크를 쓰는 컨테이너는 기본적으로 호스트 밖에서 접근할 수 없다. 외부에 서비스를 열려면 컨테이너 포트를 호스트 포트로 이어 줘야 하는데, 이 과정은 패킷이 어디로 갈지 정하는 규칙과 주소를 바꾸는 처리를 필요로 한다. 이 규칙을 사람이 손으로 관리하면 충돌과 누수가 생기기 쉽다.

#2핵심 질문

컨테이너 포트를 호스트로 노출할 때, 트래픽을 어디로 보내고 무엇을 막을지 규칙을 어떻게 자동으로 관리할 것인가?

#3동작 예시

컨테이너의 80 번 포트를 호스트의 8080 번으로 게시하면, 외부에서 호스트 IP 의 8080 번으로 들어온 패킷이 그 컨테이너의 80 번으로 전달된다. 이 전달은 호스트의 방화벽 규칙과 NAT 로 구현되며, 컨테이너에서 나가는 트래픽에는 주소를 호스트 주소로 바꾸는 마스커레이딩 규칙이 적용된다. 그래서 외부 장치는 컨테이너의 내부 주소를 알 필요가 없다.

#4동작 과정

  1. 백엔드 규칙 생성Engine 은 기본적으로 iptables 로 방화벽 규칙을 만들고, firewall-backend 옵션으로 nftables 를 선택할 수도 있다. bridge 네트워크에는 규칙이 만들어지지만 ipvlan·macvlan·host 네트워킹에는 만들어지지 않는다.
  2. 게시와 주소 변환 적용-p 로 포트를 게시하면 들어오는 트래픽을 컨테이너 포트로 돌리는 규칙과, 나가는 트래픽의 주소를 바꾸는 마스커레이딩 규칙이 함께 배치된다.
  3. 전달과 격리 유지이 규칙들이 패킷을 컨테이너까지 전달하는 동시에 다른 네트워크와 외부로부터 컨테이너를 격리한다. 이 규칙은 동작에 필수라 직접 수정하면 안 된다.

컨테이너가 사라져도 데이터를 유지하도록 Docker 가 관리하는 볼륨과 바인드 마운트 등 영속 저장 방식.

#1문제 상황

컨테이너의 쓰기 가능한 계층은 컨테이너와 함께 사라진다. 컨테이너를 지우거나 다시 만들면 그 안에 쌓인 데이터도 없어진다. 게다가 컨테이너가 실행되는 호스트의 디렉터리를 그대로 붙이는 방식은 호스트의 디렉터리 구조와 운영체제에 묶여 이식성이 떨어진다.

#2핵심 질문

컨테이너가 사라져도 데이터를 남기고, 여러 컨테이너가 같은 데이터를 안전하게 공유하려면 어떻게 저장해야 하는가?

#3동작 예시

docker volume create 로 볼륨을 만들면 Docker 호스트의 한 디렉터리에 저장되고, 그 볼륨을 컨테이너에 마운트하면 이 디렉터리가 컨테이너 안으로 연결된다. 컨테이너를 지웠다가 같은 볼륨을 새 컨테이너에 다시 붙이면, 이전에 쓴 데이터가 그대로 남아 있어 이어서 쓸 수 있다.

#4동작 과정

  1. 볼륨 생성docker volume create 로 직접 만들거나, 컨테이너·서비스를 만들 때 Docker 가 자동으로 만든다. 볼륨은 호스트의 한 디렉터리로 관리된다.
  2. 마운트 연결볼륨을 컨테이너에 마운트하면 그 디렉터리가 컨테이너 안의 경로로 연결된다. 바인드 마운트는 호스트 경로를 직접 붙이지만, 볼륨은 Docker 가 관리하며 호스트의 핵심 기능과 분리되어 있다.
  3. 영속과 공유컨테이너가 사라져도 볼륨은 남고, 여러 컨테이너에 같은 볼륨을 붙여 데이터를 공유할 수 있다. 백업·이전도 볼륨 단위로 CLI 나 API 로 다룰 수 있다.

Swarm 모드

여러 Docker 호스트를 하나의 클러스터로 묶어 서비스를 분산 배포·확장하는 Swarm 모드의 개념과 운영.

#1문제 상황

단일 Docker 호스트에만 컨테이너를 띄우면, 그 호스트가 멈추는 순간 서비스도 함께 멈춘다. 여러 호스트에 컨테이너를 나눠 띄우고 장애 시 다시 살리려면 각 호스트를 따로 관리해야 하고, 어느 호스트에 무엇이 떠 있는지, 어떤 노드가 죽었는지를 사람이 추적해야 한다. 확장과 복구를 자동으로 해 줄 상위 관리 계층이 없었다.

#2핵심 질문

여러 Docker 호스트를 하나의 클러스터로 묶어, 서비스를 원하는 개수만큼 유지하고 장애가 나면 자동으로 복구하려면 어떻게 해야 하는가?

#3동작 예시

Swarm 모드를 켜면 컨테이너 대신 서비스 단위로 다룬다. docker service create 로 레플리카 3 을 지정하면, 매니저 노드가 그 서비스를 클러스터의 노드들에 나눠 배치한다. 한 노드가 죽으면 매니저는 남은 노드에 새 태스크를 만들어 개수를 다시 3 으로 맞춘다.

#4동작 과정

  1. 클러스터 구성한 호스트에서 새 swarm 을 만들면 그 노드가 매니저가 되고, 다른 호스트는 join 으로 참여해 워커나 매니저가 된다. 매니저들은 Raft 합의로 클러스터 상태를 일치시킨다.
  2. 서비스 배포docker service create 로 서비스와 레플리카 수를 선언하면, 매니저가 태스크를 만들어 노드들에 분배한다. 각 태스크는 컨테이너로 실행되고 상태가 관리된다.
  3. 유지와 복구매니저가 원하는 개수와 실제 상태를 계속 맞춘다. 노드를 drain 하면 그 노드의 태스크가 다른 곳으로 옮겨지고, 롤링 업데이트로 서비스를 중단 없이 교체할 수 있다.

#5한 줄 요약

여러 Docker 호스트를 매니저·워커 클러스터로 묶어, 서비스 개수를 자동으로 유지하고 장애를 복구하는 운영 계층을 제공하는 것

여러 컨테이너로 이루어진 애플리케이션의 서비스·네트워크·볼륨을 하나의 YAML 파일로 정의하고, 명령 하나로 함께 실행하고 관리하는 도구다.

#1문제 상황

#2핵심 질문

여러 컨테이너의 서비스·네트워크·볼륨 구성을 하나의 파일로 정의하고, 한 번의 명령으로 함께 실행·관리하려면 어떻게 해야 하는가?

#3동작 예시

compose.yaml 에 데이터베이스와 애플리케이션 서비스를 함께 적어 둔다. 애플리케이션 서비스는 데이터베이스 서비스를 이름으로 참조하고, 두 서비스는 같은 네트워크로 연결되며 데이터는 볼륨에 저장된다. Compose CLI 로 한 번 실행하면 두 컨테이너가 정의한 관계대로 함께 만들어진다.

#4동작 과정

  1. 모델 정의애플리케이션의 구성 요소를 서비스로 적는다. 서비스는 같은 이미지와 설정으로 하나 이상 실행되는 단위이고, 서로 네트워크로 통신하며 데이터는 볼륨에 저장한다. 이 형식은 Compose Specification 을 따른다.

  3. 함께 관리이후 시작·중지·확장·갱신을 파일을 기준으로 한 명령으로 다룬다. 그래서 같은 파일을 쓰면 어떤 환경에서도 같은 구성이 재현된다.

#2핵심 질문

#2핵심 질문

#3동작 예시

Flask 웹 앱과 Redis 카운터를 각각 서비스로 정의한 compose.yaml 파일이 있다고 하자. docker compose up을 실행하면 Compose가 두 서비스를 함께 만들고 같은 네트워크에 연결하며, 웹 앱은 서비스 이름인 redis로 접속한다. docker compose down을 실행하면 두 컨테이너와 함께 만든 네트워크가 정리된다.

#4동작 과정

  1. 정의 읽기Compose가 compose.yaml을 읽어 각 서비스(실행할 컨테이너 단위)의 이미지·포트·환경 변수·의존 관계를 파악한다.

  3. 실행과 정리의존 관계에 따라 컨테이너를 시작하고 상태를 추적한다. down을 실행하면 컨테이너와 네트워크를 중지·삭제하고 남길 볼륨만 남긴다.

#2핵심 질문

Compose를 리눅스에 설치·갱신하고, 만든 모델을 다른 플랫폼용 리소스로 변환하려면 어떻게 해야 하는가?

#3동작 예시

Ubuntu에서 sudo apt-get install docker-compose-plugin을 실행하면 Compose 플러그인이 설치되고, docker compose version으로 확인한다. 이 플러그인은 docker CLI의 하위 명령(docker compose)으로 동작한다. Compose Bridge는 별도 명령으로 Compose 파일을 읽어 다른 플랫폼이 이해하는 리소스 정의로 변환한다.

#4동작 과정

  1. 저장소 설정과 설치배포판별 안내에 따라 Docker 저장소를 등록하고 패키지 색인을 갱신한 뒤 패키지를 설치한다. 필요하면 바이너리를 직접 배치하는 수동 설치를 쓴다.
  2. 버전 확인과 갱신설치를 검증한 뒤 같은 패키지 명령으로 최신 버전으로 갱신하고, 더 이상 필요 없으면 제거한다.
  3. Bridge 변환Compose Bridge가 Compose 모델을 대상 플랫폼의 리소스로 변환한다. 기본 변환 규칙을 쓰거나 직접 커스터마이즈한다.

Docker 엔진(데몬)과 컨테이너를 공격으로부터 보호하고, 사용자 네임스페이스·seccomp·AppArmor 같은 커널 보안 기능으로 컨테이너를 호스트 및 서로 격리하는 영역.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 사용자 매핑/etc/subuid와 /etc/subgid 파일로 호스트의 보조 사용자·그룹 ID 범위를 지정해 컨테이너 사용자를 재매핑한다.
  2. 격리 적용userns-remap을 활성화하면 데몬이 관리하는 컨테이너의 사용자 네임스페이스가 분리된다. 이때 데몬 자체는 여전히 root로 실행된다.

보안과 공급망 — 엔진·DHI·Scout07-02

콘텐츠 신뢰(Content Trust)

서명된 이미지만 pull·push 하도록 강제해 이미지의 출처와 무결성을 검증하는 Docker Content Trust(DCT) 기능.

#1문제 상황

이미지를 pull·push 할 때 기본 동작은 태그 이름만 확인하고 내려받는다. 태그는 같은 이름으로 언제든 다른 내용을 가리킬 수 있어서, 받은 이미지가 정말 그 게시자가 올린 것인지, 중간에 바뀌지 않았는지 확인할 방법이 없다. 그래서 자동화 파이프라인이 신뢰할 수 없는 레지스트리나 중간 경로를 거치면 검증되지 않은 이미지가 그대로 배포될 수 있다.

#2핵심 질문

서명되지 않은 이미지는 배포 단계에서 어떻게 차단하고, 서명된 이미지만 자동으로 올리고 내려받게 할 수 있을까?

#3동작 예시

CI 도구가 docker push 를 실행할 때 DOCKER_CONTENT_TRUST=1 환경 변수가 전달되면, 클라이언트는 이미지를 올리기 전에 Notary(서명 메타데이터를 보관·검증하는 서버)에 서명 정보를 함께 기록한다. 이후 누군가 그 이미지를 pull 하면 서명이 확인되어야만 다운로드가 진행된다.

#4동작 과정

  1. 서명 키 준비이미지에 서명할 키를 로컬 trust 저장소에 올린다. 위임 키를 추가할 때는 DOCKER_CONTENT_TRUST_REPOSITORY_PASSPHRASE 환경 변수로 암호를 넘겨 자동화에서도 사람 손 없이 키를 불러올 수 있다.
  2. 서명하며 pushDOCKER_CONTENT_TRUST=1 을 켠 상태에서 docker push 를 실행하면, 이미지 레이어와 태그에 대한 서명이 생성되어 레지스트리와 Notary에 함께 저장된다.
  3. 검증하며 pull신뢰가 켜진 클라이언트가 이미지를 받을 때 Notary의 서명을 먼저 검사하고, 서명이 없거나 어긋나면 다운로드를 거부한다. 그래서 검증되지 않은 이미지가 실행되지 않는다.

#5한 줄 요약

이미지에 서명을 붙이고 pull·push 시점에 그 서명을 강제 검사해, 출처와 무결성이 확인된 이미지만 유통되게 하는 것

Docker Hardened Images 개념

취약점을 최소화하고 서명·SBOM·증명 등 공급망 보안 정보를 포함하도록 Docker가 강화해 제공하는 Hardened Image(DHI)의 개념과 필요성.

#1문제 상황

일반 컨테이너 이미지는 호환성과 범용성을 위해 필요한 것보다 많은 구성 요소를 담는 경우가 많다. 안에 들어 있는 소프트웨어가 많을수록 취약점도 많아지고, 배포할 때마다 어떤 취약점(CVE, 공개된 보안 결함 목록)이 문제인지 하나씩 확인해야 한다. 결국 보안팀은 매주 쏟아지는 취약점 목록을 쫓아다니느라 정작 인프라를 개선할 시간을 쓰지 못한다.

#2핵심 질문

이미지 안에 꼭 필요한 것만 남겨 취약점을 줄이고, 그 이미지가 어떻게 만들어졌는지까지 증명할 수는 없을까?

#3동작 예시

Docker Hardened Images(DHI)는 처음부터 필요한 구성 요소만 넣는 최소 설계 방식을 취한다. 그래서 표준 이미지와 나란히 비교하면 이미지 크기가 줄고, 포함된 패키지 수가 적어 스캔에서 잡히는 취약점 수가 함께 줄어든다.

#4동작 과정

  1. 최소 구성으로 빌드베이스 이미지를 강화해 불필요한 패키지와 도구를 덜어낸다. 남는 소프트웨어가 적으니 공격 표면(공격자가 건드릴 수 있는 코드 범위)이 좁아진다.
  2. 공급망 정보 첨부SBOM(이미지에 포함된 소프트웨어 목록), 서명, 출처 증명(provenance, 이미지가 어떤 소스와 절차로 만들어졌는지 기록)을 이미지에 함께 붙인다. 이를 통해 이미지의 구성과 유래를 나중에 검증할 수 있다.
  3. 지속 검사와 제공이미지에 대해 악성코드 스캔과 취약점 검사를 수행하고, CIS 벤치마크·STIG 같은 보안 기준 준수 정보도 함께 제공한다. 사용자는 별도 조사 없이 검증된 결과를 확인하고 그대로 배포할 수 있다.

#5한 줄 요약

이미지를 최소 구성으로 만들어 취약점을 줄이고, SBOM·서명·증명 같은 공급망 정보를 함께 제공해 검증된 이미지를 쓰게 하는 것

DHI 사용과 마이그레이션

Docker Hardened Images를 내려받아 사용하는 방법과 기존 이미지에서 DHI로 옮기는 절차.

#1문제 상황

기존에는 Docker Hub의 일반 이미지나 직접 만든 이미지를 그대로 받아 쓰는 방식이 흔했다. 이 방식은 쓰기 편하지만 이미지 안에 어떤 패키지가 들어 있는지, 보안 업데이트가 언제 반영되는지를 사용자가 직접 관리해야 한다. 그래서 기존 이미지를 쓰던 프로젝트를 강화 이미지로 옮기려면 무엇을 바꿔야 하는지, 어떤 이미지로 대체해야 하는지가 분명하지 않다.

#2핵심 질문

기존 이미지를 쓰던 프로젝트를 Docker Hardened Image로 옮기려면 어떤 순서로 확인하고 교체해야 할까?

#3동작 예시

DHI 퀵스타트에서는 Docker 계정으로 로그인한 뒤 dhi.io의 DHI Community 이미지를 pull·run 하고, 같은 용도의 Docker Official Image와 나란히 비교한다. 두 이미지를 직접 실행해 크기와 포함 패키지 차이를 눈으로 확인하는 것이 출발점이다.

#4동작 과정

  1. 이미지 탐색과 선택Docker Hub의 Hardened Images 카탈로그에서 검색과 필터로 쓸 이미지를 고른다. 다루는 언어·런타임에 맞는 이미지를 골라야 이후 교체가 자연스럽다.
  2. 내려받아 실행로그인 후 이미지를 pull 하고 그대로 실행해 동작을 확인한다. 필요하면 설정 파일이나 패키지를 덧붙이는 방식으로 이미지를 커스터마이즈해 기존 앱 요구에 맞춘다.
  3. 마이그레이션 점검마이그레이션 체크리스트에 따라 Alpine·Debian·Ubuntu·Wolfi 같은 기존 베이스를 DHI로 바꾸고, 스캔과 검증 단계를 거쳐 교체가 끝났는지 확인한다.

#5한 줄 요약

기존 이미지를 강화 이미지로 교체할 때 탐색·실행·점검 순서를 따라 안전하게 옮기고 검증까지 마치게 하는 것

Docker Scout

이미지와 SBOM을 분석해 취약점과 정책 위반을 찾아내 공급망 보안을 강화해 주는 Docker의 보안 도구.

#1문제 상황

이미지를 빌드하고 배포해도 그 안에 어떤 패키지가 들어 있고 어떤 취약점이 있는지 바로 알기 어렵다. 버전을 올릴 때마다 취약점이 늘었는지 줄었는지 비교하려면 사람이 일일이 스캔 결과를 대조해야 한다. 그 결과 무엇을 먼저 고쳐야 하는지 판단이 늦어지고, 팀과 결과를 공유하기도 번거롭다.

#2핵심 질문

이미지와 SBOM을 분석해 어떤 취약점과 정책 위반이 있는지 자동으로 찾아내고 고칠 방법까지 알려줄 수는 없을까?

#3동작 예시

Docker Scout 퀵스타트에서는 취약점이 있는 Node.js 예제 애플리케이션을 scout-demo:v1 태그로 빌드해 조직 네임스페이스에 push한다. Scout이 그 이미지를 분석해 패키지와 취약점 목록, 그리고 문제를 어떻게 해결할지에 대한 제안을 보여 준다.

#4동작 과정

  1. 이미지 분석Scout이 이미지 내용과 SBOM을 읽어 포함된 패키지와 취약점을 찾아낸다. 그 결과가 이미지 상세 화면과 대시보드에 정리되어 표시된다.
  2. 비교와 정책 평가이전 버전과 나란히 비교해 취약점이 늘었는지 줄었는지 보여 주고, 정책 규칙에 어긋나는 항목이 있는지 평가한다. 그래서 릴리스 전에 무엇을 고쳐야 하는지 분명해진다.
  3. 예외 처리와 공유정말 문제가 되지 않는 취약점은 예외로 등록하거나 VEX(취약점의 실제 영향 여부를 표현하는 형식)로 표시해 걸러낸다. CLI나 CI/CD 연동, 메트릭 내보내기로 결과를 팀과 파이프라인에 공유한다.

#5한 줄 요약

이미지와 SBOM을 분석해 취약점·정책 위반을 찾아내고 고칠 방향까지 제시해 공급망 보안을 강화하는 것

2단계 인증·액세스 토큰·역할과 권한 관리 등으로 Docker 계정을 안전하게 보호하는 방법.

#1문제 상황

#2핵심 질문

비밀번호 하나가 새더라도 계정과 조직 자원을 안전하게 지키려면 어떤 인증과 권한 장치를 겹쳐야 할까?

#3동작 예시

Docker 계정 설정에서 2단계 인증(2FA)을 켜면, 로그인할 때 비밀번호 외에 인증 앱이 만드는 6자리 코드를 한 번 더 요구한다. 이때 복구 코드를 복사하거나 인쇄해 두면 인증 기기를 잃어버려도 계정을 되찾을 수 있다.

#4동작 과정

  1. 2단계 인증 켜기인증 앱, 계정 비밀번호, 확인된 이메일을 준비한 뒤 계정 설정에서 2FA를 활성화하고 QR 코드나 텍스트 코드로 인증 앱을 등록한다. 이후 로그인마다 두 번째 코드가 필요해져 비밀번호만으로는 들어올 수 없다.
  2. 토큰 분리 발급자동화와 도구에는 개인 액세스 토큰이나 조직 액세스 토큰을 따로 발급해 쓴다. 사람 비밀번호 대신 용도별 토큰을 쓰면 유출 시 피해를 좁히고 폐기도 쉽다.
  3. 권한과 SSO 정리역할과 권한, 조직 액세스 토큰, OIDC 연결과 SSO(조직이 자체 로그인 체계로 사용자를 인증하는 방식)를 설정해 누가 무엇에 접근하는지 통제한다. 접근 권한이 최소로 유지되어 계정 보호가 한층 강해진다.

Hub 이미지 라이브러리와 신뢰 표시

Docker Hub에서 이미지를 검색·탐색하고, Docker 공식 이미지·검증 퍼블리셔·스폰서 오픈소스 같은 신뢰 표시(배지)로 공급자를 가늠하는 영역이다.

#1문제 상황

Docker Hub에는 수많은 이미지가 올라와 있어, 처음 쓰는 사람은 어떤 이미지를 믿고 써야 할지 판단하기 어렵다. 이름만 보고 아무 이미지나 받으면 문서가 없거나 업데이트가 끊긴 것을 쓸 수도 있고, 검증되지 않은 이미지가 위험을 안고 올 수 있다. 그래서 이미지 공급자를 가늠할 신뢰 기준이 필요하다.

#2핵심 질문

수많은 이미지 중에서 신뢰할 수 있는 공급자의 이미지를 어떻게 구분하고 골라 쓸 수 있을까?

#3동작 예시

Docker Hub의 신뢰 콘텐츠는 큐레이션된 고품질 이미지 모음으로, Docker Official Images, Docker Hardened Images와 차트, Verified Publisher 이미지, Docker-Sponsored Open Source 소프트웨어 이미지를 포함한다. 사용자는 배지와 표시를 보고 공식·검증 이미지를 골라 기반으로 삼는다.

#4동작 과정

  1. 검색과 탐색Docker Hub에서 검색과 필터로 필요한 이미지를 찾고, 설명과 문서를 확인한다. 이 단계에서 쓸 만한 후보를 좁힌다.
  2. 신뢰 표시 확인Docker Official Images, Verified Publisher, Docker-Sponsored Open Source 같은 신뢰 표시(배지)를 보고 공급자가 공식인지 검증됐는지 판단한다. 이로써 안정적이고 정기적으로 갱신되는 이미지를 고를 수 있다.
  3. 보안 정보 확인이미지 보안 인사이트와 분석 지표로 알려진 취약점과 유지보수 상태를 확인한다. 최종 선택 전에 위험 요소를 가늠하고 배포에 쓴다.

#5한 줄 요약

Docker Hub의 신뢰 표시와 보안 정보로 이미지 공급자를 판단해 안전한 이미지를 골라 쓰게 하는 것

Docker Hub와 조직 관리08-02

Hub 저장소 관리

Docker Hub에서 저장소를 만들고 태그·이미지·설명·접근 권한 같은 저장소 자산을 관리하는 방법이다.

#1문제 상황

Docker Hub에서 저장소를 만들고 이미지를 올리다 보면 태그와 이미지가 계속 쌓여 관리가 어려워진다. 어떤 이미지가 어떤 아키텍처용이고 어떤 태그가 최신인지 뒤섞이면, 잘못된 이미지를 배포하거나 오래된 것을 남겨 두기 쉽다. 게다가 태그가 바뀌면 같은 이름이 다른 내용을 가리켜 재현성도 흔들린다.

#2핵심 질문

저장소에 쌓이는 이미지·태그·접근 권한을 어떻게 정리하고 통제해야 안전하게 운영할 수 있을까?

#3동작 예시

이미지 인덱스는 여러 아키텍처용 이미지(예: AMD, ARM)를 하나로 묶어 단일 참조로 여러 플랫폼에서 동작하게 한다. 저장소 관리 화면에서 이미지와 인덱스를 골라 삭제하거나 태그를 정리하면, 하나의 태그로 여러 플랫폼을 커버하는 구조가 유지된다.

#4동작 과정

  1. 저장소 준비Docker Hub에 로그인해 저장소를 만들고, 설명과 접근 권한을 설정한다. 누가 읽고 쓸 수 있는지 정해 두면 이후 이미지 관리가 안전해진다.
  2. 이미지와 태그 정리이미지 관리 화면에서 이미지와 이미지 인덱스를 확인하고, 불필요한 항목을 지우거나 이동한다. 이때 불변(immutable) 태그가 붙은 이미지는 삭제할 수 없고, 변경 가능한 태그가 달린 항목만 지울 수 있다.
  3. 자동화와 점검웹훅으로 이미지 이벤트를 외부에 알리고, 조직 저장소를 CSV로 내보내 현황을 파악한다. 그래야 저장소 자산이 한눈에 정리된 상태로 유지된다.

#1문제 상황

기존에는 소스 코드를 고칠 때마다 개발자가 자기 컴퓨터에서 docker build를 직접 실행하고 태그를 붙여 docker push로 저장소에 올려야 했다. 이미지를 갱신할 때마다 이 수동 과정을 반복해야 했고, 빌드가 개인 환경에 묶여 있어 어떤 코드로 만든 이미지인지 일관되게 남지 않았다. 테스트를 통과하지 않은 이미지가 그대로 올라갈 위험도 있었다.

#2핵심 질문

소스 저장소에 코드를 올리면 Docker Hub가 대신 이미지를 빌드하고, 검증된 것만 올리게 할 수는 없을까?

#3동작 예시

GitHub 저장소의 특정 브랜치를 Docker Hub의 저장소에 연결해 두면, 그 브랜치에 커밋이 푸시될 때마다 Docker Hub가 소스를 받아 이미지를 빌드한다. 자동 테스트가 설정돼 있으면 테스트가 성공한 경우에만 새 이미지가 푸시된다. 사람이 로컬에서 빌드·푸시하지 않아도 이미지가 갱신된다.

#4동작 과정

  1. 저장소 연결Docker Hub에서 My Hub > Repositories로 들어가 대상 저장소를 열고 Builds 탭에서 GitHub 또는 Bitbucket을 선택해 이미지 소스 코드가 있는 곳을 연결한다. 이때 코드 저장소 서비스를 연결하기 위해 설정 페이지로 이동될 수 있다.
  2. 빌드 소스 지정빌드할 소스 저장소를 고르고, 필요하면 소스 제공자에서 조직이나 사용자를 지정한다. 기존 자동 빌드 설정을 고치는 경우에는 Configure automated builds를 선택한다.
  3. 자동 빌드와 푸시푸시가 감지되면 Docker Hub가 이미지를 빌드하고, 자동 테스트가 설정돼 있으면 테스트가 성공해야만 새 이미지를 푸시한다. 이 자동 빌드는 Pro·Team·Business 구독이 필요하며, 지원 종료가 예고된 기능이다.

#3동작 예시

#4동작 과정

  1. 도메인 검증조직에서 사용할 도메인을 등록하고 검증한다. 자동 프로비저닝을 켜려면 도메인 검증이 먼저 이뤄져야 한다.

  3. 로그인 시 자동 추가검증된 도메인 이메일로 사용자가 로그인하면 조직에 자동으로 추가된다. SSO 연결에 속한 도메인은 Just-in-Time(JIT) 프로비저닝이 자동 프로비저닝보다 우선한다.

AI 클라이언트에 MCP 서버를 붙이려면 서버마다 의존성을 설치하고 실행 설정을 맞춰야 했다. 서버가 늘어나면 프로젝트별로 어떤 서버를 켜 둘지 관리하기 어렵고, 클라이언트마다 연결 설정을 반복해야 했다. 설정 부담이 커질수록 MCP 도구를 실제로 쓰기까지의 진입이 어려워졌다.

#2핵심 질문

MCP 서버를 설치·설정 부담 없이 골라 실행하고, AI 클라이언트에 한 번에 연결할 수는 없을까?

#3동작 예시

Docker Desktop에 통합된 MCP Toolkit에서 MCP Catalog의 서버를 골라 컨테이너로 실행하고, 프로필(profile)로 묶어 AI 에이전트에 연결한다. 예를 들어 프로젝트별로 서로 다른 서버 묶음을 프로필로 만들어, 그 프로필에 담긴 서버만 클라이언트에 노출할 수 있다. 별도 의존성 관리나 런타임 설정 없이 실행된다.

#4동작 과정

  1. 서버 발견과 실행Docker Desktop 안에서 MCP Catalog를 보고 컨테이너화된 MCP 서버를 골라 실행한다. 의존성 관리나 런타임 설정이 필요 없다.
  2. 프로필로 묶기서버들을 프로필로 나눠 프로젝트·환경별 서버 모음을 만든다. 프로필이 클라이언트가 각 서버에 접근하는 관문 역할을 한다.
  3. 클라이언트 연결프로필을 Claude, Cursor 등 MCP 클라이언트에 연결한다. 여러 LLM 기반 클라이언트를 함께 지원한다.

Docker Sandboxes 개념

에이전트를 호스트와 격리된 일회성 실행 환경에서 돌리기 위한 Docker Sandboxes의 구조와 격리 방식, 로컬·클라우드 형태의 차이를 설명하는 개념이다.

#1문제 상황

코딩 에이전트를 호스트 머신에 그대로 설치해 실행하면, 에이전트가 실행하는 명령이 호스트의 실제 파일과 패키지, 네트워크에 그대로 닿는다. 에이전트가 잘못된 경로를 지우거나 전역 패키지를 바꾸면 호스트 환경 자체가 손상되고, 어떤 변경이 어디까지 번졌는지 추적하기도 어렵다. 격리 계층이 없으면 한 번의 실수가 곧 호스트 전체의 문제가 된다.

#2핵심 질문

에이전트가 호스트를 건드리지 않고 자유롭게 설치하고 실행하도록 하려면 무엇을 어떻게 격리해야 하는가?

#3동작 예시

sbx create에 워크스페이스 경로를 넘기지 않으면 호스트 작업 디렉터리를 바인드 마운트하지 않고, 템플릿 이미지에 설정된 WORKDIR을 기본 작업 디렉터리로 쓴다. Docker가 제공하는 에이전트 템플릿은 이 값을 /home/agent/workspace로 정해 두고, 그 안에서 만든 파일은 샌드박스 안에 남아 중지와 재시작 사이에도 유지된다. 경로를 넘기면 그 디렉터리가 파일시스템 통과 방식으로 마운트되어 샌드박스가 호스트의 실제 파일을 보게 된다.

#4동작 과정

  1. 환경 준비이미지 설정에서 사용할 수 있는 절대 경로 WORKDIR(작업 기준 디렉터리)를 확인하고, 없으면 /home/agent/workspace로 대체한다. 이로써 샌드박스는 호스트와 분리된 자기 작업 공간을 갖는다.
  2. 실행 격리에이전트가 샌드박스 안에서 패키지 설치와 명령 실행을 자유롭게 수행한다. 그 결과물은 샌드박스 내부에만 쌓여 호스트에는 반영되지 않는다.
  3. 수명 관리샌드박스를 중지하고 재시작해도 내부 파일은 유지되고, 샌드박스를 제거하면 그 안의 변경이 함께 정리된다.

에이전트의 실행 환경을 호스트와 분리된 일회성 공간으로 두어 자유로운 작업과 호스트 보호를 동시에 얻는 것

#1문제 상황

에이전트에게 이미지 빌드와 테스트, 데이터베이스 기동 같은 개발 작업을 맡기면, 그 활동이 호스트의 Docker 데몬과 자원에 그대로 나타난다. 호스트에서 직접 돌린 컨테이너와 에이전트가 만든 컨테이너가 뒤섞여 docker ps 출력이 지저분해지고, 설치한 패키지와 이미지가 호스트에 계속 남는다. 작업이 끝난 뒤 정리할 대상이 명확하지 않아 환경이 점점 오염된다.

#3동작 예시

샌드박스 안에서 에이전트는 sudo 권한을 가지므로 패키지를 설치하고 데이터베이스를 띄우며 테스트 의존성을 준비할 수 있고, 설치한 패키지는 그 샌드박스의 수명 동안 유지된다. 에이전트는 이미지를 빌드하고 컨테이너를 실행하며 Compose도 쓸 수 있지만, 이 모든 것은 샌드박스 안의 사설 Docker 데몬에서 돌기 때문에 호스트의 docker ps에는 절대 나타나지 않는다. 샌드박스를 제거하면 그 안의 이미지와 컨테이너와 볼륨이 함께 삭제된다.

#4동작 과정

  1. 환경 구성에이전트가 샌드박스 안에서 sudo로 필요한 패키지와 서비스, 테스트 의존성을 설치한다. 이 준비 작업은 그 샌드박스에만 적용되어 호스트에는 설치 흔적이 남지 않는다.
  2. 빌드와 테스트 실행에이전트가 사설 Docker 데몬에서 이미지를 빌드하고 컨테이너를 띄워 프로젝트 테스트를 돌린다. 컨테이너는 호스트 데몬이 아니라 샌드박스 내부에서만 보인다.
  3. 정리와 반복반복되는 준비 과정은 커스터마이즈로 템플릿이나 킷으로 묶고, 작업이 끝난 샌드박스를 제거하면 내부 자원이 한 번에 정리된다.

Docker Build Cloud

Docker 가 제공하는 관리형 클라우드 빌드 서비스로, 로컬 머신 대신 클라우드 빌더에서 이미지를 빠르게 빌드한다.

#1문제 상황

기존에는 개발자 각자의 로컬 머신에서 docker build를 실행해 이미지를 만들었다. 빌드에 쓰이는 CPU·메모리·네트워크가 그 사람의 노트북에 묶여 있어, 사양이 낮으면 빌드가 오래 걸리고 그동안 다른 작업을 하기 어렵다. 팀원마다 캐시가 따로 쌓여 같은 이미지를 여러 번 처음부터 다시 빌드하는 낭비도 생긴다.

#2핵심 질문

로컬 머신 자원에 묶이지 않고 이미지를 더 빠르게 빌드하려면 어떻게 해야 하는가?

#3동작 예시

빌드 명령에 --builder 플래그를 붙여 클라우드 빌더를 지정하면, 빌드 작업이 그 빌더에서 실행된다. 예를 들어 docker buildx build --builder cloud-<ORG>-<BUILDER_NAME> --tag <IMAGE> .처럼 실행하면 <ORG> 조직에 속한 클라우드 빌더가 빌드를 대신 수행한다. 매번 플래그를 붙이기 번거로우면 docker buildx use cloud-<ORG>-<BUILDER_NAME> --global로 그 빌더를 기본값으로 삼을 수 있다.

#4동작 과정

  1. 빌더 지정--builder 플래그로 클라우드 빌더 이름을 넘기거나, docker buildx use ... --global로 기본 빌더로 설정한다. 이렇게 하면 빌드 요청이 로컬이 아니라 선택한 클라우드 빌더로 향한다.
  2. 클라우드에서 빌드 실행지정된 빌더가 이미지 빌드를 수행한다. 로컬 머신은 빌드 연산을 하지 않으므로 그 자원이 비고, 빌더에 공유된 캐시를 재사용할 수 있다.
  3. 이미지 반환빌드가 끝난 이미지가 결과로 돌아온다. 로컬 머신에서는 이 이미지를 그대로 실행하거나 레지스트리에 푸시하면 된다.

Docker Offload

로컬의 빌드·실행 작업을 클라우드의 관리형 Docker 환경으로 넘겨 로컬 자원 부족 없이 컨테이너 작업을 처리하는 기능이다.

#1문제 상황

기존에는 컨테이너 빌드와 실행이 모두 로컬 Docker Desktop 위에서 이뤄졌다. 이 방식은 로컬 CPU·메모리·디스크 성능에 그대로 묶여, 무거운 워크로드를 돌리면 머신이 느려지거나 메모리가 부족해진다. 가상 데스크톱(VDI) 환경이나 중첩 가상화를 지원하지 않는 시스템에서는 아예 컨테이너를 돌리기 어렵다는 제약도 있다.

#2핵심 질문

로컬 자원이 부족하거나 가상 환경이라도 익숙한 Docker 도구 그대로 컨테이너 작업을 이어가려면 어떻게 해야 하는가?

#3동작 예시

Docker Desktop, Docker CLI, Docker Compose처럼 이미 쓰던 도구로 명령을 내리면, 그 작업이 클라우드에 임시로 만들어진 실행 환경에서 처리된다. 사용자는 로컬에서 하던 것과 같은 방식으로 포트를 열고 파일을 붙이며 컨테이너를 다루지만, 실제 연산은 클라우드 러너가 맡는다.

#4동작 과정

  1. 클라우드 러너 준비컨테이너 세션마다 클라우드 환경이 자동으로 만들어진다. 작업이 끝나면 이 환경은 자동으로 정리되어 임시로만 존재한다.
  2. 안전한 연결Docker Desktop과 클라우드 환경 사이는 암호화된 터널로 연결된다. 이 통로를 통해 시크릿과 이미지를 안전하게 주고받고, 포트 포워딩과 바인드 마운트(로컬 폴더를 컨테이너에 연결하는 것)로 로컬 개발 경험을 유지한다.
  3. 작업 수행과 반환클라우드에서 빌드·실행이 이뤄진다. 로컬 자원을 거의 쓰지 않으므로 VDI나 중첩 가상화 미지원 시스템에서도 컨테이너 작업을 계속할 수 있다.

Extensions 개요와 배포

Docker Desktop 에 추가 설치해 기능을 확장하는 플러그인으로, 마켓플레이스를 통해 배포·설치한다.

#1문제 상황

기존 Docker Desktop은 이미지 빌드·실행·관리라는 정해진 기능만 제공했다. 그 밖에 로그 확인, 데이터베이스 관리, 클라우드 연동 같은 부가 작업을 하려면 별도 도구를 따로 설치해 Docker와 오가며 써야 했다. 필요한 기능을 Docker Desktop 안에서 바로 꺼내 쓰는 방법이 없었던 것이다.

#2핵심 질문

Docker Desktop에 없던 기능을 외부 개발자가 만들어 붙이고, 사용자는 그것을 안전하게 골라 설치하려면 어떻게 해야 하는가?

#3동작 예시

Docker Desktop 대시보드에서 Extensions 탭을 열면 Extensions Marketplace의 Browse 탭이 나타난다. 여기서 쓸 수 있는 확장을 둘러보고 설치하면, 그 기능이 Docker Desktop 안에 추가된다. 일부 확장은 사용 전에 별도 계정을 만들어야 한다.

#4동작 과정

  1. 마켓플레이스에서 탐색Marketplace에는 두 종류의 확장이 있다. Docker Extensions 팀이 직접 검토해 Reviewed로 표시되는 확장과, 개발자가 자율 게시하고 자동 검증만 거쳐 Not reviewed로 표시되는 확장이다.
  2. 설치대시보드의 Extensions 탭에서 원하는 확장을 골라 설치하면 Docker Desktop에 기능이 더해진다. 이때 확장은 호스트 수준 권한으로 실행되어 바이너리 설치, Docker Engine 접근, 명령 호출, 파일 접근까지 할 수 있으므로 신뢰하는 게시자의 확장만 설치해야 한다.
  3. 사용과 관리설치한 확장은 Docker Desktop 안에서 바로 쓴다. Marketplace 확장은 Docker가 검토하지만 전체 보안 감사까지 거치는 것은 아니라는 점을 감안해 신뢰 여부를 판단한다.

  3. 개발과 게시메타데이터와 보안 요건을 갖춰 확장을 빌드하고, 이미지 라벨을 붙이고, 필요하면 멀티 아키텍처로 만든 뒤 Marketplace에 게시한다.

Testcontainers

테스트 코드에서 일회용 컨테이너를 띄워 실제 DB·서비스 환경 그대로 통합 테스트를 수행하게 해주는 라이브러리다.

#1문제 상황

기존 통합 테스트는 실제 DB나 외부 서비스 대신 목(mock)이나 인메모리 서비스를 썼다. 이런 대체물은 운영 환경의 실제 서비스와 동작이 달라, 테스트는 통과했는데 운영에서 문제가 터지는 일이 생긴다. 실제 서비스를 테스트에 붙이려 해도 설치·설정·정리 부담이 커서 자동화가 어렵다.

#2핵심 질문

목이나 인메모리 대체물 없이, 운영에서 쓰는 것과 같은 실제 서비스로 테스트하려면 어떻게 해야 하는가?

#3동작 예시

테스트 코드 안에서 필요한 서비스를 Docker 컨테이너로 띄우고, 그 주소로 테스트 대상 코드를 연결한다. 예를 들어 DB가 필요한 테스트라면 그 테스트가 시작될 때 실제 DB 컨테이너가 뜨고, 코드는 목이 아니라 그 컨테이너에 붙어 쿼리를 실행한다. 테스트가 끝나면 컨테이너는 정리된다.

#4동작 과정

  1. 의존 서비스 정의테스트가 필요로 하는 DB·서비스 이미지를 코드로 지정한다. librarie들이 컨테이너 시작·중지·연결 정보 조회를 대신 처리하는 가벼운 API를 제공한다.
  2. 컨테이너 기동테스트 실행 시 해당 서비스가 Docker 컨테이너로 로컬에 뜬다. 이것은 운영에서 쓰는 것과 같은 실제 서비스이므로 목이나 인메모리 서비스가 필요 없다.
  3. 테스트와 정리코드가 그 컨테이너에 연결해 실제 환경 그대로 테스트를 수행하고, 끝나면 컨테이너가 정리된다. 운영 의존성과 같은 조건에서 검증되므로 배포 후 어긋날 위험이 줄어든다.

#5한 줄 요약

테스트가 필요로 하는 실제 서비스를 일회용 컨테이너로 띄워 운영 환경과 같은 조건에서 통합 테스트를 하게 하는 것

#2핵심 질문

앱이 의존하는 DB·메시징·프록시 같은 인프라를 운영 환경과 가깝게, 설치 부담 없이 로컬에서 돌리려면 어떻게 해야 하는가?

#3동작 예시

#4동작 과정

  1. 컨테이너로 DB 실행로컬에서 DB 컨테이너를 띄운다. 호스트에서도, 다른 컨테이너에서도 그 DB에 접속할 수 있고, 컨테이너 셸에 들어가 직접 다룰 수도 있다.

GenAI·AI 가이드

RAG, PDF 챗봇, 에이전트 앱 등 생성형 AI·AI 애플리케이션을 Docker로 구축하고 실행하는 공식 가이드.

#1문제 상황

대규모 언어 모델(LLM, 방대한 텍스트로 학습해 문장을 생성하는 모델)은 학습 시점에 없던 정보를 모른다. 그래서 사내 문서나 최신 데이터를 물어보면 그럴듯하지만 틀린 답을 만들어낸다.

이를 보완하려고 외부 지식 소스를 검색해 붙이는 RAG(검색 증강 생성)를 쓰지만, 전통적인 RAG는 대부분 벡터 데이터베이스에 문장 조각을 저장한다. 이 방식은 조각들 사이의 연결 관계를 살리지 못해, "누가 누구와 어떤 관계인가" 같은 관계 중심 질문에는 약하다.

#2핵심 질문

검색한 정보를 모델에 붙여 줄 때, 데이터 사이의 연결 관계까지 살려서 더 정확한 답을 만들 수 없을까?

#3동작 예시

Neo4j 같은 그래프 데이터베이스(데이터를 점과 선의 연결로 저장하는 DB)에 문서를 넣고 RAG와 결합한다. 사용자가 "A 부서가 담당하는 프로젝트를 맡은 사람"을 물으면, 질문을 벡터로 바꿔 관련 조각을 찾는 동시에 그래프를 따라 A 부서와 연결된 프로젝트와 사람 노드를 함께 끌어온다.

이렇게 모은 연결 정보를 프롬프트(모델에 주는 입력문)에 함께 넣어 보내면, 모델은 조각 하나만 보고 추측하지 않고 관계를 근거로 답한다.

#4동작 과정

  1. 지식 적재문서를 잘게 나눠 임베딩(문장을 숫자 벡터로 바꾸는 것)으로 저장하고, 문서·사람·개체 사이의 관계도 그래프에 함께 기록한다. 그래서 검색이 "비슷한 문장"뿐 아니라 "연결된 대상"도 찾을 수 있게 된다.
  2. 검색 및 결합사용자 질문을 벡터로 바꿔 관련 조각을 찾고, 그래프를 따라 이어진 노드까지 모아 하나의 문맥으로 묶는다. 그래서 답의 근거가 되는 정보 범위가 넓어진다.
  3. 생성 및 배포이 문맥과 질문을 LLM에 넘겨 답을 만들고, 이 스택 전체를 Docker 컨테이너(앱과 실행 환경을 한 묶음으로 포장한 단위)로 올려 어디서든 같은 구성으로 실행한다. 그래서 모델·DB·앱 버전이 어긋나지 않는다.

외부 지식의 검색 결과에 데이터 간 연결 관계를 더해 LLM의 답을 근거 있게 만드는 것

공식 랩

Docker가 제공하는 실습형 튜토리얼(Lab)로, 정해진 순서를 따라 하며 이미지 빌드·Compose·MCP 등을 직접 익히는 학습 자료.

#1문제 상황

문서를 읽기만 하면 명령어와 개념이 머릿속에 남지 않는다. 실제로 컨테이너를 띄우고 이미지를 만들어 봐야 하는데, 직접 환경을 준비하려면 도구 설치와 버전 충돌을 먼저 해결해야 한다.

그 준비 과정에서 막히면 정작 배워야 할 Docker의 핵심 개념에 도달하기 전에 포기하게 된다.

#2핵심 질문

설치와 설정에 시간을 쓰지 않고, 정해진 순서를 따라가며 컨테이너를 직접 다뤄 볼 수는 없을까?

#3동작 예시

Docker 공식 랩은 labspace라는 실습 환경을 명령어 한 줄로 띄운다. 예를 들어 Getting Started 랩은 docker compose -p labspace -f oci://dockersamples/labspace-container-getting-started up -d를 실행하면 필요한 환경이 컨테이너로 올라오고, 브라우저에서 http://localhost:3030을 열면 실습 화면이 뜬다.

이 화면에서 미리 만들어진 컨테이너를 실행하고, Node.js 앱을 패키징하는 Dockerfile을 직접 쓰고, 이미지를 빌드하고, 끝나면 docker compose -p labspace down으로 정리한다.

#4동작 과정

  1. 환경 실행docker compose up 한 줄로 labspace(실습용 컨테이너 묶음)를 내려받아 실행한다. 그래서 별도 설치 없이 브라우저만으로 실습을 시작할 수 있다.
  2. 순서대로 실습모듈별 안내를 따라 컨테이너 실행, 로그·파일시스템 확인, 라이프사이클 관리, Dockerfile 작성과 레이어 캐시(변경 없는 단계를 재사용해 빌드를 빠르게 하는 것)를 익힌다. 그래서 개념이 실제 명령과 결과로 연결된다.
  3. 정리 및 확장실습이 끝나면 docker compose down으로 환경을 내리고, 원하면 만든 이미지를 Docker Hub에 올려 본다. 그래서 배운 흐름을 실제 배포까지 이어 볼 수 있다.

관리자·워크플로 가이드

조직 도입, 사용자·접근 관리, CI 파이프라인 연동 등 관리자와 개발 워크플로를 위한 공식 가이드.

#1문제 상황

조직에 Docker를 들여오면 개발자마다 환경이 제각각이 된다. 어떤 팀은 최신 버전을, 어떤 팀은 예전 설정을 쓰고, 계정과 권한은 아무 기준 없이 늘어난다.

그 결과 빌드가 사람마다 다르게 나오고, 접근 권한을 통제하기 어렵고, 보안·컴플라이언스 정책을 지키기 힘들어진다. 개발자는 배포 문제를 매번 손으로 해결하다 시간을 잃는다.

#2핵심 질문

조직 전체가 같은 환경과 통제된 권한으로 Docker를 쓰면서 개발 속도를 떨어뜨리지 않으려면 어떻게 설정해야 할까?

#3동작 예시

관리자가 조직 계정과 사용자·접근 관리를 표준으로 맞춘다. 그리고 Buildx Bake나 Compose Bake 같은 빌드 정의 파일로 여러 이미지와 플랫폼(x86, ARM 등)을 한 번에 빌드하도록 규칙을 정한다.

이렇게 하면 개발자는 로컬에서도 CI 파이프라인에서도 같은 명령으로 같은 결과를 얻고, 관리자는 Scout로 취약점을 점검하며 공급망을 통제할 수 있다.

#4동작 과정

  1. 환경·권한 표준화조직 단위로 Docker 제품을 구성하고 사용자와 접근 권한을 정리한다. 그래서 누가 무엇을 쓸 수 있는지가 일관되게 관리된다.
  2. 빌드·배포 규칙 통일Bake 정의와 Compose로 이미지와 멀티 컨테이너 앱 실행 방식을 한 파일에 선언한다. 그래서 로컬과 CI가 같은 빌드 결과를 낸다.
  3. 보안·검증 자동화Scout로 이미지의 취약점을 점검하고, 필요하면 Hardened Images(보안 강화 이미지)를 사용한다. 그래서 배포 전에 위험을 걸러내고 정책을 지킬 수 있다.

공식 문서가 제공하는 예제 애플리케이션 모음으로, 언어·스택별 실제 Dockerfile과 Compose 파일을 참고할 수 있다.

#1문제 상황

Dockerfile과 Compose 파일을 처음부터 직접 쓰면 시행착오가 크다. 특히 프레임워크마다 요구하는 베이스 이미지, 포트, 볼륨, 환경 변수 설정이 달라서 무엇이 정석인지 알기 어렵다.

이 상태로 배포용 파일을 만들면 개발 환경에서만 돌아가거나, 이미지가 불필요하게 커지거나, 데이터가 사라지는 문제가 뒤늦게 드러난다.

#2핵심 질문

언어와 스택별로 검증된 Dockerfile과 Compose 구성을 그대로 참고해 내 프로젝트에 맞게 시작할 수 없을까?

#3동작 예시

공식 샘플은 스택별로 완성된 예제를 제공한다. 예를 들어 Python 항목에는 Flask, Django, FastAPI 같은 프레임워크별 앱과, Nginx·MySQL·MongoDB 같은 부가 서비스를 함께 엮은 구성이 올라 있다. AI/ML 샘플은 Neo4j·LangChain·Ollama를 묶은 구성도 보여준다.

사용자는 이 중 자기 스택에 가까운 예제를 골라 Dockerfile과 Compose 파일을 그대로 가져다 쓰고, 이미지 이름과 소스 경로만 바꿔 실행한다.

#4동작 과정

  1. 예제 선택언어(Go, Java, Python 등)나 프레임워크 기준으로 목록에서 맞는 샘플을 고른다. 그래서 내 스택에 맞는 검증된 출발점을 얻는다.
  2. 파일 복사·조정샘플의 Dockerfile과 Compose 파일을 가져와 경로·포트·환경 변수를 내 프로젝트에 맞게 바꾼다. 그래서 처음부터 작성하지 않고 핵심만 손본다.
  3. 실행·확장docker compose up으로 여러 서비스를 함께 띄우고 동작을 확인한 뒤, 필요하면 DB나 캐시 같은 서비스를 같은 방식으로 덧붙인다. 그래서 개발 환경을 빠르게 재현한다.
