1Docker의 출발점01-01

Docker란 무엇인가

애플리케이션을 컨테이너로 싸서 개발·배포·실행하는 개방형 플랫폼이다.

#1문제 상황

애플리케이션을 서버에 올리려면 운영체제와 라이브러리 버전을 맞추느라 환경마다 다르게 동작했고, 되는 곳과 안 되는 곳이 갈렸다. 배포할 때마다 손으로 맞추다 보니 시간이 들고 실수도 잦았다.

팀원이 늘수록 각자 PC 환경이 달라 같은 코드가 다르게 도는 일이 반복됐다. 테스트를 통과한 것이 운영에서 깨지면 환경 탓인지 코드 탓인지 가리는 것부터 일이 됐다.

#2핵심 질문

개발한 그대로를 어디서든 똑같이 실행할 수는 없을까?

#3동작 예시

웹 앱과 실행 환경을 이미지 하나로 묶으면 노트북과 테스트 서버와 운영 서버가 같은 묶음을 돌려 결과가 같아진다. 개발자가 묶은 것을 테스트팀이 그대로 받고, 검증된 묶음이 운영으로 올라가니 환경 차이로 생기던 다툼이 사라진다. 묶음 안에는 코드와 해석기와 설정이 함께 굳어 있다.

#4동작 과정

  1. 이미지로 묶기앱과 실행 환경을 하나의 이미지로 만든다. 이미지에는 코드와 해석기와 설정이 함께 굳어 나중에 바뀌지 않는다.
  2. 어디든 나르기레지스트리에 올린 이미지를 필요한 곳에서 받는다. 전송되는 것은 파일 묶음이라 가볍고 버전별로 쌓인다.
  3. 똑같이 실행받은 이미지를 컨테이너로 띄워 동일하게 돌린다. 어디서 띄워도 안의 모습은 같아 환경 다툼이 사라진다.

#2핵심 질문

#3동작 예시

docker stop web으로 멈추고 docker start web으로 다시 켜고 docker rm web으로 지우면 수명주기가 손에 잡힌다. 재시작 정책을 걸어 두면 서버가 일어나며 따라 일어나 야근이 준다.

#2핵심 질문

#3동작 예시

save와 load로 이미지 파일을 옮기고 안 쓰는 이미지를 정리하는 방법이다.

→ 06-05 참조

#1문제 상황

망이 막힌 서버에는 레지스트리로 이미지를 못 가져갔다. 묵은 이미지가 쌓여 디스크가 차는데 무엇부터 지워야 할지 몰라 손을 못 댔고, 차는 대로 두다 멈췄다.

가져갈 길과 치울 길이 다 막히면 손이 묶인다. 옮기는 법과 비우는 법을 몰라 그때그때 허둥댔다.

#2핵심 질문

이미지를 파일로 옮기고 안 쓰는 것을 쓸어낼 수는 없을까?

#3동작 예시

save로 묶은 파일을 담아 가서 load로 풀고 prune으로 놀고 있는 것들을 한 번에 치우면 막힌 망에서도 돌리고 디스크도 비워진다. 옮길 길과 비울 길이 함께 뚫린다.

#4동작 과정

  1. 묶어내기save로 이미지 파일을 만든다. 파일이 곧 꾸러미라 들고 간다.
  2. 풀어넣기load와 import로 등록한다. 막힌 곳에서도 받아 돌릴 수 있다.
  3. 쓸어내기목록을 보고 지우고 prune으로 비운다. 놀고 있는 것이 먼저고 쓰는 것은 남는다.

Dockerfile이란

이미지를 만드는 설계도로 명령을 순서대로 적으면 빌드가 그대로 따라 만드는 문서다.

#1문제 상황

이미지를 손으로 조립하면 순서가 사람마다 달라 재현이 안 됐다. 나중에 같은 것을 만들려 해도 과정을 기억하지 못했고, 인수인계는 더 막막해 사람이 바뀌면 처음부터 다시 헤매야 했다.

손의 기억에 의존하니 팀이 흔들렸다. 잘 되던 것도 왜 되는지 몰라 고치면 깨졌다.

#2핵심 질문

만드는 과정을 문서로 적어두면 그대로 재현되지 않을까?

#3동작 예시

FROM과 COPY와 RUN을 순서대로 적은 파일을 build에 주면 누구나 같은 이미지를 같은 층으로 얻는다. 파일이 곧 레시피가 돼 사람이 바뀌어도 결과가 같다.

#4동작 과정

  1. 순서대로 적기기반·복사·설치를 명령으로 나열한다. 순서가 곧 층이라 읽으면 보인다.
  2. 빌드에 주기파일과 함께 보낼 묶음을 정한다. 보낼 범위가 정해져 새는 것이 없다.
  3. 그대로 얻기빌드가 적힌 대로 이미지를 쌓는다. 사람이 달라도 결과가 같아 믿을 수 있다.

FROM·WORKDIR·COPY

기반 이미지를 고르고 작업 위치를 정한 뒤 파일을 담는 이미지 뼈대 명령들이다.

#1문제 상황

매번 빈 바닥부터 운영체제와 실행환경을 깔려니 Dockerfile이 길어졌다. 파일 복사와 작업 위치가 제각각이라 읽기도 힘들고 고치기도 무서워 손을 못 댔다.

바닥부터 깔면 알게 모르게 달라졌다. 같은 파일인데 만든 사람마다 내용이 달라 믿을 수 없었다.

#2핵심 질문

바탕 고르기와 자리 잡기와 파일 담기를 세 명령으로 끝낼 수는 없을까?

#3동작 예시

FROM python:3.12에 WORKDIR /app을 잡고 COPY . .을 하면 소스가 이미지 안 정해진 자리로 들어간다. 세 줄로 뼈대가 서고 읽는 눈도 하나로 모인다.

#4동작 과정

  1. 바탕 고르기FROM으로 검증된 기반을 받는다. 바닥부터 깔지 않아 어긋날 곳이 없다.
  2. 자리 잡기WORKDIR로 기준 경로를 정한다. 이후 길의 기준이 돼 헤맬 일이 없다.
  3. 담기COPY로 필요한 파일을 넣는다. ADD는 특수한 때만 써서 단순하게 둔다.

RUN·CMD·ENTRYPOINT

RUN은 만들 때 실행하고 CMD와 ENTRYPOINT는 뜰 때 실행할 것을 정하는 명령들이다.

→ 02-05 참조

#1문제 상황

설치 명령과 실행 명령을 섞어 적으면 만들 때 돌릴 것과 뜰 때 돌릴 것이 뒤엉켰다. 실행 명령을 바꾸려 할 때마다 이미지를 다시 만들어 기다렸고, 기다림이 쌓여 고치기 싫어졌다.

뒤엉키니 읽는 것도 힘들었다. 어느 줄이 언제 도는지 몰라 손댈 곳을 못 찾았다.

#2핵심 질문

만들 때와 뜰 때를 갈라 실행 명령은 나중에 바꿀 수는 없을까?

#3동작 예시

RUN pip install로 만들 때 깔고 CMD ["python","app.py"]로 뜰 때 돌리면 실행 명령만 run에서 덮을 수 있다. ENTRYPOINT로 틀을 고정하면 인자만 바뀌는 형태로도 써서 굳히기와 바꾸기를 함께 얻는다.

#4동작 과정

  1. 만들 때 굳히기RUN으로 설치와 설정을 층에 박는다. 빌드 때 한 번 돌아 이미지에 남는다.
  2. 뜰 때 정하기CMD와 ENTRYPOINT로 기본 실행을 정한다. 컨테이너가 뜰 때 돌아 바꿀 여지가 남는다.
  3. 덮어 쓰기실행 시 인자로 기본 실행을 바꾼다. 이미지는 그대로 두고 결과만 바꾼다.

#1문제 상황

값이 흩어지니 바꿀 때마다 뒤져야 했다. 어디에 무엇이 있는지 아는 사람만 고칠 수 있었다.

#2핵심 질문

값과 용도와 주인을 이미지 안에 선언해 둘 수는 없을까?

#3동작 예시

ENV로 기본 포트를 정하고 ARG로 빌드 때 버전을 받고 EXPOSE 8000으로 용도를 알리고 USER app으로 낮춰 돌리면 이미지가 스스로를 설명한다. 받는 쪽은 읽기만 하면 된다.

#4동작 과정

  1. 값 정하기ENV는 실행값 ARG는 빌드값을 받는다. 살아가는 때가 달라 헷갈릴 일이 없다.
  2. 용도 알리기EXPOSE로 쓰는 포트를 표시한다. 여는 것은 게시가 하지만 용도는 여기서 안다.
  3. 주인 낮추기USER로 실행 사용자를 정한다. 관리자대로 돌리지 않아 탈 때 덜 아프다.

빌드에 보낼 파일 묶음을 정하고 빼고 빌드 속도와 보안을 챙기는 설정이다.

#1문제 상황

빌드할 때마다 폴더 통째가 넘어가 로그와 캐시까지 딸려 갔다. 전송이 느려지고 비밀 파일이 이미지에 섞여 들어가 보안 사고로 번질 뻔했고, 알고도 못 고치는 때가 있었다.

보낼 것을 안 가리니 매번 무거웠다. 무거운 것은 느리고 느린 것은 손이 안 가게 했다.

#2핵심 질문

보낼 묶음을 정하고 빼고 필요한 것만 넘길 수는 없을까?

#3동작 예시

.dockerignore에 .git과 node_modules를 적으면 빌드 묶음에서 빠져 전송이 가벼워지고 비밀도 안 섞인다. BuildKit은 쓰는 만큼만 달라고 하니 옛날처럼 통째로 넘기지 않는다.

#4동작 과정

  1. 묶음 정하기빌드 명령이 가리키는 경로가 묶음이 된다. 범위가 정해져 새는 것이 없다.
  2. 빼기.dockerignore로 빼고 것만 고른다. 비밀과 찌꺼기가 빠져 가벼워진다.
  3. 필요분만 넘기기빌드가 쓰는 만큼만 요청해 받는다. 옛날처럼 통째가 아니라 필요한 만큼만이다.

#1문제 상황

만드는 데 쓴 컴파일러와 소스가 최종 이미지에 그대로 남아 뚱뚱했다. 실행에 필요 없는 도구가 들어 있어 공격 면도 넓고 받는 시간도 길어 배포가 느려졌다.

돌리는 데 필요 없는 것이 돌리는 것에 딸려 다녔다. 무거운 것은 옮기기 힘들고 지키기도 힘들었다.

#2핵심 질문

만들 때와 돌릴 때를 나눠 결과물만 최종에 담을 수는 없을까?

#3동작 예시

golang 단계에서 지은 실행 파일 하나를 alpine 단계로 복사하면 컴파일러 없는 몇 MB 이미지가 남는다. 만드는 방과 도는 방이 나뉘어 가볍고 단단해진다.

#4동작 과정

  1. 만드는 단계도구를 갖춘 단계에서 결과물을 지는다. 소스와 도구는 여기까지고 나가지 않는다.
  2. 결과물만 옮기기COPY --from으로 필요한 것만 가져온다. 이름으로 단계를 가리켜 정확히 가져간다.
  3. 가볍게 굳히기최종 단계에는 실행분만 남긴다. 작고 단단해져 옮기고 지키기 쉽다.

늦게 아는 것은 비쌌다. 다 만들고 알면 고치는 데도 처음부터 다시 들어갔다.

#2핵심 질문

#4동작 과정

#1문제 상황

#2핵심 질문

#4동작 과정

  1. 수명 알기컨테이너 안 파일은 지우면 함께 간다는 것을 안다. 읽기쓰기 층의 운명이라 피할 수 없다.
  2. 밖에 두기오래 둘 것은 별도 저장소에 둔다. 셋 중에 골라 두면 수명이 갈라진다.
  3. 이어 쓰기새 컨테이너가 같은 곳을 본다. 갈아끼워도 끊기지 않아 운영이 된다.

여러 컨테이너를 한 앱으로 묶어 파일 하나로 띄우고 내리는 실행 단위다.

#1문제 상황

웹과 DB와 캐시를 따로따로 띄우려니 순서와 연결을 매번 손으로 맞췄다. 팀원마다 띄우는 법이 달라 같은 앱이 다르게 돌았고, 인수인계 때마다 구두 설명이 필요해 사람이 바뀌면 처음부터였다.

손으로 띄우니 손을 탔다. 손을 타니 사람이 바뀌면 무너졌다.

#2핵심 질문

여러 컨테이너를 한 앱으로 묶어 파일 하나로 띄울 수는 없을까?

#3동작 예시

compose.yaml에 웹과 DB를 적고 up을 치면 두 개가 순서대로 뜨고 down을 치면 함께 걷힌다. 띄우는 법이 파일에 굳어 누구나 같이 돌리고 사람이 바뀌어도 그대로다.

#4동작 과정

  1. 묶어 적기앱의 구성품을 파일에 적는다. 말이 아니라 글이 돼 남는다.
  2. 한 번에 띄우기up으로 묶음 전체를 올린다. 순서까지 맡기니 손이 안 간다.
  3. 함께 걷기down으로 묶음 전체를 내린다. 뒷정리까지 돼 찌꺼기가 안 남는다.

compose.yaml 뼈대

서비스 목록을 적는 YAML로 프로젝트 이름이 자원들을 한 묶음으로 엮는다.

#1문제 상황

설정 파일이 있어도 이름 규칙이 제각각이라 어느 것이 본 파일인지 몰랐다. 두 앱을 띄우면 자원 이름이 겹쳐 꼬였고, 지우다 남의 것을 건드릴 뻔해 손이 떨렸다.

이름이 겹치면 남의 것을 건드린다. 건드리면 함께 죽는다.

#2핵심 질문

뼈대를 정하고 묶음 이름으로 가를 수는 없을까?

#3동작 예시

compose.yaml에 services를 적고 project name을 shop으로 두면 자원 앞에 shop이 붙어 다른 앱과 안 겹친다. 겹칠 걱정이 사라지니 지우는 손도 가벼워진다.

#4동작 과정

  1. 이름 맞추기정해진 파일 이름으로 둔다. 찾는 곳이 하나라 헤맬 일이 없다.
  2. 뼈대 세우기서비스 목록을 최상위에 적는다. 구성품이 보여 빠뜨릴 곳이 없다.
  3. 묶음 짓기프로젝트 이름으로 자원을 엮는다. 남의 것과 안 섞여 안심이다.

서비스 정의

이미지·포트·환경값으로 각 역할을 적고 의존과 재시작까지 거는 방법이다.

#1문제 상황

서비스마다 이미지·포트·환경값을 적는데 위치가 달라 헤맸다. 의존과 재시작을 어디에 거는지 몰라 앱이 순서 없이 떴고, 죽으면 그대로 누워 있어 깨워야 했다.

적을 곳을 모르니 적는 것도 제각각이었다. 제각각이니 읽는 것도 힘들었다.

#2핵심 질문

서비스 하나를 어디에 무엇을 적는지 정해둘 수는 없을까?

#3동작 예시

web 서비스에 image와 ports와 environment를 적고 depends_on으로 DB를 먼저 뜨게 하고 restart로 꺼지면 다시 켠다. 자리가 정해지니 헤맬 곳이 없고 읽는 눈도 모인다.

#4동작 과정

  1. 밑천 적기이미지나 빌드를 지정한다. 무엇으로 돌릴지 정해 흔들리지 않는다.
  2. 통로와 값 적기포트와 환경값을 단다. 드나듦과 값을 정해 경우에 맞춘다.
  3. 관계 걸기의존과 재시작을 건다. 순서와 부활을 맡겨 밤에 잘 잔다.

네트워크·볼륨·설정·시크릿

망과 저장소를 선언하고 설정·민감값은 파일로 주입받는 네 가지 장치다.

#1문제 상황

망과 저장소를 서비스마다 따로 만들다 보니 이름이 엇갈렸다. 설정 파일과 비밀번호를 이미지 안에 박아 유출될 뻔했고, 돌려가며 고치기도 힘들었다.

박힌 것은 바꾸기 힘들다. 흩어진 것은 모으기 힘들다.

#2핵심 질문

넷을 선언하고 값은 파일로 주입받게 할 수는 없을까?

#3동작 예시

최상위에 networks와 volumes를 선언하고 configs로 설정 파일을 시크릿으로 DB 암호를 주입받아 쓴다. 이미지는 깨끗하고 값은 밖에서 오니 바꾸기도 쉽고 새지도 않는다.

#4동작 과정

  1. 선언하기망과 저장소를 최상위에 선언한다. 주인이 분명해져 엇갈릴 일이 없다.
  2. 붙이기서비스에서 필요한 것을 골라 붙인다. 쓰는 것만 가져가 가볍다.
  3. 주입받기설정과 민감값은 파일로 받는다. 이미지에 박지 않아 새는 곳이 없다.

up·down·살펴보기

up으로 띄우고 down으로 걷고 ps와 logs와 exec로 들여다보는 일주기다.

#1문제 상황

파일은 썼는데 띄우고 내리는 명령이 헷갈렸다. 떴는지 안 떴는지 로그는 어디서 보는지 몰라 손을 놓고 쳐다만 봤고, 물어보기도 민망했다.

쓴 것과 돌리는 것이 이어지지 않으면 파일은 장식이다. 장식이 되면 다시 손으로 하게 된다.

#2핵심 질문

띄우고 걷고 들여다보기를 일주기로 외울 수는 없을까?

#3동작 예시

up -d로 띄우고 ps로 상태를 보고 logs -f로 흐름을 보고 exec로 안으로 들어가고 down으로 걷는다. 다섯 손가락 안에 들어 외울 것이 없다.

#4동작 과정

  1. 띄우기up으로 묶음을 올린다. 선언이 현실이 돼 파일대로 된다.
  2. 살펴보기ps와 logs와 exec로 본다. 겉과 속을 다 봐서 모르는 곳이 없다.
  3. 걷기down으로 묶음을 내린다. 뒷정리까지 돼 다음이 깨끗하다.

디버그 도구는 profiles로 평소엔 끄고 소스는 watch로 자동반영하고 운영값은 별 파일로 합쳐 쓴다. 환경이 바뀌어도 손가는 곳이 정해져 헤맬 일이 없다.

  3. 합쳐 쓰기여러 파일을 순서대로 합친다. 순서가 곧 우선순위라 읽으면 안다.

건강해진 뒤에 뜨게 묶고 늘리고 다시 띄우는 실전 운영 요령을 갖추는 단계다.

#1문제 상황

#2핵심 질문

건강해진 뒤에 뜨게 하고 죽으면 살리는 운영 요령을 갖출 수는 없을까?

#3동작 예시

depends_on에 건강 조건을 걸면 DB가 준비된 뒤 웹이 뜨고 restart를 걸면 죽은 것이 다시 살아난다. 순서와 부활을 파일에 맡기면 밤전화가 준다.

#4동작 과정

  1. 순서 걸기준비된 뒤에 뜨게 묶는다. 재촉하지 않아 깨질 일이 없다.
  2. 늘리기scale로 같은 것을 여럿 둔다. 나누어 갖게 해 여유가 생긴다.
  3. 살리기재시작 정책으로 죽으면 되살린다. 밤전화가 줄어 잠을 잔다.

#1문제 상황

변수와 조각으로 짧게 쓰고 배포 맛도 볼 수는 없을까?

#3동작 예시

${TAG:-latest}로 버전을 꽂고 공통 묶음은 조각으로 빼 쓰고 deploy 맛보기로 자원 상한을 적는다. 길던 파일이 반으로 줄고 손댈 곳이 하나로 모인다.

#4동작 과정

  2. 빼 쓰기조각과 확장으로 반복을 줄인다. 한 번 적고 여럿이 써서 어긋날 곳이 없다.
  3. 맛보기배포 요소를 조금씩 얹는다. 필요한 만큼만 넓혀 무리하지 않는다.

레지스트리란

이미지 창고라 Hub가 기본값이고 사내 전용 창고를 따로 둘 수도 있다.

#1문제 상황

만든 이미지를 동료에게 주려니 파일로 보내고 버전도 말로 전했다. 누가 최신을 가졌는지 아무도 몰라 서로 다른 것을 돌렸고, 다르다는 것도 늦게 알았다.

말로 전하는 것은 새기 마련이다. 새면 어긋나고 어긋나면 싸운다.

#2핵심 질문

이미지 창고를 하나 두고 거기서 주고받으면 되지 않을까?

#3동작 예시

Hub를 기본 창고로 쓰면 push로 올리고 pull로 받는 자리가 생겨 파일 전달이 사라진다. 창고가 최신을 정하니 물을 곳이 하나가 된다.

#4동작 과정

  1. 창고 알기기본 창고의 자리를 안다. 못 박힌 약속이라 헤맬 일이 없다.
  2. 올리기만든 것을 창고에 둔다. 나눌 준비가 돼 혼자 품지 않는다.
  3. 받기필요한 쪽이 창고에서 받는다. 같은 것을 받아 어긋날 일이 없다.

저장소 만들고 푸시

Hub에 저장소를 만들고 태그를 붙여 push하면 어디서든 pull로 받는다.

#1문제 상황

이미지는 있는데 올릴 자리가 없어 개인 PC에만 있었다. 다른 서버에서 쓰려면 매번 파일을 옮겨야 했고, 옮기는 사이에 버전이 어긋나 무엇이 최신인지 몰랐다.
