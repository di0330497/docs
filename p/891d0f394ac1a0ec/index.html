1컨테이너와 Docker 플랫폼의 구조이미지·컨테이너·레지스트리·데몬이라는 대상을 먼저 알아야 뒤의 모든 명령과 파일 형식이 무엇을 조작하는지 이해된다.52설치와 CLI 첫걸음실습 환경이 없으면 이후 모든 명령을 확인할 수 없다. 플랫폼별 설치와 CLI 문법을 여기서 끝낸다.53이미지 빌드Dockerfile을 읽고 이미지를 만드는 것은 모든 컨테이너 작업의 출발점이다. 빌드 도구와 최적화 방법을 묶는다.84컨테이너 실행이미지를 컨테이너로 실행하고 관리하는 법. 실행 옵션·포트·리소스·모니터링을 한 단계에 묶는다.55스토리지컨테이너 데이터를 영속화하고 성능을 내는 방법. 볼륨·마운트·스토리지 드라이버를 묶는다.56네트워킹컨테이너 간 통신과 외부 노출을 담당하는 네트워크 드라이버와 방화벽을 묶는다.57Docker Compose다중 컨테이너 애플리케이션을 정의하고 실행하는 도구. 파일 형식·네트워크·시크릿·프로파일을 묶는다.98Docker Engine 관리데몬 설정·로깅·모니터링·보안 운영을 묶는다. 실무 환경에서 Engine을 다루는 방법이다.69보안컨테이너 격리·데몬 보호·레지스트리 인증·콘텐츠 무결성을 묶는다.510Docker Hub이미지를 공유하고 관리하는 레지스트리 서비스. 저장소·태그·자동 빌드·보안을 묶는다.511Swarm 모드여러 Engine을 묶어 클러스터를 만드는 방법. 노드·서비스·네트워크·보안을 묶는다.512Docker Scout와 공급망 보안이미지 취약점 분석·SBOM·빌드 정책·강화 이미지를 묶어 공급망 보안을 다룬다.4

컨테이너란 무엇인가 — 가상머신과의 차이

앱과 그 실행 환경을 하나로 묶어 호스트 커널 위에서 격리된 프로세스로 실행하는 단위이며, 하드웨어를 가상화하는 가상머신보다 훨씬 가볍게 시작한다.

1문제 상황

여러 앱을 한 대의 서버에 올릴 때, 전통적인 방식은 앱마다 전용 물리 서버를 두거나 가상머신으로 운영체제째 복제하는 것이었습니다. 가상머신은 하드웨어를 통째로 에뮬레이션하기 때문에 게스트 OS와 가상 하드웨어 계층을 전부载入해야 하고, 부팅에 수십 초에서 분 단위가 걸리며, 하나의 서버에서 동시에 띄울 수 있는 개수에도 한계가 있습니다. 운영체제와 런타임이 앱마다 따로 복제되므로 패치와 버전 관리도 개별 대상이 되어 관리 비용이 그대로 늘어납니다.

2핵심 질문

앱과 그 실행 환경을 하나로 묶어, 어디서든 빠르게 가볍게 실행할 수 있을까요?

3동작 예시

Node.js로 만든 API 서버를 배포한다고 해 봅니다. 앱 코드와 Node 런타임을 묶어 만든 이미지를 읽기 전용 파일시스템으로 올린 뒤, 그 위에 쓰기 가능한 층을 얹고 프로세스 하나를 시작합니다. 게스트 운영체제를 실행하지 않으므로 이미지解压가 끝나면 바로 요청을 받을 수 있고, 프로세스를 멈추면 파일은 사라지고 다시 시작하면 같은 상태로 돌아옵니다.

4동작 과정

  1. 이미지 준비앱 코드와 런타임 라이브러리를 묶은 읽기 전용 이미지를 가져와 컨테이너 실행의 출발점으로 삼습니다.
  2. 격리 경계 생성네임스페이스로 파일시스템·프로세스·네트워크 시야를 나누고, cgroups로 CPU와 메모리 사용 상한을 지정해 이웃한 컨테이너의 영향을 막습니다.
  3. 프로세스 실행컨테이너 안의 프로세스가 호스트 커널을 그대로 공유하며 돌아갑니다. 시작과 종료가 빠르고, 어떤 호스트에서든 같은 이미지에서 같은 결과를 얻습니다.

5한 줄 요약

앱과 실행 환경을 묶어 호스트 커널 위의 격리된 프로세스로 실행하는 것

Docker가 푸는 문제와 플랫폼 쓰임새

코드와 실행 환경이 어긋나서 생기는 문제를 풀기 위해 '패키징 → 실행 → 공유' 흐름을 표준화한 플랫폼으로, 개발·배포·확장을 하나의 경로로 묶어 준다.

1문제 상황

코드는 각자의 컴퓨터에서 돌아가고, 배포는 서버의 환경을 손으로 맞춰야 했습니다. 개발자는 내 로컬에서는 잘 되는 앱이 서버에서는 라이브러리 버전 차이, 설정 파일 누락, 의존 서비스 부재 때문에 실행되지 않는 상황을 반복해서 겪었습니다. 결국 팀마다 배포 스크립트와 설치 문서가 따로 놀았고, 신입이 합류할 때마다 같은 문제를 처음부터 다시 해결해야 했습니다.

2핵심 질문

같은 코드가 어느 환경에서든 똑같이 돌아가게 만들 수 있을까요?

3동작 예시

팀원이 만든 Flask 앱을 그대로 컨테이너로 실행하면, 파이썬과 라이브러리, 설정 파일이 모두 이미지 안에 들어 있어 받은 즉시 같은 결과로 동작합니다. 배포 서버는 이 이미지를 받아 컨테이너를 하나 띄우기만 하면 되고, 이슈가 생기면 그 환경에서 그대로 재현해 볼 수 있습니다.

4동작 과정

  1. 패키징앱, 런타임, 설정을 컨테이너 이미지로 만들어 버전이 붙은 산출물 하나로 보관합니다.
  2. 실행이미지를 내려받아 컨테이너를 시작하면 어디서든 같은 프로세스가 같은 구성으로 구동됩니다.
  3. 공유·배포·확장레지스트리에 이미지를 올려 팀과 배포 환경이 같은 산출물을 받고, 여러 복제본을 띄워 수평으로 확장합니다.

패키징부터 실행과 공유까지를 하나의 표준 경로로 묶어 환경 불일치를 없애는 것

docker 명령이 클라이언트로서 소켓을 통해 dockerd 데몬에 요청을 보내고, 데몬이 Engine API 응답으로 이미지를 가져오고 컨테이너를 만드는 클라이언트-서버 구조.

1문제 상황

Docker를 쓰기 전에는 서버마다 전용 도구를 직접 설치하고 설정을 손으로 맞췄습니다. 명령을 내리는 프로그램과 실제로 컨테이너를 관리하는 작업이 분리되지 않아, 도구를 어디에 붙는지 매번 경로를 지정해야 했습니다. 원격 서버를 다루려면 별도 전송 수단을 또 만들어야 했고, 도구가 어디로 명령을 보내는지 사용자가 알기 어려웠습니다.

2핵심 질문

명령을 내리는 쪽과 실제 작업을 수행하는 쪽을 어떻게 분리할까요?

3동작 예시

docker ps를 치면 docker 명령이 클라이언트로서 로컬 소켓을 통해 dockerd 데몬에 요청을 보냅니다. 데몬은 네트워크 주소가 담긴 컨텍스트를 보고 대상 서버를 정한 뒤, Engine API로 응답을 돌려주고 클라이언트가 화면에 표를 그립니다. 요청을 실제로 처리하는 쪽은 언제나 데몬입니다.

4동작 과정

  1. 클라이언트 요청docker 명령이 실행 컨텍스트를 읽고 대상 데몬의 소켓에 요청을 보냅니다.
  2. 데몬 처리dockerd가 요청을 받아 이미지를 가져오거나 컨테이너를 생성·시작하고, 모든 상태를 내부에서 관리합니다.
  3. API 응답Engine API 규격에 맞춘 응답이 돌아와 클라이언트가 결과를 출력 형식으로 정리해 보여줍니다.

1문제 상황

서버마다 설치된 프로그램 버전이 다르면 설치와 제거를 손으로 반복해야 했고, 그 결과를 남길 방법이 없었습니다. 같은 상태를 다시 만들어 내려면 누가 무엇을 어떤 순서로 설치했는지 기록해 두고 매번 따라 해야 했습니다. 여러 서비스가 붙으면 이 기록이 서로 얽혀 원인을 찾기 어려워졌습니다.

2핵심 질문

어떤 상태를 파일 몇 개로 재현하고, 그 상태를 나눠 쓰고, 어디에 보관할 수 있을까요?

3동작 예시

docker pull로 받은 이미지는 파일 변경이 없는 기반 층을 공유하는 여러 층의 목록입니다. 이 이미지를 읽기 전용으로 두고 그 위에 쓰기 가능한 층을 얹어 시작한 것이 컨테이너입니다. 이미지 목록은 레지스트리에 올려 다른主机가 그대로 받을 수 있고, 이미지를 만든 사람과 태그, 생성 시각 같은 정보는 이미지 설정에 남아 있습니다.

4동작 과정

  1. 이미지루트 파일시스템과 실행 명령, 환경 변수, 설정을 층 단위로 묶은 읽기 전용 산출물입니다.
  2. 컨테이너이미지를 기반으로 쓰기 가능한 층과 실행 중인 프로세스를 합친 실행 단위이며, 정지하면 그 층은 사라집니다.
  3. 레지스트리와 객체레지스트리가 이미지를 저장하고 배포하며, Docker가 다루는 기본 단위는 이미지·컨테이너·네트워크·볼륨입니다.

컨테이너를 만드는 커널 기술

네임스페이스로 프로세스·파일시스템·네트워크를 격리하고 cgroups로 자원을 제한한 뒤, runc 같은 OCI 런타임이 그 경계를 실제 커널로 만들어 컨테이너를 띄운다.

1문제 상황

한 서버에 여러 서비스를 함께 올리면 각 서비스가 서로의 파일과 포트와 메모리를 건드릴 수 있습니다. 프로세스끼리 격리가 없으면 하나의 오류가 전체로 번지고, 어떤 서비스가 자원을 얼마나 쓰는지 알 수 없어 장애 원인을 늦게 찾습니다. 이 문제를 해결하려고 각 서비스에 별도 운영체제를 띄우면 대신 자원과 시작 시간이 크게 듭니다.

2핵심 질문

별도 운영체제 없이도 프로세스를 격리하고 자원 사용량을 제한할 수 있을까요?

3동작 예시

컨테이너를 만들 때 커널의 네임스페이스를 복제해 새 프로세스에게 파일시스템·호스트 이름·네트워크 인터페이스 목록이 따로 보이게 합니다. cgroups로 CPU와 메모리 상한을 지정하고, runc 같은 OCI 런타임이 이 경계를 실제 커널 오브젝트로 만들어 프로세스를 띄웁니다. 컨테이너 안에서는 자기 파일시스템과 루트 디렉터리만 보입니다.

4동작 과정

  1. 격리 경계 설정namespaces(가상 pid·ipc·uts·mnt·net·user)를 만들어 프로세스마다 독립된 시야를 부여합니다.
  2. 자원 제한cgroups(control groups)로 CPU, 메모리, 디스크 I/O, 프로세스 수의 상한과 가중치를 지정합니다.
  3. 런타임 실행OCI 런타임이 runc 컨테이너 런타임 기준으로 설정된 경계를 실제 커널 호출로 적용해 컨테이너 프로세스를 실행합니다.

2핵심 질문

3동작 예시

  3. Engine 설치docker-ce, containerd.io, docker-compose-plugin을 설치하고 버전 명령으로 데몬과 CLI가 함께 준비됐는지 확인합니다.

2핵심 질문

3동작 예시

4동작 과정

  1. 권한 부여docker 그룹에 사용자를 추가해 로컬 소켓에 대한 권한이 그룹 단위로 적용되게 합니다.
  2. 서비스 등록systemctl enable docker로 부팅 시 자동 시작을 켜고 systemctl start docker로 데몬을 즉시 띄웁니다.
  3. 동작 확인docker info와 hello-world 실행으로 클라이언트가 데몬과 통신하는지 확인하고, 필요하면 데몬 설정 파일에서 저장 위치와 로그 옵션을 지정합니다.

3동작 예시

4동작 과정

  1. 플랫폼 확인Mac·Windows·Linux 중 어느 환경인지, Intel인지 Apple Silicon인지 구분해 해당 설치 파일을 고릅니다. 운영체제와 CPU 아키텍처가 다르면 실행할 수 없는 설치 파일이 있습니다.
  2. 설치 파일 실행과 라이선스 수락설치 프로그램을 실행해 Docker Desktop을 시스템에 넣고 라이선스 계약을 수락합니다. Windows는 WSL 2(Windows용 리눅스 서브시스템)를, 리눅스 계열은 설치 패키지나 저장소 설정을 먼저 처리합니다.
  3. 엔진 기동과 동작 확인앱이 백그라운드에서 리눅스 가상 머신과 Docker Engine을 시작합니다. 대시보드가 곧장 켜지는지, docker 명령이 응답하는지로 설치를 확인하고 엔진이 살아 있는 동안 GUI와 CLI 양쪽으로 작업합니다.

1문제 상황

Dockerfile로 만든 이미지를 그대로 배포하면 전체를 통째로 옮겨야 했고, Dockerfile 한 줄을 고쳐도 전체를 다시 만들어야 했습니다. 어떤 부분이 바뀌었는지 알 수 없어 빌드와 배포가 모두 무조건 전체 작업이 되었고, 이미지 크기도 어느 지점에서 커졌는지 파악하기 어려웠습니다.

2핵심 질문

이미지를 여러 조각으로 나누어 쌓아 두고, 바뀐 조각만 다시 만들어 크기와 빌드 시간을 줄일 수 있을까요?

3동작 예시

4동작 과정

  1. 명령 하나가 레이어 하나Dockerfile의 FROM, COPY, RUN 같은 명령 하나하나가 이미지의 읽기 전용 파일 묶음인 레이어가 됩니다. 이 레이어들이 위에서 아래로 순서대로 쌓여 최종 이미지를 이룹니다.
  2. 변경 지점 이후만 재생성빌드는 위에서부터 명령을 차례로 비교해 앞 레이어가 그대로면 재사용하고, 달라진 명령을 만나면 그 지점부터 아래 레이어를 새로 만듭니다. 따라서 같은 명령을 같은 순서에 두는 것이 재사용의 조건이 됩니다.
  3. 이미지 크기와 공유 구조레이어는 이미지 안에서 중복 저장되지 않고 개별 파일 묶음으로 관리되므로, 여러 이미지가 같은 레이어를 공유하면 전체 저장 공간이 줄어듭니다. 대신 변경된 레이어가 쌓일수록 이미지 크기가 커지므로, 쓰이지 않는 중간 레이어를 여러 단계로 나눠 최종 이미지에는 필요한 것만 남기는 편이 유리합니다.

Go로 만든 프로그램을 빌드하면 첫 번째 단계에서 소스를 컴파일해 실행 파일 하나가 나오고, 두 번째 단계에서는 그 파일만 COPY --from=0 /app/app . 로 가져옵니다. 최종 이미지에는 실행 파일과 최소한의 실행 환경만 남아 컴파일러가 전혀 들어가지 않습니다.

4동작 과정

  1. 단계 분리Dockerfile 안에서 FROM을 여러 번 쓰면 여러 단계가 생깁니다. 보통 앞 단계는 빌드 단계, 마지막 FROM 이후가 실행 단계가 되어 AS 이름으로 각 단계를 구분해 둡니다.
  2. 빌드 단계에서만 도구 사용앞 단계에서 RUN으로 컴파일러를 설치하고 코드를 빌드해 산출물을 만듭니다. 이 단계의 내용은 최종 이미지에는 포함되지 않으므로 도구 설치에 드는 시간과 용량을 최종 결과가 감당하지 않습니다.
  3. 결과물만 복사COPY --from=빌드단계로 빌드 산출물만 실행 단계에 옮깁니다. node나 python처럼 실행 시 반드시 필요한 런타임은 실행 단계에서 직접 설치합니다. 그러면 빌드 도구는 빌드 단계에서 버려지고 최종 이미지에는 실행에 필요한 것만 남습니다.
공식 문서https://docs.docker.com/build/building/multi-stage/

이미지 빌드·태그·푸시

docker build로 이미지를 만든 뒤 이름(태그)을 붙이고 docker push로 레지스트리에 올려 다른 환경에서 받을 수 있게 하는 일련의 과정이다.

1문제 상황

Dockerfile만으로는 이미지가 만들어지지 않는다. 여기서 만들어진 이미지는 특정 서버 컴퓨터의 로컬 디스크에만 남고, 이름이 없으면 다른 사람이 찾을 수 없다. 같은 Dockerfile을 다른 사람이 빌드해도 로컬 캐시와 빌드 컨텍스트가 달라 결과가 달라질 수 있다. 결국 각자 자기 컴퓨터에서 따로 빌드하고, 어떤 파일이 어떤 설정으로 들어갔는지 기록이 남지 않는다.

이 과정에서 이미지 이름, 즉 태그가必须有 필요해진다. 이름이 있어야 레지스트리에 올려 다른 환경에서 받을 수 있고, 같은 이미지의 어떤 버전이 어디에 쓰이는지 추적할 수 있다.

2핵심 질문

빌드한 이미지에 이름(태그)을 붙여 식별 가능하게 하고, 원격 레지스트리에 올려 다른 환경에서 그대로 받아 쓸 수 있게 하는 방법이 무엇인가?

3동작 예시

docker build -t myapp:1.0 . 를 실행하면 현재 폴더의 Dockerfile을 읽어 레이어를 쌓고, 결과에 myapp:1.0 이라는 이름표를 붙여 로컬 이미지 목록에 등록한다. 여기서 이름이 docker.io/myorg/myapp:1.0 처럼 레지스트리 주소까지 포함하면 그 주소가 실제 업로드 대상이 된다. 이후 docker login 으로 인증 토큰을 저장하고 docker push docker.io/myorg/myapp:1.0 를 실행하면 로컬에 있던 레이어가 그대로 레지스트리로 전송되고, 다른 컴퓨터에서는 docker pull 로 같은 이름의 이미지를 받아 컨테이너를 실행하게 된다.

4동작 과정

  1. 빌드docker build 가 Dockerfile의 각 명령문을 실행해 파일 시스템 변경을 레이어(읽기 전용 계층) 단위로 쌓고, 이들을 묶은 이미지를 로컬에 만든다.
  2. 태그 부여-t 옵션으로 지정한 이름:태그 를 이미지 메타데이터에 기록해 여러 이미지를 구분하고 버전을 구분한다. 태그는 사람이 읽는 별명이므로 같은 이미지에 여러 태그를 붙일 수 있다.
  3. 레지스트리 지정docker tag 로 이름 앞부분에 레지스트리 서버 주소를 붙여, 이 태그가 어느 저장소의 어느 저장소로 가야 하는지 정한다.
  4. 푸시docker login 이 저장한 인증 정보로 docker push 가 이미지의 각 레이어를 레지스트리에 올린다. 이미 서버에 있는 레이어는 다시 보내지 않고 참조만 기록해 중복 전송을 줄인다.

5한 줄 요약

빌드한 이미지에 이름표를 붙여 식별하고, 레지스트리 서버로 보내 원격에서도 같은 이미지를 받을 수 있게 하는 과정

BuildKit과 Dockerfile 프론트엔드

BuildKit은 Docker 빌드를 실제로 수행하는 엔진이고, Dockerfile 프론트엔드는 그 엔진을 구동해 Dockerfile을 해석하고 결과 조립을 맡는 컴포넌트다.

1문제 상황

예전 Docker 빌드는 Dockerfile 명령을 순서대로 한 줄씩 실행하고, 실행할 때마다 이미지를 잠깐 컨테이너로 띄워 그 위에 명령을 적용했다. 중간에 한 줄이 실패하면 그 지점부터 다시 시작해야 했고, 여러 이미지를 동시에 만들면 엔진 하나가 순차로 처리해 느렸다. 또한 Dockerfile 문법이 엔진 코드에 직접 박혀 있어 문법이 바뀔 때마다 엔진 전체를 새로 배포해야 했다.

2핵심 질문

Dockerfile을 해석해 이미지를 만들되, 병렬 실행과 효율적인 캐시 활용을 담당하고 문법 변경에 유연하게 대응할 수 있는 빌드 구조는 무엇인가?

3동작 예시

docker build 를 치면 BuildKit이 빌드 그래프(Dockerfile의 각 명령을 노드로, 의존 관계를 간선으로 표현한 구조)를 먼저 만들고, 서로 의존하지 않는 노드들은 동시에 실행한다. Dockerfile 해석은 Dockerfile 프론트엔드가 맡아, 엔진과 분리된 컴포넌트가 파일을 읽어 내부 작업 그래프로 바꿔 BuildKit에 넘긴다. 결과 조립과 최종 이미지 생성까지는 BuildKit이 수행한다.

4동작 과정

  1. 프론트엔드가 Dockerfile 해석Dockerfile 프론트엔드(기본값 dockerfile.v0)가 Dockerfile을 읽어 각 명령을 의미 단위로 분리하고, 실행 가능한 작업 목록과 의존 관계로 변환해 BuildKit에 전달한다. 프론트엔드 교체만으로 다른 입력 형식을 같은 엔진으로 빌드할 수 있다.
  2. BuildKit이 그래프를 계획하고 병렬 실행BuildKit은 작업 목록을 그래프로 보고 동시에 실행 가능한 노드들을 병렬로 돌린다. 의존하지 않는 레이어가 겹쳐 돌아가므로 빌드 시간이 크게 줄어든다.
  3. 빌드 컨텍스트를 효율적으로 전송빌드 컨텍스트 전체를 매번 복사하지 않고, 이전 빌드에서 이미 처리한 파일은 다시 읽지 않도록 판단해 필요한 입력만 사용한다.
  4. 결과 레이어 조립실행된 작업들을 입력 이미지 위에 차례로 쌓아 최종 루트 파일 시스템과 이미지 설정을 만들고, 이를 이미지로 등록한다.

5한 줄 요약

Dockerfile 해석을 프론트엔드에 맡기고 병렬 실행과 캐시 관리까지 BuildKit 엔진에 맡기는 구조

공식 문서https://docs.docker.com/build/buildkit/frontend/
이전이미지 빌드·태그·푸시다음빌드 드라이버와 빌드 관리

3이미지 빌드03-07

빌드 드라이버와 빌드 관리

빌드 드라이버는 BuildKit을 어디에서 실행할지(Engine 내장, 컨테이너, 클라우드 등) 정하는 설정으로, docker buildx create·ls·use 명령으로 빌더를 만들고 골라 쓴다.

1문제 상황

빌드 엔진을 어디에 둘지 정하지 않으면 모든 빌드가 기본 엔진 위에서 같은 방식으로만 돌아간다. 그러면 특정 CPU 아키텍처용 이미지를 만들거나, 멀티 플랫폼 이미지를 한 번에 만들어야 할 때 이 기본 경로로는 부족해 이질적인 방법을 쓰게 된다. 어떤 빌드가 어떤 설정으로 실행됐는지도 기록되지 않아 동일한 결과를 다시 만들기가 어렵다.

2핵심 질문

빌드를 실제로 수행하는(BuildKit 인스턴스) 빌더를 만들고 선택해, 필요한 빌드 동작과 설정을 지정한 뒤 재사용하려면 어떻게 해야 하는가?

3동작 예시

docker buildx create --name multi --driver docker-container --platform linux/amd64,linux/arm64 mybuilder 를 실행하면 이름이 multi이고 드라이버가 docker-container인 빌더가 만들어져 Docker 엔진 안에 별도 컨테이너로 뜬다. docker buildx use multi 로 그 빌더를 기본 선택하고, docker buildx ls 로 목록과 어떤 드라이버가 쓰이는지 확인한다. 이후 docker build 도 이 빌더를 통해 BuildKit이 동작한다.

4동작 과정

  1. 드라이버로 실행 위치 지정빌드 드라이버(빌드를 구동하는 방식 규칙)는 BuildKit을 어디서 돌릴지 정한다. 드라이버를 docker로 두면 엔진 내장 BuildKit을 쓰고, docker-container(빌드를 컨테이너로 띄워 실행)나 클라우드 드라이버를 고르면 외부·격리된 환경에서 빌드가 일어난다.
  2. 빌더 생성docker buildx create 가 이름·드라이버·연결 대상을 지정해 빌더를 등록한다. 컨테이너 드라이버는 이 시점에 빌드용 컨테이너를 생성하고 BuildKit 이미지까지 받아 둔다.
  3. 빌더 선택과 확인docker buildx use <이름> 으로 기본 빌더를 바꾸고, docker buildx ls 에서 이름·드라이버·상태·노드 목록을 확인해 어떤 것이 실제 쓰이는지 검증한다.
  4. 빌드 실행docker buildx build 가 선택된 빌더의 BuildKit에 빌드를 넘기고, 다중 플랫폼 지정 시 플랫폼별 빌드를 각 환경에서 수행한 뒤 이미지를 하나로 합친다.

5한 줄 요약

빌드 엔진을 담고 있는 빌더를 만들어 골라 쓰 thereby, 빌드 실행 위치와 방식을 설정으로 관리하는 것

Bake로 빌드 구성 관리

Bake는 docker-bake.hcl 같은 HCL 파일에 타깃·변수·플랫폼을 선언해 여러 이미지의 빌드 구성을 한 곳에 모으고 한 번에 빌드하게 해주는 Buildx 기능이다.

1문제 상황

프로젝트에 이미지 종류가 여럿이고 각 이미지가 다른 플랫폼, 다른 빌드 인자, 다른 Dockerfile을 쓰면 빌드 구성이 명령어와 CI 스크립트 여기저기에 흩어진다. 어떤 이미지를 만들 때 무슨 값을 넣어야 하는지 한눈에 보이지 않고, 같은 설정을 사람이 매번 다시 입력해야 한다. 결국 로컬과 CI의 빌드 결과가 달라지거나, 필요한 인자를 빼먹고 빌드가 실패한다.

2핵심 질문

여러 이미지의 타깃·변수·플랫폼 설정을 파일 한 곳에 모아 두고 같은 명령으로 일관되게 빌드하려면 어떻게 해야 하는가?

3동작 예시

docker-bake.hcl 에 target "api" { dockerfile = "Dockerfile.api" args = { VERSION = "2.1.0" } } 처럼 타깃을 정의해 두고 docker buildx bake 를 실행하면 Bake가 파일을 읽어 해당 타깃 목록을 자동 생성하고, 필요한 경우 이미지가 레지스트리에 있는 설정이면 푸시까지 이어서 수행한다. 변수값을 바꿔야 하면 docker buildx bake --set api.args.VERSION=2.2.0 처럼 실행 시점에 덮어쓴다.

4동작 과정

  1. HCL 파일에 타깃 선언docker-bake.hcl 에 target 블록으로 빌드 단위를 정의하고, 각 타깃에 Dockerfile 경로·빌드 인자·플랫폼·캐시 설정을 선언한다. 전역 변수를 만들어 여러 타깃이 함께 참조하게 할 수도 있다.
  2. 파일 해석과 기본 타깃 계산Bake가 HCL을 파싱해 실제 Buildx 빌드 호출 목록을 만든다. 타깃을 지정하지 않으면 기본 타깃이 선택되고, 그룹 블록으로 묶으면 한 번에 여러 타깃을 처리한다.
  3. 변수 덮어쓰기와 파일 조합명령줄 --set 으로 선언값을 덮어쓰고, 여러 HCL 파일을 함께 불러와 프로젝트·환경별로 설정을 나눠 관리한다. 환경변수도 변수로 주입된다.
  4. 일괄 빌드 실행계산된 호출 목록을 Buildx 빌더에 한 번에 전달해 빌드하고, 파일에 푸시 대상이 지정돼 있으면 빌드 후 레지스트리 업로드까지 이어서 수행한다.

5한 줄 요약

여러 이미지의 빌드 구성을 HCL 파일에 모아 두고 한 번의 명령으로 일관되게 빌드·푸시하게 하는 것

이전빌드 드라이버와 빌드 관리다음컨테이너 실행과 기본 옵션

4컨테이너 실행04-01

컨테이너 실행과 기본 옵션

docker run 명령으로 이미지로부터 컨테이너를 만들어 실행하고, 이름·백그라운드 실행·환경변수·볼륨·실행 명령 같은 기본 옵션으로 동작을 지정하는 것.

1문제 상황

이미지는 파일 시스템과 실행 설정이 담긴 정지된 상태다. 서버마다 운영체제와 라이브러리를 직접 설치하고 설정을 맞춰야 하며, 같은 프로그램을 시작하고 멈추고 로그를 확인하는 절차를 매번 손으로 반복했다. 실행 환경을 통째로 복제하거나 격리된 상태로 돌릴 수단이 없어, 한 프로그램의 문제가 같은 컴퓨터의 다른 작업에 영향을 주기도 했다.

2핵심 질문

이미지로부터 격리된 실행 단위인 컨테이너를 한 번의 명령으로 만들어 시작하고, 이름·백그라운드·환경변수·볼륨 같은 기본 옵션으로 실행 동작을 지정하려면 어떻게 해야 하는가?

3동작 예시

docker run -d --name web -e MODE=prod -v /data:/app/data -p 8080:80 nginx 를 실행하면 nginx 이미지로부터 이름이 web인 컨테이너가 생성되어 백그라운드로 시작된다. 컨테이너 안의 80번 포트는 호스트의 8080번 포트로 연결되고, MODE=prod 환경변수가 주입되며, 호스트의 /data 디렉터리가 컨테이너의 /app/data 자리에 붙는다. 호스트 환경에 따라 docker run 과 docker create + docker start 로 나눌 수 있다.

4동작 과정

  1. 컨테이너 생성이미지에서 읽기 전용 계층을 가져와 쓰기 가능한 계층 하나를 얹고, 이미지 설정에 이름·환경변수·포트·볼륨·사용자 같은 실행 설정을 덮어씌운 컨테이너를 만든다. 이 단계까지만 하고 실행하지 않을 수도 있다.
  2. 시작과 프로세스 실행컨테이너를 시작하면 지정된 실행 명령(ENTRYPOINT 와 CMD, 필요하면 인자)이 프로세스로 올라간다. 이 프로세스가 종료되면 컨테이너도 종료되며, 살아 있는 동안만 상태가 running으로 표시된다.
  3. 격리와 네트워크·저장소 연결컨테이너는 별도의 파일 시스템과 프로세스·네트워크 환경을 갖고 동작한다. -p 로 호스트 포트를 연결하고, -v 로 호스트 디렉터리나 볼륨을 컨테이너 경로에 붙이며, -e 로 환경변수를 넣는다.
  4. 백그라운드 실행과 이름 부여-d 를 주면 명령이 즉시 반환되어 컨테이너가 계속 돌고, --name 으로 붙인 이름으로 나중에 docker logs, docker exec, docker stop 같은 명령이 해당 컨테이너를 지정한다.

4컨테이너 실행04-02

컨테이너 기본값 재정의

이미지에 미리 들어 있는 기본값(기본 명령어, 작업 디렉터리, 사용자, 환경변수 등)을 docker run 옵션으로 컨테이너를 만드는 시점에 덮어쓰는 것.

1문제 상황

Dockerfile에는 이미 CMD, WORKDIR, USER, ENV 같은 기본값이 미리 들어 있다. 이 값들은 이미지마다 다르고, 같은 이미지를 개발 환경에서는 한 포트로, 운영 환경에서는 다른 포트와 권한으로 실행해야 할 때가 많다. 기본값이 마음에 안 들면 Dockerfile을 새 이미지로 다시 빌드해야 했고, 한 이미지를 상황별로 다르게 쓰기가 어려웠다.

2핵심 질문

이미지에 들어 있는 기본 실행 설정을 이미지를 다시 빌드하지 않고, 컨테이너를 만드는 시점에 docker run 옵션으로 덮어쓰려면 어떻게 해야 하는가?

3동작 예시

이미지의 Dockerfile에 CMD ["python", "app.py"] 가 있고 WORKDIR이 /app 인데, docker run -w /srv --user 1000 -e DEBUG=1 -e PORT=9000 -p 9000:9000 myimg python -u app.py --port 9000 를 실행하면 작업 디렉터리가 /srv, 실행 사용자가 uid 1000, 환경변수 DEBUG와 PORT이 새 값으로 설정되고, CMD 대신 python -u app.py --port 9000 가 실행 명령으로 쓰인다. 이미지는 그대로 두고 실행 조건만 바뀐다.

4동작 과정

  1. 기본값이 온 시점Dockerfile의 WORKDIR, USER, ENV, EXPOSE, ENTRYPOINT, CMD 가 빌드 시점에 이미지 설정에 기록되어, 컨테이너가 따로 지정하지 않으면 그대로 쓰인다.
  2. 시점 선택docker run 실행 시 덮어쓰는 것과, 이미 만들어 둔 컨테이너에 docker container update 로 반영하는 것이 다르다. 볼륨·포트처럼 컨테이너 생성 이후 바꿀 수 없는 항목은 docker run 에서만 지정한다.
  3. CLI로 덮어쓰기-w(작업 디렉터리), --user(실행 사용자), -e(환경변수), -p(포트 매핑) 같은 옵션이 이미지 설정보다 우선한다. docker run 이 실행 명령을 따로 주면 CMD를 무시하고, 인자만 주면 ENTRYPOINT 뒤에 CMD 자리에 붙는다.
  4. 보존되는 값지정하지 않은 항목은 이미지의 기본값이 그대로 유지된다. 컨테이너 기본값은 이미지 안에서 바뀌지 않으므로 여러 컨테이너가 서로 다른 값으로 같은 이미지를 동시에 쓸 수 있다.

5한 줄 요약

이미지 안의 기본 실행 설정을 컨테이너를 만드는 시점의 docker run 옵션으로 덮어써, 이미지 재빌드 없이 실행 조건을 바꾸는 것

포트 발행과 노출

-p 옵션으로 컨테이너가 안에서 듣는 포트를 호스트의 포트에 연결해 바깥에서 접근하게 하는 것으로, EXPOSE는 정보를 남길 뿐 실제 외부 공개는 하지 않는다.

1문제 상황

컨테이너는 자체적인 네트워크 환경을 갖기 때문에 내부에서 80번 포트로 서비스를 듣더라도 호스트 바깥에서는 그 포트에 바로 접근할 수 없다. 같은 호스트의 다른 컨테이너끼리는 내부 통신망으로 연결할 수 있지만, 브라우저나 외부 클라이언트에서 접속하려면 별도의 경로가 필요하다. 어떤 포트를 열어 두어야 하는지 Dockerfile에 적어 두고도 실제로 외부에 공개되지는 않아, 문서와 실제 동작이 어긋나게 види기도 한다.

2핵심 질문

컨테이너 안에서 듣는 포트를 호스트의 포트에 연결해 외부에서 접근할 수 있게 하는 것은 무엇이고, 단순한 안내와 실제 공개는 어떻게 구분되는가?

3동작 예시

docker run -d -p 8080:80 nginx 를 실행하면 컨테이너의 80번 포트가 호스트의 8080번 포트로 연결되고, 브라우저에서 http://localhost:8080 으로 접속하면 nginx 페이지가 열린다. -p 127.0.0.1:8080:80 처럼 호스트 IP를 함께 적으면 그 주소로 들어오는 요청만 받고, -p 80 처럼 컨테이너 포트만 적으면 호스트의 빈 포트 중 하나가 자동으로 배정된다. 반면 Dockerfile의 EXPOSE 80 은 정보를 남길 뿐, -p 없이 이미지만 실행하면 외부에 공개되지 않는다.

4동작 과정

  1. 컨테이너 내부 포트 대기컨테이너는 자체 네트워크 인터페이스에서 지정된 포트로 요청을 받는다. 이 포트는 컨테이너 안에서만 의미가 있고 호스트와는 별개의 주소 공간이다.
  2. 호스트 포트 연결-p [호스트IP:]호스트포트:컨테이너포트 로 컨테이너 포트를 호스트 포트에 바인딩한다. 이렇게 연결된 포트를 발행(publish)이라고 하며, 바인딩은 컨테이너가 실행 중일 때만 유지된다.
  3. 방향과 주소 제한컨테이너 안에서 밖으로 나가는 아웃바운드 통신은 별도 설정 없이 가능하지만, 안으로 들어오는 인바운드는 이 바인딩이 있어야 한다. 바인딩 주소를 127.0.0.1로 제한하면 같은 호스트의 로컬 프로세스만 접속할 수 있다.
  4. EXPOSE와의 구분EXPOSE 는 이미지에 사용될 포트를 기록해 문서화와 자동 설정에 쓰이는 선언일 뿐이며, 그 자체로 방화벽을 열거나 포트를 외부에 공개하는 동작을 수행하지 않는다.

5한 줄 요약

컨테이너가 듣는 포트를 호스트 포트에 바인딩해 외부에서 접근할 수 있게 하되, EXPOSE 선언만으로는 공개되지 않는 것

--memory, --cpus 같은 옵션으로 컨테이너가 쓸 수 있는 메모리와 CPU를 상한으로 제한해 한 컨테이너가 다른 컨테이너와 호스트 자원을 압도하지 않게 하는 것.

1문제 상황

컨테이너를 실행하면 그 안의 프로세스는 호스트의 CPU와 메모리를 요청한 만큼 그대로 쓸 수 있고, 설정한 상한이 없다. 그 결과 메모리를 많이 먹는 프로세스 하나가 호스트의 자원 전체를 점유해 다른 컨테이너와 도커 데몬까지 반응을 멈추게 만든다.

2핵심 질문

한 컨테이너가 사용할 수 있는 CPU와 메모리의 상한을 정해, 다른 컨테이너와 호스트가 멈추지 않게 만들 수 있는가?

3동작 예시

docker run --memory 512m --cpus 1.5 로 컨테이너를 띄우면, 안의 프로세스는 메모리를 512MB보다 많이 쓰면 커널이 OOM(메모리 부족으로 프로세스를 강제 종료하는 상태)에 걸려 죽고, CPU는 1.5코어 분량까지만 얻는다. 나머지 CPU는 다른 컨테이너가 그대로 쓴다.

4동작 과정

  1. 옵션으로 상한 지정docker run 또는 docker update에 --memory, --memory-swap, --cpus, --cpu-shares 같은 값을 넘겨 컨테이너가 쓸 수 있는 양을 정한다.
  2. 커널이 개입해 제한Docker 엔진이 이 값을 리눅스 커널의 cgroup(프로세스를 묶어 자원 사용량을 통제하는 기능)에 적용한다. 컨테이너가 상한을 넘으려 하면 커널이 그 요청을 막거나 줄인다.
  3. 초과 시 처리메모리 상한을 넘긴 프로세스는 OOM으로 종료되고, --restart를 켜 두면 같은 설정으로 다시 시작된다. CPU는 상한까지만 얻으므로 다른 컨테이너의 속도에는 영향이 없다.

2핵심 질문

실행 중인 컨테이너의 자원 사용량을 실시간으로 확인하고, 데몬이 재기동될 때 컨테이너가 자동으로 다시 시작되게 할 수 있는가?

3동작 예시

터미널에서 docker stats를 실행하면 CPU 비율, 메모리 사용량, 네트워크 입출력량이 컨테이너별로 표 형태로 계속 갱신된다. 여기에 --restart unless-stopped를 붙여 실행해 두면 데몬이 죽었다 다시 올라와도 그 컨테이너는 아무 명령 없이 다시 실행된다.

4동작 과정

  2. 확인docker stats가 이 값을 주기적으로 읽어 화면에 띄우고, docker ps의 상태 정보로 컨테이너가 살아 있는지도 함께 보여 준다.
  3. 자동 시작 등록--restart always나 unless-stopped 같은 재시작 정책을 컨테이너 설정으로 저장해 두고, 데몬이 시작될 때 그 목록을 읽어 해당 컨테이너를 다시 실행한다.

5스토리지05-01

5단계 스토리지

Docker가 호스트 쪽 디스크 영역을 직접 관리해 주는 네임드 저장소로, 컨테이너가 지워져도 데이터는 남는다.

1문제 상황

docker run으로 만든 컨테이너는 자신의 파일시스템을 컨테이너专属 저장 계층에 두기 때문에, 컨테이너를 rm하면 그 안의 데이터가 함께 사라진다. 데이터를 남기려면 호스트 경로를 직접 연결해야 하는데, 경로 권한을 일일이 맞추는 반복 작업이 필요했다.

2핵심 질문

컨테이너가 사라져도 데이터를 보존되는 별도의 저장 공간을 컨테이너에 붙일 수 있는가?

3동작 예시

docker volume create mydata로 볼륨을 만들고 docker run -v mydata:/var/lib/postgresql 로 실행하면, 컨테이너 안의 /var/lib/postgresql은 호스트의 디스크 영역을 직접 쓰게 된다. 컨테이너를 지우고 다시 같은 볼륨으로 만들면 이전 데이터가 그대로 남아 있다.

4동작 과정

  1. 볼륨 생성docker volume create가 호스트의 한 디렉터리를 Docker가 관리하는 네임드 볼륨으로 등록하고, 볼륨 이름을 경로 대신 식별자로 쓴다.

2핵심 질문

호스트에 이미 존재하는 파일이나 디렉터리 경로를 컨테이너 안의 경로에 그대로 연결해, 수정·공유를 즉시 반영할 수 있는가?

3동작 예시

docker run -v C:\project:/app 로 실행하면, 호스트의 C:\project에 저장한 소스 코드가 컨테이너의 /app에 즉시 보인다. 호스트에서 파일을 고치면 컨테이너 안에서도 같은 내용이 보이며, 컨테이너에서 만든 파일도 호스트에 남는다.

4동작 과정

  1. 경로 지정docker run -v <호스트경로>:<컨테이너경로> 로 두 경로를 명시한다. 경로를 그대로 주면 바인드 마운트로 취급하고, 없는 이름의 볼륨을 주면 볼륨으로 만든다.
  2. 연결엔진이 마운트 시점에 컨테이너의 마운트 지점을 호스트 경로로 바꿔치기해, 양쪽이 같은 inode(파일 시스템에서 파일을 가리키는 내부 번호)를 보게 한다.
  3. 동기 반영마운트는 실행 중에도 유지되므로 양쪽 어디에서 쓰든 즉시 서로 반영되고, 컨테이너를 지워도 호스트의 원본 데이터는 남는다.

  3. 임시 사용컨테이너 안에서 만든 파일은 RAM에 저장되며, 실행 중인 동안 스왑 영역으로 넘어갈 수 있다. 컨테이너가 종료되면 할당된 메모리가 바로 해제된다.

6네트워킹06-01

브리지 네트워크

호스트의 실제 브리지 위에 붙여 같은 네트워크의 컨테이너끼리 이름을 통해 직접 통신하게 하는 기본 네트워크 드라이버.

1문제 상황

컨테이너마다 격리된 네트워크가 붙으면 컨테이너끼리 통신할 방법이 없다. IP 주소만 알고 직접 붙여 쓰면 컨테이너가 재생성될 때마다 주소가 바뀌고, 어떤 이름으로 상대 컨테이너를 찾을지 알 수도 없다. 한 컨테이너가 다른 컨테이너에 요청하려면 开发자가 주소와 포트를 직접 관리해야 한다.

2핵심 질문

같은 호스트에서 함께 동작하는 컨테이너들이 서로를 이름으로 찾고 직접 통신할 수 있게 하려면 어떻게 해야 하는가?

3동작 예시

호스트 안에 실제 네트워크 브리지(호스트의 모든 NIC가 붙는 소프트웨어 스위치)를 하나 만들고, 그 위에 web 이라는 이름으로 컨테이너를 실행한다. 그러면 호스트의 실제网卡들과 컨테이너网卡가 같은 스위치에 꽂혀 있는 상태가 되고, 컨테이너에서 다른 컨테이너를 이름으로 부르면 그 이름이 IP 로 바뀐 뒤 직접 패킷이 전달된다.

4동작 과정

  1. 브리지 생성데몬이 호스트에 브리지 인터페이스를 만들고, 그 브리지에 물리 NIC 를 붙여 외부와 통신하는 경로를 만든다. 브리지는 여러 포트를 하나의 논리적 연결로 묶는 호스트의 기능이다.
  2. 네트워크 생성docker network create 로 만들어진 사용자 정의 브리지 네트워크에 컨테이너가 붙는다. 사용자 정의 네트워크에서는 Docker 가 내부 DNS(컨테이너 이름을 IP 로 바꿔주는 기능)를 자동으로 운영한다.
  3. 컨테이너 연결컨테이너는 이 네트워크에 접속하면서 전용 IP 를 받는다. 브리지의 내부 DNS 가 이름 조회 요청을 해석해 주므로, http://api:8080 처럼 이름으로 통신할 수 있다. 기본 bridge 네트워크에는 이 자동 이름 해석이 없고, 대신 포트 발행(06-04)으로 외부에 노출한다.

6네트워킹06-02

호스트·논·오버레이 네트워크

컨테이너를 호스트와 네트워크를 공유하거나 완전히 차단하고, 여러 스움 노드 사이를 가상의 계층 2 망으로 이어 주는 나머지 기본 드라이버들.

1문제 상황

브리지 네트워크는 NAT 를 거치므로 컨테이너가 호스트와 같은 IP 주소를 쓰지 못하고, 방화벽이나 특정 포트에만 붙을 수 있다. 어플리케이션이 자기 IP 주소를 직접 감지하거나, 감지한 주소를 그대로 반환하거나, 고유 포트를 필요로 할 때는 브리지 방식으로는 불가능하다. 여러 호스트에 흩어진 컨테이너끼리 통신하는 길도 필요했다.

2핵심 질문

컨테이너를 호스트의 네트워크에 완전히 붙여 버리거나, 여러 머신에 걸친 컨테이너들을 하나의 가상 근거리망으로 묶을 수 있는가?

3동작 예시

--network host 로 실행한 컨테이너에는 네트워크 인터페이스가 새로 생기지 않는다. 컨테이너 안에서 본 eth0 이 곧 호스트의 실제 인터페이스이고, 컨테이너는 호스트가 이미 listening 중인 포트를 그대로 사용한다. 오버레이 네트워크에서는 여러 호스트 위의 컨테이너가 각자 내부에서 sees 같은 IP 대역과 MAC 주소를 받기 때문에, 실제 랜 케이블이 없는 가상의 이더넷 위에서 서로 통신한다.

4동작 과정

  1. 호스트 네트워크컨테이너가 호스트의 네트워크 네임스페이스를 공유한다. 주소 변환이나 포트 매핑 없이 호스트의 모든 인터페이스와 포트를 직접 쓴다. none 드라이버는 그 반대 끝으로, 인터페이스를 하나도 주지 않아 외부 통신이 불가능하다.
  2. 오버레이 네트워크docker network create -d overlay 로 만들면 각 호스트에 터널(다른 호스트로 패킷을 감싸 보내는 통로)을 세운다. 스위마 그리 드라이버가 여러 데몬을 하나로 묶어, 각 데몬이 관리하는 컨테이너들이 같은 가상 이더넷에 붙게 된다.
  3. 컨테이너 연결오버레이에 붙은 컨테이너는 마운트한 디렉터리에 있는 암호화된 키 파일을 통해 다른 호스트의 터널과 서로를 authenticate 한다. 그래서 여러 머신에 걸친 통신도 같은 방식으로 동작한다.

6네트워킹06-03

Macvlan·IPvlan 네트워크

컨테이너에 물리 머신처럼 별도의 MAC·IP 주소를 배정해 라우터와 물리 호스트가 컨테이너를 독립된 통신 상대로 취급하게 하는 드라이버.

1문제 상황

브리지 네트워크의 컨테이너는 주소가 변환되어 나가기 때문에 라우터가 컨테이너를 하나의 물리 장치로 보지 않는다. 물리 머신처럼 다루어야 하는 환경, 예를 들어 스위치의 포트 보안이나 802.1Q 를 VLAN 태그에 의존하는 환경에서는 이 변환 방식이 그대로 문제를 일으킨다. 결과적으로 컨테이너를 물리 호스트처럼 등록해 관리해야 한다.

2핵심 질문

물리적 IP 와 MAC 주소가 이미 정해진 네트워크에서, 컨테이너를 그 주소까지 그대로 가진 독립된 통신 상대로 만들 수 있는가?

3동작 예시

물리 네트워크에 192.168.1.0/24 가 있고 호스트가 192.168.1.10 을 쓴다고 하자. docker network create -d macvlan -o subnet=192.168.1.0/24 -o parent=eth0 mynet 을 실행한 뒤, docker network connect mynet 컨테이너 로 붙이면 컨테이너가 192.168.1.0/24 대역에서 별도의 주소를 배정받는다. 이제 라우터는 컨테이너를 192.168.1.10 이라는 호스트가 아니라 다른 장비로 인식하고, 그 장비는 어디에도 설치되지 않았지만 실제 통신 상대로 동작한다.

4동작 과정

  1. 드라이버 선택macvlan 은 컨테이너에 고유한 MAC 주소를 배정한다. ipvlan 은 여러 컨테이너가 하나의 호스트 MAC 주소를 공유하고, 컨테이너별로 구분하는 것은 IP 주소와 네트워크 인터페이스 이름뿐이다.
  2. 주소 배정-o subnet= 과 -o parent= 옵션으로 물리 인터페이스의 하위 대역과 상위 인터페이스를 지정한다. Docker 는 이 범위 안에서 컨테이너에 주소를 배정하고, 브리지처럼 NAT 하지 않는다.
  3. 접속 방식 지정macvlan 은 private 또는 bridge 모드가 필요하다. private 은 같은 호스트의 다른 컨테이너와 통신할 수 없고, bridge 는 가능하게 만든다. ipvlan 은 부모 인터페이스 이름을 컨테이너에 그대로 보여 준다.

5한 줄 요약

NAT 없이 컨테이너에 별도의 MAC·IP 주소를 직접 배정해 라우터와 물리 호스트가 컨테이너를 독립된 장비로 보게 만드는 것

포트 발행과 방화벽

컨테이너 포트를 호스트 포트로 열어 외부에서 닿게 하는 규칙과, 그 과정에서 데몬이 iptables·nftables에 자동으로 추가하는 방화벽 규칙을 함께 다룬다.

1문제 상황

컨테이너 안에서만 도는 서비스는 컨테이너 내부 주소로는 외부에서 닿을 수 없다. 서비스를 바깥에 알리려면 어떤 주소의 어떤 포트로 들어온 요청을 컨테이너의 어느 포트로 넘길지 정해야 하고, 이 규칙을 매번 수동으로 만들면 컨테이너가 바뀔 때마다 직접 갱신해야 한다. 또한 새로 열린 통로가 다른 서비스에 노출되지 않도록 방화벽 규칙도 함께 관리해야 한다.

2핵심 질문

컨테이너 안의 특정 포트로 외부에서 직접 닿을 수 있게 하고, 그 과정에서 방화벽 규칙까지 자동으로 맞추려면 어떻게 해야 하는가?

3동작 예시

docker run -p 8080:80 myapp 을 실행하면 호스트의 8080 포트로 들어온 요청이 컨테이너의 80 포트로 전달된다. 데몬은 이 규칙을 iptables 의 nat 테이블 DNAT 규칙으로 만들어 넣고, 출발·도착 인터페이스 체인에 규칙을 추가해 패킷을 온다 갔다 한다. 컨테이너가 삭제되면 그 규칙은 함께 사라진다.

4동작 과정

  1. 포트 매핑 선언-p 에 호스트 포트와 컨테이너 포트를 함께 적는다. 8080:80 처럼 쓰면 모든 인터페이스에서 받지만, 127.0.0.1:8080:80 처럼 호스트 주소를 함께 적으면 그 주소에서만 접근할 수 있다. 포트를 생략하면 호스트의 임의의 빈 포트가 배정되어 그 번호를 docker port 로 확인할 수 있다.
  2. 방화벽 규칙 자동 추가데몬은 publishing 을 요청할 때 iptables 의 nat 테이블과 filter 테이블에 규칙을 직접 넣는다. 이 규칙은 컨테이너 수명에 묶여 있어, 컨테이너가 끝나면 함께 제거된다. DOCKER-USER 체인(사용자가 직접 규칙을 끼워 넣는 지점)도 함께 만들어진다.
  3. 백엔드 규칙 자동 추가컨테이너가 시작될 때 등에는 그 컨테이너에만 해당하는 백엔드 규칙이 추가된다. 컨테이너가 시작 상태가 아니면 publishing 규칙만 남아 있고, 방화벽은 여전히 포트를 닫아 둔 상태로 유지된다.

5한 줄 요약

호스트 포트로 들어온 요청을 컨테이너 포트로 넘기는 규칙을 선언만 하면 데몬이 방화벽까지 자동으로 맞춰 주는 것

1문제 상황

하나의 애플리케이션은 보통 여러 컨테이너로 이루어진다. 데이터베이스, 웹 서버, 캐시처럼 역할이 다르며, 서로 통신해야 하므로 네트워크 이름과 환경 변수와 볼륨을 맞춰 붙여야 한다. 이걸 명령줄 옵션으로 하나씩 실행하면 어떤 컨테이너가 어떤 설정으로 떴는지 기록하기 어렵고, 컨테이너를 다시 띄울 때 같은 명령을 다시 입력해야 한다.

2핵심 질문

여러 컨테이너를 하나의 애플리케이션 단위로 묶어, 구성과 실행 상태를 한 번의 명령으로 함께 다루려면 어떻게 해야 하는가?

3동작 예시

compose.yaml 에 서비스 A 가 서비스 B 에서 쓰는 이미지 이름과 함께 네트워크를 정의해 두면, docker compose up 한 번으로 데몬은 정의된 순서대로 컨테이너를 만들고, 기본 네트워크 하나를 만들어 그 위에 전부 붙인다. 그 뒤 docker compose ps 로 이 애플리케이션에 속한 컨테이너만 골라 볼 수 있다.

4동작 과정

  1. 애플리케이션 모델Compose 는 여러 컨테이너를 하나의 애플리케이션으로 다루는 단위로 정의한다. 각 컨테이너는 여기서 서비스라 부르고, 이 서비스들의 집합이 애플리케이션 하나가 된다. docker compose 명령의 대상은 이 애플리케이션이다.
  2. 선언이미지나 빌드 방법, 환경 변수, 포트, 볼륨, 네트어�� 의 연결 관계를 YAML 파일 하나에 적는다. 실행 명령이 아니라 구성 자체가 저장되므로, 같은 파일로 언제든 같은 구성을 다시 만들 수 있다.
  3. 수명 주기 관리up 은 필요한 컨테이너를 만들고 시작하고, down 은 이 애플리케이션의 컨테이너와 네트워크를 제거한다. start 나 stop 은 이미 만들어진 컨테이너만 다룬다. 일반 docker run 으로 만든 컨테이너는 docker compose run 처럼 이 애플리케이션 바깥의 대상으로 남는다.

Compose 파일 작성

compose.yaml 라는 YAML 파일에 services 항목 아래에 컨테이너별로 image나 build, ports, volumes 같은 속성을 적어 앱 구성을 선언하는 일.

1문제 상황

구성을 파일에 적지 않으면 컨테이너를 실행할 때마다 같은 옵션들을 손으로 다시 입력해야 하고, 무엇을 어떻게 띄웠는지 알 수 없다. 파일에 적더라도 어디에 무엇을 써야 규칙이 성립하는지 모르면 여전히 실행이 불가능하다. Compose 파일은 정해진 최상위 항목과 services 아래 속성 구조를 따라야 파서가 제대로 읽는다.

2핵심 질문

Compose 파일에 무엇을 어디에 적어야 데몬이 그 구성대로 컨테이너를 만들 수 있는가?

3동작 예시

최상위에 services 항목 아래에 서비스 이름 하나를 두고, 그 아래에 image 와 ports 를 적으면 데몬은 해당 이미지를 받아 컨테이너를 만들고 포트를 발행한다. 여기에 build 를 대신 적으면 원본 코드가 있는 경로에서 이미지를 직접 빌드한 뒤 그 결과로 컨테이너를 만든다.

4동작 과정

  1. 최상위 구조compose.yaml 의 최상위 항목은 services(컨테이너 정의), networks(네트워크 정의), volumes(볼륨 정의), configs, secrets 다. services 아래 각 항목이 컨테이너 하나를 나타내며, 그 이름이 docker compose run 에 넘기는 이름이 된다.
  2. 이미지 지정image 는 사용할 이미지 이름과 태그를 적는다. build 는 빌드할 컨테이너의 경로와 Dockerfile 을 지정한다. image 와 build 를 함께 쓰면 build 로 만든 이미지를 image 이름으로 태그해 두는 의미가 된다. pull_policy 로 이미지 가져오기 시점을 조절한다.
  3. 연결과 자원 지정ports 는 8080:80 처시 바깥 포트와 안쪽 포트를 함께 적고, volumes 는 호스트 경로와 컨테이너 경로를 경로:경로 로 짝지어 데이터 저장 위치를 정한다. depends_on 은 다른 서비스에 대한 의존 관계를, environment 는 환경 변수 목록을, profiles 는 실행 시 선택적으로 띄울 대상을 지정한다.

Compose 파일 안에서 ${변수} 같은 문법으로 호스트 환경 변수나 .env 파일의 값을 집어 넣어 이미지 태그·비밀값·경로 등을 실행 시점에 채우는 기능.

1문제 상황

Compose 파일은 텍스트로 저장되어 그대로 읽히기 때문에 이미지 태그나 경로 같은 값이 파일 안에 박혀 있다. 같은 파일을 개발과 운영에 나눠 쓰려면 값을 매번 고쳐야 하고, 비밀값이 필요하면 그 자리에도 값을 적어 넣어야 한다.

2핵심 질문

Compose 파일에 값을 고정해 적지 않고, 실행하는 시점의 환경에 맞춰 그 자리를 채울 수 있는가?

3동작 예시

이미지 태그를 image: myapp:${VERSION}으로 적고 VERSION=2.1.0 docker compose up을 실행하면, 조립 과정에서 그 자리에 2.1.0이 들어가 myapp:2.1.0으로 확정된 구성이 만들어진다.

4동작 과정

  1. 값 선언${변수} 문법으로 값을 넣을 자리를 남기고, 비어 있을 때 쓸 기본값은 ${변수:-기본값} 형태로 같은 자리에 적는다.
  2. 값 해석Compose 엔진이 실행 시점에 호스트 환경 변수와 프로젝트 디렉터리의 .env 파일을 차례로 찾아 해당 값을 자리에 넣는다.
  3. 구성 확정채워진 최종 텍스트를 컨테이너 생성 인자로 넘기므로, 컨테이너 안에는 이미 확정된 값만 보인다.

Compose 네트워킹

프로젝트마다 자동으로 하나 만들어지는 기본 네트워크에 모든 서비스가 붙어 서비스 이름으로 서로 통신할 수 있게 하는 구성이며, 외부·브리지·오버레이 네트워크를 명시해 제어하기도 한다.

1문제 상황

여러 컨테이너를 함께 띄우면 각 컨테이너는 자기만의 IP를 갖고 격리된 채로 뜨기 때문에, 서로 통신하려면 주소를 직접 알아야 한다. 포트를 하나씩 매핑해 접속하는 방식도 컨테이너가 늘어날수록 연결 정보를 관리하기 어려워진다.

2핵심 질문

프로젝트 안의 컨테이너들이 서로의 IP를 몰라도 이름만으로 통신할 수 있게 만들 수 있는가?

3동작 예시

Compose로 만든 프로젝트에는 프로젝트 이름과 같은 기본 네트워크가 하나 자동으로 생기고 모든 서비스가 그 위에 붙는다. api 서비스가 다른 서비스에 http://api:8080으로 요청하면 내장 DNS가 이 이름을 해당 컨테이너의 IP로 바꿔 돌려준다.

4동작 과정

  1. 네트워크 생성Compose가 프로젝트 이름의 기본 네트워크를 만들고 그 위에서 모든 서비스를 시작한다. 기본 드라이버는 브리지라 같은 호스트 안의 컨테이너끼리만 통신이 가능하다.
  2. 이름으로 통신내장 DNS 서버가 서비스 이름을 컨테이너 IP에 대응시킨다. 그래서 컨테이너는 이름으로 요청만 보내면 되고 포트를 따로 매핑할 필요가 없다.
  3. 네트워크 명시networks 키로 외부 네트워크를 미리 만들어 두거나 드라이버를 오버레이로 지정해 여러 호스트의 컨테이너를 같은 이름 공간에 묶을 수도 있다.

비밀값을 Compose 파일에 직접 적지 않고 비밀 파일로 선언해 컨테이너에 /run/secrets 경로로 마운트해, 빌드 시점과 실행 시점 모두에서 노출을 줄이는 방법.

2핵심 질문

비밀값을 구성 파일이나 이미지에서 분리해 컨테이너 실행 시에만 전달할 수 있는가?

3동작 예시

docker secret create로 만든 비밀을 서비스에 배정하면 컨테이너 안의 /run/secrets/db_password 파일로 전달된다. 애플리케이션은 이 파일의 내용을 읽어 연결하고, 비밀 값 자체는 실행되지 않은 어떤 상태에도 저장되지 않는다.

  2. 선언과 배정Compose 파일의 secrets 항목에 비밀 이름을 적어 어떤 서비스에 붙일지 선언한다. file로 외부 비밀 파일을 가리키거나 Compose 시크릿 파일 포맷으로 직접 선언할 수 있다.

프로파일와 서비스 그룹화

서비스에 profiles 이름을 붙여 두고 docker compose --profile 이름으로 up 할 때만 그 그룹을 함께 띄우게 하는 기능으로, 개발용 도구나 선택적 구성 요소를 조건부로 다룰 수 있다.

1문제 상황

Compose 파일 하나에 운영에 필요한 서비스와 개발에만 쓰는 도구를 함께 적으면, 실행할 때 필요 없는 것까지 같이 떠오른다. 반대로 목록에서 지워 버리면 같은 파일을 운영에 그대로 다시 쓸 수 없게 된다.

2핵심 질문

하나의 구성 파일에서 어떤 서비스는 항상 띄우고 어떤 서비스는 필요할 때만 띄울 수 있는가?

3동작 예시

관리 도구 서비스에 profiles: ["debug"]를 붙여 두면 평소 docker compose up에는 반응하지 않고, docker compose --profile debug up일 때만 함께 실행된다. 운영용 실행에는 개발용 도구가 뜨지 않는다.

4동작 과정

  1. 그룹 지정서비스에 profiles 키로 이름을 붙이고 그 이름을 가진 서비스 그룹을 만든다. 프로파일이 없는 서비스는 그룹에 속하지 않으므로 항상 실행 대상이 된다.
  2. 그룹 선택--profile 이름을 붙여 실행하면 선택한 이름의 서비스만 대상 목록에 추가된다. 이름을 콤마로 나열해 여러 그룹을 한 번에 고를 수도 있다.
  3. 상속 처리profiles는 서비스의 상속 관계를 따라 전파된다. 상위 서비스에 프로파일을 지정하지 않으면 하위 그룹 전체가 실행 대상에 포함된다.

시작 순서와 라이프사이클 훅

depends_on과 healthcheck로 어떤 서비스가 준비된 뒤 다음 서비스가 뜨게 순서를 잡고, pre_start·post_start·pre_stop 같은 훅으로 컨테이너 시작·종료 전후에 명령을 끼워 넣는 방법.

1문제 상황

컨테이너를 나열해 한 번에 시작하면 빠르게 뜨는 서비스가 아직 준비되기 전에 느린 서비스가 연결을 시도해 실패한다. 또 시작 직전에 디렉터리 생성이나 마이그레이션 같은 준비 작업이 필요한데, 그런 명령을 넣을 자리가 없다.

2핵심 질문

앞선 서비스가 실제로 준비된 뒤에 다음 서비스를 시작하고, 그 시작 전후에 필요한 명령을 실행할 수 있는가?

3동작 예시

데이터베이스 서비스에 healthcheck로 연결 확인 명령을 걸어 두면 Compose는 그 명령이 성공할 때까지 기다린다. 웹 서비스는 depends_on으로 그 서비스에 의존하므로, 데이터베이스가 healthy가 된 뒤에야 컨테이너가 시작된다.

4동작 과정

  1. 의존 선언depends_on으로 먼저 필요한 서비스를 지정하고, condition으로 시작 순서만 지킬지 상태 확인까지 기다릴지를 정한다. 쓸 수 있는 값은 service_started와 service_healthy다.
  2. 준비 확인healthcheck에 검사 명령과 검사 주기를 적으면 Compose가 주기적으로 실행해 상태를 확인하고, 조건이 충족될 때까지 다음 단계로 넘어가지 않는다.
  3. 훅 실행pre_start·post_start·pre_stop에 명령을 적어 컨테이너를 만들기 직전, 메인 프로세스를 시작한 직후, 멈추기 직전에 각각 끼워 넣는다. 각 훅은 같은 사용자 권한으로 실행되며 실패하면 Compose 실행이 중단된다.

파일 확장과 병합

여러 Compose 파일을 함께 주거나 extends·include로 다른 파일을 불러와 공통 부분을 재사용하고, 겹치는 속성은 규칙에 따라 덮어써 하나의 구성으로 합치는 방식.

1문제 상황

프로젝트 규모가 커지면 Compose 파일 하나에 모든 서비스와 공통 설정을 다 적어야 해서 관리가 어려워진다. 환경별 설정을 따로 파일로 만들면 중복이 생기고, 반대로 공통 설정을 파일로 빼면 같은 값을 여러 곳에서 고쳐야 한다.

2핵심 질문

여러 설정 파일을 하나의 실행 구성으로 합치면서 중복은 재사용하고, 겹치는 값은 정해진 규칙으로 정할 수 있는가?

3동작 예시

docker compose -f base.yml -f prod.yml up을 실행하면 base.yml의 서비스 위에 prod.yml의 같은 서비스 설정이 덮여 적용된다. base.yml의 공통 볼륨 선언은 그대로 남고 이미지 태그만 prod.yml의 값이 된다.

4동작 과정

  1. 파일 나열-f 옵션으로 파일을 나열하면 앞에서 뒤로 읽어 하나의 구성으로 합친다. 옵션을 주지 않으면 기본값인 compose.yaml 하나만 쓴다.
  2. 병합 규칙매핑 구조는 키 단위로 합쳐 뒤 파일의 값이 이긴다. ports·environment·volumes처럼 목록인 항목은 이름이나 경로 기준으로 합쳐 같은 대상의 값이 뒤 파일의 것으로 교체된다. 뒤에 나온 파일이 항상 이긴다.
  3. 재사용extends는 다른 파일의 서비스 정의를 그대로 복사해 오고, include는 다른 파일의 내용을 통째로 가져온다. 공통 부분은 한 곳에 두고 필요한 부분만 덧씌운다.

5한 줄 요약

Compose 설치와 CLI

Compose는 Docker CLI의 플러그인이나 독립 실행 파일로 설치해 docker compose up·build·down 같은 하위 명령으로 프로젝트를 다루며, docker-compose(하이픈) 같은 구형 방식과 구분된다.

1문제 상황

Compose는 이미지와 컨테이너를 다루는 Docker 엔진과는 별개로, 여러 컨테이너를 한 번에 정의하고 함께 올리는 도구가 필요하다. 예전에는 파이썬 기반의 독립 실행 파일 docker-compose와 하이픈으로 된 하위 명령을 썼기 때문에, 지금 쓰는 방식과 구형 문서가 달라 혼동이 생긴다.

2핵심 질문

설치 형태가 달라도 같은 명령으로 프로젝트 단위의 컨테이너 실행을 수행할 수 있는가?

3동작 예시

docker compose up -d을 실행하면 현재 디렉터리의 compose.yaml를 읽어 필요한 이미지를 빌드하고 컨테이너를 백그라운드로 올린다. docker compose down을 실행하면 이 프로젝트로 만든 컨테이너와 네트워크를 함께 정리한다.

4동작 과정

  1. 설치Docker CLI 플러그인으로 설치하면 docker compose라는 하위 명령으로 붙고, 독립 바이너리로 설치하면 docker-compose로 직접 호출한다. 리눅스에서는 배포판 패키지 관리자나 공식 저장소의 패키지를 쓴다.
  2. 구성 읽기실행할 때 현재 디렉터리의 compose.yaml를 기본으로 찾고, -f로 다른 파일이나 여러 파일을 지정할 수 있다. 읽은 구성으로 필요한 이미지·컨테이너·네트워크를 계산한다.
  3. 프로젝트 조작up·build·down·ps·logs 같은 하위 명령으로 전체를 띄우거나 다시 만들거나 내린다. 하위 명령 뒤에 서비스 이름을 주면 전체가 아니라 그 서비스만 다룬다.

5한 줄 요약

구성 파일 하나로 여러 컨테이너를 함께 다루게 하는 명령줄 도구

데몬 시작과 설정

dockerd 데몬을 직접 실행해 컨테이너를 관리하는 서비스를 띄우고, 데몬 설정 파일(daemon.json)과 명령줄 옵션으로 저장 드라이버·네트워크·로그 수준 같은 동작을 바꾸는 것.

1문제 상황

컨테이너를 하나 만들려면 이미지로부터 파일시스템·네트워크·프로세스를 조합하고 실행 상태를 관리하는 작업이 필요합니다. 이 일을 하던 때는 사람이 서버마다 같은 명령을 직접 입력해 왔고, 어떤 서버에서 어떤 설정으로 떠 있는지 알 방법이 없었습니다. 설정을 바꾸려면 실행 중인 서비스를 다시 띄워야 해서 중단이 필요했고, 서버가 늘수록 같은 설정과 명령을 여러 번 반복 입력해야 했습니다.

2핵심 질문

컨테이너를 대신 관리하고, 관리 방식은 설정 파일 하나로 일관되게 정해 둘 수 있을까요?

3동작 예시

dockerd를 서버에서 실행하면 컨테이너를 만들고 시작·중지·삭제하는 요청을 받아 처리하는 서비스가 계속 떠 있게 됩니다. 이 서비스가 어떤 드라이버로 이미지를 저장하고 어떤 네트워크를 만들지와 같은 동작은 /etc/docker/daemon.json에 정해 두고, dockerd --log-level=debug처럼 실행 시점에 넘긴 옵션이 그 위에 덮어씁니다. 같은 설정 파일을 여러 서버에 배포하면 어디서 띄운 데몬이든 같은 방식으로 동작합니다.

4동작 과정

  1. 데몬 기동dockerd 바이너리를 실행해 컨테이너 관리 서비스를 기동한다. 백그라운드로 상시 실행되며, 클라이언트는 이 서비스에 요청을 보내 컨테이너를 다루고, 데몬이 죽으면 관리 기능 전체가 사라진다.
  2. 설정 적용/etc/docker/daemon.json에 저장 드라이버(overlay2 등), bridge 같은 기본 네트워크, 데몬 로그 수준 등을 적는다. 모든 값은 선택 항목이라 지정하지 않은 항목은 기본값으로 동작한다.
  3. CLI 명령systemctl enable --now docker로 부팅 시 자동 시작과 기동을 함께 처리하고, dockerd -H unix:///var/run/docker.sock처럼 플래그를 주면 설정 파일의 값을 덮어써 한 번만 다르게 실행할 수 있다.

5한 줄 요약

컨테이너 관리 책임을 데몬 한 곳으로 모으고, 그 동작을 설정 파일과 실행 옵션으로 고쳐 쓸 수 있게 하는 것

원격 접근과 프록시 구성

데몬이 기본 유닉스 소켓뿐 아니라 지정한 IP와 포트로도 요청을 받아들이게 하고(원격 접근), 사내 프록시 뒤에 있을 때 데몬이 HTTP 프록시를 사용하도록 설정하는 것.

1문제 상황

데몬은 기본적으로 로컬의 유닉스 소켓으로만 요청을 받으므로 같은 머신의 클라이언트만 붙을 수 있었습니다. 다른 서버에서 컨테이너를 만들려면 그 서버에 직접 로그인해 명령을 입력해야 했고, 여러 대를 관리하려면 접속 경로와 자격증명을 각각 따로 기억해야 했습니다. 사내망에서 데몬이 있는 서버만 인터넷을 통과할 수 있는 구조라면, 클라이언트가 데몬에 연결하는 과정에서 프록시를 거치지 못해 요청이 아예 닿지 않았습니다.

2핵심 질문

지정한 IP와 포트까지 데몬이 요청을 받고 사내 HTTP 프록시를 통과하게 만들 수 있을까요?

3동작 예시

데몬을 시작할 때 -H tcp://10.0.0.5:2376을 주면 2376 포트로 열린 연결에 컨테이너 생성 요청이 그대로 전달됩니다. 이 포트로만 요청을 받고 TLS(통신 구간을 암호화하는 계층)를 함께 켜면 인증되지 않은 요청은 데몬이 받지 않습니다. 사내 프록시를 거쳐야 하는 환경이라면 클라이언트 쪽에 HTTP_PROXY, 데몬 쪽 이미지 다운로드에 HTTP_PROXY와 HTTPS_PROXY를 환경 변수로 넣고, 프록시가 아닌 주소는 NO_PROXY로 예외 처리합니다.

4동작 과정

  1. 리슨 주소 지정-H 플래그를 여러 개 반복하면 소켓과 TCP 주소를 동시에 열어 두 방식을 모두 받는다. 여기서 127.0.0.1:2375처럼 주소와 포트를 함께 적으면 어느 주소의 어느 포트로 들어올지까지 지정된다.
  2. 원격 보호tlsverify를 켜고 인증서·키 경로를 주면 암호화되지 않은 요청은 거부된다. CA 인증서를 배포한 클라이언트만 데몬이 관리하는 컨테이너를 건드릴 수 있다.
  3. 프록시 경로 설정데몬과 클라이언트 양쪽 환경 변수에 HTTP_PROXY·HTTPS_PROXY·NO_PROXY를 넣으면 각 요청이 그 주소를 거쳐 나가고 사내망 주소는 직행한다. 데몬은 systemctl 환경 파일이나 데몬 설정의 proxies 항목에 값을 넣어 영구 적용한다.

5한 줄 요약

데몬이 받을 요청의 주소와 포트를 직접 지정하고, TLS와 HTTP 프록시 설정을 얹어 안전한 지정 경로로만 명령이 닿게 하는 것

8Docker Engine 관리08-03

로깅 드라이버 구성

컨테이너가 출력한 표준 출력과 표준 오류를 어떤 드라이버(json-file, local, syslog, journald, fluentd 등)를 통해 어디에 얼마나 보낼지 데몬 설정에서 정하는 것.

1문제 상황

컨테이너가 표준 출력과 표준 오류로 내보내는 내용은 컨테이너마다 개별 파일로 흩어져 저장됩니다. 어떤 드라이버로 어디에 얼마나 남길지 정하지 않으면 장기 실행 중인 서버에서 로그가 디스크를 그대로 채우고, 나중에 장애 원인을 추적할 때 필요한 로그가 이미 밀려나 사라진 상태가 됩니다. 로그를 다 모아 두면 디스크 문제, 로컬에 두면 중앙에서 볼 수 없다는 식으로 위치와 양을 원하는 대로 제어할 방법이 없었습니다.

2핵심 질문

컨테이너 출력이 어디로 얼마나 쌓일지 데몬 설정에서 정해 둘 수 있을까요?

3동작 예시

daemon.json에 "log-driver": "local"을 적으면 데몬이 컨테이너 출력을 로컬 바이너리 형식 파일에 저장하고, 그 파일은 최대 20MB가 되도록 순환시킵니다. docker run --log-driver syslog처럼 실행 시점에 드라이버를 지정하면 그 컨테이너만 다른 목적지로 갑니다. 드라이버마다 보낼 수 있는 옵션이 달라 max-size와 max-file 같은 값은 json-file에, 태그까지 실려 가는 형식의 이름·절대 경로 같은 값은 fluentd에 줍니다.

4동작 과정

  1. 드라이버 선택데몬 설정의 log-driver가 기본값을 정하고, 컨테이너 생성 시 --log-driver가 그 기본값을 덮어쓴다. 선택한 드라이버에 맞는 옵션이 함께 지정되어야 그 드라이버가 받은 정보를 그대로 전달한다.
  2. 전송 경로 지정json-file과 local은 데몬이 직접 호스트에 파일을 쓰고, syslog·journald·fluentd·gelf 같은 드라이버는 해당 주소로 출력을 넘겨 원격 수집기가 받는다. fluentd는 태그를 붙이고, splunk는 index를, datadog은 태그와 서비스 정보를 함께 보낸다.
  3. 양 조절max-size(파일 하나 크기 상한)와 max-file(파일 개수 상한)은 도달한 뒤 순환시키거나 새로 열며, max-file을 all로 두면 상한 없이 두어 추적 로깅(fluentd 등)으로 보내는 용도다. 컨테이너를 다시 만들어야 적용되므로 실행 중인 컨테이너에는 소급되지 않는다.

5한 줄 요약

컨테이너 출력을 보낼 드라이버와 목적지, 보낼 크기와 개수를 데몬 설정 한 곳에서 정하는 것

Prometheus 메트릭 수집

데몬이 기본으로 열어 둔 /metrics 경로에 노출되는 컨테이너·빌더·이미지 관련 지표를 Prometheus가 주기적으로 긁어 가서 그래프와 알림에 쓰는 것.

1문제 상황

컨테이너가 몇 개 떠 있고 이미지가 얼마나 큰지, 빌드가 얼마나 걸렸는지를 숫자로 확인하려면 docker ps, docker images, docker system df 같은 명령을 필요할 때마다 직접 치고 눈으로 합산해야 했습니다. 순간적으로 늘어난 CPU·메모리 사용량이나 빌드 성공 실패 비율은 사람이 주시하는 동안만 보입니다. 이미 시스템 안에서 시간 구간별 숫자를 모으고 그래프로 그리는 도구가 있는데, 데몬이 그 도구에 줄 숫자를 내놓지 않아 다른 서비스의 지표만 보고 있었다.

2핵심 질문

데몬이 자체적으로 내는 지표를 기계가 긁어 갈 수 있는 형태로 제공할 수 있을까요?

3동작 예시

데몬은 기본으로 localhost:9323/metrics에 이미 열어 둔 Prometheus 규격의 텍스트 응답을 돌려줍니다. Prometheus 서버는 설정 파일에 static_configs의 targets에 host.docker.internal:9323(컨테이너에서 호스트를 가리키는 이름)을 적어 두고 일정 간격으로 주소를 긁습니다. 데몬은 이런 요청을 받는 기능이 켜져 있는 상태로, 컨테이너 실행 상태·빌드 결과·이미지 목록에 대한 숫자가 이 경로로만 나갑니다.

4동작 과정

  1. 엔드포인트 노출데몬이 /metrics 경로에서 자기 상태를 수치 형태로 내려주고, 이 요청을 처리하려면 --metrics-debian·--metrics 같은 플래그로 기능을 켠 상태여야 한다. 기본 포트는 9323이고 다른 포트로 바꿀 수 있다.
  2. 수집 대상 등록Prometheus 설정의 static_configs에 데몬이 있는 호스트와 포트를 적고 metrics_path를 /metrics로 둔다. 컨테이너 안에서 수집할 때는 호스트 이름 대신 host.docker.internal을 쓴다.
  3. 지표 해석돌아온 텍스트는 이미 생성·실행 중인 컨테이너 수, 이미지 수, 빌드 성공·캐시 상태 같은 값이 담긴 목록이다. Prometheus가 이 시계열 데이터를 저장하고 Grafana가 그래프로 그리고, 임계치를 넘으면 알림 규칙이 설정한 알림 채널로 통보한다.

5한 줄 요약

데몬이 자기 동작을 나타내는 수치를 /metrics로 내보내 시간 흐름으로 쌓고 조회하게 하는 것

8Docker Engine 관리08-05

데몬 로그·라이브 복원·IPv6

데몬 자체의 로그를 읽고 SIGUSR1 시그널로 스택 덤프를 뜨며, 데몬이 일시적으로 멈춰도 실행 중인 컨테이너를 계속 살려 두는 라이브 복원과 IPv6 네트워크 지원을 켜는 설정.

1문제 상황

데몬이 멈추거나 설정이 꼬였을 때 왜 멈췄는지는 systemd가 모아 둔 로그 파일을 직접 뒤져 알아내야 했습니다. CPU를 점유한 어떤 스레드가 어디서 멈춰 있는지 확인하려면 프로세스를 멈춰 스택 덤프를 뜰 수밖에 없었고, 그 순간 데몬이 응답하지 않는 시간이 생겼습니다. 또 데몬이 재시작되거나 설정 변경으로 잠시 멈출 때, 이미 실행 중인 컨테이너까지 함께 죽어 업무가 끊기는 일이 반복됐습니다. 사내망이 IPv6 주소를 쓰는 환경에서는 컨테이너에 IPv6 주소를 붙이지 못해 이중 스택 구성이 불가능했습니다.

2핵심 질문

데몬이 멈춘 상태의 원인을 신호만으로 확인하고, 그동안 컨테이너는 살려 두면서 IPv6 주소까지 붙일 수 있을까요?

3동작 예시

systemctl status docker는 데몬이 마지막으로 남긴 로그를 보여 주고, kill -SIGUSR1 $(pidof dockerd)를 한 번 보내면 데몬은 멈추지 않은 채 자기 스택 덤프를 로그에 찍습니다. 데몬이 정지 상태여도 컨테이너는 이미 만들어진 채로 계속 돌아가고, 데몬이 되살아나면 그 컨테이너의 정보를 다시 읽어 이어서 관리합니다. 데몬 설정에서 ipv6와 fixed-cidr-v6을 켜면 IPv6 주소를 가진 네트워크를 만들고, 컨테이너를 --network로 그 네트워크에 붙여 IPv4와 IPv6를 함께 받게 됩니다.

4동작 과정

  1. 데몬 로그 확인데몬이 남긴 메시지는 systemd의 journal이 보관한다. journalctl -u docker로 그 구간을 보고, -f를 붙이면 새로 쌓이는 줄을 따라가며 볼 수 있다.
  2. 진단과 신호 처리SIGUSR1은 Go 런타임이 각 스레드의 호출 스택을 로그에 남기게 하는 신호라 데몬을 멈추지 않는다. SIGUSR2를 주면 데몬은 systemd 소켓 단위 유닛으로 다시 구성된다. SIGHUP은 저장 드라이버를 포함한 데몬 구성 파일을 다시 읽고 반영한다.
  3. 라이브 복원과 IPv6데몬이 정지해도 컨테이너를 계속 띄워 두는 기능이 기본 켜짐으로 동작해, 데몬이 돌아오면 그 컨테이너를 그대로 다시 관리한다. daemon.json에 ipv6와 fixed-cidr-v6을 적어 재시작하면 IPv6 서브넷을 가진 사용자 정의 네트워크가 생기고, 거기에 붙은 컨테이너는 IPv6 주소를 받는다.

5한 줄 요약

데몬 자신이 남긴 로그와 신호로 원인을 확인하게 하고, 데몬이 잠시 멈춰도 컨테이너를 죽이지 않으며 IPv6 주소까지 발급하게 하는 것

컨텍스트와 리소스 정리

docker context로 여러 데몬(로컬·원격) 중 지금 쓸 대상을 골라 전환하고, docker prune으로 쓰지 않는 이미지·컨테이너·볼륨·빌드 캐시를 지워 디스크 공간을 비우는 것.

1문제 상황

여러 서버에 데몬이 올라가 있으면 같은 docker 명령을 어디로 보내는지 매번 -H로 주소와 인증서를 붙여 알려 줘야 했습니다. 대상이 바뀔 때마다 명령 전체를 다시 쓰다 보니 실수로 다른 서버에 명령을 보내는 일이 생겼고, 나중에 다시 같은 서버로 돌아오기 위해 주소를 매번 다시 찾아야 했습니다. 한편 오래 개발한 머신에는 더는 쓰지 않는 이미지와 정지된 컨테이너, 붙어 있지 않은 볼륨, 빌드 캐시가 그대로 쌓여 디스크가 부족해졌고 무엇이 얼마만큼 차지하는지 한 번에 볼 수도, 정리를 한 번에 할 수도 없었습니다.

2핵심 질문

지금 쓸 데몬을 이름으로 골라 가고, 쓰지 않는 자원을 골라서 지울 수 있을까요?

3동작 예시

docker context create prod --docker host=tcp://10.0.0.5:2376으로 만들어 둔 뒤 docker context use prod를 실행하면 이후 모든 docker 명령이 주소 지정 없이 그 데몬으로 나갑니다. 로컬로 돌아오려면 docker context use default만 치면 됩니다. 정리 쪽은 docker system df가 이미지·컨테이너·볼륨·빌드 캐시가 각각 얼마나 차지하는지 먼저 보여 주고, docker image prune은 어떤 컨테이너도 쓰지 않는 이미지만 지웁니다.

4동작 과정

  1. 컨텍스트 관리docker context create는 데몬의 접속 주소와 인증 정보를 이름 붙은 항목으로 저장한다. docker context ls로 목록을 보고 docker context use로 기본 대상을 갈아타면 모든 하위 명령이 그 대상을 따라가고, docker context rm으로 불필요한 항목을 지운다. 설정 파일은 직접 확인·수정할 때 쓰이며 DOCKER_HOST 환경 변수가 지정된 경우에는 그 값이 우선한다.
  2. 공간 점검이랑 선택 정리docker system df와 docker system df -v가 종류별 사용량과 어떤 항목이 잡아먹는지 세부를 보여 준다. container prune, image prune, volume prune, builder prune은 각 종류별로 쓰이지 않는 것만 지우고, system prune이 실행 중인 컨테이너와 네트워크를 제외한 나머지를 한 번에 정리한다.
  3. 전체 정리와 자동화-a를 붙이면 정지된 컨테이너가 붙어 있던 이미지와 빌드 캐시까지 포함한다. docker system prune -a --volumes는 쓰지 않는 볼륨까지 지우며, --filter로 조건을 좁힐 수 있고 --force로 확인 질문을 생략할 수 있다. 같은 명령을 힌트에 넣어 두면 docker 실행 시 자동으로 함께 돈다.

5한 줄 요약

쓸 데몬을 이름으로 골라 가고, 쓰이지 않는 자원은 종류별로 골라 지워 머신의 디스크를 되찾는 것

루트리스 모드

데몬과 컨테이너를 일반 사용자 권한으로 실행해 호스트 root 권한 없이 컨테이너를 다루는 실행 방식

1문제 상황

일반적인 Docker는 데몬이 호스트의 root 권한으로 실행되고, 그 권한을 물려받아 컨테이너를 만들고 실행합니다. 호스트의 root 권한이 하나의 데몬에 몰려 있으면 데몬이 가진 취약점 하나가 곧 호스트 전체 권한 탈취로 이어집니다. root 권한이 없는 사용자만 사용할 수 있는 서버에서는 애초에 데몬을 띄울 수 없어 컨테이너를 못 씁니다. 그래서 사용자 그룹에 docker 그룹을 추가해 root 권한을 나눠주는 방식이 쓰였는데, 그 그룹에 들어가는 순간 해당 사용자도 호스트 root와 같은 힘을 갖게 되는 문제가 함께 생겼습니다.

2핵심 질문

호스트 root 권한 없이 데몬과 컨테이너를 일반 사용자 권한으로만 실행할 수 있을까요?

3동작 예시

dockerd-rootless-setuptool.sh install을 일반 사용자 계정에서 실행하면 해당 사용자에게 uid와 gid 범위가 부여되고, dockerd-rootless.sh가 사용자 권한으로 데몬을 띄웁니다. 데몬은 일반 사용자의 프로세스로 동작하고, rootlesskit(사용자 권한 안에서 네트워크 네임스페이스를 만들어 주는 도구) 경유로 네트워크도 구성합니다. 컨테이너 안의 root는 이 uid 범위 안에 묶여 호스트 root 권한에 닿지 못합니다.

4동작 과정

  1. 데몬 기동dockerd-rootless-setuptool.sh install이 서브_uid·서브_gid를 등록해 컨테이너가 사용할 uid 범위를 확보하고 dockerd-rootless.sh로 사용자 세션 안에서 데몬을 시작한다. 세션이 끝나면 데몬도 함께 사라지므로 systemd 사용자 서비스로 올려 유지하는 방식을 쓴다.
  2. 권한 격리rootlesskit이 사용자 권한으로 네트워크 네임스페이스를 만들고 데몬이 그 안에서 컨테이너를 띄운다. 컨테이너 안의 root는 할당된 하위 uid 범위에서 움직여 호스트 root 권한을 얻지 못한다.
  3. 기능 제약과 사양기본으로 overlay2, fuse-overlayfs 같은 저장 드라이버를 쓰며 cgroup v2와 systemd를 함께 쓸 것을 권한다. --net=host(호스트와 같은 네트워크를 그대로 씀)와 --privileged(컨테이너에 거의 모든 권한을 부여) 같은 일부 옵션은 사용할 수 없다.

5한 줄 요약

데몬과 컨테이너를 일반 사용자 권한 아래에서 띄워 호스트 root 권한이 필요 없도록 만드는 것

9보안09-02

사용자 네임스페이스 리맵

컨테이너 안의 UID/GID를 호스트의 별도 UID 범위로 치환해 컨테이너의 root가 호스트 root 권한을 얻지 못하게 하는 데몬 설정

1문제 상황

컨테이너 안에서 프로세스는 기본적으로 호스트의 사용자 ID를 그대로 씁니다. 컨테이너 안의 root는 UID 0이고, 이 번호는 호스트에서도 root를 뜻하기 때문입니다. 컨테이너에서 실행된 코드가 버그나 공격으로 탈출하면 호스트 파일系统的 root 권한을 그대로 얻습니다. 사용자 네임스페이스 리맵이 없으면 컨테이너 경계가 사용자 권한 경계로 제대로 작동하지 않습니다.

2핵심 질문

컨테이너 안의 root가 호스트의 root 권한을 가질 수 없게 하면서, 컨테이너는 여전히 root로 동작할 수 있게 만들 수 있는가?

3동작 예시

호스트에서 100000~165535 범위의 UID를 컨테이너 전용으로 미리 만들어 두고, dockerd가 userns-remap=default 설정을 켜면 컨테이너 안의 UID 0이 호스트의 UID 100000으로 매핑됩니다. 컨테이너 안에서는 여전히 root로 동작하지만, 호스트 입장에서 이 프로세스는 일반 사용자입니다. 호스트의 실제 root(UID 0)는 컨테이너에 나타나지 않으므로, 컨테이너 탈출 시 얻는 권한도 일반 사용자 수준에서 끝납니다.

4동작 과정

  1. 서브 UID/GID 할당데몬이 리맵에 쓸 별도 범위의 연속된 UID/GID를 호스트에 생성하고, 서브 UID·서브 GID 할당 모듈(subuid/subgid, 프로세스가 다른 UID 범위를 빌릴 수 있게 하는 커널 모듈)을 활성화합니다.
  2. 데몬 기동 시 리맵 적용/etc/docker/daemon.json에 "userns-remap": "default"를 넣고 데몬을 재시작하면, 이후 생성되는 모든 컨테이너의 UID/GID에 리맵 규칙이 자동으로 적용됩니다.
  3. 파일 소유권 자동 치환데몬이 이미지 안의 파일 소유권까지 함께 바꾸기 때문에, 컨테이너 안에서는 파일이 여전히 root 소유로 보이고 호스트의 디렉터리 소유권은 손상되지 않습니다.

5한 줄 요약

Seccomp·AppArmor 프로파일

컨테이너에서 허용할 시스템 콜과 파일 접근 경로를 미리 정한 규칙(프로파일)으로 제한해 보안 위험을 줄이는 두 가지 방어 수단

1문제 상황

컨테이너는 커널을 공유하므로 컨테이너 안의 프로세스는 결국 호스트 커널의 시스템 콜을 직접 호출합니다. 이 때문에 컨테이너를 격리라고만 봐서는 안 되며, 어떤 코드가 어떤 시스템 콜을 부르는지 제한이 필요합니다. 기본 방어 수단 없이 두면 컨테이너에서 할 수 있는 시스템 콜 범위가 호스트와 사실상 같아져, 취약점 공격의 영향이 컨테이너 밖까지 나아갈 수 있습니다.

2핵심 질문

컨테이너 안의 프로세스가 호출할 수 있는 시스템 콜과 접근할 수 있는 파일 경로를 어떻게 제한해 공격의 영향 범위를 좁힐 수 있는가?

3동작 예시

기본 seccomp 프로파일은 대부분의 일반 程序이 쓰는 약 240개의 시스템 콜만 허용하고 나머지 약 2,000개는 차단합니다. 컨테이너 안의 코드가 시스템 콜을 요청하면 커널이 seccomp 규칙을 먼저 확인해 허용 목록에 없는 호출이면 즉시 실패시킵니다. AppArmor는 같은 방식으로 허용된 경로 밖의 파일 열기를 거부합니다. Docker는 두 가지 수단을 모두 켜 두어 서로 다른 계층에서 동시에 제한합니다.

4동작 과정

  1. seccomp 프로파일 적용데몬이 seccomp 필터(허용할 시스템 콜과 인자를 커널이 직접 판정하는 규칙)를 컨테이너 프로세스에 붙이고, 커널이 호출 단계마다 검사합니다.
  2. AppArmor 프로파일 적용데몬이 경로 기반 접근 제어 규칙(AppArmor가 파일 경로와 권한별로 접근을 막는 규칙)을 프로세스에 연결해 파일 읽기·쓰기 범위를 정합니다.

1문제 상황

Docker 데몬은 호스트에 있는 유닉스 소켓 파일 docker.sock를 통해 명령을 받습니다. 이 소켓에 접근할 수 있는 프로세스는 API로 원하는 컨테이너를 만들고, 호스트의 디렉터리를 마운트해 컨테이너 안으로 끌어올 수 있습니다. 소켓 접근 권한은 곧 호스트 root 권한과 같으므로, 소켓을 열어 둔 채 두면 컨테이너 격리를 우회하는 통로가 됩니다.

2핵심 질문

3동작 예시

어떤 서버가 이미 호스트의 루트 권한을 가지고 있다면, 그 서버는 TLS로 데몬에 연결하고 원격 클라이언트를 모두 제거해 단일 진입점만 남길 수 있습니다. docker group에 속한 사용자도 소켓에 닿을 수 있기 때문에, 서버를 오염시킨 사용자가 그 그룹에 있으면 사실상 root가 됩니다. Docker는 이런 경우를 감지해 경고를 내고, 소켓 권한은 출처를 아는 경로로만 연두라고 안내합니다.

4동작 과정

  1. 소켓 접근 경로 축소소켓을 건드릴 수 있는 주체를 강제해제하고, TLS로 안전하게 연결하거나(원격 클라이언트 제거) docker 그룹 권한을 통해 엄격히 제한된 경로로만 열어 둡니다.
  2. 로컬 접근 제어로컬에서 소켓을 쓸 경우 docker group에 속한 사용자만 접근할 수 있게 권한을 설정하고, 그 그룹에 어떤 사용자가 있는지 수시로 확인합니다.
  3. 노출 차단소켓은 TCP 포트로 기본 노출되지 않으며, 디렉터리 마운트·권한 상승 옵션이 가능한 엔진 설정을 통해 우회 경로를 막습니다.

3동작 예시

4동작 과정

  3. 서명 검증 활성화Content Trust를 켜면 이미지를 pull할 때 신뢰할组织和 개인 키 목록을 확인하고, 서명이 없거나 신뢰 목록에 없으면 배포를 중단합니다.

3동작 예시

로컬에서 만든 이미지에 버전 표시인 태그를 붙여 Docker Hub 저장소로 푸시하고, 그 태그를 정리하고 지워 버전별로 이미지를 관리하는 작업.

2핵심 질문

3동작 예시

로컬 이미지 목록에 있는 webapp에 latest와 1.2 태그를 만들어 두고, docker push <계정>/webapp:1.2로 올리면 저장소에 그 태그가 생깁니다. 같은 이름으로 다시 푸시하면 해당 태그가 새 이미지로 덮여가고, 원본 digest(푸시마다 계산되는 해시값)로는 이전 상태가 남습니다. Docker Hub 화면에서 태그별 push 시각과 digest를 볼 수 있어, 현재 릴리스가 어느 이미지인지 확인합니다.

4동작 과정

  1. 태그 지정docker tag로 로컬 이미지에 버전용 태그와 latest(가장 최근 이라는 뜻의 기본 태그)를 붙이고, 이미지 목록에서 태그가 제대로 붙었는지 확인합니다.
  2. 저장소로 푸시docker login으로 로그인한 계정 이름을 이미지 이름 앞에 붙여 docker push를 실행하면 태그별로 이미지가 저장소에 올라갑니다.
  3. 태그 정리더 이상 쓰지 않는 태그는 저장소 화면에서 삭제하고, 실제 릴리스는 latest를 가리키게 두어 어떤 태그가 현재 버전인지 모호하지 않게 관리합니다.

신뢰할 수 있는 콘텐츠와 취약점 스캔

Docker Hub이 공식 이미지와 같이 신뢰할 수 있다고 표시한 콘텐츠를 구분해 제공하고, 저장된 이미지 안의 알려진 취약점(CVE)을 스캔해 보여 주는 기능.

1문제 상황

Docker Hub에는出自이 불분명한 이미지가 대량으로 올라와 있어, 어느 것이 누가 만든 것인지와 안전하게 꺼내 쓸 수 있는지 알기 어렵다. 또한 이미지를 그대로 올리면 내부에 구버전 라이브러리 같은 알려진 취약점이 함께 배포된다. 이를 미리 알기 위해 별도 도구를 붙여 스캔해야 하지만, 모든 이미지에 같은 절차를 반복 적용하는 것도 부담이다.

2핵심 질문

3동작 예시

docker pull nginx 명령 하나로 이미지가 내려오는데, Docker Hub 공식 라이브러리에 있는 이미지는 공식 콘텐츠로 표시되고, 개인 계정이 올린 이미지는 출처가 다른 콘텐츠로 구분된다. 여기에 Docker Scout 같은 스캐너를 연결해 두면 각 이미지의 CVE 목록과严重도, 수정 버전이 바로 조회된다.

4동작 과정

  1. 콘텐츠 구분Docker Hub이 공식 이미지와 서드파티·개인 이미지를 서로 다른 콘텐츠 범주로 분류해 표시하고, 공식 콘텐츠에는 별도 표식을 붙여 사용자가 출처를 한눈에 판단하게 한다.
  2. 취약점 스캔이미지의 레이어 단위 패키지 목록에서 알려진 CVE 데이터베이스와 대조해, 어떤 패키지의 어느 버전이 어떤 취약점의 영향을 받는지 찾아낸다.
  3. 결과 제공스캔 결과를 심각도 등급과 수정 가능한 버전 정보로 정리해 보여 주고, 기준 등급을 넘는 취약점이 있으면 빌드 단계에서 실행을 막는 규칙으로 쓸 수 있다.

Swarm 핵심 개념

Docker Engine에 내장된 오케스트레이션 모드로, 여러 Docker 호스트를 노드로 묶고 관리자와 워커 역할을 나눠 컨테이너를 서비스 단위로 자동 배치하고 장애 시 되살리는 기능

1문제 상황

여러 대의 Docker 호스트에서 컨테이너를 하나씩 손으로 실행하면, 어떤 호스트에 무엇이 올라가 있는지 머릿속으로 관리해야 한다. 그중 한 대가 꺼졌을 때 그 호스트에서 돌던 컨테이너를 다른 곳으로 옮기는 과정도 전부 수작업이다. 컨테이너 수만 늘어나면 배치와 장애 대응에 드는 비용이 그대로 늘어난다.

2핵심 질문

여러 Docker 호스트를 하나로 묶어, 원하는 수의 컨테이너를 자동으로 배치하고 장애가 나면 자동으로 되살릴 수 있을까?

3동작 예시

같은 application's 컨테이너 3개를 스웜에 올리면 스웜은 세 대의 워커 노드에 하나씩 배치한다. 한 워커 노드가 전원이 꺼지면 그 노드에 있던 컨테이너는 사라진 자리가 채워질 때까지 다른 노드로 옮겨져 다시 실행되고, 사용자는 그것을 신경 쓰지 않는다.

4동작 과정

  1. 노드와 역할스웜에 속한 Docker 호스트를 노드라 하고, 서비스 정의와 노드를 관리하는 매니저 노드와 실제 컨테이너를 실행하는 워커 노드로 역할을 나눈다.
  2. 서비스와 태스크실행할 이미지와 replica 수를 묶어 서비스로 정의하면, 스웜이 그 수만큼 태스크를 만들어 각기 다른 노드에 분산 배치하고 상태를 계속 감시한다.
  3. 자동 복구노드가 끊기거나 태스크 컨테이너가 죽으면 스웜이 같은 서비스의 태스크를 살아 있는 다른 노드로 옮겨 다시 실행해 요구한 수를 유지한다.

11Swarm 모드11-02

Swarm 생성과 노드 참여

swarm init으로 스원을 만든 뒤 발급된 참여 토큰으로 다른 Docker 호스트를 관리자 노드나 워커 노드로 붙이는 과정

1문제 상황

호스트를 여러 대 준비했다고 해서 서로를 자동으로 알아보고 작업 분담을 하지는 않는다. 각 호스트에 같은 설정을 손으로 복사해 넣고, 장애가 났을 때 어느 호스트가 남아 있는지도 직접 파악해야 한다. 무엇보다 어떤 호스트가 이 묶음에 속하는지 기록해 둘 방법이 없다.

2핵심 질문

스웜을 딱 한 번 만들어 중앙 관리 지점을 만들고, 다른 호스트는 발급받은 토큰만으로 그 안에 편입시킬 수 있을까?

3동작 예시

첫 호스트에서 docker swarm init --advertise-addr=<IP> 를 실행하면 그 호스트가 매니저 노드가 되고, 콘솔에 docker swarm join-token worker 와 manager 두 개의 긴 토큰 문자열이 출력된다. 다른 호스트에서는 이 토큰과 매니저 IP를 조합한 docker swarm join 명령 한 줄로 워커 노드가 되고, 나중에 토큰을 회수하면 추가 참여가 막힌다.

4동작 과정

  1. 스원 생성docker swarm init 으로 한 호스트를 매니저 노드로 지정하면 스원 ID가 발급되고 Raft 로그를 저장할 저장소와 내부 통신용 네트워크가 만들어진다.
  2. 토큰 발급매니저가 docker swarm join-token 으로 워커용과 매니저용 참여 토큰을 만들며, 이 토큰이 스원에 들어갈 수 있는 권리 증명 역할을 한다.
  3. 노드 참여각 호스트에서 docker swarm join --token <토큰> <매니저 주소> 를 실행하면 해당 호스트가 지정된 역할의 노드로 등록되고, 상태 조회 명령에 함께 표시된다.

11Swarm 모드11-03

서비스 배포와 관리

docker service create로 필요한 태스크 수를 선언하면 스웜이 노드에 컨테이너를 알아서 배치하고, 스케일과 롤링 업데이트와 롤백으로 서비스 상태를 관리하는 것

1문제 상황

컨테이너를 직접 실행하는 방식은 실행할 대상이 지정된 호스트 하나뿐이라, 같은 컨테이너를 여러 곳에 띄우려면 같은 명령을 여러 번 반복해야 한다. 수동으로 띄운 컨테이너는 재시작 정책이 유한 횟수로 끝나고, 변경 사항을 되돌리려면 이전 설정과 이미지를 다시 찾아야 한다. 실행 상태가 선언된 것이 아니라 우연히 쌓인 결과물이라 관리가 되지 않는다.

2핵심 질문

원하는 태스크 수와 이미지 버전을 선언만 하면 스웜이 이를 유지하고, 언제든 스케일·업데이트·롤백으로 되돌릴 수 있을까?

3동작 예시

docker service create --replicas 5 --name web nginx:1.25 를 한 번 실행하면 nginx 1.25 컨테이너 5개가 여러 노드에 나뉘어 배치된다. replicas를 10으로 바꾸면 5개가 추가되고, --update-parallelism 1 을 붙여 새 버전으로 바꾸면 한 대씩 교체되며, --rollback previous 를 주면 바로 이전 버전으로 되돌아간다.

4동작 과정

  1. 서비스 생성docker service create 에 이미지, replica(몇 개를 유지할지), 네트워크, 포트를 지정하면 스원이 replica 수만큼 태스크를 노드에 배치하고 감시를 시작한다.
  2. 스케일과 롤링 업데이트replica 값을 바꾸면 증감된 수만큼 태스크를 추가·제거하고, 이미지 태그를 바꾸면 --update-parallelism 만큼 한 번에 교체해 구버전과 신버전이 섞인 채로 서비스가 유지된다.
  3. 상태 확인과 롤백서비스 단위 로그와 상태, replica와 현재 버전을 조회해 배포 결과를 확인하고, --rollback 으로 이전 이미지 사양으로 되돌려 실패한 업데이트를 되돌린다.

5한 줄 요약

replica 수와 이미지 사양을 선언해 스웜이 태스크를 자동 배치하게 하고 스케일·롤링 업데이트·롤백으로 관리하는 것

1문제 상황

호스트마다 브리지 네트워크가 따로 만들어져 있어, 서로 다른 호스트에 실행된 컨테이너끼리는 직접 통신할 수 없다. 각 컨테이너의 IP는 재시작마다 바뀌고, 그 주소로 프록시에 연결 정보를 등록하는 일도 반복해서 해야 한다. 무엇보다 같은 서비스의 컨테이너가 여러 대 있는데 어느 한 대가 살아 있는지 확인하려면 개별 컨테이너를 다 뒤져야 한다.

2핵심 질문

노드를 넘어 서로 다른 컨테이너를 하나의 네트워크로 연결하고, 외부 요청을 살아 있는 컨테이너에만 자동으로 전달할 수 있을까?

3동작 예시

docker network create --driver overlay mynet 으로 만든 네트워크에 서비스 두 개를 붙이면, 서로 다른 워커 노드의 컨테이너끼리 컨테이너 이름으로 통신이 된다. 외부에서 8080 포트로 들어온 요청은 스웜이 살아 있는 web 태스크 중 하나로 넘기며, 그 태스크가 노드를 옮겨도 별도 설정 없이 그대로 동작한다.

4동작 과정

  1. 오버레이 네트워크 생성--driver overlay 로 만든 네트워크는 각 노드 위에 가상의二层 레이어를 얹어, 노드를 가로질러 같은 네트워크에 속한 컨테이너끼리 직접 통신하게 한다.
  2. 서비스 할당과 통신docker service create --network mynet 으로 서비스에 네트워크를 지정하면, 그 서비스의 모든 태스크가 어느 노드에서 실행되든 같은 네트워크에 연결되어 컨테이너 이름으로 서로 찾을 수 있다.
  3. 라우팅 메시포트를 -p 8080:80 형태로 발행하면 노드에 라우팅 메시가 생성되고, 외부에서 들어온 요청이 VIP 로 전달된 뒤 스웜이 그 안의 살아 있는 태스크로 연결한다.

11Swarm 모드11-05

스웜 보안과 설정

노드 간 통신과 저장 데이터를 PKI 기반 TLS로 암호화하고, 매니저의 Raft 암호화 키를 잠가 스원 설정을 보호하는 보안 수단

1문제 상황

스웜은 여러 노드 사이에서 서비스 정보를 주고받는 통신이 계속 이어지고, 그 과정에서 TLS로 보호된 연결을 맺으려면 인증서와 암호 키가 필요하다. 이 값들을 자동으로 만들지 않으면 매번 수동으로 배포해야 하고, 한 번 쓰고 나면 다시 꺼낼 수 없다. 스원이 가진 매니저 목록과 노드 토큰처럼 스웜 자체를 조작할 수 있는 정보는 평문으로 남으면 안 된다.

2핵심 질문

노드 간 통신을 암호화하고 스원 설정을 바꾸는 키를 반환할 수 없게 만들어, 스원을 탈취하거나 조작하기 어렵게 할 수 있을까?

3동작 예시

docker swarm init 시 스웜은 매니저 노드에 이미 생성된 인증서와 키를 그대로 사용한다. docker swarm update --rotate-manager-token 을 한 번 실행하면 새 참여 토큰이 발급되고 예전 토큰은 더 이상 스원에 편입되지 않는다. CA 인증서를 다른 노드에 복사해 배치하면 그 노드도 매니저로 승격될 수 있는 기반이 갖춰진다.

4동작 과정

  1. PKI 기반 통신 보호스웜이 발급한 CA 인증서와 노드별 인증서·키로 노드 간 통신을 TLS로 암호화해, 스원 네트워크에 노출된 다른 노드가 내부 트래픽을 엿보거나 위조하지 못하게 한다.
  2. 노드 인증각 노드는 자신에게 발급된 키로 매니저에 신원을 증명하고 조인만 허용된 인증서 목록에 없는 노드는 스웜에 붙지 못하게 만들어 허위 노드의 진입을 막는다.
  3. Raft 키 잠금과 교체매니저들이 스원 설정을 주고받는 Raft 로그의 암호화 키를 기본값 그대로 두지 않고 docker swarm update --rotate-manager-token 등으로 교체해 이전 키로 들어온 요청을 무효화한다.

5한 줄 요약

노드 간 통신과 저장 데이터를 PKI 기반 TLS로 암호화하고 매니저의 Raft 암호화 키를 교체해 스웜 설정을 보호하는 것

Docker Scout 소개와 이미지 분석

Docker Scout는 이미지 안의 패키지 목록과 알려진 취약점(CVE)을 찾아나열해 이미지를 평가하는 Docker의 공급망 보안 도구다.

1문제 상황

컨테이너 이미지를 배포하기 전에는 그 안에 무엇이 들어 있는지 확인해야 한다. 이미지는 여러 단계의 빌드로 만들어지므로, 그 안에는 직접 설치하지 않은 라이브러리가 수백 개씩 들어가고 버전도 제각각이다.

기존에는 이미지를 실행해 Shell로 들어가 직접 패키지 목록을 꺼내 보고, 그 버전이 알려진 취약점(CVE)에 걸리는지 외부 데이터를 하나씩 대조해야 했다. 이미지 하나에 이런 확인이 수십 분 걸리고, 같은 라이브러리가 다른 이미지에 들어 있는지도 매번 다시 확인해야 한다.

2핵심 질문

이미지 안의 소프트웨어와 그 버전을 자동으로 전부 찾아, 알려진 취약점과 비교한 결과를 한 번에 보여 줄 수 있는가?

3동작 예시

Python 웹 앱을 베이스 이미지에 얹어 만든 최종 이미지 하나를 Docker Scout로 분석하면, 그 이미지에서 실제로 사용 중인 openssl 3.0.11 같은 라이브러리와 버전이 목록으로 나온다. Scout는 이 목록을 미리 준비된 취약점 데이터베이스와 대조해 해당 버전이 CVE-2024-xxxx에 해당하는지와 그 취약점의 심각도(CVSS 점수), 고칠 수 있는 버전이 무엇인지를 붙여 준다. 사람이 파일을 하나씩 열어 볼 필요가 없다.

4동작 과정

  1. 이미지 참조 전달이미지 이름과 태그, 또는 레지스트리에 있는 이미지 참조를 Scout에 넘기면 그 대상을 분석 대상으로 잡는다. 레지스트리에 올라간 이미지라면 저장소 전체에서 태그를 골라 여러 이미지를 한 번에 넣을 수도 있다.
  2. SBOM 기반 구성 목록 작성이미지가 빌드될 때 기록해 둔 SBOM(소프트웨어 bill of materials, 이미지 안 들어 있는 소프트웨어와 버전 목록)을 읽어 패키지 이름·버전·라이선스를 전부 뽑아 낸다. SBOM이 없으면 Scout가 직접 이미지 계층을 훑어 목록을 만든다.
  3. 취약점 매칭뽑은 목록을 취약점 데이터베이스와 버전 단위로 대조해 해당하는 CVE, 심각도 등급, 수정 버전을 붙인다. 매칭 결과는 이미지 태그별로 비교해 "이 태그는 저 태그보다 CVE 가 하나 많다"처럼 차이도 함께 볼 수 있다.
  4. 보고서 확인결과를 패키지별·심각도별로 정리한 목록으로 내보내거나, CI 파이프라인 안에서 기준 이상의 취약점이 있으면 빌드나 배포를 중단시키는 판정으로 쓴다.

5한 줄 요약

이미지 안의 모든 패키지와 버전을 자동으로 추출해 알려진 취약점과 대조하고, 그 결과를 심각도별로 한 번에 보여 주는 것

공식 문서https://docs.docker.com/scout/explore/analysis/

SBOM과 출처 증명

SBOM은 이미지에 담긴 소프트웨어와 버전의 목록이고, 출처 증명(provenance attestation)은 그 이미지가 어디서 어떤 과정으로 만들어졌는지를 기록한 메타데이터다.

1문제 상황

빌드 시스템이 관리하는 라이브러리를 직접 추가한 경우는 드물다. 실제 의존 관계는 빌드 도구가 결정하고, 그 과정에서 수십 개의 간접 의존성이 이미지에 실리게 된다. 무엇이 들어 있는지 목록으로 관리하지 않으면, 나중에 특정 취약점이 발표되었을 때 해당 라이브러리를 쓰고 있는 이미지인지 전체를 뒤져야 한다.

또한 이미지 파일만으로는 어디서 만들어졌는지 알 수 없다. 같은 태그에 다른 사람이 올린 이미지가 있어도 그_difference는 파일 내용으로 바로 드러나지 않는다. 조직이 정한 빌드 파이프라인을 거쳤는지, 승인된 소스에서 나온 코드만 사용했는지 확인하려면 별도의 절차가 필요했다.

2핵심 질문

이미지에 무엇이 들어 있는지와 이 이미지가 어디서 어떤 과정으로 만들어졌는지를, 이미지 파일과 분리해 검증 가능한 형태로 남길 수 있는가?

3동작 예시

빌드 명령에 --sbom=true --provenance=mode=max 를 붙여 이미지를 만들면, 이미지 옆에 SBOM(소프트웨어 bill of materials)과 출처 증명(provenance attestation) 두 종류의 데이터가 생긴다. SBOM에는 libssl 3.0.11 같은 패키지 목록이, 출처 증명에는 "빌드 워크플로 이름, 사용한 빌더 버전, 참조한 Git 커밋 해시, 서명된 주체" 같은 기록이 담긴다. 나중에 그 이미지를 pulled 하는 쪽은 이미지 파일 자체를 수정하지 않고도 이 데이터만 따로 받아 위조 여부와 구성 내역을 확인할 수 있다.

4동작 과정

  1. 빌드 시점 기록 생성빌드가 끝나면서 SBOM과 출처 증명을 생성해 이미지에 부착한다. SBOM은 컨테이너 이미지 표준 형식(SPDX, CycloneDX 등)으로 직렬화하고, 출처 증명은 OCI 아티팩트 형식의 서명 가능한 문서로 만든다. 둘 다 이미지의 태그와 밀폐(multi-platform)별로 구분되어 저장된다.
  2. 참조 형태로 연결이미지를 레지스트리에 올리면 이 데이터도 함께 올라가며, 이미지 참조 뒤에 sbom 같은 참조를 덧붙이는 방식으로 데이터만 따로 가져올 수 있다. 이미지 레이어를 다시 열어 확인할 필요가 없다.
  3. 서명과 검증출처 증명에는 빌드를 실행한 주체의 서명 키 정보가 들어가고, 서명 이력이 함께 남는다. 나중에 CI나 정책 검사 단계에서 서명 유효성과 빌드 워크플로 이름을 확인해, 승인된 경로에서 나온 이미지만 통과시킬 수 있다.
  4. 취약점 데이터와 결합이 증명된 목록을 Scout 같은 분석 도구에 넘기면, 이미지의 구성 내역과 출처를 함께 근거로 삼아 위험을 판단할 수 있다. 그래서 "SBOM 없이 통과한 이미지"를 구분하는 것도 가능해진다.

5한 줄 요약

이미지의 소프트웨어 목록과 생성 과정을 빌드 시점에 서명 가능한 별도 데이터로 남겨, 이미지 파일을 열어보지 않고도 구성과 출처를 검증하게 하는 것

빌드 정책과 체크

빌드 정책은 빌드를 진행하기 전에 Dockerfile과 빌드 입력을 규칙으로 검사해 조건에 어긋나면 빌드를 막고 알려 주는 검증 규칙이며, 빌드 체크는 이 규칙들의 모음이다.

1문제 상황

보안 점검을 위해 만든 Dockerfile 규칙은 사람이 읽는 문서로만 남는 경우가 많다. "베이스 이미지는 지정된 레지스트리에서만 가져온다", "apt-get 으로 설치한 뒤 캐시 디렉터리를 지운다" 같은 조건을 팀원들이 합의했지만, 실제 빌드 파이프라인에서는 아무도 자동으로 검사하지 않는다.

결과적으로 규칙 위반은 코드 리뷰나 심지어 배포 이후에야 발견된다. 또한 규칙이分散되어 있어 어떤 빌드가 어떤 조건을 통과했는지 한눈에 파악하기 어렵고, 예외를 허용할 때도 이유를 남기는 절차가 없다.

2핵심 질문

빌드를 시작하기 전에 Dockerfile과 빌드 입력을 규칙으로 검사해, 조건에 어긋나면 빌드를 막고 그 이유를 알려 줄 수 있는가?

3동작 예시

Dockerfile 에서 ADD https://example.com/app.tar.gz /app 대신 원격 URL을 그대로 받는 방식을 금지하고 싶다고 하자. 빌드 정책에 "원격 소스 URL 은 허용하지 않는다"라는 규칙(check)을 만들어 두면, 그 Dockerfile로 빌드를 시작하는 순간 규칙 검사가 먼저 돌고 위반이므로 빌드가 실행되지 않은 채 위반한 행과 규칙 이름이 출력된다. 규칙을 통과한 빌드에는 통과 표시가 붙어 나중에 다시 확인할 수 있다.

4동작 과정

  1. 정책(check) 정의와 연결규칙을 문서로 만들고 빌드 파이프라인의 어느 단계에서 검사할지 지정한다. CI 안에서 매 빌드마다 돌리거나, 사내 레지스트리에 push 하는 시점에만 돌리도록 조건을 걸 수 있다. 규칙이 하나도 없는 빌드는 별도 설정으로 통과시킬 수 있다.
  2. 빌드 전 정적 검사빌드를 실행하기 전에 Dockerfile 본문과 빌드 인자, 빌드 컨텍스트를 파싱해 규칙에 대조한다. 텍스트 패턴 검사부터 컨텍스트에 포함된 파일 내용 확인, 외부 소스 참조 차단, 지정된 베이스 이미지 요구 같은 종류가 있고, 필요한 도구(예: checkov, conftest)를 빌드 단계에서 직접 실행하는 방식도 쓴다.
  3. 위반 시 차단과 보고규칙을 하나라도 어기면 빌드를 중단하고, 위반한 규칙 ID와 해당 Dockerfile 라인을 함께 출력한다. 팀이 정한 예외 목록에 들어 있는 규칙은 경고만 남기고 통과시킬 수 있으며, 그 예외는 정책 파일에 명시적으로 적어야 한다.
  4. 결과 기록과 재확인통과와 위반 결과를 빌드 로그와 정책 리포트에 남겨 두고, 특정 빌드가 어떤 규칙을 통과했는지 나중에 조회한다. 규칙이 추가되면 이후 빌드에 자동 적용되어 검사 기준이 코드에 고정된다.

5한 줄 요약

빌드 전에 Dockerfile과 빌드 입력을 정해진 규칙으로 자동 검사해, 어긋나면 빌드 자체를 막고 위반 지점을 알려 주는 것

Docker Hardened Images

Docker Hardened Images는 불필요한 요소를 걷어낸 최소 구성, 비root 실행, 서명된 증명서 같은 보안 기본값을 넣어 Docker 가 직접 관리하는 베이스 이미지다.

1문제 상황

팀이 직접 만든 베이스 이미지는 보안 검토에 시간이 걸린다. 불필요한 셸, 패키지 매니저, 개발용 도구가 그대로 남아 있고, 기본 실행 사용자가 root라 컨테이너 하나가 뚫리면 그 안의 모든 권한이 노출된다. 무엇이 최소한으로 필요한지 판단하려면 보안 전문 지식이 필요하다.

또한 이런 기준을 이미지마다 수동으로 맞추다 보면 팀마다 편차가 생긴다. 업데이트 시점이기도 다르므로, 오래된 상태로 방치된 이미지가 그대로 배포되기도 한다.

2핵심 질문

최소 구성, 비root 실행, 서명된 증명서 같은 보안 기본값이 이미 적용된 베이스 이미지를, 같은 조직의 다른 이미지가 참조할 수 있게 제공할 수 있는가?

3동작 예시

dhi/python:3.12 처럼 Docker 가 관리하는 Hardened Images 태그를 FROM 으로 지정하면, 그 위에 패키지를 설치한 이미지는 기본 실행 사용자가 root 가 아니고 설치 도구나 셸 같은 불필요한 요소가 걷어내진 구성을 그대로 물려받는다. 이미지에는 이 구성이 어떤 검증 절차를 거쳐 만들어졌는지를 담은 증명서(attestation)가 서명되어 붙어 있어서, 이 이미지를 쓴 빌드가 어떤 기준을 통과했는지 확인할 수 있다. 업데이트가 올라오면 태그를 다시 당겨 받아 새 상태로 전환된다.

4동작 과정

  1. 최소 구성 설계베이스 이미지에서 실제로 실행에 필요한 파일과 패키지만 남기고, 셸이나 패키지 매니저 같은 공격에 쓰이기 쉬운 요소를 제거한다. 런타임에 필요한 라이브러리만 포함해 크기도 작게 유지한다.
  2. 비root 실행 기본 적용기본 실행 사용자와 파일 권한을 미리 낮춰 두고, 작업 디렉터리 소유권도 해당 사용자에게 맞춘다. 그래야 컨테이너 안의 프로세스가 루트 권한을 갖지 않아, 컨테이너 탈출을 노리는 공격의 성공 확률이 낮아진다.
  3. 증명서 서명 첨부이미지가 어떤 기준을 만족했는지를 기록한 증명서를 서명해 이미지 옆에 붙인다. 사용자는 이 서명을 확인해 이미지가 검증된 경로를 거쳤는지 판단하고, 정책 검사에서 요구하는 기준으로 삼을 수 있다.
  4. 지속 업데이트와 참조Docker 가 패치와 마이너 버전 변경을 직접 반영해 다시 배포한다. 사용자는 자신의 Dockerfile 의 베이스 이미지 태그를 이 이미지로 지정하고定期적으로 다시 가져와 업데이트 간격을 관리한다.

5한 줄 요약

최소 구성과 비root 실행 같은 보안 기본값을 넣어 Docker 가 직접 관리하고 업데이트까지 책임지는 베이스 이미지를 제공하는 것
