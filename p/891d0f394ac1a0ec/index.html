1컨테이너와 Docker 플랫폼의 구조이미지·컨테이너·레지스트리·데몬이라는 대상을 먼저 알아야 뒤의 모든 명령과 파일 형식이 '무엇을 조작하는지' 이해된다.52설치와 CLI 첫걸음실습 환경이 없으면 이후 모든 명령을 확인할 수 없다. 플랫폼별 설치와 CLI 문법을 여기서 끝낸다.43컨테이너 실행하고 다루기이미지를 만들기 전에 '컨테이너를 실행해 본 경험'이 있어야 Dockerfile 의 각 지시어가 무엇을 정하는지 감이 온다.64Dockerfile 로 이미지 만들기실행할 이미지를 스스로 만들 수 있어야 그다음의 빌드 최적화·배포·Compose 가 의미를 갖는다.95Buildx 와 BuildKit 로 빌드 다루기Dockerfile 을 쓸 줄 알게 된 다음에야 '어디서 어떻게 빌드하고 무엇을 내보낼지'를 고를 수 있다.76데이터 보존컨테이너가 사라져도 남아야 하는 것을 다룬다. 컨테이너 실행을 아는 상태에서 배워야 '왜 필요한가'가 성립한다.47네트워킹컨테이너 하나를 다룰 줄 알게 된 뒤, 여러 컨테이너를 잇기 직전에 필요한 지식이다. Compose 의 전제가 된다.58Docker Compose 로 여러 컨테이너 다루기컨테이너·이미지·네트워크·볼륨을 각각 알게 된 다음, 그것들을 하나의 애플리케이션으로 선언하는 단계다.89이미지 공유와 레지스트리내 이미지를 남과 나누는 단계. 앞에서 이미지를 만들 줄 알아야 태그·푸시·신뢰 개념이 의미를 갖는다.510보안실행·빌드·공유를 할 줄 아는 상태여야 '어디가 위험한지'를 짚을 수 있다. 운영 전 마지막 관문이다.611운영과 확장만들고 실행하는 법을 아는 사람이 마지막으로 배우는 것 — 오래 굴리기 위한 데몬 설정·관측·정리와 여러 호스트로의 확장.7

컨테이너와 Docker 플랫폼의 구조

컨테이너는 호스트 커널을 공유한 채 격리된 프로세스로 앱을 실행하는 단위로, 게스트 OS를 통째로 띄우는 가상머신보다 가볍고 빠르다.

→ 01-05 참조

1상대의 출발점 확인

가상머신은 호스트 위에 완전한 OS를 각 앱마다 띄워야 하므로, 각 가상머신마다 수 GB의 디스크 공간과 메모리가 필요하고 부팅 시간도 깁니다. 하나의 호스트에서 여러 앱을 격리해 실행하려면 이런 무거운 오버헤드를 감수해야 했습니다.

2질문 제기

호스트의 OS 커널을 공유하면서도 각 앱이 자신만의 파일시스템과 네트워크을 갖도록 격리할 수 있을까요?

3구조적 핵심 예시

Linux 커널이 하나 있을 때, 그 위에서 프로세스 A는 /app1 디렉토리가 루트(/)로 보이고 eth0이 유일한 네트워크 인터페이스로 보이게 하고, 프로세스 B는 /app2 디렉토리가 루트로 보이고 eth1이 보이도록 설정합니다. 같은 커널을 쓰지만 각 프로세스가 보는 환경은 완전히 다릅니다.

4단계별 동작 과정

  1. 호스트 커널 공유가상머신처럼 완전한 OS를 띄우지 않고 호스트의 Linux 커널을 그대로 사용합니다.
  2. 네임스페이스로 격리각 컨테이너에게 자신만의 파일시스템, 네트워크 인터페이스, 프로세스 ID 범위를 보이게 설정하는 것으로 서로 간섭하지 않게 합니다.
  3. 경량 프로세스로 실행가상머신처럼 OS 부팅 오버헤드가 없으므로 초 단위로 시작되고, 수십 MB 메모리만 사용합니다.

5본질 요약

호스트 커널을 공유하면서 네임스페이스로 격리된 환경에서 앱을 경량 프로세스로 실행하는 단위

컨테이너와 Docker 플랫폼의 구조

이미지는 컨테이너의 읽기 전용 템플릿이며, 변경분이 쌓인 레이어들로 이뤄지고 사람이 읽는 태그와 내용 해시인 다이제스트로 식별된다.

1상대의 출발점 확인

컨테이너 한 개를 직접 구성하려면 기본 OS 파일 설치, 런타임 설치, 앱 코드 복사 등 여러 단계를 매번 반복해야 합니다. 이 과정을 재현하려면 정확히 같은 명령을 다시 실행해야 하고, 사람이 빠뜨리거나 실수하기 쉽습니다.

2질문 제기

이미 설정한 환경의 상태를 저장해두고 여러 컨테이너를 그 상태로부터 생성할 수 있을까요?

3구조적 핵심 예시

Ubuntu 18.04 기본 파일들을 Layer 1로, 그 위에 Python 3.9 설치 결과를 Layer 2로, 그 위에 앱 코드를 Layer 3으로 쌓아두면, 이 이미지로부터 같은 상태의 컨테이너를 몇 개든 즉시 생성할 수 있습니다.

4단계별 동작 과정

  1. 변경분을 레이어로 쌓음Dockerfile의 각 명령(FROM, RUN, COPY 등)이 읽기 전용 레이어 하나씩을 만들고 순서대로 겹쳐집니다.
  2. 이미지는 읽기 전용 템플릿모든 레이어의 합산이 이미지이며, 컨테이너 생성 시 그 위에 쓰기 가능한 임시 계층(컨테이너 레이어)이 추가됩니다.
  3. 태그와 다이제스트로 식별사람이 읽는 이름(예: myapp:v1.0)을 태그라 하고, 내용을 SHA256으로 해시한 값을 다이제스트(예: sha256:abc123...)라 해서 정확히 같은 이미지임을 보증합니다.

1상대의 출발점 확인

이미지를 로컬 컴퓨터에만 저장하면, 팀원의 컴퓨터나 운영 서버에서는 그 이미지를 받을 수 없습니다. 각자 Dockerfile로부터 이미지를 다시 빌드해야 하고, 정확히 같은 환경임을 보장하기 어렵습니다.

2질문 제기

이미지를 중앙의 공용 서버에 저장해서 언제 어디서나 가져올 수 있을까요?

3구조적 핵심 예시

Docker Hub(또는 개인 레지스트리)에 docker.io/myteam/webapp 리포지터리가 있고, 그 안에 v1.0, v1.1, v1.2, latest 태그가 있으면, 팀원은 docker pull myteam/webapp:v1.1 한 줄로 정확히 원하는 버전을 받습니다.

4단계별 동작 과정

  1. 레지스트리는 이미지 저장소 서버Docker Hub, AWS ECR, 개인 서버 등 이미지를 보관하고 배포하는 역할을 합니다.
  2. 리포지터리는 같은 이름의 이미지 모음myapp/webapp처럼 같은 앱의 여러 태그를 모아두는 저장 단위입니다.
  3. pull로 이미지 다운로드docker pull 명령으로 레지스트리에서 특정 태그의 이미지를 다운받아 로컬에 저장합니다.

컨테이너와 Docker 플랫폼의 구조

docker CLI(클라이언트)가 Docker API로 데몬(dockerd)에 요청하면 데몬이 이미지·컨테이너·볼륨·네트워크 같은 객체를 만들고 관리한다.

1상대의 출발점 확인

docker run 명령을 입력하면 컨테이너가 생성되는 것처럼 보이지만, 실제로는 CLI(명령줄 도구) 프로세스와 백그라운드에서 실행되는 데몬(관리 프로세스) 사이에 통신이 일어나야 합니다. 이 구조를 모르면 permission denied 같은 오류를 만났을 때 원인을 이해하기 어렵습니다.

2질문 제기

docker 명령어가 입력되면 어떻게 실제 컨테이너와 이미지가 생성되고 관리될까요?

3구조적 핵심 예시

docker run ubuntu 명령을 입력하면, docker CLI가 /var/run/docker.sock Unix 소켓을 통해 Docker API 요청을 보내고, 백그라운드의 dockerd 데몬이 그 요청을 받아 이미지를 다운로드하고, 컨테이너를 생성해서 실행한 뒤 결과를 CLI에 돌려줍니다.

4단계별 동작 과정

  1. CLI가 명령을 API 호출로 변환docker 명령줄 도구가 사용자의 명령(예: docker run, docker ps)을 Docker API 요청으로 만듭니다.
  2. 데몬(dockerd)이 요청을 받아 처리백그라운드에서 항상 실행 중인 Docker 데몬이 API 요청을 받고, 이미지·컨테이너·볼륨·네트워크 같은 객체를 생성하거나 조작합니다.
  3. 결과가 CLI로 반환데몬이 작업을 완료하면 결과(컨테이너 ID, 로그 등)를 다시 CLI로 전달해서 사용자가 확인하게 합니다.

1상대의 출발점 확인

컨테이너가 호스트 커널을 공유한다는 것은, 각 컨테이너 안의 프로세스들이 같은 커널 자원(파일, 네트워크, 프로세스 등)에 접근할 가능성이 있다는 뜻입니다. 격리된 환경을 만들려면 커널 수준에서 각 컨테이너가 보는 범위를 제한하고, 사용할 수 있는 리소스(CPU, 메모리)도 제한해야 합니다.

2질문 제기

호스트 커널 하나를 여러 격리된 환경으로 나누고, 각 환경의 자원 사용을 제한할 수 있을까요?

3구조적 핵심 예시

컨테이너 A의 PID 네임스페이스에서는 자신의 프로세스들이 PID 1, 2, 3으로 보이지만, 호스트에서는 PID 5001, 5002, 5003으로 보입니다. 동시에 cgroups 설정으로 컨테이너 A는 CPU 10%, 메모리 512MB까지만 사용하도록 제한합니다.

4단계별 동작 과정

  1. 네임스페이스로 보이는 범위 격리PID, 네트워크, 마운트, IPC 등 여러 종류의 네임스페이스로 각 컨테이너가 보는 파일시스템, 프로세스, 네트워크 인터페이스를 격리합니다.
  2. cgroups로 자원 사용 제한Control Groups 메커니즘으로 CPU, 메모리, I/O 등 각 컨테이너의 자원 사용 한도를 설정합니다.
  3. containerd와 runc가 실행 담당containerd(컨테이너 런타임)가 이미지 저장소를 관리하고, runc(저수준 런타임)가 네임스페이스와 cgroups를 적용해 실제 컨테이너 프로세스를 시작합니다.

설치와 CLI 첫걸음

리눅스 배포판별 apt/dnf 저장소로 Docker Engine을 설치하고, 비루트 사용자 docker 그룹 추가·부팅 시 자동 시작 같은 설치 후 설정을 마치는 과정이다.

1상대의 출발점 확인

리눅스 시스템에서 소프트웨어를 설치하는 표준 방법은 apt(Debian/Ubuntu), dnf(Fedora/RHEL) 같은 배포판별 패키지 매니저입니다. 설치 후에는 보통 sudo 권한이 필요하거나 부팅 시 자동 시작 설정이 필요합니다.

2질문 제기

리눅스 배포판별로 Docker Engine을 설치하고, 비루트 사용자도 사용할 수 있게 설정하려면 어떤 단계를 거칠까요?

3구조적 핵심 예시

Ubuntu 시스템에서 Docker 공식 저장소를 apt 소스에 추가한 후 apt install docker-ce로 설치하고, docker 그룹에 현재 사용자를 추가(usermod -aG docker $USER)한 후, sudo systemctl enable docker로 부팅 시 자동 시작을 설정합니다.

4단계별 동작 과정

  1. 배포판 저장소 설정 및 설치각 배포판의 공식 또는 Docker 공식 저장소에서 docker-engine(또는 docker-ce) 패키지를 다운로드해 설치합니다.
  2. docker 그룹에 사용자 추가기본적으로 dockerd는 root 권한으로만 실행되는데, docker 그룹에 사용자를 추가하면 sudo 없이 docker 명령을 사용할 수 있습니다.
  3. 부팅 시 자동 시작 설정systemctl enable docker 명령으로 systemd 부팅 서비스에 docker를 등록해, 시스템 시작 시 자동으로 Docker 데몬이 실행되도록 설정합니다.

5본질 요약

설치와 CLI 첫걸음

윈도우·맥에서 Docker Desktop을 설치해 리눅스 컨테이너용 백엔드(WSL2 또는 VMM 가상머신)를 띄우고 Docker 계정으로 로그인하는 단계다.

1상대의 출발점 확인

Windows와 macOS는 Linux 커널이 없어서 컨테이너를 직접 실행할 수 없습니다. 가상머신 또는 하이퍼바이저로 Linux 커널을 띄워야만 Docker 데몬이 동작하고, 컨테이너를 실행할 수 있습니다.

2질문 제기

Windows와 macOS에서 Linux 컨테이너를 실행하려면 어떤 환경을 준비해야 할까요?

3구조적 핵심 예시

Windows 11에 Docker Desktop을 설치하면, WSL2(Windows Subsystem for Linux 2, 경량 가상머신)가 백그라운드에 자동 설치되어 Linux 커널을 띄우고, docker CLI의 명령들은 그 WSL2 위의 dockerd 데몬으로 전달돼 컨테이너를 생성합니다.

4단계별 동작 과정

  1. Docker Desktop 설치 및 백엔드 선택Docker Desktop 설치 프로그램에서 WSL2 또는 Hyper-V(또는 다른 가상화 백엔드)를 선택해 설치합니다.
  2. Linux 커널을 포함한 가상머신 자동 시작선택한 백엔드가 Linux 커널 이미지를 포함해 자동으로 설치되고, Docker 애플리케이션 시작 시 백그라운드에서 실행됩니다.
  3. Docker 계정 로그인Docker Hub 등의 이미지 저장소에서 이미지를 pull하거나 private 이미지에 접근하려면, docker login 명령으로 Docker 계정에 인증합니다.

Docker Desktop 사용: 대시보드·설정·리소스 관리

컨테이너·이미지·볼륨 목록과 로그를 GUI 대시보드에서 확인하고, 설정 화면에서 CPU·메모리·디스크 등 리소스를 조정하는 방법이다.

1상대의 출발점 확인

docker 명령어로 컨테이너와 이미지를 관리할 수 있지만, 터미널 명령만으로는 현재 실행 중인 컨테이너가 몇 개인지, 각각이 얼마나 많은 메모리를 쓰고 있는지, CPU·디스크 리소스가 충분한지 한눈에 파악하기 어렵다. 또한 Docker가 사용할 수 있는 자원을 호스트 시스템에서 직접 설정하려면 설정 파일을 찾아 편집해야 한다는 번거로움이 있다.

2질문 제기

실행 중인 컨테이너들과 이미지들을 한눈에 보고, Docker가 사용할 리소스를 마우스 클릭으로 조정할 수는 없을까?

3구조적 핵심 예시

Docker Desktop이 제공하는 대시보드를 열면, 현재 실행 중인 컨테이너 목록과 각각의 상태(CPU·메모리 사용률), 저장된 이미지 목록, 볼륨 목록이 탭별로 표시된다. 설정 메뉴에서 Docker가 사용할 CPU 개수, 메모리 크기, 디스크 용량 상한을 슬라이더나 입력 필드로 조정하면, Docker 엔진이 재시작되면서 그 설정을 적용한다.

4단계별 동작 과정

  1. 대시보드 확인Docker Desktop 창을 열면 "Containers"·"Images"·"Volumes" 탭이 보인다. Containers 탭에서 실행 중인 모든 컨테이너와 그들이 쓰는 CPU·메모리, 네트워크 송수신량을 실시간으로 확인한다.

  3. 설정 조정우측 상단의 설정 아이콘을 클릭하여 "Resources" 탭을 열고, CPU·Memory·Disk image size 슬라이더를 움직여 Docker가 호스트에서 사용할 최대 자원을 정한다.

이미지로부터 컨테이너를 만들어 실행하는 docker run 과, 생성·실행·정지·삭제로 이어지는 컨테이너의 일생을 다룬다.

1상대의 출발점 확인

이미지는 파일 시스템과 애플리케이션을 담은 템플릿일 뿐, 이것만으로는 아무것도 실행되지 않는다. 컨테이너는 이 이미지를 실제로 실행하는 독립적인 프로세스 환경인데, 처음 사용자는 이미지에서 컨테이너를 어떻게 만들고, 그 컨테이너가 어떤 상태 변화를 거치는지 알아야 한다.

2질문 제기

이미지로부터 실행 가능한 컨테이너를 만들고, 그 컨테이너의 생성부터 삭제까지 전체 수명주기를 어떻게 관리하는가?

3구조적 핵심 예시

docker run nginx를 실행하면, Docker는 먼저 nginx 이미지를 찾고(없으면 다운로드), 그 이미지로부터 새로운 컨테이너를 생성한 후 곧바로 그 컨테이너를 시작하여 nginx 프로세스를 실행한다. 이 한 명령으로 "생성" + "시작"이 동시에 일어난다.

4단계별 동작 과정

  1. 생성(Create)docker run 또는 docker create 명령이 이미지로부터 새 컨테이너를 만든다. 이때 고유한 컨테이너 ID가 할당되고, 이미지의 파일 시스템 스냅샷과 설정이 컨테이너에 복제된다.
  2. 시작(Start)docker run은 자동으로 그 컨테이너를 시작하며, 컨테이너의 초기 프로세스(entrypoint, 즉 컨테이너 시작 시 실행될 명령)가 실행된다. 프로세스가 동작하는 동안 컨테이너는 "Running" 상태다.
  3. 정지·삭제(Stop·Remove)프로세스가 종료되거나 사용자가 docker stop 명령을 실행하면 컨테이너는 "Exited" 상태가 된다. 이 시점에도 컨테이너 파일 시스템은 남아 있다. docker rm으로 명시적으로 삭제하면 그 컨테이너의 모든 데이터가 제거된다.

5본질 요약

docker run은 이미지를 컨테이너로 변환하여 실행하는 명령이며, 컨테이너는 생성된 이후 실행·정지·삭제의 상태를 거치는 일생을 갖습니다.

1상대의 출발점 확인

2질문 제기

실행 중인 컨테이너들의 상태, 자원 사용량, 로그 출력, 내부 프로세스를 각각 어떤 명령으로 확인할 수 있는가?

3구조적 핵심 예시

컨테이너 상태를 확인할 때 docker ps로는 실행 중인 컨테이너의 기본 정보(ID, 이름, 상태, 포트)를 확인하고, docker logs로는 컨테이너가 출력한 텍스트 로그를, docker stats로는 실시간 CPU·메모리 사용률을 본다. 각 명령은 필요한 관점의 정보만 빠르게 제공한다.

4단계별 동작 과정

  1. ps(list)로 개요 확인docker ps는 현재 실행 중인 컨테이너의 목록을 보여준다. 컨테이너 ID, 이미지 이름, 현재 상태(Up, Exited), 열린 포트, 시작 명령이 표시된다.
  2. logs·inspect·top·stats로 상세 정보 수집docker logs는 그 컨테이너가 표준 출력으로 쏟아낸 모든 텍스트를 보고, docker inspect는 컨테이너의 모든 설정(환경변수, 마운트, 네트워크 등)을 JSON으로 출력한다. docker top은 컨테이너 안에서 실행 중인 프로세스 목록을, docker stats는 CPU·메모리·네트워크 I/O를 실시간으로 보여준다.
  3. events로 변화 감시docker events를 실행하면 그 이후로 Docker에서 일어나는 모든 변화(컨테이너 생성, 시작, 정지, 삭제 등)를 실시간으로 스트리밍한다.

돌고 있는 컨테이너 안에서 명령을 실행하거나 터미널을 붙이고 파일을 주고받는 방법이다.

1상대의 출발점 확인

컨테이너는 독립적인 격리 환경에서 실행되므로, 호스트 셸에서 그 안의 파일을 직접 접근하거나 명령을 실행할 수 없다. 실행 중인 컨테이너 내부에서 디버깅하거나 파일을 주고받아야 하는 상황에서 컨테이너를 정지하고 재시작해야 한다면 불편하다.

2질문 제기

실행 중인 컨테이너 내부에서 명령을 실행하거나 파일을 주고받을 수 있는 방법이 있는가?

3구조적 핵심 예시

docker exec -it <컨테이너> /bin/bash를 실행하면, 호스트의 터미널이 실행 중인 컨테이너 내부의 bash 셸에 연결되어, 그 컨테이너 안에서 명령을 실행하고 결과를 볼 수 있다. 이때 컨테이너는 계속 실행 상태를 유지한다.

4단계별 동작 과정

  1. exec로 명령 실행docker exec는 실행 중인 컨테이너 내부에서 새로운 프로세스를 실행한다. -i(interactive) 플래그로 표준 입력을 열고, -t(tty) 플래그로 터미널을 할당하면, 대화형으로 셸을 제어할 수 있다.
  2. attach로 기존 프로세스에 연결docker attach는 컨테이너의 초기 프로세스(메인 애플리케이션)의 표준 입출력에 호스트 터미널을 직접 연결한다. 컨테이너가 이미 실행 중인 애플리케이션과 상호작용할 때 사용된다.
  3. cp로 파일 전송docker cp <컨테이너>:<경로> <호스트경로>로 컨테이너 내부 파일을 호스트로 복사하거나, 그 반대로 호스트 파일을 컨테이너로 복사할 수 있다. 컨테이너는 계속 실행되며, 한 번의 파일 전송만 일어난다.

1상대의 출발점 확인

이미지를 만들 때 Dockerfile에 기본 실행 명령, 환경변수, 실행 권한을 가질 사용자, 노출할 포트를 지정한다. 하지만 같은 이미지를 여러 상황에서 다르게 실행해야 할 때—개발, 테스트, 운영 환경에서 다른 설정을 써야 할 때—이미지를 매번 다시 빌드할 수는 없다.

2질문 제기

Dockerfile에 박힌 기본값을 실행 시점에 덮어써서 같은 이미지를 다양하게 실행할 수는 없을까?

3구조적 핵심 예시

docker run -e DB_HOST=prod.example.com -p 8080:80 -u appuser nginx를 실행하면, 이미지에 설정된 환경변수·포트 매핑·실행 사용자를 명령 옵션으로 바꿀 수 있다. 같은 nginx 이미지도 환경에 맞게 다양하게 실행된다.

4단계별 동작 과정

  1. 환경변수 재정의-e KEY=VALUE 또는 --env-file 옵션으로 컨테이너 환경변수를 지정한다. 이미지에 정의된 기본값을 덮어쓴다. 애플리케이션이 데이터베이스 주소, API 키, 로그 레벨 등을 환경변수로 읽도록 설계되어 있으면, 이 방법으로 배포 환경별로 동일한 이미지를 사용할 수 있다.
  2. 포트와 사용자 재정의-p 호스트포트:컨테이너포트로 포트 매핑을 지정하고, -u 사용자명으로 컨테이너 내부에서 실행될 사용자를 바꾼다. 이미지에 정의된 EXPOSE와 USER 지시어의 기본값이 이 옵션들로 교체된다.
  3. 실행 명령 재정의docker run 명령 끝에 원하는 명령을 추가하면, Dockerfile의 CMD나 ENTRYPOINT를 대체한다. 예: docker run myapp python script.py는 이미지의 기본 명령 대신 python script.py를 실행한다.

컨테이너가 죽거나 호스트가 재부팅될 때 자동으로 다시 뜨게 하고, 건강 상태를 점검하며 안전하게 멈추는 설정이다.

→ 03-02 참조

1상대의 출발점 확인

컨테이너 안의 애플리케이션이 예기치 않게 종료되거나, 호스트가 재부팅되면 컨테이너도 함께 내려간다. 운영 환경에서는 이런 상황에서 자동으로 컨테이너가 다시 시작되어야 한다. 또한 컨테이너가 "실행 중"이라고 해서 내부 애플리케이션이 정상적으로 작동하는지 알 수 없고, 컨테이너가 SIGTERM 신호를 받고 안전하게 종료되지 않으면 데이터 손상이 발생할 수 있다.

2질문 제기

컨테이너가 죽거나 호스트가 재부팅될 때 자동 재시작하고, 내부 애플리케이션의 실제 건강 상태를 점검하며, 안전한 종료를 보장할 수 있는 방법은 무엇인가?

3구조적 핵심 예시

docker run --restart=always --health-cmd="curl localhost:8080" -e STOPSIGNAL=SIGTERM myapp로 실행하면, 컨테이너가 종료되면 자동으로 다시 시작되고, Docker가 주기적으로 헬스체크 명령을 실행하여 애플리케이션이 정상인지 확인하며, 종료 신호를 받았을 때 graceful shutdown을 할 기회를 준다.

4단계별 동작 과정

  1. 재시작 정책 설정--restart 옵션으로 재시작 방식을 지정한다. no(기본값, 재시작 안 함), always(항상 재시작), on-failure(오류로 종료되면 재시작), unless-stopped(수동으로 정지하지 않으면 항상 재시작)이 있다. 호스트 재부팅 후에도 이 정책에 따라 컨테이너가 자동 시작된다.
  2. 헬스체크 정의--health-cmd 옵션으로 주기적으로 실행할 건강 점검 명령을 지정한다. curl이나 자체 스크립트를 사용하여, 애플리케이션이 정상 응답하는지 검사한다. 헬스체크가 실패하면 Docker는 이를 기록하고, docker ps 결과에 "unhealthy" 상태를 표시한다.
  3. 안전한 종료 처리SIGTERM 신호를 받을 때 애플리케이션이 현재 처리 중인 요청을 끝낸 후 종료하도록 코드를 작성한다. docker stop은 먼저 SIGTERM을 보내고, 지정된 시간(기본 10초) 안에 종료되지 않으면 SIGKILL로 강제 종료한다.

5본질 요약

--restart·--health-cmd·SIGTERM 처리는 컨테이너가 죽었을 때 자동으로 재시작되고, 내부 애플리케이션의 건강 상태를 지속적으로 감시하며, 종료될 때 데이터 손상 없이 우아하게 정리되도록 보장합니다.

리소스 제한과 GPU 접근

컨테이너가 쓸 수 있는 CPU·메모리를 제한하고 필요하면 호스트의 GPU를 쓰게 열어 주는 방법이다.

1상대의 출발점 확인

컨테이너를 실행하면 기본적으로 호스트의 CPU, 메모리, 디스크 I/O를 제한 없이 사용할 수 있다. 그러면 한 컨테이너의 폭주하는 작업이 호스트의 다른 컨테이너나 시스템 전체를 느리게 만들 수 있다.

2질문 제기

컨테이너별로 쓸 수 있는 CPU·메모리의 상한을 미리 정해 놓을 수 있을까?

3구조적 핵심 예시

docker run --memory 512m --cpus 1.5 myimage 명령은 이 컨테이너의 메모리를 512MB, CPU를 1.5코어(물리 코어의 1.5배)로 제한한다. 컨테이너가 그 이상 쓰려고 하면 메모리는 프로세스가 강제 종료되고, CPU는 사용량이 깎인다.

4단계별 동작 과정

  1. 리소스 상한 설정docker run이나 docker update의 옵션으로 메모리(--memory), CPU(--cpus), 스왑(--memory-swap), I/O 대역폭(--blkio-weight) 같은 제한값을 정한다.
  2. 커널의 cgroup이 감시리눅스 커널의 cgroup(제어 그룹)이 컨테이너의 자원 사용량을 계속 측정해서 제한값과 비교한다.
  3. 초과 시 제어메모리가 상한을 초과하면 해당 프로세스가 즉시 종료되고, CPU는 할당된 시간만큼만 실행해서 나머지는 대기 상태로 전환된다.

5본질 요약

호스트 자원의 최대 사용량을 컨테이너별로 미리 정해 두어 여러 컨테이너 사이의 자원 경쟁을 제어하는 것

docker build 와 빌드 컨텍스트·.dockerignore

docker build 는 지정한 디렉터리(빌드 컨텍스트)의 파일을 빌더에 넘겨 이미지를 만들고, .dockerignore 로 보낼 파일을 걸러낸다.

1상대의 출발점 확인

Dockerfile은 이미지를 만드는 명령어들을 담은 텍스트 파일이지만, 그것만으로는 부족하다. 소스 코드, 설정 파일, 리소스 같은 실제 파일들이 있어야 COPY나 ADD로 이미지 안에 넣을 수 있다. 그 파일들을 빌더에 어떻게 건네줄지 명시해야 한다.

2질문 제기

docker build가 이미지를 만들 때, Dockerfile과 함께 보낼 파일(빌드 컨텍스트)을 어떻게 구성하고 걸러낼까?

3구조적 핵심 예시

docker build -t myapp . 명령에서 점(.)은 현재 디렉터리를 빌드 컨텍스트로 지정한다. 이 디렉터리의 모든 파일과 폴더가 기본으로 빌더에 전송되는데, .dockerignore 파일에 .git, node_modules, *.log 같은 패턴을 쓰면 그 파일들은 제외되고 필요한 것만 보낸다.

4단계별 동작 과정

  1. 빌드 컨텍스트 경로 지정docker build 뒤에 경로를 주면 (. 또는 /path/to/dir 또는 Git URL) 그 위치를 빌드 컨텍스트로 정한다.
  2. .dockerignore로 제외 패턴 정의빌드 컨텍스트 디렉터리의 .dockerignore 파일에 제외할 파일/폴더의 glob 패턴(예: */, *.tmp)을 한 줄씩 작성한다.
  3. 빌더에 컨텍스트 전송Docker는 제외된 항목을 빼고 나머지를 모두 빌더에 보낸다. 빌더는 Dockerfile의 COPY/ADD 명령이 그 안에서 파일을 찾아 이미지에 넣는다.

5본질 요약

이미지 빌드에 필요한 파일만 선택적으로 빌더에 전달하되, 불필요한 대용량 파일(.git, node_modules 등)은 미리 걸러내서 빌드 속도를 높이고 네트워크 전송량을 줄이는 것

Dockerfile 형식과 파서 지시어(syntax·escape·check)

Dockerfile 은 명령어 한 줄씩 쓰는 텍스트 파일이며, 맨 위 주석형 파서 지시어로 문법 프론트엔드·이스케이프 문자·검사 동작을 지정한다.

1상대의 출발점 확인

Dockerfile을 읽을 때 어떤 문법 규칙을 따를지, 이스케이프 문자는 무엇일지, 무엇을 검사할지 정하지 않으면 빌더마다 다르게 해석할 수 있다. 같은 파일이 개발 환경에서는 되지만 CI 환경에서는 깨지는 식의 문제가 발생한다.

2질문 제기

Dockerfile의 문법 버전과 해석 규칙을 명시적으로 선언할 수 있을까?

3구조적 핵심 예시

Dockerfile의 맨 위에 # syntax=docker/dockerfile:1.4 라는 주석을 쓰면, 빌더는 그 버전의 문법 엔진(프론트엔드)을 사용해 파일을 해석한다. 이어서 # escape= (역슬래시 대신 백틱 사용)나 # check=skip (특정 검사 건너뛰기) 같은 지시어를 추가로 쓸 수 있다.

4단계별 동작 과정

  1. 파서 지시어 선언Dockerfile 최상단에 # syntax=..., # escape=..., # check=... 형태의 주석을 작성한다. 이들은 일반 주석과 달리 빌더의 동작을 결정한다.
  2. 문법 버전 결정syntax 지시어가 빌더가 어떤 명령어 문법과 기능(예: 히어독, RUN --mount 등)을 지원할지 정한다.
  3. 이스케이프·검사 규칙 적용escape는 백슬래시 대신 다른 문자를 이스케이프 문자로 쓰고, check는 문법 검사 강도를 조정한다.

5본질 요약

Dockerfile의 표준 문법과 빌더 기능·검사 방식을 선언적으로 명시해서, 누가 언제 어느 환경에서 빌드하든 일관된 결과를 보장하는 것

FROM 과 베이스 이미지 선택

FROM 은 새 이미지의 출발점이 될 베이스 이미지를 정하는 명령으로, 크기·보안·유지보수를 따져 고른다.

1상대의 출발점 확인

컨테이너 이미지를 처음부터 완전히 만들려면 OS 설치, 패키지 관리 도구 설정, 보안 업데이트 같은 기본 작업을 매번 반복해야 한다. 시간이 오래 걸리고, 최신 보안 패치를 빠뜨릴 수도 있으며, 유지보수도 어렵다.

2질문 제기

이미 완성된 OS와 개발 환경을 출발점으로 삼아, 그 위에만 우리 코드를 얹을 수 있을까?

3구조적 핵심 예시

FROM python:3.11 명령은 Python 3.11이 이미 설치된 리눅스 이미지를 출발점으로 정한다. 이 이미지는 Ubuntu 또는 Debian 기반이고 pip, 필요한 라이브러리가 준비되어 있다. 그 위에 RUN pip install ..., COPY . /app 같은 명령으로 추가 작업을 하면 된다.

4단계별 동작 과정

  1. 베이스 이미지 지정Dockerfile의 첫 번째(또는 멀티스테이지의 각) FROM 명령에서 사용할 이미지를 정한다. 공식 저장소(python:3.11, node:18 등) 또는 회사 내부 이미지를 쓸 수 있다.
  2. 베이스 이미지 레이어 상속지정한 이미지의 모든 레이어가 새 이미지의 출발점이 된다. 즉, 그 이미지에 있는 모든 파일, 환경 변수, 설정이 자동으로 포함된다.
  3. 그 위에 새 레이어 쌓기FROM 이후 RUN, COPY 등의 명령으로 추가 작업을 하고, 각 명령의 결과가 새로운 레이어로 쌓인다.

RUN: 셸/exec 형식·히어독·RUN 마운트

RUN 은 빌드 중 명령을 실행해 결과를 새 레이어로 남기며, 셸/exec 형식과 히어독, 캐시·시크릿 마운트를 지원한다.

→ 04-09 참조

1상대의 출발점 확인

RUN 명령은 이미지 빌드 중에 셸 명령을 실행해서 그 결과를 새 레이어로 기록한다. 하지만 명령을 어떻게 쓸지, 여러 줄 명령은 어떻게 처리할지, 캐시된 레이어를 안전하게 재사용할지에 대한 선택지가 많아서, 상황에 맞게 쓰지 않으면 빌드 속도가 느리거나 보안이 약할 수 있다.

2질문 제기

RUN 명령을 효율적이고 안전하게, 그리고 여러 줄 명령이나 임시 파일을 어떻게 처리할까?

3구조적 핵심 예시

RUN apt-get update && apt-get install -y curl (셸 형식)은 /bin/sh를 거쳐 한 프로세스에서 두 명령을 연결해 실행하고, RUN ["apt-get", "install", "-y", "curl"] (exec 형식)은 셸을 거치지 않고 /usr/bin/apt-get을 직접 호출한다. 또는 RUN <<EOF / apt-get update / apt-get install -y curl / EOF 같은 히어독(<<)을 사용해 여러 줄을 한 RUN에 묶을 수 있다.

4단계별 동작 과정

  1. 셸 형식 vs exec 형식 선택셸 형식(공백으로 구분한 문자열)은 /bin/sh를 사용해 간단하지만 약간의 오버헤드가 있고, exec 형식(JSON 배열)은 셸을 거치지 않아 빠르고 명시적이지만 복잡할 수 있다.
  2. 히어독과 마운트로 고급 기능 사용히어독(<<)으로 여러 줄 스크립트를 한 번에 작성하고, --mount 옵션으로 빌드 캐시(--mount=type=cache)나 시크릿(--mount=type=secret)을 임시로 마운트해 보안을 높이고 재빌드 성능을 개선한다.
  3. 레이어 기록 및 캐시RUN 명령의 결과가 새 레이어로 저장되고, 빌드할 때마다 이전 결과를 캐시에서 재사용할 수 있다. 입력(Dockerfile 명령, COPY된 파일 등)이 같으면 캐시 히트가 발생한다.

빌드 중 실행할 명령의 형식과 캐시·보안 옵션을 세밀하게 제어해서, 빌드 속도와 보안성을 동시에 최적화하는 것

파일 넣기: COPY 와 ADD

COPY 는 빌드 컨텍스트의 파일을 이미지 안으로 그대로 복사하고, ADD 는 URL·압축 해제 같은 추가 기능까지 처리한다.

1상대의 출발점 확인

이미지 안에 호스트의 파일을 넣어야 하는데, 단순히 그대로 복사하는 것만으로는 충분하지 않을 수도 있다. URL에서 다운로드해야 하거나, tar.gz 같은 압축 파일을 풀어야 하거나, 파일의 권한을 조정해야 할 수도 있다. 이 모든 경우를 다르게 처리해야 한다.

2질문 제기

호스트의 파일을 이미지 안으로 넣을 때, 얼마나 많은 추가 기능을 활용할 것인가?

3구조적 핵심 예시

COPY src/ /app/src/는 호스트의 src 디렉터리를 이미지의 /app/src에 그대로 복사한다. 반면 ADD archive.tar.gz /opt/는 tar.gz 파일을 자동으로 풀어서 /opt에 넣고, ADD https://example.com/file.zip /tmp/라고 쓰면 URL에서 파일을 다운로드해서 /tmp에 넣는다.

4단계별 동작 과정

  1. COPY로 단순 복사COPY는 빌드 컨텍스트의 파일/폴더를 이미지 안의 경로로 그대로 복사한다. 동작이 예측 가능하고 투명하다.
  2. ADD로 추가 처리ADD는 COPY의 기능을 포함하되, URL이면 다운로드하고, .tar, .tar.gz, .zip 등의 압축 파일이면 자동으로 해제한다.
  3. 캐시와 체크섬 추적COPY와 ADD는 모두 원본 파일의 내용 변화를 감지해 캐시 판단에 사용한다. 파일이 바뀌면 캐시가 무효화되고 다시 실행된다.

5본질 요약

빌드 컨텍스트의 파일을 이미지 안으로 옮기되, 추가 처리 기능(압축 해제, URL 다운로드)의 필요 여부에 따라 COPY(단순, 권장)와 ADD(기능 많음)를 선택하는 것

1상대의 출발점 확인

이미지가 완성되면 누군가 docker run으로 컨테이너를 시작한다. 그런데 실행자가 매번 "어떤 명령을 실행할지", "어떤 포트를 노출할지", "어느 폴더를 볼륨으로 쓸지", "상태는 어떻게 확인할지" 같은 옵션을 일일이 입력하는 것은 번거롭다. 이 정보를 이미지에 미리 내장할 수 있다면 실행자의 부담이 훨씬 줄어든다.

2질문 제기

컨테이너 실행 시 필요한 기본 명령, 포트, 볼륨, 상태검사 등을 이미지에 미리 정해 두고 실행자가 쉽게 쓸 수 있을까?

3구조적 핵심 예시

CMD ["python", "app.py"]는 docker run할 때 기본으로 실행할 명령을 정하고, EXPOSE 8080은 "이 이미지는 8080 포트를 사용합니다"라고 선언하며, HEALTHCHECK --interval=30s CMD curl http://localhost:8080/health로 30초마다 상태 확인 명령을 실행하도록 지정한다. VOLUME ["/data"]라고 쓰면 /data 경로는 기본적으로 호스트와 공유하도록 제안된다.

4단계별 동작 과정

  1. CMD/ENTRYPOINT로 기본 명령 정의CMD는 컨테이너 시작 시 기본 실행 명령을 지정하고, 실행자가 docker run myimage bash 식으로 다른 명령을 주면 덮어쓸 수 있다. ENTRYPOINT는 항상 실행할 명령이고, 전달되는 인자를 받는 역할을 한다.
  2. EXPOSE, VOLUME, LABEL로 메타정보 선언EXPOSE는 이 이미지가 어떤 포트를 사용할지 문서화(실제로 포트 열기는 run 시점), VOLUME은 어느 경로가 데이터 저장용인지, LABEL은 버전·라이선스·유지보수자 같은 임의의 메타데이터를 지정한다.
  3. HEALTHCHECK로 상태 감시 설정주기적으로 특정 명령(보통 curl 또는 스크립트)을 실행해서 컨테이너가 정상인지 확인하고, 실패 횟수를 세어 상태를 "healthy" 또는 "unhealthy"로 표시한다.

ARG·ENV 와 변수 치환·스코프

ARG 는 빌드 시점에만 쓰이는 변수, ENV 는 실행 중에도 남는 환경변수이며 각각 유효 범위와 치환 규칙이 다르다.

1상대의 출발점 확인

Dockerfile을 작성할 때 고정된 값들이 코드에 하드코딩됩니다. 빌드 시점마다 다른 값(버전, 환경 설정 등)을 사용하려면 Dockerfile을 매번 수정하거나 명령줄에서 일일이 입력해야 합니다.

2질문 제기

Dockerfile 안에서 빌드할 때만 필요한 값과 컨테이너 실행 중에도 필요한 값을 어떻게 구분해서 전달할까요?

3구조적 핵심 예시

Node.js 프로젝트에서 빌드 시점에 NODE_VERSION을 ARG로 받아 빌드하고, 실행 시점에 APP_ENV라는 환경변수를 ENV로 설정해서 애플리케이션이 읽도록 합니다.

4단계별 동작 과정

  1. ARG 선언과 빌드 시점 치환Dockerfile에 ARG NODE_VERSION을 선언하고, docker build --build-arg NODE_VERSION=18 명령으로 그 값을 넘기면 빌드 중에만 해당 변수가 유효하고, 빌드가 끝나면 이미지에서 사라집니다.
  2. ENV 선언과 이미지 실행 중 유지ENV APP_ENV=production을 Dockerfile에 작성하면 그 값이 이미지 레이어에 저장되어 컨테이너가 실행될 때마다 환경변수로 접근 가능합니다.
  3. 스코프 차이에 따른 효율성ARG는 이미지 크기를 늘리지 않으므로 빌드 단계 직후 불필요해진 값(컴파일러, 라이브러리 경로 등)을 저장할 때 쓰고, ENV는 실행 시점에 애플리케이션이 읽어야 하는 설정을 저장할 때 씁니다.

멀티스테이지 빌드

1상대의 출발점 확인

하나의 Dockerfile에서 소스 코드 컴파일, 테스트, 패키지 설치 등 모든 빌드 과정을 거쳐 최종 이미지를 만듭니다. 빌드에 필요한 컴파일러, 개발용 라이브러리, 테스트 도구 등이 모두 최종 이미지에 포함되어 이미지 크기가 커지고 보안 취약점이 늘어납니다.

2질문 제기

빌드 과정에서는 필요하지만 최종 실행에는 불필요한 것들을 이미지에서 빼고 필요한 산출물만 남길 수 있을까요?

3구조적 핵심 예시

Go 언어 빌드에서 첫 번째 단계는 Go 컴파일러와 소스 코드를 가지고 실행 파일을 만들고, 두 번째 단계는 그 실행 파일만 복사해서 최소한의 기본 OS 이미지(scratch)에 넣습니다.

4단계별 동작 과정

  1. 빌드 단계 설정Dockerfile의 FROM golang:1.20 AS builder처럼 첫 번째 FROM을 빌더로 이름 붙이고, 여기서 모든 컴파일과 의존성 설치를 수행합니다.
  2. 산출물 추출COPY --from=builder /app/binary . 명령으로 빌더 단계에서 만들어진 실행 파일만 새로운 FROM 단계(경량 기본 이미지)로 복사합니다.
  3. 최종 이미지 생성복사된 산출물만 가진 최종 단계가 가벼운 이미지로 빌드 완료됩니다.

1상대의 출발점 확인

Dockerfile의 각 명령(RUN, COPY 등)은 레이어라는 단계별 저장 단위로 나뉘며, Docker는 이전 빌드에서 명령이 변하지 않았으면 캐시된 레이어를 재사용해 빠르게 빌드합니다. 어떤 명령이 변하면 그 다음 모든 레이어 캐시가 무효화되므로 명령 순서를 잘못 정하면 빌드가 불필요하게 느려지고, 코드 변경 없는 의존성 설치도 매번 반복됩니다.

2질문 제기

자주 바뀌는 코드는 뒤에, 거의 안 바뀌는 기초 설정은 앞에 배치해서 빌드 속도를 어떻게 최적화할까요?

3구조적 핵심 예시

Node.js 프로젝트에서 package.json과 package-lock.json을 먼저 COPY해서 npm install을 실행(이 레이어는 의존성 목록이 안 바뀌면 캐시됨), 그 다음에 자주 바뀌는 소스 코드를 COPY하면 코드만 수정될 때는 의존성 설치를 건너뛰고 캐시된 레이어를 재사용합니다.

4단계별 동작 과정

  1. 명령 순서 최적화덜 변하는 명령(기본 OS 업데이트, 라이브러리 설치)을 앞에 배치하고 자주 변하는 명령(소스 코드 COPY, 앱 빌드)을 뒤에 배치해서 캐시 무효화 지점을 최소화합니다.
  2. 빌드 체크와 모범 사례 적용docker buildx build --checks=skip-unused-stages로 사용하지 않는 빌드 단계를 건너뛰거나, .dockerignore로 불필요한 파일을 제외하고, 명령을 하나의 RUN으로 묶어 레이어 수를 줄입니다.
  3. 이미지 최적화 확인빌드 후 docker image inspect로 레이어별 크기를 보고, 불필요하게 큰 레이어나 중복된 설치가 없는지 검증합니다.

5Buildx 와 BuildKit 로 빌드 다루기05-01

Buildx·BuildKit 구조와 빌더·드라이버

Buildx는 빌드 명령을 받는 CLI이고 BuildKit은 실제로 빌드를 수행하는 엔진이며, 그 BuildKit 인스턴스를 어디서 어떻게 돌릴지 정하는 것이 빌더와 드라이버다.

1상대의 출발점 확인

docker build 명령은 Docker 데몬에 내장된 기본 빌더를 사용하며, 로컬 머신의 CPU 아키텍처(보통 amd64)용 이미지만 빌드 가능합니다. 멀티 플랫폼 빌드가 불가능하고, 빌드 성능 튜닝 옵션이 제한적이며, 빌드 검사나 고급 기능을 사용할 수 없습니다.

2질문 제기

더 강력한 빌드 기능(멀티 플랫폼, 빌드 검사, 성능 최적화)을 사용하려면 어떤 도구가 필요할까요?

3구조적 핵심 예시

Buildx는 CLI 인터페이스이고 BuildKit은 실제 빌드 엔진이며, BuildKit이 Docker 데몬 위에서 돌 수도 있고(docker 드라이버), 독립 컨테이너로 돌 수도 있고(docker-container 드라이버), Kubernetes 클러스터 위에서 돌 수도 있습니다(kubernetes 드라이버).

4단계별 동작 과정

  1. Buildx 설치와 빌더 생성docker buildx create 명령으로 새로운 빌더를 생성하면 지정된 드라이버 위에 BuildKit 인스턴스가 올라옵니다.
  2. 빌더와 드라이버 선택docker buildx build --builder=<빌더 이름> 명령으로 어떤 BuildKit 인스턴스를 사용할지 선택하며, 같은 코드를 여러 빌더로 빌드하면 성능 비교나 다양한 환경 테스트가 가능합니다.
  3. 드라이버별 특성 활용docker 드라이버는 빠르지만 멀티 플랫폼 불가, docker-container 드라이버는 멀티 플랫폼 지원, kubernetes 드라이버는 클러스터 리소스 활용으로 대규모 빌드가 가능합니다.

빌드 인수·시크릿·SSH 전달

ARG로 빌드 시점 값을 넘기고, 비밀번호나 키 같은 민감 정보는 이미지 레이어에 남지 않도록 --secret·--ssh로 전달한다.

1상대의 출발점 확인

빌드 명령줄에서 --build-arg로 값을 넘기거나 Dockerfile에 ENV로 직접 작성하면, 그 값(특히 비밀번호, API 키, SSH 키)이 이미지 레이어의 히스토리에 평문으로 남습니다. 누구든지 docker history 명령으로 그 레이어를 검사하면 민감한 정보가 노출되고, 이미지를 공유할 때 보안 위험이 높아집니다.

2질문 제기

빌드 시점에만 필요한 민감한 정보(키, 비밀번호)를 이미지에 남지 않고 어떻게 안전하게 전달할까요?

3구조적 핵심 예시

npm 패키지 설치 시 private GitHub 저장소에서 코드를 받아야 하면, --ssh default 옵션으로 호스트의 SSH 에이전트를 빌드 컨테이너 안으로 연결하고, git clone에 SSH를 사용하도록 합니다. 빌드 후 SSH 접근 정보는 이미지에 저장되지 않습니다.

4단계별 동작 과정

  1. 빌드 인수 전달docker build --build-arg API_KEY=secret123 명령으로 값을 넘기면 Dockerfile의 ARG API_KEY가 치환되지만, 빌드 완료 후 그 값은 이미지에 포함되지 않습니다.
  2. 민감 정보 주입docker build --secret api_key=/path/to/secret 명령으로 파일의 내용을 마운트하고, Dockerfile의 RUN --mount=type=secret,id=api_key sh -c 'cat /run/secrets/api_key'로 읽으면 이 파일은 이미지 레이어에 저장되지 않습니다.
  3. SSH 에이전트 연결docker build --ssh default 명령으로 호스트의 SSH 에이전트를 컨테이너 안으로 노출하고, Dockerfile의 RUN --mount=type=ssh git clone git@github.com:...로 사용하면 SSH 자격정보가 이미지에 남지 않습니다.

5본질 요약

빌드에 필요한 민감한 정보를 런타임 마운트로 임시 제공하되 이미지 레이어에는 저장하지 않아 보안을 유지하는 것

1상대의 출발점 확인

일반적인 docker build 명령은 빌드를 실행하는 머신의 CPU 아키텍처(보통 amd64)용 이미지만 생성합니다. ARM 기반 서버(AWS Graviton, Apple Silicon 등)나 다른 아키텍처에서 돌리려면 각 플랫폼마다 따로 빌드해야 하고, 결과 이미지를 각각 레지스트리에 올린 후 매니페스트로 묶어야 합니다.

2질문 제기

한 번의 빌드 명령으로 amd64, arm64 등 여러 아키텍처용 이미지를 동시에 만들 수 있을까요?

3구조적 핵심 예시

docker buildx build --platform linux/amd64,linux/arm64 -t myapp:latest . 명령을 실행하면 BuildKit이 QEMU를 사용해 arm64 환경을 가상으로 만들고, 같은 Dockerfile을 amd64와 arm64 각각에서 빌드해 하나의 매니페스트 리스트로 묶은 이미지가 레지스트리에 올라갑니다.

4단계별 동작 과정

  1. 플랫폼 지정과 병렬 빌드--platform 옵션에 쉼표로 구분한 플랫폼 목록을 입력하면 BuildKit이 각 플랫폼 환경을 준비하고 병렬로 빌드를 수행합니다.
  2. 매니페스트 리스트 자동 생성각 플랫폼 빌드가 완료되면 그 결과들(amd64 이미지, arm64 이미지)을 하나의 매니페스트 리스트로 자동 묶습니다.
  3. 런타임 자동 선택docker run 명령을 실행할 때 Docker는 호스트 머신의 아키텍처를 감지해 매니페스트 리스트에서 맞는 이미지를 자동으로 선택하고 실행합니다.

1상대의 출발점 확인

docker build 명령은 빌드 결과를 Docker 이미지로 만들어 로컬 이미지 저장소나 레지스트리에만 저장 가능합니다. 빌드 결과를 tar 파일로 받고 싶거나, OCI 표준 형식으로 저장하거나, 로컬 디렉터리에 파일 형태로 내보내려면 별도의 변환 작업이 필요합니다.

2질문 제기

3구조적 핵심 예시

4단계별 동작 과정

  1. 익스포터 선택--output 옵션에서 type 파라미터로 docker(기본, 이미지 저장소), registry(레지스트리), oci(OCI 레이아웃), tar(압축 파일), local(로컬 디렉터리) 중 선택합니다.
  2. 대상 지정과 추가 옵션type 뒤에 dest=<경로> 형태로 저장 위치를 지정하고, registry 익스포터일 때는 이미지 태그 지정, local 익스포터일 때는 권한 설정 등의 추가 옵션을 설정합니다.
  3. 빌드와 동시 내보내기docker buildx build 명령 하나로 빌드 완료와 동시에 지정된 형식으로 결과를 내보내며, 여러 익스포터를 조합하면 같은 빌드를 여러 형태로 동시에 내보낼 수 있습니다.

3구조적 핵심 예시

2질문 제기

볼륨 외에 다른 방식으로 데이터나 파일 시스템을 컨테이너에 연결할 수 있을까요?

3구조적 핵심 예시

호스트의 실제 경로를 컨테이너에 직접 연결하는 바인드 마운트 (-v /host/path:/container/path), 메모리에만 저장하는 tmpfs (--tmpfs /app/cache), 다른 이미지의 파일을 읽기 전용으로 붙이는 이미지 마운트 등 여러 방식이 있습니다.

4단계별 동작 과정

  1. 바인드 마운트호스트의 실제 디렉토리나 파일을 컨테이너 경로에 직접 연결합니다. 양쪽이 같은 파일을 공유하므로, 개발 중 호스트에서 코드를 수정하면 컨테이너 내에서 즉시 반영됩니다. 데이터 영속화는 보장되지만, Docker 관리 대상이 아니므로 백업 등은 수동으로 해야 합니다.
  2. tmpfs메모리에만 저장하는 임시 파일 시스템입니다. 캐시, 세션 데이터 같은 컨테이너가 실행되는 동안만 필요한 데이터나, 빠른 읽기쓰기가 중요한 경우에 사용합니다. 컨테이너가 끝나면 모든 데이터가 사라집니다.
  3. 이미지 마운트다른 이미지의 파일을 읽기 전용으로 현재 컨테이너에 붙입니다. 자주 갱신되는 데이터나 설정 파일을 공유 이미지에서 가져올 때 유용합니다.

1상대의 출발점 확인

마운트 방식이 여러 개(볼륨, 바인드 마운트, tmpfs, 이미지 마운트)인데, 각각 장단점이 다릅니다. 어떤 상황에 어떤 방식을 써야 할지 결정하기 어렵습니다. 특히 Docker Desktop 같은 데스크톱 환경에서는 호스트와 컨테이너 사이의 파일 공유 속도가 느려서 성능 문제가 생기기도 합니다.

2질문 제기

3구조적 핵심 예시

4단계별 동작 과정

  3. 실제 운영선택한 방식대로 마운트하고, 필요하면 성능 측정(파일 읽기쓰기 시간)을 해서 병목이 생기면 캐시 모드를 조정하거나 다른 방식으로 전환합니다.

  3. 시작 순서 제어depends_on 과 헬스체크를 조합해서, 선행 서비스가 "healthy" 상태가 되면 다음 서비스가 시작되고, 라이프사이클 훅(entrypoint 스크립트 등)으로 시작 직후·종료 직전 작업을 끼워 넣을 수 있다.

태그·푸시·풀과 멀티 아키텍처 매니페스트

이미지에 이름표(태그)를 붙여 레지스트리에 올리고(push) 내려받으며(pull), 하나의 태그로 여러 CPU 아키텍처용 이미지를 묶어 제공하는 방법.

1상대의 출발점 확인

로컬에서 만든 이미지는 그 컴퓨터에만 있다. 다른 팀원이나 서버에서 같은 이미지를 쓰려면 파일을 복사해야 하는데, 이미지는 크기가 크고 전달하기 어렵다. 또한 팀이 커지면 버전 관리가 복잡해진다. x86 아키텍처로 빌드한 이미지는 ARM 아키텍처(예: Mac M1, 라즈베리파이) 위에서 실행되지 않는 호환성 문제도 있다.

2질문 제기

로컬 이미지를 중앙 저장소에 올려서 누구나 내려받도록 하고, 여러 CPU 아키텍처를 하나의 이름으로 제공할 수는 없을까?

3구조적 핵심 예시

로컬 이미지에 docker tag myimage:latest myregistry/myimage:v1.0 으로 이름표(태그)를 붙인 뒤, docker push 로 Docker Hub 같은 중앙 레지스트리에 업로드한다. 다른 곳에서는 docker pull myregistry/myimage:v1.0 으로 내려받는다. 여러 아키텍처(amd64, arm64 등)용 이미지를 각각 빌드한 뒤 docker buildx build --push --platform linux/amd64,linux/arm64 로 한 번에 빌드·푸시하면, Docker Hub 의 매니페스트(manifest)가 이들을 하나의 태그 아래 묶어서, 클라이언트의 아키텍처에 맞는 이미지를 자동으로 선택하게 한다.

4단계별 동작 과정

  1. 이미지 태깅로컬에서 빌드한 이미지를 docker tag 로 레지스트리 주소·리포지토리명·버전 태그를 붙인다(예: docker.io/username/app:1.0).
  2. 푸시(업로드)docker push 로 태그된 이미지를 중앙 레지스트리에 업로드하고, 레지스트리가 레이어 단위로 저장해서 대역폭 절약을 도모한다.
  3. 멀티 아키텍처 배포여러 아키텍처용 이미지를 각각 빌드한 뒤 같은 태그로 푸시하면, 레지스트리의 매니페스트(manifest, 메타데이터)가 각 아키텍처별 이미지 ID를 기록해서, 풀(pull) 할 때 클라이언트의 CPU 아키텍처를 감지해 맞는 이미지를 자동으로 선택한다.

  2. 로컬 저장docker login을 실행할 때 username을 입력하고 password 자리에 토큰을 입력하면, 클라이언트는 토큰을 ~/.docker/config.json에 암호화하여 저장합니다.
  3. 자동 인증 사용docker push, docker pull 등의 명령어 실행 시 저장된 토큰으로 자동으로 인증되며, 개별 명령어마다 비밀번호를 입력할 필요가 없습니다.

  2. 보안 정보 확인보안 스캔 결과(vulnerabilities), 최근 업데이트 일자, Dockerfile 소스 코드 공개 여부를 검토합니다.

2질문 제기

4단계별 동작 과정

  2. 시스템 설정각 호스트의 /etc/docker/daemon.json(Linux) 또는 Docker Desktop 설정에서 registry-mirrors, insecure-registries, allowed-registries를 구성합니다.
  3. 접근 제한 적용docker pull 또는 docker push 실행 시 정책에 위배되는 레지스트리(예: 미승인 Docker Hub 계정)로의 접근은 차단되며, 승인된 레지스트리에서만 이미지를 가져올 수 있습니다.

컨테이너 격리의 한계와 데몬 공격 표면

컨테이너는 커널을 공유하는 격리일 뿐이라 VM 만큼 완전하지 않고, root 로 도는 데몬과 그 소켓이 가장 큰 공격 표면이 된다.

1상대의 출발점 확인

컨테이너는 가상 머신처럼 완전히 격리된 환경이라고 생각할 수 있습니다. 하지만 컨테이너는 호스트의 커널을 공유하는 프로세스 격리일 뿐입니다. 격리가 불완전하므로 커널 취약점을 이용한 탈출이 가능하고, Docker 데몬이 root 권한으로 실행되기 때문에 가장 큰 공격 표면(attack surface)이 됩니다.

2질문 제기

VM과 달리 커널을 공유하는 컨테이너에서 가장 큰 보안 위험은 어디일까?

3구조적 핵심 예시

컨테이너 내 프로세스가 호스트 커널의 취약점(예: CVE-XXXX-XXXXX 같은 보안 결함)을 이용하면 호스트의 커널 공간으로 탈출할 수 있고, Docker 데몬(dockerd)이 root로 실행되며 소켓(/var/run/docker.sock)을 통해 제어되기 때문에, 데몬 제어권 = 호스트 제어권이 됩니다.

4단계별 동작 과정

  1. 격리의 한계 이해컨테이너는 namespace(네임스페이스, 프로세스·네트워크·파일시스템 격리)와 cgroup(자원 제한)만으로 격리되며, 호스트와 같은 커널을 사용합니다.
  2. 데몬의 위험성Docker 데몬이 root 권한으로 실행되고, 컨테이너는 데몬과 통신하여 명령을 실행하므로, 데몬이 공격 대상이 되면 호스트 전체가 위험합니다.
  3. 탈출 경로컨테이너 내 공격자가 호스트 커널의 취약점을 이용하여 root 권한을 획득하거나 docker.sock에 접근하여 데몬을 제어할 수 있습니다.

Docker 데몬과 컨테이너는 기본적으로 root 권한으로 실행됩니다. 컨테이너 내 프로세스가 탈출하여 호스트 커널에 접근하면 곧바로 root 권한을 얻게 되고, 호스트 전체를 제어할 수 있게 됩니다.

2질문 제기

3구조적 핵심 예시

userns-remap(사용자 네임스페이스 리매핑) 설정을 통해 컨테이너 내 uid 0(root)을 호스트의 uid 100000 같은 일반 사용자로 매핑할 수 있고, Rootless 모드에서는 Docker 데몬 자체를 비특권 사용자로 실행하므로 탈출해도 호스트에서 일반 권한만 갖습니다.

4단계별 동작 과정

  1. 사용자 네임스페이스 리매핑 설정/etc/docker/daemon.json에서 "userns-remap": "dockermapuid" 같은 설정을 추가하고, 리매핑 대상 사용자를 만든 후 /etc/subuid, /etc/subgid에서 사용자 범위를 정의합니다.
  2. Rootless 모드 설정Docker Desktop의 설정에서 "Rootless mode" 옵션을 활성화하거나, Linux에서 dockerd-rootless-setuptool.sh 설치 스크립트를 실행하여 비특권 사용자로 데몬을 실행합니다.
  3. 권한 격리 효과컨테이너 내 root 프로세스가 호스트에서는 일반 사용자로 보이며, 탈출 시에도 호스트에서 파일 쓰기, 네트워크 바인드 등이 제한됩니다.

커널 보안 기능: capability·seccomp·AppArmor

1상대의 출발점 확인

컨테이너 프로세스는 기본적으로 필요한 모든 Linux capability(특권, 예: 네트워크 포트 바인드, 파일 소유권 변경)를 가지고 있고, 모든 시스템 콜(커널에 요청하는 작업들)을 호출할 수 있습니다. 악의적인 작동이나 버그로 인해 권한이 남용될 위험이 있습니다.

2질문 제기

컨테이너가 사용할 수 있는 시스템 기능과 시스템 콜을 커널 수준에서 최소한의 범위로 제한하려면?

3구조적 핵심 예시

Linux 커널은 세 가지 보안 메커니즘을 제공합니다. Capability는 특정 권한(포트 바인드, 파일 읽기 등)만 허용하고, seccomp(secure computing mode)는 호출 가능한 시스템 콜 목록을 화이트리스트로 제한하며, AppArmor는 프로파일(정책)로 파일 접근과 네트워크 권한을 관리합니다.

4단계별 동작 과정

  1. Capability 제한docker run --cap-drop으로 불필요한 권한을 제거(예: --cap-drop=NET_RAW는 raw 패킷 금지)하고, --cap-add로 필요한 권한만 추가합니다.
  2. seccomp 적용seccomp.json 프로필에서 호출을 허용할 시스템 콜 목록을 지정하고, docker run --security-opt seccomp=<profile>으로 프로필을 적용하여 정의되지 않은 시스템 콜은 차단합니다.
  3. AppArmor 정책 적용AppArmor 정책 프로필을 작성하여 파일 접근 범위(읽기, 쓰기, 실행), 네트워크 권한, 프로세스 신호 허용 여부를 정의하고, docker run --security-opt apparmor=<profile>으로 적용합니다.

→ 10-01 참조

1상대의 출발점 확인

Docker 데몬은 호스트의 모든 리소스를 제어하기 때문에 데몬 소켓에 접근하는 것은 곧 호스트에 root 권한으로 명령을 내리는 것과 같습니다. Unix 소켓(/var/run/docker.sock)이나 TCP 포트를 통해 원격에서 데몬에 접근할 때 인증이나 암호화가 없으면 누구든지 그 권한을 얻을 수 있게 됩니다.

2질문 제기

원격에서 Docker 데몬에 접근할 때 접근자가 실제로 신뢰할 수 있는 사람/시스템인지 확인하고, 그 연결이 감시되지 않도록 보호할 수 있을까요?

3구조적 핵심 예시

TLS(전송 계층 보안)를 사용하면 클라이언트와 데몬이 인증서를 서로 검증한 뒤 암호화된 채널로만 통신합니다. 클라이언트는 서버 인증서로 "이 데몬이 정말 신뢰하는 데몬인가"를 확인하고, 서버는 클라이언트 인증서로 "이 요청자가 허가된 사용자인가"를 확인합니다.

4단계별 동작 과정

  1. TLS 인증서 준비데몬과 클라이언트용 CA 인증서, 서버 인증서, 클라이언트 인증서를 생성하고 배포합니다.
  2. 데몬 설정daemon.json에서 tls 옵션을 활성화하고 인증서 경로를 지정해 TLS 통신만 수락하도록 설정합니다.
  3. 소켓 권한 및 인가Unix 소켓에 대한 파일 권한(chmod)으로 OS 수준에서 접근을 제한하고, 필요하면 인가 플러그인(authorization plugin)으로 어떤 작업을 허용할지 세밀하게 통제합니다.

5본질 요약

2질문 제기

이미지에 포함된 모든 컴포넌트가 무엇인지 목록화하고, 그 중 취약점을 자동으로 찾아서 배포 전에 막을 수 있을까요?

3구조적 핵심 예시

SBOM(Software Bill of Materials)은 이미지에 들어있는 패키지·라이브러리의 이름과 버전을 모두 기록한 목록입니다. Docker Scout는 이 SBOM을 생성한 뒤 공개 취약점 데이터베이스(CVE 데이터베이스)와 비교해서 "libc 2.31 버전에는 CVE-2021-XXXXX 취약점이 있다"는 식으로 알려줍니다.

4단계별 동작 과정

  1. SBOM 생성docker scout 명령이나 빌드 시점에 이미지의 모든 구성 요소를 스캔해 SBOM을 생성합니다.
  2. 취약점 조회Scout가 SBOM의 각 패키지를 CVE 데이터베이스와 매칭해 알려진 취약점 목록을 얻습니다.
  3. 정책 판정조직의 취약점 정책(예: 심각도 높음 이상이면 차단)에 따라 이미지 배포를 허용할지 거부할지 결정합니다.

3구조적 핵심 예시

4단계별 동작 과정

  1. SLSA 프로비넌스 생성빌드 시스템이 누가 무엇을 어떻게 빌드했는지의 메타데이터를 SLSA 형식으로 기록합니다.
  2. 서명과 어테스테이션 저장프로비넌스를 암호화 서명하고 이미지와 함께 Cosign, Notary 등의 도구로 레지스트리에 저장합니다.
  3. VEX 정책 적용취약점이 발견되어도 실제로 그 코드 경로가 실행되지 않으면 VEX(Vulnerability Exploitability Exchange)로 "이 CVE는 우리 이미지에 영향이 없다"고 선언하고, 검증자는 이를 신뢰할 수 있습니다.

  2. 로그 진단데몬이 시작되지 않거나 컨테이너 생성이 실패하면 로그에서 에러 메시지를 찾아 원인을 파악합니다.

정리와 리소스 관리: prune·라벨·디스크 사용량

쓰지 않는 이미지·컨테이너·볼륨·빌드 캐시를 prune으로 걷어내고 디스크 사용량을 확인하는 일.

1상대의 출발점 확인

컨테이너를 계속 만들고 이미지를 수정하면서 빌드 캐시, 중단된 컨테이너, 사용하지 않는 이미지, 고아 볼륨이 디스크에 쌓입니다. docker images, docker ps -a로 확인해도 수백 개의 항목을 일일이 삭제하는 것은 번거롭고, 어떤 것을 안전하게 지울 수 있는지 판단하기 어렵습니다.

2질문 제기

실행 중이지 않은 컨테이너, 사용되지 않는 이미지, 관련 없는 볼륨과 캐시를 한 번에 정리하면서 필요한 것까지 실수로 지우지 않을 수 있을까요?

3구조적 핵심 예시

docker system prune은 모든 중단된 컨테이너, 사용되지 않는 이미지, 사용되지 않는 네트워크, 사용되지 않는 볼륨을 조회한 후 "정말 지울까요?"라고 확인합니다. 라벨(docker run --label)을 사용해 "프로덕션 필수 이미지", "임시 테스트 컨테이너" 같이 태깅하면 prune 시 그것을 판단 기준으로 활용할 수 있습니다.

4단계별 동작 과정

  1. 라벨 지정이미지와 컨테이너를 만들 때 라벨을 붙여 용도를 표시합니다(예: lifecycle=temporary, environment=production).
  2. 정리 실행docker system prune, docker image prune, docker volume prune 등을 실행해 불필요한 항목을 삭제합니다.
  3. 디스크 사용량 확인docker system df로 이미지, 컨테이너, 볼륨, 빌드 캐시가 차지하는 공간을 확인하고 추가 정리 여부를 결정합니다.

5본질 요약

라벨과 prune 명령어로 불필요한 컨테이너·이미지·캐시를 안전하게 정리해 디스크 효율을 유지하는 것

공식 문서https://docs.docker.com/reference/cli/docker/system/prune/

Docker 컨텍스트와 Engine API·SDK

docker 명령이 바라볼 데몬을 컨텍스트로 전환하고, 같은 기능을 Engine API·SDK로 프로그래밍하는 방법.

1상대의 출발점 확인

기존에는 docker 명령으로만 Docker 데몬을 제어했다. 모든 docker 명령은 정해진 하나의 데몬과만 연결되었고, 다른 데몬을 쓰려면 환경 변수를 수정하거나 설정을 바꿔야 했다. 또한 명령줄에서만 Docker를 제어할 수 있었고, 프로그래밍 언어에서 Docker 기능을 호출하려면 다른 방법이 필요했다.

2질문 제기

Docker 명령줄 도구 없이, 또는 여러 데몬을 쉽게 오가며 Docker를 제어하는 방법이 있을까?

3구조적 핵심 예시

Docker는 HTTP 기반 API를 제공한다. docker 명령 자체도 내부적으로 이 API를 호출하는 것이다. 따라서 HTTP 요청을 직접 보내거나, 프로그래밍 언어용 SDK를 사용하면 명령줄 없이도 컨테이너를 관리할 수 있다. 동시에 컨텍스트를 사용하면 CLI에서 여러 데몬 사이를 자유롭게 전환할 수 있다.

4단계별 동작 과정

  1. 컨텍스트를 통한 데몬 관리CLI에서 여러 Docker 데몬의 연결 정보를 저장해두고 docker context use로 활성 데몬을 전환한다.
  2. Engine API를 통한 직접 호출Docker 데몬은 HTTP 소켓(보통 /var/run/docker.sock)에서 API 요청을 받고, curl이나 프로그래밍 언어로 직접 요청을 보낼 수 있다.
  3. SDK를 통한 추상화Python, Go, Node.js 등의 SDK는 HTTP API를 래핑(묶음)하여 프로그래밍 언어 문법으로 컨테이너를 조작할 수 있게 한다.

5본질 요약

Docker 데몬이 제공하는 HTTP API를 CLI 컨텍스트, 직접 호출, 언어별 SDK 등 다양한 방식으로 접근할 수 있게 하여, 명령줄 도구 없이도 여러 데몬을 자유롭게 제어할 수 있도록 하는 것

공식 문서https://docs.docker.com/engine/manage-resources/contexts/

Swarm 모드: 노드·서비스·태스크·라우팅 메시

여러 호스트를 하나의 클러스터로 묶어 서비스와 태스크로 컨테이너를 배치하는 Docker 내장 오케스트레이션.

1상대의 출발점 확인

기존에는 각 서버에서 개별적으로 docker run으로 컨테이너를 실행했다. 여러 서버를 운영할 때 어느 서버에 어느 컨테이너를 배치할지 직접 결정해야 했고, 컨테이너가 죽으면 수동으로 다시 띄워야 했다. 또한 컨테이너 간 통신이나 부하 분산도 별도로 설정해야 했다.

2질문 제기

여러 서버를 하나의 시스템처럼 관리하면서 컨테이너의 배치, 재시작, 통신을 자동으로 처리할 수 있을까?

3구조적 핵심 예시

Swarm은 여러 Docker 호스트(서버)를 클러스터로 묶고, 그 클러스터 위에 서비스(service)를 정의하면 자동으로 여러 서버에 컨테이너(태스크라고 부름)를 배치하는 오케스트레이션 시스템이다. 예를 들어 "웹 애플리케이션 3개 복사본을 실행"이라는 서비스를 정의하면 Swarm이 자동으로 3개의 태스크를 클러스터의 여러 노드에 분산시켜 배치한다.

4단계별 동작 과정

  1. 노드 클러스터링여러 Docker 호스트가 하나의 Swarm 클러스터에 참여하고, 매니저 노드가 전체 클러스터를 제어한다.
  2. 서비스 정의 및 배치사용자가 서비스(이미지, 복사본 수, 포트 등)를 정의하면 Swarm 스케줄러가 클러스터 내 노드들에 태스크(컨테이너 인스턴스)를 분산 배치한다.
  3. 자동 관리태스크가 실패하거나 노드가 종료되면 Swarm이 자동으로 다른 노드에 새 태스크를 시작해 원하는 복사본 수를 유지하고, 내장 라우팅 메시(라우팅 망)가 들어오는 요청을 모든 태스크로 분산한다.

5본질 요약

여러 Docker 호스트를 클러스터로 연결하고 서비스 단위로 컨테이너를 배치·관리하며 자동 부하 분산과 장애 복구를 제공하는 Docker 내장 오케스트레이션 시스템

공식 문서https://docs.docker.com/engine/swarm/

Swarm 운영: 클러스터 구성·서비스 배포·시크릿·스택

Swarm 클러스터를 실제로 만들고 서비스·시크릿·스택을 배포하며 롤링 업데이트로 운영하는 절차.

→ 11-06 참조

1상대의 출발점 확인

Swarm 클러스터의 개념을 알아도 실제로 어떻게 만들고 운영하는지는 별개다. 클러스터를 구성하는 절차, 서비스를 배포하는 방법, 데이터베이스 암호 같은 민감한 정보를 어떻게 안전하게 관리할지, 복잡한 애플리케이션을 여러 서비스로 어떻게 정의할지 등이 명확하지 않다.

2질문 제기

실제로 Swarm 클러스터를 구성하고 서비스를 배포하며, 민감한 정보와 복잡한 애플리케이션 구조를 어떻게 관리할까?

3구조적 핵심 예시

Swarm 운영은 세 가지 핵심으로 이루어진다. 먼저 docker swarm init과 docker swarm join으로 노드를 클러스터에 참여시킨다. 다음으로 docker service create로 서비스를 배포한다. 마지막으로 민감한 정보(비밀번호, API 키)는 docker secret으로 암호화하여 저장하고, 여러 서비스를 하나의 구성 파일(docker-compose.yml)로 정의하는 것을 스택(stack)이라 한다.

4단계별 동작 과정

  1. 클러스터 구성매니저 노드에서 docker swarm init으로 클러스터를 초기화하고, 워커 노드에서 docker swarm join으로 참여한다. 각 노드는 고유한 역할(매니저/워커)을 부여받는다.
  2. 서비스 배포 및 시크릿 관리docker secret으로 암호화된 민감한 정보를 저장한 후, docker service create 또는 docker-compose 파일에서 서비스를 정의할 때 시크릿을 참조하여 컨테이너 내에 안전하게 전달한다.
  3. 스택으로 복잡한 구성 운영여러 서비스, 네트워크, 볼륨을 하나의 docker-compose.yml 파일에 정의하고 docker stack deploy로 배포하면 Swarm이 전체 구성을 한 번에 클러스터에 배치하고 롤링 업데이트(서비스 중단 없이 단계적 업데이트)를 통해 업그레이드한다.

5본질 요약

Swarm 클러스터의 초기화부터 서비스 배포, 시크릿을 통한 보안 정보 관리, 스택을 통한 다중 서비스 오케스트레이션까지 실제 운영에 필요한 모든 절차를 제공하는 것
