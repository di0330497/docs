개발자가 애플리케이션을 컨테이너로 패키징해 만들고 실행·배포·운영하는 법을 한 경로로 묶는다. 대상(컨테이너·이미지·데몬) → 실습 환경 → 이미지 → 빌드(Dockerfile/BuildKit/Buildx/Bake) → 실행·저장·네트워크·로그 → 다중 서비스(Compose) → 배포 자동화·공급망 보안(Scout) → 다중 노드(Swarm)와 도구 확장. Engine 29 의 기본 저장 백엔드가 containerd 이미지 스토어로 바뀐 점과 Compose v2·v5 구분을 현재 기준으로 삼는다.

1Docker가 다루는 대상과 구조이후 모든 명령과 파일이 조작하는 대상(컨테이너·이미지·데몬)을 먼저 정해 두어야 그 뒤의 조작법이 의미를 갖는다.52설치와 CLI 첫걸음아는 것과 해 보는 것은 별개 기술이다. 실습 환경을 만들고 CLI 문법을 끝내야 이후 모든 명령이 재현 가능하다.53이미지와 레지스트리빌드와 실행의 결과물인 이미지가 어디에 오고 가는지를 알아야 그 다음의 빌드·배포 단계가 의미를 갖는다.64컨테이너 실행과 수명주기이미지를 아는 것과 이미지를 실행해 보는 것은 다르다. 컨테이너의 상태 전이와 실행 파라미터를 여기서 익힌다.55이미지 빌드 — Dockerfile레지스트리에서 받는 이미지를 만드는 법이 Dockerfile 이다. 레이어 구조를 이해해야 캐시·크기·보안 논리가 성립한다.76BuildKit 과 BuildxDockerfile 을 실제로 실행하는 엔진이 BuildKit 이고 그것을 조종하는 CLI 가 Buildx 다. 멀티 플랫폼·원격 빌드 같은 한계가 여기서 풀린다.67데이터 저장컨테이너는 휘발된다. 데이터를 어디에 두느냐가 곧 배포 설계가 되므로 마운트 종류와 저장 백엔드를 함께 다룬다.48네트워킹컨테이너를 서로 그리고 바깥과 잇는 방법이다. 게시 방식과 드라이버 선택이 곧 보안 설정이 된다.59로깅과 관측 가능성돌아가는 컨테이너의 안을 보려면 로그와 지표가 먼저다. 데몬 운영과 문제 해결도 같은 틀에서 다룬다.510Docker Compose컨테이너 하나로는 애플리케이션이 되지 않는다. 여러 컨테이너를 파일 하나로 정의해 함께 다룬다면이 여기서 나오고, 파일 형식의 세부 규칙이 뒤따라온다.811배포 자동화와 공급망 보안만든 이미지를 반복적으로 안전하게 배포하려면 레지스트리 운영·CI 연결·공급망 검증이 함께 필요하다. 기능 추가와 보안을 분리하지 않는다.712다중 노드 운영과 도구 확장단일 데몬의 한계를 넘어 분산 실행과 도구 확장을 다루는 마지막 단계. 오케스트레이션으로 넘어가기 직전의 지점이다.5

1단계 Docker가 다루는 대상과 구조

가상머신이 자체 커널까지 통째로 담는 것과 달리, 호스트 커널을 공유한 채 프로세스·파일시스템·네트워크만 격리해 훨씬 가볍게 뜨는 실행 단위.

1문제 상황

서버에 프로그램을 올리는 방식은 크게 두 가지였다. 가상머신은 하드웨어 위에 게스트 운영체제를 통째로 설치하고 그 위에 앱을 올리는 방식이라, 앱마다 OS 전체를 복제해 두 개나 켜야 했다. OS가 크고 부팅에 시간과 메모리가 많이 들기 때문에 같은 서버에 많은 앱을 올리면 자원이 빠르게 소진된다.

또한 앱이 돌아가는 환경은 서버마다 조금씩 달랐다. 라이브러리 버전과 설정 파일, 디렉터리 구조가 다르면 같은 코드가 배포한 곳에서 다르게 동작하거나 아예 실패한다. 매번 서버 환경을 손으로 맞추고 재현하는 비용이 그대로 팀의 부담이 된다.

2핵심 질문

앱마다 운영체제를 통째로 복제하지 않고도, 서버마다 다른 환경을 없애면서 실행할 독립된 공간을 만들 수 있을까?

3동작 예시

컨테이너는 호스트 OS의 커널(하드웨어와 프로세스·메모리·파일시스템을 다루는 핵심)을 공유한 채로, 앱 프로세스 하나와 그 프로세스에게 필요한 파일시스템·네트워크만 떼어낸다. 따라서 컨테이너마다 Linux 커널을 새로 깔지 않는다. 이 때문에 컨테이너 하나가 켜지는 시간과 차지하는 용량이 가상머신보다 훨씬 작고, 이미지에는 앱과 라이브러리만 담기 때문에 어디에서 실행해도 같은 파일 구성이 그대로 재현된다.

4동작 과정

  1. 격리컨테이너마다 PID·마운트 포인트·네트워크 인터페이스·호스트 이름이 분리되어, 컨테이너 안에서 본 프로세스 목록에는 자기 것만 보인다.
  2. 가상화cpu, memory, ipc, uts, mount 등 항목별로 격리 범위를 지정해 원하는 자원만 따로 떼어낸다.
  3. 제한프로세스가 사용할 수 있는 CPU와 메모리에 상한을 걸어서, 하나의 앱이 서버 자원을 다 먹고 다른 컨테이너를 멈추게 되는 일을 막는다.
  4. 실행이렇게 만든 프로세스를 이미지로 저장해 두고, 실행할 때마다 이미지를 읽기 전용 계층 위에 얹어 컨테이너를 하나씩 띄운다.

5한 줄 요약

호스트 커널을 공유하면서 프로세스·파일시스템·네트워크만 분리해 가볍게 뜨는 앱 실행 단위를 제공하는 것

개발 환경과 운영 환경의 차이로 인한 실행 불일치를 없애고, 앱의 패키징부터 배포·실행까지를 하나의 플랫폼으로 제공하는 것.

1문제 상황

개발자는 내 컴퓨터에서 코드를 짜고 테스트를 통과시킨 뒤 그 결과를 서버로 옮긴다. 그런데 서버에는 라이브러리 버전이 다르고 환경 변수가 빠져 있고 시스템 설정이 다르다. 결과적으로 개발 중에는 멀쩡했던 앱이 배포 직후 실패하거나, 반대로 운영 서버에서만 나는 버그를 재현하지 못하는 일이 반복된다.

이 문제는 배포할 때마다 발생한다. 서버마다 환경을 손으로 맞추는 방식은 그때그때 해결되지 재현되지 않는다. 환경을 문서로 남겨 공유해도 사람이 그 문서를 읽고 그대로 재현한다는 보장이 없다.

2핵심 질문

앱과 그에 필요한 환경 구성을 한 묶음으로 만들어 어디에서든 똑같이 실행하게 할 수 있을까?

3동작 예시

앱 소스, 라이브러리, 시스템 도구, 설정을 한 디렉터리 구조에 고정해서 정의해 둔다. 이 정의를 빌드하면 실행 가능한 패키지인 이미지가 나오고, 이 이미지는 어떤 서버로 옮겨도 내부 구성이 변하지 않는다. 그래서 개발자는 내 환경에서 통과한 결과를 그대로 운영 서버에 올리면 되고, 서버마다 설정을 손으로 맞추는 작업이 사라진다.

4동작 과정

  1. 개발컨테이너 안에서 코드를 작성하고 실행해, 내 컴퓨터에 별도 도구를 설치하지 않고 필요한 라이브러리만 붙여 쓴다.
  2. 패키징Dockerfile에 앱과 의존성을 선언해 이미지라는 단일 단위로 만든다. 이 파일이 곧 배포 산출물이다.
  3. 배포이미지를 레지스트리 같은 저장소에 올리고, 대상 서버에서 받아 같은 설정으로 컨테이너를 실행한다.
  4. 운영개발, 테스트, 운영이 같은 이미지에서 출발하므로 환경 차이로 인한 실행 불일치가 줄고, 문제 생기면 이미지 버전만 교체해 되돌린다.

1문제 상황

컨테이너를 다루는 일은 privileged 권한이 필요하고 커널과 깊이 엮여 있다. 앱 개발자가 이 명령들을 직접 다뤄야 한다면 명령마다 관리자 권한이 필요하고, 실수 하나가 호스트 전체에 영향을 준다. 그래서 컨테이너를 다루는 기능을 별도의 백그라운드 프로그램으로 분리해 두고, 사용자는 그 프로그램에 요청을 보내는 방식으로 만들어야 했다.

그러나 명령을 입력하는 사람과 실제로 권한을 갖고 커널을 조작하는 사람이 같은 프로세스일 필요는 없다. 둘을 분리하면 권한 관리가 쉬워지고, 같은 컨테이너를 여러 사용자와 여러 경로에서 동시에 다룰 수 있게 된다.

2핵심 질문

권한을 가진 별도 프로그램이 커널을 조종하고, 일반 사용자는 그 프로그램에 요청만 보내게 할 수 있을까?

3동작 예시

터미널에서 docker ps를 치면 소켓에 붙은 dockerd 데몬이 요청을 받는다. 데몬은 이 요청을 Engine API 호출로 바꿔 containerd에 내보내고, containerd는 OCI 런타임에 컨테이너를 실제로 만들라고 지시한다. 데몬이 죽지 않는 한 사용자는 데몬을 거치게 되므로, 데몬이 어떤 인증을 통과시키는지에 따라 접근 권한이 정해진다.

4동작 과정

  1. 클라이언트docker CLI 같은 클라이언트가 터미널 명령을 받아 소켓에 요청을 보낸다. 클라이언트 자체는 커널 권한이 없다.
  2. 데몬dockerd가 소켓 요청을 받아 명령을 해석하고, 호출에 대한 인증과 접근 제어를 이 지점에서 수행한다.
  3. API데몬은 명령을 Engine API 호출로 변환해 containerd로 전달한다. API는 이 요청·응답 형식 자체가 정해진 규격이다.
  4. 런타임containerd가 요청을 받아 OCI 런타임(runc 등)에 컨테이너 생성·실행을 지시하고, 생성된 컨테이너의 ID와 상태를 데몬에 돌려준다.

5한 줄 요약

권한 있는 데몬이 클라이언트의 요청을 API로 받아 런타임에 컨테이너 생성·실행을 지시하는 계층 분리 구조

앱과 의존성을 담은 이미지라는 실행 템플릿, 여기서 실제로 떠 있는 컨테이너, 통신을 잇는 네트워크, 데이터를 보존하는 볼륨이라는 기본 객체들의 모음.

1문제 상황

앱 하나를 돌리려면 코드, 런타임, 라이브러리, 설정 파일, 데이터 파일이 함께 있어야 한다. 이 묶음을 그대로 서버에 복사하면, 서버마다 남는 파일이 생기고 무엇이 필요한 것인지 알 수 없다. 반대로 필요한 것만 골라 담으려면 무엇이 필요한지 매번 판단해야 해서 재현이 어렵다.

또 하나의 앱 프로세스만으로는 여러 앱이 서로 같은 컴퓨터 자원을 두고 통신하고 데이터를 안전하게 보관하는 방법이 없다. 프로세스마다 설정을 따로 심고, 임시 파일이 서로 지워지거나 덮어써지는 상황을 막을 규칙이 필요했다.

2핵심 질문

앱이 실행에 필요한 모든 것을 목록처럼 고정해 담고, 그것을 여러 프로세스가 공유하면서도 서로 간섭하지 않게 할 방법은 무엇인가?

3동작 예시

이미지는 Dockerfile에 적은 명령을 순서대로 실행해 만든 읽기 전용 계층 묶음이다. 여기서 컨테이너를 하나 실행하면, 이미지 계층 위에 쓰기 가능한 상위 계층이 얹히고 그 부분만 변경된다. 두 컨테이너가 같은 이미지에서 떠도 쓰기 계층은 따로라 서로의 변경이 보이지 않는다. 영구히 남아야 하는 데이터는 컨테이너 밖의 볼륨에 두어 컨테이너를 지워도 유지된다.

4동작 과정

  1. 이미지앱 코드, 의존성, 런타임 도구를 계층 단위로 쌓은 읽기 전용 실행 템플릿. 태그를 붙여 이름을 관리한다.
  2. 컨테이너이미지 위에서 실제로 실행 중인 프로세스 단위. 이미지에 쓰기 계층을 얹은 것이 컨테이너이고, 컨테이너를 지우면 추가된 내용은 사라진다.
  3. 네트워크컨테이너에 이름 기반의 가상 주소를 부여해 컨테이너끼리 직접 통신하게 하고, 필요한 경우 외부로 내보낸다.
  4. 볼륨컨테이너 바깥의 별도 영역에 데이터를 저장해 컨테이너가 재생성돼도 데이터가 유지되게 한다.

5한 줄 요약

네임스페이스로 프로세스 자원을 격리하고, cgroups로 CPU·메모리를 제한하며, union 파일시스템으로 읽기 전용 이미지를 여러 계층에 겹쳐 보이는 기술.

1문제 상황

여러 앱을 한 컴퓨터에서 격리해 돌리려면, 각각 서로 다른 컴퓨터처럼 보여야 한다. 프로세스가 남의 것을 볼 수 없어야 하고, 각자 자기 파일만 봐야 하며, 각자의 네트워크 주소를 갖고 CPU와 메모리를 정해진 만큼만 써야 한다. 그런데 이 컴퓨터에는 이미 다른 프로그램이 돌고 있고, 그 프로그램까지 함께 돌아가야 한다.

즉 기존 컴퓨터의 구조를 고장 내지 않으면서, 그 안에서 여러 개의 서로 간섭하지 않는 실행 공간을 동적으로 만들어야 한다. 이걸 어플리케이션 계층에서 구현하려 하면 커널 영역까지 건드려야 해서 어렵다.

2핵심 질문

기존 커널을 건드리지 않고 여러 개의 독립된 실행 공간을 만들어 자원 사용량까지 제한할 수 있는가?

3동작 예시

네임스페이스는 커널이 프로세스를 열거하거나 경로를 해석하는 대상 자체를 바꿔 치는 단위다. 프로세스·마운트·네트워크·호스트 이름·사용자 ID를 각각 다른 네임스페이스로 보내면, 컨테이너 안의 프로세스는 자기 것만 볼 수 있다. cgroups는 그 안에서 프로세스가 소비할 수 있는 CPU 시간과 메모리 총량에 상한을 걸고, union 파일시스템은 여러 디렉터리를 하나의 경로에 겹쳐 보이게 만든다.

4동작 과정

  1. 격리네임스페이스로 프로세스 ID, 파일시스템 마운트, 네트워크 인터페이스, 호스트 이름, 사용자 ID를 각각 분리해 보이는 범위를 제한한다.
  2. 제한cgroups(control groups)로 각 컨테이너가 쓸 수 있는 CPU와 메모리에 상한을 두고, 한 컨테이너가 자원을 고갈시키는 것을 막는다.
  3. 파일시스템 구성union 파일시스템(overlayfs, union mount)은 여러 저장소를 하나의 마운트 지점에 겹쳐, 아래는 그대로 읽기 전용으로 두고 위에 쓰기 계층만 얹는다.
  4. 결합이 세 가지를 한 프로세스 묶음에 적용해 독립된 실행 단위를 만들고, 여기에 이미지 계층과 실행 설정을 얹어 컨테이너로 만든다.

리눅스 배포판의 공식 패키지 저장소를 등록해 Docker Engine(클라이언트와 데몬)을 설치하고, 데몬이 실제로 동작하는지 확인하는 것.

1문제 상황

리눅스 서버에 도구를 설치할 때, 필요한 파일을 wget으로 받아 설치하고, 의존 패키지를 직접 찾아 apt로 하나씩 넣고, 권한 설정을 손으로 조정하는 과정을 거쳤었다. 이 과정에서 공식 저장소가 아닌 곳에서 받은 파일을 쓰면 버전이 뒤섞이거나 출처를 알 수 없는 실행 파일이 시스템에 들어가게 된다.

게다가 설치가 끝났다고 곧바로 동작하는 것은 아니다. 컨테이너를 만들려면 커널 권한으로 동작하는 백그라운드 프로그램이 실제로 기동하고 소켓을 열어 두어야 하는데, 방금 막 설치한 상태에서는 이것이 확인되지 않는다. 설치 명령을 실행하는 것과 도구가 실제로 돌아가는 것은 별개의 문제다.

2핵심 질문

공식 출처만으로 도구를 설치하고, 그것이 실제로 동작하는지 바로 확인할 수 있는 가장 짧은 경로는 무엇인가?

3동작 예시

배포판 공식 패키지 저장소를 시스템에 등록한 뒤, 그 저장소에서 Docker Engine 패키지를 설치한다. 설치 직후 컨테이너 하나를 띄우는 명령을 실행해 제대로 되는지 본다. 이 명령이 정상적으로 컨테이너 ID와 이미지를 출력하면 패키지 설치, 데몬 기동, 소켓 권한, 커널 지원이 모두 맞다는 뜻이므로 별도로 설정값을 뒤질 필요가 없다.

4동작 과정

  1. 저장소 등록배포판 공식 Docker 패키지 저장소 키를 등록하고, 그 저장소를 패키지 설치 대상 목록에 추가해 이후 설치가 이 경로에서만 이루어지게 한다.
  2. 패키지 설치Docker Engine 패키지를 설치하면 CLI 클라이언트와 dockerd 데몬이 함께 들어온다. 데몬은 부팅 시 자동 시작되도록 등록된다.
  3. 기동 확인데몬이 살아 있는지와 소켓에 연결할 수 있는지를 확인하고, 필요하면 데몬에 접속할 수 있는 사용자 그룹에 현재 계정을 넣는다.
  4. 스모크 테스트hello-world 같은 작은 이미지를 받아 컨테이너를 하나 실행해 설치가 정상인지 확인한다.

5한 줄 요약

Mac·Windows·Linux에 Docker Engine과 Docker Compose, Kubernetes 등을 묶어 GUI로 설치하고 관리하는 데스크톱 애플리케이션.

1문제 상황

리눅스에서는 Docker Engine을 명령어만으로 설치해 바로 쓸 수 있다. 그러나 개발자의 주 작업 환경은 Mac이나 Windows이고, 두 운영체제에서는 가상머신을 통해 리눅스 커널을 빌려 쓰지 않으면 컨테이너가 돌아가지 않는다. 그 가상머신은 다른 앱처럼 설치하고 켜고 끄고, 파일을 공유하고, 메모리와 CPU 자원을 따로 설정해야 한다.

여기에 컨테이너를 여러 개 함께 정의해 한 번에 띄우는 Compose 같은 도구, 여러 머신에 컨테이너를 펼쳐 놓는 Kubernetes 같은 도구까지 따로 설치해 관리해야 한다. 설치 대상과 관리 대상이 여러 개로 늘어나고, 서로 버전이 어긋나면 조합해서 쓰는 흐름이 끊긴다.

2핵심 질문

리눅스가 아닌 데스크톱에서도 리눅스 커널 기반 컨테이너를 쓰고, 여러 도구를 한곳에서 관리하려면 어떻게 해야 하는가?

3동작 예시

데스크톱 애플리케이션을 설치해 실행하면, 안에 포함된 리눅스 가상머신(Linux VM)이 자동으로 기동되고 그 안에서 Docker Engine이 돌아간다. 이때 호스트 파일 시스템의 일부 경로를 가상머신과 공유 처리해 두면, 호스트의 소스 코드가 별도 복사 없이 그대로 컨테이너에 마운트되어 편집 결과가 즉시 반영된다. Docker Compose와 Kubernetes 관련 도구도 같은 앱 안에서 켜고 끌 수 있다.

4동작 과정

  1. 앱 설치배포판용 설치 파일을 내려받아 애플리케이션을 설치하고, 최소 운영체제 요건을 확인한다.
  2. 가상머신 기동앱이 시작되면 내장된 리눅스 가상머신이 자동으로 올라오고, 그 안에서 Docker Engine이 백그라운드로 동작한다.
  3. 리소스 설정설정 화면에서 메모리, 디스크, CPU 자원을 정하고, 이미지 저장 위치를 지정한다. 기본값이 부족하면 빌드가 느려지므로 미리 조정한다.
  4. 파일 공유호스트와 가상머신 사이에서 공유할 경로를 지정해, 소스 디렉터리를 마운트 없이 바로 작업할 수 있게 한다.
  5. 구성요소 관리Compose와 Kubernetes를 켜고 끄는 스위치, 자동 시작 옵션, 로그 확인 기능을 같은 앱 안에서 설정한다.

5한 줄 요약

리눅스 가상머신 위의 Docker Engine을 내장해 Mac·Windows·Linux에서 컨테이너와 관련 도구를 한 앱으로 설치하고 관리하게 하는 것

첫 컨테이너 실행: docker run 이 한 일

docker run 한 번으로 이미지 다운로드, 컨테이너 생성, 시작, 기본 명령 실행까지 한꺼번에 이어지는 동작.

1문제 상황

어떤 프로세스를 띄우려면 매번 그 프로세스가 필요로 하는 라이브러리를 설치하고 설정 파일을 배치한 다음 시작 명령을 실행해야 합니다. 같은 앱이라도 실행 머신마다 준비 순서와 버전이 달라 결과가 재현되지 않고, 한 머신에 설치가 쌓이면 서로 다른 앱의 라이브러리가 서로를 덮어씁니다.

2핵심 질문

실행에 필요한 환경과 설정을 미리 하나로 정리해 두고, 그 상태 그대로 한 번의 명령으로 프로세스를 띄울 수 있을까요?

3동작 예시

docker run -it --name web nginx:1.27 을 실행하면, 로컬에 nginx:1.27 이미지가 없을 때 레지스트리에서 내려받고, 이름이 web 인 컨테이너를 만들어 그 안에서 nginx 를 시작시킵니다. -i 와 -t 는 입력을 열고 pseudo-tty(입력을 주고 출력을 실시간으로 보는 터미널 장치)를 붙이라는 뜻이고, 끝에 적은 nginx 는 실행할 프로세스 이름입니다.

4동작 과정

  1. 이미지 확보지정한 이름과 태그의 이미지가 로컬에 없으면 레지스트리에서 받아 옵니다. 있으면 다시 받지 않습니다.
  2. 컨테이너 생성이미지의 파일 계층에 쓰기 가능한 저장 공간과 격리된 실행 환경(네트워크·프로세스 namespace 등)을 얹어 컨테이너를 만듭니다. --name 으로 이름을 정하고 -p 로 포트를 연결합니다.
  3. 시작과 기본 명령 실행컨테이너를 시작하면서 이미지 설정에 지정된 프로세스를 실행합니다. -d 를 붙이면 백그라운드로 돌고, 명령 뒤에 인자를 주면 그 인자로 프로세스를 실행합니다.

5한 줄 요약

필요한 환경과 실행 설정을 이미지에 묶어 두고, docker run 한 번으로 그 상태를 만들어 프로세스를 띄우는 것

Docker 컨텍스트로 여러 데몬 다루기

데몬 접속 정보(엔드포인트·TLS 등)를 이름 붙은 프로필로 저장해, 하나의 docker 클라이언트를 여러 로컬·원격 데몬 사이에서 전환해 쓰는 것.

1문제 상황

docker 명령은 기본으로 로컬 데몬에 붙습니다. 원격 머신의 데몬을 쓰려면 접속 주소와 TLS 인증서 정보를 환경변수로 매번 지정해야 하고, 다시 로컬로 돌아오려면 그 설정을 해제해야 합니다. 어느 데몬에 붙어 있는지 매번 확인하지 않으면 엉뚱한 데몬에 컨테이너를 만들거나 지우는 사고가 납니다.

2핵심 질문

여러 로컬·원격 데몬의 접속 정보를 이름 붙은 프로필로 저장해 두고, 명령 하나로 대상을 갈아탈 수 있을까요?

3동작 예시

docker context create prod --docker "host=tcp://10.0.0.5:2376" 를 실행하면 접속 정보가 prod 라는 이름의 프로필로 저장됩니다. 그다음 docker context use prod 를 치면 이후 docker 명령이 전부 10.0.0.5 의 데몬으로 갑니다. docker context use default 로 되돌리면 다시 로컬 데몬을 씁니다.

4동작 과정

  1. 컨텍스트 생성docker context create 가 엔드포인트, TLS 인증서 경로, 네임스페이스 등 접속 정보를 이름 붙은 프로필로 저장합니다. 내부적으로 ~/.docker/contexts 아래에 JSON 파일로 쌓입니다.
  2. 컨텍스트 전환docker context use <이름> 이 기본 대상을 바꿉니다. 클라이언트는 하나 그대로 두고 연결 대상만 갈아타기 때문에 명령어마다 접두어를 붙일 필요가 없습니다.
  3. 현재 상태 확인docker context ls 가 프로필 목록과 현재 쓰 중인 이름을 * 로 표시하고, docker context inspect 가 저장된 접속 정보를 그대로 보여줍니다. docker context rm 으로 쓰지 않는 프로필을 지웁니다.

5한 줄 요약

데몬 접속 정보를 이름 붙은 프로필로 저장해 두고, 현재 대상을 명령 하나로 전환해 여러 데몬을 같은 클라이언트로 다루는 것

앱을 어떤 머신에서든 똑같이 띄우려면 실행 파일, 라이브러리, 런타임, 설정 파일이 함께 전달되어야 합니다. 이 목록을 수동으로 관리하면 어떤 항목이 빠졌는지 알 수 없고, 다른 머신에서는 다시 설치해야 하며, 목록을 어디에 저장할지 정하는 것 자체가 부담이 됩니다.

2핵심 질문

앱 실행에 필요한 파일과 설정을 하나로 묶어, 어디에서나 같은 상태로 꺼내 컨테이너를 띄울 수 있게 만들 수 있을까요?

3동작 예시

nginx:1.27 이미지를 받으면 그 안에는 웹 서버 실행 파일, 설정 파일, 로그가 쌓일 디렉터리 구조, 참조 라이브러리가 이미 들어 있습니다. 이 읽기 전용 상태를 그대로 컨테이너로 띄우면 별도 설치 없이 웹 서버가 실행됩니다.

4동작 과정

  1. 선언이미지 빌드 지시서인 Dockerfile 에 Base Image(컨테이너가 출발하는 OS·언어 런타임), 복사할 파일, 환경 변수, 실행할 명령, 노출할 포트를 적습니다.
  2. 빌드docker build 가 선언대로 파일을 복사하고 명령을 실행한 결과를 레이어로 쌓아 최종 이미지를 만듭니다. 이미지는 태그 이름을 붙여 로컬에 저장됩니다.
  3. 실행이미지는 읽기 전용 템플릿이고, 실제로 실행되며 파일을 바꿀 수 있는 객체가 컨테이너입니다. 같은 이미지에서 컨테이너를 여러 개 띄워도 원본 이미지 내용은 변하지 않습니다.

이미지 레이어와 크기

이미지는 파일 변화가 기록된 읽기 전용 레이어가 순서대로 쌓인 구조이고, 이미지 크기는 그 레이어 크기의 합입니다.

→ 03-01 참조

1문제 상황

환경이 조금 바뀔 때마다 전체를 다시 만들어 처음부터 보내고 받는 것은 비효율적입니다. 그런데 이미지를 단일 파일로 다뤄야 한다면 이 증분 갱신이 불가능합니다. 결과적으로 빌드 시간과 배포 시간은 그대로이고, 같은 내용을 여러 번 저장해 공간도 낭비됩니다.

2핵심 질문

바뀐 부분만 새로 만들어 보내고 나머지는 이미 있는 것을 그대로 재사용할 수 있을까요?

3동작 예시

Dockerfile 에서 RUN apt-get install -y nginx 위쪽 부분은 그대로 두고 아래 설정 한 줄만 고쳤다고 합시다. 빌드하면 위쪽 명령에 해당하는 레이어는 앞선 빌드와 동일하므로 그대로 가져오고, 고친 줄 이후의 레이어만 새로 쌓아 이미지가 다시 만들어집니다.

4동작 과정

  1. 명령 하나가 레이어 하나Dockerfile 의 각 명령(FROM, RUN, COPY, ENV 등)이 실행 결과를 기록한 읽기 전용 레이어가 되고, 위에서부터 순서대로 쌓입니다. 이미지 크기는 이 레이어 크기의 합이며, 파일 전체를 통째로 복사할 때보다 작은 변화만으로 갱신됩니다.
  2. 캐시로 재사용앞 레이어가 같으면 그 다음 명령을 실행하지 않고 만들어진 레이어를 그대로 씁니다. 그래서 명령 순서를 바꾸면 그 아래 레이어는 전부 다시 쌓입니다.
  3. 레벨별로 전송이미지를 보낼 때 클라이언트가 레이어 해시를 비교해 없는 레이어만 레지스트리로 보내고, 받을 때도 없는 레이어만 받습니다. 같은 레이어는 서버와 로컬에 이미 있으므로 다시 오가지 않습니다.

컨테이너는 생성(create)·시작(start)·정지(stop)·삭제(rm) 같은 상태를 거치며, 재시작 정책을 지정해 두면 데몬이 다시 뜨거나 예기치 않게 끝난 뒤에도 컨테이너가 알아서 다시 시작된다.

1문제 상황

컨테이너를 하나 실행하면 그것은 살아 있지만, 이 프로세스가 죽으면 그대로 끝난다. 서버를 재부팅하거나 예기치 않게 프로세스가 종료되면 컨테이너는 시작된 상태로 남지 못하고, 다시 켜는 과정을 매번 사람이 반복해야 한다. 그 사이에는 요청을 받을 수 없는 시간이 생긴다.

2핵심 질문

컨테이너가 끝났거나 Docker 엔진이 다시 시작됐을 때, 내가 다시 켜지 않아도 의도한 프로세스가 계속 실행되게 할 수 있는가?

3동작 예시

docker run -d --restart unless-stopped web-api 로 웹 서버 컨테이너를 띄운다. 이 컨테이너가 스스로 죽으면 엔진이 곧바로 다시 시작하고, Docker 엔진이 재부팅된 뒤에도 엔진이 올라오면서 컨테이너를 자동으로 다시 시작한다. 사람이 직접 docker stop 으로 멈춘 경우에만 다시 뜨지 않는다.

4동작 과정

  1. 생성(create)이미지로부터 쓰기 가능한 컨테이너를 만들기만 하고, 아직 프로세스를 띄우지 않는다. docker create 로 따로 호출할 수 있다.
  2. 시작(start)·정지(stop)·삭제(rm)start 가 첫 프로세스를 실행하고, stop 은 시그널을 보내 정상 종료시킨 뒤 rm 이 컨테이너를 지운다. 삭제는 이미지를 지우지 않으므로 컨테이너만 재생성하면 다시 실행된다.
  3. 재시작 정책--restart always, on-failure, unless-stopped 처럼 정책값을 붙여 두면 엔진이 상태 변화를 감시해 정책에 맞는 시점에 컨테이너를 다시 시작한다.

1문제 상황

이미지에는 실행 명령, 환경변수, 작업 디렉터리 같은 값이 미리 정해져 있다. 같은 이미지 하나로 개발용, 시험용, 운영용 컨테이너를 띄우려면 매번 다른 설정이 필요하다. 이미지를 목적별로 다시 빌드하면 같은 내용에 이름만 다른 이미지가 쌓이고, 무엇이 달라졌는지 추적이 어려워진다.

2핵심 질문

이미지를 다시 만들지 않고, 실행할 때마다 다른 값만 바꿔서 같은 이미지를 원하는 설정의 컨테이너로 실행할 수 있는가?

3동작 예시

python:3.12 이미지의 기본값이 실행 명령 python, 환경변수 MODE=dev, 작업 디렉터리 /app 라고 하자. docker run -e MODE=prod -w /srv -u app python:3.12 python app.py 라고 치면 이미지에는 손대지 않고 실행 명령을 python app.py 로, 환경변수를 MODE=prod 로, 작업 디렉터리를 /srv 로, 실행 사용자를 app 로 덮어쓴 컨테이너가 시작된다.

4동작 과정

  1. 기본값 확인이미지 빌드 때 지정한 CMD(실행 명령), ENV(환경변수), WORKDIR(작업 디렉터리), USER(실행 사용자) 등이 컨테이너의 기본값이 된다.
  2. 옵션으로 덮어쓰기docker run 뒤에 -e(환경변수), -w(작업 디렉터리), -u(사용자), -p(포트), -v(볼륨) 같은 옵션을 붙여 해당 항목만 원하는 값으로 바꿔 실행한다.

Dockerfile 지시문

Dockerfile 은 FROM·RUN·COPY 같은 지시문으로 이미지 구성 방법을 적는 텍스트 파일이며, 각 지시문은 앞선 단계 위에 레이어 하나씩을 쌓아 이미지를 만든다.

1문제 상황

기존에는 이미지에 라이브러리를 넣거나 설정을 바꿀 때마다 명령을 손으로 실행하고, 바뀐 부분 전체를 다시 만들어야 했다. 이때 어떤 파일이 어떤 순서로 들어갔는지 기록하기 어려워 같은 이미지를 다시 만들면 결과가 달라졌다.

2핵심 질문

이미지를 구성하는 모든 단계를 텍스트로 남겨, 같은 지시문을 실행하면 언제나 같은 이미지가 만들어지게 할 수 있을까?

3동작 예시

FROM node:20 으로 시작해 WORKDIR /app 으로 작업 위치를 잡고, COPY package.json . 로 파일 하나만 복사한 뒤 RUN npm ci --omit=dev 로 의존성만 설치한다. 이어서 COPY . . 으로 나머지 소스를 넣고 CMD ["node","server.js"] 를 적으면, 이 이미지 안에서 지정한 명령이 기본 실행 대상이 된다.

4동작 과정

  1. 베이스 지정FROM 으로 기반이 되는 이미지를 고른다. 여기서 없는 파일과 명령어가 전부 들어 있으므로 시작점이 결정된다.
  2. 설정과 복사WORKDIR·ENV·ARG 로 작업 위치와 환경값을 정하고, COPY·ADD 로 컨텍스트 안의 파일을 복사한다.
  3. 설치와 실행 명령RUN 으로 패키지를 설치하고, ENTRYPOINT 와 CMD 로 컨테이너가 뜰 때 실행할 명령을 지정한다.

Go 로 만든 서버를 빌드한다고 하자. 첫 번째 단계에서 FROM golang AS build 로 빌드 도구가 있는 이미지를 쓰고 소스를 복사해 바이너리 하나를 만든다. 두 번째 단계에서는 FROM alpine 로 바꿔 그 바이너리만 복사한다. 컨테이너에서 실제로 실행되는 것은 두 번째 단계에 들어 있는 파일뿐이고, 첫 단계의 컴파일 도구는 이미지에 남지 않는다.

4동작 과정

  1. 빌드 단계컴파일러가 있는 베이스 이미지에서 소스를 조립해 결과물이나 의존성 모음을 만든다. 이 단계는 중간 결과일 뿐 최종 이미지에 포함되지 않는다.
  2. 베이스 이미지 교체실행 전용 베이스 이미지를 FROM 으로 다시 지정해, 이전 단계의 파일 중 필요한 것만 가져올 시작 상태를 만든다.
  3. 결과물 이월빌드 단계가 만든 산출물을 새 베이스 이미지로 복사해, 실행 환경에 필요한 최소 구성만 담긴 이미지를 완성한다.

5이미지 빌드 — Dockerfile05-04

빌드 변수와 빌드 시크릿

빌드 변수는 ARG·ENV 로 빌드 시점에 값을 받아 Dockerfile 을 재사용하게 하고, 빌드 시크릿은 RUN --mount=type=secret 으로 비밀값을 이미지 기록 없이 빌드 중에만 제공하는 기능이다.

1문제 상황

서로 다른 환경에서 같은 Dockerfile 을 쓰려면 버전이나 서버 주소를 소스에 박아넣어야 했고, 이를 바꿀 때마다 파일을 수정해야 했다. DB 비밀번호 같은 값을 Dockerfile 에 적으면 그 값이 이미지 기록과 로그에 남을 위험이 있었다.

2핵심 질문

환경에 따라 달라지는 값은 빌드 시점에 받아쓰고, 비밀값은 이미지 기록에 남지 않게provide할 수 있을까?

3동작 예시

ARG APP_VERSION 을 선언하고 빌드할 때 APP_VERSION=1.4.0 을 넘기면 이후 지시문에서 그 값을 쓸 수 있다. DB 비밀번호는 RUN --mount=type=secret,id=db_pwd 로 빌드 중 그 순간에만 파일로 전달받아 명령에 넣고 쓰고, ENV 로 남기지 않으므로 이미지 기록에 비밀번호가 저장되지 않는다.

4동작 과정

  1. ARG 로 빌드 값 받기ARG 로 선언한 이름은 docker build --build-arg 로 넘긴 값으로 채워져, RUN 과 COPY 안에서 $NAME 으로 참조된다. 선언한 단계 안에서만 유효하다.
  2. ENV 로 실행 값 고정ENV 로 지정한 값은 빌드가 끝난 뒤 컨테이너 실행 중에도 남으므로, 실행 시점에도 필요한 설정에 쓴다.
  3. 시크릿 마운트로 비밀 전달RUN --mount=type=secret 지시문은 빌드 단계에서만 지정한 비밀 파일을 붙여준다. 값은 그 명령이 끝나면 사라지고 이미지 계층에 기록되지 않는다.

5한 줄 요약

ARG·ENV 로 빌드 시점 값을 받아 재사용하고, 시크릿 마운트로 비밀값을 이미지 기록 없이 빌드 중에만 제공하는 것

멀티 플랫폼 빌드는 하나의 Dockerfile 로 여러 CPU 아키텍처용 이미지를 만들어 하나의 매니페스트 리스트로 묶는 것으로, Buildx 의 --platform 과 QEMU 에뮬레이션을 사용한다.

1문제 상황

하나의 CPU 아키텍처용 이미지를 그대로 다른 아키텍처 서버에 옮기면 실행 파일 형식이 맞지 않아 뜨지 않는다. 아키텍처별로 Dockerfile 을 따로 관리하면 같은 내용을 여러 벌로 유지해야 하고, 배포 대상도 헷갈렸다.

2핵심 질문

Dockerfile 하나만으로 여러 CPU 아키텍처에서 실행되는 이미지를 만들어 한 이름으로 배포할 수 있을까?

3동작 예시

ARM64 개발 노트북에서 amd64 서버용 이미지를 만들 때, 빌더가 RUN 명령을 네이티브 amd64 환경에서 돌려 실제 파일을 만든다. 이 방식을 에뮬레이션이라고 하며, 지정한 아키텍처 목록 전체에 대해 빌드한 결과를 하나의 매니페스트 리스트에 묶어 저장한다. 나중에 pull 하면 실행 중인 서버의 아키텍처에 맞는 항목이 선택된다.

4동작 과정

  1. 빌더 생성docker buildx create 로 여러 플랫폼을 동시에 빌드할 수 있는 빌더를 준비하고, 이 빌더에 여러 노드를 연결해 나눠 처리하게 한다.
  2. 플랫폼 지정 실행--platform linux/amd64,linux/arm64 을 주면 지정한 아키텍처에 맞춰 각 아키텍처용 계층을 생성한다. 네이티브가 아닌 대상은 QEMU 에뮬레이션으로 처리한다.
  3. 매니페스트 병합만들어진 여러 아키텍처 이미지를 매니페스트 리스트(여러 플랫폼을 담은 하나의 참조 단위)로 묶어 레지스트리에 올린다.

  3. 원인 추적수집된 진행 기록을 OpenTelemetry 형식 트레이스로 내보내 다른 관측 도구에서 조회하거나, 빌드 진행 로그에서 실패한 지시문 직전 상태를 확인해 원인을 찾는다.

6BuildKit 과 Buildx06-01

BuildKit 이란 무엇인가

BuildKit 은 Dockerfile 의 지시를 실제로 실행해 컨테이너 이미지를 만들어 내는 빌드 엔진으로, Docker 빌드가 기본으로 사용하는 실행 주체입니다.

1문제 상황

과거 Docker 의 빌드는 docker daemon 안에 내장된 클래식 빌더가 Dockerfile 을 한 줄씩 순서대로 실행해 이미지를 만들었다. 여러 빌드 단계를 지정해도 이들을 동시에 실행하지 못하고 앞 단계 결과가 없으면 다음 단계도 진행하지 못했다. 만들어진 레이어는 daemon 내부에만 있어 다른 머신이나 CI 에서 재사용할 방법이 없었고, 빌드 옵션도 명령줄 인자로 제한적으로만 바꿀 수 있었다.

2핵심 질문

Dockerfile 지시를 더 빠르게 병렬로 실행하고, 결과를 다른 환경에서도 재사용하도록 해 주는 빌드 엔진을 따로 둘 수 있는가?

3동작 예시

어떤 Dockerfile 에서 의존성 설치와 프론트엔드 빌드가 나란히 있다고 하자. 클래식 빌더는 의존성 설치가 끝나야 프론트엔드 빌드를 시작해 두 작업을 순서대로 기다린다. BuildKit 은 각 단계가 실제로 읽는 파일 목록을 먼저 비교해 그 파일이 바뀌지 않았으면 이전에 만들어 둔 중간 결과를 그대로 복원하고, 바뀌었으면 그 단계만 다시 실행한다. 서로 다른 파일을 읽는 두 단계는 동시에 실행할 수 있어 전체 빌드 순서가 의존 관계에 따라 다시 배치된다.

4동작 과정

  1. Dockerfile 파싱FROM, RUN, COPY 같은 지시를 읽어 단계와 단계 사이의 선후 관계를 그래프 형태로 만든다.
  2. 단계 실행같은 입력으로 이미 만들어진 결과가 캐시에 있으면 재사용하고, 없으면 직접 실행한다. 서로 의존하지 않는 단계는 병렬로 돌린다.
  3. 결과 조립만들어진 단계를 이미지 레이어로 이어 붙여 최종 이미지를 출력한다.

Dockerfile 지시를 그래프로 쪼개 병렬 실행하고 그 결과를 재사용 가능하게 만드는 빌드 엔진

Buildx 빌더와 드라이버

Buildx 는 빌드를 요청하는 CLI 클라이언트이며, 빌드를 수행하는 BuildKit 인스턴스(빌더)와 그 인스턴스를 어떤 환경에서 띄우는지를 정하는 드라이버의 조합으로 동작합니다.

2핵심 질문

빌드를 요청하는 도구와, 실제로 빌드를 수행하는 인스턴스, 그리고 그 인스턴스를 어디에 띄울지를 분리해 지정할 수 있는가?

3동작 예시

CI 서버에서 docker buildx create --driver docker-container --name builder --use 를 한 번 실행하면 빌더 하나가 만들어져 이름으로 저장된다. 이후 docker buildx build --builder builder --platform linux/amd64,linux/arm64 . 는 그 빌더를 찾아 지정한 플랫폼들의 이미지를 만든다. 같은 빌더를 원격 드라이버에 연결된 환경으로 만들면 동일한 명령이 그 환경에서 실행된다. 드라이버를 바꾸는 것은 빌드를 수행하는 장소만 바꾸고, Dockerfile 지시와 옵션은 그대로 유지된다.

4동작 과정

  1. Buildx 클라이언트빌드 요청과 옵션(플랫폼, 출력 방식, 캐시 설정 등)을 받아 빌더로 전달하는 CLI 기능.
  2. 빌더(BuildKit 인스턴스)실제로 빌드를 수행하는 프로세스. 생성해 이름을 붙여 저장하고 여러 개를 나란히 두어 골라 쓸 수 있다.
  3. 드라이버빌더를 어떤 환경에 띄울지 정하는 값으로, docker, docker-container, kubernetes, remote 등을 지정한다.

6BuildKit 과 Buildx06-03

빌드 캐시 백엔드

빌드 캐시 백엔드는 BuildKit 이 만든 레이어 캐시를 로컬 디렉터리나 레지스트리, S3 같은 외부 저장소에 보관하고 다음 빌드에서 다시 불러오게 하는 저장 위치를 말합니다.

1문제 상황

로컬에서 쌓인 빌드 캐시는 그 머신에만 남아, 다른 개발자의 PC나 CI 러너로 넘어가면 한 번도 쓰이지 못했다. 같은 Dockerfile 을 빌드할 때마다 모든 단계를 처음부터 다시 실행했고 빌드 시간은 그대로 늘었다. 캐시를 어디에 얼마나 보관할지, 다른 머신에서 그 결과를 어떻게 가져올지를 지정할 방법도 없었다.

2핵심 질문

빌드 단계의 중간 결과물을 로컬 전용이 아닌 다른 머신과 다른 런타임에서도 공유하는 저장소에 두고 재사용할 수 있는가?

3동작 예시

빌드를 시작할 때 BuildKit 은 Dockerfile 의 각 RUN, COPY 지시와 빌드 컨텍스트 파일 목록을 해시해 단계마다 고유한 키를 만든다. 그 키를 캐시 백엔드에 넘겨 해당 단계의 레이어가 이미 저장돼 있는지 물어보고, 있으면 그대로 가져와 재사용하고 없으면 새로 실행한 뒤 그 결과를 같은 키로 저장한다. 백엔드를 이미지 레지스트리에 두면 여러 러너가 하나의 저장소를 공유하므로, 팀원 중 누가 이미 만들어 둔 단계를 그대로 이어받는다.

4동작 과정

  1. 캐시 키 계산Dockerfile 의 지시와 빌드 컨텍스트 파일 내용을 해시해 단계마다 고유한 키를 만든다.
  2. 백엔드 조회지정된 저장소(로컬 디렉터리, 레지스트리, S3 같은 외부 저장소)에서 키에 해당하는 레이어를 찾아 가져온다.
  3. 누락분 실행·저장없는 단계만 직접 실행하고, 그 결과를 같은 백엔드에 저장해 다음 빌드가 쓰게 한다.

6BuildKit 과 Buildx06-04

빌드 결과 내보내기(Exporter)

Exporter 는 BuildKit 이 만든 빌드 결과를 로컬 이미지 저장소, 레지스트리, 로컬 tar 파일 같은 지정된 형태로 내보내는 출력 방식을 지정하는 설정입니다.

1문제 상황

기존 빌드는 항상 이미지를 만들어 docker daemon 의 로컬 이미지 저장소에 남기는 방식으로 끝났다. 로컬에서 시험하는 이미지든 서버에 올릴 이미지든 결과의 형태가 같았고, 다른 형태로 빼내려면 docker save 같은 별도 명령을 손으로 뒤에 붙여야 했다. 중간 산출물만 필요하거나 아예 이미지 파일이 아니라 원격 레지스트리에 바로 올려야 하는 경우를 한 번에 처리할 수 없었다.

2핵심 질문

빌드가 끝난 결과를 어떤 형태로 어디에 내보낼지를 빌드 요청 단계에서 함께 지정할 수 있는가?

3동작 예시

docker buildx build --output type=docker,dest=out.tar . 로 빌드하면 이미지가 로컬 저장소 대신 out.tar 라는 tar 파일로 저장된다. 이 파일 하나를 다른 머신으로 옮기면 docker load 로 그대로 불러올 수 있다. --output type=registry 를 주면 이미지가 레지스트리에 직접 올라가고, --output type=local,dest=./dist 를 주면 최종 산출물만 해당 폴더에 놓인다. 출력 방식은 플러그인 형태로 늘어날 수 있다.

4동작 과정

  1. 내보내기 방식 지정빌드 옵션으로 exporter 의 종류와 목적지 경로·주소를 함께 정한다.
  2. 빌드 실행exporter 가 지정되면 BuildKit 은 중간 이미지를 로컬에 남기지 않고 요청된 형태로 결과를 조립한다.
  3. 결과 전달exporter 플러그인이 docker, registry, local, oci, tar 같은 각 목적지를 처리해 결과물을 보낸다.

6BuildKit 과 Buildx06-05

이미지 메타데이터와 증명

이미지 메타데이터는 이미지 구성 요소에 SBOM 이나 빌드 출처 같은 증명(attestation) 정보를 함께 붙여, 이미지가 무엇으로 만들어졌는지 검증할 수 있게 하는 정보입니다.

1문제 상황

배포된 이미지가 어떤 소스 코드에서, 어떤 빌드 파일과 어떤 단계로 만들어졌는지 이미지 파일만으로는 확인할 수 없었다. 취약점 스캔 결과가 나오면 대응하려면 어느 커밋과 어떤 설정이 관련됐는지 수작업으로 좁혀야 했다. 이미지에 사용한 패키지 목록이나 빌드 출처 같은 정보를 함께 실어 보내는 방식도 표준으로 정해져 있지 않았다.

2핵심 질문

이미지 자장본체에 그 이미지가 무엇으로 어떻게 만들어졌는지를 설명하는 정보를 함께 기록해 나중에 검증할 수 있게 할 수 있는가?

3동작 예시

docker buildx build --sbom=true --provenance=true --push . 로 빌드해 레지스트리에 올리면, 사용된 패키지 목록(SBOM)과 빌드 출처(어느 소스 커밋, 어떤 빌드 파일, 어떤 빌더를 썼는지)가 함께 전달된다. 이 정보는 이미지 파일 안에 직접 섞이지 않고 같은 레지스트리에 저장된 별도 항목으로 붙어 있어, 이미지 자장본체는 그대로 유지된다. docker buildx imagetools inspect 나 이미지 검사 도구로 이 내용을 따로 꺼내 확인할 수 있다.

4동작 과정

  1. 증명 생성BuildKit 이 빌드 중 사용한 소스, 빌드 파일, 빌더 버전, 패키지 목록을 구조화된 형태의 증명(attestation)으로 만든다.
  2. 이미지에 연결이미지 파일 목록을 담는 manifest 를 통해 증명을 대상 이미지의 진입점에 OCI 주석 형태로 붙인다.
  3. 검증·조회레지스트리에서 증명만 따로 받아 확인할 수 있고, 출처를 검증하는 규격과 도구에 그대로 넘길 수 있다.

1문제 상황

여러 이미지나 여러 아키텍처를 한 번에 빌드하려면 대상마다 docker buildx build 명령을 반복해서 직접 치고 옵션을 하나씩 맞춰 넣어야 했다. 명령이 스크립트 여러 곳에 흩어지면 어떤 이미지를 어떤 태그와 플랫폼으로 빌드했는지 한눈에 보기 어려웠고, 로컬과 CI 의 빌드 설정을 서로 다르게 만들어 두기도 했다.

2핵심 질문

여러 빌드 대상과 그 설정인 컨텍스트, 빌드 파일, 태그, 플랫폼, 산출물을 파일 하나에 모아 두고 그대로 재현해 실행할 수 있는가?

3동작 예시

bake.hcl 에 target "api" 라는 블록을 만들고 그 안에 context, dockerfile, tags, platforms 를 적는다. 여기서 docker buildx bake 를 실행하면 파일에 정의된 모든 target 이 --print 로 먼저 목록으로 출력된 뒤 그대로 빌드된다. 같은 파일을 CI 에서 그대로 호출하면 로컬과 동일한 대상·태그·플랫폼으로 빌드된다. 태그에 {{ .BRANCH }} 처럼 변수를 넣어 두면 브랜치 이름에 따라 다른 태그가 자동으로 붙는다.

4동작 과정

  1. 선언 파일 파싱bake.hcl, docker-bake.hcl, Compose 파일 가운데 지정된 선언 파일을 읽어 target 들을 모은다.
  2. target 병합파일에 적힌 값, 환경변수, 명령행 플래그를 정해진 우선순위에 따라 합쳐 각 target 의 최종 빌드 요청을 만든다.
  3. 일괄 실행완성된 요청들을 Buildx 로 넘겨 여러 이미지를 한 번에 빌드한다.

볼륨 — 데이터를 어디에 두는가

볼륨은 Docker가 관리하는 호스트 영역으로, 컨테이너를 지우고 다시 만들어도 데이터가 남는 영속 저장소다.

1문제 상황

컨테이너의 파일시스템은 컨테이너 자신의 수명과 묶여 있어서, 컨테이너를 지우면 안에 저장한 파일과 데이터베이스 파일도 함께 사라졌다. 같은 이미지로 새 컨테이너를 띄우면 이전에 데이터를 넣은 상태가 처음부터 다시 시작됐다. 여러 컨테이너가 같은 데이터 디렉터리를 함께 써야 할 때는 호스트 경로를 직접 바인드-mount 하는 방식으로 우회해야 했다.

2핵심 질문

컨테이너를 지우고 다시 만들어도 데이터가 남고, 여러 컨테이너가 함께 사용할 수 있는 저장 영역을 어떻게 만드는가?

3동작 예시

docker volume create pgdata 로 만든 볼륨은 Docker 가 관리하는 호스트 영역에 데이터를 보관한다. docker run -v pgdata:/var/lib/postgresql/data postgres 로 컨테이너를 띄우면 컨테이너 안의 /var/lib/postgresql/data 가 이 볼륨으로 바뀐다. 이 컨테이너를 docker rm 으로 지워도 볼륨의 데이터는 그대로 남고, 같은 볼륨을 다른 컨테이너에 -v pgdata:/var/lib/postgresql/data 로 다시 붙이면 두 컨테이너가 같은 데이터 디렉터리를 공유한다.

4동작 과정

  1. 볼륨 생성docker volume create 가 Docker 가 관리하는 호스트 영역 하나를 만들고 이름을 붙인다.
  2. 컨테이너에 연결-v 볼륨이름:컨테이너경로 로 지정하면 컨테이너의 해당 디렉터리가 볼륨으로 대체된다.
  3. 수명 분리컨테이너를 제거해도 볼륨은 유지되며, docker volume rm 으로 지울 때까지 데이터가 남는다.

5한 줄 요약

컨테이너 수명과 분리된 호스트 관리 영역에 데이터를 보관해 컨테이너를 다시 만들 때도 유지되는 영속 저장소

7데이터 저장07-02

바인드 마운트 — 호스트 파일을 컨테이너에

바인드 마운트는 호스트의 특정 경로를 컨테이너의 디렉터리에 그대로 연결해, 컨테이너가 호스트의 파일을 읽고 쓰게 한다.

1문제 상황

컨테이너는 실행마다 새로 만들어지고 멈추면 파일 시스템도 함께 사라진다. 컨테이너 안에서 만든 로그나 빌드 결과물은 컨테이너를 지우면 함께 없어지고, 이미지에는 들어가지도 않는다. 데이터를 컨테이너 밖의 어딘가에 두고 컨테이너에서 그 경로를 그대로 써야 한다.

2핵심 질문

컨테이너가 사라져도 살아남는 호스트의 파일을 컨테이너 안에서 읽고 쓸 수 있는가?

3동작 예시

호스트의 /home/user/data 디렉터리를 컨테이너의 /data 에 연결하고, 컨테이너에서 docker run -v /home/user/data:/data ... 로 실행한다. 이후 컨테이너 안에서 /data/a.txt 에 쓰면 그 내용은 컨테이너가 종료된 뒤에도 호스트의 /home/user/data/a.txt 에 남아 있고, 호스트에서 만든 파일도 컨테이너에서 바로 보인다.

  2. 마운트 연결도커 데몬이 호스트의 디렉터리를 컨테이너의 마운트 테이블에 등록해, 컨테이너 프로세스가 그 경로에서 파일을 열고 쓰면 실제 호스트 디스크의 같은 파일에 접근하게 된다. 읽기 전용은 :ro 를 붙인다.
  3. 수명 관리컨테이너가 멈추면 연결만 풀리고 호스트의 데이터는 그대로 남는다. docker run 에 경로를 안 주면 컨테이너 전용 저장 공간이 쓰여 데이터가 함께 사라진다.

tmpfs 와 이미지 마운트

tmpfs 마운트는 RAM 위에 임시 파일 시스템을 만들어 빠르지만 컨테이너가 멈추면 데이터가 사라지고, 이미지 마운트는 이미지의 디렉터리를 읽기 전용으로 붙인다.

1문제 상황

바인드 마운트로 데이터를 밖에 두면 저장되지만 매번 실제 디스크에 읽고 써야 하므로 느리다. 반대로 디스크 없이 메모리에만 두면 빠른 대신 컨테이너가 끝나자마자 데이터가 사라진다. 읽기 전용으로 제공해야 하는 디렉터리를 매번 복사해 넣는 것도 번거롭다. 빠른 임시 저장소와 읽기 전용 원본 제공이 각각 필요했다.

2핵심 질문

읽기와 쓰기가 아주 빠르면서도 수명이 짧은 임시 데이터를 어디에 둘 수 있는가?

3동작 예시

docker run --tmpfs /tmp:size=100m ... 로 실행하면 컨테이너의 /tmp 가 디스크가 아닌 RAM 영역에 만들어진다. 그 안에서 만든 파일은 메모리에만 있으므로 쓰기 속도가 빠르고 컨테이너가 종료되면 곧바로 삭제된다. 또 이미지 안의 정적 파일 디렉터리는 docker run -v /이미지경로:/컨테이너경로:ro ... 로 붙이면 복사 없이 원본 그대로 읽힌다.

4동작 과정

  1. tmpfs 생성--tmpfs 경로:size=크기 로 지정하면 데몬이 메모리 영역에 임시 파일 시스템을 만들어 컨테이너의 해당 경로에 붙인다. 기본값으로 지정하지 않으면 전체 메모리의 절반이 잡힌다.
  2. 메모리 읽기/쓰기파일 읽고 쓰기가 디스크 입출력을 거치지 않으므로 즉시 끝나지만, RAM 용량이므로 크기 제한과 함께 컨테이너 종료 시 함께 사라진다.
  3. 이미지 마운트이미지에 포함된 디렉터리를 컨테이너 경로에 읽기 전용으로 붙인다. 컨테이너는 그 내용을 그대로 읽지만 수정할 수 없고, 수정은 언제든 다시 이미지로 되돌릴 수 있다.

5한 줄 요약

빠른 임시 데이터는 메모리 위 tmpfs에 두고 사라져도 되는 정적 파일은 이미지에서 읽기 전용으로 붙이는 것

스토리지 드라이버와 containerd 이미지 스토어

스토리지 드라이버는 이미지와 컨테이너의 계층 데이터를 디스크에 저장하고 복원하는 엔진의 후반부이며, containerd 이미지 스토어는 이 저장을 containerd에 맡겨 이미지·아티팩트 관리를 확장하는 방식이다.

1문제 상황

컨테이너 이미지는 여러 계층으로 쌓이고 컨테이너를 실행할 때마다 그 위에 쓰기 가능한 층이 하나 더 얹힌다. 이 데이터를 파일마다 하나씩 그대로 저장하면 계층 간에 중복이 생기고, 컨테이너를 지울 때 실제 쓰이지 않는 바깥 층을 남겨 디스크를 많이 차지한다. 또 이미지 관리 기능이 엔진 내부 저장 코드에 묶여 있어 확장하기 어려웠다.

2핵심 질문

이미지와 컨테이너의 겹친 계층 데이터를 어떻게 디스크에 저장해 지우기와 확장을 처리할 것인가?

3동작 예시

기존 overlay2 드라이버는 이미지의 각 계층을 디스크의 디렉터리 하나씩으로 저장하고, 컨테이너를 실행할 때 그 위에 새 상위 디렉터리를 얹는다. 쓰기가 발생하면 상위 계층의 파일이 아래 계층의 같은 이름 파일을 덮어씁니다. containerd 이미지 스토어 방식을 쓰면 이 계층 관리와 이미지·아티팩트 저장을 containerd에 맡기고 엔진은 저장된 데이터를 읽어 컨테이너에 붙이는 역할만 한다.

4동작 과정

  1. 드라이버 선택데몬은 설정된 드라이버 하나를 골라 이미지 계층과 컨테이너 쓰기 계층의 저장 위치를 정한다. 드라이버마다 지원 파일 시스템이 다를 수 있다.
  2. 계층 저장과 얹기이미지의 각 계층이 순서대로 저장되고, 컨테이너가 시작되면 그 위에 쓰기 가능한 상위 계층이 추가된다. 읽기는 아래에서 위로 층층이 확인해 가장 위쪽 파일을 쓴다.
  3. 삭제와 위임컨테이너를 지울 때 그 컨테이너의 상위 계층만 제거해 데이터가 복구된다. containerd 이미지 스토어에서는 이미지 레퍼런스와 계층 압축·풀기, GC까지 containerd가 수행해 엔진은 이미지를 참조하고 붙이는 일만 한다.

5한 줄 요약

브리지 네트워크와 컨테이너 간 통신

호스트의 브리지를 그대로 공유하는 기본 bridge 와, 컨테이너에 자동 DNS 이름을 붙여 이름으로 통신하게 하는 사용자 정의 bridge 로 컨테이너끼리 주고받는 구조다.

1문제 상황

컨테이너는 각각 독립된 네트워크 환경 안에서 시작하고 호스트 밖으로는 나갈 수 없다. 하지만 서로 다른 컨테이너를 붙여 웹 서버가 앱 서버를 호출하는 식의 통신이 반드시 필요하다. 한 컨테이너에 전부 몰아 넣으면 다시 단일 프로세스 구조로 돌아가고, 각 컨테이너에 직접 IP 를 주면 IP 가 바뀌면 설정이 깨진다. 컨테이너 묶음을 한 네트워크에 묶고 서로 알아볼 방법을 정해야 한다.

2핵심 질문

독립된 컨테이너들을 한 묶음으로 묶고 서로 통신하게 할 수 있는가?

3동작 예시

docker network create app-net 을 실행하면 호스트에 가상의 브리지 인터페이스가 하나 생긴다. --network app-net 으로 붙은 컨테이너는 이 브리지에 연결되어 호스트 전용 IP 를 받고, 같은 네트워크의 다른 컨테이너는 그 IP 로 직접 접근한다. 여기서 브리지 네트워크는 컨테이너 사이의 통신 경로이며, 프록시 방식은 name 으로 받은 요청을 프록시로 전달해 처리한다.

4동작 과정

  1. 브리지 생성데몬이 호스트에 가상 브리지 인터페이스를 만들고, 그 뒤에 두 개의 단계를 둔다. 하나는 호스트가 컨테이너로 나가는 NAT 규칙, 다른 하나는 컨테이너끼리 직접 통신할 때 쓰는 경로다.
  2. 컨테이너 연결컨테이너가 시작되면 브리지의 하위 인터페이스로 붙고 사설 IP 를 받는다. 패킷은 브리지를 거쳐 같은 브리지에 붙은 다른 컨테이너로 전달되고, 브리지는 목적지 MAC 을 직접 찾아 보내기 때문에 사본만 복사하는 방식과 다르다.
  3. 이름 기반 통신기본 bridge 에서는 컨테이너가 붙을 때 이름이 아닌 IP 로만 서로를 찾을 수 있다. 사용자 정의 bridge 에서는 도커가 내장 DNS 서버를 띄워 컨테이너 이름과 별칭을 IP 로 매핑해 주므로, IP 가 바뀌어도 이름으로 부를 수 있다.

5한 줄 요약

호스트의 브리지에 컨테이너들을 붙여 사설 IP 로 서로 직접 통신하게 하고, 사용자 정의 bridge에서는 이름으로 찾을 수 있게 하는 것

컨테이너의 포트를 호스트의 포트에 대응시키는 -p 게시로 외부에서 들어올 경로를 만들고, EXPOSE 는 이런 노출을 하지 않고 선언만 하는 지시다.

1문제 상황

브리지 네트워크는 외부와 분리되어 있어 컨테이너가 만든 웹 서버에는 외부에서 접속할 방법이 없다. 직접 호스트 네트워크를 쓰면 모든 포트를 그대로 열어버려 포트 충돌과 격리 문제가 생긴다. 필요한 포트만 골라 연결하되, 그 연결이 어떤 규칙으로 만들어지는지와 컨테이너 안이 밖의 어디로 나가는지를 분리해서 알아야 한다.

2핵심 질문

외부에서 들어오는 요청을 필요한 컨테이너의 포트에만만 어떻게 연결할 것인가?

3동작 예시

docker run -p 8080:80 nginx 를 실행하면 호스트의 8080 포트로 들어온 패킷이 NAT 규칙에 의해 해당 컨테이너의 80 포트로 전달된다. -p 127.0.0.1:8080:80 으면 바인딩 주소가 127.0.0.1 로 제한되어 그 호스트의 그 주소에서만 접속할 수 있다. 그리고 이미지 안의 EXPOSE 80 은 문서용 지시일 뿐, 그 자체로 포트가 열리지는 않는다.

4동작 과정

  1. 게시 선언-p 호스트포트:컨테이너포트 로 호스트 포트를 어떤 컨테이너 포트로 넘길지 정한다. UDP 는 :53:53/udp 처럼 프로토콜까지 적는다.
  2. 규칙 생성데몬이 브리지 네트워크를 만들 때 host 의 iptables 또는 nftables 에 NAT 규칙과 필터 규칙을 직접 추가해, 호스트 포트로 들어온 패킷을 해당 컨테이너의 포트로 넘기고 컨테이너가 보낸 아웃바운드 패킷에는 출발지 주소를 호스트 주소로 바꿔 돌려보낸다.
  3. 포트 선점게시된 호스트 포트는 해당 컨테이너가 살아 있는 동안 점유되어 다른 프로세스가 그 포트를 열 수 없다. --publish-all 과 Dockerfile 의 EXPOSE 는 포트를 미리 선언해 두는 데 쓰이고, 실제 외부 노출은 -p 게시에서만 만들어진다.

네트워크 드라이버 선택

격리와 주소 배분의 필요에 따라 bridge·host·overlay·macvlan·ipvlan·none 가운데 드라이버를 고르며, host 는 호스트 스택을 그대로 공유하고 macvlan·ipvlan 은 컨테이너를 물리 머신처럼 보이게 한다.

1문제 상황

브리지는 보안과 포트 분리에는 유리하지만 사설 IP 를 쓰기 때문에 물리 머신에 바로 붙지 못하고, 많은 컨테이너가 붙으면 주소가 모자랄 수 있다. 다중 호스트에 걸친 컨테이너를 하나로 묶어야 할 때는 사설 범위를 넘어야 한다. 어떤 환경에 올릴지 미리 정해지지 않기 때문에 드라이버를 못 고르면 필요한 아키텍처를 만들 수 없다.

2핵심 질문

배치 환경과 격리 요구에 맞는 네트워크 드라이버를 어떻게 골라야 하는가?

3동작 예시

docker run --network host ... 로 실행하면 컨테이너에 별도 네트워크 이름 공간을 만들지 않고 호스트의 스택을 그대로 쓴다. 그래서 컨테이너 웹 서버는 호스트의 80 포트를 직접 열고, 내부 IP 없이 외부 클라이언트와 통신한다. 단 다른 컨테이너와 같은 호스트 포트를 동시에 쓸 수 없다. 여러 호스트에 걸친 묶음에는 overlay 드라이버를 쓰고, 물리 머신처럼 보이게 하려면 macvlan 을 쓴다.

4동작 과정

  1. 격리되는 driverbridge 는 가상 브리지와 사설 IP 로 다른 컨테이너와 격리된 네트워크를 만든다. none 은 네트워킹을 완전히 끄고, host 는 이름 공간 격리를 해제해 호스트 스택을 그대로 공유한다.
  2. 물리망에 붙는 drivermacvlan 은 컨테이너에 물리 인터페이스의 주소를 직접 배정해 가상 머신이 아니라 실제 머신처럼 외부에 보이고 통신한다. ipvlan 은 물리 인터페이스를 공유하는 방식으로 같은 호스트 안의 통신 지연 문제를 줄이고, 각 컨테이너가 별도 L3 도메인을 가진다.
  3. 여러 호스트를 잇는 driveroverlay 는 각 호스트에 터널을 깔아 위에서 하나의 L2 네트워크를 만들어, 서로 다른 호스트의 컨테이너가 같은 이름으로 통신할 수 있게 한다. 드라이버 선택은 결국 격리와 주소 배분의 필요에서 결정된다.

방화벽 연동 — iptables 와 nftables

데몬은 브리지 네트워크를 만들 때 호스트의 iptables 또는 nftables에 NAT·필터 규칙을 직접 넣고 제거하며, 데몬 설정의 iptables=false 같은 항목으로 이 자동화를 끌 수 있다.

1문제 상황

호스트는 이미 iptables 나 nftables 로 방화벽을 돌리고 있고, 별도 방화벽 데몬이 체인 형태로 규칙을 관리한다. 그런데 도커 데몬이 브리지 네트워크를 만들 때 NAT 와 필터 규칙을 직접 만들어 넣고 컨테이너가 붙을 때마다 지웠다 다시 만들며, 규칙 위치를 예상할 수 없어게 지긋난다. 데몬이 규칙을 조작하는 것을 전부 멈추고 싶거나, 방화벽을 nftables 로 옮기고 싶은 환경이 있다.

2핵심 질문

도커가 만드는 NAT 와 필터 규칙을 사용자가 직접 관리하는 규칙과 어떻게 구분하고 제어할 것인가?

3동작 예시

방화벽 데몬이 만든 규칙은 일반 체인인 DOCKER-USER 에 있고, 도커가 만드는 규칙은 별도의 체인(DOCKER, DOCKER-FORWARD 등)에 들어간다. 그러므로 도커가 규칙을 지워도 방화벽 데몬의 규칙은 남는다. 데몬 설정의 iptables=false 로 두면 도커는 아무 규칙도 만들지 않아 방화벽 규칙 전부를 사용자가 손으로 관리하는 상태가 되고, ip6tables=false 는 IPv6 에만 적용된다.

4동작 과정

  1. 자동 규칙 주입브리지 네트워크를 만들 때 데몬은 호스트의 iptables 또는 nftables 에 NAT 규칙(마스커레이드, 포트 게시)을 넣고, 패킷이 브리지를 지날 때 적용할 FORWARD 체인 규칙과 체인을 추가한다. 브리지를 삭제할 때는 자신이 만든 규칙만 골라 제거한다.
  2. 사용자 규칙과의 분리사용자가 직접 만든 규칙은 DOCKER-USER 체인에 두어 도커가 건드리지 않는 위치를 정해, 도커 규칙이 갱신돼도 방화벽 데몬의 정책이 유지되게 한다. 규칙 순서는 FORWARD 체인에서 DOCKER-USER 가 DOCKER-FORWARD 보다 먼저 평가되는 순서로 배치된다.
  3. 자동화 끄기와 예외데몬 설정의 iptables=false 나 ip6tables=false 로 자동 주입을 끄고, 브리지 대신 호스트 네트워크를 쓰면 NAT 규칙이 아예 필요 없어 규칙 관리를 단순하게 유지한다. 네트워크 생성 시 --opt com.docker.network.bridge.enable_icc=false 같은 항목으로 컨테이너 간 통신 규칙만 따로 끌 수도 있다.

4동작 과정

Compose 파일 구조와 사양

Compose 파일은 services·networks·volumes 같은 최상위 요소로 구성되는 YAML 문서이며, 이 구조와 속성 규칙을 정한 것이 Compose Specification 이다.

1문제 상황

여러 컨테이너를 함께 띄워야 할 때 예전에는 docker run 명령에 이미지, 포트, 볼륨, 환경 변수를 나열해 직접 입력했다. 실행에 필요한 정보가 명령어 한 줄에 흩어져 있으므로 같은 구성을 다시 만들려면 같은 내용을 다시 타이핑해야 했다. 무엇이 표준 형식인지 정해진 것도 없어서, 도구마다 같은 정보를 다르게 해석하거나 아예 읽지 못했다. 결국 서버마다 실행 방법이 조금씩 달라지고, 그 구성을 원래 상태로 되돌릴 방법도 남지 않았다.

2핵심 질문

여러 컨테이너의 실행 설정을 사람이 읽는 문서 하나에 적고, 그 문서를 어느 도구에서 실행해도 같은 meaning으로 해석되게 할 수 있는가?

3동작 예시

compose.yaml 파일 하나를 두고 최상위에 services, networks, volumes 를 나열한 뒤, 그 아래에 services.web, services.db 처럼 컨테이너 항목을 중첩해 적는다. docker compose up 을 실행하면 도구가 이 파일을 그대로 읽어 각 항목에 해당하는 컨테이너를 만들고 네트워크와 볼륨까지 함께 구성한다. 같은 폴더에 파일을 두기만 하면 별도 설치나 설정 없이 이 구조를 그대로 재실행할 수 있다.

4동작 과정

  1. YAML 문서 파싱파일 전체를 읽어 중첩된 키와 값을 그대로 자료구조로 펼쳐 놓는다. 들여쓰기로 상위·하위 관계가 결정된다.
  2. 최상위 요소 해석services 는 실행할 컨테이너, networks 와 volumes 는 이름만 미리 선언해 두고 다른 요소가 참조하게 한다. configs 와 secrets 도 같은 방식으로 선언만 해 둔다.
  3. 사양 검증 후 실행Compose Specification 에 적힌 속성명과 자료형과 대조해 유효하지 않은 키를 걸러내고, 통과한 설정을 바탕으로 컨테이너를 생성한다.

5한 줄 요약

서비스 정의와 최상위 요소

1문제 상황

docker run 으로 컨테이너를 띄우면 이미지 이름, 실행 명령, 포트, 마운트할 볼륨, 환경 변수, 네트워크까지 모든 정보를 명령줄에 나열해야 한다. 인자가 많아지면 옵션 순서를 외워야 하고, 같은 애플리케이션의 다른 서비스는 결국 거의 같은 긴 명령을 다시 반복하게 된다. 무엇이 앱 실행에 필요한 항목이고 무엇이 설정 사항인지도 구분되지 않는다. 결과적으로 컨테이너 하나를 정의하는 비용이 그대로 남아, 서비스가 늘수록 관리할 수 있는 범위가 줄어든다.

2핵심 질문

컨테이너 하나를 실행하는 데 필요한 모든 속성을, 명령이 아니라 항목 하나로 누락 없이 정의할 수 있는가?

3동작 예시

4동작 과정

  1. 서비스 항목 펼치기services 아래 각 하위 항목을 컨테이너 한 개로 해석한다. build 만 있으면 빌드로 얻은 이미지를, image 가 있으면 해당 이름을 원본으로 삼는다.
  2. 속성 종류별로 배정실행에는 image·build·command·entrypoint, 외부 노출에는 ports, 연결에는 networks·depends_on, 데이터에는 volumes·configs·secrets 가 쓰인다. 각 속성은 정해진 키 이름과 자료형만 따른다.
  3. 선언 요소 연결최상위 networks·volumes·configs·secrets 의 선언을 각 서비스의 참조에 맞춰 만들어 붙인다. 참조되지 않은 항목은 만들지 않는다.

Compose 파일 안의 ${변수} 표기를 실행 시점의 환경 변수나 .env 파일의 값으로 바꿔 넣는 기능으로, 하나의 파일을 여러 환경에서 재사용하게 해 준다.

같은 구성을 개발 서버와 운영 서버에 배포하려면 이미지 태그, 접속할 DB 주소, 포트 번호, 자격 증명 값이 전부 달라진다. 그 값들을 Compose 파일에 그대로 적으면 파일이 환경 하나에 고정되고, 운영에 쓸 값을 운영용 파일에 복사해 두는 방식으로 관리하게 된다. 복사한 파일이 실제 서버와 어긋나면 어디가 최신본인지 알기 어렵고, 값이 여러 파일에 흩어져 한 곳을 고쳐도 빠뜨리는 일이 생긴다. 값이 실수로 저장소에 남는 문제도 함께 생긴다.

2핵심 질문

값이 달라지는 자리만 파일 밖으로 빼 두면서 파일 본문은 하나로 유지할 수 있는가?

3동작 예시

Compose 파일에는 db.example.internal 대신 ${DB_HOST} 라고 적어 두고, 실행하는 환경에서 DB_HOST=db.example.internal 을 주거나 같은 폴더의 .env 파일에 그 값을 둔다. docker compose up 을 실행하면 ${DB_HOST} 가 그 값으로 바뀐 상태로 파싱된다. ${DB_PORT:-5432} 처럼 기본값을 함께 적으면 값이 없을 때 그 숫자가 쓰이고, ${API_KEY:?필수} 처럼 오류 표기를 넣으면 값이 빠졌을 때 실행 전에 멈춘다.

4동작 과정

  1. 값 수집실행 셸의 환경 변수와, 프로젝트 폴더의 .env 파일 또는 --env-file 로 지정한 파일에서 이름에 대응하는 값을 모은다. 같은 이름이면 셸의 값이 우선한다.
  2. 표기 치환파일을 파싱할 때 ${변수} 형태를 모두 앞서 모은 값으로 바꾼다. ${변수:-기본값} 은 값이 비었을 때, ${변수:?메시지} 는 비면 오류로 멈추고, ${변수-기본값} 은 값이 없을 때만 기본값을 쓴다. 리터럴 달러 기호는 $$ 로 쓴다.
  3. 치환된 설정 사용바뀐 문자열로 설정을 완성한 뒤 컨테이너 생성, 환경 변수 주입, build.args 전달에 그대로 사용한다.

5한 줄 요약

값이 달라지는 자리만 ${} 표기로 남겨 두고 실행 시점의 환경 변수로 채워, 파일 하나를 여러 환경에서 그대로 재사용하게 하는 것

Compose 에서 이미지 빌드하기

Compose 파일의 build 항목에 Dockerfile 과 빌드 인자를 적어 두면 docker compose build 가 그 설정대로 이미지를 만들어 컨테이너 실행에 사용한다.

1문제 상황

개발 중에는 코드가 자주 바뀌므로 컨테이너용 이미지를 직접 만들어야 한다. 예전에는 docker build 로 이미지를 만들고 docker tag 로 이름을 붙인 다음, 그 이름을 Compose 파일이나 실행 명령에 손으로 적어 넣었다. Dockerfile을 고쳐도 이미지 이름은 그대로라 안의 코드가 어떤 상태인지 알 방법이 없고, 빌드 설정과 실행 설정이 서로 다른 파일이나 명령에 흩어진다. 설정을 바꿔 이미지를 다시 만들었는데 실행 명령에 남은 옛 이름을 써서 낡은 이미지가 뜨는 경우도 반복됐다.

3동작 예시

서비스에 build: {context: ., dockerfile: Dockerfile.dev, args: {NODE_ENV: development}} 를 적어 두면 docker compose up 이 필요한 서비스를 먼저 빌드한다. 만들어진 이미지는 기본적으로 프로젝트이름-서비스이름 태그가 붙고, 같은 실행 명령이 그 이미지를 그대로 사용한다. image 와 build 를 함께 적으면 빌드가 끝난 뒤 그 이름으로 다시 태깅한다.

4동작 과정

  1. 빌드 설정 해석context 를 빌드 컨텍스트 루트로 잡고, dockerfile·target·args·platform·cache_from 등 속성을 빌드에 적용한다. args 는 Dockerfile의 ARG 로 전달된다.
  2. 이미지 제작빌드 컨텍스트를 Docker 데몬에 넘기고 Dockerfile 지시대로 레이어를 쌓아 이미지를 만든다. 이때 Compose 가 정한 기본 태그를 붙이고, image 가 적혀 있으면 그 이름으로 다시 태깅한다.
  3. 실행에 사용컨테이너를 만들 때 빌드가 만든 이미지를 우선 사용하고, 빌드 결과가 이미 있는 상태면 재사용한다. build 와 image 를 모두 주면 이미지 이름으로 가져온 결과를 다시 빌드해 덮어쓴다.

5한 줄 요약

이미지 제작에 필요한 Dockerfile 위치와 빌드 인자를 Compose 파일에 함께 적어, 빌드와 실행 설정을 하나로 묶고 같은 명령이 만든 이미지를 쓰게 하는 것

개발 루프 편의 기능

docker compose watch 처럼 소스 코드가 바뀔 때마다 컨테이너를 자동으로 다시 빌드하거나 동기화해 주는 개발 편의를 위한 기능.

1문제 상황

개발 중 코드를 고칠 때마다 컨테이너 안에 반영하는 과정이 손으로 반복된다. 컨테이너 안에서 직접 편집하면 호스트의 파일과 내용이 달라지고, 새로 만든 파일이나 삭제는 그대로 반영되지 않는다. 호스트 파일을 컨테이너로 복사해 넣으면 반영은 되지만 어느 파일이 바뀌었는지 매번 확인해서 명령을 다시 실행해야 한다. 가벼운 변경까지 전체를 다시 만들고 재기동하면 확인까지 오래 걸려 흐름이 끊긴다.

2핵심 질문

소스 코드가 저장될 때마다 컨테이너가 그 변경을 자동으로 받아 반영하게 할 수 있는가?

3동작 예시

Compose 파일에 develop.watch 로 호스트의 ./src 와 컨테이너 안의 /app/src , 그리고 action: sync 를 적어 두고 docker compose watch 를 실행한다. 이 상태에서 소스 파일을 저장하면 변경된 파일만 컨테이너로 복사된다. 컨테이너 안에서 실행 중인 프로세스가 있다면 파일을 넘긴 뒤 docker compose restart 로 프로세스를 다시 시작해 새 코드를 반영한다.

4동작 과정

  1. 감시 규칙 등록develop.watch 의 경로 쌍과 action 값을 읽어 파일 변경 이벤트를 구독할 대상을 정한다. sync 는 파일 복사, rebuild 는 이미지 재생성을 뜻한다.
  2. 변경 감지 후 전파이벤트가 오면 경로 규칙에 맞는 파일만 처리한다. sync 는 해당 파일을 컨테이너 안 경로에 복사하고, rebuild 는 정의된 빌드 순서대로 이미지를 다시 만든 뒤 컨테이너를 교체한다.
  3. 실행 상태 맞추기파일을 넘긴 뒤 실행 중 프로세스가 있으면 재시작하고, exec 형식의 명령을 지정한 경우 그 명령을 새로 실행해 프로세스를 다시 띄운다.

5한 줄 요약

소스 변경을 파일 단위로 감지해 컨테이너에 자동으로 넘기고 재시작까지 이어 주는, 개발 중 반복 작업을 줄여 주는 자동 반영 기능

실행 순서와 수명주기 제어

depends_on 과 healthcheck, pre_start 같은 훅으로 어떤 서비스를 먼저 띄우고 언제 멈출지를 정해 주는 컨테이너 실행 순서와 수명주기 제어 방식.

1문제 상황

여러 서비스가 함께 뜨는 구성에서 DB가 준비되기 전에 애플리케이션이 접속을 시도하면 실패한다. docker run 을 손으로 차례로 치면 그나마 순서를 지킬 수 있지만, 그 순서가 파일에 남아 있지 않으므로 다른 사람이 같은 구성을 띄우면 또 다른 결과가 나온다. depends_on 을 단순히 적은 경우에도 컨테이너가 만들어졌다는 사실만 확인할 뿐, 그 안의 DB가 접속을 받을 준비가 됐는지는 보장하지 않는다. 결국 재시도 코드를 스스로 넣거나 로그를 보며 기다리는 일이 반복된다.

2핵심 질문

앞선 서비스가 실제로 동작할 준비를 마쳤을 때만 뒤의 서비스를 시작시킬 수 있는가?

3동작 예시

db 서비스에 healthcheck 로 pg_isready 명령을 지정하고, api 서비스에 depends_on: {db: {condition: service_healthy}} 를 적는다. 기동 시 db 컨테이너가 만들어지고 pg_isready 가 정상 응답을 반환해 healthy 가 된 뒤에야 api 컨테이너가 시작된다. 기동 여부와 관계없이 기기에 붙여야 하는 작업은 pre_start 훅으로 컨테이너 생성 전에 실행하게 둘 수 있다.

4동작 과정

  1. 선행 조건 지정depends_on 으로 어떤 서비스가 먼저여야 하는지, 그리고 그 조건을 service_started(생성됨), service_healthy(정상 응답), service_completed_successfully(정상 종료) 가운데 무엇으로 볼지 정한다.
  2. 상태 확인healthcheck 에 적힌 명령을 interval 간격으로 반복 실행하고 retries 만큼 연속 실패하면 unhealthy 로 판정한다. start_period 동안은 실패를 정상으로 간주해 부팅 시간을 벌어 준다.
  3. 수명주기 실행조건이 충족되면 뒤의 서비스를 시작하고, 종료할 때는 stop_signal 과 stop_grace_period 로 종료 신호와 대기 시간을 정해 차례로 멈춘다. 기기 준비 같은 작업은 pre_start 훅으로 시작 전에 한 번만 건다.

5한 줄 요약

선행 서비스의 상태 조건과 점검 명령을 함께 선언해, 준비가 끝난 뒤에 다음 서비스를 시작시키고 정해진 순서로 멈추게 하는 실행 순서 제어

운영·배포와 확장 기능

deploy 요소로 자원과 배포 방식을 정해 운영 환경에 맞추고, docker compose scale 로 서비스의 인스턴스 수를 늘리는 운영·배포와 확장 기능.

1문제 상황

개발 환경에서 docker compose up 으로 띄운 구성을 운영에 그대로 쓰면 자원이 정해져 있지 않아 한 서버에 여러 컨테이너를 올렸을 때 서로 자원을 다툰다. 처리량이 늘어 인스턴스를 늘려야 하면 같은 설정을 여러 번 손으로 실행하고 포트를 하나씩 바꿔 붙여야 하며, 특정 인스턴스만 멈출 때 어떤 컨테이너인지 특정하기 어렵다. 인스턴스 수를 바꿀 때마다 실행 명령을 다시 입력해야 하고, 서버가 여러 대라면 같은 내용을 각 서버에 반복 입력하게 된다.

2핵심 질문

운영에 필요한 자원 한도와 배포 방식을 파일에 함께 선언하고, 인스턴스 수를 명령 한 줄로 조정할 수 있는가?

3동작 예시

서비스에 deploy: {replicas: 3, resources: {limits: {cpus: '0.5', memory: 256M}}} 를 적으면 인스턴스 3개가 각자 CPU 0.5코어와 메모리 256M 안에서 동작한다. 이후 docker compose scale web=5 를 실행하면 web 인스턴스만 5개로 늘고, 각 인스턴리는 서로 다른 포트 번호로 외부에 노출된다. restart_policy 를 함께 적어 두면 예기 종료된 인스턴스를 정책에 따라 다시 띄운다.

4동작 과정

  1. 배포 속성 선언deploy 안에서 replicas 로 인스턴스 수를, resources.limits 로 CPU·메모리 상한과 예약량을, restart_policy 와 update_config 로 재시작·갱신 방식을 정한다. placement 으로 어느 라벨의 머신에 둘지도 지정한다.
  2. 인스턴스 수 조정docker compose scale 명령이나 --scale 옵션으로 특정 서비스의 인스턴스 수를 바꾼다. 지정된 자원 한도와 모듈 모드로 정한 공유 규칙 안에서만 각 컨테이너가 동작한다.
  3. 환경별 반영일반 docker compose up 에서는 replicas 와 resources 가 반영되고, placement 같은 스케줄링 속성은 Swarm 모드에서만 적용된다. 속성이 없는 항목은 해당 기능이 없는 상태로 실행된다.

5한 줄 요약

자원 한도와 배포 방식을 파일에 선언해 운영 환경에 맞추고, 인스턴스 수를 명령 한 줄로 늘리고 줄일 수 있게 하는 배포·확장 기능

Docker Hub 자동 빌드와 운영

GitHub 같은 소스 저장소에 코드가 올라오면 Docker Hub 가 대신 Dockerfile 을 빌드해 이미지를 만들고, 그 빌드와 테스트 상태를 관리하는 기능.

1문제 상황

코드를 GitHub 에 올리면 사람이 Dockerfile 을 직접 읽고 명령을 실행해 이미지를 만들었다. 그리고 만든 이미지가 테스트를 통과했는지, 어떤 커밋에서 만들어졌는지를 별도 기록으로 관리했다. 이 방식은 빌드를 돌리는 사람과 결과물을 확인하는 사람이 분리돼 있어, 커밋이 올라간 뒤 며칠 뒤에야 이미지가 나가는 경우도 생겼다. 무엇보다 로컬에서 빌드하므로 팀마다 Docker 버전이 달라 같은 코드가 서로 다른 이미지로 나가는 결과도 생겼다.

2핵심 질문

소스 저장소에 코드가 올라오는 순간, 표준화된 방식으로 이미지를 자동으로 빌드하고 그 결과를 어디에서나 확인할 수 있는가?

3동작 예시

GitHub 의 main 브랜치에 커밋이 하나 올라오면 Docker Hub 가 그 저장소와 연결된 빌드 정의를 읽고, 저장소 안의 Dockerfile 을 서버에서 직접 빌드해 태그가 붙은 이미지를 만든다. 그 결과 화면에는 커밋 해시, 빌드 성공 여부, 만들어진 이미지의 크기와 취약점 개수가 한 줄로 남고, 실패하면 어느 줄에서 깨졌는지 로그로 남는다.

4동작 과정

  1. 빌드 정의 연결Docker Hub 저장소에서 어느 브랜치의 어느 경로에 있는 Dockerfile 을 쓸지 지정하고, 자동 빌드를 켠다. 이때 소스 저장소와 Docker Hub 계정이 서로 인증되어 있어야 한다.
  2. 커밋 이벤트 감지소스 저장소에서 푸시나 PR(Pull Request, 변경 내용을 검토하기 위해 보내는 요청) 이 올라오면 Docker Hub 가 해당 커밋의 빌드를 큐에 넣고, Docker 빌드 워커라는 실행 환경이 하나씩 집어 처리한다.
  3. 빌드 실행과 결과 기록워커가 Dockerfile 의 각 명령을 순서대로 실행해 이미지를 만들고, Digest(내용 해시로 이미지를 유일하게 가리키는 값) 와 빌드 로그, vuln(취약점) 정보를 이미지와 함께 저장한다. 성공한 빌드만 태그를 달아 레지스트리에 푸시되며, 실패하면 태그가 갱신되지 않는다.

1문제 상황

Docker Hub 자동 빌드는 저장소에서 미리 정해 둔 한 가지 방법만 실행한다. 그래서 테스트를 돌리고 여러 이미지 태그를 붙이는 같은 작업을 하려면 빌드 정의를 손으로 늘려야 했다. 또한 큰 프로젝트는 이미지 빌드가 오래 걸리는데 매번 처음부터 다시 빌면 CI 시간이 계속 늘었고, 레지스트리에 붙일 인증 정보(시크릿)를 워크플로 어디에 넣어야 안전한지 정해진 기준도 없었다.

2핵심 질문

소스 저장소의 자동화 기능 안에서 이미지를 빠르고 안전하게 빌드하고 레지스트리에 올리는 표준화된 방법은 무엇인가?

3동작 예시

GitHub Actions 의 워크플로 yaml 파일에서 ubuntu-latest 러너(자동화용 가상 머신) 에 Docker Buildx 플러그인을 설치한 뒤, 소스 코드를 체크아웃하고 docker/build-push-action 을 실행해 이미지 두 개를 병렬로 빌드해 Docker Hub 에 푸시한다. 이때 GITHUB_TOKEN(저장소가 발급하는 임시 사용권한 토큰) 을 로그인 자격 증명으로 쓰고, 빌드 단계 사이에는 이미 만들어진 레이어를 재사용해 시간을 줄인다.

4동작 과정

  1. Buildx 빌더 준비워크플로 러너에 Docker Buildx 플러그인을 설치하고, 여러 이미지나 여러 CPU 아키텍처를 동시에 빌드할 수 있는 빌더 드라이버를 지정한다.
  2. 캐시와 시크릿 주입GitHub Actions 캐시로 이전 빌드의 레이어를 재사용하고, 레지스트리 로그인 토큰과 SSH 키 같은 시크릿(민감한 값)을 워크플로 안에서만 쓰는 환경 값으로 주입한다. BuildKit 덕분에 빌드가 끝난 뒤 SBOM(이미지에 들어 있는 소프트웨어 구성품 목록) 와 Attestation(빌드를 누가 어떤 조건에서 만들었는지 적은 증명) 을 함께 생성할 수 있다.
  3. 빌드와 푸시docker/build-push-action 이 Dockerfile 을 읽어 여러 태그의 이미지를 병렬로 빌드해 레지스트리에 푸시하고, 결과 digest 를 워크플로 출력에 남겨 다음 단계가 참조하게 한다.

빌드를 내 컴퓨터 대신 Docker Build Cloud 의 관리형 빌더나 Docker Offload 로 수행해 여러 아키텍처 이미지를 빠르게 만들고 로컬 자원을 아끼는 방식.

1문제 상황

로컬에서 Docker 이미지를 빌드하면 CPU 와 메모리를 그대로 점유해서 개발 중 다른 작업이 느려지고, arm64 Mac 과 x86 서버처럼 아키텍처가 다른 환경에 올리려면 자기 컴퓨터에서 QEMU 같은 에뮬레이터를 켜고 느리게 빌드해야 했다. 이 상태에서 여러 아키텍처를 한꺼번에 만들려면 빌드를 순차로 반복해야 하므로 전체 시간이 길어졌다.

2핵심 질문

내 컴퓨터 자원을 쓰지 않고 여러 아키텍처용 이미지를 빠르게 만들 수 있는 관리형 빌드 환경은 무엇인가?

3동작 예시

개발자는 로컬에서 docker build --platform linux/amd64,linux/arm64 -t 사내앱:v1 . 을 실행하지만 실제 빌드는 전부 원격 빌드 클라우드에서 진행된다. 로컬은 파일 목록만 전송하고, 클라우드는 amd64 와 arm64 를 병렬로 빌드해 레지스트리에 푸시한 뒤 digest 를 알려 준다. Docker Offload 를 켜면 QEMU 를 직접 켜지 않고 Cloud Native Buildpacks(빌드 단계와 실행 이미지를 자동으로 맞춰 주는 규격) 로 다중 아키텍처 이미지를 만든다.

4동작 과정

  1. 원격 빌더 선택Docker Build Cloud 의 관리형 빌더를 사용하거나, 계정별로 제공되는 Docker Offload 빌더를 지정해 빌드가 실행될 서버를 정한다. 로컬에는 빌드 설정만 남고 실제 작업은 그 서버에서 돌아간다.
  2. 멀티 플랫폼 병렬 빌드요청한 아키텍처별 빌드를 동시에 시작하고, 소스 컨텍스트를 한 번만 전달해 각 빌드가 공유한다. BuildKit 이 에뮬레이션 대신 네이티브 실행을 쓰도록 지시하면 arm64 빌드를 x86 서버에서 직접 수행한다.
  3. 푸시와 로컬 반영빌드된 이미지를 레지스트리에 푸시해 digest 를 반환하고, Build Cloud 는 캐시로 다음 빌드 시간을 줄인다. 로컬 Docker 컨텍스트에 기록해 두고, pull 로 이미지를 내려받으면 이후 실행은 로컬에서 처리된다.

빌드 정책으로 빌드 거버넌스

1문제 상황

개발자는 편한 베이스 이미지를 아무거나 골라 Dockerfile 을 쓰기 때문에 같은 조직 안에서도 외부에서 끌어온 이미지, 개인 PC 에서 만든 임시 Dockerfile, 이미 알려진 결함이 있는 오래된 태그가 그대로 빌드되어 레지스트리에 올라갔다. 이 상태에서 무엇을 막을지는 전부 담당자 개인의 취향에 달려 있었고, 조직 전체에 같은 기준을 강제할 방법이 없었다.

2핵심 질문

빌드가 실행되는 시점에 어떤 소스와 어떤 베이스 이미지만 허용할지 규칙으로 강제할 수 있는가?

3동작 예시

정책으로 FROM 절의 베이스 이미지를 registry.example.com/approved/ 이미지로 시작하는 것만 허용해 두면, 다른 레지스트리나 Docker Hub 의 무검증 이미지를 베이스로 쓰는 Dockerfile 은 빌드가 시작되기도 전에 거부된다. 개발자 컴퓨터에서 만든 Dockerfile 을 소스 외부에서 직접 빌드하려 할 때도 같은 규칙이 적용된다.

4동작 과정

  1. 정책 정의관리자가 소스 저장소(어느 Git 저장소에서 온 빌드인지), Dockerfile 위치(어느 경로의 빌드 설정인지), 베이스 이미지 출처와 태그(어디서 온 이미지인지, 어느 버전인지) 를 조건으로 묶어 정책으로 등록한다. 이미지에 포함된 자격 증명이나 에러 로그의 공개 여부도 함께 지정할 수 있다.
  2. 빌드 시점 강제빌드가 시작되면 정책 엔진이 Dockerfile 과 빌드 컨텍스트를 조건에 대조한다. Frontend(FROM 절의 이미지), Git 주소, 빌드 파일 경로가 하나라도 어긋나면 빌드를 거부하고 위반 사유를 출력한다.
  3. 감사와 완화정책을 통과한 빌드만 실제 빌드로 넘어가고, 통과 기록과 거부 기록이 남는다. 규칙이 너무 좁아 정상 작업이 막히면 예외 규칙을 좁은 범위로 추가해 완화한다.

컨테이너 보안 격리와 데몬 보호

seccomp·AppArmor·사용자 네임스페이스로 컨테이너가 호스트를 건드리지 못하게 격리하고, Docker 데몬 소켓 접근을 통제해 호스트를 지키는 보안 설정.

1문제 상황

컨테이너는 호스트 커널을 공유하므로 격리가 약하면 컨테이너 안의 프로세스가 호스트 파일 시스템과 커널 기능을 그대로 건드릴 수 있었다. 특히 기본 seccomp 프로필은 일반적인 앱에 필요한 시스템 호출만 허용하지만, 이 설정을 꺼 두거나 권한을 넓게 주면 컨테이너 하나가 호스트 전체를 장악할 위험이 생겼다. 여기에 컨테이너 내부에 마운트된 Docker 소켓은 API 를 그대로 들고 있어서, 그것까지 노출되면 그 컨테이너가 사실상 호스트 관리자 권한을 갖게 된다.

2핵심 질문

컨테이너 안의 프로세스가 호스트를 변경하지 못하도록 시스템 호출과 접근 권한을 어디까지 제한해야 하는가?

3동작 예시

컨테이너가 파일을 만들고 네트워크로 패킷을 보내는 것은 허용되지만, 커널 모듈을 로드하거나 다른 프로세스의 메모리를 읽는 시스템 호출은 seccomp 프로필에서 빠져 있으므로 호출 자체가 실패한다. 또한 마운트한 Docker 소켓을 읽기 전용으로 붙이고 권한 부여를 빼면, 컨테이너 안에서는 이미지 목록을 볼 수만 있고 컨테이너를 만들거나 지울 수는 없다.

4동작 과정

  1. 시스템 호출 필터링seccomp(허용된 시스템 호출 목록으로 커널 호출을 걸러 내는 기능) 로 컨테이너 프로세스가 쓸 수 있는 시스템 호출을 정한다. Docker 는 일반 앱용 기본 프로필을 제공하며, 필요한 호출이 빠르면 SCMP_ACT_ALLOW 항목으로 개별적으로 추가한다.
  2. 권한 분리AppArmor 와 사용자 네임스페이스(호스트와 다른 UID 범위를 만들어 관리자 권한이 그대로 넘어오지 않게 하는 기능) 를 함께 써서 파일 접근 경로와 사용자 ID 를 격리한다. 또한 읽기 전용 루트 파일시스템과 no-new-privileges 로 실행 중 권한 상승을 막는다.
  3. 데몬 소켓 보호Docker 데몬(컨테이너를 실제로 만들고 관리하는 프로세스) 에 접근할 수 있는 사용자를 docker 그룹 등 제한된 목록으로 한정하고, 민감한 서비스에는 소켓을 마운트하지 않거나 읽기 전용으로만 붙인다.

5한 줄 요약

시스템 호출 필터와 권한·데몬 소켓 접근 제한으로 컨테이너가 호스트를 건드리지 못하게 만드는 보안 격리

Docker Scout 로 취약점 관리

Docker Scout 로 이미지 안의 패키지와 알려진 취약점(CVE)을 분석·추적하고, 예외 처리와 정책 평가로 실제로 고칠 대상만 골라내는 방법.

1문제 상황

이미지에 어떤 패키지가 어떤 버전으로 들어 있는지와 그 버전에 알려진 취약점이 있는지는 이미지 안에서 자동으로 알 수 없었다. 그래서 보안팀이 이미지 전체를 스캔하면 수백 개가 한 번에 나오는 취약점 목록을 받아야 했고, 이 중 실제로 쓰이지 않는 코드 경로에 있는 것까지 고치라고 지시해야 했다. 결과적으로 대응 대상이 계속 밀려 있었고, 취약점 대응 상태가 이미지 단위로도, 배포 후 운영 단계에서도 계속 갱신되지 않았다.

2핵심 질문

이미지에 포함된 패키지의 알려진 취약점을 계속 추적하면서, 실제로 고쳐야 할 것만 골라내는 기준을 세울 수 있는가?

3동작 예시

Scout 에서 이미지를 대상으로 스캔을 실행하면 패키지 목록과 CVE(공개된 취약점 식별 번호) 가 표로 나오고, 잘 알려진 취약점이 아예 없는 것부터, 표시되는 CVE 의 심각도 등급까지 붙는다. 여기서 이미지가 실제로 호출하는 경로에 있는 취약점만 포함하도록 기준을 정하면 목록이 크게 줄고, 그 기준은 이미지 업데이트마다 다시 평가된다.

4동작 과정

  1. 이미지 스캔이미지 레지스트리나 Docker Hub 에 있는 이미지를 대상으로 SBOM(소프트웨어 구성품 목록) 를 읽어 패키지별 버전과 알려진 취약점을 매칭한다. CVE 별 심각도 등급이 결과에 붙는다.
  2. 예외 처리 설정특정 CVE 를 무시하거나, 특정 사람이 승인한 항목만 무시하는 예외 규칙을 추가한다. 이 예외는 보정 트리거를 통해 자동화되고, 예외가 사라지면 다음 평가에서 다시 드러난다.
  3. 정책 평가와 비교조직이 정한 기준(예외를 무시한 상태에서도 이 등급 이하면 허용한다) 으로 이미지가 통과·차단되는지 판정한다. 두 이미지나 두 커밋의 결과를 나란히 비교해 개선 폭을 볼 수 있고, 차단 기준에 걸리면 레지스트리에 푸시되지 않게 연결할 수 있다.

조직 인증과 권한 관리

Docker 조직에서 SSO·액세스 토큰·OIDC 로 인증을 붙이고, 역할(Member·Editor·Owner)과 커스텀 역할·프로비저닝으로 사람과 자동화 시스템의 권한을 나누는 관리 체계.

1문제 상황

Docker 조직에 사람이 늘어나면 공개 저장소와 비공개 저장소가 섞여 있고, 누가 어떤 저장소를 볼 수 있으며 어떤 이미지를 지울 수 있는지 권한이 하나로 뭉뚱그려져 있었다. 회사 계정 시스템에서 이미 로그아웃한 사람의 Docker 계정이 남거나, CI 에 쓰던 액세스 토큰이 개인에게 발급된 것이 끝이라 그 사람이 퇴사하면 자동화까지 함께 멈춰야 하는 상황도 생겼다. 개인 계정으로 이미지 푸시를 기록하면 공개 저장소 개설자 이름을 확인하는 정도로 감사 정보가 거의 남지 않았다.

2핵심 질문

사람과 자동화 시스템 각각에게 필요한 최소한의 접근 권한을 누구의 계정으로 부여하고, 조직 전체에 일관되게 관리할 수 있는가?

3동작 예시

조직에 SSO(중앙 인증 시스템 로그인)와 OIDC(인증 결과를 서명된 토큰으로 전달하는 방식) 를 걸어 두면 구성원은 Docker 계정 비밀번호를 따로 만들지 않고 회사 계정으로 로그인한다. CI 용으로는 조직 계정이 발급하는 액세스 토큰을 저장소의 시크릿에 넣고, 그 토큰에는 권한이랑 만료일이 정해져 있어 사람이 아닐 경우 무엇을 할 수 있는지가 코드로 남는다.

4동작 과정

  1. 인증 방식 부착조직 단위로 SSO 나 OIDC 를 설정해 구성원은 조직 계정으로 로그인하고, 필요하면 2FA(두 번째 인증 요소를 요구하는 방식) 를 강제한다. 액세스 토큰(조직 대신 사용자를 대신해 API 를 호출하는 자격 증명)을 발급해 스크립트나 CI 에서 SSO 없이 인증하게 한다.
  2. 역할로 권한 배분구성원에게 Member(읽기·쓰기, 관리자 기능은 없음), Editor(저장소 관리 가능), Owner(조직 전체 관리) 같은 역할을 부여하고, 필요하면 저장소 단위로만 동작하는 커스텀 역할(예: 특정 저장소 읽기와 이미지 삭제만 가능)을 만들어 붙인다. 역할이 너무 많으면 그룹 단위로 묶어 배분한다.
  3. 정기 검증과 회수프로비저닝(SAML SCIM 같은 표준 방식으로 조직 디렉터리에서 사용자와 그룹을 자동 생성·회수하는 것)으로 계정과 접근 권한을 주기적으로 맞추고, 주기적 검토와 권한 강등을 통해 불필요한 권한을 회수한다. 이때 설정으로 남는 감사 로그를 확인해 누가 무엇을 했는지 확인한다.

1문제 상황

컨테이너를 여러 대의 컴퓨터에 띄우려면 각 서버에 직접 접속해 같은 명령을 반복해서 실행해야 합니다. 어떤 서버가 죽었는지, 어떤 서버에 몇 개를 더 띄워야 하는지, 이미 떠 있는 것을 언제 교체할지 전부 사람이 판단하고 손으로 관리해야 합니다.

Scale이 커질수록 이 수작업이 그대로 따라오지 못합니다. 서버마다 실행 버전이 달라지고, 수동으로 옮겨 놓은 컨테이너는 상태를 추적하기 어렵고, 장애가 났을 때 대체 컨테이너를 직접 띄우는 시간만큼 서비스가 멈춥니다. 결국 "여러 서버를 하나의 덩어리로 다루는 기능"이 엔진에 없다면, 운영 체계 전체를 별도로 만들어 붙여야 합니다.

2핵심 질문

여러 Docker Engine 호스트를 하나의 클러스터로 묶고, 어떤 서버가 죽어도 정해진 규칙대로 컨테이너를 알아서 채우게 할 수 있을까요?

3동작 예시

매니저 노드 하나를 골라 스웸을 켜고, 같은 역할을 하는 워커 노드 세 대를 편입시킵니다. 이때 이미지 web:1.0 을 복제본 3개로 선언하면, 스웸은 그 복제본 중 하나씩을 세 노드에 골라 태스크로 스케줄합니다. 그다음 한 워커를 통째로 꺼내면, 꺼진 노드의 태스크는 실행 중이 아니게 표시되고 남아 있는 두 노드에 자동으로 다시 스케줄되어 복제본 3개가 유지됩니다.

4동작 과정

  1. 스웸 모드 초기화노드 중 하나에 docker swarm init 을 실행해 그 노드를 매니저로 지정하고 클러스터의 기준 정보를 저장합니다. 매니저는 스원의 모든 상태를 저장하는 역할만 하고 직접 컨테이너를 실행하지는 않습니다.
  2. 노드 편입나머지 노드에서 docker swarm join 을 실행해 매니저에 등록합니다. 등록된 노드는 워커로 동작하며, 매니저 역할을 함께 맡는 노드를 붙이면 실행 중 매니저도 여러 대가 됩니다.
  3. 서비스 선언과 자동 배치docker service create 로 이미지·복제본 수·노드 제약을 선언하면 스웜이 이를 여러 개의 태스크(컨테이너 한 개 단위)로 쪼개 각 워커 노드에 배치합니다. 노드가 죽거나 예약된 상태가 되면 다른 노드로 자동 재배치되고, 수동 변경은 새 서비스 버전을 모든 노드에 순차 반영해 롤백도 가능하게 합니다.

매니저 노드를 하나 골라 스웜을 초기화한 뒤 워커·매니저 노드를 붙이고, 노드 promote/drain/rm 같은 명령으로 클러스터 구성을 관리하는 것.

1문제 상황

클러스터를 구성한 뒤에도 노드 상태는 계속 변합니다. 유지보수를 위해 잠시 서버를 꺼야 하고, 그 서버에서 돌던 컨테이너는 건드리지 않고 다른 곳으로만 옮겨야 합니다. 반대로 장애가 발생한 노드나 용도 없는 노드는 목록에서 지워야 합니다.

기존의 단일 서버 방식에는 이런 상태를 다루는 명령이 없습니다. 컨테이너를 하나씩 확인하고 필요하면 직접 지운 뒤 다시 띄우는 수작업만 가능하며, 서버가 몇 대로 늘어나면 이걸 사람이 기억하고 처리할 수 없습니다. 그래서 노드 단위의 상태 변경을 즉시 반영하는 클러스터 관리 명령이 필요합니다.

2핵심 질문

노드를 유지보수 상태로 만들거나, 역할을 바꾸거나, 목록에서 제거하는 일을 서버에 손대지 않고 명령 한 줄로 끝낼 수 있을까요?

3동작 예시

워커 노드 세 대가 돌아가는 스웸에서, 유지보수가 필요해 web-2 를 drain 합니다. drain 은 그 노드에서 새로 스케줄되는 것을 막고, 이미 실행 중인 태스크는 다른 노드로 이동을 시키고 나서 노드를 예약 불가 상태로 남겨 둡니다. 이 과정을 거치면 서버를 꺼도 서비스 복제본 수는 그대로 유지됩니다.

4동작 과정

  1. 스웸 초기화와 클러스터 참여매니저 노드에서 docker swarm init 으로 스웜을 만들고, 나머지 노드는 --token 으로 발급된 비밀값을 docker swarm join 에 넣어 편입합니다. 이때 --advertise-addr 로 클러스터 간 통신에 쓸 주소를 지정하고, docker node ls 로 편입된 노드와 상태를 확인합니다.
  2. 노드 상태 제어docker node update 의 --availability drain 은 그 노드에 새 태스크를 배정하지 않게 하고 실행 중인 태스크를 다른 곳으로 옮깁니다. --availability active 는 다시 배정을 허용하고, --role manager 로는 매니저와 워커 역할을 바꿉니다. 새로 편입한 워커를 매니저로 올릴 때는 노드를 drain 한 뒤 promote 해야 기존 태스크를 먼저 비울 수 있습니다.
  3. 노드 제거매니저 노드에서 docker swarm leave 또는 docker node update --availability drain 후 docker node rm 으로 노드를 클러스터에서 지웁니다. 제거된 노드에 할당돼 있던 태스크는 다른 노드로 재배치되고, 매니저 노드를 지울 때는 먼저 다른 매니저로 옮겨야 합니다.

5한 줄 요약

게다가 클라이언트나 다른 컨테이너가 그 컨테이너에 접속하려면 각 서버의 IP와 포트를 일일이 알아야 하고, 한 서버가 죽을 때마다 접속 대상을 직접 바꿔야 합니다. 결국 "어떤 컨테이너를 몇 개 어디에 띄울지"와 "누가 어디로 접근하는지"를 코드로 선언할 수 있는 수단이 필요합니다.

2핵심 질문

원하는 컨테이너와 개수, 배치 제약을 명령으로 선언하면 여러 노드에 자동으로 배치되고, 서비스 이름만으로 그 컨테이너에 접근할 수 있게 할 수 있을까요?

3동작 예시

docker service create --name web -p 8080:80 --replicas 3 nginx 를 실행하면, 이미지 nginx 의 복제본 3개가 세 노드에 나뉘어 태스크로 실행되고, 각 컨테이너 안의 80번 포트가 실행한 노드의 8080 포트로 공개됩니다. 외부에서 web 이라는 이름으로 접속하면 8080 포트로 들어온 요청이 세 복제본 중 하나로 전달되고, 특정 노드가 죽으면 그 태스크가 다른 노드로 옮겨가 같은 이름으로 계속 접근됩니다.

4동작 과정

  1. 서비스 선언docker service create 로 이미지, 복제본 수(--replicas), 포트 발행, 노드 제약(--constraint)을 함께 적습니다. 스웸은 이 선언을 태스크 단위로 쪼개 조건에 맞는 워커 노드에 배치하고, 서비스의 상태와 로깅 드라이버, 롤백 지점도 이 선언의 일부로 관리합니다.
  2. 접근 경로 부여클라이언트 모드 ingress 는 노드마다 포트를 열어 두고 요청을 받을 때마다 살아 있는 태스크 하나에 forwards 방식으로 연결합니다. 게시한 포트 수를 노드 수보다 크게 잡으면, 어떤 노드가 죽어도 다른 노드로 요청이 도달할 수 있는 포트가 남습니다. 내부 통신만 필요하면 --mode host 로 노드의 네트워크를 그대로 사용합니다.
  3. 업데이트와 롤백docker service update 로 이미지·복제본·제약을 바꾸면 현재 버전에서 수정 버전으로 롤링 업그레이드가 일어나고, 한 노드에서 한 번에 하나씩 태스크를 갈아끼웁니다. docker service rollback 은 이전 버전으로 되돌리며, 스케줄 불가 상태로 만든 노드(--availability drain)는 자동 재배치 대상에서 빠집니다.

1문제 상황

Docker 엔진이 기본으로 제공하는 명령만으로는 현장에서 필요한 기능을 모두 다루기 어렵습니다. 특정 저장소 연동을 자동으로 설정하고 싶거나, 보안 스캔 결과를 바로 상세하게 보고하고 싶어도 기본 CLI에 해당 명령이 없습니다.

이렇게 필요한 기능마다 외부 스크립트를 따로 만들어 어디에 설치됐는지 관리해야 하고, 사용자는 어떤 플러그인이 있는지, 무엇이 설치됐는지 알 수 없습니다. 설치 경로와 관리 주체도 제각각이라 설치·삭제·버전 확인을 일일이 해야 합니다.

2핵심 질문

Docker에 기본으로 없는 기능을 정해진 규격으로 만들어 붙이면, 설치·목록·삭제까지 명령으로 관리되며 CLI와 대시보드에서 바로 쓸 수 있을까요?

3동작 예시

직접 만든 플러그인 바이너리에 metadata.json 과 플러그인 등록 정보를 넣고, 클라이언트 쪽에 설치하면 docker scan --severity high 같은 명령이 셸 경로 탐색 규칙에 따라 플러그인 바이너리로 전달됩니다. 이제 기본 엔진 바이너리에는 손대지 않고도 새 서브명령이 붙고, docker info 나 대시보드에서 플러그인 목록과 활성화 상태를 확인할 수 있습니다.

4동작 과정

  1. 확장 지점 정의엔진은 볼륨 플러그인, 네트워크 플러그인, 인증 플러그인, metric, attestation 등 정해진 지점에 외부 구현이 끼어들 수 있도록 gRPC 기반 계약을 노출합니다. 플러그인은 이 계약을 지켜 만들어야 엔진이 호출할 수 있습니다. 또한 관리자 플러그인 API(metadata.json, 루트 디렉터리, 네트워크 접근 범위, 권한 동작)를 통해 CLI에 붙는 플러그인의 배치와 권한을 선언합니다.
  2. 배포와 설치플러그인은 전용 레지스트리에 OCI 아티팩트로 푸시하고, 데스크톱에서 docker desktop plugin install 로 설치하며 서버에서는 플러그인 디렉터리에 직접 배치합니다. 관리자 플러그인은 ~/.docker/cli-plugins 에, 볼륨·네트워크 같은 전역 플러그인은 ~/.docker/plugins 에 두는처럼 설치 위치가 정해져 있고, 클라이언트는 이 위치와 PATH 를 정해진 순서로 탐색해 플러그인 전용 바이너리를 찾습니다.
  3. 관리와 사용설치된 플러그인은 docker info 와 대시보드에서 이름·버전·활성 여부로 확인하고, 필요한 것은 disable·uninstall 로 끄거나 지웁니다. 대시보드 쪽 확장은 Settings 의 Plugins 항목에서 사용자 플러그인을 탭으로 붙이며, 이미지·볼륨·빌더·Kubernetes 화면을 프로젝트·조직에 맞춰 바꾸는 기능을 함께 제공합니다.

Testcontainers처럼 코드에서 컨테이너를 임시로 띄워 실제 서비스로 통합 테스트하고, 기존 자동 빌드·테스트 환경을 현대적인 CI/CD 구성으로 옮기는 방법.

1문제 상황

애플리케이션이 실제로 만나는 메시지 저장소나 데이터베이스를 가짜로 대체해 테스트하면, 실제 환경과 동작이 달라져 버그가 그대로 통과합니다. 그렇다고 CI 서버마다 DB를 직접 설치해 두면 버전이 서로 어긋나고, 설치와 정리까지 매번 수작업으로 따라야 합니다.

기존 테스트 환경은 개발자 PC에 의존하는 경우가 많아 팀마다 다른 버전과 다른 설정으로 테스트하게 되고, 테스트가 끝난 뒤 남은 프로세스 때문에 다음 실행이 실패하기도 합니다. 결국 필요한 외부 서비스를 자동으로 준비하고 자동으로 치우는 수단이 없으면 실제 서비스와의 연동 검증이 구조적으로 불가능합니다.

2핵심 질문

테스트 코드 안에서 필요한 외부 서비스 컨테이너를 잠깐 띄우고 테스트가 끝나면 자동으로 치울 수 있게 만들면, 실제 서비스와 붙는 통합 테스트를 어디서든 같은 조건으로 돌릴 수 있을까요?

3동작 예시

테스트 코드에서 PostgreSQL 컨테이너를 요청하면 Testcontainers 가 Docker API로 컨테이너를 생성하고, 로그 한 줄이 나올 때까지 기다린 뒤 랜덤한 포트로 매핑해 접속 정보를 넘겨줍니다. 테스트가 끝나면 컨테이너와 볼륨을 자동 삭제하므로, 개발자 PC든 CI 컨테이너 안이든 같은 테스트 코드가 그대로 실행됩니다.

4동작 과정

  1. 컨테이너 선언과 준비테스트 코드가 모듈·이미지/태그·환경변수·포트 조건을 지정해 컨테이너를 요청하고, Testcontainers 가 Docker 엔진에 컨테이너를 생성해 이미지가 빌드되고 실행될 때까지 기다립니다. replica 모드 컨테이너를 쓰면 같은 이미지를 여러 개 띄우고 그 안에서 클러스터를 직접 구성해 볼 수 있습니다.
  2. 대기와 네트워크 매핑지정한 로그 문자열이 나타나거나 포트 응답이 살아날 때까지 폴링해 실제 준비 완료 시점을 잡습니다. 각 컨테이너는 랜덤 포트를 호스트에 매핑되므로 여러 테스트나 여러 컨테이너가 포트 충돌 없이 동시에 돌아가고, 내부망으로 서로 통신할 수 있는 네트워크도 만들어 줍니다.
  3. 수명 주기와 마이그레이션테스트가 끝나면 컨테이너와 볼륨을 한꺼번에 회수해 이전 실행의 흔적을 남기지 않습니다. 기존 자동 빌드·테스트 파이프라인에서는 빌드 단위를 컨테이너 이미지로 옮기고, 개발용 의존 서비스도 코드로 선언해 두고, 파이프라인 전체를 코드로 관리하는 방식으로 구성을 현대화합니다.
