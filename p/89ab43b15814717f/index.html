데이터를 처리하는 방식은 두 가지였습니다. 배치 처리는 정해진 시간에 모아둔 데이터를 한 번에 처리했고, 스트리밍 처리는 개별 데이터가 들어올 때마다 즉시 처리했습니다. 대량의 데이터를 처리하려면 한 대의 컴퓨터는 부족하므로 여러 노드로 나눠 계산했습니다. 그리고 이 모든 자원은 AWS 리전과 VPC라는 네트워크 경계 안에 배치됩니다.

#2핵심 질문

데이터 엔지니어는 배치와 스트리밍을 어떻게 선택하고, 대규모 처리를 어떻게 분산시키며, 클라우드 인프라의 경계 안에서 어떻게 자원을 구성하는가?

#3동작 예시

시스템 아키텍처는 세 겹의 선택지를 가집니다. 첫째, 처리 방식(배치 vs 스트리밍) — 정해진 시간에 대량 처리할 것인가, 발생 즉시 처리할 것인가. 둘째, 컴퓨팅 방식(분산) — 한 컴퓨터로 할 수 없는 크기면 여러 노드로 나눠 계산합니다. 셋째, 배치 위치(리전·VPC) — 어느 AWS 리전에서 실행할지, 어느 VPC 서브넷에서 실행할지를 결정합니다.

#4동작 과정

  1. 처리 패턴 결정배치는 매시간, 매일 등 정해진 주기에 누적된 데이터를 한 번에 처리하고(예: 일일 리포트 생성), 스트리밍은 실시간 이벤트가 들어올 때마다 즉시 처리합니다(예: 클릭 이벤트 수집). 사업 요건에 따라 선택합니다.
  2. 분산 아키텍처 구성한 대의 머신으로 처리할 수 없는 규모면, Spark나 Hadoop 같은 분산 처리 엔진을 여러 노드에서 병렬로 실행합니다. AWS Glue(Spark 기반)나 EMR(Hadoop/Spark)을 사용합니다.
  3. 클라우드 인프라 배치모든 자원(컴퓨팅 노드, 저장소, 네트워크)은 특정 AWS 리전 내에, 그리고 VPC라는 격리된 가상 네트워크 안에 배치됩니다. 이는 데이터 지역성, 보안, 규정 준수 등의 요구사항을 충족시킵니다.

#5한 줄 요약

데이터 처리를 배치 또는 스트리밍 중 하나로 선택하고, 대규모 계산을 분산 컴퓨팅으로 확장하며, 이 모든 것을 AWS 리전과 VPC라는 경계 안에서 안전하게 구성하는 데이터 엔지니어링의 기본 틀

S3 버킷·객체·키와 스토리지 클래스별 비용 구조

S3는 버킷이라는 통 안에 키(이름)로 객체(파일)를 넣는 저장소이며, 얼마나 자주 꺼내 쓰느냐에 따라 Standard·Intelligent-Tiering·Glacier 같은 스토리지 클래스를 골라 비용을 조절한다.

#1문제 상황

지금까지는 파일 저장소를 사용할 때 모든 데이터에 같은 가격을 냈습니다. 자주 꺼내 쓰는 데이터도, 거의 안 꺼내 쓰는 데이터도 같은 비용이었습니다. AWS S3는 데이터 사용 패턴에 따라 저장소를 여러 등급으로 나누어, 실제 사용량에 맞게 비용을 조정하게 합니다.

#2핵심 질문

S3에서는 데이터의 사용 빈도에 따라 어떻게 저장 방식과 비용을 다르게 책정하는가?

#3동작 예시

S3 버킷은 통 역할을 하고, 그 안에 객체(파일)를 키(이름)로 저장합니다. 각 객체는 저장할 때 스토리지 클래스를 지정할 수 있습니다. Standard(자주 쓰는 데이터, 비싼 저장료·싼 조회료), Intelligent-Tiering(사용 패턴 모르면 자동 최적화), Glacier(거의 안 쓰는 데이터, 싼 저장료·비싼 조회료). 사용 패턴에 맞춰 고르면 전체 비용이 줄어듭니다.

#4동작 과정

  1. 버킷과 객체 구조 이해S3 버킷은 전 세계에서 고유한 이름을 가진 저장소이며, 그 안에 객체를 저장합니다. 각 객체는 키(경로/파일명)로 식별되고, 메타데이터(크기, 수정 시간, 스토리지 클래스 등)를 가집니다.
  2. 사용 패턴에 따른 클래스 선택데이터가 들어올 때 그것을 어디에 저장할지 결정합니다. 실시간 분석에 쓸 데이터는 Standard, 정기적으로만 쓸 데이터는 Standard-IA(Infrequent Access), 거의 안 쓸 데이터는 Glacier로 저장하여 비용을 절감합니다.
  3. 저장료와 조회료 트레이드오프Standard는 저장료가 높지만 꺼내 쓸 때 추가 비용이 적습니다. Glacier는 저장료가 싸지만 꺼낼 때 추가 비용이 발생합니다. 데이터별 사용 빈도를 고려해 선택합니다.

#5한 줄 요약

데이터의 사용 빈도를 기준으로 여러 스토리지 클래스를 제공하여, 자주 쓰는 데이터는 빠르게, 거의 안 쓰는 데이터는 저렴하게 저장할 수 있도록 하고, 전체 저장 비용을 최소화하는 것

S3 수명주기·버전 관리·복제와 데이터 보존·삭제·복원력

수명주기 규칙으로 오래된 데이터를 자동으로 저렴한 클래스로 옮기거나 지우고, 버전 관리와 복제로 실수 삭제와 리전 장애에 대비하는 보존 전략이다.

#1문제 상황

데이터를 저장하면서 두 가지 위험이 생깁니다. 첫째, 데이터를 실수로 삭제하거나 덮어쓸 수 있습니다. 둘째, AWS 리전 전체가 장애나 재해로 손상될 수 있습니다. 또한 오래된 데이터를 수동으로 하나하나 삭제하거나 저장 클래스를 바꾸는 것은 번거롭습니다.

#2핵심 질문

S3에서는 오래된 데이터를 자동으로 관리하고, 실수 삭제와 리전 장애로부터 데이터를 보호하려면 어떤 기능을 써야 하는가?

#3동작 예시

S3는 세 가지 보호 메커니즘을 제공합니다. 수명주기(Lifecycle) 규칙으로 오래된 데이터를 자동으로 저장 클래스를 바꾸거나 삭제합니다. 버전 관리(Versioning)를 켜면, 같은 객체를 덮어쓰거나 삭제해도 이전 버전들이 남습니다. 복제(Replication)를 설정하면, 한 리전의 객체가 다른 리전으로 자동 복사되어 리전 장애에 대비합니다.

#4동작 과정

  1. 수명주기 규칙 설정객체가 30일 된 후 Intelligent-Tiering으로 옮기고, 90일 된 후 Glacier로 옮기고, 1년 후에 삭제하라는 규칙을 설정합니다. 이제 부터는 데이터가 자동으로 정책에 따라 이동하고 정리됩니다.
  2. 버전 관리 활성화버킷에 버전 관리를 켜면, 같은 키로 여러 객체를 업로드해도 이전 버전이 보존됩니다. 실수로 덮어쓰거나 삭제한 데이터도 버전 ID를 알면 복구할 수 있습니다.
  3. 복제 구성같은 리전이나 다른 리전으로 자동 복제 규칙을 설정합니다. 한 리전이 장애나 재해로 손상되어도 다른 리전의 복제본으로 데이터 손실을 방지합니다.

#5한 줄 요약

수명주기로 데이터를 자동 정리하고, 버전 관리로 실수 삭제로부터 보호하며, 복제로 리전 장애에 대비하여 데이터 보존 전략을 구현하고 비즈니스 연속성을 확보하는 것

데이터 파일 형식과 압축: CSV·JSON·Avro·Parquet·ORC

행 단위로 저장하는 CSV·JSON·Avro와 열 단위로 저장하는 Parquet·ORC의 차이, 그리고 압축 코덱 선택이 스캔량과 쿼리 비용을 좌우한다.

#1문제 상황

CSV와 JSON은 데이터를 한 줄(행) 단위로 저장합니다. 특정 몇 개 열만 필요해도 전체 행을 읽어야 하므로 불필요한 데이터까지 메모리에 로드됩니다. Parquet과 ORC는 데이터를 열 단위로 저장해서 필요한 열만 읽을 수 있지만, 행 기반 형식에 비해 초기 학습 곡선이 높습니다.

#2핵심 질문

같은 데이터를 행 단위로 저장하는 것과 열 단위로 저장하는 것은 쿼리 성능과 스토리지 비용에 어떻게 영향을 미칠까요?

#3동작 예시

100열짜리 테이블에서 3개 열만 필요할 때, CSV/JSON은 100개 열을 모두 읽고 나머지는 버립니다. Parquet/ORC는 필요한 3개 열의 파일 블록만 읽습니다. 이것이 I/O 감소의 핵심입니다.

#4동작 과정

  1. 행 기반 형식의 동작CSV와 JSON은 각 행을 연속된 바이트로 저장합니다. Athena(AWS의 SQL 쿼리 엔진)가 한 행을 읽으려면 모든 열의 데이터를 함께 로드해야 하므로 선택하지 않은 열까지 S3에서 읽어옵니다.
  2. 열 기반 형식의 동작Parquet과 ORC는 각 열의 데이터를 별도 블록으로 저장합니다. 쿼리 엔진은 필요한 열의 블록만 S3에서 요청하므로 읽는 데이터양이 대폭 줄어듭니다.
  3. 압축 코덱의 선택gzip, snappy, lz4 등 압축 알고리즘은 압축률과 압축/해제 속도가 다릅니다. 행 기반 형식도 열 기반 형식도 압축 가능하지만, 열 기반 형식은 열 내 데이터 특성이 더 균질해서 압축률이 더 높습니다.

파티셔닝·파일 크기·정렬 등 저장 레이아웃 최적화

날짜 같은 기준으로 폴더를 나누고(파티셔닝) 파일을 너무 잘게 쪼개지 않게 모아 두면 쿼리가 읽을 데이터를 줄여 훨씬 빠르고 싸진다.

#1문제 상황

기존 방식은 S3에 저장된 모든 데이터가 단순 폴더 구조로 놓여있거나 너무 잘게 쪼개진 작은 파일들로 산재합니다. 쿼리를 실행할 때 필요 없는 영역의 파일까지 모두 스캔해야 하고, 너무 많은 작은 파일은 S3 요청 오버헤드를 증가시킵니다.

#2핵심 질문

쿼리가 꼭 필요한 데이터만 읽도록 파일을 미리 정리해두면 스캔량을 줄일 수 있을까요?

#3동작 예시

1년치 로그 데이터 1PB가 있을 때, 특정 날짜 3일의 데이터만 필요합니다. 파티셔닝이 없으면 1PB를 모두 스캔하지만, year=2026/month=09/day=14/ 같은 폴더 구조로 나누면 3일치 폴더만 읽으므로 스캔량이 1/120로 줄어듭니다.

#4동작 과정

  1. 파티셔닝으로 범위 축소날짜, 지역, 사용자 ID 같은 조회 기준으로 폴더를 구분합니다. Athena는 WHERE 절에서 파티션 조건을 감지하면 해당 폴더만 스캔합니다.
  2. 파일 크기 최적화너무 작은 파일(수 MB)은 많은 개수의 S3 요청을 만들고, 너무 큰 파일(수 GB)은 병렬 처리를 방해합니다. 일반적으로 파일당 128MB~1GB 크기가 최적입니다.
  3. 통계 정보와 정렬파티션 내 파일들을 정렬 키 순서로 저장하면 쿼리 엔진이 조기 종료(early termination)를 할 수 있고, 파일의 최소/최대값 통계를 저장하면 불필요한 파일 블록을 건너뜁니다.

개방형 테이블 형식: Apache Iceberg·Hudi·Delta Lake와 S3 Tables

S3 위의 파일 묶음에 스키마 변경·시점 조회·행 단위 갱신 같은 데이터베이스다운 기능을 얹는 테이블 형식들이며, S3 Tables는 Iceberg 테이블을 AWS가 관리해 주는 전용 버킷이다.

#1문제 상황

S3의 파일은 한 번 쓰면 수정할 수 없으므로 스키마 변경, 데이터 삭제/갱신, 특정 시점의 스냅샷 조회는 모두 새로운 파일을 만들어야 합니다. 이는 ACID 트랜잭션 같은 데이터베이스의 기본 기능을 S3 데이터 레이크에서 구현하기 어렵게 만듭니다.

#2핵심 질문

S3의 파일들 위에 메타데이터 레이어를 얹어 스키마 진화, 트랜잭션, 시점 조회 같은 데이터베이스 기능을 만들 수 있을까요?

#3동작 예시

Iceberg는 S3의 각 파일을 버전 관리합니다. 스키마를 변경할 때 새로운 메타데이터 파일을 작성하고, 이전 스키마는 메타데이터 히스토리에 남습니다. 쿼리할 때 특정 메타데이터 버전을 지정하면 과거 스냅샷을 조회할 수 있습니다.

#4동작 과정

  1. 메타데이터 레이어Apache Iceberg, Apache Hudi, Delta Lake는 모두 S3의 파일 묶음을 추적하는 메타데이터 디렉토리(manifest, transaction log 등)를 관리합니다. 이 메타데이터가 현재 테이블의 상태를 정의합니다.
  2. 스키마 진화와 트랜잭션스키마 변경, 데이터 삽입, 삭제, 갱신 같은 작업은 메타데이터만 변경하고 기존 파일은 유지합니다. 이를 통해 다중 쓰기 작업도 안전하게 처리하고 ACID 보장을 제공합니다.
  3. S3 Tables 서비스AWS는 Iceberg 호환 테이블 형식을 자신이 관리하는 전용 S3 버킷 내에서 제공합니다. 사용자는 메타데이터 관리 복잡성을 줄이고 네이티브 AWS 서비스(Athena, EMR 등)와의 통합을 단순화할 수 있습니다.

#5한 줄 요약

S3의 파일 묶음에 메타데이터 기반 버전 관리와 트랜잭션 지원을 얹어 데이터 레이크의 안정성과 유지보수성을 관계형 데이터베이스 수준으로 끌어올리는 것

데이터 스토어 선택: 접근 패턴·비용·성능 트레이드오프

데이터를 어떻게 읽고 쓰는지(접근 패턴)를 먼저 정하고 그에 맞는 스토어를 고르는 것이 비용·성능의 출발점이다.

#1문제 상황

AWS는 S3, RDS, DynamoDB, Redshift, ElastiCache 등 다양한 데이터 스토어를 제공합니다. 기존 방식은 어떤 스토어를 선택해야 할지 기술 이름과 기능만 비교했고, 실제 데이터 접근 방식이 각 스토어의 성능과 비용에 어떻게 영향을 미치는지 고려하지 않았습니다.

#2핵심 질문

데이터를 어떤 방식으로 읽고 쓸지에 따라 최적의 스토어와 비용이 달라질까요?

#3동작 예시

같은 고객 정보 데이터를 세 가지 방식으로 접근합니다: (1) 분석 쿼리로 전체 고객의 구매 패턴을 분석하면 S3 + Athena, (2) 특정 고객 ID로 실시간 주문 조회하면 DynamoDB, (3) 여러 테이블을 조인한 복잡한 보고서는 RDS/Aurora입니다. 같은 데이터도 접근 방식에 맞는 스토어를 고르면 비용과 응답 시간이 크게 달라집니다.

#4동작 과정

  1. 접근 패턴 정의데이터를 어떻게 읽을지(스캔/포인트 조회/범위 검색), 얼마나 자주 쓸지(배치/실시간), 일관성 요구도(강한 일관성/최종 일관성)를 먼저 파악합니다.
  2. 각 스토어의 특성 이해S3는 대용량 배치 분석, RDS/Aurora는 복잡한 쿼리와 트랜잭션, DynamoDB는 단순하고 빠른 키-값 조회, Redshift는 대규모 OLAP에 최적화되어 있습니다.
  3. 트레이드오프 평가각 스토어의 처리량, 지연 시간, 저장 비용, 쿼리 비용을 조합해 전체 TCO(총소유비용)를 계산합니다. 가장 저렴한 것이 아니라 요구사항을 만족하면서 비용이 최소인 선택지를 고릅니다.

#5한 줄 요약

데이터 스토어 선택의 첫 번째 기준은 접근 패턴이며, 접근 패턴에 맞는 스토어를 고르는 것이 비용과 성능의 모든 최적화의 시작점이라는 것

Amazon RDS와 Aurora: 관계형 스토어·복제본·잠금 관리

RDS는 관리형 관계형 DB이고 Aurora는 스토리지를 분리해 읽기 복제본과 장애 복구를 빠르게 만든 클라우드 네이티브 엔진이다.

#1문제 상황

전통적인 관계형 데이터베이스(MySQL, PostgreSQL)는 스토리지(디스크)와 컴퓨트(CPU, 메모리)가 같은 서버에 묶여있습니다. 읽기 부하를 줄이려면 복제본을 만들어야 하는데, 각 복제본이 독립적인 스토리지를 가지므로 비용이 많이 들고, 장애 복구도 느립니다.

#2핵심 질문

스토리지와 컴퓨트를 분리하면 읽기 복제본 확장과 장애 복구 속도를 크게 개선할 수 있을까요?

#3동작 예시

RDS는 기존 엔진을 관리형 서비스로 제공합니다. Aurora는 MySQL/PostgreSQL 호환 문법을 유지하면서 내부 아키텍처를 완전히 바꿨습니다. 공유 스토리지 계층(AWS 독점 엔진)을 여러 읽기 전용 복제본이 동시에 접근하므로, 각 복제본이 전체 데이터 사본을 갖지 않아도 됩니다.

#4동작 과정

  1. RDS의 구조주 인스턴스(읽기/쓰기)와 읽기 복제본(읽기 전용)이 각각 독립적인 스토리지를 가집니다. 쓰기는 주 인스턴스에만 가능하고 복제본으로 비동기 복제됩니다.
  2. Aurora의 아키텍처여러 읽기 복제본이 하나의 공유 스토리지 계층에 접근합니다. 스토리지 계층은 자동으로 3개 가용영역에 복제되므로 개별 복제본은 전체 데이터를 갖지 않아도 됩니다. 주 인스턴스 장애 시 읽기 복제본이 즉시 승격(promote)되어 복구 시간이 몇 초로 단축됩니다.
  3. 잠금과 일관성 관리Aurora는 분산 잠금 메커니즘으로 다중 쓰기 인스턴스를 지원합니다(MySQL 8.0 호환). 모든 인스턴스가 같은 스토리지에 접근하므로 강한 일관성을 유지합니다.

#5한 줄 요약

스토리지 계층을 분리해 읽기 복제본 확장성과 장애 복구 속도를 획기적으로 개선하면서도 ACID 트랜잭션과 강한 일관성을 유지한다는 것

DynamoDB 데이터 모델: 파티션 키·정렬 키·보조 인덱스

파티션 키로 데이터를 흩뿌리고 정렬 키로 범위를 찾으며, 다른 조회 축이 필요하면 보조 인덱스를 만든다.

#1문제 상황

관계형 데이터베이스는 여러 테이블을 조인해서 유연한 쿼리를 만듭니다. 하지만 규모가 커지면 조인이 느려지고 수평 확장이 어려워집니다. NoSQL로의 전환을 시도해도 어떻게 데이터를 구조화해야 할지 명확하지 않습니다.

#2핵심 질문

조인 없이도 자주 필요한 데이터를 빠르게 찾고 범위 검색까지 할 수 있는 데이터 모델은 어떻게 설계할까요?

#3동작 예시

주문 데이터에서 고객 ID 12345의 모든 주문을 찾으려면, 파티션 키를 customer_id로 설정합니다. 그 고객의 최근 주문부터 찾으려면 정렬 키를 order_date(내림차순)으로 설정합니다. 그러면 DynamoDB가 파티션 키로 12345 데이터를 찾고, 그 내에서 날짜 순서로 스캔하므로 조인 없이 한 번의 쿼리로 끝납니다.

#4동작 과정

  1. 파티션 키로 수평 분산파티션 키는 DynamoDB가 데이터를 여러 파티션(서버)에 흩뿌리는 기준입니다. 같은 파티션 키를 가진 모든 항목은 같은 파티션에 저장되고 1개 파티션의 처리량 한계는 4KB/초입니다. 파티션 키를 잘못 고르면 핫 파티션(특정 파티션에 트래픽 집중)이 발생합니다.
  2. 정렬 키로 범위 검색파티션 키가 같은 항목들을 정렬 키로 순서대로 저장합니다. 쿼리는 파티션 키로 파티션을 찾고 정렬 키의 범위(예: 2026-01-01부터 2026-09-14까지)를 지정해서 검색합니다.
  3. 보조 인덱스로 다른 조회 축 지원파티션 키로만 쿼리하면 다른 속성(예: 상품 ID)로는 검색할 수 없습니다. 보조 인덱스(Global Secondary Index, GSI)를 만들면 다른 속성을 파티션 키로 하는 별도 인덱스 테이블을 생성해서 다양한 조회 축을 지원합니다.

#5한 줄 요약

파티션 키로 수평 확장을 실현하고 정렬 키와 보조 인덱스로 조인 없이도 다양한 접근 패턴을 지원하는 구조

DynamoDB 운영: 용량 모드·스로틀링·TTL·DynamoDB Streams

온디맨드/프로비저닝 용량 모드로 처리량을 정하고, 한도를 넘으면 스로틀링이 나며, TTL로 만료 삭제하고 Streams로 변경을 흘려보낸다.

→ 03-03 참조

#1문제 상황

기존 데이터베이스는 처리량(초당 읽기/쓰기 횟수)을 미리 예약하거나 수동으로 늘려야 합니다. 트래픽 변동에 대응하기 어렵고 예상치 못한 스파이크가 오면 쿼리가 실패합니다. 데이터 정리와 변경 추적도 수동으로 해야 합니다.

#2핵심 질문

DynamoDB의 처리량을 자동으로 조절하고 데이터 변경을 다른 시스템에 흘려보낼 수 있을까요?

#3동작 예시

온디맨드 모드에서는 요청이 오면 요청 단위로 비용을 냅니다. 프로비저닝 모드에서는 초당 읽기/쓰기 용량을 미리 정하고 고정 비용을 냅니다. TTL을 설정하면 지정한 시간 후 자동으로 항목을 삭제합니다. Streams를 활성화하면 모든 쓰기 작업(INSERT, UPDATE, DELETE)이 변경 스트림으로 흘러나와서 Lambda, Firehose 같은 외부 서비스가 구독할 수 있습니다.

#4동작 과정

  1. 용량 모드 선택온디맨드(On-Demand) 모드는 트래픽 변동이 크거나 예측하기 어려운 워크로드에 적합합니다. 프로비저닝 모드는 트래픽이 안정적이고 예측 가능하면 더 저렴합니다. 용량을 초과하면 스로틀링(throttling)이 발생해서 요청이 실패하거나 재시도 지연이 생깁니다.
  2. 스로틀링과 TTL 관리프로비저닝 모드에서 용량을 초과한 요청은 거부되므로 애플리케이션은 지수 백오프(exponential backoff) 재시도로 대응해야 합니다. TTL(Time To Live)을 설정하면 만료된 항목을 DynamoDB가 자동으로 삭제해서 스토리지와 비용을 절감합니다.
  3. Streams로 변경 추적DynamoDB Streams는 모든 쓰기 작업을 순서대로 기록하고, 초당 1MB의 처리량으로 외부로 흘려보냅니다. Lambda 함수가 이를 구독해서 실시간 알림 전송, 분석 데이터 로깅, 다른 데이터베이스 동기화 같은 작업을 자동으로 처리할 수 있습니다.

#5한 줄 요약

데이터를 웨어하우스로 옮기지 않고 S3(Spectrum)나 운영 DB(페더레이티드 쿼리)를 직접 조회하고, 구체화 뷰로 결과를 미리 저장하며, zero-ETL로 소스 DB 변경을 파이프라인 없이 자동 복제한다.

#1문제 상황

기존 방식은 모든 데이터를 먼저 Redshift로 복사한 후 분석해야 하므로 ETL 파이프라인을 구성해야 합니다. 복사 과정에서 시간과 비용이 소모되고, 원본 데이터가 자주 변경되면 동기화가 복잡하며, 저장 비용도 증가합니다.

#2핵심 질문

데이터를 이동하지 않고 원본 위치에서 직접 조회하거나, 변경사항을 자동으로 반영할 수 있을까요?

#3동작 예시

S3에 있는 로그 파일을 Spectrum으로 Redshift SQL에서 직접 조회하고, 운영 DB의 테이블을 페더레이티드 쿼리로 조인하며, 자주 조회하는 집계 결과(월별 매출 합계)는 구체화 뷰로 미리 계산해 저장하고, 소스 DB의 변경(INSERT, UPDATE, DELETE)은 zero-ETL로 자동 반영합니다.

#4동작 과정

#2핵심 질문

#4동작 과정

  1. 클러스터 생성프로비저닝형(브로커 개수·크기 사전 지정) 또는 Serverless(자동 스케일) 중 선택해 Kafka 클러스터를 구성합니다.
  2. 토픽과 메시지 흐름토픽(Kafka의 메시지 채널)을 만들고, Producer에서 메시지를 보내면 Consumer가 구독해 받습니다.

#2핵심 질문

#3동작 예시

DMS 복제 인스턴스가 먼저 원본 DB 전체를 스냅샷으로 대상(AWS RDS·Redshift 등)에 복사한 후, 계속 원본의 변경사항만 따라가며 적용하므로 운영을 중단하지 않아도 됩니다.

AWS Glue 구성 요소

Glue 작업은 Spark·Python shell·스트리밍 등 유형을 고르고 워커 타입(G.1X 등)과 DPU 수로 처리 용량을 정하는 서버리스 ETL 실행 단위다.

#1문제 상황

데이터 변환 작업을 전통적으로 하려면 Spark 클러스터를 직접 띄워야 했다. 클러스터 구성, 스케일 조정, 비용 예측이 복잡했고, 사용하지 않는 시간에도 비용이 발생했다. 변환 작업의 크기가 크면 클러스터를 미리 크게 띄워야 하고, 작으면 자원이 낭비된다.

#2핵심 질문

변환 작업의 크기에 맞춰 유연하게 리소스를 할당하면서도 인프라 관리는 최소화하려면 어떻게 할까?

#3동작 예시

일일 데이터 정제 작업이 2시간 걸리면, Glue 작업을 정의할 때 '10개의 DPU(처리 능력 단위)로 Python 코드 실행'이라고 지정하면, AWS가 자동으로 그 크기의 워커 장비를 할당했다가 작업이 끝나면 비용 청구 없이 해제한다.

#4동작 과정

  1. 작업 유형 선택Spark 배치 처리, Python Shell(가벼운 작업), 스트리밍 중 어느 방식으로 실행할지 선택한다.
  2. 워커와 DPU 결정워커 타입(G.1X는 일반용, G.2X는 고성능)과 DPU 개수(데이터 처리 능력)를 지정해서 필요한 리소스 크기를 정한다.
  3. 서버리스 실행지정된 스펙으로 AWS가 자동으로 워커 장비를 띄웠다가 작업 완료 후 비용 청구 없이 해제한다.

Glue ETL 개발

스키마가 유연한 DynamicFrame과 Spark DataFrame으로 변환 코드를 짜고, Glue Studio 비주얼 편집기와 작업 북마크(이미 처리한 데이터 건너뛰기)로 개발과 증분 처리를 단순화한다.

#1문제 상황

일반적인 Spark DataFrame은 엄격한 스키마를 요구하므로, 반정형 또는 스키마가 자주 바뀌는 데이터(JSON 중첩 구조, 동적 필드 등)를 다루기 어렵다. 스키마 불일치로 작업이 실패하면 코드를 수정해서 다시 실행해야 한다. 큰 파일을 다시 처리할 때 이미 처리한 부분까지 다시 계산하므로 시간이 낭비된다.

#2핵심 질문

스키마가 불확실한 데이터도 유연하게 처리하고, 이미 처리한 데이터는 건너뛰면서도 개발을 빠르게 하려면?

#3동작 예시

JSON 파일의 'customer' 필드 내부 구조가 고객마다 다를 때, 표준 DataFrame은 파싱 실패로 멈추지만, Glue의 DynamicFrame(동적 구조의 데이터를 다루는 전용 형식)을 쓰면 구조를 강제하지 않고 있는 필드만 추출해 처리할 수 있다. 또한 작업 북마크를 켜면, 어제 처리한 파일들은 자동으로 건너뛰고 새로 들어온 파일만 처리한다.

#4동작 과정

  1. DynamicFrame으로 데이터 로드유연한 스키마 해석이 필요하면 DynamicFrame을 써서 구조가 불완전하거나 변동해도 파싱이 진행되도록 한다. 정확한 타입 변환이 필요하면 나중에 Spark DataFrame으로 변환한다.
  2. Glue Studio 또는 코드 편집비주얼 드래그앤드롭 편집기(Glue Studio)로 필터, 조인, 변환 노드를 조립하거나, Python/Scala 코드를 직접 짠다.
  3. 작업 북마크 활성화이전 실행 때 처리한 파일/레코드를 내부적으로 기록했다가, 다음 실행 때 새로 들어온 것만 처리해서 증분 처리를 자동화한다.

Glue 연결과 커넥터

Glue 연결은 JDBC/ODBC 접속 정보와 VPC·서브넷·보안 그룹을 묶어 두는 객체로, 프라이빗 데이터 저장소에 안전하게 접근하게 해 준다.

#1문제 상황

기업 내부의 RDS 데이터베이스나 온프레미스 Oracle은 공개 인터넷에 노출되지 않는다. Glue 작업에서 이런 프라이빗 데이터 저장소에 접근하려면 호스트명, 포트, 사용자명, 비밀번호를 코드에 직접 박아 놓아야 했다. 비밀번호가 노출되는 보안 위험이 있고, 여러 작업에서 같은 정보를 반복 입력해야 한다.

#2핵심 질문

프라이빗 데이터베이스에 안전하게 연결하면서도 접속 정보를 중앙에서 관리하고 재사용하려면?

#3동작 예시

회사 RDS MySQL에 Glue 작업 10개가 모두 접근해야 한다면, Glue 연결 객체 하나를 만들어서 호스트, 포트, 사용자명, VPC 서브넷, 보안 그룹 정보를 한 곳에 저장한다. 그러면 각 작업은 '접속 정보를 직접 쓰지 말고 이 연결 객체를 쓰라'는 참조만 지정하면 된다.

#4동작 과정

  1. Glue 연결 객체 생성JDBC(관계형 DB 접근 규약) 또는 ODBC 타입을 선택해서 데이터베이스 호스트, 포트, 사용자명, 비밀번호를 입력한다. 비밀번호는 AWS Secrets Manager에 안전하게 보관된다.
  2. VPC 및 네트워크 설정프라이빗 RDS가 있는 VPC의 서브넷과 보안 그룹을 지정해서, Glue 작업이 그 네트워크 내부에서 접근할 수 있도록 한다.
  3. 작업에서 연결 참조Glue 작업 코드 내에서 데이터베이스 정보를 직접 쓰지 않고, 생성한 연결 객체의 이름을 참조해서 자동으로 모든 정보를 불러온다.

Glue Data Catalog와 크롤러

크롤러가 데이터 저장소를 훑어 분류자로 형식을 판별하고 테이블·파티션 메타데이터를 Data Catalog에 자동 등록·갱신한다.

#1문제 상황

데이터가 S3에 들어오면, 그 데이터의 구조(스키마)를 알아내기 위해 누군가는 파일을 직접 열어서 필드를 파악하고, 어느 테이블인지 분류하고, 어떤 파티션 구조로 저장되었는지 메모해야 했다. 새로운 데이터가 들어올 때마다 이 작업을 반복하므로 시간이 오래 걸리고 실수하기 쉬웠다.

#2핵심 질문

S3에 도착하는 데이터를 자동으로 구조 파악, 분류, 메타데이터 등록까지 다 처리하려면?

#3동작 예시

매일 밤 S3 폴더에 CSV, JSON, Parquet 파일이 섞여 들어온다. Glue 크롤러를 설정해서 그 폴더를 '매일 밤 2시에 훑어라'라고 하면, 크롤러가 자동으로 파일들을 샘플링해서 CSV 파일의 필드는 'name(문자), age(숫자)' 이런 식으로 판별하고, 파티션 구조를 감지해서 메타데이터를 Glue Data Catalog(데이터 저장소의 목록 DB)에 자동 등록한다.

#4동작 과정

  1. 크롤러 작업 정의탐색할 S3 경로와 실행 일정(예: 매일 밤 2시)을 지정하고, 데이터 형식 판별에 쓸 '분류자' 규칙들을 선택한다. 분류자는 파일 확장자, 헤더 패턴, 첫 몇 줄의 형식을 보고 CSV인지 JSON인지 판별한다.
  2. 데이터 탐색 및 분류크롤러가 지정된 S3 경로의 샘플 파일들을 읽고 분류자로 형식을 판별한 후, 각 파일의 필드명과 데이터 타입을 추출한다.
  3. 메타데이터 등록파악된 스키마와 파티션 구조를 테이블 정보로 변환해서 Glue Data Catalog에 자동 등록 또는 갱신한다. 다른 AWS 서비스(Athena, Redshift 등)가 이 메타데이터를 참조해서 데이터를 바로 쿼리할 수 있다.

스키마 진화와 스키마 변환

Glue Schema Registry는 스트리밍 스키마의 버전과 호환성 규칙을 관리하고, DMS Schema Conversion은 이기종 DB의 스키마·코드를 대상 엔진에 맞게 변환한다.

→ 06-04 참조

#1문제 상황

스트리밍 데이터를 처리할 때, 송신자 쪽이 데이터 구조를 바꿔서 보내면 수신 시스템이 갑자기 파싱 실패로 멈춘다. 기존 코드와 새로운 코드 간 호환성을 보장하기 어렵고, 무수히 많은 마이크로서비스가 같은 데이터를 받을 때 모두가 같은 버전을 동시에 업그레이드해야 한다. 이기종 DB 간 마이그레이션할 때 SQL 방언이 다르거나 데이터 타입이 맞지 않아서 수동 변환이 필요하다.

#2핵심 질문

데이터 구조 변화를 버전 관리하고, 호환성 규칙을 적용하며, 다른 DB 엔진 간의 스키마 차이를 자동 변환하려면?

#3동작 예시

Kafka 토픽에서 받는 고객 주문 메시지 스키마가 v1.0에서 v1.1로 변경되고 새 필드 'discount'가 추가되었다. Glue Schema Registry에 호환성 규칙을 '백워드 호환성(이전 버전 코드도 새 메시지를 읽을 수 있어야 함)'으로 설정하면, 모든 consumer가 동시에 업데이트되지 않아도 새로운 필드는 무시하고 기존 필드만 처리해서 계속 작동한다. 반대로 Oracle에서 AWS Redshift로 마이그레이션할 때는 DMS Schema Conversion이 Oracle의 'NVARCHAR2' 타입을 Redshift의 'VARCHAR' 타입으로 자동 변환해주고, PL/SQL 프로시저도 Redshift 호환 T-SQL로 변환한다.

#4동작 과정

  1. 스키마 레지스트리에 버전 등록송수신 데이터의 스키마를 JSON 스키마나 Avro 형식으로 정의해서 Glue Schema Registry에 등록하고, 호환성 규칙(백워드, 포워드, 전체 호환 등)을 설정한다.
  2. 스키마 진화 검증새로운 스키마가 들어오면 레지스트리가 자동으로 호환성 규칙을 검사해서, 위반하면 거부하거나 경고하고, 통과하면 새 버전으로 기록한다.
  3. 이기종 DB 스키마 변환DMS Schema Conversion 도구가 원본 DB(Oracle, MySQL, PostgreSQL 등)의 테이블 정의, 인덱스, 프로시저, 함수를 읽고 대상 DB(Redshift, Aurora 등) 엔진의 문법과 데이터 타입에 맞게 변환한 후 자동 생성 스크립트를 제공한다.

AWS Glue DataBrew: 레시피·프로파일링·데이터 정제

#1문제 상황

#2핵심 질문

화면에서 클릭으로 데이터 정제 단계를 시각적으로 구성하고, 정제 전에 데이터 품질을 자동으로 점검할 수 없을까요?

#3동작 예시

DataBrew에서 정제 규칙들을 "레시피"라는 순서 목록으로 화면에서 추가합니다. 예를 들어 "공백 제거" 규칙 → "형식 변환" 규칙 → "이상치 제거" 규칙을 순서대로 클릭으로 쌓고, 이 레시피의 나열이 저장됩니다. 프로파일 작업을 실행하면 정제 전 데이터의 통계(누락 비율, 이상치 분포 등)를 자동으로 계산해 시각화합니다.

#4동작 과정

  1. 레시피 정의화면의 규칙 팔레트에서 필요한 정제 단계들을 순서대로 클릭해 추가합니다. 각 규칙(예: "null 값 제거", "숫자 형식 변환", "문자열 길이 자르기")은 순서 있는 나열로 저장됩니다.
  2. 프로파일 작업 실행DataBrew가 원본 데이터 샘플을 스캔해 통계를 자동 계산하고 시각화 대시보드에 표시합니다(누락된 값 비율, 이상치, 분포).
  3. 레시피 적용 및 정제S3에 있는 원본 데이터에 레시피를 적용해 정제된 데이터를 생성하고, 정제 후 데이터 프로파일도 같이 생성해 품질 변화를 확인합니다.

EMR 클러스터: 노드 유형·인스턴스 플릿·스팟·EMRFS

EMR 클러스터는 프라이머리·코어·태스크 노드로 구성되며, 인스턴스 플릿과 스팟으로 비용을 낮추고 EMRFS로 S3를 파일 시스템처럼 쓴다.

#1문제 상황

단일 EC2 인스턴스에서는 대용량 데이터 처리가 느리고, 여러 EC2를 분산 처리 클러스터로 구성하려면 보안 그룹·네트워크·SSH 키 설정 등을 손으로 관리해야 했습니다.

#2핵심 질문

여러 EC2를 하나의 분산 처리 클러스터로 자동으로 구성하고, 스팟 인스턴스로 비용을 낮출 수는 없을까요?

#3동작 예시

EMR은 클러스터를 세 종류 노드로 자동 구성합니다. 프라이머리 노드 1개(조정자 역할, 전체 작업 스케줄링)와 코어 노드 여러 개(데이터 저장소 역할)와 태스크 노드 여러 개(처리 전담)를 지정한 개수만큼 자동으로 띄웁니다. 인스턴스 플릿으로 온디맨드(정가)와 스팟(할인가) 인스턴스를 섞고, EMRFS(EMR File System)로 S3를 클러스터 내 파일 시스템처럼 접근합니다.

#4동작 과정

  1. 클러스터 구성 및 자동 생성프라이머리·코어·태스크 노드 개수와 인스턴스 타입(예: m5.xlarge)을 지정하면 AWS가 EC2들을 자동으로 띄우고 보안 그룹·네트워크를 자동 설정합니다.
  2. 인스턴스 전략 설정인스턴스 플릿으로 여러 인스턴스 타입을 지정하고 온디맨드와 스팟의 비율을 설정하면, AWS가 비용을 낮추기 위해 스팟 여유 용량을 우선으로 사용합니다.
  3. 스토리지 연동EMRFS(Elastic MapReduce File System)로 S3를 로컬 디스크처럼 읽고 쓸 수 있으므로, 비용이 저렴한 S3를 클러스터의 분산 스토리지로 사용합니다.

#5한 줄 요약

EMR 클러스터프라이머리·코어·태스크 노드를 자동으로 조합하고, 스팟 인스턴스와 인스턴스 플릿으로 비용을 낮우며, EMRFS로 S3를 분산 스토리지로 연동하는 관리형 분산 처리 클러스터

EMR 애플리케이션: Spark·Hive·Presto와 성능·비용·데이터 스큐

EMR에 Spark·Hive·Presto 등 오픈소스 엔진을 설치해 대규모 처리를 하고, 파티션 편중(데이터 스큐)과 리소스 설정을 조정해 성능과 비용을 맞춘다.

#1문제 상황

EMR 클러스터가 있어도 그 위에 어떤 처리 엔진을 설치할지 선택해야 합니다. Spark는 인메모리 처리로 빠르고, Hive는 SQL 호환성이 높으며, Presto는 여러 데이터 소스를 한 번에 쿼리할 수 있습니다. 또한 데이터가 특정 키에 몰려 있으면(데이터 스큐) 일부 노드만 과부하가 걸려 전체 처리가 느려집니다.

#2핵심 질문

EMR에 어떤 엔진을 선택하고, 데이터 편중과 리소스를 어떻게 조정해 성능과 비용의 균형을 맞출까요?

#3동작 예시

EMR 클러스터 생성 시 Spark·Hive·Presto 등을 선택하면 각 엔진이 자동으로 설치되고, 클러스터의 모든 노드에서 병렬로 실행됩니다. 데이터가 특정 파티션에 몰려 있으면, 파티션을 다시 설계하거나 리소스 할당을 조정(예: 일부 노드에 더 많은 메모리 할당)해서 부하를 분산합니다.

#4동작 과정

  1. 엔진 선택 및 설치클러스터 생성 시 "Spark", "Hive", "Presto" 체크박스를 선택하면, AWS가 모든 노드에 해당 엔진의 바이너리를 설치하고 데몬을 실행합니다.
  2. 데이터 스큐 확인 및 조정각 파티션의 데이터 크기를 비교해서 특정 파티션이 다른 파티션보다 훨씬 크면, 파티션 키를 재설계하거나 리소스 할당을 불균형하게 조정합니다.
  3. 성능·비용 튜닝캐시 전략(자주 쓰는 데이터를 메모리에 고정), 병렬 처리 도(Spark의 partition 개수), 불필요한 노드 제거 등으로 전체 성능과 비용을 최적화합니다.

#5한 줄 요약

EMR 애플리케이션Spark·Hive·Presto 등의 오픈소스 엔진을 클러스터에 설치하고, 데이터 스큐를 감지해 파티션과 리소스 설정을 조정하는 방식으로 성능과 비용을 최적화하는 것

EMR Serverless·EMR on EKS와 컨테이너 기반 처리

클러스터를 직접 관리하지 않는 EMR Serverless와 쿠버네티스(EKS) 위에서 Spark를 돌리는 EMR on EKS는 EMR의 서버리스·컨테이너형 배포 옵션이다.

#1문제 상황

EMR 클러스터는 사용자가 계획한 크기대로 비용이 발생하고, 노드를 추가하거나 줄일 때마다 클러스터를 재시작해야 합니다. 또한 스케일링과 노드 관리를 사용자가 직접 해야 했습니다.

#2핵심 질문

클러스터를 직접 관리하지 않으면서도 Spark 같은 분산 처리를 대규모로 실행할 수 없을까요?

#3동작 예시

EMR Serverless는 클러스터 개념이 없고 작업만 제출하면 AWS가 자동으로 필요한 리소스를 할당해 처리한 후 완료되면 즉시 해제합니다. EMR on EKS는 쿠버네티스 클러스터(EKS)를 먼저 띄운 후, 그 위에 Spark를 컨테이너로 실행하는 방식으로, 쿠버네티스의 포드 관리 기능을 활용합니다.

#4동작 과정

  1. EMR Serverless 방식애플리케이션(Spark 작업) 등록 → 작업 파라미터(코어 수, 메모리) 지정 후 제출 → AWS가 자동으로 필요한 리소스 할당 후 처리 → 작업 완료 후 리소스 자동 해제.
  2. EMR on EKS 방식쿠버네티스 클러스터(EKS)를 먼저 생성 → EMR 가상 클러스터(Virtual Cluster) 정의 → Spark 컨테이너 이미지 준비 → Kubernetes Job으로 Spark 작업 제출 → 쿠버네티스가 포드 스케줄링 및 관리.

#5한 줄 요약

EMR Serverless와 EMR on EKS각각 서버리스 환경과 컨테이너 환경에서 분산 처리를 제공하며, 클러스터 노드 관리 오버헤드를 제거하는 것

Lambda·AWS Batch 기반 처리: 동시성·메모리·스토리지 마운트

짧은 이벤트 처리는 동시성·메모리·임시 스토리지를 설정한 Lambda로, 오래 걸리는 배치 작업은 컴퓨팅 환경과 작업 대기열을 쓰는 AWS Batch로 처리한다.

#1문제 상황

이벤트(예: S3 파일 업로드)가 발생했을 때 짧은 처리를 하려면 EC2를 항상 띄워두거나, 필요할 때마다 띄워야 하므로 비효율적입니다. 반대로 오래 걸리는 배치 작업 여러 개를 동시에 실행하려면 큐 관리와 우선순위 처리를 수동으로 해야 합니다.

#2핵심 질문

이벤트 기반 짧은 처리와 오래 걸리는 배치 작업을 각각 효율적으로 실행하는 방법은 무엇일까요?

#3동작 예시

Lambda는 S3 파일 업로드 같은 이벤트마다 함수를 즉시 실행합니다(동시성·메모리는 설정으로 제어). AWS Batch는 작업 정의(어떤 컨테이너를 실행할지), 컴퓨팅 환경(어느 EC2에서), 작업 대기열(우선순위)을 미리 설정해두고, 대량의 배치 작업을 자동으로 스케줄링합니다.

#4동작 과정

  1. Lambda 처리동시성(몇 개 함수가 동시에 실행될 수 있는지)과 메모리(128MB ~ 10GB)를 설정 → 이벤트 발생 → Lambda가 함수를 즉시 실행 → /tmp에 최대 512MB 임시 데이터 저장 가능 → 로그는 CloudWatch에 저장.
  2. AWS Batch 처리작업 정의(Docker 이미지·리소스 요청) + 컴퓨팅 환경(EC2 인스턴스 풀·스팟/온디맨드 비율) + 작업 대기열(우선순위·FIFO 순서) 설정 → 작업 제출 → Batch가 대기열 순서대로 스케줄링 후 EC2에 배치 → 완료 후 결과 저장.
  3. 스토리지 관리Lambda는 /tmp로 제한되므로 S3·EBS는 외부 서비스 호출. AWS Batch는 EBS를 컴퓨팅 환경의 EC2에 마운트해 대용량 임시 데이터 저장 가능.

#5한 줄 요약

Lambda와 AWS Batch각각 동시성·메모리로 이벤트 기반 단기 처리를 제공하고, 작업 정의·컴퓨팅 환경·대기열로 배치 작업을 대규모 자동 관리하는 것

Amazon Athena: 엔진·테이블·워크그룹·결과 위치

서버를 띄우지 않고 S3에 있는 데이터를 SQL로 바로 조회하는 서비스로, 데이터 카탈로그의 테이블 정의를 읽고 워크그룹 단위로 쿼리 실행과 결과 저장 위치·비용 한도를 관리한다.

#1문제 상황

S3에 있는 데이터를 분석하려면 EMR 클러스터를 띄워야 했고, 클러스터 비용이 계속 발생했습니다. 간단한 SQL 쿼리 하나를 위해 여러 노드를 띄우는 것은 낭비였습니다.

#2핵심 질문

서버를 띄우지 않고 S3에 있는 데이터를 SQL로 바로 조회할 수 없을까요?

#3동작 예시

Athena는 서버가 없고, 사용자가 SQL을 입력하면 데이터 카탈로그에서 테이블 메타데이터(열 이름·형식)를 읽어 S3의 해당 데이터를 스캔하고 결과를 반환합니다. 비용은 스캔한 데이터량(5센트/TB)만 부과됩니다.

#4동작 과정

  1. 데이터 카탈로그 설정AWS Glue 크롤러로 S3 폴더를 자동 스캔하거나 수동으로 테이블을 정의합니다(열 이름·형식·파티션 정보).
  2. 워크그룹 및 결과 위치 설정쿼리 결과를 저장할 S3 위치, 쿼리 실행 비용 한도, 결과 포맷(CSV·Parquet 등)을 워크그룹 단위로 지정합니다.
  3. 쿼리 실행 및 결과 반환SQL을 Athena 콘솔에 입력 → Athena가 카탈로그의 테이블 정의를 읽어 S3를 스캔 → 결과를 워크그룹의 결과 위치 S3에 저장 후 콘솔에 표시.

#5한 줄 요약

Athena 최적화: 파티션 프로젝션·CTAS·성능과 비용

스캔하는 데이터 양을 줄이는 것이 곧 속도이자 비용 절감이며, 파티션 설계와 CTAS로 컬럼형·압축 포맷 테이블을 만들어 쿼리를 최적화한다.

Athena는 단순하지만 스캔하는 데이터가 많으면 쿼리가 느리고 비용이 높아집니다(비용은 스캔 데이터량 기준). 파티션이 없으면 필요 없는 데이터까지 모두 읽어야 합니다.

#2핵심 질문

Athena에서 스캔하는 데이터를 줄이고 쿼리 속도를 높이면서 비용도 절감하는 방법은 무엇일까요?

#3동작 예시

S3를 year=2024/month=01/day=15/ 형태로 파티션하고 테이블을 정의하면, "where year=2024 and month=01"로 필터링할 때 해당 폴더만 스캔하고 다른 폴더는 스킵합니다. 원본 CSV를 Parquet(컬럼형) 형식으로 변환하고 Snappy 압축을 적용하면 필요한 열만 읽고 파일 크기도 줄어들어 성능과 비용이 모두 개선됩니다.

#4동작 과정

  1. 파티션 설계S3 폴더 구조를 year/month/day 형태로 미리 정의하거나, 파티션 프로젝션(Partition Projection)을 설정해 AWS가 자동으로 파티션 경로를 생성합니다. 쿼리 필터에 파티션 조건(예: where year=2024)이 있으면 해당 폴더만 스캔합니다.
  2. CTAS로 포맷 변환"Create Table As Select" SQL로 원본 테이블(CSV 등)을 Parquet 포맷 + Snappy 압축 새 테이블로 변환합니다. 이 과정에서 Athena가 변환 쿼리 실행 비용을 부과합니다.
  3. 쿼리 재실행 및 성능·비용 확인최적화된 테이블을 대상으로 같은 쿼리를 다시 실행하면 스캔 데이터량이 대폭 줄어들어 속도와 비용이 모두 개선됩니다.

Athena 최적화파티션 설계와 CTAS로 컬럼형·압축 포맷 테이블을 만들어 스캔 데이터를 최소화하고, 그 결과 쿼리 속도와 비용을 동시에 개선하는 것

#3동작 예시

  2. 페더레이티드 쿼리 실행S3 데이터와 외부 데이터를 JOIN하거나 WHERE 절로 필터링하는 등 통합 SQL을 한 번에 실행할 수 있다.

#2핵심 질문

#4동작 과정

Apache Airflow는 오픈소스이고, 설치·운영·확장을 사용자가 직접 관리해야 한다. 메타데이터 데이터베이스와 워커 서버를 항상 켜둬야 해서 비용이 발생한다. 문제가 생기면 인프라 레벨에서부터 디버깅해야 하고, 대규모 DAG 실행 시 워커 확장도 수동으로 설정해야 한다.

#2핵심 질문

Airflow의 DAG 정의·스케줄·모니터링 기능은 그대로 사용하면서 서버 운영과 확장을 AWS가 대신해 줄 수 있을까?

#3동작 예시

S3에 DAG 파이썬 파일을 올려두면, MWAA가 자동으로 메타데이터 데이터베이스와 워커 서버를 관리한다. Python 파일에서 "매일 오전 9시에 데이터 수집 → 검증 → 로딩"을 DAG 객체로 정의하면, MWAA가 스케줄대로 자동 실행하고 필요하면 워커를 확장한다.

#4동작 과정

  1. 관리형 환경 구성AWS 콘솔에서 MWAA 환경을 생성하고, S3 버킷(Airflow 메타데이터와 DAG 저장소)을 지정하면, AWS가 데이터베이스와 워커 인프라를 자동 구축한다.
  2. DAG 작성 및 배포Python으로 작업 흐름을 DAG 객체로 정의해서 S3에 업로드하면, MWAA가 자동으로 감지해서 로드하고 스케줄대로 실행한다.
  3. 모니터링과 문제 해결MWAA 웹 UI와 CloudWatch에서 DAG 실행 상태·로그·오류를 추적하고, 특정 작업만 재실행하거나 DAG 파이썬 파일을 수정해서 빠르게 대응한다.

#5한 줄 요약

MWAA는 Apache Airflow의 DAG 정의와 스케줄 기능을 그대로 제공하면서 AWS가 서버·데이터베이스·확장을 완전 관리하는 서비스다.

#2핵심 질문

Glue 워크플로·트리거와 Lambda 기반 서버리스 오케스트레이션

Glue 크롤러와 잡을 트리거로 엮어 하나의 ETL 흐름으로 돌리고, 짧은 접착 로직은 Lambda 함수로 처리하는 방식이다.

→ 08-01 참조

#1문제 상황

예전에는 Glue 크롤러와 Glue 잡을 따로 따로 수동으로 시작했거나, 정해진 시간에 스케줄만 걸어뒀다. 이 방식은 한 잡이 끝나야 다음 잡을 시작할 수 있는 조건(예: 데이터가 특정 테이블에 로드되었을 때)을 처리하지 못한다. 또한 잡들 사이에 데이터를 정리하거나 검증하는 짧은 로직을 넣으려면 복잡했다.

#2핵심 질문

여러 Glue 크롤러와 잡을 조건부로 연결해서 하나의 완전한 파이프라인으로 만들되, 중간에 간단한 로직이 필요하면 어떻게 끼워 넣을 것인가?

#3동작 예시

Glue 워크플로(Workflow)는 Glue 작업을 노드(node)로 그리고 트리거(trigger)를 간선(edge)으로 연결한 그래프 구조다. 크롤러 A가 끝나면 자동으로 잡 B를 시작하고, 잡 B가 성공하면 Lambda 함수 C를 호출한다. Lambda에서 검증 로직을 실행한 후, 그 결과에 따라 잡 D를 시작하거나 중단한다.

#4동작 과정

  1. 워크플로 정의크롤러, 잡, Lambda를 노드로 등록하고, 실행 조건(트리거)을 설정한다. 예를 들어 "크롤러 A 성공 → 잡 B 시작" 같은 규칙을 정의한다.
  2. 첫 번째 작업 실행파이프라인이 시작되면(수동 또는 스케줄) 크롤러 A가 먼저 실행되고, S3에서 스키마를 읽어 Glue 카탈로그(메타데이터 저장소)에 테이블 정의를 기록한다.
  3. 연쇄 실행과 Lambda 통합크롤러 A 완료 이벤트가 발생하면 워크플로 엔진이 트리거 조건을 확인하고, 잡 B를 자동으로 실행한다. 잡 B가 끝나면 Lambda 함수 C가 호출되어 결과 데이터를 검증하거나 다음 단계를 결정하고, 그 반환값에 따라 다음 잡을 실행하거나 건너뛴다.

#5한 줄 요약

여러 ETL 작업(크롤링, 변환, 적재)을 조건부로 연결해서 하나의 자동화된 파이프라인으로 만들고, Lambda로 중간 로직을 쉽게 통합하는 오케스트레이션 도구

SNS·SQS 알림과 파이프라인 복원력: 재시도·멱등성·DLQ

SNS로 알리고 SQS 큐로 완충하며, 재시도·멱등 처리·데드레터 큐로 실패해도 데이터가 사라지지 않게 만드는 설계다.

#1문제 상황

과거에는 한 서비스가 다른 서비스에 직접 API를 호출했다. 네트워크가 불안정하거나 상대 서비스가 일시적으로 먹통이면 요청이 사라졌다. 재시도를 하려면 각 서비스에서 직접 코드를 짜야 했고, 실패 원인을 추적하기 어려웠다.

#2핵심 질문

데이터 손실 없이 느슨하게 연결된 서비스들 사이에 메시지를 안정적으로 전달하되, 실패하면 자동으로 재시도하고 최종 실패는 별도로 기록하려면 어떻게 할 것인가?

#3동작 예시

Glue 잡이 끝나면 SNS 토픽(주제)에 "데이터 로드 완료" 메시지를 보낸다. SQS 큐가 이 토픽을 구독(subscribe)하고 있어서 메시지를 받으면 큐에 쌓인다. 다운스트림 Lambda가 SQS에서 메시지를 하나씩 꺼내 처리한다. 처리 중 실패하면 SQS는 자동으로 재시도하고, 일정 횟수 이상 실패하면 DLQ(데드레터 큐)에 옮긴다.

#4동작 과정

  1. 메시지 발행 (SNS)Glue 잡이 성공하면 AWS Lambda 또는 SNS API를 호출해 메시지를 SNS 토픽에 발행한다. SNS는 즉시 구독자들에게 전달을 시도한다.
  2. 메시지 큐잉과 재시도 (SQS)SQS 큐가 SNS 토픽을 구독하고 있으므로 메시지를 받아 보관한다. 소비자 애플리케이션이 메시지를 꺼내 처리하는데, 처리 중 예외가 발생하면 메시지를 반환하고, SQS는 설정된 기간 후 자동으로 재시도한다. 이를 여러 번 반복한다(가시성 타임아웃·재시도 메커니즘).
  3. 최종 실패와 DLQ재시도 횟수(MaxReceiveCount)를 초과하면 SQS는 메시지를 DLQ라는 별도의 큐로 이동시킨다. 운영 팀이 DLQ의 메시지를 모니터링해서 원인을 파악하고 수동으로 재처리하거나 문제를 해결한다.

#5한 줄 요약

메시지 손실 없이 느슨한 결합(loose coupling)으로 서비스를 연결하고, 자동 재시도와 데드레터 큐로 실패를 추적해 시스템 복원력을 높이는 패턴

프로그래밍·SDK와 데이터 엔지니어링 코드 품질

Boto3 같은 AWS SDK로 서비스를 코드에서 호출하고, 재사용·테스트 가능한 형태로 파이프라인 코드를 관리하는 일이다.

#1문제 상황

처음에는 콘솔에서 Glue 잡을 하나하나 만들고 PySpark 스크립트를 붙여넣곤 했다. 로직이 복잡해지면 코드 복제가 많아지고, 같은 버그가 여러 곳에서 반복됐다. 테스트도 어려웠고, 어느 버전의 코드가 실제로 실행 중인지 추적 불가능했다.

#2핵심 질문

재사용 가능하고 테스트 가능한 형태로 ETL 파이프라인을 Python 코드로 작성하되, AWS 서비스를 제어하려면 어떻게 해야 할 것인가?

#3동작 예시

Boto3(AWS SDK for Python)는 Python에서 AWS API를 직접 호출하는 라이브러리다. 예를 들어 glue_client = boto3.client('glue') 로 클라이언트를 만들고, glue_client.start_job_run(JobName='my_job') 로 Glue 잡을 시작한다. 이를 재사용 가능한 함수로 래핑하고 단위 테스트를 붙이면, 파이프라인 로직이 독립적으로 검증 가능해진다.

#4동작 과정

  1. 코드 모듈화데이터 읽기, 변환, 적재 같은 각 단계를 별도의 함수나 클래스로 분리한다. 각 함수는 입력값을 받아 출력값을 반환하는 순수 함수 형태로 작성하면 테스트가 쉽다.
  2. AWS SDK 통합Boto3로 S3, Glue, RDS 같은 서비스를 호출하는 코드를 함수 안에 넣는다. 예를 들어 S3에서 데이터를 읽거나, Glue 크롤러를 시작하거나, RDS에 데이터를 적재할 때 Boto3 클라이언트를 사용한다.
  3. 버전 관리와 배포코드를 Git으로 관리하고, 코드 변경이 있으면 자동으로 테스트를 실행한 후 AWS Glue Job이나 Lambda에 배포한다. 이렇게 하면 어느 버전의 코드가 언제 실행됐는지 명확하다.

#5한 줄 요약

Boto3 SDK를 통해 AWS 서비스를 프로그래밍적으로 제어하고, 모듈화·테스트 가능한 구조로 파이프라인 코드를 관리해 신뢰도와 유지보수성을 높이는 개발 방식

#3동작 예시

#4동작 과정

CloudWatch Logs와 Logs Insights: 수집·보존·쿼리

서비스와 잡이 남긴 로그를 로그 그룹에 모아 보존 기간을 정하고, Logs Insights 쿼리로 원인을 찾아내는 로그 분석 도구다.

#1문제 상황

과거에는 Glue 잡의 로그를 찾으려고 콘솔을 여러 번 클릭해야 했다. 실패한 이유를 알려면 로그의 큰 텍스트 덩어리를 눈으로 읽어야 했고, 여러 실행의 로그를 비교하기는 거의 불가능했다. 로그를 무한정 보관하면 비용도 올라갔다.

#2핵심 질문

방대한 로그를 중앙에서 수집·보관하되, SQL 같은 쿼리로 빠르게 원인을 찾고 비용을 제어하려면 어떻게 할 것인가?

#3동작 예시

Glue 잡이 실행되면 표준 출력/에러를 CloudWatch Logs의 로그 그룹에 자동 저장한다. Logs Insights에서 fields @timestamp, @message | filter @message like /ERROR/ | stats count() by @message 같은 쿼리를 실행하면, 특정 오류가 몇 번 나왔는지 즉시 집계한다. 동시에 "30일 후 자동 삭제" 같은 보존 정책을 설정해서 오래된 로그를 자동으로 정리할 수 있다.

#4동작 과정

  1. 로그 수집 및 저장Glue 잡, Lambda, 애플리케이션이 출력한 로그 메시지를 CloudWatch Logs에 자동 전송한다. 각 로그는 타임스탬프, 메시지, 메타데이터(예: 함수명, 에러 코드)와 함께 저장된다.
  2. 보존 정책 설정로그 그룹마다 보존 기간(예: 7일, 30일, 무제한)을 설정한다. 기간이 지난 로그는 자동으로 삭제되어 비용을 절감한다. 규정상 장기 보관이 필요하면 S3로 아카이빙할 수도 있다.
  3. Logs Insights로 분석로그 그룹에서 SQL 같은 문법으로 쿼리를 실행해서 특정 오류, 성능 이상, 패턴을 찾아낸다. 결과를 그래프나 통계로 시각화할 수 있다.

CloudTrail과 CloudTrail Lake: API 호출 추적과 감사

계정에서 누가 언제 어떤 API 를 호출했는지 기록하고, CloudTrail Lake 에서 SQL 로 그 감사 기록을 조회한다.

#1문제 상황

예전에는 누가 AWS 콘솔에서 뭘 했는지, 또는 프로그램이 어떤 API를 호출했는지 알 방법이 없었다. 데이터가 갑자기 삭제되거나 설정이 바뀌어도 원인을 추적할 수 없었고, 보안 감사나 규정 준수 증명이 불가능했다.

#2핵심 질문

#3동작 예시

CloudTrail은 계정의 모든 API 호출을 로그 파일로 기록한다. 예를 들어 IAM 사용자 "data-engineer"가 오후 3:45에 s3:DeleteBucket API를 호출했고 성공했다면, 그 모든 정보를 JSON 로그에 기록한다. CloudTrail Lake는 이 로그들을 쿼리 가능한 데이터 레이크에 저장해서 SELECT eventName, userIdentity.principalId, eventTime FROM cloudtrail_events WHERE eventSource = 's3' 같은 SQL 쿼리로 즉시 조회 가능하게 한다.

#4동작 과정

  1. API 호출 기록누구든(콘솔 사용자, 애플리케이션, AWS 서비스)이 AWS API를 호출하면 CloudTrail이 호출 정보(누가, API 이름, 파라미터, 결과, 타임스탬프, 소스 IP 등)를 JSON으로 기록한다. 기본값으로는 S3 버킷에 저장된다.
  2. CloudTrail Lake로 통합CloudTrail 로그를 CloudTrail Lake 데이터 레이크로 수집하면, 로그가 파싱되어 구조화된 데이터베이스 테이블 형태로 저장된다. 이렇게 하면 로그 파일을 일일이 분석할 필요가 없다.
  3. SQL 쿼리로 감사CloudTrail Lake에서 SQL을 실행해서 "어떤 IAM 역할이 RDS 인스턴스를 삭제했는가", "특정 S3 버킷에 접근한 모든 사용자와 시간", "실패한 로그인 시도" 같은 질문을 즉시 답할 수 있다.

DQDL 규칙으로 결측·중복·범위 위반 같은 데이터 이상을 자동 검사하고 점수로 판정해 나쁜 데이터의 하류 유입을 막는다.

#1문제 상황

데이터를 처리한 후 문제를 발견하면 이미 나쁜 데이터가 하류 시스템으로 흘러간 뒤입니다. 결측값, 중복 레코드, 범위를 벗어난 값 같은 이상은 데이터 분석 결과를 왜곡하거나 다운스트림 애플리케이션을 깨뜨립니다.

#2핵심 질문

나쁜 데이터가 파이프라인의 더 아래로 흘러가기 전에 어떻게 막을 수 있을까?

#3동작 예시

DQDL(Data Quality Definition Language)로 "order_id는 중복이 없어야 한다", "price는 0 이상 999999 이하여야 한다", "created_at은 결측이 없어야 한다" 같은 규칙을 미리 코드로 작성하면, Glue 잡이 실행될 때마다 데이터를 자동으로 검사해서 각 규칙을 만족하는 행의 개수와 비율을 계산하고, 전체 데이터 중 몇 %가 품질 기준을 맞추는지 점수로 냅니다.

#4동작 과정
