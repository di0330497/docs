라우팅 프로토콜(I) — OSPFv2/v3·MP-BGP

데이터센터 언더레이에서 OSPFv2/v3로 링크·경로를 학습하고 MP-BGP로 VXLAN EVPN의 주소 패밀리(IPv4/IPv6, EVPN) 경로를 교환하는 라우팅 체계다.

#1문제 상황

기존 데이터센터는 경로를 정적 라우팅이나 장비별 개별 설정으로 관리했고, L2 중심으로 네트워크를 넓히려면 스위치를 계속 연결해야 했다. 링크가 늘고 IPv6와 가상 네트워크가 섞이면 사람이 경로를 손으로 맞춰야 하는 부분이 커지고, 링크 하나가 끊겼을 때 우회 경로를 다시 계산해 반영하기까지 트래픽이 멈춘다.

#2핵심 질문

데이터센터 언더레이의 링크 장애와 새 경로를 사람 손 없이 학습하고, IPv4·IPv6는 물론 가상 네트워크 경로까지 한 체계로 교환하려면 어떻게 해야 하는가?

#3동작 예시

두 스파인 스위치와 리프 스위치를 연결한 패브릭에서, 각 스위치는 OSPFv2로 링크의 IPv4 주소와 토폴로지를 학습해 최단 경로를 채운다. 같은 스파인·리프 사이에서는 MP-BGP 세션을 맺어 주소 패밀리별로 경로를 교환하고, EVPN 경로를 통해 VTEP(터널 끝점) 주소와 가상 네트워크 정보를 주고받아 오버레이가 어디로 트래픽을 보낼지 알게 된다.

#4동작 과정

  1. 이웃 수립(OSPF)각 스위치가 Hello 패킷으로 이웃을 찾고 링크 상태 정보를 교환해 토폴로지를 맞춘다. 그래서 물리 링크와 경로가 자동으로 학습된다.
  2. 경로 계산·전파동일 비용 최단 경로를 계산하고 링크 상태 광고(LSA, 링크 상태를 알리는 메시지)로 변경을 이웃에 전파한다. 그래서 링크 장애 시 우회 경로가 즉시 반영된다.
  3. EVPN 경로 교환(MP-BGP)스파인·리프 사이에 MP-BGP 세션을 맺어 IPv4/IPv6와 EVPN 등 주소 패밀리별 경로를 교환한다. 그래서 오버레이가 원격 MAC·VTEP 정보를 제어 평면에서 알게 된다.

#5한 줄 요약

언더레이의 물리 경로 학습(OSPFv2/v3)과 오버레이의 가상 경로 교환(MP-BGP)을 분리해 연결함으로써, 데이터센터가 경로를 스스로 학습하고 장애를 우회하게 만드는 것

라우팅 프로토콜(II) — PIM·FHRP

PIM으로 멀티캐스트 트래픽을 분배하고 FHRP(HSRP/VRRP)로 게이트웨이 이중화를 제공하는 데이터센터 라우팅 기능이다.

#1문제 상황

한 송신자에서 여러 수신자로 같은 데이터를 보낼 때 유니캐스트로 하나씩 복사하면 수신자 수만큼 대역폭이 곱절로 늘고 서버에도 부하가 걸린다. 또한 호스트의 기본 게이트웨이가 한 대뿐이면 그 장비가 죽는 순간 해당 호스트 전체가 통신을 멈추고, 모든 호스트의 게이트웨이 주소를 사람이 바꿔야 한다.

#2핵심 질문

같은 데이터를 여러 수신자에게 효율적으로 전달하면서, 게이트웨이가 죽어도 호스트가 주소를 바꾸지 않고 통신을 유지하려면 어떻게 해야 하는가?

#3동작 예시

여러 서버가 같은 시장 데이터나 영상 스트림을 동시에 구독할 때, PIM-SM으로 수신자가 있는 경로에만 트래픽이 복제되도록 트리를 만든다. 동시에 두 라우터가 HSRP 또는 VRRP로 하나의 가상 IP를 공유해, 활성 라우터가 죽어도 호스트는 같은 게이트웨이 주소로 계속 트래픽을 보낸다.

#4동작 과정

  1. 멀티캐스트 트리 구성(PIM)수신자가 IGMP로 그룹에 가입하면 PIM이 역방향 경로 검사(RPF, 송신자 방향이 맞는지 확인)를 거쳐 소스·공유 트리에 브랜치를 만든다. 그래서 필요한 경로에만 패킷이 복제된다.
  2. 게이트웨이 가상화(FHRP)활성 라우터가 가상 IP·MAC으로 호스트의 기본 게이트웨이 역할을 하고, 대기 라우터가 주기 메시지로 활성 상태를 감시한다. 그래서 호스트는 실제 어느 라우터가 살아 있는지 몰라도 된다.
  3. 장애 전환활성 라우터가 응답하지 않으면 대기 라우터가 가상 IP·MAC를 승계해 포워딩을 이어간다. 그래서 게이트웨이가 바뀌어도 호스트 설정은 그대로다.

#5한 줄 요약

멀티캐스트 전달을 수신자 경로에만 한정(PIM)하고 게이트웨이를 가상 주소로 공유(FHRP)해, 대량 전달의 대역폭 낭비와 단일 장애점을 함께 없애는 것

스위칭 프로토콜 — RSTP+·LACP·vPC

루프 방지를 위한 RSTP+, 링크 묶음을 위한 LACP, 두 Nexus 스위치를 하나처럼 쓰는 vPC를 적용하는 스위칭 기술이다.

#1문제 상황

이중화를 위해 스위치를 두 대 연결하면 L2 루프가 생겨 브로드캐스트가 무한히 돌 수 있어, 스패닝 트리 프로토콜이 한쪽 링크를 막아 둔다. 그래서 남는 대역폭을 쓰지 못하고 수렴도 느리며, 링크를 여러 개 묶어도 스패닝 트리가 다시 하나만 남긴다. 두 스위치를 독립 장비로 관리하면 설정과 장애 대응이 이중으로 든다.

#2핵심 질문

루프를 막으면서도 남는 링크의 대역폭을 모두 쓰고, 두 스위치를 하나처럼 관리하려면 어떻게 해야 하는가?

#3동작 예시

두 스위치를 vPC 도메인으로 묶어 하나의 논리 스위치처럼 동작시키고, 서버와 각 스위치 사이의 물리 링크들은 LACP 포트채널로 묶어 하나의 논리 링크로 만든다. 나머지 이중 링크는 RSTP+가 대체 포트로 미리 계산해 두어, 장애가 나면 빠르게 활성화되어 백업 경로 역할을 한다.

#4동작 과정

  1. 루프 차단(RSTP+)스위치가 브리지 ID와 경로 비용으로 루트 브리지를 선출하고 대체 포트를 미리 계산해 둔다. 그래서 링크 장애 시 대체 포트가 빠르게 활성화된다.
  2. 링크 묶음(LACP)두 장비가 링크 집속 제어 프로토콜(LACP)로 협상해 여러 물리 포트를 하나의 포트채널로 묶는다. 그래서 대역폭이 합쳐지고 일부 링크가 죽어도 묶음이 유지된다.
  3. 장비 이중화(vPC)vPC 피어 링크로 두 스위치가 제어 정보를 맞춰, 하위 장비가 두 스위치에 동시에 연결해도 루프로 보지 않는다. 그래서 두 대가 하나의 스위치처럼 동작한다.

#5한 줄 요약

루프 방지를 유지한 채 남는 링크를 LACP로 묶고 vPC로 두 스위치를 하나처럼 만들어, L2 이중화의 대역폭 낭비와 단일 장애점을 함께 줄이는 것

오버레이 — VXLAN EVPN

VXLAN으로 L2를 IP 네트워크 위에 터널링하고 EVPN(BGP)으로 MAC·VTEP 정보를 제어 평면에서 학습하는 오버레이 네트워크다.

#1문제 상황

일반 VLAN은 식별자 길이가 제한적이라 만들 수 있는 세그먼트 수가 적고, L2 도메인을 넓히려면 스위치를 계속 연결하며 루프를 관리해야 한다. 가상 머신을 다른 랙으로 옮기려면 같은 L2에 있어야 하므로 물리 네트워크를 다시 설계해야 하고, 서버의 이동 범위가 물리 위치에 묶인다.

#2핵심 질문

물리 네트워크 구조를 바꾸지 않고 L2 세그먼트를 훨씬 많이 늘리며, 가상 머신을 어디로 옮겨도 같은 L2에 붙게 하려면 어떻게 해야 하는가?

#3동작 예시

리프 스위치의 VTEP(터널 끝점)가 서버의 L2 프레임을 VXLAN 헤더로 감싸 IP 언더레이를 통해 전송하고, 다른 리프의 VTEP가 이를 풀어 같은 세그먼트로 전달한다. MAC 주소와 VTEP 정보는 EVPN(BGP로 경로를 교환하는 제어 평면)으로 미리 학습해, 목적지가 어디 있는지 모를 때 생기는 불필요한 플러딩 없이 전달한다.

#4동작 과정

  1. 캡슐화(VXLAN)VTEP가 원본 L2 프레임 앞에 VXLAN 헤더와 UDP/IP 헤더를 붙여 터널로 보낸다. 그래서 L2 프레임이 IP 언더레이 위를 지난다.
  2. 제어 평면 학습(EVPN)VTEP가 자신이 가진 MAC·세그먼트(VNI) 정보를 MP-BGP EVPN 경로로 광고한다. 그래서 각 VTEP가 원격 MAC의 위치를 미리 안다.
  3. 전달수신 VTEP가 VNI로 세그먼트를 구분해 캡슐을 풀고 목적지 호스트로 프레임을 넘긴다. 그래서 같은 L2 세그먼트가 랙을 넘어 확장된다.

#5한 줄 요약

L2 프레임을 IP 위에 터널링(VXLAN)하고 MAC 위치를 BGP(EVPN)로 학습해, 물리 위치와 무관하게 확장되는 가상 L2 네트워크를 만드는 것

ACI 개념과 패브릭·액세스 정책

SDN 기반 ACI에서 패브릭을 초기 구성하고 스위치·인터페이스·VLAN 풀을 액세스 정책으로 추상화해 연결을 정의하는 개념이다.

#1문제 상황

전통 데이터센터는 스위치마다 VLAN·ACL·라우팅을 개별 명령줄로 설정해, 새 서비스 하나를 붙일 때 여러 장비를 사람이 손으로 맞춰야 한다. 설정이 장비마다 흩어져 있어 전체 연결 규칙을 한눈에 보기 어렵고, 한 곳의 변경 실수가 곧바로 장애로 이어진다.

#2핵심 질문

개별 장비 설정 대신 연결 의도를 한 곳에서 정의하고 패브릭 전체에 자동으로 반영하려면 어떻게 해야 하는가?

#3동작 예시

관리자가 APIC(중앙 컨트롤러)에서 스위치 프로파일과 인터페이스, VLAN 풀을 액세스 정책으로 한 번 정의하고, 그 정책을 리프 스위치의 특정 인터페이스에 매핑한다. 그러면 패브릭이 해당 포트에 필요한 VLAN 설정을 스스로 내려보내, 관리자는 장비별 명령줄 대신 정책만 관리하게 된다.

#4동작 과정

  1. 패브릭 구성스파인·리프 스위치를 APIC에 등록하고 패브릭을 초기화해 스위치 간 언더레이 연결을 세운다. 그래서 물리 토폴로지 위에 중앙 제어 계층이 올라간다.
  2. 액세스 정책 정의스위치 프로파일·인터페이스 프로파일·VLAN 풀을 정책 객체로 만들고 인터페이스에 매핑한다. 그래서 어떤 포트가 어떤 VLAN을 받을지 선언적으로 정해진다.
  3. 정책 배포APIC가 그 정책을 해당 리프 스위치에 내려보내고, 엔드포인트(서버·가상 머신)가 붙으면 포트 설정이 적용된다. 그래서 연결 의도가 패브릭 전체에 자동 반영된다.

#5한 줄 요약

물리 스위치 설정을 중앙 컨트롤러(APIC)의 정책 객체로 추상화해, 데이터센터 연결을 선언적으로 정의하고 자동 배포하는 것

ACI VMM 통합

ACI 패브릭을 VMware 등 가상화 환경(VMM)과 연동해 VM 네트워킹을 정책 기반으로 자동 구성하는 통합 기능이다.

#1문제 상황

가상화 환경에서는 가상 머신을 만들 때마다 가상 스위치의 포트그룹과 물리 스위치의 VLAN 설정을 사람이 양쪽에서 각각 맞춰야 한다. 가상 머신이 늘거나 다른 호스트로 옮겨지면 두 설정이 어긋나 통신이 끊기고, 어느 설정이 실제로 적용됐는지 추적하기도 어렵다.

#2핵심 질문

가상 머신의 생성과 이동에 맞춰 물리 네트워크 정책을 사람 손 없이 가상화 환경과 동기화하려면 어떻게 해야 하는가?

#3동작 예시

APIC이 vCenter 같은 가상화 관리 서버와 연동해, 관리자가 정의한 엔드포인트 그룹(EPG)에 가상 머신을 넣으면 그 머신이 속한 가상 스위치 포트와 연결된 리프 스위치의 VLAN 설정이 함께 자동으로 맞춰진다. 그래서 가상 머신을 옮겨도 관리자가 물리 스위치를 다시 설정하지 않는다.

#4동작 과정

  1. VMM 도메인 등록APIC가 가상화 관리 서버의 주소와 자격 증명을 등록하고 가상 스위치·호스트 목록을 가져온다. 그래서 물리 자원과 가상 자원이 하나의 목록으로 보인다.
  2. 정책 매핑ACI의 EPG·VLAN 풀과 가상 스위치의 포트그룹을 연결하고, 가상 머신이 붙을 위치를 정책에 묶는다. 그래서 가상 머신의 배치가 곧 네트워크 정책이 된다.
  3. 동적 프로비저닝가상 머신이 생성·이동되면 APIC와 관리 서버가 이벤트를 주고받아 해당 포트와 VLAN을 자동 설정한다. 그래서 가상 머신 이동 시 물리 설정을 다시 만지지 않는다.

#5한 줄 요약

물리 패브릭 정책(ACI)과 가상화 관리 계층을 연동해, 가상 머신의 생성·이동에 맞춰 네트워크 설정이 자동으로 따라가게 만드는 것

패킷 플로우 분석

유니캐스트·멀티캐스트·브로드캐스트 트래픽이 데이터센터 패브릭을 지나는 경로와 포워딩 동작을 분석하는 능력이다.

#1문제 상황

데이터센터 패브릭에서 트래픽은 여러 스위치와 링크를 거쳐 이동한다. 기존에는 개별 인터페이스의 카운터만 보며 트래픽을 확인했기 때문에, 특정 트래픽이 어느 경로로 흘러 어디서 막히는지 알기 어려웠다. 그래서 유니캐스트·멀티캐스트·브로드캐스트가 각각 어떤 포워딩 동작을 거치는지 분석하지 못하면 장애 원인을 좁히기 힘들다.

#2핵심 질문

데이터센터 패브릭에서 각 트래픽 유형이 어떤 경로와 포워딩 규칙으로 이동하며, 문제가 생기면 그 흐름을 어떻게 추적할 수 있는가?

#3동작 예시

같은 서브넷의 두 호스트가 통신할 때 유니캐스트는 목적지 MAC을 학습한 포트로만 전달된다. 목적지 MAC을 아직 모르면 브로드캐스트로 같은 세그먼트 전체에 뿌려지고, 멀티캐스트는 그룹에 등록된 포트로만 복제된다. 이 세 경우를 구분해 관찰하면 한 트래픽이 패브릭을 지나는 방식을 파악할 수 있다.

#4동작 과정

  1. 트래픽 유형 판별목적지 주소를 보고 유니캐스트·멀티캐스트·브로드캐스트 중 무엇인지 구분한다. 그래서 같은 프레임이라도 처리 경로가 달라진다.
  2. 포워딩 테이블 조회MAC·라우팅 테이블과 멀티캐스트 그룹 정보를 조회해 나갈 포트를 정한다. 그래서 목적지가 학습돼 있으면 해당 포트로만, 아니면 플러딩으로 전달된다.
  3. 경로 추적·검증카운터, 미러링, 플로우 로그로 각 구간을 확인해 어느 홉에서 변형되거나 드롭되는지 찾는다. 그래서 장애 지점을 정확히 좁힐 수 있다.

#5한 줄 요약

데이터센터 패브릭을 지나는 트래픽을 유형별 포워딩 동작과 경로 단위로 추적해 장애와 지연의 원인을 찾아내는 것

클라우드 서비스·배포 모델

NIST 800-145 기준으로 IaaS/PaaS/SaaS 서비스 모델과 프라이빗·퍼블릭·하이브리드·커뮤니티 배포 모델을 구분하는 개념이다.

#1문제 상황

기존 온프레미스 방식은 서버·스토리지·네트워크를 직접 구매해 운영해야 했다. 자원이 필요할 때마다 조달과 설치에 시간이 걸리고, 수요가 줄면 유휴 장비가 남아 비용이 낭비된다. 이 한계를 어떤 책임 분담과 운영 형태로 나눌지가 문제였다.

#2핵심 질문

어떤 자원까지 제공자에게 맡기고 어떤 수준의 통제를 유지할 것인가를, 서비스 모델과 배포 모델로 어떻게 구분하는가?

#3동작 예시

NIST 800-145 기준에서 IaaS는 가상 머신·스토리지·네트워크 같은 기반 자원을 제공하고 사용자가 그 위 계층을 직접 관리한다. PaaS는 런타임과 개발 환경까지 제공해 사용자는 애플리케이션만 올리면 되고, SaaS는 완성된 소프트웨어를 그대로 사용한다. 같은 클라우드라도 어디까지 관리하느냐에 따라 모델이 갈린다.

#4동작 과정

  1. 서비스 모델 선택IaaS·PaaS·SaaS 중 제공 범위를 정한다. 그래서 사용자가 직접 관리할 계층이 달라진다.
  2. 배포 모델 선택프라이빗·퍼블릭·하이브리드·커뮤니티 중 자원 소유와 접근 범위를 정한다. 그래서 보안·규제 요건과 비용 구조가 달라진다.
  3. 책임 경계 확정관리 책임이 제공자와 사용자 사이에서 어디서 나뉘는지 확정한다. 그래서 보안과 운영 업무의 주체가 명확해진다.

#5한 줄 요약

컴퓨팅 자원을 서비스 모델과 배포 모델이라는 두 축으로 나눠, 관리 책임과 통제 범위를 명확히 하는 것

소프트웨어 업데이트(I) — 중단/무중단

소프트웨어 업그레이드가 서비스 중단(disruptive)인지 무중단(nondisruptive)인지와 그 영향(ISSU, 재부팅 등)을 이해하는 개념이다.

→ 03-03 참조

#1문제 상황

스위치 운영체제를 올리려면 기존에는 재부팅이 필요했다. 재부팅하는 동안 포트가 내려가고 트래픽이 끊겨, 서비스 중단 시간을 감수해야 했다. 업데이트가 잦아질수록 이 중단 비용이 커지는 것이 문제였다.

#2핵심 질문

서비스를 멈추지 않고 소프트웨어를 올릴 수 있는가, 아니면 어느 정도 중단을 감수해야 하는가?

#3동작 예시

disruptive 업데이트는 새 이미지를 설치한 뒤 장비를 재부팅한다. 이때 프로세스와 포워딩이 함께 멈춰 트래픽 단절이 생긴다. 반면 nondisruptive 업데이트는 ISSU(In-Service Software Upgrade, 서비스 중 소프트웨어 업그레이드)로 활성 프로세스와 대기 프로세스를 순차 전환해, 재부팅 없이 새 버전으로 넘어간다.

#4동작 과정

  1. 영향 유형 판별업데이트가 재부팅을 요구하는 disruptive인지, 무중단 전환이 가능한 nondisruptive인지 확인한다. 그래서 필요한 유지보수 창과 위험 수준이 정해진다.
  2. 이미지 설치·사전 점검새 소프트웨어를 설치하고 호환성과 자원 여유를 점검한다. 그래서 전환 실패 요인을 미리 걸러낸다.
  3. 전환·재부팅ISSU로 프로세스를 순차 전환하거나, disruptive면 재부팅한다. 그래서 무중단이면 서비스가 유지되고 아니면 단절 후 새 버전으로 올라온다.

#1문제 상황

스위치에는 운영체제 외에도 FPGA나 모듈에 들어가는 펌웨어(EPLD)가 있다. 이 펌웨어가 운영체제 버전과 맞지 않으면 특정 기능이 오동작하거나 아예 인식되지 않는다. 운영체제만 올리고 펌웨어를 그대로 두면 이런 불일치가 남는다.

#2핵심 질문

운영체제 업데이트와 별개로 하드웨어 펌웨어와 패치를 어떤 순서와 조건으로 맞춰야 하는가?

#3동작 예시

EPLD 업그레이드는 대상 모듈이나 슈퍼바이저의 FPGA 이미지를 다시 프로그램한다. 이 작업은 해당 모듈의 재부팅을 요구할 수 있어 진행 중인 트래픽에 영향을 준다. 반면 소프트웨어 패치는 전체 이미지를 교체하지 않고 특정 결함만 고치는 작은 수정본을 적용하는 방식이다.

#4동작 과정

  1. 대상 확인현재 운영체제 버전과 EPLD·패치 버전을 대조해 갱신이 필요한 모듈을 찾는다. 그래서 불필요한 작업과 호환성 문제를 줄인다.
  2. 적용EPLD는 모듈별로 이미지를 다시 쓰고, 패치는 결함 수정본을 설치한다. 그래서 하드웨어 동작과 소프트웨어 결함이 함께 정리된다.
  3. 재부팅·검증펌웨어 특성상 모듈 재부팅이 필요할 수 있어 그 영향을 확인하고, 적용 후 버전과 동작을 검증한다. 그래서 기능 이상 없이 새 상태로 맞춰진다.

#2핵심 질문

스위치 구성을 어떻게 저장하고 비교하며, 문제가 생겼을 때 신속히 되돌릴 수 있는가?

#3동작 예시

변경 전에 현재 구성(running-config)을 시작 구성이나 별도 파일로 백업해 두면, 잘못된 변경이 생겼을 때 그 파일로 되돌린다. 체크포인트를 만들면 특정 시점 구성을 통째로 저장해 두고 롤백할 수 있고, 두 구성 파일을 비교하면 어떤 줄이 달라졌는지 바로 보인다.

#4동작 과정

  1. 백업·체크포인트 생성현재 구성을 파일이나 체크포인트로 저장한다. 그래서 변경 전 상태가 보존된다.
  2. 변경·비교설정을 바꾸고 이전 구성과 비교해 차이를 확인한다. 그래서 의도한 변경인지 검증할 수 있다.
  3. 복원·롤백문제가 생기면 저장한 구성으로 되돌린다. 그래서 장애 시간을 줄이고 일관된 상태로 복구된다.

#2핵심 질문

트래픽 흐름과 장비 상태를 어떤 데이터로 수집하고, 여러 장비를 한곳에서 어떻게 통합해 볼 수 있는가?

#3동작 예시

NetFlow는 스위치를 지나는 플로우의 출발지·목적지·포트·바이트 수를 레코드로 내보내, 어떤 통신이 얼마나 오갔는지 보여준다. SPAN은 특정 포트의 트래픽을 분석 장비가 연결된 포트로 복제해 패킷 단위로 뜯어볼 수 있게 한다. Nexus Dashboard는 이렇게 수집된 정보와 장비 상태를 한 화면에 모아 보여준다.

네트워크 어슈어런스 — 스트리밍 텔레메트리

주기적 폴링 대신 스트리밍 텔레메트리로 장비의 상태 데이터를 실시간 푸시 수집해 네트워크를 상시 검증하는 어슈어런스 개념이다.

#1문제 상황

기존 네트워크 상태 수집은 주로 SNMP 폴링(polling) 방식이었다. 관리 서버가 정해진 주기마다 장비에 질의를 보내 CPU·인터페이스 카운터 같은 값을 받아 오는 형태다.

이 방식은 질의 주기와 다음 질의 사이에 일어난 급격한 변화를 놓친다. 순간적으로 발생하는 트래픽 급증이나 링크 오류는 두 폴링 사이에 벌어지면 기록되지 않고 사라진다.

또한 관리 대상 장비가 늘어날수록 서버가 각 장비에 반복 질의를 던져야 하므로 부하가 커진다. 어떤 값을 볼지 미리 정해 질의해야 하므로, 나중에 필요해진 새로운 상태 항목은 바로 수집 대상에 넣기도 어렵다.

#2핵심 질문

폴링 주기에 묶이지 않고 장비의 상태를 실시간으로 계속 받아 네트워크를 상시 검증할 수는 없을까?

#3동작 예시

장비가 자신의 인터페이스 카운터, CPU 사용률, 전원 상태 같은 값을 정해진 텔레메트리 스트림(telemetry stream)으로 수집기(collector)에 계속 밀어 넣는다. 관리 서버가 "지금 값을 달라"고 요청하지 않아도, 장비가 값이 생길 때마다 능동적으로 전송하므로 관리 측은 항상 최신 상태를 받는다.

#4동작 과정

  1. 스트림 구독·설정관리자가 어떤 상태 항목을 어떤 주기로 내보낼지 장비와 수집기 사이에 정의한다. 이때 수집할 지표와 전송 주기가 정해져 이후 흐름이 자동으로 돌아간다.
  2. 장비의 능동 푸시장비가 정의된 지표를 지정 주기마다 스스로 묶어 수집기로 전송한다. 관리 서버가 질의하지 않으므로 서버 부하가 줄고 폴링 사이 공백이 사라진다.
  3. 상시 검증·활용수집기가 받은 연속 데이터로 상태 추이를 실시간 분석하고 이상 징후를 검증한다. 결과적으로 네트워크 상태가 끊김 없이 감시되고 문제가 빨리 드러난다.

#5한 줄 요약

장비가 상태 데이터를 스스로 실시간 푸시하게 해, 폴링의 공백과 부하 없이 네트워크를 상시 검증하는 것

Nexus Dashboard 기능

Nexus Dashboard가 제공하는 통합 대시보드·사이트 관리·인사이트·오케스트레이션 등 데이터센터 운영 기능을 설명하는 개념이다.

→ 04-2d 참조

#1문제 상황

데이터센터 네트워크를 운영하려면 여러 사이트와 여러 종류의 컨트롤러·스위치를 각각의 개별 관리 화면에서 따로 봐야 했다. 사이트마다, 장비군마다 관리 도구가 흩어져 있어 전체 상태를 한눈에 파악하기 어렵다.

개별 도구는 자기 영역의 데이터만 보여 주므로, 사이트를 넘나드는 문제나 정책 일관성을 확인하려면 관리자가 화면을 오가며 수동으로 대조해야 한다. 이 과정에서 이상 징후를 늦게 발견하고, 반복 작업에 시간이 많이 든다.

운영 자동화도 도구별로 따로 구성해야 해서, 여러 사이트에 같은 정책을 일괄 적용하거나 통합된 인사이트를 얻기가 어렵다.

#2핵심 질문

여러 사이트와 컨트롤러의 상태·정책·운영을 하나의 통합된 화면과 자동화로 관리할 수는 없을까?

#3동작 예시

Nexus Dashboard에 여러 사이트와 컨트롤러를 연결해 두면, 관리자는 하나의 대시보드에서 사이트별 상태·경보·인사이트를 함께 본다. 개별 화면을 오갈 필요 없이 통합된 시점에서 전체를 확인하고, 필요한 정책이나 운영 작업을 한곳에서 지시한다.

#4동작 과정

  1. 사이트·컨트롤러 연결각 데이터센터 사이트와 컨트롤러를 Nexus Dashboard에 등록한다. 분리돼 있던 관리 대상이 하나의 통합 관리 평면으로 모인다.
  2. 통합 뷰·인사이트 수집연결된 대상의 상태·경보·지표를 모아 대시보드와 인사이트로 보여 준다. 관리자는 사이트를 넘나드는 전체 상황과 이상 징후를 한 화면에서 파악한다.
  3. 정책·운영 자동화 적용대시보드에서 정책과 운영 작업을 정의해 여러 사이트에 일괄 반영한다. 결과적으로 일관된 구성과 반복 작업 자동화가 이뤄진다.

UCS 랙 서버

Cisco UCS 랙 서버는 블레이드 섀시 없이 독립적으로 장착하는 1~4U 랙마운트 서버로, CIMC(통합 관리 컨트롤러)로 관리하며 서비스 프로파일을 통해 랙 단위 컴퓨트 자원을 추상화해 구성한다.

#1문제 상황

전통적인 랙마운트 서버는 대개 장비 한 대마다 BIOS·펌웨어·네트워크·부팅 설정을 개별적으로 잡아야 했다. 서버 대수가 늘어나면 같은 설정을 서버마다 반복 입력해야 하고, 설정이 조금씩 어긋나 관리가 어려워진다.

고장 난 서버를 교체할 때도 새 장비에 기존 설정을 사람이 다시 넣어야 한다. 이 과정에서 누락이나 오입력이 생기고, 교체·복구에 시간이 오래 걸린다.

또한 하드웨어 구성 정보가 장비에 흩어져 있어, 어떤 서버가 어떤 자원을 쓰는지 일관된 기준으로 파악하기 어렵다.

#2핵심 질문

서버 한 대씩 설정을 손으로 잡지 않고, 랙 서버의 구성과 자원을 일관된 정책으로 추상화해 관리할 수는 없을까?

#3동작 예시

관리자는 서버마다 BIOS·네트워크·펌웨어 설정을 직접 넣는 대신, 서비스 프로파일(service profile)이라는 논리적 정의를 만들어 랙 서버에 적용한다. 같은 프로파일을 다른 서버에 얹으면 동일한 구성이 그대로 재현되므로, 새 서버를 넣어도 설정을 처음부터 다시 잡지 않는다.

#4동작 과정

  1. 관리 연결·등록랙 서버의 CIMC(통합 관리 컨트롤러, 서버 내장 관리 칩)로 접근해 장비를 관리 체계에 등록한다. 이후 하드웨어 상태와 구성 정보를 중앙에서 볼 수 있게 된다.
  2. 서비스 프로파일 정의BIOS·네트워크·부팅·펌웨어 등 원하는 구성을 담은 서비스 프로파일을 만든다. 설정이 개별 장비가 아니라 논리적 정의로 분리돼 재사용할 수 있게 된다.
  3. 프로파일 적용·연결정의한 프로파일을 대상 랙 서버에 연결해 실제 구성으로 반영한다. 결과적으로 동일 구성이 일관되게 적용되고, 교체 서버에도 같은 프로파일을 얹어 빠르게 복구할 수 있다.

#5한 줄 요약

랙 서버의 구성을 서비스 프로파일로 추상화해, 개별 수작업 없이 일관되게 관리·재현하는 것

블레이드 섀시 초기 설정

UCS 블레이드 섀시 초기 설정은 새 섀시를 전원 연결 후 FI(Fabric Interconnect)에 연결하고 클러스터 구성·관리 IP·정책을 지정해 관리 가능한 상태로 만드는 일련의 단계다.

#1문제 상황

새 블레이드 섀시를 랙에 장착하고 전원을 넣어도, 그 자체로는 관리·운영이 불가능하다. 섀시와 내부 블레이드는 설정이 없으면 어떤 관리 주소로도 접근할 수 없고, 어느 관리 체계에 속하는지도 정해져 있지 않다.

여러 섀시를 하나로 묶어 운영하려면 클러스터 구성과 관리 IP 같은 기본 정보를 먼저 잡아야 한다. 이 초기 설정이 제대로 끝나지 않으면 이후 정책 적용이나 자원 할당이 시작조차 되지 않는다.

초기 값은 한 번 잘못 넣으면 관리 접근 자체가 막혀 복구가 번거로우므로, 순서와 입력 항목을 정확히 지키는 것이 중요하다.

#2핵심 질문

전원만 들어온 새 섀시를 관리·운영 가능한 상태로 만들려면 어떤 초기 설정을 어떤 순서로 잡아야 할까?

#3동작 예시

새 섀시의 전원을 켜고 콘솔로 접속하면, 관리자는 섀시가 어떤 FI(Fabric Interconnect, 섀시를 관리·네트워킹하는 상위 인터커넥트)에 연결될지와 관리 IP를 지정한다. 이 값이 들어가면 섀시가 클러스터에 합류해 중앙 관리 화면에서 보이기 시작한다.

#4동작 과정

  1. 전원·연결 확인섀시 전원을 넣고 FI와의 연결과 내부 링크 상태를 확인한다. 물리 연결이 정상이어야 다음 단계의 구성이 유효해진다.
  2. 클러스터·관리 IP 지정섀시가 속할 클러스터와 관리 주소를 설정한다. 이 정보가 잡혀야 관리 체계가 섀시를 인식하고 중앙에서 접근할 수 있다.
  3. 정책·초기화 마무리기본 정책과 관리 설정을 마저 넣어 섀시가 운영 가능한 상태가 된다. 결과적으로 새 섀시가 클러스터에 통합돼 정책 적용과 자원 할당을 받을 준비를 마친다.

#5한 줄 요약

새 섀시에 연결·클러스터·관리 주소를 지정해 관리 가능한 상태로 끌어올리는 초기 설정 절차

블레이드 섀시 인프라 관리

블레이드 섀시 인프라 관리는 FI·IOM·섀시 전원·냉각·펌웨어 같은 물리 인프라 구성요소를 UCS Manager에서 등록·모니터링·정책으로 제어하는 활동이다.

#1문제 상황

블레이드 섀시는 FI, IOM(섀시 내부 스위치 모듈), 전원, 냉각, 펌웨어 등 여러 물리 구성요소가 맞물려 동작한다. 이 요소들을 각각 따로 점검하고 관리하면, 어느 하나의 상태 변화가 전체에 미치는 영향을 놓치기 쉽다.

펌웨어나 전원·냉각 상태를 장비별로 수동 확인하면, 문제가 커진 뒤에야 발견하게 된다. 구성요소 간 연관을 사람이 계속 추적하기도 부담이 크다.

또한 정책과 실제 하드웨어 상태가 분리돼 관리되면, 특정 구성요소에 적용된 설정이 무엇인지 일관되게 파악하기 어렵다.

#2핵심 질문

FI·IOM·전원·냉각·펌웨어 같은 물리 구성요소를 하나의 관리 체계에서 등록·모니터링·정책 제어할 수는 없을까?

#3동작 예시

UCS Manager에서 섀시의 FI·IOM·전원·냉각 모듈을 한 화면에 등록해 두면, 관리자는 각 구성요소의 상태와 펌웨어를 함께 본다. 예를 들어 특정 IOM의 펌웨어 정책을 지정하면, 그 정책이 해당 모듈에 연결돼 상태와 함께 추적된다.

#4동작 과정

  1. 구성요소 등록·인식FI·IOM·전원·냉각 등 물리 요소를 관리 체계에 등록한다. 각 요소가 어떤 섀시·슬롯에 속하는지 관리 화면에서 식별된다.
  2. 상태 모니터링등록된 구성요소의 동작 상태와 펌웨어 수준을 지속적으로 수집·표시한다. 이상이 생기면 어느 요소에서 발생했는지 바로 짚을 수 있다.
  3. 정책 제어·적용전원·펌웨어 등에 대한 정책을 정의해 구성요소에 반영한다. 결과적으로 물리 인프라가 정책과 함께 일관되게 관리·유지된다.

#5한 줄 요약

섀시의 물리 구성요소를 하나의 관리 체계에서 등록·모니터링·정책 제어로 묶어 일관되게 유지하는 것

UCS 네트워크 관리

UCS 네트워크 관리는 VLAN·LAN 풀과 정책, 파이버 채널/FCoE 스위칭, QoS, 네트워크 템플릿 등을 정의해 서버가 사용할 가상 네트워크 자원을 UCS Manager에서 논리적으로 구성하는 작업이다.

#1문제 상황

서버마다 VLAN, 대역폭, 스토리지 연결 같은 네트워크 자원을 개별적으로 잡으면, 대수가 늘수록 설정이 흩어지고 서로 어긋나기 쉽다. 어떤 서버가 어떤 VLAN과 정책을 쓰는지 일관되게 파악하기 어렵다.

파이버 채널이나 FCoE 같은 스토리지 트래픽과 일반 LAN 트래픽을 함께 다뤄야 하는데, 이를 장비별로 따로 구성하면 설정이 중복되고 관리 부담이 커진다.

QoS처럼 트래픽 우선순위를 다루는 설정도 서버마다 손으로 넣어야 하면 실수가 생기고, 동일한 표준을 유지하기 어렵다.

#2핵심 질문

서버가 사용할 VLAN·스토리지 스위칭·QoS 같은 네트워크 자원을 논리적으로 한곳에서 정의해 일관되게 적용할 수는 없을까?

#3동작 예시

UCS Manager에서 VLAN 풀과 LAN 풀, QoS 정책, 네트워크 템플릿을 미리 정의해 둔다. 서버에 서비스 프로파일을 적용할 때 이 정의들이 함께 연결되므로, 서버마다 같은 네트워크 자원이 재현되고 관리자는 어느 서버가 어떤 VLAN·정책을 쓰는지 한눈에 본다.

#4동작 과정

  1. 풀·정책 정의VLAN, LAN 주소, QoS 등 사용할 자원을 풀(pool)과 정책으로 미리 정의한다. 값이 개별 서버가 아니라 공통 자원으로 분리된다.
  2. 스토리지·네트워크 스위칭 구성파이버 채널/FCoE(이더넷 위로 스토리지 트래픽을 나르는 방식)와 LAN 스위칭을 설정한다. LAN과 스토리지 트래픽이 하나의 관리 체계 안에서 다뤄진다.
  3. 템플릿 연결·적용정의한 풀·정책을 담은 네트워크 템플릿을 서버 프로파일에 묶어 적용한다. 결과적으로 동일한 네트워크 자원이 여러 서버에 일관되게 반영된다.

#5한 줄 요약

서버가 쓸 VLAN·스토리지 스위칭·QoS를 풀·정책·템플릿으로 논리적으로 정의해 일관되게 적용하는 것

UCS 스토리지 관리

UCS 스토리지 관리는 SAN 연결, Fibre Channel 존·VSAN, WWN 풀, SAN 정책과 템플릿을 구성해 서버와 스토리지 간 가상 SAN 접속을 제공하는 작업이다.

#1문제 상황

과거에는 서버와 스토리지를 연결할 때 서버마다 개별 HBA 카드를 꽂고, 스토리지 스위치의 각 포트에 접속 설정을 하나씩 손으로 넣었다. 서버가 수십 대만 넘어가도 어떤 서버의 어떤 포트가 어느 스토리지 볼륨에 연결되는지 관리 대장이 금방 어긋났다.

게다가 서버를 한 대 교체하면 그 서버가 쓰던 세계고유이름(WWN, 스토리지가 포트를 식별하는 주소)도 함께 바뀌어 스토리지 쪽 접속 허용 목록과 존 설정을 다시 손봐야 했다. 서버 한 대 때문에 스토리지 네트워크 전체 설정이 흔들리고, 사람이 손으로 맞추는 과정에서 접속이 끊기거나 잘못된 볼륨이 보이는 사고가 반복됐다.

#2핵심 질문

여러 서버의 스토리지 접속 주소와 경로를 사람이 일일이 고치지 않고, 서버 교체나 확장 때도 같은 방식으로 자동 유지하려면 어떻게 해야 하는가?

#3동작 예시

UCS에서 SAN 스토리지 정책을 하나 만들고 WWN 풀에서 주소를 미리 떼어 둔다. 이 정책을 서비스 프로파일에 묶어 두면, 블레이드를 새로 꽂아도 프로파일이 지정한 WWN과 VSAN(Virtual SAN, 물리 스위치 하나를 여러 개의 논리 SAN으로 나눈 것) 값이 그대로 적용된다. 스토리지 쪽 존 설정은 이 미리 약속된 WWN을 기준으로 이미 잡혀 있으므로, 새 서버는 별도 작업 없이 정해진 볼륨에 그대로 접속한다.

#4동작 과정

  1. 자원 정의WWN 풀에 사용할 주소 범위를 등록하고, VSAN·Fibre Channel 존(스위치 포트를 용도별로 묶는 논리 구역) 정보와 SAN 연결 정책·템플릿을 UCS Manager에 만든다. 주소와 경로 규칙이 사람 손이 아니라 정책에 담긴다.
  2. 프로파일에 결합만든 SAN 정책과 템플릿을 서비스 프로파일(서버에 적용할 설정 묶음)에 연결하고 WWN 풀에서 주소를 할당한다. 서버가 어떤 스토리지에 어떤 주소로 붙을지가 프로파일 하나로 정해진다.
  3. 적용과 유지프로파일을 물리 서버에 적용하면 지정된 WWN·VSAN으로 SAN 접속이 이뤄지고, 서버를 교체해도 같은 프로파일이 같은 주소와 경로를 다시 부여해 스토리지 접속이 그대로 유지된다.

#5한 줄 요약

SAN 접속 정보를 WWN 풀·VSAN·정책·템플릿에 미리 정의해 서비스 프로파일로 서버에 자동 부여함으로써, 서버 교체와 확장에도 스토리지 연결을 일관되게 유지하는 것

UCS 서버 관리

UCS 서버 관리는 서버 풀과 부팅 정책, 서비스 프로파일·템플릿을 정의해 물리 서버에 적용함으로써 서버 자원을 추상화하고 일관되게 배포·운영하는 작업이다.

#1문제 상황

기존 방식에서는 서버 한 대마다 BIOS 설정, 부팅 순서, 네트워크 어댑터 설정을 콘솔에 접속해 직접 넣었다. 서버가 수백 대로 늘어나면 대수만큼 같은 작업을 반복해야 했고, 설정 하나가 다르면 장애 원인을 찾기도 어려웠다.

서버가 고장 나 예비 장비로 교체하면 그 장비에 다시 똑같은 설정을 손으로 넣어야 했고, 그 사이 서비스는 멈춰 있었다. 서버마다 설정이 조금씩 달라지는 형상 불일치가 쌓이면 배포와 운영이 사람 기억에 의존하게 된다.

#2핵심 질문

서버 대수와 무관하게 동일한 설정을 한 번 정의해 두고, 교체·증설 때도 자동으로 그대로 적용할 수는 없는가?

#3동작 예시

서버 풀에 예비 서버 여러 대를 등록해 두고, 부팅 정책에 "로컬 디스크 → SAN 부팅 → PXE 네트워크 부팅" 순서를 정의한다. 서비스 프로파일 템플릿에 이 부팅 정책과 BIOS·어댑터 설정을 담고, 이 프로파일을 특정 서버에 연결하면 새 서버도 템플릿에 적힌 대로 부팅 순서와 펌웨어 설정이 자동 적용된다. 서버 한 대가 죽으면 예비 서버에 같은 프로파일을 붙이는 것만으로 동일한 서버가 다시 살아난다.

#4동작 과정

  1. 풀과 정책 정의서버 풀(사용할 물리 서버들의 묶음)과 부팅 정책(부팅 순서를 정한 규칙)을 만든다. 어떤 서버를 어떤 순서로 부팅시킬지가 정책으로 고정된다.
  2. 템플릿 작성서버 자원을 추상화한 서비스 프로파일 템플릿에 BIOS·어댑터·부팅 정책을 담는다. 서버 설정의 원본이 하나로 모여 대수만큼 반복할 필요가 없어진다.
  3. 프로파일 적용템플릿에서 만든 서비스 프로파일을 서버 풀의 물리 서버에 연결하면, 그 서버의 설정이 템플릿과 일치하도록 맞춰지고 교체·증설 시에도 같은 방식으로 재현된다.

#5한 줄 요약

서버 설정을 서버 풀·부팅 정책·서비스 프로파일 템플릿으로 추상화해 물리 서버에 자동 적용함으로써, 대수와 무관하게 동일한 서버를 일관되게 배포·운영하는 것

UCS-X와 Intersight Managed Mode

UCS-X와 Intersight Managed Mode는 차세대 UCS X-시리즈를 로컬 UCS Manager 대신 클라우드 기반 Cisco Intersight로 정책·프로파일을 관리하는 운영 모델이다.

#1문제 상황

전통적인 UCS Manager 방식에서는 각 사이트에 로컬 관리 컨트롤러(FI)가 있고, 관리자가 그 장비에 직접 접속해 정책과 프로파일을 관리했다. 사이트가 여러 곳으로 늘어나면 사이트마다 개별 관리 화면을 따로 열어 같은 정책을 손으로 맞춰야 했고, 전체 서버 상태를 한눈에 보기 어려웠다.

또 관리 기능이 로컬 장비에 묶여 있어, 장비가 영향을 받으면 관리 자체가 제한되고 원격 사이트 대응이 늦어졌다. 정책을 사이트마다 다르게 관리하다 보니 설정 불일치와 관리 부담이 쌓였다.

#2핵심 질문

여러 사이트의 UCS 장비를 사이트별 로컬 관리 화면에 의존하지 않고 하나의 정책으로 일관되게 관리할 수는 없는가?

#3동작 예시

UCS X-시리즈 섀시를 클라우드 기반 Cisco Intersight에 등록하면, 정책과 서비스 프로파일을 Intersight 화면에서 만들어 여러 사이트 장비에 내려보낼 수 있다. 관리자는 사이트마다 접속하지 않고 한 대시보드에서 정책을 배포하고 각 서버 상태를 확인한다. 로컬 UCS Manager 대신 클라우드 관리 평면이 정책을 중앙에서 내려주는 구조다.

#4동작 과정

  1. 등록UCS X-시리즈 장비를 Intersight 계정에 연결하고 관리 대상으로 등록한다. 관리 지점이 로컬 장비에서 클라우드 관리 평면으로 옮겨진다.
  2. 정책 정의Intersight에서 서버 정책과 서비스 프로파일을 작성한다. 정책 원본이 한 곳에 모여 사이트별 중복 작업이 사라진다.
  3. 중앙 배포·모니터링정의한 정책을 여러 장비에 내려보내 적용하고, 각 서버·섀시 상태와 텔레메트리를 중앙에서 수집한다. 사이트가 늘어도 같은 정책으로 관리가 확장된다.

#5한 줄 요약

UCS X-시리즈의 정책·프로파일 관리를 로컬 UCS Manager에서 클라우드 기반 Cisco Intersight로 옮겨, 여러 사이트의 서버를 하나의 정책으로 중앙 관리하는 것

펌웨어·소프트웨어 업데이트 영향

펌웨어·소프트웨어 업데이트 영향이란 블레이드·랙 서버와 섀시 구성요소의 펌웨어/FI 소프트웨어를 올릴 때 재부팅·서비스 중단 여부(disruptive/nondisruptive)와 무중단 업그레이드 순서를 이해하는 개념이다.

#1문제 상황

블레이드·랙 서버와 섀시 구성요소는 각각 BIOS, 어댑터, 관리 컨트롤러, 패브릭 인터커넥트(FI, 서버와 네트워크를 연결하는 UCS 관리 장비) 소프트웨어 등 여러 펌웨어를 따로 갖고 있다. 이 버전들이 서로 맞지 않으면 구성요소 간 호환 문제나 예상치 못한 장애가 생긴다.

문제는 업데이트가 항상 무중단이 아니라는 점이다. 어떤 구성요소는 재부팅이 필요해 그 서버의 서비스가 잠시 멈추고, 어떤 것은 서비스 영향 없이 올라간다. 무중단/중단 여부와 올리는 순서를 모르고 진행하면 예정에 없던 서비스 중단을 부른다.

#2핵심 질문

여러 구성요소의 펌웨어·소프트웨어를 올릴 때 어떤 것이 서비스를 중단시키고 어떤 순서로 올려야 중단을 최소화할 수 있는가?

#3동작 예시

서버의 BIOS·어댑터 펌웨어와 FI 소프트웨어를 같은 목표 버전으로 맞추는 경우를 본다. FI를 먼저 올려 관리 평면을 준비한 뒤, 서버 펌웨어는 정해진 유지보수 시간에 올린다. BIOS처럼 재부팅이 필요한 구성요소는 그 서버의 서비스가 중단되므로, 서비스 영향이 없는 구성요소와 중단이 필요한 구성요소를 구분해 순서를 잡는다.

#4동작 과정

  1. 영향 파악각 구성요소 업데이트가 재부팅이나 서비스 중단을 일으키는지(중단/무중단) 확인한다. 무엇이 서비스에 영향을 주는지 먼저 가려낸다.
  2. 순서·시점 결정호환되는 목표 버전을 정하고, 무중단 구성요소와 중단 구성요소의 순서, 유지보수 시간을 계획한다. 중단이 예정된 작업으로 정리된다.
  3. 적용과 확인계획한 순서대로 펌웨어·소프트웨어를 올리고 버전이 목표와 일치하는지 확인한다. 중단을 최소화하며 구성요소 간 버전 정합성이 맞춰진다.

#5한 줄 요약

각 구성요소 업데이트의 중단/무중단 여부와 호환 버전을 파악해 올리는 순서와 시점을 정함으로써, 서비스 중단을 최소화하며 펌웨어·소프트웨어를 정합성 있게 유지하는 것

컴퓨트 구성 관리(백업·복원)

컴퓨트 구성 관리(백업·복원)는 UCS Manager 전체 구성과 서비스 프로파일을 정기적으로 내보내고 필요 시 복원해 장애나 재해에서 컴퓨트 구성을 신속히 되돌리는 작업이다.

#1문제 상황

UCS Manager에는 서버 풀, 정책, 서비스 프로파일 등 컴퓨트 운영에 필요한 설정이 모두 들어 있다. 이 설정을 백업해 두지 않으면, 관리 장비가 고장 나거나 설정이 잘못 변경됐을 때 수백 대 서버의 프로파일과 정책을 처음부터 다시 만들어야 한다.

설정은 사람이 콘솔에서 하나씩 바꾸기 때문에 언제 무엇이 바뀌었는지 추적하기도 어렵다. 장애나 실수로 구성이 손상되면 복구에 오랜 시간이 걸리고, 그동안 서버 배포와 운영이 멈춘다.

#2핵심 질문

관리 장비 장애나 설정 손상 시 컴퓨트 구성을 처음부터 다시 만들지 않고 신속히 되돌리려면 어떻게 해야 하는가?

#3동작 예시

UCS Manager 전체 구성과 서비스 프로파일을 정기적으로 파일로 내보내 보관한다. 이후 관리 장비가 교체되거나 설정이 잘못 바뀌면, 백업해 둔 파일을 불러와 이전 구성으로 되돌린다. 정책·풀·프로파일이 백업 시점 그대로 복원되어 서버가 원래대로 운영된다.

#4동작 과정

  1. 백업 생성UCS Manager 전체 구성과 서비스 프로파일을 정기적으로 내보내 파일로 보관한다. 현재 구성의 원본이 서버 밖에 확보된다.
  2. 변경·장애 발생설정 변경이나 관리 장비 장애로 구성이 손상된다. 손상 전 시점의 백업이 복구 기준이 된다.
  3. 복원백업 파일을 불러와 구성을 되돌리고 정상 여부를 확인한다. 정책·풀·프로파일이 복구되어 컴퓨트 운영이 신속히 재개된다.

컴퓨트 인프라 모니터링(SPAN·Intersight)

컴퓨트 인프라 모니터링은 SPAN으로 트래픽을 복제·분석하고 Cisco Intersight로 서버·섀시의 상태와 텔레메트리를 수집해 이상을 조기에 감지하는 활동이다.

#1문제 상황

서버와 섀시에서 문제가 생겨도 로그와 상태 지표를 각 장비에서 따로 확인하면, 이상 징후를 뒤늦게 발견하기 쉽다. 특히 서버와 스토리지 사이를 오가는 트래픽 문제는 장비 자체 상태만 봐서는 원인을 잡기 어렵다.

트래픽을 분석하려면 스위치 포트를 지나는 패킷을 복제해야 하는데, 장비마다 이를 따로 설정하고 수집하면 전체 흐름을 한눈에 보기 어렵다. 상태·텔레메트리가 여러 화면에 흩어지면 장애를 조기에 감지하고 대응하는 속도가 떨어진다.

#2핵심 질문

여러 서버·섀시의 상태와 트래픽을 한 곳에서 모아 이상 징후를 조기에 감지하려면 어떻게 해야 하는가?

#3동작 예시

SPAN(스위치 포트를 지나는 트래픽을 복제해 분석 장비로 보내는 기능)을 설정해 특정 포트의 패킷을 복제하고, Cisco Intersight로 서버·섀시의 상태와 텔레메트리를 수집한다. 관리자는 복제된 트래픽으로 통신 문제를 들여다보고, Intersight 화면에서 여러 장비의 상태를 함께 확인해 이상을 빨리 찾아낸다.

#4동작 과정

  1. 수집 설정SPAN으로 분석할 포트와 복제 대상을 지정하고, 장비를 Intersight에 등록한다. 트래픽과 상태를 모을 경로가 마련된다.
  2. 데이터 수집복제된 트래픽이 분석 대상으로 전달되고, 서버·섀시의 상태·텔레메트리가 Intersight로 모인다. 흩어져 있던 정보가 한곳에 쌓인다.
  3. 분석·감지수집된 트래픽과 텔레메트리를 살펴 이상 징후를 조기에 감지하고 대응한다. 문제를 장비별로 따로 보지 않고 통합해 파악한다.

Fibre Channel 개요

SAN에서 서버와 스토리지가 전용 고속 네트워크로 블록 데이터를 주고받기 위한 표준 전송 계층이다.

#1문제 상황

서버가 스토리지의 데이터를 읽고 쓰는 전통적인 방식은 이더넷 네트워크 위에 파일 공유 프로토콜을 얹어 처리하는 것이었다. 이 구조는 여러 서버가 같은 링크를 공유하기 때문에 대량의 블록 데이터를 다룰 때 지연이 커지고 속도가 들쭉날쭉해진다.

스토리지 입장에서는 누가 언제 얼마나 요청할지 예측하기 어렵고, 장애가 났을 때 어느 경로가 문제인지 추적하기도 번거롭다. 그래서 안정적인 대역폭과 낮은 지연이 필요한 블록 스토리지에는 별도의 전용 고속 네트워크가 필요해졌다.

#2핵심 질문

서버와 스토리지가 블록 데이터를 안정적인 속도와 낮은 지연으로 주고받으려면 어떤 전용 전송 계층이 필요한가?

#3동작 예시

서버의 HBA(Host Bus Bus Adapter, 서버를 FC 네트워크에 연결하는 어댑터)가 스토리지의 대상 포트로 데이터를 보낸다. 이때 데이터는 고정 크기 프레임 단위로 쪼개져 전용 링크를 따라 순서대로 흐르고, 스토리지는 받은 프레임을 정해진 주소로 되돌려 응답한다. 이 전용 경로 위에서만 블록 데이터가 오가므로 다른 트래픽과 섞이지 않는다.

#4동작 과정

  1. 연결 설정서버의 HBA와 스토리지 포트가 패브릭(Fibre Channel 스위치망)에 접속하고 각자 고유 주소를 부여받아 서로를 식별할 수 있게 된다.
  2. 프레임 전송데이터가 FC 프레임(정해진 크기의 전송 단위)으로 나뉘어 전용 링크를 통해 목적지 주소로 전달되고, 순서와 흐름 제어가 함께 관리된다.
  3. 응답과 확인스토리지가 수신을 확인하는 응답을 보내고, 서버는 그 결과에 따라 다음 블록 작업을 이어가 전체 입출력이 안정적으로 완료된다.

#5한 줄 요약

SAN에서 서버와 스토리지가 전용 고속 네트워크로 블록 데이터를 안정적으로 주고받게 하는 표준 전송 계층

스위치 패브릭 초기화

FC 스위치가 부팅할 때 principal switch를 선출하고 도메인 ID를 할당받아 패브릭에 합류하는 초기화 과정이다.

#1문제 상황

여러 FC 스위치가 서로 연결된 패브릭에서는 각 스위치가 고유한 도메인 ID를 가져야 주소 충돌 없이 트래픽을 전달할 수 있다. 그런데 스위치를 새로 켜거나 링크가 끊겼다 복구되면, 어느 스위치가 이 주소 체계를 관리할지 정해져 있지 않으면 서로 같은 ID를 주장하며 충돌한다.

이 상태에서는 프레임이 엉뚱한 곳으로 가거나 아예 전달되지 않아 전체 패브릭이 불안정해진다. 그래서 부팅 시점에 역할과 주소를 자동으로 확정하는 절차가 반드시 필요하다.

#2핵심 질문

여러 FC 스위치가 연결될 때 누가 주소 체계를 관리하고 각 스위치는 어떤 도메인 ID를 가질지 어떻게 자동으로 정하는가?

#3동작 예시

스위치 두 대가 ISL(Inter-Switch Link, 스위치 사이를 잇는 링크)로 연결되어 부팅한다. 두 스위치가 서로 우선순위 정보를 교환하고, 더 높은 우선순위를 가진 쪽이 principal switch(주소 체계를 총괄하는 대표 스위치)로 선출된다. 대표가 된 스위치는 나머지 스위치에 도메인 ID를 하나씩 나눠 주고, 각 스위치는 부여받은 ID로 패브릭에 정식 합류한다.

#4동작 과정

  1. 교섭연결된 스위치들이 각자의 우선순위와 설정 정보를 주고받으며 누가 대표가 될지 비교한다.
  2. 대표 선출가장 높은 우선순위의 스위치가 principal switch로 결정되고, 나머지는 대표에게 도메인 ID를 요청한다.
  3. 주소 할당과 합류대표가 충돌 없는 도메인 ID를 배정하면 각 스위치는 그 ID를 확정하고 패브릭 구성원으로 동작을 시작한다.

#5한 줄 요약

FC 스위치가 부팅할 때 대표 스위치를 선출하고 도메인 ID를 배정받아 충돌 없이 패브릭에 합류하게 하는 초기화 절차

FC 포트 채널과 FCID

여러 ISL 링크를 묶어 대역폭을 늘리는 포트 채널과, 패브릭 내 각 포트에 부여되는 고유 주소인 FCID를 다룬다.

→ 03-02 참조

#1문제 상황

패브릭에서 스위치 사이를 잇는 ISL 링크 하나만 쓰면 그 링크의 대역폭이 전체 성능을 제한한다. 트래픽이 몰리면 링크가 포화되고, 그 링크가 끊기면 경로 자체가 사라져 통신이 중단된다.

또한 패브릭 안에는 수많은 포트가 있는데, 각 포트가 고유하게 식별되지 않으면 프레임이 정확한 목적지로 전달될 수 없다. 대역폭 확보와 주소 식별이라는 두 가지 문제를 함께 풀어야 한다.

#2핵심 질문

스위치 간 링크의 대역폭을 늘리면서 패브릭 안 모든 포트를 고유하게 식별하려면 어떻게 해야 하는가?

#3동작 예시

스위치 A와 B 사이에 물리 링크 두 개를 묶어 하나의 포트 채널(여러 링크를 하나로 합쳐 쓰는 논리 링크)로 만든다. 이제 트래픽은 두 링크에 나뉘어 실려 대역폭이 늘어나고, 한 링크가 끊겨도 나머지로 통신이 유지된다. 한편 이 패브릭에 접속한 포트 하나하나는 FCID(Fibre Channel ID, 패브릭 내 포트 고유 주소)를 부여받아, 프레임이 그 주소를 보고 정확한 목적지로 간다.

#4동작 과정

  1. 링크 묶기여러 ISL을 하나의 포트 채널로 구성해 대역폭을 합치고, 링크 하나가 끊겨도 나머지로 트래픽이 계속 흐르게 한다.
  2. 주소 부여포트가 패브릭에 접속하면 도메인 ID와 포트 번호를 조합한 FCID를 할당받아 고유 주소를 갖는다.
  3. 전달과 활용프레임은 목적지 FCID를 기준으로 전달되고, 포트 채널 덕분에 링크를 늘리거나 줄여도 통신이 끊기지 않는다.

#5한 줄 요약

여러 ISL을 묶어 대역폭과 이중화를 확보하고, 각 포트에 고유한 FCID를 부여해 프레임이 정확히 전달되게 하는 것

CFS·Zoning·FCNS

CFS로 서비스 설정을 패브릭 전체에 분산·동기화하고, Zoning으로 디바이스 간 접근을 제어하며, FCNS로 이름 서비스를 제공한다.

→ 03-07 참조

#1문제 상황

패브릭이 커지면 스위치마다 같은 설정을 사람이 하나하나 넣어야 해서 시간이 오래 걸리고 실수도 잦다. 어떤 스위치에는 새 설정이 반영되고 다른 스위치에는 안 되어 있으면 동작이 서로 달라진다.

또한 아무 포트나 서로 통신할 수 있게 두면 접근이 제어되지 않아 보안과 성능 모두 위험해진다. 그리고 각 포트가 어떤 이름과 주소를 쓰는지 조회할 수단이 없으면 연결 대상을 찾기가 어렵다. 설정 동기화, 접근 제어, 이름 조회를 함께 해결해야 한다.

#2핵심 질문

패브릭 전체의 설정을 자동으로 맞추고, 디바이스 간 접근을 제어하며, 각 포트의 이름 정보를 조회하려면 무엇이 필요한가?

#3동작 예시

한 스위치에서 zoning(포트 간 접근 허용 목록) 규칙을 추가하면, CFS(Cisco Fabric Services, 스위치 간 설정을 자동으로 분산·동기화하는 서비스)가 이 설정을 다른 스위치로 전파해 모든 스위치가 같은 규칙을 갖게 된다. 이 규칙에 등록된 서버 포트와 스토리지 포트만 서로 통신할 수 있고, 나머지는 차단된다. 연결 대상을 찾을 때는 FCNS(Fibre Channel Name Server, 포트의 이름·주소 정보를 등록하고 조회하는 서비스)에 질의해 원하는 디바이스의 주소를 확인한다.

#4동작 과정

  1. 설정 동기화한 스위치의 설정 변경을 CFS가 감지해 패브릭의 다른 스위치로 전파하고, 각 스위치가 같은 설정을 유지하도록 맞춘다.
  2. 접근 제어zoning으로 허용된 포트 조합만 통신하도록 제한해, 규칙 밖의 연결은 차단한다.
  3. 이름 조회FCNS에 등록된 포트 정보를 통해 원하는 디바이스의 이름과 주소를 조회해 관리와 연결에 활용한다.

긴 WWN 대신 사람이 읽기 쉬운 이름을 매핑해 zoning 등 설정과 관리 작업을 쉽게 하는 기능이다.

→ 03-04 참조

#1문제 상황

FC의 각 포트는 WWN(World Wide Name, 디바이스를 식별하는 고유 주소)으로 구분되는데, 이 값은 16자리 긴 16진수라 사람이 외우거나 눈으로 구분하기 어렵다. zoning 같은 설정을 할 때마다 이 긴 문자열을 직접 입력하면 오타가 나기 쉽고, 어느 주소가 어느 장비인지 헷갈린다.

장비가 늘어날수록 잘못된 주소를 넣어 설정이 어긋나는 일이 잦아지고, 관리 작업의 정확도가 떨어진다.

#2핵심 질문

외우기 어려운 긴 WWN을 사람이 읽기 쉬운 이름으로 대신 써서 설정 실수를 줄이려면 어떻게 해야 하는가?

#3동작 예시

스토리지 포트의 WWN에 "db_storage_port1" 같은 별칭을 매핑해 둔다. 이후 zoning 규칙을 만들 때 긴 주소 대신 이 별칭을 써서 지정하면, 설정이 짧고 읽기 쉬워지고 어느 장비를 가리키는지도 바로 알 수 있다. 실제 패브릭에는 별칭이 원래 WWN으로 변환되어 적용된다.

#4동작 과정

  1. 별칭 정의관리자가 특정 WWN에 사람이 읽기 쉬운 이름을 매핑해 등록한다.
  2. 설정에 사용zoning 등에서 긴 주소 대신 별칭을 입력하고, 시스템이 이를 실제 WWN으로 해석한다.
  3. 관리 편의별칭 목록을 보고 장비를 식별하며, 주소를 바꾸지 않고도 읽기 쉬운 이름으로 설정을 유지한다.

NPV와 NPIV

NPIV는 하나의 물리 FC 포트에 여러 FCID를 부여하고, NPV는 엣지 스위치가 코어 스위치의 주소 체계를 빌려 쓰는 방식이다.

#1문제 상황

패브릭에 서버가 많아질수록 각 서버 포트가 스위치 포트를 하나씩 차지해 스위치의 물리 포트가 금방 부족해진다. 포트를 늘리려면 스위치를 추가해야 하는데, 새 스위치가 모두 도메인 ID를 가져야 해서 주소 체계가 복잡해지고 관리 부담이 커진다.

또한 가상 환경에서는 하나의 물리 포트로 여러 대상에 접속해야 하는데, 물리 포트당 주소가 하나뿐이면 이를 유연하게 다룰 수 없다.

#2핵심 질문

물리 포트 수를 늘리지 않고 여러 서버와 가상을 하나의 포트로 수용하려면 주소 체계를 어떻게 다루어야 하는가?

#3동작 예시

NPIV(N_Port ID Virtualization)를 켜면 하나의 물리 FC 포트가 여러 개의 FCID를 받아, 마치 여러 포트인 것처럼 동작한다. 여기에 NPV(N_Port Virtualization)를 적용한 엣지 스위치는 스스로 도메인 ID를 갖지 않고, 코어 스위치가 가진 주소 체계를 빌려 서버 연결을 대신 전달한다. 덕분에 엣지 스위치가 늘어나도 패브릭의 도메인 수가 함부로 늘지 않는다.

#4동작 과정

  1. 주소 가상화NPIV가 물리 포트 하나에 여러 FCID를 부여해, 하나의 포트가 여러 디바이스처럼 주소를 갖게 한다.
  2. 엣지 위임NPV로 설정된 엣지 스위치는 직접 도메인 ID를 만들지 않고 코어 스위치의 주소 체계에 연결을 위임한다.
  3. 연결 전달서버 트래픽은 엣지 스위치를 거쳐 코어로 전달되고, 코어가 부여한 주소로 목적지까지 이어져 포트 부족과 주소 복잡도를 줄인다.

#5한 줄 요약

NPIV로 한 물리 포트에 여러 FCID를 부여하고, NPV로 엣지 스위치가 코어의 주소 체계를 빌려 쓰게 해 포트와 도메인 부담을 줄이는 것

VSAN

하나의 물리 FC 패브릭을 논리적으로 분할해 각기 독립된 SAN처럼 격리 운영하는 가상 SAN이다.

→ 03-04 참조

#1문제 상황

초기의 SAN은 물리적 Fibre Channel(서버와 스토리지를 광케이블로 잇는 저장 전용 네트워크) 스위치 여러 대를 한 덩어리 패브릭으로 묶어 사용했다. 이 방식에서는 새 장비를 붙이거나 구성을 바꿀 때마다 케이블과 스위치를 물리적으로 다시 배선해야 했고, 각 팀의 트래픽이 같은 패브릭을 공유해 서로 간섭했다.

용량을 늘리려면 스위치를 추가로 사서 물리적으로 연결하는 수밖에 없었고, 한 곳의 설정 변경이 전체 SAN에 영향을 줄 수 있었다. 결국 물리 장비 수가 늘수록 격리와 확장이 점점 어려워졌다.

#2핵심 질문

하나의 물리적 Fibre Channel 스위치 장비 위에서 여러 개의 독립된 SAN을 동시에 운영할 수는 없을까?

#3동작 예시

물리 FC 스위치 한 대가 여러 개의 VSAN에 포트를 나눠 할당한다고 하자. 1번 VSAN에 묶인 서버와 스토리지는 서로만 통신하고, 2번 VSAN에 묶인 장비들은 1번 VSAN의 존재를 전혀 알지 못한다. 같은 스위치, 같은 케이블을 쓰지만 논리적으로는 완전히 다른 SAN 두 개가 돌아가는 셈이다.

#4동작 과정

  1. VSAN 생성과 포트 할당관리자가 스위치에서 VSAN 번호를 만들고, 각 물리 포트를 특정 VSAN에 소속시킨다. 그 순간 포트는 그 VSAN에만 속한 저장 네트워크의 일부가 된다.
  2. 패브릭 격리포트가 VSAN에 묶이면 로그인·주소 할당·이름 서비스 같은 패브릭 동작이 VSAN별로 따로 처리된다. 서로 다른 VSAN의 장비는 같은 스위치에 있어도 상대를 보지 못해 간섭이 사라진다.
  3. 확장과 운영새 SAN이 필요하면 물리 스위치를 더 사는 대신 VSAN을 하나 더 만들고 포트를 할당하면 된다. 물리 인프라는 그대로 두고 논리적 분할만 늘려 격리된 SAN을 추가한다.

NFS·iSCSI와 스토리지 운영

IP 네트워크를 통해 스토리지에 접근하는 파일 기반 NFS와 블록 기반 iSCSI의 개념과 운영 방식을 설명한다.

#1문제 상황

전통적인 Fibre Channel SAN은 전용 스위치와 광케이블, 전용 어댑터를 갖춰야 해서 비용과 구축 부담이 컸다. 이미 깔려 있는 이더넷 IP 네트워크를 그대로 저장 트래픽에 재사용하고 싶어도, FC는 별도의 저장 전용 망을 요구했다.

또한 서버가 스토리지를 쓰는 방식은 크게 파일 단위냐 블록 단위냐로 갈리는데, 이 차이를 모르면 어떤 프로토콜을 어디에 써야 할지 판단하기 어렵다. 소프트웨어 업데이트를 하면 서비스가 끊기는지 아닌지, 저장 장비를 계속 지켜볼 방법은 무엇인지도 함께 정해야 하는 운영상의 문제가 남는다.

#2핵심 질문

기존 IP 네트워크를 그대로 쓰면서 파일 단위와 블록 단위 스토리지에 접근하고, 그 위에서 장비 상태를 어떻게 지속적으로 감시할 수 있을까?

#3동작 예시

서버 한 대가 파일 공유 스토리지를 쓴다고 하자. NFS(Network File System, 네트워크로 디렉터리를 공유해 파일처럼 읽고 쓰는 방식)로 원격 디렉터리를 마운트하면 서버는 그 안의 파일을 자기 로컬 파일처럼 열고 저장한다. 반대로 데이터베이스처럼 블록을 직접 다뤄야 하는 경우에는 iSCSI(SCSI 명령을 IP 패킷에 실어 보내는 방식)로 원격 디스크를 자기 로컬 디스크처럼 인식시켜 쓴다.

#4동작 과정

  1. 접근 방식 선택공유 폴더처럼 파일 단위로 다루면 NFS를, 원시 블록을 직접 제어해야 하면 iSCSI를 고른다. 서버와 스토리지가 같은 IP 네트워크를 통해 요청을 주고받는다는 점은 공통이다.
  2. 운영과 업데이트펌웨어나 소프트웨어를 올릴 때 서비스가 끊기는 무중단(nondisruptive) 방식과 끊기는 중단(disruptive) 방식을 구분해 적용하고, EPLD(장비 내부 로직을 담은 소자) 업데이트는 별도 절차로 다룬다.
  3. 모니터링SPAN(특정 포트 트래픽을 복제해 관찰 지점으로 보내는 기능)으로 저장 트래픽을 떠 보고, Nexus Dashboard 같은 관리 도구로 장비 상태와 이상 징후를 한곳에서 지켜본다.

#5한 줄 요약

기존 IP 네트워크 위에서 파일 기반 NFS와 블록 기반 iSCSI로 스토리지에 접근하고, 업데이트와 모니터링까지 함께 운영하는 것

자동화·스크립팅 개요

데이터센터 장비 설정·운영을 사람 손 대신 코드와 도구로 반복·자동 실행하는 개념과 그 도구 체계를 말한다.

#1문제 상황

데이터센터 장비 설정은 오랫동안 사람이 터미널에 명령을 하나씩 입력하는 방식으로 이뤄졌다. 장비가 몇 대일 때는 문제가 없지만 수십, 수백 대로 늘어나면 같은 설정을 반복 입력하다 오타가 나고 장비마다 설정이 조금씩 달라진다.

한 대를 고칠 때 다른 장비에도 같은 작업을 손으로 다시 해야 하므로 시간이 오래 걸리고, 누가 언제 무엇을 바꿨는지 추적하기도 어렵다. 사람 손으로 처리하는 한 속도와 정확성 모두 한계에 부딪힌다.

#2핵심 질문

사람이 반복 입력하던 설정과 운영 작업을 코드로 한 번 작성해 여러 장비에 빠짐없이 실행하려면 어떻게 해야 할까?

#3동작 예시

새 스위치 20대에 같은 VLAN 설정을 넣어야 한다고 하자. 관리자가 장비마다 접속해 명령을 치는 대신, 설정 명령을 스크립트(자동 실행되는 명령 묶음) 한 파일에 적어 두고 20대에 차례로 실행한다. 사람은 스크립트를 한 번만 작성하고, 나머지 반복은 도구가 대신한다.

#4동작 과정

  1. 도구 선택어떤 작업을 자동화할지 정한 뒤, 이벤트에 반응하는 EEM, 정해진 시각에 도는 Scheduler, 스위치 안에서 도는 Guest Shell, 외부에서 호출하는 NX-API 같은 도구 중 알맞은 것을 고른다.
  2. 스크립트 작성반복할 명령과 조건을 코드로 적는다. 같은 작업을 장비마다 손으로 치지 않고 파일 하나로 표현해 두면, 그 내용이 곧 실행 절차가 된다.
  3. 실행과 반복스크립트를 대상 장비에 실행해 설정과 운영 작업을 한 번에 적용한다. 사람이 하던 반복이 코드로 대체되어 속도와 일관성이 올라간다.

#5한 줄 요약

장비 설정과 운영 작업을 사람 손 대신 코드와 도구로 반복 실행해 속도와 정확성과 일관성을 확보하는 것

EEM과 Scheduler

EEM(Embedded Event Manager)은 장비 내부 이벤트에 반응해 정책(applet)을 실행하는 기능이고, Scheduler는 정해진 시각에 명령을 주기적으로 실행하는 기능이다.

#1문제 상황

장비에 문제가 생겼을 때 관리자가 그 순간 화면 앞에 없으면 알 방법이 없었다. 인터페이스가 내려가거나 로그에 이상한 메시지가 찍혀도, 누군가 주기적으로 들어와 상태를 확인해 주지 않으면 대응이 늦어졌다.

반대로 매일 새벽에 백업을 돌리는 것처럼 정해진 시각에 반복해야 하는 작업은 사람이 계속 기억하고 손으로 실행해야 했다. 잊으면 빠지고, 사람이 자리를 비우면 아무 일도 일어나지 않았다.

#2핵심 질문

장비 내부에서 무슨 일이 생겼을 때 자동으로 반응하고, 정해진 시각에 반복 작업을 스스로 실행하게 하려면 어떻게 해야 할까?

#3동작 예시

어느 인터페이스가 다운되었다는 로그가 장비에서 올라온다고 하자. EEM(Embedded Event Manager, 장비 내부 이벤트에 반응해 미리 정한 동작을 실행하는 기능)에 그 로그를 감지 조건으로 등록해 두면, 로그가 찍히는 즉시 지정한 명령이 자동으로 실행된다. 한편 매일 새벽 2시에 설정 백업 명령을 돌리고 싶으면 Scheduler(정해진 시각에 명령을 주기적으로 실행하는 기능)에 그 시각과 명령을 등록해 둔다.

#4동작 과정

  1. 정책 등록EEM에는 감시할 이벤트(로그 메시지, 인터페이스 상태 변화 등)와 그때 실행할 동작을 applet이라는 정책 단위로 묶어 등록한다. Scheduler에는 실행 시각과 주기, 명령을 등록한다.
  2. 이벤트 감지와 트리거실제로 그 이벤트가 발생하면 EEM이 이를 감지해 등록된 정책을 실행한다. Scheduler는 정해 둔 시각이 되면 스스로 명령을 시작한다.
  3. 자동 실행 결과사람이 개입하지 않아도 대응 명령이나 반복 작업이 그 순간 실행되고, 그 결과가 장비 로그에 남아 나중에 확인할 수 있다.

#5한 줄 요약

장비가 내부 이벤트에 스스로 반응하고 정해진 시각에 반복 작업을 자동 실행하게 하는 것

Bash·Guest Shell

NX-OS의 Guest Shell을 이용해 스위치 안에서 Linux Bash 환경과 Python 스크립트를 실행하는 기능이다.

#1문제 상황

NX-OS 스위치는 자체 CLI 명령 체계를 갖고 있어서, 설정을 자동화하려면 그 명령을 스크립트로 흉내 내야 했다. 하지만 CLI는 리눅스처럼 파일을 다루고 반복문을 돌리고 프로그램을 설치하는 환경이 아니라서, 복잡한 자동화 로직을 짜기 어려웠다.

자동화를 하려면 외부 서버를 따로 두고 스위치에 원격 접속해 명령을 밀어 넣어야 했다. 그 서버와 스위치 사이의 연결을 관리하고 인증을 맞추는 부담이 늘 따라붙었다.

#2핵심 질문

스위치 밖에 별도 서버를 두지 않고, 장비 안에서 직접 리눅스 환경과 스크립트를 돌릴 수는 없을까?

#3동작 예시

스위치에서 Guest Shell을 켜면 그 안에 리눅스 기반 Bash 환경이 하나 열린다. 관리자는 이 안에서 bash 명령으로 파일을 만들고 Python 스크립트를 작성해 실행한다. 스크립트는 같은 스위치의 NX-OS CLI 명령도 호출할 수 있어, 리눅스 쪽 편의 기능과 스위치 설정을 한 스크립트 안에서 함께 다룰 수 있다.

#4동작 과정

  1. Guest Shell 활성화NX-OS에서 Guest Shell을 켜면 스위치 내부에 격리된 리눅스 컨테이너 환경이 만들어진다. 그 안에는 Bash 셸과 Python 실행 환경이 들어 있다.
  2. 스크립트 작성과 실행관리자가 그 셸에 들어가 Bash 명령이나 Python 스크립트를 작성하고 실행한다. 스크립트는 컨테이너 안에서 도는 동시에 필요하면 NX-OS CLI 명령을 호출해 스위치 설정에도 손을 댄다.
  3. 장비 내 자동화별도 외부 서버 없이 스위치 한 대 안에서 자동화가 완결된다. 리눅스 도구와 스위치 명령을 함께 쓰면서 관리 지점이 줄어든다.

#5한 줄 요약

스위치 안에 리눅스 Bash와 Python 환경을 띄워 장비 자체에서 스크립트 자동화를 돌리는 것

REST API — NX-API·JSON·XML

NX-API로 스위치에 HTTP/HTTPS 기반 REST 호출을 보내 CLI 명령이나 설정을 JSON·XML 형식으로 주고받는 인터페이스다.

#1문제 상황

스위치를 자동화하려면 외부 프로그램이 장비에 명령을 보내고 결과를 받아야 하는데, 전통적인 방법은 원격 접속으로 CLI 화면을 흉내 내는 방식이었다. 이 방식은 사람이 보는 화면 출력을 프로그램이 억지로 읽어야 해서, 출력 형식이 조금만 바뀌어도 파싱이 깨졌다.

또 CLI는 사람이 읽기 좋게 만들어진 텍스트라서 프로그램이 구조적으로 다루기 어려웠다. 여러 장비에서 받은 결과를 모아 처리하려면 매번 출력을 다시 해석해야 했고, 자동화 코드가 화면 모양에 얽매여 잘 깨졌다.

#2핵심 질문

프로그램이 스위치에 명령을 보내고 결과를, 사람이 읽는 화면이 아니라 구조화된 데이터로 주고받으려면 어떻게 해야 할까?

#3동작 예시

외부 프로그램이 NX-API(NX-OS 스위치에 HTTP/HTTPS로 요청을 보내 명령을 실행하는 인터페이스)로 스위치에 요청을 보낸다고 하자. 요청에는 실행할 CLI 명령과 결과를 JSON 또는 XML(프로그램이 읽기 쉬운 구조화된 데이터 형식)로 달라는 지정이 담긴다. 스위치는 명령을 실행한 뒤 그 결과를 지정한 형식의 구조화된 데이터로 돌려주고, 프로그램은 그 값을 그대로 꺼내 쓴다.

#4동작 과정

  1. 요청 전송외부 프로그램이 HTTP/HTTPS 위에서 REST 호출을 만들어 NX-API로 보낸다. 이 요청에 실행할 명령과 원하는 출력 형식(JSON·XML)을 함께 지정한다.
  2. 스위치 처리NX-API가 요청을 받아 안쪽의 CLI 명령을 실행하고, 그 결과를 사람이 보는 텍스트가 아니라 지정한 구조화된 형식으로 변환한다.
  3. 구조화된 응답프로그램은 돌려받은 JSON·XML에서 필요한 필드를 곧바로 꺼내 쓴다. 출력 형식이 고정되어 있어 파싱이 안정적이고 여러 장비의 결과를 일관되게 다룰 수 있다.

#5한 줄 요약

스위치 명령과 결과를 HTTP 기반 REST 호출로 주고받고 그 값을 JSON·XML 구조로 다뤄 자동화가 화면 텍스트에 얽매이지 않게 하는 것

On-box Python

스위치 장비 내부에서 직접 실행되는 Python 인터프리터로, NX-OS 명령과 API를 스크립트로 호출하는 기능이다.

#1문제 상황

기존에는 스위치 한 대에 CLI로 접속해 show 명령을 한 줄씩 직접 입력하고, 그 결과를 눈으로 읽어 확인했다. 장비가 여러 대면 같은 명령을 장비마다 반복 입력해야 하고, 사람이 순서를 빠뜨리거나 값을 잘못 넣으면 그대로 설정 오류로 이어진다.

또한 CLI는 장비 밖에서 돌아가는 별도 서버가 없으면 자동 분기나 결과 가공을 할 수 없다. 예를 들어 수집한 값이 임계치를 넘었을 때만 다음 명령을 실행하는 같은 처리를 하려면 결국 사람이 매번 판단해야 한다.

#2핵심 질문

장비 밖 서버 없이 스위치 안에서 직접 스크립트를 돌려 NX-OS 명령과 API 호출을 자동으로 처리할 수는 없을까?

#3동작 예시

NX-OS CLI에서 python을 입력하면 장비에 내장된 Python 인터프리터로 들어간다. 여기서 import cli로 NX-OS 명령 실행 기능을 불러오고, cli.cli('show interface')를 호출하면 그 명령의 출력이 문자열로 반환된다. 반환된 문자열을 스크립트에서 조건문과 반복문으로 가공해 특정 조건일 때만 설정 명령을 다시 실행하도록 만들 수 있다.

#4동작 과정

  1. 인터프리터 진입CLI에서 Python을 실행하면 장비 내부의 인터프리터가 뜨고, 스크립트 파일을 지정해 부팅 시 자동 실행하게 할 수도 있다.
  2. 명령·API 호출스크립트가 cli 모듈로 NX-OS 명령을 실행하거나 NX-API 같은 인터페이스를 호출해 결과를 데이터로 받는다. 이때 장비 외부 통신 없이 로컬에서 처리된다.
  3. 결과 가공·재실행받은 값을 조건에 따라 판단해 추가 명령이나 설정을 실행하고, 그 결과가 곧바로 장비 상태에 반영된다.

#5한 줄 요약

외부 서버 없이 스위치 내부 인터프리터에서 NX-OS 명령과 API를 스크립트로 자동 실행하는 것

오케스트레이션(I) — Ansible

Ansible은 에이전트 없이 SSH·API로 여러 네트워크 장비에 설정을 배포하는 선언형 자동화·오케스트레이션 도구다.

#1문제 상황

기존에는 관리자가 장비마다 SSH로 접속해 설정 명령을 손으로 입력했다. 장비 수가 늘면 같은 작업을 반복해야 하고, 장비마다 설정이 조금씩 달라지는 불일치가 생기기 쉽다.

또 명령을 한 번 더 실행했을 때 현재 상태를 확인하지 않고 그대로 다시 넣으면 중복 설정이나 오류가 난다. 작업 이력과 결과를 일관된 방식으로 남기기도 어렵다.

#2핵심 질문

여러 네트워크 장비에 같은 설정을 사람 손을 거치지 않고 일관되게 배포하고 반복 실행해도 안전하게 유지할 수는 없을까?

#3동작 예시

Ansible에서는 hosts에 대상 장비 목록을, tasks에 수행할 작업을 적은 playbook 파일 하나를 작성한다. 각 작업은 NX-OS용 모듈을 지정하고 원하는 설정 값을 적는다. playbook을 실행하면 Ansible이 장비 각각에 접속해 그 작업을 순서대로 수행하고, 이미 원하는 상태인 장비에는 같은 설정을 다시 넣지 않는다.

#4동작 과정

  1. 대상·작업 정의playbook에 대상 장비와 수행할 작업을 선언형으로 적는다. "이 상태가 되어야 한다"만 기술하고 절차는 적지 않는다.
  2. 접속·실행Ansible이 대상 장비에 SSH나 API로 접속해 작업을 실행한다. 장비에 상주하는 별도 에이전트가 필요 없는 agentless 방식이다.
  3. 상태 확인·보고각 작업은 현재 상태와 목표 상태를 비교해 필요한 변경만 적용하고, 장비별 성공·변경 여부를 결과로 보고한다.

#5한 줄 요약

에이전트 없이 SSH·API로 여러 장비의 목표 상태를 선언형으로 선언하고 일관되게 배포하는 것

오케스트레이션(II) — Python·POAP

Python 스크립팅과 POAP(PowerOn Auto Provisioning)으로 새 스위치를 부팅 시 자동으로 이미지·설정까지 프로비저닝하는 기술이다.

#1문제 상황

새 스위치를 데이터센터에 투입하려면 콘솔 케이블을 연결해 부팅 과정을 지켜보고, 운영체제 이미지를 설치한 뒤 설정을 하나씩 입력해야 했다. 장비 한 대마다 이 과정을 사람이 반복하므로 시간이 오래 걸리고 입력 실수가 생기기 쉽다.

장비가 수십 대 규모로 들어오면 같은 작업을 대수만큼 반복해야 해서 투입 속도가 사람 손에 묶인다. 또 이미지 버전과 초기 설정이 장비마다 달라지는 문제도 생긴다.

#2핵심 질문

새 스위치를 전원만 켜면 사람이 손대지 않아도 이미지와 설정까지 자동으로 갖춰지게 할 수는 없을까?

#3동작 예시

#4동작 과정

  1. 부팅·주소 요청전원이 켜진 새 스위치가 DHCP로 주소를 요청하고, 응답에 담긴 서버 안내 값으로 프로비저닝 서버 위치를 파악한다.
  2. 스크립트 내려받기·실행안내받은 서버에서 POAP 스크립트를 받아 실행한다. 이 스크립트는 Python으로 작성되어 어떤 이미지와 설정을 가져올지 결정한다.
  3. 이미지·설정 적용스크립트가 운영체제 이미지를 내려받아 설치하고 지정된 설정을 적용한 뒤 장비를 재부팅해 목표 상태로 완료한다.

#1문제 상황

데이터센터 네트워크는 스위치와 라우터가 서버·스토리지·관리 트래픽을 한 물리 인프라 위에서 함께 나른다. 처음 설계될 때 우선순위는 속도와 가용성이었고, 보안은 경계 방화벽 한 곳에서 처리하는 경우가 많았다.

문제는 트래픽이 한 번 경계를 통과한 뒤 내부에서는 거의 무제한으로 흐른다는 점이다. 워크로드 하나가 침해되면 같은 VLAN이나 같은 서브넷 안의 다른 서버로 옮겨 다니기 쉬워진다. 어디까지 허용하고 어디서 막을지 정하는 기준이 계층마다 흩어져 있어, 정책을 한 곳에서 일관되게 적용하기 어렵다.

#2핵심 질문

경계를 넘은 내부 트래픽까지 계층별로 인증·권한·보호를 나눠 적용해 접근을 통제하려면 무엇이 필요한가?

#3동작 예시

관리자 PC가 스위치에 SSH로 접속하려는 상황을 보자. 접속 시도는 먼저 AAA 서버로 가서 사용자 신원을 확인받고(인증), 그 다음 역할에 따라 설정 변경 명령을 쓸 수 있는지 판정받는다(권한 부여). 서버가 "이 사용자는 조회 권한만 있다"고 답하면 스위치는 show 계열 명령만 허용하고 설정 명령은 거부한다. 이처럼 같은 접속 시도에 인증·권한·기록이 계층을 따라 나뉘어 적용된다.

#4동작 과정

  1. 트래픽 분류사용자·단말·워크로드가 어느 계층(관리 평면, 제어 평면, 데이터 평면)에 속하고 어떤 정책을 받을지 정한다. 무엇이 어디서 시작되는지 정해지면 보호 지점이 명확해진다.
  2. 인증과 권한 확인입장 시점에 신원을 검증하고(인증), 역할에 따라 허용 범위를 정한다(권한 부여). 같은 자원이라도 누가 접근하느냐에 따라 결과가 달라진다.
  3. 트래픽 보호와 기록허용된 흐름만 통과시키면서 암호화·무결성 보호를 링크나 구간 단위로 적용하고, 접근 내역을 남긴다(과금). 위반 시도가 생기면 즉시 차단되고 로그로 추적할 수 있다.

네트워크 AAA와 RBAC

AAA는 사용자 인증(Authentication)·권한 부여(Authorization)·과금(Accounting)을 중앙에서 처리하고, RBAC는 역할 기반으로 명령·자원 접근 권한을 제한하는 방식이다.

#1문제 상황

장비마다 로컬 계정과 비밀번호를 개별로 심어두면, 사용자가 늘고 장비가 늘수록 같은 계정을 수십 대에 똑같이 복제해야 한다. 담당자가 퇴사하면 어느 장비에 그 계정이 남았는지 찾아 하나씩 지워야 한다.

권한 관리도 문제다. 모든 관리자에게 똑같은 최고 권한을 주면 조회만 필요한 사람도 설정을 바꿀 수 있다. 누가 언제 어떤 명령을 실행했는지 중앙에 남는 기록도 없어, 사고가 나도 원인을 좇기 어렵다.

#2핵심 질문

계정과 권한을 장비마다 따로 관리하지 않고 중앙에서 인증·권한·기록까지 처리하려면 어떻게 해야 하는가?

#3동작 예시

관리자가 스위치에 접속하면, 스위치는 직접 비밀번호를 대조하지 않고 AAA 서버로 인증을 요청한다. 서버가 사용자 이름과 비밀번호를 확인해 승인하면 접속이 열리고, 동시에 "이 사용자는 network-operator 역할"이라는 권한 정보도 함께 내려온다. 스위치는 그 역할에 맞춰 설정 명령은 거부하고 상태 조회 명령만 허용하며, 실행한 명령 목록을 다시 서버로 보내 기록한다.

#4동작 과정

  1. 인증 요청사용자가 장비에 접속하면 장비는 로컬 계정 대신 AAA 서버에 신원 확인을 요청한다(Authentication). 자격 증명이 중앙 한 곳에서 검증되므로 계정 추가·삭제가 서버 한 번의 변경으로 끝난다.
  2. 권한 부여인증이 끝나면 서버가 사용자의 역할과 그 역할이 쓸 수 있는 명령 범위를 돌려준다(Authorization). RBAC는 역할에 권한을 묶어 두는 방식이라, 개인별로 권한을 흩어 두지 않아도 필요한 만큼만 열어줄 수 있다.
  3. 기록과 감사사용자가 실행한 명령과 접속 시간이 서버로 전달되어 로그로 남는다(Accounting). 사고가 생기면 누가 무엇을 했는지 중앙 기록에서 바로 확인할 수 있다.

#5한 줄 요약

인증·권한 부여·기록을 중앙 서버에서 처리하고 역할 단위로 권한을 제한해, 계정과 명령 접근을 한 곳에서 통제하는 것

ACI 계약과 마이크로세그멘테이션

ACI에서 Contract로 EPG 간 허용 트래픽을 정의하고, 세밀한 EPG/ESG 단위 정책으로 워크로드 간 마이크로세그멘테이션을 구현한다.

#1문제 상황

VLAN과 서브넷 중심으로 정책을 짜면, 같은 서브넷에 있는 서버끼리는 별도 규칙 없이 서로 통신할 수 있다. 보안을 강화하려면 서브넷을 잘게 쪼개야 하는데, 그러면 IP 주소 설계와 라우팅 설정이 급격히 복잡해진다.

게다가 정책이 스위치·방화벽·라우터 곳곳에 흩어져 있으면 "웹 서버는 DB 서버의 특정 포트만 쓸 수 있다" 같은 규칙을 여러 장비에 걸쳐 손으로 맞춰야 한다. 서버가 늘거나 옮겨질 때마다 각 장비 설정을 다시 고쳐야 하고, 어느 한 곳만 빠져도 허용되지 않아야 할 트래픽이 열린다.

#2핵심 질문

서브넷을 다시 쪼개지 않고도 워크로드 사이의 허용 트래픽을 정책 하나로 정의하고 적용할 수 있는가?

#3동작 예시

EPG(Endpoint Group, 같은 정책을 받는 서버 묶음)로 웹 서버 그룹과 DB 서버 그룹을 나눈 상태를 보자. 두 그룹 사이에 Contract(계약) 하나를 걸고, 그 안에 "DB가 제공하는 포트만 사용 허용"이라는 필터를 넣는다. 이 계약이 없으면 두 그룹은 서브넷이 같든 다르든 기본적으로 통신하지 못한다. 서버를 다른 랙으로 옮겨도 그 서버가 어느 EPG에 속하는지만 유지되면 정책은 그대로 따라간다.

#4동작 과정

  1. 그룹 정의같은 정책을 받을 엔드포인트를 EPG(정책을 공유하는 서버 묶음)나 ESG(세밀한 단위로 나눈 그룹)로 묶는다. 개별 IP가 아니라 그룹 단위로 다루므로 서버가 늘어도 정책 대상이 한 곳에 모인다.
  2. 계약으로 허용 정의제공자와 소비자 그룹 사이에 Contract를 맺고, 그 안에 어떤 프로토콜·포트를 허용할지 필터로 지정한다. 명시적으로 계약을 맺은 흐름만 통과하고 나머지는 차단된다.
  3. 정책 적용컨트롤러가 이 계약을 각 스위치에 일관되게 밀어 넣는다. 그룹 변경이나 서버 이동이 있어도 정책 지점이 바뀌지 않으므로, 워크로드 단위로 세밀하게 허용 범위를 좁힐 수 있다.

#5한 줄 요약

EPG 사이에 Contract로 허용 트래픽을 정의해, 서브넷 재설계 없이도 워크로드 단위로 통신을 세밀하게 통제하는 것

First-hop 보안 기능

DHCP snooping, Dynamic ARP Inspection, IP Source Guard 등으로 엔드포인트의 L2/L3 위조 트래픽을 차단하는 스위치 보안 기능이다.

#1문제 상황

스위치의 엔드포인트 포트는 기본적으로 열려 있어, 아무 단말이나 꽂으면 그 세그먼트에 참여한다. 이 환경에서는 악의적인 단말이 정상 서버의 IP나 MAC 주소를 위조해 트래픽을 가로채거나, 가짜 DHCP 서버를 띄워 다른 단말에 잘못된 게이트웨이 정보를 줄 수 있다.

관리자가 이 위조를 눈으로 구분하기는 어렵다. 트래픽은 정상 주소로 흐르는 것처럼 보이지만, 실제로는 중간에서 가로채이거나 잘못된 경로로 보내진다. 클라이언트가 게이트웨이를 위조당하면 외부로 나가는 모든 트래픽이 공격자를 거쳐 가게 된다.

#2핵심 질문

단말이 임의로 IP·MAC·게이트웨이 정보를 위조하지 못하게 하려면 스위치가 무엇을 확인해야 하는가?

#3동작 예시

DHCP snooping을 켠 스위치에서 단말이 DHCP 요청을 보내는 상황을 보자. 스위치는 신뢰하는 포트(trusted, 주로 서버·업링크 쪽)에서 온 DHCP 응답만 통과시키고, 일반 단말 포트에서 온 DHCP 응답은 버린다. 이때 스위치는 어느 MAC이 어느 IP를 받았는지 바인딩 표로 기록해 둔다. 이후 그 단말이 다른 IP를 주장하면 Dynamic ARP Inspection이 이 표를 대조해 위조로 판정하고 프레임을 차단한다.

#4동작 과정

  1. 신뢰 경계 설정DHCP 서버와 업링크가 연결된 포트를 신뢰 포트로 지정한다(trusted). 신뢰하지 않는 일반 단말 포트에서 나온 서버 응답은 차단되어, 가짜 DHCP 서버가 게이트웨이를 뿌리는 것을 막는다.
  2. 바인딩 기록단말이 DHCP로 IP를 받으면 스위치가 "이 MAC은 이 IP"라는 바인딩 표를 만든다. 이후 이 표가 IP·MAC 위조를 판별하는 기준이 된다.
  3. 위조 검사와 차단ARP 응답이 오면 바인딩 표와 맞는지 대조하는 DAI(Dynamic ARP Inspection)가 검사하고, 데이터 트래픽에서는 IP Source Guard가 출발지 IP·MAC이 표와 다른 패킷을 버린다. 위조 패킷이 통과하지 못하고 정상 통신만 유지된다.

#5한 줄 요약

스위치가 신뢰 포트와 바인딩 기록을 기준으로 단말의 IP·MAC·게이트웨이 위조를 걸러내, L2/L3 신원 위장을 차단하는 것

Keychain 인증

라우팅·관리 프로토콜에서 시간 기반으로 교체되는 키 집합(Keychain)을 사용해 메시지 인증을 수행하는 기능이다.

#1문제 상황

라우팅 프로토콜이나 관리 접속에서 인증을 쓰지 않으면, 경로 정보를 주고받는 메시지에 아무 확인 절차가 없다. 이 상태에서는 제3자가 라우팅 업데이트를 위조해 흘려보내도 장비가 정상 메시지로 받아들여, 트래픽 경로가 조작될 수 있다.

정적 비밀번호 하나로 인증하는 방식도 한계가 있다. 비밀번호를 교체하려면 통신하는 양쪽 장비를 같은 시점에 고쳐야 하고, 교체 전후 시점이 어긋나면 인증이 깨져 경로가 끊긴다. 비밀번호가 노출되면 즉시 바꿔야 하지만, 그 순간 통신이 끊길 위험 때문에 미루게 된다.

#2핵심 질문

인증 키를 주기적으로 자동 교체하면서도 교체 순간에 통신이 끊기지 않게 하려면 어떻게 해야 하는가?

#3동작 예시

라우터 두 대가 인증 키를 교체하는 상황을 보자. Keychain에 "지금 유효한 키"와 "다음에 쓸 키"를 시작 시각과 함께 미리 정의해 둔다. 첫 번째 키의 수명이 끝나면 장비는 두 번째 키로 자동 전환해 메시지 인증을 계속한다. 두 장비가 같은 시각 기준으로 키를 바꾸므로, 교체 시점에 관리자가 개입하지 않아도 인증이 유지되며 라우팅 메시지는 끊기지 않는다.

#4동작 과정

  1. 키 집합 정의Keychain에 여러 개의 키를 만들고 각 키에 값과 유효 시간(시작·종료)을 지정한다. 미리 다음 키를 준비해 두므로 교체 시점을 사람이 맞출 필요가 없다.
  2. 시간 기반 전환장비 시각을 기준으로 현재 유효한 키를 골라 메시지 인증에 사용한다. 수명이 끝난 키는 자동으로 빠지고 다음 키가 활성화되어, 교체 순간에도 통신이 끊기지 않는다.
  3. 메시지 검증수신 장비가 같은 Keychain 규칙을 가지고 검증하므로, 키가 맞는 메시지만 받아들여진다. 위조되거나 오래된 키로 서명된 메시지는 버려져 라우팅 정보가 보호된다.

#5한 줄 요약

시간에 따라 자동 교체되는 키 집합으로 메시지를 인증해, 키를 바꾸는 순간에도 통신이 끊기지 않게 라우팅·관리 프로토콜을 보호하는 것

MACsec

IEEE 802.1AE 기반으로 이더넷 링크 구간의 프레임을 암호화·무결성 보호하는 L2 홉-바이-홉 보안 기술이다.

#1문제 상황

데이터센터 안의 링크는 대개 내부 구역에 있다는 이유로 평문으로 흐른다. 하지만 같은 케이블이나 중간 장비를 거치는 구간에서는 다른 트래픽과 섞이거나, 링크를 물리적으로 건드릴 수 있는 위치라면 프레임을 그대로 읽고 변조할 수 있다.

상위 계층의 암호화는 이런 위험을 모두 덮지 못한다. 애플리케이션 암호화는 그 애플리케이션 트래픽만 보호하고, 스위치가 프레임을 전달하는 계층에서는 내용이 그대로 보인다. 그래서 링크를 지나는 모든 프레임을 구간 단위로 보호하는 별도의 수단이 필요하다.

#2핵심 질문

이더넷 링크를 지나는 프레임을 구간마다 암호화하고 변조 여부까지 확인하려면 무엇이 필요한가?

#3동작 예시

스위치 두 대가 연결된 링크에 MACsec을 설정하면, 두 장비가 먼저 세션 키를 협상해 같은 암호 키를 공유한다. 이후 이 링크로 나가는 프레임은 암호화되고 무결성 검사 값이 붙는다. 수신 스위치는 값을 확인해 변조되지 않은 프레임만 받아들이고, 중간에서 프레임을 읽으려 해도 내용이 보이지 않는다. 같은 링크를 쓰는 다른 장비가 있어도 그 구간의 트래픽은 보호된다.

#4동작 과정

  1. 키 협상링크 양 끝 장비가 세션을 맺고 암호 키를 교환한다(키 합의). 이때 만들어진 키로 이후 프레임을 보호하므로, 사전에 같은 비밀 값을 수동으로 맞출 필요가 없다.
  2. 프레임 암호화링크로 나가는 이더넷 프레임을 암호화하고 무결성 검사 값을 덧붙인다. 링크를 지나는 동안 내용이 보이지 않고, 전달 계층에서도 원문이 노출되지 않는다.
  3. 수신 검증반대편 장비가 무결성 값을 확인해 변조·재전송 여부를 판정하고, 통과한 프레임만 상위로 올린다. 링크 단위로 암호화와 무결성이 함께 보장되어 홉-바이-홉 구간이 보호된다.

#5한 줄 요약

이더넷 링크의 두 끝점 사이에서 프레임을 암호화하고 무결성을 검증해, 링크 구간을 홉-바이-홉으로 보호하는 것

컴퓨트 보안 — AAA·RBAC

UCS/Intersight 등 컴퓨트 관리 환경에서 AAA와 역할 기반 접근 제어로 사용자와 관리 권한을 통제하는 방법이다.

→ 05-02 참조

#1문제 상황

UCS와 Intersight 같은 컴퓨트 관리 환경에는 여러 관리자가 동시에 접속해 서버 프로파일, 펌웨어 정책, 가상 인터페이스 설정을 바꾼다. 초기 구성에서는 관리 포트에 접속할 수 있는 사람이면 누구든 같은 관리자 계정 하나를 공유하거나, 장비마다 로컬 계정을 따로 만들어 두는 방식이 흔했다.

이 방식은 두 가지가 무너진다. 첫째, 누가 어떤 변경을 했는지 계정이 공유되면 구분할 수 없어 책임 소재가 사라진다. 둘째, 로컬 계정은 장비마다 따로 관리해야 하므로 사람이 퇴사하거나 권한이 바뀔 때 수십 대의 서버에서 하나씩 지우고 고쳐야 하고, 그중 하나라도 빠지면 권한이 그대로 남는다.

#2핵심 질문

여러 컴퓨트 장비의 관리 접근을 중앙에서 인증하고, 사용자마다 할 수 있는 일의 범위를 어떻게 나눌 것인가?

#3동작 예시

관리자가 UCS Manager에 로그인하면 장비는 로컬 계정을 먼저 뒤지지 않고 설정된 AAA 서버(RADIUS 또는 TACACS+ 서버)로 사용자 이름과 비밀번호를 보내 검증을 요청한다. 서버가 인증을 승인하면, 이번에는 그 사용자에게 매핑된 역할(예: 서버 구성만 가능한 역할, 전체 관리자 역할)에 따라 메뉴와 명령이 열린다. 신입 관리자 계정으로 로그인하면 서버 프로파일 조회는 되지만 삭제 버튼은 보이지 않는 식이다.

#4동작 과정

  1. 인증(Authentication) 처리관리자가 로그인하면 장비가 자격 증명을 중앙 AAA 서버로 넘겨 사용자가 맞는지 확인한다. 그래서 계정을 장비마다 만들 필요 없이 한 곳에서 관리하고, 퇴사자의 계정도 중앙에서 한 번만 비활성화하면 된다.
  2. 권한 부여(Authorization)인증이 끝나면 사용자에게 부여된 역할(RBAC의 역할)에 따라 허용되는 작업 목록이 정해진다. 역할 기반 접근 제어(RBAC, 역할별로 권한을 묶어 나누는 방식) 덕분에 사람마다 권한을 하나씩 지정하지 않고 역할 단위로 관리한다.
  3. 감사·계정 기록(Accounting)누가 언제 어떤 명령을 실행했는지가 AAA 서버나 장비 로그에 남는다. 변경 이력을 사용자 단위로 추적할 수 있어 문제가 생겼을 때 원인과 책임을 확인할 수 있다.

#5한 줄 요약

컴퓨트 관리 접근을 중앙에서 인증하고 역할 단위로 권한을 나눠, 누가 무엇을 할 수 있는지 통제하고 기록하는 것

스토리지 보안 — AAA·RBAC

MDS/스토리지 패브릭에서 AAA와 역할 기반 접근 제어로 관리 접근과 명령 권한을 제한하는 방법이다.

→ 05-02 참조

#1문제 상황

MDS 스위치로 구성한 스토리지 패브릭(SAN)은 서버와 스토리지 배열을 잇는 핵심 경로라, 설정을 잘못 건드리면 여러 서버의 디스크 접근이 한꺼번에 끊긴다. 예전에는 각 스위치에 로컬 관리자 계정을 만들어 두고, 접속한 사람이면 zone 설정이나 포트 설정 같은 위험한 명령까지 모두 실행할 수 있었다.

이 구조에서는 스위치 대수만큼 계정을 따로 관리해야 하고, 권한 구분 없이 한 계정으로 모든 명령이 가능해 실수 한 번이 패브릭 전체 장애로 이어질 수 있다. 또한 누가 어떤 명령을 실행했는지 계정이 공유되면 구분할 수 없어, 장애 원인을 추적하기 어렵다.

#2핵심 질문

스토리지 패브릭 관리 접근을 중앙에서 인증하고, 관리자마다 실행할 수 있는 명령 범위를 어떻게 제한할 것인가?

#3동작 예시

관리자가 MDS 스위치에 로그인하면 스위치는 자격 증명을 설정된 AAA 서버(RADIUS 또는 TACACS+)로 보내 검증한다. 승인되면 그 사용자에게 매핑된 역할에 따라 사용할 수 있는 명령이 달라진다. 예를 들어 모니터링만 담당하는 사용자는 zone 상태를 조회할 수 있지만 zone을 새로 만들거나 지우는 명령은 거부되고, 이 거부 기록이 남는다.

#4동작 과정

  1. 인증(Authentication)로그인 시 스위치가 자격 증명을 중앙 AAA 서버로 전달해 사용자를 검증한다. 계정을 스위치마다 따로 만들지 않아도 되어, 사람이 바뀌어도 한 곳에서 권한을 회수할 수 있다.
  2. 권한 부여(Authorization)사용자에게 부여된 역할에 따라 허용 명령과 차단 명령이 나뉜다. 역할 기반 접근 제어(RBAC, 역할별로 권한을 묶어 관리하는 방식)로 조회 담당과 구성 담당을 분리해, 실수로 인한 패브릭 변경을 막는다.
  3. 기록(Accounting)실행한 명령과 결과가 AAA 서버에 남아 사용자별 감사가 가능해진다. 패브릭 장애가 발생했을 때 누가 어떤 명령을 언제 실행했는지 확인할 수 있다.

#5한 줄 요약

스토리지 패브릭 관리 접근을 중앙에서 인증하고 역할별로 명령 권한을 나눠 위험한 변경을 통제하는 것

스토리지 포트 보안

스토리지 스위치 포트에 허용 WWN/NPWWN을 바인딩해 지정된 장치만 접속하도록 제한하는 포트 보안 기능이다.

#1문제 상황

SAN 패브릭의 스위치 포트는 설정만 맞으면 어떤 장치든 접속해 로그인할 수 있다. 기본 상태에서는 포트에 케이블을 꽂고 올바른 설정을 갖춘 장치면 패브릭에 참여해 zone 정보를 주고받으며 통신할 수 있다.

문제는 이 기본 동작이 비인가 장치의 접속도 그대로 허용한다는 점이다. 케이블을 잘못 꽂거나, 누군가 임의의 HBA(서버에 꽂는 스토리지용 어댑터)를 같은 포트에 연결하면 그 장치가 패브릭 일부로 인식되어 원치 않는 트래픽이나 접근이 생길 수 있다. 포트 단위로 "이 포트에는 이 장치만"이라는 제한이 없으면 그런 접속을 막을 방법이 없다.

#2핵심 질문

스위치 포트에 접속할 수 있는 장치를 지정된 하나로 못 박아, 비인가 장치가 패브릭에 들어오는 것을 어떻게 막을 것인가?

#3동작 예시

관리자가 특정 포트에 허용할 장치의 WWN(장치마다 부여되는 고유 주소)을 등록하고 포트 보안을 켜 둔다. 이후 다른 WWN을 가진 장치가 그 포트에 연결되면 스위치는 접속을 거부하고 포트를 격리한다. 등록된 WWN 장치만 패브릭에 참여해 zone 통신을 이어갈 수 있다.

#4동작 과정

  1. WWN 등록포트마다 허용할 장치의 WWN(장치 고유 주소)과 NPWWN(포트에 부여된 고유 주소)을 설정에 묶어 둔다. 이렇게 하면 그 포트의 정상 접속 대상이 하나로 정해진다.
  2. 접속 검사장치가 포트에 연결되면 스위치가 장치의 WWN을 등록값과 대조한다. 값이 다르면 로그인을 허용하지 않아 비인가 장치가 패브릭에 참여하지 못한다.
  3. 위반 처리등록과 다른 장치가 감지되면 해당 포트는 트래픽을 막는 상태로 남고 위반 기록이 남는다. 그래서 허용된 장치 외에는 패브릭 자원에 접근할 수 없다.

#5한 줄 요약

스토리지 스위치 포트에 허용 WWN을 묶어, 등록된 장치만 패브릭에 접속하도록 제한하는 것

패브릭 바인딩

스토리지 패브릭에서 스위치 WWN과 도메인 ID를 정적으로 바인딩해 비인가 스위치의 패브릭 참여를 차단하는 기능이다.

#1문제 상황

SAN 패브릭은 여러 스위치가 서로 연결(ISL)되어 하나의 논리적 네트워크처럼 동작한다. 스위치가 패브릭에 참여하려면 도메인 ID라는 고유 번호를 받아야 하고, 기본 동작에서는 스위치가 켜지거나 링크가 올라오면 자동으로 도메인 ID를 협상해 참여한다.

이 자동 참여 방식은 편리하지만, 스위치 WWN과 도메인 ID를 서로 확인하지 않는다. 그래서 비인가 스위치가 케이블로 연결되면 자동 협상으로 패브릭에 합류할 수 있고, 도메인 ID 충돌이나 설정 불일치가 생기면 기존 패브릭 전체가 흔들린다. 누가 어떤 스위치를 붙여도 막지 못하는 구조인 것이다.

#2핵심 질문

패브릭에 참여할 수 있는 스위치를 미리 정해 두고, 비인가 스위치의 참여를 어떻게 차단할 것인가?

#3동작 예시

관리자가 패브릭 바인딩을 켜고, 참여를 허용할 각 스위치의 WWN과 그 스위치가 사용할 도메인 ID를 정적으로 등록해 둔다. 이후 목록에 없는 스위치가 ISL로 연결되면 스위치는 도메인 ID를 받지 못해 패브릭에 합류하지 못한다. 등록된 스위치만 정해진 도메인 ID로 참여한다.

#4동작 과정

  1. 바인딩 목록 설정허용할 스위치의 WWN(스위치 고유 주소)과 도메인 ID(패브릭 내 스위치 식별 번호)를 관리자가 직접 등록한다. 자동 협상 대신 정해진 값만 유효해진다.
  2. 참여 검사스위치가 도메인 ID를 요청하면 패브릭이 그 WWN과 ID가 등록값과 일치하는지 대조한다. 일치하지 않으면 ID를 주지 않아 비인가 스위치가 패브릭 구성원이 되지 못한다.
  3. 참여 확정등록된 스위치만 도메인 ID를 받아 패브릭에 합류하고 다른 스위치와 ISL 통신을 맺는다. 그래서 승인된 스위치 외에는 패브릭에 들어올 수 없다.

#5한 줄 요약

스위치 WWN과 도메인 ID를 정적으로 묶어, 등록된 스위치만 스토리지 패브릭에 참여하도록 통제하는 것
