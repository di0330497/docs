1보안 개념 (Security Concepts, 25%)01-01

온프레미스 환경의 일반적인 위협

자체 데이터센터·사내 네트워크에서 발생하는 멀웨어, 랜섬웨어, 무단 접근, 내부자 위협 등 주요 위협의 경향과 대응 개념.

#1문제 상황

온프레미스 환경에서는 운영자가 서버, 네트워크, 보안 장비를 전부 직접 관리한다. 과거에는 방화벽과 백신 프로그램만 설치하면 사내 네트워크가 안전하다고 여겼다. 그런데 공격 기법이 정교해지면서 멀웨어(악성 소프트웨어), 랜섬웨어(데이터를 암호화하고 몸값을 요구하는 악성코드), 무단 접근, 내부자 위협 같은 공격이 방화벽을 우회하거나 네트워크 내부에서 발생한다. 경계 장비 하나만 믿는 방식으로는 이 위협들을 막을 수 없다.

#2핵심 질문

자체 데이터센터와 사내 네트워크를 지키기 위해 어떤 위협이 존재하고, 어떻게 대응해야 할까?

#3동작 예시

직원이 낚시 이메일(피싱)의 첨부 파일을 열면 악성코드가 다운로드되어 사내 PC가 감염된다. 감염된 PC는 내부망을 통해 다른 서버로 옮겨 퍼지고, 관리자 계정의 자격 증명이 탈취된 뒤 데이터가 암호화되는 랜섬웨어 사고로 이어진다. 이 흐름은 백신 프로그램과 엔드포인트 탐지·대응(EDR)이 이상 행위를 감지해 차단하는 것으로 중단된다.

#4동작 과정

  1. 침투이메일 첨부나 취약한 웹 페이지를 통해 악성코드가 사내 PC에 유입된다.
  2. 확산과 권한 상승감염된 PC가 내부망을 통해 다른 시스템으로 전파되고, 관리자 계정 탈취 등으로 권한을 넓힌다.
  3. 탐지·대응백신과 EDR이 비정상 행위를 발견해 차단하고, 감염 범위를 격리해 피해를 최소화한다.

#5한 줄 요약

온프레미스 환경의 침투·확산·탐지 흐름을 이해하고 멀웨어, 랜섬웨어, 무단 접근, 내부자 위협에 대응하는 보안 개념을 갖추는 것

#3동작 예시

#4동작 과정

IPsec 구성과 NAT-T

IPsec(ESP·AH, 보안 연관성 SA, IKE)의 동작 방식과 NAT 환경에서 ESP 패킷을 통과시키는 NAT-T(NAT Traversal) 구성 개념.

#1문제 상황

인터넷 같은 공용망으로 데이터를 보내면 패킷이 여러 라우터를 거치면서 제3자가 내용을 보거나 중간에서 조작할 수 있다. 기존에는 개별 통신만 암호화하거나 전용 회선을 빌리는 방식이 있었지만, 적용 범위가 제한적이거나 비용이 크다는 한계가 있다. IPsec은 IP 패킷 자체를 암호화·인증해 공용망 위에 안전한 연결을 만들지만, 사내 네트워크에 있는 NAT(사설 주소를 공인 주소로 바꿔주는 장치)가 IPsec의 ESP 패킷을 그대로 통과시키지 못하는 문제가 추가로 발생한다.

#2핵심 질문

NAT 환경에서도 IPsec 터널이 정상 동작하도록 하려면 어떻게 구성해야 할까?

#3동작 예시

본사와 지사를 IPsec으로 연결한다고 하자. 지사에 NAT 장비가 있다면, 양쪽 보안 게이트웨이가 IKE(키 교환 프로토콜)로 암호화 방식과 키 값을 협상해 보안 연관성(SA, 통신 규칙 합의)을 만든다. 이후 실제 데이터를 ESP로 암호화하고, NAT-T(NAT Traversal)가 ESP 패킷을 UDP에 감싸 보내면 NAT 장비가 주소를 바꿔도 패킷이 유실되지 않고 목적지에 도착한다.

#4동작 과정

  1. SA 수립IKE로 암호화 방식과 키 값을 협상해 보안 연관성(SA)을 만든다.
  2. ESP 캡슐화와 NAT-T실제 데이터를 ESP로 암호화하고, NAT-T가 이 패킷을 UDP에 감싼다.
  3. 통과·복원NAT 장비가 UDP 패킷을 통과시키고, 수신 측이 원래 ESP 패킷을 복원해 복호화한다.

NetFlow 는 장비가 흐름(flow) 단위로 수집한 트래픽 통계(IP·포트·프로토콜 등)를 수집기로 내보내는 기능이고, Flexible NetFlow 는 관찰할 필드와 캐시를 사용자가 정의할 수 있는 확장 버전이다.

#2핵심 질문

#4동작 과정

#1문제 상황

#4동작 과정

  1. 인증(Authentication)장비나 네트워크에 접속하려는 사람이 누구인지 TACACS+ 또는 RADIUS 서버가 사용자 이름과 비밀번호로 확인한다.

  3. 계정 관리(Accounting)로그인 시각, 실행한 명령, 사용한 서비스와 트래픽 양을 서버에 계속 기록해 감사와 과금 근거를 남긴다.

안전한 네트워크 관리

SNMPv3 의 USM 인증·암호화, NETCONF·RESTCONF 같은 보안 관리 API, 인증이 적용된 NTP, 안전한 syslog 전송으로 장비를 안전하게 원격 관리하는 방법이다.

#1문제 상황

초기 SNMP 버전은 커뮤니티 문자열이라는 평문 비밀번호만으로 장비 조회를 허용해서, 패킷을 엿보는 공격자가 문자열을 가로채 장비 정보를 읽거나 설정을 바꿀 수 있었다. 텔넷이나 평문 SNMP로는 관리 명령·설정 전송 내용이 그대로 노출되고, 시각 동기화에 쓰는 NTP는 인증 없이 시간을 속여 인증서 유효성 판단을 흐트러뜨릴 수 있다. 결국 관리 채널 자체가 공격 대상이 되는 상황이다.

#2핵심 질문

원격에서 장비를 관리할 때, 관리 트래픽의 도청과 위조를 막으려면 어떻게 해야 할까?

#3동작 예시

관리자가 SNMPv3으로 장비 상태를 조회할 때, USM(User-based Security Model)이 사용자별 키로 패킷 전체를 암호화하고 무결성 검증 값을 붙여 보낸다. 장비는 키가 맞고 값이 변조되지 않았을 때만 응답한다. 같은 원리로, 관리자는 NETCONF나 RESTCONF를 HTTPS 위에서 사용해 설정을 읽고 쓰며, NTP는 인증 키를 교환한 뒤에만 시각 정보를 받아들이고, syslog는 암호화된 전송으로 로그를 안전하게 중앙 서버에 보낸다.

#4동작 과정

  1. 관리 프로토콜 보안 설정SNMPv3의 USM으로 사용자별 인증·암호화 키를 장비와 관리 시스템에 등록하고, NETCONF·RESTCONF는 HTTPS 전송을 켠다.
  2. 보조 서비스 보안 설정NTP에 인증 키를 적용해 신뢰할 수 있는 서버의 시각만 받고, syslog 전송을 암호화 채널(예: TLS)로 바꾼다.
  3. 운용 및 검증관리자는 암호화된 채널로만 장비에 접속하고, 로그와 시각 정보가 정상 수집되는지 주기적으로 확인한다.

#3동작 예시

#1문제 상황

기존 방식은 기업이 서버, 네트워크, 애플리케이션, 데이터까지 자체 데이터센터에서 직접 사서 관리했다. 이 방식은 초기 투자 비용이 크고, 사용량이 늘거나 줄 때 장비를 새로 사거나 내려야 해서 대응이 느리다. 클라우드는 이런 인프라를 인터넷으로 제공하지만, 무엇까지 공급자가 맡고 무엇을 고객이 관리해야 하는지가 서비스마다 달라 기준이 없었다.

#3동작 예시

#4동작 과정

  1. 서비스 계층 구분IaaS는 인프라(서버·저장소·네트워크), PaaS는 플랫폼(실행 환경·미들웨어), SaaS는 완성된 소프트웨어를 제공한다. 고객이 관리하는 범위는 IaaS가 가장 넓고 SaaS가 가장 좁다.

  3. 모델 매핑과 책임 확인서비스를 세 모델 중 하나에 대입하고, 그 모델에서 공급자가 관리하는 계층과 고객이 관리하는 계층을 구분한다.

DevSecOps

개발(Dev)·보안(Sec)·운영(Ops)을 통합해 소프트웨어 개발 파이프라인의 처음부터 보안을 내장하는 방식이다.

#1문제 상황

전통적인 개발 방식에서는 개발팀이 기능을 만들고, 운영팀이 배포하고, 보안팀이 마지막에 검토했다. 보안 점검이 배포 직전에 한 번만 일어나 문제가 발견되면 배포가 늦어지고, 늦은 발견 때문에 수정 비용도 커진다. 개발과 운영만 통합한 DevOps 환경에서도 보안이 마지막 단계에 남아 빠른 배포 속도를 따라가지 못하는 병목이 된다.

#2핵심 질문

빠르게 반복되는 개발·배포 흐름에서 보안을 마지막이 아니라 처음부터 함께 넣으려면 어떻게 해야 할까요?

#3동작 예시

개발자가 코드를 저장소에 올리면 그 순간 정적 분석(코드를 실행하지 않고 소스만 읽어 취약점을 찾는 검사)이 자동으로 실행된다. 문제가 발견되면 개발자에게 바로 알림이 돌아가고, 문제가 없을 때만 빌드가 다음 단계로 진행된다. 보안 검사가 사람 대신 파이프라인 속에 들어가 매번 자동으로 도는 것이 DevSecOps의 동작 방식이다.

#4동작 과정

  1. 시프트 레프트보안 검사를 개발 초기 단계로 옮겨 코드가 저장소에 올라올 때마다 자동으로 실행한다.
  2. 파이프라인 자동화빌드·테스트·배포 단계마다 보안 도구를 연결하고, 검사에 실패하면 배포를 멈추는 게이트(통과 조건)로 만든다.
  3. 운영 피드백배포 후에도 런타임 보안 모니터링과 사고 기록을 개발팀에 전달해 다음 사이클의 검사 항목에 반영한다.

이메일은 조직에 들어오는 가장 흔한 공격 경로인데, 기존 안티바이러스만으로는 새로 나오는 악성코드와 정교한 스팸·피싱을 놓치기 쉽다. 게다가 한 번도 본 적 없는 첨부 파일과 내부 정보가 외부로 유출되는 것까지 기존 방식으로는 막을 수 없다.

#2핵심 질문

스팸·악성코드·정보 유출 등 이메일 기반 위협을 한 곳에서 어떻게 모두 차단할 수 있을까?

#3동작 예시

외부에서 첨부 파일이 든 메일이 ESA(이메일 보안 어플라이언스)에 도착하면, ESA가 스팸 점수 확인과 바이러스 검사를 한 뒤 수상한 첨부를 샌드박스(격리 환경)에서 실제로 실행해 보고, 문제가 없을 때만 사서함으로 전달한다.

#4동작 과정

  1. 수신 검사ESA가 SMTP(메일 전송 프로토콜) 단계에서 발신자 평판·스팸 점수·안티바이러스 시그니처로 메일을 검사해 위험 메일을 먼저 걸러낸다.
  2. 심층 분석수상한 첨부는 샌드박스에서 실행시켜 악성 행위가 있는지 확인하고, DLP(데이터 유출 방지)로 본문·첨부의 개인정보·기밀 패턴을 검출한다.
  3. 처리와 전달통과한 메일을 사서함으로 보내고 필요하면 암호화를 적용하며, 모든 판정을 기록으로 남긴다.

#4동작 과정

  3. 기록과 보고모든 접속 시도를 로그로 남겨 관리자가 조직 전체의 위협 현황을 보고로 확인한다.

Umbrella 구성요소와 이점

가상 어플라이언스, 로밍 클라이언트, DNS·프록시 계층 등 Umbrella 의 구성요소와 빠른 구축·통합 가시성 같은 운영 이점

#1문제 상황

DNS 기반 차단만 하던 기존 웹 보안은 회사 네트워크 안에서만 동작해서, 사무실 밖에 있는 사용자의 인터넷 사용은 통제하지 못했다. 지사를 보호하려면 지사마다 별도 보안 장비를 두고 일일이 관리해야 했고, 운영 비용과 복잡도가 커졌다. 또한 DNS 조회 시점에만 검사하면 악성 사이트에 직접 접속하는 트래픽(HTTPS 요청 등)은 통제에서 빠져나갈 수 있었다.

#2핵심 질문

모든 장소와 모든 기기에서 사용자의 인터넷 접속을 한곳에서 통제하려면 어떻게 해야 할까?

#3동작 예시

사용자가 어떤 컴퓨터에서든 악성 도메인을 입력해 접속을 시도하면, 그 DNS 조회 요청이 Umbrella의 글로벌 DNS 서버로 전달된다. Umbrella는 해당 도메인이 악성으로 등록된 도메인인지 판단해 차단 응답을 돌려주기 때문에, 실제 웹 서버에 연결되기 전에 접속이 멈춘다.

#4동작 과정

  1. DNS 계층 차단사용자 기기의 DNS 조회(도메인을 IP 주소로 바꾸는 요청)를 Umbrella 리졸버가 받아 악성 도메인 여부를 확인하고 차단한다.
  2. 프록시 계층 검사허용된 요청이라도 Umbrella 가상 어플라이언스 또는 통합 프록시를 경유시켜 URL·파일 다운로드 단계까지 심층 검사한다.
  3. 로밍 클라이언트 적용회사가 아닌 장소에서도 로밍 클라이언트가 기기 설정에 DNS 주소를 적용해 동일한 정책을 그대로 시행한다.

DNS와 프록시 계층을 클라우드에 두고 어디서나 같은 정책으로 인터넷 접속을 차단·검사하는 것

Umbrella 웹 보안 통제 설정

Umbrella 에서 대상·정책·차단 설정을 구성해 부서별 웹 접근 통제와 위협 차단을 시행하는 방법

#1문제 상황

회사마다 부서별로 허용할 웹 사이트 범위가 다르지만, 기존 방식은 모든 사용자에게 동일한 차단 목록 한 벌을 적용해 부서별 정책을 세밀하게 못 만들었다. 정책을 바꾸려면 장비 설정 파일을 수정해 다시 배포하는 번거로운 절차가 필요했다. 관리자가 부서별 접근 기준을 명확히 설정할 수 없다 보니, 불필요한 사이트는 막지 못하면서 필요한 사이트가 차단되는 경우도 생겼다.

#2핵심 질문

부서별로 서로 다른 웹 접근 기준을 한곳에서 정하고 즉시 시행하려면 어떻게 해야 할까?

#3동작 예시

인사 부서는 업무용 채용 사이트를 허용하고 SNS를 차단하며, 개발 부서는 기술 문서 사이트를 전부 허용하고 게임 사이트를 차단하도록 두 개의 정책을 만든다. 두 정책을 각 부서의 사용자 그룹에 연결하면, 사용자가 접속을 시도하는 순간 자신의 그룹에 맞는 정책이 적용된다.

#4동작 과정

  1. 대상과 정책 정의관리자가 차단할 카테고리(성인, SNS, 게임 등)와 허용할 도메인 목록을 정책으로 구성한다.
  2. 그룹에 정책 연결사용자를 부서 단위 그룹으로 묶고, 그룹마다 적용할 정책을 지정해 매핑한다.
  3. 조회 시점 적용사용자의 DNS 조회가 Umbrella에 도달하면 소속 그룹의 정책에 따라 차단 또는 허용 응답이 즉시 반환된다.

#5한 줄 요약

EPP 와 EDR 비교

공격을 사전에 차단하는 EPP(엔드포인트 보호 플랫폼)와 침해 후 탐지·조사·대응하는 EDR(엔드포인트 탐지·대응)의 역할 차이와 상호 보완 관계를 이해하는 기준.

#1문제 상황

기존 안티바이러스 같은 엔드포인트 보호 제품은 이미 알려진 악성코드가 실행되는 순간 차단하는 데 집중했다. 그러나 새로 만든 공격이나 정상 프로그램을 악용하는 공격은 시그니처로 잡아내지 못해, 막지 못하고 침투를 허용하는 경우가 많았다. 막지 못한 공격의 흔적을 확인하고 원인을 조사하는 기능이 없어서, 침해가 발생한 뒤에는 무엇이 어떻게 진행됐는지 알 수 없었다.

#2핵심 질문

막지 못한 공격까지 탐지하고 조사하려면, 사전 차단과 사후 대응을 어떻게 나누어 설계해야 할까?

#3동작 예시

EPP는 정상적인 설치 프로그램에 위장한 악성 실행 파일을 실행 시점에 차단하고, 만약 EPP가 통과시킨 변종 공격이 실행되면 EDR이 그 프로세스의 행위를 기록하고 경고를 띄워 조사할 수 있게 한다. 같은 엔드포인트에서 두 제품이 각각 진입 차단과 사후 추적을 담당한다.

#4동작 과정

  1. EPP의 사전 차단파일 실행 시 시그니처(악성코드 고유 패턴)와 행위 분석으로 의심 파일을 찾아 실행을 막는다.
  2. EDR의 지속 기록차단을 통과한 프로세스의 실행·파일 접근·네트워크 연결 행위를 연속으로 수집한다.
  3. 탐지와 대응수집된 행위에서 이상 징후가 발견되면 경고를 만들고, 관리자가 기록을 추적해 원인을 조사하고 격리한다.

#5한 줄 요약

EPP가 공격의 진입을 막고 EDR이 진입을 통과한 공격을 기록·탐지·조사해 서로 보완하는 것

엔드포인트 안티멜웨어 보호

시그니처·행위 분석 등으로 악성코드를 탐지해 차단·치료하는 엔드포인트 안티멜웨어 보호 통제(SI-3).

#1문제 상황

초기 안티바이러스는 알려진 악성코드의 고유 패턴만 대조해 잡아냈기 때문에, 변종이 조금만 바뀌어도 탐지를 피해갔다. 새 악성코드가 만들어지는 속도는 시그니처가 갱신되는 속도를 앞서는 경우가 많아서, 탐지 공백이 계속 벌어졌다. 한 번 악성코드가 실행되면 파일 삭제·암호화 같은 피해가 이미 시작되므로, 실행 후 사후 치료보다 실행 전 탐지가 더 중요했다.

#2핵심 질문

새로운 악성코드까지 실행 전에 찾아내 차단하려면 시그니처 외에 무엇을 더 봐야 할까?

#3동작 예시

사용자가 이메일 첨부 파일을 열려고 하면, 안티멜웨어가 그 파일의 시그니처를 대조하고 동시에 가상 환경에서 실행해 행위를 관찰한다. 파일이 시스템 설정을 무단 변경하거나 다른 프로그램을 내려받는 행위를 보이면 악성으로 판정해 실행을 막고 치료한다.

#4동작 과정

  1. 파일 검사와 시그니처 대조실행 대상 파일을 알려진 악성코드 패턴 데이터베이스와 대조해 일치 여부를 확인한다.
  2. 행위 분석과 샌드박스 실행의심 파일을 격리된 가상 환경에서 실행해 파일 변조·네트워크 통신 등 악성 행위가 나타나는지 관찰한다.
  3. 차단과 치료악성으로 판정되면 실행을 중단하고 감염 파일을 격리·삭제하거나 원래 상태로 복구한다.

#5한 줄 요약

시그니처 대조에 행위 분석을 더해 알려지지 않은 악성코드까지 실행 전에 탐지해 차단·치료하는 것

발생 확산 통제와 격리

침해 발생 시 감염된 엔드포인트를 네트워크에서 격리·차단하여 피해 확산을 통제하는 대응(Respond) 활동.

#1문제 상황

침해가 발생했을 때 기존 대응은 감염된 기기를 확인한 뒤 수작업으로 연결을 끊는 데 그쳐, 확인 사이에 다른 기기로 공격이 퍼져나가는 시간이 생겼다. 감염 기기가 네트워크에 남아 있으면 같은 네트워크의 다른 기기와 데이터를 계속 주고받아 피해 범위가 넓어졌다. 확산을 빠르게 막는 절차가 없다 보니, 사고 대응팀이 원인을 조사하는 동안에도 공격자는 내부에서 계속 움직일 수 있었다.

#2핵심 질문

침해가 확인된 엔드포인트가 다른 기기로 공격을 퍼뜨리지 못하게 하려면 어떻게 해야 할까?

#3동작 예시

#4동작 과정

  1. 감염 기기 식별EDR 경고나 안티멜웨어 탐지로 감염된 엔드포인트를 확정한다.
  2. 네트워크 격리감염 기기의 다른 기기와의 통신을 차단하고 보안 관리 채널만 남겨 둔다.
  3. 조사와 복구 후 해제원인을 분석하고 악성코드를 제거한 뒤 검증이 끝나면 격리를 해제해 정상 업무에 복귀시킨다.

엔드포인트 보안의 정당성

엔드포인트가 공격자의 주요 진입점이라는 위험 근거를 바탕으로 엔드포인트 보안의 배치와 투자를 정당화하는 논리.

#1문제 상황

많은 조직이 방화벽과 같은 네트워크 경계 보안에 투자를 집중하면서, 개별 컴퓨터와 노트북 같은 엔드포인트 보안은 상대적으로 소홀히 뒀다. 그런데 공격자는 방화벽을 뚫기보다 이메일 첨부 파일, 악성 웹 사이트 접속 같은 방법으로 사용자 기기를 먼저 장악하는 경우가 훨씬 많다. 사용자 기기가 장악되면 그 기기를 발판으로 내부 시스템에 접근할 수 있으므로, 엔드포인트를 보호하지 않으면 네트워크 경계를 아무리 단단히 해도 소용없게 된다.

#2핵심 질문

공격자의 주요 진입점이 엔드포인트라면, 보안 투자를 엔드포인트에 배치해야 하는 근거는 무엇일까?

#3동작 예시

공격자가 이메일 피싱으로 한 직원의 노트북에 악성코드를 설치하면, 그 노트북은 내부 업무망에 정식으로 접속할 수 있는 장비이므로 방화벽이 정상 트래픽으로 통과시킨다. 반면 그 노트북에 엔드포인트 보안이 설치되어 있으면 악성코드 실행 자체를 차단해 내부 진입이 처음부터 막힌다.

#4동작 과정

  1. 진입 경로 확인공격자의 초기 침투가 대부분 이메일·웹을 통한 엔드포인트 감염으로 시작됨을 사고 데이터로 확인한다.
  2. 위험 대비 투자 판단엔드포인트 침해 시 내부 시스템 전체로 확산될 수 있는 피해 규모와 보호 비용을 비교한다.
  3. 방어 계층 포함네트워크 경계 보안과 함께 엔드포인트 차단·탐지 기능을 필수 방어 계층으로 배치한다.

엔드포인트 기기 관리와 자산 목록

조직의 모든 엔드포인트 기기를 식별·등록·추적하여 관리하는 자산 인벤토리 통제(CM-8).

#1문제 상황

조직에 어떤 기기가 실제로 존재하는지 파악하지 못한 채 보안 장비와 정책을 운영하면, 관리 목록에 없는 기기는 아무 보호도 받지 못한다. 직원이 개인 노트북을 업무에 쓰거나 새 기기를 구매해 연결하는 일이 반복되면서, 보호되지 않는 기기가 늘어났다. 목록이 없으면 취약한 기기, 오래된 운영체제, 정책을 위반한 소프트웨어가 있는 기기도 찾아낼 수 없어, 사고가 났을 때 어느 기기가 관련됐는지 파악하는 데도 오래 걸렸다.

#2핵심 질문

보호하지 못하는 기기가 없도록 하려면, 조직의 모든 엔드포인트를 어떻게 식별하고 추적해야 할까?

#3동작 예시

회사 네트워크에 새 노트북이 연결되면, 자산 관리 시스템이 그 기기의 운영체제와 소유자 정보를 자동으로 등록한다. 등록된 기기는 보안 정책 적용 대상이 되어 업데이트 상태가 점검되고, 관리 목록에 없는 기기가 발견되면 접속이 제한된다.

#4동작 과정

  1. 기기 식별과 등록네트워크에 연결된 엔드포인트를 자동으로 발견해 고유 식별자, 운영체제, 소유자를 자산 목록에 기록한다.
  2. 정책 점검과 추적등록 기기의 보안 패치·소프트웨어 상태를 주기적으로 점검하고 변경 사항을 목록에 반영한다.
  3. 미등록 기기 통제목록에 없는 기기가 접속을 시도하면 보안 정책 적용을 거부하거나 접속을 제한한다.

다중 요소 인증 전략

비밀번호에 추가 인증 요소(토큰·생체 등)를 결합하여 계정 탈취 피해를 줄이는 RADIUS 기반 인증 강화 전략.

#1문제 상황

기존 인증 방식은 비밀번호 하나만 확인하고 로그인을 허용한다. 그런데 비밀번호는 피싱, 유출, 재사용으로 쉽게 탈취되고, RADIUS 서버가 비밀번호만 대조하는 구조라 도용된 비밀번호와 진짜 사용자의 비밀번호를 구분할 방법이 없다. 비밀번호가 탈취되면 공격자는 그대로 계정에 로그인해 내부 자원에 접근할 수 있었다.

#2핵심 질문

비밀번호가 탈취되어도 공격자는 로그인하지 못하게 하려면 어떻게 해야 할까?

#3동작 예시

사용자가 로그인을 시도하면 RADIUS 서버가 먼저 비밀번호를 확인하고, 통과하면 사용자만 가진 장치에서 생성되는 일회용 토큰 입력을 추가로 요구한다. 토큰은 매번 새로 생성되고 사용자 외에는 알 수 없으므로 비밀번호만 훔친 공격자는 두 번째 요소를 통과하지 못한다.

#4동작 과정

  1. 인증 요청사용자가 비밀번호와 함께 RADIUS 인증 요청을 보내면 서버가 1차 요소를 확인한다.
  2. 추가 요소 확인서버가 토큰이나 생체 정보 같은 두 번째 요소를 요구하고 응답을 검증한다.
  3. 접근 허용모든 요소가 일치할 때만 접근 허용 응답을 보내고, 어느 하나라도 틀리면 거부한다.

  3. 적용과 검증정기 패치로 결함을 보정하고 적용 여부를 재확인해 구멍이 남지 않게 한다.

6안전한 네트워크 접근·가시성·시행 (Secure Network Access, Visibility, and Enforcement, 15%)06-01

아이덴티티 관리와 안전한 네트워크 접근

사용자·기기의 신원을 인증·인가·과금(AAA)으로 확인하고, 그 신원에 따라 네트워크 접근을 허용하는 체계

#1문제 상황

기존 방식은 네트워크에 붙은 장치 자체를 신뢰하고 내부 자원을 열어줬다. 누가 어떤 장치로 접속하는지 확인하지 않으므로 탈취한 자격 증명이나 승인되지 않은 장치로 접근하는 것을 막을 수 없다. 신원 확인 없이 열린 네트워크에서는 권한 밖의 자원에 닿는 일이 잦다.

#2핵심 질문

네트워크에 접근하기 전에 누가 어떤 기기로 접속하는지 확인할 수 있을까?

#3동작 예시

사용자가 로그인하면 RADIUS 기반 AAA가 신원 확인(인증), 허용 범위 결정(인가), 접속 기록 저장(과금)을 수행하고, 확인된 신원에 맞는 권한만 네트워크 접근으로 부여한다. 신원이 확인되지 않으면 어떤 서비스도 열리지 않는다.

#4동작 과정

  1. 인증사용자와 기기의 자격 증명을 RADIUS 서버가 확인한다.
  2. 인가확인된 신원에 따라 허용할 서비스와 권한 범위를 정한다.
  3. 과금과 시행접속 기록을 남기고 정해진 권한만 네트워크에서 사용하게 한다.

네트워크 접근 제어 방식

802.1X, MAB, WebAuth 같은 포트 기반 인증 방식으로 장치가 네트워크에 접속하기 전에 신원을 검증하는 방법

#1문제 상황

기존 방식은 네트워크 포트에 연결만 하면 인증 없이 바로 사용할 수 있었다. 물리적으로 연결되는 것만으로 내부망에 들어올 수 있어 무단 장치가 내부 자원에 닿기 쉽고, 누가 접속했는지 기록도 남지 않는다. 포트가 항상 열려 있으면 네트워크 경계가 사실상 무너진 상태다.

#2핵심 질문

장치가 네트워크에 접속하기 전에 그 신원을 어떻게 검증할까?

#3동작 예시

802.1X는 스위치 포트에 연결된 장치가 인증 서버와의 대화를 거쳐 인증에 성공해야만 포트가 데이터 통신을 열어준다. 자격 증명을 갖추지 못한 장치는 MAB로 MAC 주소를, WebAuth로 웹 로그인을 거쳐 신원을 확인받는다.

#4동작 과정

  1. 접속 시도 차단장치가 포트에 연결되면 인증 전까지 포트는 데이터 통신을 막는다.
  2. 신원 검증802.1X, MAB, WebAuth 중 하나로 장치·사용자의 신원을 인증 서버가 확인한다.
  3. 포트 개방인증에 성공한 경우에만 포트를 열어 해당 장치에 네트워크 사용을 허용한다.

→ 06-02 참조

#1문제 상황

기존 방식은 한번 인증된 세션의 권한을 바꾸려면 재인증을 하거나 세션을 끊어야 했다. 세션을 강제로 끊으면 진행 중이던 사용자 작업이 중단되고, 위험 장치가 발견돼도 즉시 대응하기 어렵다. 권한 변경이 느리고 번거로워서 보안 사고에 뒤늦게 반응하게 된다.

#2핵심 질문

연결을 끊지 않고 접속 중인 세션의 권한이나 정책을 즉시 바꿀 수 없을까?

#3동작 예시

NAC가 접속 중인 기기에서 악성 행위를 감지하면 정책 서버가 RADIUS CoA(Change of Authorization) 요청을 스위치로 보내 해당 세션을 격리 구역으로 옮기도록 지시한다. 사용자 로그인은 유지된 채 접근 범위만 즉시 좁아진다.

#4동작 과정

  1. 정책 변경 판단정책 서버가 접속 중인 세션에 새 정책을 적용할 필요를 판단한다.
  2. CoA 요청 전송정책 서버가 RADIUS CoA 요청을 스위치나 무선 컨트롤러로 보낸다.
  3. 세션 갱신스위치가 새 정책을 적용해 세션을 끊지 않고 접근 범위를 즉시 바꾼다.

기기 준법과 애플리케이션 제어의 이점

기기의 보안 준법 상태(포스처)를 점검해 부적합 기기를 격리하고, 애플리케이션 사용을 통제해 위험을 줄이는 이점

#1문제 상황

기존 방식은 네트워크 안으로 들어온 뒤의 위협만 처리했다. 준법하지 않은 기기가 내부에 들어오면 단 하나의 취약 기기가 전체 네트워크를 위험에 노출시키고, 함부로 설치된 애플리케이션은 추가 침투 경로가 된다. 진입 전 통제가 없으면 내부의 위험을 하나씩 찾아내는 일이 계속 벌어진다.

#2핵심 질문

들어오는 기기의 준법 상태와 사용하는 애플리케이션을 통제하면 위험을 줄일 수 있지 않을까?

#3동작 예시

부적합 기기는 네트워크 접속 전에 격리되고, 정책에 어긋나는 애플리케이션은 실행·이용이 차단된다. 그 결과 취약한 기기와 허용되지 않은 프로그램이 내부 자원에 닿지 못해 공격 표면이 줄어든다.

#4동작 과정

  1. 준법 점검접속하는 기기의 보안 자세를 확인해 부적합 기기를 격리한다.
  2. 애플리케이션 통제허용 목록과 차단 목록으로 사용 가능한 애플리케이션을 제한한다.
  3. 위험 감소부적합 기기와 허용되지 않은 애플리케이션이 네트워크에 닿지 못해 침투 경로가 줄어든다.

데이터 유출 기법

DNS 터널링, 암호화 채널, 물리적 매체 이동 등 공격자가 내부 데이터를 외부로 빼돌리는 다양한 경로와 기법

#1문제 상황

기존 보안 관리는 외부 공격자가 네트워크 경계를 뚫고 들어오는 침입을 막는 데 집중했다. 방화벽과 침입 탐지 시스템은 내부에서 외부로 나가는 트래픽보다 들어오는 트래픽을 더 정밀하게 검사했다. 그런데 공격자는 침입에 성공한 뒤 목표 데이터를 몰래 빼내는 과정에서, 정상 트래픽처럼 보이게 하거나 보안 장비가 보지 못하는 채널을 이용해 탐지를 회피한다. 내부 데이터가 외부로 나가는 경로를 추적하지 못하면 유출이 한참 뒤에야 발견되거나 아예 발견되지 않는다.

#2핵심 질문

공격자는 보안 장비의 검사를 피하면서 어떻게 내부 데이터를 외부로 빼돌리는가?

#3동작 예시

DNS 터널링이 대표적이다. 공격자는 유출할 데이터를 잘게 쪼개어 DNS 질의 이름(도메인 이름)에 숨겨 넣고, 공격자가 통제하는 DNS 서버에 이 질의를 보낸다. DNS 질의는 모든 네트워크에서 허용되는 정상 트래픽이라 방화벽이 거의 막지 않으며, 그 안의 데이터 조각을 공격자 서버가 모아 원본 데이터를 복원한다.

#4동작 과정

  1. 데이터 가공·은닉공격자가 유출할 데이터를 인코딩하여 DNS 질의 이름이나 암호화 채널의 페이로드처럼 정상 트래픽 형식에 맞춘다.
  2. 외부 전송은닉한 데이터를 정상 트래픽으로 위장해 DNS 질의, HTTPS 연결, 또는 물리적 매체(USB) 등 검사가 약한 경로로 외부에 전송한다.
  3. 수집·복원공격자가 통제하는 외부 서버가 전달된 조각들을 모아 원본 데이터를 완전히 복원한다.

네트워크 텔레메트리의 이점

NetFlow 같은 텔레메트리로 트래픽 흐름을 수집·가시화하여 이상 징후, 성능 문제, 위협을 사전에 파악하는 이점

#1문제 상황

기존에는 패킷 캡처 방식으로 네트워크를 감시했다. 전체 패킷을 저장하면 정보는 정확하지만 저장 공간과 처리 비용이 커서 대규모 네트워크 전체를 오래 감시할 수 없었다. 반대로 로그만 수집하면 트래픽의 흐름 자체는 보이지 않아 이상 징후를 조기에 발견하기 어려웠다. 감시 대상이 넓어질수록 관찰 비용과 관찰 정확도 사이에서 타협을 강요받는 것이 기존 방식의 한계였다.

#2핵심 질문

전체 패킷을 저장하지 않으면서도 네트워크에서 무슨 일이 일어나는지 흐름 단위로 빠짐없이 볼 수는 없을까?

#3동작 예시

NetFlow가 그 답이다. 라우터나 스위치가 지나가는 트래픽을 패킷을 통째로 저장하는 대신 "어느 IP에서 어느 IP로, 어떤 포트로, 언제, 얼마나 많은 패킷과 바이트가 흘렀는지"라는 흐름 요약 레코드만 만들어 수집 서버로 보낸다. 이 요약만으로 전체 트래픽의 흐름 지도가 그려지고, 저장 비용은 패킷 저장의 수십 분의 일 이하로 줄어든다.

#4동작 과정

  1. 흐름 생성네트워크 장비가 동일한 출발지·목적지·포트를 가진 연속 패킷들을 하나의 흐름으로 묶고 시작·종료 시각, 패킷 수, 바이트 수 같은 요약 정보를 만든다.
  2. 레코드 전송장비가 만든 흐름 레코드를 NetFlow 수집기(collector)라는 서버로 주기적으로 전송한다.
  3. 가시화·분석수집 서버가 레코드를 모아 트래픽 흐름을 시각화하고, 비정상적인 대량 전송이나 평소 없던 통신 패턴 같은 이상 징후를 감지한다.

수집된 네트워크 트래픽과 흐름 데이터를 분석·탐지하여 위협과 이상 행위를 식별하는 네트워크 분석 솔루션

#1문제 상황

네트워크 장비 하나하나는 자기 구간의 트래픽만 보고 있어 각 장비의 로그만으로는 전사적인 공격 흐름이 보이지 않는다. 보안 담당자가 여러 장비의 로그를 수동으로 대조해 위협을 찾는 방식은 느리고, 이상 징후를 놓치기 쉽다. 방화벽과 침입 탐지 시스템은 각자 정해진 규칙으로만 판정해서 아직 알려지지 않은 공격이나 여러 장비에 걸쳐 진행되는 공격은 탐지하지 못한다.

#2핵심 질문

여러 네트워크 장비에서 나온 트래픽과 흐름 데이터를 한곳에 모아 위협과 이상 행위를 자동으로 식별할 수는 없을까?

#3동작 예시

네트워크 분석 제품이 스위치, 라우터, 방화벽에서 보낸 NetFlow 흐름 레코드를 한곳에 모아 전체 트래픽의 기준선(baseline)을 만든다. 어느 날 같은 출발지에서 평소보다 100배 많은 데이터가 외부로 나가는 흐름이 감지되면, 제품이 이 흐름을 정상 패턴과 비교해 즉시 데이터 유출 의심으로 표시하고 경고한다.

#4동작 과정

  1. 데이터 수집네트워크 장비의 흐름 레코드, 로그, 패킷 샘플을 분석 제품이 한곳으로 모은다.
  2. 분석·탐지수집한 데이터를 정상 트래픽 기준선과 실시간 패턴 매칭으로 비교해, 평소와 다른 대량 전송이나 알려진 공격 시그니처를 찾아낸다.
  3. 알림·대응탐지된 위협을 우선순위와 함께 보안 담당자에게 알리고, 필요하면 차단 규칙을 네트워크 장비에 적용해 대응한다.

#5한 줄 요약

네트워크 전체의 트래픽과 흐름 데이터를 한곳에 모아 자동으로 분석함으로써 단일 장비로는 보이지 않는 위협과 이상 행위를 식별하는 솔루션

클라우드·조사·인지 제품

클라우드 환경 보안, 보안 사고 조사, 인지/머신러닝 기반 분석을 제공하는 통합 보안 제품군

#1문제 상황

기존 보안은 사내 데이터센터의 장비를 기준으로 설계되어 클라우드에 분산된 워크로드, 즉 애플리케이션이나 데이터는 같은 방식으로 보호할 수 없었다. 또 보안 사고가 나면 각 장비의 로그를 수동으로 뒤져 원인과 피해 범위를 재구성해야 했고, 알려지지 않은 신종 위협은 기존 시그니처로 잡을 수 없었다. 환경이 클라우드로 옮겨가고 공격이 고도화될수록 기존 방식의 사각지대가 커지는 것이 문제였다.

#2핵심 질문

클라우드 환경까지 포함해서, 사고 조사와 신종 위협 대응까지 한곳에서 해결하는 보안 체계를 만들 수는 없을까?

#3동작 예시

클라우드 보안 제품이 클라우드 안의 가상 서버(워크로드)에 보안 에이전트를 설치해 그 서버의 트래픽과 프로세스 동작을 수집한다. 집계된 데이터가 인지 분석 엔진에 들어가면, 엔진이 정상 동작 패턴에서 벗어난 프로세스가 암호화 통신으로 데이터를 전송하는 모습을 학습된 모델로 이상 징후로 판정한다. 사고가 확인되면 조사 제품이 그 시점 전후의 통신 기록과 파일 변경 기록을 자동으로 모아 피해 범위를 재구성해 준다.

#4동작 과정

  1. 수집·모니터링클라우드 보안 제품이 클라우드 워크로드와 온프레미스(사내) 장비의 트래픽·로그·동작 정보를 한곳에 모아 지속적으로 감시한다.
  2. 인지 분석·탐지머신러닝 기반 인지 분석 엔진이 수집된 데이터의 정상 패턴을 학습해, 그 패턴에서 벗어난 신종 위협과 이상 행위를 시그니처 없이 탐지한다.
  3. 조사·대응탐지된 사고에 대해 관련 통신·파일·접속 기록을 자동으로 연결해 사고 조사를 지원하고, 위협 차단 조치를 실행한다.

#5한 줄 요약

클라우드 환경 보안, 머신러닝 기반 위협 탐지, 사고 조사를 하나의 제품군으로 통합해 온프레미스와 클라우드를 아우르는 감시와 대응을 제공하는 것

암호화 트래픽 분석

복호화 없이 TLS 등 암호화 트래픽의 메타데이터와 패턴을 분석해 숨겨진 위협을 탐지하는 기술

#1문제 상황

TLS(전송 계층 보안)는 웹 트래픽을 암호화하므로 오늘날 대부분의 통신이 보안 장비에서 내용을 들여다볼 수 없는 형태로 흐른다. 암호화를 푸는 복호화 방식(SSL 검사)은 개인정보·인증서 문제 때문에 모든 트래픽에 적용할 수 없고, 적용하더라도 성능 부담이 크다. 공격자도 이 점을 노려 악성 명령과 유출 데이터를 암호화 통신에 숨겨 보내므로, 복호화 없이는 숨겨진 위협을 볼 수 없다는 것이 기존 방식의 한계다.

#2핵심 질문

암호화 통신을 복호화하지 않고서도 그 안에 숨겨진 위협을 알아낼 수는 없을까?

#3동작 예시

TLS 핸드셰이크(연결 시작 시 암호화 방식과 키를 주고받는 과정)에서는 서버 인증서, 암호화 방식 목록, 키 교환 방식 같은 메타데이터가 평문으로 노출된다. 암호화 트래픽 분석 제품은 이 메타데이터와 연결의 패킷 길이·타이밍·통신 방향 같은 패턴을 수집해, 평소 연결이 없던 도메인으로 가는 암호화 연결이나 악성 서버와 동일한 인증서를 쓰는 연결을 위협으로 판정한다.

#4동작 과정

  1. 메타데이터 수집보안 장비가 TLS 핸드셰이크의 인증서·암호화 방식·SNI(서버 이름 표시)와 패킷 길이·타이밍 같은 비암호화 정보를 수집한다.
  2. 패턴 분석수집한 정보를 신뢰할 수 없는 인증서, 평소에 없던 통신 대상, 비정상적인 패킷 크기 패턴 등 알려진 위협 신호와 대조한다.
  3. 탐지·차단위협으로 판정된 암호화 연결을 식별해 알림을 보내고, 해당 연결만 차단한다.

#5한 줄 요약

복호화 없이 암호화 트래픽의 메타데이터와 통신 패턴만 분석해 그 안에 숨겨진 위협을 탐지하는 것

엔드포인트 네트워크 가시성 모듈

엔드포인트에 설치되어 그 장비의 네트워크 통신(NetFlow)을 수집·전송해 보이지 않는 구간까지 가시화하는 모듈

→ 06-06 참조

#1문제 상황

네트워크 텔레메트리는 라우터나 스위치 같은 인프라 장비에 의존하므로, 장비 외부로 나가지 않는 엔드포인트(개별 PC, 서버) 내부의 통신은 보이지 않는다. 예를 들어 한 서버 안에서 프로세스가 데이터를 몰래 전송하거나, 장비가 연결되지 않은 구간에서 통신이 일어나면 흐름 데이터가 생성되지 않아 감시망에서 빠진다. 인프라 장비만으로는 엔드포인트 단위의 통신을 볼 수 없다는 것이 기존 방식의 사각지대다.

#2핵심 질문

라우터와 스위치가 보지 못하는 엔드포인트 안에서 일어나는 통신까지 텔레메트리로 볼 수는 없을까?

#3동작 예시

엔드포인트 가시성 모듈을 서버에 에이전트 형태로 설치하면, 그 서버가 보내고 받는 트래픽을 서버 자체에서 흐름 레코드로 만들어 수집 서버로 보낸다. 한 서버의 프로세스가 평소 통신한 적 없는 외부 IP로 데이터를 보내기 시작하면, 이 모듈이 만든 흐름 레코드에서 그 통신이 즉시 이상 징후로 드러난다. 인프라 장비 없이도 엔드포인트 단위의 통신이 가시화된다.

#4동작 과정

  1. 로컬 흐름 생성엔드포인트에 설치된 모듈이 그 장비의 네트워크 인터페이스를 지나는 트래픽을 NetFlow 형식의 흐름 레코드로 만들어 로컬에서 수집한다.
  2. 수집 서버 전송모듈이 생성한 흐름 레코드를 중앙 텔레메트리 수집 서버로 보내 다른 네트워크 장비의 레코드와 합친다.
  3. 통합 가시화수집 서버가 엔드포인트와 인프라 장비의 흐름을 하나의 트래픽 지도로 합쳐, 엔드포인트 단위의 비정상 통신까지 감시 대상에 포함한다.

#5한 줄 요약

엔드포인트에 설치된 모듈이 그 장비의 네트워크 통신을 흐름 레코드로 수집·전송하여 인프라 장비가 못 보는 구간까지 가시화하는 것
