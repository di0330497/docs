DOP-C02 시험의 정체 - 대상 후보와 검증 능력

AWS 환경에서 CI/CD·자동화·운영을 2년 이상 다뤄본 사람을 대상으로, 분산 시스템을 프로비저닝·운영·관리하는 능력을 검증하는 전문가(Professional) 등급 자격시험이다.

#1문제 상황

AWS 자격증 체계에서 Associate 레벨(1년 경력)까지의 자격증은 있었지만, 그 이상 심화 자격증이 없었을 때는 클라우드 환경에서 개발·운영·배포를 다루는 사람들이 자신의 전문성을 체계적으로 검증받을 방법이 없었습니다.

#2핵심 질문

DOP-C02 시험은 어떤 수준의 DevOps 전문성을 가진 사람을 대상으로 누구의 역량을 검증하는가?

#3동작 예시

시험 대상은 "AWS 환경에서 CI/CD·자동화·운영을 2년 이상 다뤄본" 실무 경험자이고, 시험이 검증하는 것은 "분산 시스템을 프로비저닝하고, 지속적으로 운영하며, 문제가 생겼을 때 관리하는" 세 가지 능력입니다.

#4동작 과정

  1. 대상 설정2년 이상의 AWS 환경 실무 경험(특히 CI/CD·배포 자동화·운영 담당)을 갖춘 개발자, 인프라 엔지니어, DevOps 엔지니어를 대상으로 합니다.
  2. 검증 영역분산 시스템을 프로비저닝(인프라 구축)하고, 운영 중 지속적으로 관리하며, 장애·이벤트에 대응하는 역량을 검증합니다.
  3. 자격 증명시험 합격은 AWS에서 "DevOps Engineer - Professional" 자격 보유자로 공식 인정받게 되어 조직 내 역할 신뢰도와 경력 가치가 높아집니다.

시험 형식과 채점 방식

객관식과 복수응답 문항으로 구성된 시험을 정해진 시간 안에 풀고, 100~1000 척도의 환산 점수로 합격 여부가 결정되며 채점 대상이 아닌 예비 문항도 섞여 있다.

#1문제 상황

AWS 시험이 단순 객관식이므로, 정답을 맞춘 개수만으로는 응시자의 진정한 능력 수준을 세밀하게 구분하기 어렵고, 시험마다 다른 점수대를 쓰면 자격증 간 비교와 평가가 불가능합니다.

#2핵심 질문

Professional 레벨 시험의 난이도와 응시자 역량을 공평하게 측정하기 위해 어떤 채점 방식을 써야 할까?

#3동작 예시

시험은 객관식·복수응답 문항을 정해진 시간 안에 풀고, 맞춘 개수를 100~1000 척도의 환산 점수로 변환해 합격 여부를 결정하며, 채점 대상이 아닌 예비 문항이 섞여 있어 새로운 문제의 난이도를 미리 검증합니다.

#4동작 과정

  1. 응시객관식 1지선다와 복수응답 문항(여러 개 선택)을 정해진 시간 안에 푸는 형식입니다.
  2. 채점맞춘 답안을 집계하고, 시험 난이도 보정을 거쳐 100~1000 스케일의 환산 점수로 변환합니다(예: 실제 정답 70개 → 환산 점수 800점).
  3. 판정합격선(보통 환산 점수 일정 이상) 도달 여부로 합격·불합격이 결정됩니다.

#5한 줄 요약

시험을 무작정 봤던 과거와 달리, Professional 레벨은 범위가 방대해서 모든 주제를 똑같은 비중으로 공부할 수 없고, 시험에 출제되는 주제와 빈도가 명확하지 않으면 효율적인 학습 계획을 세울 수 없습니다.

#2핵심 질문

방대한 DevOps 주제 중 시험에서 어떤 영역에 점수 비중이 가장 높은가?

#3동작 예시

시험은 6개 콘텐츠 도메인으로 나뉘어 있고, 각 도메인이 배점 비중(예: 도메인1 20%, 도메인2 18% 등)을 가져서, 그 비중이 곧 공부할 우선순위와 시간 배분을 결정합니다.

#4동작 과정

  1. 도메인 분류SDLC 자동화, 구성 관리와 IaC(코드로 인프라 정의), 복원력 있는 클라우드 솔루션, 모니터링과 로깅, 인시던트·이벤트 대응, 보안과 규정 준수 6개 영역으로 분류합니다.
  2. 배점 할당AWS가 각 도메인에 배점 비중을 공개하여(예: 도메인1 18%, 도메인2 20% 등) 전체 시험 구성을 투명하게 공시합니다.
  3. 학습 계획 수립배점이 높은 도메인부터 우선적으로 공부하고, 배점에 따라 각 주제별 학습 시간을 배분합니다.

#4동작 과정

계정·조직·자격증명 기반02-01

IAM 엔티티와 정책 유형

사용자·그룹·역할 같은 IAM 엔티티와, 자격증명 기반·리소스 기반 정책이 각각 무엇에 붙어 권한을 정하는지 구분하는 기초.

#1문제 상황

IAM은 "권한을 줄 때" 복잡합니다. 사용자에게 권한을 주려면, 직접 정책을 붙일지(Identity-based), 리소스에 붙인 정책을 통해 권한을 받을지(Resource-based) 선택해야 하는데, 이 둘의 차이를 모르면 권한 설계가 꼬이고, 누가(User, Group, Role) 어디에(IAM 엔티티 vs 리소스) 정책을 붙이는지 헷갈리면 권한이 제대로 작동하지 않습니다.

#2핵심 질문

IAM에서 권한을 정할 때 사용자·그룹·역할 중 어디에, 그리고 누가 정책을 정의해야 하는가?

#3동작 예시

IAM 엔티티(User, Group, Role)에 붙는 정책을 Identity-based 정책이라 하고(예: 사용자에게 S3 읽기 권한 정책 붙이기), S3 버킷이나 Lambda 함수 같은 리소스 자체에 붙는 정책을 Resource-based 정책이라 합니다(예: S3 버킷 정책에 "이 역할만 접근 허용"). 두 정책이 모두 만족해야 실제 작동합니다.

#4동작 과정

  1. Identity-based 정책IAM 사용자, 그룹, 역할에 정책을 직접 붙여서 "이 엔티티가 무엇을 할 수 있는지" 정합니다(예: CodePipeline 역할에 "S3 읽기·쓰기 허용" 정책 붙이기).
  2. Resource-based 정책S3, Lambda, SQS 같은 AWS 리소스 자체에 정책을 붙여서 "어떤 외부 엔티티가 이 리소스에 접근하는지" 제어합니다(예: S3 버킷 정책에 "특정 역할만 이 버킷 읽기 가능" 명시).
  3. 함께 작동실제 권한 부여는 Identity-based와 Resource-based 정책이 모두 "허용"해야 작동합니다.

#5한 줄 요약

권한을 "누가 할 수 있는지"(Identity-based)와 "누가 리소스에 접근하는지"(Resource-based) 두 측면에서 동시에 제어하여, 권한 부여의 투명성과 보안성을 높이는 IAM 설계 방식

역할 위임과 AWS STS - AssumeRole·인스턴스 프로파일·MFA

장기 키 대신 STS가 발급하는 임시 자격증명을 역할로 받아 쓰는 위임 방식과 인스턴스 프로파일·MFA 결합 패턴.

#1문제 상황

장기 키(Access Key ID + Secret Access Key)를 EC2 인스턴스나 개발자 머신에 저장하면, 키가 노출되었을 때 계속 유효해서 보안 위험이 크고, 누가 누구의 권한으로 뭘 하는지 감시할 수 없으면 보안 감시와 감사가 어려워집니다.

#2핵심 질문

장기 키의 보안 위험을 없애면서도, 프로세스(EC2, Lambda)나 사람이 AWS 리소스에 임시로 접근하려면 어떻게 해야 할까?

#3동작 예시

STS(Security Token Service)는 Role(역할)에 대한 AssumeRole 요청을 받아서, 임시 자격증명(임시 Access Key + Secret Key + Session Token, 기본 1시간 유효)을 발급하고, 이를 EC2는 인스턴스 프로파일을 통해 받으며, 사람은 MFA 인증 후 자신의 계정에서 다른 역할로 전환하는 방식입니다.

#4동작 과정

  1. 역할 정의IAM에서 역할을 만들고 "누가 이 역할을 맡을 수 있는지"(신뢰 관계, Trust Policy) 정의합니다.
  2. 임시 자격증명 발급AssumeRole 요청 시 STS가 임시 자격증명(Session Token 포함, 기본 1시간 유효)을 발급하고, EC2 인스턴스는 인스턴스 프로파일(Instance Profile) 메타데이터 엔드포인트를 통해 자동으로 받습니다. 사람은 MFA 인증 후 다른 계정/역할로 임시로 전환할 수 있습니다.
  3. 접근 제어임시 자격증명으로 요청하면 CloudTrail(감사 로그)에 "누가, 어느 역할로, 언제" 기록되고, 토큰 만료 후 자동으로 접근이 불가능합니다.

#5한 줄 요약

장기 키 대신 STS가 발급하는 일시적 자격증명으로 권한을 위임하고(AssumeRole), EC2 등 프로세스는 인스턴스 프로파일로 자동 갱신받으며, 사람은 MFA 인증 후 역할 전환을 가능하게 하여 보안과 감시 기능을 동시에 확보하는 권한 위임 패턴

최소 권한 설계와 RBAC·ABAC 접근 제어 패턴

필요한 만큼만 허용하는 원칙을 역할 기반(RBAC)과 태그 기반 속성(ABAC) 두 방식으로 구현하는 설계법.

→ 02-05 참조

#1문제 상황

권한을 "Administrator" 정책처럼 무지막지하게 주면, 한 명의 개발자가 실수로 핵심 리소스를 지워도 막을 수 없고, 실수나 악의적 행동에 대한 책임 추적이 어려워지며, "이 사람은 어느 팀이고, 어느 환경에서 뭘 해야 하는가"를 정책에 반영하지 않으면 권한 관리가 확장 불가능(각 사람마다 일일이 정책 만들기)해집니다.

#2핵심 질문

복잡한 조직 구조에서 각 사람이 필요한 만큼만 권한을 갖도록 하면서도, 권한 관리를 확장 가능하게 하려면?

#3동작 예시

RBAC(역할 기반)은 "프론트엔드 개발자" 같은 직급/팀별로 사전에 정책 묶음을 만들어 할당하고, ABAC(속성 기반)은 "팀=frontend, 환경=dev" 같은 태그를 IAM 엔티티와 리소스에 붙여서, 정책에서 "태그가 일치하는 역할만 이 리소스 접근"이라고 명시하는 방식입니다.

#4동작 과정

  1. RBAC 설계"DevOps Engineer" "Backend Developer" "Security Auditor" 같은 역할을 미리 정의하고, 각 역할에 필요한 권한을 정책으로 묶어 할당합니다(예: DevOps Engineer 역할은 EC2·RDS·CloudFormation 권한).
  2. ABAC 설계사용자와 리소스에 태그(예: 사용자의 "team=backend, environment=dev" 태그)를 붙이고, 정책에서 "요청자의 team 태그 값이 리소스의 team 태그 값과 일치할 때만 접근"이라고 조건을 명시합니다.
  3. 최소 권한 원칙 적용두 방식 모두 "필요한 것만, 필요한 기간만, 필요한 리소스만" 권한을 부여하여 실수·악의 피해를 최소화합니다.

#5한 줄 요약

이 설계역할 기반(RBAC) 또는 태그 기반 속성(ABAC) 두 가지 방식으로 "필요한 만큼만 허용"하는 최소 권한 원칙을 구현하여, 조직이 커져도 권한 관리를 일관되고 확장 가능하게 유지하면서 보안 위험을 낮추는 접근 제어 패턴

2단계 계정·조직·자격증명 기반

여러 계정을 조직과 OU로 묶고 서비스 제어 정책(SCP)으로 계정 전체의 권한 상한을 거는 조직 차원의 울타리.

#1문제 상황

AWS 계정이 여러 개일 때, 각 계정을 IAM으로 개별 제어하려면 같은 정책을 계정마다 반복 작성해야 합니다. 그러면 정책 변경 시 모든 계정을 돌아다니며 수정해야 하고, 계정이 많아질수록 누락이나 불일치 위험이 커집니다. 또한 어느 계정에서든 관리자가 실수로 금지된 작업을 허용할 수 있습니다.

#2핵심 질문

여러 AWS 계정 전체에서 금지되어야 할 작업들(예: 특정 리전 사용 금지, 암호화 정책 무시)을 한 번에 정책으로 거는 방법은?

#3동작 예시

Organizations로 계정들을 OU(조직 단위)로 묶고, OU에 SCP(서비스 제어 정책)를 붙이면 그 OU 내 모든 계정의 작업이 그 정책에 먼저 걸립니다. 각 계정의 IAM 권한이 있어도 SCP가 "안 된다"고 하면 작동하지 않습니다.

#4동작 과정

  1. 조직 구성루트 계정에서 Organizations를 켜고 여러 계정들을 초대해 트리 구조로 묶습니다. OU(조직 단위)는 폴더처럼 계정을 그룹화합니다.
  2. SCP 적용특정 OU에 서비스 제어 정책(SCP, 정책 언어로 쓴 권한 제한 규칙)을 붙입니다. 예를 들어 "eu-west-1이 아닌 리전에서 EC2 시작 금지" 같은 규칙을 정하면 그 정책은 모든 하위 계정에 적용되는 천장이 됩니다.
  3. 계정별 추가 권한 관리각 계정에서는 IAM으로 역할과 정책을 만들지만, SCP의 천장을 넘을 수 없습니다. 즉 SCP와 IAM 정책이 모두 허용해야만 최종 권한이 됩니다.

#5한 줄 요약

조직 수준의 거버넌스 정책(SCP)으로 여러 계정 전체의 작업 범위를 미리 정해 두고, 각 계정의 IAM은 그 범위 안에서만 역할을 부여하도록 하는 것

#1문제 상황

일반적으로 관리자가 모든 IAM 역할을 직접 만들고 권한을 부여합니다. 팀이 자체적으로 역할을 만들 권한을 주면 관리자의 실수나 과도한 권한 부여 위험이 커집니다. 조직이 커질수록 관리자가 모든 요청의 병목이 되고, 팀의 자유도가 제한됩니다.

#2핵심 질문

팀이 자유롭게 역할을 만들면서도 위험한 권한을 주지 않도록 어떻게 안전하게 위임할 수 있을까?

#3동작 예시

권한 경계(Permission Boundary)는 개별 IAM 주체(사람, 역할)가 가질 수 있는 최대 권한을 미리 정해 두는 천장입니다. 예를 들어 "이 팀 리더는 최대 S3만 건드릴 수 있다"는 경계를 정하면, 그 리더가 만드는 모든 역할도 S3 범위를 넘을 수 없습니다.

#4동작 과정

  1. 경계 정책 정의팀 리더가 다룰 수 있는 권한의 최대 범위를 정책 문서로 정합니다. 예: "S3, EC2 인스턴스 읽기만, RDS는 금지" 등.

  3. 팀이 자유롭게 운영리더는 경계 범위 안에서 팀원들의 역할을 만들고 권한을 조정할 수 있습니다. 관리자에게 매번 요청할 필요가 없어집니다.

#1문제 상황

#2핵심 질문

#3동작 예시

Control Tower는 AWS 계정 팩토리처럼 작동해서 "표준 랜딩 존" 템플릿을 기반으로 새 계정을 한 번에 만듭니다. IAM Identity Center(구 AWS SSO)는 모든 계정 사용자들의 로그인을 한 곳의 디렉터리에서 관리하고, 외부 IdP(예: Active Directory, Google Workspace)를 연결하면 회사 계정 하나로 모든 AWS 계정에 접근할 수 있습니다.

#4동작 과정

  1. Control Tower 초기화Organizations와 클라우드 로그, 클라우드 추적(감사 기능)을 자동으로 켜고, 기본 보안 정책(SCP)과 람다 기반 예방·탐지 기능들을 미리 배포합니다. 이후 새 계정 신청 시 이 표준이 자동 적용됩니다.

  3. 로그인과 접근사용자는 Identity Center 포털(또는 회사 AD 계정)로 한 번 로그인하면 권한 있는 모든 AWS 계정에 즉시 접근할 수 있습니다. 로그인·로그아웃·권한 변경이 모두 한곳에서 추적됩니다.

서버와 네트워크 같은 인프라를 손으로 만들지 않고 코드 파일로 선언해 반복 생성하는 방식이며, AWS에서는 CloudFormation·CDK·Service Catalog 중 팀 역량과 표준화 요구에 맞춰 고른다.

#1문제 상황

AWS 콘솔에서 손으로 EC2, RDS, 보안 그룹 등을 만들고, 실수하면 다시 만들고, 같은 구성을 다른 환경에 만들 때 또 손으로 합니다. 오타나 누락이 발생하면 환경 간 불일치가 생기고, 운영 문서를 따로 작성해야 하며, 대규모 변화는 위험합니다.

#2핵심 질문

서버·네트워크 같은 인프라를 손으로 만들지 않고 코드로 선언해 반복하고 버전 관리할 수 있을까?

#3동작 예시

IaC(Infrastructure as Code)는 EC2 인스턴스, 데이터베이스, 네트워크 설정 등을 일반 코드 파일에 텍스트로 적어 두고, 그 파일을 실행하면 AWS가 정확히 같은 구성을 자동으로 만듭니다. 파일은 깃으로 버전 관리되고, 누가 언제 뭘 바꿨는지 추적되며, 리뷰와 테스트 같은 코드 관행을 그대로 적용할 수 있습니다.

#4동작 과정

  1. 선언형 기술 선택AWS는 CloudFormation(JSON/YAML 템플릿), AWS CDK(파이썬, 타입스크립트 등 프로그래밍 언어), Service Catalog(재사용 가능한 상품 카탈로그) 세 가지를 제공합니다. CloudFormation은 AWS 고유 문법이므로 러닝 커브가 있지만 표준이고, CDK는 친숙한 언어로 쓸 수 있지만 최종 CloudFormation으로 변환됩니다. Service Catalog는 팀이 이미 만든 템플릿을 셀프서비스 상품처럼 제공할 때 쓰입니다.
  2. 팀 역량과 요구에 맞춰 도구 선택신입 팀은 표준이 명확한 CloudFormation, 개발자 경험을 중시하면 CDK, 대규모 조직에서 표준화된 구성을 계속 재사용해야 하면 Service Catalog를 고릅니다.
  3. 코드 리뷰·테스트·배포 자동화변경을 깃 풀 리퀘스트로 제출하면 팀이 검토하고, 자동 테스트(cfn-lint, Policy as Code 검사 등)를 거친 뒤, 승인되면 파이프라인이 자동으로 배포합니다.

#5한 줄 요약

인프라를 텍스트 파일로 선언하고 버전 관리·자동 배포하며, 소프트웨어 개발 방식(리뷰, 테스트, 추적)을 인프라 관리에 적용하는 것

Parameters·Resources·Outputs 등 정해진 섹션으로 인프라를 기술하고 Ref·Fn::GetAtt 같은 내장 함수로 값들을 서로 연결하는 템플릿 문법이다.

#1문제 상황

#2핵심 질문

여러 리소스를 한 파일에서 서로 연결하고, 변수처럼 다시 쓰면서 일관성 있게 관리할 수 있을까?

#3동작 예시

CloudFormation 템플릿은 정해진 섹션(Parameters·Resources·Outputs)을 YAML/JSON으로 작성한 파일입니다. Ref와 Fn::GetAtt 같은 내장 함수로 리소스들을 서로 참조하면, 생성 순서는 CloudFormation이 자동으로 맞추고, 리소스의 ID나 속성 값은 함수가 동적으로 채워 넣습니다.

#4동작 과정

  1. Parameters·Resources 작성Parameters 섹션에는 배포할 때 입력받을 값(예: 인스턴스 타입, 환경 이름)을 정의하고, Resources에는 만들 EC2, RDS, 보안 그룹 등을 나열합니다. 각 리소스에는 고유한 논리적 ID를 붙입니다.
  2. 내장 함수로 리소스 연결Ref 함수는 다른 리소스의 ID를 참조하고(예: Ref: MySecurityGroup), Fn::GetAtt는 속성을 가져옵니다(예: Fn::GetAtt: [MyRDS, Endpoint.Address]). 이렇게 하면 어느 보안 그룹 ID가 어디 쓰이는지 명시되고, 리소스 생성 순서는 CloudFormation이 자동으로 결정합니다.
  3. Outputs 정의스택이 만들어진 후 필요한 값들(예: EC2의 공인 IP, RDS 엔드포인트)을 Outputs에 정의하면, 배포 후 그 값들이 콘솔에 표시되거나 프로그래매틱하게 읽을 수 있습니다.

#1문제 상황

#2핵심 질문

스택 업데이트 전에 어떤 리소스가 바뀔지 미리 보고, 실패 시 자동으로 되돌리며, 콘솔에서의 직접 편집을 감지할 수 있을까?

#3동작 예시

CloudFormation은 변경 세트(스택을 바꾸기 전 변경 내역을 미리 보는 기능), 자동 롤백(배포 실패 시 이전 상태로 되돌림), 드리프트 감지(실제 리소스 상태와 템플릿의 차이를 찾음)를 제공합니다.

#4동작 과정

  2. 배포 및 자동 롤백변경 세트를 실행하면 CloudFormation이 하나씩 리소스를 변경합니다. 도중에 오류가 발생하면 롤백 정책(전체 롤백, 부분 계속 등)에 따라 이전 상태로 자동으로 돌아갑니다. 수동 개입이 필요 없습니다.

  2. 사용자 지정 리소스와 람다 함수CloudFormation이 직접 지원하지 않는 작업(예: GitHub 레포 자동 생성, Slack 알림 전송)을 하려면, 사용자 지정 리소스 타입을 정의하고 그 뒤에 람다 함수를 붙입니다. CloudFormation이 그 리소스를 생성·삭제할 때 람다를 호출해 원하는 작업을 수행합니다.

자동으로 오래된 아티팩트를 삭제하고 필요한 것만 보관할 수 있을까요?

#3동작 예시

CodeArtifact는 저장소에 보존 규칙을 설정해서 일정 개수 이상의 버전이나 일정 기간이 지난 패키지를 자동으로 삭제할 수 있습니다. S3도 라이프사이클 정책(Lifecycle Policy)으로 30일 이상 사용하지 않은 파일을 자동으로 삭제하거나 저비용 저장소로 옮길 수 있습니다.

#4동작 과정

  1. 보존 규칙 설정CodeArtifact는 유지할 최신 버전 개수를, S3 라이프사이클 정책은 보관 기간과 삭제 조건을 정합니다.
  2. 시간 경과에 따른 자동 정리일정 시간이 지나면 정책에 따라 오래된 아티팩트가 자동으로 삭제되거나 저비용 저장 클래스로 옮겨집니다.
  3. 비용 최적화불필요한 저장소 비용을 줄이고, 남은 아티팩트 중 자주 사용하는 것은 접근 속도가 빠른 위치에 유지됩니다.

#2핵심 질문

CodePipeline 구조 - 스테이지·액션·아티팩트 전달·승인 게이트

파이프라인은 순서대로 실행되는 스테이지들로 이루어지고, 각 스테이지의 액션이 S3 아티팩트로 결과를 다음 단계에 넘기며, 수동 승인 액션으로 배포 전 사람이 검토할 수 있다.

#1문제 상황

기존에는 소스 코드 변경 후 빌드, 테스트, 스테이징 환경 배포, 프로덕션 배포 같은 각 단계를 사람이 수동으로 실행했고, 어느 단계를 거쳤는지 추적하기 어려웠습니다. 또한 프로덕션 배포 전 사람이 반드시 검토하고 승인해야 하는 단계를 강제할 방법이 없었습니다.

#2핵심 질문

여러 단계의 배포 작업을 자동으로 실행하면서 필요한 지점에서 사람의 승인을 받을 수 있을까요?

#3동작 예시

CodePipeline은 Source(소스 감지) → Build(컴파일·테스트) → Deploy Staging(스테이징 배포) → Manual Approval(수동 승인 게이트) → Deploy Production(프로덕션 배포) 같은 순차적 스테이지를 정의합니다. 각 스테이지가 완료되면 결과물(아티팩트)을 S3에 저장하고 다음 스테이지로 전달하며, Manual Approval 스테이지에서 멈춰서 사람이 검토한 후 승인하면 다음 단계로 진행됩니다.

#4동작 과정

  1. 스테이지와 액션 정의파이프라인을 여러 스테이지로 나누고(Source, Build, Deploy 등), 각 스테이지에서 실행할 액션(CodeBuild 실행, 승인 대기 등)을 순서대로 설정합니다.
  2. 아티팩트 자동 전달각 스테이지가 끝나면 출력 결과를 S3에 저장하고, 다음 스테이지가 이를 자동으로 가져가서 사용합니다.
  3. 승인 게이트와 조건부 실행Manual Approval 액션은 파이프라인을 멈춰서 담당자의 승인을 기다리고, 승인 여부나 이전 단계 성공 여부에 따라 다음 실행 여부를 결정합니다.

#5한 줄 요약

배포 과정을 순차적 스테이지로 나누고 아티팩트를 자동 전달하며, 필요한 지점에 승인 게이트를 두어서 안전하고 추적 가능한 자동화 배포를 구현하는 것

코드 변경이 올라올 때마다 빌드 서비스가 테스트를 실행하고, 종료 코드와 커버리지 리포트로 통과 여부를 자동 판정해 병합을 막거나 허용한다.

#1문제 상황

기존에는 개발자가 코드를 풀 리퀘스트(PR)로 올리면, 누군가 수동으로 테스트를 실행하고 결과를 확인했습니다. 사람의 실수가 있을 수 있고, 언제 병합할지를 주관적으로 판단해야 합니다.

#2핵심 질문

코드가 올라올 때마다 자동으로 테스트를 실행하고, 그 결과로 병합을 자동 통제할 수 있을까요?

#3동작 예시

#4동작 과정

  1. PR 생성 시 자동 트리거PR이 생성되거나 커밋이 추가되면 GitHub webhook이 빌드 서비스에 신호를 보내 테스트 실행을 자동 시작합니다.
  2. 테스트 실행 및 결과 수집빌드 서비스가 코드를 빌드하고 테스트를 실행한 후, exit code(0=성공, 1=실패)와 커버리지 데이터(어느 줄까지 테스트되었는지)를 수집합니다.
  3. 자동 판정 및 병합 제어판정 결과를 GitHub PR의 상태로 기록해, 보호된 브랜치(main, master)로의 병합을 자동 허용(테스트 통과) 또는 거부(테스트 실패)합니다.

#1문제 상황

배포 후 운영 환경에서 성능 저하나 보안 취약점이 발견되면 이미 사용자에게 영향을 미친 상태입니다. 파이프라인의 어느 단계에서 실패했는지 찾기도 어렵습니다.

#2핵심 질문

#4동작 과정

  1. 스테이징 배포 후 검사새 버전을 스테이징 환경에 배포한 후, 부하 테스트(수천 개의 동시 요청 생성)와 보안 스캔(SQL Injection, XSS 등 일반적인 취약점 검사)을 자동 실행합니다.
  2. 실패 기준 판정응답 시간, 에러율, 취약점 개수 등의 메트릭을 미리 정한 기준과 비교해, 기준을 벗어나면 파이프라인을 중단하고 경고를 발송합니다.
  3. 원인 추적 및 복구파이프라인 실행 이력(각 단계가 언제 언제 완료되었는지), 빌드 로그, 배포 버전 정보를 검토해 문제의 원인을 특정한 후, 버전 관리 시스템에서 이전 버전으로 되돌리거나(rollback) 수정 후 재배포합니다.

기존 서버를 고쳐 쓰는 변경 가능(mutable) 방식과 새 인프라를 만들어 교체하는 불변(immutable) 방식을 비교해, 다운타임·비용·롤백 요구사항에 맞는 배포 전략을 고르는 기준이다.

#2핵심 질문

#3동작 예시

#4동작 과정

  3. 배포 도구 구성변경 가능: CodeDeploy에서 파일 복사 및 애플리케이션 재시작, 불변: CodeBuild로 새 AMI 빌드 → Auto Scaling Group의 시작 템플릿 변경 → 기존 인스턴스 자동 교체.

#1문제 상황

EC2 인스턴스 여러 개에 애플리케이션을 배포할 때, 어느 인스턴스에, 어떤 파일을, 어떤 순서로 복사할지, 그리고 배포 전후에 어떤 검증을 할지 일일이 수동으로 정의하기는 복잡하고 오류가 생기기 쉽습니다.

#2핵심 질문

EC2 인스턴스 여러 개에 같은 애플리케이션을 일관되게 배포하면서, 배포 전후 검증을 자동화할 수 있을까요?

#3동작 예시

CodeDeploy는 배포 그룹(대상 EC2 인스턴스의 모음)을 정의하고, AppSpec 파일(무엇을 어디에 어떤 순서로, 각 단계에서 실행할 검증 스크립트 포함)을 읽어서, 각 인스턴스의 CodeDeploy 에이전트(배포 작업을 수행하는 프로그램)에 명령을 내려 애플리케이션을 배포하고, 수명주기 후크(BeforeInstall, AfterInstall 등)로 배포의 각 단계마다 자동으로 검증 스크립트를 실행하는 구조입니다.

#4동작 과정

  1. AppSpec 파일 정의YAML 또는 JSON 형식으로 배포할 파일의 출처와 목적지(예: S3에서 애플리케이션을 다운로드해 /opt/myapp에 복사), 파일의 소유자와 권한, 각 단계에서 실행할 스크립트(설치 전 기존 프로세스 중단, 설치 후 신 버전 검증)를 명시합니다.
  2. 배포 그룹 생성 및 배포 실행대상 EC2 인스턴스를 AutoScaling Group 또는 태그로 지정해 배포 그룹을 만들고, CodeDeploy에 배포를 요청하면 각 인스턴스의 에이전트가 AppSpec 파일의 순서대로 작업을 수행합니다.
  3. 수명주기 후크 자동 실행에이전트가 각 단계(ApplicationStop → BeforeInstall → ApplicationStart → ValidateService)를 순차 실행하며, 각 단계의 끝에서 AppSpec에 정의된 검증 스크립트를 자동 실행해 배포의 성공 여부를 판정합니다.

#1문제 상황

기존 방식은 EC2 인스턴스에 애플리케이션을 직접 배포하는 것이었다. 배포할 때마다 서버를 중지하고 새 코드를 복사한 후 재시작해야 했으며, 배포 중에는 사용자 요청이 끊긴다. 확장할 때도 새 인스턴스를 수동으로 추가하고 애플리케이션을 각각 설정해야 했다.

#2핵심 질문

컨테이너 이미지를 여러 서버에 자동으로 배포하면서 배포 중에 사용자 요청을 끊기지 않으려면?

#3동작 예시

ECS는 Docker 컨테이너 이미지를 클러스터(여러 EC2 인스턴스 모임)에 작업(Task)으로 올린다. 새 버전을 배포할 때 기존 작업을 중지하기 전에 새 버전 작업을 먼저 띄우므로 요청이 끊기지 않는다. Fargate나 App Runner는 이 과정에서 인스턴스 관리까지 AWS가 대신 처리한다.

#4동작 과정

  1. 이미지 준비애플리케이션을 Docker 컨테이너로 패키징하고 ECR(이미지 저장소)에 올린다.
  2. 작업 정의ECS에 "이 이미지를 얼마만큼의 CPU·메모리로 실행하라"는 작업 정의(Task Definition)를 등록한다.
  3. 배포 실행새 이미지가 올라오면 ECS는 롤링 배포로 새 작업을 먼저 띄우고 트래픽을 이동시킨 후 기존 작업을 내린다.

구성요소들이 직접 연결되지 않으면서도 서로의 변화에 빠르게 반응할 수 있는 방법이 있을까요?

#3동작 예시

이벤트는 "무언가 일어났다"는 신호입니다. 주문이 생성되면 "주문 생성됨" 이벤트를 발행하고, 이 이벤트를 받는 모든 구성요소(결제, 배송, 이메일 알림 등)가 각자 독립적으로 반응합니다. 각 구성요소는 다른 것의 내부 구조를 몰라도 됩니다.

#4동작 과정

  1. 이벤트 발생AWS 서비스(EC2 시작, 주문 생성, DynamoDB 업데이트 등)에서 상태 변화가 일어나면 이벤트를 생성합니다.
  2. 이벤트 발행이벤트를 중앙 버스(EventBridge, SNS 등)로 흘려보냅니다.
  3. 독립적 반응버스를 구독하는 각 구성요소(Lambda, SQS, 다른 서비스)가 이벤트를 받아 각자 필요한 일을 처리합니다.

#1문제 상황

기존에는 서비스 간 이벤트를 전달하려고 각 서비스 쌍마다 별도의 통합 로직을 만들어야 했습니다. EC2 이벤트를 Lambda로 보내려면, RDS 이벤트를 SNS로 보내려면 각각 다른 코드를 짜야 했고, 새로운 서비스가 추가되면 또 새로운 통합을 만들어야 했습니다.

#2핵심 질문

AWS 전체 서비스의 이벤트를 한 곳에서 받아 규칙에 따라 대상에게 자동으로 보낼 수 있을까요?

#3동작 예시

EventBridge는 중앙 이벤트 버스입니다. EC2, RDS, S3, 커스텀 애플리케이션 등 모든 이벤트 소스에서 버스로 이벤트를 보냅니다. 버스에는 규칙(rule)이 있어서, 예를 들어 "source가 ec2이고 detail-type이 'EC2 Instance State-change Notification'이면 Lambda에 보내라"는 식으로 패턴에 맞는 이벤트를 자동으로 대상에게 라우팅합니다.

#4동작 과정

  1. 이벤트 수신AWS 서비스나 커스텀 애플리케이션에서 이벤트를 EventBridge 버스로 전송합니다.
  2. 규칙 매칭버스의 각 규칙에 정의된 이벤트 패턴(JSON 형태의 필터)과 수신 이벤트를 비교해 매칭되는 규칙을 찾습니다.
  3. 대상으로 배달매칭된 규칙의 대상(Lambda, SNS, SQS, HTTP 엔드포인트 등)에 이벤트를 전달합니다. 또한 스케줄 기능으로 정해진 시각에 대상을 호출할 수도 있습니다.

SNS·SQS·Lambda·Step Functions 이벤트 처리 워크플로

알림 발행(SNS), 작업 대기열(SQS), 서버 없는 실행(Lambda), 단계 조율(Step Functions)을 엮어 이벤트를 실제 처리 흐름으로 만드는 방법이다.

#1문제 상황

기존에는 이벤트를 받기만 했고, 그 이벤트를 처리하는 방식이 제각각이었습니다. 어떤 서비스는 즉시 처리했고, 어떤 것은 처리를 미뤘고, 복잡한 단계들을 거쳐야 하면 각각의 서비스가 다음 단계를 직접 호출해야 했습니다. 이렇게 되면 에러 처리도 복잡하고 워크플로 진행 상황을 추적하기 어려웠습니다.

#2핵심 질문

이벤트를 받아 여러 단계를 거쳐 처리하는 워크플로를 조직적으로 만들 수 있을까요?

#3동작 예시

SNS는 이벤트를 발행하고 구독자들에게 즉시 알립니다. SQS는 작업을 대기열에 넣어 나중에 처리할 수 있게 합니다. Lambda는 이벤트가 올 때 서버 없이 함수를 실행합니다. Step Functions는 이 모든 것을 조율해서, 예를 들어 "먼저 Lambda로 데이터 검증 → SQS에 대기 → Lambda로 처리 → SNS로 결과 알림" 같은 복잡한 흐름을 한 곳에서 관리할 수 있게 합니다.

#4동작 과정

  1. 이벤트 발행 및 전달EventBridge나 S3 같은 소스에서 이벤트를 발생시키거나, SNS로 알림을 발행합니다. 대기가 필요하면 SQS에 메시지를 넣습니다.
  2. 워크플로 조율Step Functions가 정의된 단계들(Lambda 실행, SQS 폴링, 조건 분기, 재시도 로직 등)을 순서대로 진행하면서 각 단계의 결과를 다음 단계에 전달합니다.
  3. 결과 처리 및 모니터링최종 단계에서 결과를 SNS로 알리거나 데이터베이스에 저장하고, Step Functions는 전체 워크플로의 상태와 실행 이력을 제공합니다.

#1문제 상황

기존 방식은 리소스 설정이 변경되면 모니터링을 통해 사람이 이를 발견하고, 수동으로 원래 상태를 복구해야 합니다. 이 방식의 명확한 한계는 설정 변경을 감지하는 데 시간이 걸리고, 복구 과정에서 휴먼 에러가 발생하며, 장애 원인이 "누군가 실수로 설정을 바꿈"일 때 대응이 늦어진다는 점입니다.

#2핵심 질문

#3동작 예시

AWS Config Rule로 "보안 그룹이 0.0.0.0/0에 대해 SSH(22번 포트)를 열어서는 안 된다"는 규칙을 정의하고, 이 규칙을 위반하는 변경이 감지되면 Lambda 함수가 자동으로 그 권한 규칙을 즉시 삭제합니다.

#4동작 과정

  1. 정책 및 규칙 정의Config Rule에서 "리소스가 이런 상태여야 한다"는 규정을 미리 설정합니다.
  2. 실시간 변경 감지EventBridge(실시간 이벤트 브로커)가 AWS API 호출을 포착하고, Config Rule이 현재 상태를 즉시 검사해 규칙 위반을 발견합니다.
  3. 자동 교정 실행AWS Systems Manager 또는 Lambda가 자동으로 실행되어 리소스를 원래 상태로 되돌리거나 바로잡습니다.

#3동작 예시

#4동작 과정

#3동작 예시

#4동작 과정

  1. 가용성 목표 해석SLA 목표를 백분율로 읽고 이것이 연간 몇 분의 장애를 허용하는지 계산합니다. (예: 99.9% = 8시간 46분, 99.99% = 52분 36초)

Elastic Load Balancing과 상태 확인

들어오는 트래픽을 여러 대상에 나눠 보내고, 상태 확인에 실패한 대상은 자동으로 제외해 장애를 감춰 주는 로드 밸런서.

#1문제 상황

기존 방식은 트래픽을 주로 한 서버로 보내거나, 서버 목록을 수동으로 관리합니다. 명확한 한계는 서버 하나가 다운되면 그 순간 서비스 중단이 발생하고, 서버 추가나 제거 때마다 설정을 수동으로 바꿔야 한다는 점입니다.

#2핵심 질문

서버 상태를 실시간으로 확인하면서 정상 서버로만 트래픽을 자동으로 분배할 수 있을까요?

#3동작 예시

웹 서버 3대가 로드 밸런서 뒤에 있고, 밸런서가 매 10초마다 각 서버에 HTTP 요청을 보내 "정상인가?"를 체크합니다. 한 서버가 응답을 멈추면 밸런서는 자동으로 그 서버를 "제외" 상태로 표시하고, 나머지 2대로만 신규 요청을 분산합니다.

#4동작 과정

  1. 트래픽 분배로드 밸런서가 들어오는 요청을 여러 대상(EC2, 컨테이너, 온프레미스 서버 등)에 라운드 로빈(순서대로 돌아가며) 또는 최소 연결 수(가장 여유 있는 대상 우선) 방식으로 나눠 보냅니다.
  2. 상태 확인(헬스 체크)정기적으로 각 대상에 HTTP 요청 또는 TCP 포트 확인을 하고, 응답 없음 또는 비정상 코드를 받으면 "비정상"으로 표시합니다.
  3. 자동 제외 및 복구비정상 대상은 트래픽 풀에서 제외되므로 사용자 요청이 정상 대상으로만 흐르고, 상태가 정상으로 돌아오면 자동으로 다시 포함됩니다.

#5한 줄 요약

실시간 상태 확인을 바탕으로 정상 대상만 선별해 트래픽을 분배해 개별 서버 장애를 투명하게 처리하는 것

Route 53 라우팅 정책·상태 확인·리전 간 장애 조치

DNS 단계에서 가중치·지연 시간·장애 조치 같은 정책과 상태 확인을 조합해 트래픽을 건강한 리전으로 돌리는 방법.

→ 10-02 참조

#1문제 상황

기존 방식은 사용자의 DNS 질의에 항상 같은 IP 주소를 반환하거나, 리전 간 장애 조치를 수동으로 관리합니다. 한계는 리전 장애 시 자동으로 다른 리전으로 트래픽을 돌릴 수 없고, 장애 발견과 수동 복구에 오랜 시간이 걸린다는 점입니다.

#2핵심 질문

DNS 응답 단계에서 각 리전의 상태를 감지하고, 건강한 리전으로만 트래픽을 자동 라우팅할 수 있을까요?

#3동작 예시

Route 53에 "미국 리전과 유럽 리전 각각에 애플리케이션이 돌고 있다"고 등록하고 장애 조치 정책을 설정하면, 미국 리전의 로드 밸런서가 응답을 멈출 때 Route 53은 자동으로 DNS 쿼리에 유럽 리전의 IP를 반환해 사용자가 자동으로 유럽으로 연결됩니다.

#4동작 과정

  1. 라우팅 정책 정의Route 53에서 가중치 기반(리전 A에 80%, 리전 B에 20%), 지연 시간 기반(사용자와 가장 가까운 리전 우선), 또는 장애 조치(주 리전 다운 시 보조 리전으로) 정책 중 하나를 선택합니다.
  2. 상태 확인 설정각 리전의 로드 밸런서나 엔드포인트에 헬스 체크를 정의해 정기적으로 "살아있나?"를 확인합니다.
  3. DNS 응답 결정사용자의 DNS 쿼리가 들어오면 상태 확인 결과를 보고 정상 리전의 IP만 반환하므로, 사용자는 자동으로 건강한 리전으로 연결됩니다.

#5한 줄 요약

DNS 응답 레벨에서 리전 상태를 실시간으로 반영해 트래픽을 지능적으로 라우팅하고, 리전 장애 시 자동으로 다른 곳으로 전환하는 것

EC2 Auto Scaling과 AWS Auto Scaling

부하 지표에 따라 인스턴스 수를 자동으로 늘리고 줄이며, 비정상 인스턴스는 교체해 용량을 유지하는 구조.

#1문제 상황

기존 방식은 필요한 서버 수를 미리 정하고 수동으로 인스턴스를 구성 및 유지합니다. 명확한 한계는 트래픽이 갑자기 증가하면 대응이 늦어 서비스 성능이 저하되고, 트래픽이 줄어도 서버를 제때 제거하지 않으면 불필요한 비용 낭비가 지속된다는 점입니다.

#2핵심 질문

CPU 부하나 요청 수에 따라 서버 개수를 자동으로 늘렸다 줄였다 할 수 있을까요?

#3동작 예시

웹 서버의 평균 CPU 사용률이 70%를 넘으면 Auto Scaling이 인스턴스를 2대 추가하고, 20% 이하로 떨어지면 1대를 제거합니다. 또한 헬스 체크에 실패한 인스턴스는 자동으로 새 인스턴스로 교체되므로 항상 정상 개수를 유지합니다.

#4동작 과정

  1. Auto Scaling Group 설정"이 그룹의 최소 인스턴스 수는 2대, 최대는 10대, 원하는 상태는 4대"라는 용량 범위를 정합니다.
  2. 스케일링 정책 정의"CPU 70% 초과 시 2대 추가", "CPU 20% 미만 시 1대 제거" 같은 규칙을 설정합니다. 목표 추적(원하는 메트릭 값을 자동 유지하는 방식) 또는 단계별 스케일링도 가능합니다.
  3. 지속적 유지 및 교체메트릭을 계속 모니터링하면서 인스턴스 개수를 조절하고, 비정상 인스턴스를 감지하면 자동으로 새 인스턴스로 교체합니다.

#5한 줄 요약

수요 변화에 자동으로 반응해 인스턴스 개수를 동적으로 조절하고 장애 인스턴스를 자동 교체해 서비스 용량과 안정성을 지속적으로 유지하는 것

서비스별 스케일링과 캐싱·글로벌 배포

ECS·Lambda·DynamoDB 등 서비스마다 다른 확장 방식과 CloudFront·ElastiCache 같은 캐싱으로 부하를 분산하는 접근.

#1문제 상황

기존 방식은 모든 계층(웹 서버, 애플리케이션, 데이터베이스)을 같은 방식으로 스케일링하거나, 데이터베이스 부하를 주로 서버 개수 증가로만 해결하려 합니다. 한계는 서비스마다 병목이 다른데 일관된 해결책을 쓰면 비용 낭비가 심하고, 응답 시간 개선 효과가 제한적이라는 점입니다.

#2핵심 질문

애플리케이션 계층, 함수, 데이터베이스를 각각 다른 방식으로 확장하면서, 자주 쓰는 데이터는 캐시에 미리 담아 부하를 나눌 수 있을까요?

#3동작 예시

웹 애플리케이션에서 ECS 컨테이너는 CPU 기반으로 스케일링하고, Lambda 함수는 동시 실행 수로, DynamoDB는 온디맨드 빌링으로 자동 확장하며, 자주 조회하는 상품 정보는 ElastiCache(메모리 캐시)에 미리 저장해 데이터베이스 부하를 줄이고, 정적 콘텐츠와 이미지는 CloudFront 엣지 로케이션(전 세계에 분산된 캐시)에 배포해 각 계층의 부하를 효율적으로 분산합니다.

#4동작 과정

  1. 계층별 스케일링 정책 설정ECS는 메모리/CPU 기반, Lambda는 동시 실행 수 제한, DynamoDB는 테이블 용량 또는 온디맨드 모드, RDS는 읽기 복제본 추가 등 서비스 특성에 맞는 규칙을 정합니다.
  2. 캐싱 레이어 배치자주 조회하는 데이터(세션, 상품 정보, 사용자 프로필 등)를 ElastiCache나 DynamoDB DAX(분산 캐시 가속기)에 저장해 데이터베이스 직접 쿼리를 줄입니다.
  3. 글로벌 배포와 라우팅CloudFront CDN으로 정적 콘텐츠를 전 세계 엣지 서버에 캐시하고, Route 53 지연 시간 기반 라우팅으로 동적 콘텐츠를 사용자와 가장 가까운 리전으로 보내 응답 시간을 단축합니다.

#5한 줄 요약

각 계층의 특성에 맞는 스케일링 방식과 다층 캐싱, 글로벌 분산을 조합해 여러 지점의 부하를 동시에 처리하고 사용자 응답 시간을 최소화하는 것

데이터 계층 복제와 리전 간 솔루션

RDS 다중 AZ·읽기 전용 복제본, DynamoDB 글로벌 테이블, S3 복제처럼 데이터를 여러 위치에 복제해 지키는 방법.

#1문제 상황

기존에는 한 곳의 데이터베이스나 스토리지에만 데이터를 저장했다. 만약 그 서버가 고장나거나 리전 전체에 장애가 생기면 데이터에 접근할 수 없었고, 복구하는 데 시간이 오래 걸렸다. 또한 읽기 부하가 증가하면 원본 서버 하나로는 모든 요청을 처리할 수 없었다.

#2핵심 질문

여러 위치에 데이터를 자동으로 복사해 장애가 생겨도 다른 곳에서 즉시 접근할 수 있고, 동시에 읽기 성능도 올릴 수 없을까?

#3동작 예시

RDS 다중 AZ 설정에서 주 데이터베이스(Primary)에 데이터가 쓰여질 때마다 AWS가 자동으로 대기 데이터베이스(Standby)에 동일한 데이터를 동기식으로 복제한다. 주 데이터베이스에 장애가 나면 대기 데이터베이스가 자동으로 승격되어 애플리케이션이 중단 없이 계속 동작한다.

#4동작 과정

  1. 데이터 쓰기 감지애플리케이션이 RDS 주 데이터베이스에 데이터를 쓰면 AWS는 이를 감지한다.
  2. 자동 복제 실행감지된 데이터가 같은 리전 내 다른 가용영역(AZ)의 대기 데이터베이스 또는 다른 리전의 읽기 전용 복제본(Read Replica)으로 자동 복제된다.
  3. 장애 발생 시 자동 전환주 데이터베이스가 다운되면 AWS가 자동으로 대기 데이터베이스를 주 데이터베이스로 승격하거나, 읽기 전용 복제본을 주 데이터베이스로 변환해 서비스를 계속 운영한다.

#5한 줄 요약

여러 위치에 데이터를 자동 복제해 한 곳의 장애가 전체 서비스를 중단시키지 않으면서 동시에 읽기 성능을 향상하는 것

RTO·RPO와 DR 전략·복원력 검증

복구 시간·데이터 손실 허용치를 정하고 백업·파일럿 라이트·웜 스탠바이·다중 사이트 중 전략을 골라 실제 훈련으로 검증하는 일.

#1문제 상황

기존에는 장애가 발생했을 때 얼마나 빨리 복구할 수 있는지, 그리고 최대 얼마나 많은 데이터를 잃어도 되는지를 명확히 정의하지 않았다. 그러다 보니 백업은 있어도 필요한 시점에 복구 계획이 없었고, 실제 장애 상황에서는 패닉에 빠져 복구 시간이 더 오래 걸렸다.

#2핵심 질문

비즈니스 요구에 맞게 복구 목표를 정하고 그에 따라 정확한 전략을 선택한 후 미리 연습해 실제 장애 때 신속하게 복구할 수는 없을까?

#3동작 예시

금융 거래 시스템의 경우 RTO(복구 시간 목표)를 1시간, RPO(데이터 손실 허용치)를 5분으로 정했다면, 이를 달성하기 위해 다중 AZ와 동기 복제본을 사용하는 전략을 선택하고, 매월 한 번씩 실제로 장애 상황을 만들어 1시간 안에 5분 이내의 데이터 손실로 복구하는지 테스트한다.

#4동작 과정

  1. RTO·RPO 정의비즈니스 요구사항에 따라 복구 완료까지 허용 가능한 시간(RTO)과 잃어도 되는 최대 데이터 양(RPO)을 명확히 정의한다.
  2. DR 전략 선택RTO·RPO 목표에 맞춰 백업(느리지만 저비용), 파일럿 라이트(테스트 환경 미리 구성), 웜 스탠바이(대기 환경 항상 최신 상태 유지), 다중 사이트(완벽한 이중화) 중 하나를 선택한다.
  3. 정기적 복원력 검증선택한 전략으로 실제 복구가 RTO·RPO 목표를 충족하는지 정기적으로 테스트해 계획의 실효성을 입증한다.

#5한 줄 요약

비즈니스 목표에 맞는 복구 시간과 데이터 손실 허용치를 정의하고 그에 걸맞는 방어 전략을 선택한 후 주기적으로 검증해 장애 발생 시 예측 가능하게 대응하는 것

네트워크 보안 구성 - 보안 그룹·NACL·라우팅·VPC

VPC 안에서 보안 그룹(인스턴스 단위 상태 저장 방화벽), 네트워크 ACL(서브넷 단위 무상태 필터), 라우팅 테이블을 조합해 트래픽이 어디로 오갈 수 있는지를 결정하는 기본 방어선이다.

#1문제 상황

기존에는 인터넷을 통해 서버로 향하는 모든 트래픽이 바로 도착했다. 방화벽이 없으면 누구든지 서버로 접근할 수 있었고, 서버 간 통신도 제어할 수 없었다. 또한 어떤 네트워크 주소가 어디로 가야 하는지 경로를 명확히 결정할 방법이 없었다.

#2핵심 질문

VPC 내에서 들어오는 트래픽과 나가는 트래픽을 여러 계층에서 필터링하고, 서버 간의 통신도 제어하면서 동시에 데이터 흐름의 경로도 명확히 정할 수 없을까?

#3동작 예시

EC2 인스턴스가 있는 VPC에서 보안 그룹은 인스턴스 개별 수준에서 누가 들어올 수 있는지(포트 80은 모두 허용, SSH는 특정 IP만)를 결정하고, 네트워크 ACL은 그 인스턴스가 있는 서브넷 수준에서 들어오고 나가는 트래픽을 먼저 필터링하며, 라우팅 테이블은 서브넷 내 트래픽이 인터넷 게이트웨이로 갈지 NAT 게이트웨이로 갈지를 결정한다.

#4동작 과정

  1. VPC 생성 및 서브넷 분할VPC 내에 공개 서브넷과 프라이빗 서브넷을 나누어 역할을 분리한다.
  2. 보안 그룹과 네트워크 ACL 설정보안 그룹으로 인스턴스가 어떤 포트로 통신을 받을지 결정하고, 네트워크 ACL로 서브넷 경계에서 상태 비저장 필터링(무조건 규칙 검사)을 수행한다.
  3. 라우팅 테이블 구성각 서브넷의 라우팅 테이블에서 트래픽이 인터넷 게이트웨이(공개), NAT 게이트웨이(프라이빗에서 나가기), VPN 연결 등으로 어디로 향할지를 명시한다.

#5한 줄 요약

보안 그룹(상태 저장, 인스턴스 단위)과 네트워크 ACL(상태 비저장, 서브넷 단위), 라우팅 테이블을 조합해 VPC 경계에서 허용할 트래픽과 거절할 트래픽을 명확히 제어하고 데이터 흐름의 경로를 결정하는 것

WAF·Shield·Network Firewall로 만드는 심층 방어

애플리케이션 계층 공격은 WAF 규칙으로, DDoS는 Shield로, VPC 경계 트래픽은 Network Firewall로 막아 여러 겹의 방어를 쌓는 방식이다.

→ 11-01 참조

#1문제 상황

기존에는 공격이 여러 계층에서 발생했다. SQL 인젝션이나 크로스 사이트 스크립팅(XSS) 같은 애플리케이션 계층 공격은 방화벽으로 막을 수 없었고, DDoS 대량 접속은 서버 용량을 초과시켰으며, VPC 경계의 이상 트래픽도 탐지하기 어려웠다.

#2핵심 질문

애플리케이션 계층, 네트워크 계층, VPC 경계 각각에서 다른 종류의 공격을 동시에 차단할 수 있을까?

#3동작 예시

웹 애플리케이션이 CloudFront 뒤에 있을 때, WAF는 CloudFront 앞에서 요청의 헤더와 바디를 검사해 SQL 인젝션이나 XSS 패턴을 찾아 차단하고, Shield는 같은 계층에서 DDoS 대역폭 공격을 감지해 흡수하며, VPC 내로 진입하기 전 Network Firewall이 IPS(침입 방지) 규칙으로 알려진 악성 패턴을 추가로 필터링한다.

#4동작 과정

  1. 애플리케이션 계층 방어WAF 규칙으로 HTTP/HTTPS 요청의 내용을 검사해 악의적인 패턴(SQL 커맨드, 스크립트 코드 등)이 있으면 차단한다.
  2. DDoS 계층 방어AWS Shield가 알려진 DDoS 공격 서명을 인식하고 CloudFront 또는 ALB에서 그 트래픽을 필터링해 실제 서버까지 도달하지 못하게 한다.
  3. VPC 경계 방어Network Firewall이 VPC 경계를 통과하는 모든 트래픽을 상태 저장으로 검사하고, 알려진 악성 IP나 도메인 목록(Threat Intelligence)과 대조해 차단한다.

#5한 줄 요약

WAF로 애플리케이션 공격을, Shield로 DDoS 공격을, Network Firewall로 VPC 경계의 이상 트래픽을 각각 차단해 여러 계층의 방어선을 동시에 구성하는 것

데이터 보호 - 분류·KMS·CloudHSM·ACM과 PKI

데이터를 민감도로 분류한 뒤 KMS나 CloudHSM 키로 저장 시 암호화하고, ACM 인증서로 전송 구간을 암호화해 보호하는 체계다.

#1문제 상황

기존에는 모든 데이터를 같은 수준으로 보관했다. 개인정보, 결제 정보, 공개 정보가 구분 없이 같은 서버에 저장되었고, 어떤 키로 암호화할지도 정하지 않았다. 암호화 키가 노출되면 모든 데이터가 한 번에 복호화될 위험이 있었다.

#2핵심 질문

데이터의 민감도에 따라 분류한 후 각각에 맞는 암호화 방식과 키 관리 방법을 적용하면 어떻게 될까?

#3동작 예시

전자상거래 서비스에서 고객의 신용카드 번호는 최고 등급 민감 데이터로 분류해 CloudHSM 전용 하드웨어 보안 모듈이 관리하는 키로 암호화하고, 개인정보는 AWS KMS(Key Management Service) 마스터 키로 암호화하며, 상품 목록 같은 공개 정보는 암호화하지 않는다. 또한 HTTPS 통신 시에는 ACM 인증서로 전송 구간 암호화를 한다.

#4동작 과정

  1. 데이터 분류데이터를 최고 등급(신용카드·비밀번호), 중간 등급(개인정보·거래 기록), 공개 정보로 분류한다.
  2. 저장 시 암호화 적용KMS 마스터 키나 CloudHSM 같은 관리형 또는 전용 하드웨어 보안 모듈로 데이터를 암호화해 저장한다.
  3. 전송 구간 암호화ACM 인증서로 HTTPS/TLS를 설정해 클라이언트와 서버 간 통신 데이터를 암호화한다.

#5한 줄 요약

데이터를 민감도로 분류한 뒤 저장 시에는 KMS/CloudHSM으로, 전송 시에는 ACM 인증서로 각각 암호화해 데이터 유출이나 도청으로부터 보호하는 것

머신 자격증명 회전 자동화

애플리케이션이 쓰는 DB 비밀번호·API 키 같은 자격증명을 Secrets Manager 등으로 주기적으로 자동 교체해 유출 위험을 줄이는 작업이다.

#1문제 상황

기존에는 애플리케이션이 데이터베이스 비밀번호나 API 키를 하드코딩하거나 설정 파일에 저장했다. 이 자격증명이 한 번 유출되면 공격자가 무기한 사용할 수 있었고, 주기적으로 바꿀 방법도 없었다. 자격증명을 변경하려면 각 서버의 설정을 수동으로 수정해야 했다.

#2핵심 질문

애플리케이션이 사용하는 자격증명을 중앙에서 자동으로 주기적으로 교체해 한 번의 유출이 미치는 범위를 제한할 수 없을까?

#3동작 예시

Secrets Manager에 데이터베이스 비밀번호를 등록하고 회전 주기를 30일로 설정하면, AWS가 매달 자동으로 새로운 비밀번호를 생성해 RDS 데이터베이스에서 비밀번호를 변경하고, Secrets Manager에 저장된 값을 업데이트한다. 애플리케이션은 비밀번호를 직접 저장하지 않고 Secrets Manager에 요청해 현재 비밀번호를 얻으므로, 자격증명 변경에 대응할 필요가 없다.

#4동작 과정

  1. Secrets Manager에 자격증명 저장데이터베이스 비밀번호, API 키 등을 Secrets Manager에 중앙 집중식으로 저장한다.
  2. 회전 정책 설정회전 주기(예: 30일)와 회전 실행 람다(Lambda) 함수를 정의해 자동 교체 프로세스를 등록한다.
  3. 자동 회전 실행AWS가 정기적으로 새 자격증명을 생성해 리소스에 적용하고 Secrets Manager를 갱신하면, 애플리케이션은 항상 최신 자격증명을 사용한다.

#5한 줄 요약

자격증명을 Secrets Manager 같은 중앙 저장소에서 자동으로 주기적 교체해 유출된 자격증명의 유효 기간을 제한하는 것

위협·취약점 탐지와 Security Hub 기반 다계정 보안 제어

GuardDuty·Inspector 등이 찾아낸 위협과 취약점을 Security Hub로 모아 여러 계정의 보안 상태를 한 곳에서 점검하고 통제하는 구조다.

#1문제 상황

기존에는 여러 AWS 계정을 운영할 때 각 계정의 보안 상태를 따로 확인해야 했다. GuardDuty가 악성 활동을 탐지하고, Inspector가 인스턴스 취약점을 찾아도 결과가 분산되어 있었다. 한 계정에서 심각한 위협이 있어도 다른 계정에서 놓칠 수 있었고, 조직 전체의 보안 정책을 중앙에서 강제할 방법이 없었다.

#2핵심 질문

여러 AWS 계정에서 감지된 위협과 취약점을 한 곳으로 모아 조직 차원에서 실시간으로 보안 상태를 파악하고 통제할 수 없을까?

#3동작 예시

보안 조직이 AWS Organizations 관리 계정에 Security Hub를 활성화하고 모든 멤버 계정의 GuardDuty, Inspector, Config 결과를 자동 통합하도록 설정하면, Security Hub 대시보드에서 조직 전체의 위협(악성 IP 접근 시도, 비정상 API 호출 등)과 취약점(보안 그룹 과도한 개방, 미지원 OS 등)을 한눈에 본다. 심각도가 높은 항목은 자동으로 SNS 알람을 보내고, 규정 미준수 리소스는 Config 규칙으로 자동 교정한다.

#4동작 과정

  1. 위협 탐지GuardDuty가 VPC 플로우 로그와 CloudTrail 로그를 분석해 비정상 네트워크 활동, 의심 API 호출, 알려진 악성 IP 접근을 탐지한다.
  2. 취약점 탐지Inspector가 EC2 인스턴스와 컨테이너 이미지를 스캔해 알려진 CVE(보안 약점) 및 네트워크 노출 포인트를 발견한다.
  3. 중앙 집계 및 통제Security Hub가 모든 계정의 위협과 취약점을 모아 심각도 순으로 정렬하고, 자동화 규칙으로 고위험 항목에 대해 알람, 차단, 또는 자동 수정을 실행한다.

#5한 줄 요약

GuardDuty·Inspector 같은 탐지 도구들이 찾아낸 위협과 취약점을 Security Hub로 중앙 집계해 여러 AWS 계정의 보안 상태를 한 곳에서 모니터링하고 자동 통제하는 것

보안 감사와 이상 이벤트 알림

CloudTrail·Config로 누가 무엇을 바꿨는지 기록을 남기고, 규정에 어긋나거나 수상한 이벤트가 생기면 자동으로 알림을 보내는 감사 체계다.

→ 11-05 참조

#1문제 상황

기존에는 AWS 리소스 변화를 추적하려면 로그를 수동으로 확인하거나, 문제가 발생한 후에 원인을 파악해야 한다. 누가 무엇을 언제 바꿨는지 알기 어렵고, 규정 위반 사항을 즉시 감지할 수 없어 사후 대응만 가능하다.

#2핵심 질문

클라우드에서 모든 인프라 변화를 자동으로 기록하고, 규정 위반이나 비정상 이벤트를 실시간으로 감지해 알림을 보낼 수 있을까?

#3동작 예시

CloudTrail은 AWS API 호출 기록 시스템으로, 누군가 EC2 인스턴스를 삭제하거나 보안 그룹을 변경하는 순간 그 API 호출·요청자·실행 시간이 자동 기록된다. AWS Config는 리소스 설정을 추적해 규정 규칙(예: S3 버킷은 암호화되어야 한다)에 어긋나면 위반으로 표시한다. EventBridge가 이 규정 위반 이벤트를 감시하다가 감지하면, 자동으로 SNS 알림을 보내거나 Lambda 함수를 실행한다.

#4동작 과정

  1. 기록 단계CloudTrail이 모든 API 호출을 기록하고, Config가 리소스의 구성 상태 변화를 감시한다.
  2. 규칙 평가 단계Config 규칙에 비춰 리소스를 평가하고, 규정 위반 사항을 표시한다.
  3. 자동 알림 단계EventBridge가 규정 위반 이벤트를 감지하면 즉시 SNS·Lambda·Slack 등으로 알림을 보낸다.

모든 인프라 변화를 기록하고 규정 준수 여부를 자동 평가해서 위반이나 이상을 실시간으로 알리는 감사 체계

#1문제 상황

기존에는 클라우드와 온프레미스 환경이 분리되어 있어서, 배포 파이프라인을 따로 구축해야 한다. 같은 코드를 배포해도 클라우드 배포 프로세스와 온프레미스 배포 프로세스가 다르고, 모니터링·로그 확인도 별개 시스템을 써야 해 관리 복잡도가 높다.

#2핵심 질문

클라우드와 온프레미스 서버를 하나의 배포 파이프라인으로 통합 관리할 수 있을까?

#3동작 예시

#4동작 과정

  1. 에이전트 설정 단계온프레미스 서버들에 CodeDeploy 에이전트를 설치하고, AWS 자격증명(IAM 역할)을 부여해 CodeDeploy와 통신하도록 준비한다.
  2. 파이프라인 통합 단계같은 CodePipeline 안에 클라우드와 온프레미스 배포 그룹을 모두 추가하고, 각 배포 그룹이 실행할 배포 구성(배포 속도, 인스턴스 수)을 정의한다.
  3. 단일 배포 실행 단계코드 커밋이나 수동 트리거 시, 파이프라인이 클라우드와 온프레미스 서버들에 동시에 배포를 실행한다.

비슷한 서비스 고르기와 비용 최적화

기능이 겹치는 AWS 서비스 중 요구사항과 비용에 맞는 것을 고르는 판단 기준을 정리한다.

#1문제 상황

AWS에는 비슷한 기능을 제공하는 여러 서비스가 존재한다(로드 밸런서 3종류, 데이터베이스 여러 종류). 개발자가 각 서비스의 차이와 가격 구조를 정확히 모르면 성능 요구사항에 안 맞는 서비스를 선택하거나, 불필요한 비용을 낸다.

#2핵심 질문

같은 문제를 해결하는 여러 AWS 서비스 중 상황과 비용에 맞는 최적의 서비스를 어떻게 판단할까?

#3동작 예시

로드 밸런싱의 예: ALB는 HTTP/HTTPS 기반 요청을 URL·호스트명·경로로 구분 라우팅한다(웹 애플리케이션용). NLB는 TCP/UDP 프로토콜 수준 초고속 처리(게임·IoT·극도로 낮은 지연시간 필요)가 필요할 때다. CLB는 단순 TCP/SSL 로드 밸런싱만 필요할 때다. 데이터베이스의 예: RDS는 SQL 기반 정형 데이터와 트랜잭션 일관성이 중요할 때. DynamoDB는 NoSQL, 키-값 기반 고속 조회와 자동 스케일링이 필요할 때다.

#4동작 과정

  1. 요구사항 분석 단계데이터 형태(정형/비정형), 성능 요구(초당 요청 수, 허용 지연시간), 일관성 수준, 비용 민감도를 파악한다.
  2. 후보 서비스 비교 단계각 서비스의 처리 모델, 가격 구조, 관리 복잡도를 정리해 거른다(예: 관리형 vs 자체 관리, 종량제 vs 예약).
  3. 선택 및 최적화 단계선택한 서비스의 구성 파라미터(인스턴스 크기, 처리량, 자동 스케일링)를 조정해 성능과 비용을 균형 맞힌다.

#5한 줄 요약

#1문제 상황

시험 준비할 때는 단일 주제 기반으로 각 도메인을 따로 학습한다. 하지만 실제 시험에서는 CI/CD, 모니터링, 보안, 배포가 한 시나리오에 섞여 나온다. 각 도메인 지식은 있어도 복수 기술을 상황에 맞춰 통합해서 적용하는 능력이 부족하면 문제를 풀기 어렵다.

#2핵심 질문

복수 도메인이 섞인 실무 시나리오 문제를 어떻게 체계적으로 분석하고 풀까?

#4동작 과정

  1. 시나리오 분해 단계문제를 읽고 숨겨진 요구사항들을 도메인별로 분류한다(예: "배포 자동화" → 도메인 1, "보안 감사" → 도메인 6). 각 도메인에서 요구하는 핵심 기술을 목록화한다.
  2. 의존성 파악 단계도메인 간 순서 관계를 파악한다(예: 배포 전에 보안 검사가 먼저 실행되어야 함). 어떤 기술이 다른 기술의 입력이 되는지 추적한다.
  3. 통합 솔루션 제시 단계각 도메인의 서비스와 기술을 선택하고, 파이프라인 흐름 안에서 어떻게 연결되는지 구체적으로 설명한다(예: CodeCommit → CodeBuild → 보안 검사 → CodeDeploy → CloudWatch + CloudTrail).
