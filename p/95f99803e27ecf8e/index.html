GuardDuty가 푸는 문제와 에이전트리스 탐지 모델

GuardDuty는 AWS 계정·워크로드·데이터에서 이미 만들어지는 로그와 이벤트를 대신 읽어 악성 활동을 찾아주는 관리형 위협 탐지 서비스로, 기본 탐지에는 별도 설치가 필요 없다.

1상대의 출발점 확인

AWS 계정과 워크로드를 운영할 때 API 호출, 네트워크 연결, DNS 쿼리 같은 활동들이 끝없이 만들어진다. 이 데이터들을 모니터링해서 악성 활동(비정상 접속, 권한 오용, 악성 도메인 접근 등)을 찾아내려면 보안팀이 직접 로그를 분석 시스템에 연결하고 탐지 규칙을 짜야 한다. 이 과정은 시간과 전문 지식이 많이 들고, 설정이 복잡해서 놓치기 쉽다.

2질문 제기

AWS 계정과 워크로드에서 이미 만들어지는 로그를 AWS 자체가 읽어서 악성 활동을 자동으로 찾아줄 수는 없을까?

3구조적 핵심 예시

GuardDuty는 CloudTrail이 기록한 모든 API 호출 로그를 자동으로 흡수해서 분석한다. 예를 들어, IAM 사용자가 평소와 다른 시간에 다른 리전에서 대량의 EC2 인스턴스 정보를 조회 요청하면, GuardDuty는 이 패턴을 비정상으로 인지해서 "발견(finding)"이라는 경고를 생성한다. 이 모든 과정이 에이전트나 추가 설치 없이 AWS 콘솔에 GuardDuty를 켜는 것만으로 시작된다.

4단계별 동작 과정

  1. 로그 자동 수집CloudTrail, VPC Flow Logs, DNS 로그 같은 기존 AWS 로그를 GuardDuty가 자동으로 가져온다.
  2. 패턴 분석AWS가 학습한 머신러닝 모델과 알려진 위협 정보를 사용해 이상한 API 호출, 비정상 네트워크 흐름, 의심 도메인 접근을 감지한다.
  3. 발견 생성위협이 감지되면 심각도와 함께 발견(finding) 데이터를 생성해 콘솔이나 연결된 SIEM(보안 정보 관리 시스템)으로 보낸다.

3구조적 핵심 예시

서울(ap-northeast-2) 리전에서 GuardDuty를 켜면 "ap-northeast-2"라는 디텍터 ID가 생기고, 이 리전의 모든 CloudTrail 이벤트와 VPC 로그를 이것이 담당한다. 같은 AWS 계정이라도 도쿄(ap-northeast-1) 리전에서 GuardDuty를 따로 켜면 "ap-northeast-1"이라는 별도의 디텍터 ID가 만들어져 그 리전만 독립적으로 모니터링한다.

4단계별 동작 과정

  1. 리전 선택AWS 콘솔에서 사용 중인 각 리전으로 이동한다.
  2. 리전마다 디텍터 생성리전마다 GuardDuty를 켜면 그 리전의 고유한 디텍터 ID가 생긴다.
  3. 독립적 탐지 운영각 디텍터가 해당 리전의 로그만 읽고 발견을 생성해서, 리전별로 위협을 따로 관리한다.

GuardDuty 콘솔을 열면 "계정"이라는 개념부터 시작한다. 하나의 AWS 계정이 있고, 그 안에서 여러 보호 계획(예: EC2, RDS, S3 보호)을 켤 수 있다. 각 보호 계획이 켜지면 그 계획에 속한 기능(feature)들(예: 런타임 모니터링, Kubernetes 이상 탐지)이 동작하기 시작한다. 이 기능들이 감지한 원본 신호(시그널, 예: 비정상 API 호출)를 종합해서 최종 발견(finding, 예: "루트 자격증명으로 비정상 로그인")을 만든다.

  2. 보호 계획 선택EC2, Lambda, RDS, S3 같은 리소스별 보호 계획을 개별적으로 켤 수 있다.
  3. 기능→시그널→발견의 연쇄각 보호 계획 안의 기능(feature)들이 로그를 분석해 시그널(신호)을 감지하고, 여러 시그널을 조합해 최종 발견(finding)으로 만든다.

  3. DNS 로그 분석EC2 인스턴스에서 조회한 도메인을 읽어 알려진 악성 도메인, DGA(동적 도메인 생성) 도메인 접근 같은 C&C(명령 제어) 통신을 탐지한다.

3구조적 핵심 예시

  2. API feature 이름 규칙 정의GuardDuty API는 각 기능을 고유한 이름(예: "GUARDDUTY_FINDINGS", "S3_DATA_EVENTS", "EKS_RUNTIME_MONITORING")으로 식별하여, 프로그래밍 방식의 일괄 제어를 가능하게 합니다.

  1. EBS 스냅샷 생성GuardDuty가 대상 EC2 인스턴스의 EBS 볼륨을 지정하면, AWS가 현재 상태의 스냅샷(포인트 인 타임 복사본)을 생성합니다. 이 작업 중 인스턴스는 계속 운영됩니다.
  2. 스냅샷 마운트 및 악성코드 검사GuardDuty 서비스가 생성된 스냅샷을 자신의 임시 환경에 마운트(연결)하고, 알려진 악성코드의 서명(파일 패턴)과 비교 검사를 수행합니다.
  3. 결과 보고 및 스냅샷 삭제검사 결과(악성코드 발견 여부)를 GuardDuty 발견(Finding)으로 기록하고, 임시 스냅샷을 삭제해서 스토리지 비용을 청소합니다.

1상대의 출발점 확인

기존 악성코드 검사는 사용자가 수동으로 요청하거나 정해진 시간에 자동 실행되는 방식입니다. 한계는 의심스러운 활동이 감지되었을 때 즉시 파일 검사를 시작할 수 없다는 점으로, 위협이 드러났을 때의 신속한 대응이 어렵습니다.

2질문 제기

의심 활동 발견 시 자동으로 악성코드 검사를 시작해서 감염 여부를 신속하게 확인할 수 있을까?

3구조적 핵심 예시

GuardDuty가 Runtime Monitoring이나 다른 탐지 기능에서 의심 활동(비정상 프로세스, 통신 시도, 파일 쓰기 등)을 발견하면 자동으로 해당 EC2 인스턴스의 EBS 악성코드 스캔을 트리거하고, 동시에 사용자는 필요시 언제든 수동으로 스캔을 요청할 수 있습니다.

4단계별 동작 과정

  1. GuardDuty 자동 스캔 트리거Runtime Monitoring, Network Activity 분석 등에서 의심 활동을 발견하면, GuardDuty가 자동으로 해당 EC2 인스턴스의 EBS 볼륨 악성코드 스캔을 즉시 시작합니다. 이를 GuardDuty-initiated scan이라고 합니다.
  2. 온디맨드 스캔 요청사용자가 수동으로 GuardDuty 콘솔에서 EC2 인스턴스를 지정하고 스캔 버튼을 누르면, 별도의 스캔 작업이 즉시 시작됩니다. 정기 점검이나 응급 진단이 필요할 때 사용됩니다.
  3. 스캔 결과 분석 및 대응모든 스캔의 결과는 GuardDuty 발견(Finding)으로 생성됩니다. 악성코드 감염이 발견되면 심각도와 파일 정보를 포함한 상세 발견이 보고되어 보안 팀이 격리, 제거 등의 대응을 수행합니다.

1상대의 출발점 확인

기존에는 전체 EC2 인스턴스나 스토리지 전체를 모두 스캔하거나, 아니면 아무것도 스캔하지 않는 이진 선택만 가능했습니다. 이렇게 되면 중요하지 않은 임시 인스턴스까지 스캔해서 비용을 낭비하거나, 반대로 보호가 필요한 리소스를 빠뜨릴 수 있습니다. 또한 한 번 감염된 스냅샷이 남으면 실수로 그것을 복원할 때 악성 파일까지 함께 되살아나는 문제가 있습니다.

2질문 제기

어떻게 스캔 대상을 세밀하게 선별하고, 감염 이력을 남겨두면서도 실수로 감염 데이터를 복원하지 않을 수 있을까요?

3구조적 핵심 예시

GuardDuty는 EC2 인스턴스의 태그를 읽어서 스캔 대상을 결정합니다. 예를 들어 "scan=true"라는 태그가 붙은 인스턴스만 스캔하고, "scan=false"라는 태그가 붙은 인스턴스는 건너뜁니다. 동시에 스냅샷도 따로 설정해서, 감염된 스냅샷에 "infected" 표시를 남기되 자동 삭제는 하지 않게 할 수 있습니다.

4단계별 동작 과정

  1. 태그 기반 필터링각 EC2 인스턴스의 태그를 확인하고, 포함(include) 또는 제외(exclude) 태그가 있는지 검사합니다. 지정된 태그와 값이 일치하는 인스턴스만 스캔 대상에 포함됩니다.
  2. 스냅샷 보존 정책 설정감염된 파일이 발견된 EBS 스냅샷을 언제 자동 삭제할지, 아니면 수동으로만 삭제할지 정합니다. 보존 기간(예: 7일)을 설정하면 그 기간 동안 감염 증거를 유지할 수 있습니다.
  3. 스캔 커버리지 범위 확정특정 가용 영역(AZ)만 스캔하거나 전체 리전을 스캔할지, 신규 인스턴스가 자동으로 스캔 대상에 포함될지 여부를 정합니다.

  2. 탐지 결과 집계스캔 완료 후 "clean" 또는 "malware found" 결과를 인스턴스·볼륨·파일 경로별로 상세 기록해 CloudWatch 대시보드에 표시합니다.

스캔 결과를 얻기만 해서는 의미가 없습니다. 악성 파일을 탐지했으면 그 파일을 격리하거나, 알림을 보내거나, 애플리케이션이 그 파일을 사용하지 않게 해야 합니다. 그런데 스캔 결과가 GuardDuty 콘솔에만 남으면, 다른 시스템과 연동해서 자동 대응을 할 수 없습니다.

2질문 제기

S3 스캔 결과를 GuardDuty 밖의 다른 시스템과 자동으로 공유해서 후속 조치를 어떻게 자동화할까요?

3구조적 핵심 예시

GuardDuty가 S3 객체를 스캔하면, 결과를 세 가지 방식으로 내보냅니다. (1) 객체 자체에 "guardduty:malware-scan-result=clean" 같은 태그를 붙여서, 애플리케이션이 다운로드 전에 태그를 확인하고 거부할 수 있게 합니다. (2) EventBridge 이벤트로 스캔 완료 신호를 보내서, Lambda 함수나 SNS 알림을 트리거합니다. (3) CloudWatch 메트릭으로 시간대별 탐지 건수를 집계합니다.

4단계별 동작 과정

  1. 객체 태그 기록스캔 완료 후 대상 객체에 검사 결과(clean/malware)를 태그로 기록합니다. 애플리케이션은 S3에서 객체를 받을 때 이 태그를 먼저 확인하고, malware 태그가 있으면 거부합니다.
  2. EventBridge 이벤트 발행GuardDuty는 스캔 완료 이벤트를 EventBridge로 보내고, 구독 중인 Lambda, SNS, SQS 등으로 자동 전달됩니다. 예를 들어 악성 파일 탐지 시 관리자 메일 발송이나 자동 격리 프로세스를 시작할 수 있습니다.
  3. CloudWatch 지표 기록시간 단위로 스캔한 객체 수, 탐지된 악성 파일 수를 CloudWatch 메트릭으로 남겨서, 대시보드에서 추이를 모니터링하고 임계값 기반 알람을 설정합니다.

Malware Protection for AWS Backup: 복구 지점 스캔

백업으로 만든 복구 지점을 복원 전에 검사해, 감염된 데이터를 되살리는 사고를 막는 기능이다.

1상대의 출발점 확인

랜섬웨어 공격이나 악성 코드 감염이 발생해서 데이터베이스나 볼륨을 복구해야 할 때, AWS Backup에 저장된 복구 지점(recovery point)을 되살린다고 가정합시다. 그런데 그 복구 지점 자체가 감염된 데이터를 담고 있다면, 복원하는 순간 악성 코드가 다시 활동을 시작합니다. 감염된 백업을 확인할 방법이 없으면, 깨끗한 데이터를 되찾으려다 오염된 데이터를 되살리게 됩니다.

2질문 제기

백업 복구 지점에 악성 코드가 들어 있지는 않은지, 복원하기 전에 어떻게 확인할까요?

3구조적 핵심 예시

GuardDuty는 AWS Backup으로 생성된 복구 지점(EBS 스냅샷, RDS 데이터베이스 스냅샷 등)을 정기적으로 스캔합니다. 복원 전에 해당 복구 지점의 스캔 결과를 확인할 수 있고, 악성 파일이 발견되었다면 그 복구 지점 사용을 회피하고 더 이전의 깨끗한 지점을 선택할 수 있습니다.

4단계별 동작 과정

  1. Backup 복구 지점 식별GuardDuty는 AWS Backup에서 관리하는 모든 복구 지점 목록을 주기적으로 받아서, 스캔 대상 목록에 추가합니다.
  2. 지점별 악성 코드 스캔각 복구 지점의 스냅샷을 임시로 연결해서, GuardDuty가 파일 시스템을 스캔하고 악성 코드 여부를 검사합니다.
  3. 스캔 결과 기록 및 복원 차단스캔 결과(clean 또는 malware detected)를 GuardDuty 콘솔과 CloudWatch에 기록하고, 악성 파일이 발견된 복구 지점은 복원 시도 시 경고 또는 거부합니다.

Extended Threat Detection과 공격 시퀀스

여러 개별 신호를 하나로 엮어 다단계 공격 흐름을 critical 등급 '공격 시퀀스' 발견으로 만들어 주는 GuardDuty 기본 기능이다.

1상대의 출발점 확인

GuardDuty가 개별 위협 신호(예: 비정상적인 API 호출, 의심 IP 접속)를 각각 탐지한다고 해도, 그것들이 실제로 연결된 하나의 공격 캠페인인지, 아니면 무관한 사건들인지 구분할 수 없습니다. 많은 경고가 쌓이면 보안 팀의 번아웃이 생기고, 진짜 공격을 놓칠 수 있습니다.

2질문 제기

여러 개의 개별 경고를 어떻게 하나의 다단계 공격 흐름으로 엮어서 중대 위협으로 판정할까요?

3구조적 핵심 예시

GuardDuty는 시간대, 출처, 영향 범위를 분석해서 연관 있는 경고들을 묶습니다. 예를 들어 "의심 IP에서 어떤 IAM 사용자가 로그인 시도" → "그 사용자가 민감한 S3 버킷에 접근" → "평소와 다른 리전에서 EC2 인스턴스 생성" 이 세 개 경고가 1시간 내에 같은 공격자 IP에서 나왔다면, 이를 하나의 "공격 시퀀스(Attack Sequence)"로 묶어서 CRITICAL 등급 발견으로 표시합니다.

4단계별 동작 과정

  1. 개별 신호 수집GuardDuty의 각 탐지 엔진(IP 평판, API 비정상 분석, 리소스 접근 패턴 등)이 개별 위협 신호를 생성합니다.
  2. 신호 상관분석 및 엮기시간 순서, IP 출처, 영향받은 리소스, 사용자 정보 등을 비교해서, 논리적으로 연결된 신호들을 그룹화합니다.
  3. 공격 시퀀스 생성 및 등급 상향연관된 신호가 3개 이상이고 시간 간격이 일정 범위 내라면, 이를 하나의 "공격 시퀀스" 발견으로 만들고 등급을 CRITICAL로 설정해서 보안 팀의 주의를 집중시킵니다.

Custom Detection Rules: 규칙·시그널·Live와 Dry run

AWS가 제공하는 탐지 규칙을 계정에 켜서 내 환경에 맞는 발견을 만들되, Dry run으로 먼저 영향을 시험해 볼 수 있는 기능이다.

3구조적 핵심 예시

  1. 규칙 선택 및 설정AWS가 제공하는 Custom Detection Rules 중에서 필요한 규칙을 선택하고 조직에 맞게 매개변수를 조정합니다.
  2. Dry run 실행규칙을 테스트 모드로 실행해서 결과를 수집하고, 생성되는 발견의 정확도와 양을 검토합니다.

  2. RDS 이상 접근 조치데이터베이스의 비정상적인 로그인 시도나 대량 쿼리(unusual login patterns, brute force attempts 등)를 탐지하면 DB 계정의 비밀번호를 변경하고 의심스러운 세션을 강제 종료합니다.
  3. Lambda 함수 조치Lambda 함수의 비정상적인 실행 패턴(unusual execution behavior, excessive resource usage 등)을 감지하면 해당 함수 버전을 비활성화하고 실행 로그와 메트릭을 분석합니다.

기존에는 AWS 리소스에 접근할 때 누가 어떤 권한을 가졌는지를 IAM 정책으로 설정했다. 하지만 GuardDuty처럼 AWS 서비스 자체가 고객 계정의 로그 데이터에 접근해야 할 때는 어떻게 권한을 줄 것인가 하는 문제가 생긴다. 동시에 팀 멤버가 GuardDuty를 활성화·비활성화·설정 변경할 수 있는 권한도 별도로 관리해야 한다.

2질문 제기

GuardDuty가 계정의 로그를 읽을 수 있게 하고, 동시에 팀 멤버들이 GuardDuty만 조작하도록 권한을 나누려면 어떻게 해야 할까?

3구조적 핵심 예시

GuardDuty 소유자가 "GD-read-only" 정책을 만들어 보안 팀에 할당하면, 그 팀은 GuardDuty 대시보드를 볼 수만 있고 설정 변경은 못 한다. 동시에 GuardDuty 서비스 자체는 "GuardDutyServiceRole"이라는 서비스 연결 역할을 통해 고객의 VPC 플로우 로그, CloudTrail, S3 등을 읽을 수 있는 권한을 받는다.

4단계별 동작 과정

  1. IAM 자격 증명 기반 정책어떤 사용자나 역할이 GuardDuty API(CreateDetector, GetFindings 등)를 호출할 수 있는지를 정의한다. 예를 들어 개발팀은 GetFindings만 허용하고 DeleteDetector는 불가능하게 제한한다.
  2. AWS 관리형 정책AWS가 미리 만들어놓은 "GuardDutyReadOnlyAccess", "GuardDutyFullAccess" 같은 정책을 사용자나 역할에 붙여서 권한 관리를 단순화할 수 있다.
  3. 서비스 연결 역할(SLR)GuardDuty 서비스 자체가 CloudTrail, VPC 플로우 로그, S3에 접근하기 위해 사용하는 역할로, 처음 GuardDuty를 활성화할 때 AWS가 자동으로 만든다.

5본질 요약

데이터 보호·옵트아웃·규정 준수·복원력과 CloudTrail 감사

GuardDuty가 분석하는 데이터의 암호화·보관 방식과 서비스 개선 목적 사용 옵트아웃, 규정 준수 프로그램, 다중 AZ 복원력, 그리고 모든 API 호출을 CloudTrail로 남겨 감사하는 방법.

1상대의 출발점 확인

기존에는 보안팀이 GuardDuty 탐지 결과를 받으면 그것이 어떻게 저장되고 누가 접근할 수 있는지 명확하지 않았다. GuardDuty가 수집하는 데이터(로그 분석 결과, 메타데이터)가 AWS 내부에서 어떻게 암호화·보관되는지 알 수 없으면 규정 준수(GDPR, PCI-DSS 등)를 증명하기 어렵다. 또한 GuardDuty 서비스 개선을 위해 고객 데이터를 AWS가 사용하는지 여부도 제어할 수 없었다.

2질문 제기

GuardDuty가 분석하는 데이터의 암호화·보관 방식을 확인하고, 서비스 개선 목적 사용을 거부하며, 모든 API 호출을 감사할 수 있을까?

3구조적 핵심 예시

고객이 CloudTrail을 켜면 GuardDuty CreateDetector, UpdateThreatIntelSet 같은 모든 API 호출이 기록되어 "누가, 언제, 뭘 했는가"를 추적할 수 있다. 동시에 GuardDuty는 데이터를 AWS KMS 키로 암호화해서 저장하고, 고객이 AWS 콘솔의 "Data Protection" 설정에서 "Opt-out" 버튼을 누르면 서비스 개선 목적 사용을 거부할 수 있다.

4단계별 동작 과정

  1. 암호화 및 보관GuardDuty가 분석 결과와 메타데이터를 기본적으로 AWS 관리 키로 암호화하고, 고객이 원하면 CMK(고객 관리 키)로 업그레이드해 더 엄격하게 제어할 수 있다.
  2. 데이터 사용 및 옵트아웃AWS는 서비스 개선, 모델 학습 목적으로 탐지 패턴을 분석할 수 있는데, 고객이 이를 거부할 수 있는 옵션을 제공한다.
  3. CloudTrail 감사 기록모든 GuardDuty API 호출(활성화, 설정 변경, 결과 조회)이 CloudTrail에 남아 규정 준수 감사에 증거로 사용된다.

인프라 보안과 VPC 엔드포인트(AWS PrivateLink)

GuardDuty 통신이 TLS와 SigV4로 보호되는 방식, 그리고 인터넷을 거치지 않고 VPC 내부에서 GuardDuty에 접속하게 해주는 PrivateLink 인터페이스 엔드포인트 설정.

1상대의 출발점 확인

기존에는 GuardDuty와 통신할 때 고객의 요청이 AWS 공인 인터넷(퍼블릭 API 엔드포인트)을 거쳐야 했다. 인터넷을 거치면 데이터가 공개 네트워크에 노출될 위험이 있고, 특정 규정(엄격한 보안 정책)에서는 인터넷 통신을 허용하지 않는다. 또한 모든 API 요청이 인터넷 게이트웨이를 통과하면서 비용과 레이턴시 증가도 생긴다.

2질문 제기

GuardDuty와 통신할 때 인터넷을 거치지 않고, VPC 내부 프라이빗 네트워크만 사용할 수 있을까?

3구조적 핵심 예시

VPC 엔드포인트(PrivateLink 인터페이스 엔드포인트)를 활성화하면, EC2나 Lambda 같은 VPC 내 리소스가 프라이빗 IP 주소로 GuardDuty API에 직접 접근할 수 있다. 데이터는 AWS 백본 네트워크(프라이빗)를 통해 전송되고, 인터넷 게이트웨이나 NAT 게이트웨이를 거치지 않는다.

4단계별 동작 과정

  1. TLS와 SigV4 암호화모든 GuardDuty API 요청은 TLS(전송 계층 보안)로 암호화되고, AWS Signature Version 4(SigV4) 서명으로 위변조 방지가 된다.
  2. VPC 엔드포인트 생성고객의 VPC에 "GuardDuty" VPC 엔드포인트(AWS PrivateLink 인터페이스 엔드포인트)를 만들면, VPC 서브넷 내에 ENI(탄성 네트워크 인터페이스)가 생성되어 로컬 프라이빗 IP로 접근 가능하게 된다.
  3. 프라이빗 라우팅VPC 내 EC2나 Lambda는 이 엔드포인트의 프라이빗 IP로 요청을 보내면, AWS 내부 네트워크를 통해 GuardDuty 백엔드에 도달한다.

5본질 요약

Security Hub CSPM·Amazon Detective 통합

GuardDuty 결과를 Security Hub CSPM으로 보내 ASFF 형식으로 한데 모아 보고, Detective로 넘겨 관련 로그를 시각적으로 파고드는 연계 방식.

1상대의 출발점 확인

기존에는 GuardDuty가 탐지한 보안 위협(악성 IP 접근, 이상 API 호출 등)이 GuardDuty 대시보드에만 남았다. 다른 보안 도구(AWS Config, SecurityHub 등)와 연계되지 않으면 조직 전체의 보안 태세를 한눈에 보기 어렵다. 또한 GuardDuty가 탐지한 위협이 정확히 어떤 로그와 리소스에서 비롯되었는지 깊이 있게 파고들 수 없었다.

2질문 제기

GuardDuty 탐지 결과를 다른 보안 서비스와 한데 모아 보고, 관련 로그를 시각적으로 추적할 수 있을까?

3구조적 핵심 예시

GuardDuty가 "EC2 인스턴스에서 비정상적인 API 호출 감지" 결과를 생성하면, Security Hub가 이를 ASFF(AWS Security Finding Format) 표준으로 변환하여 중앙 대시보드에 표시한다. 그다음 보안팀이 마우스 클릭으로 Amazon Detective에 넘기면, Detective가 해당 EC2 인스턴스의 CloudTrail, VPC 플로우 로그, DNS 쿼리 기록을 자동으로 수집해 관계도 형태로 보여준다.

4단계별 동작 과정

  1. GuardDuty → Security HubGuardDuty가 탐지한 위협을 ASFF 형식으로 자동 전송하면, Security Hub가 다른 AWS 보안 서비스(Config, Inspector 등)의 결과와 함께 한곳에서 관리할 수 있게 통합한다.
  2. CSPM(클라우드 보안 태세 관리)Security Hub는 수집된 모든 탐지 결과를 태세 점수로 변환하여 조직의 전체 보안 건강도를 시각화하고, 우선순위가 높은 위협부터 대응하도록 지원한다.
  3. Amazon Detective 연계보안팀이 GuardDuty 결과를 Detective로 보내면, 해당 리소스의 관련 로그(CloudTrail, VPC Flow Logs 등)를 자동으로 그래프 형태로 시각화해 조사 시간을 단축한다.

5본질 요약

GuardDuty 탐지 결과를 보안 서비스 생태계(Security Hub, Detective, Config)에 통합하여 중앙 집중식 모니터링과 신속한 위협 조사를 가능하게 하는 것

할당량·관리형 인스턴스·공지 구독·레거시 파라미터

계정·리전당 신뢰 목록 수 같은 GuardDuty 서비스 할당량, SSM 관리형 인스턴스 지원 범위, SNS로 받는 서비스 공지, 그리고 더 이상 권장되지 않는 레거시 액션·파라미터 정리.

1상대의 출발점 확인

기존에는 GuardDuty 사용 시 계정당, 리전당 만들 수 있는 리소스 개수 제한(할당량)을 개별 문서에서 찾아야 했다. GuardDuty가 특정 인스턴스 타입이나 환경을 지원하는지 알기 어려웠고, 서비스 업데이트나 주요 공지를 받으려면 별도 구독 설정이 필요했다. 또한 과거 버전의 파라미터나 API는 점진적으로 제거되는데, 레거시 기능을 사용하면서도 모를 수 있었다.

2질문 제기

GuardDuty 사용 시 리전별 제한, 지원하는 인스턴스 범위, 서비스 공지를 어떻게 체계적으로 관리하고 레거시 파라미터를 피할 수 있을까?

3구조적 핵심 예시

AWS 콘솔의 "Service Quotas" 페이지에서 "GuardDuty"를 검색하면 "Detectors per account"(계정당 5개 한정) 같은 할당량이 표시되고, 필요하면 AWS에 상향 요청할 수 있다. 동시에 SNS 구독 설정에서 GuardDuty 공지 채널을 켜면, EC2 Findings export 형식 변경 같은 중요한 업데이트를 미리 받을 수 있다.

4단계별 동작 과정

  1. 서비스 할당량계정·리전별로 신뢰 목록(ThreatIntelSet), 필터 조건 개수, 동시 실행 가능한 작업 등이 제한되어 있으며, AWS Service Quotas 콘솔이나 API로 확인 및 상향 요청이 가능하다.
  2. 관리형 인스턴스 지원GuardDuty의 에이전트 기반 탐지(런타임 탐지)는 특정 EC2 인스턴스 OS(Linux, Windows)와 아키텍처(x86_64, ARM)만 지원하므로, 사전에 호환성 확인이 필요하다.
  3. 공지 구독과 레거시 파라미터SNS 또는 AWS Health Dashboard를 통해 GuardDuty 기능 변경·추가를 구독할 수 있으며, 문서에서 "더 이상 권장되지 않음(Deprecated)" 표기된 액션·파라미터는 점진적으로 제거되므로 미리 대체 버전으로 마이그레이션해야 한다.
