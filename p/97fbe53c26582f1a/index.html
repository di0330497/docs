아키텍처 도메인 개요

ENCOR 아키텍처 도메인이 다루는 엔터프라이즈 설계 개념(SD-WAN·SD-Access·고가용성·QoS)의 범위와 목표를 정리한 영역이다.

#1문제 상황

기존에는 캠퍼스·WAN·데이터센터·클라우드 연결을 각각 따로 설계하고 장비별 CLI로 관리했다. 그래서 사이트마다 정책이 제각각이 되고, 변경 하나가 다른 영역에 미치는 영향이 전체 그림에서 보이지 않아 운영 부담이 커졌다. 개별 장비 설정만 맞추는 방식으로는 확장과 장애 대응이 느려진다.

#2핵심 질문

엔터프라이즈 네트워크 전체를 하나의 일관된 구조로 다루려면 어떤 설계 영역과 원칙을 함께 봐야 하는가?

#3동작 예시

캠퍼스에 새 지점을 추가할 때, 액세스 스위치 설정만 바꾸는 것이 아니라 WAN 연결과 고가용성 이중화, QoS 정책까지 같은 설계 기준으로 함께 정한다. 이렇게 하면 영역이 달라도 하나의 정책 흐름으로 이어진다.

#4동작 과정

  1. 영역 구분엔터프라이즈 설계를 캠퍼스·WAN·데이터센터·클라우드 연결 같은 영역으로 나눠 각각의 요구를 정리한다.
  2. 공통 원칙 적용계층화·이중화·확장성·단순성 같은 원칙을 모든 영역에 같은 기준으로 적용해 정책이 어긋나지 않게 한다.
  3. 자동화·정책 연계SD-WAN·SD-Access 같은 소프트웨어 정의 방식을 더해 정책을 중앙에서 내려보내고 영역 간 일관성을 유지한다.

#5한 줄 요약

이 아키텍처 도메인엔터프라이즈 네트워크를 구성하는 설계 영역과 원칙을 하나의 일관된 구조로 정리하는 것

#1문제 상황

#2핵심 질문

늘어나는 트래픽과 사이트를 감당하면서도 장애와 변경에 흔들리지 않는 구조는 무엇을 기준으로 설계해야 하는가?

#3동작 예시

액세스 계층 스위치 여러 대를 분배 계층 스위치 두 대에 이중으로 연결하고, 단말 간 통신은 분배 계층에서 처리하게 하면 한 링크가 끊겨도 통신이 유지된다. 같은 패턴을 사이트마다 반복하면 설정을 재사용할 수 있다.

#4동작 과정

  1. 계층화액세스·분배·코어로 역할을 나눠 각 계층이 맡은 일만 하게 한다. 그래서 문제 지점을 좁히기 쉬워진다.
  2. 이중화링크·장비·경로를 둘 이상 두어 하나가 멈춰도 서비스가 이어진다. 그래서 단일 장애 지점이 사라진다.
  3. 단순성·확장성반복되는 표준 패턴을 재사용하고 필요한 곳만 키운다. 그래서 사이트를 늘려도 관리 부담이 비례해 커지지 않는다.

#1문제 상황

#2핵심 질문

#3동작 예시

사용자가 수백 명 규모의 단일 건물이면 분배와 코어를 합친 2-tier로 설계하고, 대규모 캠퍼스면 코어를 분리한 3-tier로 설계한다. 클라우드로 나가는 트래픽은 분배 계층에서 직접 인터넷으로 내보내 지연을 줄인다.

장비·링크 이중화와 FHRP, SSO 같은 기법으로 단일 장애 지점 없이 서비스를 지속하는 방법이다.

→ 01-02 참조

#1문제 상황

단말은 기본 게이트웨이 주소 하나만 알고 있어, 그 주소를 가진 라우터가 멈추면 같은 망에 다른 라우터가 있어도 통신이 끊긴다. 링크와 장비를 이중으로 둬도 게이트웨이가 하나뿐이면 그 지점이 단일 장애 지점이 된다. 장비가 바뀌는 동안 세션과 라우팅 상태가 사라지면 기존 연결도 다시 맺어야 한다.

#2핵심 질문

게이트웨이 장비 하나가 멈춰도 단말이 통신을 끊기지 않게 하려면 어떻게 해야 하는가?

#3동작 예시

두 라우터가 하나의 가상 IP와 가상 MAC을 공유하고, 평소에는 활성 라우터가 응답하다가 그것이 멈추면 대기 라우터가 같은 가상 주소로 응답을 이어받는다. 단말은 게이트웨이 주소를 바꾸지 않고 그대로 통신한다.

#4동작 과정

  1. 가상 게이트웨이 구성여러 라우터가 하나의 가상 IP·MAC을 공유한다(HSRP·VRRP·GLBP). 그래서 단말은 게이트웨이를 하나로 인식한다.

#2핵심 질문

#3동작 예시

물리 서버 위에 하이퍼바이저가 올라가고, 그 위에서 여러 가상 머신이 각자 운영체제를 실행한다. 한 가상 머신이 다른 가상 머신에 영향을 주지 않고 독립적으로 동작하며, 필요하면 가상 스위치로 가상 네트워크를 구성한다.

#4동작 과정

  1. 자원 추상화CPU·메모리·디스크·네트워크를 소프트웨어 계층으로 추상화해 물리 자원 위에 논리 자원을 만든다.

장치 가상화 기술

물리 하드웨어나 장치 기능을 소프트웨어 계층으로 분리해 여러 인스턴스가 자원을 공유하도록 만드는 기술을 말한다.

#1문제 상황

초기 서버 운영은 한 대의 물리 장비에 운영체제 하나와 응용 하나만 올리는 방식이 일반적이었다. 이 방식에서는 CPU와 메모리, 디스크, 네트워크 포트의 사용률이 낮은 상태로 남는 경우가 많았고, 새 서비스를 추가할 때마다 물리 장비를 별도로 구매하고 설치해야 했다. 장비 대수가 늘면 전력, 냉각, 랙 공간 비용도 함께 늘고, 하나의 장치 장애가 그 장치의 모든 기능을 한꺼번에 멈추게 하는 문제가 있었다.

#2핵심 질문

물리 하드웨어와 장치 기능을 소프트웨어 계층으로 분리해 여러 인스턴스가 하나의 자원을 나눠 쓰게 하려면 어떻게 해야 하는가?

#3동작 예시

물리 서버 한 대의 CPU 코어 16개, 메모리 128GB, 네트워크 포트 4개를 가상화 계층이 나눠 잡는다. 가상 머신 A에는 코어 4개와 메모리 32GB, 가상 머신 B에는 코어 8개와 메모리 64GB를 배정하고, 물리 포트 하나는 여러 가상 머신이 논리 포트를 통해 함께 쓴다. 이렇게 하면 물리 장비를 추가하지 않고도 서로 다른 운영체제를 동시에 실행할 수 있다.

#4동작 과정

  1. 자원 추상화물리 CPU, 메모리, 디스크, 네트워크 포트를 소프트웨어가 다룰 수 있는 논리 자원으로 바꾼다. 이때 각 인스턴스는 자신만의 자원을 가진 것처럼 보이게 된다.
  2. 자원 할당과 격리추상화된 자원을 인스턴스별로 나눠 배정하고, 한 인스턴스의 동작이 다른 인스턴스에 영향을 주지 않도록 경계를 만든다. 그래서 한쪽 장애가 전체로 번지지 않는다.
  3. 공유와 중재남는 자원을 여러 인스턴스가 함께 쓰도록 스케줄링하고, 동시 접근이 충돌하지 않게 순서를 조정한다. 그 결과 물리 자원의 사용률이 올라간다.

#1문제 상황

가상 머신을 여러 개 돌리려면 물리 자원을 나눠 주고 각 가상 머신을 대신 실행해 주는 소프트웨어가 필요하다. 초기에는 이 소프트웨어를 일반 운영체제 위에 응용처럼 올리는 방식이 흔했다. 이 방식은 운영체제가 이미 잡아 둔 자원을 다시 거쳐 가상 머신에 전달해야 해서 입출력 지연이 커지고, 호스트 운영체제가 불안정해지면 그 위의 모든 가상 머신이 함께 영향을 받는 한계가 있었다.

#2핵심 질문

가상 머신 실행 소프트웨어를 하드웨어 위에 직접 올릴 것인가, 일반 운영체제 위에 올릴 것인가?

#4동작 과정

  1. Type 1 배치하이퍼바이저가 하드웨어 위에 직접 올라가 자원을 관리한다. 중간 계층이 없어 입출력 경로가 짧아지고 성능과 안정성이 높아진다.
  2. Type 2 배치일반 운영체제가 먼저 하드웨어를 점유하고, 그 위에서 하이퍼바이저가 응용처럼 동작한다. 설치가 간편하지만 운영체제를 한 번 더 거치므로 성능 부담이 커진다.
  3. 가상 머신 실행어느 유형이든 하이퍼바이저가 가상 머신의 명령과 자원 요청을 받아 물리 자원에 매핑한다. 그래서 가상 머신은 실제 하드웨어를 직접 다루지 않고도 운영체제를 구동한다.

가상 스위칭

하이퍼바이저 내부에서 가상 머신 간 또는 가상 머신과 물리 네트워크 사이의 트래픽을 소프트웨어로 연결·전달하는 계층을 말한다.

#1문제 상황

가상 머신이 여러 개 생기면 이들 사이의 트래픽을 어디로 보낼지 정할 계층이 필요하다. 초기에는 가상 머신의 트래픽이 호스트 운영체제의 네트워크 스택을 거쳐 물리 네트워크로 나갔다. 이 경로는 설정이 번거롭고 가상 머신 간 통신도 물리 포트까지 갔다 돌아와 지연이 커졌으며, 가상 머신별로 원하는 네트워크 분리나 정책 적용이 어려웠다.

#2핵심 질문

하이퍼바이저 내부에서 가상 머신 간 트래픽과 물리 네트워크로 나가는 트래픽을 소프트웨어로 어떻게 연결하고 전달할 것인가?

#3동작 예시

같은 물리 서버에 있는 가상 머신 A와 가상 머신 B가 통신할 때, 트래픽은 하이퍼바이저 안의 가상 스위치에서 목적지 가상 포트를 찾아 바로 전달된다. 외부 네트워크로 나가야 하는 트래픽만 가상 스위치에서 물리 네트워크 어댑터로 넘어간다. 가상 머신 A와 B 사이의 통신은 물리 케이블을 타지 않는다.

#4동작 과정

  1. 포트 연결하이퍼바이저가 각 가상 머신의 네트워크 인터페이스를 가상 스위치의 논리 포트에 연결한다. 그래서 모든 가상 머신이 하나의 스위치에 꽂힌 것처럼 동작한다.
  2. 프레임 전달가상 스위치가 목적지 주소를 보고 같은 서버 안의 가상 머신이면 해당 포트로 바로 넘기고, 바깥이면 물리 네트워크 어댑터로 보낸다. 그래서 불필요한 물리 구간 왕복이 줄어든다.
  3. 정책 적용포트별로 가상 LAN 구분이나 대역 제한 같은 규칙을 건다. 그래서 하나의 물리 인프라 위에서도 가상 머신들을 서로 다른 네트워크로 나눌 수 있다.

데이터 경로 가상화 구성

실제 데이터가 흐르는 포워딩 경로를 논리적으로 분리·터널링해 여러 가상 네트워크가 같은 물리 인프라를 공유하도록 구성하는 작업이다.

#1문제 상황

여러 가상 네트워크가 같은 물리 장비를 공유하면 실제 데이터가 흐르는 포워딩 경로도 분리해야 한다. 분리하지 않으면 서로 다른 네트워크의 트래픽이 같은 경로로 섞여 들어가, 주소가 겹치거나 정책이 충돌하는 문제가 생긴다. 각 가상 네트워크마다 물리 장비를 따로 두는 방식은 비용과 관리 부담이 커서 확장하기 어렵다.

#2핵심 질문

실제 데이터가 흐르는 포워딩 경로를 논리적으로 분리·터널링해 여러 가상 네트워크가 같은 물리 인프라를 공유하도록 하려면 어떻게 구성해야 하는가?

#3동작 예시

하나의 물리 라우터에 두 개의 가상 네트워크를 올린다. 첫 번째 네트워크의 트래픽은 논리 터널 인터페이스로 들어가 캡슐화되고, 두 번째 네트워크의 트래픽은 별도 터널로 들어간다. 두 흐름은 같은 물리 포트를 지나지만 서로 다른 터널로 갈라져 목적지에 도착하므로, 주소가 겹쳐도 섞이지 않는다.

#4동작 과정

  1. 경로 분리포워딩 인스턴스와 라우팅 테이블을 가상 네트워크별로 따로 만든다. 그래서 각 네트워크의 경로 정보가 서로 보이지 않는다.
  2. 터널 캡슐화원본 데이터에 가상 네트워크를 구분하는 헤더를 붙여 논리 터널로 보낸다. 그래서 같은 물리 링크를 지나도 출처와 목적지가 구분된다.
  3. 해제와 전달터널 끝에서 헤더를 벗겨 원래 데이터를 꺼내 해당 가상 네트워크의 포워딩 경로로 넘긴다. 그래서 물리 인프라는 공유하면서도 데이터 경로는 독립적으로 유지된다.

#5한 줄 요약

VRF

하나의 물리 라우터 안에서 독립된 라우팅 테이블과 포워딩 인스턴스를 여러 개 운영해, 논리적으로 분리된 네트워크를 만드는 기술이다.

#1문제 상황

하나의 라우터로 서로 다른 조직이나 서비스의 네트워크를 함께 운영하면 라우팅 테이블이 하나뿐이라 경로가 서로 섞인다. 서로 다른 고객이 같은 주소 대역을 쓰면 라우터는 어느 쪽 경로가 맞는지 구분하지 못하고, 한쪽의 경로 변경이 다른 쪽 도달성에 영향을 준다. 조직마다 라우터를 따로 두는 방식은 장비와 회선 비용이 크게 늘어난다.

#2핵심 질문

하나의 물리 라우터 안에서 독립된 라우팅 테이블과 포워딩 인스턴스를 여러 개 운영해 논리적으로 분리된 네트워크를 만들려면 어떻게 해야 하는가?

#3동작 예시

물리 라우터 하나에 VRF 두 개를 만든다. VRF A에는 10.1.0.0/16 경로를, VRF B에도 10.1.0.0/16 경로를 넣는다. 같은 주소 대역이지만 각 VRF의 라우팅 테이블이 따로 관리되므로 두 경로는 충돌하지 않고, 각 VRF에 연결된 인터페이스로 들어온 트래픽은 자기 테이블만 참조해 전달된다.

#4동작 과정

  1. 인스턴스 생성라우터 안에 VRF를 만들고 각 VRF에 독립된 라우팅 테이블과 포워딩 인스턴스를 배정한다. 그래서 라우터 하나가 여러 대의 논리 라우터처럼 동작한다.
  2. 인터페이스 할당물리 인터페이스나 하위 인터페이스를 특정 VRF에 넣는다. 그래서 그 인터페이스로 들어온 트래픽은 해당 VRF의 테이블만 참조한다.
  3. 경로 유지와 격리각 VRF가 자기 경로만 학습·광고하고 다른 VRF의 경로는 보지 않는다. 그래서 주소가 겹쳐도 네트워크가 서로 분리된 상태로 유지된다.

#5한 줄 요약

하나의 물리 라우터 안에서 독립된 라우팅 테이블과 포워딩 인스턴스를 여러 개 운영해 논리적으로 분리된 네트워크를 만드는 것

GRE와 IPsec 터널링

GRE는 임의의 프로토콜 패킷을 캡슐화해 전달하는 터널이고, IPsec은 그 터널이나 트래픽에 암호화·인증을 더해 안전하게 전송하는 기술이다.

#1문제 상황

사설 IP를 쓰는 두 지점을 인터넷으로 연결하려 하면, 사설 주소는 인터넷 라우터가 전달하지 못하므로 그대로는 통신할 수 없다. 또 두 지점 사이 트래픽을 그대로 내보내면 중간에서 내용을 들여다보거나 위조할 수 있다. 단순한 라우팅만으로는 주소 전달과 보안을 동시에 해결할 수 없다.

#2핵심 질문

서로 다른 두 사설망을 인터넷 너머로 연결하면서 중간에서 내용을 볼 수 없게 하려면 어떻게 해야 하는가?

#3동작 예시

라우터 A와 B 사이에 GRE 터널을 만들면 A의 사설 패킷이 GRE 헤더로 감싸져 공인 IP 패킷 안에 실려 B로 간다. 여기에 IPsec을 함께 적용하면 그 패킷 전체가 암호화되어, 중간 라우터는 공인 IP 헤더만 보고 안의 내용은 읽지 못한다.

#4동작 과정

  1. 캡슐화송신 라우터가 사설 패킷 앞에 GRE 헤더(터널임을 알리는 표시)를 붙여 새 IP 패킷으로 감싼다. 그래서 사설 주소가 인터넷을 건너간다.
  2. 보호IPsec이 그 GRE 패킷을 암호화하고 인증해 내보낸다. 그래서 중간 장비가 내용을 못 읽고 변조도 탐지된다.
  3. 해제수신 라우터가 IPsec을 풀고 GRE 헤더를 벗겨 원래 사설 패킷을 꺼낸다. 그래서 내부망은 터널이 있는지 모른 채 통신한다.

GRE와 IPsec 터널링사설 트래픽을 인터넷 위에 캡슐화해 전달하고 그 위에 암호화·인증을 더하는 것

네트워크 가상화 개념

물리 토폴로지 위에 논리적 오버레이 네트워크를 구성해 다수의 가상 네트워크를 독립적으로 제공하는 개념이다.

#1문제 상황

전통 네트워크는 물리 장비와 링크에 토폴로지가 고정되어, 새 부서나 서비스를 추가할 때마다 케이블·포트·VLAN을 물리적으로 다시 설계해야 한다. 장비가 늘면 관리 대상과 설정 오류도 함께 늘고, 같은 인프라를 여러 팀이 나눠 쓰기도 어렵다. 결국 물리 배선을 바꾸지 않고는 네트워크를 유연하게 바꿀 수 없다.

#2핵심 질문

물리 장비를 그대로 둔 채 여러 개의 독립된 네트워크를 논리적으로 만들어 쓰려면 어떻게 해야 하는가?

#3동작 예시

하나의 물리 스위치에 VLAN 10과 VLAN 20을 만들면, 같은 장비에 연결된 포트라도 VLAN 10의 PC는 VLAN 20의 PC와 통신하지 못한다. 즉 물리 장비 한 대가 두 개의 별도 네트워크처럼 동작한다.

#4동작 과정

  1. 논리 분리물리 포트를 VLAN·VRF 같은 논리 단위에 나눠 배정한다. 그래서 한 장비가 여러 개의 독립 네트워크를 담는다.
  2. 오버레이 구성물리 경로 위에 터널·캡슐화로 가상 링크를 얹어 논리 토폴로지를 만든다. 그래서 물리 배선과 무관하게 연결 구조를 정한다.
  3. 제어 분리중앙 컨트롤러나 프로토콜이 논리 네트워크를 만들고 관리한다. 그래서 변경이 물리 작업 없이 설정만으로 끝난다.

네트워크 가상화물리 인프라 위에 독립적으로 동작하는 논리 네트워크를 여러 개 만들어 유연하게 분리·관리하는 것

LISP와 VXLAN

LISP은 위치(RLOC)와 식별자(EID)를 분리하는 컨트롤 플레인 프로토콜이고, VXLAN은 이를 활용해 L2 네트워크를 L3 위에 확장하는 오버레이 데이터 플레인이다.

#1문제 상황

가상화 환경에서는 가상 머신이 다른 물리 위치로 옮겨 다니는데, 옮겨간 뒤에도 IP 주소는 그대로 유지되어야 한다. 기존 IP 라우팅은 주소가 곧 위치라서, 주소를 바꾸지 않고 옮기면 라우팅이 따라가지 못한다. 또 L2 네트워크를 여러 데이터센터로 넓히면 이더넷 브로드캐스트가 넘쳐 확장성이 떨어진다.

#2핵심 질문

주소(누구인가)와 위치(어디에 있는가)를 분리해, 주소를 바꾸지 않고 단말을 다른 위치로 옮길 수 있는가?

#3동작 예시

호스트의 EID(단말 식별자, 예: 10.1.1.10)는 그대로 두고, 그 단말이 붙어 있는 라우터의 RLOC(위치 주소, 예: 192.0.2.1)만 새 위치 값으로 바꾼다. LISP이 이 매핑을 알려 주면 트래픽은 새 위치로 전달된다.

#4동작 과정

  1. 등록·질의끝 단말이 붙은 라우터가 자기 EID와 RLOC 매핑을 맵 서버에 등록하고, 목적지 EID의 RLOC를 질의한다. 그래서 송신 측이 목적지 위치를 안다.
  2. 캡슐화송신 측 라우터가 원래 패킷을 새 IP 헤더로 감싸 RLOC로 보낸다. L2 프레임이면 이 구간에서 VXLAN 헤더로 터널링된다.
  3. 전달·해제중간 IP망은 RLOC만 보고 전달하고, 수신 측 라우터가 헤더를 벗겨 원래 패킷을 꺼낸다. 그래서 주소는 그대로인 채 위치 이동이 끝난다.

Layer 2 개요

MAC 주소 기반으로 같은 네트워크 안에서 프레임을 전달하는 계층으로, VLAN·트렁킹·EtherChannel·스패닝 트리 같은 기술이 동작하는 기반이다.

#2핵심 질문

#3동작 예시

스위치가 목적지 MAC 주소를 보고 해당 포트로만 프레임을 내보낸다. 목적지 MAC을 아직 모르면 연결된 모든 포트로 한 번 뿌려 위치를 학습하고, 이후에는 그 포트로만 전달한다.

#4동작 과정

  1. 학습스위치가 들어온 프레임의 출발지 MAC과 포트를 MAC 주소 테이블에 기록한다. 그래서 어느 MAC이 어디에 있는지 알게 된다.
  2. 전달목적지 MAC이 테이블에 있으면 그 포트로만 보낸다. 없으면 플러딩(전 포트 전송)으로 목적지를 찾는다.
  3. 분리·중복 제거VLAN으로 논리 네트워크를 나누고 스패닝 트리(STP)로 루프 경로를 막는다. 그래서 확장해도 루프와 혼잡을 통제한다.

EtherChannel 트러블슈팅

여러 물리 포트를 하나의 논리 포트로 묶어 대역폭과 이중화를 얻는 EtherChannel이 형성되지 않을 때, 양쪽의 채널 모드·프로토콜(LACP/PAgP)·포트 파라미터 불일치를 확인해 문제를 해결하는 작업이다.

→ 03-03 참조

#1문제 상황

여러 물리 포트를 하나의 논리 포트로 묶는 EtherChannel은 대역폭을 늘리고 링크 하나가 끊겨도 서비스가 유지되게 한다. 문제는 이 묶음이 자동으로 만들어지지 않는다는 점이다. 양쪽 스위치의 채널 모드와 협상 프로토콜, 그리고 각 포트의 속도·duplex·허용 VLAN 같은 파라미터가 어긋나면 채널 전체가 형성되지 않는다.

채널이 안 만들어지면 겉으로는 케이블이 꽂혀 있고 링크 LED도 들어오는데, 트래픽은 묶음이 아니라 포트 하나로만 흐른다. 이때는 STP가 각 링크를 별도 경로로 보고 일부를 차단해 버려, 관리자는 "링크는 살아 있는데 왜 대역폭이 안 늘지"를 케이블 문제로 오해하기 쉽다. 그래서 어느 쪽 파라미터가 어긋났는지 확인하는 절차가 따로 필요하다.

#2핵심 질문

양쪽 스위치의 어떤 모드·프로토콜·포트 파라미터가 어긋나 EtherChannel이 형성되지 않는가?

#3동작 예시

스위치 A의 포트 두 개에 channel-group 1 mode active를, 스위치 B의 같은 두 포트에 channel-group 1 mode on을 설정했다고 하자. A는 LACP(링크 묶음을 협상하는 표준 프로토콜)로 상대를 찾지만, B는 on이라 협상 자체를 하지 않는다. 이 조합에서는 채널이 만들어지지 않고, 두 스위치는 각 링크를 독립 포트로 취급한다. 여기서 B를 mode active로 바꿔 양쪽을 LACP로 맞추면 채널이 형성된다.

#4동작 과정

  1. 모드·프로토콜 확인양쪽의 channel-group 모드를 본다. 한쪽은 LACP(active/passive), 다른 쪽은 PAgP(desirable/auto)거나 on이면 서로 협상하지 못하므로, 양쪽을 같은 프로토콜로 맞춰야 채널이 맺어진다.
  2. 포트 파라미터 대조속도·duplex·허용 VLAN·트렁크 설정이 모든 묶음 포트에서 동일한지 본다. 하나라도 다르면 그 포트만 채널에서 빠지고, 그 차이가 곧 대역폭 손실로 나타난다.
  3. 상태 검증show etherchannel summary에서 묶음 포트가 사용 중(번들)인지, 구성원 포트가 빠졌는지 확인한다. 어긋난 포트를 고친 뒤 다시 묶이면 대역폭과 이중화가 의도대로 복구된다.

STP(RSTP·MST)와 보호 기능

루프 방지를 위해 이중 경로 중 하나를 논리적으로 차단하는 스패닝 트리 프로토콜과, 루트 탈취·BPDU 비정상 유입을 막는 root guard·BPDU guard 같은 보호 기능을 구성·검증하는 것이다.

→ 03-02 참조

#1문제 상황

스위치 네트워크에 이중 경로가 있으면, 목적지를 모르는 브로드캐스트 프레임이 양쪽 경로로 계속 돌아 영원히 사라지지 않는 루프가 생긴다. 이 트래픽이 폭증하면 스위치 CPU와 링크가 포화되어 네트워크 전체가 멈춘다. 스패닝 트리 프로토콜(STP)은 이중 경로 중 하나를 논리적으로 차단해 루프를 막는다.

문제는 기본 STP가 수렴이 느려 토폴로지가 바뀔 때마다 수십 초 동안 트래픽이 끊긴다는 점이다. 또 관리자가 차단 경로를 조정하려고 루트 브리지 정보를 조작하면, 의도치 않게 엉뚱한 스위치가 루트가 되어 경로가 꼬일 수 있다. 이런 한계를 보완하려고 더 빠른 수렴 방식과, 루트 탈취·비정상 BPDU 유입을 막는 보호 기능이 함께 쓰인다.

#2핵심 질문

루프를 막으면서도 더 빠르게 수렴하고, 루트 탈취나 비정상 BPDU가 토폴로지를 흔들지 못하게 하려면 어떻게 구성해야 하는가?

#3동작 예시

스위치 네 개가 사각형으로 연결된 토폴로지를 생각하자. 그중 하나를 루트 브리지로 두면, 나머지 스위치들이 각자 어느 포트로 루트까지 갈지 계산해 한쪽 링크를 차단한다. 이때 접속 단말이 꽂히는 포트를 spanning-tree portfast(링크가 올라오면 바로 전달 상태로 여는 설정)로 지정하고 bpduguard를 걸어 둔다. 그러면 STP 수렴을 기다리지 않고 단말이 바로 통신하되, 그 포트로 BPDU(스위치끼리 토폴로지를 주고받는 제어 프레임)가 들어오면 즉시 포트를 막아 루프를 예방한다.

#4동작 과정

  1. 프로토콜 선택RSTP(빠른 수렴 스패닝 트리)나 MST(여러 VLAN을 하나의 인스턴스로 묶어 관리하는 스패닝 트리)를 쓴다. RSTP는 대체 포트를 미리 준비해 두어 링크 장애 시 수렴이 빨라지고, MST는 VLAN마다 따로 계산하지 않아 자원을 아낀다.
  2. 루트·역할 지정원하는 스위치를 루트로 고정하고 포트 역할과 상태를 확인한다. 루트 탈취를 막으려면 하위 스위치의 상향 포트에 root guard를 걸어, 그 포트로 우세한 BPDU가 들어와도 루트 자리를 빼앗기지 않게 한다.
  3. 보호 기능 검증단말 포트에 BPDU guard를 적용해 비정상 BPDU 유입 시 차단되게 하고, show spanning-tree로 루트와 포트 상태가 의도대로인지 확인한다. 이렇게 하면 루프는 계속 차단되면서 장애 복구는 빨라진다.

#5한 줄 요약

Layer 3 개요

IP 주소와 라우팅 테이블을 근거로 서로 다른 네트워크 사이에서 패킷을 전달하는 계층으로, 라우팅 프로토콜·정책 기반 라우팅·게이트웨이 이중화가 이 위에서 동작한다.

#1문제 상황

같은 네트워크 안에서는 스위치가 MAC 주소를 보고 프레임을 전달하지만, 서로 다른 네트워크로 나가려면 그 방식이 통하지 않는다. 목적지가 다른 대역에 있으면 스위치는 그 주소를 어디로 보내야 할지 알지 못한다. 앞서 배운 2계층 전달만으로는 네트워크와 네트워크를 연결할 수 없다.

이 문제를 푸는 계층이 Layer 3다. IP 주소를 기준으로 목적지가 어느 네트워크에 있는지 판단하고, 라우팅 테이블에 적힌 경로를 골라 다음 장비로 패킷을 넘긴다. 이때 경로를 사람이 일일이 적을 수도 있지만 네트워크가 커지면 감당이 안 되므로, 라우팅 프로토콜이 경로를 자동으로 주고받는다. 여기에 정책으로 경로를 조정하는 방식과 게이트웨이 이중화가 얹혀 실제 네트워크가 돌아간다.

#2핵심 질문

서로 다른 IP 네트워크 사이에서 패킷을 올바른 다음 장비로 넘기려면 어떤 정보를 기준으로 경로를 정하는가?

#3동작 예시

PC가 10.1.1.10, 다른 대역의 서버가 10.2.2.20이라고 하자. PC는 목적지가 자기 대역이 아니라서 기본 게이트웨이(자기 대역 밖 목적지를 넘기는 출구 라우터)로 패킷을 보낸다. 라우터는 목적지 10.2.2.20에 대한 경로를 라우팅 테이블에서 찾는다. 그 경로의 다음 홉(next-hop, 패킷을 넘길 바로 다음 라우터의 IP)으로 패킷을 전달하면, 이 과정이 홉마다 반복되어 서버까지 도달한다.

#4동작 과정

  1. 목적지 판단들어온 패킷의 목적지 IP를 보고, 그 주소가 직결된 네트워크인지 아니면 다른 곳으로 넘겨야 하는지 정한다. 목적지가 자기 대역이 아니면 라우팅 테이블을 참조한다.
  2. 경로 선택라우팅 테이블에서 가장 알맞은 경로 하나를 고른다. 이 테이블 항목은 관리자가 직접 넣은 정적 경로이거나, 라우팅 프로토콜이 학습한 동적 경로다.
  3. 전달과 이중화고른 다음 홉으로 패킷을 넘긴다. 게이트웨이 라우터가 죽는 상황에 대비해 첫 홉 이중화(FHRP)로 여러 라우터가 하나의 가상 게이트웨이를 공유하게 하면, 단말 설정을 바꾸지 않고도 통신이 이어진다.

EIGRP와 OSPF 라우팅 개념 비교

EIGRP(고급 거리 벡터)와 OSPF(링크 상태)를 경로 선택·메트릭·로드 밸런싱·영역 구조·경로 연산 방식 측면에서 대조해 각 프로토콜의 동작 원리 차이를 이해하는 것이다.

→ 03-08 참조

#1문제 상황

라우팅 프로토콜은 이웃끼리 경로 정보를 주고받아 라우팅 테이블을 채운다. 문제는 이 정보를 "누구에게서 얼마나 멀리 있는지"로 파악하느냐, "각 링크 상태를 전체가 똑같이 그려서" 파악하느냐에 따라 동작이 크게 갈린다는 점이다. 같은 목적지라도 프로토콜이 다르면 다른 경로를 고르거나 다른 방식으로 수렴한다.

EIGRP는 거리 벡터 방식을 정교하게 다듬은 고급 거리 벡터로, 이웃에게 받은 정보를 자기 관점의 거리로 바꿔 전파한다. OSPF는 링크 상태 방식으로, 각 라우터가 자기 주변 링크 상태를 모두에게 알리고 같은 지도를 그려 경로를 계산한다. 이 차이를 모르면 두 프로토콜이 섞인 망에서 경로가 왜 다르게 잡히는지, 영역을 어떻게 나눠야 하는지 판단할 수 없다.

#2핵심 질문

EIGRP의 거리 벡터 방식과 OSPF의 링크 상태 방식은 경로 선택·메트릭·영역 구조에서 어떻게 다른가?

#3동작 예시

목적지까지 가는 경로가 두 개 있고 대역폭이 각각 다르다고 하자. EIGRP는 대역폭과 지연 등을 조합한 메트릭으로 더 좋은 경로를 계산하고, 그 값이 같으면 두 경로에 트래픽을 나눠 보낸다. OSPF는 링크 비용(cost)의 합이 작은 경로를 고르며, 비용이 같으면 역시 두 경로로 나눈다. 즉 두 프로토콜 모두 메트릭이 같은 경로에 부하를 분산하지만, 메트릭을 만드는 재료와 계산법이 서로 다르다.

#4동작 과정

  1. 정보 수집 방식EIGRP는 이웃과 인접 관계를 맺고 받은 경로 정보를 자기 거리로 환산해 전파한다. OSPF는 링크 상태 정보를 영역 안에 넘겨 모든 라우터가 동일한 토폴로지 지도를 갖게 한다.
  2. 경로 계산과 영역EIGRP는 메트릭이 가장 작은 경로를 후보로 두고 대체 경로까지 미리 준비한다. OSPF는 영역(area)으로 망을 나눠 영역 내부는 상세 정보를, 영역 사이는 요약 정보를 주고받아 확장성을 얻는다.
  3. 경로 선택과 분산최종 메트릭이 가장 좋은 경로를 라우팅 테이블에 올리고, 같은 값의 경로가 여럿이면 로드 밸런싱한다. 이때 두 프로토콜의 메트릭 기준이 달라 같은 망에서도 우선 경로가 달라질 수 있다.

#5한 줄 요약

OSPFv2/v3 구성 — 다중 영역·요약·필터링

OSPF를 여러 normal 영역으로 나누어 구성하고, 인접 관계·네트워크 타입(point-to-point·broadcast)·passive-interface를 설정하며, 영역 간 경로 요약과 필터링까지 적용·검증하는 것이다.

→ 03-07 참조

#1문제 상황

OSPF를 하나의 영역으로만 운영하면 모든 라우터가 같은 상세 토폴로지 정보를 들고 있어야 한다. 라우터가 늘고 링크가 늘수록 경로 계산 부담과 링크 상태 정보의 양이 함께 커져, 작은 변화 하나에도 망 전체가 다시 계산한다. 망이 커질수록 이 부담이 감당하기 어려워진다.

이 문제를 줄이려고 OSPF는 망을 여러 normal 영역으로 나눈다. 영역 안에서는 상세 정보를 공유하되, 영역 경계 라우터가 다른 영역으로 넘길 때는 경로를 요약해 정보량을 줄인다. 또 라우터끼리 인접 관계를 맺는 방식과, 단말만 붙은 포트에서 불필요한 인접 맺기를 막는 설정까지 함께 맞춰야 안정적으로 동작한다. 요약·필터링을 어디에 적용하느냐에 따라 전파되는 경로가 달라진다.

#2핵심 질문

OSPF를 여러 영역으로 나누고 경로를 요약·필터링하려면 인접 관계와 네트워크 타입, passive-interface를 어떻게 구성해야 하는가?

#3동작 예시

한 라우터의 포트 두 개 중 하나는 다른 라우터와 직접 연결되고, 다른 하나는 PC만 붙어 있다고 하자. 라우터 간 포트는 point-to-point(라우터 두 대가 1대1로 연결된 네트워크 타입)로 두어 인접 관계를 맺게 하고, PC만 붙은 포트는 passive-interface로 지정해 OSPF 인접을 시도하지 않게 한다. 그러면 헛된 인접 시도가 사라지고, 영역 경계에서는 여러 세부 경로를 하나의 요약 경로로 묶어 넘길 수 있다.

#4동작 과정

  1. 영역과 인터페이스 구성포트별로 어느 영역에 속할지 정하고, 네트워크 타입을 point-to-point나 broadcast(여러 장비가 한 망에 붙어 인접을 맺는 타입)로 맞춘다. 타입이 어긋나면 인접 관계가 맺어지지 않는다.
  2. 인접·passive 설정라우터끼리 맞닿은 포트는 인접을 맺게 두고, 단말만 있는 포트는 passive-interface로 지정한다. 그래야 불필요한 인접 시도와 경로 광고가 줄어든다.
  3. 요약·필터링 적용영역 경계에서 세부 경로를 요약해 넘기거나 특정 경로를 걸러 전파 범위를 조정하고, 인접 상태와 학습된 경로를 확인해 의도대로 동작하는지 검증한다.

#5한 줄 요약

OSPF를 여러 영역으로 나누고 인접·네트워크 타입·passive-interface를 맞춘 뒤, 영역 경계에서 경로를 요약·필터링해 정보량을 줄이는 것

eBGP(직접 연결 이웃)

서로 다른 AS에 속해 직접 연결된 라우터끼리 eBGP 이웃 관계를 맺고, best path 선택 알고리즘에 따라 최적 경로를 고르는 과정을 구성·검증하는 것이다.

→ 03-06 참조

#1문제 상황

OSPF나 EIGRP 같은 내부 라우팅 프로토콜은 하나의 관리 주체가 운영하는 망 안에서 최적 경로를 찾는 데 맞춰져 있다. 그런데 서로 다른 조직이나 사업자가 운영하는 망, 즉 서로 다른 AS(자율 시스템) 사이에서는 상대 망의 내부 사정을 알 수 없고, 경로를 그대로 신뢰할 수도 없다. 내부 프로토콜만으로는 이 경계를 넘는 경로를 안정적으로 주고받기 어렵다.

BGP는 이 경계에서 경로를 교환하는 프로토콜이고, 그중 서로 다른 AS에 속한 라우터끼리 직접 연결해 맺는 것이 eBGP다. 문제는 BGP가 "가장 좋은 경로 하나"를 정하는 기준이 단순 메트릭이 아니라 여러 조건을 순서대로 따지는 알고리즘이라는 점이다. 이 순서를 모르면 왜 특정 경로가 선택됐는지 설명할 수 없다.

#2핵심 질문

서로 다른 AS에 직접 연결된 두 라우터가 eBGP 이웃을 맺고, 여러 후보 중 어떤 경로를 최적으로 고르는가?

#3동작 예시

AS 100의 라우터와 AS 200의 라우터가 직접 연결되어 있다고 하자. 각 라우터는 상대를 이웃으로 지정하고, 자신이 아는 경로를 상대에게 알린다. 같은 목적지에 대해 여러 경로가 들어오면, BGP는 먼저 다음 홉까지 도달 가능한지 확인하고, 그다음 AS 경로 길이(거쳐 가는 AS의 수)가 짧은 쪽을, 그것도 같으면 다른 조건들을 순서대로 따져 하나를 고른다. 즉 "짧은 AS 경로"가 이른 단계의 강한 기준이다.

#4동작 과정

  1. 이웃 맺기두 AS의 라우터가 서로의 주소를 이웃으로 지정하고 TCP 연결을 맺는다. 이때 양쪽의 AS 번호가 달라야 eBGP 관계가 되며, 연결이 서면 경로 정보를 주고받을 준비가 된다.
  2. 경로 교환각 라우터가 자기 AS의 경로를 상대에게 광고하고, 상대가 보낸 경로를 받아 BGP 테이블에 넣는다. 이 단계에서 AS 경로 정보가 함께 오가 서로의 출처를 구분한다.
  3. 최적 경로 선택받은 후보들에 best path 선택 알고리즘을 순서대로 적용해 하나를 고르고 라우팅 테이블에 올린다. 도달 가능성, AS 경로 길이 같은 조건을 차례로 따져 최종 경로가 정해진다.

#5한 줄 요약

서로 다른 AS에 직접 연결된 라우터끼리 eBGP 이웃을 맺고, 정해진 순서의 best path 선택 알고리즘으로 최적 경로 하나를 고르는 것

정책 기반 라우팅(PBR)

목적지 주소만 보는 일반 라우팅과 달리, 출발지·프로토콜·포트 같은 조건을 route-map으로 지정해 패킷을 특정 다음 홉이나 인터페이스로 보내는 라우팅 방식이다.

#1문제 상황

일반 라우팅은 패킷의 목적지 주소만 보고 경로를 고른다. 같은 목적지로 가는 패킷은 출발지가 다르고 용도가 달라도 모두 같은 다음 홉으로 가게 된다.

이 방식은 라우팅 테이블에 적힌 최적 경로 하나만 따르기 때문에, 특정 트래픽만 다른 회선으로 보내거나 특정 대역만 우회시키는 제어가 불가능하다. 회선을 용도별로 나눠 쓰고 싶어도 목적지가 같으면 손을 쓸 방법이 없다.

#2핵심 질문

목적지 주소만 보는 라우팅으로는 왜 출발지나 포트 같은 조건에 따라 경로를 바꿀 수 없을까?

#3동작 예시

관리자가 출발지 대역이 10.1.1.0/24인 패킷은 전용 회선 쪽 인터페이스로 보내고, 그 외 트래픽은 기본 경로로 보내도록 설정한다. 같은 목적지로 가는 패킷이라도 출발지가 다르면 서로 다른 다음 홉으로 빠져나간다.

#4동작 과정

  1. 조건 매칭패킷이 인터페이스에 들어오면 route-map의 match 문이 출발지 주소·프로토콜·포트 같은 조건과 일치하는지 검사한다. 이 route-map은 경로를 고를 때 적용할 규칙 목록이다.
  2. 다음 홉 지정조건이 맞으면 set 문에 적힌 다음 홉 주소나 출력 인터페이스로 패킷을 보낸다. 조건이 맞지 않으면 다음 규칙으로 넘어간다.
  3. 기본 라우팅으로 위임어느 규칙에도 맞지 않으면 평소처럼 목적지 기반 라우팅 테이블을 참고해 전달한다.

#5한 줄 요약

목적지가 아니라 출발지·프로토콜·포트 같은 조건으로 패킷의 다음 홉을 지정해, 같은 목적지라도 트래픽별로 다른 경로를 태우는 것

IP 서비스 개요

네트워크 운영에 필요한 시간 동기화(NTP·PTP), 주소 변환(NAT/PAT), 게이트웨이 이중화(FHRP), 멀티캐스트 같은 부가 IP 서비스의 범위와 역할을 정리한 것이다.

#1문제 상황

패킷을 목적지까지 전달하는 라우팅만 갖춰도 통신은 되지만, 운영 단계에서는 그 위에 필요한 기능들이 따로 있다. 장비마다 시각이 어긋나면 로그 순서가 뒤섞이고, 사설 주소만 쓰는 내부 호스트는 외부와 통신할 수 없으며, 게이트웨이 하나가 죽으면 그 뒤 호스트 전체가 끊긴다.

이런 요구는 라우팅 자체가 아니라 라우팅을 보조하는 별도 서비스로 해결해야 한다. 각각 다른 목적을 갖기 때문에 범위와 역할을 나눠서 이해할 필요가 있다.

#2핵심 질문

라우팅 외에 네트워크를 실제로 운영하려면 어떤 부가 IP 서비스들이 필요할까?

#3동작 예시

한 지사 네트워크에서 내부 호스트는 사설 주소를 쓰면서 외부로 나갈 때 주소 변환을 거치고, 게이트웨이 라우터 두 대는 가상 IP를 공유해 한 대가 죽어도 호스트가 그대로 통신하며, 모든 장비는 같은 시각 서버를 바라봐 로그 시간이 일치한다. 이 세 가지가 각각 주소 변환, 게이트웨이 이중화, 시간 동기화라는 서로 다른 IP 서비스에 해당한다.

#4동작 과정

  1. 시간 동기화NTP·PTP 같은 프로토콜로 장비 간 시각을 맞춘다. 로그와 인증서 검증의 기준 시각이 일관되게 유지된다.
  2. 주소 변환NAT·PAT로 사설 주소와 공인 주소를 변환한다. 내부 호스트가 외부 네트워크와 통신할 수 있게 된다.
  3. 가용성·전달 확장FHRP(첫 홉 라우터 이중화)로 게이트웨이를 이중화하고, 멀티캐스트로 하나의 송신을 다수 수신자에게 전달한다. 게이트웨이 장애에도 통신이 유지되고 대규모 전달이 가능해진다.

#5한 줄 요약

라우팅 위에서 시간 동기화·주소 변환·게이트웨이 이중화·멀티캐스트 같은 부가 서비스를 제공해 네트워크를 안정적으로 운영하게 하는 것

NTP와 PTP

장비 간 시각을 맞추는 프로토콜로, NTP는 패킷 교환 기반으로 밀리초 수준의 시각을 동기화하고 PTP는 하드웨어 타임스탬프로 더 정밀한 동기화를 제공한다.

#1문제 상황

각 장비가 자기 시계를 따로 관리하면 시간이 조금씩 어긋난다. 로그를 모아 보면 사건의 선후가 뒤바뀌고, 인증서 유효성 검사나 이벤트 상관 분석처럼 정확한 시각이 필요한 작업이 어긋난 시간 때문에 실패한다.

장비가 많아질수록 수동으로 시각을 맞추는 것은 현실적이지 않다. 네트워크를 통해 기준 시각을 자동으로 전파하고 지속적으로 보정하는 방법이 필요하다.

#2핵심 질문

여러 장비의 시각을 네트워크로 자동으로 일치시키려면 어떻게 해야 할까?

#3동작 예시

한 대의 서버를 기준 시각원으로 두고, 나머지 장비가 그 서버에 주기적으로 질의해 시각을 받아 자기 시계를 조정한다. 이때 네트워크를 오가는 데 걸린 지연을 계산해 보정하므로, 단순히 현재 시각만 받아 쓰는 것보다 오차가 훨씬 줄어든다.

#4동작 과정

  1. 기준 시각 확보기준 장비(서버)가 상위 시각원에서 현재 시각을 얻어 자신의 기준 시각으로 삼는다.
  2. 질의·응답 교환클라이언트가 서버에 시각을 요청하고 응답을 받는다. 요청을 보낸 시각과 응답을 받은 시각을 함께 기록해 왕복 지연과 시간 차이를 계산한다. NTP는 이 방식으로 밀리초 수준의 시각을 맞춘다.
  3. 지속 보정계산된 오차만큼 자기 시계를 조정하고, 이후에도 주기적으로 반복해 시간이 흘러도 어긋나지 않게 유지한다. 하드웨어 타임스탬프를 쓰는 PTP는 이 과정을 더 정밀하게 수행한다.

#5한 줄 요약

기준 시각을 네트워크로 전파하고 지연을 보정해 여러 장비의 시각을 지속적으로 일치시키는 것

NAT/PAT

사설 IP 주소를 공인 IP 주소로 변환해 외부와 통신하게 하는 기술로, NAT는 주소를 일대일로, PAT는 포트까지 함께 사용해 여러 호스트가 하나의 공인 주소를 공유하게 한다.

#1문제 상황

내부 네트워크는 사설 IP 주소를 쓰기 때문에 그대로는 외부 인터넷과 통신할 수 없다. 사설 주소는 전 세계에서 유일하지 않아 외부로 나가는 패킷의 주소로 쓸 수 없기 때문이다.

모든 내부 호스트에 공인 주소를 하나씩 주는 방법도 있지만, 공인 주소는 한정되어 있어 비용과 관리 부담이 크다. 내부 주소를 그대로 쓰면서 외부와 통신할 수 있게 해 주는 변환 장치가 필요하다.

#2핵심 질문

사설 주소를 쓰는 내부 호스트가 공인 주소 없이도 외부와 통신하려면 어떻게 해야 할까?

#3동작 예시

내부 호스트가 사설 주소로 외부 서버에 접속하면, 경계 라우터가 패킷의 출발지 주소를 자기 공인 주소로 바꿔 내보낸다. 돌아오는 응답은 그 공인 주소로 도착하고, 라우터가 원래 내부 호스트를 찾아 주소를 되돌려 전달한다. 한 개의 공인 주소를 여러 호스트가 나눠 쓸 때는 포트 번호로 각 연결을 구분한다.

#4동작 과정

  1. 변환 테이블 등록내부 호스트의 패킷이 라우터를 지날 때, 원래 출발지 주소와 포트를 공인 주소와 포트로 변환하고 그 매핑을 테이블에 기록한다.
  2. 주소 변환 후 전달주소가 바뀐 패킷이 외부로 나가고, 응답 패킷이 공인 주소로 돌아온다. NAT는 주소를 일대일로 바꾸고, PAT는 포트까지 함께 써서 여러 호스트가 하나의 공인 주소를 공유한다.
  3. 역변환테이블을 보고 응답의 목적지 주소를 원래 내부 호스트로 되돌려 전달한다. 내부 호스트는 사설 주소를 그대로 유지한다.

#5한 줄 요약

사설 주소를 공인 주소로 변환하고 포트로 연결을 구분해, 여러 내부 호스트가 적은 공인 주소로 외부와 통신하게 하는 것

FHRP — HSRP·VRRP

여러 라우터가 하나의 가상 IP를 공유하는 가상 게이트웨이를 만들어, 첫 홉 라우터가 죽어도 호스트의 통신이 끊기지 않도록 이중화하는 프로토콜이다.

→ 03-06 참조

#1문제 상황

호스트는 기본 게이트웨이 주소 하나를 설정해 두고 그 라우터로만 외부 패킷을 보낸다. 이 라우터가 죽으면 호스트 설정을 바꾸지 않는 한 통신이 완전히 끊긴다.

라우터를 두 대 두더라도 호스트는 그중 한 대의 주소만 알고 있으므로 나머지 한 대는 대기 상태로만 남는다. 게이트웨이 장애를 호스트가 인지하고 스스로 경로를 바꾸는 것도 기대하기 어렵다.

#2핵심 질문

첫 홉 라우터가 죽어도 호스트가 설정을 바꾸지 않고 통신을 이어가려면 어떻게 해야 할까?

#3동작 예시

라우터 두 대가 하나의 가상 IP 주소를 공유하고, 그중 한 대만 실제로 트래픽을 처리한다. 호스트는 이 가상 IP를 기본 게이트웨이로 설정해 둔다. 활성 라우터가 죽으면 대기 라우터가 가상 IP를 넘겨받아 그대로 트래픽을 처리하므로, 호스트는 게이트웨이가 바뀐 줄도 모른 채 통신을 계속한다.

#4동작 과정

  1. 가상 게이트웨이 구성여러 라우터가 같은 가상 IP와 가상 MAC 주소를 공유하고, 우선순위에 따라 활성과 대기 역할을 나눈다. 호스트는 이 가상 주소를 기본 게이트웨이로 쓴다.
  2. 상태 감시활성 라우터가 주기적으로 살아 있음을 알리고, 대기 라우터는 그 신호가 오는지 확인한다. 이 신호는 상대가 정상인지 판단하는 기준이 된다.
  3. 역할 전환활성 라우터의 신호가 끊기면 대기 라우터가 가상 IP를 넘겨받아 활성이 된다. 호스트 입장에서는 같은 게이트웨이가 계속 응답하는 것처럼 보인다.

#1문제 상황

같은 데이터를 여러 수신자에게 보낼 때 유니캐스트로 각각 보내면 수신자 수만큼 복사본이 생겨 송신자와 네트워크에 부담이 커진다. 반대로 브로드캐스트로 보내면 관심 없는 장비까지 모두 받아 불필요한 트래픽이 퍼진다.

수신자 그룹에게만, 그리고 필요한 구간에서만 한 번씩 전달하려면 그룹 가입 상태를 관리하고 경로를 분배하는 별도의 프로토콜이 필요하다.

#2핵심 질문

하나의 송신 데이터를 관심 있는 다수 수신자에게, 각 구간에서 한 번씩만 효율적으로 전달하려면 어떻게 해야 할까?

#3동작 예시

수신자 호스트가 특정 그룹 주소에 가입하면, 그 가입 정보가 라우터를 통해 네트워크 안으로 전달된다. 라우터들은 송신자에서 수신자 방향으로 이어지는 경로만 골라 트래픽을 복제해 내려보낸다. 관심 없는 구간에는 데이터가 흐르지 않는다.

#4동작 과정

  1. 그룹 가입수신자 호스트가 IGMP로 원하는 멀티캐스트 그룹에 가입한다. 이 프로토콜은 호스트와 라우터 사이에서 그룹 가입 상태를 주고받는 역할을 한다.
  2. 경로 설정라우터들이 PIM 같은 프로토콜로 송신자에서 수신자까지의 분배 경로를 만든다. 이때 RPF 검사로 패킷이 올바른 방향에서 들어왔는지 확인해 루프를 막는다. SM은 수신자가 있는 곳으로만 경로를 뻗고, SSM·bidir은 특정 목적에 맞춘 방식이다.
  3. 전달·연결송신 데이터가 분기점마다 필요한 만큼만 복제되어 가입한 수신자에게 전달된다. 서로 다른 도메인에 걸친 그룹 정보는 MSDP로 주고받아 연결한다.

debug(조건부 debug 포함), traceroute, ping, SNMP, syslog 같은 도구로 네트워크 장애의 원인과 경로를 확인하는 진단 활동이다.

#1문제 상황

네트워크에 장애가 생기면 관리자는 어느 구간에서 무슨 일이 벌어졌는지 직접 확인해야 한다. 장비 설정만 보고 판단하거나 사용자 신고에만 의존하면, 패킷이 실제로 어디까지 도달했는지, 어느 홉에서 끊겼는지, 어떤 메시지가 오갔는지를 알 수 없다. 그래서 문제를 재현하고 원인을 좁히는 데 시간이 오래 걸린다.

#2핵심 질문

패킷이 어디까지 도달했고 어느 지점에서 끊겼는지, 그리고 장비가 무슨 메시지를 남겼는지를 어떻게 확인할 수 있을까?

#3동작 예시

목적지 서버로 가는 경로가 어디서 끊기는지 확인할 때, ping(연결 확인 메시지를 보내 응답을 재는 명령)으로 도달 여부를 먼저 보고, traceroute(경로를 한 홉씩 밟아 가며 확인하는 명령)로 어느 라우터까지 갔고 그 다음이 어디서 멈췄는지를 홉 단위로 본다. 여기에 debug(특정 이벤트가 일어날 때 장비가 상세 메시지를 실시간 출력하는 기능)를 켜 두면 그 구간에서 실제로 어떤 처리가 일어났는지도 함께 드러난다.

#4동작 과정

  1. 도달 여부 확인ping을 보내 응답이 오는지 확인한다. 응답이 오면 양방향 연결이 살아 있다는 것이고, 오지 않으면 다음 단계로 원인을 좁힌다.
  2. 경로 추적traceroute로 홉을 하나씩 지나가며 각 구간의 응답을 확인한다. 어느 홉에서 응답이 끊기는지 알면 문제 구간이 그 지점 근처로 좁혀진다.
  3. 내부 상태 관찰SNMP(장비 상태를 주기적으로 수집하는 관리 프로토콜)와 syslog(장비가 남기는 로그 메시지), debug로 장비 내부의 카운터·이벤트·오류 메시지를 확인해 원인을 확정한다.

Flexible NetFlow

트래픽을 플로우 단위로 분류·기록해 누가 무엇을 얼마나 주고받는지 통계로 수집하는 Cisco의 유연한 NetFlow 구현이다.

#1문제 상황

네트워크를 지나는 트래픽은 누가 어디로 얼마나 보내는지 알기 어렵다. 장비는 패킷을 목적지로 전달할 뿐, 그 흐름을 따로 기록하지 않으면 어떤 응용이 대역폭을 많이 쓰는지, 어느 통신이 비정상적으로 많은지를 파악할 수 없다. 그래서 용량 계획이나 이상 트래픽 탐지가 감에 의존하게 된다.

#2핵심 질문

어떤 출발지와 목적지 사이의 통신이 얼마나 많은 패킷과 바이트를 주고받는지 통계로 남길 수 있을까?

#3동작 예시

장비에 수집 규칙을 정의해, 같은 출발지 IP·목적지 IP·포트·프로토콜로 묶이는 패킷들을 하나의 흐름(플로우)으로 취급하게 한다. 그 흐름마다 패킷 수와 바이트 수를 세어 캐시에 쌓고, 일정 조건이 되면 그 기록을 수집 서버로 전송한다. 그래서 "이 서버로 가는 특정 포트 트래픽이 얼마나 되는가" 같은 질문에 숫자로 답할 수 있다.

#4동작 과정

  1. 플로우 정의레코드(무엇을 기록할지 정한 필드 묶음)와 매치 필드(흐름을 나누는 기준)를 정해, 어떤 패킷 조합을 하나의 흐름으로 볼지 규칙을 만든다.
  2. 수집과 집계정의한 기준에 맞는 패킷이 지나가면 캐시에 흐름별 패킷·바이트·시각 정보를 누적한다. 그래서 트래픽 사용량이 흐름 단위로 쌓인다.
  3. 내보내기캐시가 가득 차거나 시간이 되면 기록을 수집 서버로 전송한다. 그러면 관리 도구에서 누가 무엇을 얼마나 주고받는지 통계로 확인할 수 있다.

SPAN·RSPAN·ERSPAN

스위치 포트의 트래픽을 분석 장비로 복제해 보내는 포트 미러링 기법으로, 로컬은 SPAN, 원격은 RSPAN·ERSPAN을 쓴다.

#1문제 상황

스위치는 패킷을 목적지 포트로만 전달하므로, 분석 장비를 아무 포트에 꽂아도 남의 트래픽은 보이지 않는다. 그래서 문제를 분석하려면 대상 장비에 직접 들어가거나 통신을 끊고 그 지점에 장비를 넣어야 했다. 여러 포트의 트래픽을 한 곳에서 보고 싶어도 스위치가 원래 흘려보내지 않으니 방법이 없었다.

#2핵심 질문

통신을 방해하지 않으면서, 원하는 포트의 트래픽을 분석 장비로 그대로 복제해 볼 수 있을까?

#3동작 예시

스위치에서 특정 포트를 복제 원본(source)으로, 분석 장비가 연결된 포트를 복제 대상(destination)으로 지정한다. 그러면 원본 포트를 지나는 패킷이 원래 목적지로 가면서 동시에 복제본이 분석 포트로도 전달된다. 분석 장비는 실제 통신에 끼어들지 않고 그 복제본만 받아 들여다본다.

#4동작 과정

  1. 복제 원본 지정감시할 포트나 VLAN을 source로 정한다. 그래서 그 구간을 지나는 트래픽이 복제 대상이 된다.
  2. 복제 대상 지정분석 장비가 붙은 포트를 destination으로 정한다. 같은 스위치 안에서 처리하면 SPAN이다.
  3. 원격 전달원본과 분석 장비가 다른 스위치에 있으면 RSPAN(전용 VLAN으로 복제 트래픽을 실어 보내는 방식)을, 라우팅을 넘어 보내야 하면 ERSPAN(복제 트래픽을 IP 패킷으로 감싸 보내는 방식)을 쓴다.

#1문제 상황

#2핵심 질문

#3동작 예시

한 장비에서 다른 장비로 일정 간격마다 합성 트래픽(측정만을 위해 만든 시험 패킷)을 보내고 돌아오는 시간을 잰다. 이때 왕복 시간, 지연의 흔들림(지터), 손실 개수를 기록한다. 측정값이 정한 기준을 넘으면 그 자체를 이벤트로 삼아 경로 전환이나 알림 같은 후속 동작을 걸 수 있다.

#4동작 과정

  1. 측정 대상 지정어느 장비로, 무슨 종류의 시험(에코·지연·경로 추적 등)을, 몇 초 간격으로 보낼지 정의한다. 그래서 감시할 구간이 정해진다.
  2. 주기적 측정정의한 간격마다 합성 패킷을 보내고 응답 시간·지터·손실을 기록한다. 그래서 연결 품질이 시간에 따라 숫자로 쌓인다.
  3. 임계 판정과 연동기록값이 정한 임계치를 넘는지 판정하고, 넘으면 경로 전환·알림 같은 후속 동작을 실행한다. 그래서 품질이 나빠지기 전에 대응할 수 있다.

네트워크 장비가 많아지면 각 장비에 따로 접속해 설정을 넣고 상태를 확인해야 한다. 장비마다 화면과 명령이 달라 같은 작업을 반복하게 되고, 설정이 서로 어긋나도 전체를 한눈에 비교하기 어렵다. 그래서 구성·모니터링·관리가 장비 수에 비례해 느려지고 실수가 늘어난다.

#2핵심 질문

여러 장비의 설정과 상태를 한 곳에서 일관된 방식으로 적용하고 관리할 수 있을까?

#3동작 예시

중앙 컨트롤러가 관리 대상 장비를 등록해 두고, 관리자가 의도한 설정을 한 번 정의하면 그것을 장비들에 일괄 적용하는 방식으로 동작한다. 여기에 더해 AI 기반 워크플로는 수집된 상태 데이터를 분석해 이상 징후를 짚어 주고, 관리자가 그 결과를 근거로 조치하도록 돕는다.

#4동작 과정

  1. 장비 등록과 수집관리할 장비를 중앙에 등록하면 컨트롤러가 각 장비의 설정과 상태를 모아 온다. 그래서 전체 네트워크가 한 곳에서 보인다.
  2. 설정 일괄 적용관리자가 정의한 구성을 여러 장비에 한 번에 내려보낸다. 그래서 같은 작업을 장비마다 반복하지 않아도 되고 설정이 일관되게 유지된다.
  3. 모니터링과 분석수집한 상태를 계속 감시하고, AI 기반 워크플로가 이상 징후를 분석해 제시한다. 그래서 문제를 미리 살피고 조치할 수 있다.

NETCONF와 RESTCONF

YANG 데이터 모델을 기반으로 네트워크 장비를 프로그램 방식으로 구성·조회하는 표준 프로토콜로, NETCONF는 XML, RESTCONF는 REST/HTTP를 쓴다.

#1문제 상황

장비를 설정하려면 사람이 장비마다 접속해 명령을 직접 입력해야 한다. 장비 제조사와 모델마다 명령 형식이 달라 자동화 도구가 공통으로 다루기 어렵고, 명령 출력은 사람이 읽는 텍스트라 프로그램이 결과를 안정적으로 해석하기도 힘들다. 그래서 설정과 조회를 코드로 자동화하기가 어렵다.

#2핵심 질문

장비마다 다른 명령 대신, 정해진 데이터 형식으로 구성을 넣고 조회할 수는 없을까?

#3동작 예시

YANG(장비가 가질 수 있는 설정·상태 항목을 정의한 데이터 모델)으로 "무엇을 설정할 수 있는가"가 정해져 있으면, 클라이언트는 그 모델에 맞춰 값을 보낸다. 인터페이스 주소 하나를 바꾸는 작업도 명령어 문자열이 아니라 정해진 필드에 값을 채워 보내는 식이라, 똑같은 요청을 여러 장비에 반복 적용할 수 있다. NETCONF는 XML 형식으로, RESTCONF는 HTTP 기반 REST 방식으로 이 요청을 주고받는다.

#4동작 과정

  1. 모델 확인클라이언트가 장비가 제공하는 YANG 모델을 읽어 어떤 항목을 설정·조회할 수 있는지 파악한다. 그래서 사람마다 다른 명령을 몰라도 대상이 명확해진다.
  2. 요청 전송바꿀 값을 모델에 맞춘 요청으로 만들어 보낸다. NETCONF는 XML로, RESTCONF는 HTTP 메서드와 경로로 전달한다.
  3. 적용과 확인장비가 요청을 적용하고 결과를 같은 모델 형식으로 돌려준다. 그래서 프로그램이 응답을 안정적으로 해석하고 자동화를 이어갈 수 있다.

#1문제 상황

장비를 처음 설치하면 콘솔 케이블을 꽂거나 원격에서 Telnet·SSH로 접속해 설정을 바꾼다. 이때 별도 인증 없이 접속이 허용되면, 같은 네트워크에 있는 사람이나 물리적으로 장비에 닿을 수 있는 사람이 곧바로 관리자 권한을 얻게 된다.

기본 설정 상태에서는 콘솔과 VTY(원격 접속용 가상 회선)에 비밀번호가 걸려 있지 않은 경우가 많고, 걸어 두더라도 누가 접속했는지 구분하지 못한다. 접속 경로마다 따로 관리하면 어떤 계정이 어떤 통로로 들어왔는지 추적할 수 없고, 퇴사자 계정을 지우려면 장비마다 일일이 확인해야 한다.

#2핵심 질문

장비에 들어오는 모든 관리 접근 경로를 하나의 인증 기준으로 통제하려면 어떻게 해야 하는가?

#3동작 예시

관리자가 SSH로 장비에 접속하면 장비는 아이디와 비밀번호를 요구한다. 이때 입력값을 장비에 저장된 로컬 계정 목록과 대조해 일치할 때만 명령 프롬프트를 내주고, 불일치하면 세션을 끊는다.

#4동작 과정

  1. 접근 경로 구분콘솔, VTY, 보조(AUX) 포트를 각각 하나의 line으로 나누고 어떤 경로를 인증 대상으로 삼을지 정한다.
  2. 인증 방식 지정각 line에 login 방식(로컬 계정 대조, 또는 외부 AAA 서버 위임)을 묶어 접속 시 자격 증명을 요구하게 한다.
  3. 자격 검증과 세션 부여입력된 계정이 통과하면 관리 세션을 열어 주고, 실패하면 접속을 거부한다. 그 결과 모든 관리 통로가 동일한 기준으로 통제된다.

라인과 로컬 사용자 인증

장치의 line(콘솔·VTY) 설정에 로컬 username/password와 login 방식을 묶어 접속 자체를 인증하는 방법.

#1문제 상황

초기 장비는 line 설정에 비밀번호 한 줄만 걸어 두는 방식으로 접속을 막았다. 이 방식은 비밀번호를 아는 사람이면 누구나 같은 권한으로 들어올 수 있고, 접속한 사람이 누구인지 장비가 기록하지 못한다.

또 콘솔용 비밀번호와 VTY용 비밀번호를 따로 관리하면, 한쪽만 바뀌어도 다른 쪽은 그대로 남아 보안 구멍이 된다. 사용자별 권한을 나누거나 특정 계정만 차단하려면 결국 계정 개념이 필요하다.

#2핵심 질문

장비에 계정을 만들어 두고, 각 접속 line이 그 계정으로 인증하도록 하려면 어떻게 설정하는가?

#3동작 예시

장비에 username admin password 로 계정을 하나 만들고, line vty 0 4 안에서 login local 을 지정한다. 이후 SSH로 접속하면 장비는 이 로컬 계정 목록과 대조해 admin 계정이 맞을 때만 프롬프트를 연다.

#4동작 과정

  1. 계정 생성장비에 사용자 이름과 비밀번호를 등록해 로컬 사용자 목록을 만든다. 이제 장비가 "누구인지"를 판별할 기준이 생긴다.
  2. line에 login 방식 묶기콘솔·VTY line에 login local 을 지정해, 접속 시 로컬 계정 대조를 요구하도록 연결한다.
  3. 접속 시 검증접속한 사용자가 입력한 자격 증명을 로컬 목록과 비교해 일치하면 세션을 열고, 다르면 접속을 끊는다. 그 결과 line마다 누가 들어왔는지 구분되는 인증이 적용된다.

AAA 인증·인가

인증(Authentication)·인가(Authorization)·과금(Accounting)을 외부 서버로 위임해 중앙에서 사용자 접근을 관리하는 프레임워크.

#1문제 상황

장비마다 로컬 계정을 따로 만들면, 관리하는 장비가 늘어날수록 계정을 반복 생성하고 비밀번호를 각각 바꿔야 한다. 사용자 권한을 한 번에 조정하거나 퇴사자 계정을 일괄 삭제하기도 어렵다.

또 로컬 인증만으로는 "누가 어떤 명령을 실행했는가"를 별도로 모으기 어렵다. 접속은 통과했지만 특정 명령은 막고 싶다는 식의 세밀한 통제를 장비 안에서만 처리하려면 설정이 장비 수만큼 흩어진다.

#2핵심 질문

인증과 권한 부여, 사용 기록을 중앙 서버에 위임해 여러 장비를 한 기준으로 관리하려면 어떻게 하는가?

#3동작 예시

관리자가 장비에 접속하면 장비는 자격 증명을 직접 판단하지 않고 AAA 서버로 보낸다. 서버가 "이 사용자는 인증 성공, 관리자 권한 부여"라고 답하면 장비는 그 범위의 명령을 허용하고, 서버는 이 접속과 실행 내역을 기록한다.

#4동작 과정

  1. AAA 활성화와 서버 등록장비에서 AAA를 켜고 인증·인가를 담당할 서버 주소와 공유 키(장비와 서버가 서로를 확인하는 암호)를 지정한다.
  2. 방식 목록 정의인증과 인가에 사용할 순서 목록(method list)을 만들어, 어떤 순서로 서버를 조회하고 실패 시 로컬로 넘어갈지 정한다.
  3. 요청 위임과 결과 적용접속이나 명령 시점에 장비가 서버로 판단을 요청하고, 돌아온 결과대로 세션을 열거나 명령을 허용·차단한다. 그 결과 여러 장비가 동일한 중앙 기준으로 관리된다.

인프라 보안 기능

포트 보안·DHCP snooping·동적 ARP 검사·IP Source Guard 등 스위치/라우터 계층에서 위협을 차단하는 기능 묶음.

#1문제 상황

스위치에 아무 포트나 연결할 수 있는 환경에서는, 직원 책상 아래에 허브나 공유기를 몰래 물려 여러 기기를 붙이거나, 가짜 DHCP 서버를 띄워 단말에 잘못된 게이트웨이 정보를 나눠줄 수 있다.

또 공격자가 자신의 MAC 주소를 계속 바꿔 가며 같은 IP를 주장하면 ARP(IP와 MAC을 짝지어 주는 프로토콜) 응답이 오염되어 트래픽이 공격자에게 돌아간다. 이런 위협은 라우터의 접근 목록만으로는 스위치 내부에서 걸러지지 않는다.

#2핵심 질문

스위치와 라우터 계층에서 허가되지 않은 단말·서버·주소 위조를 어떻게 차단하는가?

#3동작 예시

액세스 포트에 switchport port-security maximum 1 을 걸어 두면, 그 포트에 처음 학습된 MAC 주소 하나만 통과한다. 이후 다른 기기를 연결하면 위반으로 판단해 포트를 차단하고, 그 자리에서 통신이 끊긴다.

#4동작 과정

  1. 포트 보안 적용액세스 포트에 허용할 MAC 주소 수와 위반 시 동작을 지정해, 정해진 기기 외에는 연결되지 않게 한다.
  2. DHCP snooping·IP Source Guard 설정신뢰할 수 있는 포트에서만 DHCP 응답을 허용해 가짜 서버를 막고, 단말이 실제로 받은 IP와 MAC이 아니면 전송을 걸러 주소 위조를 차단한다.
  3. 동적 ARP 검사 연동snooping이 만든 IP·MAC·포트 매핑 표를 기준으로 ARP 패킷을 검사해, 표와 어긋나는 응답을 버려 트래픽 탈취를 막는다.

ACL

출발지·목적지 주소와 포트, 프로토콜 조건으로 패킷의 통과·차단을 순차 규칙으로 결정하는 접근 제어 목록.

#1문제 상황

네트워크를 연결만 해 두면 어느 대역이든 서로 통신할 수 있어, 관리 구역이나 서버 대역으로 원하지 않는 트래픽이 그대로 흘러 들어간다. 라우터는 목적지까지 가는 경로만 알 뿐, "이 출발지는 이 목적지로 못 간다" 같은 판단은 하지 않는다.

장비의 Telnet·SSH 접근을 특정 대역으로만 제한하려 해도, 무엇을 허용하고 무엇을 막을지 규칙으로 표현할 수단이 없다. 결국 트래픽을 주소와 포트 단위로 걸러낼 기준이 필요하다.

#2핵심 질문

주소·포트·프로토콜 조건으로 패킷의 통과와 차단을 규칙 순서대로 결정하려면 어떻게 하는가?

#3동작 예시

ACL에 "출발지 10.0.0.0/24 대역에서 관리 대역 172.16.10.0/24로 가는 트래픽을 허용"하는 규칙을 넣고 인터페이스에 적용하면, 그 대역 출발 트래픽만 통과하고 나머지 출발지는 기본적으로 차단된다.

#4동작 과정

  1. 규칙 목록 작성허용·차단할 조건을 출발지·목적지 주소와 포트, 프로토콜로 나열해 위에서 아래로 검사할 ACL을 만든다.
  2. 인터페이스·방향에 적용ACL을 인터페이스와 방향(들어오는지 나가는지)에 묶어, 해당 트래픽이 검사를 거치게 한다.
  3. 순차 매칭과 판정패킷을 규칙과 위에서부터 비교해 처음 일치하는 규칙의 허용·차단을 적용하고, 끝까지 일치하는 규칙이 없으면 마지막 기본 규칙에 따라 차단한다.

CoPP

컨트롤 플레인으로 향하는 트래픽을 정책으로 분류·속도 제한해 CPU 자원 고갈과 라우팅 프로토콜 공격을 막는 기능.

#1문제 상황

라우터의 CPU는 데이터를 실제로 전달하는 일뿐 아니라 라우팅 프로토콜, 관리 접속, ARP 같은 제어용 트래픽도 처리한다. 이 제어용 트래픽이 한꺼번에 몰리면 CPU가 감당하지 못하고 라우팅 자체가 흔들린다.

공격자가 제어 패킷을 대량으로 퍼붓거나, 설정 실수로 제어 트래픽이 폭주하면 정작 처리해야 할 정상 제어 패킷까지 밀려 낙하한다. CPU를 보호할 별도 장치가 없는 라우터에서는 이 상황이 곧 서비스 장애로 이어진다.

#2핵심 질문

컨트롤 플레인으로 향하는 트래픽을 분류하고 속도를 제한해 CPU를 지키려면 어떻게 하는가?

#3동작 예시

CoPP 정책에 "라우팅 프로토콜 트래픽은 초당 정해진 양까지 허용, 초과분은 버림"이라는 규칙을 만들면, 라우팅 패킷이 그 한도를 넘길 때 초과분이 CPU로 전달되기 전에 걸러진다.

#4동작 과정

  1. 트래픽 분류컨트롤 플레인으로 가는 패킷을 종류별(라우팅 프로토콜, 관리 접속, ARP 등)로 나누는 분류 규칙을 만든다.
  2. 클래스별 정책 연결분류한 각 클래스에 허용할 속도와 초과 시 처리(버림 등)를 지정한 정책을 묶는다.
  3. 컨트롤 플레인에 적용정책을 컨트롤 플레인에 붙여, CPU로 가는 트래픽이 이 한도 검사를 거치게 한다. 그 결과 과도한 제어 트래픽이 CPU 자원을 고갈시키지 못한다.

REST API 보안

RESTCONF·HTTPS 기반 API 접근을 인증·인가와 전송 암호화(TLS)로 보호해 관리 인터페이스를 안전하게 노출하는 원칙.

#1문제 상황

네트워크 장비를 RESTCONF 같은 REST API로 관리하면, 사람이 콘솔에 로그인하지 않고도 HTTP 요청으로 설정을 읽고 바꿀 수 있다. 편리한 대신 API 엔드포인트가 네트워크에 열려 있으면 누구든 요청을 보내 설정을 조회하거나 변경할 수 있다는 위험이 생긴다. 기존의 CLI 접속은 장비별 계정과 접속 제어로 막았지만, API는 표준 HTTP라서 그대로 노출하면 인증 없이 접근될 수 있다.

#2핵심 질문

API로 장비를 관리할 때, 요청을 보낸 주체가 누구인지 확인하고 그에게 허용된 작업만 수행하게 하려면 어떻게 해야 하는가?

#3동작 예시

관리 서버가 장비에 GET https://device/restconf/data/interfaces 를 보낸다고 하자. 이때 요청 헤더에 인증 정보가 없으면 장비는 401로 거절한다. 유효한 자격 증명을 담아 보내면 장비는 인증을 통과시킨 뒤, 그 계정에 부여된 권한 범위 안에서만 응답한다. 전송 구간은 TLS(전송 계층 암호화)로 감싸여 URL·헤더·본문이 암호화된다.

#4동작 과정

  1. 인증(Authentication)클라이언트가 자격 증명이나 토큰을 요청에 실어 보내고, 장비는 그 주체가 등록된 사용자인지 먼저 확인한다. 통과하지 못하면 요청은 처리되지 않는다.
  2. 인가(Authorization)인증된 주체에게 어떤 데이터와 조작이 허용되는지 권한을 대조해, 읽기만 가능한 계정이 설정을 바꾸는 요청을 보내면 거부한다. 그래서 같은 API라도 계정별로 할 수 있는 일이 달라진다.
  3. 전송 보호(TLS)HTTPS로 통신 구간을 암호화해 자격 증명과 설정 데이터가 중간에서 노출되거나 변조되지 않게 한다. 결과적으로 관리 인터페이스는 인증·인가·암호화를 모두 통과한 요청만 처리한다.

#5한 줄 요약

REST API 보안API로 들어오는 모든 요청을 인증으로 신원 확인하고 인가로 권한을 제한하며 TLS로 전송을 암호화해 관리 인터페이스를 안전하게 노출하는 것

네트워크 보안 설계 구성 요소

방화벽·IPS·VPN·정책 세그멘테이션 등 위협을 계층별로 방어하도록 네트워크 보안 아키텍처를 구성하는 요소들.

#1문제 상황

네트워크를 하나의 신뢰 구역으로만 운영하면 외부에서 침입이 들어왔을 때 내부 전체가 그대로 노출된다. 경계에 장비 한 대만 세워 두는 방식은 한 지점이 뚫리면 안쪽 자원을 막을 추가 방어선이 없고, 위협이 어떤 경로로 들어오는지 구분하지 못한다. 그래서 구역마다 다른 수준의 방어를 두는 계층적 설계가 필요해졌다.

#2핵심 질문

여러 종류의 위협을 각기 다른 위치에서 막으려면, 네트워크 보안 아키텍처에 어떤 구성 요소를 어떤 층에 배치해야 하는가?

#3동작 예시

사용자 구역에서 데이터센터 구역으로 가는 트래픽을 생각하자. 경계 방화벽은 허용된 포트와 주소만 통과시키고, 내부 구간의 IPS(침입 방지 시스템)는 통과한 트래픽의 내용을 검사해 공격 패턴을 차단한다. 원격 사용자는 VPN(가상 사설망)으로 암호화 터널을 맺어 내부에 들어오고, 서버 구역은 별도 세그먼트로 나뉘어 있어 침해가 나도 옆 구역으로 번지지 않는다. 같은 트래픽이 위치마다 다른 검사를 받는 구조다.

#4동작 과정

  1. 경계 방어방화벽과 IPS를 신뢰 경계에 두고 허용 규칙과 공격 서명으로 외부에서 들어오는 트래픽을 걸러낸다. 그래서 명시적으로 허용된 흐름만 내부로 진입한다.
  2. 접속 보호VPN으로 원격·지사 트래픽을 암호화된 터널로 묶어 전송 구간 노출을 막는다. 그래서 외부망을 지나도 내부 통신 내용이 보호된다.
  3. 구역 분리세그멘테이션으로 내부를 목적별 구역으로 나누고 구역 간 이동에 정책을 적용한다. 그래서 한 구역이 침해돼도 다른 구역으로 확산되는 범위가 제한된다.

위협 방어와 엔드포인트 보안

침입 방지·악성코드 차단·엔드포인트 검사(예: AMP, NAC)로 단말과 내부 자원을 위협으로부터 지키는 접근.

#1문제 상황

경계에서 트래픽을 걸러도 이미 내부에 들어온 단말이 악성코드에 감염되면 그 단말을 통해 공격이 퍼진다. 기존의 정적 방어는 알려진 공격 패턴만 막아 새로 나타난 위협을 놓치고, 단말이 어떤 상태인지 검사하지 않으면 감염된 기기가 그대로 내부 자원에 접근한다. 그래서 통과 여부만 보던 방식으로는 단말에서 시작되는 위협을 막을 수 없다.

#2핵심 질문

내부로 들어온 트래픽과 단말 자체를 검사해, 감염된 기기와 악성 행위를 내부 자원에 도달하기 전에 차단하려면 어떻게 해야 하는가?

#3동작 예시

직원 노트북이 내부 서버에 접속하려 한다. NAC(네트워크 접근 제어)는 접속 시점에 그 단말의 보안 상태를 검사해, 백신이 최신이 아니거나 감염 의심이 있으면 격리 구역으로 보낸다. 정상 단말만 내부 구역에 들어가고, 통과한 트래픽도 IPS가 악성 행위 패턴을 검사해 차단한다. 단말 하나의 상태가 그 단말의 접근 가능 범위를 결정한다.

#4동작 과정

  1. 침입 방지IPS가 네트워크를 지나는 트래픽의 내용을 실시간으로 검사해 공격·스캔·악성 패턴을 탐지하면 해당 흐름을 차단한다. 그래서 경계를 통과한 뒤의 공격도 내부에서 걸러진다.
  2. 악성코드 차단위협 방어 기능이 파일과 통신에서 알려진 악성코드와 의심 행위를 탐지해 실행·전송을 막는다. 그래서 감염 시도가 단말과 서버에 도달하기 전에 끊긴다.
  3. 엔드포인트 검사NAC가 단말 접속 시 보안 자세(백신·패치 등 상태)를 확인하고 기준을 못 채우면 격리한다. 그래서 자격이 검증된 정상 단말만 내부 자원에 접근한다.

차세대 방화벽·TrustSec·MACsec

애플리케이션 인지형 차세대 방화벽, 그룹 기반 세그멘테이션(TrustSec/SGT), 링크 계층 암호화(MACsec)로 내부 통신을 보호하는 기술.

#1문제 상황

전통적 방화벽은 IP 주소와 포트만 보고 통과 여부를 정해, 같은 포트를 쓰는 정상 앱과 악성 앱을 구분하지 못한다. 내부 통신도 주소 기반 규칙으로 관리하면 사용자와 기기가 이동할 때마다 규칙이 흔들리고, 구간을 지나는 데이터는 암호화되지 않아 물리적으로 연결만 되면 내용을 읽을 수 있다. 그래서 주소가 아니라 대상과 내용을 기준으로 내부까지 보호할 방법이 필요해졌다.

#2핵심 질문

애플리케이션을 인식해 통제하고, 주소 대신 그룹으로 내부 접근을 제한하며, 구간 데이터까지 암호화하려면 무엇이 필요한가?

#3동작 예시

사용자 그룹 A가 서버 그룹 B에 접속한다고 하자. 차세대 방화벽은 이 트래픽이 어떤 애플리케이션인지 식별해 허용·차단을 결정한다. TrustSec은 A와 B에 붙은 SGT(보안 그룹 태그)를 보고 A에서 B로 가는 흐름만 허용하고 나머지 그룹 조합은 막는다. 두 스위치를 잇는 링크는 MACsec(링크 계층 암호화)으로 암호화되어, 같은 링크를 지나는 데이터가 노출되지 않는다.

#4동작 과정

  1. 애플리케이션 인식차세대 방화벽이 트래픽의 애플리케이션과 사용자·내용을 식별해, 포트가 아니라 실제 앱과 행위를 기준으로 정책을 적용한다. 그래서 같은 포트를 쓰는 위험한 흐름도 구분해 차단할 수 있다.
  2. 그룹 기반 세그멘테이션TrustSec이 사용자·기기에 SGT라는 보안 그룹 태그를 부여하고, 구간을 지날 때 그 태그로 접근을 통제한다. 그래서 주소가 바뀌어도 그룹 정책에 따라 내부 이동이 제한된다.
  3. 링크 암호화MACsec이 이더넷 링크 구간의 프레임을 암호화하고 무결성을 검증한다. 그래서 링크를 도청하거나 변조하려 해도 데이터가 보호된다.

자동화 도메인 개요와 Python 기초

네트워크 자동화가 설정·검증·수집 작업을 코드로 반복 실행하는 영역이며, Python 은 그 코드를 작성하는 대표 언어로 변수·자료형·조건문·반복문·함수·모듈 같은 기본 구성 요소로 스크립트를 이룬다.

#1문제 상황

장비 수가 늘면 같은 설정과 확인 작업을 사람이 장비마다 반복해야 하고, 오타나 순서 실수로 결과가 장비마다 달라진다. 명령을 손으로 입력하는 방식은 작업량에 비례해 시간이 늘고, 같은 일을 두 번 하면 같은 실수가 재발할 수 있다. 그래서 설정·검증·수집을 사람 손 대신 코드로 반복 실행하려는 자동화가 필요해졌다.

#2핵심 질문

반복되는 네트워크 작업을 사람이 매번 손으로 하지 않고 코드로 실행하려면, 그 코드를 어떤 기본 요소로 작성하는가?

#3동작 예시

여러 장비에서 인터페이스 상태를 모아 출력하는 스크립트를 생각하자. 장비 주소 목록을 변수에 담고, for 반복문으로 목록의 각 주소에 대해 접속과 명령 실행을 반복한 뒤, 결과를 조건문으로 검사해 정상 여부를 표시한다. 이 동작을 함수로 묶어 두면 장비 목록만 바꿔 같은 처리를 다시 실행할 수 있다. 장비가 늘어도 코드는 그대로다.

#4동작 과정

  1. 데이터 담기변수에 장비 주소·명령 같은 값을 저장하고, 문자열·숫자·리스트·딕셔너리 같은 자료형으로 여러 값을 구조화한다. 그래서 반복해서 쓸 값과 목록을 코드가 다룰 수 있게 된다.
  2. 흐름 제어조건문으로 값에 따라 다른 처리를 고르고, 반복문으로 목록의 항목마다 같은 작업을 실행한다. 그래서 사람이 장비 수만큼 손으로 하던 반복이 코드 한 번의 실행으로 대체된다.
  3. 묶고 재사용자주 쓰는 처리를 함수로 정의하고 관련 기능을 모듈로 나눠 불러온다. 그래서 같은 로직을 여러 스크립트에서 반복 작성하지 않고 재사용한다.

JSON 인코딩 파일

JSON 은 키-값 쌍과 배열로 데이터를 표현하는 텍스트 기반 데이터 교환 형식으로, 중괄호·대괄호·쉼표·따옴표 규칙을 지켜야 유효한 파일이 되며 API 요청·응답 본문에 널리 쓰인다.

#1문제 상황

서로 다른 시스템이 데이터를 주고받으려면 양쪽이 같은 형식을 이해해야 한다. 형식이 정해지지 않은 텍스트를 주고받으면 어디서 값이 시작하고 끝나는지 구분할 수 없어, 프로그램이 그 내용을 안정적으로 읽지 못한다. 그래서 구조를 명확히 표시하는 규칙을 가진 데이터 형식이 필요해졌고, 그중 하나가 키-값 쌍과 배열로 표현하는 JSON이다.

#2핵심 질문

데이터를 교환할 때 양쪽 프로그램이 같은 구조로 해석하도록, JSON은 어떤 규칙을 지켜야 유효한 파일이 되는가?

#3동작 예시

장비 정보 하나를 표현한다고 하자. 객체는 중괄호 안에 "hostname": "sw1" 같은 키-값 쌍을 쉼표로 나열하고, 여러 장비를 담을 때는 대괄호 안에 객체를 나열한다. 키와 문자열 값은 큰따옴표로 감싸고, 각 쌍 사이와 배열 원소 사이에는 쉼표를 넣는다. 이 규칙을 어기면 파일을 읽는 쪽에서 파싱 오류가 난다.

#4동작 과정

  1. 키-값 쌍 작성객체를 중괄호로 열고 "키": 값 형태로 항목을 적으며, 키는 항상 큰따옴표로 감싼다. 그래서 각 값이 어떤 이름에 대응하는지 분명해진다.
  2. 구조 중첩여러 항목을 담을 때 대괄호로 배열을 만들고 그 안에 값이나 객체를 쉼표로 나열한다. 그래서 목록과 중첩 구조를 표현할 수 있다.
  3. 문법 검사모든 괄호·대괄호가 짝을 이루고, 쉼표 위치와 따옴표가 규칙에 맞는지 확인한다. 그래서 이 조건을 모두 만족할 때만 유효한 JSON 파일로 인식된다.

데이터 모델링 언어 YANG

YANG 은 네트워크 장비의 설정과 상태 데이터를 계층적 트리 구조로 정의하는 데이터 모델링 언어로, NETCONF·RESTCONF 같은 프로토콜이 주고받는 데이터의 스키마 역할을 한다.

#1문제 상황

장비를 자동으로 설정하려면 외부 프로그램이 장비에 명령을 보내야 한다. 이때 각 제조사와 장비마다 설정 항목 이름과 구조가 제각각이면, 프로그램은 장비 종류마다 다른 형식을 따로 알아야 한다.

예전에는 사람이 쓰는 CLI 명령 문자열을 그대로 흉내 내어 보내는 방식이 흔했다. 명령 문자열은 장비가 바뀌면 순서와 표기가 달라지고, 지금 장비에 어떤 설정 항목이 존재하는지 프로그램이 미리 알 수 없어 오타나 잘못된 값도 그대로 전달됐다. 결국 자동화 코드가 장비마다 새로 작성돼야 했다.

#2핵심 질문

설정과 상태 데이터를 장비와 무관하게 같은 구조로 주고받으려면 그 구조를 무엇으로 정의해야 하는가?

#3동작 예시

YANG 모델 하나에 인터페이스 목록과 각 인터페이스의 이름·사용 여부·IP 주소 같은 항목이 트리로 정의돼 있다고 하자. 프로그램이 이 모델을 읽으면 어떤 항목이 있고 값이 숫자인지 문자열인지 알 수 있고, NETCONF나 RESTCONF로 데이터를 요청할 때도 모델에 정의된 경로로만 접근한다.

#4동작 과정

  1. 모델 정의YANG 파일에 설정·상태 데이터를 계층적 트리(상위 항목 아래에 하위 항목이 매달리는 구조)로 적고, 각 항목의 타입과 필수 여부를 명시한다.
  2. 프로토콜 전달NETCONF·RESTCONF 같은 프로토콜이 이 모델을 스키마(데이터의 형식을 정해 둔 틀)로 삼아, 요청과 응답 데이터를 모델에 맞는 구조로 주고받는다.
  3. 검증과 처리장비와 프로그램이 모두 같은 모델을 기준으로 값을 검사하므로, 형식이 어긋난 요청은 미리 걸러지고 남은 데이터는 정해진 구조대로 저장·조회된다.

Catalyst Center·SD-WAN Manager API

Cisco Catalyst Center 와 SD-WAN Manager 가 제공하는 REST 기반 API 로, 인증 후 HTTP 요청을 보내 사이트·장비·정책·토폴로지 같은 네트워크 정보를 조회하고 설정을 자동화한다.

#1문제 상황

네트워크가 커지면 사이트·장비·정책을 사람이 장비마다 하나씩 접속해 설정하기 어려워진다. 관리 화면에서 클릭으로 처리하던 작업도 반복 횟수가 늘면 시간이 많이 들고, 같은 설정을 여러 장비에 똑같이 적용했는지 확인하기도 힘들다.

이때 관리 도구가 제공하는 기능을 외부 프로그램이 직접 불러 쓸 수 없다면, 자동화는 결국 사람이 화면을 조작하는 수준에 머문다. 조회 결과를 다른 시스템과 연동하거나 대량 변경을 스크립트로 처리하려면, 관리 도구의 데이터에 프로그램이 접근할 수 있는 통로가 필요하다.

#2핵심 질문

관리 도구가 가진 정보와 설정 기능을 외부 프로그램이 표준 방식으로 호출해 자동화하려면 어떻게 해야 하는가?

#3동작 예시

프로그램이 먼저 인증을 거쳐 토큰(일정 시간 유효한 접근 증명)을 받는다. 그다음 사이트 목록을 조회하는 주소로 HTTP 요청을 보내면 JSON 형식의 응답이 돌아오고, 같은 방식으로 특정 장비의 상태를 읽거나 정책을 생성·수정하는 요청을 보내 설정을 바꾼다.

#4동작 과정

  1. 인증관리 도구에 아이디와 비밀번호 같은 자격 증명을 보내 토큰을 발급받고, 이후 모든 요청에 이 토큰을 함께 실어 보낸다.
  2. 요청 전송조회는 읽기 방식, 생성·변경은 쓰기 방식의 HTTP 요청을 정해진 주소로 보내고, 사이트·장비·정책·토폴로지 같은 대상을 주소와 데이터로 지정한다.
  3. 응답 처리돌아온 상태 코드로 성공·실패를 판단하고 JSON 본문에서 필요한 값을 꺼내, 다음 자동화 단계나 다른 시스템에 넘긴다.

REST API 응답 코드와 페이로드

REST 호출의 결과를 알리는 HTTP 상태 코드(200·201·400·401·404·500 등)와 응답 본문(JSON 페이로드)의 의미를 해석해, 요청 성공·인증 실패·잘못된 입력·서버 오류를 구분한다.

#1문제 상황

자동화 프로그램이 REST 요청을 보내면 응답이 항상 성공으로 오지 않는다. 인증이 풀렸거나, 주소가 틀렸거나, 보낸 값이 규칙에 맞지 않거나, 서버 쪽 문제가 생길 수 있다.

그런데 응답 본문만 보고 성공 여부를 판단하면 문제가 생긴다. 인증 실패와 정상 조회가 모두 어떤 데이터를 담아 돌아올 수 있어서, 프로그램은 실패를 성공으로 착각하거나 원인을 구분하지 못한 채 다음 작업을 계속 진행하게 된다.

#2핵심 질문

REST 요청의 결과를 정확히 판단해 성공과 각 실패 원인을 구분하려면 무엇을 읽어야 하는가?

#3동작 예시

사이트 목록을 조회하는 요청에 대해 응답 코드 200과 JSON 본문이 오면 조회 성공으로 보고 본문에서 목록을 꺼낸다. 반면 토큰 없이 보낸 요청에 401이 오면 인증 실패로 판단해 토큰을 다시 받고, 본문에 규칙에 어긋난 값이 있어 400이 오면 보낸 데이터를 고쳐 다시 요청한다.

#4동작 과정

  1. 상태 코드 확인응답의 HTTP 상태 코드(요청 결과를 숫자로 알리는 표시)를 먼저 보고, 200·201은 성공, 400은 잘못된 입력, 401은 인증 실패, 404는 대상 없음, 500은 서버 오류로 구분한다.
  2. 본문 해석성공이면 JSON 페이로드(응답에 담겨 온 실제 데이터)에서 필요한 값을 꺼내고, 실패면 본문의 오류 설명을 읽어 원인을 파악한다.
  3. 후속 조치 결정인증 문제면 토큰을 갱신하고, 입력 문제면 값을 고치고, 서버 문제면 잠시 후 다시 시도하는 식으로 원인에 맞게 다음 동작을 정한다.

#5한 줄 요약

REST 응답 처리상태 코드로 성공과 실패 원인을 가르고 페이로드로 실제 결과를 얻는 것

EEM 애플릿 작성

EEM(Embedded Event Manager) 애플릿은 장비 내부의 이벤트(로그·SNMP·타이머 등)를 감지하면 미리 정의한 CLI 명령을 자동 실행하도록 event·action 구조로 작성하는 소형 스크립트다.

#1문제 상황

장비에서 특정 상황이 생길 때마다 관리자가 직접 접속해 명령을 쳐야 한다면 대응이 늦는다. 인터페이스가 내려가거나 로그에 이상한 문구가 찍히는 순간에 사람이 곧바로 알아채기 어렵고, 심야나 휴일에는 더욱 그렇다.

외부 관리 서버가 이벤트를 감시하고 명령을 대신 실행하는 방법도 있지만, 그 서버가 닿지 않거나 장비 자체가 독립적으로 동작해야 하는 상황에서는 쓸 수 없다. 장비 안에서 스스로 이벤트를 감지하고 정해 둔 명령을 실행하는 기능이 필요하다.

#2핵심 질문

장비가 스스로 특정 이벤트를 감지해 정해 둔 명령을 자동으로 실행하게 하려면 어떻게 작성해야 하는가?

#3동작 예시

"인터페이스가 내려갔다는 로그가 찍히면, 그 로그 내용과 인터페이스 상태를 파일로 저장한다"는 동작을 애플릿 하나로 작성한다고 하자. event 부분에 감시할 로그 문구를 적고, action 부분에 저장할 명령을 적으면, 그 문구가 실제로 찍히는 순간 장비가 스스로 명령을 실행한다.

#4동작 과정

  1. event 정의감시할 대상(로그·SNMP 알림·타이머 등)과 그중 어떤 조건이 발생하면 애플릿을 깨울지 적는다.
  2. action 정의이벤트가 발생했을 때 실행할 CLI 명령을 순서대로 적고, 필요하면 이벤트에서 뽑은 값을 명령에 넘긴다.
  3. 실행과 결과조건이 충족되면 장비가 사람 개입 없이 명령을 실행해 설정 변경·문제 수집·데이터 저장을 처리하고, 그 결과가 다시 로그나 파일로 남는다.

#5한 줄 요약

EEM 애플릿장비 내부 이벤트를 감지해 미리 정한 명령을 사람 없이 자동 실행하게 하는 것

에이전트 vs 에이전트리스 오케스트레이션

오케스트레이션 방식에서 에이전트 기반은 각 장비에 상주하는 소프트웨어가 관리 서버와 통신하는 구조이고, 에이전트리스는 장비에 추가 설치 없이 SSH·NETCONF·RESTCONF 같은 표준 프로토콜로 외부에서 직접 제어하는 구조다.

#1문제 상황

여러 장비를 중앙에서 관리하려면 관리 서버가 각 장비의 상태를 읽고 설정을 내려보내야 한다. 이때 장비와 서버가 어떤 방식으로 연결되느냐에 따라 설치 부담과 호환성이 달라진다.

장비마다 별도 소프트웨어를 설치해 통신하는 방식은 세밀한 제어가 가능하지만, 그 소프트웨어를 배포·갱신·관리해야 하고 장비 종류나 버전에 제약이 생긴다. 반대로 설치 없이 표준 프로토콜로만 제어하는 방식은 준비가 가볍지만, 장비가 지원하는 프로토콜과 기능 범위 안에서만 동작한다.

#2핵심 질문

장비를 중앙에서 제어할 때, 상주 소프트웨어를 두는 방식과 두지 않는 방식은 무엇이 다르고 언제 각각을 쓰는가?

#3동작 예시

같은 "설정 변경" 작업을 두 방식으로 비교해 보자. 에이전트 방식은 장비에 설치된 상주 프로그램이 관리 서버와 미리 연결을 유지하다가 명령을 받아 대신 실행한다. 에이전트리스 방식은 관리 서버가 장비에 SSH·NETCONF·RESTCONF 같은 표준 프로토콜로 직접 접속해 명령을 보내고 결과를 받는다.

#4동작 과정

  1. 에이전트 기반각 장비에 상주 소프트웨어를 설치하고, 그 소프트웨어가 관리 서버와 지속적으로 통신하며 명령 실행·상태 보고를 담당한다. 세밀한 제어가 가능한 대신 설치와 갱신 대상이 장비 수만큼 늘어난다.
  2. 에이전트리스 기반장비에 추가 설치 없이 관리 서버가 표준 프로토콜로 외부에서 접속해 명령을 보낸다. 준비가 가볍고 기존 장비에도 적용하기 쉬운 대신, 장비가 제공하는 프로토콜과 기능 범위 안에서만 제어된다.
  3. 선택과 혼용장비 특성과 제어 정밀도 요구에 따라 방식을 고르거나, 일부는 상주 소프트웨어로 일부는 표준 프로토콜로 제어하는 식으로 섞어 운용한다.

#5한 줄 요약

이 비교장비에 상주 소프트웨어를 두고 세밀하게 제어할지, 표준 프로토콜로 설치 없이 가볍게 제어할지를 고르는 것
