개발자를 위한 AWS 토대01-02

리전·가용 영역·서비스 엔드포인트와 ARN·태그로 리소스 가리키기

AWS 자원은 특정 리전의 데이터센터 묶음(가용 영역)에 놓이고, 그 하나하나를 ARN이라는 전역 고유 이름과 태그로 정확히 지목한다.

#1문제 상황

리소스를 이름으로만 구분하면 전 세계 AWS 시스템에서 같은 이름의 리소스가 많이 충돌한다. AWS는 리소스를 물리적 위치와 고유 식별자로 정확히 지목해야 한다.

#2핵심 질문

AWS 자원 하나를 전역 규모에서 명확하게 가리키고, 그 위치와 속성을 한눈에 알려면 어떻게 해야 하나?

#3동작 예시

ARN(Amazon Resource Name)이라는 표준 형식으로 리소스를 전역적으로 고유하게 가리킨다. 예를 들어 arn:aws:s3:::my-bucket/my-object는 S3 버킷의 특정 객체를 세계 어디서나 유일하게 지목한다. 리소스가 위치한 리전과 가용 영역도 별도로 지정하여 물리적 배치를 제어한다.

#4동작 과정

  1. 리전 선택리소스를 배포할 지리적 위치(us-east-1, eu-west-1 등)를 선택한다. 레이턴시, 규정 준수, 비용이 결정 기준이다.
  2. 가용 영역 할당선택한 리전 내에서 물리적으로 떨어진 데이터센터(가용 영역)에 리소스를 분산하여 고가용성을 확보한다.
  3. ARN으로 고유 식별 및 태그로 분류리소스마다 ARN이 자동 부여되어 API와 정책에서 그것을 참조한다. 태그는 추가 메타데이터로 비용 추적, 권한 제어, 자동화에 활용한다.

#5한 줄 요약

리전과 가용 영역이라는 물리적 계층 구조 위에 ARN이라는 전역 고유 식별자와 태그를 얹어 AWS 자원을 위치 지각적으로 식별하고 관리하는 것

개발자를 위한 AWS 토대01-03

AWS API 호출의 구조: 요청 서명(SigV4)·자격 증명 공급자 체인·프로그래밍 방식 접근 구성

모든 AWS 호출은 HTTPS 요청에 서명 키로 도장을 찍는 일이며, 그 키는 환경 변수·프로파일·역할 순으로 탐색되는 자격 증명 공급자 체인이 자동으로 찾아 준다.

#1문제 상황

HTTPS 요청만으로는 요청 발신자가 진짜 권한이 있는지 검증할 수 없다. AWS는 모든 호출을 암호로 서명하여 요청이 위변조되지 않았음을 보증해야 한다.

#2핵심 질문

AWS API 요청을 보낼 때 그 요청이 정말 나의 자격 증명으로 서명되었음을 어떻게 증명하나?

#3동작 예시

AWS Signature Version 4(SigV4)는 요청의 HTTP 메서드, 경로, 헤더, 본문을 특정 순서로 조합하여 비밀 액세스 키로 HMAC-SHA256 서명을 만들고, 그것을 요청에 붙인다. AWS는 같은 방식으로 요청을 검증하여 위변조 여부를 확인한다.

#4동작 과정

  1. 자격 증명 탐색SDK 또는 CLI가 환경 변수, AWS 프로파일 파일, IAM 역할 순서로 액세스 키 ID와 비밀 액세스 키를 자동으로 찾는다. 가장 먼저 발견된 것을 사용한다.
  2. 요청 서명발견한 자격 증명과 현재 타임스탬프를 사용하여 요청 전체를 SigV4 알고리즘으로 서명하고, 서명값을 Authorization 헤더에 포함시킨다.
  3. HTTPS 전송서명된 요청을 HTTPS로 AWS에 전송한다. AWS 측에서는 서명을 검증하여 권한과 요청 무결성을 확인 후 응답한다.

#5한 줄 요약

모든 AWS API 호출을 SigV4로 서명하고, 자격 증명 공급자 체인이 키를 자동으로 탐색·적용하여 보안과 편의성을 동시에 달성하는 것

#2핵심 질문

AWS API를 프로그래밍 방식으로 호출할 때 서명, 직렬화, 재시도 등의 저수준 세부사항을 어떻게 간단히 처리하나?

#3동작 예시

#4동작 과정

  1. 클라이언트 생성 및 구성리전(예: us-west-2)과 자격 증명(프로파일, 역할 등)을 지정하여 클라이언트를 초기화한다.
  2. 메서드 호출서비스별 메서드(예: describe_instances())를 호출하고, 선택적으로 페이지네이션 옵션(결과 페이지 크기, 최대 결과 수)을 지정한다.

#5한 줄 요약

AWS CLI와 CloudShell: 프로파일·설정 우선순위·출력 제어·명령 구조

터미널에서 aws <서비스> <명령> 꼴로 같은 API를 부르는 도구이며, 설정은 명령줄 옵션·환경 변수·프로파일 파일 순으로 우선한다.

#1문제 상황

AWS 콘솔(웹 UI)로 리소스를 관리하는 것은 마우스 클릭이 많아 느리고, 반복 작업이 어렵다. 터미널에서 명령어로 제어할 필요가 있다.

#2핵심 질문

코드를 작성하지 않고도 터미널에서 AWS 자원을 빠르게 조회하고 제어하려면?

#3동작 예시

CLI는 aws s3 ls, aws ec2 describe-instances 같은 형태의 명령어로 같은 AWS API를 호출한다. 설정 우선순위는 명령줄 옵션 > 환경 변수 > 프로파일 파일 순이므로, 프로파일을 미리 구성하고 필요시 옵션으로 덮어쓸 수 있다.

#4동작 과정

#1문제 상황

기존 개발 방식은 웹 서버 한두 대가 세션 메모리에 상태를 저장하고 사용자 요청을 처리했다. 이 구조는 서버를 늘리기 어렵고 장애 한 대가 전체를 중단시킨다.

#3동작 예시

#4동작 과정

#4동작 과정

  1. 루트 사용자와 IAM 사용자 분리루트 사용자는 계정 초기 설정용으로만 사용하고, 일상적 개발은 IAM 사용자로 합니다.

#1문제 상황

AWS의 각 서비스마다 다른 UI와 문법으로 접근 권한을 설정하면 학습 곡선이 높고, 한 곳에서 설정한 권한과 다른 곳의 권한이 상충할 수 있습니다.

#2핵심 질문

AWS의 모든 서비스에 통일된 방식으로 누가 무엇을 할 수 있는지 정의할 수 있을까요?

#3동작 예시

IAM 정책은 JSON 문서로 작성되며, Effect(허용 또는 거부), Action(수행할 작업, 예: s3:GetObject), Resource(대상, 예: arn:aws:s3:::버킷명/*), Condition(조건, 예: IP 제한)을 명시합니다. 예를 들어 특정 S3 버킷의 객체만 다운로드할 수 있게 하려면 Effect를 Allow, Action을 s3:GetObject, Resource를 해당 버킷의 ARN으로 설정합니다.

#4동작 과정

  1. 정책 문서 정의Effect, Action, Resource, Condition을 JSON 형태로 작성합니다.
  2. 명시적 Deny 우선 평가요청이 들어오면 정책들을 확인하여 명시적 거부(Deny)가 하나라도 있으면 즉시 접근을 거부합니다.
  3. 명시적 Allow 확인 및 기본 거부Deny가 없으면 명시적 Allow를 찾고, 없으면 기본적으로 거부합니다.

#5한 줄 요약

IAM 정책 평가는 JSON 기반 통일된 문법으로 명시적 Deny를 우선하고 기본 거부 원칙에 따라 요청을 허용 또는 거부합니다.

#4동작 과정

#5한 줄 요약

IAM 권한은 사용자 또는 리소스에 붙일 수 있고, 재사용성과 관리 범위에 따라 관리형 또는 인라인으로 정의하며, 권한 경계로 최대 권한을 제한하는 구조입니다.

STS 임시 자격 증명과 역할 맡기(AssumeRole), 교차 계정 접근

AWS STS가 만료 시간이 있는 임시 키를 발급해 역할을 맡게 하고, 신뢰 정책을 통해 다른 계정의 리소스에도 접근하게 해 주는 구조다.

#1문제 상황

애플리케이션이 AWS 리소스에 접근하려면 장기적인 액세스 키를 가져야 하는데, 그 키가 유출되면 공격자가 계속 악용할 수 있습니다. 또한 다른 AWS 계정의 리소스에 접근해야 할 때 추가 키를 관리해야 합니다.

#2핵심 질문

유효 시간이 제한된 임시 자격 증명으로 보안 위험을 줄이면서도 다른 계정의 리소스에 접근할 수 있을까요?

#3동작 예시

AWS STS는 AccessKeyId, SecretAccessKey, SessionToken 세 개로 이루어진 임시 자격 증명을 발급하며, 이 자격 증명은 기본 1시간 유효합니다. AssumeRole API를 호출하면 다른 계정의 역할을 맡을 수 있고, 신뢰 정책으로 누가 그 역할을 맡을 수 있는지 제어합니다.

#4동작 과정

  1. 신뢰 정책 확인애플리케이션이나 다른 계정이 AssumeRole 요청을 보내면, 대상 역할의 신뢰 정책에서 이 주체가 역할을 맡을 권리가 있는지 확인합니다.
  2. 임시 자격 증명 발급신뢰 정책을 통과하면 STS가 유효 시간이 있는 임시 자격 증명(AccessKey, SecretKey, SessionToken) 발급합니다.
  3. 임시 자격 증명으로 AWS API 호출애플리케이션은 발급받은 임시 자격 증명으로 AWS API를 호출하고, 유효 시간이 만료되면 새로 요청합니다.

#5한 줄 요약

STS는 제한된 유효 시간을 가진 임시 자격 증명을 발급해서 보안 노출 시간을 줄이고, 신뢰 정책을 통해 교차 계정 접근을 안전하게 허용합니다.

#1문제 상황

EC2 인스턴스나 Lambda 함수 안에서 AWS 리소스에 접근하려면 액세스 키를 코드에 하드코딩하거나 환경 변수로 주입해야 합니다. 이는 키 유출 위험이 크고, 키 순환(정기적 교체)도 복잡합니다.

#2핵심 질문

액세스 키를 애플리케이션 코드에 직접 포함하지 않으면서도 EC2, Lambda, ECS 같은 서비스에서 안전하게 AWS 리소스에 접근할 수 있을까요?

#3동작 예시

실행 환경(EC2 인스턴스, Lambda 함수, ECS 작업)에 IAM 역할을 붙이면, SDK(boto3 등)가 자동으로 메타데이터 서비스에 요청하여 해당 역할의 임시 자격 증명을 받아서 사용합니다. EC2의 경우 인스턴스 프로파일, Lambda의 경우 실행 역할, ECS의 경우 작업 역할이라는 이름으로 붙입니다.

#4동작 과정

  1. 실행 환경에 역할 연결EC2 인스턴스 프로파일, Lambda 실행 역할, ECS 작업 역할로 역할을 연결합니다.
  2. SDK가 메타데이터 서비스에 요청애플리케이션이 AWS API를 호출할 때, SDK가 자동으로 로컬 메타데이터 서비스에 현재 역할의 임시 자격 증명을 요청합니다.
  3. 자동 갱신 및 사용SDK가 획득한 임시 자격 증명으로 API를 호출하고, 만료 시간이 가까워지면 자동으로 새 자격 증명을 갱신합니다.

#5한 줄 요약

서비스 역할은 EC2/Lambda/ECS 같은 실행 환경에 IAM 역할을 붙여 SDK가 자동으로 임시 자격 증명을 관리하게 하고, 하드코딩된 키를 제거합니다.

페더레이션과 애플리케이션 수준 세분화 권한 부여

SAML·OIDC 같은 외부 신원 공급자나 Cognito로 로그인한 사용자에게 역할을 매핑하고, 정책 변수·조건으로 사용자별 데이터만 접근하게 좁히는 방법이다.

→ 02-03 참조

#1문제 상황

AWS IAM 사용자로만 관리하면 회사의 기존 Active Directory, Okta, Google Workspace 같은 신원 관리 시스템과 연동이 어렵습니다. 모든 직원마다 별도의 IAM 사용자를 만들어야 하고, 키 관리 복잡도가 급증합니다.

#2핵심 질문

외부 신원 공급자를 통해 로그인한 사용자에게 AWS 권한을 동적으로 부여하면서도 각 사용자별로 접근 범위를 세분화할 수 있을까요?

#3동작 예시

SAML(Security Assertion Markup Language), OIDC(OpenID Connect), Cognito 같은 외부 신원 공급자로 인증한 후, 그 사용자의 속성(사용자명, 부서, 그룹)을 담은 토큰을 받습니다. 이 토큰으로 AWS의 역할을 맡으면, 그 역할의 정책에서 정책 변수(aws:userid, aws:username 같은)를 사용하여 로그인한 사용자 본인의 데이터만 접근할 수 있도록 좁힙니다.

#4동작 과정

  1. 외부 신원 공급자에서 인증사용자가 Okta, Google, SAML 제공자 등 외부 신원 공급자로 로그인하고, 사용자 속성을 담은 토큰을 받습니다.
  2. AWS 역할에 매핑 및 AssumeRole그 토큰으로 STS의 AssumeRoleWithSAML, AssumeRoleWithWebIdentity 같은 API를 호출해 AWS 역할을 맡습니다.
  3. 정책 변수로 세분화역할의 정책에서 정책 변수를 사용하여 로그인한 사용자의 속성에 맞는 데이터(예: 자신의 S3 폴더, 자신의 DynamoDB 레코드)만 접근하도록 제한합니다.

#5한 줄 요약

페더레이션은 외부 신원 공급자 인증을 AWS 역할에 연동하고, 정책 변수와 조건을 통해 사용자별로 접근 범위를 세분화하여 기존 신원 관리 시스템과 통합합니다.

DynamoDB: 기본 데이터 저장소03-01

핵심 구성요소: 테이블·아이템·속성·기본 키와 지원 데이터 타입

DynamoDB는 테이블 안에 아이템(행)을 담고 각 아이템은 속성(열)으로 이뤄지며, 파티션 키 단독 또는 파티션 키+정렬 키 조합의 기본 키로 아이템을 유일하게 식별한다.

→ 03-02 참조

#1문제 상황

전통 관계형 데이터베이스에서는 모든 행이 정확히 같은 열을 가져야 하고, 고유성을 보장하기 위해 주키를 신중하게 설계해야 합니다. 스키마를 변경하려면 마이그레이션 작업이 필요합니다.

#2핵심 질문

모든 아이템이 정확히 같은 속성을 가져야 하지 않으면서도, 각 아이템을 유일하게 구분할 수 있는 키 구조는 무엇일까요?

#3동작 예시

DynamoDB 테이블의 각 아이템은 파티션 키(Partition Key) 또는 파티션 키 + 정렬 키(Sort Key) 조합으로 유일하게 식별됩니다. 예를 들어 사용자 테이블에서 파티션 키를 userId로, 정렬 키를 timestamp로 설정하면, 같은 사용자의 여러 활동 기록을 구분할 수 있습니다. 각 아이템이 가진 속성(username, email, age 등)은 자유로우며, 아이템마다 다를 수 있습니다. 지원 데이터 타입은 문자열, 숫자, 바이너리, 불린, 리스트, 맵 등입니다.

#4동작 과정

  1. 기본 키 설계테이블 생성 시 파티션 키(필수)와 정렬 키(선택)를 정의합니다. 파티션 키만으로는 한 개의 정확한 아이템을 조회하고, 파티션 키 + 정렬 키로는 여러 아이템을 범위 조회합니다.
  2. 유연한 속성 정의각 아이템 안의 속성은 자유로우며, 어떤 데이터 타입(문자열, 숫자, 맵, 리스트 등)을 가질지 미리 정할 필요가 없습니다.
  3. 데이터 조회 및 필터링파티션 키와 정렬 키로 빠르게 대상 아이템들을 찾은 후, 필요하면 속성 값으로 추가 필터링합니다.

#5한 줄 요약

DynamoDB는 파티션 키와 정렬 키 조합으로 각 아이템을 유일하게 식별하고, 속성은 스키마 제약이 적어 유연한 데이터 저장을 가능하게 합니다.

파티션 키 설계와 데이터 분산

DynamoDB는 파티션 키의 해시값으로 데이터를 여러 파티션에 나눠 저장하므로, 값이 골고루 퍼지는 고카디널리티 키를 써야 특정 파티션에 트래픽이 몰리는 핫 파티션을 피할 수 있다.

→ 03-03 참조

#1문제 상황

기존 관계형 DB는 테이블이 하나의 서버나 스토리지에 저장되므로 데이터가 커지면 그 서버의 용량과 성능에 한계가 생깁니다. DynamoDB는 테이블을 여러 파티션(각각 독립적인 스토리지 단위)으로 나눠 저장해서 수평 확장합니다. 하지만 파티션 키를 잘못 설계하면 모든 데이터와 요청이 한두 개의 파티션에만 몰려서 그 파티션이 과부하 상태에 빠지는 핫 파티션 문제가 발생합니다.

#2핵심 질문

파티션 키를 어떻게 설계해야 모든 파티션에 데이터와 트래픽을 골고루 분산할 수 있을까요?

#3동작 예시

사용자 ID를 파티션 키로 쓰되, 값이 1부터 1000만까지 균등하게 분포하는 경우 해시 함수가 각 사용자 ID를 다른 파티션에 대응시켜 데이터가 고르게 흩어집니다. 반대로 국가 코드를 파티션 키로 쓰면 저카디널리티(값의 종류가 적음) 때문에 대부분 데이터가 "KR", "US" 같은 몇 개 값에만 쏠려서 해당 파티션이 모든 요청을 받아 과부하됩니다.

#4동작 과정

  1. 파티션 키 해싱파티션 키 값을 받아서 해시 함수로 계산하면 어느 파티션에 저장할지 결정됩니다.
  2. 데이터 분산해시값이 고르게 퍼져야 데이터도 여러 파티션에 고르게 분산되고, 각 파티션의 부하도 균등해집니다.
  3. 핫 파티션 피하기파티션 키 값이 골고루 분포하지 않으면 특정 파티션에만 요청이 몰려서 스로틀링(요청 거부 또는 지연)이 발생합니다.

#5한 줄 요약

파티션 키의 해시값으로 데이터를 여러 파티션에 나눠 저장하므로, 값이 골고루 퍼지는 고카디널리티 키를 써야 트래픽과 처리 부하를 균등하게 분산할 수 있다는 것

#1문제 상황

기존 관계형 DB는 서버의 물리적 자원(CPU, 메모리, 디스크)이 정해지면 그 한계 안에서만 요청을 처리합니다. DynamoDB는 요청량이 예측 불가능하게 달라질 수 있으므로, 미리 처리 능력을 정하거나 쓴 만큼만 비용을 내는 방식 중 하나를 선택해야 합니다. 할당된 처리 능력을 초과하면 요청이 거부되지만(스로틀링), 순간적인 초과는 버스트 용량이나 적응형 용량이 일부 흡수합니다.

#2핵심 질문

테이블의 읽기·쓰기 처리량을 얼마나 할당하거나 관리해야 비용 효율과 안정성 사이의 균형을 맞출 수 있을까요?

#3동작 예시

온디맨드 모드: 매일 사용량이 10배 이상 달라지는 서비스(예: 트렌드 해시태그)는 쓴 만큼만 내면 되므로 낭비가 없습니다. 프로비저닝 모드: 사용량이 예측 가능한 서비스(예: 내부 사원 정보 조회)는 미리 RCU(읽기 처리량 단위)와 WCU(쓰기 처리량 단위)를 정하면 고정된 가격으로 처리량이 보장됩니다.

#4동작 과정

  1. 용량 모드 선택온디맨드(사용량 변화에 따라 비용 증감)와 프로비저닝(RCU·WCU 미리 할당) 중 하나를 선택합니다.
  2. 버스트와 적응형 용량순간적인 초과 요청은 버스트 용량(미리 쌓인 예비 처리량 크레딧)이 흡수하거나, 적응형 용량이 자동으로 조정합니다.
  3. 스로틀링 처리할당된 용량을 초과하면 스로틀링이 발생하므로, 애플리케이션이 재시도하거나 용량을 늘려야 합니다.

#5한 줄 요약

테이블 처리량을 쓴 만큼 내는 온디맨드와 RCU/WCU를 미리 정하는 프로비저닝 중 하나로 선택하고, 버스트·적응형 용량이 순간 초과를 흡수하며, 한계를 넘으면 스로틀링으로 요청을 제어한다는 것

#1문제 상황

여러 파티션에 복제되는 데이터는, 한 파티션에 쓴 직후 다른 파티션의 복제본이 아직 업데이트되지 않았을 수 있습니다. 즉, 쓰기 직후 읽기를 하면 옛 값을 읽을 수도 있고 새 값을 읽을 수도 있습니다. 이를 해결하려면 읽기 일관성 수준을 명시적으로 선택해야 합니다.

#2핵심 질문

데이터를 읽을 때 최신 값을 반드시 받거나 약간 늦은 값을 받아도 되는지 어떻게 선택할까요?

#3동작 예시

장바구니 페이지: 새 상품을 추가한 후 목록을 읽을 때 최신 내용을 확실히 봐야 하므로 강한 일관성(모든 복제본 완료 대기)을 씁니다. 추천 상품 목록: 약 1초 정도 늦은 정보를 읽어도 상관없으므로 최종적 일관성(복제 완료 대기 안 함)을 쓰면 비용이 낮고 속도가 빠릅니다.

#4동작 과정

  1. 읽기 일관성 선택최종적 일관성(기본값, 빠르고 저렴)은 복제 완료를 기다리지 않고, 강한 일관성은 모든 파티션 복제가 같은 값을 가질 때까지 기다립니다.
  2. 아이템 단위 CRUDGetItem(읽기)·PutItem(전체 덮어쓰기)·UpdateItem(특정 속성 수정)·DeleteItem(삭제)을 하나씩 수행하거나, BatchGetItem·BatchWriteItem으로 여러 개를 한 번에 처리합니다.
  3. 결과 반환요청한 일관성 수준에 맞춰 결과가 반환되고, 쓰기 연산은 성공 또는 실패로 즉시 확정됩니다.

#5한 줄 요약

기본으로 최종적 일관된 읽기를 쓰면서 필요하면 강한 일관성을 선택하고, 아이템 단위 CRUD는 개별 연산(GetItem 등)과 다건 처리 연산(Batch 등)으로 수행한다는 것

Query와 Scan의 차이, 보조 인덱스(LSI·GSI)와 프로젝션

Query는 키 조건으로 필요한 항목만 효율적으로 읽고 Scan은 테이블 전체를 훑으며, 다른 키로 조회하려면 LSI(같은 파티션 키·다른 정렬 키)나 GSI(완전히 다른 키)를 만들고 프로젝션으로 복제할 속성을 정한다.

→ 03-02 참조

#1문제 상황

DynamoDB 테이블은 파티션 키와 정렬 키로 항목을 저장합니다. 파티션 키와 정렬 키 조건으로 조회하면 빠르지만, 다른 속성으로 조회하려면 테이블 전체를 처음부터 끝까지 훑어야 하므로 느리고 비싸고 처리량이 많이 듭니다.

#2핵심 질문

기본 키가 아닌 다른 속성으로 효율적으로 조회하려면 어떻게 할까요?

#3동작 예시

테이블의 기본 키가 (user_id, timestamp)라면, 같은 user_id의 여러 항목을 timestamp 범위로 빠르게 조회할 수 있습니다. 하지만 email 주소로 사용자를 찾으려면 GSI(Global Secondary Index, 이메일을 파티션 키로 하는 별도 인덱스)를 만들어서, 데이터의 복제본을 추가 저장하고 이메일로 직접 조회합니다.

#4동작 과정

  1. Query파티션 키와 정렬 키 조건으로 필요한 항목만 효율적으로 읽습니다. 필터 조건을 붙여 추가 필터링도 가능합니다.
  2. Scan테이블(또는 인덱스) 전체를 처음부터 끝까지 훑어서 원하는 항목을 찾습니다. 속도가 느리고 비싸므로 필요할 때만 씁니다.
  3. 보조 인덱스LSI(같은 파티션 키·다른 정렬 키)나 GSI(완전히 다른 키)를 만들고, 프로젝션(복제할 속성 목록)으로 인덱스 크기와 비용을 조절합니다.

#5한 줄 요약

Query로 키 조건에 맞는 항목을 효율적으로 읽고 Scan으로 전체를 훑으며, 다른 키로 조회하려면 LSI(같은 파티션 키·다른 정렬 키)나 GSI(완전히 다른 키)를 만들고 프로젝션으로 복제 범위를 정한다는 것

조건식으로 특정 조건일 때만 쓰기를 허용하고 UpdateExpression의 ADD/SET으로 원자적 증감을, 버전 속성 기반 낙관적 잠금과 TransactWriteItems/TransactGetItems로 여러 항목의 전부-또는-전무 처리를 보장한다.

#1문제 상황

여러 클라이언트가 동시에 같은 항목을 읽고 쓰면 한쪽의 변경이 다른 쪽에 덮어씌워질 수 있습니다. 또한 여러 항목을 함께 업데이트할 때 중간에 실패하면 일부만 변경되어 데이터 불일치가 생깁니다.

#2핵심 질문

여러 클라이언트가 동시에 데이터를 수정할 때 충돌을 피하고, 여러 항목 업데이트가 전부 성공하거나 전부 실패하도록 보장하려면 어떻게 할까요?

#3동작 예시

은행 계좌: 잔액을 조회한 후 출금하려 할 때, 조회 후 출금 전에 다른 사람이 출금했다면 계좌 잔액이 음수가 될 수 있습니다. 버전 속성 기반 낙관적 잠금(조회할 때 버전을 함께 읽고 업데이트할 때 버전을 확인)으로 이를 감지하고, TransactWriteItems로 두 계좌 간 이체를 전부-또는-전무로 처리합니다.

#4동작 과정

  1. 조건식특정 속성 값이 기대하는 값일 때만 쓰기를 허용합니다. 조건을 만족하지 않으면 요청이 거부됩니다.
  2. 원자적 업데이트ADD(숫자 증감)·SET(속성 지정)·DELETE(속성 제거) 같은 UpdateExpression을 한 번에 실행하므로, 중간 상태가 노출되지 않습니다.
  3. 낙관적 잠금과 트랜잭션버전 속성으로 충돌을 감지하고, TransactWriteItems·TransactGetItems로 여러 항목의 전부-또는-전무 처리를 보장합니다.

#5한 줄 요약

조건식으로 특정 조건일 때만 쓰기를 허용하고, UpdateExpression의 원자적 연산으로 중간 상태를 피하며, 버전 속성 기반 낙관적 잠금과 TransactWriteItems로 여러 항목의 일관성을 보장한다는 것

DynamoDB Streams·TTL·DAX 캐싱·백업과 복원

Streams는 항목 변경 이력을 시간순으로 흘려보내 Lambda 트리거로 잇고, TTL은 만료된 항목을 자동 삭제하며, DAX는 마이크로초 단위 읽기 캐시를, 온디맨드 백업과 PITR은 데이터 복구 수단을 제공한다.

#1문제 상황

테이블에 항목이 추가·변경·삭제되면 그 이벤트 자체는 어디에도 남지 않습니다. 데이터를 더 오래 보관하려면 별도 저장소가 필요하고, 자주 읽는 데이터를 매번 데이터베이스에서 읽으면 지연 시간이 깁니다. 실수로 삭제한 데이터를 복구할 수 없습니다.

#2핵심 질문

항목 변경 이력을 수집하고, 자주 읽는 데이터를 빠르게 액세스하고, 실수로 삭제된 데이터를 복구하려면 어떻게 할까요?

#3동작 예시

주문 시스템: Streams로 주문 추가 이벤트를 Lambda로 보내서 이메일 발송 로직을 자동 트리거하고, TTL로 30일 뒤 임시 장바구니 데이터를 자동 삭제하며, DAX로 자주 조회되는 상품 카탈로그를 마이크로초 단위로 빠르게 읽고, PITR(특정 시간 이전으로 복구)로 실수로 삭제된 주문을 되살립니다.

#4동작 과정

  1. Streams항목 변경(추가·수정·삭제)을 시간순 이벤트로 흘려보내므로, Lambda나 Kinesis로 받아서 후속 처리(알림, 감시 로그, 다른 저장소 동기화 등)를 합니다.
  2. TTL과 DAXTTL은 특정 속성의 유닉스 타임스탬프가 지나면 항목을 자동 삭제하고, DAX(DynamoDB Accelerator)는 테이블 앞에 캐싱 계층을 두어 마이크로초 단위 응답을 제공합니다.
  3. 백업·복원온디맨드 백업은 수동 스냅샷을 남기고, PITR(Point-in-Time Recovery)은 과거 임의 시점으로 복구할 수 있게 해줍니다.

#5한 줄 요약

Streams로 항목 변경 이력을 시간순으로 흘려보내 Lambda 트리거로 잇고, TTL로 만료된 항목을 자동 삭제하며, DAX로 마이크로초 단위 읽기 캐시를, 온디맨드 백업과 PITR로 데이터 복구 수단을 제공한다는 것

#1문제 상황

전통 파일 시스템은 폴더 구조와 파일 시스템 메타데이터(권한, 타임스탬프)로 파일을 관리하고, 보관 기한이 없어서 수동으로 삭제하거나, 버전 관리가 없어서 덮어씌우면 이전 파일을 복구할 수 없습니다.

#2핵심 질문

수십억 개의 파일을 저장·관리하면서 비용을 낮추고, 파일 버전을 유지하며, 오래된 파일을 자동으로 처리하려면 어떻게 할까요?

#3동작 예시

로그 저장소: S3 버킷 "logs"에 키 "2026/09/14/app.log"로 로그 파일을 저장하고, 메타데이터로 압축 여부·생성자를 기록합니다. 버전 관리를 켜면 같은 키로 덮어씌워도 이전 버전이 남고, 수명 주기 규칙으로 30일 뒤 Glacier(저렴한 장기 저장소)로 옮기고 90일 뒤 삭제합니다.

#4동작 과정

  1. S3 구조버킷(최상위 컨테이너)·키(경로/파일명)·객체(실제 데이터)·메타데이터(태그, 권한, 커스텀 속성 등)로 계층 구조 없이 평탄하게 저장합니다.
  2. 스토리지 클래스와 수명 주기스토리지 클래스(Standard·Glacier·Deep Archive 등)로 비용을 정하고, 수명 주기 규칙으로 자동 전환·삭제를 설정합니다.
  3. 버전 관리버전 관리를 켜면 같은 키로 쓰기·삭제해도 이력이 남으므로, 실수 삭제·덮어쓰기를 복구할 수 있습니다.

#5한 줄 요약

S3가 버킷 안에 키로 객체를 저장하는 객체 스토리지이고, 스토리지 클래스로 비용을, 수명 주기 규칙으로 자동 전환·삭제를, 버전 관리로 덮어쓰기·삭제 이력을 관리한다는 것

S3와 나머지 데이터 저장소04-02

객체 다루기: 업로드·멀티파트 업로드·프리사인드 URL·무결성 검사

큰 파일은 여러 조각으로 나눠 올리는 멀티파트 업로드로, 권한 없는 사용자에게는 기한이 정해진 프리사인드 URL로 넘기며, 체크섬으로 전송이 깨지지 않았는지 확인한다.

#1문제 상황

기존에 S3에 파일을 올릴 때는 작은 파일을 한 번에 통째로 올렸다. 하지만 큰 파일을 한 번에 올리면 네트워크가 끊기거나 오류가 나면 처음부터 다시 올려야 하고, 전송 중간에 손상되는지 확인할 방법이 없었다.

#2핵심 질문

큰 파일을 안전하게, 부분별로 올리고, 권한이 없는 사람에게 안전하게 업로드 권한을 주려면 어떻게 해야 할까?

#3동작 예시

100MB짜리 비디오 파일을 S3에 올릴 때, 멀티파트 업로드는 이 파일을 5MB씩 20개 조각으로 나눠 각각을 따로 올린다. 한 조각 업로드 실패하면 그 조각만 다시 올리면 되므로 네트워크 문제에 강하다.

#4동작 과정

  1. 멀티파트 업로드 시작업로드 ID를 받아 이후 조각들을 같은 업로드 ID로 묶을 준비를 한다.
  2. 조각 올리기파일을 여러 부분으로 나눠 각각 업로드하고, 각 조각의 ETag(데이터가 훼손되지 않았는지 확인하는 태그)를 기록한다.
  3. 완료 및 검증모든 조각이 올라오면 완료 요청을 하면서 모든 ETag를 보낸다. S3는 이 태그들이 맞는지 확인한 후 최종 파일을 만든다.

프리사인드 URL은 제한된 시간 동안만 쓸 수 있는 서명된 URL로, 예를 들어 "이 링크는 2시간만 유효하고 이 사용자가 이 객체에 업로드할 수 있다"는 정보를 URL에 담아 준다. 권한이 없는 클라이언트에게 이 URL을 넘기면, AWS 자격 증명 없이도 그 URL을 통해서만 파일을 올리거나 다운로드할 수 있다.

#5한 줄 요약

큰 파일을 여러 조각으로 나눠 올려 네트워크 신뢰성을 높이고, 체크섬으로 무결성을 보장하며, 제한된 시간의 서명된 URL로 자격 증명 없이 안전하게 접근 권한을 위임하는 것

S3와 나머지 데이터 저장소04-03

S3 접근 제어와 웹 공개: 버킷 정책·퍼블릭 액세스 차단·ACL·CORS·이벤트 알림·정적 호스팅

누가 무엇을 할 수 있는지는 버킷 정책과 퍼블릭 액세스 차단으로 정하고, 브라우저 호출은 CORS로 허용하며, 객체 변경은 이벤트 알림으로 Lambda·SQS에 흘려보내고 버킷 자체를 정적 웹사이트로 띄울 수도 있다.

#1문제 상황

기존에는 S3 버킷 전체의 권한을 정하는 방법이 ACL(여러 사용자별 권한) 정도였는데, 이것만으로는 특정 요청을 막거나 특정 IP에서만 허용하거나 웹 브라우저 요청을 처리하기 어려웠다.

#2핵심 질문

누가 어떤 객체를 어떻게 접근할 수 있는지, 그리고 웹 브라우저에서 이 버킷의 파일들을 쓸 수 있으려면 어떻게 설정해야 할까?

#3동작 예시

버킷 정책으로 "특정 IAM 사용자만 이 버킷의 모든 객체를 읽을 수 있다" 또는 "이 버킷의 public/ 폴더 안의 파일은 누구나 읽을 수 있지만, 수정은 못 한다"는 규칙을 JSON으로 정의한다. 브라우저에서 JavaScript가 S3에 요청을 보낼 때, CORS 설정으로 "이 도메인에서 오는 PUT, GET, DELETE 요청을 허용한다"고 명시한다.

#4동작 과정

  1. 버킷 정책 설정누가 어떤 액션(읽기, 쓰기, 삭제)을 할 수 있는지를 JSON 규칙으로 정의하고, 퍼블릭 액세스 차단(개별 객체는 퍼블릭이어도 버킷 자체는 정책으로만 공개되도록 함)을 조합해 세밀한 제어를 한다.
  2. 이벤트 알림 설정객체가 생성되거나 삭제되면, S3가 Lambda나 SQS 같은 서비스로 알림을 보내 자동 처리(예: 썸네일 생성, 로그 저장)를 연결한다.
  3. CORS 및 정적 호스팅웹 브라우저에서의 크로스 오리진 요청을 CORS 규칙으로 허용하고, 필요하면 버킷 자체를 정적 웹사이트로 설정해 index.html 같은 파일을 직접 제공한다.

#5한 줄 요약

버킷 정책과 퍼블릭 액세스 차단으로 정교한 접근 제어를 하고, CORS로 웹 요청을 안전하게 받으며, 이벤트 알림으로 파일 변경에 자동 반응하는 것

ElastiCache와 캐싱 전략: 지연 로딩·라이트 스루·TTL·세션 저장소

ElastiCache는 Redis/Valkey·Memcached를 관리형으로 제공하는 인메모리 캐시로, 필요할 때 채우는 지연 로딩과 쓰기 시 함께 갱신하는 라이트 스루를 TTL과 조합해 DB 부하를 줄이고 세션도 보관한다.

#1문제 상황

기존에는 데이터베이스에 매번 직접 접근했다. 자주 쓰는 데이터를 매번 DB에서 읽으면 DB 부하가 높아지고, 네트워크 지연도 커진다. 메모리에 임시로 데이터를 보관하려면 직접 관리해야 했다.

#2핵심 질문

자주 접근하는 데이터를 빠르게 꺼낼 수 있으면서도, DB 부하는 줄이고, 사용자 세션도 보관할 수 있으려면?

#3동작 예시

ElastiCache는 Redis나 Memcached를 AWS가 관리하는 형태로 제공한다. 사용자가 상품 정보를 요청하면, 먼저 ElastiCache에 있는지 확인하고 없으면 DB에서 읽은 후 ElastiCache에 저장한다(지연 로딩). 반대로 상품 정보를 업데이트할 때는 DB를 먼저 갱신한 후 ElastiCache의 해당 데이터도 함께 지운다(라이트 스루).

#4동작 과정

  1. 지연 로딩요청이 오면 캐시를 먼저 확인하고, 없으면 DB에서 읽은 후 캐시에 저장한다. TTL(일정 시간 후 자동 삭제)을 설정해 오래된 데이터는 자동으로 제거된다.
  2. 라이트 스루데이터를 쓸 때는 DB와 캐시를 모두 갱신해 일관성을 지킨다.
  3. 세션 저장소사용자 세션 정보를 ElastiCache에 보관하면, 서로 다른 서버들이 같은 세션을 공유할 수 있고, 메모리 기반이라 매우 빠르다.

#5한 줄 요약

메모리 기반 인메모리 캐시로 자주 쓰는 데이터를 빠르게 제공하고, 지연 로딩과 라이트 스루로 일관성을 유지하며, 세션과 임시 데이터 저장소로도 활용하는 것

RDS와 Aurora를 애플리케이션에서 사용하기: 연결·자격 증명·읽기 복제본

RDS·Aurora는 관리형 관계형 DB로, 엔드포인트로 연결하고 암호를 Secrets Manager나 IAM 인증으로 다루며 읽기 복제본으로 조회 부하를 분산한다.

#1문제 상황

기존에 데이터베이스를 연결할 때는 호스트, 포트, 사용자명, 비밀번호를 직접 코드에 넣거나 설정 파일에 저장했다. 이렇게 하면 자격 증명이 노출되기 쉽고, 여러 환경(개발, 스테이징, 운영)마다 별도로 관리해야 했다.

#2핵심 질문

데이터베이스 자격 증명을 안전하게 관리하면서, 여러 서버에서 같은 DB에 연결하고, 조회 부하를 분산시키려면?

#3동작 예시

RDS와 Aurora는 데이터베이스 엔드포인트(예: mydb.c12abc.us-east-1.rds.amazonaws.com)라는 이름으로 제공되는데, 이 엔드포인트로 연결하면 AWS가 자동으로 기저의 데이터베이스 서버를 관리한다. 자격 증명은 Secrets Manager(보안이 강화된 저장소)에 보관하거나 IAM 인증으로 임시 토큰을 받아 쓴다. 읽기 복제본(주 DB의 복제 본)을 만들면 조회 요청을 여기로 보내 부하를 분산한다.

#4동작 과정

  1. 엔드포인트로 연결애플리케이션이 RDS 엔드포인트에 연결하면 AWS가 기저 서버를 관리하므로 직접 서버를 운영할 필요가 없다.
  2. 자격 증명 관리Secrets Manager에 데이터베이스 암호를 보관하고 자동 로테이션(주기적으로 암호 변경)을 설정하거나, IAM 인증으로 임시 토큰을 받아 매번 새로운 자격 증명으로 연결한다.
  3. 읽기 복제본으로 부하 분산쓰기는 주 데이터베이스로, 읽기는 읽기 복제본으로 보내 조회 부하를 줄인다.

#5한 줄 요약

관리형 데이터베이스 엔드포인트로 연결하고, 자격 증명을 Secrets Manager나 IAM으로 안전하게 관리하며, 읽기 복제본으로 조회 부하를 분산하는 것

접근 패턴에 따른 저장소 선택: OpenSearch Service·Athena·EBS·EFS

검색·로그 분석은 OpenSearch, S3 파일에 바로 SQL을 던지는 건 Athena, 인스턴스 전용 블록 디스크는 EBS, 여러 서버가 공유하는 파일 시스템은 EFS로 접근 패턴에 맞춰 고른다.

#1문제 상황

기존에는 모든 데이터를 관계형 데이터베이스(RDS)에만 저장했다. 하지만 텍스트 검색이 필요하면 DB 성능이 떨어지고, S3에 있는 파일들을 쿼리하려면 전부 다운로드해야 했으며, 인스턴스마다 독립적인 디스크나 공유 파일 시스템이 필요할 때 별도 관리가 필수였다.

#2핵심 질문

검색, 로그 분석, 파일 시스템, 블록 스토리지 같이 접근 방식이 다른 데이터들을 어떻게 각각 최적의 저장소에 보관할 수 있을까?

#3동작 예시

OpenSearch Service는 ElasticSearch 기반으로 텍스트 검색에 최적화되어, 로그나 메시지를 저장하고 "에러 메시지 포함" 같은 복잡한 검색을 빠르게 한다. Athena는 S3에 있는 CSV나 JSON 파일에 직접 SQL 쿼리를 던져 전체 데이터베이스 구축 없이 조회한다. EBS는 EC2 인스턴스 전용 블록 저장소로, EFS는 여러 EC2 인스턴스가 동시에 접근할 수 있는 공유 파일 시스템이다.

#4동작 과정

  1. 검색 및 로그OpenSearch에 로그나 이벤트 데이터를 저장하고, 키워드 검색이나 시간 범위 조회를 빠르게 처리한다.
  2. S3 파일 쿼리Athena로 S3의 데이터에 SQL을 바로 던져 데이터 웨어하우스 구축 없이 분석한다.
  3. 인스턴스별 블록 스토리지 또는 공유 파일 시스템EBS는 특정 EC2에만 붙이는 영구 디스크로, EFS는 여러 인스턴스가 마운트하는 공유 네트워크 파일 시스템으로 선택한다.

#5한 줄 요약

검색은 OpenSearch, S3 파일 조회는 Athena, 인스턴스 전용 블록은 EBS, 다중 인스턴스 공유는 EFS처럼 접근 패턴별로 최적의 저장소를 선택하는 것

실행 모델: 핸들러·이벤트·컨텍스트와 실행 환경 수명주기, 콜드 스타트

Lambda 는 이벤트가 오면 실행 환경을 만들어 핸들러 함수에 이벤트와 컨텍스트를 넘겨 실행하고, 환경을 잠시 재사용하며 처음 만들 때 지연이 생기는 것이 콜드 스타트다.

#1문제 상황

기존에는 서버를 항상 띄워두고 요청이 오면 이미 실행 중인 프로세스가 처리했다. 하지만 항상 띄워두면 요청이 없어도 비용이 들고, 트래픽 급증에 자동으로 대응하려면 로드 밸런싱, 오토 스케일링 같은 인프라를 직접 관리해야 했다.

#2핵심 질문

요청이 올 때만 코드를 실행하고, 실행 환경을 자동으로 관리하면서, 처음 시작할 때의 지연을 최소화할 수 있을까?

#3동작 예시

Lambda 함수가 S3 파일 업로드 같은 이벤트를 받으면, AWS가 그 순간 컨테이너를 만들어 핸들러 함수를 실행한다. 핸들러는 이벤트(업로드된 파일 정보) 객체와 컨텍스트(남은 실행 시간, 로그 그룹, 함수명 등)를 인자로 받는다. 요청이 끝나면 컨테이너는 일시 중지되었다가, 다음 요청이 5분 이내에 오면 다시 깨워 재사용한다.

#4동작 과정

  1. 이벤트 수신S3, API Gateway, CloudWatch 같은 AWS 서비스가 이벤트를 Lambda에 보낸다.
  2. 핸들러 실행AWS가 필요하면 새 실행 환경(콜드 스타트)을 만들거나 기존 컨테이너를 깨워 핸들러 함수에 이벤트와 컨텍스트를 전달한다. 콜드 스타트는 처음 컨테이너를 만들고 코드를 로드하는 과정이라 100ms~1초 정도 지연이 생긴다.
  3. 결과 반환핸들러가 끝나면 결과를 반환하고, 컨테이너는 일시 중지되어 다음 요청을 기다린다.

#5한 줄 요약

이벤트가 오면 실행 환경을 자동으로 만들거나 재사용해 핸들러를 실행하고, 처음 만들 때 발생하는 콜드 스타트 지연을 감수하면서도 요청이 없을 때는 비용을 쓰지 않는 것

함수 구성: 메모리·타임아웃·아키텍처·환경 변수·임시 스토리지·VPC와 파일 시스템

함수마다 메모리(=CPU 비례)·최대 실행 시간·CPU 아키텍처·환경 변수·/tmp 용량·VPC 연결·EFS 마운트를 설정해 실행 조건을 정한다.

#1문제 상황

기존에는 서버의 스펙(메모리, CPU, 디스크)을 미리 정해 운영했다. Lambda도 마찬가지로 함수마다 실행 조건을 정해야 하는데, 처음에는 이 설정들이 독립적으로 존재했을 뿐 데이터베이스, VPC, 파일 시스템 같은 외부 자원과 연결되지 않았다.

#2핵심 질문

각 Lambda 함수가 필요한 메모리, 시간, CPU, 환경 설정, 파일 시스템, 네트워크를 어떻게 구성해야 할까?

#3동작 예시

함수를 생성할 때 메모리(128MB~10,240MB)를 정하면 CPU가 비례하게 할당되고, 실행 시간 제한(1초~15분), 아키텍처(x86 또는 ARM)를 선택한다. 환경 변수로 데이터베이스 URL이나 API 키를 주고, /tmp(512MB 임시 디스크)에 임시 파일을 쓸 수 있다. VPC에 연결하면 RDS나 ElastiCache 같은 프라이빗 네트워크 자원에 접근 가능하고, EFS를 마운트하면 함수들이 공유 파일 시스템을 쓸 수 있다.

#4동작 과정

  1. 기본 구성메모리로 CPU를 정하고, 최대 실행 시간 제한(타임아웃)을 설정하며, 환경 변수로 필요한 설정값을 주입한다.
  2. 임시 스토리지 및 네트워크/tmp에 임시 파일을 저장할 수 있고(512MB 한계), VPC 연결로 프라이빗 데이터베이스나 캐시에 접근할 수 있다.
  3. 공유 파일 시스템EFS를 마운트하면 여러 Lambda 함수가 같은 파일을 읽고 쓸 수 있다.

AWS Lambda 배포 패키지와 런타임

코드는 .zip 압축본이나 컨테이너 이미지로 올리고, 공통 라이브러리는 레이어로, 모니터링 같은 부가 기능은 확장으로 붙인다.

#1문제 상황

함수 코드를 만들 때마다 필요한 라이브러리를 매번 함께 패키징해서 올려야 한다. 예를 들어 Python 함수에 requests 라이브러리가 필요하면 코드와 site-packages 폴더를 한데 묶어 올린다. 하지만 여러 함수가 같은 라이브러리를 쓸 때마다 중복으로 올리는 비효율이 생기고, 코드 업로드 크기가 커지며, 라이브러리를 중앙에서 관리하기 어렵다.

#2핵심 질문

코드와 의존 라이브러리를 어떻게 함수에 전달하면서 중복을 피하고 크기를 줄일 수 있을까?

#3동작 예시

세 개의 함수가 모두 numpy 라이브러리를 쓴다면, .zip 파일 하나에 numpy를 담고 "이것은 레이어다"라고 지정한 뒤, 각 함수가 이 레이어를 참조하면 세 함수 모두 같은 numpy를 쓸 수 있다. 코드 .zip은 작게 유지하고, 라이브러리는 한 번만 업로드한다.

#4동작 과정

  1. 패키지 선택코드와 의존물을 .zip 파일로 묶거나, 컨테이너 이미지(도커 형식)로 만든다.
  2. 레이어 활용공통 라이브러리를 별도 .zip(레이어)로 분리하고 함수에 첨부한다. 함수는 런타임에 레이어의 파일들을 경로에 포함시켜 코드에서 쓸 수 있다.
  3. 확장 추가CloudWatch Insights, X-Ray 등 모니터링·기능 확장이 필요하면 확장(Lambda Extension) 프로그램을 함수에 붙인다.

AWS Lambda05-04

AWS Lambda 호출 방식

결과를 기다리는 동기 호출, 큐에 넣고 바로 응답하는 비동기 호출, 스트림·큐를 폴링해 배치로 넘기는 이벤트 소스 매핑이 있고 필터로 원하는 이벤트만 받는다.

#1문제 상황

함수를 실행하려면 누군가 함수를 호출해야 한다. API를 직접 호출하거나, CloudWatch 이벤트가 발생할 때마다 함수를 깨워야 하는데, 호출자가 결과를 기다려야 하는 경우도 있고 기다릴 수 없는 경우도 있다. 또한 S3에 파일이 계속 들어올 때마다 함수를 일일이 호출하는 방식은 비효율적이다.

#2핵심 질문

호출자의 필요에 따라, 그리고 데이터 소스의 특성에 따라 함수를 어떻게 다르게 호출할 수 있을까?

#3동작 예시

주문 결제 API는 결과를 곧바로 얻어야 하므로 동기 호출(함수 실행 완료까지 기다림)을 쓰고, 이메일 전송은 즉시 응답할 필요가 없으므로 비동기 호출(함수를 큐에 넣고 바로 응답)을 쓴다. SQS 큐에 메시지가 쌓이면 Lambda 서비스가 자동으로 배치 단위로 꺼내 함수에 넘기는 이벤트 소스 매핑을 쓴다.

#4동작 과정

  1. 동기 호출API 클라이언트나 AWS 서비스가 함수를 직접 호출하고 실행 완료를 기다린다. 응답이 필요한 작업(조회, 계산)에 쓴다.
  2. 비동기 호출호출자가 함수를 큐(내부 버퍼)에 넣고 즉시 응답을 얻는다. 함수는 비동기 처리되며 재시도와 실패 처리(DLQ)가 자동으로 관리된다.
  3. 이벤트 소스 매핑SQS, Kinesis, DynamoDB Streams 같은 스트림·큐를 Lambda가 자동으로 폴링(주기적으로 확인)하고 배치 단위로 레코드를 함수에 보낸다. 이벤트 필터를 붙이면 특정 속성을 가진 이벤트만 함수에 전달한다.

#5한 줄 요약

호출자의 대기 필요성과 데이터 소스 특성에 따라 동기·비동기·배치 호출을 구분해 함수를 가장 효율적으로 실행하는 것

AWS Lambda05-05

AWS Lambda 권한과 트리거

함수가 다른 서비스를 쓰려면 실행 역할이, 다른 서비스가 함수를 부르려면 리소스 기반 정책이 필요하며 함수 URL 로 HTTPS 엔드포인트를 바로 열 수 있다.

#1문제 상황

함수가 실행되려면 IAM 권한이 필요하다. 함수 코드에서 DynamoDB 테이블을 읽거나 S3 버킷에 파일을 쓰려면 먼저 누가 이 작업을 할 권한이 있는지 확인되어야 한다. 반대로 S3 버킷이나 API Gateway 같은 외부 서비스가 함수를 호출할 때도 호출 권한이 있는지 확인되어야 한다.

#2핵심 질문

함수가 다른 서비스에 접근하려면, 그리고 다른 서비스가 함수를 부르려면 어떻게 권한을 설정해야 할까?

#3동작 예시

함수가 DynamoDB를 쓰려면 함수의 실행 역할(IAM Role)에 DynamoDB 읽기 권한을 붙인다. API Gateway가 함수를 호출하려면 함수 자신에 리소스 기반 정책(함수에 붙이는 권한)을 추가해서 "API Gateway는 이 함수를 호출 가능"이라고 명시한다.

#4동작 과정

  1. 실행 역할함수가 생성될 때 IAM 역할이 자동으로 부여되며, 이 역할에 정책(S3 읽기, DynamoDB 쓰기 등)을 첨부하면 함수는 그 권한으로 AWS 리소스에 접근한다.
  2. 리소스 기반 정책함수 자체에 정책을 붙여서 특정 서비스(S3, SNS, EventBridge 등)나 계정이 함수를 호출하도록 허용한다.
  3. 함수 URL과 서비스 통합함수 URL 기능으로 HTTPS 엔드포인트를 즉시 만들어 HTTP 요청을 받거나, 다른 AWS 서비스 트리거(S3 이벤트, SQS 메시지, CloudWatch 규칙 등)를 달아 이벤트 기반 호출을 설정한다.

#5한 줄 요약

실행 역할로 함수의 외부 접근 권한을 관리하고, 리소스 기반 정책으로 함수 호출 권한을 관리하며, 함수 URL과 트리거로 호출 경로를 다양하게 제공하는 것

AWS Lambda05-06

AWS Lambda 동시성과 확장

동시에 실행되는 함수 인스턴스 수가 동시성이며, 예약 동시성으로 상한·보장을 두고 프로비저닝된 동시성으로 미리 데워 두며 한도를 넘으면 스로틀링된다.

#1문제 상황

Lambda 함수는 요청이 오면 새로운 인스턴스(독립 실행 환경)를 생성해 병렬로 처리한다. 하지만 너무 많은 함수가 동시에 실행되면 AWS 계정의 계산 자원이 고갈되거나, 함수가 데이터베이스 연결을 너무 많이 열어 DB 리소스가 부족해질 수 있다. 반대로 요청 급증에 대비해 미리 함수 인스턴스를 준비하지 않으면 초기 응답 시간(콜드 스타트)이 길어진다.

#2핵심 질문

동시에 실행되는 함수 수를 어떻게 제어하고, 성능 저하 없이 확장할 수 있을까?

#3동작 예시

동시성 한도를 함수마다 100개로 예약하면, 그 함수는 동시에 최대 100개 인스턴스까지만 실행 가능하다. 프로비저닝된 동시성으로 10개 인스턴스를 미리 "데워 두면" 새 요청이 오면 콜드 스타트 지연 없이 즉시 처리를 시작할 수 있다. 한도를 넘으면 스로틀링(throttling, 초과 요청 거부)이 발생한다.

#4동작 과정

  1. 예약 동시성함수의 최대 동시 실행 수를 정해서 상한을 설정한다. 다른 함수와 리소스 경합을 피하고, DB 연결 한도 등을 제어할 수 있다.
  2. 프로비저닝된 동시성미리 지정한 수의 함수 인스턴스를 항상 실행 상태로 유지한다. 요청이 오면 콜드 스타트(새 인스턴스 생성·초기화 시간) 없이 즉시 처리를 시작한다.
  3. 스로틀링과 확장동시 실행 한도를 넘으면 추가 요청은 스로틀링되며, AWS가 자동으로 인스턴스를 더 만들어 확장하거나(계정 한도까지), 한도에 도달하면 요청을 거부한다.

#5한 줄 요약

동시성 한도로 함수 실행을 제어해 리소스 낭비와 공유 리소스 충돌을 방지하고, 프로비저닝으로 콜드 스타트를 제거해 응답 성능을 보장하는 것

AWS Lambda05-07

AWS Lambda 버전·별칭·배포와 오류 처리

코드를 버전으로 고정하고 별칭으로 가리켜 가중치 기반 점진 배포를 하며, 재시도·DLQ 로 실패를 다루고 메모리 조정·SnapStart 로 성능을 높인다.

#1문제 상황

함수 코드를 수정해 배포하면 기존에 실행 중인 요청이나 이미 참조 중인 코드가 갑자기 새 버전으로 바뀌어 문제가 생길 수 있다. 또한 새 버전에 버그가 있으면 모든 사용자가 피해를 입는다. 함수 실패 시 자동 재시도나 별도 처리 메커니즘이 없으면 데이터 손실이 발생할 수 있다.

#2핵심 질문

새 코드를 배포하면서 기존 사용자에게 영향을 최소화하고, 실패를 안전하게 처리하며, 성능을 최적화하려면 어떻게 할까?

#3동작 예시

함수를 버전 1, 버전 2로 고정하고 별칭 "프로덕션"이 버전 1을 가리키다가, 테스트 후 별칭을 버전 2로 가리키면 클라이언트는 여전히 "프로덕션" 별칭을 쓰므로 영향이 없다. 트래픽을 90% 버전 1, 10% 버전 2로 나누는 가중 기반 배포도 가능하다. 함수 실패 시 비동기 호출은 자동으로 재시도하고, 결국 실패하면 DLQ(Dead Letter Queue, 사망 문자 큐)에 메시지를 보낸다.

#4동작 과정

  1. 버전·별칭 관리함수 코드를 버전으로 고정하고(버전 1, 2, 3…), 별칭(프로덕션, 스테이징)이 특정 버전을 가리키게 한다. 클라이언트는 별칭을 호출하므로 버전을 바꿔도 호출 코드는 그대로다.
  2. 점진 배포별칭의 가중치 기반 트래픽 분할(Shifting)로 신 버전으로의 트래픽을 천천히 늘린다. 문제 발생 시 가중치를 조정해 빠르게 롤백할 수 있다.
  3. 오류 처리와 성능비동기 호출 실패는 자동 재시도(최대 2회)되고, 최종 실패 시 DLQ로 보낸다. SnapStart(스냅샷 재시작)로 콜드 스타트를 줄이고, 메모리 크기를 조정해 CPU 할당량을 올려 성능을 개선한다.

#5한 줄 요약

버전과 별칭으로 배포를 안전하게 관리하면서, 재시도와 DLQ로 실패를 처리하고, 메모리·SnapStart로 성능을 최적화하는 것

API Gateway API 유형과 엔드포인트 유형

API Gateway는 REST(기능 풍부)·HTTP(경량 저비용)·WebSocket(양방향 실시간) 세 가지 API와 에지 최적화·리전·프라이빗 엔드포인트 유형을 제공하며 요구사항에 맞게 고른다.

#1문제 상황

클라이언트가 서버 기능(데이터 조회, 저장, 삭제)을 HTTP 요청으로 호출해야 할 때, AWS 리소스를 노출하는 엔드포인트가 필요하다. 하지만 모든 HTTP 요청을 그대로 함수에 보내면 인증, 요청 유효성 검증, 응답 변환, 레이트 제한 같은 공통 작업을 매번 함수에서 처리해야 한다. 또한 같은 기능을 여러 클라이언트가 부르는데 각 클라이언트마다 다른 URL을 만들어야 한다면 관리가 복잡해진다.

#2핵심 질문

클라이언트 요청을 백엔드 함수로 라우팅하면서 인증, 변환, 제한을 중앙에서 관리하고, 여러 엔드포인트 형태를 선택할 수 있도록 하려면?

#3동작 예시

API Gateway가 "GET /users" 요청을 받으면, 인증을 확인하고, 요청을 Lambda 함수로 보내고, 함수가 반환한 데이터를 JSON 형태로 클라이언트에 보낸다. API는 REST(기능이 많고 구성이 복잡), HTTP(기능이 적고 빠르고 저렴), WebSocket(양방향 실시간 통신) 세 종류가 있고, 엔드포인트는 에지 최적화(전 세계 배포), 리전(한 리전), 프라이빗(VPC 내부) 중 선택한다.

#4동작 과정

  1. API 유형 선택REST는 CORS, 요청·응답 변환, 권한 관리, 요청 유효성 검증 등을 지원하지만 비용이 높고 지연이 크다. HTTP는 기본 기능만 제공해 빠르고 저렴하지만 제한이 있다. WebSocket은 클라이언트와 서버가 양방향으로 실시간 메시지를 주고받아야 할 때(채팅, 알림)에 쓴다.
  2. 엔드포인트 유형 선택에지 최적화는 CloudFront CDN 캐시를 통해 전 세계 사용자에게 저지연 서비스를 제공한다. 리전 엔드포인트는 한 지역 내 높은 처리량을 다루고, 프라이빗 엔드포인트는 VPC(가상 네트워크) 내부에서만 접근 가능해 보안을 강화한다.

#5한 줄 요약

API 유형(REST·HTTP·WebSocket)과 엔드포인트 유형(에지·리전·프라이빗)을 조합해 기능성, 성능, 비용, 보안 요구사항에 맞는 API를 선택하는 것

API Gateway 리소스·메서드·통합

URL 경로(리소스)와 HTTP 동사(메서드)를 정의하고, 각 메서드를 Lambda 프록시·HTTP·AWS 서비스·모의(Mock)·VPC 링크 중 하나의 백엔드 통합에 연결한다.

#1문제 상황

HTTP 요청을 받아 처리하려면 먼저 어떤 URL 경로(리소스)와 HTTP 동사(GET, POST 등 메서드)의 조합인지 정의해야 한다. 그 다음 그 조합을 어디로 보낼지(백엔드) 정해야 하는데, Lambda, HTTP 엔드포인트, AWS 서비스, 더미 응답 등 여러 선택지가 있다. 각 선택에 따라 요청·응답 형식 변환, 호출 방식, 오류 처리가 달라진다.

#2핵심 질문

클라이언트 요청의 경로와 메서드를 정의하고, 각각을 어떤 백엔드로 연결할 때 어떤 방식을 쓸까?

#3동작 예시

"/users/{id}" 리소스에 "GET" 메서드를 정의하고, 이를 Lambda 프록시 통합으로 연결하면, API Gateway는 전체 HTTP 요청 정보(헤더, 쿼리, 본문, 경로 변수)를 JSON 형태로 Lambda에 보내고, Lambda가 반환한 응답(상태 코드, 헤더, 본문)을 클라이언트에 그대로 전달한다.

#4동작 과정

  1. 리소스와 메서드 정의URL 경로를 리소스로 구조화한다(예: "/users", "/users/{id}"). 각 리소스에 HTTP 메서드(GET, POST, PUT, DELETE)를 붙여 어떤 작업을 할지 정의한다.
  2. 백엔드 통합 선택Lambda 프록시(전체 요청·응답을 통과)로 함수가 모든 처리를 담당하거나, HTTP 통합으로 외부 HTTP 서버로 요청을 보내거나, AWS 서비스 통합으로 DynamoDB·SNS 등을 직접 호출하거나, 모의(Mock) 통합으로 더미 응답을 반환한다. VPC 링크로 VPC 내 프라이빗 리소스에 접근할 수도 있다.
  3. 요청·응답 처리각 메서드마다 요청 변환(매핑)과 응답 변환을 설정해 클라이언트와 백엔드 간 데이터 형식을 맞춘다. 오류 응답(4xx, 5xx)도 통합별로 다르게 처리된다.

#5한 줄 요약

URL 경로와 HTTP 메서드를 조합해 엔드포인트를 정의하고, 각 엔드포인트를 Lambda, HTTP, AWS 서비스, 모의, VPC 링크 중 적절한 백엔드로 연결해 요청을 라우팅·변환·처리하는 것

API 계층과 콘텐츠 전송06-03

요청 검증·데이터 변환·게이트웨이 응답·CORS·바이너리 미디어

모델로 들어오는 요청을 검증하고 매핑 템플릿으로 요청·응답 데이터를 변환하며, 게이트웨이 응답 커스터마이즈·CORS 허용·바이너리 미디어 타입 처리를 설정한다.

#1문제 상황

API에서 클라이언트의 요청을 받을 때, 기존에는 백엔드 코드가 직접 들어온 데이터를 검증했습니다. 잘못된 형식의 요청이나 필수 파라미터가 빠진 요청도 그대로 백엔드 로직까지 도달했고, 여러 클라이언트 형식(JSON, XML, 이진 데이터 등)을 처리하려면 각 엔드포인트마다 변환 코드를 반복해야 했습니다.

#2핵심 질문

클라이언트의 요청을 백엔드에 도달하기 전에 API 계층에서 검증하고 통일된 형식으로 변환할 수 있을까요?

#3동작 예시

API Gateway는 요청이 들어오면 먼저 메서드 요청 검증(매개변수, 헤더, 본문 스키마)을 수행하고, 통과한 요청을 매핑 템플릿(Velocity Template Language, VTL)으로 변환합니다. 예를 들어 클라이언트가 XML로 보낸 데이터를 Lambda 입력 형식인 JSON으로 바꾸고, 응답도 클라이언트가 원하는 형식(JSON, XML, 바이너리)으로 역변환하는 식입니다.

#4동작 과정

  1. 요청 검증요청이 들어올 때 필수 매개변수 확인, 형식 검사, 헤더 유효성 확인을 API Gateway에서 수행합니다. 검증 실패하면 400 오류를 즉시 반환해 불필요한 백엔드 호출을 줄입니다.
  2. 데이터 매핑 및 변환매핑 템플릿(VTL)을 사용해 들어온 요청을 백엔드가 이해하는 형식으로 변환합니다. 동시에 응답도 클라이언트가 원하는 형식으로 역변환합니다.
  3. 게이트웨이 응답 및 CORS 설정백엔드 응답을 받으면 게이트웨이 응답(오류, 인증 실패 등)을 커스터마이즈하고, CORS(Cross-Origin Resource Sharing, 다른 도메인의 브라우저 요청 허용) 헤더를 자동으로 추가합니다. 바이너리 미디어 타입(이미지, PDF 등)도 이곳에서 처리합니다.

SQS 큐 유형: 표준 큐와 FIFO 큐, 전달 보장·메시지 그룹·중복 제거

SQS 표준 큐는 최소 1회 전달과 순서 미보장 대신 거의 무제한 처리량을 주고, FIFO 큐는 메시지 그룹 ID 단위 순서 유지와 중복 제거 ID 기반 정확히 1회 처리를 보장한다.

#1문제 상황

메시지 처리 시스템에서 처리량이 많으면서도 순서를 보장해야 한다면, 두 가지 요구를 동시에 충족하기 어렵습니다. 기존 큐는 속도를 우선하면 순서가 뒤바뀔 수 있고, 순서를 보장하면 처리량이 떨어졌습니다. 또한 메시지가 중복으로 처리될 가능성도 있었습니다.

#2핵심 질문

메시지의 처리량, 순서 보장, 정확히 한 번 처리를 어느 수준까지 보장할 수 있을까요?

#3동작 예시

SQS의 표준 큐는 처리량 제한이 거의 없지만 메시지 순서를 보장하지 않고 중복 처리가 가능합니다. FIFO(First In First Out) 큐는 메시지 그룹 ID로 같은 그룹의 메시지는 순서대로 처리하고, 중복 제거 ID로 정확히 한 번만 처리하도록 보장합니다. 단, FIFO 큐는 그룹당 초당 300개 메시지 처리량으로 제한됩니다.

#4동작 과정

  1. 큐 유형 선택표준 큐는 높은 처리량이 필요하고 순서가 중요하지 않은 작업(로그 수집, 통계)에 사용하고, FIFO 큐는 순서와 정확히 1회 처리가 필수인 작업(결제, 주문)에 사용합니다.
  2. 메시지 그룹 ID와 중복 제거 ID 설정FIFO 큐에 메시지를 보낼 때 그룹 ID(같은 그룹은 순서 보장)와 중복 제거 ID(5분 내 같은 ID는 거부)를 지정합니다.
  3. 메시지 발행 및 소비발행자가 메시지를 큐에 넣고, 소비자가 폴링(주기적으로 확인) 또는 롱 폴링(대기)으로 메시지를 받아 처리합니다.

#5한 줄 요약

#1문제 상황

메시지 처리 중인 상태를 다른 소비자로부터 보호하고, 실패한 메시지와 대용량 데이터를 어떻게 처리할까요?

#3동작 예시

소비자가 메시지를 받으면 그 메시지는 가시성 제한 시간(기본 30초, 설정 가능) 동안 다른 소비자에게 보이지 않습니다. 처리를 완료하면 메시지를 삭제하고, 실패하면 가시성 제한 시간이 끝난 후 다시 큐에 나타나 재시도됩니다. 반복 실패하면 DLQ(Dead Letter Queue, 처리 불가 메시지 보관소)로 보냅니다. 256KB를 넘는 메시지는 본문을 S3에 저장하고 S3 참조만 큐에 넣습니다.

#4동작 과정

  1. 메시지 수신 및 가시성 제한소비자가 메시지를 받으면 가시성 제한 시간 동안 다른 소비자에게 숨겨집니다. 처리 중인 메시지가 중복 처리되지 않도록 보호합니다.
  2. 처리 및 폴링 전략소비자가 메시지를 처리합니다. 롱 폴링(최대 20초 대기)을 사용하면 빈 응답이 줄어들어 비용이 감소합니다.
  3. 실패 처리 및 DLQ처리 실패 시 재시도 횟수를 세고, 횟수 초과하면 DLQ로 보냅니다. 대용량 메시지는 S3에 저장하고 참조 URL을 큐에 넣습니다.

가시성 제한 시간과 재시도 정책, DLQ로 메시지 처리의 안정성을 높이고, 대용량 메시지 처리와 효율적인 폴링 방식으로 확장성을 확보하는 것

#1문제 상황

#3동작 예시

#4동작 과정

  1. 주제 생성 및 구독자 등록SNS에서 주제를 만들고, 여러 구독자(SQS, Lambda, HTTP 웹훅 등)를 등록합니다. 각 구독자는 독립적으로 메시지를 받습니다.
  2. 메시지 발행발행자가 주제에 메시지를 발행하면, SNS가 즉시 모든 구독자에게 밀어 보냅니다(Push 방식). 발행자는 구독자 목록을 알 필요 없습니다.

Cognito에서 사용자가 로그인하면 토큰을 받지만, 받은 토큰이 실제로 유효한지, 누가 발급했는지 확인해야 API를 보호할 수 있습니다. 기존에는 API 호출 때마다 데이터베이스에 조회해 세션이 유효한지 확인했으므로 성능이 떨어지고, 중앙 시스템에 의존해야 했습니다.

#2핵심 질문

Cognito가 발급한 토큰으로 API를 안전하게 보호할 수 있을까?

#3동작 예시

Cognito는 로그인 성공 시 JWT(JSON Web Token)를 발급합니다. JWT는 헤더·페이로드·서명 세 부분으로 이루어져 있으며, Cognito의 공개 키로 서명을 검증하면 토큰이 위변조되지 않았고 Cognito가 발급한 것임을 확인할 수 있습니다. 클라이언트는 이 액세스 토큰을 HTTP Authorization 헤더에 "Bearer <token>" 형태로 담아 보내고, API는 서명과 만료 시간, 클레임(사용자 정보)을 검증한 후 요청을 처리합니다.

#4동작 과정

  1. 로그인 후 토큰 수령사용자가 Cognito에서 인증되면 ID 토큰, 액세스 토큰, 갱신 토큰을 받습니다.
  2. 토큰을 베어러로 전송클라이언트는 API 호출 시 Authorization 헤더에 "Bearer <액세스토큰>"을 담아 보냅니다.
  3. API에서 토큰 검증API는 서명을 검증하고(Cognito 공개 키 사용), 만료 시간과 필요한 클레임(예: user ID, scope)을 확인한 후 요청을 허용하거나 거부합니다.

#5한 줄 요약

서명된 JWT 토큰을 베어러 토큰으로 사용해 API가 매번 중앙 시스템에 조회하지 않고도 토큰의 유효성과 사용자 정보를 검증하는 것

KMS 키와 봉투 암호화: 데이터 키·암호화 컨텍스트·키 정책·그랜트·키 교체

KMS 키로 데이터 키를 만들어 실제 데이터를 암호화하는 봉투 암호화 방식이며, 접근은 키 정책과 그랜트로, 무결성 보조는 암호화 컨텍스트로, 수명 관리는 키 교체로 한다.

#1문제 상황

데이터를 암호화하려면 암호화 키를 관리해야 하는데, 키를 애플리케이션 코드에 저장하면 보안 위협이 크고, 키가 노출되면 복구 불가능합니다. 또한 키를 자주 교체해야 하는데 기존 데이터의 암호를 다시 푸는 복잡한 작업이 필요합니다.

#2핵심 질문

데이터 암호화 키를 안전하게 관리하고, 주기적으로 교체하면서 이전 데이터도 보호할 수 있을까?

#3동작 예시

KMS는 마스터 키(KMS 키)를 AWS가 관리하고, 실제 데이터는 이 마스터 키로 생성한 임시 데이터 키로 암호화하는 봉투 암호화(Envelope Encryption) 방식을 사용합니다. 예를 들어 데이터베이스 기록을 암호화할 때, KMS 마스터 키를 요청해 데이터 키를 받고, 이 데이터 키로 기록을 암호화한 후 암호화된 데이터 키를 데이터와 함께 저장합니다. 나중에 복호화할 때는 암호화된 데이터 키를 KMS에 보내 원래 데이터 키를 받고 사용합니다.

#4동작 과정

  1. 마스터 키 생성 및 정책 설정관리자가 KMS 키를 생성하고 키 정책(누가 키를 사용할 수 있는지)과 그랜트(일시적 권한)로 접근 권한을 제어합니다.
  2. 데이터 키 생성 및 암호화애플리케이션이 KMS에 요청해 데이터 키를 받고, 이 키로 데이터를 암호화합니다. 암호화 컨텍스트(추가 검증 정보, 예: user-id="123")를 함께 보내면 나중에 같은 컨텍스트에서만 복호화 가능하도록 강제할 수 있습니다.
  3. 자동 키 교체KMS는 주기적으로 마스터 키를 자동 교체하지만, 이전 버전의 키도 보관해 기존 암호화 데이터를 복호화할 수 있습니다.

#3동작 예시

AWS Secrets Manager와 SSM Parameter Store는 둘 다 비밀을 중앙에서 저장하는 서비스이지만 목적이 다릅니다. Secrets Manager는 데이터베이스 비밀번호, API 키 같은 단기 비밀을 저장하고 자동 교체(Rotation)를 지원하므로 정기적으로 비밀을 갱신할 수 있습니다. Parameter Store의 SecureString은 설정값 중 민감한 것(예: 외부 서비스 키)을 저장하는 용도로, 자동 교체는 지원하지 않지만 더 저렴합니다.

#4동작 과정

  1. 비밀 저장관리자가 Secrets Manager에 데이터베이스 비밀번호를, Parameter Store에 API 키를 저장합니다.
  2. 런타임에 조회애플리케이션이 시작할 때 AWS SDK를 통해 이 저장소에서 비밀을 조회해 메모리에 로드합니다.

#2핵심 질문

#4동작 과정

CloudWatch 지표와 사용자 정의 지표: 네임스페이스·차원·통계·EMF

CloudWatch 지표는 시간에 따른 숫자 데이터를 네임스페이스와 차원으로 구분해 모아 통계로 보여주며, 애플리케이션이 PutMetricData나 EMF(로그에 지표를 embed하는 형식)로 자신만의 지표도 올릴 수 있다.

#1문제 상황

지금까지 모니터링은 EC2의 CPU, 메모리 같은 인프라 수준 지표에만 의존합니다. 비즈니스 관점에서 중요한 정보(주문 수, 에러율, 결제 실패 횟수)는 로그 파일에 흩어져 있고, 실시간으로 집계하기 어렵습니다.

#2핵심 질문

애플리케이션이 직접 보내는 비즈니스 지표를 CloudWatch에서 실시간으로 모니터링하고 알림을 받을 수 있을까요?

#3동작 예시

Node.js 애플리케이션에서 주문이 완료될 때마다 AWS SDK의 putMetricData({Namespace: 'MyEcommerce', MetricData: [{MetricName: 'OrdersCompleted', Value: 1}]}) 호출하면, CloudWatch가 이 호출들을 수집해 시간대별로 합산하고 그래프로 그려줍니다.

#4동작 과정

  1. 지표 정의Namespace(예: 'MyEcommerce')로 지표 그룹을 나누고, MetricName(예: 'OrdersCompleted')으로 지표를 구분하며, Dimensions(예: {'Region': 'us-east-1'})로 세부 분류해 나중에 리전별·서버별로 따로 볼 수 있게 합니다.
  2. 지표 전송 방법SDK의 PutMetricData를 직접 호출하거나, CloudWatch Logs에 JSON 형식의 EMF(Embedded Metric Format)를 write하면 자동으로 지표로 변환됩니다.
  3. 모니터링과 알람CloudWatch 대시보드에서 지표를 그래프로 시각화하고, 임계값을 설정해 지표가 넘으면 SNS·이메일·Slack으로 알림을 받을 수 있습니다.

#5한 줄 요약

애플리케이션이 직접 정의한 비즈니스 지표를 Namespace와 Dimensions로 분류해 CloudWatch에 올리고 실시간으로 모니터링하고 알림하는 것

CloudWatch Logs: 로그 그룹·스트림·보존, 지표 필터·구독 필터와 Logs Insights

CloudWatch Logs는 애플리케이션 로그를 로그 그룹/스트림 단위로 보관 기간을 정해 저장하고, 지표 필터로 숫자 지표를 뽑거나 구독 필터로 실시간 전달하며 Logs Insights 쿼리로 검색·분석한다.

#1문제 상황

애플리케이션에서 발생하는 로그는 서버나 로컬 파일에만 저장된다면, 여러 인스턴스에서 나온 로그를 모으려면 직접 각 서버에 접속해야 하고, 정해진 기간만 보관할 수 없으며, 특정 오류 패턴을 찾거나 통계를 내기 위해서는 매번 로그를 직접 파싱해야 한다.

#2핵심 질문

분산된 애플리케이션의 로그를 한곳에 모아 정해진 기간 동안 자동 보관하면서, 로그 데이터에서 원하는 정보를 빠르게 검색하고 분석할 수 있게 할 수 없을까?

#3동작 예시

Lambda 함수 3개가 각각 로그를 출력할 때, 각 함수의 로그는 CloudWatch Logs의 같은 로그 그룹(log group) 안의 서로 다른 로그 스트림(log stream)으로 자동 모여진다. 로그 그룹에 30일 보존 정책을 설정하면 30일이 지난 로그는 자동 삭제되고, Logs Insights라는 SQL 비슷한 쿼리로 모든 로그를 한 번에 검색·분석할 수 있다.

#4동작 과정

  1. 로그 저장 및 정리애플리케이션의 모든 로그는 로그 그룹 아래 스트림 단위로 저장되고, 각 스트림은 시간순으로 로그 이벤트를 기록한다.
  2. 자동 보관 및 폐기로그 그룹에 설정한 보존 기간(retention period)이 지나면 자동으로 삭제되어 저장 비용을 줄인다.
  3. 검색·추출·분석Logs Insights 쿼리로 로그를 검색하거나, 지표 필터(metric filter)로 로그에서 숫자 지표를 추출해 CloudWatch 대시보드에 표시하거나, 구독 필터(subscription filter)로 특정 패턴의 로그를 실시간으로 다른 서비스로 전달할 수 있다.

#5한 줄 요약

분산된 애플리케이션 로그를 중앙에서 저장하고 자동 관리하면서, 쿼리·필터·구독을 통해 로그 데이터에서 필요한 정보를 신속하게 뽑아 낼 수 있는 체계

CloudWatch 경보·대시보드와 알림 자동화

경보는 지표가 정한 임계값 조건을 만족하면 상태가 바뀌면서 SNS 알림이나 자동 조치를 실행하고, 대시보드는 여러 지표와 경보를 한 화면에 모아 보여준다.

#1문제 상황

지표(지연 시간, 에러율, CPU 사용률 등)는 계속 변하고, 문제 상황을 수동으로 모니터링하려면 24시간 누군가 대시보드를 봐야 한다. 임계값을 벗어난 상황을 즉시 알지 못하면 서비스 장애가 심해질 때까지 대응이 늦어진다.

#2핵심 질문

지표가 미리 정한 기준을 벗어나면 자동으로 감지해서 즉시 알림을 보내고 대응 조치를 실행할 수 있게 할 수 없을까?

#3동작 예시

Lambda 평균 지연 시간을 모니터링하는 경보(alarm)를 "1000밀리초 초과"로 설정하면, 지연 시간이 1000ms를 넘는 순간 경보 상태가 "알림" 상태로 바뀌면서 SNS 주제로 메시지를 보내 슬랙이나 이메일로 알림이 전달되고, 동시에 자동 복구 조치(예: 타임아웃 설정 조정, 동시 실행 제한 조정)를 실행할 수 있다.

#4동작 과정

  1. 경보 설정지표와 임계값·비교 조건(초과, 미만, 이상, 이하 등)을 정의하고, 조건을 언제 판단할 평가 기간을 설정한다.
  2. 상태 변화 감지지표가 조건을 만족하면 경보 상태가 "정상" → "알림" 또는 "정지"로 바뀐다.
  3. 알림 및 조치 실행SNS, 이메일, SQS, Lambda 등 여러 채널로 알림을 보내고, 필요하면 자동 조치(Auto Scaling, 정책 실행 등)를 트리거한다.

#5한 줄 요약

지표가 정한 임계값 조건을 만족했을 때 상태 변화를 자동 감지해서 알림과 자동 대응 조치를 즉시 실행해 서비스 장애를 빠르게 대응하도록 하는 것

AWS X-Ray로 분산 추적: 세그먼트·주석·샘플링·서비스 맵

X-Ray는 하나의 요청이 여러 서비스를 거치는 경로를 세그먼트/서브세그먼트로 기록해 서비스 맵과 트레이스로 보여 주며, 주석으로 검색하고 샘플링 규칙으로 수집량을 조절한다.

#1문제 상황

마이크로서비스 아키텍처에서 API Gateway → Lambda → DynamoDB 같은 여러 서비스를 거치는 하나의 요청이 있을 때, 어느 서비스에서 지연이 발생했는지 알아내려면 각 서비스의 로그와 지표를 따로 봐야 한다. 서비스 간 호출 순서, 각 구간의 지연 시간, 실패 지점을 파악하기 어렵다.

#2핵심 질문

하나의 요청이 여러 서비스를 거칠 때 어느 단계에서 얼마나 시간이 걸렸는지, 그리고 어디서 오류가 발생했는지를 한눈에 추적할 수 있을까?

#3동작 예시

클라이언트 요청이 API Gateway를 거쳐 Lambda로 가고, Lambda가 DynamoDB에 접근해 응답하는 과정을 X-Ray가 추적하면, 각 서비스 구간이 세그먼트(segment) 또는 서브세그먼트(subsegment)로 기록되고, 전체 경로를 시각화한 서비스 맵(service map)이 나타나며, 각 구간의 지연 시간·성공·실패 여부를 트레이스(trace)로 확인할 수 있다.

#4동작 과정

  1. 트레이스 생성 및 전파요청이 들어오면 고유 트레이스 ID가 생성되고, 각 서비스는 이 ID를 헤더에 담아 다음 서비스로 전달해 요청의 경로를 추적 가능하게 한다.
  2. 세그먼트·서브세그먼트 기록각 서비스에서 일어난 작업(API 호출, 데이터베이스 쿼리 등)을 세그먼트나 서브세그먼트로 기록하고, 주석(annotation)이나 메타데이터를 붙여 검색 가능하게 한다.
  3. 샘플링·필터링·시각화샘플링 규칙으로 수집할 트레이스 비율을 조절해 비용을 최적화하고, X-Ray 콘솔에서 서비스 맵과 트레이스 목록을 보며 성능 병목과 오류 지점을 찾는다.

#5한 줄 요약

하나의 요청이 여러 서비스를 거치는 경로를 트레이스로 기록해 각 단계의 지연·성공·실패를 시각화하고 성능 문제의 근본 원인을 빠르게 파악할 수 있도록 하는 것

근본 원인 분석: 배포 실패와 서비스 통합 문제 추적, CloudTrail

CloudTrail은 계정에서 일어난 API 호출을 누가·언제·무엇을 했는지 이벤트로 남겨, 배포 실패나 서비스 간 권한·통합 오류의 근본 원인을 되짚는 근거가 된다.

#1문제 상황

Lambda 배포에 실패하거나, DynamoDB 테이블 접근 권한이 없거나, SNS 메시지 발행이 안 될 때, 어떤 IAM 정책이 거부했는지, 누가 어떤 설정을 변경했는지 알기 어렵다. 문제를 재현해서 추적해야 하고, API 호출 이력을 남기는 중앙 로그가 없으면 근본 원인을 찾는 데 시간이 오래 걸린다.

#2핵심 질문

AWS 계정에서 일어난 모든 API 호출과 리소스 변경을 누가·언제·무엇을 했는지 남겨 배포 실패와 권한·통합 문제의 원인을 되짚을 수 있게 할 수 없을까?

#3동작 예시

IAM 역할을 수정하면 CloudTrail이 "PutRolePolicy" API 호출 이벤트를 기록하고, Lambda 함수가 DynamoDB 테이블을 읽으려 했을 때 권한이 없어 거부되면 CloudTrail에 "AccessDenied" 상태의 호출 기록이 남아, 어떤 정책 문제인지 추적할 수 있다.

#4동작 과정

  1. API 호출 기록AWS 계정의 모든 API 호출은 CloudTrail에 의해 자동 기록되고, 호출 ID·타임스탬프·수행자·대상 리소스·결과(성공·거부·에러)가 포함된다.
  2. 이벤트 저장 및 검색이벤트는 CloudTrail 로그 파일로 S3에 저장되고, CloudTrail 콘솔이나 CloudWatch Logs 구독을 통해 검색·필터링할 수 있다.
  3. 근본 원인 파악API 호출 순서와 실패 원인을 보면서, 권한 부족·구성 오류·외부 서비스 거부 등의 근본 원인을 규명한다.

#5한 줄 요약

AWS 계정의 모든 API 호출을 누가·언제·무엇을 했는지 기록해 배포 실패나 서비스 통합 문제의 근본 원인을 추적하고 보안 감시·규정 준수 증명에 쓸 수 있도록 하는 것

성능과 비용 최적화, 그리고 개발 보조 도구

관측 데이터를 근거로 지연·처리량을 개선하고, 로그·지표 수집량과 리소스 설정을 조정해 비용을 줄이며, 개발 보조 도구로 문제 해결을 앞당긴다.

#1문제 상황

지연 시간과 에러율이 높거나, 로그·지표·트레이스 데이터가 기하급수적으로 쌓여서 저장 비용이 올라간다. 언제 어디를 최적화해야 하는지는 알지 못하고, 문제를 찾기 위해 로그를 일일이 훑어야 한다. 개발 중에도 로컬 환경과 AWS 환경의 차이로 인한 오류를 재현하고 디버깅하는 데 시간이 걸린다.

#2핵심 질문

관측 데이터를 기반으로 지연과 처리량을 개선하고, 수집하는 로그·지표의 양을 줄여 비용을 최적화하면서, 개발 중 문제를 더 빨리 찾을 수 있게 할 수 없을까?

#3동작 예시

X-Ray 트레이스로 Lambda 함수의 평균 지연이 2초임을 알면, DynamoDB 쿼리 최적화나 병렬 처리로 1초로 줄이는 목표를 세울 수 있다. CloudWatch Logs Insights로 정확히 어느 부분에서 시간이 걸리는지 찾으면, 메모리 크기를 높이거나 코드 알고리즘을 개선해 최적화한다. 또한 불필요한 로그 레벨을 낮추거나 샘플링 비율을 조절해 저장량을 줄이면 비용도 내려간다.

#4동작 과정

  1. 지연·처리량 개선X-Ray와 CloudWatch Logs Insights로 각 단계의 지연을 파악하고, 병목 지점을 확인한 후 Lambda 메모리·타임아웃·동시 실행 제한, 데이터베이스 인덱스, 캐싱 등으로 성능을 높인다.
  2. 로그·지표 수집량 최적화로그 스트림의 보존 기간을 줄이거나, 불필요한 로그 레벨을 INFO에서 WARNING으로 변경하거나, 지표 필터 조건을 더 정밀하게 하고, X-Ray 샘플링 비율을 조절해 데이터 저장량을 줄인다.
  3. 개발 도구와 조기 문제 해결CloudWatch Insights, X-Ray 콘솔, CloudTrail 로그 검색 등을 활용해 프로덕션 환경의 문제를 신속하게 파악하고, 로컬 개발 중에도 AWS SDK에 CloudWatch 에이전트를 붙여 실시간 문제를 추적함으로써 배포 전 오류를 줄인다.

#5한 줄 요약

관측 데이터를 근거로 성능 병목을 찾아 개선하고, 데이터 수집량과 리소스 설정을 최적화해 비용을 절감하면서, 개발 과정에서 문제 해결을 앞당기는 것
