버전 관리와 분산 버전 관리

파일의 변경 이력을 기록·복원하는 것이 버전 관리이고, 모든 참여자가 전체 이력 사본을 각자 갖는 방식이 분산 버전 관리다.

1상대의 출발점 확인

버전 관리가 없으면 파일을 수정할 때마다 파일명을 바꿔서 저장해야 합니다. file_v1.txt, file_v2.txt, file_final.txt 같은 식입니다. 여러 사람이 같은 파일을 수정하면 누가 언제 뭘 바꿨는지 알 수 없습니다. 예전 버전으로 돌아가는 것도 수동으로 찾아야 합니다.

2질문 제기

파일의 모든 변경을 자동으로 기록하고, 누가 언제 뭘 바꿨는지 추적하며, 필요하면 이전 상태로 되돌릴 수 있을까?

3구조적 핵심 예시

버전 관리 없음: file.txt를 수정하면 이전 내용이 사라지고 새 내용으로 덮어써집니다. 버전 관리 있음: file.txt를 수정할 때마다 이전 상태와 현재 상태가 모두 저장소에 기록되어 둘 다 나중에 접근 가능합니다. 분산 버전 관리는 이 저장소 사본을 개발자 A도 갖고, 개발자 B도 각각 가짐으로써 중앙 서버 없이도 전체 이력을 유지합니다.

4단계별 동작 과정

  1. 변경 기록파일을 수정할 때마다 변경 내용과 메타정보(누가, 언제, 왜)를 저장소에 기록합니다.
  2. 사슬 구조각 기록은 시간순으로 쌓여 체인을 형성하여, 한 버전이 이전 버전을 가리키고 다음 버전과 연결됩니다.
  3. 복원 가능필요할 때 언제든 원하는 시점의 파일 상태로 돌아갈 수 있습니다.

5본질 요약

파일의 모든 변경을 시간순으로 기록하고, 이 기록의 사본을 각 참여자가 독립적으로 유지함으로써 중앙 서버 없이도 협업하고 이력을 보존할 수 있게 하는 것

1Git이라는 도구의 전제01-02

스냅샷과 해시: Git이 데이터를 보는 방식

Git은 변경분(diff)이 아니라 시점마다의 파일 전체 상태를 스냅샷으로 저장하고, 각 객체를 내용 기반 SHA 해시로 식별한다.

1상대의 출발점 확인

기존 버전 관리 시스템(CVS, SVN)은 변경분만 저장합니다. 예를 들어 v1에서 1줄을 추가해 v2가 되고, v2에서 다른 줄을 수정해 v3이 된다면, 각 버전의 변경분(diff)만 기록합니다. 특정 시점의 완전한 파일 상태를 보려면 초기 버전부터 여러 변경분을 순서대로 조합해야 하므로 시간이 걸리고, 중간 데이터가 손상되면 복구가 어렵습니다.

2질문 제기

각 시점마다 파일 상태를 완전한 스냅샷으로 저장하면서도 효율적으로 관리할 수 있을까?

3구조적 핵심 예시

변경분 방식: v1 → (줄 추가) → v2 → (줄 수정) → v3. 각 단계에서 변경분만 저장합니다. 스냅샷 방식: v1에서 모든 파일의 전체 내용을 저장하고, v2에서 또 모든 파일의 전체 내용을 저장합니다. 두 스냅샷이 같은 파일을 가졌다면 Git은 내용을 계산하여 같은 해시(고유 번호)를 부여하므로 중복 저장을 피할 수 있습니다.

4단계별 동작 과정

  1. 스냅샷 생성파일을 커밋할 때 전체 파일들의 상태를 스냅샷으로 저장합니다.
  2. 해시 계산Git은 그 스냅샷의 내용을 SHA-1 해시로 계산하여 40자 16진수 문자열(예: a1b2c3d4...)로 변환합니다.
  3. 식별자로 사용이 해시가 그 버전의 유일한 식별자가 되어 이전 버전을 가리키고 다음 버전과 연결되므로 내용이 바뀌면 해시도 반드시 바뀝니다.

5본질 요약

각 커밋 시점의 모든 파일을 통째로 저장하고, 내용 기반의 SHA 해시로 각 스냅샷을 식별함으로써 손상 감지 및 중복 제거를 자동으로 처리하고 접근 속도를 높이는 것

1Git이라는 도구의 전제01-03

1상대의 출발점 확인

파일을 수정하는 것과 저장소에 기록하는 것을 바로 연결하면 문제가 생깁니다. 여러 파일을 동시에 수정하다 보면 완성되지 않은 수정도 있고, 서로 무관한 변경들이 섞입니다. 모든 변경을 한 번에 커밋하면 "로그인 기능 추가"라는 커밋에 "버튼 색상 변경"까지 포함되어 나중에 이력을 읽을 때 혼란스럽습니다.

2질문 제기

작업 중인 여러 변경 중에서 지금 커밋할 것만 골라서 저장소에 기록할 수 있을까?

3구조적 핵심 예시

파일 A, B, C가 모두 수정되었습니다(작업 트리). 이 중 A, B만 다음 커밋에 포함시키고 C는 계속 작업하고 싶다면, A와 B만 별도 영역에 올려놓습니다(인덱스). 그다음 커밋하면 A, B만 저장소에 기록되고, C는 작업 트리에만 남아 계속 수정할 수 있습니다.

4단계별 동작 과정

  1. 작업 트리실제로 파일을 편집하는 공간입니다. 모든 변경이 여기서 일어나며, 완성된 변경도 미완성 변경도 모두 포함됩니다.
  2. 인덱스(스테이징 영역)git add 명령으로 파일을 올려놓는 임시 영역입니다. 다음 커밋에 포함할 변경을 여기서 선택하고 정리합니다.
  3. 저장소(.git)git commit 명령으로 인덱스의 내용을 확정 기록으로 저장하는 공간입니다. 영구적인 이력이 쌓여 언제든 접근 가능합니다.

5본질 요약

작업 트리에서 수정된 파일들 중 일부만 인덱스에 선택하여 올려놓고, 그것을 커밋해 저장소에 저장함으로써 논리적으로 연관된 변경들을 하나의 의미 있는 커밋으로 정리할 수 있게 하는 것

1상대의 출발점 확인

Git을 처음 설치하면 Git이 사용자가 누구인지 알 수 없습니다. 커밋을 할 때 "이 변경을 누가 했는가"를 기록해야 하는데, 설정이 없으면 오류가 발생합니다. 매 커밋마다 사용자 정보를 입력할 수도 없습니다. 또한 Git이 동작하는 방식(어떤 에디터로 메시지를 편집할지, 라인엔딩을 어떻게 처리할지 등)도 사전에 설정해야 합니다.

2질문 제기

3구조적 핵심 예시

4단계별 동작 과정

  1. 시스템 수준 설정이 컴퓨터의 모든 사용자가 공유하는 설정입니다. 거의 사용하지 않습니다.
  2. 전역 설정현재 사용자의 모든 Git 저장소에 적용되는 설정입니다. git config --global로 설정하며, 보통 여기서 개인 정보를 등록합니다.
  3. 저장소 수준 설정특정 저장소에만 적용되는 설정입니다. 전역 설정을 덮어쓰므로, 예를 들어 직장 프로젝트는 직장 이메일로 따로 설정할 수 있습니다.

2질문 제기

모든 Git 명령이 일관된 형식을 따르고, 언제든 공식 매뉴얼을 바로 볼 수 있을까?

3구조적 핵심 예시

명령어 git add file.txt는 git(프로그램) + add(명령) + file.txt(인자)로 구성됩니다. 옵션 git add -u는 같은 구조에 -u(옵션, 수정된 파일만 추가 의미)를 붙입니다. 도움말 git add --help를 입력하면 즉시 add 명령어의 공식 매뉴얼이 터미널에서 열려 언제든 정보를 확인할 수 있습니다.

4단계별 동작 과정

  1. 명령줄 구조모든 명령이 git <명령어> [옵션] [인자] 형태를 따릅니다. 이 일관된 형식을 배우면 새로운 명령어도 같은 로직으로 이해할 수 있습니다.
  2. 옵션 규칙짧은 옵션은 -u 형태, 긴 옵션은 --update 형태로 표준화되어 있어 한눈에 기능을 예측할 수 있습니다.
  3. 즉시 도움말git help <명령어> 또는 git <명령어> --help를 입력하면 공식 매뉴얼이 터미널에서 즉시 열리므로 언제든 자세한 정보에 접근할 수 있습니다.

2저장소를 만들고 변경을 기록하기02-01

저장소 만들기: init과 clone

빈 폴더를 Git 저장소로 바꾸는 git init과, 원격 저장소를 통째로 복제해 오는 git clone으로 작업을 시작한다.

1상대의 출발점 확인

프로젝트를 시작하는 방식은 두 가지입니다. 하나는 로컬 폴더에서 새로 시작하는 것이고, 다른 하나는 다른 사람의 저장소에서 코드를 받아 시작하는 것입니다. 두 경우 모두 "Git이 이 코드를 추적하기 시작해야 한다"는 공통점이 있지만, 상황과 필요한 조치가 다릅니다. 로컬에서 새로 시작하면 이력이 없고, 기존 저장소를 받으면 모든 이력도 함께 받아야 합니다.

2질문 제기

로컬 폴더를 Git 저장소로 만들거나, 원격 저장소를 통째로 복제해 옮겨올 수 있을까?

3구조적 핵심 예시

빈 폴더 ~/my-project에서 git init을 실행하면 .git 디렉터리가 생성되고 Git이 추적을 시작합니다. GitHub의 저장소 주소로 git clone https://github.com/user/repo.git을 실행하면 저장소 전체(모든 파일, 모든 커밋 이력)가 로컬에 복제되고, .git 디렉터리도 함께 복제되므로 전체 이력에 접근할 수 있습니다.

4단계별 동작 과정

  1. git init현재 폴더 안에 .git 디렉터리를 생성하여 Git 저장소로 초기화합니다. 새 프로젝트를 로컬에서 시작할 때 사용하며, 이력은 비어 있습니다.
  2. git clone원격 저장소의 모든 파일과 커밋 이력을 로컬로 복제합니다. 초기 .git 디렉터리도 함께 복제되므로 복제 후 즉시 모든 이력에 접근할 수 있습니다.
  3. 결과두 경우 모두 작업을 시작할 수 있는 Git 저장소가 로컬에 준비됩니다. init은 이력 없이 시작하고, clone은 기존 이력을 모두 가진 상태로 시작합니다.

5본질 요약

git init과 clone이 Git 저장소 준비의 두 경로로, init은 로컬 폴더를 새로운 저장소로 만들고 clone은 원격 저장소를 통째로 복제함으로써 새로운 프로젝트를 시작하거나 기존 프로젝트에 합류할 수 있게 하는 것

1상대의 출발점 확인

3구조적 핵심 예시

파일 A를 수정하기만 했다면 git status는 "modified: A"를 빨간색으로 표시합니다(인덱스에는 없음). 파일 B를 스테이징한 후 또 수정했다면 git status는 초록색 "modified: B"(스테이징된 상태)와 빨간색 "modified: B"(추가로 수정된 상태)를 함께 표시하므로, 어떤 부분이 커밋될지 즉시 알 수 있습니다.

  2. 스테이징된 파일 목록인덱스에 올려놓은 파일을 초록색으로 표시합니다. "new file:", "modified:", "deleted:" 등으로 구분하여 다음 커밋에 포함될 변경을 명확히 보여줍니다.
  3. 미추적 파일 목록Git이 아직 추적하지 않는 파일을 빨간색 "Untracked files:"로 표시합니다. 새로 생성된 파일이나 의도적으로 추적 대상에서 제외한 파일들입니다.

git restore로 아직 커밋하지 않은 변경을 되돌리고, git revert로 이미 남긴 커밋을 취소하는 새 커밋을 만들며, git clean으로 추적되지 않는 파일을 정리한다.

변경을 했지만 실수였을 때 되돌리고 싶습니다. 하지만 상황에 따라 대응 방식이 다릅니다. 아직 커밋하지 않은 변경은 버리고 싶을 수도, 이미 커밋해서 다른 곳에 영향을 끼친 변경은 새 커밋으로 취소하고 싶을 수도, 추적되지 않는 임시 파일은 정리하고 싶을 수도 있습니다.

2질문 제기

3구조적 핵심 예시

테스트 코드를 수정했지만 테스트가 깨진 경우 아직 커밋하지 않았다면 git restore 파일을 써서 수정 전으로 되돌립니다. 하지만 이미 main에 머지된 커밋이 버그를 만들었다면 git revert 커밋해시로 그 커밋의 반대 변경을 새 커밋으로 만들어 이력에 기록하는 게 안전합니다.

4단계별 동작 과정

  1. git restore로 커밋되지 않은 변경 버리기git restore 파일을 실행하면 작업 트리의 파일을 마지막 인덱스 상태로 되돌립니다. git restore --staged 파일을 쓰면 인덱스에 올려진 변경을 마지막 커밋 상태로 복구합니다.
  2. git revert로 이미 적용된 커밋 취소git revert 커밋해시를 실행하면 그 커밋의 반대 변경을 새 커밋으로 만들어 이력에 "이 커밋을 취소했다"는 사실을 명확하게 기록합니다.
  3. git clean으로 추적되지 않는 파일 정리git clean -fd를 실행하면 .gitignore에 지정되지 않은 추적되지 않는 파일들을 디스크에서 삭제합니다.

Git 저장소는 파일 내용(blob), 디렉터리 목록(tree), 스냅샷과 이력(commit), 이름표(tag) 네 종류의 객체를 해시 이름으로 저장한다.

1상대의 출발점 확인

Git은 파일을 저장합니다. 하지만 단순히 "파일들"로 저장하는 것이 아니라, 파일 내용, 디렉터리 구조, 스냅샷 메타데이터, 이름표를 분리해서 저장합니다. 이 네 가지 객체 종류와 그들의 연결 방식을 이해하면 Git이 왜 강력한 이력 관리 도구인지가 명확해집니다.

2질문 제기

Git이 변경 이력을 내부적으로 어떤 단위로 저장하고, 그 단위들이 어떻게 연결되어 이력을 만들까?

3구조적 핵심 예시

파일 두 개(login.js, config.json)를 수정해서 커밋했을 때, Git은 각 파일의 새 내용을 blob이라 불리는 개별 객체로 저장하고, 프로젝트의 전체 디렉터리 구조와 파일 목록을 tree 객체로 저장하며, 그 tree를 가리키고 이전 커밋을 부모로 가리키는 commit 객체를 만들어 이 커밋이 언제, 누가, 왜 만들었는지와 이전 상태와의 관계를 기록합니다.

4단계별 동작 과정

  1. Blob 객체각 파일의 내용을 SHA-1 해시로 이름 붙인 객체입니다. 같은 내용이면 같은 해시를 가지므로 같은 파일이 여러 브랜치에 있어도 한 번만 저장되고, 파일이 수정될 때마다 새 blob이 생성됩니다.
  2. Tree 객체디렉터리 계층을 표현하는 객체로, 파일들의 이름과 그들의 blob 객체를 기록하고 하위 디렉터리의 tree를 참조합니다.
  3. Commit 객체와 TagCommit은 특정 시점의 tree를 가리키고 부모 커밋을 참조해서 이력 체인을 구성하며, 커밋 메시지·작성자·날짜를 기록합니다. Tag는 특정 커밋에 "v1.0" 같은 이름을 붙이는 참조입니다.

3구조적 핵심 예시

4단계별 동작 과정

  1. 개별 커밋 생성새 커밋을 만들 때마다 현재 HEAD가 가리키는 커밋을 "부모"로 기록한다.
  2. 부모 관계 누적여러 커밋이 차례로 쌓이면서 각각이 이전 커밋을 가리킨다. 병합 커밋의 경우 두 개의 부모를 가진다.

2질문 제기

브랜치와 태그의 이름들이 정확히 어디에 어떤 형태로 저장되어 있을까?

  3. packed-refs 최적화참조가 많아지면 여러 파일을 하나의 .git/packed-refs 파일로 압축 저장할 수 있다.

새로운 작업 라인이 필요할 때 어떻게 빠르게 만들고, 언제든 목록을 보고, 필요 없어지면 정리할 수 있을까?

3구조적 핵심 예시

4단계별 동작 과정

  1. 브랜치 생성지정한 커밋(또는 현재 HEAD)의 해시를 .git/refs/heads/브랜치이름 파일에 저장한다.
  2. 브랜치 목록 조회.git/refs/heads/ 디렉토리의 모든 파일을 읽으면 존재하는 모든 로컬 브랜치를 얻는다.
  3. 브랜치 삭제해당 파일을 지우거나, 병합 기이력에 반영되었는지 확인한 후 삭제한다.

1상대의 출발점 확인

기존에는 한 브랜치에 머물러 있다가 다른 브랜치로 이동할 때, 단순히 "전환"한다고 생각했다. 하지만 실제로는 작업 트리(working directory)의 모든 파일 내용이 대상 커밋 상태로 바뀌고, HEAD가 가리키는 대상도 바뀐다.

2질문 제기

다른 브랜치로 이동할 때 작업 중인 파일들은 어떻게 안전하게 바뀌고, HEAD는 정확히 어디를 가리켜야 할까?

3구조적 핵심 예시

4단계별 동작 과정

  1. 대상 확인전환할 브랜치(또는 특정 커밋)를 지정한다.
  2. 충돌 검사 및 작업 트리 갱신현재 변경사항이 있는지 확인하고, 안전하면 목표 커밋의 파일 내용을 작업 트리에 복원한다.
  3. HEAD 갱신브랜치 이름으로 전환했다면 HEAD가 그 브랜치를 가리키도록 설정하고, 특정 커밋을 직접 지정했다면 detached HEAD 상태가 된다(HEAD가 브랜치 대신 커밋을 직접 가리킴).

병합의 두 얼굴: fast-forward와 3-way merge

갈라지지 않았으면 포인터만 앞으로 옮기는 fast-forward, 갈라졌으면 공통 조상을 기준으로 양쪽 변경을 합치는 3-way merge 가 일어난다.

1상대의 출발점 확인

브랜치를 나누어 작업한 후 다시 합칠 때, 두 가지 상황이 발생한다. 첫째, 메인 브랜치는 변경이 없고 작업 브랜치만 앞으로 나아간 경우다. 둘째, 메인과 작업 브랜치가 모두 앞으로 나아가 두 갈래가 갈라진 경우다. Git은 이 두 상황을 다르게 처리해야 한다는 것을 모를 수 있다.

2질문 제기

갈라진 두 브랜치를 합칠 때, 상황의 복잡도에 따라 다른 방식이 필요한가?

3구조적 핵심 예시

메인 브랜치에서 작업 브랜치로 갈라져 작업 브랜치만 5개 커밋을 진행한 경우, Git은 메인의 포인터를 단순히 앞으로 옮기면 된다. 하지만 그 사이 메인도 3개 커밋을 진행했다면, 메인과 작업 브랜치의 공통 조상 이후로 양쪽이 어떻게 변경했는지 모두 고려해서 합쳐야 한다.

4단계별 동작 과정

  1. Fast-forward메인 브랜치가 변경되지 않고 작업 브랜치만 앞으로 나아간 상황에서는 메인의 HEAD 포인터를 작업 브랜치의 끝점으로 옮기기만 하면 된다.
  2. 3-way merge메인과 작업 브랜치가 모두 변경된 경우, Git은 공통 조상 커밋(merge base, 두 브랜치가 갈라지기 전의 마지막 공통 커밋)을 찾아 그 커밋 이후 메인이 한 변경과 작업 브랜치가 한 변경을 모두 적용한 새로운 병합 커밋(merge commit)을 만든다.

5본질 요약

갈라짐의 정도에 따라 단순한 포인터 이동(fast-forward)과 변경 사항 통합(3-way merge)을 구분하는 것

  3. 완료 등록git add로 파일을 스테이징하고 git commit으로 병합 커밋을 만들어 충돌 해결을 확정한다.

1상대의 출발점 확인

충돌을 해결한 후 나중에 같은 부분이 다시 충돌하면, 처음부터 다시 수동으로 해결해야 한다. 같은 방식으로 여러 브랜치를 병합하거나 rebase할 때 반복되는 충돌이 나타나면 비효율적이다.

작업 미루기: stash

커밋하기 애매한 작업 중 변경사항을 잠시 치워 두고 깨끗한 상태로 돌아갔다가 나중에 되살리는 임시 보관함.

작업 중인 변경사항이 있을 때, 다른 브랜치로 전환하거나 급한 버그를 먼저 처리하려면 현재 작업을 커밋해야 한다. 하지만 완성되지 않은 작업까지 커밋하고 싶지 않으면, 현재 상태를 임시로 어딘가 보관할 방법이 필요하다.

2질문 제기

완성되지 않은 작업 중 상태를 어디 임시 보관했다가 필요할 때 되돌릴 수 있을까?

3구조적 핵심 예시

파일 3개를 수정 중일 때 git stash로 변경사항을 임시 저장하고 깨끗한 상태로 돌린 다음, 다른 브랜치에서 급한 일을 처리한 후 git stash pop으로 수정 상태를 되살린다.

4단계별 동작 과정

  1. 임시 저장git stash로 현재 수정 중인 변경사항과 스테이징된 변경을 .git 내부의 임시 저장소에 저장하고 작업 폴더를 마지막 커밋 상태로 되돈다.
  2. 작업 전환깨끗한 상태에서 다른 브랜치로 이동하거나 다른 급한 작업을 진행할 수 있다.
  3. 상태 복구git stash pop으로 저장해 둔 변경사항을 다시 작업 폴더에 되살린다. pop 대신 apply를 쓰면 stash 목록에서 제거하지 않는다.

5원격 저장소와 함께 일하기05-01

원격이란 무엇인가: remote와 origin

원격(remote)은 인터넷이나 네트워크 어딘가에 있는 같은 프로젝트의 저장소를 가리키는 이름표이고, 클론하면 기본으로 origin 이라는 이름이 붙는다.

1상대의 출발점 확인

로컬 저장소에서만 작업할 때는 다른 사람과 코드를 공유할 방법이 없다. 팀 협업을 하려면 중앙의 공유 저장소(GitHub, GitLab 등)가 필요하고, 로컬 저장소가 그것을 어떻게 참조하는지 알아야 한다.

2질문 제기

로컬 저장소가 원격에 있는 같은 프로젝트의 저장소와 연결되려면 어떻게 해야 할까?

3구조적 핵심 예시

git clone https://github.com/user/project.git으로 복제하면, 로컬 저장소가 자동으로 그 GitHub 주소를 origin이라는 이름으로 등록해 둔다.

4단계별 동작 과정

  1. 원격 등록git remote add origin <URL>로 원격 저장소의 주소를 origin이라는 이름표에 저장한다. 클론할 때는 자동으로 origin이 등록된다. 같은 저장소에 여러 이름표를 붙일 수도 있다.
  2. 목록 확인git remote -v로 등록된 모든 원격(remote)과 그 주소를 확인할 수 있다. 각 원격마다 push 주소와 fetch 주소를 따로 설정할 수 있다.
  3. 사용push, pull, fetch 같은 명령에서 origin을 지정해 어느 원격과 동기화할지 결정한다. 예: git push origin main, git pull origin feature.

5본질 요약

원격 저장소의 주소를 이름표(origin 등)에 저장해, 명령어에서 긴 URL 대신 짧은 이름으로 참조하는 주소 관리 시스템

5원격 저장소와 함께 일하기05-02

refspec과 원격 추적 브랜치

refspec 은 "내 어떤 참조를 상대의 어떤 참조에 맞출지"를 적는 규칙이고, 그 결과 origin/main 같은 원격 추적 브랜치가 원격의 상태를 그대로 비춰 준다.

→ 05-03 참조

1상대의 출발점 확인

기존에는 원격 저장소와 로컬 저장소를 동기화할 때, 어떤 참조(브랜치, 태그)가 어디에 있고 어디로 가야 하는지를 직접 추적해야 했습니다. 특히 여러 원격이 있거나 브랜치 이름이 다를 때 혼동이 생기고, 원격의 상태를 로컬에서 정확히 파악하기 어려웠습니다.

2질문 제기

내 로컬 브랜치와 원격의 브랜치를 어떻게 명확하게 연결하고, 원격의 현재 상태를 로컬에서 언제든 확인할 수 있을까요?

3구조적 핵심 예시

refspec은 "내 로컬의 refs/heads/main을 origin의 refs/heads/main에 맞춘다"는 규칙을 적는 방식입니다. 예를 들어 refs/heads/*:refs/remotes/origin/* 규칙은 원격의 모든 브랜치를 로컬의 origin/ 폴더 아래 복사본으로 유지하겠다는 뜻입니다.

4단계별 동작 과정

  1. refspec 규칙 설정git clone이나 git remote add 시에, 기본 refspec이 자동으로 설정되어 어떤 참조들을 추적할지 정해집니다.
  2. fetch 수행원격에서 새로운 커밋을 가져올 때, refspec 규칙에 따라 해당 커밋들이 로컬의 정해진 위치(원격 추적 브랜치)에 저장됩니다.
  3. 원격 추적 브랜치 유지origin/main 같은 원격 추적 브랜치는 원격의 실제 상태를 계속 반영하므로, 언제든 원격이 어디에 있는지 확인할 수 있습니다.

5본질 요약

로컬과 원격의 참조를 자동으로 대응하는 규칙(refspec)을 정해서, 원격 추적 브랜치가 항상 원격의 상태를 정확히 비춰줄 수 있게 하는 것

5원격 저장소와 함께 일하기05-03

가져오기: fetch와 pull

fetch 는 원격의 새 커밋만 내려받아 원격 추적 브랜치를 갱신하고, pull 은 그 fetch 에 병합(또는 리베이스)까지 이어서 내 브랜치에 반영한다.

→ 05-02 참조

1상대의 출발점 확인

기존에는 원격 저장소의 새로운 커밋을 받으려면, 직접 모두 다운로드한 후 동시에 로컬 브랜치에 합쳐야 했습니다. 하지만 이렇게 하면 원격의 상태를 먼저 확인하지 않고 무조건 병합을 시도하게 되어 충돌 위험이 있었습니다.

2질문 제기

원격의 새 커밋을 먼저 확인한 후에 내 브랜치에 안전하게 반영하려면 어떻게 해야 할까요?

3구조적 핵심 예시

fetch는 원격의 커밋만 받아서 origin/main 같은 원격 추적 브랜치에만 저장하고, 아직 내 작업 브랜치(main)에는 손을 대지 않습니다. 그 후 pull은 fetch 한 후에 병합(merge, 두 브랜치를 합치는 것) 또는 리베이스(rebase, 커밋을 재배열하는 것)까지 한 번에 수행합니다.

4단계별 동작 과정

  1. fetch 실행원격 저장소에서 새로운 커밋들만 내려받아, 원격 추적 브랜치(origin/main)를 갱신합니다. 이 단계에서는 내 작업 브랜치는 변하지 않습니다.
  2. 충돌 확인fetch 결과를 보고 충돌 가능성을 미리 파악할 수 있습니다.
  3. 병합 또는 리베이스pull은 fetch 후에 자동으로 merge 또는 rebase를 수행하여, 원격의 변화를 내 브랜치에 반영합니다.

5본질 요약

fetch로 원격의 상태를 안전하게 먼저 확인한 후, pull로 그것을 내 브랜치에 합치는 2단계 과정을 제공하여 실수를 줄이는 것

5원격 저장소와 함께 일하기05-04

보내기: push의 규칙과 안전장치

push 는 내 커밋을 원격에 올리는 명령이며, 남의 작업을 지우지 않도록 fast-forward 규칙과 --force-with-lease 같은 안전장치를 둔다.

1상대의 출발점 확인

기존에 내 커밋을 원격에 올릴 때, 다른 사람이 이미 올린 커밋을 실수로 덮어쓸 수 있었습니다. 특히 여러 사람이 동시에 작업할 때 누군가의 작업이 사라질 수 있는 위험이 있었습니다.

2질문 제기

내 커밋을 원격에 올리면서도 남의 작업을 실수로 지우지 않으려면 어떻게 해야 할까요?

3구조적 핵심 예시

push의 기본 규칙은 fast-forward 검사입니다. 만약 원격의 커밋이 내 커밋의 상위에 있다면(즉, 내가 모르는 새로운 커밋이 있다면) push를 거부하고, 먼저 fetch와 병합을 하도록 강제합니다. 더 세밀한 제어가 필요하면 --force-with-lease 옵션으로 내가 마지막으로 본 원격 상태를 기준으로만 강제 푸시를 허용합니다.

4단계별 동작 과정

  1. fast-forward 검사push 명령을 받으면 먼저 원격의 최신 커밋과 내 커밋을 비교해서, 원격이 더 앞서 있으면 거부합니다.
  2. --force-with-lease 안전장치--force 옵션으로 강제 푸시를 할 때도, 내가 마지막으로 본 원격 상태를 기억했다가, 그 사이 남이 바꿨으면 여전히 거부하는 방식으로 추가 보호를 합니다.
  3. 푸시 성공fast-forward 조건을 만족하면 내 커밋이 원격에 기록되고, 다른 사람의 fetch/pull이 내 커밋을 받게 됩니다.

5본질 요약

push 시에 fast-forward 규칙으로 기본 보호를 하고, 필요한 경우 --force-with-lease로 더 세심한 제어를 하여 협업 중 실수로 타인의 작업을 지우는 것을 방지하는 것

5원격 저장소와 함께 일하기05-05

전송 프로토콜: local·ssh·git·http(s)

Git 은 같은 디스크의 경로(local), SSH, git 데몬, HTTP(S) 네 가지 방식으로 저장소 주소를 표현하고 데이터를 주고받는다.

1상대의 출발점 확인

원격 저장소는 로컬 디스크, 다른 서버, 클라우드 등 여러 곳에 위치할 수 있는데, 각 위치에 맞는 접근 방식이 달라야 합니다. 같은 네트워크를 쓰는 사람들도, 인터넷을 통해 접근하는 사람들도 있기 때문에, 위치와 접근 방식에 맞는 주소 형식과 통신 규칙이 필요했습니다.

2질문 제기

로컬 경로, SSH, 회사 네트워크, 인터넷을 통해 다양하게 위치한 저장소에 모두 접근하려면 어떻게 표현하고 통신해야 할까요?

3구조적 핵심 예시

Git은 각 상황에 맞는 네 가지 주소 형식을 지원합니다. 같은 컴퓨터의 경로(/home/repo 또는 file:///home/repo), SSH 서버(git@github.com:user/repo.git), 전용 git 데몬(git://server/repo), HTTP(S) 웹 프로토콜(https://github.com/user/repo.git) 각각이 다른 프로토콜을 통해 데이터를 주고받습니다.

4단계별 동작 과정

  1. 주소 해석Git 클라이언트가 주소를 보고 어느 프로토콜을 써야 할지 결정합니다 (SSH 형식이면 SSH 포트 22 사용, http(s)면 포트 80/443 사용 등).
  2. 인증 및 연결각 프로토콜에 맞게 서버에 연결하고 필요한 자격 증명을 전송합니다 (SSH는 공개키 기반, HTTPS는 토큰이나 비밀번호 기반).
  3. 데이터 전송연결이 확립되면, 동일한 Git pack format으로 커밋·객체를 주고받습니다.

5본질 요약

로컬, SSH, git 데몬, HTTP(S) 네 가지 프로토콜을 지원해서, 저장소의 위치와 접근 환경에 상관없이 유연하게 연결할 수 있게 하는 것

인증과 자격 증명 저장

HTTPS 로 원격에 접근할 때 매번 아이디·토큰을 입력하지 않도록, Git 의 credential helper 가 자격 증명을 캐시하거나 OS 저장소에 보관해 준다.

→ 05-05 참조

1상대의 출발점 확인

기존에는 HTTPS로 원격에 접근할 때마다 아이디, 비밀번호, 또는 토큰을 입력해야 했습니다. fetch, pull, push를 할 때마다 매번 입력하는 것은 번거롭고, 같은 정보를 반복 입력하는 것은 보안 위험도 있었습니다.

2질문 제기

매번 자격 증명을 입력하지 않으면서도, 저장된 정보를 안전하게 관리하려면 어떻게 해야 할까요?

3구조적 핵심 예시

Git의 credential helper는 처음 입력한 아이디·토큰을 메모리에 캐시했다가 이후 동일 호스트로의 요청에 자동으로 써줍니다. 더 안전하게 하려면 OS의 암호 관리자(Windows Credential Manager, macOS Keychain, Linux pass 등)에 저장하는 방식도 선택할 수 있습니다.

4단계별 동작 과정

  1. 첫 번째 인증HTTPS로 접근할 때 처음에만 자격 증명을 입력합니다.
  2. Credential Helper 저장입력한 정보를 Git의 설정된 저장 방식에 따라 보관합니다 (캐시, OS 저장소 등).
  3. 이후 자동 사용같은 호스트로의 다음 접근부터는 저장된 자격 증명을 자동으로 사용하므로, 재입력이 필요 없습니다.

5본질 요약

1상대의 출발점 확인

매우 오래된 Git 저장소(예: Linux 커널, 대형 회사의 모노레포)는 역사가 수십 년이고, 파일도 매우 많습니다. 전체 역사와 전체 파일을 모두 클론하면 저장 공간이 수십 GB에 달할 수 있고, 첫 클론도 수 시간이 걸립니다. 하지만 대부분의 개발자는 최근 코드와 자신의 프로젝트 부분만 필요합니다.

2질문 제기

거대한 저장소를 다룰 때, 필요한 부분만 받아서 공간과 시간을 절약하려면 어떻게 해야 할까요?

3구조적 핵심 예시

  2. 부분 클론 (lazy loading)모든 파일의 내용을 처음부터 받지 않고, 실제로 파일을 열거나 명령을 내릴 때만 그때그때 서버에서 가져옵니다.
  3. sparse-checkout 적용로컬 작업 디렉터리에 프로젝트의 일부 경로(예: src/, docs/)만 펼쳐서, 불필요한 파일들의 디스크 점유를 피합니다.

5본질 요약

커밋 옮기기와 되돌리기: cherry-pick과 revert 심화

cherry-pick은 다른 브랜치의 특정 커밋만 골라 지금 브랜치에 복사하고, revert는 기존 커밋을 취소하는 새 커밋을 만들어 히스토리를 지우지 않고 되돌린다.

1상대의 출발점 확인

한 브랜치에서 만든 특정 기능이 다른 브랜치에도 필요할 때, 그 브랜치 전체를 merge하면 원하지 않는 커밋까지 들어옵니다. 또한 이미 푸시한 공개 커밋을 취소하려면 그냥 지울 수 없고, 취소 기록을 남겨 두어야 합니다.

2질문 제기

특정 커밋만 골라 가져가거나, 커밋을 지웠다는 사실을 기록하면서 히스토리는 유지할 수 있을까요?

3구조적 핵심 예시

cherry-pick은 한 커밋의 변경 사항만 추출해 현재 브랜치에 새 커밋으로 만듭니다. revert는 특정 커밋의 반대 변경을 담은 새 커밋을 만들어, 그 커밋의 효과를 취소하면서도 히스토리에는 취소 기록을 남깁니다.

4단계별 동작 과정

  1. cherry-pick커밋 선택 및 변경 추출** — 다른 브랜치의 커밋 해시를 지정하면, 그 커밋이 만든 변경(diff)을 읽어 현재 HEAD 위에 적용합니다.
  2. revert반대 변경 생성** — 취소 대상 커밋의 변경을 정반대로 뒤집은 새 커밋을 만들어, 파일 상태는 그 커밋 이전으로 돌아가면서도 커밋 기록은 남깁니다.
  3. 충돌 처리두 작업 모두 대상 코드에 다른 변경이 있으면 충돌이 생기므로 직접 해결해야 합니다.

3구조적 핵심 예시

filter-repo(또는 구 filter-branch)는 저장소 전체를 순회하면서 각 커밋의 내용·트리·메타데이터를 검사하고 지정한 규칙대로 바꿉니다. 예를 들어 "모든 커밋에서 .env 파일 제거"라는 규칙을 주면, 처음부터 끝까지 모든 커밋이 재작성됩니다.

1상대의 출발점 확인

두 브랜치를 통합하는 방법은 merge와 rebase 두 가지입니다. merge는 양쪽의 변경을 다 기록하고, rebase는 한쪽을 다른 쪽 위로 옮깁니다. 어느 것을 쓸지에 따라 최종 히스토리의 모습이 크게 달라집니다.

2질문 제기

3구조적 핵심 예시

merge는 두 브랜치의 최신 커밋을 부모로 갖는 병합 커밋을 만들어 양쪽 흐름을 모두 기록하고, rebase는 내 커밋들을 다른 브랜치 위에 다시 적용해 한 줄로 정렬합니다. merge는 사실에 충실하고, rebase는 읽기 쉬운 히스토리를 만듭니다.

4단계별 동작 과정

  1. merge 선택 시브랜치의 분기점과 통합 시점이 모두 히스토리에 남아, 어떤 작업이 언제 병합되었는지 명확합니다. 공개된 커밋은 반드시 merge를 씁니다.
  2. rebase 선택 시내 로컬 커밋들을 기준 브랜치 위에 다시 쓰므로, 히스토리가 한 줄이 되어 읽기 쉽습니다. 하지만 이미 푸시한 커밋은 절대 rebase하지 않습니다.
  3. 원칙공유 커밋은 rebase 금지** — 다른 사람이 가져가거나 기반해서 작업한 커밋을 rebase하면, 그들의 히스토리가 깨집니다.

코드와 이력 검색: grep과 pickaxe

작업 트리의 문자열은 git grep 으로, 그 문자열이 추가·삭제된 커밋은 log -S/-G(pickaxe)로 찾는다.

문자열을 찾을 때 보통 grep으로 현재 코드에서만 검색한다. 그런데 과거에 존재했던 문자열이나 특정 커밋에서만 있던 코드를 찾으려면 모든 커밋을 일일이 확인해야 한다.

2질문 제기

특정 문자열이 어느 브랜치에 있는지, 또는 그 문자열을 추가하거나 삭제한 커밋이 정확히 어느 것인지를 빠르게 찾으려면?

3구조적 핵심 예시

git grep은 특정 커밋 또는 브랜치의 코드에서만 패턴을 검색한다. 예를 들어, git grep "function_name" main~10..main이라고 하면, main 브랜치의 과거 10개 커밋 범위에서만 해당 함수를 찾는다. pickaxe(log -S/-G)는 그 반대로, 특정 문자열을 추가하거나 삭제한 커밋 자체를 찾는다.

4단계별 동작 과정

  1. 코드 내 패턴 검색git grep은 지정한 커밋이나 브랜치의 실제 코드에서 패턴을 매칭한다.
  2. 변화 이력 검색log -S/-G(pickaxe)는 커밋 로그를 순회하면서 그 문자열이 추가되거나 삭제된 커밋을 찾는다.
  3. 검색 결과 반환grep은 매칭한 줄들을, pickaxe는 해당 커밋들을 나열한다.

bisect로 회귀 커밋 찾기

정상 커밋과 고장난 커밋 사이를 이진 탐색해 버그를 처음 만든 커밋을 자동으로 찾아내는 기능.

1상대의 출발점 확인

버그가 발생했을 때 그 원인을 찾으려면 어느 커밋에서부터 버그가 생겼는지 파악해야 한다. 커밋이 많으면 하나하나 확인하기에는 시간이 너무 오래 걸린다.

3구조적 핵심 예시

bisect는 이진 탐색 알고리즘을 사용한다. 정상 커밋과 고장난 커밋의 정확한 범위를 입력하면, 그 사이의 중간 커밋으로 자동 이동한 후 테스트 결과(정상/고장)를 입력받는다. 그 결과에 따라 범위를 반으로 줄인 후 다시 반복하는 방식으로, 10개 커밋이면 4번, 100개면 7번 정도만 테스트하면 원인 커밋을 찾을 수 있다.

4단계별 동작 과정

  1. 범위 설정정상 커밋과 고장난 커밋을 지정한다.
  2. 이진 탐색 반복범위 중간의 커밋으로 이동해 테스트 후, 고장/정상 결과를 입력받는다. 그 결과에 따라 탐색 범위를 반으로 줄인다.
  3. 원인 커밋 도출범위가 1개 커밋으로 좁혀지면, 그것이 버그를 처음 만든 커밋이다.

diff 심화: 알고리즘·이름변경·range-diff

diff 알고리즘 선택, 이름변경 감지, 그리고 두 커밋 묶음 자체를 비교하는 range-diff 로 변경을 더 정확히 읽는 법.

1상대의 출발점 확인

일반적인 diff는 추가된 줄과 삭제된 줄로만 변경을 보여준다. 하지만 파일 이름이 바뀌면 새 파일 추가·기존 파일 삭제로 오인하고, 두 커밋 묶음(branch) 자체를 비교할 때는 각 커밋 간 변경을 따로따로 봐야 한다.

2질문 제기

코드 변경을 더 정확하게 읽기 위해 diff 알고리즘을 조정하거나, 이름 변경을 감지하거나, 복수의 커밋을 한눈에 비교하려면?

3구조적 핵심 예시

diff 알고리즘은 여러 종류가 있다. 기본값은 기존 알고리즘(myers)이고, patience는 구조가 뚜렷한 코드에서 더 읽기 좋다. 이름변경 감지(-M 옵션)를 켜면, 파일 삭제 후 유사한 내용의 파일 생성이 감지되면 이름 변경으로 표시한다. range-diff는 두 커밋 묶음(A1~A5 vs B1~B5)을 비교할 때, 각 커밋 간 변경을 순서대로 보여준다.

4단계별 동작 과정

  1. diff 알고리즘 적용지정한 알고리즘으로 두 버전의 차이를 계산한다.
  2. 이름변경·유사도 감지-M 옵션을 사용하면 삭제와 추가 조합에서 이름 변경을 인식한다.
  3. 결과 표시알고리즘과 옵션에 따라 변경을 다르게 표현한다. range-diff는 커밋 묶음 간 구조를 보여준다.

  2. 변경 적용diff를 작업 트리에 입힌다(apply는 여기서 종료).
  3. 커밋 생성am은 추가로 메일 헤더의 작성자·날짜 정보와 커밋 메시지를 사용해 새 커밋을 만든다.

1상대의 출발점 확인

기존 방식에서는 .gitignore로 추적할 파일을 정하지만, 이미 추적 중인 파일의 처리 방식(텍스트/바이너리, 줄바꿈 표준)은 단순히 OS 기본값을 따릅니다. Windows(CRLF)와 Unix/Mac(LF) 개발자가 섞여 있으면 같은 파일을 수정할 때마다 모든 줄이 변경된 것으로 나타나 diff가 지저분해지고, 바이너리 파일을 텍스트로 처리하면 손상됩니다.

2질문 제기

파일 경로 패턴마다 Git이 어떻게 다루어야 할지(텍스트인지, 줄바꿈을 어떻게 정규화할지)를 미리 정할 수 있을까?

3구조적 핵심 예시

.gitattributes 파일에 *.txt text eol=lf, *.bin binary 같이 쓰면, Git은 커밋할 때 .txt는 줄바꿈을 CRLF에서 LF로 통일하고, .bin은 바이너리 파일로 취급해 내용을 건드리지 않습니다.

4단계별 동작 과정

  1. 속성 매칭Git이 파일을 add/commit/checkout할 때, .gitattributes 파일의 경로 패턴(와일드카드 포함)과 비교해 매칭되는 속성을 찾습니다.
  2. 줄바꿈 정규화text 속성이 붙으면 커밋 시(add 단계에서, clean이라 부름) 줄바꿈을 LF로 통일하고, checkout 시 운영체제 기본값(Windows는 CRLF)으로 변환합니다. binary 속성이면 어떤 변환도 하지 않습니다.
  3. 저장소 상태 유지이 규칙을 모든 개발자가 같은 .gitattributes로 따르면, 실제 파일 내용은 PC마다 다르지만 저장소 안에는 통일된 줄바꿈으로만 저장됩니다.

  1. worktree 생성git worktree add <경로> <브랜치명> 명령으로 새로운 작업 디렉터리를 만들고 지정한 브랜치를 그곳에 체크아웃한다.
  2. 동시 작업각 worktree는 독립적인 작업 디렉터리이지만 같은 저장소의 .git을 공유하므로, 한 worktree에서 커밋하면 다른 worktree에서도 그 커밋이 보인다.
  3. 정리작업을 마친 worktree는 git worktree remove <경로>로 삭제할 수 있다.

저장소 내보내기: archive와 bundle

특정 시점의 파일들을 tar/zip으로 뽑아내거나(archive), 저장소 히스토리를 파일 하나로 담아 오프라인 전송(bundle)하는 방법.

1상대의 출발점 확인

프로젝트의 특정 시점 파일들을 배포하거나 백업하려면, 전체 .git 디렉터리와 함께 저장소를 복사해야 했다. 또한 네트워크가 끊긴 환경에서는 저장소의 히스토리를 전달할 방법이 없었다.

2질문 제기

특정 커밋 시점의 파일들만 tar나 zip으로 뽑아내거나, 히스토리 전체를 파일 하나로 담아 오프라인 전송할 수는 없을까?

3구조적 핵심 예시

git archive HEAD --format=tar | gzip > backup.tar.gz를 실행하면 현재 HEAD 커밋의 모든 파일이 압축 파일로 만들어진다. 반면 git bundle create repo.bundle --all을 실행하면 저장소의 모든 커밋과 브랜치 정보가 하나의 파일에 담겨 이메일로도 전송할 수 있다.

4단계별 동작 과정

  1. archive로 스냅샷 생성git archive는 특정 커밋(보통 HEAD)의 모든 파일을 뽑아내 tar, zip, tgz 같은 압축 형식으로 만든다. Git 히스토리는 포함되지 않는다.
  2. bundle로 히스토리 전송git bundle은 특정 커밋 범위(또는 모든 브랜치)의 모든 객체와 참조를 하나의 파일로 압축한다.
  3. bundle 받기와 복구받은 쪽에서 git clone repo.bundle 또는 git fetch repo.bundle 같은 명령으로 히스토리를 복구할 수 있다.

5본질 요약

  2. 프로토콜 선택 및 공개git daemon(Git 프로토콜, 빠르고 단순), HTTPS(안전하고 방화벽 통과), SSH(인증 필수)를 선택해서 팀원들이 접근할 수 있게 허용한다.
  3. 클라이언트 연결팀원들이 주어진 URL로 clone/push/fetch를 실행해서 중앙 저장소와 동기화한다.

  2. 풀리퀘스트 생성변경을 원본 저장소로 신청하며, 어떤 기능을 추가했는지, 테스트 결과는 무엇인지 설명을 함께 제시한다.
  3. 유지보수자의 검토 및 통합코드 리뷰로 품질을 확인하고, 필요시 수정을 요청한 후 merge로 반영한다.

기존에는 Subversion 같은 다른 버전관리 도구에서 작업 중이었는데, Git으로 전환하려고 해도 10년 이상의 이력을 버려야 했다. 이전 커밋들을 수동으로 옮기려면 엄청난 시간이 걸렸고, 그 과정에서 이력이 손실되기도 했다. 다른 도구와 함께 사용할 수는 더더욱 없었다.

기존 버전관리 시스템의 모든 이력을 Git으로 어떻게 옮기거나 함께 사용할 수 있을까?

4단계별 동작 과정

  1. 변환 도구 선택git-svn(Subversion용), 또는 다른 버전관리 도구에 맞는 변환기를 선택한다.
  2. 이력 복사원본 저장소의 모든 커밋, 브랜치, 태그를 Git 저장소로 옮긴다. 커밋 메시지와 작가 정보도 함께 보존된다.
  3. 연동 또는 전환필요시 git remote로 양쪽 저장소를 연결해서 동시 운영하거나, 완전히 Git으로 전환한다.

5본질 요약

다른 버전관리 도구나 외부 저장소의 이력을 손실 없이 보존하면서 Git으로 마이그레이션하거나 동시에 운영할 수 있게 하는 상호운영 기능
