데이터를 표 형태로 저장하고 SQL 질의로 다루는 관계형 데이터베이스 관리 시스템으로, 서버·클라이언트 구조로 동작하며 여러 사람이 동시에 같은 데이터에 접근할 수 있게 해 주는 소프트웨어다.

#1문제 상황

온라인 쇼핑몰 주문을 어디에 적어 둬야 할지 정해야 한다. 파일에 저장하면 동시 구매가 겹칠 때 값이 깨지고, 조건 검색도 직접 코드로 짜야 한다.

MySQL은 데이터를 표 형태로 저장하고 SQL 문으로 다루는 관계형 데이터베이스 관리 시스템이다. 서버와 클라이언트 구조로 동작하며 여러 사람이 동시에 같은 데이터에 접근할 수 있다(→ 01-02).

MySQL Data Dictionary는 그 정보를 한곳에 모은 저장소다. 이 서버는 transactional data dictionary를 내장해 객체 정보를 트랜잭션으로 다룬다(→ 02-02).

  3. 캐시에 담아 둔다Dictionary Object Cache는 자주 쓰는 사전 항목을 메모리에 올려 같은 확인을 반복하지 않는다.

2. 서버 안쪽을 들여다보다02-02

사전 데이터는 트랜잭션으로 저장된다

사전의 정보도 일반 테이블 데이터처럼 커밋과 롤백이 적용되며, 변경 기록은 InnoDB 의 언두 로그에 보관되므로 롤백하면 사전 내용도 함께 되돌아간다.

먼저 알아야 할 것 02-01

#1문제 상황

사전 정보(→ 02-01)를 평범한 파일로 따로 저장하면 DDL 이 중간에 실패했을 때 파일과 실제 구조가 어긋난다. 서버를 켤 때마다 구조를 다시 뒤져 맞춰야 한다.

Transactional Storage of Dictionary Data 는 사전 데이터를 트랜잭션 InnoDB 테이블에 넣어 이 어긋남을 없앤다. mysql 데이터베이스의 mysql.ibd 테이블스페이스 하나에 모여 일반 데이터와 같은 커밋·롤백 규칙을 따른다.

#2핵심 질문

사전 정보도 트랜잭션으로 저장하면 무엇이 달라지는가?

#3동작 예시

ALTER TABLE 로 열을 하나 추가하는 도중 서버가 죽는다. 다시 켜면 이 ALTER 는 롤백된 상태로 복구된다. 사전 파일을 직접 뒤집던 구조라면 파일과 실제 테이블 구조가 서로 다를 수 있었다.

#4동작 과정

  1. 사전 테이블을 만든다사전 정보와 일반 시스템 테이블이 mysql 데이터베이스에 InnoDB 테이블로 함께 놓인다. 이 표들을 담는 mysql.ibd 테이블스페이스 파일은 MySQL 데이터 디렉터리 안에 있어야 하고 이름을 바꿀 수 없다.

  3. 보호한다사전 데이터는 서버 쓰기(→ 02-04)가 계측하는 대상에 함께 올라간다. 성능이 궁금하면 Performance Schema(→ 02-04)로 어느 연산이 시간을 먹는지 본다.

InnoDB 소개와 기본 이점

먼저 알아야 할 것 01-01

#1문제 상황

엔진을 고르지 않으면 MyISAM 처럼 트랜잭션도 롤백도 없는 동작이 기본이 되고, 중간에 죽으면 데이터가 깨질 수 있다. 데이터 신뢰성을 기본값으로 깔고 싶어도 엔진 설정을 매번 붙여 줘야 했다.

The InnoDB Storage Engine 는 범용 저장 엔진으로 MySQL 8.4 의 기본 저장 엔진이다. Benefits of Using InnoDB Tables 가 나열한 트랜잭션과 행 수준 잠금, 외래 키 기능이 별도 설정 없이 따라 온다.

#2핵심 질문

왜 MySQL 은 InnoDB 를 기본 엔진으로 삼았는가?

#3동작 예시

ENGINE=InnoDB 를 생략하고 CREATE TABLE 을 실행한다. 만든 테이블의 엔진이 InnoDB 로 표시된다. 별도 설정 없이 트랜잭션 안에서 여러 문장을 묶을 수 있다.

#4동작 과정

  1. 기본 엔진으로 만든다Introduction to InnoDB 기준으로 기본 저장 엔진이 InnoDB 이다. ENGINE 절을 생략한 CREATE TABLE 은 InnoDB 테이블이 된다.
  2. 지침대로 다듬는다Best Practices for InnoDB Tables 지침에 따라 데이터 페이지 크기와 버퍼 풀 크기를 실제 작업에 맞춘다.
  3. 검증한다Verifying that InnoDB is the Default Storage Engine 항목으로 서버 설정의 기본 엔진이 InnoDB 인지 확인한다. Testing and Benchmarking with InnoDB 로 실제 데이터에서 시험해 보기도 한다.
  4. 확인해 볼 것INFORMATION_SCHEMA.TABLES(→ 02-03)의 ENGINE 값을 조회해 테이블이 InnoDB 인지 확인한다.

ACID 모델

모든 트랜잭션이 원자성(전부 또는 전무), 일관성(정해진 규칙 유지), 격리성(중간 결과 비노출), 지속성(커밋 후 영구 보존) 네 속성을 지켜야 하는 이유를 다룬다.

먼저 알아야 할 것 03-01

→ 03-01 참조

#1문제 상황

프로세스가 죽거나 하드웨어가 오작동하면 여러 문장을 걸친 변경이 중간에 남을 수 있다. 그러면 데이터가 깨지고 읽은 결과가 틀린다.

ACID 는 이런 상황에서 데이터가 상하지 않고 결과가 왜곡되지 않게 정한 네 속성의 묶음이다. InnoDB and the ACID Model 에서 설명하듯 MySQL 의 InnoDB(→ 03-01) 엔진이 이 모델에 충실하게 동작한다.

#2핵심 질문

예상 못한 장애가 나도 데이터와 결과를 지키려면 어떤 조건이 필요한가?

#3동작 예시

이체 처리에서 계좌 차감 문장까지 성공하고 입금 문장이 죽었다. atomicity 때문에 입금까지 처리된 상태로 남거나, 둘 다 되돌아간다. 중간 잔액이 남는 일은 없다. durability 때문에 커밋된 것은 서버가 죽어도 지워지지 않는다.

#4동작 과정

  1. 원자성을 지킨다atomicity 는 모두 실행되거나 전혀 실행되지 않아야 한다. 커밋 전 실패한 변경은 전부 지워진다.
  2. 일관성을 지킨다관련 규칙(예: 잔액 합)이 커밋 전후로 유지되어야 한다. 오류 난 변경은 커밋되지 않는다.
  3. 격리성을 지킨다동시 실행 중인 다른 트랜잭션이 중간 결과를 보지 못하게 한다. 지속성을 지킨다는 것은 durability 가 커밋이 끝났다면 서버가 죽어도 그 결과를 남긴다는 뜻이다.
  4. 확인해 볼 것트랜잭션 중 일부 문장 뒤에 오류를 내고 롤백했을 때 첫 문장의 변경까지 남아 있는지 확인한다.

다중 버전 동시성 제어

데이터를 덮어쓰지 않고 이전 버전을 undo 로그에 남겨 읽는 요청은 자신이 시작한 시점의 값을 보고 쓰는 요청은 최신 버전에 반영하게 하는, InnoDB의 동시성 제어 방식을 설명한다.

먼저 알아야 할 것 03-02

→ 03-02 참조

#1문제 상황

한 트랜잭션이 읽은 행을 다른 트랜잭션이 고쳐 버리면, 읽던 쪽은 근거 없는 값을 본다. 그래서 InnoDB는 InnoDB Multi-Versioning, 즉 multi-versioning 방식을 쓴다. ACID 속질이 요구하는 락 없는 읽기가 가능해진다(→ 03-02).

#2핵심 질문

읽는 중에도 다른 트랜잭션이 값을 고칠 때, 읽는 쪽은 어떻게 자기 시점의 값을 유지하는가?

#3동작 예시

주문 목록을 조회 중인 화면에서 다른 사람이 같은 주문의 상태를 결제 완료로 바꾼다. 조회 중인 트랜잭션은 아직 커밋하지 않은 자기 시점의 값을 계속 보고, 갱신은 최신 버전에만 반영된다.

#4동작 과정

  1. 변경을 기록한다고쳐진 행의 옛 값을 undo 테이블스페이스의 롤백 세그먼트에 남긴다. 같은 값이 디스크에도 남으므로 재시작 후에도 이전 버전을 만든다.

먼저 알아야 할 것 04-02

→ 04-02 참조

#1문제 상황

MySQL 은 요청 하나하나를 자동으로 끝내는 기본 상태로 돌아가 있다(→ 04-02). 그래서 INSERT 한 문과 UPDATE 한 문이 따로따로 처리되면 그 사이에 다른 요청이 끼어들어 계좌 금액이 어긋난다.

여러 문장을 하나의 묶음으로 묶는 START TRANSACTION, COMMIT, and ROLLBACK Statements가 그 구간을 하나로 붙인다. 그 안에서 다른 트랜잭션의 변경을 몇 단계로 보여 줄지는 isolation 수준으로 정한다.

#2핵심 질문

같은 데이터를 여러 사람이 고칠 때 서로의 변경을 어디까지 보게 할까?

#3동작 예시

#4동작 과정

  1. 묶음을 연다START TRANSACTION 으로 뒤따를 문장을 한 묶음으로 묶는다. ROLLBACK 은 묶음을 되돌리고 COMMIT 은 확정한다.

  3. 접근 방식을 정한다같은 문장에서 READ WRITE 또는 READ ONLY 를 지정해 쓰기 가능 여부까지 정할 수 있다. Transactional and Locking Statements가 이 조절 문장들을 묶은 이름이다.
  4. 확인해 볼 것SELECT @@transaction_isolation 으로 현재 세션의 격리 수준이 무엇으로 되어 있는지 확인한다.

잠금이 꼬여 다른 문장의 작업을 기다리게 되는 죽음과 타임아웃 같은 문제와, InnoDB가 파일을 열고 읽을 때 사용자 요청과 무관하게 스스로 거는 내부 잠금의 종류를 다룬다.

먼저 알아야 할 것 04-03

#1문제 상황

여러 명령이 같은 테이블을 동시에 다루면 잠금 경쟁이 생긴다(→ 04-02). 경합이 심해지면 명령이 서로를 기다리다 결국 시간이 지나 포기해야 한다.

Optimizing Locking Operations는 이런 문제를 줄이는 방법을 모은 장이다. 그 안에서 서버 안에서만 도는 Internal Locking Methods와, 서버 밖의 프로그램끼리 파일로 조율하는 External locking을 나눠 다룬다.

#2핵심 질문

잠금이 서로를 막아 멈출 때 어떻게 알아내고 우회할까?

#3동작 예시

화면에서 주문을 저장한다. UPDATE 문이 다른 세션이 잡은 행을 기다리다 lock wait timeout 이고, 그 세션은 종료됐다. 이어 두 세션이 같은 순서로 두 행을 잡으려 하면 어느 쪽도 끝내지 못하는 deadlock이 발생한다.

#4동작 과정

  1. 경합을 잰다Performance Schema의 계측표에서 어느 세션이 어느 잠금을 잡고 기다리는지 본다(→ 02-04).
  2. 내부 잠금을 고른다Internal Locking Methods는 서버가 표를 읽을 때 읽기 잠금과 쓰기 잠금 가운데 무엇을 걸지 정하는 방식이다. Table Locking Issues는 이 방식이 언제 경합을 키우는지를 설명한다.
  3. 바깥 잠금으로 조율한다서버 외 프로그램까지 같은 파일을 건드리면 파일 시스템 잠금인 external locking이 필요하다.
  4. 확인해 볼 것SHOW ENGINE INNODB STATUS 의 Locks 섹션에서 어느 트랜잭션이 어느 레코드를 잡고 기다리는지 확인한다.

→ 04-03 참조

#1문제 상황

ALTER TABLE 로 열을 추가하는데 그 사이에도 다른 사람이 그 테이블에서 SELECT 하고 있다. 둘을 동시에 처리하면 구조와 데이터의 어긋남이 생길 수 있다.

Metadata Locking은 이 접근을 조율한다. 대상은 표뿐 아니라 스키마, 저장 프로시저, 트리거, 테이블스페이스에도 걸린다.

#2핵심 질문

테이블 구조를 바꾸는 동안 다른 질의를 어떻게 세워 둘까?

#3동작 예시

#4동작 과정

  1. 문을 기다리게 한다구조를 요구한 첫 문장이 metadata lock을 잡는다. 뒤따르는 DDL 은 같은 구조를 고칠 수 없어 기다린다.
  2. DML 과 DDL 의 충돌을 만든다데이터만 다루는 DML 문도 구조를 확인하므로 DDL 이 붙들고 있으면 함께 멈춘다. DML and DDL contention이 이 충돌이다.
  3. 점유자를 살핀다Performance Schema의 metadata_locks 표에서 어떤 세션이 잠금을 잡았는지와 누구가 막혔는지 볼 수 있다.
  4. 확인해 볼 것metadata_locks 표를 조회해 어떤 세션이 어떤 객체의 잠금을 보유 중인지 확인한다.

먼저 알아야 할 것 04-05

→ 04-05 참조

#1문제 상황

대부분은 서버 혼자 파일을 다룬다고 본다(→ 04-06 이전 항목 기준: 04-01). 하지만 같은 데이터 디렉터리를 쓰는 서버가 둘이거나, 서버를 끄고 myisamchk 같은 점검 도구를 돌리는 경우 그 가정이 깨진다.

External Locking은 그렇게 여러 프로그램이 같은 표를 다룰 때 접근 순서를 파일 잠금으로 맞추는 방법이다. LOCK TABLES와 UNLOCK TABLES 문장으로 서버 안의 접근도 직접 묶을 수 있다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 파일 잠금에 의존한다서버가 표 파일에 잠금을 걸어 다른 프로그램의 접근을 막는다.
  2. 접근을 명시해 묶는다LOCK TABLES와 UNLOCK TABLES Statements로 한 세션이 쓸 표를 직접 지정한다. 지정하지 않은 표는 그 세션에서 열 수 없다.
  3. 백업 시점을 잠근다LOCK INSTANCE FOR BACKUP과 UNLOCK INSTANCE Statements는 백업 시작 시점의 데이터가 유지되도록 서버 전체를 묶는다.
  4. 확인해 볼 것LOCK TABLES 로 표를 묶은 뒤 묶지 않은 다른 표를 읽으려 했을 때 막히는지 확인한다.

5. SQL 언어 — 구조와 타입05-03

데이터 타입과 범위 초과 처리

각 열은 정수·실수·날짜·문자열 같은 데이터 타입이 정해져 있고, 그 타입이 담을 수 있는 범위 밖의 값을 넣으면 오류가 나거나 값이 경계값으로 잘리는데, MySQL 은 어떤 결과로 처리할지 정해진 규칙을 따른다.

먼저 알아야 할 것 05-02

#1문제 상황

열마다 담을 수 있는 값의 범위가 정해져 있는데, 범위를 벗어난 값을 넣었을 때 서버가 무엇을 할지 약속이 없다면 매번 따로 처리해야 한다.

MySQL 은 Data Types, 즉 열에 저장되는 값의 종류를 정해 주는 타입 체계와 Out-of-Range and Overflow Handling, 즉 범위를 벗어난 값을 처리하는 규칙을 함께 둔다. strict 모드라면 거절하고, 아니면 경계값으로 잘라 저장한다.

#2핵심 질문

타입이 담지 못하는 값이 들어오면 MySQL 은 무슨 결과로 처리할까?

#3동작 예시

주문 금액을 저장하는 정수 열에 허용 범위를 넘는 값을 넣는다. strict 모드에서는 삽입이 실패하고 오류 메시지가 돌아온다.

조용히 허용된 모드라면 서버가 대신 경계값을 저장하고, 이 값을 다시 읽으면 원래 넣은 값과 다른 경계값이 보인다.

#4동작 과정

  1. 값을 받는다서버는 대상 열의 타입이 허용하는 범위인지 먼저 본다. 이 판정 기준이 Optimizing MySQL Data Types 에서 다룬 타입 크기 정하기와 이어진다.
  2. 끝점을 정한다strict 모드면 SQL 표준대로 오류로 거절한다. 아니면 타입 범위의 끝값으로 잘라 그 값을 저장한다.
  3. 확인해 볼 것같은 값을 넣고 SELECT로 다시 읽었을 때 오류가 나는지, 아니면 경계값이 나오는지를 확인한다.

문자열 타입

문자열 타입은 고정 길이 CHAR, 가변 길이 VARCHAR, 가변 길이 텍스트를 쌓아 두는 TEXT 계열, 이진 데이터를 담는 BINARY·VARBINARY·BLOB 로 나뉘며, 각자 저장 방식과 최대 길이가 다르다.

먼저 알아야 할 것 05-03

#1문제 상황

문자열은 길이가 제각각인데, 저장 공간과 비교 방식을 하나로 정할 수는 없다. 정해진 길이만 들어오는 값과 길이가 자꾸 바뀌는 값을 같은 방식으로 다룰 수는 없다.

MySQL 의 String Data Types 는 CHAR, VARCHAR, BINARY, VARBINARY, BLOB, TEXT, ENUM, SET으로 나뉜다. String Data Type Syntax 는 각 타입 이름 뒤에 길이를 쓰는 표기 방법을 정해 준다.

#2핵심 질문

문자열을 저장할 때 고정 길이와 가변 길이 중 무엇을 골라야 할까?

#3동작 예시

사용자 로그인 아이디를 저장하는 열은 자릿수가 고정이 아니라 VARCHAR 로 둔다. 대신 국가 코드처럼 두 자리만 오는 열은 CHAR 로 정한다.

주문 메모처럼 길이가 수천 자까지 갈 수 있는 값은 TEXT 계열로 옮기고, 이미지 바이트는 BINARY 나 BLOB 로 넣는다.

#4동작 과정

  1. 길이 성격을 정한다항상 같은 길이면 CHAR, 길이가 달라지면 VARCHAR 를 고른다. 두 타입 모두 바이트 단위 길이를 함께 적는다.
  2. 범위를 정한다VARCHAR 가 넘을 수 없는 최대 길이만큼 손실 없이 담고 싶으면 TEXT 계열로 바꿔 둔다.
  3. 저장 형태를 정한다사람이 읽는 글자가 아니라 바이트 덩어리면 BINARY, VARBINARY, BLOB 쪽을 고르고, 허용된 값의 목록만 쓸 거면 ENUM 이나 SET 을 쓴다.
  4. 확인해 볼 것정한 타입으로 만든 열에 값을 넣고 SELECT 로 읽었을 때 공백이나 잘림 없이 그대로 나오는지 확인한다.

#4동작 과정

문자 집합과 정렬 규칙 일반

문자 집합은 텍스트를 어떤 바이트 값으로 저장할지 정하는 규칙이고 정렬 규 collation은 그 텍스트를 사전순으로 어떻게 비교하고 정렬할지를 정하는 규칙입니다.

먼저 알아야 할 것 05-04

#1문제 상황

문자는 사람이 읽는 기호이고 저장되는 것은 숫자 바이트다. 어떤 기호를 몇 번으로 저장하고 그 번호를 어떻게 비교할지가 정해지지 않으면 정렬 결과가 제멋대로 달라진다.

Character Sets and Collations in General, 즉 문자 집합과 정렬 규칙의 관계는 이 둘을 분리해 정의한다. MySQL 에서는 Character Sets and Collations in MySQL 규칙으로 서버가 이를 관리한다.

#2핵심 질문

문자를 어떤 바이트로 저장하고 그 바이트를 어떤 기준으로 비교할까?

#3동작 예시

네 글자로 된 가상의 문자 집합에서 A는 0, B는 1, a는 2, b는 3으로 번호를 붙인다. 이 번호들의 전체가 문자 집합이다.

두 문자열을 비교할 때 번호만 비교하면 A가 B보다 앞선다. 이 규칙이 binary collation 이고, 대소문자를 무시하려면 다른 정렬 규칙을 고른다.

#4동작 과정

  1. 기호에 번호를 붙인다Character Set Repertoire, 즉 한 문자 집합이 담는 기호 전체의 목록을 정하고 각 기호에 저장용 번호를 부여한다.
  2. 비교 규칙을 정한다정렬 규칙은 그 번호를 어떤 순서로 볼지 결정한다. 대소문자 구분 여부와 억양 처리 여부가 여기서 갈린다.
  3. 함께 고른다MySQL 은 문자 집합마다 사용할 수 있는 정렬 규칙 목록을 정해 두고, 서버 설정과 열 정의에서 그 둘을 짝지어 지정한다.
  4. 확인해 볼 것한 열에 대소문자가 섞인 값을 넣고 ORDER BY 로 정렬해, 대소문자 구분 정렬 규칙과 비구분 정렬 규칙에서 순서가 어떻게 달라지는지 본다.

두 피연산자의 collation이 다를 때 MySQL은 어느 정렬 규칙을 골라 비교하는가?

#3동작 예시

한 열의 collation은 utf8mb4_general_ci인데 연결 문자 집합 쪽 정렬 규칙은 달라서(→ 06-03) 조건절을 실행하면 Illegal mix of collations 오류가 난다. 열 쪽에 COLLATE를 붙여 규칙을 지정하면 오류 없이 결과 행이 나온다.

#4동작 과정

  1. 충돌을 찾는다Collation Issues는 비교에 쓰인 값들의 collation이 서로 다를 때 MySQL이 내는 오류 상황이다. 서버는 두 값의 우선순위를 비교해 답을 정한다.
  2. 우선순위를 정한다이 순서를 Collation Coercibility in Expressions, 식 안에서 각 값이 얼마나 강한 정렬 규칙을 요구하는지를 나타내는 숫자 체계로 표현한다. 숫자가 작은 쪽이 이긴다.
  3. 명시해서 덮어쓴다COLLATE를 쓰면 그 자리에서 쓸 정렬 규칙을 직접 정해 준다. Collation Coercibility가 자동으로 정하는 답을 덮어쓴다.
  4. 확인해 볼 것오류가 난 문장에 COLLATE를 붙여 다시 실행해 결과가 나오는지 확인한다.

utf8mb4는 유니코드 전체 영역을 표현해 4바이트 문자와 이모지까지 저장할 수 있는 MySQL의 기본 문자 집합으로, 예전 utf8mb3는 3바이트까지만 담았습니다.

#1문제 상황

한글은 BMP 안에 있어 3바이트 문자로 저장된다. 그 밖의 영역에 있는 보조 문자는 예전 utf8mb3로는 아예 담지 못했다. 그래서 그 문자를 넣으려 하면 열이 오류로 막힌다.

MySQL은 Unicode Support, 유니코드 문자 전체를 다룰 수 있도록 utf8mb3에서 utf8mb4로 기본을 옮겼다. 이제 어떤 문자든 저장된다.

#2핵심 질문

유니코드 전체 영역을 빠짐없이 저장하려면 어떤 문자 집합을 써야 하는가?

#3동작 예시

상품 설명 열에 이모지를 넣으려 한다. utf8mb3로 만들어진 열에서는 문자가 들어가지 않았지만, utf8mb4로 바꾸면 저장이 되고 그 값을 읽어 화면에도 그대로 보인다.

#4동작 과정

  1. 문자를 나눠 담는다The utf8mb4 Character Set, 유니코드를 최대 4바이트까지 쓰는 문자 집합이 utf8mb4다. BMP 문자와 보조 문자, 즉 3바이트를 넘는 영역을 모두 담는다. 저장된 값은 16비트 BMP 문자와 같다.
  2. 옛 문자 집합과 가른다The utf8mb3 Character Set는 BMP 문자만 다루고 문자당 최대 3바이트다. BMP 문자는 utf8mb4와 코드값·인코딩·길이가 모두 같고, 보조 문자만 utf8mb4가 추가로 담는다. utf8mb4가 더 큰 집합이다.
  3. 변환한다Converting Between 3-Byte and 4-Byte Unicode Character Sets 절차로 utf8mb3 열을 utf8mb4로 바꾼다. utf8mb3에 없던 문자는 변환 전에 넣을 대상이 아니다.
  4. 확인해 볼 것INFORMATION_SCHEMA에서 해당 열의 CHARACTER SET_NAME이 utf8mb4로 바뀌었는지 확인한다(→ 02-03).

MySQL 은 색인을 어떻게 쓰나

색인은 특정 열의 값 순서로 정렬해 둔 보조 자료 구조로, WHERE 절의 조건에 맞는 행을 표 전체를 훑지 않고 찾아낸다.

색인은 특정 열의 값을 정렬해 따로 저장해 두는 보조 자료 구조다. 색인이 있으면 데이터 파일 가운데로 바로 뛰어 들어가 조건에 맞는 행만 읽는다. MySQL 은 대개 색인을 B-Tree 로 만들고 공간 데이터 타입만 R-Tree 를 쓴다.

#2핵심 질문

#4동작 과정

  1. 정렬된 목록을 만든다지정한 열의 값을 정렬해 색인에 따로 저장한다. 데이터 타입별로 어떤 값이 몇 행에 몰려 있는지는 → 05-03 의 규칙을 따른다.
  2. 탐색을 건너뛴다색인이 있으면 데이터 파일 가운데로 바로 점프해 조건에 맞는 구간만 읽는다. 열 값이 공간 데이터 타입이면 R-Tree 라는 다른 자료 구조를 쓰고, FULLTEXT 색인은 역색인 목록으로 뒤집어 저장한다.
  3. 실행 계획을 세운다MySQL 은 이 찾기 방식을 Optimization Overview 라는 절차에서 실행 계획으로 정리한다. 실제 계획을 보는 법은 → 08-04 다.
  4. 확인해 볼 것조건에 쓰는 열에 PRIMARY KEY 나 INDEX 가 걸려 있는지 테이블 구조 화면에서 확인한다.

B-Tree 색인은 키 값이 정렬된 트리 구조다. 키가 정확히 같은 경우뿐 아니라 범위 비교와 정렬된 결과도 처리한다. Hash 색인은 해시 테이블 방식이라 같은 값인 경우만 가장 빠르게 찾는다. 어느 구조를 쓸 수 있는지는 저장 엔진이 정한다.

InnoDB 는 디스크에서 읽은 데이터와 색인을 메모리 영역인 Buffer Pool 에 보관한다(→ 03-04). 이 영역이 작으면 같은 페이지를 반복해서 디스크에서 읽어 응답이 느려진다.

InnoDB Buffer Pool Optimization은 그 영역을 어떻게 채우고 비울지 정한다. Optimizing InnoDB Configuration Variables는 이 조정을 설정 변수로 바꾸는 자리를 가리킨다.

#2핵심 질문

버퍼 풀의 크기와 구성은 어떻게 정하는가?

#3동작 예시

조회 폭이 큰 서비스를 운영하다 버퍼 풀 크기를 늘리고 여러 버퍼 풀 인스턴스로 나눈다. 이후 시스템 변수의 현재 값이 어떤지 콘솔에서 확인하고, 다시 슬owness가 늘면 그때 손본다.

#4동작 과정

  1. 크기를 정한다메모리에서 InnoDB 전체가 차지할 예산을 먼저 나누고 그 안에서 버퍼 풀이 몫을 받는다. 너무 작으면 디스크 읽기가 늘어난다.
  2. 나눠 배치한다버퍼 풀 인스턴스를 여러 개 두면 서로 다른 청크를 맡아 잠금 경쟁이 줄어든다.
  3. 읽기와 비우기를 조절한다리드 어헤드 설정으로 미리 읽을 범위를 정하고, 버퍼 풀 flushing 설정으로 언제 디스크에 내릴지 정한다. 데이터 흐름이 규칙적인 서비스는 스캔 저항 설정으로 불필요한 페이지가 밀려나는 것을 막는다.
  4. 확인해 볼 것시스템 변수에서 버퍼 풀 크기와 인스턴스 수, flushing 관련 값이 어떻게 잡혀 있는지 확인한다.

버퍼 풀 최적화디스크에서 읽은 데이터를 메모리에 얼마나 잘 남겨 반복 입출력을 줄이는 것

9. InnoDB 튜닝09-02

트랜잭션 관리 최적화

InnoDB 트랜잭션이 row lock 을 얼마나 오래 붙들고 어떤 대기로 시간을 보내는지(lock wait timeout, deadlock, isolation level, autocommit 등)를 조절해 동시 처리량과 응답 시간을 함께 챙기는 일.

먼저 알아야 할 것 04-01

#1문제 상황

데이터를 바꿀 때마다 커밋하면 커밋마다 로그를 디스크에 내보내야 한다(→ 03-06). 초당 수천 번 커밋하는 서비스에서는 그 대기 시간만으로 느려진다.

Optimizing InnoDB Transaction Management는 이(transaction management) 손익을 맞추는 방법을 다룬다. 기본값인 AUTOCOMMIT=1이 그대로 쓰이면 개별 insert마다 로그 flush가 일어난다.

#2핵심 질문

트랜잭션 기능의 안전장과 처리 속도 중 어디서 균형을 잡는가?

#3동작 예시

주문 처리기가 건별로 커밋해 느려진다. 여러 건을 START TRANSACTION으로 묶어 한 번에 COMMIT하도록 바꾸자 flush 횟수가 크게 줄고 응답 시간이 낮아진다.

#4동작 과정

  1. 커밋 단위를 정한다SET AUTOCOMMIT=0으로 둔 뒤 관련 변경을 한 트랜잭션에 모아 마지막에 COMMIT한다. 묶은 수만큼 flush가 줄어든다.
  2. 커밋 비용을 센다데이터 수정이 있었던 커밋은 InnoDB 가 로그를 디스크에 내보내야 하므로, 읽기만 하는 트랜잭션은 비용이 훨씬 낮다.
  3. 둘을 맞춰 본다커밋을 크게 묶으면 장애 시 되돌릴 범위가 커진다. 처리량과 복구 비용 가운데 어느 쪽을 택할지 정한다.
  4. 확인해 볼 것실행 중인 요청에서 autocommit 값이 0으로 바뀐 뒤 묶인 INSERT 뒤에 COMMIT이 오는지 로그에서 확인한다.

읽기 전용 트랜잭션 최적화

데이터를 고치지 않는 읽기 전용 트랜잭션이 undo log 를 만들고 innodb_read_only 같은 변수 대신 더 가벼운 경로를 쓰는 형태로, 다중 버전 동시성 제어의 부하를 줄이는 일.

먼저 알아야 할 것 09-02

#1문제 상황

데이터를 읽기만 하는 요청도 다중 버전 동시성 제어를 위해 트랜잭션 ID를 얻는다(→ 03-03). 이 ID는 읽기 전용이라는 사실만으로 없애도 되는 값이다.

Optimizing InnoDB Read-Only Transactions는 InnoDB가 read-only transactions를 어떻게 알아채고 ID를 건너뛰는지 다룬다.

#2핵심 질문

쓰지 않는 트랜잭션에 굳이 ID를 붙이는 비용을 어떻게 없애는가?

#3동작 예시

조회 화면을 띄우는 프로그램이 START TRANSACTION READ ONLY로 트랜잭션을 연다. 나중에 UPDATE를 시도하면 오류가 나고 트랜잭션은 읽기 전용 상태로 유지된다.

#4동작 과정

  1. 읽기 전용으로 시작한다START TRANSACTION READ ONLY로 트랜잭션을 연다. 트랜잭션 ID는 쓰기나 SELECT ... FOR UPDATE 같은 잠금 읽기가 있을 때만 필요하다.
  2. ID를 생략한다InnoDB 가 처음부터 ID를 만들지 않는다. 질의마다 읽기 뷰를 만들 때 뒤따르는 내부 구조가 작아져 비용이 줄어든다.
  3. 상태를 유지한다읽기 전용 상태에서 변경을 시도하면 오류가 나고 트랜잭션은 그 상태로 계속된다.
  4. 확인해 볼 것읽기 전용 세션에서 UPDATE를 실행하면 상태가 유지된다는 오류가 나는지 확인한다.

9. InnoDB 튜닝09-04

Redo 로깅 최적화

커밋된 변경을 crash recovery 에 쓸 수 있도록 남기는 redo log 와 그 버퍼의 크기, flush 방식, 체크포인트 주기를 조정해 쓰기 지연과 복구 시간을 절충하는 일.

먼저 알아야 할 것 03-06

#1문제 상황

커밋된 변경을 재시작 때 되돌리기 위해 Redo Log에 적는다(→ 03-06). 이 파일이 빨리 차면 체크포인트가 자주 돌아 버퍼 풀의 내용을 디스크에 여러 번 내보내야 한다.

Optimizing InnoDB Redo Logging은 로그 용량과 버퍼 크기를 늘릴 방향을 제시한다.

#2핵심 질문

로그를 얼마나 넉넉히 확보해야 불필요한 디스크 쓰기와 복구 시간을 줄이는가?

#3동작 예시

대량 갱신이 몰리는 시간대에 디스크 쓰기가 급격히 늘어난다. 로그 용량을 키운 뒤 같은 시간대를 다시 재현해 디스크 입출량이 줄었는지 본다.

#4동작 과정

  1. 용량을 늘린다innodb_redo_log_capacity로 전체 크기를 정한다. InnoDB 는 같은 크기의 파일 여러 개를 나두고 순환하며 쓴다.
  2. 버퍼를 늘린다Log Buffer는 아직 디스크에 못 내보낸 로그를 모았다가 내보내는 곳이다. 크기가 크면 큰 트랜잭션이 버퍼 부족으로 기다리지 않는다.
  3. 체크포인트 주기를 본다로그가 차면 체크포인트가 돌아 버퍼 풀의 수정 내용을 디스크에 쓴다. 용량을 키우면 이 횟수가 줄어든다.
  4. 확인해 볼 것innodb_redo_log_capacity 값이 얼만큼 잡혀 있는지 서버 상태 화면에서 확인한다.

9. InnoDB 튜닝09-05

일괄 데이터 적재와 디스크 입출력

LOAD DATA 나 대량 INSERT 로 많은 행을 넣을 때 인덱스 생성과 로그 flush 를 억제해 적재를 빠르게 하고, InnoDB 의 데이터·인덱스·Redo 로그 입출력을 순차 읽기로 모아 디스크 부담을 줄이는 일.

먼저 알아야 할 것 09-04

#1문제 상황

수백만 행을 넣을 때 한 행마다 인덱스를 만들고 로그를 내보내면 적재가 몇 시간씩 걸린다. Bulk Data Loading for InnoDB Tables는 이를 피하는 절차를 제시한다.

#2핵심 질문

많은 행을 한 번에 넣을 때 불필요한 색인 생성과 로그 쓰기를 어떻게 억제하는가?

#3동작 예시

운영 DB에 백천만 행을 옮긴다. 자동 커밋을 끄고 고유성 검사도 잠시 끈 뒤 한 번에 넣고, 마지막에 다시 켠다. 걸린 시간과 색인 재구성 시간이 눈에 띄게 줄고, Optimizing InnoDB Disk I/O 지침까지 적용해 디스크 부담을 더 낮춘다.

#4동작 과정

  1. 자동 커밋을 끈다SET autocommit=0으로 두고 마지막에 COMMIT한다. insert마다 일어나던 로그 flush가 한 번으로 모인다.
  2. 검사 비용을 낮춘다보조 색인에 UNIQUE 제약이 있으면 SET unique_checks=0으로 잠시 끈다. 이 조건은 Optimizing Storage Layout for InnoDB Tables가 다루는 저장 구조 배치와 함께 본다.
  3. 순차 읽기로 모은다데이터·색인·Redo 로그 입출력을 흩어진 곳이 아니라 한 흐름으로 모아 디스크가 찾기해야 하는 횟수를 줄인다.
  4. 확인해 볼 것적재 세션에서 autocommit 값이 꺼져 있다가 마지막 COMMIT에서 다시 1로 돌아가는지 확인한다.

일반 보안 문제와 지침

MySQL 서버를 다룰 때 생길 수 있는 대표적 보안 위험(파일 권한, 외부 프로그램 실행, 네트워크 노출 등)과 그것을 피하기 위해 서버 관리자가 지켜야 할 기본 지침을 설명한 장이다.

먼저 알아야 할 것 01-01

#1문제 상황

인터넷에 붙은 컴퓨터에서 MySQL을 그대로 두면 데이터가 새거나 조작될 수 있다. 위험은 MySQL 서버만의 문제가 아니라 서버가 올라간 컴퓨터 전체에 있다.

Security는 이런 위험을 다루는 영역이다. General Security Issues는 자주 겪는 실패 유형이고, Security Guidelines는 그 실패를 피하기 위한 지침이다. 지킨다는 것은 연결·질의·작업마다 권한을 따로 확인하고, 암호화된 연결을 쓰며, 설치 방법을 조심한다는 뜻이다.

#2핵심 질문

MySQL을 운영할 때 어떤 위험을 미리 막아야 하는가?

#3동작 예시

새로 설치한 서버를 방금 세팅해 공개망에 붙였다. 계정들이 인터넷에서 접근할 수 있고 암호화 연결도 꺼져 있다.

공격자가 들어와 계정 목록을 보고 그 계정으로 실제 데이터까지 읽는다.

#4동작 과정

  1. 범위를 정한다서버가 있는 컴퓨터 자체를 지킨다. 도청, 변조, 재생, 서비스 마비 같은 공격이 대상이 된다.
  2. 권한을 건다사용자가 시도하는 모든 연결과 질의에 ACL, 즉 무엇을 허용할지 적힌 목록을 적용한다. SSL 암호화 연결도 지원한다. 같은 지침은 MySQL 밖의 어플리케이션에도 그대로 적용된다.
  3. 지침을 따른다Security Guidelines에 적힌 설치와 운영 수칙을 순서대로 적용한다.
  4. 확인해 볼 것클라이언트에서 연결 상태를 보면 암호화 연결이 사용 중인지 표시되는지 확인한다.

#5한 줄 요약

General Security Issues와 Security Guidelines의 본질은 서버를 둘러싼 모든 공격을 미리 가정하고 막는 것입니다.

#1문제 상황

MySQL 서버에 연결할 때 암호를 써도 그 암호는 평문으로 흘러보내지 않는다. 하지만 나머지 정보는 모두 텍스트로 오가므로, 연결을 지켜보는 사람은 전부 읽을 수 있다(→ 10-01).

Making MySQL Secure Against Attackers는 이 노출을 막는 방법을 모은 절이다. 압축 프로토콜로 내용을 해독하기 어렵게 만들거나, MySQL 내부 SSL 지원으로 연결을 더 안전하게 만든다. 신뢰할 수 없는 네트워크에서는 SSH로 암호화된 TCP/IP 연결을 얻는 방법도 쓴다.

#2핵심 질문

서버로 오가는 내용을 중간에서 읽히지 않게 어떻게 막는가?

#3동작 예시

운영 서버와 관리 PC를 사내망으로 연결한다. 그대로 두면 질의 내용과 결과가 평문으로 지나간다.

암호화 연결로 바꾸자 중간에서 본 내용으로도 내용을 알 수 없고, 공격자가 암호를 훔쳐 재사용할 수도 없어진다.

#4동작 과정

  1. 암호를 건다연결할 때 반드시 암호를 써서 그 암호가 평문으로 오가지 않게 한다. 계정 관리 방법은 10-03에서 다룬다.
  2. 전송 방식을 바꾼다압축 프로토콜을 쓰면 내용을 해독하기 훨씬 어렵다. MySQL 내장 SSL 지원을 켜면 연결 자체를 안전하게 만든다.
  3. 설치 상태를 조인다신뢰할 수 없는 구간에는 SSH로 암호화된 TCP/IP 연결을 새로 잡고, Improve MySQL Installation Security가 정한 설치 기본 조건을 지킨다. 이 절에 든 Security-Related mysqld Options and Variables은 노출을 줄이도록 서버 설정을 조는 변수 목록이다. 암호화 연결 설정 절차는 10-04에서 다룬다.
  4. 확인해 볼 것서버 정보를 볼 때 클라이언트가 어느 전송 방식으로 붙었는지 나타나는지 확인한다.

#2핵심 질문

계정마다 무엇을 허용해 MySQL 서버에 들어오게 할까?

#3동작 예시

#4동작 과정

  2. 권한을 준다Privileges Provided by MySQL가 정한 권한 가운데 필요한 것만 GRANT로 부여한다. 여러 권한을 role 묶음으로 한 번에 주는 방법도 있다.

  4. 확인해 볼 것해당 계정으로 접속한 뒤 다른 테이블을 조회하면 권한 오류가 나는지 확인한다.

  4. 확인해 볼 것클라이언트에서 연결 정보를 보면 암호화가 사용 중인지 나타나는지 확인한다.

#1문제 상황

비밀번호를 하나씩 맞혀보며 로그인을 반복하는 시도가 들어올 수 있다. 계정을 그대로 열어 두면 그 시도가 성공할 때까지 계속된다.

Account Locking은 이런 계정을 잠갔다 푸는 기능이다. CREATE USER와 ALTER USER에 ACCOUNT LOCK, ACCOUNT UNLOCK 절을 붙여 새 계정의 초기 상태를 정하거나 기존 계정의 상태를 바꾼다.

#2핵심 질문

로그인 실패가 쌓인 계정을 어떻게 잠그고 다시 열까?

#3동작 예시

ALTER USER에 UNLOCK을 붙여 실행하면 로그인 실패 때문에 임시로 잠겼던 계정이 열린다.

#4동작 과정

  1. 초기 상태를 정한다CREATE USER에 ACCOUNT LOCK을 붙이면 새 계정이 잠긴 상태로 만들어지고, 붙이지 않으면 열린 상태로 만들어진다.
  2. 상태를 바꾼다ALTER USER에 LOCK이나 UNLOCK을 붙여 기존 계정을 잠그거나 연다. 아무 절도 없으면 이전 상태가 그대로 유지된다. 계정을 잠가도 암호는 유지되므로 다시 열면 그대로 로그인된다.
  3. 암호를 함께 지킨다validate_password 컴포넌트를 켜 두면 암호 없이 만든 계정을 만들지 못하게 하며 잠긴 계정에도 같은 규칙이 적용된다. 여기에 Security Components and Plugins의 컴포넌트를 설치해 인증 정책을 넓히고, Connection Control Plugins는 실패 횟수를 세어 계정을 잠그는 기능을 맡긴다.
  4. 확인해 볼 것잠긴 계정으로 로그인을 시도하면 어떤 메시지가 나오는지 확인한다.

11. 백업·복구와 복제11-01

백업과 복구의 유형

데이터베이스를 덮어쓰는 사고가 났을 때 원본을 되찾는 방법에는, 서버가 멈췄을 때 파일째 그대로 옮겨 두는 물리적 백업(복원 시간이 짧고 데이터가 최신 상태)과, 같은 종류의 데이터 안에서 일부만 골라 저장해 두는 논리적 백업(선택적으로 되돌릴 수 있고 파일 크기가 작음)이 있다.

먼저 알아야 할 것 10-01

#1문제 상황

테이블을 잘못 지우거나 서버 디스크가 나갔다. 원본을 어디서 가져올지 정해 둔 사람이 없다면 되살릴 수 없다.

Backup and Recovery Types는 두 갈래를 구분한다. Physical (Raw) Versus Logical Backups에서 물리적 백업은 데이터베이스 내용을 담은 디렉터리와 파일을 그대로 복사하는 것이고, 논리적 백업은 CREATE DATABASE·CREATE TABLE 문과 INSERT 문 같은 구조와 내용으로 저장하는 것이다. Backup and Recovery는 이 둘로 언제 무엇을 쓰는지 정한다.

#2핵심 질문

사고가 났을 때 파일째 복사할지, 문장으로 되돌릴지 어떻게 고르는가?

#3동작 예시

서비스 시간이 줄어 urgently 복원해야 하는 큰 데이터베이스가 있다. 변환 없이 파일을 그대로 복사한 백업을 풀면 데이터가 가장 최근 상태 그대로 돌아온다.

데이터가 적은 쪽이라면 값과 구조를 SQL 문으로 저장한 백업을 고른다. 필요한 부분만 고쳐서 다른 컴퓨터에서 다시 만들 수 있다.

#4동작 과정

  1. 물리적 백업을 든다데이터 디렉터리 전체나 일부를 그대로 복사한다. 변환 없이 파일 복사만 하므로 논리적 백업보다 빠르다. 데이터베이스가 크고 문제가 생겼을 때 빨리 복구해야 할 때 쓴다.
  2. 논리적 백업을 든다구조 문장과 내용 문장으로 나누어 저장한다. 값이나 구조를 직접 고쳐 쓰거나, 다른 기종 컴퓨터에서 다시 만드는 데 쓴다.
  3. 용도에 맞춰 고른다크고 중요한 데이터베이스에는 물리적을, manipulates해야 하는 작은 데이터에는 논리적을 고른다.
  4. 확인해 볼 것백업 파일을 열어 물리적 백업은 데이터 디렉터리 파일이 나오고 논리적 백업은 CREATE TABLE과 INSERT 문이 나오는지 확인한다.

백업 방법과 정책 세우기

어떤 데이터는 하루마다, 어떤 데이터는 일주일에, 어떤 데이터는 아예 보관하지 않는다는 식으로 빈도와 보관 기간을 정하고, 그 기준을 지키는지를 자동으로 확인하는 규칙을 백업 정책이라 하며, 서버를 멈추지 않고도 맞게 돌아가는지 이 문서가 방법을 나열한다.

먼저 알아야 할 것 11-01

#1문제 상황

Database Backup Methods는 전체 데이터를 한 시점의 사본으로 만드는 통째 백업과 그 외 방식을 나눈다. Backup Strategy Summary와 Establishing a Backup Policy는 여기에 예시 백업 전략(Example Backup and Recovery Strategy)을 얹어, 언제 무엇을 얼마나 오래 지킬지 정한다. 그러면 복구할 때 무엇을 고르면 되는지 미리 보인다.

#2핵심 질문

데이터마다 백업 주기와 보관 기간을 어떻게 정해야 사고에 대비할 수 있는가?

#3동작 예시

일요일 낮 1시에 부하가 낮을 때 전체 백업을 뜨기로 정한다. 명령 한 줄로 모든 데이터베이스의 InnoDB 테이블을 SQL 파일로 빼고 그 결과를 보관 기간이 지난 파일부터 지운다.

#4동작 과정

  1. 방법을 고른다통째 백업은 파일이나 mysqldump으로 online 상태에서도 가능하다. 이 예시는 mysqldump으로 논리 백업을 만든다.
  2. 주기를 정한다부하가 낮은 시간대에 주간 단위로 돌리게 예약한다. 여기에 이진 로그를 겹치면 마지막 백업 이후 변경까지 되돌릴 수 있다(→ 11-04).
  3. 보관한다보관 기간이 지난 백업 파일은 삭제한다. 기간을 못 정하면 복구 시 고를 수가 없다.
  4. 확인해 볼 것백업 파일이 생긴 시각과 크기를 보고 마지막 백업이 예정대로 끝났는지 확인한다.

mysqldump

테이블의 데이터 값을 CREATE TABLE과 INSERT 문장, 즉 서버가 다시 읽어 실행할 수 있는 SQL 문장으로 바꿔 텍스트 파일로 빼내는 MySQL 기본 도구로, 선택한 테이블만 내보내거나 저장소 형식(서로 의존되는 여러 테이블을 한 파일에 모으는 형식)을 쓸 수 있다.

먼저 알아야 할 것 11-02

#1문제 상황

데이터를 통째로 옮기려면 파일째 복사해야 하는데, 서버를 멈춰야 할 때가 많다.

Using mysqldump for Backups는 서버를 멈추지 않고 Dumping Data in SQL Format with mysqldump으로 내용을 빼낸다. 결과 파일에는 다시 불러들일 수 있는 문장이 들어 있어 아무 서버에나 옮길 수 있다. Reloading SQL-Format Backups는 그 문장을 다시 넣는 쪽을 설명한다.

#2핵심 질문

서버를 내리지 않고 데이터베이스를 SQL 문장 파일로 어떻게 빼낼 수 있는가?

#3동작 예시

운영 중인 서버에서 백업 서버로 옮길 데이터베이스를 골라 파일 하나로 덤프한다. 받은 파일은 다른 서버에서 그대로 실행해 같은 테이블들을 다시 만든다.

#4동작 과정

  1. 고른다내보낼 데이터베이스와 테이블을 지정한다. 전체를 뺄 수도 있다.
  2. 문장으로 뺀다테이블 구조는 CREATE TABLE로, 행은 INSERT로 뽑아 텍스트 파일에 모은다. 서버는 멈추지 않는다.
  3. 팁을 적용한다mysqldump Tips에 따라 오류를 함께 저장하고, 큰 덤프는 MySQL Shell의 병렬 덤프 도구로 압축하며 진행 상황을 볼 수 있다.
  4. 확인해 볼 것파일 앞에 CREATE TABLE 문장이 나오고 그 뒤를 이어 INSERT 문장이 이어지는지 본다.

시점 복구

가장 최근 백업 이후의 변경 내용도 이진 로그(데이터에 일어난 모든 변경을 순서대로 적어 둔 기록)에서 찾아 되감아, 백업이 끝난 어느 한 순간까지의 상태로 되돌리는 절차.

먼저 알아야 할 것 11-03

#1문제 상황

하루에 한 번 백업하면 그 사이의 변경은 사라진다. 실수로 지운 테이블이 그날 오후에 만들어졌다면 복구할 수 없다.

Point-in-Time (Incremental) Recovery는 백업 다음부터 일어난 변경까지 되돌리는 일이다. Point-in-Time Recovery Using Binary Log가 이진 로그를 재료로 삼고, Point-in-Time Recovery Using Event Positions는 로그 안의 위치로 어디까지 되돌릴지 정한다. Using Backups for Recovery는 복구의 출발점이 되는 백업을 정한다.

#2핵심 질문

백업 이후에 사라진 변경을 언제까지 되돌릴 수 있는가?

#3동작 예시

어제 오후 3시 20분쯤 실수로 한 고객의 주문이 지워졌다. 백업을 복원한 뒤 이진 로그를 재생해 그 시각 직전까지 되돌리면 지워진 주문이 돌아온다.

#4동작 과정

  1. 백업을 되돌린다통째 백업으로 서버를 백업 시점 상태로 먼저 맞춘다. 복구 출발선이다.
  2. 목표를 정한다되돌릴 시각을 고르고 이진 로그에서 거기까지의 변경만 취한다.
  3. 재생한다mysqlbinlog로 이진 로그를 사람이 읽고 실행할 수 있는 문장으로 바꿔 순서대로 실행한다(→ 11-05). 목표 지점 다음의 문장은 실행하지 않는다.
  4. 확인해 볼 것복구한 서버에서 해당 주문 행이 다시 있는지 조회한다.

11. 백업·복구와 복제11-05

이진 로그

서버가 받는 모든 데이터 변경을 파일 또는 테이블에 순서대로 남기는 기록으로, 복제와 시점 복구의 근거가 되며, 이 내용을 사람이 읽을 수 있는 문장으로 바꿔 주는 mysqlbinlog 도구가 함께 제공된다.

먼저 알아야 할 것 11-04

#1문제 상황

테이블이 지워졌다. 백업 파일만으로는 지워진 시점의 상태를 알 수 없다. 그때 무슨 일이 있었는지 남는 기록이 필요하다.

The Binary Log는 테이블 생성이나 데이터 변경을 담은 이벤트, 그리고 그 변경에 걸린 시간을 담는다. 그래서 복원 뒤 여기서 원하는 지점까지 재생할 수 있다. binary log를 켜는 서버 옵션과 시스템 변수는 Server Option, System Variable, and Status Variable Reference에 정리돼 있고, Utility for Processing Binary Log Files인 mysqlbinlog이 이를 사람이 읽을 문장으로 바꿔 준다.

#2핵심 질문

서버에서 일어난 변경을 어디에 순서대로 남겨 두고 어떻게 다시 실행할 수 있는가?

#3동작 예시

어떤 UPDATE 문장이 데이터 몇 행을 고쳤는지 이진 로그에서 찾는다. mysqlbinlog으로 그 구간을 문장 파일로 뽑아 다른 서버에 그대로 실행하면 같은 변화가 재현된다.

#4동작 과정

  1. 남긴다서버가 받는 변경을 이벤트로 적어 이진 로그 파일 또는 테이블에 순서대로 쌓는다. 데이터 안 바꾼 DELETE처럼 아무 행도 못 건 문장도 기본적으로 남는다.
  2. 읽는다mysqlbinlog이 로그를 사람이 읽고 실행할 수 있는 문장으로 바꾼다. 이 결과가 시점 복구의 재료가 된다(→ 11-04).
  3. 보낸다복제와 관계없이, 이 로그가 다른 서버로 넘길 변경 목록이 된다.
  4. 확인해 볼 것SHOW BINARY LOGS로 서버가 가진 로그 파일 목록과 크기가 보이는지 본다.

#5한 줄 요약

복제

한 서버(소스)에 들어온 변경을 다른 서버(복제본)로 그대로 전달해 두 벌의 데이터베이스를 유지하는 기능으로, 그래서 읽기를 나누거나 서버가 죽었을 때 대신 서게 할 수 있다.

먼저 알아야 할 것 11-05

#1문제 상황

하나의 서버가 죽으면 서비스가 끊긴다. 읽기 запрос까지 같은 서버에 몰리면 느려진다.

Replication은 소스 서버의 변경을 복제본 서버로 넘겨 두 벌의 데이터베이스를 유지한다. 그래서 읽기를 나누고 한 서버가 없어도 나머지가 대신 선다. 이 흐름은 소스의 이진 로그가 근거가 되며(→ 11-05), 복제본을 다루는 SQL Statements for Controlling Replica Servers, Replication Functions, 소스를 다루는 SQL Statements for Controlling Source Servers가 함께 온다.

#2핵심 질문

한 서버에 들어온 변경을 어떻게 다른 서버에 그대로 전달할 수 있는가?

#3동작 예시

운영 서버가 쓰기만 하고 읽기 요청은 별도 서버로 보낸다. 운영 서버에 새 행이 들어가면 곧 그 서버에도 같은 행이 생겨 읽기가 갈린다. 운영 서버를 끄면 읽기 서버가 대신 응답한다.

#4동작 과정

  1. 설정한다소스에서 변경을 이진 로그에 남기고 복제본에서 소스를 가리키게 한다. 위치 기반 방식과 GTID 방식이 있다.
  2. 전달한다복제본이 소스의 이진 로그를 읽어 그대로 실행한다. 중간에서 끊기면 릴레이 로그에 쌓아 두었다가 이어받는다.
  3. 확인한다복제 상태를 보는 명령으로 복제본이 소스를 따라가고 있는지 살핀다.
  4. 확인해 볼 것복제본에서 시작 명령을 실행해 소스보다 얼마나 밀렸는지 확인한다.

11. 백업·복구와 복제11-07

그룹 복제와 InnoDB Cluster

여러 MySQL 서버를 하나의 일관된 집합으로 묶어 어느 한 서버가 없어도 나머지가 계속 서비스를 제공하고 필요하면 새 서버를 자동으로 대신하며, MySQL Shell의 관리 도구와 함께 쓰면 데이터베이스를 여러 대에 자동 배치하고 한 번에 확인하고 고칠 수 있다.

먼저 알아야 할 것 11-06

#1문제 상황

복제본은 보통 한 대가 죽으면 그것만 멈추고 나머지는 그대로다. 쓰는 쪽은 어느 서버가 살아 있는지 직접 관리해야 한다.

Group Replication은 여러 서버가 서로의 상태를 확인해 같은 결정에 따라 동작하도록 묶는다. InnoDB Cluster는 여기에 MySQL Shell의 관리 도구를 얹어 데이터베이스를 여러 대에 자동 배치하고 한 번에 확인하고 고치게 한다. 같은 기술 위에 한 대씩 짝을 이루는 InnoDB ReplicaSet도 있고, 상태를 살피는 Group Replication Functions가 따라온다.

#2핵심 질문

여러 서버를 어떻게 하나의 팀처럼 움직이게 할 수 있는가?

#3동작 예시

세 대의 서버를 그룹으로 묶어 둔다. 한 대가 전원을 잃어도 나머지 두 대가 계속 처리하고, MySQL Shell에서 그룹 전체 상태를 한 번에 조회해 어느 서버를 교체할지 판단한다.

#4동작 과정

  1. 묶는다Group Replication 플러그인을 켜고 서버들을 그룹에 참여시킨다. 쓰기는 한 대가 맡는 단일 주 모드와 여러 대가 받는 다중 주 모드가 있다.
  2. 관리한다InnoDB Cluster로 데이터베이스를 여러 곳에 자동 배치하고 상태를 한 번에 본다. MySQL Shell을 쓴다.
  3. 안전을 확인한다Group Replication Functions의 상태 함수로 그룹의 일관성이 유지되는지 살핀다.
  4. 확인해 볼 것그룹 상태 조회 명령에서 각 서버의 역할과 살아 있는지 여부가 목록으로 보이는지 확인한다.

#5한 줄 요약

Group Replication과 InnoDB Cluster여러 서버를 하나처럼 움직이게 묶어 한 대가 없어도 계속 돌게 묶는 것
