1SNS의 위치와 기본 개념01-01

퍼블리셔·토픽·구독자 모델

퍼블리셔(게시자)가 메시지를 토픽에 보내면 토픽이 그 메시지를 구독자 각각에게 전달하는 발행-구독 모델의 핵심 개념.

#1문제 상황

기존에는 메시지를 보내는 쪽이 받는 쪽을 하나하나 직접 호출하는 1:1 전송이 일반적이었다. 예를 들어 주문이 생기면 주문 서비스가 이메일 발송 서비스, 로그 저장 서비스, 알림 서비스에 각각 따로 API를 호출해야 했다. 받는 쪽이 하나 추가될 때마다 보내는 쪽 코드에 호출이 하나씩 늘어났고, 보내는 쪽은 언제나 모든 수신자의 주소와 형식을 알고 있어야 했다. 수신자가 바뀌거나 빠지면 보내는 쪽 코드가 그대로 깨지는 구조라, 수신자가 늘어날수록 보내는 쪽의 수정 비용과 결합도가 함께 커지는 한계가 있었다.

#2핵심 질문

메시지를 보내는 쪽이 받는 쪽이 누구인지 전혀 몰라도, 같은 메시지를 여러 받는 쪽에 한 번에 전달할 수는 없을까?

#3동작 예시

Amazon SNS는 퍼블리셔(메시지를 보내는 쪽), 토픽(메시지를 모으는 중간 지점), 구독자(메시지를 받는 쪽) 셋으로 나뉜다. 주문 서비스가 "주문 생성됨" 메시지를 토픽 하나에 발행하면, 그 토픽을 구독하고 있는 이메일 주소, SQS 대기열, Lambda 함수가 각자 메시지를 받는다. 주문 서비스는 토픽 이름(ARN)만 알면 되고 구독자가 몇 명인지, 누구인지, 어떤 프로토콜인지 알 필요가 없다.

#4동작 과정

  1. 발행퍼블리셔가 Publish API로 토픽에 메시지를 보낸다. 퍼블리셔는 토픽의 ARN(Amazon 리소스 이름, AWS 안에서 토픽을 가리키는 고유 주소)만 지정하면 된다.
  2. 구독자 조회SNS가 토픽에 등록된 구독자 목록을 확인하고, 메시지의 복사본을 구독자마다 전달할 준비를 한다.
  3. 전달SNS가 각 구독자의 프로토콜(HTTP/HTTPS, SQS, Lambda, 이메일, SMS 등)에 맞는 형태로 메시지를 보낸다. 구독자는 자신의 환경에 맞는 방식으로 메시지를 소비한다.

SNS의 두 갈래: A2A 팬아웃과 A2P 알림

SNS는 애플리케이션 간 메시지 전달(A2A 팬아웃)과 사용자 대상 알림(A2P: SMS·모바일 푸시·이메일)이라는 두 용도로 나뉜다.

#1문제 상황

기존에는 시스템 간 메시지 전달과 사람에게 알림을 보내는 일을 각각 다른 경로로 따로 구축했다. 애플리케이션 사이의 이벤트 전달은 큐나 메시지 브로커를, 사람에게 보내는 SMS·이메일·모바일 푸시는 별도의 게이트웨이나 연동 서비스를 준비해야 했다. 두 경로를 따로 운영하면 구축 비용이 두 배가 되고, 같은 이벤트를 시스템에도 사람에게도 보내려면 메시지를 두 번 만들고 두 시스템에 각각 전송해야 하는 중복과 복잡함이 생긴다.

#2핵심 질문

시스템 사이의 메시지 전달과 사람에게 보내는 알림이라는 서로 다른 두 요구를 하나의 토픽 모델로 함께 처리할 수는 없을까?

#3동작 예시

SNS는 같은 토픽에 두 종류의 구독을 함께 둘 수 있다. Application-to-application(A2A)은 시스템 간 팬아웃으로, SQS 대기열이나 Lambda 함수 같은 애플리케이션 대상이 메시지를 받는다. Application-to-person(A2P)은 사용자 대상 알림으로, 이메일, 문자(SMS), 모바일 푸시 같은 사람이 읽는 채널이 메시지를 받는다. "주문 생성됨" 이벤트 하나를 발행하면 SQS 대기열(시스템 처리용)과 운영자 이메일(사람 확인용)이 각자 받아간다.

#4동작 과정

  1. 토픽과 구독 구성토픽을 만들고, 용도에 맞춰 A2A 구독(애플리케이션 대상)과 A2P 구독(사람 대상 채널)을 등록한다.
  2. 발행퍼블리셔가 메시지 하나를 토픽에 발행한다. 발행 시점에 구독이 A2A인지 A2P인지 구분해 보낼 필요가 없다.
  3. 갈래별 전달SNS가 구독 유형에 따라 전달 경로를 정한다. A2A 구독에는 메시지 그대로 시스템 간 전달을, A2P 구독에는 문자·이메일·푸시 알림의 형태로 변환해 사람에게 전달한다.

토픽과 구독, 메시지 흐름

토픽은 메시지가 모였다가 나가는 중간 지점이고, 구독은 전달 대상을 등록하는 것이며, 메시지는 퍼블리셔 → 토픽 → 구독자 순으로 흐른다.

#1문제 상황

직접 연결 방식에서는 메시지를 보내는 쪽이 수신자의 목록을 항상 알고 있어야 했다. 수신자가 새로 생기면 보내는 쪽에 추가 작업이 필요했고, 수신자가 제거되어도 보내는 쪽 코드에는 그 사실이 그대로 남았다. 수신자 목록의 변경이 곧바로 발신 코드의 변경으로 이어지므로, 발신자와 수신자는 언제나 서로의 존재를 알고 있어야 하는 강한 결합 상태였다.

#2핵심 질문

메시지를 받을 대상이 지금 몇 개인지, 누구인지에 상관없이 발신자는 토픽에 한 번만 보내면 되게 만들 수는 없을까?

#3동작 예시

토픽의 ARN(토픽을 가리키는 고유 주소)이 발신자와 수신자를 잇는 유일한 연결점이다. 발신자는 구독자 목록을 전혀 모른 채 토픽 ARN에 메시지를 발행한다. 수신자 쪽에서 Subscribe API로 구독만 추가하면, 그 순간부터 SNS가 새 구독자에게도 같은 메시지를 전달하기 시작한다. 구독이 늘거나 줄어도 발신자 코드는 바뀌지 않는다.

#4동작 과정

  1. 토픽 생성이름을 정해 토픽을 만들면 ARN이 부여된다. 이 ARN이 이후 모든 발행과 구독의 기준점이 된다.
  2. 구독 등록받는 쪽이 Subscribe API로 프로토콜(HTTP/HTTPS, SQS, Lambda, 이메일, SMS 등)과 엔드포인트(받을 주소나 대상)를 지정해 구독을 등록한다. 이메일·HTTPS 구독은 소유 확인 절차를 거쳐 활성 상태가 된다.
  3. 발행과 전달발신자가 토픽 ARN에 메시지를 발행하면, SNS가 토픽의 구독 목록을 순회하며 활성 구독자에게 각자의 프로토콜에 맞는 형식으로 메시지를 전달한다.

#5한 줄 요약

토픽을 중심으로 발행과 구독을 느슨하게 연결해, 구독자의 추가·제거가 발신자 코드를 전혀 바꾸지 않는 메시지 흐름을 만드는 것

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

#1문제 상황

기존 방식에서는 발행자가 각 수신자에게 서로 다른 주소와 형식으로 개별 전송을 해야 했다. 이메일로 보낼 때, 큐에 넣을 때, 함수를 호출할 때마다 전송 방법과 데이터 형식이 달라서, 발행자 쪽이 모든 수신 방식의 차이를 알고 코드로 처리해야 했다. 수신자의 종류가 늘어날수록 발행자 코드에 변환과 전송 로직이 계속 쌓이는 한계가 있었다.

#2핵심 질문

발행자가 메시지 본문을 한 번만 보내면, SNS가 그 메시지를 구독자마다 다른 형식으로 감싸 전달하게 하려면 어떻게 해야 할까?

#3동작 예시

Publish API는 TopicArn(토픽 주소)과 Message(본문)를 받아 토픽에 메시지를 넣는다. 발행자는 형식 변환을 하지 않는다. HTTP 구독자에게는 SNS가 Notification 형태의 JSON 봉투(MessageId, Timestamp, TopicArn, Message 등을 담은 JSON)로 감싸 보내고, SQS 구독자에게는 큐의 메시지로, Lambda 구독자에게는 함수의 이벤트로 각각 전달한다. 같은 본문이 구독자 종류에 따라 각자 맞는 포장으로 바뀌어 도착한다.

#4동작 과정

  1. 발행퍼블리셔가 Publish API로 토픽 ARN과 메시지 본문, 필요한 경우 제목(Subject)이나 메시지 속성을 지정해 전송한다.
  2. 구독 목록 확인SNS가 메시지를 받아 검증하고, 토픽에 등록된 구독자 목록과 각 구독의 프로토콜을 확인한다.
  3. 프로토콜별 변환·전달SNS가 각 구독 프로토콜에 맞는 형식(HTTP용 JSON 봉투, SQS 메시지, Lambda 이벤트, 이메일 본문 등)으로 변환해 각 구독자에게 전달한다.

메시지 속성

메시지 본문과 함께 보내는 키-값 메타데이터로, 구독 필터링·전달 결정·데이터 보호에 활용된다.

#1문제 상황

기존에는 메시지에 대한 부가 정보(이벤트 종류, 중요도, 발신 서비스 등)를 본문 안에 직접 넣어 구분했다. 받는 쪽은 본문을 전부 읽고 파싱(문자열을 구조로 해석하는 작업)해야 이 정보를 알 수 있었고, 분류를 위한 파싱 코드와 본문 형식이 강하게 결합되었다. 본문 형식이 바뀌면 분류 코드도 함께 바뀌어야 했고, 메시지를 받아야 할지 말아야 할지도 본문을 열어봐야만 판단할 수 있었다.

#2핵심 질문

메시지 본문을 건드리지 않고 메시지에 대한 정보를 따로 붙여, 받는 쪽이 본문을 열지 않고도 수신 여부를 결정하게 하려면 어떻게 해야 할까?

#3동작 예시

발행할 때 MessageAttributes로 키-값 메타데이터를 함께 보낼 수 있다. 예를 들어 "event_type"이라는 이름에 DataType "String", StringValue "order_created"를 붙여 발행한다. 이 속성은 본문과 분리된 별도 정보라서, 구독 필터 정책(속성값 조건을 보고 맞는 메시지만 받게 하는 규칙)이 이 값을 확인해 "event_type이 order_created인 메시지만 받겠다"처럼 본문을 열지 않고도 선별할 수 있다.

#4동작 과정

  1. 속성 지정 후 발행발행자가 Publish 호출에 메시지 속성(이름, 데이터 형식 String/Number/Binary, 값)을 함께 담아 보낸다. 속성은 메시지 하나당 최대 10개까지 지정할 수 있다.
  2. 토픽에서 속성 평가SNS가 도착한 메시지와 속성을 토픽에 전달하고, 각 구독의 필터 정책이 속성값과 일치하는지 판단한다.
  3. 선별 전달조건이 맞는 구독자에게만 메시지와 함께 속성이 전달된다. 조건에 맞지 않는 구독자에게는 메시지가 전달되지 않는다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 배치 구성보낼 메시지들을 모아 요청 하나에 담는다. 각 메시지는 고유 Id와 함께 넣고, 대상 토픽이나 메시지 속성(키-값 메타데이터)은 메시지마다 다르게 실을 수 있다.

  3. 결과 수신SNS가 메시지 Id별 성공·실패 결과를 응답으로 돌려준다. 실패한 메시지는 응답에 담긴 코드와 내용으로 원인을 확인해 다시 보낼 수 있다.

기존에는 발행하는 메시지의 본문을 SNS API 요청에 그대로 실어 보냈다. 그러나 SNS는 메시지 본문에 256KB 크기 상한을 두고 있고, 일부 구독 프로토콜은 전달할 수 있는 페이로드 크기에 더 엄격한 제약이 있다. 그런데 실제 데이터는 이 한도를 넘기는 경우가 흔하다. 이미지나 파일 묶음, 긴 로그, 대량의 레코드를 담은 데이터는 256KB를 쉽게 넘기 때문에 그대로는 발행할 수 없고, 발행이 실패하거나 애플리케이션이 데이터를 잘라 보내야 하는 문제가 생긴다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. S3 저장발행 전에 큰 페이로드를 Amazon S3 객체로 올리고, 그 객체의 버킷 이름과 키(객체 경로)를 확보한다.
  2. 포인터 발행SNS에 보내는 메시지에 S3 객체 위치를 가리키는 포인터를 실어 발행한다. 본문이 작아 한도 안에 들어오고, 구독자에게는 평소와 같은 알림이 전달된다.

구독 필터 정책은 메시지 속성(attribute)을 기준으로 구독자별로 수신 메시지를 걸러 주는 규칙이며, 토픽 전체가 아닌 개별 구독 단위로 적용된다.

#1문제 상황

기존에는 토픽에 발행된 메시지가 모든 구독자에게 그대로 전달되었다. 구독은 "이 토픽의 메시지를 받겠다"는 연결이라서, 구독한 순간부터 그 토픽에 들어오는 메시지는 종류와 무관하게 전부 받게 된다. 관심 없는 메시지까지 SQS 큐나 Lambda 함수로 흘러들어가 처리량과 비용이 낭비되고, 애플리케이션 쪽에서 다시 걸러내는 코드를 따로 만들어야 하는 부담이 생긴다. 구독자마다 원하는 메시지가 다르다는 요구를 시스템이 반영하지 못하는 것이 기존 방식의 한계다.

#2핵심 질문

토픽의 모든 메시지를 받는 대신, 구독자가 원하는 메시지만 골라 받게 하려면 어떻게 해야 할까?

#3동작 예시

구독에 필터 정책(subscription filter policy)이라는 JSON 조건을 하나 붙이면, 그 구독은 조건에 맞는 메시지만 수신한다. 예를 들어 메시지 속성(키-값 메타데이터) 중 특정 키의 값이 정책에 적은 값과 일치하는 메시지만 받도록 지정한다. 정책은 구독 단위로 따로 적용되므로, 같은 토픽에 붙은 구독자들이 각자 다른 조건으로 메시지를 골라 받을 수 있다.

#4동작 과정

  1. 조건 정의구독에 적용할 필터 정책 JSON을 만든다. 정책은 메시지 속성의 키와 값 매칭 조건을 담으며, 메시지 본문은 검사 대상이 아니다.
  2. 대조·판정메시지가 토픽에 도착하면 SNS가 그 메시지의 속성을 구독의 정책과 대조한다. 일치하면 전달하고, 일치하지 않으면 그 구독으로는 전달하지 않는다.
  3. 구독별 차등 적용정책이 없는 구독은 모든 메시지를 받고, 정책이 있는 구독만 조건을 통과한 메시지를 받는다. 따라서 하나의 메시지가 구독마다 전달 여부가 달라진다.

필터 정책 문법: AND/OR와 키 매칭

필터 정책은 JSON 객체로 작성되며, 메시지 속성 이름을 키로 정확히 매칭하고 키-값 조건들을 AND/OR 논리로 결합하는 문법을 따른다.

#1문제 상황

필터 정책이 있더라도 조건 표현이 "속성 하나가 값 하나와 같은지"만 검사하는 단순한 형태라면, 실제 사용에서 필요한 조건을 담을 수 없다. 발행되는 메시지는 보통 여러 개의 속성 키를 갖고, 각 키마다 여러 후보 값 중 하나와 일치해야 하는 경우가 많다. 또 "두 조건을 동시에 만족해야 한다"는 요구와 "여러 값 중 하나만 맞아도 된다"는 요구를 정책 하나로 조합해야 한다. 단순 동등 비교만 지원하면 이런 복합 필터링이 아예 불가능하다는 한계가 있다.

#2핵심 질문

여러 속성 키와 AND·OR 조건을 하나의 필터 정책으로 표현하려면 어떤 문법이 필요할까?

#3동작 예시

필터 정책은 JSON 객체로, "속성 키 → 그 키에 적용할 매칭 규칙"의 대응이다. 키의 값에 배열을 주면 배열 안 값 중 하나라도 일치하면 통과(OR)하고, 키가 여러 개면 모든 키가 각각 통과해야 전달(AND)한다. 예를 들어 {"type": ["A", "B"], "region": ["kr"]} 는 type이 A 또는 B이면서(OR) region이 kr인(AND) 메시지만 통과시킨다. 키 이름은 소문자로 정규화해 대조한다.

#4동작 과정

  1. 키 매칭정책의 키와 메시지 속성의 키를 대조한다. 키 이름은 소문자로 정규화(대소문자 차이를 없앰)한 뒤 비교한다.
  2. 값 매칭같은 키 안에서 정책의 값 배열과 메시지 속성의 값을 대조한다. 배열의 값 중 하나라도 일치하면 그 키는 통과(OR)한다.
  3. 복합 판정정책에 키가 여럿이면 모든 키가 각각 통과해야 최종 전달(AND)된다. 전체 조건을 충족한 메시지만 구독자에게 전달된다.

#5한 줄 요약

숫자·문자열 값 매칭과 제약

숫자 값은 비교 연산자(>, <, >=, <=)와 범위로, 문자열 값은 정확·접두사·anything-but 방식으로 매칭하며, 정책 크기와 속성 개수 등의 제약이 따른다.

→ 03-02 참조

#1문제 상황

값 매칭이 "정확히 같은 값인지"만 판별하는 동등 비교뿐이라면, 실무에서 자주 쓰는 조건들을 표현할 수 없다. "가격이 100보다 크다", "이름이 prod-로 시작한다", "특정 값을 제외한다" 같은 범위·접두어·제외 조건은 일치 여부가 단순하지 않기 때문이다. 또 값의 타입이 숫자인지 문자열인지에 따라 비교 방식이 달라져야 하는데, 한 가지 비교 방식으로는 둘 다 제대로 처리하지 못한다. 동등 비교만으로는 필터 정책이 다룰 수 있는 상황이 크게 제한된다.

#2핵심 질문

값 타입에 맞는 비교 규칙으로 크기·접두어·제외·패턴까지 매칭하려면 어떤 규칙이 필요할까?

#3동작 예시

값 매칭은 값의 타입에 따라 전용 규칙을 적용한다. 숫자 속성은 비교 연산자를 쓰는데, {"price": [{"numeric": [">=", 100, "<=", 200]}]} 는 100 이상 200 이하인 가격만 통과시킨다. 문자열 속성은 {"name": [{"prefix": "prod-"}]} 처럼 접두어 매칭으로 "prod-"로 시작하는 이름만 통과시키고, 전체 문자열과 정확히 일치하는 exact, 특정 값을 제외하는 anything-but, 패턴을 쓰는 wildcard 매칭도 있다.

#4동작 과정

  1. 값 타입 판정메시지 속성의 값이 숫자인지 문자열인지 확인하고, 그 타입에 맞는 규칙을 적용한다. 필터링은 메시지 속성에만 적용되며 메시지 본문은 검사하지 않는다.
  2. 규칙 대조numeric 규칙이 비교 연산자(>, >=, <, <=, =)로 범위를 검사하고, 문자열 규칙이 exact(완전 일치)·prefix(접두어)·anything-but(제외)·wildcard(와일드카드 패턴)로 일치 여부를 판정한다.
  3. 제약 내 판정정책은 정해진 형식과 크기 상한(최대 256KB) 안에서 작성되어야 하며, 제약을 지킨 정책이 최종 일치를 판정하고 통과한 메시지만 구독자에게 전달된다.

필터 정책 적용과 제거

만든 필터 정책을 SetSubscriptionAttributes API나 콘솔로 구독에 적용하고, 빈 정책으로 설정해 언제든 필터링을 제거하는 방법을 다룬다.

#1문제 상황

필터 정책을 만들기만 하고 구독에 연결하지 않으면 아무 효과가 없다. 구독 생성 시점에만 정책을 지정할 수 있고, 만들어진 뒤에는 정책을 바꾸거나 없앨 방법이 없다면, 조건을 조정할 때마다 구독을 삭제하고 다시 만들어야 한다. 운영 중인 구독을 삭제·재생성하면 그 사이 메시지 전달이 중단되고, 새 구독 설정을 잘못 내려보내는 실수 위험도 커진다. 정책을 만든 뒤에도 언제든 적용·변경·제거할 수 있는 별도 경로가 있어야 한다는 것이 기존 방식의 한계다.

#2핵심 질문

이미 만들어진 구독의 필터 정책을 새로 적용하거나 바꾸거나 제거하려면 어떤 작업을 해야 할까?

#3동작 예시

필터 정책은 구독 속성(SubscriptionAttributes) 중 하나인 FilterPolicy로 관리된다. 콘솔·CLI·API 어느 쪽이든 구독의 FilterPolicy 속성에 JSON 조건을 세팅하면 그 자리에서 정책이 적용되고, 이 속성을 비우면 정책이 제거되어 그 구독은 토픽의 모든 메시지를 다시 받는다. 구독을 처음 만들 때 Subscribe 호출의 속성에 정책을 함께 실을 수도 있다.

#4동작 과정

  1. 정책 지정구독 생성 시 Subscribe 호출에 FilterPolicy를 실어 만들거나, 이미 있는 구독에는 SetSubscriptionAttributes로 FilterPolicy 속성을 갱신한다. 적용할 JSON 조건을 속성 값으로 넘긴다.
  2. 즉시 적용속성이 갱신되면 이후 도착하는 메시지부터 새 조건으로 필터링된다. 이미 대기 중이던 과거 메시지에는 적용되지 않는다.
  3. 정책 제거·교체FilterPolicy 속성을 빈 값으로 세팅하면 필터링이 해제되어 모든 메시지를 받고, 다른 JSON을 세팅하면 조건이 그대로 교체된다. 구독을 다시 만들 필요가 없다.

전달 개요: 크로스 계정·크로스 리전

#1문제 상황

SNS 토픽은 기본적으로 같은 AWS 계정과 같은 리전 안에서 동작하도록 만들어져 있습니다. 구독자(메시지를 받는 대상)가 다른 계정이나 다른 리전에 있으면, 아무 설정 없이는 메시지를 보낼 수 없습니다. 조직이 AWS 계정을 여러 개 운영하거나 서비스를 여러 리전에 배포하는 경우가 많아지면서, 메시지를 보내려는 쪽과 받으려는 쪽이 흩어져 있는 상황이 흔해졌습니다. 기존 방식에서는 그런 상황마다 별도의 전달 경로를 만들거나 중간에 자체 전달 계층을 두어야 했고, 계정과 리전이 늘어날수록 관리할 경로가 기하급수적으로 늘어나는 한계가 있었습니다.

#2핵심 질문

다른 AWS 계정이나 다른 리전에 있는 구독자에게도 같은 토픽의 메시지를 그대로 전달할 수 없을까?

#3동작 예시

#4동작 과정

  3. 전달발행자가 메시지를 게시하면 SNS가 계정·리전 경계를 지나 해당 구독자에게 전달하고, 크로스 계정의 경우 구독자 계정의 SQS 큐에 메시지가 저장된다.

원본 메시지 전달(raw delivery)

SNS가 메시지를 JSON 래핑 없이 구독자(SQS·HTTP 등)에게 원본 그대로 전달하도록 만드는 구독 속성 기능.

#1문제 상황

기본적으로 SNS는 구독자에게 메시지를 보낼 때 래퍼(포장지)를 씌웁니다. 메시지 본문뿐 아니라 MessageId(메시지 고유 번호), Timestamp(발행 시각), TopicArn(토픽 주소), 서명 관련 필드 등 여러 메타데이터가 함께 담긴 JSON 형태로 전달됩니다. SQS 큐나 Lambda(서버 없이 실행되는 함수) 같은 구독자는 이 래퍼를 받아 파싱(필요한 부분을 꺼내는 처리)해야 실제 메시지 본문을 얻을 수 있습니다. 이런 방식은 받는 쪽에서 항상 JSON 파싱 코드를 작성해야 하고, 불필요한 필드 때문에 메시지 크기도 커지는 한계가 있습니다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 속성 설정구독자(또는 토픽) 속성에서 RawMessageDelivery를 true로 설정해 원본 전달을 켠다.
  2. 발행발행자가 메시지를 게시하고, SNS가 해당 구독자에게 메시지를 전달한다.
  3. 수신구독자가 JSON 래퍼 없이 메시지 본문만 그대로 받아 추가 파싱 없이 처리한다.

전달 재시도 정책

HTTP/HTTPS·SQS·Lambda 등 구독 유형별로 전달 실패 시 몇 번, 어떤 간격으로 재시도할지 정하는 정책.

#1문제 상황

구독자, 특히 HTTP 엔드포인트(웹 주소로 메시지를 받는 대상)는 일시적으로 응답하지 못하는 경우가 있습니다. 서버 점검이나 순간적인 장애로 잠시 다운된 동안 SNS가 보낸 메시지는 전달되지 못하고 유실될 수 있습니다. 기본 동작만으로는 전달 실패 시 다시 시도하는 규칙을 운영자가 제어할 수 없어서, 짧은 순간의 장애가 곧 메시지 유실로 이어지는 한계가 있었습니다.

#2핵심 질문

구독자가 일시적으로 실패해도 SNS가 정해진 규칙에 따라 다시 시도해서 메시지를 놓치지 않게 할 수 없을까?

#3동작 예시

HTTP 구독자에게 메시지를 보냈는데 500 응답(서버 오류)이 오면, SNS는 정해진 재시도 횟수만큼 다시 보냅니다. 재시도 정책에서 최대 재시도 횟수(예: 10회)와 재시도 간격(예: 처음 1초, 그다음 2초처럼 점점 늘어나는 지수 백오프 방식)을 직접 설정할 수 있어, 구독자가 잠시 다운되어도 복구되면 남은 재시도로 메시지를 전달할 수 있습니다.

#4동작 과정

데드레터 큐(DLQ)

재시도가 모두 소진된 메시지를 격리해 보관하는 SQS 큐로, 전달 실패 메시지를 놓치지 않고 분석·재처리할 수 있게 해주는 기능.

#1문제 상황

#2핵심 질문

#4동작 과정

5FIFO 토픽05-01

FIFO 토픽 개념과 사용 사례

FIFO 토픽은 게시 순서대로 메시지를 전달하고 중복을 제거하는 Amazon SNS 토픽 유형으로, 순서가 중요한 금융·주문 처리 등에 쓰인다.

#1문제 상황

일반 SNS 토픽(표준 토픽)은 발행 순서를 보장하지 않습니다. 메시지가 게시된 순서와 다르게 구독자에게 도착할 수 있고, 같은 메시지가 여러 번 전달될 수도 있습니다. 대부분의 알림에는 문제가 없지만, 주문 처리나 금융 거래처럼 "먼저 온 일이 먼저 처리되어야" 하는 작업에서는 순서가 뒤집히거나 중복이 발생하면 시스템이 잘못된 상태가 됩니다. 순서와 중복을 직접 제어할 수 없는 것이 기존 방식의 한계였습니다.

#2핵심 질문

메시지의 전달 순서가 보장되고 중복 없이 전달되는 토픽을 만들 수 없을까?

#3동작 예시

주문 이벤트를 처리하는 시스템에서 "주문 생성 → 결제 → 배송" 이벤트는 이 순서대로 처리되어야 합니다. FIFO 토픽은 같은 메시지 그룹(MessageGroupId, 순서를 지킬 묶음 기준)에 속한 메시지를 발행된 순서 그대로 구독자에게 전달하고, 지정된 시간 안에 같은 내용이 다시 발행되면 중복으로 간주해 하나만 전달합니다. 주문 생성이 결제보다 늦게 도착하는 일이 발생하지 않습니다.

#4동작 과정

  1. 토픽 생성이름이 .fifo로 끝나는 FIFO 토픽을 만들고, 구독자도 FIFO 방식을 지원하는 대상(SQS FIFO 큐 등)으로 연결한다.
  2. 발행메시지에 MessageGroupId(순서를 지킬 그룹)와 MessageDeduplicationId(중복 판별 키)를 붙여 게시한다.
  3. 전달SNS가 그룹 안에서 발행 순서대로, 중복 없이 구독자에게 메시지를 전달한다.

기존의 표준(Standard) SNS 토픽은 메시지의 순서를 보장하지 않는다. 발행한 순서와 무관하게 구독자에게 전달될 수 있고, 전달에 실패한 메시지를 재시도하는 과정에서도 순서가 뒤바뀐다. 여러 발행자가 동시에 메시지를 보내면 도착 순서가 더욱 들쭉날쭉해진다. 주문 생성 → 결제 → 배송처럼 순서가 중요한 이벤트를 흘려보내기에는 이 방식으로는 부족하다.

#2핵심 질문

#3동작 예시

FIFO 메시지 전달과 필터링

FIFO 토픽은 구독자 유형별 메시지 전달 방식을 정하고 구독 필터 정책으로 구독자별 수신 메시지를 걸러 낸다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 필터 정책 설정구독자마다 메시지 속성(예: 이벤트 종류)의 조건을 JSON 형태의 필터 정책으로 지정한다.
  2. 속성과 함께 발행발행자가 메시지에 그룹 ID와 함께 구독자가 필터링에 쓸 속성 값을 실어 보낸다.
  3. 조건 대조 후 전달SNS가 각 구독자의 필터 조건과 메시지 속성을 대조해 조건이 맞는 구독자에게만 메시지를 순서대로 전달한다.

#2핵심 질문

#3동작 예시

#4동작 과정

FIFO 보안과 내구성

FIFO 토픽은 서버 측 암호화 등 보안 기능과 메시지 내구성 보장으로 안전하고 손실 없이 메시지를 전달한다.

#1문제 상황

일반 SNS 토픽도 접근 통제, 저장 암호화, 전달 실패 처리 같은 보안·내구성 기능을 제공하지만, FIFO 토픽은 순서 보장과 중복 제거라는 추가 제약이 붙는 구조라 보안과 내구성 기능을 어떤 방식으로 조합해야 하는지가 다르다. 순서가 중요한 메시지일수록 권한 없는 접근과 메시지 손실이 더 치명적이므로 이 둘을 함께 살펴야 한다.

#2핵심 질문

FIFO 토픽의 순서·중복 제거 성질을 해치지 않으면서 메시지를 암호화하고 접근을 통제하고 손실 없이 저장할 수 있을까?

#3동작 예시

FIFO 토픽에 저장 암호화용 KMS 키를 지정하면 메시지가 저장 시점에 암호화되고 전달 시 복호화된다. IAM 정책과 토픽 정책으로 발행·구독 권한을 누가 갖는지 제한하고, 전달에 실패한 메시지는 재시도한 끝에 데드레터 큐(죽은 편지 큐, 처리 실패한 메시지를 모아 두는 큐)로 보내 손실 없이 남긴다. 메시지는 리전 안의 여러 가용 영역에 복제되어 저장된다.

#4동작 과정

  1. 접근 통제IAM 정책과 토픽 정책으로 누가 이 토픽에 발행하고 구독할 수 있는지 제한한다.
  2. 저장 암호화SNS가 지정된 KMS 키로 FIFO 토픽의 메시지를 저장 시점에 암호화하고 구독자에게 전달할 때 복호화한다.
  3. 전달 보장전달에 실패한 메시지는 정책에 따라 재시도하고, 끝내 실패하면 데드레터 큐에 넣어 보관한다. 메시지는 리전 내 여러 가용 영역에 복제되어 저장된다.

#2핵심 질문

6단계 메시지 데이터 보호

콘솔·CLI·SDK·CloudFormation 등으로 데이터 보호 정책을 생성·조회·삭제하고 실행 동작을 관리하는 절차.

#1문제 상황

데이터 보호 정책이 있다고 해도, 실제로 정책을 만들고 토픽에 붙이고 확인하고 지우는 절차가 정리되어 있지 않으면 운영에서 쓰기 어렵다. 특히 실수로 잘못된 정책을 붙이면 정상 메시지까지 차단될 수 있어, 적용 전에 정책 내용을 다시 확인하고 필요할 때는 빠르게 제거할 수 있어야 한다. 콘솔·CLI·SDK·CloudFormation(인프라를 코드로 정의하는 도구) 등 진입 경로가 여러 개라, 각 경로에서 정책을 일관되게 관리하는 방법이 필요했다.

#2핵심 질문

데이터 보호 정책을 만들고, 확인하고, 삭제하는 운영 절차를 여러 도구에서 일관되게 관리하려면 어떻게 해야 할까?

#3동작 예시

데이터 보호 정책은 토픽(또는 구독)의 한 속성(DataProtectionPolicy)으로 저장되는 JSON 이다. 그래서 정책 생성은 이 속성에 정책 JSON 을 설정하는 것이고, 조회는 이 속성 값을 읽는 것이며, 삭제는 속성을 제거하는 것이다. 콘솔 화면에서 하든, AWS CLI 명령어로 하든, CloudFormation 템플릿으로 하든 이 속성 하나를 대상으로 한다는 점은 같다.

#4동작 과정

  1. 정책 생성·적용콘솔·AWS CLI·SDK·CloudFormation 중 한 경로로 토픽이나 구독의 DataProtectionPolicy 속성에 정책 JSON 을 설정한다. 적용 즉시 해당 리소스의 메시지가 검사 대상이 된다.
  2. 정책 확인적용된 정책을 조회해 의도한 데이터 식별자와 조치가 제대로 들어갔는지, 형식 오류가 없는지 검증한다.
  3. 정책 삭제더 이상 보호가 필요 없거나 잘못 적용된 경우 속성을 제거해 보호를 해제한다. 이후 해당 리소스의 메시지는 검사 없이 전달된다.

#5한 줄 요약

데이터 보호 정책을 토픽·구독의 속성 하나로 관리해 콘솔·CLI·SDK·CloudFormation 어느 경로에서든 생성·조회·삭제를 일관되게 수행하는 구성 운영 절차

7단계 A2A: 애플리케이션 간 팬아웃

하나의 SNS 토픽에 게시된 메시지를 여러 구독 대상으로 동시에 전달하는 애플리케이션 간 메시징(팬아웃)의 개요와, 이벤트를 보내는 소스와 받는 대상 유형을 설명한다.

#1문제 상황

기존에는 하나의 이벤트를 여러 애플리케이션이 처리해야 할 때, 각 애플리케이션이 이벤트를 직접 가져가야 했다. 주기적으로 큐나 저장소를 확인하는 폴링(polling, 정해진 간격으로 데이터가 있는지 확인하는 방식)을 애플리케이션마다 각자 구현하거나, 이벤트를 받는 서버에 소비자가 직접 붙어 있었다. 이벤트를 받아야 하는 애플리케이션이 늘어날수록 소스 쪽 코드를 고쳐야 했고, 소스와 소비자가 서로 단단히 연결되어 한쪽이 바뀌면 다른 쪽도 바뀌어야 하는 문제가 있었다.

#2핵심 질문

한 번 발행된 메시지를 여러 애플리케이션에 동시에 나눠 주고, 소스와 소비자를 서로 분리하려면 어떻게 해야 할까?

#3동작 예시

SNS 토픽에 구독자를 여러 개 등록하면, 메시지를 한 번 발행했을 때 SNS 가 그 메시지를 복제해 등록된 모든 구독자에게 전달한다. 이벤트 소스(이벤트를 만들어내는 AWS 서비스나 애플리케이션)는 토픽에 메시지를 내보내기만 하고, SQS 큐·Lambda 함수·Firehose·HTTPS 엔드포인트 같은 이벤트 대상(event destination, 메시지를 받아 처리하는 곳)이 토픽을 구독한다. 소스는 구독자가 누구인지 알 필요가 없고, 대상이 늘어나도 소스 코드는 바뀌지 않는다.

#4동작 과정

  1. 소스가 발행이벤트 소스(애플리케이션 또는 AWS 서비스)가 토픽에 메시지를 한 번 발행한다. 소스는 누가 메시지를 받는지 몰라도 된다.
  2. SNS 가 복제 전달토픽이 이 메시지를 복제해 구독 중인 모든 이벤트 대상에 병렬로 전송한다. 각 대상은 서로 다른 속도로 처리할 수 있다.
  3. 대상이 비동기 처리SQS 큐는 큐에 저장해 둔 뒤 워커가 가져가고, Lambda 함수는 곧바로 실행되는 식으로 각 대상이 자기 방식대로 메시지를 처리한다.

#5한 줄 요약

이벤트 소스가 토픽에 한 번만 발행하면 여러 대상이 각자 독립적으로 메시지를 받아 처리하게 만들어 소스와 소비자를 분리하는 A2A 팬아웃 구조

7단계 A2A: 애플리케이션 간 팬아웃

SNS 토픽에 SQS 큐를 구독해 한 번 게시된 메시지를 여러 대기열 구독자가 각자 소비할 수 있게 하는 패턴.

#1문제 상황

메시지를 즉시 처리하지 않고 나중에, 또는 천천히 처리하고 싶은 경우가 있다. 그럴 때 애플리케이션이 SNS 메시지를 직접 받아 다시 SQS 큐에 넣는 중간 단계를 코드로 구현하거나, 여러 처리기가 SNS 를 직접 폴링하며 메시지를 가져가는 방식을 썼다. 직접 받아 큐에 다시 넣는 방식은 그 중간 로직을 개발자가 만들고 유지해야 했고, 폴링 방식은 처리기가 늘어날수록 메시지를 중복으로 가져가거나 누락되는 문제를 관리하기 어려웠다.

#2핵심 질문

SNS 로 발행된 메시지를 개발자가 중간 코드를 만들지 않고도 SQS 큐로 안정적으로 보낼 수는 없을까?

#3동작 예시

SQS 큐를 토픽의 구독자로 등록하면, SNS 가 발행된 메시지를 직접 그 큐에 푸시한다. 여러 개의 큐를 같은 토픽에 구독하면 발행된 메시지가 각 큐에 복제되어 들어가고, 각 큐를 폴링하는 워커(Worker, 큐에서 메시지를 꺼내 처리하는 실행 단위)들이 자기 큐의 속도에 맞춰 메시지를 꺼내 처리한다. 중간에 메시지를 옮겨 담는 코드가 필요 없다.

#4동작 과정

  1. 큐 구독SQS 큐를 토픽에 구독시킨다. SNS 가 큐에 메시지를 보낼 수 있도록 큐 쪽에 SNS 에 대한 권한 정책도 함께 설정한다.
  2. 메시지 푸시토픽에 메시지가 발행되면 SNS 가 이 메시지를 구독된 각 SQS 큐로 전송해 저장한다. 메시지는 큐에 남아 즉시 소비되지 않아도 된다.
  3. 워커가 소비각 큐를 폴링하는 워커들이 큐에서 메시지를 하나씩 꺼내 처리하고, 처리가 끝나면 큐에서 메시지를 삭제한다. 처리 속도는 큐별로 독립적으로 조절된다.

#5한 줄 요약

SQS 큐를 토픽의 구독자로 등록해 발행된 메시지를 큐에 직접 푸시하고, 각 큐의 워커가 자기 속도로 메시지를 처리하게 하는 팬아웃 방식

Lambda 함수로 팬아웃

SNS 토픽에 Lambda 함수를 구독해 메시지가 게시될 때마다 서버리스 함수가 자동으로 호출되어 처리하는 방식.

#1문제 상황

토픽에 게시된 메시지를 코드로 처리해야 할 때, 기존에는 항상 실행 중인 서버나 별도의 소비자가 필요했다. 서버를 띄워 두고 메시지가 왔는지 주기적으로 확인(polling)하는 방식은, 메시지가 없을 때도 서버를 켜 두어야 하므로 비용이 낭비되고 메시지량이 늘면 서버를 직접 늘려야 했다. SQS 큐를 거치는 방식도 큐에서 메시지를 꺼내 처리하고 삭제하는 별도 프로그램을 항상 운영해야 해서, "메시지가 게시되는 순간 바로 처리"하려면 여전히 상시 실행 컴퓨팅 리소스가 필요했다.

#2핵심 질문

토픽에 메시지가 게시될 때마다 상시 실행 서버나 폴링 없이 코드가 자동으로 실행되게 하려면 어떻게 해야 할까?

#3동작 예시

SNS 토픽에 Lambda 함수를 구독자로 등록하면, 누군가 그 토픽에 메시지를 발행하는 순간 SNS가 해당 Lambda 함수를 자동으로 호출하고 메시지 내용을 함수의 입력으로 전달한다. 예를 들어 "주문 생성" 토픽에 주문 저장용 Lambda 함수를 구독해 두면, 주문 메시지가 게시될 때마다 함수가 자동 실행되어 주문을 데이터베이스에 기록한다. 서버도, 폴링도, 메시지를 기다리는 프로세스도 없다.

#4동작 과정

  1. 함수 구독Lambda 함수에 SNS 트리거를 추가해 토픽을 지정하면 구독이 생성되고, SNS가 그 함수를 호출할 수 있는 권한이 부여된다.
  2. 메시지 발행퍼블리셔가 토픽에 메시지를 게시하면 SNS는 구독된 Lambda 함수를 해당 메시지와 함께 비동기로 호출한다.
  3. 함수 처리Lambda가 메시지 payload(메시지 본문)를 받아 코드를 실행하고, 실행이 실패하면 SNS가 정해진 횟수만큼 재시도하거나 데드레터 큐로 보낸다.

#5한 줄 요약

SNS 토픽에 Lambda 함수를 구독시켜 메시지가 게시되는 순간 서버나 폴링 없이 함수가 자동으로 호출되어 그 메시지를 처리하는 것

Firehose로 팬아웃: 아카이빙·분석

SNS 토픽에 Kinesis Data Firehose 전송 스트림을 구독해 메시지를 S3·OpenSearch Service·Redshift 등으로 전달해 아카이빙하거나 분석하는 방식.

#1문제 상황

토픽에 흐르는 메시지를 저장하거나 분석해야 할 때, 기존에는 구독자 쪽에서 전용 처리 코드를 직접 만들어야 했다. 예를 들어 S3에 메시지를 쌓으려면 수신 코드를 작성하고, 일정 크기로 모아서(batch) 파일을 만들고, 압축하고, S3에 올리는 절차를 전부 직접 관리해야 했다. 메시지가 자주 오는 토픽일수록 이 적재 파이프라인의 버퍼링·재시도·포맷 변환을 운영하는 부담이 커졌고, 각 처리 단계가 하나라도 어긋나면 메시지가 유실될 위험이 있었다.

#2핵심 질문

발행되는 메시지를 별도의 처리 코드 없이 저장소에 쌓아 분석 가능한 형태로 만들려면 어떻게 해야 할까?

#3동작 예시

SNS 토픽에 Firehose 전송 스트림(delivery stream)을 구독시키면, 게시된 메시지가 Firehose로 전달되고 Firehose가 정해진 목적지(S3, OpenSearch Service, Redshift, HTTP 등)로 모아서 배치 적재한다. 예를 들어 "결제 이벤트" 토픽에 S3로 가는 Firehose 스트림을 구독해 두면, 결제 메시지가 게시될 때마다 Firehose가 일정량을 모아 압축한 뒤 S3 버킷에 파일로 쌓는다.

#4동작 과정

  1. 스트림 구독목적지를 지정한 Firehose 전송 스트림을 만들고 토픽에 구독시켜, 게시된 메시지가 전달될 경로를 연결한다.
  2. 버퍼링·변환Firehose가 전달받은 메시지를 일정 크기 또는 일정 시간 조건으로 모은 뒤 압축·변환을 적용한다.
  3. 목적지 적재버퍼 조건이 차면 모아진 메시지를 S3 등의 목적지에 배치로 기록하여, 아카이빙되거나 분석 서비스에서 조회 가능한 상태가 된다.

#5한 줄 요약

SNS 토픽에 Firehose 전송 스트림을 구독시켜 발행되는 메시지를 별도 처리 코드 없이 버퍼링·압축해 S3 등의 목적지에 배치로 적재함으로써 아카이빙과 분석을 가능하게 하는 것

HTTPS 엔드포인트로 팬아웃

SNS 토픽에 HTTP/HTTPS 엔드포인트를 구독해 게시된 메시지를 외부 웹 서비스로 POST 전송하는 방식.

#1문제 상황

AWS 바깥에 있는 자체 웹 서비스로 알림을 보내려면, 기존에는 보내는 쪽이 상대 서비스의 주소와 호출 코드를 직접 관리해야 했다. 상대 서비스가 메시지를 받을 준비가 됐는지, 받은 요청이 진짜 우리가 보낸 것인지, 서비스가 잠시 죽어 있으면 그 사이의 알림은 어떻게 할지까지 발신 쪽이 일일이 정해야 했다. HTTP 요청을 그냥 보내는 방식은 누구나 위조된 알림을 보낼 수 있고, 상대 서버가 내려가면 알림이 그대로 유실되는 문제가 있었다.

#2핵심 질문

AWS 안팎을 가리지 않고 자체 HTTP/HTTPS 서비스에 SNS 알림을 안전하고 안정적으로 보내려면 어떻게 해야 할까?

#3동작 예시

회사가 운영하는 자체 알림 API의 HTTPS 엔드포인트를 토픽에 구독시키면, 메시지가 게시될 때 SNS가 그 엔드포인트로 JSON 알림을 POST 전송한다. 예를 들어 "주문 알림" 토픽에 자체 고객 알림 서버의 URL을 구독해 두면, 주문 메시지가 게시될 때마다 그 서버가 메시지를 받아 고객에게 문자나 앱 알림을 보내는 처리를 이어서 수행한다.

#4동작 과정

  1. 엔드포인트 구독·확인HTTPS URL을 토픽에 구독시키면 SNS가 구독 확인(SubscriptionConfirmation) 요청을 그 주소로 보내고, 엔드포인트가 이에 응답해야 구독이 활성화된다.
  2. 메시지 POST 전송이후 메시지가 게시되면 SNS가 엔드포인트로 JSON 알림을 POST하고, 전송 실패 시 구독 재시도 정책에 따라 다시 보낸다.
  3. 서명 검증·수신 처리엔드포인트는 메시지에 포함된 서명을 검증해 진짜 SNS가 보낸 메시지인지 확인한 뒤 내용을 처리한다.

#5한 줄 요약

SNS 토픽에 HTTP/HTTPS 엔드포인트를 구독시켜 게시된 메시지를 구독 확인과 서명 검증 절차를 거쳐 외부 웹 서비스로 POST 전송함으로써 AWS 밖의 시스템까지 알림을 전달하는 것

메시지 서명 검증과 형식 파싱

HTTPS 구독자 측에서 수신 메시지의 서명을 검증하고 알림·구독 확인 등 다양한 JSON 메시지 형식을 파싱해 신뢰성 있게 처리하는 방법.

#1문제 상황

HTTP 엔드포인트는 누구나 HTTP 요청을 보낼 수 있는 곳이라, 기존처럼 받은 요청을 무조건 신뢰하면 SNS를 사칭한 위조 메시지도 그대로 처리하게 된다. 또 SNS가 보내는 메시지는 종류에 따라 JSON 구조가 다른데, 구독 확인(SubscriptionConfirmation), 알림(Notification), 구독 해지(UnsubscribeConfirmation)를 구분하지 않고 같은 방식으로 파싱하면 없는 필드를 읽으려다 오류가 나거나, 확인 절차가 필요한 구독을 활성화하지 못하는 문제가 있었다.

#2핵심 질문

누구나 보낼 수 있는 HTTP 요청 중에서 진짜 SNS가 보낸 메시지만 골라내고, 종류별로 다른 JSON 형식을 안전하게 처리하려면 어떻게 해야 할까?

#3동작 예시

SNS가 보내는 모든 메시지에는 AWS가 서명한 Signature 필드가 들어 있다. 수신 측은 메시지에 적힌 인증서 URL에서 토픽의 공개 키를 가져와 서명을 검증해 위조 여부를 판별하고, MessageType 필드를 먼저 읽어 그 종류에 맞는 JSON 구조로 파싱한다. 예를 들어 MessageType이 SubscriptionConfirmation이면 Token 필드를 꺼내 ConfirmSubscription API를 호출해 구독을 활성화한다.

#4동작 과정

  1. 메시지 수신SNS가 HTTPS 엔드포인트로 메시지를 POST하면, 본문 안에 MessageType, Message, Signature, SigningCertURL 같은 필드가 담겨 온다.
  2. 서명 검증SigningCertURL에 있는 인증서의 공개 키로 Signature를 검증해 메시지가 SNS에서 온 것인지 확인한다.
  3. 형식별 파싱MessageType 값에 맞는 JSON 구조(구독 확인·알림·구독 해지)로 필드를 읽어 처리하고, 구독 확인이면 Token으로 구독을 활성화한다.

#5한 줄 요약

SNS가 보내는 메시지의 서명을 공개 키로 검증해 위조를 걸러내고, MessageType에 따라 다른 JSON 형식을 올바르게 파싱하여 HTTPS 구독자가 신뢰할 수 있는 메시지만 안전하게 처리하는 것

Event Fork Pipelines와 EventBridge Scheduler

SNS가 제공하는 AWS Event Fork Pipelines로 이벤트를 저장·검색·재생 파이프라인에 전달하거나, EventBridge Scheduler로 메시지 게시를 예약하는 방식.

#1문제 상황

토픽으로 들어오는 이벤트를 보관하거나 나중에 재처리하려면, 기존에는 저장용 버킷, 검색용 색인, 재생용 큐를 각각 만들고 그 용도에 맞는 파이프라인 코드를 직접 작성해 토픽에 연결해야 했다. 각 파이프라인의 배포·연동·권한 설정을 전부 직접 관리해야 하므로 구성이 복잡했고, 한 번만 써야 하는 이벤트를 잃어버리면 복구할 방법이 없었다. 또한 "매일 정해진 시각에 메시지를 보낸다" 같은 예약 발행은 애플리케이션에서 스케줄러를 직접 띄워 관리해야 했다.

#2핵심 질문

게시된 이벤트를 저장·검색·재생 파이프라인으로 자동 분기하고, 원하는 시각에 메시지를 게시하려면 어떻게 해야 할까?

#3동작 예시

AWS Event Fork Pipelines는 SNS 토픽에 바로 구독시킬 수 있게 만들어진 파이프라인 묶음으로, 이벤트를 S3에 저장하는 파이프라인, OpenSearch Service에 색인하는 파이프라인, 재생용 큐로 보내는 파이프라인에 같은 이벤트를 복제해 보낸다. 또 EventBridge Scheduler를 사용하면 cron 표현으로 지정한 예약 시각에 토픽의 Publish API를 호출해 메시지 발행을 자동화할 수 있다.

#4동작 과정

  1. 파이프라인 배포·구독저장·검색·재생 파이프라인을 배포하고 각각을 토픽에 구독시켜, 게시된 이벤트가 세 파이프라인으로 동시에 전달되게 한다.
  2. 이벤트 분기 보존이벤트는 S3 버킷(저장), OpenSearch(검색), SQS 재생 큐로 나뉘어 적재되고, 장애 시 재생 큐에서 이벤트를 다시 꺼내 처리한다.
  3. 예약 발행EventBridge Scheduler가 cron 일정에 따라 토픽으로 Publish API를 호출해 정해진 시각에 메시지를 게시한다.

#5한 줄 요약

게시된 이벤트를 저장·검색·재생 파이프라인 구독으로 자동 분기시켜 보존과 복구를 가능하게 하고, EventBridge Scheduler로 예약 시각에 메시지 발행을 자동화하는 것

SMS 메시징 개요와 시작

Amazon SNS가 휴대폰 번호(문자 메시지)로 알림을 보내는 A2P SMS 메시징의 개념과 시작 방법을 소개하는 항목.

#1문제 상황

애플리케이션이 사람의 휴대폰으로 문자를 보내려면, 기존에는 통신사 문자 게이트웨이와 직접 계약하거나 별도 SMS 전문 업체를 쓰는 경우가 많았다. 이런 경로는 계약 절차와 인프라 구성이 복잡하고, 발송 코드가 특정 업체의 방식에 묶여 있어 다른 경로로 바꾸기도 어려웠다. 서버에서 문자를 보내는 API를 직접 구현하려면 수신 번호 관리, 발송 상태 확인, 대량 발송 처리까지 전부 자체적으로 만들어야 해서 시작 장벽이 높았다.

#2핵심 질문

애플리케이션이 코드 한 번으로 사람의 휴대폰에 문자 메시지를 보내려면 어떻게 해야 할까?

#3동작 예시

SNS 토픽에 휴대폰 번호를 직접 구독시키고, 그 토픽에 Publish API로 메시지를 보내면 SNS가 SMS 프로바이더를 거쳐 그 번호로 문자를 전송한다. 예를 들어 "계정 알림" 토픽에 자신의 휴대폰 번호를 구독해 두고 메시지를 게시하면, SNS가 그 번호로 문자를 보내 실제로 휴대폰에서 받아볼 수 있다.

#4동작 과정

  1. 전화번호 구독토픽에 SMS 구독을 만들고 휴대폰 번호를 등록한다(프로덕션 전환 전에는 샌드박스에서 검증된 번호만 사용할 수 있다).
  2. 메시지 게시Publish 호출로 토픽에 메시지를 보내면 SNS가 SMS 프로바이더를 통해 해당 번호로 문자를 전송한다.
  3. 전송 확인·비용 관리전송 상태 로깅과 CloudWatch 지표로 전송 성공 여부를 확인하고, 월간 지출 상한(MonthlySpendLimit) 같은 SMS 설정으로 발송 비용을 제어한다.

SMS 샌드박스

프로덕션 전환 전 SMS를 테스트하는 제한된 환경으로, 전화번호 추가·검증과 프로덕션 이전 절차를 다루는 항목.

#1문제 상황

SMS는 실제로 보낼 때 발신 번호와 프로덕션 액세스 권한이 필요하다. 그런데 아무 제한 없이 새 계정이 문자를 보낼 수 있게 두면, 누군가 스팸 문자를 대량으로 뿌려 계정과 AWS 전체의 SMS 평판을 망칠 수 있다. 그래서 AWS는 신규 계정을 SMS 샌드박스(제한된 테스트 환경)에 두고 시작한다. 이 제한의 문제점은, 테스트를 시작하려는 개발자가 자기 휴대폰 번호로 문자를 보내 보고 싶어도 등록되지 않은 번호로는 아무 데도 보낼 수 없다는 것이다. 테스트 대상 번호를 하나하나 등록하고 검증해야만 전송이 가능하다.

#2핵심 질문

프로덕션에서 SMS를 남용할 위험을 막으면서도, 신규 계정이 실제 문자 전송을 안전하게 테스트하려면 어떻게 해야 하는가?

#3동작 예시

샌드박스에서는 검증된 전화번호만 수신 대상이 된다. 개발자가 콘솔에서 자신의 휴대폰 번호를 샌드박스에 등록하면, AWS가 그 번호로 확인 코드(일회용 숫자 코드)를 실제 문자로 보낸다. 개발자가 그 코드를 콘솔에 입력해 "내 번호가 맞다"는 것을 증명하면, 그 번호가 검증된 테스트 수신자로 등록되고 이후 그 번호로만 테스트 SMS를 보낼 수 있다.

#4동작 과정

  1. 번호 등록개발자가 콘솔에서 테스트에 사용할 휴대폰 번호를 샌드박스에 추가한다.
  2. 번호 검증AWS가 그 번호로 확인 코드를 보내고, 개발자가 코드를 입력해 본인 번호임을 증명하면 검증이 완료된다.
  3. 제한 전송 후 전환 신청검증된 번호로만 테스트 SMS를 보내고, 프로덕션으로 나가기 위해 AWS에 샌드박스 해제(프로덕션 액세스) 요청을 제출한다.

#5한 줄 요약

신규 계정이 검증된 번호로만 SMS를 테스트하게 강제함으로써 스팸 남용을 막는 제한 환경

문자 메시지를 받는 사람은 그 문자가 누구에게서 왔는지 바로 알아야 진짜 알림인지 스팸인지 판단할 수 있다. 발신자를 식별할 수단이 없는 기존 방식에서는 수신자 화면에 출처를 알 수 없는 번호만 표시되어 신뢰를 얻지 못하고, 통신사도 스팸 문자를 걸러내기 어려워져 발신 번호가 차단되기 쉽다. 따라서 전송 전에 발신자를 명확히 식별하는 정보를 마련해야 한다.

#2핵심 질문

수신자와 통신사가 이 문자가 진짜 어디에서 왔는지 확인할 수 있게 하려면 어떻게 해야 하는가?

#3동작 예시

#4동작 과정

  1. 유형 선택전송 목적(대량 마케팅이면 단문 코드, 브랜드 신뢰가 중요하면 발신자 ID)과 대상 국가 규정을 보고 발신 식별 유형을 고른다.
  2. 등록 및 승인국가별 요구사항에 따라 통신사나 AWS에 발신자 ID 등록을 신청하고 승인받는다.
  3. 전송에 반영등록된 발신자 ID를 사용해 SMS를 보내면 수신자 화면에 해당 번호나 이름이 출처로 표시된다.

#4동작 과정

디바이스 토큰과 푸시 인증

각 디바이스의 고유 식별자인 디바이스 토큰을 Amazon SNS 에 등록하고, APNs·FCM 푸시 서비스에 인증받기 위한 자격 증명을 설정하는 방법.

#1문제 상황

기존 방식에서는 모바일 앱이 푸시 알림을 받으려면 개발자가 푸시 서비스(APNs, FCM)의 인증 정보를 앱 서버에 직접 넣어 두고, 각 디바이스의 토큰을 앱 서버 데이터베이스에 직접 저장하고 관리했다. 이 방식은 인증 키가 만료되거나 교체될 때 서버 설정을 일일이 고쳐야 하고, 토큰이 갱신되거나 무효화되는 것을 앱 서버가 직접 추적해야 했다. 푸시 서비스에 대한 인증과 디바이스 토큰 관리라는 두 가지 책임을 전부 개발자가 떠안는 구조였다.

#2핵심 질문

푸시 서비스별로 다른 인증 방식과 계속 바뀌는 디바이스 토큰을, 메시지를 보내는 쪽이 신경 쓰지 않아도 되게 하려면 어떻게 해야 할까?

#3동작 예시

Amazon SNS는 푸시 서비스 인증 정보를 플랫폼 애플리케이션에 한 번 등록하고, 앱이 실행될 때마다 받는 디바이스 토큰은 플랫폼 엔드포인트(디바이스 하나를 가리키는 등록 대상)로 만들어 둔다. 이후 메시지를 보낼 때는 플랫폼 엔드포인트만 지정하면 SNS가 저장된 인증 정보로 해당 푸시 서비스에 연결해 토큰으로 메시지를 전달한다. 개발자는 인증 키 교체에 따른 서버 수정이나 토큰 목록 관리 없이 디바이스 하나하나에 알림을 보낼 수 있다.

#4동작 과정

  1. 인증 정보 등록APNs나 FCM에서 받은 인증 키를 이용해 플랫폼 애플리케이션을 만들고, 이 애플리케이션이 SNS가 푸시 서비스와 통신할 때 쓰는 자격 증명이 된다.
  2. 토큰 등록앱이 시작될 때 푸시 서비스가 발급한 디바이스 토큰을 SNS에 넘겨 플랫폼 엔드포인트를 생성하고, SNS가 이 엔드포인트를 디바이스의 수신 주소로 삼는다.
  3. 메시지 전달메시지를 게시할 때 엔드포인트를 지정하면 SNS가 등록된 인증 정보와 토큰을 사용해 푸시 서비스로 전송하고, 푸시 서비스가 해당 디바이스에 알림을 내려 보낸다.

전송 대상 플랫폼(APNs, FCM 등)마다 다른 페이로드 형식으로 푸시 알림 메시지를 게시하는 방법.

#1문제 상황

기존 방식에서는 여러 모바일 플랫폼(APNs, FCM)에 알림을 보낼 때 각 플랫폼이 요구하는 메시지 형식이 달라서, 개발자가 플랫폼마다 별도의 전송 코드와 메시지 조립 로직을 만들어야 했다. APNs는 특정 키 이름을 쓰고 FCM은 다른 키 이름을 쓰기 때문에, 같은 알림도 플랫폼별로 메시지 본문을 따로 만들어 전송했다. 플랫폼이 늘어날수록 중복 코드가 늘고, 한 형식만 수정하면 다른 플랫폼 전송이 깨지는 일이 잦았다.

#2핵심 질문

플랫폼마다 다른 페이로드 형식 때문에 전송 코드를 중복으로 유지하지 않으려면 어떻게 해야 할까?

#3동작 예시

Amazon SNS는 하나의 토픽에 APNs 구독자와 FCM 구독자가 함께 있고, 게시자가 각 플랫폼 전용 페이로드를 담은 메시지 속성(JSON 형식의 부가 데이터)을 함께 보내면, SNS가 각 구독자의 플랫폼에 맞는 페이로드만 골라 전달한다. 예를 들어 APNs 전용 키와 FCM 전용 키를 하나의 게시 호출에 함께 넣어 두면, APNs 엔드포인트에는 APNs 형식으로, FCM 엔드포인트에는 FCM 형식으로 각각 변환되어 도착한다.

#4동작 과정

  1. 페이로드 작성게시자가 메시지에 플랫폼별 키(APNs용, FCM용)로 나뉜 커스텀 페이로드를 담아 한 번에 게시한다.
  2. 플랫폼 판별SNS가 각 구독자가 등록된 플랫폼 애플리케이션 종류(APNs인지 FCM인지)를 확인해 해당하는 페이로드 부분을 선택한다.
  3. 형식 변환 후 전달선택된 페이로드를 그 플랫폼의 요구 형식에 맞게 조합해 푸시 서비스로 보내고, 각 디바이스에는 자기 플랫폼에 맞는 형식의 알림만 도착한다.

#5한 줄 요약

하나의 게시 호출에 플랫폼별 페이로드를 함께 담아 두면 SNS가 구독자의 플랫폼에 맞는 형식만 골라 변환·전송해, 전송 코드를 플랫폼마다 중복으로 만들지 않게 하는 형식 분기 처리

#1문제 상황

기존 방식에서는 토픽으로 흐르는 메시지를 보관하거나 분석하려면, 메시지가 전달된 뒤에도 그것을 저장할 별도 파이프라인을 직접 만들어야 했다. 구독자(람다, SQS, HTTP 등)가 메시지를 받아 소비해 버리면 기록이 남지 않아서, 나중에 "어떤 메시지가 언제 흘렀는지"를 확인하거나 집계 분석할 방법이 없었다. 저장과 분석을 위해 별도 수집 로직을 붙이는 것은 구축과 유지 비용이 컸다.

#2핵심 질문

토픽에 흐르는 메시지를 전달과 별개로 보관하고 분석하려면, 추가 수집 코드 없이 어떻게 해야 할까?

#3동작 예시

#4동작 과정

  1. 저장 파이프라인 준비메시지를 받아 저장할 대상(Firehose 전송 스트림, 그리고 그 도착지인 S3 등)을 생성한다.
  2. 구독 연결그 전송 스트림을 토픽의 구독자로 등록하면, 토픽에 게시되는 모든 메시지가 이 구독으로도 전달된다.
  3. 보관과 분석전달된 메시지가 대상 버킷에 형식에 맞춰 쌓이고, 저장된 데이터를 쿼리 도구로 조회해 기간별 건수 같은 집계 분석을 수행한다.

누가 어떤 SNS 작업(주제 생성·구독·게시 등)을 할 수 있는지를 IAM 정책과 접근 정책 언어로 규정하는 권한 관리 방식이다.

#1문제 상황

기존 방식에서는 Amazon SNS 토픽을 만들면 기본적으로 AWS 계정 안의 모든 사용자가 그 토픽에 메시지를 게시하고 구독할 수 있었습니다. 계정 자격 증명만 있으면 누구든 토픽을 조작할 수 있었기 때문에, 한 명의 권한만으로 팀 전체가 토픽을 마음대로 바꿀 수 있었고 잘못된 설정이나 과금 문제가 생겨도 누가 한 일인지 추적하지 못했습니다. 사용자마다 역할을 나누고 싶어도 SNS가 '누가 무엇을 할 수 있는지'를 구분하는 방법이 없어서, 결국 계정 전체를 하나의 권한 덩어리로 다룰 수밖에 없었습니다. 이런 구조에서는 한 사용자의 실수가 전체 서비스에 바로 영향을 주었습니다.

#2핵심 질문

토픽마다 '누가 게시하고, 누가 구독하고, 누가 관리하는지'를 개별적으로 통제할 수는 없을까?

#3동작 예시

AWS IAM(자격 증명과 접근 관리 서비스)에서는 JSON 형식의 접근 정책 문서 하나가 '어떤 주체가 어떤 작업을 어떤 리소스에 대해 할 수 있는지'를 선언합니다. 예를 들어 "arn:aws:sns:ap-northeast-2:123456789012:OrderTopic"이라는 토픽에 대해 sns:Publish(메시지 게시 권한)만 허용하는 정책을 만들면, 그 정책이 연결된 사용자는 해당 토픽에 메시지를 보낼 수 있지만 토픽을 삭제하거나 구독 목록을 보는 일은 할 수 없습니다. 정책 언어는 Effect(허용/거부), Action(작업), Resource(대상 리소스), Condition(조건) 네 가지 요소로 이루어져 있고, SNS는 이 문서를 읽어 요청이 허용되는지 판단합니다.

#4동작 과정

  1. 요청 도착사용자가 SNS API를 호출합니다(예: Publish). 이때 사용자의 자격 증명과 함께 어떤 작업을 어떤 토픽에 요청했는지가 전달됩니다.
  2. 정책 평가SNS가 요청한 사용자에게 연결된 자격 정책과 토픽에 연결된 리소스 정책을 모두 모아, 각 정책의 Effect·Action·Resource가 요청과 일치하는지 대조합니다. 하나라도 명시적 Deny(거부)가 있으면 그 즉시 거부되고, 명시적 Allow(허용)가 있으면 허용됩니다.
  3. 허용 판정어떤 정책도 일치하지 않으면 기본값인 거부로 판정되어 요청이 실패합니다. 일치하는 Allow가 있으면 해당 작업이 실행됩니다.

#1문제 상황

기존 방식에서는 AWS 계정을 만들 때 발급되는 장기 자격 증명(액세스 키와 시크릿 키 한 쌍)을 코드나 서버 설정 파일에 넣어 두고 SNS API를 호출했습니다. 이 키는 만료되지 않으므로 한 번 유출되면 누군가가 영구적으로 그 계정의 SNS 작업을 수행할 수 있었고, 키가 어디에 퍼졌는지 추적하기도 어려웠습니다. 또한 팀원이 바뀔 때마다 키를 생성하고 공유하고 폐기하는 과정이 반복되었으며, 코드 안에 하드코딩된 키는 보안 점검에서 계속 걸려 나왔습니다. 자격 증명을 '누구에게, 얼마나 오래, 어떤 범위로 줄지'를 세밀하게 정할 방법이 없었습니다.

#2핵심 질문

만료 기간이 있고, 필요한 순간에만 발급되며, 특정 작업에만 쓰이는 안전한 자격 증명으로 SNS를 호출할 수는 없을까?

#3동작 예시

AWS STS(보안 토큰 서비스)는 임시 자격 증명을 발급하는 서비스로, AssumeRole(역할 맡기) API를 호출하면 액세스 키·시크릿 키·세션 토큰 세 개가 최대 수 시간 동안만 유효하게 발급됩니다. 예를 들어 서버가 시작될 때 "SNS 게시 전용 역할"을 맡아 임시 키를 받고, 그 키로만 토픽에 메시지를 게시합니다. 발급 시점에 역할의 정책이 함께 적용되므로 임시 키는 SNS 게시 외에는 아무것도 할 수 없고, 정해진 시간이 지나면 자동으로 쓸 수 없게 됩니다.

#4동작 과정

  1. 역할 맡기 요청애플리케이션이 STS의 AssumeRole API를 호출하며 '어떤 역할을 맡을지'와 '세션 이름'을 지정합니다. 여기엔 장기 자격 증명이 필요하지만 코드 노출 없이 안전하게 보관된 키를 사용합니다.
  2. 임시 자격 증명 발급STS가 역할에 연결된 권한 정책을 기준으로 임시 키와 세션 토큰을 만들어 반환합니다. 이 자격 증명은 지정된 만료 시간 안에서만 동작합니다.
  3. SNS 호출과 만료애플리케이션이 임시 키로 SNS API를 호출해 메시지를 게시합니다. 만료 시간이 지나면 SNS는 해당 자격 증명을 더 이상 인정하지 않으므로, 유출되더라도 피해 기간이 제한됩니다.

#1문제 상황

기존 방식에서는 SNS 토픽에 게시되는 메시지가 서비스 내부에 평문(읽을 수 있는 그대로의 텍스트)으로 저장되었습니다. 메시지는 구독자에게 전달되기 전까지 토픽 버퍼에 일시적으로 보관되는데, 이 상태에서 저장 장치에 접근 권한이 있는 관리자나 유출된 백업 계정이 있다면 메시지 내용을 그대로 읽을 수 있었습니다. 특히 결제 정보나 개인 식별 정보처럼 민감한 내용을 담은 알림이 많아질수록, 전송 중이 아닌 '저장된 상태'에서 데이터를 보호할 방법이 필요해졌고, 규정 때문에 저장 데이터 암호화를 요구받는 서비스들은 SNS를 사용하기 어려웠습니다.

#2핵심 질문

#3동작 예시

서버 측 암호화(SSE)는 SNS가 토픽에 도착한 메시지를 저장 장치에 쓰기 전에 자동으로 암호화하고, 구독자에게 보낼 때만 복호화하는 기능입니다. 토픽을 생성할 때 AWS KMS(키 관리 서비스)에서 만든 고객 관리형 키를 지정하면, 게시된 메시지는 그 키로 암호화되어 저장됩니다. 예를 들어 "알림 전용 키" 하나를 만들어 결제 알림 토픽에 연결해 두면, 키를 삭제하거나 비활성화하는 순간 그 토픽에 저장된 모든 메시지는 복호화할 수 없게 되어 데이터 폐기를 강제할 수도 있습니다.

#4동작 과정

  1. 메시지 수신발신자가 토픽에 메시지를 게시하면 SNS가 메시지를 받아 저장 단계로 넘깁니다. 이 시점에 토픽에 KMS 키가 연결되어 있는지 확인합니다.
  2. 암호화 저장SNS가 KMS에 키 사용을 요청해 데이터 키를 받고, 그 데이터 키로 메시지를 암호화한 뒤 저장합니다. 실제 메시지 내용은 암호문으로만 디스크에 존재합니다.
  3. 복호화 전달구독자에게 메시지를 전달할 차례가 되면 SNS가 같은 KMS 키로 메시지를 복호화하고, 구독 유형에 맞는 형식으로 보냅니다. 전달이 끝난 임시 메시지는 파기됩니다.

VPC 엔드포인트와 트래픽 보호

VPC 내부 리소스가 인터넷을 거치지 않고 프라이빗 네트워크로 SNS에 접근하도록 연결해 트래픽을 보호하는 방식이다.

#1문제 상황

기존 방식에서는 VPC(프라이빗 가상 네트워크) 안에 있는 EC2 인스턴스가 SNS에 메시지를 게시하려면, 내부 요청이 인터넷 게이트웨이를 통과해 공용 인터넷으로 나갔다가 다시 AWS의 SNS 엔드포인트로 들어와야 했습니다. 이 경로는 요청이 공용 네트워크를 거치므로 패킷이 중간에서 가로채이거나 변조될 여지가 있었고, VPC의 보안 그룹과 네트워크 ACL(접근 제어 목록)로는 외부로 나가는 SNS 트래픽을 세밀하게 통제할 수 없었습니다. 또한 인터넷 경로를 꼭 열어야 하므로 VPC의 폐쇄적인 보안 설계가 깨졌고, 데이터 전송이 외부 네트워크에 의존해 지연과 장애 지점도 늘었습니다.

#2핵심 질문

VPC 안의 서비스가 공용 인터넷을 거치지 않고 AWS 사설 네트워크만으로 SNS에 접근할 수는 없을까?

#3동작 예시

인터페이스 VPC 엔드포인트는 VPC 안에 SNS 전용의 사설 네트워크 인터페이스(ENI)를 하나 만들고, 그 인터페이스를 통해 SNS API를 호출하는 방식입니다. 예를 들어 프라이빗 서브넷의 애플리케이션 서버가 sns.ap-northeast-2.amazonaws.com이라는 이름으로 요청을 보내면, 그 요청은 VPC 내부의 엔드포인트 인터페이스로 전달되어 AWS 백본(사설 백본망)을 타고 SNS에 도달합니다. 응답도 같은 사설 경로로 돌아오므로 공용 인터넷을 전혀 거치지 않습니다.

#4동작 과정

  1. 엔드포인트 생성과 정책 설정VPC 안에 SNS용 인터페이스 엔드포인트를 만들고, 엔드포인트 정책(어떤 계정·어떤 토픽·어떤 작업만 허용할지)을 연결합니다.
  2. 사설 DNS로 라우팅VPC 안의 요청이 SNS의 공용 주소 대신 엔드포인트 인터페이스의 사설 IP를 가리키도록 DNS 설정이 바뀝니다. 서버 코드는 수정하지 않아도 됩니다.
  3. 사설망 전달요청이 엔드포인트를 통해 AWS 사설 네트워크로 들어가 SNS에 도착하고, 응답도 같은 경로로 돌아옵니다. VPC 밖으로 나가는 트래픽이 없으므로 보안 통제가 그대로 유지됩니다.

#1문제 상황

기존 방식에서는 SNS 토픽에 메시지가 게시되고 전달되는 과정이 블랙박스였습니다. 메시지를 보냈는데 구독자가 받지 못했을 때, 게시 자체가 실패했는지 전달이 실패했는지, 어느 구독 유형에서 문제가 생겼는지 알 수단이 없었습니다. 문제가 생겨도 API 호출 기록이나 지표가 남지 않았기 때문에 장애 원인을 찾으려면 로그를 직접 넣어 코드를 다시 배포하거나 AWS 지원에 문의해야 했고, SMS나 이메일 전송이 조용히 유실되는 경우를 사전에 감지할 방법도 없었습니다.

#2핵심 질문

메시지 게시와 전달이 실제로 어떻게 일어나는지, 누가 언제 호출했는지, 실패는 어디서 나는지 객관적으로 확인할 수는 없을까?

#3동작 예시

SNS는 두 가지 감시 수단을 제공합니다. 하나는 AWS CloudTrail(API 호출 기록 서비스)로, "누가 어떤 IP에서 언제 Publish나 CreateTopic을 호출했는지"가 JSON 로그로 남습니다. 다른 하나는 Amazon CloudWatch(지표 수집 서비스)로, 토픽별 게시 건수·전달 성공 건수·실패 건수가 숫자 지표로 계속 쌓여 대시보드에서 실시간으로 보입니다. 예를 들어 "NumberOfNotificationsDelivered"가 0인데 "NumberOfNotificationsFailed"가 늘고 있으면 전달 장애가 발생 중임을 바로 알 수 있습니다.

#4동작 과정

  1. 기록 생성누군가 SNS API를 호출하면 그 호출 내용이 CloudTrail에 이벤트로 기록되고, 전달 시도가 일어날 때마다 성공·실패가 CloudWatch 지표로 집계됩니다.
  2. 지표 수집과 시각화CloudWatch가 토픽별 지표를 수집해 대시보드에 그래프로 표시하고, 설정한 임계값을 넘으면 알림을 보냅니다. CloudTrail 로그는 S3에 저장되어 언제든 조회할 수 있습니다.
  3. 원인 분석실패 지표가 감지되면 CloudTrail 로그로 호출 주체를 확인하고, 전달 실패가 반복되는 구독에는 데드레터 큐(실패 메시지를 모아 두는 큐)에 쌓인 원본 메시지로 실패 원인을 추적합니다.

규제 요구사항 충족과 장애 복원력을 갖추고, AWS가 권장하는 보안 구성 관행을 지켜 SNS를 안전하게 운영하는 것이다.

#1문제 상황

기존 방식에서는 SNS를 서비스에 붙이면 보안 책임이 온전히 사용자에게 있었습니다. 토픽이 리전 하나에만 존재하므로 그 리전의 데이터 센터에 장애가 나면 알림 전체가 멈췄고, 리전을 넘어서는 고가용성 설계가 준비되어 있지 않았습니다. 또 금융·의료처럼 규제를 받는 업종은 "이 서비스가 감사에 통과하는 보안 인증을 받았는지"를 확인할 수 없어 도입 자체를 망설였고, 암호화·접근 제어·모니터링을 각각 따로 챙겨야 해서 빠뜨리는 부분이 생기기 쉬웠습니다.

#2핵심 질문

규제 요건을 충족하고, 리전 장애에도 견디며, 보안 설정을 빠짐없이 갖추려면 SNS를 어떤 기준으로 운영해야 할까?

#3동작 예시

SNS의 보안 설계는 세 축으로 정리됩니다. 첫째, 규정 준수: SNS는 SOC, PCI DSS, ISO 27001, HIPAA 같은 보안 인증·규정 준수 프로그램을 지원하며, 감사에 필요한 준수 정보를 AWS Artifact에서 서류로 받을 수 있습니다. 둘째, 복원력: 토픽을 여러 리전에 만들고 게시를 분산하면 한 리전이 장애가 나도 다른 리전이 알림을 계속 전달합니다. 셋째, 모범 사례: 최소 권한 정책·서버 측 암호화·CloudTrail 감시·VPC 엔드포인트 사용을 함께 적용합니다. 예를 들어 결제 처리 서비스가 SOC 보고서로 감사를 통과하고, 프라이머리·백업 두 리전에 토픽을 두고, 게시 자격을 역할로 제한하는 구성이 바로 그 예입니다.

#4동작 과정

  1. 준수 확인사용 중인 리전에서 필요한 인증(예: HIPAA, PCI)이 지원되는지 확인하고 AWS Artifact에서 준수 보고서를 받아 감사에 활용합니다.
  2. 복원력 설계주요 토픽을 두 리전 이상에 배포하고, 장애 시 다른 리전으로 전환하는 절차를 정합니다. SNS가 리전별로 독립 운영되므로 한 리전의 장애가 다른 리전으로 번지지 않습니다.
  3. 모범 사례 적용IAM 최소 권한 정책을 토픽에 연결하고, KMS 암호화를 켜고, CloudTrail 로깅을 활성화하고, 프라이빗 서비스는 VPC 엔드포인트로 연결합니다. 이 기본 세트를 모든 토픽에 동일하게 적용합니다.

SNS가 규정 준수 인증을 제공하고 리전별 독립 운영으로 복원력을 확보하며, 최소 권한·암호화·로깅·VPC 엔드포인트라는 보안 모범 사례를 기본으로 갖추어야 안전하게 운영되는 관리형 알림 서비스

X-Ray로 토픽 문제 진단

Amazon SNS 토픽의 메시지 전송 경로를 AWS X-Ray 추적으로 추적·분석해 전달 실패나 지연 같은 문제를 진단하는 방법

#1문제 상황

X-Ray 활성 추적을 쓰지 않는 기존 방식에서는 토픽 문제를 진단할 때 CloudWatch 지표로 토픽 전체의 발행 수, 전달 실패 수 같은 합계 수치를 확인했다. 이 방식은 "어떤 메시지가 실패했다"는 사실은 알려 주지만, 그 메시지 하나가 토픽에 도착했는지, 필터 정책에서 걸러졌는지, 구독자 쪽 전달에서 실패했는지처럼 실패가 일어난 정확한 단계는 보여 주지 못한다. 또 여러 구독자가 있을 때 어느 구독자에게만 문제가 있는지도 메시지 단위로는 알 수 없어서, 원인을 찾기 위해 로그를 뒤지거나 추측으로 범위를 좁혀야 했다.

#2핵심 질문

토픽에 보낸 메시지가 구독자에게 도달하지 않았을 때, 그 메시지 하나가 어느 단계에서 왜 멈췄는지 어떻게 알 수 있을까?

#3동작 예시

AWS X-Ray의 활성 추적(active tracing)을 토픽에서 켜면, 이후 발행되는 각 메시지에 추적 ID가 자동으로 부여되고, 그 메시지가 토픽에 도착한 순간부터 필터링을 거쳐 각 구독자에게 전달 완료될 때까지의 각 구간이 X-Ray에 세그먼트(구간 기록)로 남는다. 예를 들어 "주문 완료" 토픽에 메시지를 보냈는데 이메일 구독자에게만 안 갔다면, X-Ray 콘솔의 트레이스 맵에서 그 메시지의 경로를 열어 이메일 구독자로 향하는 구간에서 오류가 찍힌 것을 바로 확인할 수 있다.

#4동작 과정

  1. 활성 추적 켜기토픽 설정에서 X-Ray 활성 추적을 활성화하면, 활성화 이후 발행되는 모든 메시지에 추적 ID가 부여된다.
  2. 경로 기록메시지가 토픽에 도착하는 발행 구간, 필터 정책이 적용되는 구간, 각 구독자 유형(HTTP, SQS, Lambda 등)으로 전달되는 구간이 각각 세그먼트로 기록되어 메시지가 어디를 거쳤는지 타임라인에 남는다.
  3. 트레이스 확인X-Ray 콘솔에서 트레이스 맵과 타임라인을 열어, 실패한 메시지가 어느 구간에서 오류를 냈는지 상태와 응답 시간까지 확인해 원인 단계를 특정한다.

#5한 줄 요약

토픽에 흐르는 메시지 하나하나에 추적 ID를 부여해 발행부터 구독자 도달까지의 전체 경로를 시각화함으로써, 문제가 생긴 메시지의 실패 지점을 구간 단위로 찾아내는 것
