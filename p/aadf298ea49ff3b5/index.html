1단계 기초 — 서비스 이해

AWS가 인프라를 관리하는 검색·분석 관리형 서비스로, OpenSearch 엔진 기반 도메인을 만들어 검색·로그 분석·벡터 검색을 실행한다.

1상대의 출발점 확인

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 Amazon OpenSearch Service에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. 검색 기능이 필요한 서비스가 있다면, 여러분은 검색 엔진을 직접 설치하고, 그 서버를 띄우고, 장애가 나면 직접 고치고, 데이터가 늘면 직접 확장해야 했습니다. 그런데 여기서 문제가 되는 지점은 바로 이겁니다. 서버 관리라는 일이 검색이라는 본질적인 작업과는 전혀 관계가 없음에도, 그 관리 부담을 전부 개발자가 떠안아야 한다는 것입니다. 인프라를 꾸리는 시간만큼 실제 검색 기능을 만드는 시간은 줄어들게 되시겠죠.

2질문 제기

핵심 질문을 정확히 하나만 정하고 가겠습니다. 인프라 관리의 부담은 덜어내면서, 검색이라는 핵심 기능은 온전히 가져가려면 어떻게 해야 할까요?

3구조적 핵심 예시

하나의 예시를 정확히 보고 가겠습니다. 여러분이 로그 분석을 하려고 한다고 합시다. 관리형 서비스라면 이렇게 동작합니다. 여러분은 AWS 콘솔에서 "도메인"이라는 클러스터 하나를 만들기만 하면 됩니다. 그러면 AWS가 그 뒤의 인프라, 즉 서버의 생성·패치·모니터링·장애 대응까지 전부 관리합니다. 여러분은 만들어진 도메인의 엔드포인트(주소)를 받아서 문서를 넣고 검색 요청을 보내면 되는 것이고, 검색·로그 분석·벡터 검색을 그 위에서 실행합니다. 이 구조가 핵심입니다. 관리할 것은 도메인 하나, 실행할 것은 검색 기능 전부. 이 둘의 분리가 Amazon OpenSearch Service의 구조 그 자체입니다.

4단계별 동작 과정

과정을 단계별로 정확히 정리하겠습니다. - 도메인 생성 — OpenSearch 엔진 기반의 관리형 클러스터(도메인)를 AWS가 프로비저닝합니다. 이때 인프라 관리는 AWS가 넘겨받습니다. - 데이터 적재와 쿼리 — 만들어진 도메인의 엔드포인트로 문서를 보내고 검색·분석 요청을 실행합니다. 요청은 앞 단계에서 만들어진 도메인을 통해서만 동작하게 되시겠죠. - AWS의 사후 관리 — 패치·백업·확장 같은 운영 작업을 AWS가 계속 수행하여, 사용자는 결과적으로 검색 기능 자체만 바라봅니다.

1단계 기초 — 서비스 이해

오픈소스 OpenSearch를 직접 운영할지 AWS 관리형 OpenSearch Service를 쓸지 결정하는 기준으로, 운영 부담·확장성·비용·기능 차이를 비교한다.

1상대의 출발점 확인

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 OpenSearch와 Service 선택 기준에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. OpenSearch는 오픈소스 프로젝트입니다. 즉 누구나 이 코드를 받아서 자기 서버에 직접 설치하고 운영할 수 있습니다. 여러분이 그 길을 선택하면, 클러스터를 직접 띄우고, 버전 업그레이드를 직접 하고, 데이터가 늘면 노드를 직접 늘리고, 장애 나면 직접 복구합니다. 여기서 문제가 되는 지점은 명확합니다. 그 모든 운영 부담은 전적으로 여러분 몫이라는 것입니다. 반대로 AWS가 관리하는 서비스형으로 가면 그 부담이 사라지지만, 반대로 제어권과 비용 구조가 달라지게 됩니다. 이 두 길 사이에서 무엇을 기준으로 골라야 할지가 바로 출발점입니다.

도메인의 OpenSearch 엔진 버전을 업그레이드하거나 스냅샷·재색인 등을 이용해 기존 데이터를 다른 도메인으로 옮기는 절차.

1상대의 출발점 확인

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 도메인 업그레이드와 마이그레이션에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. 도메인은 만들어진 시점의 OpenSearch 엔진 버전으로 운영됩니다. 그런데 엔진 버전은 계속 올라가고, 오래된 버전은 결국 지원이 끝나는 시점이 옵니다. 지원이 끝난 버전을 계속 쓰는 것은 보안이나 기능 면에서 감당할 수 없는 상태가 되겠죠. 그런데 버전을 올리는 일은 단순히 스위치 하나 켜는 것이 아닙니다. 엔진이 바뀌면 데이터도 새 버전 기준으로 맞춰져야 하고, 경우에 따라서는 데이터를 아예 다른 도메인으로 옮겨야 할 수도 있습니다. 여기서 문제가 되는 지점은 "버전을 올리거나 도메인을 옮기는 절차를 제대로 알아야 데이터 손실 없이 진행할 수 있다"는 것입니다.

2질문 제기

핵심 질문을 정확히 하나만 정하고 가겠습니다. 도메인의 OpenSearch 엔진 버전을 올리거나, 기존 데이터를 다른 도메인으로 옮기려면 어떤 절차를 따라야 할까요?

3구조적 핵심 예시

하나의 예시를 정확히 보고 가겠습니다. 현재 운영 중인 도메인이 오래된 엔진 버전이라고 해 봅시다. 우선 그 도메인 자체로 엔진 버전 업그레이드(Upgrade)를 할 수 있습니다. OpenSearch Service가 업그레이드 가능한 대상 버전을 안내하고, 그 범위 안에서 버전을 올립니다. 그런데 더 큰 변화가 필요하거나 도메인 자체를 바꿔야 하는 경우에는 마이그레이션(Migration)이 필요합니다. 이때는 기존 도메인의 스냅샷을 떠서 새 도메인에 복원하거나, 재색인(Reindex)을 통해 데이터를 새 도메인으로 옮깁니다. 즉 "같은 도메인 안에서 버전을 올리는 것이 업그레이드, 데이터를 다른 도메인으로 옮기는 것이 마이그레이션"입니다. 이 구조가 핵심입니다.

4단계별 동작 과정

과정을 단계별로 정확히 정리하겠습니다. - 경로 선택 — 현재 도메인의 버전을 그대로 올리는 업그레이드(Upgrade)를 할지, 데이터를 새 도메인으로 옮기는 마이그레이션(Migration)을 할지 정합니다. 이후의 모든 단계가 이 선택에 따라 달라집니다. - 데이터 이전 준비 — 마이그레이션 경로라면 기존 도메인의 스냅샷을 만들거나 재색인(Reindex) 대상을 준비합니다. 앞 단계의 선택을 받아 이전할 데이터를 확보하는 단계입니다. - 이전·완료 — 업그레이드는 도메인 내에서 버전이 올라가고, 마이그레이션은 새 도메인에 데이터가 옮겨져 서비스가 전환됩니다. 이후 도메인은 새 버전 또는 새 도메인 기준으로 운영되겠죠.

패키지와 커스텀 플러그인

도메인에 사전·플러그인 같은 커스텀 패키지를 업로드해 검색 기능을 확장하는 방법을 다루는 문서다.

1상대의 출발점 확인

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 도메인에 사전이나 플러그인 같은 커스텀 패키지를 올려 검색 기능을 확장하는 방법에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. OpenSearch는 기본적으로 내장된 형태 분석기와 플러그인만 가지고 동작합니다. 여러분이 검색을 하다 보면, 예를 들어 한국어나 일본어 같은 언어의 형태소 분석, 혹은 특수한 사전 기반 검색이 필요해지는 순간이 옵니다. 그런데 기본 상태에서는 그런 기능이 도메인에 없습니다. 세팅을 바꿔 봐야 도메인에 올라가 있는 커스텀 바이너리가 없으니까 그 기능 자체가 존재하지 않습니다. 여기서 문제가 되는 지점은, 도메인은 클라우드에서 관리되는 환경이라 여러분이 서버에 직접 들어가 플러그인을 깔 수 없다는 것입니다. 관리형 서비스니까 파일을 손으로 넣을 수 없는 거죠. 그래서 검색 기능을 확장하고 싶어도 방법이 막혀 있는 상태입니다.

2질문 제기

그럼 핵심 질문을 정확히 하나만 정하고 가겠습니다. 관리되는 도메인 안에서 커스텀 사전과 플러그인을 어떻게 안전하게 배포하고 적용할 수 있을까요?

3구조적 핵심 예시

하나의 예시를 정확히 보고 가겠습니다. 여러분이 영화 정보를 검색하는 서비스를 만든다고 합시다. 영화 제목 검색에서 "아바타"라고만 쳐도 "아바타: 물의 길"까지 함께 나오게 하려면, 형태소 분석기가 "아바타"라는 단어를 제대로 인식하고 인덱싱할 때 그 단어를 쪼개지 않고 유지해야 합니다. 여기서 필요한 게 커스텀 사전입니다. 그렇다면 이 사전 파일은 어디서 오는가. 여러분이 로컬에서 사전 텍스트 파일을 준비해서 S3 버킷에 올립니다. 그 S3 객체가 패키지가 되고, 여러분의 도메인이 그 패키지를 참조하게 됩니다. 도메인은 그 패키지를 받아서 노드에 배포하고, 인덱스가 그 사전을 사용하는 형태소 분석기로 생성됩니다. 이 구조가 핵심입니다. 즉, "파일을 직접 넣는 것"이 아니라 "S3에 있는 패키지를 도메인이 참조해 배포하는 것"이 이 기능의 골격입니다. 어떤 플러그인을 쓰든, 사전이 어떤 언어든, 이 구조는 동일하게 유지됩니다.

4단계별 동작 과정

  1. 패키지 생성 및 업로드사전이나 플러그인 바이너리를 묶어 S3에 업로드하고, CreatePackage API로 패키지 메타데이터를 등록합니다. 이 시점까지 도메인은 아무것도 모르고, 단지 S3에 객체가 하나 생긴 상태입니다.
  2. 도메인 연결(Association)AssociatePackage API로 패키지를 도메인에 연결합니다. 그러면 도메인 서비스가 S3에서 패키지를 내려받아 도메인을 구성하는 각 데이터 노드에 배포하고, 이 배포가 끝나면 도메인이 잠시 재시작됩니다. 앞 단계에서 만든 패키지가 이제야 실제로 도메인 안에 존재하게 되는 겁니다.
  3. 패키지 사용과 해제도메인에 배포된 플러그인·사전을 인덱스 설정이나 분석기에서 사용하고, 더 이상 필요 없으면 DissociatePackage로 연결을 끊습니다. 이 단계의 결과가 곧 검색 기능의 확장·축소입니다.

5본질 요약

자, 본질을 정확히 한 문장으로 정리하겠습니다. 이 기술S3에 올린 커스텀 사전·플러그인 패키지를 도메인에 연결해 배포함으로써 관리형 환경에서도 검색 기능을 확장하는 것입니다. 이 문장을 기준으로 나머지를 이해하면 됩니다

SQL 지원

OpenSearch 데이터를 익숙한 SQL 문법으로 질의할 수 있게 해주는 기능으로, SQL을 REST API·도구를 통해 실행한다.

1상대의 출발점 확인

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 OpenSearch 데이터를 SQL로 질의하는 기능에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. OpenSearch의 기본 질의 방식은 JSON 기반 Query DSL입니다. 여러분이 "매출이 100만 원 넘는 주문을 찾아라" 같은 검색을 하려면 쿼리 구조를 JSON으로 조립해서 _search API로 던져야 합니다. 그런데 잠깐, 여러분 중에 SQL만 해온 분이라면 이 JSON 조립이 꽤 낯설고, 작성하는 데도 시간이 걸립니다. 데이터베이스에서는 SELECT ... WHERE ... ORDER BY로 하던 일을, 여기서는 중첩된 JSON 구조로 다시 표현해야 합니다. 여기서 문제가 되는 지점은 러닝커브입니다. SQL에 익숙한 개발자·분석가가 단순히 데이터를 확인하려는 목적인데도 Query DSL을 처음부터 배워야 하는 진입 장벽이 생깁니다. 도구도, 스킬도, 이미 SQL 쪽으로 맞춰져 있는데 검색만 DSL로 갈아타야 한다면 비효율적이죠.

2질문 제기

그럼 핵심 질문을 정확히 하나만 정하고 가겠습니다. 익숙한 SQL 문법으로 OpenSearch 데이터를 질의할 수 있게 하려면 어떻게 해야 할까요?

3구조적 핵심 예시

하나의 예시를 정확히 보고 가겠습니다. 예를 들어 로그 인덱스 my-index에서 5월 이후에 발생한 오류 로그만 뽑고 싶다고 합시다. 여러분은 DSL 대신 다음과 같이 씁니다. SELECT timestamp, message FROM my-index WHERE severity = 'ERROR' AND timestamp > '2026-05-01' ORDER BY timestamp DESC. 이 문장은 명령 도구나 SQL 작업 영역 같은 REST API를 통해 OpenSearch에 전달됩니다. 그러면 OpenSearch의 SQL 엔진이 이 문장을 받아서 내부적으로 질의 계획을 세우고, 이 인덱스에 맞는 검색 실행으로 바꿔 결과를 테이블 형태로 돌려줍니다. 이 구조가 핵심입니다. 여러분이 쓰는 건 전적으로 SQL이고, SQL을 검색으로 변환하는 일은 전부 OpenSearch 쪽에서 일어납니다. 결과도 표 형태로 나오니 익숙하게 읽을 수 있습니다.

4단계별 동작 과정

  1. 질의 전송SQL 문장을 REST API의 SQL 엔드포인트로 보내거나 SQL 작업 영역 같은 도구에서 실행합니다. 이 시점의 질의는 여전히 평범한 문자열입니다.
  2. 파싱과 변환OpenSearch가 SQL을 파싱해 검증하고, 내부 질의 계획으로 만든 뒤 해당 인덱스에서 실행할 검색 질의로 변환합니다. 앞 단계에서 받은 문자열이 이제야 실제 검색 실행 계획이 되는 겁니다.
  3. 결과 반환검색이 실행되어 매칭된 문서가 테이블 형태의 결과로 돌아오고, 집계·정렬 같은 SQL 기능도 함께 적용됩니다. 이 결과가 곧 여러분이 보는 최종 응답입니다.

5본질 요약

자, 본질을 정확히 한 문장으로 정리하겠습니다. 이 기술사용자가 익숙한 SQL 문장을 던지면 OpenSearch가 내부에서 검색 질의로 변환해 실행하고 표 형태로 결과를 돌려주는 것입니다. 이 문장을 기준으로 나머지를 이해하면 됩니다

크로스 클러스터 검색

여러 OpenSearch 클러스터(도메인)에 흩어진 인덱스를 하나의 질의로 함께 검색할 수 있게 하는 기능이다.

1상대의 출발점 확인

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 여러 OpenSearch 도메인에 걸친 검색, 크로스 클러스터 검색에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. 지금까지 여러분은 하나의 도메인, 하나의 클러스터 안에 있는 인덱스만 검색해 왔습니다. 질의를 보내면 그 도메인 안의 샤드들만 검색되고, 다른 도메인에 있는 데이터는 애초에 검색 대상에 포함되지 않습니다. 그런데 서비스를 운영하다 보면 데이터가 한 도메인에만 있는 경우는 드뭅니다. 리전을 달리해 재해 복구용으로 복제해 둔 경우, 팀별로 도메인을 각자 쓰는 경우, 데이터 성격에 따라 인덱스를 도메인별로 나눠 둔 경우 — 실제 데이터는 여러 도메인에 흩어져 있습니다. 여기서 문제가 되는 지점은 이 흩어진 데이터를 한 번에 보려면 클라이언트가 각 도메인을 일일이 질의하고 결과를 직접 합쳐야 한다는 것입니다. 두 번 호출하고, 중복을 정리하고, 정렬을 다시 해야 하는데 이건 검색이 아니라 잡일입니다.

2질문 제기

그럼 핵심 질문을 정확히 하나만 정하고 가겠습니다. 여러 클러스터에 흩어진 인덱스를 마치 하나의 클러스터인 것처럼 한 번의 질의로 검색하려면 어떻게 해야 할까요?

3구조적 핵심 예시

하나의 예시를 정확히 보고 가겠습니다. 서울에 주문 도메인, 도쿄에 재고 도메인이 있다고 합시다. 여러분은 "서울에 있고 도쿄에 재고가 남은 상품"을 찾으려고 합니다. 크로스 클러스터 검색을 쓰면 하나의 질의만 던지면 됩니다. 질의가 도착하는 곳은 연결 대상 클러스터입니다. 연결 대상이 각 클러스터를 검색하고, 그 결과를 모아서 하나의 응답으로 돌려줍니다. 이 구조가 핵심입니다. 질의 자체는 한 번이고, 여러 클러스터로의 실행과 결과 병합은 전부 연결 대상 클러스터가 처리합니다. 클라이언트 입장에서는 인덱스가 어느 도메인에 있는지조차 몰라도 됩니다. 그냥 인덱스 이름으로 질의하면 그 인덱스가 어디 있든 찾아주는 겁니다.

4단계별 동작 과정

  1. 연결 설정검색 대상이 되는 도메인을 outbound 연결로 등록합니다. 대상 도메인 쪽에는 inbound 연결 허용이 설정되어 있어야 합니다. 이 단계가 끝나야 두 도메인 사이에 통신 경로가 생깁니다.
  2. 질의 실행과 분산연결 대상 클러스터에 질의를 보내면 그것이 outbound 연결을 통해 여러 원격 클러스터의 샤드에 병렬로 전달되어 실행됩니다. 앞 단계에서 맺은 연결이 이제야 실제 검색 트래픽을 운반하는 겁니다.
  3. 결과 병합 반환각 클러스터가 돌려준 결과를 연결 대상 클러스터가 모아 점수·정렬 기준에 맞춰 병합해 하나의 검색 응답으로 돌려줍니다. 클라이언트가 받는 것은 여러 번 질의한 흔적 없는 단일 결과입니다.

5본질 요약

자, 본질을 정확히 한 문장으로 정리하겠습니다. 이 기술클러스터 사이에 연결을 맺어 두고, 클라이언트가 한 번 던진 질의를 연결 대상이 여러 클러스터에 분산 실행한 뒤 결과를 병합해 돌려주는 것입니다. 이 문장을 기준으로 나머지를 이해하면 됩니다

Learning to Rank

검색 결과의 순위를 사용자 상호작용·피드백 데이터로 기계학습 모델을 학습시켜 개선하는 기능이다.

1상대의 출발점 확인

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 기계학습으로 검색 순위를 개선하는 Learning to Rank에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. 지금까지 검색 결과의 순서는 관련성 점수, 즉 BM25 같은 수식이 결정했습니다. 이 수식은 질의와 문서의 단어 매칭을 토대로 점수를 계산합니다. 그런데 이 방식에는 눈에 보이는 한계가 있습니다. 수식은 "사람이 실제로 어떤 결과를 선호했는지"를 전혀 알지 못합니다. 예를 들어 "아이폰"을 검색했을 때 단어 매칭만으로는 어떤 상품 문서가 더 잘 팔리는지, 사용자가 어떤 결과를 실제로 클릭했는지는 점수에 들어가지 않습니다. 일반 사용자가 검색에서 기대하는 순서와 단어 매칭 점수 순서는 꽤 자주 어긋납니다. 여기서 문제가 되는 지점은 관련성의 판단 기준이 "단어의 일치"에 고정되어 있어, 실제 사용자 행동에서 얻을 수 있는 정보를 전혀 활용하지 못한다는 것입니다. 매칭이 아니라 만족, 그걸 점수에 담을 방법이 없는 상태입니다.

2질문 제기

그럼 핵심 질문을 정확히 하나만 정하고 가겠습니다. 사용자의 실제 상호작용과 피드백으로 검색 순위를 학습시켜 관련성을 높이려면 어떻게 해야 할까요?

3구조적 핵심 예시

하나의 예시를 정확히 보고 가겠습니다. 쇼핑 검색에서 "무선 이어폰"이라고 검색한다고 합시다. 수백 개 문서가 검색되지만, 사용자들은 로그를 보면 특정 브랜드의 결과를 압도적으로 많이 클릭합니다. 기존 방식은 이 정보를 모릅니다. Learning to Rank에서는 이 관찰 가능한 행동을 학습 데이터로 만듭니다. 클릭·구매 같은 상호작용에서 "어떤 문서가 더 나은 결과였는가"라는 순서 정보를 뽑아서, 그 데이터로 모델을 학습시킵니다. 그리고 검색이 실행될 때, 이 모델이 잠재 후보 문서들의 순서를 다시 매겨 최종 결과를 정렬합니다. 이 구조가 핵심입니다. 단어 매칭 수식이 1차 후보를 뽑고, 학습된 모델이 그 후보들의 순서를 실제 사용자 선호에 맞게 바꾸는 것, 이 두 단계가 합쳐져서 순위가 결정됩니다.

4단계별 동작 과정

  1. 학습 데이터 준비클릭·구매 같은 사용자 상호작용 로그를 정제해, 질의마다 어떤 문서가 더 선호되었는지 순서 정보가 담긴 학습 데이터로 만듭니다. 이 데이터가 곧 모델이 배울 "답"입니다.
  2. 모델 학습과 연결그 데이터로 XGBoost 같은 기계학습 모델을 학습시키고, 학습된 모델을 OpenSearch 플러그인에 등록해 도메인과 연결합니다. 앞 단계에서 만든 데이터가 이제야 순위를 매기는 능력으로 바뀌는 겁니다.
  3. 검색에 적용검색 질의가 들어오면 먼저 기본 검색으로 후보 문서들을 모으고, 이어서 학습된 모델이 그 후보들의 순서를 다시 매겨 최종 결과를 반환합니다. 이후 사용자의 새 행동이 다시 로그로 쌓이며 학습 데이터에 보태집니다. 이 결과가 곧 개선된 검색 순위입니다.

비동기 검색과 Point in time

큰 질의를 백그라운드에서 처리하는 비동기 검색과, 특정 시점의 일관된 인덱스 상태(PIT) 위에서 페이징 검색을 가능하게 하는 기능이다.

1상대의 출발점 확인

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 큰 질의를 처리하는 비동기 검색과 Point in time에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. 지금까지 여러분은 _search API에 질의를 보내고, 응답이 올 때까지 기다렸습니다. 이건 동기식 동작입니다. 그런데 이 방식이 부담스러워지는 순간이 있습니다. 검색 대상이 수십억 건으로 커지면, 질의 하나를 처리하는 데 1분, 2분이 걸리는 상황이 생깁니다. 여러분은 그 시간 동안 연결을 붙잡고 기다려야 하고, 결과가 늦게 오면 클라이언트는 타임아웃을 내며 끝나버립니다. 페이징을 한다면 이야기는 더 복잡해집니다. 페이지를 넘기는 동안 뒤에서 데이터가 계속 바뀌면, 1페이지에서 본 결과와 2페이지에서 본 결과가 서로 다른 시점의 상태라 일관성이 깨집니다. 여기서 문제가 되는 지점은 두 가지입니다. 하나는 큰 질의를 기다리며 묶여 있는 시간, 다른 하나는 페이지가 넘어가는 동안 흔들리는 데이터의 일관성입니다.

2질문 제기

그럼 핵심 질문을 정확히 하나만 정하고 가겠습니다. 오래 걸리는 질의를 기다리지 않고도 처리하고, 페이징 중에도 일관된 결과를 보려면 어떻게 해야 할까요?

3구조적 핵심 예시

하나의 예시를 정확히 보고 가겠습니다. 여러분이 수십억 건의 이벤트 로그에서 조건에 맞는 건을 뽑는 대시보드를 만든다고 합시다. 동기 검색이라면 대시보드는 수 분 동안 그냥 멍하니 기다려야 합니다. 비동기 검색에서는 질의를 보내면 즉시 작업 ID가 돌아옵니다. 그동안 서버는 백그라운드에서 질의를 진행하고, 여러분은 다른 작업을 하다가 상태 확인 요청으로 결과가 준비되었는지 확인하고, 준비되면 결과를 받습니다. 페이징은 여기서 한 겹 더 얹힙니다. 검색을 시작할 때 IT(Point in time)라는 것을 열어 둡니다. 이건 검색을 시작한 그 시점의 인덱스 상태를 고정해 두는 것입니다. 이 고정 상태 위에서 페이지를 넘기면, 뒤에서 데이터가 아무리 바뀌어도 여러분이 보는 결과는 시작 시점의 일관된 모습입니다. 이 구조가 핵심입니다. 긴 작업은 백그라운드로 돌리고, 일관성은 특정 시점 스냅샷으로 보장한다. 이 두 가지가 합쳐져서 생기는 것이 바로 이 기능의 전부입니다.

4단계별 동작 과정

  1. 비동기 질의 시작질의를 비동기 검색 API로 보내면 즉시 작업 ID를 받고, 동시에 검색을 시작한 시점의 인덱스 상태로 PIT가 열립니다. 이 시점부터 여러분은 기다리지 않아도 되고, 결과의 기준 시점도 고정됩니다.
  2. 상태 확인과 결과 수신작업 ID로 진행 상태를 확인하다가 완료가 확인되면 결과를 받습니다. 앞 단계에서 돌려받은 ID가 이제야 결과를 찾아가는 열쇠가 되는 겁니다.
  3. PIT 위에서 페이징열려 있는 PIT를 기준으로 페이지 단위로 결과를 이어서 가져오고, 작업이 끝나면 PIT와 비동기 작업을 정리합니다. 이 결과가 곧 시작 시점 기준으로 일관된 전체 검색 결과입니다.

자, 본질을 정확히 한 문장으로 정리하겠습니다. 이 기술오래 걸리는 질의를 작업 ID만 남기고 백그라운드에서 돌리면서, 특정 시점에 고정한 인덱스 상태(PIT) 위에서 일관된 페이징 결과를 얻는 것입니다. 이 문장을 기준으로 나머지를 이해하면 됩니다

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 ML 기반 검색, 시맨틱·에이전틱·자연어 검색에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. 지금까지의 검색은 모두 키워드 매칭이었습니다. 여러분이 "노트북이 너무 느린데"라고 검색해도, 시스템은 "노트북"과 "느리"라는 단어가 문서에 같은 단어로 들어 있는지, 그리고 BM25 점수로 얼마나 일치하는지만 봅니다. 단어가 정확히 일치하지 않으면 아무리 의미가 같아도 결과에서 밀려납니다. 예를 들어 "배터리가 빨리 닳는 폰"이라는 질의로 "배터리 수명이 짧은 휴대전화"라는 문서를 찾으려면 키워드 매칭만으로는 이 둘이 같은 뜻이라는 사실을 알 방법이 없습니다. 여기서 문제가 되는 지점은 검색이 단어의 철자에만 반응한다는 것입니다. 의미를 이해하지 못하니까, 같은 뜻을 다른 말로 쓴 문서들은 검색에서 빠져버립니다. 그리고 질의를 만드는 것조차 사용자의 몫이라, 검색 의도가 복잡해지면 표현을 어떻게 해야 할지도 골치아파집니다.

"배터리가 빨리 닳는" 질의의 벡터와 "배터리 수명이 짧은" 문서의 벡터가 의미상 가까우면, 철자가 전혀 달라도 검색에서 매칭됩니다. 여기서 에이전틱 검색이 한 단계 더 갑니다. 사용자가 자연어로 "최근 3일간 결제 실패한 사용자 좀 알려줘"라고 하면, 에이전트가 그 의도를 받아 스스로 질의를 구성하고 필요한 인덱스에 실행합니다. 자연어 검색은 이걸 한 번 더 단순화해서, 사용자의 평범한 질문 문장을 검색 시스템이 이해할 수 있는 질의로 만들어 줍니다. 이 구조가 핵심입니다. 단어를 의미 벡터로 바꾸는 임베딩, 그리고 질의 구성을 대신하는 에이전트·자연어 처리, 이 두 축이 기존 키워드 검색을 의미 기반 검색으로 끌어올립니다.

  3. 의미 기반 결과 반환유사도가 높은 문서부터 정렬해 결과를 돌려주고, 이 과정은 사용자가 검색한 의도와 의미상 가까운 문서부터 보여주는 결과로 끝납니다.

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 도메인에 데이터를 저장하지 않고 외부 소스를 직접 질의하는 Direct Queries에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. 지금까지는 데이터를 검색하려면 먼저 그 데이터를 OpenSearch 도메인 안으로 들여와야 했습니다. Index State Management

7단계 인덱스 관리와 스토리지 계층

다른 클러스터나 리전으로 인덱스를 실시간 복제(cross-cluster replication)하거나 원격 인덱스에서 다시 색인(remote reindex)하는 기능.

1상대의 출발점 확인

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 복제와 재색인에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. 인덱스는 하나의 클러스터, 하나의 리전 안에 묶여 있습니다. 그래서 데이터를 다른 지역으로 옮기거나 다른 환경으로 나르려면 덤프를 떠서 옮기고 다시 올리는 식의 번거로운 절차가 필요했던 것이죠. 여기서 문제가 되는 지점은 바로 그 이동 과정에서 데이터가 멈춰 있고, 실시간성이 전혀 보장되지 않는다는 것입니다.

2질문 제기

그럼 여기서 물어봅시다. 운영 중인 인덱스를 멈추지 않고 다른 클러스터나 리전으로 실시간으로 옮길 수는 없을까요?

3구조적 핵심 예시

하나의 예시를 정확히 보고 가겠습니다. 서울 리전에서 운영 중인 클러스터의 인덱스를 도쿄 리전의 클러스터로 계속 따라가게 만든다고 해 봅시다. 리더 역할을 하는 원본 클러스터의 인덱스에 새 문서가 들어오면, 그 변경이 팔로워 클러스터의 복제 인덱스로 흘러들어가 똑같이 반영됩니다. 혹은 원격 인덱스를 대상으로 다시 색인을 돌리면, 원본 인덱스의 문서를 읽어 다른 클러스터의 인덱스에 처음부터 다시 색인해 넣습니다. 기존 데이터를 그대로 두고 복제본이 따로 자라나는 구조, 이 구조가 핵심입니다.

4단계별 동작 과정

저장 데이터(encryption at rest)와 노드 간 전송 데이터를 AWS KMS 키로 암호화해 무단 열람을 막는 기능이다.

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 암호화에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. 여러분이 도메인에 데이터를 넣으면, 그 데이터는 디스크에 그대로 저장되고 노드 사이를 이동하는 동안 평문 그대로 오갑니다. 도메인 밖으로 나가지 않으니 안심이 될 수 있겠지만, 물리적 디스크나 볼륨 스냅샷에 접근할 방법이 생기면 데이터가 그대로 노출되게 되시겠죠. 여기서 문제가 되는 지점은 저장 중인 데이터와 전송 중인 데이터가 아무런 조치 없이는 암호화되어 있지 않다는 것입니다.

하나의 예시를 정확히 보고 가겠습니다. MCP, 즉 Model Context Protocol은 에이전트가 외부 데이터에 접근하는 표준 규약입니다. OpenSearch가 MCP 서버를 제공하면, 에이전트는 이 프로토콜을 통해 인덱스 목록과 데이터를 조회하는 도구들을 사용할 수 있게 됩니다. 여기에 에이전트 스킬을 더하면, 에이전트가 특정 작업을 수행하는 방법을 미리 정의된 지침으로 받아 예를 들어 로그 분석을 올바른 순서로 실행할 수 있습니다. 이 서버와 스킬의 조합이 핵심입니다.

4단계별 동작 과정

과정을 단계별로 정확히 정리하겠습니다. - MCP 서버 연결 — 에이전트가 OpenSearch가 제공하는 MCP 서버에 표준 프로토콜로 연결합니다. 이후의 데이터 접근이 이 연결을 통해 이뤄집니다. - 에이전트 스킬 적용 — 에이전트가 작업에 맞는 스킬의 지침을 받아 조회·분석 순서를 정합니다. 어떤 도구를 어떤 절차로 쓸지가 여기서 결정됩니다. - 데이터 조회·분석 수행 — 에이전트가 제공된 도구와 스킬로 OpenSearch 데이터를 조회하고 분석해 결과를 돌려줍니다.

5본질 요약

본질을 정확히 한 문장으로 정리하겠습니다. 이 기능에이전트가 OpenSearch의 데이터를 조회·분석할 수 있게 해주는 MCP 서버와 에이전트 스킬을 제공하는 것입니다. 이 문장을 기준으로 나머지를 이해하면 됩니다

Security Analytics

보안 로그에서 위협을 탐지·조사하고 대응 흐름을 자동화하도록 돕는 보안 분석 기능.

1상대의 출발점 확인

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 Security Analytics에 대해 함께 확인해 보겠습니다. 먼저 기존 방식의 동작을 정확히 보겠습니다. 보안 로그를 다룰 때는 로그를 OpenSearch 도메인에 적재해 두고, 보안 담당자가 쿼리로 직접 위협을 찾아내거나 Logstash 파이프라인을 거친 별도 보안 도구를 따로 돌리는 방식이 일반적이었습니다. 이 방식은 탐지가 사람의 손에 달려 있고, 위협을 찾아도 조사와 대응이 수작업으로 끊겨 있었죠. 그래서 로그는 쌓이는데 위협이 발견되기까지 시간이 걸리고, 발견된 뒤에도 대응까지 이어지는 흐름이 자동화되지 않습니다. 여기서 문제가 되는 지점은 탐지·조사·대응이라는 세 작업이 도구와 업무상 모두 분리되어 있다는 것입니다.

2질문 제기

핵심 질문을 정확히 하나만 정하고 가겠습니다. 보안 로그에서 위협을 탐지하고 조사하고 대응하는 흐름을 하나의 OpenSearch 도메인 안에서 자동화할 수 있지 않을까요?

3구조적 핵심 예시

하나의 예시를 정확히 보고 가겠습니다. 도메인에 VPC Flow 로그와 CloudTrail 로그가 수집되어 있다고 합시다. Security Analytics는 이 로그 유형에 맞는 탐지 규칙을 정기적으로 실행해서 위협 신호를 찾아내고, 발견된 위협은 Finding(탐지 결과)으로 기록된 뒤 Correlated Query(여러 로그를 이어 붙여 보는 조사 쿼리)로 그 원인을 추적합니다. 마지막으로 이 결과가 OpenSearch Alerting의 알림과 자동 대응 동작으로 넘어가죠. 로그 유형 → 탐지 규칙 → 조사 → 알림·대응이 한 파이프라인으로 이어지는 이 구조가 핵심입니다. 사람이 쿼리를 돌려 찾는 것이 아니라 규칙이 계속 돌면서 위협을 찾고, 그 결과가 자동으로 다음 단계로 흘러갑니다.

4단계별 동작 과정

과정을 단계별로 정확히 정리하겠습니다. - 데이터 소스와 탐지 규칙 구성 — 먼저 보안 로그 유형(예: VPC Flow, CloudTrail, DNS)을 도메인에 수집하고, 해당 로그에서 위협을 찾아낼 탐지 규칙을 지정합니다. Security Analytics는 Sigma 규칙(공개 보안 탐지 규칙 표준) 기반의 규칙을 지원하며, 이 규칙이 이후 모든 탐지의 기준이 됩니다. - 탐지 실행과 Finding 생성 — 규칙이 로그에 대해 주기적으로 실행되어 위협 신호를 탐지하고, 탐지된 위협은 Finding(탐지 결과 레코드)으로 기록됩니다. 이 Finding이 다음 단계의 입력이 됩니다. - 조사와 대응 자동화 — Finding을 조사하기 위한 Correlated Query(여러 인덱스·로그를 연결해 위협 흐름을 추적하는 쿼리)를 수행하고, 그 결과를 Alerting의 알림 채널(이메일·웹훅)과 자동 대응 동작으로 연결해 대응 흐름을 마무리합니다.

5본질 요약

본질을 정확히 한 문장으로 정리하겠습니다. Security Analytics의 본질은 보안 로그에서 위협을 탐지·조사하고 대응 흐름을 자동화하도록 돕는 보안 분석 기능입니다. 이 문장을 기준으로 나머지를 이해하면 됩니다. 로그가 들어오면 규칙이 탐지하고, 조사가 이어지고, 알림과 대응까지 자동으로 흘러간다는 것, 그 하나만 기억하시면 됩니다.

1상대의 출발점 확인

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 모범 사례와 사이징에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. 도메인을 처음 만들 때 대부분 저장 용량이 얼마나 될지, 샤드(인덱스를 나누는 단위)를 몇 개로 할지, 인스턴스 유형을 무엇으로 할지 대략적으로 정하고, 운영하면서 문제가 생기면 그때그때 키우는 방식으로 갑니다. 그런데 이 방식은 데이터가 커질수록 샤드 하나에 부하가 몰리고, 인스턴스 사양이 저장 용량에 맞지 않아 성능이 떨어지거나 반대로 낭비가 생깁니다. 큰일 나기 전까지는 티가 안 나지만, 어느 순간 클러스터가 불안정해지기 시작합니다. 여기서 문제가 되는 지점은 용량·샤드·인스턴스가 서로 독립적으로 정해진다는 것입니다.

4단계별 동작 과정

과정을 단계별로 정확히 정리하겠습니다. - 저장 용량 산정 — 원본 데이터의 크기와 복제본(레플리카) 수, 워밍 데이터·콜드 데이터의 보관 기간을 고려해 도메인이 담아야 할 전체 저장 용량을 산정합니다. 이 값이 이후 모든 산정의 출발점이 됩니다. - 샤드 수 산정 — 산정된 용량을 샤드 하나당 권장 크기(공식 지침의 이상적인 범위)로 나누어 샤드 수를 정합니다. 샤드가 너무 많으면 오버헤드가, 너무 적으면 샤드당 부하가 생기므로 여기서 균형을 잡습니다. - 인스턴스 유형 선택 — 정해진 샤드 수가 요구하는 힙 메모리와 CPU를 감당할 수 있는 인스턴스 유형을 골라 도메인에 배치합니다. 이 단계에서 비로소 용량·샤드·인스턴스가 하나의 산정 사슬로 완성됩니다.

비용 최적화와 전용 노드

Reserved Instance·UltraWarm 같은 비용 절감 방안과 전용 코디네이터·마스터 노드 배치를 다루는 비용·아키텍처 지침.

1상대의 출발점 확인

자, 여러분 만나서 반갑습니다. 자, 이번 시간에는 비용 최적화와 전용 노드에 대해 함께 확인해 보겠습니다. 기존 방식의 동작을 정확히 보겠습니다. 기본적인 구성은 모든 데이터를 확장 검색 스토리지(핫 스토리지)에 두고, 인스턴스를 온디맨드(사용한 만큼 비용을 내는 방식)로 쓰며, 마스터 노드와 코디네이터 노드 역할까지 데이터 노드가 전부 겸하는 형태입니다. 이 방식은 자주 조회하지 않는 오래된 데이터까지 비싼 저장소에 계속 보관하고, 노드 하나에 역할이 몰려 있어 비용도 안정성도 모두 아쉽습니다. 데이터가 쌓이면 쌓일수록 지출은 계속 커지고, 노드 하나가 죽으면 역할까지 한꺼번에 흔들리게 되죠. 여기서 문제가 되는 지점은 저장·청구·역할이라는 세 축이 모두 분리되어 있지 않다는 것입니다.

2질문 제기

핵심 질문을 정확히 하나만 정하고 가겠습니다. 비용을 줄이면서도 도메인의 안정성을 유지하려면 저장소와 청구 방식과 노드 역할을 각각 어떻게 나눠야 할까요?

3구조적 핵심 예시

하나의 예시를 정확히 보고 가겠습니다. 조회 빈도가 낮아진 오래된 인덱스를 UltraWarm(저비용 온라인 스토리지 계층)으로 옮기고, 온디맨드 대신 Reserved Instance(사전 약정 할인 인스턴스)를 도입해 고정 워크로드의 비용을 미리 낮춥니다. 동시에 마스터 노드와 코디네이터 노드를 데이터 노드와 분리해 전용 노드로 배치합니다. 저장 계층을 나누고 청구 방식을 약정하고 역할을 분리하는, 이 세 개가 동시에 맞물리는 구조가 핵심입니다. 어느 하나만 바꾸면 비용은 줄지만 안정성이 흔들리거나, 안정성만 챙기면 비용이 그대로입니다.

4단계별 동작 과정

과정을 단계별로 정확히 정리하겠습니다. - 스토리지 계층 분리 — 자주 조회하는 데이터는 핫 스토리지(확장 검색 스토리지)에 두고, 조회 빈도가 낮은 데이터는 UltraWarm(저비용 온라인 스토리지 계층)으로 이동시켜 저장 비용부터 줄입니다. 이 분리가 이후 청구와 노드 결정의 바탕이 됩니다. - 청구 방식 최적화 — 온디맨드 상태로 두었던 인스턴스 중 사용량이 안정적인 부분을 Reserved Instance(일정 기간을 약정하고 할인받는 청구 방식)로 전환합니다. 이 단계는 앞서 정리된 스토리지 계층의 워크로드 규모를 받아서 진행됩니다. - 전용 노드 배치 — 클러스터 관리(마스터 노드)와 클라이언트 요청 중계(코디네이터 노드)를 데이터 노드에서 분리해 전용 노드로 배치합니다. 이로써 데이터 노드의 부하가 줄고, 역할이 한 노드에 몰려 생기던 안정성 위험이 제거되며 비용 구조가 완성됩니다.

5본질 요약

본질을 정확히 한 문장으로 정리하겠습니다. 비용 최적화와 전용 노드Reserved Instance·UltraWarm 같은 비용 절감 방안과 전용 코디네이터·마스터 노드 배치를 통해 비용과 안정성을 함께 확보하는 아키텍처 지침입니다. 이 문장을 기준으로 나머지를 이해하면 됩니다. 저장은 나누고, 청구는 약정하고, 역할은 분리한다, 그 세 축만 기억하시면 됩니다
