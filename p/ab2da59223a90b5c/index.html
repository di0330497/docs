Amazon EC2

Amazon EC2(Amazon Elastic Compute Cloud)를 AWS 리전 안에서 가상 컴퓨터(인스턴스)를 필요한 만큼 띄우고 그 라이프사이클·네트워크·저장소·보안까지 관리하는 컴퓨트 서비스로 해석했다. 순서는 무엇을 띄우는가(EC2·리전·파라미터·launch template) → 무엇을 띄울지(AMI) → 어떤 크기로 띄울지(instance type) → 얼마에 띄울지(요금·Spot·전용 호스트) → 띄우고 붙는가(실행·접속) → 그 인스턴스의 수명주기(정지·hibernate·종료·복구·metadata) → 디스크와 네트워크 → 여러 대를 한 번에(EC2 Fleet·Spot Fleet·placement group) → 들어오는 것을 막고(키 페어·보안 그룹·IAM role·NitroTPM) → 상태를 보고 고치다(지표·이벤트·직렬 콘솔)로 잡았다. Linux/Windows 별 운영 세부, 디바이스 드라이버, GPU 드라이버 설치, STIG 스크립트 같은 문서는 항목이 아니라 세부 절차로 보고 excluded 에 사유를 적었다.

Amazon EC2 란 무엇인가 — 가상 컴퓨터를 빌리는 것

Amazon EC2(Elastic Compute Cloud)는 AWS 클라우드에서 실제 서버 장비를 직접 소유하지 않고도, 필요할 때 네트워크와 저장소가 붙은 가상 컴퓨터(인스턴스)를 시간 단위로 빌려 쓰고 반납하는 서비스다.

#1문제 상황

회사가 서버를 사려면 주문하고 자료실에 두고 운영체제를 설치하고 전원을 켜야 한다. 오래 걸리고 비용도 미리 고정된다.

Amazon EC2는 이 장비를 직접 사지 않고 빌린다. EC2 instance는 AWS 클라우드 안에서 도는 virtual server이며, 필요할 때 필요한 만큼 만들고 필요 없어지면 반납한다.

#2핵심 질문

서버 장비를 사지 않고 원하는 때에 빌려 쓰려면 어떻게 해야 할까?

#3동작 예시

결제 처리 프로그램에 요청이 몰리면 서버가 모자란다. 운영자가 콘솔에서 인스턴스를 5대 추가로 시작한다.

몇 분 뒤 EC2 콘솔의 running 목록에 5대가 나타나고, 각 인스턴스에 미리 지정한 IP 주소로 접속해 된다.

#4동작 과정

  1. 인스턴스를 시작한다고를 instance type이 정하는 하드웨어 사양을 갖는 가상 서버를 띄운다. AMI는 부팅할 운영체제 패키지이고, 이 계층의 저장소를 instance store라 한다.
  2. 보안과 네트워크를 입힌다security group은 인스턴스로 들어오는 트래픽을 출발 IP와 포트로 걸러 내는 가상 방화벽이다. elastic IP address는 인스턴스를 붙였다 떼어도 남는 고정 IP 주소로, 다른 곳에서 같은 주소로 계속 접속하게 해 준다.
  3. 반납한다쓰던 인스턴스를 종료하면 할인을 끝낸다. 처리량이 늘면 다시 늘리고 줄이면 다시 줄이는 식으로 용량을 바꾼다.
  4. 확인해 볼 것콘솔 인스턴스 목록에서 상태가 running으로 표시되는 행이 새로 생겼는지 확인한다.

리전과 가용 영역 — 어디에 띄울지

리전(Region)은 AWS의 독립된 지리 단위인 데이터 센터 묶음이고, 그 안에 있는 독립 데이터 센터 하나하나가 가용 영역(Availability Zone, AZ)이며, 각 리전은 보통 3개 이상의 AZ로 구성된다.

그래서 AWS는 지리적으로 떨어진 여러 Region과, 그 Region 안에 서로 분리된 여러 Availability Zone으로 나뉜다. 한쪽이 멈춰도 다른 쪽에서 인스턴스를 다시 띄울 수 있는 구조다.

그 안에서 zonal 인스턴스를 만들면 가까운 가용 영역 하나가 정해지고, Region 전체를 아우르는 Regional 자원은 여러 가용 영역에 흩어져 놓인다.

  2. Availability Zone을 확인한다Region 안에는 전력이 따로 들어오는 독립 데이터 센터가 여러 개 있고, 하나의 Region은 보통 그 셋 이상으로 이루어진다. 서로 독립이라 한 곳의 장애가 전체로 번지지 않는다.
  3. AWS Global View로 바꾼다한 화면에서 여러 리전의 리소스를 같이 본다. 요구하는 데이터가 어떤 리전에서 쓰이는지 한 번에 확인할 수 있다.
  4. 확인해 볼 것리전 선택 목록에서 고른 리전 이름이 인스턴스 목록 화면 상단에 표시되는지 확인한다.

인스턴스 상태 변화 — pending 에서 terminated 까지

인스턴스는 시작 요청 후 pending, running(또는 stopped)의 stopped, shutting-down, terminated, stopping, rebooting, shutting-down-ebs, instance-reboot(EBSSupport) 같은 상태를 거치며 인스턴스 유형과 EBS 볼륨에 따라 변경되는 상태가 다르다.

먼저 알아야 할 것 01-03

#1문제 상황

인스턴스(→ 01-01)를 시작하고 나면 곧바로 쓸 수 있는 줄 알지만, 실제로는 준비 기간이 지난 뒤에야 준비가 된다. pending은 아직 준비 중이라 아직 과금되지 않는다.

그래서 인스턴스 상태 변화의 각 단계가 정해져 있고, 그 단계에 따라 과금되는지 달라진다. terminated는 삭제되어 다시는 쓸 수 없는 마지막 상태다. EBS 볼륨과 Elastic IP 주소는 상태와 상관없이 따로 과금된다.

#2핵심 질문

내 인스턴스는 지금 어느 상태에 있고 그 상태에서 비용이 발생하는가?

#3동작 예시

운영자가 중지된 인스턴스를 시작한다. 콘솔 상태가 pending으로 바뀌었다가 잠시 뒤 running으로 바뀐다.

그 인스턴스를 중지하면 stopping을 거쳐 stopped가 되고, 삭제하면 shutting-down을 거쳐 terminated가 되어 목록에서 사라진다.

#4동작 과정

  1. 시작을 건다새 인스턴스를 띄우거나 stopped에서 깨울 때 pending 상태가 된다. 아직 준비 중이라 과금되지 않는다.
  2. 쓸 수 있게 된다running 상태는 실행되어 바로 쓸 수 있다는 뜻이고, 이때부터 과금된다.
  3. 멈추거나 없앤다stopping을 거쳐 stopped가 되고, 삭제하면 shutting-down을 거친 뒤 terminated가 되어 다시는 쓸 수 없다. 상태가 바뀔 때마다 알림을 받을 수도 있다.
  4. 확인해 볼 것인스턴스 목록의 Status 열에서 상태가 pending에서 running으로 넘어가는 것을 본다.

AMI(Amazon Machine Image)는 인스턴스를 띄우기 위해 미리 만들어 둔 운영체제 패키지로, OS 와 애플리케이션이 들어 있는 루트 볼륨 템플릿과 어떤 볼륨·커널·시작 스크립트를 쓸지를 적은 매니페스트 정보로 이루어집니다.

먼저 알아야 할 것 01-03

#1문제 상황

#2핵심 질문

AMI는 무엇으로 이루어져 있고 어떤 기준으로 고르는가?

#3동작 예시

#4동작 과정

  1. 구성 정보를 읽는다manifest가 어떤 볼륨을 붙이는지와 커널, 시작 스크립트를 쓸지를 정한다. 이 연결 정보는 block device mapping으로 표현되어 어떤 디스크를 어느 슬롯에 붙는지 정한다.
  2. 부팅 방식을 고른다root volume type과 boot mode가 정해져 운영체제가 어느 방식으로 올라오는지 달라진다.
  3. 사용 권한을 확인한다launch permissions로 이 AMI를 누가 실행할 수 있는지 정한다. 소유 계정만 쓰거나 특정 계정이나 조직에 허용하거나 모두에게 공개한다.
  4. 확인해 볼 것AMI 검색 결과 목록에서 Region와 Architecture가 고른 조건과 같은지 확인한다.

먼저 알아야 할 것 02-01

#1문제 상황

AMI는 리전별 자원이므로 같은 이미지가 리전마다 다른 ID를 갖는다(→ 02-01). 운영체제와 아키텍처, 루트 볼륨 종류가 제각각인 이미지를 앞에서부터 뒤집어다녀야 한다.

#2핵심 질문

어느 리전에 어떤 사양의 AMI가 있는가?

#3동작 예시

목록에서 하나를 고르면 루트 볼륨 종류가 Amazon EBS인지 instance store인지 함께 보인다.

#4동작 과정

  1. 리전을 고른다콘솔 상단의 리전 선택으로 작업할 리전을 먼저 정한다. AMI ID는 리전 안에서만 유효하므로 이 단계가 기준이다.
  2. 조건을 좁힌다owner는 이미지를 만든 주체, architecture는 32비트·64비트·64비트 ARM 같은 CPU 규격이다. Amazon Linux처럼 AWS가 제공하는 이미지도 이 기준으로 골라 낸다.
  3. 다시 쓸 ID를 남긴다반복해서 쓰는 AMI ID는 Systems Manager parameters, 즉 이름으로 값을 꺼내 쓰는 설정 저장소인 Systems Manager 파라미터 스토어에 public parameters로 저장해 둔다. 스크립트에서 참조하게 되면 리전이 바뀌어도 ID를 한 군데서만 고치면 된다.
  4. 확인해 볼 것Images 페이지 목록에 고른 이미지의 owner와 아키텍처가 검색 조건과 맞게 표시되는지 확인한다.

AMI 를 만드는 것은 인스턴스를 만든 다음 EBS 볼륨을 스냅샷으로 찍고 그 스냅샷과 함께 매니페스트를 등록해, 해당 상태 그대로 다시 띄울 수 있는 이미지를 얻는 작업입니다.

먼저 알아야 할 것 02-01

#1문제 상황

설정을 한 인스턴스 상태로 매번 다시 만들려면 패키지 설치를 되풀이해야 한다. create an AMI는 그 상태를 그대로 이미지로 남긴다.

#2핵심 질문

맞춰 둔 인스턴스 상태를 어떻게 나중에 그대로 되풀이할까?

#3동작 예시

등록된 AMI로 새 인스턴스를 띄우면 보정 프로그램이 이미 깔려 있어 바로 서비스만 시작한다.

#4동작 과정

  1. 인스턴스를 준비한다기존 AMI로 띄운 EBS 기반 인스턴스(→ 02-01)에 필요한 패키지와 설정을 적용한다. 암호화된 볼륨과 평문 볼륨 모두 같은 절차를 쓴다.

  3. 다시 쓴다새 AMI로 인스턴스를 띄우면 같은 상태가 재현된다. Sysprep은 Windows 이미지를 다른 인스턴스에 올릴 수 있게 일반화해 주는 준비 단계다.
  4. 확인해 볼 것Images 목록에 방금 만든 AMI가 새 상태로 보이는지 확인한다.

AMI 복사·저장·복원

AMI 는 다른 리전이나 계정으로 복사할 수 있고, AWS Backup 같은 서비스로 저장했다가 필요할 때 복원할 수 있으며, 삭제로 사라지지 않도록 보관해 두는 방식입니다.

먼저 알아야 할 것 02-03

#1문제 상황

AMI는 리전에 묶인 자원이라(→ 02-01) 다른 리전에서 쓰려면 옮겨야 하고, 계정 간 공유를 위해 사본이 필요하다. 그대로 두면 실수로 지울 위험도 있다.

copying an AMI는 대상 리전이나 계정으로 같은 AMI를 복제하는 기능이다. encrypted AMI는 볼륨 암호화 키까지 함께 옮겨 갈 때 쓴다.

#2핵심 질문

필요한 리전과 계정에서 같은 AMI를 어떻게 확보하는가?

#3동작 예시

본사 리전에서 만든 표준 이미지(→ 02-03)를apsed 가까운 다른 리전에서도 쓰려 한다. Images 페이지에서 해당 AMI를 선택해 대상 리전을 고른다.

복사가 끝나면 대상 리전의 Images 목록에 같은 이름의 AMI가 두 개 볼륨과 함께 나타난다.

#4동작 과정

  1. 방법을 고른다같은 파티션 안의 리전 간 복사와, 파티션을 넘나드는 복사가 갈린다. 파티션을 넘기는 경우에는 store and restore an AMI 절차를 쓴다.
  2. 저장해 둔다AMI를 AWS Backup에 보관하면 필요할 때 되살릴 수 있다. 이때 실제로 도는 단위는 store image task 하나로, 복원이 이 작업 단위로 처리된다.
  3. 암호화를 유지한다encrypted AMI를 복사하면 암호화 상태를 유지한 채 볼륨이 넘어간다. how AMI copy works에 따라 EBS 볼륨과 매니페스트 순서로 진행되는 과정이 콘솔에 단계로 나타난다.
  4. 확인해 볼 것복사 대상 리전의 Images 목록에 새 AMI와 그 상태가 나타나는지 확인한다.

  2. 허용 목록으로 막는다allowed AMIs는 계정 수준에서 실행 가능한 이미지를 목록으로 한정하는 방식이다. 소유권을 넘기지 않고 통제할 때 쓴다.

먼저 알아야 할 것 02-04

#1문제 상황

공유한 이미지가 실제로 어디서 얼마나 쓰이는지 몰라 지울지 판단할 수 없다.(→ 02-05) 이미지에 담긴 데이터는 암호화되어 있어야 한다.

AMI encryption은 볼륨 스냅숏을 AWS KMS 키로 잠근다. AMI usage는 그 이미지를 참조한 계정과 리소스를 기록해 보여 준다.

#2핵심 질문

내 이미지가 어디에서 쓰이고 있는지와 데이터의 암호화 상태를 어떻게 함께 관리하는가?

#3동작 예시

공유해 둔 이미지 목록을 열자 recent activity 항목에 마지막 실행 시각과 실행한 계정이 보인다. 아무도 쓰지 않는 이미지가 눈에 띈다.

이미지를 만들 때 KMS 키를 지정했는지 다시 확인해 본다.

#4동작 과정

  1. 암호화한다AMI를 만들 때 AWS KMS 키를 지정하면 루트 볼륨을 포함한 EBS 볼륨과 스냅숏이 그 키로 암호화된다.
  2. 사용을 모은다AMI usage reports는 어떤 AWS 계정이 어떤 리소스 유형으로 내 AMI를 참조하는지 보여 준다. 공유받은 계정 범위를 넘어 본다.
  3. 시각을 잰다last launched time을 보면 마지막 사용 시점을 알 수 있어 AMI watermarks, 즉 기준선 아래로 떨어진 사용량을 다시 보고 정리 대상으로 지목할 수 있다.
  4. 확인해 볼 것이미지 상세의 사용 이력에 마지막 실행 시각이 표시되는지 확인한다.

인스턴스 유형과 세대 구분

인스턴스 유형은 CPU·메모리·네트워크·성능 등 사양의 조합을 미리 정해 이름(m5, c7g 등)으로 묶은 것으로, 이름 앞부분이 계열(용도), 숫자가 세대, 끝의 g가 그래픽 가속기 같은 추가 사양을 뜻합니다.

먼저 알아야 할 것 01-03

#1문제 상황

인스턴스를 띄우려면 CPU·메모리·디스크 사양을 골라야 하는데(→ 01-03) 조합이 너무 많아 무엇이 자신에게 맞는지 판단하기 어렵다.

instance types는 사양 조합을 미리 정해 이름으로 묶은 목록이다. instance family와 instance generation을 알면 이름만 보고 대략적인 용도와 세대를 읽는다.

#2핵심 질문

내 workload에 맞는 인스턴스 유형을 무엇 기준으로 고르는가?

#3동작 예시

웹 서버를 띄우기 전에 인스턴스 유형 목록에서 범용 계열을 고른다. 그래프를 보니 vCPU와 메모리가 예상 트래픽에 맞는다.

이후 비용이 아까워 더 싼 유형으로 바꾸고 싶을 때 EC2 instance type finder를 다시 열어 후보를 좁힌다.

#4동작 과정

  1. 계열로 거른다instance type은 인스턴스마다 다르고, 사용 사양에 따라 인스턴스별로 다르게 공유되거나 독점한다. 이 구분을 반영해 EC2 instance type finder에서 용도별 후보를 훑어 본다.
  2. 이름을 읽는다앞 글자는 계열, 숫자는 세대, 끝의 부수는 추가 사양(그래픽 가속기 등)을 뜻한다. 옛 세대 이름이 아직 쓰이는 이유를 여기서 안다.
  3. 추천을 받는다실제 사용량이 쌓이면 Compute Optimizer recommendations가 인스턴스를 더 크거나 작은 유형으로 바꾸는 제안을 준다.
  4. 확인해 볼 것유형 목록에서 선택한 항목의 vCPU 수와 메모리가 카드에 표시되는지 확인한다.

T 유형처럼 기본 성능보다 CPU 사용량을 왔다갔다하는 인스턴스로, 추가 CPU를 쓰면 credit을 소비하고 credit이 바닥나면 baseline 성능으로 낮아집니다.

먼저 알아야 할 것 03-01

#1문제 상황

대부분의 시간은 CPU를 조금만 쓰는 서버에 항상 같은 크기를 내면 용량이 놀고, 늘렸다 줄였다 하면 시간이 걸린다.

burstable performance instances는 T instance types로, baseline performance 위에 잠깐 더 쓸 수 있는 여유를 함께 산다. 이 여유를 CPU credits로 치환해 관리한다.

#2핵심 질문

평소엔 조용하고 가끔만 CPU를 쓰는 서버 비용을 어떻게 낮출까?

#3동작 예시

평소에는 10%만 쓰는 웹 서버가 유저 몰릴 때 100%를 쓴다. CloudWatch에서 InstanceCreditBalance 지표가 함께 쌓이고 쌓이는 것을 본다.

Credit이 바닥나 같은 크기의 M 유형에 비해 느려지는 순간이 온다.

#4동작 과정

  1. 기본을 정한다baseline performance는 일반적인 마이크로서비스·웹 서버·데이터베이스의 대다수가 요구하는 CPU 기준선이다.
  2. 넘쳐 쓰면 빌린다기준선을 넘게 CPU를 쓰는 만큼 CPU credits, 즉 기준선 이상의 CPU 시간을 미리 빌린 시간을 소비한다. 이 여유를 쌓아 두는 방식이다.
  3. 방식을 고른다standard mode는 크레딧이 떨어지면 baseline으로 낮춘다. unlimited mode는 크레딧 소모 대신 인접 호스트의 여유 CPU를 빌려 추가 요금으로 더 쓴다.
  4. 확인해 볼 것인스턴스 그래프에 CPUUtilization과 InstanceCreditBalance가 함께 표시되는지 확인한다.

EBS 최적화는 인스턴스와 별개로 EBS 볼륨 처리용 전용 대역폭과 처리량 할당을 미리 확보하는 옵션으로, 켜면 인스턴스 기본 네트워크를 건드리지 않고 디스크 I/O가 빨라집니다.

먼저 알아야 할 것 03-01

#1문제 상황

인스턴스는 네트워크로 들어오는 트래픽과 디스크로 나가는 입출력 데이터를 한꺼번에 처리한다(→ 03-01). 그래서 웹 요청이 몰리면 EBS 볼륨 읽기와 쓰기가 밀린다.

EBS optimization은 인스턴스 타입을 고를 때 enable EBS optimization을 켜 EBS 볼륨 처리 전용 대역폭과 처리량 할당을 따로 받게 한다. EBS-optimized instance types는 기본값으로 이 대역폭이 잡혀 있다.

#2핵심 질문

디스크 입출력이 네트워크 트래픽에 밀리지 않게 하려면 무엇을 켜야 할까?

#3동작 예시

DB 서버가 갑자기 느려졌다. CloudWatch에서 EBS 볼륨의 처리량이 임계치에 붙은 것을 본다.

인스턴스 사양에서 EBS optimization을 켠 타입으로 바꾸고 다시 측정하면, 같은 요청량에서도 볼륨 처리량이 안정적으로 유지된다.

#4동작 과정

  1. 유형을 고른다EBS-optimized instance types를 고르면 전용 대역폭이 이미 배정된 상태로 켜진다. 기본 제공 대역폭을 network baseline bandwidth라 하고, 그 위에 짧게 더 쓰는 처리량을 burst throughput이라고 한다.
  2. 연결해 확인한다gp3·io2 같은 볼륨을 붙이면 볼륨 종류별로 약속한 입출력 성능을 대부분 시간에 내준다. 못 내는 시간은 고르게 흩어져 있다.
  3. 확인해 볼 것인스턴스 사양 화면에 EBS optimized 항목이 켜져 있는지, EBS 볼륨 성능 그래프가 임계치에 묶이지 않는지 본다.

먼저 알아야 할 것 03-01

#1문제 상황

인스턴스 유형 이름만 고르면 그 유형이 가진 vCPUs가 전부 켜진다(→ 03-01). 코어를 다 쓰면 소프트웨어 라이선스 비용이 오른다.

CPU options은 코어 수와 threads per core를 직접 정해, 전체보다 적은 CPU만 쓰게 한다.

#2핵심 질문

필요한 코어만 남기고 나머지 CPU를 끄려면 어떻게 지정할까?

#3동작 예시

메모리는 넉넉한데 CPU를 다 쓰지 않는 서버가 있다. 라이선스 비용이 코어 수에 따라 달라서다.

CPU options으로 코어 수를 줄여 띄우면 라이선스를 낼 코어 수에 맞춰 잡히고, 나머지 메모리는 그대로 남는다.

#4동작 과정

  1. 코어를 정한다Number of CPU cores에 원하는 코어 수를 적는다. 이 값이 전체 vCPUs 중 쓸 수 있는 몫이 정해진다.
  2. SMT를 끌지 정한다threads per core를 1로 두면 SMT를 꺼 코어당 스레드를 하나만 쓴다. SMT는 물리 코어 하나에서 여러 스레드를 동시에 돌리는 기능이다.
  3. 확인해 볼 것인스턴스 사양에서 optimize CPUs 항목에 지정한 코어 수와 threads per core가 그대로 표시되는지 본다.

먼저 알아야 할 것 03-01

#1문제 상황

일반 인스턴스는 CPU만 계산한다(→ 03-01). 병렬 연산이 많은 학습·렌더링·암호 연산은 코어를 늘려도 빨라지지 않는다.

GPU는 여러 연산을 한꺼번에 나눠 처리하는 연산 전용 칩이고, Mac 인스턴스는 Apple Mac 하드웨어를 그대로 빌려 온다. 가속기 인스턴스는 이런 전용 하드웨어를 붙여 그 연산을 하드웨어에 맡긴다.

#2핵심 질문

병렬 연산이 많은 일을 CPU가 아닌 전용 하드웨어로 돌리려면 어떤 유형을 골라야 할까?

#3동작 예시

모델 학습 작업을 맡았다. GPU 인스턴스를 띄우고 NVIDIA 드라이버를 설치한 뒤 학습을 시작한다.

CUDA나 OpenCL 같은 병렬 연산 프레임워크가 GPU에서 돌아가 같은 학습이 훨씬 빠르게 끝난다.

#4동작 과정

  1. 유형을 고른다GPU instances는 물리 GPU를 붙인 유형이고, Mac instances는 Apple Mac 하드웨어를 그대로 띄운다. 암호 연산용 칩이 들어간 유형도 여기에 속한다.
  2. 드라이버를 넣는다NVIDIA나 AMD GPU를 쓰려면 해당 드라이버를 인스턴스에 설치한다. 보안 기능을 쓰는 유형은 AMD SEV-SNP로 메모리를 암호화하고 attestation으로 환경이 바르다는 증명을 낸다.
  3. 확인해 볼 것인스턴스에 디바이스 목록에서 GPU가 하나 붙어 인식되는지, 화면에 디스플레이 출력이 잡히는지 본다.

#3동작 예시

작은 인스턴스가 부족해 늘려야 한다. 인스턴스를 중지한 뒤 더 큰 유형을 고른다.

다시 시작하면 같은 EBS 볼륨으로 부팅되고, 운영체제가 새 크기에 맞춰 자동으로 맞춰진다. 다른 인스턴스로 갈아타려면 migrate to a new instance type로 옮긴다.

#4동작 과정

  1. 중지한다resize 전에 인스턴스를 중지한다. EBS 볼륨은 붙은 채 유지된다.
  2. 유형을 바꾼다콘솔이나 명령 줄에서 새 인스턴스 유형을 지정해 다시 시작한다. 바꾼 뒤에는 새 유형의 요금이 적용된다. 유형 간 호환 여부(compatibility)를 먼저 확인한다.
  3. 옮길 때 참고한다크기만 고치는 게 아니라 새 인스턴스로 데이터를 옮길 때는 migrate to a new instance type 절차로 진행한다. AWS Compute Optimizer가 적합한 유형을 추천해 준다.
  4. 확인해 볼 것인스턴스 화면에서 이전 유형과 현재 유형이 함께 보이고 상태가 running으로 올라갔는지 본다.

Spot Instances — 경매로 빌리는 여분 용량

AWS가 보유한 여분의 컴퓨팅 용량을 입찰 방식으로 싸게 빌리는 인스턴스로, 내가 설정한 입찰가가 현재 가격보다 높으면 그대로 실행되지만 그보다 낮아지면 남은 시간이 끝날 때까지 중단될 수 있다.

먼저 알아야 할 것 04-03

#1문제 상황

온디맨드(→ 04-02)는 필요한 만큼 빌릴 수 있지만 요금이 가장 비싸다. 미리 예약하는 방식(→ 04-03)도 평소 쓰지 않는 시간까지 값을 지불한다.

Spot Instances는 AWS가 보유한 남는 용량을 경매로 빌리는 방식이라 훨씬 싸게 떨어진다. 대신 실행 시점이 정해지지 않고 중단될 수 있어, 언제든 멈춰도 되는 작업에 맞춰야 한다.

#2핵심 질문

언제 멈춰도 괜찮은 작업을 AWS의 남는 용량으로 어떻게 싸게 돌리는가?

#3동작 예시

야간에 이미지 몇만 장을 변환하는 배치 작업을 짠다. 실행 시간이 정해져 있지 않고 도중에 멈춰도 다시 걸면 되므로, 이 작업을 Spot Instances로 요청한다.

평소보다 싼 값으로 여러 대가 동시에 붙고, 결과는 같은 오브젝트 저장소에 쌓인다.

#4동작 과정

  1. 요청한다Spot request를 넣어 인스턴스 유형과 가용 영역을 지정한다. one-time 또는 persistent 중 하나로 묶어 반복 요청 여부를 정하고, 최대 가격을 남기면 그 가격을 넘을 때 중단된다.
  2. 붙는다how Spot Instances work에 따라 용량이 있으면 Spot price로 인스턴스가 실행된다. 이 시간 단위 가격은 AWS가 오랫동안 본 수요와 남는 양에 따라 완만하게 조정한다.
  3. 확인해 볼 것EC2 콘솔의 인스턴스 목록에서 해당 인스턴스의 구매 옵션이 Spot으로 표시되는지 확인한다.

스팟 인스턴스가 중단되기 전에 알림을 받고, 두 분 이내에 체크포인트로부터 다른 스팟 인스턴스로 재시작하거나 온디맨드로 옮길 수 있도록 하는 절차와 재배치 권고 기능.

먼저 알아야 할 것 04-04

#1문제 상황

Spot Instance interruptions를 미리 알지 못하면 처리 중인 작업이 그냥 잘려 나간다.

#2핵심 질문

스팟 인스턴스가 끊기기 전에 그 사실을 알고 다른 곳으로 옮기려면 어떻게 하는가?

#3동작 예시

다음 날 출근해 보면 같은 배치가 이어져 있다.

#4동작 과정

  1. 알림을 받는다termination notice와 함께 두 분 전 두 정도의 경고(two-minute warning)가 먼저 온다. 중단 방식(interruption behavior)을 stop·hibernate·terminate 중으로 정해 두면 그 뒤에 경고가 온다.
  2. 옮긴다Rebalance recommendations가 뜨면 capacity가 균형에 맞지 않는다는 뜻이라, 두 분 이내에 체크포인트에서 다른 스팟 인스턴스로 재시작하거나 온디맨드로 옮긴다. Spot Instance interruption 원인은 요청에 적어 둔 최대 가격 초과일 때도 생긴다.
  3. 확인해 볼 것EC2 콘솔의 이벤트 목록에서 해당 인스턴스의 중단 관련 이벤트가 시간순으로 남아 있는지 확인한다.

물리 서버 한 대를 나만 쓸 수 있게 예약하는 Dedicated Hosts와, 특정 가용 영역에서 특정 인스턴스 유형의 실행 가능 개수를 미리 사수해 두는 Capacity Reservations라는 두 가지 전용 용량 확보 수단.

먼저 알아야 할 것 04-02

#1문제 상황

온디맨드(→ 04-02)는 필요할 때 붙이지만 특정 인스턴스 유형이 품절이면 기다려야 한다. 라이선스를bring your own licenses 형태로 직접 관리해야 하는 환경에서는 호스트가 남 사람과 섞이면 안 된다.

Dedicated Hosts와 Capacity Reservations는 이 둘을 각각 물리 서버 단위와 인스턴스 개수 단위로 미리 확보해 준다.

#2핵심 질문

반드시 특정 인스턴스를 곧바로 띄울 수 있는 자리를 미리 확보하려면 어떻게 하는가?

#3동작 예시

다음 분기 대시보드 공개를 위해 이 리전의 m 인스턴스 20대를 사수해 둔다.apacity reservation이 있는 대상 가용 영역에서 온디맨드로 요청하면 예약 수를 넘지 않는 한 추가 비용 없이 붙는다.

큰 이벤트나 재해 복구 때는 다른 가용 영역에도 같은 방식으로 예약해 둔다.

#4동작 과정

  1. 서버를 잡는다Dedicated Hosts는 물리 서버 한 대를 계정 안에서 나만 쓰는 형태로 예약하는 수단이다. 호스트가 하드웨어 문제로 멈춰도 자동으로 다른 호스트로 옮겨주는 host recovery를 걸 수 있다.
  2. 개수를 사수한다Capacity Reservations는 특정 가용 영역에서 특정 인스턴스 유형의 실행 가능 개수를 미리 확보한다. On-Demand Capacity Reservations는 규모 확장 이벤트나 규제 요건, 재해 복구를 미리 대비하는 데 쓰고, 쓰지 않는 부분은 계정 내 다른 작업에 내주고 필요하면 되찾을 수 있다.
  3. 확인해 볼 것EC2 콘솔의 Capacity Reservations 화면에서 대상 가용 영역과 예약 인스턴스 수, 남은 예약 상태를 확인한다.

인스턴스 실행하기

AMI(인스턴스를 부팅할 수 있게 미리 묶어 둔 이미지)와 인스턴스 유형을 골라 보안 그룹과 키 페어까지 지정한 뒤 EC2 콘솔이나 명령줄 도구로 가상 서버 한 대를 새로 만들어 시작하는 것.

먼저 알아야 할 것 02-01

#1문제 상황

AWS에서 직접 서버 장비를 사면 구매와 운영을 전부 맡아야 한다. 서버가 필요 없는 시간에도 비용이 나고, 만들었다 없애는 데 시간이 걸린다.

EC2에서 인스턴스를 띄우면 AMI(→ 02-01)에 담긴 운영체제와 애플리케이션이 붙은 가상 컴퓨터가 minutes 단위로 생겨나고, 필요 없으면 반납할 수 있다.

#2핵심 질문

내가 원하는 운영체제와 사양의 가상 서버 한 대를 지금 바로 어떻게 만드는가?

#3동작 예시

새 AWS 계정에서 EC2 콘솔을 열고 인스턴스 시작 화면으로 들어간다. 무료 사용 범위에 들어가는 리전에서 t 유형을 골라AMI를 선택하고, 보안 그룹(→ 10-02)을 새로 만들고 키 페어(→ 10-01) 이름을 넣는다.

시작을 누르면 인스턴스가 pending을 거쳐 running이 되고, 공개 IP가 붙는다.

#4동작 과정

  1. 구성을 고른다launch instance wizard에서 AMI와 인스턴스 유형을 정한다. launch from an existing instance를 고르면 이미 돌고 있는 인스턴스의 디스크 모양을 그대로 따라 AMI가 만들어진다.
  2. 그대로 띄운다반복해서 쓰는 구성이라면 launch using a launch template로 저장한 틀(→ 01-04)을 그대로 쓴다. 보안 그룹과 키 페어, 태그를 함께 지정한다.
  3. 확인해 볼 것인스턴스 목록에서 상태가 running으로 바뀌고 공개 IP가 채워진 것을 확인한다.

SSH로 Linux 인스턴스에 접속

비공개 키 페일로 만든 쌍 중 개인 키를 ~/.ssh 에 두고 ssh -i 명령으로 Linux 서버에 원격 셸을 열어 명령을 실행하는 접속 방식.

먼저 알아야 할 것 05-01

#1문제 상황

인스턴스(→ 05-01)가 떴다고 해서 그 안에서 애플리케이션을 실행하고 로그를 볼 수는 없다. 직접 만지고 싶어도 물리 키보드가 붙어 있는 서버가 아니다.

Linux는 서버에서 쓰는 운영체제이고, SSH는 키로 상대를 증명한 뒤 원격 셸을 여는 암호화 접속 방식이다. 접속하지 않으면 배포도 설정도 할 수 없으므로, 처음 만든 서버로 들어가는 통로가 필요하다.

#2핵심 질문

만들어진 Linux 인스턴스에 첫 셸을 어떻게 여는가?

#3동작 예시

Mac이나 Linux 터미널에서 ~/.ssh 아래 있는 개인 키 파일을 지정해 ssh -i 명령을 친다. 사용자 이름을 붙여 접속하니 셸 프롬프트가 뜨고, 서버에서 ps aux 명령을 치면 실행 중인 프로세스가 나온다.

파일은 scp 명령으로 인스턴스에서 그대로 내려받을 수도 있다.

#4동작 과정

  1. 준비를 확인한다일반 접속 요건으로 인스턴스가 상태 검사(→ 11-01)를 통과했는지 본다. 개인 키를 ~/.ssh 에 두고 권한을 좁히며, 보안 그룹(→ 10-02)이 22번 포트를 허용하는지 확인한다.
  2. 붙는다connect using an SSH client로 개인 키 파일을 지정해 로그인한다. 키 페어(→ 10-01)를 인스턴스에 넣은 상태여야 한다.
  3. 확인해 볼 것접속한 셸에서 whoami 명령을 쳐 로그인한 사용자 이름이 나오는 것을 확인한다.

#5한 줄 요약

SSH 접속개인 키로 증명해 Linux 인스턴스 셸을 처음 여는 것

RDP로 Windows 인스턴스에 접속

리모션 데스크톱 프로토콜(RDP) 클라이언트로 Windows 서버의 그래픽 데스크톱 화면을 열고 마우스·키보드를 직접 다루는 접속 방식.

먼저 알아야 할 것 05-01

#1문제 상황

Windows 인스턴스(→ 05-01) 안에서 해야 하는 일은 대개 관리자 권한이 필요한 설정과 화면을 보는 작업이다. 리눅스처럼 명령만으로는 부족하고 원격 화면이 필요하다.

그 화면은 SSH가 아니라 리모션 데스크톱 프로토콜(RDP), 즉 Windows의 화면을 압축해 전송하는 방식으로 열린다.

#2핵심 질문

Windows 인스턴스의 데스크톱 화면을 직접 어떻게 여는가?

#3동작 예시

Windows PC에서 시작 메뉴에 mstsc를 치고 접속 대상 주소에 인스턴스의 비공개 IP(→ 08-01)를 넣는다. administrator 비밀번호를 넣으면 원격 데스크톱이 열리고 인스턴스의 마우스를 그대로 움직일 수 있다.

열린 화면에서 파일을 밀어 넣으면 인스턴스 쪽에 그대로 떨어진다.

#4동작 과정

  1. 도구를 준비한다connect using an RDP client를 쓴다. Windows에는 RDP 클라이언트가 기본으로 있어 mstsc로 확인하고, 다른 운영체제에서는 Remote Desktop 앱을 설치한다. 상태 검사 통과와 개인 키 권한 설정은 공통 요건이다.
  2. 화면을 연다접속 주소에 비공개 IP를 쓰고 Windows administrator password를 입력한다. 보안 그룹(→ 10-02)이 RDP 포트를 허용해야 하며, 파일 이동은 RDP 드라이브 매핑으로 처리한다. Systems Manager Fleet Manager나 EC2 Instance Connect Endpoint로도 대신 붙을 수 있다.
  3. 확인해 볼 것원격 데스크톱 창이 열리고 인스턴스의 마우스를 움직여 커서가 따라 움직이는 것을 확인한다.

Session Manager로 브라우저에서 접속

SSM 에이전트를 경유해 AWS 콘솔 안의 브라우저 탭으로 리눅스 셸을 열어 키 페일을 직접 쓰지 않고 접속하는 방식.

먼저 알아야 할 것 05-02

#1문제 상황

SSH(→ 05-02)로 들어가려면 개인 키를 관리하고 22번 포트를 외부에 열어 두어야 한다. 키를 분실하면 되돌아갈 길이 막히고, 공개 포트 하나가 그대로 노출된다.

Session Manager는 AWS Systems Manager에 들어 있는 기능으로, 인바운드 포트를 따로 열지 않고 브라우저에서 곧바로 셸을 열 수 있는 길이다.

#2핵심 질문

개인 키도 공개 포트도 없이 브라우저 탭에서 인스턴스 셸을 어떻게 여는가?

#3동작 예시

EC2 콘솔에서 인스턴스를 고르고 연결 항목에서 Session Manager를 누른다. 브라우저 안의 탭에 셸 프롬프트가 뜨고, 이 자리에서 systemctl 명령으로 서비스를 다루고 tail로 로그를 따라간다.

창을 닫아도 인스턴스 상태는 그대로다.

#4동작 과정

  1. 세션을 연다Session Manager는 AWS Systems Manager의 기능이다. 인스턴스가 SSM 에이전트가 붙은 상태로 관리되고 AmazonSSMManagedInstanceCore 정책이 붙은 IAM 역할(→ 10-03)이 있어야 하며, 이 구성에서 without opening an inbound port가 가능하다.
  2. 셸을 쓴다세션이 열리면 다른 접속 방식과 똑같이 명령을 대화형으로 실행한다. 여러 대를 한 화면에서 다루려면 Fleet Manager를 쓴다.
  3. 확인해 볼 것연결 창이 새 브라우저 탭으로 열리고 셸 프롬프트가 나타나는 것을 확인한다.

5. 띄우고 붙기 — 실행과 접속05-05

EC2 Instance Connect — 공개 IP로 짧게 붙는다

IAM 권한과 보안 그룹이 허용된 경우 인스턴스가 받아온 공개 IP 주소로 22번 포트를 직접 열어 로그인하는 접속 방식.

먼저 알아야 할 것 05-02

#1문제 상황

서버마다 개인 키 파일을 복사해 두면 키가 여러 곳에 흩어지고 회수도 어렵다(→ 10-01). 키를 계속 들고 다녀야 하니 권한 철회도 즉시 되지 않는다.

EC2 Instance Connect는 키 파일을 나눠 주지 않는다. IP 주소는 네트워크에서 장비를 찾아가는 숫자 주소다. IAM 권한이 있는 사용자가 접속할 때만 인스턴스 안으로 공개 키를 밀어 넣고, 60초 뒤에는 사라진다. 접속 기록은 CloudTrail에 남는다.

#2핵심 질문

개인 키 파일을 따로 관리하지 않고 인스턴스에 SSH로 붙을 수 있을까?

#3동작 예시

운영자가 EC2 콘솔에서 인스턴스에 "Connect"를 누르고 사용자 이름을 입력한다. 콘솔이 잠깐 새 셸을 열어 로그인시킨 뒤 닫아 버린다.

그 다음 개발자는 자기 노트북에서 평소 쓰던 ssh 명령으로 그 인스턴스에 바로 들어간다.

#4동작 과정

  1. 키를 밀어 넣는다EC2 Instance Connect API가 접속 요청자의 공개 키를 인스턴스 metadata에 60초간 올린다. IAM policy가 이 요청을 허가해야 하며, 인스턴스에는 AuthorizedKeysCommand 설정이 깔려 있다.
  2. 숨겨진 키로 붙는다사용자는 개인 키 없이 ssh 명령만 실행한다. SSH 데몬이 metadata에서 임시 키(temporary SSH key)를 읽어 그 키로 세션을 연다.
  3. 기록을 남긴다모든 접속 요청이 CloudTrail에 저장된다. 어떤 신원이 언제 붙었는지 확인할 수 있다.
  4. 확인해 볼 것EC2 콘솔의 인스턴스 화면에서 Connect를 눌러 셸이 열리는지 확인한다.

EC2 Instance Connect Endpoint — 사설 IP로 붙는다

VPC 안에 띄운 전용 엔드포인트가:aws:ec2-instance-connect 경로로 세션을 중계해 인터넷에 공개 IP를 노출하지 않고 사설 IP로 SSH 접속을 허용하는 방식.

먼저 알아야 할 것 05-05

#1문제 상황

공개 IP는 인터넷에 노출되고 공개 IPv4 주소에는 비용이 붙는다(→ 08-01). 반면 Bastion host(중계용 서버)를 직접 띄우고 유지하는 것도 부담이다.

EC2 Instance Connect Endpoint는 VPC 안에 만든 전용 중계 지점을 둔다. 이 경로가 aws:ec2-instance-connect다. 인스턴스는 private IP만 가져도 되고 VPC가 직접 인터넷에 연결될 필요도 없다.

#2핵심 질문

공개 IP 없이도 인터넷에서 인스턴스에 안전하게 SSH로 붙을 수 있을까?

#3동작 예시

운영자가 VPC 안의 서브넷에 EC2 Instance Connect Endpoint를 만든다. 인스턴스에는 공개 IP를 부여하지 않는다.

그래도 사내에서 실행한 ssh 명령이 그대로 인스턴스에 닿아 로그인된다.

#4동작 과정

  1. 엔드포인트를 만든다VPC 안의 subnet에 EC2 Instance Connect Endpoint를 세운다. VPC endpoint는 VPC 내부에서 AWS 서비스로 나가는 전용 통로다.
  2. 접속 권한을 제한한다엔드포인트의 VPC endpoint policy와 보안 그룹(security groups)으로 어느 신원만 붙을지 정한다. 그 신원만 콘솔에서 접속 요청을 보낼 수 있다.
  3. 중계로 붙는다connect to an instance 요청이 엔드포인트를 지나 세션이 중계된다. 인스턴스에는 공개 IP가 필요 없다.
  4. 확인해 볼 것VPC 콘솔의 Endpoints 화면에 엔드포인트 상태가 available로 보이는지 확인한다.

Stop 과 Start

인스턴스를 정지(Stop)하면 가상 머신이 메모리 상태를 잃고 종료되지만 EBS 볼륨과 인스턴스 설정은 유지되어, 다시 시작(Start)하면 같은 인스턴스가 이전 볼륨으로 부팅된다.

먼저 알아야 할 것 05-01

#1문제 상황

인스턴스를 계속 켜 두면 사용하지 않는 시간에도 요금이 붙는다(→ 04-02). 그런데 매번 새로 만들면 설정과 데이터를 다시 붙여야 한다.

Stop and start는 두 가지를 함께 한다. 가상 머신만 내리고 디스크는 남긴다. 다시 시작하면 같은 인스턴스 ID로 부팅된다.

#2핵심 질문

서버를 잠깐 내렸다가 같은 설정 그대로 다시 켜려면 어떻게 하는가?

#3동작 예시

야간 배치 서버가 새벽이 되면 인스턴스를 Stop한다. 아무 요청이 없다.

아침에 Start를 누르니 같은 인스턴스가 이전 볼륨으로 그대로 올라와 이어서 처리한다.

#4동작 과정

  1. 정지한다기본 정지 방식을 쓰면 how it works 규칙대로 동작한다. 게스트에게 종료 버튼 신호가 전달되고 ACPI 종료가 시작된다. 메모리 상태는 사라지고 EBS 볼륨과 설정은 유지된다.
  2. 다시 켠다methods for stopping an instance를 고르면 정지 동작이 달라진다. stop protection을 켜 두면 실수로 정지되지 않는다.
  3. 부팅을 확인한다인스턴스 상태가 pending을 거쳐 running으로 되돌아오는지 본다. stop과 start는 reboot(→ 06-03)와 달리 과금 주기가 다시 시작된다.
  4. 확인해 볼 것인스턴스 목록에서 해당 인스턴스의 상태가 stopped로 바뀌고 볼륨 목록이 그대로 남아 있는지 확인한다.

Hibernation — 메모리를 파일로 접어 둔다

Hibernation은 정지할 때 메모리 내용을 암호화해 루트 볼륨에 저장하고, 시작할 때 그 내용을 그대로 되돌려 인스턴스를 멈춘 시점의 상태 그대로 깨우는 기능이다.

먼저 알아야 할 것 06-01

→ 06-01 참조

#1문제 상황

Stop으로 껐다가 켜면 OS를 처음부터 다시 띄워야 하므로 애플리케이션이 다 warms up되는 데 시간이 걸린다(→ 06-01).

Hibernation은 그 시작 비용을 없앤다. RAM contents를 그대로 저장해 두기 때문이다.

#2핵심 질문

인스턴스를 껐다 켜도 실행 중인 프로그램 상태가 그대로 이어지게 할 수 있는가?

#3동작 예시

인스턴스를 hibernate-enabled AMI로 띄운다. 웹 애플리케이션이 요청을 처리하던 상태에서 Hibernation으로 정지한다.

다시 시작하니 프로세스가 중단된 자리에서 그대로 resume된다.

#4동작 과정

  1. 저장한다hibernate 명령을 주면 RAM contents를 암호화해 EBS-backed instance의 루트 볼륨에 옮긴다. EBS 볼륨과 인스턴스 ID는 그대로 유지된다.
  2. 깨운다시작할 때 루트 볼륨이 이전 상태로 복원되고 RAM contents가 다시 적재된다. 붙어 있던 데이터 볼륨도 다시 붙는다.
  3. 미리 데운다부팅이 오래 걸리는 인스턴스는 원하는 상태까지 띄운 뒤 hibernate해 두었다가 resume하는 방식으로 미리 준비할 수 있다.
  4. 확인해 볼 것인스턴스를 시작했을 때 이전에 띄워 둔 프로세스가 살아 있는지 콘솔과 애플리케이션 화면에서 확인한다.

#5한 줄 요약

Hibernation정지 순간 메모리 내용을 디스크에 접어 두고 시작할 때 그대로 펼치는 것

Reboot 과 Terminate

Reboot은 운영체제만 재시작해 인스턴스와 볼륨을 그대로 두는 동작이고, Terminate는 인스턴스를 삭제해 기본적으로 함께 붙어 있던 EBS 볼륨까지 없애는 동작이다.

먼저 알아야 할 것 06-01

#1문제 상황

어떤 변화는 서버를 다시 띄워야 반영된다. 반대로 쓰지 않는 서버는 아예 없애야 계정이 비워진다. 두 요구가 정반대 방향이다.

인스턴스의 수명주기에는 그 사이 동작이 이미 나뉘어 있다. Reboot은 인스턴스를 남겨 두고 운영체제만 다시 시작하는 동작이고, Terminate는 인스턴스를 삭제하는 동작이다.

#2핵심 질문

인스턴스를 남겨 두고 운영체제만 다시 띄리는 방법과, 아예 삭제하는 방법을 어떻게 구분하는가?

#3동작 예시

OS 업데이트를 적용해야 한다. 인스턴스를 Reboot하면 같은 인스턴스 ID와 IP가 유지된 채 셸이 다시 열린다.

쓰지 않는 테스트 서버는 Terminate로 삭제해 인스턴스 목록에서 사라지게 한다.

#4동작 과정

  1. 재부팅한다reboot은 운영체제만 다시 시작한다. 인스턴스 ID와 IP 주소, instance store 볼륨의 데이터가 모두 유지된다. 과금 주기도 이어진다.
  2. 종료한다terminate는 인스턴스를 삭제한다. 종료 전에 확인 절차를 두거나 termination protection(종료 방지 설정)을 켜 둘 수 있다.
  3. 방식을 정한다rebooting은 사용자가 직접 건 뒤 AWS가 자동 복구나 유지보수 목적으로 건드릴 수 있다. initiated shutdown behavior로 종료 시그널 처리를 정해 둘 수 있다.
  4. 확인해 볼 것인스턴스 상세 화면의 상태가 pending에서 running으로만 바뀐 뒤 stopped나 terminated로 넘어가지 않았는지 확인한다.

종료할 때 볼륨을 남기기

기본값인 DeleteOnTermination을 끄면 인스턴스를 종료해도 연결된 EBS 볼륨이 삭제되지 않고 남아, 같은 볼륨으로 새 인스턴스를 다시 만들 수 있다.

먼저 알아야 할 것 06-03

→ 06-03 참조

#1문제 상황

인스턴스를 종료하면 붙어 있던 EBS 볼륨이 기본값 DeleteOnTermination 따라 함께 지워진다(→ 06-03). 데이터가 그대로 사라진다.

데이터를 살리는 방법은 종료 전에 다른 저장소로 옮기거나, 볼륨이 남도록 설정을 바꾸는 것이다.

#2핵심 질문

인스턴스를 종료해도 데이터 디스크를 지우지 않고 남겨 두려면 어떻게 하는가?

#3동작 예시

운영자가 볼륨 설정에서 종료 시 삭제 항목을 끄고 인스턴스를 종료한다.

인스턴스는 사라지고 볼륨만 available 상태로 남아 있다. 그 볼륨을 붙여 새 인스턴스를 만든다.

#4동작 과정

  1. 설정을 확인한다EBS 볼륨마다 preserve data when an instance is terminated 값이 있다. 기본값은 삭제다. instance store 볼륨은 이 설정과 무관하게 종료와 함께 지워진다.
  2. 루트 볼륨을 다룬다root volume은 시작할 때 종료 후 유지되도록 지정하거나, replace a root volume로 다른 볼륨으로 바꿀 수 있다.
  3. 필요하면 옮긴다남길 수 없는 데이터는 종료 전에 EBS 볼륨·S3 버킷·EFS 같은 지속 저장소로 복사해 둔다.
  4. 확인해 볼 것인스턴스를 종료한 뒤 볼륨 목록에서 해당 볼륨이 남아 상태가 available인지 확인한다.

자동 복구는 인스턴스가 잘못된 상태로 멈췄을 때 Amazon이 백그라운드에서 자동으로 해당 인스턴스를 재부팅해 정상 상태로 되돌리는 기능이다.

먼저 알아야 할 것 06-03

#1문제 상황

인스턴스를 쓰는 도중 문제가 생기면 사람이 로그인을 하려고 해도 서버가 이미 멈춰 있다(→ 11-01).

AWS가 원인을 감지하면 그 자리에서 대신 처리해 줄 수 있다.

#2핵심 질문

인스턴스가 멈췄을 때 사람의 조작 없이 AWS가 알아서 되살려 줄 수 있는가?

#3동작 예시

새벽에 자동 복구가 동작해 인스턴스가 의도치 않은 재부팅으로 다시 올라온다. 운영자는 아침에 로그인했을 뿐 아무것도 몰랐다.

#4동작 과정

  1. 감지한다AWS는 시스템 status check(→ 11-01)가 실패하는 하드웨어나 소프트웨어 문제를 찾아낸다.
  2. 옮긴다두 가지 방식이 있다. simplified automatic recovery는 곧바로 처리하고, Amazon CloudWatch action based recovery는 CloudWatch 지표에 묶인 동작 규칙을 따라 처리한다.
  3. 되살린다Automatic instance recovery는 문제가 있는 호스트에서 인스턴스를 다른 호스트로 옮긴다. 성공하면 사용자에게는 계획하지 않은 재부팅처럼 보인다.
  4. 확인해 볼 것인스턴스의 재부팅 이력에서 복구로 인한 재부팅이 기록되었는지 확인한다.

User data 와 instance metadata

User data는 인스턴스를 처음 시작할 때 실행할 스크립트를 손으로 넣는 수단이고, instance metadata는 실행 중인 인스턴스 자신의 ID·IAM 역할 같은 정보를 인스턴스가 직접 조회할 수 있는 서비스다.

먼저 알아야 할 것 05-01

#1문제 상황

범용 AMI 하나만으로는 웹 서버 인스턴스를 여러 곳에서 다르게 켤 수 없다. 첫 접속마다 따로 접속해 설정을 손으로 바꿔야 한다.

User data는 인스턴스를 처음 시작할 때 실행할 스크립트를 넘기는 수단이고, instance metadata는 실행 중인 인스턴스 자신의 정보를 인스턴스가 직접 읽는 서비스다. 둘을 같이 쓰면 인스턴스가 스스로 자기 정보를 읽어 첫 사용 설정을 끝낸다.

#2핵심 질문

인스턴스가 처음 켜지는 순간 스스로 자기 정보를 읽고 설정을 마치게 할 수 있을까?

#3동작 예시

같은 AMI로 웹 서버 열 대를 켜고, 각 인스턴스의 S3 버킷 이름만 user data에 다르게 넣는다. 인스턴스는 부팅 때 자기 instance-id를 metadata에서 읽고 그 버킷에서 사이트 설정을 받아 온다. 콘솔에는 정상으로 두 대가 뜬다.

#4동작 과정

  1. 스크립트를 건넨다시작 요청에 run commands at launch 형태로 user data를 붙인다. 스크립트는 첫 부팅 때 한 번 실행된다.
  2. 자신의 정보를 읽는다access instance metadata로 instance-id, 호스트 이름, 보안 그룹을 가져 온다. 시작 시점에 만들어지는 동적 정보도 이 경로로 온다.
  3. 안전하게 조회한다IMDSv2는 요청마다 토큰을 먼저 받아야 하는 방식으로 다른 인스턴스가 정보를 훔쳐 보지 못하게 막는다.
  4. 확인해 볼 것인스턴스에 접속해 /latest/meta-data/instance-id를 출력해 자기 ID가 표시되는지 본다.

Torn write prevention과 VSS 스냅숏

Torn write prevention은 EBS 볼륨이 동시에 두 번의 쓰기를 하는 위험을 막아 한 번의 쓰기가 온전히 끝난 상태로만 기록되게 하는 기능이고, VSS 스냅숏은 이 기능을 이용해 애플리케이션이 쓰기 작업을 멈춘 시점의 일관된 스냅숏을 뜬다.

먼저 알아야 할 것 07-01

#1문제 상황

Windows VSS는 애플리케이션이 쓰는 데이터를 잠시 멈춰 한 시점의 일관된 상태로 만드는 Windows의 스냅숏 기능이다. 쓰기 도중 전원이 끊기면 한 번의 쓰기가 일부만 기록되어 데이터가 깨진다. 데이터베이스는 이를 막기 위해 추가 기록을 하지만, 그만큼 느려진다.

torn write prevention은 볼륨 차원에서 이 문제를 막는다. 그 위에 application-consistent snapshots를 뜸직한 시점을 잡아 데이터가 온전한 스냅숏을 얻는다.

#2핵심 질문

쓰기 도중 죽어도 깨지지 않는 스냅숏을 어떻게 얻는가?

#3동작 예시

Windows 데이터베이스 서버의 볼륨에서 스냅숏을 뜬다. 스냅샷이 뜬 뒤에도 데이터베이스는 아무 이상이 없고, 스냅릿을 복원하면 그 시점 상태 그대로 돌아온다.

#4동작 과정

  1. 켜 둔다볼륨 생성 시 configure workload로 supported block sizes를 맞춰 torn write prevention을 켠다.
  2. 한 번의 쓰기를 지킨다볼륨이 전원 차단 상황에서도 한 번의 쓰기가 다 끝난 상태로만 기록되게 한다.
  3. 앱을 멈춰 뜬다Windows VSS로 애플리케이션 쓰기를 잠시 quiesce하고 스냅숏을 뜬 뒤 다시 쓴다.
  4. 확인해 볼 것볼륨에서 스냅숏을 뜬 뒤 데이터베이스에 접속해 데이터가 정상으로 읽히는지 본다.

인스턴스 밖의 저장소 — S3·EFS·FSx

S3는 객체 단위 객체 스토리지, EFS는 여러 인스턴스가 동시에 붙는 네트워크 파일 시스템(NFS), FSx는 Windows용 SMB 파일 스토리지로, 셋 다 인스턴스 밖에서 데이터가 남는 저장소다.

먼저 알아야 할 것 07-01

→ 07-01 참조

#1문제 상황

EBS 볼륨은 인스턴스에 붙어 있어야 하고 한 번에 하나의 인스턴스만 쓴다(→ 07-01). 여러 서버가 같은 파일을 함께 봐야 할 때 곤란하다.

인스턴스 밖의 저장소는 데이터가 인스턴스와 분리되어 남는다. Amazon S3는 파일 하나하나를 객체 단위로 저장하는 객체 스토리지이고, Amazon EFS와 Amazon FSx는 여러 인스턴스가 함께 붙는 파일 스토리지다. 접근 방식은 용도에 따라 object storage와 file storage로 갈린다.

#2핵심 질문

인스턴스와 무관하게 남고 여러 서버가 함께 읽는 저장소는 어디에 두는가?

#3동작 예시

여러 웹 서버가 같은 이미지 파일을 배포한다. 이미지 원본은 Amazon S3 버킷에 두고, 각 인스턴스는 시작 시 그 경로를 받아 쓴다. 여러 인스턴스가 동시에 쓰는 공유 디렉터리는 Amazon EFS를 마운트해 쓴다.

#4동작 과정

  1. 객체로 둔다Amazon S3는 파일 하나하나를 객체로 저장해 어디서든 가져온다. 인스턴스 안에서는 로컬 디스크처럼 보이지만 별도 서비스다.
  2. 파일로 공유한다Amazon EFS는 여러 인스턴스가 동시에 붙는 NFS 파일 시스템이다. Amazon FSx는 Windows 인스턴스가 쓰는 SMB 파일 저장소다.
  3. 읽기를 가속한다Amazon File Cache로 반복해서 읽는 데이터를 캐시에 받아 두면 지연이 줄어든다.
  4. 확인해 볼 것Linux 인스턴스에서 EFS 마운트 지점에 파일을 쓰고 다른 인스턴스에서 그 파일이 보이는지 본다.

인스턴스 IP 주소

인스턴스가 네트워크에서 식별되고 통신하기 위해 갖는 주소로, 인스턴스를 시작할 때마다 바뀔 수 있는 비공개 IP 주소와, 다른 리소스가 항상 같은 주소로 접속할 수 있는 공개 IP 주소로 나뉜다.

먼저 알아야 할 것 05-02

#1문제 상황

인스턴스를 띄우면 네트워크에서 그 컴퓨터를 부를 이름이 필요하다. AWS는 VPC 안에서 사설 주소 범위(CIDR 블록)를 정해 두고, 인스턴스를 시작할 때 그 서브넷 범위에서 주소를 하나 받게 한다.

이 주소 배정 방식이 instance IP addressing이다. 기본은 IPv4 addresses 방식이고, VPC에 IPv6 CIDR 블록을 두면 인스턴스에 IPv6 addresses를 함께 붙일 수 있다.

#2핵심 질문

인스턴스가 VPC 안과 인터넷에서 각각 어떤 주소로 통신해야 할까?

#3동작 예시

개발용 웹 서버 인스턴스를 시작한다. 인스턴스 목록에 10.0.1.24가 자동으로 붙어 있고, 같은 VPC의 다른 인스턴스는 이 주소로 바로 접속한다. 외부에서 들어와야 하면 public IPv4 address를 추가로 받는다.

#4동작 과정

  1. 주소를 받는다인스턴스를 시작할 때 VPC와 서브넷을 지정하면, 서브넷의 사설 주소 범위에서 private IP address가 하나 배정된다. 이 주소는 시작할 때마다 달라질 수 있다.
  2. 외부 주소를 더한다필요에 따라 public IPv4 address와 IPv6 addresses를 함께 붙인다. 서로 다른 VPC의 인스턴스가 이 주소로 통신하면 트래픽은 공개 인터넷을 거치지 않고 AWS 사설 글로벌 네트워크를 지난다.
  3. 확인해 볼 것EC2 콘솔의 인스턴스 상세 화면에서 Private IP와 Public IP가 각각 어떻게 표시되는지 본다.

먼저 알아야 할 것 08-01

→ 08-01 참조

#1문제 상황

인스턴스가 VPC에서 받는 주소를 하나만 쓴다면, 인스턴스를 늘려야 여러 서비스를 한 컴퓨터에서 처리할 수 있다(→ 08-01).

secondary IP addresses와 network interfaces를 쓰면 인스턴스를 그대로 둔 채 주소 수와 인터페이스 수를 늘릴 수 있다.

#2핵심 질문

인스턴스를 늘리지 않고 여러 서비스가 각자 주소를 쓰게 하려면?

#3동작 예시

같은 인스턴스에서 웹 서버와 데이터 수집기를 함께 돌린다. 웹 서버에는 보조 주소 하나를, 수집기에는 다른 보조 주소를 붙인다. 운영체제 설정만 고치면 두 서비스가 각자 주소로 통신한다.

#4동작 과정

  1. 주소를 덧붙인다보조 IP 주소는 네트워크 인터페이스에 추가로 붙는 IPv4 주소다. 시작할 때나 실행 중 어느 때든 붙일 수 있고, IP addresses per network interface 값으로 몇 개까지 붙일지 정한다. IPv6 주소도 여러 개 붙일 수 있다.
  2. 인터페이스를 여러 개 붙인다multiple network interfaces를 쓰면 하나의 인스턴스에 네트워크 인터페이스를 여러 개 달아 각기 다른 서브넷에 놓을 수 있다. 그중 처음 붙어 있는 것을 primary network interface라 부르고, 인스턴스의 기본 주소는 여기서 온다.
  3. 확인해 볼 것인스턴스의 ENI 화면에서 보조 IP 주소 목록이 몇 개 채워져 있는지 확인한다.

#1문제 상황

일반적인 public IPv4 address는 인스턴스가 중지되거나 재시작되면 바뀐다(→ 08-01). 그 주소를 도메인에 등록해 둔 서비스는 주소가 바뀔 때마다 설정도 손봐야 한다.

Elastic IP address는 계정에서 따로 만들어 두는 static public address라 이 문제를 없앤다.

#2핵심 질문

인스턴스가 교체되어도 외부에서 쓰는 주소가 변하지 않게 하려면?

#3동작 예시

서버 인스턴스가 고장 나 멈춘다. Elastic IP 주소를 새 인스턴스에 붙이자마자 같은 주소로 클라이언트 요청이 새 서버에 닿는다. 도메인의 DNS 기록도 그대로 둔다.

#4동작 과정

  1. 할당한다Elastic IP address를 계정 안에서 빌리면 그 계정의 소유가 되고, release an Elastic IP address로 되돌려 놓기 전까지 유지된다. 이 주소는 인터넷에서 닿는 public IPv4 주소다.
  2. 붙인다associate an Elastic IP address로 인스턴스에 연결한다. public IPv4 주소가 없는 인스턴스에도 붙여 인터넷 통신을 열 수 있다. 인스턴스가 죽었을 때 주소를 다른 인스턴스로 빠르게 옮기면 그 실패를 가릴 수 있다.
  3. 넘긴다transfer 기능으로 다른 AWS 계정으로 옮길 수도 있다.
  4. 확인해 볼 것EC2 콘솔의 Elastic IP 화면에서 주소가 계정에 할당된 상태로 목록에 보이는지 본다.

인스턴스 이름과 도메인 이름으로 만든 호스트 이름을 부여하는 기능으로, 프라이빗 호스트 이름과 퍼블릭 호스트 이름이 있고 역방향 DNS 로 IP 주소에서 이름을 되찾을 수도 있다.

먼저 알아야 할 것 08-01

→ 08-03 참조

#1문제 상황

IP 주소를 그대로 쓰면 사람이 읽기 어렵고 하드코딩한 설정이 인스턴스마다 다르게 남는다(→ 08-01).DNS는 도메인 이름을 IP 주소로 변환해 주는 이름 조회 체계다. 이를 쓰면 주소를 이름으로 부르고 되돌릴 수 있고, VPC 안에서만 쓰는 이름을 외부에 숨길 수도 있다.

hostnames and domains 기능은 인스턴스에 이름을 붙이고, 필요하면 IP 주소에서 그 이름을 되찾을 수 있게 한다.

#2핵심 질문

인스턴스 주소를 사람이 읽을 수 있는 이름으로 부르고 되돌릴 수 있게 하려면?

#3동작 예시

같은 VPC 안의 서비스들이 인스턴스 IP 대신 호스트 이름으로 접속한다. PrivateDnsName으로 설정한 프라이빗 호스트 이름은 VPC 안에서만 해석되고, internet에서는 이름이 풀리지 않는다.

#4동작 과정

  1. 종류를 고른다hostname types는 프라이빗과 퍼블릭으로 나뉜다. 프라이빗 호스트 이름은 VPC 안에서만 사설 주소로 해석되고, 퍼블릭 호스트 이름은 VPC 안에서는 사설 주소로, 외부에서는 공개 IP로 해석되는 split-horizon DNS 방식이다.
  2. 설정 위치를 정한다프라이빗 호스트 이름은 인스턴스 수준에서 설정하고, 퍼블릭 호스트 이름은 네트워크 인터페이스 수준에서 설정한다.
  3. 되돌려 찾는다reverse DNS를 켜면 IP 주소에서 호스트 이름을 다시 확인할 수 있다. domain name은 이 이름을 도메인 아래 붙일 때 쓴다.
  4. 확인해 볼 것인스턴스 상세 화면에 프라이빗 호스트 이름과 퍼블릭 호스트 이름이 각각 어떤 값으로 표시되는지 본다.

Enhanced networking — ENA 와 ENA Express

네트워크 카드 역할을 하는 가상의 인터페이스를 여러 개 붙이고 더 높은 처리량과 낮은 지연을 제공하는 기능으로, ENA Express 는 여러 인터페이스를 하나의 묶음으로 사용해 처리량을 더 끌어올린다.

먼저 알아야 할 것 08-02

→ 08-02 참조

#1문제 상황

가상화된 기본 네트워크 인터페이스는 CPU를 더 쓰고 지연이 일정하지 않다. 패킷을 많이 보내는 인스턴스에서는 이 손실이 그대로 처리량 감소로 나타난다(→ 08-02). 한 인스턴스가 가진 대역폭을 다 쓰게 하려면 어댑터를 직접 건드려야 한다.

enhanced networking은 네트워크 어댑터를 직접 쓰게 해 처리량과 초당 패킷 수를 끌어올린다.

#2핵심 질문

네트워크 처리량이 인스턴스 사양에 못 미치지 않게 하려면?

#3동작 예시

동일한 CPU와 메모리 사양의 두 인스턴스에 트래픽을 똑같이 흘려보낸다. enhanced networking을 켠 쪽의 network bandwidth 수치가 더 높고 지연 흔들림이 작다.

#4동작 과정

  1. 어댑터를 고른다Elastic Network Adapter(ENA)는 지원 인스턴스에서 100 Gbps까지 네트워크 속도를 낸다. Nitro 기반 인스턴스는 모두 ENA를 쓴다. SR-IOV는 이 어댑터가 쓰는 디바이스 가상화 방식으로, 전통 방식보다 I/O 성능이 높고 CPU 사용이 적다.
  2. 묶음으로 처리한다ENA Express와 ENA queues는 여러 인터페이스의 요청을 한 묶음으로 처리해 실효 대역폭을 더 높인다. Elastic Fabric Adapter는 다른 방식으로 처리량을 끌어올리는 대안이다.
  3. 확인해 볼 것인스턴스 상세 화면에 ENA 지원 표시에 해당 어댑터가 잡혀 있는지 본다.

#1문제 상황

새로 받은 public IPv4 address는 기존에 쓰던 주소와 다르다(→ 08-01). 사내망 정책상 이미 소유한 주소 범위를 그대로 쓰고 싶을 수 있다.

BYOIP 는 고객이 이미 보유한 IP 주소 범위를 AWS 계정에 등록해 EC2 에서 그대로 쓰는 기능이다. 또한 같은 데이터를 보낼 때 묶음 크기 MTU가 크면 오버헤드 비율이 줄고 필요한 패킷 수가 줄어든다.

#2핵심 질문

#3동작 예시

사내 DNS와 방화벽 정책에 등록된 기존 대역에서 인스턴스에 public 주소를 부여한다. 그 주소 범위를 AWS에 미리 등록해 둔 뒤 온보드한 것이다.

#4동작 과정

  1. 주소 범위를 등록한다Bring your own IP addresses(BYOIP)는 고객이 이미 보유한 IP 범위를 AWS 계정에 온보드해 EC2에 쓸 수 있게 하는 기능이다. 온보드한 범위에서 주소를 받아 다른 리소스에서도 그대로 쓴다.
  2. MTU를 정한다network MTU는 이더넷 프레임에서 한 번에 보낼 수 있는 최대 크기다. 표준 이더넷 v2는 1500 MTU를 쓰고, jumbo frames는 9001 MTU로 데이터 비중을 높인다. set the MTU로 인스턴스마다 값을 맞추고 Path MTU Discovery로 실제 크기를 확인한다.
  3. 확인해 볼 것인스턴스에서 네트워크 인터페이스의 MTU 설정에 어떤 값이 잡혀 있는지 본다.

EC2 Fleet 개념

EC2 Fleet 은 서로 다른 인스턴스 유형과 구매 방식(On-Demand·Spot·Reserved·Capacity Reservation)을 한 요청으로 섞어 지정된 목표 용량을 채우는 다중 인스턴스 실행 기능이다.

#1문제 상황

인스턴스를 한 대씩 띄우면 어떤 유형이 품절일 때 멈추고, 구매 방식마다 따로 관리해야 한다.

EC2 Fleet은 한 요청 안에서 여러 인스턴스 유형과 구매 방식을 섞어 띄우게 해준다.

#2핵심 질문

여러 유형과 구매 방식을 섞어 정해진 용량을 계속 채우려면?

#3동작 예시

장애-tolerant 서비스의 목표를 인스턴스 20대로 정해 Fleet을 만든다. EC2 Fleet은 지정된 구매 방식으로 부족한 만큼 채우고, On-Demand and Spot capacity가 모두 모자라면 목표를 채우지 못했다고 보인다.

#4동작 과정

  1. 요청을 만든다EC2 Fleet request 하나로 On-Demand와 Spot 구매 방식을 함께 지정하고, 각 인스턴스는 미리 저장한 설정 틀인 런치 템플릿이나 직접 적은 launch parameters로 정의한다(→ 01-04).
  2. 유형을 섞어 채운다하나의 인스턴스 유형만 쓴 요청과 달리 여러 유형을 지정하면, 특정 유형이 한정된 상황에서 전체 가용성이 오른다. fleet method를 고르면 On-Demand와 Spot만 쓰는 Spot Fleet도 같은 틀에서 다룰 수 있다.
  3. 지켜본다Fleet monitor에서 실행 중 인스턴스 상태와 부족분을 확인하고, 할당량에 걸리면 늘린다(→ 09-06).
  4. 확인해 볼 것Fleet 콘솔 화면에서 목표 용량 대비 실행 중인 인스턴스 수가 어떻게 표시되는지 본다.

#1문제 상황

EC2 Fleet(→ 09-01)은 온디맨드·스팟·예약 구매 방식과 여러 인스턴스 유형을 한 요청에 섞어 넣는다. 그런데 목표 용량을 한 번만 채울지, 줄어들 때 인스턴스를 빼고 늘 때 붙일지를 먼저 정해야 한다. 어떤 풀에서 뽑을지도 정해야 비용과 성능이 정해진다.

Request types 는 이 유지 방식을 정하고, allocation strategies 는 인스턴스를 어떤 조건에 고르는지를 정하는 규칙이다.

#2핵심 질문

Fleet 이 목표 용량을 한 번만 채울지 계속 지킬지, 그리고 어디에서 어떤 인스턴스를 고를지 어떻게 정할까?

#3동작 예시

주문 처리 인스턴스 20대를 목표 용량으로 건 Fleet 요청을 만든다. request type 을 maintain 로 두면 화면에 인스턴스 20대가 running 으로 뜬다. 스팟 가격이 오르면 Fleet이 알아서 더 싼 유형으로 교환한다.

#4동작 과정

  1. 유지 방식을 정한다Request types 는 instant·request·maintain 세 가지다. instant 는 목표 용량을 한 번에 동기 요청으로 채우고, request 도 단발형, maintain 는 시간에 따라 용량을 계속 맞춘다.
  2. 뽑을 풀을 정한다allocation strategies 는 lowest price처럼 가격 기준이나 용량·분산 기준으로 인스턴스를 고르는 규칙이다. 실행 가능한 인스턴스 유형이 없으면 요청이 실패 상태로 남는다.
  3. 유형을 고른다인스턴스 유형 목록을 직접 고르지 않고 속성 조건으로 고르는 attribute-based instance type selection 을 쓸 수 있다. 목록을 넘기는 방식보다 새 유형이 자동으로 후보에 들어온다.
  4. 확인해 볼 것Fleet 콘솔 화면에서 요청 상태가 유지되는지, 실행된 인스턴스 유형 목록이 조건에 맞는지 본다.

Instance weighting 과 spending limit

instance weighting 은 각 인스턴스 유형에 원하는 크기 기준값(가중치)을 붙여 작은 유형 여러 대가 큰 유형 한 대로 계산되게 하는 기능이고, spending limit 은 Fleet 이 지불하는 최대 금액(또는 최대 인스턴스 시간 단위)을 정해 그 이상을 자동 중단시키는 상한이다.

먼저 알아야 할 것 09-02

→ 09-02 참조

#1문제 상황

Fleet(→ 09-01)에 인스턴스 유형을 여러 개 넣으면 크기가 달라 목표 용량을 어떻게 채워야 할지 애매하다. small 여러 대로 채울지 large 한 대로 채울지 알 수 없다. 비용이 어디까지 커질지도 막을 방법이 없다.

Instance weighting 은 유형마다 용량 기준값을 붙여 이 문제를 푼다. spending limit 은 같은 Fleet 요청의 지출 상한을 둔다.

#2핵심 질문

크기가 다른 인스턴스 유형을 같은 기준으로 계산하고 비용 상한까지 걸려면 어떻게 정할까?

#3동작 예시

m5.large 에 가중치 1, m5.2xlarge 에 가중치 4를 준다. 목표 용량 8이면 Fleet 은 어느 조합으로든 8을 채운다. 화면에는 실행된 유형별 대수가 유형별 목표 용량을 만족한 상태로 표시된다.

#4동작 과정

  1. 가중치를 붙인다각 인스턴스 유형이 전체 목표 용량에 기여하는 용량 단위를 정한다. 목표 용량을 가중치로 나눈 값이 그 유형의 필요 대수다.
  2. 조건을 함께 둔다targeted Capacity Reservations(→ 04-06)나 On-Demand as primary capacity 를 지정해 어떤 용량을 우선 쓸지 정할 수 있고, Capacity Rebalancing 을 켜면 공급이 얼어붙기 전에 다른 유형으로 미리 옮긴다.
  3. 지출을 막는다spending limit 을 금액이나 인스턴스 시간 단위로 정하고, 넘으면 Fleet 이 자동으로 인스턴스를 중단시킨다.
  4. 확인해 볼 것Fleet 상세 화면에서 유형별로 실행된 대수가 설정한 가중치 기준에 맞는지 확인한다.

  2. 상태를 읽는다Spot Fleet request states 는 요청이 진행 중인지, 오류로 끝났는지, 사용자 동작으로 멈췄는지를 알려 주는 상태 값이다.

  4. 확인해 볼 것Fleet 콘솔에서 요청 상태와 실행된 스팟·온디맨드 인스턴스 수의 비율을 확인한다.

#1문제 상황

Fleet(→ 09-01)이 인스턴스를 여러 대 띄워도 각자의 위치는 서로 정해지지 않는다. 노드끼리 통신량이 많은 워크로드에서는 서로 다른 호스트에 나뉘면 통신이 느려지고, 복제본이 몰리면 한 번에 함께 죽을 수 있다.

placement groups 는 인스턴스 수를 묶어 배치 규칙을 한 번에 지정한다. 그 규칙 이름이 placement strategies 다.

#2핵심 질문

여러 인스턴스 사이의 거리를 원하는 모양으로 정할 수 있는가?

#3동작 예시

분산 데이터베이스 노드 6대를 띄우고자 placement group 을 만든다. 전략을 spread 로 고르면 각 노드가 서로 다른 하드웨어 위에 놓인다. Console의 인스턴스 목록에서 그룹 소속 여부가 보인다.

#4동작 과정

  1. 그룹을 만든다placement group 을 만들고 인스턴스를 한 번에 넣는다. 그룹에 넣을 때 인스턴스 유형(→ 03-01)을 정하면 같은 하드웨어에 못 들어가는 조합은 걸러진다.
  2. 전략을 고른다placement strategies 의 cluster 는 한 AZ 안에서 최대한 붙여 놓고 지연을 낮춘다. partition 은 논리 파티션으로 나눠 파티션마다 다른 하드웨어를 쓴다. spread 는 소수 인스턴스를 서로 다른 하드웨어에 엄격히 흩뿌려 동시 장애를 막는다.
  3. 인스턴스를 옮긴다change instance placement 를 쓰면 실행 중인 인스턴스를 중지 없이 다음 최적 위치로 옮길 수 있다. 시간 기반 스케줄로 묶어 두면 매주 자동으로 옮겨 간다.
  4. 확인해 볼 것인스턴스 목록에서 같은 placement group 에 속한 인스턴스가 함께 표시되는지 확인한다.

→ 09-01 참조

#1문제 상황

monitor your fleet 화면과 EC2 Capacity Manager 가 이 둘을 맡는다.

#2핵심 질문

Fleet 의 상태 변화와 용량 상한을 한곳에서 보고 자동으로 대응시키려면 무엇을 쓰는가?

#3동작 예시

Fleet 모니터 화면에서 실행 인스턴스 수와 요청 상태를 본다. CloudWatch 에는 시간별 지표가 쌓이고 EventBridge 에는 인스턴스 종료 같은 이벤트가 뜬다. Capacity Manager 에서 온디맨드·스팟 사용량 한도를 올린다.

#4동작 과정

  1. 눈으로 확인한다Fleet 모니터에서 Fleet 요청의 상태·실행 인스턴스·집행 이력을 조회한다. 여기서 목표 용량 대비 실제 대수를 본다.
  2. 지표와 이벤트로 반응한다CloudWatch metrics for the fleet 로 인스턴스 수를 시간별로 모아 11-02 의 alarm 을 건다. EventBridge 규칙을 만들면 인스턴스 종료나 Fleet 상태 변경 때 자동으로 돌아갈 수 있다.
  3. 상한을 관리한다EC2 Capacity Manager 가 여러 요청을 한데 묶는다. Capacity Manager metrics 로 한도 대비 사용량을 보고 상한을 조정한다.
  4. 확인해 볼 것Fleet 콘솔의 모니터 화면에서 요청 상태와 실행 인스턴스 목록이 보이는지 확인한다.

키 페어

인스턴스에 처음 접속할 때 사용하는 비밀번호 대신 암호화 개인 키와 공개 키 한 쌍을 발급받아, 개인 키로 SSH 로그인을 대신하는 방식이다.

먼저 알아야 할 것 05-02

#1문제 상황

인스턴스에 처음 붙으면(→ 05-01) 비밀번호를 직접 정해야 하는데, 그대로 쓰면 사람이 아는 문자열이 서버로 오간다. 누가 들어왔는지 추적하기도 어렵다.

키 페어는 이 둘을 없애고 개인 키 파일 하나로만 문을 여는 방식을 쓴다.

#2핵심 질문

비밀번호 없이 그리고 누가 접속했는지 개인 키로 확인할 수 있게 하려면 어떻게 시작하는가?

#3동작 예시

키 페어를 만들면 personal key file 이 로컬에 내려온다. 인스턴스를 시작할 때 이 키 페어를 고른다. Linux 라면 개인 키로 SSH 로그인하고 Windows 라면 개인 키로 관리자 비밀번호를 풀어 RDP(→ 05-03)로 들어간다.

#4동작 과정

  1. 키 페어를 만든다create a key pair 를 실행하면 개인 키 파일과 key pair ID 가 나온다. 개인 키 파일은 이때 단 한 번 저장할 수 있다.
  2. 공개 키는 서버에, 개인 키는 손에Amazon EC2 는 public key 를 인스턴스에 저장하고 사용자는 private key 를 보관한다. 개인 키를 가진 사람은 그 키 페어를 쓰는 모든 인스턴스에 붙을 수 있다.
  3. 다른 키를 더 넣는다인스턴스가 첫 부팅할 때 지정한 공개 키가 등록된다. 이후 add or replace a public key 로 살아 있는 인스턴스의 키를 바꾸거나 추가한다.
  4. 확인해 볼 것키 페어 목록에서 각 키의 fingerprint 가 보이는지, 인스턴스의 키 페어 항목이 비어 있지 않은지 본다.
  5. 확인해 볼 것서버 안의 ~/.ssh/authorized_keys 에 공개 키가 들어 있는지 확인한다.

보안 그룹

인스턴스에 들어오는 트래픽의 출발 IP와 포트를 규칙으로 지정해 통과시키거나 차단하는 가상 방화벽이다.

먼저 알아야 할 것 08-02

#1문제 상황

공개 IP(→ 08-01)로 열린 인스턴스는 전 세계에서 접속을 시도받는다. 어떤 포트를 열어 두었는지 인스턴스마다 다르게 관리하면 어떤 구멍이 열린지 알 수 없다.

보안 그룹은 그 판단을 VPC 안에서 미리 정해 두는 방화벽이다.

#2핵심 질문

인스턴스에 들어오고 나가는 트래픽을 어디서만 허용할지 어떻게 정하고 관리할까?

#3동작 예시

웹 서버 인스턴스를 만들 때 보안 그룹에 80번 포트만 모든 출발지에서 받도록 규칙을 넣는다. 외부에서 22번 포트로 붙어 보지만 규칙에 없으므로 연결이 막힌다. 규칙을 바꾸면 허용된 포트만 열린다.

#4동작 과정

  1. 그룹을 만든다create a security group 으로 VPC 안에 보안 그룹을 만든다. 인스턴스를 시작할 때 지정하지 않으면 VPC 의 기본 보안 그룹이 붙는다.
  2. 규칙을 넣는다inbound rules 은 들어오는 트래픽을, outbound rules 은 나가는 트래픽을 출발지 IP와 포트로 허용한다. 규칙은 번호 순서로 평가된다.
  3. 인스턴스에 붙인다인스턴스를 시작한 뒤에도 change security groups for your instance 로 그룹을 바꾸거나 여러 그룹을 함께 붙인다. 그룹이 여러 개면 모두의 규칙을 만족해야 통과한다.
  4. 확인해 볼 것보안 그룹 화면에서 각 규칙의 프로토콜·포트·출발지가 어떻게 찍혀 있는지 확인한다.

IAM role 을 인스턴스에 붙이기

권한이 정해진 AWS 신원 역할을 인스턴스에 연결해, 인스턴스 안의 프로그램이 자격 증명을 직접 만들지 않고 그 역할의 권한으로 AWS API 를 호출하게 하는 것.

먼저 알아야 할 것 10-02

→ 03-02 참조

#1문제 상황

인스턴스에서 AWS API를 부르려면 접근 키를 각 인스턴스에 직접 심어야 한다. AWS가 대신 만든 스팟 인스턴스나 Auto Scaling 인스턴스에는 심을 수 없고, 키를 바꿀 때마다 다시 배포해야 한다.

IAM roles는 이 문제를 없앤다. IAM role은 권한이 정해진 AWS 신분이고, 이를 인스턴스에 붙이면 instance profile을 통해 자격 증명이 자동으로 전달되어 키 관리를 안 해도 된다.

#2핵심 질문

인스턴스에서 비밀키를 직접 다루지 않고 AWS API를 부르려면?

#3동작 예시

S3에 이미지를 올리는 프로그램을 EC2 인스턴스에서 실행한다. 코드에는 접근 키가 없고 IAM role만 지정돼 있다. 실행하면 인스턴스가 스스로 자격 증명을 받아 그 role에 허용된 버킷에만 파일을 올린다.

#4동작 과정

  1. role을 만든다정책으로 허용할 작업을 정해 IAM role을 만든다. permission to pass IAM roles는 이 role을 인스턴스에 넘길 수 있게 하는 조건이다.
  2. 인스턴스에 붙인다attach a role to an instance로 인스턴스를 시작할 때 role을 지정하면 instance profile이 만들어진다. instance profile은 role을 담는 컨테이너다.
  3. 자격 증명을 받는다인스턴스 안의 프로그램은 retrieve security credentials로 임시 자격 증명을 받아 API를 부른다. 프로그램이 키를 저장하지 않으므로 남는 것이 없다.
  4. 확인해 볼 것EC2 콘솔의 인스턴스 상세에서 붙어 있는 role 이름이 Security 탭에 보이는지 확인한다.

NitroTPM

AWS 의 Nitro 시스템 안에 들어 있어, 인스턴스 부팅 시 measurements 라는 기록을 만들어 저장하는 TPM(신뢰된 플랫폼 모듈) 칩으로 암호화 키를 인스턴스 안에서 보호하는 기술.

먼저 알아야 할 것 10-03

#1문제 상황

인스턴스 안의 비밀번호나 인증서, 암호화 키는 외부에서 알 수 없는 곳에 있어야 한다. 그렇지 않으면 원격 서버가 내 인스턴스인증을 속일 수 있다.

NitroTPM은 인스턴스 안에 trusted platform module, 즉 비밀값을 안전하게 저장하는 칩을 제공한다. 이 칩이 키와 인증서를 지키고 부팅 과정도 기록한다.

#2핵심 질문

인스턴스 안의 암호화 키와 부팅 과정을 어떻게 지킬 수 있을까?

#3동작 예시

인스턴스를 시작하자마자 비밀키를 암호화해 저장한다. 이후 원격 서버가 서명 값을 요구하므로 NitroTPM이 저장된 키로 서명한다. 키가 인스턴스 밖으로 나오지 않는다.

#4동작 과정

  1. 지원 여부를 확인한다verify NitroTPM support로 인스턴스 유형이 NitroTPM을 지원하는지 보고, requirements에 적힌 운영체제와 인스턴스 유형 조건을 맞춘다.
  2. 활성화한다enable NitroTPM으로 인스턴스를 띄운다. 칩이 부팅 파일마다 measurements, 즉 해시값을 만들어 Platform Configuration Registers(PCR)에 누적해 둔다.
  3. 키를 묶는다키와 비밀값에 특정 PCR 값을 태그해 두면 그 값이 달라진 경우 키에 접근할 수 없게 된다. 부팅이 변조되면 자동으로 막힌다.
  4. 확인해 볼 것인스턴스를 NitroTPM 활성 상태로 시작할 수 있는지 콘솔에서 시도해 본다.

원격 서버에 사용 중인 비밀키가 실제 인스턴스 안에 안전하게 보관되어 있는지 암호적으로 확인해, 그 서버가 내가 시작한 인스턴스임을 증명하는 절차.

먼저 알아야 할 것 10-04

→ 10-04 참조

#1문제 상황

클라이언트는 비밀키로 서명해서 자기 신원을 밝힌다. 그런데 그 키가 정말 원격 서버 안에 안전하게 있는지 알 방법은 없다. 서버를 위조하면 아무도 모르게 키를 빼낼 수 있다.

EC2 instance attestation은 이 의심을 없앤다. NitroTPM(→ 10-04)에 저장된 키로 부팅 기록을 증명해 준다.

#2핵심 질문

내 비밀키를 들고 있는 서버가 정말 내가 띄운 인스턴스임을 어떻게 확인할까?

#3동작 예시

인스턴스에 접속한 클라이언트가 서버의 서명을 요구한다. 서버는 Attestation Document, 즉 증명 문서를 만들어 보낸다. 클라이언트는 이 문서의 measurement를 미리 받아 둔 기준값과 비교해 일치하면 접속을 허용한다.

#4동작 과정

  1. attestable AMI를 만든다증명용으로 처음부터 만든 attestable AMIs를 띄운다. 이 AMI의 기준 measurement를 미리 받아 둔다.
  2. 인스턴스를 띄운다NitroTPM이 켜진 인스턴스를 그 AMI로 시작한다. NitroTPM 도구로 Attestation Document를 만든다.
  3. 비교한다문서에 담긴 실제 measurement를 기준값과 맞춰 본다. 다르면 AMI 안의 소프트웨어나 설정이 바뀐 것이다. AWS KMS attestation을 써서 문서를 서명하고 KMS에 검증용으로 남길 수도 있다.
  4. 확인해 볼 것NitroTPM 도구가 만든 Attestation Document에 부팅 measurement가 들어 있는지 확인한다.

PrivateLink 와 데이터 보호

공개 인터넷으로 나가지 않고 AWS 내부의 사설 연결만 통하도록 VPC 엔드포인트를 만들어, 데이터가 AWS 밖으로 노출되지 않게 하는 방식.

먼저 알아야 할 것 10-02

#1문제 상황

VPC 안의 인스턴스가 AWS API를 부르려면 인터넷 게이트웨이나 NAT을 거쳐 공개 IP로 나가야 한다. 그 구간은 트래픽이 노출되고, 인프라 보안 규정도 어기게 된다.

AWS PrivateLink는 중간 장비 없이 VPC 안에서만 AWS 서비스로 직접 닿게 한다. interface VPC endpoint를 만들면 인스턴스에 공개 IP가 필요 없어진다.

#2핵심 질문

인스턴스를 공개 IP 없이 AWS 내부에서만 연결하려면?

#3동작 예시

인스턴스가 Amazon EC2 API를 호출하려 한다. internet gateway나 NAT, VPN 없이 VPC 안의 사설 주소로만 요청이 나가고, VPC 밖으로 나가지 않는다.

#4동작 과정

  1. 엔드포인트를 만든다서비스 이름 com.amazonaws.region.ec2로 interface VPC endpoint를 만든다. 엔드포인트는 VPC 안에서 해당 서비스로 이어지는 사설 연결 지점이다.
  2. 정책을 정한다endpoint policy를 붙여 그 경로로 갈 수 있는 요청을 제한한다. 기본값은 Amazon EC2 API 전체 접근이다.
  3. 연결을 지킨다data protection과 infrastructure security를 위해 public subnet과 라우팅을 점검하고 Resilience를 위해 여러 가용 영역에 엔드포인터를 둔다.
  4. 확인해 볼 것VPC 콘솔의 엔드포인트 목록에서 만든 엔드포인트가 privateIpAddress를 갖고 나타나는지 확인한다.

Status check — 인스턴스가 살아 있는지

인스턴스가 정상적으로 동작 중인지 두 단계로 확인하는 EC2의 기본 진단 기능으로, 1분마다 자동으로 검사해 시스템(status) 검사와 두 개 이상의 핵심 구성요소(인스턴스 status)를 각각 통과했는지 알려 줍니다.

먼저 알아야 할 것 01-05

#1문제 상황

인스턴스가 멈췄는지, 아직 부팅 중인지, 곧 종료될지 알 길이 없다. 원격 접속이 막힌 상태에서 원인을 알 수 없으면 복구도 늦다.

status checks는 EC2가 자동으로 돌리는 검사 결과다. 이 결과는 Amazon CloudWatch 지표(→ 11-02)와 합쳐 인스턴스별 운영 상황을 보여 준다.

#2핵심 질문

내 인스턴스가 지금 정상으로 돌아가고 있는지는 어떻게 아는가?

#3동작 예시

웹 서버 인스턴스에 접속이 안 되자 인스턴스 목록을 연다. system status check는 통과, instance status check는 2회 연속 실패로 나와 있다. 운영체제 쪽 구성요소가 문제라는 뜻이다.

#4동작 과정

  1. 자동 검사를 받는다EC2가 1분마다 system status check와 instance status check를 각각 돌려 결과를 남긴다. system은 운영체제 자체를, instance status check는 두 개 이상의 핵심 구성요소를 본다.
  2. 사건 상태를 함께 본다state change events와 scheduled events에서 재부팅이나 종료 같은 예정된 작업의 시각과 사유를 확인한다.
  3. 앱 상태를 따로 본다application status checks를 붙이면 내가 정한 방식으로 인스턴스 안의 애플리케이션 응답까지 검사한다.
  4. 확인해 볼 것콘솔 인스턴스 목록의 Status checks 열에서 두 검사의 통과 횟수를 확인한다.

먼저 알아야 할 것 11-01

→ 11-01 참조

#1문제 상황

인스턴스가 살아 있다는 사실(→ 11-01)만으로는 서비스가 느려지는 이유를 알 수 없다. 문제가 커지기 전에 CPU나 네트워크 사용량 이상을 먼저 알아야 한다.

CloudWatch metrics는 CPU 사용량과 네트워크 트래픽 같은 값을 시간별 수치로 모은다. 여기에 alarm을 두면 임계치를 넘는 순간 알림이 간다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 지표가 쌓인다EC2는 기본적으로 5분 단위로 지표를 보내고 이력은 15개월간 남는다. detailed monitoring을 켜면 1분 단위로 좁혀 보낸다.
  2. alarm을 만든다인스턴스 alarms를 정해 임계치와 유지 시간을 지정한다. 조건이 맞으면 알림 상태로 바뀐다.
  3. 행동을 붙인다alarm action으로 알림 대상과 자동 처리 도구를 지정한다. 지표 원본은 CloudWatch 콘솔의 그래프로 따로 볼 수 있다.
  4. 확인해 볼 것CloudWatch 콘솔의 알림 목록에서 만든 alarm이 정상 상태로 보이는지 확인한다.

EventBridge로 자동 대응

인스턴스 상태가 바뀌는 등의 EC2 이벤트를(EventBridge) 받아 Lambda 함수나 자동화 도구를 곧바로 실행해, 알림 보내기부터 자동 복구까지 사람의 개입 없이 이어지는 자동 대응 체계를 만드는 방법입니다.

먼저 알아야 할 것 11-01

#1문제 상황

인스턴스가 멈췄는지 알림을 받으려면 사람이 상태 확인을 반복해야 한다(→ 11-01). 이런 확인을 사람이 하지 않는다면 장애가 오래 남는다.

Amazon EventBridge는 AWS 서비스에서 일어나는 일을 거의 즉시 받아 규칙으로 걸러내는 서비스다. EC2의 state change events 같은 신호가 오면 정해 둔 동작을 자동 실행한다.

#2핵심 질문

인스턴스 상태가 바뀔 때 알림과 자동 복구를 어떻게 사람의 개입 없이 잇는가?

#3동작 예시

밤 사이에 테스트 서버 인스턴스가 stopped 상태로 넘어갔다고 하자. EventBridge가 그 이벤트를 받아 Lambda 함수를 실행하고, 함수는 SNS 토픽으로 알림을 보낸다.

같은 규칙에 EC2 Run Command 호출을 묶어 두면 인스턴스를 재부팅시키는 명령까지 자동으로 나간다.

#4동작 과정

  1. 이벤트를 받는다Amazon EventBridge가 인스턴스 상태 변화 같은 state change events를 받아 온다. 누가 어떤 API 호출을 했는지는 AWS CloudTrail 기록에서 볼 수 있고, 감사에 쓸 수 있다.
  2. 규칙으로 거른다이 규칙에 create alarm for instance state changes를 걸어 두고 원하는 이벤트만 골라 낸다. 규칙은 어떤 이벤트를Interested에 따라 거르고 어떤 동작을 붙일지 정한다.
  3. 동작을 실행한다규칙에 맞는 이벤트에 Lambda 함수 실행, EC2 Run Command, SNS 토픽 알림, SQS 큐 전송 같은 action calls를 건다. 앞의 세 가지 11-01 이후 상태 판단과 함께 쓰면 자동 복구 흐름이 된다.
  4. 확인해 볼 것EventBridge 콘솔의 규칙 목록에서 만든 규칙이 이벤트 패턴과 연결된 대상 두 개를 함께 보여 주는지 본다.

#1문제 상황

인스턴스 상태가 바뀐 건 운영체제 권한 문제인지 자동 예약인지 지금 알 수 없다. 예약된 작업이 왜 실행됐는지 기록으로 확인하려면 예약 기능 자체가 필요하다.

Scheduled events는 특정 시각에 인스턴스를 재부팅·중지·종료하도록 미리 예약하는 기능이다. 예약과 실행 기록이 남아 있어 예약대로 동작했는지 검증할 수 있다.

#2핵심 질문

예약해 둔 재부팅이 왜 그리고 언제 실행됐는지 어떻게 확인하는가?

#3동작 예시

정기 점검이 예정돼 인스턴스 재부팅이 예약돼 있다. 콘솔 대시보드에서 해당 인스턴스가 Scheduled events 항목에 뜬 것을 보고, Events 창에서 재부팅 시각과 사유를 본다.

유지보수 기간을 앞당기고 싶다면 그 예약만 다시 잡아 일정을 바꾼다.

#4동작 과정

  1. 예약한다특정 시각에 재부팅·중지·종료가 되도록 scheduled events를 미리 만든다. AWS가 자동 처리하는 유형이면 별도 요청 없이 유지보수 일정이 함께 들어간다.
  2. 목록에서 찾는다콘솔 대시보드의 Scheduled events 영역과 Events 창에서 예약된 리소스를 본다. 이벤트 유형·리소스 유형·가용 영역으로 거를 수 있고, event windows로 처리 시간 구간을 본다.
  3. 기록으로 검증한다명령 줄의 describe-instance-status로 인스턴스 이벤트를 조회해 예약 시각과 사유를 확인한다. 실행 시각이 안 맞으면 예약을 reschedule로 다시 잡는다.
  4. 확인해 볼 것Events 창에서 예약된 인스턴스에 사유와 시작·종료 시각이 붙어 있는 항목이 보이는지 확인한다.

#1문제 상황

인스턴스가 시작되지도 않아 원격 접속 자체가 불가능하다(→ 11-01). 네트워크가 살아나지 않은 unreachable instances 상태라 SSH도 RDP도 연결할 방법이 없다.

EC2 Serial Console는 인스턴스에 모니터를 키보드로 직접 붙여 원격으로 조작하는 기능이다. networking capabilities 없이도 부팅 과정 텍스트를 볼 수 있다.

#2핵심 질문

원격 접속이 전혀 안 되는 인스턴스의 boot failures 로그를 어떻게 본다?

#3동작 예시

운영체제가 로딩도 되지 않아 인스턴스가 계속 pending에 머문다. EC2 Serial Console를 열면 부팅 순간의 텍스트가 줄줄이 나타나 어디서 멈췄는지 읽힌다.

#4동작 과정

  1. 권한을 준비한다prerequisites로 조직이 계정 접근을 허용하고 사용자에게 IAM 정책을 부여해야 한다. 기본값으로는 열려 있지 않다.
  2. 접근 범위를 좁힌다인스턴스 ID와 리소스 태그 같은 IAM 수단으로 인스턴스 단위 권한을 준다. 누가 어느 서버를 봤는지 흔적을 남길 수 있다.
  3. 부팅 화면을 본다콘솔이나 AWS CLI로 세션을 열어 키보드·모니터를 붙인 것처럼 명령을 입력한다. 인스턴스 재부팅·중지 동안에도 세션이 이어지며, 재부팅 시점의 모든 부팅 메시지를 볼 수 있다.
  4. 확인해 볼 것Serial Console 창에 커널 부팅 메시지가 시간 순서로 흐르는지 확인한다.
