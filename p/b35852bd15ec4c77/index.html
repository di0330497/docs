1GraphQL 개관과 자리잡기01-01

GraphQL 정의와 REST 대비 특성

GraphQL은 타입 시스템으로 기술된 API에 대해 필요한 만큼만 요청하고 버전 없이 진화시키는 질의 언어이자 런타임이다.

#1문제 상황

기존 REST 방식에서는 엔드포인트마다 정해진 응답이 돌아오므로 화면에 필요한 조각이 여러 자원에 흩어지면 여러 번 요청해야 했다. 남는 필드까지 함께 받거나 모자란 조각을 또 요청하는 일이 잦았고, 자원이 바뀔 때마다 새 버전의 엔드포인트를 열어 관리 부담이 커졌다.

#2핵심 질문

화면이 필요한 데이터만 한 번에 요청하고 서버는 같은 계약으로 계속 진화할 수는 없을까?

#3동작 예시

me { name } 같은 조회는 타입에 정의된 me와 User의 name에서 딱 그 값만 돌려받고, 서버는 각 필드에 붙은 함수로 값을 채운다. 스펙이 2015년에 공개된 뒤 여러 언어가 같은 계약으로 구현을 내놓았고, 특정 저장소에 종속되지 않고 기존 코드와 데이터를 그대로 잇는다.

#4동작 과정

  1. 타입으로 기술제공할 데이터의 모양을 타입과 필드로 먼저 적어 계약으로 삼는다.
  2. 필요분만 조회클라이언트가 고른 필드만 실행해 한 번의 요청으로 받는다.
  3. 함수로 채우기각 필드의 리졸버 함수가 기존 코드와 데이터를 이어 결과를 만든다.

1GraphQL 개관과 자리잡기01-02

타입 시스템으로 API 기술하기

스키마는 조회 가능한 데이터의 집합을 타입으로 기술한 계약이며 모든 요청은 그 계약에 대해 검증·실행된다.

#1문제 상황

기존에는 API가 무엇을 주는지 문서나 예제 응답으로 어림잡았고, 문서와 실제 동작이 어긋나면 클라이언트가 실행 중에야 문제를 알았다. 필드가 사라지거나 형태가 바뀌어도 요청을 보내기 전에 알 방법이 마땅치 않아 수정과 확인이 반복됐다.

#2핵심 질문

조회 가능한 데이터를 미리 정확히 기술해 요청 전에 결과를 예측할 수는 없을까?

#3동작 예시

type Character { name: String! appearsIn: [Episode!]! }처럼 객체와 필드를 적어 두면 hero { name } 요청이 무엇을 돌려줄지 스키마만 보고 알 수 있다. 여섯 가지 명명 타입과 수정자로 가능한 조합을 닫힌 집합으로 표현하므로 요청 모양과 결과 모양이 나란히 맞는다.

#4동작 과정

  1. 가능 집합 선언스키마가 조회 가능한 타입과 필드의 전체를 미리 적는다.
  2. 계약 대조 검증들어온 요청을 스키마에 비추어 실행 전에 가부를 가린다.
  3. 예측 가능한 실행검증된 요청만 실행해 요청 모양을 닮은 결과를 돌려준다.

1GraphQL 개관과 자리잡기01-03

그래프 사고와 비즈니스 로직 층

도메인을 노드와 관계의 그래프로 모델링하고 검증·권한·오류 규칙은 단일 비즈니스 로직 층에 둔다.

#1문제 상황

기존에는 REST와 RPC 같은 진입점마다 검증과 권한과 오류 처리를 따로 두어 같은 규칙이 통로별로 어긋나기 쉬웠다. 스키마를 저장소 구조 그대로 본뜨면 클라이언트 쓰임새와 맞지 않는 모양이 그대로 노출됐고, 통로를 바꿀 때마다 다른 결과가 돌아왔다.

#2핵심 질문

프래그먼트 재사용과 인자

프래그먼트는 필드 집합의 재사용 단위로 여러 조회에 끼워 쓰고 인자로 변형을 줄 수 있다.

#1문제 상황

기존에는 두 영웅을 나란히 보는 화면처럼 같은 필드 묶음이 반복되면 질의가 길어지고 고칠 곳도 여러 군데로 흩어졌다. 묶음마다 조금씩 값을 다르게 주고 싶어도 묶음 단위에서는 값을 받을 방법이 없었다.

#2핵심 질문

필드 묶음을 이름으로 묶어 쓰고 묶음마다 값을 따로 줄 수는 없을까?

#3동작 예시

#4동작 과정

  1. 묶음 빼내기반복되는 필드 집합을 이름 있는 조각으로 둔다.
  2. 자리에 끼우기필요한 조회마다 조각을 펼쳐 넣는다.
  3. 값 달리 주기끼워 넣는 자리마다 인자 값을 다르게 준다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 공통 먼저 읽기추상 자리의 공통 필드를 그대로 읽는다.
  2. 조건 붙이기종류별 필드를 타입 조건 조각 안에 적는다.

#2핵심 질문

권한 위임과 스키마 지시자

인가는 비즈니스 로직 층에 위임하고 스키마에는 규칙을 드러내는 지시자 정도만 둔다.

#1문제 상황

기존에는 인가 코드를 리졸버마다 박아 넣어 같은 규칙이 통로별로 어긋났다. 글쓴이 본인만 보게 하려 해도 진입점마다 코드를 맞추느라 한쪽이 새기 일쑤였다.

#2핵심 질문

인가 규칙은 한곳에 모으고 스키마에는 규칙의 자리만 드러낼 수는 없을까?

#3동작 예시

Post의 body를 돌려줄지는 글쓴이인지를 따지는 저장소 함수에 맡기고, 리졸버는 그 함수에 사용자와 글을 넘겨 답만 받는다. @auth(rule: IS_AUTHOR) 같은 지시자를 달아 둘 수도 있으나 셈은 여전히 비즈니스 로직 층에서 한다.

#4동작 과정

  1. 규칙 모으기인가 셈을 비즈니스 로직 층의 한곳에 둔다.
  2. 얇게 잇기리졸버는 사용자 정보만 넘기고 답만 받는다.
  3. 자리 드러내기스키마에는 규칙이 걸린 자리를 지시자로 보인다.

페더레이션 합성과 분산 스키마

페더레이션은 여러 서비스의 스키마를 합쳐 단일 그래프로 제공하는 분산 구성이다.

#1문제 상황

기존에는 덩치가 큰 하나의 스키마를 한 팀이 붙들고 있어 고칠 때마다 줄이 길어졌다. 쪼개자니 조각들이 따로 놀아 하나의 그래프처럼 보이지 않았다.

#2핵심 질문

팀마다 조각을 맡기면서도 바깥에서는 하나의 그래프로 보이게 할 수는 없을까?

#3동작 예시

각 서비스가 자기 조각의 스키마를 맡아 내놓으면 합성 과정에서 하나의 그래프로 꿰매어 단일 끝점처럼 보인다. 합성 스키마 워킹그룹이 이 꿰매기의 표준을 다듬어 여러 구현이 같은 방식으로 합치게 한다.

#4동작 과정

  1. 조각 맡기기각 서비스가 자기 몫의 스키마를 내놓는다.
  2. 하나로 꿰매기조각들을 합쳐 단일 그래프로 보인다.
  3. 표준 맞추기같은 합성 규칙을 여러 구현이 함께 쓴다.

소유권과 거버넌스 모델

중앙·연합·혼합 소유권 모델 중 조직에 맞는 스키마 운영 주체를 정한다.

#1문제 상황

기존에는 스키마의 어느 조각을 누가 맡는지 정해져 있지 않아 고칠 때마다 눈치를 봤다. 한 팀이 다 붙들면 일관성은 서는데 느려졌고, 각자 맡기면 빠르지만 모양이 어긋났다.

#2핵심 질문

조직의 속도와 감시에 맞는 맡김 모양을 고를 수는 없을까?

#3동작 예시

한 팀이 전체를 맡는 중앙형과 팀마다 맡는 연합형과 섞은 혼합형 가운데 점찍고, 맡은 경계와 바꾸는 절차를 문서로 굳힌다. 쓰임과 감시와 돌림 속도를 저울질해 맞는 모양을 고른다.

#4동작 과정

  1. 모양 고르기중앙형과 연합형과 혼합형 가운데 점찍는다.
  2. 경계 굳히기누가 어느 조각을 맡는지 문서로 굳힌다.
  3. 저울질하기일관성과 돌림 속도를 함께 달아 절차를 정한다.

#2핵심 질문

바꿈을 심사하는 절차와 기계를 두고 버전 걱정을 덜 수는 없을까?

#3동작 예시

조각마다 맞는 심사 무게를 정해 한 팀은 가벼운 코드 심사로, 여러 팀은 자동 검사와 승인으로, 겹치는 조각은 합성 검사와 함께 본다. 주기적인 감사로 묵은 표시와 비대해진 자리를 돌본다.

#4동작 과정

  1. 무게 맞추기조각과 겹침에 맞는 심사 절차를 정한다.
  2. 기계 세우기자동 검사와 승인문을 심사길에 세운다.
  3. 돌아보기주기 감사로 묵은 표시와 비대함을 다듬는다.

고급 실행 파이프라인과 실험 기능

#1문제 상황

기존에는 execute 한 방으로 돌리다 보니 실행 중간에 끼어들 여지가 없었다. 인가와 변수 다듬기와 결과 직렬화를 매번 손으로 엮어야 해서 파이프라인을 나누고 싶어도 나눌 도구가 없었다.

#3동작 예시

#4동작 과정

  1. 미리 다듬기실행 인자를 검증해 validated 덩어리로 만든다.
  2. 나눠 돌리기루트 선택 집합 실행을 따로 떼어 돌린다.
  3. 곁가지 넓히기실험 기능과 신호와 훅과 추적을 곁들인다.
