1. S3의 뼈대 — 버킷·오브젝트·키와 네 종류의 버킷01-01

Amazon S3 란 무엇인가

Amazon S3는 클라우드에서 파일을 저장하고 필요할 때 내려받는.object 스토리지 서비스로, 버킷이라는 컨테이너에 오브젝트라는 파일 조각을 넣어 관리한다.

#1문제 상황

앱이 만든 사진과 문서를 앱 서버의 디스크에 두면 서버가 사라질 때 함께 사라지고, 사람이 직접 옮겨야 늘어난다. Amazon S3는 이런 파일을 클라우드에 두어 크기 상관없이 저장하고 어디서든 다시 꺼내 쓰게 한다.

Amazon S3는 object storage, 즉 파일 단위로 저장하는 서비스다. 데이터 레이크, 웹사이트, 백업, 빅데이터 분석 같은 곳에 쓰인다. 파일은 bucket이라는 이름 붙은 통에 넣고, 안의 각 파일 조각을 object라고 부른다. object storage / bucket / object / object key 라는 네 단어가 이후 모든 설명의 뼈대다(→ 01-02, 01-03).

bucket은 AWS Region 안에 만들어지고, Region은 데이터가 실제로 놓이는 지리적 구역이다. S3는 이 통마다 암호화, 접근 권한, 비용 집계 같은 관리 기능을 붙여 준다.

#3동작 예시

앱이 사용자 사진을 올리면 PutObject로 버킷 안에 오브젝트가 생기고, 화면에는 그 키의 URL이 저장된다. 다른 사람이 그 주소를 열면 S3가 파일을 그대로 돌려준다.

#4동작 과정

  1. 버킷을 만든다이름 붙은 통을 리전에 세운다. 안에 들어갈 파일의 규모와 용도에 따라 종류를 고른다(→ 01-04).
  2. 오브젝트를 올린다key라는 이름과 함께 데이터를 보낸다. 대용량 파일은 여러 조각으로 나눠 올린다(→ 04-01).
  3. 내려받아 쓴다key로 찾아 읽거나 다른 이름으로 복사한다(→ 03-01, 03-02).
  4. 확인해 볼 것콘솔에서 버킷을 열어 오브젝트 목록에 방금 올린 이름과 크기가 보이는지 본다.

버킷과 오브젝트 — 무엇이 무엇을 담는가

버킷은 오브젝트를 담는 이름 붙은 컨테이너이고, 오브젝트는 버킷 안에 저장되는 파일의 실제 데이터와 그 파일을 설명하는 정보를 묶은 단위다.

먼저 알아야 할 것 01-01

#1문제 상황

클라우드에 파일을 두려면 몇 가지를 정해야 한다. 어떤 통에 넣을지, 통 안에서 파일을 어떻게 부를지, 파일과 함께 무엇을 남길지가 정해지지 않으면 나중에 그 파일을 못 찾는다(→ 01-01).

S3의 두 단위는 이렇게 나뉜다. bucket은 오브젝트를 담는 이름 붙은 컨테이너고, object는 그 안에 저장되는 하나하나의 파일이다. general purpose buckets, 즉 범용 버킷은 일반 파일을 담는 기본 형태다(→ 01-04).

오브젝트는 세 부분으로 이루어진다. object key는 오브젝트를 부르는 이름이다. object data, 즉 value는 저장한 본문으로 0바이트부터 50TB까지의 바이트 나열이다. metadata는 본문과 따로 붙는 설명 정보로, Content-Type처럼 파일 형식을 알려 준다(→ 01-06). 여기에 S3가 붙이는 version ID가 있어 같은 키가 여러 번 저장돼도 각 판을 구별한다(→ 10-01).

#2핵심 질문

S3는 파일을 어떤 단위로 담고 그 안에서 어떻게 부르는가?

#3동작 예시

개발자가 콘솔에서 버킷 하나를 열어 report.pdf를 올린다. 목록에는 report.pdf라는 키가 뜨고, 그 줄을 열면 본문과 함께 파일 형식과 크기, 버전 ID가 함께 나온다.

#4동작 과정

  1. 버킷을 연다범용 버킷 하나가 파일을 담는 자리다. 버킷 이름 규칙을 지켜야 만든다(→ 02-01).
  2. 오브젝트를 올린다key와 함께 데이터를 보낸다. 본문 바이트와 metadata가 한 단위로 묶여 저장된다.
  3. 버전을 함께 본다버전 관리가 켜진 버킷에서는 key와 version ID가 합쳐져 오브젝트 하나를 가리킨다(→ 10-02).
  4. 확인해 볼 것오브젝트 하나를 선택해 상세 화면에 Content-Type과 크기가 함께 표시되는지 본다.

오브젝트 키는 버킷 안에서 각 오브젝트를 유일하게 가리키는 문자열 이름으로, 슬래시(/)로 폴더처럼 경로 구조를 흉내 낼 수 있다.

먼저 알아야 할 것 01-02

#1문제 상황

버킷 안의 오브젝트는 폴더로 분류되지 않는다(→ 01-02). 그런데 수만 개를 한데 쌓아두면 나중에 원하는 파일을 찾을 수 없다. 그래서 버킷 안에서 오브젝트마다 이름을 직접 정한다.

object key, 즉 key name은 버킷 안에서 오브젝트를 유일하게 가리키는 문자열 이름이다. 앞뒤로 붙은 접두사와 대괄호 없는 슬래시가 층을 만든다. 예를 들어 photos/puppy.jpg에서 photos는 key prefix, 즉 접두사고 그 뒤가 파일 이름이다. 콘솔은 이 구조를 폴더처럼 보여 준다.

키 이름은 UTF-8로 인코딩된 유니코드 문자의 나열이며 최대 1,024바이트다. 접두사와 슬래시, 파일 이름을 모두 합쳐 이 한도를 쓴다. 대소문자를 구별하고 문자 집합(character set)에 따라 한 글자가 여러 바이트를 차지할 수 있다.

네 가지 버킷 종류 — 무엇을 담는 버킷인가

S3의 버킷은 범용 버킷, 디렉터리 버킷, 테이블 버킷, 벡터 버킷의 네 종류로 나뉘며, 각각 일반 파일, 키-값 대량 조회, 표 형식 데이터, 벡터 검색이라는 다른 용도를 맡는다.

먼저 알아야 할 것 01-02

#1문제 상황

버킷 하나에 아무 파일이나 넣으면 관리가 복잡해진다. 대용량 키-값 데이터를 키마다 조회하려면 매번 전체를 훑어야 하고, 표 형식 데이터는 열 단위로 잘라야 한다. 용도마다 요구하는 조회 방식이 다르다(→ 01-02).

그래서 S3의 버킷은 네 종류로 나뉜다. general purpose buckets는 일반 파일을 담고, directory buckets는 키-값 데이터를 한 번에 많이 조회하는 데 맞고, table buckets는 표 형식 데이터의 행과 열을 다루며, vector buckets는 벡터 검색을 맡는다. 디렉터리 버킷은 리전 아래 s3express 네임스페이스 안에 만들어진다.

이름의 유일성은 파티션 단위로 갈린다. 파티션은 aws와 aws-cn, aws-us-gov처럼 AWS 계정 환경이 나뉜 묶음이다. 같은 파티션 안에서 버킷 이름이 겹치지 않아야 한다(→ 02-01).

#2핵심 질문

어떤 모양의 데이터를 담는 버킷을 골라야 하는가?

#3동작 예시

#4동작 과정

  1. 용도를 고른다일반 파일이면 범용 버킷, 키-값 대량 조회는 디렉터리 버킷을 고른다.
  2. 특수 형태면 전용 버킷을 쓴다표 형식은 table buckets, 벡터 검색은 vector buckets가 맡는다.
  3. 이름이 겹치지 않게 한다같은 파티션 안에서 버킷 이름을 지킨다(→ 02-01).
  4. 확인해 볼 것버킷 속성 화면에 버킷 유형이 범용 버킷으로 표시되는지 본다(→ 02-04).

1. S3의 뼈대 — 버킷·오브젝트·키와 네 종류의 버킷01-05

일관성 모델 — 쓰고 바로 읽으면 무엇이 보이나

S3는 오브젝트 목록과 읽기에 강한 일관성을 제공해 쓰자마자 읽으면 방금 쓴 데이터가 보이고, 버킷 설정 같은 관리 정보만 최종 일관성을 갖는다.

먼저 알아야 할 것 01-02

#1문제 상황

여러 대의 서버가 같은 버킷에 파일을 올리는 상황에서, 방금 쓴 파일이 목록에 아직 안 보이는 일이 생기면 코드가 꼬인다. 읽기와 목록이 언제 반영되는지 알아야 그 위에서 설계를 세울 수 있다(→ 01-02).

S3는 strong read-after-write consistency, 즉 쓰자마자 읽으면 방금 쓴 내용이 그대로 보인다. 목록 API도 같은 성질을 갖는다.

여러 쓰기가 겹칠 때 last-writer-wins가 적용된다. 같은 키에 동시에 쓰면 가장 나중의 쓰기가 남고, atomic updates로 갱신이 중간에 보이지 않는다. 반면 bucket configurations처럼 버킷 설정을 바꾸는 관리 정보는 eventual consistency를 가져 다른 리전의 복제 지점에서 잠시 옛 값이 보일 수 있다.

#2핵심 질문

방금 쓴 오브젝트를 바로 읽고 목록에서 찾을 수 있는가?

#3동작 예시

서버가 PutObject로 report.csv를 올린 직후 GetObject로 읽으면 방금 보낸 바이트가 그대로 나온다. 이어 같은 키를 덮어써도 S3 안에는 두 판이 남고 읽을 때 마지막에 쓴 판이 나온다(→ 10-01).

#4동작 과정

  1. 쓴다PutObject가 끝나면 그 데이터는 바로 읽을 수 있는 상태가 된다. 갱신은 atomic updates로 처리된다.
  2. 읽고 목록을 본다strong read-after-write consistency로 방금 쓴 값이 즉시 보인다. 겹친 쓰기는 last-writer-wins로 정해지고 오브젝트 목록에도 새 키가 바로 오른다(→ 05-02).
  3. 설정을 본다버킷 설정은 eventual consistency라 다른 리전에서 옛 값이 잠깐 보일 수 있다.
  4. 확인해 볼 것업로드 직후 목록 새로 고침에서 방금 올린 키가 보이는지 본다.

메타데이터 — 파일을 설명하는 짐

메타데이터는 오브젝트의 본문과 따로 저장되는 설명 정보로, 사용자 정의 키-값 쌍(Content-Type, Cache-Control 등)으로 파일의 형식과 처리 방식을 지정한다.

먼저 알아야 할 것 01-02

#1문제 상황

오브젝트를 내려받으면 본문만 온다. 브라우저가 이게 텍스트인지 이미지인지 알 수 없어 제목을 저장하지 않고, 캐시 정책도 적용할 수 없다(→ 01-02).

metadata는 이 설명을 본문과 따로 저장한다. S3가 직접 채우는 system-defined metadata에는 Content-Type처럼 파일의 MIME 형식을 나타내는 값이 들어간다. 업로드할 때 사용자가 붙이는 user-defined metadata는 Content-Type, Cache-Control 같은 키-값 쌍이며, S3는 사용자 정의 키 앞에 x-amz-meta를 붙여 다른 키와 구분한다.

올라간 뒤에는 user-defined metadata를 고칠 수 없다. 고치려면 값을 바꿔 오브젝트 사본을 새로 만들어야 한다(→ 03-02).

#2핵심 질문

본문과 따로 어떤 정보를 붙여 파일을 어떻게 다뤄야 하는지 알려 주는가?

#3동작 예시

파일을 올릴 때 Content-Type을 image/png로 지정한다. 브라우저가 그 주소로 접근하면 저장된 메타데이터를 보고 이미지로 렌더링한다. Cache-Control도 함께 붙여 캐시 기간을 정한다.

#4동작 과정

  1. 올릴 때 값을 붙인다user-defined metadata를 키-값 쌍으로 넣어 업로드한다.
  2. 형식이 전달된다system-defined metadata의 Content-Type으로 본문의 형식이 알려 진다.
  3. 고치려면 새로 만든다붙인 값을 바꾸려면 오브젝트를 복사해 다시 올린다(→ 03-02).
  4. 확인해 볼 것오브젝트 상세 화면의 Metadata 탭에 Content-Type이 보이는지 본다.

버킷 이름 규칙과 한계

S3 버킷 이름은 같은 리전과 파티션(aws / aws-cn / aws-us-gov / aws-eusc) 안에서 유일해야 하며 3~63자 소문자·숫자·하이픈과 점으로만 이루어지고 IP 주소 형태로 해석되지 않아야 하는 등 길이와 문자, 형식에 대한 제약이 있다.

먼저 알아야 할 것 01-04

#1문제 상황

버킷 이름은 S3가 관리하는 전역 이름이라 아무 이름이나 쓸 수 없다. 실수로 겹치거나 나중에 못 찾으면 문제가 된다. 범용 버킷이 어떤 이름과 길이까지 받는지 알아야 한다(→ 01-04).

bucket naming rules는 네 가지를 정한다. 3-63 characters, 즉 3자에서 63자까지의 길이. 소문자(lowercase), 숫자, 점, 하이픈만 쓸 수 있고, 이름이 IP 주소 형태로 해석되지 않아야 한다. 그리고 global namespace, 전 세계 이름 공간에서 이름이 겹치지 않아야 한다. 같은 계정 안의 리전마다 이름을 따로 쓰는 regional namespace도 있다.

버킷이 범용 버킷이 아니면 이 규칙이 달라진다. BucketRestrictions와 같은 설정에서 허용 문자나 형식이 더 느슨해진다. 디렉터리 버킷은 이름에 영역 지정 접미사를 붙인다(→ 11-02).

#2핵심 질문

버킷에 어떤 이름과 길이까지 붙일 수 있는가?

#3동작 예시

개발자가 media-2026-reports라는 이름을 짓는다. 소문자와 숫자, 하이픈만 있고 IP 주소처럼 보이지 않아 규칙을 통과한다. 같은 리전의 계정 안에 같은 이름이 이미 있으면 거절된다.

#4동작 과정

  1. 길이와 문자를 맞춘다3~63자 안에서 소문자·숫자·하이픈·점만 쓴다.
  2. IP 형태로 안 읽히게 한다숫자만 나열된 점 표기가 들어가면 안 된다.
  3. 겹치지 않는 이름을 고른다global namespace를 피해 조직 접두어를 넣고, 계정 안에서만 쓸 거면 regional namespace를 쓴다(→ 02-03).
  4. 확인해 볼 것버킷 생성 화면에 이름을 넣었을 때 규칙 위반 사유가 즉시 뜨는지 본다.

버킷 만들기 — 이름과 리전을 고른다

버킷 만들기는 사용할 이름과 리전, 디렉터리 버킷인지 일반 목적 버킷인지, 암호화 여부를 정해 AWS 콘솔·CLI·SDK·API 중 하나로 버킷을 생성하는 작업이다.

먼저 알아야 할 것 02-01

→ 02-01 참조

#1문제 상황

버킷 이름은 전 세계에서 하나뿐이어야 하고, 만든 뒤에는 이름·소유자·리전을 바꿀 수 없다(→ 02-01). 이름과 리전을 미리 정하지 않으면 나중에 다시 만들 일이 생긴다.

create a general purpose bucket, 즉 범용 버킷을 만들면 이름과 AWS Region, 즉 데이터가 저장되는 지리적 구역을 고르고 S3가 관리하는 암호화 설정을 켠다. 만든 계정이 그 버킷의 소유자가 된다.

#2핵심 질문

어떤 이름과 리전으로 버킷을 만들고 누가 소유하게 하는가?

#3동작 예시

S3 콘솔의 Buckets 화면에서 Create bucket을 누르고 이름 칸에 my-app-images, 리전 목록에서 서울 리전을 고른다.

Object Ownership 설정에서 Bucket owner enforced, 즉 새 오브젝트의 소유자와 ACL을 버킷 소유자로 고정하는 방식을 고르고 버킷을 만든다. 목록에 방금 만든 버킷이 열린다.

#4동작 과정

  1. 이름과 리전을 정한다범용 버킷을 만들 때 반드시 고르는 두 값이다. 둘 다 만든 뒤에는 바꿀 수 없어서 처음부터 잘 정해야 한다.
  2. 소유 규칙을 정한다Object Ownership에서 Bucket owner enforced를 고르면 이후 올라오는 모든 오브젝트의 소유자가 버킷 소유자가 되고 ACL은 꺼진다.
  3. 만든다console, CLI, SDK, REST API 가운데 아무 경로로나 버킷 생성 요청을 보낸다. 성공하면 버킷이 계정 목록에 추가된다.
  4. 확인해 볼 것콘솔의 버킷 목록에서 방금 만든 버킷 이름과 Region이 보이는지 확인한다.

버킷 이름 패턴 — 충돌을 피하는 관례

버킷 이름은 전 세계에서 하나뿐이어야 하므로 서비스·환경·계정·리전 같은 접두사와 접미사를 조합해 조직 안에서 사람이 읽고 구별할 수 있는 이름 패턴을 짓는 관례가 있다.

먼저 알아야 할 것 02-01

→ 02-01 참조

#1문제 상황

버킷 이름은 전 세계 하나뿐이라 이미 쓰인 이름을 그대로 고르면 다른 계정이 그 이름을 먼저 가져갈 수 있다. AWS는 예측하기 어려운 이름을 권고한다(→ 02-01).

common bucket patterns는 이 문제를 피하려고 정한 이름 짓기 방식이다. 애플리케이션 이름 뒤에 랜덤 접미사, 즉 예측할 수 없는 임의 문자열을 붙여 실수로 겹칠 확률을 낮춘다.

#2핵심 질문

전 세계에서 겹치지 않고 찾기 쉬운 버킷 이름을 어떻게 지을까?

#3동작 예시

어떤 서비스의 이미지 저장 버킷을 만든다고 하자. AWS가 권하는 방식대로 my-app-images 뒤에 난수를 붙여 my-app-images-a8f3c1을 고른다.

나중에 목록에서 서비스 이름 부분만 보고 어떤 버킷인지 알아보며, 이름이 남에게 맞힐 수 없어 다른 계정이 선점할 수도 없다.

#4동작 과정

  1. 기준을 고른다multi-tenant 버킷은 팀이나 워크로드마다 버킷을 따로 두고, bucket-per-use는 용도 하나에 버킷 하나를 두는 방식이다. 문서에는 이 두 패턴과 계정별 리전 네임스페이스가 제시된다.
  2. 애플리케이션 이름을 넣는다prefix and suffix naming, 즉 앞뒤에 이름을 덧붙여 사람이 읽을 수 있는 부분을 남긴다. AWS 소유 계정의 튜토리얼은 계정 번호를 접두사에 쓴다.
  3. 접미사로 충돌을 막는다random suffix를 붙여 이름을 예측 불가능하게 만든다. 만들어지기 전까지 이름이 비어 있다고 가정하지 않는다.
  4. 확인해 볼 것만든 버킷 이름이 애플리케이션 이름과 난수 접미사로 나뉘어 있는지 확인한다.

버킷 속성과 목록 보기

ListBuckets는 계정이 소유한 버킷 목록과 생성 시각·리전을 돌려주고, 버킷 속성 보기 기능은 선택한 버킷의 리전·버킷 유형·암호화·버전 관리·태그 같은 설정값을 콘솔에서 확인하게 해 준다.

#1문제 상황

버킷을 여러 개 만들면 어느 것이 무슨 용도이고 어떤 설정인지 관리하기 어렵다. 설정 하나를 기억 못하면 암호화나 버전 관리 여부를 착각한다.

view bucket properties를 쓰면 한 버킷의 설정을 한 화면에서 확인할 수 있다. 계정 전체의 버킷 목록은 list buckets, 즉 ListBuckets API로 함께 본다.

#2핵심 질문

내가 가진 버킷이 어떤 설정으로 만들어졌는지를 어디서 확인하는가?

#3동작 예시

S3 콘솔에서 버킷 하나를 골라 Properties 탭을 연다. 버킷 ARN, 리전, 생성일, 버전 관리 상태, 기본 암호화 설정, 태그 목록이 표로 나온다.

같은 콘솔의 Buckets 화면이나 ListBuckets API로는 이 계정이 소유한 버킷 이름과 생성 시각, 리전을 한 번에 볼 수 있다.

#4동작 과정

  1. 목록을 가져온다list buckets, 즉 ListBuckets가 소유한 버킷의 이름과 creation date, 리전을 돌려준다. 계정 안에 있는 버킷의 수를 세는 데 쓴다.
  2. 버킷을 지정한다콘솔에서 버킷을 선택하면 bucket ARN, 즉 버킷을 AWS가 유일하게 부르는 이름이 함께 보인다. 정책에 이 값을 넣어야 버킷 하나만 지정할 수 있다(→ 07-03).
  3. 설정을 훑는다버전 관리는 새 버킷에서 꺼진 상태로 시작하고, Tags는 키-값 쌍의 메타데이터로, Default encryption은 저장 시 자동 암호화로 켠다. 태그는 비용 배분과 ABAC에 쓴다(→ 02-06).
  4. 확인해 볼 것Properties 화면에 Region과 Bucket Versioning, Default encryption 항목의 현재 값이 떠 있는지 확인한다.

버킷 비우기와 삭제

S3는 버킷 안에 오브젝트가 남아 있으면 삭제를 거절하므로, 버전 관리가 켜진 경우 모든 버전과 삭제 마커까지 지운 뒤에야 DeleteBucket으로 빈 버킷을 삭제할 수 있다.

먼저 알아야 할 것 02-02

#1문제 상황

테스트용 버킷을 치우는데 오브젝트가 남아 있으면 삭제 요청이 거절된다(→ 03-01). 무엇이 몇 개 남았는지도 모르는 상태다.

delete a bucket은 빈 버킷만 지운다. 지워진 이름은 전 세계 네임스페이스에서 풀려 다시 쓰일 수 있다.

#2핵심 질문

버킷 안의 오브젝트를 모두 없애고 버킷 자체를 지우는 순서는?

#3동작 예시

버킷을 열어 Objects 탭에서 모든 오브젝트를 고르고 Delete를 누른다. 몇 시간이 걸린다는 안내와 함께 지워진다.

이제 비어 있는 버킷에 대해 Delete bucket을 누른다. 삭제 마커만 남은 버킷이면 안내 문구에 따라 다시 시도하면 지워진다.

#4동작 과정

  1. 비운다empty a bucket, 즉 delete all objects로 남은 오브젝트를 먼저 지운다. 수백만 개면 화면에서 고르는 대신 S3 Batch Operations를 쓴다(→ 05-04).
  2. 버킷을 지운다console, CLI, SDK, REST API 어느 경로로든 삭제를 요청한다. non-empty bucket, 즉 오브젝트가 남은 버킷은 거절된다.
  3. 되돌릴 방법을 먼저 정한다삭제는 되돌릴 수 없다. 이름을 계속 써야 한다면 지우지 말고 비우기만 하는 편이 낫다.
  4. 확인해 볼 것Objects 탭에 오브젝트가 하나도 안 보이는지 확인한다.

#5한 줄 요약

버킷 비우기와 삭제는 남은 오브젝트를 먼저 없애고, 되돌릴 수 없는 이름을 풀어 주는 두 단계 작업입니다.

#1문제 상황

버킷이 수십 개 되면 무엇이 무엇인지 이름만으로는 모른다. 권한을 팀마다 다르게 주고 싶어도 버킷 이름으로만 구분해야 한다.

bucket tags를 붙이면 버킷에 키-값 쌍을 저장해 두고 그것을 기준으로 권한과 비용을 나눌 수 있다.

#2핵심 질문

버킷에 붙는 표시로 권한과 비용을 어떻게 나눠 관리할까?

#3동작 예시

버킷의 Tags 탭에서 태그 키 team, 값 payments를 추가한다. 다른 버킷에는 team=search를 붙인다.

이후 IAM 정책에 s3:TagKeys 조건을 넣어 team=payments 태그가 있는 버킷에만 접근하게 할 수 있고, 비용 배분 리포트에서도 태그별로 금액이 나뉜다.

#4동작 과정

  1. 태그를 붙인다bucket tags는 버킷을 만들 때나 나중에 콘솔·CLI·API로 관리한다. tag key와 값의 쌍으로 저장한다.
  2. 권한 조건으로 쓴다attribute-based access control, 즉 ABAC는 태그 값을 조건으로 삼아 접근 범위를 키우는 방식이다. 범용 버킷은 기본으로 꺼져 있어 켜야 동작한다.
  3. 비용을 나눈다cost allocation에서 태그를 고르면 AWS Billing and Cost Management 리포트에 태그별 저장량과 요금이 나온다.
  4. 확인해 볼 것버킷의 Tags 탭에 넣은 태그의 키와 값이 목록에 보이는지 확인한다.

3단계 3. 오브젝트를 올리고 내려받는다

S3 버킷에 파일(오브젝트)을 올리는 동작이 업로드(PutObject), 내려받는 동작이 다운로드(GetObject)이며, 콘솔·CLI·SDK 어느 경로로든 같은 오브젝트를 다루게 됩니다.

먼저 알아야 할 것 01-02

#1문제 상황

버킷은 만들어졌지만 안에는 아직 파일이 없다(→ 01-02). 원본은 여러 컴퓨터에 흩어져 있고 서버를 거치면 느려진다.

upload objects로 올리고 download objects로 내려받으면 서버를 거치지 않고 파일이 S3로 바로 오간다. 오브젝트는 파일 데이터와 그 파일을 설명하는 메타데이터를 묶은 단위다(→ 01-02).

#2핵심 질문

내 파일을 버킷에 올리고 다시 내려받는 동작은 무엇인가?

#3동작 예시

버킷을 열어 Objects 탭의 Upload을 누르고 로컬 이미지 파일을 고른다. 업로드가 끝나면 목록에 크기와 마지막 수정 시각이 적힌 새 오브젝트가 나타난다.

오브젝트 이름을 누르면 브라우저에서 바로 열리고, 콘솔이 아니면 같은 파일을 GetObject로 내려받아 프로그램에서 읽는다.

#4동작 과정

  1. 올린다버킷에 쓰기 권한이 있어야 PutObject가 되고, 권한은 IAM과 버킷 정책로 정한다(→ 07-01). console, CLI, SDK, REST API 중 어느 경로로든 보낸다. 콘솔로 올릴 수 있는 최대 크기는 160 GB이고 이를 넘으면 CLI나 SDK를 쓴다. 버전 관리가 켜진 버킷에서는 같은 키에 새 판을 쌓는다(→ 10-01).
  2. 내려받는다GetObject로 오브젝트 데이터를 꺼내 쓴다. object size만큼 응답이 오므로 범위를 나눠 받지 않을지 판단해야 한다.
  3. 확인해 볼 것Objects 탭 목록에 방금 올린 파일의 이름과 크기가 보이는지 확인한다.

#5한 줄 요약

#1문제 상황

오브젝트를 정리하다가 같은 파일을 다른 버킷에도 보관해야 한다. 내려받아 다시 올리면 파일 크기만큼 시간이 걸리고 중간에 끊길 수 있다(→ 03-01).

S3 안에서 곧바로 복사하면 오브젝트를 다시 읽어 쓰지 않고 옮긴다. 파일을 옮기거나 이름만 바꾸는 것도 이 동작 하나로 처리된다.

#2핵심 질문

오브젝트를 복사하고 옮기고 이름까지 바꾸는 동작은 무엇인가?

#3동작 예시

원본을 지우면 이동이 되고, 원본 키와 같은 키로 다른 버킷에 복사하면 이름 변경이 된다.

#4동작 과정

  1. 복사한다CopyObject는 한 번에 5 GB까지 한 번의 원자적 동작으로 복사한다. 그보다 큰 오브젝트는 CLI나 SDK의 멀티파트 업로드 경로로 복사하고, 멀티파트로 올린 오브젝트의 성능을 유지하려면 콘솔이 아니라 CLI나 SDK를 쓴다(→ 04-01).
  2. 옮기거나 이름을 바꾼다move objects는 목적지에 복사한 뒤 원본을 지우는 두 동작을 이 API 한 번으로 처리하고 다른 리전으로도 옮긴다. rename objects도 복사한 뒤 원본을 지우는 것으로 끝나며 키 이름 자체는 언제든 새로 지정한다.
  3. 확인해 볼 것목적 버킷의 Objects 탭에 지정한 키로 새 오브젝트가 잡히는지 확인한다.

먼저 알아야 할 것 03-01

#1문제 상황

S3의 모든 오브젝트는 저장 공간을 차지하고 그만큼 요금이 붙는다(→ 01-02). 그래서 다 쓴 로그 파일이나 임시 파일을 버킷에 그냥 두면 비용만 계속 쌓인다.

오브젝트 지우기는 필요 없어진 오브젝트를 버킷에서 걷어 내는 기능이다. delete a single object은 하나씩 지우고, delete multiple objects는 키를 여러 개 담아 한 번에 지운다. 콘솔에서 지운 오브젝트와 버전은 되돌릴 수 없다.

#2핵심 질문

목록에 있던 파일들이 모두 사라지고 버킷의 총 저장량이 줄어든 것이 콘솔 요약에 반영된다.

#4동작 과정

  1. 하나를 지운다오브젝트 키를 지정해 DeleteObject를 호출한다. 데이터는 즉시 gone이 되고 응답이 돌아온다.
  2. 여러 개를 지운다지울 키들을 요청에 담아 보내 한 번에 처리한다. 성공한 키와 실패한 키가 함께 돌아온다.
  3. 정리 규칙을 건다같은 종류의 정리는 lifecycle rule로 만들어 두면 S3가 스스로 지운다(→ 11-05).
  4. 확인해 볼 것버킷 콘솔의 Objects 목록에서 지운 키가 사라지고 객체 수가 줄었는지 본다.

#1문제 상황

큰 파일을 올리거나 내려받는 동안 비트 하나가 뒤집히면 S3는 정상 응답을 주지만 내용은 틀어진다. 그래프나 이미지처럼 조금만 잘못돼도 문제가 되는 데이터다.

checksum은 데이터에서 뽑아 낸 짧은 지문값이다. upload와 download 때 양쪽이 이 값을 비교해 data integrity를 확인한다.

#2핵심 질문

올바른 데이터를 정말 전송받았는지 어떻게 확인하지?

#3동작 예시

백업 이미지 파일을 내려받는다. 응답 헤더에 들어 있는 체크섬과 로컬에서 계산한 값을 대조한다.

두 값이 다르면 전송 중 손상된 것으로 보고 파일을 버린다.

#4동작 과정

  1. 알고리즘을 고른다CRC32, CRC32C, SHA256, MD5 등 지원 알고리즘 중 하나를 정한다. 기본값은 CRC64NVME다.
  2. 값을 붙여 보낸다업로드할 때 x-amz-checksum-md5 같은 헤더로 미리 계산한 content MD5를 실어 보낼 수도 있다. SDK는 MD5를 자동으로 계산하지 않는다.
  3. 비교한다내려받을 때 S3가 계산한 값과 내 값이 같은지 확인해 깨짐을 잡는다. additional checksums를 함께 계산해 검증력을 높일 수도 있다.
  4. 확인해 볼 것GET 응답 헤더에 체크섬 값이 함께 오는지 확인한다.

먼저 알아야 할 것 01-06

#1문제 상황

버킷에는 서로 다른 팀과 종류의 파일이 한데 섞여 들어 있다. 어떤 파일이 무슨 것인지 이름만 보고는 알 수 없고, 파일마다 따로 부가 정보를 적어 둘 수도 없다.

object tagging은 오브젝트마다 키-값 쌍의 태그를 붙인다. 하나당 최대 10개까지 달 수 있고 키는 128자, 값은 256자까지 가능하다.

#2핵심 질문

오브젝트에 분류용 정보를 어디에 붙여 두는가?

#3동작 예시

업로드할 때 팀 이름과 문서 종류를 태그로 함께 보낸다. 나중에 태그 기준으로 버킷을 정리하거나 정책의 조건으로 쓴다(→ 07-05).

태그 자리에는 담기 어려운 큰 결과물이면 annotations으로 따로 남긴다.

#4동작 과정

  1. 태그를 정한다키-값 쌍을 만들고 키를 오브젝트 안에서 유일하게 지킨다. 키와 값은 대소문자를 구분한다.
  2. 업로드와 함께 붙인다새 오브젝트를 올릴 때 태그를 같이 보내거나, 이미 있는 오브젝트에 managing object tags로 나중에 붙인다.
  3. 큰 내용은 주석으로 둔다값이 256자를 넘거나 10개를 넘는 구조화된 데이터, 머신러닝 추론 결과 같은 풍부한 내용은 annotations으로 따로 기록한다.
  4. 확인해 볼 것오브젝트 상세 화면에 붙인 태그의 키와 값이 목록으로 보이는지 본다.

먼저 알아야 할 것 03-01

#1문제 상황

몇 GB짜리 파일을 PutObject 한 번으로 올리면 중간에 전송이 끊겼을 때 처음부터 다시 시작해야 한다. 조각 전체가 업로드되지 않으면 S3는 그 파일을 완성된 오브젝트로 보지 않는다.

multipart upload는 데이터를 여러 조각으로 나눠 각각 올리는 방식이다. 조각별로 따로 전송하고 실패한 조각만 다시 보내도 되며 전부 모이면 하나로 보인다(→ 03-01).

#2핵심 질문

아주 큰 파일을 어떻게 끊김이 있어도 다시 처음부터 하지 않고 올리는가?

#3동작 예시

수십 GB의 백업 파일을 올린다. 파일을 조각으로 잘라 순서를 섞어 각각 올리고 마지막에 조각 목록을 제출한다.

버킷에는 조각이 아니라 이름 그대로의 오브젝트 하나가 나타난다.

#4동작 과정

  1. 시작한다initiate multipart upload로 조각을 담을 자리를 열고 upload ID를 받는다. 이 ID가 이번 작업의 이름표가 된다.
  2. 조각을 올린다part number를 붙여 조각마다 따로 올린다. 각 조각은 연속된 구간(part)이고 순서와 무관하게 보낸다.
  3. 합친다part number 순으로 목록을 넣어 complete multipart upload를 호출하면 하나의 오브젝트가 된다. 한 조각만 실패하면 그 조각만 다시 보낸다.
  4. 확인해 볼 것조각 목록에서 part number가 빠짐없이 이어지는지 확인한다.

먼저 알아야 할 것 04-01

#1문제 상황

멀티파트 업로드(→ 04-01)는 완성되지 않은 채로 방치될 수 있다. 그때 남은 조각들은 버킷에 쌓여 용량을 차지하고 과금된다. 하지만 목록에는 완성된 오브젝트만 보여 조각이 있다는 사실이 드러나지 않는다.

멀티파트 업로드 관리는 list multipart uploads로 진행 중인 작업을 훑고, incomplete multipart upload를 지우는 작업이다.

#2핵심 질문

중단하고 방치한 멀티파트 업로드의 조각을 어떻게 회수하는가?

#3동작 예시

어제 업로드를 중간에 끊은 팀원이 야근에 집에 간다. 며칠 뒤운영자가 list multipart uploads로 보니 진행 중인 upload ID가 남아 있다.

abort multipart upload를 실행해 남은 조각을 지운다.

#4동작 과정

  1. 찾아본다list multipart uploads로 진행 중인 업로드의 키와 upload ID, 시작 시각을 확인해 tracking a multipart upload를 한다.
  2. 중단한다필요 없는 작업에 abort multipart upload를 걸면 그 조각들이 모두 삭제된다.
  3. 자동으로 맡긴다lifecycle rule의 AbortIncompleteMultipartUpload에 며칠 뒤를 지정해 두면 S3가 알아서 미완성 업로드를 멈추고 조각을 지운다. 이미 진행 중인 것과 앞으로 만들 것도 함께 적용된다.
  4. 확인해 볼 것진행 중인 멀티파트 업로드 목록이 비어 있는지 확인한다.

먼저 알아야 할 것 04-01

#1문제 상황

멀티파트 업로드(→ 04-01)는 아무 크기 파일도 무한히 나눠 받을 수는 없다. 조각 수에는 상한이 있고, 조각을 합친 결과가 원본과 같은지도 따로 확인해야 한다.

multipart upload limits와 함께 추가 체크섬을 걸어 verify data integrity를 강화할 수 있다.

#2핵심 질문

멀티파트 업로드가 밀어낼 수 있는 한계는 무엇이고 조각 전체의 무결성은 어떻게 보는가?

#3동작 예시

정해진 규칙대로 큰 파일을 나눠 maximum part size에 맞춰 여러 파일로 쪼갠다. 이어서 추가 체크섬을 지정한 채 멀티파트 업로드를 만든다.

완성 뒤 MD5와 추가 체크섬을 각각 비교해 두 겹으로 확인한다.

#4동작 과정

  1. 한계를 확인하고 체크섬을 고른다multipart upload limits에서 조각 수의 최댓값과 조각 크기 범위를 보고 분할 계획을 세운다. checksum algorithm을 하나 정해 initiate multipart upload 단계에서 추가 체크섬을 걸어 둔다.
  2. 조각을 올리고 합친다조각을 보내고 조각 목록을 조회해 빠짐을 확인한 뒤 업로드를 완성한다.
  3. 검증한다완성된 오브젝트를 MD5로도, 추가 체크섬으로도 확인해 verify data integrity를 마친다.
  4. 확인해 볼 것조각 목록 화면에서 조각 개수와 크기가 계획과 맞는지 본다.

조건부 읽기와 쓰기

If-None-Match나 If-Modified-Since 같은 조건 헤더를 붙여, 지정한 상태와 다를 때만 읽기가 진행되고 지정한 값이 그대로일 때만 쓰기가 반영되도록 요청을 제한하는 기능이다.

먼저 알아야 할 것 03-01

#1문제 상황

여러 사람이 같은 오브젝트 키에 동시에 PutObject를 보내면 나중에 도착한 요청이 앞 결과를 조용히 덮어쓴다. 내가 본 파일과 지금 저장된 파일이 같은지도 모른다.

conditional requests는 요청에 조건 헤더를 하나 더 붙여, 조건이 맞지 않으면 S3가 그 연산을 실패시키게 한다.

#2핵심 질문

내 요청이 최신 상태에만 반영되도록 어떻게 보장하는가?

#3동작 예시

동시에 돌아가는 두 작업이 같은 키에 쓰려고 한다. 각 요청에 If-None-Match를 넣어 키가 아직 없을 때만 쓰게 한다.

먼저 도착한 요청만 성공하고 나중 요청은 오류를 받는다.

#4동작 과정

  1. 조건을 정한다S3 API 호출에 추가 헤더를 붙인다. ETag(엔터티 태그, 오브젝트를 가리키는 지문값)나 마지막 수정 시각을 조건으로 쓴다.
  2. 읽기를 제한한다conditional reads는 GET, HEAD, COPY에서 지원한다. 특정 날짜 이후에 고쳐진 오브젝트만 받거나 특정 버전만 가져올 수 있다.
  3. 쓰기를 제한한다conditional writes를 쓰면 PUT에서 같은 키의 오브젝트가 이미 있으면 덮어쓰지 않고 실패시킨다. 다른 작업이 먼저 썼는지 알 수 있다.
  4. 확인해 볼 것조건이 맞지 않았을 때 요청이 오류로 끝나는지 확인한다.

#1문제 상황

여러 팀이 같은 오브젝트 키에 파일을 올리면 조건 없이 들어온 쓰기 요청이 앞선 결과를 조용히 덮어쓴다(→ 03-02). 클라이언트마다 조건 헤더를 붙이게 만들지 않으면 규칙이 어긋나기 쉽다.

조건부 요청 강제하기(enforce conditional writes)는 버킷 정책에 조건 키 s3:if-match 나 s3:if-none-match 를 넣어, 조건 없는 쓰기 요청을 S3가 거부하게 한다. 그래서 덮어쓰기와 삭제를 막는 규칙이 버킷에 고정된다.

#2핵심 질문

조건 없이 들어온 쓰기·삭제 요청을 버킷이 어떻게 거절하게 만들까?

#3동작 예시

업로드 스크립트가 If-None-Match 없이 PutObject을 보낸다. 버킷 정책에 조건부 쓰기 강제가 켜져 있으면 S3가 그 요청을 거절하고 오류 코드를 돌려준다.

#4동작 과정

  1. 버킷에 조건을 건다버킷 정책에 s3:if-none-match 또는 s3:if-match 조건을 넣는다. 조건부 쓰기 강제는 PutObject와 CompleteMultipartUpload, 여러 키를 한 번에 지우는 조건부 deletes를 대상으로 한다.
  2. 조건을 확인한다S3가 요청 헤더에 정해진 조건이 있는지를 본다. 없는 요청은 prevent object overwrites 규칙에 따라 거절되고, 조건부 deletes도 같은 방식으로 막힌다.
  3. 확인해 볼 것콘솔에서 버킷 정책 문서에 s3:if-none-match 조건이 들어 있는지 확인한다.

먼저 알아야 할 것 01-03

→ 05-02 참조

#1문제 상황

버킷에 사진이 수천 개 쌓이면 모든 키를 한 줄씩 훑어야 어느 것이 어디 묶음인지 알 수 없다. 파일 시스템처럼 폴더가 있으면 좋겠다.

접두사(prefix)는 오브젝트 키 앞부분의 문자열이다. 키에 슬래시(/)를 넣어 photos/2026/img.jpg 처럼 쓰면 폴더(folder)처럼 보이는 계층 구조(hierarchical structure)가 생기고, 접두사로 검색하면 그 문자열로 시작하는 키만 나온다.

#2핵심 질문

폴더가 없는 버킷에서 자료를 어떻게 계층처럼 묶어 볼까?

#3동작 예시

사진을 photos/2026/ 아래에 키로 업로드한다. 콘솔에서 버킷을 열면 photos 라는 이름의 묶음이 보인다. 그 안으로 들어가면 2026 묶음이 한 번 더 보인다.

#4동작 과정

  1. 슬래시를 접두사로 쓴다키 이름에 /를 넣어 앞부분 문자열이 같은 오브젝트를 한 묶음으로 만든다. 접두사는 폴더가 아니라 키 이름의 일부다.
  2. delimiter 로 접는다목록 요청에 구분자(delimiter)인 /를 주면 같은 접두사를 가진 키를 한 줄로 모아 common prefixes로 보여 준다. 그래서 폴더처럼 단계가 생겨 보인다.
  3. 확인해 볼 것콘솔에서 버킷을 열어 접두사 묶음이 단계별로 접혀 보이는지 확인한다.

#1문제 상황

#2핵심 질문

오브젝트 전체를 내리지 않고 필요한 행만 어떻게 골라낼까?

  2. SQL 을 보낸다요청에 SQL 식을 실어 S3 안에서 걸러 낼 조건을 말한다. query in place 라는 이 방식은 오브젝트 하나씩만 다룬다.
  3. 결과 형식을 정한다결과는 CSV 또는 JSON으로 받을 수 있고 레코드 구분자를 지정할 수 있다. 암호화된 오브젝트에도 쓸 수 있다.
  4. 확인해 볼 것콘솔에서 오브젝트를 열어 S3 Select로 조건을 넣었을 때 걸린 행만 보이는지 확인한다.

6. 바깥에 내보내다 — 주소 하나를 잠깐 빌려준다06-01

presigned URL — 권한을 담은 임시 주소

AWS SDK로 서명한 뒤 발급되는, 인증 정보가 서명 안에 들어 있어 사용자가 그 링크만 가지고 권한 없이도 오브젝트를 내려받거나 올릴 수 있게 해 주는 만료 시간이 정해진 임시 URL 이다.

먼저 알아야 할 것 03-01

#1문제 상황

앱 사용자에게 파일을 내려받게 하려면 IAM 자격 증명을 넘기게 된다(→ 03-01). 자격 증명 없이 그리고 사용 기한을 정해 링크만 건네는 방법이 없다.

presigned URL 은 query string authentication 방식으로 서명 정보를 URL에 포함한 임시 주소다. 발급할 때의 서명(signature)이 권한을 대신하므로, 링크를 받은 사람은 AWS 자격 증명이 없어도 지정된 오브젝트만 만진다.

#2핵심 질문

#3동작 예시

백엔드가 SDK로 presigned URL 을 만든 뒤 웹 화면의 다운로드 버튼 주소로 넘긴다. 사용자는 로그인 없이 그 링크를 브라우저에 넣어 파일을 내려받는다.

#4동작 과정

  1. 서명해 발급한다AWS SDK로 보안 자격 증명을 넣어 만료 시각과 동작을 정해 서명한다. 생성한 URL 안에는 query string authentication 정보가 들어 있다. URL 안의 자격 증명은 그 presigned URL 을 만든 IAM 주체의 것이다.
  2. 링크로 쓰기·읽기를 한다링크를 브라우저나 프로그램에 넣어 오브젝트를 내려받을 수 있다. upload with presigned URL 로는 상대방에게 AWS 보안 자격 증명이나 권한이 없어도 지정한 오브젝트 하나를 올릴 수 있고, 같은 키의 오브젝트가 있으면 새 파일로 대체된다.
  3. 만료까지 쓴다expiration 이 지나기 전까지 presigned URL 을 여러 번 사용할 수 있다. 주석 API인 PutObjectAnnotation 등에도 쓸 수 있다.
  4. 확인해 볼 것만든 링크로 파일 한 개를 내려받아 응답이 오는지 확인한다.

버킷에 공개 읽기 권한과 웹사이트 호스팅 설정을 주면 오브젝트가 HTML·CSS·파일 형태로 담긴 버킷 자체가 정적 웹사이트 서버처럼 동작하는 기능이다.

먼저 알아야 할 것 02-02

#1문제 상황

HTML·CSS·JS로 된 페이지를 웹에 올리려면 보통 웹 서버를 따로 준비하고 배포 파이프라인을 붙여야 한다. 오브젝트만 넣어 두고 그대로 서비스할 방법은 없다.

static website hosting은 버킷에 enabling website hosting을 적용해 버킷을 정적 사이트 서버로 쓰게 한다. 공개 읽기가 붙은 오브젝트가 그대로 페이지가 되고, 접속 주소는 버킷마다 정해진 website endpoint로 정해진다. 별도 서버 없이 수동으로 올린 페이지를 바로 공개한다. 이 주소는 HTTP 전용이라 HTTPS 주소는 따로 필요하다.

#2핵심 질문

서버를 준비하지 않고 버킷에 올린 페이지를 어떻게 웹에 공개할까?

#3동작 예시

개발자가 marketing 버킷에 index.html과 logo.png를 올리고 웹사이트 호스팅을 켠다. 브라우저에 버킷의 website endpoint 주소를 넣으면 두 오브젝트가 합쳐진 페이지가 열린다.

누군가 없는 경로로 주소를 치면 이때는 오류 화면이 뜨고, 어떤 문서를 보여 줄지는 다음 항목에서 정한다.

#4동작 과정

  1. 호스팅을 켠다버킷의 권한 탭에서 static website hosting을 선택해 켠다. 사이트는 HTTP로만 응답하며 다른 오브젝트 API 주소와 별개로 동작한다.
  2. 파일을 올린다index.html을 루트에 두고 CSS·이미지를 오브젝트로 올린다. 접두사 폴더를 쓰면 하위 경로에도 문서를 넣을 수 있다(→ 05-01).
  3. 접속한다S3가 정해 둔 website endpoint 주소로 요청을 받는다. 주소를 직접 치면 브라우저 주소창에 bucket name endpoint가 자동으로 찍힌다.
  4. 확인해 볼 것콘솔 Permissions의 Static website hosting 항목에서 엔드포인트 주소와 편집 화면이 열렸는지 확인한다.

먼저 알아야 할 것 06-02

→ 06-02 참조

#1문제 상황

웹사이트 호스팅을 켜도(→ 06-02) 사용자가 문서 이름 없이 주소만 치면 S3는 어떤 파일을 보여 줘야 할지 모른다. 없는 경로를 치르면 S3 기본 오류 문서(raw XML)가 그대로 노출된다.

이 설정은 그런 두 경우에 보여 줄 파일을 직접 정한다. 웹사이트 설정에서 index document 이름을 지정하면 그 이름의 오브젝트가 기본 페이지로 나오고, error document를 지정하면 오류가 났을 때 그 파일이 대신 보인다. 폴더마다 다른 인덱스를 둘 수도 있다. 다른 오브젝트 접근 방식인 REST API 경로에는 영향을 주지 않는다.

#2핵심 질문

문서 이름 없이 들어온 요청과 없는 경로 요청에 무엇을 보여 줄까?

#3동작 예시

운영자가 index.html과 404.html을 올리고 웹사이트 설정에서 index document를 index.html, error document를 404.html로 지정한다.

방문자가 example.com/ 을 치면 index.html이 열리고, 없는 주소 /missing 를 치면 404.html이 열린다.

#4동작 과정

  1. 인덱스 문서를 정한다index document 이름을 넣는다. 루트나 하위 폴더 주소로 요청이 오면 S3는 그 이름의 오브젝트를 돌려준다. 문서 이름 뒤의 슬래시는 있어도 되고 없어도 같은 결과다.
  2. 오류 문서를 정한다404처럼 실패했을 때 보여 줄 error document 파일 이름을 넣는다. 이 문서도 오브젝트로 업로드해 두어야 한다.
  3. 접근 권한을 맞춘다웹사이트가 외부에 보여야 하므로 public read access가 필요하고, 실제 파일은 오브젝트 오너가 소유한 상태여야 한다(→ 07-06). 조건이 맞지 않으면 오류 문서조차 대신 보여 주지 않는다.
  4. 확인해 볼 것주소창에 문서 이름 없이 도메인만 쳤을 때 인덱스 문서가 열리고, 없는 경로를 쳤을 때 지정한 오류 문서가 나오는지 확인한다.

CORS — 브라우저가 다른 곳에서 읽도록

브라우저 보안 규칙 때문에 웹 페이지가 다른 출처의 오브젝트를 읽지 못하는 것을, 허용할 출처와 메서드·헤더를 규칙으로 등록해 풀어 주는 설정이다.

먼저 알아야 할 것 06-02

#1문제 상황

웹사이트는 자기 버킷에, 이미지나 업로더 스크립트는 다른 도메인에 있다고 하자. 브라우저 보안 규칙인 동일 출처 정책 때문에 다른 도메인에서 온 요청은 본문까지 오지 않는다. 개발자 도구에는 오류만 남고 S3는 아무 문제가 없다.

CORS는 이 요청에 답을 내놓도록 버킷에 규칙을 등록하는 기능이다. 버킷의 CORS configuration에 allowed origin을origin을 이름으로 적고, 거기에 허용할 메서드와 헤더를 함께 정한다. 등록된 출처에서 온 요청만 본문을 받을 수 있다. 버킷 하나에 규칙을 여러 개 둘 수 있다.

#2핵심 질문

다른 도메인에 있는 내 웹 페이지가 S3 오브젝트를 읽게 할 수 있는가?

#3동작 예시

업로드 페이지를 example.com에서 서비스하고 이미지를 assets 버킷에 둔다. 브라우저가 보내는 preflight request가 거절된다.

버킷에 example.com을 allowed origin으로 넣은 규칙을 저장하고 나면, 같은 요청이 허용 응답을 받고 이미지 로딩이 된다.

#4동작 과정

  1. 규칙을 정의한다CORS configuration에 각 규칙마다 허용할 origin을 적고 메서드(예: GET, PUT)와 허용 헤더, 노출 헤더를 지정한다. 규칙은 여러 개가 가능하다.
  2. 규칙을 붙인다버킷에 규칙을 저장한다. 지워버리면 같은 문제가 바로 되돌아온다.
  3. 요청을 받아 준다S3는 해당 origin의 요청에 Access-Control-Allow-Origin 헤더를 담아 답을 돌려준다. 목록에 없는 origin에는 헤더를 주지 않아 브라우저가 차단한다.
  4. 확인해 볼 것브라우저 개발자 도구의 네트워크 창에서 해당 요청 응답에 Access-Control-Allow-Origin 헤더가 붙어 있는지 확인한다.

Transfer Acceleration — 먼 거리에서도 빨리

버킷과 사용자 사이의 장거리를 엣지 로케이션과 내부 네트워크를 통해 단축해 장거리 업로드·다운로드 전송 속도를 높이는 유료 버킷 기능이다.

먼저 알아야 할 것 06-02

#1문제 상황

버킷 리전에서 아주 먼 곳의 사용자가 큰 파일을 올리면 데이터가 사용자와 버킷 사이를 그대로 지나며 전송이 느려진다. 파일을 여러 번 나누어 올리는 방식(→ 04-01)으로도 왕복 구간이 그대로 남는다.

S3 Transfer Acceleration은 버킷 수준에서 켜는 기능이다. 데이터를 클라이언트에서 가장 가까운 Amazon CloudFront edge locations로 먼저 보내고, 그곳에서 S3로 가는 구간은 AWS 내부의 최적화된 네트워크 경로로 이어 준다. 켠 버킷은 전용 bucket name endpoint 주소를 받으며, 켜는 동안 별도 데이터 전송 비용이 붙는다. 같은 리전 근처에서는 이득이 적다.

#2핵심 질문

사용자와 버킷 사이의 거리가 멀 때 전송 속도를 어떻게 높일까?

#3동작 예시

같은 CLI 명령을 bucket name endpoint 주소로 보내면 파일이 가까운 엣지 로케이션까지만 이동하고 나머지는 내부 경로로 넘어가 전체 시간이 줄어든다.

#4동작 과정

  1. 버킷에서 켠다enable Transfer Acceleration 옵션을 켠다. 일반 목적 버킷에만 적용된다(→ 11-02 디렉터리 버킷 제외). 계정과 버킷이 서로 다른 소유자일 때도 쓸 수 있다.
  2. 엣지로 보낸다클라이언트가 엣지 로케이션으로 데이터를 올린다. 이 구간에서 S3로 들어가는 방향이 최적화된다.
  3. 내부로 넘긴다엣지에서 S3로 데이터는 AWS 내부 네트워크를 따라 이동해 목적 버킷까지 도달한다.
  4. 확인해 볼 것버킷 설정에서 Transfer Acceleration이 켜진 상태인지 보고, 콘솔이 알려 주는 bucket name endpoint 주소가 어떤 모양인지 확인한다.

IAM 이 S3 를 보는 방식

IAM(신원 및 접근 관리)은 누가 무엇에 대해 어떤 작업을 할 수 있는지를 관리하는 AWS 서비스이며, S3 는 이 서비스가 붙여 주는 권한과 버킷·객체에 붙은 정책을 함께 보아 접근을 허용한다.

먼저 알아야 할 것 06-01

#1문제 상황

S3 오브젝트는 API로만 다뤄지고(→ 03-01) 그 API는 전부 요청 신원을 확인한 뒤에만 동작한다. 누가 버킷을 만들고 누가 어떤 파일을 지울 수 있는지 정해 둔 곳이 없다면 모든 사용자가 모든 버킷을 건드릴 수 있게 된다.

AWS Identity and Access Management(IAM)는 신원 주체를 만들고 무엇이 허용되는지 관리하는 AWS 서비스다. S3는 여기서 온 권한과 버킷·오브젝트에 직접 붙인 규칙을 함께 보고 접근을 정한다. 규칙은 어디에 붙느냐로 나뉜다. principal은 규칙이 누구를 향하는지 정하는 대상이고, identity-based policy는 사람과 역할에 붙고, resource-based policy는 버킷과 오브젝트에 붙는다.

#2핵심 질문

S3에 들어오는 요청에서 누가 무엇을 할 수 있다고 어떻게 정하는가?

#3동작 예시

신입 개발자에게_orders 버킷의 읽기 권한만 주고 쓰기 권한은 주지 않는다. IAM에서 그 사람용 role에 identity-based policy를 붙인다.

role로 AssumeRole한 뒤 GetObject는 되고 PutObject는 거부되며, 이 결과는 S3 IAM permissions로 확인할 수 있다.

#4동작 과정

  1. 신원을 정한다IAM에서 누가 요청하는지 정한다. 사람이면 IAM 사용자, 어플리케이션이면 role을 만들어 credentials로 AssumeRole해 세션을 받는다. S3는 이 시그니처로 요청자가 누구인지 알아낸다.
  2. 규칙을 붙인다identity-based policy를 주체에 붙이고, 필요하면 버킷 쪽에 resource-based policy를 함께 둔다. 두 규칙이 만나는 부분에서 허용 범위가 정해진다.
  3. 요청을 판정한다S3는 붙은 규칙을 모두 모아 요청을 허용할지 정한다. 허용되지 않으면 Access Denied 오류를 돌려준다(→ 07-02가 그 순서를 정한다).
  4. 확인해 볼 것IAM 콘솔에서 해당 role에 붙은 S3 관련 정책 문장을 보고 어떤 action이 허용돼 있는지 확인한다.

#1문제 상황

버킷 정책과 IAM 정책이 동시에 붙어 있으면 어느 쪽을 먼저 보는지 모호해 보인다. 겉보기에는 허용처럼 보이는 규칙도 뒤 단계에서 막히고, 정책 문서에는 문제가 없는데 Access Denied이 난다.

request authorization은 이 상황을 위해 정해진 판정 순서다. S3는 요청이 오면 관련 정책과 ACL(→ 07-06)을 한 묶음으로 만들어 정해진 단계대로 검사한다. 버킷 대상 작업(bucket operation)과 오브젝트 대상 작업(object operation)을 나누어 처리하고, 다른 계정 주체의 요청에는 cross-account access 규칙을 마지막에 적용한다. owner of the resource의 권한도 단계마다 따로 반영한다. 한 단계라도 거절하면 그 뒤는 보지 않는다.

#4동작 과정

  1. 규칙을 모은다사용자 정책(→ 07-04), 버킷 정책(→ 07-03), 버킷·오브젝트 ACL을 실행 시점에 평가용 한 벌로 변환한다. 이 묶음이 판정의 재료가 된다.
  2. 단계별로 검사한다소유자 권한, 버킷 정책, IAM 정책, ACL, 공개 정책 차단 설정(→ 07-05), 조직 정책·권한 경계·세션 정책, 명시적 거절을 정해진 순서로 거친다. 각 단계는 필요한 정책 일부만 문맥에 맞게 본다.
  3. 교차 계정을 본다요청 주체가 다른 계정이면 cross-account access 규칙을 마지막에 확인해 그 계정의 정책까지 반영한다. 모든 단계가 허용해야 요청이 통과한다.
  4. 확인해 볼 것S3 콘솔의 Error response와 요청 로그에 Access Denied이 떠 있는지 보고, 그 요청이 어느 정책 단계에서 막혔는지 CloudTrail 기록에서 찾는다(→ 12-01).

버킷 정책 — 버킷에 붙는 규칙

버킷 정책은 버킷 하나에 붙이는 JSON 문서의 규칙으로, 계정 내부·외부 주체의 principal 이 버킷과 그 안의 객체에 대해 어떤 action 을 어떤 resource 와 조건에서 수행할 수 있는지를 서술한다.

→ 07-04 참조

#1문제 상황

특정 계정의 서비스만 이 버킷에 파일을 올리게 하고, 나머지 접근은 모두 막아야 한다. 사람마다 권한을 따로 주는 대신 버킷 자체에 규칙을 걸고 싶다. 다른 계정의 principal에게 열어 주는 경우도 같다.

bucket policy가 그것이다. resource-based policy의 한 형태이며 버킷에 직접 붙는 JSON 문서다. IAM policy language(→ 07-01의 정체성 기반 정책과 같은 문법)를 쓰고, resource를 오브젝트 ARN으로 적어 어디까지 열지 정한다. Condition key를 넣으면 IP 주소나 시간 같은 조건에 걸린 요청만 허용할 수 있다. 문서 전체는 20 KB 한도 안이어야 한다. 버킷 소유자만 붙일 수 있고, 다른 계정 소유 오브젝트에는 적용되지 않는다.

#2핵심 질문

버킷 자체에 접근 규칙을 붙여 누구에게 무엇을 어디까지 허용할까?

#3동작 예시

파트너 계정이 report/ 접두사에만 PutObject를 올리게 하려고 한다. 버킷 정책 문서에서 principal을 파트너 계정으로, action을 PutObject로, resource를 해당 접두사의 오브젝트 ARN으로 적고 PublicAccessBlock 설정과 함께 저장한다.

이제 파트너 계정은 지정된 경로에 올릴 수 있고 다른 오브젝트에는 거절된다.

#4동작 과정

  1. 문서를 만든다policy language로 Statement를 쓴다. 각 문장에 principal, action, resource를 넣고 필요하면 Condition key로 조건을 단다. 허용과 거절 둘 다 명시할 수 있다.
  2. 버킷에 붙인다버킷 소유자 계정으로만 저장을 한다. 권한은 버킷 소유자가 소유한 오브젝트 전체에 적용되며 다른 계정이 올린 오브젝트에는 닿지 않는다. 20 KB를 넘으면 저장이 거부된다.
  3. 요청에 겹친다버킷 정책은 IAM 정책(→ 07-04)과 함께 있을 때 둘 다 만족해야 한다. bucket owner enforced 설정이 켜진 버킷은 ACL(→ 07-06)이 꺼져 권한이 정책으로만 정해진다.
  4. 확인해 볼 것S3 콘솔의 Permissions에서 버킷 정책 문서를 열어 principal과 resource가 의도한 대로 저장돼 있는지 확인한다.

#1문제 상황

IAM identity policies는 IAM 사용자·그룹·역할에 붙는 JSON 규칙으로, 그 주체가 어떤 S3 action을 어떤 resource에 할 수 있는지 적는다. 요청이 허용되려면 이 규칙과 버킷 정책을 모두 만족해야 한다(→ 07-02).

각 사람이 S3에서 무엇을 할 수 있는가를 어디에 적는가?

#3동작 예시

  1. 필요한 작업을 정한다먼저 팀이 실제로 누를 S3 API를 나열한다. 이때 어떤 action에 어떤 권한이 필요한지는 required permissions for S3 API operations 문서에서 본다.
  2. 정책을 붙인다IAM 정책 편집기에 JSON 문서를 적어 그룹이나 역할에 묶는다. 오브젝트 읽기에는 s3:GetObject, 올리기에는 s3:PutObject, 버킷 목록 보기에는 s3:ListBucket을 쓰고 resource에 버킷 ARN과 키 경로를 함께 적는다.
  3. 확인해 볼 것IAM 콘솔에서 해당 그룹에 정책이 붙은 목록이 보이는지 확인한다.

ACL 과 객체 소유

ACL(접근 제어 목록)은 버킷과 객체마다 개별 주체에게 READ·WRITE 등 권한을 직접 부여하는 방식이며, 버킷 소유자 강제 소유 설정을 켜면 ACL 이 disable 되므로 권한은 정책으로만 관리하게 된다.

#1문제 상황

정체성 기반 정책와 버킷 정책으로 대부분의 권한을 정리한다(→ 07-04, → 07-03). 그래도 다른 AWS 계정 하나에게 특정 오브젝트 읽기만 허용해야 하는 자리는 남는다.

access control list는 버킷과 오브젝트에 주체별 권한을 직접 부여하는 방식이다. 이 방식은 다른 AWS 계정에게만 줄 수 있고 조건부 권한이나 명시적 거절은 지원하지 않는다. object ownership는 버킷 수준 설정으로, 기본값이 Bucket owner enforced여서 모든 ACL이 비활성화되고 버킷 소유자가 모든 오브젝트를 소유한다.

파트너 계정에 특정 폴더만 올리게 한다. canned ACL, 즉 미리 정해진 이름의 ACL을 붙여 업로드하면 그 오브젝트의 소유권과 권한이 정해진 대로 따라간다.

#4동작 과정

  1. 소유자 방식을 정한다버킷의 object ownership를 Bucket owner enforced로 두면 ACL이 꺼져 권한은 정책으로만 관리된다(→ 07-03). 다른 계정에 ACL을 건네야 할 때만 다른 값으로 바꾼다.
  2. ACL을 붙인다버킷 또는 오브젝트에 read 같은 정해진 권한 조합을 주체별로 직접 부여하거나, canned ACL 이름 하나를 지정해 한 번에 적용한다.
  3. 확인해 볼 것오브젝트 권한 화면에서 ACL 항목이 활성 상태인지, 아니면 비활성화되어 있는지 확인한다.
  4. IAM Access Analyzer for S3로 공개 범위를 훑어볼 수도 있다.

Access Points — 버킷 한 조각에 이름 붙이기

버킷 전체에 권한을 주는 대신 버킷 안의 특정 접두사(폴더)나 오브젝트 하나만 가리키는 이름표를 붙여, 애플리케이션마다 다른 입구가 되게 하는 기능이다.

먼저 알아야 할 것 07-03

#1문제 상황

버킷 하나에 여러 팀의 데이터가 섞여 있다. 팀마다 전체 버킷 권한을 나눠 주면 어느 팀이 어디까지 볼 수 있는지 정하기 어렵다(→ 07-03).

S3 access points는 버킷 같은 데이터 소스에 붙는 이름 붙은 네트워크 엔드포인트다. 각 접근 지점에 접두사나 오브젝트 하나만 가리키는 범위를 주고 그 이름으로 GetObject와 PutObject 같은 오브젝트 작업을 수행한다.

#2핵심 질문

버킷의 일부만 Application 이름의 입구로 따로 열 수 있는가?

#3동작 예시

이미지 처리 서비스용 접근 지점을 만들고 범위를 images/2026/ 로 건다. 그 application's 이름으로 오브젝트를 올리면 범위 아래에만 쌓이고, 다른 경로 키는 이 입구로 접근되지 않는다.

#4동작 과정

  1. 범위를 정한다접근 지점을 붙일 data source를 고르고, 버킷의 특정 접두사나 오브젝트 하나를 가리키게 만든다. shared datasets처럼 여러 앱이 함께 쓰는 데이터도 이 방식으로 묶는다.
  2. 이름을 짓고 식별한다접근 지점에 이름을 붙이고 access point alias, 즉 버킷처럼 보이게 하는 별칭 이름을 만든다. 권한 부여와 로깅에는 access point ARN을 쓴다.
  3. 확인해 볼 것S3 콘솔의 접근 지점 목록에서 범위가 적은 항목이 들어 있는지 확인한다.

Access Point의 권한과 VPC 제한

Access Point마다 별도의 권한 정책을 붙여 그 입구로 들어온 요청만 허용하고, 동시에 네트워크 경로가 특정 VPC 안으로만 열려 있도록 못 박아 두는 규칙이다.

먼저 알아야 할 것 08-01

→ 08-01 참조

#1문제 상황

접근 지점을 만들었다(→ 08-01). 이제 그 이름이 아무 곳에서나 쓰이면 입구 하나가 곧 공개 통로가 된다.

access point policy는 접근 지점을 리소스로 삼는 IAM 정책으로, 주체·리소스·조건별로 그 입구의 사용을 통제한다. policy에 적은 제한은 그 접근 지점을 지나는 요청에만 적용되고, 버킷에 직접 오는 요청은 그대로 동작한다. VPC restrictions를 함께 쓰면 접근 지점 안에서도 지정한 VPC에서 온 요청만 받는다. Block Public Access는 접근 지점에도 그대로 적용된다.

#2핵심 질문

접근 지점 입구를 어느 주체와 어느 네트워크에서만 열 것인가?

#3동작 예시

접근 지점에 정책 문서를 붙여 특정 역할의 principal과 s3:GetObject·s3:PutObject만 허용한다. 같은 VPC에 있는 application's 인스턴스가 그 이름으로 요청하면 되고, VPC 밖의 곳에서는 거부된다.

#4동작 과정

  1. 정책을 붙인다접근 지점에 IAM 리소스 정책을 연결해 허용할 주체와 action, 조건을 적는다. 버킷도 요청을 허용해야 두 조건이 함께 맞는다.
  2. 경로를 닫는다VPC restrictions를 켜서 VPC ID와 같은 리전 조건을 넣는다. 조건을 넣을 수 있는 위치는 access point policy 안에 있다.
  3. 호환성을 정한다다른 S3 기능과 함께 쓸 수 있는지는 access point compatibility 설정으로 고른다.
  4. 확인해 볼 것접근 지점 상세에서 정책 문서와 VPC 제한 항목이 함께 보여 주는지 확인한다.

S3 Access Grants — 조직의 신원과 버킷을 잇다

IAM 정책 문장을 직접 쓰지 않고 '누가 어느 버킷의 어느 경로에 무엇을 할 수 있는가'를 세 요소(신원·권한·리소스)의 조합으로 선언해 조직 전체에 한 번에 적용하는 방식이다.

먼저 알아야 할 것 07-01

→ 08-02 참조

#1문제 상황

IAM 정책과 버킷 정책을 직접 쓰면 데이터셋이 늘어날수록 정책 문서 크기(버킷 정책 20KB, IAM 정책 5KB 한계)에 걸리고 관리할 주체 수도 늘어난다(→ 07-04).

S3 Access Grants는 그 규모 문제를 풀기 위한 방식이다. 대신 IAM 문장을 쓰지 않고 location과 grant 두 요소로 신원·권한·리소스를 선언한다. 요청이 오면 S3 Access Grants가 짧은 수명의 vended credentials를 발급해 corporate directory 쪽 신원까지 한 번에 이어 준다.

#2핵심 질문

데이터셋이 많아져도 정책 문서를 늘리지 않고 접근 규칙을 관리하려면?

#3동작 예시

데이터셋이 수백 개로 늘어난 조직이 위치와 권한 조합을 등록해 둔다. 구성원이 S3 콘솔이나 CLI에서 그 데이터셋을 고르면 자격 증명이 발급되어 해당 경로만 읽을 수 있다.

#4동작 과정

  1. 위치를 등록한다organization에서 S3 Access Grants를 켜고 버킷과 접두사 단위의 location을 만든다. 이 위치가 grant가 가리킬 리소스다.
  2. grant를 선언한다이 location에 어떤 신원이 어떤 권한을 가지는지 조합으로 등록한다. 문서를 직접 쓰지 않으므로 조합 수만큼 늘어나도 정책 크기를 걱정하지 않는다.
  3. 접근을 받는다선언된 신원은 자격 증명이 발급된 상태로 데이터셋을 쓰고 읽는다.
  4. 확인해 볼 것S3 콘솔에서 Access Grants 화면에 등록된 location과 grant 목록이 보이는지 확인한다.

먼저 알아야 할 것 07-05

→ 08-02 참조

#1문제 상황

애플리케이션이 S3로 나갈 때 트래픽이 공용 네트워크를 지나고, S3 주소가 어디로 해석되는지 애플리케이션이 외워야 한다. 버킷 공개 차단을 켜 두면(→ 07-05) 사설망에서만 붙는 방법이 필요하다.

AWS PrivateLink for Amazon S3는 이 사설 경로를 만든다. VPC 안의 서브넷에서 private IP를 받은 하나 이상의 ENI(탄력 네트워크 인터페이스)로 VPC endpoint가 표현되고, 요청은 이 경로로만 S3에 전달된다. 게이트웨이 엔드포인트와 달리 인터페이스 엔드포인트 방식이다. 요청 경로가 AWS 내부에만 존재해 infrastructure security가 그대로 확보된다.

#2핵심 질문

인터넷으로 나가지 않고 VPC 안에서만 S3에 닿게 하려면?

#3동작 예시

#4동작 과정

  1. 엔드포인트를 만든다VPC에서 interface endpoint를 프로비저닝하고 private IP를 받는 서브넷을 고른다. 온프레미스는 VPN과 Direct Connect, 다른 리전은 VPC peering으로 닿는다.
  2. 경로를 고정한다엔드포인트 정책과 Private DNS 설정을 정해 버킷·접근 지점·S3 Control API 호출을 이 경로로 보낸다(→ 08-01). 온프레미스 DNS 설정도 함께 갱신한다.
  3. 확인해 볼 것VPC 콘솔의 엔드포인트 목록에서 상태가 사용 가능으로 뜨고, 해당 엔드포인트의 네트워크 인터페이스에 서브넷의 private IP가 붙어 있는지 확인한다.

버킷을 파일처럼 쓰기 — Mountpoint와 Storage Browser

버킷을 디스크에 붙여 일반 파일처럼 즉시 읽고 쓸 수 있게 하는 Mountpoint와, 버킷 내용을 웹 화면으로 둘러보고 정리할 수 있게 해 주는 Storage Browser를 함께 쓰는 방법을 다룬다.

먼저 알아야 할 것 03-01

#1문제 상황

S3는 업로드와 다운로드 API로만 오브젝트를 다룬다(→ 03-01). 기존 애플리케이션이 파일 열기와 읽기 방식으로 데이터를 읽으려면 코드를 고쳐야 한다.

Mountpoint for Amazon S3는 버킷을 파일처럼 붙여 그대로 읽게 한다. Storage Browser for Amazon S3는 버킷 내용을 웹 화면으로 정리해 준다.

#2핵심 질문

기존 코드를 바꾸지 않고 버킷을 디스크처럼 읽을 수 있을까?

#3동작 예시

이미지가 많은 학습 애플리케이션이 데이터 레이크의 원본 파일을 읽어야 한다. Mountpoint를 경로로 지정해 두면 코드 안의 파일 열기와 읽기가 그대로 동작하고, 화면에는 버킷의 폴더 목록이 나온다.

#4동작 과정

  1. 붙인다Mountpoint for Amazon S3를 경로로 지정해 버킷을 파일 시스템처럼 연다. POSIX는 파일의 권한·링크·잠금 같은 규칙을 정한 표준이고, Mountpoint는 이 표준의 file system interface를 일부만 지원해 기존 코드를 바꾸지 않게 한다.
  2. 읽고 쓴다파일 연기와 읽기가 S3 오브젝트 API 호출로 자동 번역된다. 쓰기는 지원하지 않고 파일 목록 확인과 새 파일 만들기가 가능하다.
  3. 지켜본다Storage Browser for Amazon S3를 켜면 버킷 내용을 웹 화면에서 둘러보고 정리할 수 있다.
  4. 확인해 볼 것Mountpoint 경로로 텍스트 파일을 열 때 내용이 그대로 보이는지 확인한다.

암호화 전체 모양 — 어디에 무엇을 씌우나

S3 암호화는 저장 시점에 서버가 데이터를 자동으로 암호화하는 서버 측 암호화와, 데이터를 클라이언트에서 먼저 암호화해 보내는 클라이언트 측 암호화로 나뉘며 서버 측 암호화는 AWS 소유 키(SSE-S3), KMS 키(SSE-KMS), 이중 암호화(SSE-ECS/SSE-KMS 이중), 고객 소유 키(SSE-C)로 다시 나뉜다.

먼저 알아야 할 것 07-05

#1문제 상황

버킷을 만들면 파일을 올리는 순간 누군가에게 넘어갈 수 있다. 그래서 S3는 data encryption, 즉 데이터에 암호화를 걸어 원문을 못 알아보게 만드는 수단을 기본 제공해 왔다.

data protection는 나뉜 두 구간을 각각 지킨다. 하나는 encryption at rest, 디스크에 저장돼 있는 상태이고 다른 하나는 encryption in transit, 클라이언트와 S3 사이를 오가는 상태다.

#2핵심 질문

저장된 데이터와 전송 중인 데이터를 각각 어떻게 지킬까?

#3동작 예시

이미지를 버킷에 올리면 따로 지시하지 않아도 S3가 암호화해 저장한다. 같은 파일을 다른 서버로 내려받아 볼 때 HTTPS로 오가는 구간도 암호화되어 있다.

#4동작 과정

  1. 저장할 때server-side encryption으로 S3가 받는 즉시 암호화한다. 암호화 키는 AWS 소유 키나 KMS 키(→ 09-02, → 09-03) 중 고른다.
  2. 보낼 때client-side encryption으로 클라이언트가 먼저 암호화해 보낸다. 서버는 암호문만 다루며, 전송 구간은 TLS로 지킨다(→ 09-06).
  3. 확인해 볼 것오브젝트를 조회한 응답의 헤더에 암호화 방식이 적혀 있는지 확인한다.

SSE-S3 — 키를 AWS 가 맡는다

SSE-S3는 S3가 자체적으로 관리하는 AES-256 키로 오브젝트를 자동 암호화하는 방식으로, 사용자가 키를 만들거나 관리할 필요 없이 암호화를 켜기만 하면 되고 암호문을 안전하게 보관해 주는 책임은 AWS가 진다.

먼저 알아야 할 것 09-01

#1문제 상황

암호화를 직접 켜지 않으면 어떤 키로 보호했는지 알 수 없다. 그러면 저장된 데이터가 드러났을 때 스스로 확인할 방법이 없다.

SSE-S3는 Amazon S3 managed encryption keys로 오브젝트를 자동 암호화한다. 키 관리와 암호문 보관 책임은 AWS가 진다.

#2핵심 질문

키를 직접 만들지 않고 저장 데이터 암호화를 어떻게 켜는가?

#3동작 예시

버킷에서 파일 하나를 내려받아 열면 내용이 정상으로 보인다. 별도 키 설정 없이도 S3가 저장과 조회 때 자동으로 암호화와 복호를 처리한다.

#4동작 과정

  1. 자동으로 건다S3는 모든 새 오브젝트를 SSE-S3로 암호화해 저장한다. AES-256 계열 알고리즘을 쓰고 오브젝트마다 고유 키를 쓴다.
  2. 키도 한 겹 더 감춘다그 오브젝트 키 자체를 S3가 주기적으로 교체하는 키로 다시 암호화해 보관한다.
  3. 요청마다 방식을 밝힌다default bucket encryption 설정으로 새 버킷의 기본값을 정할 수 있고, 요청 응답 헤더에 x-amz-server-side-encryption가 붙는다.
  4. 확인해 볼 것업로드 응답에 x-amz-server-side-encryption 값이 어떻게 표시되는지 확인한다.

SSE-KMS — KMS 키로 직접 암호화한다

SSE-KMS는 AWS Key Management Service(KMS)의 고객 관리형 키로 오브젝트를 암호화하는 방식으로, 어떤 키가 쓰였는지 권한과 접근 기록을 직접 통제할 수 있어 회귀 방지 같은 목적에 맞는다.

먼저 알아야 할 것 09-02

#1문제 상황

SSE-S3는 S3가 알아서 암호화한다(→ 09-02). 하지만 데이터가 유출된 뒤 이력이 남아 있지 않다면 무엇이 언제 드러났는지 알 수 없다.

SSE-KMS는 AWS KMS의 KMS key를 직접 지정한다. 그 키에 대한 권한을 정해 두면 읽기를 제한하고 기록을 남길 수 있다.

#2핵심 질문

어떤 키가 오브젝트를 암호화했는지 통제하고 기록을 남기려면 어떻게 하나?

#3동작 예시

회귀 방지 규칙을 지키려고 KMS에서 회사에만 허용된 키를 만든다. 그 키로 암호화한 오브젝트를 다른 계정에서 내려받으려 하면 kms:Decrypt 권한이 없어 거부된다.

#4동작 과정

  1. 키를 고른다SSE-KMS를 쓰면 오브젝트 암호화에 쓸 KMS key를 지정한다. 키 정책에 aws:kms 조건으로 접근자를 묶을 수 있다.
  2. 저장한다S3가 암호문을 저장하고, 키로 다시 복호화해 준다. kms:Decrypt 권한이 있어야 이 동작이 가능하다.
  3. 경로를 막는다암호화 키를 KMS에 두는 구성은 S3 버킷 키(→ 09-04)와 함께 쓸 수 있다.
  4. 확인해 볼 것오브젝트 메타데이터에 암호화 키 ARN이 적혀 있는지 확인한다.

버킷 키로 KMS 비용 줄이기

버킷 키는 S3가 버킷 수준에서 KMS에 요청할 때만 데이터 키를 받게 해 오브젝트마다 KMS 호출 비용이 나지 않게 하는 기능으로, 암호화 강도는 그대로 두고 KMS 요청과 비용만 크게 낮춘다.

먼저 알아야 할 것 09-03

→ 09-03 참조

#1문제 상황

SSE-KMS로 오브젝트를 하나씩 암호화하면(→ 09-03) 파일 수만큼 KMS에 요청이 나간다. 데이터 레이크처럼 오브젝트가 많은 워크로드에서는 이 요청이 비용으로 커진다.

S3 Bucket Keys는 그 요청을 버킷 단위로 묶는다. 암호화 강도는 그대로 두고 KMS request cost만 낮춘다.

#2핵심 질문

오브젝트가 아주 많을 때 KMS 호출 비용을 어떻게 낮추는가?

#3동작 예시

수백만 오브젝트가 있는 버킷에서 KMS 요청이 크게 늘어난 걸 본다. 버킷 키를 켜 같은 내용을 다시 올리면 KMS로 나가는 요청 수는 훨씬 적어진다.

#4동작 과정

  1. 키를 하나 받는다버킷 키를 켜면 S3가 버킷 수준에서 KMS에 요청해 bucket key를 받는다. bucket key는 오브젝트별 데이터 키를 감싸는 키다.
  2. 나눠 쓴다S3는 받은 bucket key로 여러 오브젝트를 암호화한다. KMS를 직접 부르는 횟수가 줄어 비용이 낮아진다.
  3. 범위를 정한다버킷 키는 DSSE-KMS(→ 09-05)에서는 쓸 수 없고, 복제 대상 버킷에도 따로 설정해야 한다.
  4. 확인해 볼 것버킷 설정에서 S3 Bucket Keys가 켜졌는지 확인한다.

DSSE-KMS와 SSE-C — 두 겹과 직접 들고 오기

DSSE-KMS는 헤더와 본문을 서로 다른 키와 알고리즘으로 각각 한 번 더 암호화해 이중으로 보호하는 방식이고, SSE-C는 암호화 키를 사용자가 직접 만들어 매 요청마다 헤더로 보내 S3가 쓰되 저장하지 않는 방식이다.

먼저 알아야 할 것 09-03

→ 09-03 참조

#1문제 상황

SSE-KMS는 한 겹만 암호화한다(→ 09-03). 한 겹이 뚫리면 데이터가 그대로 드러난다. 또 키를 S3에 맡기면 언제 그 키로 뭘 했는지 세부가 남지 않는다.

DSSE-KMS는 두 겹을 씌우고, SSE-C는 customer-provided encryption keys를 사용자가 들고 다닌다.

#2핵심 질문

암호화를 두 겹으로 하거나 키를 내 손에 두려면 어떻게 하나?

#3동작 예시

이중 암호화를 켠 오브젝트는 kms:Decrypt 권한이 있는 쪽만 열 수 있다. SSE-C로 올린 오브젝트는 키를 보낸 그 요청에서만 읽히고, S3에는 키가 남지 않는다.

#4동작 과정

  1. 두 번 건다DSSE-KMS의 dual-layer server-side encryption는 본문을 KMS가 만든 데이터 키로 암호화하고, 그 암호문을 S3가 관리하는 AES-256 키로 다시 암호화한다. 한 겹이 깨져도 다른 겹이 지킨다.
  2. 키를 들고 간다SSE-C는 매 요청마다 x-amz-server-side-encryption-customer-key 헤더로 키를 보낸다. S3는 그 키로 암호화하고 저장하지 않는다.
  3. 기억한다두 방식 다 매번 키를 다시 보내야 읽히므로 애플리케이션이 키를 안전하게 보관할 곳을 마련해야 한다.
  4. 확인해 볼 것오브젝트 응답에서 암호화 방식을 나타내는 헤더 값이 어떻게 다른지 확인한다.

전송 구간 암호화

전송 구간 암호화는 클라이언트와 S3 사이를 지나는 데이터를 HTTPS의 TLS 계층 암호화로 보호하는 것으로, 저장 시점 암호화와 달리 서버에 도착하기 전 구간까지 안전하게 만드는 수단이다.

먼저 알아야 할 것 09-01

→ 09-01 참조

#1문제 상황

저장 시점 암호화가 있어도(→ 09-01) 데이터는 클라이언트에서 서버로 오가는 동안 그대로 노출된다. 그 구간에서 훔쳐 보면 서버는 아무것도 막지 못한다.

전송 구간 암호화는 그 구간을 따로 지킨다. 보호 대상은 encryption in transit, 이동 중인 데이터다.

#2핵심 질문

데이터가 서버로 이동하는 동안에는 어떻게 지킬까?

#3동작 예시

S3 콘솔에서 버킷의 URL을 열어 보면 주소가 https로 시작한다. 내려받는 응답이 중간에서 바뀌지 않았음을 클라이언트가 확인한다.

#4동작 과정

  1. 연결한다HTTPS로 접속하면 TLS가 전송 내용을 암호화한다. S3는 클라이언트가 지원하는 가장 강한 TLS 버전을 자동으로 고른다.
  2. 버전을 정한다S3는 모든 API 엔드포인트에서 TLS 1.2와 TLS 1.3을 지원하고, AWS SDK와 CLI는 기본으로 TLS 1.3을 쓴다.
  3. 한 겹 더 진다hybrid post-quantum key exchange를 켜면 미래의 양자 공격에도 대비한 키 교환을 함께 쓴다. client-side encryption을 더하면 서버 도착 전에도 내용은 안 보인다.
  4. 확인해 볼 것S3 엔드포인트 접속 시 실제로 사용된 TLS 버전이 무엇인지 확인한다.

버전 관리 — 같은 이름의 여러 판

버전 관리란 오브젝트를 다시 저장할 때마다 같은 키(전체 경로 이름) 아래에 시간과 번호가 붙은 새로운 판을 쌓아 두어 과거 판도 되살릴 수 있게 하는 기능이다.

먼저 알아야 할 것 02-02

#1문제 상황

같은 파일 이름으로 덮어쓰면 이전 내용은 사라진다. 실수로 지우거나 잘못 덮어써도 원래대로 되돌릴 길이 없다.

S3 Versioning은 버킷에 저장된 모든 오브젝트의 판을 보존하고 복구하는 기능이다. 키(전체 경로 이름)는 그대로 두고 판마다 다른 번호가 붙는다.

#2핵심 질문

덮어썼거나 지운 오브젝트를 어떻게 다시 되살릴까?

#3동작 예시

사진 파일 report.pdf를 고쳐 다시 올린다. 같은 키 아래에 새 판이 쌓이고, 이전 판은 지워지지 않은 채 남는다.

실수로 이 파일을 지워도 그 자리에 지워졌다는 표시만 남고 원본 데이터는 그대로 있다.

#4동작 과정

  1. 버전 관리를 켠다버킷의 Bucket Versioning 상태를 enabled로 바꾸면 새 판이 쌓이기 시작한다. 기본값은 꺼진 상태다.

Object Lock은 오브젝트를 지정한 보관 기간(Governance 모드에서 통제 모드)이나 법적으로 보존 기간(컴플라이언스 모드) 동안 삭제나 덮어쓰기를 AWS가 거부하도록 잠그는 기능이다.

먼저 알아야 할 것 10-03

#1문제 상황

Object Lock은 write-once-read-many, 즉 한번 쓰고 여러 번 읽기만 허용하는 방식으로 오브젝트 판을 잠근다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 잠근다Object Lock을 켜면 오브젝트 판에 쓰기 한 번만 허용되고 이후 쓰기와 삭제가 거부된다.
  2. 보관 기간을 건다retention period는 판이 잠기는 고정 시간을 지정한다. 두 유형이 있어 governance mode는 권한이 있는 사람이 조제를 풀 수 있고, compliance mode는 그 조제도 막는다.
  3. 법적 보존을 건다legal hold는 기간을 정하지 않고 수동으로든 켜고 꺼는 보존 상태다. 판은 기간과 보존 중 하나 또는 둘 다 가질 수 있다.
  4. 확인해 볼 것버킷 설정에서 Object Lock이 켜져 있는지, 오브젝트의 보존 상태가 표시되는지 확인한다.

#1문제 상황

#1문제 상황

#4동작 과정

  1. 감시 비용을 낸다S3가 모든 오브젝트를 세어 보는 monitoring object charges가 붙는다. 요금 한도를 정해 두고 그 안에서만 계층을 움직인다.

  4. 확인해 볼 것버킷의 오브젝트 목록에서 파일마다 붙은 Intelligent-Tiering 접근 상태 표시가 frequent access인지 archive access인지 확인한다.

#4동작 과정

  1. 태그로 소속을 표시한다버킷이나 오브젝트에 cost allocation tags를 키-값 쌍으로 붙인다. 이 태그를 기준으로 과금이 분류된다.
  2. 과금 보고서를 연다Billing and usage reporting에서 S3 비용이 태그별로 묶인 요약을 본다. usage report는 시간대별로 어떤 사용 유형과 작업이 얼마나 발생했는지 모아 준다.
  3. 저장 구성을 잰다Storage Class Analysis가 버킷을 스캔해 저장 클래스별 객체 수와 크기를 집계한다. 어느 클래스에 데이터가 몰려 있는지 보고 옮길 대상을 정한다.
  4. 확인해 볼 것버킷 콘솔에서 Storage Class Analysis 결과를 열어 객체 수와 크기가 저장 클래스별로 나뉘어 표시되는지 확인한다.

CloudTrail — 누가 무엇을 요청했나

CloudTrail 은 누가 언제 어떤 S3 API 호출(예: PutObject, DeleteObject)을 했는지 요청 단위로 남기는 감사 기록 기능으로, 누가 어떤 데이터를 읽고 지웠는지 사후에 확인할 수 있게 한다.

먼저 알아야 할 것 07-02

#1문제 상황

버킷에서 민감한 오브젝트가 사라졌는데 누가 지웠는지 알 수 없다. 서버 접근 로그(→ 12-02)도 대안이 되지만, 권한 판정 과정까지 남기는 쪽이 원인 규명에 낫다.

AWS CloudTrail은 S3 요청을 남겨 사후에 조회하게 한다.

#2핵심 질문

누가 언제 어떤 S3 요청을 보냈는지 어떻게 남겨 두고 찾아 보는가?

#3동작 예시

내부 신원이 갑자기 이름이 같은 오브젝트를 지웠다는 제보를 한다. CloudTrail을 켜 두고 요청 기록을 별도 버킷에 모아 뒀다.

그 기록에서 지워진 시간과 호출자를 찾아 내고, 같은 사람이 지운 다른 오브젝트도 함께 확인한다. 요청 단위로 기록이 남으므로 권한 판정이 어디서 막혔는지도 보인다.

#4동작 과정

  1. 기록을 켠다CloudTrail trail을 만들어 S3 이벤트를 목적지 버킷으로 보낸다. 목적지 버킷의 AWSLogs 경로 아래 날짜별로 폴더가 생긴다.
  2. 압축 기록이 쌓인다기록은 CloudTrail events로 남고 압축된 JSON 파일로 저장된다. 이런 포맷을 다루는 S3 request logging 도구와 결합해 원인 요청을 좁힌다.
  3. 종류를 나눈다bucket 설정 같은 관리 동작은 management events로, 오브젝트 읽기·쓰기 같은 개별 데이터 동작은 data events로 따로 기록한다. 어느 걸 봐야 하는지 다르니 구분해서 연다.
  4. 확인해 볼 것목적지 버킷의 AWSLogs 폴더에 날짜별 CloudTrail 디렉터리가 생기고 안에 JSON 로그가 들어 있는지 확인한다.

서버 접근 로그 — 버킷에 들어온 요청 목록

서버 접근 로그는 S3 버킷에 도착한 모든 요청을 요청자·리소스·응답 코드·바이트 수 등의 항목으로 적은 로그 파일로, 보통 별도의 로그 버킷에 보관한다.

먼저 알아야 할 것 12-01

#1문제 상황

버킷에 누가 무엇을 요구했는지 전체 목록을 보고 싶을 때가 있다. CloudTrail(→ 12-01)은 요청 단위 기록이라 목록 전체를 보기는 어렵다.

서버 접근 로그는 버킷에 도착한 요청을 형식에 맞춰 한 줄씩 적어 쌓는다. 운영 분석과 보안 점검, 사용량 정산에 쓴다.

#2핵심 질문

버킷으로 들어온 요청 전체를 항목별로 어디에 모아 두는가?

#3동작 예시

버킷 관리자가 지난 주 요청 흐름을 돌아본다. 어떤 클라이언트가 가장 많이 불렀고, 오류 응답이 어느 키에서 몰렸는지 서버 접근 로그를 내려받아 본다.

CloudWatch Logs로 보냈다면 CloudWatch Logs Insights에서 같은 내용을 기간별로 질의해 볼 수 있다.

#4동작 과정

  1. 로그를 켠다버킷에 대상 버킷과 권한을 지정해 로그 수집을 켠다. S3가 일정 주기로 접근 기록을 모아 목적지로 보낸다.
  2. 목적지를 고른다Amazon CloudWatch Logs에 보내면 정해진 log file format 그대로 구조화된 형태로 쌓이고, 별도 S3 버킷에 보내면 파일로 보존된다. 둘 다 쓸 수 있다.
  3. 항목을 읽는다각 줄에 요청자·대상 리소스·응답 코드·전송 바이트 수가 들어 있어, identifying S3 requests 규칙으로 특정 요청을 골라낼 수 있다.
  4. 확인해 볼 것목적지 버킷이나 CloudWatch Logs의 log group에 새 로그가 시간 순서대로 들어와 있는지 확인한다.

CloudWatch 지표 — 숫자로 상태를 본다

CloudWatch 지표는 버킷의 요청 수·저장 바이트·오류 발생 수 같은 수치를 시간별로 집계해 CloudWatch 그래프와 알림 임계값에 쓸 수 있게 해 주는 값이다.

먼저 알아야 할 것 12-01

#1문제 상황

버킷에 이상이 생겼는지 로그를 한 줄씩 뒤져야만 알 수 있다(→ 12-01, → 12-02). 누가 무엇을 했는지(events)는 보이더라도, 지금 이 버킷이 정상 규모로 돌아가는지 숫자로 판단할 기준이 없다.

CloudWatch 지표는 S3가 버킷의 요청 수·저장 바이트·오류 발생 수를 시간별로 집계해 Amazon CloudWatch에 내보내는 값이다. 하루 단위 저장 지표와 1분 단위 요청 지표가 나뉘고, 이 값을 그래프와 알림 임계값에 그대로 쓸 수 있다.

#2핵심 질문

버킷의 상태를 숫자로 보고, 이상이 보이면 알림까지 걸려면 무엇을 써야 할까?

#3동작 예시

이미지 업로드가 늘어난 시간대에 CloudWatch 콘솔의 지표 그래프를 연다. 버킷의 PutObject 요청 수와 4xx 오류 수가 함께 오른 것이 보이고, 특정 접두사만 갑자기 늘었다는 사실을 집어낸다.

#4동작 과정

  1. 모으고 켠다CloudWatch metrics configurations에서 어떤 지표를 받을지 골라 켠다. 켜진 뒤 request metrics는 모든 오브젝트 조작에 대해 1분 간격으로 보고된다.
  2. 분류해 붙인다metrics dimensions는 지표를 나눠 보는 기준이다. BucketName과 StorageType 같은 차원을 조합해 버킷별·저장 클래스별 수치를 따로 본다.
  3. 알림을 건다CloudWatch 알림에 이 지표를 조건으로 묶으면 임계값을 넘을 때 경보가 간다. 낮게 잡은 항목은 Amazon CloudWatch 알림으로 슬랙이나 메신저로 전달할 수 있다.
  4. 확인해 볼 것CloudWatch 콘솔에서 해당 버킷의 요청 수 그래프가 시간 간격으로 그려지는지 확인한다.

이벤트 알림 — 변화가 생기면 알려 달라

이벤트 알림은 오브젝트 생성·삭제나 버킷 태그 변경 같은 특정 사건이 발생하면 S3가 Amazon SNS, Lambda, EventBridge 같은 목적지에 자동으로 알림을 보내는 기능이다.

먼저 알아야 할 것 12-01

#1문제 상황

누군가 버킷의 특정 폴더에 새 파일을 올렸는지 알림 없이 Polling으로 계속 확인해야 한다. 파일이 늘어난 양을 수시로 알려면 지표 그래프(→ 12-03)로는 보이지 않는다. 그 순간의 사실만 바로 받으려면 다른 수단이 필요하다.

Amazon S3 Event Notifications는 오브젝트 생성·삭제 같은 사건이 발생하면 S3가 지정한 곳으로 알림을 직접 보내는 기능이다. 알림은 한 번 이상 전달되는 방식으로, 보통 몇 초 안이지만 더 걸릴 수도 있다.

#2핵심 질문

버킷 안에서 무슨 일이 생겼는지 Polling 없이 바로 알림으로 받으려면?

#3동작 예시

Lambda 함수가 이미지 버킷에 업로드한다. 곧바로 그 함수가 실행되고, 전달된 event message structure 안에서 오브젝트 키 이름을 읽어 썸네일을 만든다.

#4동작 과정

  1. 설정한다버킷의 notification 서브리소스에 알림 구성을 저장한다. 어떤 사건을 publish할지와 어디로 보낼지를 함께 적는다.
  2. 걸러 낸다object key name filtering으로 특정 접두사의 오브젝트만 걸러 알림을 받는다. 나머지 접두사는 아예 통보되지 않는다.
  3. 보낸다목적지는 Amazon SQS나 Amazon SNS 큐·토픽일 수 있고, AWS Lambda 함수나 Amazon EventBridge일 수도 있다. 복제 완료와 Lifecycle 전환 같은 사건도 같은 통로로 보낸다.
  4. 확인해 볼 것버킷 설정의 알림 화면에 등록된 사건과 목적지가 목록으로 보이는지 확인한다.

Storage Lens 와 Inventory — 전체를 조감해 보다

Storage Lens 는 전체 계정의 저장량·비용·보안 상태를 집계해 보여 주는 대시보드이고, S3 Inventory 는 버킷의 오브젝트 목록과 크기·스토리지 클래스·수정 시각 같은 메타데이터를 정기적으로 목록 파일로 만들어 주는 기능이다.

먼저 알아야 할 것 12-03

#1문제 상황

버킷이 여러 개이고 오브젝트가 수백만 개다. 어디에 용량이 몰렸고 어떤 버킷이 관리를 놓치고 있는지 개별 조회로는 그림이 안 그려진다. 모아 둔 목록도 항상 최신은 아니다(→ 12-01).

S3 Storage Lens는 계정과 조직의 저장량·비용·보안 상태를 지표로 모아 대시보드로 보여 주고, Amazon S3 Inventory는 버킷의 오브젝트 목록을 보고서 파일로 따로 만든다.

#2핵심 질문

전체 저장과 비용 흐름을 한눈에 보고, 오브젝트 목록을 분석용 파일로 받아오려면?

#3동작 예시

비용이 올라간 주말에 Storage Lens 대시보드를 연다. 가장 빠르게 자라는 버킷이 보이고, 거기서 Lifecycle 규칙이 없어 며칠 지난 미완성 멀티파트 조각이 쌓인 것이 지표로 확인된다.

#4동작 과정

  1. 모은다S3 Storage Lens가 계정 단위로 metrics를 집계하고 추천을 계산한다. 이 dashboards를 대시보드 화면에서 볼 수 있고 data export로 다른 분석 도구로 보낼 수 있다.
  2. 규칙을 확인한다지표에는 버전 관리나 복제, Lifecycle 같은 데이터 보호 관행이 빠진 버킷이 빠진 자리로 표시된다. 확인 뒤 바로 규칙을 넣을 곳을 정한다.
  3. 목록을 받는다inventory configuration으로 Amazon S3 Inventory를 정하면 정해진 주기에 따라 inventory report가 지정한 버킷에 생성된다.
  4. 확인해 볼 것대시보드에서 버킷별 저장량과 비용 배분 막대 그래프가 그려지는지 확인한다.
