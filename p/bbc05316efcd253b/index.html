1기초 — 서비스 이해01-01

Amazon OpenSearch Service 개요

AWS가 인프라를 관리하는 검색·분석 관리형 서비스로, OpenSearch 엔진 기반 도메인을 만들어 검색·로그 분석·벡터 검색을 실행한다.

1상대의 출발점 확인

검색 기능이 필요해지면, 기존 방식에서는 서버를 준비하고 그 위에 검색 엔진을 직접 설치했습니다. 엔진을 설치하는 것으로 끝이 아닙니다. 클러스터를 구성하고, 패치를 올리고, 백업을 떠야 하고, 데이터가 늘면 용량 계획까지 세워야 합니다. 검색이라는 본질과는 상관없는 인프라 운영에 시간과 인력이 계속 들어갑니다. 여기서 문제가 되는 지점은 검색 기능을 쓰기 위해 인프라 관리까지 통째로 부담해야 한다는 것입니다.

2질문 제기

검색과 분석 기능을 쓰면서, 그 밑에 깔린 인프라 운영까지 내가 전부 관리해야만 하는 것일까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 서버 여러 대를 직접 준비하는 대신, 콘솔에서 도메인 하나를 만듭니다. 이름과 버전, 인스턴스 유형을 정하고 생성하기만 하면, 검색 요청을 받을 준비가 된 관리형 클러스터가 준비됩니다. 거기에 로그 데이터를 밀어 넣고 검색 쿼리를 보내면 결과가 돌아옵니다. 내가 신경 쓴 것은 데이터를 넣고 검색하는 일뿐입니다. 여기서 본질은 인프라 관리를 AWS에 맡기고 사용자는 검색에만 집중한다는 것입니다.

4단계별 동작 과정

  1. 도메인 생성검색·분석을 실행할 관리형 클러스터(도메인)를 AWS에 만든다.
  2. 데이터 색인문서를 도메인에 올려 검색 가능한 구조로 저장한다.
  3. 검색·분석 실행쿼리로 문서를 찾고, 로그 분석이나 벡터 검색까지 수행한다.

5본질 요약

AWS가 인프라를 관리하고 사용자는 도메인만 만들어 데이터를 넣으면 즉시 검색·로그 분석·벡터 검색을 실행할 수 있는 관리형 서비스라는 것

1기초 — 서비스 이해01-02

OpenSearch와 Service 선택 기준

오픈소스 OpenSearch를 직접 운영할지 AWS 관리형 OpenSearch Service를 쓸지 결정하는 기준으로, 운영 부담·확장성·비용·기능 차이를 비교한다.

1상대의 출발점 확인

기존 방식으로는 오픈소스 OpenSearch를 직접 운영했습니다. EC2 인스턴스에 엔진을 설치하고, 버전 업그레이드에 따른 호환성 점검과 패치 적용, 노드 장애 대응과 백업까지 전부 우리 손으로 해야 합니다. 데이터가 늘면 클러스터를 어떻게 확장할지도 직접 설계해야 합니다. 여기서 문제가 되는 지점은 검색 엔진의 기능보다 운영 부담이 선택을 좌우한다는 것입니다.

2질문 제기

엔진이 오픈소스라면, 굳이 비용을 내고 관리형 서비스를 선택해야 하는 것일까요?

3구조적 핵심 예시

트래픽이 급증해 노드를 늘려야 하는 상황을 보겠습니다. 직접 운영할 때는 스토리지와 샤드 구성을 점검하고, 노드를 추가한 뒤 재분배가 안정적으로 끝나는지 계속 지켜봐야 합니다. 관리형 서비스라면 원하는 인스턴스 개수를 지정하고 상태를 확인하면 됩니다. 여기서 본질은 같은 엔진이라도 운영 부담과 확장 방식이 선택 기준이 된다는 것입니다.

4단계별 동작 과정

  1. 운영 부담 비교직접 운영은 패치·백업·모니터링을 모두 직접 하지만, 관리형은 AWS가 인프라 운영을 담당한다.
  2. 확장성 비교직접 운영은 용량 계획을 세워 증설하지만, 관리형은 클러스터 구성을 조정해 대응한다.
  3. 비용·기능 비교직접 운영은 자원 비용만 들지만, 관리형은 관리 편의에 대한 비용이 더해지고 AWS 서비스와의 통합 기능을 제공한다.

5본질 요약

이 기준운영 부담과 확장성, 비용과 제공 기능을 비교해 검색 엔진을 직접 운영할지 AWS에 맡길지를 결정하는 것

1기초 — 서비스 이해01-03

지원 버전과 표준·확장 지원

OpenSearch Service가 지원하는 엔진 버전(OpenSearch 및 레거시 Elasticsearch OSS)과 버전별 표준·확장 지원 정책을 설명한다.

1상대의 출발점 확인

기존 방식에서는 버전 선택을 단순하게 봤습니다. 최신 버전을 쓰면 그만이라고 생각했습니다. 그러나 관리형 서비스에서는 상황이 다릅니다. 지원하는 엔진 버전에는 OpenSearch와 레거시 Elasticsearch OSS가 있고, 버전마다 지원되는 기능이 다르며, 지원 기간도 따로 정해져 있습니다. 여기서 문제가 되는 지점은 버전을 고를 때부터 지원 기간과 기능 차이를 함께 봐야 한다는 것입니다.

2질문 제기

  2. 패키지 업로드 및 연결만들어진 패키지를 OpenSearch Service 콘솔이나 API로 도메인에 업로드하고, 도메인 설정(ClusterConfig 커스텀 패키지 목록)에 연결합니다. 연결된 패키지는 도메인 인스턴스에 배포됩니다.
  3. 설정 반영과 사용패키지가 배포되면 인덱스 매핑·분석기 설정에서 해당 플러그인이나 사전을 참조해 검색에 사용합니다. 이로써 기본 구성에 없던 검색 기능이 실제 질의에서 동작합니다.

SQL 지원

OpenSearch 데이터를 익숙한 SQL 문법으로 질의할 수 있게 해주는 기능으로, SQL을 REST API·도구를 통해 실행한다.

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 지금까지 여러분은 데이터를 꺼내려면 OpenSearch의 질의 DSL을 써 왔습니다. DSL은 JSON으로 질의를 표현하는 방식이라, 검색에는 강력하지만 데이터베이스처럼 행과 열을 조건에 따라 뽑아내고 집계하는 작업에는 익숙하지 않습니다. 익숙한 SQL 문법에 길든 사람이 DSL만으로 뭔가를 뽑아내려면, JSON 구조와 쿼리 문맥을 새로 익혀야 합니다. 여기서 문제가 되는 지점은 이것입니다. 데이터 질의를 위한 언어의 장벽입니다. OpenSearch 안에 데이터가 있는데, 그 데이터를 다루는 데 익숙한 수단이 없다 보니 접근 자체가 어려워집니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. OpenSearch에 저장된 데이터를, SQL에 익숙한 사람이 그대로 질의할 수는 없을까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 여러분이 로그 인덱스에서 status가 500인 문서와 그 개수를 뽑고 싶다고 합시다. DSL로는 큰 JSON 질의를 짜야 하지만, SQL 지원을 쓰면 SELECT * FROM logs WHERE status = 500 같은 한 줄이 곧 질의입니다. 이 질의 문자열을 SQL REST API에 실어 보내면 OpenSearch가 질의를 분석해 실행하고, 결과를 받아옵니다. 여기서 본질은 이것입니다. SQL은 OpenSearch 데이터에 접근하는 또 하나의 공식 질의 통로라는 것입니다. 내부 데이터가 어떻게 저장되어 있는지와 무관하게, SQL 문법이라는 익숙한 창구로 데이터를 뽑아내는 것이 이 기능의 핵심입니다.

4단계별 동작 과정

  1. 질의 작성SQL을 지원하는 REST API(_plugins/_sql)에 SELECT 문으로 된 질의 문자열을 담아 요청을 보냅니다. 여기서 SQL은 일반 데이터베이스에서 쓰는 것과 같은 문법입니다.
  2. 질의 변환과 실행OpenSearch가 받은 SQL을 내부의 질의 DSL로 번역해 인덱스에 대해 실행합니다. 사용자는 변환 과정을 볼 필요 없이 결과만 받습니다.
  3. 결과 반환실행 결과를 JSON 등 형식으로 돌려받습니다. SQL을 지원하는 도구나 시각화 클라이언트에서도 같은 질의를 그대로 사용할 수 있습니다.

여러 OpenSearch 클러스터(도메인)에 흩어진 인덱스를 하나의 질의로 함께 검색할 수 있게 하는 기능이다.

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 지금까지 여러분의 질의는 하나의 도메인 안에서만 살아 있었습니다. 도메인 하나에 인덱스가 몇 개든, 검색은 그 도메인의 데이터만 뒤졌습니다. 그런데 운영을 하다 보면 도메인이 여럿으로 갈리는 일이 생깁니다 — 환경을 분리했다든가, 데이터 성격별로 도메인을 나눴다든가, 리전이 달라졌다든가. 그 상태에서 전체 데이터를 한 번에 뒤지려면, 여러분은 각 도메인에 질의를 따로따로 보내고 결과를 직접 합쳐야 합니다. 여기서 문제가 되는 지점은 이것입니다. 데이터가 흩어져 있는 만큼 질의도 흩어진다는 것입니다. 도메인이 늘어날수록 질의 코드도, 결과 정리도 그만큼 늘어납니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. 여러 도메인에 흩어진 인덱스를, 하나의 질의로 함께 검색할 수는 없을까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. A 도메인에 올해 로그, B 도메인에 작년 로그가 있다고 합시다. 여러분은 A 도메인에 연결해 크로스 클러스터 검색을 설정하고, 질의에서 B 도메인의 인덱스를 원격 인덱스로 참조합니다. 그다음 한 번의 검색 요청 — 예를 들어 두 도메인의 로그를 함께 뒤지는 질의 — 을 A 도메인에 보내면, A가 B로 질의를 전달해 결과를 모아 돌려줍니다. 여기서 본질은 이것입니다. 크로스 클러스터 검색은 질의를 한 곳에 모으는 일이라는 것입니다. 데이터의 물리적 위치와 무관하게, 사용자는 하나의 진입점으로 모든 인덱스를 검색하게 되는 것이 이 기능의 핵심입니다.

4단계별 동작 과정

  1. 연결 설정검색을 시작할 도메인(로컬 클러스터)에 원격 도메인(원격 클러스터)의 연결 정보를 등록합니다. 이때 인증과 허용 목록으로 어떤 도메인끼리 연결되는지 정합니다.
  2. 원격 인덱스 질의질의에서 원격클러스터:인덱스 형태로 원격 인덱스를 참조해 로컬 도메인에 검색 요청을 보냅니다. 로컬 클러스터가 질의를 원격 클러스터로 전달합니다.
  3. 결과 통합 반환각 클러스터의 검색 결과가 모여 하나의 응답으로 돌아옵니다. 사용자는 결과가 어느 클러스터에서 왔는지 구분하지 않고 전체 검색 결과를 사용합니다.

Learning to Rank

검색 결과의 순위를 사용자 상호작용·피드백 데이터로 기계학습 모델을 학습시켜 개선하는 기능이다.

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 지금까지 검색 결과의 순위는 질의와 문서의 점수, 즉 유사도 점수에 의해서만 정해졌습니다. 문서가 질의와 얼마나 어휘적으로 맞는지가 순위의 전부였습니다. 그런데 실제 서비스에서 잘 맞는 결과를 보면, 순위가 반드시 점수 순서와 같지는 않습니다. 사용자가 자주 고르는 결과가 있고, 자주 무시하는 결과가 있습니다. 그런데 기존 순위는 그런 사용자의 행동을 전혀 반영하지 못합니다. 여기서 문제가 되는 지점은 이것입니다. 순위가 사용자의 실제 선호를 모른다는 것입니다. 점수는 텍스트 사이의 관계일 뿐, 사람이 결과를 어떻게 받아들이는지는 담지 못합니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. 검색 순위가 사용자의 실제 선택과 피드백을 배워서 더 나은 순서를 만들 수는 없을까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 쇼핑 검색에서 "운동화"를 검색했을 때, 기존 순위는 텍스트 유사도가 높은 순서대로 나옵니다. 그런데 로그를 보면 사용자들이 실제로는 다른 상품을 더 많이 클릭하고 구매합니다. 여러분은 이 클릭·구매 데이터를 피드백으로 모아 기계학습 모델을 학습시킵니다 — 어떤 문서가 질의에 대해 더 좋은 결과인지를 배우는 모델입니다. 그 학습된 모델을 검색 파이프라인에 붙이면, 이후 질의는 유사도 점수에 모델의 판단까지 합쳐져 순위가 다시 매겨집니다. 여기서 본질은 이것입니다. Learning to Rank는 순위를 '계산'에서 '학습'으로 바꾸는 것이라는 것입니다. 텍스트만 보던 순위가, 사람의 행동이라는 증거를 보고 순서를 정하게 되는 것이 이 기능의 핵심입니다.

4단계별 동작 과정

  1. 학습 데이터 준비검색 로그에서 사용자 상호작용·피드백 데이터(클릭, 구매, 선호 순위)를 추출해 학습 데이터로 만듭니다. 이 데이터가 모델이 배울 정답입니다.
  2. 모델 학습과 업로드학습 데이터로 랭킹 모델을 학습시킵니다. 학습된 모델은 추론 엔진과 함께 도메인에 업로드됩니다. 여기서 모델은 질의-문서 쌍에 대한 더 나은 순위 점수를 출력합니다.
  3. 검색 파이프라인 적용검색 요청이 오면 기존 유사도 점수에 모델의 점수를 결합해 최종 순위를 매깁니다. 이후의 모든 질의가 학습된 순위 기준으로 결과를 돌려줍니다.

비동기 검색과 Point in time

큰 질의를 백그라운드에서 처리하는 비동기 검색과, 특정 시점의 일관된 인덱스 상태(PIT) 위에서 페이징 검색을 가능하게 하는 기능이다.

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 지금까지 여러분은 검색을 보낸 그 순간, 그 응답을 기다리는 동기 방식으로만 질의했습니다. 요청을 보내면 클라이언트는 결과가 올 때까지 연결을 붙잡고 있고, 질의에 시간이 걸리면 그만큼 응답이 늦어집니다. 큰 질의, 많은 인덱스를 뒤지는 질의는 몇 초를 넘기기도 하고, 그동안 클라이언트는 아무 일도 못 합니다. 거기에 페이징 — 여러 페이지에 걸쳐 결과를 나누어 받는 일 — 도 까다롭습니다. 그 사이에 인덱스에 문서가 추가되거나 삭제되면 페이지마다 보이는 결과가 달라질 수 있기 때문입니다. 여기서 문제가 되는 지점은 이것입니다. 검색이 클라이언트를 기다리게 하고, 페이지 사이에 기준이 흔들린다는 것입니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. 큰 질의를 기다리지 않고 백그라운드로 처리하면서, 일관된 기준 위에서 페이지를 넘길 수는 없을까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 수천만 건 로그를 뒤지는 질의를 생각해 봅시다. 동기 방식이었다면 클라이언트는 몇 초를 통째로 기다렸을 것입니다. 비동기 검색으로 바꾸면, 여러분은 질의를 던지고 질의 ID 하나를 받아옵니다. 그 사이 클라이언트는 다른 일을 할 수 있고, 나중에 그 ID로 결과가 준비되었는지 확인해 받아갑니다. 그리고 Point in time(PIT)을 만들어 두면, 페이징하는 내내 검색 기준이 고정됩니다. 여기서 본질은 이것입니다. 비동기 검색은 '기다리는 검색'을 '나중에 찾는 검색'으로 바꾸는 것이고, PIT는 그 검색의 기준을 흔들리지 않게 고정하는 것입니다. 이 둘이 합쳐져 큰 질의도 안정적으로 처리됩니다.

4단계별 동작 과정

  1. 비동기 질의 제출비동기 검색 API로 질의를 보내고, 즉시 질의 ID를 돌려받습니다. 검색은 백그라운드에서 실행되며 클라이언트는 대기하지 않습니다.
  2. 결과 확인 및 수신질의 ID로 상태를 확인하다가 결과가 준비되면 받아갑니다. 처리 중에도 일부 결과는 중간 상태로 조회할 수 있습니다.
  3. PIT 위에서 페이징필요하면 검색 전에 Point in time을 생성해 인덱스 상태의 스냅샷을 고정하고, 그 기준 위에서 페이지를 넘깁니다. 검색이 끝나면 질의와 PIT를 정리합니다.

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 시맨틱 검색의 핵심 재료는 벡터 임베딩입니다 — 문서와 질의를 각각 숫자 벡터로 바꾸어, 뜻이 가까운 것끼리 벡터가 가까워지게 만드는 것입니다. 문서를 임베딩해 인덱스에 저장해 두면, "비용이 저렴한 노트북"이라는 질의도 임베딩되어 "가성비 좋은 랩탑" 문서의 벡터와 가까운 거리로 검색됩니다. 여기에 에이전틱 검색을 더하면, 에이전트가 질의를 분석해 여러 인덱스에서 필요한 질의를 스스로 구성하고 실행합니다. 자연어 검색은 쿼리 생성기(LLM)가 일상 문장을 검색 질의로 만들어 줍니다. 여기서 본질은 이것입니다. 이 검색들은 '단어 비교'를 '의미 비교'로 바꾸고, '질의 설계'를 시스템에게 맡기는 것이라는 것입니다.

4단계별 동작 과정

  1. 벡터화와 저장문서를 모델로 임베딩해 벡터로 만들고, k-NN(최근접 이웃) 방식으로 검색할 수 있게 인덱스에 함께 저장합니다. 단어의 뜻이 벡터의 위치로 표현됩니다.
  2. 의미 기반 질의 실행질의도 같은 모델로 임베딩해, 저장된 문서 벡터와의 거리로 관련 문서를 찾습니다. 에이전틱 검색에서는 에이전트가 이 과정의 질의 구성을 스스로 처리하고, 자연어 검색에서는 LLM이 문장을 질의로 변환합니다.

직접 질의(Direct Queries)

도메인에 데이터를 저장하지 않고 S3·CloudWatch Logs·Security Lake·Managed Prometheus 같은 외부 데이터 소스를 SQL·PPL로 직접 질의하는 기능이다.

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 지금까지 OpenSearch로 무언가를 검색하려면, 먼저 데이터를 OpenSearch 도메인에 넣어야 했습니다. 데이터를 인덱싱 — 문서를 가져와 인덱스 구조로 저장하는 일 — 해야 비로소 질의할 수 있었습니다. 그런데 분석하고 싶은 데이터가 S3에 있고, 로그가 CloudWatch Logs에 있고, 보안 데이터가 Security Lake에 있다면 어떻겠습니까. 그 데이터를 질의하려고 전부 OpenSearch로 복사해 인덱싱하는 것은 비용도 시간도 큽니다. 여기서 문제가 되는 지점은 이것입니다. 질의하려면 데이터를 먼저 옮겨야 한다는 것입니다. 데이터가 있는 곳과 질의하는 곳이 분리되어, 이동이라는 중간 단계가 항상 붙습니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. 데이터를 OpenSearch로 옮기지 않고, 데이터가 있는 원천을 그대로 질의할 수는 없을까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 여러분의 서버 로그가 S3 버킷에 Parquet 파일로 쌓여 있다고 합시다. 기존 방식이라면 그 파일들을 읽어 도메인에 인덱싱한 뒤에야 검색할 수 있었습니다. 직접 질의를 쓰면, 여러분은 OpenSearch에 소스(데이터의 위치와 형식)를 등록해 두고 SELECT * FROM S3 로그 테이블 형태로 질의를 보냅니다. OpenSearch가 S3의 데이터를 그 자리에서 읽어 결과를 돌려줍니다. 여기서 본질은 이것입니다. 직접 질의는 '데이터 이동' 단계를 통째로 생략하는 것입니다. 데이터가 있는 곳에 질의가 찾아가는 것이 이 기능의 핵심입니다.

4단계별 동작 과정

  1. 소스 등록S3, CloudWatch Logs, Security Lake, Managed Prometheus 같은 외부 데이터 소스의 위치와 형식을 OpenSearch에 등록합니다. 여기서 소스는 질의할 데이터의 정보다.
  2. 질의 실행SQL이나 PPL(파이프라인 처리 언어)로 소스의 데이터를 직접 질의합니다. OpenSearch가 외부 데이터를 읽어 처리하고, 실행 계획을 세워 질의를 수행합니다.
  3. 결과 반환과 정리질의 결과를 돌려받습니다. 데이터는 원천에 그대로 남아 있으며, OpenSearch로 복사되지 않습니다.

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 지금까지 여러분이 써 온 검색은 전부 키워드 검색입니다. 문서 안에 "벡터"라는 단어가 정확히 들어 있는지, 그 단어가 몇 번 나오는지, 그런 걸 보고 관련도를 매겼죠. 그 방식이 가진 본질적 한계는 이것입니다. 문자가 아니라 의미를 봐야 하는 상황이 오면, 키워드 검색은 아예 답을 못 냅니다. 3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. "반려견"이라는 단어를 숫자 벡터로 바꾼다고 합시다. 컴퓨터가 단어를 (0.4, 0.9, 0.2) 같은 숫자 배열로 바꿔놓으면, "강아지"라는 단어가 (0.41, 0.88, 0.21) 로 변환되어 의미상 가까운 숫자가 됩니다. 검색은 이제 단어 비교가 아니라 숫자 사이의 거리 비교가 됩니다. 그 거리가 가까운 문서를 찾는 방식이 벡터 검색이고, 그때 쓰는 알고리즘이 k-NN, 최근접 이웃입니다. 검색어 벡터와 가장 가까운 이웃 k개를 찾아내는 것이죠. 여기서 본질은 이것입니다. 의미를 숫자로 바꿔서, 거리라는 수학적 기준으로 유사도를 재는 것입니다.

  2. k-NN 검색 실행검색어도 같은 방식으로 벡터로 바꾼 뒤, 저장된 문서 벡터들과의 거리를 계산해 가장 가까운 이웃, 즉 k-NN 알고리즘으로 유사한 항목 k개를 찾아냅니다.
  3. 결과 반환거리가 가까운 순서대로 상위 결과를 사용자에게 돌려줍니다. 의미가 비슷한 문서가 검색 결과로 나옵니다.

3구조적 핵심 예시

  2. 벡터 인덱스 생성·병합 가속화GPU가 벡터 거리 계산을 수천 개 단위로 병렬 처리해, 인덱스 생성과 세그먼트 병합 작업을 크게 단축합니다.
  3. 검색에 활용만들어진 인덱스에 일반적인 벡터 검색을 수행합니다. 색인은 빨라졌지만 검색 질의 응답은 그대로 정확하게 동작합니다.

다른 클러스터나 리전으로 인덱스를 실시간 복제(cross-cluster replication)하거나 원격 인덱스에서 다시 색인(remote reindex)하는 기능.

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 지금까지는 인덱스 하나가 도메인 하나에 종속되어 있었습니다. 그 말은, 데이터를 넣고 서비스하는 곳이 한 곳뿐이라는 뜻입니다. 여기서 문제가 되는 지점은 이것입니다. 그 한 곳에 장애가 나면, 또는 사용자가 다른 리전에 살고 있는데 인덱스가 먼 리전에만 있으면, 서비스가 멈추거나 응답이 느려집니다. 같은 데이터를 두 군데에 두고 싶은데, 지금 방식으로는 그냥 복사해서 갖다 놓는 것밖에 방법이 없었고, 그 복사본은 원본과 점점 달라집니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. 데이터를 다른 클러스터나 리전으로 옮기고, 원본이 바뀌면 복사본도 따라 바뀌게 하려면 어떻게 해야 할까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 서울에 있는 인덱스를 도쿄 리전의 도메인으로 실시간 복제한다고 해보겠습니다. 원본 인덱스에 새 문서가 하나 들어오면, 그 변경이 그대로 도쿄의 복제본에 반영됩니다. 반면에 이미 만들어진 인덱스를 통째로 다른 곳에서 다시 색인할 수도 있는데, 이 경우는 데이터를 원격 인덱스에서 읽어 와서 새 위치에 처음부터 다시 쌓는 작업입니다. 여기서 본질은 이것입니다. 실시간으로 따라가는 것과, 한 번에 다시 쌓는 것, 이 둘은 목적이 다릅니다.

4단계별 동작 과정

  1. 복제 구성원본 인덱스와 대상 클러스터를 지정하고 복제 관계를 만듭니다. 복제란 원본의 변경이 즉시 반영되는 연결입니다.
  2. 원본 변경 반영원본 인덱스에 문서가 추가·수정·삭제되면 그 변경이 자동으로 대상 클러스터의 복제본 인덱스에 전달됩니다.
  3. 재색인 수행복제와 달리, 원격 인덱스에서 데이터를 읽어 새 인덱스로 다시 쌓는 원격 재색인(remote reindex)을 실행하고 그 결과로 새 인덱스가 완성됩니다.

5본질 요약

같은 인덱스를 다른 클러스터나 리전에 실시간으로 복제하거나, 원격 인덱스에서 다시 색인해 데이터의 가용성과 이동을 확보하는 것입니다. 본질을 알았으니 어떤 상황에도 흔들리지 않습니다

이거 하나만 딱 보고 가겠습니다. CloudWatch 지표로 CPU 사용률과 디스크 여유 공간을 추적하고, 느린 검색 로그로 어떤 쿼리가 오래 걸리는지 확인하고, CloudTrail로 누가 도메인 설정을 바꿨는지 감사하는 모습을 상정해 보겠습니다. 이 세 가지는 보는 대상이 다릅니다. 지표는 숫자로 된 성능, 로그는 도메인 내부의 활동, CloudTrail은 AWS API 호출 기록입니다. 여기서 본질은 이것입니다. 모니터링은 도구 하나가 아니라, 각자 다른 층을 보는 도구 묶음입니다.

클러스터 메트릭(CloudWatch)

OpenSearch Service가 도메인의 CPU·메모리·디스크 사용률, 검색·인덱싱 처리량, 노드 상태 등을 CloudWatch 지표로 자동 게시해 콘솔과 알람에서 추적하게 하는 기능.

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 도메인을 운영할 때, 노드가 열 개든 스무 개든 우리 눈에 보이는 것은 콘솔의 화면 하나뿐입니다. 각 노드가 CPU를 얼마나 쓰는지, 디스크가 얼마나 남았는지는 화면만 봐서는 알 수 없습니다. 여기서 문제가 되는 지점은 이것입니다. 수치를 눈으로 확인할 방법이 없으면, 용량이 꽉 차거나 노드가 과부하에 걸려도 그 순간까지 모릅니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. 도메인을 구성하는 노드들의 CPU·메모리·디스크 상태를 자동으로 수치화해서 계속 추적하려면 어떻게 해야 할까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 도메인을 만들면 OpenSearch Service가 클러스터의 CPU 사용률, 메모리 사용률, 디스크 여유 공간, 그리고 검색·인덱싱 처리량을 CloudWatch 지표로 자동으로 게시합니다. 우리는 콘솔에서 이 지표를 그래프로 보고, 특정 수치를 넘으면 알림을 받도록 설정할 수 있습니다. 여기서 본질은 이것입니다. 측정과 게시는 서비스가 자동으로 하고, 우리가 할 일은 그것을 보고 알람을 거는 것뿐입니다.

4단계별 동작 과정

  1. 자동 지표 게시OpenSearch Service가 도메인의 CPU·메모리·디스크 사용률, 검색·인덱싱 처리량, 노드 상태를 CloudWatch 지표로 자동 게시합니다.
  2. 콘솔 추적CloudWatch 콘솔과 OpenSearch Service 콘솔에서 해당 지표를 그래프로 확인합니다.
  3. 알람 설정특정 지표가 임계값을 넘으면 알림이 오도록 CloudWatch 알람을 구성해 이상을 즉시 인지합니다.

로그·감사 로그 모니터링

느린 검색·느린 인덱싱·오류·애플리케이션 로그와 보안 감사 로그를 CloudWatch Logs로 게시해 도메인 내부 활동을 추적하고 문제를 진단하는 기능.

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. CloudWatch 지표는 숫자입니다. CPU가 90%다, 처리량이 초당 얼마다 하는 값을 보여주죠. 그런데 숫자는 "느리다"는 사실만 알려주지, "어떤 쿼리가 느린지"는 알려주지 않습니다. 여기서 문제가 되는 지점은 이것입니다. 지표만으로는 도메인 안에서 무슨 일이 일어나는지, 어떤 요청이 오래 걸렸는지, 어떤 인덱싱이 실패했는지 알 수 없습니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. 도메인 내부에서 일어나는 검색·인덱싱·오류·보안 활동의 실제 기록을 남겨서 문제를 진단하려면 어떻게 해야 할까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 어떤 검색 쿼리가 5초나 걸린다고 해보겠습니다. 지표로는 검색이 느려졌다는 것만 보입니다. 그런데 느린 검색 로그(slow search log)를 켜 두면, 그 5초짜리 쿼리가 어떤 문장이었는지가 로그에 남습니다. 여기서 본질은 이것입니다. 로그는 지표가 못 보여주는 "누가, 무엇을, 얼마나 오래"라는 구체적인 기록입니다.

4단계별 동작 과정

  1. 로그 게시 구성느린 검색·느린 인덱싱·오류·애플리케이션 로그를 CloudWatch Logs로 게시하도록 도메인을 설정합니다.
  2. 기록 수집임계값을 넘는 검색과 인덱싱, 발생한 오류, 애플리케이션 활동이 로그 스트림에 쌓입니다.
  3. 진단과 추적CloudWatch Logs에서 로그를 조회해 느린 쿼리와 오류의 원인을 찾고, 보안 감사 로그로 도메인 내부의 접근·변경 활동을 추적합니다.

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 지금까지 본 지표와 로그는 도메인 "안에서" 일어나는 일을 보여줍니다. 그런데 도메인 "자체에" 일어나는 일, 예를 들어 도메인이 생성되거나 삭제되거나, 구성이 바뀌거나, 오류 알림이 발생하는 일은 다른 이야기입니다. 여기서 문제가 되는 지점은 이것입니다. 이런 상태 변경을 우리가 콘솔에 들어가서 일일이 확인해야 한다면, 변경 사실을 놓치기 쉽습니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. 도메인의 상태 변경이 생긴 순간을 자동으로 감지해서, 그에 맞는 작업을 자동으로 실행하려면 어떻게 해야 할까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 도메인 하나가 삭제되는 상황을 보겠습니다. OpenSearch Service는 도메인의 생성·삭제·구성 변경·오류 알림 같은 상태 변경을 Amazon EventBridge 이벤트로 발생시킵니다. 우리는 이 이벤트에 규칙을 걸어 두면, 도메인이 삭제되는 순간 알림을 보내는 워크플로를 자동으로 실행할 수 있습니다. 여기서 본질은 이것입니다. 이벤트는 "일어난 사실"을 알려주는 신호이고, 우리는 그 신호에 반응 규칙을 연결하는 것입니다.

4단계별 동작 과정

  1. 이벤트 발생OpenSearch Service가 도메인의 생성·삭제·구성 변경·오류 알림을 Amazon EventBridge 이벤트로 발생시킵니다.

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 4단계별 동작 과정

  2. 복원력 설계스냅샹 자동화와 재해 복구 구성을 도메인 단위로 설계한다. 데이터 손실 시점(RPO)과 복구 시간(RTO) 기준을 정한다.
  3. 장애 복구 실행장애 발생 시 스냅샷으로 데이터를 복원하거나 재해 복구 구성을 통해 도메인을 재개한다. 데이터가 복원되고 서비스가 정상화되는 것이 마지막 결과다.

Serverless 개요와 비교

클러스터 관리 없이 검색·분석 용량을 자동으로 조정하는 서버리스형 OpenSearch 로, 관리형 도메인과의 차이를 이해하는 출발점

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 관리형 도메인에서는 우리가 클러스터의 크기, 인스턴스 수, 스토리지 용량을 직접 정하고 관리합니다. 그 방식은 예측 가능한 워크로드에서는 잘 동작합니다. 하지만 검색 요청이 늘었다 줄었다 하는 워크로드에서는 문제가 생깁니다. 용량을 넉넉하게 잡아 두면 요청이 적을 때 비용이 낭비되고, 용량을 정확히 맞추면 갑작스러운 요청 증가에서 도메인이 버티지 못합니다. 여기서 문제가 되는 지점은, 클러스터 관리와 용량 예측이 사용자의 몫이라는 것입니다. 우리는 검색 기능을 쓰고 싶은 것이지, 클러스터가 몇 대인지 항상 신경 쓰고 싶은 것이 아닙니다. 바로 여기서 출발합니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. 클러스터를 관리하지 않으면서도 검색과 분석을 그대로 쓸 수는 없을까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. OpenSearch Serverless의 비교 문서에서, 관리형 도메인과 Serverless를 나란히 놓고 보면 차이가 바로 드러납니다. 관리형 도메인은 우리가 클러스터를 만들고 용량을 정하고 운영합니다. Serverless는 컬렉션이라는 단위를 만들면 용량 조정은 서비스가 알아서 합니다. 여기서 본질은 이것입니다. 두 방식 모두 OpenSearch의 검색·분석 기능을 제공하지만, 관리 책임이 어디 있느냐가 갈라지는 지점입니다. 관리형 도메인은 우리가 관리 계층을 다루고, Serverless는 관리 계층을 서비스에 넘깁니다. 이 책임의 이동이 곧 Serverless의 본질입니다.

4단계별 동작 과정

  1. 컬렉션 생성도메인 대신 컬렉션이라는 기본 단위를 만든다. 클러스터 크기나 인스턴스 타입을 지정하지 않는다.
  2. 용량 자동 조정서비스가 요청량을 관찰하며 검색·분석 용량을 자동으로 늘리고 줄인다. 사용자가 용량을 예측하지 않는다.
  3. 기능 비교 적용관리형 도메인의 기능이 Serverless에서 지원되는지 비교 문서로 확인하고, 지원되는 기능은 Serverless 위에서 그대로 쓴다. 결과는 관리 부담 없이 검색·분석을 쓰는 환경이다.

컬렉션과 벡터 검색

Serverless 의 기본 단위인 컬렉션과, 벡터 임베딩을 저장·검색하는 벡터 검색 컬렉션을 만들고 다루는 방법

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 관리형 도메인에서 우리는 인덱스를 만들고 문서를 넣고 검색하는 일을, 인덱스와 샤드 같은 클러스터 개념과 함께 다룹니다. 그런데 Serverless에서는 기본 단위가 도메인이나 인덱스가 아니라 컬렉션입니다. 여기서 문제가 되는 지점은, 기존에 도메인 단위로 생각하던 사고방식을 컬렉션 단위로 바꿔야 한다는 것입니다. 컬렉션이 무엇이고, 그 안에서 벡터 임베딩을 어떻게 저장하고 검색하는지가 서로 이어져 있습니다. 이 연결을 먼저 봐야 합니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. Serverless에서 데이터를 담는 단위인 컬렉션은 무엇이고, 벡터 검색은 거기서 어떻게 동작할까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 벡터 검색 컬렉션을 하나 만든다고 합시다. 우리는 텍스트나 이미지 같은 데이터를 임베딩 모델로 벡터로 변환해서, 그 벡터를 컬렉션 안의 인덱스에 저장합니다. 검색할 때는 질의를 같은 방식으로 벡터로 바꿔서, 저장된 벡터들과의 유사도를 계산해 가까운 결과를 돌려받습니다. 여기서 본질은 이것입니다. 일반 검색이 키워드 일치를 보는 것이라면, 벡터 검색은 의미의 거리를 보는 것입니다. 컬렉션은 이 벡터 데이터를 담는 Serverless의 기본 저장·검색 단위이고, 그 안에서 벡터 유사도 검색이 인덱스 단위로 동작합니다.

4단계별 동작 과정

  1. 컬렉션 생성 및 인덱스 구성벡터 검색을 지원하는 컬렉션을 만들고, 벡터 필드의 차원과 유사도 계산 방식(kNN)을 지정한 인덱스 매핑을 구성한다.
  2. 벡터 저장데이터를 임베딩 모델로 벡터로 변환해 컬렉션 인덱스에 문서로 넣는다. 각 문서가 벡터 필드를 품은 형태가 된다.
  3. 유사도 검색질의를 벡터로 바꿔 저장된 벡터들과 거리를 계산하고, 가장 가까운 결과를 순위로 돌려받는다. 이것이 벡터 검색의 마지막 결과다.

5본질 요약

컬렉션이 Serverless의 기본 단위로서 벡터 임베딩을 저장하고, 질의 벡터와의 유사도 계산으로 의미 기반 검색을 수행하는 것

IAM·데이터 접근 제어·암호화·네트워크 접근·SAML 등 Serverless 컬렉션을 보호하는 보안 체계

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 관리형 도메인에서는 IAM, 데이터 접근 제어, 암호화, 네트워크 접근, SAML 같은 보안 요소를 도메인 단위로 구성합니다. Serverless에서는 이 보안 체계가 그대로 필요합니다. 다만 적용 대상이 컬렉션이라는 점, 그리고 네트워크 접근이 컬렉션에 연결되는 방식이 다릅니다. 여기서 문제가 되는 지점은, 컬렉션은 클러스터가 아니라는 사실입니다. 기존에는 도메인에 VPC나 보안 그룹을 붙였지만, Serverless에서는 데이터 접근 정책과 네트워크 정책을 컬렉션에 연결하는 구조입니다. 보안의 목적은 같지만 적용 단위가 바뀌는 것을 정확히 짚어야 합니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. 클러스터가 없는 Serverless에서 컬렉션의 접근과 데이터는 어떻게 보호할까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 컬렉션 하나에 데이터 접근 정책을 연결한다고 합시다. 그 정책은 어떤 보안 주체가(IAM 역할), 어떤 작업을(검색, 인덱스 쓰기), 어떤 인덱스에 대해 할 수 있는지를 명시합니다. 여기서 본질은 이것입니다. Serverless 보안은 권한을 정책 문서로 표현해서 컬렉션에 붙이는 정책 기반 접근 제어입니다. 암호화는 서비스가 키 관리와 함께 처리하고, 네트워크 접근은 정책으로 통제합니다. IAM과 SAML은 컬렉션에 들어오는 주체와 인증 방식을 정하고, 그 주체가 정책에 따라 데이터에 접근하는 구조입니다.

4단계별 동작 과정

  1. 데이터 접근 정책 구성보안 주체, 허용 작업, 대상 인덱스를 담은 정책을 컬렉션에 연결한다. 권한의 기준이 되는 부여 정책이다.
  2. 네트워크 및 암호화 설정네트워크 접근 정책으로 접근 가능한 경로를 통제하고, 데이터 암호화와 키 관리를 서비스 설정으로 확정한다.
  3. 인증 연동IAM과 SAML로 접근 주체를 인증한다. 인증된 주체가 정책에 부여된 범위 안에서만 컬렉션 데이터에 접근하는 것이 마지막 결과다.

5본질 요약

IAM과 SAML로 주체를 인증하고, 데이터 접근·네트워크 정책을 컬렉션에 연결하며 암호화로 데이터를 보호하는 정책 기반 보안 체계

Serverless 용량·스케일·모니터링

용량 한도 관리와 scale-to-zero 로 비용을 조절하고, CloudWatch·CloudTrail·EventBridge 로 상태를 모니터링하는 방법

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 관리형 도메인에서는 클러스터 크기를 우리가 정하고, 사용량이 줄면 그대로 비용이 남습니다. Serverless는 용량이 자동으로 조정되고 사용하지 않으면 0으로 줄어드는 scale-to-zero를 지원해서, 비용을 사용량에 맞출 수 있습니다. 그런데 여기서 문제가 되는 지점은, 자동 조정이 무한정이라는 뜻이 아니라는 것입니다. 용량에는 한도가 있고, 스케일이 어떻게 움직이는지 그리고 상태가 정상인지는 우리가 모니터링으로 확인해야 합니다. 자동화된 용량 조정 위에 한도 관리와 관측이라는 운영 책임이 남아 있습니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. 용량이 자동으로 조정되는 환경에서 비용과 상태는 어떻게 관리하고 확인할까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 하루 중 검색 요청이 많은 시간대와 적은 시간대가 있는 서비스가 있다고 합시다. Serverless는 요청이 몰리면 검색·분석 용량을 자동으로 늘리고, 조용해지면 줄여서 결국 0까지 내려갑니다. 여기서 본질은 이것입니다. scale-to-zero는 사용량이 없을 때 용량을 0으로 줄여 비용을 절감하는 메커니즘이고, 그 조정은 우리가 정한 한도 안에서 일어납니다. CloudWatch는 지표와 로그로 상태를 보여주고, CloudTrail은 API 호출을 기록하며, EventBridge는 상태 변화에 이벤트로 반응하게 합니다. 자동 조정이 비용을, 모니터링이 가시성을 담당합니다.

4단계별 동작 과정

  1. 용량 한도 관리컬렉션의 검색·분석 용량 한도를 확인하고 필요에 따라 조정한다. 자동 조정이 일어나는 범위가 바로 이 한도다.
  2. 상태 모니터링CloudWatch로 용량과 오류 지표를, CloudTrail로 계정의 API 활동을 확인한다. 조정이 한도 안에서 정상적으로 일어나는지 본다.
  3. 이벤트 대응EventBridge 규칙으로 상태 변화나 임계값 초과를 이벤트로 받아 알림이나 자동 조치를 연결한다. 결과는 사용량에 맞는 비용과 관측 가능한 운영 상태다.

5본질 요약

용량 한도 안에서 scale-to-zero로 비용을 사용량에 맞추고, CloudWatch·CloudTrail·EventBridge로 상태를 관측하고 대응하는 것

Serverless 데이터 수집·스냅샷·ML

컬렉션으로 데이터를 수집하고 스냅샷으로 백업하며 머신러닝·신경 검색을 설정하는 방법

1상대의 출발점 확인

Serverless에서는 이 세 가지가 컬렉션을 대상으로 동작합니다. 여기서 문제가 되는 지점은, 데이터를 실제로 컬렉션에 넣는 방법과, 백업·복원의 방식, 그리고 머신러닝 설정이 각각 다른 진입점을 가진다는 것입니다. 인덱싱은 클라이언트가, 스냅샷은 백업 절차가, ML은 모델 등록과 신경 검색 설정이 담당합니다. 이 셋을 한 흐름으로 이어 봐야 합니다.

2질문 제기

Amazon OpenSearch Ingestion은 소스에서 OpenSearch Service 도메인이나 Serverless 컬렉션으로 데이터를 실시간 수집·변환하는 완전관리형 파이프라인 서비스다.

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 지금까지는 데이터를 넣을 때 클라이언트가 직접 인덱싱 요청을 보내는 방식을 봤습니다. 그 방식은 단건 또는 소량의 데이터에서는 잘 동작합니다. 하지만 로그나 이벤트처럼 끊임없이 흘러드는 대량의 데이터를, 변환까지 포함해서 도메인이나 컬렉션에 밀어 넣어야 한다면 문제가 생깁니다. 여기서 문제가 되는 지점은, 수집 파이프라인을 우리가 직접 만들고 운영해야 한다는 것입니다. 데이터를 받아서, 필요하면 바꾸고, 목적지에 안정적으로 전달하는 그 과정 전체를 직접 관리하는 것은 큰 운영 부담입니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다. 데이터를 받아 변환하고 OpenSearch로 보내는 수집 파이프라인을, 직접 운영하지 않고 쓸 수는 없을까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. 애플리케이션 로그가 계속 쌓이는 상황을 보겠습니다. Amazon OpenSearch Ingestion은 소스에서 데이터를 실시간으로 받아, 파이프라인 안에서 필요에 따라 변환한 뒤, OpenSearch Service 도메인이나 Serverless 컬렉션으로 보냅니다. 여기서 본질은 이것입니다. Ingestion은 실시간 수집·변환·전달을 하나의 완전관리형 파이프라인으로 처리하는 서비스라는 것입니다. 우리가 파이프라인 자체를 운영하지 않기 때문에, 데이터를 받아서 목적지에 넣기까지의 고통을 서비스가 대신 짊어집니다.

4단계별 동작 과정

  1. 파이프라인 정의소스에서 데이터를 받아 변환하고 목적지로 보내는 파이프라인 구성을 정의한다. 이 구성이 수집 작업의 설계도다.
  2. 실시간 수집·변환서비스가 파이프라인을 실행해 소스의 데이터를 실시간으로 받고 필요에 따라 변환한다. 데이터가 흘러드는 동안 형태가 정리된다.
  3. 목적지 전달변환된 데이터를 OpenSearch Service 도메인이나 Serverless 컬렉션으로 전달해 인덱싱한다. 검색 가능한 데이터가 목적지에 쌓이는 것이 마지막 결과다.

파이프라인 생성과 블루프린트

YAML 설정으로 파이프라인을 만들고, 블루프린트는 공통 사용 사례에 맞춰 미리 준비된 파이프라인 구성을 시작점으로 쓰는 템플릿이다.

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. OpenSearch Service에 데이터를 넣으려면 지금까지는 도메인에 인덱스를 만들고, 클라이언트가 데이터를 보내기 전에 인덱스 매핑(mapping, 필드의 형식을 정의하는 규칙)을 먼저 설정하고, 변환이 필요하면 애플리케이션 쪽에서 직접 파이프라인을 구성해야 했습니다. 데이터가 들어오는 경로가 제각각이라서, 데이터가 어디서 오는지에 따라 전처리(preprocessing, 도착한 데이터를 저장 전에 정제·변형하는 작업)를 일일이 따로 구현해야 했죠. 여기서 문제가 되는 지점은 이것입니다. 데이터가 많아질수록 전처리 코드가 애플리케이션과 뒤엉켜서, 데이터 경로 하나를 바꿀 때마다 애플리케이션 전체를 다시 손봐야 한다는 것입니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다 — 데이터를 받아서 저장까지의 모든 처리를, 애플리케이션과 분리된 하나의 독립적인 흐름으로 만들 수는 없을까요?

3구조적 핵심 예시

이거 하나만 딱 보고 가겠습니다. S3 버킷에 로그 파일이 쌓이고, 이 로그를 OpenSearch 도메인에 넣어야 한다고 합시다. 이때 파이프라인(pipeline, 데이터가 소스에서 싱크까지 흐르는 처리 경로)이라는 것을 YAML 설정 파일 하나로 정의합니다. YAML 안에는 세 가지가 들어갑니다. 데이터를 어디서 읽을지(소스, source), 읽은 데이터를 어떻게 가공할지(프로세서, processor), 가공한 결과를 어디에 쓸지(싱크, sink)입니다. 이 설정 파일을 만들면 그 순간부터 데이터는 애플리케이션을 거치지 않고 S3에서 OpenSearch로 바로 흐릅니다. 그리고 이 구성을 처음부터 빈 종이에 쓰는 게 아니라, 블루프린트(blueprint, 공통 사용 사례에 맞춰 미리 준비된 파이프라인 구성 템플릿)를 골라 시작점으로 삼습니다. 여기서 본질은 이것입니다. 파이프라인은 YAML이라는 선언적 설정 하나로 데이터의 전체 여정을 정의하고, 블루프린트는 그 여정의 뼈대를 이미 짜 둔 것입니다.

4단계별 동작 과정

차근차근 따라오시죠. - 블루프린트 선택 — 파이프라인을 만들 때 시작점으로 쓸 블루프린트를 고릅니다. 예를 들어 S3에서 로그를 수집하는 블루프린트는 소스·프로세서·싱크의 기본 뼈대가 이미 갖춰져 있어서, 여기서 필요한 부분만 고치면 됩니다. - YAML 설정 작성 및 검증 — 선택한 구성을 바탕으로 YAML 파일을 완성합니다. 소스는 어디서 읽을지, 프로세서는 어떻게 가공할지, 싱크는 어디에 쓸지를 정확히 쓰고, 설정이 올바른지 파이프라인 검증(pipeline validation, 설정 문법과 구성의 오류를 미리 점검하는 기능)을 통과시킵니다. - 파이프라인 생성과 실행 — 검증을 마친 설정으로 파이프라인을 생성합니다. 생성된 파이프라인이 실행되면서 소스에서 데이터를 읽고, 프로세서를 거쳐 가공하고, 싱크인 OpenSearch 도메인의 인덱스로 넣는 전체 흐름이 하나의 관리 대상으로 동작합니다. 이 파이프라인은 애플리케이션과 완전히 분리되어 있으므로, 이후에는 파이프라인 설정만 고쳐서 데이터 경로를 바꿀 수 있습니다.

DynamoDB의 스트림을 읽는 방법, 인증을 처리하는 방법, 변경을 감지하는 방법은 전부 커넥터가 이미 처리해 줍니다. 이 예시가 보여주는 본질은 이것입니다. 커넥터는 서비스별 연결의 복잡함을 파이프라인 설정 뒤로 숨기고, 사용자는 그저 어떤 커넥터를 쓸지만 고르면 됩니다.

S3, Kafka(MSK·Confluent), DynamoDB, Lambda 등 연결하려는 서비스가 그대로 소스나 싱크(sink, 데이터가 도착하는 곳)로 지정됩니다. - 연결 설정 작성 — 선택한 커넥터에 필요한 연결 정보를 YAML에 씁니다. 예를 들어 S3 커넥터라면 버킷 이름과 읽을 경로를, DynamoDB 커넥터라면 테이블 이름을 넣습니다. 인증과 연결 규약은 커넥터가 대신 처리합니다. - 파이프라인 실행과 데이터 흐름 — 파이프라인이 실행되면 커넥터가 해당 서비스에 연결해 데이터를 읽거나 쓰고, 읽은 데이터는 프로세서를 거쳐 싱크인 OpenSearch 도메인으로 전달됩니다. 이후에는 커넥터의 연결 방식이 아니라 설정에 적힌 연결 정보만 바꾸면 같은 커넥터를 그대로 재사용할 수 있습니다.

MCP 서버와 에이전트 스킬

1상대의 출발점 확인

기존 방식의 동작부터 정확히 보겠습니다. 지금까지 데이터를 넣고, 보고, 머신러닝까지 연결했습니다. 그런데 이 모든 조작에는 한 가지 공통점이 있습니다. 사람이 화면을 열거나 쿼리를 보내야 한다는 것입니다. 에이전트(agent, 사용자 대신 작업을 수행하는 프로그램)가 데이터를 직접 조회하고 분석하려면, 에이전트가 OpenSearch에 접근하는 방법을 따로 구현해야 했습니다. API를 호출하는 코드를 만들어 에이전트에 붙이거나, 에이전트마다 다른 방식으로 OpenSearch를 호출하게 만들면, 에이전트 하나가 바뀔 때마다 그 연결도 함께 바뀌어야 합니다. 여기서 문제가 되는 지점은 이것입니다. 에이전트가 OpenSearch의 데이터를 쓰려면 에이전트와 OpenSearch 사이의 연결을 에이전트마다 따로 구축해야 한다는 것입니다.

2질문 제기

여러분이 여기서 가져야 할 질문은 이것입니다 — 에이전트가 OpenSearch의 데이터를 조회하고 분석할 수 있게 해 주는, 표준화된 연결 창구는 없을까요?

MCP(Model Context Protocol, 에이전트와 도구·데이터를 연결하는 표준 프로토콜) 서버가 OpenSearch에 붙어 있고, 에이전트는 이 서버를 통해 도메인에 접속합니다. 에이전트가 요청하면 MCP 서버가 그 요청에 맞는 OpenSearch 쿼리로 바꿔 실행하고, 결과를 에이전트가 이해하는 형태로 돌려줍니다. 에이전트는 OpenSearch의 내부를 몰라도 데이터를 조회할 수 있고, 추가로 에이전트 스킬(agent skill, 에이전트가 OpenSearch를 다루는 데 쓰는 표준 작업 정의)을 제공받아 분석 작업을 미리 알고 수행합니다. 여기서 본질은 이것입니다. MCP 서버는 에이전트와 OpenSearch 사이의 표준화된 창구이고, 에이전트 스킬은 그 창구에서 쓸 작업 방식을 미리 규정해 둔 것입니다.

4단계별 동작 과정

차근차근 따라오시죠. - MCP 서버 구성 — OpenSearch를 위한 MCP(Model Context Protocol, 에이전트와 데이터·도구를 표준 프로토콜로 연결하는 규약) 서버를 구성합니다. 이 서버가 에이전트와 OpenSearch 도메인 사이의 연결점이 됩니다. - 에이전트와 연결 — 에이전트가 MCP 서버에 연결합니다. 연결된 순간부터 에이전트는 MCP 서버가 노출하는 OpenSearch의 조회·분석 기능을 표준화된 방식으로 호출할 수 있습니다. - 스킬 활용과 분석 — 에이전트가 에이전트 스킬(에이전트가 OpenSearch 데이터를 조회·분석하는 데 쓰는 표준 작업 정의)을 사용해 요청을 처리합니다. 에이전트의 요청은 MCP 서버를 거쳐 OpenSearch 쿼리로 실행되고, 그 결과가 다시 에이전트에게 전달되어 분석에 사용됩니다.

차근차근 따라오시죠. - 저장 계층 분리 — 자주 쓰는 데이터는 고성능 인스턴스에 두고, 오래되어 잘 조회되지 않는 데이터는 UltraWarm 같은 비용 효율적인 저장 계층으로 옮깁니다. 이로써 저장 비용이 줄어듭니다. - 전용 노드 배치 — 클러스터 전체 상태를 관리하는 전용 마스터 노드와, 들어오는 요청을 데이터 노드로 분배하는 전용 코디네이터 노드를 따로 배치합니다. 데이터 노드는 검색과 색인 작업에만 집중하게 됩니다. - 장기 비용 절감 — 안정적으로 계속 운영할 도메인은 Reserved Instance(예약 인스턴스)로 구매해 장기 비용을 낮춥니다. 이로써 성능을 유지하면서 전체 운영 비용이 최적화됩니다.
