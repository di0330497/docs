1부. 서버리스와 Lambda의 기본 개념001

서버리스 컴퓨팅(Serverless Computing)

서버를 직접 빌리지 않고 코드만 올려 실행한다는 발상이 무엇인지

쇼핑몰 이벤트 페이지처럼 하루에 몇 번만 접속이 몰리는 서비스를 만든다면, 서버를 미리 빌려 두는 방식은 손님이 없는 새벽에도 요금을 내게 하고 정작 몰리는 순간에는 서버가 버티지 못하게 합니다. 서버리스 컴퓨팅(Serverless Computing)은 서버를 통째로 빌리지 않고 코드만 올려 두었다가 필요할 때만 실행하는 클라우드 컴퓨팅(Cloud Computing)의 한 방식입니다.

자가용을 사면 타지 않는 날에도 보험과 주차비가 나가지만, 택시를 타면 실제로 탄 거리만큼만 요금을 내는 것과 같습니다. 손님이 손을 흔드는 일이 코드를 깨우는 신호가 되고, 목적지를 말하는 일이 실행할 함수를 지정하는 일이 되며, 기사가 데려다주는 차 안이 코드가 돌아가는 격리된 공간이 됩니다.

회사는 차고나 정비공을 따로 두지 않아도 되고, 손님이 몰리면 택시가 여러 대 불려오듯 같은 코드가 동시에 여러 벌로 실행됩니다. 요금은 차를 세워 둔 시간이 아니라 실제로 달린 거리, 곧 코드가 실행된 시간과 호출된 횟수를 기준으로 매겨집니다.

정리하면 서버리스 컴퓨팅은 서버 운영과 용량 산정을 클라우드 사업자에게 넘기고, 개발자는 사건이 있을 때 실행되는 코드와 그 실행에 따른 비용만 다루는 방식입니다. 그래서 서버가 없다는 말은 서버가 정말 없다는 뜻이 아니라, 서버를 직접 관리하지 않는다는 뜻입니다.

Amazon Lambda 개요

Lambda가 어떤 서비스이고 개발자 대신 무엇을 해주는지

이미지가 올라올 때마다 썸네일을 만드는 작은 작업 하나 때문에 서버 한 대를 띄워 두면, 그 서버의 보안 패치와 장애 감시와 로그 확인까지 개발자가 떠안게 됩니다. Amazon Lambda는 이런 자질구레한 작업을 위해 서버를 준비하지 않아도 되도록, 코드를 맡겨 두면 필요한 순간에 대신 실행해 주는 서비스입니다.

일이 생길 때만 사람을 보내는 파견 사무소를 떠올리면 이해가 쉽습니다. 개발자는 어떤 일이 오면 어떻게 처리하라는 매뉴얼을 사무소에 맡겨 두고, 사무소는 일감이 들어오는 순간에만 직원을 붙여 매뉴얼대로 처리하게 합니다.

직원은 매번 깨끗한 책상에서 일을 시작하고 일이 끝나면 책상을 치우고 돌아가므로, 앞선 일의 흔적이 다음 일에 섞이지 않습니다. 사무소가 건물과 채용과 교육을 책임지므로 개발자는 매뉴얼을 고치는 일에만 집중하면 됩니다.

실제로 Lambda는 코드를 함수(Function) 단위로 등록해 두면 이벤트가 발생할 때마다 대신 실행해 주는 서버리스 컴퓨팅 서비스입니다. 서버 준비와 확장, 운영체제 패치, 로그 수집 같은 일을 서비스가 맡고, 사용자는 실행 횟수와 실행 시간에 대한 요금만 부담합니다.

함수(Function)

Lambda에서 배포하는 실행 단위 하나가 무엇으로 이루어지는지

코드를 파일 서버에 그냥 올려 두면 무엇이 하나의 실행 단위인지 흐려지고, 배포할 때 환경 변수나 권한, 메모리 설정을 빠뜨리기 쉽습니다. Lambda의 함수(Function)는 코드와 그 코드를 실행하는 데 필요한 설정을 한데 묶어, 흩어지지 않는 하나의 배포 단위로 만든 것입니다.

주방에 레시피 카드를 한 장씩 정리해 두는 모습과 비슷합니다. 카드에는 조리법인 코드, 필요한 조리 도구인 런타임(Runtime), 한 번에 만들 수 있는 양인 메모리, 조리를 포기하는 시각인 타임아웃(Timeout)이 함께 적혀 있습니다.

요리가 끝나면 그 카드 한 장에 대한 기록이 남고, 같은 카드를 여러 손님이 동시에 주문하면 주방은 카드마다 별도의 조리대를 준비합니다. 카드를 새로 쓰더라도 이전 카드를 지우지 않고 번호를 붙여 보관하므로, 문제가 생기면 예전 카드로 되돌릴 수 있습니다.

결국 함수는 코드 파일 하나가 아니라, 실행에 필요한 런타임과 권한, 메모리와 타임아웃 같은 설정을 함께 묶은 배포 단위입니다. 이 묶음 단위로 판본을 남기고 트래픽을 나눠 보내기 때문에, 같은 코드를 조금씩 바꾼 여러 판본을 동시에 운영할 수 있습니다.

이벤트 소스(Event Source)

함수를 대신 깨워 주는 사건이 무엇인지

코드가 언제 실행되어야 하는지 개발자가 직접 지켜봐야 한다면, 파일이 올라왔는지 몇 초마다 확인하는 일만으로도 비용과 수고가 계속 쌓입니다. 이벤트 소스(Event Source)는 그렇게 지켜보는 일을 대신 맡아, 무언가 일어난 순간에 함수를 깨워 주는 쪽입니다.

현관에 여러 개의 초인종이 달려 있고, 각 초인종이 울리면 정해진 사람이 문을 열러 가는 구조와 같습니다. 파일이 저장되면 울리는 초인종, 정해진 시각에 울리는 초인종, 대기열(Queue)에 메시지가 쌓이면 울리는 초인종이 각각 다른 함수를 부릅니다.

방문객이 문 앞에서 답을 기다리는지, 택배처럼 물건만 두고 가는지에 따라 함수가 결과를 돌려주는 방식과 그냥 처리하고 끝나는 방식이 갈립니다. 초인종을 개발자가 직접 달지 않고 건물 관리 사무소가 연결해 주는 경우도 있는데, 이것이 Lambda가 이벤트 소스를 자동으로 연결해 주는 경우입니다.

정리하면 이벤트 소스는 함수를 실행시킬 사건을 만들어 내는 쪽이며, 파일 저장소와 메시지 대기열, 스케줄러, HTTP 요청 등이 여기에 해당합니다. 함수는 스스로 돌지 않고 이런 사건에 반응해 깨어난다는 점이 서버리스 실행 모델의 핵심입니다.

핸들러(Handler)

코드가 실제로 실행을 시작하는 진입점이 어디인지

코드 안에 함수가 여러 개 있으면 실행이 어디서 시작되어야 하는지 알기 어렵고, 공통 준비 코드를 요청마다 다시 돌리면 호출이 느려집니다. 핸들러(Handler)는 그 시작 지점을 하나로 못 박아, 실행 환경이 어떤 코드를 먼저 부를지 분명하게 만드는 장치입니다.

식당에 주문이 들어왔을 때 가장 먼저 주문서를 받아 읽는 접수 창구 직원을 떠올리면 됩니다. 직원은 주문서인 이벤트(Event)와 주방 사정을 알려 주는 상황판인 컨텍스트(Context)를 받아, 정해진 순서대로 요리를 지시하고 결과를 돌려줍니다.

주문서를 읽는 이 직원이 누구인지 코드에 이름표로 알려 주는 일이 핸들러 지정입니다. 접수 창구 뒤편의 공통 준비, 곧 라이브러리를 불러오고 연결을 미리 맺는 일은 가게가 문을 열 때 한 번만 하고 주문마다 되풀이하지 않습니다.

핸들러는 함수가 호출되었을 때 실행을 시작하는 진입점(Entry Point)으로, 이벤트와 컨텍스트를 인자로 받아 결과를 반환하는 코드 조각입니다. 언어마다 지정하는 형식이 달라, 파이썬(Python)은 파일 이름과 함수 이름의 조합으로, 자바(Java)는 정해진 인터페이스를 구현한 클래스의 메서드로 가리키는 식입니다.

실행 환경(Execution Environment)

함수가 어떤 격리된 공간에서 돌아가는지

한 함수의 코드가 다른 고객의 데이터를 건드리거나, 서로 다른 라이브러리 버전이 한 공간에서 부딪히면 예측할 수 없는 장애가 생깁니다. 실행 환경(Execution Environment)은 함수마다 격리된 공간을 따로 내주어, 이런 충돌이 남의 실행에 번지지 않게 막습니다.

호텔 객실을 빌리는 것과 비슷합니다. 손님은 예약할 때 정한 크기의 방과 기본 비품만 받고, 방은 다른 손님과 섞이지 않으며, 체크아웃하면 방을 치워 다음 손님을 맞습니다.

방의 크기와 비품은 함수에 지정한 메모리와 런타임이 결정하고, 방이 준비되는 데 걸리는 시간이 첫 호출의 지연, 곧 콜드 스타트(Cold Start)가 됩니다. 한 번 쓰인 방을 바로 다음 손님에게 내주면 준비 시간이 줄어들지만, 앞 손님이 남긴 흔적에 기대는 코드는 예고 없이 깨질 수 있습니다.

실행 환경은 함수가 실행되는 격리된 컨테이너로, 운영체제와 런타임, 함수 코드, 임시 저장 공간이 한 벌씩 들어 있습니다. Lambda는 이 환경을 재사용하므로 전역 변수에 담아 둔 값이 다음 호출에 남을 수 있지만, 그 재사용이 항상 보장되지는 않습니다.

이벤트 객체와 컨텍스트 객체

함수가 받는 두 개의 인자에 각각 무엇이 담기는지

서버리스 함수를 처음 실행하면 코드는 분명히 짰는데 값이 어디서 들어오는지 몰라 손을 놓게 됩니다. 함수에 들어오는 신호를 아무것도 챙기지 않으면 무엇이 요청했는지, 얼마나 걸릴지 알 수 없어 예외 처리도 제대로 못 하게 됩니다.

그래서 AWS Lambda는 함수를 부를 때 두 개의 인자를 함께 건네주는데, 첫째가 이벤트 객체(Event Object)이고 둘째가 컨텍스트 객체(Context Object)입니다. 이벤트 객체는 택배 상자에 붙은 주문서와 같아서 누가 무엇을 요청했는지가 담겨 있습니다. 콘솔에서 시험 실행을 하면 이 상자 안에 간단한 키와 값 몇 개가 들어오고, API Gateway나 S3 같은 서비스가 부르면 그 서비스가 정해 둔 모양의 내용이 들어옵니다. 컨텍스트 객체는 배송 기사에게 붙는 근무표와 같아서 이번 실행의 이름, 남은 시간, 로그를 찍는 도구 같은 것이 들어 있습니다. 코드는 이 두 상자를 열어 보며 요청을 처리하고, 남은 시간을 읽어 오래 걸리는 작업을 미리 줄이기도 합니다.

정리하면 이벤트는 바깥에서 온 요청 내용이고 컨텍스트는 이번 실행에 대한 실행 환경 정보이며, 둘 다 함수의 인자로만 받는다는 점이 핵심입니다.

반환값과 응답 형식

함수가 돌려준 값이 호출한 쪽에서 어떻게 쓰이는지

함수를 불러 놓고 결과를 돌려받지 못하면 호출한 쪽은 성공인지 실패인지 알 수 없어 다음 일을 시작하지 못합니다. Lambda는 함수가 끝날 때 값을 하나 돌려주도록 되어 있고, 그 값이 호출한 쪽에 결과로 전달됩니다.

이 구조는 택배를 보내고 운송장 번호와 배송 결과를 받는 것과 비슷합니다. 함수 코드에서 return 문으로 값을 내보내면 그 값이 응답 본문이 되고, 형식은 부른 쪽이 정한 약속을 따릅니다. 예를 들어 API Gateway가 부르면 상태 코드와 헤더, 본문을 담은 정해진 모양으로 감싸서 돌려주고, 다른 서비스가 직접 부르면 그 값 자체가 결과가 됩니다. 값을 돌려주지 않거나 오류가 나면 호출한 쪽은 실패로 기록하고 재시도 여부를 판단합니다.

결국 반환값은 함수의 출력 그 자체이며, 호출 방식에 맞는 형식을 지키는 일이 안정적인 연결의 출발점입니다.

1부. 서버리스와 Lambda의 기본 개념009

동기 호출과 비동기 호출

호출 방식 두 가지가 결과 전달에서 어떻게 다른지

같은 함수를 불러도 결과를 기다렸다 받는 경우와 그냥 맡기고 잊는 경우가 있는데, 이 차이를 모르면 시간 초과나 중복 실행에 당황하게 됩니다. Lambda는 이 두 가지를 각각 동기 호출(Synchronous Invocation)과 비동기 호출(Asynchronous Invocation)로 나눠 제공합니다.

동기 호출은 은행 창구에서 번호표를 뽑고 결과를 받을 때까지 그 자리에서 기다리는 것과 같습니다. 부른 쪽이 함수의 응답을 그대로 받아 다음 판단에 쓰고, 함수가 오류를 내면 그 오류도 바로 전달됩니다. 비동기 호출은 편지를 우체통에 넣고 돌아서는 것과 같아서, Lambda가 요청을 큐에 넣어 두고 알아서 실행하며 실패하면 정해진 횟수만큼 다시 시도합니다. 그래서 사용자는 결과를 즉시 받지 못하고, 결과가 필요하면 별도의 완료 알림이나 저장된 기록을 확인해야 합니다.

정리하면 동기 호출은 응답을 그 자리에서 받는 방식이고 비동기 호출은 실행을 맡기고 결과를 나중에 확인하는 방식이며, 어떤 서비스가 어떤 방식으로 부르는지가 동작을 좌우합니다.

Lambda의 과금 구조

무엇을 얼마나 썼는지로 요금이 매겨지는지

함수를 몇 개 만들었는지가 아니라 실제로 얼마나 썼는지로 요금이 나오면 예산을 세우기 쉬워집니다. Lambda의 과금 구조가 바로 그렇게 되어 있어서, 요청 횟수와 실행 시간이라는 두 가지를 기준으로 비용이 계산됩니다.

이 방식은 택시 요금과 비슷합니다. 기본 요금에 해당하는 요청 수가 있고, 거기에 몇 초 동안 달렸는지를 곱해 요금이 붙습니다. 실행 시간은 함수가 시작해 끝날 때까지의 밀리초 단위로 재고, 메모리를 많이 잡을수록 같은 시간이라도 단가가 올라갑니다. 함수가 놀고 있을 때는 요금이 붙지 않지만, 호출 한 번이 아주 짧아도 최소 과금 단위가 적용됩니다.

결국 요금은 호출 횟수와 실행 시간, 그리고 할당한 메모리 크기로 결정되므로 이 세 가지를 줄이는 것이 비용 절감의 핵심입니다.

화면 설명만 읽고는 어디를 눌러야 할지 몰라 첫 함수를 만들지 못하는 경우가 많습니다. AWS 콘솔은 이 첫걸음을 위해 함수 생성 화면과 시험 실행 기능을 한곳에 모아 두었습니다.

런타임(Runtime) 선택

어떤 언어와 버전으로 코드를 돌릴지 고르는 기준

코드를 짜 놓고도 어떤 언어와 버전에서 돌아갈지 정하지 않으면 실행 자체를 시작할 수 없습니다. Lambda는 함수마다 실행 환경인 런타임(Runtime)을 고르게 해 두었고, 이 선택이 코드가 쓸 수 있는 기능과 동작을 결정합니다.

런타임은 식당의 주방 설비와 비슷합니다. 어떤 요리를 할지 정하면 그에 맞는 오븐과 도구가 갖춰지고, 주방이 바뀌면 같은 조리법이라도 손질 방식이 달라집니다. 콘솔에서 언어를 고르면 그 언어의 실행 파일과 기본 라이브러리가 준비된 환경이 함께 만들어집니다. 버전은 지원 기간이 정해져 있어 오래된 버전은 언젠가 실행되지 않으므로, 새로 만들 때는 현재 지원되는 버전을 고르는 편이 안전합니다. 라이브러리 설치나 실행 시간 같은 조건도 언어에 따라 다르므로 팀이 이미 쓰는 언어를 기준으로 정하는 것이 유지에 유리합니다.

결국 런타임은 함수가 돌아가는 언어와 버전의 실행 환경이며, 지원 기간과 팀의 기술 선택을 함께 보고 정하는 것이 핵심입니다.

런타임 지원 수명 주기

런타임 버전이 언제 지원 종료되는지와 미리 옮기는 방법

쓰던 런타임 버전이 어느 날 지원 종료되면 함수를 새로 만들 수도 없고 고칠 수도 없게 되며 보안 패치도 더 이상 들어오지 않습니다. 그래서 AWS는 각 런타임에 지원 기간과 종료 일정을 미리 공지하는 런타임 지원 수명 주기(runtime support lifecycle)를 두고, 사용자가 그 전에 상위 버전으로 옮기도록 안내합니다. 이는 서버를 직접 관리하지 않고 코드만 올려 실행하는 Lambda의 실행 환경 위에서, 언어별 실행기가 언제까지 유지되는지를 정한 일정표라고 볼 수 있습니다.

아파트 단지의 노후 승강기를 떠올려 보면 이해가 쉽습니다. 승강기 모델이 단종되면 부품을 더는 구할 수 없어 고장이 나도 고칠 수 없으므로, 관리사무소는 단종 예고가 나온 시점부터 교체 계획을 세웁니다.

Lambda도 마찬가지로 각 런타임에 지원 종료 예정일이 공지되고, 그 날짜가 지나면 새 함수 생성과 코드 업데이트가 막히며 기존 함수도 결국 실행되지 않습니다.

그래서 미리 코드와 라이브러리가 새 버전에서도 도는지 확인하고, 시험용 함수를 새 런타임으로 하나 만들어 검증한 뒤 옮기는 것이 안전합니다.

정리하면 런타임 지원 수명 주기는 언어 실행기의 유지보수 일정표이며, 종료 공지가 나오면 새 버전에서의 동작을 미리 시험해 두는 것이 핵심입니다.

배포 패키지와 크기 제한

코드와 라이브러리를 어떤 형태로 묶어 올리는지

함수 코드를 서버에 올릴 때 아무렇게나 파일을 밀어 넣으면 실행에 필요한 라이브러리가 빠져 오류가 나고, 반대로 필요한 것을 모두 넣으면 용량 제한에 걸려 배포가 막힙니다. 그래서 Lambda는 코드와 의존 파일을 하나의 압축 묶음인 배포 패키지(deployment package)로 만들어 올리게 하고, 압축한 파일과 압축을 푼 뒤의 크기에 각각 상한을 둡니다.

택배를 보낼 때 상자 크기와 무게에 한도가 있는 것과 비슷합니다. 물건을 상자에 담고 완충재로 감싸 테이프로 봉인하듯, 코드 파일과 라이브러리를 폴더 구조 그대로 압축해 하나의 상자로 만듭니다.

택배사가 상자 크기와 무게를 따로 재듯 Lambda도 압축된 파일 크기와 풀었을 때의 크기를 각각 확인하고, 한도를 넘으면 접수를 받지 않습니다.

그래서 쓰지 않는 파일을 빼고 큰 라이브러리는 함수 밖으로 덜어내는 식으로 상자를 가볍게 만듭니다.

정리하면 배포 패키지는 코드와 의존성을 담은 하나의 압축 묶음이며, 압축 전후의 크기 제한을 함께 고려해 최대한 가볍게 유지하는 것이 중요합니다.

2부. 첫 함수 만들기와 배포 단위015

의존성 패키징

외부 라이브러리를 함께 넣을 때 무엇을 조심해야 하는지

내 컴퓨터에서는 잘 돌던 함수가 배포 후에 모듈을 찾을 수 없다는 오류로 죽는 일이 흔한데, 실행 환경에 그 라이브러리가 없기 때문입니다. 그래서 외부 라이브러리를 코드와 함께 패키지에 넣는 의존성 패키징(dependency packaging)이 필요하고, 여기에는 몇 가지 주의점이 따릅니다.

이사할 때 짐을 싸는 일과 같습니다. 새 집에 없는 물건은 반드시 챙겨야 하고, 원래 집에 있던 가구를 또 사 가면 짐만 무거워지며, 문 크기에 맞지 않는 큰 가구는 들여놓을 수 없습니다.

Lambda도 실행 환경에 기본으로 들어 있는 라이브러리가 있어 그것까지 넣으면 패키지만 커지고, 내 컴퓨터에서 빌드한 파일이 실행 환경의 운영체제와 맞지 않으면 아예 동작하지 않습니다. 또 여러 라이브러리가 서로 다른 버전을 요구하면 충돌이 나므로 버전을 고정하고 한 곳에서 설치해 그 목록을 남겨야 합니다.

플랫폼에 맞는 파일을 설치하려면 공식 문서의 안내대로 리눅스 환경에서 설치하거나 지정된 옵션을 쓰는 것이 좋습니다.

정리하면 의존성 패키징은 실행 환경에 없는 라이브러리를 코드와 함께 넣되, 중복과 플랫폼 불일치와 버전 충돌을 피하는 작업입니다.

← 이전배포 패키지와 크기 제한다음 →계층(Layer)

2부. 첫 함수 만들기와 배포 단위016

계층(Layer)

공통 라이브러리를 함수 밖으로 빼서 재사용하는 방법

함수를 여러 개 만들다 보면 같은 라이브러리를 모든 패키지에 똑같이 넣게 되어, 하나를 고칠 때마다 여러 함수를 다시 배포해야 합니다. 그래서 공통 라이브러리를 함수 밖으로 분리해 여러 함수가 함께 쓰는 계층(Layer)이라는 구조를 둡니다.

아파트 각 세대가 똑같은 청소기를 한 대씩 사 두는 대신 지하 공용 창고에 함께 두고 필요할 때 꺼내 쓰는 것과 같습니다. 세대마다 사면 돈과 공간이 낭비되고 고장 날 때마다 집집이 바꿔야 하지만, 공용 창고에 두면 한 번 바꾸는 것으로 모두가 새것을 씁니다.

Lambda에서 계층은 라이브러리를 담은 압축 묶음으로, 함수에 붙이면 실행 시점에 함수의 폴더 옆에 펼쳐져 함께 로드됩니다. 함수 패키지에는 자기 코드만 남기고 여러 함수가 같은 계층을 참조하도록 붙이면 배포 크기도 줄고 수정도 한 곳에서 끝납니다.

정리하면 계층은 공통 라이브러리를 함수 밖에 두고 여러 함수가 공유하게 하는 구조로, 패키지를 가볍게 하고 중복 배포를 없애는 수단입니다.

2부. 첫 함수 만들기와 배포 단위017

컨테이너 이미지로 배포

익숙한 도커 이미지로 Lambda를 올리는 방식

로컬에서 도커로 잘 돌던 프로그램을 Lambda로 옮기면 라이브러리 버전과 실행 환경 차이 때문에 다시 손봐야 하는 경우가 많습니다. 그래서 익숙한 도커 이미지 그대로 Lambda를 배포하는 컨테이너 이미지 배포 방식이 있으며, 이는 Lambda가 지원하는 배포 형태 가운데 하나입니다.

이삿짐을 하나씩 들고 가는 대신 집 안 살림을 통째로 컨테이너에 담아 옮기는 것과 비슷합니다. 짐을 싸는 방식과 순서를 미리 정해 두면 새 집에서 그대로 꺼내 쓰면 되고, 집집마다 짐을 다시 고를 필요가 없습니다.

Lambda에서도 운영체제 도구와 라이브러리까지 포함한 이미지를 만들어 두면, 실행 환경이 그 이미지를 그대로 받아 띄우므로 로컬과 같은 환경이 재현됩니다. 다만 이미지 자체가 커지면 함수가 처음 뜨는 데 걸리는 시간이 길어질 수 있어, 필요한 것만 담아 이미지를 가볍게 유지하는 것이 좋습니다.

정리하면 컨테이너 이미지 배포는 코드와 실행 환경을 한 덩어리로 포장해 올리는 방식으로, 환경 차이를 줄이는 대신 이미지 크기 관리가 관건입니다.

2부. 첫 함수 만들기와 배포 단위018

환경 변수(Environment Variables)

코드 밖에서 설정값을 주입하는 방법과 주의점

데이터베이스 주소나 API 키 같은 값을 코드에 직접 적어 두면, 값을 바꿀 때마다 코드를 고쳐 다시 배포해야 하고 코드를 보는 사람 누구나 그 값을 볼 수 있습니다. 그래서 이런 설정값을 코드 밖에 두고 실행할 때 주입하는 환경 변수(environment variables)를 씁니다.

식당에서 요리법은 그대로 두고 가격표만 벽에서 바꿔 끼우는 것과 같습니다. 요리사가 쓰는 조리 순서는 조리법에 있고, 오늘의 가격이나 영업시간처럼 자주 바뀌는 값은 벽의 판에 적어 두면 판만 갈면 됩니다.

Lambda에서 환경 변수는 함수 설정에 키와 값의 쌍으로 저장되고, 함수가 실행될 때 코드가 읽어 갈 수 있는 값으로 전달됩니다. 다만 이 값은 함수 설정을 볼 권한이 있는 사람에게 그대로 보이므로, 비밀번호나 키처럼 민감한 값은 별도의 비밀 관리 서비스에 두고 그 이름만 환경 변수로 넘기는 편이 안전합니다.

값을 바꾼 뒤에는 함수가 새 설정을 읽도록 반영되는 시점이 있으므로 바로 시험해 확인하는 것이 좋습니다.

정리하면 환경 변수는 코드 수정 없이 설정값을 바꾸게 해 주는 외부 주입 통로이며, 편리한 만큼 민감한 값은 따로 보관해야 합니다.

2부. 첫 함수 만들기와 배포 단위019

함수 버전(Version)

배포한 코드를 고정된 번호로 남기는 이유

배포한 코드를 같은 자리에 계속 덮어쓰면, 어제 잘 돌던 동작이 오늘 갑자기 달라져도 어느 시점의 코드가 문제였는지 확인할 방법이 없습니다. Amazon Lambda의 버전(Version)은 배포한 코드를 고정된 번호로 남겨 이 곤란을 해결하는 장치입니다.

버전은 계약서에 도장을 찍어 확정본을 만드는 일과 같습니다. 초안을 몇 번이고 고쳐도 도장이 찍힌 확정본의 내용은 절대 바뀌지 않고, 새로 고친 내용은 새 확정본으로만 추가됩니다.

Lambda에서도 함수를 게시(publish)하면 그 순간의 코드와 설정이 1, 2, 3 같은 번호로 고정되고, 이후에 코드를 고쳐도 이미 만들어진 번호의 내용은 그대로 남습니다. 문제가 생기면 예전 번호를 다시 가리키기만 하면 되고, 번호가 붙기 전의 작업 중인 최신 상태는 $LATEST 라는 이름으로 계속 바뀝니다.

정리하면 버전은 배포 시점의 코드와 설정을 불변 스냅샷(immutable snapshot)으로 떠서 번호를 매겨 두는 장치이며, 되돌리기와 추적의 기준점이 됩니다.

2부. 첫 함수 만들기와 배포 단위020

별칭(Alias)

버전을 가리키는 이름표로 배포 대상을 바꾸는 방법

버전 번호를 호출하는 쪽이 직접 들고 있으면, 새 버전을 낼 때마다 그 함수를 부르는 모든 시스템을 함께 고쳐야 합니다. 별칭(Alias)은 버전을 가리키는 이름표를 따로 두어 이런 결합을 끊어 줍니다.

별칭은 가게의 메뉴판에 붙은 이름과 같습니다. 손님은 메뉴판의 이름만 보고 주문하고, 주방이 재료를 바꾸면 같은 이름이 다른 요리를 가리키게 됩니다.

Lambda에서도 호출하는 쪽은 prod나 dev 같은 별칭 이름만 쓰고, 그 별칭이 몇 번 버전을 가리킬지는 배포하는 사람이 바꿉니다. 그래서 prod 별칭을 3번에서 5번으로 옮기면 호출 코드는 한 줄도 고치지 않은 채 새 코드로 전환됩니다. 별칭마다 가중치(weight)를 주어 트래픽의 일부만 새 버전으로 보내는 단계적 배포도 할 수 있습니다.

결국 별칭은 버전 번호와 호출자 사이를 떼어 주는 이동 가능한 포인터로, 배포 대상 교체를 호출하는 쪽 몰래 처리하는 이름표입니다.

실행 역할(Execution Role)

함수가 다른 AWS 서비스를 쓰려면 어떤 권한이 필요한지

함수 코드가 저장소에서 파일을 읽거나 데이터베이스에 쓰려고 하면, 그 함수가 무슨 권한으로 그 일을 하는지 먼저 정해져 있어야 합니다. 실행 역할(Execution Role)은 함수가 실행되는 동안 맡는 권한의 주체입니다.

이것은 회사 출입증과 같습니다. 사람 개인이 아니라 맡은 업무에 출입증을 발급하고, 그 출입증 뒤에 열 수 있는 문 목록이 붙어 있습니다.

Lambda에서는 함수를 만들 때 IAM 역할(Role)을 하나 지정하고, 그 역할에 붙은 정책(Policy)이 함수가 부를 수 있는 AWS API를 정합니다. 함수를 실행할 때 런타임이 이 역할의 임시 자격 증명을 넣어 주므로, 코드는 자기 열쇠를 직접 들고 있지 않습니다. 역할이 허용하지 않은 호출은 코드가 아무리 잘 짜여 있어도 거부됩니다.

즉 실행 역할은 함수에 붙는 신분증이자 권한의 범위이며, 그 함수가 실제로 무엇에 손댈 수 있는지를 결정합니다.

3부. 권한과 보안022

최소 권한 정책 설계

필요한 권한만 좁게 주는 방법

편하다고 관리자 권한을 통째로 주면, 코드에 작은 실수가 생겼을 때 관계없는 리소스까지 지워질 수 있습니다. 최소 권한(least privilege) 설계는 필요한 동작과 대상만 좁게 허용하는 방식입니다.

사무실 열쇠를 나눠 주는 상황을 생각하면 이해가 쉽습니다. 모든 방 열쇠를 한 꾸러미로 주는 대신, 실제로 드나드는 방의 열쇠만 골라 주는 것입니다.

IAM 정책에서도 Action에는 실제로 쓰는 API만 적고, Resource에는 그 함수가 다루는 특정 버킷이나 테이블의 ARN만 적습니다. 와일드카드(*)를 습관적으로 붙이지 않고, 조건(Condition)을 붙여 호출 출처나 요청자까지 제한할 수 있습니다. 처음부터 딱 맞추기는 어려우므로 실제 호출 기록을 살펴 쓰이지 않는 권한을 걷어 내는 식으로 좁혀 갑니다.

결국 최소 권한 정책은 동작과 대상과 조건이라는 세 축을 좁혀, 사고가 나더라도 피해 범위를 그 함수의 업무 안에 가두는 설계입니다.

3부. 권한과 보안023

리소스 기반 정책

함수 쪽에 붙여 누가 호출할 수 있는지 정하는 방법

다른 계정의 시스템이 내 함수를 호출해야 할 때, 호출하는 쪽 계정에 권한을 주는 것만으로는 충분하지 않은 경우가 있습니다. 리소스 기반 정책(resource-based policy)은 함수 쪽에 누가 이 함수를 호출할 수 있는지를 적어 두는 방식입니다.

이는 건물 로비에 붙은 방문 허용 명단과 같습니다. 경비실이 아니라 건물 쪽에 명단이 있고, 명단에 오른 사람만 들어올 수 있습니다.

Lambda에서는 함수에 붙는 정책 문서에 Principal로 누가, Action으로 무엇을, Resource로 어느 함수인지를 적습니다. 이렇게 하면 상대 계정에 함수 호출 권한을 미리 만들어 두지 않아도 되고, 허용 범위는 함수를 소유한 쪽이 직접 관리합니다. API Gateway나 다른 계정의 이벤트가 함수를 부를 때도 이 정책이 근거가 됩니다.

정리하면 리소스 기반 정책은 권한을 가진 쪽이 아니라 권한을 받는 자원에 붙여, 호출 허용 여부를 자원 소유자가 통제하게 하는 장치입니다.

3부. 권한과 보안024

함수 안에서의 자격 증명

코드가 AWS 서비스를 호출할 때 쓰는 임시 자격 증명의 정체

코드 안에 액세스 키를 적어 두면 그 키가 유출되는 순간 계정 전체가 위험해집니다. Lambda는 코드가 AWS 서비스를 부를 때 임시 자격 증명(temporary credentials)을 자동으로 채워 주어 이 문제를 피합니다.

이것은 하루짜리 출입증과 같습니다. 정문에서 신분을 확인하고 그날만 유효한 카드를 받으며, 다음 날이면 같은 카드로는 들어갈 수 없습니다.

함수를 실행할 때 런타임이 실행 역할로부터 액세스 키와 비밀 키와 세션 토큰을 받아 환경 변수 형태로 넣어 주고, AWS SDK가 그 값을 읽어 요청에 서명합니다. 이 자격 증명은 만료 시간이 있어 오래 남지 않고, 함수 인스턴스가 재사용되면 갱신됩니다. 그래서 코드에 키를 하드코딩하지 말고 SDK의 기본 자격 증명 체인을 그대로 쓰는 것이 권장됩니다.

즉 함수 안의 자격 증명은 실행 역할에서 파생된 단기 임시 키이며, 비밀을 코드에 두지 않아도 되게 만드는 구조입니다.

← 이전리소스 기반 정책다음 →시크릿과 암호화

3부. 권한과 보안025

시크릿과 암호화

비밀번호 같은 값을 안전하게 보관하고 꺼내 쓰는 방법

온라인 쇼핑몰을 운영하는데 결제 시스템에 접속하려면 비밀번호가 필요하다고 해 보겠습니다. 그런데 이 비밀번호를 소스 코드에 그대로 적어 두면 코드가 저장소에 올라가는 순간 함께 새어 나가고, 비밀번호를 바꿀 때마다 코드를 고쳐 다시 배포해야 합니다.

이때 쓰는 것이 시크릿(secret) 관리와 암호화입니다. 회사에 하나뿐인 금고가 있다고 생각해 보십시오. 귀중품은 금고 안에 넣고, 금고 자체는 두꺼운 철문과 잠금장치로 보호하며, 꺼낼 수 있는 사람은 출입 카드를 가진 직원으로 제한합니다.

AWS에서는 Secrets Manager나 Parameter Store가 이 금고 역할을 하고, KMS(키 관리 서비스)가 금고를 잠그는 열쇠를 맡으며, 함수에 붙인 실행 역할(execution role)이 출입 카드가 됩니다. 함수는 시작할 때 금고에서 값을 꺼내 쓰고, 관리자는 정해진 주기에 따라 비밀번호를 새것으로 바꿔 넣습니다.

정리하면 시크릿 관리는 비밀번호나 API 키 같은 값을 코드와 분리해 암호화된 저장소에 두는 구조입니다. 권한을 가진 함수만 실행 시점에 그 값을 꺼내 쓰므로, 값이 바뀌어도 코드는 건드리지 않습니다.

3부. 권한과 보안026

VPC 연결

함수를 사설 네트워크 안에 넣는 설정과 그 영향

사내 데이터베이스는 인터넷에서 직접 닿지 않는 사설망 안에 있습니다. 함수를 기본 설정 그대로 두면 그 사설망 밖에 있어서 데이터베이스에 연결할 수 없고, 그렇다고 데이터베이스를 인터넷에 노출시키는 것은 훨씬 위험한 선택입니다.

그래서 함수를 가상 사설 네트워크인 VPC(Virtual Private Cloud) 안으로 옮겨 넣습니다. 아파트 단지에 비유하면 VPC는 단지 전체, 서브넷은 각 동과 층, 보안 그룹은 경비실의 출입 명단에 해당합니다. 함수가 단지에 입주하려면 세대 하나를 배정받아야 하는데, 실제로는 네트워크 인터페이스(ENI)가 그 세대 역할을 합니다.

대신 단지 밖으로 나가려면 정문인 NAT 게이트웨이를 거쳐야 하고, 입주 절차 때문에 함수가 처음 뜰 때 시간이 조금 더 걸리며 단지 안의 주소도 소모됩니다.

결국 VPC 연결은 함수를 사설 서브넷에 넣어 사내 자원과 같은 네트워크에 두는 설정입니다. 그 대가로 인터넷으로 나가는 경로와 시작 시간, 주소 개수를 함께 설계해야 합니다.

3부. 권한과 보안027

VPC 엔드포인트

인터넷을 거치지 않고 AWS 서비스를 부르는 경로

함수를 사설망 안에 넣었더니 이번에는 파일 저장소인 S3에 파일을 쓰려다 막히는 상황이 생깁니다. 인터넷으로 나가려면 NAT 게이트웨이를 거쳐야 하는데, 트래픽 비용이 붙고 경로도 한 단계 늘어납니다.

이때 담벼락에 전용 창구를 내는 것이 VPC 엔드포인트(VPC endpoint)입니다. 아파트 단지에서 택배를 받으려고 정문을 나가 도로를 돌아오는 대신, 단지 담벼락에 택배 보관함을 붙여 두는 것과 같습니다. 게이트웨이 엔드포인트는 단지 안내판에 "이 주소는 이 창구로" 한 줄을 적어 두는 방식이라 S3와 DynamoDB에 주로 쓰이고, 인터페이스 엔드포인트는 단지 안에 작은 접수처를 실제로 세우는 방식이라 대부분의 AWS 서비스 호출에 쓸 수 있습니다.

창구를 지나면 정문을 거치지 않으므로 인터넷도 NAT도 필요 없고, 누가 어느 창구를 쓸 수 있는지는 창구 쪽 정책으로 따로 통제합니다.

정리하면 VPC 엔드포인트는 사설망 안에서 AWS 서비스로 통하는 지름길입니다. 인터넷을 거치지 않고 서비스를 부르게 해 주어, 보안과 비용을 동시에 챙길 수 있습니다.

3부. 권한과 보안028

교차 계정 호출

다른 계정의 함수나 자원을 부를 때 필요한 설정

회사가 계정을 여러 개로 나눠 쓰면, 결제 계정의 함수가 정산 계정의 함수나 저장소를 불러야 하는 일이 생깁니다. 그런데 계정은 서로 격리되어 있어서 아무 설정 없이 부르면 권한이 없다는 오류만 돌아옵니다.

이때 필요한 것이 교차 계정(cross-account) 호출 설정입니다. 다른 회사 사옥에 들어가려면 방문증이 필요한 것과 같습니다. 부르는 쪽은 자기 계정에서 역할을 하나 맡아 임시 자격 증명을 받고, 불리는 쪽은 자기 자원에 "이 계정의 이 역할은 들어와도 된다"는 신뢰 정책을 적어 둡니다.

두 장의 서류가 서로 맞아야 문이 열리며, 들어간 뒤에 할 수 있는 일은 다시 권한 정책으로 좁혀집니다.

결국 교차 계정 호출은 부르는 쪽의 실행 역할과 불리는 쪽의 자원 정책을 짝지어 권한을 주는 구조입니다. 한쪽만 설정해서는 동작하지 않는다는 점이 핵심입니다.

3부. 권한과 보안029

코드 서명(Code Signing)

서명된 코드만 배포되게 막는 방법

배포 파이프라인이 뚫리거나 누군가 몰래 함수 코드를 바꿔 올리면, 겉으로는 정상 동작하는 것처럼 보이면서 내부 정보를 빼 가는 코드가 돌아갈 수 있습니다. 배포 권한을 좁히는 것만으로는 이런 변조를 알아채기 어렵습니다.

그래서 서명된 코드만 배포되게 막는 코드 서명(Code Signing)을 씁니다. 회사에서 결재 도장이 찍힌 공문만 접수하는 것과 같습니다.

코드를 올리는 사람은 서명 프로필(signing profile)로 코드를 감싸 서명을 만들고, 함수 쪽에는 신뢰하는 서명자 목록을 등록해 둡니다. 함수는 배포 순간 서명을 확인해 목록에 없거나 서명이 깨졌으면 배포를 거부합니다. 서명 키는 외부에 노출되지 않게 보관하고, 규칙을 어긴 배포는 알림으로 남깁니다.

정리하면 코드 서명은 코드에 붙은 서명과 미리 신뢰한 서명자를 대조해, 검증을 통과한 코드만 함수에 올리는 장치입니다. 권한 관리가 "누가 올릴 수 있는가"를 본다면, 이 장치는 "무엇이 올라왔는가"를 봅니다.

감사와 추적

누가 언제 함수 설정을 바꿨는지 남기는 방법

어느 날 함수 설정이 바뀌어 장애가 났는데, 누가 언제 무엇을 바꿨는지 아무도 기억하지 못하는 상황이 생길 수 있습니다. 기록이 없으면 원인을 찾는 데만 몇 시간이 걸리고, 같은 일이 다시 일어나도 막을 방법이 없습니다.

이때 쓰는 것이 감사와 추적입니다. 건물에 출입 기록부와 폐쇄회로 텔레비전을 함께 두는 것과 같습니다. AWS에서는 CloudTrail이 누가 어떤 API를 언제 호출했는지 기록하는 출입 기록부가 되고, CloudWatch Logs가 함수가 실행되며 남긴 로그를 모으며, AWS Config가 설정이 언제 어떻게 달라졌는지 대장처럼 남깁니다.

기록은 별도 저장소에 보관해 지워지지 않게 하고, 정해 둔 규칙을 벗어난 변경은 알림으로 받습니다.

정리하면 감사와 추적은 API 호출 기록과 로그, 설정 변경 이력을 남겨 두는 체계입니다. 문제가 생겼을 때 원인을 되짚고 재발을 막는 근거가 됩니다.

API Gateway 연동

HTTP 요청을 받아 함수를 실행하는 가장 흔한 구성

직원 수십 명이 함께 쓰는 사내 시스템을 만들었는데, 각자 만든 기능마다 주소가 제각각이고 누가 얼마나 불렀는지 알 길이 없다면 곧 관리가 불가능해집니다. 이런 난잡함을 정리하기 위해 요청을 한 곳에서 접수해 정해진 함수로 넘겨 주는 관문이 필요하고, 그 역할을 하는 것이 Amazon API Gateway입니다.

이를 회사 건물 정문의 안내데스크에 비유할 수 있습니다. 방문객은 안내데스크 한 곳에만 이름과 용건을 말하고, 데스크 직원은 그 내용을 확인한 뒤 해당 부서로 연결해 줍니다. Lambda 함수는 각 부서의 담당자처럼 자기 방에 앉아 있고, 안내데스크가 부르면 그때 일을 시작하며, 방문 기록과 명단 관리도 데스크가 한꺼번에 맡습니다.

즉 HTTP 요청을 받는 주소(엔드포인트)를 정하고, 인증과 호출량 제한을 통과한 요청만 함수에게 전달하는 구조입니다.

정리하면 API Gateway는 클라이언트의 HTTP 요청을 규격에 맞게 접수해 Lambda 함수를 호출하고 결과를 되돌려 주는 관리형 진입점이며, 함수 앞에 세우는 표준 창구 역할을 합니다.

4부. 이벤트 소스 연동032

함수 URL(Function URL)

API Gateway 없이 HTTPS 주소로 바로 호출하는 방법

간단한 테스트용 함수 하나를 인터넷에 노출하려는데 API Gateway를 붙이자 권한 설정과 단계 배포 같은 준비가 줄줄이 따라붙었고, 요청이 거의 없는 도구에 그 절차와 비용은 부담이었습니다. 그래서 함수 자체에 HTTPS 주소를 하나 붙여 그 주소로 바로 부를 수 있게 만든 기능이 함수 URL(Function URL)입니다.

이를 사무실 정문의 안내데스크 대신 옆문에 달린 벨로 비유할 수 있습니다. 정식 방문객은 정문 데스크를 거치지만, 직원끼리 잠깐 부를 때는 옆문 벨을 한 번 누르면 됩니다.

함수를 만들 때 이 벨을 달아 둘지 정하고, 달아 두면 고유한 주소가 함께 발급되며, 부르는 쪽은 그 주소로 HTTPS 요청을 보내기만 하면 됩니다. 다만 문이 하나뿐이라 데스크가 해 주던 명단 확인이나 호출량 조절 같은 일은 직접 챙겨야 합니다.

정리하면 함수 URL은 API Gateway 없이 Lambda 함수에 부여되는 전용 HTTPS 엔드포인트로, 간단한 호출에는 편하지만 부가 기능은 직접 구성해야 합니다.

S3 이벤트 알림

파일이 올라오거나 지워질 때 함수를 깨우는 방법

쇼핑몰에 상품 사진이 하루에도 수천 장 올라오는데, 누군가가 주기적으로 폴더를 열어 새 파일이 있는지 확인하는 방식이라면 대부분의 확인은 헛일이고 정작 새 사진은 한참 뒤에 처리됩니다. 파일이 실제로 올라오는 그 순간에만 일이 시작되면 좋겠다는 요구에서 나온 기능이 S3 이벤트 알림(Event Notification)입니다.

이를 아파트 택배 보관함에 비유할 수 있습니다. 보관함에 택배가 들어가거나 꺼내지는 사건이 일어나면 관리 앱이 곧바로 알림을 보내 주고, 집에 있던 사람은 그 알림을 받고서야 나가서 물건을 찾습니다.

S3 버킷이 보관함이라면 객체가 생성되거나 삭제되는 일이 곧 사건이고, 버킷에 알림 규칙을 걸어 두면 그 사건이 발생할 때 Lambda 함수가 자동으로 실행됩니다. 함수는 전달받은 버킷 이름과 객체 키를 보고 필요한 파일만 골라 처리합니다.

정리하면 S3 이벤트 알림은 버킷에서 객체 생성·삭제 같은 이벤트가 발생할 때 Lambda를 자동 호출하는 구성으로, 주기적 확인 없이 사건이 생긴 순간에만 반응하게 만드는 장치입니다.

4부. 이벤트 소스 연동034

SQS 트리거

대기열에 쌓인 메시지를 함수가 가져가 처리하는 방식

이벤트가 한꺼번에 밀려오면 함수가 그 수만큼 동시에 실행되다 한도를 넘겨 실패하고, 실패한 요청은 그대로 사라질 수 있습니다. 들어온 일감을 잠시 줄 세워 두고 함수가 감당할 만큼만 꺼내 가게 하려는 목적으로 쓰는 것이 SQS(Simple Queue Service) 트리거입니다.

이를 은행 창구의 번호표 시스템에 비유할 수 있습니다. 손님은 번호표를 뽑아 의자에 앉아 기다리고, 창구 직원은 자기 속도대로 다음 번호를 불러 한 명씩 응대합니다.

SQS 대기열이 번호표를 뽑아 두는 공간이라면 메시지가 손님에 해당하고, Lambda 함수는 창구 직원처럼 대기열에서 메시지를 가져가 처리합니다. 처리 중 문제가 생기면 그 메시지는 다시 대기열로 돌아와 나중에 재시도되며, 오래 처리되지 못한 메시지는 따로 모아 두는 곳으로 보낼 수 있습니다.

정리하면 SQS 트리거는 대기열에 쌓인 메시지를 Lambda가 가져가 처리하는 방식으로, 요청의 폭주를 흡수하고 실패한 작업을 잃지 않게 해 주는 완충 장치입니다.

← 이전S3 이벤트 알림다음 →SNS 트리거

4부. 이벤트 소스 연동035

SNS 트리거

한 사건을 여러 구독자에게 동시에 알리는 구성

주문이 결제되면 메일도 보내고 재고도 줄이고 통계도 남겨야 하는데, 주문을 처리하는 쪽이 이 모든 수신자를 직접 알고 하나하나 호출한다면 수신자가 늘 때마다 그 코드를 고쳐야 합니다. 사건을 한 번만 알리고 관심 있는 쪽이 각자 알아서 받아 가게 하려는 구조가 SNS(Simple Notification Service) 트리거입니다.

이를 학교 건물의 방송실에 비유할 수 있습니다. 방송실은 교실마다 스피커를 따로 찾아가지 않고 확성기 하나에 대고 말하면, 스피커가 연결된 모든 교실에 같은 내용이 동시에 퍼집니다.

SNS 토픽이 확성기라면 구독은 각 교실의 스피커를 연결해 두는 일이고, 주문 완료 같은 사건이 토픽에 게시되면 그 토픽을 구독한 Lambda 함수들이 각각 호출됩니다. 발신자는 누가 듣는지 몰라도 되고, 듣는 쪽은 새로 생겨도 스피커만 달면 됩니다.

정리하면 SNS 트리거는 하나의 사건을 토픽으로 게시해 여러 구독자에게 동시에 전달하는 팬아웃 구성이며, 발신자와 수신자를 느슨하게 분리하는 역할을 합니다.

EventBridge 규칙

AWS 서비스의 사건을 조건에 맞춰 함수로 넘기는 방법

서비스마다 사건을 알리는 형식이 다르고, 같은 사건이라도 특정 조건일 때만 함수를 깨우고 싶은 경우가 많아 모든 서비스에 개별 연결 코드를 심는 방식은 곧 감당하기 어려워집니다. 사건을 한곳에 모아 규칙에 따라 골라 넘겨 주는 서비스가 EventBridge이고, 그중 조건과 대상을 정한 것이 EventBridge 규칙(Rule)입니다.

이를 건물 경비실의 접수대로 비유할 수 있습니다. 각 부서에서 올라온 보고는 모두 경비실 접수대에 들어오고, 접수 담당자는 미리 정해 둔 지침에 따라 어떤 보고를 어느 부서로 보낼지 판단합니다.

EventBridge가 접수대라면 각 AWS 서비스가 보내는 사건이 보고이고, 규칙에 적어 둔 조건에 맞는 사건만 Lambda 함수로 전달됩니다. 조건에는 사건의 출처나 종류 같은 값을 지정할 수 있어, 관심 없는 사건은 함수를 깨우지 않고 걸러집니다.

정리하면 EventBridge 규칙은 AWS 서비스에서 발생한 사건을 조건으로 걸러 Lambda로 라우팅하는 규칙 기반 연결 방식이며, 서비스별 개별 연동 코드를 대신하는 중앙 사건 접수처입니다.

4부. 이벤트 소스 연동037

Kinesis 트리거

흘러 들어오는 데이터 스트림을 함수가 나눠 읽는 방식

쇼핑몰 클릭 로그처럼 1초에 수천 건씩 밀려드는 데이터를 함수가 한 번에 하나씩 처리하려 하면, 처리 속도가 유입 속도를 따라가지 못해 대기열이 끝없이 쌓이고 결국 데이터가 유실됩니다. 이렇게 끊임없이 흘러 들어오는 데이터 스트림(stream)을 여러 조각으로 나눠 함수가 나눠 읽게 하는 것이 Kinesis 트리거(trigger)입니다.

Kinesis 트리거는 Lambda 함수를 Kinesis 데이터 스트림에 연결해, 스트림에 새 레코드가 들어오면 자동으로 함수를 실행하도록 묶어 주는 구성입니다. 이를 물류 창고의 컨베이어 벨트에 비유하면, 끊임없이 흘러오는 택배 상자를 벨트 구간별로 나눠 여러 작업자가 동시에 집어 가는 구조와 같습니다. 스트림은 샤드(shard)라는 여러 개의 벨트 구간으로 쪼개지고, Lambda는 샤드마다 전담 리더 하나를 붙여 그 구간을 지나가는 레코드를 순서대로 읽어 갑니다.

작업자는 상자를 하나씩 꺼내 처리하고, 처리한 위치를 장부에 표시해 두었다가 다음에 그다음 상자부터 이어서 집습니다. 그래서 일부 작업자가 느려도 다른 벨트 구간은 멈추지 않고 계속 돌아가며, 처리되지 않은 상자는 정해진 보관 기간 동안 벨트에 남아 있어 다시 시도할 수 있습니다.

결국 Kinesis 트리거는 데이터 스트림을 샤드 단위로 분할하고 각 샤드에 대응하는 함수 인스턴스가 순서를 지키며 레코드를 소비하게 만들어, 대량의 연속 데이터를 유실 없이 분산 처리하는 방식입니다.

DynamoDB Streams 트리거

테이블 변경 내역을 함수가 순서대로 받아 처리하는 방법

데이터베이스 테이블의 값이 바뀔 때마다 검색용 색인을 갱신하거나 알림을 보내야 하는데, 변경을 감지하는 별도 프로그램을 직접 만들어 돌리면 누락과 지연이 생기기 쉽습니다. 테이블에 일어난 변경 내역을 기록으로 남겨 두고 함수가 그것을 순서대로 받아 처리하게 하는 것이 DynamoDB Streams 트리거입니다.

DynamoDB Streams는 테이블의 항목이 생성·수정·삭제될 때 그 변화를 시간 순서의 로그로 보관하는 기능이고, 트리거는 그 로그를 Lambda 함수와 연결해 변경이 생길 때마다 함수를 깨우는 장치입니다. 이를 아파트 관리 사무소의 방문 기록장에 비유하면, 각 세대에 택배가 들어오고 나갈 때마다 경비실이 시간과 내용을 한 줄씩 적어 두고, 그 기록장을 넘겨받은 담당자가 순서대로 확인해 후속 조치를 하는 것과 같습니다.

기록장은 여러 줄이 이어 붙은 하나의 흐름으로 유지되고, Lambda는 그 흐름을 앞에서부터 차례로 읽어 어느 항목이 어떻게 바뀌었는지 확인합니다. 처리가 실패하면 그 지점에서 다시 읽어 재시도하며, 성공한 지점까지의 위치를 기억해 중복 없이 이어 갑니다.

정리하면 DynamoDB Streams 트리거는 테이블 변경 이벤트를 순서가 보장된 스트림으로 노출하고, Lambda가 그 스트림을 순차적으로 소비해 데이터 변화에 반응하는 구조입니다.

CloudWatch Logs 구독

로그에서 특정 문구가 나올 때 함수를 실행하는 구성

서비스가 로그를 아무리 열심히 남겨도, 사람이 나중에 뒤져 보기 전까지는 그 안의 심각한 오류를 아무도 모릅니다. 로그에서 특정 문구가 나타나는 순간 함수를 자동으로 실행하도록 붙여 두는 것이 CloudWatch Logs 구독(subscription)입니다.

CloudWatch Logs는 애플리케이션이 남기는 로그를 모아 보관하는 서비스이고, 구독은 그 로그의 흐름을 다른 대상으로 전달하도록 거는 필터로, 대상을 Lambda 함수로 지정하면 조건에 맞는 로그가 들어올 때마다 함수가 호출됩니다. 이를 아파트 경비실의 화재 경보기에 비유하면, 로그는 경비실로 흘러드는 각종 감시 기록이고 필터는 연기 감지 센서이며, 센서가 반응하면 담당자를 즉시 부르는 것이 함수 실행입니다.

구독에는 어떤 문구가 나올 때 전달할지 정하는 필터 패턴(filter pattern)을 걸 수 있어, "오류"라는 단어가 포함된 줄만 골라 함수에 넘기는 식으로 잡음을 줄입니다. 전달된 로그는 압축된 묶음 형태로 함수에 도착하고, 함수는 그 안을 풀어 내용을 검사한 뒤 알림을 보내거나 대응 작업을 수행합니다.

결국 CloudWatch Logs 구독은 로그 스트림에 필터를 걸어 특정 패턴이 감지될 때 Lambda를 실행시키는 이벤트 기반 감시 구성입니다.

4부. 이벤트 소스 연동040

예약 실행(EventBridge Scheduler)

정해진 시각에 함수를 주기적으로 돌리는 방법

매일 새벽에 통계를 집계하고 정기적으로 임시 파일을 지우는 작업을 사람이 직접 돌리면, 깜빡하거나 휴가 중에 멈추는 일이 생깁니다. 정해진 시각에 함수를 주기적으로 실행하도록 시계를 걸어 두는 것이 EventBridge Scheduler를 이용한 예약 실행입니다.

EventBridge는 AWS 안팎의 이벤트를 모아 전달하는 서비스이고, 그중 Scheduler는 크론식(cron expression, 시각 규칙을 적는 표기)이나 고정 간격으로 언제 무엇을 실행할지 정해 두는 기능입니다. 이를 아파트 관리실의 정기 점검 일지에 비유하면, 매주 월요일 오전 9시에 소방 점검을 하라고 달력에 반복 일정을 걸어 두면 담당자가 따로 챙기지 않아도 그 시각에 자동으로 점검이 시작되는 것과 같습니다.

예약에는 실행할 함수와 시각 규칙, 그리고 실행이 몰릴 때 얼마나 늦게까지 허용할지를 정하는 시간 범위를 함께 적어 둡니다. 시각이 되면 Scheduler가 함수를 호출하고, 함수는 넘겨받은 실행 시각 정보를 참고해 그 회차에 맞는 작업을 수행합니다.

정리하면 EventBridge Scheduler의 예약 실행은 시각 규칙을 중앙에서 관리하며 Lambda를 주기적으로 호출하는 방식으로, 서버를 계속 띄워 두지 않고도 정기 작업을 안정적으로 돌릴 수 있게 해 줍니다.

5부. 호출과 동시성041

동기 호출의 오류 처리

호출한 쪽에 오류가 어떻게 전달되는지

사용자가 버튼을 눌러 바로 결과를 받아야 하는 기능에서 함수가 실패하면, 아무 안내 없이 화면이 멈추거나 원인 모를 오류만 보이면 사용자는 무슨 일이 일어났는지 알 수 없습니다. 호출한 쪽이 함수의 성공과 실패를 직접 확인할 수 있도록 오류를 그대로 돌려주는 것이 동기 호출(synchronous invocation)의 오류 처리입니다.

동기 호출은 요청을 보낸 쪽이 함수가 끝날 때까지 기다렸다가 결과를 받는 방식이며, 함수가 오류를 내면 Lambda가 그 오류를 호출자에게 응답으로 전달합니다. 이를 택배를 직접 건네받는 경우에 비유하면, 택배 기사가 물건을 넘기면서 받았다는 확인을 즉시 받는 구조이므로, 물건이 잘못되었으면 그 자리에서 바로 교환 요구를 할 수 있습니다.

함수가 처리하지 못한 오류는 호출한 애플리케이션에 오류 응답으로 돌아가고, 애플리케이션은 그 내용을 보고 사용자에게 안내를 하거나 다시 시도할지 결정합니다. 반면 함수가 제한 시간 안에 끝나지 않거나 메모리가 부족해 강제로 중단되는 경우에도 호출자에게는 실패 응답이 전달되며, 이때 Lambda가 저절로 다시 실행해 주지는 않습니다.

따라서 동기 호출에서는 재시도 여부와 오류 표시를 호출한 쪽이 책임지고 처리해야 하며, 이것이 실패를 즉시 알아야 하는 요청-응답 구조의 핵심입니다.

5부. 호출과 동시성042

비동기 호출의 재시도

실패한 호출을 Lambda가 몇 번, 어떻게 다시 시도하는지

사진을 올리면 썸네일을 만드는 작업처럼, 사용자는 결과를 기다리지 않고 바로 다음 화면으로 넘어가는데 뒤에서 도는 함수가 한 번 실패했다고 작업이 그냥 사라지면 나중에 썸네일 없는 사진이 남습니다. 실패한 호출을 Lambda가 일정 횟수만큼 스스로 다시 시도해 주는 것이 비동기 호출(asynchronous invocation)의 재시도입니다.

비동기 호출은 호출한 쪽이 결과를 기다리지 않고 요청만 넘기면 Lambda가 내부 대기열에 넣어 나중에 실행하는 방식이며, 실패하면 정해진 횟수까지 자동으로 다시 실행합니다. 이를 택배를 경비실에 맡기고 가는 경우에 비유하면, 집주인이 없으면 경비실이 물건을 보관했다가 다음에 다시 배송을 시도하고, 여러 번 실패하면 반송 처리해 어딘가에 기록을 남기는 것과 같습니다.

Lambda는 실패한 요청을 짧게는 몇 분에서 길게는 몇 시간에 걸쳐 두 번 더 시도하는 것이 일반적이며, 시도 사이의 간격은 점점 길어집니다. 그래도 모두 실패하면 그 요청은 사라지지 않고 실패 처리 대기열(dead-letter queue)이나 별도의 실패 기록 대상으로 보내져 나중에 원인을 확인할 수 있습니다.

정리하면 비동기 호출의 재시도는 호출자가 기다리지 않는 대신 Lambda가 자동 재시도와 실패 보관을 맡아, 일시적인 장애로 작업이 유실되는 일을 줄이는 안전장치입니다.

부분 배치 응답

여러 건을 한 번에 처리할 때 실패한 건만 다시 보내는 방법

이벤트 여러 건을 묶어서 한 번에 처리할 때, 그중 한 건이 잘못됐다고 묶음 전체를 실패로 돌려버리면 이미 성공한 건들까지 다시 처리되어 같은 일이 두 번 일어납니다. 부분 배치 응답(Partial Batch Response)은 이 문제를 고치려고 만든 장치로, 묶음에서 실패한 항목만 골라 다시 보내게 해 줍니다.

택배 집하 기사가 아파트 한 동에서 상자 열 개를 한 번에 거두는 상황을 생각하면 쉽습니다. 열 개 중 하나만 주소가 잘못되어도 전체를 창고로 되돌려 놓으면, 나머지 아홉 개는 멀쩡한데도 배송 기록이 처음부터 다시 시작됩니다. 대신 기사가 "이 한 개만 문제"라고 표시해 남겨 두면, 창고는 나머지 아홉 개는 처리 완료로 넘기고 문제 상자 하나만 다시 집하 목록에 올립니다.

함수도 마찬가지로 배치로 받은 항목마다 성공과 실패를 따로 표시해 돌려주고, 실패한 항목의 식별자만 응답에 담습니다. 그러면 시스템은 성공분은 지우고 실패분만 다시 배달하므로 같은 일을 두 번 하지 않습니다.

정리하면 부분 배치 응답은 배치 처리에서 항목 단위의 성공과 실패를 구분해 돌려주는 규약이고, 재처리 범위를 실패한 항목으로 좁혀 중복 처리와 낭비를 줄이는 기능입니다.

이벤트 필터링

관심 없는 이벤트는 함수를 깨우지도 않게 거르는 방법

저장소에 파일이 올라오거나 로그가 한 줄 찍힐 때마다 함수를 깨우면, 관심 없는 이벤트까지 전부 실행되어 비용과 소음만 늘어납니다. 이벤트 필터링(Event Filtering)은 그 앞단에서 조건에 맞는 이벤트만 통과시켜, 함수를 아예 깨우지 않게 하는 장치입니다.

아파트 우편함에 광고 전단이 매일 잔뜩 꽂히는 상황과 비슷합니다. 경비실에서 "우리 집 앞으로 오는 것 중 이름이 적힌 것만 넣어 달라"고 미리 규칙을 걸어 두면, 전단은 문 앞까지 오지도 않습니다. 함수 입장에서는 필터 규칙이 경비실 역할을 하고, 조건에 맞지 않는 이벤트는 배달 자체가 취소됩니다.

예를 들어 파일 이름이 특정 확장자로 끝나는 경우에만 통과시키는 식입니다. 이렇게 걸러진 이벤트는 실행 기록에도 남지 않고 요금도 발생하지 않습니다.

이벤트 필터링은 이벤트 원본과 함수 사이에서 조건을 미리 검사해, 필요 없는 호출을 발생 단계에서 없애는 기능입니다.

동시성(Concurrency)

같은 순간에 몇 개의 함수가 함께 돌 수 있는지

갑자기 요청이 몰리면 함수 하나가 앞의 일을 끝낼 때까지 뒤의 요청이 줄을 서게 되고, 대기 시간이 길어지다 결국 처리되지 못하는 요청이 생깁니다. 동시성(Concurrency)은 같은 순간에 몇 개의 함수 실행이 함께 돌 수 있는지를 정하는 한도로, 이 줄서기를 얼마나 넓게 풀어줄지 결정하는 값입니다.

은행 창구 비유가 잘 맞습니다. 창구가 하나뿐이면 손님 열 명이 와도 한 명씩 처리해야 하지만, 창구를 다섯 개 열면 다섯 명이 동시에 업무를 봅니다.

여기서 동시성 값은 "동시에 열어 둘 창구 수"이고, 요청이 창구 수를 넘으면 나머지는 번호표를 들고 기다립니다. 창구 수를 무작정 늘리면 유지비와 뒷단 시스템의 부담이 커지므로, 처리량과 비용을 함께 보고 조정합니다.

동시성은 함수가 동시에 처리할 수 있는 실행 수의 상한이며, 트래픽 급증 시 대기와 실패를 좌우하는 핵심 설정입니다.

예약된 동시성

특정 함수 몫으로 동시성을 떼어 두는 이유

여러 함수가 하나의 동시성 한도를 나눠 쓰면, 한 함수에 트래픽이 몰릴 때 다른 함수가 쓸 몫까지 빼앗겨 함께 느려지거나 멈춥니다. 예약된 동시성(Reserved Concurrency)은 전체 한도에서 특정 함수 몫을 떼어 두어, 그 함수만은 항상 정해진 만큼 돌 수 있게 보장하는 설정입니다.

회사 회의실을 떠올리면 이해가 쉽습니다. 공용 회의실만 있으면 갑자기 큰 회의가 잡힐 때 다른 팀이 쓸 방이 없어지지만, 특정 팀 전용으로 방 하나를 배정해 두면 그 팀은 언제든 회의를 열 수 있습니다. 반대로 그 전용 방은 다른 팀이 쓰지 못하므로, 그 팀이 회의를 안 하는 시간에도 방은 비어 있습니다.

예약된 동시성도 같은 성격이라, 떼어 둔 몫은 다른 함수가 침범하지 못하고 그 함수가 놀 때도 다른 함수가 가져다 쓸 수 없습니다.

예약된 동시성은 중요 함수의 처리 능력을 다른 함수의 폭주로부터 격리해 보장하는 대신, 그 몫만큼 전체 자원을 묶어 두는 설정입니다.

프로비저닝된 동시성

미리 데워 둔 실행 환경으로 대기 시간을 없애는 방법

함수가 처음 호출될 때는 실행 환경을 새로 준비하느라 응답이 몇 초씩 늦어지는데, 결제나 로그인처럼 즉답이 필요한 경로에서는 이 지연이 곧 사용자 이탈로 이어집니다. 프로비저닝된 동시성(Provisioned Concurrency)은 이 준비 작업을 미리 끝내 둔 실행 환경을 대기시켜, 호출 순간 바로 일을 시작하게 하는 기능입니다.

식당 비유가 알맞습니다. 손님이 들어온 뒤에야 재료를 손질하고 불을 피우면 첫 손님은 오래 기다려야 하지만, 영업 전에 재료를 다 손질해 두면 문을 열자마자 음식이 나갑니다.

프로비저닝된 동시성은 "조리대 몇 개를 미리 데워 둘지" 정하는 것과 같아서, 그 수만큼은 준비가 끝난 상태로 유지됩니다. 다만 데워 둔 조리대는 손님이 없어도 계속 유지비가 들고, 그 수를 넘는 요청은 다시 새로 준비해야 하므로 평소 트래픽을 기준으로 잡습니다.

프로비저닝된 동시성은 실행 환경을 미리 초기화해 콜드 스타트 지연을 없애는 기능이며, 상시 유지 비용과 지연 민감도를 맞바꾸는 선택입니다.

콜드 스타트(Cold Start)

함수가 처음 깨어날 때 왜 느린지

함수를 오래 쓰지 않다가 갑자기 호출하면 첫 응답만 유난히 느린 경우가 있는데, 이것이 콜드 스타트(Cold Start)입니다. 함수 서비스는 호출이 없으면 실행 환경을 정리해 자원을 아끼기 때문에, 다시 호출될 때 그 환경을 처음부터 만들어야 하고 그 준비 시간이 응답에 더해집니다.

오랫동안 손님이 없어 불을 끄고 문을 닫아 둔 가게에 손님이 들어오면, 주인은 조명을 켜고 재료를 꺼내고 기계를 예열하는 시간을 먼저 써야 합니다. 손님이 계속 오는 동안에는 가게가 열려 있어 바로 응대하지만, 손님이 끊기면 다시 정리하고 불을 끄므로 다음 손님은 또 기다립니다.

콜드 스타트는 이 "불 켜고 예열하는 시간"으로, 코드를 내려받고 실행 환경을 띄우고 초기화 코드를 돌리는 구간을 포함합니다. 그래서 초기화가 무거운 코드는 콜드 스타트가 더 길어지고, 반대로 호출이 잦아 환경이 살아 있으면 이 지연은 거의 나타나지 않습니다.

콜드 스타트는 유휴 상태의 함수가 새 실행 환경을 준비하느라 첫 호출에서 겪는 추가 지연이며, 미리 데워 두는 방식이나 초기화 최소화로 줄입니다.

SnapStart

스냅샷으로 시작 시간을 줄이는 기법과 제약

함수를 배포해 두고 처음 호출하면, 코드가 실제로 실행되기 전에 실행 환경을 새로 만들고 언어 런타임을 띄우고 라이브러리를 읽어 들이는 준비 시간이 붙습니다. 이 준비가 길면 사용자는 첫 요청에서만 유난히 느린 응답을 받게 되고, 요청이 갑자기 몰릴 때는 이런 준비가 여러 번 겹쳐 지연이 눈에 띄게 커집니다.

SnapStart 는 이 준비를 호출 시점이 아니라 배포 시점으로 옮기자는 발상입니다.

공장에 비유하면 매번 원재료부터 조립하지 않고, 완제품 직전까지 만들어 둔 반제품을 창고에 쌓아 두었다가 주문이 들어오면 마지막 포장만 해서 내보내는 것과 같습니다.

배포할 때 실행 환경을 한 번 띄워 초기화를 끝낸 뒤 그 메모리 상태를 통째로 스냅샷(snapshot)으로 떠 두고, 호출이 오면 그 스냅샷에서 환경을 되살려 곧바로 처리기를 실행합니다. 다만 되살아난 환경은 스냅샷을 뜬 시점의 상태를 그대로 이어받기 때문에, 그때 열어 둔 네트워크 연결은 다시 맺어야 하고 호출마다 달라져야 하는 값은 복원 뒤에 새로 만들어야 합니다.

그래서 모든 런타임에서 쓸 수 있는 것은 아니고, 지원되는 런타임과 조건이 정해져 있습니다.

스케일링 한도와 급증 대응

갑자기 요청이 몰릴 때 무엇이 먼저 걸리는지

서버를 직접 세워 두면 요청이 몰릴 때 늘릴 서버가 정해져 있지 않고, 그 한계를 넘는 순간 사용자는 연결 실패나 긴 대기를 겪게 됩니다. Amazon Lambda 는 서버를 미리 세우지 않고 요청마다 실행 환경을 띄워 처리하는데, 그렇다고 무한히 늘어나지는 않도록 계정과 리전 단위로 동시 실행 수(concurrency) 한도가 걸려 있습니다.

식당에 비유하면 홀의 좌석 수가 먼저 차고, 자리가 있어도 주방의 화구 수가 모자라면 주문이 밀리는 구조와 같습니다.

요청이 몰리면 플랫폼은 실행 환경을 늘려 동시에 돌리는 수를 채우는데, 이 수가 한도에 닿으면 추가 요청은 처리되지 않고 속도 제한 오류(429 TooManyRequestsException)로 돌아옵니다. 즉 급증할 때 가장 먼저 걸리는 것은 코드의 성능이 아니라 동시 실행 수라는 상한입니다.

이 상한은 예약된 동시성(reserved concurrency)으로 함수별 몫을 떼어 두거나, 미리 환경을 데워 두는 프로비저닝된 동시성(provisioned concurrency)으로 특정 함수의 준비 지연을 줄이는 식으로 다룹니다.

정리하면 Lambda 의 확장은 자동이지만 무제한이 아니며, 한도와 준비 시간이라는 두 지점에서 먼저 병목이 생깁니다.

6부. 실행 환경 심화051

임시 스토리지(/tmp)

함수가 잠깐 파일을 쓸 수 있는 공간의 크기와 수명

함수 안에서 파일을 잠깐 만들어 쓰려고 하면, 실행 환경이 언제든 사라질 수 있다는 점이 곧 문제가 됩니다. Lambda 는 이런 짧은 용도로 쓸 수 있는 임시 공간을 함수마다 붙여 주는데, 그것이 /tmp 입니다.

호텔 객실에 비유하면 투숙 기간에는 옷장과 서랍을 마음대로 쓰지만 체크아웃하면 남은 물건은 그대로 정리되는 구조와 같습니다.

이 공간은 함수를 만들 때 정한 크기만큼 주어지며, 설정 가능한 범위는 512MB 부터 10,240MB 까지입니다. 내용은 그 실행 환경이 살아 있는 동안만 유지되므로 같은 환경에서 다음 호출이 이어지면 남아 있을 수 있지만, 환경이 새로 만들어지면 비어 있는 상태로 시작합니다.

그래서 이곳에 둔 파일을 다음 호출이나 다른 동시 실행에서 반드시 찾을 수 있다고 가정하면 안 되고, 여러 호출이 함께 읽어야 하는 자료는 별도의 저장소에 두어야 합니다.

결국 /tmp 는 요청 하나를 처리하는 동안 쓰는 작업 공간이며, 크기는 설정으로 늘릴 수 있고 수명은 실행 환경과 함께하는 임시 디스크입니다.

실행 환경 재사용

앞선 호출의 메모리가 남는 특성과 그 활용법

함수를 호출할 때마다 실행 환경을 처음부터 만든다면, 앞선 호출에서 이미 해 둔 준비를 매번 다시 하게 되어 낭비가 큽니다. 그래서 Lambda 는 한 번 만든 실행 환경을 곧바로 버리지 않고 일정 시간 남겨 두었다가 다음 호출에 다시 씁니다.

단골 식당에 비유하면 주방에서 매번 새로 장을 보지 않고 상비 재료와 손에 익은 조리 도구를 그대로 둔 채 다음 주문을 받는 것과 같습니다.

처리기 바깥에서 선언한 변수는 이 환경과 함께 살아남기 때문에, 데이터베이스 연결이나 설정 값을 그 자리에서 한 번만 준비해 두면 이후 호출이 그 이득을 봅니다.

반대로 이 특성은 앞선 호출의 흔적이 남는다는 뜻이기도 해서, 요청마다 달라야 하는 값이나 사용자별 상태를 그런 변수에 담아 두면 다른 사용자의 요청에 그 값이 새어 나갈 수 있습니다.

그래서 재사용을 전제로 초기화는 바깥에 두되, 호출마다 초기화해야 하는 것은 처리기 안에서 다루는 것이 원칙입니다. 정리하면 실행 환경 재사용은 시작 비용을 아끼는 대신 상태가 남는다는 성질을 함께 안고 가는 구조입니다.

번들 크기 줄이기

패키지를 가볍게 만들어 시작 시간을 줄이는 방법

패키지가 무거우면 실행 환경이 그것을 내려받고 풀어서 읽어 들이는 시간이 그대로 시작 지연으로 이어집니다. 그래서 배포 파일을 가볍게 만드는 일은 곧 첫 응답을 앞당기는 일이 됩니다.

이삿짐을 싸는 상황에 비유하면, 쓰지도 않는 살림까지 전부 상자에 담으면 차에 싣고 내리는 시간이 길어지고, 정말 필요한 것만 골라 싸면 같은 집으로 훨씬 빨리 옮길 수 있습니다.

실제로는 쓰지 않는 의존성을 걷어 내고, 개발용 도구와 테스트 파일을 배포 대상에서 빼고, 여러 파일을 하나로 묶으면서 닿지 않는 코드를 제거하는 번들러(bundler)를 쓰는 방법이 있습니다. 여러 함수가 함께 쓰는 무거운 라이브러리는 계층(layer)으로 분리해 두면 함수마다 같은 내용을 중복해 담지 않아도 됩니다.

다만 지나치게 압축하면 읽기 어려워지고 문제를 찾기 힘들어지므로, 크기와 유지보수 사이의 균형이 필요합니다.

결국 번들 크기 줄이기는 배포물에서 실제로 실행되지 않는 부분을 덜어 내어 시작 시간과 관리 부담을 함께 낮추는 작업입니다.

런타임 API

코드가 플랫폼에 남기는 로그와 응답을 다루는 저수준 인터페이스

함수가 끝났는지, 오류가 났는지, 남긴 로그가 무엇인지를 플랫폼이 알아야 하는데, 코드가 아무 신호도 주지 않으면 플랫폼은 결과를 기다리기만 하게 됩니다. 런타임 API(runtime API)는 이 신호를 주고받는 저수준 인터페이스로, 보통 언어별 런타임이 대신 호출해 주기 때문에 개발자가 직접 다룰 일은 많지 않습니다.

택배 기사와 물류 시스템의 인수인계 창구에 비유하면, 기사가 다음 배송 건을 받아 가고, 처리 결과를 알리고, 문제가 생기면 사유를 적어 돌려보내는 절차가 정해져 있는 것과 같습니다.

흐름은 단순해서, 다음 호출을 달라고 요청해 받아 오고, 처리가 끝나면 결과를 응답으로 돌려주고, 실패하면 오류로 알립니다. 코드가 표준 출력으로 남기는 로그는 이 창구를 거쳐 모아져 로그 저장소로 전달되므로, 로그를 남기는 행위 자체가 곧 관측 자료를 만드는 일이 됩니다.

직접 이 인터페이스를 구현하면 기본 런타임에 없는 언어를 올리거나 실행 흐름을 세밀하게 제어할 수 있지만, 그만큼 호출 수명 주기를 스스로 책임져야 합니다.

정리하면 런타임 API 는 코드와 플랫폼 사이에서 호출을 건네고 결과와 로그를 돌려주는 약속된 통로입니다.

확장(Extension)

함수 옆에서 함께 도는 보조 프로세스의 쓰임

함수가 해야 할 일은 원래 업무 로직인데, 로그를 남기고 성능 지표를 모으고 설정을 불러오는 잡일까지 함수 코드 안에 넣으면 코드가 금세 지저분해지고 로직을 고칠 때마다 잡일 코드도 함께 손봐야 합니다. 그래서 Amazon Lambda는 함수 본체를 건드리지 않고 옆에서 함께 도는 보조 프로세스인 확장(Extension)을 두었습니다. 아파트 한 채를 생각하면, 세대 안으로 들어가지 않고 관리사무소 직원이 복도에 상주하며 세대의 전기와 수도를 검침하고 세대가 문을 열기 전에 공용 현관을 준비해 두는 것과 같습니다.

확장은 함수가 실행되기 전 초기화 단계에서 함께 시작되어 함수와 같은 실행 환경을 공유하고, 함수가 끝나면 함께 정리됩니다. 내부 확장(internal)은 함수와 같은 프로세스 안에서 동작하고, 외부 확장(external)은 별도 프로세스로 떠서 함수 바깥에서 계속 돌 수 있습니다. 확장은 호출이 끝난 뒤에도 남아 다음 호출에 재사용되므로, 모니터링 에이전트나 로깅, 설정 로딩처럼 매번 새로 할 필요가 없는 일을 맡기기에 적합합니다. 정리하면 확장은 Lambda 실행 환경에 함께 배치되어 초기화와 수명주기 사건에 붙고, 함수 코드와 분리된 채 로그와 지표, 설정 같은 주변 작업을 담당하는 보조 프로세스입니다.

EFS 연결

용량이 큰 공유 파일 시스템을 함수에 붙이는 방법

함수는 원래 매번 새로 떴다가 사라지는 임시 공간이라, 처리 중에 만든 파일은 다음 실행에서 흔적도 없이 사라집니다. 여러 함수가 같은 파일을 읽고 써야 하거나 몇 기가바이트짜리 모델과 라이브러리를 호출마다 다시 내려받는 것이 부담이라면, 용량이 큰 공유 파일 시스템을 붙여야 하는데 그때 쓰는 것이 Amazon EFS(Elastic File System) 연결입니다. 회사 공용 창고를 떠올리면, 각자 쓰는 책상은 퇴근하면 치워지지만 공용 창고에 물건을 넣어두면 다음 사람이 와서 그대로 꺼내 쓸 수 있습니다.

EFS는 여러 가용 영역에서 동시에 접근할 수 있는 네트워크 파일 시스템이고, Lambda 함수는 가상 사설 네트워크(VPC) 안에서 마운트 지점(mount point)을 통해 이 파일 시스템을 특정 디렉터리에 붙입니다. 붙이고 나면 함수 코드에서는 그 디렉터리를 평범한 파일 경로처럼 읽고 쓸 수 있고, 여러 함수 인스턴스가 같은 파일을 나눠 씁니다. 다만 VPC 연결이 필요하고 첫 호출 때 마운트를 준비하는 시간이 더 걸릴 수 있습니다. 즉 EFS 연결은 Lambda 함수에 네트워크 파일 시스템을 디렉터리로 마운트해, 실행 환경이 사라져도 남는 공유 저장 공간을 제공하는 방법입니다.

응답 스트리밍

결과를 한 번에 다 만들지 않고 조금씩 흘려보내는 방법

결과가 완전히 만들어질 때까지 기다리는 구조에서는 사용자가 화면 앞에서 수십 초 동안 아무것도 보지 못합니다. 응답 스트리밍(Response Streaming)은 결과를 한 번에 다 만들지 않고 조금씩 흘려보내 첫 응답 시간을 줄이는 방법입니다. 택배를 한 상자에 모두 담아 포장이 끝나야 보내는 방식과, 나오는 대로 소포를 하나씩 부쳐 받는 쪽이 먼저 온 것부터 뜯어 쓰는 방식을 생각하면 됩니다.

스트리밍에서는 함수가 응답 스트림(response stream)에 조각(chunk)을 순서대로 써 넣고, 그 조각이 만들어지는 즉시 호출한 쪽으로 전달됩니다. 그래서 큰 응답을 통째로 메모리에 담아둘 필요가 없어 메모리 사용이 줄고, 첫 바이트가 도착하는 시간(time to first byte)이 짧아집니다. Lambda에서는 이 기능을 지원하는 런타임과 호출 방식에서 쓸 수 있으며, 중간에 실패하면 이미 보낸 부분은 되돌릴 수 없다는 점을 감안해야 합니다. 결국 응답 스트리밍은 함수의 출력을 완성본 하나가 아니라 순차적인 조각의 흐름으로 내보내, 체감 대기 시간과 메모리 부담을 함께 줄이는 방식입니다.

아키텍처 선택

x86과 arm64 중 무엇을 고를지와 그 차이

같은 코드인데 어떤 프로세서 위에서 돌리느냐에 따라 비용과 속도가 달라집니다. Lambda에서 함수를 만들 때 고르는 중앙처리장치 아키텍처 선택지가 x86_64와 arm64 두 가지인데, 무엇을 고를지 판단하려면 그 차이를 알아야 합니다. 회사 배송 차량을 생각하면, 큰 트럭은 아무 짐이나 실을 수 있고 정비소도 많지만 기름을 많이 먹고, 작은 전기차는 연비가 좋지만 짐 모양에 맞춰 포장을 바꿔야 할 때가 있습니다.

x86_64는 오래 쓰인 명령어 집합이라 미리 빌드된 라이브러리와 실행 파일이 대부분 그대로 돌아가고, arm64는 전력 효율이 좋아 같은 작업을 더 낮은 비용으로 처리하는 경우가 많습니다. 다만 arm64에서는 직접 만든 코드나 컨테이너 이미지를 arm64용으로 다시 빌드해야 하고, 일부 외부 제공 실행 파일은 아직 arm64판을 주지 않을 수 있습니다. 어느 쪽이 항상 빠르다고 단정할 수는 없으므로 실제 작업으로 두 아키텍처를 비교 측정해 고르는 편이 안전합니다. 정리하면 x86_64는 호환성이 넓고 arm64는 전력 효율과 비용에서 유리할 수 있어, 라이브러리 지원과 실측 성능을 함께 보고 고르는 것이 아키텍처 선택의 핵심입니다.

메모리와 CPU의 관계

메모리를 올리면 왜 처리 속도까지 빨라지는지

메모리를 넉넉히 잡으면 비용만 오를 것 같지만, 실제로는 처리 시간이 짧아져 전체 비용이 줄어드는 일이 흔합니다. Lambda에서 메모리를 올리면 왜 연산 속도까지 함께 빨라지는지 이해하면 이 현상이 자연스러워집니다. 사무실 작업대를 비유하면, 책상을 넓히면 동시에 펼쳐둘 수 있는 서류가 늘고 회사가 그 작업대 크기에 맞춰 일하는 사람 수도 함께 늘려주는 구조입니다.

Lambda는 메모리 설정값에 비례해 중앙처리장치 성능을 함께 배정하므로, 메모리를 두 배로 올리면 연산 능력도 대략 그만큼 강해집니다. 그래서 계산이 많은 작업은 메모리를 올렸을 때 더 빨리 끝나고, 요금은 실행 시간과 메모리 양을 곱해 정해지므로 더 넉넉한 설정으로 더 짧게 도는 쪽이 총액이 낮아질 수 있습니다. 반대로 메모리를 거의 쓰지 않고 대기만 하는 작업이라면 올려도 얻는 것이 없으니, 메모리와 실행 시간을 함께 재어 비용이 가장 낮은 지점을 찾는 것이 좋습니다. 즉 Lambda의 메모리 설정은 저장 공간의 크기가 아니라 함수에 주어지는 연산 능력의 손잡이이며, 연산 성능이 메모리에 비례해 함께 올라간다는 점이 핵심입니다.

6부. 실행 환경 심화060

타임아웃 설정

실행 시간 한도를 어떻게 정하고 무엇이 걸리는지

함수가 무한 반복에 빠지거나 외부 서비스가 응답하지 않으면, 그대로 둘 경우 요청은 끝나지 않고 비용만 계속 쌓입니다. 그래서 Lambda는 함수마다 실행 시간 한도인 타임아웃(timeout)을 정해두고, 그 시간을 넘으면 강제로 중단합니다. 회의실 예약을 떠올리면, 방을 무제한으로 잡아두면 다음 팀이 들어오지 못하니 예약 시간을 정해두고 시간이 되면 알람과 함께 방을 비우게 하는 것과 같습니다.

타임아웃은 함수가 시작해서 끝날 때까지 허용되는 최대 시간이고, 설정한 시간을 넘기면 Lambda가 실행을 멈추고 오류를 돌려줍니다. 시간이 다 되면 그때까지 만든 중간 결과는 버려지고 호출한 쪽은 실패로 받게 됩니다. 또 타임아웃을 길게 잡으면 그만큼 오래 과금되므로, 정상 처리 시간을 재어 여유를 조금 둔 값으로 정하고 외부 호출에는 그보다 짧은 제한을 따로 거는 편이 좋습니다. 결국 타임아웃은 함수 실행에 걸리는 시간의 상한을 정해, 멈추지 않는 작업이 자원과 비용을 끝없이 잡아먹지 않도록 막는 안전장치입니다.

CloudWatch Logs

함수가 남긴 로그를 어디서 어떻게 보는지

함수가 갑자기 오류를 내고 멈췄는데 아무 기록도 남아 있지 않다면, 우리는 무엇이 잘못됐는지 알 방법이 없습니다. 게다가 Lambda는 직접 접속할 서버가 없는 구조라서, 함수가 남긴 기록을 대신 모아 두고 나중에 꺼내 볼 저장소가 필요하며 그것이 CloudWatch Logs(클라우드워치 로그)입니다.

비유하자면 아파트 단지의 경비 기록과 같습니다. 단지 전체를 묶는 큰 장부가 로그 그룹(Log Group)이고, 여기에는 보통 함수 하나가 대응합니다.

경비원마다 따로 쓰는 개인 기록장이 로그 스트림(Log Stream)이며, 함수가 실행 환경을 하나 새로 만들 때마다 스트림도 하나씩 생깁니다. 그 기록장에 한 줄씩 적히는 사건 하나하나가 로그 이벤트(Log Event)로, 함수가 실행되며 남긴 출력 한 줄이 여기에 해당합니다.

정리하면 CloudWatch Logs는 함수 이름으로 묶인 로그 그룹과 실행 환경별 로그 스트림에 로그 이벤트를 시간순으로 쌓아 두고, 필요할 때 검색어로 찾아보게 해 주는 서비스입니다.

구조화 로깅

나중에 검색하고 집계하기 좋은 로그 형태

오류가 났을 때 로그가 "주문 처리 실패"라는 문장 한 줄뿐이라면, 어느 주문이었고 누구의 요청이었는지는 알 수 없습니다. 그래서 로그를 사람이 읽는 문장이 아니라 기계가 곧바로 알아보는 정해진 형식으로 남기는 방식이 필요하고, 이것이 구조화 로깅(Structured Logging)입니다.

택배 송장을 떠올리면 이해가 쉽습니다. 송장에는 받는 사람, 보내는 사람, 품목이 정해진 칸에 나뉘어 적혀 있어서 누가 봐도 같은 자리에서 같은 정보를 찾습니다. 구조화 로깅도 마찬가지로 로그를 JSON 같은 형식으로 남기면서 요청 식별자, 주문 번호, 처리 시간 같은 항목에 각각 이름표를 붙입니다.

그러면 로그 수집 도구가 그 이름표를 기준으로 원하는 값만 골라 세거나 걸러 낼 수 있습니다.

결국 구조화 로깅은 로그를 읽는 사람의 눈이 아니라 검색과 집계를 하는 도구가 다루기 좋게, 항목마다 이름을 붙여 남기는 방식입니다.

CloudWatch 지표

호출 수·오류율·소요 시간 같은 숫자를 읽는 방법

로그를 한 줄씩 들여다보는 것만으로는 지금 함수가 평소보다 느린지, 오류가 늘고 있는지 판단하기 어렵습니다. 그래서 호출 수나 오류율처럼 미리 정해진 숫자를 일정 간격으로 자동 집계해 주는 기능이 필요하고, 이것이 CloudWatch 지표(Metrics)입니다.

자동차 계기판과 같습니다. 계기판은 엔진 내부를 하나하나 보여 주지 않고 속도와 연료량, 냉각수 온도처럼 운전에 필요한 몇 가지 숫자만 실시간으로 보여 줍니다. CloudWatch 지표도 함수의 호출 횟수(Invocation), 오류 횟수(Error), 실행에 걸린 시간(Duration) 같은 값을 1분 단위로 모아 하나의 숫자로 남깁니다.

이 숫자들을 시간축에 이어 그린 것이 그래프이고, 우리는 그 선이 위로 튀는 순간을 보고 이상하다는 것을 알아차립니다.

정리하면 CloudWatch 지표는 로그의 개별 사건을 세어 호출 수·오류율·소요 시간 같은 요약 숫자로 바꿔 주고, 그 변화를 그래프로 보여 주는 기능입니다.

X-Ray 추적

함수에서 다른 서비스로 이어지는 호출 경로를 따라가는 방법

한 번의 요청이 함수를 거쳐 데이터베이스와 다른 서비스까지 다녀오는데 응답이 느리다면, 어느 구간에서 시간이 새는지 로그만으로는 좀처럼 알기 어렵습니다. 요청 하나가 지나간 길을 구간별로 이어 붙여 보여 주는 도구가 필요하고, 이것이 X-Ray(엑스레이) 추적입니다.

택배 배송 조회와 같습니다. 송장 번호 하나로 집하장, 간선 터미널, 배송 기사까지 각 지점을 지날 때마다 시각이 기록되고, 우리는 어느 구간에서 오래 머물렀는지 한눈에 봅니다. X-Ray에서는 요청 하나의 전체 여정이 트레이스(Trace)이고, 각 지점에서 찍히는 기록이 세그먼트(Segment)이며, 그 안에서 더 잘게 나뉜 호출이 서브세그먼트(Subsegment)입니다.

함수가 다른 서비스를 부를 때 그 호출 정보가 함께 전달되도록 하면, 흩어진 기록이 하나의 트레이스로 이어집니다.

결국 X-Ray는 요청 하나에 고유한 추적 식별자를 붙여 서비스 사이의 호출 경로를 따라가며, 어느 구간이 얼마나 걸렸는지 보여 주는 추적 도구입니다.

Lambda Powertools

로깅·추적·지표를 손쉽게 붙이는 도구의 쓰임

로그를 남기고 추적을 붙이고 지표까지 직접 넣으려 하면, 정작 업무 로직보다 준비 코드가 더 길어집니다. 이런 공통 작업을 정해진 방식으로 대신 처리해 주는 도구가 있으면 좋고, 그것이 Lambda Powertools(람다 파워툴)입니다.

잘 정리된 공구함 하나를 떠올리면 됩니다. 드라이버와 망치와 줄자가 각각 어디에 꽂혀야 하는지 정해져 있어서, 필요한 도구를 꺼내 쓰기만 하면 됩니다. Powertools도 로깅(Logger), 추적(Tracer), 지표(Metrics)를 각각 하나의 도구처럼 제공하고, 코드에서는 데코레이터나 한 줄 호출로 붙입니다.

로거는 요청 식별자와 함께 구조화된 로그를 남기고, 트레이서는 X-Ray 기록을 자동으로 만들며, 지표 도구는 로그에 남긴 값을 CloudWatch 지표로 바꿔 줍니다.

정리하면 Lambda Powertools는 로깅·추적·지표라는 공통 작업을 표준 도구처럼 묶어 제공해서, 함수마다 같은 준비 코드를 되풀이하지 않게 해 주는 라이브러리입니다.

알람과 대시보드

문제가 생겼을 때 사람이 알아차리게 만드는 구성

아파트의 화재 경보기와 경비실 모니터를 생각하면 됩니다. 경보기는 연기가 일정 농도를 넘으면 저절로 소리를 내어 잠든 사람까지 깨웁니다. CloudWatch 알람도 오류 횟수가 5분 동안 몇 건을 넘는 식으로 조건을 정해 두면, 그 조건이 참이 되는 순간 SNS 같은 알림 채널로 메일이나 문자를 보냅니다.

경비실 모니터가 여러 층의 상태를 한눈에 보여 주듯, 대시보드는 호출 수·오류율·소요 시간 그래프를 한 화면에 배치해 상황을 빠르게 판단하게 합니다.

결국 알람은 지표가 정한 임계값을 넘을 때 사람을 깨우는 장치이고, 대시보드는 흩어진 지표를 한 화면에 모아 현재 상태를 읽게 하는 화면입니다.

오류의 두 종류

내 코드의 오류와 플랫폼 쪽 오류를 구분하는 법

새벽에 함수가 갑자기 실패하기 시작하면 가장 먼저 드는 생각은 내 코드를 고쳐야 하나 하는 것이지만, 실제로는 코드가 멀쩡한데도 실패가 쏟아지는 경우가 적지 않습니다. 그럴 때 필요한 것이 내가 쓴 코드의 문제와 플랫폼 쪽 문제를 갈라 보는 눈이며, AWS Lambda 같은 서버리스(serverless) 환경에서는 이 구분이 특히 중요합니다.

택배를 생각해 보면 이해가 쉽습니다. 내가 물건을 잘못 포장해서 깨진 것과 택배 회사 창고에 정전이 나서 물건이 상한 것은 겉으로는 똑같이 배송 실패로 보이지만 고칠 곳이 전혀 다릅니다.

함수도 마찬가지여서, 실행 로그에 내 코드가 남긴 오류 메시지가 찍혀 있으면 포장 문제이고, 코드가 아예 시작되지 못했거나 실행 환경이 준비되지 못했다는 기록만 남으면 창고 문제입니다. 전자는 내가 고치고, 후자는 같은 요청을 다시 보내거나 플랫폼 상태를 확인하는 것이 순서입니다.

정리하면 오류의 출처를 먼저 가르는 것이 대응의 시작입니다. 내 코드가 던진 함수 오류와 플랫폼이 요청을 처리하지 못해 돌려준 오류를 나눠 보고, 전자만 코드 수정 대상으로 삼으면 됩니다.

7부. 관측성과 장애 대응068

재시도 한도와 DLQ

끝내 실패한 이벤트를 잃지 않게 보관하는 방법

이벤트를 처리하다 실패하면 플랫폼은 자동으로 몇 번 더 시도합니다. 그런데 끝없이 다시 시도하면 같은 실패가 무한히 반복되고, 반대로 한 번 실패했다고 버리면 처리하지 못한 주문이 조용히 사라집니다. 이 둘 사이를 조율하는 장치가 재시도 한도(retry limit)와 죽은 편지함(DLQ, Dead Letter Queue)입니다.

택배 기사가 부재중인 집에 몇 번까지 다시 찾아갈지 정해 두는 것과 같습니다. 세 번까지 재배달하고 그래도 안 되면 그 편지를 버리지 않고 반송 전용 보관함에 넣어 두는 구조입니다.

여기서 재배달 횟수가 재시도 한도이고, 보관함이 DLQ이며, 함수가 실패를 돌려줄 때마다 남은 횟수가 하나씩 줄어듭니다. 보관함에 쌓인 편지는 나중에 원인을 고친 뒤 다시 꺼내 처리할 수 있습니다.

정리하면 재시도 한도는 실패한 이벤트를 다시 처리해 볼 최대 횟수를 정하는 값입니다. DLQ는 그 한도를 넘긴 이벤트를 버리지 않고 따로 모아 두는 안전망이며, 이 둘을 함께 두어야 실패가 조용히 사라지지 않습니다.

실패 목적지(Destinations)

성공·실패 결과를 다른 서비스로 넘기는 설정

함수가 끝났을 때 그 결과가 어디로 가는지 정해 두지 않으면, 성공했는지 실패했는지는 로그를 뒤져야만 알 수 있습니다. 처리 결과를 다른 서비스로 자동으로 넘겨 주는 설정이 실패 목적지(Destinations)이며, Lambda의 비동기 호출에서는 성공과 실패를 각각 다른 곳으로 보낼 수 있습니다.

비유는 택배 송장입니다. 송장에 배송에 성공하면 여기, 실패하면 저기라고 미리 적어 두면 기사가 따로 보고하지 않아도 물건이 알아서 갈 곳을 찾아갑니다.

함수도 실행이 끝나면 결과 기록을 큐나 알림 서비스로 보내고, 성공은 처리 완료 쪽으로 실패는 보관과 경보 쪽으로 흘러갑니다. 이렇게 하면 실패를 로그에서 찾아 헤매지 않고 정해진 통로에서 받아 볼 수 있습니다.

정리하면 실패 목적지는 비동기 호출의 성공과 실패 결과를 다른 서비스로 자동 전달하는 설정입니다. 알림과 보관을 로그와 분리해 두면 운영이 단순해지고 실패를 놓칠 가능성도 줄어듭니다.

장애 대응 절차

함수가 죽었을 때 무엇부터 확인할지

함수가 갑자기 응답하지 않으면 로그와 지표와 설정을 한꺼번에 뒤지게 되고, 그러다 보면 정작 원인은 놓치기 쉽습니다. 그래서 장애 대응은 확인 순서를 미리 정해 두는 것이 핵심이며, Lambda에서는 오류율과 실행 시간, 동시 실행 수 같은 지표가 첫 단서가 됩니다.

응급실을 떠올리면 이해가 쉽습니다. 환자가 실려 오면 의사는 원인부터 찾지 않고 숨과 맥박부터 확인합니다. 살릴 수 있는 상태인지를 먼저 보고, 그다음 어디가 다쳤는지 순서대로 좁혀 갑니다.

정리하면 장애 대응 절차는 지표로 범위를 좁히고, 배포 이력과 오류 유형으로 원인을 가르고, 마지막에 기록으로 재발을 막는 순서입니다.

정리하면 실행 시간은 총합이 아니라 구간별로 재야 의미가 있습니다. 초기화와 외부 호출과 계산 구간을 나눠 보면 개선할 곳이 분명해집니다.

메모리 튜닝

비용과 속도가 모두 좋아지는 메모리 값을 찾는 절차

메모리를 넉넉히 주면 빠를 것 같지만 요금도 함께 오르고, 아끼면 느려지거나 메모리가 부족해 아예 죽습니다. 이 둘 사이에서 비용과 속도가 함께 좋아지는 지점을 찾는 작업이 메모리 튜닝이며, Lambda는 메모리 설정에 따라 중앙 처리 장치(CPU) 성능도 함께 달라집니다.

이삿짐 차를 떠올리면 이해가 쉽습니다. 짐이 많은데 작은 차를 부르면 여러 번 왕복해야 해서 시간이 오래 걸리고, 아주 큰 차를 부르면 한 번에 끝나지만 기름값이 아깝습니다. 적당한 크기의 차를 고르면 왕복이 줄어 총비용이 오히려 내려가는 구간이 생깁니다.

함수도 마찬가지여서 메모리를 조금 올리면 실행 시간이 크게 줄어 총요금이 내려가는 값이 존재합니다. 그래서 몇 개의 값을 정해 실제 요청으로 재 보고, 걸린 시간과 요금을 함께 비교해 가장 나은 지점을 고릅니다.

정리하면 메모리 튜닝은 메모리와 실행 시간을 함께 재어 총비용이 가장 낮아지는 값을 찾는 절차입니다. 메모리를 올려 성능이 좋아지면 실행 시간이 줄어 요금도 함께 내려갈 수 있습니다.

비용 계산과 절감

청구서가 어떻게 만들어지는지 이해하고 줄이는 방법

서버를 직접 빌려 쓰던 시절에는 아무도 접속하지 않는 새벽에도 정해진 요금이 그대로 나갔고, 반대로 갑자기 손님이 몰리면 컴퓨터를 급히 늘리느라 비용이 걷잡을 수 없이 뛰었습니다. 이런 곤란을 없애려고 요청이 올 때만 코드를 실행하고 실제로 쓴 시간만큼만 돈을 받는 방식이 등장했는데, 그것이 바로 AWS Lambda(람다)입니다. 다만 "쓴 만큼 낸다"는 말은 청구서를 이해하지 못하면 오히려 더 무서운 이야기가 되므로, 요금이 어떻게 쌓이는지부터 알아야 합니다. 람다의 요금은 택배 요금과 똑같이 생각하면 쉽습니다. 택배를 보낼 때 건수마다 붙는 기본요금이 있고, 무거운 짐일수록, 오래 부칠수록 값이 올라가는데, 람다도 실행된 횟수에 붙는 요금과 실행에 걸린 시간에 메모리 크기를 곱한 요금이 따로 붙습니다.

여기에 함수가 쓰는 임시 저장 공간과 외부로 나가는 데이터 전송료가 별도로 더해지고, 함수가 다른 AWS 서비스를 부르면 그 서비스의 요금도 각각 청구됩니다. 그래서 청구서를 줄이는 일은 대개 세 가지 중 하나를 건드리는 일이 되는데, 호출 횟수를 줄이거나, 함수가 깨어 있는 시간을 줄이거나, 메모리를 실제 필요한 만큼만 주는 것입니다. 특히 메모리를 올리면 시간당 단가는 비싸지지만 처리가 빨라져서 총액이 오히려 줄어드는 경우도 있으니, 한 번씩 크기를 바꿔 실측해 보는 편이 좋습니다. 정리하면 람다의 비용은 요청 수와 실행 시간, 그리고 메모리 크기의 곱으로 결정되며, 절감은 호출을 줄이고 실행 시간을 줄이고 적정 메모리를 찾는 세 갈래로 접근합니다. 로그와 지표를 주기적으로 들여다보며 낭비 지점을 찾는 습관이 결국 가장 큰 절감책입니다.

워밍 비용의 저울질

프로비저닝된 동시성과 콜드 스타트 중 무엇이 싼지 판단하기

함수를 아무도 부르지 않다가 갑자기 부르면, 준비된 실행 환경이 없어서 코드를 새로 띄우는 동안 사용자가 몇 초씩 기다려야 하는 일이 생깁니다. 이 대기 시간을 콜드 스타트(cold start)라고 부르는데, 결제나 로그인처럼 즉답이 필요한 화면에서는 치명적인 지연이 됩니다. 그래서 미리 실행 환경을 데워 두는 프로비저닝된 동시성(provisioned concurrency)이라는 기능이 나왔고, 문제는 이 예약이 대기 시간을 없애는 대신 요금을 계속 발생시킨다는 점입니다. 이 선택은 아파트 현관에 택시를 세워 두는 일과 같습니다. 손님이 언제 나올지 모르니 기사 한 명을 하루 종일 대기시켜 두면 바로 출발할 수 있지만, 손님이 없어도 하루치 요금을 다 내야 합니다. 반대로 그냥 길에서 부르면 공짜로 기다릴 수 있지만, 바쁜 시간에는 차가 늦게 도착합니다.

프로비저닝된 동시성은 대기 중인 기사에게 붙는 고정 비용이고, 콜드 스타트는 손님이 기다리는 시간이라는 비용입니다. 어느 쪽이 싼지는 하루에 몇 번 부르는지, 그리고 그 지연이 매출에 얼마나 영향을 주는지에 달려 있습니다. 결국 판단 기준은 대기 시간의 금전적 가치와 예약 요금을 비교하는 것입니다. 호출이 뜸하거나 지연이 크게 문제되지 않는 업무라면 콜드 스타트를 감수하고, 응답 속도가 곧 매출인 업무라면 필요한 시간대만 예약하는 쪽이 합리적입니다.

배치 크기 조정

한 번에 몇 건씩 처리할 때가 가장 효율적인지

함수가 한 번에 한 건씩만 처리하도록 만들어 두면, 갑자기 수천 건이 밀려올 때 함수가 수천 번 깨어나고 그만큼 호출 요금과 대기 시간이 겹겹이 쌓입니다. 같은 일을 조금씩 나눠 여러 번 하는 것보다, 한 번에 여러 건을 묶어 처리하는 편이 훨씬 효율적인 경우가 많습니다. 이때 "한 번에 몇 건씩"을 정하는 값이 배치 크기(batch size)입니다. 택배 기사가 물건을 하나씩 배송하는 것과 여러 개를 한 번에 싣고 도는 것을 떠올리면 이해가 쉽습니다. 한 건씩 오가면 왕복 시간이 계속 붙고 기름값도 몇 배가 되지만, 트럭에 여러 개를 실으면 왕복 한 번으로 많은 집을 돌 수 있습니다.

다만 너무 많이 실으면 한 집에서 문제가 생겼을 때 트럭 전체가 지연되고, 처리 도중 실패하면 어디까지 성공했는지 다시 확인해야 하는 부담도 커집니다. 그래서 배치 크기는 처리 속도와 실패 시 재처리 범위 사이에서 고르는 값이며, 함께 설정하는 최대 대기 시간은 "몇 건이 모일 때까지 기다릴지"를 정해 줍니다. 정리하면 배치 크기는 한 번의 실행으로 처리할 건수를 정해 호출 횟수와 전체 처리 시간을 줄이는 설정입니다. 작게 잡으면 안전하지만 비효율적이고, 크게 잡으면 효율적이지만 실패 한 건이 여러 건을 막을 수 있으므로 업무 특성에 맞춰 조정해야 합니다.

캐싱 전략

같은 계산을 반복하지 않게 만드는 방법

같은 상품 정보나 같은 설정값을 매번 데이터베이스에서 다시 꺼내 온다면, 똑같은 계산과 조회를 수백 번 반복하며 시간과 요금을 낭비하게 됩니다. 게다가 그 조회가 느리면 사용자는 화면이 뜨지 않아 답답해합니다. 이 반복을 없애려고 한 번 구한 결과를 어딘가에 잠시 저장해 두고 다음부터는 그것을 다시 쓰는 방법이 쓰이는데, 이것이 캐싱(caching)입니다. 도서관 사서를 생각하면 구조가 그려집니다. 손님이 책을 찾을 때마다 창고 깊숙이 들어가면 오래 걸리므로, 자주 찾는 책 몇 권은 데스크 옆 서가에 꽂아 둡니다. 데스크 서가가 캐시이고, 창고가 원본 저장소이며, 오래된 책을 서가에서 빼는 규칙이 만료 정책입니다.

여기서 중요한 것은 원본이 바뀌었을 때 서가의 책도 바꿔야 한다는 점인데, 이 갱신을 언제 할지가 캐싱 전략의 핵심입니다. 람다에서는 실행 환경이 재사용될 때 메모리에 남는 공간을 활용할 수 있지만, 그 공간이 항상 남아 있다고 보장되지는 않으므로 영속적인 저장소와 함께 쓰는 구성이 일반적입니다. 정리하면 캐싱은 느리고 비싼 조회 결과를 가까운 곳에 임시로 두고 재사용하는 기법이며, 성패는 무엇을 얼마나 오래 저장하고 언제 무효화할지 정하는 데 달려 있습니다. 오래된 값을 보여 주는 위험과 매번 다시 계산하는 비용 사이의 균형을 잡는 일이 전략의 전부입니다.

외부 캐시 연동

Redis 같은 캐시를 함수에서 쓰는 구성과 주의점

람다 함수는 호출이 끝나면 실행 환경이 사라질 수 있어서, 함수 안에 저장한 값이 다음 호출에 그대로 있다고 믿을 수 없습니다. 여러 함수가 같은 데이터를 공유해야 하는데 매번 원본을 조회하면 응답이 느려지고 원본 저장소에도 부담이 몰립니다. 이 문제를 풀기 위해 Redis(레디스) 같은 외부 캐시를 두고 함수들이 그곳을 함께 바라보게 하는 구성이 널리 쓰입니다. 이 구성은 아파트 단지의 공용 사물함과 비슷합니다. 각 세대가 자기 집에만 물건을 두면 다른 세대와 나눠 쓸 수 없지만, 중앙 현관에 공용 사물함을 두면 누구든 열쇠로 꺼내 쓸 수 있습니다. 함수는 사물함에 값을 넣고 꺼내며, 사물함이 만료 규칙에 따라 오래된 물건을 정리합니다.

다만 사물함이 있는 곳까지 걸어가는 시간이 필요하므로 함수와 캐시를 가까운 네트워크에 두어야 하고, 사물함이 고장 나면 모든 세대가 불편해지므로 접속 실패 시 원본을 조회하는 대비책이 필요합니다. 또한 캐시에 무엇을 얼마 동안 둘지, 비밀번호 같은 값을 어떻게 보호할지도 함께 정해야 합니다. 정리하면 외부 캐시 연동은 함수 바깥에 공유 저장소를 두어 여러 실행 환경이 같은 결과를 재사용하게 만드는 구성입니다. 네트워크 지연과 장애 대비, 만료와 보안 정책을 함께 설계해야 안정적으로 동작합니다.

팬아웃과 팬인

하나의 작업을 여러 함수로 나눠 처리하고 다시 모으는 패턴

이미지 변환, 알림 발송, 보고서 생성처럼 한 번의 요청이 여러 가지 일을 동시에 해야 하는 경우가 있습니다. 이 일들을 하나의 함수 안에서 순서대로 처리하면 앞 작업이 끝날 때까지 뒤 작업이 기다리고, 중간에 하나가 실패하면 전체가 무너집니다. 그래서 큰 작업 하나를 여러 개의 작은 작업으로 쪼개 각각 다른 함수에 맡기고, 그 결과를 다시 모으는 방식이 쓰이는데, 나눠 보내는 것을 팬아웃(fan-out), 모으는 것을 팬인(fan-in)이라고 합니다. 이 구조는 총무팀이 회의 준비를 하는 방식과 같습니다. 회의 하나를 위해 한 사람이 장소 예약, 다과 주문, 자료 인쇄를 차례로 하면 늦어지지만, 세 사람에게 동시에 나눠 맡기면 훨씬 빠릅니다. 이렇게 일을 뿌리는 단계가 팬아웃이고, 세 사람의 완료 보고를 모아 "준비 끝"으로 정리하는 단계가 팬인입니다.

이때 누가 무엇을 맡았는지 기록해 두어야 하고, 한 사람이 못 끝냈을 때 다시 요청하거나 실패로 처리하는 규칙이 필요합니다. 람다에서는 보통 대기열이나 이벤트 전달 서비스를 통해 작업을 뿌리고, 결과는 별도 저장소나 상태 추적 수단에 쌓아 모읍니다. 정리하면 팬아웃과 팬인은 하나의 작업을 여러 함수로 나눠 병렬로 처리하고 그 결과를 다시 합치는 패턴입니다. 속도와 확장성을 얻는 대신, 작업 추적과 실패 재처리, 중복 실행 방지를 함께 설계해야 안전하게 운영할 수 있습니다.

스트리밍 데이터 처리

끊임없이 들어오는 데이터를 안정적으로 소화하는 설계

Lambda를 처음 쓰는 팀이 로그나 클릭 기록처럼 끊임없이 들어오는 데이터를 파일로 모아 두고 한 시간에 한 번씩 몰아서 처리한다고 해 봅시다. 그러면 그 한 시간 동안 장애가 나도 알아채지 못하고, 몰아서 처리하는 순간에만 자원이 터질 듯 바빠지는 곤란한 상황이 벌어집니다. 스트리밍 데이터 처리(streaming data processing)는 데이터를 덩어리로 모으지 않고 들어오는 즉시 조금씩 나눠 처리하는 방식이며, Amazon Lambda에서는 그 조각을 이벤트(event) 하나로 받아 함수를 실행합니다.

택배 비유로 보면, 하루 세 번 대형 트럭이 오는 창고 대신 오토바이 기사가 상자를 한 개씩 수시로 가져오는 구조로 바꾼 것과 같습니다. 기사가 상자를 내려놓는 순간 창고 직원 한 명이 그 상자만 보고 분류를 끝내므로 상자가 몰려도 일이 밀리지 않고, 상자가 없으면 그 직원은 쉬고 있습니다. 다만 상자가 갑자기 쏟아지면 잠깐 줄이 생길 수 있으므로 창고 쪽에서는 동시에 일할 직원 수의 상한을 정해 두고 밀린 상자는 대기열(queue)에 세워 둡니다.

Lambda도 같은 원리로 이벤트 원본(event source)이 함수를 하나씩 호출하고, 동시 실행 수(concurrency)라는 상한 안에서만 일을 벌입니다.

결국 스트리밍 데이터 처리는 데이터를 모으지 않고 이벤트 단위로 잘게 나눠, 그때그때 필요한 만큼만 함수를 실행하는 설계입니다. 이렇게 해 두면 처리량이 늘어도 구조를 바꾸지 않고 동시 실행 수만 조정하면 됩니다.

흔한 안티패턴

초보자가 자주 저지르는 설계 실수와 그 대안

Lambda를 처음 쓰는 사람이 흔히 하는 실수는 하나의 함수에 모든 일을 다 넣거나, 반대로 아주 작은 일마다 함수를 수십 개로 쪼개는 것입니다. 이런 설계는 처음에는 잘 도는 것처럼 보이지만 시간이 지나면 배포가 무서워지고 장애 원인을 찾는 데 몇 시간이 걸리는 곤란한 상황을 만듭니다. 그래서 초보자가 자주 저지르는 설계 실수와 그 대안을 안티패턴(anti-pattern)이라는 이름으로 미리 정리해 둡니다.

아파트 관리사무소 비유로 보면, 한 직원에게 경비와 청소와 수리와 택배 접수를 모두 맡기면 그 직원이 쉬는 날 관리사무소 전체가 멈춥니다. 반대로 우유 배달과 신문 배달과 택배 접수를 각각 다른 직원에게 나누되 서로의 업무 규칙까지 알아야 한다면 인수인계만으로 하루가 갑니다. 그래서 하는 일은 하나로 묶되 그 일에 필요한 규칙과 데이터는 그 안에서 끝내도록 경계를 긋는 것이 핵심이고, 함수끼리는 결과만 주고받게 만드는 것이 대안입니다.

실제로 자주 나오는 안티패턴은 함수 안에서 다른 함수를 동기로 줄줄이 부르는 설계, 설정값을 코드에 박아 두는 설계, 그리고 다시 시도하면 같은 일이 두 번 처리되는 설계입니다.

결국 안티패턴은 기술이 나빠서가 아니라 책임의 경계를 흐리게 그어서 생기며, 대안은 대부분 그 경계를 다시 긋는 일로 정리됩니다. 함수 하나가 하는 일이 한 문장으로 설명되지 않는다면 그때가 나눌 때입니다.

함수 책임 나누기

하나의 함수에 어디까지 맡겨야 하는지

Lambda 함수를 처음 만들 때는 대개 작게 시작하지만, 기능이 늘면서 검증과 저장과 알림과 기록 집계까지 한 함수에 계속 얹히게 됩니다. 그러면 어느 날 알림 형식만 바꾸고 싶어도 저장 로직까지 함께 건드려야 해서, 작은 수정 하나가 전체 장애로 번지는 곤란한 상황이 생깁니다. 함수 책임 나누기는 하나의 함수에 어디까지 맡길지를 미리 정해 두는 설계 습관입니다.

편의점 아르바이트 비유로 보면, 한 사람이 계산과 재고 정리와 폐기 처분과 발주까지 다 하면 그 사람이 아플 때 매장이 문을 닫아야 합니다. 대신 계산 담당은 계산만, 재고 담당은 진열과 폐기만 하도록 나누면 각자 자기 자리만 배우면 되고 한 사람이 빠져도 다른 사람이 그 자리만 대신 서면 됩니다. 다만 계산 담당이 재고 담당의 장부까지 직접 고치기 시작하면 다시 뒤엉키므로, 두 사람 사이에는 판매 기록을 넘긴다는 식의 주고받는 형식을 정해 두어야 합니다.

Lambda에서도 이 경계를 이벤트의 모양으로 정하고, 함수는 입력 이벤트 하나를 받아 결과 하나를 돌려주는 단위로 유지합니다.

결국 함수 책임 나누기는 함수를 잘게 쪼개는 일이 아니라, 변경이 생겼을 때 고칠 곳이 한 군데로 모이도록 경계를 정하는 일입니다. 그 경계는 대개 이 함수는 무엇을 입력받아 무엇을 남기는가라는 한 문장으로 확인할 수 있습니다.

오케스트레이션과 코레오그래피

흐름을 지휘하는 방식과 이벤트로 이어 붙이는 방식의 차이

여러 Lambda 함수가 함께 하나의 일을 처리할 때 누가 다음 단계를 부를지 정하지 않으면, 흐름이 코드 곳곳에 흩어져 전체 순서를 아무도 설명하지 못하게 됩니다. 오케스트레이션(orchestration)과 코레오그래피(choreography)는 이 흐름을 붙잡는 두 가지 방식이며, 둘 다 여러 서비스가 하나의 결과를 만들도록 이어 붙이는 문제를 다룹니다.

결혼식 준비 비유로 보면, 오케스트레이션은 진행자가 한 명 있어서 이제 식장으로, 다음은 축가라고 순서대로 모두에게 지시하는 방식입니다. 코레오그래피는 진행자 없이 각 담당자가 내 차례가 끝났다는 신호만 옆으로 넘기면 다음 담당이 스스로 움직이는 방식이며, 그 신호가 곧 이벤트(event)입니다. 진행자가 있으면 전체 순서와 실패 지점을 한눈에 볼 수 있지만 그 진행자가 병목이 되고, 신호만 넘기면 담당자를 쉽게 늘릴 수 있지만 지금 어디까지 진행됐는지 확인하기가 어렵습니다.

그래서 Lambda에서는 흐름이 길고 되돌려야 할 단계가 많으면 Step Functions 같은 오케스트레이터를, 단계가 적고 서로 느슨하게 연결되면 이벤트로 잇는 코레오그래피를 고릅니다.

결국 두 방식의 차이는 흐름을 누가 기억하느냐입니다. 오케스트레이션은 중앙의 지휘자가, 코레오그래피는 각 참여자가 자기 앞뒤 신호만 기억합니다.

Step Functions 연동

여러 단계를 가진 작업을 Lambda로 이어 붙이는 방법

Lambda 함수 하나는 실행 시간의 상한이 정해져 있어서, 몇 시간이 걸리는 작업을 함수 안에서 순서대로 부르면 중간에 끊기고 어디까지 했는지도 남지 않습니다. Step Functions 연동은 여러 단계를 가진 작업을 하나의 상태 기계(state machine)로 정의하고, 각 단계에서 Lambda를 호출해 이어 붙이는 방법입니다.

택배 집하와 배송 비유로 보면, 물건 하나가 접수와 분류와 간선 이동과 배송 완료라는 단계를 거친다고 할 때 한 기사가 접수부터 배송까지 혼자 들고 다니면 그 기사가 쉬는 순간 물건이 멈춥니다. 대신 각 구간에 담당자를 따로 두고 지금 이 물건은 분류 단계에 있다는 상태표를 한 곳에서 관리하면, 어느 구간에서 막혔는지 바로 보이고 막힌 구간만 다시 돌릴 수 있습니다. 상태표에 실패하면 이쪽으로 가라는 화살표를 그려 두면 오류가 났을 때 대체 경로나 재시도로 자동으로 넘어가고, 사람의 승인을 기다리는 단계도 끼워 넣을 수 있습니다.

Step Functions가 이 상태표 역할을 하고, 각 단계의 실제 일은 Lambda 함수가 맡습니다.

결국 Step Functions 연동은 긴 작업을 잘게 나눠 상태로 기록하고, 그 상태를 근거로 다음 Lambda를 호출하는 방식입니다. 함수는 한 단계만 책임지고 순서와 재시도는 상태 기계가 책임집니다.

사가 패턴

여러 서비스의 작업을 되돌릴 수 있게 설계하는 방법

여러 서비스에 걸친 작업은 중간이 실패하면 앞서 성공한 작업이 이미 데이터를 바꿔 놓은 상태로 남습니다. 하나의 트랜잭션으로 묶어 되돌릴 수 있으면 좋겠지만 서비스마다 저장소가 달라 그럴 수 없으므로, 사가 패턴(saga pattern)은 각 단계에 되돌리는 작업을 짝지어 두고 실패하면 앞 단계를 역순으로 취소합니다.

여행 예약 비유로 보면, 항공권과 호텔과 렌터카를 따로 예약하는데 렌터카만 매진이라면 예약 담당자가 호텔 취소와 항공권 취소를 차례로 처리해야 합니다. 이때 각 예약처는 자기가 받은 예약 번호를 기억하고 있어야 취소가 가능하므로, 예약을 걸 때 그 번호를 함께 남겨 두는 것이 핵심입니다. 취소 자체가 실패할 수도 있으므로 취소는 몇 번까지 다시 시도할지 정해 두고, 끝내 안 되면 사람이 손봐야 할 목록으로 넘깁니다.

Lambda에서는 보통 Step Functions가 정방향 단계와 보상(compensation) 단계를 짝지어 실행하는 방식으로 이 구조를 만듭니다.

결국 사가 패턴은 되돌릴 수 없는 일을 억지로 되돌리는 대신, 되돌리는 일을 미리 단계로 준비해 두는 설계입니다. 그래서 단계를 설계할 때는 이 단계가 실패하면 무엇을 취소해야 하는가를 항상 함께 적어 둡니다.

이벤트 기반 아키텍처

서로를 직접 부르지 않고 사건으로 연결하는 구조

온라인 쇼핑몰에서 주문이 들어올 때 주문 담당 서비스가 결제, 재고, 배송, 알림 담당 서비스를 모두 직접 호출한다고 가정해 보겠습니다. 이 방식은 서비스가 늘어날수록 호출 관계가 거미줄처럼 얽혀, 담당 서비스 하나만 느려져도 주문 전체가 멈추는 곤란을 만듭니다.

이 문제를 푸는 구조가 이벤트 기반 아키텍처(event-driven architecture)이며, 사건이 생기면 그 사실을 게시판에 붙이고 필요한 사람만 가져가 보는 방식입니다. 아파트 관리사무소에 비유하면, 입주민이 이사 사실을 접수 창구에 알리면 관리사무소가 그 내용을 공용 게시판에 한 번 붙이고, 엘리베이터 예약 담당과 주차 담당과 청소 담당이 각자 게시판을 보고 자기 일만 처리합니다. 주문 서비스는 '주문이 생성되었다'는 사건(event)만 게시하고, 결제 담당은 결제할 일이 있을 때, 재고 담당은 재고를 줄일 일이 있을 때 각자 그 게시물을 구독해 가져갑니다.

그래서 새 담당이 필요하면 게시판을 보는 사람만 추가하면 되고, 이미 붙은 게시물을 다시 쓰지 않아도 됩니다.

정리하면 이벤트 기반 아키텍처는 서비스끼리 직접 호출하는 대신 사건을 게시하고 구독하는 느슨한 연결(loose coupling)로 시스템을 잇는 설계입니다. 대신 게시판을 거치는 만큼 순서가 뒤바뀌거나 같은 사건이 두 번 도착할 수 있어, 그 점을 견디도록 만드는 일이 함께 필요합니다.

API 백엔드 구성

화면과 앱 뒤에서 요청을 처리하는 전형적인 조합

앱 화면에서 로그인 버튼을 누르면 화면이 서버에 요청을 보내고 응답을 받아 화면을 바꾸는데, 그 뒤에서 요청을 받아 처리하는 부분이 없으면 화면은 아무것도 할 수 없습니다. 이 뒤쪽 부분을 만드는 전형적인 조합이 API 백엔드 구성(API backend)이며, API는 프로그램끼리 정해진 형식으로 요청과 응답을 주고받는 접점을 뜻합니다.

식당에 비유하면 홀 직원이 주문을 받아 주방에 전달하고, 주방은 재료를 꺼내 조리해 다시 홀으로 내보내며, 계산대는 값을 치르고 영수증을 남깁니다. 여기서 홀 직원이 요청을 받는 접점(API 게이트웨이), 주방이 실제 규칙을 처리하는 응용 로직(application logic), 창고가 데이터를 보관하는 데이터베이스, 계산대가 사용자 확인과 권한 검사를 맡는 인증 계층에 해당합니다. 요청이 들어오면 먼저 입구에서 형식이 맞는지와 권한이 있는지 확인하고, 통과한 요청만 로직으로 넘겨 필요한 데이터를 꺼내 처리한 뒤 정해진 형식으로 응답을 돌려줍니다. 이렇게 역할을 나눠 두면 화면을 바꾸지 않고도 주방 설비를 늘리거나 교체할 수 있습니다.

정리하면 API 백엔드 구성은 요청을 받는 입구, 규칙을 처리하는 로직, 데이터를 보관하는 저장소, 신원을 확인하는 인증 계층을 분리해 잇는 구조입니다. 화면은 정해진 약속만 지키면 되고, 뒤쪽은 그 약속을 지키는 범위 안에서 자유롭게 바꿀 수 있습니다.

파일 처리 파이프라인

업로드된 파일을 검증·변환·저장하는 흐름

사용자가 사진이나 문서를 올리면 그 파일을 그대로 저장하는 경우가 많은데, 형식이 깨졌거나 지나치게 큰 파일이 섞여 들어오면 이후 화면에서 열리지 않거나 저장 공간이 금세 차 버립니다. 그래서 업로드된 파일을 검증하고 변환하고 저장하는 단계를 순서대로 이어 붙인 구조가 필요한데, 이것이 파일 처리 파이프라인(file processing pipeline)입니다.

택배 물류센터에 비유하면, 물건이 들어오면 먼저 크기와 포장 상태를 확인하고, 규격에 맞는 것은 분류 벨트를 지나며 용도별 상자로 다시 포장되고, 마지막에 창고의 정해진 선반에 올라갑니다. 이때 입구 검사가 파일 형식과 크기와 악성 코드를 확인하는 검증 단계, 벨트 위 재포장이 이미지 축소나 문서 형식 변환 같은 변환 단계, 선반 배치가 저장소에 넣고 주소를 기록하는 저장 단계에 해당합니다. 각 단계는 앞 단계의 결과만 받아 처리하므로, 검증에서 걸러진 파일은 뒤 단계로 가지 않고 바로 반려됩니다.

단계마다 실패한 파일을 따로 모아 두면 어느 지점에서 문제가 생겼는지도 금방 알 수 있습니다.

정리하면 파일 처리 파이프라인은 검증, 변환, 저장을 독립된 단계로 나눠 순서대로 통과시키는 흐름입니다. 단계를 나눠 두면 일부만 다시 처리하거나 새 형식을 중간에 끼워 넣기도 쉬워집니다.

주기적 배치 작업

정해진 시간에 도는 작업을 안전하게 만드는 설계

매일 새벽에 정산 리포트를 만들거나 매주 오래된 로그를 지우는 일을 사람이 매번 손으로 하면 언젠가 반드시 빠뜨리게 됩니다. 정해진 시간에 자동으로 도는 작업을 안전하게 만드는 설계가 주기적 배치 작업(periodic batch job)이며, 배치는 여러 건을 모아 한 번에 처리한다는 뜻입니다.

아파트에 비유하면 매주 화요일 아침 정해진 시간에 청소반이 각 층을 도는 일과 같으며, 시간이 되면 자동으로 출발하고 어제 어디까지 했는지 기록을 보고 이어서 하며, 끝나면 관리사무소에 완료 보고를 남깁니다. 배치 작업도 같은데, 정해진 시각에 실행을 걸어 두는 스케줄러(scheduler), 지난번에 처리한 지점을 적어 두는 체크포인트(checkpoint), 실패하면 같은 지점부터 다시 시작하는 재시도 장치가 그 역할을 나눠 맡습니다. 사람이 아직 자고 있는 새벽에 도는 일이므로, 같은 작업이 두 번 실행되지 않도록 잠금(lock)을 걸고 오래 걸리는 작업은 중간에 상태를 남기는 것이 안전합니다.

또 작업이 겹치지 않게 앞 작업이 끝났는지 확인하거나, 겹쳐도 결과가 같도록 만드는 편이 좋습니다.

정리하면 주기적 배치 작업은 스케줄러로 실행 시점을 정하고, 체크포인트와 재시도와 잠금으로 중단과 중복을 견디게 만드는 설계입니다. 시간에 맞춰 도는 것보다, 중간에 죽어도 안전하게 다시 이어지는 것이 더 중요합니다.

멱등성

같은 요청이 두 번 와도 결과가 한 번과 같게 만드는 방법

결제 요청을 보냈는데 응답이 오지 않아 다시 보냈더니 같은 결제가 두 번 찍히는 일이 실제로 일어납니다. 같은 요청이 두 번 와도 결과가 한 번 온 것과 같게 만드는 성질을 멱등성(idempotency)이라고 합니다.

엘리베이터 호출 버튼에 비유하면, 한 번 누르든 다섯 번 누르든 엘리베이터는 한 대만 오며, 이미 호출된 상태에서 또 눌러도 새로운 호출이 쌓이지 않습니다. 멱등성이 있는 요청도 이와 같아서, 요청마다 고유한 식별자(request id)를 붙여 두고 이미 처리한 식별자는 다시 처리하지 않고 앞서 보낸 결과를 그대로 돌려줍니다. 결제처럼 한 번만 일어나야 하는 일은 '아직 없으면 만들고, 있으면 그대로 둔다'는 조건부 쓰기로 처리하고, 취소나 삭제는 여러 번 해도 결과가 같도록 만듭니다.

반대로 조회는 몇 번을 해도 값이 바뀌지 않으므로 원래부터 멱등하고, 더하기처럼 부를 때마다 값이 커지는 연산은 멱등하지 않습니다.

정리하면 멱등성은 같은 요청이 여러 번 도착해도 시스템의 최종 상태가 한 번 처리한 것과 같아지는 성질입니다. 재시도가 필요한 분산 환경에서는 이 성질을 설계에 넣어 두어야 중복 피해를 막을 수 있습니다.

중복 처리 방지

재시도와 경쟁 상황에서 중복을 걸러내는 실제 기법

네트워크가 잠깐 끊기면 프로그램은 실패로 판단하고 같은 요청을 다시 보내는데, 실제로는 앞의 요청이 이미 성공했을 수 있습니다. 이런 재시도와 동시 요청 속에서 같은 일이 두 번 처리되지 않게 걸러내는 실제 기법이 중복 처리 방지(duplicate prevention)입니다.

행사 입장에 비유하면, 입구에서 손목에 팔찌를 채우고 이미 팔찌가 있는 사람은 다시 줄을 서지 않고 그대로 들여보내며, 팔찌를 채우는 순간은 한 사람만 잡을 수 있는 자물쇠로 지킵니다. 중복 처리 방지도 이렇게 여러 겹으로 만드는데, 먼저 요청에 붙은 고유 키를 저장소에 기록해 이미 본 키인지 확인하고, 두 요청이 거의 동시에 들어오면 그 키에 잠금을 걸어 하나만 통과시킵니다. 처리가 끝난 키는 일정 기간 보관해 두었다가 지우며, 보관 기간은 재시도가 일어날 수 있는 시간보다 넉넉하게 잡습니다.

또 결과를 저장할 때 고유 제약 조건을 걸어 두면, 확인과 쓰기 사이에 다른 요청이 끼어드는 틈을 데이터베이스가 마지막으로 막아 줍니다.

정리하면 중복 처리 방지는 고유 키 기록, 잠금, 저장소의 고유 제약이라는 여러 겹으로 같은 일이 두 번 처리되는 것을 막는 기법입니다. 확인만으로는 부족하고 마지막 쓰기 지점에서 한 번 더 막아 두어야 경쟁 상황에서도 안전합니다.

코드로 인프라 관리

CloudFormation과 CDK로 함수를 정의하는 방법

함수 하나를 콘솔에서 손으로 만들고 설정을 클릭으로 바꾸다 보면, 누가 언제 무엇을 바꿨는지 아무도 모르는 상태가 됩니다. 그래서 Amazon Lambda에서는 함수와 그 주변 설정을 클릭이 아니라 코드 파일에 적어 두고 그것을 읽혀 만들게 하는 코드로 인프라 관리(Infrastructure as Code) 방식을 씁니다. 이것은 아파트를 지을 때 벽돌을 손으로 하나씩 쌓지 않고 도면을 먼저 그리는 것과 같습니다. 도면에는 방이 몇 개인지, 어느 방에 수도관이 지나가는지가 적혀 있어서 시공자는 그 도면만 보고 똑같은 집을 몇 번이고 다시 지을 수 있습니다.

이때 CloudFormation은 도면을 읽고 실제로 집을 올리는 시공자에 해당하고, CDK는 그 도면을 파이썬이나 타입스크립트처럼 익숙한 언어로 그리게 해 주는 도구입니다. CDK로 쓴 코드는 결국 CloudFormation이 알아듣는 도면으로 번역되어, 함수의 메모리 크기와 실행 시간, 권한 같은 항목이 한곳에 모입니다. 정리하면 CloudFormation은 인프라를 선언적으로 적은 템플릿을 읽어 실제 자원을 만들고, CDK는 그 템플릿을 프로그래밍 언어로 작성하게 해 주는 상위 도구입니다.

SAM 템플릿 배포

서버리스 전용 도구로 빌드와 배포를 묶는 방법

CloudFormation 도면을 직접 쓰면 함수 코드를 압축해 올리고 권한과 이벤트 연결까지 손으로 엮어야 해서, 배포 한 번에 여러 단계를 사람이 순서대로 밟게 됩니다. 그 단계를 줄이려고 나온 것이 서버리스 응용 프로그램 모델(Serverless Application Model, SAM)이며, SAM 템플릿은 함수 배포에 필요한 내용을 짧게 적고 빌드와 배포를 한 도구로 묶는 서버리스 전용 방식입니다. 이것은 택배를 보낼 때 물건을 상자에 넣고, 송장을 붙이고, 배송 접수까지 따로따로 하던 일을 한 창구에서 끝내는 것과 같습니다. SAM 템플릿에는 함수가 어떤 코드 폴더에서 나오는지, 어떤 사건에 반응하는지, 어떤 권한이 필요한지가 짧은 항목으로 적힙니다.

sam build는 그 폴더의 코드와 필요한 라이브러리를 모아 배포할 수 있는 묶음으로 만들고, sam deploy는 그 묶음을 올려 CloudFormation이 실제 자원을 만들도록 넘깁니다. 덕분에 사람이 기억해야 할 것은 클릭 순서가 아니라 템플릿 파일 하나가 됩니다. 결국 SAM은 CloudFormation 템플릿의 서버리스용 축약 표현이고, sam build와 sam deploy가 코드 준비와 자원 생성을 이어 주는 도구입니다.

CI/CD 파이프라인

코드를 올리면 자동으로 검사하고 배포하는 흐름

함수를 고쳐서 올릴 때마다 누군가가 손으로 검사를 돌리고 배포 명령을 치다 보면, 바쁜 날에는 검사를 건너뛰거나 순서를 틀리는 일이 생깁니다. 그래서 코드 저장소에 변경이 올라오면 자동으로 검사하고 배포까지 이어 주는 흐름, 곧 CI/CD 파이프라인을 씁니다. 이것은 공장의 컨베이어 벨트와 같습니다. 벨트 위에 부품이 올라가면 정해진 자리마다 검사대와 조립대가 있어서, 사람이 매번 지시하지 않아도 같은 순서로 같은 일이 벌어집니다.

이때 CI(지속적 통합)는 올라온 코드를 받아 빌드하고 테스트하는 검사대에 해당하고, CD(지속적 전달 또는 지속적 배포)는 검사를 통과한 부품을 실제 환경에 올리는 조립대에 해당합니다. 불량 부품이 검사대에서 걸리면 벨트가 멈추고 뒤 단계로 넘어가지 않으므로, 나쁜 코드가 운영 환경에 도달하지 못합니다. 정리하면 CI/CD 파이프라인은 코드 변경을 빌드와 테스트, 배포 단계로 자동 연결한 흐름이고, 이 흐름을 Lambda 배포에 붙이면 사람은 코드를 올리는 일만 하면 됩니다.

가중치 배포

트래픽을 조금씩 새 버전으로 옮기는 방법

새 버전의 함수를 한 번에 전부 바꾸면, 문제가 있을 때 사용자 전원이 동시에 영향을 받습니다. 그래서 트래픽의 일부만 새 버전으로 보내 보고 조금씩 비중을 늘리는 가중치 배포, 곧 카나리 배포나 선형 배포 같은 방식을 씁니다. 이것은 식당에서 새 메뉴를 내기 전에 손님 몇 명에게만 먼저 내보는 것과 같습니다. 처음에는 열 명 중 한 명에게만 새 메뉴를 주고, 아무도 탈이 나지 않으면 절반에게, 그다음 전부에게 내놓는 식입니다.

Lambda에서는 버전 두 개를 가리키는 별칭(alias)에 가중치를 적어 두고, 그 비율만 바꾸면 됩니다. 손님 반응이 이상하면 가중치를 0으로 되돌리는 것만으로 새 메뉴를 즉시 걷어낼 수 있습니다. 결국 가중치 배포는 별칭에 붙은 두 버전 사이의 트래픽 비율을 단계적으로 옮기는 방식이고, 문제가 드러나는 범위를 좁힐 수 있다는 점이 핵심입니다.

자동 롤백

배포가 잘못됐을 때 이전 상태로 되돌리는 장치

배포한 새 버전이 조용히 실패하기 시작하면, 사람이 알아채기까지 몇 분에서 몇 시간 동안 오류가 쌓입니다. 그래서 미리 정한 지표가 나빠지면 배포를 스스로 되돌리는 자동 롤백 장치를 겁니다. 이것은 건물 천장에 달린 스프링클러와 같습니다. 불이 나면 사람이 신고하기를 기다리지 않고 열을 감지한 장치가 스스로 물을 뿌리듯, 배포 도구도 오류율이나 지연 시간 같은 지표를 지켜보다가 정한 선을 넘으면 이전 버전으로 트래픽을 되돌립니다. AWS에서는 CodeDeploy 같은 배포 도구에 경보(alarm)를 연결해 두고, CloudWatch가 그 경보를 울리면 롤백이 실행되게 구성합니다. 되돌린 뒤에는 무엇이 문제였는지 알림이 남으므로 다음 배포에서 같은 실수를 줄일 수 있습니다. 정리하면 자동 롤백은 배포 중 감시하던 지표가 기준을 벗어날 때 이전 버전으로 자동 복귀시키는 장치이고, 사람의 대응 속도에 기대지 않는다는 점이 다릅니다.

버전과 별칭 운영 규칙

여러 환경에서 버전을 어떻게 매기고 쓰는지

함수를 고칠 때마다 같은 이름을 그대로 덮어쓰면, 지금 운영 중인 코드가 어느 시점의 것인지 알 수 없고 되돌릴 지점도 사라집니다. 그래서 Lambda에서는 코드 묶음마다 번호를 붙이는 버전(version)과, 그 번호를 가리키는 이름표인 별칭(alias)을 나눠 씁니다. 이것은 아파트의 호수와 안내판의 관계와 같습니다. 호수는 101동 1001호처럼 한 번 정해지면 바뀌지 않는 고유한 주소이고, 안내판에는 관리사무소나 경비실처럼 그 주소를 가리키는 이름이 적힙니다.

Lambda의 버전은 배포할 때마다 새 번호가 붙고 한 번 만들어진 내용은 바뀌지 않으며, 별칭은 prod나 dev 같은 이름으로 특정 번호를 가리킵니다. 그래서 새 버전을 올릴 때 별칭이 가리키는 번호만 바꾸면, 호출하는 쪽은 같은 이름을 계속 쓰면서도 다른 코드를 실행하게 됩니다. 결국 버전은 바뀌지 않는 코드 스냅샷 번호이고 별칭은 그것을 가리키는 고정된 이름이며, 환경마다 별칭을 나눠 두면 배포와 되돌리기가 이름 하나를 바꾸는 일로 줄어듭니다.

설정값 관리

환경마다 다른 값을 안전하게 주입하는 방법

코드 안에 데이터베이스 주소나 비밀번호를 그대로 적어 두면, 개발 환경에서는 잘 돌던 함수가 운영 환경에 올라가는 순간 엉뚱한 곳에 접속하거나 아예 시작조차 하지 못합니다. 값이 바뀔 때마다 코드를 고치고 다시 배포해야 하는 일도 반복되고, 그 값을 아무나 볼 수 있는 저장소에 남기는 보안 사고로도 이어집니다. 그래서 코드는 그대로 두고 환경마다 다른 값만 바깥에서 갈아 끼우는 설정값 관리(Configuration Management)가 필요합니다.

아파트 단지에 같은 설계도로 지은 건물이 여러 동 있어도, 각 세대의 우편함 열쇠와 관리비 계좌는 따로인 것과 같습니다. 건물 도면은 하나로 공유하지만, 세대별 정보는 관리사무소가 따로 보관하고 입주할 때 해당 세대에만 전달합니다. 함수도 마찬가지로 로직이라는 도면은 하나이고, 주소·비밀번호·한도 같은 값은 환경 변수(Environment Variable)라는 각 세대의 우편함에 넣어 두었다가 실행할 때 꺼내 씁니다.

그래서 같은 코드를 개발·검증·운영이라는 서로 다른 동에 그대로 올려도, 각 동의 우편함에 든 값에 따라 다르게 동작합니다.

정리하면 설정값 관리는 코드와 환경 의존 값을 분리하는 설계이고, 실제로는 환경 변수나 별도의 설정 저장소에 값을 두고 실행 시점에 주입하는 방식으로 구현됩니다.

테스트 전략

단위·통합·부하 테스트를 어디까지 어떻게 할지

테스트를 아예 하지 않으면 작은 수정 하나가 결제나 로그인 같은 핵심 기능을 조용히 망가뜨리고, 그 사실을 사용자가 먼저 알게 됩니다. 반대로 모든 것을 손으로 확인하려 하면 배포할 때마다 몇 시간이 사라지고, 확인하는 사람이 바뀔 때마다 결과도 달라집니다. 그래서 어디까지를 자동으로, 어느 수준에서 검사할지를 미리 정해 두는 테스트 전략(Test Strategy)이 필요합니다.

자동차 공장의 검사 과정을 떠올리면 이해가 쉽습니다. 부품 하나하나가 규격에 맞는지 확인하는 단계가 단위 테스트(Unit Test)이고, 부품을 조립한 뒤 시동이 걸리고 계기판이 정상인지 보는 단계가 통합 테스트(Integration Test)입니다. 마지막으로 실제 도로에서 무거운 짐을 싣고 오래 달려 보는 단계가 부하 테스트(Load Test)입니다.

공장은 부품 검사에 가장 많은 검사를 배치하고, 조립 검사는 연결부 위주로 추리고, 주행 시험은 출시 전 몇 번만 합니다. 이렇게 층마다 목적을 나누면 빠르게 자주 돌릴 검사와 오래 걸리지만 꼭 필요한 검사를 구분할 수 있습니다.

결국 테스트 전략은 단위 테스트로 빠른 피드백을 확보하고, 통합 테스트로 구성 요소 사이의 연결을 확인하며, 부하 테스트로 실제 트래픽에서의 한계를 재는 역할 분담입니다.

로컬 테스트의 한계

내 PC에서 돌린 결과와 실제 환경이 다른 이유

내 컴퓨터에서 모든 테스트를 통과한 함수가 배포 직후 실패하는 일은 흔합니다. 그 이유는 로컬 환경이 실제 운영 환경과 겉모습만 비슷할 뿐, 네트워크 지연·권한·데이터 양·동시에 들어오는 요청 수 같은 조건이 전혀 다르기 때문입니다. 로컬 테스트의 한계를 아는 것이 배포 후 사고를 줄이는 출발점입니다.

실내 연습장에서 완벽하게 뜬 수영 동작이 바다에서 그대로 통하지 않는 것과 같습니다. 연습장은 물 깊이와 파도가 정해져 있고 옆 사람도 없지만, 바다는 조류가 있고 물온도가 다르며 예상치 못한 파도가 밀려옵니다.

로컬 실행 환경은 잔잔한 연습장이고, 운영 환경은 조건이 계속 변하는 바다입니다. 게다가 연습장에서는 내가 혼자 헤엄치지만, 운영에서는 수많은 사용자가 동시에 같은 자원을 두고 경쟁합니다.

그래서 로컬 테스트는 문법 오류나 논리 실수를 빠르게 걸러 주는 용도로 쓰고, 실제 환경과 비슷한 조건에서의 확인은 별도의 검증 환경이나 소량의 실제 트래픽을 흘려보내는 방식으로 보완해야 합니다.

릴리스 체크리스트

배포 전후에 반드시 확인해야 할 항목

배포 당일에는 긴장과 서두름 때문에 방금 전까지 알고 있던 것도 빠뜨리기 쉽습니다. 환경 변수 하나를 넣지 않았거나, 되돌릴 방법을 준비하지 않은 채 새 버전을 올려 장애가 길어지는 사고가 여기서 나옵니다. 그래서 배포 전후에 확인할 항목을 순서대로 적어 둔 릴리스 체크리스트(Release Checklist)가 필요합니다.

비행기가 이륙하기 전에 조종사가 같은 항목을 소리 내어 확인하는 절차와 같습니다. 경험이 많은 조종사도 연료량과 계기 상태를 눈으로 다시 확인하는데, 그것은 기억을 믿지 않고 절차를 믿기 위해서입니다.

체크리스트의 앞부분은 이륙 전 점검처럼 배포 전 확인에 해당하고, 뒷부분은 이륙 후 이상 유무를 살피는 배포 후 확인에 해당합니다. 그리고 문제가 생겼을 때 비상 절차가 정해져 있듯, 이전 버전으로 되돌리는 방법도 목록에 함께 적어 둡니다.

정리하면 릴리스 체크리스트는 설정·권한·백업·롤백 수단을 배포 전에, 핵심 지표와 오류 로그를 배포 후에 확인하도록 순서를 고정해 두는 절차입니다.

타임아웃 원인 찾기

함수가 끝나지 않을 때 어디를 의심해야 하는지

함수가 응답 없이 시간만 흘러 결국 타임아웃(Timeout)으로 끝나는 상황은 원인이 겉으로 드러나지 않아 가장 찾기 어렵습니다. 코드에 분명한 오류가 있으면 로그에 남기라도 하지, 그냥 멈춰 있는 경우에는 어디서 멈췄는지조차 알기 어렵습니다. 그래서 시간이 어디에 쓰였는지를 구간별로 나눠 보는 접근이 필요합니다.

택배가 약속한 날 오지 않을 때를 떠올리면 좋습니다. 택배가 안 온 이유는 물건이 없어서일 수도, 출발지에서 분류가 밀려서일 수도, 배송 기사가 주소를 못 찾아서일 수도 있습니다. 추적 번호로 어느 구간에서 멈췄는지 확인하지 않으면, 집 앞에서만 기다리며 헛수고를 하게 됩니다.

함수도 같아서 바깥 서비스 호출, 데이터베이스 조회, 외부 결제 승인 같은 구간마다 걸린 시간을 따로 재 두면 어느 구간에서 멈췄는지 드러납니다.

결국 타임아웃을 찾는 일은 전체 시간을 줄이는 일이 아니라, 외부 호출 구간별 소요 시간과 재시도 횟수를 로그로 남겨 병목 구간을 좁혀 가는 일입니다.

메모리 부족 오류

메모리를 올려야 하는 상황과 아닌 상황 구분

함수가 처리하던 중 갑자기 메모리 부족(Out of Memory) 오류로 죽으면, 로그에는 원인이 남지 않고 실행이 그대로 끊깁니다. 어떤 요청은 성공하고 어떤 요청은 실패하는 식으로 들쭉날쭉해지고, 원인을 찾으려 로그를 뒤져도 남은 것이 거의 없습니다. 이때 무조건 메모리를 늘리는 것이 답인지 아닌지를 구분하는 것이 중요합니다.

좁은 책상에서 서류를 정리하는 상황을 생각해 보면 차이가 분명해집니다. 책상이 좁아서 서류가 쌓이는 것이 문제라면 책상을 넓히는 것이 맞습니다. 하지만 서류를 버리지 않고 계속 쌓아 두거나, 같은 서류를 여러 벌 복사해 두는 것이 문제라면 책상을 아무리 넓혀도 곧 다시 꽉 찹니다.

메모리도 마찬가지로, 처리해야 할 데이터가 원래 큰 경우에는 할당량을 늘리는 것이 맞지만, 쓰고 난 뒤에도 붙잡고 있거나 한 번에 전체를 읽어 들이는 구조라면 할당량을 늘려도 잠깐 버틸 뿐입니다.

그래서 메모리 부족 오류를 만나면 먼저 큰 데이터를 한 번에 올리는지, 참조를 오래 잡고 있는지를 확인하고, 그런 구조적 원인이 없을 때 할당 메모리를 늘리는 것이 순서입니다.

권한 오류 진단

접근이 거부될 때 어느 정책을 봐야 하는지

함수 코드는 멀쩡한데 호출할 때마다 접근이 거부된다는 응답만 돌아오면 어디를 손대야 할지 막막합니다. 권한 오류 진단은 이런 거부를 정책 문서라는 관점에서 추적하는 작업으로, Amazon Lambda(아마존 람다)의 실행 역할(execution role)과 정책(policy) 체계 안에서 이뤄집니다.

회사 건물에 들어가려면 출입증이 필요한데, 정문 경비가 보는 명단과 각 부서 문 앞의 잠금장치가 따로 관리되는 상황을 떠올리면 이해가 쉽습니다.

출입증에 적힌 허용 범위가 실행 역할에 붙은 정책이고, 부서 문 앞의 잠금장치는 S3 버킷이나 데이터베이스처럼 접근을 받는 쪽에 붙은 리소스 기반 정책(resource-based policy)입니다. 두 명단 가운데 한 곳에서라도 허용되지 않으면 문은 열리지 않으므로, 거부 메시지에는 어느 쪽이 막았는지가 함께 적혀 나옵니다. 또 출입증이 아예 없는 경우보다 담당이 바뀐 사람이 엉뚱한 문을 여는 경우가 많아서, 실제 호출이 어떤 역할로 나가는지부터 확인하는 것이 순서입니다.

정리하면 권한 오류는 실행 역할의 정책과 대상 리소스의 정책을 차례로 대조해 허용 지점이 빠진 곳을 찾아내는 진단입니다. 함수 코드를 고치기 전에 두 정책 문서를 먼저 읽어야 합니다.

VPC 네트워크 오류

사설망에 넣은 함수가 바깥과 통신하지 못할 때

함수를 사설망(VPC)에 넣었더니 바깥 인터넷도 다른 서비스도 닿지 않아 시간 초과만 쌓이는 경우가 있습니다. VPC 네트워크 오류는 함수가 놓인 사설 서브넷(subnet)에서 바깥으로 나가는 길이 어디서 끊겼는지 찾는 점검입니다.

경비실이 있는 아파트 단지로 이사했는데 현관은 열리지만 단지 정문에서 나가는 길이 막힌 상황을 생각하면 됩니다.

함수가 사는 동이 서브넷이고, 단지 안에서만 통하는 내부 도로가 라우팅 테이블(route table)이며, 바깥 도로로 나가려면 NAT 게이트웨이(gateway)나 인터넷 게이트웨이라는 정문을 반드시 거쳐야 합니다. 여기에 더해 각 동 출입문에 걸린 보안 그룹(security group)이 누구를 들일지 정하므로, 나가는 길과 들어오는 길을 따로 봐야 합니다. 사설 주소만으로 다른 클라우드 서비스에 닿게 하려면 VPC 엔드포인트(endpoint)라는 전용 통로를 두었는지도 확인해야 합니다.

결국 VPC 네트워크 오류는 서브넷의 라우팅, 정문 역할의 게이트웨이, 출입문 역할의 보안 그룹을 차례로 짚는 진단입니다. 함수 코드보다 함수가 사는 길부터 확인하는 편이 빠릅니다.

의존성과 임포트 오류

배포 후 코드가 시작조차 못 할 때의 원인

배포는 성공했다는데 호출하자마자 시작조차 못 하고 오류가 나면 코드 로직을 의심하게 됩니다. 의존성과 임포트 오류는 함수가 첫 줄을 실행하기 전에 준비 단계에서 넘어지는 경우로, 배포 묶음과 실행 환경(runtime) 구성의 문제입니다.

가구를 조립하려는데 설명서에 적힌 부품이 상자에 없거나, 설명서가 다른 나라 말로 쓰인 상황을 떠올리면 됩니다.

배포 묶음(package)에 라이브러리가 빠졌거나 폴더 구조가 달라 임포트(import) 경로가 어긋나면 부품이 없는 셈이고, 실행 환경의 버전과 라이브러리가 요구하는 버전이 다르면 설명서가 맞지 않는 셈입니다. 여러 함수가 함께 쓰는 라이브러리는 계층(layer)으로 분리해 두었다가 경로가 실제로 잡히는지 확인해야 합니다. 처리를 시작할 함수를 가리키는 핸들러(handler) 이름이 파일명이나 함수명과 한 글자라도 다르면 같은 방식으로 시작 단계에서 멈춥니다.

정리하면 이 오류는 배포 묶음의 라이브러리, 실행 환경의 버전, 핸들러 경로라는 세 지점을 확인하는 문제입니다. 기록의 첫 오류 줄이 어느 부품이 없는지를 알려주는 단서입니다.

동시성 초과와 스로틀링

요청이 거절될 때 무엇을 늘려야 하는지

갑자기 요청이 몰리는 시간대에만 호출이 거절되고 나머지 시간에는 멀쩡하다면 코드보다 용량을 먼저 봐야 합니다. 동시성 초과와 스로틀링(throttling)은 정해진 수량을 넘는 요청을 서비스가 일부러 돌려보내는 상태입니다.

창구가 다섯 개뿐인 은행에 손님이 스무 명 몰리면 줄을 서거나 번호표를 받지 못하고 돌아가는 상황과 같습니다.

동시성(concurrency)은 지금 처리 중인 요청 수이고, 계정 전체에 허용된 총량과 함수별로 미리 떼어 둔 예약된 동시성(reserved concurrency)이 창구 수를 정합니다. 창구를 늘리는 가장 직접적인 방법은 한도를 올리는 것이지만, 뒤쪽 데이터베이스가 감당할 수 있는 양을 함께 봐야 합니다. 반대로 특정 함수가 전체 창구를 독점하지 않도록 예약된 동시성을 나눠 두면 다른 업무가 굶주리지 않습니다.

결국 스로틀링은 동시 실행 한도와 예약된 동시성 설정을 보고 늘릴 양과 나눌 양을 정하는 문제입니다. 거절은 오류가 아니라 용량이 한계에 닿았다는 신호로 읽어야 합니다.

이벤트 유실과 재처리

처리되지 않은 이벤트를 찾아 다시 돌리는 방법

이벤트가 들어왔다는 기록은 있는데 처리 결과가 없는 건이 발견되면 어디서 사라졌는지 찾기 어렵습니다. 이벤트 유실과 재처리는 처리에 실패한 이벤트를 남겨 두고 다시 돌리는 절차로, 비동기 호출의 재시도 구조 안에서 다뤄집니다.

택배 배달에 실패했을 때 기사가 물건을 버리지 않고 보관소에 쌓아 두었다가 다음 날 다시 배달하는 모습을 떠올리면 됩니다.

함수 호출이 실패하면 서비스가 정해진 횟수만큼 자동으로 다시 시도하고, 그래도 안 되면 배달 불가 물건처럼 실패 대기열(dead-letter queue, DLQ)이나 실패 목적지(destination)로 넘깁니다. 그 보관소에 쌓인 이벤트를 꺼내 원인을 고친 뒤 다시 호출하는 것이 재처리입니다. 스트림을 읽는 방식에서는 어디까지 읽었는지 표시하는 지점이 있어서, 실패한 이벤트를 건너뛰었는지 같은 자리에서 멈췄는지를 그 표시로 판단합니다.

정리하면 유실을 막는 핵심은 실패한 이벤트를 버리지 않고 실패 대기열이나 목적지에 남기는 설정입니다. 남겨 둔 이벤트를 원인 수정 뒤 다시 호출하는 일이 재처리입니다.

로그가 보이지 않을 때

실행 기록이 사라진 것처럼 보이는 상황의 점검 순서

함수가 분명히 실행됐는데 로그 화면에는 아무것도 없어서 실행 자체가 없었던 것처럼 보이는 상황이 있습니다. 로그가 보이지 않을 때의 점검은 CloudWatch(클라우드워치) 로그로 기록이 흘러가는 경로를 따라가는 작업입니다.

부서에서 보고서를 작성했는데 중앙 문서고에는 아무것도 없는 상황을 생각하면 됩니다.

함수가 로그를 쓰려면 실행 역할에 로그 그룹(log group)과 로그 스트림(stream)을 만들 권한이 있어야 하고, 이 권한이 없으면 기록은 오류 없이 조용히 버려집니다. 기록이 쌓이는 지역(region)과 화면에서 보고 있는 지역이 다르거나, 로그 그룹의 보존 기간(retention)이 짧아 오래된 기록이 지워졌을 수도 있습니다. 또 함수가 남기는 출력의 형식이 로그로 인식되는 형식과 달라 화면의 내용이 비어 보이는 경우도 있습니다.

결국 로그 공백은 실행 역할의 로그 권한, 지역과 로그 그룹, 보존 기간을 차례로 확인해 기록이 놓인 자리를 찾는 일입니다. 화면이 비어 있다는 것과 실행이 없었다는 것은 다르므로 권한부터 봐야 합니다.

서비스 할당량

계정과 리전에 걸린 한도와 늘리는 방법

평소 잘 돌던 서비스가 갑자기 배포에 실패하면서 로그에 동시 실행 한도를 넘었다는 오류만 남는다면, 코드를 아무리 들여다봐도 원인은 코드 밖에 있습니다. 이렇게 계정과 리전마다 미리 정해 둔 자원 사용 상한을 서비스 할당량(Service Quotas)이라고 부르며, AWS는 장애와 비용 폭주를 막으려고 이 한도를 기본값으로 걸어 둡니다.

아파트 단지에 들어오는 전기 계약 전력을 떠올리면 이해가 쉽습니다. 각 세대가 마음대로 전기를 끌어다 쓰면 단지 전체 변압기가 버티지 못하므로 관리사무소는 세대당 허용 용량을 정해 두고, 더 필요한 세대는 증설 신청서를 내야 합니다.

AWS도 마찬가지로 계정과 리전 조합마다 함수 동시 실행 수나 초당 요청 수 같은 허용량을 정해 두고, 그 안에서만 자원을 쓰도록 강제합니다. 한도에 가까워지면 지표와 알림으로 미리 알려 주고, 더 필요하면 Service Quotas 화면이나 지원 요청으로 상향을 신청해 승인을 받습니다.

결국 서비스 할당량은 리전별로 계정에 걸린 자원 사용의 상한선이며, 동시성(concurrency)이나 요청률 같은 값을 콘솔에서 확인하고 필요할 때 근거를 갖춰 올려 쓰는 운영 항목입니다.

리전과 가용성 설계

한 리전이 멈춰도 서비스가 살아 있게 만드는 방법

서비스가 한 리전에만 자리 잡고 있으면 그 리전의 데이터센터에 정전이나 네트워크 장애가 생기는 순간 전 세계 사용자가 동시에 접속 불능이 됩니다. 그래서 처음부터 리전 하나가 멈춰도 나머지가 일을 이어받도록 그리는 설계를 가용성 설계라고 하며, 리전과 가용 영역(Availability Zone)을 나눠 배치하는 것이 그 출발점입니다.

전국에 매장을 둔 편의점 체인을 떠올려 보면 구조가 겹칩니다. 한 도시의 매장이 화재로 문을 닫아도 다른 도시 매장이 계속 영업하고, 같은 도시 안에서도 여러 지점이 재고를 나눠 갖고 있어 한 지점이 멈춰도 손님은 옆 지점에서 물건을 삽니다.

리전은 도시에, 가용 영역은 그 도시 안의 개별 매장에 대응하며, 본사가 어느 매장으로 가라는 안내 표지판을 세우는 역할이 트래픽 라우팅(DNS 기반 라우팅)입니다. 매장마다 재고 장부를 똑같이 맞춰 두는 일이 데이터 복제에 해당하고, 평소에 다른 매장으로 손님을 돌려보는 훈련이 장애 조치(failover) 연습입니다.

정리하면 리전과 가용성 설계는 리전·가용 영역 단위로 자원을 흩어 두고 라우팅과 복제로 트래픽과 데이터를 넘겨, 한 지역의 장애가 전체 서비스 중단으로 번지지 않게 만드는 구조입니다.

다수의 함수 관리

함수가 수십 개로 늘었을 때 질서를 유지하는 방법

함수가 서너 개일 때는 콘솔에서 손으로 고쳐도 기억이 따라가지만, 수십 개로 늘어나면 어느 함수가 무엇을 하는지, 누가 마지막으로 배포했는지 아무도 답하지 못하는 상황이 옵니다. 이때 필요한 것이 이름 규칙과 공통 코드, 배포 자동화로 함수 무리를 질서 있게 유지하는 관리 방식입니다.

여러 요리를 동시에 만드는 대형 주방을 생각해 보면 좋습니다. 조리대가 늘어나도 레시피 카드에 요리 이름과 담당 구역을 같은 형식으로 적어 두면 누구든 바로 찾아 쓸 수 있고, 모든 요리에 공통으로 쓰는 육수는 한 솥에 만들어 나눠 쓰며, 주문이 들어오면 주방장이 정해진 순서대로 일을 내려 줍니다.

함수 이름과 태그(tag)를 일정한 규칙으로 붙이는 일이 레시피 카드에 해당하고, 공통 코드를 레이어(Layer)로 묶어 여러 함수가 함께 쓰는 것이 공통 육수와 같습니다. 배포를 코드로 정의해 파이프라인으로 내려보내는 일은 주방장의 지시 순서에 대응하며, 그래야 누가 언제 무엇을 바꿨는지 기록이 남습니다.

결국 다수의 함수 관리는 명명 규칙과 태그, 공유 레이어, 코드 기반 배포(infrastructure as code)를 함께 써서 함수 하나하나를 기억에 의존하지 않고 목록과 절차로 다루는 운영 방식입니다.

모니터링 자동화

사람이 보지 않아도 이상을 잡아내는 체계

새벽에 오류율이 조금씩 올라가는데 아무도 대시보드를 보지 않아 아침에야 사용자 항의로 알게 되는 일은 흔합니다. 사람이 화면을 계속 들여다보지 않아도 이상 신호를 스스로 감지해 알려 주는 체계가 모니터링 자동화입니다.

건물에 깔린 화재 경보 설비를 떠올리면 대응이 겹칩니다. 천장의 연기 센서가 공기 상태를 계속 재고, 정해 둔 수치를 넘으면 경보를 울리며, 경보는 경비실과 관리자 휴대폰으로 동시에 전달되고 필요하면 스프링클러가 저절로 작동합니다.

지표(metric)를 수집하는 것이 센서에, 임계값을 넘었는지 판정하는 경보(Alarm)가 경보기에, 알림을 보내는 통지 채널이 경비실 연락에 해당합니다. 함수가 스스로 로그를 남기고 추적(trace)을 이어 붙이게 해 두면 원인을 찾는 일도 사람 손을 덜게 됩니다.

정리하면 모니터링 자동화는 지표 수집, 임계값 경보, 알림 전달, 자동 대응을 미리 엮어 두어 사람이 지켜보지 않는 시간에도 이상을 잡아내는 운영 체계입니다.

비용 거버넌스

팀별로 비용을 나눠 보고 통제하는 방법

서비스가 커지면 청구서에 큰 숫자만 찍혀 나오고 어느 팀이 얼마를 썼는지 아무도 설명하지 못해, 비용 절감 논의가 매번 추측으로 끝납니다. 이렇게 비용을 팀과 서비스별로 나눠 보고 정해진 범위 안에서 쓰도록 관리하는 체계가 비용 거버넌스입니다.

아파트 관리비 부과 방식을 떠올리면 이해가 쉽습니다. 세대마다 전기·수도 계량기를 따로 두어 사용량을 재고, 공용 전등 같은 항목은 면적 비율로 나누며, 관리사무소는 매달 세대별 고지서를 보내고 예산을 넘길 것 같은 세대에는 미리 알립니다.

리소스에 팀 이름과 프로젝트 이름을 태그로 붙이는 일이 세대별 계량기에, 태그 기준으로 비용을 집계하는 것이 고지서 발행에 해당합니다. 여기에 팀별 예산(budget)과 초과 알림을 걸어 두면 통제가 사후 정산이 아니라 사전 경고로 바뀝니다.

결국 비용 거버넌스는 태그와 계정 구조로 비용을 팀 단위에 정확히 귀속시키고, 예산과 알림으로 사용을 미리 조율해 청구서를 사후 변명이 아닌 관리 지표로 만드는 체계입니다.

보안 점검 자동화

설정이 규칙에서 벗어나면 바로 알게 만드는 방법

누군가 급하게 권한을 넓혀 배포한 뒤 그대로 잊혀지고, 몇 달 뒤 보안 감사에서 처음 발견되는 일은 반복됩니다. 사람이 분기마다 손으로 설정을 훑는 대신 규칙을 코드로 적어 두고 어긋나는 순간 바로 알리는 방식이 보안 점검 자동화입니다.

공장의 출하 검사 라인을 떠올려 보면 구조가 같습니다. 검사 기준을 문서로만 두면 작업자마다 판정이 달라지므로, 기준을 측정 장비에 입력해 두고 컨베이어를 지나는 제품마다 자동으로 재어 불량을 골라냅니다. 불량이 나오면 라인을 세우거나 담당자에게 즉시 알리고, 같은 유형이 반복되면 공정 자체를 고칩니다.

보안에서 이 측정 장비에 해당하는 것이 규칙(rule)으로 정의한 점검 항목이고, 주기적으로 전체 계정을 훑는 평가가 컨베이어 검사에, 위반 발견 시 알림과 자동 차단이 불량 통보에 대응합니다. 저장소가 공개로 열려 있는지, 암호화가 빠졌는지 같은 항목을 코드로 적어 두면 점검이 사람의 기억에서 해방됩니다.

정리하면 보안 점검 자동화는 설정 규칙을 코드로 선언하고 주기적 평가와 알림으로 연결해, 규칙에서 벗어난 설정이 발견 즉시 드러나고 고쳐지게 만드는 체계입니다.

기존 시스템에서 옮겨오기

서버나 컨테이너에서 Lambda로 옮길 때의 판단과 절차

회사가 몇 년째 쓰던 서버 한 대가 새벽에 멈춰서 담당자 집으로 전화가 걸려 오는 상황을 한 번쯤 겪게 됩니다. 그 서버를 급하게 고쳐 쓰느냐, 아니면 관리 부담이 적은 쪽으로 옮기느냐를 두고 판단이 갈리는데, 그때 검토하는 선택지가 AWS의 서버리스 컴퓨팅 서비스인 Lambda(람다)입니다.

옮겨오기는 이사와 비슷합니다. 먼저 집 안의 짐을 전부 목록으로 만들어야 하듯, 지금 서버에서 도는 코드와 그 코드가 기대는 라이브러리, 파일 저장 위치, 외부 연결을 하나씩 적어 냅니다. 그다음 큰 가구를 방 크기에 맞춰 나누듯 기능을 함수 단위로 잘라 상자에 담고, 새 집 주소를 이웃에게 알리듯 호출 경로를 조금씩 새 쪽으로 돌립니다. 중요한 것은 옛 집을 바로 부수지 않고 한동안 창고로 남겨 두는 일인데, 새 집에서 문제가 생기면 짐을 다시 옮겨 올 수 있어야 하기 때문입니다.

그래서 실제 작업은 한 번에 갈아엎는 방식이 아니라 작은 기능 하나를 옮겨 검증하고, 트래픽을 나눠 보내며 이상이 없을 때 범위를 넓히는 순서로 진행합니다.

정리하면 기존 시스템 이전은 코드를 함수 단위로 분해하고 의존 관계를 정리한 뒤, 되돌릴 길을 남긴 채 단계적으로 호출 경로를 바꾸는 작업입니다.

Lambda를 쓰지 말아야 할 때

서버리스가 오히려 손해인 상황을 가려내는 기준

하루 종일 쉬지 않고 돌아가는 작업에 시간만큼 요금을 내는 방식을 붙이면, 같은 일을 하는 고정 요금제보다 오히려 비싸지는 일이 생깁니다. Lambda는 요청이 있을 때만 실행되고 없으면 비용이 들지 않는 대신, 계속 켜 두는 데는 불리한 구조라서 어떤 일에 맞고 어떤 일에 맞지 않는지를 먼저 가려야 합니다.

이것은 여행지에서 숙소를 고르는 것과 같습니다.

하루 이틀 묵는 출장이라면 호텔이 편하고 값도 맞지만, 1년을 지낼 사람에게는 매일 호텔비를 내는 쪽이 훨씬 손해입니다. 호텔 방은 체크인할 때마다 원래 상태로 정돈되어 있어서 짐을 두고 나가면 사라지고, 들어갈 때마다 준비 시간이 걸리듯 Lambda도 호출 사이에 메모리 상태가 유지되지 않으며 첫 호출에는 준비 시간이 붙습니다. 또 취사가 안 되는 숙소처럼 실행 시간 상한과 임시 저장 공간의 제약이 있어서, 오래 걸리는 대량 계산이나 큰 파일을 계속 다루는 작업에는 어울리지 않습니다.

따라서 상시 부하가 크거나, 연결을 계속 붙잡아야 하거나, 특수한 장비나 긴 실행 시간이 필요한 경우에는 컨테이너나 가상 서버 쪽을 검토하는 편이 낫습니다. 결국 Lambda를 쓰지 말아야 할 때는 지속적인 부하와 상태 유지, 긴 실행 시간이 핵심 요구인 경우이며, 이 기준에 걸리면 다른 실행 환경을 고르는 것이 설계의 출발점입니다.

컨테이너 서비스와의 조합

Lambda와 ECS·Fargate를 역할에 따라 나누는 설계

모든 작업을 한 가지 도구로 처리하려다 보면, 짧은 요청에는 과하게 무겁고 긴 작업에는 어설프게 맞는 구성이 되어 버립니다. 그래서 실무에서는 Lambda와 컨테이너 실행 서비스인 ECS(Elastic Container Service)나 Fargate(파게이트)를 경쟁 관계가 아니라 역할 분담 관계로 놓고 설계합니다.

이것은 회사의 인력 구성을 떠올리면 이해가 쉽습니다.

갑자기 들어오는 짧은 업무는 필요할 때만 부르는 단기 계약 인력에게 맡기고, 매일 같은 자리에서 계속 처리해야 하는 업무는 상주 직원에게 맡기는데, Lambda가 앞쪽의 단기 인력이고 Fargate가 뒤쪽의 상주 인력입니다. 두 팀은 같은 건물의 같은 층을 쓰듯 하나의 네트워크 안에 두고, 서로 일을 넘길 때는 구두 지시가 아니라 문서로 남기듯 API나 큐를 통해 주고받습니다. 이렇게 나누면 갑작스러운 요청 폭주는 Lambda가 흡수하고, 시간이 오래 걸리는 영상 변환이나 대량 배치 작업은 컨테이너 쪽이 안정적으로 처리합니다.

정리하면 Lambda는 짧고 들쭉날쭉한 요청 처리에, ECS와 Fargate는 지속적이고 무거운 처리에 두고, 양쪽을 네트워크와 큐로 연결해 하나의 흐름으로 묶는 것이 핵심입니다.

재해 복구 전략

서비스가 멈췄을 때 다시 살리는 목표와 수단

한 리전(지역 단위 데이터 센터 묶음)에 문제가 생기면 그곳에만 두었던 서비스는 한순간에 전부 멈추고, 다시 살아나기까지 몇 시간이 걸릴 수도 있습니다. 재해 복구 전략은 이때 얼마나 빨리, 어디까지 되살릴지를 미리 정해 두는 일이며, Lambda로 만든 서비스도 예외가 아닙니다.

아파트의 비상 대비와 같은 구조입니다.

각 세대에 소화기를 두고, 정전에 대비해 지하에 비상 발전기를 마련하며, 입주민이 대피 경로를 미리 익히는 훈련을 합니다. 여기서 복구 목표 시간(RTO)은 정전 후 몇 분 안에 불이 들어와야 하는지를 정하는 것이고, 복구 목표 시점(RPO)은 정전 직전까지의 기록을 어디까지 살릴 것인지를 정하는 것입니다. 발전기를 항상 돌려 두면 기름값이 들고, 완전히 꺼 두면 켜는 데 시간이 걸리므로 예비 체계를 상시 가동, 부분 가동, 대기 후 구축 같은 단계로 나눠 비용과 속도를 맞바꿉니다.

Lambda에서는 같은 코드를 다른 리전에 배포해 두거나, 설정과 데이터를 주기적으로 복제해 두는 방식으로 이 단계를 구현합니다. 결국 재해 복구는 목표 시간과 허용 가능한 데이터 손실을 먼저 숫자로 정하고, 그 숫자에 맞춰 예비 환경의 준비 수준을 고르는 설계입니다.

구성 백업과 복원

함수 설정과 코드를 잃지 않게 보관하고 되살리는 방법

코드는 저장소에 잘 보관해 두었다고 해도, 그 코드를 어떤 메모리와 어떤 권한, 어떤 트리거로 실행하고 있었는지는 아무 데도 남아 있지 않아서 함수를 다시 만들 때 한참을 헤매는 일이 생깁니다. 구성 백업과 복원은 함수의 코드뿐 아니라 그 함수를 둘러싼 설정까지 함께 보관하고 되살리는 방법입니다.

요리로 비유하면 레시피와 주방 배치의 관계입니다.

레시피만 남아 있고 어느 선반에 어떤 양념을 두었는지, 불 세기는 어디에 맞췄는지가 사라지면 같은 요리를 다시 만들 수 없으므로, 요리를 마칠 때마다 주방 사진을 찍어 두는 셈입니다. 여기서 사진에 해당하는 것이 환경 변수, 실행에 필요한 권한, 연결된 이벤트, 메모리와 시간 제한 같은 설정값이고, 더 나아가 이 모든 것을 사람이 손으로 누르지 않고 선언된 문서로 관리하는 방식을 인프라를 코드로 관리한다고 부릅니다. 복원은 새 주방에 같은 배치를 그대로 옮겨 놓는 일이라서, 평소에 백업이 실제로 되살아나는지 한 번씩 시험해 보지 않으면 막상 필요할 때 빠진 항목을 발견하게 됩니다.

정리하면 코드와 설정을 함께 문서로 남기고 정기적으로 복원 시험을 돌리는 것이, 함수를 잃지 않고 다시 세우는 가장 확실한 방법입니다.

종합 설계 실습

배운 개념을 모두 엮어 하나의 서비스로 완성하기

개념을 하나씩 배울 때는 다 아는 것 같지만, 막상 서비스 하나를 처음부터 끝까지 설계하라고 하면 어디서부터 손대야 할지 막막해집니다. 그래서 마지막 단계는 지금까지 배운 요소를 하나의 흐름으로 엮어 보는 실습이며, 예를 들어 사용자가 사진을 올리면 축소본을 만들어 주는 서비스를 가정해 볼 수 있습니다.

이것은 집을 짓는 과정과 같습니다.

먼저 몇 명이 살고 방이 몇 개 필요한지를 정하는 설계도가 요구사항이고, 외벽과 기둥을 세우듯 요청을 받는 입구와 실제 일을 하는 함수를 배치합니다. 창고를 따로 두어 짐을 보관하듯 원본 이미지는 저장소에 두고, 전기와 수도 배관을 미리 깔아 두듯 함수가 다른 자원에 접근할 수 있는 권한과 네트워크를 설계합니다. 집을 지은 뒤에도 정기 점검이 필요하듯 로그와 지표, 알림을 붙여 상태를 지켜보고, 이사나 화재에 대비하듯 백업과 복구 계획을 함께 마련해 둡니다.

이렇게 만든 뒤에는 작은 트래픽으로 먼저 열어 보고 문제가 없을 때 범위를 넓히며, 비용과 응답 시간을 재어 어느 부분을 조정할지 판단합니다. 결국 종합 설계란 요구사항을 입구, 처리, 저장, 권한, 관측, 복구라는 여섯 가지 관점으로 나누어 각각에 알맞은 서비스를 배치하고, 그 전체를 하나의 흐름으로 검증하는 일입니다.
