1Lambda의 실행 모델함수가 언제 만들어지고 언제 사라지는지를 먼저 알아야 이후의 설정·성능·과금·상태 관리가 전부 이해된다.62코드 작성: 런타임과 언어함수의 껍데기를 이해했으면, 실제 코드를 어떤 런타임 규약에 맞춰 쓰는지가 다음 전제다.53코드를 배포하는 형태: 패키징과 Layers코드를 썼으면 Lambda가 읽을 수 있는 형태로 올려야 한다. 이후의 모든 설정·버전 관리는 이 산출물 위에서 이뤄진다.44함수 설정: 실행 리소스와 네트워크같은 코드라도 이 설정값이 성능·비용·접근 가능한 리소스를 결정한다. 호출을 논하기 전에 함수의 물리적 조건을 정한다.65권한: 실행 역할과 접근 제어설정된 함수가 실제로 무언가를 하려면 권한이 있어야 하고, 다른 주체가 함수를 부르려면 허가가 있어야 한다. 호출 이야기의 직전 전제다.46함수를 호출하는 방법함수가 준비됐으니 이제 실제로 실행시킨다. 호출 방식이 재시도·오류 처리·응답 형태를 전부 결정한다.77스케일링과 시작 지연 다루기호출이 늘어나면 Lambda는 실행 환경을 복제한다. 그 규칙과 한계를 알아야 지연·스로틀·비용을 통제할 수 있다.58이벤트 소스 매핑: 스트림·큐 통합Lambda가 스스로 폴링하는 통합은 배치·재시도·스케일링 규칙이 별도로 존재한다. 푸시형 통합보다 먼저 이 공통 뼈대를 잡는다.89푸시형 서비스 통합다른 AWS 서비스가 직접 Lambda를 부르는 경우다. 이벤트 소스 매핑의 규칙이 적용되지 않는 별개 계열이라 뒤에 둔다.510관측과 문제 해결운영에 들어가면 보이지 않는 실행 환경 안을 들여다볼 방법이 필요하다. 앞의 모든 설정이 실제로 어떻게 동작하는지 확인하는 단계다.511확장과 고급 실행 모델기본 함수 모델을 완전히 이해한 뒤에야, 그 모델을 확장하거나 대체하는 Extensions·Durable functions·Managed Instances·MicroVMs를 제자리에서 판단할 수 있다.912개발 도구·테스트·운영 기준콘솔이 아니라 코드와 파이프라인으로 Lambda를 다루는 방법, 그리고 한도·모범 사례로 마무리한다.5

1Lambda의 실행 모델01-01

서버리스와 AWS Lambda: 무엇을 대신해 주는가

Lambda는 서버를 직접 만들고 관리하지 않아도 내 코드를 필요할 때만 실행해 주는 AWS의 컴퓨팅 서비스다.

1상대의 출발점 확인

기존 방식에서는 서버를 직접 구매하거나 임대한 후, 운영체제를 설치하고 애플리케이션을 배포한 다음 24시간 모니터링을 해야 했습니다. 하지만 이 방식은 사용하지 않을 때도 서버 유지비가 계속 발생하고, 서버 관리와 보안 업데이트 같은 운영 부담이 매우 큽니다.

2질문 제기

코드를 실행하려면 꼭 서버를 24시간 띄워둬야 할까?

3구조적 핵심 예시

  2. 함수 자동 실행Lambda가 그 신호에 반응하여 핸들러(handler, 함수 진입점) 코드를 자동으로 실행합니다.
  3. 종료 및 비용 청구함수 실행이 끝나면 환경이 정리되고, 실제 실행된 시간만큼만 비용이 청구됩니다.

  2. Invoke 단계Init이 완료된 후 핸들러 함수를 호출하고 비즈니스 로직을 실행합니다.
  3. Shutdown 단계함수 실행이 완료되면 실행 환경을 정리하고 리소스를 해제합니다.

2질문 제기

3구조적 핵심 예시

  2. 웜 스타트같은 환경에서 재호출되면 Init 단계를 건너뛰고 핸들러만 실행하기 때문에 매우 빠릅니다.
  3. 최적화느린 초기화(라이브러리 import, DB 연결)를 핸들러 밖에 정적으로 구성하면 웜 스타트 성능이 더욱 개선됩니다.

3구조적 핵심 예시

Lambda Layer는 라이브러리 파일들을 별도의 ZIP 아카이브로 만들어 AWS에 업로드한 후, 여러 함수가 그 레이어를 참조하도록 연결하는 방식이다. 함수 실행 시 AWS는 레이어의 파일들을 함수의 실행 환경에 자동으로 추가하고, 함수 코드는 그 파일들에 접근할 수 있다.

4단계별 동작 과정

1상대의 출발점 확인

함수를 배포할 때 얼마나 강력한 컴퓨터에서 돌릴지 지정하지 않으면, AWS는 기본값으로 최소 리소스를 할당한다. 리소스가 적으면 함수가 느려지고, 실행이 오래 걸리면 자동으로 중단되므로, 함수가 제때 끝나지 못하는 문제가 생긴다.

2질문 제기

함수가 사용할 메모리와 CPU 성능, 그리고 최대 실행 시간을 어떻게 정할까?

3구조적 핵심 예시

Lambda는 메모리 설정값만 받으면 그에 비례하는 CPU 성능을 자동으로 할당한다. 메모리 128MB에서 10,240MB까지 1MB 단위로 조절할 수 있고, 메모리가 많을수록 CPU도 더 강해진다. 타임아웃은 함수가 최대 몇 초까지 실행될 수 있는지를 정하는 값으로, 이 시간을 초과하면 AWS가 호출을 강제로 중단한다.

4단계별 동작 과정

  1. 메모리 설정함수가 필요로 하는 메모리량을 지정하면, AWS는 그 양에 정확히 비례하는 CPU 성능을 같이 할당한다. 더 많은 메모리 = 더 빠른 CPU.
  2. 타임아웃 설정함수 설정에서 최대 실행 시간(초 단위, 기본 3초, 최대 900초)을 정한다.
  3. 실행 및 중단함수 실행 시간이 타임아웃 값을 초과하면, AWS는 즉시 함수를 종료하고 실패로 처리한다.

2질문 제기

3구조적 핵심 예시

Lambda 함수는 /tmp 경로에 512MB에서 10,240MB까지 임시 저장 공간을 사용할 수 있고, 이 공간은 함수 실행이 끝나면 자동으로 지워진다. 동시에 함수를 x86_64 명령어(Intel/AMD 프로세서용) 또는 arm64 명령어(Graviton 프로세서용)로 실행하도록 선택할 수 있으며, ARM이 보통 비용이 더 싸다.

4단계별 동작 과정

  2. CPU 아키텍처 선택함수 배포 시 x86_64(기존 기본값) 또는 arm64(Graviton, 더 저렴)를 선택한다. 대부분의 코드는 둘 다에서 같은 방식으로 동작하지만 일부 바이너리 라이브러리는 호환성을 확인해야 한다.
  3. 실행 및 정리함수 실행이 끝나면 /tmp의 모든 파일은 자동으로 삭제되고, 다음 호출에서는 깨끗한 /tmp로 시작한다.

3구조적 핵심 예시

Lambda는 환경 변수(Environment Variables) 기능으로 함수 실행 시 변수 이름과 값을 주입한다. 함수 코드는 일반 언어의 환경 변수 조회 방식으로 이 값들을 읽는다. 민감한 정보(API 키, 비밀번호)는 KMS(Key Management Service)로 암호화해서 저장하고, 함수 실행 권한이 있는 사용자만 복호화할 수 있다.

  3. 실행 및 접근함수가 실행되면 환경 변수는 함수 프로세스의 메모리에 로드되고, 함수 코드에서 표준 방식으로 읽을 수 있다(예: Python의 os.environ['DB_HOST']).

1상대의 출발점 확인

기본적으로 Lambda 함수는 인터넷에 공개된 AWS 인프라에서 실행되므로, RDS 데이터베이스나 ElastiCache 같은 사설 네트워크 리소스에 직접 접근할 수 없다. 함수가 사설 리소스와 통신하려면 특별한 설정이 필요하다.

2질문 제기

Lambda 함수가 VPC 내부의 사설 리소스(RDS, ElastiCache 등)에 접근하려면 어떻게 해야 할까?

3구조적 핵심 예시

Lambda 함수를 특정 VPC(Virtual Private Cloud)의 서브넷과 보안 그룹에 연결하면, 함수의 네트워크 인터페이스가 그 VPC 내부에 생성되고, VPC 내부의 리소스들과 직접 통신할 수 있다. 함수는 여전히 AWS가 관리하지만, 네트워크상으로는 VPC 안에 있는 것처럼 작동한다.

4단계별 동작 과정

  1. VPC·서브넷·보안 그룹 선택함수 설정에서 함수를 연결할 VPC, 서브넷(최소 2개 이상 권장, 고가용성), 보안 그룹을 지정한다.
  2. 네트워크 인터페이스 생성AWS는 함수 실행 때마다 지정된 서브넷에 임시 네트워크 인터페이스를 생성하고, 함수는 그 인터페이스의 사설 IP를 갖는다.
  3. 리소스 접근함수는 이제 같은 VPC의 RDS, ElastiCache, 내부 서버 등에 사설 IP로 직접 접근할 수 있다(보안 그룹 규칙에 따라).

3구조적 핵심 예시

  3. 교차 계정 연결Transit Gateway나 VPC 피어링으로 다른 AWS 계정의 VPC를 연결하고, IAM 역할 신뢰 관계를 설정하면 교차 계정 리소스에 접근할 수 있다.

Lambda 함수의 /tmp 임시 저장 공간은 최대 10GB이고, 함수 실행이 끝나면 사라진다. 동시에 여러 함수 호출이 같은 대용량 데이터 파일(예: ML 모델, 대규모 조회 테이블)에 접근하려면 매번 S3에서 다운로드해야 하므로 느리다.

3구조적 핵심 예시

비동기 호출: 내부 큐·재시도·이벤트 최대 수명

Lambda가 이벤트를 내부 큐에 받아두고 즉시 응답한 뒤 나중에 실행하며, 실패하면 최대 수명 안에서 자동 재시도한다.

1상대의 출발점 확인

동기 호출은 함수 실행이 끝날 때까지 기다려야 하므로, 오래 걸리는 작업이 있으면 호출한 쪽도 계속 기다려야 합니다. 응답을 빨리 주고 싶지만 백그라운드에서 느리게 작업을 처리해야 하는 경우에는 이 방식이 맞지 않습니다.

2질문 제기

Lambda 함수를 호출했을 때 즉시 응답을 받고, 실제 함수 실행은 나중에 백그라운드에서 하려면 어떻게 하는가?

3구조적 핵심 예시

S3가 파일 업로드 이벤트를 Lambda에 비동기로 보내면, Lambda는 즉시 "받았다"고 응답하고 이벤트를 내부 큐에 넣습니다. 그러다 나중에 Lambda 워커가 이벤트를 꺼내 함수를 실행합니다. 함수 실행이 실패하면 Lambda는 자동으로 다시 시도합니다.

4단계별 동작 과정

  1. 호출자가 비동기 호출 요청S3나 SNS 같은 서비스, 또는 클라이언트가 Lambda를 비동기 모드로 호출합니다.
  2. Lambda가 즉시 응답하고 큐에 저장AWS Lambda는 호출을 내부 큐에 받아두고 즉시 호출자에게 응답합니다.
  3. 나중에 함수 실행 및 재시도Lambda 워커가 큐에서 이벤트를 꺼내 함수를 실행하고, 실패하면 최대 수명(TTL, Time To Live) 안에서 자동으로 재시도합니다.

1상대의 출발점 확인

비동기 호출이 안정적으로 동작할 때는 문제가 없지만, 함수가 실패하거나 최대 재시도 횟수를 초과했을 때 그 이벤트가 그냥 사라집니다. 실패한 이벤트가 어디로 갔는지, 왜 실패했는지를 추적할 방법이 없었습니다.

2질문 제기

비동기 호출이 성공하거나 끝내 실패했을 때 그 결과를 기록하고 추적하려면 어떻게 하는가?

3구조적 핵심 예시

Lambda 함수 설정에서 "성공한 이벤트는 SNS 토픽으로, 실패한 이벤트는 SQS 큐로 보내라"고 지정하면, 비동기 호출이 성공할 때마다 AWS는 성공 기록을 SNS로 보내고, 끝내 실패할 때는 실패 기록과 함수 코드 상태를 SQS로 보냅니다.

4단계별 동작 과정

  1. 함수에 대상(Destination) 또는 DLQ 설정Lambda 함수 설정에서 성공/실패 시 이벤트를 받을 목적지(SQS, SNS, EventBridge, Lambda)를 지정합니다.
  2. 비동기 호출 처리Lambda 워커가 큐에서 이벤트를 꺼내 함수를 실행합니다.
  3. 결과에 따라 대상으로 전송함수가 성공하면 성공 기록을 지정된 대상으로 보내고, 최대 재시도 후 실패하면 실패 기록을 다른 대상(DLQ)으로 보냅니다.

함수 상태·재시도 동작·재귀 루프 감지

함수가 호출 가능한 상태인지(Pending/Active), 오류 종류별 재시도 규칙은 무엇인지, 자기 자신을 무한 호출하는 루프를 Lambda가 어떻게 끊는지를 다룬다.

1상대의 출발점 확인

기존에는 함수가 호출되면 즉시 실행되는 것으로만 생각했습니다. 하지만 현실에서는 함수가 아직 이전 호출을 끝내지 못했을 수도 있고, 오류가 발생했을 수도 있습니다. 이런 상황에서 AWS가 어떻게 대응해야 하는지, 얼마나 오래 재시도해야 하는지, 함수가 자신을 무한정 호출하는 상황을 어떻게 감지하는지에 대한 규칙이 없었습니다.

2질문 제기

Lambda 함수가 현재 호출 가능한 상태인지 어떻게 파악하고, 오류 종류에 따라 어떻게 재시도하며, 무한 재귀를 감지해서 중단하려면?

3구조적 핵심 예시

함수는 호출되면 세 가지 상태 중 하나입니다. Pending(아직 리소스 확보 중), Active(현재 실행 중), Ready(준비 완료). 재시도는 오류 유형에 따라 결정됩니다. 예를 들어 내부 오류(5xx)는 재시도하지만, 인증 실패(4xx)는 재시도하지 않습니다. 재귀 루프는 함수가 자신의 이름으로 계속 호출하는 것을 감지하면 AWS가 강제로 차단합니다.

4단계별 동작 과정

  1. 상태 확인요청이 들어오면 먼저 함수가 Pending(아직 준비 중) 상태인지, Active(현재 실행 중)인지, Ready(준비됨)인지 확인합니다.
  2. 오류 분류와 재시도 판단함수가 실패하면 예외 타입을 확인합니다. Throttled(리소스 부족) 또는 ServiceException(내부 오류)은 지수 백오프(점점 더 오래 기다렸다가 다시 시도)로 재시도하며, 명시적 오류(InvalidRequestException)는 재시도하지 않습니다.
  3. 재귀 감지와 차단함수가 자기 자신을 연쇄적으로 호출하는 루프를 감지하면 AWS가 규정된 깊이(보통 수백 단계)에서 강제로 중단하고 오류를 반환합니다.

5본질 요약

Function URL: 전용 HTTPS 엔드포인트와 접근 제어

API Gateway 없이 함수에 바로 붙는 고유 HTTPS 주소로, IAM 인증 또는 공개(NONE) 중 하나로 접근을 통제한다.

1상대의 출발점 확인

이전에는 Lambda 함수를 호출하려면 반드시 API Gateway라는 별도 서비스를 거쳐야 했습니다. API Gateway를 설정하는 것은 여러 단계를 거쳐야 하고, 함수 하나마다 일일이 연결해야 했습니다. 간단한 함수를 HTTPS로 직접 노출시키려고 해도 중간 계층을 꼭 거쳐야 했던 것입니다.

2질문 제기

함수에 직접 붙는 고유 HTTPS 주소를 부여하고, 인증 방식을 단순하게 제어할 수는 없을까요?

3구조적 핵심 예시

Function URL을 활성화하면 함수마다 https://1234567890abcdefg.lambda-url.us-east-1.amazonaws.com/ 형태의 고유 주소가 생깁니다. 이 주소는 API Gateway를 거치지 않고 함수로 직접 요청을 보냅니다. 접근 제어는 두 가지만 선택합니다. NONE(누구나 접근)이거나 AWS_IAM(AWS 계정 인증 필수)입니다.

4단계별 동작 과정

  1. URL 활성화함수 설정에서 Function URL을 활성화하면 AWS가 고유한 HTTPS 엔드포인트를 할당합니다. 이 주소는 함수가 삭제될 때까지 변하지 않습니다.
  2. 인증 방식 설정NONE으로 설정하면 누구나 그 URL을 알고 있으면 호출할 수 있습니다. AWS_IAM으로 설정하면 AWS Signature v4(AWS 인증 서명)를 포함한 요청만 수락합니다.
  3. 요청 처리클라이언트가 URL로 HTTP 요청(GET, POST 등)을 보내면 Lambda는 그것을 함수의 event(입력) 파라미터로 변환해 실행하고, 함수의 반환값을 HTTP 응답으로 변환해 클라이언트에 보냅니다.

5본질 요약

API Gateway 없이 함수 하나마다 전용 HTTPS 주소를 자동으로 부여하고, 접근 제어를 IAM 인증 또는 공개 중 둘 중 하나로 간단하게 설정하는 것

응답 스트리밍

결과를 다 만든 뒤 한 번에 주는 대신, 만들어지는 대로 조각조각 클라이언트에 흘려보내는 방식이다.

→ 06-05 참조

1상대의 출발점 확인

일반적으로 Lambda 함수가 실행되면 결과를 전부 계산한 후 한 번에 클라이언트에 보냅니다. 결과가 크거나 생성 시간이 길면 클라이언트는 모든 데이터가 완성될 때까지 기다려야 합니다. 예를 들어 대량의 데이터를 조회하거나 AI 모델이 긴 텍스트를 생성하는 경우 응답 시간이 매우 길어집니다.

2질문 제기

결과를 완성한 후 한 번에 보내지 않고, 만들어지는 대로 즉시 클라이언트에 조각씩 흘려보낼 수 있을까요?

3구조적 핵심 예시

응답 스트리밍이 활성화되면 함수는 결과 전체를 버퍼에 담지 않습니다. 대신 함수가 데이터를 생성할 때마다 그 즉시 클라이언트에 보냅니다. 예를 들어 1,000개 행의 CSV를 생성한다면 1행이 완성되자마자 클라이언트가 받기 시작하고, 함수가 완전히 끝나기를 기다리지 않아도 됩니다.

4단계별 동작 과정

  1. 스트리밍 활성화함수 설정에서 응답 스트리밍을 켜면 Lambda는 클라이언트와의 연결을 지속적으로 유지합니다.
  2. 함수 실행 및 데이터 생성함수가 실행되면서 데이터를 생성합니다. 이때 완성한 데이터(보통 바이트 단위로)를 스트림 출력(stdout)에 쓰거나 SDK를 통해 직접 보냅니다.
  3. 실시간 전송AWS는 함수에서 나오는 데이터를 캡처해서 지체 없이 클라이언트에 전달합니다. 함수가 끝나면 스트림이 닫힙니다.

5본질 요약

버전과 별칭, 가중치 기반 트래픽 이동

코드를 불변 버전으로 고정하고 별칭이라는 이름표로 가리키며, 두 버전에 트래픽 비율을 나눠 점진 배포한다.

1상대의 출발점 확인

함수 코드를 업데이트하면 즉시 모든 호출자가 새 코드를 받습니다. 이는 새 코드에 버그가 있으면 모든 사용자에게 영향을 미친다는 뜻입니다. 또한 어떤 호출자는 이전 코드로 실행하고 다른 호출자는 새 코드로 실행하는 것이 불가능하므로, 배포 전 일부 트래픽으로만 테스트할 수 없었습니다.

2질문 제기

함수 코드를 불변 버전으로 나누고, 일부 사용자만 새 코드로 점진 배포하면서 검증할 수 있을까요?

3구조적 핵심 예시

함수를 배포할 때마다 AWS가 버전을 생성합니다. 예를 들어 버전 1, 2, 3처럼 번호가 매겨집니다. 별칭은 이런 버전을 가리키는 이름표입니다. 예를 들어 LIVE라는 별칭이 버전 1을 가리킨다고 하면, 클라이언트가 LIVE를 호출할 때는 버전 1의 코드가 실행됩니다. 배포할 때는 LIVE 별칭을 버전 2로 옮기되, 버전 1과 2의 가중치를 9:1로 설정하면 10%의 요청만 버전 2에서 실행됩니다.

4단계별 동작 과정

  1. 버전 생성함수 코드를 업데이트하고 배포하면 AWS가 불변 버전을 자동으로 만듭니다. 이 버전은 그 시점의 코드와 설정을 영구히 보존합니다.
  2. 별칭 설정 및 가중치 배치별칭을 생성하거나 기존 별칭이 가리키는 버전을 변경할 때, 여러 버전에 백분율 가중치를 할당합니다. 예: STAGING 별칭이 버전 1 90%, 버전 2 10%.
  3. 트래픽 라우팅클라이언트가 별칭을 호출할 때마다 AWS는 설정한 가중치에 따라 요청을 배분합니다. 이를 통해 새 버전으로의 롤아웃을 단계별로 진행할 수 있습니다.

5본질 요약

함수 코드를 불변 버전으로 스냅샷하고, 별칭이라는 이름 레이어를 거쳐 버전을 가리키며, 가중치로 트래픽을 단계적으로 분산해 안전한 배포를 가능하게 하는 것

7스케일링과 시작 지연 다루기07-01

동시성 개념과 스케일링 동작

동시성은 같은 순간에 동시에 실행 중인 함수 인스턴스 수이며, Lambda 는 요청이 늘면 인스턴스를 자동으로 늘려 처리한다.

1상대의 출발점 확인

기존 서버에서는 인스턴스 개수를 미리 정해야 했습니다. 인스턴스가 너무 적으면 병목이 생기고, 너무 많으면 비용이 올랐습니다. Lambda는 서버가 없으므로 요청이 많아졌을 때 어떻게 처리하는지 명확하지 않았습니다.

2질문 제기

Lambda는 요청이 동시에 많아지면 어떻게 자동으로 확장하고, 동시에 실행되는 함수의 개수를 어떻게 관리하는가?

3구조적 핵심 예시

동시성이란 같은 순간에 실행 중인 함수 인스턴스의 개수입니다. 예를 들어 첫 요청이 함수를 실행하고 있는데 두 번째 요청이 들어오면 AWS는 새로운 함수 인스턴스를 만들어 그것을 처리합니다. 이를 콜드 스타트(cold start)라고 합니다. 세 번째, 네 번째 요청이 계속 들어오면 AWS는 계속 새 인스턴스를 생성합니다. 동시성이 10이면 10개의 인스턴스가 동시에 실행 중인 것입니다.

4단계별 동작 과정

  1. 요청 도착 및 인스턴스 확인함수 호출 요청이 들어오면 AWS는 현재 유휴 인스턴스(사용 가능한 상태)가 있는지 확인합니다.
  2. 스케일링 판단유휴 인스턴스가 있으면 그것을 재사용합니다. 없으면 새로운 인스턴스를 생성합니다(콜드 스타트).
  3. 동시성 증가 및 회수요청이 처리될 때마다 해당 인스턴스의 동시성 카운트가 증가합니다. 요청 처리가 끝나면 동시성이 감소하고 인스턴스가 유휴 상태로 돌아갑니다.

예약 동시성(reserved concurrency)

특정 함수에 계정 동시성 중 일부를 떼어 보장해 주면서 동시에 그 함수의 상한으로도 작동하는 설정이다.

1상대의 출발점 확인

AWS 계정은 전체 동시성 제한을 가집니다. 예를 들어 계정의 총 동시성이 1,000이라면, 모든 함수를 합쳐서 1,000개 인스턴스까지만 동시에 실행할 수 있습니다. 중요한 함수가 있어도 다른 함수들이 동시성을 다 써버리면 중요한 함수는 대기하게 되는 문제가 있었습니다.

2질문 제기

중요한 함수가 동시성 부족으로 응답 지연을 겪지 않으면서도, 그 함수가 무한정 확장되지 않도록 상한을 설정할 수 있을까요?

3구조적 핵심 예시

예약 동시성은 계정 전체 동시성 풀에서 일부를 떼어 특정 함수에 할당하는 것입니다. 예를 들어 계정 동시성이 1,000이고 함수 A에 100을 예약하면, 함수 A는 항상 최소 100개 인스턴스까지 보장받습니다. 동시에 함수 A는 100을 넘어서 확장될 수 없습니다. 함수 B, C 등은 남은 900을 나눠 씁니다.

4단계별 동작 과정

  1. 예약 동시성 설정함수마다 예약 동시성 개수를 지정합니다. 예: 함수 A에 200 예약.
  2. 요청 도착 시 처리함수 A로 요청이 들어올 때, 예약된 200개 범위 내에서는 항상 새 인스턴스를 만들 수 있습니다. 200을 초과하는 요청은 throttle(거부)됩니다.
  3. 남은 동시성 반환함수 A가 사용하지 않는 예약된 동시성(예: 150만 쓰고 200은 할당받음)은 계정의 나머지 함수들이 사용할 수 있습니다.

프로비저닝된 동시성(provisioned concurrency)

미리 초기화해 대기시켜 둔 실행 환경을 확보해 콜드 스타트 없이 즉시 응답하게 하는 설정이다.

1상대의 출발점 확인

Lambda 함수가 처음 호출될 때는 콜드 스타트로 인해 실행 환경을 초기화하는 데 시간이 걸립니다. 이 지연은 보통 수백 밀리초이지만, 많은 동시 요청이 들어오거나 한동안 함수가 호출되지 않은 후 다시 요청이 들어올 때 문제가 됩니다. 금융 시스템이나 실시간 서비스에서는 이런 지연이 허용되지 않습니다.

2질문 제기

콜드 스타트를 완전히 없애고 함수가 항상 준비된 상태로 즉시 응답할 수 있게 하려면?

3구조적 핵심 예시

프로비저닝된 동시성은 미리 함수 환경을 초기화해서 대기시켜 두는 것입니다. 예를 들어 프로비저닝된 동시성을 50으로 설정하면 AWS는 50개의 함수 인스턴스를 미리 만들어서 요청을 받을 준비를 합니다. 요청이 들어오면 이 준비된 인스턴스 중 하나를 즉시 사용하므로 콜드 스타트가 없습니다.

4단계별 동작 과정

  1. 환경 사전 초기화프로비저닝된 동시성 개수를 지정하면 AWS는 그 수만큼 함수의 실행 환경을 미리 준비합니다. 런타임, 의존성 로드, 커스텀 초기화 코드 실행 등이 미리 끝납니다.
  2. 대기 상태 유지이 준비된 인스턴스들은 요청이 들어올 때까지 대기합니다. 그 동안 비용이 계속 발생합니다.
  3. 요청 즉시 처리요청이 들어오면 준비된 인스턴스 중 하나를 선택해 즉시 함수 코드를 실행합니다. 콜드 스타트 지연이 없습니다.

5본질 요약

함수의 실행 환경을 미리 초기화해서 대기시켜두고 요청이 들어올 때 즉시 사용하도록 함으로써 콜드 스타트를 제거하는 것

SnapStart: 스냅샷으로 시작 지연 줄이기

초기화가 끝난 실행 환경의 메모리·디스크 스냅샷을 미리 떠 두고 호출 때 복원해 시작 지연을 줄이는 기능이다.

1상대의 출발점 확인

Lambda 함수가 호출될 때마다 컨테이너가 새로 생성되고 코드가 로드되며 초기화 코드가 실행된다. 이 과정을 콜드 스타트라고 부르며 수백 밀리초 이상 걸린다. Java 같이 무거운 런타임은 1~2초 이상 걸릴 수 있다. 따라서 새 요청이 들어올 때마다 불가피하게 응답 지연이 발생한다.

2질문 제기

초기화를 매번 반복하는 낭비를 어떻게 없애고 즉시 실행할 수 있을까?

3구조적 핵심 예시

초기화가 완료된 함수 실행 환경의 메모리, 디스크, 로드된 라이브러리 상태 전부를 스냅샷으로 저장해 두고, 다음 호출 때는 그 스냅샷을 복원해서 즉시 코드를 실행하는 방식이다.

4단계별 동작 과정

  1. 초기 배포 후 스냅샷 생성함수가 처음 호출되거나 배포되면 초기화가 완료되는 시점에 AWS가 그 상태를 스냅샷으로 저장한다.
  2. 다음 호출 시 스냅샷 복원새로운 호출이 들어오면 저장된 스냅샷을 새 환경에 복원해서 초기화 단계를 건너뛰고 바로 함수 코드 실행을 계속한다.
  3. 결과적인 지연 제거초기화 시간이 제거되거나 극도로 줄어들어서 응답 시간이 수십 밀리초 단위로 빨라진다.

스냅샷 전후에 코드를 끼워 넣는 런타임 훅으로 난수·커넥션 같은 고유값을 복원 시점에 다시 만들어 주는 규칙과 스냅샷 암호화 보안 모델이다.

1상대의 출발점 확인

스냅샷을 그냥 저장하고 복원하면 난수 생성기의 시드값, 데이터베이스 연결, 암호화 키 같은 고유한 상태(stateful state)들이 전부 동일하게 복사된다. 이렇게 되면 같은 암호화 키로 여러 호출이 암호화되거나, 같은 DB 커넥션을 재사용하는 등의 보안 및 기능 문제가 발생한다.

2질문 제기

스냅샷을 복원할 때 난수, 커넥션 같은 고유값들을 어떻게 다시 초기화할 수 있을까?

3구조적 핵심 예시

RuntimeHook이라는 코드 훅을 정해진 시점(beforeCheckpoint, afterRestore 등)에 실행해서 스냅샷 전후에 필요한 상태를 다시 세팅한다. 예를 들어 beforeCheckpoint에서 난수 생성기의 시드를 리셋하고, afterRestore에서 데이터베이스 커넥션을 새로 열 수 있다.

4단계별 동작 과정

  1. beforeCheckpoint 훅 실행스냅샷을 저장하기 직전에 이 훅이 실행되어 시드나 커넥션 같은 고유 상태를 정리하고 리셋한다.
  2. 스냅샷 저장 및 복원AWS가 정리된 상태를 스냅샷으로 저장했다가 나중에 새 환경에 복원한다. 이때 스냅샷은 AWS KMS 암호화로 보호되며 같은 계정 권한 내에서만 복원 가능하다.
  3. afterRestore 훅 실행복원 직후 이 훅이 실행되어 난수 시드를 새로 초기화하거나 데이터베이스 커넥션을 새로 맺는다.

트리거와 이벤트 소스 매핑의 차이

트리거는 서비스가 Lambda 를 직접 호출하는 방식이고, 이벤트 소스 매핑은 Lambda 가 큐·스트림을 대신 폴링해 배치로 호출해 주는 리소스다.

1상대의 출발점 확인

트리거(trigger)는 외부 서비스(API Gateway, S3, DynamoDB Streams 등)가 Lambda 함수를 직접 호출하는 방식이다. 서비스가 Lambda를 "실행해 주세요"라고 직접 찌르는 것이다. 하지만 SQS, Kinesis 같은 큐나 스트림은 서비스가 Lambda를 호출하지 않고 메시지를 저장만 한다. 따라서 Lambda가 수동으로 그 메시지를 읽어가야 한다.

2질문 제기

큐나 스트림에 있는 메시지를 Lambda가 어떻게 자동으로 가져가서 처리할까?

3구조적 핵심 예시

이벤트 소스 매핑은 Lambda를 대신해서 큐나 스트림을 계속 폴링(주기적으로 "뭐 있어?" 하고 물어보기)하고, 메시지를 모아서 배치(batch)로 함수에 한 번에 전달하는 AWS 관리형 리소스다.

4단계별 동작 과정

  1. 권한 설정Lambda 실행 역할(IAM role)이 큐나 스트림을 읽을 권한을 가져야 한다.
  2. 폴러 시작이벤트 소스 매핑을 생성하면 AWS가 백그라운드에서 폴러(poller)라는 읽는 작업을 띄운다.
  3. 배치 호출폴러가 주기적으로 큐나 스트림을 확인하고 메시지가 있으면 여러 개를 모아서 한 번에 함수에 보낸다.

5본질 요약

8이벤트 소스 매핑: 스트림·큐 통합08-02

배치 처리: 배치 크기·배치 윈도우·페이로드 한도

한 번의 호출에 담을 레코드 수(배치 크기)와 최대 대기 시간(배치 윈도우)을 조절해 처리량과 지연 시간을 맞추되, 호출 페이로드 한도를 넘으면 배치가 쪼개진다.

1상대의 출발점 확인

큐에 메시지 100개가 있을 때, Lambda를 100번 호출할 수도, 1번 호출할 수도 있다. 호출 수가 많으면 비용과 지연이 증가하고, 너무 오래 모으면 메시지 처리 지연이 길어진다. 따라서 한 번의 호출에 담을 메시지 수와 최대 대기 시간을 맞춰야 비용과 응답 속도의 균형을 유지할 수 있다.

2질문 제기

한 번의 호출에 몇 개 메시지를 담으면 비용과 지연의 균형이 맞을까?

3구조적 핵심 예시

배치 크기(배치 크기, 한 호출에 담을 최대 레코드 수)와 배치 윈도우(메시지를 최대 얼마나 기다렸다가 보낼지)를 조절해서 균형을 맞춘다. 예를 들어 배치 크기 100, 배치 윈도우 5초이면, 100개가 모이거나 5초가 지날 때까지 기다렸다가 (둘 중 먼저 일어나는 것이) 함수를 호출한다.

4단계별 동작 과정

  1. 배치 설정 지정이벤트 소스 매핑에서 배치 크기(기본값 100)와 배치 윈도우(기본값 0초, 즉 즉시 전송)를 설정한다.
  2. 메시지 모음폴러가 메시지를 모으면서 배치 크기에 도달하거나 배치 윈도우 시간이 지날 때까지 기다린다.
  3. 함수 호출 또는 배치 분할조건이 만족되거나 함수 호출의 페이로드 한도(함수로 보낼 수 있는 최대 데이터 크기, 일반적으로 수십 MB)에 도달하면 함수를 호출한다. 페이로드 한도를 초과하면 배치가 자동으로 쪼개져서 여러 번 호출된다.

이벤트 폴러 스케일링과 프로비저닝 모드

Lambda 가 소스를 읽는 폴러 수를 자동으로 늘리고 줄이는 방식이며, 프로비저닝 모드로 최소·최대 폴러 수를 직접 지정할 수 있다.

1상대의 출발점 확인

Lambda가 이벤트 소스를 읽는 폴러(poller)는 기본적으로 AWS가 자동으로 관리한다. 메시지가 많으면 단일 폴러가 병목이 되어 느려지거나 지연이 생길 수 있다. 초당 수천 개의 레코드가 들어오는 고처리량 스트림에서는 충분한 읽기 속도를 보장하기 어렵다.

2질문 제기

폴러 수를 조절해서 더 많은 메시지를 빠르게 읽을 수 있을까?

3구조적 핵심 예시

스케일링 모드(auto scaling)에서는 AWS가 폴러 수를 자동으로 늘렸다 줄였다 하고, 프로비저닝 모드(provisioned)에서는 사용자가 최소·최대 폴러 수를 직접 지정해서 일정한 처리량을 보장한다.

4단계별 동작 과정

  1. 모드 선택이벤트 소스 매핑의 스케일링 설정(ScalingConfig)을 auto scaling 또는 provisioned 모드로 변경한다.
  2. 자동 조정 또는 고정자동 모드면 AWS가 메시지 쌓임을 감지해 폴러를 늘리고, 처리가 따라잡으면 줄인다. 프로비저닝 모드면 설정한 폴러 수(예: 최소 2, 최대 100)를 유지한다.
  3. 처리량 확보자동 모드는 비용 효율적이지만 변동이 생기고, 프로비저닝 모드는 일정한 처리량을 보장해 예측 가능한 성능을 제공한다.

이벤트 필터링으로 불필요한 호출 막기

필터 패턴에 맞는 레코드만 함수로 전달해, 관심 없는 메시지 때문에 함수가 호출되는 낭비를 없애는 기능이다.

1상대의 출발점 확인

이벤트 소스 매핑은 모든 메시지를 배치로 모아서 함수에 보낸다. 함수는 관심 없는 메시지도 받게 되고, 함수 내부에서 필터링 로직을 직접 작성해야 한다. 이렇게 되면 불필요한 함수 호출이 발생해 비용이 증가한다.

2질문 제기

관심 있는 메시지만 함수로 전달해 불필요한 호출을 줄일 수 없을까?

3구조적 핵심 예시

필터 패턴(filter pattern)이라는 JSON 경로 규칙을 이벤트 소스 매핑에 지정하면, AWS가 배치를 함수에 보내기 전에 미리 필터링해서 패턴에 맞는 레코드만 담아 보낸다.

4단계별 동작 과정

  1. 필터 패턴 설정이벤트 소스 매핑의 필터 파라미터에 필터 패턴을 설정한다. 예: {"type": ["order"], "status": ["completed"]}
  2. 필터링 수행폴러가 메시지를 모을 때 패턴과 매칭되는 레코드만 배치에 담는다. 패턴과 맞지 않는 레코드는 버려진다.
  3. 함수 호출 감소함수는 필터링된 배치만 받으므로 관심 있는 메시지만 처리하고 불필요한 호출이 줄어든다.

5본질 요약

부분 배치 실패 보고와 실패 대상

배치 중 실패한 레코드의 ID 만 응답으로 돌려주어 성공한 레코드의 재처리를 막고, 끝내 실패한 항목은 실패 대상(DLQ 등)으로 보낸다.

1상대의 출발점 확인

배치의 레코드 중 일부만 실패하면, 전체 배치가 실패한 것으로 간주되어 재시도되거나 버려진다. 이미 성공한 레코드까지 다시 처리되므로 중복 처리와 낭비가 발생한다. 따라서 배치 중 일부가 실패해도 성공한 레코드는 보존하고 실패한 레코드만 따로 처리해야 한다.

2질문 제기

배치 중에 실패한 레코드를 정확히 구분해서 다시 시도하거나 버릴 수 있을까?

3구조적 핵심 예시

함수가 응답에 실패한 레코드의 ID만 보내면(부분 배치 실패 보고), AWS는 성공한 레코드는 삭제하고 실패한 레코드만 재시도하거나 실패 대상(dead-letter queue, DLQ 등)으로 보낸다.

4단계별 동작 과정

  1. 함수 처리 및 응답함수가 배치를 처리한 후 실패한 레코드의 ID만 응답에 담아서 반환한다. 예: {batchItemFailures: [{itemId: "1"}, {itemId: "3"}]}
  2. 성공·실패 분류Lambda는 응답을 보고 성공한 레코드(ID 0, 2)는 무시하고, 실패한 레코드(ID 1, 3)만 재시도 큐에 넣거나 DLQ로 보낸다.
  3. 재시도 또는 최종 실패 처리재시도 정책(몇 번, 얼마나 기다린 후)에 따라 실패한 레코드를 다시 처리하거나 최종 실패 대상으로 버린다.

5본질 요약

Amazon SQS 연동

Lambda 가 SQS 큐를 폴링해 메시지를 배치로 처리하고, 성공하면 자동으로 삭제해 주는 표준 큐 소비 방식이다.

1상대의 출발점 확인

기존에는 애플리케이션이 메시지 큐를 직접 폴링해서 메시지를 가져오고, 배치로 묶어 처리한 후, 성공한 메시지들을 직접 삭제 처리해야 했습니다. 이는 폴링 주기 설정, 배치 크기 관리, 부분 실패 처리, 삭제 로직을 모두 직접 구현해야 한다는 뜻입니다.

2질문 제기

Lambda가 SQS 큐의 메시지를 자동으로 배치 단위로 가져가서 처리하고, 성공 여부에 따라 자동으로 삭제할 수 있을까?

3구조적 핵심 예시

SQS에 100개의 메시지가 쌓여 있을 때, Lambda 이벤트 소스 매핑을 설정하면 Lambda가 10개씩(배치 크기) 묶어서 가져가고, 함수 파라미터로 이 10개 메시지 배열을 받아 처리한 후, 성공하면 그 10개가 자동으로 큐에서 삭제되는 방식입니다.

4단계별 동작 과정

  1. 이벤트 소스 매핑 설정Lambda 함수와 SQS 큐를 연결하는 설정에서 배치 크기(몇 개씩 묶을지), 타임아웃, 에러 발생 시 DLQ(Dead Letter Queue, 처리 실패한 메시지를 보관하는 별도 큐)로 보낼지 여부를 정합니다.
  2. Lambda가 주기적으로 폴링Lambda가 설정된 간격마다 SQS를 확인하고, 메시지가 있으면 배치 크기만큼 가져가서 한 번의 함수 호출로 전달합니다.
  3. 성공 시 자동 삭제함수가 성공 상태로 종료하면 처리한 배치의 메시지들이 SQS 큐에서 자동으로 삭제되어 중복 처리되지 않습니다.

Kinesis·DynamoDB 스트림 연동과 상태 저장 윈도우

샤드 단위로 순서를 지키며 스트림 레코드를 읽고, 텀블링 윈도우로 여러 배치에 걸친 집계 상태를 이어서 유지할 수 있다.

1상대의 출발점 확인

Kinesis나 DynamoDB 스트림은 데이터 순서가 중요합니다. 하지만 Lambda 함수는 매번 독립적으로 실행되기 때문에 함수 실행 간에 상태(예: 누적 합계, 개수)를 메모리에 유지할 수 없고, 여러 배치에 걸쳐 집계하려면 외부 데이터베이스에 매번 저장했다 로드했다 해야 했습니다.

2질문 제기

Lambda가 여러 배치에 걸쳐 상태를 자동으로 유지하면서도 샤드(순서가 보장된 파티션)의 순서를 지킬 수 있을까?

3구조적 핵심 예시

센서에서 매초 온도 데이터가 Kinesis 스트림으로 들어올 때, Lambda를 30초 텀블링 윈도우(겹치지 않는 30초 구간)로 설정하면, 0~30초 동안의 모든 데이터 합계와 개수를 첫 번째 배치에서 계산하고, 30~60초 동안의 데이터에 대해 두 번째 배치를 실행할 때 첫 번째 배치의 누적 상태(합계, 개수)가 자동으로 전달되어 평균을 계산하는 방식입니다.

4단계별 동작 과정

  1. 텀블링 윈도우 설정Lambda 이벤트 소스 매핑에서 윈도우 크기(예: 30초)를 지정합니다. 이는 데이터를 겹치지 않는 구간으로 나누는 설정입니다.
  2. 상태 자동 전달각 배치 실행 시 Lambda의 Invocation Context(함수 실행 환경 메타데이터)에 이전 윈도우의 집계 상태가 포함되어 함수에 전달되므로, 함수는 그 상태에서 현재 배치를 이어서 계산합니다.
  3. 윈도우 종료 및 결과 출력윈도우 시간이 경과하면 최종 집계 결과를 출력하고 상태를 초기화한 후 다음 윈도우를 시작합니다.

8이벤트 소스 매핑: 스트림·큐 통합08-08

Kafka(MSK·자체 관리)·MQ·DocumentDB 연동

MSK·자체 관리 Kafka, Amazon MQ, DocumentDB 변경 스트림도 이벤트 소스 매핑으로 연결해 같은 배치 소비 모델로 처리한다.

1상대의 출발점 확인

MSK(Amazon Managed Streaming for Apache Kafka), 자체 관리 Kafka, Amazon MQ, DocumentDB 변경 스트림 같은 다양한 메시징·스트리밍 소스는 각각 다른 프로토콜과 클라이언트 라이브러리를 사용합니다. 애플리케이션이 각 소스에 접근하려면 프로토콜별 연결 로직을 따로 구현하고, 배치 처리·오프셋 관리도 소스마다 다르게 처리해야 했습니다.

2질문 제기

Lambda가 SQS나 Kinesis처럼 Kafka, MQ, DocumentDB도 자동 폴링해서 배치 처리할 수 있을까?

3구조적 핵심 예시

MSK 토픽에 메시지가 계속 들어올 때, Lambda 이벤트 소스 매핑을 설정하면 Lambda가 배치 크기(예: 100개)만큼 메시지를 자동으로 가져가서 함수를 호출하고, 처리 완료 후 Kafka 오프셋(다음에 읽을 메시지 위치)이 자동으로 진행되어 중복 처리를 방지하는 방식입니다.

4단계별 동작 과정

  1. 이벤트 소스 매핑 설정Lambda와 Kafka/MQ/DocumentDB 소스를 연결하고, 배치 크기, Lambda가 실행되는 VPC(Virtual Private Cloud, AWS 내 격리된 네트워크) 내 소스 접근 권한, 인증 방식(IAM, API 키 등)을 설정합니다.
  2. 자동 폴링 및 배치 처리Lambda가 주기적으로 소스를 확인하고, 메시지·문서 변경을 배치 단위로 가져가 함수를 호출합니다.
  3. 오프셋·시퀀스 자동 커밋함수가 성공하면 Kafka 오프셋이나 MQ·DocumentDB의 진행 상태(Cursor)가 자동으로 진행되어 다음 배치부터 새로운 항목만 처리합니다.

1상대의 출발점 확인

Step Functions로 워크플로 오케스트레이션

여러 Lambda 함수를 상태 머신의 단계로 이어 붙여 순서·분기·재시도를 관리하는 워크플로를 만든다.

1상대의 출발점 확인

여러 Lambda 함수를 순차 실행하거나 조건에 따라 다른 함수를 실행하려면, 첫 번째 함수가 두 번째 함수를 호출하는 식으로 함수 내부에 오케스트레이션 로직을 직접 작성해야 했습니다. 이렇게 하면 함수 간 의존성이 복잡해지고, 재시도·타임아웃·에러 처리를 각 함수마다 반복 구현해야 하며, 전체 흐름을 파악하기 어렵습니다.

2질문 제기

3구조적 핵심 예시

주문 처리에서 (1) 결제 함수 실행 → (2) 결제 성공하면 배송 함수 실행, 실패하면 환불 함수 실행 → (3) 배송 함수가 실패하면 3회까지 자동 재시도 → 전체 흐름을 Step Functions 상태 머신(State Machine, 단계와 분기를 정의한 자동화 규칙)으로 선언해서 관리하는 방식입니다.

4단계별 동작 과정

  1. 상태 머신 정의JSON 형식의 Amazon States Language(AWS 상태 정의 언어)로 각 단계(상태)별로 실행할 함수, 다음 단계로 진행할 조건, 실패 시 재시도 정책(재시도 횟수, 대기 시간), 타임아웃을 선언합니다.
  2. 실행 흐름 자동 제어사용자가 워크플로를 시작하면 Step Functions 엔진이 상태 머신 정의를 따라 Lambda 함수들을 순차·병렬로 호출하고, 분기 로직과 재시도를 자동으로 처리합니다.
  3. 실행 추적 및 모니터링각 단계의 입력·출력, 실행 시간, 상태 변화가 모두 기록되어 AWS Console에서 시각적인 실행 흐름 다이어그램으로 조회할 수 있습니다.

확장이 Lambda와 대화하는 HTTP 인터페이스로, Extensions API 는 수명주기 이벤트를 구독하고 Telemetry/Logs API 는 함수의 로그와 실행 텔레메트리를 스트림으로 받아간다.

3구조적 핵심 예시

Lambda 함수 옆에 HTTP 엔드포인트로 대기 중인 확장(Extension)이 있다. 함수가 Extensions API를 통해 "나는 SHUTDOWN 이벤트를 구독합니다"라고 등록하면, 함수가 종료될 때 그 이벤트를 확장에 전달한다. Telemetry API는 함수의 로그 스트림을 확장이 구독하도록 하고, Logs API는 CloudWatch Logs로 올라가는 로그를 동시에 확장으로도 보낸다.

4단계별 동작 과정

  1. 확장 등록함수 시작 시 Extensions API를 호출해서 "다음 이벤트들을 구독합니다"라고 선언하면 Lambda 런타임이 이를 기록한다.
  2. 이벤트 발생 및 전달함수 실행 중 로그가 생기면 Logs API 구독자에게 전송되고, 함수가 SHUTDOWN되려 하면 그 정보도 구독자에게 HTTP POST로 전달된다.
  3. 확장의 처리확장이 받은 로그·텔레메트리를 가공해서 모니터링 도구나 데이터 호수(Data Lake)로 바로 보낼 수 있다.

4단계별 동작 과정

  1. 실행 및 기록함수가 단계를 실행하고 결과를 Durable Functions 상태 저장소에 기록한다.
  2. 중단 및 재개함수가 끊어지거나 타임아웃되면, 다음 호출에서 저장된 체크포인트를 조회한다.
  3. 리플레이재개 호출에서 이미 기록된 단계들은 실제로 재실행하지 않고, 저장된 결과값으로 건너뛰고 미완료 단계부터 계속 진행한다.

Infrastructure as Code: SAM·CDK·CloudFormation

함수와 트리거, 권한을 콘솔 클릭 대신 템플릿 코드로 정의해 똑같은 환경을 반복 배포하는 방식이다.

1상대의 출발점 확인

기존에는 AWS 콘솔에서 Lambda 함수를 만들고, 트리거를 클릭해서 설정하고, IAM 권한을 수동으로 부여했다. 이런 방식은 몇 개 함수일 땐 괜찮지만, 환경이 여러 개(개발·스테이징·운영)가 되거나 팀원이 같은 셋업을 반복해야 하면 실수하기 쉽고 일관성을 유지하기 어려웠다.

2질문 제기

함수, 트리거, 권한을 손으로 클릭 대신 코드로 정의해서, 같은 환경을 반복 배포하고 버전 관리할 수 있을까?

3구조적 핵심 예시

SAM이나 CloudFormation 템플릿은 YAML이나 JSON 형태의 파일로, "이 함수를 메모리 1024MB로 만들고, S3 업로드 이벤트가 트리거고, 이 역할(IAM 권한) 아래에서 실행" 같은 내용을 텍스트로 적는다. 그 파일을 클라우드에 배포하면, 정의된 리소스가 자동으로 만들어진다.

4단계별 동작 과정

  1. 템플릿 작성YAML 파일에 함수 정의, 트리거, IAM 권한, 환경 변수 등을 선언한다.
  2. 배포CLI 명령어로 템플릿을 클라우드에 제출하면, CloudFormation(AWS의 템플릿 처리 엔진)이 정의된 리소스를 차례대로 생성한다.
  3. 재배포와 버전 관리템플릿을 수정하고 다시 배포하면 자동으로 업데이트되고, 파일이 코드 저장소에 들어가므로 누가 무엇을 바꿨는지 추적할 수 있다.

로컬 개발과 GitHub Actions CI/CD, VS Code 디버깅

내 PC에서 함수를 실행·중단점 디버깅하고, 코드를 푸시하면 자동으로 배포되게 만드는 개발 흐름이다.

1상대의 출발점 확인

이전에는 코드를 작성한 뒤 AWS에 배포하고, 클라우드에서만 테스트할 수 있었다. 로컬에서 디버거를 연결하거나 즉시 피드백을 받기 어려웠고, 배포 후 문제를 발견하면 코드를 수정하고 다시 배포하는 과정을 반복해야 했다.

2질문 제기

로컬 PC에서 디버거를 붙여 함수를 멈춰서 검사하고, 코드를 저장소에 푸시하면 자동으로 클라우드에 배포할 수 있을까?

3구조적 핵심 예시

SAM CLI는 내 PC에서 Lambda 환경을 흉내 내는 로컬 서버를 띄운다. 내 IDE(VS Code 같은 편집기)에서 중단점을 설정하고 함수를 실행하면, 서버가 그 중단점에서 멈춰서 변수를 검사할 수 있다. GitHub에 푸시하면 GitHub Actions(자동 실행 도구)가 테스트와 배포를 자동으로 실행한다.

4단계별 동작 과정

  1. 로컬 개발 및 디버깅SAM CLI를 통해 내 PC에서 함수를 실행하고, VS Code 디버거를 붙여 중단점에서 멈춰 상태를 검사한다.
  2. 코드 푸시코드를 GitHub 같은 저장소에 커밋하고 푸시한다.
  3. 자동 배포GitHub Actions 같은 CI/CD 파이프라인이 트리거되어 테스트를 실행하고, 성공하면 AWS에 자동으로 배포한다.

Powertools for AWS Lambda와 AI 코딩 에이전트 설정

구조화 로깅·메트릭·트레이싱 같은 반복 코드를 대신 처리해 주는 공식 라이브러리와, AI 코딩 에이전트가 Lambda 개발을 돕도록 붙이는 설정이다.

1상대의 출발점 확인

Lambda 함수를 작성할 때마다 로깅 코드(함수가 뭘 했는지 기록), 메트릭 전송 코드(성능 데이터 수집), 트레이싱 코드(요청이 각 단계에서 얼마나 걸렸는지 추적) 등을 반복해서 써야 했다. 이런 코드는 함수 로직과 무관하지만 필수적이어서, 매번 같은 패턴을 복사-붙여넣기 하는 낭비가 발생했다.

2질문 제기

로깅, 메트릭, 트레이싱 같은 반복 코드를 매번 쓰는 대신 자동으로 처리하고, AI 에이전트가 Lambda 코드 작성을 도와줄 수 있을까?

3구조적 핵심 예시

Powertools for Lambda는 파이썬이나 자바 라이브러리로, 함수 코드에 몇 줄의 데코레이터(함수 위에 붙이는 설정)를 추가하면 로깅, 메트릭, 트레이싱이 자동으로 처리된다. 그 위에 AI 코딩 에이전트(Claude 같은 AI)를 클라우드 IDE에 붙이면, 코드 작성을 제안받을 수 있다.

4단계별 동작 과정

  1. Powertools 설정함수 코드에 Powertools 라이브러리를 import하고, 데코레이터를 추가한다.
  2. 자동 처리함수가 실행될 때마다 로깅, 메트릭, 트레이싱이 자동으로 CloudWatch와 X-Ray(AWS의 모니터링 서비스)에 전송된다.
  3. AI 에이전트 통합VS Code나 AWS의 클라우드 IDE에 AI 코딩 에이전트를 붙이면, 코드 작성 중에 제안을 받거나 질문에 답변받을 수 있다.

Lambda 함수 테스트 전략

클라우드에 올리기 전과 후에 함수를 단위·통합 수준으로 검증하는 방법을 정리한 지침이다.

1상대의 출발점 확인

Lambda 함수는 S3, DynamoDB, SNS 같은 AWS 서비스와 연동하는데, 이들을 모두 연동한 상태에서만 테스트했다면 테스트 환경을 구성하기 복잡하고, 각 함수 버전마다 수동으로 검증해야 했다. 또한 작은 버그 하나가 프로덕션까지 가서 발견되기도 했다.

2질문 제기

함수 로직은 독립적으로, 외부 서비스 연동은 따로 테스트해서, 배포 전에 모든 케이스를 빠르게 검증할 수 있을까?

3구조적 핵심 예시

단위 테스트는 S3나 DynamoDB를 실제로 호출하지 않고, 그 서비스들이 반환할 데이터를 미리 정의(Mock 객체)해서, 함수 로직만 검증한다. 통합 테스트는 실제 AWS 서비스를 사용하거나 로컬 환경을 흉내 내서, 함수가 실제 환경에서 동작하는지 확인한다.

4단계별 동작 과정

  1. 단위 테스트외부 서비스 호출을 Mock(가짜 객체)으로 대체하고, 함수의 로직만 검증한다. 가장 빠르고 반복적으로 실행할 수 있다.
  2. 통합 테스트LocalStack(로컬에서 AWS를 흉내 내는 도구)이나 테스트용 AWS 계정을 사용해, 실제 서비스 연동을 검증한다.
  3. 배포 후 테스트프로덕션 환경의 함수를 실제 요청으로 검증하거나, 프로덕션 데이터를 복사한 환경에서 테스트한다.

단위·통합·배포 후 테스트를 계층별로 나눠서, 배포 전에 버그를 발견하고 배포 후 신뢰도를 높이는 것

쿼터·모범 사례·예제 애플리케이션

Lambda가 걸어 둔 한도 값과 권장 설계 습관, 그리고 바로 실행해 볼 수 있는 공식 예제 모음이다.

1상대의 출발점 확인

Lambda를 쓸 때 함수 타임아웃(실행 제한 시간)이나 메모리 한도, 동시 실행 개수, 배포 패키지 크기 같은 상한선이 있다는 걸 모르고 쓰다가, 갑자기 함수가 실패하거나 느려지곤 했다. 또한 어떻게 설계해야 Lambda에 적합한지, 어떤 비용 최적화 방법이 있는지 알기 어려웠다.

2질문 제기

Lambda의 한도를 미리 알고, 모범 사례에 따라 설계하면서, 공식 예제로 빠르게 학습할 수 있을까?

3구조적 핵심 예시

AWS 공식 문서는 "Lambda 함수 최대 메모리 10GB, 타임아웃 15분, 동시 실행 1000개(기본값)" 같은 쿼터(상한선)를 명시하고, "함수 크기를 작게 유지하라", "환경 변수로 설정을 외부화하라", "재사용 가능한 핸들러를 설계하라" 같은 모범 사례를 제시한다. 또한 API Gateway와 Lambda 연동, S3 이벤트 처리 등 실제 사용 패턴의 예제를 제공한다.

4단계별 동작 과정

  1. 쿼터 확인함수를 설계하기 전에 메모리, 타임아웃, 패키지 크기, 동시 실행 한도를 확인하고 설계에 반영한다.
  2. 모범 사례 적용함수 크기 최소화, 초기화 코드 분리(콜드 스타트 단축), 환경 변수 활용, 에러 처리 등의 권장 패턴을 적용한다.
  3. 예제 활용AWS 공식 예제를 참고하거나 복사해서, 흔한 사용 사례(HTTP API, 이벤트 처리, 데이터 변환)를 빠르게 구현한다.
