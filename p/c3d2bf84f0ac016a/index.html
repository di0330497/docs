1부. Redis 입문과 기본 개념001

Redis 소개

Redis가 무엇이고 어떤 문제를 푸는 도구인지

쇼핑몰에서 인기 상품 목록을 화면에 띄울 때마다 데이터베이스에 같은 질의를 수천 번 보내면 응답이 눈에 띄게 느려지고, 순간적으로 사용자가 몰리면 서버가 버티지 못합니다. 이런 곤란을 줄이려고 데이터를 메모리에 올려 아주 빠르게 읽고 쓰도록 만든 저장소가 Redis(레디스)이고, 키-값(key-value) 형태로 데이터를 다루는 NoSQL 데이터베이스 계열에 속합니다.

회사에서 서류를 찾을 때 지하 문서고까지 내려가는 대신 책상 서랍에서 바로 꺼내 쓰는 상황을 떠올리면 쉽습니다. 지하 문서고는 모든 서류를 안전하게 보관하지만 찾는 데 시간이 걸리고, 책상 서랍은 좁은 대신 꺼내는 즉시 손에 들어옵니다.

Redis가 데이터를 메모리에 두는 것은 서류를 책상 위에 올려두는 일이고, 원본 데이터베이스는 문서고처럼 모든 데이터를 디스크에 남기는 역할을 맡습니다. 여기에 만료 시간을 붙여 잠깐만 보관하거나, 여러 서버가 같은 서랍을 함께 보게 하는 식으로 확장할 수 있습니다.

정리하면 Redis는 자주 쓰는 데이터를 메모리에 보관해 아주 짧은 지연으로 응답하는 인메모리(in-memory) 키-값 저장소이며, 원본 데이터베이스 앞에서 속도를 책임지는 캐시(cache)로 가장 널리 쓰입니다.

인메모리 저장소

데이터를 메모리에 두면 왜 빠른지

웹사이트에서 같은 상품 정보를 보여줄 때마다 하드디스크나 SSD까지 다녀와야 한다면, 아무리 좋은 서버라도 1초에 처리할 수 있는 요청 수가 크게 줄어듭니다. 데이터를 메모리(memory)에 올려두고 읽는 인메모리 저장소(in-memory store)는 이 왕복을 없애 응답 시간을 줄이는 방법입니다.

주방을 떠올리면 이해가 쉽습니다. 냉장고나 창고에 있는 재료를 매번 꺼내러 가면 요리 속도가 느려지지만, 자주 쓰는 양념과 재료를 조리대 위에 올려두면 손을 뻗는 즉시 쓸 수 있습니다.

메모리는 전원이 꺼지면 내용이 사라지는 대신 전기 신호만으로 접근해 디스크보다 훨씬 빠르고, Redis는 이 특성을 그대로 받아들여 속도를 얻습니다. 그래서 서버가 다시 시작되면 메모리의 데이터는 기본적으로 사라지며, 중요한 데이터는 디스크에 따로 남기는 설정을 함께 씁니다.

결국 인메모리 저장소란 데이터를 디스크가 아닌 메모리에 두어 읽기와 쓰기의 지연을 줄인 저장 방식이고, Redis는 그 위에 만료와 복제, 영속화 같은 기능을 얹은 구현체입니다.

키-값 저장 구조

키 하나로 값을 찾는 기본 동작 방식

데이터를 목록으로 늘어놓고 하나씩 비교하며 찾으면 항목이 늘수록 느려지고, 여러 조건을 조합한 질의는 더 복잡해집니다. 키(key) 하나를 주면 값(value) 하나를 바로 돌려주는 키-값 구조는 이 탐색 비용을 없애는 가장 단순한 방법입니다.

도서관 사물함을 떠올리면 됩니다. 사물함 번호를 알면 문을 한 번 열어 물건을 꺼내지만, 번호를 모르면 수백 개를 차례로 열어봐야 합니다.

Redis는 키를 해시 테이블(hash table)로 관리해 번호에 해당하는 칸을 곧바로 찾아가고, 값 자리에는 문자열뿐 아니라 목록과 집합, 정렬된 집합 같은 여러 자료 구조를 넣을 수 있습니다. 다만 사물함 번호가 겹치면 안 되듯 키는 저장소 안에서 유일해야 하고, 값 전체를 통째로 읽고 쓰는 방식이라 값 안의 일부만 골라 고치는 질의는 지원하지 않습니다.

정리하면 키-값 저장 구조는 유일한 키로 값을 즉시 찾는 방식이고, Redis는 여기에 값의 종류를 늘리고 만료 시간을 붙여 캐시와 세션 저장 같은 용도에 맞춘 저장소입니다.

Redis vs Memcached

둘의 공통점과 결정적인 차이

캐시를 도입하려는 팀이 둘 중 무엇을 고를지 몰라 한참을 비교하다 일정을 놓치는 일이 흔합니다. 두 도구 모두 데이터를 메모리에 두는 키-값 저장소라 겉모습이 비슷하지만, 값의 형태와 확장 방식에서 갈립니다.

이삿짐 보관소를 떠올려 보면, 두 곳 모두 짐을 맡기고 찾는 기본 동작은 같지만 한 곳은 상자째 맡기는 단순 보관만 하고 다른 곳은 서류를 종류별로 나눠 꽂아둘 수 있습니다.

Memcached(멤캐시드)는 문자열 위주의 단순한 상자 보관에 집중하고, Redis는 목록과 집합, 해시 같은 구조를 값으로 담아 서버 쪽에서 가공까지 합니다. 또 Redis는 데이터를 디스크에 남기는 영속화, 복제와 클러스터 같은 확장 기능, 만료 알림과 트랜잭션을 갖추고 있어 단순 캐시를 넘어 세션 저장이나 순위표에도 쓰입니다. 반대로 Memcached는 구조가 단순하고 여러 서버에 데이터를 나누는 방식이 가벼워, 순수한 캐시만 필요하면 여전히 좋은 선택입니다.

결국 둘 다 인메모리 키-값 캐시지만, 값의 자료 구조와 영속성, 확장 기능을 어디까지 필요로 하는지가 선택을 가르며 그 폭이 넓은 쪽이 Redis입니다.

키 이름 설계

콜론으로 계층을 나누는 이름 짓기

키 이름을 user123, data1처럼 아무렇게나 붙이면 몇 달 뒤에는 어느 키가 무엇인지 알 수 없고, 같은 데이터를 서로 다른 이름으로 중복 저장해 메모리를 낭비하기 쉽습니다. 콜론으로 계층을 나누는 키 이름 규칙은 저장소를 사람이 읽을 수 있는 지도로 만드는 방법입니다.

아파트 주소를 떠올리면 됩니다. 시와 구, 동, 번지, 호수를 순서대로 적으면 한 줄만 보고도 어디인지 알 수 있고, 순서를 지키면 같은 동네 항목이 자연스럽게 모입니다.

user:42:profile 처럼 콜론으로 단계를 이어 붙이면 앞부분으로 대상을, 뒷부분으로 그 대상의 어떤 값을 담았는지 구분할 수 있습니다. 이 규칙을 지키면 공통 접두사를 가진 키만 골라 한꺼번에 지우거나 목록을 뽑는 작업이 쉬워지고, 서비스 이름을 맨 앞에 두면 한 저장소를 여러 서비스가 나눠 쓸 때도 충돌이 줄어듭니다.

정리하면 키 이름은 콜론으로 구분된 계층적 접두사 규칙을 따라 짓고, 이 규칙이 곧 조회와 삭제의 범위이자 메모리 관리의 단위가 됩니다.

Redis 설치

패키지와 도커로 개발 환경 만들기

Redis를 써보려는데 운영체제마다 설치 방법이 달라 첫 단계에서 막히는 경우가 많고, 손으로 설치한 환경은 팀원마다 버전이 달라 재현이 안 되기도 합니다. 패키지 관리자나 도커(Docker)로 개발 환경을 만드는 방법이 이 문제를 줄여줍니다.

이사를 갈 때 가구를 하나씩 사서 조립하면 집집마다 모양이 달라지지만, 규격화된 세트를 그대로 들여놓으면 어느 집이든 같은 모습입니다. 리눅스에서는 배포판의 패키지 관리자로 redis 패키지를 설치하면 실행 파일과 기본 설정이 함께 들어오고, 도커에서는 redis 이미지를 받아 컨테이너로 띄우면 호스트 운영체제와 무관하게 같은 버전을 쓸 수 있습니다. 컨테이너로 띄울 때는 포트를 호스트에 연결하고, 데이터를 남기려면 볼륨을 붙여야 하며, 개발용이라도 외부에 그대로 열지 않도록 접근 범위를 좁히는 것이 좋습니다.

결국 Redis 설치는 패키지 관리자로 직접 넣거나 도커 컨테이너로 띄우는 두 갈래이고, 팀이 같은 환경을 재현하려면 컨테이너 쪽이 편합니다.

redis-cli 사용법

명령줄에서 접속하고 명령 실행하기

Redis를 쓰기로 했는데 어디에 어떤 값이 들어 있는지 눈으로 확인할 방법이 없으면, 프로그램 코드를 고쳐 로그를 찍고 다시 배포하는 일을 반복하게 됩니다. redis-cli는 이런 때 서버에 직접 말을 걸어 값을 넣고 빼 보고 상태를 물어볼 수 있게 해 주는 명령줄 도구(command-line interface)입니다.

아파트 관리사무소 창구를 떠올려 보면 이해가 쉽습니다. 창구에는 정해진 주소(호스트)와 호 번호(포트)가 있고, 그 앞에 서서 "1101호 등기부 보여 주세요"처럼 정해진 말투로 요청하면 직원이 바로 처리해 줍니다.

redis-cli도 마찬가지로 서버의 주소와 포트로 접속한 뒤 GET이나 SET 같은 명령을 한 줄씩 건네고, 결과를 화면에 그대로 돌려받습니다. 창구에서 여러 건을 한 번에 접수하듯 명령 파일을 통째로 넘기거나, 접속한 채로 계속 대화를 이어 갈 수도 있습니다.

정리하면 redis-cli는 Redis 서버에 접속해 명령을 주고받는 대화형 도구이며, 별도 프로그램 없이 저장된 값과 서버 상태를 즉시 확인하고 고칠 수 있게 해 줍니다.

데이터베이스와 SELECT

한 인스턴스 안에서 DB를 나눠 쓰는 방법

한 Redis 서버에 여러 서비스가 함께 붙으면 서로 다른 서비스의 키가 한 바구니에 섞여, 이름이 겹치거나 실수로 남의 데이터를 지우는 사고가 생깁니다. SELECT는 한 인스턴스 안에 번호가 붙은 데이터베이스(database)를 여러 개 두고, 접속을 그중 하나로 옮겨 쓰게 해 주는 명령입니다.

아파트 한 동에 여러 세대가 사는 구조를 떠올려 보면 됩니다. 건물은 하나지만 현관문 번호가 0호, 1호, 2호처럼 나뉘어 있고, 각 세대의 신발장과 냉장고는 서로 완전히 따로 관리됩니다.

Redis도 기본값인 0번 데이터베이스에서 시작해 SELECT 1처럼 번호를 지정하면 그 번호의 공간으로 시야가 옮겨 가고, 그 뒤의 명령은 모두 그 공간에만 적용됩니다.

다만 건물의 전기와 수도처럼 서버의 메모리와 처리 능력은 모든 세대가 나눠 쓰기 때문에, 한 세대가 너무 무거운 짐을 들이면 다른 세대도 영향을 받습니다.

정리하면 SELECT는 하나의 Redis 인스턴스 안에서 번호로 구분된 논리적 데이터베이스를 골라 쓰는 명령이며, 키를 서로 격리하되 자원은 공유한다는 점을 기억하면 됩니다.

TTL과 만료

시간이 지나면 저절로 사라지는 키

세션 정보나 인증 코드처럼 잠깐만 쓰고 버릴 값을 영원히 쌓아 두면 메모리가 계속 불어나고, 언젠가는 서버가 값을 받지 못하는 지경에 이릅니다. TTL(time to live, 살아 있는 시간)은 키마다 수명을 정해 두고 시간이 지나면 Redis가 알아서 지워 주는 기능입니다.

아파트 택배 보관함에 붙은 자동 폐기 안내문을 떠올리면 쉽습니다. 물건을 넣으면서 "사흘 뒤까지 찾아가지 않으면 폐기합니다"라고 기한을 적어 두면, 관리인이 그 날짜가 지난 물건을 따로 치워 줍니다.

Redis도 EXPIRE 명령이나 SET에 붙이는 옵션으로 키에 기한을 적어 두고, 시간이 다 되면 그 키를 스스로 지웁니다.

기한이 지난 키는 조회할 때 없는 것처럼 보이고, 남은 시간은 TTL 명령으로 물어볼 수 있으며, 값을 다시 덮어쓰면 기한도 새로 잡힙니다.

정리하면 TTL은 키에 만료 시각을 붙여 자동으로 정리되게 하는 장치이며, 메모리를 사람이 직접 청소하지 않아도 되게 만드는 Redis의 대표적인 관리 기능입니다.

데이터 타입 개요

String부터 Stream까지 무엇이 있는지

값을 모두 글자 하나로만 저장한다면 목록의 순서를 유지하거나 점수순으로 정렬하는 일을 매번 프로그램에서 직접 해야 하고, 그 코드는 금세 복잡해집니다. Redis가 String부터 Stream까지 여러 데이터 타입(data type)을 제공하는 이유는, 자주 쓰는 자료 구조를 서버가 직접 이해하고 처리하게 하려는 것입니다.

철물점의 칸막이 진열장을 떠올려 보면 이해가 쉽습니다. 못은 못 칸에, 나사는 나사 칸에 넣어 두면 꺼낼 때도 찾기 쉽고 개수도 바로 셀 수 있습니다.

Redis도 하나의 값에 문자열(String), 해시(Hash), 리스트(List), 집합(Set), 정렬 집합(Sorted Set), 비트맵(Bitmap), 하이퍼로그로그(HyperLogLog), 지오(Geospatial), 스트림(Stream) 같은 타입 표시를 붙여 저장하고, 타입에 맞는 전용 명령으로 다룹니다.

그래서 순서가 중요한 일은 리스트가, 중복 없는 포함 여부는 집합이, 점수에 따른 순위는 정렬 집합이 각각 맡습니다.

정리하면 Redis의 데이터 타입은 값의 생김새와 용도에 따라 고르는 저장 형식이며, 알맞은 타입을 고르는 것만으로 애플리케이션 코드가 크게 줄어듭니다.

정리하면 String은 키와 문자열 값의 단순한 짝을 저장하는 타입이며, 단순한 만큼 캐시와 카운터, 세션 값처럼 폭넓은 자리에 가장 먼저 쓰입니다.

2부. 문자열과 기본 명령012

SET과 GET

값을 저장하고 꺼내는 기본 명령

값을 저장했는데 프로그램을 다시 켜면 사라지거나, 다른 서버에서는 같은 값을 다시 계산해야 한다면 매번 느린 원본 저장소를 거쳐야 합니다. SET과 GET은 Redis에서 값을 키에 넣고 꺼내는 가장 기본이 되는 두 명령입니다.

사물함 대여소를 떠올려 보면 딱 맞습니다. SET은 "3번 사물함에 이 가방을 넣어라"라고 지정하는 일이고, GET은 "3번 사물함 내용물을 보여 달라"라고 요청하는 일입니다. 같은 번호에 다시 SET을 하면 안에 있던 것은 새 물건으로 교체되고, 없는 번호를 GET하면 빈손이라는 표시가 돌아옵니다. 넣으면서 동시에 기한을 적거나, 이미 값이 있을 때만 넣도록 조건을 붙이는 변형도 있어 덮어쓰기 사고를 막을 수 있습니다.

정리하면 SET은 키에 값을 쓰고 GET은 그 값을 읽어 오는 명령이며, 이 두 가지가 Redis 사용의 출발점이자 가장 자주 불리는 기본 동작입니다.

2부. 문자열과 기본 명령013

SET 옵션 EX NX XX

만료와 조건을 한 번에 붙여 저장하기

만료 시간을 따로 걸지 않고 값을 저장하면 잊힌 데이터가 계속 쌓여 메모리를 조용히 잡아먹습니다. 게다가 여러 요청이 같은 키를 동시에 만들려고 하면 늦게 도착한 쪽이 먼저 저장한 값을 아무 말 없이 덮어씁니다.

이 두 가지 곤란을 한 번의 명령으로 해결하려고 Redis의 SET 명령에는 EX, NX, XX라는 옵션이 붙었습니다. 아파트 무인 택배 보관함을 떠올려 보면, EX는 물건을 넣을 때 붙이는 보관 기한 라벨과 같아서 기한이 지나면 칸이 저절로 비워집니다. NX는 빈 칸일 때만 물건을 넣으라는 조건이고, XX는 이미 예약된 칸에만 넣으라는 조건이라 조건에 맞지 않으면 넣지 않고 실패를 알려 줍니다.

이 옵션들은 값, 만료 시간, 조건을 한 줄에 함께 적을 수 있어서 먼저 확인하고 나중에 저장하는 두 번의 왕복을 없애 줍니다. 즉 SET에 EX와 NX를 함께 주면 없을 때만 정해진 시간 동안 저장하라는 규칙이 하나의 원자적(atomic, 중간에 끼어들 수 없는) 동작으로 처리됩니다.

정리하면 SET의 옵션은 값 저장에 만료와 조건을 붙여, 경쟁 상황에서도 한쪽만 성공하게 만드는 Redis의 대표적인 안전장치입니다.

2부. 문자열과 기본 명령014

INCR와 DECR

값을 원자적으로 늘리고 줄이기

조회수처럼 여러 곳에서 동시에 1씩 더하는 값을 읽고 고쳐 쓰는 방식으로 다루면, 두 요청이 같은 값을 읽은 뒤 각자 계산해 저장하면서 한 번의 증가가 사라집니다. 이런 유실은 트래픽이 몰릴 때만 드물게 나타나서 원인을 찾기도 매우 어렵습니다.

그래서 Redis는 값을 읽고 쓰는 과정을 하나로 묶은 INCR과 DECR 명령을 제공합니다.

회사 정문에 설치된 출입 카운터를 떠올려 보면, 사람이 화면의 숫자를 보고 직접 적는 것이 아니라 문을 통과하는 순간 기계가 스스로 숫자를 하나 올립니다. INCR은 이 카운터의 증가 버튼이고 DECR은 감소 버튼이며, 여러 명이 동시에 지나가도 각 통과가 정확히 한 번씩만 반영됩니다.

이 명령은 저장된 값을 숫자로 해석해 1을 더하거나 빼고 그 결과를 돌려주며, 키가 없으면 0에서 시작한 것으로 봅니다.

정리하면 INCR과 DECR은 읽기와 쓰기를 분리하지 않고 한 동작으로 처리하는 원자적(atomic) 증감 연산이라, 동시 접근에도 값이 어긋나지 않습니다.

MSET과 MGET

여러 키를 한 번에 읽고 쓰기

키를 백 개 저장해야 할 때 명령을 백 번 보내면 그만큼 네트워크 왕복이 쌓여, 값 자체보다 기다리는 시간이 더 커집니다. 읽을 때도 마찬가지라서 하나씩 요청하면 같은 지연을 백 번 치르게 됩니다.

Redis의 MSET과 MGET은 여러 키를 한 번의 요청으로 묶어 처리하도록 만든 명령입니다.

택배를 한 건씩 보내는 대신 한 트럭에 모아 실어 보내는 것과 같아서, 포장과 배송 접수라는 고정 비용을 한 번만 냅니다. MSET은 키와 값을 짝지어 여러 개 늘어놓으면 그것을 한 번에 저장하고, MGET은 키 목록을 주면 값 목록을 같은 순서로 돌려줍니다.

다만 묶음은 전부 성공하거나 전부 실패하는 방식이 아니라 각 키를 독립적으로 처리하며, MGET은 없는 키 자리에 빈 값을 넣어 순서를 지켜 줍니다.

정리하면 MSET과 MGET은 왕복 횟수를 줄이는 것이 핵심인 명령으로, 여러 키를 다룰 때 생기는 지연을 크게 낮춰 줍니다.

APPEND와 SETRANGE

문자열을 이어 붙이고 일부만 바꾸기

문자열 끝에 로그 한 줄을 덧붙이려고 기존 내용 전체를 읽어 와 다시 저장하면, 값이 길어질수록 매번 같은 크기의 데이터를 왕복시켜야 합니다. 같은 문자열의 가운데 한 글자만 바꾸고 싶을 때도 전체를 새로 쓰는 것은 낭비입니다.

APPEND와 SETRANGE는 이런 경우를 위해 문자열의 일부만 건드리는 명령으로 만들어졌습니다.

노트 한 권을 떠올려 보면, 전체를 복사해 새 공책에 옮겨 적는 대신 마지막 장 뒤에 한 줄을 이어 쓰는 것이 APPEND입니다. 이미 적힌 페이지의 특정 위치로 가서 그 자리만 새 내용으로 덮어쓰는 것이 SETRANGE이고, 그 앞뒤의 내용은 그대로 남습니다.

SETRANGE는 시작 위치를 숫자로 지정하는데, 원래 길이보다 뒤쪽을 지목하면 그 사이 빈 자리는 0으로 채워집니다.

정리하면 APPEND는 끝에 붙이고 SETRANGE는 지정한 위치를 덮어쓰는 명령으로, 둘 다 문자열 전체를 다시 쓰지 않아도 되게 해 줍니다.

2부. 문자열과 기본 명령017

문자열 크기 제한

512MB 제한과 큰 값이 만드는 부담

문자열 하나에 상한이 없다면 어떤 키가 메모리를 혼자 다 차지해 다른 데이터를 밀어내고 서버 전체가 멈출 수 있습니다. Redis는 이런 사고를 막기 위해 문자열 값의 크기를 512MB로 제한합니다.

큰 값은 저장 자체보다 그 뒤의 부담이 문제인데, 복사본을 만들 때도, 네트워크로 보낼 때도, 지울 때도 그 크기만큼 시간이 걸립니다.

창고를 떠올려 보면 한 칸에 넣을 수 있는 물건의 최대 크기가 정해져 있어서, 규격을 넘는 물건은 넣지 않고 거절합니다. 이 상한이 있으면 한 칸이 창고 전체를 잡아먹는 일을 막을 수 있고, 나머지 칸의 여유를 계산하기도 쉬워집니다.

다만 512MB는 넉넉해 보여도 실제로는 그런 값을 자주 다루지 않는 것이 좋으며, 큰 값은 응답 지연과 복제 지연을 함께 키웁니다.

정리하면 512MB 제한은 문자열 하나가 가질 수 있는 최대 크기이고, 큰 값은 메모리뿐 아니라 전송과 복사 비용까지 키우는 부담이라는 점을 기억해야 합니다.

← 이전APPEND와 SETRANGE다음 →비트 연산

2부. 문자열과 기본 명령018

비트 연산

비트를 켜고 끄는 SETBIT과 BITCOUNT

사용자 백만 명의 참석 여부를 1과 0이라는 글자로 저장하면 1메가바이트가 넘지만, 같은 정보를 비트로 담으면 8분의 1로 줄어듭니다. 참석 여부처럼 두 가지 상태만 있는 값을 다룰 때 이 차이는 저장 공간과 전송량에서 크게 벌어집니다.

Redis는 문자열을 비트 단위로 다루는 SETBIT, GETBIT, BITCOUNT 명령을 제공합니다.

극장 좌석표를 떠올려 보면 좌석마다 스위치가 하나씩 있고, SETBIT은 지정한 번호의 스위치를 켜거나 끄는 일입니다. GETBIT은 그 스위치가 켜져 있는지 확인하고, BITCOUNT는 구역 전체에서 켜진 스위치의 개수를 세어 줍니다.

좌석 번호에 해당하는 위치 값을 오프셋(offset, 몇 번째 비트인지 가리키는 번호)이라고 하며, 문자열 길이보다 먼 위치를 지정하면 그 사이는 0으로 채워집니다.

정리하면 SETBIT과 BITCOUNT는 문자열을 작은 스위치의 배열처럼 써서, 참석 여부 같은 이진 정보를 아주 작은 공간에 담고 빠르게 세는 방법입니다.

2부. 문자열과 기본 명령019

SET NX 분산 락

조건부 저장으로 잠금 흉내 내기

여러 대의 서버가 같은 재고 숫자를 동시에 고치면, 둘 다 열 개를 읽고 각자 아홉 개로 저장해 실제로는 두 개가 팔렸는데 장부에는 한 개만 줄어드는 일이 생깁니다. 이때 지금 이 값을 고치는 사람은 나 하나뿐이라는 표시를 남기는 장치가 필요한데, 그것을 Redis의 조건부 저장 명령인 SET NX로 흉내 낸 분산 락(distributed lock)이라고 합니다.

아파트 공용 창고에 열쇠가 하나뿐이라고 생각해 보면, 관리실에 열쇠가 걸려 있을 때만 그것을 가져가 문을 열 수 있고 이미 누가 가져갔다면 빈손으로 돌아와 기다려야 합니다.

SET NX는 이 키가 없을 때만 저장하라는 뜻이라, 키가 비어 있는 첫 번째 서버만 성공하고 나머지는 실패를 돌려받아 차례를 기다리게 됩니다. 여기에 만료 시간을 함께 걸어 두면 열쇠를 가진 서버가 고장 나 돌려주지 못해도 정해진 시간이 지나면 자동으로 열쇠가 관리실로 돌아옵니다.

일을 마친 서버는 자기 열쇠를 직접 반납하고, 반납할 때는 값이 자기 것인지 확인해야 남의 열쇠를 지우는 사고를 막을 수 있습니다.

결국 분산 락은 키가 없을 때만 쓰는 조건부 저장, 자동 만료, 소유자 확인 삭제라는 세 가지를 조합해 여러 서버 사이의 한 줄 서기를 만드는 기법입니다.

2부. 문자열과 기본 명령020

캐시 키 설계

원본 데이터와 캐시 데이터를 구분하기

회원 정보를 캐시에 넣어 두었다가 코드를 고쳐 화면에 보여줄 항목이 늘어나면, 예전 형식으로 저장된 값이 그대로 읽혀 일부 항목이 비어 보이는 일이 생깁니다. 이런 사고를 막으려면 캐시에 넣을 때 어떤 규칙으로 이름을 붙일지 미리 정해야 하는데, 이것이 캐시 키 설계(cache key design)입니다.

아파트 택배 보관함에 물건을 넣을 때 호수만 적으면 다른 택배 회사 물건이나 이사 간 세대의 물건과 뒤섞이므로, 동과 호수와 택배사와 날짜를 이어 붙여 한 칸을 정확히 가리키게 하는 것과 같습니다.

그래서 키는 업무 이름인 접두어, 대상을 가리키는 식별자, 값의 형식이 바뀔 때 올리는 버전 번호를 콜론으로 이어 붙여 만듭니다. 원본 데이터는 데이터베이스가 유일한 기준이고 캐시는 언제든 사라져도 다시 만들 수 있는 사본이라는 점을 키 이름만 봐도 알 수 있어야 합니다. 만료 시간은 키마다 따로 정해, 자주 바뀌는 값은 짧게 두고 거의 변하지 않는 값은 길게 두는 식으로 조절합니다.

정리하면 캐시 키는 원본과 사본을 구분하고 충돌 없이 한 대상을 가리키도록 접두어와 식별자와 버전을 규칙적으로 조합한 이름이며, 캐시는 언제 지워져도 되는 데이터라는 전제 위에서만 안전합니다.

Hash 타입

필드와 값을 묶어 객체처럼 저장하기

사용자 한 명의 이름과 나이와 이메일을 각각 다른 키에 저장하면, 같은 사람의 정보인데도 관리할 곳이 흩어지고 한 번에 모아 보기도 어렵습니다. 이렇게 한 대상에 속한 여러 값을 하나로 묶어 두고 싶을 때 쓰는 것이 Redis의 Hash 타입입니다.

한 사람의 서류를 여러 봉투에 나눠 담으면 찾을 때마다 여러 곳을 뒤져야 하지만, 한 파일철에 이름, 나이, 이메일 칸을 만들어 담으면 철 하나만 펴면 된다는 점과 같습니다.

Redis의 Hash 타입은 이 파일철과 같아서, 하나의 키 아래에 필드와 값의 쌍을 여러 개 묶어 저장합니다. 필드 이름으로 원하는 칸만 골라 읽거나 고칠 수 있고, 필드를 새로 추가해도 다른 칸은 건드리지 않습니다. 다만 한 키 안의 필드가 아주 많아지면 다시 작은 조각으로 나누는 편이 좋아, 사용자 한 명의 정보처럼 크기가 예측되는 단위로 묶는 것이 일반적입니다.

결국 Hash 타입은 하나의 키 아래에 필드와 값의 표를 두어 객체 하나를 통째로 다루는 자료 구조이며, 관련 있는 값들을 한 단위로 묶어 관리할 때 유용합니다.

3부. 해시, 리스트, 셋022

HSET과 HGET

해시의 필드를 넣고 꺼내기

해시를 쓰기로 했어도 값을 넣는 명령과 꺼내는 명령을 구분해 쓰지 않으면, 필드를 잘못 덮어쓰거나 없는 값을 읽고도 그 사실을 모르고 넘어가게 됩니다. Redis에서 해시의 필드에 값을 넣는 명령이 HSET이고, 필드 하나를 읽어 오는 명령이 HGET입니다.

이름표가 붙은 사물함을 생각해 보면, HSET은 나이 칸에 서른을 넣으면서 그 칸의 이름표까지 함께 확인하는 일이고, HGET은 나이 이름표가 붙은 칸만 열어 값을 꺼내는 일입니다.

HSET은 필드가 이미 있으면 값을 바꾸고 없으면 새 칸을 만들기 때문에, 넣기와 수정을 따로 구분할 필요가 없습니다. HGET은 없는 필드를 물으면 빈 값을 돌려주므로, 호출한 쪽은 값이 없다는 사실을 확인하고 원본 저장소에서 채워 넣는 식으로 대응합니다. 여러 필드를 한 번에 다루고 싶으면 HSET에 필드와 값을 여러 쌍 적어 넣거나 HGETALL로 전체를 읽는데, 왕복 횟수를 줄이는 것이 목적입니다.

정리하면 HSET은 해시의 필드에 값을 쓰거나 새로 만들고 HGET은 지정한 필드 하나를 읽는 명령이며, 둘을 짝으로 써서 객체의 일부만 다루는 것이 해시 활용의 기본입니다.

3부. 해시, 리스트, 셋023

해시와 JSON 비교

전체를 다시 쓰지 않고 일부만 고치는 이유

사용자 정보를 JSON 문자열 하나로 저장하면 나이 하나를 바꾸는 데도 문자열 전체를 읽어 고친 뒤 통째로 다시 써야 하고, 그 사이 다른 서버가 같은 값을 고치면 한쪽 변경이 사라집니다. 그래서 객체를 저장할 때 JSON 문자열과 해시 중 무엇을 쓸지 고민하게 되는데, 두 방식의 갈림길은 부분 수정이 가능한지에 있습니다.

계약서 한 장만 고치면 되는 일에 책 전체를 다시 인쇄해 제본하는 것과, 파일철에서 해당 장만 뽑아 바꿔 끼우는 것의 차이라고 보면 됩니다.

해시는 필드 단위로 값을 쓰기 때문에 나이 칸만 바꾸면 나머지 칸은 그대로 남고, 바꾸는 동안에도 다른 필드는 영향을 받지 않습니다. JSON은 구조가 자유롭고 중첩된 목록이나 복잡한 형태를 그대로 담을 수 있어, 객체 전체를 한 번에 읽고 쓰는 용도에는 오히려 편합니다. 반대로 해시는 필드마다 값을 따로 저장하므로 필드가 아주 많거나 깊게 중첩된 구조에는 맞지 않고, 전체를 한 번에 다루는 작업에도 불리합니다.

결국 부분 수정이 잦으면 해시, 복잡한 구조를 통째로 주고받으면 JSON이 어울리며, 두 방식 모두 원본 데이터베이스의 사본을 다룬다는 점은 같습니다.

List 타입

양쪽 끝에서 넣고 빼는 순서 있는 목록

처리해야 할 주문을 여러 서버가 나눠 가져가야 하는데 순서가 뒤섞이면, 먼저 들어온 주문이 나중에 처리되는 일이 생깁니다. 이렇게 들어온 순서를 지켜야 하는 작업을 다룰 때 쓰는 것이 Redis의 List 타입입니다.

양쪽 끝이 뚫린 긴 관을 생각해 보면, 한쪽 끝으로 공을 밀어 넣고 반대쪽 끝에서 꺼내면 먼저 넣은 공이 먼저 나오고, 같은 쪽 끝에서 넣고 빼면 나중에 넣은 것이 먼저 나옵니다.

Redis의 List는 이 관과 같아서 왼쪽과 오른쪽 양 끝에서 값을 넣고 뺄 수 있는 순서 있는 목록이며, 어느 쪽에서 넣고 빼느냐에 따라 대기열(queue)과 스택(stack) 두 가지 방식이 됩니다. 대기열로 쓸 때는 한쪽에서 넣고 반대쪽에서 꺼내 먼저 온 작업이 먼저 처리되게 하고, 여러 서버가 동시에 꺼내도 한 작업은 한 서버에만 전달됩니다. 목록이 비었을 때 꺼내려 하면 기다리게 하는 차단 명령을 쓸 수 있어, 빈 목록을 계속 확인하며 자원을 낭비하는 일을 줄입니다.

정리하면 List 타입은 양쪽 끝에서 넣고 뺄 수 있는 순서 있는 목록으로, 먼저 온 것을 먼저 처리하는 대기열이나 마지막에 온 것을 먼저 처리하는 스택을 만들 때 쓰입니다.

3부. 해시, 리스트, 셋025

LPUSH와 RPUSH

어느 쪽에 넣느냐로 순서가 달라진다

목록에 값을 넣을 때 어느 끝에 넣는지 정하지 않으면, 나중에 꺼낼 때 순서가 뒤죽박죽이 되어 일이 꼬입니다. 오전에 접수한 주문이 오후에 접수한 주문보다 늦게 처리되는 식입니다.

Redis(레디스, 메모리에 데이터를 두는 저장소)의 List(리스트, 순서가 있는 값의 줄)에는 이 방향을 정하는 두 명령이 따로 있습니다. 바로 LPUSH와 RPUSH입니다.

아파트 우편함을 생각하면 쉽습니다.

LPUSH는 왼쪽(L) 끝에, RPUSH는 오른쪽(R) 끝에 편지를 꽂는 일입니다. 왼쪽에만 계속 꽂으면 가장 최근 편지가 맨 앞에 오고, 오른쪽에만 꽂으면 먼저 온 편지가 맨 앞에 남습니다. 두 명령 모두 여러 값을 한 번에 넣을 수 있고, 넣은 뒤에는 늘어난 목록의 길이를 돌려줍니다. 같은 목록에 두 명령을 섞어 쓰면 앞뒤 양쪽에서 자라는 구조가 되므로, 어느 쪽으로 꺼낼지를 먼저 정해 두어야 합니다.

정리하면 LPUSH는 목록의 머리 쪽에, RPUSH는 꼬리 쪽에 값을 추가하는 명령이며, 이 선택이 나중에 값을 꺼낼 때의 처리 순서를 결정합니다.

3부. 해시, 리스트, 셋026

LRANGE와 LTRIM

구간만 조회하고 목록 길이 유지하기

목록이 계속 길어지기만 하면 메모리를 잡아먹고, 필요한 구간을 보려고 전체를 꺼내는 것도 낭비입니다. 최근 것 몇 개만 남기고 오래된 것은 버리는 처리가 매번 손으로 필요하다면 곤란합니다. Redis의 List에는 이 두 가지를 맡는 LRANGE와 LTRIM이 있습니다.

택배 보관함의 한 줄을 떠올려 보면 좋습니다. LRANGE는 칸 번호를 시작과 끝으로 지정해 그 구간만 꺼내 보는 일이고, LTRIM은 지정한 구간만 남기고 나머지를 잘라내는 일입니다. 번호는 0부터 세며, -1은 마지막 칸을 뜻하므로 LRANGE 키 0 -1은 전체를 보여줍니다. LTRIM 키 0 99처럼 쓰면 앞의 백 개만 남기고 뒤는 사라지며, 이때 잘려나간 값은 되돌릴 수 없습니다.

그래서 두 명령을 함께 쓰면 최근 목록만 유지하면서 원하는 구간을 확인하는 습관을 만들 수 있습니다.

결국 LRANGE는 목록의 일부 구간을 조회하는 명령이고, LTRIM은 목록의 길이를 지정한 구간으로 잘라 유지하는 명령입니다.

List로 큐 만들기

간단한 작업 대기열 구성하기

사용자가 버튼을 누를 때마다 무거운 작업을 그 자리에서 처리하면 화면이 멈추고, 몰리는 시간에는 요청이 그대로 사라지기도 합니다. 할 일을 한쪽에 쌓아 두고 처리하는 쪽이 하나씩 가져가게 만들면 이 문제가 줄어듭니다. Redis의 List는 이런 대기열을 아주 단순한 형태로 흉내 낼 수 있는 재료입니다.

식당의 주문서 꽂이를 비유로 들어 보겠습니다. 홀 직원이 주문서를 한쪽에 꽂아 두면(RPUSH), 주방에서 반대쪽부터 한 장씩 뽑아 갑니다. 넣는 쪽과 꺼내는 쪽의 방향을 다르게 정하면 먼저 들어온 주문이 먼저 처리되는 선입선출(First In First Out) 구조가 됩니다. 꺼내는 명령은 LPOP이나 RPOP처럼 반대편에서 하나를 빼는 것이고, 대기열이 비었을 때 잠깐 기다리게 하는 블로킹(blocking) 방식도 있어 빈 목록을 계속 확인하는 낭비를 줄일 수 있습니다.

다만 처리 도중 작업이 실패하면 그 항목이 사라질 수 있으므로, 확인 응답을 남기는 별도 장치가 필요할 수 있습니다.

정리하면 생산자는 RPUSH로 목록의 한 끝에 작업을 넣고 소비자는 반대 끝에서 꺼내는 방식으로, Redis List를 간단한 큐(queue)로 사용할 수 있습니다.

Set 타입

학교 축제의 입장 도장을 생각하면 이해가 빠릅니다. 손등에 도장이 한 번 찍히면 두 번 찍어도 손등은 하나이고, 명단에 이름이 한 번 적히면 다시 적어도 줄은 늘지 않습니다.

Set은 값의 순서를 기억하지 않고, 같은 값을 다시 넣어도 하나로만 유지하며, 특정 값이 있는지 매우 빠르게 답합니다. 대신 순서가 없으므로 몇 번째 값이라는 개념이 없고, 값 자체를 중복 없이 모으는 용도에만 맞습니다.

결국 Set은 중복을 허용하지 않고 순서도 두지 않는 값의 모음이며, 이미 존재하는지 확인하고 중복을 걸러내는 작업에 적합한 자료 구조입니다.

SADD와 SMEMBERS

집합에 넣고 전체를 꺼내기

도서관 회원 명단을 떠올려 보겠습니다. SADD는 명단에 이름을 적는 일인데, 이미 적힌 이름이면 줄을 늘리지 않고 새로 적었는지 여부만 알려줍니다. 그래서 중복 검사를 따로 하지 않아도 명단 자체가 깨끗하게 유지됩니다. SMEMBERS는 명단 전체를 한 번에 펼쳐 보여 주지만, 집합은 순서를 보장하지 않으므로 나오는 차례는 매번 다를 수 있습니다.

인원이 많을 때 전체를 꺼내는 것은 부담이 되므로, 개수만 볼 때는 SCARD를, 하나씩 확인할 때는 SISMEMBER를 쓰는 편이 낫습니다.

정리하면 SADD는 집합에 값을 넣으면서 중복을 자동으로 걸러 내고, SMEMBERS는 그 집합의 모든 값을 꺼내는 명령입니다.

두 명단에 함께 들어 있는 사람이 누구인지, 한쪽에만 있는 사람이 누구인지 알고 싶을 때마다 코드로 반복문을 돌리는 일은 번거롭고 느립니다. 명단이 커질수록 이 비교 작업은 더 부담스러워집니다. Redis의 Set은 이런 관계 계산을 명령 몇 개로 끝낼 수 있게 해 줍니다.

두 반의 학생 명단을 비교하는 상황을 생각해 보겠습니다. 교집합은 양쪽 명단에 모두 있는 학생이고, 합집합은 둘을 합쳐 한 명씩만 남긴 명단이며, 차집합은 한쪽에는 있고 다른 쪽에는 없는 학생입니다. Redis에서는 이를 각각 SINTER, SUNION, SDIFF라는 명령으로 계산하고, 결과를 새 키에 담을 수도 있습니다. 계산 결과 역시 중복이 없는 집합이므로, 태그 추천이나 공통 친구 찾기 같은 관계 분석에 그대로 활용됩니다.

정리하면 교집합은 SINTER, 합집합은 SUNION, 차집합은 SDIFF로 구하며, Set은 여러 집합 사이의 관계를 빠르게 계산하는 데 강점을 가진 자료 구조입니다.

Sorted Set 타입

점수로 자동 정렬되는 집합

쇼핑몰 이벤트에서 수십만 명의 참가자 점수를 매기고 순위를 실시간으로 보여줘야 한다면, 요청이 올 때마다 전체 명단을 다시 정렬하는 방식은 감당하기 어렵습니다. Redis는 이 문제를 풀기 위해 값마다 점수를 함께 저장하고 그 점수 순서를 스스로 유지하는 Sorted Set(정렬된 집합) 타입을 제공합니다.

마라톤 대회의 기록 게시판을 떠올리면 이해가 쉽습니다. 참가자마다 완주 기록이 하나씩 붙고, 게시판은 새 기록이 들어올 때마다 그 사람을 알맞은 자리에 끼워 넣어 항상 빠른 순서를 유지합니다. 이때 참가자 이름이 멤버(member), 완주 기록이 점수(score)에 해당하며, 기록이 같으면 이름 순서로 나란히 섭니다. 같은 사람의 기록이 새로 들어오면 기존 기록만 바뀌고 자리도 그에 맞게 다시 잡힙니다.

정리하면 Sorted Set은 멤버와 점수를 한 쌍으로 저장하면서 점수 기준 정렬 상태를 계속 유지하는 자료구조이고, 덕분에 순위 조회와 구간 검색을 별도 정렬 작업 없이 처리할 수 있습니다.

ZADD와 ZRANGE

점수와 함께 넣고 순위대로 조회하기

정렬된 집합에 값을 넣을 때 점수를 빠뜨리면 그 값이 어디에 서야 할지 정할 수 없어, 저장과 정렬을 따로 처리해야 하는 번거로움이 생깁니다. ZADD는 멤버와 점수를 한 번에 넘겨 저장과 정렬을 동시에 끝내는 명령이고, ZRANGE는 그렇게 쌓인 값들을 순위 순서로 꺼내는 명령입니다.

학교 시험 성적표를 만드는 상황을 비유로 들어 보겠습니다. ZADD는 학생 이름과 점수를 성적표 한 줄에 같이 적어 제출하는 일이고, 성적표는 제출되는 즉시 점수 순으로 다시 정리됩니다. ZRANGE는 정리된 성적표에서 앞에서 몇 명, 혹은 몇 등부터 몇 등까지를 읽어 오는 일에 해당합니다.

이미 적힌 학생의 점수를 다시 ZADD로 보내면 새 줄이 생기는 대신 그 학생의 점수만 갱신되고 위치도 함께 바뀝니다. 따라서 ZADD와 ZRANGE는 각각 점수를 붙여 넣는 일과 순위대로 읽는 일을 맡는 짝이며, 두 명령만으로도 간단한 순위 기능이 완성됩니다.

게임이나 이벤트에서 참가자가 늘어날 때마다 전체 목록을 정렬해 상위 순위를 계산하면, 사용자가 몰리는 순간에 응답이 눈에 띄게 느려집니다. 실시간 랭킹보드(leaderboard)는 Sorted Set 하나로 만들 수 있는데, 참가자를 멤버로, 획득 점수를 점수로 저장하면 정렬된 상태가 자동으로 유지되기 때문입니다.

Bitmap

비트 하나로 사용자 상태를 압축 저장하기

사용자 수가 수백만 명인 서비스에서 오늘 접속했는지를 사용자마다 참과 거짓으로 저장하면, 값 하나에 수십 바이트가 들어 메모리가 빠르게 불어납니다. Bitmap(비트맵)은 이 상태를 0과 1의 비트 하나로 표현해, 사용자 한 명의 여부를 1비트로 압축해 저장하는 방식입니다.

아파트 현관의 전등 스위치 판넬을 떠올려 보겠습니다. 스위치 판넬에는 집집마다 자리가 하나씩 정해져 있고, 불이 켜졌는지 꺼졌는지는 그 자리의 상태 하나로만 표시됩니다. Bitmap도 사용자 번호를 자리 번호로 삼아 그 자리의 비트만 켜고 끄므로, 사용자 백만 명의 여부가 100만 비트라는 작은 공간에 담깁니다.

특정 사용자의 상태를 확인하거나 전체에서 켜진 자리의 수를 세는 일도 비트 연산으로 한 번에 처리됩니다. 정리하면 Bitmap은 사용자 식별자를 비트 위치로 대응시켜 참과 거짓 상태를 1비트에 담는 표현 방식이며, 대량의 여부 데이터를 적은 메모리로 다룰 때 쓰입니다.

HyperLogLog

적은 메모리로 고유 개수를 추정하기

방문자 수를 셀 때 같은 사람이 여러 번 와도 한 번만 세야 하는데, 방문자마다 이름을 모두 기억하면 사용자가 늘수록 메모리가 끝없이 커집니다. HyperLogLog는 정확한 명단 대신 확률적 추정으로 고유 개수를 세는 구조로, 아주 적은 메모리로도 수백만 단위의 근사치를 제공합니다.

큰 행사장 입구에서 사람을 세는 상황을 비유로 들어 보겠습니다. 명단을 적는 대신 입구에서 무작위로 몇 명에게만 번호표를 나눠 주고, 그 번호표의 최댓값을 보고 전체 인원을 어림잡는 방식입니다. HyperLogLog도 원소를 해시(hash)로 바꾼 뒤 그 값의 앞부분에 0이 몇 개 연속되는지를 관찰하고, 그 최댓값으로 전체 규모를 추정합니다.

그래서 메모리 사용량이 데이터양과 거의 무관하게 일정하고, 대신 결과에는 몇 퍼센트 수준의 오차가 생깁니다. 정리하면 HyperLogLog는 해시 패턴을 이용한 확률적 추정으로 고유 원소 개수를 세는 방식이며, 정확한 목록이 아니라 규모 파악이 필요할 때 적합합니다.

Geospatial 인덱스

좌표를 저장하고 거리로 검색하기

배달 앱에서 "내 주변 맛집"을 보여 주려면 저장된 수십만 개의 좌표를 하나씩 꺼내 거리를 계산해야 하는데, 이걸 매번 전부 반복하면 화면이 뜨기도 전에 사용자가 떠나게 됩니다. Geospatial 인덱스는 바로 이 문제를 풀기 위해, 좌표를 정렬된 집합(sorted set) 위에 얹어 가까운 곳만 빠르게 골라내는 Redis의 기능입니다.

대형 아파트 단지 경비실에 큰 지도가 붙어 있고 각 세대 위치마다 핀을 꽂아 둔 상황을 생각하면 됩니다. 경비실은 지도를 격자로 나눠 두었다가 "이 동 앞에서 300미터" 같은 질문이 들어오면 근처 격자 칸의 핀만 추려 실제 거리를 계산합니다.

Redis도 2차원 좌표를 geohash(좌표를 짧은 문자열로 압축하는 방식)라는 1차원 값으로 바꿔 정렬된 집합에 점수로 넣어 두고, 반경 안에 드는 격자만 골라 냅니다. 그래서 전체를 다 훑지 않고도 가까운 순서대로 결과를 돌려줄 수 있습니다.

정리하면 Geospatial 인덱스는 경도와 위도를 geohash로 1차원화해 정렬된 집합에 저장하고, 반경·사각형 범위 검색과 두 지점 사이 거리 계산을 제공하는 기능입니다. 저장 구조가 정렬된 집합이라 만료나 삭제 같은 기존 명령도 그대로 쓸 수 있습니다.

Stream 타입

로그처럼 계속 쌓이는 메시지 다루기

주문 이벤트를 목록(list)에 쌓아 두고 처리하면, 소비자가 어디까지 읽었는지 기록이 없어 재시작할 때마다 처음부터 다시 읽거나 반대로 메시지를 잃게 됩니다. Redis Stream은 로그처럼 메시지를 끝에만 덧붙이고 소비자마다 읽은 위치를 기억하는 타입으로, 이 문제를 정면으로 다룹니다.

택배 접수대에 접수 건마다 일련번호가 붙은 장부가 있고, 새 접수가 들어오면 장부 맨 아래에 한 줄이 추가된다고 생각하면 됩니다. 직원은 자기 장부에 "몇 번까지 확인했다"를 적어 두므로 다음 출근 때 그 다음 줄부터 이어 봅니다.

Redis Stream도 메시지마다 시간 기반 ID를 붙여 덧붙이기만 하는 구조로 쌓고, 소비자는 마지막으로 읽은 ID를 커서처럼 들고 다닙니다. 덕분에 여러 소비자가 같은 스트림을 각자 위치에서 읽을 수 있고, 필요하면 과거 메시지를 다시 읽을 수도 있습니다.

Stream은 메시지를 시간순 ID로 계속 덧붙이는 로그 구조로, XADD로 쓰고 XREAD로 읽으며 소비자별 커서를 관리합니다. 목록과 달리 읽어도 메시지가 사라지지 않아 재처리와 다중 소비에 적합합니다.

소비 그룹

여러 소비자가 메시지를 나눠 처리하기

같은 메시지를 여러 서버가 동시에 집어 가면 중복 처리되거나, 반대로 한 대가 죽는 순간 그 메시지가 영영 처리되지 않습니다. 소비 그룹(consumer group)은 스트림의 메시지를 여러 소비자에게 나눠 주고, 처리 확인과 재할당까지 맡는 장치입니다.

식당 주방에 주문서 걸이가 있고 여러 요리사가 주문서를 하나씩 집어 간다고 생각하면 됩니다. 한 요리사가 집어 간 주문서는 다른 요리사가 집지 않으므로 같은 주문이 두 번 만들어지지 않습니다. 요리사가 일을 마치고 완료 표시를 해야 주문서가 최종적으로 내려가고, 중간에 손을 놓으면 그 주문서는 다시 걸이로 돌아옵니다.

Redis도 그룹 이름으로 소비자를 묶어 메시지를 한 명에게만 배달하고, XACK로 처리 완료를 남기며, 응답이 끊긴 소비자의 미확인 메시지는 다른 소비자가 다시 가져가게 합니다.

소비 그룹은 하나의 스트림을 여러 소비자가 나눠 처리하도록 묶는 단위로, 대기 목록(pending entries)으로 미확인 메시지를 추적하고 재할당합니다. 서버를 늘려도 같은 일을 두 번 하지 않게 해 주는 구조입니다.

타입 선택 기준

상황에 맞는 자료구조 고르기

Redis에 데이터를 넣기 전에 타입을 잘못 고르면, 나중에 필요한 조회를 못 해 문자열을 꺼내 직접 파싱하거나 전체를 훑는 코드를 짜게 됩니다. 그래서 값의 모양과 접근 패턴을 먼저 보고 String, Hash, List, Set, Sorted Set, Stream 중에서 고르는 것이 중요합니다.

회사 창고를 정리할 때 낱개 물건은 칸 하나에, 부품 묶음은 서랍 하나에, 순서대로 꺼낼 물건은 컨베이어에 두는 것과 같습니다.

값 하나를 통째로 읽고 쓰면 String, 객체의 필드를 따로 고치면 Hash, 순서와 중복이 중요하면 List가 맞습니다. 중복 없는 집합이 필요하면 Set, 점수로 정렬된 순위가 필요하면 Sorted Set, 계속 쌓이는 이벤트 로그면 Stream을 고릅니다. 여기에 만료 시간을 걸 수 있는지, 원자적 증가가 필요한지까지 따져 보면 선택이 거의 정해집니다.

결국 타입 선택은 값을 어떤 단위로 읽고 쓰는가와 어떤 순서·중복·정렬 규칙이 필요한가를 기준으로 합니다. 잘못 고르면 편의 기능을 잃고, 맞게 고르면 서버 코드가 짧아집니다.

EXPIRE와 PERSIST

만료를 걸고 다시 해제하기

세션 토큰이나 인증 코드처럼 일정 시간이 지나면 쓸모없어지는 데이터를 손으로 지우지 않으면 저장 공간이 계속 불어납니다. EXPIRE는 키에 만료 시간을 걸고, PERSIST는 걸어 둔 만료를 다시 해제하는 명령입니다.

아파트 현관에 방문객용 임시 비밀번호를 발급하면서 "오늘 자정까지"라는 사용 기한을 함께 적어 두는 것과 같습니다. 기한이 지나면 도어락이 그 번호를 스스로 무시하고, 관리자가 필요하면 기한을 지우고 계속 쓰게 할 수도 있습니다.

Redis도 EXPIRE로 초 단위 만료 시각을, PEXPIRE로 밀리초 단위 만료 시각을 붙이고 TTL로 남은 시간을 확인합니다. PERSIST를 호출하면 그 만료 시각이 사라져 키가 다시 영구 키가 되고, 만료를 다시 걸고 싶으면 EXPIRE를 또 호출하면 됩니다.

EXPIRE 계열은 키에 삭제 예정 시각을 붙이고 PERSIST는 그 예정을 취소하는 명령으로, 만료는 키 단위로만 걸립니다. 같은 키에 값을 다시 쓸 때 만료가 유지되는지는 쓰기 명령에 따라 다르므로 확인이 필요합니다.

만료 삭제 방식

지연 삭제와 주기 삭제의 차이

만료 시간을 걸어 두어도 Redis가 모든 키의 시계를 실시간으로 감시하며 지우는 것은 아니어서, 만료된 키가 잠시 남아 있을 수 있습니다. Redis는 지연 삭제(lazy expiration)와 주기 삭제(active expiration) 두 가지 방식을 함께 씁니다.

냉장고에 유통기한을 적어 두고 음식을 꺼낼 때마다 기한을 확인해 상했으면 버리는 방식이 지연 삭제입니다. 반대로 시간이 날 때 냉장고를 한 바퀴 돌며 기한 지난 것을 미리 정리하는 방식이 주기 삭제입니다.

Redis는 키를 읽거나 쓸 때 만료 여부를 확인해 그 자리에서 지우고, 별도로 초당 여러 번 무작위로 키를 골라 만료된 것을 정리합니다. 이렇게 하면 모든 키를 상시 감시하는 비용을 피하면서도 만료된 키가 무한정 쌓이지 않게 됩니다.

정리하면 지연 삭제는 접근 시점에, 주기 삭제는 백그라운드에서 표본을 골라 만료 키를 회수하는 방식입니다. 그래서 만료된 키가 즉시 사라진다고 가정하지 말고, 메모리 사용량과 TTL 결과를 함께 보는 습관이 필요합니다.

삭제 정책(Eviction)

메모리가 찰 때 무엇을 버릴지

Redis에 데이터를 계속 밀어 넣다 보면 어느 순간 정해 둔 메모리 한도에 닿고, 그때부터는 새 값을 저장하려는 요청이 줄줄이 실패하면서 서비스가 함께 멈춰 버립니다. 삭제 정책(Eviction)은 그런 순간에 메모리를 비울 여유를 스스로 만들어, 저장 공간이 꽉 차도 서비스가 계속 돌아가게 하는 장치입니다.

아파트 단지마다 정해진 넓이의 창고가 하나씩 있는데, 입주민들이 물건을 계속 들여놓다 보면 어느새 발 디딜 틈이 없어집니다.

이때 관리인은 새 물건을 받기 위해 무엇을 내보낼지 규칙을 미리 정해 두어야 하는데, 가장 오래 손대지 않은 물건부터 버리는 규칙이 LRU(Least Recently Used, 최근 최소 사용)입니다. 반대로 꺼내 간 횟수가 적은 물건부터 정리하는 규칙이 LFU(Least Frequently Used, 최소 사용 빈도)이고, 유통기한이 지난 물건을 먼저 내보내는 규칙은 TTL(Time To Live, 만료 시간)에 해당합니다. 아무 규칙도 정하지 않고 창고가 차면 새 물건을 아예 받지 않는 선택지도 있는데, 이것이 noeviction이며 이때는 저장 요청이 그대로 거절됩니다.

정리하면 삭제 정책은 메모리가 한계에 닿았을 때 어떤 키를 희생할지 미리 정해 둔 규칙이며, LRU·LFU·TTL·무작위·noeviction 같은 방식 중에서 데이터의 성격에 맞는 것을 골라 두면 됩니다.

maxmemory 설정

메모리 상한을 정하고 지키기

Redis를 메모리 상한 없이 그냥 띄워 두면 캐시가 쌓이는 만큼 서버의 물리 메모리를 계속 잡아먹고, 결국 운영체제가 다른 프로세스까지 압박을 받거나 Redis 프로세스 자체를 강제로 종료해 버립니다. maxmemory 설정은 Redis가 쓸 수 있는 메모리의 천장을 숫자로 못 박아 두는 일입니다.

작은 식당에 냉장고 한 대뿐인데 재료를 마구 사 들이면 문이 닫히지 않듯, 메모리에도 쓸 수 있는 총량을 먼저 정해 두어야 합니다.

냉장고 벽에 '이 선을 넘으면 안 된다'고 표시를 해 두는 것이 maxmemory에 바이트(byte) 단위 값을 지정하는 일이고, 선을 넘는 순간 무엇을 버릴지는 maxmemory-policy로 함께 정합니다. 선을 넘었는데 버릴 규칙이 noeviction이라면 새 재료를 넣으려는 주문은 거절되고, 반대로 규칙이 정해져 있으면 오래된 재료를 정리해 자리를 만듭니다. 이때 상한은 Redis 본체가 쓰는 몫만이 아니라 복제본과 백그라운드 작업까지 감안해 서버 전체 메모리의 일부만 잡아 두는 것이 안전합니다.

결국 maxmemory는 Redis가 넘지 않아야 할 메모리 상한값이고, maxmemory-policy는 그 상한에 닿았을 때의 행동 규칙이며, 이 둘을 함께 정해야 메모리 부족으로 인한 장애를 막을 수 있습니다.

SCAN 명령

KEYS 대신 부담 없이 키 훑기

운영 중인 Redis에서 KEYS 명령으로 모든 키를 한 번에 훑으면, 키가 많을수록 그 작업이 끝날 때까지 서버가 다른 요청을 거의 처리하지 못해 응답이 몇 초씩 밀립니다. SCAN 명령은 이렇게 한 번에 전부 훑는 대신 조금씩 나눠 훑음으로써, 서비스가 돌아가는 중에도 키를 안전하게 조사할 수 있게 해 줍니다.

큰 창고의 재고를 셀 때 하루 종일 문을 닫고 전부 세는 대신, 구역을 나눠 조금씩 세면서 그사이에도 영업을 계속하는 방식이 있습니다.

SCAN은 이처럼 한 번에 정해진 개수만큼만 키를 돌려주고, 어디까지 봤는지 가리키는 커서(cursor)를 함께 줍니다. 다음 호출에 그 커서를 넘기면 이어서 훑고, 커서가 0으로 돌아오면 한 바퀴를 다 돈 것입니다. 다만 훑는 도중 키가 추가되거나 삭제되면 같은 키가 두 번 나오거나 빠질 수 있어, 결과를 중복 제거해 쓰는 편이 안전합니다.

정리하면 SCAN은 커서를 이용해 키 공간을 조금씩 나눠 훑는 명령으로, 서버를 멈추지 않으면서도 전체 키를 조사할 수 있게 해 줍니다.

키 이름과 길이

검색하기 쉽고 메모리를 아끼는 이름

택배 창고에서 상자마다 '1번', '2번'이라고만 적어 두면 나중에 그 안에 무엇이 들었는지 알 수 없고, 반대로 주소와 내용물을 전부 크게 적으면 라벨만으로도 상자가 무거워집니다.

그래서 보통 '서비스:도메인:식별자'처럼 콜론(:)으로 구분한 계층형 이름을 붙여, 앞부분만 보고도 어느 서비스의 어떤 데이터인지 알 수 있게 합니다. 키 이름은 글자 하나하나가 메모리를 차지하고 Redis가 키를 관리하는 자료 구조에도 이름 길이만큼의 부담이 붙기 때문에, 짧게 쓰되 의미는 잃지 않아야 합니다. 사용자 ID처럼 값이 길어질 수 있는 부분은 줄이지 않되, 반복되는 접두사는 공통 규칙으로 통일해 두면 검색과 정리가 쉬워집니다.

결국 키 이름은 나중의 나와 동료가 읽을 라벨이며, 짧으면서도 서비스·용도·식별자가 드러나는 규칙을 정해 두는 것이 검색 편의와 메모리 절약을 함께 얻는 길입니다.

TYPE과 OBJECT ENCODING

값의 타입과 내부 저장 방식을 확인하기

키에 어떤 값이 들었는지 모른 채 명령을 던지면 Redis는 타입이 맞지 않는다는 오류를 돌려주며 요청을 처리하지 않습니다. TYPE과 OBJECT ENCODING은 그런 시행착오 없이 값의 종류와 내부 저장 방식을 먼저 확인하게 해 주는 명령입니다.

우편물을 처리할 때 봉투에 '서류'인지 '소포'인지 표시가 없으면, 서류용 서랍에 소포를 밀어 넣으려다 처리기가 멈춰 버립니다.

TYPE은 키에 담긴 값이 문자열(string)·리스트(list)·해시(hash)·집합(set) 같은 어느 종류인지 알려주는 표시이고, OBJECT ENCODING은 그 값이 내부에서 어떤 방식으로 저장되고 있는지 알려줍니다. 예를 들어 리스트라도 원소가 적고 짧으면 압축된 형태로, 많고 길면 일반 형태로 저장되는데, 이 차이가 속도와 메모리 사용량을 가릅니다. 그래서 명령을 쓰기 전에 TYPE으로 종류를 확인하고, 대량 데이터를 다룰 때는 OBJECT ENCODING으로 저장 방식이 기대와 맞는지 살펴보는 습관이 필요합니다.

정리하면 TYPE은 값의 종류를, OBJECT ENCODING은 그 값의 내부 저장 방식을 알려 주는 명령이며, 둘을 함께 확인하면 타입 오류와 예상 밖의 메모리 사용을 미리 막을 수 있습니다.

DUMP와 RESTORE

키 단위로 백업하고 되살리기

특정 키 하나를 잘못 지웠거나 그 키만 다른 서버로 옮겨야 하는 상황에서, 전체 백업 파일을 통째로 다루는 방식은 너무 크고 위험합니다. DUMP와 RESTORE는 키 하나만 골라 백업하고 되살릴 수 있게 해 주는 한 쌍의 명령입니다.

이삿짐을 옮길 때 집 전체를 통째로 싣는 대신, 필요한 물건만 상자에 넣어 테이프로 봉하고 새집에서 뜯는 방법이 있습니다.

DUMP는 키 하나의 값과 그 값의 타입 정보를 직렬화(serialization, 데이터를 저장하거나 전송할 수 있는 형태로 바꾸는 일)해 하나의 덩어리로 만들어 주고, RESTORE는 그 덩어리를 받아 새 키로 되살립니다. 이때 RESTORE는 덤프를 만든 Redis와 호환되는 형식이어야 하고, 이미 같은 이름의 키가 있으면 기본적으로 거부하므로 필요하면 덮어쓰기 옵션을 주어야 합니다. 또한 만료 시간은 DUMP에 담기지 않으므로, 옮길 때는 남은 만료 시간을 따로 계산해 RESTORE에 함께 지정해야 원래 동작이 유지됩니다.

결국 DUMP와 RESTORE는 키 단위로 값을 직렬화해 백업하고 되살리는 명령이며, 타입·이름 충돌·만료 시간을 함께 챙겨야 안전하게 쓸 수 있습니다.

키 공간 이벤트

키가 바뀔 때 알림 받기

Redis에 캐시를 넣어 두고 쓰는 서비스에서 특정 키가 언제 바뀌었는지 알아내려고 매초 키 목록 전체를 훑는 코드를 두면, 키가 수십만 개만 되어도 서버가 쓸데없는 일에 힘을 빼앗깁니다. 키 공간 이벤트(keyspace notification)는 이렇게 계속 물어보는 방식을 없애기 위해, Redis가 키의 변화를 사건으로 삼아 먼저 알려 주도록 만든 기능입니다.

아파트 관리사무소를 떠올려 보면 이해가 쉽습니다. 경비원이 매시간 모든 세대를 돌며 문이 열렸는지 확인하는 대신, 각 세대 출입문에 센서를 달아 두고 문이 열리는 순간 중앙 방재실로 신호가 가게 하는 방식입니다.

Redis에서 이 센서를 켜는 일이 설정의 통지 옵션이며, 어떤 종류의 사건을 감지할지 미리 골라 두어야 합니다. 센서가 보내는 신호는 지정된 채널로 발행(publish)되고, 그 채널을 구독(subscribe)한 쪽만 알림을 받으며, 알림에는 어떤 키에 무슨 일이 있었는지가 함께 담깁니다.

비유를 걷어내면, 키 공간 이벤트는 Redis가 키의 변경을 감시해 pub/sub 채널로 내보내는 기능입니다. 덕분에 폴링 없이도 캐시 무효화나 세션 만료 후처리 같은 일을 즉시 연결할 수 있습니다.

큰 키 다루기

하나의 거대한 키가 만드는 지연 줄이기

Redis에서 수백만 개 원소를 가진 리스트나 수 기가바이트짜리 해시 하나를 만들면, 그 키를 읽고 지우는 명령 하나가 서버 전체를 몇 초씩 멈춰 세울 수 있습니다. 큰 키(big key) 다루기는 이런 거대한 키가 만드는 지연을 피하려고 데이터를 쪼개고 명령을 나눠 쓰는 방법입니다.

이삿짐을 옮기는 상황에 견주어 보면 감이 잡힙니다. 아무리 짐이 많아도 한 번에 트럭에 밀어 넣고 문을 닫으려 하면 엘리베이터 앞이 오래 막히지만, 짐을 방마다 적당한 상자로 나눠 두고 필요한 상자만 꺼내 옮기면 통로가 계속 흐릅니다.

Redis에서도 하나의 거대한 리스트 대신 여러 개의 작은 키로 나누어 저장하고, 전체를 한 번에 지우는 명령 대신 조금씩 나눠 지우는 명령을 쓰는 식입니다. 또 조회할 때도 필요한 구간만 잘라 읽도록 명령에 범위를 지정해, 한 번에 옮기는 짐의 양 자체를 줄입니다.

정리하면 큰 키 문제는 데이터 양을 줄이는 싸움이 아니라, 한 명령이 붙잡는 시간을 잘게 나누어 지연이 한 곳에 몰리지 않게 하는 문제입니다. 키를 쪼개고 범위를 지정하고 삭제를 나누는 습관이 서버의 응답 시간을 지켜 줍니다.

MULTI와 EXEC

여러 명령을 묶어 한 번에 실행하기

은행 이체처럼 A 계좌에서 돈을 빼고 B 계좌에 넣는 두 명령 사이에 다른 요청이 끼어들면, 돈이 사라지거나 두 번 들어간 것처럼 보이는 순간이 생깁니다. MULTI와 EXEC는 여러 명령을 하나의 묶음으로 예약해 두었다가 한 번에 실행함으로써, 그 사이에 다른 명령이 끼어들지 못하게 하려고 만든 기능입니다.

식당에서 손님이 여러 가지를 주문하는 상황을 떠올려 보면 비슷합니다. 종업원이 '된장찌개 주세요'라고 말한 뒤 주방이 그것을 만들기 시작하고 나서야 다음 주문을 받으면, 앞 손님과 뒤 손님의 주문이 뒤섞여 엉킵니다. 그래서 종업원은 주문을 주문서에 차곡차곡 적어 두고, 손님이 다 고른 뒤 주문서를 한 번에 주방에 넘깁니다.

Redis에서는 MULTI가 주문서를 펴는 일이고, 그 뒤에 오는 명령들은 곧바로 실행되지 않고 대기열에 쌓이며, EXEC가 주문서를 넘겨 쌓인 명령을 연달아 실행합니다. 정리하면 MULTI와 EXEC는 여러 명령을 하나의 대기열에 모아 두었다가 끼어들 틈 없이 연속 실행하는 트랜잭션 묶음입니다. 다만 묶음 전체가 성공이나 실패로 갈리는 것은 아니어서, 그 한계는 따로 이해해야 합니다.

WATCH

값이 바뀌었는지 지켜보는 낙관적 잠금

재고가 하나 남은 상품을 두 사용자가 동시에 주문하면, 둘 다 재고가 있다고 읽은 뒤 각자 하나씩 빼서 재고가 마이너스가 되는 일이 생깁니다. WATCH는 이렇게 읽은 값이 실행 직전에 다른 누군가에 의해 바뀌지 않았는지 지켜보게 해 주는 낙관적 잠금(optimistic locking) 장치입니다.

중고 장터에서 마지막 물건 하나를 두 사람이 동시에 사겠다고 나서는 상황을 떠올려 보면 이해가 쉽습니다. 한 사람이 물건을 확인하는 동안 다른 사람이 먼저 결제를 마쳐 버리면, 확인만 하고 있던 사람은 헛걸음해야 합니다. 그래서 확인을 시작할 때 '이 물건 상태를 지켜보겠다'고 표시만 해 두고, 결제 직전에 그 사이 상태가 바뀌지 않았는지 다시 확인합니다.

Redis에서는 WATCH가 바로 그 표시이고, WATCH한 키가 그 사이에 바뀌면 EXEC가 묶음을 실행하지 않고 실패를 돌려주어 클라이언트가 다시 읽고 판단하게 합니다. 정리하면 WATCH는 값을 미리 잠그는 대신, 읽은 시점과 실행 시점 사이에 값이 바뀌었는지 비교해 충돌을 감지하는 낙관적 잠금입니다. 충돌이 드문 상황에서는 잠금을 오래 붙잡지 않아 훨씬 가볍게 동작합니다.

트랜잭션의 한계

중간 실패가 롤백되지 않는 이유

Redis의 MULTI 묶음에서 두 번째 명령이 잘못되어 실패해도, 먼저 성공한 첫 번째 명령은 그대로 남아 데이터가 절반만 반영된 상태가 됩니다. 트랜잭션의 한계를 아는 것은 이 기능이 무엇을 보장하고 무엇을 보장하지 않는지 구분하기 위해 꼭 필요합니다.

실행 전에 명령 자체가 잘못된 경우에는 묶음 전체를 거부하기도 하지만, 실행 중에만 드러나는 오류까지 되돌려 주지는 않는다는 점이 핵심입니다. 정리하면 Redis 트랜잭션은 격리와 순서를 지켜 주지만 원자적 롤백은 보장하지 않습니다. 그래서 실패를 스스로 판단해 되돌리는 로직이 필요할 때는 Lua 스크립팅 같은 다른 수단을 함께 씁니다.

Lua 스크립팅

서버 안에서 원자적으로 로직 실행하기

재고를 확인하고 충분하면 줄이고 아니면 거절하는 판단을 클라이언트에서 하면, 확인과 변경 사이에 다른 요청이 끼어들어 같은 재고를 두 번 파는 일이 생깁니다. Lua 스크립팅은 이 판단 자체를 Redis 서버 안으로 옮겨, 여러 단계를 그 사이에 아무도 끼어들 수 없는 하나의 실행으로 묶는 기능입니다.

은행 창구를 떠올려 보면 이해가 쉽습니다. 손님이 창구에 서류를 내면 직원이 잔액 확인과 출금 전표 작성을 창구 안에서 연달아 끝내고, 그 사이에 다른 손님이 끼어들어 같은 잔액을 건드릴 수 없습니다. Lua 스크립트는 창구 직원이 받은 업무 지시서와 같아서, Redis가 스크립트 하나를 실행하는 동안에는 다른 클라이언트의 명령이 중간에 끼어들지 못합니다.

스크립트는 키를 읽고 조건을 따진 뒤 값을 바꾸는 판단을 모두 서버 안에서 마치고, 그 결과만 클라이언트에 돌려줍니다. 정리하면 Lua 스크립팅은 조건 판단과 데이터 변경을 서버 안의 하나의 원자적 실행으로 묶는 방법입니다. 여러 번 왕복하며 생기던 경쟁 조건을 없애 주지만, 스크립트가 길어지면 서버를 오래 붙잡으므로 짧게 유지해야 합니다.

EVAL과 EVALSHA

스크립트를 등록하고 재사용하기

쇼핑몰에서 재고를 확인하고 차감하는 로직을 매 요청마다 통째로 Redis에 보낸다면, 명령 한 줄에 수십 줄짜리 스크립트 본문이 실려 나가 네트워크가 금세 비대해지고 오타 하나로 엉뚱한 키를 건드릴 위험도 커집니다. 이 곤란을 덜려고 Redis는 스크립트를 서버에 한 번 올려 두고 이름표만 불러 실행하는 방식을 제공하는데, 그 짝이 EVAL과 EVALSHA입니다.

단골 식당에 비유하면 EVAL은 주문할 때마다 요리법 전체를 소리 내어 읽어 주는 것이고, EVALSHA는 그 요리법을 한 번 적어 두고 서른여섯 자 남짓한 등록 번호(SHA1 해시)만 말하는 것입니다. 가게 주인은 처음 받은 요리법을 장부에 꽂아 두고, 손님이 번호를 대면 장부에서 찾아 그대로 따라 합니다.

Redis에서는 SCRIPT LOAD가 장부에 꽂는 일, EVALSHA가 번호로 주문하는 일에 해당하며, 서버가 재시작되어 장부가 사라지면 알아보지 못한다는 뜻의 NOSCRIPT 오류가 돌아옵니다. 그래서 클라이언트는 이 오류를 만났을 때 스크립트 본문을 담은 EVAL로 한 번 되돌아가 다시 등록하는 길을 마련해 둡니다.

정리하면 EVAL은 스크립트 본문을 그 자리에서 실행하는 명령이고 EVALSHA는 미리 등록된 스크립트를 해시값으로 찾아 실행하는 명령이며, 둘을 함께 쓰면 반복 호출에서 전송량을 줄이면서 등록이 사라진 상황까지 안전하게 메울 수 있습니다.

Lua 작성 규칙

짧고 예측 가능한 스크립트 쓰기

Redis는 명령을 한 번에 하나씩 처리하는 구조라서, 스크립트 하나가 오래 붙잡고 있으면 뒤에 줄 선 수천 개의 요청이 함께 멈춥니다. 그래서 Lua 스크립트를 쓸 때는 짧고 결과가 예측되는 형태로 쓰는 규칙이 따로 필요합니다.

창구가 하나뿐인 은행에 비유하면, 앞 손님이 서류를 꺼내 놓고 한 시간 동안 정리하면 뒤에 선 사람들도 한 시간을 그대로 서 있어야 합니다. 그래서 창구 직원은 손님에게 필요한 서류 목록을 미리 종이에 적어 내라고 하고, 그 종이에 없는 일은 창구에서 하지 않도록 정해 둡니다.

Redis에서 스크립트가 건드릴 키를 KEYS 목록으로 미리 넘기는 것이 그 서류 목록이고, 무작위 값이나 현재 시각처럼 실행할 때마다 달라지는 요소를 넣지 않는 것이 결과가 예측되는 스크립트의 조건입니다. 반복문으로 아주 큰 범위를 훑거나 오래 걸리는 계산을 넣는 일도 창구에서 서류를 다시 만드는 일과 같아서 피해야 합니다.

결국 Lua 작성 규칙이란, 접근할 키를 명시하고 실행 결과가 언제나 같아지도록 쓰며 전체 길이를 짧게 유지해, 스크립트가 Redis의 처리 흐름을 오래 붙잡지 않게 만드는 약속입니다.

서버 측 함수

Redis 7의 Function으로 로직 상주시키기

여러 서버에서 같은 스크립트를 쓰기 시작하면, 어느 서버는 옛 판본을 보내고 어느 서버는 새 판본을 보내는 일이 생겨 같은 요청이 다른 결과를 내기도 합니다. Redis 7은 이 문제를 줄이려고 스크립트를 클라이언트가 아니라 서버에 상주시키는 서버 측 함수(Function)라는 기능을 넣었습니다.

아파트 관리사무소에 비유하면, 예전에는 경비원이 각자 수첩에 적어 둔 업무 절차를 들고 출근했지만, 이제는 사무소 벽에 공용 업무 규정집 한 권을 걸어 두고 모두가 같은 책을 펼쳐 봅니다. 규정집은 라이브러리라는 단위로 묶여 이름이 붙고, FUNCTION LOAD로 사무소에 걸린 뒤 FCALL이라는 호출로 해당 조항을 실행합니다. 책이 사무소에 있으니 경비원이 바뀌어도 절차가 흔들리지 않고, 규정집 자체가 데이터와 함께 보관되고 복제되어 서버를 다시 세워도 그대로 남습니다.

정리하면 서버 측 함수는 Lua로 쓴 로직을 라이브러리 단위로 Redis에 등록해 두고 FCALL로 불러 쓰는 기능이며, 스크립트를 데이터처럼 관리하게 해 준다는 점이 EVAL 방식과의 가장 큰 차이입니다.

원자성과 경쟁 조건

동시 요청에서 안전하게 처리하기

마지막 재고 한 개를 두 손님이 동시에 주문하면, 둘 다 남은 수량 1을 읽고 각자 하나씩 사 갈 수 있다고 판단해 결국 두 개가 팔리는 일이 벌어집니다. 이렇게 여러 요청이 서로의 중간 상태를 밟고 들어와 결과가 어긋나는 것을 경쟁 조건(race condition)이라 하고, Redis는 명령을 쪼개지지 않게 처리하는 원자성(atomicity)으로 이를 막습니다.

금고 열쇠가 하나뿐인 사무실에 비유하면, 열쇠를 든 사람이 금고를 열어 돈을 세고 다시 잠글 때까지 다른 사람은 문 앞에서 기다려야 합니다. Redis의 명령 하나는 이 열쇠를 쥔 것과 같아서 중간에 다른 요청이 끼어들지 못하지만, 읽기 다음에 쓰기처럼 명령을 두세 개 이어 붙이면 그 사이로 다른 사람이 들어옵니다. 그래서 여러 명령을 한 덩어리로 묶는 트랜잭션(MULTI)과 그 사이 값이 바뀌었는지 지켜보는 WATCH를 쓰거나, 읽기와 쓰기를 한 스크립트 안에 넣어 한 번에 처리합니다.

결국 원자성이란 한 요청의 중간 상태를 남에게 보여 주지 않는 성질이고 경쟁 조건은 그 틈을 노리는 문제이므로, Redis에서는 명령 하나로 끝내거나 트랜잭션과 스크립트로 묶어 틈 자체를 없애는 것이 해법입니다.

파이프라이닝

요청을 묶어 왕복 지연 줄이기

서로 다른 키에서 값을 천 번 읽어야 할 때 요청을 하나 보내고 응답을 받고 다시 보내기를 천 번 반복하면, 실제 계산 시간보다 오가는 길에 쓰는 시간이 훨씬 길어집니다. 파이프라이닝(pipelining)은 이 왕복을 줄이려고 보낼 요청들을 응답을 기다리지 않고 한꺼번에 밀어 넣는 방식입니다.

장을 볼 때에 비유하면, 우유를 사러 갔다가 집에 두고 다시 달걀을 사러 가고 또 다시 빵을 사러 가는 대신, 살 물건 목록을 한 장에 적어 들고 한 번에 계산하는 것과 같습니다. 클라이언트는 명령들을 연달아 서버로 보내고 응답은 나중에 차례로 받아, 네트워크를 오가는 왕복 횟수가 요청 수만큼 늘지 않고 한 번에 가까워집니다. 다만 응답은 보낸 순서대로 돌아오므로, 앞선 요청의 결과를 보고 다음 요청을 정해야 하는 경우에는 이 방식이 맞지 않습니다.

정리하면 파이프라이닝은 여러 명령을 한 번의 왕복에 실어 보내 지연을 줄이는 기법이며, 앞 명령의 결과에 기대지 않는 독립적인 요청을 대량으로 보낼 때 가장 효과가 큽니다.

재시도 패턴

충돌이 났을 때 다시 시도하는 설계

동시에 몰린 요청이 충돌해 실패했을 때 모두가 곧바로 같은 순간에 다시 시도하면, 실패한 요청들이 한꺼번에 되돌아와 서버를 다시 짓누르는 일이 생깁니다. 재시도 패턴(retry pattern)은 이 되돌림을 조절해 실패를 회복 가능한 사건으로 다루는 설계입니다.

콜센터에 전화를 걸었는데 통화 중이라는 신호를 받았을 때, 끊자마자 곧바로 다시 걸면 여전히 통화 중일 가능성이 큽니다. 그래서 잠깐 기다렸다가 다시 걸고, 그래도 안 되면 기다리는 시간을 두 배씩 늘려 가며(지수 백오프) 여러 사람이 같은 간격으로 몰리지 않도록 대기 시간에 약간의 무작위를 섞습니다(지터). 여기에 더해 몇 번까지 걸어 볼지 미리 정해 두고, 그 횟수를 넘기면 포기하고 실패를 정식으로 알립니다.

정리하면 재시도 패턴은 실패한 작업을 곧바로 반복하지 않고 대기 시간을 점점 늘리며 무작위로 흩어 재시도하다가 정해진 횟수에서 멈추는 설계이고, 재시도가 중복 실행으로 이어지지 않도록 같은 작업을 두 번 처리해도 결과가 같게(멱등하게) 만드는 일이 함께 따라야 합니다.

RDB 스냅샷

특정 시점의 데이터를 파일로 저장하기

Redis(레디스)처럼 데이터를 메모리에만 두는 저장소는 서버가 꺼지거나 장비에 문제가 생기는 순간 기억하고 있던 값이 통째로 사라집니다. 매일 수천 건씩 쌓이는 장바구니 정보를 그렇게 잃으면 서비스는 그대로 멈추게 되는데, 이 문제를 풀기 위해 고안된 것이 메모리 내용을 파일로 떠 두는 RDB 스냅샷(RDB snapshot)입니다. 아파트 관리사무소가 매달 말일에 단지 전체를 사진으로 남기는 모습을 떠올리면 이해가 쉽습니다. 관리사무소는 각 세대의 살림을 하나하나 문서로 옮겨 적는 대신, 그 시점의 단지 모습을 한 장의 큰 사진으로 찍어 두고 나중에 문제가 생기면 그 사진 한 장만 꺼내 옵니다.

Redis도 이와 같이 정해진 시점에 메모리 전체를 이진 형식의 파일 하나로 내려받고, 그 안에는 그 순간의 모든 키와 값이 함께 담깁니다. 사진을 찍는 동안에도 입주민의 생활이 계속되듯, 저장이 진행되는 사이에 들어온 변경은 다음 사진에 반영됩니다. 결국 RDB 스냅샷은 특정 시점의 데이터 전체를 하나의 파일로 보관하는 방식이며, 복구할 때 그 파일 하나만 읽으면 되므로 빠르고 간단하다는 점이 핵심입니다.

7부. 영속성과 복구062

AOF 로그

모든 쓰기를 기록해 다시 재생하기

스냅샷은 찍은 시점과 지금 사이의 시간을 채워 주지 못합니다. 10분마다 사진을 찍는 설정이라면 마지막 사진 이후 9분 동안 주문한 내역은 장비가 멈추는 순간 함께 사라지는데, 이 빈틈을 메우려고 등장한 것이 모든 쓰기를 기록해 두는 AOF(Append Only File, 덧붙이는 파일) 로그입니다. 식당 주방의 주문서를 떠올려 보면 구조가 그대로 보입니다. 주문이 들어올 때마다 주방장은 번호 순서대로 주문서에 한 줄씩 적어 두고, 불이 나서 조리대가 비었다면 그 주문서를 처음부터 다시 읽으며 같은 요리를 순서대로 다시 만듭니다.

AOF도 데이터를 바꾸는 명령이 도착하는 대로 파일 끝에 한 줄씩 덧붙이고, 복구할 때는 파일을 맨 앞에서부터 차례로 실행해 같은 상태를 재현합니다. 주문서는 지우거나 고치지 않고 뒤에 계속 이어 쓰기만 하므로, 기록 자체가 곧 작업의 역사가 됩니다. 정리하면 AOF 로그는 모든 쓰기 명령을 시간 순서대로 남겨 두었다가 다시 재생하는 방식이며, 그 덕분에 마지막 순간까지의 변경을 거의 그대로 되살릴 수 있습니다.

7부. 영속성과 복구063

AOF fsync 정책

어디까지 유실을 허용할지 정하기

AOF는 명령을 파일에 적었다고 끝이 아니라, 운영체제가 잠시 들고 있는 메모리 버퍼를 실제 디스크로 밀어내야 합니다. 이 밀어내기(fsync)를 언제 하느냐를 정하지 않으면, 전원이 끊기는 순간 버퍼에 남아 있던 마지막 명령들이 조용히 사라질 수 있습니다. 택배 접수 창구를 생각하면 선택지가 분명해집니다. 접수할 때마다 곧바로 전산에 등록하면 하나도 잃지 않지만 손님이 줄을 서게 되고, 하루에 한 번 마감하며 몰아서 등록하면 빠르지만 그 사이 사고가 나면 종이 전표만 남습니다. Redis의 fsync 정책도 같은 저울질이며, always는 명령마다 즉시 디스크에 밀어내 유실을 거의 없애는 대신 느리고, everysec는 1초마다 밀어내 최대 1초 남짓의 유실을 감수하며, no는 운영체제에 맡겨 가장 빠르지만 유실 폭이 커집니다. 결국 fsync 정책은 성능과 유실 허용 범위를 맞바꾸는 설정이며, 어디까지 잃어도 되는지를 먼저 정한 뒤 그에 맞는 값을 고르는 것이 핵심입니다.

RDB와 AOF 조합

두 방식을 함께 쓸 때의 동작

두 방식은 서로의 약점을 정확히 채워 주지만, 하나만 쓰면 각자의 빈틈이 그대로 남습니다. 스냅샷만 쓰면 마지막 저장 이후의 변경이 사라지고, 로그만 쓰면 파일이 끝없이 커지고 복구 시간이 길어지는데, 그래서 실제 운영에서는 두 방식을 함께 켜 두는 조합이 흔히 쓰입니다. 회사의 장부 정리를 떠올리면 이해가 쉽습니다. 회계 담당자는 월말마다 그달의 결산표를 한 장으로 정리해 금고에 넣고, 평소에는 거래가 생길 때마다 일지에 한 줄씩 적어 둡니다.

Redis도 평소에는 AOF에 쓰기를 계속 덧붙이고, 정해진 조건이 되면 RDB 스냅샷을 떠서 그 시점까지의 상태를 압축된 한 파일로 남깁니다. 복구할 때는 먼저 결산표에 해당하는 스냅샷을 올리고, 그 뒤에 일지에 해당하는 AOF를 이어서 재생해 마지막 순간까지 따라잡습니다. 정리하면 RDB와 AOF의 조합은 큰 틀의 상태는 스냅샷으로, 그 이후의 변화는 로그로 맡기는 이중 구조이며, 두 기록이 같은 시점을 기준으로 이어질 때 가장 안전합니다.

AOF 재작성

커진 로그 파일을 줄이기

AOF는 명령을 덧붙이기만 하므로 시간이 지날수록 파일이 계속 커집니다. 같은 값을 백 번 바꾸면 그 백 번이 모두 남아 최종 상태는 한 줄이면 될 일을 백 줄로 들고 있게 되고, 이대로 두면 디스크가 차고 복구도 느려집니다. 가계부를 정리하는 방식과 같습니다. 한 달 내내 같은 항목을 고치고 지운 기록이 쌓여도, 월말에 현재 잔액과 살아 있는 항목만 다시 적으면 훨씬 얇은 새 장부가 만들어집니다.

AOF 재작성(AOF rewrite)도 지금의 데이터 상태를 만들어 내는 최소한의 명령만으로 새 파일을 따로 쓰고, 완성이 되면 기존 파일을 그것으로 바꿔 끼웁니다. 새 파일을 만드는 동안에도 들어오는 쓰기는 계속 기록되므로 서비스가 멈추지는 않습니다. 결국 AOF 재작성은 지금의 결과와 같은 상태를 만들면서 가장 짧은 로그로 다시 써 내는 작업이며, 로그의 크기와 복구 시간을 함께 줄이는 수단입니다.

복제 구조

마스터와 레플리카의 관계

서버 한 대에만 데이터를 두면 그 서버가 꺼지는 순간 서비스가 통째로 멈추고, 읽기 요청이 몰릴 때도 혼자 감당해야 합니다. 이 문제를 풀기 위해 한 서버의 데이터를 다른 서버로 계속 복사해 두는 구조를 복제(replication)라고 하며, 원본을 가진 쪽을 마스터(master), 사본을 가진 쪽을 레플리카(replica)라고 부릅니다.

본사와 지사가 같은 장부를 유지하는 모습을 떠올려 보면 이해가 쉽습니다. 새 거래는 반드시 본사에서 먼저 장부에 적고, 지사는 본사가 보내 주는 기록을 받아 자기 장부에 옮겨 적습니다.

그래서 조회는 지사에서 처리해 일을 나눌 수 있지만, 지사 장부는 본사보다 항상 조금 늦게 따라오며, 본사가 불이 나면 가장 최근에 옮겨 적지 못한 몇 줄은 지사에 없을 수 있습니다. 이런 이유로 쓰기는 마스터로 보내고 읽기는 레플리카로 나누는 구성이 흔히 쓰입니다.

정리하면 복제 구조는 마스터가 쓰기를 받아 레플리카로 흘려보내고 레플리카가 그 기록을 따라 적용하는 관계이며, 이 관계 덕분에 읽기 분산과 장애 시 대체가 가능해지지만 복제 지연이라는 대가가 따릅니다.

REPLICAOF 설정

복제 연결을 맺고 끊기

새 레플리카를 붙이거나 마스터 서버를 다른 장비로 옮길 때, 관계를 잘못 맺으면 엉뚱한 서버의 데이터를 따라가며 기존 데이터가 지워질 수 있습니다. Redis는 이 관계를 명령 한 줄로 맺고 끊을 수 있게 하는데, 그것이 REPLICAOF 설정입니다.

신문 구독 지점을 바꾸는 일과 비슷합니다. 지금까지 A 지점에서 신문을 받았는데 B 지점으로 바꾸려면 B 지점에서 받겠다는 신청을 넣어야 하고, 신청이 처리되는 순간부터는 B 지점 기준으로 배달이 시작됩니다. 이때 새 지점은 과거 신문을 모두 다시 보내 주므로 그 전에 받아 두었던 신문은 밀려나고, 구독을 아예 그만두려면 정지 신청을 따로 넣어야 합니다.

Redis에서도 REPLICAOF 호스트 포트로 대상을 지정하면 그 서버를 마스터로 삼아 데이터를 새로 받아 오고, REPLICAOF NO ONE을 실행하면 복제를 끊고 스스로 마스터가 됩니다. 다만 이 명령은 실행 중인 설정만 바꾸므로 재시작 후에도 유지하려면 설정 파일에도 함께 적어 두어야 합니다.

정리하면 REPLICAOF는 레플리카가 어느 마스터를 따라갈지 실행 중에 지정하고 해제하는 명령이며, 대상을 바꾸면 기존 데이터가 교체된다는 점과 재시작 후 유지 여부를 함께 기억해야 합니다.

비동기 복제

복제 지연이 생기는 이유

마스터 서버가 주문을 백 건 처리하는 동안 레플리카가 아흔 건만 따라왔다면, 마스터가 그 순간 멈출 때 남은 열 건은 어디에도 남지 않습니다. 그래서 Redis는 마스터가 명령을 처리해 응답한 뒤에 그 결과를 레플리카로 흘려보내는 비동기 복제(Asynchronous Replication)를 기본으로 씁니다.

회사의 결재 서류로 생각해 보면 이해가 쉽습니다. 팀장이 도장을 찍어 비서에게 사본을 넘기면, 비서가 정리하는 동안에도 팀장은 다음 서류를 계속 결재합니다.

팀장 책상에 쌓이는 속도가 비서의 정리 속도보다 빠르면 사본 서류함은 계속 뒤처지는데, 이 벌어진 간격이 곧 복제 지연(Replication Lag)입니다. 네트워크가 느리거나 레플리카가 다른 일로 바쁘거나 큰 명령 하나가 오래 걸리면 간격은 더 벌어지고, 아직 사본함에 들어가지 않은 서류는 팀장이 쓰러지는 순간 그대로 사라집니다.

정리하면 비동기 복제는 마스터가 응답을 마친 뒤 변경을 레플리카로 보내는 방식이라, 구조적으로 지연이 생길 수밖에 없습니다. 이 지연이 얼마인지 확인하고 감수할 수 있는 범위 안에서 관리하는 것이 운영의 핵심입니다.

복제 지연 확인

레플리카가 얼마나 뒤처졌는지 보기

레플리카가 마스터보다 몇 초나 뒤처졌는지 모른 채 서비스를 돌리면, 방금 저장한 값이 조회되지 않는다는 문의를 받고도 원인을 짚지 못합니다. Redis는 마스터와 레플리카가 각각 어디까지 처리했는지를 숫자로 남겨 두어, 이 간격을 직접 들여다보게 합니다.

택배 물류센터에 비유하면 이렇습니다. 마스터 창고는 상자가 입고될 때마다 일련번호를 하나씩 올리고, 레플리카 창고는 자기가 마지막으로 받은 번호를 적어 둡니다.

두 번호를 나란히 놓으면 레플리카가 몇 상자나 뒤처졌는지 바로 보이는데, 이 값을 복제 오프셋(replication offset)이라고 합니다. Redis에서는 INFO replication 명령으로 마스터의 master_repl_offset과 레플리카의 slave_repl_offset을 비교하거나, 레플리카가 보고하는 초 단위 지연 값을 확인합니다. 여기에 두 서버가 핑을 주고받는 데 걸린 시간까지 얹으면 사용자가 체감하는 지연에 가까워집니다.

결국 복제 지연은 마스터와 레플리카의 처리 지점을 가리키는 오프셋 차이로 측정하고, 이 값이 벌어지는 순간을 모니터링으로 감시하는 것이 정석입니다.

Sentinel 소개

장애를 감지해 자동으로 넘기는 구조

새벽에 마스터가 멈추면 레플리카는 멀쩡히 살아 있는데도 서비스 전체가 쓰기를 받지 못합니다. 사람이 일어나 손으로 레플리카를 마스터로 바꿔 주기 전까지 장애가 길어지는데, Redis Sentinel은 이 감지와 전환을 자동으로 맡는 감시자입니다.

아파트 경비 초소에 비유할 수 있습니다. Sentinel은 마스터에게 주기적으로 핑을 보내 대답이 오는지 확인하는 경비원이고, 한 명이 못 본 것만으로는 판단하지 않고 여러 초소가 같은 결론에 동의할 때만 장애로 인정합니다.

장애가 확정되면 살아 있는 레플리카 가운데 가장 앞선 것을 새 마스터로 세우고, 나머지 레플리카와 클라이언트에게 새 주소를 알립니다. 경비원 한 명이 쓰러져도 순찰이 끊기지 않도록 Sentinel 자체도 여러 대를 나란히 둡니다.

정리하면 Sentinel은 마스터를 감시하고, 다수결로 장애를 확정하고, 레플리카를 새 마스터로 승격시키는 일을 맡는 별도 프로세스입니다.

Sentinel 구성

쿼럼과 투표로 판단하게 만들기

Sentinel을 한 대만 띄우면 그 한 대가 네트워크 문제로 잠깐 흔들리는 사이 멀쩡한 마스터를 죽었다고 착각해 서비스가 갈아엎힐 수 있습니다. 그래서 Sentinel은 여러 대를 묶고, 정족수(quorum)와 다수 투표라는 두 겹의 합의 절차로 판단하도록 구성합니다.

아파트 관리 규약에 비유해 보겠습니다. 관리사무소가 정전인지 확인할 때 직원 한 명의 말만 듣지 않고, 규약에 적힌 인원 이상이 정전이 맞다고 보고해야 1차 판정을 내립니다.

이 문턱이 쿼럼이고, 그 뒤 실제 조치를 시작할 때는 살아 있는 감시자 과반수의 찬성을 한 번 더 받습니다. 두 절차를 나눠 둔 이유는 일부 감시자만 마스터와 단절된 상황에서 성급히 넘기는 사고를 막기 위해서입니다. 그래서 Sentinel은 보통 세 대 이상 홀수로 두고, 쿼럼은 과반수보다 작게 잡아 한 대가 빠져도 판정이 멈추지 않게 합니다.

결국 Sentinel 구성은 감시자를 홀수로 늘리고, 쿼럼으로 장애 판정의 문턱을, 과반수 투표로 실제 승격의 동의를 나눠 갖게 하는 설계입니다.

장애 조치

레플리카를 마스터로 승격하기

마스터가 죽었을 때 레플리카 중 누구를 새 마스터로 세울지 아무렇게나 정하면, 가장 뒤처진 레플리카가 뽑혀 방금 저장된 데이터가 통째로 사라질 수 있습니다. Sentinel의 장애 조치(failover)는 이 후보 선택과 승격을 정해진 순서로 자동 수행합니다.

회사의 지점장 대행을 떠올리면 비유가 됩니다. 지점장이 쓰러지면 본사는 대행을 세우기 전에 직원마다 마지막으로 처리한 업무량을 확인하고, 가장 최신 상태인 직원을 대행으로 지명합니다.

이어서 나머지 직원에게 이제부터 이 사람에게 보고하라고 공지하고, 돌아온 옛 지점장은 새 대행 아래의 조력자로 내려앉힙니다. 대행이 되기 전에 자기 기록을 마저 채우도록 잠깐 기다리는 절차가 있어, 조금이라도 더 앞선 상태를 맞춘 뒤 승격합니다. 승격이 끝나면 새 마스터의 복제 관계가 다시 맺어지고, 옛 마스터는 복구되면 레플리카로 재합류합니다.

정리하면 장애 조치는 살아 있는 레플리카 중 가장 앞선 후보를 골라 새 마스터로 승격하고, 나머지를 그 아래로 다시 묶는 일련의 절차입니다.

클라이언트 페일오버

바뀐 마스터 주소를 찾아 접속하기

장애 조치가 성공해 새 마스터가 섰는데도 클라이언트가 예전 주소만 바라보고 있으면, 서비스는 여전히 멈춘 것과 다르지 않습니다. 그래서 클라이언트는 Sentinel에게 현재 마스터 주소를 물어보고, 값이 바뀌면 새 주소로 스스로 갈아타는 페일오버(failover) 처리를 갖춰야 합니다.

단체 여행의 집결지에 비유할 수 있습니다. 가이드가 집결지를 옮기면 여행객은 예전 장소로 우직하게 가지 않고 안내 데스크에 지금 집결지가 어디냐고 물어 다시 찾아갑니다.

클라이언트 라이브러리는 Sentinel에 get-master-addr-by-name을 보내 현재 마스터 주소를 받고, 그 주소로 연결을 맺습니다. Sentinel은 마스터가 바뀌면 pub/sub 채널로 새 주소를 알리므로, 클라이언트는 그 알림을 듣고 곧바로 재접속합니다. 연결이 끊겼을 때 다시 물어보는 재시도 절차가 없으면, 알림을 놓친 클라이언트는 영원히 옛 주소에 머뭅니다.

결국 클라이언트 페일오버는 주소를 코드에 박아 두지 않고 Sentinel에 조회하고 알림을 구독해, 마스터가 바뀔 때마다 새 주소로 스스로 옮겨 가는 구조입니다.

수동 복구

자동 조치가 실패했을 때 손으로 살리기

자동 장애 조치(failover)가 붙어 있는 시스템이라도, 승격이 끝나지 않았거나 두 노드가 서로 주인이 되겠다고 우기는 상황은 실제로 일어납니다. 그때 아무도 손을 대지 않으면 서비스는 스스로 판단하지 못한 채 멈춰 있고, 사람이 개입해야 하는 순간이 오는데 이 절차를 수동 복구(manual recovery)라고 부릅니다. 자동 조치는 정해진 신호가 정상적으로 들어올 때만 작동하고, 네트워크가 반쯤 끊기거나 노드 자체가 응답을 멈추면 그 판단 근거가 사라지기 때문입니다.

아파트 소방 설비에 비유하면 이해가 쉽습니다. 평소에는 화재 감지기가 자동으로 스프링클러를 틀지만, 배관이 얼거나 감지기가 오작동하면 관리인이 직접 밸브를 잠그고 어느 동이 문제인지 확인해야 합니다. 이때 관리인은 먼저 전체 밸브를 잠가 물을 멈추고, 살아 있는 동과 죽은 동을 구분한 뒤에야 하나씩 물길을 다시 엽니다.

복구도 같은 순서라서, 먼저 쓰기가 멈춘 상태를 확인하고 어떤 노드가 마지막까지 살아 있었는지 증거를 모은 다음, 그 노드를 중심으로 다시 묶습니다. 순서를 건너뛰고 급하게 승격부터 하면 뒤늦게 돌아온 옛 주인이 자기 데이터를 최신이라고 우기며 덮어쓸 수 있습니다.

정리하면 수동 복구는 자동 승격이 멈춘 뒤 관리자가 상태를 확인하고 한 노드만 주인으로 인정해 클러스터를 다시 세우는 절차이며, 가장 중요한 원칙은 증거를 확보하기 전에는 아무 노드도 쓰기를 받지 않게 하는 것입니다.

고가용성 점검

단일 장애 지점 없애기

서버 한 대가 죽었을 뿐인데 서비스 전체가 멈추는 일은 생각보다 자주 벌어집니다. 그 한 대가 이름을 알려주는 서버였거나, 접속을 나눠 주던 장비였거나, 백업이 걸려 있지 않은 유일한 저장소였기 때문인데, 이렇게 하나가 무너지면 전체가 무너지는 지점을 단일 장애 지점(single point of failure)이라고 합니다. 고가용성 점검은 이런 지점이 남아 있는지 목록을 만들어 하나씩 없애는 작업입니다.

건물의 비상 계단에 비유해 보겠습니다. 정문 하나로만 드나드는 건물은 그 문이 잠기면 모든 입주민이 갇히므로, 비상구를 따로 만들고 불이 났을 때 안내등이 켜지는지, 계단에 짐이 쌓여 있지 않은지 주기적으로 확인합니다.

점검도 똑같이 세 가지를 봅니다. 첫째는 대체 경로가 실제로 있는지, 둘째는 그 경로로 넘어가는 판단과 전환이 자동으로 되는지, 셋째는 넘어간 뒤에도 성능이 버틸 만한지입니다. 여기서 자주 놓치는 것이 전환 자체를 담당하는 감시자나 이름 해석 서버가 다시 단일 장애 지점이 되는 경우입니다.

결국 고가용성 점검은 복제본이 있는지만 세는 일이 아니라, 노드·감시자·네트워크·이름 해석을 포함한 모든 경로에서 한 곳이 죽어도 서비스가 이어지는지 확인하고 그 구멍을 메우는 일입니다.

9부. Redis Cluster081

Cluster 소개

데이터를 여러 노드에 나눠 담는 방식

데이터가 한 대의 서버 메모리에 다 들어가지 않게 되면, 더 큰 장비를 사는 방법밖에 없다고 생각하기 쉽습니다. 하지만 장비 한 대가 감당할 수 있는 크기에는 한계가 있고, 그 한 대가 죽는 순간 전체가 사라지는 위험도 함께 커집니다. Redis Cluster는 이 두 가지 문제를 한 번에 풀기 위해 데이터를 여러 노드에 나눠 담고, 각 노드가 서로의 빈자리를 채우도록 만든 방식입니다.

물류 창고를 여러 동으로 나눈 회사에 비유할 수 있습니다. 택배를 한 창고에 다 쌓으면 그 창고가 불타는 순간 전부 잃지만, 물건마다 어느 동에 가야 하는지 규칙을 정해 두면 각 동은 자기 몫만 관리하면 됩니다. 직원은 송장을 보고 해당 동으로 가고, 그 동이 공사 중이면 옆 동이 잠시 물량을 받아 넘겨줍니다.

Redis Cluster도 키마다 담당 노드를 정하는 규칙을 공유하고, 노드끼리 서로의 생존을 확인하며, 일부 노드가 빠져도 나머지가 자기 몫은 계속 처리합니다.

정리하면 Cluster는 데이터를 샤딩(sharding)으로 나눠 여러 노드에 분산하고, 노드 간 복제와 투표를 통해 일부가 죽어도 전체가 멈추지 않게 만든 구조입니다.

9부. Redis Cluster082

해시 슬롯

16384개 슬롯에 키를 배분하기

키가 수백만 개가 되면 어떤 키가 어느 노드에 있는지 목록으로 관리하는 방식은 금세 감당이 안 됩니다. 노드가 하나 늘거나 줄 때마다 목록 전체를 다시 써야 하고, 그 사이에는 어느 노드로 가야 할지 알 수 없는 키가 생깁니다. 해시 슬롯(hash slot)은 이 문제를 피하기 위해 키를 직접 노드에 연결하지 않고, 미리 정해 둔 16384개의 칸에 먼저 배정하는 방식입니다.

아파트 우편함에 비유하면 정확합니다. 택배기사가 각 세대를 외우는 대신 동 번호와 호수로 우편함 번호를 계산하듯, Redis는 키 이름을 해시 함수로 계산해 0부터 16383 사이의 번호 하나를 얻습니다. 이 번호가 곧 슬롯이고, 각 노드는 자기가 맡은 슬롯 구간만 책임집니다.

그래서 노드가 늘거나 줄 때는 슬롯 몇 개의 주인만 옮기면 되고, 키 전체를 다시 계산할 필요가 없습니다. 같은 키는 언제나 같은 슬롯으로 가므로 담당 노드가 바뀌지 않는 한 조회도 한 번에 끝납니다.

결국 해시 슬롯은 키를 16384개의 고정된 칸으로 접어 넣어, 노드 수가 변해도 옮길 단위를 작게 유지하는 장치이며, 이 칸의 배분표가 곧 클러스터의 지도가 됩니다.

9부. Redis Cluster083

클러스터 구성

노드를 묶고 슬롯을 할당하기

노드 여러 대를 그냥 켜 두기만 하면 서로가 남인 채로 각자 다른 데이터를 들고 있게 됩니다. 어느 노드에 어떤 키가 있는지 아무도 모르고, 하나가 죽어도 나머지는 관심을 두지 않으므로 분산도 복제도 되지 않습니다. 클러스터 구성은 이 남남인 노드들을 하나의 판으로 묶고, 16384개 슬롯을 나눠 주고, 서로 감시할 짝을 정해 주는 작업입니다.

신도시에 우편 구역을 정하는 일에 비유할 수 있습니다. 먼저 어느 동이 어느 구역을 맡을지 정하고, 각 구역에 대체 담당자를 붙이고, 구역 경계가 바뀌면 주민에게 새 주소를 알립니다.

클러스터도 같은 순서를 따릅니다. 노드들을 만나게 해 서로를 알게 하고, 슬롯 범위를 나눠 주고, 각 주 노드에 복제 노드를 붙인 뒤, 마지막으로 모든 노드가 같은 지도를 갖도록 맞춥니다. 이때 노드가 홀수로 유지되어야 투표가 갈리지 않고, 각 주 노드의 복제본이 다른 물리 서버에 있어야 한 대가 통째로 꺼져도 버팁니다.

정리하면 클러스터 구성은 노드 발견, 슬롯 할당, 복제 짝짓기, 지도 동기화라는 네 단계로 이루어지며, 이 네 가지가 모두 맞아야 비로소 하나의 클러스터로 동작합니다.

9부. Redis Cluster084

MOVED와 ASK

다른 노드로 안내하는 응답 이해하기

클라이언트가 아무 노드에나 요청을 보내면, 그 노드가 모든 키를 다 갖고 있지 않으므로 엉뚱한 곳에 물어보는 일이 생깁니다. 이때 서버가 그냥 오류를 돌려주면 클라이언트는 어디로 가야 할지 영영 알 수 없습니다. Redis는 이 상황을 오류가 아니라 안내로 처리하는데, 그 안내가 MOVED와 ASK라는 두 가지 응답입니다.

호텔 안내 데스크에 비유하면 구분이 쉬워집니다. 손님이 3층 객실을 물었는데 데스크가 이 호텔이 아니라 옆 건물에 있다고 하면, 그것은 "앞으로 계속 옆 건물로 가세요"라는 영구 안내입니다. 반면 방금 이사를 마쳐 짐만 잠시 이쪽에 있는 상황이라면, "이번 한 번만 이쪽에서 찾고 다음부터는 옆 건물로 가세요"라고 알려 줍니다.

앞의 경우가 MOVED로, 담당 노드가 바뀌었으니 지도를 갱신하고 그 노드로 계속 보내라는 뜻입니다. 뒤의 경우가 ASK로, 슬롯 이사가 진행 중이라 이번 요청만 임시 노드로 보내고 지도는 아직 바꾸지 말라는 뜻입니다. 그래서 MOVED를 받으면 클라이언트는 지도를 고치고, ASK를 받으면 고치지 않은 채 한 번만 우회합니다.

결국 두 응답은 같은 "다른 곳으로 가라"는 말을 영구 이동과 일시 이동으로 나눈 것이며, 이 구분 덕분에 슬롯을 옮기는 도중에도 요청이 유실되지 않습니다.

9부. Redis Cluster085

클러스터 클라이언트

노드 변화를 따라가는 클라이언트

클러스터에 붙은 프로그램이 처음 받은 서버 주소만 기억한 채 계속 그곳으로 요청을 보낸다고 해 보겠습니다. 서버 한 대가 고장 나거나 새 서버가 합류해 담당 구역이 바뀌면, 프로그램은 이미 사라진 주소를 붙잡고 시간 초과만 되풀이하게 됩니다. 그래서 클러스터 구조를 스스로 파악하고 노드 변화를 따라가는 클러스터 클라이언트(cluster client)가 필요합니다.

아파트 단지에 물건을 배달하는 기사로 비유해 보겠습니다. 기사는 어느 동을 누가 맡는지 적힌 지도, 곧 슬롯(slot)과 노드(node)의 대응표를 들고 출발합니다. 배달 도중 관리사무소가 담당 구역을 바꾸면 기사는 낡은 지도로 헤매지 않고 새 지도를 받아 다시 길을 잡습니다.

주소가 맞지 않아 안내데스크에서 되돌아온 신호를 받으면, 그 신호를 힌트 삼아 지도를 갱신하고 같은 요청을 올바른 동으로 다시 보냅니다.

결국 클러스터 클라이언트는 슬롯이 어느 노드에 있는지 담은 표를 들고 있다가, 이동(moved) 안내나 토폴로지(topology) 변화를 받으면 그 표를 갱신해 요청을 계속 올바른 노드로 보내는 구성 요소입니다.

9부. Redis Cluster086

리샤딩

슬롯을 옮겨 부하를 분산하기

데이터가 한 노드에만 몰리면 그 노드만 느려지고 저장 공간이 먼저 차는데, 서버를 새로 한 대 붙여도 기존 데이터가 저절로 옮겨가지는 않습니다. 그래서 살아 있는 상태에서 슬롯(slot)의 주인을 다른 노드로 옮기는 리샤딩(resharding)이 필요합니다.

회사가 사무실을 넓히며 서류 캐비닛을 새 사무실로 옮기는 상황과 비슷합니다. 서류 전체를 한꺼번에 싣지 않고 서랍 하나씩 옮기며, 옮기는 동안에도 그 서랍을 찾는 사람은 원래 자리에서 안내를 받습니다. 새 자리에 서류가 도착해 확인이 끝나면 원래 서랍을 비우고, 그 서랍의 주소를 새 사무실로 바꿔 적습니다.

이렇게 하면 업무를 멈추지 않고도 짐이 고르게 분산됩니다.

실제로는 슬롯 단위로 소유권을 넘기며, 옮기는 중인 슬롯은 마이그레이팅(migrating)과 임포팅(importing) 상태로 표시되고 그 사이의 요청은 안내(ask) 응답을 따라 새 노드로 갑니다.

9부. Redis Cluster087

클러스터 장애 조치

노드가 죽으면 어떻게 대체되는가

마스터(master) 노드가 갑자기 꺼지면 그 노드가 맡던 슬롯의 데이터는 읽지도 쓰지도 못하게 되고, 사람이 알아채고 손으로 고치기까지 서비스가 멈춰 있게 됩니다. 그래서 노드가 죽으면 같은 데이터를 복제하던 노드가 자동으로 자리를 이어받는 클러스터 장애 조치(failover)가 필요합니다.

아파트 관리사무소에 담당 관리인과 부관리인이 함께 있다고 생각해 보겠습니다. 부관리인은 평소 담당 관리인의 장부를 그대로 받아 적어 두는 복제본(replica) 역할을 합니다. 담당 관리인이 일정 시간 응답하지 않으면 다른 관리인들이 모여 투표하고, 과반이 동의하면 부관리인이 열쇠와 장부를 넘겨받아 새 담당이 됩니다.

그 뒤로는 입주민에게 새 담당자의 위치가 안내되어, 예전 방문지로 간 사람도 안내를 받아 다시 찾아갑니다.

정리하면 장애 조치는 복제본이 데이터를 계속 따라 받다가, 마스터의 침묵을 감지한 노드들의 투표로 복제본을 마스터로 승격시키고 클라이언트를 새 노드로 안내하는 절차입니다.

9부. Redis Cluster088

다중 키 제약

같은 슬롯에 있어야 하는 이유

여러 키를 한 번에 읽거나 쓰는 명령을 보냈는데 키들이 서로 다른 노드에 흩어져 있으면, 그 명령은 처리되지 않고 교차 슬롯(cross slot) 오류로 되돌아옵니다. 그래서 한 번에 다루는 키들은 반드시 같은 슬롯(slot)에 있어야 한다는 다중 키 제약이 생깁니다.

택배 한 주문서에 담긴 물건들을 떠올려 보겠습니다. 같은 주문의 물건은 한 집하장에 모여 있어야 트럭 한 대에 실려 함께 배송되고, 서로 다른 집하장에 나뉘어 있으면 한 번에 보낼 방법이 없습니다. 어느 집하장으로 갈지는 키 이름을 해시(hash)로 계산한 슬롯 번호가 정합니다.

그래서 키 이름이 조금만 달라도 슬롯 번호가 달라져 다른 집하장으로 배정될 수 있습니다.

결국 다중 키 명령과 트랜잭션, 스크립트는 키들을 같은 슬롯에 두어야 원자적으로 처리할 수 있고, 클라이언트가 요청을 쪼개 여러 노드로 보내더라도 그 사이에 다른 요청이 끼어들 수 있어 하나의 작업으로 보장되지는 않습니다.

9부. Redis Cluster089

해시 태그

관련 키를 같은 슬롯에 모으기

관련 있는 키를 같은 슬롯에 모으려고 키 이름을 억지로 비슷하게 바꾸면 이름이 지저분해지고, 조금만 어긋나도 다시 다른 슬롯으로 흩어져 다중 키 명령이 실패합니다. 이때 키 이름 안의 특정 부분만 해시에 쓰도록 지정하는 해시 태그(hash tag)를 활용합니다.

이삿짐에 같은 호수 스티커를 붙이는 방식과 같습니다. 짐마다 이름은 달라도 큰 글씨로 적힌 호수가 같으면 작업자들은 그 호수만 보고 같은 트럭에 싣습니다. 중괄호 안에 든 문자열만 해시 대상으로 삼고 바깥의 나머지는 무시하기 때문에, 사용자 정보와 장바구니 키가 이름은 달라도 같은 슬롯으로 갑니다.

다만 태그를 너무 짧거나 뭉뚱그려 정하면 많은 키가 한 슬롯에 몰려 부하가 다시 치우칠 수 있습니다.

정리하면 해시 태그는 키 이름의 중괄호 부분만 슬롯 계산에 쓰게 해, 서로 다른 키를 같은 슬롯에 묶어 다중 키 작업을 가능하게 하는 표기법입니다.

클러스터 운영

재시작·확장·상태 점검하기

노드를 재시작하거나 새 노드를 늘릴 때 아무 준비 없이 껐다 켜면 그 노드의 슬롯이 사라진 것처럼 보이고, 확장한 뒤에도 데이터가 한쪽에 치우친 채로 남을 수 있습니다. 그래서 상태를 확인하고 정해진 순서로 손대는 클러스터 운영 절차가 필요합니다.

여러 지점을 가진 매장을 새로 여는 상황과 비슷합니다. 간판만 달아서는 영업이 되지 않고, 담당 구역을 다시 나누고 재고를 옮기고 순회 점검표를 채워야 합니다.

먼저 클러스터 정보와 노드 목록을 조회해 각 노드가 정상으로 보이는지 확인하고, 새 노드는 기존 노드에 소개시켜 합류시킨 뒤 슬롯을 나눠 줍니다. 재시작할 때는 노드가 자기 클러스터 상태를 기억하도록 설정이 남아 있는지 확인하고, 장애 조치가 너무 성급하거나 늦지 않도록 감지 시간을 조정합니다.

결국 클러스터 운영은 슬롯 배치와 노드 상태를 주기적으로 점검하고, 확장과 재시작을 계획된 순서로 수행해 데이터 균형과 가용성을 함께 유지하는 일입니다.

캐시 전략 개요

언제 캐시를 쓰고 언제 쓰지 않는가

같은 질문이 하루에 수만 번 반복되는데도 매번 원본 저장소까지 다녀와야 한다면, 그 길은 금세 막히고 사용자는 화면이 뜨지 않는 경험을 하게 됩니다. 이때 한 번 꺼내 온 답을 가까운 곳에 잠시 두었다가 다시 쓰는 방식이 캐시(cache)이며, 캐시 전략은 그 답을 언제 두고 언제 버릴지 정하는 규칙입니다.

도서관 사서가 자주 찾는 책 몇 권을 서고까지 가지 않고 데스크 옆 작은 서가에 꽂아 두는 모습을 떠올려 보면 이해가 쉽습니다. 손님이 책을 요청하면 사서는 먼저 옆 서가를 살피고, 거기에 없을 때만 서고까지 걸어가 책을 가져옵니다.

그렇게 다녀온 길에 그 책을 옆 서가에 한 권 더 꽂아 두면, 다음 손님은 같은 거리를 다시 걷지 않아도 됩니다. 다만 아무 책이나 옆 서가에 쌓아 두면 자리만 차지하고 정작 인기 있는 책을 놓을 곳이 사라지므로, 어떤 책을 둘지와 언제 치울지를 함께 정해야 합니다.

정리하면 캐시는 원본보다 빠르고 가까운 저장소에 결과를 복사해 두는 계층이고, 캐시 전략은 적중과 실패를 어떻게 다루고 데이터 변화를 어떻게 반영할지를 정하는 설계입니다. 읽기가 많고 같은 결과가 반복되며 조금 낡아도 괜찮은 데이터라면 캐시가 큰 이득이 되지만, 매번 달라지거나 정확성이 생명인 데이터라면 캐시를 쓰지 않거나 아주 짧게만 두는 편이 낫습니다.

Cache-Aside

읽을 때 비어 있으면 채우는 기본 패턴

캐시를 붙여 놓고도 정작 필요한 순간에 비어 있으면, 사용자는 캐시가 없을 때와 똑같이 느린 화면을 보게 됩니다. 그 빈자리를 누가 언제 채울지 정하는 가장 흔한 답이 Cache-Aside, 우리말로 곁에 두고 필요할 때 채우는 방식입니다.

요리사가 냉장고를 쓰는 모습과 같습니다. 요리사는 재료가 필요하면 먼저 냉장고 문을 열어 보고, 있으면 바로 꺼내 쓰고 없으면 마트에 다녀옵니다.

마트에서 돌아온 요리사는 이번 요리에 쓸 만큼만 쓰고 남은 것을 냉장고에 넣어 두며, 다음에 같은 재료가 필요하면 마트에 가지 않습니다. 여기서 중요한 점은 냉장고가 스스로 재료를 채우지 않는다는 것이고, 채우는 일은 항상 요리사, 즉 데이터를 요청한 응용 프로그램의 몫입니다.

Cache-Aside는 응용 프로그램이 캐시를 먼저 조회하고 없을 때만 원본 저장소에서 읽어 캐시에 넣는 방식이며, 캐시에 장애가 나도 원본으로 우회할 수 있어 가장 널리 쓰입니다. 다만 채우는 책임이 응용 프로그램에 있으므로, 원본이 바뀌었을 때 캐시를 지우는 코드를 함께 두지 않으면 낡은 값이 오래 남습니다.

Write-Through와 Write-Behind

쓰는 시점에 따른 세 가지 방식

데이터를 고쳤는데 캐시에는 옛 값이 남아 있으면, 사용자는 방금 바꾼 내용이 사라진 화면을 보게 됩니다. 그래서 캐시를 쓰는 시스템은 읽기뿐 아니라 쓰기 순서까지 정해야 하고, 그 순서에 따라 Write-Through와 Write-Behind, 그리고 캐시를 건너뛰는 Write-Around로 나뉩니다.

택배 접수 창구를 떠올려 보면 세 방식의 차이가 분명해집니다.

접수 장부를 캐시, 창고 대장을 원본 저장소라고 하면, Write-Through는 접수 장부와 창고 대장에 동시에 적고 두 곳이 다 기록된 뒤에 손님을 돌려보내는 방식입니다. Write-Behind는 접수 장부에만 먼저 적어 빠르게 손님을 보내고, 창고 대장은 잠시 뒤에 몰아서 적는 방식이라 빠르지만 그 사이에 사고가 나면 기록이 사라질 수 있습니다. Write-Around는 접수 장부를 건너뛰고 창고 대장에만 적는 방식으로, 한 번 쓰고 좀처럼 다시 읽지 않는 데이터에 어울립니다.

정리하면 Write-Through는 원본과 캐시를 함께 갱신해 일관성을 지키고, Write-Behind는 캐시에 먼저 쓰고 원본은 나중에 반영해 속도를 얻으며, Write-Around는 캐시를 우회해 쓸데없는 채우기를 줄입니다. 무엇을 고르든 캐시와 원본 중 어느 쪽이 먼저 바뀌는지, 그리고 그 사이의 짧은 틈을 서비스가 견딜 수 있는지가 판단의 기준입니다.

캐시 스탬피드

만료 순간 몰리는 요청 막기

잘 돌아가던 서비스가 정각마다, 혹은 배포 직후에 갑자기 멈추는 일이 있습니다. 원인을 살펴보면 캐시에 있던 값이 만료된 순간 수많은 요청이 한꺼번에 원본 저장소로 몰린 경우가 많고, 이렇게 한 점에 요청이 몰려 원본까지 무너지는 현상을 캐시 스탬피드(cache stampede)라고 부릅니다.

학교 매점 진열대를 떠올려 보면 상황이 잘 그려집니다. 쉬는 시간마다 학생들이 진열대에서 과자를 가져가는데, 진열대가 비는 순간 모두가 동시에 창고 문으로 달려가면 창고지기 한 명은 그 몰림을 감당할 수 없습니다.

창고 문 앞에 줄을 세워 한 명씩만 들어가게 하거나, 진열대가 완전히 비기 전에 미리 채워 두면 몰림은 생기지 않습니다. 만료 시각을 데이터마다 조금씩 어긋나게 흩어 놓는 것도 같은 이유에서 나온 방법입니다.

캐시 스탬피드는 만료라는 정상적인 사건이 순간적인 과부하로 바뀌는 문제이며, 한 요청만 원본을 읽고 나머지는 그 결과를 기다리게 하는 잠금(lock)이나 미리 채우기, 만료 시각 분산으로 막습니다. 핵심은 캐시가 비는 순간을 예측하고, 그 순간 원본으로 가는 길의 폭을 미리 정해 두는 것입니다.

캐시 일관성

원본과 캐시가 어긋나는 문제 다루기

가격을 내렸는데 어떤 손님에게는 옛 가격이 보이고 어떤 손님에게는 새 가격이 보인다면, 서비스는 신뢰를 잃습니다. 캐시는 원본의 복사본이므로 원본이 바뀐 뒤 복사본이 따라오지 않으면 어긋남이 생기고, 이 간격을 어떻게 줄일지 다루는 문제가 캐시 일관성(cache consistency)입니다.

식당의 메뉴판과 주방 레시피를 떠올려 보면 이해가 쉽습니다. 홀에 걸린 메뉴판은 캐시, 주방의 레시피는 원본 저장소에 해당합니다.

주방에서 재료를 바꿔 새 요리를 만들었는데 홀의 메뉴판을 그대로 두면, 손님은 메뉴판을 보고 주문하고 주방은 다른 요리를 내놓게 됩니다. 그래서 메뉴가 바뀌는 순간 메뉴판을 새로 쓰거나 아예 내렸다가 다시 걸어야 하고, 이때 어느 쪽을 먼저 바꾸느냐에 따라 아주 짧은 어긋남이 남기도 합니다.

캐시 일관성은 캐시와 원본이 같은 값을 가리키도록 유지하는 성질을 말하며, 보통 원본을 먼저 바꾸고 캐시를 지우는 방식과 유효 기간을 짧게 두어 어긋남을 스스로 회복하게 하는 방식으로 다룹니다. 완전히 같은 순간을 만드는 것은 현실적으로 어려우므로, 어느 정도의 어긋남을 허용할지 서비스가 먼저 정하는 것이 출발점입니다.

TTL 설계

만료 시간을 무엇으로 정할까

캐시에 넣어 둔 값을 언제까지 믿을지 정하지 않으면, 아주 오래된 값이 그럴듯한 얼굴로 사용자에게 계속 보입니다. 그래서 캐시의 모든 항목에는 살아 있는 시간, 즉 TTL(time to live)을 붙이는데, 이 시간을 무엇을 기준으로 정할지가 캐시 품질을 좌우합니다.

마트에서 유통기한을 관리하는 일과 비슷합니다. 우유처럼 상하기 쉬운 상품은 진열대에 오래 두지 않고 매일 확인해 내리며, 소금처럼 오래가는 상품은 훨씬 느긋하게 봅니다.

데이터도 마찬가지여서 재고 수량이나 로그인 상태처럼 자주 바뀌는 값은 짧게, 우편번호 목록이나 상품 분류처럼 거의 변하지 않는 값은 길게 잡습니다. 너무 짧게 잡으면 캐시가 자꾸 비어 원본을 다시 찾으러 가고, 너무 길게 잡으면 상한 정보를 계속 내놓게 됩니다.

TTL은 캐시 항목이 스스로 사라지는 시각을 정하는 값이며, 데이터가 얼마나 자주 바뀌는지와 조금 낡은 값을 얼마나 허용할 수 있는지를 함께 따져 정합니다. 확신이 서지 않을 때는 짧게 시작해 원본 부하와 어긋남을 보며 늘려 가는 편이, 길게 잡아 두고 문제를 뒤늦게 발견하는 것보다 안전합니다.

핫 키

부하가 한 키에 몰릴 때 대응하기

온라인 쇼핑몰에서 한정판 신발 하나가 판매를 시작하면 그 상품 페이지로만 요청이 폭발적으로 몰립니다. 서버를 여러 대로 늘려 두었는데도 정작 그 키를 담당한 서버 한 대만 숨이 차고 나머지는 놀고 있는 상황이 벌어지는데, 이렇게 부하가 한 키에 집중되는 현상을 핫 키(hot key)라고 부릅니다.

회사 구내식당에 창구가 다섯 개 있는데 오늘 메뉴 중 하나만 인기가 좋다고 생각해 보겠습니다. 줄은 그 메뉴를 내놓은 창구 하나에만 길게 늘어서고 다른 창구 앞은 텅 비어 있습니다.

창구를 늘리는 것만으로는 해결되지 않으니, 인기 메뉴를 여러 창구에 똑같이 나눠 담아 어느 창구에서든 받을 수 있게 만드는 것이 첫 번째 방법입니다. 줄 선 사람이 너무 많을 때 번호표를 나눠 주고 열 명씩 묶어 한 번에 처리하면 창구가 감당할 일이 확 줄어드는 것도 같은 원리입니다.

레디스에서도 특정 키의 값을 여러 복제본이나 여러 노드에 나눠 두거나, 같은 요청을 모아 한 번만 처리하고 결과를 나눠 주는 방식으로 핫 키의 부하를 분산합니다.

캐시 워밍

미리 채워 첫 요청 지연 줄이기

서비스를 새로 켜거나 캐시를 비운 직후에는 평소라면 순식간에 끝나던 요청이 몇 배로 느려집니다. 아무것도 채워지지 않은 상태에서 모든 요청이 원본 저장소까지 내려가야 하기 때문인데, 이 첫 구간을 줄이려고 미리 데이터를 채워 두는 작업을 캐시 워밍(cache warming)이라고 부릅니다.

식당을 새로 열었는데 개점 시간에 손님이 한꺼번에 들어오면 주방은 재료를 그때그때 손질하느라 첫 주문이 한없이 늦어집니다.

주방장은 영업 시작 전에 가장 많이 팔릴 메뉴가 무엇인지 장부를 보고, 그 재료만 먼저 손질해 냉장고 앞쪽에 가지런히 꺼내 둡니다. 손님이 들어와 주문서를 넣는 순간 손질된 재료가 바로 나오므로 첫 접시의 대기 시간이 줄어듭니다. 다만 아무 메뉴나 다 미리 손질하면 재료가 상하므로, 실제로 자주 팔릴 만한 것만 골라 준비해야 합니다.

레디스에서도 트래픽이 몰리기 전에 조회가 많은 키를 미리 읽어 캐시에 넣어 두면 첫 요청의 지연을 줄일 수 있고, 미리 채울 대상은 접근 기록을 근거로 골라야 합니다.

SLOWLOG

느린 명령을 찾아내기

레디스가 갑자기 느려졌는데 어느 명령이 원인인지 알 수 없다면, 서버를 세워 두고 명령을 하나씩 재 보는 수밖에 없습니다. 그런데 서비스는 멈출 수 없으니, 평소에 느린 명령만 자동으로 적어 두는 기록 장치가 있으면 원인을 훨씬 빠르게 찾을 수 있습니다.

공장 라인에서 하루에 수천 개의 부품을 조립하는데 라인 전체가 밀리기 시작했다고 생각해 보겠습니다.

관리자는 모든 작업을 다 적는 대신, 미리 정한 기준 시간을 넘긴 작업만 골라 적는 일지를 라인 옆에 붙여 둡니다. 기록에는 어떤 작업이었는지, 얼마나 걸렸는지, 언제 일어났는지가 남아 나중에 원인을 되짚을 수 있습니다. 일지가 가득 차면 오래된 기록부터 지워지므로 최근 것부터 확인하면 되고, 기준 시간을 너무 작게 잡으면 일지가 금방 넘치며 너무 크게 잡으면 정작 문제가 되는 작업을 놓칩니다.

레디스의 SLOWLOG는 설정한 시간보다 오래 걸린 명령을 실행 시간과 함께 남겨 주는 기능으로, 이를 통해 어떤 명령이 전체 지연을 끌어올리는지 찾아낼 수 있습니다.

지연 측정

응답 시간을 재고 해석하기

사용자가 화면이 느리다고 항의하는데 서버 지표는 멀쩡해 보이면 원인을 잡을 실마리가 없습니다. 전체 응답 시간만 재는 것으로는 어느 단계에서 시간이 새는지 알 수 없어, 구간을 나눠 재고 그 숫자를 해석하는 일이 필요합니다.

택배가 늦게 도착했을 때 전체 시간만 재면 어디서 늦었는지 알 수 없습니다. 주문 접수, 포장, 간선 운송, 집하장 대기, 배송 각 구간의 시간을 따로 재야 합니다.

어떤 날은 집하장 대기만 길어서 전체가 늦기도 하고, 어떤 날은 배송 기사 구간이 문제이기도 합니다. 그래서 평균 하나만 보지 않고 구간별로 나눠 잰 뒤 가장 느린 구간부터 손봅니다.

레디스에서도 응답 시간을 네트워크, 대기열, 명령 실행 구간으로 나눠 재고, 평균이 아니라 상위 백분위 지연을 함께 보아야 실제 병목이 드러납니다.

INFO와 모니터링

상태 지표를 읽는 방법

서버가 살아 있는지만 확인하고 넘어가면, 메모리가 서서히 차오르거나 연결이 조금씩 새는 변화를 놓칩니다. 그런 변화는 어느 날 갑자기 장애로 터지므로, 상태를 숫자로 보여 주는 지표를 주기적으로 읽는 습관이 필요합니다.

계기판의 모든 숫자를 매번 들여다볼 필요는 없고, 평소 값에서 크게 벗어난 항목을 찾는 것이 핵심입니다.

레디스의 INFO 명령은 메모리, 연결 수, 명령 처리량, 복제 상태 같은 지표를 한 번에 보여 주며, 이 값을 주기적으로 수집해 평소와 다른 변화를 감시하는 것이 모니터링입니다.

메모리 단편화

사용률과 단편화율 해석하기

레디스에 메모리가 넉넉히 남아 있는데도 새 데이터를 넣지 못하고 할당 오류가 나는 경우가 있습니다. 남은 공간이 여기저기 작은 조각으로 흩어져 있어 큰 덩어리를 넣을 자리가 없기 때문인데, 이 상태를 메모리 단편화(fragmentation)라고 부릅니다.

창고에 큰 짐과 작은 짐을 번갈아 넣었다 빼다 보면 전체 빈 공간은 충분한데도 큰 짐 하나를 넣을 자리가 없어집니다. 빈 자리가 이쪽저쪽에 조각으로 흩어져 있기 때문입니다.

창고 관리자가 남은 짐을 한쪽으로 밀어 붙여 빈 공간을 모아야 새 짐을 들일 수 있습니다. 그래서 창고의 전체 면적만 보지 않고 흩어진 빈틈이 얼마나 되는지를 함께 봐야 합니다.

레디스에서는 실제 사용 중인 메모리와 운영체제가 확보한 메모리의 비율로 단편화 정도를 가늠하며, 이 비율이 크게 벌어지면 재시작이나 조각 모음 같은 대응을 검토합니다.

연결 관리

접속 수와 타임아웃 다루기

Redis(레디스)를 쓰는 서비스가 갑자기 응답을 멈추면 가장 먼저 의심할 것이 접속이 어디서 막혔는지입니다. 클라이언트가 접속을 열어 두기만 하고 계속 늘리면 서버가 감당할 수 있는 한도를 넘어 새 요청을 받지 못하게 되는데, 연결 관리(connection management)는 이 접속 수를 세고 오래 붙어 있는 접속을 정리해 그런 정체를 막는 방법입니다.

은행 창구에 비유하면 창구 직원 수가 서버가 동시에 받아 줄 수 있는 접속 수이고, 손님이 창구 앞에 서서 서류를 계속 꺼내는 시간이 접속을 붙잡고 있는 시간입니다. 창구 수를 넘는 손님이 밀리면 대기줄만 길어지고, 앉은 손님이 볼일을 다 봤는데도 자리를 뜨지 않으면 뒤 손님은 영영 차례가 오지 않습니다.

그래서 은행은 대기줄 길이에 한도를 두고, 일정 시간 아무 말 없이 창구만 붙잡고 있는 손님에게는 시간 초과(timeout)를 알려 자리를 비우게 하며, 이미 떠난 손님이 남긴 빈 창구는 바로 정리합니다. Redis 에서도 maxclients 같은 설정으로 동시 접속 수를 제한하고, 클라이언트를 쉬게 두는 유휴 시간(idle timeout)과 작업 응답을 기다리는 시간(timeout)을 정해 두면 접속이 새는 일을 줄일 수 있습니다.

정리하면 연결 관리는 서버가 받아 줄 접속의 총량을 정하고, 오래 붙잡힌 접속을 시간 기준으로 걷어내는 작업입니다. 접속 수 상한과 타임아웃 값을 함께 정해 두면 갑작스러운 접속 폭주에도 서비스가 멈추지 않습니다.

ACL

사용자별로 명령과 키 권한 나누기

Redis(레디스)에 접속하는 프로그램이 모두 같은 비밀번호 하나를 쓰고 있다면, 그중 하나가 실수로 전체 데이터를 지우는 명령을 보내는 순간 나머지 서비스까지 함께 멈춥니다. ACL(Access Control List, 접근 제어 목록)은 접속하는 쪽마다 사용자를 따로 만들고, 그 사용자가 실행할 수 있는 명령과 만질 수 있는 키를 미리 정해 두는 기능입니다.

회사 건물에 비유하면 ACL 사용자는 사원증을 가진 직원 한 명이고, 명령 권한은 그 직원이 들어갈 수 있는 층, 키 권한은 열 수 있는 서랍의 범위입니다. 전 직원에게 마스터키를 주면 편하지만 한 명이 잘못 쓰면 건물 전체가 위험해지므로, 회사는 부서별로 층과 서랍을 나눠 출입증을 발급합니다.

Redis 에서도 사용자마다 허용할 명령 목록을 정하고 키 이름의 앞부분 같은 패턴으로 접근 범위를 제한하며, 정해진 것 외의 요청은 서버가 거절합니다. 덕분에 읽기만 하는 프로그램에는 읽기 명령만, 특정 서비스에는 자기 키만 보이게 나눠 줄 수 있습니다.

정리하면 ACL 은 하나의 접속 비밀번호를 여러 권한으로 쪼개, 사용자 단위로 명령과 키의 범위를 제한하는 장치입니다. 권한을 최소로 나눠 두면 사고가 나도 피해 범위가 그 사용자 몫에서 멈춥니다.

비밀번호와 TLS

접속 구간을 암호화하기

Redis(레디스)에 접속할 때 비밀번호를 아예 걸지 않았거나 평문으로 보낸다면, 같은 망에 붙은 누군가가 그 트래픽을 들여다보는 것만으로 접속 권한을 가져갈 수 있습니다. 비밀번호 설정과 TLS(Transport Layer Security, 전송 계층 보안)는 접속 자체에 신원 확인을 걸고, 클라이언트와 서버 사이를 오가는 데이터를 암호로 감싸는 방법입니다.

택배에 비유하면 비밀번호는 받는 사람에게 물어보는 암호이고, TLS 는 상자를 열 수 없는 잠금 봉투에 넣어 보내는 일입니다. 암호만 물어보면 옆에서 그 말을 들을 수 있으므로, 잠금 봉투 없이 암호만 주고받는 것은 문 앞에서 대문 비밀번호를 크게 외치는 것과 같습니다.

TLS 를 켜면 두 쪽이 먼저 서로의 인증서(certificate)를 확인해 상대가 진짜 그 서버인지 확인하고, 그다음에는 오가는 내용 전체를 암호화합니다. Redis 에서는 requirepass 같은 설정으로 비밀번호를 걸고, TLS 포트와 인증서를 지정해 암호화 접속만 받도록 구성합니다.

정리하면 비밀번호는 접속하는 쪽의 자격을 확인하는 장치이고, TLS 는 그 접속 구간을 암호화해 중간에서 엿보거나 바꿔치기하지 못하게 하는 장치입니다. 두 가지를 함께 켜야 접속 정보와 데이터가 밖으로 새지 않습니다.

위험 명령 차단

FLUSHALL 같은 명령 막기

운영 중인 Redis(레디스)에서 누군가 FLUSHALL 을 실행하면 그 서버의 모든 데이터가 한 줄의 명령으로 사라집니다. 위험 명령 차단은 이런 파괴적인 명령을 아예 실행하지 못하게 이름을 바꾸거나 지워 두는 안전장치입니다.

사무실에 비유하면 서류를 전부 태워 버리는 파쇄기를 아무 자리에나 두지 않고, 열쇠를 가진 사람만 쓸 수 있게 잠가 두는 것과 같습니다. 편하다는 이유로 파쇄기를 복도에 두면 청소 중에 실수로 스위치가 눌릴 수 있으므로, 회사는 장비의 위치를 옮기고 스위치에 덮개를 씌웁니다.

Redis 에서도 설정 파일에서 특정 명령의 이름을 다른 것으로 바꾸거나 빈 이름으로 지정해 실행 자체를 막고, 관리자만 쓸 명령은 별도 사용자에게만 허용합니다. 사용하지 않는 명령은 목록에서 지워 두는 편이, 사고가 난 뒤 되돌리는 것보다 훨씬 싸게 끝납니다.

정리하면 위험 명령 차단은 FLUSHALL, CONFIG 같은 강력한 명령의 실행 경로를 미리 없애거나 좁혀 두는 작업입니다. 지울 수 있는 명령을 남겨 두지 않는 것만으로도 큰 사고의 상당 부분을 막을 수 있습니다.

네트워크 설정

바인딩과 방화벽 점검하기

Redis(레디스)를 설치한 뒤 기본 설정 그대로 인터넷에 열어 두면, 외부에서 포트를 훑는 것만으로 접속을 시도하는 요청이 들어옵니다. 바인딩(binding)과 방화벽(firewall) 점검은 서버가 어느 주소에서 접속을 받을지 정하고, 허용한 곳 외의 접근을 망 앞에서 막는 일입니다.

아파트에 비유하면 바인딩은 건물 문을 어느 쪽에 낼지 정하는 일이고, 방화벽은 정문 외의 출입구를 막고 경비실에서 명단을 확인하는 일입니다. 문을 사방에 다 내 두면 편하지만 아무나 들어올 수 있으므로, 실제로 사람이 다니는 쪽에만 문을 내고 나머지는 벽으로 막습니다.

Redis 에서는 bind 설정으로 내부 주소나 루프백(loopback) 주소만 받도록 좁히고, 보호 모드(protected mode)를 켜 두어 외부 주소로 열렸을 때 함부로 응답하지 않게 합니다. 여기에 더해 OS 방화벽에서 정해진 포트와 정해진 대역만 허용하면, 설정을 잘못 건드렸을 때도 외부 노출을 한 겹 더 막을 수 있습니다.

정리하면 네트워크 설정 점검은 서버가 듣는 주소를 최소로 줄이고, 방화벽으로 그 주소에 닿을 수 있는 상대를 제한하는 일입니다. 두 겹을 함께 두어야 내부망 사정이 바뀌어도 서버가 그대로 문을 열어 두지 않습니다.

로그와 감사

무슨 일이 있었는지 남기기

장애가 난 뒤에 Redis(레디스)에서 무슨 일이 있었는지 아무 기록도 없으면, 원인을 짐작하는 것 말고는 할 수 있는 일이 없습니다. 로그(log)와 감사(audit)는 접속, 명령, 설정 변경 같은 사건을 시간과 함께 남겨 나중에 되짚어 볼 수 있게 하는 장치입니다.

건물에 비유하면 로그는 경비실의 출입 기록부이고, 감사는 누가 몇 시에 어느 방을 열었는지 나중에 대조해 보는 일입니다. 기록부가 없으면 사무실이 어질러진 뒤에 누가 들어왔는지 알 수 없고, 기록이 있어도 시간과 이름이 빠져 있으면 대조할 수 없으므로 형식을 정해 두는 것이 중요합니다.

Redis 는 실행 중에 일어난 일을 로그 파일에 남기고, 어떤 명령이 언제 실행됐는지 남기는 명령 로그(slow log, command log) 기능도 제공합니다. 여기에 접속과 권한 변경 같은 보안 사건을 별도로 모아 두면, 문제가 생겼을 때 시간 순서대로 원인을 좁힐 수 있습니다.

정리하면 로그와 감사는 서버에서 벌어진 일을 시각과 함께 기록해 두는 일입니다. 기록은 장애를 고치는 데만 쓰는 것이 아니라, 같은 일이 다시 일어나지 않게 확인하는 근거가 됩니다.

장애 대응 절차

증상에서 원인을 좁히는 순서

서비스가 갑자기 느려지거나 응답을 멈추면 담당자는 어디서부터 손대야 할지 몰라 이것저것을 동시에 건드리다 상황을 더 나쁘게 만들기 쉽습니다. 그런데도 많은 팀이 증상을 확인하기 전에 서버를 재시작하거나 설정을 바꾸는 식으로 대응해서, 정작 원인은 그대로 남아 같은 장애가 반복됩니다. 장애 대응 절차(incident response procedure)는 이런 혼란을 막기 위해 증상에서 출발해 원인을 한 단계씩 좁혀 가는 순서를 미리 정해 둔 규칙입니다.

이것은 응급실 진료 순서와 똑같이 이해할 수 있습니다. 환자가 "배가 아프다"고 하면 의사는 바로 수술하지 않고 먼저 어디가 어떻게 아픈지 묻고, 혈압과 체온 같은 기본 수치를 재고, 필요하면 혈액 검사나 영상 촬영으로 범위를 좁힌 뒤에야 원인을 확정합니다.

서비스도 마찬가지여서, 먼저 사용자가 겪는 증상과 발생 시각을 기록하고, 응답 시간·오류율·메모리 사용량 같은 기본 지표(metric)를 확인하고, 그다음 로그(log)와 느린 명령 기록을 살펴 어느 구간이 병목인지 좁힙니다. 이때 추측으로 설정을 바꾸면 증상이 잠깐 사라져도 원인은 남고, 무엇을 바꿨는지 기록이 없어 다음 장애에서 더 헤매게 됩니다.

정리하면 장애 대응 절차는 증상 수집, 지표 확인, 로그 분석, 원인 확정, 조치와 기록의 순서를 지키는 일이며, Redis라면 메모리 부족인지 느린 명령인지 연결 폭주인지를 이 순서로 가려내는 것이 핵심입니다.

용량 산정

필요한 메모리와 처리량 예측하기

서비스를 겨우 띄워 놓고 사용자가 늘어나자 메모리가 가득 차면서 Redis가 오래된 데이터를 지우기 시작하고, 그때부터 로그인이 풀리거나 순위가 사라지는 문제가 생깁니다. 반대로 넉넉히 잡아 두면 쓰지도 않는 메모리에 매달 비용을 내게 되므로, 필요한 만큼을 미리 계산해 두는 일이 필요합니다. 용량 산정(capacity planning)은 저장할 데이터의 양과 초당 처리할 요청 수를 예측해 필요한 메모리와 성능을 정하는 작업입니다.

이것은 이사를 앞둔 사람이 창고를 고르는 일과 비슷합니다. 짐 하나의 부피에 짐 개수를 곱해 전체 부피를 구하고, 여기에 통로와 선반이 차지할 공간을 더해야 실제 필요한 평수가 나옵니다.

Redis도 키(key) 하나가 대략 얼마를 차지하는지에 키 개수를 곱하고, Redis가 내부 관리에 쓰는 여유분과 복제본(replica)이나 백업용 사본의 몫을 더해 총메모리를 잡습니다. 처리량은 하루 요청 수를 몰아서 오는 시간대의 배수까지 고려해 초당 요청 수로 환산하고, 명령 하나가 걸리는 시간을 곱해 서버 한 대가 감당할 수 있는 양과 비교합니다. 여기에 장애 때 갑자기 몰리는 재시도 트래픽까지 얹어 두어야 계산이 실제 상황에서 버팁니다.

결국 용량 산정은 키 하나의 크기와 키 개수로 메모리를, 초당 요청 수와 명령 비용으로 처리량을 구하고 피크와 여유분을 더하는 계산이며, 이 값을 기준으로 최대 메모리(maxmemory)와 교체 정책을 정하게 됩니다.

세션 저장소

로그인 세션을 Redis에 두기

서버를 여러 대로 늘려 놓으면 사용자가 로그인한 서버와 다음 요청이 도착한 서버가 달라서, 방금 로그인했는데도 다시 로그인하라는 화면을 보게 됩니다. 서버마다 로그인 정보를 따로 들고 있으면 이 문제가 끊이지 않고, 서버 한 대가 재시작될 때 그 서버에 붙어 있던 사용자 전원이 로그아웃됩니다. 세션 저장소(session store)는 로그인 상태를 서버 밖 한곳에 모아 두어 어느 서버로 요청이 가도 같은 상태를 보게 만드는 역할을 합니다.

이것은 헬스장 사물함을 공용 보관소에 두는 것과 같습니다. 회원은 번호표 하나만 들고 다니고, 짐은 프런트의 공용 보관소에 맡기므로 어느 지점의 어느 직원에게 번호표를 보여도 같은 짐을 꺼낼 수 있습니다.

웹에서는 이 번호표가 세션 아이디(session ID)이고, Redis에 세션 아이디를 키로 삼아 사용자 정보와 만료 시각을 저장해 두면 여러 웹 서버가 같은 세션을 읽고 쓸 수 있습니다. 여기에 만료 시간(expire)을 걸어 두면 사용자가 아무 동작 없이 오래 지났을 때 세션이 저절로 사라져, 직접 지우는 코드를 곳곳에 넣지 않아도 됩니다. 세션 데이터는 사라져도 재로그인으로 복구되는 종류라서, 유실을 감수하고 속도를 택하는 구성이 흔히 쓰입니다.

정리하면 세션 저장소는 세션 아이디를 키로 로그인 상태를 서버 밖에 모아 두고 만료 시간으로 정리하는 방식이며, Redis는 그 저장소로 자주 선택되는 도구 중 하나입니다.

리더보드

Sorted Set으로 순위 관리하기

게임이나 이벤트에서 점수가 바뀔 때마다 전체 사용자를 정렬해 순위를 매기면, 사용자가 늘수록 정렬에 드는 시간이 눈덩이처럼 커져 순위 화면이 몇 초씩 늦게 뜹니다. 특정 사용자의 등수를 물을 때마다 전원을 훑는 것도 같은 이유로 감당이 어렵습니다. 리더보드(leaderboard)는 이런 순위 조회를 빠르게 하려고 점수와 사용자를 한 묶음으로 관리하는 저장 구조를 쓰며, Redis에서는 정렬된 집합(Sorted Set)이 그 역할을 맡습니다.

이것은 마라톤 대회의 기록 게시판과 같습니다. 주최자는 완주자마다 이름표와 기록을 함께 적어 두고, 기록 순서대로 게시판을 유지하므로 "전체 1등부터 10등까지"를 바로 보여 줄 수 있습니다.

Redis의 정렬된 집합도 구성원(member)마다 점수(score)를 붙여 두고 그 점수 순서로 스스로 줄을 세우며, 점수를 새로 넣으면 기존 기록이 갱신되고 순서도 다시 잡힙니다. 등수를 알고 싶으면 해당 구성원의 순위를 물어보는 명령으로 바로 답이 나오고, 상위 구간만 잘라 달라고 하면 그 구간만 꺼내 옵니다. 같은 점수일 때의 순서를 어떻게 정할지는 설계에서 정해 두어야 화면이 흔들리지 않습니다.

결국 리더보드는 사용자와 점수를 짝지어 점수순으로 유지하는 구조이며, Redis의 정렬된 집합은 점수 갱신과 순위 조회와 구간 조회를 모두 빠르게 처리하는 도구입니다.

요청 수 제한

Rate Limiting 구현하기

인기 상품이 올라오거나 자동화 프로그램이 몰리면 같은 사용자가 짧은 시간에 수천 번 요청을 보내 서버가 마비되고, 정작 일반 사용자는 아무 응답도 받지 못합니다. 요청마다 비밀번호 확인이나 데이터베이스 조회처럼 비싼 작업이 붙어 있다면 피해는 더 커집니다. 요청 수 제한(rate limiting)은 한 사용자나 한 주소가 정해진 시간 동안 보낼 수 있는 요청 수를 넘지 않게 막는 장치입니다.

이것은 주차장 입구에서 시간당 입차 대수를 제한하는 것과 같습니다. 관리인은 차가 들어올 때마다 시간대별 계수기를 하나 올리고, 정해진 대수에 도달하면 다음 시간대가 될 때까지 입차를 막습니다.

Redis에서는 사용자별 키에 요청 횟수를 세어 두고, 요청이 올 때마다 값을 하나 늘린 뒤 정해진 시간이 지나면 그 키가 저절로 사라지게 만듭니다. 이때 늘리는 것과 만료를 설정하는 것을 한 번에 처리해야 여러 서버가 동시에 요청을 받아도 횟수가 어긋나지 않습니다. 단순히 세는 방식은 시간 구간이 바뀌는 순간에 몰아서 통과시키는 약점이 있어, 요청이 몰리는 서비스에서는 조금 더 정교한 계산 방식을 함께 검토합니다.

정리하면 요청 수 제한은 사용자별 요청 횟수를 시간 창과 함께 세어 한도를 넘으면 거절하는 방식이며, Redis는 그 계수기를 여러 서버가 공유하게 해 주는 저장소로 쓰입니다.

작업 큐 연동

Celery 같은 워커와 함께 쓰기

사진을 올리면 썸네일을 만들고 메일을 보내는 작업을 요청 처리 중에 함께 하면, 사용자는 화면이 멈춘 채로 오래 기다려야 하고 트래픽이 몰릴 때는 요청 자체가 밀립니다. 이 작업들을 요청과 분리해 나중에 처리하려면 할 일을 쌓아 두는 공간과 그것을 꺼내 일하는 일꾼이 필요합니다. 작업 큐(queue) 연동은 이런 구조에서 할 일 목록을 Redis에 두고 워커(worker)가 꺼내 처리하게 만드는 방식이며, Celery 같은 도구가 이 역할을 맡습니다.

이것은 바쁜 식당의 주문서 꽂이와 같습니다. 홀 직원은 손님 주문을 받아 주문서를 꽂이에 걸어 두고 곧바로 다음 손님을 맞으며, 주방의 요리사들이 꽂이에서 주문서를 하나씩 꺼내 순서대로 요리합니다.

Redis의 목록(list)이나 스트림(stream)이 그 꽂이에 해당하고, 요리를 시작한 주문서는 처리 중인 별도 자리에 옮겨 두어 요리사가 갑자기 쓰러져도 다른 요리사가 이어받을 수 있게 합니다. 주문이 갑자기 몰리면 요리사를 더 부르면 되고, 손님이 적을 때는 요리사를 줄이면 되므로 홀의 응답 속도와 주방의 처리 속도를 따로 조절할 수 있습니다. 다만 같은 주문이 두 번 조리되지 않도록 처리 표시를 확실히 남기는 설계가 필요합니다.

결국 작업 큐 연동은 처리할 일을 Redis의 목록에 쌓고 워커가 꺼내 일하게 하는 구조이며, Celery는 그 목록을 주고받는 규칙과 재시도·실패 처리를 붙여 주는 도구입니다.

Pub/Sub

발행과 구독으로 메시지 전달하기

여러 서버가 같은 소식을 동시에 나눠야 하는데 한쪽이 계속 물어보는 방식만 있다면, 소식은 늦게 도착하고 물어보는 쪽 서버는 그 일만 하다 지칩니다. 이런 곤란을 없애려고 Redis가 내놓은 기능이 Pub/Sub(발행과 구독)입니다.

아파트 방송실을 떠올리면 쉬운데, 관리인이 마이크 앞에서 안내 방송을 하면 미리 스피커를 켜 둔 세대만 그 소리를 듣습니다.

여기서 채널(channel)은 방송을 구분하는 이름표와 같아서, 세대는 관심 있는 채널 이름을 등록해 두고 관리인은 그 이름을 불러 방송합니다. 발행자가 메시지를 보내면 Redis가 등록된 모든 구독자에게 같은 내용을 즉시 복사해 배달하고, 구독자가 없는 채널에 보낸 방송은 아무도 듣지 못한 채 사라집니다. 그래서 Pub/Sub은 지나간 방송을 다시 들려주지 않고 지금 연결된 스피커에만 소리를 전합니다.

정리하면 PUBLISH로 채널에 메시지를 던지고 SUBSCRIBE로 채널을 듣는 것이 Pub/Sub의 전부이며, 보관과 재전송이 필요하면 Stream 같은 다른 구조를 함께 써야 합니다.

실시간 알림

접속자에게 즉시 밀어주기

새 소식이 생길 때마다 사용자가 화면을 새로고침해야 알 수 있고, 서버가 몇 초마다 물어보는 방식으로는 소식이 늦게 뜨거나 서버가 헛일로 바빠집니다. 그래서 접속해 있는 사람에게 서버가 먼저 밀어 주는 실시간 알림이 필요하고, Redis에서는 Pub/Sub이 그 중심을 맡습니다.

식당 진동벨을 떠올리면 좋은데, 손님은 벨을 들고 자리에 앉아 있고 주방에서 음식이 준비되면 그 벨을 울려 부릅니다.

웹에서는 손님의 벨이 끊어지지 않는 연결(소켓)이고, 손님이 접속할 때 서버가 그 연결을 목록에 등록해 둡니다. 여러 대의 서버가 하나의 채널을 함께 구독하고 있다가 새 알림을 그 채널에 발행하면, 각 서버는 자기에게 연결된 손님에게만 골라서 알림을 밀어 줍니다. 다만 연결이 끊긴 손님의 벨은 울리지 않으므로, 놓친 알림을 나중에 보여주려면 별도의 저장이 필요합니다.

정리하면 실시간 알림은 사용자별 연결을 유지한 채 Redis의 발행과 구독으로 서버들 사이에 소식을 퍼뜨리는 구조이며, 접속 상태와 놓친 알림의 보관은 따로 설계해야 합니다.

자동완성과 태그 검색

검색 보조 자료구조 활용하기

검색창에 두세 글자만 쳤는데도 관련 단어 후보가 바로 뜨지 않으면 사용자는 답답함을 느끼고 다른 곳으로 옮겨 갑니다. 이런 즉답을 위해 Redis의 정렬된 집합(Sorted Set)과 집합(Set)이 검색 보조 자료구조로 쓰입니다.

대형 마트 입구의 안내 색인을 떠올리면 쉬운데, 코너마다 어떤 상품이 있는지 미리 정리해 둔 목록을 보고 손님은 원하는 곳으로 바로 갑니다.

자동완성은 단어의 앞부분을 기준으로 후보를 미리 묶어 두고, 정렬된 집합의 점수(score)를 인기나 최근 사용 정도로 매겨 두면 인기순으로 잘라 보여줄 수 있습니다. 같은 집합에서 사전 순 범위를 조회하는 명령을 쓰면 입력한 글자로 시작하는 단어들을 빠르게 꺼낼 수 있습니다. 태그 검색은 상품마다 붙은 태그를 집합으로 저장하고 여러 태그의 교집합을 구하는 방식으로, 두 조건을 모두 만족하는 항목만 남깁니다.

정리하면 자동완성은 접두어별 후보를 정렬된 집합에 담아 순위와 사전 순으로 꺼내는 기술이고, 태그 검색은 집합의 교집합으로 조건을 조합하는 기술입니다.

Redis Modules

모듈로 기능 확장하기

캐시로 시작한 Redis에 전문 검색이나 문서 저장, 시계열 집계까지 맡기고 싶어도 기본 명령만으로는 표현할 수 없는 요구가 생깁니다. 그때 서버를 새로 붙이는 대신 Redis 안에 기능을 끼워 넣는 방식이 Redis Modules(모듈)입니다.

스마트폰을 떠올리면 쉬운데, 전화와 문자만 되던 기기에 앱을 설치하면 사진 편집도 지도도 쓸 수 있게 됩니다.

모듈은 C나 C++로 작성해 서버에 적재하는 확장 프로그램으로, 새로운 명령과 새로운 자료형을 Redis에 더합니다. 검색을 담당하는 RediSearch, 문서를 다루는 RedisJSON, 시계열을 담당하는 RedisTimeSeries처럼 목적별 모듈이 따로 존재합니다. 모듈은 서버 프로세스 안에서 함께 도는 만큼 데이터를 밖으로 옮기지 않아 빠르지만, 그만큼 장애와 업그레이드의 책임도 함께 집니다.

정리하면 Redis Modules는 하나의 서버 안에서 명령과 자료형을 확장하는 구조이며, 필요한 모듈을 골라 적재하는 판단이 운영의 몫입니다.

클라이언트 라이브러리

언어별 클라이언트 고르기

프로그램에서 Redis에 값을 넣고 빼려면 네트워크 연결을 열고 Redis만의 응답 형식(RESP)을 직접 주고받아야 해서, 매번 그 바닥부터 짜면 실수가 잦습니다. 이 반복을 대신 처리해 주는 것이 언어별 클라이언트 라이브러리(client library)입니다.

외국에 나가서 통역사를 쓰는 상황과 비슷한데, 내 말을 그 나라 말로 바꿔 전하고 상대의 대답을 다시 내 말로 돌려줍니다.

Java에는 Jedis와 Lettuce, Python에는 redis-py, Node.js에는 node-redis, Go에는 go-redis처럼 언어마다 널리 쓰이는 클라이언트가 있습니다. 좋은 클라이언트는 연결을 미리 여러 개 열어 두는 연결 풀(pool)과 끊겼을 때의 재시도, 클러스터에서 올바른 서버를 찾아가는 라우팅을 대신 처리합니다. 같은 언어 안에서도 Jedis는 단순한 동기 방식에, Lettuce는 비동기와 논블로킹에 강점이 있어 동시 요청이 많은 서비스에서는 선택이 갈립니다.

정리하면 클라이언트 라이브러리는 응답 형식과 연결 관리를 감싸 개발자가 명령에만 집중하게 해 주는 도구이며, 언어와 동시성 요구에 맞춰 고르는 것이 핵심입니다.

다음 학습 로드맵

실무 역량으로 이어지는 순서

명령 몇 개를 외운 사람이 실제 서비스에서 Redis를 맡으면, 메모리가 차오르거나 복제가 끊기는 순간 무엇부터 봐야 할지 몰라 멈추기 쉽습니다. 그래서 학습은 자료구조에서 운영, 그리고 설계로 이어지는 순서를 따라야 실무 역량으로 남습니다.

등산 코스를 떠올리면 좋은데, 낮은 구간에서 체력을 만들고 중간 구간에서 장비를 익힌 뒤에야 높은 구간에 오를 수 있습니다.

첫 구간은 문자열·리스트·해시·집합·정렬된 집합과 만료 시간을 직접 다뤄 보며 어떤 상황에 어떤 구조가 맞는지 몸으로 익히는 단계입니다. 둘째 구간은 영속화(RDB와 AOF), 메모리 정책, 모니터링과 느린 명령 찾기를 다루는 운영 단계이고, 셋째 구간은 복제와 Sentinel, Cluster로 고가용성과 확장을 설계하는 단계입니다. 마지막 구간은 캐싱 패턴과 Pub/Sub, Stream, 모듈을 실제 기능에 붙여 보고 장애 상황을 되짚는 응용 단계입니다.

정리하면 로드맵은 자료구조, 운영, 고가용성, 응용의 네 구간으로 이어지며, 각 구간을 실제 서비스 지표와 장애 경험으로 닫아야 다음 구간이 열립니다.
