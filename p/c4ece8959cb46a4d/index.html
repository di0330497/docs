1단계 EFS의 위치와 기본 개념

EFS는 EC2 인스턴스 등 AWS 리소스가 NFS로 마운트해 함께 읽고 쓰는, 서버·용량 준비 없이 사용하는 확장형 공유 파일 스토리지 서비스다.

1상대의 출발점 확인

여러 서버가 같은 파일을 함께 쓰려면 기존에는 파일 서버라는 별도 장비를 직접 사서 운영했다. 파일 서버에 디스크를 꽂고 용량을 예측해 미리 늘려 두고, 장애가 나면 직접 복구해야 했다. EC2 인스턴스 여러 대가 같은 파일을 동시에 읽고 쓰는 상황(예: 여러 웹 서버가 같은 정적 콘텐츠를 서빙하는 경우)에서도 파일 서버를 두고 NFS로 연결하는 방식이 전형적이었다. 이 방식은 용량·성능 예측이 빗나가면 낭비나 부족이 생기고, 하드웨어를 직접 관리해야 해서 운영 부담이 컸다.

2질문 제기

저장 인프라를 직접 관리하지 않고도 여러 EC2 인스턴스가 동시에 쓰는 공유 파일 스토리지를 만들 수는 없을까?

3구조적 핵심 예시

EFS는 파일 시스템을 만들면 그 순간부터 바로 쓸 수 있는 서버리스 공유 파일 스토리지다. EC2 인스턴스 3대가 같은 EFS 파일 시스템을 각자의 디렉터리에 마운트(운영체제의 폴더로 연결)하면, 한 인스턴스가 파일을 저장하자마자 다른 인스턴스가 그 파일을 읽는다. 용량을 미리 지정하지 않고, 저장한 만큼만 비용이 나온다.

4단계별 동작 과정

  1. 파일 시스템 생성AWS 콘솔에서 이름과 리전(Region, AWS 서비스가 운영되는 물리적 지점)만 정하고 파일 시스템을 만든다. 스토리지 용량은 지정하지 않는다.
  2. 마운트 타깃 생성VPC(가상 네트워크) 안의 각 가용 영역(AZ, 데이터센터 묶음 단위)에 마운트 타깃(인스턴스가 연결하는 네트워크 지점)을 만들고, EC2 인스턴스가 NFS 포트 2049로 접근하도록 보안 그룹(방화벽 규칙)을 허용한다.
  3. 마운트 및 사용EC2 인스턴스에서 mount 명령으로 EFS를 폴더에 연결하고, 그 폴더로 파일을 읽고 쓴다. 파일이 늘어나도 서비스가 자동으로 저장 공간을 늘려 처리한다.

5본질 요약

저장 용량과 처리 인프라를 AWS가 관리하는 서버리스 공유 파일 스토리지를 만들고, NFS 프로토콜로 여러 EC2 인스턴스가 동시에 같은 파일을 읽고 쓰게 하는 것

4단계별 동작 과정

  2. 파일 잠금애플리케이션이 NFS 잠금 호출로 파일을 잠그면, 잠금이 풀릴 때까지 다른 클라이언트의 중복 쓰기가 제한된다.
  3. POSIX 권한 적용파일·디렉터리마다 소유자·그룹·권한이 유지되어 기존 Linux 애플리케이션이 수정 없이 그대로 동작한다.

EFS 성능을 평가하는 세 축으로, 지연(latency)은 응답 속도, 처리량(throughput)은 단위 시간당 데이터 전송량, IOPS는 초당 입출력 요청 수를 뜻한다.

1상대의 출발점 확인

파일 스토리지의 성능은 보통 세 숫자로 평가한다. 지연(latency, 요청 후 응답까지 걸리는 시간), 처리량(throughput, 단위 시간에 옮기는 데이터 양, MB/s), IOPS(초당 처리하는 읽기·쓰기 요청 횟수). 기존 온프레미스 파일 서버는 디스크의 개수와 종류(HDD/SSD)를 미리 정해야 했고, 이 구성이 성능을 고정시켜 예상보다 요청이 많으면 병목이, 적으면 장비 낭비가 생겼다.

2질문 제기

파일 시스템의 성능이 지연·처리량·IOPS라는 세 차원으로 측정된다면, 워크로드에 맞는 수준을 어떻게 구성하고 조정할까?

3구조적 핵심 예시

EFS에서 지연은 리전 내 마운트 타깃으로 연결된 인스턴스가 파일 I/O(입출력)를 주고받는 시간으로 나타나고, 처리량과 IOPS는 성능 모드(General Purpose/Max I/O)와 처리량 모드(Elastic/Provisioned/Bursting)로 정해진다. 예를 들어 일반적인 웹 애플리케이션은 지연이 낮은 General Purpose 모드가 맞고, 수천 대 클라이언트가 몰리는 빅데이터 분석처럼 수평 확장이 중요한 워크로드는 Max I/O 모드를 고려한다.

4단계별 동작 과정

  1. 성능 차원 확인지연(응답 시간), 처리량(MB/s), IOPS(초당 요청 수)로 현재 워크로드의 성능 목표를 정한다.
  2. 성능 모드 선택파일 시스템 생성 시 정해지는 성능 모드로, General Purpose는 낮은 지연, Max I/O는 대규모 수평 확장에 유리하다. 생성 후에는 바꿀 수 없다.
  3. 처리량 모드 조정처리량 모드를 워크로드에 맞춰 선택한다. Elastic은 사용량에 따라 자동 조정되고, Provisioned는 원하는 수준을 미리 지정하며, Bursting은 버스트 크레딧(일시적으로 처리량을 올리는 데 쓰는 적립 단위)으로 처리량을 일시적으로 높인다.

파일 수가 아주 많은 초대형 워크로드와 보통 규모에서의 낮은 지연 요구를, 하나의 파일 시스템이 동시에 만족할 수 없는 이유는 무엇인가?

3구조적 핵심 예시

파일 시스템을 생성할 때 General Purpose와 Max I/O 중 하나를 고릅니다. General Purpose는 파일 접근 지연을 10ms 미만 수준으로 낮게 유지하는 데 초점을 맞춰, 파일 수가 100만 개를 넘기 전까지의 대부분의 워크로드에 권장됩니다. Max I/O는 파일 수가 수백만~수천만 개에 이르는 초고확장 워크로드에서도 처리 성능이 유지되도록 설계되었지만, 그 대가로 지연은 더 커집니다. 두 모드는 파일 수와 지연 사이의 다른 균형점을 고른 것이며, 생성 후에는 바꿀 수 없습니다.

4단계별 동작 과정

  1. 생성 시 모드 선택파일 시스템을 만들 때 General Purpose 또는 Max I/O 중 하나를 지정합니다.
  2. 모드별 동작 차이General Purpose는 메타데이터(파일 이름·위치 정보) 처리에 사용하는 I/O(입출력)를 낮은 지연에 맞춰 운영하고, Max I/O는 파일 수가 늘어도 처리량이 떨어지지 않도록 작업을 분산 처리하되 지연은 더 커집니다.
  3. 변경 불가와 대체생성 후에는 모드를 바꿀 수 없어, 다른 모드가 필요하면 새 파일 시스템을 만들고 데이터를 옮겨야 합니다.

기존 처리량 방식은 파일 시스템 크기에 연동된 고정 처리량을 받거나, 필요한 처리량을 사람이 직접 지정해 사야 했습니다. 그런데 대부분의 파일 시스템은 평소 사용량이 낮다가 특정 시간에만 몰리는 패턴을 보이므로, 고정 처리량은 사용량이 낮을 때도 그만큼의 비용이 계속 나가고 사용량이 몰릴 때는 처리량이 부족해지는 문제가 있었습니다.

Provisioned 처리량 모드

1상대의 출발점 확인

Bursting 방식은 파일 시스템 크기에 따라 기본 처리량을 받고, 몰리는 순간에는 쌓아 둔 버스트 크레딧으로 처리량을 끌어올립니다. 그런데 크레딧은 사용하지 않을 때만 쌓이므로, 평소에 잘 쓰지 않으면서도 특정 작업 시간에는 반드시 일정 처리량이 필요한 워크로드는 크레딧이 바닥나 처리가 지연되기 쉬웠습니다.

2질문 제기

파일 시스템 크기나 쌓아 둔 크레딧과 무관하게, 항상 일정 수준의 처리량을 보장받으려면 어떻게 해야 하는가?

3구조적 핵심 예시

4단계별 동작 과정

  1. 처리량 지정파일 시스템에 필요한 처리량을 GiB/s 단위로 지정합니다.

2질문 제기

평소에는 낮은 처리량으로 비용을 아끼면서, 접근이 몰리는 순간에만 더 높은 처리량을 내려면 무엇을 쌓아 두어야 하는가?

3구조적 핵심 예시

Bursting 처리량 모드에서는 파일 시스템 크기 1TiB마다 기본 처리량 50MiB/s가 주어집니다. 이 기본 처리량을 다 쓰지 않으면 남은 양이 버스트 크레딧으로 쌓이고, 크레딧이 있는 동안에는 기본의 최대 3배(1TiB당 100MiB/s)까지 처리량을 낼 수 있습니다. 크레딧을 모두 소진하면 기본 처리량으로 돌아갑니다.

4단계별 동작 과정

  1. 기본 처리량 부여파일 시스템 크기에 비례해 초당 처리량이 결정됩니다.
  2. 버스트 크레딧 축적사용하지 않은 처리량이 버스트 크레딧으로 쌓입니다.
  3. 버스트 사용과 복귀크레딧이 있는 동안 기본의 최대 3배까지 처리량을 내다가, 크레딧이 소진되면 기본 처리량으로 돌아갑니다.

3구조적 핵심 예시

  2. 파일 시스템 지표 확인CloudWatch 지표의 PercentIOLimit로 크레딧 소진 여부를, TotalIOBytes로 실제 부하 수준을 확인해 파일 시스템 병목인지 판단합니다.
  3. 구간 분리와 원인 좁히기클라이언트 내부 처리 지연과 네트워크 지연, 파일 시스템 지연을 각각 측정해 어느 구간이 느린지 분리하고, 파일 수 증가나 메타데이터 작업 증가 같은 구체적 원인을 확인합니다.

파일 시스템을 만들 때 몇 가지 항목만 정하면, 하드웨어나 용량 예측 없이 바로 쓸 수 있는 공유 스토리지가 만들어지게 하려면 무엇을 선택해야 하는가?

3구조적 핵심 예시

콘솔이나 CLI에서 파일 시스템 생성을 실행하면, 이름과 리전, 스토리지 클래스(저장 계층), 처리량 모드, 성능 모드, 암호화 키, 수명 주기 정책, 마운트 대상(파일 시스템에 접근하는 관문)을 순서대로 정합니다. 생성을 마치면 파일 시스템 ID가 발급되고, 연결할 서버에서 NFS로 마운트하면 곧바로 파일을 주고받을 수 있습니다. 용량은 지정하지 않으며 저장된 데이터 양에 따라 자동으로 늘어납니다.

4단계별 동작 과정

  1. 기본 설정 선택이름과 리전, 스토리지 클래스(Standard 또는 IA), 처리량 모드, 성능 모드를 지정합니다.
  2. 보안·수명 주기 설정암호화에 쓸 KMS 키, 오래된 파일을 저비용 저장 계층으로 옮기는 수명 주기 정책, 태그를 지정합니다.
  3. 접근 구성 후 생성VPC(가상 네트워크) 안의 어느 서브넷에 마운트 대상을 만들지, 어떤 보안 그룹(방화벽 규칙 묶음)을 허용할지 정하고 생성합니다.

파일 시스템 삭제

더 이상 쓰지 않는 EFS 파일 시스템을 마운트 해제와 함께 영구히 제거해 저장 비용을 없애는 작업이다.

1상대의 출발점 확인

기존 스토리지에서 삭제는 신중한 작업이었다. 인스턴스에 연결된 디스크를 떼어내고, 데이터를 백업한 뒤에야 삭제할 수 있었고, 한 번 삭제하면 되돌릴 수 없었다. EFS도 마찬가지로, 파일 시스템을 삭제하면 그 안의 데이터와 마운트 타깃, 정책, 태그까지 전부 영구히 제거된다. 특히 파일 시스템이 아직 마운트된 채 삭제를 실행하면, 접속하고 있던 클라이언트가 갑자기 연결을 잃고 아직 데이터가 남아 있던 작업이 유실될 수 있다. 그래서 "지금 삭제해도 되는 상태인지"를 확인하는 절차가 없다면 한 번의 실수로 전체 데이터를 잃게 된다.

2질문 제기

마운트된 파일 시스템을 실수로 삭제해 데이터를 영구히 잃지 않으려면, 삭제 전에 어떤 확인을 거쳐야 할까?

3구조적 핵심 예시

콘솔에서 파일 시스템을 삭제하면 EFS는 먼저 "이 파일 시스템과 모든 데이터가 영구히 삭제되며 되돌릴 수 없다"는 확인 절차를 보여 준다. 사용자가 이 확인을 통과해야만 삭제가 진행된다. 삭제가 시작되면 파일 시스템 상태가 deleting으로 바뀌고, 완료되면 목록에서 사라진다. 삭제를 취소하거나 되살리는 수단은 없다.

4단계별 동작 과정

  1. 삭제 전 확인아직 마운트되어 있는 클라이언트를 언마운트하고, 보존할 데이터가 있다면 AWS Backup 백업이나 다른 저장소로 복사해 두었는지 확인한다.
  2. 삭제 요청콘솔이나 CLI에서 대상 파일 시스템을 선택해 삭제를 실행하고, 영구 삭제 경고에 대한 확인을 입력한다.
  3. 삭제 완료상태가 deleting을 거쳐 완료되면 메타데이터와 데이터가 전부 제거되고, 이후에는 어떤 방법으로도 복구할 수 없다.

파일 시스템 정책 만들기

리소스 기반 IAM 정책으로 누가 어떤 조건에서 파일 시스템에 접근할 수 있는지 제어하는 규칙 집합이다.

1상대의 출발점 확인

EFS에 대한 접근 제어는 원래 여러 계층에 나뉘어 있었다. VPC 보안 그룹은 네트워크 트래픽을, IAM 자격 증명 정책은 API 호출을, NFS 권한은 파일 수준 접근을 각각 담당했다. 이 방식은 각 계층을 따로 설정해야 해서, "이 파일 시스템에 접근할 수 있는 대상"을 한 화면에서 파악하기 어렵고 규칙이 흩어질수록 관리가 어려워진다. 특히 파일 시스템 자체에 부여되는 자원 기반 정책이 없어서, 특정 계정이나 역할만 마운트하게 하는 규칙을 파일 시스템 단위에서 강제할 수 없었다.

2질문 제기

파일 시스템 자체에 접근 규칙을 붙여, 누가 이 파일 시스템을 사용할 수 있는지를 한 곳에서 제어할 수는 없을까?

3구조적 핵심 예시

파일 시스템 정책은 IAM 정책 언어로 작성한 JSON 문서를 파일 시스템에 연결하는 자원 기반 정책(resource-based policy)이다. 예를 들어 "계정 111122223333의 특정 역할만 이 파일 시스템을 마운트하고 데이터에 접근할 수 있다"는 규칙을 정책으로 만들어 파일 시스템에 붙이면, EFS는 그 파일 시스템으로 들어오는 모든 요청을 이 정책과 IAM 정책을 함께 평가해 허용·거부를 결정한다.

4단계별 동작 과정

  1. 정책 작성IAM 정책 형식으로 Principal(누구에게), Action(마운트·읽기·쓰기 같은 어떤 작업을), Condition(어떤 조건에서)을 정의한 JSON을 작성한다.
  2. 정책 연결콘솔이나 API로 이 JSON을 대상 파일 시스템에 적용한다. 적용된 정책은 그 파일 시스템의 접근 규칙으로 즉시 동작한다.
  3. 접근 평가파일 시스템에 요청이 들어오면 EFS가 자원 기반 정책과 IAM 자격 증명 정책을 함께 확인해, 규칙에 맞는 요청만 허용하고 나머지는 거부한다.

태그: 자원 관리와 접근 제어

파일 시스템에 붙이는 키-값 메타데이터로, 비용·소유자 식별 같은 자원 관리와 IAM 정책의 조건 기반 접근 제어에 쓰인다.

1상대의 출발점 확인

파일 시스템이 여러 개가 되면 각각이 어떤 프로젝트나 환경에 속하는지 기억하거나 별도 문서로 관리해야 했다. 콘솔 목록에는 파일 시스템마다 ID와 기본 정보만 보여서, 용도별로 찾으려면 하나씩 열어 확인해야 한다. 비용도 파일 시스템 단위로 나오지 않아 어느 팀의 파일 시스템이 얼마를 쓰는지 집계하기 어렵고, 접근 제어도 개별 파일 시스템 단위로만 적용되어 "프로젝트 A에 속한 파일 시스템 전체"처럼 묶음 단위로 규칙을 만들 수 없었다.

2질문 제기

수많은 파일 시스템을 용도별로 묶어 검색하고, 비용을 집계하고, 접근 규칙까지 적용할 수는 없을까?

3구조적 핵심 예시

태그는 파일 시스템에 붙이는 key-value 쌍이다. 예를 들어 Environment=production, Team=data 같은 태그를 파일 시스템에 붙여 두면, 콘솔에서 태그 값으로 목록을 필터링해 원하는 파일 시스템만 볼 수 있다. 같은 태그는 비용 할당 보고서에서 태그별 청구 금액을 집계하는 기준이 되고, IAM 정책의 조건(condition)에서도 사용되어 특정 태그가 달린 파일 시스템에만 접근을 허용하는 규칙을 만들 수 있다.

4단계별 동작 과정

  1. 태그 부여파일 시스템 생성 시 또는 이후에 콘솔·API로 key-value 태그를 추가하고, 필요하면 수정·삭제한다.
  2. 자원 관리목록에서 태그로 필터링해 파일 시스템을 찾고, 비용 할당 태그를 활성화해 태그별 사용량·비용을 보고서로 집계한다.
  3. 접근 제어 활용IAM 정책의 조건에 태그를 사용해, 특정 태그가 없는 파일 시스템에 대한 접근을 거부하는 등 태그 기반 규칙을 적용한다.

1상대의 출발점 확인

파일 시스템을 만든 직후에 바로 마운트를 시도하면 실패하는 경우가 있다. 기존 방식에서는 "만들었으니 곧 쓸 수 있겠지"라고 기대하고 바로 작업했지만, 실제로는 파일 시스템이 아직 준비 중이어서 마운트가 거부될 수 있었다. 삭제 중인 파일 시스템에 작업을 걸어도 오류가 나는데, 이런 상황에서 파일 시스템이 지금 어떤 단계에 있는지 알려 주는 표시가 없으면 원인을 추측할 수밖에 없었다.

2질문 제기

파일 시스템이 지금 생성 중인지, 사용 가능한지, 삭제 중인지 어떻게 한눈에 알 수 있을까?

3구조적 핵심 예시

EFS는 각 파일 시스템에 상태 값을 부여한다. 콘솔의 파일 시스템 목록에서 상태 열을 보면 creating(생성 중)이면 아직 마운트할 수 없고, available(사용 가능)이 되어야 마운트할 수 있다. 삭제를 요청하면 상태가 deleting(삭제 중)으로 바뀌었다가 완료되면 목록에서 사라진다. 같은 정보는 DescribeFileSystems API로도 조회할 수 있다.

4단계별 동작 과정

  1. 상태 조회콘솔 목록이나 DescribeFileSystems API로 대상 파일 시스템의 상태 값을 확인한다.
  2. 상태 해석creating이면 마운트가 아직 불가능하므로 완료를 기다리고, available이면 마운트와 데이터 작업이 가능하며, deleting이면 어떤 작업도 할 수 없다.
  3. 상태에 맞는 작업상태가 available이 된 시점에 마운트를 수행하고, deleting이면 삭제가 완료될 때까지 기다린 뒤 목록에서 사라졌는지 확인한다.

마운트 타깃 개념과 관리

EFS 파일 시스템이 VPC 서브넷 안에서 NFS로 접근될 수 있게 해주는 네트워크 엔드포인트로, 생성·삭제·상태 확인으로 접근 경로를 관리한다.

1상대의 출발점 확인

VPC 안의 EC2 인스턴스에서 공유 파일 시스템에 접근하려면, 그 파일 시스템이 VPC 네트워크에 드러나는 접근 지점이 있어야 한다. 기존 NFS 서버는 서버 자신이 가진 IP 주소가 곧 접근 지점이었지만, EFS는 관리형 서비스라서 파일 시스템 자체에 네트워크 주소가 없다. 그래서 인스턴스 입장에서 "어디로 접근해야 하는지"가 처음에는 명확하지 않고, 여러 가용 영역에 흩어진 인스턴스가 모두 같은 파일 시스템에 접근하려면 가용 영역마다 별도의 접근 지점이 필요하다는 점도 파악하기 어렵다.

2질문 제기

VPC 안의 인스턴스들이 파일 시스템에 접근하려면, 네트워크상의 접근 지점을 어떻게 만들고 관리해야 할까?

3구조적 핵심 예시

마운트 타깃은 파일 시스템을 VPC에 연결하는 네트워크 지점이다. 파일 시스템당 가용 영역마다 하나씩 만들 수 있고, 각 마운트 타깃은 해당 가용 영역의 서브넷에 배치되어 그 서브넷의 인스턴스가 NFS(포트 2049)로 파일 시스템에 접근할 수 있게 한다. 마운트 타깃에는 보안 그룹을 붙여 어떤 대상의 트래픽을 허용할지도 함께 정한다.

4단계별 동작 과정

  1. 마운트 타깃 생성파일 시스템에 대해 VPC, 가용 영역, 서브넷, 보안 그룹을 지정해 마운트 타깃을 생성한다.
  2. 접근 경로 제공마운트 타깃이 생성되면 해당 가용 영역의 인스턴스는 마운트 타깃이 제공하는 DNS 이름이나 IP로 파일 시스템에 접근할 수 있다.
  3. 마운트 타깃 삭제더 이상 접근이 필요 없는 가용 영역의 마운트 타깃은 삭제해, 그 경로로 들어오는 접근을 끊는다.

마운트 타깃 VPC·보안 그룹 변경

마운트 타깃의 VPC는 직접 바꿀 수 없어 대상 VPC에 새 마운트 타깃을 만들어 교체하고, 연결된 보안 그룹은 마운트 타깃 구성을 수정해 변경한다.

1상대의 출발점 확인

마운트 타깃을 만들 때 지정하는 VPC와 보안 그룹은 접근 범위를 결정한다. VPC를 잘못 고르면 접근이 아예 되지 않고, 보안 그룹을 너무 넓게 잡으면 원치 않는 대상에게 접근이 열린다. 기존 방식에서는 이런 설정을 바꾸려면 마운트 타깃을 통째로 다시 만들어야 했기 때문에, 변경하는 동안 접근이 중단되는 문제가 있었다. 반면 어떤 항목은 만들어진 뒤에도 바꿀 수 있어서, 무엇이 변경 가능하고 무엇이 불가능한지 모르면 불필요한 삭제·재생성을 반복하게 된다.

2질문 제기

이미 만든 마운트 타깃의 네트워크 구성을 바꿔야 할 때, 무엇은 바꿀 수 있고 무엇은 다시 만들어야 할까?

3구조적 핵심 예시

마운트 타깃의 VPC는 생성 후 변경할 수 없다. 다른 VPC로 옮기려면 기존 마운트 타깃을 삭제하고 대상 VPC의 서브넷에 새 마운트 타깃을 만들어야 한다. 반면 보안 그룹은 실행 중인 마운트 타깃에서도 언제든 교체할 수 있어서, 접근 범위를 좁히거나 넓힐 때 마운트 타깃을 다시 만들 필요 없이 보안 그룹만 바꾸면 된다.

4단계별 동작 과정

  1. 보안 그룹 변경콘솔이나 API에서 마운트 타깃이 사용하는 보안 그룹을 교체해, NFS 트래픽을 허용할 대상의 범위를 조정한다.
  2. VPC 변경다른 VPC로 옮겨야 하면 기존 마운트 타깃을 삭제하고, 대상 VPC의 서브넷에 새 마운트 타깃을 생성한다.
  3. 접근 재검증변경 후 해당 가용 영역의 인스턴스가 정상적으로 마운트되는지, 허용된 대상만 접근할 수 있는지 확인한다.

1상대의 출발점 확인

기존에는 파일 서버를 운영하면 관리자가 방화벽을 직접 설정하고, 접근을 허용할 IP 대역을 규칙에 하나씩 추가했다. 그런데 IP 범위로만 제어하면 같은 사무실 대역이면 어떤 장비든 접근이 열리고, 허용 목록이 늘어날수록 관리자가 빠뜨리거나 잘못 넣는 규칙이 생겼다. 통신 포트를 열어 둔 채 방치하면 의도하지 않은 다른 컴퓨터가 파일 서버에 연결될 수 있는 문제도 있었다. EFS도 파일 시스템이므로, 이 네트워크 경계에서의 제어 문제를 그대로 안고 있다.

2질문 제기

마운트 요청이 오는 EC2 인스턴스가 정말 우리 것이 맞는지, 네트워크 경계에서 어떻게 1차적으로 차단할까?

3구조적 핵심 예시

VPC 안의 EC2 인스턴스가 EFS 마운트 타깃(파일 시스템이 VPC 안에 내놓은 연결 지점)에 NFS(네트워크 파일 시스템)로 2049번 포트에 연결을 시도하면, 마운트 타깃에 붙어 있는 보안 그룹(인스턴스에 적용하는 방화벽 규칙 모음)이 수신 규칙을 검사한다. 규칙에 "2049 포트로 들어오는 연결을 특정 보안 그룹에서만 허용"이라고 적혀 있으면, 그 보안 그룹을 가진 EC2에서 온 연결만 통과하고 나머지는 버려진다. 출발지를 IP 주소가 아니라 보안 그룹 ID로 보는 것이 핵심이다.

4단계별 동작 과정

  1. 보안 그룹 규칙 정의파일 시스템을 만들 때 마운트 타깃에 보안 그룹을 붙이고, TCP 2049 포트의 수신 트래픽을 접근을 허용할 EC2의 보안 그룹에서만 받아들이는 규칙을 추가한다.
  2. 연결 시도클라이언트 EC2가 마운트 타깃의 IP 주소로 2049 포트 NFS 연결을 보내면, 마운트 타깃의 보안 그룹이 패킷이 온 출발 보안 그룹을 확인한다.
  3. 허용/차단 판정출발 보안 그룹이 수신 규칙에 있으면 연결이 열려 마운트가 진행되고, 없으면 연결이 거부되어 접근 자체가 불가능하다.

1상대의 출발점 확인

기존에는 VPC 안의 EC2 인스턴스가 EFS를 사용하려면, 트래픽이 인터넷 게이트웨이(인터넷으로 나가는 통로)를 지나 AWS의 공용 네트워크를 통과해야 했다. 이 경로는 패킷이 VPC 바깥의 공용 구간을 거치므로, 규정상 인터넷을 통과하는 통신을 금지하는 환경에서는 EFS를 아예 쓸 수 없었고, 경유 구간이 길어 보안 검토 부담과 전달 지연도 생겼다.

2질문 제기

인터넷을 전혀 거치지 않고 VPC 내부 네트워크만으로 EFS에 안전하게 연결하려면 어떻게 해야 할까?

3구조적 핵심 예시

VPC에 게이트웨이 엔드포인트(VPC 안에서 AWS 서비스로 연결되도록 만든 전달 지점)를 Amazon EFS 대상으로 하나 생성하면, EC2의 연결 요청이 인터넷 게이트웨이로 나가지 않고 이 엔드포인트를 통해 AWS 내부 네트워크로만 전달된다. 여기에 엔드포인트 정책을 달아서 특정 파일 시스템에만 접근하도록 제한할 수도 있다.

4단계별 동작 과정

  1. 엔드포인트 생성VPC에 게이트웨이 엔드포인트를 만들고 대상 서비스로 Amazon EFS를 지정한 뒤, 적용할 라우팅 테이블(트래픽이 어느 경로로 갈지 정하는 표)을 선택한다.
  2. 경로 우회EC2에서 EFS로 향하는 트래픽이 라우팅 테이블에 따라 인터넷이 아닌 엔드포인트 방향으로 전달된다.
  3. 연결과 접근 제어요청이 엔드포인트를 거쳐 EFS에 도달하고, 엔드포인트 정책에 따라 파일 시스템별 접근 허용 여부가 판정된다.

5단계 마운트

EFS 파일 시스템은 VPC 안의 마운트 대상에 NFS로 연결하며, 이때 DNS 이름(권장)이나 IP 주소로 마운트한다는 기본 개념과 절차를 설명하는 개요.

1상대의 출발점 확인

기존에는 파일 서버에 연결하려면 관리자가 서버의 IP 주소를 직접 알아야 했다. IP 주소가 바뀌면 모든 클라이언트의 설정을 일일이 고쳐야 했고, 서버가 여러 대면 어느 주소로 연결할지도 관리 대상이었다. EFS도 마찬가지로 "이 파일 시스템에 연결하려면 어느 IP로 가야 하나"라는 문제가 첫 관문이다. 가용 영역마다 연결 지점이 다르고 그 주소가 바뀔 수 있기 때문에, IP를 직접 외워 쓰는 방식은 유지보수 비용만 키운다.

2질문 제기

파일 시스템의 IP 주소가 바뀌어도, 클라이언트가 항상 같은 주소만 가지고 연결할 수는 없을까?

3구조적 핵심 예시

EFS는 각 마운트 타깃(파일 시스템이 VPC 안에 내놓은 연결 지점)에 DNS 이름(도메인 형태의 주소)을 부여한다. 예를 들어 파일 시스템 ID가 fs-12345678이면 마운트 타깃은 "fs-12345678.efs.ap-northeast-2.amazonaws.com" 같은 이름으로 불리고, 이 이름은 항상 그 마운트 타깃의 현재 IP 주소로 변환된다. 클라이언트는 이 DNS 이름으로 연결하므로 IP가 바뀌어도 설정을 고칠 필요가 없다.

4단계별 동작 과정

  1. 마운트 타깃 생성파일 시스템을 만들면 VPC의 각 가용 영역(서로 다른 물리적 위치의 데이터 센터 묶음)에 마운트 타깃이 생기고, 각각에 프라이빗 IP와 DNS 이름이 할당된다.
  2. DNS 이름 해석클라이언트가 DNS 이름으로 요청하면 그 이름이 현재 마운트 타깃의 IP 주소로 변환되어 돌아온다.
  3. NFS 연결클라이언트가 돌려받은 IP로 NFS 연결을 맺어 파일 시스템에 접근하며, 이후 IP가 바뀌어도 DNS 이름이 새 IP를 계속 안내한다.

5단계 마운트

리눅스·macOS에서 NFS 클라이언트를 준비하고 EFS에 맞는 권장 마운트 옵션(하드 마운트, 시간 제한 등)을 적용해 안정적으로 연결하는 방법.

1상대의 출발점 확인

기존에는 NFS로 파일 서버를 연결할 때 마운트 옵션(연결 동작을 정하는 부가 설정)을 사용자가 각자 알아서 넣었다. 팀마다 옵션이 달라서, 서버가 응답하지 않으면 무한히 기다리는 설정을 쓴 곳은 서버 장애 시 인스턴스 전체가 멈춰 버렸고, 대기 시간을 너무 짧게 잡은 곳은 순간적인 지연에도 연결이 끊겼다. EFS도 NFS 클라이언트를 쓰는 만큼, 옵션을 잘못 고르면 같은 문제가 그대로 나타난다.

2질문 제기

EFS에 안정적으로 연결하면서도 서버 지연이나 일시적 장애에 견디는 마운트 설정은 무엇일까?

3구조적 핵심 예시

EFS 문서가 권장하는 옵션 조합을 그대로 쓰면 된다. 예를 들어 "nfsvers=4.1,timeo=600,retrans=2"는 NFS 4.1 프로토콜(EFS가 공식 지원하는 버전)을 쓰고, 응답 대기 시간을 충분히 두며, 일시적 오류 시 재전송을 하게 하는 설정이다. 클라이언트는 이 옵션을 붙인 마운트 명령 한 줄로 연결되므로, 옵션을 외워 조합할 필요가 없다.

4단계별 동작 과정

  1. NFS 클라이언트 설치EC2 인스턴스에 NFS 클라이언트 소프트웨어(파일 시스템 연결 명령을 처리하는 프로그램)를 설치한다.
  2. 권장 옵션으로 마운트 실행"sudo mount -t nfs4 -o nfsvers=4.1,timeo=600,retrans=2 마운트타깃DNS이름:/ 대상폴더" 형태로 연결해, 타임아웃과 재시도 동작을 옵션대로 적용한다.
  3. 연결 결과 확인마운트된 대상 폴더에서 파일을 읽고 써 보며 EFS와의 연결이 정상인지 확인한다.

5본질 요약

5단계 마운트

amazon-efs-utils의 마운트 헬퍼(mount.efs)가 DNS 이름만으로 최적 옵션과 TLS 암호화를 자동 적용해 마운트하게 하는 방법.

1상대의 출발점 확인

기존에는 EFS를 마운트할 때 DNS 이름, 포트, 권장 옵션, 암호화 설정을 모두 사용자가 직접 알아서 명령에 입력해야 했다. 한 글자만 틀려도 연결이 실패하고, 전송 중 암호화(TLS)를 쓰려면 별도의 도구 설정까지 손봐야 해서 초보자에게 진입 장벽이 높았다. 같은 마운트를 반복할수록 설정을 외우고 재입력하는 비용이 계속 쌓였다.

2질문 제기

마운트에 필요한 모든 설정을 사용자가 외우지 않아도, 한 명령으로 올바르게 연결할 방법은 없을까?

3구조적 핵심 예시

amazon-efs-utils라는 AWS 제공 도구를 설치해 두면 "sudo mount -t efs fs-12345678:/ /mnt/efs" 한 줄만으로 연결된다. 도구가 파일 시스템 ID만 보고 DNS 이름, 권장 옵션, TLS 암호화(전송 중 데이터를 암호화하는 기능)까지 자동으로 조합해서 마운트를 진행한다. 사용자는 파일 시스템 ID뿐만 아니라 VPC와 가용 영역 정보를 헬퍼가 자동으로 찾아낸다.

4단계별 동작 과정

  1. 헬퍼 설치인스턴스에 amazon-efs-utils 패키지(EFS 전용 마운트 헬퍼가 포함된 AWS 제공 도구 모음)를 설치한다.
  2. 마운트 명령 실행"mount -t efs 파일시스템ID:/ 대상폴더" 형태로 명령을 내리면, 헬퍼가 파일 시스템 ID를 기준으로 나머지 설정을 자동으로 채운다.
  3. 자동 연결헬퍼가 DNS 이름, 권장 옵션, 암호화 여부를 판단해 NFS 연결을 만들고 대상 폴더에 연결해 준다.

기존에는 Linux와 Mac에서 EFS를 연결하는 방법이 서로 달라서 혼란이 많았다. Linux EC2는 NFS 클라이언트만 설치하면 되지만, Mac EC2는 운영체제의 NFS 동작 특성 때문에 같은 명령으로는 연결이 실패하는 경우가 많았다. 문서마다 옵션을 다르게 알려 주어, 같은 파일 시스템이 Linux에서는 연결되고 Mac에서는 안 되는 상황도 생겼다.

2질문 제기

Linux EC2와 Mac EC2에서 각각 어떤 명령과 절차로 EFS를 안정적으로 마운트할까?

3구조적 핵심 예시

Linux EC2에서는 amazon-efs-utils를 설치한 뒤 "mount -t efs fs-12345678:/ /mnt/efs"로 마운트한다. Mac EC2에서도 amazon-efs-utils를 설치하되, Mac의 NFS 클라이언트 요구사항에 맞춰 파일 시스템 ID 대신 마운트 타깃의 DNS 이름을 직접 사용하고 필요한 옵션을 추가해 마운트한다. 두 경우 모두 결과적으로 같은 EFS 파일 시스템이 대상 폴더에 연결된다.

4단계별 동작 과정

  1. EFS 클라이언트 설치Linux EC2와 Mac EC2 각각에 amazon-efs-utils(EFS 연결용 AWS 제공 도구)를 설치한다.
  2. OS에 맞는 마운트 명령 실행Linux는 파일 시스템 ID를 쓰는 헬퍼 명령으로, Mac은 OS별 요구사항(예: 특정 NFS 옵션과 DNS 이름 사용)을 반영한 명령으로 연결을 시도한다.
  3. 마운트 폴더 접근두 OS 모두 연결이 성립되면 마운트 폴더에서 파일 읽기와 쓰기가 동일하게 가능해진다.

EFS 클라이언트 설치·업그레이드·FIPS

EFS 클라이언트(amazon-efs-utils)를 수동 또는 Systems Manager로 설치·업그레이드하고 FIPS 모드를 활성화하는 방법.

1상대의 출발점 확인

EFS를 마운트하려면 기본적으로 NFS 클라이언트만 있으면 되지만, 마운트 헬퍼, IAM 인증, 전송 중 암호화 같은 EFS 전용 기능을 쓰려면 amazon-efs-utils 라는 별도 패키지가 필요했다. 각 서버에서 수동으로 패키지를 설치하면 서버마다 버전이 제각각이 되고, 업그레이드를 놓치면 보안 패치와 새 기능이 빠진 채 운영된다. FIPS(미국 연방 정부 규격 암호화 모듈) 요구가 있는 환경에서는 기본 패키지로는 그 규정을 맞출 수 없다는 한계도 있다.

2질문 제기

EFS 전용 클라이언트를 모든 서버에 같은 방법으로 설치하고 최신 상태로 유지하면서 FIPS 요구까지 맞출 수는 없을까?

3구조적 핵심 예시

EC2 Linux 인스턴스 하나에서 sudo yum install -y amazon-efs-utils 명령으로 패키지를 설치하면 마운트 헬퍼가 생긴다. 이후 같은 패키지를 SSM(AWS 시스템 관리 서비스) 배포 방식으로 수백 대 인스턴스에 일괄 설치하고, botocore(API 호출 라이브러리)·stunnel(TLS 터널 프로그램) 업그레이드와 FIPS 모드 켜기까지 모두 이 패키지 관리 안에서 처리된다.

4단계별 동작 과정

  1. 패키지 설치amazon-efs-utils 를 수동 설치하거나 SSM 으로 여러 인스턴스에 자동 배포한다. 설치되면 efs 마운트 명령과 TLS 암호화 구성 요소가 준비된다.
  2. 구성 요소 업그레이드botocore 와 stunnel 을 최신 버전으로 올려 보안 패치와 새 기능을 반영한다. stunnel 설치에 실패하면 그 원인을 먼저 해결해야 TLS 마운트가 동작한다.
  3. FIPS 모드 활성화설정으로 FIPS 모드를 켜 정부 규격 암호화 모듈을 사용하도록 전환하면, 이후 모든 TLS 통신이 FIPS 호환 방식으로 이루어진다.

EFS 전용 클라이언트 패키지 하나로 마운트 헬퍼 설치부터 보안 업그레이드와 FIPS 암호화 요구까지 일관되게 관리하게 하는 것

자동 마운트와 언마운트

재부팅 후에도 연결이 유지되도록 자동 마운트를 설정하고, 더 이상 필요 없는 파일 시스템을 안전하게 언마운트하는 방법.

1상대의 출발점 확인

EC2 인스턴스에서 EFS를 쓰려면 부팅할 때마다 mount 명령이나 마운트 헬퍼를 수동으로 실행해야 했다. 인스턴스가 재부팅되면 마운트가 풀려서 다시 연결해 줘야 하고, 자동 확장으로 새 인스턴스가 생겨도 사람이 명령을 내리기 전까지는 파일 시스템이 비어 보인다. 반대로 더 이상 쓰지 않는 마운트를 정리하지 않으면 연결이 남아 리소스가 낭비되고 어느 서버가 어디에 붙어 있는지 혼란스러워진다.

2질문 제기

서버가 부팅될 때마다 사람이 명령을 내리지 않아도 EFS가 자동으로 연결되고, 필요 없어진 연결은 깨끗이 분리할 수는 없을까?

3구조적 핵심 예시

EC2 Linux 인스턴스의 /etc/fstab 파일(부팅 시 자동으로 마운트할 목록)에 파일시스템ID:/ efs defaults,_netdev 0 0 한 줄을 추가하면, 인스턴스가 재부팅될 때 부팅 절차가 이 줄을 읽어 EFS를 자동으로 마운트한다. _netdev 옵션은 네트워크가 준비된 뒤에 마운트하라는 지시라서 부팅 순서 문제로 실패하지 않는다.

4단계별 동작 과정

  1. 설정 반영fstab 에 EFS 마운트 줄을 추가하거나, 새 EC2 인스턴스 생성 시 사용자 데이터에 마운트 명령을 넣어 첫 부팅부터 자동 연결되게 한다. Linux·Mac 의 NFS 클라이언트에서도 동일하게 자동 마운트를 지정할 수 있다.
  2. 부팅 시 자동 마운트인스턴스가 시작되면 네트워크가 준비된 뒤 fstab 의 줄이 실행되어 EFS 파일 시스템이 지정한 디렉터리에 연결된다.
  3. 언마운트연결이 더 이상 필요 없으면 umount /마운트지점 명령으로 연결을 끊는다. 해당 디렉터리를 사용 중인 프로세스가 없어야 정상적으로 분리된다.

5본질 요약

fstab 설정과 부팅 순서를 이용해 EFS를 서버 시작 시 자동으로 연결하고, umount 명령으로 필요할 때 깨끗이 분리하게 하는 것

특수 환경 마운트: 타 리전·One Zone·IAM·액세스 포인트

타 리전, One Zone 파일 시스템, IAM 권한 부여, 액세스 포인트 등 특수 환경에서 EFS를 마운트하는 방법을 다룬다.

1상대의 출발점 확인

EFS 마운트는 기본적으로 파일 시스템이 만들어진 리전 안에서 DNS 이름으로 연결된다. 그런데 파일 시스템이 다른 리전에 있거나, One Zone 유형이라 특정 가용 영역에만 마운트 타깃이 존재하거나, IAM 권한으로만 접근을 허용하거나, 사용자마다 다른 루트 디렉터리를 강제해야 하는 경우에는 기본 마운트 명령 하나로 조건을 맞출 수 없었다. DB 서버가 다른 리전에 있는데 파일을 그 리전의 EFS에서 읽어야 하는 상황 같은 것이 대표적인 예다.

2질문 제기

리전·파일 시스템 유형·권한 체계가 다른 환경에서도 같은 파일 시스템에 안전하게 마운트할 수는 없을까?

3구조적 핵심 예시

다른 리전의 EFS에 접속할 때는 해당 리전의 마운트 타깃 IP 주소를 확인해 DNS 이름 대신 그 IP로 마운트 명령을 실행한다. IAM 인증이 필요한 경우에는 tls 옵션과 iam 옵션을 함께 지정해 클라이언트가 서명된 요청으로 접속하게 하고, 액세스 포인트를 쓸 때는 accesspoint=ap-... 옵션으로 마운트하면 강제된 사용자와 디렉터리가 적용된다.

4단계별 동작 과정

  1. 환경 확인파일 시스템의 리전과 유형(Regional/One Zone)을 확인하고, 접속할 리전의 마운트 타깃 IP 와 가용 영역을 알아낸다. One Zone 파일 시스템은 해당 가용 영역 안에서만 마운트 타깃이 동작한다.
  2. 마운트 옵션 구성타 리전이면 IP 주소로, IAM 인증이면 tls,iam 옵션으로, 액세스 포인트면 accesspoint= 옵션으로 마운트 명령을 구성한다.
  3. 마운트 실행구성된 명령이 마운트를 수행하고, 액세스 포인트를 쓴 경우 클라이언트는 강제된 사용자 ID 와 루트 디렉터리 안에서만 파일을 보게 된다.

1상대의 출발점 확인

EFS 마운트 타깃은 파일 시스템이 만들어진 VPC 안의 사설 IP 주소를 가진다. 다른 VPC 나 다른 계정의 인스턴스에서는 기본적으로 그 주소에 닿을 수 없어서, 파일을 공유하려면 파일을 복사해서 옮기거나 파일 시스템을 새로 만들어야 했다. VPC는 기본적으로 서로 격리되어 있어서 네트워크 경로가 없으면 같은 AWS 안이라도 접근이 차단되기 때문이다.

2질문 제기

3구조적 핵심 예시

4단계별 동작 과정

  1. 네트워크 연결VPC 피어링이나 전송 게이트웨이로 두 VPC를 연결하고, 각 라우팅 테이블에 상대 VPC 대역으로 가는 경로를 추가한다. 다른 계정이면 파일 시스템 쪽에서 계정 간 접근을 허용하는 설정과 IAM 권한을 준비한다.
  2. 보안 규칙 허용마운트 타깃의 보안 그룹에 상대 VPC 대역에서 NFS 포트 2049 로 들어오는 트래픽을 허용하는 규칙을 추가한다.
  3. 마운트상대 인스턴스에서 마운트 타깃의 DNS 이름이나 IP 주소로 마운트 명령을 실행해 파일 시스템을 연결한다.

1상대의 출발점 확인

마운트가 실패했을 때 원인을 한눈에 알 수 있는 경우는 드물었다. DNS 가 잘못 풀렸는지, 보안 그룹이 막혔는지, 클라이언트 도구가 빠졌는지, 파일 시스템이 삭제되었는지 등 원인이 겹쳐 있어 보이지 않았고, 사람들은 설정을 하나씩 고쳐 보며 시간을 낭비했다. 원인을 제대로 짚지 못하면 같은 실패가 반복된다는 한계가 있었다.

2질문 제기

마운트 실패의 원인을 어디서부터 확인해야 빠르게 찾아 고칠 수 있을까?

3구조적 핵심 예시

sudo mount -t efs -o tls fs-12345678:/ efs 명령이 실패했다고 하자. 가장 흔한 원인은 세 가지다. 마운트 타깃 IP 를 찾지 못하거나(DNS·네트워크 경로), 보안 그룹이 NFS 포트 2049 를 막거나, amazon-efs-utils 가 설치되지 않은 경우다. 이 세 가지를 순서대로 점검하면 대부분의 실패 원인이 드러난다.

4단계별 동작 과정

  1. 접속 경로 확인파일 시스템 상태가 available 인지, 마운트 타깃이 존재하는지, DNS 이름이 IP 로 풀리는지 확인한다. EFS 마운트 헬퍼가 만든 로그에서 오류 메시지를 뽑아 원인을 좁힌다.
  2. 네트워크 규칙 확인VPC 라우팅과 마운트 타깃·인스턴스의 보안 그룹이 NFS 포트 2049(전송 중 암호화를 쓰면 해당 TLS 터널까지)를 허용하는지 확인한다.
  3. 클라이언트 준비 확인NFS 클라이언트와 amazon-efs-utils 의 설치 여부와 최신 버전 여부를 확인하고, 문제가 해결되면 다시 마운트 명령을 실행한다.

AWS DataSync로 데이터 전송

AWS DataSync를 사용해 온프레미스 스토리지나 다른 AWS 서비스와 Amazon EFS 파일 시스템 간에 대용량 데이터를 자동으로 빠르게 전송하는 방법.

1상대의 출발점 확인

기존 스토리지의 대용량 데이터를 EFS로 옮길 때 rsync 스크립트나 수동 복사를 쓰면 수백 기가바이트에서 수 테라바이트 단위의 파일을 옮기는 데 며칠이 걸렸다. 전송 중 연결이 끊기면 처음부터 다시 시작해야 했고, 파일 수가 많을수록 전송 속도는 더 떨어졌다. 온프레미스 서버와 클라우드를 오가는 전송은 사람이 직접 감독하고 재시작해야 하는 부담이 있었다.

2질문 제기

수십 테라바이트의 기존 데이터를 전송이 끊겨도 이어서, 빠르게, 자동으로 EFS로 옮길 수는 없을까?

3구조적 핵심 예시

온프레미스 서버에 AWS DataSync 에이전트(가상 머신)를 설치하고, 소스 위치와 대상 EFS를 지정하면 DataSync 가 여러 연결을 병렬로 사용해 데이터를 전송한다. 전송 작업에는 일정을 걸 수 있어서 매일 밤 새로 생긴 파일만 증분(변경된 부분만) 전송하도록 예약할 수도 있다.

4단계별 동작 과정

  1. 에이전트와 위치 구성온프레미스에 DataSync 에이전트를 배포하고, 소스(예: 온프레미스 NFS 스토리지)와 대상(EFS) 위치를 등록한다.
  2. 작업 실행전송 작업을 만들어 소스와 대상을 연결하고, 포함·제외할 파일 필터와 실행 일정을 지정한 뒤 실행한다. DataSync 는 여러 병렬 연결로 데이터를 읽고 쓰며 전송 속도를 높인다.
  3. 전송 완료와 확인전송이 끝나면 대상 EFS에 데이터가 반영되고, 작업 로그와 보고서로 전송된 파일 수와 바이트를 확인한다. 일정 작업이면 이후 주기마다 변경된 부분만 증분 전송된다.

AWS Transfer Family 연동

AWS Transfer Family를 Amazon EFS와 연동해 SFTP, FTPS, FTP 프로토콜로 파일 시스템에 접근하고 데이터를 전송하는 방법.

1상대의 출발점 확인

EFS의 파일에 접근하는 기본 방법은 NFS 프로토콜을 쓰는 것이다. EC2 인스턴스에 EFS를 마운트하거나 DataSync로 일괄 전송해야 하므로, NFS 클라이언트를 설치하고 마운트 경로를 직접 알아야 한다. 그런데 NFS는 리눅스·유닉스 계열 환경에서 주로 쓰이고, 외부 파트너처럼 NFS를 모르는 상대에게 파일을 주고받게 하려면 마운트 권한까지 열어줘야 하는 불편함과 보안 부담이 따른다. 윈도우나 일반 FTP 도구에 익숙한 사용자는 EFS 데이터에 접근할 방법이 사실상 마땅치 않다.

2질문 제기

NFS를 직접 몰라도 SFTP·FTPS 같은 익숙한 파일 전송 프로토콜로 EFS에 파일을 주고받으려면 어떻게 해야 할까?

3구조적 핵심 예시

AWS Transfer Family가 EFS 파일 시스템 앞에 대신 서 있는 SFTP·FTPS·FTP 서버 역할을 한다. 사용자는 Transfer Family가 제공하는 엔드포인트 호스트 이름에 SFTP 클라이언트로 접속하면, 그 뒤에 연결된 EFS 파일 시스템의 디렉터리 구조가 그대로 보인다. Transfer Family는 인증된 사용자를 EFS의 특정 디렉터리에 연결해 주는 게이트웨이로 동작한다.

4단계별 동작 과정

  1. 서버와 사용자 생성Transfer Family 콘솔에서 SFTP·FTPS·FTP 중 프로토콜을 고르고, 사용자를 만들 때 그 사용자가 접근할 EFS 파일 시스템과 홈 디렉터리 경로를 지정한다.
  2. 접속과 인증사용자는 클라이언트로 엔드포인트에 접속하고, 서비스가 사용자 이름·암호나 SSH 키로 인증을 마친 뒤 해당 사용자를 지정된 EFS 디렉터리에 연결한다.
  3. 파일 전송사용자가 업로드·다운로드·삭제한 파일이 그대로 EFS 파일 시스템에 반영된다. 별도의 동기화 작업은 필요 없다.

1상대의 출발점 확인

온프레미스 데이터센터의 서버가 EFS를 쓰려면, EFS가 있는 VPC의 마운트 타깃 주소에 사내 서버가 도달할 수 있어야 한다. 그런데 VPC는 기본적으로 인터넷이나 사내 네트워크와 분리되어 있어, 사내 서버는 마운트 타깃 IP로 패킷을 보낼 길이 없다. VPN이나 전용 회선을 직접 구성하지 않은 상태에서는 사내 서버는 EFS에 접근 자체가 불가능하고, 퍼블릭 인터넷 경유 마운트는 보안상 열 수 없는 구조가 한계다.

2질문 제기

사내 데이터센터 서버가 퍼블릭 인터넷을 거치지 않고 안전하게 EFS에 접근하려면 어떻게 해야 할까?

3구조적 핵심 예시

AWS Direct Connect로 사내 네트워크와 AWS VPC 사이에 전용 회선을 연결하거나, Site-to-Site VPN으로 인터넷 위에 암호화된 터널을 만든다. 그러면 사내 서버와 VPC가 같은 사설 네트워크처럼 이어지고, 사내 서버가 마운트 타깃의 사설 IP로 NFS 마운트를 할 수 있게 된다.

4단계별 동작 과정

  1. 연결 구성Direct Connect 또는 Site-to-Site VPN으로 온프레미스 네트워크와 EFS가 있는 VPC를 연결하고, VPC 라우팅 테이블에 사내 네트워크 대역으로 가는 경로를 추가한다.
  2. 마운트사내 서버에 NFS 클라이언트를 설치하고 EFS 파일 시스템의 DNS 이름 또는 마운트 타깃 IP를 지정해 마운트한다.
  3. 사용마운트된 사내 서버가 마치 자체 스토리지처럼 EFS 파일을 읽고 쓰며, 같은 파일 시스템을 쓰는 EC2 인스턴스와 파일을 공유한다.

5본질 요약

7스토리지 계층과 비용07-01

스토리지 클래스: Standard·IA·Archive

EFS가 파일 시스템에 저장된 데이터를 접근 빈도에 따라 Standard(자주 접근), IA(덜 자주 접근), Archive(거의 접근 안 함) 클래스로 나누어 관리하는 계층 구조

1상대의 출발점 확인

기존에는 파일 시스템 안의 모든 파일이 같은 방식으로 저장되고 같은 단가가 적용되었다. 매일 읽는 파일이든 몇 달째 손대지 않은 파일이든 동일하게 취급되므로, 사용하지 않는 데이터가 쌓일수록 저장 비용이 그대로 증가한다. 파일별 접근 빈도에 따라 요금을 다르게 매길 수단이 없어서, 비용을 줄이려면 데이터를 직접 정리해 삭제하거나 다른 스토리지로 옮기는 수밖에 없었다.

2질문 제기

자주 쓰는 파일과 거의 안 쓰는 파일의 저장 비용을 구분해 전체 비용을 낮추려면 어떻게 해야 할까?

3구조적 핵심 예시

EFS는 파일을 접근 빈도에 따라 세 가지 스토리지 클래스로 나눈다. Standard는 자주 접근하는 파일이 머무는 기본 클래스, IA(Infrequent Access)는 가끔 접근하는 파일용으로 저장 단가가 낮고 읽을 때 비용이 붙는 클래스, Archive는 거의 접근하지 않는 파일용으로 저장 단가가 가장 낮은 클래스다. 세 클래스가 같은 파일 시스템 안에서 파일별로 따로 적용된다.

4단계별 동작 과정

  1. 저장새 파일은 기본적으로 Standard 클래스에 저장되어 낮은 지연 시간으로 접근된다.
  2. 참조 기록EFS가 파일별로 마지막 접근 시각을 기록해 두고, 수명주기 정책이 정한 기간(예: IA는 30일, Archive는 90일) 동안 읽히지 않은 파일을 골라낸다.
  3. 이동골라낸 파일을 IA나 Archive 클래스로 옮겨 저장 단가가 낮은 계층에서 보관한다. 파일 경로는 그대로라 같은 위치에서 계속 접근할 수 있다.

2질문 제기

3구조적 핵심 예시

수명주기 정책은 "며칠 동안 읽히지 않은 파일을 어느 클래스로 옮길지"를 규칙으로 미리 정해 두는 설정이다. 예를 들어 30일 동안 읽히지 않으면 IA로, 90일 동안 읽히지 않으면 Archive로 이동하도록 지정해 두면, EFS가 그 기준에 맞는 파일을 자동으로 골라 계층을 옮긴다.

4단계별 동작 과정

  2. 판정EFS가 주기적으로 각 파일의 마지막 접근 시각을 확인해 설정된 기간을 넘긴 파일을 찾아낸다.
  3. 자동 이동판정된 파일을 지정한 클래스로 옮긴다. 파일 경로와 권한은 그대로 유지되어 사용자는 계층 이동을 의식하지 않는다.

3구조적 핵심 예시

AWS CloudTrail이 Amazon EFS API 호출(파일 시스템 생성·삭제, 마운트 대상 변경 등)을 기록해 감사와 보안 분석에 활용하는 방법.

2질문 제기

파일 시스템에 대한 모든 API 호출을 누가, 언제, 어떻게 했는지 기록으로 남기려면 어떻게 해야 할까?

3구조적 핵심 예시

운영자가 CreateFileSystem API를 호출해 파일 시스템을 만들면, 이 호출이 AWS CloudTrail에 이벤트로 기록된다. 이벤트에는 호출한 사용자의 계정, 소스 IP, 요청 파라미터, 응답 결과가 담기고, CloudTrail 콘솔이나 API로 언제든 조회할 수 있다.

4단계별 동작 과정

  1. API 호출 발생콘솔, SDK, CLI 등 어떤 경로든 EFS에 대한 API 호출이 발생한다.
  2. 이벤트 기록CloudTrail이 호출을 감지해 누가 언제 어떤 파라미터로 호출했는지를 이벤트 형태로 기록한다.
  3. 기록 조회와 감사CloudTrail 콘솔에서 이벤트 히스토리를 조회해 변경 원인을 추적하고 감사 증적으로 활용한다.

9단계 백업과 복제

AWS Backup 서비스를 사용해 EFS 파일 시스템의 백업을 만들고 복원하는 방법을 다루는 항목

1상대의 출발점 확인

기존에는 파일 시스템의 데이터를 보호하려면 백업 스크립트를 직접 만들어 실행하거나 수동으로 파일을 복사해야 했다. 백업을 빠뜨리거나 실행 시점이 어긋나면 최근 데이터를 잃을 수 있었고, 백업본을 오래 보관하거나 다른 리전에 보관하는 것도 쉽지 않았다. 백업이 제대로 됐는지 검증할 방법도 마땅치 않았다.

2질문 제기

파일 시스템의 데이터를 일정에 따라 자동으로 백업하고, 필요한 시점에 복원할 수 있게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

AWS Backup에서 백업 계획을 하나 만들고 EFS 파일 시스템을 리소스로 지정하면, 계획에 정의한 일정에 따라 백업이 자동 실행되어 복원 지점(backup)이 생성된다. 데이터가 손실됐을 때는 이 복원 지점을 선택해 파일 시스템을 원래 시점의 상태로 되살린다.

4단계별 동작 과정

  1. 백업 계획 생성AWS Backup에서 백업 빈도와 보존 기간이 담긴 계획을 만들고 EFS 파일 시스템을 대상 리소스로 지정한다.
  2. 백업 실행과 보관계획에 따라 백업이 자동으로 실행되어 복원 지점이 생성되고 설정한 기간 동안 유지된다.
  3. 복원 수행장애나 실수로 데이터가 손상되면 원하는 복원 지점을 선택해 파일 시스템을 그 시점의 상태로 복원한다.

5본질 요약

AWS Backup이 파일 시스템을 정책 기반으로 자동 백업하고 보관하며, 필요할 때 특정 시점으로 복원할 수 있게 하는 것

9단계 백업과 복제

AWS Backup 정책으로 파일 시스템의 자동 백업을 예약하고 관리하는 방법을 다루는 항목

1상대의 출발점 확인

백업을 만들 수 있게 된 뒤에도 시작 시각, 보존 기간, 백업본을 보낼 리전, 백업 대상 태그를 하나하나 수동으로 관리해야 했다. 일정이 바뀔 때마다 스크립트나 설정을 고쳐야 했고, 백업본이 얼마나 오래 남아 있는지, 다른 리전으로 복사됐는지는 콘솔을 열어 확인하기 전에는 알 수 없었다.

2질문 제기

백업의 실행 일정과 보존 기간, 리전 복사를 사람 개입 없이 자동으로 관리하려면 어떻게 해야 할까?

3구조적 핵심 예시

매일 03시에 백업을 실행하고 35일간 보관하며 백업본을 서울 리전으로 복사하라는 내용을 백업 계획 하나로 정의한다. 이후에는 계획이 알아서 백업을 실행하고, 기간이 지난 복원 지점은 삭제하며, 지정된 리전으로 복사본을 보낸다. 특정 태그가 붙은 파일 시스템만 골라 백업할 수도 있다.

4단계별 동작 과정

  1. 계획 설정AWS Backup에서 백업 시작 시각, 빈도, 보존 기간, 복사 대상 리전을 백업 계획에 정의한다.
  2. 자동 실행과 보존 관리계획이 정해진 시각에 백업을 실행하고 복원 지점을 보존 기간 동안 유지하되, 기간이 지나면 자동 삭제한다.
  3. 리전 복사와 상태 확인백업본이 지정된 리전으로 자동 복사되고, 백업 성공·실패 상태를 콘솔에서 확인한다.

5본질 요약

백업 계획 하나로 실행 일정, 보존 기간, 리전 복사를 자동으로 관리해 백업 운영에서 사람의 개입을 없애는 것

새 파일 시스템이나 기존 파일 시스템을 대상으로 EFS 복제 구성을 만드는 방법을 다루는 항목

1상대의 출발점 확인

기존에는 다른 리전의 장애나 데이터센터 사고에 대비하려면 데이터를 직접 다른 리전으로 복사해야 했다. 복사 중간에 파일이 바뀌면 복사본이 어긋났고, 주기적으로 다시 복사하는 동안의 변경분은 유실될 수 있었다. 재해가 났을 때 즉시 쓸 수 있는 최신 복제본이 준비되어 있지 않아 복구 시간이 길어졌다.

2질문 제기

파일 시스템의 변경 내용을 다른 리전으로 자동 복제해 최신 복제본을 유지하려면 어떻게 해야 할까?

3구조적 핵심 예시

원본 파일 시스템에 대해 복제 구성을 만들면 대상 리전에 대상 파일 시스템이 자동으로 생성되고, 원본에 생기는 모든 변경이 비동기 방식으로 대상에 전파된다. 원본 리전 전체가 사용 불가가 되어도 대상 파일 시스템을 마운트해 즉시 서비스를 이어갈 수 있다.

4단계별 동작 과정

  1. 복제 구성 생성원본 파일 시스템에서 대상 리전을 지정해 복제 구성을 만든다. 이때 대상 파일 시스템의 설정을 새로 만들거나 기존 파일 시스템을 선택할 수 있다.
  2. 변경 내용 전파원본에 파일이 추가·수정·삭제될 때마다 그 변경분이 대상 파일 시스템에 비동기로 복제되어 최신 상태가 유지된다.
  3. 장애 시 복제본 사용원본 리전에 장애가 발생하면 대상 리전의 복제 파일 시스템을 마운트하여 데이터 손실 없이 운영을 재개한다.

5본질 요약

파일 시스템의 변경분을 다른 리전으로 자동 복제해 항상 최신 복제본을 유지함으로써 재해 복구를 가능하게 하는 것

계정 간 복제·복제 관리·장애 조치

다른 AWS 계정으로의 복제와 복제 상태 확인·삭제, 복제본으로의 장애 조치를 다루는 항목

1상대의 출발점 확인

EFS 복제는 원본 파일 시스템의 데이터를 다른 파일 시스템으로 연속해서 비동기로 복사해 두는 기능이다. 처음에는 같은 AWS 계정 안에서만 구성할 수 있었기 때문에, 회사 A의 파일 시스템을 회사 B의 계정으로 복제하고 싶으면 복제본을 직접 옮기거나 별도로 백업을 export 하는 수동 절차가 필요했다. 계정이 달라지면 원본과 복제본을 관리하는 주체가 달라지므로, 누가 복제 구성을 만들고 누가 복제본을 사용할 수 있는지에 대한 권한 정리도 없이 단순히 복제 기능만으로는 해결되지 않았다.

2질문 제기

다른 AWS 계정이 소유한 파일 시스템을 복제 대상으로 지정해서, 원본 계정이 복제를 관리하고 상대 계정이 복제본을 사용하게 할 수 없을까?

3구조적 핵심 예시

운영 계정 A가 원본 파일 시스템을, 개발 계정 B가 복제 대상 파일 시스템을 각자 소유하고 있다고 가정한다. 계정 A는 자신의 원본 파일 시스템에 대해 복제 구성을 만들 때 대상으로 계정 B의 파일 시스템을 지정한다. 계정 B는 자기 계정에 있는 그 대상 파일 시스템을 마운트해서 읽기 전용 복제본으로 사용한다. 이 구성이 완료되면 원본에 쓴 데이터가 계정 경계를 넘어 복제본에 연속해서 반영되고, 계정 A가 복제 구성을 삭제하기 전까지 계정 B는 이 파일 시스템을 원본으로 계속 자동 동기화된 상태로 두게 된다.

4단계별 동작 과정

  1. 복제 대상 준비대상 계정 B에 이미 존재하는 파일 시스템을 대상으로 정한다. 대상 파일 시스템은 다른 복제의 대상이거나 원본이면 안 되고, 복제 구성이 적용되면 기존에 그 파일 시스템에 있던 데이터는 보존된다.
  2. 복제 구성 생성과 상태 확인원본 계정 A가 복제 구성을 만들면 복제가 시작된다. 이후 복제 상태(원본과 대상의 동기화 진행도, 데이터 크기, 상태)를 복제 세부 정보에서 확인하고, 구성이 잘못되면 복제 구성을 삭제해 복제를 중단할 수 있다.
  3. 장애 조치복제본 승격** — 원본 계정 A에 재해가 생겨 원본을 쓸 수 없게 되면, 대상 계정 B에서 복제 구성을 삭제한다. 그러면 대상 파일 시스템이 독립된 쓰기 가능한 파일 시스템으로 바뀌어 그 자체를 서비스 파일 시스템으로 승격해 사용할 수 있다.

5본질 요약

복제 구성의 생성·상태 확인·삭제를 원본 계정이 관리하고, 복제 구성을 삭제하는 순간 대상 파일 시스템이 독립된 쓰기 가능한 파일 시스템으로 승격되는 방식으로 계정 간 장애 조치를 제공하는 것

10보안: 암호화와 접근 제어10-01

데이터 암호화: 저장·전송·KMS

EFS는 저장 데이터(파일 시스템 생성 시 KMS 키로)와 전송 데이터(TLS)를 모두 암호화하며, KMS 키로 암호화를 관장한다.

1상대의 출발점 확인

암호화 설정이 없는 파일 시스템은 데이터가 디스크에 평문 그대로 저장되고, 클라이언트와 파일 시스템 사이를 오가는 NFS 트래픽도 그대로 노출된다. 이 상태에서는 하드웨어가 도난당하거나 네트워크가 감청되면 파일 내용이 그대로 유출될 수 있다. 보안 요구사항이 있는 데이터를 다루는 조직은 이런 평문 저장과 평문 전송을 허용할 수 없어서, 스토리지를 선택할 때 암호화 지원을 필수 조건으로 본다.

2질문 제기

저장된 데이터와 전송 중인 데이터를 모두 암호화해서, 어떤 경로로든 데이터가 노출되어도 내용을 보호할 수 없을까?

3구조적 핵심 예시

파일 시스템을 만들 때 암호화를 활성화하고 KMS 키(암호화 키를 생성·관리하는 AWS 서비스)를 지정한다. 이 키로 디스크에 저장되는 모든 데이터가 암호화된다. 그다음 EC2 인스턴스에서 마운트할 때 TLS(전송 계층을 암호화하는 프로토콜) 옵션을 켜서 마운트하면, 클라이언트와 파일 시스템 사이의 모든 NFS 트래픽이 암호화된 터널을 통해 흐른다. 저장 암호화와 전송 암호화를 둘 다 켠 이 구성 하나로 파일 시스템의 모든 데이터 경로가 보호된다.

4단계별 동작 과정

  1. 저장 암호화 설정파일 시스템 생성 시 암호화를 활성화하고 KMS 키를 고른다. 기본으로 AWS 관리 키(aws/elasticfilesystem)가 쓰이고, 원하면 고객 관리 키(자신이 만들고 수명 주기를 통제하는 키)를 지정한다. 이 선택은 생성 후 바꿀 수 없으며, 이후 쓰이는 모든 데이터가 이 키로 암호화된다.
  2. 전송 암호화 설정마운트 명령에 tls 옵션을 넣는다. 마운트 헬퍼는 stunnel(암호화 터널을 만들어 주는 도구)을 이용해 클라이언트와 파일 시스템 사이의 NFS 연결을 TLS로 감싼다.
  3. KMS 키로 관리와 감사KMS 키가 데이터 암호화·복호화의 실질적인 주체가 된다. 키 사용 로그는 CloudTrail(API 호출 기록 서비스)에 남아 누가 언제 키를 사용했는지 감사할 수 있다.

IAM: API 접근과 정책·역할

IAM 정책·역할로 EFS 관리 API와 파일 시스템 자원에 대한 접근을 계정·사용자·조건 단위로 통제한다.

1상대의 출발점 확인

EFS 파일 시스템을 만들고 지우고 설정을 바꾸는 것은 모두 API 호출(예: CreateFileSystem, DeleteFileSystem)을 통해 일어난다. 이 관리 API에 아무나 접근할 수 있다면 계정 안의 누구든 파일 시스템을 삭제하거나 권한 설정을 바꿔버릴 수 있다. 그래서 누가 어떤 관리 작업을 할 수 있는지 정해 주는 접근 제어가 필요한데, 각 자원을 어떻게 보호할지에 대한 정책 설계가 없으면 기본 허용 방침 때문에 불필요하게 넓은 권한이 생긴다.

2질문 제기

EFS의 관리 API와 파일 시스템 자원에 대해, 어떤 사용자·역할이 어떤 작업을 할 수 있는지를 어떻게 엄격하게 통제할까?

3구조적 핵심 예시

운영팀 역할에는 파일 시스템을 만들고 지우는 작업을 허용하는 IAM 정책(API 호출 허용·거부를 적어 둔 문서)을 연결하고, 개발팀 역할에는 읽기 전용 조회 작업만 허용하는 정책을 연결한다. 이렇게 IAM 사용자·역할에 정책을 붙여 관리 API 접근을 정한다. 여기에 더해 특정 파일 시스템에만 파일 시스템 정책(자원에 직접 붙이는 정책)을 만들어 "어떤 계정·역할이 이 자원에 접근할 수 있는가"를 한 번 더 제한할 수 있다. 예를 들어 특정 파일 시스템은 특정 역할만 관리할 수 있게 자원 단위로 잠글 수 있다.

4단계별 동작 과정

  1. 자격 증명 기반 정책IAM 사용자·그룹·역할에 정책을 연결해 EFS API 액션(생성·조회·삭제 등)에 대한 허용·거부를 결정한다. 조건을 넣어 특정 파일 시스템이나 특정 태그가 붙은 자원만 허용하게도 한다.
  2. 자원 기반 정책파일 시스템 정책을 해당 파일 시스템에 붙여, 그 자원에 대해 어떤 보안 주체(계정·역할·사용자)가 어떤 작업을 할 수 있는지를 한 번 더 통제한다. 두 정책이 모두 허용해야 접근이 성립되는 식으로 이중 제한을 건다.
  3. 서비스 연결 역할 사용EFS가 백업·복제 등에서 다른 AWS 서비스의 자원을 대신 관리해야 할 때, AWS가 미리 정의한 서비스 연결 역할(AWSServiceRoleForAmazonElasticFileSystem)을 통해 필요한 권한만 자동으로 부여받게 한다.

파일 시스템 데이터 접근 제어(IAM for NFS)

IAM 인가(NFS 클라이언트)를 통해 IAM 정책으로 파일 시스템 데이터 읽기·쓰기 접근을 통제한다.

1상대의 출발점 확인

일반적인 NFS 마운트는 네트워크 접근(보안 그룹이 포트 2049를 열어 주는 것)만 통과하면 파일 시스템 데이터에 접근할 수 있었다. 클라이언트가 누구인지, 어떤 IAM 자격 증명을 가졌는지는 전혀 확인하지 않는다. 그래서 네트워크에 들어올 수 있는 모든 호스트가 같은 권한으로 파일을 읽고 쓸 수 있었고, 사용자 개개인에게 다른 접근 권한을 주는 것은 NFS 수준의 권한 검사에만 맡겨져 있었다. 클라이언트를 신뢰하는 이런 구조는 호스트 하나가 뚫리면 그 안의 모든 사용자가 파일 시스템에 접근할 수 있게 되는 문제가 있다.

2질문 제기

NFS 클라이언트의 요청이 실제로 어떤 IAM 자격 증명으로 왔는지 확인해서, 파일 데이터 자체에도 IAM 정책을 적용할 수 없을까?

3구조적 핵심 예시

EC2 인스턴스를 IAM 역할과 함께 시작하고, 마운트 명령에 iam 옵션을 넣어 마운트한다. 파일 시스템 데이터에 접근하려면 이 인스턴스의 IAM 역할이 elasticfilesystem:ClientWrite(파일 쓰기), elasticfilesystem:ClientMount(마운트) 같은 액션을 허용하는 정책을 가져야 한다. 허용하는 정책이 없는 인스턴스는 네트워크로는 연결할 수 있어도 데이터 작업 자체가 거부된다. 이렇게 되면 파일 시스템에 접근하는 주체가 IAM으로 식별되고, 정책 하나로 읽기·쓰기·루트 접근을 개별 통제할 수 있다.

4단계별 동작 과정

  1. IAM 인증 마운트마운트 헬퍼로 iam 옵션을 넣어 마운트한다. 클라이언트는 이후 보내는 모든 NFS 요청에 자신의 IAM 자격 증명을 이용한 서명(요청이 위조되지 않았음을 증명하는 값)을 붙인다.
  2. 신원 확인과 정책 대조EFS가 요청의 서명을 풀어 클라이언트의 IAM 신원을 확인하고, 그 신원에 연결된 IAM 정책과 파일 시스템 정책을 대조한다. 이때 액션은 ClientMount, ClientWrite, ClientRootAccess(루트 권한으로 접근)로 나뉜다.
  3. 허용·거부 결정요청한 액션(마운트·읽기·쓰기·루트 접근)이 정책에서 허용되면 데이터 작업이 진행되고, 허용되지 않으면 그 요청만 거부된다.

5본질 요약

NFS 수준 사용자·그룹·권한

POSIX 사용자·그룹 ID와 파일·디렉터리 권한(소유자·그룹·기타)이 NFS 마운트를 통한 데이터 접근을 결정한다.

1상대의 출발점 확인

NFS로 공유되는 파일 시스템은 자체적인 사용자 계정 데이터베이스를 갖지 않는다. 대신 NFS 클라이언트가 자기가 아는 사용자 ID(UID)와 그룹 ID(GID)를 요청에 실어 보내고, 파일 시스템은 그 숫자를 그대로 믿고 파일의 소유자·그룹·기타 권한 비트와 비교해 접근을 허용한다. 이 방식은 클라이언트가 보낸 신원을 검증하지 않으므로, 신원을 위조하거나 클라이언트별로 같은 UID를 다른 사람이 쓰는 경우 권한 검사가 틀어질 수 있다. 또한 사용자 목록을 중앙에서 관리하지 않기 때문에 여러 클라이언트 사이에서 "이 UID가 누구인가"가 일관되지 않는다.

2질문 제기

사용자 계정 서버 없이도, 클라이언트가 보낸 UID·GID와 파일의 POSIX 권한 정보만으로 데이터 접근을 결정할 수 있을까?

3구조적 핵심 예시

EC2 인스턴스의 사용자 A가 UID 1000을 갖고 있다고 가정한다. 이 사용자가 파일 하나를 만들면 그 파일의 소유자 UID로 1000이 기록되고, 권한 비트(소유자·그룹·기타 각각에 대한 읽기·쓰기·실행 허용)가 함께 저장된다. 나중에 다른 클라이언트에서 UID 1000으로 이 파일에 접근하면 파일 시스템은 그 숫자를 그 파일의 소유자와 비교해 소유자 권한을 적용한다. 즉 접근 결정은 클라이언트가 보낸 UID·GID와 파일에 저장된 소유자·그룹·권한 비트의 대조로만 이루어진다.

4단계별 동작 과정

  1. POSIX 메타데이터 저장파일 시스템이 모든 파일에 소유자 UID, 소유 그룹 GID, 권한 비트(읽기·쓰기·실행)를 저장한다.
  2. 클라이언트 신원 전달NFS 클라이언트가 파일 작업을 요청할 때 요청 안에 접근하는 사용자의 UID와 GID를 실어 보낸다.
  3. 권한 비교로 접근 결정파일 시스템이 요청의 UID·GID를 그 파일의 소유자·그룹·기타 권한 비트와 비교해 읽기·쓰기·실행을 허용하거나 거부한다.

5본질 요약

클라이언트가 보낸 POSIX UID·GID와 파일에 저장된 권한 비트의 대조만으로 데이터 접근을 결정해, 별도의 중앙 사용자 서버 없이도 NFS 수준의 사용자·그룹·권한 제어를 제공하는 것

액세스 포인트: 사용자·루트 디렉터리 강제

액세스 포인트가 각 애플리케이션·사용자에 OS 사용자 ID와 루트 디렉터리를 강제해 세분화된 공유 접근을 제공한다.

1상대의 출발점 확인

파일 시스템을 여러 애플리케이션이나 여러 사용자 집단이 함께 쓸 때, 보통 루트 디렉터리부터 전체 트리를 마운트하고 클라이언트 쪽에서 자기 사용자와 디렉터리를 알아서 정하도록 둔다. 그러면 각 애플리케이션이 파일 시스템 전체를 볼 수 있고, 접근하는 사용자의 신원도 클라이언트가 보낸 값 그대로라서 "이 애플리케이션은 이 사용자로 이 디렉터리까지만 보게 하자" 같은 세밀한 분리는 마운트 설정만으로는 어렵다. 잘못 구성하면 한 애플리케이션이 다른 애플리케이션의 데이터를 보거나, 의도한 사용자보다 넓은 권한으로 접근하게 된다.

2질문 제기

마운트할 때마다 사용자 신원과 시작 디렉터리를 강제해서, 애플리케이션마다 자기 몫의 영역만 자기 신원으로 보게 할 수 없을까?

3구조적 핵심 예시

한 파일 시스템에 두 애플리케이션을 올린다고 가정한다. 애플리케이션 1용 액세스 포인트는 루트 디렉터리를 /data/app1으로, OS 사용자 ID를 UID 1000으로 정해 둔다. 애플리케이션 1이 이 액세스 포인트로 마운트하면, 클라이언트가 어떤 사용자로 접근하든 모든 요청은 UID 1000으로 처리되고 시작점은 /data/app1로 고정된다. 그래서 이 애플리케이션은 /data/app1 아래만 볼 수 있고, 그 위의 다른 애플리케이션 데이터는 경로상 접근 자체가 차단된다.

4단계별 동작 과정

  1. 액세스 포인트 생성파일 시스템당 하나의 액세스 포인트를 만들 때, 강제할 루트 디렉터리(예: /data/app1)와 OS 사용자 ID·그룹 ID를 지정한다. 지정한 루트 디렉터리가 없으면 생성 여부를 함께 설정할 수 있다.
  2. 액세스 포인트로 마운트클라이언트가 마운트 명령에 accesspoint 옵션으로 해당 액세스 포인트 ID(fsap-xxxx)를 지정해 마운트한다.
  3. 신원·경로 강제 적용이후 이 마운트를 통한 모든 NFS 요청은 클라이언트가 보낸 값과 무관하게 액세스 포인트에 설정된 사용자 ID로 처리되고, 루트 디렉터리 위로는 올라갈 수 없게 경로가 강제된다.

공개 접근 차단

파일 시스템 정책과 공개 접근 차단 설정으로 의도치 않은 공개(인터넷) 접근을 원천 차단한다.

1상대의 출발점 확인

EFS 파일 시스템은 기본적으로 VPC 안에서 마운트 타깃을 통해 접근할 수 있다. 접근을 막으려면 보안 그룹, 파일 시스템 정책, IAM 인증 같은 보안 설정을 파일 시스템마다 빠짐없이 구성해야 한다. 그런데 이런 설정은 하나라도 빠지면 그 파일 시스템은 열린 상태가 되고, 퍼블릭 서브넷에 있는 EC2 인스턴스처럼 인터넷과 연결된 경로를 통해 누구나 파일을 읽거나 쓸 수 있게 된다. 보안 설정을 매번 수동으로 점검하는 방식은 실수 가능성이 크고, 파일 시스템이 많아질수록 놓친 항목을 찾아내기 어렵다.

2질문 제기

파일 시스템 하나하나의 설정에 의존하지 않고, 실수로 공개되는 상황 자체를 원천적으로 막을 수는 없을까?

3구조적 핵심 예시

계정 설정에서 공개 접근 차단을 켜면, 그 계정에 속한 모든 파일 시스템에 대해 인터넷이나 퍼블릭 경로를 통한 접근 시도가 물리적으로 거부된다. 개별 파일 시스템의 보안 설정이 어떻게 되어 있든, 공개 경로로 들어오는 요청은 아예 수용되지 않는다. 반면 VPC 내부에서 마운트 타깃으로 들어오는 정상적인 요청은 기존 설정대로 계속 허용된다.

4단계별 동작 과정

  1. 차단 활성화관리자가 콘솔이나 API에서 공개 접근 차단 옵션을 켜면 계정 수준의 차단 규칙이 적용된다.
  2. 접근 시도 평가파일 시스템에 대한 마운트나 데이터 요청이 들어오면 EFS가 그 요청이 공개 경로(퍼블릭 서브넷·인터넷 연결 경로)를 통하는지 판단한다.
  3. 허용·거부 결정공개 경로로 판단되면 요청을 거부하고, VPC 내부의 정상 경로로 판단되면 기존 접근 제어 규칙에 따라 처리한다.

규정 준수와 복원력

EFS는 규정 준수 인증 프로그램을 충족하고, 가용 영역 간 복제·백업 등으로 복원력을 확보한다.

1상대의 출발점 확인

EFS를 도입하기 전에는 규정 요구사항(GDPR, HIPAA, SOC 같은 인증·감사 기준)을 만족하는지 확인하려면 별도로 문의하거나 자료를 찾아봐야 했다. 또 스토리지를 단일 리전이나 단일 가용 영역에만 두면 그 지역에 장애가 생겼을 때 데이터 접근이 중단되는 위험이 있었다. 규정을 충족하는지, 장애를 어느 정도 견디는지가 서비스 도입 전에는 한눈에 확인되지 않아서, 설계 단계에서 규제 요구를 검증하거나 장애 대비 구조를 세우기 어려웠다.

2질문 제기

EFS가 어떤 규정 요구를 충족하고 어느 정도의 장애를 견디는지, 설계 시점에 확인할 수는 없을까?

3구조적 핵심 예시

AWS는 EFS에 대해 매년 독립 감사 기관의 인증(SOC, ISO, HIPAA 등)을 받아 갱신하고, 그 결과를 공식 문서로 공개한다. 동시에 Regional 파일 시스템은 데이터를 리전 안의 여러 가용 영역에 분산 저장하므로, 하나의 가용 영역에 장애가 나도 나머지 가용 영역의 사본으로 계속 서비스를 제공한다. 이 두 사실을 문서로 확인한 뒤 설계에 반영할 수 있다.

4단계별 동작 과정

  1. 규정 확인설계 전에 AWS 공식 준수 문서에서 EFS가 충족하는 인증·규정 목록과 대상 리전을 확인한다.
  2. 복원력 설계Regional 파일 시스템을 선택하면 데이터가 리전 내 여러 가용 영역에 분산 저장되어 단일 지점 장애를 피한다.
  3. 장애 대비 검증가용 영역 장애 시 다른 가용 영역의 사본으로 접근이 유지되는 구조가 문서로 확인되면, 이를 근거로 아키텍처에 반영한다.

쿼터와 파일 작업 오류

EFS가 계정·파일시스템별 할당량(쿼터) 한도에 도달하면 파일 작업이 실패하는데, 그 원인과 해결 방법을 설명하는 개념.

1상대의 출발점 확인

파일 시스템을 마운트해 쓰다 보면 파일이 생성되지 않거나 쓰기가 실패하는 경우가 생긴다. 기존 방식에서는 원인이 보이지 않아서 재시도만 반복하거나 "디스크가 꽉 찼다"고만 추측하기 쉽다. EFS는 사용자가 직접 볼 수 있는 고정 디스크 장치가 없는 관리형 스토리지라서, 용량 한도나 계정 한도에 도달했을 때 어디를 확인해야 하는지 알기 어렵다. 서비스에 한도(쿼터)가 존재한다는 사실을 모르는 채로는 실패 원인 자체를 찾지 못한다.

2질문 제기

EFS에서 한도에 걸려 파일 작업이 실패했을 때, 그 원인이 쿼터 때문인지 어떻게 알 수 있을까?

3구조적 핵심 예시

NFS 클라이언트에서 파일을 만들 때 "No space left on device" 오류가 나는 경우가 있다. EFS에는 실제 디스크가 없지만, 파일 시스템마다 적용되는 용량·자원 한도(쿼터)에 도달하면 이 오류가 발생한다. AWS 계정에는 리전별 파일 시스템 수 같은 서비스 한도도 존재하며, 이 한도들은 Service Quotas 콘솔에서 조회하고 조정 요청을 낼 수 있다.

4단계별 동작 과정

  1. 한도 확인Service Quotas 콘솔에서 리전별 파일 시스템 수, 파일 시스템당 용량 등 현재 쿼터 값과 사용량을 확인한다.
  2. 실패 원인 판별파일 작업 오류가 "No space left on device"처럼 쿼터 초과를 가리키는 메시지인지 확인하고, 쿼터 초과이면 쿼터 증가 요청을 제출한다.
  3. 한도 해소 후 재시도쿼터가 늘어나거나 불필요한 파일이 정리되어 공간이 확보되면, 실패했던 파일 작업을 다시 수행한다.

5본질 요약
