Amazon ECS 정의와 3계층 아키텍처

Amazon ECS는 Docker 컨테이너를 클러스터에서 실행·중지·관리하는 완전관리형 컨테이너 오케스트레이션 서비스로, 용량 공급(컴퓨트)·스케줄러(배치)·컨테이너 에이전트(실행)의 계층으로 동작한다.

#1문제 상황

기존에는 서버에 애플리케이션을 직접 설치해 실행했다. 서버가 죽거나 트래픽이 몰리면 관리자가 직접 서버를 늘리고 다시 배포해야 했고, 컨테이너를 여러 대에서 돌리려면 어느 서버에 무엇을 올릴지, 죽은 컨테이너를 누가 다시 살릴지 모두 사람이 정해야 했다. 컨테이너 수가 늘수록 이 수작업은 감당하기 어려워진다.

#2핵심 질문

컨테이너를 어디에 배치하고, 언제 늘리고 줄이며, 죽으면 어떻게 다시 살릴 것인가?

#3동작 예시

ECS에서 클러스터를 만들고 태스크 정의에 컨테이너 이미지와 CPU·메모리를 적어 서비스로 실행하면, ECS가 컨테이너를 실행할 컴퓨팅 용량을 확보하고 그 위에 컨테이너를 배치한다. 사용자는 서버 한 대를 직접 고르지 않고 이 애플리케이션을 몇 개 유지하라는 값만 정한다.

#4동작 과정

  1. Capacity(용량)컨테이너가 실제로 도는 인프라를 준비한다. Fargate, EC2 인스턴스, Managed Instances 등이 여기에 해당한다.
  2. Controller(컨트롤러)배포와 관리를 담당한다. ECS 스케줄러가 어느 용량에 컨테이너를 놓을지 결정하고 상태를 관리한다.
  3. Provisioning(프로비저닝)클러스터와 서비스 같은 리소스를 만들고 설정한다. 이 계층에서 확보한 용량 위에 컨테이너가 실행된다.

#5한 줄 요약

컴퓨트 용량, 배치 결정, 리소스 프로비저닝을 계층으로 나눠 컨테이너 실행과 관리를 AWS가 대신 맡는 완전관리형 오케스트레이션

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 템플릿 작성만들 리소스를 YAML 또는 JSON으로 선언한다. 템플릿은 만들 리소스의 청사진 역할을 한다.
  2. 스택 생성·업데이트템플릿을 제출하면 스택이 만들어지고 리소스가 생성된다. 변경 시에는 change set으로 영향 범위를 먼저 확인한다.
  3. 도구 선택콘솔, AWS CLI, SDK, CloudFormation, CDK, Copilot CLI 등으로 같은 리소스를 프로비저닝한다. 실행 환경에 맞는 도구를 고른다.

런치 타입과 용량 공급자 비교

Amazon ECS가 컨테이너를 실행할 컴퓨팅 용량을 확보하는 여러 방식(Fargate·Managed Instances·EC2·외부 인스턴스 등)을 런치 타입과 용량 공급자(capacity provider) 관점에서 비교한 개요.

#1문제 상황

ECS에서 컨테이너를 돌리려면 컴퓨팅 용량을 어떻게 확보할지 정해야 한다. 런치 타입으로만 지정하면 인스턴스 선택과 확장을 세밀하게 조정하기 어렵고, 용량이 부족하거나 남을 때 유연하게 대응하기 힘들다. 두 방식의 차이를 모르면 비용과 성능을 함께 최적화하기 어렵다.

#2핵심 질문

워크로드에 맞는 컴퓨팅 용량을 어떤 방식으로 지정하고 관리할 것인가?

#1문제 상황

컨테이너를 자원 제한 없이 실행하면 호스트에 있는 CPU와 메모리를 여러 컨테이너가 나눠 쓰게 된다. 한 컨테이너가 자원을 많이 잡아먹으면 옆 컨테이너가 밀려나지만, 어느 컨테이너에 얼마를 보장할지 정할 기준이 없다. Amazon ECS에서도 태스크별로 자원을 명시하지 않으면 배치가 되지 않거나 자원 부족으로 갑자기 종료될 수 있다.

#2핵심 질문

태스크 하나에 CPU와 메모리를 어떤 단위로 얼마씩 정해야 안전하게 배치하고 확장할 수 있을까?

#3동작 예시

CPU는 1024 단위가 1 vCPU이고, 메모리는 MiB로 잰다. 태스크에 cpu 1024와 memory 2048을 지정하면 1 vCPU와 2048 MiB를 요구하는 태스크가 된다. Fargate에서는 이 값을 임의로 정하지 못하고 미리 정해진 크기 조합 중에서 골라야 한다.

#4동작 과정

  1. 단위 이해CPU는 1/1024 vCPU 단위로, 메모리는 MiB로 측정한다는 것을 먼저 정한다.
  2. 예약과 한도 설정예약(reservation)은 태스크가 최소한 받을 자원이고, 한도(limit)는 최대로 쓸 수 있는 양이다. 예약을 넘겨 쓰는 것은 버스팅이며 한도를 넘는 CPU 사용은 스로틀링된다.
  3. 플랫폼별 조합 선택Fargate는 정해진 크기 조합에서 고르고, EC2는 인스턴스에 남은 자원에 맞춰 배치되는지 확인한다.

#1문제 상황

애플리케이션은 데이터베이스 자격 증명이나 API 키 같은 비밀 값을 필요로 한다. 이를 이미지나 태스크 정의에 평문으로 넣으면 코드 저장소와 콘솔에 그대로 노출된다. 값이 바뀔 때마다 이미지를 다시 빌드해야 하는 문제도 생긴다.

#2핵심 질문

비밀 값을 노출하지 않고 컨테이너가 실행되는 시점에 안전하게 전달하려면 어떻게 해야 할까?

#3동작 예시

컨테이너 정의의 secrets 항목에 Secrets Manager나 Systems Manager Parameter Store의 식별자를 적으면, ECS가 태스크 시작 시 값을 가져와 환경 변수로 컨테이너에 넣는다. 이미지와 태스크 정의에는 실제 값이 아니라 식별자만 남는다.

#4동작 과정

  1. 비밀 저장값을 AWS Secrets Manager나 Systems Manager Parameter Store에 두고 접근 권한을 IAM으로 제한한다.
  2. 참조 지정컨테이너 정의의 secrets나 environmentFiles에 시크릿 이름·버전과 JSON 키를 적는다. 로그 플랫폼 인증이 필요하면 secretOptions를 쓴다.
  3. 런타임 주입태스크 시작 시 값을 가져와 환경 변수나 파일로 컨테이너에 전달한다.

#2핵심 질문

#3동작 예시

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 플랫폼 확인Fargate, EC2, Managed Instances, Windows 중 어디서 돌릴지 먼저 정한다.

  3. 실행 설정runtimePlatform(운영체제·아키텍처)과 launch type을 지정해 정의가 해당 플랫폼에서 유효하도록 맞춘다.

특수 워크로드 태스크 정의

GPU·비디오 트랜스코딩·머신러닝·64비트 ARM 등 특수 목적 워크로드를 위한 태스크 정의 방식이다.

#1문제 상황

일반적인 웹 애플리케이션은 CPU만으로 충분하지만, 머신러닝 추론이나 비디오 트랜스코딩 같은 작업은 GPU나 특수 가속기가 필요합니다. 이런 워크로드는 표준 태스크 정의로는 실행할 수 없고, EC2에서는 그 목적에 맞게 설계된 인스턴스를 골라야 합니다. 즉 워크로드마다 태스크 정의에 넣어야 할 파라미터가 달라지고, 어떤 인스턴스를 써야 하는지도 달라지는 문제가 있습니다.

#2핵심 질문

GPU·비디오 트랜스코딩·머신러닝·64비트 ARM처럼 특수한 워크로드를 ECS에서 실행하려면 태스크 정의와 인스턴스를 어떻게 맞춰야 하는가?

#3동작 예시

GPU가 필요한 컨테이너를 EC2에서 실행한다면, 태스크 정의에 GPU를 요구한다고 지정하고 GPU가 장착된 인스턴스를 클러스터에 등록합니다. 그러면 ECS는 그 인스턴스에만 태스크를 배치하고, 컨테이너는 GPU 장치를 직접 사용할 수 있습니다.

#4동작 과정

  1. 워크로드 유형 파악실행하려는 작업이 GPU, 비디오 트랜스코딩, AWS Neuron 머신러닝, 딥러닝, 64비트 ARM 중 무엇에 해당하는지 정합니다. 유형마다 필요한 태스크 정의 파라미터가 다릅니다.
  2. 태스크 정의에 특수 자원 명시해당 워크로드에 맞는 파라미터를 태스크 정의에 설정합니다. 예를 들어 GPU 워크로드는 GPU를 요구하도록 지정합니다.
  3. 맞는 인스턴스 선택과 배치EC2를 쓴다면 그 워크로드를 위해 설계된 인스턴스를 골라 클러스터에 등록하고, ECS가 요구사항을 만족하는 인스턴스에 태스크를 배치합니다.

#5한 줄 요약

워크로드별로 필요한 태스크 정의 파라미터와 인스턴스를 지정해, GPU·머신러닝·ARM 같은 특수 컴퓨팅 자원에서 컨테이너를 제대로 실행시키는 것

#4동작 과정

  3. 전략 적용과 조회클러스터 기본 용량 공급자 전략으로 태스크 배치 순서가 결정되고, 공급자와 전략을 조회·설명해 현재 구성을 확인합니다.

Managed Instances 용량 공급자 관리

Amazon ECS Managed Instances 용량 공급자는 AWS가 관리하는 EC2 기반 컴퓨팅으로, 인스턴스 요구사항과 스케일링 전략을 지정하면 ECS가 인스턴스 프로비저닝과 수명주기를 대신 처리한다.

→ 04-02 참조

#1문제 상황

Fargate는 서버리스라 관리가 편하지만 가속 컴퓨팅, 특정 CPU 명령어 집합, 높은 네트워크 성능, 큰 메모리 구성처럼 표준 Fargate 옵션에 없는 요구는 채울 수 없습니다. 반대로 EC2를 직접 쓰면 원하는 인스턴스를 고를 수 있지만 패치·스케일링·유지보수를 사용자가 떠안아야 합니다. 이 둘 사이에서 관리 부담은 낮추면서 EC2의 폭넓은 선택지를 함께 쓰고 싶은 요구가 생깁니다.

#2핵심 질문

Fargate의 운영 편의성과 EC2의 유연성을 동시에 얻으려면 컴퓨팅 용량을 어떻게 관리해야 하는가?

#3동작 예시

표준 Fargate로는 감당 못 하는 고성능 요구가 있는 애플리케이션에 Managed Instances 용량 공급자를 쓰면, 인스턴스 요구사항과 스케일링 전략만 지정하면 됩니다. AWS가 소프트웨어·OS 패치, 인스턴스 스케일링, 유지보수를 처리하고, 사용자는 애플리케이션에 집중합니다.

#4동작 과정

  1. 클러스터 준비Managed Instances 클러스터를 만들고, 필요하면 클러스터 설정을 업데이트합니다.
  2. 공급자 생성인스턴스 요구사항과 스케일링 전략을 담은 공급자를 만듭니다. ECS가 이 요구사항에 맞춰 시작 템플릿(인스턴스 실행 방법을 정의한 설정)을 만들어 인스턴스를 띄웁니다.
  3. 공급자 갱신과 삭제모니터링 설정을 바꾸려면 공급자를 업데이트합니다. 이때 기존 공급자를 제자리에서 고치기보다 불변 접근(새 구성으로 교체)을 따르는 것이 모범 사례이며, 불필요해지면 공급자를 삭제합니다.

#5한 줄 요약

인스턴스 요구사항과 스케일링 전략만 지정하면 AWS가 EC2 기반 컴퓨팅의 프로비저닝과 수명주기를 대신 관리하게 하는 것

클러스터 자동 스케일링과 종료 보호

클러스터 자동 스케일링은 Auto Scaling 그룹 용량 공급자를 통해 클러스터의 EC2 인스턴스 수를 태스크 수요에 맞춰 자동 조정하고, 관리형 종료 보호로 태스크가 있는 인스턴스의 종료를 막는다.

#1문제 상황

Auto Scaling 그룹 용량 공급자로 EC2 인스턴스를 쓰는 클러스터는 태스크 수요가 늘고 줄 때 인스턴스 수도 함께 맞춰야 합니다. 사용자가 인스턴스 수를 직접 정하면 수요 급증에 늦게 대응하거나, 반대로 놀리는 자원이 생겨 비용이 낭비됩니다. 또 인스턴스를 줄이는 과정에서 아직 태스크가 도는 인스턴스를 껐다가 실행 중인 작업이 끊기는 문제도 생깁니다.

#2핵심 질문

태스크 수요에 맞춰 EC2 인스턴스 수를 자동 조정하면서, 실행 중인 태스크가 있는 인스턴스는 어떻게 안전하게 지킬 수 있는가?

#3동작 예시

태스크가 갑자기 늘어 인스턴스 자원 사용률이 목표치를 넘으면 ECS가 인스턴스를 늘리고, 수요가 줄어 사용률이 낮아지면 줄입니다. 줄일 때는 태스크가 남아 있는 인스턴스를 건드리지 않도록 막아 실행 중인 작업이 끊기지 않습니다.

#4동작 과정

  1. 관리형 스케일링 켜기Auto Scaling 그룹 용량 공급자를 만들 때 관리형 스케일링을 켜고, 인스턴스 사용률 목표치(targetCapacity)를 정합니다.
  2. 지표와 정책 자동 생성ECS가 낮은 값·높은 값 CloudWatch 경보와 대상 추적 스케일링 정책을 만들어 Auto Scaling 그룹에 붙입니다. 정책을 바꾸려면 정책을 직접 고치지 말고 공급자의 관리형 스케일링 설정을 수정합니다.
  3. 종료 보호와 드레이닝관리형 종료 보호로 태스크가 있는 인스턴스의 종료를 막고, 인스턴스를 줄일 때는 드레이닝(태스크를 안전하게 빼내는 과정)을 거쳐 작업 중단을 피합니다.

#5한 줄 요약

태스크 자원 사용률을 기준으로 EC2 인스턴스 수를 자동 조정하되 종료 보호와 드레이닝으로 실행 중인 태스크를 지키는 것

EC2 컨테이너 인스턴스와 AMI

EC2 컨테이너 인스턴스는 ECS 컨테이너 에이전트가 설치되어 클러스터에 등록된 EC2 인스턴스이며, ECS 최적화 AMI는 컨테이너 실행에 필요한 에이전트와 Docker가 미리 구성된 이미지다.

→ 04-07 참조

#1문제 상황

EC2에서 컨테이너를 돌리려면 인스턴스에 컨테이너 에이전트와 컨테이너 런타임이 설치돼 있어야 하고, 클러스터에 등록돼 있어야 합니다. 이 환경을 사용자가 처음부터 직접 만들면 설정이 복잡하고 빠뜨리기 쉽습니다. 또 Linux·Windows, Bottlerocket 등 어떤 OS를 쓰느냐에 따라 준비 방법이 달라져 진입 장벽이 높아집니다.

#2핵심 질문

컨테이너를 실행할 EC2 인스턴스를 어떤 이미지로, 어떻게 준비해 클러스터에 등록해야 하는가?

#3동작 예시

콘솔로 클러스터를 만들면 ECS가 고른 운영체제의 최신 AMI를 담은 시작 템플릿을 자동으로 만듭니다. 이 AMI에는 컨테이너 에이전트와 Docker가 미리 구성돼 있어, 인스턴스가 뜨자마자 클러스터에 등록되고 태스크를 받을 수 있습니다.

#4동작 과정

  1. AMI 선택ECS 최적화 AMI를 씁니다. AWS가 미리 구성하고 테스트한 이미지로, 시작이 가장 간단합니다. Linux·Bottlerocket·Windows 등 목적에 맞는 것을 고릅니다.
  2. 인스턴스 시작과 부트스트랩시작 템플릿으로 인스턴스를 띄우고, 필요하면 user data(시작 시 실행되는 스크립트)로 에이전트 설정을 전달합니다. 인스턴스가 컨테이너 인스턴스로 클러스터에 등록됩니다.
  3. 운영과 유지보수ENI 트렁킹으로 네트워크 인터페이스를 늘리거나 메모리 예약으로 자원을 확보하고, SSM Run Command로 원격 관리합니다. 스팟 인스턴스는 종료 알림에 맞춰 드레이닝하는 등 운영 설정을 적용합니다.

#5한 줄 요약

ECS 컨테이너 에이전트가 미리 구성된 최적화 AMI로 EC2 인스턴스를 띄워 클러스터에 컨테이너 실행 용량으로 등록하는 것

컨테이너 에이전트

ECS 컨테이너 에이전트는 각 컨테이너 인스턴스에서 실행되며 ECS API와 통신해 태스크를 시작·중지하고 인스턴스 상태를 클러스터에 보고하는 소프트웨어다.

#1문제 상황

EC2 인스턴스는 ECS 제어 영역과 대화할 방법이 있어야 태스크를 받아 실행하고 상태를 알릴 수 있습니다. 이 연결이 없으면 인스턴스는 그냥 일반 서버일 뿐이고 클러스터의 일부로 동작하지 못합니다. 또한 프라이빗 레지스트리 인증이나 로그 설정처럼 인스턴스마다 다르게 적용해야 할 구성이 생기는데, 이를 인스턴스마다 일관되게 관리하기도 어렵습니다.

#2핵심 질문

EC2 인스턴스가 ECS와 통신해 태스크를 실행·보고하고 인스턴스별 구성을 적용하려면 무엇이 필요한가?

#3동작 예시

Linux 컨테이너 인스턴스에서 /etc/ecs/ecs.config 파일에 에이전트 환경 변수를 적어 두고 에이전트를 재시작하면, 그 설정이 적용된 상태로 인스턴스가 ECS와 통신합니다. 시작 시점에 user data로 같은 변수를 넘겨 처음부터 원하는 구성으로 띄울 수도 있습니다.

#4동작 과정

  1. 에이전트 설치 확인ECS 최적화 AMI에는 컨테이너 에이전트가 이미 들어 있습니다. 사용자 지정 AMI라면 에이전트를 수동으로 설치합니다.
  2. 구성 설정에이전트 설정 대부분은 환경 변수로 지정합니다. Linux는 /etc/ecs/ecs.config 파일이나 user data로, Windows는 PowerShell 명령으로 설정한 뒤 에이전트를 재시작합니다.
  3. 버전 유지와 통신에이전트 버전을 최신으로 유지하고, 필요하면 S3에 구성을 저장하거나 프라이빗 레지스트리 인증을 인스턴스 수준에서 설정합니다. 에이전트는 ECS API와 통신해 태스크를 시작·중지하고 인스턴스 상태를 클러스터에 보고합니다.

#5한 줄 요약

컨테이너 인스턴스에서 ECS API와 통신하며 태스크 실행을 지시받고 인스턴스 상태를 보고하는 에이전트

클러스터·인스턴스 운영

운영 단계에서는 컨테이너 인스턴스를 드레이닝해 태스크를 안전히 옮기고, 등록 해제·유형 변경·클러스터 업데이트 등으로 클러스터 자원을 유지·정리한다.

→ 04-05 참조

#1문제 상황

EC2 인스턴스를 컨테이너 인스턴스로 사용하면 운영자가 인스턴스의 상태를 직접 관리해야 한다. 특정 인스턴스 위에서 태스크가 계속 돌고 있을 때, 그 인스턴스를 점검하거나 교체하거나 종료하려면 먼저 태스크를 다른 곳으로 옮겨야 한다. 그냥 인스턴스를 내리면 그 위에서 실행되던 태스크가 예고 없이 끊긴다.

또 더 이상 쓰지 않는 인스턴스가 클러스터에 등록된 채 남아 있으면 ECS는 그 인스턴스에 태스크를 배치하려 시도하며 자원을 헛되이 본다. 인스턴스 속성이나 클러스터 설정이 바뀌면 클러스터 자원 목록을 최신 상태로 유지해야 하는데, 이를 수동으로 정리하는 일은 반복적이고 실수하기 쉽다.

#2핵심 질문

인스턴스를 점검하거나 없애야 할 때, 그 위의 태스크를 중단 없이 옮기고 클러스터 자원 목록을 안전하게 최신 상태로 유지하려면 어떻게 해야 하는가?

#3동작 예시

컨테이너 인스턴스 A에서 실행 중인 태스크가 있다. 운영자가 인스턴스 A를 드레이닝(draining, 태스크를 다른 인스턴스로 옮기도록 유도하는 상태)으로 설정하면, ECS는 A에서 새 태스크를 받지 않게 하고 실행 중인 태스크를 다른 인스턴스로 옮긴다. A 위의 태스크가 모두 빠지면 A를 등록 해제(deregister)해 클러스터가 더 이상 A를 배치 대상으로 보지 않게 한다. 그다음 인스턴스를 중지하거나 종료해도 실행 중이던 태스크는 끊기지 않는다.

#4동작 과정

  1. 드레이닝 설정컨테이너 인스턴스를 DRAINING 상태로 바꾸면 새 태스크 배치가 차단되고, 실행 중인 태스크는 다른 인스턴스로 옮겨진다. 그래서 인스턴스를 내려도 서비스가 끊기지 않는다.
  2. 등록 해제와 속성 정리태스크가 모두 빠진 인스턴스를 클러스터에서 등록 해제하면 배치 대상에서 제외된다. 인스턴스 속성(attributes)을 조회·변경해 배치 제약 조건에 쓰이는 값을 갱신할 수 있다.
  3. 클러스터 유지·정리더 이상 쓰지 않는 클러스터는 삭제하고, 설정이 바뀌면 클러스터 업데이트로 반영한다. 클러스터 조회로 현재 자원 상태를 확인한다.

#5한 줄 요약

태스크 수명 주기와 상태

태스크가 생성(PENDING)에서 시작해 실행(RUNNING)을 거쳐 종료(STOPPED)에 이르기까지 거치는 상태와 그 전이 과정.

#1문제 상황

태스크를 시작하면 즉시 실행되는 것처럼 보이지만, 실제로는 실행할 컴퓨팅 용량을 찾아 컨테이너를 배치하기까지 시간이 걸린다. 이 과정을 상태로 구분하지 않으면 태스크가 아직 실행 전인지, 실행 중인지, 멈추는 중인지 알 수 없다. 예를 들어 태스크를 중지했는데 컨테이너가 바로 사라지지 않으면 사용자는 중지가 실패했다고 오해한다.

ECS 에이전트는 중지 요청을 받아도 태스크가 실제로 멈출 때까지 시간이 걸린다. 그래서 사용자가 요청한 상태와 실제로 보고되는 상태가 다를 수 있다. 이 차이를 드러내 줄 기준이 없으면 태스크의 진행 상황을 판단할 수 없다.

#2핵심 질문

태스크가 생성되어 실행되고 끝날 때까지, ECS는 그 진행 상황을 어떤 상태로 추적하고 요청한 상태와 실제 상태의 차이는 어떻게 관리하는가?

#3동작 예시

태스크를 중지 요청하면 사용자가 지정하는 desiredStatus(원하는 상태)는 곧바로 STOPPED가 된다. 하지만 컨테이너는 정리 절차를 거쳐야 하므로 lastStatus(에이전트가 보고한 마지막 실제 상태)는 잠시 RUNNING으로 남아 있다. 에이전트가 컨테이너를 실제로 멈추고 나서야 lastStatus가 STOPPED로 바뀐다. 두 값이 다르면 중지 요청은 접수됐지만 아직 끝나지 않았다는 뜻이다.

#4동작 과정

  1. 생성과 용량 확보태스크를 시작하면 먼저 PROVISIONING 상태가 된다. 이때는 태스크도 컨테이너도 아직 존재하지 않으며, ECS가 실행할 컴퓨팅 용량을 찾는 단계다.
  2. 배치와 실행용량을 찾으면 PENDING을 거쳐 RUNNING으로 간다. 컨테이너가 시작되어 태스크가 실제로 동작하고, 계속 떠 있어야 하는 서비스 태스크는 이 상태로 유지된다.
  3. 중지와 종료중지 요청이나 작업 완료로 STOPPED에 이른다. 마지막 상태와 원하는 상태를 콘솔이나 describe로 확인할 수 있다.

#5한 줄 요약

태스크가 PROVISIONING에서 RUNNING을 거쳐 STOPPED에 이르는 각 단계를 lastStatus와 desiredStatus로 추적해 진행 상황과 요청의 차이를 보여주는 것

태스크 배치 전략

클러스터의 여러 컨테이너 인스턴스 중 어디에 태스크를 배치할지 정하는 규칙으로, 분산형(spread)·균형형(binpack)·가용 영역 균형형 등이 있다.

#1문제 상황

EC2 시작 유형(launch type)으로 태스크를 실행하면 클러스터 안에 여러 컨테이너 인스턴스가 있고, ECS는 그중 어디에 태스크를 놓을지 정해야 한다. 아무 규칙 없이 배치하면 특정 인스턴스에 태스크가 몰려 자원이 부족해지고 다른 인스턴스는 놀게 된다. 태스크 수를 줄일 때도 어느 태스크를 먼저 종료할지 기준이 없으면 자원 활용이 나빠진다.

여러 가용 영역에 인스턴스가 흩어져 있을 때 한 영역에 태스크가 쏠리면, 그 영역에 장애가 생겼을 때 서비스 전체가 취약해진다. 그래서 태스크를 어디에 흩고 어디에 모을지 규칙이 필요하다.

#2핵심 질문

여러 컨테이너 인스턴스 중 어디에 태스크를 배치하고, 태스크 수를 줄일 때 무엇을 먼저 종료할지 규칙으로 정하려면 어떻게 해야 하는가?

#3동작 예시

서비스로 실행되는 태스크의 기본 배치 전략은 spread(분산)이며, 기준 속성은 attribute:ecs.availability-zone(가용 영역)이다. 태스크가 여러 개면 ECS가 가용 영역별로 나누어 배치하므로 한 영역에 태스크가 몰리지 않는다. 반대로 binpack(균형형)을 쓰면 CPU나 메모리를 가장 많이 쓰는 인스턴스부터 채워 인스턴스 수를 줄이는 쪽으로 배치한다.

#4동작 과정

  1. 전략 선택standalone 태스크(서비스에 속하지 않은 독립 태스크)에는 기본 전략이 없고, 서비스 태스크에는 가용 영역 기준 spread가 기본이다. PlacementStrategy로 원하는 전략을 지정할 수 있다.
  2. 배치 대상 결정spread는 지정 속성을 기준으로 태스크를 고르게 나누고, binpack은 사용률이 높은 인스턴스에 몰아 넣어 인스턴스 수를 줄이며, random은 무작위로 고른다.
  3. 전략은 참고, 제약은 강제배치 전략은 최선 노력(best effort)이라 최적의 자리가 없으면 다른 곳에라도 배치한다. 태스크 그룹과 조합해 쓸 수 있고 조합에는 제한이 있다.

#5한 줄 요약

컨테이너 인스턴스에 태스크를 어떻게 흩거나 모을지 규칙으로 정해 자원 활용과 가용 영역 분산을 조절하는 것

배치 제약 조건과 클러스터 쿼리 언어

특정 조건을 만족하는 컨테이너 인스턴스에만 태스크를 배치하도록 제한하는 규칙과, 그 조건을 표현하는 클러스터 쿼리 언어(CQL) 식.

→ 05-02 참조

#1문제 상황

배치 전략만으로는 "이런 인스턴스에는 태스크를 놓지 마라" 같은 강한 조건을 표현할 수 없다. 전략은 최선 노력이라 조건을 만족하는 자리가 없어도 태스크를 배치해 버린다. 예를 들어 특정 속성을 가진 인스턴스에서만 돌아야 하는 태스크가 조건과 무관한 인스턴스에 배치되면 실행에 실패한다.

또 같은 서비스의 태스크를 절대 같은 인스턴스에 두면 안 되는 경우처럼, 배치 자체를 제한해야 하는 요구가 있다. 이런 요구는 배치를 강제하는 별도 규칙으로만 만족시킬 수 있다.

#2핵심 질문

특정 조건을 만족하는 컨테이너 인스턴스에만 태스크가 배치되도록 강제하고, 그 조건을 식으로 표현하려면 어떻게 해야 하는가?

#3동작 예시

memberOf 제약에 클러스터 쿼리 언어(CQL) 식을 적어 조건을 지정한다. 예를 들어 인스턴스의 ecs.instance-type 속성이 c5.large인 곳에서만 태스크를 실행하도록 식을 쓰면, 그 조건에 맞는 인스턴스에만 태스크가 배치된다. 조건을 만족하는 인스턴스가 하나도 없으면 태스크는 PENDING 상태로 남는다. distinctInstance 제약을 쓰면 각 태스크가 서로 다른 컨테이너 인스턴스에 하나씩 배치된다.

#4동작 과정

  1. 제약 유형 선택배치 제약 조건은 컨테이너 인스턴스에 대한 규칙으로, 태스크가 그 인스턴스에서 실행되어도 되는지 판단한다. 서비스·태스크 정의·태스크에서 placementConstraint 파라미터로 지정한다.
  2. 조건 표현memberOf는 CQL 식으로 인스턴스 속성을 조건으로 걸고, distinctInstance는 태스크마다 다른 인스턴스를 요구한다. 조건에 맞는 인스턴스가 최소 하나 있어야 한다.
  3. 강제 적용제약 조건은 구속력이 있어 조건을 못 맞추면 배치를 막는다. 그 결과 조건에 맞는 인스턴스가 없으면 태스크는 PENDING에 머문다.

#5한 줄 요약

클러스터 쿼리 언어로 컨테이너 인스턴스 조건을 표현해, 조건을 만족하는 인스턴스에만 태스크가 배치되도록 강제하는 것

독립 실행 태스크와 예약 실행

서비스에 속하지 않고 한 번 실행되고 끝나는 독립 실행 태스크와, EventBridge Scheduler로 일회성 또는 반복 예약 실행하는 방법.

#1문제 상황

모든 애플리케이션이 계속 떠 있어야 하는 것은 아니다. 배치 작업처럼 한 번 돌고 스스로 끝나는 애플리케이션이 있다. 이런 작업을 서비스로 만들면 끝난 뒤에도 서비스 스케줄러가 계속 태스크 수를 유지하려 해서 불필요하게 다시 실행된다.

또 이런 작업을 정해진 시각이나 주기마다 자동으로 돌리려면 별도의 예약 수단이 필요하다. 실행이 끝난 독립 태스크는 서비스와 달리 재시작되지 않으므로, 이 차이를 이해하고 실행 방식을 골라야 한다.

#2핵심 질문

한 번 실행되고 끝나는 작업을 서비스로 만들지 않고 실행하고, 그 실행을 일회성·반복 일정으로 자동 예약하려면 어떻게 해야 하는가?

#3동작 예시

배치 처리를 한 번 돌리려면 콘솔, AWS CLI, API, SDK 중 하나로 태스크를 독립 실행한다. 태스크가 생성되면 처음에는 PROVISIONING 상태가 되는데, 이때는 태스크도 컨테이너도 아직 없다. ECS가 launch type이나 용량 공급자(capacity provider) 설정에 따라 실행할 컴퓨팅 용량을 고르는 단계다. 정해진 주기나 시각마다 돌리려면 EventBridge Scheduler로 rate 기반, cron 기반, 일회성 스케줄을 만든다.

#4동작 과정

  1. 실행 방법 선택한 번만 실행하려면 콘솔·CLI·API·SDK로 독립 태스크를 시작한다. 일정에 따라 실행하려면 EventBridge Scheduler로 스케줄을 만든다.
  2. 용량 선택과 실행태스크는 PROVISIONING으로 시작해 ECS가 launch type이나 용량 공급자 구성에 따라 용량을 고른다. Fargate면 용량 관리를 ECS가 대신하고, EC2면 인스턴스에 배치한다.
  3. 실행 후 종료작업이 끝나면 태스크는 스스로 끝난다. 서비스가 아니므로 재시작되지 않는다.

#5한 줄 요약

한 번 실행되고 끝나는 작업을 서비스와 분리해 독립 태스크로 돌리고, EventBridge Scheduler로 일회성·반복 일정에 맞춰 자동 실행하는 것

서비스와 배포06-01

서비스 개념과 서비스 스케줄러

서비스는 지정한 수의 작업(task) 인스턴스를 클러스터에서 동시에 실행·유지하도록 관리하는 Amazon ECS 리소스로, 서비스 스케줄러가 작업의 시작·중지와 개수 유지를 담당한다.

#1문제 상황

태스크를 하나 띄워 두면 그 태스크가 실패하거나 멈췄을 때 아무도 대신 띄워 주지 않는다. 사용자가 직접 다시 실행해야 하고, 트래픽이 늘어도 태스크 수는 그대로다. 여러 태스크를 띄웠어도 그중 하나가 죽으면 전체 처리량이 줄어든다.

즉 사람이 개입하지 않으면 원하는 수의 태스크를 계속 유지하기 어렵다. 태스크 하나가 죽어도 서비스 전체가 흔들리지 않으려면 개수를 자동으로 맞춰 주는 관리자가 필요하다.

#2핵심 질문

지정한 수의 태스크 인스턴스를 항상 동시에 실행 상태로 유지하고, 태스크가 실패하면 자동으로 대체하려면 어떻게 해야 하는가?

#3동작 예시

서비스의 원하는 태스크 수(desiredCount)를 3으로 두면 클러스터에 태스크 3개가 동시에 실행된다. 그중 하나가 실패해 멈추면 서비스 스케줄러가 곧바로 태스크 정의의 새 인스턴스를 하나 더 띄워 다시 3개를 맞춘다. 로드 밸런서를 서비스 뒤에 두면 들어오는 트래픽이 서비스에 연결된 태스크들로 분배된다.

#4동작 과정

  1. 서비스 정의와 배치서비스는 태스크 정의와 원하는 태스크 수, 배치 전략·제약 조건을 지정해 만든다. 서비스 스케줄러가 지정한 스케줄링 전략을 지키며 태스크를 배치한다.
  2. 개수 유지와 교체태스크가 실패하거나 멈추면 스케줄러가 새 태스크를 실행해 원하는 수에 도달할 때까지 대체한다. 기반 인프라가 실패해도 태스크를 다시 배치한다.
  3. 스로틀과 이벤트스케줄러는 한 번에 너무 많은 태스크를 시작·중지하지 않도록 스로틀 로직을 적용한다. 서비스 이벤트로 이런 변화를 확인할 수 있다.

서비스 스케줄러가 지정한 수의 태스크를 항상 실행 상태로 유지하고 실패한 태스크를 자동 교체해 장기 실행 상태 비저장 애플리케이션을 안정적으로 돌리는 것

서비스 정의 파라미터

서비스 정의 파라미터는 원하는 작업 수, 태스크 정의, 로드 밸런서, 배포 설정 등 서비스를 어떻게 실행·유지할지 지정하는 JSON 필드들이다.

#1문제 상황

서비스를 만들 때 실행 방식과 유지 규칙을 아무 데도 명시하지 않으면 기본값으로만 동작해 원하는 대로 제어할 수 없다. 예를 들어 어떤 컴퓨팅에서 돌릴지, 한 번에 몇 개까지 태스크를 늘릴지, 실패가 반복될 때 언제 멈출지를 정하지 않으면 배포가 예측 불가능해진다.

이런 값들을 하나의 정의로 모아 관리하지 않으면 서비스마다 설정이 흩어져 일관성이 깨진다. 서비스가 어떻게 돌아갈지를 담는 단일한 명세가 필요하다.

#2핵심 질문

서비스를 어떻게 실행하고 유지할지, 즉 컴퓨팅 유형·태스크 수·배포 방식·롤백 조건을 하나의 정의로 어떻게 지정하는가?

#3동작 예시

서비스 정의에서 launchType을 FARGATE로 지정하면 Fargate에서 서비스를 실행하고, launchType을 지정하지 않으면 기본 capacityProviderStrategy가 대신 쓰인다. launchType을 지정하면 capacityProviderStrategy는 함께 쓸 수 없다. 배포 구성(deploymentConfiguration)에서 최소 정상 비율과 최대 정상 비율을 정하면, 배포 중에 정상 태스크를 몇 개까지 줄이거나 넘길지 제어할 수 있다.

#4동작 과정

  1. 컴퓨팅 유형 지정launchType(EC2·FARGATE·EXTERNAL) 또는 capacityProviderStrategy로 서비스를 어디서 실행할지 정한다. 두 값은 서로 배타적이다.
  2. 배포 설정deploymentConfiguration에 최소·최대 정상 비율과 배포 회로 차단기 설정을 넣어, 배포 중 태스크 수와 실패 시 중단 여부를 제어한다.
  3. 스케줄링과 태그서비스 스케줄링 전략으로 태스크 배치 방식을 정하고, 서비스 태그로 리소스를 분류·관리한다.

원하는 태스크 수, 컴퓨팅 유형, 배포 구성 같은 필드를 서비스 정의 하나로 모아 서비스의 실행·유지 방식을 명확히 지정하는 것

배포 컨트롤러와 전략 개요

배포 컨트롤러는 서비스의 새 리비전을 어떤 방식으로 반영할지 결정하는 주체이며, 롤링 업데이트·블루/그린·선형·카나리·외부 전략 중에서 선택한다.

#1문제 상황

ECS 서비스는 한 번 실행을 시작하면 지정한 작업 정의에 따라 정해진 수의 작업을 계속 유지한다. 새 이미지나 새 설정을 서비스에 반영하려면 실행 중인 기존 작업을 멈추고 새 작업으로 바꿔야 하는데, 이 교체를 아무 규칙 없이 한 번에 밀어붙이면 요청을 받던 작업이 동시에 사라져 트래픽이 끊긴다. 교체 도중 문제가 생겼을 때 이전 상태로 되돌릴 기준도 없다.

#2핵심 질문

서비스의 새 리비전을 반영할 때, 기존 작업과 새 작업 사이의 트래픽을 어떤 주체가 어떤 방식으로 옮길 것인가?

#3동작 예시

서비스에는 배포 컨트롤러 설정이 하나 있고, 이 값이 트래픽 전환을 누가 맡는지를 정한다. ECS로 두면 서비스 스케줄러가 기존 작업을 새 작업으로 하나씩 바꾸는 롤링 업데이트를 직접 수행하고, CODE_DEPLOY로 두면 AWS CodeDeploy가 블루/그린 방식의 전환을 맡으며, EXTERNAL로 두면 서드파티 컨트롤러가 배포 과정을 직접 제어한다. 어느 컨트롤러를 고르든, 트래픽을 한 번에 옮기는지 일정 비율씩 나눠 옮기는지에 따라 롤링 업데이트·블루/그린·선형·카나리 같은 개별 전략이 정해진다.

#4동작 과정

  1. 컨트롤러 선택서비스 설정에서 배포를 수행할 주체를 ECS, CODE_DEPLOY, EXTERNAL 중 하나로 지정한다. 그래서 트래픽 전환 로직을 ECS가 직접 돌릴지, CodeDeploy나 외부 도구에 맡길지가 결정된다.
  2. 전략 결정선택한 컨트롤러의 지원 범위 안에서 롤링 업데이트, 블루/그린, 선형, 카나리 중 하나를 고른다. 그래서 작업을 얼마나 점진적으로 교체하고 트래픽을 어느 비율로 나눌지가 정해진다.
  3. 배포 실행정해진 컨트롤러와 전략에 따라 새 리비전이 기존 작업을 대체하며 반영된다. 그래서 새 버전이 실제 트래픽을 받는 상태로 서비스가 갱신된다.

롤링 업데이트 배포

롤링 업데이트 배포는 서비스 스케줄러가 기존 작업을 새 작업으로 점진적으로 교체하며 최소·최대 정상 비율을 지키는 기본 배포 방식이다.

#1문제 상황

기존 작업을 한 번에 전부 멈추고 새 작업을 올리면, 새 작업이 준비될 때까지 서비스가 요청을 받지 못하는 공백이 생긴다. 반대로 새 작업을 아무 제한 없이 한꺼번에 띄우면 클러스터 자원이 순간적으로 부족해지거나, 문제가 있는 새 버전이 모든 요청을 받아 피해가 커진다. 기존 작업과 새 작업이 섞여 있는 동안 어느 정도 수를 유지할지에 대한 기준이 없으면 배포가 안전하지 않다.

#2핵심 질문

기존 작업을 새 작업으로 교체하는 동안, 정상 상태로 유지해야 할 작업 수의 아래·위 한계를 어떻게 지키며 교체할 것인가?

#3동작 예시

서비스의 희망 작업 수가 4개이고 최소 정상 비율(minimumHealthyPercent)이 50이면, 스케줄러는 기존 작업 2개까지 멈추고 새 작업 2개를 시작할 수 있다. 여기서 최소 정상 비율은 배포 중 정상 상태로 유지해야 하는 작업 수의 하한을 희망 작업 수 대비 백분율로 나타낸 값이고, 최대 비율(maximumPercent)은 배포 중 실행될 수 있는 작업 수의 상한을 나타낸다. 이 두 값의 범위 안에서 새 작업이 뜨고 기존 작업이 내려가며 교체가 조금씩 진행된다.

#4동작 과정

  1. 새 작업 시작최대 비율이 허용하는 범위 안에서 새 리비전의 작업을 추가로 띄운다. 그래서 기존 작업이 살아 있는 상태로 새 작업이 자리를 잡는다.
  2. 정상 확인 후 기존 작업 종료새 작업이 정상 상태가 되면 최소 정상 비율을 밑돌지 않는 선에서 기존 작업을 멈춘다. 그래서 서비스가 유지하는 정상 작업 수가 하한 아래로 내려가지 않는다.
  3. 반복 완료이 교체를 희망 작업 수만큼 반복해 모든 작업이 새 리비전으로 바뀐다. 그래서 서비스를 멈추지 않고 배포가 끝난다.

#5한 줄 요약

최소 정상 비율과 최대 비율이라는 상·하한 안에서 기존 작업과 새 작업을 조금씩 맞바꿔 서비스 중단 없이 새 리비전으로 교체하는 것

블루/그린 배포는 새 버전(그린)을 별도로 띄워 검증한 뒤 로드 밸런서 트래픽을 이전 버전(블루)에서 새 버전으로 전환하는 무중단 배포 방식이다.

#1문제 상황

롤링 업데이트는 기존 작업과 새 작업이 같은 환경에서 섞여 트래픽을 나눠 받는다. 그래서 새 버전에 문제가 있으면 그 문제가 실제 사용자 요청에 그대로 노출되고, 이미 섞인 작업을 되돌리는 데 시간이 걸린다. 새 리비전을 운영 트래픽에 보내기 전에 별도 환경에서 먼저 검증할 방법이 필요하다.

#2핵심 질문

새 버전을 운영 트래픽에 연결하기 전에 별도 환경에서 검증하고, 문제가 있으면 즉시 이전 버전으로 되돌릴 수 있는가?

#3동작 예시

블루와 그린이라는 동일한 두 운영 환경을 나란히 둔다. 블루는 현재 서비스가 도는 환경이고 그린은 새 리비전을 올린 환경이다. 그린을 띄워 테스트 트래픽으로 동작을 확인한 뒤, 로드 밸런서가 운영 트래픽을 블루에서 그린으로 넘긴다. 이때 운영 트래픽이 오기 전에 별도 규칙으로 테스트 요청만 그린으로 보내 검증할 수 있어, 문제가 있으면 트래픽을 다시 블루로 돌리면 된다.

#4동작 과정

  1. 그린 환경 준비새 리비전의 작업을 기존 환경과 분리된 그린 환경에 띄운다. 그래서 운영 중인 블루 환경은 영향을 받지 않는다.
  2. 테스트 트래픽으로 검증헤더 라우팅 같은 규칙으로 테스트 요청을 그린에 보내 정상 동작을 확인한다. 그래서 실제 사용자 트래픽을 넘기기 전에 문제를 걸러낼 수 있다.
  3. 운영 트래픽 전환검증이 끝나면 로드 밸런서가 운영 트래픽을 블루에서 그린으로 넘긴다. 그래서 중단 없이 새 버전이 서비스를 맡고, 문제가 있으면 블루로 즉시 되돌린다.

선형 배포는 트래픽을 일정 비율씩 단계적으로 옮기고, 카나리 배포는 소량의 트래픽만 새 버전으로 보내 검증한 뒤 전량 전환하는 점진적 배포 방식이다.

#1문제 상황

블루/그린 배포는 검증이 끝나면 트래픽을 한 번에 새 버전으로 넘긴다. 그래서 전환 직후에 예상하지 못한 문제가 드러나면 그 순간 모든 운영 트래픽이 문제 버전을 향한다. 새 버전을 소량의 트래픽으로 먼저 겪어 보고, 각 단계의 성능을 확인하면서 조금씩 늘려 가는 방식이 필요하다.

#2핵심 질문

새 버전으로 보내는 트래픽을 일정 비율씩 나눠 옮기면서 각 단계의 결과를 확인한 뒤 다음으로 진행할 수 있는가?

#3동작 예시

선형 배포에서는 한 번에 옮길 트래픽 비율(step percent)과 각 단계 사이에 기다리는 시간(step bake time)을 정한다. 예를 들어 단계 비율을 10으로 두면 트래픽이 10%씩 여러 번에 나눠 새 리비전으로 이동한다. 카나리 배포는 이와 달리 소량의 트래픽만 먼저 새 버전으로 보내 검증하고, 문제가 없으면 나머지 트래픽을 한 번에 넘기는 2단계 구성이다.

#4동작 과정

  1. 1차 트래픽 이동정한 비율만큼 운영 트래픽을 새 리비전으로 보낸다. 카나리는 이 첫 단계에서 소량만 보내 검증한다. 그래서 새 버전이 일부 트래픽만 받는다.
  2. 대기와 관찰단계 사이의 베이크 시간 동안 새 버전의 성능과 오류를 지켜본다. 그래서 문제가 있으면 다음 단계로 가기 전에 멈출 수 있다.
  3. 전량 전환문제가 없으면 정한 비율만큼 반복해 트래픽을 더 옮기고, 최종적으로 100%를 새 리비전으로 넘긴다. 그래서 새 버전이 전체 트래픽을 안정적으로 맡는다.

#5한 줄 요약

트래픽을 정한 비율과 대기 시간으로 나눠 옮기며 각 단계를 확인한 뒤 새 버전으로 전환하는 것

CodeDeploy 블루/그린과 외부 배포

CodeDeploy 블루/그린은 AWS CodeDeploy가 트래픽 전환을 제어하는 배포 방식이고, 외부 배포는 서드파티 배포 컨트롤러로 배포 과정을 직접 제어하는 방식이다.

#1문제 상황

블루/그린 배포를 쓰려면 트래픽 전환 시점과 검증 절차를 관리하는 주체가 필요하다. ECS가 자체 제공하는 블루/그린을 쓰지 않고 예전부터 쓰던 도구나 별도 배포 파이프라인에 배포 제어를 맡기고 싶은 경우도 있다. 서비스가 어떤 컨트롤러로 배포를 수행하느냐에 따라 필요한 설정과 리소스가 달라진다.

#2핵심 질문

트래픽 전환을 ECS가 아니라 CodeDeploy나 서드파티 도구가 맡게 하려면 배포를 어떻게 구성해야 하는가?

#3동작 예시

blue/green 배포 유형에서 컨트롤러를 CodeDeploy로 두면, 서비스의 각 버전을 TaskSet(태스크 세트)이라는 단위로 관리하고 CodeDeploy가 그 사이의 트래픽 전환을 제어한다. 전환 방식은 카나리나 선형 같은 CodeDeploy 배포 구성으로 정한다. 또 EXTERNAL 컨트롤러를 쓰면 배포 과정을 외부 도구가 직접 제어하며, 트래픽 전환과 검증 절차도 그 도구가 맡는다.

#4동작 과정

  1. 컨트롤러 지정서비스에서 배포 컨트롤러를 CodeDeploy 또는 외부로 설정한다. 그래서 트래픽 전환의 주체가 ECS에서 CodeDeploy나 서드파티 도구로 넘어간다.
  2. TaskSet과 배포 구성 준비CodeDeploy 방식에서는 새 버전을 TaskSet으로 만들고 카나리·선형 같은 배포 구성으로 전환 규칙을 정한다. 그래서 언제 얼마만큼 트래픽을 옮길지가 정해진다.
  3. 전환과 마무리컨트롤러가 정한 규칙에 따라 트래픽이 새 버전으로 옮겨지고, 문제가 없으면 기존 버전이 정리된다. 그래서 서드파티 제어 아래에서 배포가 완료된다.

#5한 줄 요약

배포 실패 감지와 생명 주기 훅

배포 실패 감지는 배포 서킷 브레이커나 CloudWatch 경보로 실패를 자동 판별하고, 생명 주기 훅은 배포의 특정 단계에서 Lambda 실행이나 일시 정지로 개입하게 한다.

#1문제 상황

배포를 시작한 뒤 새 작업이 계속 비정상으로 뜨거나 오류율이 치솟아도, 사람이 지켜보지 않으면 배포가 그대로 진행되어 문제 버전이 서비스 전체를 덮을 수 있다. 배포를 무조건 끝까지 돌리면 실패를 알아채는 시점이 늦고 되돌리는 비용도 커진다. 그래서 실패를 자동으로 판별해 되돌리거나, 특정 단계에서 사람이 개입할 지점이 필요하다.

#2핵심 질문

배포가 비정상으로 흘러갈 때 이를 자동으로 감지해 되돌리거나, 정해진 단계에서 사람이 개입하게 할 수 있는가?

#3동작 예시

ECS는 배포 실패를 감지하는 방법으로 배포 회로 차단기(Deployment Circuit Breaker)와 CloudWatch 경보를 제공한다. 회로 차단기는 새 작업이 반복해서 실패하는 것을 임계값으로 세어 배포 실패를 판단하고, CloudWatch 경보는 지표가 경보 상태가 되면 실패로 판단한다. 두 방법 모두 설정해 두면 실패한 배포를 마지막으로 성공했던 상태로 자동 롤백할 수 있다.

#4동작 과정

  1. 실패 감지배포 중 회로 차단기가 감지한 실패 작업 수를 세거나 CloudWatch 경보가 울리는지 확인한다. 그래서 배포가 정상인지 자동으로 판별된다.
  2. 자동 롤백 또는 훅 개입실패로 판단되면 이전의 성공한 배포로 되돌리거나, 배포 생명 주기 훅이 걸린 단계에서 Lambda를 실행하거나 배포를 일시 중지한다. 그래서 문제 버전이 서비스 전체를 덮기 전에 멈출 수 있다.
  3. 진행 또는 중지 결정일시 중지된 배포는 ContinueServiceDeployment로 계속하거나 StopServiceDeployment로 중지한다. 그래서 사람이 확인한 뒤 다음 동작을 정한다.

#5한 줄 요약

배포 실패를 자동으로 감지해 되돌리거나 정해진 단계에서 개입하게 하여 문제 버전이 퍼지는 것을 막는 것

서비스 배포와 리비전

서비스 배포는 서비스의 워크로드 구성을 새로 반영하는 과정이며, 서비스 리비전은 그때 배포하려는 워크로드 구성 설정의 기록이다.

#1문제 상황

서비스를 여러 번 갱신하다 보면 지금 어떤 워크로드 구성이 실제로 배포되어 있고, 이번 배포가 어떤 설정에서 어떤 설정으로 바뀌는지 한눈에 파악하기 어렵다. 배포 중 롤백이 일어났는지, 어떤 경보가 울렸는지, 언제 시작해 언제 끝났는지도 흩어져 있어 추적이 번거롭다. 배포 자체를 하나의 기록 단위로 남겨 이력을 볼 방법이 필요하다.

#2핵심 질문

지금 배포된 워크로드 구성과 이번에 배포하려는 구성, 그 진행 상태와 결과를 하나의 기록으로 볼 수 있는가?

#3동작 예시

배포할 때마다 서비스 배포(ServiceDeployment)라는 읽기 전용 기록이 하나씩 만들어지고 고유 ID가 붙는다. 이 기록은 현재 배포된 구성을 나타내는 소스 서비스 리비전, 이번에 배포하려는 대상 서비스 리비전, 배포 상태, 회로 차단기가 감지한 실패 작업 수, 경보 상태인 CloudWatch 경보, 시작·완료 시각, 롤백이 있었다면 그 내용을 담는다. 서비스 리비전은 그 시점에 배포하려던 워크로드 구성 설정의 기록이다.

#4동작 과정

  1. 리비전 생성서비스의 워크로드 구성이 바뀔 때마다 그 설정이 서비스 리비전으로 기록된다. 그래서 배포 대상 구성이 하나의 스냅숏으로 남는다.
  2. 배포 기록 생성과 진행서비스 배포가 Pending, Ongoing, Completed 중 하나의 단계로 진행되며 소스 리비전에서 대상 리비전으로 넘어간다. 그래서 배포의 시작과 진행 상황이 추적된다.
  3. 결과 확인완료된 배포 기록에서 실패 작업 수, 경보, 롤백 여부 등을 확인할 수 있다. 그래서 각 배포가 어떻게 끝났는지 이력으로 남는다.

#5한 줄 요약

배포하려는 워크로드 구성을 리비전으로, 그 배포 과정을 서비스 배포 기록으로 남겨 진행 상태와 결과를 한눈에 보게 하는 것

서비스 관리 작업

서비스 관리 작업은 실행 중인 서비스의 원하는 개수·태스크 정의·배포 설정 같은 파라미터를 갱신하거나 서비스를 삭제하는 운영 절차다.

#1문제 상황

서비스를 한 번 만들면 원하는 태스크 수, 태스크 정의, 배포 설정 같은 값이 그대로 고정된다. 트래픽이 늘어 개수를 바꾸거나 새 태스크 정의로 교체하려 해도, 기존 서비스를 그대로 둔 채로는 값을 바꿀 수 없다.

예전에는 이런 변경을 하려면 서비스를 삭제하고 다시 만드는 방법밖에 없었는데, 삭제하는 순간 실행 중이던 태스크가 함께 사라져 서비스가 끊긴다. 운영 중인 서비스에는 쓸 수 없는 방식이다.

#2핵심 질문

서비스를 중단시키지 않고 원하는 개수·태스크 정의·배포 설정을 바꾸거나 서비스를 정리하려면 어떻게 해야 하는가?

#3동작 예시

원하는 태스크 수를 2에서 4로 늘리는 경우를 보자. UpdateService 호출에 원하는 개수 값만 4로 담아 보내면, 나머지 설정은 그대로 둔 채 서비스 스케줄러가 새 태스크 두 개를 배치한다.

#4동작 과정

  1. 파라미터 갱신UpdateService로 바꿀 값만 전달한다. 스케줄러는 이 서비스의 태스크 정의를 감당할 수 있는 컨테이너 인스턴스(CPU·메모리·포트·속성 조건을 만족하는 인스턴스)를 후보로 추린다.
  2. 태스크 재배치새 태스크를 가용 영역에 고르게 분산한다. 같은 가용 영역에서 이 서비스의 실행 중 태스크 수가 가장 적은 인스턴스를 우선 선택한다.
  3. 적용과 정리바뀐 개수·태스크 정의·배포 설정이 서비스에 반영되고, 더는 필요 없는 서비스는 DeleteService로 삭제한다.

서비스 로드 밸런싱

Elastic Load Balancing(ALB·NLB·GLB)을 서비스에 연결해 여러 태스크에 트래픽을 고르게 분산하고 헬스 체크로 정상 태스크에만 보내는 기능.

#1문제 상황

태스크가 여러 개인 서비스에서는 클라이언트가 어느 태스크로 접속해야 하는지 알 수 없다. 태스크는 다시 시작할 때마다 IP와 포트가 바뀌므로, 주소를 하나 정해 두는 방식은 금방 어긋난다.

게다가 특정 태스크에만 트래픽이 몰리면 그 태스크가 죽는 순간 서비스 전체가 영향을 받는다. 정상 태스크와 그렇지 않은 태스크를 구분해 보내 줄 방법도 필요하다.

#2핵심 질문

여러 태스크에 트래픽을 고르게 나누고 정상 태스크에만 보내려면 어떻게 해야 하는가?

#3동작 예시

Application Load Balancer와 대상 그룹(대상 유형을 ip로 지정)을 서비스에 연결한 경우를 보자. 태스크가 시작되면 그 태스크의 IP와 포트가 대상 그룹에 등록되고, 헬스 체크를 통과한 태스크만 트래픽을 받는다.

#4동작 과정

  1. 등록태스크가 시작되면 로드 밸런서 대상 그룹에 IP와 포트를 등록한다. 이때 대상 유형은 ip로 두어 태스크의 사설 IP를 직접 가리키며, 동적 호스트 포트 매핑을 쓰면 같은 인스턴스 위 여러 태스크가 각자 다른 호스트 포트로 등록될 수 있다.
  2. 검사헬스 체크(상태 확인)로 응답이 정상인 태스크만 트래픽 대상으로 유지한다. 비정상 태스크는 대상 목록에서 빠진다.
  3. 분산로드 밸런서가 트래픽을 정상 태스크에 나눠 보내고, 종료되는 태스크는 연결 드레이닝(기존 연결이 끝날 때까지 기다렸다가 빼는 동작)을 거친다.

24시간 내내 트래픽이 변하는 서비스를 사람이 눈으로 보고 매번 조정하는 것도 현실적으로 불가능하다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 지표 수집ECS가 서비스의 평균 CPU·메모리 사용률 같은 CloudWatch 지표를 게시한다. 이 지표를 Application Auto Scaling이 감시한다.
  2. 정책 평가대상 추적·단계 조정·예약·예측 같은 정책이 지금 필요한 원하는 태스크 수를 계산한다.
  3. 조정계산된 값으로 원하는 개수를 갱신하면 ECS가 태스크를 추가하거나 제거한다.

Service Connect

AWS Cloud Map 네임스페이스와 경량 프록시를 이용해 ECS 서비스끼리 이름으로 통신하고 트래픽 관찰·암호화까지 제공하는 서비스 간 연결 방식.

#1문제 상황

ECS 서비스끼리 통신할 때 각 태스크의 IP는 계속 바뀌고, 상대를 부르는 방법이 VPC DNS 설정에 묶여 있으면 구성이 서비스마다 흩어진다. 서비스 이름으로 안정적으로 호출하기도 어렵고, 트래픽을 관찰하거나 암호화하려면 기능을 따로 붙여야 한다.

#2핵심 질문

ECS 서비스끼리 짧은 이름만으로 안정적으로 통신하고 트래픽까지 관찰·암호화하려면 어떻게 해야 하는가?

#3동작 예시

2개 서브넷에 WordPress 클라이언트 서비스와 MySQL 서버 서비스가 하나씩 도는 구성을 보자. WordPress 컨테이너 안에서 mysql --host=mysql 같은 짧은 이름으로 MySQL 서비스를 호출하면, 각 태스크 옆에 붙은 경량 프록시가 그 이름을 해석해 대상 태스크로 연결을 중계한다.

#4동작 과정

  1. 이름 등록각 서비스의 태스크 엔드포인트를 Cloud Map 네임스페이스에 등록해 짧은 이름으로 찾을 수 있게 한다.
  2. 프록시 중계클라이언트 태스크의 프록시가 짧은 이름을 해석해 대상 태스크로 연결을 전달한다. 이 방식은 VPC DNS 구성에 의존하지 않는다.
  3. 관찰과 보호표준화된 지표·로그를 모으고, 액세스 로그·TLS 암호화·존 인식 라우팅으로 트래픽을 관찰하고 보호한다.

CloudWatch 지표와 모니터링 개요

Amazon ECS가 Amazon CloudWatch로 리소스의 원시 데이터를 수집·처리해 클러스터·서비스·태스크의 CPU·메모리 등 지표를 제공하는 모니터링 방식.

#1문제 상황

컨테이너로 서비스를 돌리면 태스크가 어느 인스턴스에서 얼마나 CPU를 쓰고 메모리를 얼마나 잡아먹는지가 계속 바뀐다. 태스크가 죽었다가 다시 뜨는 일이 반복돼도 로그를 직접 열어보기 전에는 원인을 알기 어렵다. 인스턴스에 접속해 top 명령을 돌리는 방식은 태스크 수가 늘수록 확인할 수 있는 범위가 금방 한계에 부딪힌다.

#2핵심 질문

클러스터와 서비스, 태스크가 지금 어떤 상태로 자원을 쓰고 있는지 숫자로 자동 수집해 한눈에 볼 수는 없을까?

#3동작 예시

서비스 하나가 태스크 4개로 돌고 있을 때, CloudWatch 콘솔에서 그 서비스의 CPUUtilization 지표를 열면 4개 태스크의 CPU 사용률이 1분 단위 점으로 찍힌 그래프가 나온다. 어느 시각에 사용률이 치솟았는지, 지금 평소보다 높은지 낮은지를 접속 없이 바로 확인할 수 있다.

#4동작 과정

  1. 자동 수집Amazon ECS는 클러스터·서비스·태스크의 원시 데이터를 1분 단위로 CloudWatch에 자동 전송한다(별도 설정 없이도 클러스터·서비스 무료 지표가 제공된다). 이때부터 사람이 직접 붙지 않아도 수치가 쌓인다.
  2. 보관과 조회전송된 통계는 2주 동안 보관되어 과거 이력을 돌아볼 수 있다. 지금 값만이 아니라 지난주 같은 시간대와 비교하는 판단이 가능해진다.
  3. 상세 지표 확장태스크 단위의 CPU·메모리·EBS 파일시스템 사용률까지 보려면 CloudWatch Container Insights를 켠다. 이 경우 추가 비용이 발생하지만, 클러스터·서비스 수준을 넘어 개별 태스크 수준까지 관찰 범위가 넓어진다.

ECS가 클러스터·서비스·태스크의 자원 사용 데이터를 CloudWatch로 자동 흘려보내 사람이 직접 접속하지 않고도 성능을 숫자로 확인하게 하는 것

Container Insights

CloudWatch Container Insights가 컨테이너화된 애플리케이션과 마이크로서비스의 지표·로그를 수집·집계·요약해 세밀한 관찰성을 제공하는 기능.

#1문제 상황

기본 ECS 지표만으로는 클러스터와 서비스 수준의 큰 그림은 보이지만, 어느 태스크가, 어느 컨테이너가 문제인지까지는 좁혀지지 않는다. 태스크 수가 많아지면 서비스 평균값 뒤에 숨은 특정 태스크의 이상은 드러나지 않는다. 로그와 지표를 각각 따로 뒤져야 해서 원인 파악에 시간이 걸린다.

#2핵심 질문

클러스터 안에서 돌고 있는 컨테이너 하나하나의 성능 데이터를 계층별로 모아 한눈에 볼 수는 없을까?

#3동작 예시

클러스터에 서비스가 하나 있고 태스크가 여럿 돌 때, Container Insights를 켜면 클러스터·서비스·태스크 수준의 집계 지표가 CloudWatch 자동 대시보드에 나타난다. CPU·메모리·디스크·네트워크 사용률이 계층별로 표시되어, 서비스 전체가 아니라 특정 태스크의 사용률이 튀는 것을 골라낼 수 있다.

#4동작 과정

  1. 수집과 발견Container Insights가 클러스터에서 실행 중인 모든 컨테이너를 찾아내고, 성능 스택의 각 계층에서 성능 데이터를 모은다. 이 데이터는 구조화된 JSON 스키마를 쓰는 성능 로그 이벤트로 기록된다.
  2. 집계수집된 이벤트로부터 CloudWatch가 클러스터·서비스·태스크 수준의 상위 집계 지표를 만든다. 개별 기록이 계층별 지표로 요약되어 판단하기 쉬운 형태가 된다.
  3. 표시와 한계집계된 지표는 CloudWatch 자동 대시보드에서 볼 수 있다. 다만 지표는 지정한 시간 범위에 실행 중인 태스크의 리소스만 반영하므로, 실행 중인 태스크가 없으면 그 구간에는 값이 나타나지 않는다.

컨테이너 하나하나의 성능 데이터를 계층별로 수집·집계해 클러스터·서비스·태스크 수준의 세밀한 관찰성을 제공하는 것

이벤트와 EventBridge

Amazon ECS가 태스크·서비스·컨테이너 인스턴스의 상태 변화를 Amazon EventBridge 이벤트로 내보내 자동 대응과 자동화를 가능하게 하는 체계.

#1문제 상황

태스크가 예기치 않게 멈추거나 배포가 실패해도, 그 사실을 사람이 콘솔을 계속 열어보거나 로그를 뒤지기 전에는 알기 어렵다. 상태 변화가 생길 때마다 누군가 확인하고 손으로 대응하는 방식은 서비스가 늘어날수록 놓치기 쉽고 대응도 느려진다. 상태 변화를 자동으로 감지해 후속 작업을 붙일 통로가 필요하다.

#2핵심 질문

태스크와 서비스의 상태 변화를 자동으로 감지해 사람 개입 없이 대응 작업을 실행할 수는 없을까?

#3동작 예시

태스크 하나가 중지 상태로 바뀌면, Amazon ECS가 그 변화를 이벤트로 만들어 EventBridge로 보낸다. EventBridge에 규칙을 걸어 두면 그 이벤트가 도착하는 순간 Lambda 함수가 실행되어 담당자에게 알리거나 후속 처리를 수행할 수 있다. 콘솔을 지켜보지 않아도 상태 변화가 곧 대응으로 이어진다.

#4동작 과정

  1. 상태 추적과 생성Amazon ECS는 모든 태스크와 서비스의 상태를 추적하고, 상태가 바뀌면 이벤트를 생성해 EventBridge로 보낸다. 이벤트는 컨테이너 인스턴스 상태 변경, 태스크 상태 변경, 배포 상태 변경, 훅 상태 변경, 서비스 작업, 컨테이너 인스턴스 건강 변경 같은 유형으로 나뉜다.
  2. 전달과 중복 처리하나의 활동에 여러 이벤트가 생성되기도 한다. 예를 들어 컨테이너 인스턴스에서 태스크가 시작되면 새 태스크에 대한 태스크 상태 변경 이벤트와 컨테이너 인스턴스 상태 변경 이벤트가 함께 나온다. 그래서 이벤트를 소비하는 쪽은 같은 활동이 여러 번 통보될 수 있다는 점을 감안해야 한다.
  3. 자동 대응EventBridge 규칙에 Lambda, SNS 같은 대상을 연결하면 이벤트 도착 시 자동으로 후속 작업이 실행된다. 사람이 지켜보지 않아도 오류 대응과 알림이 자동으로 돌아간다.

#5한 줄 요약

ECS의 상태 변화를 이벤트로 내보내 자동 대응과 자동화를 가능하게 하는 것

상태 확인

컨테이너 정의에 지정한 healthCheck 명령을 주기적으로 실행해 컨테이너·태스크의 정상 여부를 판정하고 비정상 시 교체하는 기능.

#1문제 상황

컨테이너 프로세스가 살아 있어도 애플리케이션이 요청을 제대로 처리하지 못하는 경우가 있다. 프로세스만 돌고 있으면 정상으로 보이지만 실제로는 응답하지 않는 상태가 서비스에 남아 트래픽을 받을 수 있다. 컨테이너 이미지 안에 들어 있는 상태 확인은 태스크 정의에 명시되지 않으면 ECS가 감시하지 않아, 비정상 컨테이너가 그대로 유지되기 쉽다.

#2핵심 질문

컨테이너가 실제로 요청을 처리할 수 있는 상태인지 주기적으로 판정해 비정상인 것을 자동으로 걸러낼 수는 없을까?

#3동작 예시

태스크 정의에 상태 확인 명령을 넣어 두면, 컨테이너가 그 명령을 주기적으로 스스로 실행하고 종료 코드로 정상 여부를 판단한다. 명령이 실패를 알리는 종료 코드를 내면 그 컨테이너는 비정상으로 표시된다. 예를 들어 웹 서버의 상태를 확인하는 명령이 응답을 못 받으면 그 태스크는 UNHEALTHY가 된다.

#4동작 과정

  1. 정의태스크 정의를 만들 때 컨테이너마다 상태 확인을 설정한다. 상태 확인은 컨테이너 안에서 로컬로 실행되는 명령이며, 명령 문자열은 CMD로 인자를 직접 실행하거나 CMD-SHELL로 컨테이너의 기본 셸을 통해 실행한다.
  2. 실행과 판정태스크 정의에 상태 확인이 정의되면 컨테이너 안에서 그 검사 프로세스가 돌고, ECS는 종료 코드를 평가해 애플리케이션 건강을 판단한다. 이때 컨테이너 정의에 지정한 상태 확인 파라미터가 이미지에 들어 있던 Docker 상태 확인을 덮어쓴다.
  3. 상태 노출과 교체판정 결과는 HEALTHY·UNHEALTHY 같은 상태로 드러나고, 로드 밸런서의 상태 확인과 연계되어 비정상 컨테이너가 트래픽에서 빠지고 교체된다. 결과적으로 서비스에는 정상 컨테이너만 남는다.

메타데이터와 인트로스펙션

실행 중인 태스크·컨테이너가 자신과 환경에 대한 메타데이터를 조회하거나 컨테이너 에이전트 인트로스펙션 API로 진단 정보를 얻는 방법.

#1문제 상황

컨테이너 안에서 실행되는 코드는 자신이 어느 태스크의 일부인지, 어떤 네트워크 설정으로 돌고 있는지 스스로 알기 어렵다. 설정을 바꾸려면 외부에서 값을 밀어 넣거나, 태스크가 뜰 때마다 달라지는 정보를 사람이 찾아 전달해야 한다. 문제가 생겼을 때 컨테이너의 IP·서브넷·상태를 확인하려면 별도 경로를 거쳐야 해서 진단이 느려진다.

#2핵심 질문

실행 중인 컨테이너가 자기 자신과 주변 환경 정보를 직접 조회해 스스로 설정을 바꾸고 문제를 진단할 수는 없을까?

#3동작 예시

컨테이너 안에서 태스크 메타데이터 엔드포인트를 호출하면 그 태스크의 네트워크 모드와 IP 주소, 컨테이너의 Docker ID·이름·이미지 정보, 태스크 상태 같은 값이 응답으로 돌아온다. 애플리케이션은 이 값을 읽어 런타임 환경에 맞춰 설정을 조정할 수 있다.

#4동작 과정

  1. 제공 방식메타데이터는 태스크·컨테이너 수준 속성, IP·서브넷·네트워크 모드 같은 네트워크 설정, 태스크 상태와 건강 정보를 담는다. 이 정보는 컨테이너 메타데이터 파일이나 태스크 메타데이터 엔드포인트 등 여러 방법으로 볼 수 있다.
  2. 조회컨테이너 안의 애플리케이션은 환경 변수로 주어진 엔드포인트 주소를 통해 자기 태스크·컨테이너 정보를 요청한다. 이때 버전에 따라 응답 형식이 달라지며, 최신 v4를 쓰면 EC2·Fargate·Managed Instances 환경의 정보를 일관된 방식으로 얻는다.
  3. 활용얻은 정보로 런타임 환경에 맞춘 설정 변경과 문제 진단을 수행한다. 컨테이너 에이전트의 인트로스펙션 API를 쓰면 에이전트 자체의 진단 정보도 확인할 수 있어, 태스크가 왜 뜨지 않는지 같은 문제를 좁혀갈 수 있다.

ECS Exec와 감사 로깅

ECS Exec로 실행 중인 컨테이너에 원격 명령을 실행해 문제를 진단하고, CloudTrail 등으로 API 호출과 작업을 감사 기록으로 남기는 기능.

실행 중인 컨테이너 안을 들여다보려면 보통 호스트 인스턴스의 운영체제에 먼저 접속한 뒤 그 안에서 컨테이너로 들어가야 한다. 이를 위해 인바운드 포트를 열거나 SSH 키를 관리해야 하고, 접속 경로가 늘어날수록 보안 관리 부담도 커진다. 접속이 가능한 EC2 기반이 아니면 이런 방식 자체가 어렵다는 한계도 있다.

#2핵심 질문

호스트에 접속하거나 포트를 열지 않고도 실행 중인 컨테이너에 직접 명령을 실행해 진단할 수는 없을까?

#3동작 예시

개발자가 AWS CLI에서 ECS Exec로 명령을 실행하면, 호스트 운영체제를 거치지 않고 컨테이너 안에서 그 명령이 바로 돌아간다. 컨테이너 안의 프로세스 상태를 확인하거나 셸을 열어 설정을 점검할 수 있고, 이 과정에서 인바운드 포트를 열 필요가 없다.

#4동작 과정

  1. 명령 실행ECS Exec를 쓰면 Amazon ECS API, AWS CLI, AWS SDK, AWS Copilot CLI 같은 경로에서 실행 중인 Linux 또는 Windows 컨테이너에 명령을 넣거나 셸을 열 수 있다. EC2 인스턴스 위의 컨테이너든 Fargate 위의 컨테이너든 같은 방식으로 접근한다.
  2. 접근 통제이 기능을 선택적으로 켜고 끄면서 더 엄격한 접근 제어 정책을 유지할 수 있다. 필요한 때만 열어 두면 상시 SSH 접속 경로를 두지 않아도 된다.
  3. 감사 기록누가 어떤 API를 호출하고 어떤 작업을 했는지는 CloudTrail API 로깅으로 감사 기록에 남고, ECS Exec의 액션 로그를 켜면 세션 안에서 실행된 명령이 기록된다. 문제를 추적할 때 이 기록이 근거가 된다.

#1문제 상황

서비스가 여러 컨테이너에 걸쳐 요청을 처리하면, 어디서 응답이 느려지는지나 어느 구간에서 오류가 나는지가 한 컨테이너의 지표만으로는 드러나지 않는다. CPU 사용률이 정상이어도 응답 시간이 치솟는 경우가 있어 자원 지표만으로는 성능 병목을 짚기 어렵다. 요청이 지나간 경로를 따라가며 구간별 시간과 오류를 봐야 한다.

#2핵심 질문

요청이 애플리케이션 안에서 어떤 경로로 처리되며 어디서 느려지고 실패하는지 추적할 수는 없을까?

#3동작 예시

애플리케이션이 추적 데이터를 만들도록 설정하고 AWS Distro for OpenTelemetry 사이드카를 태스크에 붙이면, 사이드카가 그 추적 데이터를 모아 AWS X-Ray로 보낸다. X-Ray에서 요청 하나가 지나간 구간별 소요 시간과 발생한 오류·예외를 확인할 수 있어, 어느 지점이 병목인지 짚을 수 있다.

#4동작 과정

  1. 준비Amazon ECS가 AWS Distro for OpenTelemetry와 통합되어 애플리케이션의 추적 데이터를 수집한다. 이 통합을 쓰려면 태스크 역할을 만들어 태스크 정의에 지정해야 하며, 애플리케이션 쪽에서도 추적 데이터를 생성하도록 설정해야 한다.
  2. 수집과 라우팅태스크에 붙은 AWS Distro for OpenTelemetry 사이드카 컨테이너가 추적 데이터를 모아 AWS X-Ray로 전달한다. 애플리케이션 코드가 직접 전송 경로를 관리하지 않아도 된다.
  3. 분석X-Ray에서 오류와 예외를 찾아내고 성능 병목과 응답 시간을 분석한다. 같은 통합 경로로 애플리케이션 지표를 CloudWatch나 Amazon Managed Service for Prometheus로 내보내 자원 지표와 함께 볼 수 있다.

IAM 개요와 정책

Amazon ECS 요청을 인증하고 리소스 접근을 제어하기 위해 AWS Identity and Access Management(IAM)가 사용자·역할·정책으로 권한을 부여하는 방식의 개요.

#1문제 상황

AWS 계정에는 여러 사용자와 애플리케이션이 접근한다. 아무 제한이 없으면 각 사용자는 계정 안의 모든 ECS 클러스터·서비스·태스크를 보거나 바꿀 수 있고, 애플리케이션은 필요한 범위를 넘어 다른 리소스까지 건드릴 수 있다. 누가 로그인했는지, 그 사람에게 어떤 작업을 허용할지 정하는 체계가 없으면 사고가 나도 원인과 책임 범위를 가릴 수 없다.

그래서 계정마다 “누구를 인증하고, 누구에게 어떤 작업을 허용할 것인가”를 따로 관리해야 한다. 하지만 그 규칙을 서비스마다 각자 만들면 관리가 흩어지고, 권한을 회수할 때도 여러 곳을 확인해야 한다.

#2핵심 질문

ECS 리소스에 누가 접근해 어떤 작업을 할 수 있는지를 하나의 일관된 규칙으로 어떻게 정하고 검증할 수 있을까?

#3동작 예시

IAM 정책은 “작업(Action) + 리소스(Resource) + 허용/거부(Effect)”를 적은 JSON 문서다. 예를 들어 특정 ECS 서비스 하나에 대해서만 태스크 정의를 등록할 수 있게 하려면 ecs:RegisterTaskDefinition 작업을 허용하고, 대상은 그 리소스의 ARN(리소스를 식별하는 고유 문자열)으로 좁힌다. 이 문서를 사용자·역할에 붙이면 그 범위 밖의 작업은 자동으로 거부된다.

#4동작 과정

  1. 인증사용자나 역할이 AWS에 요청을 보내면 IAM이 그 주체가 누구인지 확인한다. 서명된 자격 증명이 있어야 요청이 통과한다.
  2. 권한 평가요청이 오면 IAM이 그 주체에 연결된 정책을 모아 작업·리소스·조건을 대조한다. 명시적 거부가 하나라도 있으면 그 요청은 막고, 허용이 있으면 통과시킨다.
  3. 결과 반영허용되면 ECS가 요청을 처리하고, 거부되면 접근이 차단된다. 태그 기반 조건을 쓰면 리소스에 붙은 태그로 대상 범위를 더 좁힐 수 있고, 새 리소스를 만들 때 태그를 지정하도록 강제할 수도 있다.

인증된 주체에게 작업·리소스·조건 단위로 권한을 부여하고 검증하는 하나의 규칙 체계

IAM 역할

태스크 실행·태스크·컨테이너 인스턴스 등 ECS 구성 요소가 다른 AWS 서비스를 호출할 때 맡는, 권한을 담은 IAM 역할.

#1문제 상황

ECS의 컨테이너와 서비스는 실행 중에 이미지를 가져오거나 로그를 보내거나 다른 AWS 서비스를 호출해야 한다. 이때 각 컨테이너에 사용자 자격 증명을 직접 넣어 두면, 자격 증명이 이미지와 설정 파일에 남아 유출되고 회전도 어렵다. 또 컴포넌트마다 필요한 권한이 다른데 하나의 자격 증명으로 다 처리하면 한 곳이 뚫렸을 때 나머지까지 위험해진다.

그래서 컴포넌트별로 “무엇을 할 수 있는지”를 따로 나눠 줄 주체가 필요하다.

#2핵심 질문

ECS를 구성하는 각 요소가 필요한 권한만 골라서, 자격 증명을 코드에 넣지 않고 다른 AWS 서비스를 호출하게 하려면 어떻게 해야 할까?

#3동작 예시

태스크 실행 IAM 역할은 ECS 자체가 대신 쓰는 역할이다. Fargate에서 프라이빗 ECR 저장소의 이미지를 당겨오거나 awslogs 로그 드라이버로 CloudWatch Logs에 로그를 보낼 때, ECS는 이 역할의 권한을 빌려 그 작업을 수행한다. 반면 태스크 IAM 역할은 컨테이너 안의 애플리케이션 코드가 쓰는 역할로, 코드가 S3 같은 다른 서비스를 호출할 때 그 권한이 적용된다.

#4동작 과정

  1. 역할 선택태스크 정의의 시작 유형(launch type)과 쓰는 기능에 따라 필요한 역할이 달라진다. 표를 보고 어떤 역할이 필요한지 정한다.
  2. 권한 부여정한 역할에 그 작업에 맞는 정책을 연결한다. 실행에 필요한 최소 권한만 넣는다.
  3. 전달과 사용태스크 실행 역할은 ECS가 플랫폼 수준에서 대신 사용하고, 태스크 역할은 컨테이너에 임시 자격 증명으로 주입되어 코드가 사용한다. 컨테이너 인스턴스 IAM 역할, ECS Anywhere IAM 역할, 로드 밸런서·CodeDeploy·EventBridge 인프라 역할도 각각 맡은 호출 범위에만 쓰인다.

#5한 줄 요약

컴포넌트마다 필요한 권한만 담은 역할을 따로 부여해 자격 증명 노출 없이 AWS 서비스를 호출하게 하는 것

AWS 관리형 정책과 서비스 연결 역할

AWS가 미리 만들어 제공하는 ECS 관리형 정책과, ECS가 사용자 계정의 리소스를 관리하도록 위임하는 서비스 연결 역할.

#1문제 상황

팀에 필요한 만큼만 권한을 주는 정책을 직접 작성하려면 시간과 전문 지식이 든다. 처음부터 세밀한 정책을 만들다 보면 권한이 빠져 기능이 동작하지 않거나, 반대로 너무 넓게 열어 보안이 약해지기 쉽다. 또 ECS가 사용자를 대신해 계정 안의 리소스를 관리해야 하는 경우에는 일반 정책과는 다른 위임 구조가 필요하다.

#2핵심 질문

직접 정책을 설계하지 않고도 흔한 사용 사례에 맞는 권한을 빠르게 주고, ECS가 계정 리소스를 안전하게 관리하도록 위임하려면 어떻게 해야 할까?

#3동작 예시

AWS 관리형 정책은 AWS가 미리 만들어 제공하는 정책으로, 일반적인 사용 사례를 담고 있어 그대로 붙이면 된다. 다만 AWS가 관리·갱신하며 사용자가 내용을 바꿀 수 없고, 새 기능이 나오면 권한이 추가되어 붙인 모든 주체에 반영된다. 서비스 연결 역할은 ECS가 사용자 계정의 리소스를 관리하도록 미리 정의된 방식으로 위임하는 역할로, 클러스터나 Managed Instances 같은 기능이 사용자를 대신해 동작할 때 쓰인다.

#4동작 과정

  1. 관리형 정책 선택흔한 사용 사례에는 AWS 관리형 정책을 붙여 시작한다. 콘솔 예제 정책을 출발점으로 삼아 필요에 맞게 권한을 빼거나 더할 수도 있다.
  2. 위임 구조 구성ECS가 계정 리소스를 관리해야 하면 서비스 연결 역할을 만든다. 이 역할은 ECS가 그 목적에 정의된 작업만 수행하도록 범위가 정해져 있다.
  3. 갱신과 폐기 관리AWS는 관리형 정책을 대신 갱신하고, 단계적으로 폐기되는 관리형 정책은 미리 마이그레이션한다. 예를 들어 AmazonECS_FullAccess 같은 정책의 변경 사항을 확인해 붙인 주체가 영향을 받지 않도록 관리한다.

#5한 줄 요약

AWS가 관리하는 사전 정의 정책과 위임 전용 서비스 연결 역할로, 직접 설계 부담 없이 목적에 맞는 권한을 안전하게 부여하는 것

콘솔 권한

사용자가 Amazon ECS 콘솔에서 서비스·태스크 등을 보고 조작하는 데 필요한 추가 IAM 권한의 집합.

#1문제 상황

사용자에게 ECS 작업 자체에 대한 권한만 주면 콘솔 화면은 열리지만 일부 기능이 동작하지 않는다. 예를 들어 서비스를 만들거나 태스크 정의를 등록할 때는 ECS 권한 외에 IAM 역할 생성, EventBridge 규칙 생성 같은 부가 작업에 대한 권한이 함께 필요하다. 이런 추가 권한이 없으면 콘솔에서 버튼을 눌러도 중간에 실패한다.

#2핵심 질문

ECS 콘솔에서 서비스·태스크·배포 같은 기능을 정상적으로 보고 조작하려면 어떤 추가 권한까지 함께 줘야 할까?

#3동작 예시

최소 권한 원칙을 지키면서 콘솔을 쓰려면 AmazonECS_FullAccess 관리형 정책을 템플릿 삼아 자기 요구에 맞게 권한을 빼거나 더한 사용자 지정 정책을 만든다. 예를 들어 태스크 정의를 등록하려면 ECS 작업 권한에 더해 태스크 실행 IAM 역할을 만들 권한이 필요하고, 작업 예약용 EventBridge 규칙을 만들려면 그에 해당하는 권한이 필요하다. 이런 권한은 콘솔에서 쓰기 전에 IAM에서 미리 역할을 만들어 두면 확보된다.

#4동작 과정

  1. 필요 권한 파악콘솔에서 하려는 조작 목록을 보고 각 조작이 추가로 요구하는 권한을 확인한다. 외부 인스턴스 등록, 태스크 정의 등록, EventBridge 규칙 생성 등이 대표적이다.
  2. 권한 부여확인한 권한을 사용자·역할에 붙인다. AmazonECS_FullAccess를 템플릿으로 삼아 실제 필요한 범위만 남긴다.
  3. 기능별 확인CloudFormation 콘솔 사용, blue/green 배포의 Lambda 권한, 서비스 자동 스케일링 권한, 서비스 배포 보기 권한처럼 기능별로 추가 권한이 필요한지 점검한다.

#1문제 상황

ECS는 AWS가 관리하는 서비스지만, 사용자가 네트워크 경로와 접근 범위를 어떻게 구성하느냐에 따라 보안 수준이 달라진다. API 호출이 인터넷을 통해 이뤄지면 트래픽이 외부 경로에 노출될 수 있고, 누가 어떤 출처에서 접근하는지 제한하지 않으면 예상치 못한 곳에서 요청이 들어온다. 관리형 서비스라서 AWS가 다 책임진다고 가정하면 사용자가 반드시 해야 할 네트워크 통제를 놓치게 된다.

#2핵심 질문

ECS 트래픽을 외부 노출 없이 안전하게 전달하고, AWS와 사용자 사이의 책임 범위를 명확히 나누려면 어떻게 해야 할까?

#3동작 예시

ECS API는 AWS가 게시한 API 호출로 접근하며, 클라이언트는 TLS 1.2 이상을 지원해야 한다. VPC 엔드포인트(PrivateLink)를 쓰면 인터넷을 거치지 않고 VPC 내부에서 ECS API에 도달할 수 있다. 또한 ECS는 리소스 기반 접근 정책을 지원해 소스 IP 주소 같은 조건으로 접근을 제한할 수 있으므로, 허용할 출처를 정책에 명시해 다른 곳에서 오는 요청을 막을 수 있다.

#4동작 과정

  1. 전송 구간 보호모든 API 호출에 TLS를 적용하고 순방향 비밀성(PFS)을 제공하는 암호 스위트를 쓴다. 전송 중 데이터를 보호한다.
  2. 네트워크 경로 통제VPC 엔드포인트로 트래픽을 AWS 네트워크 안에 머물게 해 인터넷 노출을 줄인다.
  3. 책임 범위 정리AWS는 관리형 서비스의 기반 인프라를 보호하고, 사용자는 접근 정책·네트워크 구성 등 자기 환경의 통제를 맡는다. 이 공유 책임 모델에 따라 남은 통제 항목을 점검한다.

#1문제 상황

규제 산업에서는 서비스가 특정 규정 준수 프로그램의 적용 범위에 들어가는지 확인하고 감사 자료를 남겨야 한다. 그런데 어떤 서비스가 어떤 프로그램에 포함되는지는 서비스마다 다르고, 데이터 민감도와 회사 정책에 따라 사용자 책임도 달라진다. 이 범위를 확인하지 않고 도입하면 나중에 감사에서 근거를 제출하지 못한다.

#2핵심 질문

Amazon ECS가 어떤 규정 준수 프로그램의 적용 범위에 포함되는지 어떻게 확인하고, 그에 맞는 증적과 책임을 어떻게 준비할까?

#3동작 예시

#4동작 과정

  1. 범위 확인AWS 서비스 범위 목록에서 관심 프로그램(예: PCI, HIPAA, FedRAMP)을 선택해 ECS가 포함되는지 본다.
  2. 증적 확보AWS Artifact에서 감사 보고서를 내려받아 규정 준수 근거로 보관한다.
  3. 책임 점검사용 데이터의 민감도와 회사 정책에 따라 남는 규정 준수 책임을 확인한다. 새 AWS 가입 환경은 규제 워크로드용으로 설계되지 않았으므로, 필요하면 고급 기능을 활성화해 대응한다.

#1문제 상황

컨테이너 이미지는 공격에 대한 첫 방어선이다. 불필요한 실행 파일과 패키지 관리자·셸이 그대로 들어 있는 이미지는, 공격자가 컨테이너 경계를 벗어나 호스트까지 접근할 발판을 제공한다. 실행 중인 태스크에서 이상 행위가 일어나도 이를 감지하지 못하면 침해를 늦게 발견하게 된다.

#2핵심 질문

태스크와 컨테이너를 만들고 실행하는 전 과정에서 공격 표면을 줄이고 침해를 조기에 감지하려면 무엇을 지켜야 할까?

#3동작 예시

이미지는 필요한 애플리케이션과 런타임 의존성만 담은 distroless 이미지로 만든다. 이런 이미지에는 패키지 관리자나 셸이 없어 스캐너가 잡아내는 잡음이 줄고, 공격자가 컨테이너 안에서 쓸 수 있는 도구도 줄어든다. 여기에 읽기 전용 루트 파일 시스템과 최소 권한, 시크릿 관리를 함께 적용하고, GuardDuty 런타임 모니터링으로 실행 중인 태스크의 이상 행위를 감시한다.

#4동작 과정

  1. 이미지 최소화불필요한 바이너리를 제거하고 distroless 이미지를 쓴다. 낯선 공개 이미지는 각 레이어 내용을 확인한다.
  2. 실행 권한 축소읽기 전용 루트 파일 시스템과 최소 권한을 적용하고, 민감 데이터는 시크릿으로 관리해 이미지·설정에 남기지 않는다.
  3. 런타임 감시GuardDuty 런타임 모니터링을 켜서 실행 중 이상 행위를 감지한다. Fargate는 런타임 모니터링이 자동 관리되고, EC2는 보안 에이전트를 직접 관리하며 업데이트하고 문제를 해결한다.

서비스 쿼터와 API 사용

Amazon ECS의 리소스·API 서비스 쿼터(한도)와 API 호출 스로틀링, 멱등성 같은 API 사용 규칙을 이해하는 영역이다.

#1문제 상황

Amazon ECS는 Elastic Load Balancing, AWS Cloud Map, Amazon EC2 같은 여러 AWS 서비스와 긴밀하게 연동되어 서비스 로드 밸런싱, Service Connect, 태스크 네트워킹, 클러스터 오토 스케일링 같은 기능을 제공합니다. 이렇게 여러 서비스가 맞물려 동작하다 보니, 각 서비스에는 성능과 자원 활용을 일정하게 유지하기 위한 서비스 쿼터와 API 호출 속도 제한이 걸려 있습니다. 이런 제한을 모른 채 워크로드를 한꺼번에 늘리면 API 호출이 거부되거나 리소스 생성이 실패해 예상치 못한 성능 저하가 생깁니다.

#2핵심 질문

워크로드를 안전하게 확장하려면 어떤 서비스 쿼터와 API 호출 제한을 미리 알고 대비해야 하는가?

#3동작 예시

클러스터의 태스크 수를 한 번에 크게 늘리는 배포를 실행한다고 합시다. 이때 ECS는 태스크마다 RunTask 같은 API를 호출하고, 그 과정에서 로드 밸런서 등록이나 Cloud Map 서비스 검색 등록을 위해 연동 서비스의 API도 함께 호출합니다. 초당 호출 수가 정해진 속도 제한을 넘으면 초과된 호출은 오류로 돌아오고, 그 태스크는 시작되지 못합니다. 그래서 사전에 쿼터와 속도 제한을 확인하고 호출을 나눠 보내야 전체 확장이 끝까지 성공합니다.

#4동작 과정

  1. 쿼터 확인계정에 걸린 ECS 및 연동 서비스의 서비스 쿼터(예: 동시 실행 Fargate 태스크 수)와 API 속도 제한을 먼저 확인합니다. 그래서 지금 계획한 규모가 한도 안에 들어오는지 미리 판단할 수 있습니다.
  2. 한도 상향 요청계획한 규모가 기본 쿼터를 넘으면 콘솔의 쿼터 관리 화면 등에서 상향을 요청합니다. 그래서 확장 시점에 한도에 막히지 않도록 미리 여유를 확보합니다.
  3. 호출 분산과 재시도API 호출을 한꺼번에 몰아 보내지 않고 나눠 보내며, 속도 제한으로 거부된 호출은 지수 백오프 같은 방식으로 다시 시도합니다. 그래서 대규모 확장도 거부 오류 없이 안정적으로 완료됩니다.

#5한 줄 요약

ECS와 연동 서비스의 서비스 쿼터와 API 속도 제한을 미리 파악해 확장 규모를 계획하고 호출을 분산함으로써, 대규모 운영에서도 성능 저하 없이 워크로드를 늘릴 수 있게 하는 것

#2핵심 질문

중지된 태스크가 남긴 오류 코드를 보고 실패 원인을 어떻게 좁혀낼 수 있는가?

#3동작 예시

태스크가 시작 직후 바로 중지됐고 오류 메시지에 ResourceInitializationError가 적혀 있다고 합시다. 이 범주는 태스크가 시작되기 전에 필요한 자원을 준비하는 단계에서 실패했다는 뜻으로, 대개 이미지를 받아오지 못했거나 실행에 필요한 IAM 역할·네트워크 설정이 잘못된 경우입니다. 이런 식으로 오류 코드의 범주를 보면 어느 단계에서 막혔는지 방향이 잡히고, 그 범주에 맞는 해결 절차를 찾아 들어갈 수 있습니다.

#4동작 과정

  1. 오류 확인콘솔의 중지된 태스크 오류 보기나 DescribeTasks 같은 API로 중지 이유 메시지를 확인합니다. 그래서 실패한 태스크가 남긴 오류 코드를 확보합니다.
  2. 범주 분류오류 코드를 TaskFailedToStart, ResourceInitializationError, ResourceNotFoundException, SpotInterruptionError, InternalError, OutOfMemoryError, CannotPullContainer 같은 범주로 나눕니다. 그래서 문제가 시작 단계인지, 자원·권한·이미지·용량 부족 중 어디인지 좁힐 수 있습니다.
  3. 원인별 해결범주에 맞는 절차를 적용합니다. 예를 들어 이미지 문제면 태스크 연결(네트워크·엔드포인트)을 확인하고, 권한 문제면 태스크 IAM 역할이 요청한 권한을 갖는지 봅니다. 그래서 같은 오류가 다시 나지 않도록 근본 원인을 제거합니다.

#1문제 상황

ECS 서비스에서 배포가 실패하거나 태스크가 계속 비정상으로 죽는 문제가 생기면, 사용자는 어디서부터 확인해야 할지 막막합니다. 태스크 하나하나를 뒤져도 서비스 차원에서 무슨 일이 일어나는지는 보이지 않고, 배치가 실패한 것인지 오토 스케일링이 문제인지 구분이 안 됩니다. 그래서 서비스가 스스로 남기는 진단 정보를 확인하는 절차가 필요합니다.

#2핵심 질문

서비스 문제를 진단할 때 가장 먼저 확인해야 할 서비스 이벤트는 무엇을 말해주는가?

#3동작 예시

서비스 배포가 끝나지 않고 태스크가 계속 비정상으로 바뀐다고 합시다. 서비스 이벤트 로그를 보면 service (서비스이름) 접두사가 붙은 최근 이벤트들이 보이고, 그 안에 태스크 배치 시도와 인스턴스 상태 판단 결과가 남아 있습니다. 또한 오토 스케일링이 설정된 서비스라면 Message 접두사가 붙은 이벤트도 함께 보여, 스케일링 조정이 있었는지 확인할 수 있습니다. 이렇게 이벤트를 보면 문제가 배치 쪽인지 스케일링 쪽인지 방향이 갈립니다.

#4동작 과정

  1. 이벤트 수집DescribeServices API, AWS CLI, 또는 콘솔로 서비스 이벤트를 가져옵니다. 이때 API로는 서비스 스케줄러가 남긴 최근 배치·인스턴스 상태 이벤트만 오고, 콘솔은 스케줄러 이벤트와 오토 스케일링 이벤트를 함께 보여줍니다.
  2. 접두사로 출처 구분service (서비스이름) 접두사는 태스크 배치·인스턴스 상태, Message 접두사는 Application Auto Scaling 조정 이벤트입니다. 그래서 어떤 종류의 문제인지 출처를 나눠 볼 수 있습니다.
  3. 중복 제거와 캡처원인이 해결되거나 6시간이 지날 때까지 같은 이벤트는 반복 표시되지 않고 최근 100개만 보여주므로, 필요하면 이벤트 캡처를 켜서 나중에 분석할 수 있게 남깁니다. 그래서 원인을 놓치지 않고 추적할 수 있습니다.

#1문제 상황

ECS에서 도는 컨테이너 안의 문제를 진단하려면 원래는 호스트 컨테이너 운영체제에 먼저 접속한 뒤 다시 컨테이너로 들어가야 했습니다. 이를 위해 인바운드 포트를 열거나 SSH 키를 관리해야 했고, Fargate처럼 호스트에 접근할 수 없는 환경에서는 이 방법 자체가 막혔습니다. 그래서 실행 중인 컨테이너에 직접 들어가 로그와 상태를 확인할 손쉬운 방법이 필요했습니다.

#2핵심 질문

호스트 운영체제에 접속하거나 포트를 열지 않고 실행 중인 컨테이너 안을 진단할 수 있는가?

#3동작 예시

개발 중인 컨테이너에서 어떤 프로세스가 예상과 다르게 동작한다고 합시다. ECS Exec를 쓰면 Amazon EC2 인스턴스에서 도는 컨테이너든 AWS Fargate에서 도는 컨테이너든 상관없이, 호스트 OS에 들어가지 않고 ECS API·AWS CLI·AWS SDK·Copilot CLI를 통해 그 컨테이너에 명령을 실행하거나 셸을 열 수 있습니다. 이렇게 하면 실행 중인 애플리케이션의 상태와 로그를 그 자리에서 바로 확인할 수 있습니다.

#4동작 과정

  1. 기능 켜기서비스나 태스크에서 ECS Exec를 선택적으로 활성화합니다. 그래서 필요할 때만 진단 통로를 열어 접근 제어를 더 엄격하게 유지할 수 있습니다.
  2. 컨테이너 접속활성화한 뒤 API·CLI·SDK·Copilot CLI로 실행 중인 Linux 또는 Windows 컨테이너에 명령을 실행하거나 셸을 엽니다. 그래서 호스트 OS 접속이나 인바운드 포트 개방 없이 컨테이너 안으로 들어갑니다.
  3. 진단 정보 수집컨테이너 안에서 로그와 프로세스 상태를 확인하고, 필요하면 컨테이너 에이전트 로그·Docker 진단 정보를 함께 수집합니다. 그래서 운영 중 문제를 빠르게 파악하고 조치할 수 있습니다.

Managed Instances와 외부 인스턴스 문제 해결

AWS가 관리하는 Managed Instances와 온프레미스 외부 인스턴스(ECS Anywhere)에서 발생하는 문제를 진단하고 해결하는 절차다.

#1문제 상황

Amazon ECS Managed Instances나 온프레미스 외부 인스턴스(ECS Anywhere)에서 태스크가 정상적으로 뜨지 않는 문제가 생기면, 일반 EC2 환경과 진단 경로가 달라 원인을 찾기 어렵습니다. 인스턴스 자체는 보이는데 컨테이너 에이전트가 제대로 붙지 않거나 API 호출이 실패해도, 그 실패 사유가 어디에 남는지 모르면 조치를 못 합니다. 그래서 이런 환경에 맞는 진단 절차와 확인 지점이 필요합니다.

#2핵심 질문

Managed Instances와 외부 인스턴스에서 태스크가 실패할 때 어디를 보고 원인을 판단해야 하는가?

#3동작 예시

Managed Instances 용량 공급자를 쓰는 클러스터에서 태스크가 계속 시작되지 않는다고 합시다. 이때는 먼저 AWS CLI가 설치·구성되어 있고 클러스터에 Managed Instances 용량 공급자에 대한 접근 권한이 있는지 확인합니다. 그다음 컨테이너 에이전트 로그를 보기 위해 권한 있는 컨테이너에 접속해 로그 파일을 확인합니다. 여기서 에이전트가 AWS API 호출에 실패한 기록이 있으면, 그 실패 사유를 단서로 권한·네트워크 같은 원인을 좁힐 수 있습니다.

#4동작 과정

  1. 사전 요구 확인AWS CLI 설치·구성과 Managed Instances 용량 공급자가 있는 클러스터 접근 권한을 확인합니다. 그래서 진단 자체가 환경 문제로 막히지 않게 합니다.
  2. 에이전트 로그 확인권한 있는 컨테이너에 접속해 Managed Instances의 컨테이너 에이전트 로그를 확인합니다. 그래서 에이전트가 태스크 배치나 AWS API 호출에서 어디서 실패했는지 직접 봅니다.
  3. 실패 사유 분석로그에 남은 API 실패 사유를 근거로 원인을 판단합니다. Fargate 스로틀링 쿼터 같은 한도에 걸린 경우도 있으므로, 자원·권한·한도를 함께 점검해 조치합니다.

#5한 줄 요약

Managed Instances와 외부 인스턴스에서 컨테이너 에이전트 로그와 AWS API 실패 사유를 확인해, 일반 EC2와 다른 환경에서도 실패 원인을 정확히 짚어내는 것

태깅과 사용 보고서

클러스터·서비스·태스크 같은 리소스에 태그를 붙여 분류하고, 사용 보고서로 사용량과 비용을 분석하는 기능이다.

#1문제 상황

클러스터·서비스·태스크 같은 ECS 리소스가 많아지면, 어떤 리소스가 누구 것이고 어느 환경·목적에 속하는지 구분하기 어려워집니다. 같은 유형의 리소스가 계속 늘어나면 목록만 봐서는 특정 리소스를 골라내기 힘들고, 비용과 사용량이 어디서 발생하는지도 파악되지 않습니다. 그래서 리소스에 분류 기준을 붙여 관리하고 비용을 분석할 방법이 필요합니다.

#2핵심 질문

많은 ECS 리소스를 목적·소유자·환경별로 구분하고 그 사용량과 비용을 분석하려면 어떻게 해야 하는가?

#3동작 예시

여러 환경을 함께 운영하는 계정에서 컨테이너 인스턴스에 태그를 붙인다고 합시다. 각 인스턴스에 소유자와 스택 단계 같은 태그를 정의해 두면, 같은 유형의 인스턴스가 많아도 어떤 인스턴스가 누구 것이고 어느 단계에 속하는지 바로 식별할 수 있습니다. 이렇게 붙인 태그는 Cost and Usage 보고서와 함께 사용할 수 있어, ECS 리소스의 비용과 사용량을 목적별로 나눠 분석할 수 있습니다.

#4동작 과정

  1. 태그 설계각 리소스에 붙일 태그 키와 선택적 값의 집합을 목적·소유자·환경 기준으로 정합니다. 그래서 여러 리소스를 일관된 기준으로 분류할 수 있습니다.
  2. 태그 부착콘솔이나 API로 클러스터·서비스·태스크, EC2 컨테이너 인스턴스, 외부 인스턴스 등에 태그를 붙입니다. 그래서 리소스를 빠르게 식별하고 추적할 수 있습니다.
  3. 보고서 활용붙인 태그를 사용 보고서와 Cost and Usage 보고서에 연결해 분석합니다. 이때 태그에는 민감한 데이터를 넣지 않는 것이 좋습니다. DescribeTags 접근을 막아도 다른 API가 태그를 돌려줄 수 있으므로 태그 자체를 안전하게 설계해야 합니다.

#5한 줄 요약

ECS 리소스에 목적·소유자·환경 태그를 붙여 분류하고, 그 태그를 사용·비용 보고서에 연결해 사용량과 비용을 목적별로 분석하게 하는 것
