1ECS 전체상과 핵심 객체01-01

ECS란 무엇인가와 3계층 구조

ECS는 컨테이너 애플리케이션의 배포·관리·확장을 대신해 주는 AWS 완전관리형 컨테이너 오케스트레이션 서비스로, 용량·컨트롤러·프로비저닝 3계층으로 이뤄진다.

#1문제 상황

기존에는 컨테이너를 직접 실행하려면 서버를 준비하고 스케줄링과 복구 방식을 운영자가 정해야 했다. 배포할 서버를 고르고 장애 시 다시 띄우는 절차도 직접 관리해야 했다.

이 방식은 컨테이너 수가 늘면 배치 위치와 장애 대응을 일일이 판단해야 해서 운영 부담이 커진다. 리전이 바뀌면 같은 구성을 다시 맞추는 작업도 반복된다.

#2핵심 질문

서버와 배치 관리를 직접 하지 않고 컨테이너 애플리케이션의 배포와 확장을 맡길 수는 없을까?

#3동작 예시

작업 정의를 등록한 뒤 Fargate 용량을 지정해 서비스를 실행하면 ECS가 컨테이너를 배치하고 원하는 개수를 유지한다. 운영자는 클러스터 안에서 실행 상태와 확장 결과만 확인한다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 클러스터와 역할 준비클러스터를 만들고 인프라 역할(기반 시설 관리 권한)과 인스턴스 프로필(에이전트 실행 권한)을 준비하므로 실행 기반이 갖춰진다.
  2. 태스크 정의와 서비스 생성Managed Instances에 맞는 정의를 등록하고 서비스를 만들면 AWS가 인스턴스를 준비해 태스크를 올리므로 직접 서버를 다루지 않아도 된다.
  3. 실행 확인과 정리서비스 상태를 조회해 실행을 확인한 뒤 리소스를 정리하므로 첫 실행 절차가 끝난다.

#4동작 과정

  1. 런치타입으로 직접 지정태스크에 EC2, Fargate, External 중 하나를 정해 실행하므로 구조가 단순해지지만 여러 용량을 섞기 어렵다.

  3. 권장 방식으로 선택세밀한 용량 관리가 필요하면 공급자 전략을 고르므로 성능과 비용 균형을 맞추기 쉬워진다.

#3동작 예시

#4동작 과정

#3동작 예시

#4동작 과정

  1. 설계도 작성작업 정의(실행 조건을 적은 JSON 문서)에 용량(작업이 올라가는 기반 시설)과 이미지와 CPU와 메모리와 네트워크 방식(통신 연결 방법)과 로그 설정을 적으면 실행 기준이 된다.

  3. 실행 방식 고르기작업(한 번 실행하는 단위)으로 직접 실행하거나 서비스(원하는 개수를 유지하는 실행 방식)로 실행하면 상태에 맞는 실행이 이어진다.

작업 정의 만들기·갱신·등록취소·삭제

#1문제 상황

기존에는 JSON 파일을 직접 작성해 작업 정의를 등록할 때 오타와 불필요한 항목과 필수 항목 누락이 잦았다. 등록에 실패한 원인을 찾기 어려워 동일한 수정을 반복하는 경우가 많았다. 쓰지 않는 예전 버전이 쌓여 어떤 버전을 써야 하는지도 헷갈렸다.

#2핵심 질문

콘솔에서 오류를 줄이며 만들고 고치고 쓰지 않는 버전은 정리하려면 어떻게 해야 할까?

#3동작 예시

콘솔의 JSON 편집기에서 familyName(버전 묶음 이름)과 containerDefinitions(컨테이너 목록)를 포함한 정의를 작성하고 형식과 불필요한 키를 검사한다. Amazon Q 추천은 참고만 하고 확정한 뒤 등록하며 외부 실행은 requiresCompatibilities(호환 실행 방식 항목)를 외부 값으로 지정한다.

#4동작 과정

  1. 새로 만들기콘솔 경험(화면 안내 입력)이나 JSON 파일로 작업 정의를 만들면 실행할 프로그램 윤곽이 등록된다.
  2. 고쳐서 등록설정을 바꾸면 새 리비전(버전 번호가 붙은 정의)으로 등록되므로 이전 버전과 구분해 실행할 수 있다.
  3. 등록 취소·삭제쓰지 않는 리비전은 등록 취소(실행 대상에서 제외)와 삭제(목록에서 제거)로 정리하면 혼선이 줄어든다.

#1문제 상황

#2핵심 질문

프로그램 구조에 맞게 나누고 크기를 정해 빠르고 안정적으로 실행하려면 어떻게 해야 할까?

#3동작 예시

#4동작 과정

  1. 구조 나누기용도가 동일한 컨테이너를 작업 정의(실행 조건 묶음)로 묶고 다른 처리는 별도 정의로 나누면 각각 따로 확장할 수 있다.
  2. 크기 정하기CPU(처리 능력)와 메모리(기억 공간)를 처리 특성에 맞게 정하고 크기 모범 사례를 적용하면 남거나 부족한 자원이 줄어든다.
  3. 속도 다듬기이미지와 네트워크 방식(통신 연결 방법)과 용량 구성을 정리하고 실행 시간 최적화(시작을 빠르게 하는 조정)를 적용하면 시작이 빨라진다.

#1문제 상황

기존에는 컨테이너 하나가 죽으면 작업 전체를 교체해야 했다. 일시적인 실패인데도 새 작업을 시작하므로 복구가 느렸다. 개별 컨테이너만 다시 시작하는 설정이 없어 가용성을 유지하기 어려웠다.

#2핵심 질문

작업 전체를 교체하지 않고 종료된 개별 컨테이너만 다시 시작하려면 어떻게 해야 할까?

#3동작 예시

작업 정의의 컨테이너 항목에 재시작 정책을 켜고 다시 시작하지 않을 종료 코드를 지정한다. 컨테이너가 해당 코드以外로 종료되면 작업 교체 없이 해당 컨테이너만 다시 시작한다. 일정 시간 이상 정상 실행된 뒤에만 재시도하도록 두어 반복 실패를 줄인다.

#4동작 과정

  1. 정책 활성화필수와 비필수 컨테이너 정의에 재시작 정책을 켜서 개별 재시작을 허용한다.
  2. 예외 지정다시 시작하지 않을 종료 코드(성공을 뜻하는 코드)를 지정해 불필요한 재시작을 막는다.
  3. 개별 재시작종료 발생 시 작업 교체 없이 해당 컨테이너만 다시 시작해 가용성을 유지한다.

#5한 줄 요약

종료된 개별 컨테이너만 작업 안에서 다시 시작해 가용성을 유지하는 것

#2핵심 질문

GPU와 Neuron, 딥러닝과 ARM 실행에 필요한 자원을 작업 정의에 어떻게 명시해야 할까?

#3동작 예시

작업 정의에서 컨테이너 단위로 필요한 GPU 수를 지정하고 GPU 지원 인스턴스로 클러스터를 구성한다. 스케줄러는 GPU가 있는 인스턴스를 골라 물리 GPU를 해당 컨테이너에 연결한다. Neuron과 딥러닝, ARM 실행도 용도에 맞는 자원 요구와 실행 환경을 정의에 명시해 배치한다.

#4동작 과정

  1. 자원 명시작업 정의에 컨테이너 단위로 필요한 가속 장치 수를 적어 배치 조건을 만든다.
  2. 인스턴스 준비해당 장치를 지원하는 GPU 최적화 이미지와 인스턴스로 클러스터를 구성한다.
  3. 연결 배치스케줄러가 조건에 맞는 인스턴스를 골라 물리 장치를 해당 컨테이너에 연결한다.

비AWS 이미지와 private 인증

ECR 밖 이미지를 쓸 때는 private 인증 정보를 작업 정의·인스턴스에 설정한다.

#1문제 상황

기존에는 Amazon ECR에 있는 이미지를 작업 정의에 적으면 별도 로그인 설정 없이 이미지를 받아와 실행할 수 있었다. ECR 밖에 있는 사설 레지스트리의 이미지는 로그인이 필요했는데 작업 정의에 인증 정보 연결 방법이 없으면 이미지를 받지 못해 태스크가 시작되지 않았다.

#2핵심 질문

ECR 밖에 있는 사설 레지스트리 이미지를 인증을 거쳐 태스크에서 어떻게 받아와 실행할 수 있을까?

#3동작 예시

사설 레지스트리 계정 정보를 AWS Secrets Manager(자격 증명을 보관하는 저장 서비스)에 넣어 두고 작업 정의에 이미지 주소와 함께 그 참조를 적어 둔다. 태스크가 시작되면 ECS가 저장된 자격 증명으로 외부 레지스트리에 로그인한 뒤 이미지를 받아와 컨테이너를 실행한다.

#4동작 과정

  1. 자격 증명 저장사설 레지스트리 계정 정보를 AWS Secrets Manager(자격 증명을 보관하는 서비스)에 저장한다, 그래서 비밀번호를 작업 정의에 직접 적지 않는다.
  2. 작업 정의에 참조이미지 주소와 Secrets Manager 참조를 작업 정의(컨테이너 실행 명세)에 적는다, 그래서 실행 대상과 인증 수단이 함께 정해진다.
  3. 실행 시 인증과 수신Fargate와 EC2 인스턴스, Amazon ECS Anywhere의 외부 인스턴스에서 시작될 때 저장된 자격 증명으로 로그인하고 이미지를 받는다, 그래서 ECR 밖 이미지도 실행된다.

Windows·gMSA 컨테이너 특화

Windows 컨테이너는 EC2·Fargate별 작업 정의 차이를 따르고, 도메인 계정이 필요하면 gMSA를 쓴다.

#1문제 상황

기존에는 Linux용 작업 정의를 그대로 쓰면 컨테이너 정의의 여러 파라미터가 그대로 적용되어 실행 방식을 그대로 옮길 수 있었다. Windows EC2 인스턴스에서는 지원하지 않는 파라미터가 있고 다르게 동작하는 항목이 있어 그대로 복사하면 실행이 실패하거나 의도한 격리와 설정이 적용되지 않았다.

#2핵심 질문

Windows 컨테이너 태스크를 EC2와 Fargate 환경 차이에 맞추고 도메인 계정이 필요할 때 어떻게 실행할 수 있을까?

#3동작 예시

Windows용 작업 정의에서는 컨테이너 수준 CPU와 메모리를 지정하고 EC2 Windows에서 지원하지 않는 disableNetworking이나 privileged 같은 항목을 빼고 작성한다. 도메인 계정으로 동작해야 하는 컨테이너에는 gMSA(도메인 계정을 대신하는 관리형 서비스 계정) 설정을 붙여 Active Directory 권한으로 실행한다.

#4동작 과정

  1. Windows용 정의 조정EC2 Windows에서 지원하지 않거나 다르게 동작하는 작업 정의 파라미터를 제외하고 작성한다, 그래서 지원 범위 안에서 실행이 가능해진다.
  2. 리소스와 역할 지정컨테이너 수준 CPU와 메모리를 지정하고 IAM 역할(IAM roles for tasks, 컨테이너에 부여하는 권한)을 EC2 Windows용 추가 구성과 함께 붙인다, 그래서 필요한 권한과 자원이 확보된다.
  3. gMSA 연결도메인 계정이 필요하면 gMSA(도메인 인증을 대신하는 관리형 계정) 설정을 붙인다, 그래서 도메인 자원 접근이 가능한 상태로 컨테이너가 동작한다.

#5한 줄 요약

Windows 컨테이너 실행 규칙 차이를 반영해 작업 정의를 조정하고 필요할 때 gMSA로 도메인 권한을 부여하는 방식

EC2 태스크 네트워킹 모드

EC2 태스크는 awsvpc·host·bridge 중 하나로 붙으며, 모드마다 DNS·포트·격리 특성이 다르다.

#1문제 상황

기존에는 EC2 인스턴스 위에서 컨테이너를 올리면 인스턴스의 네트워크를 그대로 나누어 쓰는 방식이 기본이었다. 이 방식에서는 태스크별 주소와 격리 수준, DNS와 포트 처리 방식이 고정되어 태스크 단위 보안 그룹과 주소 관리가 어려웠다.

#2핵심 질문

EC2 위 태스크에 awsvpc와 host, bridge 중 어떤 네트워크 모드를 붙여 주소와 격리를 어떻게 다르게 할 수 있을까?

#3동작 예시

작업 정의에 awsvpc(태스크마다 네트워크 인터페이스를 주는 모드)를 지정하면 태스크가 독자적인 ENI(탄력적 네트워크 인터페이스, 가상 네트워크 카드)와 기본 프라이빗 주소를 받아 EC2 인스턴스와 같은 방식으로 통신한다. bridge(리눅스용 Docker 내장 가상 네트워크, bridge 드라이버 방식)를 쓰면 인스턴스 안의 가상 네트워크를 공유하며 Linux 기본값으로 동작한다.

#4동작 과정

  1. 모드 선택작업 정의에 awsvpc와 host, bridge 중 하나를 적는다, 그래서 태스크의 주소 부여와 격리 방식이 정해진다.
  2. 인터페이스 할당awsvpc를 고르면 태스크마다 ENI(탄력적 네트워크 인터페이스, 가상 네트워크 카드)와 프라이빗 IPv4 또는 IPv6 주소가 붙는다, 그래서 태스크 단위로 통신과 제어가 가능해진다.
  3. 모드별 통신 적용bridge에서는 인스턴스 안 가상 네트워크를 쓰고 host에서는 인스턴스 네트워크를 직접 쓴다, 그래서 DNS와 포트 처리 특성이 모드대로 달라진다.

Fargate·Managed Instances 네트워킹

#1문제 상황

기존에는 EC2 방식처럼 네트워크 모드를 고르고 인스턴스 네트워크를 나누는 설정을 직접 해야 했다. Fargate와 Managed Instances에서는 모드가 정해져 있는데 같은 방식으로 접근하면 선택할 수 없는 항목을 만지거나 서브넷과 보안그룹 지정을 놓쳐 이미지 수신과 통신이 막혔다.

#2핵심 질문

모드가 정해진 Fargate와 Managed Instances 태스크에서 서브넷과 보안그룹 지정으로 통신을 어떻게 확보할 수 있을까?

#3동작 예시

Fargate 태스크를 실행할 때 서브넷과 보안그룹을 지정하면 태스크마다 ENI(탄력적 네트워크 인터페이스, 가상 네트워크 카드)와 기본 프라이빗 IP가 붙는다. 공용 서브넷에서는 퍼블릭 IP를 추가로 붙이고 인터넷 경로를 확보하면 컨테이너 이미지를 받아올 수 있다.

#4동작 과정

  1. 서브넷과 보안그룹 지정실행 시 사용할 서브넷(주소 구간)과 보안그룹(방화벽 규칙 묶음)을 정한다, 그래서 태스크의 위치와 허용 통신이 정해진다.
  2. ENI 부여태스크마다 하나의 ENI(탄력적 네트워크 인터페이스, 가상 네트워크 카드)와 기본 프라이빗 IP가 붙는다, 그래서 태스크 단위 주소로 통신한다.
  3. 경로 확보와 내부 통신공용 서브넷에서는 퍼블릭 IP와 인터넷 경로를 붙여 이미지 수신을 가능하게 하고 같은 태스크 안 컨테이너는 localhost(자기 자신 주소)로 통신한다, 그래서 실행과 연동이 모두 가능해진다.

#2핵심 질문

태스크 데이터의 성격과 공유 범위에 따라 EBS와 EFS, FSx, S3 Files, Docker 볼륨, 바인드 중 무엇을 어떻게 골라 붙일 수 있을까?

#3동작 예시

#4동작 과정

Amazon EBS 볼륨

EBS는 실행 시점에 붙이는 블록 볼륨으로, 암호화·non-root 동작·성능 한도를 확인하고 붙지 않으면 상태 이유로 끊는다.

#1문제 상황

기존에는 컨테이너용 스토리지를 따로 붙이지 않으면 처리량이 큰 작업의 데이터를 두기 어려웠다. 실행 시점에 블록 볼륨을 붙이는 구성이 없으면 스냅샷 적재와 암호화, 성능 조건을 반영할 수 없고 문제가 생겨도 어디서 멈췄는지 알기 어려웠다.

#2핵심 질문

실행 시점에 EBS 블록 볼륨을 태스크에 어떻게 붙여 데이터 집약 작업에 쓸 수 있을까?

#3동작 예시

단독 태스크를 시작할 때 새 빈 EBS 볼륨이나 기존 스냅샷(특정 시점 복사본) 기반 볼륨을 하나 붙이도록 구성을 넘기면 ECS가 대신 관리하며 연결한다. 서비스로 유지되는 태스크에는 태스크마다 하나씩 같은 구성이 적용되어 각자 전용 블록 스토리지를 갖는다.

#4동작 과정

  1. 볼륨 구성 전달단독 태스크 시작이나 서비스 생성과 업데이트 시 새 볼륨 또는 스냅샷 기반 구성을 넘긴다, 그래서 태스크마다 붙을 블록 볼륨이 정해진다.
  2. 연결과 속성 적용ECS가 관리하며 EBS 볼륨(블록 스토리지, 가상 디스크)을 붙이고 KMS 암호화(KMS 키로 잠그는 설정)와 non-root 동작을 반영한다, 그래서 보안과 실행 권한 조건이 맞추어진다.
  3. 성능 확인과 상태 추적Fargate와 EC2, Managed Instances별 성능 한도를 확인하고 붙지 않으면 상태 이유로 연결이 끊긴다, 그래서 실패 지점을 상태 값으로 파악할 수 있다.

#1문제 상황

#2핵심 질문

공유 파일이 필요할 때 EFS와 FSx를 쓰고 읽기용 객체 참조일 때 S3 Files를 작업 정의에 어떻게 지정할 수 있을까?

#3동작 예시

여러 태스크가 같은 파일을 함께 써야 하면 Amazon EFS(탄력적 파일 시스템, 용량이 자동 증감하는 공유 저장소)를 작업 정의의 볼륨과 컨테이너 마운트 경로로 지정한다. EFS에 접근 지점(접근 경로와 권한을 고정한 진입점)을 두면 어떤 인스턴스에 떠도 동일한 영속 저장소에 닿는다.

#4동작 과정

  1. 공유 대상 선택함께 쓰는 파일이면 Amazon EFS(탄력적 파일 시스템, 공유 파일 저장소)와 FSx(파일 서버형 공유 저장소) 중 하나를 고른다, 그래서 동시 접근과 용량 증감이 가능해진다.
  2. 작업 정의에 마운트 지정파일 시스템과 볼륨 마운트(인스턴스 경로와 연결점), 컨테이너 마운트 경로를 작업 정의에 적는다, 그래서 컨테이너 경로에서 공유 파일에 닿는다.
  3. 읽기용 참조 분리읽기용 객체만 필요하면 S3 Files(S3 객체를 파일처럼 보여주는 볼륨)를 지정한다, 그래서 복제 없이 객체 내용을 참조한다.

#1문제 상황

기존에는 컨테이너 내부 파일 시스템에 데이터를 직접 저장했다. 컨테이너가 중지되거나 새 이미지로 교체되면 내부 데이터가 함께 사라졌다.

같은 인스턴스의 여러 컨테이너가 같은 데이터를 쓰려면 파일을 복사하거나 외부로 따로 옮겨야 했다. 데이터가 컨테이너 수명주기에 묶여 유지와 공유가 모두 어려웠다.

#2핵심 질문

컨테이너가 교체되어도 남고 같은 호스트의 여러 컨테이너가 함께 쓸 수 있도록 데이터를 어떻게 연결할까?

#3동작 예시

작업 정의에 Docker 볼륨 하나를 선언하고 두 컨테이너의 각 경로에 마운트한다. Docker는 컨테이너 인스턴스의 /var/lib/docker/volumes 아래 디렉터리를 만들어 데이터를 보관한다.

두 컨테이너는 각자 마운트된 경로에서 같은 볼륨 내용을 읽고 쓴다. 호스트의 특정 경로를 직접 연결해야 할 때는 바인드 마운트로 호스트 경로를 지정해 같은 방식으로 마운트한다.

#4동작 과정

  1. 볼륨 선언작업 정의에 볼륨 이름과 종류를 적는다. Docker 볼륨이면 dockerVolumeConfiguration을 지정하고, 바인드 마운트면 호스트 경로를 지정한다.
  2. 컨테이너에 연결각 컨테이너 정의에서 볼륨을 어느 경로에 마운트할지 지정한다. 그래서 컨테이너는 지정된 경로에서 볼륨 내용을 파일로 본다.
  3. 유지·공유컨테이너가 바뀌어도 볼륨 데이터는 호스트에 남는다. 그래서 여러 컨테이너가 같은 볼륨을 다른 위치에 연결해 함께 쓸 수 있다.

스왑 메모리 관리

스왑은 컨테이너 메모리 압박을 덜어 주는 여유 공간으로, 필요할 때만 설정한다.

#1문제 상황

기존에는 컨테이너가 설정된 메모리를 초과하면 바로 메모리가 부족해져 프로세스가 종료될 수 있었다. 순간적으로 메모리 사용량이 치솟는 작업은 여유가 없어 중단되기 쉬웠다.

반대로 지연에 민감한 작업은 메모리 압박이 없어도 스왑 동작으로 속도가 느려지는 것을 피하고 싶었다. 컨테이너마다 메모리 여유 정책을 다르게 둘 방법이 필요했다.

#2핵심 질문

컨테이너마다 메모리 압박에 대한 여유 공간 사용 여부와 상한을 어떻게 따로 설정할까?

#3동작 예시

작업 정의의 컨테이너 정의에서 스왑을 켜고 maxSwap(컨테이너가 쓸 수 있는 스왑 총량, MiB 단위)을 지정한다. 이 값은 컨테이너 메모리와 합산되어 docker run의 --memory-swap 옵션으로 전달된다.

부하가 걸려 메모리가 부족해지면 해당 컨테이너는 허용된 범위 안에서 스왑 공간을 사용해 종료를 피한다. 지연이 중요한 컨테이너는 스왑을 끄고, 일시적 사용량이 큰 컨테이너만 스왑을 켠다.

#4동작 과정

  1. 컨테이너별 설정컨테이너 정의에 스왑 사용 여부와 maxSwap(허용할 스왑 총량)을 적는다. 그래서 작업 안에서도 컨테이너마다 정책이 달라진다.
  2. 실행 시 전달ECS가 이 설정을 컨테이너 실행 옵션으로 변환해 적용한다. 그래서 허용된 만큼만 메모리 초과분을 스왑으로 감당한다.
  3. 부하 시 동작메모리가 부족해지면 스왑을 켠 컨테이너는 스왑을 써서 계속 동작한다. 그래서 일시적 메모리 증가로 인한 중단 가능성이 줄어든다.

클러스터 개념·상태·기본 구성

클러스터는 태스크·서비스를 담는 리전 종속 논리 그룹으로, VPC·서브넷·네임스페이스·모니터링을 갖춰 만들고 상태 전이를 따른다.

#1문제 상황

기존에는 태스크와 서비스를 개별적으로 띄우면 실행 위치와 용량을 매번 따로 정해야 했다. 어디에서 도는지, 어떤 네트워크와 모니터링을 쓰는지 한 번에 관리하기 어려웠다.

리전이 바뀌면 같은 구성을 다시 만들어야 했고 생성·변경·삭제 흐름도 흩어졌다. 묶음 단위로 용량과 설정을 관리할 그릇이 필요했다.

#2핵심 질문

태스크와 서비스를 담아 실행 용량을 제공하고 네트워크와 모니터링 설정을 함께 관리하는 논리 그룹을 어떻게 만들까?

#3동작 예시

리전에 클러스터 하나를 만들고 실행 방식에 맞는 인프라 유형을 선택한다. 클러스터에 VPC와 서브넷, 필요하면 네임스페이스와 모니터링 설정을 연결한다.

이후 태스크와 서비스는 이 클러스터 안에서 실행된다. 클러스터는 생성되고 사용되다가 삭제되는 상태 전이를 따라 관리된다.

#4동작 과정

  1. 클러스터 만들기태스크와 서비스를 담는 논리 그룹을 리전에 만든다. 인프라 유형을 고르면 실행 용량의 관리 방식이 정해진다.
  2. 기본 구성 연결VPC·서브넷(네트워크 위치)과 네임스페이스(서비스 찾기 이름 공간), 모니터링 설정을 붙인다. 그래서 실행 위치와 관찰 방식이 정해진다.
  3. 상태 따라 관리클러스터를 생성·갱신·삭제하면서 상태 변화를 따른다. 그래서 태스크와 서비스의 실행 그릇을 일관되게 유지한다.

Managed Instances 클러스터와 용량공급자

MI 클러스터는 MI 용량공급자로 용량을 받고, 모범 사례대로 만들고 갱신·삭제하며 스케일인 보호·드레이닝을 둔다.

→ 03-02 참조

#1문제 상황

기존에는 EC2 기반 용량을 쓰려면 인스턴스 준비와 패치, 확장을 직접 관리해야 했다. 태스크가 늘 때 인스턴스를 맞추고 비용에 맞는 종류를 고르는 일이 운영 부담이었다.

용량공급자 없이 클러스터만 만들면 태스크를 어디에 어떻게 분산할지 정하기 어려웠다. 용량 확장과 태스크 배치를 함께 관리할 방법이 필요했다.

#2핵심 질문

인스턴스 관리는 AWS에 맡기면서 태스크를 용량공급자들에 어떻게 나누어 실행할까?

#3동작 예시

Managed Instances(MI) 클러스터를 만들고 MI 용량공급자를 연결한다. 용량공급자는 작업 정의의 운영체제와 CPU 아키텍처, CPU·메모리 요구와 배치 조건을 보고 비용이 낮은 인스턴스를 고른다.

태스크나 서비스를 실행할 때는 클러스터 기본 전략이나 별도 전략으로 어느 용량공급자를 얼마나 쓸지 정한다. 스케일인 보호와 드레이닝을 두어 종료 중인 인스턴스의 태스크를 안전하게 옮긴다.

#4동작 과정

  1. 클러스터·공급자 만들기MI 클러스터를 만든 뒤 하나 이상의 용량공급자와 분산 전략을 연결한다. 그래서 태스크가 어느 공급자로 갈지 정해진다.
  2. 실행·분산태스크 실행 시 기본 전략이나 지정한 전략을 적용한다. 조건에 맞는 인스턴스가 선택되어 비용과 요구사항이 함께 맞춰진다.
  3. 보호·정리스케일인 보호(축소 시 태스크 있는 인스턴스 유지)와 드레이닝(종료 전 태스크 이동)으로 갱신과 삭제를 관리한다. 그래서 교체와 축소 중에도 실행이 유지된다.

Fargate 클러스터 만들기

Fargate 클러스터는 서버를 두지 않고 Fargate 용량공급자를 연결해 콘솔에서 만든다.

#1문제 상황

기존에는 컨테이너를 실행하려면 서버를 먼저 준비하고 등록해야 했다. 인스턴스 용량을 예측하고 유지하는 작업이 필요해 작은 태스크도 준비 과정이 무거웠다.

남는 용량을 값싸게 쓰고 싶어도 중단 가능성을 감수하는 실행 방식을 따로 관리하기 어려웠다. 서버 없이 실행 위치만 지정하는 방식이 필요했다.

#2핵심 질문

서버를 두지 않고 Fargate 용량으로 태스크를 어떻게 바로 실행할까?

#3동작 예시

콘솔에서 클러스터를 만들고 Fargate 용량공급자를 연결한다. 태스크는 Fargate로 실행하고, 중단이 허용되는 작업은 Fargate Spot으로 실행해 spare 용량으로 동작시킨다.

AWS가 용량을 회수해야 하면 약 2분 전 알림 뒤 해당 태스크가 중단된다. 중단되면 태스크 상태 변경 이벤트가 EventBridge로 전달되고 중단 원인이 기록된다.

#4동작 과정

  1. 클러스터·공급자 연결Fargate 클러스터를 만들고 Fargate와 Fargate Spot 용량공급자를 붙인다. 그래서 서버 준비 없이 실행 위치가 정해진다.
  2. 실행 방식 선택일반 작업은 Fargate로, 중단이 허용되는 작업은 Fargate Spot으로 실행한다. 그래서 비용과 안정성 요구에 맞게 나뉜다.
  3. 중단·알림용량 회수 시 알림 뒤 태스크가 중단되고 상태 변경 이벤트가 전달된다. 그래서 중단 원인을 추적하고 후속 처리를 할 수 있다.

EC2 용량공급자와 클러스터 오토스케일링

EC2는 Auto Scaling 그룹 용량공급자로 묶고 관리형 스케일링·종료 보호·온오프를 설정해 용량을 자동으로 맞춘다.

#1문제 상황

기존에는 EC2 인스턴스로 용량을 쓸 때 Auto Scaling 그룹의 확장과 축소를 직접 조절해야 했다. 태스크가 늘면 인스턴스가 모자랐고, 줄면 남는 인스턴스가 비용이 되었다.

이미 실행 중이던 인스턴스를 나중에 용량공급자에 묶으면 등록이 어긋날 수 있었다. 실행 부하에 맞춰 용량을 자동으로 맞추는 연결이 필요했다.

#2핵심 질문

Auto Scaling 그룹을 용량공급자로 묶어 클러스터 용량을 부하에 맞게 어떻게 자동으로 조절할까?

#3동작 예시

비어 있는 Auto Scaling 그룹을 새로 만들어 용량공급자로 등록하고 클러스터에 연결한다. 관리형 스케일링을 켜면 ECS가 태스크 요구를 보고 그룹의 확장·축소를 직접 조절한다.

종료 보호를 두면 태스크가 동작 중인 인스턴스가 축소 과정에서 함부로 끝나지 않는다. 필요에 따라 관리형 스케일링을 켜거나 꺼서 자동과 직접 관리를 바꾼다.

#4동작 과정

  1. 그룹·공급자 묶기Auto Scaling 그룹으로 용량공급자를 만들고 클러스터에 연결한다. 새 빈 그룹을 쓰면 기존 등록 어긋남을 피할 수 있다.
  2. 자동 조절관리형 스케일링을 켜면 ECS가 확장·축소를 관리한다. 그래서 부하에 맞는 수의 EC2 인스턴스가 유지된다.
  3. 보호·전환종료 보호로 실행 중 인스턴스를 지키고 켜기·끄기로 자동 여부를 바꾼다. 그래서 안정성과 운영 방식이 함께 정해진다.

EC2 컨테이너 인스턴스: AMI와 에이전트

EC2 인스턴스는 ECS 최적화 Linux·Windows·Bottlerocket AMI로 띄우고 컨테이너 에이전트를 설치·설정·업데이트한다.

#1문제 상황

기존에는 EC2 인스턴스에 컨테이너 실행 환경을 매번 직접 설치하고 설정해야 했다. 운영체제와 실행 도구 버전이 인스턴스마다 달라질 수 있었다.

에이전트 설치와 설정 저장 방식이 흩어지면 클러스터 등록과 업데이트가 번거로웠다. 바로 쓸 수 있는 이미지와 관리 흐름이 필요했다.

#2핵심 질문

컨테이너 실행에 맞게 준비된 이미지로 인스턴스를 띄우고 에이전트를 어떻게 설치·설정·업데이트할까?

#3동작 예시

ECS 최적화 AMI 중 Linux, Windows, Bottlerocket 가운데 목적에 맞는 것을 골라 EC2 인스턴스를 시작한다. AMI에는 컨테이너 실행에 필요한 구성과 컨테이너 에이전트(인스턴스와 ECS를 연결해 작업을 받아 실행하는 프로그램)가 준비되어 있다.

에이전트를 설치·설정하고 필요하면 S3에 저장한 설정으로 불러온 뒤 업데이트로 최신 상태를 유지한다. 인스턴스는 이후 클러스터에 등록되어 태스크를 실행한다.

#4동작 과정

  1. 이미지로 시작ECS 최적화 Linux·Windows·Bottlerocket AMI로 인스턴스를 띄운다. 그래서 컨테이너 실행 환경이 미리 갖춰진다.
  2. 에이전트 연결컨테이너 에이전트를 설치·설정하고 S3 설정 저장을 필요에 따라 쓴다. 그래서 인스턴스가 ECS와 연결되어 작업을 받는다.
  3. 업데이트 유지에이전트를 업데이트해 기능을 유지한다. 그래서 클러스터 등록 상태와 실행 능력이 계속 유지된다.

EC2 인스턴스 운영과 정리

인스턴스는 시작·부트스트랩·원격 관리·프록시·웜풀·에이전트 업데이트로 운영하고, 안 쓰는 태스크·이미지를 정리·등록 해제·드레이닝한다.

#1문제 상황

EC2 방식을 쓰면 인스턴스를 직접 띄우고 부트스트랩 스크립트로 클러스터 연결 설정을 넣은 뒤 운영자가 계속 관리해야 한다. 스팟 중단 통지 설정이 없거나 프록시 설정과 에이전트 버전이 맞지 않으면 태스크 배치가 멈추거나 외부 통신이 끊긴다. 종료된 컨테이너와 쓰지 않는 이미지가 쌓이면 디스크가 차서 새 태스크가 시작되지 않는다.

#2핵심 질문

EC2 인스턴스를 중단 없이 운영하면서 불필요한 태스크와 이미지는 어떻게 정리할 것인가?

#3동작 예시

Auto Scaling 그룹에서 새 Linux 인스턴스가 시작될 때 부트스트랩 스크립트로 클러스터 이름을 등록하고 스팟 중단 통지를 받도록 설정한다. 운영 중에는 원격 관리 통로로 상태를 점검하고 프록시를 거쳐 외부와 통신하며 ECS 컨테이너 에이전트를 최신 버전으로 갱신한다. 종료 전에는 인스턴스를 드레이닝 상태로 바꿔 실행 중인 태스크를 다른 곳으로 옮긴 뒤 등록을 해제하고 남은 컨테이너와 이미지를 삭제한다.

#4동작 과정

  1. 시작과 부트스트랩인스턴스를 시작하고 부트스트랩 설정으로 클러스터에 연결하며 스팟 중단 통지 수신과 프록시 설정, 웜풀 사전 초기화를 적용해 배치 가능한 상태로 만든다.
  2. 운영과 갱신원격 관리 방식으로 상태를 점검하고 컨테이너 에이전트(인스턴스에서 ECS와 통신하는 프로그램)를 업데이트해 기능과 수정 사항을 반영한다.
  3. 정리와 해제불필요한 태스크와 이미지를 삭제하고 드레이닝(새 태스크를 받지 않고 기존 태스크를 이동시키는 조치)으로 비운 뒤 등록을 해제한다.

태스크 수명주기와 스케줄링 개요

태스크는 정의의 실행 단위로 수명주기를 돌며, 단독 실행과 서비스 소속 실행 중 목적에 맞는 쪽을 고른다.

#1문제 상황

기존에는 컨테이너를 띄우면 시작과 종료 사이에서 지금 어떤 상태인지 알기 어려웠다. 배치 작업처럼 끝나야 하는 것과 서비스처럼 계속 돌아야 하는 것을 같은 방식으로 다루면 중지 요청과 확장 요청이 꼬였다. 에이전트가 보고하는 실제 상태와 사용자가 원하는 상태가 따로 관리되지 않으면 확장 시점이 어긋났다.

#2핵심 질문

실행 목적이 다른 태스크를 상태 변화에 맞춰 시작과 중지, 확장과 축소로 어떻게 다뤄야 하는가?

#3동작 예시

태스크 정의의 실행 단위로 태스크를 시작하면 PENDING을 거쳐 RUNNING으로 이동한다. 배치 작업은 할 일을 마치면 STOPPED로 끝나고 서비스 소속 태스크는 원하는 개수를 유지하며 계속 실행된다. 중지나 확장을 요청하면 에이전트가 lastStatus(현재 확인된 상태)와 desiredStatus(목표 상태)를 추적해 콘솔과 API에 보여준다.

#4동작 과정

  1. 시작과 배치수동 실행이나 서비스 요청으로 태스크를 만들고 컴퓨팅 용량을 찾아 PENDING 상태에서 준비한 뒤 실행 대상으로 올린다.
  2. 실행과 유지RUNNING 상태에서 동작하며 배치 작업은 종료까지 진행하고 서비스 소속 태스크는 개수 증감에 따라 유지와 확장을 반복한다.
  3. 중지와 반영중지나 개수 변경 요청이 오면 desiredStatus를 바꾸고 에이전트가 lastStatus에 반영해 STOPPED로 정리한다.

배치는 전략(분산 방식)과 제약(쓸 인스턴스 조건)으로 정하고, 복잡한 조건은 클러스터 쿼리 언어로 적으며 관련 태스크는 그룹으로 묶는다.

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 전략 지정과 분산배치 전략(인스턴스를 고르는 분산 방식)을 정해 무작위 배치나 인스턴스 간 균등 분산 같은 규칙으로 배치 대상을 고른다.
  2. 제약 지정과 묶음배치 제약(반드시 만족해야 하는 배치 규칙)으로 가용 영역과 인스턴스 유형 같은 조건을 걸고 관련 태스크는 그룹으로 묶어 함께 다룬다.
  3. 조건 기록과 대기복잡한 조건은 클러스터 쿼리 언어(인스턴스 속성을 고르는 조회 문법)로 적고 조건 불일치 시 PENDING으로 대기시킨다.

EventBridge Scheduler로 태스크 예약

정기 실행은 EventBridge Scheduler·CloudWatch Events로 듣고, 중지 이벤트는 SNS 알림으로 받는다.

#1문제 상황

#2핵심 질문

정기 실행과 일회성 실행을 중앙 일정으로 등록하고 종료 알림까지 받으려면 어떻게 해야 하는가?

#3동작 예시

EventBridge Scheduler에 속도 기반과 cron 기반, 일회성 일정 중 하나를 등록해 ECS 태스크를 대상으로 지정한다. 지정된 시각과 시간대가 되면 스케줄러가 ECS 실행 API를 호출해 태스크를 시작한다. 중지된 태스크 이벤트는 CloudWatch Events로 받아 SNS 알림으로 전달한다.

#4동작 과정

  1. 일정 등록과 실행EventBridge Scheduler(서버 없이 일정을 관리하는 중앙 스케줄러)에 속도 기반과 cron 기반, 일회성 일정을 등록해 지정 시각에 ECS 태스크를 호출한다.
  2. 호출과 배치스케줄러가 대상 API를 호출해 태스크를 시작하고 ECS가 용량을 확보해 실행한다.

스케일인 보호와 폴트 인젝션

중요 태스크는 스케일인 보호로 지켜 주고, 장애 내성은 Fargate 폴트 인젝션 엔드포인트로 미리 시험한다.

#1문제 상황

기존에는 이용률이 낮아지거나 새 배포가 시작되면 자동 확장이 실행 중인 태스크를 함께 종료했다. 동영상 변환처럼 몇 시간 도는 작업과 게임 서버처럼 계속 켜둬야 하는 작업이 중간에 끊겨 처음부터 다시 시작해야 했다. 장애가 났을 때 어떻게 동작하는지 미리 시험할 방법이 없어 실제 장애에서야 문제를 확인했다.

#2핵심 질문

중요한 태스크를 축소 종료에서 지키면서 장애 상황을 미리 시험하려면 어떻게 해야 하는가?

#3동작 예시

장시간 변환 작업을 처리하는 태스크에 스케일인 보호를 켜서 자동 확장과 배포 과정의 종료 대상에서 제외한다. Fargate에서 제공하는 폴트 인젝션용 엔드포인트로 장애를 주입해 종료와 재시작 흐름을 시험한다. 시험이 끝나면 보호를 해제해 다시 확장 대상으로 되돌린다.

#4동작 과정

  1. 보호 지정과 유지중요 태스크에 스케일인 보호(축소 시 종료하지 않는 표시)를 설정해 자동 확장과 배포 과정에서도 실행을 유지한다.
  2. 장애 주입과 확인Fargate의 폴트 인젝션 엔드포인트(장애를 일부러 일으켜 내성을 시험하는 접속 지점)로 장애를 발생시켜 동작을 확인한다.
  3. 해제와 복귀작업 완료나 시험 종료 뒤 보호를 해제해 다시 확장 대상에 포함되도록 되돌린다.

서비스 개념과 수명주기 관리

서비스는 원하는 태스크 수를 유지하는 장기 실행 단위로, 스케줄러가 실패·비정상 태스크를 교체하고 파라미터를 갱신·삭제한다.

#1문제 상황

이전에는 태스크 정의로 태스크를 직접 실행하고 개수를 사람이 세어 맞췄다. 태스크 하나가 실패하거나 중지되면 빈자리를 알아채고 다시 실행하기까지 공백이 생겼다. 장시간 켜 두어야 하는 웹 서버에는 이런 수동 관리가 계속 부담이 됐다.

#2핵심 질문

실패한 태스크를 자동으로 교체해서 원하는 개수를 계속 유지하려면 어떻게 해야 할까?

#3동작 예시

원하는 개수를 4로 둔 서비스가 태스크 1개의 실패를 감지하면 스케줄러가 같은 태스크 정의로 새 태스크 1개를 시작한다. 새 태스크가 정상 실행되면 서비스에 다시 4개가 채워지고 요청은 살아 있는 태스크들에 분산된다. 관리자가 일일이 세지 않아도 개수가 기준대로 돌아온다.

#4동작 과정

  1. 개수 유지스케줄러(태스크를 배치하고 교체하는 주체)가 실행 중인 태스크 수를 원하는 개수(유지해야 할 태스크 수)와 비교하고 부족하면 새 태스크를 시작하므로 실패가 생겨도 개수가 유지된다.
  2. 설정 갱신콘솔이나 API로 파라미터를 바꾸면 새 배포가 시작되고 태스크가 교체되므로 이미지가 바뀌어도 서비스가 이어진다.
  3. 삭제 정리서비스를 삭제하면 관련 태스크와 스케줄링이 끝나므로 더 이상 태스크가 다시 시작되지 않는다.

롤링 업데이트 배포

롤링은 새 리비전을 조금씩 갈아끼우는 기본 배포로, 파라미터 모범 사례·이른 성공 기준을 둔다.

#1문제 상황

이전에는 새 버전을 배포할 때 기존 태스크를 먼저 멈추고 새 태스크를 올리는 방식을 썼다. 교체 중간에는 처리할 태스크가 부족해 요청이 끊기거나 느려졌다. 새 버전에 문제가 있어도 되돌리기가 바로 되지 않았다.

#2핵심 질문

서비스를 중단 없이 새 버전으로 조금씩 갈아끼우면서 문제가 생기면 멈추려면 어떻게 해야 할까?

#3동작 예시

원하는 개수 4에 최소 정상 비율(배포 중에도 유지해야 할 정상 태스크 비율)을 50퍼센트로 둔 서비스가 새 리비전으로 롤링을 시작한다. 스케줄러는 기존 태스크 2개를 멈추기 전에 새 태스크 2개를 먼저 시작해 전체 개수를 맞춘다. 새 태스크가 정상이 되면 나머지 기존 태스크도 같은 방식으로 교체한다.

#4동작 과정

  1. 교체 수 결정배포 설정(한 번에 멈추거나 시작할 태스크 수를 정하는 값)으로 멈출 수와 시작할 수를 정하므로 정상 태스크가 기준 아래로 떨어지지 않는다.
  2. 조금씩 교체스케줄러가 구 태스크를 멈추고 새 리비전(배포에 쓰는 새 작업 설정) 태스크를 시작하는 일을 반복하므로 서비스는 요청을 계속 처리한다.
  3. 성공 조기 확정이른 성공 기준(새 태스크가 안정적이면 배포를 일찍 완료로 판단하는 조건)이 만족되면 남은 대기를 줄이고 배포를 끝내므로 반영이 빨라진다.

블루/그린 배포

블루/그린은 신구를 나란히 두고 트래픽을 옮기는 배포로, ALB·NLB·Service Connect 자원을 갖춰 만들고 문제를 푼다.

#1문제 상황

이전에는 같은 서비스 안에서 구 태스크를 새 태스크로 바로 교체하는 방식이 주로 쓰였다. 새 버전을 실제 운영 요청으로 미리 검증할 별도 환경이 없어 문제가 배포 후에야 드러났다. 문제가 생겨도 원래 버전으로 되돌리는 데 시간이 걸렸다.

#2핵심 질문

새 버전을 별도 환경에서 검증한 뒤 운영 트래픽을 한 번에 옮기고 문제 생기면 바로 되돌리려면 어떻게 해야 할까?

#3동작 예시

운영 중인 파란색(기존) 서비스 옆에 같은 설정의 초록색(새 버전) 서비스를 만들고 로드 밸런서(요청을 여러 태스크에 나누어 보내는 장치) 뒤에 함께 연결한다. 먼저 테스트 요청만 초록색으로 보내 동작을 확인하고 이상이 없으면 운영 트래픽을 초록색으로 옮긴다. 초록색에 문제가 생기면 운영 트래픽을 다시 파란색으로 돌린다.

#4동작 과정

  1. 새 환경 준비새 리비전으로 초록색 환경을 만들고 로드 밸런서와 대상 그룹(요청을 받을 태스크 모음)을 연결하므로 운영과 분리된 검증 통로가 생긴다.
  2. 트래픽 전환테스트 트래픽으로 검증한 뒤 운영 트래픽을 파란색에서 초록색으로 옮기므로 중단 없이 새 버전이 운영을 맡는다.
  3. 문제 대응전환 중 오류가 나면 트래픽을 파란색으로 되돌리므로 장애 시간이 짧아진다.

리니어·카나리·외부와 CodeDeploy 전환

이전에는 새 버전이 검증되면 운영 트래픽을 한 번에 새 쪽으로 옮기는 경우가 많았다. 새 버전에 숨은 문제가 있으면 모든 요청에 바로 영향이 갔다. 외부 배포 도구에 나눠진 설정도 함께 관리해야 해서 절차가 복잡해졌다.

#2핵심 질문

새 버전에 보내는 트래픽 비율을 단계적으로 늘리면서 검증하고 필요하면 외부에서 직접 제어하려면 어떻게 해야 할까?

#3동작 예시

새 리비전에 10퍼센트씩 트래픽을 옮기고 대기 시간을 두고 다음 단계로 넘어가는 리니어 배포를 시작한다. 각 단계에서 지표가 정상이면 다음 10퍼센트를 더 옮겨 운영 트래픽을 조금씩 새 쪽으로 모은다. 중간에 이상이 생기면 추가 이동을 멈추고 이전 상태로 되돌린다.

#4동작 과정

  1. 리니어 이동리니어(같은 비율씩 나누어 옮기는 방식)가 전체 트래픽을 같은 증가분씩 일정한 대기 시간을 두고 옮기므로 각 단계마다 성능을 확인하면서 진행된다.
  2. 카나리 검증카나리(소량 먼저 보내 검증하는 방식)가 먼저 소량의 운영 트래픽만 새 리비전에 보내고 정상이면 비율을 키우므로 문제를 작게 가두면서 확대할 수 있다.
  3. 외부 제어와 이관외부 배포(전환 시점과 비율을 외부 절차에서 직접 정하는 방식)를 쓰면 제어가 외부에 남고 옛 CodeDeploy 방식은 ECS 네이티브 설정으로 옮기므로 관리 위치가 하나로 모인다.

배포 실패 감지와 수명주기 훅

회로 차단기·CloudWatch 경보로 실패를 잡고, Lambda·일시정지 훅으로 검증 뒤 계속·중지한다.

#1문제 상황

이전에는 배포가 끝난 뒤 사람이 지표를 보고 실패 여부를 판단했다. 실패한 배포가 그대로 두어지면 오류 태스크가 계속 요청을 받았다. 검증 절차를 배포 중간에 끼워 넣을 자리가 없어 판단이 늦어졌다.

#2핵심 질문

실패한 배포를 자동으로 감지해 되돌리고 중간에 검증을 넣어 계속할지 멈출지 정하려면 어떻게 해야 할까?

#3동작 예시

롤링 배포 중에 새 태스크가 계속 실패하면 배포 회로 차단기(실패가 이어지면 배포를 실패로 판단하는 기능)가 배포를 중단하고 이전 정상 상태로 되돌린다. 배포 중간에 일시정지 훅(다음 단계로 가기 전 검증을 기다리는 지점)이 걸리면 Lambda(작은 검증 코드를 실행하는 계산 기능)가 검사를 마칠 때까지 다음 단계가 멈춘다. 검증 결과에 따라 배포를 계속하거나 중지한다.

#4동작 과정

  1. 실패 감지회로 차단기가 태스크 실패를 세고 CloudWatch 경보(지표가 기준을 넘으면 울리는 감시 설정)가 이상을 알리므로 실패 신호가 자동으로 모인다.
  2. 검증 대기수명주기 훅이 배포를 일시정지시키고 Lambda 검증을 실행하므로 다음 단계 전에 결과를 확인할 수 있다.

#1문제 상황

서비스를 태스크 여러 개로 띄워도 진입 주소가 각 태스크에 따로 있으면 요청이 한 태스크에 몰린다. 태스크가 교체될 때마다 주소가 바뀌어 클라이언트가 매번 새 위치를 알아야 한다.

태스크 집합을 그대로 두면 HTTP와 TCP를 구분해 나눠주기도 어렵다. 포트 하나만 열면 서비스 하나가 여러 포트를 쓰고 싶어도 외부에서 나눠 받기 어렵다.

#2핵심 질문

여러 태스크 앞에 무엇을 두어야 요청을 고르게 나누고 프로토콜에 맞게 연결할 수 있는가?

#3동작 예시

#4동작 과정

  1. 유형 선택HTTP/HTTPS면 ALB(애플리케이션 로드밸런서, 7계층에서 경로와 호스트로 나누는 방식)를 쓰고 TCP·UDP면 NLB(네트워크 로드밸런서, 연결 단위로 빠르게 넘기는 방식)를 쓰며 어플라이언스를 경유하면 GLB(게이트웨이 로드밸런서, 트래픽을 경유지로 보내는 방식)를 두므로 프로토콜에 맞게 분산된다.
  2. 타깃그룹 연결서비스에 여러 타깃그룹을 붙여 로드밸런서 여러 개와 노출 포트 여러 개를 연결하므로 한 서비스가 여러 입구를 가질 수 있다.
  3. 균등 분배로드밸런서가 살아 있는 태스크들에 요청을 고르게 나누어 보내므로 특정 태스크에 부하가 쏠리지 않는다.

#1문제 상황

타깃그룹에 태스크를 등록만 하고 건강 상태를 확인하지 않으면 죽은 컨테이너에도 요청이 계속 들어간다. 등록 직후 바로 정상으로 치면 아직 뜰 준비가 안 된 컨테이너가 요청을 받아 오류를 낸다.

배포나 축소 때 연결을 바로 끊으면 처리 중이던 요청이 중간에 잘린다. 헬스체크 간격이 서비스 기동 속도와 안 맞으면 배포가 느려지거나 실패로 잘못 판단된다.

#2핵심 질문

등록된 컨테이너가 요청을 받을 준비가 됐는지 어떻게 판단하고 교체 시 진행 중 요청을 어떻게 보호할 수 있는가?

#3동작 예시

로드밸런서가 타깃그룹에 등록된 ECS 컨테이너에 주기적으로 상태 확인 요청을 보낸다. 등록된 대상은 한 번이라도 확인을 통과해야 정상으로 분류돼 요청을 받기 시작한다. ECS 에이전트는 로드밸런서의 보고가 정상으로 나올 때까지 기다렸다가 컨테이너 상태를 정상으로 확정한다.

#4동작 과정

  1. 타깃 등록컨테이너를 타깃그룹(요청을 받을 대상 묶음)에 등록한 뒤 한 번의 헬스체크(살아 있는지 묻는 확인 요청) 통과를 요구하므로 준비 안 된 대상에 요청이 가지 않는다.
  2. 주기적 확인헬스체크 간격(확인 요청 사이의 초 단위 시간)과 임계값을 서비스 기동 속도에 맞춰 조정하므로 느리게 뜨는 서비스도 정상적으로 판단되고 배포 속도가 안정된다.
  3. 연결 드레이닝교체 대상은 등록 해제 후 일정 시간 동안 기존 연결을 마저 처리하게 하는 드레이닝(배수 기간)을 적용하므로 진행 중 요청이 끊기지 않고 끝난 뒤에 종료된다.

서비스 오토스케일링: 타깃추적·단계

타깃추적·단계 정책으로 원하는 태스크 수를 자동 조절하고, 필요한 IAM 권한과 문제해결을 갖춘다.

#1문제 상황

원하는 태스크 수를 고정해 두면 피크 시간에는 요청이 밀리고 한가한 시간에는 빈 태스크가 비용을 먹는다. 사람이 직접 개수를 바꾸면 반응이 늦어 수요 변화를 따라가기 어렵다.

CPU와 메모리 사용량은 CloudWatch에 찍히는데도 임계값과 조절 폭을 손으로 정하면 과하게 늘리거나 늦게 줄인다. 배포 중 자동 조절이 겹치면 개수가 서로 다르게 움직여 혼란이 생긴다.

#2핵심 질문

수요 변화에 맞춰 서비스의 원하는 태스크 수를 어떻게 자동으로 늘리고 줄일 수 있는가?

#3동작 예시

평균 CPU 사용률을 기준으로 서비스를 자동 조절하도록 둔다. 사용률이 높아지면 Application Auto Scaling(원하는 개수를 대신 조절해주는 자동 조절 서비스)이 원하는 태스크 수를 올려 새 태스크를 추가한다. 수요가 빠지면 개수를 내려 빈 태스크를 정리해 비용을 줄인다.

#4동작 과정

  1. 지표 수집ECS가 서비스의 평균 CPU와 메모리 사용량을 CloudWatch 지표(시간별 수치 기록)로 내보내므로 현재 부하를 숫자로 볼 수 있다.
  2. 정책 적용타깃추적(특정 지표값을 목표로 삼아 자동으로 맞추는 방식)이나 단계 조절(값 구간별로 늘릴 폭을 정하는 방식)을 골라 적용하므로 부하에 따라 원하는 태스크 수가 자동으로 바뀐다.
  3. 권한과 점검자동 조절용 IAM(실행 권한 관리) 권한을 갖추고 배포와 겹칠 때 동작과 문제해결 절차를 확인하므로 조절이 멈추거나 엇나가지 않는다.

예약·예측·큐 기반 스케일링

정해진 시간은 예약, 패턴이 읽히면 예측, 대기열 길이면 큐 기반으로 늘리고 줄인다.

#1문제 상황

실시간 지표만 보고 늘리면 출근 시간처럼 정해진 피크에 매번 늦게 대응한다. 초기화에 오래 걸리는 앱은 늘리는 도중에 지연이 생겨 사용자가 느림을 먼저 겪는다.

정해진 시간의 작업이나 주기적 배치는 패턴이 뻔한데도 매번 같은 대응을 반복한다. 대기열에 일이 쌓이는 구조에서는 CPU가 낮아도 처리할 메시지가 밀리는데 지표 기반 조절만으로는 이를 못 본다.

#2핵심 질문

시간이 정해진 수요와 반복되는 패턴, 쌓이는 대기열에 맞춰 태스크 수를 어떻게 미리 또는 맞게 늘릴 수 있는가?

#3동작 예시

평일 낮에만 사용자가 몰리는 서비스에 과거 트래픽 기록을 분석한 예측 조절을 건다. 시스템은 매일 아침 수요가 오르기 전에 태스크를 미리 늘려 둔다. 야간 배치처럼 시간이 정해진 작업은 예약 동작으로 시작 시각에 맞춰 개수를 올렸다가 끝나면 내린다.

#4동작 과정

  1. 예약 조절스케줄 동작(지정한 시각에 원하는 개수를 바꾸는 예약)을 두어 정해진 시간에 늘리고 줄이므로 매일 같은 피크에 늦지 않게 대응된다.
  2. 예측 조절과거 부하 데이터로 일간·주간 패턴을 분석해 수요를 미리 예측하고 태스크를 선행 증설하므로 초기화 시간이 긴 앱도 지연 없이 수요를 받는다.
  3. 큐 기반 조절대기열 길이 같은 사용자 지정 지표를 기준으로 개수를 바꾸므로 CPU는 낮아도 밀린 작업이 있으면 태스크가 늘어나 처리가 빨라진다.

Service Connect 서비스 메시

Service Connect는 짧은 이름으로 서비스끼리 붙이는 내부 메시로, 구성·공유 네임스페이스·액세스 로그·구역 인식·TLS를 둔다.

#1문제 상황

서비스끼리 직접 주소로 붙으면 태스크가 교체될 때마다 상대 주소를 다시 찾아야 한다. VPC DNS 설정에 의존하면 네임스페이스가 달라질 때마다 호출 방식도 달라진다.

서비스가 늘면 누가 누구를 부르는지 설정이 흩어진다. 호출량과 로그 형식이 서비스마다 다르면 어디가 느린지 묶어 보기 어렵다.

#2핵심 질문

바뀌는 태스크 주소와 상관없이 서비스끼리 짧은 이름으로 안정되게 호출하게 하려면 어떻게 묶어야 하는가?

#3동작 예시

WordPress 클라이언트 서비스와 MySQL 서버 서비스를 같은 Service Connect 구성에 넣는다. 클라이언트는 서버의 짧은 이름만 호출하면 각 서브넷과 가용영역에 있는 실제 태스크 중 살아 있는 곳으로 연결된다. 태스크가 교체돼도 이름은 그대로이므로 호출 코드를 고칠 필요가 없다.

#4동작 과정

  1. 구성 연결각 서비스에 Service Connect 설정(서비스 간 호출을 위한 이름과 포트 규칙)을 넣어 배포 단위로 관리하므로 주소가 바뀌어도 이름 기반 호출이 유지된다.
  2. 내부 메시 형성서비스 탐색과 서비스 메시(서비스 간 호출을 중개·관측하는 내부 통신층)가 함께 생겨 공유 네임스페이스 안에서 표준 방식으로 서로를 찾는다.
  3. 관측과 보호표준 지표와 액세스 로그로 전체 호출을 묶어 보고 구역 인식 라우팅(가까운 구역 우선 연결)과 TLS(암호화와 상대 확인) 옵션으로 빠르고 안전하게 연결된다.

DNS 발견이 필요하면 서비스 디스커버리, 계정·VPC를 넘나들면 VPC Lattice를 쓰고, AZ 쏠림은 리밸런싱으로 푼다.

#1문제 상황

서비스 주소를 코드에 고정하면 태스크가 바뀌거나 늘어날 때마다 접속 정보를 고쳐야 한다. DNS 이름 없이 IP만 쓰면 어느 서비스가 어디 있는지 찾기 어렵다.

계정이나 VPC를 넘어 호출해야 할 때는 한 VPC 안의 이름만으로 부족하다. 특정 가용영역(AZ, 독립된 데이터센터 구역)에 태스크가 몰리면 장애 시 영향이 커지는데 손으로 옮기기 어렵다.

#2핵심 질문

DNS 이름으로 서비스를 찾게 하고 VPC를 넘어 연결하며 가용영역 쏠림을 어떻게 바로잡을 수 있는가?

#3동작 예시

ECS 서비스에 서비스 탐색을 켜면 AWS Cloud Map(API로 이름 공간을 관리하는 등록 서비스)에 DNS 이름이 등록된다. 다른 서비스는 그 DNS 이름만 호출하면 현재 살아 있는 태스크 주소로 연결된다. 태스크가 교체돼도 이름은 그대로이므로 호출 쪽 수정이 필요 없다.

#4동작 과정

  1. DNS 등록서비스를 만들 때 서비스 탐색을 켜서 HTTP와 DNS 네임스페이스(이름 공간)에 등록하므로 이름 호출만으로 살아 있는 태스크에 닿는다.
  2. 범위 확장계정과 VPC를 넘나드는 연결이 필요하면 VPC Lattice 서비스(여러 네트워크를 묶는 연결 관리)를 생성해 붙이므로 외부 범위에서도 호출이 이어진다.
  3. 쏠림 해소AZ 리밸런싱(가용영역별 개수를 고르게 되돌리는 조정)이 쏠림을 감지해 재배치하므로 특정 구역 장애에도 서비스가 유지된다.

CloudWatch 메트릭과 Container Insights

#2핵심 질문

#3동작 예시

ECS가 클러스터와 서비스의 데이터를 1분 간격으로 CloudWatch에 보내면 2주간 기록이 남는다. Fargate 서비스는 CPU와 메모리 사용률 지표를 보고, 더 세밀한 태스크 단위 확인이 필요하면 Container Insights를 켜서 CPU와 메모리, 디스크 사용량을 본다.

#4동작 과정

  1. 자동 수집ECS가 클러스터와 서비스의 원시 데이터를 1분 단위로 CloudWatch 지표로 보내서 바로 읽을 수 있게 한다.
  2. 기본 지표 확인무료로 제공되는 클러스터와 서비스 지표, Fargate의 CPU와 메모리 사용률로 현재 상태와 예약, 사용 흐름을 본다.
  3. 심화 관측 켜기필요하면 클러스터에 Container Insights를 켜서 태스크 단위 CPU와 메모리, 파일시스템 사용량을 확인한다.

#1문제 상황

#2핵심 질문

ECS 상태 변화를 실시간에 가깝게 받아 정해진 대응을 자동으로 실행할 수는 없을까?

#3동작 예시

#4동작 과정

  1. 이벤트 받기인스턴스와 태스크, 서비스와 배포, 상태 확인 관련 ECS 이벤트를 EventBridge가 실시간에 가깝게 전달받아 변화를 바로 알게 한다.
  2. 규칙 매칭미리 적은 규칙으로 관심 있는 이벤트인지 판별해서 대응 대상만 걸러낸다.
  3. 자동 실행로그 기록과 Lambda 실행, Step Functions 실행, SNS나 SQS 알림 같은 동작을 실행해서 대응을 남기고 이어지게 한다.

#2핵심 질문

#3동작 예시

#4동작 과정

  2. 상태 읽기컨테이너 상태 확인(헬스체크, 정상 여부를 확인하는 설정)과 태스크 메타데이터 엔드포인트(컨테이너 정보를 조회하는 주소)로 현재 상태를 파악한다.
  3. 기록과 추적필요하면 로그 확인과 추적, 지표 확인으로 이어서 원인을 좁히고 긴급 접근 기록을 남긴다.

#2핵심 질문

#4동작 과정

  1. 인증 구분IAM 사용자나 역할이 누구인지 확인하는 절차와 ECS 자원을 쓸 수 있게 허락하는 절차를 나눠서 관리 주체를 분명히 한다.
  2. 역할 분리실행 역할과 태스크 역할, 인스턴스 역할, 배포와 로드밸런서 관련 역할, 서비스 연결 역할을 나눠서 각 작업에 필요한 권한만 준다.
  3. 통제와 점검정책 예제와 관리형 정책, 태그 기반 접근 통제(태그 값에 따라 허용을 정하는 방식)와 모범 사례로 권한을 좁히고 문제를 확인한다.
