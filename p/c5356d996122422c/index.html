Amazon ECS와 3계층 구조: 용량·컨트롤러·프로비저닝

Amazon ECS 는 컨테이너를 대신 실행·관리해 주는 AWS 완전 관리형 오케스트레이션 서비스로, 컨테이너가 돌아갈 용량 계층·원하는 상태를 지켜주는 컨트롤러 계층·사람이 조작하는 프로비저닝 계층의 세 층으로 이해하면 된다.

#1문제 상황

전통적으로 컨테이너를 직접 관리할 때는 서버에 Docker를 설치하고, 실행 상태를 수동으로 모니터링하고, 필요시 직접 재시작하거나 추가 서버를 구비해야 했습니다. 또한 이런 인프라 수준의 관리와 개발자가 원하는 애플리케이션 상태(원하는 개수의 컨테이너 계속 유지, 실패한 컨테이너 자동 재시작)를 맞춰나가는 것이 복잡했습니다.

#2핵심 질문

컨테이너를 실행하기 위해 필요한 인프라와 상태 관리를 AWS가 대신 책임지면서도, 내가 원하는 대로 제어할 수 있는 방법이 있을까?

#3동작 예시

Amazon ECS는 컨테이너 작업을 실행하고 관리하는 과정을 세 개의 계층으로 나눕니다. 아래부터 위로, 용량 계층(어디서 돌릴 것인가)에서 EC2 인스턴스나 Fargate 리소스 같은 컴퓨팅 기반을 준비하고, 그 위 컨트롤러 계층(몇 개를 유지할 것인가)에서 서비스가 원하는 작업 개수를 지속적으로 유지하며, 최상단 프로비저닝 계층(사람이 명령 내리기)에서 사용자가 콘솔이나 CLI로 "3개 띄워달라", "이 이미지를 사용해달라" 등 원하는 상태를 선언합니다.

#4동작 과정

  1. 용량 계층 준비컨테이너가 실행될 EC2 인스턴스나 Fargate 리소스를 확보합니다.
  2. 컨트롤러 계층이 상태 유지서비스가 사용자가 선언한 원하는 작업 개수를 감시하다가, 실패한 작업을 감지하면 자동으로 새로운 작업을 실행해 개수를 맞춥니다.
  3. 프로비저닝 계층이 사용자 명령 수용사용자가 콘솔이나 CLI로 명령하면 컨트롤러와 용량 계층이 그에 맞게 작동합니다.

#5한 줄 요약

Amazon ECS사용자가 원하는 애플리케이션 상태(몇 개 실행, 어떤 이미지)만 선언하면, AWS가 인프라와 런타임 상태를 자동으로 유지해주는 선언형 오케스트레이션 서비스

클러스터(작업이 모이는 논리 공간), 작업 정의(컨테이너 실행 설계도), 작업(실제 실행 단위), 서비스(원하는 개수를 계속 유지), 컨테이너 인스턴스(작업을 태우는 서버) 다섯 가지가 ECS 를 이루는 기본 부품이다.

#1문제 상황

컨테이너 한두 개만 돌릴 때는 직접 관리해도 되지만, 여러 컨테이너가 협력하고 프로덕션 환경에서 스케일링되려면 각각을 어떻게 정의하고, 어디에 배치하고, 어떻게 지속적으로 유지할지 체계적으로 관리해야 합니다.

#2핵심 질문

여러 컨테이너를 조직적으로 정의하고, 실행하고, 지속적으로 유지하려면 어떤 기본 구성 요소가 필요할까?

#3동작 예시

웹 서비스를 ECS에서 돌린다면, 먼저 작업 정의(Task Definition)에서 Docker 이미지와 CPU, 메모리 같은 실행 스펙을 정의하고, 서비스(Service)가 이 작업을 항상 3개 띄운 상태로 유지하며, 컨테이너 인스턴스(Container Instance)들이 그 작업들을 실제로 호스트합니다. 이 모든 것이 클러스터(Cluster)라는 하나의 논리 공간에 모입니다.

#4동작 과정

  1. 클러스터작업이 모이는 논리적 단위로, 한 AWS 계정 내에 여러 클러스터를 생성할 수 있습니다.
  2. 작업 정의, 작업, 컨테이너 인스턴스작업 정의는 컨테이너 실행 설계도, 작업은 실제 실행 단위, 컨테이너 인스턴스는 그 작업을 호스트하는 서버 또는 리소스입니다.
  3. 서비스원하는 개수의 작업을 지속적으로 실행하고 유지하는 관리 단위입니다.

#5한 줄 요약

Amazon ECS클러스터, 작업 정의, 작업, 서비스, 컨테이너 인스턴스라는 다섯 가지 기본 구성 요소를 통해 컨테이너 애플리케이션의 정의와 실행, 유지를 체계화한 오케스트레이션 프레임워크

ECS를 조작하는 인터페이스: 콘솔·CLI·SDK·CDK·CloudFormation·Copilot·MCP

같은 ECS API 를 웹 콘솔, AWS CLI, 각 언어 SDK, 코드형 인프라(CDK·CloudFormation), 앱 중심 Copilot CLI, AI 에이전트용 ECS MCP 서버 등 여러 창구로 똑같이 조작할 수 있다.

#1문제 상황

일반적으로 AWS 서비스를 다루려면 웹 콘솔에만 익숙하거나, AWS CLI(명령줄 도구)를 따로 배워야 합니다. 인프라가 복잡해지면 Python, Java, Node.js 같은 특정 언어 SDK도 써야 하고, Infrastructure as Code를 하려면 또 다른 도구를 배워야 하므로 학습 곡선이 가팔랐습니다.

#2핵심 질문

같은 ECS 작업을 웹 콘솔로 할 때와 코드로 할 때, 다른 학습과 도구를 일일이 배워야 할까?

#3동작 예시

ECS API는 한 번만 설계되어 있고, 웹 콘솔, AWS CLI, Python·Java·Node.js 같은 각 언어 SDK, Terraform·CloudFormation 같은 코드형 인프라 도구, 앱 중심의 Copilot CLI, AI 에이전트용 ECS MCP 서버는 모두 같은 API를 다른 인터페이스로 제공할 뿐입니다. 어느 방식을 택하든 내부적으로는 같은 ECS 리소스가 생성되고 관리됩니다.

#4동작 과정

  1. 개발자용 직접 조작 도구웹 콘솔(시각적 인터페이스), AWS CLI(스크립트), 각 언어 SDK(프로그래밍 방식)는 모두 같은 ECS API를 호출합니다.
  2. 코드형 인프라 도구CloudFormation과 CDK(AWS의 IaC 도구), Terraform은 ECS 리소스를 선언적으로 정의하고, 결국 같은 API를 통해 배포합니다.
  3. 상위 추상화Copilot CLI는 앱 중심으로, ECS MCP 서버는 AI 에이전트가 조작하게 하는 식으로, ECS 복잡도를 더 상위에서 감춥니다.

첫 배포로 흐름 익히기: 설정·이미지 생성·작업 실행

계정·IAM·CLI 설정을 마치고 컨테이너 이미지를 만들어 레지스트리에 올린 뒤 작업 정의를 등록해 실행하는 것이 ECS 의 가장 기본적인 배포 흐름이다.

#1문제 상황

컨테이너를 직접 관리할 때는 Docker를 설치하고, 이미지를 빌드하고, 이미지 레지스트리에 올리고, 서버에 SSH로 접속해서 직접 실행하는 여러 단계를 수동으로 해야 했습니다. 각 단계마다 환경 차이, 권한 설정, 네트워킹 문제 등이 발생할 여지가 많았습니다.

#2핵심 질문

ECS를 처음 사용할 때, 가장 최소한의 단계로 컨테이너를 실행하는 흐름은 무엇인가?

#3동작 예시

AWS 계정 설정과 IAM 권한이 준비된 후, 로컬에서 Docker 이미지를 만들고 Amazon ECR(AWS 이미지 저장소)에 push한 뒤, ECS 콘솔에서 작업 정의를 등록하고 작업을 실행하면, ECS 클러스터 내 컨테이너가 자동으로 실행됩니다. 이것이 가장 기본적인 배포 경로입니다.

#4동작 과정

  1. 사전 설정AWS 계정 생성, IAM 권한 부여, AWS CLI 설치 및 자격증명 구성을 완료합니다.
  2. 이미지 준비Dockerfile을 작성해 로컬에서 이미지를 빌드하고, AWS CLI로 ECR에 push합니다.
  3. ECS 배포ECS 콘솔에서 작업 정의를 등록(이미지 주소, CPU, 메모리 지정)하고, 클러스터에서 작업을 실행합니다.

#5한 줄 요약

Amazon ECS사용자가 로컬에서 준비한 컨테이너 이미지만 ECR에 올리면, ECS가 그 이미지를 클러스터 내 인스턴스에서 자동으로 실행하고 관리하는 간단한 배포 경로를 제공하는 서비스

Amazon ECS Express Mode: 최소 입력으로 완성형 서비스

Express Mode 는 컨테이너 이미지와 포트 정도만 주면 클러스터·로드 밸런서·네트워킹·서비스까지 ECS 가 알아서 만들어 인터넷에 공개되는 웹 서비스를 한 번에 띄워 주는 간편 경로다.

#1문제 상황

웹 서비스를 ECS에서 프로덕션처럼 돌리려면 보통 클러스터를 만들고, 로드 밸런서(ALB 또는 NLB)를 설정하고, 네트워킹(VPC, 서브넷, 보안 그룹)을 구성하고, 서비스 리소스를 정의해야 합니다. 간단한 웹 서비스도 여러 구성 단계가 필요했습니다.

#2핵심 질문

컨테이너 이미지와 포트 정도만으로 인터넷에 접근 가능한 완성된 웹 서비스를 한 번에 띄울 수 있을까?

#3동작 예시

ECS Express Mode는 Dockerfile 또는 기존 공개 이미지와 노출할 포트 번호만 주면, ECS가 클러스터, ALB(Application Load Balancer, 트래픽 분산), 보안 그룹(방화벽 규칙), 서비스를 자동으로 생성하고 퍼블릭 IP를 할당해서 몇 분 안에 웹 서비스가 인터넷에 공개됩니다.

#4동작 과정

  1. Dockerfile 또는 이미지 준비자신의 Dockerfile을 준비하거나 기존 공개 이미지(nginx, node, python 등)를 선택합니다.
  2. Express Service 선택 및 포트 입력ECS 콘솔에서 "Create service" → "Express Service" 선택, 노출할 포트를 입력합니다.
  3. 자동 구성 및 배포ECS가 클러스터, 로드 밸런서, 네트워킹, 서비스를 자동 생성하고 즉시 시작합니다.

#5한 줄 요약

Amazon ECS Express Mode컨테이너 이미지 하나로 완성형 웹 서비스 인프라를 자동 생성해주는 간편 경로로, 복잡한 설정 없이 빠르게 애플리케이션을 배포하는 데 초점을 맞춘 기능

실행 유형과 용량 공급자: 무엇이 다르고 무엇을 고를 것인가

태스크를 어떤 인프라에서 돌릴지 정하는 선택지(Fargate·EC2·Managed Instances·External)와, 그 용량을 자동으로 대주는 용량 공급자의 차이를 비교하는 출발점.

#1문제 상황

컨테이너를 어디서 돌릴지 정하는 것은 비용, 성능, 제어 사이의 트레이드오프입니다. EC2 인스턴스를 직접 구매하면 제어는 최대이지만 비용 관리가 복잡하고, 반대로 Fargate 서버리스는 편하지만 가격 변동에 반응이 늦을 수 있습니다.

#2핵심 질문

ECS에서 컨테이너를 돌릴 인프라를 선택할 때, 비용과 제어의 균형을 어떻게 잡을 것인가?

#3동작 예시

Fargate(서버리스, 태스크당 CPU·메모리 비용)에서 시작해 비용이 높으면 EC2(인스턴스 단위, 여러 작업 공유)로 옮기고, 더 제어하고 싶으면 EC2 On-Demand 대신 Reserved Instances(1~3년 할인) 또는 Spot Instances(여유 용량 낙찰)를 선택하는 식으로, 실행 유형(Fargate, EC2, Managed Instances, External)과 용량 공급자(Capacity Provider, 자동 스케일링)를 조합해 최적을 찾습니다.

#4동작 과정

  1. 실행 유형 선택Fargate(간단, 비용 고정, 서버 관리 없음), EC2(비용 낮음, 제어 큼, 인스턴스 관리 필요), Managed Instances(AWS가 EC2 관리), External(온프레미스 또는 타 클라우드)의 네 가지 중 선택합니다.
  2. 용량 공급자 결정각 실행 유형마다 자동 스케일링 규칙을 설정하고, 부하에 따라 자동으로 확장·축소하도록 구성합니다.
  3. 서비스 연결서비스가 용량 공급자를 통해 작업을 배치하고, 필요한 만큼만 리소스를 사용합니다.

#5한 줄 요약

Amazon ECS실행 유형과 용량 공급자라는 두 개의 선택지를 통해 동일한 컨테이너를 다양한 비용·제어 조합으로 배포할 수 있게 하는 유연한 인프라 추상화

AWS Fargate: 서버리스 컴퓨팅과 플랫폼 버전

서버(EC2 인스턴스)를 하나도 만들지 않고 태스크 단위로만 CPU·메모리를 지정해 실행하는 서버리스 방식이며, 실행 환경의 커널·에이전트 조합은 플랫폼 버전으로 관리된다.

#1문제 상황

전통적으로 애플리케이션을 배포하려면 EC2 인스턴스를 구매하고, OS와 런타임을 설치하고, 보안 패치를 관리하고, 한 인스턴스가 여러 애플리케이션을 호스트해야 합니다. 이 모든 관리 부담이 있었습니다.

#2핵심 질문

인스턴스라는 개념 없이, 필요한 CPU와 메모리만 지정해서 컨테이너를 실행할 수 있을까?

#3동작 예시

AWS Fargate는 "m5.large 인스턴스 3개 구매"가 아니라 "CPU 1024, 메모리 2048 MiB인 작업을 3개 돌린다"는 선언만 하면, AWS가 뒤에서 EC2 인스턴스와 Linux 커널, ECS 에이전트(관리 소프트웨어) 같은 런타임 환경 전체를 관리합니다. 플랫폼 버전(LINUX_V1_4 같은)으로 커널과 에이전트의 버전 조합을 선택할 수 있습니다.

#4동작 과정

  1. 작업 정의에서 리소스 지정EC2처럼 인스턴스 타입을 선택하지 않고, 필요한 CPU와 메모리만 입력합니다.
  2. Fargate 실행 유형 선택ECS가 플랫폼 버전(Linux 커널·ECS 에이전트 조합)을 자동으로 선택하거나 사용자가 지정하고, AWS 관리 인프라에서 실행합니다.
  3. 청구EC2 인스턴스 단위가 아니라 실제 실행한 CPU·메모리·시간에 대해서만 초 단위로 청구됩니다.

#5한 줄 요약

AWS Fargate인스턴스 관리를 완전히 추상화하고, 사용자가 필요한 컴퓨팅 리소스(CPU·메모리)만 지정하면 AWS가 플랫폼 버전(커널·에이전트 조합)을 통해 서버리스 환경을 제공하는 완전 관리형 컨테이너 실행 방식

Fargate 태스크 운영 특성: 이미지 풀·임시 스토리지·태스크 은퇴

Fargate 태스크는 매번 이미지를 새로 내려받고, 정해진 크기의 임시 스토리지를 쓰며, 플랫폼 갱신 시 AWS 가 태스크를 은퇴시켜 교체한다는 운영상의 제약.

→ 02-02 참조

#1문제 상황

전통적으로 EC2 인스턴스를 직접 소유하면, 한 번 띄운 인스턴스는 사용자가 패치하고 관리할 때까지 계속 존재합니다. 하지만 Fargate는 완전 관리형 서버리스 환경이므로, 태스크의 생명 주기와 스토리지가 고정되지 않습니다. AWS가 플랫폼을 갱신할 때마다 태스크가 자동으로 교체되고, 스토리지도 제한된 임시 용량만 제공됩니다.

#2핵심 질문

Fargate 에서 실행되는 태스크는 언제든 교체될 수 있고, 스토리지도 제한되는데 이를 감안하고 설계해야 하는 이유는 무엇인가?

#3동작 예시

Fargate 태스크가 시작되면 Docker 이미지를 매번 새로 다운로드하고, 사용 중인 임시 스토리지는 정해진 크기(예: 20GB)로 제한됩니다. AWS가 플랫폼을 정기적으로 갱신할 때 이 태스크는 자동으로 은퇴되고 새로운 태스크로 교체됩니다.

#4동작 과정

  1. 이미지 풀태스크 시작 시 매번 Docker 이미지를 Amazon ECR(Elastic Container Registry, 컨테이너 이미지를 저장하는 저장소)에서 새로 다운로드합니다.
  2. 임시 스토리지 할당태스크에 할당된 고정 크기의 임시 스토리지를 사용하며, 이 용량을 초과할 수 없습니다.
  3. AWS 플랫폼 갱신 시 태스크 은퇴AWS 인프라 정기 갱신 시 실행 중인 태스크는 자동으로 중단되고 새 태스크로 교체됩니다.

#5한 줄 요약

Fargate 태스크가 일시적 특성을 가지며 매번 새롭게 시작되고 AWS의 플랫폼 갱신에 따라 언제든 교체될 수 있다는 운영 제약을 이해하고 설계하는 것

EC2 실행 유형: 직접 소유하고 관리하는 컨테이너 인스턴스

사용자가 직접 띄우고 패치·확장까지 책임지는 EC2 인스턴스를 클러스터에 등록해 컨테이너를 돌리는 전통적인 방식.

#1문제 상황

서버를 직접 구매해서 데이터센터에 두는 온프레미스 방식에서는 인스턴스 선택부터 패치, 확장까지 모든 것을 사용자가 관리합니다. EC2 실행 유형도 동일한 철학입니다. 사용자가 EC2 인스턴스를 직접 선택·생성·등록하고, 컨테이너 기반의 인프라를 직접 관리해야 합니다.

#2핵심 질문

인프라의 모든 것을 직접 통제하면서 ECS에서 컨테이너를 실행하려면 어떻게 하는가?

#3동작 예시

사용자가 EC2 인스턴스(예: t3.medium)를 AWS 콘솔에서 직접 생성하고, 그 인스턴스에 ECS 에이전트를 설치한 후 ECS 클러스터에 등록하면, 그 인스턴스는 컨테이너 실행 환경이 됩니다.

#4동작 과정

  1. EC2 인스턴스 생성사용자가 직접 원하는 사양(CPU, 메모리, 스토리지)의 EC2 인스턴스를 선택해 생성합니다.

#1문제 상황

#2핵심 질문

전체 작업이 얼마만큼의 CPU와 메모리를 필요로 하는지 미리 정하고, 그 만큼을 인스턴스에서 예약하려면 어떻게 해야 할까요?

#3동작 예시

#4동작 과정

  1. 작업 수준 CPU 지정전체 작업이 예약할 CPU 유닛을 정합니다(256, 512, 1024, 2048 등).

  3. EC2 인스턴스에서 스왑 설정(선택사항)EC2 런치 타입을 쓸 때 스왑 메모리 크기를 따로 설정할 수 있습니다.

태스크 네트워크 모드: awsvpc·bridge·host

컨테이너가 네트워크에 붙는 방식으로, awsvpc는 작업마다 전용 ENI와 사설 IP를 주고 bridge는 도커 가상 네트워크를, host는 호스트 인스턴스의 네트워크를 그대로 쓴다.

#1문제 상황

기존에는 컨테이너가 네트워크에 붙는 방식이 고정되어 있었고, 다양한 워크로드의 요구를 충족하기 어려웠습니다. 격리가 필요한 경우도 있고, 컨테이너 간 통신이 쉬워야 하는 경우도 있고, 성능을 위해 호스트 네트워크를 직접 써야 하는 경우도 있었는데, 선택지가 제한되었습니다.

#2핵심 질문

작업의 각 컨테이너가 네트워크에 어떻게 연결되어야 할까요 — 전용 네트워크 인터페이스를 받을지, Docker의 가상 네트워크를 쓸지, 아니면 호스트의 네트워크를 직접 공유할지?

#3동작 예시

awsvpc 모드 작업은 각 작업마다 전용 탄력적 네트워크 인터페이스(가상 네트워크 카드)를 받아서 VPC 내 사설 IP 주소를 할당받습니다. bridge 모드 컨테이너는 Docker 내부의 가상 네트워크를 통해 통신하고, host 모드 컨테이너는 실제 호스트 인스턴스의 네트워크 인터페이스를 그대로 공유해서 성능상 오버헤드가 거의 없습니다.

#4동작 과정

  1. 네트워크 모드 선택awsvpc(작업마다 전용 ENI), bridge(Docker 가상 네트워크), host(호스트 네트워크 공유) 중 하나를 선택합니다.
  2. 네트워크 자원 할당awsvpc는 ECS가 자동으로 ENI를 만들고 사설 IP를 할당하며, bridge와 host는 기존 네트워크 인프라를 사용합니다.
  3. 컨테이너 트래픽 흐름모든 컨테이너 네트워크 트래픽이 선택된 경로를 통해 흘러갑니다.

#5한 줄 요약

작업의 네트워크 격리 수준과 성능 요구에 따라 세 가지 네트워크 모드 중 선택하는 것입니다: 격리와 VPC 기능이 필요하면 awsvpc, 컨테이너 간 통신이 쉬워야 하면 bridge, 최고 성능이 필요하면 host

#4동작 과정

  2. 작업 정의에서 ARN으로 참조실제 값이 아니라 저장소의 ARN이나 이름만 작업 정의에 적습니다.
  3. 런타임에 ECS가 주입작업이 시작될 때 ECS가 Secrets Manager에서 값을 가져와 환경 변수로 컨테이너에 전달합니다.

특수 하드웨어 워크로드 작업 정의: GPU·Neuron·ARM64·트랜스코딩

GPU 개수, AWS Neuron 추론 칩, ARM64 CPU 아키텍처, VT1 비디오 트랜스코딩 같은 특수 자원을 작업 정의에서 명시해 알맞은 인스턴스에 배치되게 하는 방법이다.

#1문제 상황

기존에는 모든 작업이 범용 인스턴스에서만 실행되었습니다. 머신러닝, 비디오 처리, 추론 같은 특수 워크로드가 특정 하드웨어(GPU, AWS Neuron 칩, 특정 CPU 아키텍처)를 필요로 해도 그것을 명시할 방법이 없었고, 결과적으로 성능이 떨어지거나 사용할 수 없는 상황이 생겼습니다.

#2핵심 질문

작업이 GPU, AWS Neuron, ARM64 같은 특수 하드웨어를 필요로 한다면 어떻게 명시해서 올바른 인스턴스에 배치시킬까요?

#3동작 예시

머신러닝 추론 작업이 1개의 GPU를 필요하면 작업 정의에 requiresCompatibilities: ["gpu"]와 containerDefinitions[].resourceRequirements 에 GPU 개수 1을 명시합니다. ECS 스케줄러는 이 작업을 배치할 때 GPU가 최소 1개 이상 남아있는 인스턴스만 선택합니다.

#4동작 과정

  1. 작업 정의에 하드웨어 요구사항 선언GPU 개수, Neuron 유닛, ARM64 요구사항, VT1 비디오 트랜스코딩 능력 등을 명시합니다.
  2. ECS 스케줄러가 호환 인스턴스 필터링요청된 하드웨어가 없는 인스턴스는 배제됩니다.
  3. 선언된 하드웨어가 있는 인스턴스에만 배치작업은 필요한 자원이 충분한 곳에서만 실행됩니다.

#5한 줄 요약

작업 정의에서 필요한 특수 하드웨어를 명시해서 ECS 스케줄러가 그 하드웨어를 가진 인스턴스를 선택하도록 강제하는 것

플랫폼별 파라미터 차이와 작업 정의 수명 주기 관리

같은 작업 정의라도 Fargate·EC2·Managed Instances에 따라 지원되는 파라미터가 다르며, 리비전 등록·업데이트·등록 해제·삭제로 수명 주기를 관리한다.

→ 03-01 참조

#1문제 상황

기존에는 컨테이너를 실행할 때 CPU, 메모리, 포트, 환경변수 등 모든 설정을 일일이 지정해야 했습니다. 하지만 같은 컨테이너를 여러 번 실행하려면 설정을 계속 반복 입력해야 하는 번거로움이 있었고, 설정 실수가 발생할 위험도 높았습니다.

#2핵심 질문

컨테이너 실행에 필요한 모든 설정을 한 번 정의한 후 여러 번 재사용하면서, 실행 환경(Fargate/EC2/Managed Instances)에 맞게 파라미터를 구분해서 관리할 수 있을까요?

#3동작 예시

작업 정의는 컨테이너 실행에 필요한 설정을 JSON 형식으로 저장하는 템플릿입니다. 예를 들어 Node.js 웹 애플리케이션을 실행하려면 "컨테이너 이미지 주소, 포트 8080 사용, 메모리 512MB 할당, 환경변수 DATABASE_URL=xxx" 같은 내용을 한 번 정의하면, 나중에 이 정의를 불러와 동일한 설정으로 여러 번 태스크를 생성할 수 있습니다.

#4동작 과정

  1. 작업 정의 등록컨테이너 이미지, 리소스(CPU/메모리), 포트 맵핑, 로그 설정 등을 JSON으로 작성하고 ECS에 등록합니다. 이를 리비전(revision)이라 하며, 같은 이름의 정의를 여러 번 등록할 때마다 버전 번호가 증가합니다(my-app:1, my-app:2 등).
  2. 플랫폼별 파라미터 구분Fargate에서 실행할 때는 networkMode를 "awsvpc"로 고정하고 정확한 CPU/메모리 조합만 허용하지만, EC2에서는 더 다양한 옵션을 지원합니다. 각 플랫폼이 지원하는 파라미터만 지정해야 태스크 실행이 성공합니다.
  3. 수명 주기 관리새로운 버전을 등록하거나 기존 리비전을 "ACTIVE"(현재 사용 중)에서 "INACTIVE"(더 이상 사용 안 함)로 변경할 수 있으며, 불필요한 정의는 삭제합니다.

#5한 줄 요약

컨테이너 실행에 필요한 모든 설정을 버전 관리되는 템플릿으로 저장해 재사용성을 높이고, 각 실행 환경이 지원하는 파라미터만 선택 적용할 수 있도록 하는 것

4클러스터와 인프라 운영04-01

클러스터의 역할과 Fargate 클러스터 만들기

클러스터는 태스크와 서비스를 담는 논리적 그룹이며, Fargate 클러스터는 서버 관리 없이 바로 컨테이너를 실행할 수 있는 가장 단순한 출발점이다.

#1문제 상황

기존에는 컨테이너를 실행하려면 먼저 서버를 구매하고, 운영체제를 설치하고, 컨테이너 런타임을 설정한 후, 그 서버에 접속해 컨테이너를 실행해야 했습니다. 서버 관리와 컨테이너 실행이 섞여 있어서 복잡했고, 서버가 부족하면 추가로 구매해야 하는 번거로움이 있었습니다.

#2핵심 질문

서버 관리 없이 바로 컨테이너만 실행할 수 있는 환경을 어떻게 만들 수 있을까요?

#3동작 예시

클러스터는 태스크와 서비스가 실행되는 논리적 그룹입니다. Fargate 클러스터를 만들면 AWS가 서버를 대신 관리하므로, 사용자는 "얼마나 많은 CPU와 메모리가 필요한가"만 지정하고 컨테이너를 실행하면 됩니다. 백그라운드에서 AWS가 적절한 서버를 할당하고 관리합니다.

#4동작 과정

  1. Fargate 클러스터 생성"Fargate 시작 유형" 옵션으로 클러스터를 만들면, 서버 관리가 필요 없는 상태가 됩니다. 클러스터 이름과 VPC, 서브넷 같은 네트워크 설정만 지정합니다.
  2. 태스크 정의와 함께 실행작업 정의(task definition)에서 "Fargate" 플랫폼을 선택하고 필요한 CPU와 메모리를 지정합니다.
  3. 태스크 자동 배치ECS는 지정한 리소스(CPU/메모리)가 가능한 서버를 자동으로 찾아 태스크를 실행합니다. 사용자는 서버 개수나 상태를 신경 쓸 필요가 없습니다.

#5한 줄 요약

클러스터를 논리적 경계로 삼아 태스크를 그룹화하고, Fargate를 사용해 서버 인프라 관리 책임을 AWS에 넘겨 컨테이너 실행에만 집중하게 하는 것

EC2 워크로드용 Auto Scaling 그룹 용량 공급자

용량 공급자는 EC2 Auto Scaling 그룹을 ECS 클러스터에 연결해, 태스크 수요에 맞춰 인스턴스 용량을 자동으로 공급하는 다리 역할을 한다.

#1문제 상황

EC2 인스턴스에서 컨테이너를 실행하려면 먼저 필요한 개수의 인스턴스를 구매한 후 ECS 클러스터에 등록해야 합니다. 하지만 처음에 구매한 인스턴스 개수로는 충분하지 않을 수 있고, 정확히 몇 개가 필요한지 예측하기 어려우며, 수동으로 인스턴스를 추가하거나 제거하는 과정이 번거롭습니다.

#2핵심 질문

EC2 인스턴스의 개수를 태스크 수요에 맞춰 자동으로 조절할 수 있을까요?

#3동작 예시

용량 공급자는 EC2 Auto Scaling 그룹(여러 인스턴스를 자동으로 늘리고 줄이는 기능)을 ECS 클러스터에 연결하는 연결고리입니다. 예를 들어 "최소 2개, 최대 10개의 t3.medium 인스턴스"를 Auto Scaling 그룹으로 만들고, 이를 ECS의 용량 공급자로 등록하면, ECS는 실행 중인 태스크 수를 보고 필요한 인스턴스 개수를 자동 조절합니다.

#4동작 과정

  1. Auto Scaling 그룹 생성사용할 인스턴스 타입, 최소/최대 개수, VPC와 서브넷을 지정해 Auto Scaling 그룹을 만듭니다.
  2. 용량 공급자 등록ECS 클러스터에서 "용량 공급자" 메뉴로 이 Auto Scaling 그룹을 연결합니다. ECS가 이제 이 그룹에 접근할 권한을 가집니다.
  3. 태스크 수에 따라 자동 조절새로운 태스크를 실행할 때 충분한 인스턴스 공간이 없으면 Auto Scaling 그룹이 인스턴스를 추가하고, 태스크가 종료되어 리소스가 남으면 인스턴스를 줄입니다.

#5한 줄 요약

EC2 Auto Scaling 그룹을 ECS에 연결해 태스크 수요에 맞춰 인스턴스 개수를 자동으로 공급하는 것

4클러스터와 인프라 운영04-03

클러스터 오토 스케일링: 관리형 스케일링·종료 보호·드레이닝

ECS 가 CloudWatch 기반 관리형 스케일링으로 인스턴스를 늘리고, 종료 보호와 드레이닝으로 태스크가 도는 인스턴스를 안전하게 줄이는 구조다.

#1문제 상황

Auto Scaling 그룹만으로는 인스턴스 개수 조절이 충분하지 않습니다. 단순히 "CPU 사용률이 70%이면 인스턴스 추가" 같은 기준으로는 컨테이너 태스크가 실행될 충분한 공간을 보장할 수 없고, 태스크가 실행 중인 인스턴스를 무작정 종료할 수도 없습니다. 또한 수동으로 인스턴스를 종료할 때 실행 중인 태스크를 처리하는 과정이 복잡합니다.

#2핵심 질문

ECS가 직접 태스크 배치를 고려해서 인스턴스를 추가하고, 태스크 안전성을 보장하면서 인스턴스를 종료할 수 있을까요?

#3동작 예시

ECS의 관리형 스케일링은 "현재 태스크들이 필요로 하는 전체 CPU/메모리" 대 "인스턴스에 남은 여유 리소스"를 비교하고, 부족하면 인스턴스를 추가합니다. 반대로 불필요한 인스턴스를 종료할 때는 먼저 해당 인스턴스의 태스크를 다른 인스턴스로 옮긴 후(드레이닝, draining) 인스턴스를 끕니다.

#4동작 과정

  1. 관리형 스케일링 활성화용량 공급자에서 "관리형 스케일링" 옵션을 켜면, ECS가 자동으로 스케일링을 제어합니다. 사용자는 목표 CPU/메모리 사용률(예: 80%)만 지정합니다.
  2. 종료 보호와 드레이닝인스턴스 종료 전에 ECS는 해당 인스턴스의 모든 태스크를 다른 인스턴스로 옮깁니다(드레이닝). 이 과정 중 새로운 태스크가 이 인스턴스에 배치되지 않도록 보호합니다(종료 보호, termination protection).
  3. 인스턴스 정리모든 태스크가 옮겨진 후, 인스턴스를 안전하게 종료합니다.

#5한 줄 요약

ECS가 태스크 수요를 예측해 인스턴스를 추가하고, 인스턴스 종료 시 운영 중인 태스크를 안전하게 이동시켜 서비스 중단 없이 인프라를 관리하는 것

Managed Instances 클러스터와 용량 공급자 관리

Managed Instances 는 EC2 인스턴스의 프로비저닝·패치·수명 관리를 AWS 가 대신 맡아주는 방식으로, 전용 클러스터와 용량 공급자로 구성한다.

#1문제 상황

EC2 인스턴스를 직접 관리하면 보안 패치 설치, 운영체제 업데이트, ECS 에이전트 버전 관리 등 많은 유지보수 작업이 발생합니다. 또한 인스턴스가 손상되거나 성능이 저하되는 상황을 감지하고 대응하는 것도 사용자의 책임입니다. 이런 관리 부담이 누적되면 신뢰성과 보안이 떨어질 수 있습니다.

#2핵심 질문

EC2 인스턴스의 패치, 업데이트, 상태 모니터링 같은 관리를 AWS에 맡길 수 있을까요?

#3동작 예시

Managed Instances는 AWS가 EC2 인스턴스의 프로비저닝, 패치, 수명 관리를 대신 담당하는 방식입니다. 사용자는 "이 클러스터에는 t3.medium 인스턴스가 최소 5개 필요"라고 지정하기만 하면, AWS가 필요한 인스턴스를 만들고, 보안 업데이트를 자동 적용하고, 장애난 인스턴스를 교체하는 모든 과정을 처리합니다.

#4동작 과정

  1. Managed Instances 클러스터 생성클러스터 생성 시 "EC2" 시작 유형 대신 "Managed Instances" 옵션을 선택합니다. 인스턴스 타입과 원하는 개수만 지정합니다.
  2. 용량 공급자 자동 구성Managed Instances 클러스터는 자동으로 용량 공급자를 만들고, 관리형 스케일링을 활성화합니다. 사용자는 추가 설정이 거의 필요 없습니다.
  3. 자동 유지보수AWS가 정기적으로 패치와 업데이트를 적용하고, 장애 인스턴스를 자동 교체합니다. 사용자는 이 모든 과정을 투명하게 볼 수 있습니다.

#5한 줄 요약

EC2 인스턴스 관리 책임의 대부분(패치, 업데이트, 상태 모니터링, 교체)을 AWS에 위임하고, 사용자는 필요한 용량과 성능 만 지정하는 것

ECS 최적화 AMI와 컨테이너 인스턴스 시작·구성

ECS 최적화 AMI 는 에이전트와 런타임이 미리 들어간 이미지로, 이를 사용해 컨테이너 인스턴스를 시작하고 부트스트랩 설정을 넣는다.

#1문제 상황

일반 EC2 인스턴스에 컨테이너를 실행하려면 먼저 Docker 같은 컨테이너 런타임을 설치하고, ECS 에이전트를 설치한 후, 에이전트가 ECS 제어 평면과 통신하도록 IAM 권한을 설정해야 합니다. 이런 설정을 처음부터 다 하는 것은 복잡하고 실수하기 쉽습니다.

#2핵심 질문

컨테이너 런타임과 ECS 에이전트가 이미 설치된 상태의 인스턴스를 바로 시작할 수 있을까요?

#3동작 예시

ECS 최적화 AMI(Amazon Machine Image)는 AWS가 미리 준비한 이미지로, 컨테이너 런타임(Docker, containerd 등)과 ECS 에이전트가 이미 설치되어 있습니다. 이 이미지로 인스턴스를 시작하면 추가 설치 없이 바로 컨테이너를 실행할 수 있습니다.

#4동작 과정

  1. ECS 최적화 AMI 선택EC2 인스턴스 시작 시 AWS에서 제공하는 "ECS 최적화 AMI" 목록에서 원하는 버전을 선택합니다. AMI는 OS별(Amazon Linux, Ubuntu 등) 여러 종류가 있습니다.
  2. 부트스트랩 스크립트 추가인스턴스가 시작될 때 실행할 추가 설정(예: 환경변수, 로그 설정)을 부트스트랩 스크립트로 지정합니다. 이 스크립트는 인스턴스 첫 시작 시 자동 실행됩니다.
  3. 인스턴스 시작인스턴스가 부팅되면 미리 설치된 ECS 에이전트가 자동으로 시작되고, ECS 클러스터에 등록됩니다. 곧바로 태스크를 배치할 수 있습니다.

#5한 줄 요약

컨테이너 런타임과 ECS 에이전트를 미리 구성한 AMI 이미지를 제공해, 사용자가 복잡한 초기 설정 없이 바로 컨테이너 인스턴스를 운영 상태로 시작하게 하는 것

ECS 컨테이너 에이전트: 설치·설정·업데이트·정리

컨테이너 에이전트는 각 인스턴스에서 ECS 제어 평면과 통신하며 태스크를 실행하는 데몬으로, 설치·환경변수 설정·업데이트·이미지 정리를 관리한다.

#1문제 상황

EC2 인스턴스는 그 자체로는 ECS 제어 평면과 통신할 방법이 없습니다. 또한 실행할 태스크가 무엇인지, 어떻게 배치할지 지시를 받을 방법이 없고, 실행 중인 태스크의 상태를 ECS에 보고할 방법도 없습니다. 이런 통신과 조율을 담당할 소프트웨어가 필요합니다.

#2핵심 질문

EC2 인스턴스가 ECS의 지시를 받고, 태스크를 실행하고, 그 결과를 ECS에 보고할 수 있게 하는 에이전트는 어떻게 설치하고 관리할까요?

#3동작 예시

ECS 컨테이너 에이전트는 각 EC2 인스턴스에서 실행되는 데몬(항상 실행 중인 프로세스)으로, ECS 제어 평면과 주기적으로 통신합니다. "이 인스턴스에서 태스크 A를 실행해달라"는 명령을 받으면 컨테이너 런타임에 지시하고, 태스크 실행 상태를 ECS에 보냅니다. 또한 인스턴스의 CPU, 메모리, 디스크 상태를 모니터링해서 리포트합니다.

#4동작 과정

  1. 에이전트 설치ECS 최적화 AMI를 사용하면 에이전트가 이미 설치되어 있으므로 추가 설치가 필요 없습니다. 일반 AMI를 사용하는 경우에만 Docker 이미지로 에이전트를 직접 실행합니다.
  2. 환경변수와 설정에이전트가 어느 클러스터에 등록될지, 로그는 어디로 보낼지 등을 환경변수로 지정합니다. IAM 역할을 부여해 ECS API에 접근할 권한을 줍니다.
  3. 업데이트와 정리AWS가 주기적으로 에이전트 업데이트를 배포합니다. 인스턴스에서 다운로드한 컨테이너 이미지가 쌓이면 에이전트의 정리 기능이 자동으로 오래된 이미지를 삭제합니다.

#5한 줄 요약

각 EC2 인스턴스에서 실행되는 에이전트 프로세스가 ECS 제어 평면과 통신하며 태스크를 받고 실행하고, 상태를 지속적으로 보고하는 양방향 연결을 유지하는 것

클러스터와 컨테이너 인스턴스 수명 주기 관리

클러스터 업데이트·삭제와 인스턴스 등록 해제·드레이닝·타입 변경까지, 인프라를 무중단으로 교체하고 정리하는 운영 절차다.

#1문제 상황

기존 방식에서는 클러스터나 인스턴스를 변경할 때 모든 작업을 중단한 후 업데이트를 진행했다. 변경이 완료되면 작업을 다시 시작해야 했다. 한계점: 서비스가 중단되는 시간이 발생하고, 작업을 수동으로 옮기고 정리해야 하는 번거로움이 있다.

#2핵심 질문

실행 중인 서비스를 멈추지 않으면서 인프라를 업데이트하고 불필요한 인스턴스를 정리할 수 있을까?

#3동작 예시

ECS 클러스터 내에서 여러 인스턴스가 작업을 실행하고 있을 때, 한 인스턴스를 업데이트하려면 그 인스턴스 위의 작업들을 다른 건강한 인스턴스로 옮긴 후, 비운 인스턴스만 업데이트하거나 제거한다.

#4동작 과정

  1. 드레이닝 (Draining)업데이트 대상 인스턴스를 "드레인" 상태로 변경하면, ECS는 그 인스턴스에서 실행 중인 작업을 자동으로 다른 건강한 인스턴스로 옮긴다. 새로운 작업이 그 인스턴스에 배치되지 않는다.
  2. 인스턴스 업데이트 또는 제거모든 작업이 다른 인스턴스로 이동한 후, 대상 인스턴스를 업데이트하거나 클러스터에서 제거한다.
  3. 복구 확인업데이트가 완료되면 인스턴스를 다시 활성화하거나, 제거한 경우 필요하면 새로운 인스턴스를 추가한다.

#5한 줄 요약

작업을 자동으로 다른 인스턴스로 이동시킨 후 인스턴스를 관리하는 프로세스로, 서비스를 중단하지 않으면서도 인프라를 업데이트·교체·정리할 수 있도록 하는 것

작업 수명 주기: PROVISIONING 부터 STOPPED 까지

ECS 작업이 생성 요청부터 종료까지 거치는 PROVISIONING·PENDING·RUNNING·DEACTIVATING·STOPPED 등의 상태 흐름.

#1문제 상황

기존 방식에서는 프로세스나 애플리케이션을 실행하면 시작되거나 중단되는 두 가지 상태만 생각했다. 한계점: 실제로 컨테이너가 시작되려면 자원을 준비하고, 대기하고, 실행되고, 종료하는 여러 단계를 거친다. 각 단계의 상태를 모르면 작업이 왜 아직 실행 중인지, 정말로 종료되는 중인지 파악하기 어렵다.

#2핵심 질문

ECS 작업이 요청 후 실제로 실행되고 종료되기까지 거치는 각 상태는 무엇인가?

#3동작 예시

사용자가 "작업 실행"을 요청하면, 먼저 자원을 예약하는 PROVISIONING 상태에서 시작해 인스턴스에 할당을 기다리는 PENDING 상태를 거치고, 실제 실행 중인 RUNNING 상태가 되며, 종료 요청을 받고 정리 중인 DEACTIVATING 상태를 지나 완전히 종료된 STOPPED 상태에 이른다.

#4동작 과정

  1. 예약 및 대기 (PROVISIONING → PENDING)작업 생성 요청이 들어오면 ECS가 필요한 자원(CPU, 메모리)을 예약한 후, 클러스터의 인스턴스에 할당될 자리를 기다린다.
  2. 실행 (RUNNING)할당 대상 인스턴스가 결정되면 컨테이너가 시작되고, 애플리케이션이 실제로 동작한다.
  3. 종료 (DEACTIVATING → STOPPED)작업 중단 명령을 받으면 컨테이너에 종료 신호를 보내 정리 작업을 진행한 후, 모든 리소스를 해제하고 STOPPED 상태가 된다.

#5한 줄 요약

ECS 작업의 각 상태를 정의하여 작업의 생명 주기를 투명하게 추적할 수 있도록 하고, 각 단계에서 일어나는 일을 명확하게 보여주는 것

#1문제 상황

기존 방식에서는 여러 서버에 작업을 배분할 때 수동으로 어느 서버에 올릴지 정했거나, 간단한 규칙(예: 용량이 남는 곳)만 사용했다. 한계점: 복잡한 요구사항(예: 특정 유형의 CPU가 필요, 특정 인스턴스에만 올릴 수 있음)을 맞추기 어렵고, 리소스 낭비가 발생한다.

#2핵심 질문

클러스터에 여러 인스턴스가 있을 때, ECS는 어느 인스턴스에 새로운 작업을 배치할지 어떻게 결정하는가?

#3동작 예시

ECS 스케줄러는 모든 인스턴스 목록에서 작업이 필요로 하는 자원(CPU, 메모리)을 충족하는 후보를 찾고, 배치 제약(특정 인스턴스만 가능 등)으로 더 좁힌 후, 배치 전략(자원을 많이 쓰거나 적게 쓰거나 균등하게)에 따라 최종 인스턴스를 선택한다.

#4동작 과정

  1. 자원 필터링 (Resource Filtering)ECS 스케줄러가 모든 인스턴스 중에서 작업이 요청한 CPU, 메모리, GPU 같은 자원을 충분히 가진 인스턴스만 선별한다.
  2. 제약 평가 (Constraint Evaluation)배치 제약(예: 특정 속성을 가진 인스턴스만, 또는 다른 작업과 같은 인스턴스에만)을 적용하여 후보 인스턴스를 더 줄인다.
  3. 전략 적용 및 선택 (Strategy Application)남은 후보 중에서 배치 전략(binpack, spread, random)에 따라 최종적으로 어느 인스턴스에 배치할지 결정하고 작업을 할당한다.

자원, 제약, 전략을 차례로 평가하는 결정 프로세스로, 복잡한 요구사항을 만족하면서도 클러스터의 리소스를 효율적으로 배분하는 것

배치 전략과 태스크 그룹

binpack·random·spread 로 작업을 어떻게 흩뿌릴지 정하고, 태스크 그룹으로 관련 작업을 묶어 함께 다루는 방법.

→ 05-02 참조

#1문제 상황

기존 방식에서는 작업을 배분할 때 어느 인스턴스를 우선순위로 선택할지 기준이 명확하지 않았다. 또한 여러 작업이 서로 관련 있을 때 각각 따로 배치되어 관리가 복잡했다. 한계점: 자원 효율이 떨어지거나, 관련 작업들이 떨어져서 실행되어 통신 오버헤드가 늘어난다.

#2핵심 질문

관련된 작업들을 함께 또는 흩어져서 배치하고, 리소스 사용 방식을 제어할 수 있는 방법은 무엇인가?

#3동작 예시

ECS에서 배치 전략은 binpack(한 인스턴스를 최대한 꽉 채운다), spread(인스턴스에 고르게 배분한다), random(무작위로 선택한다)로 정의되고, 태스크 그룹은 여러 작업을 하나의 논리적 단위로 묶어 같은 배치 규칙을 적용한다.

#4동작 과정

  1. 배치 전략 정의서비스를 만들 때 배치 전략을 지정한다. binpack(한 인스턴스를 최대한 활용), spread(여러 인스턴스에 고르게), random(무작위) 중 하나를 선택하면 새로운 작업이 그 전략에 따라 배치된다.
  2. 태스크 그룹 구성관련된 여러 작업을 하나의 태스크 그룹으로 묶으면, 같은 그룹 내 작업들이 공통 배치 규칙을 따른다.
  3. 배치 실행새 작업이 들어올 때 그 작업이 속한 그룹의 전략에 맞춰 배치되고, 기존 작업들과 일관된 위치 선택이 이루어진다.

#5한 줄 요약

배치 전략으로 리소스 활용 방식을 정하고, 태스크 그룹으로 관련 작업을 묶어 일관된 배치 규칙을 적용하는 것으로, 클러스터의 자원 효율성과 작업 간의 물리적 근접성을 동시에 제어하는 것

#1문제 상황

기존 방식에서는 작업을 배치할 때 "용량이 남는 인스턴스"나 "이미 이 작업이 실행 중인 인스턴스" 같은 조건을 수동으로만 확인할 수 있었다. 한계점: 세분화된 조건(예: GPU 종류, 인스턴스 크기, 특정 속성)을 한 번에 적용하기 어렵고, 정책을 반복해서 적용하는 것이 번거롭다.

#2핵심 질문

배치 대상이 충족해야 할 다양한 조건을 어떻게 한 번에 정의하고 반복 적용할 수 있을까?

#3동작 예시

ECS 클러스터 쿼리 언어는 "instanceType =~ t2.*"(t2 계열 인스턴스만), "attribute:ecs.instance-type =~ m5.*"(특정 CPU 유형), "distinctInstance"(다른 작업과 다른 인스턴스에만) 같은 표현식으로 후보를 필터링한다.

#4동작 과정

  1. 제약 조건 정의서비스나 작업 정의에서 배치 제약을 지정할 때, 클러스터 쿼리 언어로 조건을 표현한다. 예를 들어 "이 작업은 GPU가 있는 인스턴스에만 올려야 한다"는 속성 조건으로 쓴다.
  2. 제약 평가새로운 작업이 배치될 때, ECS가 정의한 제약 조건을 각 인스턴스에 적용하여 조건을 만족하는 인스턴스만 남긴다.
  3. 선택 및 배치조건을 만족하는 인스턴스들 중에서 배치 전략에 따라 최종 인스턴스를 정하고 작업을 할당한다.

#2핵심 질문

서비스 없이 한 번만 실행되는 작업과 정해진 시간마다 자동으로 실행되는 작업을 어떻게 관리할 수 있을까?

#3동작 예시

ECS에서 한 번만 실행해야 하는 배치 작업은 run-task API로 직접 시작하고, 정기 실행은 AWS EventBridge Scheduler와 연결하여 일정에 맞춰 자동으로 작업을 생성하고 실행한다.

  3. 결과 추적각 실행은 별도의 작업 ID를 가지고 CloudWatch 로그에 기록되므로, 언제 무엇이 실행되었는지 이력을 확인할 수 있다.

서비스와 스케줄링 전략: REPLICA 와 DAEMON

서비스는 지정한 개수의 태스크를 항상 실행 상태로 유지해주는 장기 실행 관리 단위이며, REPLICA 는 원하는 개수만큼, DAEMON 은 조건에 맞는 모든 인스턴스마다 한 개씩 태스크를 띄운다.

#1문제 상황

기존 방식에서는 컨테이너를 실행할 때 "이 애플리케이션을 실행해"라는 명령만 내렸다. 만약 실패하거나 중단되면 수동으로 다시 시작해야 했다. 또한 모든 인스턴스에 같은 역할의 작업을 띄워야 할 때 각각 수동으로 시작해야 했다. 한계점: 작업 개수를 유지하기 어렵고, 인스턴스가 많아질수록 관리 비용이 커진다.

#2핵심 질문

특정 개수의 작업을 항상 실행 상태로 유지하고, 인스턴스마다 일정한 패턴으로 작업을 배치하는 방법은 무엇인가?

#3동작 예시

ECS 서비스는 "원하는 개수 3개를 항상 띄워라"고 지시하면 자동으로 3개를 실행 상태로 유지하고, 하나가 죽으면 자동으로 새로운 것을 시작한다. DAEMON 모드를 사용하면 클러스터의 모든 인스턴스(또는 조건 맞는 인스턴스)에 자동으로 정확히 한 개의 작업을 띄운다.

#4동작 과정

  1. REPLICA 전략서비스를 생성할 때 "원하는 개수"를 지정하면, ECS는 그 개수만큼 작업을 시작하고 항상 유지한다. 작업이 실패하거나 중단되면 자동으로 새것을 배치하여 개수를 맞춘다.
  2. DAEMON 전략DAEMON으로 설정하면 클러스터의 모든 활성 인스턴스(또는 제약에 맞는 인스턴스)에 정확히 한 개의 작업을 띄운다. 새 인스턴스가 추가되면 자동으로 작업을 띄우고, 제거되면 작업도 정리된다.
  3. 상태 유지 및 정리두 전략 모두 ECS가 지정한 상태를 계속 모니터링하고 유지하며, 필요하면 실패한 작업을 교체하고 종료된 작업을 정리한다.

#5한 줄 요약

서비스가 지정한 작업 개수나 배치 패턴을 자동으로 유지하여, 개발자가 실행 상태 관리에 신경 쓰지 않고 비즈니스 로직에만 집중할 수 있도록 하는 것

6서비스와 배포 전략06-03

롤링 업데이트 배포와 배포 구성

기존 태스크를 조금씩 새 태스크로 바꿔가는 기본 배포 방식으로, minimumHealthyPercent 와 maximumPercent 로 교체 속도와 가용 용량을 조절한다.

#1문제 상황

서비스를 배포할 때 모든 태스크를 한 번에 새 버전으로 바꾸면 배포 중에 서비스가 완전히 중단됩니다. 따라서 기존 태스크와 새 태스크가 일정 시간 함께 실행되면서 점진적으로 교체하는 방식이 필요합니다.

#2핵심 질문

배포 중에 서비스 가용성을 유지하면서 기존 태스크를 얼마나 빠르게 새 태스크로 바꿀 수 있을까?

#3동작 예시

원래 서비스에 태스크 4개가 실행 중입니다. 배포를 시작하면 먼저 새 태스크 2개를 띄웁니다(최대값 150%). 동시에 기존 태스크 중 2개를 종료합니다(최소 건강 비율 50%). 그 다음 또 기존 2개를 더 종료하고 새 태스크 2개를 더 띄웁니다. 이렇게 기존 것이 남아 있는 동안 새 것을 조금씩 늘려가는 방식입니다.

#4동작 과정

  1. minimumHealthyPercent 설정배포 중에 항상 살아 있어야 하는 기존 태스크의 최소 비율입니다(기본값 100%). 값이 낮을수록 배포 중에 처리 능력이 줄어들지만 배포가 빨라집니다.
  2. maximumPercent 설정배포 중에 허용되는 전체 태스크의 최대 비율입니다(기본값 200%). 값이 높을수록 새 태스크를 미리 많이 띄울 수 있어 빠른 배포가 가능하지만 리소스를 더 씁니다.
  3. 점진적 교체두 파라미터의 조합에 따라 몇 개씩 묶어서 교체할지가 결정되며, ECS가 기존 태스크를 하나씩 또는 여러 개를 묶어서 종료하고 새 태스크를 띄웁니다.

#5한 줄 요약

배포 중 서비스 가용성과 배포 속도를 두 개의 파라미터로 균형 맞추는 것

블루/그린·선형·카나리 배포와 필요 리소스

새 버전을 별도 집합으로 띄워 트래픽을 한 번에·일정 비율씩·소량 시험 후 전환하는 ECS 네이티브 배포 방식들로, 로드 밸런서 리스너와 두 개의 대상 그룹 같은 리소스가 필요하다.

#1문제 상황

롤링 업데이트는 기존 환경과 새 환경이 섞여 있는 상태가 필연적이므로, 같은 리소스에 두 버전이 함께 실행될 수 없거나 즉각적인 전환이 필요한 경우에 쓸 수 없습니다. 또한 문제 발생 시 빠른 롤백이 어렵습니다.

#2핵심 질문

기존 버전과 새 버전을 완전히 분리된 환경에서 띄워 놓고 트래픽을 제어할 수 있을까?

#3동작 예시

블루 환경(기존)과 그린 환경(새 버전)을 별도로 구성합니다. 로드 밸런서의 리스너 규칙이 모든 트래픽을 블루 대상 그룹으로 보냅니다. 배포할 때 그린 환경에 새 버전 태스크들을 띄우고, 테스트를 거친 후 리스너 규칙을 한 줄 수정해 트래픽을 그린으로 한 번에 전환합니다. 문제가 생기면 다시 블루로 되돌립니다. 선형 배포는 그린 환경에 10% 트래픽만 먼저 보낸 후 조건을 확인해 20%, 30% 이런 식으로 늘려가고, 카나리 배포는 소량(예: 5%) 트래픽을 먼저 보내 검증한 후 나머지를 한 번에 전환합니다.

#4동작 과정

  1. 환경 준비새 버전의 태스크들을 별도 집합으로 준비합니다. 이를 위해 로드 밸런서 리스너에 대상 그룹(기존 버전용과 새 버전용) 2개가 필요합니다.
  2. 트래픽 제어선택한 배포 방식에 따라 리스너 규칙(또는 가중 라우팅)으로 트래픽 비율을 조절합니다. 한 번에 전환(블루/그린), 일정 비율씩(선형), 소량 먼저(카나리).
  3. 검증 및 전환각 단계 사이에 헬스 체크나 메트릭을 확인해 진행 여부를 결정하고, 문제 시 언제든 이전 환경으로 되돌립니다.

#5한 줄 요약

새 버전을 별도 리소스에 띄워 놓고 로드 밸런서 규칙으로 트래픽 흐름을 제어해 배포의 안전성과 속도를 동시에 확보하는 것

배포 안전장치

배포 서킷 브레이커와 CloudWatch 경보로 실패를 감지해 자동 롤백하고, Lambda·일시 정지 훅과 배포 계속/중지 명령으로 배포 흐름을 통제한다.

→ 06-04 참조

#1문제 상황

배포 과정 중에 새 버전의 태스크에 문제가 생길 수 있습니다. 예를 들어 시작하자마자 크래시되거나, 트래픽을 받으니 메모리 부족 오류가 난다거나, 의존성 문제로 응답 시간이 너무 길어질 수 있습니다. 이런 상황을 감지하지 못하고 배포가 계속 진행되면 전체 서비스가 손상됩니다.

#2핵심 질문

배포 중에 새 버전에 문제가 생겼음을 감지하고 자동으로 롤백할 수 있을까?

#3동작 예시

배포가 시작되면 ECS가 새 태스크들의 헬스 체크 상태를 지켜봅니다. 동시에 CloudWatch에 설정한 경보(예: 오류율 5% 초과, CPU 95% 이상)도 감시합니다. 문제를 감지하면 배포 서킷 브레이커가 자동으로 새 태스크 띄우기를 중단하고 기존 태스크로 돌아갑니다. 또한 배포를 일시 정지한 후 수동으로 검증하거나 Lambda 함수를 실행해 추가 확인을 하고 배포를 계속 진행하거나 중단할 수 있습니다.

#4동작 과정

  1. 실패 감지배포 서킷 브레이커(자동)와 CloudWatch 경보(설정한 메트릭)로 새 버전의 문제를 감지합니다.
  2. 자동 롤백 또는 일시 정지서킷 브레이커가 작동하면 자동으로 배포를 멈추고 기존 태스크로 되돌립니다. 또는 배포를 일시 정지해 Lambda 훅으로 추가 검증을 수행합니다.
  3. 배포 제어일시 정지 상태에서 수동으로 검증한 후 계속 진행하거나 중지합니다.

#5한 줄 요약

배포 중에 자동과 수동 검증 메커니즘을 함께 써서 문제를 빠르게 감지하고 손해를 최소화하는 것

서비스 배포와 서비스 리비전으로 배포 추적

서비스 배포는 한 번의 배포 작업 단위이고 서비스 리비전은 그 배포가 사용한 서비스 설정 스냅샷으로, 둘을 보면 언제 무엇이 어떻게 나갔는지 추적할 수 있다.

#1문제 상황

서비스는 계속 변합니다. 태스크 정의가 바뀌고, 배포되었다가 문제가 생겨 옛날 버전으로 돌아가고, 다시 새 버전을 배포합니다. 이 모든 변화가 언제 일어났고 어떤 설정이었는지 알기 어렵습니다.

#2핵심 질문

배포 이력을 추적하고, 특정 배포가 언제 어떤 태스크 정의를 사용했는지 알 수 있을까?

#3동작 예시

서비스 배포는 한 번의 배포 작업 단위입니다. 배포할 때마다 배포 ID가 생기고, 그 배포가 언제 시작되었는지, 상태가 뭔지(성공/실패), 몇 개의 태스크가 실행 중인지 기록됩니다. 서비스 리비전은 그 배포가 사용한 태스크 정의, 로드 밸런서 설정, 배포 컨트롤러 등 모든 설정의 스냅샷입니다. "서비스 리비전 5번이 배포 2번에서 사용되었다"는 식으로 추적할 수 있으므로, 옛날에 정확히 무엇이 나갔는지 알 수 있습니다.

#4동작 과정

  1. 배포 기록배포할 때마다 배포 객체가 생기고, ID, 시작 시간, 상태(진행 중/성공/실패), 실행 중인 태스크 개수 등이 저장됩니다.
  2. 리비전 스냅샷그 배포에서 사용한 태스크 정의 버전, 로드 밸런서 대상 그룹, 배포 전략 등 모든 설정이 서비스 리비전으로 기록됩니다.
  3. 이력 조회배포 목록과 리비전 목록을 보면 어느 배포에서 어느 리비전을 썼는지 알 수 있고, 필요하면 이전 설정으로 돌아갈 수 있습니다.

배포 작업과 그 배포가 사용한 설정을 분리해 기록함으로써 전체 변화 이력을 추적 가능하게 만드는 것

서비스 업데이트·삭제와 서비스 정의 파라미터

서비스의 태스크 정의·개수·용량 공급자 등 파라미터를 갱신하면 새 배포가 시작되고, 더 이상 필요 없으면 서비스를 삭제해 정리한다.

#1문제 상황

서비스를 한 번 만든 후 그대로 두지 않습니다. 태스크 정의가 새 버전으로 올라가고, 실행할 태스크 개수를 조절하고, 용량 공급자(온디맨드/스팟 인스턴스의 비율)를 바꿉니다. 이런 변경 하나하나가 배포를 트리거해야 하는데, 여러 파라미터를 함께 바꿀 때 어떤 순서로 어떻게 적용할지가 복잡합니다.

#2핵심 질문

서비스의 여러 파라미터를 안전하게 업데이트하고, 필요 없으면 서비스를 정리할 수 있을까?

#3동작 예시

서비스 업데이트 명령어를 실행할 때 여러 파라미터를 함께 지정할 수 있습니다. 예를 들어 "태스크 정의를 app:v2로 바꾸고, 실행 중인 태스크를 4개에서 6개로 늘리고, 용량 공급자를 온디맨드 80%, 스팟 20%로 설정"이라고 하면, ECS가 이 모든 변경을 반영해 새 배포를 시작합니다. 배포 중에는 기존 설정으로 실행되던 태스크들이 조금씩 새 설정으로 바뀝니다. 더 이상 필요 없으면 서비스를 삭제해 정리하는데, 기존 태스크들을 먼저 모두 종료한 후 서비스 자체를 제거합니다.

#4동작 과정

  1. 파라미터 선택태스크 정의, 원하는 태스크 개수, 용량 공급자, 배포 컨트롤러 등 중 바꿀 것을 선택합니다.
  2. 업데이트 실행업데이트 명령어로 변경사항을 전달하면, ECS가 새 배포를 시작하고 선택한 배포 전략에 따라 기존 태스크를 새 태스크로 교체합니다.
  3. 삭제 및 정리서비스가 더 이상 필요하면 삭제 명령어를 실행하고, 기존 태스크들을 모두 종료한 후 서비스를 제거합니다.

#5한 줄 요약

서비스 설정의 여러 측면을 유연하게 업데이트하면서 배포 과정은 일관되게 유지하고, 더 이상 필요 없으면 깔끔하게 정리하는 것

#1문제 상황

컨테이너 애플리케이션은 자신의 작업만 하지 않습니다. 모니터링 에이전트(메트릭을 수집해 보내기), 로그 라우터(로그를 중앙 집중식 저장소로 보내기), 보안 에이전트(악성 활동 감지) 같은 보조 컨테이너를 함께 실행해야 합니다. 하지만 이런 보조 컨테이너를 직접 관리하는 것은 번거롭습니다. 클러스터 내의 모든 인스턴스에 깔아야 하고, 업데이트되면 모두에 배포해야 하고, 혹시 죽으면 다시 띄워야 합니다.

#2핵심 질문

모니터링, 로깅, 보안 같은 인프라 에이전트를 개별 애플리케이션 태스크와 분리해서 AWS가 대신 관리할 수 있을까?

#3동작 예시

관리형 데몬 기능을 켜면, AWS가 자동으로 클러스터의 모든 EC2 인스턴스에 지정한 보조 컨테이너를 띄웁니다. 예를 들어 "모든 인스턴스에 CloudWatch 에이전트를 데몬처럼 띄워라"라고 하면 AWS가 배포하고, 인스턴스가 새로 추가되면 자동으로 거기에도 띄워집니다. 에이전트 버전이 올라가면 AWS가 자동으로 업데이트하고, 혹시 에이전트가 죽으면 AWS가 다시 띄웁니다. 개발자는 자신의 애플리케이션에만 집중하면 됩니다.

#4동작 과정

  1. 데몬 설정클러스터 차원에서 어떤 보조 컨테이너(예: CloudWatch 에이전트, ECS Exec 에이전트)를 데몬으로 띄울지 선택합니다.
  2. 자동 배포 및 복구AWS가 클러스터의 모든 기존 인스턴스에 데몬을 띄우고, 새 인스턴스가 추가되면 자동으로 거기에도 띄웁니다. 데몬이 죽으면 자동으로 다시 시작합니다.
  3. 자동 업데이트AWS가 관리하는 데몬의 새 버전이 출시되면 클러스터의 모든 인스턴스에 자동으로 업데이트합니다.

서비스 로드 밸런싱: ALB·NLB·GLB 와 대상 그룹

ECS 서비스가 실행 중인 태스크를 Elastic Load Balancing 대상 그룹에 자동 등록해 들어오는 트래픽을 여러 태스크로 나눠 보내는 방식이며, HTTP 라우팅은 ALB, 초고성능 TCP/UDP 는 NLB, 보안 어플라이언스 경유는 GLB 를 쓴다.

#1문제 상황

ECS 태스크들이 여러 개의 서버에서 실행되는데, 들어오는 요청을 어느 태스크로 보낼지 수동으로 관리할 수 없다. 또한 요청을 여러 태스크에 고르게 분배해야 하고, 어떤 태스크가 정상인지도 판단해야 한다.

#2핵심 질문

여러 태스크에 들어오는 트래픽을 자동으로 분배하면서, HTTP·TCP/UDP·보안 어플라이언스 경유 등 프로토콜과 사용 사례별로 최적화된 로드 밸런서를 어떻게 선택해서 사용할 것인가?

#3동작 예시

Elastic Load Balancing의 대상 그룹에 ECS 서비스의 태스크들을 등록하면, 로드 밸런서는 들어오는 요청을 여러 태스크에 나눠 보낸다. HTTP 요청은 ALB(Application Load Balancer)가 처리하고, 초고속 TCP/UDP 연결은 NLB(Network Load Balancer)가, 보안 어플라이언스를 거쳐야 하는 트래픽은 GLB(Gateway Load Balancer)가 처리한다.

#4동작 과정

  1. 태스크 자동 등록ECS 서비스를 만들 때 로드 밸런서의 대상 그룹(요청을 받을 태스크들의 목록)을 지정하면, 서비스가 시작한 모든 태스크는 자동으로 그 그룹에 등록된다.
  2. 요청 분배로드 밸런서는 들어오는 요청을 대상 그룹의 태스크 중 하나를 선택해 보낸다. ALB를 쓰면 HTTP 헤더의 호스트명이나 경로 패턴(예: /api/*, /images/*)에 따라 다른 태스크 그룹으로 보낼 수 있다.
  3. 태스크 제거태스크가 종료되거나 미호가 나면 로드 밸런서는 그것을 대상 그룹에서 등록 해제해 더 이상 요청을 보내지 않는다.

#5한 줄 요약

ECS 태스크를 로드 밸런서의 대상 그룹에 자동 등록해 들어오는 트래픽을 여러 태스크로 나누고, 프로토콜과 사용 사례에 맞춰 ALB·NLB·GLB 중 하나를 선택하는 것

헬스 체크와 연결 드레이닝 파라미터 최적화

로드 밸런서가 태스크의 정상 여부를 판단하는 주기·임계값과, 종료되는 태스크가 진행 중인 요청을 끝낼 때까지 기다리는 시간(등록 해제 지연)을 조정해 배포·스케일링 중 오류를 줄이는 튜닝이다.

#1문제 상황

로드 밸런서가 요청을 태스크로 보낼 때, 어떤 태스크가 정말 정상인지 알 방법이 없다. 또한 태스크가 종료되거나 새 버전으로 배포될 때 진행 중인 요청이 끊어질 수 있다.

#2핵심 질문

로드 밸런서가 태스크의 정상 여부를 자동으로 판단하고, 태스크가 종료될 때 진행 중인 요청을 안전하게 끝낼 때까지 기다릴 수 있게 하려면 어떤 조정이 필요한가?

#3동작 예시

로드 밸런서는 일정 주기(예: 30초마다)로 태스크에 헬스 체크 요청을 보낸다. 일정 횟수(예: 3회) 연속으로 응답이 없으면 그 태스크를 정상이 아닌 것으로 표시해 더 이상 요청을 보내지 않는다. 동시에 태스크가 종료될 때는 등록 해제 지연(일정 시간, 보통 30초)이라는 기간 동안 기존 요청은 계속 처리하되 새 요청은 받지 않으며, 그 시간이 끝나면 연결을 닫는다.

#4동작 과정

  1. 헬스 체크 설정로드 밸런서가 태스크의 특정 경로(예: /health)로 주기적으로 요청을 보내고, 정상 응답 코드(보통 200)를 받으면 태스크를 healthy로 표시한다. 몇 번 연속으로 실패하면 unhealthy로 바뀐다.
  2. 비정상 태스크 제외unhealthy로 표시된 태스크에는 더 이상 요청을 보내지 않으므로, 자동으로 정상 태스크로만 트래픽이 흘러간다.
  3. 우아한 종료태스크가 종료되거나 배포 중에 새 태스크로 교체될 때, 로드 밸런서는 등록 해제 지연 시간 동안 기존 요청은 끝내되 새 연결은 받지 않으며, 그 시간 후 연결을 끊는다.

#5한 줄 요약

로드 밸런서가 헬스 체크로 정상 태스크를 확인하고, 등록 해제 지연으로 태스크 종료 시 진행 중인 요청이 끝날 때까지 기다려 오류를 줄이는 것

Service Connect: 구성 요소와 네임스페이스

ECS 서비스들이 짧은 논리 이름으로 서로를 호출하도록 태스크마다 프록시를 붙여 주는 기능으로, AWS Cloud Map 네임스페이스를 공용 주소록처럼 사용한다.

#1문제 상황

ECS에서 여러 서비스가 실행될 때, 서로 다른 서비스의 태스크들은 각각의 IP 주소가 다르고, 태스크가 생겼다 사라졌다 하면서 IP도 자꾸 바뀐다. 어떤 서비스가 다른 서비스를 호출할 때 코드에 IP 주소를 하드코딩할 수 없다.

#2핵심 질문

ECS의 여러 서비스들이 자신의 IP 주소 변화를 신경 쓰지 않고 짧은 논리 이름으로 서로를 호출할 수 있게 하려면?

#3동작 예시

Service Connect는 각 태스크마다 로컬 프록시(envoy proxy)를 사이드카처럼 붙여, 서비스가 localhost의 특정 포트로 다른 서비스를 호출하면 그 프록시가 실제 대상 태스크를 찾아 요청을 전달한다. 대상 태스크들의 주소는 AWS Cloud Map이라는 중앙 네임스페이스에 자동으로 등록되어 있어서, 프록시는 거기서 조회한다.

#4동작 과정

  1. 네임스페이스 생성AWS Cloud Map에서 네임스페이스(예: "myapp.local")를 만든다. 이것이 공용 주소록 역할을 한다.
  2. 서비스 자동 등록각 ECS 서비스가 시작되면 Service Connect 설정에 따라 그 서비스의 이름(예: "api-service")이 네임스페이스에 자동 등록되고, 해당 서비스의 태스크 IP들이 기록된다.
  3. 프록시를 통한 호출다른 서비스의 태스크에서 "api-service.myapp.local:PORT"로 요청을 보내면, 그 태스크의 로컬 프록시가 네임스페이스에서 실제 대상 태스크를 찾아 요청을 전달한다.

#5한 줄 요약

각 태스크마다 프록시를 붙여서 짧은 논리 이름으로 호출하면 Cloud Map 네임스페이스에서 실제 대상을 조회해 요청을 전달하는 것

Service Connect 보안·관측·라우팅

Service Connect 트래픽을 TLS 로 암호화하고, 액세스 로그·메트릭으로 호출을 관측하며, 존 인식 라우팅으로 같은 가용 영역 안에서 우선 호출하도록 만드는 설정들이다.

→ 07-03 참조

#1문제 상황

Service Connect로 서비스들이 서로 호출되지만, 서비스 간 통신이 암호화되지 않으면 보안 위험이 있고, 어떤 서비스가 어디로 요청을 보냈는지 추적하기 어렵고, 태스크들이 여러 가용 영역에 흩어져 있으면 네트워크 지연이 커질 수 있다.

#2핵심 질문

Service Connect 트래픽을 보호하고, 서비스 간 호출을 관측하고, 네트워크 지연을 줄이려면 어떤 설정을 해야 하는가?

#3동작 예시

Service Connect 트래픽을 TLS(암호화 통신 표준)로 암호화해 도청을 막고, 각 프록시가 엑세스 로그와 메트릭(요청 수, 응답 시간, 상태 코드 등)을 기록하도록 설정해 CloudWatch에서 조회하며, 태스크가 같은 가용 영역(availability zone, AWS 데이터센터)에 있는 대상 태스크를 우선해서 호출하도록 존 인식 라우팅을 켠다.

#4동작 과정

  1. TLS 암호화 설정Service Connect 정책에서 TLS를 활성화하면, 프록시가 모든 서비스 간 통신을 자동으로 암호화한다.
  2. 로그와 메트릭 수집프록시가 각 요청의 출발지, 목적지, 응답 시간, 상태 코드 같은 정보를 기록해 CloudWatch로 보내므로, 나중에 서비스 간 호출 패턴을 분석할 수 있다.
  3. 존 인식 라우팅라우팅 정책을 "존 어웨어"로 설정하면, 같은 가용 영역 안의 대상 태스크가 있을 때 우선해서 호출해 네트워크 지연과 비용을 줄인다.

#5한 줄 요약

Service Connect의 프록시가 TLS로 암호화하고, 로그·메트릭으로 호출을 추적하며, 존 인식 라우팅으로 같은 가용 영역 안 호출을 우선해 보안과 성능을 높이는 것

서비스 디스커버리·VPC Lattice 와 네트워킹 설계

Cloud Map DNS 기반 서비스 디스커버리와 VPC·계정을 넘나드는 VPC Lattice 를 포함해, 서비스 간 연결 방식을 무엇으로 고를지 정하는 네트워킹 설계 관점이다.

#1문제 상황

ECS에서 서비스 간 연결 방식이 여러 개(로드 밸런서 + 대상 그룹, Service Connect + Cloud Map, VPC Lattice 등)가 있는데, 각각 언제 어떤 경우에 써야 할지 알기 어렵다. VPC나 계정이 다르면 더 복잡해진다.

#2핵심 질문

여러 서비스 간 연결 방식 중 어떤 것을 선택할지, 그리고 VPC·계정을 넘나드는 경우 어떻게 설계할지를 결정하려면?

#3동작 예시

같은 VPC 내 여러 서비스 간 짧은 이름으로 호출하려면 Service Connect + Cloud Map을 쓰면 되고, 여러 VPC나 다른 계정의 서비스까지 포함해야 하면 VPC Lattice(여러 VPC의 서비스들을 일관된 방식으로 연결하는 네트워킹 기반 구조)를 쓴다. 외부 트래픽(인터넷에서 오는 요청)은 로드 밸런서 + 대상 그룹으로 받으면 된다.

#4동작 과정

  1. 서비스 디스커버리 선택같은 VPC 안에만 있으면 Cloud Map DNS 기반 디스커버리(Service Connect)로 충분하고, 더 복잡한 라우팅이나 정책 관리가 필요하면 VPC Lattice를 검토한다.
  2. VPC·계정 경계 확인모든 서비스가 같은 VPC·계정 안에 있으면 Service Connect로 충분하지만, 여러 VPC나 계정에 걸쳐 있으면 VPC Lattice 네트워크를 구성해 모든 서비스를 연결한다.
  3. 외부·내부 트래픽 분리외부 요청은 Application Load Balancer를 통해 수신하고, 내부 서비스 간 호출은 Service Connect나 VPC Lattice로 처리한다.

#5한 줄 요약

같은 VPC 내는 Cloud Map 기반 서비스 디스커버리로, 여러 VPC·계정은 VPC Lattice로 통일해 네트워킹을 설계하되, 외부 트래픽은 로드 밸런서로 받는 것

#1문제 상황

ECS 서비스는 고정된 개수의 태스크를 실행하므로, 트래픽이 많아지면 요청이 쌓여 응답이 느려지고, 트래픽이 적으면 사용하지 않는 태스크 때문에 비용이 낭비된다.

#2핵심 질문

ECS 서비스가 실행하는 태스크의 개수를 수요에 맞춰 자동으로 늘리고 줄일 수 있게 하려면?

#3동작 예시

Application Auto Scaling 서비스가 ECS 서비스의 원하는 태스크 수(desired count)를 모니터링 지표(CPU, 메모리, 요청 수 등)에 따라 자동으로 조절한다. 예를 들어 CPU 사용률이 70%를 넘으면 태스크를 2개 더 추가하고, 20% 이하로 떨어지면 1개 줄이는 식이다.

#4동작 과정

  1. 조정 대상 지정ECS 서비스를 Application Auto Scaling의 조정 대상으로 등록하고, 최소·최대 태스크 개수(예: 최소 2, 최대 10)를 정한다.
  2. 조정 정책 설정어떤 지표(CPU, 메모리, 요청 수)를 기준으로 몇 개씩 늘리고 줄일지 정한다. 예를 들어 "CPU 사용률 70% 유지"처럼 목표값을 정하는 방식도 있다.
  3. 자동 조절CloudWatch가 지표를 지속적으로 수집해 Application Auto Scaling에 전달하면, 조정 정책에 따라 태스크 개수를 자동으로 조절한다.

대상 추적 조정 정책

CPU·메모리·요청 수 같은 지표를 목표값에 붙들어 두도록 태스크 수를 자동 조절하는, 가장 널리 쓰이는 조정 정책이다.

#1문제 상황

오토 스케일링을 하려면 조정 정책(언제 몇 개씩 늘릴지)을 정해야 하는데, CPU 70%, 메모리 80% 같은 고정 임계값을 여러 개 정하기는 복잡하고, 실제 수요 변화에 제때 대응하기 어렵다.

#2핵심 질문

단순한 규칙 하나로 CPU·메모리·요청 수 같은 지표를 목표값에 맞춰 자동으로 조절하려면?

#3동작 예시

대상 추적 조정 정책은 하나의 지표(예: 태스크당 평균 요청 수 100개)를 목표값으로 지정하면, Application Auto Scaling이 자동으로 현재값과 목표값의 차이를 계산해 태스크를 늘리거나 줄인다. 만약 현재 태스크당 요청이 200개면 태스크를 2배 늘려 목표에 가깝게 만든다.

#4동작 과정

  1. 지표와 목표값 선택CPU 사용률, 메모리 사용률, 요청 수, 또는 사용자 정의 지표 중 하나를 선택하고 목표값(예: CPU 70%)을 정한다.
  2. 목표값 계산Application Auto Scaling이 현재 지표의 평균을 구하고(예: 현재 CPU 140%), 목표값(70%)과의 비율을 계산해 필요한 태스크 개수를 역산한다. 140 / 70 = 2배 필요하면 태스크 수를 2배로 조절한다.
  3. 자동 조절계산한 태스크 개수에 맞춰 스케일 업(늘림) 또는 스케일 다운(줄임)을 실행한다. 이후 계속 지표를 모니터링해 목표값에서 벗어나면 다시 조절한다.

#5한 줄 요약

하나의 지표를 목표값으로 지정하면 Application Auto Scaling이 현재값과 목표값의 비율로 자동 계산해 태스크를 조절하므로, 복잡한 규칙을 여러 개 정할 필요가 없는 것

#1문제 상황

스케일인 중에는 ECS가 오래된 태스크부터 무조건 종료한다. 그 태스크가 중요한 데이터베이스 마이그레이션이나 오래 실행되는 배치 작업을 처리 중이라도 상관없이 강제 종료되어 작업이 중단되거나 손상될 수 있다. 또한 여러 가용 영역(물리적으로 떨어진 데이터센터)에 걸쳐 태스크를 실행할 때, 일부 영역에만 태스크가 몰려 있으면 그 영역의 장애에 매우 취약해진다.

#2핵심 질문

중요한 작업 중인 태스크는 축소에서 보호하면서도 필요할 때는 효율적으로 용량을 줄일 수 있을까?

#3동작 예시

데이터 마이그레이션 태스크는 스케일인 보호로 표시해 축소 명령이 와도 절대 종료되지 않도록 한다. 동시에 100개의 태스크가 가용 영역 A에 5개, B에 45개, C에 50개로 불균형하게 분산되면, 리밸런싱 기능이 이들을 다시 배치해 각 영역에 약 33~34개씩 고르게 분산시킨다.

#4동작 과정

  1. 스케일인 보호 확인태스크 축소 명령이 내려오면 ECS는 각 태스크가 보호 상태(Protection)로 표시되어 있는지 먼저 확인하고, 보호된 태스크는 종료 대상에서 제외한다.
  2. 보호되지 않은 태스크만 선택종료할 태스크를 고르되 보호된 태스크를 피하고, 보호되지 않은 것들만 우선 종료한다.

  2. 컨테이너 또는 에이전트 인트로스펙션애플리케이션이 HTTP 요청을 보내면 ECS 에이전트가 그 컨테이너의 태스크 ID, 컨테이너 이름, 할당된 리소스, IAM 역할 정보, 환경 변수 등을 응답합니다.
  3. 런타임 메타데이터 사용애플리케이션은 이 정보를 로깅에 포함시키거나 모니터링 에이전트로 전달하거나, 자신의 상태를 진단할 때 참고합니다.

#5한 줄 요약

컨테이너가 로컬 HTTP 엔드포인트를 통해 ECS 에이전트에 질의해 자신이 속한 태스크와 리소스 할당 정보를 직접 얻는 인트로스펙션 메커니즘

ADOT 사이드카를 붙여 요청 추적은 X-Ray로, 애플리케이션 지표는 CloudWatch나 Managed Service for Prometheus로 내보내는 방법.

#1문제 상황

이전에는 애플리케이션이 로그만 남기거나 기본 메트릭(CPU, 메모리)만 수집했습니다. 그러면 요청이 어느 지점에서 느려지는지, 어떤 외부 서비스 호출이 병목인지, 에러가 어디서 발생했는지를 알기 어려웠습니다. 분산된 마이크로서비스 환경에서는 요청 하나가 여러 컨테이너를 거쳐 다니므로, 각 구간의 성능과 의존성을 추적할 수 없으면 장애 원인을 찾을 수 없습니다.

#2핵심 질문

ECS에서 실행되는 애플리케이션이 요청 전체 경로를 추적하고 각 단계의 성능 지표를 수집해 한 곳에 모아볼 수 있을까요?

#3동작 예시

태스크 정의에 ADOT(AWS Distro for OpenTelemetry) 사이드카 컨테이너를 추가하면, 애플리케이션의 요청 추적 데이터(trace)와 성능 지표(metric)가 자동으로 수집되어 X-Ray(추적용)와 CloudWatch 또는 Managed Service for Prometheus(지표용)로 전송됩니다.

#4동작 과정

  1. ADOT 에이전트 배포태스크 정의에서 ADOT를 사이드카 컨테이너로 추가하고, 애플리케이션이 로컬 호스트의 ADOT 수신 포트로 데이터를 보내도록 설정합니다.
  2. 데이터 수집 및 변환애플리케이션이 보낸 추적 데이터와 지표는 ADOT가 받아 X-Ray 형식(분산 추적)과 Prometheus 형식(시계열 지표)으로 변환합니다.
  3. AWS 서비스로 전송변환된 데이터는 X-Ray, CloudWatch, 또는 Managed Service for Prometheus로 전송되어 애플리케이션 성능을 시각화하고 분석할 수 있게 됩니다.

#5한 줄 요약

ADOT 사이드카가 애플리케이션 요청의 전체 경로를 추적하고 성능 지표를 수집해 X-Ray와 CloudWatch로 보냄으로써, 분산된 마이크로서비스의 성능을 통합 관점에서 진단할 수 있게 하는 것

감사와 운영 진단 도구·CloudTrail·Action Logs·Live Tail·ECS Exec

누가 어떤 API를 불렀는지(CloudTrail), ECS가 무슨 조치를 했는지(Action Logs), 로그를 실시간으로(Live Tail), 컨테이너 안에 직접 들어가(ECS Exec) 확인하는 운영 진단 수단들.

#1문제 상황

기존에는 ECS 클러스터와 태스크의 상태 변화를 추적할 방법이 제한적이었습니다. 누가 어떤 API를 호출했는지(CloudTrail로 기록되지만 ECS 콘솔에서는 잘 안 보임), ECS 자체가 어떤 조치를 취했는지(태스크 시작 실패, 스케일링 결정 등), 그리고 컨테이너 내부에서 실제로 무슨 일이 일어나는지를 일관되게 추적하기 어려웠습니다.

#2핵심 질문

ECS 환경에서 API 호출부터 태스크 상태 변화, 컨테이너 내부 진단까지 모든 층위의 이벤트와 로그를 일관되게 추적하고 실시간으로 확인할 수 있을까요?

#3동작 예시

ECS는 네 가지 로깅/감시 수단을 제공합니다. CloudTrail은 누가 API를 호출했는지(예: 누가 태스크를 정지했는지), Action Logs는 ECS가 스스로 어떤 조치를 취했는지(예: 비정상 태스크를 다시 시작), Live Tail은 로그를 실시간으로 흘려보기, ECS Exec는 실행 중인 컨테이너에 원격 셸로 접속해 직접 확인합니다.

#4동작 과정

  1. 감사 기록 수집CloudTrail이 ECS API 호출 기록을 저장하고, ECS Action Logs가 ECS 서비스 자체의 내부 조치(태스크 배치, 리소스 할당 결정 등)를 기록합니다.
  2. 실시간 로그 모니터링CloudWatch Live Tail로 여러 컨테이너의 로그를 실시간으로 스트리밍해서 이벤트 흐름을 즉시 파악할 수 있습니다.
  3. 직접 진단ECS Exec로 실행 중인 컨테이너에 접속해 파일 시스템, 프로세스, 네트워크 상태를 직접 확인하고 문제를 즉시 해결합니다.

#5한 줄 요약

CloudTrail, Action Logs, Live Tail, ECS Exec라는 네 가지 도구로 API 호출·ECS 내부 조치·실시간 로그·컨테이너 내부 상태를 다층적으로 추적해 운영 문제의 원인을 빠르게 찾을 수 있게 하는 것

공동 책임 모델과 ECS 보안 영역 지도

AWS 가 지키는 부분과 사용자가 지켜야 하는 부분을 실행 유형별로 나눈 기준이며, ECS 보안이 다루는 영역 전체의 출발점이다.

#1문제 상황

클라우드 환경에서 보안을 생각할 때 누가 무엇을 책임지는지가 명확하지 않으면, 설정할 것을 빠뜨리거나 서로 책임을 미루는 상황이 발생합니다. AWS는 인프라와 하이퍼바이저 같은 기저층을 보호하지만, 애플리케이션 설정, 네트워크 규칙, 데이터 암호화, 접근 제어는 사용자가 해야 합니다. ECS는 EC2 인스턴스 위에서 실행되는지, Fargate로 서버리스하게 실행되는지에 따라 책임 경계가 달라집니다.

#2핵심 질문

ECS를 사용할 때 AWS가 보호하는 영역과 내가 반드시 지켜야 하는 영역은 실행 유형별로 어떻게 나뉠까요?

#3동작 예시

ECS on EC2에서는 AWS가 호스트 커널과 하이퍼바이저를 관리하고, 사용자는 EC2 인스턴스 보안 그룹, 이미지 취약점, 애플리케이션 로직의 보안을 책임집니다. Fargate에서는 AWS가 인스턴스까지 관리해서 사용자의 보안 책임 범위가 이미지와 애플리케이션 레벨로만 좁혀집니다.

#4동작 과정

  1. AWS의 책임AWS는 ECS 서비스 자체, 인프라 물리 보안, 호스트 운영 체제 패치(Fargate의 경우)를 책임집니다.
  2. 사용자의 책임사용자는 IAM 권한 설정, 네트워크 보안 그룹, 컨테이너 이미지 보안(취약점 스캔), 데이터 암호화, 로그 보안을 책임집니다.
  3. 공동 책임 영역패치 관리(EC2에서는 호스트 OS, 사용자는 컨테이너 이미지), 접근 제어 정책(AWS IAM 구조 제공, 사용자가 정책 작성)은 양쪽이 협력합니다.

#5한 줄 요약

ECS 보안이 AWS의 인프라 보호와 사용자의 애플리케이션 및 권한 설정 책임으로 명확하게 나뉜다는 경계를 명시해, 보안 사각지대 없이 설정할 수 있게 하는 것

ECS의 IAM 역할: 작업 실행·작업·컨테이너 인스턴스·인프라 역할

ECS 에서 누가 무엇을 할 수 있는지를 정하는 네 종류의 역할로, 이미지·로그를 가져오는 실행 역할과 앱이 AWS 를 호출하는 작업 역할 등이 서로 다른 목적을 가진다.

#1문제 상황

IAM 역할을 하나만 사용하면 권한을 섬세하게 제어할 수 없습니다. 예를 들어, 이미지를 ECR에서 가져오는 권한과 애플리케이션이 S3 버킷을 접근하는 권한을 구분하지 않으면, 이미지 풀 과정이 실패했을 때 S3 권한 문제인지 ECR 문제인지 진단하기 어렵고, 보안상 각 작업이 최소 권한만 가지도록 제한할 수 없습니다.

#2핵심 질문

ECS에서 이미지 pull, 애플리케이션 실행, 인스턴스 관리 같은 여러 작업 단계가 각각 필요한 권한을 최소한만 가질 수 있을까요?

#3동작 예시

ECS는 네 가지 역할로 권한을 분리합니다. ecsTaskExecutionRole은 ECS 에이전트가 ECR에서 이미지를 pull하고 CloudWatch에 로그를 보내는 데 쓰고, ecsTaskRole은 애플리케이션이 S3나 DynamoDB 같은 AWS 서비스를 호출할 때 쓰고, 인스턴스/인프라 역할은 호스트가 ECS 클러스터와 통신하는 데 쓰고, 서비스 연결 역할은 ECS가 ALB나 보안 그룹을 관리하는 데 씁니다.

#4동작 과정

  1. 태스크 실행 역할(ecsTaskExecutionRole)ECS 에이전트가 이 역할을 사용해 Amazon ECR에서 컨테이너 이미지를 pull하고, CloudWatch Logs에 태스크 로그를 보내고, Secrets Manager에서 민감한 정보를 가져옵니다.
  2. 태스크 역할(ecsTaskRole)애플리케이션 자체가 이 역할을 사용해 S3 버킷을 읽거나, DynamoDB 테이블을 쿼리하거나, SNS 주제에 메시지를 보냅니다. 애플리케이션이 IAM 자격증명을 환경 변수로 받게 됩니다.
  3. 인스턴스·인프라 역할EC2 인스턴스나 서비스 연결 역할이 ECS 클러스터와의 통신, 로드 밸런서 관리 같은 인프라 레벨의 작업을 수행합니다.

#5한 줄 요약

이미지 pull, 애플리케이션 실행, 인스턴스 관리 같은 서로 다른 목적의 작업을 별도 IAM 역할로 분리해, 각 계층이 최소 권한만 가지고 보안 침해 범위를 최소화할 수 있게 하는 것

서비스 연결 역할·관리형 정책·기능별 필요 권한

ECS 가 스스로 리소스를 관리하려고 쓰는 서비스 연결 역할과 AWS 가 미리 만들어 둔 관리형 정책으로 권한을 손쉽게 붙이는 방법이다.

→ 10-02 참조

#1문제 상황

IAM 역할과 정책을 매번 처음부터 만들면 필요한 권한을 빠뜨리기 쉽고, 설정 과정이 복잡합니다. 특히 ECS가 Application Load Balancer 같은 다른 AWS 서비스와 통신하거나 리소스를 관리할 때 필요한 권한들은 많고 세부 사항이 많아서, 사용자가 일일이 작성하면 실수하거나 과도한 권한을 부여할 수 있습니다.

#2핵심 질문

ECS 기능별로 필요한 권한을 AWS가 미리 준비해 두고, 사용자는 그것을 그대로 붙이거나 최소한만 커스터마이즈할 수 있을까요?

#3동작 예시

ECS가 ALB를 관리하거나 자동 스케일링을 할 때 쓰는 서비스 연결 역할(Service Linked Role)은 AWS가 미리 만들어 두고, 사용자가 처음 해당 기능을 쓸 때 자동으로 생성됩니다. 일반적인 ECS 사용에는 관리형 정책(AWS에서 미리 만든 정책)을 붙이기만 하면, 권한 설정이 끝납니다.

#4동작 과정

  1. 서비스 연결 역할 자동 생성ECS 서비스가 로드 밸런서 통합이나 오토 스케일링을 처음 사용할 때, AWS가 자동으로 서비스 연결 역할을 생성해 ECS가 필요한 리소스를 관리하게 합니다.
  2. 관리형 정책 할당사용자가 IAM 콘솔에서 ecsTaskExecutionRolePolicy나 ecsTaskRole용 관리형 정책(예: AmazonS3ReadOnlyAccess)을 역할에 붙입니다.
  3. 기능별 커스텀 권한만약 기본 관리형 정책이 정확하지 않으면, 해당 기능에 필요한 최소 권한을 포함한 인라인 정책을 추가로 작성합니다.

ECS가 자동으로 서비스 연결 역할을 생성하고 AWS가 미리 만든 관리형 정책을 붙임으로써, 사용자가 권한 설정의 복잡도를 크게 줄이고 필요시에만 세부 조정할 수 있게 하는 것

#1문제 상황

EC2 인스턴스에서 ECS API에 접근할 때 기존 방식은 인터넷 게이트웨이를 거쳐 AWS API 서버로 요청을 보낸다. 이 경로에서는 트래픽이 공인 인터넷을 거치므로 데이터 유출 위험이 높고, 규정 준수 요구사항(예: 특정 산업의 데이터 비공개 네트워크 운영 의무)을 충족하기 어렵다.

#2핵심 질문

인터넷을 거치지 않는 비공개 네트워크 경로만 사용하여 AWS 서비스에 안전하게 접근할 수 있을까?

#3동작 예시

#4동작 과정

  1. VPC 엔드포인트 생성VPC 내에서 ECS API 서비스 이름을 지정하여 엔드포인트를 만들면, AWS는 해당 서브넷에 ENI(탄성 네트워크 인터페이스, 네트워크 통신 인터페이스)를 배치한다.
  2. 요청 라우팅EC2 인스턴스에서 ECS API로 향한 요청이 인터넷 게이트웨이를 건너뛰고 VPC 엔드포인트의 비공개 IP로 자동 라우팅된다.
  3. AWS 내부 경로로 전달엔드포인트가 요청을 AWS 내부 네트워크를 거쳐 ECS API 서버로 전달하고, 응답을 돌려받는다.

ECS 작업이 제대로 실행되지 않을 때, 문제가 ECS 에이전트에 있는지, Docker 엔진에 있는지, 네트워크 연결 문제인지 파악하려면 EC2 인스턴스에 직접 접속해 /var/log/ecs/ecs-agent.log, /var/log/docker, 시스템 로그 등 여러 파일을 개별적으로 확인해야 한다.

#2핵심 질문

ECS 인스턴스의 진단 정보와 로그를 한 번에 수집하고 분석할 수 있을까?

#3동작 예시

ECS logs collector는 한 번의 명령 실행으로 ECS 에이전트 상태, Docker 버전, 네트워크 설정, 디스크 공간, 메모리 사용량과 함께 ECS 에이전트 로그, Docker 로그, 시스템 로그, 커널 메시지를 모두 묶어서 tar 파일로 생성한다.

#4동작 과정

  1. 스크립트 실행EC2 인스턴스에 SSH 접속하여 ECS logs collector 스크립트를 실행한다.
  2. 진단 정보 수집스크립트가 에이전트 상태, Docker 상태, 네트워크 인터페이스, 리소스 사용 현황, 관련 로그 파일을 모두 수집한다.
  3. 결과 다운로드생성된 tar 파일을 로컬에 다운로드하여 AWS 지원팀에 전달하거나 로컬에서 직접 분석한다.

#5한 줄 요약

ECS 인스턴스의 진단 정보와 로그를 자동으로 수집하여 문제 해결에 필요한 모든 정보를 한 번에 얻는 것

서비스 할당량·API 스로틀링·멱등성

계정별 리소스 한도와 API 호출 속도 제한을 이해하고, 재시도 시 중복 생성을 막는 멱등성 토큰을 쓰는 법.

#1문제 상황

AWS 계정은 각 서비스별로 동시에 생성할 수 있는 리소스 개수, API 호출 속도에 제한이 있다. 이를 모르면 대규모 배포 중 예기치 않게 요청이 거부되거나, 배포 스크립트가 재시도할 때 중복된 리소스가 생성될 수 있다.

#2핵심 질문

리소스 한도를 초과하지 않으면서 안전하게 재시도하려면?

#3동작 예시

ECS에는 계정당 생성할 수 있는 태스크 정의 개수, 동시 작업 수, 서비스 개수 등의 할당량(서비스 할당량)이 설정되어 있다. 또한 CreateService 같은 API 호출은 초당 최대 10회 같은 스로틀 제한이 있다. API 요청을 보낼 때 idempotencyToken(멱등성 토큰, 고유한 요청 ID)을 포함하면, 동일한 요청을 여러 번 보내도 한 번만 처리되므로 재시도 중 중복 생성을 방지한다.

#4동작 과정

  1. 할당량 확인AWS 콘솔의 Service Quotas 페이지에서 현재 계정의 ECS 할당량과 사용 현황을 조회한다.
  2. 필요시 증가 요청할당량이 부족하면 AWS에 증가 요청을 제출하고 승인을 대기한다.
  3. 안전한 API 호출CreateService, RunTask 등 작업 생성 API를 호출할 때 고유한 idempotencyToken을 포함하여 재시도 중 중복 생성을 방지한다.

#5한 줄 요약

계정 리소스 한도를 파악하고, API 호출 제한을 존중하며, 멱등성 토큰으로 안전한 재시도를 보장하는 것
