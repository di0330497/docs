1. Amazon Athena 의 자리01-01

Amazon Athena 란 무엇인가

Amazon Athena 는 S3 등에 저장된 데이터를 서버를 준비하지 않고 표준 SQL 로 직접 조회해 빠르게 알아낼 수 있게 해 주는 서버리스 서비스다.

#1문제 상황

데이터를 분석하려면 서버를 미리 세팅하고 데이터를 옮겨 적재해야 한다. 분석할 때마다 이 준비가 반복된다.

Amazon Athena 는 이 준비를 없앤다. serverless, 즉 사용자가 서버를 준비하고 관리하지 않는 방식으로 동작해 Amazon S3 에 둔 데이터에 표준 SQL 을 바로 실행한다. 콘솔에서 Athena 를 데이터 위치에 연결하면 곧바로 질의해 수 초 만에 결과를 받는다. Apache Spark 을 붙여 대화형 분석도 한다.

#2핵심 질문

S3 에 흩어 둔 데이터를 서버 준비 없이 표준 SQL 로 빠르게 조회하려면 어떻게 해야 하는가?

#3동작 예시

분석 담당자가 Athena 콘솔의 질의 편집기에 SELECT 문을 적고 실행한다. 파일이 있는 저장 위치의 데이터를 직접 읽어 수 초 안에 행 단위 결과가 화면에 나온다.

#4동작 과정

  1. 데이터를 가리킨다콘솔에서 Athena 가 어느 Amazon S3 위치를 볼지 정해 둔다. 데이터를 옮기지 않고 그 자리에서 읽는다.
  2. SQL 을 실행한다표준 SQL 로 ad-hoc, 즉 미리 정해 두지 않는 즉석 질의를 보낸다. Trino 와 Presto 계보의 처리 엔진이 질의를 나누어 돌리고 Apache Arrow 형식으로 결과를 넘긴다.
  3. 노트북으로 넓힌다Apache Spark 코드를 노트북에서 실행해 결과를 바로 받을 수도 있다.
  4. 확인해 볼 것질의 편집기에서 S3 의 데이터 파일을 가리키는 SELECT 문을 실행해 결과 행이 나오는지 본다.

#1문제 상황

federated queries는 원본 데이터가 있는 곳에서 직접 데이터를 읽어오게 한다. 카탈로그에 테이블을 복제하지 않아도 여러 데이터 원본을 한 번에 조회하게 된다.

#3동작 예시

처리량을 확인하려고 Athena 콘솔에서 해당 쿼리의 실행 이력을 연다.

#4동작 과정

  1. 연결자를 고른다대상 데이터 원본에 맞는 data source connector를 등록한다. 정해진 규격의 방식으로 접속 정보를 넘겨 원본 저장소와 연결을 만든다.
  2. Lambda function으로 읽는다연결자가 Athena에서 온 쿼리를 실제 읽기 명령으로 바꿔 실행한다. 이 변환과 실행은 cloud에서 도는 Lambda function 안에서 이뤄지고, 연결자가 병렬 처리와 조건 필터 내리기를 함께 맡는다.
  3. 권한을 함께 확인한다연결자가 쿼리를 낸 사람의 권한에 따라 볼 수 있는 데이터를 가를 수 있다. 정밀한 데이터 통제는 Lake Formation을 경유해 Glue 데이터 카탈로그 계층에서 추가로 얹는다(→ 09-04).
  4. 확인해 볼 것Athena 콘솔에서 카탈로그 목록에 등록한 연결자 이름이 뜨는지 확인한다.

#1문제 상황

이미 사내에서 Hive로 쌓아 둔 테이블이 많다. Hive metastore에는 그 테이블 정의와 권한 정보가 들어 있다. 이를 전부 AWS Glue Data Catalog로 옮기지 않고 그대로 두고 Athena로 읽으려면 연결 방법이 필요하다.

Athena는 메타데이터를 옮길 필요 없이 private VPC 안에 있는 이 저장소에 연결해 기존 Hive 데이터를 조회하게 해 준다.

#2핵심 질문

옛 Hive 환경의 테이블 정의를 옮기지 않고 Athena로 그대로 조회하려면 어떻게 연결해야 할까?

#3동작 예시

분석가가 Athena 콘솔에서 카탈로그를 고를 때 사내 Hive metastore가 목록에 보인다. 이 카탈로그를 선택해 스키마를 펼치고 저장된 Hive view를 열어 같은 데이터가 나온다.

질의 결과의 소요 시간과 읽은 데이터 크기를 실행 이력에서 함께 본다.

#4동작 과정

  1. Lambda function을 준비한다사설망의 Hive metastore에 말을 거는 Lambda function을 만든다. 직접 코드를 넣어도 되고 기본 제공 구현체를 그대로 써도 된다.
  2. 보안 통로로 연결한다Lambda function과 metastore 사이의 연결은 private Amazon VPC 통로를 타고 인터넷으로 나가지 않는다. IAM 실행 역할 권한을 붙여 필요한 접근만 연다.
  3. external metastore로 등록한다배포한 연결자를 Athena에 external metastore 카탈로그로 등록해 쿼리에서 이름을 붙여 쓴다. 이 경로에서는 카탈로그 이름을 생략하면 기본 카탈로그가 쓰이는 점에 주의한다.
  4. 확인해 볼 것Athena 콘솔에서 해당 카탈로그를 열어 스키마와 Hive view 목록이 뜨는지 확인한다.

데이터 카탈로그 접근 제어

데이터 카탈로그 접근 제어는 Glue Data Catalog 의 테이블과 데이터베이스를 누가 보고 고칠 수 있는지를 IAM 정책와 세분 권한으로 정해 쿼리 대상 자체를 가리는 방법이다.

먼저 알아야 할 것 02-05

→ 02-04 참조

#1문제 상황

한 카탈로그에는 여러 팀의 테이블이 함께 들어 있다. S3 파일 권한만으로는 Athena는 S3에 파일이 있다는 사실만 알 뿐 어떤 테이블이 존재하는지는 상관없이 보여 준다.보 수 없 되게 하려면 카탈로그 쪽에서 걸러야 한다.

IAM 신원 기반 정책에 자원 수준 권한을 정의하면 Athena가 쓸 데이터베이스와 테이블을 가릴 수 있다. 열과 행 단위의 control access는 Lake Formation이 맡는다(→ 09-04).

#2핵심 질문

S3 파일은 보이지 않게 하면서 특정 데이터베이스와 테이블만 조회하게 만들려면 어디에서 권한을 정해야 할까?

#3동작 예시

운영자가 S3 에는 원본 데이터가 그대로 있는데 Athena 콘솔의 카탈로그 브라우저에서는.team 데이터베이스가 보이지 않는다.

반대로 데이터 권한이 있는 사람은 같은 콘솔에서 그 데이터베이스를 열어 테이블 목록을 본다.

#4동작 과정

  1. IAM 신원 기반 정책을 만든다Athena가 쓰는 카탈로그의 데이터베이스와 테이블을 자원으로 삼아 정책 문장 하나를 추가한다. 이 방식은 리소스 기반 정책과 다르니 혼동하지 않는다.
  2. catalog access policy를 붙인다데이터베이스와 테이블 접근 권한을 catalog access policy로 모아 손볼 수 있게 한다. 파티션과 테이블 버전 단위 권한 설정도 이 계층에서 한다.
  3. 계정 밖 연결을 정한다다른 계정에 있는 테이블은 cross-account catalog 설정으로 접근 경로를 열어 준다.
  4. 확인해 볼 것권한 없는 계정으로 Athena 콘솔을 열어 그 데이터베이스가 목록에 뜨지 않는지 확인한다.

JDBC 와 ODBC 로 Athena 접속

JDBC 와 ODBC 는 외부 프로그램이 정해진 접속 규약으로 Athena 에 연결해 쿼리를 보내고 결과를 받는 통로로 BI 도구 같은 클라이언트에서 Athena 를 쓸 수 있게 해 준다.

먼저 알아야 할 것 02-05

→ 02-05 참조

#1문제 상황

Athena 콘솔에서 손으로 쿼리를 치는 방식은 반복 분석에 맞지 않는다. 팀이 쓰는 BI tool이나 사내 프로그램에서 Athena 데이터를 그대로 읽어야 한다. 콘솔 밖의 프로그램이 Athena에 붙는 길이 필요하다.

Athena는 JDBC와 ODBC 접속을 모두 열어 준다. 어느 규약으로 붙을지만 정하면 클라이언트에서 그대로 SQL을 다룬다.

#2핵심 질문

BI 도구 같은 외부 프로그램에서 Athena에 접속하려면 어떤 접하을 써야 할까?

#3동작 예시

분석가가 BI tool에서 Athena 데이터 소스를 새로 추가한다. 드라이버를 고르고 리전과 작업 그룹을 입력해 연결을 시험한다.

연결이 되면 BI 도구 화면에서 Athena의 데이터베이스와 테이블을 보고 그래프를 만든다.

#4동작 과정

  1. 접속 방식을 정한다클라이언트가 지원하는 규약에 따라 JDBC driver나 ODBC driver를 고른다. 둘 다 설치 순서가 정해져 있어 안내대로 따른다.
  2. 연결 정보를 채운다드라이버 관리자에서 드라이버를 등록하고 Athena의 리전과 엔드포인트를 적은 뒤 작업 그룹 이름을 넣는다. 자격 증명은 IAM 역할 방식으로 넘긴다.
  3. BI tool에서 연결한다BI tool 안에서 Athena를 데이터 원본으로 선택해 테스트 연결을 돌린다. 연결되면 SQL 을 직접 쓰지 않고도 카탈로그를 열어 보고 시각화를 만든다.
  4. 확인해 볼 것BI 도구에서 테스트 연결을 눌러 테스트 테이블 목록이 뜨는지 확인한다.

#5한 줄 요약

JDBC와 ODBC 연결클라이언트 규약으로 Athena를 열어서 BI 도구에서 바로 쓰게 하는 것

데이터베이스 만들기

CREATE DATABASE 문장으로 S3 에 저장된 여러 테이블을 한 덩어리로 묶어 이름 짓고 권한과 위치를 지정하는 작업이다.

먼저 알아야 할 것 02-01

#1문제 상황

테이블을 만들려면 그것이 속한 덩어리가 먼저 있어야 한다. Athena에서 테이블 묶음은 데이터베이스가 맡고 이름과 속성을 함께 정해 준다. 그리고 쿼리 결과를 받아 둘 S3 위치가 있어야 시작할 수 있다.

CREATE DATABASE를 실행하면 이름을 가진 데이터베이스가 만들어지고 그 안에서 테이블을 묶어 관리하게 된다.

#2핵심 질문

Athena에서 테이블을 묶어 담을 데이터베이스는 어떤 명령으로 만들고 무엇을 정해 주는가?

#3동작 예시

분석가가 Athena 콘솔의 쿼리 편집기에서 CREATE DATABASE로 sales_db를 만든다. 이어 USE sales_db를 실행해 이후 입력할 문장이 이 데이터베이스를 가리키게 한다.

목록을 열어 sales_db 아래에 붙은 테이블들이 묶여 나타나는지 본다.

#4동작 과정

  1. 쿼리 결과 위치를 만든다쿼리 출력을 담을 S3 버킷 위치를 먼저 정한다. 데이터베이스를 만들기 전에 이 단계가 필요하다.
  2. CREATE DATABASE를 실행한다이름을 적은 CREATE DATABASE 문장을 콘솔에서 실행한다. 만들어진 데이터베이스의 이름과 위치가 카탈로그에 등록되며, 권한이나 이름 같은 database properties를 함께 적어 둘 수 있다.
  3. USE로 기본 대상을 정한다USE 문장을 실행해 이후 쿼리가 어느 데이터베이스를 볼지 정해 둔다. 더는 쓰지 않을 때는 drop database로 통째로 지울 수 있다.
  4. 확인해 볼 것콘솔의 카탈로그 브라우저에서 만든 데이터베이스 이름이 목록에 뜨는지 확인한다.

테이블 만들기

열 이름과 자료형 그리고 데이터가 있는 S3 위치를 CREATE TABLE 로 선언해 스키마를 등록하는 작업이다.

먼저 알아야 할 것 03-01

→ 03-01 참조

#1문제 상황

Athena는 스키마를 먼저 읽어 두고 나중에 S3의 원본에서 데이터를 읽는다. 데이터가 이미 S3에 있는데 열 이름과 자료형을 알려 주는 선언이 있어야 쿼리로 다룰 수 있다. 그리고 파일 모양에 맞는 읽기 방식을 골라야 한다.

CREATE TABLE은 데이터를 고치는 문장이 아니라 S3에 있는 데이터의 구조와 위치를 선언해 등록하는 문장이다.

#2핵심 질문

S3에 이미 있는 데이터를 다룰 테이블을 어떤 명령으로 어떤 정보를 담아 선언하는가?

#3동작 예시

분석가가 CREATE TABLE로 주문 테이블을 선언한다. 열 이름과 자료형을 적고 LOCATION에 S3 경로를 적은 뒤 SerDe를 지정한다.

선언을 마친 뒤 SELECT로 행을 꺼내 보고 등록한 스키마대로 값이 나오는지 확인한다.

#4동작 과정

  1. 열을 정의한다각 열에 이름과 자료형을 적은 column definition을 차례대로 적는다. Athena는 Apache Hive 방식으로 테이블을 정의하므로 열 목록이 곧 읽는 규약이 된다.
  2. 위치와 형식을 정한다데이터가 있는 Amazon S3의 경로를 LOCATION으로 적고, 파일 모양에 맞는 SerDe 라이브러리와 table property를 함께 지정한다.
  3. 등록만 한다이 문장을 실행해도 S3의 원본 데이터는 고쳐지지 않는다. 스키마는 AWS Glue Data Catalog에 저장되며, 데이터를 읽는 시점에 선언한 스키마를 적용하는 방식이라 필요하면 표 구조를 바꿔 다시 선언할 수 있다.
  4. 확인해 볼 것등록한 테이블에 SELECT을 걸어 원본 행이 열 순서대로 나오는지 확인한다.

3. 데이터베이스와 테이블 만들기03-03

이름 규칙과 예약어

데이터베이스·테이블·열 이름에 쓸 수 있는 문자와 길이 제한을 지키고 SELECT 같은 예약어는 큰따옴표로 묶어야 한다는 규칙이다.

먼저 알아야 할 것 03-02

→ 03-02 참조

#1문제 상황

CREATE TABLE 로 만든 테이블은 SQL 문장에 이름이 바로 쓰이기 때문에 이름이 잘못되면 이후 모든 쿼리가 깨진다(→ 03-02).

naming rules 는 데이터베이스·테이블·column 이름이 UTF-8 문자열이면서 소문자여야 하고 1바이트 이상 255바이트 이하여야 한다고 정한다. Athena 는 DDL 에서 올라온 대문자 이름을 자동으로 소문자로 낮춘다. 여기에 reserved keyword 을 열 이름으로 쓰면 SQL 문법과 부딪혀 쿼리가 실패한다.

#2핵심 질문

테이블과 열 이름을 어떤 규칙으로 지어야 나중에 쿼리가 깨지지 않을까?

#3동작 예시

분석자가 주문 테이블에 order_date 라는 열을 만들려 한다. order 는 SQL 에 이미 쓰이는 reserved keyword 이라 그대로 두면 이후 SELECT 문이 오류로 걸린다.

큰따옴표로 감싸 CREATE TABLE 문을 다시 실행하고 show table information 명령으로 등록된 열 이름을 확인한다.

#4동작 과정

  1. 이름을 정한다소문자로 1바이트에서 255바이트 사이의 UTF-8 문자열을 고르고 앞쪽 공백이 없도록 한다. Athena 가 DDL 의 대문자 이름을 소문자로 바꿔 주므로 쿼리에서는 소문자로 적힌 이름이 보인다.
  2. 예약어를 피한다SELECT 같은 reserved keyword 을 열 이름으로 쓰려면 큰따옴표로 감싼다. CloudFormation 으로 Glue 데이터베이스를 만들 때 이름이 없으면 Glue 가 정한 이름이 만들어지며 이 이름은 Athena 에서 그대로 쓸 수 없다.
  3. 확인해 볼 것콘솔에서 show table information 을 실행해 등록된 열 이름이 소문자로 저장된 것과 큰따옴표로 감싼 열이 붙어 있는지 본다.

#5한 줄 요약

행과 열의 구분 방식을 알려 주는 SerDe 라는 설정으로 텍스트 파일도 CSV 처럼 구조가 있는 테이블로 읽어 오게 만드는 작업이다.

먼저 알아야 할 것 03-02

→ 03-03 참조

#1문제 상황

S3 에 있는 텍스트 파일은 한 줄에 값이 나란히 적혀 있어 어디까지가 한 행이고 어디부터가 열인지는 파일 안에 적혀 있지 않다(→ 03-02).

SerDe 는 serialization 과 deserialization 즉 값을 줄로 바꾸고 줄을 열로 되돌리는 방식을 정한 설정이다. ROW FORMAT DELIMITED 를 적으면 Athena 가 기본으로 LazySimpleSerDe 를 쓰고 어떤 구분 기호로 나눌지도 함께 지정하게 된다.

#2핵심 질문

구조가 없는 텍스트 파일을 어떻게 표처럼 나눠 읽을 수 있을까?

#3동작 예시

쉼표로 구분한 주문 로그 파일을 테이블로 등록한다. row format delimited 뒤에 fields terminated by ',' 를 적고 각 열의 자료형과 S3 위치를 선언한다.

이후 쿼리를 내면 Athena 가 파일을 한 줄씩 읽고 쉼표 위치마다 잘라 각 열 값으로 넣는다.

#4동작 과정

  1. 구분 방식을 고른다ROW FORMAT DELIMITED 를 쓰면 Athena 는 LazySimpleSerDe 를 기본으로 삼는다. FIELDS TERMINATED BY 로 열 구분 기호를, COLLECTION ITEMS TERMINATED BY 로 배열 안 구분 기호를, MAP KEYS TERMINATED BY 로 맵 키 구분 기호를 적는다.
  2. SerDe 를 직접 지정한다ROW FORMAT SERDE 에 정한 SerDe 이름과 WITH SERDEPROPERTIES 의 설정값을 적어 읽기와 쓰기 동작을 정한다. 기본값으로 충분하면 ROW FORMAT DELIMITED 로 짧게 쓸 수 있다.
  3. 확인해 볼 것만든 테이블에서 SELECT 한 줄을 돌려 구분 기호대로 값이 각 열에 들어갔는지 확인한다.

4. 저장 형식과 직렬화04-01

Parquet

행을 묶어서 컬럼 단위로 압축 저장하는 컬러너 저장 형식이라 조회를 할 때 읽는 데이터량만 줄어드는 게 아니라 서로 다른 컬럼을 함께 보는 집계 쿼리도 빠르게 돌아갑니다.

먼저 알아야 할 것 03-04

#1문제 상황

행마다 모든 값을 붙여 적는 형식에서는 특정 열 하나만 조회해도 그 열이 있는 블록을 통째로 읽어야 한다. 전체 파일을 다시 만들지 않고는 형식을 바꿀 수 없다(→ 03-04).

Parquet 는 columnar 저장 형식으로 각 컬럼 값만 모아 압축해 둔다. 그래서 필요 없는 컬럼은 아예 읽지 않는 column pruning 이 되고 여러 컬럼으로 짜는 집계 쿼리도 덜 읽고 빨리 끝난다.

#2핵심 질문

여러 컬럼을 함께 보는 집계 쿼리를 어떻게 빠르게 돌리게 할까?

#3동작 예시

비행 지연 데이터가 Parquet 로 저장된 테이블에서 출발 공항별 지연 시간 합계를 구한다.

Athena 는 도착 공항 컬럼과 지연 시간 컬럼만 읽고 나머지는 건너뛴다.

#4동작 과정

  1. 형식을 지정한다Parquet SerDe 는 이름 org.apache.hadoop.hive.ql.io.parquet.serde.ParquetHiveSerDe 로 등록되어 있고 CREATE EXTERNAL TABLE 에서 이 SerDe 를 지정해 Parquet 로 저장된 S3 데이터를 테이블로 만든다.
  2. 필요한 컬럼만 읽는다columnar 저장이라 column pruning 이 가능하다. 쿼리에 없는 컬럼의 블록은 디스크에서 읽지 않아 데이터량과 시간이 함께 줄어든다.
  3. 확인해 볼 것두 컬럼만 고른 쿼리와 전체 컬럼을 고른 쿼리의 실행 화면에서 읽은 데이터 크기가 다른지 본다.

ORC

#1문제 상황

ORC SerDe 를 쓰면 같은 방식으로 저장된 파일을 CREATE EXTERNAL TABLE 로 그대로 테이블에 연결할 수 있다.

#2핵심 질문

ORC 로 저장된 기존 데이터를 Athena 에서 그대로 조회하려면 어떻게 할까?

#3동작 예시

파티션도 함께 선언해 두면 날짜별로 나눠 조회할 수 있다.

#4동작 과정

  1. 테이블을 만든다STORED AS ORC 를 적으면 serialization library 이름 대신 이 구문을 쓴다. 실제로 쓰이는 라이브러리 이름은 org.apache.hadoop.hive.ql.io.orc.OrcSerde 다. 컬럼 단위로 저장하므로 필요한 컬럼만 읽는다.
  2. 파티션을 함께 둔다이 예 테이블에는 파티션도 들어가므로 파티션 기준 조회와 전체 조회를 같은 테이블에서 고를 수 있다.
  3. 확인해 볼 것테이블 목록에서 만든 ORC 테이블이 파티션과 함께 표시되는지 확인한다.

CSV 와 Amazon Ion

먼저 알아야 할 것 03-04

#1문제 상황

쉼표로 구분한 CSV 는 값을 큰따옴표로 감싸기도 하고 UNIX 숫자 시각을 넣기도 해 어떤 방식으로 읽을지 골라야 한다(→ 03-04).

Athena 는 그 선택에 따라 CSV SerDe 를 Lazy Simple SerDe 와 Open CSV SerDe 로 나누고 Amazon Ion 은 따로 다룬다.

#2핵심 질문

내 CSV 파일에는 어떤 SerDe 를 골라야 하는가?

#3동작 예시

큰따옴표로 감싼 값이 들어 있는 파일이면 Open CSV SerDe 를 지정한다. 아무것도 지정하지 않으면 Lazy Simple SerDe 가 쓰인다.

시각 값이 1579059880000 같은 UNIX 숫자로 들어 있으면 Open CSV SerDe 가 맞고 java.sql.Timestamp 형식이면 Lazy Simple SerDe 가 맞는다.

#4동작 과정

  1. SerDe 를 고른다값에 큰따옴표가 있으면 Open CSV SerDe 를 쓰고 없으면 지정 없이 Lazy Simple SerDe 를 쓴다. delimiter 는 ROW FORMAT DELIMITED 의 구문으로 정하고 첫 줄 머리글은 skip header row 설정으로 건너뛸 수 있다.
  2. 자료형을 맞춘다UNIX 숫자 TIMESTAMP 값이면 Open CSV SerDe 를 고르고 java.sql.Timestamp 형식 데이터면 Lazy Simple SerDe 를 고른다.
  3. 확인해 볼 것읽은 결과를 표로 띄워 첫 줄 머리글이 값으로 섞이지 않고 열 이름만 되었는지 확인한다.

  3. 논리 계획을 본다Logical plan 탭은 읽기와 결합의 논리 순서를 보여 준다. optimizer 가 무엇을 바꿔 치환했는지 여기서 확인하고 data scanned 가 큰 단계를 좁힌다.

ACID 트랜잭션

ACID 트랜잭션은 여러 쿼리에 걸친 변경을 모두 성공시키거나 모두 되돌리는 규칙으로, 중간에 실패한 갱신이 데이터에 반쪽짜리 상태로 남지 않게 해 준다.

먼저 알아야 할 것 07-01

#1문제 상황

S3 에 저장된 표는 원래 읽기 전용이라 한 행을 지우거나 고치려면 원본 파일을 다시 써야 했다. 그동안 다른 사람이 읽던 쿼리는 도중에 결과가 달라져 버릴 수 있었다.

ACID transactions는 이 데이터에 한 표 한정으로 insert, delete, update와 time travel을 제공하는 기능이다. 변경이 한 묶음으로 처리되고, Athena가 잠금과 조정을 알아서 맡아 따로 기록 잠금 장치를 붙이지 않아도 된다.

#2핵심 질문

S3 데이터의 여러 행을 안전하게 고치면서 다른 사람의 조회 결과가 뒤섞이지 않게 하려면 어떻게 할까?

#3동작 예시

고객이 정보 삭제를 요청해 주문 표에서 해당 주문을 지운다. 콘솔에서 SQL DELETE 문을 실행하면 Athena가 변경을 한 번에 처리하고 결과 화면에 지워진 행 수가 나온다.

문제가 생기면 time travel로 특정 시점의 표 상태를 다시 불러와 원래 값을 볼 수 있다.

#4동작 과정

  1. transactional 표를 연다ACID transactions가 적용된 표 형식(table format)으로 만든 표를 읽는다. Athena는 이때 파일 형식이 아니라 표가 갱신 이력을 저장하는 방식을 본다.
  2. 변경을 한 번에 건다SQL DELETE나 UPDATE 문을 실행하면 여러 행의 삭제를 insert, delete, update 연산으로 나눠 한 묶음으로 처리한다. snapshot isolation은 이미 시작된 쿼리가 시작 시점의 데이터만 보게 해 다른 조회와 섞이지 않게 한다.
  3. 과거 시점을 다시 본다처리 뒤 시간대를 지정해 time travel로 그 시점의 표를 조회한다. 되돌릴 값을 확인한 뒤 확정한다.
  4. 확인해 볼 것Athena 콘솔에서 같은 표를 두 번 조회해 갱신 전후의 행 수가 달라지는지 본다.

먼저 알아야 할 것 07-02

#1문제 상황

갱신과 삭제를 남기려면 어떤 파일이 최신인지 따로 관리해야 한다. 그 목록을 매번 다시 만들면 조회가 느려지고 목록이 어긋나면 결과가 틀린다.

#2핵심 질문

갱신과 삭제가 섞인 표를 Athena에서 그대로 정확하게 조회하려면 어떻게 할까?

#3동작 예시

주문 표에서 취소된 주문을 지운 뒤 최신 주문 수를 확인한다. 콘솔에서 같은 표를 조회하면 지워진 행이 반영된 수가 나오고, 특정 시점을 지정하면 지우기 전 상태가 나온다.

#4동작 과정

  1. 표를 읽는다Delta Lake 형식으로 쓰인 표를 AWS Glue 에 등록한 뒤 Athena 가 그 표를 읽는다. Athena는 파일별로 저장된 컬럼별 최소값과 최대값을 보고 조건에 맞지 않는 파일을 건너뛰어 읽는 양을 줄인다.
  2. 갱신한다MERGE 문으로 upsert 을 한다. 조건에 맞는 행은 바꾸고 없는 행은 새로 넣는 동작이다.

Apache Iceberg와 Hudi는 쓰기마다 데이터 파일과 그 파일 목록을 따로 관리해 스냅숏 조회와 스키마 변경을 지원하는 오픈소스 표 형식이며, Athena에서 SQL 로 바로 조회할 수 있다.

먼저 알아야 할 것 07-02

#1문제 상황

일반 파일로 저장된 표는 열을 추가하거나 바꾸면 기존에 쓰던 쿼리가 깨지고, 지금 어느 파일이 유효한지 따로 알기 어렵다.

Apache Iceberg 와 Apache Hudi는 이런 문제를 파일 목록을 따로 관리하는 방식으로 푼다. Athena에서 두 형식의 표를 SQL로 바로 읽을 수 있다.

#2핵심 질문

데이터를 고쳐 쓴 뒤에도 스키마를 지키며 과거 시점의 표를 볼 수 있게 하려면 어떤 표 형식을 써야 할까?

#3동작 예시

이벤트 표에 새 열을 넣고 과거 집계 쿼리를 다시 돌린다. Athena에서 같은 SQL을 실행하면 열이 늘어도 오류 없이 결과가 나오고, partition evolution 덕분에 파티션 기준도 바꿀 수 있다.

#4동작 과정

  1. 표를 읽는다Iceberg 또는 Hudi 형식으로 저장된 표를 Athena에서 SELECT로 조회한다. 두 형식은 개가 레코드 단위의 insert, update, delete와 time travel 쿼리를 지원한다.
  2. 수정이 겹쳐도 읽는다파일 목록이 따로 관리되므로 여러 사람이 동시에 써도 데이터가 섞이지 않고 각자 읽은 결과가 유지된다.
  3. 스키마를 바꾼다schema evolution으로 열을 추가하고 파티션 구성을 바꾼다. hidden partitioning은 열 이름이 아니라 저장된 값 기준으로 파티션을 찾는다.
  4. 확인해 볼 것Athena 콘솔에서 같은 표를 열을 추가한 뒤 다시 조회해 오류 없이 결과가 나오는지 본다.

스키마 변경 처리는 어떤 열 추가와 파티션 갱신을 어떤 파일 형식이 지원하는지 먼저 보고 맞는 문장을 쓰게 한다.

#2핵심 질문

#3동작 예시

#4동작 과정

  2. 열을 추가한다ALTER TABLE 문의 ADD COLUMNS로 새 열을 선언한다. 파일 형식에 따라 열 위치 지정 방식이 달라진다.

  4. 확인해 볼 것콘솔에서 방금 고친 표를 다시 조회해 열이 결과에 포함되는지 본다.

#2핵심 질문

#3동작 예시

#4동작 과정

  4. 확인해 볼 것콘솔에서 struct 로 저장한 표를 조회해 필드 이름별로 값이 나뉘어 보이는지 본다.

먼저 알아야 할 것 06-01

#1문제 상황

매장 위치, 항공 노선, 날씨 보고처럼 위도 경도가 붙은 데이터가 흔하다. 이 값을 그냥 숫자 열로만 두면 두 지점 사이가 얼마나 떨어졌는지 SQL 로 계산할 방법이 없다.

공간 데이터는 Athena 가 이런 지리 정보를 다룰 수 있게 정한 규약이다. 지리 정보를 표준 형식으로 담으면 거리와 포함 여부를 쿼리로 구한다.

#2핵심 질문

위치 정보가 담긴 테이블에서 거리와 포함 여부를 어떻게 계산할까?

#3동작 예시

매장 위치를 담은 테이블에서 특정 지점으로부터 가까운 순으로 매장 목록을 뽑는다. geospatial 함수를 쓴 쿼리 한 줄로 각 매장까지의 거리가 계산되어 거리 순으로 행이 나온다.

#4동작 과정

  1. 자료형을 정한다geography 는 위도 경도와 같은 지리 정보를 다루고 geometry 는 점과 선과 다각형 모양을 다룬다. 점·선·폴리곤·멀티폴리곤 같은 도형을 뺄 수 있다.
  2. 관계를 계산한다spatial function 로 두 지점의 거리와 같은지 다른지를 구한다. 두 점 사이 거리, 포함 여부, 닿는지 같은 연산이 여기에 든다.
  3. 조건을 걸어 필터한다범위 안에 들어오는 행만 남긴다. 계산된 거리 값에 WHERE 절을 붙이면 가까운 곳만 골라 낼 수 있다.
  4. 확인해 볼 것쿼리 결과에 거리 값이 계산된 열이 나오는지와 필터한 행 수를 확인한다.

사용자 정의 함수

사용자 정의 함수는 Athena SQL 에 없는 기능을 직접 정의해 쿼리에서 쓸 수 있게 한 것이며 랜덤 함수 같은 내장 함수와는 별개로 동작한다.

먼저 알아야 할 것 06-01

#1문제 상황

Athena SQL 의 내장 함수로는 없는 계산이 필요할 때가 있다(→ 11-02). 매번 쿼리 안에서 여러 단계를 거쳐 값을 만들어 내야 하고 같은 계산이 반복된다.

사용자 정의 함수는 그 계산을 이름 붙은 함수 하나로 만들어 쿼리에서 부를 수 있게 한다. UDF 는 입력을 받아 작업하고 결과를 돌려주는 동작 단위다.

#2핵심 질문

Athena 에 없는 계산을 쿼리 안에서 어떻게 부를 수 있을까?

#3동작 예시

쿼리 앞에 USING EXTERNAL FUNCTION 절을 적고 SELECT 문에서 그 함수를 부른다. 함수가 만든 결과 열이 결과 탭에 나온다.

#4동작 과정

  1. 함수를 준비한다Lambda function UDF 는 AWS Lambda 에 넣은 함수다. Java 배포 패키지 안에서 메서드로 정의하고 같은 패키지에 여러 개를 담을 수 있다.
  2. 쿼리에 선언한다SELECT 문 앞에 USING EXTERNAL FUNCTION 절을 쓰고 함수 이름과 Lambda 함수 이름을 적는다. SELECT 문은 그 함수를 부르며 넘길 변수를 지정한다.
  3. 제약을 지킨다UDF limitations 은 이 방식이 가지는 사용 한계다. Lambda 로 직접 배포하거나 AWS Serverless Application Repository 를 쓸 수 있다.
  4. 확인해 볼 것함수를 부른 쿼리 결과에 계산된 열이 나오는지 확인한다.

#5한 줄 요약

사용자 정의 함수Athena 에 없는 계산을 Lambda 함수로 만들어 SQL에서 이름으로 부르게 하는 것

데이터 보호와 암호화

Athena는 저장된 데이터와 주고받는 네트워크 구간, 그리고 쿼리 결과가 임시로 모이는 S3 오브젝트를 암호화해 사용자 데이터가 노출되지 않게 지키는 수단을 제공한다.

먼저 알아야 할 것 01-04

#1문제 상황

Athena 로 조회하면 원본은 그대로 두고 쿼리 결과를 다른 곳에 새로 쓴다(→ 06-01). 다루는 데이터는 사용자 데이터이므로 어디가 잠겨 있고 어디가 열려 있는지 한눈에 알아야 한다.

데이터 보호는 저장된 데이터 암호화와 네트워크를 오가는 구간 암호화, 그리고 결과가 잠깐 모이는 S3 오브젝트 암호화를 묶은 수단이다. KMS 로 암호화 키를 직접 관리할 수도 있다.

#2핵심 질문

Athena 로 다뤘던 사용자 데이터를 누가 보지 못하게 어떻게 지키는가?

#3동작 예시

팀 계정에서 Athena 에 접근하는 사람을 정한다. AWS IAM Identity Center 로 사용자별 계정을 만들고 다중 인증을 켜 두면 한 사람이 남의 계정으로 들어가는 일이 줄어든다.

#4동작 과정

  1. 암호화 상태를 정한다encryption at rest 로 저장된 데이터를 잠그고 encryption in transit 로 오가는 구간을 잠근다. 키 관리가 필요하면 KMS 를 쓴다.
  2. 계정과 사람 단위를 나눈다계정 자격 증명을 지키고 사용자마다 AWS IAM Identity Center 나 IAM 으로 계정을 세운다. 그 사람에게 필요한 권한만 준다.
  3. 접근 자격을 강화한다계정마다 multi-factor authentication 을 켠다. 설정 목록에서 어느 항목이 켜져 있는지 본다.
  4. 확인해 볼 것콘솔의 설정 화면에서 계정과 사용자가 분리되어 있고 암호화 관련 항목이 켜져 있는지 확인한다.

IAM 권한

IAM 권한은 AWS Identity and Access Management 정책으로 누가 어떤 Athena API 호출과 Glue 데이터 자원에 접근할 수 있는지를 정해 주는 규칙이다.

먼저 알아야 할 것 09-01

IAM 권한은 IAM policy 로 그 경계를 긋는다. policy action 은 실행할 수 있는 동작을 정한다.

#2핵심 질문

누가 어떤 Athena 기능과 데이터에 접근할 수 있는지를 어떻게 정하는가?

#3동작 예시

새 팀원을 추가하면서 Athena 로 쿼리를 돌릴 수 있고 지정된 버킷의 데이터만 볼 수 있게 권한을 정한다. 그 사람은 다른 테이블에는 접근이 막힌 상태로 Athena 콘솔을 연다.

#4동작 과정

  1. 필요한 자원을 나열한다Athena 는 S3 에 저장된 원본 데이터 위치와 AWS Glue Data Catalog 안의 데이터베이스와 테이블 자원에 권한이 있어야 한다(→ 02-02).
  2. 허용할 동작을 고른다Athena API action 목록 중 쓸 동작을 골라 policy 에 적는다. 전체 목록은 서비스 권한 참조 문서에 있다.
  3. 정책을 붙인다data access 를 어디까지 넓힐지 정책 조건으로 정한다. IAM 모범 사례를 따라 최소 권한으로 좁힌다.
  4. 확인해 볼 것Athena 콘솔을 열어 볼 수 있는 테이블 목록에 필요한 테이블만 뜨는지 확인한다.

#1문제 상황

워크그룹과 태그 접근은 그 대상을 ARN 으로 정확히 밝히고, 태그까지 붙여 접근 범위를 다시 나누는 방법이다.

#2핵심 질문

워크그룹 정책가 지정하는 대상을 어떻게 정확히 밝히고 나눌까?

#3동작 예시

#4동작 과정

  1. 대상을 ARN 으로 적는다워크그룹 이름을 입력으로 받는 policy action 이 있으면 리전과 계정 번호를 붙인 workgroup ARN 으로 지정한다.
  2. 태그로 범위를 나눈다resource tag 를 AWS 자원에 붙여 이름표를 만들고 그 태그를 조건으로 삼는다. tag policy 로 보이는 워크그룹을 가른다.
  3. 신뢰 식별 전파를 고려한다trusted identity propagation 이 켜진 워크그룹은 AWS IAM Identity Center 사용자를 IdentityCenterApplicationArn 에 배정해야 접근이 된다.
  4. 확인해 볼 것Athena 콘솔에서 자신의 워크그룹 목록에 지정된 워크그룹이 보이는지 확인한다.

Lake Formation

Lake Formation은 데이터 위치와 테이블에 대한 권한을 한곳에서 관리해 Athena가 어떤 데이터를 읽을 수 있게 통제하는 Glue 기반 서비스이다.

먼저 알아야 할 것 09-02

#1문제 상황

S3 에 저장된 데이터의 권한을 IAM 정책에 따로 적으면 테이블이 늘어날수록 규칙이 산으로 쌓이고 어떤 사람이 어떤 열을 볼 수 있는지 한눈에 파악하기 어렵다(→ 09-02).

Lake Formation은 Glue 기반 서비스로 데이터베이스와 테이블 그리고 열에 대한 권한을 계층으로 두고 주고 빼는 통제 수단을 만든다. 이 한 겹의 권한 체계로 fine-grained access control, 즉 세분 접근 제어를 구현한다.

#2핵심 질문

데이터 위치마다 권한을 따로 적지 않고도 Athena 가 읽을 수 있는 데이터의 범위를 어디까지 좁힐 수 있을까?

#3동작 예시

한 팀은 주문 테이블의 전체를 볼 수 있고 다른 팀은 같은 주문 테이블에서 금액 열만 볼 수 있게 한다. Athena 에서 그 팀이 주문을 조회하면 등록된 계정이 지운 행과 막힌 열이 제외된 값만 나온다.

Lake Formation 에 등록되지 않은 데이터도 Athena 로 조회할 수 있고 등록된 데이터의 권한 규칙이 적용된다.

#4동작 과정

  1. 권한을 등록한다데이터 위치와 데이터 카탈로그를 Lake Formation 에 넘기고 데이터베이스와 테이블과 열에 권한을 계층별로 부여한다. 이때 row-level 과 column-level 권한을 각각 지정해 같은 테이블 안에서도 사람마다 보이는 범위를 갈라 둔다.
  2. Athena 가 권한을 확인한다Athena 는 S3 원본이나 카탈로그를 읽기 전에 Lake Formation 의 권한을 확인해 허용된 데이터만 반환한다. 쓰기 작업에는 이 권한이 적용되지 않는다.
  3. 쿼리를 실행한다콘솔에서 일반 SQL 로 조회하면 등록된 데이터에는 권한이 걸리고 등록되지 않은 데이터는 그대로 읽힌다.
  4. 확인해 볼 것Athena 콘솔에서 같은 테이블을 서로 다른 두 계정으로 열어 보고 보이지 않는 열이 각기 다른지 확인한다.

먼저 알아야 할 것 09-05

#1문제 상황

Athena 는 서버를 따로 두지 않고 그 자리에서 직접 데이터를 읽어 답하므로(→ 01-01) 문제가 생겼을 때 무엇을 확인해야 할지 자체 로그는 알기 어렵다. 누가 어떤 쿼리를 보냈는지 흔적이 남아 있지 않다면 권한 문제도 재현도 못 한다.

AWS CloudTrail 에 Athena 콘솔 호출과 Athena API 호출이 이벤트로 남는다. 여기에 서비스 상태와 availability 지표를 함께 보면 장애 때 누가 무엇을 했는지 살필 수 있다.

#2핵심 질문

누가 언제 어떤 쿼리를 Athena 로 보냈는지 나중에 확인할 수 있을까?

#3동작 예시

운영자가 Athena 콘솔에 접근해 이상한 쿼리가 많이 나왔는지 확인한다. CloudTrail 이벤트 기록에서 요청을 보낸 IP 주소와 요청자, Athena 로 전달된 요청 내용을 시간순으로 확인한다. Athena 로 CloudTrail 로그 파일 자체를 조회하면 다른 AWS 서비스의 기록도 함께 볼 수 있다.

#4동작 과정

  1. 호출을 기록한다CloudTrail 이 Athena 콘솔과 API 호출을 이벤트로 남긴다. 각 이벤트에서 누가 보냈는지와 어느 IP 에서 보냈는지, 언제 보냈는지와 요청 내용이 함께 담긴다.
  2. 기록을 되조회한다Athena 는 CloudTrail 로그 파일을 테이블로 읽어 Athena 외의 AWS 서비스 이력까지 같은 SQL 로 함께 살핀다.
  3. 사용량을 살핀다Amazon Quick 같은 관리형 분석 도구로 대시보드를 만들어 Athena 사용량과 서비스 상태를 함께 확인한다.
  4. 확인해 볼 것CloudTrail 콘솔에서 Athena 콘솔 접근 이벤트를 시간순으로 열어 누가 언제 접속했는지 보이는지 확인한다.

10. 비용과 성능10-01

워크그룹

여러 사람이 함께 Athena를 쓸 때 쿼리 실행 권한과 데이터 접근 범위, 그리고 과금 기준을 하나로 묶어 관리하는 단위다.

먼저 알아야 할 것 09-03

#1문제 상황

Athena 는 계정마다 묶여 있어 자동 보고서 작업과 분석가의 즉석 조회를 같은 자리에서 돌리면 비용도 섞이고 한쪽이 다른 쪽을 막는다.

workgroup 는 쿼리마다 지정하는 묶음 단위다. 워크그룹마다 쿼리 실행 기록과 결과 위치가 따로 생기고 과금도 그 안에서만 계산된다.

#2핵심 질문

서로 다른 팀의 쿼리를 어떻게 나누고 비용과 권한을 따로 지키게 할까?

#3동작 예시

운영팀에는 자동 보고서용 워크그룹을 하나 만들고 분석팀에는 즉석 조회용 워크그룹을 하나 만든다. 분석가가 큰 테이블을 잘못 훑어도 워크그룹별 bytes scanned cutoff 이 걸려 있어 비용이 정해 둔 상한을 넘지 못하고 결과 파일도 지정한 output location 에 따로 쌓인다.

#4동작 과정

  1. 묶음을 만든다용도에 따라 워크그룹을 하나씩 만들고 각기 멤버와 output location 을 지정한다. 워크그룹은 IAM 자원이므로 resource-level identity-based policies 로 접근 팀을 나눌 수 있다.
  2. 쿼리를 나눠 보낸다자동 스케줄 작업과 분석가의 즉석 조회를 서로 다른 워크그룹에서 돌린다. 각 워크그룹은 자체 쿼리 기록과 저장 쿼리 목록을 갖는다.
  3. 제한을 건다per-query cost control 로 쿼리마다 읽는 데이터 양과 결과를 저장할 위치를 강제한다. bytes scanned cutoff 을 두면 바깥 데이터 스캔이 많은 쿼리가 미리 막힌다.
  4. 확인해 볼 것Athena 콘솔의 워크그룹 목록에서 각 워크그룹의 결과 위치와 설정을 따로 열람해 본다.

쿼리 처리 용량 관리

워크그룹마다 동시에 돌릴 수 있는 쿼리 수를 정해 두어 특정 사용자가 서비스 전체의 처리 능력을 다 쓰고 다른 사람의 쿼리가 밀리는 일을 막는 설정이다.

먼저 알아야 할 것 10-01

→ 10-01 참조

#1문제 상황

기본 상태에서는 모든 워크그룹이 하나의 처리 용량을 나눠 쓴다(→ 10-01). 많은 사람이 동시에 큰 쿼리를 보내면 어떤 사람은 빨리 끝나고 어떤 사람은 한참 기다려야 한다.

capacity reservations 는 중요 워크로드가 먼저 자리를 잡도록 자리를 따로 예약하는 기능이다.

#2핵심 질문

한꺼번에 들어오는 쿼리 사이에서 중요한 워크로드의 처리 자리를 어떻게 먼저 확보할까?

#3동작 예시

운영팀이 새벽 집계 쿼리를 돌리려고 한다. 운영팀 워크그룹은 예약된 capacity reservation 에 붙어 있어 그 시간에 다른 팀이 아무리 많이 잡아도 처리 용량이 줄지 않는다. 반면 예약 밖 워크그룹은 남는 용량만 쓴다.

#4동작 과정

  1. 예약한다capacity reservation 을 만들고 필요한 Data Processing Units, 즉 DPU 수를 정한다. capacity management 가 용량의 우선순위와 크기 조절을 맡는다.
  2. 워크그룹을 붙인다용량을 받을 워크그룹을 하나 이상 예약에 배정한다. auto scaling 이 필요에 따라 예약 용량을 늘리고 줄인다.
  3. 용량을 공유한다서버리스 방식이라 예약한 만큼만 유지되며 SQL 문을 고칠 필요는 없다. compute capacity 가 overprovisioned 된 상태는 비용 낭비로 볼 수 있다.
  4. 확인해 볼 것Athena 콘솔에서 예약에 배정된 워크그룹 목록에 자신이 쓰는 워크그룹이 붙어 있는지 본다.

10. 비용과 성능10-03

성능 조정

데이터를 어떻게 나누어 저장하고 어떤 파일 형식과 분할 방식으로 읽게 할지 등을 손봤을 때 Athena 쿼리가 더 빨리 끝나도록 고치는 일.

먼저 알아야 할 것 06-02

→ 10-04 참조

#1문제 상황

같은 결과를 내는 쿼리라도 데이터를 어떻게 나누어 두고 어떤 파일로 저장했느냐에 따라 걸리는 시간이 크게 달라진다. Athena 는 클라우드 규모로 동작하는 서비스라 처리량이 관건이다.

performance tuning 은 서비스 사용법과 쿼리문 그리고 데이터 구조 세 갈래를 손보는 일이다.

#2핵심 질문

Athena 쿼리가 느릴 때 무엇을 바꾸면 더 빨리 끝낼 수 있을까?

#3동작 예시

운영자가 느린 집계 쿼리의 실행 계획을 연다(→ 06-02). 읽은 데이터가 예상보다 훨씬 많다. 해당 테이블의 파티션 키가 조회 조건과 맞지 않아 전체 파일을 읽고 있음을 보고 파티션 프젝션과 clustered column 을 적용해 읽는 양만 줄인다.

#4동작 과정

  1. 원인을 본다쿼리 실행 계획에서 어느 단계에서 얼마나 많이 읽는지 살펴본다. 여기서 partition pruning 이 일어나지 않는 구간이 있으면 병목이다.
  2. 데이터를 나눈다partition projection 으로 필터 값이 없어도 읽을 구간만 지정하고 clustered column 으로 같은 키의 값을 한 파일에 모아 읽기 단위를 줄인다.
  3. 형식을 고른다columnar storage formats 를 써서 필요한 컬럼만 꺼내 읽고 cache 로 반복되는 조회를 다시 계산하지 않게 한다. S3 throttle 이 걸리면 읽기 요청을 조절한다.
  4. 확인해 볼 것같은 쿼리를 다시 실행해 쿼리 통계에 나타는 처리 시간이 줄었는지 확인한다.

압축 형식

열려 있는 데이터가 저장될 때 여러 값을 묶어 작게 압축해 둔 형태이며, Athena 는 이 형식을 읽는 데 필요한 데이터만 꺼내므로 전체를 다 읽지 않아도 된다.

먼저 알아야 할 것 04-01

→ 10-03 참조

#1문제 상황

데이터를 풀어 놓고 저장하면 같은 내용을 더 많이 읽고 옮겨야 해 조회가 느려지고 비용도 오른다(→ 04-01).

Athena 는 파일을 통째로 읽는 대신 필요한 컬럼만 골라 읽는 압축 형식인 Parquet 과 ORC 를 권한다.

#2핵심 질문

저장 용량과 읽는 비용을 함께 줄이려면 어떤 압축 형식으로 파일을 써야 할까?

#3동작 예시

한 테이블의 Parquet 파일이 절반은 Snappy 로 절반은 GZIP 으로 압축돼 있다. Athena 는 이 테이블을 문제 없이 읽어 낸다. 같은 원칙이 ORC 와 텍스트 파일 그리고 JSON 저장 형식에도 적용된다.

#4동작 과정

  1. 형식을 고른다Athena 가 지원하는 압축 형식은 BZIP2 와 DEFLATE 와 GZIP 그리고 LZ4 와 Snappy 와 ZSTD 등이다. LZ4 는 압축률보다 압축과 풀 속도를 중시한다.
  2. 기본값을 쓴다엔진 버전 2 와 3 의 Hive 테이블에서는 GZIP 이 Parquet 와 텍스트 파일의 기본 쓰기 압축 형식이다.
  3. 섞어도 읽는다한 테이블 안에서 파일마다 압축 형식이 달라도 그대로 읽힌다. tar.gz 형태의 파일은 지원하지 않는다.
  4. 확인해 볼 것같은 테이블에서 컬럼 몇 개만 골라 조회해 전체 파일을 읽지 않고도 결과가 나오는지 확인한다.

10. 비용과 성능10-05

서비스 할당량

Athena 계정 전체에 미리 정해진 한계로 예를 들면 한 번에 열 수 있는 데이터 크기나 실행 중인 쿼리 수가 정해져 있고, 넘어가면 오류가 나거나 요청이 거절된다.

먼저 알아야 할 것 10-01

#1문제 상황

Athena 는 요청이 몰리면 그대로 받으려 든다(→ 10-02). 그래서 계정 전체에 미리 정해진 한계, 즉 서비스 할당량이 걸려 있다.

Service Quotas 는 이렇게 정해진 한계와 그 값이다. 한도를 넘기면 쿼리가 멈추거나 요청이 거절된다. 조절 가능한 항목은 상향을 요청할 수 있다.

#2핵심 질문

한 번에 얼마나 많은 쿼리를 얼마나 오래 돌릴 수 있는가?

#3동작 예시

운영자가 대시보드 쿼리부터 야간 집계까지 한꺼번에 건다. 집계와 조회를 한꺼번에 건다. 실행 중인 DML 쿼리 수를 넘어 할당량에 걸린다.

콘솔의 쿼리 기록에서 실패한 쿼리가 어떤 한계에 닿았는지 보고, 상향 여부를 정한다.

#4동작 과정

  1. 한계를 확인한다limit, 즉 계정에 걸린 상한값을 본다. 값은 AWS 리전마다 다르다. request quota 는 실행 중인 DML 쿼리 수를 뜻하고 SELECT 와 CTAS, INSERT INTO 가 여기에 든다.
  2. 시간 상한을 본다DML query timeout 과 DDL query timeout 은 쿼리가 실행될 수 있는 최대 분 수다. 넘으면 Athena 가 스스로 취소한다. CREATE TABLE 같은 DDL 쿼리는 Active DDL queries 로 따로 센다.
  3. 조절한다상향이 필요한 항목은 Service Quotas 콘솔에서 요청한다. Glue 쪽 스키마 제약은 별도 할당량 문서를 본다.
  4. 확인해 볼 것Athena 콘솔의 쿼리 기록에서 상태가 실패로 남은 쿼리를 열어 어느 한계에 닿았는지 확인한다.

엔진 버전 관리

Athena 가 쿼리를 실행할 때 쓰는 처리 엔진의 종류와 버전을 작업 부하에 맞게 골라 지정하고 바꾸는 기능으로, 엔진 버전이 올라가면 더 빠른 처리와 지원 기능이 늘어난다.

엔진 버전 관리는 워크그룹에 engine version 을 지정해 이 차이를 없앤다.

#2핵심 질문

각 워크그룹이 어느 엔진 버전으로 쿼리를 돌릴지 어떻게 정하는가?

#3동작 예시

쿼리 편집기에도 지금 쓰이는 엔진이 표시되므로 같은 화면에서 확인이 끝난다.

#4동작 과정

  1. 기본값을 확인한다워크그룹은 자동 승격, 즉 auto upgrade 가 켜진 채로 만들어진다. Athena 가 대신 버전을 올려 준다.
  2. 버전을 고정할지 정한다특정 버전을 지정하면 Athena 가 그 버전을 그대로 쓴다. 정한 버전을 바꾸지 않는다.
  3. 올라간 것을 확인한다새 엔진 버전이 나오면 Athena 콘솔과 AWS Health Dashboard 로 알린다. AWS Health Dashboard 는 계정과 서비스에 영향을 주는 일을 알려 주는 화면이다.
  4. 확인해 볼 것Athena 콘솔의 워크그룹 상세 페이지에서 지정된 엔진 버전이 표시되는지 확인한다.

SQL 참조

Athena 의 데이터 형식은 CREATE TABLE 같은 DDL 문에는 Apache Hive 이름으로, SELECT 와 CTAS, INSERT INTO 같은 DML 문에는 Trino 이름으로 열을 선언하게 한다.

  2. DML 이름을 쓴다SELECT 와 CTAS, INSERT INTO 에서는 Trino 데이터 형식 이름을 쓴다. DDL 과 DML 이 같은 열을 다르게 부르는 경우가 있어 표로 나란히 비교된다.

비 Hive 테이블 형식

Apache Iceberg 나 Apache Hudi 같은 Hive 밖의 표 형식을 쓰면 갱신과 스냅숏 같은 트랜잭션 기능을 얻는 대신 지원 버전과 조작 방식에 제약이 따라온다.

먼저 알아야 할 것 07-04

#1문제 상황

표 형식마다 갱신과 스냅숏 같은 트랜잭션 기능 지원 여부가 달라 어떤 형식을 쓸지 골라야 한다(→ 07-04). Athena for Spark 세션과 노트북에서는 Apache Hive 테이블에 더해 Linux Foundation Delta Lake, Apache Hudi, Apache Iceberg 테이블을 쓸 수 있다. 대신 제약이 따라온다.

#2핵심 질문

노트북에서 Hive 밖의 표 형식을 쓸 때 무엇을 지켜야 하는가?

#3동작 예시

분석가가 Iceberg 로 저장된 표를 갱신한 뒤 읽어 본다. 스냅숏으로 이전 시점도 볼 수 있지만 같은 노트북에서 Hudi 표까지 함께 다루려 하면 안 된다.

#4동작 과정

  1. 형식을 고른다노트북에서 Delta Lake, Apache Hudi, Apache Iceberg 가운데 non-Hive table format 을 하나 고른다. Iceberg in Spark 과 Hudi in Spark 그리고 Delta Lake in Spark 은 각각 이 형식으로 읽고 쓰는 방식을 다룬다.
  2. 범위를 지킨다한 노트북에는 한 가지 형식만 쓸 수 있고 다른 형식이 필요하면 노트북을 따로 만든다.
  3. 메타 저장소를 정한다검증된 조합은 AWS Glue 를 메타 저장소로 쓰는 경우이며 다른 메타 저장소는 지원하지 않는다.
  4. 확인해 볼 것노트북에서 표를 읽을 때 어느 형식의 표인지 노트북 설정에서 확인한다.
