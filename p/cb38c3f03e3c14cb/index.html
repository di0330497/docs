1. EFS 의 뼈대 — 무엇을 공유하는가01-01

Amazon EFS 란 무엇인가

Amazon EFS(Elastic File System)는 여러 컴퓨터가 네트워크를 통해 동시에 하나의 파일 저장소를 읽고 쓰는 관리형 서비스로, 따로 디스크를 붙이지 않아도 저장 공간을 공유할 수 있다.

#1문제 상황

여러 컴퓨터가 같은 파일을 나눠 써야 하는데, 각 컴퓨터에 디스크를 붙여 두면 용량과 용도를 따로 관리해야 한다. 파일이 늘어도 미리 큰 디스크를 사 두어야 한다.

Amazon EFS는 파일 데이터만 공유하면 되는 경우를 대신한다. serverless로 돌아가며 별도 서버를 두지 않아도 되고, shared file system으로 여러 컴퓨터가 함께 쓴다. 파일을 넣고 빼는 만큼 용량과 성능이 자동으로 늘어나고 줄어드는 elastic 동작을 기본으로 한다.

#2핵심 질문

파일을 따로 관리하지 않고 여러 컴퓨터가 함께 쓰는 저장 공간을 어떻게 만드는가?

#3동작 예시

여러 대의 서버가 같은 설정 파일과 이미지 파일을 읽어야 한다. EFS 파일 시스템을 하나 만들고 각 서버에 붙였다. 서버 한 대가 파일을 고치자 나머지 서버가 같은 내용을 바로 읽는다.

#4동작 과정

  1. 파일 시스템을 만든다웹 콘솔이나 API로 요청하면 AWS가 파일을 담을 저장소와 이를 노출하는 managed NFS file system, 즉 NFS 규약으로 외부에 내놓는 관리형 저장 공간을 만들어 준다. 파일 데이터만 올리면 된다.
  2. 여러 컴퓨터가 함께 붙는다shared file system은 여러 클라이언트가 동시에 붙어 읽고 쓰는 구조를 뜻한다. 각 컴퓨터는 자기 저장소처럼 해당 경로를 쓴다.
  3. 양에 따라 늘어난다elastic은 파일을 추가하거나 지우는 양에 따라 용량과 처리량이 함께 늘어나고 줄어드는 성질이다. 시작할 때 크기를 미리 정하지 않는다.
  4. 확인해 볼 것콘솔의 파일 시스템 목록에 만든 파일 시스템이 상태와 함께 나타나는지 본다.

#5한 줄 요약

Amazon EFS용량을 미리 정하지 않고 자동으로 늘리며 여러 컴퓨터가 함께 쓰는 관리형 NFS 파일 저장 공간

#1문제 상황

파일 서버를 직접 만들면 서버를 켜고 디스크와 권한을 관리하고 장애 때 복구하는 일을 모두 해야 한다. 클라이언트가 어디로 요청을 보내는지 경로도 정해 줘야 한다(→ 01-01).

EFS는 이 구조를 이미 만들어 둔 뒤에 파일 시스템과 네트워크 상의 접점을 나눠 둔다. 클라이언트는 VPC 안의 mount target에 붙어 파일을 읽고 쓰며, 여러 NFS 클라이언트가 동시에 붙어 있을 수 있다.

#2핵심 질문

클라이언트가 EFS에 붙어 파일을 주고받는 과정은 어떻게 이어지는가?

#3동작 예시

EC2 인스턴스가 파일 시스템에 마운트된 뒤 파일 하나를 연다. 클라이언트가 mount target으로 요청을 보내고 EFS가 해당 데이터를 돌려준다. 같은 파일을 다른 인스턴스도 같은 경로에서 연다.

#4동작 과정

  1. 파일 시스템을 만든다EFS 안에서 데이터를 담는 file system을 만들고 여기에 IP 주소를 부여한다(→ 01-01). 파일 시스템 하나에 여러 접점을 둘 수 있다.
  2. 접점을 만든다mount target은 VPC 안에서 파일 시스템으로 들어오는 자리다. file system의 Availability Zone, 즉 서로 분리된 구역마다 접점을 하나씩 둔다.
  3. 클라이언트가 붙는다VPC 안에서 NFSv4를 통해 파일 시스템을 EC2 인스턴스에 마운트한다. 그 뒤 파일을 만들고 읽고 고치는 요청이 마운트된 경로에서 그대로 동작한다.
  4. 확인해 볼 것인스턴스에서 마운트한 경로로 이동해 파일 목록이 보이는지 확인한다.

#5한 줄 요약

EFS의 동작 구조는 클라이언트가 가용 영역별 mount target을 통해 파일 시스템에 요청을 보내는 것입니다.

1. EFS 의 뼈대 — 무엇을 공유하는가01-03

EFS 의 특징

EFS 는 파일을 저장하고 읽는 양이 늘어날수록 별도 설정 없이 저장 공간과 처리량이 함께 늘어나고, 여러 가용 영역에 걸친 높은 가용성과 공유 파일 액세스를 기본으로 제공한다.

먼저 알아야 할 것 01-01

#1문제 상황

파일 저장소를 미리 정해진 크기로 만들면 나중에 부족하거나 남게 된다. 한 컴퓨터의 장애가 저장 공간 전체의 중단으로 이어지기도 한다(→ 01-01).

EFS의 Features는 이 문제를 두 축에서 푼다. elastic capacity로 파일 양에 따라 용량을 정하지 않고, 여러 가용 영역에 접점을 두어 한 곳이 흔들려도 나머지가 받쳐 준다. 데이터는 Amazon EBS 위에 저장되며 저장 중 암호화를 지원한다. 인증과 권한은 IAM 자격 증명으로 관리한다.

#2핵심 질문

EFS는 용량 확정과 장애 대응 문제를 어떻게 함께 풀어 주는가?

#3동작 예시

팀이 로그 파일을 모은다. 처음에는 작은 양이었고 곧 매일 늘어나는 양이 쌓였다. 파일 시스템 크기를 다시 정하지 않았는데도 용량이 따라 늘었고, 한 가용 영역의 자리가 끊겨도 다른 곳의 접점으로 계속 읽었다.

#4동작 과정

  1. 저장 공간을 정하지 않는다elastic capacity는 파일을 추가하고 지우는 양에 맞춰 저장 공간과 처리량이 함께 오르내리는 특징이다. 미리 크기를 정할 필요가 없다.
  2. 여러 곳에서 함께 붙는다shared access는 여러 클라이언트가 동시에 같은 파일 시스템에 붙어 읽고 쓸 수 있는 성질이다. 각 Availability Zone마다 mount target을 둔다.
  3. 데이터를 안전하게 둔다파일은 backed by Amazon EBS, 즉 AWS의 블록 저장 위에 올려지며 암호화된 상태로 저장된다. 관리 콘솔과 API 요청에는 유효한 IAM 자격 증명이 필요하다.
  4. 확인해 볼 것파일 시스템 상세 화면에서 가용 영역별 mount target 목록과 암호화 설정이 보이는지 본다.

#5한 줄 요약

EFS 특징크기를 미리 정하지 않고 여러 가용 영역에서 함께 쓰는 안전한 공유 파일 저장

NFS 와의 관계

EFS 는 네트워크를 통해 파일을 주고받는 표준 규약인 NFS 를 통해 클라이언트에 노출되므로, NFS 를 이해하고 있으면 EFS 의 마운트와 권한 동작을 함께 이해할 수 있다.

먼저 알아야 할 것 01-02

#1문제 상황

클라이언트가 EFS에 붙을 때 어떤 규약으로 말을 하는지 알지 못하면 마운트도 권한 오류도 이유를 알 수 없다. 규약을 직접 만들어야 한다면 모든 클라이언트를 고쳐야 한다.

EFS는 파일을 주고받는 표준 규약인 Network File System, 줄여서 NFS로 클라이언트에 노출한다. 그래서 NFSv4를 지원하는 클라이언트는 도구를 바꿀 필요 없이 붙는다. 다만 파일을 실제로 읽고 고칠 수 있는지는 NFS가 전달하는 unix permissions, 즉 사용자·그룹·권한 모드가 정한다.

#2핵심 질문

클라이언트는 어떤 규약으로 EFS에 붙고 파일 권한은 누가 정하는가?

#3동작 예시

리눅스 인스턴스의 파일 목록에 EFS 항목이 없다. 마운트 명령에 nfs4 유형과 파일 시스템의 DNS 이름, 2049 포트를 넣어 다시 실행하자. 경로가 생겼고, 안의 파일을 고치는 것도 가능했다.

#4동작 과정

  1. NFS로 노출한다NFS는 파일을 네트워크로 주고받는 표준 규약이다. EFS는 이 규약으로 클라이언트에 파일 시스템을 내놓는다.
  2. NFSv4로 붙인다EFS는 NFSv4를 지원한다. 최신 리눅스나 macOS의 NFS 클라이언트와 EFS mount helper를 함께 쓰면 붙을 수 있다(→ 03-02).
  3. 권한은 unix 권한이 정한다NFSv4가 보낸다고 한 unix permissions는 소유자·그룹·권한 비트다. 네트워크로 신원은 오지만 파일을 고칠 수 있는지는 이 값이 정한다.
  4. 확인해 볼 것인스턴스에서 마운트된 파일의 소유자와 권한 표시가 어떻게 나오는지 본다.

#5한 줄 요약

NFS와의 관계EFS가 표준 규약으로 노출되어 규약을 아는 클라이언트가 그대로 붙는다는 점

처음 파일 시스템을 만들고 붙여 본다

콘솔에서 EFS 파일 시스템을 만든 뒤, EC2 인스턴스에 마운트 헬퍼로 붙여 그 안의 디렉터리가 실제 폴더처럼 보이게 하는 일련의 첫 단계를 말한다.

먼저 알아야 할 것 01-03

#1문제 상황

EFS가 무엇인지 알아도 처음 한 번은 어디서부터 손을 대야 할지 막막하다. 파일 시스템과 인스턴스가 서로 다른 VPC에 있으면 처음부터 붙지 않는다(→ 01-03).

Getting started는 그 첫 순서를 정해 준다. 콘솔에서 파일 시스템을 만들고 EC2 인스턴스를 띄운 뒤, 마운트 헬퍼로 붙여 파일을 옮기고 마지막에 자원을 정리한다. 파일 시스템 lifecycle, 즉 만들고 붙이고 지우는 흐름 전체를 한 번에 따라간다.

#2핵심 질문

처음 EFS 파일 시스템을 만들고 EC2에 붙이는 순서는 어떻게 되는가?

#3동작 예시

콘솔에서 Getting started 페이지를 연다. 파일 시스템과 EC2 인스턴스를 같은 리전 같은 VPC에 만들고, 인스턴스에 SSH로 들어가 마운트 헬퍼 명령을 친다. 화면에 파일이 올라간 마운트 경로가 폴더로 나타난다.

#4동작 과정

  1. 준비를 확인한다EFS, EC2, VPC 자원이 같은 AWS 리전에 있고 기본 VPC와 키 페어, 보안 그룹이 준비돼 있어야 한다. EC2 인스턴스를 띄울 수 있는 상태부터 갖춘다.
  2. 파일 시스템과 인스턴스를 만든다콘솔에서 EFS 파일 시스템을 만들고 EC2 인스턴스를 띄운다. AWS CLI로 같은 요청을 대신 낼 수도 있다.
  3. 인스턴스에 붙인다인스턴스에 접속해 mounting on EC2 Linux 방식으로 마운트 헬퍼를 실행한다. 파일 시스템에 있던 디렉터리가 로컬 폴더로 보인다.
  4. 확인해 볼 것인스턴스에서 마운트 경로에 들어가 파일을 하나 만들어 다시 보이는지 본다.

#5한 줄 요약

2단계 2. 파일 시스템을 만든다

Amazon EFS 파일 시스템은 콘솔이나 CLI 로 요청한 크기와 처리량 대신, 쓰인 만큼 용량과 처리량이 늘어나는 NFS 기반 관리형 파일 저장 공간이다.

먼저 알아야 할 것 01-05

#1문제 상황

디스크나 블록 저장소는 만들 때 크기와 성능을 미리 정해야 한다. 틀리면 다시 만들어야 한다. 파일을 몇 개 올릴지도 모른 상태에서 이러한 선택은 부담이다.

Creating file systems는 그 선택을 건너뛴다. 파일 시스템은 쓰인 양만큼 용량과 처리량이 늘어나는 NFS 기반 관리형 저장 공간이다(→ 01-01). 콘솔에서는 Quick create로 권장 설정을 그대로 쓰고, AWS CLI나 EFS API로도 같은 요청을 보낸다.

#2핵심 질문

크기를 정하지 않고 EFS 파일 시스템을 처음 만들려면 무엇을 고르는가?

#3동작 예시

콘솔의 EFS 화면에서 파일 시스템을 생성한다. Quick create를 고르자 권장 설정이 그대로 채워졌다. 생성이 끝나면 화면에 file system ID, 즉 파일 시스템을 가리키는 식별자가 떴고 그 이름으로 곧바로 쓸 수 있었다.

#4동작 과정

  1. 생성 방식을 고른다콘솔의 Quick create는 권장 설정으로 즉시 만든다. 설정을 바꿔야 하면 사용자 지정으로 각 항목을 정한다. AWS CLI나 EFS API로도 같은 파일 시스템을 만들 수 있다.
  2. 성능과 저장을 정한다Quick create는 general purpose 성능 모드와 elastic throughput mode, 그리고 저장 데이터를 암호화하고 30일 뒤 IA 계층으로 옮기는 lifecycle 정책을 고른다. 중복 요청을 구분하는 CreationToken도 함께 정한다.
  3. 접점과 식별자를 챙긴다생성한 리전의 각 Availability Zone마다 mount target이 지정한 서브넷의 IPv4 주소로 만들어진다. 생성이 끝나면 file system ID가 정해지고 이 값을 보관해 두고 지울 때도 쓴다.
  4. 확인해 볼 것콘솔 목록에 방금 만든 파일 시스템의 ID와 상태가 나타나는지 본다.

#5한 줄 요약

파일 시스템 만들기크기를 고르지 않고 권장 설정으로 NFS 저장 공간을 즉시 얻는 것

2. 파일 시스템을 만든다02-02

파일 시스템 정책

파일 시스템 정책은 파일 시스템에 어떤 요청이 허용되는지를 IAM 사용자·역할이 아닌 리소스 자체에 붙여 기술하는 JSON 규칙이다.

먼저 알아야 할 것 02-01

#1문제 상황

IAM 사용자·역할에 권한을 주면(→ 05-01) 그 주체만 제어한다. 다른 계정이나 서비스가 EFS 파일 시스템에 붙으려면 권한을 따로 찾아 붙여 줘야 한다.

파일 시스템 정책은 그 파일 시스템에 붙는 resource policy다. 허용할 요청을 JSON 으로 적어 두면 해당 파일 시스템으로 들어오는 접근을 스스로 거른다.

#2핵심 질문

이 파일 시스템에 어떤 요청을 허용할까?

#3동작 예시

운영팀 계정의 백업 도구가 nightly 로 이 파일 시스템에 파일을 쓰게 하려 한다. 콘솔에서 파일 시스템을 고르고 File system policy 탭에서 정책에 그 계정의 쓰기 요청만 적어 넣는다.

이후 그 계정에서 오는 요청은 정책에 적힌 대로 통과하고, 다른 곳에서 오는 요청은 거절된다.

#4동작 과정

  1. 정책 문서를 고른다Creating file system policies 절차에 따라 JSON 형식의 정책 문서를 파일 시스템에 붙인다. 이 과정은 AWS SDK 나 Amazon EFS API 로도 코드에서 대신할 수 있다.
  2. 허용할 요청을 적는다정책 안에는 어느 주체가 어떤 파일 경로에 무슨 동작을 하는지를 적는다. cross-account access를 허용하려면 그 계정의 ARN 을 주체로 지정한다.

액세스 포인트는 파일 시스템의 루트 경로 아래에 그 쓰기 권한과 POSIX 사용자 정보가 고정된 별칭 지점을 만들어, 클라이언트가 붙을 경로를 정해 주는 단위다.

먼저 알아야 할 것 02-01

#1문제 상황

액세스 포인트는 파일 시스템의 루트 디렉터리 아래에 가상의 입구를 하나씩 만든다. 클라이언트는 그 입구로만 붙이고 그 안에서만 파일을 읽고 쓴다.

#2핵심 질문

각 클라이언트가 붙을 경로와 그 안의 권한을 어떻게 정할까?

#3동작 예시

Lambda 함수가 이미지 파일만 읽도록 하고 싶어 한다. 해당 함수용 액세스 포인트를 만들고 root directory를 images 폴더로 지정한 뒤, 함수에서 그 access point ID를 넘겨 파일을 연다.

함수는 images 폴더 밖에 있는 파일을 볼 수 없고, POSIX user로 지정한 신원으로만 파일을 다룬다.

#4동작 과정

  1. 액세스 포인트를 연다콘솔의 Access points 창에서 Create access point를 눌러 만든다. 파일 시스템 이름이나 ID 를 먼저 골라 대상을 정한다.
  2. root directory를 정한다파일 시스템 안에서 이 액세스 포인트가 나타날 경로를 정한다. 클라이언트는 이 경로를 루트로 본다.
  3. POSIX user를 붙인다그 경로에서 파일을 다룰 사용자·그룹 ID 와 권한 모드를 정한다. 이 신원은 파일 시스템 밖의 IAM 신원과는 따로 움직인다.
  4. 확인해 볼 것액세스 포인트 목록에서 만든 항목의 access point ID 와 root directory 경로가 보이는지 확인한다.

태그 붙이고 지우기

파일 시스템에 이름·용도 같은 태그를 붙여 비용과 관리를 그룹별로 정리하고, 쓰지 않는 파일 시스템은 삭제 명령으로 없앤다.

먼저 알아야 할 것 02-01

#1문제 상황

파일 시스템이 여러 개 쌓이면 어느 것이 무엇인지 목록만으로는 알기 어렵다. 비용과 사용처도 정리되지 않는다.

태그는 AWS 자원에 붙이는 이름표다. Tagging resources 를 쓰면 tag key로 파일 시스템을 묶어 보고, 쓰지 않는 것은 삭제 명령으로 지운다.

#2핵심 질문

이 파일 시스템을 어떻게 구분하고 쓸데없는 것은 어떻게 없애는가?

#3동작 예시

환경이 여러 개인 팀에서 EFS 콘솔을 연다. 각 파일 시스템에 environment 태그 값을 붙여 두고, Using tags 화면에서 prod 값이 붙은 파일 시스템만 골라낸다.

다시 쓰지 않는 파일 시스템을 골라 삭제 명령을 내리면 목록에서 사라진다.

#4동작 과정

  1. tag key와 값을 정한다Tagging resources 규칙에 따라 자원 종류마다 일관된 tag key를 정한다. key는 필수이고 값은 없어도 된다.
  2. 태그를 붙이고 걸러 본다파일 시스템마다 용도·소유자·환경 값을 붙인다. 같은 key를 계정에 통일해 두면 콘솔에서 태그로 검색해 필요한 파일 시스템만 꺼낼 수 있다.
  3. 지우려는 파일 시스템을 삭제한다삭제 명령을 내리면 파일 시스템이 DELETING 상태로 바뀌고 없어진다. 되돌릴 수 없다.
  4. 확인해 볼 것파일 시스템 상세 화면의 태그 목록에 붙인 tag key와 값이 보이는지 확인한다.

파일 시스템 상태 읽기

파일 시스템 상태 값은 저장된 데이터가 손상되지 않았는지, 삭제나 성능 모드에 전환 중인지 같은 상황 정보를 나타내며, 상태에 따라 사용할 수 없는 시점이 생긴다.

먼저 알아야 할 것 02-01

#1문제 상황

파일 시스템에 붙으려 했는데 안 되는 이유를 알기 어렵다. 저장된 데이터가 안전한지, 지금 어떤 처리가 돌고 있는지도 파일마다 다를 수 있다.

파일 시스템은 언제나 하나의 상태 값을 갖는다. 그 값을 읽으면 지금 이 파일 시스템이 쓰일 수 있는지 알 수 있다.

#2핵심 질문

이 파일 시스템은 지금 어떤 상태인가?

#3동작 예시

개발용 파일 시스템 하나가 갑자기 붙지 않는다. EFS 콘솔의 파일 시스템 목록에서 상태 값을 확인한다.

CREATING 이 남아 있으면 아직 만들던 중이고, AVAILABLE 이면 문제는 그쪽이 아니다. One Zone 파일 시스템이면 ERROR 가 뜰 수 있고, 이때는 백업에서 되돌린다.

#4동작 과정

  1. 상태 값을 읽는다Understanding file system status 표에서 현재 값의 뜻을 찾는다. AVAILABLE 는 정상·사용 가능, CREATING 은 만드는 중, DELETING 은 삭제 요청 처리 중, UPDATING 은 업데이트 요청 처리 중이다.
  2. DELETED 를 확인한다삭제 요청이 끝나면 파일 시스템이 사라진다.
  3. ERROR 를 확인한다One Zone 파일 시스템과 복제 구성 파일 시스템에서 실패해 복구할 수 없는 상태다. 저장된 데이터는 백업에서 복원한다.
  4. 확인해 볼 것콘솔 파일 시스템 목록의 상태 열에 이 파일 시스템의 상태 값이 어떻게 찍히는지 확인한다.

EFS 파일 시스템을 클라이언트 컴퓨터에 붙이기 전에 정해야 하는 사항들 — 붙이는 경로 방식, 클라이언트 쪽 준비물(efs-utils 등), 보안 그룹과 NFS 권한, 전송 암호화 여부를 미리 정해 두는 단계.

먼저 알아야 할 것 02-01

#1문제 상황

파일 시스템을 만들었다(→ 02-01). 그대로 EC2 인스턴스에 붙이려 하면 어느 경로로 붙일지, 클라이언트에 무엇을 준비할지 정하지 않아 실패한다.

Mounting considerations for Linux 는 붙이기 전에 정해야 할 선택지를 모아 둔 목록이다. 여기서 정한 값이 그대로 마운트 명령에 들어간다.

#2핵심 질문

인스턴스에 붙이기 전에 무엇을 정해 두어야 하는가?

#3동작 예시

개발팀이 웹 서버 인스턴스에 파일 시스템을 붙인다. 로컬 경로 /mnt/efs 로 정하고, 클라이언트 도구를 설치하고, 보안 그룹에서 NFS 포트를 연 뒤 마운트 명령을 실행한다.

그러면 인스턴스의 /mnt/efs 디렉터리에 파일이 나타난다.

#4동작 과정

  1. 이름과 경로를 정한다파일 시스템 고유 DNS name 을 붙일 대상과 대조하고 로컬 마운트 경로를 정한다(→ 07-01). 클라이언트 쪽 준비물(→ 04-01)을 설치하고 인스턴스 하나에 한 번만 붙이는 one mount per instance 원칙을 지킨다.
  2. 보안 그룹을 연다NFS 포트로의 인바운드 규칙을 지정한 클라이언트에만 연다(→ 06-01). 보안 그룹은 신원이 아니라 주소로 접근을 거른다.
  3. 성능 값을 정한다hard 는 요청이 시간 지나면 응답이 올 때까지 계속 다시 시도하게 만들어 데이터 무결성을 지킨다. soft 를 쓸 때는 timeo를 150(deciseconds) 이상으로 둔다. rsize 와 wsize 는 한 번의 네트워크 요청으로 주고받는 바이트 수이며 최대값인 1048576 을 쓰면 성능 손실을 피할 수 있다.
  4. 확인해 볼 것마운트한 인스턴스에서 지정한 로컬 경로의 파일 목록이 보이는지 확인한다.

EFS mount helper — 권장된 길

mount.efs 명령 하나로 마운트 시 자동으로 암호화·성능 최적화 옵션을 적용해 주는 EFS 전용 도구로, Amazon Linux 에 기본 설치되어 공식 권장 방식이다.

먼저 알아야 할 것 03-01

#1문제 상황

일반 mount 명령에 옵션을 손으로 나열하면 빠뜨리는 것이 생기고, 암호화 여부도 매번 따로 정해야 한다(→ 03-01).

EFS mount helper 는 마운트 전용 명령 mount.efs 를 따로 제공한다. 이 명령이 암호화와 성능 옵션을 자동으로 붙여 준다.

#2핵심 질문

옵션을 손으로 나열하지 않고 권장대로 마운트하려면 어떻게 하는가?

#3동작 예시

Amazon Linux 인스턴스에 로그인해 파일 시스템의 DNS 이름으로 mount 명령 대신 mount.efs 를 실행한다. 경로를 지정하면 안에서 암호화 연결과 권장 성능 설정이 함께 적용된다.

/etc/fstab 에 efs 항목과 _netdev 를 적어 두면 부팅할 때도 자동으로 붙는다.

#4동작 과정

  1. Prerequisites를 확인한다클라이언트에 amazon-efs-utils 가 있어야 한다(→ 04-02). EC2 Windows 인스턴스 마운트는 지원하지 않는다.
  2. mount.efs 로 붙인다명령이 마운트 시점에 tls 로 암호화 연결과 mount settings 의 성능 최적화를 자동으로 적용한다.
  3. 부팅 시 자동 마운트를 등록한다/etc/fstab에 파일 시스템과 경로를 적고 _netdev 옵션을 넣는다. 이 옵션이 없으면 인스턴스가 멈출 수 있다.
  4. 확인해 볼 것마운트 명령을 실행한 뒤 경로에 파일이 보이는지 확인한다.

NFS 클라이언트로 직접 붙이기

일반 리눅스 명령인 mount 명령과 nfs4 유형으로 EFS 의 DNS 이름과 2049 포트를 지정해 직접 붙이는 방식으로, 도구를 따로 설치하지 않고 싶을 때 쓴다.

먼저 알아야 할 것 03-01

#1문제 상황

마운트 헬퍼를 쓰지 않는 환경이라면 EFS 전용 패키지 없이 붙여야 한다(→ 03-02). 이럴 때 쓰는 방법이 NFS 클라이언트로 직접 붙이기다. 운영체제에 이미 들어 있는 NFS 클라이언트를 이용해 mount 명령에 파일 시스템의 DNS 이름과 2049 포트를 직접 적는다. 전송 중 암호화가 필요하면 TLS 로 붙여야 하며, 그 경우에는 EFS 클라이언트를 쓰는 편이 낫다.

#2핵심 질문

추가 패키지 없이 EFS 에 마운트하려면 어떻게 명령을 적어야 하는가?

#3동작 예시

  3. 확인해 볼 것붙은 디렉터리로 이동해 파일 목록을 보고 루트가 비어 있지 않은지 확인한다.

  3. 확인해 볼 것마운트 후 EFS 콘솔에서 그 파일 시스템의 마운트 타깃이 한 곳에만 있는지 확인한다.

4. 클라이언트를 준비한다04-03

botocore 와 stunnel 올리기

efs-utils 가 파일ystems 요청을 보낼 때 쓰는 AWS SDK 라이브러리 botocore 와, 그 요청을 암호 터널로 감싸 AWS 로 안전하게 전달하는 stunnel 을 클라이언트 컴퓨터에 함께 설치해 EFS 파일 시스템에 붙일 수 있어야 합니다.

먼저 알아야 할 것 04-02

#1문제 상황

efs-utils만 설치된 컴퓨터는 마운트 자체는 되지만(→ 04-02), 요청이 실패했는지 성공했는지 알 수 없다. EFS 파일 시스템에 접근하려면 efs-utils가 파일 시스템 요청을 보낼 수 있어야 하는데, 이 일은 두 가지 부품이 맡는다.

botocore는 efs-utils가 AWS로 요청을 보낼 때 쓰는 AWS SDK 라이브러리다. stunnel은 그 요청을 암호 터널로 감싸서 AWS에 안전하게 전달하는 프로그램이다. 이 둘을 함께 올려야 마운트 성공·실패를 CloudWatch Logs로도 볼 수 있다.

#2핵심 질문

클라이언트 컴퓨터에 요청용 라이브러리와 암호 터널을 어떻게 올리는가?

#3동작 예시

새로 만든 EC2 인스턴스에 SSH로 접속해 efs-utils를 설치한 뒤, botocore를 설치하고 버전을 올린다. 이어서 stunnel을 설치하고 설정까지 마친다. 그러면 마운트할 때 요청이 제대로 전달된다.

#4동작 과정

  1. botocore를 설치하고 올린다AWS 공식 amazon-efs-utils 저장소의 안내대로 efs-utils가 요구하는 버전의 botocore를 설치한 뒤 최신으로 올린다. 라이브러리가 있어야 파일 시스템 요청을 보낼 수 있다.
  2. stunnel을 설치하고 설정한다stunnel은 요청을 감싸는 암호 터널이며, 설치 중 문제 있으면 해결 절차를 따라 처리한다. Resolving issues with installing stunnel이 그 절차다.

FIPS 모드는 미국 연방 표준의 암호화 규격을 따르는 모드로, 이 모드를 켜면 efs-utils 가 파일 데이터를 주고받을 때 FIPS 검증에 통과한 암호 알고리즘만 사용해 요구사항을 충족합니다.

FIPS 모드는 그렇게 하는 설정이다. federal information processing standards는 미국 연방 표준의 암호화 규격이다. 이 모드를 켜면 efs-utils가 파일 데이터를 주고받을 때 FIPS 검증에 통과한 알고리즘만 쓴다.

#2핵심 질문

#3동작 예시

EC2 인스턴스에 SSH로 로그인해 /etc/amazon/efs/efs-utils.conf 파일을 연다. 그 안의 fips_mode_enabled 값을 false에서 true로 바꾸고 저장한다. 이후 마운트를 하면 FIPS 검증된 알고리즘으로 통신한다.

#4동작 과정

  1. 설정 파일을 연다SSH로 인스턴스에 로그인해 /etc/amazon/efs/efs-utils.conf를 편집기로 연다. Enabling FIPS mode가 이 설정 절차다.
  2. 값을 켠다fips_mode_enabled = false를 fips_mode_enabled = true로 바꾸고 저장한다. 단, FIPS 모드는 설치된 OpenSSL이 FIPS 지원으로 빌드되어 있어야 한다.
  3. 연결 경로를 정한다FIPS에 맞는 서비스 주소가 필요하면 FIPS endpoints로 지정한다. 이 주소들은 FIPS 모드를 켠 클라이언트가 연결하는 전용 끝점이다.
  4. 확인해 볼 것설정 파일을 다시 열어 fips_mode_enabled 값이 true로 저장되어 있는지 확인한다.

#1문제 상황

그래서 액세스 포인트에 신원 강제 기능이 있다. 이 기능을 켜면 EFS가 클라이언트가 보낸 사용자·그룹 ID를 무시하고 액세스 포인트에 정해 둔 신원을 모든 파일 작업에 대신 쓴다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 액세스 포인트를 준비한다Working with access points 절차를 따라 만들고, 그 경로로 클라이언트를 붙인다. uid와 gid는 POSIX 사용자·그룹의 숫자 ID다.
  2. 신원을 강제한다Enforcing a user identity를 켠다. EFS가 클라이언트의 NFS 사용자·그룹 ID를 무시하고 액세스 포인트 신원으로 모든 파일 작업을 처리한다.
  3. 루트를 강제한다Enforcing a root directory로 클라이언트가 지정된 루트 밖으로 못 나가게 한다. 신원 강제는 IAM의 ClientRootAccess 권한이 있어야 쓸 수 있다.
  4. 확인해 볼 것클라이언트가 마운트한 안에서 새로 만든 파일의 소유자가 액세스 포인트의 사용자 ID로 되어 있는지 확인한다.

신원은 정해졌는데 그 사람이 실제로 어느 파일을 만질 수 있나?

#3동작 예시

직원이 개인 디렉터리 /alice 에 로그인해 자기 파일을 만든다. 같은 직원이 다른 직원의 디렉터리에 들어가 같은 명령을 내면 거부된다. IAM 이 두 사람에게 같은 권한을 줬더라도 NFS 계층이 다른 결과로 만든다.

#4동작 과정

  1. 사용자 ID 를 전달한다NFSv4.1 클라이언트는 자신이 신뢰할 수 있는 사용자·그룹 ID 를 요청에 실어 보낸다. NFS-level users, groups, and permissions 계층은 기본적으로 이 주장(클라이언트가 밝힌 신원)을 그대로 믿는다.
  2. 비트 권한을 비교한다File and directory permissions 규칙으로 소유자와 그룹, 그리고 그 밖의 사용자에게 허용된 비트를 확인한다. 이 결과로 읽기·쓰기·실행과 삭제가 갈린다.
  3. root 를 막을 수 있다root_squash 를 켜면 클라이언트가 root 라고 주장해도 낮은 권한 사용자로 낮춰 처리한다. EFS access points 를 쓰면 클라이언트가 보낸 신원 정보를 덮어쓸 수도 있다(→ 02-03).
  4. 확인해 볼 것파일과 디렉터리 화면에서 소유자와 권한 표시가 어떻게 나왔는지 확인한다.

5. 접근 권한을 세 겹으로 정한다05-06

공개 접근 막기

모든 클라이언트가 인터넷에서 파일 시스템으로 붙지 못하게 공개 접근 차단 설정을 켜고, 사설 서브넷과 마운트 타깃 보안 그룹으로 네트워크 경로 자체를 막는 방법.

먼저 알아야 할 것 05-02

#1문제 상황

새로 만든 EFS 파일 시스템은 기본적으로 공개 접근을 허용하지 않는다. 그런데 파일 시스템 정책(→ 02-02)을 고치면 public access, 즉 누구나 붙을 수 있는 상태가 생길 수 있다.

Blocking public access to file systems 는 파일 시스템에 직접 붙은 리소스 정책으로 공개 접근이 부여되지 못하게 막는 설정이다. Network isolation 과 함께 네트워크 경로 자체도 닫는다.

#2핵심 질문

파일 시스템 정책이 잘못돼서 외부에서 붙지 못하게 어떻게 막나?

#3동작 예시

운영자가 파일 시스템 정책에 모든 계정에 읽기와 쓰기를 허용하는 규칙을 실수로 넣었다. 파일 시스템 설정에서 Block Public Access 를 켜 두면 그 규칙은 이제 아무 권한도 주지 못한다. 정책 본문은 그대로 남지만 잘못 설정된 리소스 정책으로 실행되지 않는다.

#4동작 과정

  1. 막기를 켠다파일 시스템 단위에서 Block Public Access 를 켠다. 공개 접근 block 상태로 바뀌어 파일 시스템 정책의 공개 규칙이 적용되지 않는다.
  2. 붙은 정책들을 훑는다파일 시스템에 붙은 리소스 정책과, 관련된 AWS 주체(예: IAM 역할)의 신원 기반 정책, AWS KMS 키 정책이 공개 접근을 주지 않는지 확인한다.
  3. 네트워크를 닫는다Network isolation 을 위해 파일 시스템을 사설 서브넷에 두고 마운트 타깃 보안 그룹(→ 06-01)에서 허용된 클라이언트만 통과시킨다.
  4. 확인해 볼 것파일 시스템 설정 화면에 공개 접근 차단이 켜져 있는지 확인한다.

VPC 보안 그룹으로 막기

EC2 인스턴스에 붙은 가상 방화벽인 보안 그룹에 EFS 마운트 대상( NFS 포트 2049)으로의 인바운드 규칙을 추가해, 지정한 클라이언트만 파일 시스템에 붙을 수 있게 만드는 것.

먼저 알아야 할 것 03-02

#1문제 상황

파일 시스템 하나를 여러 컴퓨터가 함께 쓰려면 클라이언트가 마운트 타깃에 닿아야 한다(→ 01-02). 문제는 어떤 컴퓨터까지 닿게 할지 정하는 수단이 없다는 것이다.

Using VPC security groups 를 쓰면 마운트 타깃에 보안 그룹을 붙인다. 보안 그룹은 클라이언트 쪽 인스턴스의 가상 방화벽이며, inbound NFS port 규칙으로 어떤 서버에서만 inbound 인바운드 접근이 닿는지 정한다.

#2핵심 질문

마운트 타깃에 어떤 클라이언트만 NFS 요청을 보낼 수 있게 할까?

#3동작 예시

앱 서버 인스턴스 세 대만 파일을 공유해야 한다. 마운트 타깃의 보안 그룹에 그 인스턴스의 보안 그룹을 등록하고 NFS 포트로 인바운드를 연다. 등록되지 않은 컴퓨터에서 mount 명령을 내면 연결이 막힌다.

#4동작 과정

  1. 마운트 타깃을 고른다EFS 콘솔에서 파일 시스템을 열고 Network 항목에서 마운트 타깃 목록을 본다(→ 07-01).
  2. 보안 그룹을 붙인다Manage 로 들어가 마운트 타깃의 mount target security groups 에 클라이언트가 쓰는 보안 그룹을 추가하거나 뺀다. 콘솔·CLI·AWS SDK 어느 쪽으로도 고칠 수 있다.
  3. 방향을 모두 연다인바운드는 NFS 포트, 아웃바운드는 응답을 되돌리기 위한 outbound 규칙을 함께 허용한다. 빠진 쪽이 있으면 마운트도 파일 요청도 통과하지 못한다.
  4. 확인해 볼 것마운트 타깃의 보안 그룹 목록에 클라이언트 보안 그룹이 붙어 있는지 확인한다.

VPC 엔드포인트로 사설 경로 만들기

VPC 안에서만 열리는 프라이빗 IP 를 가진 EFS 엔드포인트를 만들어, 클라이언트가 인터넷을 거치지 않고 AWS 내부망으로 파일 시스템에 연결되게 하는 것.

먼저 알아야 할 것 06-01

→ 06-01 참조

#1문제 상황

클라이언트가 EFS API 로 요청을 보내려면 보통 인터넷 게이트웨이나 NAT 를 거쳐야 한다. 사설망에 있는 시스템에서는 그 경로가 없거나, 열어 두는 것 자체가 부담이 된다.

Working with VPC endpoints 는 VPC 안에서만 열리는 프라이빗 IP 주소를 만들어 그 요청을 받는다. 만들어지면 서브넷 안에 탄성 네트워크 인터페이스가 생기고, 클라이언트는 인터넷을 거치지 않고 내부망으로 EFS API 요청을 보낸다.

#2핵심 질문

인터넷 게이트웨이 없이 사설망에서 EFS API 에 닿게 어떻게 하나?

#3동작 예시

사설 서브넷의 서버가 파일을 쓰려고 DNS 이름을 찾는다. interface endpoint 로 잡힌 주소가 VPC 안에서만 열려 있고, 요청은 그대로 EFS 로 전달된다. NAT 비용도 나가지 않는다.

#4동작 과정

  1. 엔드포인트를 만든다VPC 콘솔·API·CLI 중 어느 쪽으로든 Amazon EFS 용 엔드포인트를 생성한다. AWS PrivateLink 기술로, 이 기능이 사설 IP 주소만으로 AWS 서비스끼리 통신하게 해 준다.
  2. 네트워크 인터페이스가 붙는다선택한 서브넷 안에 프라이빗 IP 를 가진 탄성 네트워크 인터페이스가 생기고 그 주소가 EFS API 요청을 받는다.
  3. 바깥 경로를 없앤다interface endpoint 로 API 접근을 처리하고, 파일 데이터는 gateway endpoint 로 묶어 VPC 내부망에서만 오게 한다.
  4. 확인해 볼 것VPC 콘솔의 엔드포인트 목록에 EFS 용 엔드포인트와 상태가 보이는지 확인한다.

리전 간 통신 프라이버시

서로 다른 리전의 리소스가 EFS 파일 시스템을 VPC 피어링이나 Transit Gateway 같은 사설 연결로 통해 통신하고, 해당 리전의 리소스가 파일 시스템에 붙을 수 있게 허용하는 것.

먼저 알아야 할 것 06-01

#1문제 상황

리전이 다르면 네트워크가 끊어져 있다. 그러니 서로 다른 리전의 자원이 EFS 파일 시스템에 붙거나, 사설망의 클라이언트가 AWS 쪽으로 요청을 보내려면 연결을 직접 만들어야 한다.

Internetwork privacy 는 그 연결 위에서 리전이 다른 리소스도 파일 시스템에 닿게 한다. 전송 중 데이터는 in transit 상태로 보호되어야 하므로 TLS 가 쓰인다.

#2핵심 질문

리전이 다른 자원과 사설망 클라이언트가 파일 시스템에 닿게 어떻게 하나?

#3동작 예시

다른 리전의 분석 서버가 파일 시스템의 데이터를 읽는다. 두 리전은 VPC peering 으로 연결돼 있고 regional data 는 그 안에서만 오간다. 요청은 TLS 로 암호화되어 들어온다.

#4동작 과정

  1. 사설 연결을 잇는다사설망과 AWS 사이는 Site-to-Site VPN 연결 또는 Direct Connect 연결 두 가지 중 하나로 잇는다. 리전 간 리소스는 VPC peering 이나 Transit Gateway 로 연결한다.
  2. 암호 규격을 맞춘다클라이언트는 TLS 1.2 이상을 지원해야 하고, 권장 사양은 TLS 1.3 이상이다. PFS 를 지원하는 암호 스위트, 예로 DHE 와 ECDHE 도 쓸 수 있다.
  3. 요청에 서명한다액세스 키 ID 와 시크릿 액세스 키로 요청에 서명하거나, AWS STS 로 임시 자격 증명을 발급받아 쓴다.
  4. 확인해 볼 것VPC 콘솔에서 피어링 연결 또는 Transit Gateway 연결 상태가 활성인지 확인한다.

IAM 인증으로 붙이기

IAM 인증 옵션을 켜 두면, 클라이언트는 EFS API 로 받은 유효한 토큰을 IAM 정책의 조건으로 검사받아 권한이 있을 때만 파일 시스템에 접근하는 것.

먼저 알아야 할 것 05-01

#1문제 상황

NFS 로 붙으면 클라이언트가 보낸 신원을 그대로 믿는다(→ 05-05). 그래서 정책과 상관없이 권한이 넓어질 수 있다.

Mounting with IAM authorization 은 그 신뢰를 IAM 으로 넘긴다. 파일 시스템에서 IAM 인증 옵션을 켜 두면, 클라이언트가 EFS API 로 받은 토큰을 매 요청마다 IAM 정책이 검사하고 통과한 요청만 처리한다.

#2핵심 질문

클라이언트 신원을 IAM 이 직접 검사하게 어떻게 하나?

#3동작 예시

인스턴스 프로필이 붙은 EC2 인스턴스에서 마운트한다. efs-utils 가 EFS API 로 토큰을 받아 매 요청에 실어 보내고, IAM 정책이 그 토큰의 조건을 검사해 허용 여부를 정한다.

#4동작 과정

  1. 마운트 지점을 만든다붙일 디렉터리를 하나 만들어 둔다. 예로 sudo mkdir efs 명령으로 마운트 지점 디렉터리를 만든다.
  2. 인스턴스 프로필로 붙인다프로필이 있는 EC2 인스턴스에서는 tls 와 iam 마운트 옵션을 함께 준다. efs-utils 가 IAM authentication 을 처리한다.
  3. 자동 마운트를 등록한다재부팅마다 복원되도록 /etc/fstab 에 파일 시스템 ID, 마운트 지점, 그리고 efs 와 _netdev,tls,iam 옵션을 한 줄로 적어 둔다. 별도 프로필 이름으로 붙일 때도 같은 방식으로 지정한다.
  4. 확인해 볼 것마운트 지점이 마운트 목록에 잡혀 있고 읽기·쓰기가 되는지 확인한다.

#1문제 상황

마운트 troubleshooting은 이 실패 뒤에 원인을 하나씩 지워 가는 절차다. 어느 지점에서 막혔는지 알아내면 바로 고친다.

#2핵심 질문

mount 명령이 실패했을 때 어느 지점이 원인일까?

#3동작 예시

인스턴스에서 mount.efs 명령을 치면 wrong fs type가 난다. 문서에서 적은 원인별 확인 목록을 따라 DNS 이름이 풀리는지 본다.

그다음 efs-utils 설치 여부와 보안 그룹의 2049 포트 인바운드 규칙을 확인해 범위를 좁힌다.

#4동작 과정

  1. 증상을 분류한다공식 문서는 오류 문구별로 원인을 나눠 적어 둔다. Access denied by server는 권한 문제이고 nfs not responding은 경로가 닫힌 경우로 좁힌다.
  2. 경로를 확인한다DNS 이름이 VPC 안에서 푸는지 보고, 클라이언트가 마운트 타깃의 서브넷에 속하는지 본다. 보안 그룹 인바운드 규칙으로 EFS NFS 포트 2049가 열려 있는지도 함께 본다(→ 06-01).
  3. 도구를 확인한다efs-utils가 설치됐는지 보고 mount helper log를 열어 실제 오류를 읽는다. 서버에 도달한 뒤 tunnel이 실패하면 stunnel errors가 남는다.
  4. 확인해 볼 것mount helper log를 열어 오류가 DNS 조회 단계인지, NFS 요청 단계인지 적힌 줄이 보이는지 확인한다.

#1문제 상황

#2핵심 질문

#3동작 예시

리전 파일 시스템의 콘솔에서 가용 영역 세 곳을 고르고 각 영역의 서브넷을 하나씩 지정해 마운트 타깃을 만든다.

#4동작 과정

  1. 만든다Creating mount targets로 파일 시스템에 VPC와 서브넷을 지정한다. 한 파일 시스템은 한 번에 한 VPC에서만 마운트 타깃을 가진다.
  2. 한계를 정한다같은 가용 영역에 서브넷이 여러 개여도 그중 하나에만 마운트 타깃을 만든다. 대신 그 영역의 EC2 인스턴스는 모두 그 하나로 붙는다.
  3. 범위를 정한다접근할 가용 영역마다 최소 하나씩 만든다. 다른 VPC로 옮기려면 Deleting mount targets로 지운 뒤 새로 만들고, Changing mount target VPC로 바꾼다.
  4. 확인해 볼 것파일 시스템의 마운트 타깃 목록에 영역마다 하나씩 IP 주소와 상태가 초록색으로 보이는지 확인한다.

먼저 알아야 할 것 07-01

#1문제 상황

파일 시스템은 처리할 수 있는 양의 한계가 정해져 있고, 그 안에서 얼마나 고르게 밀어낼지가 성능을 가른다(→ 07-01).

Managing throughput는 그 한계 안에서 throughput mode를 정하고 CloudWatch 지표로 실제 사용량을 지켜보는 일이다.

#2핵심 질문

워크로드에 맞는 처리량 모드를 무엇으로 정하고 어떻게 지킬까?

#3동작 예시

사용 패턴이 정해지지 않은 서비스는 기본값인 elastic throughput로 둔다. 밤 사이 접속이 몰리는 배치라면 다른 모드로 바꿔 본다.

CloudWatch에서 MeteredIOBytes 지표를 주시해 실제 얼마나 나갔는지 살핀다.

#4동작 과정

  1. 모드를 고른다throughput mode를 고른다. elastic throughput는 처리량이 워크로드에 맞춰 자동으로 오르내린다. Proviced throughput은 크기와 무관하게 원하는 처리량을 미리 지정하는 선택지다.
  2. 규칙을 정한다burst throughput로 짧은 시간의 한도와 그 안에서 처리할 수 있는 시간을 따로 정한다. 평상시에 낮게 두고 필요할 때만 올리는 데 쓴다.
  3. 지켜본다CloudWatch의 MeteredIOBytes로 실제 사용량을 보고 임계치를 넘으면 알람을 건다.
  4. 확인해 볼 것파일 시스템 설정 화면에 선택된 throughput mode와 그 상태가 표시되는지 확인한다.

먼저 알아야 할 것 07-01

#1문제 상황

필요한 처리량이 어느 수준인지는 워크로드를 돌려 보기 전에는 알 수 없다. 그래서 미리 정해진 기준값이 필요하다(→ 07-01).

성능 규격은 파일 시스템 타입과 성능 모드가 정해졌을 때 나올 수 있는 처리량·IOPS·지연 시간 수치를 알려 준다.

#2핵심 질문

이 구성의 파일 시스템이 어느 정도까지 빨라질 수 있는가?

#3동작 예시

요청 하나가 크고 지연에 민감하지 않은 서비스라면 Regional 파일 시스템과 General Purpose 모드로 충분하다고 판단한다.

반대로 작은 요청이 아주 많이 오는 서비스라면 performance specifications를 보고 모드를 다시 고른다.

#4동작 과정

  1. 축을 정한다성능은 latency, throughput, Input/Output operations per second (IOPS) 세 축으로 잰다. performance and scalability 기준으로 이 셋을 함께 본다.
  2. 구성을 고른다영향을 주는 것은 파일 시스템 타입(Regional 또는 One Zone), 성능 모드(General Purpose 또는 Max I/O), throughput per file system다. Max I/O는 동작당 지연이 더 크다.
  3. 맞춘다빠른 처리가 필요하면 General Purpose로 두고 지연이 허용될 때만 Max I/O를 고른다. IOPS 를 많이 뽑으려면 elastic throughput를 쓴다.
  4. 확인해 볼 것파일 시스템 콘솔의 성능 모드 항목에 General Purpose 또는 Max I/O 중 무엇으로 설정되어 있는지 보인다.

  1. 증상을 고른다Poor performance when opening many files in parallel, Application writing large amounts of data hangs 같은 항목으로 증상을 먼저 정한다. 각 항목이 의심 원인을 따로 적어 둔다.
  2. 기저를 확인한다Troubleshooting AMI and kernel issues로 최근 Linux 커널을 쓰는지 본다. 배포판마다 amazon Linux 2 kernel 4.3, RHEL 7.3, Ubuntu 16.04, SLES 12 같은 기준이 있다.
  3. 설정을 걷어 낸다custom NFS settings나 여러 파일을 병렬로 여는 방식이 지연을 만드는지 확인해 기본 설정으로 되돌려 결과를 비교한다.
  4. 확인해 볼 것인스턴스의 파일 시스템 요청에서 latency 값이 느려진 시점과 평소 값이 어떻게 다른지 나타나는지 확인한다.

스토리지 lifecycle — 안 쓰는 것을 싸게

스토리지 lifecycle 은 파일을 마지막으로 읽은 시각을 파일 시스템이 기록해 두었다가 설정한 기간이 지나면 값이 싼 저장 계층(IA 계층)으로 자동 옮겨 두는 기능이다.

먼저 알아야 할 것 07-02

#1문제 상황

모든 파일을 기본 저장 클래스인 Standard 에 두면 매일 읽히지 않는 로그와 백업 파일도 같은 단가로 저장된다(→ 01-03). 스토리지 lifecycle 은 저장 클래스 사이 자동 전환을 시키는 기능이다. 안 쓰는 파일을 싼 계층으로 내려 비용을 낮춘다.

#2핵심 질문

읽히지 않는 파일을 자동으로 싼 저장 클래스로 옮겨 비용을 아끼려면?

#3동작 예시

팀이 로그 파일을 한 달에 한 번만 확인한다. 파일 시스템에 lifecycle policy를 두고 30일이 지나면 EFS가 파일을 IA storage class로 옮긴다. 콘솔에서 해당 파일 시스템의 lifecycle 설 보면 전환 기준일이 보인다.

#4동작 과정

  1. 정책을 정한다Configuring lifecycle policies에서 파일별로 언제 옮길지 정한다. 이 설정이 Managing storage lifecycle의 기준이 된다.
  2. 접근 시각을 잰다transition after access는 Standard에 있던 파일이 마지막으로 읽힌 시각을 EFS 내부 타이머가 기록하는 기준이다. 파일을 읽을 때마다 이 시각이 초기화된다.
  3. 자동으로 옮긴다설정한 기간이 지나면 파일이 IA storage class로 넘어간다. 이 정책은 파일 시스템 전체에 적용된다.
  4. 확인해 볼 것파일 시스템의 lifecycle 설정 화면에 전환 기간이 저장되어 있는지 본다.

데이터 보호와 암호화

EFS 는 파일을 디스크에 저장할 때 암호화로 보호하고, 클라이언트가 HTTPS 를 통해서만 그 암호문을 내려받게 만들어 저장 매체와 네트워크 어느 쪽에서도 원문이 노출되지 않게 하는 안전 장치다.

먼저 알아야 할 것 05-01

#1문제 상황

클라우드 계정의 안전은 AWS 가 기반 구조를 지키는 것과 내가 자료와 권한 구성을 관리하는 것으로 나뉜다. Data protection 는 그중 데이터 자체를 지키는 축이다.

EFS 는 Data encryption 을 디스크에 저장할 때 적용해 at rest 상태의 파일을 보호한다. 클라이언트가 내려받을 때도 in transit 구간은 암호화로 막는다.

#2핵심 질문

저장된 파일과 주고받는 파일이 둘 다 노출되지 않게 하려면?

#3동작 예시

개발자가 EC2 에서 EFS 파일을 읽는다. 서버 디스크를 따로 떼어 내도 파일 내용은 읽히지 않는다. 켜 둔 암호화는 파일 시스템마다 따로 설정하지 않아도 기본으로 동작한다.

#4동작 과정

  1. 저장할 때 Encrypt파일을 디스크에 넣는 순간 암호화해 at rest 로 둔다.
  2. 보낼 때 TLS클라이언트와 주고받는 구간을 TLS 로 막아 in transit 중 노출을 없앤다.
  3. 신원을 정리한다문서는 계정 보호를 위해 AWS IAM Identity Center 와 IAM 로 사용자별 최소 권한을 주고 multi-factor authentication(MFA)을 켤 것을 권한다.
  4. 확인해 볼 것파일 시스템의 암호화 관련 항목을 콘솔에서 열어 상태가 어떻게 표시되는지 본다.

AWS Backup 사용

AWS Backup 은 AWS Backup 규칙(무엇을·얼마나 자주·얼마나 오래 보관할지 정한 설정)을 만들어 EFS 파일 시스템의 백업과 복원, 그리고 다른 AWS 서비스의 백업까지 한곳에서 관리하게 해 주는 서비스다.

먼저 알아야 할 것 08-01

#1문제 상황

파일 하나를 날렸을 때 지난 시점으로 되돌릴 방법이 없다. 사용자가 직접 스크립트로 복사본을 떠 두면 백업 누락도 생긴다.

AWS Backup 은 EFS 를 포함한 여러 리소스의 백업을 함께 관리한다. 복원 지점도 함께 정해 둘 수 있다.

#2핵심 질문

EFS 파일을 정기적으로 백업하고 필요할 때 되돌리려면?

#3동작 예시

운영자가 실수로 디렉터리 하나를 지웠다. AWS Backup 콘솔에서 지난 주의 복원 지점을 골라 새 파일 시스템이나 기존 파일 시스템으로 되돌린다. 콘솔에서 만든 파일 시스템은 자동으로 백업 대상이 된다.

#4동작 과정

  1. 규칙을 만든다AWS Backup 의 backup plan 에 무엇을·얼마나 자주·얼마나 오래 보관할지 정한다.
  2. 백업을 돈다plan 에 따라 파일 시스템이 자동으로 백업된다. 콘솔에서 만든 파일 시스템은 기본으로 켜져 있고, CLI 나 API 로 만들면 One Zone 파일 시스템만 기본 켜짐이 된다.
  3. 되돌린다restore point 를 골라 새 파일 시스템 또는 기존 파일 시스템으로 복원한다. 전체 복원과 항목 단위 복원을 고를 수 있다.
  4. 확인해 볼 것AWS Backup 콘솔의 복원 지점 목록에 EFS 항목이 시간순으로 보이는지 본다.

자동 백업 관리

자동 백업 관리는 EFS 가 사용자가 건드리지 않아도 스스로 정해진 주기로 파일 시스템의 데이터를 백업해 두는 기능으로, 규칙을 확인 수정하거나 백업을 되돌리는 방법을 아는 영역이다.

먼저 알아야 할 것 08-02

#1문제 상황

백업을 켜 두면 잊어버린다. 그런데 언제 마지막으로 백업됐는지, 언제 지워지는지는 아무도 모른다(→ 08-02).

Managing automatic backups 는 이 과정을 콘솔에서 켜고 끄고 확인하는 일이다. 콘솔이나 CLI 로 파일 시스템을 만든 뒤에도 바꿀 수 있다.

#2핵심 질문

EFS 자동 백업을 켜고 상태와 보관을 어떻게 관리하지?

#3동작 예시

운영자가 EFS 콘솔의 파일 시스템 상세 화면에서 편집을 눌러 자동 백업을 끈다. 그러면 EFS 는 파일 시스템에 aws:elasticfilesystem:default-backup 이라는 system tag 값을 붙인다. AWS Backup 콘솔에서 백업 목록을 열어 지난 백업을 본다.

#4동작 과정

  1. 켜고 끈다파일 시스템 상세 화면의 편집에서 자동 백업을 on·off 로 바꾼다. 콘솔·CLI·EFS API 로도 가능하다.
  2. 기본 규칙을 본다AWS Backup 콘솔에서 기본 EFS backup plan 의 frequency 와 retention 을 확인하고 고친다.
  3. 결과를 확인한다automatic backups 목록에서 언제 백업됐는지 보고, 백업 본문은 backup vault 에 보관되며 lifecycle 설정으로 정리된다.
  4. 확인해 볼 것파일 시스템의 태그 목록에 default-backup 키가 붙어 있는지 확인한다.

파일 시스템 복제

파일 시스템 복제는 한 리전의 EFS 데이터를 실시간으로 다른 리전(또는 같은 리전의 다른 파일 시스템)에 계속 복사해 두는 기능으로, 원본이 없어져도 복제본으로 업무를 이어 갈 수 있게 한다.

먼저 알아야 할 것 08-02

#1문제 상황

백업은 특정 시점만 남는다(→ 08-02).전용 시설이 통째로 사라지는 상황에서는 그 시점의 사본만으로는 부족하다.

Replicating file systems 는 원본(source file system)의 내용을 destination file system 에 실시간으로 넘긴다. 복제 설정(replication configuration)을 만들면 Amazon EFS 가 두 파일 시스템을 알아서 맞춘다.

#2핵심 질문

다른 리전에 살아 있는 복제본을 두려면?

#3동작 예시

운영자가 원본 파일 시스템에서 Configuring replication to new file system 으로 복제 설정을 만든다. 그러면 새로운 파일 시스템이 생기고 이후 원본에 쓴 내용이 계속 그쪽으로 넘어간다. 콘솔에서 Last sync time 을 보고 얼마나 최근까지 맞았는지 본다.

#4동작 과정

  1. 복제 설정을 만든다replication configuration 으로 source file system 과 destination file system 을 짚는다.
  2. 계속 맞춘다Amazon EFS 가 원본의 변경을 목적 파일 시스템에 자동으로 넘긴다.
  3. 시점을 읽는다변경은 시점 단위로 맞추지 않고 Last sync time 을 기준으로 넘겨진다. 이 시각이 마지막 동기화 시점을 알려 준다.
  4. 확인해 볼 것복제 설정 화면에서 Last sync time 이 최근 시각으로 갱신되는지 본다.

복제 상태와 복제본 쓰기

복제 상태 확인은 원본·복제본 쌍이 지금 정상적으로 함께 돌고 있는지 보고, 장애 시에 복제본을 쓰기 가능 상태로 승격해 원본 대신 쓰게 하는 절차를 다루는 영역이다.

먼저 알아야 할 것 08-04

#1문제 상황

원본 리전이 통째로 끊겼다면 복제본을 곧바로 업무에 써야 한다. 그런데 복제 설정이 살아 있는 동안 복제본은 읽기 전용이라 애플리케이션이 쓰기를 못 한다(→ 08-04).

failover 로 복제본을 원본 자리로 올리는 절차를 정해 두면 된다.

#2핵심 질문

원본이 죽었을 때 복제본을 언제쯤 쓰게 전환하지?

#3동작 예시

장애가 발생해 운영자가 복제 설정을 지운다. 복제본이 writeable 상태로 바뀌어 애플리케이션을 그대로 붙인다. 복구 뒤에는 복제본을 계속 주 파일 시스템으로 쓰거나 failback 로 원본을 다시 주역으로 돌린다.

#4동작 과정

  1. 상태를 본다Viewing replication details 로 원본·복제본 쌍이 정상적으로 붙어 있는지 확인한다.
  2. 설정을 지운다delete replication configurations 를 실행하면 복제본이 writeable 이 되어 write to the destination 이 가능하다.
  3. 되돌리기도 고른다failback 때 복제본에 쌓인 변경을 버릴지 원본에 복사해 남길지 고른다. 버리면 원본에 복제 설정을 다시 만들고, 남기면 그 변경을 원본으로 되돌린다.
  4. 확인해 볼 것복제 설치를 삭제한 뒤 복제본 상세에서 쓰기 가능 상태로 표시되는지 본다.

데이터를 옮기기

데이터 옮기기는 기존 서버나 다른 AWS 서비스에 있던 파일을 EFS 로 옮기거나 EFS 에서 꺼내는 것을 뜻하며, 대량 전송에는 AWS DataSync 나 AWS Transfer Family 같은 전용 도구를 쓴다.

먼저 알아야 할 것 08-01

#1문제 상황

서버가 직접 파일을 나르려면 네트워크 설정과 용량, 전송 스크립트를 손으로 맞춰야 하고 대량일수록 느리다. EFS 에서 빼낼 때도 같은 문제가 있다(→ 08-01).

데이터를 옮기기는 AWS 가 제공하는 전송 도구로 그 일을 대신하게 한다. 파일 하나씩 옮기지 않고 저장소 사이의 전송을 맡긴다.

#2핵심 질문

대량의 파일을 다른 저장소에서 EFS 로 옮기는 것은 어떻게 시작하는가?

#3동작 예시

옮길 파일이 들어 있는 S3 버킷을 만든 다음 그 버킷을 DataSync 작업의 원본으로 지정한다. 작업이 끝나면 파일이 EFS 파일 시스템 안의 지정한 디렉터리에 같은 계층 구조로 놓여 있다.

#4동작 과정

  1. 전송 작업을 만든다Transferring data, 즉 데이터를 옮기는 작업으로 원본 저장소와 EFS 파일 시스템을 짝지어 한 번 옮기거나 주기적으로 반복하게 한다. Using AWS DataSync 는 NFS·SMB 서버, S3 버킷, Snowball Edge, EFS, FSx 사이를 오갈 수 있고 다른 리전이나 다른 계정의 파일 시스템끼리도 옮긴다.
  2. 보조 경로로 보낸다파일을 S3 로 먼저 올렸다가 내려받는 방식도 쓴다. AWS Transfer Family 로는 클라이언트에 presigned URL, 즉 로그인 없이 정해진 시간에만 쓰도록 서명한 주소를 건네 줄 수 있다.
  3. 한 번 옮기고 반복하기첫 화면에 나타난 DataSync 작업의 상태와 옮겨진 파일 수를 확인한다. 정기 적재나 복제용으로 같은 작업을 되풀이할 수 있다.
  4. 확인해 볼 것DataSync 콘솔에서 방금 만든 작업의 상태가 성공으로 표시되고 대상 EFS 파일 시스템 안에 파일이 보이는지 확인한다.

#2핵심 질문

#3동작 예시

  3. 별도로 본다Viewing storage class size 는 클래스별 크기 합계를 따로 꺼내 보는 일이다. 콘솔의 파일 시스템 크기 수치와 청구되는 양이 어긋날 때 여기서 원인을 찾는다.
  4. 확인해 볼 것파일 시스템 콘솔의 크기 항목에서 Standard 와 IA 합계가 각각 어떻게 표시되는지 확인한다.

#2핵심 질문

EFS 파일 시스템이 지금 얼마나 바쁘고 느린지 수치로 어떻게 확인하는가?

#3동작 예시

CloudWatch 콘솔에서 그 파일 시스템의 지표를 고르면 저장 바이트 수와 요청 수가 시간대별로 그래프로 나온다. 1분 단위로 쌓인 값이라 어느 시간대에 부하가 몰렸는지 바로 보인다.

#4동작 과정

  1. 모으기Monitoring metrics with CloudWatch 는 클라이언트 요청·처리량·용량·지연 시간을 CloudWatch 지표로 남긴다. CloudWatch metrics 라고 부르는 이 값은 기본적으로 1분 주기로 자동으로 올라간다.
  2. 찾아 보기ActiveClientCount 는 파일 시스템에 붙어 있는 클라이언트 수를, MeteredIOBytes 는 계량된 입출력 바이트 수를 나타낸다. 지표는 15개월치 기록으로 조회할 수 있다.
  3. 그래프로 읽기EFS 콘솔도 같은 원본 데이터로 그래프를 그린다. 값은 바이트 단위로 올라오므로 단위를 감안해 본다.
  4. 확인해 볼 것CloudWatch 콘솔에서 해당 파일 시스템의 지표 목록에 요청 수와 지연 시간 항목이 시간대별 값으로 나타나는지 확인한다.

  4. 확인해 볼 것CloudWatch 콘솔의 대시보드에 계산식에서 나온 새 시계열 그래프가 추가되어 있는지 확인한다.

  2. 설정을 직접 고칠 때손으로 설치한 경우에는 /etc/amazon/efs/efs-utils.conf 를 직접 고쳐 로그 기능을 켠다.
  3. 호출을 남긴다Logging API calls with CloudTrail 은 누가 언제 EFS API 를 불렀는지 기록으로 남긴다. mount failures 와 같은 시간대 로그와 맞춰 보면 원인 지점을 좁힐 수 있다.
  4. 확인해 볼 것CloudWatch Logs 의 해당 로그 그룹에서 마운트 시도의 성공과 실패가 각각 어떤 항목으로 남아 있는지 확인한다.

EFS는 저장한 데이터량(GB-스텝), 프로비저닝한 처리량(스텝-스텝), 액세스 포인트 수에 따라 과금되며 그 내역은 AWS Billing 과 Cost Explorer 리포트에서 월별로 확인할 수 있다.

먼저 알아야 할 것 09-02

#1문제 상황

EFS 요금은 월 단위로 표시되지만 실제 과금은 시간 단위로 잘라 한 달 평균 사용량으로 계산된다(→ 09-02). 파일 시스템 만든 사람이 아니라 파일 시스템 소유 계정에 요금이 붙는다. 그래서 팀이 여러 파일 시스템을 함께 쓰면 어디서 비용이 나왔는지 헤매는 일이 생긴다.

Using billing and usage reports는 그런 상황을 숫자로 남기는 리포트 모음이다. AWS Billing reports는 사용 중인 AWS 서비스 전체를 한눈에 보고, Usage reports는 특정 서비스의 활동만 시간·일·월 단위로 모아 낸다.

#2핵심 질문

EFS에 낸 요금이 얼마나 나오고 어디서 나왔는지 어디에서 확인하는가?

#3동작 예시

운영자가 지난 달 EFS 청구서를 확인하려고 AWS Billing 콘솔로 들어간다. Billing reports에서 계정의 EFS 비용이 리전별로 나뉘어 보이고, 그 옆에 리포트를 만드는 방법을 AWS Cost Explorer에 가깝게 묶어 둔다.

다음으로 Usage reports에서 파일 시스템별로 GB 단위 저장량과 프로비저닝한 처리량을 시간 단위로 내려받는다.

#4동작 과정

  1. 리포트를 고른다Billing reports는 계정이 쓰는 AWS 서비스 활동을 큰 그림으로 보여 주고, Usage reports는 EFS 한 서비스의 사용량만 모아 준다. 후자는 usage type과 연산을 골라 어떤 값을 넣을지 정한다.
  2. 저장량과 비용을 나눠 본다저장 데이터는 storage class 값에 따라 GB 단위로 계량되고(→ 09-02), 새로 저장한 데이터는 재사용 여부에 따라 별도 usage type으로 잡힌다. 이 구분이 요금 변동의 원인이 된다.
  3. 비용을 나눠 귀속한다리포트에서 태그나 리전 단위로 값을 쪼개 팀과 환경에 돌려쓴다. 정해 둔 분류 기준이 없으면 다시 찾기 어려운 비용이 남는다.
  4. 확인해 볼 것AWS Billing 콘솔에서 EFS 항목이 리전과 usage type별로 나뉘어 표시되는지 확인한다.

할당량과 파일 작업 오류

서비스 할당량(파일 시스템·마운트 타깃·액세스 포인트 수, 연결 수 등)을 넘거나 디스크가 가득 차면 파일 작업이 실패하며, 그 원인은 오류 코드별로 구분해 찾아낸다.

먼저 알아야 할 것 10-01

#1문제 상황

여러 팀이 파일 시스템을 한꺼번에 만들면 어느 순간 계정 전체가 만들어 둘 수 있는 개수를 넘는다. 갑자기 모든 파일 시스템이 안 붙고, 이미 붙어 있던 클라이언트의 파일 읽기와 쓰기도 오류 코드와 함께 실패한다. 원인을 모른 채 파일 권한 문제로 착각하기 쉽다.

Amazon EFS quotas는 바로 그 경계선이다. Service Quotas 콘솔에서 늘릴 수 있는 값과 그대로 두어야 하는 값이 나뉘어 있고, 늘림 요청은 AWS Support를 통해 받는다.

#2핵심 질문

파일이 안 열리는 이유가 권한이 아니라 한계선에 닿은 것일까?

#3동작 예시

테스트용 파일 시스템을 짧은 시간에 여러 개 만든 뒤 EC2 인스턴스에서 파일을 열어 본다. 이번에는 마운트도 안 되고 파일 열기 명령이 오류 코드와 함께 즉시 실패한다.

Troubleshooting file operation errors related to quotas 문서로 넘어가 무엇이 한계에 걸렸는지 확인한다.

#4동작 과정

  1. 한계선을 확인한다Quotas는 리전마다 정해지는 서비스 사용량 상한이다. 파일 시스템 수와 액세스 포인트 수처럼 AWS Support에 요청해 늘릴 수 있는 값이 있고, NFS 클라이언트 연결 수나 지원하지 않는 NFS 버전처럼 손댈 수 없는 값도 있다.
  2. 증상을 갈라 본다할당량을 넘긴 경우에는 마운트 자체가 붙지 않는다. 반면 마운트는 되는데 파일이 열리지 않으면 디스크가 가득 찬 상황일 수 있어 두 경우를 나눠 본다.
  3. 오류 코드로 좁힌다실패한 파일 작업은 오류 코드를 함께 돌려주므로 코드 종류로 원인이 갈라지는지 살핀다. file system count처럼 무엇이 넘었는지를 API Reference의 오류 설명과 맞춰 본다.
  4. 확인해 볼 것Service Quotas 콘솔에서 EFS 항목의 현재 한계값이 계정별로 어떻게 표시되는지 확인한다.

회복 설계

EFS의 데이터를 지키는 방법은 AWS Backup 자동 백업으로 특정 시점의 사본을 만드는 것과, 다른 리전·계정으로 파일 시스템을 복제해 장애 시 복제본을 승격시키는 것으로 나뉜다.

먼저 알아야 할 것 08-04

#1문제 상황

한 리전의 파일 시스템이 통째로 사라지는 상황을 생각해 보자(→ 08-04). 같은 리전 안에 있는 여러 가용 영역이 각각 떨어져 있어 한 곳이 죽어도 버티는 구조는 되지만, 리전 전체를 잃을 확률은 남아 있다. 그때 같은 리전 안의 사본만으로는 자리가 없다.

disaster recovery는 그 상황을 미리 설계해 두는 일이다. resilience는 어느 정도의 장애를 견디는 구조를 확보하고, disaster recovery는 큰 재해 뒤에도 서비스를 되살리는 절차까지 정해 둔다는 차이가 있다.

#2핵심 질문

리전 하나를 잃었을 때 파일을 어디서 다시 일하게 할 것인가?

#3동작 예시

원본 리전의 파일 시스템이 사라지는 상황을 가정해, 같은 리전 안의 다른 가용 영역으로 붙는 경로를 먼저 열어 둔다. 그다음 다른 리전으로 복제본을 만들어 장애 시 그쪽으로 옮긴다.

장애가 나면 failover 절차를 따라 복제본을 쓰기 가능한 대상으로 올리고 클라이언트 마운트 경로를 그쪽으로 바꾼다.

#4동작 과정

  1. 가용 영역 장애를 견딘다Resilience는 한 리전 안에서 가용 영역 하나 이상이 사라져도 마운트 타깃이 계속 받쳐 주는 구조를 말한다. 마운트 타깃의 IP와 DNS는 고정이라 경로를 다시 적을 필요가 없다.
  2. 리전을 넘어 사본을 둔다cross-Region 복제 대상을 만들어 두면 원본 데이터가 다른 리전에 계속 복사된다. 두 리전의 위치는 서로 물리적으로 떨어져 있어 한쪽의 문제가 다른 쪽으로 번지지 않는다.
  3. 되살리는 순서를 정한다disaster recovery 계획에는 언제 복제본을 정식 자료원으로 삼는지, DNS와 애플리케이션 설정은 어디서 바꾸는지까지 적어 둔다. 이 목록이 없으면 장애 때 판단하지 못한다.
  4. 확인해 볼 것파일 시스템의 복제 상태 화면에서 원본과 복제본이 정상적으로 함께 도는지 확인한다.

리포트 해석과 IAM 문제 해결

청구·사용량 리포트의 각 지표가 뜻하는 바를 읽어 예상과 다른 요금의 원인을 찾고, IAM 권한 문제로 인한 접근 거부 오류는 역할과 정책 조건을 점검해 해결한다.

먼저 알아야 할 것 10-01

#1문제 상황

청구서를 보면 요금 항목마다 짧은 약어가 붙어 있다. 리전 약어와 사용 유형 이름이 나열되어 있는데, 어느 것이 어느 리전의 어느 동작인지 알기 어렵다(→ 10-01). 이걸 모르면 예상보다 큰 청구액이 나와도 어디서 늘었는지 찾을 수 없다. 같은 문서 묶음에 IAM troubleshooting도 함께 다뤄진다.

#2핵심 질문

예상과 다른 요금이 나온 이유와 붙지 않는 파일의 이유를 각각 어떻게 좁히는가?

#3동작 예시

지난 달 청구액이 늘었다고 리포트에서 usage type을 내려받는다. 표에 있는 리전 약어를 문서의 약어 목록과 대조해 어느 리전에서 늘었는지 본다. 늘어난 항목이 데이터 저장 쪽인지 처리량 쪽인지에 따라 확인 방향이 갈린다.

한편 EC2 인스턴스가 파일을 못 읽는 AccessDenied 오류를 내면 IAM troubleshooting으로 넘어가 역할을 확인한다.

#4동작 과정

  1. 약어를 풀어 읽는다Understanding billing and usage reports는 리전 약어 목록과 각 usage type이 뜻하는 동작을 표로 정리한다. 이 표를 리포트 값과 대조해 어느 항목이 늘었는지 좁힌다.
  2. 저장 데이터를 나눠 본다같은 저장 데이터도 storage class가 다르면 계량 이름이 갈린다. 마지막 읽은 시각 기준 이동 여부를 함께 보면 어느 값이 늘었는지 설명할 수 있다.
  3. 역할과 조건을 훑는다IAM troubleshooting은 권한이 안 되는 이유를 역할의 신뢰 관계, 정책 조건, 파일 시스템 정책 쪽으로 좁혀 가는 절차다. S3가 아니라 EFS의 파일 시스템 정책(→ 02-02)과 액세스 포인트 강제(→ 05-03)도 함께 확인한다.
  4. 확인해 볼 것CloudTrail 기록에서 거부된 요청이 어느 API 호출이었는지 확인한다.
