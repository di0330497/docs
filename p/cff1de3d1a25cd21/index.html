보안 개념 도메인 개요와 공통 위협

SCOR 보안 개념 영역의 첫 단계로, 온프레미스·하이브리드·클라우드 환경 전반에 공통적으로 존재하는 위협 유형을 분류해 이해하는 큰 틀이다.

#1문제 상황

기존에는 온프레미스 경계에 방화벽을 두고 외부 침입을 막는 방식이 중심이었다. 서버와 데이터가 사내에 모여 있으면 경계만 지켜도 내부 자원을 보호할 수 있었다. 그런데 자원이 클라우드와 하이브리드로 흩어지면서 지켜야 할 경계가 하나로 모이지 않게 됐다. 같은 공격이 사내 계정과 클라우드 계정 양쪽에 동시에 들어와도 한 지점의 방어만으로는 전체를 막을 수 없다.

#2핵심 질문

온프레미스·하이브리드·클라우드가 섞인 환경에서 공통적으로 어떤 위협이 어디에서 나타나는가?

#3동작 예시

한 조직이 사내 서버와 퍼블릭 클라우드를 함께 쓴다고 하자. 자격증명 탈취 시도가 사내 계정과 클라우드 계정 양쪽에 동시에 들어온다. 사내 경계 방화벽은 사내로 들어오는 트래픽만 보므로 클라우드 쪽 시도는 그대로 통과한다. 환경별로 위협을 나눠 두어야 각 지점에 맞는 통제를 배치할 수 있다.

#4동작 과정

  1. 자산과 환경 구분보호 대상이 온프레미스·하이브리드·클라우드 중 어디에 있는지 나눈다. 그래야 환경마다 다른 통제 지점이 드러난다.
  2. 위협 유형 분류악성코드·DoS/DDoS·피싱·중간자 공격 같은 공통 위협과, 데이터 유출·안전하지 않은 API·자격증명 탈취 같은 클라우드 고유 위협을 구분해 목록화한다.
  3. 통제 매핑분류한 위협마다 어떤 방어를 어디에 둘지 정한다. 이렇게 하면 한 환경의 방어가 다른 환경의 빈틈을 남기지 않는다.

#5한 줄 요약

환경이 섞여도 위협을 유형별로 나눠 각 환경에 맞는 방어를 배치하는 공통 기준을 세우는 것

온프레미스·클라우드 환경별 위협

바이러스·트로이목마·DoS/DDoS·피싱·루트킷·중간자 공격·SQL 인젝션·XSS 등 온프레미스 위협과, 데이터 유출·안전하지 않은 API·자격증명 탈취 등 클라우드 고유 위협을 환경별로 구분한 것이다.

#1문제 상황

온프레미스에서는 바이러스·트로이목마·루트킷 같은 악성코드와 DoS/DDoS, 피싱, 중간자 공격, SQL 인젝션, XSS가 주된 위협이었다. 서버를 직접 운영하므로 취약점을 직접 패치하고 경계를 직접 관리해야 했고, 내부 사용자 한 명이 뚫리면 내부망 전체가 노출됐다. 클라우드로 옮기면 이런 위협이 사라지는 것이 아니라, 데이터 유출·안전하지 않은 API·자격증명 탈취처럼 관리 경계 밖에서 생기는 위협이 더해진다.

#2핵심 질문

온프레미스와 클라우드에서 각각 어떤 위협이 다르게 나타나는가?

#3동작 예시

웹 애플리케이션 입력란에 스크립트를 넣어 다른 사용자의 브라우저에서 실행시키는 XSS는 온프레미스 웹 서버에서도 클라우드 웹 서비스에서도 그대로 성립한다. 반면 클라우드에서는 API 키나 서비스 계정 자격증명이 유출되면 공격자가 콘솔 권한으로 데이터를 내려받을 수 있다. 같은 애플리케이션이라도 환경에 따라 지켜야 할 지점이 달라진다.

#4동작 과정

  1. 온프레미스 위협 식별악성코드, DoS/DDoS, 피싱, 루트킷, 중간자 공격, SQL 인젝션, XSS처럼 경계와 내부 자산을 노리는 위협을 정리한다.
  2. 클라우드 위협 식별데이터 유출, 안전하지 않은 API, DoS/DDoS, 자격증명 탈취처럼 클라우드 서비스 구조에서 생기는 위협을 따로 정리한다.
  3. 공통·고유 구분양쪽에 겹치는 위협과 한쪽에만 있는 위협을 나눠, 환경별 방어 우선순위를 정한다.

일반 보안 취약점 비교

소프트웨어 버그, 취약하거나 하드코딩된 암호, OWASP Top 10, 암호화 알고리즘 누락, 버퍼 오버플로, 경로 순회, XSS·CSRF 같은 대표 취약점을 서로 비교해 이해하는 개념이다.

#1문제 상황

소프트웨어는 개발 과정에서 버그를 남기기 마련이고, 그중 일부는 공격에 그대로 악용된다. 약하거나 하드코딩된 암호, 암호화 알고리즘 누락, 버퍼 오버플로, 경로 순회, XSS·CSRF 같은 취약점이 대표적이다. 문제는 이런 취약점이 서로 다른 원인과 공격 경로를 가져서 하나의 방어로 묶어 막을 수 없다는 점이다. 각 취약점이 무엇을 노리고 어떻게 악용되는지 비교하지 않으면 우선순위를 세울 수 없다.

#2핵심 질문

대표 취약점들은 각각 무엇을 노리고 서로 어떻게 다른가?

#3동작 예시

로그인 폼에서 입력값을 검증하지 않으면 공격자는 아이디 칸에 SQL 구문을 넣어 인증을 우회할 수 있다. 같은 폼에 스크립트를 넣으면 다른 사용자 브라우저에서 실행되는 XSS가 된다. 입력 검증 하나가 빠져도 취약점의 종류와 결과가 달라지므로, 각 취약점을 따로 이해해야 한다.

#4동작 과정

  1. 원인 파악버그·설정 실수·설계 누락처럼 취약점이 생기는 근본 원인을 본다. 예를 들어 하드코딩된 암호는 코드에 값이 박혀 있어 유출되면 전부 노출된다.
  2. 공격 경로와 영향 비교각 취약점이 어느 입력 지점으로 들어와 무엇을 훔치거나 바꾸는지 비교한다. OWASP Top 10은 이런 대표 취약점을 목록화한 기준이다.
  3. 완화책 매핑취약점마다 입력 검증, 암호 저장 방식, 암호화 적용 같은 대응을 연결한다. 이렇게 하면 같은 실수가 다른 곳에서 반복되지 않는다.

암호화 구성요소

해싱, 암호화, PKI, SSL, IPsec, IPsec용 NAT-T IPv4, 사전 공유 키, 인증서 기반 인가 등 데이터 보호에 쓰이는 암호화 구성요소의 기능을 설명하는 것이다.

#1문제 상황

데이터를 평문으로 저장하거나 전송하면 중간에서 읽히거나 바뀔 수 있다. 이를 막으려면 해싱·암호화·PKI·SSL·IPsec 같은 구성요소를 목적에 맞게 골라 써야 한다. 그런데 이들은 모두 "데이터를 안전하게 한다"는 한 줄로 뭉뚱그려져 있어, 무결성 검증에 쓸 것과 기밀성 유지에 쓸 것이 섞인다. 목적을 구분하지 않고 하나만 쓰면 필요한 보호가 빠진다.

#2핵심 질문

각 암호화 구성요소는 어떤 보호를 담당하고 언제 쓰이는가?

#3동작 예시

파일이 전송 중에 변조되지 않았는지 확인하려면 해싱으로 만든 값을 비교한다. 내용 자체를 읽지 못하게 하려면 암호화로 평문을 암호문으로 바꾼다. 두 목적이 다르므로 한 구성요소로 둘 다 해결하려 하면 한쪽이 비게 된다.

#4동작 과정

  1. 목적 구분무결성, 기밀성, 인증 중 무엇을 원하는지 먼저 정한다. 해싱은 무결성, 암호화는 기밀성에 주로 쓰인다.
  2. 구성요소 선택PKI와 인증서로 키와 신원을 관리하고, SSL은 전송 구간을, IPsec은 네트워크 구간을 보호한다. IPsec의 NAT-T IPv4는 NAT 환경에서도 IPsec이 통과하도록 돕는다.
  3. 키 관리 방식 결정사전 공유 키(preshared key)를 쓸지 인증서 기반 인가를 쓸지 정한다. 인증서 방식은 키 배포와 폐기 관리가 쉬워 규모가 커질수록 유리하다.

VPN 배포 유형과 구성요소

사이트 간 대 원격 접속 VPN 배포 유형과 가상 터널 인터페이스, 표준 기반 IPsec, DMVPN, FlexVPN, Cisco Secure Client 등 구성요소를 고가용성 고려사항과 함께 비교하는 개념이다.

#1문제 상황

원격 사용자와 지사가 본사 네트워크에 접속하려면 공용 인터넷 위에 암호화된 통로를 만들어야 한다. 사이트 간 VPN과 원격 접속 VPN은 연결 대상과 규모가 달라 같은 방식으로 구성할 수 없다. 게다가 터널이 하나 끊기면 업무가 멈추므로 이중화까지 고려해야 한다. 배포 유형과 구성요소를 구분하지 않으면 보안은 되지만 끊김에 취약한 구성을 만들게 된다.

#2핵심 질문

사이트 간 VPN과 원격 접속 VPN은 각각 어떤 구성요소로 어떻게 이중화하는가?

#3동작 예시

본사와 지사 라우터 사이에 표준 기반 IPsec 터널을 세우면 두 사이트의 사설 대역이 하나처럼 연결된다. 재택 사용자는 Cisco Secure Client로 본사에 접속해 자기 트래픽만 터널로 보낸다. 같은 IPsec 기반이라도 연결을 라우터끼리 맺는지 사용자 장비가 맺는지가 다르다.

#4동작 과정

  1. 배포 유형 선택지사처럼 고정된 두 지점을 잇는 사이트 간 VPN인지, 개별 사용자를 붙이는 원격 접속 VPN인지 정한다.
  2. 구성요소 배치가상 터널 인터페이스로 암호화 통로를 만들고, 표준 기반 IPsec으로 암호화와 인증을 적용한다. DMVPN과 FlexVPN은 다수 지사와 유연한 토폴로지를 다루는 방식이다.
  3. 고가용성 설계터널이나 헤드엔드가 끊겨도 대체 경로로 붙도록 이중화한다. 이렇게 해야 한 지점 장애가 전체 접속 중단으로 번지지 않는다.

보안 인텔리전스

위협 정보를 생산(authoring)하고 공유(sharing)하며 소비(consumption)하는 보안 인텔리전스의 순환 과정을 설명하는 개념이다.

#1문제 상황

새 위협은 계속 나오는데 각 조직이 이를 혼자 수집하고 분석하면 시간과 비용이 크게 든다. 한 곳에서 발견한 공격 지표도 다른 곳에 전달되지 않으면 같은 공격에 반복해서 당한다. 위협 정보를 만드는 쪽과 쓰는 쪽이 따로 놀면 정보가 실제 방어로 이어지지 않는다. 정보를 생산·공유·소비의 순환으로 묶어야 방어가 빨라진다.

#2핵심 질문

위협 정보를 어떻게 만들어 공유하고 실제 방어에 소비하는가?

#3동작 예시

한 보안 업체가 악성코드가 접속하는 도메인 목록을 관찰해 침해 지표로 정리한다. 이를 공유 형식으로 배포하면 다른 조직이 자기 방화벽과 탐지 장비에 그 도메인을 차단 목록으로 넣어 같은 공격을 미리 막는다.

#4동작 과정

  1. 생산(authoring)관찰한 공격에서 침해 지표와 위협 정보를 정리해 만든다. 이 단계가 없으면 공유할 내용 자체가 없다.
  2. 공유(sharing)정리한 정보를 표준 형식으로 다른 조직이나 플랫폼에 배포한다. 형식이 맞아야 받는 쪽이 자동으로 반영할 수 있다.
  3. 소비(consumption)받은 정보를 자기 방어 장비의 차단·탐지 규칙에 넣는다. 이렇게 순환이 닫혀야 새 위협에 대한 대응이 빨라진다.

피싱·소셜 엔지니어링 대응 통제

피싱과 소셜 엔지니어링 공격을 방어하기 위해 사용하는 기술적·교육적 통제 수단을 설명하는 개념이다.

#1문제 상황

기존 이메일 보안은 발신자 주소나 특정 키워드로 스팸을 걸러 내는 방식이 중심이었다. 이 방식은 정상 도메인을 위조하거나 이미 탈취한 실제 계정에서 보낸 메시지를 걸러 내지 못한다. 결국 필터를 통과한 메시지가 사용자에게 도달하고, 사용자는 발신자를 신뢰해 자격 증명을 입력하거나 첨부 파일을 실행하게 된다.

이런 공격은 기술적 결함이 아니라 사람의 판단을 노린다는 점이 문제다. 메일 필터만 강화하면 공격자는 문자·전화·메신저 등 다른 채널로 옮겨 간다. 그래서 메시지 검사 같은 기술적 통제와 사용자 교육을 함께 두지 않으면 막지 못하는 구간이 계속 남는다.

#2핵심 질문

사람을 속여 자격 증명이나 정보를 빼내는 공격을 기술적 통제와 교육으로 어떻게 겹쳐 막을 것인가?

#3동작 예시

이메일 게이트웨이가 들어온 메시지의 발신 도메인 인증 결과를 확인해 위조 여부를 판정한다. 사용자가 본문의 링크를 누르면 보안 프록시가 그 시점에 링크를 실제로 열어 악성 페이지인지 다시 검사하고, 악성이면 접속을 끊는다.

#4동작 과정

  1. 메시지 입구 검사게이트웨이가 발신 도메인 인증과 첨부 파일·링크의 평판을 확인해 의심 메일을 격리한다. 그 결과 정상처럼 위장한 대량 피싱이 내부로 들어오기 전에 걸러진다.
  2. 클릭 시점 재검사사용자가 누른 링크를 보안 프록시(사용자 대신 접속해 검사하는 중계 서버)가 실시간으로 열어 악성 페이지면 차단한다. 그 결과 메일 발송 후에 바뀐 악성 페이지도 막힌다.
  3. 사용자 교육·신고의심 메일을 신고하는 버튼과 정기 모의 훈련으로 사용자가 스스로 판단하게 한다. 그 결과 필터가 놓친 메시지도 조기에 신고되어 차단된다.

SDN 아키텍처의 North Bound·South Bound API

SDN 아키텍처에서 컨트롤러를 중심으로 상위 애플리케이션과 통신하는 North Bound API와 하위 네트워크 장비와 통신하는 South Bound API의 역할 차이를 설명하는 개념이다.

#1문제 상황

전통 네트워크는 장비마다 관리자가 콘솔에서 설정을 넣고, 경로를 결정하는 제어 기능과 패킷을 전달하는 기능이 같은 장비에 함께 들어 있다. 장비 수가 늘수록 각 장비 설정을 따로 맞춰야 하고, 정책을 한 번에 바꾸거나 전체를 한 관점에서 관리하기 어렵다.

제어가 장비에 흩어져 있으면 네트워크 동작을 소프트웨어로 프로그래밍하기도 힘들다. 상위 애플리케이션이 원하는 정책을 내려도 그것을 장비별 명령으로 번역해 주는 통로가 없기 때문이다.

#2핵심 질문

네트워크 제어 로직을 장비에서 분리해 중앙에서 다루되, 상위 애플리케이션과 하위 장비는 각각 어떤 인터페이스로 연결할 것인가?

#3동작 예시

SDN 컨트롤러가 중앙에 있고, 위쪽으로는 애플리케이션이 REST API를 통해 "이 트래픽은 특정 경로로 보내라"는 정책을 전달한다. 아래쪽으로는 컨트롤러가 OpenFlow 같은 프로토콜로 각 스위치에 흐름 규칙을 내려보내 실제 전달을 지시한다.

#4동작 과정

  1. North Bound API 수신상위 애플리케이션이 주로 REST 기반 인터페이스로 컨트롤러에 정책과 요청을 전달한다. 그 결과 관리자가 장비별 명령을 직접 치지 않고 앱 수준에서 네트워크를 제어한다.
  2. 컨트롤러 정책 계산컨트롤러가 전체 토폴로지와 정책을 바탕으로 각 장비에 필요한 규칙을 계산한다. 그 결과 네트워크 전체를 본 일관된 결정이 만들어진다.
  3. South Bound API 하달계산된 규칙을 South Bound 프로토콜(예: OpenFlow)로 스위치에 내려보낸다. 그 결과 장비는 전달만 수행하고 제어는 중앙 컨트롤러에 모인다.

#5한 줄 요약

North Bound API로 애플리케이션의 의도를 받고 South Bound API로 장비를 제어해, 제어 기능을 중앙 컨트롤러로 모으는 것

Cisco DNA Center API

Cisco DNA Center가 제공하는 API를 네트워크 프로비저닝, 최적화, 모니터링, 트러블슈팅에 어떻게 활용하는지 설명하는 개념이다.

#1문제 상황

네트워크 운영자가 장비를 하나씩 콘솔에서 설정하고 상태를 확인하면, 장비 수가 늘수록 같은 작업을 반복하게 되고 입력 실수도 함께 늘어난다. 문제가 생겼을 때 어느 장비가 어떤 상태인지 파악하는 데도 시간이 걸린다.

장비별 수작업은 자동화된 상위 시스템과 연결되지 않는다. 그래서 프로비저닝, 최적화, 모니터링, 트러블슈팅을 코드로 호출할 수 있는 통로가 필요해진다.

#2핵심 질문

프로비저닝·최적화·모니터링·트러블슈팅을 API로 자동화하려면 무엇을 어떤 순서로 호출해야 하는가?

#3동작 예시

스크립트가 DNA Center의 인증 API로 접근 토큰을 받고, 그 토큰을 헤더에 넣어 장비 목록 조회 API와 설정 템플릿 적용 API를 호출한다. 이렇게 하면 새 스위치 여러 대에 같은 템플릿을 한 번에 배포할 수 있다.

#4동작 과정

  1. 인증 토큰 획득스크립트가 자격 증명으로 DNA Center에 로그인해 접근 토큰을 받는다. 그 결과 이후 호출이 해당 사용자의 권한으로 승인된다.
  2. 목적별 API 호출프로비저닝, 모니터링, 트러블슈팅 등 목적에 맞는 엔드포인트로 요청을 보낸다. 그 결과 장비별 수작업 대신 일괄 자동화가 이뤄진다.
  3. 응답 수신·후속 처리작업 ID, 상태, 데이터 같은 응답을 받아 다음 단계나 알림에 연결한다. 그 결과 운영 상태가 시스템 사이에서 자동으로 흘러간다.

Cisco 보안 어플라이언스 API 호출 Python 스크립트

Cisco 보안 어플라이언스의 API를 호출하는 기초 Python 스크립트를 읽고 그 동작을 해석하는 능력이다.

#1문제 상황

보안 어플라이언스의 설정 변경과 상태 확인을 사람이 콘솔에서 반복하면 규모가 커질수록 느려지고 실수가 생긴다. 작업을 자동화하려면 장비가 제공하는 API를 어떤 순서로 호출하는지 코드에서 읽어낼 수 있어야 한다.

API 호출은 보통 접근 권한을 확인하는 단계와 실제 작업을 요청하는 단계가 나뉘어 있다. 이 순서를 모르면 스크립트가 왜 실패하는지, 토큰이 어디에 쓰이는지 해석할 수 없다.

#2핵심 질문

Python 스크립트가 보안 어플라이언스 API를 호출해 작업을 수행하는 흐름을 어떻게 해석할 것인가?

#3동작 예시

``python import requests r = requests.post(url + "/api/fmc_platform/v1/auth/generatetoken", auth=(user, pw), verify=False) token = r.headers["X-auth-access-token"] h = {"X-auth-access-token": token} dev = requests.get(url + "/api/fmc_config/v1/domain/default/devices", headers=h, verify=False) print(dev.json()) ``

이 스크립트는 먼저 인증 엔드포인트를 호출해 토큰을 받고, 그 토큰을 헤더에 실어 장비 목록을 조회한 뒤 응답을 출력한다.

#4동작 과정

  1. 토큰 요청스크립트가 자격 증명으로 인증 엔드포인트를 호출해 접근 토큰을 받는다. 그 결과 이후 요청이 인증된 사용자로 처리된다.
  2. 헤더에 토큰을 실어 API 호출받은 토큰을 요청 헤더에 넣고 원하는 리소스에 GET이나 POST를 보낸다. 그 결과 장비 정보 조회나 정책 변경을 코드가 대신 수행한다.
  3. 응답 해석돌려받은 JSON(구조화된 데이터)을 파싱해 값을 쓰거나 다음 호출에 넘긴다. 그 결과 결과가 자동 분기나 알림으로 이어진다.

#5한 줄 요약

스크립트가 토큰을 받아 헤더에 실어 보안 어플라이언스 API를 호출하고 응답을 해석해 작업을 자동화하는 것

네트워크 보안 도메인 개요와 IPS·방화벽 솔루션 비교

네트워크를 통과하는 트래픽에서 침입을 탐지·차단하는 IPS와 트래픽을 정책으로 허용·차단하는 방화벽 기능을 제공하는 여러 네트워크 보안 솔루션의 차이를 비교하는 영역이다.

→ 01-04 참조

#1문제 상황

방화벽은 접속 규칙에 따라 연결을 허용하거나 끊지만, 일단 열어둔 포트로 들어오는 공격은 내용을 보지 않고 통과시킬 수 있다. 반대로 IPS만 두면 어떤 연결을 기본으로 허용하고 차단할지에 대한 정책 기준이 약하다. 그래서 어느 하나만 쓰면 막지 못하는 구간이 생긴다.

두 기능은 검사하는 대상과 판단 기준이 다르다. 방화벽은 연결 단위로, IPS는 연결 안을 흐르는 데이터 단위로 본다. 이 차이를 이해하지 않으면 솔루션 비교와 조합을 잘못 판단하게 된다.

#2핵심 질문

연결을 정책으로 통제하는 방화벽과 침입을 탐지·차단하는 IPS 기능을 어떤 솔루션으로 어떻게 조합할 것인가?

#3동작 예시

하나의 어플라이언스가 먼저 출발·목적지 IP, 포트, 프로토콜로 이뤄진 연결 정보를 보고 해당 연결을 허용한다. 이어서 허용된 흐름의 페이로드(실제로 오가는 데이터 내용)를 알려진 공격 시그니처와 비교해 패턴이 맞으면 그 세션을 차단한다.

#4동작 과정

  1. 정책 기반 허용·차단방화벽 기능이 접속 규칙에 따라 연결을 통과시키거나 끊는다. 그 결과 허용된 경로의 트래픽만 다음 검사 대상이 된다.
  2. 심층 검사IPS 기능이 통과한 트래픽의 내용과 패턴을 시그니처와 비교해 악성 여부를 판정한다. 그 결과 허용된 포트로 들어오는 공격도 잡힌다.
  3. 차단·기록악성으로 판정되면 세션을 끊고 로그와 경보를 남긴다. 그 결과 사후 분석과 정책 조정이 가능해진다.

#5한 줄 요약

연결 정책 통제(방화벽)와 침입 탐지·차단(IPS)을 결합해 허용된 구간 안의 공격까지 막는 것

IPS·방화벽 배포 모델

IPS와 방화벽 기능을 네트워크 어디에 어떤 형태(인라인, 탐지 전용, 가상·클라우드 등)로 배치하는지에 대한 배포 아키텍처를 설명하는 개념이다.

#1문제 상황

보안 장비를 네트워크 어디에 어떤 형태로 두느냐에 따라 막을 수 있는 범위와 장애 영향이 달라진다. 실제 트래픽 경로에 직접 넣는 방식은 그 자리에서 차단할 수 있지만, 장비에 문제가 생기면 그 구간 통신도 함께 멈춘다.

복제된 트래픽만 받아 보는 방식은 통신을 방해하지 않지만 탐지와 기록만 하고 직접 차단하지는 못한다. 이 차이를 고려하지 않으면 원하는 보호 수준과 가용성을 동시에 얻지 못한다.

#2핵심 질문

IPS·방화벽을 인라인·탐지 전용·가상·클라우드 중 어떤 형태로 어디에 배치할 것인가?

#3동작 예시

트래픽이 지나는 경로에 장비를 직접 넣는 인라인 배치는 악성 패킷을 그 자리에서 버릴 수 있다. 대신 장비가 멈추면 그 구간을 지나는 통신도 함께 멈추므로, 우회 동작이나 이중화를 함께 정해야 한다.

#4동작 과정

  1. 배치 형태 선택인라인(경로에 직접 통과), 탐지 전용(복제된 트래픽만 수신), 가상·클라우드(소프트웨어 형태) 중 위치와 역할에 맞는 형태를 고른다. 그 결과 차단 가능 범위와 장애 영향이 정해진다.
  2. 트래픽 경로 연결실제 트래픽이 장비를 지나가게 하거나 복제본이 전달되도록 연결한다. 그 결과 검사할 흐름이 확보된다.
  3. 정책 적용·감시정책을 배포하고 우회(fail-open) 여부와 이중화를 정해 운영한다. 그 결과 차단 성능과 가용성 사이에서 균형을 맞춘다.

#5한 줄 요약

네트워크 위치와 트래픽 경로에 맞춰 인라인·탐지 전용·가상 배치를 선택해 검사와 차단 효과를 확보하는 것

NetFlow와 Flexible NetFlow

라우터·스위치를 지나는 트래픽의 흐름 정보를 레코드로 수집·내보내 네트워크 사용 현황과 이상 징후를 파악하게 해주는 NetFlow 및 그 확장판 Flexible NetFlow의 구성·기능·이점을 다룬다.

→ 06-06 참조

#1문제 상황

전통적인 SNMP 기반 모니터링은 장치의 인터페이스별 누적 카운터(초당 비트, 패킷 수, 오류 수)만 주기적으로 가져온다. 이 방식은 "링크가 얼마나 찼는가"는 알려주지만, 그 트래픽이 누가 누구에게 어떤 포트와 프로토콜로 보낸 것인지는 남기지 않는다. 그래서 대역폭 급증이나 이상 트래픽이 생겨도 출발지·목적지·애플리케이션 단위로 원인을 좁히기 어렵고, 문제를 겪는 동안 추측에 의존해야 한다.

#2핵심 질문

링크 사용량 숫자만으로는 알 수 없는 트래픽의 출발지·목적지·프로토콜·포트별 흐름을 어떻게 기록하고 내보내 이상 징후를 정확히 짚어낼 것인가?

#3동작 예시

한 사용자가 특정 서버의 443 포트로 대량 다운로드를 시작하면, 라우터는 출발지 IP·목적지 IP·출발지/목적지 포트·프로토콜·ToS·입력 인터페이스 같은 값이 같은 패킷들을 하나의 흐름으로 묶는다. 플로우가 끝나거나 일정 시간이 지나면 그 흐름의 패킷 수·바이트 수·시작·종료 시각을 담은 레코드를 만들어 수집 서버로 내보낸다. 수집 서버는 이 레코드로 "이 서버·이 포트로 트래픽이 집중됐다"는 사실을 지목할 수 있다.

#4동작 과정

  1. 플로우 정의관리자가 매칭할 키(출발지/목적지 IP, 포트, 프로토콜, 인터페이스 등)를 지정해 같은 값을 가진 패킷을 하나의 흐름으로 묶는 기준을 세운다.
  2. 캐시 집계장치는 흐름별 캐시 항목에 패킷 수·바이트 수·타임스탬프를 갱신하고, 흐름이 끝나거나 타임아웃되면 레코드를 완성한다.
  3. 레코드 내보내기완성된 레코드를 UDP 등으로 외부 수집기(컬렉터)에 전송하고, 수집기는 이를 저장·분석해 사용 현황과 이상 징후 파악에 쓴다. Flexible NetFlow는 플로우 정의·캐시·내보내기 대상을 독립적으로 조합·확장할 수 있게 해 준다.

트래픽을 출발지·목적지·프로토콜 단위의 흐름 레코드로 정리해 네트워크 사용 현황과 이상 징후를 보이게 하는 것

VLAN 세그멘테이션, 포트 보안, DHCP 스누핑, 동적 ARP 검사, 스톰 컨트롤, PVLAN 등으로 MAC·ARP·VLAN 호핑·STP·DHCP 공격을 막는 2계층 보안 기법이다.

→ 06-02 참조

#1문제 상황

2계층 스위치는 프레임을 그대로 전달하는 장치라, MAC 주소·ARP·DHCP·STP 같은 프로토콜을 악용한 공격에 그대로 노출된다. 공격자는 위조 MAC을 쏟아내 MAC 테이블을 넘치게 하거나, 위조 ARP 응답으로 트래픽을 가로채거나, 가짜 DHCP 서버로 게이트웨이 정보를 밀어 넣을 수 있다. 기본 설정만으로는 이런 프레임을 구분할 근거가 없어, 한 포트의 침해가 같은 세그먼트 전체로 번지기 쉽다.

#2핵심 질문

같은 스위치에 연결된 여러 단말 사이에서 위조 MAC·ARP·DHCP·VLAN 우회 프레임을 어떻게 걸러 신뢰할 수 있는 포트만 통과시킬 것인가?

#3동작 예시

스위치 포트 Gi1/0/5에 DHCP 스누핑을 켜고 신뢰 포트를 실제 DHCP 서버가 붙은 Gi1/0/1로만 지정한다. 그러면 Gi1/0/5에서 가짜 DHCP 응답이 들어오면 스위치가 이를 버리고, DHCP 클라이언트가 보낸 요청은 신뢰 포트 방향으로만 전달한다. 스위치는 이 과정에서 "IP-MAC-포트-VLAN" 바인딩 표를 만들어 두고, 뒤이어 들어오는 ARP 응답을 동적 ARP 검사(DAI)로 검증하는 데 재사용한다.

#4동작 과정

  1. 세그먼트 분리VLAN으로 브로드캐스트 도메인을 나누고 PVLAN으로 같은 VLAN 안의 단말 간 통신까지 제한해, 침해가 미치는 범위를 좁힌다.
  2. 포트·프레임 통제포트 보안으로 포트별 허용 MAC 수와 위반 시 동작을 고정하고, 스톰 컨트롤로 브로드캐스트·멀티캐스트·유니캐스트 폭주를 제한한다.
  3. 위조 프레임 차단DHCP 스누핑으로 신뢰할 수 없는 DHCP 응답을 막고 그 바인딩 표를 동적 ARP 검사에 넘겨 위조 ARP를 버리며, 네이티브 VLAN과 트렁크 설정을 엄격히 해 VLAN 호핑·STP 조작·MAC 플러딩 같은 공격을 차단한다.

장치 하드닝 — 컨트롤·데이터·관리 플레인

네트워크 보안 장비의 컨트롤 플레인·데이터 플레인·관리 플레인을 각각 보호하도록 불필요한 서비스와 접근을 제거·제한하는 장치 강화 기법이다.

#1문제 상황

네트워크 장비는 기본 설정 상태에서 쓰지 않는 서비스와 관리 접근이 함께 열려 있는 경우가 많다. HTTP·Telnet 같은 평문 관리 채널, 불필요한 CDP·LLDP, 사용하지 않는 포트가 그대로 남으면 공격 표면이 넓어지고, 설정 변경 권한이 탈취되면 네트워크 전체가 위험해진다. 장비 한 대가 뚫리는 것이 곧 그 장비를 지나가는 모든 트래픽이 뚫리는 것과 같으므로, 장비 자체를 보호하는 일이 선행되어야 한다.

#2핵심 질문

장비를 지나가는 트래픽을 처리하는 평면과 장비를 조작하는 평면을 각각 어떻게 분리하고 불필요한 접근을 제거할 것인가?

#3동작 예시

관리 플레인에서는 Telnet을 끄고 SSH만 남기며, ACL로 관리 서브넷에서만 접속을 허용하고 로컬 사용자 대신 AAA로 인증을 위임한다. 데이터 플레인에서는 사용하지 않는 스위치 포트를 shutdown하고, 포트 보안과 트래픽 필터로 실제 전달되는 프레임·패킷을 제한한다. 컨트롤 플레인에서는 라우팅·관리 프로토콜 트래픽에 속도 제한(CoPP)을 걸어 제어 평면 자원이 고갈되지 않도록 보호한다.

#4동작 과정

  1. 평면 구분컨트롤 플레인(라우팅·시그널링), 데이터 플레인(실제 전달 트래픽), 관리 플레인(장비 접속·설정)을 나누고 각각에 적용할 보호 규칙을 정한다.
  2. 노출 제거불필요한 서비스와 포트를 끄고, 평문 관리 프로토콜을 암호화된 프로토콜로 바꾸며, 배너·비밀번호·권한 등 기본 자격 증명을 강화한다.
  3. 접근 제한·감시ACL·AAA·속도 제한으로 평면별 접근을 필요한 주체에게만 허용하고, 로그와 변경 감시로 설정 이탈을 빠르게 발견한다.

#5한 줄 요약

장비를 세 개의 평면으로 나누어 각 평면의 불필요한 접근과 자원 고갈을 차단하는 것

#1문제 상황

네트워크가 하나의 평평한 신뢰 구역으로 묶여 있으면, 한 대의 감염 단말이 곧바로 다른 모든 자산에 접근할 수 있고 누가 무엇을 하는지 구분할 근거도 없다. IP·포트만 보는 전통적 ACL은 같은 포트를 쓰는 정상 앱과 악성 트래픽을 구분하지 못하며, 알려진 시그니처가 없는 공격이나 악성 URL·파일은 통과시키기 쉽다.

#2핵심 질문

누가 어디에 접근할 수 있는지를 신원·역할·애플리케이션·위협 수준에 따라 나누어 통제하려면 어떤 정책을 어디에 세워야 하는가?

#3동작 예시

사용자 세그먼트에서 서버 세그먼트로 가는 트래픽에 접속 제어 정책을 걸어, 재무 앱은 재무 그룹에만 허용하고 나머지는 기본 차단한다. 같은 정책 위에서 AVC(애플리케이션 가시성·제어)가 트래픽을 애플리케이션 단위로 식별해 허용·차단·대역 제한을 적용하고, URL 필터링이 요청을 평판·범주별로 판정하며, 침입·멀웨어 정책이 시그니처와 평판으로 악성 흐름을 잡아낸다.

#4동작 과정

  1. 세그먼트 분리자산과 사용자 그룹을 세그먼트로 나누고 세그먼트 간 허용 경로만 정의해 기본 차단 원칙을 세운다.
  2. 가시성 확보AVC로 어떤 애플리케이션이 오가는지 식별하고, URL 필터링으로 요청 목적지를 판정해 정책 판단의 근거를 만든다.
  3. 정책 집행접속 제어·침입·멀웨어 정책을 결합해 허용·차단·검사·대역 제한을 실제 트래픽에 적용하고, 결과를 로그와 이벤트로 남긴다.

#5한 줄 요약

세그먼트·신원·애플리케이션·위협이라는 여러 기준을 하나의 정책으로 묶어 트래픽을 필요한 만큼만 허용하는 것

보안 솔루션 관리 옵션

보안 솔루션을 단일 장치 관리자와 다중 장치 관리자, 인밴드와 아웃오브밴드, 클라우드와 온프레미스 중 어떤 방식으로 관리할지 선택하는 관리 옵션을 구현하는 개념이다.

#1문제 상황

보안 장비가 한 대일 때는 장비별 관리 화면에서 직접 설정해도 버틸 만하다. 그러나 장비 수가 늘면 정책을 장비마다 따로 입력하게 되어 불일치와 누락이 생기고, 변경 이력과 일관성을 확인할 방법이 사라진다. 또한 관리 트래픽을 어떤 경로로 보내고 관리 시스템을 어디에 두는지에 따라 운영 편의와 보안 수준이 크게 달라지는데, 이를 고려하지 않으면 관리 채널 자체가 공격 경로가 된다.

#2핵심 질문

여러 보안 장비의 정책을 일관되게 관리하고, 관리 접속과 관리 시스템을 어떤 방식으로 배치할 것인가?

#3동작 예시

여러 방화벽과 IPS를 단일 중앙 관리자에 등록해 정책을 한 번 정의하고 각 장비에 배포하면, 모든 장비가 같은 정책 버전을 참조하게 된다. 관리 접속은 사용자 데이터와 분리된 별도 관리 대역으로 빼서(아웃오브밴드) 정책 위반이나 장애가 나도 관리 채널이 끊기지 않게 하고, 정책 콘솔은 클라우드 관리자에 두어 원격지 장비까지 같은 방식으로 다룬다.

#4동작 과정

  1. 관리 범위 결정장비별 단독 관리자(single)로 갈지 하나의 다중 장비 관리자(multidevice)로 묶을지 정해 정책 일관성과 운영 부담을 맞바꾼다.
  2. 관리 경로 설계관리 트래픽을 데이터 경로와 같은 망으로 보낼지(in-band) 분리된 관리망으로 뺄지(out-of-band) 결정해 가용성과 노출을 조정한다.
  3. 관리 위치 선택관리 시스템을 온프레미스에 둘지 클라우드에 둘지 정해 확장성·접근성·규제 요건에 맞춘다.

AAA 구성 — TACACS+·RADIUS

장치 및 네트워크 접속에 대해 인증·인가·계정관리(AAA)를 TACACS+나 RADIUS 프로토콜로 구성해 사용자 접근을 통제하는 방법이다.

→ 06-02 참조

#1문제 상황

장비마다 로컬 계정을 따로 만들면 사용자가 늘고 장비가 늘수록 계정과 비밀번호를 각 장비에서 관리해야 한다. 퇴사자 계정을 모든 장비에서 지우지 못하거나, 누가 언제 어떤 명령을 실행했는지 확인할 기록이 남지 않거나, 사용자별로 허용할 명령 수준을 장비마다 다르게 맞추기 어렵다. 자격 증명이 장비에 흩어져 있으면 그중 한 곳이 뚫리는 것만으로 전체 접근 권한이 새어 나갈 수 있다.

#2핵심 질문

장비 접속과 네트워크 접속의 인증·인가·계정관리를 중앙 서버에서 일관되게 처리하고 기록하려면 어떻게 구성해야 하는가?

#3동작 예시

관리자가 장비에 SSH로 접속하면 장비는 로컬 계정 대신 중앙 AAA 서버로 자격 증명을 보내 검증을 요청한다. 서버가 인증에 성공하면 어떤 명령 등급까지 허용할지 인가 정보를 돌려주고, 장비는 관리자가 실행한 명령과 접속 시각을 계정관리 기록으로 서버에 남긴다. 이때 TACACS+는 장비 관리 명령 단위의 세밀한 인가에, RADIUS는 네트워크 접속 인증과 계정 기록에 주로 쓰인다.

#4동작 과정

  1. AAA 대상 지정장비 접속(관리자)과 네트워크 접속(사용자) 각각에 대해 인증·인가·계정관리 중 무엇을 어떤 서버로 처리할지 정하고 서버 주소와 공유 비밀을 등록한다.
  2. 인증·인가 적용접속 시 중앙 서버가 자격 증명을 검증하고, 성공하면 사용자별 권한과 허용 명령 범위를 장비에 내려 준다.
  3. 계정관리·감사접속 시작·종료와 실행한 명령을 서버에 기록해 누가 무엇을 했는지 추적하고, 서버 장애 시 로컬 계정으로 대체할지 여부를 정한다.

안전한 네트워크 관리 — SNMPv3·NetConf·RestConf·syslog·NTP

SNMPv3, NetConf, RestConf, API, 보안 syslog, 인증을 적용한 NTP 등으로 경계 보안 장비와 인프라 장비를 안전하게 관리하도록 구성하는 방법이다.

→ 01-07 참조

#1문제 상황

기존 관리 방식은 장비에 사람이 콘솔로 접속해 명령을 반복 입력하거나, SNMPv1·v2c 처럼 커뮤니티 문자열을 평문으로 주고받는 프로토콜에 의존했다. 이런 커뮤니티 문자열과 관리 트래픽은 암호화되지 않아 중간에서 스니핑하면 그대로 노출되고, 값이 맞기만 하면 조회·변경이 허용되어 접근 통제가 약하다. syslog도 기본은 평문 UDP 514로 전송되어 로그를 도청하거나 위조할 수 있고, NTP를 인증 없이 쓰면 시각 자체를 조작당해 로그 상관 분석과 인증서 유효성 검증이 어긋난다. 그 결과 장비 설정이 사람마다 달라지고 감사 근거도 신뢰할 수 없게 된다.

#2핵심 질문

경계 보안 장비와 인프라 장비를 콘솔 반복 작업이나 평문 프로토콜에 기대지 않고, 인증과 암호화가 적용된 표준 방식으로 안전하게 구성·감사하려면 어떻게 해야 하는가?

#3동작 예시

IOS-XE 라우터에 SNMPv3 사용자를 인증 SHA와 프라이버시 AES로 생성해 조회 권한만 부여하고, 로그는 TLS로 보호되는 secure syslog 서버로 보내며, NTP는 인증 키를 지정해 신뢰할 수 있는 서버와 시각을 맞춘다. 설정 자체는 NetConf(SSH 기반)나 RestConf(HTTPS 기반)로 YANG 모델에 맞춰 자동화해 사람이 매번 CLI를 입력하지 않게 한다. 이렇게 하면 자격 증명과 관리 데이터가 네트워크에서 보호되고, 누가 어떤 값으로 장비를 바꿨는지 추적할 수 있다.

#4동작 과정

  1. 안전한 관리 채널 수립SNMPv3는 사용자별 인증·프라이버시를, NetConf는 SSH를, RestConf는 HTTPS를 사용해 관리 트래픽과 자격 증명을 암호화한다.
  2. 표준 모델로 관리 데이터 교환NetConf·RestConf는 YANG 모델에 정의된 구조로 설정을 읽고 쓰고, SNMP는 상태·통계를 폴링해 장비와 관리 시스템이 같은 형식으로 데이터를 주고받는다.
  3. 로그와 시각의 무결성 확보이벤트는 secure syslog로 안전하게 전송하고 NTP 인증으로 시각을 맞춰, 로그 순서와 인증서 판단의 기준 시각을 신뢰할 수 있게 한다.

사이트 간 VPN 구성 — IOS 라우터

Cisco 라우터와 IOS를 사용해 두 사이트 사이의 트래픽을 암호화·터널링하는 사이트 간 VPN을 구성하고 검증하는 방법이다.

#1문제 상황

본사와 지사는 각자 사설 IP 대역을 쓰면서 인터넷 회선으로 연결되는데, 공용 인터넷을 그냥 지나는 트래픽은 암호화되지 않아 도청과 변조에 노출된다. 사이트 사이에 전용선을 깔면 안전하지만 비용이 크고, GRE 터널만 쓰면 캡슐화는 되어도 내용은 평문이라 기밀성이 확보되지 않는다. 결국 두 사설망을 하나처럼 연결하면서도 공용 구간에서 안전하게 보호할 수단이 필요하다.

#2핵심 질문

값비싼 전용선 없이 공용 인터넷 위에서 두 사이트의 사설망 트래픽에 기밀성과 무결성을 보장하며 하나의 망처럼 연결하려면 어떻게 구성해야 하는가?

#3동작 예시

본사 라우터와 지사 라우터에 IKEv2 기반 IPsec 터널을 구성한다. 각 라우터에 IKEv2 proposal과 policy로 암호·해시·인증 방식을 정하고, IPsec 프로파일을 만들어 터널 인터페이스에 보호를 적용하며, 어느 트래픽을 터널로 보낼지 ACL로 지정한다. 양쪽 사설 대역 간 트래픽이 이 조건에 걸리면 자동으로 암호화되어 상대 라우터에서 복호화되고, 그 외 인터넷 트래픽은 터널을 타지 않는다.

#4동작 과정

  1. IKE 협상두 라우터가 IKEv2로 서로를 인증(사전 공유 키 또는 인증서)하고, 사용할 암호 스위트(예: SHA, AES)를 합의해 세션 키를 만든다.
  2. IPsec 보안 연결 수립합의된 키로 ESP(암호화와 무결성을 함께 제공하는 IPsec 프로토콜) 보안 연결을 세우고 터널 인터페이스에 적용한다.
  3. 트래픽 암호화 전달관심 트래픽이 터널로 들어가 암호화되어 전송되고, 반대편 라우터가 복호화해 사설망으로 전달한다.

클라우드 보안 도메인 개요와 보안 솔루션

퍼블릭·프라이빗·하이브리드 클라우드 환경에서 자산을 보호하기 위해 사용하는 보안 솔루션과 그 목적을 식별하는 영역이다.

#1문제 상황

온프레미스에서는 방화벽과 경계 장비로 트래픽을 통제하고 자산이 물리적으로 사내에 있었다. 클라우드에서는 자산이 외부 사업자 인프라에 놓이고 콘솔과 API로 원격 관리되면서, 통제할 경계 자체가 사라지고 관리자가 모든 계층을 눈으로 보기 어려워진다. 설정 한 줄이 인터넷에 자원을 노출시키고, 자격 증명 탈취나 권한 오설정이 곧바로 대규모 사고로 이어질 수 있다. 그래서 온프레미스식 단일 경계 방어로는 부족하다.

#2핵심 질문

경계가 사라진 클라우드 환경에서 자산을 지키기 위해 어떤 보안 솔루션을 어떤 목적으로 배치해야 하는가?

#3동작 예시

클라우드 계정 접근은 IAM과 MFA, 최소 권한 정책으로 통제하고, 워크로드 앞에는 로드 밸런서와 WAF를 두어 웹 공격을 걸러내며, 네트워크는 보안 그룹과 클라우드 방화벽으로 구간을 나눈다. 서버 자체는 워크로드 보호 에이전트로 지키고, 로그는 중앙으로 모아 SIEM으로 상관 분석하며, 구성 오설정은 CSPM으로 지속 점검한다. 각 솔루션이 접근·네트워크·워크로드·태세라는 서로 다른 계층을 맡는다.

#4동작 과정

  1. 자산과 접근 보호IAM, MFA, 최소 권한으로 계정과 API 접근을 통제해 자격 증명 탈취의 영향을 줄인다.
  2. 네트워크와 워크로드 보호보안 그룹·방화벽·WAF로 트래픽을 걸러내고 워크로드 보호 에이전트로 인스턴스를 지킨다.
  3. 가시성과 태세 관리로그를 모아 SIEM으로 분석하고 CSPM으로 구성 오설정을 점검해 위협과 결함을 탐지·조치한다.

퍼블릭·프라이빗·하이브리드·커뮤니티 클라우드 배포 유형과 SaaS·PaaS·IaaS 서비스 모델을 구분하는 개념이다.

→ 03-01 참조

#1문제 상황

조직마다 클라우드를 쓰는 목적과 인프라를 소유·운영하는 범위가 다르다. 누가 자원을 쓰는지, 제공자가 어디까지 관리하는지를 구분하지 않고 도입하면 각자의 책임 범위를 오해하게 된다. 배포 유형(사용 주체)과 서비스 모델(제공 범위)을 뒤섞어 이해하면 통제 지점과 보안 책임이 어디에 있는지 판단할 수 없다.

#2핵심 질문

클라우드는 누가 사용하는가와 무엇을 서비스로 제공받는가라는 두 기준으로 어떻게 구분하는가?

#3동작 예시

NIST 800-145 기준으로 보면 배포 유형은 퍼블릭(불특정 다수가 공유하는 공용 인프라), 프라이빗(단일 조직 전용), 하이브리드(둘 이상을 결합), 커뮤니티(공통 관심사를 가진 조직 그룹 전용)로 나뉜다. 서비스 모델은 가상 자원을 제공하는 IaaS, 실행 환경을 제공하는 PaaS, 완성된 애플리케이션을 제공하는 SaaS로 나뉜다. 같은 퍼블릭 클라우드라도 IaaS인지 SaaS인지에 따라 고객이 직접 관리하는 범위가 크게 달라진다.

#4동작 과정

  1. 배포 유형 구분누가 자원을 사용하고 소유하는가를 기준으로 퍼블릭·프라이빗·하이브리드·커뮤니티를 나눈다.
  2. 서비스 모델 구분제공자가 어디까지 관리하는가를 기준으로 IaaS·PaaS·SaaS를 나눈다.
  3. 책임 경계 판단선택한 조합에서 고객 관리 범위가 게스트 OS·미들웨어·애플리케이션·데이터 중 어디까지인지 정한다.

클라우드 책임 분담과 패치·보안 평가

클라우드 서비스 모델별로 고객과 제공자의 보안 책임 경계를 나누고 패치 관리와 보안 평가를 수행하는 방식이다.

→ 03-02 참조

#1문제 상황

클라우드 제공자는 물리 인프라와 하이퍼바이저 같은 아래 계층을 관리하지만, 그 위에 남는 계층은 고객이 책임져야 한다. 어디까지가 제공자 몫인지 헷갈리면 게스트 OS나 애플리케이션 패치가 누락되고, 이미지나 설정을 방치해 취약점이 쌓인다. 또 클라우드 자산의 보안 상태를 주기적으로 평가하지 않으면 오설정과 위협을 뒤늦게 발견하게 된다.

#2핵심 질문

서비스 모델별로 고객과 제공자의 보안 책임을 어떻게 나누고, 고객에게 남은 구간의 패치와 보안 평가를 어떻게 수행하는가?

#3동작 예시

IaaS에서는 고객이 게스트 OS와 그 위 미들웨어·애플리케이션을 직접 패치하고, PaaS에서는 런타임과 미들웨어를 제공자가 관리하는 대신 고객이 애플리케이션과 데이터를 책임지며, SaaS에서는 대부분을 제공자가 관리하고 고객은 계정·데이터·접근을 관리한다. 이 경계를 공유 책임 모델로 문서화한 뒤, 고객 구간은 취약점 스캔과 주기적 패치·이미지 재배포로 관리하고, 전체 태세는 CSPM과 모니터링으로 지속 점검한다. 침투 테스트가 필요하면 제공자 정책에 따라 사전 허가를 받고 수행한다.

#4동작 과정

  1. 책임 경계 확정서비스 모델별로 제공자와 고객이 각각 관리할 범위를 공유 책임 모델로 합의해 문서화한다.
  2. 패치 관리 실행고객 책임 구간의 OS·애플리케이션·이미지를 주기적으로 갱신하고, 불변 이미지를 새로 배포하는 방식으로 취약점을 줄인다.
  3. 보안 평가와 검증CSPM·취약점 스캔·모니터링으로 구성을 지속 점검하고 발견된 결함을 조치해 상태를 유지한다.

#5한 줄 요약

서비스 모델마다 고객에게 남는 책임 구간을 명확히 하고 그 구간의 패치와 보안 평가를 지속 수행하는 것

CI/CD 파이프라인·컨테이너 오케스트레이션·보안 소프트웨어 개발에 보안을 내장하는 개발 운영 문화와 개념이다.

#1문제 상황

기존 개발 방식은 개발팀이 기능을 다 만든 뒤 보안팀이 배포 직전에 검사를 맡는 순서였다. 보안 검사가 파이프라인 맨 끝에 몰려 있어 문제를 늦게 발견하고, 이미 완성된 코드를 되돌려 고치는 비용이 커진다. 그 결과 보안은 배포를 막는 병목으로 인식되고 자주 건너뛰게 된다.

#2핵심 질문

보안 검사를 개발·배포 흐름 안으로 옮겨 처음부터 안전하게 만들려면 어떻게 해야 하는가?

#3동작 예시

개발자가 코드를 커밋하면 CI 파이프라인(코드를 자동으로 빌드하고 테스트하는 흐름)이 실행된다. 이때 의존성 취약점 스캔과 정적 코드 분석이 같은 흐름 안에서 함께 돌고, 기준을 넘는 문제가 발견되면 빌드가 실패해 취약한 코드가 다음 단계로 넘어가지 못한다.

#4동작 과정

  1. 코드 작성개발자가 커밋하는 시점에 비밀 키가 섞여 들어갔는지, 의존 라이브러리에 알려진 취약점이 있는지 자동 검사가 돌아 문제를 조기에 드러낸다.
  2. 빌드·테스트CI 파이프라인이 정적 분석(소스 코드를 실행하지 않고 결함을 찾는 검사)과 동적 분석(실행 중인 애플리케이션을 시험하는 검사)을 수행해 통과한 코드만 이미지로 만든다.
  3. 배포·운영컨테이너 이미지와 실행 환경을 스캔하고 서명·권한을 확인한 뒤 배포하며, 런타임에서도 이상 행위를 계속 감시한다.

#5한 줄 요약

보안을 별도 단계가 아니라 개발부터 배포·운영까지 이어지는 파이프라인 전 과정에 내장하는 것

#1문제 상황

기존 온프레미스 환경에서는 데이터가 회사 경계 안에 모여 있고 경계의 방화벽 하나로 접근을 통제할 수 있었다. 클라우드에서는 데이터가 여러 리전과 관리형 서비스, API로 흩어지고 접근하는 주체도 사람·서비스·외부 연동으로 늘어난다. 그래서 경계만 지키는 방식으로는 데이터가 어디서 어떻게 쓰이는지 통제하기 어렵다.

#2핵심 질문

클라우드에서 애플리케이션과 데이터를 저장된 곳과 이동하는 곳 모두에서 안전하게 지키려면 무엇을 구현해야 하는가?

#3동작 예시

객체 스토리지 버킷에 파일을 저장할 때 저장 데이터 암호화(디스크에 기록된 상태로 암호를 걸어 두는 것)를 켜고, 키 관리 서비스로 암호 키를 따로 보관한다. 같은 파일을 네트워크로 주고받을 때는 전송 중 암호화(TLS 같은 통신 구간 암호화)를 적용해 경로 상에서 내용이 노출되지 않게 한다.

#4동작 과정

  1. 접근 통제사용자와 서비스에 필요한 최소 권한만 부여하고, 아이덴티티 기반 정책으로 누가 어떤 데이터에 접근하는지 규칙으로 정해 둔다.
  2. 암호화 적용데이터가 저장될 때와 이동할 때 각각 암호화를 걸고, 키는 데이터와 분리해 관리 서비스에서 다룬다.
  3. 지속 감시·보호접근 기록을 모니터링하고 이상 접근을 탐지하며, 민감 데이터는 분류해 별도의 보호 규칙을 적용한다.

#1문제 상황

클라우드 도입 초기에는 각 팀이 자기 계정의 콘솔에서 설정을 직접 바꾸기 때문에 보안 기준이 팀마다 제각각이 된다. 계정과 리소스가 늘수록 어떤 자원이 어떤 규칙으로 보호되는지 파악하기 어려워지고, 잘못된 공개 설정 하나가 전체 데이터를 노출시킬 수 있다. 이 문제는 클라우드를 어떤 배포 모델로 쓰느냐에 따라 더 커진다.

#2핵심 질문

여러 배포 모델의 클라우드에서 보안 역량을 일관되게 적용하고 정책을 중앙에서 관리하려면 어떻게 해야 하는가?

#3동작 예시

정책을 코드로 정의해 두고, 리소스를 배포할 때 그 규칙이 자동으로 검사되게 한다. 예를 들어 "스토리지 버킷은 공개 접근을 허용하지 않는다"는 규칙을 정책 파일로 선언해 두면, 이 규칙을 어기는 배포 요청은 만들어지는 순간 차단된다.

#4동작 과정

  1. 역량 식별아이덴티티 관리, 암호화, 네트워크 격리, 로깅, 취약점 관리 중 조직에 필요한 보안 기능을 먼저 정한다.
  2. 배포 모델 결정공용·전용·하이브리드·커뮤니티 클라우드 중 데이터 민감도와 규제에 맞는 형태를 고르고 그에 맞는 통제 지점을 정한다.
  3. 정책 관리정책을 중앙에서 선언적으로 정의해 모든 계정에 일괄 적용하고, 위반 여부를 자동 점검해 지속적으로 바로잡는다.

#5한 줄 요약

필요한 보안 역량을 배포 모델에 맞춰 고르고, 정책을 중앙에서 일관되게 강제해 클라우드 전체를 안전하게 유지하는 것

클라우드 로깅과 모니터링

클라우드 환경에서 로그를 수집하고 모니터링 체계를 구성해 보안 이벤트를 감시하는 방법론이다.

#1문제 상황

기존에는 문제가 생기면 해당 서버에 직접 접속해 로그 파일을 확인하면 됐다. 클라우드에서는 리소스가 필요할 때만 생성되고 삭제되며, 로그도 서비스마다 다른 위치에 따로 쌓인다. 그래서 사고가 난 뒤에 전체 흐름을 재구성하려면 여러 서비스의 로그를 각각 뒤져야 하고, 삭제된 리소스의 기록은 이미 사라졌을 수 있다.

#2핵심 질문

서비스별로 흩어진 클라우드 로그를 한곳에 모아 보안 이벤트를 실시간으로 감시하려면 어떻게 구성해야 하는가?

#3동작 예시

API 호출 감사 로그(누가 어떤 클라우드 API를 언제 호출했는지 남기는 기록)를 중앙 저장소로 모으고, 그 위에 탐지 규칙을 걸어 둔다. 예를 들어 평소 쓰지 않던 지역에서 대량의 데이터를 내려받는 호출이 발생하면 경보가 즉시 올라온다.

#4동작 과정

  1. 수집각 서비스와 계정의 로그를 중앙 로그 저장소로 모으고, 필요하면 여러 계정·리전의 기록을 한곳에 통합한다.
  2. 정규화·저장서로 다른 형식의 로그를 공통 형식으로 맞춰 분석 가능한 상태로 만들고, 보존 기간과 접근 권한을 정해 안전하게 보관한다.
  3. 탐지·대응규칙과 이상 행위 분석으로 위협을 탐지해 경보를 발생시키고, 원본 로그를 근거로 조사와 대응을 진행한다.

#5한 줄 요약

흩어진 클라우드 로그를 한곳에 모아 공통 형식으로 관리하고 이상 징후를 실시간으로 탐지하는 것

클라우드의 애플리케이션과 워크로드를 보호하기 위한 보안 개념과 원칙을 설명한다.

→ 03-05 참조

#1문제 상황

전통적인 환경에서는 네트워크 경계를 지키면 그 안의 애플리케이션은 비교적 안전하다고 봤다. 클라우드에서는 애플리케이션이 컨테이너와 서버리스 함수로 잘게 나뉘고 서로 API로 통신하기 때문에 안과 밖의 경계가 사라진다. 그래서 경계 하나를 지키는 방식으로는 개별 워크로드가 안전한지 보장할 수 없다.

#2핵심 질문

경계가 사라진 환경에서 각 애플리케이션과 워크로드 자체를 안전하게 지키려면 어떤 원칙을 적용해야 하는가?

#3동작 예시

하나의 애플리케이션이 다른 서비스의 데이터를 읽어야 할 때, 고정된 비밀 키를 코드에 넣는 대신 워크로드에 부여된 아이덴티티로 필요한 범위의 권한만 받아 접근한다. 이렇게 하면 그 워크로드가 침해되더라도 접근할 수 있는 대상이 부여된 범위로 제한된다.

#4동작 과정

  1. 최소 권한 부여각 워크로드가 실제로 필요한 자원과 동작에만 접근하도록 권한을 좁히고, 사람 계정과 서비스 계정을 분리한다.
  2. 워크로드 격리·검증컨테이너와 실행 환경을 격리하고, 배포하는 이미지와 아티팩트의 출처와 무결성을 검증한다.
  3. 런타임 감시실행 중인 워크로드의 행위를 관찰해 비정상 동작을 탐지하고 침해 시 영향을 최소화한다.

#5한 줄 요약

경계에 기대지 않고 각 워크로드에 필요한 최소 권한만 주고 그 자체를 격리·검증·감시해 지키는 것

콘텐츠 보안 도메인 개요와 웹 프록시 트래픽 리다이렉션

콘텐츠 보안(Content Security)은 웹·이메일로 오가는 트래픽을 검사하고 통제해 악성코드·피싱·데이터 유출을 막는 영역이며, 웹 프록시 트래픽 리다이렉션은 사용자 웹 요청을 WCCP·PBR·프록시 PAC·명시적 프록시 등으로 웹 보안 어플라이언스로 우회시켜 검사하게 하는 배포 기법이다.

#1문제 상황

기존에는 사용자의 웹 요청이 클라이언트에서 외부 사이트로 곧바로 나갔다. 그러면 악성코드 배포 사이트나 피싱 페이지로 향하는 요청이 그대로 통과하고, 이를 막으려면 각 PC마다 설정을 개별적으로 바꿔야 했다. 사용자와 장비가 늘수록 이 방식은 일관된 통제가 불가능에 가까워진다.

#2핵심 질문

사용자의 웹 요청을 검사 지점으로 우회시켜 모든 트래픽을 빠짐없이 검사하게 하려면 어떻게 해야 하는가?

#3동작 예시

네트워크 장비가 웹 트래픽을 인식해 웹 보안 어플라이언스로 넘기도록 리다이렉션을 설정한다. 사용자가 주소를 입력하면 그 요청은 클라이언트 설정 변경 없이 자동으로 검사 지점을 거치고, 어플라이언스가 허용·차단을 판단한 뒤에야 실제 사이트로 전달된다.

#4동작 과정

  1. 리다이렉션 설정네트워크 장비나 클라이언트 설정으로 웹 요청이 웹 보안 어플라이언스를 우회해 지나가도록 경로를 정한다.
  2. 요청 검사어플라이언스가 URL 평판, 카테고리, 악성코드·피싱 여부를 확인해 요청의 안전성을 판단한다.
  3. 허용·차단·기록안전한 요청만 실제 대상으로 전달하고 위험한 요청은 차단하며, 처리 결과를 로그로 남겨 추적과 정책 조정에 사용한다.

#5한 줄 요약

사용자 웹 트래픽을 검사 지점으로 우회시켜 모든 요청을 중앙에서 검사하고 통제하는 것

웹 프록시 ID·인증과 투명 사용자 식별

웹 프록시가 사용자 신원을 확인해 정책을 적용하는 방식으로, 명시적 인증(프록시 자체 로그인·NTLM·Kerberos·SAML)·LDAP/AD 연동과, 별도 로그인 없이 AD 에이전트나 서버 측 세션 정보로 사용자를 식별하는 투명 사용자 식별(transparent user identification)을 포함한다.

#1문제 상황

웹 프록시를 처음 도입하면 사용자별 정책을 걸 수 없다는 벽에 부딪힌다. 프록시는 요청이 어디서 왔는지는 알아도 그 요청을 누가 보냈는지는 모르기 때문에, 모든 사용자에게 같은 규칙을 적용하거나 IP 주소 단위로만 통제하게 된다.

IP 주소는 사람이 아니라 장비에 붙는다. 여러 사람이 같은 NAT 주소를 공유하면 한 명의 위반이 부서 전체 차단으로 번지고, 반대로 허용된 IP 뒤에 앉은 누구든 정책을 우회할 수 있다. 사용자를 정확히 알아야 정책도 정확해진다.

#2핵심 질문

프록시는 별도 로그인 부담 없이 어떻게 각 요청의 실제 사용자를 확인해 사용자별 정책을 적용할 수 있을까?

#3동작 예시

직원이 브라우저를 열어 사이트에 접속한다. 프록시는 사용자에게 아무것도 묻지 않고, 이미 그 사용자가 도메인에 로그인해 받아 둔 인증 정보나 서버가 들고 있는 세션 정보를 근거로 "이 요청은 김 대리"라고 판단한다. 그 판단 위에서 김 대리에게만 열린 카테고리와 시간대 정책을 그대로 적용한다.

#4동작 과정

  1. 인증 방식 선택프록시 자체 로그인, NTLM·Kerberos 같은 도메인 인증, SAML 같은 외부 인증 중 환경에 맞는 방식을 정한다. 사용자가 매번 자격 증명을 넣지 않아도 되는 방식일수록 도입 저항이 줄어든다.
  2. 사용자 저장소 연동LDAP나 Active Directory와 연결해 계정·그룹 정보를 가져온다. 그룹 정보를 가져와야 개인별이 아니라 조직 단위 정책을 만들 수 있다.
  3. 투명 사용자 식별 적용별도 로그인 없이 AD 에이전트나 서버 측 세션 정보로 사용자를 식별한다. 이 단계가 되면 사용자는 인증을 의식하지 않고, 관리자는 사용자·그룹 기준 정책과 로그를 그대로 얻는다.

#5한 줄 요약

프록시가 요청의 출처가 아니라 실제 사용자를 확인하게 해, 통제의 단위를 IP에서 사람으로 옮기는 것

이메일·웹 보안 솔루션 비교

온프레미스·하이브리드·클라우드 배포 형태에 따라 Cisco Secure Email Gateway(온프레미스 장비), Cisco Secure Email Cloud Gateway(클라우드), Cisco Secure Web Appliance(온프레미스 웹 프록시)의 구성요소·기능·장단점을 비교하는 것이다.

#1문제 상황

이메일과 웹 보안 장비를 온프레미스로만 두면, 트래픽이 회사 밖으로 나가는 순간 보호가 끊긴다. 재택·출장 사용자는 사무실 게이트웨이를 거치지 않으므로 검사 대상에서 빠지고, 회사는 지점마다 장비를 설치하고 관리해야 한다.

클라우드로 옮기면 어디서 접속하든 같은 정책을 받지만, 장비를 직접 통제하지 못하고 트래픽이 외부 서비스를 경유한다는 점이 부담이 된다. 그래서 배포 형태별 장단점을 알아야 환경에 맞게 고를 수 있다.

#2핵심 질문

온프레미스·하이브리드·클라우드 배포는 구성요소와 기능, 이점에서 각각 무엇이 다를까?

#3동작 예시

같은 웹 요청 하나를 세 환경에 넣어 본다. 온프레미스에서는 회사 경계의 Cisco Secure Web Appliance가 요청을 받아 검사한다. 하이브리드에서는 사내 사용자는 어플라이언스가, 재택 사용자는 클라우드 게이트웨이가 나눠 맡는다. 클라우드에서는 어디서 접속하든 클라우드 게이트웨이가 먼저 받아 검사한 뒤 목적지로 넘긴다.

#4동작 과정

  1. 배포 형태 확인보호할 사용자가 사내에 있는지, 재택·지점에 흩어져 있는지 먼저 본다. 사용자 위치가 곧 필요한 배포 형태를 정한다.
  2. 제품 구성요소 대응온프레미스는 Cisco Secure Email Gateway(장비형 이메일 게이트웨이)와 Cisco Secure Web Appliance(장비형 웹 프록시), 클라우드는 Cisco Secure Email Cloud Gateway(클라우드 이메일 게이트웨이)로 나눠 매핑한다. 같은 기능이 어디에서 도는지를 구분하는 것이 비교의 핵심이다.
  3. 기능·이점 비교검사 위치와 관리 부담, 확장 방식, 원격 사용자 커버리지를 기준으로 장단점을 정리한다. 이 비교가 온프레미스·하이브리드·클라우드 중 무엇을 고를지 결정하는 근거가 된다.

#5한 줄 요약

같은 보안 기능을 어디에 두고 돌리느냐에 따라 구성요소와 이점이 달라진다는 것을 비교해, 환경에 맞는 배포 형태를 고르게 하는 것

웹·이메일 보안 배포 방법

온프레미스 사용자, 하이브리드 환경, 원격 사용자를 보호하기 위해 웹·이메일 보안 솔루션을 어떤 위치에 어떤 방식(어플라이언스·클라우드 커넥터·프록시 설정 등)으로 배치하고 동작을 검증하는지 설정하는 방법이다.

#1문제 상황

보안 솔루션을 설치했는데도 사내 사용자만 보호되고 재택 사용자는 그대로 노출되는 경우가 많다. 사내 트래픽은 게이트웨이를 지나도록 강제되지만, 외부에서 노트북으로 접속하면 그 경로를 비껴가기 때문이다.

반대로 클라우드 게이트웨이를 켜 두어도 사용자 트래픽이 그쪽으로 향하도록 연결하지 않으면 아무것도 검사되지 않는다. 배포는 "설치"가 아니라 "트래픽이 실제로 검사 지점을 지나가게 만드는 일"이다.

#2핵심 질문

온프레미스·하이브리드·원격 사용자 모두의 트래픽이 보안 검사를 거치도록 어떻게 배치하고 동작을 확인할까?

#3동작 예시

사내 직원 브라우저는 프록시 설정이나 PAC(프록시 자동 구성)로 사내 어플라이언스로 향하게 한다. 재택 직원은 클라우드 커넥터나 클라우드 게이트웨이로 트래픽을 보내도록 한다. 두 경로 모두 통과 후 사용자에게 "차단됨" 페이지나 로그가 남으면, 정책이 실제로 적용되고 있다는 증거가 된다.

#4동작 과정

  1. 사용자 그룹별 경로 설계사내·하이브리드·원격을 나눠 각각 어떤 검사 지점을 지나게 할지 정한다. 경로가 정해져야 보호되지 않는 사용자가 남지 않는다.
  2. 배치와 연결 적용어플라이언스, 클라우드 커넥터, 프록시 설정 등으로 트래픽을 검사 지점으로 유도하고 정책을 내려보낸다. 이 단계에서 검사 대상 범위가 실제로 넓어진다.
  3. 동작 검증각 그룹에서 실제 접속을 시도해 차단·허용 결과와 로그를 확인한다. 검증이 통과해야 배포가 됐다고 말할 수 있다.

#5한 줄 요약

모든 사용자 그룹의 트래픽이 실제로 검사 지점을 통과하도록 배치하고 그 사실을 검증하는 것

이메일 보안 기능

이메일 게이트웨이에서 스팸 필터링, 악성코드 필터링, DLP(데이터 유출 방지), 블록리스트, 이메일 암호화 등 스팸·악성·유출 메일을 차단하고 보호하는 기능을 설정·검증하는 것이다.

#1문제 상황

이메일은 스팸·악성코드·정보 유출이 모두 한 통의 메일로 들어오는 통로다. 필터가 없으면 스팸이 받은편지함을 채우고, 첨부파일 하나로 악성코드가 실행되며, 내부 자료가 외부로 나가도 아무 흔적이 남지 않는다.

기능을 하나씩만 켜면 우회 경로가 남는다. 스팸만 걸러도 악성 첨부는 통과하고, 악성코드만 막아도 제목·본문으로 나가는 유출은 막지 못한다. 여러 기능을 함께 설정해야 빈틈이 줄어든다.

#2핵심 질문

스팸·악성코드·정보 유출 메일을 이메일 게이트웨이에서 어떻게 차단하고 보호할까?

#3동작 예시

외부에서 첨부파일이 달린 메일 한 통이 들어온다. 게이트웨이는 먼저 발신 평판과 스팸 패턴으로 스팸 여부를 판정하고, 통과한 메일에 대해서는 첨부파일을 열어 악성코드 검사를 한다. 본문·첨부가 DLP(데이터 유출 방지) 규칙에 걸리면 발송을 막거나 암호화한다.

#4동작 과정

  1. 스팸·악성코드 필터링발신 평판과 스팸 패턴으로 스팸을 걸러 내고, 남은 메일의 첨부·링크를 악성코드 검사한다. 이 단계에서 대량 스팸과 감염 파일이 대부분 차단된다.
  2. DLP와 블록리스트 적용DLP(데이터 유출 방지) 규칙으로 민감 정보가 외부로 나가는 것을 막고, 블록리스트에 올린 발신자·도메인을 차단한다. 이 단계가 유출과 반복 침입 경로를 좁힌다.
  3. 암호화와 검증필요한 메일은 암호화해 전송하고, 실제 발송·차단 결과와 로그를 확인한다. 검증까지 해야 각 기능이 동작한다고 확신할 수 있다.

#5한 줄 요약

스팸·악성코드·정보 유출을 각각 다른 필터로 막고 그 결과를 검증해 이메일 통로의 빈틈을 줄이는 것

Cisco Umbrella SIG와 웹 보안 기능

Cisco Umbrella Secure Internet Gateway(SIG)에서 블록리스트, URL 필터링, 악성코드 스캔, URL 카테고리 분류, 웹 애플리케이션 필터링, TLS 복호화 등 클라우드 기반 웹 보안 기능을 설정·검증하는 것이다.

#1문제 상황

사용자가 회사 밖으로 나가면 웹 보안 검사가 그대로 우회된다. 사내 프록시를 거치지 않고 바로 인터넷에 붙으면 URL 필터도 악성코드 스캔도 적용되지 않아, 재택·지점 사용자가 그대로 위험에 노출된다.

게다가 요즘은 대부분의 트래픽이 HTTPS로 암호화되어 있어, 내용을 보지 않고서는 악성 다운로드인지 정상 트래픽인지 구분할 수 없다. 클라우드에서 이 검사를 대신해야 할 필요가 생긴다.

#2핵심 질문

클라우드 기반 보안 게이트웨이에서 URL·악성코드·애플리케이션·암호화 트래픽을 어떻게 검사할까?

#3동작 예시

재택 직원이 브라우저로 파일을 내려받는다. 트래픽은 사내 장비가 아니라 Cisco Umbrella Secure Internet Gateway(SIG, 클라우드 보안 게이트웨이)를 먼저 지난다. SIG는 접속하려는 URL의 카테고리를 확인하고, 다운로드된 파일을 악성코드로 스캔하며, 필요한 경우 HTTPS 세션을 복호화해 내용까지 검사한 뒤 허용 또는 차단을 결정한다.

#4동작 과정

  1. URL 분류·필터링접속 URL을 카테고리로 분류하고 정책에 따라 허용·차단을 정한다. 미분류·위험 카테고리로 향하는 접속이 여기서 걸러진다.
  2. 악성코드 스캔과 앱 제어다운로드 파일을 악성코드로 검사하고, 웹 애플리케이션 필터링으로 정책에 어긋나는 앱 사용을 통제한다. 검사가 사용자 위치와 무관하게 적용된다.
  3. TLS 복호화HTTPS 트래픽을 복호화해 내용을 검사한 뒤 다시 암호화한다. 암호화에 가려졌던 위협까지 이 단계에서 드러난다.

#5한 줄 요약

사용자가 어디에 있든 클라우드 게이트웨이가 URL·파일·앱·암호화 트래픽을 검사해 웹 사용을 통제하는 것

Cisco Umbrella 구성요소와 웹 보안 제어

Cisco Umbrella 의 핵심 구성요소(DNS 리졸버·클라우드 보안 플랫폼·커넥터 등)와 그 기능·이점을 이해하고, ID(신원), URL 콘텐츠 설정, 대상 목록, 리포팅 등 Umbrella 웹 보안 제어를 구성·검증하는 것이다.

#1문제 상황

클라우드 웹 보안을 도입하려면 먼저 요청이 어디로 가서 어떻게 검사되는지 이해해야 한다. 구성요소를 모른 채 켜면 어떤 트래픽이 검사되는지, 정책이 어디서 결정되는지 파악하지 못해 제어가 되지 않는다.

또한 사용자를 구분하지 못하면 모든 사람에게 같은 규칙만 적용된다. 누가 무엇을 하는지 모르는 상태에서는 정책도 로그도 의미가 없어, 신원·대상 목록·리포팅을 함께 다뤄야 실제 통제가 된다.

#2핵심 질문

Umbrella의 구성요소 위에서 사용자별 웹 보안 제어를 어떻게 구성하고 검증할까?

#3동작 예시

사용자 PC가 특정 도메인을 조회한다. 이 요청은 Umbrella의 DNS 리졸버(DNS 질의를 대신 처리하는 서버)로 가고, 그 질의는 클라우드 보안 플랫폼에서 정책과 대조된다. 플랫폼이 그 도메인을 위험 카테고리로 판단하면 차단 응답을 돌려보내 접속이 막히고, 그 기록이 리포팅에 남는다.

#4동작 과정

  1. 구성요소 파악DNS 리졸버, 클라우드 보안 플랫폼, 커넥터 등이 각각 무엇을 담당하는지 이해한다. 어느 지점에서 검사와 정책 결정이 일어나는지 알아야 이후 설정이 맞는다.
  2. ID·URL 설정 구성신원(사용자·네트워크), URL 콘텐츠 설정, 대상 목록을 정해 누구에게 어떤 카테고리를 허용·차단할지 정한다. 이 단계에서 정책이 사람과 목적지 단위로 구체화된다.
  3. 적용과 리포팅 검증설정을 적용한 뒤 차단·허용 결과와 리포팅을 확인한다. 로그가 의도대로 남아야 제어가 동작한다고 볼 수 있다.

#5한 줄 요약

Umbrella의 DNS·클라우드 구성요소 위에서 신원과 목적지 기준 정책을 세우고 리포팅으로 그 동작을 확인하는 것

엔드포인트 도메인 개요와 EPP vs EDR

EPP는 알려진 시그니처 기반으로 감염 전 차단에 집중하는 예방 플랫폼이고, EDR은 엔드포인트에서 일어나는 행위를 지속적으로 수집·분석해 침해 후 탐지·대응까지 담당하는 솔루션이다.

#1문제 상황

전통적인 백신 프로그램은 이미 알려진 악성코드의 서명(시그니처) 목록을 내려받아 파일과 대조하는 방식으로 동작한다. 이 방식은 목록에 있는 위협은 잘 막지만, 처음 등장한 악성코드나 목록에 없는 변종은 실행되기 전까지 알아보지 못한다.

또한 파일 검사만으로는 정상 프로그램을 악용해 메모리에서만 동작하는 공격을 잡아내기 어렵다. 그래서 감염을 막는 예방 기능과, 이미 뚫린 뒤라도 행위를 관찰해 찾아내는 탐지 기능을 각각 구분해서 운영할 필요가 생겼다.

#2핵심 질문

감염을 막는 예방 기능과 침해 이후의 탐지·대응 기능을 어떻게 역할로 나누어 운영해야 하는가?

#3동작 예시

사내 PC에서 문서 편집기가 정상적으로 실행되다가, 갑자기 시스템 폴더의 여러 파일을 연속으로 덮어쓰기 시작한다고 하자. EPP는 이 실행 파일이 알려진 악성 시그니처와 일치하는지 보고 정상 서명 파일이면 통과시킨다. 반면 EDR은 "문서 편집기가 시스템 폴더를 대량 수정한다"는 행위 패턴 자체를 이상 신호로 기록하고 경보를 올린다. 같은 장면을 두 제품이 서로 다른 근거로 판단한다.

#4동작 과정

  1. 시그니처 대조EPP 에이전트가 파일이 실행되거나 저장되는 시점에 알려진 악성코드 서명 목록과 대조하고, 일치하면 실행 전에 차단한다. 그래서 아직 감염되지 않은 상태가 유지된다.
  2. 행위 수집EDR 에이전트가 프로세스 생성, 파일 쓰기, 네트워크 연결 같은 엔드포인트 행위를 계속 기록해 중앙으로 보낸다. 그래서 엔드포인트에서 실제로 무슨 일이 있었는지 시간순으로 남는다.
  3. 분석·대응수집된 행위를 규칙과 분석 모델에 대조해 이상 징후를 찾아내고, 감염 의심 장치를 격리하거나 프로세스를 종료하도록 지시한다. 그래서 시그니처에 없던 위협도 사후에 잡아낸다.

Cisco Secure Endpoint와 아웃브레이크 제어·격리

Cisco Secure Endpoint(구 AMP for Endpoints)로 엔드포인트에 안티멀웨어 보호를 구성하고, 감염 확산 시 아웃브레이크 제어와 엔드포인트 격리로 감염을 제한한다.

#1문제 상황

엔드포인트 안티멀웨어는 각 장치에 에이전트를 설치해 파일을 검사하는 방식으로 동작한다. 그런데 관리자가 장치마다 정책을 따로 배포하면 설정이 제각각이 되고, 어떤 장치에 어떤 보호가 켜져 있는지 파악하기 어려워진다.

더 큰 문제는 한 장치가 감염됐을 때다. 감염된 장치가 사내 네트워크에 그대로 연결돼 있으면 같은 악성코드가 옆 장치로 퍼져 나가고, 보안팀이 대응하는 동안에도 확산은 계속된다.

#2핵심 질문

감염이 확인된 순간 확산을 어떻게 즉시 멈추고 피해 범위를 제한할 수 있는가?

#3동작 예시

여러 대의 PC가 중앙 콘솔에서 정책을 받아 안티멀웨어 검사를 수행한다고 하자. 한 PC에서 악성코드가 탐지되면 콘솔에 해당 장치와 실행 파일 이름이 표시된다. 관리자는 그 장치를 격리 대상으로 지정하고, 콘솔에서 실행 중인 프로세스를 종료시키는 명령을 내린다. 다른 장치들은 계속 정상 통신하지만 감염된 장치만 통신이 차단된다.

#4동작 과정

  1. 정책 배포콘솔에서 안티멀웨어 검사·실행 차단 정책을 한 번 만들면 등록된 모든 엔드포인트 에이전트에 내려간다. 그래서 장치마다 일관된 보호 설정이 유지된다.
  2. 탐지 보고에이전트가 파일 검사와 행위 관찰로 위협을 찾아내면 감염 파일·프로세스 정보를 콘솔로 보고한다. 그래서 어떤 장치에서 무슨 위협이 확인됐는지 한눈에 보인다.
  3. 아웃브레이크 제어와 격리콘솔에서 해당 장치를 격리(다른 네트워크와의 통신을 끊고 관리 연결만 유지)하거나 프로세스를 종료하도록 지시한다. 그래서 감염이 옆 장치로 번지기 전에 범위가 묶인다.

#5한 줄 요약

중앙 콘솔로 엔드포인트 보호 정책을 일괄 적용하고, 감염이 확인되면 격리와 프로세스 종료로 확산을 즉시 제한하는 것

엔드포인트 기반 보안의 근거

네트워크 경계가 흐려진 환경에서 실제 위협이 실행되는 지점이 엔드포인트이므로, 파일·프로세스·행위 수준의 가시성과 차단을 위해 엔드포인트 기반 보안이 필요하다는 정당성을 설명한다.

#1문제 상황

예전에는 네트워크 경계에 방화벽을 두고 바깥에서 들어오는 트래픽을 걸러내면 내부는 안전하다고 봤다. 하지만 사용자가 재택근무로 집에서 접속하고, 업무 시스템이 클라우드로 옮겨 가면서 트래픽이 사내 경계를 지나지 않는 경우가 늘었다.

게다가 공격자는 이메일 첨부, 악성 문서, 정상 프로그램 악용 같은 방법으로 보안 경계 안쪽에 이미 들어온 상태에서 위협을 실행한다. 경계 장비는 암호화된 트래픽이나 내부에서 시작된 행위를 다 볼 수 없으므로, 실제로 위협이 실행되는 지점을 따로 봐야 한다.

#2핵심 질문

경계가 지켜 주지 못하는 상황에서 위협이 실제 실행되는 지점을 어떻게 관찰하고 막을 것인가?

#3동작 예시

직원이 외부에서 받은 문서를 열었는데 그 문서가 매크로를 실행해 정상 프로그램 권한으로 시스템 정보를 수집하고 외부로 전송한다고 하자. 이 통신은 사내 서버를 거치지 않고 직원 PC에서 바로 나가므로 경계 방화벽에는 잡히지 않는다. 엔드포인트에 설치된 보호 에이전트는 문서가 매크로를 실행하고 프로세스가 네트워크에 연결하는 일련의 흐름을 그 장치 안에서 관찰해 차단할 수 있다.

#4동작 과정

  1. 실행 지점 관찰엔드포인트 에이전트가 파일·프로세스·행위를 그 장치 안에서 직접 본다. 그래서 트래픽이 사내 경계를 지나든 안 지나든 상관없이 위협 실행 장면이 잡힌다.
  2. 행위 기준 판단무슨 파일인지뿐 아니라 어떤 프로세스가 어떤 순서로 무슨 동작을 하는지로 판단한다. 그래서 시그니처가 없어도 정상과 다른 흐름을 이상 징후로 구분한다.
  3. 차단·기록기준을 벗어난 실행이나 연결을 그 자리에서 막고 무슨 일이 있었는지 기록을 남긴다. 그래서 경계를 우회한 위협에도 대응 근거가 확보된다.

#5한 줄 요약

네트워크 경계를 우회해 엔드포인트에서 직접 실행되는 위협을 파일·프로세스·행위 수준에서 관찰하고 차단하는 것

엔드포인트 장치 관리와 자산 인벤토리 — MDM

MDM(Mobile Device Management)으로 등록·관리되는 모든 엔드포인트 장치를 인벤토리로 파악하고 정책을 배포함으로써, 어떤 자산이 존재하고 어떤 상태인지 통제하는 것의 가치를 설명한다.

#1문제 상황

조직에 노트북, 데스크톱, 태블릿, 스마트폰이 섞여 늘어나면 어떤 장치가 사내 자원에 접속하는지 목록조차 없어지는 경우가 많다. 장치를 수기 표나 개별 담당자 기억에 의존해 관리하면, 새 장치가 등록되지 않은 채 접속하거나 퇴사자 장치가 그대로 남아도 알아채기 어렵다.

또한 장치마다 보안 설정을 사람이 하나씩 맞추면 빠뜨리는 곳이 생기고, 어떤 장치가 최신 상태인지 확인할 방법이 없다. 자산을 파악하지 못하면 그 자산을 보호하고 있다고 말할 수 없다.

#2핵심 질문

조직이 관리하는 엔드포인트 장치가 무엇이고 어떤 상태인지 어떻게 일관되게 파악하고 통제할 것인가?

#3동작 예시

관리자가 새 노트북을 지급할 때 MDM(Mobile Device Management, 여러 장치를 중앙에서 등록·설정하는 관리 시스템) 등록 절차를 거친다고 하자. 이때 장치가 인벤토리에 자동으로 등록되고, 화면 잠금, 암호화, 필수 앱 설치 같은 정책이 함께 내려간다. 이후 관리자는 콘솔 목록에서 전체 장치 대수와 모델, 정책 적용 여부를 한 화면에서 확인한다.

#4동작 과정

  1. 등록장치가 MDM에 등록되면 고유 식별 정보와 모델, 운영체제 같은 속성이 인벤토리에 기록된다. 그래서 어떤 자산이 존재하는지 목록이 만들어진다.
  2. 정책 배포콘솔에서 정한 보안 설정과 필수 앱 설치 규칙이 등록된 장치에 일괄 적용된다. 그래서 장치마다 설정이 제각각이 되는 일이 줄어든다.
  3. 상태 감시장치가 정책을 지키고 있는지, 분실·퇴사 등으로 관리 대상에서 빼야 하는지 중앙에서 확인하고 조치한다. 그래서 통제 밖 장치를 목록에서 걸러낼 수 있다.

#5한 줄 요약

등록된 모든 엔드포인트를 인벤토리로 파악하고 정책을 일괄 배포해, 조직이 어떤 자산을 어떤 상태로 통제하는지 명확히 하는 것

MFA 전략

비밀번호 하나만으로는 계정 탈취를 막을 수 없으므로 지식·소유·생체 등 서로 다른 두 가지 이상의 인증 요소를 요구하는 다중 인증(MFA) 전략의 용도와 중요성을 설명한다.

#1문제 상황

계정 보호를 비밀번호 하나에만 맡기면, 사용자가 여러 사이트에 같은 비밀번호를 쓰다가 한 곳이 유출될 때 다른 계정까지 함께 뚫린다. 비밀번호는 재사용, 추측, 피싱 페이지 입력 등으로 공격자 손에 들어가기 쉽고, 한번 새어 나가면 그 자체로는 더 이상 신뢰할 근거가 되지 못한다.

비밀번호를 자주 바꾸라고 강제하는 방식도 사용자의 불편만 늘릴 뿐 유출 자체를 막지 못한다. 결국 비밀번호가 새더라도 그것만으로 로그인이 끝나지 않게 하는 별도의 장치가 필요하다.

#2핵심 질문

비밀번호가 유출되더라도 공격자가 그 계정으로 로그인하지 못하게 하려면 무엇을 더 확인해야 하는가?

#3동작 예시

사용자가 아이디와 비밀번호를 입력해 로그인을 시도한다고 하자. 서버는 비밀번호가 맞아도 곧바로 로그인을 허용하지 않고, 등록된 스마트폰 앱으로 승인 요청을 보낸다. 사용자가 그 앱에서 승인을 눌러야 로그인이 완료되고, 공격자가 비밀번호만 알아낸 경우에는 승인 단계를 통과하지 못해 실패한다.

#4동작 과정

  1. 1차 요소 확인사용자가 아는 정보(비밀번호나 PIN)를 입력한다. 그래서 본인만 아는 첫 번째 근거가 확인된다.
  2. 2차 요소 확인사용자가 가진 것(등록된 휴대폰 앱, 보안 키)이나 사용자 자신(지문 같은 생체 정보)으로 추가 확인을 요구한다. 그래서 비밀번호만으로는 통과할 수 없는 두 번째 근거가 더해진다.
  3. 서로 다른 요소 조합 판정지식·소유·생체 가운데 서로 다른 종류를 두 가지 이상 통과했을 때만 로그인을 허용한다. 그래서 한 요소가 유출돼도 계정 탈취로 이어지지 않는다.

#5한 줄 요약

비밀번호 하나가 유출되더라도 서로 다른 종류의 인증 요소를 두 가지 이상 요구해 계정 탈취를 막는 것

엔드포인트 포스처 평가

접속 시점에 엔드포인트의 OS·백신·패치·암호화 등 보안 상태(포스처)를 검사하여 기준을 충족한 장치만 네트워크 접근을 허용하는 포스처 평가 솔루션을 설명한다.

#1문제 상황

장치가 사내 네트워크에 접속할 때 사용자 인증만 통과하면 곧바로 내부 자원을 쓰게 하는 방식이 흔하다. 이 경우 접속한 장치의 운영체제가 최신 보안 패치를 적용했는지, 안티멀웨어가 켜져 있는지, 디스크가 암호화됐는지는 확인하지 않는다.

그래서 보안이 허술한 장치 하나가 내부망에 들어와 전체의 약한 고리가 된다. 사용자가 맞는지만 봤기 때문에, 그 사용자가 쓰는 장치의 상태는 통제 밖에 남는다.

#2핵심 질문

네트워크에 접속하려는 장치가 실제로 안전한 상태인지 어떻게 확인하고 기준 미달 장치를 걸러낼 것인가?

#3동작 예시

직원 노트북이 사내 네트워크에 접속을 시도한다고 하자. 접속 과정에서 시스템이 그 장치의 운영체제 버전, 보안 패치 적용 여부, 안티멀웨어 실행 상태, 디스크 암호화 여부를 확인한다. 기준을 모두 충족하면 정상 접근을 허용하고, 패치가 빠져 있으면 격리 구역에만 연결해 패치를 받게 한 뒤 다시 평가한다.

#4동작 과정

  1. 상태 수집접속 시점에 장치의 운영체제·패치·백신·암호화 같은 보안 상태 정보를 장치에서 읽어 온다. 그래서 사용자 신원과 별개로 장치 자체의 현재 상태가 드러난다.
  2. 정책 대조수집한 상태를 조직이 정한 기준(포스처 정책)과 비교한다. 그래서 어떤 장치가 기준을 충족하고 어떤 장치가 미달인지 판정된다.
  3. 접근 제어기준 충족 장치는 정상 네트워크 접근을 허용하고, 미달 장치는 패치·백신 설치만 가능한 제한 구역으로 돌린다. 그래서 안전하지 않은 장치가 내부 자원에 도달하지 못한다.

#5한 줄 요약

접속 시점에 장치의 보안 상태를 검사해, 정해진 기준을 충족한 장치만 네트워크 접근을 허용하는 것

엔드포인트 패칭 전략

공격자에게 악용되는 취약점을 줄이기 위해 OS·애플리케이션·펌웨어 패치를 정기적으로 식별·적용·검증하는 엔드포인트 패칭 전략의 중요성을 설명한다.

#1문제 상황

엔드포인트(사용자가 직접 쓰는 PC·노트북·서버)는 OS, 브라우저, 문서 뷰어, 펌웨어 등 수많은 소프트웨어 조각으로 이루어져 있다. 새 취약점이 공개되면 공격자는 아직 고치지 않은 장치를 골라 침투를 시도하고, 한 대가 뚫리면 내부 네트워크 전체가 노출된다.

이전에는 관리자가 각 장치를 직접 찾아다니며 수동으로 업데이트를 설치했다. 장치 수가 늘고 원격 근무가 늘면서 어떤 장치가 어떤 버전을 쓰는지 파악조차 어려워졌고, 패치되지 않은 장치가 계속 남아 공격 표면이 줄지 않았다.

#2핵심 질문

취약점이 공개된 뒤 얼마나 빨리, 어떤 장치에, 어떤 패치를 적용했는지 확인하고 빠짐없이 최신 상태로 유지하려면 어떻게 해야 하는가?

#3동작 예시

한 사무실 PC에서 오래된 PDF 뷰어 취약점이 알려졌다고 하자. 패칭 시스템이 이 PC의 소프트웨어 목록을 수집해 취약한 버전임을 확인하고, 해당 뷰어의 최신 버전을 자동으로 내려받아 설치한다. 관리자는 대시보드에서 "취약 버전 3대 중 3대 패치 완료"를 확인한다.

#4동작 과정

  1. 자산·버전 식별엔드포인트에 설치된 OS·애플리케이션·펌웨어 버전을 주기적으로 수집해 목록을 만든다. 그래야 어떤 장치가 위험한지 알 수 있다.
  2. 패치 판단과 배포수집된 버전과 공개된 취약점 정보를 비교해 필요한 패치를 고르고, 정책에 따라 자동 또는 승인 후 배포한다. 한 번에 전체를 밀지 않고 단계적으로 적용해 문제를 줄인다.
  3. 적용 검증과 재확인설치가 끝나면 실제 버전이 올라갔는지 확인하고, 실패하거나 미적용된 장치는 목록에 남겨 다시 처리한다. 그 결과 패치되지 않은 장치가 남지 않는다.

#5한 줄 요약

공격에 악용될 수 있는 취약점을 줄이기 위해 엔드포인트의 패치 상태를 지속적으로 파악하고 빠짐없이 최신으로 유지하는 관리 체계

보안 네트워크 접속 도메인 개요와 ID 관리

게스트 서비스·프로파일링·자세 평가·BYOD 같은 개념으로 사용자와 장치의 신원을 확인하고 적절한 접속 권한을 부여하는 보안 네트워크 접속의 기반 영역이다.

#1문제 상황

전통적인 네트워크는 스위치 포트에 케이블을 꽂으면 그대로 연결을 허용했다. 누가 접속했는지, 어떤 장치인지, 안전한 상태인지 확인할 방법이 없었고, 한 번 연결되면 내부 자원에 거의 제한 없이 접근할 수 있었다.

무선과 개인 장치(BYOD)가 늘면서 문제는 커졌다. 사내 장치와 외부인 장치, 손님 장치가 같은 망에 섞이면 감염된 장치 하나가 전체에 피해를 준다. 접속 자체를 신원과 장치 상태 기준으로 통제할 필요가 생겼다.

#2핵심 질문

네트워크에 접속하려는 사용자와 장치가 누구인지 확인하고, 그 신원과 장치 상태에 맞는 권한만 주려면 어떻게 해야 하는가?

#3동작 예시

직원이 노트북을 사내 Wi-Fi에 연결하면, 먼저 사용자 계정으로 로그인하게 한다. 이어서 장치 프로파일링이 노트북의 종류와 OS를 인식하고, 자세 평가(posture assessment — 백신 실행 여부·OS 패치 상태 같은 보안 조건을 점검하는 절차)를 통과하는지 확인한다. 통과하면 사내 서버 접근 권한을, 통과하지 못하면 인터넷만 되는 제한망을 부여한다.

#4동작 과정

  1. 신원 확인사용자 계정과 장치 정보를 인증 서버로 보내 누구인지 확인한다. 게스트는 별도 등록 절차를 거쳐 손님용 권한을 받는다.
  2. 장치 파악과 상태 점검프로파일링(장치 종류·OS·제조사 등을 식별하는 과정)으로 장치를 분류하고, 자세 평가로 보안 조건 충족 여부를 검사한다. 그래서 같은 사용자라도 장치 상태에 따라 다른 취급을 받는다.
  3. 권한 부여확인 결과에 따라 사내망·제한망·게스트망 같은 접속 등급을 정하고 그에 맞는 접근 권한을 준다. 결과적으로 자격과 상태에 맞는 자원만 열린다.

#5한 줄 요약

접속하는 사용자와 장치의 신원과 상태를 확인해 각자에게 맞는 권한만 부여함으로써 네트워크를 안전하게 개방하는 것

네트워크 접속 제어 — 802.1X·MAB·WebAuth

802.1X·MAB·WebAuth 같은 접속 제어 메커니즘으로 유선·무선 네트워크에 접속하는 장치의 인증과 인가를 구성·검증하는 방법이다.

#1문제 상황

스위치 포트나 무선 AP에 장치를 연결하면 별도 인증 없이 바로 통신이 가능했다. 인증이 없으니 허가되지 않은 노트북, 임의의 공유기, 공격자 장치도 사내망에 들어올 수 있었다.

모든 장치에 인증을 요구하면 편의성이 떨어지므로 장치 종류에 맞는 여러 접속 방식이 필요해졌다. 그래서 인증을 지원하는 장치용 방식, 지원하지 않는 장치용 방식, 사용자가 직접 로그인하는 방식이 나뉘어 쓰인다.

#2핵심 질문

장치와 사용자를 인증해 유선·무선 접속을 허가하되, 인증 기능이 없는 장치와 임시 사용자까지 어떻게 다룰 것인가?

#3동작 예시

인증을 지원하는 노트북을 스위치 포트에 꽂으면 스위치는 802.1X(포트 기반 인증 표준 — 접속 장치에게 자격 증명을 요구하는 방식)로 사용자 인증을 요청하고, 인증 서버가 승인하면 포트가 열린다. 반면 인증을 못 하는 프린터는 MAC 주소를 미리 등록해 두는 MAB(MAC 주소 기반 인증 — 장치 고유 주소로 식별)로 통과시키고, 손님 노트북은 브라우저 로그인 창을 띄우는 WebAuth로 임시 접속을 허용한다.

#4동작 과정

  1. 접속 시도 감지장치가 포트나 무선에 연결되면 스위치·AP가 이를 감지하고 인증 절차를 시작한다. 이때 어떤 인증 방식을 쓸지 장치 특성에 따라 정해진다.
  2. 자격 증명 수집과 검증802.1X는 사용자 자격 증명을, MAB는 MAC 주소를, WebAuth는 웹 로그인 정보를 인증 서버로 보내 검증한다. 서버는 등록된 정보와 대조해 승인 여부를 판단한다.
  3. 포트 개방과 권한 적용검증이 끝나면 스위치가 포트를 열고 정해진 VLAN이나 접근 권한을 적용한다. 실패하면 포트는 닫히거나 제한망에 머문다.

장치와 사용자를 상황에 맞는 인증 방식으로 검증해 허가된 대상만 네트워크에 접속시키는 것

CoA를 이용한 네트워크 접속

CoA(Change of Authorization)로 이미 인증된 세션의 권한을 재인증 없이 동적으로 변경하는 네트워크 접속 제어 방식이다.

#1문제 상황

한 번 인증에 성공한 세션은 접속을 끊고 다시 인증하기 전까지 같은 권한을 유지했다. 그래서 로그인 후 장치가 감염되거나 정책 위반이 발견돼도 즉시 권한을 회수하기 어려웠고, 관리자가 개입하려면 세션을 강제로 끊는 수밖에 없었다.

세션을 끊으면 사용자는 작업을 처음부터 다시 해야 했다. 보안 정책을 바꾸려면 많은 사용자의 접속이 일시에 끊기는 불편이 따랐다. 재인증 없이 권한만 바꿀 수 있는 방법이 필요했다.

#2핵심 질문

이미 인증된 세션을 끊지 않고도 보안 상태 변화에 따라 권한을 즉시 바꾸려면 어떻게 해야 하는가?

#3동작 예시

자세 평가를 통과해 사내망에 접속한 노트북에서 백신이 꺼진 것이 탐지됐다고 하자. 인증 서버는 CoA(Change of Authorization — 이미 허가된 세션의 권한을 바꾸는 메시지)를 스위치에 보내, 세션을 끊지 않고 그 포트만 제한망으로 옮긴다. 사용자는 연결을 유지한 채 인터넷만 쓸 수 있고, 백신을 다시 켜면 CoA로 원래 권한이 복구된다.

#4동작 과정

  1. 상태 변화 탐지접속 후에도 장치 상태나 정책 위반 여부를 계속 감시하고, 문제가 발견되면 인증 서버가 알림을 받는다.
  2. 권한 변경 지시 전송서버가 네트워크 장치에 CoA 요청을 보내 해당 세션에 적용할 새 권한을 지정한다. 이때 세션은 유지된 채 속성만 바뀐다.
  3. 새 권한 즉시 적용스위치·AP가 그 세션에 새 권한(VLAN·접근 목록 등)을 적용하고 사용자는 재로그인 없이 바뀐 권한으로 계속 작업한다. 결과적으로 위험은 즉시 차단되고 편의는 유지된다.

또한 어떤 애플리케이션이 오가는지 통제하지 않으면 업무와 무관한 도구나 위험한 프로그램이 자유롭게 사용됐다. 장치 상태 확인과 애플리케이션 통제를 접속 단계에서 묶어야 할 필요가 생겼다.

#2핵심 질문

접속하는 장치가 보안 정책을 지키는지 확인하고 허용된 애플리케이션만 쓰도록 하면 무엇이 나아지는가?

#3동작 예시

A 장치가 OS 보안 업데이트를 최신으로 유지하고 회사가 허용한 업무 앱만 설치한 상태라면 컴플라이언스(정책 준수) 판정을 통과해 사내 자원에 접근한다. 반대로 정책을 어긴 B 장치는 자세 평가에서 걸려 제한망에 머물고, 위험한 앱이 탐지되면 그 앱의 통신이 차단된다.

#4동작 과정

  1. 장치 상태 평가접속 장치의 패치 수준, 백신 상태, 설정을 점검해 정책 준수 여부를 판정한다. 그래서 안전한 장치만 신뢰 등급을 얻는다.
  2. 애플리케이션 식별과 통제오가는 애플리케이션을 인식해 허용·차단 목록과 비교하고, 위험하거나 금지된 앱의 트래픽을 막는다. 그래서 승인된 앱만 실제로 동작한다.
  3. 결과에 따른 권한 적용준수 장치에는 필요한 자원을 열고, 미준수 장치는 제한하거나 교정 조치를 안내한다. 결과적으로 침해 위험이 줄고 정책이 일관되게 지켜진다.

유출 기법

DNS 터널링·HTTPS·이메일·FTP/SSH/SCP/SFTP·ICMP·메신저·IRC·NTP 등 정상 트래픽에 위장해 데이터를 외부로 빼내는 기법들이다.

#1문제 상황

방화벽과 보안 장비는 대개 정상적인 통신을 막지 않는다. 공격자는 이 점을 이용해 데이터를 일반 트래픽처럼 위장해 외부로 빼낸다. 그래서 겉으로 보면 평범한 트래픽인데도 안에 중요한 정보가 실려 나가는 일이 생긴다.

가장 흔히 쓰이는 경로가 웹, DNS, 이메일, 파일 전송, 메신저 등 이미 허용된 서비스다. 이 통로들은 업무에 꼭 필요해 다 막을 수 없고, 그 틈으로 데이터가 조금씩 새어 나가도 눈에 잘 띄지 않는다.

#2핵심 질문

허용해야 하는 정상 서비스의 틈을 이용해 데이터를 몰래 빼내는 행위를 어떻게 알아채고 막을 것인가?

#3동작 예시

감염된 PC가 중요한 파일을 조각내어 DNS 질의 이름에 실어 보낸다고 하자. DNS 터널링(이름 조회 트래픽에 데이터를 숨겨 주고받는 기법)에 해당하며, 조회가 비정상적으로 길고 잦으면 보안 장비가 이를 탐지한다. 마찬가지로 HTTPS·이메일·FTP/SSH/SCP/SFTP·ICMP·메신저·IRC·NTP 같은 정상 프로토콜에 데이터를 실어 보내는 방식도 각각 탐지 대상이 된다.

#4동작 과정

  1. 정상 트래픽 기준 설정각 프로토콜의 정상적인 사용량·크기·빈도를 파악해 기준선을 만든다. 그래야 이상한 패턴이 드러난다.
  2. 이상 패턴 탐지평소와 다른 크기, 빈도, 조회 길이를 보이는 흐름을 찾아낸다. 예컨대 짧은 시간에 대용량이 나가거나 DNS 질의가 비정상적으로 길면 의심한다.
  3. 차단과 조사의심 흐름을 막고 관련 호스트를 격리해 추가 유출을 막는다. 그 결과 데이터가 외부로 빠져나가는 통로가 좁아진다.

#5한 줄 요약

허용된 정상 서비스에 위장해 데이터를 빼내는 흐름을 패턴으로 탐지하고 차단하는 것

네트워크 텔레메트리의 이점

네트워크 장치와 트래픽에서 실시간 측정 데이터를 수집·분석해 가시성과 위협 탐지 능력을 높이는 것의 이점이다.

#1문제 상황

예전에는 장애나 침해가 터진 뒤에야 관리자가 장비에 직접 접속해 로그를 하나씩 열어 원인을 찾았다. 이 방식은 문제가 이미 벌어진 뒤에야 알 수 있고, 수집 주기도 몇 분 단위라 그 사이에 무슨 일이 있었는지 알 수 없다. 게다가 장비마다 로그 형식이 제각각이라 여러 장비에서 일어난 일을 하나로 이어 붙여 보기도 어렵다.

#2핵심 질문

네트워크에서 벌어지는 일을 실시간으로 계속 관찰해 위협과 장애를 더 빨리 알아채려면 어떻게 해야 하는가?

#3동작 예시

스위치가 트래픽 양, 연결 상태, 라우팅 변화, 인터페이스 오류 같은 측정값을 일정한 간격으로 계속 내보낸다. 수집 서버는 이 값을 시간 순서대로 쌓아 두고, 특정 구간의 트래픽이 갑자기 치솟거나 평소와 다른 흐름이 나타나면 즉시 그래프와 경보로 드러낸다.

#4동작 과정

  1. 측정값 내보내기네트워크 장치가 트래픽 양·연결 상태·오류 같은 상태를 정해진 주기로 스트리밍(연속 전송) 방식으로 내보낸다. 몇 분마다 한 번 물어보는 방식과 달리 변화가 생기면 거의 바로 전달된다.
  2. 수집과 저장수집 서버가 여러 장치에서 온 값을 한곳에 모아 시간 순서로 저장한다. 장치가 달라도 같은 기준으로 비교할 수 있게 형식이 통일된다.
  3. 분석과 경보저장된 값을 평소 패턴과 견주어 이상한 흐름을 찾아내고 경보를 띄운다. 관리자는 문제가 커지기 전에 어느 장치·어느 구간에서 무슨 일이 벌어지는지 확인할 수 있다.

#5한 줄 요약

네트워크 장치의 측정값을 실시간으로 모아 분석해, 문제가 커지기 전에 가시성과 위협 탐지 능력을 확보하는 것

#1문제 상황

방화벽과 침입 차단 장비는 각자 정해진 규칙에 걸리는 트래픽만 막아 준다. 그래서 규칙에 걸리지 않으면서 오랫동안 조금씩 정보를 빼 가는 행위나, 평소에 없던 새 연결이 슬금슬금 늘어나는 변화는 놓치기 쉽다. 사내망과 클라우드가 섞이면 트래픽을 한눈에 보기도 어려워, 어디서 이상한 흐름이 시작됐는지 찾기 힘들다.

#2핵심 질문

규칙에 걸리지 않는 이상 행위를 네트워크와 클라우드 트래픽 흐름에서 찾아내려면 어떻게 해야 하는가?

#3동작 예시

사내 서버가 밤마다 외부의 낯선 주소로 일정한 양의 데이터를 보내기 시작한다고 하자. 규칙 기반 장비는 이 연결을 정상으로 통과시키지만, 흐름을 기준으로 평소와 다른 패턴을 학습한 분석 제품은 이 새로운 관계를 이상 신호로 표시하고 어느 호스트가 관여했는지 보여 준다.

#4동작 과정

  1. 흐름 수집네트워크 장치와 클라우드 환경에서 누가 누구와 언제 얼마나 통신했는지 나타내는 흐름 정보를 모은다. 패킷 전체가 아니라 통신의 요약이므로 대규모 트래픽도 부담이 적다.
  2. 행위 기준선 학습모은 흐름으로 평소의 정상 패턴을 기준선(보통 상태)으로 만들어 둔다. 각 호스트·서비스가 어떤 상대와 어떻게 통신하는지가 기준이 된다.
  3. 이상 탐지와 조사기준선에서 벗어난 흐름을 이상으로 표시하고 관련 호스트와 경로를 한 화면에 보여 준다. 관리자는 규칙에 걸리지 않은 위협도 흐름 단위로 추적할 수 있다.

#1문제 상황

한 조직이 방화벽, 접속 제어, 침입 탐지, 위협 분석 제품을 각각 따로 운영하면, 한 제품이 알아낸 정보가 다른 제품에 전달되지 않는다. 그래서 침입 탐지 장비가 의심스러운 단말을 발견해도 접속 제어 장비는 그 사실을 모른 채 계속 접속을 허용한다. 제품마다 정책을 따로 입력해야 하니 같은 내용을 여러 번 설정하게 되고, 대응도 사람이 제품을 옮겨 다니며 수동으로 처리해야 한다.

#2핵심 질문

서로 다른 보안 제품들이 알아낸 정보와 정책을 실시간으로 공유해 한 제품의 판단이 다른 제품의 조치로 바로 이어지게 하려면 어떻게 해야 하는가?

#3동작 예시

침입 탐지 제품이 특정 단말에서 악성 통신을 발견하면, 그 단말의 식별 정보를 pxGrid에 게시한다. 이 정보를 구독하고 있던 접속 제어 제품이 곧바로 그 단말의 네트워크 접속을 차단하는 조치를 실행한다.

#4동작 과정

  1. 정보 게시한 제품이 알아낸 단말 상태·위협 정보·정책 같은 컨텍스트(상황 정보)를 pxGrid에 올린다. 누가 어떤 사건을 언제 발견했는지가 공유된다.
  2. 구독과 전달그 정보가 필요한 다른 제품들이 미리 구독을 걸어 두고, 게시되는 순간 실시간으로 전달받는다. 각 제품은 자기에게 필요한 정보만 받는다.
  3. 조치 실행전달받은 정보를 근거로 각 제품이 자기 기능에 맞는 조치를 실행한다. 한 곳의 탐지가 다른 곳의 차단·격리로 바로 이어진다.

Cisco Umbrella Investigate

도메인·IP·해시 등의 위협 인텔리전스와 평판 정보를 조회해 조사에 활용하는 Cisco Umbrella Investigate의 구성·기능·이점이다.

#1문제 상황

경보가 뜬 뒤에 담당자가 도메인이나 IP를 하나씩 검색해 악성인지 판단하려 하면 근거가 빈약하고 시간도 오래 걸린다. 같은 주소라도 언제 처음 보였는지, 누가 등록했는지, 어떤 다른 주소들과 함께 쓰였는지 같은 맥락을 알 수 없으면 정상인지 악성인지 가릴 수 없다. 조사가 늦어지는 동안 위협은 이미 퍼져 있을 수 있다.

#2핵심 질문

의심스러운 도메인·IP·파일 해시가 실제로 위협인지 판단할 근거를 빠르게 모으려면 어떻게 해야 하는가?

#3동작 예시

의심스러운 도메인 하나를 조회하면, 그 도메인이 언제 등록되었는지, 어떤 IP로 연결되는지, 그 IP가 과거에 어떤 도메인들과 함께 쓰였는지, 악성으로 분류된 이력이 있는지가 한 화면에 모여 나온다. 담당자는 여러 출처를 따로 뒤지지 않고도 판단 근거를 얻는다.

#4동작 과정

  1. 대상 지정조사할 도메인·IP·파일 해시를 입력한다. 경보에서 나온 값이나 사용자가 제보한 값을 그대로 넣는다.
  2. 평판과 이력 조회해당 대상의 평판 점수와 과거 관측 이력, 관련 대상과의 연결 관계를 위협 인텔리전스(위협 정보 모음)에서 가져온다.
  3. 판단 근거 제시평판·연결 관계·시점 정보를 함께 보여 준다. 담당자는 이 근거로 차단·허용·추가 조사를 결정한다.

Cisco Cognitive Intelligence

Cisco 보안 텔레메트리와 위협 인텔리전스를 수집·상관 분석해 위협 사냥과 대응을 지원하는 Cisco Cognitive Intelligence의 구성·기능·이점이다.

#1문제 상황

조직 곳곳의 보안 제품이 저마다 경보와 로그를 쏟아 내는데, 담당자는 이걸 제품별 화면에서 따로따로 봐야 한다. 그래서 서로 관련된 사건인데도 각각 별개의 경보로 보이고, 어디서부터 살펴야 할지 우선순위를 정하기 어렵다. 위협 사냥(숨어 있는 위협을 능동적으로 찾는 활동)을 하려 해도 흩어진 자료를 사람이 손으로 이어 붙여야 하니 시간이 오래 걸린다.

#2핵심 질문

여러 제품에서 흩어져 나오는 보안 정보를 한데 모아 상관 분석해, 숨어 있는 위협을 능동적으로 찾아내려면 어떻게 해야 하는가?

#3동작 예시

여러 제품에서 특정 사용자에 관한 알림이 조금씩 올라온다고 하자. 하나는 낯선 로그인, 다른 하나는 평소와 다른 데이터 전송, 또 하나는 의심스러운 도메인 접속이다. 이걸 따로 보면 각각 사소해 보이지만, 한데 모아 같은 사용자·같은 시간대의 사건으로 묶으면 하나의 위협 시나리오로 드러난다.

#4동작 과정

  1. 텔레메트리 수집여러 보안 제품과 네트워크에서 나오는 측정값·경보·이벤트를 한곳으로 모은다. 흩어진 자료가 같은 시간 축 위에 올라간다.
  2. 상관 분석같은 사용자·단말·시간대로 이어지는 조각들을 서로 연결해 하나의 사건으로 묶는다. 개별로는 사소한 신호가 결합해 의미 있는 위협으로 바뀐다.
  3. 사냥과 대응 지원묶인 결과를 바탕으로 숨어 있는 위협을 찾아내고 대응 우선순위를 제시한다. 담당자는 흩어진 자료를 손으로 잇지 않고도 조사에 집중할 수 있다.

Cisco Encrypted Traffic Analytics

암호화를 해제하지 않고 네트워크 트래픽의 메타데이터와 패턴을 분석해 암호화된 위협을 탐지하는 Cisco Encrypted Traffic Analytics의 구성·기능·이점이다.

#1문제 상황

요즘 대부분의 통신은 암호화되어 있어, 중간의 보안 장비가 내용을 들여다볼 수 없다. 그래서 암호화된 통신 안에 악성코드가 숨어 있어도 겉으로는 정상 트래픽과 구분되지 않아 그냥 통과된다. 내용을 보려고 암호를 풀면 처리 부담이 커지고 개인정보·규제 문제도 생기며, 암호를 푸는 장비 자체가 공격 표적이 되기도 한다.

#2핵심 질문

암호를 풀지 않고도 암호화된 트래픽 안에 숨은 위협을 탐지하려면 어떻게 해야 하는가?

#3동작 예시

암호화된 연결 하나를 두고, 그 연결의 크기·시간 간격·방향·순서 같은 겉모습 정보와 암호 협상 과정의 특징을 모은다. 악성코드가 만드는 통신은 이런 겉모습 패턴이 알려진 정상 통신과 다르므로, 내용을 보지 않고도 의심스러운 연결로 표시할 수 있다.

#4동작 과정

  1. 메타데이터 추출패킷의 내용이 아니라 크기·시간 간격·방향·순서 같은 겉모습 정보와 암호 협상 특징을 뽑는다. 암호를 풀지 않으므로 처리 부담과 규제 문제가 없다.
  2. 패턴 분석뽑은 특징을 알려진 악성·정상 통신 패턴과 견준다. 내용이 아닌 흐름의 모양으로 위협 여부를 가른다.
  3. 위협 표시와 대응알려진 악성 패턴과 일치하면 해당 연결을 의심으로 표시하고 차단·조사로 이어 준다. 암호화된 위협도 네트워크 단계에서 걸러낼 수 있다.

#5한 줄 요약

암호를 풀지 않고 트래픽의 메타데이터와 패턴만으로 암호화된 위협을 탐지하는 것

Cisco Secure Client NVM

엔드포인트에서 발생하는 네트워크 흐름·프로세스 정보를 수집해 가시성을 제공하는 Cisco Secure Client Network Visibility Module(NVM)의 구성·기능·이점이다.

#1문제 상황

엔드포인트에서 어떤 프로세스가 어떤 목적지로 접속하는지는 그 단말 안에서만 벌어지는 일이라 네트워크 장비 쪽에서는 보이지 않는다. 방화벽은 IP와 포트만 보고 트래픽을 통과시키므로, 그 흐름을 만든 프로그램이 정상 업무 도구인지 악성코드인지 구분할 근거가 없다.

그래서 침해가 일어난 뒤에도 "어느 사용자의 어떤 앱이 어디로 데이터를 보냈는가"를 사후에 재구성하기 어렵다. 트래픽은 있었지만 그것을 만든 주체가 기록에 남지 않기 때문이다.

#2핵심 질문

엔드포인트에서 발생하는 네트워크 흐름을 어떤 프로세스가 만들었는지까지 함께 모아 가시성을 확보하려면 어떻게 해야 하는가?

#3동작 예시

사용자 PC의 Cisco Secure Client에서 NVM(Network Visibility Module, 네트워크 가시성 모듈)을 켜면, 모듈이 그 PC에서 나가는 연결마다 "어떤 프로세스가, 어느 사용자 권한으로, 어느 목적지에, 얼마나 데이터를 주고받았는가"를 함께 묶어 기록한다. 예를 들어 IP 주소 10.1.1.50에서 외부 서버로 나간 연결 하나가 방화벽 로그에는 그냥 "10.1.1.50 → 203.0.113.9"로만 남지만, NVM이 수집한 정보에는 이 연결을 만든 프로세스 이름과 사용자 계정까지 붙어 있어 그 흐름의 주체를 바로 확인할 수 있다.

#4동작 과정

  1. 수집엔드포인트의 Cisco Secure Client 안에서 NVM(네트워크 가시성 모듈)이 그 단말의 네트워크 흐름과 프로세스 정보를 함께 관찰한다. 그래서 트래픽과 그 트래픽을 만든 주체가 하나의 기록으로 묶인다.
  2. 전달수집된 흐름 정보가 정해진 수집 서버(예: Cisco Secure Network Analytics 같은 분석 시스템)로 전송된다. 그래서 단말마다 흩어져 있던 가시성이 한곳에 모인다.
  3. 분석·활용모인 데이터를 바탕으로 어떤 프로세스·사용자가 어디로 통신했는지 조회·분석한다. 그래서 이상 흐름의 주체를 식별하고 정책 판단에 쓸 근거가 생긴다.

#5한 줄 요약

엔드포인트의 네트워크 흐름을 그것을 만든 프로세스·사용자 정보와 함께 수집해, 누가 무엇을 하는지 보이지 않던 구간에 가시성을 확보하는 것
