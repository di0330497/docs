FortiGate 와 FortiOS 는 무엇을 하는 장비인가

#1문제 상황

기존에 회사 네트워크를 보호하려면 방화벽·VPN·위협 탐지 역할을 여러 대의 장비로 따로 구성했다. 각 장비가 독립적이어서 설정과 통합이 복잡하고, 유지보수할 점도 많다.

#2핵심 질문

이런 여러 역할을 하나의 장비에서 통합으로 처리할 수 없을까?

#3동작 예시

FortiGate는 네트워크 입구에 놓인 하나의 장비로서, 들어오는 모든 데이터를 검사한다. 데이터가 정책에 맞는지 확인하고, 위협이 있는지 분석하고, 필요하면 암호화된 VPN 터널로 안전하게 보낸다. 이 모든 작업을 하나의 장비에서 처리한다.

#4동작 과정

  1. 트래픽 도착네트워크에서 데이터가 FortiGate 포트에 들어온다.
  2. 정책 검사와 위협 분석FortiOS(FortiGate 전용 운영체제)가 이 데이터를 방화벽 규칙으로 걸러 내고, 안티바이러스와 IPS(침입 방지 시스템)로 위협이 있는지 조사한다.
  3. 통과 또는 차단안전하다면 목적지로 전달하고, 위협이 있거나 정책 위반이면 차단한다.

#5한 줄 요약

방화벽·VPN·위협 탐지를 하나의 장비에 통합해 네트워크 입구에서 모든 트래픽을 한 번에 제어하는 것

FortiGate의 물리 포트를 실제 네트워크에 쓰려면 먼저 어떤 설정을 해야 할까?

#3동작 예시

FortiGate는 각 물리 포트마다 인터페이스(Interface) 객체를 만들어 설정한다. 인터페이스 설정에서 그 포트의 역할(WAN/LAN/DMZ)을 고르고, IP 주소 설정 방식을 선택한다. IP는 수동으로 입력하거나(고정 IP), DHCP 서버에서 자동으로 받거나(DHCP), 또는 PPPoE(인터넷 서비스 제공자 방식)로 얻을 수 있다.

#4동작 과정

  1. 인터페이스 객체 생성Network > Interface에 들어가 물리 포트를 선택한 뒤 새 인터페이스로 추가한다.
  2. 역할과 주소 지정 방식 설정그 인터페이스의 Type(정적 IP/DHCP/PPPoE 등)을 정하고, IP 주소와 서브넷 마스크(또는 DHCP 클라이언트 활성화)를 설정한다.
  3. 결과FortiGate가 그 포트로 지정된 IP 대역의 트래픽을 수신하고, 정책에 따라 처리한다.

#5한 줄 요약

FortiGate의 각 물리 포트에 인터페이스를 만들어 역할(WAN/LAN/DMZ)을 정의하고, IP 주소 설정 방식(수동/DHCP/PPPoE)을 선택함으로써 네트워크 연결을 시작하는 것

논리 인터페이스: VLAN·존·소프트스위치·집합/이중화

물리 포트 위에 VLAN·존·소프트스위치·LAG(집합)/이중화 같은 논리 인터페이스를 얹어 하나의 포트를 여러 용도로 나누거나 여러 포트를 하나로 묶는 방법이다.

#1문제 상황

기존에는 물리 포트 하나가 하나의 역할만 담당했습니다. 예를 들어 이더넷 포트 1번은 내부 직원 네트워크로만, 포트 2번은 외부 인터넷으로만 사용했습니다. 그런데 포트가 많지 않거나 같은 포트를 여러 네트워크 그룹이 공유해야 한다면, 또는 여러 포트를 하나의 대역폭으로 묶고 싶다면 이 구조로는 부족합니다.

#2핵심 질문

하나의 물리 포트를 여러 목적으로 나누거나, 여러 물리 포트의 처리량을 하나로 합칠 수 있을까요?

#3동작 예시

VLAN 태깅을 이용하면 한 포트의 케이블을 통해 여러 네트워크가 동시에 흐를 수 있습니다. 패킷 헤더에 VLAN ID를 붙여서 "이 데이터는 VLAN 10입니다"라고 표시하면, FortiGate가 그 ID를 읽어 올바른 논리 인터페이스로 분류합니다. LAG(Link Aggregation)로 여러 포트를 묶으면 병렬로 데이터를 전송하여 대역폭을 합산할 수 있습니다.

#4동작 과정

  1. 논리 인터페이스 정의VLAN ID, 존(보안 영역), 소프트스위치 멤버십, 또는 LAG 그룹을 설정하여 물리 포트 위에 논리 계층을 만듭니다.
  2. 태깅 및 집합 구성수신한 패킷의 VLAN 태그를 읽거나 붙이고(trunk), LAG 포트들이 트래픽을 분산하도록 해시 알고리즘을 적용합니다.
  3. 인터페이스 처리분류된 패킷은 그 논리 인터페이스의 IP 주소, 방화벽 정책, 라우팅 규칙을 적용받아 처리됩니다.

#5한 줄 요약

물리 포트 위에 VLAN, 존, LAG 같은 논리 계층을 얹어 하나의 포트를 여러 용도로 나누고 여러 포트를 하나로 묶는 메커니즘

동작 모드: NAT 모드와 트랜스페어런트 모드

FortiGate가 IP를 가진 라우터처럼 동작하는 NAT 모드와, IP 없이 브리지처럼 기존 망 사이에 끼어드는 트랜스페어런트 모드의 차이다.

#1문제 상황

라우터는 자신의 IP 주소를 가지고 패킷의 출발지·목적지 IP를 변환(NAT)하며 네트워크 경계에서 동작합니다. 반면 투명 브리지는 IP 주소가 없고 기존 네트워크 경로를 바꾸지 않으면서 중간에 끼어들어 트래픽을 감시합니다. FortiGate는 이 둘 중 어느 방식으로 동작할지 선택할 수 있습니다.

#2핵심 질문

FortiGate를 라우터처럼 주소를 변환하면서 동작할까, 아니면 투명하게 기존 네트워크에 끼어들까요?

#3동작 예시

NAT 모드에서 내부 단말(192.168.1.100)이 인터넷으로 나가는 패킷은 FortiGate의 외부 IP(203.0.113.50)로 변환되고, 응답 패킷은 다시 원래 주소로 되돌려집니다. 트랜스페어런트 모드에서는 FortiGate 자신이 IP 주소를 가지지 않으며, MAC 주소만 학습하여 L2 포워딩처럼 동작합니다.

#4동작 과정

  1. 모드 설정 선택관리자가 NAT 모드 또는 트랜스페어런트 모드를 선택하면 FortiGate의 인터페이스 동작 방식이 결정됩니다.
  2. 주소 처리NAT 모드는 패킷의 IP 주소를 수정하고 포트 매핑을 유지하며, 트랜스페어런트 모드는 L3 주소를 건드리지 않고 MAC 주소만 처리합니다.
  3. 트래픽 통과정책 및 방화벽 규칙을 거친 후 패킷이 목적지 인터페이스로 전송됩니다.

FortiGate가 라우터처럼 주소를 변환하거나 투명하게 네트워크에 끼어드는 두 가지 포워딩 방식을 선택하는 메커니즘

#1문제 상황

기존에는 사무실의 모든 단말에 IP 주소를 관리자가 수동으로 입력했습니다. 단말이 100대면 100번, 주소를 변경할 때마다 다시 설정해야 했고, 중복 할당이나 오입력의 위험이 있었습니다.

#2핵심 질문

FortiGate가 자동으로 단말들에게 IP 주소를 할당하고 관리할 수 있을까요?

#3동작 예시

FortiGate의 DHCP 서버가 192.168.1.0/24 범위에서 주소 풀을 만들면, 내부 단말이 "IP를 달라"고 요청할 때 그 풀에서 192.168.1.50처럼 주소를 꺼내 단말에 할당합니다. 리스 기간(예: 24시간)이 끝나면 단말은 갱신을 요청하거나 주소를 반환합니다.

#4동작 과정

  1. DHCP 요청 수신단말이 "나에게 IP 주소를 주세요"라는 DHCP Discover 메시지를 브로드캐스트합니다.

  3. 응답과 리스할당받은 주소, 게이트웨이, DNS 등의 정보를 단말에 보내고, 정해진 기간 동안 유효합니다.

#4동작 과정

  3. DDNS 갱신공인 IP 주소 변경을 감지하면 자동으로 도메인 등록소에 새 주소를 등록합니다.

네트워크가 작을 때는 정적 라우트로 충분하지만, 라우터가 많아지거나 링크가 끊어졌다가 다시 살아나는 상황에서는 모든 경로를 수동으로 유지하기 불가능합니다. 게다가 새로운 라우터를 추가할 때마다 모든 이웃 라우터를 찾아다니며 설정을 바꿔야 합니다.

#2핵심 질문

이웃 라우터들과 경로 정보를 자동으로 주고받아 라우팅 테이블을 동적으로 갱신할 수 있을까요?

#3동작 예시

OSPF는 이웃 라우터와 링크의 상태(동작 중/다운)를 교환하여 최단 경로를 계산합니다. BGP는 자율시스템(AS, 독립적 라우팅 정책을 가진 네트워크 그룹) 단위로 경로를 광고하고 필터링합니다. 예를 들어 "우리 자율시스템 65001은 192.168.0.0/16을 관리한다"고 이웃에게 알리고, 불필요한 경로는 받지 않도록 필터합니다.

#4동작 과정

  1. 이웃 라우터 발견OSPF나 BGP 프로세스가 활성화되면 설정된 인터페이스로 이웃을 찾고 연결을 맺습니다.
  2. 경로 정보 교환 및 계산라우터들이 자신이 아는 경로 정보를 주고받고, OSPF는 최단 경로 우선(SPF) 알고리즘으로, BGP는 정책 기반으로 최적 경로를 선택합니다.
  3. 테이블 갱신 및 제어동적으로 계산된 경로가 테이블에 추가되며, 라우트맵(route map)과 프리픽스 리스트로 경로를 필터링하고 속성을 수정합니다.

멀티캐스트·VRF·IPv6 네트워킹

1대다 전송을 위한 멀티캐스트 라우팅, 라우팅 테이블을 논리적으로 분리하는 VRF, 그리고 IPv6 주소·라우팅 지원을 묶어 다룬다.

#1문제 상황

IP 통신은 유니캐스트(한 목적지로 1대1)와 브로드캐스트(같은 네트워크 내 모든 단말에 1대다)만 지원했습니다. 하지만 실제로는 특정 그룹(예: 스트리밍 수신자들)에게만 데이터를 전송해야 할 때가 있습니다. 또한 한 FortiGate에서 여러 고객 네트워크를 격리하거나 IPv4만으로는 부족한 규모에 IPv6이 필요합니다.

#2핵심 질문

특정 그룹 단말들에게만 1대다 전송하고, 네트워킹 공간을 논리적으로 분리하고, 128비트 주소로 확장할 수 있을까요?

#3동작 예시

멀티캐스트는 224.0.0.0/4 대역의 주소로 그룹을 정의하고, IGMP 프로토콜로 어느 단말이 그룹에 참여하는지 추적한 후 패킷을 그 그룹 멤버들에게만 보냅니다. VRF(Virtual Routing and Forwarding)는 라우팅 테이블을 논리적으로 분리하여 같은 FortiGate 안에 독립적인 네트워크를 만듭니다. IPv6은 128비트 주소로 주소 고갈 문제를 해결하고 라우팅 구조를 개선합니다.

#4동작 과정

  1. 주소·라우팅·VRF 설정멀티캐스트 주소 범위, VRF 인스턴스 정의, IPv6 주소와 라우팅을 각각 설정합니다.
  2. 그룹 관리 및 테이블 격리IGMP로 멀티캐스트 그룹 멤버를 추적하고, VRF마다 독립된 라우팅 테이블과 정책을 유지합니다.
  3. 포워딩 적용멀티캐스트 패킷은 등록된 그룹 수신자에게, 유니캐스트·VRF 패킷은 해당 테이블 규칙에 따라 전송됩니다.

확장 연결: FortiExtender·LTE/5G WAN·LAN extension

유선이 없거나 백업이 필요한 지점에서 FortiExtender와 LTE/5G 회선을 WAN으로 쓰거나, 원격 지점 LAN을 본사로 확장하는 방법이다.

#1문제 상황

지사나 원격지에 인터넷 연결을 하려면 유선 WAN 회선(MPLS, 전용선 등)을 깔거나 일반 광인터넷을 가져다 놓아야 한다. 하지만 유선이 없는 외곽 지역이거나 서비스 비용이 너무 크거나, 주 회선이 끊었을 때 백업이 필요한 경우가 있다. 이런 상황에서는 유선 네트워크 인프라만으로는 연결성을 보장할 수 없다.

#2핵심 질문

유선이 없거나 백업이 필요한 원격 지점에서 어떻게 FortiGate와 본사를 연결할 수 있을까?

#3동작 예시

FortiExtender는 FortiGate 옆에 연결하는 작은 장비로, 4G/LTE나 5G 모뎀이 내장되어 있다. FortiGate에서 인터넷이 필요할 때 이 FortiExtender를 거쳐서 이동통신사 네트워크로 나간다. 지역 특성에 따라 FortiGate는 주 WAN 회선을 쓰거나 FortiExtender(LTE/5G)로 자동 전환한다.

#4동작 과정

  1. FortiExtender 추가FortiGate 관리 콘솔에서 FortiExtender 장비를 등록하고, 이를 어떤 WAN 인터페이스로 쓸지 설정한다.
  2. LTE/5G 신호 수신FortiExtender가 이동통신사의 신호를 받아 데이터 연결을 확보한다.
  3. 정책에 따라 트래픽 라우팅FortiGate의 방화벽 정책과 라우팅 규칙에 따라 트래픽을 주 회선으로 보낼지, FortiExtender(LTE/5G)로 보낼지 결정한다. 주 회선이 끊어지면 자동으로 FortiExtender로 전환된다.

#5한 줄 요약

WAN 회선이 없거나 장애 상황에서 이동통신 네트워크를 FortiGate의 추가 WAN 경로로 사용하는 것

#1문제 상황

#4동작 과정

  3. 세션 기록 및 후속 패킷 처리정책에 따라 허용되면 이 통신의 정보를 세션 테이블에 기록해 두고, 같은 통신에 속한 다음 패킷들은 정책을 다시 확인하지 않고 세션 기록으로 빠르게 처리한다.

방화벽 정책과 객체03-04

서비스·스케줄·인터넷 서비스 정의

서비스는 포트/프로토콜 묶음, 스케줄은 정책이 유효한 시간대, 인터넷 서비스(ISDB)는 포티넷이 관리하는 유명 서비스의 IP·포트 목록이다.

→ 03-02 참조

#1문제 상황

정책을 만들 때 포트나 프로토콜을 직접 입력한다. 어떤 포트가 HTTP인지 HTTPS인지 외워야 하고, 여러 정책에서 같은 포트 조합을 반복 입력해야 한다. 또한 특정 시간대에만 정책을 유효하게 하려면 매번 시간 범위를 지정해야 한다.

#2핵심 질문

포트/프로토콜 조합이나 정책이 유효한 시간, 유명 서비스의 포트 정보를 어떻게 한 번에 관리할까?

#3동작 예시

"HTTP" 서비스 객체를 "TCP 80"으로 정의해 두면, 정책에서 "HTTP"라고 선택하기만 하면 된다. 또 "업무 시간" 스케줄을 "월-금 09:00-18:00"으로 정의해 두고 정책에 붙이면 그 시간대에만 정책이 유효하다.

#4동작 과정

  1. 서비스 정의포트와 프로토콜을 묶음으로 만든다. TCP 80(HTTP), TCP 443(HTTPS), UDP 53(DNS) 같은 식으로 커스텀 서비스를 만들 수도 있다.
  2. 스케줄 정의특정 시간대, 요일, 날짜 범위를 설정해서 정책이 유효한 시간을 제한한다.
  3. 인터넷 서비스 (ISDB) 활용포티넷이 관리하는 유명 서비스 데이터베이스에서 검색한 서비스의 IP·포트 정보를 정책에 바로 적용할 수 있다.

#5한 줄 요약

포트/프로토콜 조합, 유효 시간대, 유명 서비스의 포트 목록을 미리 정의해서, 정책에서 반복 입력하지 않고 참조하는 것

방화벽 정책과 객체03-05

소스 NAT: 인터페이스 NAT·IP 풀·센트럴 SNAT

내부에서 나가는 트래픽의 출발지 IP를 공인 IP로 바꿔주는 것이 소스 NAT이며, 나가는 인터페이스 IP를 쓰거나 IP 풀을 지정하거나 중앙 SNAT 테이블로 관리한다.

→ 03-06 참조

#1문제 상황

내부 네트워크의 모든 PC가 자신의 사설 IP로 인터넷으로 나가려고 하면, 인터넷 쪽에서 이 사설 주소를 인식하지 못해서 응답이 돌아오지 않는다. 사설 IP 주소는 공인 네트워크에서 라우팅되지 않기 때문이다.

#2핵심 질문

내부에서 나가는 트래픽의 출발지 IP를 공인 IP로 어떻게 바꿀까?

#3동작 예시

직원의 PC(192.168.1.10)가 인터넷으로 요청을 보낼 때, FortiGate에서 그 패킷의 출발지 주소를 회사 공인 IP(203.0.113.50)로 바꿔서 인터넷으로 보낸다. 인터넷의 서버는 203.0.113.50에서 온 요청으로 알고 응답을 보내고, FortiGate는 이 응답의 목적지를 다시 192.168.1.10으로 바꿔서 직원의 PC로 돌려보낸다.

#4동작 과정

  1. 인터페이스 NAT나가는 인터페이스의 IP 주소를 자동으로 쓴다. WAN 인터페이스가 203.0.113.50이면, 모든 내부 트래픽이 203.0.113.50으로 변환된다.
  2. IP 풀 NAT여러 공인 IP를 풀로 묶어서, 각 통신마다 다른 공인 IP로 번갈아가며 변환한다. 부하 분산이나 한 곳에서 차단당하지 않기 위해 쓴다.
  3. 센트럴 SNAT 테이블특정 내부 IP나 서브넷에 대해 어떤 공인 IP로 변환할지를 중앙에서 일괄 정의한다.

#5한 줄 요약

내부 사설 주소를 공인 IP로 바꿔서 인터넷 통신을 가능하게 하는 것이고, 방식에 따라 인터페이스 주소를 쓰거나 여러 공인 IP로 분산하거나 중앙 규칙으로 관리한다

방화벽 정책과 객체03-06

목적지 NAT: 가상 IP·포트 포워딩·서버 로드밸런싱

밖에서 들어오는 트래픽의 목적지 공인 IP를 내부 서버 IP로 바꿔주는 것이 목적지 NAT이고, 가상 IP(VIP)와 포트 포워딩, 여러 서버로 분산하는 로드밸런스 VIP로 구현한다.

→ 03-05 참조

#1문제 상황

인터넷에서 회사 내부 서버로 접근하려면 서버의 사설 IP로 직접 연결할 수 없다. 사설 IP는 인터넷에 공개되지 않기 때문이다. 따라서 외부에서 접근하려면 공인 IP를 통해 내부 서버로 매핑해야 한다.

#2핵심 질문

외부에서 접근할 수 있도록 내부 서버의 사설 IP를 공인 IP로 어떻게 매핑할까?

#3동작 예시

내부에 웹 서버가 192.168.1.100:80에 있다. 이를 공인 IP 203.0.113.50:8080으로 가상 매핑해 두면, 외부에서 203.0.113.50:8080으로 접근한 트래픽이 자동으로 192.168.1.100:80으로 변환되어 서버에 도달한다.

#4동작 과정

  1. 가상 IP (VIP) 생성공인 IP와 포트의 조합을 가상 IP로 정의한다. 이 가상 IP는 FortiGate의 인터페이스 주소는 아니지만, 외부에서 이 주소로 접근하면 FortiGate가 받을 수 있도록 설정한다.
  2. 포트 포워딩 정의가상 IP의 특정 포트로 들어온 트래픽을 내부 서버의 IP와 포트로 변환한다. 포트 번호도 바꿀 수 있다.
  3. 로드밸런스 VIP (선택사항)여러 내부 서버가 있으면, 한 개의 가상 IP로 들어온 트래픽을 여러 서버에 분산한다.

#5한 줄 요약

외부에서 접근하는 공인 IP/포트를 내부 서버의 사설 IP/포트로 변환하고, 필요시 여러 서버로 트래픽을 분산하는 것

방화벽 정책과 객체03-07

특수 정책 - 로컬-in, DoS, ACL, 인터페이스 정책, 프록시 정책

일반 통과 정책과 달리 장비 자신으로 향하는 트래픽(로컬-in), 플러딩 차단(DoS), 하드웨어 수준 차단(ACL), 프록시 모드 트래픽 등을 다루는 별도 정책들이다.

→ 03-01 참조

#1문제 상황

일반 방화벽 정책은 한 인터페이스에서 다른 인터페이스로 가는 트래픽만 본다. 하지만 방화벽 장비 자체를 향하는 트래픽(SSH 관리 접근, HTTPS 웹 콘솔, DNS 쿼리 등), 공격자가 의도적으로 보내는 플러딩 트래픽, 하드웨어 수준에서 처리되는 패킷, 프록시 기능으로 처리되는 트래픽 등은 일반 정책으로 통제할 수 없다. 이런 특수한 경우들을 각각 다루려면 별도의 정책 체계가 필요하다.

#2핵심 질문

방화벽 장비 자신으로 향하거나, 공격으로 간주되거나, 프록시 기능을 거치는 트래픽을 일반 정책과 다르게 통제하려면 어떻게 해야 할까?

#3동작 예시

관리자가 SSH로 FortiGate에 접속하려고 한다. 이 패킷은 외부 인터페이스에 도착하지만, 내부 인터페이스로 나가는 것이 아니라 장비 자신의 포트 22로 들어간다. 이를 통제하려면 '로컬-in 정책'에서 "어떤 IP 범위의 SSH 접근을 허락할지" 따로 정의해야 한다.

#4동작 과정

  1. 특수 트래픽 분류FortiGate는 수신한 패킷을 확인해 "장비 자신으로 향하는가", "플러딩 공격인가", "하드웨어 레벨에서 차단할 것인가", "프록시로 처리되는가"를 판단한다.
  2. 정책 선택분류 결과에 따라 로컬-in 정책, DoS 방어 정책, ACL(하드웨어 필터), 인터페이스별 정책, 프록시 정책 중 맞는 것을 적용한다.
  3. 허가 또는 차단정책 규칙이 일치하면 허락하거나 차단한다. 일반 통과 정책과는 별개로 독립적으로 작동한다.

방화벽 정책과 객체03-08

트래픽 셰이핑과 QoS

대역폭에 상한·보장·우선순위를 매겨 중요한 트래픽이 먼저 가도록 조절하는 기능으로, 셰이퍼를 정책이나 셰이핑 정책에 붙여 적용한다.

→ 03-02 참조

#1문제 상황

방화벽은 기본적으로 들어온 패킷을 모두 같은 속도로 내보낸다. 하지만 실제 네트워크에서는 동영상 스트리밍, VoIP 전화, 이메일 전송이 동시에 일어나고, 대역폭이 부족하면 중요하지 않은 트래픽이 중요한 것을 밀어낼 수 있다. 또한 특정 애플리케이션에 대역폭을 지나치게 많이 쓰도록 놔두면 전체 네트워크 성능이 떨어진다.

#2핵심 질문

중요한 업무 트래픽을 먼저 보내고, 대역폭 낭비를 줄이며, 각 애플리케이션이 차지할 수 있는 대역폭을 제한하려면 어떻게 해야 할까?

#3동작 예시

회사에서 VoIP 전화와 유튜브를 동시에 쓴다. 네트워크 대역폭이 100Mbps인데, 유튜브가 80Mbps를 쓰면 VoIP는 끊긴다. 셰이퍼를 설정하면 "유튜브는 최대 30Mbps, VoIP는 최소 10Mbps를 보장"하도록 제한할 수 있다.

#4동작 과정

  1. 셰이퍼 정의대역폭 최댓값, 보장값, 우선순위를 설정한 셰이퍼 객체를 미리 만든다 (예: "스트리밍-셰이퍼: 최대 50Mbps").
  2. 정책에 셰이퍼 적용방화벽 정책이나 셰이핑 정책(트래픽 제어 정책)에 셰이퍼를 붙인다. 그 정책에 일치하는 모든 트래픽이 그 셰이퍼의 제한을 받는다.
  3. 대역폭 제어패킷이 정책을 통과할 때 셰이퍼가 활성화되고, 정해진 속도 이상을 쓰려는 패킷은 지연되거나 버려진다. 중요한 트래픽이 먼저 큐에 들어간다.

#5한 줄 요약

정책에 대역폭 제한과 우선순위를 붙여, 중요한 트래픽이 필요한 대역폭을 확보하고 낭비적인 트래픽을 제어하는 것

사용자와 인증04-01

사용자·그룹과 방화벽 인증이 걸리는 방식

로컬/원격 사용자를 그룹으로 묶고, 방화벽 정책에 그 그룹을 걸어 트래픽이 통과하기 전에 신원을 확인하게 만드는 기본 구조다.

#1문제 상황

일반 방화벽 정책은 IP 주소와 포트 번호만 본다. 출발지 IP가 10.0.0.50이면 그 컴퓨터를 쓰는 사람이 누구든 같은 규칙이 적용된다. 하지만 같은 IP를 여러 사람이 쓰거나, 한 사람이 여러 IP에서 접속할 때는 IP 기반 정책만으로는 부족하다. 직급, 부서, 역할에 따라 다른 권한을 주거나, 특정 개인만 제한하려면 사용자 신원 정보가 필요하다.

#2핵심 질문

방화벽이 사용자의 신원을 알고 있어야, 사람 단위로 접근 권한을 통제할 수 있지 않을까?

#3동작 예시

회사에서 영업팀원은 고객 데이터베이스에 접근 가능하지만, 지원팀원은 접근 불가능하게 해야 한다. 두 팀 모두 같은 사무실 같은 네트워크에 있고 IP도 겹칠 수 있다. FortiGate는 먼저 사용자를 인증해서 "이건 영업팀의 A씨"임을 확인한 후, "영업팀 → 고객DB" 정책만 허락한다.

#4동작 과정

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 인증 서버 연결 설정FortiGate 관리자가 "LDAP 서버는 192.168.1.100, 포트 389"라고 정의한다. RADIUS나 TACACS+ 같은 다른 프로토콜도 같은 방식으로 등록한다.
  2. 정책에 인증 서버 지정사용자 인증이 필요한 정책을 만들 때 "인증: LDAP 서버" 옵션을 선택한다.
  3. 인증 요청과 응답사용자가 로그인하면 FortiGate는 credentials(자격 정보)를 외부 서버에 물어본다. 서버가 "정상" 응답을 주면 그 사용자를 믿는다.

#1문제 상황

비밀번호 하나만으로는 계정 도용 위험이 크다. 강한 비밀번호도 피싱으로 탈취되거나, 직원이 공개 WiFi에서 입력해 패킷 캡처로 노출될 수 있다. VPN이나 원격 접근처럼 외부에서 회사 네트워크에 들어오는 접속은 더욱 조심해야 한다. 비밀번호만 있으면 누구든 계정을 빼앗을 수 있다면, 추가 검증 단계가 필요하다.

#2핵심 질문

비밀번호 외에 또 다른 확인 방법을 한 번 더 거쳐야, 실제 본인이 로그인하려는 것임을 확실하게 할 수 있지 않을까?

#3동작 예시

사용자가 비밀번호를 입력한 후, FortiGate가 "이제 휴대폰에서 받은 6자리 숫자를 입력하세요"라고 묻는다. 해당 사용자의 휴대폰에만 SMS가 도착하거나, FortiToken 앱(또는 하드웨어 토큰)이 매분 바뀌는 숫자를 표시한다. 누군가 비밀번호를 알아도 사용자의 휴대폰이나 토큰이 없으면 로그인할 수 없다.

#4동작 과정

  1. 첫 번째 인증비밀번호** — 사용자가 아이디와 비밀번호를 입력하고 FortiGate가 확인한다.
  2. 두 번째 인증 생성FortiGate가 일회용 코드를 생성해서 이메일·SMS로 전송하거나, FortiToken 앱/하드웨어에 표시되는 숫자를 기준으로 삼는다.
  3. 두 번째 인증 확인사용자가 받은 코드나 토큰에 표시된 숫자를 입력한다. 일치하면 로그인을 완료한다.

인증서와 PKI - 로컬 인증서, CA, CRL, 인증서 인증

FortiGate가 쓰는 서버 인증서와 신뢰할 CA, 폐기 목록(CRL)을 관리하고, 비밀번호 대신 인증서로 사용자를 인증하는 체계다.

#1문제 상황

비밀번호는 사람이 기억해야 하므로 복잡함에 한계가 있고, 네트워크 전송 중에 탈취될 수 있다. 또한 서버가 위조되는 공격(중간자 공격)을 막을 수 없다. 예를 들어 공격자가 진짜 웹사이트를 흉내 낸 페이크 사이트를 만들어 사용자를 속이면, 사용자는 거기에 비밀번호를 입력해 도용당한다. 단순히 비밀번호만으로는 상대방의 정체를 확실하게 알 수 없다.

#2핵심 질문

서버가 정말 그 서버인지 증명하고, 비밀번호 없이 강력한 암호 기반의 신원 확인을 할 수는 없을까?

#3동작 예시

회사의 웹사이트에 HTTPS로 접속하면, 브라우저가 사이트의 디지털 인증서를 받는다. 이 인증서는 신뢰할 수 있는 인증 기관(CA)이 "이 인증서는 정말 company.com 소유"라고 서명해줬다. 사용자는 CA의 서명을 확인함으로써, 자신이 진짜 회사 서버에 연결되었다고 확신할 수 있다.

#4동작 과정

  1. 로컬 인증서 발급FortiGate가 자신이 쓸 SSL/TLS 인증서를 보유한다. VPN이나 HTTPS 웹 콘솔 접근에 이 인증서를 제시한다.
  2. 신뢰하는 CA 등록FortiGate 관리자가 "이 CA(인증 기관)의 서명은 믿는다"고 등록한다. 또한 해지된 인증서 목록(CRL)을 주기적으로 받아 업데이트한다.
  3. 인증서 기반 사용자 인증사용자가 인증서를 제시하면, FortiGate는 그 인증서가 신뢰하는 CA에서 서명받았는지, 해지되지 않았는지 확인한다. 모두 정상이면 로그인을 허락한다.

#5한 줄 요약

싱글 사인온 - FSSO와 폴링/에이전트 모드

사용자가 이미 AD에 로그인한 사실을 FortiGate가 넘겨받아 별도 로그인 없이 정책에 신원을 적용하는 것이 FSSO이고, 정보를 받는 방식이 에이전트/폴링 모드다.

→ 04-02 참조

#1문제 상황

직원이 아침에 회사 PC에 로그인하면 Active Directory가 "kim@company.com이 로그인했다"고 기록한다. 하지만 그 후 같은 직원이 VPN에 접속하거나 방화벽을 통과할 때마다 또 로그인을 해야 한다면, 사용자 경험이 나빠진다. 게다가 관리자 입장에서는 AD에서는 kim이 로그인했다고 알지만, FortiGate는 IP 주소만 보고 "누가 접근하는지" 모른다. 같은 사람인데도 여러 시스템에서 따로 인증하는 것은 비효율적이다.

#2핵심 질문

사용자가 AD에 이미 로그인했다는 사실을 FortiGate도 알게 되면, 한 번의 로그인으로 여러 시스템을 쓸 수 있지 않을까?

#3동작 예시

직원이 아침에 회사 PC에서 "kim@company.com"으로 로그인한다. Active Directory는 "kim이 192.168.1.50에서 로그인함"을 기록한다. FortiGate는 AD와 연결되어 있어서 이 정보를 실시간으로 받는다. 같은 직원이 나중에 방화벽 정책이 필요한 서비스에 접근하면, FortiGate는 "192.168.1.50은 kim의 IP다"라고 알고 있기 때문에, 사용자 신원을 자동으로 인식한다. 다시 로그인할 필요가 없다.

#4동작 과정

  1. AD 로그인 정보 수집에이전트 모드(DC 에이전트 소프트웨어)나 폴링 모드(FortiGate가 AD를 주기적으로 질의)로 "누가 어느 IP에서 로그인했는가"를 파악한다.
  2. FortiGate에 정보 등록수집한 IP-사용자 매핑 정보가 FortiGate 메모리에 저장된다 (예: "kim = 192.168.1.50").
  3. 정책 적용패킷이 정책과 일치할 때, FortiGate는 출발지 IP를 보고 등록된 사용자 정보에서 찾는다. "192.168.1.50 = kim"이면 "kim 그룹" 정책을 적용한다. kim은 별도의 로그인 없이 권한이 활성화된다.

기기 식별과 자산: 디바이스 인벤토리·EMS 태그

네트워크에 붙은 단말의 종류·OS·MAC을 자동으로 알아내 인벤토리로 모으고, FortiClient EMS가 붙여준 태그를 정책 조건으로 쓰는 기능이다.

#1문제 상황

네트워크 관리자는 보안 정책을 세울 때 어떤 기기가 네트워크에 연결되어 있는지 알아야 합니다. 기존에는 DHCP 로그를 확인하거나 네트워크 스캔 도구를 따로 실행해 수동으로 기기 목록을 만들었습니다. 이 방식은 정보가 부정확하고, 기기 추가·삭제 때마다 수동 업데이트가 필요하며, 기기의 정확한 OS나 용도를 파악하기 어렵습니다.

#2핵심 질문

네트워크를 흐르는 트래픽을 보면서 어떤 기기인지, OS는 무엇인지, MAC 주소는 뭔지를 자동으로 알아내 정책 결정에 쓸 수 있을까?

#3동작 예시

FortiGate가 네트워크 트래픽을 흐르게 하면서 동시에 관찰합니다. 어떤 기기에서 온 패킷의 특징(예: User-Agent 헤더, TCP 윈도우 크기, 포트 사용 패턴)을 보고 "이것은 Windows 10 노트북", "저것은 iOS 기기", "이건 프린터"라고 자동으로 판정한 후 목록에 기록합니다.

#4동작 과정

  1. 트래픽 수집 및 특징 분석기기가 네트워크에서 보내는 패킷의 프로토콜, 포트, User-Agent, MAC 주소 등을 FortiGate가 수집하고 분석합니다.
  2. 기기 분류 및 인벤토리 생성수집한 특징으로부터 기기의 종류(노트북, 스마트폰, 프린터 등), OS, 버전을 판정하고 디바이스 인벤토리(기기 목록)에 추가합니다.
  3. EMS 태그 연동 및 정책 적용FortiClient Endpoint Management Server(EMS)에서 받은 추가 정보나 태그(예: 부서, 보안 상태)를 함께 기록하고, 정책에서 "Windows 기기만 허용", "감염된 기기 격리" 같은 조건으로 사용합니다.

패킷을 흘려보내며 검사하는 flow 모드와 파일 전체를 모아 검사하는 proxy 모드의 성능·정확도 트레이드오프.

#1문제 상황

방화벽이 트래픽을 검사할 때 두 가지 상충하는 목표가 있습니다. 하나는 빠르게 처리해 네트워크 지연을 최소화하는 것, 다른 하나는 파일 전체를 검사해 악성 콘텐츠를 정확하게 탐지하는 것입니다. 기존에는 두 방식을 선택할 수 없거나 성능 손실을 감수해야 했습니다.

#2핵심 질문

패킷을 빠르게 통과시킬 것인지, 아니면 전체 파일을 모아 완벽하게 검사할 것인지를 어떻게 구분 적용할 것인가?

#3동작 예시

Flow 모드는 물이 흐르는 파이프 같습니다. 물(패킷)이 도착하는 그 순간 검사하고 바로 통과시킵니다. Proxy 모드는 물을 탱크에 모은 후 완전히 검사하고 나서 흘려보냅니다. 탱크에서의 지연은 있지만 내용물을 더 완벽하게 확인할 수 있습니다.

#4동작 과정

  1. Flow 모드 동작패킷이 FortiGate에 도착하면 즉시 시그니처 검사와 기본 필터링을 거쳐 통과 또는 차단 결정을 내립니다. 전체 파일을 기다리지 않으므로 지연이 거의 없습니다.
  2. Proxy 모드 동작데이터 흐름의 양쪽 끝(클라이언트와 서버)과 연결을 맺은 후, 전체 파일이나 전체 HTTP 요청·응답을 메모리나 버퍼에 모은 뒤 완전히 검사합니다. 검사 정확도가 높지만 지연이 발생합니다.
  3. 모드별 적용프로토콜·서비스·상황에 따라 각 프로파일에서 Flow 또는 Proxy를 선택 적용합니다. 예를 들어 동영상 스트리밍은 Flow, 파일 다운로드는 Proxy로 설정할 수 있습니다.

SSL/SSH 심층 검사와 CA 인증서 배포

암호화된 트래픽을 방화벽이 중간에서 복호화해 검사하려면 FortiGate CA 인증서를 클라이언트에 신뢰시켜야 한다.

#1문제 상황

현대의 웹 트래픽과 원격 접속은 거의 HTTPS(SSL/TLS)와 SSH로 암호화되어 있습니다. 방화벽이 이 암호화된 연결을 그대로 통과시키면, 중간에 악성 콘텐츠가 숨어 있어도 검사할 수 없습니다. 기존에는 암호화된 트래픽을 검사할 방법이 없어 보안 맹점이 생겼습니다.

#2핵심 질문

암호화된 통신 내용을 방화벽이 검사하려면 암호화를 풀 권한을 어떻게 얻을 것인가?

#3동작 예시

클라이언트가 서버에 HTTPS로 접속하려 할 때, FortiGate가 그 연결을 가로채 자신이 서버 역할을 하고, 동시에 실제 서버와는 별도로 연결을 맺습니다. 클라이언트는 FortiGate의 인증서를 받으므로, FortiGate의 CA 인증서를 미리 신뢰하도록 설정하면 "정상 연결"로 간주합니다. 이렇게 양쪽 암호화 연결을 동시에 제어하면서 중간에서 데이터를 보고 검사할 수 있습니다.

#4동작 과정

  1. FortiGate CA 인증서 배포관리자가 FortiGate 자체 CA 인증서를 모든 클라이언트 PC나 모바일 기기에 설치하고 신뢰하는 인증서로 등록합니다.
  2. 중간자(MITM) 위치 확보클라이언트가 서버에 HTTPS 연결을 시도하면, FortiGate가 그 연결을 가로채 클라이언트에게는 자신의 인증서로 응답하고, 실제 서버와는 별도 HTTPS 연결을 맺습니다. 클라이언트는 FortiGate의 인증서를 신뢰하므로 정상 연결로 봅니다.
  3. 양방향 복호화 및 검사클라이언트→FortiGate, FortiGate→서버의 양쪽 암호화된 데이터를 각각 복호화해 내용을 검사(악성 코드, 정책 위반 등)한 후, 필요하면 통과시키거나 차단합니다.

#5한 줄 요약

FortiGate가 암호화된 연결을 중간에서 가로채고 복호화해 검사하기 위해, 자신의 CA 인증서를 클라이언트에 신뢰시키는 것

안티바이러스: 스캔 방식·격리·아웃브레이크 방지

시그니처와 클라우드 조회로 악성 파일을 잡아내고 격리하며, 신종 유행에는 outbreak prevention 으로 대응하는 엔진.

#1문제 상황

악성 파일 탐지는 오래전부터 바이러스 시그니처(알려진 악성 파일의 패턴)로 이루어졌습니다. 관리자는 최신 시그니처 업데이트를 받아 알려진 악성 파일을 차단했습니다. 하지만 새로운 악성 파일이 매일 등장하고, 시그니처 업데이트가 나오기 전에 공격을 받을 수 있으므로, 알려진 악성만으로는 충분하지 않습니다.

#2핵심 질문

알려진 악성 파일 시그니처만으로는 부족한데, 신종 악성까지 탐지하고 신속하게 대응할 수 있을까?

#3동작 예시

FortiGate 안티바이러스는 세 가지 방법을 결합합니다. 먼저 파일의 해시(지문)를 로컬 시그니처 데이터베이스와 비교해 알려진 악성을 즉시 차단합니다. 그 다음 FortiGuard 클라우드에 온라인 조회를 해서 새로 수집된 위협 정보를 확인합니다. 마지막으로 신종 악성 유행이 발생하면 outbreak prevention이 자동으로 차단 규칙을 활성화합니다.

#4동작 과정

  1. 로컬 시그니처 검사파일이 FortiGate를 통과할 때 그 파일의 해시를 로컬 안티바이러스 시그니처 데이터베이스와 대조합니다. 일치하면 즉시 악성으로 판정하고 파일 전달을 차단합니다.
  2. FortiGuard 클라우드 조회 및 Outbreak Prevention로컬 시그니처에 없는 파일이거나, 신종 악성 유행이 감지되면 FortiGuard 클라우드 데이터베이스에 조회해 최신 위협 정보를 확인합니다. Outbreak prevention이 활성화되면, 유행 중인 신종 악성에 대한 차단 규칙이 자동으로 적용됩니다.
  3. 격리 및 사용자 알림악성으로 판정된 파일은 사용자에게 전달되지 않고 격리되거나 삭제되며, 관리자와 사용자에게 탐지 사실이 알려집니다.

#5한 줄 요약

알려진 악성 시그니처, 클라우드 위협 정보, 신종 유행 대응을 조합해 악성 파일을 다층으로 탐지하고 차단하는 것

샌드박스 연동: FortiSandbox 와 인라인 스캐닝

알려지지 않은 파일을 외부 샌드박스에서 실행해 판정하고, 인라인 스캐닝은 판정이 날 때까지 파일을 붙잡아 둔다.

→ 05-03 참조

#1문제 상황

안티바이러스 시그니처와 클라우드 검사는 이미 알려진 악성 파일만 탐지합니다. 하지만 조직을 겨냥한 맞춤형 악성(targeted malware)이나 완전히 새로운 악성 기법은 어떤 데이터베이스에도 없을 수 있습니다. 이런 파일이 통과하면 심각한 피해를 입을 수 있습니다.

#2핵심 질문

알려지지 않은 의심 파일이 정말 악성인지를 실제 동작으로 검증할 수는 없을까?

#3동작 예시

FortiGate는 의심 파일을 FortiSandbox(Fortinet 클라우드의 격리된 테스트 환경)에 보냅니다. 샌드박스는 그 파일을 가상의 Windows나 Linux 환경에서 실행해봅니다. 파일이 악성 동작(예: 다른 파일 삭제, 레지스트리 변경, 원격 명령 수신)을 하면 악성으로 판정하고, 정상이면 허용합니다.

#4동작 과정

  1. 샌드박스로 파일 제출알려지지 않은 파일이나 의심 파일이 FortiGate를 통과하려 하면, 그 파일을 FortiSandbox 클라우드로 업로드합니다.
  2. 격리 환경에서 동작 분석FortiSandbox는 가상 시스템에서 파일을 실행하고, 메모리 접근, 파일 생성·삭제, 네트워크 연결, 레지스트리 변경 등을 기록합니다. 이 행동 패턴이 악성으로 알려진 동작과 일치하면 악성으로 판정합니다.
  3. 판정 결과 적용 및 인라인 스캐닝판정 결과(악성/정상)를 FortiGate에 보내고, 인라인 스캐닝(inline scanning) 모드라면 판정이 나올 때까지 사용자에게 파일을 전달하지 않습니다. 정상 판정이 나오면 파일을 허용하고, 악성이면 차단합니다.

#5한 줄 요약

알려지지 않은 파일을 외부 격리 환경에서 실행해 실제 악성 동작 여부를 검증하는 것

웹 필터: 카테고리·URL 필터·콘텐츠 제어

FortiGuard 웹 카테고리 등급과 직접 지정한 URL 목록으로 웹 접속을 허용·차단·경고하는 프로파일.

#1문제 상황

네트워크 관리자는 업무 생산성이나 보안을 위해 특정 웹사이트 접속을 제어해야 합니다. 기존에는 차단할 URL을 일일이 목록에 등록하거나, 모든 웹 접속을 허용하거나 전체 차단하는 방식뿐이었습니다. 웹사이트 속성에 따라 그룹으로 관리할 방법이 없었습니다.

#2핵심 질문

웹사이트를 카테고리(소셜미디어, 게임, 뉴스 등)로 자동 분류하고, 카테고리별로 접속을 제어할 수 있을까?

#3동작 예시

사용자가 어떤 URL에 접속하려 하면, FortiGate는 그 URL이 FortiGuard 웹 카테고리 데이터베이스에 어느 카테고리로 분류되어 있는지 조회합니다. 예를 들어 youtube.com은 "스트리밍 미디어" 카테고리, facebook.com은 "소셜미디어" 카테고리로 기분류되어 있습니다. 관리자의 정책이 "스트리밍 미디어 차단"이라면, youtube.com은 자동으로 차단되고, "소셜미디어 경고"라면 facebook.com 접속 시 경고 페이지를 보여줍니다.

#4동작 과정

  1. URL 카테고리 조회사용자가 웹사이트에 접속하려 하면, FortiGate가 그 URL의 도메인을 FortiGuard 웹 필터 데이터베이스에서 찾아 카테고리를 확인합니다.
  2. 관리자 정책과 비교조회한 카테고리와 관리자가 설정한 웹 필터 프로파일(정책)을 비교합니다. 또한 관리자가 직접 지정한 URL 화이트리스트·블랙리스트도 확인합니다.
  3. 접속 결정 및 실행정책에 따라 접속을 허용, 차단, 또는 경고로 설정합니다. 차단이면 차단 페이지를 표시하고, 경고면 사용자 확인 후 진행하게 하거나 로그만 남깁니다.

#5한 줄 요약

DNS 필터와 비디오 필터

이름 해석 단계에서 악성·차단 도메인을 걸러내고, 유튜브 등 동영상 채널 단위로 시청을 통제한다.

→ 05-05 참조

#1문제 상황

클라이언트는 웹사이트에 접속하기 전에 도메인 이름을 IP 주소로 변환해달라고 DNS 서버에 요청합니다. 기존 웹 필터는 URL 요청이 HTTP 프로토콜로 이루어진 후에야 차단할 수 있습니다. 또한 유튜브나 넷플릭스 같은 동영상 플랫폼은 채널이나 콘텐츠 수준의 제어가 어려웠습니다.

#2핵심 질문

DNS 단계에서 악성 도메인을 미리 차단하고, 동영상 플랫폼을 채널 단위로 시청 제어할 수 있을까?

#3동작 예시

DNS 필터는 클라이언트가 도메인 이름 해석을 요청하는 순간에 개입합니다. 예를 들어 malicious-site.com을 조회하려 하면, DNS 필터가 미리 준비한 악성 도메인 목록에서 찾아 응답을 차단하거나 변경해 접속 자체를 불가능하게 합니다. 비디오 필터는 HTTPS 연결할 때 서버 이름(SNI)으로 어느 플랫폼(유튜브, 틱톡 등)인지 식별하고, 채널이나 카테고리 정보를 보며 시청 여부를 결정합니다.

#4동작 과정

  1. DNS 조회 차단클라이언트가 도메인 이름을 IP로 변환해달라고 DNS 요청을 하면, FortiGate의 DNS 필터가 그 도메인을 악성·차단 목록과 확인합니다. 목록에 있으면 조회 응답을 거부하거나 안전한 IP로 변경해 악성 사이트 접속을 차단합니다.
  2. 동영상 플랫폼 식별클라이언트가 유튜브나 틱톡 같은 동영상 플랫폼에 HTTPS로 연결할 때, FortiGate가 TLS 핸드셰이크의 SNI(Server Name Indication) 필드를 보고 어느 플랫폼인지 식별합니다.
  3. 채널 또는 콘텐츠 제어비디오 필터 프로파일에 따라 플랫폼 전체를 차단하거나, 특정 채널(예: 교육용 채널만 허용)을 지정하거나, 콘텐츠 등급(성인 제한 등)을 적용해 시청 여부를 결정합니다.

#5한 줄 요약

DNS 단계에서 악성 도메인을 조기 차단하고, 동영상 플랫폼의 채널이나 콘텐츠 수준으로 시청을 제어하는 것

애플리케이션 제어: 시그니처·카테고리·필터

포트가 아니라 트래픽 패턴으로 앱을 식별해 카테고리·시그니처 단위로 허용·차단·대역 제한한다.

#1문제 상황

기존에는 포트 번호만으로 어떤 애플리케이션인지 판단했습니다. HTTP는 80, HTTPS는 443 같은 식입니다. 하지만 이 방식에는 명백한 한계가 있습니다. WebEx와 YouTube 모두 443 포트를 사용하지만, 포트만으로는 둘을 구분할 수 없습니다. 또한 애플리케이션이 포트를 바꾸면 제어를 우회할 수 있습니다.

#2핵심 질문

포트가 아니라 애플리케이션의 실제 통신 패턴으로 그것이 어떤 앱인지 정확히 알아낼 수 있을까요?

#3동작 예시

각 애플리케이션은 고유한 통신 패턴을 가집니다. Fortinet은 WebEx, YouTube, Slack 같은 각 앱의 데이터 흐름을 분석해서 시그니처(고유 패턴의 기록)를 만들어 둡니다. 트래픽이 지날 때 이 시그니처와 비교하면 포트와 상관없이 정확한 앱을 식별할 수 있습니다.

#4동작 과정

  1. 시그니처 구축Fortinet이 각 애플리케이션의 통신 패턴을 분석해 시그니처 데이터베이스를 만들고 FortiGate에 제공합니다.
  2. 패킷 검사 및 앱 식별패킷이 지날 때 FortiGate가 그 데이터 흐름을 시그니처와 대조해서 정확한 애플리케이션을 식별합니다.
  3. 정책 적용식별된 애플리케이션을 카테고리(소셜미디어, 스트리밍, 생산성 도구 등)와 시그니처 단위로 허용, 차단, 대역 제한하는 정책을 적용합니다.

#5한 줄 요약

포트 번호가 아니라 애플리케이션의 실제 통신 패턴을 시그니처로 분석해 앱을 정확히 식별하고, 그 기반 위에 카테고리와 시그니처 단위로 세밀한 제어를 하는 기술

IPS: 시그니처·필터·레이트 기반 탐지와 튜닝

알려진 공격 시그니처와 임계치 기반 탐지로 침입을 막고, 오탐을 줄이려 필터와 예외를 조정하는 작업.

#1문제 상황

기존의 방화벽은 출발지, 목적지, 포트만 봅니다. 이 정보만으로는 정상 패킷과 악의적인 패킷을 구분할 수 없습니다. HTTPS 연결 자체는 정상으로 보이지만, 그 내부에 SQL Injection이나 버퍼 오버플로우 같은 공격 페이로드(악의적 데이터)가 숨어 있을 수 있는데, 방화벽은 이를 감지하지 못합니다.

#2핵심 질문

정상적인 연결처럼 보이는 트래픽 안에 숨어 있는 알려진 공격 패턴이나 비정상적 행동을 찾아낼 수 있을까요?

#3동작 예시

SQL Injection 공격은 정상 웹 요청으로 위장해서 HTTPS로 전송됩니다. IPS는 패킷 내용을 검사해서 "DROP TABLE users" 같은 SQL 명령어 패턴을 탐지합니다. 또한 특정 포트로 매초 수천 개의 연결을 시도하는 포트 스캔 행동도, 누적된 연결 수(임계치)를 초과하면 이상 행동으로 판단합니다.

#4동작 과정

  1. 시그니처 대조패킷의 페이로드(내용)를 알려진 공격 시그니처(공격 패턴의 기록)와 비교해서 정확히 일치하는 공격이 있는지 검사합니다.
  2. 이상 탐지시그니처로 매칭되지 않는 새로운 공격이나 포트 스캔, 무작위 접속 같은 비정상 행동을 통계 기반 임계치(한도)로 감지합니다.
  3. 오탐 조정정상 애플리케이션까지 차단되는 것을 피하기 위해 특정 시그니처를 비활성화하거나 예외 규칙을 추가해서 탐지 정확도를 높입니다.

#5한 줄 요약

패킷 내용을 공격 시그니처와 비교하고 통계 기반 이상 탐지로 침입을 조기에 잡되, 오탐을 줄이도록 지속적으로 튜닝하는 기술

파일 필터와 DLP

확장자·실제 파일 타입으로 전송을 막는 파일 필터와, 내용 속 민감정보 유출을 탐지·차단하는 DLP.

#1문제 상황

기존 방화벽은 누가 어떤 파일을 다운로드하거나 업로드하는지 제어하지 못합니다. 악성 실행 파일(.exe), 백도어가 담긴 스크립트, 또는 회사의 민감정보가 담긴 문서도 자유롭게 외부로 나갑니다.

#2핵심 질문

파일의 타입과 내용 안의 민감정보를 근거로 외부 전송을 차단할 수 있을까요?

#3동작 예시

.exe 확장자는 차단하되, 공급사의 정상 소프트웨어 배포 서버만 화이트리스트로 허용합니다. 동시에 DLP 규칙에서 "13자리 숫자 패턴"(주민번호)이나 "신용카드 번호 형식"을 감지하면 그 파일을 포함한 전체 업로드를 자동으로 차단합니다.

#4동작 과정

  1. 파일 식별확장자로 먼저 파일 타입을 판단하되, 파일 헤더(파일 맨 앞의 고유 코드)를 검사해서 실제 파일 타입을 검증합니다. 예를 들어 .jpg로 위장한 실행 파일도 헤더로 구분 가능합니다.
  2. 콘텐츠 검사DLP(Data Loss Prevention, 데이터 유출 방지)가 파일 내용을 스캔하고, 정규표현식(특정 패턴을 나타내는 규칙)으로 신용카드 번호, 주민번호, 회사 기밀 키워드 등의 민감정보를 탐지합니다.
  3. 제어 적용차단, 허용, 암호화, 또는 로깅 중 하나의 정책을 실행합니다.

#5한 줄 요약

파일의 확장자와 실제 타입, 그리고 내용 속 민감정보 패턴을 근거로 외부로의 전송을 제한하는 기술

외부 검사 서버 연동(ICAP), 웹서버 보호(WAF), 스팸·VoIP 제어와 검사 대상 포트를 정하는 프로토콜 옵션.

→ 05-01 참조

#1문제 상황

지금까지 설명한 프로필들(애플리케이션 제어, IPS, 파일 필터)은 FortiGate 내부 엔진으로 동작합니다. 하지만 웹 애플리케이션 공격, 스팸 이메일, VoIP 통화의 품질 이상 같은 특수한 위험들은 각각 전문화된 검사가 필요합니다. 또한 FortiGate 내장 엔진의 능력을 초과하는 고급 분석이 필요한 경우도 있습니다.

#2핵심 질문

웹 공격, 스팸, VoIP 같은 프로토콜별 특수한 위협을 각각 잡고, 필요하면 외부 검사 서버까지 연동해서 더 강력하게 보호할 수 있을까요?

#3동작 예시

웹서버로 들어오는 요청 중 XSS 또는 SQL Injection 공격을 WAF(Web Application Firewall)로 탐지하고, 메일 서버로의 스팸 메시지는 안티스팸 엔진이 헤더와 본문을 검사해서 차단하며, VoIP 통화는 비정상적인 RTP 흐름이나 신호 이상을 감지합니다. 필요시 ICAP(Internet Content Adaptation Protocol, 외부 검사 서버 연동 규약)을 통해 의심 파일을 외부 고급 샌드박스로 분석하도록 보냅니다.

#4동작 과정

  1. 프로토콜 감지포트 번호와 데이터 패턴으로 웹(HTTP/HTTPS), 이메일(SMTP/POP3), VoIP(SIP/RTP) 등을 구분합니다.
  2. 전문 엔진 적용WAF는 웹 요청 내 SQL/XSS 공격 패턴, 안티스팸은 메일 헤더와 본문의 스팸 특징, VoIP는 비율 이상이나 지연을 각각 검사합니다.
  3. 외부 연동ICAP를 지원하는 정책에서는 의심 콘텐츠를 외부 검사 서버로 보내 고급 분석(예: 샌드박스 실행)을 받은 후 결과를 반영합니다.

#5한 줄 요약

웹·이메일·VoIP 같은 애플리케이션별 전문화된 검사 엔진을 적용하고, ICAP를 통해 외부 고급 분석까지 연동해서 포트 검사만으로는 막을 수 없는 애플리케이션 계층 공격을 다층으로 차단하는 기술

VPN: 지점과 원격 사용자 연결06-01

IPsec 기본: IKE 협상과 페이즈1/페이즈2

IPsec VPN은 인터넷 구간을 암호화 터널로 감싸는 기술이며, 페이즈1에서 서로를 인증하고 안전한 관리 채널을 만든 뒤 페이즈2에서 실제 데이터가 흐를 암호화 터널을 만든다.

#1문제 상황

인터넷 구간의 데이터는 기본적으로 평문(암호화되지 않은 상태)으로 전송됩니다. 또한 패킷의 출발지 주소는 위조 가능하므로, 정말 신뢰할 수 있는 곳에서 온 패킷인지 검증할 방법이 없습니다.

#2핵심 질문

인터넷 구간을 안전하게 암호화하면서 동시에 상대방이 정말 신뢰할 수 있는 상대인지 상호 확인할 수 있을까요?

#3동작 예시

A 지점의 FortiGate와 B 지점의 FortiGate가 IPsec VPN을 만들 때, 먼저 서로를 인증해서(인증서나 사전공유키로) 신뢰 관계를 확립하고, 그 안전한 채널 위에서 실제 데이터를 암호화할 키와 암호화 방식을 협상합니다.

#4동작 과정

  1. 페이즈1(IKE 협상)양쪽 FortiGate가 인증서(공개키 기반) 또는 사전공유키(미리 정한 암호)로 서로를 인증하고, 향후 협상에 쓸 안전한 관리 채널을 암호화한 상태로 확립합니다.
  2. 페이즈2페이즈1의 안전한 채널 위에서 실제 데이터 전송용 암호화 알고리즘(AES, 3DES 등), 키 길이, 키 교환 주기 등을 협상합니다.
  3. 터널 수립 및 데이터 암호화협상된 키와 알고리즘으로 실제 데이터 패킷을 암호화해서 터널로 전송합니다.

#5한 줄 요약

인터넷 구간을 상호 인증과 암호화 키 협상 과정을 거쳐 안전한 터널로 만들고, 그 터널을 통해 모든 데이터를 암호화해 보내는 기술

#1문제 상황

본사와 지점이 각각 인터넷으로 외부 서버에 접속할 때 지연이 발생하고 비용도 증가합니다. 또한 지점의 내부망이 고립되어 본사의 파일서버, 데이터베이스 같은 자원에 직접 접근하려면 별도의 VPN이나 프록시를 거쳐야 하는데 이는 번거롭고 느립니다.

#2핵심 질문

본사와 지점의 내부망을 마치 같은 사내망처럼 인터넷을 통해 직접 통신하게 할 수 있을까요?

#3동작 예시

#4동작 과정

  1. 터널 수립양쪽 FortiGate가 고정 공인IP로 IPsec 터널을 상시 유지합니다. 통상 한쪽이 능동적으로 접속 요청을 하고 다른 쪽이 받습니다.
  2. 라우팅 설정각 FortiGate의 라우팅 테이블에 "상대 내부망 IP 대역으로 가는 패킷은 이 IPsec 터널로 전송하라"는 경로를 추가합니다.
  3. 투명한 통신본사와 지점의 일반 사용자는 터널이 있는지 모르고 평상시처럼 통신합니다. 패킷이 자동으로 터널을 통해 암호화되어 전달됩니다.

IP가 매번 바뀌는 재택 근무자나 소규모 지점이 먼저 접속을 걸어오면 FortiGate가 받아주는 방식의 IPsec VPN이다.

#1문제 상황

사이트 간 IPsec VPN은 양쪽이 고정된 공인IP를 가진 지점이어야 합니다. 하지만 재택근무자는 가정 집의 인터넷(DHCP로 IP가 매번 바뀜)을 쓰고, 소규모 지점은 공인IP가 없거나 모바일 오피스처럼 위치가 자주 바뀝니다. 이런 상황에서는 고정 공인IP 기반의 터널을 미리 설정할 수 없습니다.

#2핵심 질문

공인IP가 고정되지 않은 원격 사용자나 지점이 먼저 회사 방화벽에 접속을 요청하면 받아줄 수 있을까요?

#3동작 예시

재택근무자가 FortiClient(Fortinet의 클라이언트 소프트웨어)를 실행해서 회사의 FortiGate 공인IP(또는 도메인명)로 접속을 거는 방식입니다. 사용자의 집 인터넷 IP가 DHCP로 192.168.0.100일 때도, 다음날 DHCP로 192.168.0.200이 될 때도, FortiClient는 회사 FortiGate의 고정 주소를 알고 있으니 언제든 접속할 수 있습니다.

#4동작 과정

  1. 클라이언트 발동사용자가 FortiClient를 실행하고 회사 FortiGate의 공인IP 또는 DNS 이름(예: vpn.company.com)으로 접속 요청을 보냅니다.
  2. 인증 및 터널 수립FortiGate가 사용자 이름과 암호(또는 인증서)로 사용자를 인증한 후, IPsec 터널을 동적으로 생성합니다.
  3. 내부망 접근터널이 수립되면 사용자의 FortiClient는 회사 내부망으로 접근할 수 있으며, 마치 회사 사무실의 네트워크에 연결된 것처럼 동작합니다.

#5한 줄 요약

클라이언트 측에서 주도적으로 접속을 발동할 수 있는 다이얼업 방식의 IPsec VPN으로, 고정 공인IP가 없는 재택근무자나 유동적인 지점도 동적으로 안전하게 연결하는 기술

#1문제 상황

허브-스포크 구성에서 모든 지점 간 통신이 허브를 거친다. 지점 A에서 지점 B로 데이터를 보내려면 먼저 허브에 도착한 후, 다시 지점 B로 나간다. 이 방식의 한계는 허브에 트래픽이 집중되면서 허브의 부하가 증가하고, 지점 간 통신 지연이 늘어난다는 것이다.

#2핵심 질문

지점 간 통신이 발생할 때마다 자동으로 지점 간 직통 터널을 만들어 허브를 우회할 수 없을까?

#3동작 예시

지점 A와 지점 B 사이에 통신이 필요하면, FortiGate가 자동으로 감지해 A-B 간 IPsec 터널을 즉시 수립한다. 이후 A-B 트래픽은 허브를 거치지 않고 직통 터널로 흐른다.

#4동작 과정

  1. 통신 감지지점 간 트래픽이 발생하면 FortiGate가 이를 감지한다.
  2. 터널 자동 수립통신 상대에 대한 IPsec 터널이 아직 없으면, 자동으로 양쪽 지점 간의 암호화 터널(IKE Phase 1, 2를 거쳐)을 수립한다.
  3. 직통 통신터널이 완성되면 그 이후 트래픽은 허브를 거치지 않고 지점 간 직통 터널로 이동한다.

#1문제 상황

기존 IPsec VPN은 클라이언트 소프트웨어를 설치하고 설정해야 하므로, 설치 복잡도가 높고 임시 사용자 관리가 어렵다. 특히 원격 근무자가 많아지면 클라이언트 배포와 업데이트 관리 부담이 커진다.

#2핵심 질문

브라우저만으로 간단하게 사내 자원에 접속할 수 있도록 하면서, 필요에 따라 전체 네트워크 연결도 가능하게 할 수 있을까?

#3동작 예시

사용자가 노트북 브라우저에서 FortiGate의 SSL VPN 주소에 접속하면 HTTPS로 보호된 포털 페이지가 열리고, 인증 후 웹만 볼지(웹 모드) 아니면 VPN 클라이언트로 전체 네트워크를 연결할지(터널 모드) 선택할 수 있다.

#4동작 과정

  1. HTTPS 연결사용자가 FortiGate의 SSL VPN 주소에 브라우저로 접속하면, HTTPS 암호화 연결이 수립된다.
  2. 인증 및 모드 제공사용자를 인증한 후, 웹 모드(특정 자원만 웹으로 접근) 또는 터널 모드(VPN 클라이언트 연결) 중 선택할 수 있게 제공한다.
  3. 자원 접근웹 모드는 포털 페이지와 웹 자원만 열어주고, 터널 모드는 VPN 클라이언트를 설치해 사내 전체 네트워크에 접속하게 한다.

기존 정적 라우팅은 각 회선의 용도를 미리 정해놓는다(예: 중요한 트래픽은 MPLS, 인터넷 트래픽은 ISP). 한계는 회선의 지연이 늘어나거나 일부 회선에 장애가 나도, 수동으로 라우팅을 바꿔야 한다는 것이다.

#2핵심 질문

회선의 상태를 실시간으로 감지해 자동으로 최적의 회선을 선택하는 동적 라우팅이 가능할까?

#3동작 예시

MPLS, ISP 1, ISP 2 세 회선을 SD-WAN 멤버로 등록하고 하나의 존으로 묶은 후, 규칙을 정하면 각 트래픽이 상태에 따라 최적의 회선으로 자동 분산된다.

#4동작 과정

  1. 멤버 정의사용 가능한 회선(MPLS, ISP, 전용선 등)을 SD-WAN 멤버로 등록한다.
  2. 존 구성여러 멤버를 하나의 논리적 그룹인 SD-WAN 존으로 묶는다.
  3. 규칙 설정트래픽 유형과 우선순위, 선택 전략(최저 비용, 최적 품질, 로드 밸런싱)을 정의한다.

#1문제 상황

#2핵심 질문

회선이 살아있는 것만으로 충분한가, 실제 통신 품질도 함께 측정해야 하지 않을까?

#3동작 예시

#4동작 과정

  1. 프로브 전송정기적으로 헬스체크 패킷(ICMP 핑, HTTP 요청, DNS 쿼리 등)을 보낸다.
  2. 메트릭 측정왕복 시간(지연), 지연의 변동성(지터), 손실된 패킷 수를 계산한다.
  3. 임계값 판정측정값이 SLA 임계값(threshold)을 충족하면 회선을 사용 가능으로, 미충족이면 사용 불가로 표시한다.

SD-WAN 라우팅과 VPN 오버레이 설계

정적·BGP 라우팅과 IPsec 오버레이(ADVPN 포함)를 SD-WAN 위에 얹어 지사-본사 연결을 구성하는 방법.

→ 06장 VPN 참조

#1문제 상황

SD-WAN은 회선 선택만 제공한다. 그 위에 라우팅(정적 또는 BGP)과 암호화(IPsec)를 계층적으로 더 얹어야 지사-본사 연결이 완성된다. 한계는 여러 계층을 모두 고려하면서 설계 복잡도가 증가한다는 것이다.

#2핵심 질문

SD-WAN 회선 선택 위에 라우팅과 IPsec 암호화를 어떻게 겹쳐 구성하면 견고하고 유연한 지사 연결을 만들까?

#3동작 예시

본사-지사 간 ADVPN IPsec 터널을 SD-WAN 존(MPLS와 ISP 멤버)에 올린 후, BGP로 라우트를 광고하면, MPLS 링크 문제 시 ISP로 자동 우회되며 암호화는 계속 유지된다.

#4동작 과정

  1. 라우팅 설계지사-본사 라우팅을 정적 라우팅 또는 BGP로 정의하고, 라우트 목적지를 SD-WAN 존으로 지정한다.
  2. IPsec 오버레이 수립ADVPN 또는 수동 터널 설정으로 지사-본사 간 IPsec 암호화 터널을 수립한다.
  3. 계층적 통신지사에서 본사로 향하는 트래픽이 먼저 IPsec 터널(암호화)에 진입한 후, 터널 패킷이 SD-WAN 규칙에 따라 MPLS 또는 ISP 회선으로 동적 전송된다.

#5한 줄 요약

회선 선택(SD-WAN), 경로 결정(정적·BGP 라우팅), 암호화(IPsec)를 계층적으로 조합해 효율성과 견고성을 갖춘 지사 연결을 구성하는 것

SD-WAN 고급 구성·클라우드 온램프·운영

애플리케이션 스티어링, SaaS/클라우드 온램프, 모니터링과 문제 해결 등 실제 운영 단계의 고급 주제.

#1문제 상황

기존의 WAN 관리에서는 각 지사나 원격 사무실이 통신사 회선 하나에만 의존했습니다. 그 회선이 끊기면 인터넷이 완전히 단절되고, 회선 속도도 업체와의 계약에 따라 고정되어 있어 변화하는 트래픽에 유연하게 대응할 수 없었습니다. 또한 어느 회선을 써야 빠를지, 어느 애플리케이션이 어느 경로로 가야 할지는 관리자가 일일이 설정해야 했습니다.

#2핵심 질문

여러 개의 서로 다른 인터넷 회선(회사 전용선, 통신사 인터넷, 모바일 회선 등)을 한 방화벽에서 동시에 쓰면서, 각 애플리케이션이 가장 빠르고 안전한 경로로 자동으로 흐르게 할 수 있을까요?

#3동작 예시

FortiGate가 설정된 정책에 따라 실시간으로 회선 상태(지연 시간, 패킷 손실, 대역폭 사용량)를 감시하다가, 송금 애플리케이션은 가장 안정적인 전용선으로, 비디오 스트리밍은 대역폭이 넉넉한 인터넷 회선으로 자동 분기하는 방식입니다.

#4동작 과정

  1. 애플리케이션 기반 분류들어오는 패킷의 출발지, 목적지, 포트, 심지어 애플리케이션 자체를 식별해 어느 그룹에 속하는지 판정합니다.
  2. 회선 선택 및 모니터링분류된 애플리케이션에 맞춰 정의된 정책이 가장 적합한 회선을 선택하고, 그 회선의 실시간 상태를 계속 확인합니다.
  3. 트래픽 경로 결정 및 재조정선택된 회선이 장애가 나거나 성능이 떨어지면, 나머지 회선 중 조건을 만족하는 다음 회선으로 자동 전환합니다.

#5한 줄 요약

여러 회선의 실시간 상태를 감시하면서 각 애플리케이션을 정책 기반으로 가장 적합한 경로에 자동으로 보내고, 회선 장애 시 즉시 다른 경로로 전환하는 지능형 트래픽 관리

SD-WAN 과 ZTNA07-06

ZTNA 기본 - 액세스 프록시와 태그 기반 접근

사용자와 기기 상태(태그)를 매번 확인한 뒤에만 애플리케이션 접근을 허용하는 제로 트러스트 프록시 구조.

#1문제 상황

기존의 네트워크 보안은 방화벽 너머 내부라면 신뢰한다는 전제(경계 기반 보안)에 의존했습니다. 한번 회사 네트워크에 연결되면 사용자 신원을 다시 확인하지 않고 자원에 접근할 수 있었고, 회사 관리 밖의 개인 기기나 원격 접속자도 같은 방식이었습니다. 이렇게 되면 악의적 사용자나 감염된 기기가 내부에 침입하면 광범위하게 데이터에 접근할 수 있었습니다.

#2핵심 질문

사용자나 기기가 애플리케이션에 접근할 때마다 신원, 기기 상태, 보안 수준을 확인한 후에만 그 접근을 허용하려면 어떻게 해야 할까요?

#3동작 예시

사용자가 중요한 데이터베이스에 접근하려 할 때, 시스템이 사용자 신원(AD 계정), 기기 상태(안티바이러스 설치 여부, 암호화 활성화 등을 담은 정보를 태그라고 함), 위치(회사 네트워크인가 원격인가)를 함께 확인한 후 모든 조건을 만족할 때만 접근 권한을 주는 방식입니다.

#4동작 과정

  1. 사용자 및 기기 인증사용자가 애플리케이션 접근을 요청할 때 FortiGate의 액세스 프록시(Access Proxy, 접근을 중개하는 서비스)가 사용자의 신원을 확인하고 기기의 정책 준수 상태를 조사합니다.
  2. 태그 기반 정책 평가기기에 붙은 태그(관리되는 기기인가, 안티바이러스가 활성화되어 있는가 등의 속성 정보)를 검사해 접근 정책과 비교합니다.
  3. 조건부 접근 허가모든 조건을 만족하면 그 사용자/기기만을 위한 보안 터널을 열어 애플리케이션으로의 접근을 허용합니다.

기본적인 ZTNA 구성(사용자와 기기 확인)만으로도 많은 환경에서는 충분하지만, 레거시 시스템이 섞여 있거나 고도로 제한된 요구사항이 있는 조직은 추가적인 유연성이 필요합니다. 예를 들어 기존 SSH 도구나 원격 데스크톱 같은 비표준 프로토콜을 써야 하거나, 기기 신원 확인을 위해 MAC 주소나 IP 주소 같은 네트워크 식별자를 써야 할 수도 있습니다. 기본 설정으로는 이런 다양한 접근 방식을 모두 지원하기 어렵습니다.

#2핵심 질문

웹 브라우저만이 아니라 SSH, RDP, TCP 포트 기반의 애플리케이션까지도 ZTNA로 보호하려면, 그리고 그 과정에서 문제가 생기면 어떻게 진단해야 할까요?

#3동작 예시

FortiGate를 통해 SSH 터널을 설정할 때, 사용자의 인증서(클라이언트가 소유한 암호화된 신원 증명)와 기기의 MAC/IP 기반 식별자를 함께 검증한 후, 특정 TCP 포트로의 트래픽만 중개하는 구성입니다.

#4동작 과정

  1. 프로토콜별 포워딩 설정SSH, RDP, 일반 TCP 포트 등 각 프로토콜에 맞춰 FortiGate의 포트 포워딩(Port Forwarding, 특정 포트로 들어오는 통신을 다른 곳으로 전달하는 기능) 규칙을 정의하고, 각 규칙에 인증서 기반 인증을 적용합니다.
  2. 네트워크 식별자 기반 접근 제어IP/MAC 기반 정책을 추가해 기기의 고유한 네트워크 주소가 미리 등록된 목록에 있는지 확인하는 검증 계층을 넣습니다.
  3. 로그와 인증서를 통한 장애 진단접근 실패 시 FortiGate의 ZTNA 로그와 클라이언트의 인증서 검증 기록을 확인해 어느 단계에서 거부되었는지 파악합니다.

#5한 줄 요약

인증서와 네트워크 식별자를 조합해 비웹 프로토콜의 접근도 보호하고, 로그를 통해 제로 트러스트 접근 제어의 각 단계를 진단할 수 있게 하는 심화 구성 방식

WiFi 컨트롤러 - FortiAP 등록과 SSID 만들기

FortiGate 내장 WiFi 컨트롤러로 FortiAP 를 인증·등록하고 SSID(무선 네트워크 이름)와 보안 방식을 정의해 무선 서비스를 켜는 작업이다.

#1문제 상황

기존에는 각 무선 액세스 포인트(AP, Access Point)를 따로 설정했습니다. 각 AP의 관리 인터페이스에 일일이 접속해 SSID(무선 네트워크 이름), 보안 설정, 채널을 개별적으로 구성해야 했고, 여러 AP가 있을 때 설정이 불일치하거나 펌웨어 업데이트를 하나하나 해야 했습니다. 어느 AP가 제대로 작동하는지도 한 곳에서 모니터링하기 어려웠습니다.

#2핵심 질문

여러 무선 액세스 포인트를 FortiGate 방화벽 화면 하나에서 중앙으로 등록하고, 일관된 SSID와 보안 정책을 한 번에 적용할 수 있을까요?

#3동작 예시

FortiAP(포티 무선 액세스 포인트)를 FortiGate에 등록할 때, FortiGate가 DHCP나 기타 자동 발견 방식으로 FortiAP를 찾아 인증하고, 그 이후로는 FortiGate 웹 화면에서 SSID, WPA 암호, 채널 등을 입력하면 모든 등록된 FortiAP가 같은 설정을 자동으로 받는 방식입니다.

#4동작 과정

  1. FortiAP 자동 발견 및 등록FortiGate가 네트워크 상의 FortiAP를 찾고 상호 인증을 거쳐 자신의 관리 대상으로 등록합니다.
  2. SSID 및 보안 정책 정의FortiGate 관리자가 SSID 이름, WPA3/WPA2 같은 암호화 방식(암호화 방식, 비밀번호를 사용해 무선 신호를 보호하는 기술), 사용자 인증 방식을 정의합니다.
  3. 정책 배포정의된 설정이 등록된 모든 FortiAP로 자동 배포되고 즉시 적용됩니다.

#5한 줄 요약

FortiAP를 FortiGate 중앙 컨트롤러에 등록해 여러 무선 액세스 포인트의 SSID와 보안 설정을 한 곳에서 통일하게 관리하는 중앙화된 무선 관리

무선 운영 - 라디오 설정·로그 AP 탐지·클라이언트 모니터

채널·출력 등 라디오 파라미터를 조정하고, 허가되지 않은 로그(rogue) AP 를 탐지하며, 접속 클라이언트 상태를 모니터링해 무선 품질과 보안을 유지하는 운영 작업이다.

#1문제 상황

무선 네트워크를 구축한 후 설정만 하고 끝내면, 시간이 지나면서 성능이 떨어지거나 보안 문제가 생깁니다. 사용자가 많아지면 특정 채널이 혼잡해지지만 관리자는 그걸 모르고, 회사 몰래 설치된 불법 AP(로그 AP, Rogue AP)가 비밀번호를 가로챌 수 있지만 탐지하지 못합니다. 또한 접속한 클라이언트가 제대로 작동하는지, 신호 강도는 충분한지 알 방법이 없습니다.

#2핵심 질문

무선 채널의 혼잡도와 전력 출력을 실시간으로 조정하고, 허가되지 않은 불법 AP를 자동으로 탐지하며, 접속한 클라이언트의 상태를 모니터링할 수 있을까요?

#3동작 예시

FortiGate의 무선 모니터링 대시보드에서 각 채널의 신호 강도와 간섭 정도를 그래프로 보면서 혼잡한 채널의 FortiAP 출력(전송 전력)을 조정하고, 주변에서 감지된 신호 중 승인되지 않은 SSID가 있으면 "로그 AP 발견" 알림을 받는 방식입니다.

#4동작 과정

  1. 라디오 파라미터 모니터링 및 최적화FortiGate가 각 FortiAP의 채널, 대역폭(2.4GHz인가 5GHz인가), 전송 전력을 실시간으로 감시하고, 간섭이 높은 채널은 자동으로 덜 붐비는 채널로 변경하거나 출력을 조정합니다.
  2. 로그 AP 탐지 및 알림FortiGate가 근처의 모든 무선 신호를 스캔해 미리 등록되지 않은 SSID를 발견하면 관리자에게 알림을 보냅니다.
  3. 클라이언트 상태 모니터링각 무선 클라이언트의 신호 강도, 데이터 속도, 연결 유지 시간, 에러율을 추적해 문제가 있는 클라이언트를 식별합니다.

#5한 줄 요약

무선 환경의 주파수 혼잡도와 보안 위협을 실시간으로 감시하면서 라디오 설정을 자동 최적화하고 불법 AP와 문제 있는 클라이언트를 탐지하는 주파수 수준의 운영 관리

스위치 컨트롤러 - FortiLink과 FortiSwitch 관리

FortiLink 링크로 FortiSwitch 를 FortiGate 에 물려, 스위치의 VLAN·포트 설정과 펌웨어까지 방화벽 화면 하나에서 관리하는 기능이다.

#1문제 상황

기존에는 FortiGate 방화벽과 FortiSwitch 스위치가 독립적으로 작동했습니다. 스위치의 VLAN(여러 물리적 네트워크를 논리적으로 분리하는 기술), 포트 속도, 포트별 보안 정책을 따로 관리했고, 스위치 펌웨어 업데이트도 별도로 해야 했습니다. 방화벽과 스위치 간에 정책 충돌이 생기거나 설정이 불일치할 수 있었습니다. 또한 스위치 상태를 모니터링하려면 스위치 관리 인터페이스에 따로 접속해야 했습니다.

#2핵심 질문

FortiGate 방화벽 화면 하나에서 스위치의 VLAN, 포트 설정, 심지어 펌웨어 업데이트까지 모두 관리할 수 있을까요?

#3동작 예시

FortiLink이라는 전용 링크로 FortiSwitch를 FortiGate에 연결한 후, FortiGate 관리자가 웹 화면에서 "포트 1번은 VLAN 10에 속하고, 포트 2번은 VLAN 20에 속한다"고 설정하면 FortiSwitch가 자동으로 그 명령을 받아 포트를 재구성하는 방식입니다.

#4동작 과정

  1. FortiLink 연결 설정FortiSwitch의 특정 포트를 FortiGate의 특정 포트에 물려 FortiLink 링크를 만들고, 양쪽이 서로를 인증합니다.
  2. 스위치 관리 정책 정의FortiGate 관리자가 VLAN 구성, 각 포트의 속도/듀플렉스(통신 방향 설정, 한 방향만인지 양방향인지), 포트별 접근 제어 정책을 중앙에서 정의합니다.
  3. 설정 배포 및 펌웨어 관리정의된 설정이 FortiSwitch로 배포되고, FortiGate에서 필요시 FortiSwitch의 펌웨어도 업데이트합니다.

#5한 줄 요약

FortiLink으로 FortiSwitch를 FortiGate 중앙 관리 체계에 편입해 스위치의 VLAN, 포트, 펌웨어까지 방화벽 화면 하나에서 통일 관리하는 통합 네트워크 인프라 관리

액세스 계층 보안 - 802.1X·NAC 정책·포트 보안

스위치 포트에 접속하는 단말을 802.1X 인증과 NAC 정책으로 식별해 알맞은 VLAN 에 자동 배치하고, 미인가 단말을 차단하는 접속 지점 보안이다.

→ 08-03 참조

#1문제 상황

기존의 스위치 보안은 물리적 포트 수준에서만 관리했습니다. 포트에 누군가 연결되면 그냥 네트워크 접근을 허용했고, 어떤 단말이 연결되었는지, 그 단말이 회사 관리 대상인지, 보안 정책을 지키는지는 확인하지 않았습니다. 미인가 기기나 감염된 컴퓨터가 포트에 꽂히면 곧장 네트워크에 접근할 수 있었습니다. 또한 한 포트에 여러 기기를 연결하면 제어하기 어려웠습니다.

#2핵심 질문

스위치 포트에 연결되는 단말을 사전에 인증하고, 보안 정책 준수 상태를 확인한 후 알맞은 네트워크 그룹(VLAN)에 자동으로 배치할 수 있을까요?

#3동작 예시

스위치 포트에 노트북이 연결되면 802.1X 인증(포트 수준의 네트워크 접근 제어 프로토콜, 802.1X는 포트 기반 접근 제어, 액세스 포인트라고 부르는 인증 서버에 물어봄)이 시작되어 사용자 ID를 확인하고, 동시에 NAC(Network Access Control) 정책이 그 노트북이 안티바이러스를 설치했는지, 방화벽을 켰는지 검사한 후, 두 조건을 모두 만족하면 "신뢰할 수 있는 기기" VLAN으로 배치하는 방식입니다.

#4동작 과정

  1. 802.1X 포트 인증단말이 스위치 포트에 연결되면 FortiSwitch가 802.1X 요청을 보내 RADIUS(원격 인증 서비스, 중앙의 ID 서버로 인증을 일임하는 프로토콜) 서버(보통 FortiGate나 기업의 Active Directory 같은 인증 서버)에 물어봐 사용자를 식별합니다.
  2. NAC 정책 검사사용자가 인증되면 FortiGate가 그 단말의 운영 체제, 설치된 보안 소프트웨어, 방화벽 상태 같은 컴플라이언스(준수) 정보를 수집해 미리 정의된 NAC 정책과 비교합니다.
  3. VLAN 동적 할당인증과 NAC 검사 결과에 따라 단말을 신뢰할 수 있는 VLAN, 격리된 VLAN, 또는 접근 거부 상태로 자동 배치합니다.

#5한 줄 요약

스위치 포트 수준에서 단말의 사용자 신원과 보안 준수 상태를 확인한 후 조건에 맞춰 알맞은 VLAN으로 자동 배치하는 엔드포인트 기반 접근 제어

관리자 계정과 권한 프로파일

#2핵심 질문

#3동작 예시

#1문제 상황

#2핵심 질문

FortiGate 주 장비가 고장났을 때 자동으로 예비 장비가 트래픽을 이어받게 하려면 어떻게 해야 하나?

#3동작 예시

FortiGate 두 대를 FGCP(Fortinet Clustering Protocol) 클러스터로 묶어 마스터 장비의 모든 설정과 세션 정보를 슬레이브 장비에 계속 동기화하다가, 마스터 장비에 이상이 감지되면 슬레이브 장비가 마스터 역할을 자동으로 인수받습니다.

#4동작 과정

  1. 클러스터 구성두 대 이상의 FortiGate를 같은 클러스터로 묶고, 하나를 마스터로 지정합니다.
  2. 설정 및 세션 동기화마스터의 모든 설정, 방화벽 정책, 활성 세션 정보가 슬레이브 장비로 실시간 동기화됩니다.
  3. 자동 페일오버마스터 장비가 응답하지 않거나 하트비트(heartbeat, 생존 신호)를 보내지 않으면 슬레이브가 자동으로 마스터 역할을 맡아 트래픽 처리를 계속합니다.

FortiGate는 활성 세션(열린 연결) 수와 메모리 사용량에 제한이 있습니다. 트래픽이 계속 증가하면 언젠가 이 한계에 도달합니다. 한계를 넘으면 새로운 연결이 거부되거나 기존 연결이 끊어져 네트워크가 불안정해집니다.

#2핵심 질문

FortiGate의 세션과 메모리 한계에 도달했을 때 어떻게 보호하고, 처리 성능을 더 올릴 수 있나?

#3동작 예시

세션과 메모리 사용량을 지속적으로 감시하다가 임계값(예: 메모리 80%)에 도달하면 conserve 모드로 전환해 최소한의 기능만 유지하고, 동시에 암호화나 고급 검사 같은 무거운 작업을 NP 칩(network processor, 전용 하드웨어)에 오프로드해 CPU 부하를 줄입니다.

#4동작 과정

  1. 자원 감시FortiGate가 활성 세션 개수와 메모리 사용률을 실시간으로 모니터링하고, 설정된 임계값과 비교합니다.
  2. Conserve 모드 활성화메모리나 세션이 한계에 가까워지면 conserve 모드를 자동으로 활성화해 로깅, 자동 업데이트 같은 부차 기능을 일시 중단하고 핵심 보안 기능만 유지합니다.
  3. 하드웨어 오프로드IPS·암호화 같은 무거운 처리를 CPU 대신 NP/CP(암호화 전용 칩)에 오프로드해 전체 처리량과 응답성을 높입니다.

#5한 줄 요약

세션과 메모리 사용량을 감시해 한계 도달 시 conserve 모드로 보호하고, NP/CP 하드웨어 오프로드로 처리 성능을 극대화해 안정성과 처리량을 함께 확보하는 운영 기법

Security Fabric 구성과 보안 등급

여러 포티넷 장비를 루트/다운스트림 관계로 묶어 하나처럼 관리하고, 설정 점검 결과를 점수로 보여주는 기능이다.

#1문제 상황

기존에는 각 포티넷 장비(FortiGate, IPS, 스위치 등)를 독립적으로 관리했다. 각 장비마다 따로 로그인해서 상태를 봐야 했고, 보안 정책도 각 장비별로 따로 설정했으며, 한 장비의 위협 정보를 다른 장비와 공유하기 어려웠다. 보안 설정이 충분한지 점검하려면 전문가가 수동으로 각 설정을 하나하나 확인해야 했다.

#2핵심 질문

여러 포티넷 장비를 하나의 보안 시스템처럼 묶어 중앙에서 통합 관리하고, 보안 설정이 얼마나 잘되어 있는지 점수로 한눈에 알 수 있을까?

#3동작 예시

본사의 FortiGate를 루트(중심)로, 지점들의 FortiGate들을 다운스트림(아래 계층)으로 등록한다. 루트에서 정책을 내리면 모든 다운스트림 장비가 같은 정책을 자동으로 받아 적용하고, 루트는 모든 장비의 세션·위협·로그를 하나의 대시보드에서 본다. 동시에 FortiGate는 방화벽 룰, 인증서 설정, 로깅 활성화, 암호화 강도 같은 1000개 항목을 검사해 점수(Security Rating)를 산출하고, 각 약점을 구체적으로 지적한다.

#4동작 과정

  1. 루트-다운스트림 연결FortiManager를 통해 여러 FortiGate를 루트-다운스트림 계층 구조로 등록하면, 루트에서 아래 장비들을 제어할 수 있는 통로가 열린다.
  2. 정책 및 로그 동기화루트가 내린 정책이 자동으로 다운스트림에 적용되고, 모든 장비의 로그, 세션 정보, 탐지 위협이 루트로 모인다.
  3. 자동 보안 평가 및 개선 권고Security Rating 엔진이 설정을 검사하고 점수를 매기며, 점수를 높이기 위한 구체적 개선 조치(예: "AV 시그니처 업데이트 활성화", "로깅 레벨 상향")를 제시한다.

#5한 줄 요약

분산된 보안 장비들을 루트-다운스트림 관계로 묶어 중앙 관리를 실현하고 자동 검사로 보안 수준을 점수화해 개선하도록 하는 것

#1문제 상황

기존에는 AWS, Azure, 온프레미스 네트워크처럼 여러 환경의 IP 주소 범위나 대역을 FortiGate의 주소 객체로 등록할 때, 관리자가 수동으로 문서를 보며 입력했다. 클라우드 환경이 계속 변하거나 새로운 서버가 추가되면 그때마다 FortiGate 설정을 다시 업데이트해야 했고, 이 과정에서 실수가 생기거나 정보가 최신이 아닐 수 있었다.

#2핵심 질문

AWS, Azure, SDN, 온프레미스 같은 외부 시스템의 주소·사용자·위협 정보를 FortiGate가 자동으로 받아와 동기화할 수 있을까?

#3동작 예시

AWS Connector를 FortiGate에 설정해서 AWS API 키를 입력하면, FortiGate가 AWS API를 주기적으로(예: 매시간) 호출해 EC2 인스턴스 IP, VPC 서브넷, 보안 그룹 정보 같은 것을 자동으로 받아온다. 그 정보는 FortiGate의 주소 객체로 자동 생성되거나 업데이트되므로, AWS 인프라가 변할 때마다 FortiGate의 주소 객체도 함께 변경된다.

#4동작 과정

  1. 커넥터 등록 및 인증AWS, Azure 같은 외부 시스템에서 API 키나 서비스 계정을 발급받아 FortiGate의 커넥터 설정에 입력한다.
  2. 자동 데이터 수집FortiGate가 정해진 주기마다(또는 이벤트 기반으로) 외부 시스템의 API를 호출해 변경된 주소, 사용자 정보, 위협 정보 등을 받아온다.
  3. 객체 및 정책 자동 반영받아온 정보로 주소 객체, 사용자 그룹을 자동으로 생성·수정하고, 기존 보안 정책에 반영된다.

#5한 줄 요약

외부 시스템과의 자동 연동으로 주소·사용자·위협 정보를 실시간 동기화하고 수동 입력의 번거로움과 버전 관리 문제를 없애는 것

#2핵심 질문

특정 보안 이벤트가 발생했을 때 사람의 개입 없이 자동으로 여러 대응 조치를 동시에 실행할 수 있을까?

#3동작 예시

"높은 등급의 IPS 위협이 탐지되면(트리거) 자동으로 Slack 채널에 알림을 보내고(액션1), 그 공격 출발지 IP를 차단 정책에 추가하고(액션2), 외부 SIEM으로 원본 로그를 전송한다(액션3)"는 규칙을 스티치로 만든다. 위협이 탐지되는 순간 이 세 가지가 동시에 실행된다.

#4동작 과정

  1. 트리거 정의FortiGate의 이벤트 중 "IPS 고위협 탐지", "비정상 로그인 횟수 초과", "정책 위반" 같은 조건 1개를 선택해 언제 자동화를 시작할지 정한다.
  2. 액션 구성 및 순서 설정트리거가 발생할 때 실행할 1개 이상의 액션(메일/Slack 발송, 정책 수정, 로그 수집, CLI 스크립트 실행, 외부 웹훅 호출 등)을 순서대로 엮는다.
  3. 자동 실행 및 감사트리거 조건이 만족되면 정의된 액션들이 자동으로 연쇄 실행되고, 어느 액션이 성공·실패했는지 로깅되어 나중에 감사(audit)할 수 있다.

#2핵심 질문

FortiGate를 통과하는 트래픽, 현재 활성 세션, 탐지된 위협을 실시간으로 한 화면에서 확인하고 빠르게 문제를 발견할 수 있을까?

#3동작 예시

대시보드에서 CPU 사용률, 메모리, 네트워크 대역폭 사용량, 현재 활성 세션 수, 탐지된 악성 파일 건수, 차단된 공격 건수 같은 10~20개의 주요 지표를 위젯(작은 창) 형태로 배열해 놓는다. 관리자는 한 화면에서 모든 중요 상태를 보고, 숫자나 그래프가 비정상이면 FortiView나 상세 로그 화면으로 들어가 원인을 추적한다.

#4동작 과정

  1. 대시보드 위젯 구성관리자가 보고 싶은 지표(트래픽 추이 그래프, 위협 분류별 개수, 세션 상태, 디스크 여유도 등)를 선택해 하나의 화면에 배치한다.
  2. 실시간 데이터 수집 및 위젯 갱신FortiGate가 수집하는 모니터링 데이터가 1초~수초 단위로 업데이트되어 각 위젯에 반영된다.
  3. 드릴다운 분석위젯의 숫자나 그래프를 클릭하면 FortiView(세로 깔때기 모양으로 트래픽을 분류해 보여주는 시각화)나 로그 상세 페이지로 이동해 출발지·도착지·프로토콜·응용 프로그램별 분석을 할 수 있다.

#5한 줄 요약

주요 지표들을 위젯으로 시각화해 FortiGate의 모든 중요 상태를 실시간으로 한 화면에 보여주고 빠른 문제 인식과 대응을 가능하게 하는 것

로깅: 로그 종류·저장 대상·필터·리포트

트래픽·이벤트·보안 로그를 어디에 남기고 어떻게 걸러 보고서로 만들지 정하는 기록 체계다.

→ 10-04 참조

#1문제 상황

기존에는 FortiGate의 모든 로그가 디바이스 내부 디스크에만 저장되었다. 디스크 용량이 제한되어 있으므로 이전 로그가 자동으로 삭제되었고, 수십만 개의 로그 중에서 필요한 것을 찾기 어려웠으며, 여러 FortiGate의 로그를 한 곳에서 비교·분석할 수 없었다. 또한 장기 보존이 필요할 때는 수동으로 로그를 내려받아야 했다.

#2핵심 질문

트래픽, 보안 이벤트, 정책 위반 같은 여러 종류의 로그를 중앙 저장소에 오래 보관하고, 필터로 빠르게 찾고, 자동으로 리포트를 만들 수 있을까?

#3동작 예시

로그를 FortiGate 내부 디스크, Syslog 서버, Splunk, ElasticSearch, Azure Log Analytics, AWS S3 같은 여러 저장소에 동시에 보낼 수 있도록 설정한다. 예를 들어 "높은 등급의 IPS 탐지 로그는 Splunk로 실시간 전송해서 즉시 알림을 받고, 모든 트래픽 로그는 아카이브용으로 S3에 매일 저장한다"는 식이다.

#4동작 과정

  1. 로그 종류 선택트래픽 로그(모든 세션 정보), 이벤트 로그(시스템 변화 및 설정 변경), 보안 로그(위협 탐지, 정책 위반, 침입 탐지), 시스템 로그(부팅, 하드웨어 에러) 등 필요한 종류를 정한다.
  2. 저장 대상과 필터 설정어느 종류의 로그를 어느 저장소로 보낼지, 그리고 필터 조건(예: 높은 등급 위협만, 차단된 트래픽만)을 정한다.
  3. 리포트 생성 및 배포모아진 로그를 자동으로 분석해 일일·주간·월간 리포트(예: "이번 주 탐지 위협 40건, 차단율 95%, 주요 공격국가 3개")를 만들고 이메일로 자동 발송한다.

#5한 줄 요약

여러 종류의 로그를 다양한 저장소로 분산 보관하고 필터와 리포트로 필요한 정보를 빠르게 추출하며 장기 보존과 감사(audit) 추적성을 가능하게 하는 것

문제 해결 도구: 디버그 플로우·패킷 캡처·진단 명령

패킷이 어느 정책·경로에서 어떻게 처리되는지 CLI와 캡처로 추적해 원인을 찾는 진단 수단이다.

#1문제 상황

기존에는 네트워크에 문제가 생기면 관리자가 "왜 이 트래픽이 차단되는가?", "왜 이 정책이 적용 안 되는가?" 같은 질문에 답하려고 FortiGate 로그를 수동으로 뒤져야 했다. 로그가 많으면 관련 항목을 찾기 어렵고, 패킷이 FortiGate 내부에서 어느 정책을 타고 어느 보안 모듈을 거쳐서 어떤 결과가 나왔는지 추적하기 복잡했다.

#2핵심 질문

특정 패킷이 FortiGate 내에서 어느 정책·보안 모듈을 거쳐 어떤 결과(통과·차단·수정)로 처리되는지 단계별로 추적할 수 있을까?

#3동작 예시

CLI에서 diagnose debug flow filter add 192.168.1.100 192.168.2.50 명령으로 출발지 192.168.1.100에서 도착지 192.168.2.50로 가는 패킷만 추적하도록 필터를 걸고, diagnose debug flow trace start 명령으로 추적을 시작한다. 그러면 FortiGate가 그 패킷이 어느 ingress 인터페이스에 도착했는지, 매칭된 정책명이 무엇인지, IPS/안티바이러스 같은 보안 모듈에서 어떤 처리를 받았는지, 최종적으로 어느 egress 인터페이스로 나가는지를 라인 단위로 보여준다.

#4동작 과정

  1. 추적 대상 필터링CLI나 GUI에서 디버그 플로우 필터를 설정해 특정 출발지, 도착지, 포트만 추적하도록 제한한다. (필터를 쓰지 않으면 로그가 너무 많아서 읽을 수 없다.)
  2. 패킷 흐름 추적 및 기록필터에 매칭되는 패킷이 FortiGate를 지나갈 때, 매칭된 정책명, 통과한 보안 모듈(IPS 탐지 여부, AV 판정), 최종 결과(허용·차단·수정)를 시간순으로 기록한다.
  3. 패킷 캡처와 상세 분석동시에 tcpdump 명령으로 패킷의 헤더와 페이로드 원본을 파일로 저장해서 WireShark 같은 분석 도구로 네트워크 수준의 상세 정보를 확인한다.

#5한 줄 요약

특정 패킷의 전체 내부 경로(ingress→정책 매칭→보안 모듈 처리→egress)를 추적해 네트워크 문제의 원인을 정확히 찾고 설정을 올바르게 수정하도록 하는 것
