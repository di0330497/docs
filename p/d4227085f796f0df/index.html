AWS Certified Developer – Associate(DVA-C02)는 클라우드에서 애플리케이션을 개발하고 배포·운영하는 일을 실제 AWS 서비스 사용법으로 검사하는 자격 시험이다.

#1문제 상황

AWS를 쓰려면 무엇을 어디까지 해야 하는지가 막연하다. 개발자는 코드를 짜고 시험하고 배포하고 오류를 고치는 일을 반복하지만, 어디까지가 개발자의 몫인지 기준이 없다.

AWS Certified Developer – Associate(DVA-C02)는 AWS 클라우드 애플리케이션을 개발하고 시험하고 배포하고 디버깅하는 능력을 재는 시험이다. 범위는 developing, testing, deploying, and debugging AWS Cloud-based applications로 정리돼 있다.

#2핵심 질문

AWS 위에서 애플리케이션을 개발하고 배포할 때 꼭 알아야 할 AWS 서비스는 무엇일까?

#3동작 예시

신입 개발자가 주문 처리 애플리케이션을 만든다. 코드를 AWS Lambda에 올려 시험하고, Amazon ECR에 이미지를 저장해 배포하고, CloudWatch Logs에서 오류를 찾아 고친다.

이렇게 이어지는 AWS 서비스 사용 능력의 범위가 시험에 들어가는지 확인하려고 시험 안내 페이지를 본다.

#4동작 과정

  1. 범위를 정한다시험이 대상으로 삼는 AWS 서비스 목록을 확인한다. 범위는 Develop and optimize applications on AWS, Package and deploy by using continuous integration and continuous delivery (CI/CD) workflows, Secure application code and data, Identify and resolve application issues 네 갈래로 나뉜다.
  2. 범위에 든 서비스를 익힌다목록에 있는 Amazon EC2, AWS Lambda, Amazon ECS, Amazon DynamoDB 같은 서비스를 어디에 쓸지 정한다. 각 서비스는 Analytics, Compute, Database 같은 분류로 묶여 제시된다.

아키텍처 패턴을 구별한다

애플리케이션 코드를 어떻게 조립할지 정해 놓은 구조로, 한 컴퓨터 안에서 돌아가는 서버리스·단일 서버·컨테이너와 여러 컴퓨터로 나누는 분산 방식처럼 부품을 나누고 서로 부르는 방식이 서로 다른 패턴이다.

먼저 알아야 할 것 01-01

#1문제 상황

AWS 위에서 돌아가는 애플리케이션 코드를 짤 때 부품을 어떻게 나눌지 정하지 않으면 나중에 고치기 어렵다. 하나의 덩어리로 짜면 한 부분의 문제가 전체로 번진다.

아키텍처 패턴은 코드를 어떤 부품으로 나누고 서로 어떻게 부르는지 정한 구조다. 구별 대상은 event-driven, microservices, monolithic, choreography, orchestration, fanout다.

#2핵심 질문

같은 기능을 만들더라도 코드 조립 방식을 어떻게 다르게 고를 수 있는가?

#3동작 예시

주문이 들어온다. 주문 처리 애플리케이션이 알림을 보내야 해서 주문이 끝난 뒤 알림 모듈을 따로 부른다.

구조를 어떻게 잡느냐에 따라 이 호출이 바로 일어나지, 이벤트 큐를 거쳐 나중에 일어나지가 갈린다.

#4동작 과정

  1. 한 덩어리로 짠다monolithic은 모든 기능을 한 프로세스에 함께 둔다. 배포가 단순하지만 한 부분의 문제가 전체 실행에 영향을 준다.
  2. 여러 부품으로 나눈다microservices는 기능을 서비스 단위로 잘라 각각 배포한다. 이벤트를 주고받는 event-driven은 작업이 끝난 사실을 알림 서비스로 알리고 각자가 반응한다.
  3. 나눠 부르는 방식을 정한다orchestration은 중앙 지휘자가 각 서비스에 순서대로 일을 지시하고, choreography는 각 서비스가 서로의 사건을 보고 스스로 다음 일을 정한다. fanout은 한 요청을 여러 목적지로 한꺼번에 흘리는 방식이다.
  4. 확인해 볼 것Skill 1.1.1에 나열된 예시 패턴 목록을 시험 안내에서 찾아 읽는다.

#1문제 상황

#3동작 예시

메시지가 쌓인 것을 재고 쪽이 먼저 읽을 수 있을 때 처리하므로, 재고 모듈이 잠깐 멈춰도 주문 처리는 계속된다.

#4동작 과정

  1. 읽지 않고 데이터만 본다느슨하게 결합된 부품은 상대 구현을 몰라도 정해진 데이터만 주고받는다. 그 경로가 application integration, 즉 부품 사이의 연결 방식이다.
  2. 기다렸다 답을 받는다동기 호출은 상대가 답할 때까지 현재 흐름이 멈춘다. 순서가 확실한 작업에 쓴다.

#3동작 예시

외부 결제 회사의 API에 주문 승인 요청을 보낸다. 그 회사가 잠시 응답하지 않아 요청이 멈춘다.

코드가 기다리지 않고 곧바로 실패를 돌려주되, 몇 번 더 재시도하고 계속 실패하면 그 주문을 보류 상태로 남긴다.

#4동작 과정

  1. 여러 벌로 나눠 띄운다같은 기능을 여러 인스턴스에서 돌려 한 곳이 멈춰도 요청이 다른 곳으로 넘어간다.
  2. 다시 시도한다정해진 횟수까지 같은 요청을 반복해 일시적인 실패를 넘긴다. 이것을 재시도 로직이라 한다.
  3. 실패를 격리한다회로 차단기(circuit breaker)는 실패가 이어지면 그 호출을 잠시 아예 막는다. 옆 부품이 그 실패를 같이 당하지 않게 하는 것이다.

#1문제 상황

Lambda 함수는 코드 한 덩어리를 올리면 자동으로 실행되며, 같은 코드가 호출마다 새 환경에서 돈다. 그런데 함수마다 메모리와 시간 제한, 환경 변수 값이 다르고 그걸 코드 안에 직접 적으면 배포할 때마다 고쳐야 한다.

그래서 Lambda 함수는 콘솔에서 이름, 런타임, handler, 메모리, timeout 같은 설정 항목으로 동작을 고정한다. 함수 밖에서 값을 바꾸면 코드를 다시 올리지 않아도 된다.

#2핵심 질문

#4동작 과정

  1. 함수를 정의한다Lambda 콘솔에서 이름과 런타임, handler를 정해 만든다. handler는 코드 안에서 요청을 받을 함수의 이름이다. layers로 공통 라이브러리 묶음을 붙이고 extensions로 AWS 도구나 보안 필터를 더한다.
  2. 동작 값을 고정한다memory와 timeout, concurrency를 정한다. concurrency는 같은 함수가 동시에 처리할 수 있는 요청 수의 상한이다. environment variables에 environment variables와 parameters를 넣어 값만 따로 둔다.

이벤트 수명주기와 오류 처리

Lambda 함수는 호출 이벤트를 받아 실행하고 결과를 반환하는 한 사이클을 반복하며, 코드에서 예외를 던지면 호출이 실패한 것으로 기록되고 재시도와 오류 처리(dead-letter 큐, 실패 지점) 설정이 적용된다.

먼저 알아야 할 것 03-02

→ 03-02 참조

#1문제 상황

Lambda 는 호출 이벤트를 받을 때마다 실행을 시작해 결과를 반환하고 멈춘다. 그런데 처리 도중 예외가 나면 호출은 실패한 것으로 남고 그 이벤트만 사라진다. 실패한 데이터를 다시 보려면 어디서 왜 멈췄는지 남는 기록이 있어야 한다.

그래서 Lambda 는 이 한 사이클을 오류 처리까지 포함해 관리한다. 실패한 호출은 재시도하고, 그래도 못 되면 Lambda Destinations나 dead-letter queues로 넘긴다.

#2핵심 질문

Lambda 호출이 실패했을 때 그 이벤트를 어디로 넘기고 무엇을 남길까?

#3동작 예시

S3 에 파일이 올라와 함수가 시작됐는데 코드에서 파싱 중 예외가 났다. 함수 화면의 오류 지점에 같은 호출이 반복으로 실패한 기록이 남아 있고, 재시도 한도를 넘은 호출은 지정한 대기열로 넘어가 있다.

#4동작 과정

  1. 이벤트를 받는다호출 이벤트가 들어오면 새 실행 환경에서 핸들러가 실행되고 결과가 호출한 쪽에 돌아간다. 성공과 실패는 실행 기록으로 남는다.
  2. 실패를 다시 건다호출이 실패하면 자동 재시도가 반복된다. 이 흐름은 실행 폴로워가 관리해 같은 실패가 반복되는지 지켜본다.
  3. 실패를 넘긴다Lambda Destinations로 성공·실패 결과를 다른 함수나 대기열로 보낼 수 있고, dead-letter queues는 끝내 처리되지 못한 호출을 SQS나 SNS로 넘긴다. 넘긴 뒤에는 어떤 대상을 쓰느냐가 달라진다.

먼저 알아야 할 것 02-01

#1문제 상황

Amazon DynamoDB 는 데이터를 파티션이라는 통에 나누고 각 파티션을 따로 처리한다. 그런데 파티션 키로 값이 적은 쪽만 쓰면 몇 개의 통만 계속 바빠지고 나머지는 비어 있다.

그래서 파티션 키는 서로 다른 값이 최대한 많이 나오도록 고른다. 기수(cardinality)는 서로 다른 값의 개수이며, 이 값이 높아야 파티션 접근이 고르게 퍼진다.

#2핵심 질문

#3동작 예시

주문 테이블의 파티션 키를 주문 상태로만 정했다. 대기 중인 주문이 한 파티션에 몰려 그 통만 느려진다. 주문 번호를 키로 바꾸니 같은 순서로 들어온 데이터가 여러 파티션에 나뉘어 처리된다.

#4동작 과정

  1. 키 후보를 든다주문 번호, 사용자 ID, 기기 ID처럼 개별 항목마다 달라지는 값을 고른다. 상태나 국가처럼 몇 가지 값뿐인 것은 기수가 낮다.
  2. 키로 파티션을 나눈다DynamoDB 는 파티션 키 값을 해시해 어느 파티션에 넣을지 정한다. 키 값이 서로 다를수록 파티션도 고르게 찬다.
  3. 접근을 나눠 확인한다balanced partition access를 보려면 각 파티션의 항목 수와 저장소 지표를 비교해 편차가 큰 파티션을 찾는다. Database 관점에서 조회 패턴이 파티션 키 하나만 보게 설계되는지도 함께 본다.
  4. 확인해 볼 것테이블 화면의 파티션 항목 수를 비교해 어느 한쪽에 몰렸는지 확인한다.

Query와 Scan의 차이

Query는 파티션 키를 정확히 지정해 그 안의 항목만 찾고, Scan은 테이블 전체를 훑으며 조건 필터를 적용하므로 데이터가 많으면 느리다.

먼저 알아야 할 것 04-02

→ 04-02 참조

#1문제 상황

파티션 키가 고르게 나뉘도록 테이블을 잘 짜놓아도(→ 04-01) 데이터를 찾는 방법이 옳지 않으면 항목 수에 비례해 느려진다. 조건 하나만 걸고 싶은데 수백만 건을 다 훑으면 읽기 용량과 시간이 함께 늘어난다.

그래서 DynamoDB 는 두 가지 찾기 방법을 따로 둔다. Query는 키를 보고 한 파티션만 찾고, Scan은 전체를 훑어 조건으로 거른다.

#2핵심 질문

키가 정해진 항목을 찾을 때 일부만 훑는 방법과 전체를 훑는 방법을 어떻게 나눠 쓰는가?

#3동작 예시

한 사용자의 주문 목록을 띄운다. 사용자 ID를 파티션 키로 지정한 Query를 쓰면 그 파티션만 읽고 목록이 나온다. 상태 조건이 필요해 Scan을 썼다면 테이블 전체를 읽고 버린 항목이 대부분이었다.

#4동작 과정

  1. 파티션을 정한다Query는 파티션 키를 정확히 지정해야 한다. 정렬 키 조건을 더해 그 안에서 범위를 좁힌다.
  2. 항목을 훑는다Scan은 테이블 전체를 읽고 filter expression으로 조건에 걸린 것만 남긴다. 페이지 크기와 반복 호출로 나눠 읽지만 비용은 여전히 늘어난다.
  3. 읽기 용량을 본다키가 정해져 있는 접근이면 Query가 낫고, 키에 없는 속성으로 찾아야 할 때만 Scan을 쓴다.
  4. 확인해 볼 것DynamoDB 콘솔에서 같은 조건을 Query와 Scan으로 각각 실행해 읽은 항목 수가 다른지 확인한다.

파티션 키와 정렬 키로 Primary Key를 만들고, 다른 속성을 기준으로 찾기 위해 보조 인덱스(GSI·LSI)를 정의하는 일.

먼저 알아야 할 것 04-03

→ 04-03 참조

#1문제 상황

테이블에 항목을 넣을 때 DynamoDB는 정해 둔 키를 기준으로만 항목을 찾아 준다(→ 04-03). 파티션 키와 정렬 키로 만든 Primary Key 밖의 속성, 예를 들어 이메일 주소로 유저를 찾는 요구는 이 키 구조로는 처리되지 않는다.

Define Amazon DynamoDB keys and indexing는 읽는 기준을 더 늘리는 일이다. 보조 인덱스를 정의하면 같은 테이블에서 여러 기준으로 항목을 찾을 수 있다.

#2핵심 질문

같은 데이터를 여러 기준으로 찾아야 할 때 키와 인덱스를 어떻게 정의할까?

#3동작 예시

주문 테이블에 주문번호로 항목을 찾고, 그 주문의 유저가 가진 다른 주문도 함께 보고 싶다고 한다. 유저 ID를 보조 인덱스로 추가한 뒤, 애플리케이션 코드가 인덱스 이름을 지정해 유저 ID로 주문을 조회한다.

#4동작 과정

  1. Primary Key를 만든다파티션 키와 정렬 키를 합쳐 항목을 찾을 기준을 정한다. 키 값의 분산이 고르지 않으면 특정 파티션에 항목이 몰린다(→ 04-01).
  2. 보조 인덱스를 정의한다다른 속성을 찾는 기준을 더한다. GSI는 파티션 키와 정렬 키를 새로 가져 테이블 전체의 일부 항목만 담고, LSI는 같은 파티션 안에서 정렬 속성만 추가한다. 인덱스는 쓰기마다 함께 갱신되므로 많은 인덱스는 쓰기 비용을 올린다.
  3. 쿼리를 보낸다애플리케이션이 인덱스 이름과 키 값을 지정해 요청한다. Query는 지정한 파티션 안에서만 훑어 빠르고, Scan은 테이블 전체를 훑으며 느리다(→ 04-03).
  4. 확인해 볼 것DynamoDB 콘솔에서 해당 테이블의 인덱스 목록에 정의한 GSI와 LSI가 보이는지 확인한다.

#5한 줄 요약

DynamoDB 키와 색인 정의는 찾을 기준을 Primary Key와 보조 인덱스로 늘리는 일입니다.

데이터 직렬화와 저장소 유지 관리

객체를 바이트 형태로 바꿔 저장·전송하는 직렬화(예: JSON, AttributeValue marshalling)를 쓰고, TTL 삭제와 백업·PITR 등으로 저장소를 건강하게 유지하는 것.

먼저 알아야 할 것 04-04

→ 04-04 참조

#1문제 상황

애플리케이션은 객체를 만들어 저장소로 보내고, 다시 읽어 쓸 때 같은 형태가 필요해 있다. 메모리에 있는 객체를 그대로 저장소로 보낼 수는 없으므로 변환이 필요하고, 변환 방법이 달라지면 읽은 값이 원래 모양이 아니다.

Serialize and deserialize data to provide persistence to a data store는 이 변환을 정해 둔 규격으로 수행하게 한다. Use, manage, and maintain data stores는 저장된 데이터의 삭제 시점과 복구 수단까지 정한다.

#2핵심 질문

객체를 저장소에 어떻게 바꿔 보내고, 저장된 데이터를 오래 안전하게 지키는가?

#3동작 예시

주문 객체를 JSON 문자열로 바꿔 항목 속성에 넣고 저장한다. 나중에 읽을 때 다시 객체로 되돌려 화면에 보여 준다. 오래된 임시 데이터는 TTL 설정이 지난 뒤 자동으로 사라지고, 실수로 지워져도 PITR로 시간대를 골라 되돌린다.

#4동작 과정

  1. 직렬화하고 되돌린다객체를 바이트나 JSON 같은 형태의 값으로 바꿔 저장하고, 읽은 값을 같은 규격으로 역변환해 원래 객체를 되살린다. DynamoDB에서는 항목 값을 AttributeValue로 감싸 저장하고, 읽을 때도 같은 규격으로 되돌려야 값이 일치한다.
  2. 수명을 정한다TTL 속성에 만료 시각을 넣어 지난 항목을 저장소가 지우게 한다. 지워지기 전 알림이 필요하면 DynamoDB Streams로 삭제 이벤트를 먼저 받는 방법이 있다.
  3. 복구 수단을 둔다Amazon RDS와 Amazon Aurora에서는 자동 백업과 PITR로 지워진 구간을 시간 단위로 되살린다. 데이터 규모가 커 분석용으로 따로 쓰면 Amazon Redshift가 쓰인다.
  4. 확인해 볼 것콘솔의 백업 목록에서 마지막 자동 백업 시각과 보존 기간이 어떻게 설정돼 있는지 확인한다.

#5한 줄 요약

데이터 직렬화와 저장소 유지 관리는 객체를 바꿔 저장하고 정해진 수명으로 지우되 되돌릴 수 있게 두는 일입니다.

데이터 수명주기·캐시·전용 저장소

TTL로 데이터의 수명주기를 정하고 ElastiCache로 자주 읽는 값을 빠르게 만들고, Aurora·Redshift 같은 전용 저장소를 목적에 맞게 함께 쓸 수 있다는 점.

먼저 알아야 할 것 04-05

→ 04-05 참조

#1문제 상황

항목은 계속 쌓이지만 과거 기록을 오래 들고 있을 필요는 없다. 그대로 두면 저장소가 느려지고, 반대로 자주 읽는 값을 매번 원본에서 읽으면 요청마다 지연이 늘어난다.

Manage data lifecycles는 데이터를 얼마나 살려 둘지 정한다. Use data caching services와 Use specialized data stores based on access patterns는 읽는 방식에 맞춰 저장소를 갈라 쓴다.

#2핵심 질문

데이터를 얼마나 오래 보관하고, 자주 읽는 값은 어디에서 빠르게 가져올까?

#3동작 예시

주문 목록 화면을 열 때마다 주문 저장소를 직접 읽는 대신 캐시에서 먼저 찾는다. 새로 들어온 주문은 캐시에도 함께 넣고, 일주일이 지난 주문은 TTL이 지나면 자동으로 지운다.

#4동작 과정

  1. 수명주기를 정한다DynamoDB의 TTL로 항목마다 만료 시각을 지정한다. 지난 항목은 저장소가 백그라운드에서 지워 저장소가 늘어나지 않게 한다.
  2. 캐시를 앞에 둔다Amazon ElastiCache로 자주 읽는 값을 메모리에 저장해 두었다가 돌려준다. 원본 저장소를 다시 읽지 않으므로 같은 요청이 빨라지고, 캐시는 DB 대신 채워 세워 사본으로 쓰는 쪽이다.
  3. 전용 저장소를 골라 쓴다형태와 내용으로 항목을 찾아야 하는 일은 DynamoDB의 키와 인덱스로는 어려우니 Amazon OpenSearch Service에 검색용 사본을 둔다. 시간별 집계와 분석은 Amazon Athena 같은 분석 경로로 따로 처리한다.
  4. 확인해 볼 것DynamoDB 콘솔의 TTL 항목 설정과 ElastiCache 콘솔의 캐시 노드 목록에서 어떤 키가 들어 있는지 확인한다.

#5한 줄 요약

데이터 수명주기·캐시·전용 저장소는 오래된 값은 지우고 자주 읽는 값은 앞단에서 즉시 내주는 구성입니다.

신원 공급자를 이용한 연동 접근

자체 로그인 시스템 대신 회사가 이미 쓰는 외부 신원 공급자(예: 사내 Active Directory, Okta 등)의 사용자 계정을 AWS 서비스가 그대로 인정해 로그인할 수 있게 하는 것.

먼저 알아야 할 것 01-03

#1문제 상황

회사에 사내 Active Directory나 Okta 같은 계정 체계가 이미 있다. AWS 쪽에 사용자 계정을 따로 만들고 비밀번호를 두 번 관리하면, 계정이 늘 때마다 두 곳의 정보를 맞춰야 하고 퇴사자를 놓치기 쉽다.

Use an identity provider to implement federated access는 이 중복을 없앤다. 외부 신원 공급자가 확인한 결과만 AWS가 신뢰해 로그인을 받아 준다.

#2핵심 질문

기존 회사 계정으로 AWS에 로그인하게 만들려면 어떻게 연결하는가?

#3동작 예시

직원이 사내 계정으로 로그인 페이지를 연다. Amazon Cognito가 사내 Active Directory로 그 계정이 유효한지 확인하고, 결과에 맞게 AWS 임시 자격 증명을 만들어 토큰으로 넘겨 준다. 콘솔에는 그 직원의 권한으로 바로 들어간다.

#4동작 과정

  1. 신원 공급자를 연결한다Amazon Cognito 사용자 풀에서 사내 계정 체계를 신뢰할 공급자로 등록한다. 신원 공급자란 사용자 계정을 갖고 로그인을 확인해 주는 외부 시스템이다.
  2. 로그인을 받는다사용자가 사내 계정으로 들어가면 자격 증명이 AWS가 이해하는 형식으로 바뀌어 돌아온다. 이 방식이 연동(federation), 즉 여러 시스템이 하나의 계정 체계를 함께 쓰는 것이다.
  3. 권한을 정한다누가 이 방식으로 들어와도 허용될지는 IAM 정책과 사용자 풀의 그룹 매핑이 함께 정한다(→ 05-04). 신뢰는 로그인 확인까지만이고, 무슨 작업을 할지는 IAM이 막는다.
  4. 확인해 볼 것사용자 풀 설정에서 연결된 공급자 목록이 보이는지 확인한다.

#5한 줄 요약

신원 공급자를 이용한 연동 접근은 사외 계정 체계를 그대로 AWS 로그인에 물리는 방식입니다.

베어러 토큰으로 애플리케이션을 잠근다

먼저 알아야 할 것 05-01

→ 05-01 참조

#1문제 상황

애플리케이션 API는 누구나 호출할 수 있는 창구다. 안에서 확인할 로그인 세션이 없으므로, 호출마다 이 사람이 누구인지와 접근 권한이 있는지를 따로 알려 줘야 한다.

Secure applications by using bearer tokens은 그 확인을 표준 토큰 하나로 해결한다. 요청마다 같은 자격 증명을 붙여 보내지 않아도 호출자는 확인된다.

#2핵심 질문

API를 호출할 때 이 사람이 누구이며 권한이 있는지 어떻게 증명하는가?

#3동작 예시

웹 앱이 Amazon Cognito에서 로그인해 받은 토큰을 브라우저에 담아 둔다. 상품 목록을 요청할 때 그 토큰을 Authorization 헤더에 실어 보낸다. 서버는 서명과 만료 시각을 확인하고, 안 지났으면 목록을 돌려준다.

#4동작 과정

  1. 토큰을 받는다로그인에 성공하면 서버는 짧은 만료를 가진 서명 있는 토큰, 대표적으로 JWT를 돌려준다. 서명은 내용에 보이지 않는 표식으로 출처를 확인하게 한다.
  2. 헤더에 실어 확인받는다클라이언트는 호출마다 이 증장을 Authorization 헤더에 넣는다. Amazon API Gateway는 서명과 만료 시각과 발급자를 확인해 통과시킨다.
  3. 신원을 다음 단계로 넘긴다통과한 요청에 담긴 신원 정보를 AWS AppSync처럼 리졸버가 다음 단계에 넘기므로, 같은 토큰으로 접근 범위가 갈린다. 토큰이 만료되면 호출이 거절되고 재발급은 사용자 풀에서 관리한다.
  4. 확인해 볼 것API 요청의 Authorization 헤더에 토큰이 실리는지, 토큰을 빼면 요청이 거절되는지 확인한다.

#5한 줄 요약

베어러 토큰은 로그인 결과를 짧은 증장으로 바꾸어 매 호출마다 함께 보내는 방식입니다.

콘솔로 리소스를 만들면 사람이 손댈 때마다 클릭을 반복해야 하고, 한 번에 백 개는 불가능하다. 같은 자원이 계속 생기고 지는 것을 자동화하고 싶은데 사람 로그인은 코드가 대신할 수 없다.

Configure programmatic access to AWS는 이 반복을 없앤다. 코드 안에서 AWS API를 호출해 자원 생성부터 삭제까지 자동으로 이어 간다.

#2핵심 질문

사람 대신 코드가 AWS 자원을 만들고 지우게 하려면 어떻게 붙는가?

#3동작 예시

배포 스크립트가 새 버전을 올리기 위해 Amazon S3 버킷을 만들고, 파일을 올리고, 수정이 끝나면 불필요해진 이전 버전을 지운다. 같은 작업을 사람이 콘솔에서 매번 반복할 필요가 없어진다.

#4동작 과정

  1. 자격 증명을 붙인다코드가 쓸 자격 증명을 만들고 AWS SDK에 넘긴다. 사람 계정의 비밀키를 코드에 넣지 않고 역할 맡기를 쓰는 것이 일반적이다(→ 05-04).
  2. 인증된 호출을 보낸다AWS SDKs가 요청에 서명해 보내면 AWS가 자격 증명을 확인하고 자원을 만든다. AWS Command Line Interface (AWS CLI)는 같은 호출을 터미널에서 직접 해 보는 도구이며, AWS CloudShell은 콘솔 안에서 이 CLI를 바로 쓸 수 있는 공간이다.
  3. 결과를 확인해 볼 것AWS CloudShell에서 AWS CLI로 목록 조회를 한 번 실행해 콘솔의 목록과 같은 값이 나오는지 본다.

#1문제 상황

어떤 서버가 버킷을 바꿔야 할 때 그 서버에 키를 저장해 두면, 키가 새고 그 권한은 영원히 남는다. 사람 계정 키를 코드에 넣는 것도 피해야 한다.

Assume an IAM role은 자격 증명을 잠시 바꿔 입히고, Define permissions for IAM principals는 그 순간 무엇을 할 수 있는지를 정한다.

#2핵심 질문

한 서비스가 다른 계정의 자원에 일할 때 권한을 제한된 시간 안에만 행사하게 하려면?

#3동작 예시

배포 서버가 S3 버킷을 만들려고 AWS Security Token Service (AWS STS)에 AssumeRole을 요청한다. 수락되면 짧게 만료되는 임시 자격 증명이 돌아온다. 서버는 그 자격 증명으로 버킷을 만들고, 세션이 끝나면 같은 증명으로 다시 작업하지 못한다.

#4동작 과정

  1. 역할을 정의한다신뢰 정책에 누가 이 역할을 맡을 수 있는지 적고, 허용할 작업의 권한 정책을 붙인다. 이 역할은 권한이 붙은 이름표이며 그 자체로 아무 작업도 하지 않는다.
  2. 맡기를 요청한다호출자는 sts:AssumeRole로 역할을 빌려 달라고 요청한다. AWS Security Token Service (AWS STS)가 처리해 역할과 같은 이름의 임시 자격 증명을 만들어 준다.
  3. 임시 증명으로 일한다그 시간 동안은 붙은 정책의 권한만 행사하고 세션이 끝나면 증명도 사라진다. AWS CloudShell에서 sts assume-role으로 이 흐름을 시험할 수 있다.
  4. 확인해 볼 것IAM 콘솔의 역할 목록에서 신뢰 정책 주체와 붙은 정책 이름을 눌러 실제 허용된 작업을 확인한다.

먼저 알아야 할 것 05-04

→ 05-04 참조

#1문제 상황

IAM 정책과 역할은 어떤 주체가 어떤 자원에 닿을 수 있는지 정한다(→ 05-04). 그래서 인증은 통과했는데 볼 수 없어야 할 값을 볼 수 있는 경우를 막지 못한다. application-level authorization은 애플리케이션 코드 안에서 호출자의 신원과 요청 내용을 보고 접근을 판단하는 마지막 관문이다. 권한을 기능 단위로 잘게 나눠 거부까지 코드에서 처리한다.

#2핵심 질문

인증만으로는 막을 수 없는 접근을 애플리케이션 코드 안에서 어떻게 거부할까?

#3동작 예시

주문 조회 API를 호출한 사용자 토큰에서 사용자 ID를 꺼낸다. 그 주문이 본인의 것이 아니면 데이터를 내보내지 않고 거부 로그만 남긴다. 요청한 항목 수는 늘지 않고 접근 범위만 좁아진다.

#4동작 과정

  1. 신원을 확인한다API Gateway가 넘긴 서명된 토큰(→ 05-02)을 검증해 호출자 ID를 얻는다. 여기서부터 판정은 신원 값에 근거해 내려간다.
  2. 조건을 대조한다코드 안에서 그 ID와 요청한 자원 소유자를 비교한다. fine-grained access control은 권한을 자원·행위 단위로 쪼개 조건을 붙이는 것이다.
  3. 거부한다맞지 않으면 응답을 끊고 거부 사실만 기록한다. IAM deny를 정책에 써 두면(→ 05-04) 코드 밖에서도 막을 수 있다.
  4. 확인해 볼 것다른 계정 토큰으로 API를 호출해 거부 응답과 남은 로그를 콘솔에서 본다.

#5한 줄 요약

애플리케이션 수준의 세분 접근 제어인증 뒤에 남은 판단을 코드에서 끝내 권한을 더 잘게 쪼개는 것

마이크로서비스 구조의 서비스 간 인증

여러 마이크로서비스가 서로 API를 호출할 때 사용자 자격 증명을 그대로 넘기는 대신 AWS IAM 역할과 내부 서비스 인증을 써서 호출 주체와 호출 여부를 확인하는 것.

먼저 알아야 할 것 05-05

→ 05-04 참조

#1문제 상황

주문 서비스가 재고 서비스를 부를 때 사용자 토큰을 그대로 전달하면, 재고 서비스까지 그 사용자의 모든 권한을 대신 행사할 수 있다. microservice architectures에서 cross-service authentication은 사용자 신원을 그대로 전파하는 대신 호출한 서비스가 상대 서비스에 자격을 증명하게 만든다. 내부 호출마다 신원 체인이 짧고 끊기지 않는다.

#2핵심 질문

서비스가 서비스를 부를 때 사용자 토큰을 넘기지 않고 호출 자격을 어떻게 증명할까?

#3동작 예시

주문 서비스가 재고 서비스의 API를 부른다. 이때 넘어가는 것은 사용자 토큰이 아니라 주문 서비스의 IAM 역할을 맡은 임시 자격 증명이다. 재고 서비스는 이 자격만 보고 호출을 받고 호출자를 주문 서비스로 기록한다.

#4동작 과정

  1. 자격을 넘긴다호출 서비스가 iam:AssumeRole로 역할을 잠깐 맡아 임시 자격 증명을 얻는다. 이는 자격 증명을 역할로 바꾸는 절차다(→ 05-04).
  2. 상대를 확인한다상대 서비스는 서명된 요청과 맡은 역할의 정책을 확인해 호출자를 특정한다. 사용자 권한이 아니라 호출자 서비스의 권한만 적용된다.
  3. 범위를 좁힌다역할 정책과 애플리케이션 수준의 조건(→ 05-05)을 함께 걸어 볼 수 있는 자원을 한정한다.
  4. 확인해 볼 것호출 로그에서 주체가 사용자 ID가 아니라 서비스 역할로 찍히는 것을 본다.

#5한 줄 요약

마이크로서비스 구조의 서비스 간 인증사용자 신원을 넘기지 않고 호출한 서비스의 역할로 상대를 증명하는 것

6. 도메인 2 태스크 2 — 암호화06-01

저장 시 암호화와 전송 중 암호화

저장 시 암호화는 디스크나 데이터베이스에 저장된 데이터를 잠근 상태로 보관해 디스크를 통째로 빼앗겨도 내용을 못 읽게 하는 것이고, 전송 중 암호화는 네트워크로 나가는 데이터에 TLS 같은 방식으로 잠금을 걸어 도청과 변조를 막는 것이다.

먼저 알아야 할 것 01-01

#1문제 상황

애플리케이션이 다루는 데이터는 두 곳에서 노출된다. 디스크에 평문으로 남으면 저장 장치를 빼앗겼을 때 다 읽힌다. 네트워크로 나가는 값을 그냥 두면 도청과 변조를 당한다. encryption at rest와 encryption in transit는 각각 그 두 위험을 막는 수단이며, AWS는 어느 쪽도 별도 설정 없이 켜 두는 것을 기본으로 삼는다.

#2핵심 질문

데이터가 저장된 자리와 네트워크를 지나가는 자리에서 각각 무엇을 잠가야 할까?

#3동작 예시

RDS 인스턴스에 주문 정보를 넣고 API로 읽어 낸다. 콘솔에서 해당 인스턴스의 암호화 상태를 보면 저장 시 암호화가 켜져 있고, 클라이언트 연결도 HTTPS로만 되어 있다.

#4동작 과정

  1. 저장할 때 잠근다데이터베이스의 암호화 옵션을 켜면 디스크에 쓰기 전에 암호화된다. 꺼져 있던 인스턴스에 켠 키는 나중에 못 바꾼다.
  2. 보낼 때 잠근다클라이언트와 서비스 사이를 TLS로 연결해 기밀성과 무결성을 함께 지킨다. 인증서로 상대 신원을 확인한다(→ 06-02).
  3. 키를 관리한다두 암호화의 안전은 키 보관에 달려 있다. AWS Key Management Service (AWS KMS)가 키를 들고 권한을 나눠 준다(→ 06-04).
  4. 확인해 볼 것저장소 콘솔의 암호화 항목과 클라이언트 설정의 프로토콜을 확인한다.

#5한 줄 요약

저장 시 암호화와 전송 중 암호화데이터가 머무는 자리와 이동하는 자리에서 각각 따로 잠그는 것

인증서 관리와 개발용 인증서·SSH 키

인증서 관리는 발급·갱신·배포·폐기를 자동화해 기한이 지난 인증서로 서비스가 끊기지 않게 하는 일이고, 개발 환경에서는 실제 운영 인증서 대신 짧은 기간만 쓰는 자체 서명 인증서와 SSH 키 쌍으로 테스트하는 것이 안전하다.

먼저 알아야 할 것 06-01

→ 06-01 참조

#1문제 상황

운영 인증서에는 유효 기간이 있고, 갱신하지 않으면 서비스가 끊긴다. 운영 인증서를 개발에 그대로 쓰면 실수로 남거나 만료된다. certificate management는 이 수명을 자동화하고, 개발 환경은 자체 서명 인증서와 자체 SSH 키 쌍으로 대신한다.

#2핵심 질문

인증서가 만료돼 서비스가 끊기지 않게 하면서 개발에서는 운영 인증서를 어떻게 피할까?

#3동작 예시

개발 서버의 API에 HTTPS를 붙인다. 운영 인증서를 쓰지 않고 자체 서명 인증서를 만들어 넣는다. 브라우저 경고는 나지만 실제 연결은 암호화돼 있어 개발에는 충분하다.

#4동작 과정

  1. 키 쌍을 만든다개발 환경에서만 쓸 인증서 요청과 SSH 키 쌍을 만든다. 공개 키는 서버에 보내고 비밀 키는 개발자 컴퓨터에 둔다.
  2. 서명한다AWS Private CA는 내 계정 안에서 인증서를 발급하고 관리하는 서비스로, 사내 시스템끼리 서로를 검증할 때 쓴다.
  3. 갱신을 자동화한다certificate management가 갱신과 배포 시점을 관리한다. 실패하면 인증서가 그대로 만료된다.
  4. 확인해 볼 것인증서 목록에서 상태와 만료일자가 어떻게 보이는지 확인한다.

클라이언트 측과 서버 측 암호화의 차이

서버 측 암호화는 서버 안에서 암호화와 복호화를 끝내 클라이언트가 평문을 보기 전에 이미 잠긴 상태를 뜻하고, 클라이언트 측 암호화는 클라이언트가 데이터를 보내기 전에 직접 잠그고 서버는 잠긴 상태만 다루어 서버가 암호문을 해독할 수 없게 하는 방식이다.

먼저 알아야 할 것 06-02

→ 06-02 참조

#1문제 상황

서버가 데이터를 받고 저장 전에 잠그는 방식은 편하지만, 서버가 잠근 뒤를 전제로 설계된다. 서버가 볼 수 없어야 하는 데이터라면 반대 방향이 필요하다. client-side encryption은 클라이언트가 보내기 전에 직접 잠가서 서버는 암호문만 만지고, server-side encryption은 서버 안에서 암복호화를 끝낸다(→ 06-01). 어느 쪽인지 정하면 키를 누가 쥐어야 하는지가 갈린다.

#2핵심 질문

서버가 평문을 보지 못하게 해야 할 때 암호화는 어느 쪽에서 수행할까?

#3동작 예시

노트에 업로드한 메모를 서버를 거쳐 자기 단말로 되돌린다. 클라이언트가 잠가 보낸 값은 저장소 콘솔에서 암호문으로만 보이고, 단말에서 열쇠로 풀어 원래 메모가 나온다.

#4동작 과정

  1. 키를 고른다클라이언트 측이면 각 사용자가 자기 키를 쥐고 서버 측이면 서버가 쥔다. 서버 측 키는 AWS Key Management Service (AWS KMS)로 관리한다(→ 06-04).
  2. 잠근다클라이언트 측 암호화는 전송 전에, 서버 측 암호화는 저장 전에 값을 잠근다. 잠근 뒤의 값은 어느 쪽도 비슷하다.
  3. 검증한다복호화는 같은 키로만 되돌릴 수 있다. 키를 잃으면 데이터를 되살릴 방법이 없다.
  4. 확인해 볼 것저장된 값을 직접 열어 평문이 아니라 암호문으로 보이는지 본다.

암호화 키로 데이터를 암복호화한다

암호화 키는 암호문을 평문으로 되돌리는 유일한 수단이므로 키를 안전하게 보관하고 접근 권한을 따로 관리해야 하며, 암호화에는 키가 필요하지만 복호화 권한은 KMS 의 정책과 IAM 권한을 통해 필요한 사람과 서비스에만 부여한다.

먼저 알아야 할 것 06-03

→ 06-03 참조

#1문제 상황

데이터를 잠갔다 푸는 유일한 수단은 키다(→ 06-03). 그 키를 애플리케이션 코드에 적어 두면 코드가 있는 곳에 키가 함께 있다. AWS Key Management Service (AWS KMS)는 키를 AWS 쪽에 두고 암호화는 널리 허용하면서 복호화는 좁게 제한해, 키 자체를 애플리케이션에 두지 않게 한다.

#2핵심 질문

키를 애플리케이션에 두지 않고 암호화와 복호화를 수행하려면 어떻게 하는가?

#3동작 예시

애플리케이션이 KMS에 평문을 보내 암호문을 받고 저장한다. 나중에 다시 KMS를 호출해 복호문으로 되돌린다. KMS 콘솔의 정책 화면을 보면 복호화 권한은 특정 역할에만 붙어 있다.

#4동작 과정

  1. 키를 만든다KMS에서 암호화 키를 만든다. 키 자체와 키에 대한 권한은 서로 다른 대상이 따로 관리된다.
  2. 암호화한다데이터를 KMS에 넘겨 암호문을 받는다. 암호화는 데이터가 어디에 있든 되돌릴 수 있게 하는 것이 아니라 그냥 못 읽게 하는 것이다.
  3. 복호화한다키 정책과 IAM 권한을 함께 봐서 허가된 주체만 되돌릴 수 있다. 권한은 호출한 신원을 기준으로 판단한다(→ 05-05).
  4. 확인해 볼 것키 정책에서 암호화와 복호화 권한이 붙은 주체를 따로 보는지 확인한다.

#5한 줄 요약

암호화 키되돌릴 수 없게 하는 값이 아니라 그 값을 다시 평문으로 되돌리는 통제권

→ 06-04 참조

#1문제 상황

조직과 서비스가 여러 AWS 계정에 나뉘어 있으면, 앞 단 계정이 뒤 단 계정의 키로 데이터를 잠가야 한다. 내 키가 내 계정에 쓰였다고 남의 계정까지 열리면 안 되므로 권한을 직접 좁혀 줘야 한다. 키를 오래 한 개만 두면 그 키가 유출되었을 때 과거 데이터까지 위험해진다.

#2핵심 질문

다른 AWS 계정이 내 키로 데이터를 잠그게 하면서도 키 사용 범위는 어떻게 통제할까?

#3동작 예시

앞 단 계정의 애플리케이션이 뒤 단 계정 버킷에 객체를 쓰며 계정 간 키를 쓴다. 뒤 단 계정 콘솔의 키 정책에 앞 단 계정이 암호화 호출만 할 수 있도록 적혀 있다. 몇 달이 지나면 새 키가 활성화되어 이후 객체는 새 키로 잠긴다.

#4동작 과정

  1. 키 정책에 계정을 적는다크로스 계정 키 정책에 상대 계정 ID를 넣고 허용할 동작을 암호화로 좁힌다. ARN 권한으로 어떤 키를 쓸지도 지정한다(→ 06-04).
  2. 키를 순환한다enable and disable key rotation으로 새 키를 주기적으로 활성화한다. 새 데이터는 새 키로 암호한다.
  3. 오래된 키를 남긴다이전 키는 비활성 상태로 두고 복호화만 허용한다. 예전 데이터를 되읽을 길은 막지 않는다.
  4. 확인해 볼 것키 목록에서 현재 활성화된 키와 이전 키의 상태가 어떻게 표시되는지 본다.

7단계 7. 도메인 2 태스크 3 — 애플리케이션 코드의 민감한 데이터

애플리케이션이 다루는 데이터를 공개되지 않아도 되는 일반 데이터와비밀번호처럼 노출되면 보안 사고가 나는 민감한 데이터로 나누어, 각각 다르게 다루기 위해 붙이는 분류 표시.

먼저 알아야 할 것 06-01

#1문제 상황

애플리케이션 코드는 주문 내역과 로그를 한꺼번에 다룬다. 그런데 그 안에 전화번호나 진단 기록 같은 값이 섞여 있으면, 로그를 남기는 순간 개인정보가 어디로 새어나갈지 알 수 없다.

데이터 분류는 데이터를 성격에 따라 나눠 붙이는 표시이다. personally identifiable information(PII)은 사람을 특정할 수 있는 정보고, protected health information(PHI)은 건강과 관련된 민감 정보다. 표시가 있으면 다룰 방법이 달라진다.

#2핵심 질문

이 데이터가 다뤄져도 되는 일반 값인지, 손대면 안 되는 민감한 값인지 어떻게 나누나?

#3동작 예시

주문 저장 기능을 고쳐 보니 주문 목록에 고객 전화번호가 들어 있다. 목록 조회는 되지만 그 값은 표시하지 않기로 정한다.

결제 모듈은 주문 본문 전체를 다뤄야 하므로 민감 값이 들어 있다고 표시해 둔 뒤, 로그에는 값 없이 항목 이름만 남기게 한다.

#4동작 과정

  1. 값을 훑어본다코드에서 쓰는 필드를 하나씩 살피고 PII와 PHI에 해당하는 값을 찾아 표시한다. 전화번호·주소처럼 사람에 관한 값이 여기 들어간다.
  2. 등급을 정한다표시를 붙여 두고 다룰 방법도 함께 정한다. 이 값은 화면에서 가리고, 이 값은 암호화해 둔다.
  3. 코드에서 막는다표시가 있는 값이 응답이나 로그로 나가는 자리를 막는다. 남은 처리는 → 07-03에서 한다.
  4. 확인해 볼 것애플리케이션 응답과 로그에 표시해 둔 값이 그대로 남아 있지 않은지 확인한다.

환경 변수 암호화와 비밀 관리 서비스

애플리케이션 코드에 직접 적지 않고 설정으로 따로 보관한 비밀번호·API 키 같은 비밀 값을, 암호화해 저장하고 필요할 때만 꺼내 쓸 수 있게 하는 AWS Secrets Manager 같은 서비스.

먼저 알아야 할 것 07-01

#1문제 상황

데이터베이스 비밀번호를 코드 안에 적어 두면 그 파일이 빌드된 이미지 저장소까지 함께 퍼진다. 값을 바꿀 때마다 코드를 고쳐 배포해야 한다.

환경 변수 암호화와 비밀 관리는 비밀 값을 코드 밖으로 빼는 일이다. 암호화한 상태로 저장하고 실행 시에만 꺼내 쓴다(→ 07-01).

#2핵심 질문

비밀 값을 코드에서 빼내 안전한 곳에 보관하고 필요한 순간에만 꺼내 쓰는가?

#3동작 예시

결제 모듈이 데이터베이스에 붙을 때 연결 문자열이 필요하다. 배포 화면에서 손으로 적는 대신 비밀 저장소에서 이름으로 값을 읽어 온다.

그 값은 암호화되어 있어 화면과 저장소 어디에도 평문으로 남지 않는다.

#4동작 과정

  1. 비밀을 등록한다데이터베이스 비밀번호나 API 키를 AWS Secrets Manager에 넣는다. 타입별로 값과 갱신 주기를 함께 지정한다.
  2. 코드는 이름만 쓴다애플리케이션은 값 대신 비밀 이름만 적고 실행 시에 값을 받아 온다. 암호화는 이때도 저장과 전달 내내 유지된다.
  3. 자격 증명으로 붙는다AWS Systems Manager의 Parameter Store에도 비밀을 둘 수 있다. 같은 방식으로 파라미터를 넣어 코드가 꺼내 쓴다.
  4. 확인해 볼 것코드 저장소와 배포 설정 화면에 비밀 값이 평문으로 남아 있지 않은지 확인한다.

먼저 알아야 할 것 07-02

#1문제 상황

비밀 값은 따로 모았어도(→ 07-02), 주문 데이터 안의 전화번호는 그대로 코드와 로그에 남는다. 오류 로그 한 줄로 개인정보가 그대로 노출된다.

데이터 정제와 마스킹은 값의 일부를 지우거나 가리는 처리다. 처리 결과로 원래 목적은 살고 사람은 드러나지 않는다.

#2핵심 질문

개인정보가 화면과 로그에 남지 않게 하면서 필요한 정보만 남기는가?

#3동작 예시

결제 실패 로그에 주문 번호와 함께 고객 전화번호가 찍힌다. 로그를 남기는 코드가 전화번호를 가리고 마지막 네 자리만 남기도록 고친다.

화면에 주문 내역을 보여 주는 곳도 같은 규칙을 쓰므로, 전화번호가 그대로 나오지 않는다.

#4동작 과정

  1. 들어갈 값을 정한다정제에 대상이 되는 값은 07-01에서 표시해 둔 값이다. 표시가 없으면 정제 대상도 정해지지 않는다.
  2. 가린다마스킹은 필요한 일부만 남기고 나머지를 기호로 바꾼다. 애플리케이션 수준의 마스킹은 애플리케이션 코드 안에서 이 처리를 직접 수행하는 것이다.
  3. 지운다지우기(sanitize)는 애초에 필요 없는 민감 값을 코드에서 빼는 쪽이다. 로그에 전화번호 자체를 남기지 않게 한다.
  4. 확인해 볼 것처리한 로그 줄을 열어 개인정보가 가려졌는지 확인한다.

#1문제 상황

한 애플리케이션을 여러 회사가 함께 쓰면 같은 테이블에 각 회사의 주문이 함께 쌓인다. tenant id 같은 값 하나를 빼먹은 조회 한 번이 남의 데이터가 그대로 노출된다.

다중 테넌트 애플리케이션의 데이터 접근 패턴은 사용자(테넌트)와 데이터의 연결을 코드와 저장 구조에 미리 심어 두는 일이다.

#2핵심 질문

여러 사용자의 데이터가 섞이지 않도록 조회 조건을 어떻게 심어 두는가?

#3동작 예시

주문 조회 화면에서 tenant id 없이 주문 번호만으로 찾아 반환되는 코드가 있다. 조건에 tenant id를 함께 넣도록 고친다.

이제 남의 주문 번호를 찍어 넣어도 아무 결과가 나오지 않는다.

#4동작 과정

  1. 사용자를 살핀다로그인한 사람에게 tenant id를 붙여 매 요청마다 알려 준다(→ 05-02). 여기서 값이 빠지면 뒤 단계가 전부 흔들린다.
  2. 키로 새긴다저장 구조에서 tenant id를 파티션 키에 넣어 한 사용자의 데이터가 한 묶음에 모이게 한다(→ 04-04). 조건 없는 조회가 한 회사로만 좁아진다.
  3. 항상 건다모든 조회와 쓰기에 tenant id 조건을 넣고 코드에서 빠뜨리지 않게 한다. 정제 대상이 되는 값은 → 07-03에서 정리한다.
  4. 확인해 볼 것다른 tenant id로 만든 요청으로 조회했을 때 데이터가 나오지 않는지 확인한다.

#3동작 예시

팀원에게 받은 코드를 로컬에서 띄우려니 라이브러리 하나가 없어 시작이 안 된다. 매니페스트에 적힌 이름과 버전을 그대로 설치하니 같은 코드가 로컬에서 그대로 돌기 시작한다.

#4동작 과정

  1. 매니페스트에 적는다의존 라이브러리와 버전을 매니페스트 파일에 나열한다. 파이썬에서는 requirements.txt가 이 역할을 한다.
  2. 설정값을 뺀다접속 정보처럼 환경마다 다른 값은 configuration files와 environment variables로 코드 밖에 둔다(→ 03-02).
  3. 실행 형태로 묶는다컨테이너로 배포한다면 container images 안에 라이브러리와 코드를 함께 담아 하나의 묶음으로 만든다(→ 08-03).
  4. 확인해 볼 것매니페스트만 보고 의존 라이브러리를 모두 설치해도 코드가 실행되는지 확인한다.

#3동작 예시

  3. 맞춰 묶는다의존 파일과 설정 파일을 정한 경로에 넣는다. 어떤 라이브러리가 필요한지는 → 08-01에서 정해 온 목록을 따른다.

개발·테스트·프로덕션 등 환경마다 다른 설정값(접속 정보, 기능 켜기 끄기 같은 환경 변수)을 설정 파일이나 파라미터 저장소로 따로 관리하는 것.

먼저 알아야 할 것 08-03

→ 08-03 참조

#1문제 상황

같은 코드가 개발 환경과 운영 환경에서 모두 돌아간다. 그런데 접속할 데이터베이스 주소와 기능 켜기 끄기 여부는 달라야 한다. 이 값을 코드 안에 적으면 코드를 고칠 때마다 배포를 다시 해야 한다.

환경별 애플리케이션 구성은 그 값들을 코드 밖으로 꺼내 환경마다 따로 두는 일이다. 코드는 그대로 두고 설정만 갈아 끼울 수 있다.

#2핵심 질문

같은 코드를 여러 환경에 올릴 때 환경마다 다른 설정값을 어디에 두고 어떻게 갈아 끼울까?

#3동작 예시

개발자가 주문 서비스를 로컬에서 띄운다. 주문 기능은 켜 두고 실제 결제 연동은 꺼 두려 한다. 코드 수정 없이 설정 파일의 값만 바꾼다.

결제 호출은 개발 환경에서 건너뛰고, 주문 처리 화면은 그대로 열린다.

#4동작 과정

  1. 값을 분리한다접속 주소·기능 플래그 같은 환경 변수와 설정 파일을 코드 밖에서 관리한다. 이는 Prepare application configurations for specific environments 라고 부른다.
  2. 환경마다 보관한다같은 키 이름으로 값을 저장하되 개발·테스트·프로덕션에서 다른 값을 넣는다. AWS AppConfig 는 이런 설정을 서비스로 관리하고 필요한 애플리케이션에 내려 보낸다.
  3. 읽어 오게 한다애플리케이션은 자기 환경에 해당하는 값만 읽는다. 환경이 바뀌어도 코드 배포는 필요 없다.
  4. 확인해 볼 것각 환경의 설정 화면에서 같은 키에 다른 값이 들어 있는지 확인한다.

#5한 줄 요약

환경별 애플리케이션 구성환경마다 다른 설정값을 코드 밖에서 따로 관리해 코드 수정 없이 갈아 끼우는 것

배포된 코드를 시험한다

실제 환경에 올린 애플리케이션이 기대한 대로 동작하는지 기능과 성능을 확인하고, 문제 있으면 로그·모니터링 자료로 원인을 찾아 고치는 것.

먼저 알아야 할 것 08-04

→ 08-04 참조

#1문제 상황

개발 컴퓨터에서 테스트를 통과한 코드가 배포된 환경에서는 다른 값을 읽는다. 그래서 화면이 깨지거나 기능이 멈춘다.

Test deployed code by using AWS services and tools 는 배포된 상태를 그대로 시험하는 일이다. 서버가 살아 있는 것만으로는 부족하고 다른 서비스를 붙인 흐름 전체가 맞는지 봐야 한다.

#2핵심 질문

배포된 코드가 실제 환경에서 기대한 대로 동작하는지 어떻게 확인하고 실패하면 무엇을 고칠까?

#3동작 예시

주문 서비스를 시험 환경에 올리고 주문을 넣는다. 주문은 저장되는데 결제 단계에서 실패한다.

로그를 보면 외부 결제 API 호출에서 시간 초과가 반복됐다. 코드 로그에 남긴 요청 식별자로 실패 구간만 골라 확인한다.

#4동작 과정

  1. 옮겨 시험한다배포한 대상으로 요청을 보내 실제 응답을 확인한다. 시험용 데이터를 만들고 되돌릴 수 있게 해 둔다.
  2. 바깥을 살짝 가린다Write integration tests and mock APIs for external dependencies 로 외부 API를 모의 구현으로 바꿔 시험한다. 외부 서비스가 없어도 같은 흐름을 재현할 수 있다.
  3. 실패 지점을 좁힌다로그와 지표를 붙여 본다. 로깅과 관측 전략은 10-01 과 11-02 를 따른다.
  4. 확인해 볼 것시험 환경에서 주문 요청이 끝까지 통과했는지 로그에서 확인한다.

#5한 줄 요약

배포된 코드를 시험한다는 것은 실제 환경의 응답과 로그로 흐름 전체를 확인해 원인을 좁히고 고치는 것입니다.

먼저 알아야 할 것 08-05

→ 08-05 참조

#1문제 상황

코드는 배포됐지만 어디로 접속해야 하는지 정해지지 않았다. API를 만든 자원과 그를 여는 주소, 단계(stage) 설정이 떨어져 있어 한 번에 움직이기 어렵다.

개발 엔드포인트와 스택 업데이트는 배포된 자리에 진입점을 붙이고, 자원 묶음을 새 버전으로 교체하는 일이다. 인프라 정의를 코드로 적어 둔 AWS SAM 템플릿으로 이 교체를 되돌릴 수 있게 만든다.

#2핵심 질문

배포한 애플리케이션에 외부에서 부르는 주소를 어떻게 붙이고 자원 묶음을 새 버전으로 어떻게 갈아 끼울까?

#3동작 예시

새 API 버전을 운영에 올린다. Amazon API Gateway의 단계(dev·test·prod)를 나눠 각 단계가 다른 주소로 연결되게 한다.

SAM 템플릿을 고쳐 배포하면 자원이 새 코드로 교체된다. 단계별 주소로 호출해 어느 단계가 갱신됐는지 본다.

#4동작 과정

  1. 진입점을 연다Test applications by using development endpoints 로 개발용 주소 하나를 만들어 시험에만 쓴다.
  2. 단계를 나눈다configuring stages in Amazon API Gateway 로 단계마다 배포본과 설정을 나눠 둔다. 환경 구분은 09-02 와 이어진다.
  3. 교체한다Deploy application stack updates to existing environments 로 자원 묶음을 새 버전으로 바꾼다. deploying an AWS SAM template to a different staging environment 로 다른 환경에 올릴 수도 있다.
  4. 확인해 볼 것각 단계의 주소로 호출해 어느 단계가 어떤 버전을serve 하는지 본다.

애플리케이션에 시험 이벤트를 심고 그것을 감지해 시험 사양(테스트 케이스)을 자동으로 만들어 내는 방식으로, 사람이 매번 시험 항목을 손으로 만들 필요를 없앤다.

먼저 알아야 할 것 08-05

#1문제 상황

시험 항목을 매번 손으로 짜야 한다. 무엇을 넣어 봐야 빠지는지 놓치고, 같은 일을 반복해서 입력한다.

애플리케이션 시험 이벤트는 시험해 볼 상황을 데이터로 만들어 두는 방식이다. Create application test events 로 상황을 정의하면 시험 사양을 만들어 내는 데 쓸 수 있다.

#2핵심 질문

시험해야 할 상황을 어떻게 데이터로 표현해 반복되는 시험을 대신 만들어 낼까?

#3동작 예시

AWS Lambda 함수를 만든다. 함수 단축키를 눌 시험 화면에서 Create application test events 를 누르고 사건 이름을 고른다.

그 바깥에 감쌀 JSON payloads for testing 이 그려진다. 이 값을 그대로 넣어 함수를 돌리면 저장 없이 결과만 확인한다.

#4동작 과정

  1. 상황을 고른다시험할 함수를 고르고 그 함수가 받는 사건 형태를 고른다. AWS SAM 자원이면 템플릿에 시험 사건을 함께 정의해 둔다.
  2. 값을 채운다사건 안의 값은 JSON 페이로드로 적어 실제와 같은 모양으로 만든다. Use Amazon Q Developer to generate automated tests 로 같은 패턴의 시험 코드를 만들어 반복 시험에 쓴다.
  3. 확인해 볼 것시험 화면에 만든 사건 목록이 보이는지 확인한다.

API 자원을 여러 환경에 배포한다

API(프로그램이 다른 프로그램과 통신하기 위해 정한 규약) 자원을 시험·운영 등 여러 환경으로 나눠 각 환경에 맞게 따로 배포하고 관리하는 것.

먼저 알아야 할 것 09-01

#1문제 상황

API 하나를 만들어 운영에 바로 올리면 시험할 곳이 없다. 실수로 운영 데이터를 건드리게 되며, 문제가 생겨도 되돌릴 곳이 없다.

Deploy API resources to various environments 는 같은 API 정의를 환경마다 따로 배포하는 일이다. 환경 이름은 AWS AppConfig 같은 설정 저장소와 함께 관리한다.

#2핵심 질문

같은 API 정의를 개발·시험·운영으로 나눠 각각 올리고 관리할 수 있을까?

#3동작 예시

운영 중인 주문 API가 있다. 새 기능을 시험하려고 시험 환경에 같은 API를 새로 배포한다. 이 환경은 운영과 다른 데이터베이스를 본다.

주문을 넣어 확인하니 운영에는 아무 변화가 없다.

#4동작 과정

  1. 자원을 나눈다Manage environments in individual AWS services 로 환경마다 붙는 이름표와 설정을 따로 둔다. 기능 켜기 끄기 값은 08-04 를 따른다.
  2. 배포한다환경 하나를 골라 그 자원에 API를 배포한다. API를 여는 단계는 08-06 에서 다뤘다.
  3. 구분한다differentiating between development, test, and production in API Gateway 로 환경마다 다른 연결과 기능을 배정한다.
  4. 확인해 볼 것환경별 목록에서 각 환경에 올라간 API 주소가 따로 적혀 있는지 확인한다.

#5한 줄 요약

API 자원을 여러 환경에 배포한다는 것은 같은 API 정의를 환경별로 따로 올려 서로 건드리지 않게 관리하는 것입니다.

승인된 버전으로 통합 시험 환경을 만든다

검토와 승인을 통과한 특정 버전의 코드와 자원을 조합해 여러 사람이 함께 확인하는 통합 시험 환경을 만드는 것.

먼저 알아야 할 것 09-02

#1문제 상황

각자가 자기 브랜치에서 시험하면 서로 다른 코드가 섞인다. 무엇이 같이 동작하는지 알 수 없어 통합 마지막에 문제가 몰린다.

승인된 버전으로 만든 환경은 조합이 고정된다. 이 조합을 쓰는 쪽은 Lambda alias, container image tags, AWS Amplify branches, AWS Copilot environments 로 가리킨다.

#2핵심 질문

승인을 통과한 버전들만 골라 함께 동작하는 통합 시험 환경을 어떻게 만들고 붙잡을까?

#3동작 예시

승인된 조합을 고정해 함께 시험할 수 있는 환경을 어떻게 만들까?

#4동작 과정

  1. 버전을 정한다검토를 통과한 버전만 승인된 목록에 넣는다.
  2. 고정해서 묶는다Lambda alias 로 함수 버전과 $LATEST를 갈라 붙이고, 컨테이너는 이미지 태그로 묶는다. AWS Amplify branches 와 AWS Copilot environments 로도 같은 역할을 한다.
  3. 환경을 만든다그 조합만 올라간 환경을 세워 두고 여러 사람이 한 주소로 들어와 확인한다.
  4. 확인해 볼 것환경의 각 구성 요소가 승인된 버전으로 표시되는지 본다.

먼저 알아야 할 것 09-03

#1문제 상황

자원을 콘솔에서 하나씩 만들면 무엇을 만들었는지 기록이 남지 않는다. 같은 환경을 다시 세울 때도 같은 일을 반복한다.

Implement and deploy infrastructure as code (IaC) templates 는 인프라를 템플릿 파일로 적어 두고 그것을 실행해 자원을 세우는 일이다. 같은 파일을 다시 배포하면 같은 모양의 환경이 된다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 방식을 고른다AWS SAM templates 는 애플리케이션 자원용이고, AWS CloudFormation templates 는 일반 자원용이다.
  2. 정의를 적는다템플릿에 자원과 속성을 코드로 적는다. AWS Cloud Development Kit (AWS CDK) 로 같은 정의를 코드로 만들 수도 있다.
  3. 배포한다템플릿을 그대로 배포해 자원을 구현한다. 환경별로 여러 벌을 나눠 세운다(→ 08-06).
  4. 확인해 볼 것템플릿 배포 기록에 생성된 자원 목록이 나왔는지 확인한다.

#4동작 과정

  1. 패키지로 만든다함수 코드와 의존 라이브러리를 묶어 올린다. Lambda deployment packaging options에는 zip 파일, 컨테이너 이미지, Amazon ECR 이미지 저장소로 나누어 올리는 방법이 있다.

#1문제 상황

Update existing IaC templates는 템플릿을 수정해 반영하는 작업이고, Manage application environments는 그 위의 애플리케이션 자원을 환경별로 관리하는 일이다. 이 둘은 Management and governance 영역의 AWS 서비스로 묶여 다룬다.

#2핵심 질문

#4동작 과정

  1. 고쳐 반영한다템플릿의 차이점을 고쳐 같은 IaC 도구로 다시 적용한다. 지금 상태와 선언한 상태의 차이만 반영되므로 다른 자원은 그대로 남는다.
  2. 환경을 나눈다파라미터와 비밀을 환경별로 따로 두고 각 자원이 그 값을 읽게 한다. 공통 AWS 계정 관리 기능은 Systems Manager의 Parameter Store 같은 Management and governance 서비스를 쓴다.

새 버전을 한꺼번에 바꾸는 대신 일부에만 먼저 나눠 배포하는 전략(블루그린·캔 Canary 등)을 쓰고, 문제가 보이면 이전 버전으로 되돌리는 것.

#1문제 상황

#2핵심 질문

#3동작 예시

전량 교체까지 기다릴 필요가 없어졌다.

#4동작 과정

  1. 전략을 정한다blue/green는 두 벌을 띄워 한 번에 전환하고, canary는 일부 비율만 새 버전으로 보내며, rolling은 대상을 차례대로 바꿔 간다.
  2. 배포한다정한 비율만큼만 새 버전으로 트래픽을 보내 결과를 지켜본다. canary나 rolling은 반응이 나쁘면 다음 단계로 넘어가지 않는다.
  3. 되돌린다Perform application rollbacks로 이전 버전으로 되돌리면 되돌린 사실이 배포 기록에 남는다. 배포 인프라는 AWS CodeDeploy가 맡는다.
  4. 확인해 볼 것배포 기록에서 어떤 전략으로 전환됐고 현재 어느 버전이Primary인지 확인한다.

logging, monitoring, observability의 차이를 나누어 두면 어디까지 해 둔 상태인지 알 수 있다.

#2핵심 질문

애플리케이션 상태를 파악한다는 말은 logging, monitoring, observability 중 어느 것을 뜻하는가?

#3동작 예시

결제가 느려진다. 서버가 남긴 주문 처리 기록(logging)을 보고, 요청 수가 평소보다 적은지 숫자로 확인하고(monitoring), 내부에서 무슨 일이 벌어지는지 로그·지표·트레이스만 보고 짐작하는 상태가 되도록 해 둔 것이 observability다.

#4동작 과정

  1. 기록을 남긴다logging은 애플리케이션의 동작과 상태를 글로 적어 남기는 일이다. 어디에서 뭐가 일어났는지 원본 자료를 만든다.
  2. 모은 것을 지켜본다monitoring은 수집된 지표와 상태를 주시하는 일이다. logging에서 나온 수치를 보고 정해 둔 기준과 비교한다(→ 10-02).
  3. 내부 상태를 추정하게 만든다observability는 바깥에서 보이는 지표·로그·트레이스만으로 내부 상태를 짐작할 수 있게 만드는 목표다. 그래서 어떤 상황에서 무엇을 올릴지 미리 정해 둬야 한다.
  4. 확인해 볼 것CloudWatch 콘솔에서 지표·로그·트레이스 세 종류가 어느 화면에서 각각 조회되는지 확인한다.

효과적인 로깅 전략과 구조화 로깅

먼저 알아야 할 것 11-01

#1문제 상황

자유 문장으로 남긴 로그는 아무리 모아도 검색과 집계가 어렵다. 문제가 생겼을 때 필요한 한 줄을 못 찾아 이전 방식으로 되돌아간다.

structured logging은 로그를 정해진 키와 값으로 가진 형식(예: JSON)으로 남겨 기계가 읽고 묶을 수 있게 만드는 것이다.

#2핵심 질문

나중에 원인을 찾을 수 있는 형태의 로그를 어떻게 남겨야 하는가?

#3동작 예시

주문 실패가 반복돼 CloudWatch Logs에서 그 요청 ID의 기록을 찾는다. 구조화된 로그에서는 requestId, status, latencyMs 필드만 걸어 골라도 전체 요청이 시간순으로 드러난다.

#4동작 과정

  1. 무엇을 남길지 정한다effective logging strategy는 애플리케이션의 동작과 상태를 적을 항목과 수준을 미리 정하는 일이다. 너무 적으면 원인이 안 잡히고 너무 많으면 탐색 시간이 늘어난다.
  2. 형식을 고정한다structured logging은 timestamp, level, request id 같은 정해진 키와 값을 갖는 형식으로 애플리케이션 이벤트와 사용자 동작을 남긴다. 이 형태여야 CloudWatch Logs에서 조건으로 골라 질의할 수 있어 앞의 로그 질의(→ 10-03)에 이어진다.
  3. 확인해 볼 것CloudWatch Logs에서 한 건을 열어 정해진 키와 값이 파싱되어 보이는지 확인한다.

사용자 정의 지표와 알림 만들기

사용자 정의 지표는 CloudWatch에 애플리케이션이 직접 올리는 숫자 값이고, 알림은 이 지표나 로그 패턴이 정해진 임계값을 넘었을 때 경보로 알려 주는 설정입니다.

먼저 알아야 할 것 11-02

#1문제 상황

알림을 걸어 두지 않으면 문제가 생긴 뒤에야 로그를 뒤지게 된다. 그리고 기본 제공 지표에는 우리 서비스에서 중요한 동작이 잡혀 있지 않다(→ 10-04).

code that emits custom metrics는 애플리케이션이 직접 CloudWatch에 숫자 값을 올리는 코드다.

#2핵심 질문

내가 정해 둔 기준이 깨졌을 때 자동으로 알려 주는 장치를 어떻게 만들 수 있는가?

#3동작 예시

결제 재시도 횟수가 치솟는다. 코드에서 올린 사용자 정의 지표에 임계값 알림을 걸어 두면 기준을 넘는 순간 경보가 울리고 알림 대상에 메일과 메시지가 도착한다.

#4동작 과정

  1. 보낼 지표를 정한다custom metric은 애플리케이션의 고유 동작을 나타내는 이름 붙은 숫자 값이다. 지표 이름과 보낼 시점을 코드에 정하고 CloudWatch에 올리면 사용자 정의 지표로 나타난다. 구조화 로그와 함께 보낼 때는 embedded metric 형식을 쓴다(→ 11-02).
  2. 알림을 만든다notification alerts는 정해진 조건이 충족될 때 경보를 보내는 설정이다. 특정 동작·사용량 한계·배포 완료 같은 시점에 알림을 걸 수도 있다.
  3. 조건을 정한다지표 하나와 비교 대상과 임계값을 정해 두면 값이 넘을 때만 알림이 울린다. 경보가 없으면 이상 징후를 놓친다.
  4. 확인해 볼 것CloudWatch 콘솔의 알림 목록에서 만든 알림이 어떤 지표를 지켜보는지 확인한다.

트레이싱과 주석

트레이싱은 요청 한 건이 지나간 경로를 단계별로 기록해 병목과 오류를 좁히는 것으로, 주석(annotation)은 트레이스 위에 보여 지연 구간·오류 같은 표시를 붙여 원인 구간을 짚어 줍니다.

먼저 알아야 할 것 11-03

#1문제 상황

느린 요청 하나가 있어도 어느 구간에서 시간이 쓰이는지 알 수 없다. 지표는 전체 합계만 보여 주고 개별 요청의 경로는 남기지 않는다(→ 10-02).

tracing은 요청 한 건이 지나간 경로를 단계 단위로 남긴다. annotation은 그 위에 표시를 붙여 원인 구간을 짚어 준다.

#2핵심 질문

한 요청이 느릴 때 어느 구간에서 지연이 생겼는지 어떻게 찾는가?

#3동작 예시

체크아웃 요청 하나를 AWS X-Ray 콘솔에서 열어 본다. 흐름도에서 결제 확인 구간만 긴 막대로 드러나 있고, 그 구간에 붙은 annotation에 오류 메시지가 표시되어 있다.

#4동작 과정

  1. 경로를 기록한다AWS X-Ray는 애플리케이션이 지나는 각 단계와 그 소요 시간을 하나의 흐름도로 모은다. 그래프 형태로 요청별 지연 구간이 보인다.
  2. 단계를 나누어 재다각 호출은 하나의 하위 구간(subsegment)으로 쪼개져 따로 지연 시간이 남는다. 어느 구간이 시간을 먹었는지 그 단위로 본다.
  3. 표시를 붙인다annotation은 트레이스 위의 한 지점에 이름을 붙인 표시다. 지연 구간이나 오류가 난 지점에 달아 원인 구간을 바로 짚는다.
  4. 확인해 볼 것X-Ray 콘솔에서 하나의 트레이스를 열어 하위 구간별 시간과 annotation 표시가 보이는지 확인한다.

건강 확인과 준비 상태 검사

건강 검사는 프로세스가 살아 있는지만 가볍게 보고하고, 준비 상태 검사는 의존 자원까지 갖춰 트래픽을 받을 수 있는지를 확인하는 것으로 두 기준을 분리한 로드 밸런서의 기동 지표입니다.

먼저 알아야 할 것 11-04

#1문제 상황

컨테이너가 여러 대 돌 때 단순히 프로세스가 살아 있는지만 보면, 시작 직후 아직 데이터베이스에 연결되지 않은 인스턴스에도 트래픽이 들어간다(→ 11-04). 그 요청은 실패한다.

건강 검사와 준비 상태 검사는 이 둘을 나눈다. 건강 검사는 프로세스가 살아 있는지만 보고하고, 준비 상태 검사는 의존 자원까지 갖춰 트래픽을 받을 수 있는지 본다. Amazon ECS와 Amazon EKS 모두 이 두 기준을 따로 설정한다.

#2핵심 질문

컨테이너가 살아 있어도 트래픽을 받을 준비가 되었는지 어떻게 구분해 알려 줄까?

#3동작 예시

주문 서비스 배포 직후 로드 밸런서가 컨테이너 목록을 본다. 프로세스는 켜져 있어 건강 검사는 통과한다.

준비 상태 검사가 아직 실패라 해당 컨테이너는 목록에서 빠진다. 연결 문자열이 채워진 뒤 검사가 통과되니 그때부터 요청이 들어온다.

#4동작 과정

  1. 두 기준을 정한다건강 검사는 컨테이너 프로세스 상태를 보고하고 준비 상태 검사는 의존 자원 연결 여부를 확인한다. 건강 검사가 먼저 통과되어도 준비 상태 검사가 실패하면 트래픽은 보내지 않는다.
  2. 결과를 자동 판정에 쓴다두 검사 결과로 컨테이너를 목록에 넣고 뺀다. Amazon ECS의 서비스 스케일러와 Amazon EKS의 kubelet이 이 결과로 트래픽 대상을 정한다.
  3. 확인해 볼 것ECS 콘솔의 서비스 탭에서 컨테이너 상태가 RUNNING과 Healthy로 표시되는지 확인한다.

동시성과 최소 자원 결정하기

동시성은 여러 요청이 동시에 도착할 때의 처리 방식을 고르는 결정이고, 최소 자원 결정은 그 선택에 맞춰 트래픽의 최고점에서 버틸 수 있는 가장 작은 CPU·메모리 크기를 정하는 일입니다.

먼저 알아야 할 것 11-05

#1문제 상황

애플리케이션을 아무 크기로나 띄우면, 메모리를 넉넉히 잡아도 느려지는 경우가 있고 적게 잡아 요청이 밀린다. 크기를 골라 주는 기준이 없다.

동시성은 이런 선택을 정리해 주는 결정이다. 최소 자원 결정은 그 결정에 맞춰 필요한 최소 CPU와 메모리를 정한다(→ 11-05). 이 결과가 비용과 용량 관리에 쓰인다.

#2핵심 질문

동시성을 정했을 때 애플리케이션에 필요한 최소 CPU와 메모리는 얼마일까?

#3동작 예시

Lambda 함수의 메모리를 512 MB에서 1024 MB로 올린다. 테스트 호출에서 실행 시간이 절반으로 줄었다.

메모리를 늘리면 CPU도 함께 늘어나기 때문이다. 이제 최고 트래픽에서 버틸 최소 크기를 그 기준으로 정한다.

#4동작 과정

  1. 동시성을 정의한다동시성은 여러 요청이 동시에 도착할 때 프로필처럼 순차 처리할지 병렬 처리할지 고르는 결정이다. 이 선택이 필요한 메모리와 실행 시간 상한을 함께 정한다(→ 03-05).
  2. 성능을 측정한다애플리케이션 성능을 실제 부하로 재서 CPU 사용량과 응답 시간을 남긴다. 최소 메모리와 컴퓨팅 파워는 이 수치에서 역산한다.
  3. 크기를 올린다최소 컴퓨팅 파워를 정하고 그만큼만 할당해 비용을 관리한다. 자원 사용량과 요금을 함께 보며 조정한다.
  4. 확인해 볼 것Lambda 함수의 Configuration 화면에서 메모리 값과 그에 붙는 Provisioned concurrency 설정을 확인한다.

11. 도메인 4 태스크 2·3 — 관측 가능성과 최적화11-07

구독 필터 정책과 요청 헤더 기반 캐시

CloudFront의 구독 필터 정책은 Origin Shield와 오리진 간에 어떤 트래픽만 암호화해서 보낼지 고르고, 헤더 기반 캐시는 요청 헤더 값을 키로 삼아 서로 다른 요청이 같은 캐시 항목을 공유하지 않게 하는 설정입니다.

먼저 알아야 할 것 11-06

#1문제 상황

CloudFront에서 모든 요청을 오리진까지 내려보내면 지연이 늘고, 반대로 캐시가 너무 넓으면 사용자마다 다른 응답이 섞인다.

구독 필터 정책은 그중 어떤 트래픽만 암호화해서 보낼지 고르고, 헤더 기반 캐시는 요청 헤더를 키로 삼는다. Amazon API Gateway 앞 단에도 같은 선택지가 있다.

#2핵심 질문

CloudFront에서 어떤 트래픽만 오리진까지 보내고, 무엇을 캐시하지 않게 할까?

#3동작 예시

Viewer-Language 헤더가 다른 두 사람이 같은 URL을 연다. 한국어 요청에는 한국어 문서가, 영어 요청에는 영어 문서가 돌아온다.

헤더 기반 캐시가 없다면 한 사람이 받은 응답이 다른 사람에게도 재사용되어 언어가 뒤틀린다. 캐시 정책에 해당 헤더를 넣으니 요청마다 항목이 갈라진다.

#4동작 과정

  1. 구독 필터 정책을 정한다구독 필터 정책은 메시징 최적화에도 쓰이며 Origin Shield와 오리진 사이에서 어떤 트래픽만 암호화해 보낼지 고른다(→ 11-04). 나머지는 그대로 통과시킨다.
  2. 캐시 키에 헤더를 넣는다Amazon CloudFront 캐시 정책에 헤더 항목을 넣어 캐시 항목을 나눈다. 같은 URL이어도 헤더 값이 다르면 다른 항목으로 저장된다.
  3. API 앞 단에도 적용한다Amazon API Gateway의 캐시 단계와 인validation을 같은 방식으로 묶어 API 응답도 나눈다.
  4. 확인해 볼 것CloudFront 콘솔의 캐시 정책 화면에서 Cache policy에 Viewer-Language가 포함됐는지 확인한다.

11. 도메인 4 태스크 2·3 — 관측 가능성과 최적화11-08

애플리케이션 수준 캐시로 성능 개선하기

애플리케이션 수준 캐시는 데이터베이스 결과나 자주 읽는 항목을 메모리나 Redis 같은 빠른 저장소에 먼저 담아 두어 같은 요청이 원본 저장소를 다시 읽지 않게 하는 기법입니다.

먼저 알아야 할 것 11-07

#1문제 상황

데이터베이스를 매번 읽으면 같은 값을 여러 번 가져와 지연이 늘고, 애플리케이션 자원과 트래픽 최고점 사이의 간격이 커진다.

애플리케이션 수준 캐시는 그 값을 메모리에 먼저 둔다. Amazon ElastiCache 같은 저장소를 함께 쓰면 여러 인스턴스가 그 값을 나눠 쓴다(→ 11-07).

#2핵심 질문

같은 값을 반복해서 읽는 요청을 원본 저장소에 가지 않고 어떻게 빠르게 끝낼까?

#3동작 예시

상품 목록을 보여 주는 화면에서 캐시가 비어 있으면 첫 요청은 데이터베이스를 읽고 결과를 캐시에 담는다. 그 뒤 요청은 캐시에서 바로 읽는다.

캐시에서 읽힌 응답 시간은 첫 요청보다 짧다. 캐시 만료 뒤에는 다시 원본을 읽고 다시 담는다.

#4동작 과정

  1. 병목을 찾는다애플리케이션 로그에서 반복되는 조회가 어디서 느린지 본다. 애플리케이션 성능 문제의 원인 구간을 먼저 정한다.
  2. 캐시 계층을 둔다애플리케이션 수준 캐시를 코드 안에 두고 자주 읽는 항목만 담는다. 여러 인스턴스가 함께 써야 하면 Amazon ElastiCache를 쓴다.
  3. 자원 사용을 줄인다캐시가 곧바로 적용되지 않는 항목은 애플리케이션 자원 사용량을 보고 크기를 조정한다. 애초에 읽지 않도록 고친다.
  4. 확인해 볼 것애플리케이션 로그에서 같은 조회 요청이 반복된 횟수를 세어 캐시 적용 전후를 비교한다.

#5한 줄 요약

애플리케이션 수준 캐시자주 읽는 값을 빠른 저장소에 먼저 담아 원본 읽기를 없애는 것
