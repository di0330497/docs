생명주기의 뼈대01-01

1단계 생명주기의 뼈대

소프트웨어가 아이디어 착수에서 개발·운영을 거쳐 폐기될 때까지 지나는 전체 기간을 단계로 나눠 관리하는 틀이다.

#1문제 상황

기존에는 소프트웨어 개발을 프로젝트 하나로 보고, 일이 진행되면서 벌어지는 일들을 기록하지 않았다. 어떤 단계에 누가 뭘 했는지, 언제 결정된 것인지, 그리고 나중에 운영하면서 문제가 생기면 어디서 뭐가 잘못되었는지 추적할 수 없었다. 개발이 끝나면 그만이라고 생각했다.

#2핵심 질문

소프트웨어는 아이디어부터 폐기까지 어떻게 단계적으로 관리하고, 각 단계에서 뭘 확인해야 한다?

#3동작 예시

집을 짓는 과정이 있다면, 땅 고르기→평면도 작성→기초 공사→벽 세우기→인테리어→입주→유지보수→철거라는 단계가 있다. 소프트웨어도 비슷하게 착수→요구 정의→설계→구현→검증→배포→운영→폐기라는 단계들이 차례로 일어난다. 각 단계마다 검수와 승인이 들어가야 다음 단계로 넘어갈 수 있다.

#4동작 과정

  1. 생명주기 범위 정의소프트웨어가 태어나는 순간(아이디어 제안)부터 죽는 순간(서비스 종료, 코드 삭제)까지의 전체 여정을 하나의 큰 틀로 본다.
  2. 단계 구분 및 프로세스 수립착수·계획·요구·설계·구현·검증·배포·운영 같은 명확한 단계들을 나누고, 각 단계마다 누가 뭘 해야 하는지를 문서로 정의한다.
  3. 추적·제어·평가소프트웨어가 각 단계를 통과할 때마다 상태를 기록하고, 나중에 문제가 생기면 그 추적 기록을 따라 원인을 찾을 수 있도록 만든다.

#5한 줄 요약

소프트웨어 개발 전체를 명확한 단계들로 나눠 체계적으로 관리하고, 각 단계의 활동과 산출물을 추적 가능하도록 하는 관리 틀

1단계 생명주기의 뼈대

계획에서 시작해 요구 정의, 설계, 구현, 검증을 거쳐 운영으로 이어지는 여섯 국면이 SDLC 의 기본 흐름이다.

#1문제 상황

개발을 시작할 때, 팀들이 각자 다르게 진행했다. 누군가는 설계를 무시하고 바로 코딩했고, 누군가는 계획 없이 요구를 받았고, 테스트는 따로 관여하지 않았다. 결과적으로 같은 프로젝트인데도 진행 방식이 제각각이었고, 다른 회사 사람과 협력하거나 표준화가 필요할 때 문제가 생겼다.

#2핵심 질문

소프트웨어 개발이 항상 거쳐야 하는 필수 단계는 어떤 것들이고, 그 순서는 어떻게 되는가?

#3동작 예시

SDLC의 표준 흐름은 6개 국면으로 이루어진다. 먼저 계획 단계에서 프로젝트 목표와 자원을 정의한다. 요구 분석 단계에서 "정확히 뭘 만들어야 하는가"를 문서로 작성한다. 설계 단계에서 "어떻게 만들 것인가"의 구조를 그려본다. 구현 단계에서 실제 코드를 작성한다. 검증 단계에서 그 코드가 요구대로 작동하는지 확인한다. 마지막으로 운영 단계에서 사용자들에게 제공하고 문제를 처리한다.

#4동작 과정

  1. 계획 (Plan)프로젝트 목표, 기간, 투입 인력, 예산을 정의하고 리스크를 미리 파악한다.
  2. 요구·설계·구현·검증 (Requirements → Design → Development → Testing) — 고객의 요구사항을 명확히 하고, 그에 맞춰 구조를 설계한 뒤 코드로 구현한 후, 요구사항대로 동작하는지 테스트한다.
  3. 운영 (Operations)완성된 소프트웨어를 사용자에게 제공하고, 버그 수정 및 업데이트를 계속 진행한다.

#5한 줄 요약

소프트웨어를 만들 때 반드시 거쳐야 할 6개의 순차적 국면(계획·요구·설계·구현·검증·운영)을 정의해, 모든 팀이 같은 방식으로 진행하도록 하는 표준화된 틀

12207:2017 은 소프트웨어 생명주기 활동을 합의·조직지원·기술관리·기술 프로세스 그룹으로 묶어 표준화한 국제 규격이다.

#1문제 상황

SDLC를 6개 단계로 구분하는 것만으로는 부족했다. 실제로는 팀 내에서 누가 뭘 해야 하는지, 프로젝트 관리자는 뭘 감시해야 하는지, 품질 보증은 언제 개입하는지 등이 명확하지 않았다. 각 회사마다 해석이 달랐고, 결과적으로 프로젝트마다 진행 방식이 다르면서 협력이나 감시가 어려워졌다.

#2핵심 질문

소프트웨어 생명주기의 모든 활동을 체계적으로 분류하고 각 활동의 책임 범위를 정의하는 국제 표준이 있는가?

#3동작 예시

ISO/IEC/IEEE 12207:2017은 소프트웨어 생명주기의 모든 활동을 4개 그룹으로 분류한다. 첫째, 합의 프로세스는 계약자와 공급자 간 합의 내용을 정의한다. 둘째, 조직지원 프로세스는 조직이 프로젝트를 관리·지원하는 방식을 정의한다. 셋째, 기술관리 프로세스는 실제 개발을 통제·감시하는 활동을 정의한다. 넷째, 기술 프로세스는 개발·검증·지원·운영 같은 기술 활동 자체를 정의한다.

#4동작 과정

  1. 프로세스 그룹 분류소프트웨어 생명주기에 필요한 모든 활동을 합의, 조직지원, 기술관리, 기술 네 범주로 나눈다.
  2. 각 프로세스 정의각 그룹 안에서 구체적인 프로세스(예: "요구사항 분석 프로세스", "변경 제어 프로세스")를 정의하고, 그 프로세스가 언제 필요한지, 누가 책임인지를 명시한다.
  3. 국제 표준으로 통합이 분류를 ISO/IEC/IEEE 12207 표준으로 정의해, 전 세계 소프트웨어 조직들이 같은 기준으로 작업할 수 있게 한다.

#5한 줄 요약

소프트웨어 생명주기의 모든 활동을 합의·조직지원·기술관리·기술이라는 4개 그룹으로 체계적으로 분류하고, 국제 표준으로 정의해 모든 조직이 일관되게 운영할 수 있도록 하는 것

기획자·개발자·테스터·운영자·고객처럼 생명주기 각 단계에서 책임을 지거나 결과에 이해관계를 갖는 사람들이다.

#1문제 상황

소프트웨어 프로젝트를 진행할 때, 누가 뭘 결정하는지 불분명했다. 요구사항은 누가 정하는가, 설계는 누가 승인하는가, 테스트를 통과했는지 누가 판단하는가. 책임 소재가 명확하지 않으면 결정이 지연되고, 문제가 생기면 누구 책임인지 싸움이 났다. 그리고 요구사항을 가진 고객이 실제로 원하는 게 뭔지 알기 어려웠다.

#2핵심 질문

소프트웨어 개발 과정에서 각 단계마다 누가 의견을 내고, 누가 결정하고, 누가 책임을 지는가?

#3동작 예시

SDLC에 참여하는 역할들은 다음과 같다. 기획자(PM)는 프로젝트의 전체 목표와 일정을 정의한다. 비즈니스 분석가는 고객의 요구를 듣고 정확히 뭘 만들어야 하는지 문서화한다. 개발자(엔지니어)는 설계를 받아 코드로 구현한다. 테스터는 완성된 코드를 검증하고 버그를 찾는다. 운영자는 배포된 소프트웨어를 운영하고 문제를 해결한다. 고객은 최종 요구사항을 제시하고 결과물을 승인한다. 각 역할이 정해진 책임을 수행하면 시스템 전체가 흘러간다.

#4동작 과정

  1. 역할 정의프로젝트마다 PM, 분석가, 개발자, 테스터, 운영자, 고객처럼 필요한 역할을 정하고 각각의 책임 범위를 명확히 한다.
  2. 이해관계자 파악프로젝트에 영향을 받거나 영향을 주는 모든 사람(이해관계자)을 파악하고, 그들이 언제, 어떤 결정에 참여해야 하는지 정한다.
  3. 의사소통 구조 수립각 역할 간에 정보가 제때 전달되고, 결정이 지연되지 않도록 보고 경로와 승인 프로세스를 정한다.

#5한 줄 요약

소프트웨어 개발에 참여하는 모든 역할(기획자, 개발자, 테스터, 운영자, 고객)을 명확히 하고, 각각이 언제 어떤 책임을 지는지 정의해 프로젝트가 명확한 의사결정과 책임 추적을 통해 진행되도록 하는 것

1단계 생명주기의 뼈대

요구서·설계서·코드·빌드 결과 같은 산출물을 남기고 서로 연결해 어떤 요구가 어떤 코드와 테스트로 이어졌는지 되짚는 능력이다.

#1문제 상황

개발이 끝나고 나중에 문제가 생기면, 어느 요구사항이 어느 코드와 연결되는지 알 수 없었다. 테스트는 언제 되었나, 무엇을 테스트했나, 그 테스트가 어느 코드 부분을 검증하는 건가. 변경 사항이 생기면 어디서부터 뭘 확인해야 하는지 명확하지 않았고, 그 결과 버그 원인을 찾는 데 오래 걸렸다.

#2핵심 질문

고객의 요구사항이 실제 코드, 테스트, 배포, 운영까지 어떻게 연결되어 추적 가능하게 할 수 있는가?

#3동작 예시

추적성은 요구사항부터 시작해 역으로 따라가는 능력이다. 예를 들어 사용자가 "로그인 기능이 3초 이내에 완료되어야 한다"는 요구사항을 제시했다면, 그 요구사항은 설계 문서에 반영되고, 설계는 코드(로그인 모듈의 캐싱 로직)로 구현되고, 테스트 케이스(3초 이내 로그인 속도 측정)로 검증되고, 배포 후 모니터링에서 확인된다. 나중에 "로그인이 느리다"는 버그 보고가 들어오면, 이 연결고리를 따라 어느 요구사항에서 시작된 건지, 어느 코드가 책임인지, 어느 테스트가 실패한 건지 한눈에 파악할 수 있다.

#4동작 과정

  1. 산출물 정의각 단계에서 생산되는 결과물(요구서, 설계서, 소스 코드, 테스트 케이스, 배포 로그)을 정의하고 고유하게 식별(ID, 버전)한다.
  2. 추적 연결고리 구축각 산출물 간의 관계를 명시한다. 예를 들어, "요구사항 #123은 설계 문서 #456을 통해 구현되었고, 코드 모듈 xyz에 반영되었으며, 테스트 케이스 #789로 검증되었다" 같은 관계를 기록한다.
  3. 변경·추적 관리코드, 요구사항, 테스트 중 하나가 변경되면 그것과 연결된 다른 것들도 함께 변경되었는지 확인하는 프로세스를 운영한다.

#5한 줄 요약

요구사항부터 코드, 테스트, 운영까지 모든 산출물을 서로 연결해 기록하고, 나중에 문제 추적이나 영향 범위 분석을 할 때 어디서부터 어디까지 영향이 미치는지 명확하게 파악할 수 있도록 하는 것

요구사항을 먼저 확정하고 분석·설계·구현·시험을 한 방향으로 순서대로 진행하며, V 모델은 각 개발 단계에 대응하는 시험 단계를 짝지어 놓은 방식이다.

#1문제 상황

프로젝트를 시작할 때, 모든 요구사항을 미리 모아서 처음부터 끝까지 계획한 뒤 한 방향으로 진행했다. 요구사항을 먼저 받으면 분석하고, 설계를 완료하고, 코드를 다 작성한 뒤에야 테스트를 시작했다. 하지만 개발 중에 요구사항이 바뀌거나 고객이 뭔가 다르다고 하면, 이미 설계와 코드가 완성되어 바꾸기 어려웠다. 그리고 마지막 단계인 테스트에서 대량의 버그가 발견되면 프로젝트가 지연되는 일이 많았다.

#2핵심 질문

변경이 자주 일어나거나 요구사항이 명확하지 않은 상황에서, 처음부터 끝까지 순서대로 진행하는 방식의 한계는 무엇인가?

#3동작 예시

폭포수 모델은 건축 공사와 비슷하다. 설계도를 완벽하게 확정한 뒤에 기초 공사를 시작하고, 기초가 완료되어야 벽을 세운다. 만약 벽을 다 세운 후에 "설계도 잘못됐다, 방 배치를 바꿔야 한다"고 하면, 이미 지어진 기초부터 허물어야 한다. V 모델은 여기에 한 가지를 추가했다. 각 개발 단계마다 대응하는 테스트 단계를 짝지어 놓아, 요구사항 분석 직후에 요구사항 검증 테스트를 준비하고, 설계 직후에 설계 검증 테스트를 준비하는 식으로 진행했다. 이렇게 하면 버그를 일찍 찾을 수 있다.

#4동작 과정

  1. 전체 요구사항 확정프로젝트 시작 단계에 고객이 원하는 모든 것을 받아서, 변경 없이 진행한다는 가정 하에 시작한다.
  2. 순차적 진행요구 분석 → 설계 → 구현 → 테스트 → 배포를 한 방향으로 진행하며, 각 단계의 산출물이 검토되고 승인될 때까지 다음 단계로 넘어가지 않는다.
  3. V 모델의 추가V 모델은 각 개발 단계마다 그에 대응하는 테스트 단계를 병렬로 준비해, 구현 직후 바로 테스트할 수 있게 한다.

#5한 줄 요약

요구사항을 먼저 완벽하게 확정하고, 그에 따라 설계와 구현을 순차적으로 진행하되, V 모델에서처럼 각 개발 단계마다 테스트를 병렬로 준비해 검증을 앞당기는 예측형 프로세스 모델

제품을 작은 주기로 여러 번 나눠 만들고 다듬어 가는 방식으로, 나선형 모델은 각 주기마다 위험 분석을 넣어 크고 불확실한 프로젝트를 다룬다.

#1문제 상황

폭포수 모델과 V 모델은 처음부터 모든 요구사항을 확정하고 진행하는 방식이었다. 하지만 현실의 프로젝트는 다르다. 사용자의 요구사항이 계속 바뀌고, 시작할 때는 뭘 원하는지 완전히 알 수 없는 경우가 많다. 또한 시장이 빨리 변하면, 완성할 때까지 기다릴 수 없고 중간에라도 사용자에게 보여줘야 한다. 그래서 처음부터 끝까지 한 번에 하는 대신, 작은 단위로 여러 번 반복하면서 만들고, 각 반복마다 고객 피드백을 받아 조정하는 방식이 필요해졌다.

#2핵심 질문

요구사항이 명확하지 않거나 자주 바뀌고, 시간이 제한되어 있을 때, 전체를 한 번에 만드는 대신 작은 단위로 여러 번 만들면서 검증하는 방식을 어떻게 체계화할 수 있는가?

#3동작 예시

반복·점증 모델은 소프트웨어를 한 덩어리가 아니라 작은 조각들로 나눠 만든다. 예를 들어 1주일 단위(스프린트)로 계획하고, 그 주 동안 작은 기능들을 구현·테스트·배포하고, 주말에 고객에게 보여준다. 고객의 피드백을 받으면 다음 주 계획에 반영한다. 이렇게 2주, 3주를 반복하다 보면, 요구사항이 바뀌어도 이미 완성된 부분은 그대로 두고 다음 주기에서만 조정하면 된다. 나선형 모델은 여기에 더해 각 주기마다 위험 분석을 넣는다. 크고 불확실한 프로젝트일수록, "이 기능을 만들면 기술적으로 문제가 없을까", "보안 문제는 없을까" 같은 리스크를 매 주기마다 확인한다.

#4동작 과정

  1. 작은 범위로 계획전체 요구사항을 먼저 완성하려 하지 않고, 1~3주 정도의 짧은 사이클(스프린트, 이터레이션)로 나눠 계획한다.
  2. 반복하며 피드백 반영각 사이클마다 계획→설계→구현→테스트→배포를 끝내고, 고객에게 작동하는 부분을 보여줘 피드백을 얻는다. 피드백은 다음 사이클의 요구사항에 반영된다.
  3. 나선형 모델에서는 리스크 관리 추가각 사이클마다 기술적 위험, 보안 위험, 일정 위험을 분석해, 큰 문제가 될 것 같은 것부터 우선적으로 다룬다.

#5한 줄 요약

소프트웨어를 작은 주기로 반복해 만들면서 각 주기마다 고객 피드백을 받아 반영하고, 나선형 모델에서 각 주기마다 리스크를 분석해 크고 불확실한 프로젝트를 안정적으로 진행하는 적응형 프로세스 모델

애자일 선언 — 네 가치와 열두 원칙

문서·계약·계획보다 사람·동작하는 소프트웨어·협력·변화 대응을 앞세운 네 가지 가치와, 이를 실천으로 풀어낸 열두 원칙이다.

#1문제 상황

기존 개발 방식은 프로젝트 시작 시 전체 요구사항을 정확히 파악한 후 상세한 계획을 세우고, 계획에 따라 개발했습니다. 하지만 개발 중에 비즈니스 요구사항이 바뀌거나 새로운 조건이 생기면, 처음부터 계획을 다시 세워야 했습니다. 이렇게 되면 이미 진행된 개발이 낭비되고, 계획을 수립하는 데만 시간과 비용이 계속 들었습니다.

#2핵심 질문

개발 중에 요구가 바뀔 때마다 계획부터 다시 세우지 않으려면?

#3동작 예시

개발팀이 매주 동작하는 소프트웨어를 내놓고, 그것을 보고 사용자나 기획자가 요구를 조정합니다. 예를 들어 1주차에 기본 로그인 화면을 완성해서 보여주면, 사용자가 "여기 이 버튼을 이렇게 바꿔달라" 하고 피드백을 주고, 2주차에 그것을 반영한 새 버전을 내놓는 식입니다.

#4동작 과정

  1. 초기 요구 수집시작할 때는 완벽한 계획이 아니라 대략적인 방향과 가장 중요한 것들만 파악합니다.
  2. 자주 동작하는 결과 생성매주 또는 격주마다 실제로 동작하는 소프트웨어 일부를 만들어 냅니다.
  3. 피드백 반영그것을 보고 받은 요구사항을 다음 주기 계획에 반영합니다.

#5한 줄 요약

완벽한 계획을 세운 후 그대로 실행하는 것이 아니라, 자주 동작하는 결과를 내놓으며 그때그때 요구를 조정하는 방식

Scrum — 책무·이벤트·산출물·확약

Scrum Guide 2020 기준으로 세 책무(PO·SM·개발자), 다섯 이벤트(스프린트와 네 회의), 세 산출물과 각 산출물의 확약으로 짜인 경험적 프레임워크다.

#1문제 상황

애자일 방식으로 자주 결과를 내놓는다는 건 좋은데, 실제로는 누가 무엇을 책임지는지, 어떤 일정으로 일을 진행하는지, 어떤 결과물을 내놓는지가 애매했습니다. 팀마다 다르게 이해해서 협력이 흐트러지거나, 계획 없이 돌아가다 보니 중간중간 혼란이 생겼습니다.

#2핵심 질문

애자일을 실제로 실행하려면 누가 뭘 하고, 어떤 리듬으로 일해야 하나?

#3동작 예시

제품소유자(PO)가 사용자 요구를 우선순위 순으로 정리하고, 스크럼 마스터(SM)가 회의 진행과 장애물 제거를 담당하며, 개발자들이 2주 동안 해야 할 일(스프린트)을 정한 뒤 매일 오전에 어제 한 일, 오늘 할 일, 막힌 것을 공유하고, 2주 후에는 완성한 기능을 사용자 앞에서 보여주며 피드백을 받습니다.

#4동작 과정

  1. 스프린트 계획 회의이번 스프린트(보통 2주)에 무엇을 만들지, 누가 무엇을 책임질지 정합니다.
  2. 매일의 협력매일 아침에 짧은 회의(보통 15분)에서 진행 상황을 공유하고, 막혀있는 부분을 즉시 푼다.
  3. 스프린트 종료와 검증2주 후 완성한 결과(산출물)를 실제 사용자 앞에서 보여주고 피드백을 받으며, 팀이 잘한 점과 개선할 점을 함께 정리합니다.

#5한 줄 요약

3개 역할(제품소유자·스크럼 마스터·개발자)이 정해진 스프린트(보통 2주) 주기로 계획·실행·피드백을 반복하는 구조

Kanban과 흐름 기반 관리

작업을 보드에 시각화하고 진행 중 업무 수(WIP)를 제한해 흐름과 리드타임을 개선하는, 역할·주기를 강제하지 않는 관리 방식이다.

#1문제 상황

Scrum처럼 정해진 2주 주기로 일하면, 각 팀이나 역할마다 일하는 속도가 다를 때 문제가 생깁니다. 누군가는 이미 일을 다 끝냈는데 다음 스프린트를 기다려야 하거나, 누군가는 일이 남아있어서 다음 사이클에 밀려갑니다. 이렇게 되면 일의 흐름이 끊기고 전체 효율이 떨어집니다.

#2핵심 질문

정해진 주기 없이도 일을 효율적으로 계속 흘려보낼 수 있나?

#3동작 예시

모든 작업을 보드에 "할 일", "진행 중", "완료" 세 칸으로 나눠 놓고, 동시에 진행하는 작업 개수를 정해서(예: 진행 중 칸에는 최대 3개만 있도록) 한 칸당 작업이 쌓이는 것을 막습니다. 그러면 일이 왼쪽에서 오른쪽으로 계속 흘러가고, 각 작업이 얼마나 빨리 완료되는지도 명확해집니다.

#4동작 과정

  1. 작업 시각화모든 작업(할 일, 진행 중, 완료)을 보드에 눈에 보이도록 표시합니다.
  2. 진행 중 작업 제한(WIP 제한)동시에 진행할 작업의 최대 개수를 미리 정해두고, 그 개수를 넘지 않도록 합니다.
  3. 흐름 개선일이 왼쪽에서 오른쪽으로 흘러가는 속도를 높이고, 각 작업이 완료될 때까지 걸리는 시간(리드타임)을 줄입니다.

#5한 줄 요약

정해진 주기 없이 작업을 시각화하고 진행 중인 일의 개수를 제한해서 일이 흘러가는 속도를 높이는 방식

모델 선택 기준과 대규모 애자일

요구 변동성·위험·규제·팀 규모를 따져 모델을 고르고, 팀이 여러 개로 커지면 SAFe·LeSS·Scrum of Scrums 같은 확장 틀로 조율한다.

#1문제 상황

Scrum과 Kanban은 각각 다른 상황에 맞습니다. 어떤 프로젝트는 빨리 요구가 바뀌므로 Scrum의 정해진 주기가 좋지만, 다른 프로젝트는 요구가 비교적 안정적이므로 Kanban으로 계속 흘려보내는 게 효율적입니다. 또한 팀이 작을 땐 한 팀이 Scrum을 하면 되지만, 팀이 20명을 넘으면 여러 팀의 작업을 조율하는 문제가 생깁니다.

#2핵심 질문

어떤 경우에 Scrum을 쓸지, Kanban을 쓸지, 팀이 여러 개일 땐 어떻게 조율할지?

#3동작 예시

요구가 자주 바뀌는 신규 기능 프로젝트는 Scrum으로 2주씩 조정하고, 기존 시스템 유지보수처럼 요구가 비교적 안정적인 업무는 Kanban으로 계속 흘려보냅니다. 팀이 10명 이상이면 각 팀이 Scrum으로 자신의 일을 하면서, 팀 간 조율은 "Scrum of Scrums"(팀 리더들이 모여서 의존성 확인)나 SAFe(대규모 애자일 프레임워크)로 합니다.

#4동작 과정

  1. 프로젝트 특성 평가요구 변동성, 위험도, 규제 수준, 팀 규모를 확인합니다.
  2. 모델 선택평가 결과에 맞는 Scrum 또는 Kanban을 선택합니다.
  3. 대규모 조율팀이 2개 이상이면 여러 팀의 작업을 조율할 틀(Scrum of Scrums, SAFe, LeSS)을 덧붙입니다.

#5한 줄 요약

프로젝트의 특성과 팀 규모에 따라 Scrum이나 Kanban 같은 모델을 고르고, 필요하면 대규모 조율 틀을 덧붙이는 것

#4동작 과정

#4동작 과정

  1. 사용자 스토리사용자 관점에서 한 문장으로 "누가 무엇이 필요한 이유"를 적습니다.

시스템 전체를 어떤 독립적인 부분들로 나누고, 그것들이 어떻게 통신하도록 할 것인가?

#4동작 과정

  1. 아키텍처 설계시스템을 기능 또는 도메인 기준으로 주요 덩어리(컴포넌트)로 나누고, 각 덩어리 간의 인터페이스(API, 메시지 포맷 등)와 데이터 흐름을 정합니다.

  3. 일관성 검증아키텍처와 상세 설계가 서로 맞는지, 전체 시스템이 요구사항을 만족할 수 있는지 검토합니다.

성능·보안·신뢰성·유지보수성 같은 품질 속성(비기능 요구)이 무엇을 얼마나 중요하게 볼지 정하고, 그 우선순위가 아키텍처 선택을 좌우한다.

#1문제 상황

아키텍처를 설계할 때 "기능이 동작하면 된다"는 기준만으로 결정하면, 시스템이 완성된 뒤에 성능이 느려서 병목이 생기고, 보안 취약점이 터지고, 한 곳을 수정하면 다른 곳이 무너지고, 새로운 기능을 추가하기 어려워지는 문제가 발생합니다.

#2핵심 질문

#3동작 예시

은행 거래 시스템을 만들 때 "신뢰성과 보안이 최고 우선"이면 모든 거래를 즉시 검증하고 암호화하도록 설계합니다. 반면 SNS 피드 시스템을 만들 때 "사용성과 응답성이 최고 우선"이면 약간의 지연을 감수하고 캐시를 적극 활용한 설계를 합니다. 같은 기술이라도 품질 우선순위에 따라 완전히 다른 아키텍처가 나옵니다.

#4동작 과정

  1. 품질 속성 정의성능(처리 속도), 신뢰성(장애 복구), 보안(데이터 보호), 유지보수성(수정 용이성), 확장성(규모 증대 대응) 등 비기능 요구사항(품질 모델)을 명시합니다.
  2. 우선순위 결정이 시스템에서 가장 중요한 품질 속성 3개를 선택합니다.
  3. 아키텍처 선택선택된 품질 속성을 최대한 달성할 수 있는 구조(예: 분산 시스템, 마이크로서비스, 캐싱 레이어 등)를 설계합니다.

모듈화·결합도·응집도와 느슨한 결합

기능을 관련 있는 것끼리 한 모듈로 모으고(응집도 높게) 모듈 사이 의존은 최소화해서(결합도 낮게) 한 곳을 고쳐도 다른 곳이 무너지지 않게 만드는 설계 원칙이다.

#1문제 상황

코드가 엉켜있으면, 한 곳을 수정할 때 다른 곳까지 영향을 받고, 한 기능을 추출해 재사용하기 어렵고, 테스트를 하려면 관련된 모든 부분을 함께 실행해야 합니다. 이렇게 되면 수정과 추가가 점점 더 어려워집니다.

#2핵심 질문

한 곳의 변경이 다른 곳까지 연쇄적으로 영향을 주지 않으려면, 기능들을 어떻게 조직화하고 분리해야 할까?

#3동작 예시

전자상거래 시스템에서 "결제 처리 로직"과 "배송 조회 로직"을 별개의 모듈로 분리하고, 둘이 필요할 때만 정해진 인터페이스(예: API)를 통해 호출하도록 합니다. 결제 처리의 내부 구현이 바뀌어도 배송 조회 모듈은 영향을 받지 않습니다.

#4동작 과정

  1. 모듈 식별기능을 비즈니스 도메인이나 기술 계층 기준으로 관련 있는 것끼리 묶어 모듈로 나눕니다.
  2. 응집도 높이기각 모듈 내부의 요소들(클래스, 함수)은 강한 관계를 가지게 하고(내부적으로는 밀착), 한 모듈이 하나의 책임만 집중하도록 설계합니다.
  3. 결합도 낮추기모듈 사이의 의존성을 최소화하고, 꼭 필요한 부분만 정해진 인터페이스로 노출해 한 모듈의 변경이 다른 모듈에 미치는 영향을 줄입니다.

#5한 줄 요약

시스템을 독립적으로 이해하고 수정할 수 있는 응집된 모듈들로 분할하고, 모듈 사이의 결합을 최소화해 변경의 영향 범위를 제한하는 것

아키텍처 스타일: 모놀리스·계층형·마이크로서비스

하나로 뭉친 모놀리스, 표현·업무·데이터 층으로 쌓는 계층형, 독립 배포되는 작은 서비스들로 쪼개는 마이크로서비스 등 검증된 시스템 구성 패턴들이다.

#1문제 상황

시스템이 작을 때는 모든 기능을 하나의 프로그램으로 묶어도 괜찮지만, 시스템이 커지면 특정 부분의 변경이 전체에 영향을 주고, 한 부분만 빠르게 재배포하기 어렵고, 한 부분의 부하가 전체 시스템의 성능을 떨어뜨리는 문제가 생깁니다.

#2핵심 질문

시스템 규모가 커질수록 기능을 어느 정도 크기로 나누고 배포해야 변경과 운영이 독립적으로 될까?

#3동작 예시

쇼핑몰 시스템에서 모놀리스 방식은 상품 관리, 주문 처리, 결제, 배송을 모두 하나의 war 파일로 배포합니다. 계층형은 UI 계층, 비즈니스 로직 계층, 데이터 계층으로 수직으로 나눕니다. 마이크로서비스는 상품 서비스, 주문 서비스, 결제 서비스, 배송 서비스를 독립적인 프로세스/컨테이너로 실행하고 각각 따로 배포합니다.

#4동작 과정

  1. 모놀리스모든 기능을 하나의 애플리케이션으로 구성하고, 수정할 때마다 전체를 다시 컴파일하고 배포하는 방식입니다.
  2. 계층형표현(UI), 비즈니스 로직, 데이터 접근을 수직 계층으로 분리하되, 여전히 하나의 배포 단위로 움직입니다.
  3. 마이크로서비스각 비즈니스 도메인을 독립 배포 가능한 작은 서비스로 분할하고, 서비스 간은 네트워크 통신(REST, 메시지 큐 등)으로 연결합니다.

#5한 줄 요약

시스템 규모와 팀 규모에 따라 기능을 나누고 배포하는 단위를 결정하는 것으로, 변경과 배포의 독립성을 높일수록 개발 속도와 안정성이 향상됩니다

데이터 설계와 스키마 변경 관리

어떤 데이터를 어떤 저장소에 어떤 구조로 담을지 정하고, 운영 중 스키마를 바꿀 때 기존 데이터와 코드가 깨지지 않도록 버전을 관리하며 단계적으로 바꾸는 일이다.

#1문제 상황

기존에는 데이터베이스의 테이블 구조를 처음부터 정해놓고 시작했다. 하지만 서비스가 커지면서 새로운 데이터를 저장해야 하거나 기존 구조를 바꿔야 할 때, 이미 저장된 수백만 건의 데이터가 있으면 구조 변경이 위험해진다. 데이터베이스 스키마(테이블의 열과 데이터 타입 정의)를 바꾸는 순간 기존 코드가 깨지거나 데이터 손실이 생길 수 있기 때문이다.

#2핵심 질문

운영 중인 서비스의 데이터베이스 구조를 안전하게 어떻게 변경할 수 있을까?

#3동작 예시

사용자 테이블에 새로운 열(예: phone 필드)을 추가하려고 한다면, 먼저 빈 상태의 그 열을 생성하고, 코드를 수정해 새 필드를 쓸 수 있게 만든 다음, 나중에 기존 데이터를 채우는 방식으로 진행한다. 한 번에 모든 걸 바꾸지 않는 것이다.

#4동작 과정

  1. 필드 호환성 유지새 필드를 추가할 때는 없어도 작동하는 상태로 시작한다. 예를 들어 phone 필드가 빈 상태거나 기본값을 갖도록 한다. 그러면 기존 코드가 이 필드를 무시해도 계속 실행된다.
  2. 코드 먼저 배포새 필드를 사용할 수 있는 코드를 서버에 배포한다. 이 코드는 필드가 없으면 건너뛰고, 있으면 쓴다.
  3. 데이터 마이그레이션기존 데이터 값을 채우거나 형식을 바꾼다. 이 작업은 코드 배포와 분리되어 진행되므로 실수해도 데이터베이스와 코드가 동시에 깨지지 않는다.

#5한 줄 요약

데이터 구조 변경을 여러 단계로 나누어, 각 단계에서 시스템이 여전히 작동하도록 하면서 점진적으로 전환하는 것

설계 검토와 아키텍처 결정 기록

설계를 코드로 옮기기 전에 여럿이 함께 따져보고, 무엇을 왜 그렇게 정했는지와 버린 대안을 ADR 문서로 남겨 나중에 이유를 되짚을 수 있게 하는 활동이다.

#1문제 상황

보통은 팀의 리드나 아키텍트가 설계를 혼자 또는 몇몇과 정한 다음, 그것을 코드로 옮기기 시작한다. 하지만 나중에 다른 개발자가 "왜 이렇게 설계했지?"라고 묻거나, 새 기술이 나와서 다른 방식이 더 나을 것 같을 때, 기록이 없으면 설계 이유를 알 수 없다. 결국 같은 논쟁을 반복하거나 잘못된 결정을 다시 내린다.

#2핵심 질문

설계 결정의 이유와 버린 대안들을 어떻게 기록해서 나중에 되짚을 수 있을까?

#3동작 예시

어느 팀이 데이터베이스를 선택할 때 PostgreSQL, MongoDB, DynamoDB 중에 고민했다고 하자. 최종적으로 PostgreSQL을 정했다면, 선택 이유(트랜잭션이 중요해서), 고려한 대안들(MongoDB는 트랜잭션 약하고 비용이 높다), 앞으로 재검토할 조건(데이터가 너무 커지면 수평 확장 고민)을 문서에 남긴다.

#4동작 과정

  1. 설계 검토 회의여럿이 함께 가능한 방안들을 놓고 따져본다. 각 방안의 장점과 단점, 비용과 효과를 구체적으로 논의한다.
  2. 결정 기록ADR(Architecture Decision Record, 아키텍처 결정 기록)라 불리는 짧은 문서를 남긴다. 여기에는 무엇을 정했는지, 왜 그 결정을 내렸는지, 고려한 다른 선택지와 그걸 버린 이유를 기록한다.
  3. 공유와 추적이 문서를 버전 관리 시스템(깃)에 함께 저장해서 팀 모두가 접근할 수 있고, 나중에 그 기록을 되짚을 수 있다.

#5한 줄 요약

중요한 설계 결정을 이유와 함께 기록하고 공유함으로써, 팀의 지식이 한 사람의 머릿속에만 남지 않도록 하는 것

구현과 형상관리05-01

코딩 표준·스타일 가이드·개발 환경

팀이 같은 규칙으로 코드를 쓰도록 정한 작성 규약과, 그 규칙을 자동으로 강제해 주는 편집기·린터·포매터 등 개발 환경을 갖추는 일이다.

#1문제 상황

각자 자기 방식대로 코드를 쓰면, 같은 프로젝트에 이름 짓기 방식이 제각각이고, 들여쓰기도 다르고, 어떤 개발자는 세미콜론을 쓰지 않는다. 그러면 코드 리뷰할 때 "왜 이 변수를 camelCase로 썼어?" 같은 스타일 논쟁이 생기고, 가장 위험한 것은 실수를 감지하기 어려워진다. 바뀐 코드가 정말 버그인지, 아니면 그냥 다른 스타일인지 구분하기 힘들기 때문이다.

#2핵심 질문

팀 전체가 같은 규칙으로 코드를 쓰도록 강제하고, 그 규칙을 자동으로 점검할 수 있을까?

#3동작 예시

JavaScript 팀이 Prettier(자동 포매팅 도구)와 ESLint(규칙 점검 도구)를 편집기에 연결한 경우, 개발자가 저장 버튼을 누르는 순간 자동으로 들여쓰기가 맞춰지고, 사용하지 않는 변수나 위험한 패턴이 있으면 경고가 나타난다. 별도의 검수 과정 없이 도구가 일관성을 보장한다.

#4동작 과정

  1. 코딩 표준 정의팀이 변수 이름(camelCase vs snake_case), 들여쓰기, 한 줄의 최대 글자 수 등을 함께 정한다.
  2. 자동화 도구 적용Prettier(포매팅), ESLint(규칙 검사), Checkstyle(스타일 점검) 같은 도구를 빌드 파이프라인과 편집기에 연결해서, 코드 저장이나 커밋할 때 자동으로 규칙을 확인하고 위반하면 진행을 막는다.
  3. 개발 환경 공유모든 개발자가 같은 편집기 설정 파일(예: .editorconfig, .prettierrc)을 쓰도록 해서, 누가 어디서 작업해도 같은 환경이 된다.

#5한 줄 요약

인간의 일관성 유지 노력을 자동화 도구로 대체해서, 팀원 모두가 동일한 코드 품질 기준을 유지하도록 하는 것

버전 관리와 Git의 기본 모델

소스 코드의 변경 이력을 스냅샷(커밋)으로 저장하고 되돌릴 수 있게 하는 도구가 버전 관리이며, Git 은 각자 저장소 사본을 갖는 분산형 모델을 쓴다.

#1문제 상황

옛날에는 소스 코드를 파일로 관리했다. 새 버전을 만들 때마다 파일을 복사해서 code_v1.py, code_v2.py, code_v3.py 같은 식으로 저장했다. 문제는 어느 버전에서 어떤 버그가 고쳐졌는지 알 수 없고, 여럿이 동시에 작업하면 누가 뭘 바꿨는지 충돌이 생긴다는 것이다. 또한 이전 버전으로 돌아가려 해도 몇 달 전 코드를 어디에 뒀는지 기억할 수 없다.

#2핵심 질문

소스 코드의 모든 변경을 추적하고, 필요할 때 이전 상태로 되돌릴 수 있으며, 여럿이 동시에 작업해도 충돌을 관리할 수 있는 방법이 있을까?

#3동작 예시

Git은 코드의 각 상태를 스냅샷으로 저장한다. 파일을 바꾸고 커밋(commit)이라는 명령으로 "현재 상태를 이 메시지와 함께 기록하겠다"고 하면, Git이 그 시점의 모든 파일 내용을 저장한다. 나중에 이전 커밋으로 돌아가고 싶으면 그 커밋의 해시값(고유 번호)을 지정해서 상태를 복원한다.

#4동작 과정

  1. 커밋으로 기록작업자가 코드를 수정한 후 git commit으로 변경을 저장소에 기록한다. 각 커밋에는 타임스탬프, 작업자, 변경 내용, 그리고 작업자가 입력한 메시지가 함께 저장된다.
  2. 분산 저장소 모델Git은 중앙 서버가 아니라 각 개발자의 컴퓨터에 저장소의 완전한 사본(로컬 저장소)을 갖는다. 따라서 인터넷 연결이 없어도 로컬에서 히스토리를 조회하고 되돌릴 수 있다.
  3. 서버와 동기화팀 작업을 위해 원격 저장소(보통 GitHub 같은 서비스)에 변경을 푸시(업로드)하고, 다른 사람의 변경을 풀(다운로드)하면서 협업한다.

#5한 줄 요약

코드의 모든 변경을 시간순으로 기록하고 되돌릴 수 있게 하며, 각자의 로컬 저장소를 갖는 분산형 모델로 팀의 협업을 가능하게 하는 것

브랜칭 전략: 토픽 브랜치·장수 브랜치·트렁크 기반 개발

작업을 어느 가지에서 하고 언제 합칠지 정하는 규칙으로, 짧게 쓰고 버리는 토픽 브랜치와 자주 통합하는 트렁크 기반 개발이 현대적 기본이다.

#1문제 상황

처음에는 모두가 같은 브랜치(마스터 브랜치)에서 작업했다. 하지만 A 개발자가 새 기능을 만들고 있는 와중에 B 개발자가 급히 버그를 고쳐야 한다면, A의 완성되지 않은 코드가 버그 수정과 섞여서 혼란스럽다. 또한 코드 충돌을 해결하는 데 시간이 오래 걸리고, 여러 기능이 섞여서 어느 쪽 버그인지 원인을 파악하기 어렵다.

#2핵심 질문

여러 개발자가 동시에 다른 작업을 하면서도 서로의 미완성 코드를 섞지 않고, 완성된 것만 메인 코드로 합칠 수 있을까?

#3동작 예시

팀이 Git을 쓸 때, 각 개발자가 마스터(메인)에서 토픽 브랜치를 따로 만들어 작업한다. A는 feature/login 브랜치에서 로그인 기능을, B는 bugfix/profile-crash 브랜치에서 프로필 충돌 버그를 고친다. 둘 다 마스터에 영향을 주지 않으면서 병렬로 작업하고, 각각의 작업이 끝나면 마스터로 합친다(머지).

#4동작 과정

  1. 토픽 브랜치 생성각 작업(새 기능, 버그 수정, 리팩토링)마다 메인 브랜치에서 따로 브랜치를 만든다. 이름은 무엇을 하는 브랜치인지 쉽게 알 수 있게 짓는다(예: feature/*, bugfix/*, refactor/*).
  2. 병렬 작업과 자주 통합각자 자신의 브랜치에서 작업하고, 작업이 완료되면 코드 리뷰를 거쳐 메인 브랜치로 머지한다. 트렁크 기반 개발(Trunk-Based Development)은 이 과정을 하루에 여러 번 반복해서 큰 충돌을 방지한다.
  3. 병렬 안정성 유지메인 브랜치는 항상 실행 가능한 상태를 유지한다. 미완성 코드가 섞이지 않기 때문에, 메인에서 빌드나 테스트가 실패해도 그 원인이 명확하다.

#5한 줄 요약

브랜치를 이용해 작업을 격리하고 자주 통합하면서, 메인 코드의 안정성을 지키고 충돌을 최소화하는 것

구현과 형상관리05-04

코드 리뷰와 풀 리퀘스트

합치기 전에 다른 개발자가 변경을 읽고 의견을 다는 절차이며, 풀 리퀘스트는 그 리뷰와 자동 검사를 묶어 진행하는 표준 창구다.

#1문제 상황

과거에는 개발자가 코드를 완성하고 메인 브랜치에 바로 커밋했다. 누군가는 자기 코드를 남이 읽기 전에 병합했고, 버그가 있어도 나중에 발견되었다. 보안 취약점, 성능 문제, 스타일 일관성 문제들이 코드 리뷰 없이 메인에 들어가면서, 나중에 고치는 비용이 크다.

#2핵심 질문

다른 개발자의 검증을 거친 후에만 코드를 메인에 합칠 수 있는 방법이 있을까?

#3동작 예시

개발자가 로그인 기능을 feature/login 브랜치에서 완성했다면, GitHub의 풀 리퀘스트(PR) 기능을 사용해서 "이 브랜치를 메인에 합쳐도 되는가"라는 요청을 팀에 던진다. 다른 개발자들이 코드를 읽고 의견을 남기고, 자동 테스트가 통과하면, 팀이 승인한 후에 비로소 머지된다.

#4동작 과정

  1. 풀 리퀘스트 생성토픽 브랜치에서의 변경을 메인으로 합치기 전에, 풀 리퀘스트라는 창구를 통해 "이 코드를 봐 달라"는 요청을 던진다. PR에는 변경 내용의 설명과 왜 이 코드가 필요한지가 명시된다.
  2. 자동 검사와 수동 리뷰풀 리퀘스트가 생성되면 자동으로 테스트, 린트, 빌드 같은 검사가 실행된다. 동시에 팀원들이 코드를 읽고 문제점을 지적하거나 승인한다.
  3. 승인과 머지충분한 리뷰를 받고 자동 검사를 통과한 후, 지정된 사람이 풀 리퀘스트를 머지하여 메인 브랜치에 합친다.

#5한 줄 요약

코드를 메인에 합치기 전에 팀의 검증 단계를 거쳐서, 품질 기준을 유지하고 버그가 프로덕션에 들어가는 것을 방지하는 것

의존성 관리와 서드파티 컴포넌트

외부 라이브러리의 버전을 고정·추적하고 취약점과 라이선스를 점검해, 남의 코드가 만든 위험까지 관리하는 일이다.

→ 08-03 참조

#1문제 상황

대부분의 프로젝트는 처음부터 다 만들지 않는다. 로그인은 OAuth 라이브러리를, HTTP 통신은 Requests 라이브러리를, 데이터 검증은 Pydantic을 써서 다른 사람이 만든 코드를 재사용한다. 하지만 이런 외부 라이브러리를 특정 버전으로 고정하지 않으면, 팀원마다 다른 버전을 설치해서 "내 컴퓨터에선 돼요"라는 상황이 생긴다. 또한 외부 라이브러리에 보안 취약점이 발견돼도 모르고 쓸 수 있다.

#2핵심 질문

외부 라이브러리의 버전을 일관되게 관리하고, 보안 위험과 라이선스 문제를 미리 파악할 수 있을까?

#3동작 예시

Python 프로젝트에서 requirements.txt 파일에 requests==2.31.0이라고 명시하면, 팀의 모든 개발자와 서버가 정확히 2.31.0 버전을 설치한다. 나중에 requests에 보안 패치가 나와서 2.31.1로 업그레이드하기로 정했을 때, requirements.txt에 이 파일만 수정하고 버전 관리 시스템에 커밋하면 변경 이력이 남고, 팀원 모두에게 통보된다.

#4동작 과정

  1. 의존성 명시프로젝트가 필요로 하는 모든 외부 라이브러리와 정확한 버전을 requirements.txt(Python), package.json(Node.js), pom.xml(Java) 같은 파일에 기록한다.
  2. 보안과 라이선스 검사정기적으로 또는 빌드 파이프라인에서 자동으로 의존성의 알려진 취약점과 라이선스 제약을 검사한다. 위험한 버전을 발견하면 경고하거나 빌드를 중단한다.
  3. 버전 업데이트 계획새 버전이 나왔을 때 바로 갱신하지 않는다. 변경 사항을 검토하고, 자동 테스트를 실행해서 호환성을 확인한 후, 결정한다.

#5한 줄 요약

외부 라이브러리의 버전을 추적·고정·검사함으로써, 팀 전체의 일관성을 보장하고 외부 코드가 야기하는 보안 및 라이선스 위험을 사전에 관리하는 것

5단계 구현과 형상관리

MAJOR.MINOR.PATCH 세 숫자로 호환성 파괴·기능 추가·버그 수정을 구분해 알려 주는 버전 번호 규칙이다.

#1문제 상황

소프트웨어를 릴리스할 때 버전을 1.0, 1.1, 2.0 같은 숫자로 붙인다. 하지만 사용자 입장에서는 이 숫자가 정확히 무엇을 의미하는지 알 수 없다. "1.1로 업데이트했더니 쓰던 기능이 안 된다"거나 "2.0에서 새 기능이 생겼는데 왜 안 쓸 수 있는 상황이 있을까" 같은 혼동이 생긴다. 버전 숫자 자체가 그 안에 담긴 변화를 명확하게 드러내지 못하는 것이 문제다.

#2핵심 질문

버전 번호만 봐도 이전 버전과 어떤 종류의 변화가 있었는지, 내 코드가 깨질 위험은 없는지 바로 알 수 있는 방법이 있을까?

#3동작 예시

시맨틱 버저닝은 버전을 MAJOR.MINOR.PATCH 세 부분으로 나눈다. - MAJOR: 기존 기능과 호환되지 않는 변경(다른 방식으로 동작하거나 없어진 기능)이 있으면 증가 → 2.0.0 - MINOR: 기존 기능은 그대로 유지하면서 새 기능이 추가되면 증가 → 1.5.0 - PATCH: 버그만 수정해서 호환성을 유지하면 증가 → 1.4.3

이렇게 하면 1.4.3 → 1.4.4라는 버전 번호만 봐도 "버그 수정이 있었고 내 코드는 안 깨진다"는 것을 즉시 안다.

#4동작 과정

  1. 버전 번호 구성MAJOR, MINOR, PATCH 세 자리를 정의하고, 각각 언제 증가할지 팀 전체가 합의한다.
  2. 변경 사항 분류새 버전을 만들기 전에 이번 릴리스에 포함된 변화를 "호환성을 깨는 변화인가", "새 기능인가", "버그 수정인가"로 분류한다.
  3. 번호 갱신 및 릴리스분류 결과에 따라 해당하는 자리수만 증가시키고, 뒤의 자리수는 초기화한다(1.5.7에서 호환성 깨는 변화가 있으면 2.0.0이 된다).

#5한 줄 요약

시맨틱 버저닝버전 번호 자체가 변화의 종류를 명확히 드러내서, 사용자가 업데이트 여부와 영향 범위를 빠르게 판단할 수 있게 하는 버전 관리 규칙

5단계 구현과 형상관리

코드를 얼마나 쉽게 고칠 수 있는지가 유지보수성이고, 당장 빠르려고 미룬 정리 작업이 이자처럼 쌓인 비용이 기술 부채다.

#1문제 상황

코드를 짜다 보면 시간 압박이나 일정 문제로 "지금은 빨리 돌리고 나중에 정리하자"고 미룬다. 이렇게 미룬 정리 작업(리팩토링, 테스트 추가, 문서화)들이 모인다. 처음에는 괜찮지만, 쌓이면 쌓일수록 나중에 코드를 고치거나 기능을 추가할 때 시간이 점점 더 오래 걸린다. 작은 변화 하나에도 전체 시스템을 다시 확인해야 하고, 버그가 늘어나고, 새로운 코드를 짜는 것보다 기존 코드를 이해하는 데 시간을 쓴다.

#2핵심 질문

코드가 복잡해지고 고치기 어려워지는 상황을 어떻게 측정하고 관리할 수 있을까?

#3동작 예시

유지보수성은 "변수 이름이 명확한가", "함수가 한 가지 일만 하는가", "중복 코드가 없는가" 같은 코드 품질 지표들의 합이다. 기술 부채는 이런 정리를 미루면 나중에 갚아야 할 이자처럼 누적된다. 지금 버그 수정에 2시간이 걸리는데, 기술 부채가 크면 같은 버그를 나중에 고치려면 5시간이 걸릴 수 있다.

#4동작 과정

  1. 유지보수성 평가코드의 복잡도, 가독성, 테스트 커버리지, 문서화 수준을 측정해서 "현재 이 코드를 고치기가 얼마나 쉬운가"를 수치화한다.
  2. 기술 부채 인식빠르게 짠 코드나 문제 있는 구조를 기술 부채(기술 대출금)로 명시하고, 팀이 그 비용을 인식하도록 한다.
  3. 계획적 상환각 개발 사이클(스프린트)에서 새 기능만 아니라 기술 부채 상환(리팩토링, 테스트 추가)에 시간을 할당해서 장기적으로 개발 속도를 유지한다.

#1문제 상황

코드를 짜면 끝이라고 생각하기 쉽다. 하지만 인간이 코드를 작성하는 과정에서 실수를 하고, 그 실수가 코드에 결함으로 남는다. 개발자가 의도와 다르게 코드를 짰거나, 엣지 케이스를 고려하지 못했거나, 다른 코드와의 상호작용을 제대로 계산하지 못한 경우가 있다. 이런 결함을 발견하지 못하면 사용자가 실행했을 때 실패(오류 메시지, 예상치 못한 동작)가 터진다.

#2핵심 질문

인간의 실수가 코드에 결함으로 남는 것을 어떻게 조기에 발견할 것인가?

#3동작 예시

테스트는 의도적으로 코드를 실행하거나 검사해서 "예상한 대로 동작하는가"를 확인하는 활동이다. 예를 들어, 두 수를 더하는 함수를 짰다면 2 + 3 = 5를 테스트한다. 만약 2 + 3 = 6이 나오면 "이 코드에 결함이 있다"는 품질 정보를 얻는다.

#4동작 과정

  1. 오류(Error) 발생개발자가 의도와 다르게 코드를 작성한다(논리 실수, 예외 케이스 무시).
  2. 결함(Defect) 고착그 오류가 코드에 남아 있다(테스트되지 않은 경로, 미처리된 입력).
  3. 테스트로 드러남일정한 입력값에 대해 테스트를 돌리면 예상 결과와 다른 실패(Failure)가 나타난다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 코드 리뷰다른 개발자가 짠 코드를 읽고, 논리 오류, 스타일 위반, 보안 문제를 지적한다(사람의 경험과 지식을 활용).

#2핵심 질문

복잡한 소프트웨어를 어디서부터 검증하고, 어느 범위까지 테스트할 것인가?

#3동작 예시

테스트 레벨은 작은 부분부터 전체까지 단계를 나눠서 검증하는 구조다. 작은 함수부터 시작해서, 함수들의 조합, 전체 시스템, 실제 사용자의 업무 흐름 순서로 검증하면, 각 단계에서 결함을 빠르게 좁혀 찾을 수 있다.

#4동작 과정

  1. 단위 테스트(Unit Test)함수나 클래스 하나를 고립된 환경에서 테스트한다(의존 부분을 가짜로 대체). 가장 빠르고 좁은 범위.
  2. 통합 테스트(Integration Test)여러 모듈이나 컴포넌트를 함께 연결해서 테스트한다(데이터베이스, API 호출 포함). 모듈 간 상호작용을 검증.

동등 분할·경계값·결정표 같은 규칙으로 적은 테스트 케이스로 넓은 범위를 덮는 방법.

#1문제 상황

가능한 모든 입력값에 대해 테스트하려고 하면 무한하다. 예를 들어, 정수를 입력받는 함수면 -무한대부터 +무한대까지 다 테스트할 수는 없다. 만약 전화번호 입력을 테스트한다면, 올바른 번호 형식, 너무 짧은 번호, 너무 긴 번호, 특수문자가 섞인 번호 등 모든 케이스를 일일이 테스트하기에는 시간이 너무 오래 걸린다. 그래서 많은 경우를 최소한의 테스트 케이스로 커버하는 기법이 필요하다.

#2핵심 질문

한정된 테스트 케이스로 최대한 많은 오류를 찾을 수 있는 기법이 있을까?

#3동작 예시

테스트 설계 기법은 입력값의 범위를 그룹으로 나눠서 각 그룹에서 하나씩만 테스트하거나, 경계값(가장 극단적인 값)을 집중적으로 테스트한다. 예를 들어, 나이 입력(0~150)을 테스트하면 -1(범위 밖), 0(최소), 150(최대), 151(범위 밖)만 테스트해도 대부분의 오류를 잡을 수 있다.

#4동작 과정

  1. 동등 분할(Equivalence Partitioning)입력값을 그룹으로 나눈다(유효한 범위, 범위 이하, 범위 초과). 각 그룹에서 대표값 하나씩만 테스트한다.
  2. 경계값 분석(Boundary Value Analysis)각 그룹의 경계에 있는 값들(최소값, 최대값, 최소값-1, 최대값+1)을 테스트한다(경계에서 많은 오류가 발생하기 때문).
  3. 결정표(Decision Table)여러 조건의 조합에 따른 결과를 표로 정리하고, 모든 조합을 테스트한다(조건이 여러 개일 때 효과적).

#4동작 과정

지속적 인도(CD)와 지속적 배포의 차이

지속적 인도는 언제든 배포 가능한 상태까지 자동화하고 마지막 배포만 사람이 승인하는 것이고, 지속적 배포는 그 마지막 단계까지 자동으로 운영에 내보내는 것이다.

#1문제 상황

기존에는 개발자들이 몇 주 또는 몇 달 동안 코드를 쌓아두었다가, 수동으로 각종 테스트를 거쳐 마지막에 한 번에 배포했습니다. 배포 전 확인해야 할 것이 많았고, 배포 때마다 장시간 중단이 필요했으며, 문제가 생기면 원인 파악과 롤백(되돌리기)이 복잡했습니다.

#2핵심 질문

코드 변경을 자동으로 검증해서 언제든 배포 가능한 상태로 준비하되, 실제 배포의 시점과 승인 권한은 어떻게 나눠야 할까요?

#3동작 예시

개발자가 커밋하면 자동으로 빌드·테스트·보안 검사를 모두 통과한 후 "배포 준비됨" 상태가 됩니다. 지속적 인도(Continuous Delivery)는 여기까지만 자동화하고, 마지막 "배포 버튼"은 담당자가 수동으로 누릅니다. 지속적 배포(Continuous Deployment)는 그 버튼까지도 자동으로 누르는 것입니다.

#4동작 과정

  1. 코드 변경과 자동 검증개발자가 커밋하면 CI 파이프라인이 자동으로 빌드, 단위 테스트, 통합 테스트, 보안 검사를 수행합니다.
  2. 배포 준비 상태 도달모든 자동 검증을 통과한 산출물은 "배포 가능"으로 표시되고, 지속적 인도는 여기서 멈춥니다.
  3. 배포 실행지속적 배포는 자동화된 승인 규칙(예: 모든 테스트 통과, 보안 검사 통과)을 만족하면 운영 환경에 자동 배포합니다.

#5한 줄 요약

자동화된 검증을 통해 배포 준비 상태까지는 기계적으로 처리하되, 지속적 인도는 마지막 승인은 사람이 하고 지속적 배포는 규칙에 따라 자동 배포하는 차이

기존에는 운영 중인 앱을 중단하고 새 버전으로 교체했습니다. 교체 중에는 사용자가 서비스를 쓸 수 없었고, 새 버전에 버그가 있으면 모든 사용자가 한 번에 영향을 받았습니다. 문제를 발견했을 때 이전 버전으로 돌리려면 전체 앱을 다시 교체해야 했습니다.

#2핵심 질문

새 버전으로의 전환 중에 서비스를 중단하지 않으면서, 문제 발생 시 빠르게 대응하고 영향 범위를 제한하려면 어떻게 해야 할까요?

#3동작 예시

블루/그린 전략: 구 버전(파란색)이 실제 트래픽을 처리하고, 새 버전(초록색)을 별도로 준비해 검증한 뒤 트래픽 분기점(로드 밸런서)에서 한 번에 새 버전으로 모든 요청을 돌림. 롤링 전략: 5개 서버가 있으면 1개씩 순서대로 교체해서 항상 나머지 4개 서버가 서비스 중. 카나리 전략: 새 버전을 5% 사용자에게만 보내서 오류가 없으면 10%, 50%, 100%로 늘림.

#4동작 과정

  1. 블루/그린운영 중인 구 버전(블루) 외에 새 버전(그린)을 동일한 규모로 별도 환경에 준비하고, 모든 검증을 통과하면 로드 밸런서(들어오는 요청을 나누는 역할)의 라우팅 규칙(어디로 보낼지 정하는 규칙)을 한 번에 그린으로 전환합니다.
  2. 롤링 배포여러 서버 중 일부만 교체해 항상 일부 서버는 구 버전으로 서비스하고, 교체된 서버에 문제가 없으면 나머지 서버를 순차적으로 교체합니다.
  3. 카나리 배포모든 사용자가 아니라 선택된 소수 사용자 그룹이나 전체 트래픽의 일부만 새 버전으로 보내 초기 단계에서 문제를 발견합니다.

#5한 줄 요약

새 버전으로의 전환을 여러 방식으로 나눠서 한 번에 배포되는 위험을 줄이고, 문제 발생 시 즉시 이전 버전으로 돌릴 수 있도록 하는 것

#1문제 상황

기존에는 서버를 할당받으면 담당자가 수동으로 OS를 설치하고, 필요한 패키지를 하나하나 설치하고, 방화벽 규칙을 설정했습니다. 서버마다 설정이 다를 수 있었고, 설정을 변경하면 다른 서버는 누락될 수 있었습니다. 장애 발생 후 서버를 새로 만들어야 할 때, 처음부터 수동으로 다시 설정해야 했습니다.

#2핵심 질문

서버, 네트워크, 보안 설정 같은 인프라를 코드로 정의해서 버전 관리하고 자동 반복하려면 어떻게 해야 할까요?

#3동작 예시

Terraform이나 CloudFormation 같은 도구에서 "AWS EC2 인스턴스 3개, 각 8GB 메모리, Ubuntu 22.04, Python 3.10 설치, 포트 8080 개방"을 코드로 작성하면, 그 코드 한 줄을 실행해서 모든 설정이 동일하게 자동 적용됩니다. 설정을 코드로 저장하면 Git에서 버전 관리하고, 같은 코드를 언제든 반복 실행해서 동일한 인프라를 재현할 수 있습니다.

#4동작 과정

  1. 인프라를 코드로 작성필요한 서버, 네트워크, 보안 규칙, 스토리지 등을 선언적 형식으로 정의합니다(예: "3개의 t3.large 인스턴스").
  2. 코드 검토 및 승인다른 팀원이 인프라 변경 코드를 검토하고 승인합니다(일반 코드 리뷰와 동일).
  3. 자동 배포 및 재현CI/CD 파이프라인이 코드를 읽어 인프라 도구(Terraform, Ansible)로 자동 실행하고, 같은 코드는 언제든 동일한 결과를 만듭니다.

컨테이너와 오케스트레이션이 배포에 주는 영향

앱과 실행 환경을 이미지 하나로 묶어 어디서나 같게 돌리고, 오케스트레이터가 배치·확장·교체를 대신 관리해 배포를 표준화한다.

#1문제 상황

기존에는 앱과 그 앱이 필요한 실행 환경(Python 3.9, Node.js 18, 라이브러리 버전들)을 서버에 수동으로 설치했습니다. 개발자 로컬 환경과 운영 서버의 환경이 미묘하게 달라서 "내 컴퓨터에서는 잘 되는데 운영에서 왜 안 되지?"가 발생했습니다. 새 서버를 추가할 때마다 환경 셋업(초기 설정)에 시간이 걸렸습니다.

#2핵심 질문

앱과 그것이 필요한 모든 실행 환경을 하나의 패키지로 묶어서, 어느 서버에서나 동일하게 동작하게 하면서 자동 배치(배치: 여러 서버에 분산)와 확장을 어떻게 할까요?

#3동작 예시

Docker 이미지는 앱 코드 + Python 3.10 + 필요한 모든 라이브러리 + 설정 파일을 한 파일로 묶습니다. 이 이미지를 어느 서버에서나 실행하면(docker run), 환경에 상관없이 동일한 컨테이너(경량 가상 환경)가 구동됩니다. Kubernetes 같은 오케스트레이터는 "이 앱의 복사본 5개를 여러 서버에 분산 실행하고, CPU가 높으면 10개로 자동 증가"라는 명령 하나로 전부 관리합니다.

#4동작 과정

  1. 컨테이너 이미지 생성Dockerfile에 앱, 언어, 라이브러리를 정의하고 빌드해서 하나의 불변(절대 바뀌지 않는) 이미지를 만듭니다.
  2. 오케스트레이터에 배포Kubernetes에 "이 이미지 5개 복사본을 실행하고, 메모리 부족하면 10개로 늘려"라고 선언하면, 오케스트레이터가 자동으로 배치하고 실행합니다.
  3. 자동 관리오케스트레이터는 장애난 컨테이너를 자동 재시작하고, 트래픽에 따라 복사본 개수를 자동 조절하며, 새 이미지 배포 시 기존 것을 점진적으로 교체합니다(무중단 배포).

롤백·기능 플래그·안전한 배포 관행

문제가 생기면 이전 버전으로 되돌리거나 코드 배포와 기능 공개를 분리하는 스위치를 두어, 사고 영향을 빠르게 줄이는 관행이다.

#1문제 상황

기존에 새로운 코드를 배포하면 그 순간부터 모든 사용자가 즉시 새 버전을 사용합니다. 만약 배포 직후에 심각한 버그를 발견했다면, 버그를 고쳐서 다시 배포할 때까지 모든 사용자가 그 문제를 겪어야 합니다. 코드를 이전 버전으로 되돌릴 때도 수동으로 과거 코드를 찾아 배포해야 하고, 새로운 기능을 일부 사용자에게만 먼저 테스트하려면 특별한 방법이 없습니다.

#2핵심 질문

배포 후 문제가 생겼을 때 빠르게 피해를 줄이고, 새 기능을 안전하게 일부부터 공개하려면 어떻게 해야 할까요?

#3동작 예시

배포와 기능 공개를 분리합니다. 코드는 배포되지만, 코드 안의 스위치(기능 플래그)로 그 기능을 켜고 끌 수 있습니다. 예를 들어 결제 시스템을 개선한 코드를 배포한 후, 처음에는 결제 플래그를 '켜지 않은' 상태로 두어 아무도 새 결제 코드를 사용하지 않습니다. 테스트 사용자 1%에게만 플래그를 켜서 돌려본 뒤, 문제가 없으면 조금씩 비율을 높입니다. 문제가 발견되면 플래그를 끄는 것만으로 즉시 모든 사용자를 이전 코드로 되돌릴 수 있습니다.

#4동작 과정

  1. 롤백 준비이전 버전의 코드와 데이터를 항상 접근 가능하게 유지하고, 어떤 버전이 현재 운영 중인지 추적합니다.
  2. 기능 플래그로 점진적 공개새 코드는 배포되지만, 플래그를 끄면 그 코드 경로가 실행되지 않습니다. 플래그 값을 설정 파일이나 데이터베이스에서 읽어 실시간으로 기능을 켜거나 끕니다.
  3. 문제 발생 시 빠른 대응플래그를 끄거나(기능 끄기) 이전 버전으로 되돌리기(롤백)를 선택해 몇 초 내에 영향을 최소화합니다.

#5한 줄 요약

배포(코드 서버 반영)와 공개(사용자가 사용하는 기능)를 분리해 문제 발생 시 빠르게 대응하고 새로운 기능을 안전하게 일부부터 시작할 수 있도록 하는 것

#1문제 상황

개발 팀이 소프트웨어를 만들어 배포하면 그것이 끝이 아닙니다. 실제 사용자가 사용하는 시스템은 24시간 365일 돌아가야 하고, 서버 자원 부족, 보안 업데이트, 성능 저하, 갑작스러운 장애 등 예상 못 한 일들이 계속 생깁니다. 배포된 소프트웨어를 그대로 두면 시간이 지날수록 문제가 쌓여 결국 사용 불가능해질 수 있습니다.

#2핵심 질문

배포된 소프트웨어를 실제 사용자 환경에서 안정적으로 계속 작동시키려면 누가 무엇을 해야 할까요?

#3동작 예시

운영 팀(또는 DevOps 팀)은 배포된 소프트웨어를 감시하고 유지하는 역할을 합니다. 매일 로그를 확인해 이상 신호가 없는지 살펴보고, 필요하면 서버 용량을 늘리고, 보안 패치를 적용하고, 새로운 배포 요청을 처리합니다. 릴리스 엔지니어링은 이 모든 배포를 자동화하고 추적 가능하게 만들어, 누구든 같은 방식으로 배포할 수 있고 문제가 생기면 이전 버전으로 돌릴 수 있게 하는 일입니다.

#4동작 과정

  1. 지속적 감시운영 팀이 시스템의 상태(CPU 사용률, 메모리, 응답 시간 등)를 계속 확인해 이상을 조기에 발견합니다.
  2. 배포 자동화릴리스 엔지니어가 배포 과정(코드를 받아 테스트 후 서버에 올리기)을 스크립트로 만들어 자동으로 진행하게 하고, 누가 언제 무엇을 배포했는지 기록합니다.
  3. 장애 대응 및 회복문제가 발생하면 운영 팀이 빠르게 알림을 받고, 롤백하거나 핫픽스(긴급 수정)를 배포해 서비스를 복구합니다.

시스템이 밖으로 내보내는 로그·메트릭·트레이스를 코드에 심어(계측) 내부에서 무슨 일이 벌어지는지 밖에서 알아낼 수 있게 하는 능력이다.

#1문제 상황

소프트웨어가 서버에서 작동할 때, 개발자나 운영팀은 시스템 내부에서 무슨 일이 일어나는지 직접 볼 수 없습니다. 사용자가 "뭔가 느려요"라고 하거나 에러가 발생했다는 신고를 받아야만 문제를 알 수 있습니다. 문제를 찾기 위해 코드를 켜놓고 하나하나 추적해볼 수도 없습니다.

#2핵심 질문

서버에서 돌아가는 시스템이 내부적으로 어떻게 작동하고 있는지, 밖에서 알 수 있을까요?

#3동작 예시

코드 곳곳에 관찰 가능한 정보를 내보내는 명령어(계측)를 심습니다. 결제 처리 함수는 "결제 시작됨", "데이터베이스 조회 중", "결제 완료" 같은 메시지를 순차적으로 출력합니다. 또한 결제에 걸린 시간(메트릭)도 기록합니다. 이 정보들이 로그 파일이나 데이터베이스로 흘러가서, 운영팀이 나중에 분석할 수 있습니다. 로그는 무슨 일이 일어났는지(텍스트), 메트릭은 얼마나 오래 걸렸는지(숫자), 트레이스는 요청이 여러 서비스를 거쳐 어떻게 처리되었는지(경로) 보여줍니다.

#4동작 과정

  1. 계측(코드에 정보 삽입)개발자가 코드에 로그 출력, 시간 측정, 이벤트 기록 같은 명령어를 미리 심어놓습니다.
  2. 데이터 수집소프트웨어가 실행될 때 이 정보들이 로그 파일, 메트릭 수집 시스템, 분산 추적 시스템(트레이싱 시스템)으로 전송됩니다.
  3. 분석 및 시각화운영팀이 수집된 로그, 메트릭, 트레이스를 대시보드(화면)에서 보거나 검색해 문제의 원인을 찾습니다.

#5한 줄 요약

시스템이 내보내는 로그, 메트릭, 트레이스 데이터를 코드에 심어 내부 작동을 밖에서 볼 수 있게 만드는 것

알림과 온콜

정해둔 조건이 깨지면 사람에게 자동으로 연락하고, 당번(온콜)이 교대로 그 연락을 받아 대응하는 체계다.

#1문제 상황

시스템이 24시간 돌아가는데, 운영팀이 매초 모니터링 화면을 들여다보고 있을 수 없습니다. 특히 밤이나 휴일에 장애가 생기면 누가 알 수 있을까요? 문제가 생겨도 몇 시간 뒤에야 발견되어 그 사이 사용자들이 피해를 입을 수 있습니다.

#2핵심 질문

시스템에 문제가 생기면 자동으로 담당자에게 연락해 빠르게 대응하려면 어떻게 해야 할까요?

#3동작 예시

미리 정한 조건(예: CPU 사용률이 90% 이상 5분 지속, 응답 시간이 2초 초과 등)을 모니터링 시스템이 계속 확인합니다. 그 조건이 깨지면 자동으로 담당자의 휴대폰, 이메일, 메신저에 알림을 보냅니다. 당번 제도(온콜)를 통해 특정 시간대마다 담당자를 정해, 그 시간에 알림이 오면 그 담당자가 대응합니다.

#4동작 과정

  1. 임계값 설정운영팀이 "어떤 상황이면 문제인가"를 정합니다. (CPU 90%, 에러율 5%, 응답 시간 2초 등)
  2. 조건 감시 및 알림 발송모니터링 시스템이 메트릭을 계속 확인해 임계값을 초과하면 즉시 알림을 보냅니다.
  3. 온콜 당번이 대응정해진 담당자가 알림을 받고 상황을 파악해 문제를 해결하거나 에스컬레이션(상급자에게 보고)합니다.

#5한 줄 요약

시스템 상태의 이상을 자동으로 감지해 담당자에게 즉시 알리고, 당번 제도로 지속적인 대응 체계를 유지하는 것

SLI·SLO·에러 예산

서비스 품질을 숫자로 재는 지표(SLI)와 지켜야 할 목표치(SLO), 그리고 목표를 어겨도 되는 남은 여유분(에러 예산)이다.

#1문제 상황

소프트웨어는 완벽하지 않으므로 가끔 장애가 생깁니다. 팀에서 "서비스를 99% 안정적으로 유지해야 한다"고 말해도, 그것이 무엇을 의미하는지, 어떻게 측정하는지, 누가 책임지는지 명확하지 않습니다. 또한 "안정성을 높이려면 배포를 자주 할 수 없다"고 가정하는 경우가 많지만, 실제로는 그 반대일 수 있습니다.

#2핵심 질문

서비스 품질을 숫자로 정확히 측정하고, 그 목표를 지키면서도 개발 속도를 유지하려면 어떻게 해야 할까요?

#3동작 예시

은행 서비스가 "99.9% 가용성(서비스가 정상 작동하는 시간 비율)"을 목표로 정합니다. 이를 SLO(Service Level Objective)라 합니다. 실제로 측정되는 가용성(예: 99.95%)을 SLI(Service Level Indicator)라 합니다. 목표 99.9%에서 실제 99.95%라면, 0.05% 남은 여유분을 에러 예산(error budget)이라 합니다. 팀은 이 남은 여유분을 써서 자유롭게 배포, 실험, 성능 개선을 할 수 있습니다. 에러 예산을 다 쓰기 전까지는 "우리가 안정성 목표를 지키고 있다"는 뜻입니다.

#4동작 과정

  1. SLI 정의 및 측정"가용성(작동 시간 비율)"이나 "에러율"처럼 서비스 품질을 숫자로 나타낼 수 있는 지표를 정하고, 매 시간 또는 매일 계산합니다.
  2. SLO 설정SLI의 목표값을 정합니다. (예: 99.9% 가용성, 에러율 1% 이하)
  3. 에러 예산으로 우선순위 결정남은 여유분(에러 예산)을 계산해, 그 범위 내에서 배포 빈도, 기능 개발 속도, 위험한 실험을 결정합니다.

#5한 줄 요약

서비스 품질을 숫자(SLI)로 측정하고 목표(SLO)를 정한 뒤, 그 목표를 어겨도 되는 남은 여유(에러 예산)를 배포 속도와 안정성의 균형을 맞추는 도구로 사용하는 것

사건 대응과 사건 관리

장애가 났을 때 감지·분류·복구·소통을 정해진 역할과 절차로 진행해 서비스를 가장 빨리 되돌리는 활동이다.

#1문제 상황

시스템에 장애가 나면 여러 사람이 동시에 대응하려 들어 혼란이 생깁니다. 누가 무엇을 하는지 불명확하고, 같은 작업을 중복으로 하거나 중요한 부분을 놓치기도 합니다. 또한 사용자에게 상황을 알릴 담당자, 기술 문제를 해결할 담당자, 경영진에게 보고할 담당자가 정해져 있지 않아 시간을 낭비합니다.

#2핵심 질문

시스템 장애가 났을 때 역할을 나누고 정해진 절차를 따르면, 더 빠르게 서비스를 복구할 수 있지 않을까요?

#3동작 예시

장애 감지 후 사건 관리팀이 온콜에게 연락합니다. 사건 지휘관(incident commander)이 전체 상황을 통제하고, 기술팀은 원인 파악과 복구에 집중합니다. 커뮤니케이션팀은 고객에게 상황을 알립니다. 각자 명확한 역할이 있어 중복 없이 병렬로 작업 가능하고, 사건 지휘관은 5분마다 상태를 모두에게 알립니다.

#4동작 과정

  1. 감지 및 분류모니터링 시스템이나 사용자 신고를 통해 장애를 인식하고, 심각도를 판단합니다. (심각하면 P1, 보통이면 P2 등)
  2. 역할 분담 및 대응사건 지휘관, 기술팀, 소통팀 등 역할을 나누고, 각각 원인 파악, 복구, 고객 안내를 동시에 진행합니다.
  3. 복구 및 종료서비스가 정상화되면 사건을 종료하고, 장애 발생 시간, 영향받은 사용자 수, 해결 시간을 기록합니다.

#5한 줄 요약

장애 발생 시 역할을 명확히 나누고 정해진 절차를 따라 빠르게 대응해 서비스 복구 시간을 최소화하는 것

포스트모템과 비난 없는 학습

장애가 끝난 뒤 사람 탓 대신 시스템과 절차의 원인을 기록·공유해 같은 일이 반복되지 않게 만드는 회고다.

#1문제 상황

장애가 끝나면 "누가 실수했는가"를 찾아 책임을 묻는 경우가 많습니다. 이런 관행 아래에서는 사람들이 실수를 숨기거나 과장되게 보고하고, 진짜 원인이 무엇인지 솔직하게 이야기하지 않습니다. 결과적으로 같은 장애가 반복되고, 팀은 신뢰가 무너져 속도도 느려집니다.

#2핵심 질문

장애의 진짜 원인을 솔직하게 찾고, 다시는 같은 일이 일어나지 않게 하려면 어떻게 해야 할까요?

#3동작 예시

"배포 자동화 검사가 누락되어 테스트되지 않은 코드가 배포되었다"는 기술적 원인을 찾습니다. "엔지니어가 한때 잠깐 실수했다"처럼 개인을 탓하지 않습니다. 대신 "검사 과정을 자동화하지 않았던 시스템 설계의 문제", "당시 피로도가 높았던 근무 환경", "코드 리뷰 문화가 약했던 조직 구조" 같은 시스템과 절차의 원인을 기록합니다. 그 원인들을 공유하면 팀 전체가 배우고, 개선 방안을 함께 정합니다.

#4동작 과정

  1. 사건 재검토장애가 완전히 복구된 후 1~2주 뒤, 타임라인(시간 흐름)과 각 단계별 조치를 정확히 기록합니다.
  2. 근본 원인 분석"왜 이 상황이 발생했는가"를 5단계 why로 파고들어 기술·절차·조직 차원의 원인을 찾습니다. 개인을 탓하지 않습니다.
  3. 개선 방안 도출 및 공유원인을 바탕으로 코드 검사 자동화, 매뉴얼 개선, 배포 절차 강화 같은 구체적 개선책을 정하고, 팀 전체와 공유해 같은 장애가 반복되지 않게 합니다.

#5한 줄 요약

장애 후 개인 책임 추궁 대신 시스템과 절차의 원인을 찾아 기록·공유함으로써, 같은 실수를 막고 팀의 신뢰와 학습 문화를 구축하는 것

유지보수 유형과 폐기

운영 중 소프트웨어를 고치고(수정) 맞추고(적응) 개선하고(완전화) 예방하는 네 가지 유지보수와, 수명이 다한 제품을 계획적으로 내리는 폐기 단계다.

#1문제 상황

소프트웨어를 한 번 출시하면 끝이 아닙니다. 출시 후에도 버그가 발견되고, 새로운 운영환경에 맞춰야 하며, 사용자 요청에 따라 기능을 더해야 합니다. 기존에는 이 모든 것을 필요할 때마다 급하게 처리했고, 계획 없이 자잘한 수정이 쌓이다 보니 코드가 복잡해지고 안정성이 떨어지는 문제가 발생했습니다.

#2핵심 질문

운영 중인 소프트웨어를 언제까지 유지해야 하고, 어떤 종류의 수정과 개선을 체계적으로 관리할 것인가?

#3동작 예시

자동차를 사고 난 후 일상적으로 하는 일들을 생각해보면, 엔진 오류를 수리하는 것(버그 수정), 새 배출가스 규제에 맞춰 배기장치를 바꾸는 것(적응), 연비를 더 좋게 개선하는 것(완전화), 주기적으로 오일을 갈고 부품을 점검하는 것(예방)처럼 운영 중인 소프트웨어도 네 가지 유지보수를 구분해서 합니다.

#4동작 과정

  1. 수정 유지보수(Corrective)발견된 버그(결함)를 고쳐 정상 작동하도록 복원하는 활동입니다.

기존에는 소프트웨어 개발 과정을 거쳐 완성되면 출시 직전에 보안팀이 취약점을 점검했습니다. 하지만 이 시점에는 이미 코드가 완성되어 있어서, 보안 문제를 발견해도 고치는 데 시간이 오래 걸리고 비용이 많이 들며, 출시 일정에 영향을 미칩니다. 결국 보안을 완전히 해결하지 못하고 출시하는 경우도 발생했습니다.

#2핵심 질문

보안 문제를 가장 빨리, 가장 저렴하게 발견하고 고칠 수 있는 시점은 언제인가?

#3동작 예시

건설 프로젝트에서 건물을 다 지은 후 안전 점검을 하는 것보다, 설계 단계·기초 단계·공사 단계마다 안전 기준을 확인하는 것이 효율적입니다. 소프트웨어도 마찬가지로 요구사항을 정할 때부터, 설계할 때, 코드를 쓸 때, 테스트할 때마다 보안을 지속적으로 점검합니다.

#4동작 과정

  1. 시프트 레프트(Shift Left)개발 생명주기 왼쪽(초반 단계)으로 보안 활동을 앞당기는 접근입니다. 원래는 출시 직전에 한 번 점검하던 것을 요구사항부터 시작해 지속적으로 반복합니다.
  2. 각 단계별 보안 활동요구사항 단계에서는 보안 필요조건을 정하고, 설계 단계에서는 위협을 분석하고, 개발 단계에서는 안전한 코딩을 하고, 테스트 단계에서는 자동화된 보안 도구로 점검합니다.
  3. 피드백 루프발견된 문제가 즉시 이전 단계로 돌아가서 원인을 없애고, 같은 실수가 반복되지 않도록 프로세스 자체를 개선합니다.

NIST SSDF의 네 그룹

NIST SP 800-218 SSDF v1.1 은 안전한 개발 관행을 조직 준비(PO)·소프트웨어 보호(PS)·안전한 소프트웨어 생산(PW)·취약점 대응(RV) 네 그룹으로 정리한 틀이다.

#1문제 상황

회사마다 보안을 다르게 관리했기 때문에, 뭐가 정말 중요한 관행인지 공통 기준이 없었습니다. 미국 정부는 공급업체에서 납품하는 소프트웨어의 보안 수준을 일관되게 평가하기 위해 NIST라는 표준 기관을 통해 안전한 개발 관행의 틀을 정했습니다.

#2핵심 질문

조직이 지켜야 할 기본적인 보안 개발 관행을 어떻게 체계적으로 정리하고 평가할 것인가?

#3동작 예시

NIST SSDF v1.1(Secure Software Development Framework)은 안전한 소프트웨어 개발 관행 14개를 네 개의 그룹으로 묶어서 제시합니다. 각 그룹은 조직이 보안을 관리하는 방식의 다른 측면을 담당합니다.

#4동작 과정

  1. 조직 준비(PO, Prepare Organization)보안 정책·역할·책임을 정하고, 보안 교육을 제공하고, 보안 기준을 문서화합니다.
  2. 소프트웨어 보호(PS, Protect Software)접근 제어, 암호화, 취약한 의존성 관리 등으로 소프트웨어와 그 부품을 보호하는 활동입니다. 안전한 소프트웨어 생산(PW, Produce Well-Secured Software)은 코드를 안전하게 작성하고, 보안 테스트를 자동화하고, 결함을 추적 관리하는 개발 프로세스입니다.
  3. 취약점 대응(RV, Respond to Vulnerabilities)발견된 보안 결함을 신속하게 분류하고, 패치를 만들고, 사용자에게 알리고, 수정 여부를 확인합니다.

#5한 줄 요약

안전한 소프트웨어 개발의 모든 측면(조직·보호·개발·대응)을 네 그룹으로 정리해서 조직이 체크리스트처럼 점검할 수 있는 공통 기준을 제공하는 것

→ 03-02 참조

#1문제 상황

기존에는 기능 요구사항만 정해놓고 개발을 시작했기 때문에, "고객 정보는 암호화돼야 한다" 같은 보안 조건을 개발 도중에 갑자기 추가해야 했습니다. 이미 지어진 건물에 보안카메라를 달려고 하니 공사가 필요한 것처럼, 개발이 진행된 후에 보안 요구사항을 추가하면 재작업이 많아집니다.

#2핵심 질문

소프트웨어가 지켜야 할 보안 조건을 개발이 시작되기 전에 어떻게 정할 것인가?

#3동작 예시

온라인 쇼핑몰을 만든다면 요구사항은 "상품 검색 기능", "결제 기능" 같은 기능 요구사항만이 아니라 "결제 정보는 국제 표준에 따라 암호화", "고객 데이터에 접근하는 직원은 보안 교육을 받아야 함" 같은 보안 요구사항도 함께 정해야 합니다.

#4동작 과정

  1. 보안 요구사항 정의보호해야 할 자산(데이터, 기능, 성능)과 보호 수준을 명시합니다. "고객 신용카드 정보는 AES-256 암호화로 보호"처럼 구체적으로 적습니다.
  2. 위협 모델링공격자 관점에서 소프트웨어를 어떻게 악의적으로 이용할 수 있는지 그려봅니다. 사용자 입력값이 제대로 검증되지 않으면 SQL 주입 공격이 가능한지, 통신이 암호화되지 않으면 중간 도청이 가능한지 같은 위협을 찾아냅니다.
  3. 대응책 설계각 위협에 대해 미리 어떻게 방어할 것인지 설계에 반영합니다. 입력값 검증 함수, 안전한 암호화 라이브러리 등을 선택합니다.

안전한 설계·암호 표준·검증된 프레임워크

최소 권한·기본 안전 같은 설계 원칙을 따르고, 암호와 인증은 직접 만들지 말고 검증된 표준 라이브러리와 프레임워크를 쓰는 것이다.

#1문제 상황

개발자가 보안을 처음 생각하면 보안 기능을 직접 만들려고 합니다. 암호화 알고리즘을 직접 구현하거나 인증 로직을 처음부터 짜는 것입니다. 하지만 보안은 한 군데 실수하면 전체가 무너지는 분야라서, 검증되지 않은 코드는 숨겨진 취약점을 많이 가집니다. 또한 설계 단계에서 최소 권한 원칙을 무시하고 과도한 권한을 부여하면 나중에 고치기 어렵습니다.

#2핵심 질문

안전한 소프트웨어를 만들기 위해 개발자가 스스로 구현해야 할 것과 기존 표준을 쓰면 되는 것을 어떻게 나눌 것인가?

#3동작 예시

자동차에서 제동 시스템을 자동차 제조업체가 스스로 설계하고 재료를 고르듯이, 암호화·인증 같은 보안 핵심 기능도 검증된 표준 라이브러리를 사용하고, 설계 원칙(최소 권한, 기본 안전)을 따릅니다.

#4동작 과정

  1. 설계 원칙 적용최소 권한(Least Privilege, 사용자에게 필요한 권한만 부여) 원칙에 따라 기본적으로 모든 접근을 막고 필요한 것만 열어줍니다. 관리자 계정으로 모든 작업을 처리하지 않습니다.
  2. 암호와 인증은 직접 만들지 않기OpenSSL, bcrypt 같은 검증된 암호화 라이브러리를 쓰고, 인증은 OAuth 2.0 같은 표준 프로토콜을 쓰며, JSON Web Token(JWT)은 검증된 구현체를 사용합니다.
  3. 보안 프레임워크 사용OWASP 같은 커뮤니티가 정한 검증된 웹 프레임워크를 기반으로 개발하면 많은 보안 문제를 미리 방지할 수 있습니다.

코드 정적 분석(SAST)·실행 중 취약점 점검(DAST)·오픈소스 의존성 검사를 파이프라인에 넣고, OWASP ASVS 5.0.0 을 검증 기준표로 삼는 것이다.

#1문제 상황

기존에는 보안 테스트를 사람이 수동으로 하거나 출시 직전에 외부 보안팀이 점검했습니다. 사람이 놓치는 취약점이 많고, 발견된 문제를 고치려면 재배포까지 시간이 오래 걸렸습니다. 또한 오픈소스 라이브러리에 알려진 취약점이 있어도 개발자가 모르는 채로 사용했습니다.

#2핵심 질문

개발 파이프라인의 매 단계에서 코드의 보안 문제를 자동으로 찾아낼 수 있는 방법은 무엇인가?

#3동작 예시

코드를 짜고 나면 단위 테스트로 기능을 점검하듯이, 보안도 자동화된 도구로 세 가지 각도에서 계속 점검합니다. 코드를 정적으로 읽어서 취약점을 찾고(SAST), 실제로 실행해서 공격을 시뮬레이션하고(DAST), 쓰는 오픈소스 부품의 알려진 결함을 체크합니다(의존성 검사).

#4동작 과정

  1. SAST(Static Application Security Testing, 정적 분석) — 코드를 실행하지 않고 소스코드를 자동으로 분석해서 SQL 주입, 하드코딩된 비밀번호, 버퍼 오버플로우 같은 보안 결함을 찾습니다. 개발자가 커밋하면 즉시 실행되어 피드백이 빠릅니다.
  2. 의존성 검사와 DAST프로젝트에 포함된 오픈소스 라이브러리(의존성)가 알려진 취약점을 가지고 있지 않은지 확인합니다. 애플리케이션이 실제로 실행되는 상황에서 공격을 흉내내서(DAST, Dynamic Application Security Testing) 런타임 취약점을 발견합니다. 예를 들어 입력값을 조작해서 SQL 주입이 가능한지, CSRF 공격이 가능한지 테스트합니다.
  3. OWASP ASVS 검증Application Security Verification Standard 5.0.0 같은 검증 표준에 따라 소프트웨어가 최소한의 보안 조건을 만족하는지 체크리스트로 확인합니다.

소프트웨어 공급망 보안: SBOM·프로비넌스·SLSA

제품에 든 부품 목록(SBOM)과 빌드 출처 증명(프로비넌스)을 남겨, SLSA v1.0 단계에 따라 빌드 과정의 변조를 막는 것이다.

#1문제 상황

자동차를 사면 부품 목록과 어디서 왔는지 알 수 있지만, 소프트웨어는 어떤 오픈소스 라이브러리가 몇 버전으로 들어가 있는지, 그 부품들이 올바른 출처에서 온 것인지 확인할 수 없었습니다. 악의적인 개발자가 빌드 서버에 접근해서 코드를 몰래 변조하거나, 신뢰할 수 없는 출처의 부품이 섞여 들어가도 알 길이 없었습니다.

#2핵심 질문

소프트웨어에 무엇이 들어 있고, 그것이 진정 믿을 수 있는 출처에서 온 것임을 어떻게 증명할 수 있는가?

#3동작 예시

의약품 제조 회사는 원재료의 목록과 생산 과정의 기록을 남겨서, 누군가 제품을 변조하지 않았음을 증명합니다. 소프트웨어도 부품 목록(SBOM)과 빌드 과정의 증명서(프로비넌스)를 남겨서 공급망의 무결성을 보장합니다.

#4동작 과정

  1. SBOM(Software Bill of Materials) 작성최종 제품에 포함된 모든 오픈소스 라이브러리와 버전을 명시하는 문서입니다. 사용자나 보안팀이 의존성의 알려진 취약점을 확인할 때 필요합니다.
  2. 빌드 프로비넌스(Build Provenance) 기록누가, 언제, 어느 서버에서 빌드했는지, 어떤 소스코드 버전을 썼는지 암호화 서명과 함께 기록합니다. 이것으로 코드가 변조되지 않았음을 증명할 수 있습니다.
  3. SLSA v1.0 단계 준수SLSA(Supply Chain Levels for Software Artifacts)는 빌드 과정의 보안 수준을 4단계로 정의합니다. 낮은 단계(소스 코드 버전 관리)부터 높은 단계(암호 서명, 변경 추적, 격리된 빌드 환경)까지 점진적으로 강화하면서 공급망의 위협을 줄입니다.

#5한 줄 요약

최종 소프트웨어 제품에 든 모든 부품의 목록을 남기고 빌드 과정의 기록을 암호화 서명으로 증명해서, 공급망에서의 변조를 탐지할 수 있도록 하는 것

#1문제 상황

개발팀이 보안 취약점을 발견하거나 외부에서 신고받을 때 보통 아무 계획 없이 대응합니다. 발견되는 즉시 수정하거나 무시하거나 급하게 패치를 내보냅니다. 이렇게 하면 같은 문제가 반복되고, 얼마나 많은 취약점이 있는지, 얼마나 빨리 고쳤는지 기록이 남지 않습니다. 또한 개발 환경 자체(코드 저장소, 빌드 서버, 배포 계정의 비밀키, 개발자 도구)도 보호되지 않으면 악의적으로 악용될 여지가 생깁니다.

#2핵심 질문

신고된 보안 문제를 체계적으로 처리하고, 개발 환경 자체도 보호하려면?

#3동작 예시

누군가 "이 라이브러리의 인증 로직에 버그가 있다"고 신고 → 팀이 버그를 분석해 우선순위 정함 → 패치 코드 작성 후 테스트 → 배포 후 공개 → 다음 번에 같은 문제가 나오지 않도록 테스트 코드 추가.

#4동작 과정

  1. 신고 접수 및 분석외부에서 신고되거나 내부에서 발견한 취약점을 한 곳에서 모아 분석하고 진짜 위험한지, 얼마나 널리 영향을 미치는지 판단합니다.
  2. 수정 및 배포우선순위가 높은 것부터 패치를 만들고, 이미 배포된 서비스에도 그 패치를 빠르게 적용합니다.
  3. 환경 보호코드 저장소에 접근하는 계정, 빌드 서버의 비밀키, 개발자 개인 도구 등에 접근 권한을 제한하고 로그(누가 언제 접근했는지 기록)를 남깁니다.

DORA 4대 지표와 배포 성과

#2핵심 질문

#3동작 예시

팀 A는 한 달에 1번 배포, 팀 B는 하루에 10번 배포 → 같은 시간에 팀 B가 더 많이 배포했습니다. 또한 배포할 때마다 버그가 생기는지(변경 실패율), 버그가 생기면 얼마나 빨리 고치는지(복구 시간)도 함께 봅니다.

#4동작 과정

  1. 배포 빈도 측정일정 기간(보통 1주)에 프로덕션(실제 운영 서버)에 배포한 횟수를 센다.
  2. 변경 리드 타임 측정코드 작성 시작부터 프로덕션에 배포될 때까지 걸린 시간의 평균을 계산한다.
  3. 변경 실패율과 복구 시간 측정배포 후 문제가 생긴 비율과, 문제 발생 후 정상 복구까지의 시간을 기록한다.

성숙도 평가: OWASP SAMM

보안 활동을 거버넌스·설계·구현·검증·운영 다섯 영역으로 나눠 현재 수준을 점수화하고 다음 단계를 정하는 모델.

#1문제 상황

개발팀의 보안 수준이 어느 정도인지 어떻게 알 수 있을까요? "보안 테스트를 한다"는 팀도 있고, "한 번도 안 했다"는 팀도 있습니다. 각 팀이 보안에서 뭘 하는지, 뭘 못 하는지 체계적으로 알 수 없습니다.

#2핵심 질문

팀의 보안 능력을 여러 관점에서 체계적으로 평가하고 다음 개선 단계를 정하려면?

#3동작 예시

팀이 "요구사항 단계에서 보안 위험을 생각한다"(거버넌스), "보안 설계 리뷰를 한다"(설계), "보안 코딩 규칙을 따른다"(구현), "침투 테스트(해커 입장에서 공격 시뮬레이션)를 한다"(검증), "배포 후 보안 이벤트를 모니터링한다"(운영)의 5개 영역을 각각 1단계부터 5단계까지 점수화합니다.

#4동작 과정

  1. 5개 영역 평가거버넌스(규칙·정책), 설계(보안 아키텍처 검토), 구현(안전한 코딩 실천), 검증(보안 테스트), 운영(모니터링·사고 대응) 각 영역에서 팀이 뭘 하는지 확인합니다.
  2. 현재 점수 계산각 영역을 1~5 단계로 평가해 팀의 현재 성숙도 프로필을 만듭니다.
  3. 개선 로드맵 수립가장 약한 영역부터 또는 가장 높은 영향을 미치는 영역부터 단계적으로 개선할 계획을 세웁니다.

#5한 줄 요약

보안 활동을 5개 영역으로 나눠 현재 수준을 점수화하고 체계적으로 다음 단계로 나아가도록 하는 성숙도 평가 모델

규정 준수·감사·추적성

요구사항부터 코드·빌드·배포까지 누가 언제 무엇을 바꿨는지 증거로 이어붙여 감사에 답할 수 있게 만드는 일.

#1문제 상황

은행이나 보험 같은 규제 산업에서는 감사를 받습니다. 감사자가 "이 코드는 왜 프로덕션에 있는가?"라고 물으면, 당신은 "왜냐하면..."이라고 증거를 보여줘야 합니다. 그런데 "사실 누가 언제 배포했는지 모르고, 왜 그 코드가 필요했는지도 기억 안 나요"라면 감사를 통과할 수 없습니다.

#2핵심 질문

요구사항부터 실제 배포까지 모든 변경을 추적하고 증거로 남기려면?

#3동작 예시

기획자가 "사용자 로그인 기능 추가"라는 요구사항을 등록 → 개발자가 코드 작성 후 커밋(누가, 언제, 뭘 했는지 기록) → 빌드 시스템이 자동으로 테스트 실행(로그 저장) → 배포 시스템이 프로덕션으로 배포(배포자, 시간, 버전 기록) → 감사자가 요구사항 ID와 코드 커밋, 빌드 로그, 배포 기록을 연쇄적으로 추적해 "이게 실제로 요구사항을 충족한다"고 확인합니다.

#4동작 과정

  1. 변경 기록 자동 수집코드 저장소(git), 빌드 시스템, 배포 시스템이 각 단계에서 누가 언제 뭘 했는지를 자동으로 기록합니다.

DevOps 문화: 협업·책임 이동·짧은 주기

개발과 운영이 벽을 없애고 만든 사람이 운영까지 책임지며 작게 자주 내보내는 일하는 방식.

#1문제 상황

전통적으로 개발팀과 운영팀은 따로 일합니다. 개발자는 "빨리 새로운 기능을 배포해야 해"라고 생각하고, 운영팀은 "함부로 건드리면 서비스가 멈춘다"고 생각합니다. 배포 전에 운영팀의 승인을 받으려면 서류를 작성하고 오래 기다립니다. 배포 후 문제가 생기면 "누가 이걸 배포했어?"라면서 책임을 미룹니다.

#2핵심 질문

개발과 운영의 벽을 없애고 빠르고 안정적으로 배포하려면?

#3동작 예시

개발자 A가 기능을 개발해서 배포하고, 배포 후 모니터링도 A가 직접 합니다. 에러가 생기면 "내가 만든 코드니까 내가 고쳐야지"라는 마음으로 바로 고칩니다. 에러는 자신의 책임이라는 주인의식이 생깁니다.

#4동작 과정

  1. 팀 구조 통합개발자와 운영자가 같은 팀으로 묶이고, 같은 목표(빠르고 안정적인 배포)를 갖습니다.
  2. 책임 이동"배포는 운영팀이 해"라는 분담을 없애고, 개발자가 자기 코드의 배포부터 모니터링까지 책임집니다.
  3. 짧은 주기큰 변경을 한 번에 하지 말고, 작은 변경을 자주 배포합니다. 피드백이 빨리 오고, 문제가 생겨도 원인을 찾기 쉽습니다.

개발과 운영이 협업하고, 개발자가 배포까지 책임지며, 작은 단위로 자주 내보내는 문화

지속적 개선: 회고·가치 흐름·실험

회고로 배우고 가치 흐름에서 병목을 찾아 작은 실험으로 검증하며 프로세스를 계속 다듬는 습관.

#1문제 상황

팀이 배포 시스템을 갖추고 자동화도 했습니다. 그런데 매주 배포할 때마다 "어? 여기서 계속 30분이 걸려?"라거나 "이 단계가 필요한가?"라는 생각이 듭니다. 지금 프로세스가 최선인지 알 수 없습니다. 또한 "이 개선을 하면 정말 빨라질까?"라는 불확실성도 있습니다.

#2핵심 질문

프로세스의 병목을 찾아 계속해서 더 효율적으로 다듬어나가려면?

#3동작 예시

팀이 배포 과정을 기록해보니 "코드 리뷰 대기 시간"이 가장 깁니다 → 작은 가설을 세운다 → "리뷰어를 2명 늘리면 기다리는 시간이 줄어들까?" → 실제로 1주일 시도해본다 → 결과를 확인한다 → 효과가 있으면 계속한다, 없으면 다른 방법을 시도한다.

#4동작 과정

  1. 회고주기마다(보통 1주일 또는 2주일) 팀이 모여 "이번 주에 뭐가 잘 됐고, 뭐가 안 됐나?" 배웁니다.
  2. 가치 흐름 분석요구사항이 배포될 때까지의 과정(코드 작성, 리뷰, 빌드, 테스트, 배포)에서 가장 오래 걸리는 단계(병목)를 찾습니다.
  3. 작은 실험병목을 개선하기 위한 작은 가설을 실험한다(도구 바꾸기, 프로세스 간소화, 인력 조정 등). 정해진 기간 후 결과를 확인하고 계속하거나 롤백합니다.

#5한 줄 요약

경험에서 배우고, 가치 흐름에서 병목을 찾으며, 작은 실험으로 검증해 프로세스를 지속해서 개선하는 습관
