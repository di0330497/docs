1. Lambda 의 뼈대 — 코드가 도는 자리01-01

AWS Lambda 란 무엇인가

요청이 들어올 때마다 AWS 가 미리 준비해 둔 서버에서 사용자가 올린 함수를 잠깐 실행하고 다시 잠자는, 서버를 직접 관리하지 않아도 되는 서버리스 컴퓨팅 서비스다.

#1문제 상황

온(always) 돌아가는 서버를 직접 준비하면 서버 유지보수, 용량 확보, 부하에 따른 확장을 모두 직접 해야 한다._traffic 이 없는 시간에도 비용이 나고, 코드가 오류를 내면 서버 상태까지 직접 살핀다.

AWS Lambda 는 이렇게 준비된 서버 없이 코드만 올리는 serverless 컴퓨팅 서비스다. 인프라 관리는 전부 Lambda 가 맡는다.

#2핵심 질문

서버를 직접 준비하지 않고 코드를 자동으로 실행하려면 어떻게 해야 하는가?

#3동작 예시

이미지가 S3 버킷에 업로드된다. 버킷에 붙은 연결이 함수를 깨워 Lambda 는 그 함수(function)를 실행하고, 처리 결과와 실행 기록이 CloudWatch Logs 에 남는다.

#4동작 과정

  1. 연결한다함수에 트리거를 붙여 어떤 신호가 오면 실행되게 한다. 이벤트는 API 요청이나 일정 같은 것이라면 JSON 으로 함수에 건네는 형식이다.
  2. 실행한다호출 한 번마다 함수가 따로 실행되고 결과는 반환값으로 내놓는다. 호출 사이에는 상태가 남지 않으므로 pay per request, 즉 쓴 만큼만 내는 과금 방식이 가능하다.
  3. 확인해 볼 것함수를 실행한 뒤 콘솔의 로그 탭에서 이번 호출의 요청 ID와 출력 줄이 함께 뜨는지 확인한다.

실행 환경 — 코드가 어디서 돌며 어떻게 재사용되나

Lambda 는 실행 환경(내부적으로 마이크로 가상머신)이라는 격리된 샌드박스를 만들어 그 안에서 함수를 돌리고, 호출이 끝나면 환경을 되돌려 다음 호출에 재사용하는 방식을 쓴다.

먼저 알아야 할 것 01-01

#1문제 상황

서버에는 메모리와 임시 디스크가 있고, 방금 실행한 코드의 결과가 어디까지 남았는지 알 수 없다(→ 01-01). 그래서 매 호출마다 서버를 새로 띄우면 느리고, 안 띄우면 이전 호출의 흔적과 섞인다.

Lambda 는 실행 환경(execution environment)을 하나 만들어 그 안에서 함수를 돌리고, 호출이 끝나면 환경을 되돌려 다음 호출에 재사용하는 방식을 쓴다. 첫 호출만 환경을 만드는 cold start 가 생기고 그 뒤 호출은 재사용된 환경에서 시작한다. 환경마다 메모리가 따로 붙어 있다(→ 03-01).

#2핵심 질문

함수를 돌리는 환경은 어떻게 준비되고 다음 호출에서 어떻게 다시 쓰이는가?

#3동작 예시

단순한 함수를 짧은 간격으로 세 번 부른다. 첫 호출은 새 환경을 만들어 시작하고, 이어지는 두 번은 되돌아온 환경에서 그대로 실행된다.

#4동작 과정

  1. 환경을 만든다Lambda 는 마이크로 가상머신(작은 가상머신) 단위로 격리된 실행 환경을 띄운다. 이 안에서 코드를 해석하고 실행하는 것이 runtime 이다.
  2. 재사용한다처리가 끝나면 환경에 붙어 있던 임시 상태를 비우고 런타임과 메모리를 다음 호출에 넘긴다. 외부 확장이 함께 붙어 있으면 그 수명 주기도 이 안에서 관리한다.
  3. 확인해 볼 것함수의 Metrics 화면에서 첫 호출 이후의 Duration 값이 낮게 유지되는지 확인한다.

개발자가 코드로 지정한 진입 함수인 핸들러(handler)에 이벤트 객체 하나가 전달되어 그 결과를 반환하는 구조이며, Lambda 는 이 약속을 모든 언어에서 동일하게 정의한다.

먼저 알아야 할 것 01-02

#1문제 상황

코드를 올려도 Lambda 는 어느 함수부터 실행해야 하는지 알 수 없다(→ 01-02). 실행 환경 안에서 매 호출마다 상태는 지워지므로, 들어온 요청을 어떻게 넘기고 결과를 어디로 보낼지 약속이 필요하다.

Lambda 의 programming model 은 그 약속이다. 같은 규약이 모든 런타임에 동일하게 적용된다.

#2핵심 질문

#3동작 예시

함수 설정에서 진입점 이름을 handler 로 지정한다. 호출이 들어오면 런타임이 event 와 context 를 넘기고, 함수가 처리한 결과를 반환하면 그 값이 호출한 쪽에 전달된다.

#4동작 과정

  1. 핸들러를 정한다함수 설정에 진입점 이름(handler)을 적어 두고 코드의 해당 이름만 실행시킨다. 어느 언어든 이 이름 하나가 실행 지점이 된다.
  2. 객체를 받는다런타임이 호출 event 를 담은 event 객체와 context 객체를 넘긴다. context 객체에는 함수 이름과 요청 ID 같은 이번 호출의 정보가 들어 있다.
  3. 반환한다핸들러가 돌려준 반환값이 그 호출의 결과가 되며, 값은 JSON 으로 직렬화된다. 같은 실행 환경에서도 호출마다 새 이벤트가 다시 넘어온다(→ 01-02).
  4. 확인해 볼 것콘솔의 Test 창에서 테스트 이벤트를 고르고 Invoke 를 눌러 반환값이 화면에 뜨는지 확인한다.

#1문제 상황

함수를 서로 직접 부르면 앞쪽이 멈출 때 뒤쪽도 함께 멈추고, 두 코드를 같이 고쳐야 한다(→ 01-03). 이런 결합을 끊지 않으면 규모가 커질수록 고치기 어려워진다.

event-driven architecture 는 AWS 서비스가 만든 event 를 함수가 받아 처리하게 연결해 이 결합을 끊는다. 사건이 없는 동안에는 코드가 전혀 실행되지 않는다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 트리거를 건다이벤트를 만들어 내는 AWS 서비스에 함수를 직접 호출하도록 붙인다. push 방식이라 그 서비스가 함수를 부른다.
  2. 매핑으로 당겨 온다지원 서비스에 이벤트 소스 매핑을 설정하면 Lambda 가 큐나 스트림을 직접 확인해(pull) 함수를 부른다. 폴링과 호출은 Lambda 가 맡는다.
  3. 형식을 맞춘다함수에 넘겨지는 이벤트는 JSON 형식이고 구조는 만들어 낸 서비스와 이벤트 종류마다 다르다. 이벤트는 짧은 처리에 잘 맞는다.
  4. 확인해 볼 것이벤트를 발생시킨 뒤 함수의 호출 횟수가 증가하고 로그에 새 호출이 남는지 확인한다.

#1문제 상황

그래서 Lambda 애플리케이션은 설계 원칙을 따로 정해 둔다. 아래는 designing an application 을 짤 때 볼 지침이다.

#2핵심 질문

여러 함수를 붙인 애플리케이션을 어떻게 나눠야 안전한가?

#3동작 예시

한 주문 처리에 검증, 결제, 알림을 맡는 함수가 따로 있다. 결제 함수가 응답을 잃어 같은 요청이 다시 들어와도 이미 처리한 주문이면 다시 청구하지 않고 결과만 돌려준다.

#4동작 과정

  1. 일을 나눈다한 함수에는 한 가지 일만 맡긴다(단일 책임). 상태 없이(stateless) 돌게 설계해 실행 환경이 바뀌어도 결과가 같게 만든다(→ 01-02).
  2. 안전하게 만든다같은 요청이 여러 번 들어와도 결과가 변하지 않는 멱등성(idempotency)을 확보한다. 커스텀 코드보다 AWS 서비스를 함께 쓰고, 결합도 낮춘다.
  3. 큰 흐름을 정한다복잡한 흐름은 오케스트레이션 방식을 따로 고르고, 즉석 묶음 처리보다 요청이 올 때 하는(on-demand) 방식으로 처리한다. 여러 AWS 계정으로 할당량을 나누는 것도 권장된다.
  4. 확인해 볼 것함수를 목록에서 펼쳐 각 함수의 메모리와 타임아웃 설정이 역할별로 다르게 지정돼 있는지 확인한다.

코드를 .zip 으로 묶어 Lambda 에 올리는 기본 배포 방식으로, 디렉터리 구조와 의존성 라이브러리 포함 규칙을 지켜 압축 파일 하나를 함수에 붙여 배포하는 방식이다.

먼저 알아야 할 것 01-06

#1문제 상황

Lambda 는 컨테이너 이미지와 .zip file archives, 두 가지 배포 패키지 형태를 받는다(→ 02-02). 여기서는 압축 파일 하나를 올리는 방법을 다룬다.

코드를 단일 .zip 파일로 묶어 함수에 붙이면 배포가 끝난다. 이 압축 파일을 deployment package 이라고 부른다.

#2핵심 질문

함수 코드를 Lambda 에 어떤 형태로 올려야 하는가?

#3동작 예시

함수 코드 폴더에서 의존성 라이브러리까지 포함해 .zip 파일을 만들고 Lambda 콘솔에서 함수에 업로드한다. 코드 수정 뒤 같은 파일을 다시 올리면 새 코드로 함수가 실행된다.

기본값으로 Lambda 는 올린 코드의 사본을 Lambda-managed storage 에 따로 보관한다.

#4동작 과정

  1. 구조를 맞춘다핸들러 파일 위치를 맞춰 .zip 파일을 만든다. organize function 규칙에 따라 진입 함수의 경로가 정해진다(→ 01-03).
  2. 암호화를 정한다encrypt-zip-package 설정을 켜면 압축 파일을 Lambda-managed encryption key 로 암호화해 올린다. 암호화는 저장과 전송 중 코드를 보호한다.
  3. 가져오기를 정한다self-managed S3 코드 저장소를 쓰면 Lambda 가 S3 버킷에서 코드를 읽고 별도 사본을 두지 않는다(→ 03-06).
  4. 확인해 볼 것함수의 코드 탭에서 올린 .zip 파일의 이름과 코드가 반영됐는지 확인한다.

먼저 알아야 할 것 02-01

#1문제 상황

Lambda 는 container images와 .zip file archives 두 형태의 deployment package을 받는다(→ 02-01). .zip 으로 담기 어려운 큰 의존성이 있어 이미지 형태가 필요하다.

컨테이너 이미지 배포는 코드를 이미지로 빌드해 그대로 실행시키는 방식이다. 어떤 언어나 패키징 방식을 쓰든 같은 방식으로 함수를 배포할 수 있다.

#2핵심 질문

어떤 언어와 라이브러리 조합이든 Lambda 에 올릴 컨테이너 이미지를 어떻게 만드나?

#3동작 예시

빌드한 이미지를 ECR에 푸르고 그 image URI를 함수에 지정한다. 함수가 호출되면 Lambda 가 그 이미지를 당겨 실행 환경에서 그대로 구동한다.

multi-architecture 빌드로 여러 CPU 아키텍처용 이미지를 한 번에 만들면 골라 쓸 수 있다.

#4동작 과정

  1. 기본 이미지를 고른다AWS base image는 언어 런타임과 Lambda 와 코드가 통신하는 runtime interface client가 이미 들어 있다. AWS OS-only base image에는 Amazon Linux와 런타임 인터페이스 에뮬레이터만 있어 Go·Rust 같은 컴파일 언어나 직접 만든 런타임에 쓴다(→ 02-05).
  2. 빌드해 저장한다컨테이너 이미지를 만들어 ECR에 올리고 그 image URI를 함수에 지정한다. 로컬에서 시험할 때는 런타임 인터페이스 에뮬레이터를 함께 쓴다.
  3. 확인해 볼 것함수 설정에서 지정한 image URI와 ECR에 올라간 이미지의 태그가 같은지 확인한다.

프로그래밍 언어 선택

먼저 알아야 할 것 02-01

#1문제 상황

Lambda 는 Node.js, Python, Java, Go, C#, Rust 등 여러 programming languages를 지원한다. 다만 언어마다 실행에 필요한 환경이 달라 그대로 둘 수는 없다.

그래서 각 언어는 대응하는 runtime을 갖고 있고, 이 런타임이 그 언어에 맞는 실행 환경을 제공한다. 언어를 고르면 런타임이 정해진다.

#2핵심 질문

어떤 언어로 함수를 만들면 그 코드가 실행될 환경을 무엇으로 맞춰야 하는가?

#3동작 예시

팀에서 이미 쓰는 언어가 Python이라 함수를 그 언어로 만든다. 함수 설정에서 Python에 대응하는 런타임 식별자를 고르면 그 런타임이 코드를 실행한다.

코드와 핸들러 구조는 언어마다 관용적인 방식으로 작성한다(→ 01-03).

#4동작 과정

  1. 언어를 고른다Lambda 가 지원하는 programming languages 목록에서 팀이 쓰는 언어를 선택한다. 언어마다 개발 경험이 다르게 맞춰져 있다.
  2. 런타임 식별자를 정한다고른 언어에 대응하는 runtime 식별자를 함수에 붙인다. 이 식별자가 실제 실행 환경의 버전을 정한다(→ 02-04).
  3. 맞춤형 기능을 본다일부 언어는 전용 라이브러리나 인터페이스를 제공해 그 언어답게 함수와 이벤트를 다룰 수 있게 한다.
  4. 확인해 볼 것함수의 코드 탭에서 런타임 항목에 선택한 언어와 식별자가 표시되는지 확인한다.

런타임 버전 관리 — 자동 갱신과 롤백

함수에 붙은 런타임 식별자를 자동(auto)·수동 함수 업데이트(function update)·수동(manual) 세 가지 갱신 방식으로 관리하고, 새 런타임에서 문제가 생기면 이전 런타임으로 되돌리는 롤백 절차를 정해 두는 것.

먼저 알아야 할 것 02-03

#1문제 상황

런타임은 보안 패치와 언어 버전이 올라가면서 여러 버전으로 차례로 배포된다. 함수마다 어떤 버전을 쓰는지 관리하지 않으면 갱신 뒤 문제가 생긴다.

런타임 버전 관리는 이 갱신을 누가 맡을지 정하고, 문제가 생겼을 때 되돌릴 자리를 남기는 일이다.

#2핵심 질문

함수의 런타임 갱신을 자동에 맡길지 직접 판단할지 어떻게 정하고, 문제가 생기면 어떻게 되돌리는가?

#3동작 예시

새 런타임 버전이 배포되어 함수를 갱신한다. 그런데 배포 직후 호출이 실패해 이전 버전으로 되돌린다. 돌아간 함수는 이전 런타임 버전에서 다시 호출된다.

#4동작 과정

  1. 관리 방식을 정한다Automatic runtime update를 켜 두면 Lambda 가 런타임 버전 패치 작업을 대신 맡는다. 끄면 Automatic runtime update가 아닌 함수 업데이트 방식으로 직접 갱신한다.
  2. 버전을 추적한다각 런타임 버전에는 버전 번호와 ARN 이 붙는다. 함수 상태에서 현재 어떤 런타임 버전이 붙어 있는지 확인한다.
  3. 되돌린다새 런타임에서 문제가 생기면 이전 런타임 버전으로 함수를 갱신해 돌아간다. 계획된 지원 종료 deprecation 에 대비하는 절차를 미리 정해 둔다.
  4. 확인해 볼 것함수 설정에서 런타임 관리 설정과 현재 런타임 식별자가 어떻게 되어 있는지 확인한다.

OS 전용 런타임 — 직접 만든 실행 환경

AWS 가 미리 만든 런타임 대신 특정 운영체제 계열(예: Amazon Linux)에서 직접 준비한 라이브러리와 환경으로 코드를 실행하게 하는 사용자 정의 런타임을 구성하는 일.

먼저 알아야 할 것 02-04

→ 02-04 참조

#1문제 상황

AWS 가 준비한 런타임에 없는 언어나 라이브러리, 또는 Lambda 가 제공하지 않는 언어 버전을 써야 할 때가 있다. OS는 운영체제로, 코드가 실제로 돌아가는 기반 환경을 뜻한다. 미리 만든 런타임으로는 그 코드를 돌릴 수 없다.

그래서 특정 운영체제 계열에서 직접 준비한 환경으로 코드를 실행하는 사용자 정의 런타임을 구성한다.

#2핵심 질문

AWS 가 제공하지 않는 언어와 환경을 함수에서 돌리려면 무엇을 직접 준비해야 하는가?

#3동작 예시

자체 런타임 파일을 만들어 배포 패키지에 넣고 provided.al2023 계열 런타임을 선택해 함수를 만든다. 함수가 호출되면 bootstrap 이 실행되며 런타임 API 규약에 따라 응답을 돌려준다.

#4동작 과정

  1. 운영체제 계열을 고른다OS-only runtimes, 즉 provided 런타임 계열을 선택한다. Amazon Linux 계열이 쓰이며 OS-only base image로 이미지를 만들 수도 있다(→ 02-02).
  2. 런타임을 구현한다custom runtime는 호출 시 핸들러를 돌리는 프로그램이다. bootstrap 이라는 실행 파일이 시작되며, 초기화 뒤 환경 변수에서 핸들러 이름을 읽어 함수를 부른다.
  3. 규약을 지킨다함수를 부르고 응답을 돌리는 일은 runtime API 규약으로 정해져 있다. 응답 스트리밍도 이 규약 안에서 구현한다. 레이어로 런타임을 함께 배포할 수도 있다(→ 02-06).
  4. 확인해 볼 것함수의 런타임 항목에 OS 전용 런타임 계열이 표시되는지 확인한다.

레이어와 확장

공통 라이브러리나 확장(extension) 파일을 .zip 으로 묶어 Lambda 계정 단위로 등록해 두고 여러 함수가 공유·가져오게 하는 패키징 재사용 방식이다.

먼저 알아야 할 것 02-03

#1문제 상황

여러 함수에 같은 라이브러리가 필요하다. 함수마다 직접 넣으면 배포가 무겁고 버전도 제각각이다.

layers는 공통 라이브러리나 사용자 정의 런타임, 설정 파일을 .zip 파일로 묶어 계정 단위에 등록해 두는 방식이다.

#2핵심 질문

여러 함수가 같은 라이브러리를 함께 쓰게 하려면 어떻게 등록하고 가져오는가?

#3동작 예시

공통 라이브러리를 packaging layers 단계에서 .zip 파일로 묶어 Lambda 계정에 레이어로 등록한다. 함수를 만들 때 이 레이어를 최대 다섯 개까지 선택해 붙이고, 등록된 목록에서 수정하거나 지운다.

#4동작 과정

  1. 묶어 등록한다레이어 내용을 .zip 파일 하나로 묶어 Lambda 계정에 등록한다. 함수들이 Amazon Linux 에서 도므로 내용물이 Linux 환경에서 컴파일·빌드되어야 하며, Docker 같은 도구로 만드는 것을 권장한다.
  2. 붙이면 올려진다함수를 만들 때 레이어를 선택하면 Lambda 가 실행 환경의 /opt 디렉터리에 레이어 내용을 올린다. 각 runtime의 경로에 맞춰 PATH 변수가 이미 잡혀 있어 라이브러리가 바로 잡힌다.
  3. 확장도 함께 쓴다extensions은 레이어 형태로 붙이는 확장 파일이다. Extensions API로 시작과 종료 시점을 처리하고, Telemetry API와 Logs API로 지표를 내보내고 로그를 남긴다.
  4. 확인해 볼 것함수 설정의 레이어 목록에 등록한 레이어 이름과 버전이 나란히 보이는지 확인한다.

메모리 — 크기가 곧 CPU

함수에 할당하는 메모리 크기를 키우면 그만큼 더 많은 CPU 시간과 처리 능력을 함께 얻는다는 사실, 즉 메모리가 CPU 속도 자체를 정한다는 것.

먼저 알아야 할 것 02-01

#1문제 상황

Lambda 는 함수를 올릴 때 실행 환경에 줄 메모리와 CPU 를 미리 정해 놓는다(→ 01-02). 기본값인 128 MB 로는 이미지 처리나 큰 파일 파싱 같은 함수가 시간 안에 끝나지 않는다.

메모리(memory)는 함수의 실행 속도를 정하는 핵심 손잡이다. memory configuration 으로 128 MB 부터 10,240 MB 까지 1 MB 단위로 올릴 수 있고, 1,769 MB 를 넘으면 CPU power 가 vCPU 한 개 분량으로 따라 rises 한다. CPU 는 따로 늘릴 수 없다.

#2핵심 질문

함수에 얼마나 많은 메모리를 줘야 원하는 속도로 끝나게 할 수 있을까?

#3동작 예시

동영상 썸네일을 만들던 함수가 30초 가까이 걸려 타임아웃에 걸린다. 메모리를 1,769 MB 로 올려 다시 돌린다.

같은 코드가 CPU 를 하나 온전히 쓰면서 훨씬 짧은 시간에 끝나고, 배포한 함수 목록의 Duration 그래프가 낮아진다.

#4동작 과정

  1. 값을 정한다함수 설정의 메모리 값을 고르고 저장한다. 이 값이 memory configuration 이며 실행되는 동안 CPU 비율(CPU proportional)도 함께 정해진다.
  2. 아키텍처를 고른다instruction sets 항목에서 ARM 과 x86 중 어느 것을 쓸지 정한다. ARM 은 같은 메모리에서 더 적은 비용으로 도는 경우가 많다.
  3. 추천을 받는다콘솔의 메모리 권장 기능이 실행 기록을 보고 더 나은 값을 제안한다. 그대로 적용하거나 이전 값으로 되돌린다.
  4. 확인해 볼 것함수 목록에서 메모리 값과 Duration 이 어떻게 함께 바뀌는지 확인한다.

임시 저장소

함수가 실행 중인 동안에만 유지되고 호출이 끝나면 지워지는 디스크 영역으로, 기본 512MB에서 최대 10,240MB까지 늘릴 수 있다.

먼저 알아야 할 것 03-01

#1문제 상황

Lambda 실행 환경의 디스크는 함수마다 따로 있다(→ 01-02). 기본 크기로는 중간 파일이나 내려받은 압축 파일을 담지 못해 코드가 실패한다.

ephemeral storage 는 호출마다 새로 만들어지는 임시 디스크 영역이다. 이 안의 /tmp 는 실행 중에 사라진다. 512 MB 에서 10,240 MB 까지 늘릴 수 있고 max size 를 넘기면 오류가 난다.

#2핵심 질문

함수가 실행 중에만 쓸 임시 디스크를 얼마나 크게 잡아야 할까?

#3동작 예시

S3 에서 큰 CSV 를 받아 변환한 뒤 다시 업로드하는 함수를 만든다. 파일을 임시 폴더에 받아 처리한다.

임시 저장소를 늘리면 받아 둔 파일이 잘리지 않는다. 처리가 끝나면 임시 폴더는 비어 다시 쓰인다.

#4동작 과정

  1. 크기를 정한다함수의 Ephemeral storage 값을 고른다. 기본은 512 MB 이고 1 MB 단위로 늘릴 수 있다.
  2. 임시 폴더에 쓴다코드가 /tmp 아래에 파일을 만들고 지운다. 실행 환경마다 별개라 호출끼리 파일을 공유하지 않는다.
  3. 정리된다호출이 끝나면 ephemeral storage 의 내용은 사라진다. 다음 호출에서 같은 공간이 다시 쓰인다.
  4. 확인해 볼 것함수 설정에서 Ephemeral storage 값이 저장된 것을 확인한다.

타임아웃

한 번의 호출이 실행될 수 있는 최대 시간으로, 기본 3초에서 최대 15분까지 설정하며 넘으면 실행 중인 호출은 강제 종료된다.

먼저 알아야 할 것 03-01

#1문제 상황

Lambda 는 호출이 끝났는지 알 수 없어 정해진 시간까지만 기다린다. 기본값 3초는 대부분의 함수를 끊는다.

timeout 은 한 번의 호출이 실행될 수 있는 maximum duration 이다. 기본 3초에서 900초(15분)까지 1초 단위로 올린다. 이 시간 안에 끝나지 않으면 실행 중인 호출이 강제 종료된다.

#2핵심 질문

함수가 끝날 때까지 기다려 줄 최대 시간을 얼마로 정해야 할까?

#3동작 예시

외부 API 를 세 번 순회해야 하는 함수를 만든다. 3초를 넘기 반복 호출에서 타임아웃이 발생한다.

타임아웃 값을 올려 다시 호출하자 함수가 끝까지 도는지 확인된다.

#4동작 과정

  1. 값을 정한다함수의 Timeout 값을 초 단위로 지정한다. timeout value 를 바꾸면 다음 호출부터 새 시간이 적용된다.
  2. 기다린다호출이 시작되면 정한 시간 안에서 함수가 끝나기를 기다린다. 이 동안 다른 호출도 별도로 붙는다.
  3. 끊는다시간이 넘으면 maximum duration 에 닿아 진행 중인 호출이 멈춘다. 로그에서 시간 초과로 남는다.
  4. 확인해 볼 것함수 설정의 Timeout 값과 설정 페이지의 maximum duration 설명을 함께 본다.

환경변수와 그 암호화

함수를 코드와 함께 배포해 실행 중에 참조하는 키-값 설정으로, 평문 대신 암호화되도록 지정할 수 있으며 값은 암호문 상태로 암호화 키로 복호화해 런타임에 전달된다.

먼저 알아야 할 것 03-01

#1문제 상황

코드에 API 키나 데이터베이스 접속 정보를 그대로 적어 두면 코드 저장소에 값이 남고 회전도 어렵다.

environment variables 는 함수 설정에 이름과 값을 넣는 키-값 목록이다. 함수 버전별로 저장되며 런타임이 실행 중에 코드에 제공한다. 값은 모두 문자열로 그대로 읽힌다.

#2핵심 질문

비밀 값을 코드에 넣지 않고 실행 중에 읽을 수 있게 하려면 어떻게 해야 할까?

#3동작 예시

함수 설정의 Environment variables 항목에 데이터베이스 주소를 넣고 배포한다. 코드는 이 이름으로 값을 읽어 접속한다.

값을 encrypt 할 때 AWS KMS 로 지정하면 저장 단계에서 암호화되고, 실행할 때만 암호화 키로 풀려 코드에 전달된다.

#4동작 과정

  1. 값을 넣는다콘솔이나 명령행 도구로 환경변수 이름과 값을 등록한다. plaintext 로도 저장할 수 있어 조심해야 한다.
  2. 암호화한다securing environment variables 를 켜 KMS encryption 을 지정한다. 저장된 값은 평문이 아니라 암호문으로 남는다.
  3. 읽힌다런타임이 함수를 시작할 때 값을 복호화해 코드에 전달한다. Lambda 자체 정보가 담긴 변수도 함께 설정된다.
  4. 확인해 볼 것함수 설정 화면에 등록한 변수 이름이 목록에 보이는지 확인한다.

먼저 알아야 할 것 03-02

#1문제 상황

함수마다 임시 디스크가 따로라 여러 함수가 같은 데이터를 함께 써야 할 때 서로 볼 수 없다. 큰 파일을 함수에 붙여 넣는 것도 번거롭다.

Lambda file system mount 는 함수를 VPC 서브넷에 붙이고(file systems) 공유 파일 시스템을 붙이는 설정이다. Amazon EFS 는 사용량에 따라 자동으로 늘리는 서버리스 파일 시스템이며, 함수에서 여러 개를 동시에 연결할 수 있다.

#2핵심 질문

여러 Lambda 함수가 같은 파일을 함께 쓰게 하려면 어떻게 해야 할까?

#3동작 예시

이미지가 올라오면 썸네일을 만들어 EFS 폴더에 저장하는 함수를 만든다. 함수를 VPC 에 붙이고 EFS 액세스 포인트를 연결한다.

썸네일을 목록으로 보여 주는 다른 함수가 그 폴더를 읽어 같은 파일을 본다.

#4동작 과정

  1. 자리를 정한다함수를 VPC 서브넷에 붙인다. 보안 그룹도 함께 지정해 파일 시스템에 닿게 한다.

  3. 권한을 준다실행 역할에 elasticfilesystem:ClientMount 와 elasticfilesystem:ClientWrite 를 넣는다. 읽기 전용이면 ClientWrite 는 필요 없다. Amazon S3 Files 도 같은 방식으로 붙일 수 있다.
  4. 확인해 볼 것함수 설정의 File systems 항목에 EFS 연결이 표시되는지 확인한다.

#2핵심 질문

코드 사본을 Lambda 에 맡기지 않고 내 S3 버킷에 두려면 어떻게 해야 할까?

#3동작 예시

몇 GB 분량의 컨테이너 구성물을 포함하는 함수 묶음을 자체 버킷에 업로드하고, 그 버킷을 code storage location 으로 지정해 함수를 만든다.

deploy 이후에도 버킷의 코드가 그대로 실행에 쓰인다.

  2. 저장소를 지정한다code storage location 을 그 버킷으로 지정해 함수를 만든다. layer 와 함께 쓸 때도 버킷에서 읽는다.
  3. 저장 방식을 바꾼다필요하면 저장 모드를 Lambda-managed storage 로 되돌릴 수 있다. 함수 수정이 끝나면 코드 위치가 유지되는지 살핀다.
  4. 확인해 볼 것함수 설정에서 코드가 어느 버킷에서 오고 있는지 확인한다.

4. VPC 안에 넣는다 — 사설망에서 부르기04-01

VPC 에 함수 붙이기

VPC(Virtual Private Cloud, 가상 사설 네트워크) 안에 Lambda 함수를 배치해 사설 자원만 접근할 수 있게 만드는 설정으로, 함수가 VPC 서브넷과 보안 그룹을 쓰도록 지정한다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 서브넷을 고른다VPC 안의 프라이빗 서브넷을 지정한다. subnet 은 VPC 안에서 나뉜 구역이다.

VPC 함수의 인터넷 접근

VPC 안의 Lambda 함수가 외부 인터넷(예: AWS 서비스 API 호출)에 나가도록 NAT 게이트웨이를 만들고 함수를 퍼블릭 서브넷이 아닌 프라이빗 서브넷의 NAT 게이트웨이에 연결하는 배치.

먼저 알아야 할 것 04-01

#1문제 상황

VPC 에 붙은 함수는(→ 04-01) 그 VPC 밖으로 나갈 수 없다. 그래서 S3 나 다른 AWS API 호출이 전부 막힌다. internet access for VPC functions 를 붙여야 한다.

#2핵심 질문

사설망에 있는 함수가 인터넷으로 나가려면 무엇이 필요한가?

#3동작 예시

프라이빗 서브넷의 함수가 S3 버킷에서 파일을 받아 온다. 서브넷 밖으로 나가는 경로가 있어야 요청이 나가고 응답이 들어온다.

#4동작 과정

  1. NAT 게이트웨이를 만든다NAT gateway 는 사설 서브넷의 트래픽을 인터넷으로 내보내는 대리 장비다. NAT 는 Network Address Translation 으로 바뀐 말이다.
  2. 라우팅을 건다프라이빗 서브넷의 라우팅 테이블에서 인터넷으로 가는 경로를 그 게이트웨이로 지정한다. 대안으로 egress-only internet gateway 를 쓴다.
  3. 따로 권한을 준다함수가 만든다고 해서 자동으로 열리지는 않는다. NAT 게이트웨이 생성과 IAM 권한을 따로 준비한다.
  4. 확인해 볼 것같은 프라이빗 서브넷에 있는 EC2 인스턴스가 인터넷으로 나가는지 확인한다.

VPC 함수의 인바운드 경로

VPC 안의 Lambda 함수를 다른 곳에서 호출할 수 있게 하려면 해당 프라이빗 서브넷에 AWS PrivateLink 기반 VPC 엔드포인트(VPC endpoint)를 만들어 Lambda 서비스로의 전용 경로를 여는 배치.

먼저 알아야 할 것 04-01

#1문제 상황

VPC 에서 밖의 Lambda API 를 부르면 공개 인터넷을 지나야 한다. 그래서 공개 IP 가 필요하고 회사가 막을 수 있다. VPC endpoint 를 두면 그 구간을 건너뛴다.

#2핵심 질문

공개 인터넷을 거치지 않고 VPC 안에서 함수를 어떻게 부르는가?

#3동작 예시

프라이빗 서브넷의 서버가 Lambda 함수를 호출한다. 서버에는 공개 IP 가 없는데도 요청이 Lambda 까지 닿는다.

#4동작 과정

  1. 엔드포인트를 만든다interface VPC endpoint 를 Lambda 용으로 만든다. 이는 AWS PrivateLink 방식으로 트래픽이 AWS 네트워크 안에서만 오간다.
  2. 사설 주소를 받는다엔드포인트는 서브넷마다 elastic network interface 를 두고 거기에 사설 IP 를 붙인다. 그 주소가 Lambda 로 들어가는 입구다.
  3. 연결을 붙든다keep-alive 설정으로 회선을 다시 쓰게 하면 지연이 줄고 호출이 막히지 않는다.
  4. 확인해 볼 것엔드포인트 목록에서 Lambda 용 엔드포인트가 해당 서브넷에 붙어 있는지 확인한다.

먼저 알아야 할 것 04-01

#1문제 상황

VPC 안의 Lambda 함수를 붙이는 설정은 같은 계정 안에서 끝난다(→ 04-01). 그런데 자원을 가진 쪽은 다른 계정인 경우가 있다.

다른 AWS 계정의 VPC에 있는 Lambda 함수를 만들려면 호출을 허용하는 권한과 함수를 보호하는 리소스 기반 정책이 함께 있어야 한다(→ 09-03).

#2핵심 질문

다른 계정의 VPC에 있는 Lambda 함수를 만들고 호출하려면 권한을 어떻게 엮어야 하는가?

#3동작 예시

자원을 가진 계정의 관리자가 그 VPC와 서브넷·보안 그룹 정보를 전달한다. 호출 쪽 계정의 관리자가 크로스 계정 권한으로 그 VPC에 함수를 만들고, 함수를 호출할 수 있도록 두 계정의 설정을 맞춘다.

#4동작 과정

  1. 권한을 연다크로스 계정 권한으로 다른 계정의 VPC 자원에 접근해 Lambda 함수를 만들 수 있게 한다. 그 계정 권한은 계정 경계를 넘는 신뢰를 표현한다.
  2. 함수 쪽을 허용한다함수를 호출할 수 있도록 리소스 기반 정책에 호출 주체와 조건을 적는다. 신원 기반 정책과 반대 방향에서 접근을 주는 자리다.
  3. 확인해 볼 것함수의 네트워크 설정에 붙은 VPC·서브넷·보안 그룹 항목이 자원을 가진 계정의 값과 일치하는지 확인한다.

먼저 알아야 할 것 01-03

#1문제 상황

요청한 쪽이 결과를 즉시 받아야 하는 경우가 있다. 함수가 오래 걸리면 그만큼 화면이 멈춘다. synchronous invocation 은 이 대기를 그대로 감수하는 방식이다.

#2핵심 질문

함수의 결과를 바로 받아야 할 때 어떻게 부르는가?

#3동작 예시

웹 화면의 조회 버튼이 함수를 부른다. 함수가 계산을 마치고 넘긴 값이 응답 본문으로 돌아와 화면에 목록이 나타난다.

#4동작 과정

  1. 지시를 보낸다함수를 부르고 응답을 기다린다. 이 방식을 request-response 라고도 부른다.
  2. 결과를 받는다함수가 끝나면 반환값과 함께 어느 버전이 실행됐는지 담긴 메타데이터가 돌아온다.
  3. 실패하면 다시 보낸다호출 API 는 오류가 나면 지시를 반복해 보낸다. 두 번 연속 실패하면 그 요청은 버린다.
  4. 확인해 볼 것호출 결과에서 StatusCode 가 성공을 뜻하는 값으로 오는지 확인한다.

먼저 알아야 할 것 05-01

#1문제 상황

결과가 당장 필요 없는 요청도 있다. 예컨대 이미지 변환 같은 일은 기다릴 이유가 없다. asynchronous invocation 은 그 일을 큐에 맡긴다.

#2핵심 질문

결과를 기다리지 않고 함수를 미리 시켜 놓으려면 어떻게 부르는가?

#3동작 예시

파일을 올리면 함수를 부른 호출자는 즉시 성공 응답을 받는다. 함수는 큐에서 꺼내 나중에 실행되고, 호출자는 그 뒤를 모른다.

#4동작 과정

  1. 큐에 넣는다Lambda 가 이벤트를 내부 queue 에 두고 추가 정보 없는 성공 응답을 돌려준다.
  2. 따로 꺼내 실행한다별도의 과정이 큐를 읽어 함수를 부르고, 큐가 비어 있으면 멈춘다.
  3. 실패를 다시 건다retry attempts 까지 다시 부르고, maximum event age 를 넘기면 그 이벤트를 버린다. 실행 기록은 SQS 나 EventBridge 로 보내고, concurrent requests 로 큐 크기를 정할 수도 있다.
  4. 확인해 볼 것호출 응답에 결과 없이 성공만 표시되는지 확인한다.

먼저 알아야 할 것 05-02

#1문제 상황

비동기 호출(→ 05-02)에서 함수가 오류를 내면 Lambda 가 알아서 몇 번 다시 부른다. 그래도 끝까지 실패하면 그 요청은 사라져 원인을 다시 고칠 기회가 없다.

이 기능은 실패한 요청을 보존해 두었다가 사용자가 직접 꺼내 다시 실행하게 한다. 그 요청을 다른 곳으로 넘길 수도 있다.

#2핵심 질문

비동기 호출이 끝까지 실패한 요청을 다시 실행하려면 어떻게 해야 하는가?

#3동작 예시

이미지 처리 함수를 비동기로 부르고 세 번 다 실패했다. 운영자가 Lambda 콘솔에서 실패한 이벤트 목록을 열어 내용을 확인하고, 코드를 고친 뒤 그 이벤트를 다시 실행한다.

#4동작 과정

  1. 다시 부른다함수 오류와 타임아웃 뒤 Lambda 가 기본 두 번 더 부른다. 이 error handling 흐름이 끝나도 실패하면 그만 둔다.
  2. 보관한다retaining records 는 실패한 이벤트 사본을 Lambda 계정에 남겨 두는 기능이다. 콘솔에서 골라 다시 실행할 수 있고 Amazon EventBridge 규칙으로 알림도 보낼 수 있다.
  3. 넘긴다on-failure destination 은 실패한 이벤트를 지정한 Amazon SQS 큐나 SNS 토픽으로 보내는 설정이다. 이때 쓰는 Amazon SQS 큐를 dead-letter queue 라고 부른다.
  4. 확인해 볼 것Lambda 콘솔의 비동기 호출 실패 목록에 남은 이벤트가 있는지 확인한다.

클라우드에서 고유한 HTTPS 주소를 함수에 붙여 브라우저나 curl 로 인증 없이 바로 호출할 수 있게 하는 기능입니다.

먼저 알아야 할 것 05-01

#1문제 상황

Lambda 함수를 HTTP 로 받으려면 보통 API Gateway 를 앞단에 붙여야 한다(→ 05-01). 자잘한 설정 없이 브라우저에서 바로 열어 볼 길이 없다.

function URLs 는 Lambda 가 함수마다 직접 만든 HTTPS 엔드포인트다. API Gateway 없이 인증 없는 요청으로 함수를 invoke 할 수 있다.

#2핵심 질문

앞단 게이트웨이 없이 함수에 HTTP 주소를 바로 붙이는 방법은 무엇인가?

#3동작 예시

개발자가 함수의 함수 URL 을 만들고 주소를 복사해 브라우저 창에 연다. GET 요청이 그대로 함수에 전달되고, 함수가 돌려 준 JSON 응답이 화면에 그대로 나타난다.

#4동작 과정

  1. 만든다Lambda 콘솔이나 API 로 함수 URL 을 추가하면 https://<url-id>.lambda-url.<region>.on.aws 형태의 고유 주소가 정해진다. 만들어진 주소는 바뀌지 않는다.
  2. 공개 여부를 정한다public access 를 켜면 인증 없이 누구나 요청을 보낼 수 있다. 꺼 두면 AWS_IAM 방식으로 IAM 권한을 요구한다.
  3. 요청을 넘긴다주소로 들어온 HTTP 요청이 invoke 호출로 함수에 전달된다. 인증과 권한을 세게 다뤄야 하면 Amazon API Gateway 를 앞에 붙이는 쪽을 고르면 된다.
  4. 확인해 볼 것함수의 함수 URL 화면에 생긴 주소로 브라우저를 열어 응답이 오는지 본다.

버전과 별칭 — 배포를 되돌릴 자리

코드를 수정할 때마다 함수에 번호 버전을 남기고 그 버전들을 가리키는 별칭 이름을 만들어, 별칭만 바꿔 이전 코드로 되돌리는 구조입니다.

먼저 알아야 할 것 05-01

#1문제 상황

함수에 코드를 올리면 지금 돌던 코드가 그대로 덮여 쓰인다(→ 05-01). 문제가 생겼을 때 예전 코드로 되돌릴 자리가 없다.

versions 로는 배포마다 번호가 붙은 사본을 남기고, aliases 로는 그 버전에 이름을 붙여 두었다가 이름만 바꿔 되돌린다.

#2핵심 질문

배포한 코드를 되돌릴 자리를 어떻게 만들어 두는가?

#3동작 예시

운영자가 수정 코드를 배포해 prod 별칭이 가리키는 버전 번호를 확인한다. 오류가 나자 prod 별칭을 배포 전 버전으로 다시 지정한다. 곧바로 이전 코드가 호출을 받는다.

#4동작 과정

  1. 남긴다publish version 을 실행하면 $LATEST 코드의 사본이 번호가 붙은 버전으로 굳는다. 확정된 버전의 코드와 런타임, 메모리, 레이어는 바꿀 수 없다.
  2. 이름을 붙인다aliases 는 특정 버전이나 $LATEST 를 가리키는 이름이다. 이 이름으로 호출하면 그 대상이 실행된다.
  3. 나눠 쓴다weighted aliases 는 한 이름에 버전별 가중치를 나눠 두어 일부 요청만 새 버전으로 보내는 방식으로, 배포를 조금씩 옮길 때 쓴다.
  4. 확인해 볼 것함수 화면의 버전과 별칭 목록에서 새 버전 번호와 별칭이 가리키는 버전 번호가 보이는지 본다.

함수 상태와 재귀 호출 막기

같은 함수가 자기 자신을 다시 부르는 재귀 호출이 순환을 일으키지 않도록 AWS_LAMBDA_FUNCTION_NAME 환경 변수로 구분하고 최대 호출 깊이를 정하는 안전장치입니다.

먼저 알아야 할 것 05-01

#1문제 상황

함수가 자기 자신을 다시 부르는 재귀 호출이 생기면 요청이 끝없이 이어진다. 예상 못한 요금과 함수 호출 폭증으로 이어진다.

recursive loop detection 은 이 순환을 Lambda 가 알아채고 끊어 내는 기능이다. 함께 보이는 function states 는 현재 호출이 어디까지 갔는지를 나타내는 상태 표시다.

#2핵심 질문

함수가 자신을 무한히 부르는 순환을 어떻게 막는가?

#3동작 예시

함수가 SQS 큐에 메시지를 넣고 그 큐가 같은 함수를 다시 부르는 구조를 만들었다. Lambda 콘솔에 순환 감지 알림이 뜨고, AWS_LAMBDA_FUNCTION_NAME 으로 어느 경로에서 출발했는지 구분해 원인을 찾는다.

#4동작 과정

  1. 감지한다함수를 부른 서비스로 다시 결과를 쓰는 구조면 순환이 생길 수 있다. recursive loop detection 은 그 흐름을 추적해 순환을 찾아 낸다.
  2. 알린다감지되면 해당 호출이 재귀 루프에 들어갔다고 알림이 뜬다. 이때 함수 상태는 Active, Inactive, Failed 로 표시된다.
  3. 멈추게 한다함수를 같은 리소스로 되돌려 보내지 않게 코드를 고치거나, 함수를 그대로 두어야 하면 이 동작을 허용하는 설정을 켠다.
  4. 확인해 볼 것Lambda 콘솔의 재귀 루프 알림 목록에 감지된 호출이 남아 있는지 확인한다.

이벤트 소스 매핑의 개념

이벤트 소스 매핑은 SQS 큐나 S3 버킷 같은 AWS 서비스가 새 이벤트를 저장할 때 그 자리를 Lambda 가 계속 확인해 함수를 자동으로 호출하도록 해 주는 설정이다.

먼저 알아야 할 것 05-02

#1문제 상황

큐나 버킷에 이벤트가 생길 때마다 누가 함수를 부를지 직접 연결해야 한다(→ 05-02). 연결 대상이 늘어날수록 이 작업이 반복된다.

event source mapping 은 이벤트 소스와 함수를 한 번만 연결해 두면 이후 호출을 Lambda 가 알아서 하게 한다.

#2핵심 질문

이벤트 소스가 새 이벤트를 저장할 때 함수를 자동으로 부르려면 어떻게 연결하는가?

#3동작 예시

운영자가 SQS 큐를 Lambda 콘솔에서 함수에 매핑으로 등록한다. 그 뒤 누군가 큐에 메시지를 넣으면 함수가 자동으로 실행되어 CloudWatch Logs 에 처리 결과가 남는다.

#4동작 과정

  1. 연결한다event source mapping 을 만들 때 이벤트 소스인 SQS·DynamoDB·Kinesis 같은 자원과 함수를 지정한다.
  2. 확인한다Lambda 안에서 도는 event poller 가 큐와 스트림을 주기적으로 뒤져 새 이벤트를 찾는다.
  3. 한 번에 건넨다polling 은 이 확인 동작이고, batch size 는 한 번에 몇 건까지 가져올지 정하는 값이다. 부분 실패가 나면 partial batch response 를 반환해 성공한 항목만 남길 수 있다.
  4. 확인해 볼 것해당 함수의 이벤트 소스 매핑 목록에 매핑이 Active 상태로 보이는지 본다.

  3. 실패한 것만 알린다일부만 성공한 묶음은 services-ddb-batchfailurereporting 응답 형식으로 실패한 레코드만 되돌려 보낸다. Powertools for AWS Lambda 의 Batch Processor 가 이 처리를 대신 해 준다.

#1문제 상황

한 함수가 트래픽을 몰아서 계정 전체의 실행 환경을 차지하면 다른 함수가 호출을 거부당한다. 계정 전체 동시성(account concurrency)만으로는 이걸 막을 수 없다. reserved concurrency 는 함수 하나에 필요한 만큼만 남겨 두는 상한이다.

#2핵심 질문

중요한 함수가 항상 실행될 자리를 남기면서 한 함수의 폭주를 어떻게 막는가?

#3동작 예시

핵심 주문 함수에 reserved concurrency 를 50으로 정한다. 이 함수가 50을 넘게 동시에 불리면 초과 요청은 throttling 이라 는 형태로 거절되고, 그만큼 다른 함수용 용량이 남는다.

#4동작 과정

  1. 상한을 정한다함수에 reserved concurrency 수를 지정한다. 이 값이 해당 함수의 maximum concurrency 가 된다.
  2. 여유를 남긴다지정한 수만큼은 그 함수만 쓰고 다른 함수는 쓸 수 없다. 하한 역할도 해서 중요 함수에 용량이 항상 붙어 있다.
  3. 초과를 막는다상한을 넘는 요청은 throttling 으로 걸러지므로 데이터베이스 연결 같은 후속 자원도 압박받지 않는다. 설정 자체에는 추가 비용이 없다.
  4. 확인해 볼 것상한을 1로 낮춘 함수를 동시에 여러 번 호출해 나머지 호출이 실패하는지 확인한다.

#3동작 예시

#4동작 과정

  4. 확인해 볼 것함수의 로그에서 단계가 끝날 때마다 남는 체크포인트 기록을 찾아 본다.

Durable function 만들기

지원 런타임과 SDK 를 골라 실행할 작업을 코드로 선언하고 배포해 Lambda 가 체크포인트와 재개를 관리하는 함수를 구성하는 절차.

먼저 알아야 할 것 08-01

#1문제 상황

Durable functions 의 개념을 알아도(→ 08-01) 실제로는 어디서부터 손대야 할지 막힌다. 어떤 런타임을 써야 하고 코드가 함수 코드 안에 어떻게 들어가는지 정해야 한다.

creating durable functions 는 그 첫 단계를 정해 주는 절차다. 코드를 함수 안에서 실행 상태와 함께 관리하는 방식이다.

#2핵심 질문

Durable function을 어떤 런타임으로 어떤 순서로 만들어 배포하는가?

#3동작 예시

시간이 지난 뒤 함수를 다시 깨우면 이전 단계 기록을 재실행해 멈췄던 지점부터 이어서 돈다.

#4동작 과정

  1. 런타임과 SDK를 고른다supported runtimes 은 Python, Node.js(JavaScript/TypeScript), Java와 컨테이너 이미지(OCI)를 지원한다.
  2. 코드에서 선언한다DurableContext 객체를 받아 steps 로 체크포인트를 만들고 waits 로 실행을 멈추는 코드를 작성한다.
  3. 배포해 확인한다콘솔 코드 편집기 또는 AWS CLI, infrastructure as code(IaC)로 함수를 만든 뒤 실행을 반복해 replay 가 동작하는지 본다.
  4. 확인해 볼 것콘솔에서 함수를 직접 실행해 단계가 실행되고 멈춘 지점이 로그에 남는지 확인한다.

Durable function 설정

Durable function 이 실행되는 실행 환경의 메모리·타임아웃·권한 같은 함수 설정과 상태를 보존하는 방식을 지정해 동작을 맞추는 것.

먼저 알아야 할 것 08-01

#1문제 상황

Durable function은 며칠씩 실행 기록을 남기고 상태를 보존해야 한다(→ 08-01). 기본 함수 설정인 메모리와 권한(→ 09-01)만으로는 그 기간을 담지 못하고, 잘못 고르면 중간에 잘려 실행이 끊긴다.

그래서 configure durable functions 단계가 실행 자체의 시간과 기록 보존 범위를 따로 정한다.

#2핵심 질문

Durable function이 얼마나 오래 돌고 상태를 얼마나 남기게 할 것인가?

#3동작 예시

개발자가 함수를 만들 때 DurableConfig에 실행 타임아웃을 3600초, 기록 보존을 30일로 지정한다. 함수가 멈춘 사이에도 실행 기록이 이 기간 동안 남아 재개 때 읽힌다.

저장된 기록을 KMS 키로 암호화해 두면 접근 권한을 따로 관리할 수 있다.

#4동작 과정

  1. 함수 생성 때 켠다durable execution 은 함수를 만들 때만 켤 수 있어 DurableConfig 객체를 생성 요청에 넣는다.
  2. 시간과 보존을 정한다execution timeout 을 정해 전체 실행이 얼마나 이어질지 정하고, RetentionPeriodInDays 로 실행 기록을 얼마나 남길지 정한다.
  3. 암호화와 권한을 붙인다KMSKeyArn 으로 기록을 암호화하고 security and permissions 를 설정한다. 재시도 동작은 retry policy 로 다룬다.
  4. 확인해 볼 것함수의 구성 화면에 DurableConfig 값이 저장되어 있는지 확인한다.

Durable functions 와 Step Functions 의 관계

Lambda 안에서 코드로 워크플로를 실행하는 Durable functions 와 별도 서비스인 AWS Step Functions 가 같은 오케스트레이션 문제를 어떻게 나눠 맡는지 비교하는 것.

먼저 알아야 할 것 08-01

#1문제 상황

여러 서비스를 순서대로 잇는 워크플로를 만들 때 두 선택지가 있다. Lambda 안에서 코드로 짜는 durable functions 와 별도 서비스인 Step Functions 다(→ 08-01).

둘 다 워크플로를 만들기 때문에 겉보기에 같다. 하지만 팀의 성격과 워크플로 범위가 다르면 선택이 갈린다.

#2핵심 질문

Lambda 안의 코드형 워크플로와 AWS 서비스 전반의 선언형 워크플로 중 언제 무엇을 쓸까?

#3동작 예시

개발팀이 Lambda 함수 안에서 주문 처리를 코드로 이어 붙인다. 별도 팀과 서비스 경계를 넘는 승인 절차는 시각으로 볼 수 있는 워크플로가 필요하다.

그래서 그 부분은 Step Functions 로 두고 함수 안의 세부 로직은 durable functions 로 처리한다.

#4동작 과정

  1. Lambda 안일 때 durable functions 를 쓴다팀이 익숙한 언어와 도구를 쓰고 실행 상태를 코드로 세밀하게 다뤄야 하는 경우다.
  2. 서비스를 넘을 때 Step Functions 를 쓴다여러 AWS 서비스를 오케스트레이션하고 팀 간에 보이는 시각 표현이 필요할 때다. AWS 서비스 연동을 코드 없이 쓴다.
  3. when to use 를 나눠 정한다함수와 워크플로의 결합이 강하고 빠르게 반복할 때는 앞을, 여러 서비스의 공식 연동을 어디서든 맞춰 쓰는 일이 많으면 뒤를 고른다.
  4. 확인해 볼 것한 워크플로에서 역할이 갈리는지 팀과 정해 보고 함수 목록과 Step Functions 목록에 각각 무엇이 잡히는지 확인한다.

Durable function 을 호출할 때 실패한 시도를 같은 실행 id 로 안전하게 다시 시도해 같은 작업이 두 번 처리되지 않게 하는 재시도·멱등성 규칙.

먼저 알아야 할 것 08-03

#1문제 상황

Durable function은 오래 걸리니 기다리는 동안 장애가 나기 쉽다(→ 08-01). 다시 부를 때 같은 주문을 두 번 처리하면 재고가 어긋난다.

그래서 invoking durable functions 가 재시도와 멱등성 규칙을 함께 정한다.

#2핵심 질문

실패한 Durably 실행을 안전하게 다시 부르면서 같은 작업을 한 번만 처리하게 하려면?

#3동작 예시

대기 중인 주문 처리가 시간 초과로 멈췄다. 운영자가 같은 실행 이름으로 함수를 다시 부르면 이력과 체크포인트가 이어져 중단된 단계부터 돈다.

결제 단계는 이미 처리된 것으로 기록되어 있어 다시 청구되지 않는다.

#4동작 과정

  1. 호출 방식을 고른다동기 호출은 응답을 기다리지만 최대 15분에 묶인다. 비동기 호출과 event source mapping 은 결과를 기다리지 않고 맡긴다.
  2. 이름으로 재시도한다execution name parameter 로 실행 이름을 지정해 같은 이름으로 다시 부르면 이미 끝난 단계를 건너뛴다.
  3. 멱등성을 지킨다idempotency 규칙에 따라 중복 부름이 두 번 처리로 이어지지 않게 하고, 되돌리기(retries)와 함께 오류를 다룬다.
  4. 확인해 볼 것CloudWatch에서 같은 실행 이름의 호출 기록이 이어져 붙는지 확인한다.

9. 권한을 나눈다 — 누가 함수를 부르고 함수는 무엇을 읽나09-01

실행 역할 — 함수가 다른 자리에 갈 때

함수를 만들 때 Lambda 가 함수 코드가 다른 AWS 서비스(예: S3 버킷, DynamoDB 테이블)에 접근할 수 있도록 주는 IAM 역할로, 함수가 호출되지 않은 다른 자리가 맡는 모든 일을 대신 수행한다.

먼저 알아야 할 것 04-01

#1문제 상황

함수 코드는 S3 버킷을 읽거나 DynamoDB 테이블에 써야 한다. 하지만 함수에는 계정 권한이 없다.

execution role 은 Lambda 가 함수를 실행할 때 대신 쓰는 IAM 역할이다. 함수에 이 역할을 붙여 주면 Lambda 가 알아서 그 역할을 AssumeRole 하고, 함수 코드는 역할이 허용한 AWS 자원에만 닿는다. CloudWatch Logs 로 로그를 보내는 권한은 AWSLambdaBasicExecutionRole 이라는 관리 정책으로 붙일 수 있고, permissions for functions to access other resources 를 추가하면 다른 자원에 대한 권한도 얹는다.

#2핵심 질문

함수가 스스로 권한을 만들지 않고도 다른 AWS 자리에 접근하게 하려면?

#3동작 예시

S3 버킷의 이미지 썸네일을 줄이는 함수를 만든다. 콘솔에서 함수를 만들 때 S3 에서 객체를 읽고 CloudWatch Logs 에 쓰는 실행 역할을 고른다. 배포한 뒤 함수가 버킷을 읽고 로그를 남기는 것이 보인다.

#4동작 과정

  1. 역할을 만든다함수가 다른 자리에 접근하게 해 줄 권한을 IAM 역할로 만든다. 함수를 호출할 때 Lambda 가 이 역할을 자동으로 AssumeRole 하므로 코드에서 직접 AssumeRole 을 부르지 않는다.
  2. 정책을 붙인다AWSLambdaBasicExecutionRole 같은 managed policies 로 로그 전송 권한을 주고, 버킷이나 테이블 접근 권한을 추가한다. 역할의 신뢰 정책에는 Lambda 서비스 주체만 신뢰 대상으로 둔다.
  3. 함수에 연결한다함수의 설정에서 이 역할을 지정한다. 이제 함수 실행 중에는 부여된 작업만 가능하다.
  4. 확인해 볼 것함수의 Configuration 탭에서 연결된 실행 역할 이름이 보이는지 확인한다.

AWS IAM 사용자·그룹·역할 같은 신원(principal)에게 어떤 함수를 호출할 수 있는지를 직접 허용하는 정책으로, 그 신분이 실행할 수 있는 AWS 동작(액션)과 대상 리소스를 조건 없이 지정해 grants 방식으로 부여한다.

먼저 알아야 할 것 09-01

#1문제 상황

배포 파이프라인에서 함수를 고쳐 올리고, 운영자가 콘솔에서 함수를 호출해야 한다. 누가 무엇을 해도 되게 열어 두면 아무나 다른 함수를 지울 수 있다.

identity-based policies 는 사용자·그룹·역할 같은 신원에 직접 붙이는 정책이다. 어떤 동작을 어떤 대상에 허용할지 직접 적는다. 호출을 허용할 때 쓰는 API 동작은 lambda:InvokeFunction 이며, access permissions 의 범위는 정책에 적은 만큼만 열린다. AWS 는 AWSLambda_FullAccess 와 AWSLambda_ReadOnlyAccess 같은 관리 정책도 제공한다.

#2핵심 질문

특정 신원에게 함수 호출 권한만 주려면 어떻게 하나?

#3동작 예시

배포 서버가 맡은 IAM 역할에 주문 처리 함수 호출 권한을 준다. 콘솔에서는 그 함수를 함수를 호출할 수 없다. 함수를 만든 뒤 저장소에서 권한을 붙인다.

#4동작 과정

  1. 신원을 정한다허용할 대상이 AWS IAM 사용자·그룹·역할 중 무엇인지 먼저 고른다. 다른 계정의 신원이라면 그 계정에서 역할을 맡도록 허용할 수도 있다.
  2. 정책을 붙인다identity policies 에 lambda:InvokeFunction 같은 동작과 대상 함수 ARN 을 적어 해당 신원에 직접 부여한다. 이 경로는 함수 쪽에 붙이지 않는다.
  3. 범위를 좁힌다AWSLambda_FullAccess 처럼 넓은 관리 정책 대신 함수 ARN 을 지정하면 바꿀 수 있는 함수만 열린다.
  4. 확인해 볼 것해당 신원으로 함수 호출을 시도해 되고, ARN 을 지정하지 않은 다른 함수는 막혀 있는지 본다.

리소스 기반 정책과 AWS 서비스 접근

함수 쪽에 붙이는 정책으로, AWS 서비스가 해당 함수를 호출하거나 다른 계정(크로스 어카운트) 및 AWS 조직 소속 계정이 함수를 호출하도록 허용해 신원 기반 정책과 반대 방향으로 접근을 부여한다.

먼저 알아야 할 것 09-02

#1문제 상황

서로 다른 회사의 서비스와 AWS 서비스가 함수를 호출해야 한다. 신원 기반 정책(→ 09-02)으로는 상대 계정 쪽 권한을 건드릴 수 없다.

resource-based policies 는 함수에 직접 붙이는 JSON 문서다. 안에 Principal, Action, Effect, Resource 를 한 문장씩 적는다. AWS service access 를 허용하면 AWS 서비스가 그 함수를 부를 수 있고, cross-account access 로 다른 AWS 계정에 열어 줄 수 있다. AWS Organizations 에 속한 계정 전체에만 허용하는 형태도 이 문서에 담는다.

#2핵심 질문

내 계정의 함수를 다른 계정이나 AWS 서비스가 부르게 하려면?

#3동작 예시

파트너 회사의 계정에서 이미지 처리 함수를 부르도록 한다. 함수에 리소스 기반 정책을 붙이고 그 계정을 주체로 지정한다. 저장하면 파트너 계정의 호출이 통과하고 다른 계정은 여전히 막힌다.

#4동작 과정

  1. 함수에 정책을 붙인다함수 쪽에 resource policy 를 추가한다. 신원 기반 정책과 반대로 대상 자원 쪽에 서 있는 정책이다.
  2. 주체와 동작을 적는다허용할 AWS 계정이나 IAM 역할, AWS 서비스를 Principal 에 두고 허용할 API 동작과 대상 함수를 Resource 에 적는다.
  3. 범위를 넓힌다AWS 조직 소속 계정 전체에 열어 주는 조건을 넣으면 계정을 하나씩 나열하지 않아도 된다.
  4. 확인해 볼 것함수의 Permissions 탭에서 붙은 리소스 기반 정책 문서가 보이는지 확인한다.

태그로 접근 막기

함수에 붙인 태그(key=value 쌍) 조건을 IAM 정책의 조건으로 참조해, 특정 태그가 붙은 함수에만 호출 권한을 주는 방식으로 권한 범위를 태그 단위로 세밀하게 제한한다.

먼저 알아야 할 것 09-02

#1문제 상황

환경별로 함수가 수백 개씩 생긴다. ARN 을 하나씩 정책에 적으면 새 함수가 생길 때마다 IAM 정책도 고쳐야 한다.

attribute-based access control 은 자원이 아니라 태그로 접근을 정하는 방식이다. 여기서 tag-based access 를 쓰면 ARN 을 적지 않고 조건에 태그만 쓸 수 있다. 조건에서 lambda:FunctionArn tag condition 으로 태그를 검사한다. ABAC 를 쓰면 새 함수에 태그만 붙여도 권한이 따라 늘어난다.

#2핵심 질문

함수 ARN 을 나열하지 않고 태그로 권한 범위를 정하려면?

#3동작 예시

운영용 함수에 env=prod 태그를 붙인다. 정책에는 prod 태그가 있는 함수만 호출하도록 조건을 넣는다. 콘솔에서 env=prod 태그가 없는 함수를 그 신원으로 부르면 거부된다.

#4동작 과정

  1. 태그를 붙인다함수에 key=value 형태의 태그를 부여한다. 코드 서명 설정처럼 태그를 쓸 수 있는 Lambda 자원은 정해져 있다.
  2. 조건에 태그를 적는다IAM 정책의 조건 요소에서 태그 키와 값을 지정해 접근을 가른다. ARN이나 ARN 패턴을 적지 않아도 된다.
  3. 새 함수에 태그만 추가한다이후 새로 만드는 함수에는 태그만 붙이면 정책 수정 없이 권한이 따라온다.
  4. 확인해 볼 것함수의 태그 목록에 조건에서 참조한 키와 값이 실제로 붙어 있는지 확인한다.

테넌트 격리

같은 Lambda 계정 안에 여러 사용자나 조직(테넌트)의 함수가 함께 있을 때, 함수 목록 조회나 호출 요청에서 한 테넌트의 함수가 다른 테넌트에게 보이지 않도록 격리하는 기능이다.

먼저 알아야 할 것 09-02

#1문제 상황

SaaS 플랫폼에서 여러 고객의 코드를 같은 AWS 계정의 Lambda 로 돌린다. 호출이 섞이면 한 고객의 요청이 다른 고객을 위해 만들어진 실행 환경에서 실행될 수 있다.

tenant isolation 을 켜면 Lambda 는 요청마다 고객이 정한 tenant identifier 를 읽어 그 값을 요청에 붙이고, 해당 테넌트를 위한 실행 환경만 찾아 그 안에서 함수를 돌린다. 즉 multi-tenant 구성에서 실행 환경 격리가 필요할 때 쓰는 방식이다. 실행 환경 자체는 Firecracker virtualization 기반 격리로 이미 나뉘어 있고, 여기에 테넌트 context 가 한 겹 더 얹혀진다.

#2핵심 질문

여러 고객의 코드를 같은 Lambda 계정에서 서로 섞이지 않게 돌리려면?

#3동작 예시

Workflow 자동화 SaaS 에서 고객 A 와 B 가 각자 코드를 등록한다. 함수를 테넌트 격리 모드로 두고 호출 요청에 고객 식별자를 실어 보낸다. 고객 A 호출과 고객 B 호출이 서로 다른 테넌트의 실행 환경에서 실행된 것이 함수 로그의 요청 항목에서 구분된다.

#4동작 과정

  1. 테넌트를 정한다호출을 보낼 때 어떤 고객의 호출인지 tenant identifier 로 지정한다. 함수 코드가 아니라 호출 요청 쪽에서 붙인다.
  2. 요청을 라우팅한다Lambda 는 그 식별자에 해당하는 실행 환경만 찾아 그 안에서 함수를 돌린다. 다른 테넌트 요청은 같은 환경을 쓰지 않는다.
  3. 격리를 유지한다실행 환경은 Firecracker virtualization 기반 격리 위에 tenancy 가 얹힌 구조라 테넌트별 분리 요구를 함께 만족한다.
  4. 확인해 볼 것함수를 목록에 띄워 두 tenant isolation 상태가 켜져 있는지 확인한다.

→ 10-05 참조

#1문제 상황

서버가 없으니 서버 계정을 열 수 없다. 함수가 아파 보이는지 판단하려면 실행 결과 숫자만 알아야 한다.

function metrics 는 Lambda 가 직접 집계해 CloudWatch 로 보내는 값이다. 호출이 들어올 때마다 invocations 와 errors, duration 이 쌓인다. 함수 호출 지표는 성공·실패를 0과 1로 찍는 이진 지표라 Sum 으로 1분 단위로 합쳐 세는 방식이 기본이다. 성능 지표와 동시성 지표, 비동기 호출 지표, 배포 지표도 같은 방식으로 나뉜 metric types 다.

#2핵심 질문

서버 없이 함수 상태를 숫자로 어떻게 살필까?

#3동작 예시

Lambda 콘솔에서 함수의 Monitor 탭을 연다. invocations 그래프가 갑자기 솟고 errors 도 같이 올라간다. duration 그래프도 평소보다 길다. 서버에 접속할 수 없어도 여기서 실패가 늘었는지 알 수 있다.

#4동작 과정

  1. 집계한다Lambda 는 호출마다 호출 횟수와 오류 여부, 실행에 걸린 시간을 센다. 호출 자체가 실패하거나 스로틀링된 경우는 호출 횟수에 세지 않는다.
  2. 분류해 보낸다이 값들은 호출 지표, 성능 지표, 동시성 지표, 배포 지표, 비동기 호출 지표, 이벤트 소스 매핑 지표로 나뉘어 CloudWatch 로 보낸다.
  3. 읽어 낸다errors 는 호출당 1 로 찍히므로 1분 주기의 Sum 으로 합쳐 그 분에 몇 번 실패했는지 본다.
  4. 확인해 볼 것함수 Monitor 탭에서 invocations 와 errors 그래프가 시간순으로 그려지는지 확인한다.

로그 — 표준 출력과 CloudWatch Logs

함수 코드에서 표준 출력으로 출력한 문자열이 자동으로 CloudWatch Logs 의 해당 로그 그룹에 저장되는 구조로, 서버를 직접 볼 수 없는 Lambda 환경에서 코드가 실제로 한 일을 남기는 유일한 기록이다.

먼저 알아야 할 것 10-01

→ 10-03 참조

#1문제 상황

서버가 없는 Lambda 에서는 콘솔에 접속할 자리가 없다. 코드가 실제로 무슨 일을 했는지 남는 곳이 없다면 실패한 호출의 원인을 찾을 수 없다.

로그는 함수 코드가 표준 출력으로 출력한 문자열을 Lambda 가 CloudWatch Logs 에 자동 저장하는 기능이다. 기본적으로 /aws/lambda/<function-name> 라는 이름의 로그 그룹에 쌓이며, 필요하면 다른 로그 그룹으로 보낼 수도 있다.

#2핵심 질문

돌아가지 않는 함수 안에서 코드가 한 일을 어떻게 남겨 두는가?

#3동작 예시

결제 함수가 주문을 처리하다 실패했다. CloudWatch 콘솔에서 해당 로그 그룹을 열어 마지막 요청의 request id 를 찾고, 그 뒤에 이어지는 로그 줄에서 어떤 값이 비어 있었는지 본다.

#4동작 과정

  1. 남긴다함수가 표준 출력으로 쓴 문자열이 function logs, 즉 호출별 실행 기록이 되어 CloudWatch Logs 로 올라간다. 기본 도착지는 /aws/lambda/<function-name> 로그 그룹이다.
  2. 거른다log-level filtering 으로 정한 등급보다 낮은 로그는 저장하지 않는다. debug 같은 말을 남기면 디버깅에 쓸 수 있다.
  3. 보낸다로그가 많은 경우 Firehose 로 다른 저장소로 넘길 수 있다. 한 건의 호출을 이으는 request id 로 여러 줄을 묶어 볼 수 있다.

Managed Instances 는 현재 세대의 Amazon EC2 인스턴트에서 함수를 돌리면서 인스턴스 수명 관리와 패치, 라우팅, 부하 분산, 스케일링 정책은 Lambda 가 맡는 방식이다.

  1. 선택한다Managed Instances 를 컴퓨트 방식으로 고르고 인스턴스 계열을 정한다. 전용 instance 를 다루지 않고 capacity providers 로 필요한 만큼 늘린다.

  4. 확인해 볼 것Lambda 콘솔에서 함수의 컴퓨트 방식이 Managed Instances 로 표시되는지 본다.

#1문제 상황

Managed Instances 는 scaling 신호를 보고 비동기로 늘린다. 용량을 미리 마련해 둘 위치인 capacity providers 와 그 배정을 열쇠로 쓰는 operator role 이 붙는다.

#2핵심 질문

#4동작 과정

  1. 늘릴 신호를 본다CPU 사용량과 실행 환경의 동시성 포화로 scaling 을 시작한다. 일반 Lambda 와 달리 늘림이 요청과 무관하게 먼저 일어난다.
  2. 자리를 나눠 건다capacity providers 가 실행 환경의 보안 경계이자 배치 기준이다. 어떤 함수 집합을 어디에 둘지 여기서 정한다.

→ 11-02 참조

#1문제 상황

Managed Instances 안에서 함수는 컨테이너로 실행되지만, 컨테이너는 워크로드 사이의 보안 경계가 되지 못한다(→ 01-02). 같은 인스턴스에 놓인 함수들은 서로 신뢰할 수 있다고 봐야 한다.

그래서 신뢰할 수 없는 워크로드는 다른 capacity provider 로 떼어 내야 한다.

#2핵심 질문

서로 믿을 수 없는 함수를 Managed Instances 안에서 어떻게 나눠 놓는가?

#3동작 예시

#4동작 과정

  1. 경계를 나눈다capacity provider 를 신뢰 수준이 갈리는 경계로 삼고, 서로 믿을 수 없는 워크로드는 다른 provider 에 둔다. 함수를 그곳에 놓을 권한인 lambda:PassCapacityProvider 를 계정 관리자가 허용한 신분에게만 주는 것이 안전장치다.
  2. 네트워크를 긋는다networking 설정으로 환경이 어느 서브넷과 경로를 쓰는지 정해 다른 곳에서 임의로 붙지 못하게 한다.
  3. 관측을 붙인다CloudWatch Logs 에 남는 system logs 와 metrics 로 함수 상태와 환경 이상을 살핀다.
  4. 확인해 볼 것함수 배치 화면에서 capacity provider 를 바꿨을 때 권한 오류가 어떤 메시지로 뜨는지 본다.

MicroVM — 마이크로 가상머신으로 함수 돌리기

MicroVM 은 Lambda 가 함수 하나를 돌릴 때 사용하는 가벼운 가상머신 단위의 실행 환경으로, 손님 수준 격리를 유지하면서 여러 시간짜리 워크로드도 다룰 수 있게 해 준다.

먼저 알아야 할 것 11-01

#1문제 상황

Managed Instances 는 컨테이너를 나눠 쓰기 때문에 오래 도는 워크로드마다 격리를 세울 수 없다(→ 11-03). 여러 시간 걸리는 작업을 서로 보이는 환경에 두게 된다.

MicroVM 은 테넌트 하나마다 별도의 가상머신 자원을 만들어 이 문제를 없앤다.

#2핵심 질문

MicroVM 은 무엇을 담는 자원이고 언제 멈췄다가 다시 뜨는가?

#3동작 예시

긴 보고서 작업 하나를 MicroVM 에서 돌린다. 인바운드 HTTPS 로 요청이 들어오고 유휴가 되면 suspend 되며, 메모리와 디스크 상태가 남은 채 트래픽이 돌아오면 그 상태에서 곧바로 이어진다.

#4동작 과정

  1. 자원을 받는다MicroVM 은 단일 테넌트·사용자 세션·작업 하나를 위한 격리된 컴퓨트 자원이고, 안에는 Amazon Linux 2023 이 돈다.
  2. 이미지를 만든다microVM image 가 실행 환경을 정의하고, Lambda 가 이 이미지에서 스냅샷을 떠서 만들 때 거의 즉시 시작할 수 있다.
  3. 실행 주기를 돈다launching MicroVMs 단계로 시작해 유휴일 때 suspend 되고, 트래픽이 오면 그 지점에서 resume 된다.
  4. 확인해 볼 것MicroVM 목록에서 유휴 상태로 남은 자원이 suspend 상태로 표시되는지 본다.

→ 11-04 참조

#1문제 상황

실행 환경마다 코드를 따로 올리면 환경이 조금씩 달라지고 시작이 느려진다(→ 11-04). 같은 환경으로 시작하기 위해 무엇을 어디에 올려야 하는지 정해져 있지 않다.

MicroVM Images 가 그 환경 그 자체를 하나의 리소스로 만든다.

#2핵심 질문

실행 환경을 고정해 두고 재사용하려면 무엇을 어디에 올려야 하는가?

#3동작 예시

Dockerfile 과 애플리케이션 산출물을 zip 으로 묶어 S3 에 올리고 MicroVM image 를 만든다. Lambda 가 Lambda-managed MicroVM base image 위에 Dockerfile 을 실행해 컨테이너 이미지를 만들고 스냅샷으로 저장한다. base image 를 갱신할 때마다 새 버전이 생긴다.

#4동작 과정

  1. 묶어 올린다Dockerfile 과 앱 산출물이 든 zip 패키지를 Amazon S3 에 올려 이미지 정의를 시작한다. 이 정의를 MicroVM Images 라고 한다.
  2. 만들어 저장한다Lambda-managed MicroVM base image 위에서 Dockerfile 을 실행해 컨테이너 이미지를 만들고 snapshots 로 저장해 재사용한다.
  3. 보안과 연동을 정한다security 설정과 integrations 의 networking 을 지정해 환경의 접근 범위를 좁히고, 갱신할 때마다 새 버전으로 나눈다.
  4. 확인해 볼 것이미지 목록에서 갱신 전후로 새 버전이 하나씩 늘었는지 확인한다.
