Amazon ECS

Amazon ECS = AWS 가 완전히 관리해 주는 컨테이너 오케스트레이션 서비스. 컨테이너 워크로드를 클러스터·태스크 정의·태스크·서비스 네 객체로 기술하고, 그 태스크를 Fargate·EC2·Managed Instances·ECS Anywhere 네 가지 용량 위에 올리는 방법까지 다루는 것으로 해석했다. 입문 교과서이므로 '무엇을 어디에 올리는가 → 어떻게 선언하고 배치하는가 → 트래픽과 스케일을 어떻게 다루는가 → 어떻게 보고 고치는가' 순으로 배열했다.

Amazon ECS 란 무엇인가 — 완전 관리형 컨테이너 오케스트레이션

컨테이너(앱과 그 실행 환경을 묶은 표준 단위)를 원하는 수만큼 실행하고healthy 상태를 유지하며 스케일까지 대신해 주는 AWS의 완전 관리형 오케스트레이션 서비스로, 서버를 직접 관리하지 않고 컨테이너 배치와 운영만 다룰 수 있게 해 준다.

#1문제 상황

앱과 그 실행 환경을 묶어 배포하는 단위는 컨테이너다(→ 01-02). 하지만 컨테이너를 서버에 직접 올리면 서버마다 상태가 달라지고, 장애 난 컨테이너를 사람이 다시 띄워야 하며, 수량 조절도 수작업이 된다.

Amazon Elastic Container Service, 즉 Amazon ECS는 fully managed container orchestration, 즉 컨테이너 오케스트레이션을 AWS가 전부 수행하는 서비스다. 사용자는 실행할 앱만 알면 되고 서버 환경은 관리하지 않는다.

#2핵심 질문

컨테이너를 서버 환경 관리 없이 실행하고 수량까지 조절하려면 어떻게 해야 하는가?

#3동작 예시

개발자가 앱 이미지를 등록하고 실행할 개수를 정해 요청한다. AWS가 정해진 수만큼 컨테이너를 띄우고health 상태가 나쁜 것을 교체한다.

트래픽이 몰리면 컨테이너가 알아서 늘어난다. Amazon Elastic Container Registry에 이미지를 두면 함께 쓰기 편하고, Docker 같은 서드파티 도구와도 붙는다.

#4동작 과정

  1. 등록한다컨테이너 이미지를 저장소에 두고 실행 조건을 정의한다. ECS는 control plane, 즉 어떤 태스크를 어디에 띄울지 결정하는 부분을 사용자가 직접 관리하지 않는다.
  2. 실행한다요청한 수만큼 컨테이너를 시작하고 상태를 살핀다. AWS 리전에 있는 클라우드 환경뿐 아니라 온프레미스에서도 같은 방식으로 확장할 수 있다.
  3. 확인해 볼 것콘솔의 클러스터 목록에서 클러스터 하나를 고르고 그 안의 실행 중인 태스크 수를 본다.

#5한 줄 요약

Capacity·Controller·Provisioning 세 계층

ECS 는 용량을 어디에 둘지(Capacity: Fargate·EC2 등), 어떤 방식(Controller: 태스크나 서비스)으로 배치할지, 그 자리를 누가 준비할지(Provisioning: 수동 등록·Autoscaling·Spot 등)를 서로 분리된 세 층으로 나눠 선택하게 한다.

먼저 알아야 할 것 01-01

#1문제 상황

컨테이너는 코드가 아니라 read-only template인 이미지로 빌드해 registry에 저장한 뒤 실행해야 한다(→ 01-01). 문제는 그 이미지를 어떤 컴퓨터 위에서 돌릴지, 한 번만 띄울지 계속 유지할지, 그 컴퓨터는 누가 준비할지가 한 덩어리로 엮여 있다.

ECS는 이 갈래를 capacity 계층, controller 계층, provisioning 계층으로 분리한다. container가 실제로 실행되는 인프라를 어디까지 AWS가 맡을지 정할 수 있다.

#2핵심 질문

실행 인프라 선택과 실행 방식, 인프라 준비 주체를 어떻게 분리해 고를 수 있는가?

#3동작 예시

팀이 웹 서버를 만들 때 capacity 계층에서 서버리스 환경 하나를 고른다. controller 계층에서 장시간 도는 서비스 방식을 고르면 원하는 개수만큼 계속 떠 있다.

provisioning 계층에서 capacity를 자동 확보하는 방식을 고르면, 인스턴스 증설을 직접 하지 않아도 태스크가 자리에 놓인다. Amazon ECS scheduler가 어떤 서버에 어느 태스크를 올릴지 정한다.

#4동작 과정

  1. 인frastructure를 고른다capacity 계층에서 container가 실제로 실행되는 인프라를 정한다. 서버를 직접 챙기는 쪽과 AWS가 맡는 쪽을 나눠 고른다.
  2. 방식을 고른다controller 계층에서 태스크로 한 번 실행할지 서비스로 유지할지 정한다. 이 선택이 실행 시간과 유지 방식을 바꾼다.
  3. 확인해 볼 것태스크 정의 화면에서 선택한 capacity 관련 항목이 어떤 값으로 채워져 있는지 확인한다.

#5한 줄 요약

Capacity·Controller·Provisioning 세 계층실행 위치와 실행 방식과 인프라 준비 주체를 분리해 각각 고르게 하는 것

태스크와 서비스를 묶어 담는 컨테이너의 논리적 경계로, 하나의 클러스터 안에서 계정 오버라이드 같은 공통 설정을 적용하고 자원을 격리해 관리 단위로 삼는다.

먼저 알아야 할 것 01-02

#1문제 상황

여러 팀이 하나의 AWS 계정에서 컨테이너를 실행하면 설정과 권한 관리가 한 덩어리로 섞인다(→ 01-01). 무엇이 어느 팀 것인지 경계가 없으면 계정 설정을 바꿀 때 영향 범위를 알 수 없다.

cluster는 태스크와 서비스를 담는 논리적 경계다. 클러스터마다 인프라 유형을 정하고 account setting을 갈아 끼울 수 있다.

#2핵심 질문

여러 컨테이너 묶음을 서로 다른 설정과 통제 아래 분리하려면 어떻게 해야 하는가?

#3동작 예시

운영팀과 데이터팀이 서로 다른 cluster를 만들어 각각 다른 인프라 유형을 고른다. 데이터팀 쪽에 account setting을 바꾸면 데이터팀 클러스터에만 적용된다.

cluster를 만들 때 clusterArn이 함께 만들어진다. 이 식별자로 태스크와 서비스가 어느 클러스터 소속인지 콘솔에서 구분된다.

#4동작 과정

  1. 경계를 만든다cluster 안에서 실행할 인프라 유형을 고른다. Amazon ECS Managed Instances, Fargate Serverless, 온프레미스용 유형이 있다.
  2. 규칙을 적용한다cluster 기본 동작을 정한다. account setting으로 관리되는 기본 클러스터는 계정 수준 설정을 그대로 따른다.
  3. 확인해 볼 것콘솔의 클러스터 목록에서 각 클러스터의 상태와 소속 계정 기본값을 비교한다.

#5한 줄 요약

클러스터태스크와 서비스를 담는 논리적 경계로 공통 설정을 한 덩어리로 적용하게 하는 것

태스크 정의 — 실행할 애플리케이션의 설계도

실행할 컨테이너 이미지·CPU와 메모리·환경변수·네트워크·로그·IAM 역할 같은 실행 조건을 서술한 설계도로, 이 정의를 바탕으로 ECS 가 실제 컨테이너 묶음인 태스크를 시작한다.

먼저 알아야 할 것 01-02

#1문제 상황

컨테이너 이미지를 만들었다고 실행되지는 않는다(→ 01-02). 어떤 서버 위에서 어느 이미지이고, 메모리를 얼마나 잡고, 어떤 네트워크와 로그 설정을 쓸지 정해야 한다.

task definition은 그 조건을 적은 JSON 설계도다. 이 설계도를 먼저 등록해야 실제 컨테이너 묶음인 태스크가 시작된다.

#2핵심 질문

실행에 필요한 모든 조건을 미리 정해 두고 반복해서 재사용하려면 어떻게 기록해야 하는가?

#3동작 예시

개발자가 이미지 이름, 태스크당 CPU와 메모리, Docker networking mode, 로깅 설정, IAM role을 적은 task definition을 등록한다.

태스크를 시작할 때 이 정치를 읽는다. 고칠 때는 새 정의를 쓰고 task definition revision라는 새 번호가 붙는다.

#4동작 과정

  1. 설계도를 등록한다task definition을 JSON으로 적어 컨테이너 수와 이미지, CPU·메모리, 네트워크 모드, 로그 설정, IAM role을 명시한다. 실행 인프라를 쓰는 지정도 여기에 들어간다.
  2. 버전으로 쌓는다정의를 고치면 task definition revision이 늘어난다. 과거 태스크는 등록 당시의 정치를 그대로 쓴다.
  3. 확인해 볼 것콘솔의 태스크 정의 화면에서 family 이름 아래 revision 목록이 쌓이는지 확인한다.

#5한 줄 요약

태스크 정의실행에 필요한 모든 조건을 JSON 설계도로 남겨 태스크를 반복해서 같은 모양으로 띄우게 하는 것

태스크와 서비스 — 한 번 끝나는 작업과 계속 도는 작업

태스크는 지정한 태스크 정의로 컨테이너를 한 번 실행하는 단위이고, 서비스는 원하는 태스크 수를 계속 유지해 주는 단위로, 배치 후 유지가 필요 없는 작업과 웹 서버처럼 계속 떠 있어야 하는 작업을 같은 방식으로 다룰 수 있게 구분해 준다.

먼저 알아야 할 것 01-04

→ 01-04 참조

#1문제 상황

컨테이너를 띄워 놓는다고 다 같은 상황이 아니다(→ 01-04). 야간 배치는 끝나면 사라져야 하고 웹 서버는 늘어난 개수만큼 계속 떠 있어야 한다.

task는 한 번 실행하는 단위, service는 desired count라는 원하는 태스크 수를 유지하는 단위다. 양쪽 모두 cluster 안에서 함께 관리된다.

#2핵심 질문

한 번만 도는 작업과 계속 유지해야 하는 작업을 어떻게 구분해 실행할 수 있는가?

#3동작 예시

배치 작업을 태스크로 실행하면 PENDING에서 RUNNING을 거쳐 STOPPED로 끝난다. 웹 서버는 서비스로 만들어 두면 컨테이너 하나가 죽어도 다른 것이 대신 자리를 찬다.

desired count를 바꾸면 컨테이너 agent가 상태 변화를 lastStatus와 desiredStatus로 좇는다.

#4동작 과정

  1. 태스크로 실행한다task는 배치 작업 형태로 지정한 태스크 정의로 컨테이너 묶음을 한 번 띄운다. 상태가 PROVISIONING을 거쳐 STOPPED까지 진행되며 다시 시작되지 않는다.
  2. 서비스로 유지한다service는 장시간 무상태 애플리케이션 형태로 desired count만큼 태스크를 계속 띄운다. 한 태스크가 죽으면 같은 수를 되돌려 놓는다.
  3. 확인해 볼 것콘솔에서 태스크 하나의 상태 변화를 보고 서비스의 태스크 목록이 desired count와 같은 수인지 확인한다.

#5한 줄 요약

태스크와 서비스한 번 끝나는 작업과 계속 유지할 태스크 수를 두 실행 단위로 나누는 것

계정 설정과 프로비저닝 수단 — 기능을 켜고 리소스를 만든다

먼저 알아야 할 것 01-03

#1문제 상황

ECS를 처음 쓰면 태스크 실행에 필요한 IAM 역할과 VPC 로깅 같은 기능이 꺼져 있다(→ 01-01). 기능을 계정 단위로 켜 두고 리소스도 원하는 수단으로 만들어야 태스크가 붙는다.

account settings가 이 역할을 맡는다. 여기서 바꾼 값은 태스크 정의의 기본값에도 영향을 준다.

#2핵심 질문

ECS 기능을 계정 수준에서 켜 두고 리소스를 여러 수단 중 원하는 곳에서 만들려면 어떻게 하나?

#3동작 예시

관리자가 AWS Management Console의 account settings에서 기능을 켠다. containerInsights를 켜면 지표 수집이 켜지고 tagResourceAuthorization를 조정하면 태그 조회를 누가 할지 정해진다.

이후 리소스는 AWS Command Line Interface나 AWS SDKs, AWS CDK 같은 수단으로 만든다. AWS CloudFormation 템플릿으로도 같은 구조를 코드로 적을 수 있다.

#4동작 과정

  1. 기능을 켠다account settings에서 리전별로 기능을 켜거나 끈다. 여기서 정한 값이 태스크 정의의 기본값으로 쓰인다.
  2. 수단을 고른다리소스 생성은 AWS Management Console, AWS Command Line Interface, AWS SDKs, AWS CDK, AWS CloudFormation 중 하나로 한다.
  3. 확인해 볼 것콘솔의 account settings 화면에서 켜 둔 항목이 계정 수준으로 표시되는지 확인한다.

실행 환경 선택 — 컨테이너가 올라갈 곳02-01

네 가지 실행 환경 비교와 launchType·capacity provider 선택

태스크(컨테이너 묶음)를 어디에 돌릴지 정하는 일로, EC2 인스턴스·Fargate·Managed Instances·ECS Anywhere 네 가지 launchType의 차이와 각 환경의 비용·운영 책임·확장 방식의trade-off를 비교한 뒤 용량 공급 방식(capacity provider)을 고르는 기준.

먼저 알아야 할 것 01-05

#1문제 상황

서비스로 유지할 태스크 수를 정했으면(→ 01-05) 그 태스크를 어느 컴퓨터 위에 띄울지 남는다. 서버를 직접 관리하는 쪽과 AWS가 맡는 쪽은 운영 부담과 비용 구조가 다르다.

launchType은 EC2, FARGATE, EXTERNAL, MANAGED_INSTANCES 네 가지를 고를 수 있다. capacity provider는 FARGATE와 FARGATE_SPOT 같은 선택지를 더 세분화한다.

#2핵심 질문

태스크를 돌릴 실행 환경과 용량 공급 방식을 무엇을 기준으로 고르며, 둘 중 무엇을 선택해야 하는가?

#3동작 예시

팀이 서버 없이 돌릴 수 있는 환경을 원해 capacityProviderStrategy에 FARGATE를 넣는다. 남는 용량을 싸게 쓰고 싶다면 FARGATE_SPOT을 섞는다.

서버를 직접 다루는 여유가 있으면 EC2나 MANAGED_INSTANCES를 고른다. AWS는 capacity provider를 launchType보다 권장한다.

#4동작 과정

  1. 비교한다launchType 네 가지의 차이를 본다. 서버를 직접 챙기는 선택은 운영 자유도가 높지만 준비할 일이 남는다.
  2. 공급 방식을 정한다capacity provider는 FARGATE, FARGATE_SPOT, Auto Scaling group 기반 EC2, Amazon ECS Managed Instances를 공급한다. capacityProviderStrategy에 조합해 쓴다.
  3. 확인해 볼 것콘솔에서 태스크를 실행할 때 선택 목록에 어떤 launchType이 뜨는지 확인한다.

2단계 실행 환경 선택 — 컨테이너가 올라갈 곳

EC2 인스턴스를 직접 관리하지 않고 태스크 정의에 지정한 CPU·메모리만 빌려 컨테이너를 실행하는 서버리스 방식의 컴퓨트 엔진으로, 인스턴스 운영·패치·스케일링을 AWS 가 대신 맡는다.

먼저 알아야 할 것 02-01

#1문제 상황

기존에는 컨테이너를 돌릴 가상 컴퓨터 묶음을 직접 만들고 서버 종류와 규모, 스케일 시점을 손으로 정해야 했다. 실행할 때마다 운영체제 패치와 용량 계획까지 올라오는 몫이었다.

AWS Fargate는 이 단계를 없앤 serverless 컴퓨트 엔진이다. 어떤 서버에 붙일지, 몇 대를 준비할지 정하지 않고 CPU와 메모리만 선언하면 컨테이너가 실행된다. 비용은 pay-as-you-go 과금으로 사용한 만큼 붙는다.

#2핵심 질문

서버를 미리 준비하지 않고 필요한 만큼만 빌려 컨테이너를 실행할 수 있을까?

#3동작 예시

개발자는 이미지 이름과 CPU·메모리 값, 네트워크와 IAM 정책만 태스크 정의에 적는다. 그러면 그 태스크가 실행된 상태가 콘솔의 태스크 목록에 바로 뜬다.

화면에는 어느 인스턴스에 붙었는지가 아니라 실행 중인 태스크와 그 상태만 보인다.

#4동작 과정

  1. CPU와 메모리를 선언한다태스크 정의에 cpu와 memory를 적는다. 서버 종류나 클러스터 크기를 고르는 일은 없어진다. 태스크 정의의 requiresCompatibilities에 FARGATE를 넣으면 이 방식으로 실행된다.

#3동작 예시

세 컨테이너로 이루어진 태스크에서 task cpu와 task memory를 먼저 정한다. 그다음 각 컨테이너의 cpu와 memory 값이 그 안에 배분되어 들어간다. 하드 한도와 소프트 한도가 다르게 적용되어 정해진 범위에서만 늘어난다.

#4동작 과정

  1. 총량을 정한다태스크 수준의 cpu와 memory를 선언한다. 이것이 태스크 크기를 가른다.
  2. 컨테이너에 나눠 준다containerDefinitions 안의 cpu와 memory로 배분한다. 컨테이너 수준 자원 제한은 이 범위를 넘지 못한다.
  3. 확인해 볼 것태스크 정의 편집 화면에서 태스크 총량과 컨테이너별 값이 함께 보이는지 본다.

#5한 줄 요약

cpu와 memory 할당태스크 총량을 먼저 정하고 컨테이너 안에 나눠 주는 것

이미지·시작 명령·환경변수·시크릿 주입

컨테이너 정의의 image·command·entryPoint·environment·secrets 필드로 어떤 이미지를 어느 명령으로 띄우고 어떤 환경변수와 비밀값을 받을지 선언하며, 비밀값은 평문이 아니라 Secrets Manager 나 SSM Parameter Store 에서 런타임에 조회해 주입할 수 있다.

먼저 알아야 할 것 03-01

#1문제 상황

컨테이너는 같은 이미지를 이름만 바꿔 여러 앱으로 복사해 쓰기 쉽다. 그래서 실행에 필요한 값이 이미지마다 다르게 굳어 있다. 배포마다 이미지를 다시Bake해야 한다.

태스크 정의의 image·command·entryPoint·environment·secrets 필드는 실행 particulars를 이미지 밖에서 선언한다. 이미지를 안 만들고도 시작 명령과 환경변수를 바꿀 수 있다. 비 AWS 컨테이너 이미지도 그대로 올린다.

#2핵심 질문

어떤 이미지를 어느 명령으로 띄우고 어떤 환경변수를 받을지 어디에 선언할까?

#3동작 예시

결제 앱이 새 DB 주소를 받아야 한다. 태스크 정의의 image를 고정한 채 environment에 새 주소를 넣고 배포한다. 새 태스크가 그 주소로 기동되며 코드는 수정하지 않는다.

DB 비밀번호는 secrets로 넣는다. 태스크가 뜨면 Amazon ECS가 비밀값을 찾아 컨테이너에 전달한다.

#4동작 과정

  1. 선택한다image로 베이스 이미지를 고르고 command와 entryPoint로 실행 인자를 정한다. entryPoint는 프로그램이 시작될 때 가장 먼저 받는 인자다. 비 AWS 컨테이너 이미지도 여기서 지정한다.
  2. 넘긴다environment에 환경변수 이름과 값을 적는다. 이 값은 태스크 정의를 볼 수 있는 모든 주체에게 보인다. 값이 많으면 environmentFiles로 Amazon S3에 있는 파일을 통째로 읽어 넣는다.
  3. 보관한다secrets에 비밀값의 이름만 적는다. Amazon Secrets Manager나 AWS Systems Manager Parameter Store에서 런타임에 조회해 주입한다. 평문 비밀값은 태스크 정의에 남지 않는다.
  4. 확인해 볼 것태스크 상세에서 컨테이너의 환경변수 목록에 적은 이름과 값이 보이는지 확인한다.

컨테이너 간 의존성과 재시작 정책

container dependency 는 특정 컨테이너이 HEALTHY 상태(정상 판정)를 되기 전까지 뒤의 컨테이너를 시작하지 못하게 만들며, 재시작 정책(restartPolicy) 은 실패한 컨테이너를 어떤 조건과 횟수만큼 다시 띄울지 정한다.

먼저 알아야 할 것 03-03

#1문제 상황

한 태스크 안에는 웹 서버와 데이터 수집기 같은 여러 컨테이너가 같이 오른다. 순서를 모르면 수집기가 필요한 파일을 못 만든다. 그리고 컨테이너 하나가 죽었을 때 태스크 전체를 버리면 낭비가 크다.

dependsOn으로 컨테이너 시작 순서를 잡고 restartPolicy로 재시도를 정한다. 정상 종료는 재시작 대상에서 빼고, essential로 태스크에 필수인 컨테이너를 표시해 한쪽만 복구되게 한다.

#2핵심 질문

컨테이너를 어떤 순서로 띄우고 죽으면 언제 다시 띄울까?

#3동작 예시

웹 서버와 로거가 든 태스크에서 로거를 웹 서버 뒤에 둔다. 로거의 health check가 통과되어야 웹 서버가 시작된다. 그러면 웹 서버는 항상 로거가 붙은 상태로 올라간다.

웹 서버가 오류로 죽으면 태스크를 갈아타는 대신 그 컨테이너만 다시 뜬다.

#4동작 과정

  1. 순서를 정한다dependsOn으로 앞 컨테이너를 지정한다. 앞 컨테이너가 HEALTHY 상태, 즉 점검에서 정상으로 판정된 뒤에야 뒤 컨테이너가 시작된다.
  2. 필수를 표시한다essential인 컨테이너는 그 하나가 실패하면 태스크 전체가 종료된다. 비필수 컨테이너만 재시작 정책으로 따로 살릴 수 있다.
  3. 재시작을 정한다restartPolicy로 재시작할 횟수와 startTimeout, 다시 띄우지 않을 종료 코드를 정한다. 성공 종료 코드 0은 기본적으로 재시작 대상이 아니다.
  4. 확인해 볼 것태스크 상세의 컨테이너 목록에서 의존한 컨테이너가 HEALTHY가 된 뒤에 뒤 컨테이너가 시작되었는지 확인한다.

#5한 줄 요약

컨테이너 간 의존성과 재시작 정책컨테이너별 시작 순서와 실패 복구 범위를 태스크 정의에서 정하는 것

특수 워크로드 태스크 정의 — GPU·ARM·Neuron·비디오 트랜스코딩

GPU 를 붙인 태스크는 리전과 스케줄러 제약을 함께 지켜야 하고, ARM64 아키텍처·AWS Inferentia(Trainium/Neuron) 가속기·Elastic Transcoder 같은 전용 하드웨어는 해당 리소스를 지원하는 인스턴스 유형이나 Fargate 조합에서만 실행된다.

먼저 알아야 할 것 03-02

#1문제 상황

범용 인스턴스에 어떤 태스크든 올리면 된다. 하지만 GPU workload나 deep learning instance, 비디오 트랜스코딩 태스크 정의는 필요한 칩이 인스턴스에 실제로 있어야 실행된다. 태스크 정의만 고쳐서는 자리가 없어서 실패한다.

GPU workload는 태스크 정의에서 GPU 개수를 지정한다. ECS는 그 수를 받을 인스턴스를 찾아 고르고 GPU를 컨테이너에 고정한다. ARM64 아키텍처와 AWS Neuron도 같은 방식으로 런타임 플랫폼과 리전을 맞춰 둔다.

#2핵심 질문

특수 하드웨어가 필요한 태스크를 어떤 자리에 올릴까?

#3동작 예시

모델 학습 태스크 정의에 GPU 개수를 2로 지정한다. 태스크를 올리면 GPU가 붙은 인스턴스로만 스케줄링되고 그 GPU가 해당 컨테이너에 할당된다.

리전에 GPU 인스턴스가 없으면 태스크는 자리 확보를 기다린다. 인스턴스 유형 목록에서 AWS Neuron을 지원하는 유형을 골라 같은 방식으로 지정할 수 있다.

#4동작 과정

  1. 요구량을 적는다태스크 정의에서 컨테이너별로 필요한 GPU 개수를 지정한다. GPU workload는 이 값이 배치 검토에 쓰인다.
  2. 자리를 고른다ECS는 GPU를 가진 컨테이너 인스턴스만 찾고 물리 GPU를 컨테이너에 고정한다. GPU-optimized AMI는 NVIDIA 커널 드라이버와 Docker GPU 런타임을 미리 갖춰 둔다.
  3. 플랫폼을 맞춘다ARM64 아키텍처나 AWS Neuron을 쓰면 런타임 플랫폼과 리전을 지원 범위 안에서 지정한다. 비디오 트랜스코딩 태스크 정의도 전용 리전에서만 돌아간다.
  4. 확인해 볼 것실행된 태스크의 컨테이너에 GPU가 할당되어 있는지와 리전이 지원하는 리전인지 확인한다.

#5한 줄 요약

특수 워크로드 태스크 정의하드웨어 요구량을 태스크 정의에 적어 그 자원을 가진 인스턴스에만 태스크를 올리는 것

IaC로 태스크 정의 만들기 — CloudFormation·Copilot·CDK

태스크 정의를 코드(AWS CloudFormation·AWS Copilot·AWS CDK)로 선언해 두면 같은 사양의 태스크 정의를 반복 등록하거나 손으로 편집하는 대신 템플릿을 버전 관리해 한 번에 배포하고 되돌릴 수 있다.

먼저 알아야 할 것 03-04

#1문제 상황

태스크 정의를 콘솔에서 손으로 고치면 어떤 버전이 실제 실행 중인지 알 수 없다. 같은 정의를 여러 클러스터에 반복해서 만들고, 되돌릴 방법도 없다.

IaC로 태스크 정의 만들기는 템플릿 파일 하나로 정의를 코드에 둔다. AWS CloudFormation은 YAML이나 JSON 템플릿을 읽어 AWS::ECS::TaskDefinition 자원을 만든다. 같은 일을 AWS Copilot CLI와 AWS CDK로도 할 수 있다.

#2핵심 질문

태스크 정의를 어떻게 코드로 남기고 반복 배포할까?

#3동작 예시

운영팀이 태스크 정의 템플릿을 저장소에 두고 이미지 태그를 고친 뒤 배포한다. CloudFormation이 예제 CloudFormation 템플릿을 읽어 스택을 갱신하고 태스크 정의가 새로 등록된다.

문제가 생기면 이전 템플릿으로 되돌린다. 변경 전에 change set으로 바뀔 내용을 먼저 확인한다.

#4동작 과정

  1. 선택한다선언할 방법을 고른다. AWS CloudFormation은 템플릿을 스택으로 올리고, AWS Copilot CLI는 앱과 서비스 구조를 명령으로 짜고, AWS CDK는 코드로 자원을 만든다.
  2. 선언한다예제 CloudFormation 템플릿에 이미지·명령·환경변수와 CPU·메모리 값을 적는다. 태스크 정의는 AWS::ECS::TaskDefinition 타입으로 만들어진다.
  3. 검토한다템플릿을 제출하기 전에 change set로 바뀔 내용을 본다. 스택 갱신·삭제는 이 검토를 거쳐 진행한다.
  4. 확인해 볼 것배포한 뒤 태스크 정의 목록에 새 리전이 잡혔는지 확인한다.

#5한 줄 요약

IaC로 태스크 정의 만들기태스크 정의를 템플릿 코드로 보관해 반복 배포와 되돌리기를 가능하게 하는 것

클러스터 생성과 설정 변경

여러 ECS 태스크를 한데 묶어 관리하는 단위인 클러스터를 만들고, 그 설정값을 콘솔이나 API로 고치는 절차.

먼저 알아야 할 것 01-03

#1문제 상황

태스크를 하나씩 올리면 서로 관련 있는지 알 수 없다. 서비스 간 연결과 이동을 묶는 단위도 없다.

클러스터 생성은 태스크를 한데 묶는 관리 단위를 만드는 일이다. 콘솔에서 만들면 CloudFormation 스택이 리소스를 만들고 Fargate와 Fargate Spot 용량 공급자를 자동으로 붙인다. 이후 클러스터 설정에서 바꾸면 된다.

#2핵심 질문

여러 태스크를 한데 묶어 관리하는 단위를 어떻게 만들고 바꾸는가?

#3동작 예시

신입이 콘솔에서 클러스터 생성을 누르면 스택이 만들어지고 클러스터가 뜬다. 아무것도 안 만들었다면 쓰는 클러스터가 없어 기본 클러스터 하나를 쓴다.

클러스터 설정을 열어 태그를 붙이고 서비스 간 통신용 네임스페이스를 추가한다.

#4동작 과정

  1. 만든다콘솔에서 클러스터를 생성한다. 콘솔은 CloudFormation 스택을 만들어 필요한 리소스를 붙이고 Fargate와 Fargate Spot 용량 공급자를 연다.

#1문제 상황

클러스터에서 태스크를 어디에 실을지 정하지 않으면 태스크가 자리 없이 멈춘다. 반대로 아무 보호 없이 축소하면 hours 단위로 도는 긴 작업이 도중에 잘린다.

capacity provider를 지정하면 실행 자리가 생긴다. capacity provider strategy에서 base와 weight로 비율을 정하고 managed scaling과 managed termination protection으로 조절한다. 여기에 task scale-in protection을 걸면 지정한 태스크는 인스턴스 안전 종료 단계에서 살아남는다.

#2핵심 질문

태스크가 도는 자리를 지정하고 축소에 휘둘리지 않게 하려면?

#3동작 예시

새 요청이 몰리면 용량 공급자가 자리를 늘리고 weight 비율대로 분배한다.

#4동작 과정

  1. 자리를 정한다capacity provider로 Fargate나 Auto Scaling 그룹, Managed Instances를 고른다. capacity provider strategy의 base를 정하고 weight로 비율을 나눈다.
  2. 늘리게 한다managed scaling을 켜면 용량 공급자가 필요할 때 자동으로 크기를 키운다. 조정은 provider 전략에 모인 값으로 한다.
  3. 지킨다task scale-in protection을 태스크에 걸면 서비스 오토스케일링과 배포의 축소 이벤트에도 종료 대상에서 빠진다. managed termination protection은 축소 과정에서 태스크를 먼저 비우는 방식을 정한다.
  4. 확인해 볼 것태스크 목록에서 보호가 걸린 태스크가 축소 이벤트 뒤에도 RUNNING 상태로 남는지 확인한다.

Auto Scaling 그룹 용량 공급자와 클러스터 오토스케일링

Auto Scaling 그룹을 클러스터의 용량 공급자로 연결해 인스턴스를 자동 확보하고, 클러스터 전체의 목표 용량에 맞춰 그룹의 크기를 자동으로 조정하는 방식.

먼저 알아야 할 것 04-02

#1문제 상황

인스턴스를 미리 넉넉히 사두면 유휴 비용이 늘고, 적게 두면 태스크가 밀린다. 사용량을 보며 자리를 늘리는 판단을 직접 해야 한다.

Auto Scaling group capacity provider를 쓰면 그 판단을 맡길 수 있다. cluster auto scaling을 켜고 목표 비율을 정하면 Amazon ECS가 CloudWatch 지표와 target tracking 정책, 경보 두 개를 만들어 그룹 크기를 조절한다.

#2핵심 질문

클러스터 전체가 사용할 인스턴스 수를 어떻게 자동으로 정하는가?

#3동작 예시

트래픽이 몰려 ECSClusterCapacityUtilization 지표가 목표치를 넘는다. Amazon ECS가 만든 CloudWatch 경보가 울리고 대상 추적 정책이 scale out을 실행한다.

목표 대비 낮아지면 scale in이 일어난다. 축소는 scale-in 보호 대상을 먼저 비운 뒤 진행된다.

#4동작 과정

  1. 연결한다Auto Scaling 그룹 용량 공급자를 클러스터에 붙이고 managed scaling을 켠다. 그룹이 자리 공급자가 되어 태스크를 그 인스턴스에 올린다.
  2. 지표를 만든다ECSClusterCapacityUtilization 지표를 만들고 목표 비율을 정한다. Amazon ECS가 이 지표에 대한 CloudWatch 경보와 target tracking scaling policy를 자동으로 생성해 그룹에 건다.
  3. 조절한다scale out과 scale in은 이 지표 값에 따라 ECS가 수행한다. 클러스터 오토스케일링 속도 조절로 반응의 빠르기를 바꿀 수 있고 축소에는 scale-in 보호를 적용한다.
  4. 확인해 볼 것CloudWatch에서 ECSClusterCapacityUtilization 지표와 자동 생성된 경보가 있는지 확인한다.

  2. 주소를 정한다서브넷에서 프라이빗 IP 주소가 하나 배정된다. VPC Flow Logs로 태스크로 들어오고 나가는 통신을 볼 수 있다.

bridge 모드는 컨테이너마다 프라이빗 IP를 갖고 호스트를 거쳐 나가며, host 모드는 컨테이너가 호스트의 IP와 포트를 그대로 공유하고, none 모드는 외부 통신을 완전히 차단하는 모드다.

먼저 알아야 할 것 05-01

→ 05-01 참조

#1문제 상황

EC2에 올라간 태스크는 AWS 자원이 아니라 호스트 컴퓨터 위에서 돌아간다. 그래서 태스크가 밖과 통신하는 모양이 세 가지로 갈린다.

bridge network mode는 호스트와 컨테이너 사이에 가상 브리지를 둔다. host network mode는 호스트의 네트워크 네임스페이스를 컨테이너가 그대로 공유하고, none network mode는 네트워크를 만들지 않는다.

#2핵심 질문

EC2 안의 컨테이너가 호스트를 거쳐 나가려면 어떤 설정을 쓰는가?

#3동작 예시

운영자가 bridge로 태스크를 띄우고 호스트의 80번 포트를 컨테이너의 3000번 포트에 연결한다. 브라우저에서 EC2 인스턴스의 IP와 80번 포트로 접속해 컨테이너 앱 화면이 열린다.

같은 호스트에 두 번째 태스크를 띄우려 하면 80번 포트가 겹쳐 실패한다.

#4동작 과정

  1. 브리지를 건다bridge network mode에서 정적 또는 동적 포트 매핑으로 호스트 포트를 컨테이너 포트로 바꾼다. 컨테이너는 들어온 요청을 자신의 3000번 포트로 본다.
  2. 호스트를 공유한다host network mode는 포트를 그대로 씁니다. 대신 한 호스트에서 태스크를 여러 개 띄울 수 없습니다.
  3. 확인해 볼 것EC2 인스턴스의 포트 목록에서 태스크가 실제로 열고 있는 포트를 확인한다.

서브넷 선택과 IPv6·이중 스택

태스크를 시작할 때 어느 서브넷에 배치할지 VPC와 서브넷을 고르는 설정이며, IPv6만 쓰거나 IPv4와 IPv6를 함께 쓰는 이중 스택 구성을 쓸 수 있다.

먼저 알아야 할 것 05-02

#1문제 상황

태스크를 VPC 어디에 놓느냐에 따라 밖에서 보이는 주소와 나가는 경로가 달라진다. 그래서 태스크를 실행하기 전에 서브넷을 고르는 과정이 반드시 필요하다.

AWS는 서브넷 세 종류를 둔다. public IP 주소가 배정되는 공개 서브넷, 프라이빗 IP만 배정되는 비공개 서브넷, 그리고 IPv6-only 서브넷이다. 이 중에서 태스크를 놓을 곳을 정한다.

#2핵심 질문

태스크를 VPC의 어느 서브넷에 놓고 어느 주소 체계를 쓸 것인가?

#3동작 예시

운영자가 내부 전용 서비스의 태스크를 비공개 서브넷에 두고 실행한다. 태스크에는 프라이빗 IP만 붙고, 인터넷으로 나가는 요청은 NAT 게이트웨이를 거친다.

IPv6만 쓰는 서비스라면 dual-stack endpoint 대신 IPv6-only 서브넷을 고른다.

#4동작 과정

  1. 서브넷을 고른다태스크 정의에서 awsvpc 모드에 쓸 서브넷 목록을 적는다. 이 서브넷에서 프라이빗 IP가 배정된다.
  2. 주소 체계를 정한다IPv6-only 서브넷을 쓰거나, dual-stack 방식으로 IPv4와 IPv6를 함께 쓴다. 큰 규모 서비스는 Local Zone, Wavelength Zone, AWS Outposts 같은 전용 영역을 쓴다.
  3. 확인해 볼 것태스크 상세에서 배정된 프라이빗 IP와 ENI가 붙은 서브넷 ID를 확인한다.

VPC endpoint로 나가는 통신

태스크가 인터넷 게이트웨이나 NAT 게이트웨이 대신 AWS 내부 네트워크를 통해 S3·DynamoDB 같은 다른 AWS 서비스로 나가게 해 주가는 프라이빗 연결 지점이다.

먼저 알아야 할 것 05-02

#1문제 상황

태스크가 S3이나 DynamoDB에 닿으려면 보통 NAT 게이트웨이를 거쳐 인터넷으로 나간다. 그만큼 비용과 경로가 늘어난다.

interface VPC endpoint는 VPC 안에서 프라이빗 IP로 AWS 서비스에 직접 닿는 지점이다. 이 기술은 AWS PrivateLink이며, VPC와 Amazon ECS 사이의 통신을 모두 AWS 내부망으로 묶는다.

#2핵심 질문

태스크가 다른 AWS 서비스로 나갈 때 인터넷을 거치지 않게 하려면 어떻게 하는가?

#3동작 예시

운영자가 콘솔에서 VPC에 ecs.api, ecs-t, ecs-agent.endpoint 같은 interface VPC endpoint를 만든다. 태스크에서 S3으로 나가는 요청이 NAT 게이트웨이 대신 VPC 안에서만 움직인다.

#4동작 과정

  1. 엔드포인트를 만든다interface VPC endpoint를 만든다. 인터페이스 엔드포인트는 ssm과 logs처럼 태스크가 쓰는 AWS 서비스별로 따로 필요하고, 프라이빗 DNS 이름을 부여해 API 주소를 대신한다.
  2. 트래픽을 붙인다어떤 엔드포인트도 비워 두면 그 통신은 공개 엔드포인트로 나간다. VPC와 Amazon ECS 사이 트래픽은 Amazon PrivateLink 내부로만 흐른다.
  3. 확인해 볼 것VPC 엔드포인트 목록에서 엔드포인트 종류와 서비스가 붙었는지 확인한다.

6단계 스케줄링과 태스크 배치 — 어디에 무엇을 놓을지 | 스케줄러와 desiredStatus·lastStatus

ECS 스케줄러는 태스크의 desiredStatus(원하는 상태)를 보고 lastStatus(실제로 도달한 상태)와 비교해, PROGRESSING·RUNNING·DEACTIVATED·STOPPED·NONE 중 어디인지 판정하며 원하는 상태와 실제 상태가 다를 때만 그 차이를 좁히는 작업을 반복해 태스크를 실행 가능한 컨테이너 인스턴스로 배치합니다.

먼저 알아야 할 것 04-01

#1문제 상황

여러 대의 컨테이너 인스턴스 위에 태스크를 올려야 하는데, 어느 기계에 놓을지는 자동으로 정해진다. 이 결정을 Amazon ECS scheduler가 내린다.

스케줄러는 각 태스크의 desiredStatus(원하는 상태)와 lastStatus(마지막으로 확인한 상태)를 비교한다. 둘이 다를 때만 그 차이를 좁히는 작업을 반복하고, 마지막에 실행 가능한 컨테이너 인스턴스에 배치한다.

#2핵심 질문

수많은 컨테이너 인스턴스 중 태스크를 놓을 자리를 어떻게 정하는가?

#3동작 예시

프런트엔드 서비스의 태스크 정의에 인스턴스 유형 조건을 걸고 서비스를 만든다. 스케줄러는 조건에 맞는 인스턴스를 찾아 컨테이너 자원을 예약하고 태스크를 거기 붙인다. 같은 인스턴스에 태스크가 몰리면 다음 태스크는 다른 곳을 고른다.

#4동작 과정

  1. 상태를 비교한다스케줄러가 desiredStatus와 lastStatus를 대조해 다르면 차이를 좁히는 작업을 반복한다. RESULT는 PROGRESSING·RUNNING·DEACTIVATED·STOPPED·NONE 가운데 하나이며, 이걸로 현재 몇 단계 왔는지 안다.
  2. 자원을 예약한다고른 컨테이너 인스턴스에서 태스크가 쓸 자원을 먼저 잠근다. 잠근 뒤 컨테이너를 만들고 시작 시키므로 같은 자원을 다른 태스크가 뺏어 가지 않는다.
  3. 결정을 반복한다남은 태스크마다 배치 결정을 새로 내린다. CPU나 메모리 사용량, 가용 영역 같은 요인이 이 결정을 바꾸며, 결정 기록은 클러스터 상태로 남는다.
  4. 확인해 볼 것콘솔에서 태스크를 열어 마지막 상태와 이벤트 순서를 보고 어느 단계에서 멈췄는지 확인한다.

태스크 배치 전략은 서비스가 여러 태스크를 클러스터에 띄울 때 어떤 고유한 호스트를 고를지를 정하는 규칙으로, 균형 잡힌 배치(replica), 가장 적은 태스크가 든 인스턴스 선택, 빈 인스턴스 우선, 빈도 기반 최소 배치 등 몇 가지가 있으며 어느 전략을 쓰느냐에 따라 비용과 장애 대응 동작이 달라집니다.

먼저 알아야 할 것 06-01

#1문제 상황

서비스 태스크를 여러 인스턴스에 나눌 때 아무렇게나 놓으면 한 곳에 몰린다. 그러면 한 대가 죽을 때 함께 사라지고 자원도 낭비된다.

태스크 배치 전략은 고를 인스턴스 규칙을 정한다. 서비스의 기본값은 spread로, 가용 영역 단위로 흩뿌리고 cpu와 memory 가중치로 선호도를 준다. binpack은 한 인스턴스를 채우고 다음으로 넘어가며, random은 아무 인스턴스나 고른다. Managed Instances를 쓰면 스케일링과 배치를 함께 다룰 수 있다.

#2핵심 질문

여러 태스크을 여러 인스턴스에 나눌 때 어느 규칙으로 고를까?

#3동작 예시

가용 영역이 세 개인 클러스터에서 서비스 desired count를 3으로 올린다. spread 전략이라 세 태스크이 각 영역에 한 대씩 놓인다. 화면에서는 영역별 태스크 수가 고르게 표시된다.

#4동작 과정

  1. 전략을 고른다서비스에서는 기본이 spread고 standalone task에는 기본 제약이 없다. binpack은 몰아서 채우고 random은 무작위로 고른다.
  2. 선호도를 반영한다cpu와 memory 가중치로 어느 인스턴스를 더 좋게 볼지 정한다. 가용 영역 속성을 함께 주면 영역 단위로 분산된다.
  3. 축소할 때도 쓴다태스크 수를 줄일 때도 같은 규칙으로 어떤 태스크를 먼저 끝낼지 정한다. 전략은 최선이 아니면 다른 자리를 시도하고, 제약은 지시를 지켜 강제로 막는다.
  4. 확인해 볼 것서비스의 태스크 목록에서 인스턴스 번호가 어느 영역에 고르게 분포됐는지 눈으로 확인한다.

배치 제약 조건은 memberOf·distinctInstance 같은 표현식을 넣어 태스크가 특정 속성의 인스턴스나 서로 다른 인스턴스에만 놓이도록 좁히는 조건이고, 클러스터 쿼리 언어는 attribute:ecs.instance-type 같은 형식으로 인스턴스 메타데이터를 표현해 그 조건을 계산해 주는 문법입니다.

먼저 알아야 할 것 06-02

#1문제 상황

인스턴스가 여러 종류와 영역에 흩어져 있으면, 어떤 태스크는 특정 인스턴스에만 올라가야 한다. 그리고 인스턴스를 고를 때 보려는 정보가 자꾸 늘어난다.

배치 제약 조건은 그 범위를 식으로 좁힌다. cluster query language는 그 식에 쓰는 문법이다. attribute 제약은 attribute:ecs.instance-type 같은 속성 값으로, 사용자 정의 속성은 컨테이너 인스턴스에 직접 붙인 메타데이터다.

#2핵심 질문

태스크가 올라갈 수 있는 인스턴스의 범위를 어떻게 표현하고 검사하는가?

#3동작 예시

GPU가 필요한 태스크 정의에 distinctInstance 제약과 GPU 속성 조건을 넣는다. 스케줄러가 조건에 맞는 인스턴스를 찾아 태스크를 올리고, 조건에 맞는 곳이 없으면 태스크는 배치되지 않고 대기한다.

#4동작 과정

  1. 인스턴스를 분류한다컨테이너 인스턴스에 속성을 붙인다. 기본 속성에는 가용 영역과 ecs.instance-type이 있고, 사용자 정의 컨테이너 인스턴스 속성은 직접 추가하는 값이다.
  2. 식을 만든다subject 연산자 값 형태로 조건을 쓴다. memberOf는 특정 그룹에 속한 인스턴스만, distinctInstance는 서로 다른 인스턴스에 하나씩만 놓게 한다.
  3. 검사한다스케줄러가 식을 계산해 대상 인스턴스를 고르고, attribute 제약은 어느 속성인지 지정하는 데 쓰인다. 결과가 없으면 배치는 보류된다.
  4. 확인해 볼 것콘솔에서 태스크 이벤트를 열어 제약 때문에 배치가 멈췄는지 확인한다.

#1문제 상황

태스크 그룹은 task group 이름으로 태스크를 묶어 하나의 배치 단위로 만든다. 독립 실행 태스크는 이름이 없으면 태스크 정의 이름을 그룹 이름으로 쓴다.

#2핵심 질문

여러 태스크을 하나처럼 다루고 배치의 묶음으로 삼을 수 있는가?

#3동작 예시

데이터베이스 태스크를 그룹 이름 databases로 묶고 spread 전략을 건다. 이제 같은 그룹의 태스크가 가용 영역별로 나뉘어 놓인다. 화면에서 그룹 이름이 같은 태스크만 골라 한 번에 멈출 수 있다.

#4동작 과정

  1. 그룹을 붙인다태스크를 만들 때 task group 이름을 준다. 이름을 안 주면 standalone task는 태스크 정의 이름이 그대로 그룹 이름이 된다.
  2. 배치 묶음으로 쓴다spread 전략은 같은 그룹의 태스크를 한 묶음으로 보고 균형을 맞춘다. memberOf 제약에 그룹을 넣으면 그 그룹 태스크가 있는 인스턴스만 고른다.
  3. 한 번에 다룬다태스크 그룹 단위 멈춤과 삭제를 요청할 수 있다. 한꺼번에 정리할 대상을 정해 두는 일이다.
  4. 확인해 볼 것태스크 목록에서 태스크 그룹 이름이 같은 항목들이 한 묶음으로 보이는지 확인한다.

  4. 확인해 볼 것태스크 상세에서 예약된 규칙과 마지막 실행 시각을 확인한다.

태스크 lifecycle은 태스크가 요청·인스턴스 배치·이미지 풀·시작·헬스체크·정지·삭제로 이어지는 진행 단계(PROVISIONING·PULLING·PENDING·ACTIVATING·RUNNING 등)를 뜻하고, 어느 단계에서 멈췄는지를 보면 실패 원인을 좁힐 수 있습니다.

먼저 알아야 할 것 06-05

#1문제 상황

태스크가 왜 안 뜨는지 볼 때 어디까지 갔는지 알 수 없다. 인스턴스 배치에서 막힌 건지, 이미지를 못 받아온 건지 구분되지 않는다.

태스크 lifecycle은 PROVISIONING에서 DELETED까지 이어지는 진행 단계다. 마지막으로 확인된 상태는 lastStatus로, 요청한 상태는 desiredStatus로 따로 본다.

#2핵심 질문

태스크가 멈췄을 때 어느 단계에서 막혔는지 어떻게 알 수 있는가?

#3동작 예시

돌아가야 할 태스크가 멈춰 있다. 태스크를 설명하면 lastStatus가 PENDING에서 DEACTIVATING을 거쳐 STOPPING으로 내려가는 게 보인다. StopTimeout이 지나도 멈추지 않으면 SIGTERM을 못 받아들여 강제 종료로 넘어간 것으로 읽는다.

#4동작 과정

  1. 자리를 잡는다PROVISIONING에서 인스턴스를 찾고 자원을 정한다. 이후 PENDING에서 이미지를 받고 ACTIVATING에서 컨테이너를 시작한다.
  2. 실행한다RUNNING이 되면 헬스체크와 앱 실행 상태가 함께 표시된다. 여기에 desiredStatus와의 차이로 서비스가 원하는 조정을 계속한다.
  3. 끝낸다DEACTIVATING과 STOPPING을 거쳐 STOPPED로 내려간다. 앱이 지워질 때 StopTimeout 동안 기다리고, 안 끝나면 SIGKILL로 마지막 정리를 한다.
  4. 확인해 볼 것콘솔에서 태스크 상태 변화와 이벤트 순서를 보고 마지막으로 통과한 단계를 확인한다.

먼저 알아야 할 것 06-01

#1문제 상황

여러 태스크을 늘어난 줄 모르게 띄워 두고, 하나가 죽으면 자동으로 채워 주기를 원한다. 그래야 사용자는 늘 같은 수의 서버를 보게 된다.

ECS service가 이 역할을 한다. 등록된 태스크 정의로 desired count만큼을 유지하고, 태스크 하나가 멈추면 같은 정의의 새 태스크를 띄운다.

#2핵심 질문

원하는 태스크 수를 계속 지키면서 비정상 태스크를 자동 교체하려면 어떻게 하는가?

#3동작 예시

  3. 백로그를 막는다한 번에 띄울 자리가 없으면 service throttle logic이 반복 시도 횟수를 제한한다. 지연된 요청을 그만 보내는 제어다.

#1문제 상황

새 태스크가 기동에 실패해도 배포는 멈추지 않는다. 배포가 성공한 것처럼 남아 서비스가 계속 깨진 상태가 된다.

배포 실패 감지는 이런 상태를 막는다. 롤링 업데이트와 blue/green 배포에서 새 태스크가 정상 기동하지 못하면 ECS가 자동 rollback으로 되돌린다. 여기에 lifecycle hook을 더하면 태스크를 보류해 교체 순간 트래픽을 지킬 수 있다.

#2핵심 질문

새 태스크가 정상 기동하지 못했을 때 사람이 개입하기 전에 배포를 알아서 되돌릴 수 있는가?

#3동작 예시

DB 접속 설정이 빠진 태스크 정의로 배포한다. 새 태스크가 기동을 마치지 못하고 배포가 실패로 판정되면 ECS가 이전 버전으로 자동 rollback 한다.

CloudWatch alarm 기반 배포 실패 감지를 걸어 둔 경우에는 alarm이 ALARM 상태가 되는 것만으로 배포가 실패로 판정되어 같은 되돌리기가 동작한다.

#4동작 과정

  1. deployment circuit breaker를 건다한 번 실패하면 그 뒤 배포를 시도하지 않는 차단기다. 반복 실패를 막는다.
  2. rollback을 건다성공했던 COMPLETED 상태의 이전 배포로 되돌린다. CloudWatch alarm 기반 배포 실패 감지를 함께 켜면 감시 지표가 ALARM이 되는 것만으로 실패가 되고 되돌아간다. 두 방법을 같이 쓰면 어느 쪽이든 실패를 일으킬 수 있다.
  3. lifecycle hook을 건다태스크를 PREPARE 상태로 잠깐 보류해 기동을 기다린다. Lambda hook은 외부 함수를, Pause hook은 정해진 시간만큼 기다린다.
  4. 확인해 볼 것서비스의 배포 기록에서 자동 되돌림이 실행된 것의 상태가 어떻게 표시되는지 확인한다.

#1문제 상황

blue/green deployment는 같은 설정의 blue 서비스와 green 서비스를 따로 띄운다. green에 테스트 트래픽만 보내 확인한 뒤, 트래픽 전환으로 production target group을 한 번에 green으로 바꾼다.

#3동작 예시

새 이미지 태그를 green 서비스에 배포하고 test target group으로 검증 트래픽을 보낸다. 응답과 오류율을 확인한 뒤 albRule의 리스너 규칙이 가리키는 production target group을 green으로 전환한다.

화면에서 하나의 고정된 주소로 들어온 트래픽이 이제 green의 태스크로만 나뉜다. 문제가 생기면 전환을 blue으로 되돌리면 된다.

#4동작 과정

  1. green을 새로 띄운다blue과 같은 구성의 green 서비스를 만들어 올린다. 이 단계에서 production 트래픽은 아직 blue이 받는다.
  2. test target group으로 검증한다albRule이 만든 테스트 리스너를 통해 green에 트래픽을 보낸다. 리스너는 들어오는 요청을 어떤 대상 그룹으로 넘길지 정하는 규칙이다.
  3. 트래픽을 전환한다production target group을 green으로 한 번에 바꿔 트래픽을 넘긴다. 전환 전에 호출할 명령과 리스너, 실패 시 되돌릴지를 blueGreenDeploymentConfiguration으로 정해 둔다. blue은 그대로 남아 되돌릴 수 있다.
  4. 확인해 볼 것로드 밸런서의 리스너 규칙에서 production 대상 그룹이 어느 서비스를 가리키는지 확인한다.

service revision은 그 기록이다. 서비스나 배포 설정을 바꿀 때마다 읽기 전용 스냅샷이 하나씩 생기고, service revision 속성에는 그때의 태스크 정의와 배포 설정이 함께 담긴다.

#2핵심 질문

지금 올라간 버전과 배포 전 버전의 설정을 비교하고 바로 되돌리려면 무엇이 필요한가?

#3동작 예시

배포 중인 서비스에서 지금 올라간 리비전을 source로, 배포할 리비전을 target으로 지정해 설정을 나란히 본다. 문제가 보이면 rollback을 눌러 마지막으로 성공한 리비전으로 되돌린다.

화면에는 그 서비스의 service deployment 기록이 시간순으로 쌓여 있고, 각 배포가 끝났는지 진행 중인지 나타난다.

#4동작 과정

  1. 기록을 남긴다서비스를 만들거나 배포 설정을 바꾸면 ECS가 새 service revision을 자동으로 만든다. 스냅샷은 읽기 전용이고 고유 식별자를 가진다.
  2. 비교한다배포 중 source와 target 리비전을 나란히 놓으면 태스크 정의와 배포 설정의 차이를 볼 수 있다.
  3. 되돌린다rollback을 쓰면 ECS가 마지막으로 성공한 리비전으로 자동으로 되돌린다. 되돌린 뒤 배포 전략 변경으로 CodeDeploy blue/green에서 ECS blue/green으로 옮길 수 있다. 배포 상태는 service deployment 기록에서 확인한다.
  4. 확인해 볼 것서비스의 리비전 목록에서 생성 시각과 상태가 어떻게 보이는지 확인한다.

먼저 알아야 할 것 07-01

#1문제 상황

태스크는 만들고 사라지는 임시 자원이라 고정된 주소로 도달할 수 없다. 같은 서비스를 여러 태스크로 늘려도 클라이언트는 어디로 붙어야 하는지 모른다.

load balancer는 고정된 주소 하나를 밖으로 내주며, 여러 컨테이너 인스턴스나 태스크로 트래픽을 나눠 보낸다. 대상 그룹은 그 주소로 들어온 요청을 실제로 받게 될 태스크들의 묶음이다. ECS는 이 대상 그룹에 태스크를 등록해 health check를 통과한 대상만 받게 한다.

#2핵심 질문

변하는 태스크들을 어떻게 하나의 주소로 묶어 건너뛰지 않고 트래픽을 보낼 것인가?

#3동작 예시

ALB의 고정 주소로 요청이 들어온다. ECS 서비스의 태스크가 대상 그룹에 등록되어 있고 health check를 통과한 대상에만 요청이 나뉜다. 태스크 하나가 죽으면 대상에서 빠지고 새 태스크가 등록되면 다시 나뉜다.

화면에는 대상 그룹의 대상 목록에서 등록 상태와 health 상태가 보인다.

#4동작 과정

  1. 로드 밸런서를 정한다Application Load Balancer는 HTTP/HTTPS 트래픽을 처리하고, Network Load Balancer는 고정 포트를 처리하며, Gateway Load Balancer는 방화벽 같은 장비 통과용이다.
  2. 대상 그룹을 등록한다서비스 트래픽 분산은 대상 그룹에 태스크를 자동 등록하고 빼는 동작이다. 한 서비스에 여러 대상 그룹을 붙여 여러 포트를 노출할 수 있다.
  3. 등록 방식을 정한다target type ip는 태스크 IP를, target type instance는 인스턴스 ID와 포트 조합을 등록한다. 동적 호스트 포트 매핑을 쓸 수 있는 Application Load Balancer는 ip 방식을 쓴다.
  4. 확인해 볼 것대상 그룹의 대상 목록에서 태스크 IP가 healthy 상태로 올라와 있는지 확인한다.

#1문제 상황

로드 밸런서를 붙이는 것만으로는 트래픽이 끊긴다. health check가 늦으면 교체 중인 태스크로 요청이 계속 보내지고, 대상이 빠질 때 진행 중 요청이 끊긴다.

#3동작 예시

화면에서는 health check 결과가 healthy로 올라오는 시간이 평소보다 짧아진다.

#4동작 과정

  1. 종류를 고른다Application Load Balancer는 계층 7인 HTTP/HTTPS 라우팅을, Network Load Balancer는 계층 4 고정 포트와 높은 처리량을, Gateway Load Balancer는 트래픽 처리 장비 통과를 담당한다.
  2. 체크와 대기 시간을 정한다health check 파라미터로 주기와 성공 조건을 정하고, deregistration delay은 대상을 빼고 나서 기존 요청을 받으며 기다리는 시간이다. connection draining에 해당한다.
  3. 태스크 종료 시간을 맞춘다대상에서 빠진 뒤의 요청을 기다리는 시간이 ECS 태스크의 stopTimeout보다 길어야 기존 요청이 끊기지 않는다.
  4. 확인해 볼 것로드 밸런서의 health check 설정에서 주기와 성공 임계값이 어떻게 적혀 있는지 확인한다.

먼저 알아야 할 것 08-01

→ 08-04 참조

#1문제 상황

여러 ECS 서비스가 서로 통신하려면 각 태스크의 IP와 포트를 직접 알아야 하고, VPC DNS 설정을 따로 맞춰야 한다. 태스크가 새로 붙거나 빠질 때마다 그 주소도 바뀐다.

Amazon ECS Service Connect는 이 두 가지를 한 번에 해결한다. service connect configuration이라는 설정 하나로 서비스 디스커버리와 서비스 메시를 ECS 안에서 구성하고, VPC DNS 설정과 무관하게 네임스페이스 안의 이름으로 서비스를 가리킨다. dnsName은 그 이름에 붙는 주소다.

#2핵심 질문

코드에서 IP나 포트를 몰라도 다른 서비스의 이름으로 통신하려면?

#3동작 예시

워드프레스 태스크 안에서 MySQL에 접속한다. 코드에는 호스트를 dnsName 형식의 이름으로만 적혀 있다. 실행하면 MySQL 태스크 중 하나로 연결되고, 호출 쪽에는 호출 수와 지연 시간에 대한 표준 지표와 로그가 남는다.

#4동작 과정

  1. 서비스를 잇는다서비스 정의에 service connect configuration을 넣고 상대 서비스 이름을 적은다. Amazon ECS Service Connect가 클라이언트 쪽에 호출을 중계하는 구성 요소를 붙여 이름을 실제 통신으로 바꿔 준다.
  2. 이름으로 찾는다호출은 named space 안의 dnsName으로 대상 서비스를 찾는다. VPC DNS 설정과 상관없이 동작하고, 기존 서비스 디스커버리 방식을 그대로 쓰는 것보다 설정이 줄어든다.
  3. 상태를 본다태스크가 여러 개면 Service Connect가 알아서 분산해 붙인다. 표준 지표와 로그가 남으므로 응답 시간과 오류를 콘솔에서 함께 확인한다.
  4. 확인해 볼 것서비스의 연결 화면에서 클라이언트와 서버 서비스의 이름이 쌍으로 보여 주는지 확인한다.

AWS Cloud Map 네임스페이스와 VPC Lattice

Cloud Map은 컨테이너 인스턴스에 DNS 이름을 등록해 서비스가 이름으로 서로 발견하게 하는 네임스페이스 기반 서비스 디스커버리이고, VPC Lattice는 그 위에서 여러 계정·여러 VPC를 걸친 서비스 간 통신을 관리·암호화하는 기능이다.

먼저 알아야 할 것 08-03

→ 08-03 참조

#1문제 상황

서로 다른 VPC나 계정에 있는 서비스끼리는 VPC 안에서만 동작하는 이름으로는 서로를 찾을 수 없다. 서비스마다 VPC DNS 설정과 방화벽 규칙을 따로 맞춰야 한다.

AWS Cloud Map은 그 사이의 이름을 만들어 준다. service discovery는 Cloud Map API로 ECS 서비스의 HTTP·DNS 네임스페이스를 관리하는 동작이며, shared namespace에 이름을 등록해 두면 어느 VPC에서든 그 이름으로 상대를 찾는다. 더 넓은 범위와 암호화가 필요하면 AWS VPC Lattice를 쓴다.

#2핵심 질문

여러 VPC와 계정에 걸친 서비스를 이름으로 서로 찾게 하려면?

#3동작 예시

한 VPC에서 주문 서비스가 있고 다른 VPC에 결제 서비스가 있다. 결제 서비스를 shared namespace에 등록한 뒤 주문 서비스의 태스크 정의를 배포한다. 실행된 태스크는 VPC 위치와 상관없이 등록된 이름으로 결제 서비스에 닿는다.

#4동작 과정

  1. 네임스페이스를 만든다Cloud Map에서 HTTP 또는 DNS 형식의 네임스페이스를 만든다. 네임스페이스는 서비스 이름을 모아 두는 그릇이고, ECS 서비스는 여기에 인스턴스 주소를 등록하고 지운다.
  2. 이름을 붙인다서비스 정의에서 이 네임스페이스를 고르고 alias를 정한다. 인스턴스가 붙을 때마다 주소가 등록되므로, 찾을 대상은 고정된 주소가 아니라 이름이 된다.
  3. 범위를 넓힌다VPC와 계정을 넘어 묶어야 할 때 AWS VPC Lattice를 쓴다. 계정과 VPC를 걸친 여러 대상을 하나의 이름 뒤에 두고 통신을 암호화한다.
  4. 확인해 볼 것콘솔에서 해당 네임스페이스의 인스턴스 목록에 ECS 태스크 주소가 들어와 있는지 확인한다.

#1문제 상황

Service Connect로 서비스를 잇어도 통신은 평문이고, 호출 대상이 특정 영역의 태스크에만 닿을 수 있다. 인증서 발급과 교체를 손으로 맡기는 것도 번거롭다.

Service Connect TLS는 이 둘을 설정으로 해결한다. 영역 인지 라우팅은 호출 서비스가 대상 서비스의 모든 영역에 걸친 컨테이너 인스턴스 주소를 알고 요청을 고르게 보내게 한다.

#2핵심 질문

서비스 사이 통신을 암호화하고 장애 난 영역을 피해 보내려면?

#3동작 예시

서비스 정의를 AWS Private CA를 향하게 설정한다. 배포가 끝나면 Amazon ECS가 인증서를 발급해 각 서비스에 배포하고, 호출은 암호화된 통로를 지나 다른 영역의 태스크에도 닿는다.

#4동작 과정

  1. 인증서를 준비한다서비스가 AWS Private Certificate Authority를 가리키게 한다. Amazon ECS가 TLS 인증서를 만들어 발급하고 회전까지 맡아 암호화 통신에 쓴다.
  2. 영역을 나눠 부른다zone-aware routing이 대상 서비스의 영역별 컨테이너 인스턴스 주소를 호출 서비스에 알려 준다. 한 영역이 비어도 요청이 살아 있는 다른 영역의 태스크로 넘어간다.
  3. 흔적을 남긴다Service Connect access logs를 켜면 어떤 통신이 언제 오갔는지 기록으로 남는다. 중계는 Envoy라는 프록시가 담당한다.
  4. 확인해 볼 것서비스 연결 화면에서 TLS 인증서 상태와 영역별 대상 주소가 보이는지 확인한다.

#1문제 상황

인스턴스가 고장 나거나 스케일 인으로 줄면 태스크들이 한쪽 가용 영역에 몰린다. 그러면 그 영역 장애 때 서비스 전체가 영향을 받고 배포도 느려진다.

#2핵심 질문

#4동작 과정

  1. 조건을 정한다첫 배치 전략이 Availability Zone spread이거나 전략이 없을 때가 대상이다. 여러 영역에 태스크를 흩는 순서가 정해져 있어야 재분산을 판단할 수 있다.
  2. 몰림을 찾는다ECS가 영역별 태스크 수를 계산해 한 영역에 치우친 것을 찾아낸다. 그런 태스크들을 다른 영역의 인스턴스로 옮기는 것이 리밸런싱이다.
  3. 멈추고 확인한다리밸런싱 상태가 서비스별로 표시되며 필요하면 진행 중인 리밸런싱을 중지할 수 있다. 옮기는 동안 기존 태스크는 계속 요청을 받는다.
  4. 확인해 볼 것서비스의 태스크 목록에서 같은 영역에 남는 태스크 수가 고르게 나눠졌는지 확인한다.

먼저 알아야 할 것 07-01

#1문제 상황

트래픽이 몰릴 때 태스크 수를 손으로 늘리면 늘리는 시점이 늦고, 줄이는 판단도 매번 사람이 해야 한다. Amazon ECS는 CloudWatch로 서비스의 평균 CPU와 메모리 사용량을 퍼블리시하므로 이 지표를 그대로 판단 재료로 쓸 수 있다.

service auto scaling은 Application Auto Scaling을 통해 그 판단을 자동화한다. 목표값 추적(target tracking)은 정한 지표를 목표값에 맞추고, 단계 조정(step scaling)은 지표가 임계값을 넘은 폭에 따라 정해진 수만큼 한 번에 늘린다.

#2핵심 질문

부하에 따라 태스크 수를 늘리고 줄이는 판단을 어떻게 자동화할까?

#3동작 예시

평일 낮 업무 시간이면 CPU가 오른다. 목표값 추적 스케일링 정책이 CPU 목표치를 넘으면 ECSServiceAverageCPUUtilization 지표를 보고 태스크를 추가하고, 저녁에 사용량이 떨어지면 다시 뺀다. 시작과 종료는 최소 최대 작업 수 안에서만 움직인다.

#4동작 과정

  1. 기준을 정한다target tracking scaling policy로 목표 지표와 목표값을 고른다. ECSServiceAverageCPUUtilization과 ECSServiceAverageMemoryUtilization 같은 지표를 쓰며, 정한 값을 유지하도록 태스크 수를 늘리고 줄인다.
  2. 단계를 나눈다step scaling policy는 지표가 임계값을 넘은 폭에 따라 정해진 수만큼 한 번에 늘린다. 급한 피크에는 빠르고, 평소에는 target tracking을 쓴다.
  3. 시간을 정한다scheduled action으로 요일과 시각별 예정 수량을 지정한다. 미리 늘려 두면 늘리는 지연 없이 그 시간에 맞춰 응답한다.
  4. 확인해 볼 것서비스의 자동 조정 화면에 적용된 정책과 최근 조정 이력이 보이는지 확인한다.

#1문제 상황

target tracking은 지표가 이미 오른 뒤에야 태스크를 늘린다. 앱이 오래 걸리는 초기화 단계면 그동안 응답이 느려진다. 또 갑자기 들어온 요청은 CPU 지표에 아직 드러나지 않는다.

predictive scaling은 과거 흐름을 미리 보고 늘리며, queue-based scaling은 대기 중인 작업의 개수를 지표로 삼는다.

#2핵심 질문

지표가 오르기 전에 태스크를 미리 늘리려면?

#3동작 예시

#4동작 과정

  1. 흐름을 본다과거 지표를 분석해 앞으로 필요한 수를 추정한다. 주기적 트래픽과 정해진 주기로 켜고 꺼지는 작업, 시작이 오래 걸리는 앱에서 효과가 크다.
  2. 정책을 정한다예측 스케일링 정책이 custom metrics와 metric math expression으로 만든 지표를 재료로 삼는다. 대상 시간대를 지정하면 그 구간은 동적 스케일링 대신 예측값을 따른다.
  3. 큐로 본다처리할 작업이 SQS 큐에 쌓이는 구조라면 queue-based scaling을 쓴다. 큐 적체량을 지표로 삼아 태스크를 미리 늘리고, 처리가 끝나면 다시 줄인다.
  4. 확인해 볼 것CloudWatch 알람 화면에서 SQS 큐 길이 지표를 스케일링 정책에 붙인 것이 보이는지 확인한다.

#1문제 상황

CPU는 전체 vCPU를 1024로 나눈 단위로, 메모리는 mebiby이트로 잰다. 어떤 조합을 고르는지가 태스크 사이즈 결정이며, 그것이 인스턴스에 몇 개를 채워 넣는지와 이어진다.

#2핵심 질문

한 태스크에 줄 CPU와 메모리를 어떻게 정해야 할까?

#3동작 예시

CPU 512 단위와 메모리 1GiB로 태스크를 정의한다. 이 예약량만 채워질 자리가 있는 인스턴스에만 ECS가 태스크를 붙인다. 실제 앱이 더 쓰는 CPU는 한계선 안에서 bursting으로 더 쓸 수 있다.

#4동작 과정

  1. 예약과 한계를 나눈다resource reservations는 태스크에 보장되는 최소 자원이고 limits는 그 태스크가 쓸 수 있는 최댓값이다. 예약량은 반드시 채워질 자리가 있는 인스턴스에 대해서만 배치가 일어난다.
  2. 비율을 잰다ECS에서 CPU 와 메모리의 비율을 정하면 그 조합이 되는 태스크 크기가 정해진다. 앱이 평소에 얼마나 먹는지를 보고 가깝게 잡아야 태스크가 많이 올라간다.
  3. 밀도를 본다이 크기가 인스턴스 몇 개를 채우는지가 binpack과의 관계다. 크게 잡을수록 한 인스턴스에 붙는 태스크 수가 줄어 오버프로비저닝, 즉 남는 자리가 늘어난다.
  4. 확인해 볼 것태스크를 여러 개 올린 인스턴스에서 남는 CPU와 메모리가 얼마나 되는지 확인한다.

#1문제 상황

대규모 서비스에서는 배포와 스케일링이 한꺼번에 몰려 Amazon ECS API를 끊임없이 호출한다. 모든 고객이 같은 성능을 받도록 API request throttling, 즉 정해진 시간 동안 허용되는 호출 수가 있다.

그 한계를 넘으면 ThrottlingException 오류로 명령이 실패한다. 개발자 도구에서 태스크를 못 띄우고 배포가 멈춘 것처럼 보인다. 그래서 service quotas, 즉 계정과 리전별로 정해진 호출 한도를 확인하고 필요하면 할당량 상향을 요청해야 한다.

#2핵심 질문

#3동작 예시

배포 스크립트가 DescribeClusters를 반복 호출하다가 Rate exceeded 메시지를 받고 멈춘다. 팀은 Amazon ECS 콘솔의 할당량 화면에서 ECS API 호출 한도와 AWS Fargate throttling quotas를 확인한다.

한도가 낮으면 상향 요청을 넣고, 그사이엔 재시도와 지수 백오프를 넣어 호출 간격을 늘린다.

#4동작 과정

먼저 알아야 할 것 03-01

#1문제 상황

컨테이너는 다시 만들어지면 안의 파일이 사라진다. 로그나 업로드물을 잠깐 두는 것과 서비스 재시작 후에도 남기는 것을 같은 방식으로 처리할 수 없다.

그래서 태스크 정의에서 volume을 고르고 각 컨테이너의 mountPoints에 경로를 연결한다. 다른 컨테이너가 그 볼륨을 빌려 쓰게 하는 volumesFrom도 함께 정한다.

#2핵심 질문

데이터를 어디에 붙여야 용도에 맞는 보존과 성능을 얻는가?

#3동작 예시

한 태스크에 웹 서버 컨테이너와 로그 처리 컨테이너를 함께 둔다. 서비스가 관리하는 태스크라 컨테이너가 재생성돼도 로그가 남도록 Fargate ephemeral storage를 넉넉히 잡고 같은 볼륨을 두 컨테이너에 붙인다. 운영에서는 볼륨 선택 기준에 따라 유지가 필요한 데이터는 다른 방식으로 분리한다.

#4동작 과정

  1. 용도를 나눈다잠깐 쓸 데이터면 태스크와 함께 사라지는 ephemeral storage를 쓴다. 남겨야 하는 데이터면 아래 방식 중 하나를 고른다.
  2. 지속 볼륨을 고른다블록 단위 고성능 저장을 원하면 Amazon EBS 볼륨을, 여러 태스크가 같은 디렉터리를 함께 써야 하면 Amazon EFS 볼륨을 쓴다. 각각 적용 가능한 컴퓨팅 환경이 정해져 있다.
  3. 붙인다태스크 정의의 volume과 컨테이너의 mountPoints로 연결하고, 공유가 필요하면 volumesFrom으로 다른 컨테이너에 빌려 준다. 빌려 준 컨테이너는 경로를 다시 쓰지 않고 그 볼륨을 본다.
  4. 확인해 볼 것태스크 정의에서 각 컨테이너에 붙은 볼륨 경로가 목록에 보이는지 확인한다.

AWS 블록 스토리지 서비스인 Amazon EBS의 볼륨을 태스크에 붙여 컨테이너가 재시작되어도 유지되는 데이터 영역을 쓰고, 필요하면 스냅샷으로 되돌리거나 암호화까지 지정하는 방법이다.

먼저 알아야 할 것 10-01

#1문제 상황

데이터베이스가 들어 있는 컨테이너가 서비스 갱신으로 재생성되면 디스크까지 초기화된다. 애플리케이션 데이터는 계속 쌓이면서 재시작마다 지워지면 안 된다.

Amazon ECS가 Amazon EBS 볼륨을 대신 붙여 주고 관리한다. 재시작 후에도 블록 단위의 빠르고 안정적인 저장소를 그대로 쓴다.

#2핵심 질문

데이터를 잃지 않는 블록 저장소를 태스크에 어떻게 붙이는가?

#3동작 예시

단독 태스크를 실행할 때 볼륨 설정을 넘기면 새 빈 볼륨이 붙는다. 볼륨 스냅샷을 지정하면 그 내용으로 볼륨이 채워져 데이터베이스가 이어진다. 스냅샷에서 데이터를 가져오는 속도는 volumeInitializationRate로 정한다.

#4동작 과정

  1. 설정을 넘긴다단독 태스크 실행 또는 서비스 생성·갱신 시 volumeConfiguration으로 볼륨 한 개의 구성을 준다. 서비스가 관리하는 태스크에는 태스크마다 볼륨 하나가 붙는다.
  2. 볼륨을 채운다새 빈 볼륨을 쓰거나 스냅샷으로 기존 데이터를 불러온다. 암호화가 필요하면 AWS KMS 키를 지정한다.
  3. 쓰게 한다볼륨은 EC2 인스턴스 유형에서 컨테이너 사용자 권한으로 접근된다. Fargate에서는 성능 한계가 낮으므로 더 큰 디스크가 필요하면 다른 방식을 함께 고려한다.
  4. 확인해 볼 것서비스의 태스크를 조회하면 각 태스크에 붙은 볼륨 목록이 보인다.

먼저 알아야 할 것 10-01

#1문제 상황

업로드 이미지나 공용 설정 파일처럼 여러 컨테이너가 함께 읽고 써야 하는 데이터가 있다. 태스크마다 따로 붙이면 파일이 갈라지고, 컨테이너 안의 디스크에 두면 사라진다.

Amazon EFS 볼륨은 컨테이너 인스턴스 어느 곳에 태스크가 놓여도 같은 영속 저장소를 보게 한다. 용량은 파일 추가·삭제에 맞춰 자동으로 늘고 줄어든다.

#2핵심 질문

여러 태스크가 같은 파일을 동시에 보게 어떻게 붙이는가?

#3동작 예시

서비스를 여러 태스크로 늘리면 각 태스크가 다른 인스턴스에 놓인다. 그럼에도 efsVolumeConfiguration에 지정한 파일 시스템의 같은 디렉터리를 읽고 쓰며, 읽기 전용이 아니라 쓰기가 필요한 위치에만 권한을 좁힌 accessPointId를 쓴다. transitEncryption을 켜면 파일 시스템과 컨테이너 사이를 오가는 데이터를 암호화한다.

#4동작 과정

  1. 파일 시스템을 붙인다태스크 정의의 volumes에 efsVolumeConfiguration으로 Amazon EFS 파일 시스템 ID와 컨테이너 안 경로를 적는다. 그 경로에 볼륨이 붙는다.
  2. 접근을 좁힌다accessPointId로 그 볼륨의 한 지점만 열고 그 아래 권한을 정한다. 여러 컨테이너가 같은 볼륨을 보더라도 경로는 나눠진다. transitEncryption으로 오가는 데이터를 암호화할 수 있다.
  3. 여러 태스크가 함께 쓴다태스크가 어느 컨테이너 인스턴스에 배치되든 같은 파일을 본다. 그래서 서비스의 태스크 수를 늘려도 데이터는 하나로 모인다.
  4. 확인해 볼 것태스크 정의에서 각 컨테이너의 마운트 경로가 EFS 볼륨을 가리키는지 확인한다.

Windows 파일 서버인 FSx for Windows File Server 볼륨을 태스크에 마운트해 여러 Windows 컨테이너가 공유 파일 저장소를 읽고 쓰게 하는 방법이다.

먼저 알아야 할 것 10-01

#1문제 상황

Windows 앱은 공유 파일 저장소를 요구하는 경우가 많다. 쓰기만 하는 임시 디스크로는 부족하고, 여러 Windows 컨테이너 인스턴스가 같은 디렉터리를 함께 봐야 한다.

FSx for Windows File Server를 쓰면 Windows 태스크에 영속적이고 분산된 공유 파일 저장소를 붙일 수 있다. 한 개 이상을 한 컨테이너에 마운트할 수 있다.

#2핵심 질문

Windows 컨테이너가 공유할 수 있는 영속 파일 서버를 어떻게 붙이는가?

#3동작 예시

Windows 인스턴스 위에서 도는 ECS 컨테이너에 공유 파일이 필요하다. 태스크 정의에서 FSx for Windows File Server 볼륨의 fileSystemConfig로 파일 서버 이름과 rootDirectory를 지정하고 마운트 경로를 연결한다. 컨테이너는 서버가 관리하는 디스크 대신 공유 디렉터리에 파일을 남긴다.

#4동작 과정

  1. 경로를 지정한다볼륨에 fileSystemConfig로 파일 서버와 그 안의 rootDirectory를 적는다. 태스크 정의에서 이 볼륨의 이름과 마운트 경로를 컨테이너에 연결한다.
  2. 여러 컨테이너가 함께 쓴다공유 디스크가 필요해 한 컨테이너에 여러 볼륨을 붙이고, 같은 볼륨을 다른 컨테이너에도 공유할 수 있다. 데이터는 인스턴스마다 흩어지지 않는다.
  3. 환경 제약을 지킨다Windows 컨테이너 전용이다. Fargate의 Windows 구성에서는 이 볼륨을 쓸 수 없고, EC2의 Windows 인스턴스에서만 붙는다.
  4. 확인해 볼 것Windows 태스크의 컨테이너 목록에서 FSx 볼륨이 마운트 경로와 함께 보이는지 확인한다.

10단계 저장소와 볼륨 — 데이터가 어디에 붙는가

태스크 정의의 volumes 항목을 통해 호스트 디렉터리를 그대로 컨테이너에 노출하는 bind mount 와, S3 버킷을 읽기 전용 폴더처럼 붙이는 S3 Files 같은 가장 단순한 데이터 연결 방식을 다룬다.

먼저 알아야 할 것 10-01

#1문제 상황

Docker는 컨테이너 이미지를 빌드하고 실행하는 소프트웨어다. 외부에서 받아 온 파일을 컨테이너에 그대로 노출해야 한다. 설정 파일이나 로그는 컨테이너 안의 디스크에 두면 컨테이너가 바뀔 때 사라진다.

태스크 정의의 volumes 항목으로 연결 경로를 지정한다. bind mount는 호스트 디렉터리를 그대로 노출하고, Amazon S3 Files 볼륨은 버킷을 폴더처럼 붙인다.

#2핵심 질문

호스트의 데이터와 S3 버킷을 컨테이너에 어떻게 그대로 붙이는가?

#3동작 예시

설정 파일을 이미지 대신 호스트 디렉터리에 두고 태스크 정의에서 bind mount로 노출한다. 컨테이너는 그 경로의 파일을 그대로 읽고 수정 결과가 호스트에 남는다. 배포 스크립트에서 올린 파일은 S3 버킷에 두고 Amazon S3 Files 볼륨으로 읽기 전용 폴더처럼 붙인다.

#4동작 과정

  1. 볼륨 항목을 적는다태스크 정의의 volumes에 dockerVolumeConfiguration을 넣고 컨테이너에 마운트 경로를 연결한다. Docker 볼륨은 인스턴스의 /var/lib/docker/volumes 아래에 Docker가 디렉터리를 만들어 저장한다.
  2. 호스트 경로를 연다bind mount를 쓰면 hostPath로 지정한 호스트 디렉터리가 컨테이너 안 경로에 그대로 나타난다. 로그와 설정처럼 바깥에서 관리할 데이터에 쓴다.
  3. 버킷을 붙인다Amazon S3 Files 볼륨을 쓰면 S3 버킷이 컨테이너의 폴더로 나타난다. 이미지가 담긴 파일을 따로 디스크에 복사하지 않고 읽어 쓴다.
  4. 확인해 볼 것태스크 정의에서 컨테이너별 마운트 경로와 그 경로에 연결된 볼륨 종류가 어떻게 보이는지 확인한다.

CloudWatch 지표와 Container Insights

ECS 가 태스크·컨테이너의 CPU·메모리 사용량 같은 수치를 CloudWatch 지표로 남기고, Container Insights 를 켜면 이 수치를 대시보드 형태로 모아 보는 것입니다.

먼저 알아야 할 것 04-04

#1문제 상황

태스크가 살아도 느려지는 원인은 컨테이너 안에서만 드러납니다. 밖에서는 태스크가 실행 중이라는 사실만 보입니다(→ 11-05).

Amazon CloudWatch 지표는 ECS 가 CPU·메모리 사용량을 1분마다 남기는 수치입니다. CPUReservation은 클러스터나 서비스에서 예약한 CPU 비율이고, CPUUtilization과 MemoryUtilization은 실제 사용 비율입니다. Container Insights를 켜면 이 수치를 모아 하나의 화면에서 볼 수 있습니다.

#2핵심 질문

실행 중인 태스크와 컨테이너의 자원 사용량을 어디에서 한눈에 볼까?

#3동작 예시

주문 서비스가 느려져 CloudWatch에서 Container Insights 대시보드를 연다. 서비스와 태스크 단위로 묶인 그래프에서 Fargate 사용량 지표의 급등이 보인다.

클릭해 내려가면 어느 태스크가 한계에 닿았는지 알 수 있고, Container Insights의 enhanced observability를 켜 두면 컨테이너 단위까지 내려간다.

#4동작 과정

  1. 수치화한다ECS 가 1분마다 Amazon CloudWatch 지표를 보낸다. 태스크가 RUNNING 상태일 때만 값이 실리고, 태스크가 없으면 그 구간에는 지표가 없다.
  2. 모은다Container Insights가 클러스터·서비스 단위 지표를 하나의 대시보드로 합친다.enhanced observability를 켜면 태스크와 컨테이너 단위까지 쪼개 보여 준다.
  3. 확인해 볼 것Container Insights 대시보드에서 서비스 하나를 열어 태스크별 CPUUtilization 그래프가 그려지는지 본다.

컨테이너 로그 — awslogs 로 CloudWatch Logs 로 보내기

태스크 정의의 logConfiguration 에 awslogs 드라이버를 지정해 컨테이너가 출력한 표준 스트림과 에러를 CloudWatch Logs 로 자동 전송하게 만드는 설정입니다.

먼저 알아야 할 것 03-03

→ 11-01 참조

#1문제 상황

컨테이너가 출력한 내용을 봐야 원인 파악이 됩니다. 하지만 EC2에서 컨테이너를 돌리면 그 내용은 컨테이너 인스턴스의 디스크에 쌓여 그대로 사라집니다.

awslogs 드라이버는 컨테이너의 표준 출력과 에러를 CloudWatch Logs로 넘깁니다. 기본으로 잡히는 것은 컨테이너에서 직접 실행한 명령의 출력입니다.

#2핵심 질문

컨테이너가 남긴 로그를 어디에 모아 두고 어떻게 바로 확인할까?

#3동작 예시

결제가 실패한다는 고객 문의를 받는다. 태스크 정의의 logConfiguration에서 awslogs-stream-prefix를 pay로 정해 둔 상태였다.

CloudWatch Logs에서 pay 컨테이너 이름으로 시작하는 로그 스트림을 열어 마지막 오류 줄을 찾는다. 실시간으로 나오는 내용은 Live Tail로 붙어서 본다.

#4동작 과정

  1. 지정한다태스크 정의의 logConfiguration에 awslogs 드라이버와 awslogs-group, awslogs-region, awslogs-stream-prefix를 적는다. 전송할 로그 그룹과 지역이 여기서 정해진다.
  2. 보낸다컨테이너가 표준 출력과 에러에 남긴 줄이 awslogs 드라이버를 지나 CloudWatch Logs로 전달된다. EC2라면 컨테이너 인스턴스 디스크도 덜 차지한다.
  3. 확인해 볼 것CloudWatch Logs의 해당 스트림을 열어 컨테이너 명령의 출력이 시간순으로 쌓이는지 본다.

Fluent Bit 기반 라우터를 사이드카 컨테이너로 붙여 컨테이너 로그를 목적지에 맞게 가공해 Elasticsearch나 S3 같은 임의의 백엔드로 보내는 기능입니다.

먼저 알아야 할 것 11-02

→ 11-02 참조

#1문제 상황

awslogs 드라이버는 모든 로그를 CloudWatch Logs 한 곳에 모읍니다(→ 11-02). 목적지를 바꿔 보내거나 필터를 걸고 싶은 경우엔 이 한 곳으로 모으는 방식이 맞지 않습니다.

AWS FireLens는 태스크 안에 로그 라우터를 하나 더 두는 방식입니다. fluent-bit이나 fluentd가 로그를 읽어 설정된 곳으로 넘깁니다.

#2핵심 질문

컨테이너 로그를 원하는 백엔드로 보내고 중간에서 가공하려면 어떻게 하나?

#3동작 예시

운영 로그를 사내 Elasticsearch로 모아 검색하게 한다. FireLens 컨테이너를 태스크에 사이드카로 붙이고 awslogs-stream-prefix로 목적지 스트림을 정한다.

로그가 조금 지나면 Kibana에서 컨테이너별 필드가 붙은 문서가 검색된다.

#4동작 과정

  1. 붙인다FireLens 컨테이너를 사이드카로 넣으면 ECS 가 의존 관계를 맞춰 로그를 보내는 컨테이너보다 먼저 이 컨테이너를 띄운다.
  2. 읽어 간다aws-for-fluent-bit 이미지가 fluent-bit을 실행해 각 컨테이너의 로그 스트림을 읽는다. 직접 만든 fluent-bit이나 fluentd 이미지로도 대체할 수 있다.
  3. 보낸다가공한 로그를 정해진 목적지로 넘긴다. Firehose로 보내는 경우 태스크의 IAM 역할에 해당 API 호출 권한이 있어야 하며, 고처리량 로그 설정으로 목적지별 전송량을 조절한다.
  4. 확인해 볼 것FireLens 컨테이너 로그를 열어서 목적지로 보낸 기록이 남는지 확인한다.

각 태스크 안에서 호출할 수 있는 HTTP 엔드포인트와 컨테이너에 마운트되는 파일을 통해 태스크·컨테이너의 ID와 상태를 애플리케이션이 직접 조회할 수 있게 하는 통로입니다.

먼저 알아야 할 것 03-02

#1문제 상황

컨테이너는 앱 코드를 담아 이미지로부터 띄운 실행 단위다. 컨테이너 metadata file은 컨테이너 안에서 읽을 수 있는 파일이다. 애플리케이션이 자기 태스크의 ID를 모르면 다른 서비스에 자기 자신을 알릴 수 없습니다. ID를 이미지에 미리 써 넣으면 태스크가 새로 뜰 때마다 값이 틀어집니다.

task metadata endpoint는 이런 정보를 직접 넣어 주는 통로입니다.

#2핵심 질문

실행 중인 앱이 자기 태스크와 컨테이너 정보를 코드에서 어떻게 얻을까?

#3동작 예시

주문 앱이 시작할 때 다른 서비스에 자기 주소를 등록해야 한다. 환경변수에 주어진 task metadata endpoint에 접속해 태스크 정보를 읽는다.

가져온 값으로 컨테이너 ID와 로컬 IP를 알 수 있다.

#4동작 과정

  1. 연결한다컨테이너 안에서 ECS_CONTAINER_METADATA_URI로 지정한 주소로 task metadata endpoint에 접속한다. task metadata endpoint version 4를 쓰면 태스크와 컨테이너 정보를 한 번에 묶어 주는 task metadata v4 JSON을 받는다.
  2. 읽는다여기서 태스크 단위 속성, 컨테이너 단위 속성의 Docker ID와 이미지 정보, IP와 서브넷 같은 네트워크 설정, 태스크 상태와 health를 얻는다. version 3과 version 2는 주는 항목이 더 적다.
  3. 파일을 연다컨테이너 metadata file을 쓰는 방법도 있다. 컨테이너 에이전트 1.15.0부터 쓸 수 있고, ECS_CONTAINER_METADATA_FILE로 지정한 경로의 파일에서 같은 정보를 읽는다.
  4. 확인해 볼 것컨테이너 안에서 해당 경로의 파일을 열어 태스크 ID 필드가 채워져 있는지 본다.

컨테이너 헬스 체크와 태스크 건강 판정

태스크 정의에서 검사 명령과 주기·임계값을 지정해 컨테이너가 살아 있는지 주기적으로 확인하고, 실패하면 ECS 가 그 컨테이너를 죽였다 되살리는 규칙입니다.

먼저 알아야 할 것 03-04

#1문제 상황

프로세스가 살아 있어도 내부적으로 응답을 못 하는 컨테이너가 있습니다. ECS 는 프로세스 생존 여부만 보기 때문에 이 상태를 알 수 없습니다.

container health check는 앱이 직접 검사하게 하는 방법입니다.

#2핵심 질문

앱이 응답을 못 하는 상태를 어떻게 자동으로 알아내고 처리할까?

#3동작 예시

웹 서버 컨테이너가 프로세스는 살아 있지만 응답을 멈춘다. 태스크 정의에 검사 명령을 넣어 두었다가 임계값에 연속 실패하면 상태가 UNHEALTHY로 바뀐다.

이 컨테이너가 essential이면 태스크 건강 판정 결과가 실패로 뒤집혀 태스크가 재생성된다.

#4동작 과정

  1. 지정한다태스크 정의에 container health check 명령과 주기, 임계값을 적는다. 컨테이너 에이전트는 태스크 정의에 적힌 검사만 살피며, 상태는 HEALTHY와 UNHEALTHY로 표시된다. 이미지에 들어 있는 Docker 헬스 체크는 따로 보지 않고 태스크 정의 값이 이긴다.

#1문제 상황

container instance IAM role 은 그 에이전트 신원이다. 클러스터에 인스턴스를 등록하기 전에 만든다.

#2핵심 질문

태스크를 받치는 에이전트는 어떤 권한으로 AWS 자원에 접근하는가?

#3동작 예시

EC2 한 대에 ECS 에이전트를 설치하고 클러스터에 등록한다. 등록된 인스턴스가 목록에 뜨고, 이후 이 인스턴스에 태스크가 스케줄된다. 이미지 pull 과 로그 전송은 이 인스턴스 역할이 수행한다.

#4동작 과정

  1. 인스턴스 역할을 만든다container instance IAM role 을 만들고 인스턴스 프로파일에 연결한다. instance profile 은 이 역할을 인스턴스에 붙이는 통로다.
  2. 환경별 역할을 가른다Amazon ECS Anywhere IAM role 은 외부 인스턴드용이고 Systems Manager 권한도 요구한다. 로드 밸런서를 붙일 때는 별도의 infrastructure role 이 쓰인다.
  3. 확인해 볼 것클러스터 화면에서 인스턴스 목록에 해당 인스턴스가 정상 표시되는지 확인한다.

ECS 를 다룰 때 IAM 에 미리 만들어지는 권한 묶음들이다 — AmazonECS_FullAccess 같은 AWS 관리형 정책, ECS 가 다른 서비스를 대신 호출할 때 쓰는 service-linked role, 그리고 태그에 조건을 걸어 특정 태그의 리소스만 조작하게 만드는 접근 제어 방식.

먼저 알아야 할 것 12-02

→ 12-01 참조

#1문제 상황

ECS 를 다루는 IAM 권한을 매번 처음부터 쓰기는 번거롭고, 쓰고 나면 필요한 것보다 넉넉해진다. 어떤 역할은 AWS 가 대신 만들어 주기도 한다.

AWS managed policy 는 이런 권한 묶음을 미리 만들어 둔 것이다. service-linked role 은 ECS 가 다른 서비스를 대신 호출할 때 자동으로 붙는 역할이다.

#2핵심 질문

ECS 권한을 어떻게 빠르게 붙이고 어디까지 좁힐 수 있는가?

#3동작 예시

개발자에게 AmazonECS_FullAccess 를 붙였다가 테스트 태그가 붙은 서비스만 보게 좁힌다. 태그 기반 접근 제어를 켜면 태그 조건 키로 리소스를 걸러 낸다.

#4동작 과정

  1. 묶음을 붙인다AWS managed policy 를 쓰면 정책 문서를 직접 쓰지 않아도 된다. AmazonECS_FullAccess 가 대표적이며, 일부 정책은 앞으로 단계적으로 적용 범위가 좁아진다.
  2. 자동 역할을 이해한다service-linked role 은 ECS 가 CloudWatch Logs 나 CodeDeploy 같은 서비스를 호출할 때 ECS 쪽에서 만들어 두는 역할이다.
  3. 태그로 좁힌다태그 기반 접근 제어를 쓰면 조건 키에 태그를 넣어 지정한 태그의 리소스만 다루게 할 수 있다.
  4. 확인해 볼 것IAM 콘솔에서 태그 조건이 들어간 정책을 열어 어느 리소스에 걸리는지 본다.

ECS 가PCI DSS·HIPAA 같은 규제 요건을 충족하도록 구성하는 방법(Fargate Spot 금지, 암호화, 태스크 격리 등)과 FIPS 140-3 검증 모드를 쓸 때의 제약을 정리한 내용으로, 보안 설계를 처음 세울 때 확인해야 할 목록이다.

먼저 알아야 할 것 12-01

#1문제 상황

컨테이너를 그대로 배포하면 이미지에 설치된 패키지가 구버전이고, 컨테이너가 루트로 실행되며, 루트 파일 systemsystem 쓰기 가능하다. 이런 상태는 규정 준수를 요구하는 환경에서 그대로 통과하지 않는다.

AWS Fargate FIPS-140 은 검증된 암호 모듈만 쓰는 실행 모드다.

#2핵심 질문

컨테이너와 태스크를 어떻게 구성해야 규제 요건과 보안 기준을 맞출 수 있는가?

#3동작 예시

배포 파이프라인에서 이미지를 스캔하고 최소 구성 이미지로 교체한다. 태스크는 비루트 사용자로 실행하고 읽기 전용 루트 파일 systemsystem 을 붙인다. 암호화는 고객 관리 키(CMK)로 이미지 저장소에서 처리한다.

#4동작 과정

  1. 이미지를 단단하게 만든다최소 이미지나 distroless 이미지를 쓰고 취약점 스캔과 정적 코드 분석을 거친다. 불필요한 권한과 Linux capability 를 뺀다.
  2. 태스크를 조인다비루트 사용자로 실행하고 읽기 전용 루트 파일 systemsystem 을 쓴다. CPU와 메모리 한계를 지정하며, EC2 에서는 privileged 실행을 피한다.
  3. 암호와 규정을 맞춘다AWS Fargate FIPS-140 모드로 바꾸고 컴플라이언스 프로그램의 요구 범위에 맞춰 태스크 격리와 저장소 암호화를 정한다.
  4. 확인해 볼 것태스크 정의에서 user 칸이 루트가 아닌 값으로 채워져 있는지 확인한다.

stopped task 에러 코드 읽기와 트러블슈팅 도구

멈춘 태스크에 붙는 'CannotPullContainerError' 같은 사유 코드를 표로 찾아 원인을 확인하고, describe-tasks·service events 같은 AWS CLI 명령으로 실제 메세지와 이전 성공 이력을 좁혀 가는 방법.

먼저 알아야 할 것 11-05

#1문제 상황

태스크가 뜨지 않고 바로 멈췄다. 서비스 화면에는 태스크만 줄 줄 쌓일 뿐 왜 멈췄는지는 안 보인다.

stopped task reason 은 멈춘 태스크에 붙는 사유 코드다. TaskFailedToStart 나 ResourceInitializationError 같은 상위 분류와 그 아래 세분 코드가 원인을 알려 준다.

#2핵심 질문

멈춘 태스크가 왜 멈췄는지를 어느 코드에서부터 찾아야 하는가?

#3동작 예시

운영자가 멈춘 태스크를 열어 사유가 ResourceInitializationError 임을 본다. 아래 분류인 ResourceNotFoundException 이라는 점이 NetworkNotFound 인 것을 확인해 태스크 정의의 서브넷 설정을 좁힌다.

#4동작 과정

  1. 분류를 고른다stopped task reason 은 TaskFailedToStart, ResourceInitializationError, ResourceNotFoundException, SpotInterruptionError, OutOfMemoryError, ContainerRuntimeError 같은 분류 아래에 세분 코드가 있다.
  2. 메시지를 읽는다aws ecs describe-tasks 로 실제 message 를 보고, service event message 로 이력이 어디서부터 끊겼는지 좁힌다.
  3. 결론을 확인한다API failure reasons 를 확인하고 verify-connectivity 로 태스크의 네트워크가 AWS API 에 닿는지 본다. ECS logs collector 로 container agent 로그를 모아 한 번에 검토한다.
  4. 확인해 볼 것describe-tasks 결과의 stoppedReason 필드가 어떤 코드로 채워져 있는지 확인한다.
