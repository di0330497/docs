Amazon ECS

Amazon ECS(Amazon Elastic Container Service)를 클라우드 컨테이너 오케스트레이션 서비스로 해석했다. 컨테이너·클러스터·태스크 정의·서비스라는 핵심 자원 구조를 먼저 잡고, 태스크 정의 → 실행 기반(Fargate/Managed Instances/EC2/Anywhere/Express Mode) → 클러스터와 용량 → 네트워크 → 스토리지 → 스케줄링 → 서비스와 배포 전략 → 트래픽 분산과 자동 확장 → 관측성 → 권한과 보안, 그리고 마지막에 운영의 나머지(Managed Daemons, Outposts, Blue/green 후속, 태그·리포트, MCP 서버)로 흐르는 순서로 배열했다. 서브 페이지(파라미터 레퍼런스·예제·튜토리얼)는 개별 항목이 아니라 그 개념의 항목 안에 흡수시켰다.

Amazon ECS란 무엇인가 — 컨테이너 오케스트레이션의 경계

컨테이너 이미지를 AWS 위에서 원하는 수만큼 실행하고 그 실행 상태를 관리·감시하는 AWS의 컨테이너 오케스트레이션 서비스로, 어디에 배치할지와 언제 켤지를 대신 결정해 준다.

#1문제 상황

컨테이너 하나만 띄우는 일은 쉽지만, 여러 개를 켜고 죽은 것을 다시 살리며 요청량을 따라 늘리는 일은 남는다. 그걸 직접 하면 서버 준비와 장애 대응을 모두 떠안는다.

Amazon ECS는 fully managed container orchestration, 즉 컨테이너 오케스트레이션을 전부 관리형으로 해 주는 서비스다. containerized application, 즉 컨테이너로 묶인 애플리케이션의 배치와 수량 조절을 대신해 준다. 이미지는 Amazon ECR에 두고, 외부 요청은 Elastic Load Balancing으로 받으며, 작업은 AWS Region과 온프레미스 어디서든 돈다.

#2핵심 질문

컨테이너 애플리케이션을 어디에 몇 개나 돌리고 언제 다시 살릴지, 그 결정을 AWS에 맡길 수 있을까?

#3동작 예시

주문 애플리케이션을 배포한다. 이미지 한 벌을 만들어 Amazon ECR에 올리고 ECS에 올린다. 사람이 한 대의 서버를 준비하지 않아도 컨테이너 여러 개가 자동으로 켜져 있고, 하나가 죽으면 다른 것이 대신 요청을 받는다.

#4동작 과정

  1. 정한다실행할 컨테이너와 개수를 지시한다. control plane, 즉 배치를 결정하고 상태를 감시하는 ECS의 관리 영역이 어떤 컴퓨터에 놓을지와 멈춘 것을 다시 켤지를 계산한다.
  2. 배치한다지시한 수만큼 컨테이너를 실제 컴퓨터에 올린다. 서버 준비는 AWS 쪽에서 끝나므로 운영자는 이미지와 설정만 챙긴다.
  3. 감시한다실행 상태를 계속 확인한다. Elastic Load Balancing으로 요청을 healthy 상태인 컨테이너에만 보내고, 상태가 나빠지면 ECS가 다시 띄운다.
  4. 확인해 볼 것ECS 콘솔의 클러스터 화면에서 컨테이너가 몇 개 실행 중이며 어떤 상태로 표시되는지 확인한다.

Capacity·Controller·Provisioning 세 계층

ECS가 작업을 나눠 세 층으로 처리하는 구조로, 어떤 컴퓨터 자원을 쓸지(Capacity) 어떤 방식으로 돌릴지(Controller) 그 자원을 어디서 얻고 붙일지(Provisioning)를 각각 별개의 결정으로 분리한 것이다.

먼저 알아야 할 것 01-01

→ 01-04 참조

#1문제 상황

ECS를 처음 보면 설정 이름이 많아 무엇을 정해야 하는지 헷갈린다(→ 01-01). 사실 ECS는 결정을 세 층으로 나눈다.

capacity는 어떤 컴퓨터 자원을 쓸지 정하는 층이다. controller는 그 자원을 어떤 방식으로 태스크로 조립할지 정하는 층이다. provisioning은 자원을 어디서 얻어 클러스터에 붙일지 정하는 층이다. scheduler는 이 결정을 모아 태스크를 실제 자리에 놓는 기능이다. 세 층을 알면 태스크 정의 하나가 왜 그 모양인지 읽힌다.

#2핵심 질문

태스크를 돌릴 컴퓨터 자원과 실행 방식을 따로 따로 정할 수 있을까?

#3동작 예시

팀은 capacity를 인스턴스 묶음으로 고르고 controller를 서비스로 정한다. provisioning은 그 인스턴스 묶음을 자동으로 늘리도록 설정한다. 실행 자원 교체와 실행 방식 변경을 서로 건드리지 않고 바꾼다.

#4동작 과정

  1. 자원을 고른다capacity를 정한다. 어떤 컴퓨터에 태스크를 놓을 수 있는지를 정하는 기준이며, 실행 자원 종류와 조건이 여기 들어간다.
  2. 방식을 고른다controller를 정한다. 태스크를 몇 개 유지할지 같은 방식으로 돌릴지 결정한다.
  3. 붙인다provisioning을 정한다. 자원을 어디서 얻고 클러스터에 붙일지 정한 뒤, scheduler가 이 세 값을 합쳐 태스크를 놓는다.
  4. 확인해 볼 것클러스터 화면에서 어떤 용량과 어떤 스케줄러 설정이 붙어 있는지 확인한다.

다섯 가지 핵심 자원 — cluster, task definition, task, service, account setting

ECS를 다루는 다섯 개의 기본 단위로, 컨테이너 묶음인 클러스터, 실행할 컨테이너와 설정을 적은 태스크 정의, 실제로 실행 중인 태스크, 태스크 개수를 유지하는 서비스, 리전 단위 기능 스위치인 계정 설정이 이에 해당한다.

먼저 알아야 할 것 01-02

#1문제 상황

ECS 용어를 익힐 때 가장 막히는 건 같은 말 뜻이 달라 보이는 것이다. 다섯 단어만 구분해 두면 이후 문서가 읽힌다.

task definition은 실행할 컨테이너와 설정을 적은 설계 문서다. cluster는 그 태스크가 모이는 묶음이다. task는 실제로 실행 중인 태스크 하나다. service은 정해진 수의 task를 계속 유지해 주는 단위다. account setting은 리전마다 기능을 켜고 끄는 스위치다.

#2핵심 질문

ECS를 다루는 기본 단위는 무엇이고 각각 무슨 일을 하는가?

#3동작 예시

주문 서비스가 늘어난다. 콘솔에서 cluster를 열면 그 안의 service이 보인다. service는 task를 정해진 수만큼 유지하고, 각 task는 같은 task definition을 그대로 실행한다. 수를 바꾸려면 definition이 아니라 service의 목표 개수를 고친다.

#4동작 과정

  1. 설계한다task definition을 적는다. 이미지 이름과 CPU·메모리, 네트워크, 로그 설정을 JSON으로 남기면 실행 조건이 고정된다.
  2. 묶는다definition을 cluster에 연결해 태스크를 올린다. 실제로 떠 있는 것이 task이며, 하나라도 멈추면 ECS가 다시 띄운다.
  3. 지킨다service로 task 개수를 유지한다. service auto scaling과 cluster auto scaling을 켜면 수요에 따라 그 수가 자동으로 늘고 줄어든다.
  4. 확인해 볼 것ECS 콘솔에서 한 cluster 안의 service 목록과 각 service의 실행 중인 task 수를 확인한다.

#1문제 상황

태스크를 어디서 돌릴지 고를 때 후보가 여러 개라 무엇이 다른지 모른다(→ 01-03). 이 선택은 태스크 정의에도 기록되므로 되돌리기 어렵다.

launch type은 EC2, Fargate, External처럼 직접 관리하는 EC2 인스턴스 실행 기반이다. capacity provider는 AWS가 관리하는 컴퓨팅을 세분 단위로 묶어 지정하는 방식이다. 여기에는 Fargate와 Fargate Spot, 오토 스케일링 그룹 기반 EC2, Amazon ECS Managed Instances가 들어간다.

#2핵심 질문

태스크를 돌릴 실행 기반은 무엇으로 고르고 두 방식의 차이는 무엇인가?

#3동작 예시

팀은 capacity provider를 고른다. 실행 대상마다 CPU와 메모리 크기를 다르게 지정하고, 남는 자리에 Fargate Spot을 섞어 쓴다. 나중에 capacity provider strategy로 어느 대상을 먼저 채울지 정해 둔다.

#4동작 과정

  1. 고른다launch type 또는 capacity provider를 정한다. launch type이면 EC2 인스턴스를 직접 준비해 등록하고, capacity provider이면 관리형 컴퓨팅이 쓰인다.
  2. 선언한다태스크 정의의 RequiresCompatibilities에 실행 대상을 적어 둔다. 이 값은 정해 두면 나중에 바꿀 수 없다.
  3. 배정한다capacity provider strategy로 대상 중 무엇을 우선 쓸지 정한다. FARGATE_SPOT을 섞으면 중단 가능한 자리를 먼저 쓴다.

클러스터와 태스크 정의 같은 ECS 리소스를 웹 화면, 명령줄 도구, 프로그래밍 언어 라이브러리, 코드로 인프라를 선언하는 도구인 CDK를 통해 만드는 네 가지 방식이다.

먼저 알아야 할 것 01-03

#1문제 상황

ECS 리소스를 손으로 하나씩 만들면 나중에 무엇이 무엇인지 기억할 수 없다(→ 01-03). 화면에서 누르는 과정은 그대로 재현되지 않는다.

그래서 만드는 방법이 네 갈래로 나뉜다. AWS Management Console은 웹 화면이다. AWS CLI는 명령줄 도구다. AWS SDKs는 프로그래밍 언어로 호출하는 라이브러리다. AWS CDK는 코드로 인프라를 선언하는 도구다. AWS Copilot CLI는 웹앱용 배포를 간단하게 만드는 보조 도구이고, Amazon ECS MCP server는 생성 작업을 대신 처리하게 한다.

#2핵심 질문

클러스터와 태스크 정의를 어떤 도구로 만들어야 반복되는 배포를 대신할 수 있을까?

#3동작 예시

팀은 코드로 클러스터와 태스크 정의를 적어 둔다. 수정이 필요하면 코드를 고쳐 다시 적용하고, 배포 이력은 코드 저장소 기록으로 남는다. 처음 배울 때는 웹 화면으로 클러스터를 하나 만들어 흐름만 확인한다.

#4동작 과정

  1. 방법을 고른다AWS Management Console로 익히고, 반복 작업은 AWS CLI나 AWS CDK로 옮긴다. 자동화할수록 AWS SDKs를 코드에서 호출한다.
  2. 이미지를 만든다Dockerfile로 이미지를 만들고 Amazon ECR 개인 저장소에 올린다.
  3. 리소스를 만든다고른 도구로 클러스터와 태스크 정의를 등록한다. AWS Copilot CLI를 쓰면 로드 밸런서와 네트워킹까지 갖춘 배포를 함께 만든다.

#2핵심 질문

리전마다 다른 ECS 기능 동작은 계정 설정에서 어떻게 켜고 끄는가?

#4동작 과정

  3. 확인하기항목 상태를 저장한 뒤 태스크를 새로 만든다. 이미 실행 중인 태스크에는 설정이 나중에 적용되지 않는다.

task definition의 구조와 revision

태스크 정의는 컨테이너 이미지·CPU/메모리·네트워크 같은 실행 조건을 JSON으로 미리 적어 둔 설정 문서이며, 고칠 때마다 새 revision(버전 번호)이 붙어 이전 정의는 그대로 남는다.

먼저 알아야 할 것 01-03

#1문제 상황

실행 중인 태스크의 조건을 바꾸려면 직접 고칠 수 없다. 태스크 하나하나를 손대지 않고도 바뀐 조건을 안전하게 굴려야 한다.

task definition은 그 조건을 JSON으로 적어 둔 설계 문서다. family 이름 아래에 revision이라는 버전 번호가 붙고, 고칠 때마다 새 revision이 추가된다. task definition state는 그 정의가 활성 상태인지 표시한다. registerTaskDefinition은 새 revision을 등록하는 호출이다.

#2핵심 질문

태스크가 어떻게 실행될지 미리 적어 두고, 바뀐 내용을 되돌릴 수 있게 버전을 남기는 방법은 무엇인가?

#3동작 예시

메모리 설정이 부족해 태스크가 반복해서 죽는다. task definition에서 메모리를 올려 registerTaskDefinition을 다시 부른다. 서비스가 새 revision을 받아 태스크를 차례로 교체하고, 이전 revision은 그대로 남아 있어 문제가 생기면 그 버전으로 되돌린다.

#4동작 과정

  1. 적을 수를 정한다어떤 값을 넣을지 고른다. 이미지, CPU와 메모리, 네트워크 모드, 로그 설정, 컨테이너 명령, 볼륨, IAM 역할이 여기에 든다.
  2. 등록한다registerTaskDefinition을 부르면 family 아래 새 revision이 생긴다. requiresCompatibilities로 EC2나 Fargate 같은 실행 대상을 함께 선언한다.
  3. 사용한다서비스가 새 revision을 받아 태스크를 교체한다. 실패하면 이전 revision을 다시 지정해 되돌린다.
  4. 확인해 볼 것태스크 정의 목록에서 같은 family 이름에 revision 번호가 여러 줄로 쌓여 있는 것을 확인한다.

#4동작 과정

  1. 컨테이너를 명세한다container definition 블록을 만들어 실행할 컨테이너를 하나씩 적는다. image는 사용할 이미지 이름과 태그이고, command와 entryPoint는 컨테이너 안에서 실행할 프로그램과 그 인자를 지정한다.

runMode는 태스크를 EC2 인스턴스형이나 Fargate 같은 서버리스 방식으로 어디서 돌릴지 정하는 값이고, 태스크 크기(CPU·메모리)는 컨테이너가 실제로 사용할 연산 자원과 메모리 양을 정한다.

먼저 알아야 할 것 02-02

#1문제 상황

ECS에서 용량은 CPU와 메모리 두 지표로 표현된다. CPU는 1/1024 vCPU 단위이고 메모리는 MiB 단위다. 태스크를 올릴 자원이 어디에서 얼마만큼 나오는지는 실행 기반을 고르지 않으면 정해지지 않는다.

cpu와 memory를 태스크 크기로 지정하고 runMode로 실행 기반을 고르면, 그만큼의 자리가 확보된 곳에서 태스크가 시작된다.

#2핵심 질문

태스크가 실행될 자원을 얼마나 준비하고 어느 방식 위에 올릴지 어떻게 함께 정하는가?

#3동작 예시

운영자가 API 서버 태스크에 cpu와 memory를 적은 뒤 등록한다. runMode가 FARGATE면 AWS가 그 크기의 서버를 준비하고, EXTERNAL이면 고객이 준비한 외부 인스턴스에, MANAGED_INSTANCES이면 AWS가 관리하는 EC2 인스턴스에 태스크가 올라간다.

화면에는 태스크 크기와 실행 기반이 그대로 함께 표시된다.

#4동작 과정

  1. 크기를 적는다cpu와 memory로 태스크 크기를 정한다. 예약(reservation)한 양은 보장되며 실제 사용은 그 이상 늘어날 수 있는데 이를 bursting이라 한다.
  2. 한도를 함께 정한다softMemoryLimit과 hardMemoryLimit으로 메모리 상한을 지정한다. 상한은 태스크 크기에 허용된 범위 안에서 정한다.
  3. 실행 기반을 고른다runMode에 FARGATE, EXTERNAL, MANAGED_INSTANCES 중 하나를 넣는다. FARGATE는 서버리스 컴퓨트(→ 03-01)이고 나머지는 인스턴스를 직접 준비하거나 AWS에 맡긴다.
  4. 확인해 볼 것태스크 정의의 CPU·메모리 칸에 적은 값과 runMode가 요청한 값으로 저장되어 있는지 확인한다.

awslogs 드라이버는 컨테이너 표준 출력을 CloudWatch Logs로 보내고, FireLens(Fluent Bit 기반)는 여러 목적지로 로그를 모아 보낼 수 있는 라우터를 태스크 안에서 함께 띄운다.

먼저 알아야 할 것 02-02

#1문제 상황

컨테이너가 남긴 로그는 기본적으로 STDOUT와 STDERR라는 표준 출력 스트림에 들어 있다. 그대로 두면 EC2 기반에서는 컨테이너 인스턴스의 디스크를 차지하고 확인하려면 컨테이너마다 들어가야 한다.

logConfiguration으로 logDriver를 지정하면 이 로그가 Amazon CloudWatch Logs로 모여 어디서든 태스크와 서비스 단위로 볼 수 있다. awslogs는 표준 출력을 그대로 넘기는 드라이버이고 FireLens는 여러 목적지로 분기해 보내는 라우터다.

#2핵심 질문

컨테이너의 표준 출력을 한곳에 모아 두고 확인하려면 어떻게 설정하는가?

#3동작 예시

운영자가 주문 서비스 태스크의 컨테이너 정의에 logConfiguration을 넣고 logDriver를 awslogs로 지정한다. 태스크가 올라가면 컨테이너가 출력한 줄이 CloudWatch Logs의 로그 그룹 아래 awslogs-stream-prefix로 접두된 스트림에 쌓인다.

콘솔에서 그 스트림을 열어 컨테이너가 뱉은 문장을 그대로 본다.

#4동작 과정

  1. 드라이버를 고른다logConfiguration의 logDriver를 정한다. awslogs는 표준 출력을 CloudWatch Logs로 바로 넘기고, FireLens는 AWS for Fluent Bit 기반 라우터를 태스크 안에서 함께 띄워 여러 목적지로 보낸다.
  2. 보낼 이름을 정한다awslogs-stream-prefix로 로그 스트림 이름의 접두 부분을 정한다. 한 태스크의 여러 컨테이너 로그가 같은 이름 아래 나란히 쌓인다.
  3. 확인해 볼 것CloudWatch Logs에서 해당 태스크의 로그 그룹 안에 컨테이너 출력 줄이 시간순으로 들어 있는지 확인한다.

환경 변수와 평문 secrets는 태스크 정의에 값을 그대로 적어 넣는 방식이고, Secrets Manager나 SSM Parameter Store를 참조하면 비밀번호 같은 비밀값이 문서에 노출되지 않고 실행 시점에 주입된다.

먼저 알아야 할 것 02-02

#1문제 상황

애플리케이션은 데이터베이스 비밀번호나 API 키 같은 sensitive data를 자주 쓴다. 이 값을 태스크 정의에 평문으로 적으면 JSON 문서와 그 사본 어디에나 노출된다.

environment variable와 secrets를 사용해 값을 지정하되, 비밀은 AWS Secrets Manager나 Systems Manager Parameter Store에서 가져와 실행 시점에 주입하게 만든다.

#2핵심 질문

비밀값을 태스크 정의 문서에 남기지 않고 컨테이너에 넣으려면 어떻게 지정하는가?

#3동작 예시

운영자가 DB 비밀번호를 Secrets Manager에 저장해 두고 태스크 정의의 secrets 항목에 그 시크릿 이름과 키를 적는다. 태스크가 시작되면 그 자리에서 실제 값이 조회되어 컨테이너의 환경 변수로 들어간다.

태스크 정의 JSON에는 값 대신 참조만 남아 있다.

#4동작 과정

  1. 일반 설정은 환경 변수로 넣는다environment variable로 이름과 값을 태스크 정의에 직접 적어 컨테이너에 전달한다. 값이 많으면 environment file로 묶어 넣을 수도 있다.
  2. 비밀은 참조만 적는다secrets에 AWS Secrets Manager 또는 Systems Manager Parameter Store의 시크릿 이름과 키를 적는다. 조회 권한은 태스크 role로 주어진다(→ 11-01).
  3. 확인해 볼 것태스크 정의 화면의 secrets 항목에 값이 아니라 시크릿 이름만 적혀 있는지 확인한다.

먼저 알아야 할 것 02-02

#1문제 상황

컨테이너가 스스로 끝나거나 오류로 죽으면 태스크 전체를 교체해야 한다. 하지만 정상 종료 코드 0으로 끝난 배치 작업까지 다시 띄울 필요는 없다.

container restart policy와 dependsOn을 쓰면 재시작할지 여부와 컨테이너 시작 순서를 태스크 정의에서 정할 수 있다.

#2핵심 질문

컨테이너가 끝났을 때 다시 띄울지, 그리고 어떤 순서로 띄울지를 어떻게 정하는가?

#3동작 예시

운영자가 태스크 정의에 두 컨테이너를 두고 첫 컨테이너의 restartPolicy를 활성화하고 dependsOn으로 정상 상태가 될 때까지 두 번째를 기다리게 한다.

첫 컨테이너가 예기치 않게 종료되면 ECS가 태스크를 교체하지 않고 그 컨테이너만 다시 띄우며, 재시도 횟수는 containerStatuses에서 볼 수 있다.

#4동작 과정

  1. 재시작 조건을 정한다container restart policy를 활성화하면 컨테이너가 종료될 때 ECS가 태스크를 새로 만들지 않고 그 컨테이너만 다시 실행한다. 기본값은 꺼짐이다.
  2. 재시작 예외를 정한다ignoredExitCodes에 성공을 뜻하는 0 같은 종료 코드를 적어 그 경우 재시작하지 않게 한다. restartPolicy에는 재시도를 시도하기 전에 컨테이너가 성공적으로 실행되어야 하는 시간을 적는다.
  3. 시작 순서를 잡는다dependsOn으로 앞 컨테이너가 정상 상태가 될 때까지 뒤 컨테이너를 기다리게 한다. 상태는 task 메타데이터 엔드포인트나 CloudWatch Container Insights로 본다(→ 10-03).
  4. 확인해 볼 것컨테이너 상태 화면에서 앞 컨테이너가 RUNNING인 뒤에 뒤 컨테이너가 시작되어 있는지 확인한다.

인스턴스를 미리 만들지 않고 컨테이너 실행에 필요한 CPU·메모리만 지정해 제출하면, AWS 가 그만큼의 서버를 잠깐 만들어 실행해 주는 서버리스 컨테이너 실행 방식이다.

먼저 알아야 할 것 01-04

#1문제 상황

컨테이너를 직접 돌리려면 서버 종류를 고르고 클러스터 크기를 정하고 어디에 태스크를 어떻게 채울지 직접 최적화해야 한다. launch type을 EC2로 두면 이 부담이 전부 고객 몫이다(→ 01-04).

AWS Fargate는 이 준비와 확장을 맡아 준다. serverless 방식이므로 인스턴스 준비 없이 태스크와 서비스만 실행한다.

#2핵심 질문

인스턴스를 만들지 않고 CPU·메모리만 정해서 컨테이너를 실행하려면 무엇을 쓰는가?

#3동작 예시

개발자가 이미지 묶음과 CPU·메모리 요구량, 네트워킹과 IAM 정책을 정해 태스크를 실행한다. AWS Fargate가 그 크기의 실행 환경을 만들어 컨테이너를 띄운다.

각 태스크는 커널·CPU·메모리·ENI를 다른 태스크와 공유하지 않는 고립 경계를 갖는다. 요금은 pay-as-you-go로 사용한 만큼 낸다.

#4동작 과정

  1. 선언해 실행한다이미지 패키징, CPU·메모리 요구량, 네트워크와 IAM 정책을 정해 태스크와 서비스를 실행한다. 인프라 준비·설정·스케일 조정을 따로 하지 않아도 된다.
  2. 호환을 표시한다태스크 정의의 requiresCompatibilities에 launch type FARGATE를 넣어 이 정의가 Fargate에서 돌아갈 수 있음을 밝힌다.
  3. 저렴한 실행도 고른다중단 가능한 워크로드에는 Fargate Spot으로 대체 실행 지점을 얻을 수 있고, pay-as-you-go 방식으로 비용이 붙는다.
  4. 확인해 볼 것ECS 콘솔의 태스크 목록에서 실행된 태스크의 리전과 실행 기반이 Fargate로 표시되는지 확인한다.

#5한 줄 요약

AWS Fargate서버 준비와 스케일 결정을 대신 맡아 CPU·메모리만 지정하면 컨테이너가 실행되게 하는 것

플랫폼 버전이라는 이름 뒤에 1.4.0 같은 숫자를 붙여 Fargate 런타임(커널·도커 등)의 버전 묶음을 고르는 것으로, 숫자를 고정한 채로 업데이트되지 않는다.

먼저 알아야 할 것 03-01

→ 03-01 참조

#1문제 상황

AWS Fargate에서 태스크는 계층적으로 버전이 다른 운영체제와 컨테이너 런타임 위에서 돈다. 환경이 조용히 바뀌면 같은 코드가 다른 상태로 돌아 실행 결과가 달라진다.

platform version은 이 런타임 묶음의 버전을 고정한 이름이다. Amazon Linux 2는 1.3.0, Bottlerocket은 1.4.0 같은 숫자를 쓴다.

#2핵심 질문

태스크가 돌릴 커널과 컨테이너 런타임의 버전을 어떻게 고정하고 갱신하는가?

#3동작 예시

운영자가 태스크 실행이나 서비스 생성 시 platform version을 고른다. 그 태스크는 실행 기간 동안 해당 platform version의 한 revision에서만 돈다.

보안 문제가 발견되면 AWS는 같은 이름의 새 revision을 만든다. 새 태스크는 항상 최신 revision에서 시작하고, 실행 중인 태스크는 그대로 둔다.

#4동작 과정

  1. 버전 이름을 고른다platform version은 커널과 컨테이너 런타임 버전의 조합이다. 운영체제 계열마다 Linux platform version과 Windows platform version이 따로 있다.
  2. LATEST를 쓴다LATEST를 지정하면 항상 새 revision이 시작된다. 새 태스크는 보안 패치가 반영된 최신 인프라에서 뜨게 된다.
  3. 갱신을 확인한다기존 버전이 지원 범위를 벗어났는지 platform version deprecation 상태로 확인한다.
  4. 확인해 볼 것실행한 태스크 상세에서 platform version 이름과 revision 번호가 표시되는지 확인한다.

#5한 줄 요약

플랫폼 버전Fargate 런타임 묶음의 버전을 이름으로 고정해 실행 환경이 조용히 바뀌지 않게 하는 것

Fargate의 제약 — Linux·Windows·저장소 한계

Fargate는 OS 계열별로 정해진 CPU·메모리·EPH와 임시 디스크 크기 안에서만 도커나 ECR 이미지를 쓸 수 있어, 그 범위를 넘는 작업은 EC2 기반 실행으로 넘어가야 한다는 뜻이다.

먼저 알아야 할 것 03-02

→ 03-01 참조

#1문제 상황

Fargate(→ 03-01)는 태스크 정의의 모든 설정을 그대로 받지는 못한다. gpu, ipcMode, privileged, maxSwap 같은 항목은 아예 쓸 수 없고, volumes와 linuxParameters는 쓸 수 있어도 기능이 줄어든다. Windows containers on Fargate는 Windows 계열 태스크 정의가 따로 정해져 있어 이 차이도 함께 생긴다. CPU·메모리·임시 디스크 크기도 정해진 범위를 넘을 수 없다.

범위를 넘는 작업은 launch type EC2(→ 03-05)로 넘어가야 한다. Fargate의 한계를 알면 실행 기반을 고를 수 있다.

#2핵심 질문

Fargate에서 태스크를 실행할 때 무엇을 그대로 쓸 수 없는가?

#3동작 예시

운영팀이 GPU와 swap 영역이 필요한 컨테이너를 태스크 정의에 적는다. Fargate 태스크는 이 두 항목을 받지 않아 태스크 생성이 거부된다. 실행 기반을 EC2로 바꾸자 태스크가 정상적으로 올라간다.

#4동작 과정

  1. 쓸 수 없는 항목을 뺀다태스크 정의에서 Fargate 태스크는 gpu, privileged, maxSwap, extraHosts, links 등을 받지 않는다. container image pull behavior도 OS 계열마다 다른 규칙을 따라 이미지를 당겨 온다.
  2. 기능이 줄어든 항목을 확인한다linuxParameters는 capability로 CAP_SYS_PTRACE만 추가할 수 있고 devices와 tmpfs는 지원하지 않는다. gMSA도 Fargate 쪽 제약이 따로 있다.
  3. 범위를 넘는지 확인한다Linux·Windows 계열별로 정해진 CPU·메모리·EPH와 ephemeral storage 크기를 넘어서면 그 요구는 Fargate에서 그대로 돌릴 수 없다.
  4. 확인해 볼 것태스크 정의 편집 화면에서 cpu, memory, ephemeralStorage, osFamily 값을 보고 정해진 조합 안에 들어가는지 확인한다.

#5한 줄 요약

Fargate의 제약은 태스크 정의의 모든 설정을 받지 못하는 대신 CPU·메모리·임시 디스크의 정해진 범위 안에서만 도커와 ECR 이미지를 돌린다는 것입니다.

Amazon ECS Managed Instances — AWS 가 관리하는 EC2

ECS가 고객 대신 EC2 인스턴스의 생성·등록·패치·관리를 수행하는 컴퓨트 방식으로, 고객은 클러스터를 만들되 그 위 인스턴스를 직접 운영하지 않는다.

먼저 알아야 할 것 01-04

#1문제 상황

Fargate(→ 03-01)는 서버를 신경 쓰지 않아 편하지만 GPU 가속이나 특정 CPU 아키텍처처럼 특수한 인스턴스 기능은 쓸 수 없다. 그러면 인스턴스를 직접 만들어 ECS에 등록해야 하는데 관리가 붙는다.

Amazon ECS Managed Instances는 launch type EC2의 그 자리에 들어가되 관리 일을 AWS 가 맡는다. GPU 가속, 특별한 CPU 아키텍처, 높은 네트워크 성능, 전용 인스턴스 타입을 그대로 쓰면서 운영 부담만 뺀다.

#2핵심 질문

인스턴스를 직접 관리하지 않으면서 특수한 EC2 인스턴스 타입을 어떻게 쓰겠는가?

#3동작 예시

팀이 모델 추론에 GPU 인스턴스가 필요하다. Amazon ECS Managed Instances를 컴퓨트 방식으로 골라 인스턴스 타입으로 GPU 모델을 지정한다. 인스턴스 생성과 패치는 AWS 가 하고 팀은 GPU 태스크만 띄운다.

#4동작 과정

  1. 컴퓨트 방식을 고른다managed instance type을 지정해 EC2 인스턴스 타입 전체 범위에서 태스크를 돌릴 자리를 정한다. GPU 가속이나 특정 CPU 아키텍처가 필요할 때 여기까지 올라온다.
  2. 인스턴스를 고르고 넓힌다instance selection으로 쓸 인스턴스 종류를 좁히고, infrastructure optimization으로 트래픽에 맞춰 AWS 가 인스턴스 구성과 수를 조정한다.
  3. 패치와 수리를 맡긴다patching은 인스턴스의 OS와 드라이버 갱신을 AWS 가 수행한다. GPU가 제대로 붙지 않아 태스크가 실패하면 GPU auto repair가 문제를 감지해 해당 인스턴스를 치환한다.
  4. 확인해 볼 것클러스터 화면의 capacity provider 목록에서 Managed Instances로 등록된 인스턴스 그룹이 동작 중으로 보이는지 확인한다.

EC2 launch type과 외부 인스턴스 — 직접 관리하는 EC2

launch type EC2는 고객이 직접 준비한 Amazon EC2 인스턴스를 컨테이너 호스트로 등록해 작업을 올리는 방식이며, on-premises의 ECS Anywhere나 Outposts 같은 외부 인스턴스까지 같은 형태로 편입할 수 있다.

먼저 알아야 할 것 01-04

→ 03-01 참조

#1문제 상황

태스크가 올라갈 자리는 capacity provider와 클러스터로 정해진다(→ 04-01). 서버가 없다고 AWS 에 전부 맡기면 기능에 한계가 있고(→ 03-03), 그렇다고 모든 인스턴스를 직접 손보기는 번거롭다.

EC2 launch type은 그 중간이다. 고객이 준비한 EC2 인스턴스를 container instance로 등록해 그대로 쓴다. 사내 데이터센터나 온프레미스 장비도 External instance라는 같은 형태로 편입할 수 있다.

#2핵심 질문

직접 관리하는 컴퓨터 위에서 태스크를 어떻게 돌릴까?

#3동작 예시

사내망의 고정된 서버 한 대에 컨테이너를 올린다. 인스턴스를 ECS 클러스터에 등록해 bootstrap을 수행하면 ECS container agent(→ 04-02)가 붙는다. 그러면 같은 리전의 다른 태스크처럼 그 인스턴스에도 태스크를 배치할 수 있다.

#4동작 과정

  1. 컴퓨트 방식을 고른다태스크 정의의 launch type을 EC2로 지정해 인스턴스 위에서 직접 돌린다. 여기서 container instance는 컨테이너를 실행하는 호스트 컴퓨터를 뜻한다.
  2. 인스턴스를 붙인다준비한 인스턴스를 클러스터에 등록하고 bootstrap으로 ECS가 돌아갈 준비를 시킨다. 사내이나 데이터센터 장비는 Amazon ECS Anywhere의 External instance로 같은 절차를 거친다.
  3. 태스크를 나눠 올린다등록된 인스턴스들은 하나의 풀에 함께 들어간다. 태스크 정의(→ 02-01)를 목적별로 쪼개 만들고 서비스로 묶어 인스턴스 수보다 많은 태스크를 올릴 때 Scale out 한다.
  4. 확인해 볼 것클러스터의 container instances 목록에서 ACTIVE 상태로 표시되는 인스턴스가 몇 대인지 확인한다.

Amazon ECS Express Mode — 웹앱 배포 간소화

클라우드 매니저 콘솔이나 간단한 명령 몇 개로 로드 밸런서부터 네트워킹까지 갖춘 웹앱용 ECS 서비스가 만들어지는 즉시 사용 가능한 배포 방식이다.

먼저 알아야 할 것 03-01

#1문제 상황

웹 애플리케이션을 ECS에 올리려면 서비스와 태스크 정의를 만들고 로드 밸런서를 붙이고 자동 확장 정책까지 정해야 한다(→ 09-01, → 09-03). 정적인 앱이나 시험 배포에 그 설정 묶음이 과하다.

Amazon ECS Express Mode는 그 설정을 ECS가 한 번에 만들어 준다. 입력은 세 가지뿐이고 나머지 인프라는 전부 자동 구성된다.

#2핵심 질문

최소한의 것만 넣어서 바로 접속 가능한 웹 서비스를 어떻게 만드니까?

#3동작 예시

팀이 프론트엔드 앱을 시험 배포한다. 빌드된 컨테이너 이미지 주소와 역할 두 개만 지정해 Express Mode 서비스를 만든다. 곧바로 고유한 URL이 나와 HTTPS로 접속되며, 요청이 늘면 태스크 수도 자동으로 늘어난다.

#4동작 과정

  1. 세 가지를 준비한다container image와 task execution role(→ 11-01), infrastructure role을 준비해 넘긴다. 이 셋 외에 세밀하게 설정할 값은 없다.
  2. 인프라를 자동 구성한다Express Mode가 Fargate 기반 ECS 서비스, 고유한 접근 URL, SSL/TLS가 붙은 Application Load Balancer, 네트워킹 구성, 모니터링을 한꺼번에 만든다.
  3. 부하에 맞춰 늘린다만들어진 auto scaling policy가 요청량에 따라 태스크 수를 조절한다. 짧은 기간 실험하거나 API를 빠르게 검증하는 데 맞는다.
  4. 확인해 볼 것Express Mode 서비스 상세 화면에 표시된 고유 URL로 브라우저에서 접속해 응답이 오는지 확인한다.

클러스터 만들기 — 태스크가 모이는 단위

클러스터는 같은 계정 안에서 컨테이너 인스턴스와 Fargate 태스크가 함께 실행되는 컨테이너의 최상위 그룹으로, 계정마다 서로 다른 리전별로 여러 개를 둘 수 있다.

먼저 알아야 할 것 01-03

→ 04-04 참조

#1문제 상황

태스크는 어느 컴퓨터 위에서 실행되는지 알지 못한다. 어느 자리에 붙어 있는지를 한 번 정해야 태스크가 서로 찾아가고 서로 간섭하지 않는다.

cluster가 바로 그 자리다. 계정 안에서 리전별로 여러 개를 둘 수 있고, 각 클러스터는 실행 기반과 AWS 클라우드 계층의 인프라도 따로 고를 수 있다.

#2핵심 질문

태스크들이 함께 모여 돌아갈 단위를 어떻게 정할까?

#3동작 예시

운영용과 개발용 앱이 한 계정에 있다. 콘솔에서 각각 다른 이름으로 클러스터 두 개를 만든다. 개발용 클러스터에는 Fargate를, 운영용 클러스터에는 Amazon ECS Managed Instances를 골라(→ 03-04) 태스크를 따로 배치한다. 아무 태스크가 없어도 클러스터 자체는 남아 있다.

#4동작 과정

  1. 실행 기반을 고른다클러스터 만들 때 인프라 유형을 셋 중에서 고른다. Managed Instances, Fargate 서버리스, 그리고 VPC를 직접 만든 뒤 EC2 인스턴스를 붙이는 방식이다.
  2. createCluster로 만든다콘솔이나 명령으로 클러스터를 만들고 고유한 cluster ARN이 붙는다. ARN은 이 클러스터를 가리키는 AWS 안의 고유 주소다.
  3. 지우고 다시 본다deleteCluster는 그 위에서 돌던 태스크를 모두 정리하고 클러스터를 없앤다. long ARN format을 켜 두면 계정 전체를 한 ARN에 담아 충돌 가능성을 낮춘다.
  4. 확인해 볼 것ECS 콘솔의 클러스터 목록에 만든 클러스터가 ACTIVE 상태로 보이는지 확인한다.

Amazon ECS container agent — 에이전트가 하는 일

ECS container agent는 EC2 인스턴스마다 하나씩 돌아가면서 태스크를 인스턴스에 배정하고 실행·중지·로그·상태 보고를 처리해 주는 ECS가 각 인스턴스에 설치한 관리 프로세스다.

먼저 알아야 할 것 03-05

#1문제 상황

EC2 launch type은 인스턴스를 직접 등록해 태스크를 올린다(→ 03-05). 태스크가 인스턴스에서 실제로 돌아가려면 이 둘 사이를 이어 주고 실행을 대신하는 것이 있어야 한다.

그 역할을 하는 것이 Amazon ECS container agent다. agent version이 다르면 쓸 수 있는 기능도 달라진다.

#2핵심 질문

ECS의 명령을 EC2 인스턴스에서 실제로 수행하게 해 주는 것은 무엇인가?

#3동작 예시

서비스의 desired count를 3에서 5로 올린다. 각 인스턴스의 에이전트가 ECS의 지시를 받아 컨테이너를 띄우고, 컨테이너 표준 출력을 CloudWatch Logs로 보낸 뒤 상태를 ECS에 보고한다. 콘솔에서 태스크 상태가 RUNNING으로 보이면 에이전트가 일을 하고 있는 것이다.

#4동작 과정

  1. 에이전트를 확인한다인스턴스마다 ECS container agent가 하나씩 돌아간다. 이 프로세스가 인스턴스와 ECS 사이의 통신을 중재한다.
  2. 버전을 읽는다agent version마다 지원 기능과 수정 내용이 다르다. 최신 버전을 쓰는 것이 권장되며 어떤 기능이 어느 버전에 들어갔는지는 릴리스 기록에서 본다.
  3. 엔진과 설정을 끼워 넣는다컨테이너 엔진 설정을 넣는 container agent configuration을 쓰고, 엔진 종류는 ECS_ENGINE 값으로 지정한다. awslogs 드라이버나 EBS 볼륨(→ 06-02), Service Connect 같은 기능도 이 설정을 거쳐 켜진다.
  4. 확인해 볼 것인스턴스에 SSH로 들어가 실행 중인 ECS container agent 프로세스를 목록에서 확인한다.

ECS-optimized AMI와 Bottlerocket

ECS-optimized AMI는 ECS container agent와 Docker 또는 containerd, 로그 드라이버 등 ECS 실행에 필요한 구성 요소를 미리 넣어 둔 AMI이며, 최소 보안·최신 커널을 갖춘 채 유지하는 Bottlerocket은 이 목적을 위해 AWS가 만든 컨테이너 호스트용 최소 운영체제다.

먼저 알아야 할 것 03-05

#1문제 상황

EC2 launch type은 인스턴스를 직접 준비한다(→ 03-05). 운영체제 이미지를 아무 것이나 고르면 필요한 구성 요소가 빠져 태스크가 뜨지 않는다.

Amazon ECS-optimized AMI는 그 구성을 미리 넣어 둔 이미지다. Amazon Linux 2와 Amazon Linux 2023이 그 계열이고, 보안 패치를 작게 유지하는 최소 운영체제로는 Amazon ECS-optimized Bottlerocket AMI가 따로 있다.

#2핵심 질문

ECS 태스크가 바로 돌 수 있도록 준비된 운영체제 이미지는 무엇인가?

#3동작 예시

팀이 인스턴스를 만들 때 ECS-optimized Amazon Linux 2023 AMI를 선택한다. 부팅된 인스턴스에는 컨테이너 엔진과 ECS container agent(→ 04-02)가 이미 들어 있어 태스크를 올리기만 하면 된다. 최소 운영체제가 필요하면 Bottlerocket AMI를 고른다.

#4동작 과정

  1. AMI를 고른다Linux 계열은 Amazon ECS-optimized AMI 중에서 고르고, 지원 기간이 긴 Amazon Linux 2023 기반을 쓰는 것이 권장된다. Windows 작업이라면 Windows AMI를 쓴다.
  2. 필요한 것이 들어 있음을 안다이 이미지는 ECS 실행에 필요한 구성 요소와 권장 사항이 미리 들어 있다. 관례상 Amazon Linux 2 기반은 2년 뒤 사용 중단 예정이라 이전 계획이 있으면 확인한다.
  3. 최소 운영체제를 고른다Amazon ECS-optimized Bottlerocket AMI는 필요한 부분만 남기고 업데이트를 작게 나눠 배포해 보안을 유지한다. Container Insights 수집도 설정으로 켠다.
  4. 확인해 볼 것EC2 인스턴스 목록에서 선택한 이미지가 어느 ECS-optimized 계열로 표시되는지 확인한다.

4. 클러스터와 용량 공급자 — 태스크가 올라갈 자리를 만든다04-04

capacity provider — 인스턴스 묶음을 등록하고 쓰는 규칙

capacity provider는 태스크를 실행할 EC2 인스턴스 묶음(예: 오토 스케일링 그룹)과 ECS가 그것을 관리·배정하는 방식(배정 전략, 리밸런싱, 종료 보호)을 묶어서 등록한 규칙이며, 클러스터의 기본 provider로 지정하면 태스크를 그 묶음에 자동으로 놓는다.

먼저 알아야 할 것 04-01

#1문제 상황

태스크를 EC2 인스턴스에 올리려면(→ 03-05) 그 인스턴스가 이미 존재해야 하고, 직접 관리하는 동안에는 인스턴스 수와 태스크 수를 사람이 맞춰야 한다.

capacity provider는 EC2 인스턴스 묶음과 그 묶음을 다루는 규칙을 하나로 묶어 등록한다. Auto Scaling group capacity provider는 오토 스케일링 그룹 하나를 묶음으로 삼는다. 관리·배정 방식과 capacity provider strategy를 함께 지정해 두면 태스크가 그 묶음에 자동으로 올라간다.

#2핵심 질문

태스크를 어느 인스턴스 묶음에 배치할지 ECS가 스스로 알게 할 수 있을까?

#3동작 예시

주문 서비스의 desired count를 10으로 올린다(→ 08-01). 등록된 capacity provider가 인스턴스 4대에 태스크를 나눠 배치하고, 한 대가 unhealthy가 되면 다른 곳에 다시 놓으려 한다.

ECS 콘솔에서 해당 클러스터의 capacity provider 목록에 이 묶음이 조회되며 strategy가 어느 대가 어떤 수를 맡는지 보인다.

#4동작 과정

  1. 묶음을 등록한다인스턴스 묶음과 관리 방식을 한 항목으로 등록한다. scale-in과 scale-out을 ECS가 대신하면 managed scaling behavior가 켜진다.
  2. 배정 방법을 정한다capacity provider strategy에 여러 묶음을 나열해 어느 곳에 태스크를 놓을지 정한다. 등록된 auto scaling 그룹이 미리 클러스터에 붙어 있던 인스턴스는 이 전략에 정상 등록되지 않을 수 있어 새 그룹을 권장한다.
  3. 인스턴스를 지키며 빼낸다managed termination protection을 켜면 자동 축소가 터진 인스턴스도 그 위 태스크를 정리한 뒤 줄인다.
  4. 확인해 볼 것클러스터 화면에서 해당 capacity provider의 인스턴스 수와 strategy에 잡힌 desired count를 확인한다.

cluster auto scaling은 클러스터에서 실행 중인 태스크 수와 ECS가 정한 목표를 비교해 용량 provider의 인스턴스 수를 자동으로 늘리거나 줄이는 기능이다.

먼저 알아야 할 것 04-04

#1문제 상황

capacity provider(→ 04-04)로 묶음을 등록해도 인스턴스 수를 고르는 일은 남아 있었다. 사람이 지표를 보고 늘렸다 줄였다 하면 그 사이 트래픽이 빠진다.

cluster auto scaling은 그 판단을 ECS가 대신한다. 실행 중인 태스크의 자원 사용량을 목표 비율과 비교해 인스턴스 수를 스스로 정한다.

#2핵심 질문

트래픽에 맞춰 용량 공급자의 인스턴스 수를 자동으로 맞춰 줄 수 있을까?

#3동작 예시

오전 주문량 증가로 CPU 사용률이 목표를 넘는다. CloudWatch 알람이 울리고 오토 스케일링 그룹의 scale-out이 일어나 인스턴스가 늘어난 뒤 새 태스크가 그 위에 뜬다.

밤에는 사용률이 떨어져 scale-in이 일어나고, 그 인스턴스의 태스크는 다른 인스턴스로 옮겨 간다.

#4동작 과정

  1. 자동 관리를 켠다provider를 만들 때 managed scaling을 켜고 인스턴스 사용률 목표 비율(targetCapacity)을 정한다. scale-out과 scale-in은 ECS가 실행한다.
  2. 지표를 만든다ECS가 CloudWatch 지표와 높은 값·낮은 값 알람, 목표 추적 확장 정책을 만들어 관리한다. 정책은 provider를 고쳐야 고쳐진다.
  3. 여유분을 미리 잡는다warm pool을 두면 새 인스턴스를 기다리는 시간이 줄어든다.
  4. 확인해 볼 것콘솔에서 인스턴스 수가 목표 비율에 맞춰 늘고 줄었다가 돌아오는지 확인한다.

container instance draining — 인스턴스를 안전하게 빼는 절차

container instance draining은 인스턴스를 ECS에서 등록 해제할 때 그 위의 컨테이너를 순서대로 정상 종료시키며 기존 태스크가 다른 곳에서 다시 실행되도록 하는 절차다.

먼저 알아야 할 것 04-04

#1문제 상황

인스턴스를 관리하다가 유지보수나 오토 스케일링으로 그 인스턴스가 사라지면, 그 위 태스크가 통째로 죽어 서비스가 흔들린다.

container instance draining은 그 전에 인스턴스를 DRAINING 상태로 바꿔 태스크를 정리하는 절차다. container instance status가 이 상태를 나타낸다.

#2핵심 질문

인스턴스를 빼기 전에 그 위 태스크를 어쩔 수 없이 죽지 않게 할 수 있을까?

#3동작 예시

Spot Instance interruption이 예고되어 그 인스턴스를 autoscaling 그룹에서 떼어 낸다. ECS가 먼저 DRAINING으로 바꾸고 RUNNING 상태의 태스크를 STOPPED로 옮긴다.

서비스 스케줄러가 같은 클러스터의 남은 인스턴스로 대체 태스크를 띄우며, 세대 게이트나 health check 실패가 나면 원래 배포 설정에 따라 되돌린다.

#4동작 과정

  1. 배치를 막는다container instance draining을 시작하면 DRAINING 상태로 바뀌어 그 인스턴스에는 새 태스크가 더 이상 배치되지 않는다.
  2. 태스크를 정리한다PENDING 상태의 서비스 태스크는 바로 멈추고, RUNNING 상태 태스크는 STOPPED로 전환한 뒤 대체 태스크를 띄운다. 남는 용량이 부족하면 그 사실이 서비스 이벤트로 남는다.
  3. 쫓아내고 살핀다관리자가 인스턴스를 강제로 빼는 경로도 있다. container instance health 상태로 그런 문제를 미리 볼 수 있다.
  4. 확인해 볼 것클러스터 화면에서 해당 인스턴스의 상태가 DRAINING으로 바뀌고, 대체 태스크가 올라온 것을 확인한다.

태스크가 VPC 안에서 각자 자체 IP 주소를 갖고 직접 통신하는 네트워크 구성으로, awsvpc 모드는 태스크를 실행하는 계산 자원(Fargate·EC2·Managed Instances)과 관계없이 모든 태스크에 ENI 를 붙여 이 방식을 동일하게 적용한다.

먼저 알아야 할 것 02-02

#1문제 상황

같은 태스크 안의 컨테이너끼리는 포트를 나눠 쓰면 그만이다(→ 02-02). 문제는 태스크끼리인데, 네트워크 설정 없이는 VPC 안에서 각자 어디에 붙어 있는지 알 수 없다.

task networking과 awsvpc network mode는 태스크마다 task ENI라는 네트워크 인터페이스를 붙인다. 그래서 실행 자원이 무엇이든 subnet과 security group가 같은 방식으로 적용된다.

#2핵심 질문

태스크마다 VPC 안에서 독립된 주소와 보안 그룹을 줄 수 있을까?

#3동작 예시

VPC의 private subnet에 태스크를 올리면 ECS가 ENI를 만들고 지정한 security group을 붙인 뒤 그 자리에 얹는다. 태스크 안에서는 ENI를 통해 요청을 주고받는다.

같은 태스크의 컨테이너끼리는 localhost로 통신하고, VPC Flow Logs로 태스크에서 나가고 들어오는 트래픽을 볼 수 있다.

#4동작 과정

  1. ENI를 붙인다awsvpc network mode에서는 ECS가 task ENI를 만들어 실행 자원에 붙인다. ENI가 태스크의 주소가 된다.
  2. 범위를 정한다태스크가 놓일 subnet과 security group을 태스크 정의에서 정해 VPC 안에서만 쓰게 한다.
  3. 예외를 정한다같은 태스크 안의 컨테이너는 localhost 인터페이스로 서로 통신한다.
  4. 확인해 볼 것태스크의 ENI 주소와 VPC Flow Logs에 잡히는 트래픽을 확인한다.

#1문제 상황

bridge network mode와 host network mode는 태스크가 인터페이스를 독점하지 않는 대신 포트나 격리를 손으로 맞추는 방식이다.

#2핵심 질문

호스트의 주소를 그대로 쓰거나 포트를 매핑해 붙일 수 있는 네트워크 모드는 무엇일까?

#3동작 예시

host network mode로 태스크를 띄우면 컨테이너가 EC2 인스턴스의 IP 주소를 그대로 쓰고, 트래픽이 그대로 넘어온다.

bridge network mode에서는 호스트 포트 80을 컨테이너 포트 3000에 고정해 연결할 수 있다. docker default bridge는 컨테이너들이 함께 쓰는 가상 브리지다.

#4동작 과정

  1. 모드를 고른다network mode를 host로 두면 컨테이너가 호스트의 IP 주소와 커널을 같이 쓴다. 경계가 없어진다는 점이 관건이다.
  2. 브리지를 건다bridge 모드에서는 docker default bridge 같은 가상 브리지가 호스트와 컨테이너 사이에 놓인다.
  3. 포트를 잇는다브리지 모드에서 호스트 포트를 컨테이너 포트로 재매핑한다. 정적 매핑은 포트를 직접 적고, 동적 매핑은 임의의 빈 포트를 쓴다.
  4. 확인해 볼 것EC2 인스턴스에 포트 80으로 요청해 컨테이너의 3000 포트 응답이 도는지 확인한다.

Service Connect의 구성 요소 — 짧은 이름으로 서비스 연결

ECS가 내부적으로 DNS 기반 이름(short name)을 만들어 주므로 애플리케이션 코드를 고치지 않고 그 이름으로 다른 서비스의 태스크를 찾고 통신할 수 있게 해 주는 기능이다.

먼저 알아야 할 것 05-01

→ 05-04 참조

#1문제 상황

다른 서비스의 태스크 IP를 하드코딩해서 부르면 인스턴스가 바뀔 때마다 고쳐야 한다(→ 05-01). service discovery로 이름을 붙여도 클라이언트가 찾기·연결을 직접 해야 한다.

Service Connect는 짧은 이름만으로 상대 태스크에 붙게 한다. 사이드카 역할을 하는 Service Connect proxy가 붙고, 이 구성이 service mesh로도 쓰인다.

#2핵심 질문

코드에서 IP를 몰라도 상대 서비스의 태스크에 어떻게 붙을 수 있을까?

#3동작 예시

주문 서비스가 재고 서비스를 client alias인 재고라는 짧은 이름으로 부른다. 코드는 그 이름만 쓰고, Service Connect가 namespace 안의 재고 서비스 태스크 중 하나로 연결해 준다.

client-server service는 서버 역할 서비스로, 포트 매핑에 이름을 붙이고 discovery name으로 노출 이름을 정한다.

#4동작 과정

  1. 네임스페이스에 편입한다client 서비스는 serviceConnectConfiguration으로 들어갈 AWS Cloud Map namespace를 정한다. 그 안에 필요한 서버 서비스가 모두 있어야 한다.
  2. 이름을 붙인다client-server service는 태스크 정의의 portMappings에 name을 넣고 서비스의 discovery name으로 노출 이름을 정한다.
  3. 프록시로 잇는다Service Connect proxy가 client-server service에 붙어 상대 endpoint를 찾아 붙인다. 이 프록시 구성이 service mesh의 기본 단위다.
  4. 확인해 볼 것client 서비스의 태스크에서 짧은 이름으로 상대 서버의 엔드포인트에 접속되는지 확인한다.

service discovery — 레지스트리로 태스크 주소 찾기

Cloud Map 같은 레지스트리에 서비스 이름을 등록해 두면, 이름을 조회하는 클라이언트가 그 이름에 해당하는 태스크들의 IP 주소와 포트를 찾아 연결할 수 있게 되는 이름 기반 주소 찾기 방식이다.

먼저 알아야 할 것 05-01

#1문제 상황

클라이언트가 상대 태스크에 직접 붙으려면 그 태스크의 IP를 알아야 하고, 태스크는 늘었다 줄었다 한다(→ 05-01).

service discovery는 이름과 IP의 연결을 레지스트리에 맡긴다. ECS 서비스 discovery registry가 그 등록 정보를 관리한다.

#2핵심 질문

변하는 태스크의 주소를 이름 하나로 어떻게 찾아 붙을까?

#3동작 예시

주문 서비스의 태스크가 시작되고 container port를 declaring하면 AWS Cloud Map service에 이름이 등록된다.

lookup 클라이언트는 그 이름을 조회해 현재 살아 있는 재고 서비스 태스크의 IP와 포트를 얻고 그중 하나에 연결한다.

#4동작 과정

  1. 네임스페이스를 만든다service discovery는 AWS Cloud Map API로 HTTP와 DNS 네임스페이스를 다룬다.
  2. 이름을 등록한다ECS 서비스 discovery registry에 서비스 이름을 두고 노출할 container port를 알려 준다.
  3. 이름으로 찾는다클라이언트가 이름을 조회하면 그 이름에 해당하는 태스크들의 주소와 포트를 돌려 받고 직접 연결한다.
  4. 확인해 볼 것Cloud Map 콘솔에 등록된 이름과 조회 결과의 태스크 수를 확인한다.

5. 네트워크 — 태스크가 서로 통신하는 경로를 만든다05-05

Amazon VPC Lattice

VPC 안의 여러 서비스·리소스를 하나의 논리적 단위로 묶고 관리하는 경로 계층 서비스로, 요청 수·가중치 같은 규칙을 따라 트래픽을 각 대상에 나눠 보낸다.

먼저 알아야 할 것 05-03

#1문제 상황

한 애플리케이션이 여러 VPC와 계정의 EC2 인스턴스, IP 주소, Lambda 함수, 로드 밸런서에 걸쳐 흩어지면 각 목적지의 위치를 코드에 직접 적어야 하고 연결 상태를 눈으로 확인하기 어렵다.

Amazon VPC Lattice는 AWS 가 전부 관리하는 애플리케이션 네트워킹 서비스다. 앱 코드 수정 없이 여러 대상을 하나의 묶음으로 묶고 거는 경로를 만들어 준다.

#2핵심 질문

여러 VPC와 계정에 흩어진 서비스에 요청을 규칙대로 나눠 보내는 경로를 코드를 고치지 않고 만들 수 있을까?

#3동작 예시

결제 서비스가 여러 계정의 Lambda 함수와 EC2 인스턴스를 함께 호출한다. ECS 결제 서비스의 태스크를 VPC Lattice 타깃 그룹에 등록하자마자, 새로 뜬 태스크가 자동으로 등록되고 호출 경로 하나가 생긴다.

이후에는 트래픽 규칙만 바꿔도 호출 대상과 비율이 조율된다.

#4동작 과정

  1. 묶음을 만든다VPC Lattice는 애플리케이션 통신을 관리하는 서비스다. 안에는 service network라는 논리 묶음이 생기고, 그 안에 resource configuration으로 요청을 나눠 줄 규칙(대상·요청 수·가중치)을 적는다.
  2. 태스크를 등록한다target group은 요청을 받을 대상 자원을 모은 집합이다. ECS 서비스를 여기에 묶으면 태스크가 IP 대상으로 들어가고, 새로 실행된 태스크는 ECS 가 자동으로 등록한다.
  3. 전달을 관찰한다VPC Lattice는 VPC·계정을 가로질러 대상을 관찰하고 보안과 경로를 관리한다. 연결 실패가 생기면 networking troubleshooting 절차로 어느 지점에서 막혔는지 좁힌다.
  4. 확인해 볼 것ECS 서비스 화면에서 VPC Lattice 타깃 그룹에 등록된 태스크 목록에 새 태스크가 자동으로 올라온 것을 본다.

요청 흐름이 VPC 안과 밖 어디를 지나는지 콘솔에서 확인한다.

#4동작 과정

  4. 확인해 볼 것Service Connect를 붙인 서비스의 태스크 목록에서 짧은 이름이 각 태스크에 붙어 대상 주소로 쓰이는 것을 본다.

6. 스토리지 — 태스크 안에서 데이터를 어디에 쓰는지06-01

Fargate ephemeral storage

Fargate 태스크가 임시 볼륨으로 제공하는 컨테이너 쓰기 가능 디스크 영역으로, 태스크가 끝나면 함께 사라지고 크기는 태스크 메모리 크기에 따라 정해지며 루트 볼륨과 /var/lib/docker 같은 경로가 기본으로 포함됩니다.

먼저 알아야 할 것 03-03

#1문제 상황

Fargate 태스크는 인스턴스를 미리 만들지 않으므로(→ 03-01) 쓰기 작업이 생길 디스크를 어디에 둘지 정해야 한다. 태스크가 끝나면 그 디스크도 함께 사라진다.

task ephemeral storage는 Fargate가 태스크마다 주는 임시 디스크 영역이다. 그 크기를 정해 두면 컨테이너가 읽고 쓸 수 있는 공간이 생긴다.

#2핵심 질문

Fargate 태스크에서 컨테이너가 쓸 수 있는 임시 디스크를 어디서 얻고 얼마나 지정할까?

#3동작 예시

빌드 과정에서 큰 압축 파일을 푸는 컨테이너가 있다. 태스크 정의에 ephemeralStorage로 크기를 크게 지정하자 그만큼의 디스크가 배정되고, 작업이 끝나면 디스크가 태스크와 함께 지워진다.

#4동작 과정

  1. 디스크를 받는다Fargate는 태스크에 쓰기 가능한 디스크 영역을 기본으로 붙여 준다. 태스크 정의의 volumes·mountPoints·volumesFrom로 여러 컨테이너가 이 영역을 함께 쓸 수 있다. Windows 컨테이너에서는 지원되지 않는다.
  2. 크기를 정한다ephemeral storage size는 태스크 정의의 ephemeralStorage로 지정한다. 지정하지 않으면 기본 크기를 받고, 이미지 용량을 제외한 나머지가 컨테이너가 쓸 수 있는 공간이 된다.
  3. 암호를 걸 수 있다Fargate ephemeral storage encryption은 임시 저장 영역의 암호화를 켜는 설정이다.
  4. 확인해 볼 것태스크 정의에서 ephemeralStorage 값을 넣고 저장한 뒤 태스크 상세에 디스크 용량이 표시되는 것을 본다.

6. 스토리지 — 태스크 안에서 데이터를 어디에 쓰는지06-02

Amazon EBS volume

ECS 태스크에 붙여 쓰는 블록 스토리지 볼륨으로, 태스크 정의의 volume 항목에 EBS 볼륨 구성(크기·볼륨 유형·IOPS·gp3 대역폭)을 적어 넣으면 컨테이너가 디스크 장치처럼 마운트해 쓰고 데이터를 유지할 수 있습니다.

먼저 알아야 할 것 06-01

#1문제 상황

데이터베이스를 쓰는 컨테이너는 태스크가 바뀌어도 데이터가 남아야 한다. 태스크를 붙어 있는 EC2 인스턴스의 로컬 디스크(→ 04-02)에 두면 인스턴스를 뺄 때 같이 사라진다.

Amazon EBS volume은 ECS 가 대신 붙여 주는 블록 스토리지 볼륨이다.

#2핵심 질문

Fargate 태스크에서도 컨테이너가 쓰고 다시 읽을 수 있는 블록 디스크를 어떻게 붙일까?

#3동작 예시

주문 내역을 담는 태스크를 새 버전으로 교체한다. volume 항목에 EBS 볼륨 구성을 적어 두면 ECS 가 새 태스크마다 볼륨을 붙이고, 스냅샷에서 데이터를 불러와 이전 내역이 이어진다.

태스크가 사라져도 디스크는 남아 다음 태스크가 다시 붙는다.

#4동작 과정

  1. 구성을 적는다volume configuration에 크기·볼륨 유형·IOPS 같은 값을 태스크 정의의 volume 항목에 넣는다. standalone task는 태스크 하나당 볼륨 하나를 붙이고, 서비스는 태스크마다 하나씩 붙인다.

#1문제 상황

컨테이너가 쓸 디스크를 주는 방법이 두 가지 있다.

#2핵심 질문

컨테이너가 호스트 디스크의 공간을 보게 하려면 어떤 두 가지 설정을 쓰는가?

#3동작 예시

한 태스크의 컨테이너가 만든 처리 결과를 같은 태스크의 다른 컨테이너가 이어서 읽는다. bind mount를 쓰면 hostPath로 적은 호스트 디렉터리가 그대로 두 컨테이너에 보인다.

같은 디렉터리를 여러 태스크가 함께 쓰게 되면 이름이 겹치니 Docker volume을 쓴다.

#4동작 과정

  1. 경로를 직접 준다bind mount는 컨테이너가 쓸 hostPath를 그대로 준다. 이 설정은 Fargate와 EC2 양쪽 태스크에서 동작하고, containerPath로 컨테이너 안의 붙을 위치를 정한다.
  2. ECS 가 자리를 만든다Docker volume은 volume name으로 지정해 ECS 가 호스트에 디렉터리를 만들어 준다. 여러 태스크가 같은 위치를 써도 충돌하지 않는다.
  3. 수명을 정한다기본값은 그 컨테이너가 멈추면 지워진다. EC2에서는 host와 sourcePath를 지정해 데이터가 EC2 인스턴스 수명에 묶이게 할 수 있다.
  4. 확인해 볼 것태스크를 멈췄다가 다시 같은 태스크 정의로 실행하면, hostPath에 둔 데이터가 남아 있는 것으로 붙어 쓰기 여부를 본다.

swap memory는 디스크의 스왑 영역을 대신 쓰는 설정으로, 컨테이너별 memory reservation과 soft memory limit을 함께 지정해 이 상황을 나눠 다룬다.

#2핵심 질문

#3동작 예시

결과적으로 메모리가 순간적으로 큰 컨테이너는 스왑으로 버티고, 지연에 민감한 컨테이너는 스왑으로 느려지지 않는다.

#4동작 과정

  1. 예약한다컨테이너 인스턴스에서 각 컨테이너가 쓸 메모리를 미리 확보한다. memory reservation은 하드 한계, soft memory limit은 그 아래에서 커널이 캐시 같은 것을 되찾아 비우기 시작하는 선이다.
  2. 스왑을 정한다maxSwap으로 컨테이너가 쓸 스왑 양을 MiB 단위로 정한다. 값이 0이면 그 컨테이너는 swap memory를 쓰지 않는다.
  3. 확인해 볼 것태스크 정의의 컨테이너별 스왑과 메모리 예약 항목이 의도한 값으로 저장됐는지 확인한다.

task lifecycle는 태스크가 거치는 task state의 정해진 순서로, 각 상태에서 무엇이 일어나는지 알려 준다. 상태는 PENDING에서 PROVISIONING을 거쳐 RUNNING, DEPROVISIONING, STOPPED로 바뀐다.

#4동작 과정

  3. 끝낸다정지 요청이 오면 DEPROVISIONING에서 컨테이너를 정리한 뒤 STOPPED가 된다.
  4. 확인해 볼 것콘솔에서 태스크를 선택해 lastStatus와 desiredStatus가 어디로 옮겨 갔는지 본다.

#1문제 상황

task placement은 ECS가 용량 유형과 조건을 확인해 태스크를 놓을 자리를 고르는 과정이다. 어떤 조건을 걸었는지에 따라 결과가 달라진다.

#2핵심 질문

ECS는 어떤 기준으로 태스크를 실행할 자리를 고르는가?

#3동작 예시

개발자가 GPU 인스턴스에만 올라가게 하는 조건을 붙여 태스크를 실행한다. ECS는 container instance마다 그 조건이 맞는지 훑고, 맞는 인스턴스가 없으면 태스크를 PENDING 상태로 둔다.

이후 조건을 만족하는 자리가 생기면 그곳에 태스크가 배치된다.

#4동작 과정

  1. 구성 요소를 읽는다task placement은 전략, task group, task placement constraint 세 가지를 본다. 조건이 맞지 않으면 태스크는 배치되지 않고 PENDING state로 남는다.
  2. 용량을 고른다Managed Instances와 EC2은 container instance를 찾아 검사하고, Fargate는 launch type에 따라 자리를 정한다. capacity provider 전략을 따를 수도 있다.
  3. 확인해 볼 것조건에 맞지 않아 태스크가 PENDING에 머물 때 ECS 콘솔의 서비스 이벤트로 어디서 막혔는지 본다.

task placement strategy — 태스크를 나누고 모으는 알고리즘

서비스의 태스크 여러 개를 인스턴스에 나눠 놓을 때 쓰는 규칙인 배치 전략으로, replica·daemon·binpack(random)·spread 등이 있다.

먼저 알아야 할 것 07-02

#1문제 상황

서비스의 태스크를 인스턴스에 올릴 때, 기본값만 쓰면 가용 영역마다 고르게 퍼진다. 어느 한 인스턴스에 태스크를 몰아 실어야 할 때는 이 기본값이 맞지 않는다.

task placement strategy는 인스턴스를 고르는 알고리즘이다. random은 임의로, binpack은 남은 자원이 큰 곳을, spread는 지정한 attribute 값이 다른 곳에 하나씩 놓는다.

#2핵심 질문

태스크를 인스턴스에 어떻게 나눠 놓을 것인가?

#3동작 예시

인스턴스 오버헤드를 줄이려고 서비스의 배치 전략을 binpack으로 바꾼다. 그러면 실행 중인 태스크 수가 적은 인스턴스가 먼저 선택된다.

결과적으로 새 태스크가 이미 일하는 인스턴스에 붙고, 새로 붙는 인스턴스 수가 줄어든다.

#4동작 과정

  1. 전략을 정한다replica, daemon, binpack, random, spread 중 하나를 고른다. 서비스 태스크의 기본값은 attribute인 ecs.availability-zone 기준 spread다.
  2. 분배한다spread는 attribute 값이 다른 자리로 최대한 겹치지 않게 놓는다. binpack은 단위를 크게 잡아 한 인스턴스에 몰아 놓는다. scaling down 때도 같은 전략으로 종료할 태스크를 고른다.
  3. 확인해 볼 것서비스의 태스크가 어느 인스턴스에 몇 개씩 붙어 있는지 콘솔에서 본다.
  4. 확인해 볼 것전략은 최선의 자리를 못 구해도 태스크를 올린다. 조건이 막힌 경우에만 배치가 멈춘다.

먼저 알아야 할 것 07-02

#1문제 상황

서비스의 태스크를 아무 인스턴스나 오르지 않게 하려면 특정 인스턴스 타입이나 가용 영역에만 놓아야 한다. 이런 조건은 스트링 하나가 아니라 문법으로 표현해야 한다.

task placement constraint는 인스턴스가 만족해야 할 규칙이다. 표현식은 cluster query language로 쓰며 attribute 이름 ecs.instance-type 같은 것과 memberOf 연산자를 쓴다.

#2핵심 질문

태스크가 놓일 인스턴스의 조건을 어떻게 표현하고 강제하는가?

#3동작 예시

GPU 워크로드가 특정 인스턴스 타입에서만 도는 애플리케이션이다. 서비스에 memberOf 조건을 걸어 GPU 태스크가 있는 인스턴스 그룹에만 새 태스크를 놓는다.

조건에 맞는 인스턴스가 하나도 없으면 태스크는 PENDING에 남는다.

#4동작 과정

  1. 유형을 고른다distinctInstance는 실행 중인 태스크마다 다른 인스턴스를 쓰게 한다. memberOf는 같은 task group의 태스크가 있는 인스턴스로만 보낸다.
  2. 식을 쓴다placementConstraints의 expression에 cluster query language로 조건을 적는다. ecs.availability-zone 같은 attribute와 인스턴스 유형을 지정한다.
  3. 확인해 볼 것조건에 어긋나 태스크가 PENDING에 멈췄는지 콘솔에서 확인한다.
  4. 확인해 볼 것맞는 인스턴스가 하나도 없을 때 배치가 아예 안 되는지 본다. 조건은 강제지만 전략은 최선 시도로만 동작한다(→ 07-03).

#1문제 상황

한 클러스터에서 데이터베이스와 웹 서버가 함께 돌아간다. 데이터베이스 태스크만 가용 영역에 고르게 뿌려 두고 싶어도 태스크는 이름만 다를 뿐이라 그 묶음을 알 수 없다.

task group은 태스크를 묶는 이름이다. 같은 task group name의 태스크는 spread 전략에서 한 단위로 보고, 제약 조건의 기준으로도 쓴다.

#2핵심 질문

관련된 태스크들을 하나의 묶음으로 어떻게 표시하는가?

#3동작 예시

ECS는 이제 databases 묶음을 가용 영역에 고르게 나눠 놓고, 다른 태스크는 그 결과에 영향을 주지 않는다.

#4동작 과정

  1. 이름을 붙인다태스크 실행 시 task group name을 정한다. standalone task는 따로 정하지 않으면 태스크 정의의 family 이름을 묶음 이름으로 쓴다.
  2. 함께 본다같은 이름의 태스크는 spread task placement strategy에서 한 세트로 계산해 고르게 배치한다. 가용 영역이 다르면 같은 영역으로 몰지 않는다.
  3. 확인해 볼 것실행한 태스크의 묶음 이름이 의도한 task group name으로 기록됐는지 콘솔에서 본다.

먼저 알아야 할 것 07-01

#1문제 상황

정기적으로 한 번씩 처리만 하면 되는 작업이 있다. 서비스를 만들면 desired count를 유지하느라 태스크가 계속 살아 있어 비용과 운영이 따라온다.

standalone task는 서비스 밖에서 직접 실행해 일이 끝나면 멈추는 태스크다. 주기적으로 돌리려면 EventBridge Scheduler를 쓴다.

#2핵심 질문

한 번만 실행하고 멈출 작업을 어떻게 실행하는가?

#3동작 예시

하루 한 번 야간 배치를 돌려야 한다. 콘솔이나 AWS CLI에서 RunTask로 태스크를 직접 실행한다.

태스크는 PROVISIONING에서 이미지에 올라가고(→ 07-01) RUNNING으로 작업하다가 끝나면 STOPPED로 멈춘다. 매일 반복하려면 EventBridge Scheduler에 cron 일정을 등록한다.

#4동작 과정

  1. 직접 실행한다콘솔·AWS CLI·API·SDK 중 원하는 경로로 RunTask를 호출해 태스크를 한 번 실행한다. 서비스나 스케줄러에 묶이지 않는다.
  2. 돌게 만든다주기 실행이 필요하면 EventBridge Scheduler에서 rate나 cron 일정을 정해 같은 태스크 정의를 반복 실행시킨다.
  3. 멈춘다작업을 끝낸 태스크는 스스로 STOPPED가 되고, 필요하면 stop task를 요청해 중간에 종료시킬 수 있다.
  4. 확인해 볼 것실행한 태스크가 서비스 목록이 아니라 태스크 목록에서 곧 STOPPED로 끝났는지 본다.

서비스 스케줄러 전략 — replica와 daemon

ECS 서비스가 유지할 태스크의 개수와 배치 방식을 정하는 설정으로, replica(desired count만큼 항상 동일 수를 유지)와 daemon(모든 대상 컨테이너 인스턴스에 하나씩 실행)이 있다.

먼저 알아야 할 것 07-03

#1문제 상황

태스크 하나를 직접 실행하면 그 태스크가 죽을 때 아무도 그것을 대신하지 않는다(→ 07-06). 요청이 늘면 태스크를 늘릴 판단도, 늘어난 만큼 다시 줄일 판단도 운영자가 직접 해야 한다.

그래서 ECS의 service는 태스크 묶음을 대신 감시하고 정해진 수를 유지해 준다. 어떤 수를 유지할지와 어디에 놓을지는 scheduling strategy로 정한다. 여기에는 REPLICA scheduling strategy와 DAEMON scheduling strategy 두 가지가 있다.

#2핵심 질문

서비스는 태스크를 몇 개나 유지하고 어디에 나눠 놓는가?

#3동작 예시

주문 서비스의 desired count를 4로 둔 채 운영한다. 태스크 하나가 죽으면 ECS가 빈자리를 채우고, 나머지 세 개는 계속 요청을 받는다.

인스턴스가 늘면 새 인스턴스마다 태스크가 한 개씩 배정되어 hostname을 감시하는 데모 같은 작업이 함께 돌아간다.

#4동작 과정

  1. 전략을 고른다REPLICA scheduling strategy는 desired count만큼 태스크를 두고 유지한다. service scheduler가 가용 영역에 고르게 나누며 DAEMON scheduling strategy는 조건을 만족하는 활성 인스턴스마다 정확히 하나씩 둔다. 이 방식은 desired count나 자동 확률이 필요 없고 Fargate 태스크에서는 쓸 수 없다.
  2. 배치를 정한다REPLICA에서는 task placement strategy와 constraint로 태스크가 놓일 인스턴스를 좁힌다(→ 07-03). placement constraint를 만족하는 인스턴스만 대상이 되므로 대상이 없으면 태스크가 뜨지 않는다.
  3. 확인해 볼 것서비스의 태스크 목록에 몇 개의 태스크가 올라와 있고 어느 인스턴스에 배정됐는지 확인한다.

deployment controller는 ECS가 이 교체를 직접 진행할지 외부 도구가 진행할지를 정한다. ECS, CODE_DEPLOY, EXTERNAL 세 값 중 하나를 고르고, deployment strategy로 교체 순서를 정한다. 기본 조합은 ECS가 직접 진행하는 ROLLING이다.

#2핵심 질문

새 태스크 정의를 어떤 주체로 어떤 순서로 반영할까?

#3동작 예시

운영자가 태스크 정의의 새 revision로 서비스를 업데이트한다. ECS가 기존 태스크를 desired count만큼 남긴 채 새 태스크를 하나씩 추가해 health check를 통과시킨다.

problem 없는 배포라면 교체가 끝나고, 코드 배포 방식(CODE_DEPLOY)을 고른 환경이면 ECS가 CodeDeploy에 넘겨 blue/green 교체를 진행시킨다.

#4동작 과정

  1. 주체를 고른다ECS는 DEPLOYMENT_CONTROLLER가 ECS일 때 rolling 방식을 직접 수행한다. CODE_DEPLOY를 고르면 교체를 AWS CodeDeploy에 맡기고, EXTERNAL은 밖에서 정한 순서대로 ECS가 대기하는 방식이다.
  2. 순서를 고른다deployment strategy로 ROLLING, BLUE_GREEN, LINEAR, CANARY 중 하나를 고른다. 각 방식은 교체를 어떤 크기와 순서로 진행할지만 다르다.
  3. 여유분을 정한다deployment configuration으로 한 번에 바꿀 수 있는 태스크 수의 상·하한을 정한다. 하한인 minimumHealthyPercent가 낮을수록 교체가 빠르고, 서비스가 잠깐이라도 얇아진다.
  4. 확인해 볼 것서비스 화면의 배포 상태가 진행 중에서 완료로 넘어가는지 확인한다.

8. 서비스와 배포 전략 — 태스크 수를 유지하고 바꾸는 법08-03

rolling update deployment

기존 실행 중인 태스크를desired count만큼 유지한 채 새 태스크 정의를 단계적으로 배치해 health check를 통과시키면서 한 대씩 교체하는 기본 배포 방식이다.

먼저 알아야 할 것 08-02

#1문제 상황

ECS 서비스의 태스크를 전부 지우고 새로 띄우면 그 사이 요청을 받을 태스크가 없어진다. 반대로 하나만 내리고 하나만 올리는 방식은 단계마다 용량이 줄어든다.

rolling update deployment은 둘 사이를 택하지 않는다. 서비스의 deployment configuration으로 정한 최소 정상 비율만 지키면서 새 태스크를 올리고 health check가 통과한 것을 보고 다음 단계로 넘어간다.

#2핵심 질문

한 번에 전부 바꾸지 않으면서 새 버전을 어디까지 밀어 넣을까?

#3동작 예시

desired count가 4인 서비스에서 minimumHealthyPercent를 50으로 두고 새 태스크 정의를 반영한다. 스케줄러는 기존 태스크 두 개를 먼저 내리고 새 태스크 두 개를 띄운다.

두 개가 정상 판정을 받으면 다음 두 개를 같은 방식으로 교체한다. 교체 중에도 남은 태스크가 요청을 받는다.

#4동작 과정

  1. 여유분을 정한다minimumHealthyPercent는 교체를 지켜야 하는 정상 태스크 수의 하한이다. maximumPercent는 이 과정에 새로 붙여도 되는 태스크 수의 상한이다. 이 두 값은 deployment configuration으로 서비스마다 지정한다.
  2. 한 단위씩 올린다ECS는 하한이 깨지지 않는 범위에서 새 태스크를 추가하고 기존 태스크를 내린다. 태스크가 healthy 상태가 되어야 다음 단계로 넘어간다.
  3. 끝낸다desired count가 새 태스크 정의의 태스크로 모두 채워지면 교체가 완료 상태가 된다. early success criteria를 켜면 전체 태스크가 healthy 가 되기 전에 완료로 볼 수 있다.
  4. 확인해 볼 것서비스의 배포 상태와 실행 중 태스크의 desired revision 이 바뀐 것을 확인한다.

blue/green deployment과 service revision

기존 태스크 세트를 blue로 그대로 두고 service revision으로 새 태스크 정소를 green 세트로 따로 띄운 뒤, 테스트를 거쳐 traffic을 전환하는 무중단 배포 방식이다.

먼저 알아야 할 것 08-02

#1문제 상황

rolling update deployment(→ 08-03)는 교체 도중 구버전과 신버전이 한꺼번에 요청을 받는다. 그래서 어떤 요청이 새 버전에서 실패했는지 확인하기 어렵다.

service는 정해진 수의 태스크를 계속 띄워 두는 ECS의 실행 단위이며(→ 08-01), 이 service가 새 태스크 정의 revision으로 교체될 때(→ 02-01) 어느 시점에 트래픽을 넘길지 정해야 한다.

blue/green deployment은 두 세트를 분리해 둔다. 기존 blue 세트는 그대로 살아 있고, production 트래픽이 새 세트로 넘어갔는지는 validation listener가 반환하는 값으로 확인한다.

#2핵심 질문

새 버전이 정상인지 따로 본 뒤에 production 트래픽만 한 번에 갈아끼울 수 있을까?

#3동작 예시

운영자가 새 태스크 정의를 반영한다. ECS가 기존 blue 세트와 나란히 새 세트를 띄우고 이 새 세트를 green이라 부른다.

green에는 CODE_DEPLOY_LAUNCH 규칙과 validation listener가 붙어 있고, listener가 테스트를 통과했는지를 production 트래픽 전환 여부로 쓰인다. 문제가 보이면 blue로 되돌린다.

#4동작 과정

  1. green을 띄운다ECS가 새 태스크 정의 revision을 green 세트로 실행한다. blue 세트는 멈추지 않아 production 요청을 계속 받는다.
  2. 규칙을 건다load balancer의 target group과 listener rule로 두 세트에 트래픽 경로를 나눈다. validation listener는 테스트 트래픽을 받아 새 service revision의 응답을 확인해 production 전환을 판단하는 자리다.
  3. 바꾸거나 되돌린다검증을 통과하면 production 트래픽을 green으로 옮기고, 문제가 있으면 blue 세트를 다시 production 대상으로 되돌린다.
  4. 확인해 볼 것blue/green 배포 화면에서 production 트래픽이 어느 서비스 revision을 향해 있는지 확인한다.

linear deployment과 canary deployment

새 태스크 정의를 일부에만 먼저 적용해 관찰한 뒤 점차 늘리는 방식으로, linear는 일정 비율씩, canary는 고정된 소수 비율이나 태스크 하나만 먼저 노출한다.

먼저 알아야 할 것 08-04

#1문제 상황

blue/green deployment(→ 08-04)은 검증을 통과하면 production 트래픽을 한꺼번에 green으로 넘긴다. 새 버전의 오류가 요청량 일부에서만 나타나는 경우라면 그 시점에 이미 문제가 퍼진 뒤다.

linear deployment과 canary deployment은 일부 트래픽만 먼저 보내 새 버전의 상태를 살핀 뒤 비율을 늘린다. 이 절차를 traffic shift, 즉 production 트래픽을 옮기는 과정으로 다룬다.

#2핵심 질문

새 버전에 작은 비율의 트래픽만 먼저 보내 보고 괜찮으면 늘릴 수 있을까?

#3동작 예시

linear deployment으로 새 세트에 처음에는 적은 비율의 트래픽만 보낸다. 정해진 시간이 지나면 비율을 다시 올려 보낸다.

canary deployment이면 태스크 하나나 아주 적은 수의 트래픽만 먼저 노출해 보고, 문제가 없으면 나머지를 한 번에 넘긴다. 단계마다 bake time 동안 상태를 관찰한다.

#4동작 과정

  1. 첫 비율을 정한다linear deployment는 정해진 비율씩 늘린다. canary deployment는 태스크 한 개나 고정된 소수 비율로 먼저 시작한다.
  2. 기다린다step bake time은 traffic shift 단계 사이에 멈춰 두는 시간이다. 이 시간 동안 새 버전의 상태를 보고 늘릴지 멈출지 정한다.
  3. 끝까지 보낸다비율을 100까지 올리면 production 트래픽 전체가 새 세트에 있다. weight는 각 세트에 보낼 트래픽의 비중으로 쓴다.
  4. 확인해 볼 것트래픽 이동 단계가 몇 개로 잡혔고 지금 어느 단계인지 확인한다.

deployment failure detection과 lifecycle hook

배포 중인 태스크가 실패하면 ECS가 자동으로 배포를 중단·롤백하는 기능으로, 실패 감지 기준과 함께 배포 전후에 실행되는 lifecycle hook으로 마이그레이션이나 점검을 끼워 넣는다.

먼저 알아야 할 것 08-03

#1문제 상황

rolling update deployment(→ 08-03)은 새 태스크 정의가 잘못되었다면 실패한 태스크를 계속 띄우며 진행한다. 사람이 어느 순간 스크롤을 볼 때까지 나쁜 버전이 노출된다.

deployment failure detection은 실패를 ECS가 스스로 판정해 배포를 멈추게 한다. 이 판정은 deployment circuit breaker 방식과 CloudWatch alarm 방식 두 가지이며, 둘 다 rolling update deployment와 blue/green deployment에서만 동작한다.

#2핵심 질문

배포가 실패했다는 걸 사람이 확인하기 전에 ECS가 먼저 멈출 수 있을까?

#3동작 예시

운영자가 배포를 시작한다. 새 태스크가 시작되지 못하고 죽어가자 deployment circuit breaker가 실패를 세어 배포를 중단하고 이전 배포로 되돌린다.

같은 배포에 pause hook을 걸어 두면, 다음 단계로 넘어가기 전에 Lambda hook이 데이터 마이그레이션을 끝냈는지 확인한다.

#4동작 과정

  1. 실패를 센다deployment circuit breaker는 ECS가 정한 기준에 닿으면 배포를 실패로 본다. CloudWatch alarm을 함께 쓰면 그 알람의 상태로도 같은 판정을 내릴 수 있고, 둘 중 하나만 걸려도 배포가 멈춘다.
  2. 되돌린다되돌리기는 이전 배포가 COMPLETED 상태로 남아 있어야 가능하다. 배포 상태가 바뀌면 EventBridge 이벤트가 발생한다.
  3. 사건을 끼워 넣는다lifecycle hook은 배포 전후에 실행되는 자리다. Lambda hook이 스크립트를 돌린 뒤 pause 상태로 기다리고, continue service deployment로 다음 단계가 진행된다.
  4. 확인해 볼 것서비스 배포 이력에서 실패로 기록된 배포와 되돌아간 결과를 확인한다.

9. 트래픽 분산과 자동 확장 — 상황에 맞춰 수량을 조절한다09-01

로드밸런서로 서비스 트라픽 분산

ECS 서비스에 연동한 로드밸런서가 healthy 상태인 태스크에만 요청을 보내고, ALB·NLB·GWLB 중 어느 종류를 어떤 포트·프로토콜로 붙일지를 태스크 정의와 서비스 설정에서 정하는 것.

먼저 알아야 할 것 08-01

#1문제 상황

서비스 태스크가 여러 대라면 태스크마다 직접 주소가 붙어 들어온다(→ 01-03). 죽은 태스크로도 요청이 가고, 컨테이너 포트가 매번 달라 어느 주소로 붙어야 할지 알 수 없다.

그래서 ECS 서비스는 Elastic Load Balancing을 붙인다. 요청은 healthy 상태인 태스크에만 보내지고, unhealthy 태스크는 자동으로 요청 대상에서 빠진다.

#2핵심 질문

여러 태스크 앞에 하나를 붙여 요청을 정상 태스크에만 보내려면 무엇을 고르아야 할까?

#3동작 예시

주문 서비스에 Application Load Balancer를 붙인다. 하나의 서비스에 여러 target group을 지정해 여러 포트를 노출할 수 있고, Fargate와 EC2 태스크 모두 이 구성을 쓴다.

이후 로드밸런서가 주기적으로 태스크에 요청을 보내 응답을 확인한다. 이 확인이 load balancer health check이며 unhealthy로 판정된 태스크는 트래픽을 받지 않는다.

#4동작 과정

  1. 종류를 고른다HTTP·HTTPS 요청이면 Application Load Balancer를 쓴다. TCP나 UDP 계층을 그대로 전달하려면 Network Load Balancer를, 다른 로드밸런서가 만든 트래픽을 한 번에 분산하려면 Gateway Load Balancer를 고른다.
  2. 묶음을 만든다target group은 요청을 보낼 태스크 묶음이다. 하나의 서비스에 여러 target group과 여러 포트를 지정할 수 있고, 같은 태스크 집합은 로드밸런서를 쓰거나 쓰지 않는 설정을 섞을 수 없다.
  3. 체크를 건다load balancer health check가 정한 경로와 주기로 태스크를 검사한다. 검사에서 떨어진 태스크는 healthy가 되기 전까지 요청을 받지 않는다.
  4. 확인해 볼 것로드밸런서의 대상 목록에서 태스크 상태가 healthy로 표시되는지 확인한다.

target tracking 기반 서비스 자동 확장

ECS가 CloudWatch에서 수집한 CPU·메모리 같은 지표의 목표값을 유지하도록 태스크 수를 스스로 늘리고 줄이는 자동 확장 방식으로, 각 태스크가 하나의 지표만 추적하며 조정 최소 시간을 두고 동작한다.

먼저 알아야 할 것 09-01

#1문제 상황

트래픽이 늘면 replica 서비스(→ 08-01)의 desired count만큼 태스크만 돌아서는 요청이 밀린다. 늘어난 걸 사람이 감지해 수동으로 고치는 것도 매번 반복된다.

target tracking 기반 서비스 자동 확장은 지표의 목표값을 정해 두고 ECS가 스스로 수량을 조절하게 한다.

#2핵심 질문

지표가 목표값을 벗어날 때 태스크 수를 자동으로 늘리고 줄일 수 있는가?

#3동작 예시

평일 낮 동안 CPU가 올라간다. Amazon ECS service auto scaling이 CloudWatch에서 받은 CPU 사용률과 target value를 비교해 태스크를 늘린다.

밤에는 CPU가 내려가 태스크가 줄어든다. scale-out cooldown과 scale-in cooldown 동안은 조정이 멈춰 태스크 수가 출렁이지 않는다.

#4동작 과정

  1. 지표를 정한다서비스 하나에서 추적할 지표(CPUUtilization, MemoryUtilization 등)를 고르고 target value를 정한다. service auto scaling이 이 조합으로 하나의 자동 확장 정책을 만든다.
  2. 조절한다Application Auto Scaling이 CloudWatch 알람을 대신 만들고 조정량을 계산한다. 지표가 용량을 늘리면 낮아지는 쪽이면 태스크를 더 늘리는 식으로 비율 조절도 한다.
  3. 기다린다scale-out cooldown과 scale-in cooldown으로 조정 간격을 정해 태스크 수가 급격히 출렁이는 것을 막는다.
  4. 확인해 볼 것서비스의 자동 확장 화면에서 추적 지표와 target value가 표시된 것을 본다.

단계 조정과 예약 확장

단계 조정(scale step)은 지표가 임계값을 넘으면 정해진 수만큼 한 번에 태스크를 추가·제거하는 방식이고, 예약 확장(scheduled scaling)은 요일과 시간대를 미리 지정해 수요가 없더라도 필요한 태스크 수를 미리 확보해 두는 방식이다.

→ 09-03 참조

#1문제 상황

지표 하나만 보고 늘리면 CPU 사용률처럼 순간적으로 튀는 값에 태스크가 크게 늘어 비용이 낭비된다. 반대로 오전 9시 오픈처럼 시간대가 정해진 수요는 지표가 오르기 전에 준비해야 한다.

단계 조정과 예약 확장은 임계값 단계와 시간표를 미리 지정해 이 두 문제를 다룬다.

#2핵심 질문

지표의 크기와 요일·시간대별로 태스크 수를 미리 정해 둘 수 있는가?

#3동작 예시

평균 CPU가 50%를 넘으면 태스크 2개를 추가하고, 80%를 넘으면 5개를 추가하는 scaling policy를 건다.

CloudWatch 알람이 임계값을 넘으면 step adjustment 크기대로 한 번에 태스크가 늘어난다. 별도로 scheduled action을 등록해 월요일 아침마다 minimum capacity를 20으로 올려 두면 지표가 아직 낮아도 태스크가 미리 늘어난다.

#4동작 과정

  1. 단계로 건다알람이 임계값을 넘으면 step scaling이 발동한다. 넘은 임계값에 대응하는 step adjustment 크기만큼 태스크를 한 번에 추가하거나 제거한다.
  2. 시간표를 건다scheduled action으로 요일과 시간을 지정해 그 시각에 태스크 수를 minimum capacity와 maximum capacity 사이의 값으로 맞춘다.
  3. 확인해 볼 것서비스 자동 확장 화면의 스케줄 목록에서 등록한 scheduled action의 요일과 시간이 보이는지 본다.

먼저 알아야 할 것 09-03

→ 09-04 참조

#1문제 상황

예측 확장 앞선 방식들(→ 09-03 · 09-04)은 지표가 이미 오른 뒤에 반응한다. 앱이 켜지는 데 오래 걸리면 태스크가 늘어도 그 시간 동안 요청이 느리게 처리된다.

예측 확장 및 대기열 기반 확장은 미리 예측하거나, 지표 대신 실제로 쌓인 작업량을 세어 이 공백을 메운다.

#2핵심 질문

수요가 오기 전에 태스크를 늘리고, 쌓인 작업량에 맞춰 태스크 수를 조절할 수 있는가?

#3동작 예시

평일 업무 시간에만 트래픽이 늘어난다는 패턴이 반복된다. 과거 CloudWatch 지표로 forecast를 내면 ECS가 scaling plan을 만들어 정해진 시각에 미리 태스크를 늘린다.

다른 서비스는 SQS 대기열에 메시지가 쌓이기만 한다. queue-based scaling은 queue length, 즉 대기열 길이를 지표로 삼아 태스크 수를 늘린다.(custom metrics와 metric math expression으로 필요한 값을 계산해 쓴다)

#4동작 과정

  1. 예측한다과거 CloudWatch 지표로 forecast를 내고 반복 패턴이 확인되면 scaling plan을 만든다. 순환형 트래픽이나 주기적 배치 작업처럼 규칙이 뚜렷할 때 잘 맞는다.
  2. 선제한다예측값에 맞춰 정해진 시각 전에 태스크를 늘린다. 앱 초기화 시간이 긴 서비스일수록 효과가 크다.
  3. 대기열을 본다queue-based scaling은 queue length를 CloudWatch 지표로 올린다. 그 지표가 임계값을 넘으면 태스크를 늘리고, 낮아지면 되돌린다.
  4. 확인해 볼 것서비스 자동 확장 화면에서 만들어진 scaling plan의 시간표가 보이는지 본다.

가용 영역 재분산과 축소 보호는 이 두 상황을 막는다.

#2핵심 질문

한 가용 영역이 불안정할 때 태스크를 다시 고르게 나눌 수 있는가?

#3동작 예시

어느 가용 영역의 자원이 부족해 태스크가 그쪽에 몰린다. Availability Zone rebalancing이 service rebalancing을 실행해 태스크 묶음을 다른 영역으로 비율대로 옮긴다.

자동 확장 정책이 새벽에 축소하려 해도 task scale-in protection이 켜져 있으면 정해진 시각 동안 최소 태스크 수가 유지된다.

#4동작 과정

  1. 재분배한다Availability Zone rebalancing이 영역별 불균형을 감지하면 service rebalancing으로 태스크 묶음을 나눠 옮긴다. 첫 번째 배치 전략이 가용 영역 분산이거나 배치 전략이 없을 때 이 기능을 쓸 수 있다.
  2. 이벤트로 남긴다재분배가 일어난 사실은 rebalance event로 기록돼, 나중에 어디로 태스크가 옮겨 갔는지 확인할 수 있다.
  3. 지킨다task scale-in protection이 지정한 재실행 보호 시간 동안 최소 태스크 수를 못 줄이게 막는다. 새벽 배치나 유지보수로 최소 수를 남겨 두는 데 쓴다.
  4. 확인해 볼 것서비스의 이벤트 목록에서 rebalance event가 발행된 기록을 본다.

CloudWatch 지표로 ECS 관측

ECS가 작업(Task)과 서비스(Service)에 대해 자동 수집해 CloudWatch에 보내는 CPU·메모리 사용량 같은 수치 지표를 보고, 클러스터 자원 사용과 서비스 상태를 파악하는 것.

먼저 알아야 할 것 08-01

#1문제 상황

컨테이너가 몇 개 돌고 있는지(→ 08-01)는 콘솔에서 바로 보인다. 하지만 CPU와 메모리를 얼마나 썼는지는 보이지 않아, 병목이 생겼을 때 어디를 먼저 봐야 하는지 판단하기 어렵다.

CloudWatch 지표로 ECS 관측은 그 수치를 ECS가 직접 올려 주게 한다.

#2핵심 질문

클러스터와 서비스의 자원 사용량을 어디에서 숫자로 확인하는가?

#3동작 예시

서비스가 느려져 CloudWatch 콘솔의 ECS 메트릭 대시보드를 연다. 서비스별 CPUUtilization 그래프가 임계치에 붙어 있고, MemoryUtilization은 낮다.

CPU만 높으면 실행 중인 태스크 수보다 컨테이너 쪽 문제로 좁힌다. 이 지표는 1분 단위로 쌓이므로 며칠치 과거 추이를 본다.

#4동작 과정

  1. 보낸다ECS가 Amazon ECS metrics를 만들어 CloudWatch로 보낸다. 작업과 서비스 단위의 CPUUtilization과 MemoryUtilization이 기본 지표다.
  2. 모은다지표가 1분 주기로 기록돼 시간 범위를 골라 그래프를 그릴 수 있다. cluster utilization과 service utilization도 같은 방식으로 확인한다.
  3. 붙인다usage report로 태그별 사용량을 묶어 볼 수 있다. 태스크별 CPU·메모리와 파일시스템 사용은 Container Insights를 켜면 더 볼 수 있다(→ 10-03).
  4. 확인해 볼 것CloudWatch 콘솔에서 CPUUtilization과 MemoryUtilization 그래프가 시간에 따라 그려지는 것을 본다.

EventBridge로 ECS 이벤트에 자동 대응

작업이 시작되거나 서비스 배포 상태가 바뀌는 같은 ECS의 상태 변화가 EventBridge 이벤트로 발행되는데, 이를 규칙으로 받아 알림 발송이나 자동 조치 같은 대응을 걸어 두는 것.

먼저 알아야 할 것 10-01

#1문제 상황

배포가 실패했는지 태스크가 죽었는지 알려 주는 화면은 ECS 콘솔뿐이다. 콘솔을 계속 열어 두고 있어야 하니, 놓치면 원인을 늦게 알게 된다.

EventBridge로 ECS 이벤트에 자동 대응은 그 변화를 이벤트로 밖으로 내보내 알림을 자동으로 붙인다.

#2핵심 질문

태스크와 서비스의 상태 변화를 어떻게 알림과 자동 조치로 이어 붙이는가?

#3동작 예시

배포가 시작되고 태스크가 하나씩 바뀌는 동안 service action 이벤트가 EventBridge로 나간다. 여기에 채팅 앱 알림 규칙을 걸어 둔다.

어떤 태스크가 STOPPED가 되고 배포가 멈추면 container instance health change 이벤트도 붙는다. 규칙이 그 상태를 받으면 알림을 보내고 롤백 명령을 실행한다.

#4동작 과정

  1. 보낸다태스크나 서비스의 상태가 바뀌면 ECS가 이벤트를 생성해 EventBridge로 보낸다. 이 Amazon ECS events는 task state change events와 service action events로 나뉜다.
  2. 걸러낸다규칙에서 태스크 상태 변경과 배포 상태 변경, health event 가운데 필요한 것만 골라 낸다. 같은 작업에 여러 이벤트가 발생할 수 있어 중복 수신에 대비한다.
  3. 동작시킨다규칙이 알림 대상과 자동 처리 대상을 지정한다. 코드로 이벤트 JSON을 읽을 때는 앞으로 추가될 유형도 처리하게 해 둔다.
  4. 확인해 볼 것EventBridge 규칙 목록에서 ECS를 소스로 삼은 규칙이 있는 것을 본다.

Container Insights와 컨테이너 상태 확인

ECS가 CloudWatch에 보내는 상태 지표를 Container Insights가 모아 클러스터·작업·컨테이너 단위로 대시보드에 보여 주고, HEALTHCHECK 명령으로 컨테이너가 스스로 살아 있는지 검사한 결과를 함께 확인하는 것.

먼저 알아야 할 것 10-01

#1문제 상황

ECS의 기본 지표는 작업과 서비스 단위만 보여 준다(→ 10-01). 태스크가 여러 개면 어느 태스크가, 그 안의 어느 컨테이너가 문제인지 알 수 없다.

Container Insights는 클러스터에서 실행 중인 컨테이너를 찾아 성능 데이터를 모아 CloudWatch 대시보드에 태스크·컨테이너 단위로 보여 준다. 여기에 container health check 결과를 함께 얹어 컨테이너 health status로 볼 수 있다. 이 기능에 태스크와 컨테이너 지표를 더 확장한 것이 enhanced observability다.

#2핵심 질문

실행 중인 태스크와 컨테이너가 정상인지 어디서 한 화면으로 확인하려고?

#3동작 예시

주문 서비스가 느려져 CloudWatch 콘솔에서 Container Insights 대시보드를 연다. 태스크 목록에서 한 태스크의 CPU 그래프가 한계에 붙어 있고 상태는 HEALTHY로 보인다. 그 태스크를 열어 컨테이너를 내려가 본다.

컨테이너 health check 결과가 실패로 떠 있어 원인이 드러난다.

#4동작 과정

  1. 수집한다클러스터의 실행 중인 컨테이너를 찾아 성능 데이터를 모은다. 데이터는 정해진 JSON 스키마로 된 performance log events로 저장된다.
  2. 표시한다CloudWatch가 클러스터·서비스·태스크·컨테이너 단위 지표로 묶어 대시보드에 보여 준다. 태스크가 없는 리소스는 그 시간 구간에서 집계되지 않는다.
  3. 확인해 볼 것대시보드에서 태스크 하나를 열어 컨테이너별 CPU·메모리 그래프와 health status가 따로 보이는지 확인한다.

작업 메타데이터 엔드포인트와 컨테이너 메타데이터 파일

실행 중인 컨테이너가 task-arn 같은 자신의 속성을 내부에서 조회할 수 있도록 ECS가 제공하는 작업 메타데이터 엔드포인트와, 같은 정보를 파일·환경 변수로 노출하는 컨테이너 메타데이터 파일을 활용하는 것.

먼저 알아야 할 것 10-01

#1문제 상황

컨테이너 안의 애플리케이션은 자신이 어느 태스크에서 어떤 네트워크 설정을 가지고 있는지 모른다. 로그에 태스크 주소를 직접 넘겨 주기도 번거롭다.

task metadata endpoint와 container metadata file은 실행 중인 컨테이너가 스스로 이 정보를 조회하게 해 준다. 보안상 민감한 값은 넣지 않는다.

#2핵심 질문

컨테이너 안에서 자신의 태스크와 네트워크 정보를 어떻게 확인하려고?

#3동작 예시

주문 컨테이너가 외부 서비스에 접속할 때 호출할 대상 주소를 하드코딩하지 않는다. 대신 task metadata endpoint를 조회해 태스크의 상태와 IP 주소를 읽고 그 주소로 요청한다.

#4동작 과정

  1. 제공한다ECS가 태스크 수준 속성, 컨테이너의 ID·이름·이미지, IP 주소와 서브넷 같은 네트워크 설정, 태스크 상태를 컨테이너에서 읽을 수 있게 제공한다.
  2. 파일로 넘긴다container metadata file은 이 정보를 호스트에 파일로 만들고 컨테이너에 마운트한다. metadata file format으로 구조가 정해져 있다. 환경 변수로 넘길 값은 ECS environment variables로 따로 넣는다.
  3. 버전을 정한다task metadata endpoint version 4를 지정하면 어떤 항목이 노출되는지 정해진다.
  4. 확인해 볼 것컨테이너 안에서 메타데이터 경로를 열어 태스크 상태와 컨테이너 이름이 보이는지 확인한다.

ECS Exec은 이미 떠 있는 컨테이너에 명령을 넣어 진단 정보를 얻게 해 준다.

#2핵심 질문

#4동작 과정

  1. 켜 둔다태스크 정의에서 이 기능을 켜고 실행 권한 역할을 지정한다.
  2. 접속한다명령줄 도구로 aws ecs execute-command를 실행해 컨테이너 셸을 연다.
  3. 확인해 볼 것켜 둔 태스크에서 명령을 실행해 셸 응답이 오는지 확인한다.

#2핵심 질문

#4동작 과정

  1. 붙인다key와 선택적 value로 이루어진 tag를 클러스터·태스크 정의·서비스에 붙인다. 용도·소유자·환경 기준으로 묶는 용도다.
  2. 보고한다Cost and Usage Reports와 Usage Reports에서 tag별 사용량과 비용을 정리한다. 이것이 cost allocation의 기준선이 된다.
  3. 따로 막는다tagResourceAuthorization으로 tag에 민감한 값을 넣지 않는 권장 사항을 함께 기억한다.
  4. 확인해 볼 것콘솔에서 클러스터 목록의 tag 열에 붙인 key와 value가 보이는지 확인한다.

11. 권한과 네트워크 보안 — 무엇에 접근할 수 있는가11-01

task 실행 IAM role과 task role

ECS가 이미지를 받아와 컨테이너를 띄우는 동작 자체를 위해 쓰는 task execution IAM role과, 실행 중인 애플리케이션 컨테이너가 AWS 자원에 접근할 때 쓰는 task role이라는 두 가지 역할을 나누어 권한을 주는 구조입니다.

먼저 알아야 할 것 02-05

#1문제 상황

ECS가 이미지를 받아와 컨테이너를 띄우는 일과, 그 안의 애플리케이션이 AWS 서비스를 호출하는 일은 서로 다르다. 권한을 한 곳에 몰아넣으면 컨테이너가 필요 없는 권한까지 갖게 된다.

task execution IAM role과 task IAM role을 나누면 두 영역의 권한이 갈라진다.

#2핵심 질문

ECS 자체의 동작과 컨테이너 앱의 AWS 접근을 어떻게 권한으로 분리할까?

#3동작 예시

컨테이너가 S3 버킷의 설정을 읽어야 한다. ECS가 이미지를 받는 권한은 task execution IAM role에 주고, S3 읽기 권한은 task IAM role에 붙여 앱에 넘긴다.

#4동작 과정

  1. 실행 역할task execution IAM role은 ECS 컨테이너 에이전트와 Fargate 에이전트가 사용자를 대신해 AWS API를 부를 수 있게 한다. 이 자격 증명은 컨테이너에서 직접 쓸 수 없다.
  2. 앱 역할task IAM role은 실행 중인 애플리케이션 코드에 주는 권한이다. AWS KMS 권한과 image pull 권한도 이 역할에 붙일 수 있다.
  3. 확인해 볼 것태스크 정의에서 두 역할이 각각 어떤 이름으로 지정되어 있는지 확인한다.

service-linked role — ECS가 대신 관리하게 허용하기

cluster 등 ECS 리소스를 만들 때 그 리소스를 ECS가 사용자의 대신해 자동 관리할 수 있게 위임하는 AWS 전용 역할로, 사용자가 직접 권한 정책을 만들지 않아도 되게 합니다.

먼저 알아야 할 것 11-01

#1문제 상황

클러스터를 만들면 서비스 자동 확장이나 이벤트 발행 같은 다른 AWS 서비스까지 ECS가 대신 호출해야 한다. 필요한 권한을 사용자가 정책으로 하나씩 정의하면 번거롭고 빠뜨리기 쉽다.

service-linked role은 그 권한을 미리 담고 있다.

#2핵심 질문

ECS가 내 대신 다른 AWS 서비스를 호출하게 할 권한을 어떻게 간단히 줄까?

#3동작 예시

새 리전에 클러스터를 만든다. 콘솔이 요구하는 권한 목록을 직접 만들지 않아도 ECS가 알아서 전용 역할을 만들어 연관시킨다.

#4동작 과정

  1. 만들어진다ECS 리소스를 만들면 service-linked role이 AWS에 의해 생성되어 그 리소스에 연결된다.
  2. 자동 부여된다이 역할은 ECS가 사용자 대신 다른 AWS 서비스를 부르는 데 필요한 권한을 담고 있으며, 사용자가 직접 정책에 쓰지 않는다.
  3. 따로 준다나머지는 별도 역할을 쓴다. IAM permissions for service auto scaling 권한과 CodeDeploy IAM role, EventBridge IAM role가 그렇다.
  4. 확인해 볼 것IAM 콘솔에서 ECS 전용 역할을 목록에서 이름에 ECS가 들어간 역할을 찾는지 확인한다.

resource tag와 IAM policy로 접근 제어

ECS 리소스에 붙인 이름표(tag) 조건을 IAM 정책의 조건절에 넣어 특정 태그가 있는 클러스터·서비스·태스크에만 접근하도록 권한 범위를 좁히는 방법입니다.

먼저 알아야 할 것 11-02

#1문제 상황

클러스터마다 허용된 작업을 IAM 정책(policy, 누가 무엇을 할 수 있는지 적은 규칙 문서)에 하나씩 적으면 정책이 길어지고 관리가 어렵다. 리소스의 속성인 태그로 판단하게 만들면 정책이 짧아진다.

resource tag를 IAM 정책 조건에 넣으면 된다.

#2핵심 질문

사용자가 다룰 수 있는 리소스를 태그 값으로 어떻게 한 번에 정할까?

#3동작 예시

일반 사용자는 클러스터를 지울 수 있게 하되 environment=production 태그가 붙은 클러스터는 지우지 못하게 정책에 쓴다.

#4동작 과정

  1. 붙인다resource tag를 리소스에 붙이고 identity-based policy의 조건절에서 aws:ResourceTag 조건 키로 허용·거부한다. 이런 방식을 attribute-based access control(ABAC)이라 부른다.
  2. 예외를 적는다Describe 계열 동작은 리소스 수준 권한을 지원하지 않으므로 조건 없는 별도 문장으로 분리한다. example policies를 참고해 tagResourceAuthorization 형태로 쓴다.
  3. 기본을 정한다AWS managed policy를 기본으로 두고 필요한 조건만 덧붙인다.
  4. 확인해 볼 것조건 없는 정책 문장과 태그 조건이 있는 문장이 분리되어 있는지 확인한다.

VPC endpoint로 프라이빗 경로 만들기

internet을 거치지 않고 VPC 안에서만 ECS가 S3나 ECR 같은 AWS 서비스에 닿도록, 해당 서비스 앞단에 프라이빗 DNS 이름을 가진 VPC endpoint를 만들어 붙이는 것입니다.

먼저 알아야 할 것 11-02

#1문제 상황

태스크가 이미지를 받아오거나 로그를 보낼 때 internet을 거치면 트래픽이 VPC 밖으로 나갔다가 들어온다(→ 05-01).

VPC endpoint로 프라이빗 경로 만들기는 그 구간에 Interface VPC endpoint를 세워 internet을 거치지 않게 한다. AWS PrivateLink 기술이 기반이며, 인터넷 게이트웨이나 NAT 장치가 필요 없다.

#2핵심 질문

internet을 거치지 않고 VPC 안에서만 ECS가 AWS 서비스에 닿게 할 수 있을까?

#3동작 예시

보안 정책상 아웃바운드가 막힌 VPC에 이미지 배포 파이프라인을 세운다. 태스크가 ECR에서 이미지를 받아온다.

이미지가 정상적으로 내려오고, VPC 흐름 로그에도 외부로 나간 기록이 없다.

#4동작 과정

  1. 엔드포인트를 만든다VPC에 Interface VPC endpoint를 만들고 전용 프라이빗 DNS 이름을 부여한다. 트래픽이 VPC 안의 프라이빗 IP로만 ECS API에 닿고 AWS 네트워크 밖으로 나가지 않는다.
  2. 필요한 종류를 고른다ECS 관련 트래픽과 S3로 이미지·레이어만 주고받으려면 S3 gateway endpoint를 쓴다. 리전별 서비스 이름인 com.amazonaws.region.ecs와 ecs-agent, ecs-telemetry 같은 항목을 모두 만들지 않으면 그 트래픽은 공개 엔드포인트로 빠져나간다.
  3. 확인해 볼 것VPC의 엔드포인트 목록에서 ECS 관련 항목과 S3 gateway endpoint가 모두 private 상태로 보이는지 확인한다.

stopped task 오류 코드 읽기

태스크가 시작되지 못하고 멈췄을 때 ECS가 남기는 오류 코드를 보고, 권한 부족·이미지 문제·메모리 초과처럼 원인이 다른 경우를 구분해 대응하는 것입니다.

먼저 알아야 할 것 07-01

#1문제 상황

태스크를 실행했는데 PENDING 상태로 잠깐 보이다가 사라진다(→ 07-01). 화면에는 아무 설명이 없다.

stopped task errors는 태스크가 시작되지 못하고 멈췄을 때 ECS가 남기는 오류 코드 목록이다. 원인이 권한·이미지·메모리 중 어디인지 구분해 준다.

#2핵심 질문

태스크가 시작되지도 못하고 멈췄을 때 원인을 어떻게 구분해 대응할까?

#3동작 예시

새로 배포한 서비스의 태스크가 계속 사라진다. 서비스 이벤트에서 태스크가 중단됐다가 대체됐다는 기록이 보인다.

stopped task errors에서 ResourceInitializationError 아래 ContainerRuntimeError와 CannotPullContainerError가 함께 나왔고, 호스트의 컨테이너 런타임 로그에서 인증 실패를 확인한다.

#4동작 과정

  1. 코드를 찾는다ECS가 남긴 stopped task errors에서 첫 줄의 TaskFailedToStart 같은 상위 코드와 그 안에 붙은 원인을 본다. OutOfMemoryError이면 태스크가 허용된 메모리를 넘긴 것이고, CannotPullContainerError이면 이미지를 받지 못한 것이다.
  2. 범위를 좁힌다태스크를 만든 주체가 서비스라면 ECS 서비스 이벤트에서 중단·대체 이력을 확인한다. EC2 기반이면 호스트의 컨테이너 런타임 로그와 ECS container agent 로그를 함께 본다(→ 04-02).
  3. 확인해 볼 것서비스 이벤트 목록에서 해당 태스크의 stoppedReason과 reason 필드가 어떻게 적혀 있는지 확인한다.

서비스 오류 좁히기 — 이벤트·쿼터·로그

서비스가 기동을 못하거나 unhealthy 판정을 받을 때 ECS 서비스 이벤트와 AWS 서비스 쿼터, CloudWatch Logs를 차례로 확인해 원인을 좁혀 가는 절차입니다.

먼저 알아야 할 것 11-05

#1문제 상황

서비스를 만들었는데 태스크가 안 뜨거나 unhealthy 로만 남는다. 원인이 배치 실패인지 설정 실수인지 단서가 없다.

서비스 오류 좁히기 — 이벤트·쿼터·로그는 그 자리에서 service event messages, 서비스 쿼터, 로그 순으로 좁혀 가는 절차다.

#2핵심 질문

서비스가 unhealthy 이거나 기동하지 못할 때 어디부터 확인해야 원인을 찾을 수 있을까?

#3동작 예시

배포 직후 서비스 대시보드에서 desired 수만큼 태스크가 없어 desired 상태가 안 맞는다. 서비스 이벤트를 연다.

태스크 배치 실패가 반복되는 것을 보고 AWS 서비스 쿼터의 태스크 수 상한에 걸렸는지 확인한 뒤, CloudWatch Logs에서 마지막 로그를 확인한다.

#4동작 과정

  1. 이벤트를 읽는다service event messages에는 서비스 스케줄러의 태스크 배치·인스턴스 상태 이벤트가 service(이름) 접두사로 붙는다. 콘솔은 최근 이벤트만 보여 주고 같은 내용은 원인 해결되거나 시간이 지나기 전까지 반복하지 않는다.
  2. 쿼터를 확인한다AWS 서비스 쿼터에서 태스크 수나 리전별 상한에 걸렸는지 본다. service throttle logic이 걸리면 요청이 API request throttling으로 거절된다.
  3. 로그를 본다마지막으로 CloudWatch Logs에서 컨테이너 마지막 로그와, EC2 기반이면 container agent 로그를 확인한다. 앞에서 못 잡은 원인이 여기에 남는다.
  4. 확인해 볼 것서비스 이벤트 목록에 같은 사유가 몇 번 반복되는지, 그리고 상태가 어떻게 표시되는지 확인한다.
