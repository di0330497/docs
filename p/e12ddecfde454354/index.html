1. 로드 밸런서의 뼈대 — 네 종류와 공통 구조01-01

Elastic Load Balancing 이란 무엇인가

클라이언트 요청을 여러 서버(타깃)로 나눠 보내고 그중 healthiest 한 곳에 연결시키는 AWS 서비스로, 사용량에 따라 자동으로 용량이 늘고 줄어든다.

#1문제 상황

여러 대의 서버에 앱을 올려 두고 클라이언트 요청을 한 곳에 몰아 보내면 그 서버가 막힐 때 서비스 전체가 함께 멈춘다. Elastic Load Balancing은 이런 트래픽을 여러 대상으로 나눠 보내는 AWS 서비스이며, 사용자가 직접 서버를 붙였다 떼지 않아도 된다. 한 대상이 죽어도 나머지가 요청을 이어 받는다.

load balancer는 요청을 여러 계산 자원에 나눠 보내는 앞단 장치다. Elastic Load Balancing은 이 장치를 AWS가 운영·확장까지 맡아 주는 managed service 형태로 제공한다.

#2핵심 질문

여러 서버 앞단에 하나의 진입점을 두고 요청을 정상 서버에만 나눠 보내려면 어떻게 해야 하는가?

  1. 들어온 트래픽을 나눈다Elastic Load Balancing은 클라이언트 요청을 EC2 인스턴스·컨테이너·IP 주소 같은 여러 대상으로 분배한다. distributed computing은 계산을 여러 컴퓨터에 나누어 수행하는 방식이라 대상을 늘리면 처리량이 늘어난다.

  3. 용량을 알아서 맞춘다들어오는 트래픽 변화에 따라 용량이 자동으로 늘고 줄어든다.
  4. 확인해 볼 것콘솔에서 로드 밸런서의 타깃 그룹을 열어 각 대상 상태가 healthy로 표시되는지 확인한다.

  3. 가상 장비를 통과시킬 때Gateway Load Balancer를 쓴다. 모든 트래픽을 가상 네트워크 장비로 보내 처리하게 한다.

#1문제 상황

HTTP 트래픽을 여러 서버에 나눠 보내려면 리스너와 목적지, 그리고 서버가 든 묶음을 처음부터 손으로 맞춰야 한다(→ 01-01, → 01-03).

create an Application Load Balancer 를 수행하면 이 구성이 한 번에 만들어진다. Application Load Balancer 는 리스너와 대상 그룹을 엮은 로드 밸런서 묶음이며, scheme 로 내부·외부 중 어느 쪽에 노출할지 정하고(→ 01-05), type application 로 종류를 정하며, load balancer attributes 로 삭제 보호 같은 동작 설정을 함께 지정한다.

#2핵심 질문

HTTP 요청을 여러 서버로 나눠 보내는 로드 밸런서를 처음부터 어떻게 만드는가?

#3동작 예시

콘솔에서 로드 밸런서 만들기 화면을 열고 이름을 붙인 뒤 서브넷을 고른다. 보안 그룹과 리스너 포트를 지정하고 만들기를 누르면 DNS 이름이 나온다.

그 이름으로 브라우저에 접속하면 요청이 등록된 대상 서버 중 하나로 전달된다.

#4동작 과정

  1. 서브넷을 정한다VPC 안의 서브넷을 골라 배치하고(→ 02-02) 각 가용 영역에 대상 서버를 하나 이상 둔다. 그래야 어느 영역이 죽어도 요청이 남는다.
  2. 리스너를 만든다받을 포트와 프로토콜을 정한다(→ 03-01). HTTP·HTTPS 를 받으며 Application Load Balancer 는 이 두 프로토콜을 다룬다.
  3. 대상 그룹을 붙인다서버 묶음을 등록해 리스너가 거기로 보내게 한다(→ 04-01). 대상 서버의 보안 그룹이 리스너 포트와 헬스체크 포트에 대해 로드 밸런서 발신만 허용해야 대상이 in service 로 뜬다.
  4. 확인해 볼 것로드 밸런서를 고른 상태에서 DNS 이름이 표시되고 대상 그룹의 상태가 in service 인지 본다.

로드 밸런서를 어느 서브넷에 두고 어떤 트래픽을 통과시킬 것인가?

#3동작 예시

가용 영역 두 개의 프라이빗 서브넷을 골라 로드 밸런서를 만든다. 그 뒤 각 영역에서 대상 서버가 하나 이상 등록돼 있지 않으면 그 영역으로 요청이 잘 나가지 않는 것을 확인한다.

요청이 목적지 서버로 잘 못 가면 보안 그룹 규칙부터 본다.

#4동작 과정

  1. 서브넷을 고른다VPC 안에서 최소 두 개의 가용 영역에 걸쳐 서브넷을 고른다. Application Load Balancer 는 영역을 넘어 모든 대상에 요청을 보내는 cross-zone load balancing 이 켜져 있다.
  2. 보안 그룹을 정한다load balancer subnets 에 붙는 보안 그룹으로 클라이언트 발신만 허용해 들어오는 트래픽을 거른다. 나가는 방향은 outbound rules 로 필요한 곳만 열어 준다.
  3. 서브넷 앞단도 확인한다network ACLs 는 서브넷 경계에서 트래픽을 추가로 거르므로, 여기서 막히면 보안 그룹을 바꿔도 소용없다.
  4. 확인해 볼 것로드 밸런서의 Network mapping 탭에서 영역별 상태와 서브넷이 켜졌는지 본다.

IP 주소 타입은 로드 밸런서가 클라이언트에게 제공하는 주소가 IPv4 인지 IPv6 인지를 정하고, IP 풀은 Elastic IP 를 미리 모아 두는 주소 묶음이다.

먼저 알아야 할 것 02-01

#1문제 상황

IPv6 클라이언트까지 함께 받으려면 로드 밸런서만 바꿔서는 되지 않는다. VPC·서브넷·라우팅 테이블·보안 그룹·서브넷 앞단 필터가 함께 준비돼 있어야 한다(→ 02-02).

이 항목은 IP address type 을 정하고, dualstack 이나 IPv6 모드로 어느 주소를 내놓을지 고르는 곳이다. IP pools 는 사설 주소가 필요한 내부 로드 밸런서에서 static IP addresses 를 미리 모아 둔다.

#2핵심 질문

로드 밸런서가 클라이언트에게 내어 줄 주소를 IPv4 와 IPv6 중 어느 형태로 낼 것인가?

#3동작 예시

Network mapping 탭에서 Edit IP address type 을 열어 dualstack 을 고른다. 서브넷에 IPv6 CIDR 이 없다면 저장이 거절되고, 먼저 서브넷과 보안 그룹, network ACLs 를 고친 뒤 다시 고른다.

바뀐 뒤에는 같은 DNS 이름으로 IPv4 와 IPv6 어느 쪽에서도 접속할 수 있다.

#4동작 과정

  1. 타입을 고른다IP address type 을 만들 때도 나중에라도 고를 수 있다. dualstack 을 고르면 두 주소를 함께 받는다. 로드 밸런서는 대상 그룹의 IP address type 에 맞춰 대상과 통신한다.
  2. IPv6 준비를 한다VPC 와 서브넷에 IPv6 CIDR 이 있어야 하고, 로드 밸런서 서브넷의 라우팅 테이블이 IPv6 트래픽을 전달해야 한다. 보안 그룹과 network ACLs 도 IPv6 트래픽을 허용해야 한다.
  3. IP 풀을 쓴다내부 로드 밸런서가 고정된 사설 주소가 필요하면 IP pools 에 static IP addresses 를 미리 할당한다. 그래서 지정한 주소로만 내부에서 접속할 수 있다.
  4. 확인해 볼 것로드 밬런서를 고른 뒤 Network mapping 탭의 IP 주소 타입 항목에 저장된 값이 보이는지 본다.

#3동작 예시

  2. 보호를 건다deletion protection 을 켜면 실수로 삭제하려 할 때 삭제가 막힌다. 지우려면 이 값을 먼저 꺼야 한다.

  4. 확인해 볼 것속성 목록에서 삭제 보호 값이 켜짐으로 표시되고 대시보드 상단에 붙인 태그 이름이 보이는지 본다.

먼저 알아야 할 것 02-04

#1문제 상황

ALB 는 Application Load Balancer 의 줄임말로, HTTP 요청을 여러 서버에 나눠 보내는 로드 밸런서다(→ 02-01). 테스트로 만든 ALB 를 치우려는데 삭제가 막히고, 요청이 통하지 않을 때 어디서 문제인지 하나씩 뒤져야 한다.

이 항목은 delete a load balancer 를 끝내는 순서와 troubleshooting 문서가 정해 둔 증상 목록을 다룬다.

#2핵심 질문

로드 밸런서를 어떻게 지우고, 증상마다 무엇을 먼저 확인해야 하는가?

#3동작 예시

대상 서버 하나가 in service 가 되지 않아 화면에 그대로 뜬다. 문서 troubleshooting 목록에서 등록된 대상이 in service 가 아니다 항목을 찾아 health check port 로 대상에 직접 요청해 본다.

외부 로드 밸런서로 클라이언트가 붙지 않는다면 보안 그룹과 subnet 을 차례로 확인한다.

#4동작 과정

  1. 멈춰부터 정리한다delete a load balancer 를 수행하기 전에 리스너와 타깃 그룹을 먼저 정리한다(→ 06-01). 남은 리스너가 있으면 삭제 자체가 막힌다.
  2. 증상을 분류한다등록 대상이 in service 가 아닌 경우, 외부 로드 밸런서에 연결이 안 되는 경우, HTTP 오류를 내는 경우처럼 troubleshooting 문서가 증상별로 묶어 둔다.
  3. 요청을 좇는다custom domain 으로 온 요청이 닿지 않는다면 리스너 규칙과 인증서 발급 상태(→ 08-01), access denied 면 권한 문제부터 본다. 리소스 수를 넘긴 경우에는 limits 문서에서 한계를 확인한다.
  4. 확인해 볼 것대상 그룹의 타깃 목록에서 상태가 in service 인 대상만 남아 있는지 본다(→ 04-04).

리스너가 무엇인가

리스너는 로드 밸런서가 어떤 포트와 프로토콜의 요청을 받을지 정해 둔 연결 지점이다.

먼저 알아야 할 것 02-01

#1문제 상황

Application Load Balancer를 만든 직후에는 아무 요청도 받지 못한다. 리스너가 하나도 없으면 클라이언트 트래픽이 로드 밸런서에 닿을 통로가 없기 때문이다.

리스너는 로드 밸런서가 받을 프로토콜(protocol)과 포트(port)를 정하는 설정이고, 그 안에서 요청을 어디로 보낼지 결정한다. listeners를 등록하면 로드 밸런서가 EC2 인스턴스 같은 타깃(→ 01-02)으로 요청을 넘길 수 있다.

#2핵심 질문

로드 밸런서가 클라이언트 요청을 받을 통로를 어떻게 만드는가?

#3동작 예시

주문 서비스의 로드 밸런서를 만들고 리스너를 추가한다. 포트 80과 프로토콜 HTTP를 고른다.

그 뒤 브라우저로 도메인에 접속하면, 아무 설정이 없던 로드 밸런서가 요청을 받아 지정한 타깃 그룹으로 보내 응답이 돌아온다.

#4동작 과정

  1. 리스너를 만든다포맷의 Protocol:Port 지점에서 새 리스너를 추가한다. protocol은 HTTP와 HTTPS를 받고 port는 1부터 65535까지 지정한다.
  2. 기본 동작을 정한다조건에 걸리지 않은 요청이 갈 곳을 default action으로 지정한다. 이 기본 대상은 forward로 타깃 그룹 하나를 가리키는 것이 보통이다.
  3. 확인해 볼 것콘솔의 Listeners and rules 탭에서 새 리스너의 프로토콜과 포트가 Protocol:Port 목록에 보이는지 확인한다.

HTTPS 리스너와 인증서

HTTPS 리스너는 암호화된 요청을 받는 리스너로, ACM에 등록한 SSL/TLS 인증서를 붙여 상대방의 신원을 확인하고 내용을 복호화한다.

먼저 알아야 할 것 03-01

→ 03-03 참조

#1문제 상황

HTTP 리스너(→ 03-01)는 요청과 응답을 평문으로 주고받는다. 그 위에서 카드번호나 로그인 정보가 그대로 노출된다.

HTTPS 리스너는 암호화를 스스로 처리한다. AWS Certificate Manager에서 발급받은 서버 인증서를 붙여야 이 리스너가 만들어진다.

#2핵심 질문

클라이언트가 신뢰할 수 있는 인증서를 로드 밸런서에 어떻게 붙이는가?

#3동작 예시

HTTPS 리스너를 만들면서 shop.example.com 인증서를 지정한다. 도메인 이름이 다르면 클라이언트가 TLS 핸드셰이크에서 인증서를 검증하지 못하고 연결이 끊긴다.

보통 도메인 하나로 기본 인증서 하나만 두고, 여러 도메인을 함께 받을 때 listener certificates를 더 붙인다. 서버가 어떤 인증서를 제시할지 클라이언트가 미리 알려 주는 방식은 SNI다.

#4동작 과정

  1. 인증서를 준비한다AWS Certificate Manager에서 도메인 이름이 적힌 인증서를 발급받는다. 클라이언트가 요청한 호스트 이름과 인증서의 도메인이 일치해야 검증에 성공한다.
  2. HTTPS 리스너를 만든다protocol을 HTTPS로 고르고 이 인증서를 default certificate로 지정한다. 로드 밸런서가 암호화와 복호화를 대신 처리해 타깃은 평문 요청만 받는다.
  3. 추가 도메인을 붙인다여러 이름을 한 리스너에서 받으려면 listener certificates로 인증서를 더 등록한다. 어떤 인증서를 제시할지는 SNI로 클라이언트가 먼저 알려 준다.
  4. 확인해 볼 것리스너 상세 화면에서 기본 인증서의 도메인 이름이 내 도메인과 같은지 확인한다.

보안 정책은 리스너가 허용하는 암호화 방식과 TLS 버전의 조합을 정한 이름 붙은 설정으로, 정책 이름을 골라 그때그때 필요한 수준을 고른다.

먼저 알아야 할 것 03-02

→ 03-02 참조

#1문제 상황

HTTPS 리스너(→ 03-02)가 있다고 해서 모든 암호화를 허용하면 된다. 아니다. 연결을 맺는 쪽마다 지원하는 암호 방식과 TLS version이 다르다.

그 조합이 클라이언트와 로드 밸런서 사이에 맞지 않으면 연결 자체가 안 열린다. 그래서 하나의 정해진 조합을 골라야 한다.

#2핵심 질문

리스너가 어떤 암호 방식과 TLS 버전을 받아들일지 어떻게 정하는가?

#3동작 예시

구형 장비가 있는 내부망까지 붙어 있어 오래된 TLS 버전이어야 한다. 그래도 보안 정책 하나를 그대로 쓰면 구형 장비가 연결되지 않는다.

리스너마다 보안 정책 이름을 갈아 씌워 허용 범위를 맞춘다.

#4동작 과정

  1. 정책을 고른다보안 정책은 protocol과 cipher의 조합이다. cipher는 암호 키로 평문을 부호화하는 알고리즘이고, protocol은 이 암호 알고리즘들을 쓴다.
  2. 버전을 정한다policy 안에서 TLS version이 정해져 클라이언트와 로드 밸런서가 같은 조합으로 협상한다. 서로 겹치는 조합이 없으면 협상이 실패한다.
  3. 목록을 확인한다describe-ssl-policies 명령으로 현재region에서 쓸 수 있는 정책 이름을 미리 볼 수 있다.
  4. 확인해 볼 것리스너 상세 화면에 선택한 보안 정책 이름이 보이는지 확인한다.

리스너 규칙의 구조

리스너 규칙은 조건과 그 조건을 만족할 때 할 동작을 한 쌍으로 묶은 설정으로, 리스너마다 규칙 목록을 위에서부터 차례로 검사한다.

먼저 알아야 할 것 03-01

#1문제 상황

리스너 하나에 기본 동작 하나만 두면 모든 요청이 같은 곳으로 간다(→ 03-01). 하나의 로드 밸런서로 여러 서비스나 마이크로서비스를 함께 받으려면 갈 곳을 나눠야 한다.

나눔의 기준이 규칙이다. 조건을 만족한 요청에만 정해진 동작을 적용한다.

#2핵심 질문

요청마다 어떤 조건을 보고 어디로 보낼지 어떻게 정하는가?

#3동작 예시

하나의 로드 밸런서 앞에 이미지 서버와 주문 API를 함께 둔다. 요청의 host-header가 img.example.com이면 이미지 타깃 그룹으로 보낸다.

주문 API는 그 외의 요청을 받아 주문 타깃 그룹으로 보내면 된다.

#4동작 과정

  1. 우선순위를 정한다listener rule마다 rule priority를 매기고, 리스너는 번호가 작은 규칙부터 차례로 검사한다.
  2. 조건을 건다rule condition을 하나 이상 붙인다. host-header는 요청의 도메인 이름을, path-pattern은 경로를 본다.
  3. 동작을 정한다forward action으로 조건이 맞을 때 보낼 타깃 그룹을 지정한다. 기본 동작(→ 03-01)과 같은 방식으로 동작을 하나 고른다.
  4. 확인해 볼 것리스너의 Rules 탭에서 규칙이 우선순위 번호 순으로 나열되어 있는지 확인한다.

#2핵심 질문

#4동작 과정

  1. 종류를 고른다rule action types 가운데 forward(지정 타깃 그룹으로 전달), redirect(주소 넘기기), fixed-response(직접 만든 HTTP 응답 반환) 중 하나를 고른다. HTTPS 리스너에서는 authenticate-cognito로 사용자 인증을 걸 수도 있다.
  2. 변환을 더한다transform에 정규식과 대체 문자열을 넣으면 매칭된 부분이 바뀐다. URL rewrite로 경로를 고쳐 보내는 것도 이 안에서 한다.
  3. 확인해 볼 것규칙 편집 화면의 Actions 항목에 고른 동작 종류가 목록으로 보이는지 확인한다.

타깃 그룹이 무엇인가

타깃 그룹은 로드 밸런서가 요청을 보낼 서버·컨테이너 같은 처리 대상들을 하나의 묶음으로 등록해 관리하는 단위이며, 이 묶음을 가리키는 이름이 리스너 규칙의 목적지로 쓰인다.

먼저 알아야 할 것 03-04

#1문제 상황

리스너 규칙은 요청을 어느 곳으로 보낼지 이름 하나로 정한다(→ 03-04). 하지만 그 이름이 어떤 서버 묶음을 뜻하는지 정하지 않으면 규칙이 완성되지 않는다.

target group은 로드 밸런서가 요청을 보낼 서버나 컨테이너 같은 처리 대상들을 한 묶음으로 등록해 관리하는 단위다. 이 묶음을 가리키는 이름이 리스너 규칙의 목적지로 쓰인다. 대상은 인스턴스 ID, IP 주소, Lambda 함수 중 등록 방식(target type)에 따라 골라진다.

#2핵심 질문

리스너 규칙이 요청을 보낼 목적지를 무엇으로 지정할까?

#3동작 예시

일반 주문 요청과 결제 요청의 경로를 다르게 하려고 타깃 그룹을 둘 만든다. 일반 요청은 주문 서버 묶음으로, 결제 경로가 맞는 요청은 결제 서버 묶음으로 보낸다.

각 묶음은 따로 health check 설정을 갖고, 그 안의 정상 대상에게만 트래픽이 갈린다.

#4동작 과정

  1. 묶음을 만든다대상을 담을 target group을 만들고 protocol과 port로 받을 트래픽의 종류를 정한다. 같은 대상을 여러 타깃 그룹에 넣을 수도 있다.
  2. 규칙에서 가리킨다리스너 규칙에 target group 이름을 적어 둔다. 조건이 맞으면 그 묶음으로 트래픽이 넘어가고, 조건별로 묶음을 다르게 둘 수 있다.
  3. 설정을 다듬는다target group attributes로 느린 시작이나 영역 간 분산 같은 동작을 조절하고, target group tags로 묶음을 찾아 관리한다. 한 묶음은 로드 밸런서 하나에만 붙인다.
  4. 확인해 볼 것콘솔에서 타깃 그룹을 열면 등록된 대상과 상태가 보이는지 확인한다.

#5한 줄 요약

타깃 그룹요청을 받을 대상들을 한 묶음으로 묶어 리스너 규칙이 가리키게 하는 것

타깃 등록과 해제

타깃 등록은 처리 대상을 타깃 그룹에 새로 추가해 요청을 받을 수 있게 하는 절차이고, 타깃 해제는 그 대상을 그룹에서 빼고 더 이상 요청을 보내지 않게 하는 절차다.

먼저 알아야 할 것 04-01

#1문제 상황

트래픽이 늘면 등록된 대상만으로는 감당이 안 된다. 반대로 유지보수로 서버를 내리고 싶어도, 대상을 빼는 동작이 없다면 로드 밸런서는 계속 그 서버로 보낸다(→ 04-01).

register targets는 처리 대상을 타깃 그룹에 새로 넣어 요청을 받을 수 있게 하는 절차다. deregister targets는 그 대상을 그룹에서 빼고 더 이상 요청을 보내지 않게 하는 절차다. 대상은 target ID로 가리키고 어떤 availability zone의 어느 port에 있는지로 짚는다.

#2핵심 질문

요청을 받을 대상을 타깃 그룹에 넣고빼는 절차는 무엇인가?

#3동작 예시

주문 서버 두 대로 부족해 새 인스턴스 한 대를 세운다. 그 인스턴스를 타깃 그룹에 등록하자마자 로드 밸런서가 상태 확인을 돌려 통과를 기다린다.

통과하면 그 인스턴스로도 요청이 나뉘어 들어간다. 유지보수할 때는 대상을 해제해 새 요청이 그쪽으로 가지 않게 한다.

#4동작 과정

  1. 등록한다대상의 식별자를 타깃 그룹에 넣는다. 등록 절차가 끝나고 초기 health check를 통과하면 로드 밸런서는 그 대상으로 요청을 보낸다.
  2. 해제한다대상을 그룹에서 빼면 로드 밸런스는 그 대상으로 가는 요청을 즉시 멈춘다. 대상이 다시 준비되면 등록 절차를 거친다.
  3. 분산한다대상을 여러 availability zone에 나누어 두면 로드 밸런서가 영역별로 고르게 보낸다. 어느 한 port만 받을 대상으로 좁혀 등록할 수도 있다.
  4. 확인해 볼 것타깃 그룹의 대상 목록에 새 대상이 추가됐고 상태가 Healthy로 바뀌는지 확인한다.

헬스체크의 종류

헬스체크는 로드 밸런서가 주기적으로 타깃에 요청을 보내 응답이 정상인지 확인해, 실패한 타깃을 잠시 제외하고 복구되면 다시 넣는 확인 절차다.

먼저 알아야 할 것 04-01

#1문제 상황

서버가 켜져 있어도 애플리케이션이 응답하지 않을 수 있다. 그런 서버까지 로드 밸런서가 트래픽을 보내면 사용자가 오류를 본다(→ 04-01).

health checks는 로드 밸런서가 주기적으로 타깃에 요청을 보내 정상 응답을 확인하는 절차다. 실패한 타깃은 잠시 제외하고 다시 통과하면 넣는다. 요청을 보내는 대상과 경로는 protocol과 health check path로 정하고, 무엇을 정상으로 볼지는 matcher로 정한다. unhealthy threshold 연속 실패 횟수를 넘으면 unhealthy로 판정한다.

#2핵심 질문

어떤 대상이 요청을 받을 수 있는지 로드 밸런서는 어떻게 판정하는가?

#3동작 예시

체크 경로를 /health로 둔 주문 서버 묶음을 본다. 한 대가 응답을 멈추자 몇 번 연속 실패가 쌓여 상태가 unhealthy로 바뀐다.

그 대상으로는 트래픽이 가지 않고 나머지 대상만 받는다. 서버가 고쳐지면 다음 체크를 통과해 다시 healthy로 돌아온다.

#4동작 과정

  1. 보낸다등록 직후부터 health check를 주기적으로 보내고, 통과한 대상을 healthy로 본다. 한 번의 검사 뒤에는 그때 쓴 연결을 닫는다.
  2. 빼고 되돌린다unhealthy threshold만큼 연속 실패하면 대상을 제외하고, 다시 통과하면 healthy로 되돌린다. 검사 경로와 matcher는 health check path와 정상 응답 조건으로 정해 둔다.
  3. 예외를 정한다묶음 안의 등록 대상이 모두 unhealthy면 로드 밸런서는 상태와 상관없이 전부로 보낸다. 이 fail open 동작이 전체가 막히는 것을 막아 준다.
  4. 확인해 볼 것타깃 그룹의 상태 화면에서 Healthy와 Unhealthy 대상 수가 어떻게 나눠지는지 확인한다.

헬스체크주기적으로 대상을 찔러 보고 정상 응답하는 대상에만 트래픽을 보내는 것

헬스체크를 직접 확인한다

헬스체크를 직접 확인한다는 것은 타깃 그룹의 타깃별 상태와 사유(healthy, unhealthy, unused 등)를 콘솔이나 CLI 로 조회해 어떤 타깃이 요청을 받고 있는지 파악하는 것이다.

먼저 알아야 할 것 04-03

#1문제 상황

주문이 간헐적으로 실패한다. 헬스체크가 도는 것은 알지만 어떤 대상이 왜 빠졌는지는 모른다(→ 04-03).

check target health는 타깃 그룹의 대상별 상태와 그 사유를 직접 조회해 확인하는 기능이다. 확인한 결과가 target health state와 reason description으로 보인다. 상태가 정상 밖이면 그 사유가 함께 붙어 원인을 짚을 수 있다. health check settings로 검사 조건 자체도 함께 본다.

#2핵심 질문

어떤 대상이 왜 요청을 받고 있지 않은지 어떻게 확인하는가?

#3동작 예시

헬스체크 실패로 접속이 끊긴 Orders 서비스의 타깃 그룹을 연다. 상세 화면에서 대상 하나가 Unhealthy이고 사유가 타임아웃으로 떠 있다.

같은 화면에서 검사 경로와 matcher가 어떻게 설정됐는지도 함께 확인해 원인을 좁힌다.

#4동작 과정

  1. ta깃 그룹을 연다타깃 그룹의 상세 화면으로 가면 상태별 대상 수가 한눈에 보인다. Targets 탭의 Status 열이 대상별 상태를 보여 준다.
  2. 사유를 읽는다Healthy가 아닌 대상은 Status details에 사유가 함께 나온다. 이 사유가 실패 지점을 짚어 준다.
  3. CLI로 확인한다같은 정보를 명령으로만 조회해 반복해서 볼 수도 있다. 실패 원인이 계속되면 health check logs를 켜서 검사 자체의 내용을 S3에 남겨 본다.
  4. 확인해 볼 것콘솔의 대상 목록에서 상태와 사유가 대상마다 붙어 표시되는지 확인한다.

Lambda를 타깃으로 쓰기

Lambda 를 타깃으로 쓰면 함수 ARN 을 타깃 그룹에 등록해 요청을 함수로 직접 넘기는 방식으로, 서버 없이 함수 하나로 리스너를 구성할 수 있다.

먼저 알아야 할 것 04-02

#1문제 상황

간단한 처리를 위해 서버를 켜 두는 것은 낭비다. 서버 없이 요청만 받고 응답하고 싶은 경우도 많다(→ 04-02).

Lambda functions as targets는 AWS Lambda 함수를 타깃 그룹에 등록해 요청을 함수로 넘기는 방식이다. 등록 방식(target type)을 Lambda로 고르면 함수 ARN이 대상 식별자가 된다. 로드 밸런서는 네트워크 연결을 띄우지 않고 함수를 직접 호출하며, 요청 본문은 JSON 형식으로 전달된다.

#2핵심 질문

서버 없이 함수 하나로 요청을 받고 응답할 수 있는가?

#3동작 예시

경로가 /ping으로 들어온 요청을 Lambda 함수가 처리하게 한다. 함수가 함수 ARN으로 타깃 그룹에 등록돼 있고 리스너 규칙이 그 묶음을 가리킨다.

요청이 오면 로드 밸런서가 함수를 직접 부르고, 함수가 돌려 준 응답이 그대로 클라이언트로 나간다.

#4동작 과정

  1. 함수를 준비한다AWS Lambda 함수를 만들고 요청을 받을 형식으로 응답값을 정한다. 응답 헤더를 여러 개 넘겨야 하면 multi-value headers 지원을 켠다.
  2. 묶음을 만들고 등록한다target type을 Lambda로 지정해 타깃 그룹을 만들고 함수를 ARN으로 등록한다. 호출을 허용하려면 함수가 받을 permission을 함께 설정한다.
  3. 연결하고 확인한다리스너 규칙이 그 타깃 그룹을 가리키게 한다. health checks를 켜면 함수가 응답하는지 검사하며, 필요 없으면 대상을 deregister해 다시 뗀다.
  4. 확인해 볼 것타깃 그룹 화면에서 대상이 Lambda 함수로 표시되고 상태가 Healthy인지 확인한다.

타깃 그룹의 속성과 태그

타깃 그룹의 속성은 등록 방식이나 느린 시작 같은 동작을 조절하는 설정값이고, 태그는 이름과 값을 붙여 비용·권한 관리에서 자산을 구분해 찾는 표시다.

먼저 알아야 할 것 04-01

#1문제 상황

타깃 그룹을 만들어도 동작 세부가 기본값으로 정해진다. 서버를 빼낼 때 기존 요청을 끝까지 받게 하고 싶어도 기본값만으로는 부족하다(→ 04-01).

target group attributes는 그런 동작을 조절하는 설정값 묶음이다. 해제 지연 시간, 라우팅 알고리즘, 느린 시작 모드, 영역 간 분산, 헬스체크 설정, Sticky sessions, WAF 동작이 여기에 속한다. target group tags는 묶음에 이름과 값을 붙여 비용·권한 관리에서 찾아 쓰는 표시다.

#2핵심 질문

타깃 그룹의 동작을 바꾸는 설정값은 무엇인가?

#3동작 예시

주문 서버를 교체한다. 기본값으로 해제하면 진행 중인 요청이 끊길 수 있으니 해제 지연 시간을 늘려 끝까지 받게 한다.

느린 시작 모드도 켜서 새 서버가 천천히 요청을 받도록 하고, 이 묶음에는 서비스 이름 태그를 붙여 나중에 찾는다.

#4동작 과정

  1. 속성을 본다타깃 그룹의 속성 화면에서 대상의 동작을 정하는 값들을 확인한다. deregistration delay는 기본 300초 동안 진행 중인 요청이 끝나기를 기다린다.
  2. 끄기와 켜기Slow start mode로 새 대상의 가중치를 서서히 올리고, Sticky sessions로 같은 클라이언트를 같은 대상에 붙인다. Cross-zone load balancing과 Automatic Target Weights 같은 값도 여기서 정한다.
  3. 태그를 붙인다target group tags로 이름과 값을 넣어 비용 배분과 권한 관리에서 이 묶음을 구분한다. stickiness 같은 나머지 설정도 같은 목록에 있다.
  4. 확인해 볼 것속성 화면에서 해제 지연 시간과 느린 시작 모드의 설정값이 보이는지 확인한다.

5단계 5. Network LB — 연결 계층에서 받는다

TCP 같은 전송 계층 프로토콜을 그대로 받아 서버 묶음에 분배하는, AWS의 Layer 4 부하 분산 장치이다.

먼저 알아야 할 것 01-03

#1문제 상황

LB 는 Load Balancer 의 줄임말로, 요청을 여러 서버에 나눠 보내는 방식을 가리킨다. Application Load Balancer 는 HTTP 요청의 헤더와 경로를 읽어 라우팅한다(→ 01-03). 그래서 단순 TCP 로만 동작하는 게임 서버나 오래된 프로토콜에는 맞지 않는다.

Network Load Balancer 는 포트만 보고 연결을 나누는 방식이다. type network 로 만들면 이런 트래픽을 받을 수 있고, scheme 로 내부·외부 여부를 고르며, static IP addresses 로 고정 주소를 쓸 수 있다.

#2핵심 질문

TCP 처리를 다루는 게임 서버 같은 트래픽을 어떤 로드 밸런서로 받을까?

#3동작 예시

게임 서버가 여러 대 켜져 있고 모든 방을 같은 주소로 붙여 세워야 한다. Network Load Balancer 앞에서 하나의 주소를 내보내고, 들어온 연결을 서버 중 한 대로 보낸다.

서버 한 대가 점검 중이면 그 서버로 새 연결을 보내지 않고 나머지 서버가 받는다.

#4동작 과정

  1. 만든다로드 밸런서를 만들면서 type 을 network 로 정한다. scheme 으로 인터넷에 공개할지 VPC 안에서만 볼지 고르고, static IP addresses 를 지정해 고정 주소를 붙인다.
  2. 등록한다처리할 서버 묶음을 타깃 그룹으로 묶어 등록한다(→ 05-04). 로드 밸런서는 등록된 대상의 상태를 주기적으로 확인해 정상인 곳으로만 보낸다.
  3. 확인해 볼 것콘솔의 로드 밸런서 목록에서 생성한 이름이 Internet-facing 또는 Internal 로 표시되는지 확인한다.

가용 영역과 프라이빗 주소

부하 분산기가 고객의 요청에 응답할 AWS 안의 격리된 구역 단위이며, 각 가용 영역에 하나씩 배치되면 여기에 할당된 프라이빗 IP 로 내부에서만 접근할 수 있다.

먼저 알아야 할 것 05-01

#1문제 상황

Network Load Balancer 를 VPC 안에 만들면 어느 서브넷에 놓을지 정해야 한다(→ 05-01). 영역 하나에만 놓으면 그 영역이 흔들릴 때 함께 멈춘다.

Availability Zones 는 AWS 안에서 서로 독립된 구역이다. area 당 subnet 하나를 고르면 그 subnet에서 load balancer subnets 가 정해지고, 그 안에 Elastic IP addresses 를 쓸 수 있으며, 걸어 들어오는 트래픽은 security groups 규칙으로 걸러진다.

#2핵심 질문

로드 밸런서를 장애 없는 여러 구역에 어떻게 나눠 놓을까?

#3동작 예시

Internet-facing Network Load Balancer 를 만든다. 콘솔에서 두 개의 영역에 대해 subnet 을 하나씩 고른다.

각 영역 안에 로드 밸런서 노드가 하나씩 생기고, 그 노드는 선택한 subnet 의 네트워크 인터페이스로 IPv4 주소를 받는다.

#4동작 과정

  1. 영역을 고른다활성화할 Availability Zone 마다 그 영역에서 subnet 하나를 지정한다. 영역을 켠 뒤부터 그 영역에 등록된 타깃으로 요청이 흐른다.
  2. 노드를 만든다Elastic Load Balancing 이 고른 영역마다 Network Load Balancer 노드와 subnet 용 네트워크 인터페이스를 만든다. 이 인터페이스로는 주소를 볼 수만 바꿀 수는 없다.
  3. 주소를 붙인다internet-facing 이면 subnet 이 지정한 조건을 만족해야 하고, address 필요량으로 Elastic IP addresses 를 예약해 고정 주소로 쓴다.
  4. 확인해 볼 것로드 밸런서의 상태를 보면 영역별로 enabled 상태가 따로 표시되는지 확인한다.

NLB 의 리스너와 규칙

들어오는 연결을 받을 포트와 프로토콜을 정하는 설정이며, 리스너에는 조건에 따라 요청을 어느 타깃 그룹으로 보낼지 정하는 규칙을 덧붙일 수 있다.

먼저 알아야 할 것 05-01

#1문제 상황

NLB 는 Network Load Balancer 의 줄임말이다. 이 로드 밸런서를 만들어도 어떤 포트의 연결을 받을지 정하지 않으면 아무것도 응답하지 않는다(→ 05-01). 게임 클라이언트는 9000 포트로 붙는 쪽이다.

리스너를 만들면 그 포트와 프로토콜이 정해진다. 그 위에 update listener rules 로 조건을 덧붙이고, TLS listener 에는 SSL 인증서를 붙여 연결을 끝낸 뒤 내부로 넘긴다.

#2핵심 질문

Network Load Balancer 가 받을 포트와 그 안에서 갈라지는 조건을 어떻게 정할까?

#3동작 예시

TCP 9000 포트로 들어오는 게임 연결을 받는 리스너를 만든다. 그 뒤 규칙 하나를 추가해 host header 조건이 특정 값일 때 다른 타깃 그룹으로 보내게 한다.

콘솔에서 리스너를 열면 포트·프로토콜과 그 아래 규칙 목록이 보인다.

#4동작 과정

  1. 리스너를 만든다로드 밸런서를 만들 때도 만들고 나중에도 더할 수 있다. 기본 동작에 보낼 타깃 그룹은 필수다.
  2. TLS 를 붙인다TLS listener 는 SSL 인증서를 지정해야 한다. 로드 밸런서가 그 인증서로 연결을 끊고 암호를 풀어 목적지 요구사항을 충족시킨 뒤 원본을 평문으로 넘긴다.
  3. 규칙을 더한다update listener rules 로 조건과 동작을 짝지어 추가한다. host header 조건을 쓰면 요청이 요구한 호스트 이름에 따라 갈리는 타깃 그룹을 정할 수 있다.
  4. 확인해 볼 것리스너 목록에 포트와 프로토콜이 보이는지, 규칙 목록에 조건이 몇 개 걸려 있는지 확인한다.

NLB 리스너받을 포트와 프로토콜을 정해 두고 그 안에서 요청을 갈라 보낼 조건을 더하는 것

IP 타깃 등록

요청을 실제로 처리할 대상의 IP 주소를 미리 등록해 두는 것이며, 등록된 대상 집합을 타깃 그룹이라 부른다.

먼저 알아야 할 것 05-03

#1문제 상황

리스너가 갈 곳을 정했다(→ 05-03). 그런데 어디로 보내야 하는지는 아직 없다. EC2 인스턴스 번호를 넣을 수도 있고 IP 주소를 넣을 수도 있다.

타깃 그룹은 등록 방식인 target type 을 고르고, ip 를 고르면 IP addresses as targets 를 넣게 된다. 등록된 대상은 preserve client IP 설정까지 함께 정해진다.

#2핵심 질문

요청을 실제로 처리할 대상을 로드 밸런서에 어떻게 알려 주는가?

#3동작 예시

서버가 매니페스트로 주소를 받으므로 인스턴스 번호 대신 IP 주소 목록을 타깃 그룹에 넣는다. 등록이 끝나고 첫 상태 확인을 통과하면 로드 밸런서가 그 주소로 요청을 보낸다.

#4동작 과정

  1. 유형을 고른다타깃 그룹의 등록 방식에 따라 인스턴스 ID, IP 주소, Application Load Balancer 등을 등록할 수 있다. IP 를 넣는 그룹은 target type 을 ip 로 둔다.
  2. 등록한다register targets 로 대상을 추가한다. 등록 절차가 끝나고 초기 상태 확인을 통과하면 그때부터 요청이 흐른다.
  3. 뺀다수요가 줄면 대상을 해제한다. 로드 밸런서가 그 대상에 요청을 보내지 않게 되는 데는 몇 분 걸릴 수 있다. 이때 preserve client IP 를 켜 두면 클라이언트 주소가 그대로 전달된다.
  4. 확인해 볼 것타깃 그룹에서 각 대상의 상태가 healthy 로 떠 있는지 확인한다.

유휴 시간 초과와 속성

연결이 오간 없이 놀기만 하는 상태로 허용되는 시간(유휴 시간 초과)과, 교체를 시도하는 위치나 대상 등록 방식 같은 부하 분산기 설정값을 조절하는 작업이다.

먼저 알아야 할 것 05-01

#1문제 상황

긴 세션에서 한쪽이 말없이 연결만 붙들고 있으면 그 연결을 언제 끊을지 정해야 한다. 기본 상태로 두면 느린 서버가 있는 서비스에서 끊기기까지 연결이 오래 남아 곤란하다.

이 판단은 idle timeout 이 한다. 여기서 다룰 것은 load balancer attributes 로 바꾸는 값과 cross-zone load balancing 같은 설정, 대상 쪽에 두는 target group attributes 다.

#2핵심 질문

연결이 놀기만 하는 동안 언제 끊을지 어떻게 정하는가?

#3동작 예시

게임 세션이 10분은 말을 안 하는 구간이 있다. 이 로드 밸런서의 TCP 유휴 시간 초과를 그 길게 맞춰 둔다.

콘솔에서 로드 밸런서를 열고 속성 항목에서 그 값을 확인한다.

#4동작 과정

  1. 지정한다idle timeout 은 클라이언트와 대상 양쪽 모두 정해진 시간 동안 데이터를 보내지 않으면 그 연결을 닫는다. TCP 흐름의 기본값은 350초다.
  2. TLS 는 건드리지 않는다TLS listener 의 연결 유휴 시간 초과는 350초다. 더 길게 정한다면 대상의 ENI 연결 추적 유휴 시간(TcpEstablishedTimeout)이 NLB 유휴 시간 초과보다 크거나 같은지 확인한다. 어긋나면 대상 쪽이 먼저 연결 상태를 버린다.
  3. 나머지 값을 정한다load balancer attributes 로 cross-zone load balancing 을 켜 한 영역의 여유분을 다른 영역에서도 쓸 수 있게 하고, 대상 쪽 설정은 target group attributes 로 따로 지정한다.
  4. 확인해 볼 것로드 밸런서 속성 목록에서 유휴 시간 초과 값이 어떻게 표시되는지 확인한다.

6. Classic LB — 이전 세대06-01

Classic LB 의 구조

Classic Load Balancer 는 TCP/SSL 앞단에서 클라이언트 연결을 고정된 한 대의 프록시 서버로 받아들여 등록된 EC2 인스턴스로 나눠 보내는, AWS 의 가장 오래된 형태의 로드 밸런서입니다.

먼저 알아야 할 것 01-03

#1문제 상황

AWS 는 지금 세 가지 방식을 권한다(→ 01-03). 그 전에 쓰던 형태가 남았다.

Elastic Load Balancing 안의 Classic Load Balancer, 줄여 쓰면 LB, 는 그 이전 세대 유형이다. 앞단에서 클라이언트 연결을 받고, load balancer members 라 부르는 프록시 서버가 front end 로 받아 back end 의 EC2 인스턴스로 나눠 보낸다. 지금은 새Current 세대 유형으로 옮기라는 안내가 붙는다.

#2핵심 질문

이전 세대 로드 밸런서는 어떤 모양으로 트래픽을 나누는가?

#3동작 예시

같은 방식으로 만든 EC2 인스턴스 네 대 앞에 Classic Load Balancer 를 하나 둔다. 클라이언트는 그 로드 밸런서의 DNS 이름으로 접속하고, 인스턴스는 따로 알 필요가 없다.

인스턴스 하나가 상태 확인에서 탈락하면 그 인스턴스로는 새 요청이 가지 않는다.

#4동작 과정

  1. 만든다Elastic Load Balancing 이 Classic Load Balancer 를 두고, 앞에서부터 front end 를 받아들인다.
  2. 나눠 보낸다그 연결을 load balancer members 가 back end 에 등록된 EC2 인스턴스로 분배한다. 인스턴스가 여러 가용 영역에 나뉘어 있어도 앞에서 한 번에 받아 나눈다.
  3. 살핀다등록된 대상의 상태를 계속 확인해 정상인 곳으로만 보내고, 유입량이 변하면 로드 밸런서도 그에 맞춰 늘고 줄어든다.
  4. 확인해 볼 것로드 밸런서 상태 페이지에서 인스턴스 목록이 healthy 로 표시되는지 확인한다.

#5한 줄 요약

6. Classic LB — 이전 세대06-02

내부·외부 Classic LB

내부 Classic LB 는 VPC 안에서만 클라이언트가 접근할 수 있는 로드 밸런서이고, 외부 Classic LB 는 인터넷에 공개되어 퍼블릭 DNS 이름으로 접근할 수 있는 로드 밸런서입니다.

먼저 알아야 할 것 06-01

#1문제 상황

Classic Load Balancer 는 프록시 서버 한 대를 앞단에 두고 등록된 EC2 인스턴스로 나눠 보낸다(→ 06-01). 이때 이 인스턴스를 VPC 안에만 둘지, 인터넷에 노출할지 정해야 한다.

Elastic Load Balancing 의 내부 load balancer 는 노드에 프라이빗 IP만 붙고 외부 load balancer 는 퍼블릭 IP를 갖는다. 도메인 이름이 어느 쪽 주소로 풀리는지가 곧 차이다.

#2핵심 질문

같은 Classic Load Balancer 를 VPC 안에서만 볼지, 인터넷에 공개할지는 어떻게 고르는가?

#3동작 예시

웹 서버는 외부에, 데이터베이스는 VPC 안에 있다고 하자. 데이터베이스 앞단에 내부 Classic LB 를 세우고 웹 서버만 그 DNS 이름으로 접속하게 한다.

외부에서 그 이름으로 들어오는 요청은 VPC 접근 권한이 없어 막히고, 웹 서버에서 온 요청만 데이터베이스 쪽으로 전달된다.

#4동작 과정

  1. 배치를 고른다서브넷을 골라 로드 밸런서를 그 안에 만든다(→ 05-02). 서브넷이 프라이빗이면 내부, 퍼블릭이면 외부 internet-facing load balancer 가 된다.
  2. 주소를 정한다노드에 프라이빗 IP만 쓰거나 퍼블릭 IP를 함께 쓴다. 내부 것은 내부에서만, 외부 것은 인터넷에서 요청을 받는다.
  3. 이름을 걸어 둔다로드 밸런서의 DNS 이름이 그 IP로 풀리게 등록한다. 다층 구조라면 내부와 외부를 함께 쓸 수 있다.
  4. 확인해 볼 것로드 밸런서 설명에서 서브넷이 VPC 안 어디로 표시되는지 본다.

#5한 줄 요약

내부와 외부 Classic Load Balancer로드 밸런서를 VPC 안에만 둘지 인터넷에 공개할지를 정하는 배치 구분

6. Classic LB — 이전 세대06-03

스티키 세션과 커넥션 드레인

스티키 세션은 같은 클라이언트를 항상 같은 인스턴스로 보내 세션이 유지되게 하는 설정이고, 커넥션 드레인은 인스턴스를 등록에서 빼낼 때 기존 연결을 천천히 끊어 요청을 다 마친 뒤 종료하는 기능입니다.

먼저 알아야 할 것 06-01

#1문제 상황

인스턴스 여러 대에 요청이 흩어지면 사용자의 로그인 상태가 인스턴스마다 따로 생겨 세션이 매번 풀린다. 또 인스턴스를 빼낼 때 이미 붙어 있는 연결이 끊기면서 사용자에게 오류가 난다.

sticky sessions 와 connection draining 은 이 두 가지를 설정으로 다룬다.

#2핵심 질문

사용자 세션을 한 인스턴스에 붙여 두고, 인스턴스를 교체할 때 연결을 안전하게 정리하려면 어떻게 하는가?

#3동작 예시

장바구니 목록을 인스턴스 메모리에 보관하는 앱이라 세션이 풀리면 장바구니가 비워진다. 스티키 세션을 켜면 같은 브라우저는 항상 같은 인스턴스로 간다.

인스턴스를 교체하려 해 커넥션 드레인을 먼저 켠다. 기존 연결은 요청을 다 처리하고 나서 끊긴다.

#4동작 과정

  1. 같은 인스턴스로 묶는다sticky sessions 는 세션을 특정 인스턴스에 묶는 기능이다. 앱이 자체 세션 쿠키를 쓰면 그 기간을 따르고, 없으면 로드 밸런서가 AWSELB 라는 쿠키를 만들어 기간을 직접 정한다.
  2. 연결을 천천히 정리한다connection draining 은 등록을 해제할 때 남은 연결을 정해진 시간 동안 유지한 뒤 종료하는 설정이다. 시간 안에 새 요청은 더 이상 받지 않는다.
  3. 영역을 나눠 보내고 흔들림을 덜한다cross-zone load balancing 은 가용 영역을 가로질러 인스턴스를 고르게 나누는 설정이고, desync mitigation mode 는 고정 세션이 꼬였을 때 재분배를 조정하는 모드다.
  4. 확인해 볼 것스티키 세션을 켠 뒤 같은 브라우저로 여러 번 요청해 인스턴스가 안 바뀌는지 본다.

#5한 줄 요약

스티키 세션과 커넥션 드레인세션을 한 인스턴스에 묶어 두고 교체 시 연결을 끊지 않고 정리하는 설정

SSL 리스너는 암호화된 HTTPS 요청을 받아 SSL 로드 밸런서로 보내는 연결 설정으로, 리스너를 만들 때 AWS Certificate Manager 에서 발급받은 서버 인증서를 지정해야 합니다.

먼저 알아야 할 것 06-01

#1문제 상황

SSL 은 클라이언트와 로드 밸런서 사이의 통신을 암호화하는 규약이다. 이 암호화가 없으면 프록시 서버가 클라이언트에게 그대로 노출돼 통신을 도청당하기 쉽다. 받은 요청을 풀어 읽은 뒤 인스턴스로 보내려면, 중간에서 암호화를 풀 수 있는 앞단이 필요하다.

Classic Load Balancer 의 HTTPS listener 가 그 앞단 역할을 한다.

#2핵심 질문

클라이언트와 로드 밸런서, 로드 밸런서와 인스턴스 사이를 암호화하려면 무엇을 설정해야 하는가?

#3동작 예시

브라우저가 https 로 접속한다. 로드 밸런서가 미리 준비한 인증서를 꺼내 제시하고, 브라우저는 그 인증서가 등록된 도메인 소유임을 확인한다.

암호가 풀린 요청은 로드 밸런서 안쪽에서 다시 암호화되어 EC2 인스턴스로 전달된다.

#4동작 과정

  1. front-end listener 를 연다HTTPS listener 를 만들어 클라이언트 쪽 연결을 받는다. 이 자리에서 SSL server certificate 를 지정해야 한다.
  2. 암호화 수준을 고른다SSL negotiation policy 라는 이름 붙은 보안 정책으로 허용할 암호화 방식과 TLS 버전을 정한다. 미리 정해진 정책과 직접 만든 정책 중에서 고른다.
  3. 안쪽 연결을 잇는다로드 밸런서가 클라이언트 암호를 푼 뒤 인스턴스 쪽 연결은 정해진 cipher suite로 다시 암호화한다. 인스턴스의 클라이언트 인증은 따로 켤 수 있다.
  4. 확인해 볼 것리스너 목록에 SSL/HTTPS 가 붙은 리스너가 있고 인증서가 지정되어 있는지 본다.

#5한 줄 요약

SSL 리스너와 인증서프록시 앞에서 암호화를 풀고 다시 감싸며 통신을 보호하는 설정

7. Gateway LB — 장비를 앞단에 놓는다07-01

Gateway Load Balancer 로 시작하기

Gateway Load Balancer 는 방화벽 같은 가상 네트워크 장비를 클라이언트와 서버 사이에 배치해 모든 트래픽을 그 장비를 통과시키면서 장비들을 한 자리에 묶어 관리하고 확장할 수 있게 해 주는 부하 분산기입니다.

먼저 알아야 할 것 01-03

#1문제 상황

네 종류의 로드 밸런서 중 앞의 세 종류는 요청을 서버로 넘기는 곳에서 끝난다(→ 01-03). 각 서버 앞에 보안 장비를 따로 붙이면 장비 수가 늘고 관리도 복잡해진다.

Gateway Load Balancer 는 모든 트래픽을 장비 한 묶음으로 통과시키는 자리를 만든다.

#2핵심 질문

여러 대의 가상 네트워크 장비를 손대지 않고 한곳에 모아 모든 트래픽을 통과시키려면 어떻게 구성하는가?

#3동작 예시

서버마다 붙어 있던 방화벽을 모두 걷어내고 장비 인스턴스 몇 대만 한 타깃 그룹에 넣는다. 모든 서버로 가는 트래픽이 그 장비들을 거쳐 간다.

장비가 늘어나도 서버 쪽 설정은 건드리지 않는다.

#4동작 과정

  1. create a Gateway Load Balancer 를 준비한다콘솔에서 이름을 정하고 IP 주소 타입과 네트워크 정보를 넣는다.
  2. type gateway 로 만든다gateway load balancer 라는 타입을 골라 앞에서 받은 트래픽을 장비로 보내는 동작을 켠다.
  3. 리스너와 타깃 그룹을 정한다트래픽을 어느 타깃 그룹으로 보낼지 규칙으로 정한다. 이 로드 밸런서는 GENEVE 프로토콜을 쓰는 타깃 그룹만 받는다.
  4. 확인해 볼 것로드 밸런서 타입이 gateway 로 표시되고 리스너에 타깃 그룹이 연결돼 있는지 본다.

#5한 줄 요약

Gateway Load Balancer 로 시작하기가상 네트워크 장비를 한 자리에 모아 모든 트래픽을 통과시키는 구성

7단계 7. Gateway LB — 장비를 앞단에 놓는다

리스너는 Gateway Load Balancer 가 어떤 포트의 연결을 받을지 정하는 설정이고 타깃 그룹은 그 연결을 실제로 처리할 장비 인스턴스들의 집합으로, 리스너가 가리키는 등록 단위입니다.

먼저 알아야 할 것 07-01

#1문제 상황

Application Load Balancer 는 포트와 프로토콜을 정해야 리스너가 만들어진다(→ 03-01). Gateway Load Balancer 를 GWLB 라고 부르는데, 이 장치는 방화벽 같은 장비가 붙은 뒤에야 의미가 있어서 포트를 고르는 방식이 그대로 통하지 않는다(→ 07-01).

이 로드 밸런서의 리스너는 다르게 만들어진다.

#2핵심 질문

Gateway Load Balancer 의 리스너는 어떤 포트를 받고 어디로 보내는가?

#3동작 예시

장비 인스턴스들이 UDP 로 통신을 검사하는 배치를 한다. 로드 밸런서 리스너가 모든 패킷을 받아 그 장비 타깃 그룹으로 넘긴다.

장비를 다른 그룹으로 갈아끼우려면 리스너 규칙만 고치면 된다.

#4동작 과정

  1. 받는 범위를 정한다gateway listeners 는 모든 포트의 모든 IP 패킷을 받는다. 포트나 프로토콜을 직접 지정하지 않는다.

헬스체크와 속성

헬스체크는 주기마다 타깃 장비에 요청을 보내 장비가 정상적으로 트래픽을 처리할 수 있는지 확인해 unhealthy 로 판정된 타깃으로 트래픽을 보내지 않게 하는 검사이고, 속성은 그 검사 주기나 드레인 등 동작을 조절하는 설정값입니다.

먼저 알아야 할 것 07-02

#1문제 상황

Gateway Load Balancer 앞단에는 방화벽 장비를 여러 대 두는데(→ 07-01), 그중 한 대가 응답을 멈추면 트래픽이 그 장비로 계속 몰린다. 그래서 장비를 등록한 뒤에도 정상인지 계속 확인해 unhealthy 로 판정된 타깃으로는 보내지 않아야 한다. 이 확인 절차가 health checks for Gateway Load Balancer 이고, 검사 주기나 드레인 같은 설정값은 load balancer attributes와 target group attributes에서 바꾼다.

#2핵심 질문

장비가 멈췄을 때 그 장비로 트래픽을 보내지 않도록 어떻게 판단할까?

#3동작 예시

#4동작 과정

  1. 검사한다Gateway Load Balancer가 등록된 각 타깃에 주기적으로 요청을 보내 상태를 본다. 검사 뒤에는 그 요청에 쓰인 연결을 닫아 둔다.
  2. 빼고 다시 넣는다연속 실패가 UnhealthyThresholdCount를 넘으면 그 타깃을 서비스에서 빼고, 연속 성공이 HealthyThresholdCount를 넘으면 다시 넣는다. 이 기준값은 target group attributes로 고른다.
  3. 간격을 정한다검사 주기와 기다리는 시간 같은 값은 load balancer attributes에 들어 있다. 장비 교체 중 기존 연결을 천천히 끊는 드레인도 이 자리에서 켠다.
  4. 확인해 볼 것타깃 그룹 화면에서 각 장비의 상태가 healthy 로 표시되는지 본다.

  4. 확인해 볼 것브라우저로 해당 도메인에 접속해 인증서 창에서 도메인 이름이 일치하는지 본다.

먼저 알아야 할 것 08-01

#1문제 상황

사용자가 로그인해야 하는 서비스를 만들면 앱 안에 로그인 화면, 세션 관리, 소셜 로그인 연동을 직접 짜야 한다. 서버 인증서(→ 08-01)는 HTTPS 경로만 지켜 주지 사용자 신원은 확인하지 않는다. Amazon Cognito는 로그인 화면과 사용자 정보를 보관해 주는 Cognito 사용자 풀을 제공하는 서비스다. 이 authentication flow는 로드 밸런서가 사용자 인증을 대신 맡도록 만들어 준다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 사용자 풀을 잇는다리스너의 인증 동작인 authenticate users에 Amazon Cognito 사용자 풀을 지정한다. 소셜·기업 계정 로그인도 이 풀을 통해 같은 방식으로 받는다.
  2. 로그인 흐름을 연다OIDC 규격에 맞는 identity provider(IdP)를 쓰거나 Cognito를 쓴다. 각 제공자에 맞게 OIDC를 준비하고 리다이렉트 주소를 등록한다.
  3. 규칙을 정하고 넘긴다인증되지 않은 요청의 처리는 on-unauthenticated-request로 정하고, 결과는 사용자 클레임 인코딩과 서명 검증 방식에 맞춰 백엔드 헤더로 전달한다.
  4. 확인해 볼 것인증 없이 URL에 접속하면 로그인 화면으로 넘어가는지 본다.

#2핵심 질문

서버가 아니라 로드 밸런서가 JWT가 진짜인지 어떻게 판별할까?

#3동작 예시

앱이 ID 토큰을 붙여 API를 호출한다. 로드 밸런서가 서명을 확인하고 iss와 exp를 검사한 뒤 통과시킨다. 서명이 맞지 않거나 만료된 토큰이면 요청을 거절하고 응답으로 그 사실이 담긴 코드가 보인다.

#4동작 과정

  1. 준비한다토큰을 발급하는 identity provider(IdP)에 등록해 client ID와 client secret을 받고, JWKS가 있는 엔드포인트를 알려 준다.
  2. 검사한다verify a JSON Web Token 동작이 서명을 검증한다. 필수 클레임은 iss, 즉 발급자,와 exp, 즉 만료 시각이다. 있으면 nbf와 iat도 함께 검사한다.
  3. 클레임을 더 정한다추가로 검사할 클레임을 최대 10개까지 지정할 수 있다. 값 형식은 한 글자 하나, 공백으로 구분한 값, 문자열 배열 세 가지를 쓴다.
  4. 통과시킨다유효하면 로드 밸런서는 토큰을 그대로 붙여 백엔드로 넘기고, 아니면 거절한다.
  5. 확인해 볼 것만료된 토큰을 붙여 보낸 요청이 거절되는지 본다.

요청 헤더 — 앞에서 뒤에 무엇을 알려줄까

로드 밸런서가 백엔드로 넘길 때 X-Forwarded-For 같은 헤더를 덧붙여 원래 클라이언트의 IP와 프로토콜 정보가 숨겨지지 않게 전달하는 기능이다.

먼저 알아야 할 것 08-01

#1문제 상황

로드 밸런서가 클라이언트와 서버 사이에 들어가면 서버 입장에서는 모든 요청이 로드 밸런서에서 온 것처럼 보인다. 그러면 접속 로그의 IP가 전부 로드 밸런서 주소로 남고, 어떤 프로토콜로 들어왔는지도 알 수 없다. 이 header modification은 빠진 정보를 헤더로 다시 붙여 준다.

#2핵심 질문

로드 밸런서 뒤의 서버가 원래 클라이언트를 어떻게 알 수 있을까?

#3동작 예시

서버의 접속 로그를 보니 요청 출발지가 모두 로드 밸런서 주소로만 찍힌다. 그런데 애플리케이션 코드가 X-Forwarded-For 헤더를 읽으면 사용자 IP가 들어 있고, X-Forwarded-Port에서 HTTPS임을 알 수 있어 접근 기록을 제대로 남길 수 있게 된다.

#4동작 과정

  1. 헤더를 붙인다Application Load Balancer는 들어온 요청에 HTTP 헤더를 자동으로 더한다. 헤더는 이름과 값이 콜론으로 이어진 쌍이다.
  2. 출발지를 알려 준다X-Forwarded-For에는 클라이언트 IP가 담긴다. 로드 밸런서가 중간에 끼어 있어 원래 IP가 가려졌기 때문에 넣는다.
  3. 방향을 알려 준다X-Forwarded-For와 함께 X-Forwarded-For가 아닌 X-Forwarded-Proto로 들어온 프로토콜을, X-Forwarded-Port로 포트를 함께 넘긴다.
  4. 확인해 볼 것백엔드에서 받은 요청의 헤더를 찍어 X-Forwarded-For 값이 사용자 IP인지 확인한다.

어댑터와 리스너 속성

로드 밸런서 어댑터(Application·Network·Gateway)가 리스너와 로드 밸런서 자체의 동작을 바꾸는 설정값의 묶음으로, 어떤 방식을 쓸지와 얼마나 오래 기다릴지 같은 항목을 타입별로 따로 지정해 관리한다.

먼저 알아야 할 것 02-04

#1문제 상황

Application Load Balancer 를 만든 뒤에도 접속자가 끊기는 일이 있다. 파일 업로드 도중 연결이 닫히거나, 실수로 로드 밸런서가 삭제되기도 한다. 이런 값은 로드 밸런서마다 따로 건드려야 한다.

load balancer attributes는 이런 동작을 조절하는 이름 붙은 설정값 묶음이다. 타입별로 따로 지정하므로 로드 밸런서마다 원하는 대로 고를 수 있다.

#2핵심 질문

접속이 끊기는 상황을 막으려면 로드 밸런서의 어떤 값을 바꾸어야 할까?

#3동작 예시

대용량 파일을 올리는 서비스에서 업로드가 자주 중간에 끊긴다. 운영자는 로드 밸런서의 Attributes 탭에서 Connection idle timeout을 길게 잡는다.

그 뒤에는 같은 업로드도 끝까지 진행된다. 삭제는 실수로 막기 위해 Deletion protection을 켠다.

#4동작 과정

  1. 값을 고른다로드 밸런서의 Attributes 탭에서 고칠 이름을 고른다. connection idle timeout은 데이터가 오가지 않은 채 유지되는 연결을 닫기까지의 시간이다. 시간이 짧으면 긴 작업이 끊긴다.
  2. 방식을 정한다routing.http는 HTTP 처리 방식을 정하는 항목이다. 동작을 바꾸는 이름들이 타입별로 따로 있고, access logs로 접근 기록을 남길지 정할 수도 있다.
  3. 저장한다고른 값을 저장하면 새 연결부터 적용된다. 삭제를 막으려면 Deletion protection을 켜 두어야 한다.
  4. 확인해 볼 것Attributes 탭에 방금 고친 이름이 목록에 보이는지 확인한다.

#5한 줄 요약

#1문제 상황

NLB 어댑터의 프록시 프로토콜은 이 문제를 푼다. 헤더를 붙여 실제 클라이언트를 알려 준다.

#2핵심 질문

서버가 로드 밸런서 뒤에서 원래 클라이언트를 어떻게 알 수 있을까?

#3동작 예시

설정을 켜고 나니 각 기록에 실제 방문자 주소가 붙어 들어온다.

#4동작 과정

  1. 헤더를 붙인다load balancer attributes for NLB에서 proxy protocol을 켠다. 타깃은 헤더에서 client IP preservation, 즉 클라이언트 주소를 그대로 알아낼 수 있다.
  2. 나머지 값을 정한다같은 화면에서 유휴 연결 정리와 영역별 분산, 보조 IP 주소 같은 항목을 고른다. 이름은 Network Load Balancer용 목록에 따로 있다.
  3. 삭제를 막는다Deletion protection을 켜 두면 실수로 지우는 것을 막는다. 지우기 전에 이 값을 꺼야 한다.
  4. 확인해 볼 것NLB의 Attributes 탭에 Deletion protection 항목이 보이는지 확인한다.

#1문제 상황

로드 밸런서는 여러 가용 영역에 흩어져 있다. 그런데 특정 가용 영역 하나에 장애가 나면 그 영역의 자원을 걷어내지 않는 한 일부 요청이 계속 실패한다.

zonal shift는 이걸 한 번의 설정으로 처리한다.

#2핵심 질문

가용 영역 하나의 장애가 사용자 요청 실패로 이어지지 않게 하려면 어떻게 해야 할까?

#3동작 예시

한 가용 영역의 자원에 문제가 생겼다. 운영자는 로드 밸런서의 Attributes 탭에서 가용 영역 라우팅 설정을 켠 뒤 zonal shift를 시작한다.

그 뒤 요청이 나머지 영역의 대상으로만 전달되는지 본다.

#4동작 과정

  1. 켜 둔다Attributes 탭의 가용 영역 라우팅 설정에서 enable zonal shift를 켠다. CLI로는 zonal_shift.config.enabled 속성을 true로 둔다.
  2. 시작한다start zonal shift로 그 영역으로 향하던 트래픽을 나머지 영역으로 옮긴다. shift traffic가 멈춘 영역의 요청만 대상이 된다.
  3. 되돌린다문제가 끝나면 update and cancel로 갱신하고 취소해 원래 배치로 되돌린다.
  4. 확인해 볼 것로드 밸런서에 zonal shift가 시작된 상태로 표시되는지 확인한다.

#5한 줄 요약

zonal shift는 한 가용 영역의 트래픽을 나머지 영역으로 밀어내는 AWS 로드 밸런서 기능입니다.

먼저 알아야 할 것 10-01

#1문제 상황

서비스가 느려졌다고 느끼는 것과 어디가 느린지 아는 것은 다르다. 요청이 얼마나 들어오고, 연결이 얼마나 쌓였는지 숫자로 남지 않으면 판단할 근거가 없다.

#2핵심 질문

로드 밸런서의 트래픽 상태를 숫자로 계속 확인하려면 어디를 봐야 할까?

#3동작 예시

운영자가 CloudWatch 콘솔에서 로드 밸런서 지표를 시간별로 본다. ActiveConnectionCount 그래프가 예상보다 높게 붙어 있다.

TargetResponseTime 그래프까지 같이 보면 타깃이 느려졌다는 사실을 확인한다.

#4동작 과정

  1. 보낸다로드 밸런서는 요청이 흐를 때 CloudWatch로 지표를 보낸다. 지표란 시간에 따라 나열되는 수치 묶음이다.
  2. 항목을 본다ActiveConnectionCount는 활성 연결 수, NewConnectionCount는 새로 열린 연결 수를 뜻한다. ProcessedBytes는 처리한 바이트 수다.
  3. 지표를 정한다TargetResponseTime은 타깃이 응답까지 걸린 시간이다. 지표를 지정하면 CloudWatch 알람이 지정 범위를 벗어날 때 알림을 보낸다.
  4. 확인해 볼 것CloudWatch의 해당 리소스 지표 목록에 로드 밸런서 지표가 시간순으로 나타나는지 확인한다.

요청 추적과 CloudTrail

먼저 알아야 할 것 10-01

#1문제 상황

요청이 로드 밸런서를 지나 어디까지 갔는지 알기 어렵다. 문제는 로드 밸런서 앞뒤 어느 지점에 있는지도 모른다(→ 01-02).

request tracing 은 로드 밸런서가 각 요청에 X-Amzn-Trace-Id 헤더를 붙이는 기능이다. 헤더 형식은 Root=version-time-id 이고 version 은 1, time 은 초 단위 8자리, id 는 24자리 16진수다. 로드 밸런서 뒤의 다른 서비스도 같은 헤더에 자기 항목을 덧붙일 수 있다. 설정 변경 이력은 CloudTrail 기록으로 남는다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 추적을 켠다request tracing 을 켜면 들어온 요청마다 로드 밸런서가 X-Amzn-Trace-Id 헤더를 만들어 타깃으로 넘긴다. 뒤쪽 서비스도 필드를 덧붙이고 로드 밸런서는 보존한다.
  2. 값을 찾는다접근 로그를 켜 두면 헤더 내용이 함께 기록된다. 같은 id 를 가진 항목들을 맞춰 어디를 지나왔는지 본다.
  3. 변경 이력을 확인한다누가 언제 API calls 로 무엇을 바꿨는지는 CloudTrail 기록에서 확인한다. monitoring 용 기록과 설정 변경 기록이 나뉘어 있다.
  4. 확인해 볼 것타깃 쪽에서 받는 요청에 X-Amzn-Trace-Id 헤더가 붙어 있는지 확인한다.

  3. CLB 는 지표로 본다Classic Load Balancer 는 CloudWatch 지표 중심으로 상태를 본다.
  4. 확인해 볼 것NLB 의 Integrations 탭에 로깅 항목이 보이는지, TLS 리스너에서만 로그가 남는지 확인한다.

11. 가용성과 운영 — 흔들리지 않게, 끝까지 쓰게11-01

zonal shift 를 켜고 옮기기

zonal shift 는 가용 영역 한 곳의 장애가 전체로 번지지 않도록 리소스를 그 영역에서 밀어내는 기능으로, 활성화하고·상태를 갱신하고·되돌리는 세 가지 동작으로 관리한다.

먼저 알아야 할 것 09-04

#1문제 상황

한 가용 영역(→ 05-02)에 문제가 생기면 그 영역으로 향하던 요청만 밀려난다. zonal shift 는 이 영역 밖으로 트래픽을 밀어내는 기능이다(→ 09-04). AWS 의 Availability Zone Routing for Catalyst 라는 재해석 설정이 이 기능을 받친다.

관리 동작은 enable zonal shift, update a zonal shift, cancel zonal shift 세 가지다. 콘솔의 Attributes 탭에서 켤 수 있고, AWS CLI 로는 modify-load-balancer-attributes 명령에 zonal_shift.config.enabled 속성을 true 로 주면 된다.

#3동작 예시

#4동작 과정

  1. 켜고로드 밬런서 Attributes 탭의 Availability Zone routing configuration 에서 Enable 을 고른다. zonal shift status 로 켜졌는지 확인한다.
  2. 갱신한다update a zonal shift 로 대상 영역이나 설정을 바꿔 준다. CLI 와 CloudFormation 에서도 같은 상태를 지정할 수 있다.
  3. 되돌린다cancel zonal shift 로 이동을 취소해 원래 배치로 돌아간다.
  4. 확인해 볼 것로드 밸런서 속성 목록에 zonal_shift.config.enabled 가 어떤 값으로 표시되는지 본다.

capacity unit reservation — 자리를 미리 잡아두기

capacity unit reservation 은 Application Load Balancer 가 쓸 처리 용량(LCU)을 리전별로 미리 예약해 두는 것으로, 돌발 트래픽에 새 자리가 배정되기를 기다리지 않고 바로 늘어난다.

먼저 알아야 할 것 11-01

→ 11-03 참조

#1문제 상황

Application Load Balancer 는 감지한 부하에 맞춰 자동으로 늘고 줄어든다(→ 01-01). minimum capacity 를 정하면 그 아래로 내리지 않지만, 자리 배정 자체를 미리 잡아두지는 않는다.

capacity unit reservation 은 리전별로 사용할 LCU를 미리 예약해 두는 기능이다. 예고 없는 큰 트래픽이나 단기적 변동이 잦은 부하, 정해진 시각에 서비스를 올리거나 옮겨 시작해야 할 때, 그리고 로드 밸런서 사이에서 부하를 옮길 때 쓰면 새 자리가 배정되기를 기다리지 않는다.

#2핵심 질문

트래픽이 갑자기 몰릴 때 자리를 기다리지 않고 늘리려면 어떻게 해야 하는가?

#3동작 예시

행사 시작 시각을 정해 둔 팀이 capacity unit reservation 으로 자리를 잡아둔다. 예약 상태를 조회하면 예약된 최소 capacity units 가 몇 개인지 보인다.

#4동작 과정

  1. 예약한다request a reservation 으로 리전에 확보할 최소 용량을 지정해 예약한다.
  2. 자동 확장과 함께 쓴다로드 밸런서는 받은 트래픽에 따라 계속 오르내리지만 예약한 minimum capacity units 아래로는 내려가지 않는다.
  3. 예약을 살핀다monitor reservations 로 예약 상태와 양을 확인하며 남는 자리를 판단한다.
  4. 확인해 볼 것로드 밸런서 속성에서 예약된 최소 capacity units 값이 표시되는지 본다.

NLB 와 GWLB 의 예약

Network Load Balancer 와 Gateway Load Balancer 도 각각의 처리 단위(NLCU·GWLCU)를 같은 방식으로 리전에 미리 예약해 두어 용량 확보 시점을 직접 정한다.

먼저 알아야 할 것 11-02

#1문제 상황

Network Load Balancer 는 트래픽을 재고 없이 늘리고 줄인다. 그래서 갑작스러운 유행이나 서비스 이전 시각에 용량이 늦게 따라온다.

capacity unit reservation for NLB 는 처리 단위 NLCU 를 미리 확보하는 기능이다. reservation for GWLB 도 같은 방식으로 GWLB 에서 쓰인다(→ 11-02).

#2핵심 질문

트래픽 급증 전에 부하 분산기 용량을 미리 확보하려면?

#3동작 예시

새벽 행사 개설을 앞두고 팀이 Network Load Balancer 의 예약 처리 단위를 늘려 둔다. 행사 직후 접속자가 몰려도 기다리는 시간이 없다.

#4동작 과정

  1. 예약할 단위를 고른다리전에 확보할 처리 단위 수를 정한다. Network Load Balancer 는 NLCU, Gateway Load Balancer 는 GWLCU 를 쓴다.
  2. 예약을 적용한다자동 확장이 Reflection 되게 최소 용량을 함께 정해 둘 수도 있다.
  3. 예약 상태를 본다monitor capacity unit reservation 는 예약이 실제로 얼마나 쓰였는지 확인하는 기능이다.
  4. 확인해 볼 것로드 밸런서 콘솔에서 예약된 처리 단위 수와 이름이 표시되는지 본다.

한계와 할당량

한계와 할당량은 리소스 종류별로 한 계정·한 리전이 한 번에 만들 수 있는 로드 밸런서·리스너·타깃 그룹 등의 수와 크기에 대한 상한으로, 이 범위를 넘으려면 할당량 증가를 요청해야 한다.

먼저 알아야 할 것 02-06

#1문제 상황

한 리전에서 Application Load Balancer 를 같은 이름으로 몇 개 더 만들려고 하면 거절당한다. 만들 수 있는 개수와 크기에는 상한이 있기 때문이다.

load balancer limits 는 리소스 종류별 상한이고, quotas 는 그 상한을 관리하는 이름이다. limits for your load balancers 는 종류별로 어디까지 가능한지 적어 둔 표이고 target group limits 는 대상 그룹 쪽 상한이다. 이 한계를 넘으려면 증가를 요청해야 하며, 늘릴 수 없는 항목도 있다.

#2핵심 질문

한 리전에서 로드 밸런서를 몇 개까지 만들 수 있는가?

#3동작 예시

팀이 리전에 로드 밸런서를 한꺼번에 60개 만들려는 계획을 세운다. 50개까지만 가능하다는 상한을 알고 대상 그룹을 늘리는 방향으로 계획을 바꾼다.

#4동작 과정

  1. 종류를 나눠 본다로드 밸런서, 대상 그룹, 규칙, 신뢰 저장소, 인증서, HTTP 헤더, Load Balancer Capacity Units 로 상한이 따로 있다.
  2. 숫자를 확인한다Service Quotas 콘솔의 Elastic Load Balancing 항목에서 현재 값을 본다. CLI 의 describe-account-limits 로도 같다.
  3. 올라간 값을 요청한다Service Quotas 에서 증가를 요청한다. 늘릴 수 없는 상한도 따로 표시된다.
  4. 확인해 볼 것콘솔의 한계 목록에서 항목 이름과 현재 사용량이 함께 보이는지 본다.

IAM 과 서비스 연결 역할

IAM 과 서비스 연결 역할은 Elastic Load Balancing 이 사용자를 대신해 리소스를 만들 때 쓸 권한을(aws-service-role 형태의)역할로 위임해, 계정 관리자 권한을 직접 쓰지 않게 하는 장치다.

먼저 알아야 할 것 08-01

#1문제 상황

로드 밸런서를 만들면 보안 그룹이나 태그 같은 옆자리 리소스까지 함께 생긴다. 그 권한을 사용자에게 직접 주면 관리 범위가 넓어진다.

Identity and access management(IAM)는 이런 권한을 누가 가지는지 정하는 체계이고(→ 11-04), service-linked role 은 Elastic Load Balancing 이 사용자를 대신해 쓸 권한을 넘겨 받은 이름이다. role 이름은 AWSServiceRoleForElasticLoadBalancing 이고 AWS managed policies 의 AWSElasticLoadBalancingServiceRolePolicy 로 권한이 묶여 있다. 이 역할을 만들려면 대응하는 API permissions 가 있어야 하지만 역할 자체는 사용자가 직접 만들지 않는다.

#2핵심 질문

Elastic Load Balancing 이 내 계정 권한을 어떻게 쓰면서도 남에게 열지 않을까?

#3동작 예시

실무자가 콘솔에서 로드 밸런서를 만든다. 콘솔에는 이 동작을 허용하는 화면이 없는 계정이어서 역할을 먼저 만들어 준 뒤 다시 시도한다.

#4동작 과정

  1. 권한 체계를 정한다IAM 으로 어떤 요청이 허용되는지 관리한다(→ 11-04).
  2. 역할이 권한을 맡는다service-linked role 이 elasticloadbalancing.amazonaws.com 만 믿도록 묶여 다른 서비스를 대신 호출한다.
  3. 정책을 확인한다AWS managed policies 에서 AWSElasticLoadBalancingServiceRolePolicy 의 권한 내용을 본다.
  4. 확인해 볼 것IAM 콘솔에서 AWSServiceRoleForElasticLoadBalancing 역할이 존재하는지 본다.

데이터 보호와 VPC 엔드포인트

VPC 엔드포인트를 쓰면 로드 밸런서가 인터넷을 거치지 않고 VPC 안에서만 API·데이터를 주고받아 데이터가 외부로 새지 않게 하고, 전송 구간은 암호화로 보호한다.

먼저 알아야 할 것 11-05

#1문제 상황

VPC 안에서 로드 밸런서를 만들려면 API 호출이 인터넷으로 나가야 한다. 인터넷 게이트웨이나 NAT 게이트웨이를 붙여야 하며, 관리자가 그 구간을 지켜야 한다.

data protection 는 다루어야 할 데이터가 어디로 새지 않게 하느냐의 문제다. VPC endpoints 는 VPC 안에서 AWS 서비스로 곧바로 붙는 사설 주소 지점이고, 이 기능은 AWS PrivateLink 로 제공된다. VPC endpoint policy 로 그 지점에서 허용할 대상을 좁히고, encryption in transit 로 전송 구간을 암호화한다.

#2핵심 질문

인터넷 게이트웨이 없이 VPC 안에서 로드 밸런서 API를 부를 수 있는가?

#3동작 예시

망이 분리된 환경의 서버가 로드 밸런서를 조회한다. 사설 주소로 열린 엔드포인트를 통해 API 버전 2015-12-01 과 2012-06-01 을 부른다. 인터넷으로 나가는 구간이 없다.

#4동작 과정

  1. 엔드포인트를 만든다Elastic Load Balancing 용 interface endpoint 를 생성해 사설 연결을 연다. AWS PrivateLink 가 이 연결을 받친다.
  2. 정책으로 범위를 정한다VPC endpoint policy 를 붙여 어디로만 보낼지 정한다.
  3. 전송 구간을 지킨다encryption in transit 를 적용해 VPC 안에서 오가는 내용을 암호로 지킨다.
  4. 확인해 볼 것VPC 콘솔의 엔드포인트 목록에 Elastic Load Balancing 항목이 사설 주소로 보이는지 본다.
