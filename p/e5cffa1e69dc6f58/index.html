관계형 데이터베이스는 서버를 직접 준비하고 스키마를 먼저 설계해야 하며, 사용자 수가 늘면 늘어난 만큼 운영 부담도 함께 따라온다.

Amazon DynamoDB는 완전 관리형 분산 NoSQL 데이터베이스로, 서버 관리를 맡기고 key-value 형태의 데이터를 어느 규모에서나 일관된 처리 속도로 저장하고 검색하게 해 준다.

#2핵심 질문

서버를 직접 준비하지 않고도 어느 규모에서나 일관된 속도로 데이터를 저장하고 찾을 수 있는가?

#3동작 예시

쇼핑몰의 장바구니 기능을 만들 때 장바구니 항목을 DynamoDB에 저장한다. 사용자가 10만이든 1천만이든 같은 코드로 항목을 넣고 빼고 읽는다.

사용자가 늘어나도 서버를 늘리는 작업을 하지 않아도 응답이 일정한 수준으로 유지된다.

#4동작 과정

  1. 데이터를 저장한다key-value 형태로 항목을 넣어 두고 필요할 때 키로 찾아 온다. 서버와 스케일링은 서비스가 맡는다.
  2. 성능을 유지한다어떤 규모에서도 일관된 밀리초 단위 응답을 목표로 설계되었다. 이용자가 늘면 데이터와 처리 능력이 함께 늘어난다.
  3. 확인해 볼 것AWS 콘솔의 DynamoDB 화면에서 테이블을 하나 만들고 항목을 넣어 다시 읽어 본다.

DynamoDB 서비스를 이루는 여러 부분으로, 테이블·항목(item)·속성(attribute)·파티션 키·정렬 키 같은 데이터 모델 요소와 이를 다루는 읽기·쓰기·관리 API·보조 인덱스·Streams·백업 복구 기능 등을 아우르는 상위 개념.

먼저 알아야 할 것 01-01

#1문제 상황

DynamoDB의 Core components는 table 안에 item이 들어가고, item은 attribute의 모음이며, primary key가 각 item을 유일하게 구분하는 구조다.

#2핵심 질문

데이터를 담는 덩어리와 그것을 유일하게 부르는 키는 어떻게 구성되는가?

#3동작 예시

사람들의 연락처를 담은 People 테이블을 만든다. 각 행이 하나의 item이고, 행 안의 이름·전화번호·이메일이 attribute다.

같은 이름의 사람이 있을 수 있어 기본 키로 회원번호를 넣어 item을 구분한다.

#4동작 과정

  1. 테이블을 만든다table은 데이터를 모으는 가장 큰 단위다. People 같은 이름표를 정하고 기본 키를 지정한다.
  2. 항목을 넣는다item은 테이블 안의 한 줄이고, attribute는 그 줄의 이름-값 하나다. 값의 종류는 다음 항목에서 다룬다.
  3. 키로 구분한다partition key와 sort key를 합친 primary key가 item을 유일하게 가리킨다. 두 키의 쓰임은 뒤 항목에서 나눠 본다.
  4. 확인해 볼 것테이블을 열고 몇 개의 item을 넣은 뒤 항목 수와 기본 키가 보인다.

DynamoDB API

네트워크 요청으로 DynamoDB에 보내는 동작들의 규격으로, 데이터를 다루는 읽기·쓰기 API와 테이블 생성·삭제·수정 같은 관리는 API 유형으로 나뉘고 각각의 입력·출력 형식이 정해져 있다.

#1문제 상황

DynamoDB에 테이블을 새로 만들고, 설정을 바꿔 보고, 데이터를 넣고 빼려면 각각의 동작을 어떤 순서로 부르는지 알아야 한다.

DynamoDB API는 이 동작들의 입출력 형식을 정해 둔 규격이다. 요청과 응답은 JSON 형식이며 두 종류로 나뉜다.

#2핵심 질문

테이블을 관리하는 동작과 항목을 다루는 동작을 각각 어떤 API로 부르는가?

#3동작 예시

새 서비스의 테이블을 만들려고 CreateTable을 부른다. 파티션 키와 정렬 키, 처리량 설정, 보조 색인과 Streams 사용 여부를 함께 넣는다.

목록을 보려면 ListTables, 현재 설정을 보려면 DescribeTable을 부르고 결과를 JSON으로 받는다.

#4동작 과정

  1. control plane을 부른다테이블과 색인, Streams처럼 테이블에 딸린 대상을 만들고 고치는 동작이다. CreateTable, DescribeTable, ListTables, UpdateTable, DeleteTable가 여기에 든다.
  2. data plane을 부른다만든 테이블에서 항목을 읽고 쓰는 동작이다. 읽기와 쓰기 API로 나뉘며 각각 요청과 응답이 정해져 있다.
  3. 함께 다루는 대상DynamoDB Streams와 Transactions도 이 API 체계 안에서 다룬다.
  4. 확인해 볼 것API 문서의 조작 목록에서 control plane과 data plane 항목이 따로 나뉘어 있는 것을 본다.

데이터 타입과 이름 규칙

DynamoDB이 저장하는 값의 종류(String, Number, Binary, Boolean, Null, Document, Set 등)와, 테이블·속성 이름을 지을 때 지켜야 하는 길이·문자·예약어 제약 규칙.

먼저 알아야 할 것 01-02

#1문제 상황

이전 항목의 attribute(항목 안의 이름-값)마다 저장할 수 있는 값의 종류가 다르고, 이름 짓기에도 지켜야 할 제약이 있다.

Supported data types는 그 값의 종류를 정하고, naming rules는 테이블·속성·인덱스 이름의 길이와 사용할 문자를 정한다.

#2핵심 질문

어떤 값의 종류를 저장할 수 있고 이름에는 어떤 규칙을 지켜야 하는가?

#3동작 예시

사람 정보를 담는 테이블에 이름을 String, 나이를 Number, 구매 목록을 List로 저장한다. 속성 이름은 통틀어 몇 글자로 짧게 지어 둔다.

한 사람이 가진 태그는 Set으로 넣어 중복을 없앤다.

#4동작 과정

  1. 값의 종류를 고른다String, Number, Binary 같은 기본 타입이 있다. Map은 이름-값 쌍의 묶음, List는 순서 있는 값의 목록, Set은 중복 없는 값의 모음이다.
  2. 이름을 짓는다모든 이름은 UTF-8로 인코딩하고 대소문자를 구분한다. 테이블과 인덱스 이름은 3자에서 255자 사이여야 하고 영문자, 숫자, 밑줄, 하이픈, 점만 쓸 수 있다.
  3. 이름을 짧게 유지한다속성 이름은 한 글자 이상이어야 하고 64 KB를 넘지 못한다. 짧게 지면 읽기 비용을 줄인다.
  4. 확인해 볼 것테이블 만들기에 넣은 이름이 대소문자를 바꾸어 서로 다른 이름으로 취급되는 것을 본다.

파티션과 데이터 분산

테이블의 모든 데이터가 파티션 키 값에 따라 여러 파티션으로 나뉘어 저장되는 구조로, 같은 파티션 키 값을 가진 항목들은 파티션 안에서 정렬 키로 정렬되어 함께 배치된다.

먼저 알아야 할 것 01-04

#1문제 상황

큰 테이블의 데이터를 몇 군데에 나눠 두어야 읽기와 쓰기가 빠르고, 한 곳에 몰리면 느려지는 문제가 생긴다.

Partitions and data distribution은 파티션 키 값을 해시(hash)해 그 결과에 따라 데이터를 나란히 배치한다. 파티션은 SSD로 만들고 리전 안 여러 가용 영역에 복제한다.

#2핵심 질문

테이블의 데이터를 어떻게 나눠 어디에 배치하는가?

#3동작 예시

주문 테이블을 만들면서 주문번호를 파티션 키로 정한다. 주문번호를 해시(hash)한 값이 다른 파티션으로 갈라져 저장된다.

주문이 몰리는 날에도 파티션 키가 잘 나뉘면 여러 파티션에 읽기와 쓰기가 나뉜다.

#4동작 과정

  1. 파티션을 나눈다physical partition은 테이블의 저장 공간 한 단위다. 파티션 키 값을 해시(hash)해 어느 파티션에 넣을지 정한다.
  2. 용량을 늘린다지정한 처리량을 버티기 어려워지거나 파티션이 가득 차면 DynamoDB가 뒤에서 자동으로 파티션을 더 만든다.
  3. 같은 키를 모은다파티션 키 값이 같은 항목들은 한 파티션 안에 함께 들어간다.
  4. 확인해 볼 것DescribeTable 결과에서 파티션 수와 파티션당 저장 크기를 본다.

#1문제 상황

DynamoDB table classes는 저장할 데이터의 성격에 따라 계층을 고르게 한다. 모든 테이블은 하나의 테이블 클래스에 붙는다.

#2핵심 질문

데이터의 보관 기간과 접근 빈도에 맞춰 어떤 저장 계층을 고르는가?

#3동작 예시

신입 사원 첫날 이후 다시 보지 않는 사원 정보를 담은 테이블을 만든다. 오래된 주문 이력과 애플리케이션 로그도 여기에 해당한다.

접근이 드문 데이터에는 DynamoDB Standard-Infrequent Access 계층을 선택한다.

#4동작 과정

  1. 계층을 고른다기본은 DynamoDB Standard이며 대부분의 workloads에 권장된다. 저장 비용이 큰 데이터에는 DynamoDB Standard-IA 계층이 맞는다.
  2. 색인도 함께 따라간다테이블에 붙은 보조 색인은 테이블과 같은 테이블 클래스를 쓴다.
  3. 비용 구조를 본다테이블 클래스에 따라 데이터 저장 비용과 읽기·쓰기 요청 비용이 달라진다.
  4. 확인해 볼 것테이블 콘솔에서 테이블 클래스가 어떤 값으로 표시되는지 본다.

관계형인가 NoSQL 인가

DynamoDB 는 정해진 스키마 없이 파티션 키와 정렬 키만 정해 두면 나머지 속성은 자유롭게 넣을 수 있어, 스키마를 먼저 설계해야 하는 관계형 데이터베이스와 달리 읽기·쓰기 성능을 예측 가능하게 해 주는 NoSQL 저장소다.

먼저 알아야 할 것 01-01

#1문제 상황

관계형 데이터베이스는 정해진 스키마를 먼저 짜고 그 틀에 맞춰 행을 넣는다(→ 01-01). 확장에 맞춰 서버를 늘리는 방식이라 사용자가 늘면 직접 대비해야 한다.

Amazon DynamoDB 는 파티션 키와 정렬 키만 정해 두면 나머지 속성은 항목마다 자유롭게 넣는다. 이 NoSQL 방식에서는 스키마가 없어도 읽기·쓰기 성능을 예측할 수 있고, 데이터가 늘어나면 처리량을 늘리는 쪽으로 간다. 대신 여러 테이블을 한 번에 묶는 joins 는 없으므로 필요한 데이터를 한곳에 모아 둔다. 읽을 때 필요한 형태를 정해 주는 schema on read 도 함께 쓴다.

#2핵심 질문

스키마를 미리 정하지 않고도 데이터가 늘어나는 애플리케이션을 어떻게 저장할까?

#3동작 예시

처음 사용자도 데이터도 적은 게임을 DynamoDB 에 넣는다. 성공해서 사용자가 늘고 하루 새 데이터가 테라바이트 단위로 생겨도 테이블은 키 조합만으로 읽기와 쓰기를 처리한다.

질의가 나중에 달라지면 보조 색인을 추가하거나(→ 02-04) 데이터를 한 항목에 함께 저장해 query flexibility 를 얻는다.

#4동작 과정

  1. 키만 정한다파티션 키와 정렬 키를 골라 넣을 자리를 정한다. 나머지 속성은 항목마다 달라도 된다.
  2. 함께 넣어 둔다한 번에 보여 줄 데이터를 같은 항목에 모아 저장한다. joins 로 합치지 않아도 질의 한 번으로 답이 나온다.
  3. 쓰고 나서 형태를 정한다읽는 방식이 정해지면 그에 맞춰 schema on read 형태로 데이터를 배치한다.
  4. 확인해 볼 것콘솔에서 한 테이블의 항목 화면에 서로 다른 속성이 섞여 저장된 것을 확인한다.

#5한 줄 요약

NoSQL 저장소스키마를 미리 정하지 않고 데이터 크기에 맞춰 읽기·쓰기를 예측 가능하게 유지하는 것

#1문제 상황

관계형 데이터베이스는 CREATE TABLE 문장으로 열과 데이터 타입을 전부 미리 정해야 한다(→ 02-01). 속성이 하나 늘 때마다 스키마를 고쳐야 한다.

DynamoDB의 Creating a table은 파티션 키와 정렬 키로 이루어진 primary key만 먼저 정하고 나머지 속성은 쓰 때마다 넣게 한다. 만들어진 테이블은 이름 붙은 저장 단위로 남고, describe table로 정보를 본다.

#2핵심 질문

DynamoDB 테이블을 만들고 현재 상태를 확인하려면 어떻게 하나?

#3동작 예시

음원 서비스의 Music 테이블을 만든다. primary key로 Artist와 SongTitle을 지정하고 쓰기·읽기 용량 모드를 고른다.

콘솔에서 describe table을 실행해 파티션 수와 테이블 크기, 붙은 색인이 무엇인지 확인한다.

#4동작 과정

  1. 키를 정해 테이블을 만든다파티션 키와 정렬 키를 primary key로 지정해 Creating a table을 수행한다. 다른 속성 이름과 데이터 타입은 미리 정하지 않는다(→ 02-01).
  2. 읽기와 쓰기 모드를 고른다용량 모드를 붙여 테이블의 사용 설정을 고정한다. 모드별 차이는 뒤 항목에서 다룬다.
  3. 상태를 조회한다Getting information about a table, 즉 describe table로 파티션 수·크기·색인 목록을 읽는다.
  4. 확인해 볼 것콘솔의 테이블 목록에서 만든 테이블을 고르고 항목 수와 저장 크기가 표시되는지 확인한다.

#5한 줄 요약

테이블을 만들고 정보를 본다는 것은 키와 용량 설정만으로 저장 단위를 세우고 describe table로 상태를 읽는 것입니다.

데이터를 쓰고 읽는다

PutItem 으로 항목 전체를 저장하고 GetItem·Query·Scan 으로 되돌리며, 기본 읽기는 약간 오래된 값을 볼 수 있어 필요할 때 ConsistentRead 로 최신 값을 보장한다.

먼저 알아야 할 것 02-02

→ 02-02 참조

#1문제 상황

SQL에서는 행을 열 순서대로 가진 INSERT 문으로 넣고 SELECT로 꺼낸다(→ 02-01). DynamoDB에는 열이 없고 attribute를 가진 item이 들어간다.

그래서 Writing data to a table는 put item 한 번으로 항목 전체를 저장하고, Reading data from a table은 get item 같은 primary key lookup으로 되돌린다.

#2핵심 질문

항목을 테이블에 넣고 다시 꺼내려면 어떤 API를 쓰는가?

#3동작 예시

배우가 'No One You Know', 곡명이 'Call Me Today'인 항목을 put item으로 넣는다.

get item으로 primary key인 Artist와 SongTitle을 넘기면 앨범·연도·가격 속성이 함께 돌아온다.

#4동작 과정

  1. 항목을 저장한다put item으로 키와 속성 묶음을 통째로 보낸다. 같은 키로 다시 보내면 항목이 새로써진다.
  2. 키로 되돌린다Reading data from a table, 즉 get item에 primary key를 주면 그 항목만 찾아온다. 키를 모르면 scan으로 전체를 훑어야 한다(→ 03-04).
  3. 최신값을 보장한다ConsistentRead를 켜면 읽은 리전에서 방금 쓴 값을 본다. 끄면 약간 오래된 값이 나올 수 있다(→ 03-01).
  4. 확인해 볼 것콘솔의 항목 탭에서 방금 넣은 항목의 속성이 목록에 보이는지 확인한다.

#5한 줄 요약

데이터를 쓰고 읽는다는 것은 put item으로 저장하고 get item으로 키 지정 조회해 되돌리는 것입니다.

2. 관계형과 무엇이 다른가02-04

색인 관리

테이블의 기본 파티션 키·정렬 키 조합으로 못 찾는 질의를 위해, GSI(다른 파티션·정렬 키 조합) 와 LSI(같은 파티션 키에 정렬 키 하나 더) 같은 보조 색인을 붙여 조회 패턴을 늘린다.

먼저 알아야 할 것 02-03

#1문제 상황

기본 파티션 키와 정렬 키 조합으로 안 잡히는 질의가 생긴다. SQL처럼 색인을 여러 개 두면 되지만(→ 02-01), 쓰기가 일어날 때 모든 색인을 함께 고쳐야 한다.

그래서 Managing indexes를 통해 필요한 것만 secondary index로 붙인다. global secondary index는 다른 파티션·정렬 키 조합을, local secondary index는 같은 파티션 키에 정렬 키 하나를 더 둔다.

#2핵심 질문

기본 키로 못 찾는 질의를 어떻게 처리할까?

#3동작 예시

장르로 음악을 찾는 기능이 필요하다. Genre를 파티션 키로 둔 global secondary index를 테이블에 추가한다.

이제 장르가 같은 항목들을 그 인덱스로 묶어 읽을 수 있다.

#4동작 과정

  1. 필요한 색인을 고른다조회 패턴에 맞는 secondary index만 만든다. 쓰기가 많은 테이블일수록 색인 하나마다 쓰기 비용이 붙는다.
  2. GSI를 붙인다global secondary index는 다른 파티션 키와 정렬 키 조합을 쓰므로 다른 기준으로 묶어 본다.
  3. LSI를 붙인다local secondary index는 파티션 키를 그대로 두고 정렬 키만 하나 더 쓰는 구조다. 파티션별로 묶은 채 정렬 기준만 늘릴 때 쓴다(→ 06-02).
  4. 확인해 볼 것콘솔에서 테이블의 인덱스 목록에 만든 색인 이름과 상태가 ACTIVE로 보이는지 확인한다.

#5한 줄 요약

색인 관리는 기본 키로 못 잡는 질의에 secondary index를 붙여 조회 패턴을 늘리는 것입니다.

먼저 알아야 할 것 02-04

→ 02-03 참조

#1문제 상황

SQL 문장은 여러 테이블을 조인으로 한 번에 묶는다(→ 02-01). DynamoDB는 조인 대신 키 조건으로 좁혀 읽는다.

그래서 Learn how to go from SQL to NoSQL의 다른 점을 따라가며 Accessing and authentication, Modifying data, Deleting data, Removing a table 같은 동작을 각각 대응시킨다.

#2핵심 질문

익숙한 SQL 질의를 NoSQL 요청으로 어떻게 옮기는가?

#3동작 예시

앨범과 곡을 따로 조회하던 서비스를, 곡 항목 안에 앨범 정보를 함께 넣어 한 테이블로 바꾼다.

앨범 목록을 읽을 때는 곡 Query를 여러 번 이어 붙이고, 곡 수정은 update item으로 처리한다.

#4동작 과정

  1. 요구하는 질의를 먼저 센다애플리케이션이 어떤 조건으로 찾는지를 나열한다(→ 05-01). 조인이 필요한 조건은 데이터 중복 저장으로 대신한다(→ 05-05).
  2. 쿼리를 API로 옮긴다Accessing and authentication, 즉 연동과 인증을 먼저 붙여 두고 요청 경로를 정리한다.
  3. 쓰기와 삭제를 바꾼다Modifying data와 Deleting data는 각각 update item, delete item으로 대응시킨다.
  4. 확인해 볼 것애플리케이션 로그에서 같은 화면 데이터가 몇 번의 요청으로 모이는지 확인한다.

#5한 줄 요약

SQL에서 NoSQL로 가는 법은 조인 대신 비정규화 저장과 여러 번의 좁은 읽기로 같은 결과를 만드는 것입니다.

3. 읽고 쓴다 — 일관성과 두 가지 길03-01

읽기 일관성

DynamoDB 가 같은 데이터를 읽을 때 방금 쓴 값이 언제 보일지를 정하는 규칙으로, 기본은 eventual consistency(쓰기 직후 반영을 보장하지 않음)이고 strongly consistent read(동일 리전 읽기 replica 에서 최신값 보장)를 선택적으로 쓸 수 있다.

먼저 알아야 할 것 01-02

#1문제 상황

쓰기 요청이 성공 응답을 준 뒤 곧바로 다시 읽었는데 예전 값이 나온다. DynamoDB는 여러 파티션에 흩어 저장하므로(→ 01-05) 복제 지연이 생긴다.

그래서 DynamoDB read consistency 규칙으로 읽기마다 어느 수준을 보장할지 고른다(→ 03-03).

#2핵심 질문

쓴 직후의 값을 바로 읽는 것을 보장하려면 어떻게 하나?

#3동작 예시

장바구니에 수량을 반영하고 곧바로 장바구니 화면을 다시 연다.

기본 읽기에서는 아직 반영되지 않은 수량이 보일 수 있고, 일관성 옵션을 켠 요청에서는 반영된 수량이 보인다.

#4동작 과정

  1. 기본값을 쓴다모든 읽기의 기본은 eventually consistent read다. 쓰기 응답이 성공해도 복제 사본 반영은 나중일 수 있다.
  2. 강하게 읽는다DynamoDB read consistency에서 strongly consistent read를 선택하면 같은 리전의 읽기 복제본에서 최신값을 보장하는 read-after-write가 된다. 단, GSI와 Streams 읽기는 늘 eventual consistency다.
  3. 비용을 안다읽기는 항목 크기와 일관성 종류에 따라 읽기 용량 소모량이 달라진다(→ 04-01).
  4. 확인해 볼 것같은 항목에 연속해서 읽기 요청을 보내고 응답 값이 일관적으로 유지되는지 확인한다.

#5한 줄 요약

읽기 일관성은 쓴 값이 언제 읽히는지 정하는 규칙으로, 기본은 eventual consistency이고 strongly consistent read는 즉시 반영을 보장합니다.

3. 읽고 쓴다 — 일관성과 두 가지 길03-02

읽기와 쓰기 연산

테이블의 데이터를 다루는 API 동작으로, 쓰기(PutItem·UpdateItem·DeleteItem)와 읽기(GetItem·Query·Scan·BatchGetItem)로 나뉘며 각각 파라미터로 조건부 표현식과 반환할 속성을 지정한다.

먼저 알아야 할 것 03-01

#1문제 상황

관계형 데이터베이스는 문장 하나로 행을 넣고 고치고 지운다(→ 02-05). DynamoDB에서는 그 동작이 API 호출 단위로 나뉘어 있다.

Read and write operations라는 범주 아래 쓰기는 PutItem, UpdateItem, DeleteItem으로, 읽기는 GetItem, Query, Scan으로 나뉜다. 여러 항목을 한 번에 묶는 BatchWriteItem도 같은 쪽에 속한다.

#2핵심 질문

테이블의 항목을 넣고 고치고 지우는 동작은 어떤 API로 나뉘는가?

#3동작 예시

주문 상태를 바꿀 때 UpdateItem을 호출해 Status 속성만 새 값으로 바꾼다.

가격이나 앨범 같은 나머지 속성은 그대로 두고 바뀐 값만 반환받는다.

#4동작 과정

  1. 항목을 만든다PutItem은 항목을 통째로 저장한다. 같은 키가 있으면 덮어쓴다.
  2. 부분을 고친다UpdateItem은 지정한 속성만 바꾸고, 조건 표현식을 걸면 조건이 맞을 때만 반영한다(→ 03-03).
  3. 지우고 묶어서 보낸다DeleteItem이 항목 삭제를 담당하고 BatchWriteItem은 여러 항목을 한 번에 쓴다.
  4. 확인해 볼 것콘솔 항목 목록에서 속성이 바뀐 항목과 사라진 항목을 각각 확인한다.

먼저 알아야 할 것 03-02

#1문제 상황

API마다 무엇을 고칠지, 무엇을 되돌릴지를 따로 파라미터로 넘기는 방식은 다루기 번거롭다(→ 03-02).

그래서 DynamoDB는 Using expressions라는 문자열 문법을 따로 두었다. condition expression, update expression, key condition expression, projection expression, filter expression이 그 종류다.

#2핵심 질문

갱신 대상과 조건, 반환할 속성을 어떤 문법으로 지정하는가?

#3동작 예시

#4동작 과정

  1. 문법을 고른다갱신은 update expression, 조건은 condition expression, 키 범위는 key condition expression으로 고른다.
  2. 조회 대상을 정한다projection expression은 받을 속성을, filter expression은 Query 결과 중 남길 항목을 지정한다.
  3. 값을 변수로 넣는다코드에 값과 이름을 직접 쓰지 않고 expression attribute values로 참조해 예약어 충돌을 피한다.
  4. 확인해 볼 것저장한 표현식을 같은 요청에 다시 넣어 조건이 맞지 않을 때 실패하는지 확인한다.

Query — 키로 좁혀 읽는다

테이블 또는 보조 인덱스에서 파티션 키가 같은 항목들만 골라 읽는 연산으로, 정렬 키 조건과 필터를 더해 필터를 더해 결과 항목 수를 줄이는 방식이다.

먼저 알아야 할 것 03-03

#1문제 상황

테이블 전체를 훑지 않고 필요한 항목만 골라 읽으려면, 파티션 키 값 하나를 정확히 알아야 한다. Query는 파티션 키 속성과 값 하나를 받아 그 값을 가진 모든 항목을 돌려주는 연산이다. 정렬 키를 함께 주면 비교 연산자로 범위를 더 좁힐 수 있다.

#2핵심 질문

파티션 키 값 하나로 묶인 항목들만 골라 읽으려면 어떻게 요청하나?

#3동작 예시

상품 주문 목록을 볼 때 주문 번호(파티션 키)가 같은 주문 항목들만 부른다. 주문일이 특정 달 이후라는 정렬 키 조건을 함께 넣으면 그 기간의 주문만 남는다.

#4동작 과정

  1. 키를 고른다파티션 키 속성과 값 하나를 반드시 준다. 이 값이 같은 항목만 묶어서(Querying tables) 읽는다.
  2. 범위를 좁힌다정렬 키에 비교 연산자를 넣는다(sort key condition). 키 조건식은 문자열로 씀(→ 03-03).
  3. 거른다FilterExpression으로 남길 속성을 정한다. Limit을 주면 반환 항목 수를 제한한다. 일관성은 ConsistentRead로 지정한다(→ 03-01).
  4. 확인해 볼 것콘솔에서 같은 파티션 키의 항목만 목록에 모여 오는지 확인한다.

Scan과 PartiQL

Scan 은 테이블 전체를 훑으며 조건에 맞는 항목을 찾는 방식이라 큰 테이블에서 비싸고, PartiQL 은 SQL 비슷한 문장으로 여러 테이블에 걸친 조건부 조회와 업데이트를 한 번에 기술하는 방식이다.

먼저 알아야 할 것 03-04

#1문제 상황

파티션 키를 몰라서 아무 데나 찍을 때 쓰는 것이 Scan이다. Scan은 테이블이나 색인 전체를 훑으므로(Scanning tables) 큰 테이블에서는 읽기와 비용이 크게 든다. PartiQL은 SQL 비슷한 문장인 PartiQL query language로 여러 테이블을 함께 다루는 다른 방법이다.

#2핵심 질문

파티션 키를 모를 때 테이블을 어떻게 탐색하고, 여러 테이블을 한 문장으로 어떻게 다루나?

#3동작 예시

고객 목록 화면에서 이름으로 한 사람을 찾으려고 Scan에 이름 필터를 건다. 결과는 나오지만 테이블 크기만큼 전부 읽어야 해서 요청이 느리다. PartiQL로는 여러 테이블에서 조건에 맞는 행을 골라 한 번에 갱신한다.

#4동작 과정

  1. 훑는다Scan은 테이블의 모든 항목을 읽으며 파티션 키 값은 정렬되지 않은 순서로 나온다. 같은 파티션 안에서는 정렬 키 오름차순이다.
  2. 줄인다ProjectionExpression으로 일부 속성만 받고, filter expression으로 조건에 안 맞는 항목을 걸러 낸다. 한 번의 Scan이 가져올 수 있는 양은 1MB라 다음 줄을 계속 요청하는 pagination이 필요하다.
  3. 문장으로 쓴다PartiQL query language를 쓰면 여러 테이블에 걸친 조건부 조회를 한 문장에 쓴다. 인덱스 없는 속성으로 조인도 가능하지만 전체를 훑는 비용은 그대로 든다.
  4. 확인해 볼 것콘솔에서 Scan 결과가 파티션 키 순으로 정렬되지 않은 채 오는지 확인한다.

on-demand 용량 모드

요청이 들어올 때 자동으로 읽기·쓰기 처리량을 늘려 capacity unit 예약 없이 사용하는 DynamoDB의 과금 방식이다.

먼저 알아야 할 것 03-02

#1문제 상황

테이블에 쓸 용량을 미리 정해 두려면 예측이 필요하고, 예측이 틀리면 느려지거나 돈만 낼 수 있다. DynamoDB on-demand capacity mode는 capacity unit 예약 없이 pay per request로 쓴 만큼만 낸다. traffic가 이전 최고치를 넘으면 DynamoDB가 알아서 처리량을 늘린다.

#2핵심 질문

쓰기 전에 용량을 정하지 않고도 얼마만큼이나 처리해 줄 수 있나?

#3동작 예시

새 서비스의 테이블을 만들 때 처리량을 지정하지 않는다. 평소엔 요청이 적게 들어오고 배포 직후maximum throughput가 크게 뛴다. DynamoDB가 곧바로 스케일해 별도 설정 없이 버틴다.

#4동작 과정

  1. 모드로 고른다DynamoDB on-demand capacity mode를 선택한다. 기본값이자 서버리스 앱에 권장되는 선택이다.
  2. 쓴 만큼 낸다읽기와 쓰기 요청별로 pay per request 과금이 붙는다. 유휴 용량에 대한 비용은 없다.
  3. 자동으로 오른다새 최고치에 닿으면 double the previous peak 수준까지 처리량이 늘어난다. 한 번 확장된 뒤에는 같은 수준까지 즉시 처리한다.
  4. 확인해 볼 것콘솔에서 테이블의 처리량 모드가 on-demand로 표시되는지 확인한다.

provisioned 용량 모드

테이블을 만들 때 읽기와 쓰기의 초당 처리량(capacity unit)을 미리 지정해 그 양만큼 읽기·쓰기 용량을 확보하는 방식이다.

먼저 알아야 할 것 04-01

#1문제 상황

트래픽 예측이 서면 비용을 미리 정해 두는 편이 낫다. Provisioned capacity mode는 읽기와 쓰기의 처리량을 초당 값으로 지정한다. 사용한 만큼이 아니라 예약한 시간당 양으로 과금된다.

#2핵심 질문

요청이 늘기 전에 읽기와 쓰기 용량을 얼마로 잡아야 하나?

#3동작 예시

주간 보고용 테이블을 만들 때 시간대별 요청 수를 보고 읽기·쓰기 capacity unit을 지정한다. 밤에는 그 값이 남아도 과금은 예약량 기준이다.

#4동작 과정

  1. 용량을 지정한다테이블에 read capacity units와 write capacity units를 초당 값으로 넣는다. 과금 기준은 이 예약량이다.
  2. 요구량에 맞춰 조정한다트래픽이 바뀌면 값을 고쳐 읽기와 쓰기 처리량을 늘리거나 줄인다.
  3. 한도를 넘으면 막는다지정한 용량을 넘는 요청은 ProvisionedThroughputExceededException으로 거절된다. 이때 auto scaling으로 자동 조정할 수 있다.
  4. 확인해 볼 것콘솔에서 테이블에 지정된 읽기와 쓰기 처리량 값이 보이는지 확인한다.

#1문제 상황

낮에는 적고 낮에만 몰리는 앱이나 unexpectedly popular 게임은 사람이 밤새 용량을 조절하기 어렵다. auto scaling은 그 조정을 대신한다. 장기간 예측 가능한 부하는 reserved capacity로 미리 결제해 사 두는 편이 싸다.

#2핵심 질문

사용량에 맞춰 provisioned 처리량을 자동으로 늘리려면 어떻게 설정하나?

#4동작 과정

  1. 범위를 정한다최소·최대 읽기/쓰기 용량과 target utilization 비율을 정한다. Application Auto Scaling 은 이 값으로 자동 조정을 지시한다.
  2. 늘리고 줄인다DynamoDB auto scaling이 CloudWatch 알람을 통해 실제 트래픽을 감시하고(→ 11-04), Managing throughput capacity with auto scaling이라 부르는 이 동작이 GSI에도 적용돼 테이블과 색인의 provisioned 처리량을 함께 올린다.
  3. 예측 가능한 부하는 구매한다장기간 이어질 부하는 reserved capacity로 미리 결제해 구매한 양으로 처리한다.
  4. 확인해 볼 것콘솔에서 테이블의 auto scaling 설정 화면이 열리는지 확인한다.

warm throughput

프로비저닝된 테이블에서도 처음부터 on-demand로 동작하게 설정해, 읽기·쓰기 스케일 업 전에 예열(초기 용량 확보) 시간이 드는 문제를 없애는 기능이다.

먼저 알아야 할 것 04-03

→ 04-01 참조

#1문제 상황

on-demand 테이블도 스케일 아웃 직후에는 확보된 용량이 부족해 요청이 느려지는 시간이 생긴다. Warm throughput는 과거 사용량으로 테이블과 GSI에 기본값을 둬 첫 요청부터 그 처리량까지 즉시 받게 한다.

#2핵심 질문

테이블이 바로 스케일된 뒤에도 첫 요청이 느리지 않게 하려면 무엇을 확인하나?

#3동작 예시

on-demand 테이블이 스케일 아웃되어 트래픽이 100배 늘릴 행사 전에 콘솔에서 check your table's warm throughput로 현재 값을 본다. 부족하면 increase warm throughput로 올려 둔다.

#4동작 과정

  1. 값이 있다모든 테이블과 GSI에는 과거 사용량에 근거한 warm throughput 값이 기본으로 존재한다.
  2. 즉시 받는다on-demand 모드이거나 provisioned 처리량을 그 값으로 올리면 그 수치까지는 바로 요청을 처리한다.
  3. 올려 둔다increase warm throughput로 처리량 설정과 과금 모드를 바꾸지 않고 값만 미리 높일 수 있다. 제품 출시나 세일 같은 예상 급증에 쓴다.
  4. 확인해 볼 것콘솔의 테이블 정보에서 warm throughput 값이 보이는지 확인한다.

burst와 adaptive capacity

먼저 알아야 할 것 04-04

→ 04-01 참조

#1문제 상황

평소엔 적은 용량을 잡아도 순간적으로 요청이 몰리면 throttling이 난다. DynamoDB는 burst capacity와 adaptive capacity로 이를 완화한다(→ 04-02).

#2핵심 질문

평소보다 훨씬 많은 요청이 순간적으로 몰릴 때 어떻게 처리하나?

#3동작 예시

할인 행사가 시작된 직후 읽기 요청이 갑자기 늘어난다. 방금까지 남겨 두었던 용량으로 그 폭발적인 요청(burst of throughput)도 처리되어 오류 없이 넘어간다.

#4동작 과정

  1. 남겨 둔다사용하지 않는 읽기·쓰기 처리량 중 일부를 burst capacity로 최대 5분 동안 보존한다.
  2. 긴 순간에 쓴다예상 밖의 읽기·쓰기가 throttling 없이 성공하며, 초당 provisioned 처리량보다 더 빠르게 소진될 수 있다.
  3. 불균등한 접근에 맞춘다adaptive capacity가 접근 패턴이 고르지 않은 테이블을 위해 파티션별로 쓰기에 사용된 만큼만 할당해 hot partition을 자동으로 넓힌다.
  4. 확인해 볼 것콘솔에서 테이블의 상태 항목에 적응 용량 상태가 표시되는지 확인한다.

용량 모드 전환

provisioned와 on-demand 사이를 양방향으로 바꿀 수 있으며, on-demand에서 provisioned으로 내릴 때 한도 내에서 쓰기 처리량을 하나씩 되돌릴 수 있는 전환 규칙이 있다.

먼저 알아야 할 것 04-05

→ 04-02 참조

#1문제 상황

provisioned 용량 모드(→ 04-02)는 읽기와 쓰기 처리량을 미리 지정하고 그 양을 유지한다. 하지만 실제 부하는 예측하지 못한 순간에 몰린다. 반대로 on-demand(→ 04-01)는 대기 없이 처리하지만 평소 적은 트래픽에서는 예약을 낭비한다.

Switching capacity modes는 테이블의 용량 모드를 양방향으로 바꾸는 기능이다. 예측 가능한 부하에는 provisioned를, 예측하기 어려운 부하에는 on-demand를 골라 두 모드를 오갈 수 있다. 전환 뒤에는 그 방식에 맞춰 다시 확정하지 않아도 테이블이 계속 동작한다.

#2핵심 질문

부하 예측이 틀렸을 때 테이블의 용량 모드를 어떻게 바꾸는가?

#3동작 예시

결제 배치 시간에 주문 테이블의 쓰기가 평소의 열 배로 뛴다. provisioned 상태에서는 미리 읽어 둔 용량을 넘겨 요청이 밀린다. 운영자는 테이블을 on-demand로 전환하고 배치가 끝난 뒤 다시 provisioned로 되돌린다.

#4동작 과정

  1. on-demand로 전환한다처리량을 미리 지정하지 않고 요청한 만큼만 쓰는 상태로 바꾼다. 이 동작을 switch to on-demand라 하며 24시간 구간 안에서 최대 네 번까지 가능하다.
  2. provisioned로 되돌린다읽기와 쓰기 처리량을 다시 지정해 두는 상태로 되돌린다. 이 동작을 switch to provisioned라 하며 언제든 할 수 있다.
  3. 처음부터 on-demand로 시작한다스케일 업 전에 용량을 확보하는 대기 시간이 없도록, 처음부터 on-demand로 동작하게 지정할 수 있다. 이는 warm throughput(→ 04-04) 설정을 뜻한다.
  4. 확인해 볼 것콘솔의 테이블 요약에서 용량 모드 항목에 현재 상태가 on-demand로 표시되는지 확인한다.

5. 데이터 모델링 — 스키마를 미리 그린다05-01

데이터 모델링 기초

애플리케이션이 요구하는 조회 패턴(어떤 조건으로 데이터를 찾는가)을 먼저 나열한 뒤, 그 패턴에 맞춰 DynamoDB 테이블의 파티션 키와 정렬 키를 정해 스키마를 미리 설계하는 작업.

먼저 알아야 할 것 02-05

#1문제 상황

관계형 데이터베이스에서는 스키마를 먼저 세우고 그에 맞춰 질의를 만든다(→ 02-05). DynamoDB에서는 파티션 키와 정렬 키를 먼저 정해야 읽기와 쓰기 속도가 정해진다. 키를 나중에 고르면 데이터가 한 파티션에 몰려 속도가 떨어진다.

Data modeling foundations는 조회를 어떤 조건으로 할지(access patterns) 먼저 적고, 그 패턴에 맞는 partition key and sort key 를 골라 스키마를 세우는 순서를 정한다. 결과로 여러 데이터 종류가 한 테이블에 나란히 놓여 data distribution 가 정해진다.

#2핵심 질문

어떤 조건으로 데이터를 찾는지 먼저 알고 스키마를 어떻게 세우는가?

#3동작 예시

게임 프로필 화면은 한 유저의 캐릭터 목록과 최근 점수를 함께 보여 준다. 설계자는 두 조회를 조회 패턴 목록에 적고, 하나의 파티션 키 아래 정렬 키로 두 종류의 항목을 구분해 저장한다. 한 번의 요청으로 필요한 항목이 모두 나온다.

#4동작 과정

  1. 조회 패턴을 나열한다애플리케이션이 데이터 찾으려고 어떤 조건을 쓰는지, 읽기와 쓰기 모두 적는다. 파티션 키 선택은 이 목록에서 나온다.
  2. 키를 정한다각 패턴이 하나의 파티션 안에서 맞춰지도록 파티션 키와 정렬 키를 정한다. 이 둘로 한 번에 읽는 단위가 정해진다.
  3. 한 테이블에 모은다파티션 키 값이 같은 항목들은 같은 파티션에 놓이는 item collection(→ 05-03) 관계를 이용해, 여러 종류의 데이터를 한 테이블에 저장한다.
  4. 확인해 볼 것콘솔에서 테이블 항목으로 파티션 수와 항목 수가 의도한 대로 나뉘어 있는지 확인한다.

모델링 구성 요소

먼저 알아야 할 것 05-01

→ 05-01 참조

#1문제 상황

관계 모델을 그대로 옮기면 외래 키가 어긋난다(→ 05-05). 그래서 NoSQL 스키마는 관계를 다르게 표현해야 한다. 설계 문서에는 어떤 묶음을 어떻게 이어 붙이는지 규칙이 필요하다.

Data modeling building blocks는 스키마를 이루는 최소 단위인 블록(entity)과 그 사이의 relationships, 그리고 속성을 걸러 내는 filter와 색인, 여러 항목을 하나로 모으는 aggregation 규칙을 정한다. 이 블록 목록과 각 블록의 액세스 패턴을 적으면 스키마가 구체화된다.

#2핵심 질문

읽고 쓰는 묶음을 어떤 블록으로 나누고 그 사이 관계를 어떻게 이어 붙이는가?

#3동작 예시

장바구니 스키마를 만든다. 상위 계층과 하위 계층을 해시 기호로 이어 붙인 복합 정렬 키를 정렬 키 값으로 써서, 상위 항목과 하위 항목을 같은 파티션 안에 순서대로 놓는다. 장바구니 전체를 한 번에 읽는다.

#4동작 과정

  1. 블록을 나눈다한 번에 읽고 쓸 단위를 블록으로 정한다. 각 블록에는 어떤 entity와 속성이 들어가는지 적는다.
  2. 관계를 잇는다상위와 하위 항목을 정렬 키에 이중화 구조로 이어 쓴다. 이 규칙을 쓰면 조인 없이 계층 전체가 조회된다.
  3. 묶음 이름을 정한다index로 다른 속성 기준의 조회 경로를 만들고, filter로 읽은 항목 중 일부만 걸러 낸다. 여러 블록을 함께 쓰는 질의가 많으면 aggregation 규칙을 함께 적는다.
  4. 확인해 볼 것스키마 문서의 블록 목록에서 각 블록의 키와 액세스 패턴이 하나씩 채워져 있는지 확인한다.

Item Collection

하나의 파티션 키 값을 공유해 같은 파티션 안에 들어 있는 모든 Item 의 묶음으로, 파티션 키만 조건에 넣고 정렬 키 조건을 좁혀 Query 로 읽어 내는 기본 단위다.

먼저 알아야 할 것 05-01

#1문제 상황

사용자마다 여러 개의 항목이 따로 떨어져 있으면 사용자 하나를 전부 읽을 때 여러 번 요청해야 한다. DynamoDB는 파티션 키 값이 같은 항목들을 한 파티션에 모아 둔다(→ 05-01). 이 묶음을 이해해야 한 번의 읽기로 모두 가져올 수 있다.

Working with Item Collections는 이 묶음을 뜻하며, partition key grouping 으로 파티션 키만 조건에 넣고 related items 를 정렬 키 조건으로 좁혀 Query로 읽어 낸다(→ 03-04). 기본 키가 파티션 키와 정렬 키로 된 테이블에서만 만들어진다.

#2핵심 질문

한 파티션 키 아래 묶인 항목들을 어떻게 한 번에 다루는가?

#3동작 예시

게임의 사용자 계정마다 무기 목록 항목이 따로 저장돼 있다. 사용자가 인벤토리를 열면 파티션 키로 그 사용자를 지정하고 정렬 키가 무기 접두사로 시작하는 항목만 물어본다. 한 요청으로 그 사용자의 무기 목록이 나온다.

#4동작 과정

  1. 묶음을 만든다같은 파티션 키 값을 가진 항목이 같은 파티션에 나란히 놓인다. 이게 item collection 이고, 기본 테이블과 보조 색인 양쪽에 생긴다.
  2. 정렬 키로 좁힌다정렬 키를 계층 이름으로 이어 써서 묶음 안에서 범위를 지정한다. 파티션 키만 찍고 이 범위 조건을 더해 질의한다.
  3. 여러 묶음을 한 번에 고친다관련 항목이 여러 묶음에 걸치면 TransactWriteItems 로 한 번에 처리한다. 트랜잭션(→ 06-04)은 중간에 다른 요청이 끼어드는 것을 막는다.
  4. 확인해 볼 것Query 결과에 같은 파티션 키를 가진 항목들이 정렬된 형태로 함께 오는지 확인한다.

먼저 알아야 할 것 05-02

→ 05-02 참조

#1문제 상황

기존 서비스는 여러 테이블에 데이터를 나눠 정규화해 두고 조인으로 합쳐 읽는다. DynamoDB에는 조인이 없어서 같은 화면을 만들려면 여러 번 읽어야 한다.

Relational modeling 은 이 구조를 옮기는 지침이다. NoSQL 은 정해진 스키마 없이 파티션 키와 정렬 키만 두면 나머지 속성은 자유롭게 넣는 저장 방식이다. First steps 로 데이터를 함께 읽을 묶음을 정한 뒤, 필요한 값을 파티션 키와 정렬 키 쪽에 중복 저장해 한 번에 읽게 만든다. 정규화로 중복을 없애던 습관을 여기서는 일부 되돌린다.

#2핵심 질문

조인이 없는 저장소에서 여러 테이블에 걸친 데이터를 어떻게 한 번에 읽을까?

#3동작 예시

주문과 주문 항목이 별도 테이블에 있다. 주문 목록 화면을 낼 때 함께 쓰는 주문자와 상태 값을 주문 항목에 함께 넣어 둔다. 주문 파티션을 한 번 읽으면 화면에 필요한 값이 다 나온다.

#4동작 과정

  1. 정규화의 이득을 먼저 본다Traditional relational database models 에서는 중복을 없애는 정규화가 쓰인다. normalization trade-off 를 이해해야 무엇을 포기할지 정할 수 있다.
  2. 첫 묶음을 정한다First steps 에서 화면 하나가 필요로 하는 데이터만 한 묶음으로 정한다. 조인이 필요할 때마다 묶음을 넓히지 않는다.
  3. 값을 중복 저장한다Example 단계에서 함께 읽어야 하는 값을 같은 파티션에 넣는다. How DynamoDB eliminates the need for JOIN operations 로 조인 없는 화면 구성이 가능하다.
  4. 확인해 볼 것화면에 필요한 값이 한 번의 Query로 다 나오는지, 빠진 값이 없는지 확인한다.

테이블을 만들 때 정해야 하는 파티션 키와 정렬 키를 지정해 여러 항목(Item)을 담는 가장 기본적인 저장 단위를 구성하는 일.

먼저 알아야 할 것 05-01

#1문제 상황

데이터를 넣으려면 저장 공간이 먼저 있어야 한다. DynamoDB에서 그 공간이 파티션 키와 정렬 키를 가진 테이블이다. 키를 잘못 잡으면 나중에 수정이 어렵다(→ 05-01).

Basic operations on tables는 테이블을 다루는 기본 동작 모음이다. create table 로 시작해 describe table 로 확인하고, 필요하면 update table 로 고치고 delete table 로 없앤다. 이름 규칙과 키 지정은 처음 만들 때 정한다.

#2핵심 질문

테이블을 만들고 확인하고 고치고 지우는 기본 동작은 무엇인가?

#3동작 예시

주문 저장용 테이블을 만든다. 이름과 파티션 키, 정렬 키를 지정해 CreateTable을 부르고, 만들어진 뒤 DescribeTable로 파티션 수와 상태를 확인한다. 이후 읽기·쓰기 용량 모드나 보조 색인을 바꾸려면 UpdateTable을 쓴다.

#4동작 과정

  1. 테이블을 만든다create table 에 테이블 이름과 기본 키를 준다. 기본 키는 파티션 키 하나이거나 파티션 키와 정렬 키 두 개다. 이름 규칙을 지켜야 한다.
  2. 정보를 본다describe table 로 현재 파티션 수, 크기, 상태를 확인한다. 이름만 보려면 목록 조회도 쓸 수 있다.
  3. 설정을 고친다update table 로 읽기·쓰기 용량이나 보조 색인, 삭제 보호 여부를 바꾼다. 키 자체는 바꿀 수 없다.
  4. 확인해 볼 것콘솔의 테이블 목록에서 상태가 ACTIVE로 표시되는지 확인한다.

보조 색인 — GSI와 LSI

원래의 파티션 키·정렬 키 조합 대신 다른 속성 값으로 항목을 찾아 주는 색인 구조로, GSI는 다른 파티션 키 조합을, LSI는 같은 파티션 키 안에서 다른 정렬 키를 쓴다.

먼저 알아야 할 것 06-01

#1문제 상황

DynamoDB는 기본 파티션 키와 정렬 키의 값으로 항목을 빠르게 찾는다(→ 01-05). 그런데 애플리케이션이 찾는 조건이 배송 상태라서 기본 키 조합에 없는 속성으로 검색해야 한다면, 테이블 전체를 훑어야 한다(→ 03-05).

보조 색인인 secondary index는 테이블의 속성 일부와 다른 키를 따로 모아 둔 데이터 구조다. GSI, 즉 Global secondary indexes는 다른 파티션 키와 정렬 키 조합을 쓰고, LSI, 즉 Local secondary indexes는 기존 파티션 키를 그대로 둔 채 정렬 키 하나를 더 쓴다. 하나라도 만들면 Query로 원하는 조건만 좁혀 읽을 수 있다.

#2핵심 질문

기본 키가 아닌 속성으로 항목을 빠르게 찾으려면 어떻게 해야 할까?

#3동작 예시

주문 테이블에 GSI를 하나 두고 파티션 키를 배송 상태, 정렬 키를 주문 시각으로 정한다. 배달팀이 미배송 목록을 열면 Console에서 해당 GSI에 Query를 보내 상태가 대기 중인 항목만 시간순으로 나온다.

#4동작 과정

  1. 색인을 만든다Global secondary indexes는 다른 파티션 키와 정렬 키 조합을 쓰고, Local secondary indexes는 기존 파티션 키를 그대로 둔 채 정렬 키 하나를 더 쓴다. 이 alternative sort key는 같은 파티션 안에서 항목 묶음을 다른 순서로 보고 싶을 때 쓴다.
  2. 항목을 함께 쓴다색인에도 원본 항목의 속성이 들어 있어 쓰기는 원본 테이블에 한 번만 한다. 색인에는 Working with secondary indexes 절차를 따라 직접 채우거나, 읽을 때만 채우는 선택이 있다.
  3. Query로 읽는다색인마다 읽기와 쓰기 처리량, 파티션 수 같은 사용 설정을 따로 정한다. 벡터 인덱스는 이 색인과 다른 조회 방식을 쓴다.
  4. 확인해 볼 것테이블 화면에서 Indexes 목록에 만든 GSI와 LSI가 각각 몇 개인지 확인한다.

항목에 담긴 다차원 숫자 벡터를 근접도 순서로 저장해 두고, 새 벡터와 가장 비슷한 항목들을 찾아 주는 검색 구조다.

먼저 알아야 할 것 06-02

#1문제 상황

키 값이 정확히 같은 항목을 찾는 보조 색인(→ 06-02)으로는 비슷한 의미를 가진 항목을 찾을 수 없다. 상품 설명을 숫자 벡터로 바꾼 뒤 입력과 가장 닮은 상품을 찾는 일은 다른 저장소가 필요해 보였다.

vector indexes는 그런 검색을 테이블 안에서 직접 처리한다. 별도의 vector database와 데이터를 복제해 두지 않아도 된다.

#2핵심 질문

새 벡터와 가장 비슷한 항목을 테이블에서 바로 어떻게 찾아낼까?

#3동작 예시

사용자가 입력한 상품 설명을 임베딩 벡터로 변환한다. CreateTable과 UpdateTable API의 vector 인덱스 파라미터로 지정한 인덱스에 SearchVectors를 보내면 비슷한 상품 다섯 건이 similarity score 순으로 돌아온다.

#4동작 과정

  1. 벡터를 함께 저장한다작업 데이터 옆에 vector embeddings를 항목 속성으로 넣는다. 인덱스 정의는 Creating and searching vector indexes 절차에 따라 테이블 생성이나 변경 때 같이 넣는다.
  2. 가까운 값을 찾는다vector similarity를 위해 approximate nearest neighbor(ANN) 검색을 쓴다. 정확한 일치와 범위 질의로 찾던 방식과 달리 근사값을 돌려주지만 큰 테이블에서도 빠르게 동작한다.
  3. 결과를 점수로 매긴다SearchVectors가 similarity score로 순위를 매겨 가장 비슷한 항목부터 돌려준다. 보안은 다른 API와 같은 IAM 방식으로 다루며, 요구 조건과 제약은 문서의 Requirements and limitations 절에 정리되어 있다.
  4. 확인해 볼 것테이블의 인덱스 목록에서 vector 인덱스가 다른 색인과 따로 표시되는지 확인한다.

게임에서 아이템을 교환할 때 플레이어 프로필과 보유 아이템 목록을 함께 바꿔야 한다. 항목별로 따로 쓰면 중간에 실패해 프로필만 바뀌거나, 다른 요청이 그 사이의 값을 읽을 수 있다.

Transactions는 이 여러 동작을 한 묶음으로 처리해 ACID 성질을 제공한다. 데이터 정확성이 뒤틀리는 일이 없다.

#2핵심 질문

여러 항목을 한꺼번에 바꿀 때 모든 변경만 반영되게 어떻게 보장할까?

#3동작 예시

한 주문에 상품 재고 감소와 주문 항목 추가를 묶어 TransactWriteItems 하나로 보낸다. Console의 CloudWatch 지표에서 이 요청이 실행된 것을 확인하면 두 항목 모두 반영되었거나 모두 그대로다.

#4동작 과정

  1. 묶음을 만든다TransactWriteItems에 여러 Put, Update, Delete, ConditionCheck 동작을 담아 한 번에 보낸다. 읽기 쪽도 여러 Get을 TransactGetItems 하나로 묶을 수 있어 Working with transactions가 하나의 API 묶음으로 처리된다.
  2. 한 번만 보낸다요청이 여러 번 도착해도 같은 결과가 되도록 idempotent request token을 넣는다. 재시도로 중복 차감되는 일을 막는다.
  3. 권한을 정한다Using IAM with transactions 절에서 볼 수 있듯 트랜잭션도 항목별 권한을 함께 검사받는다.
  4. 확인해 볼 것코드 로그에서 하나의 TransactWriteItems 요청이 항목별 개별 요청보다 단위로 처리된 것을 확인한다.

Streams

테이블 안의 항목이 생성·수정·삭제될 때 그 변경 기록을 시간 순서대로 남겨 이후 다른 시스템이 순서대로 소비할 수 있게 하는 기능이다.

먼저 알아야 할 것 06-01

#1문제 상황

모바일 앱이 주문 데이터를 초당 수천 번씩 고친다. 이 변화를 캐시 갱신이나 알림 발송에 쓰고 싶은데, 애플리케이션이 매번 변경된 값을 찾아 다른 시스템으로 보내야 한다.

DynamoDB Streams는 테이블 안에서 일어나는 변경을 테이블 밖으로 내보내 이 일을 대신한다.

#2핵심 질문

테이블에서 일어난 변경을 어떻게 순서대로 다른 시스템에 전달할까?

#3동작 예시

주문 항목이 수정될 때마다 변경 기록이 스트림에 쌓인다. 별도 소비 애플리케이션이 이 기록을 읽어 재고 알림을 보내고, 지난 기록은 보관 기간이 지나면 지워진다.

#4동작 과정

  1. 변경을 남긴다DynamoDB Streams는 항목의 생성·수정·삭제마다 stream records를 시간 순서로 기록한다. 테이블에서 직접 켜는 기능이라 애플리케이션이 쓰기 코드를 바꿀 필요가 없다.
  2. 읽어 간다소비자는 event stream를 앞에서부터 순서대로 읽으며, 읽은 위치는 이어서 쓰기할 지점으로 남는다. 애플리케이션마다 읽는 지점을 따로 관리한다.
  3. 다른 스트림으로 보낸다Kinesis Data Streams로도 변경 내용을 보낼 수 있다. 그쪽에 맞춰 스트림 주기를 고르는 방식이다.
  4. 확인해 볼 것테이블의 Streams 탭에서 스트림이 켜져 있고 기록이 쌓이는지 확인한다.

태그와 TTL

테이블에 이름-값 형태의 라벨(태그)을 달아 관리·비용 배분용으로 쓰고, 항목에 만료 시각을 지정해 그 시간이 지나면 자동으로 지우는 TTL(Time To Live) 설정이다.

먼저 알아야 할 것 06-01

#1문제 상황

테이블이 많아지면 어떤 테이블이 어느 팀의 어떤 환경 것인지 구분하기 어렵고, 청구서에도 서비스 이름만 적힌다. 또 세션 정보처럼 금방 필요 없어지는 데이터를 직접 지우는 작업을 매번 해야 한다.

태그와 TTL은 이 두 가지를 각각 설정만으로 해결한다.

#2핵심 질문

테이블을 분류해 관리하고 쓰고 지워야 할 항목을 자동 정리하려면 어떻게 해야 할까?

#3동작 예시

운영용 테이블에 환경과 담당자 태그를 붙인다. 청구 리포트에서 태그 값별로 비용이 나뉘어 보이고, 세션 항목에는 만료 시각을 넣어 시간이 지나면 DynamoDB가 지운다.

#4동작 과정

  1. 태그를 단다Tags and labels로 이름과 값 쌍을 붙인다. 목적, 담당자, 환경 같은 기준으로 리소스를 모아 보고, tag-based access에서는 태그 값을 조건으로 접근을 나눌 수 있다.
  2. 값을 정한다Tagging resources로 태그를 만들 때 DynamoDB의 태그 제약을 먼저 확인한다. 해당 테이블의 LSI와 GSI에는 같은 태그가 자동으로 붙는다.
  3. 만료를 정한다Time to Live(TTL)를 테이블에 켜고 항목에 만료 시각을 넣으면, 그 시간이 지난 expired items는 DynamoDB가 지운다.
  4. 확인해 볼 것테이블의 Tags 목록에 붙인 이름과 값이 보이는지 확인한다.

7. 읽기를 빠르게 — DAX07-01

DAX이란 무엇인가

DynamoDB Accelerator(DAX)는 DynamoDB 앞단에 놓여 요청 결과를 메모리에 저장해 두었다가 돌려주는 인메모리 캐시 서비스로, 같은 데이터를 반복 읽는 application's 응답 지연을 마이크로초 단위로 줄여 준다.

먼저 알아야 할 것 06-02

#1문제 상황

DynamoDB의 일반적인 응답 시간은 한 자릿수 밀리초 수준이다. 어떤 애플리케이션은 마이크로초 단위 응답을 요구하는데, 같은 데이터를 반복해서 읽는 요청을 매번 테이블까지 보내면 느리다.

DynamoDB Accelerator(DAX)는 그 반복 읽기를 앞단에서 대신 처리하는 캐시 서비스다.

#2핵심 질문

같은 데이터를 계속 읽는 애플리케이션을 어떻게 마이크로초 단위로 빠르게 답할 수 있을까?

#3동작 예시

인증 토큰을 항목에 넣어 두고 매 요청마다 읽는 서비스가 있다. DAX를 앞에 세우면 첫 읽기 이후에는 메모리에 있는 값을 돌려주므로 응답 시간이 마이크로초로 내려간다.

#4동작 과정

  1. 앞에 선다In-memory acceleration with DAX 방식은 DynamoDB와 같은 API를 받는 프록시 형태로 동작해 코드를 크게 바꾸지 않는다.
  2. 메모리에 담아 둔다DynamoDB Accelerator가 읽은 결과를 캐시에 적재해 두고 다음 요청에 돌려준다. 한 자릿수 밀리초에서 마이크로초 수준으로 줄어든다.
  3. 반복 읽기를 줄인다how it works가 설명하듯 캐시가 읽기 요청을 흡수해 DynamoDB로 가는 횟수를 줄이고, 읽기가 몰리는 순간 유용하다.
  4. 확인해 볼 것애플리케이션 로그에서 DAX를 거친 요청의 소요 시간이 짧게 찍히는 것을 확인한다.

#5한 줄 요약

DAX반복되는 DynamoDB 읽기를 메모리에 저장해 마이크로초 단위로 돌려주는 캐시 서비스

DAX 클러스터 구성요소와 생성

DAX 클러스터는 캐시를 담당하는 노드들로 이루어진 하나 이상의 노드 그룹과, 노드 그룹을 관리하는 파라미터 그룹, 그리고 클러스터의 IAM 역할로 구성되며, 이 세 요소를 준비해야 클러스터가 만들어진다.

먼저 알아야 할 것 07-01

#1문제 상황

DAX는 캐시를 여러 컴퓨터에 나눠 둬야 큰 읽기 처리량을 감당한다(→ 07-01). 어떤 컴퓨터를 몇 대 준비하고 어디에 두는지부터 정해야 실제로 캐시가 돈다.

DAX는 이 컴퓨터 묶음을 클러스터로 부르고, 그 안의 부분을 노드라고 부른다.

#2핵심 질문

캐시를 돌릴 컴퓨터 묶음을 만들고 어디에 둘지 어떻게 준비할까?

#3동작 예시

읽기 처리량이 큰 서비스에 DAX 클러스터를 만든다. 같은 노드 유형의 노드 여러 대가 묶여 있고, 애플리케이션은 cluster endpoint 하나만 바라보면서 캐시 요청을 보낸다.

#4동작 과정

  1. 노드를 고른다DAX cluster components에서 노드는 캐시 데이터 사본 하나를 들고 도는 최소 단위다. 노드 수를 늘리면 클러스터 전체 읽기 처리량이 늘고, 큰 node type을 고르면 용량 자체가 커진다.
  2. 클러스터를 묶는다Creating a DAX cluster 절차를 따라 노드를 클러스터로 묶는다. 같은 클러스터 안의 노드는 모두 같은 node type이고 같은 캐시 소프트웨어를 돈다. DAX T3/T2 burstable instances는 비용을 낮추는 선택지다.
  3. 둘 곳을 정한다클러스터는 리전별로 만들고 가용 영역에 걸쳐 배치한다. 보조 정리 작업 시간인 maintenance window도 함께 정한다.
  4. 확인해 볼 것DAX 콘솔에서 클러스터의 cluster endpoint와 노드 목록이 보이는지 확인한다.

7. 읽기를 빠르게 — DAX07-03

DAX 일관성 모델

DAX는 DynamoDB의 즉시 반영(eventually consistent) 읽기와 달리 기본적으로 캐시에 적재되는 순간부터 갱신된 값을 돌려주는 write-through 방식으로 동작해 읽기 후 쓰기(read-after-write) 일관성을 제공하며, 캐시에서 제거된 데이터는 원본 DynamoDB에 즉시 반영된다.

먼저 알아야 할 것 07-02

→ 07-01 참조

#1문제 상황

DynamoDB의 기본 읽기는 eventual consistency라 쓰자마자 읽으면 갱신 전 값이 나올 수 있다(→ 03-01). DAX를 앞단에 두면(→ 07-01) 이 문제도 같이 따라온다.

DAX는 DynamoDB와 별개로 동작하므로 consistency model을 따로 정한다. 기본은 write-through로, 캐시에 적히는 순간 갱신된 값을 돌려준다.

#2핵심 질문

캐시를 거쳐도 읽은 뒤 쓴 값이 바로 보이나?

#3동작 예시

상품 정보를 DAX로 고쳐 저장한 직후 같은 값을 다시 읽는다. 캐시 miss라면 DynamoDB로 가고, 적중이라면 방금 저장한 값이 돌아온다.

기본 설정에서는 두 경우 모두 저장한 값이 보인다. 노드 여러 개로 클러스터를 만들면 노드 사이에도 같은 값이 복제된다.

#4동작 과정

  1. 쓰기를 캐시에 반영한다DynamoDB에 쓴 값을 DAX가 즉시 캐시에도 넣어 둔다. 이 방식을 write-through라 하며, 읽은 뒤 쓴 값이 바로 보이는 read-after-write 일관성이 생긴다.
  2. 캐시를 지운다cache invalidation은 항목의 TTL이 끝나거나 항목이 제거될 때 원본 DynamoDB에 즉시 반영되는 동작이다. 캐시 안에서 사라진 데이터가 원본에 남아 있는 경우를 막는다.
  3. 값을 오래 붙들지 않는다없는 값을 찾는 요청은 negative caching으로 짧게 기억해 반복 조회를 덜 되게 하고, 트랜잭션 읽기와 강한 일관성 읽기도 지정할 수 있다.
  4. 확인해 볼 것값을 고친 뒤 바로 다시 읽어 방금 쓴 값이 오는지 콘솔에서 확인한다.

DAX 일관성 모델쓰자마자 읽어도 최신 값이 보이도록 캐시를 먼저 갱신하는 것

DAX 클라이언트로 개발

DAX 클라이언트는 기존 DynamoDB API를 같은 모양 그대로 두고 엔드포인트만 DAX 클러스터로 바꿔 붙이는 라이브러리여서, application's 코드에서 읽기·쓰기 코드를 거의 바꾸지 않고 캐시를 쓸 수 있다.

먼저 알아야 할 것 07-03

→ 07-03 참조

#1문제 상황

DynamoDB에 직접 붙은 애플리케이션은 같은 데이터를 반복해서 읽는다(→ 07-01). DAX를 쓰려면 코드를 전부 다시 쓰는 것은 부담이다.

Developing with the DAX client은 기존 DynamoDB 클라이언트를 DAX 클라이언트로 바꿔 붙이는 일만으로 캐시를 거치게 한다.

#2핵심 질문

기존 애플리케이션 코드를 거의 고치지 않고 DAX를 쓰려면?

#3동작 예시

Java 애플리케이션에서 DynamoDbAsyncClient를 만들던 자리를 ClusterDaxAsyncClient로 바꾼다. 그 뒤의 GetItem·PutItem 코드는 그대로 돈다.

차이는 클라이언트를 만들 때 넣는 endpoint다. DAX 클러스터 주소를 넣으면 요청이 캐시로 먼저 나간다.

#4동작 과정

  1. 클라이언트를 만든다DAX 클라이언트는 DynamoDB low-level client와 API 모양이 같은 라이브러리다. 때문에 읽기·쓰기 코드를 다시 쓰지 않는다.
  2. 연결 정보를 넣는다Making an existing application을 고칠 때는 endpoint에 dax://로 시작하는 클러스터 주소와 region을 넣고, credentials는 기존과 같은 방식으로 준다.
  3. 모니터링을 붙인다CloudWatch에 지표를 보내는 metric publisher를 추가하면 캐시 상태도 지표로 남는다. 통신은 TLS로 보호한다(→ 09-05).
  4. 확인해 볼 것클러스터의 항목 수가 늘어 ReadIOs 지표가 바뀌는지 콘솔에서 확인한다.

DAX 클러스터 관리와 관측

클러스터 관리에는 파라미터 그룹 조정과 CloudWatch 지표·로그를 이용한 상태 확인이 포함되며, 캐시 적중률(cache hit rate)이나 CPU 같은 지표를 보고 파라미터를 바꿔 트래픽에 맞춘다.

먼저 알아야 할 것 07-02

#1문제 상황

DAX 클러스터는 노드 그룹과 파라미터 그룹, IAM 역할로 만들어진다(→ 07-02). 만들어 놓고 트래픽을 받으면 무슨 상태인지 확인할 길이 없다.

Managing DAX clusters는 이 상태를 보고 크기와 파라미터를 고치는 일을 다룬다.

#2핵심 질문

캐시가 원격지에서 느려질 때 무엇을 보고 어떻게 고치나?

#3동작 예시

Monitoring with Amazon CloudWatch에서 캐시 적중률이 낮게 나온다. 파라미터 그룹에서 TTL을 짧게 잡아 항목이 오래 남지 않게 바꾼다.

Logging을 켜면 DAX의 동작이 CloudWatch Logs로 남아 문제가 난 요청의 흔적을 찾을 수 있다.

#4동작 과정

  1. 모니터링 계획을 세운다DAX를 보기 전에 목표·대상 리소스·확인 주기·사용 도구·알림 받을 사람을 정한다. 이 계획이 Monitoring DynamoDB Accelerator의 출발점이다.
  2. 지표를 본다CloudWatch에서 캐시 적중률과 CPU 같은 값을 확인한다. DAX cluster sizing guide에 따라 노드 수와 파라미터를 고쳐 scaling 한다.
  3. 호출 기록을 남긴다Logging과 AWS CloudTrail을 켜면 DAX가 받은 요청의 기록이 남아 문제 시점을 좁힌다.
  4. 확인해 볼 것CloudWatch에서 캐시 적중률 그래프가 그려지는지 확인한다.

7. 읽기를 빠르게 — DAX07-06

DAX 권한·암호화·계정 간 접근

DAX 접근 제어는 DAX 클러스터에 대한 IAM 정책과 리소스 기반 정책을 함께 쓰며, 데이터는 저장 시 암호화(at-rest encryption)를 적용하고 클라이언트와의 통신에는 전송 시 암호화(in-transit encryption)를 쓸 수 있고, 다른 계정에서 DAX 클러스터에 접근하는 것은 크로스 계정 정책으로 허용한다.

먼저 알아야 할 것 07-05

#1문제 상황

DynamoDB의 권한은 IAM과 리소스 기반 정책으로 막는다(→ 09-02). DAX는 DynamoDB와 별개의 access control 방식을 쓴다.

그래서 DAX를 넣으면 두 서비스의 보안 모델을 따로 이해하고 맞춰야 한다. 잘못 열면 캐시를 통해 원본 데이터가 드러난다.

#2핵심 질문

DAX를 앞단에 둘 때 접근과 암호화를 어떻게 맞추나?

#3동작 예시

DAX 클러스터에 IAM 정책과 리소스 기반 정책을 함께 붙여 허용된 주체만 캐시를 읽게 한다. 다른 AWS 계정의 애플리케이션에는 크로스 계정 정책으로 접근을 열어 준다.

클러스터 이름에는 고객 계정 번호 같은 신원 정보를 넣지 않는다. 이름이 계정 밖에서도 보일 수 있기 때문이다.

#4동작 과정

  1. 접근을 막는다DAX access control은 DAX 클러스터에 대한 IAM 정책과 리소스 기반 정책으로 이루어진다. DAX encryption at rest와 encryption in transit는 각각 저장 시와 통신 시의 암호화로, 후자는 ACM이 발급한 TLS 인증서를 쓴다.
  2. 계정을 넘어 허용한다Accessing DAX across AWS accounts는 다른 AWS 계정이 클러스터에 붙도록 하는 설정이다.
  3. 자동 권한을 확인한다DAX가 IAM 리소스를 다루는 service-linked roles가 어떤 것인지 확인해 과도한 권한이 남지 않게 한다.
  4. 확인해 볼 것다른 계정의 애플리케이션에서 클러스터에 붙어 볼 수 있는지 확인한다.

8. 전역 확장 — 여러 리전에서 한 테이블처럼08-01

글로벌 테이블 개념

같은 테이블의 복제본을 여러 리전에 두고 어느 리전에서 읽고 쓰든 하나의 DynamoDB 테이블처럼 쓸 수 있게 해 주는 기능.

먼저 알아야 할 것 06-05

#1문제 상황

한 리전만 두면 그 리전이 끊길 때 서비스가 함께 멈춘다. 같은 데이터를 여러 리전에 복제해 두는 게 필요하다.

Working with global tables와 Core concepts는 그런 복제를 직접 만들지 않고 맡겨 주는 기능을 다룬다.

#2핵심 질문

여러 리전에 같은 데이터가 있을 때 어디서 읽고 써도 하나처럼 보이게 할 수 있나?

#3동작 예시

서울과 오스aka에 같은 테이블의 replica table을 둔다. 서울에서 고친 데이터가 오스aka에도 복제되어 어느 쪽에서 읽어도 한 테이블처럼 보인다.

한 리전이 멈추면 트래픽을 다른 리전으로 돌릴 수 있어 업무가 끊기지 않는다.

#4동작 과정

  1. 복제본을 둔다replica tables가 각 리전에 만들어지고 replication이 자동으로 돌아 데이터가 복제된다. 어느 복제본에서든 읽기와 쓰기가 가능하다.
  2. 일관성 방식을 고른다만들 때 consistency mode를 정한다. multi-Region eventual consistency(MREC)와 multi-Region strong consistency(MRSC) 중 하나를 고르고, 지정하지 않으면 기본값이 쓰인다.
  3. 트래픽을 옮긴다한 리전의 처리가 끊기면 요청을 다른 리전으로 바꿔 Recovery Point Objective를 낮게 유지한다.
  4. 확인해 볼 것각 리전의 테이블 콘솔에서 항목 수가 같아지는지 확인한다.

→ 08-01 참조

#1문제 상황

Same-account global table은 모든 복제본이 한 계정 안에 있는 형태다.

#2핵심 질문

복제본을 한 AWS 계정 안에 모아 멀티 리전 애플리케이션을 어떻게 단순하게 구성하나?

#3동작 예시

한 계정에서 두 리전을 골라 글로벌 테이블을 만든다. 복제와 충돌 해결은 서비스가 맡으므로 애플리케이션은 업무 로직만 신경 쓴다.

같은 계정이라 권한 모델과 소유권이 복제본마다 같고, 리전을 고르는 것 외에 따로 손댈 게 없다.

#4동작 과정

  1. 리전을 고른다같은 계정 안에서 복제본을 둘 AWS Region을 고른다. DynamoDB가 있는 모든 리전에서 쓸 수 있다.
  2. 자동 복제를 맡긴다global tables가 replica table 사이의 복제를 자동으로 처리한다.
  3. 충돌을 자동 해결한다built-in conflict resolution이 같은 항목에 여러 쓰기가 겹쳤을 때 결과를 정리해 준다.
  4. 확인해 볼 것계정의 테이블 목록에서 같은 이름의 복제본이 리전별로 몇 개 잡혔는지 확인한다.

#2핵심 질문

계정 수준으로도 격리를 두고 하나의 데이터로 묶어 쓰려면 어떻게 구성하나?

#3동작 예시

  3. 확인해 볼 것각 계정의 테이블 목록에서 같은 이름의 복제본이 보이는지 확인한다.

#1문제 상황

글로벌 테이블은 같은 테이블의 복제본을 여러 리전에 두고 어느 리전에서 읽고 쓰든 하나처럼 쓰게 해 준다(→ 08-01). 그런데 복제본이 여럿이라 쓰기를 어느 리전에 보낼지, 리전이 멈췄을 때 어디로 옮길지 정하지 않으면 지연과 값 불일치가 생긴다.

#2핵심 질문

여러 리전 복제본 사이에서 쓰기와 읽기를 어떻게 나눠 보내야 하는가?

#3동작 예시

한국 사용자의 주문을 가까운 리전에 쓰고, 목록 조회는 같은 리전에서 받도록 코드를 정해 둔다. 나중에 한 리전이 점검 중이면 같은 규칙이 나머지 리전으로 요청을 옮긴다.

#4동작 과정

  1. 쓰기 모드를 정한다Write modes는 쓰기를 어느 리전에서 처리할지 정하는 규칙이다. 한 리전에 모으는 방식과 여러 리전이 나누는 방식 중 고른다.
  2. 요청 경로를 정한다Routing strategies in DynamoDB는 읽기와 쓰기를 어느 리전으로 보낼지 가르는 방식이다. 가까운 리전을 고르거나 지정한 리전에 고정하거나 둘을 섞어 쓴다. 어느 리전으로 부하가 넘어가는지 보고 Throughput capacity planning으로 복제본마다 처리량을 미리 계산한다.
  3. 리전을 비운다Evacuation processes는 한 리전을 쓸 수 없을 때 요청을 남은 리전으로 옮기는 절차다. 어떤 신호로 시작하고 대상 리전을 어떻게 정하는지 미리 정해 둔다.
  4. 확인해 볼 것콘솔의 글로벌 테이블 화면에서 리전 목록과 각 리전에 표시된 쓰기 모드가 어떻게 나오는지 확인한다.

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

  2. 복제에 붙는 비용을 센다replicated write units는 다른 리전으로 복제된 쓰기에 붙는 단위다. 이 값이 글로벌 테이블의 추가 비용으로 붙는다.
  3. 버전 차이를 확인한다Global tables versions는 2017년 이전 세대와 최신 버전이 다른 과금 방식을 쓰는지 알려 주는 구분이다. 기존 테이블을 새 리전에 붙일 때도 기준이 달라질 수 있다.

IAM — 신원 기반 권한

누가(사용자·역할) 무엇을 할 수 있는지를 신원별로 정하는 방식이며, AWS 자격 증명으로 호출자를 구별해 DynamoDB API 작업에 대한 허용과 거부를 결정한다.

먼저 알아야 할 것 06-02

#1문제 상황

테이블 하나를 여러 팀이 함께 쓴다(→ 06-02). IAM(Identity and Access Management)은 AWS 자격 증명으로 호출자를 구별해 DynamoDB 작업을 허용할지 거부할지를 정하는 곳이다. 그 자리를 비워 두면 아무나 데이터가 사라지고, 권한을 사용자마다 하나씩 적는 일도 그만 이어지지 않는다.

#2핵심 질문

어떤 주체가 어떤 DynamoDB 작업을 할 수 있는가?

#3동작 예시

#4동작 과정

  1. 신원을 붙인다IAM에 붙인 정책은 DynamoDB와 DynamoDB Accelerator(→ 07-01) 리소스에 대한 허용과 거부를 정한다.
  2. 정책을 고른다AWS managed policies는 AWS가 미리 만들어 둔 권한 묶음이다. 테이블 하나에만 쓸 거면 직접 만든 사용자 관리 정책이 더 좁다.
  3. 조건을 더한다Using conditions는 정책의 조건문에 따라 같은 API 작업도 상황마다 다르게 허용하는 방식이다.
  4. 확인해 볼 것IAM 콘솔에서 해당 역할에 붙은 정책에 dynamodb:BatchGetItem이 들어 있는지 확인한다.

#1문제 상황

리소스 기반 정책은 다른 계정에 문서를 열 수 있다(→ 09-02). 계정 ID를 하나 적는 방식이라 실수로 넓은 범위를 허용하기 쉽고, 모든 계정에 공개된 접근을 그대로 두면 테이블이 노출된다.

#2핵심 질문

다른 계정은 열어 두면서 모든 계정에 열린 접근은 어떻게 막는가?

#3동작 예시

계정 A가 계정 B의 주문 테이블에 GetItem 권한만 받게 한다. 그 사이 DynamoDB 콘솔의 Permissions 탭에서 IAM Access Analyzer가 이 허용이 외부 노출로 보고되는지 보여 준다.

#4동작 과정

  1. 허용 대상을 좁힌다Cross-account access는 리소스 기반 정책에 상대 계정의 account ID와 허용할 작업을 적어 다른 계정에서 들어오는 요청을 받는 방식이다.
  2. 공개 접근을 막는다Blocking public access는 모든 계정에 허용되는 조건이 든 정책을 정책 수준에서 거부해 외부 노출을 막는다.
  3. 주의점을 지킨다best practices는 허용할 때 계정 ID와 작업 범위를 최소한으로 적고 정기적으로 허용 목록을 다시 보는 지침이다. 콘솔의 Permissions 탭에서 Access Analyzer findings로 현재 허용이 감지되는지 본다.
  4. 확인해 볼 것테이블의 Permissions 탭에 교차 계정 허용 항목과 IAM Access Analyzer 보고가 함께 뜨는지 확인한다.

ABAC — 태그로 접근 막기

리소스에 붙은 키·값 형태의 태그를 조건으로 삼아, 태그가 일치할 때만 접근을 허용하는 접근 제어 방식.

먼저 알아야 할 것 09-01

#1문제 상황

팀마다 테이블을 따로 두면 관리가 늘어난다. 그렇다고 한 테이블을 전부 열어 두면 안 된다. ABAC(Attribute-based access control)는 주체(→ 09-01)마다 테이블을 나눠 만들지 않고도 권한을 나눌 수 있게 해 준다.

ABAC는 리소스에 붙은 태그를 조건으로 삼아 태그가 일치할 때만 접근을 허용하는 방식이다. 태그 한 쌍만으로 여러 테이블의 권한을 한꺼번에 정리할 수 있다.

#2핵심 질문

테이블을 늘리지 않고 태그로 접근 수준을 어떻게 나누는가?

#3동작 예시

주문 테이블에 team=orders 태그를 단다. IAM 정책의 조건에 같은 태그 조건을 넣자, 주문 팀 주체만 그 테이블을 읽을 수 있다.

#4동작 과정

  1. 태그를 붙인다DynamoDB 테이블에 키와 값 형태의 라벨(→ 06-06)을 다는데, 이 태그가 권한 판단의 기준이 된다. 한 테이블에 최대 50개를 붙일 수 있다.
  2. 조건에 태그를 쓴다tag-based conditions는 IAM 정책의 조건문에 태그를 넣어 태그가 일치할 때만 동작을 허용하는 방식이다.
  3. 파생 대상까지 이어진다ABAC for tables and indexes는 태그를 물려받은 인덱스(→ 06-02)까지 같은 조건으로 묶는 것이고, ABAC for DynamoDB Streams는 스트림(→ 06-05)에도 같은 태그 조건을 적용하는 것이다.
  4. 확인해 볼 것콘솔의 해당 테이블 Tags 화면에 붙은 태그의 키와 값이 어떻게 보이는지 확인한다.

#2핵심 질문

저장된 데이터와 오가는 통신을 각각 어떻게 지키는가?

#3동작 예시

주문 테이블의 이름에 고객 계좌번호를 넣었다가 지운다. 이름 같은 자유 입력란에는 민감 정보를 두지 않고, 통신은 전부 TLS를 거치게 해 둔다.

#4동작 과정

  1. 저장 상태를 지킨다Encryption at rest는 디스크와 저장 장치에 놓인 값을 암호문으로 두어 권한 없이 읽혀도 해석되지 않게 하는 것이다. 키 관리는 AWS KMS가 맡는다.
  2. 통신 상태를 지킨다Securing DynamoDB connections는 클라이언트와 DynamoDB 사이를 지나는 요청과 응답을 TLS로 암호화해 도청과 변조를 막는 일이다. 온프레미스 클라이언트와 같은 리전 안의 다른 AWS 서비스로 가는 구간도 포함한다.
  3. 이름을 조심한다data protection 지침은 테이블 이름이나 DAX 클러스터 이름 같은 자유 입력란에 고객 계좌번호 같은 신원 정보를 넣지 말라고 망라다. 진단 로그와 공개 인증서 투명성 로그에 그 이름이 기록될 수 있다.
  4. 확인해 볼 것테이블의 Encryption 항목에 암호화 설정과 사용 중인 키가 어떻게 표시되는지 확인한다.

9. 권한을 세 축으로 정한다09-06

PrivateLink 와 보안 모범사례

VPC 안에서 DynamoDB로 가는 트래픽을 공개 인터넷을 거치지 않는 전용 연결로 보내 네트워크를 격리하고, 보안 모범사례에 따라 권한·암호화·감사를 설계하는 것.

먼저 알아야 할 것 09-05

#1문제 상황

암호화와 연결 보호로 클라이언트와 DynamoDB 사이를 TLS로 지켰지만(→ 09-05), 앱이 VPC 밖에 있다면 요청은 공개 인터넷을 거쳐 AWS의 퍼블릭 엔드포인트로 나간다. 그 구간은 회사가 통제할 수 없다.

AWS PrivateLink for DynamoDB는 VPC 안에 interface endpoint를 만들어 그 요청을 사설 경로로 붙는다. AWS PrivateLink for DynamoDB Streams는 스트림, AWS PrivateLink for DAX는 캐시 읽기 경로에도 같은 방식을 적용한다.

#2핵심 질문

VPC 밖의 앱에서도 DynamoDB 트래픽을 공개 인터넷에 내놓지 않고 연결하려면?

#3동작 예시

온프레미스 서버가 VPN으로 VPC에 들어와 있다. 애플리케이션 설정의 DynamoDB 엔드포인트 자리에 VPC 인터페이스 엔드포인트 주소를 넣는다.

그러면 PutItem과 GetItem 요청이 인터넷 대신 VPC 안으로 나가고, 엔드포인트에 붙인 정책과 Security best practices의 권한·감사 설정을 함께 쓴다.

#4동작 과정

  1. 엔드포인트를 만든다VPC 안에서 DynamoDB용 interface endpoint를 프로비저닝한다. 이건 VPC 내부 전용 IP를 가진 가상 장치이며, 온프레미스 VPN·Direct Connect나 VPC peering으로도 같은 주소로 붙을 수 있다.
  2. 경로를 바꾼다애플리케이션의 DynamoDB 엔드포인트를 그 주소로 가리킨다. 엔드포인트 정책(endpoint policy)을 두면 엔드포인트로 들어오는 요청을 거를 수 있다.
  3. 규칙을 함께 정한다Security best practices에 따라 권한·암호화·감사 설정을 점검한다. 내부에서 쓰는 애플리케이션은 AWS Management Console Private Access로 콘솔 접근도 사설 경로에 묶을 수 있다.
  4. 확인해 볼 것엔드포인트 목록에서 해당 인터페이스 엔드포인트의 상태가 사용 가능인지 확인한다.

NoSQL 설계와 Well-Architected Lens

관계형 데이터베이스에 맞지 않는 규모나 접근 패턴에서는 리전션셜 데이터의 이점을 얻기 위해 DynamoDB 같은 문서 저장 NoSQL 데이터베이스를 선택하고, AWS Well-Architected 관점의 검토 항목으로 설계를 점검하는 것.

먼저 알아야 할 것 05-01

#1문제 상황

관계형 데이터베이스는 질의를 자유롭게 쓰지만 질의가 비싸고 트래픽이 몰리면 잘 늘지 않는다. DynamoDB는 파티션 키와 정렬 키를 먼저 정해야(→ 05-01) 그 대신 읽기와 쓰기 성능을 미리 예측할 수 있다(→ 02-01).

NoSQL 설계는 이 차이를 인정한 뒤 애플리케이션이 실제로 요구하는 접근 패턴을 기준으로 스키마를 짜는 일이다. NoSQL Workbench for DynamoDB는 이 설계를 도구로 옮긴 것이다. DynamoDB Well-Architected Lens는 AWS Well-Architected Framework가 특정 기술을 다룬 부분 가운데 DynamoDB 설계 항목과 cost optimization 같은 관점을 모아 점검 기준을 만든 것이다.

#2핵심 질문

관계형에서 NoSQL로 옮길 때 무엇을 먼저 정해야 예측 가능한 성능을 얻는가?

#3동작 예시

기존 주문 테이블을 옮긴다고 정한다. 접근 패턴을 나열해 보니 "고객의 최근 주문 10건"과 "주문번호로 하나 조회" 두 가지가 나온다.

파티션 키를 고객 ID로, 정렬 키를 주문 시각으로 정하면 두 패턴이 같은 파티션 안에서 정렬 키 구간 조회로 풀린다.

#4동작 과정

  1. 접근 패턴을 먼저 적는다애플리케이션이 어떤 조건으로 뭘 찾는지를 나열한다. NoSQL design에서 이 목록이 파티션 키와 정렬 키 결정의 유일한 근거다.
  2. 강약을 나란히 놓는다RDBMS와 NoSQL의 장단점을 비교해 각 접근 패턴이 어느 쪽에 맞는지 판단한다.
  3. Lens로 점검한다DynamoDB Well-Architected Lens 항목으로 설계를 다시 훑는다. 표에서 불필요한 속성이나 색인이 과한지 보고 cost optimization 관점에서 다듬는다.
  4. 확인해 볼 것NoSQL Workbench에서 접근 패턴 목록이 파티션 키와 정렬 키 정의와 일대일로 대응하는지 본다.

#5한 줄 요약

파티션 키 설계

테이블 데이터를 물리적으로 나눠 저장하는 기준인 파티션 키를, 한 파티션에 쓰기가 몰리지 않고 요청이 고르게 분산되도록 정하는 작업.

먼저 알아야 할 것 10-01

#1문제 상황

테이블이 아무리 커도 파티션 키 값 하나에 요청이 몰리면 그 파티션이 병목이 된다. 스캔으로 몰아 넣거나 특정 키만 hottest로 두면 테이블 용량 전체가 아니라 그 한 파티션의 한계에 걸린다.

partition key design는 테이블과 보조 인덱스 전체에 활동이 고르게 나게 하는 것을 목표로 삼는다(→ 10-01).

#2핵심 질문

부하가 한 파티션에 몰리지 않게 파티션 키를 무엇으로 정할까?

#3동작 예시

주문 테이블에 주문 ID를 파티션 키로 뒀다. 특정 회사가 하루 주문의 절반을 만들어 두면 그 회사의 파티션만 쓰기 한계에 닿고 다른 파티션은 쉬고 있었다.

write sharding을 써서 회사에 접미 번호를 붙인 파티션 키 몇 개로 나누니 쓸어헤갈 수 있었다.

#4동작 과정

  1. 키 후보를 고른다cardinality, 서로 다른 파티션 키 값의 개수를 본다. 값이 적으면 파티션이 조각나지 않으므로 값이 많은 쪽을 고르고, 불가피하면 분산 작업을 쓴다.
  2. 부하를 나눈다Distributing workloads를 고려해 키를 설계한다. write sharding은 키에 접미 번호를 붙여 같은 논리 키의 쓰기를 여러 파티션으로 흩어 놓는 방법이다. 읽을 때는 전체에 흩어 놓은 키를 함께 조회해야 한다.
  3. 입력을 빠르게 채운다Uploading data efficiently를 따져 WriteRequest를 묶어 보내고, 항목 크기를 읽기·쓰기 단위 한계 계산에 반영한다.
  4. 확인해 볼 것테이블에서 파티션 키 값이 몇 개로 나뉘어 있는지 Metric을 확인한다.

정렬 키 설계

같은 파티션 안에서 항목을 정렬해 두고 조건에 맞는 구간만 읽어 오도록 만드는 기준인 정렬 키(소트 키)의 스키마를 정하는 작업.

먼저 알아야 할 것 10-02

#1문제 상황

파티션 키가 같아도 항목이 많으면 전부 읽어야 한다. 정렬 키가 없어서 begins_with나 범위 조건을 못 쓰면(→ 03-04) 한 번에 몇 항목만 골라 올릴 방법이 없다.

sort key design는 정렬 키 스키마 하나가 조회 패턴 몇 개를 동시에 해결하게 한다.

#2핵심 질문

같은 파티션 안에서 필요한 항목만 골라 읽게 정렬 키를 어떻게 모양 지을까?

#3동작 예시

장소 목록 테이블의 정렬 키를 [country]#[region]#[state]#[county]#[city]#[neighborhood] 형태의 복합 정렬 키로 만들었다.

그러면 동네 목록부터 나라 단위 목록까지 어느 수준이든 between 연산자로 구간 조회가 됐다.

#4동작 과정

  1. 정렬 방향을 정한다sort key order는 정렬 키 값을 오름차순이냐 내림차순이냐 정한다. 시간이 쌓이는 데이터는 최신 것이 앞으로 오도록 뒤집는 편이 보통이다.
  2. 계층을 새긴다country, region, state 같은 값을 구분자로 이어 붙인다. 이런 composite sort key는 sort key order를 따라 정렬된 구간을 열어 주는 range queries로 어느 계층의 목록이든 읽는다.
  3. 이어 읽게 한다pagination을 위해 마지막 항목의 정렬 키를 기억해 두고 다음 요청의 시작점으로 넘긴다. 데이터가 갱신돼도 같은 지점에서 이어진다.
  4. 확인해 볼 것Query 결과에서 마지막 항목의 정렬 키를 다음 요청 조건으로 넣어 같은 파티션의 다음 구간이 나오는지 본다.

색인 설계

기본 테이블이 가진 파티션 키와 정렬 키 외의 속성으로 질의할 수 있게 해 주는 보조 색인을, 질의 패턴에 맞춰 골라 만들고 필요한 경우에만 채워 넣도록 하는 작업.

먼저 알아야 할 것 10-03

#1문제 상황

색인은 두 번째 색인 하나를 쓰면 모든 쓰기에 추가 비용이 붙는다. 그래서 다 쓰기 편한 색인만 남기면 조회 패턴이 늘 때 곤란하고, 남은 색인에서도 표 전체를 훑는 부류가 있다.

Secondary indexes를 어떤 기준으로 만들지 정하는 것이 이 항목의 몫이다.

#2핵심 질문

어떤 보조 색인을 만들고 무엇을 저장하며 언제 비워 두는가?

#3동작 예시

집계 질의가 느렸다. Streams로 바뀐 항목을 받아 미리 계산한 결과를 sparse GSI에 넣는 aggregation pipeline을 세웠다.

쓰기 흔한 항목에만 집계 값을 남기게 되어, 아무도 안 읽는 집계 행에 쓰기 비용을 쓰지 않는다.

#4동작 과정

  1. 필요한 색인만 고른다General guidelines에 따라 조회 패턴에 실제 쓰이는 색인만 만든다. 여러 색인에 같은 값을 오버로드하면 GSI write sharding 전략으로 나눠 고르게 쓴다.
  2. 저장 범위를 정한다projection을 골라 키와 속성 중 무엇만 남길지 정한다. 자주 함께 읽는 값은 미리 넣고 아니면 나중에 가져오게 둔다.
  3. 빈 칸을 활용한다sparse indexes는 해당 항목만 색인에 들어가는 색인이다. aggregation이 필요한 속성만 가진 항목에 채워 넣고, 나머지는 비워 둔다.
  4. 확인해 볼 것DescribeTable에서 만든 색인의 항목 수를 비교해 비어 있는 색인이 있는지 확인한다.

10. 설계 모범사례 — 나중에 안 후회하기10-05

대량 작업과 동시 갱신

테이블 생성이나 대량 쓰기 같은 무거운 작업을 테이블에 접근하는 애플리케이션과 분리해 수행하고, 여러 요청이 같은 항목을 동시에 고칠 때는 낙관적 잠금 같은 방식으로 충돌을 제어하는 것.

먼저 알아야 할 것 10-04

#1문제 상황

테이블을 새로 만들거나 수백만 항목을 한꺼번에 넣는 무거운 작업을 사용 중인 애플리케이션 요청 경로에 두면, 그 요청들이 기다리거나 용량 한계에 걸린다(→ 10-06).

동시에 같은 항목을 고치는 요청이 겹치면 나중 쓰기가 앞 결과를 조용히 덮어쓸 수도 있다.

#2핵심 질문

무거운 작업을 안전한 곳에 떼어 놓고, 항목 충돌은 어떻게 알아채는가?

#3동작 예시

재고 수량을 두 주문 요청이 거의 동시에 고쳤다. 먼저 읽은 쪽의 버전을 조건식에 넣어 저장했다.

나중 요청은 버전이 이미 바뀌어 조건이 맞지 않아 ConditionalCheckFailedException을 받고, 다시 읽고 재시도했다.

#4동작 과정

  1. 작업을 분리한다Bulk data operations는 애플리케이션과 떨어진 위치에서 수행한다. 대량 쓰기는 파티션 키를 여러 값에 흩어 보내 한 파티션에 몰리지 않게 한다.
  2. 버전으로 막는다Conditional batch update에서 버전 속성을 조건식에 넣는다. Optimistic locking은 이 조건이 어긋나면 실패로 돌려주는 방식이다. 충돌이 드물고 재시도가 값싸면 맞는다.
  3. 다른 방법을 고른다충돌이 잦으면 pessimistic locking with transactions로 바꾸고, 애플리케이션 여러 곳이 같은 자원을 지키는 distributed locking을 쓴다. 트랜잭션 자체는 원자성만 보장하므로 잠금은 따로 필요하다.
  4. 확인해 볼 것충돌이 났을 때 애플리케이션 로그에 ConditionalCheckFailedException과 함께 새 버전 값이 찍히는지 본다.

#5한 줄 요약

대량 작업과 동시 갱신무거운 일을 떼어 놓고 버전 조건으로 겹치는 쓰기를 막는 것

제어면과 청구 리포트

데이터를 저장하고 읽는 데이터면과 달리 테이블 생성·수정 같은 관리 동작만 담당하는 제어면을 실제 데이터 접근 경로와 분리하고, 어디에 비용이 발생했는지 청구 리포트에서 확인하는 것.

먼저 알아야 할 것 10-01

#1문제 상황

항목을 읽고 쓰는 경로와 테이블을 만들고 고치는 경로가 한 코드에 섞여 있다. 둘은 성격이 달라 실패할 때의 대응도, 누가 반복해서 부르는지도 다르다. 반대로 비용은 어디서 늘었는지 골라낼 기준이 필요하다.

#2핵심 질문

관리 동작과 데이터 접근을 어떻게 분리하고 늘어난 비용의 출처를 어떻게 찾는가?

#3동작 예시

애플리케이션이 DescribeTable을 항목 조회와 같은 함수에서 부르고 있었다. 이 동작은 control plane 호출이라 가볍게 반복하면 안 되는 종류였다.

한 계정에서 만든 테이블을 다른 계정으로 넘길 때도 control plane 경로만 따라 옮기고, 비용은 Billing and Usage Reports에서 항목별로 확인했다.

#4동작 과정

  1. 경로를 나눈다Control plane 호출과 데이터 plane 호출을 같은 코드에 섞지 않는다. 하나의 리소스 변경은 한 클라이언트에서만 요청하고 추적한다.
  2. 반복을 줄인다control plane을 지나치게 자주 부르지 않는다. 짧은 간격으로 같은 테이블 정보를 여러 번 읽지 말고 캐시에 담아 처리하고, 호출이 막히면 backoff를 두고 재시도한다.
  3. 비용을 좇는다Billing and Usage Reports에서 항목별·리전별로 어디서 비용이 늘었는지 본다. account 간 테이블 이전 같은 관리 작업은 이 리포트와 조-control plane 조회를 함께 쓴다.
  4. 확인해 볼 것리포트에서 항목별로 읽기와 쓰기 요청 수가 어디서 붙었는지 확인한다.

11. 지킨다·연결한다·본다11-01

PITR — 시간 점 백업

테이블의 과거 어느 시점 상태로 되돌려 복구할 수 있게 해 주는 기능으로, 오직 과거 데이터만 보존하는 백업이라 백업 보관 비용이 아낫고 원하는 시점의 스키마·데이터·인덱스를 그대로 되살린다.

먼저 알아야 할 것 06-01

#1문제 상황

테이블을 직접 복사해 두려면 스냅숏을 만들고 보관하는 작업을 반복해야 한다. 과거 어느 순간으로 되돌려야 할 때가 왔을 때 그 시점의 데이터만 골라 낼 방법이 없다.

Point-in-time recovery, 즉 PITR는 DynamoDB가 테이블의 과거 상태를 1초 단위로 계속 기록해 두는 기능이다(→ 06-01). 원하는 시점으로 되돌리는 동작이 생긴다.

#2핵심 질문

데이터를 실수로 지웠을 때 언제 그 시점으로 정확히 되돌릴 수 있는가?

#3동작 예시

운영자가 실수로 수만 건의 주문 항목을 삭제했다. DynamoDB 콘솔에서 해당 테이블의 백업 화면을 열고 삭제 직전 10분 전 시점을 고른다.

10분 전 상태의 새 테이블이 만들어지고, 원래 테이블은 그대로 남아 있다.

#4동작 과정

  1. 켜 놓으면 계속 기록한다Enable point-in-time recovery로 기능을 켜면 DynamoDB가 테이블의 과거 상태를 초 단위로 이어서 남긴다. 만들어 놓을 백업 일정도, 직접 지킬 사본도 필요 없다.
  2. 보관 기간을 정한다recovery window는 복구 지점을 몇 일치 남길지 정하는 값이다. 기본은 35일이고 1일에서 35일 사이로 정한다. 기간을 줄여도 요금은 바뀌지 않는다.
  3. 복구한다Recovery by initiating a table restore는 고른 시점의 데이터·스키마·보조 색인 상태를 가진 새 테이블을 만들어 낸다. 원래 테이블은 지워지지 않는다.
  4. 확인해 볼 것테이블의 백업 화면에서 복구 가능한 가장 오래된 시각과 가장 최근 시각이 목록에 보이는지 확인한다.

#5한 줄 요약

PITRDynamoDB가 스스로 과거 시점을 계속 기록해 두어 골라 되돌릴 수 있게 하는 것

온디맨드 백업과 AWS Backup

언제든 필요할 때 직접 생성해 보관하는 온디맨드 백업과, 백업·복구·보존 정책을 AWS Backup 이라는 AWS 통합 백업 서비스가 중앙에서 관리·자동화하는 방식을 함께 다루는 영역.

먼저 알아야 할 것 11-01

→ 11-01 참조

#1문제 상황

PITR로 되돌릴 수 있는 기간은 정해져 있다. 그보다 오래된 데이터를 법감 보관이나 장기 보관용으로 남겨야 한다면 따로 사본을 만들어 유지해야 한다.

On-demand backups는 언제든 직접 만들어 보관하는 전체 백업이다. AWS Backup으로 쓰면 여러 테이블의 백업과 보존 기간을 한곳에서 관리한다. 백업과 복구는 테이블 성능과 가용성에 영향을 주지 않는다.

#2핵심 질문

오래 보존해야 할 테이블의 백업과 보존 기간을 어디서 관리할까?

#3동작 예시

분기마다 실행되는 규정 보관 보고를 준비한다. DynamoDB 콘솔에서 주문 테이블의 온디맨드 백업을 하나 만들어 이름과 만료일을 지정한다.

몇 달 뒤 같은 요청이 와서 그 백업을 골라 새 테이블로 복원한다.

#4동작 과정

  1. 직접 백업을 만든다On-demand backups는 콘솔에서 몇 번 클릭하거나 API 한 번 호출해 테이블 전체를 한 점으로 보관한다. 데이터는 다시 쓸 수 없는 상태로 저장된다.
  2. 보관을 맡긴다Using AWS Backup은 백업 계획에 테이블을 넣어 AWS Backup이 일정과 보관 기간을 대신 관리하게 한다. 이 방식의 on-demand backups는 DynamoDB가 직접 만든 것보다 과금 기준이 다르다.
  3. 사본을 옮긴다Copying backups로 백업 사본을 다른 리전이나 계정으로 옮길 수 있다. Billing for backups는 보관한 크기와 기간으로 비용이 쌓이는 것을 확인하는 자리다.
  4. 확인해 볼 것백업 목록에서 만든 시각과 상태가 보이는지, AWS Backup의 백업 계획 목록에 테이블이 잡혀 있는지 확인한다.

온디맨드 백업원하는 때 직접 만든 테이블 전체 사본을 오랫동안 들고 있는 것

재해 복구 전략

지역이나 계정 전체가 끊겼을 때 데이터베이스를 다시 살아나게 하는 여러 방식을, 목표 복구 시간(RTO)과 목표 복구 시점(RPO)이라는 두 기준에 맞춰 분류해 고르는 틀.

먼저 알아야 할 것 11-02

→ 11-01 참조

#1문제 상황

한 리전이 통째로 끊기면 그 리전에 남은 사본으로는 일을 계속할 수 없다. 하지만 언제나 이중화로 복구 시간을 0으로 만들 필요는 없다. 복구 속도, 잃어도 되는 데이터량, 구현 난이도, 운영 비용 사이에서 균형을 잡아야 한다.

Choosing your disaster recovery strategy는 이 네 요소를 기준으로 방식을 고르는 기준이다.

#2핵심 질문

재해가 났을 때 얼마나 빨리, 얼마나 많은 데이터를 잃지 않고 돌아설 수 있는가?

#3동작 예시

주요 리전의 연결이 끊겨 화면에 오류가 난다. 사전에 정해 둔 RPO와 RTO에 따라 대응이 갈린다.

RTO가 몇 분 수준이면 다른 리전의 복제본인 글로벌 테이블(→ 08-01)로 읽기를 돌리고, RPO가 거의 0이어야 하면 쓰기도 받아 준다.

#4동작 과정

  1. 숫자를 정한다RPO는 Recovery point objective로, 마지막 백업 지점 이후 감내할 수 있는 최대 시간이다. RTO는 Recovery time objective로, 중단 뒤 복구까지 허용되는 최대 시간이다. 둘 다 길수록 시스템이 단순해진다.
  2. 방식을 고른다Restores는 백업이나 시간 점 복구로 새 테이블을 다시 만드는 방법이다. RPO가 짧을수록 더 자주 백업하거나 지연이 짧은 복제를 쓴다.
  3. 되돌리고 되돌린다Recovery by rolling back unwanted writes in-place는 원격 리전에 남아 있는 삭제 기록으로 지워진 항목을 되살린다. 전부 지워버린 경우를 자연스럽게 복구할 수 있다.
  4. 확인해 볼 것복구 계획 문서에 RPO와 RTO 값과 그에 대응하는 복구 절차가 적혀 있는지 확인한다.

#5한 줄 요약

재해 복구 전략감내할 downtime과 데이터 손실을 먼저 숫자로 정하고 거기에 맞는 복구 방식을 고르는 것

CloudWatch 지표와 알람

CloudWatch 라는 AWS 모니터링 서비스가 수집하는 DynamoDB 테이블의 사용량·지연·오류 수치와, 그 값이 기준을 넘으면 이메일을 보내는 알람 설정 방법을 다룬다.

먼저 알아야 할 것 04-01

#1문제 상황

가용 모드(→ 04-01)로 돌아간 테이블의 비용이 갑자기 오른 이유를 아무도 모른다. 테이블 안에서 무슨 일이 일어나는지 숫자로 보여 주는 자리가 필요하다.

Monitoring metrics는 DynamoDB가 CloudWatch로 자동으로 보내는 지표 묶음이다. 이 숫자를 보고 알람까지 걸어 둘 수 있다.

#2핵심 질문

이 테이블이 지금 얼마나 읽히고 밀리고 있으며 언제 이상 징후를 알려 줄까?

#3동작 예시

담당자가 DynamoDB 콘솔의 지표 화면에서 최근 처리량 그래프를 연다. 평소보다 read 요청이 훨씬 높게 솟은 시간이 보인다.

그래프 옆에 있던 알람 이력에는 그 시간대에 이미 한 번 알림이 남아 있다.

#4동작 과정

  1. 숫자를 모은다DynamoDB는 ConsumedReadCapacityUnits 같은 지표를 기본으로 CloudWatch에 보낸다. 기록은 일정 기간 보관되어 지난 시점의 동작을 다시 본다.
  2. 차원을 붙인다Metrics and dimensions는 지표를 잘라 볼 기준이다. 테이블 이름이나 작업 이름별로 값을 나눠 보면 어느 곳에서 값이 나왔는지 알 수 있다. TTL 삭제 속도 같은 항목별 지표도 같은 방식으로 본다.
  3. 알람을 건다Creating CloudWatch alarms는 기준값과 비교 조건을 정해 두고, 넘으면 이메일로 알려 달라고 걸어 두는 설정이다. 기준은 용량 모드나 쓰기 지연 같은 실제 값으로 잡는다.
  4. 확인해 볼 것CloudWatch 콘솔의 지표 화면에서 해당 테이블의 처리량 곡선이 시간 단위로 그려지는지 확인한다.

CloudWatch 지표테이블의 사용량과 지연을 숫자로 계속 재서 이상 징후를 알려 주는 것

11. 지킨다·연결한다·본다11-05

CloudTrail 과 Contributor Insights

누가 언제 어떤 API 를 호출했는지 남기는 CloudTrail 감사 로그와, 테이블에서 과금이나 성능 저하를 일으키는 주된 작업 주체를 찾아내는 Contributor Insights 분석 기능을 함께 다룬다.

먼저 알아야 할 것 11-04

#1문제 상황

테이블 비용이 올랐고 특정 항목만 유난히 느리다. CloudTrail은 누가 언제 어떤 요청을 보냈는지 남기는 감사 기록이다. 전체 접근 흐름은 알겠는데 어느 호출이 원인이 되는지를 짧게 골라 내야 한다.

Logging operations로 남긴 API 호출 기록과 Contributor Insights 분석을 함께 쓰면 원인이 드러난다.

#2핵심 질문

이 테이블에서 비용과 지연을 끌어올린 주된 작업은 무엇인가?

#3동작 예시

운영자가 지연 알람을 받고 그 시간대 CloudTrail 로그를 훑는다. 한 자동화 프로그램이 같은 항목을 계속 스캔한 것이 보인다.

DynamoDB 콘솔의 Contributor Insights 화면을 열면 그 항목이 접근이 가장 많은 항목으로 바로 나온다.

#4동작 과정

  1. 로그를 남긴다DynamoDB의 Logging operations는 CloudTrail에 데이터 플레인 API 호출도 기록하도록 켜는 설정이다. Understanding DynamoDB log file entries는 그 로그 한 줄의 각 필드가 무슨 뜻인지 읽는 설명이다.
  2. 분석을 켠다테이블이나 전역 보조 색인에 Contributor Insights를 켜면 접근이 가장 많은 항목과 요청이 막힌 항목을 뽑아 준다. 비용은 CloudWatch 쪽에 청구된다.
  3. 주체를 좁힌다top contributors 결과에서 한 항목이나 한 패턴이 위로 올라오면 그 주체를 대상으로 권한이나 코드를 손본다(→ 09-01).
  4. 확인해 볼 것DynamoDB 콘솔에서 Contributor Insights 화면을 열어 접근이 가장 많은 항목 목록이 보이는지 확인한다.

#5한 줄 요약

CloudTrail 과 Contributor Insights남은 API 호출 기록에서 과금과 지연의 주된 주체를 찾아 내는 것

11. 지킨다·연결한다·본다11-06

다른 AWS 서비스와 잇기

DynamoDB 를 S3 로 내보내기, Redshift 로 무중단 복제하기, EventBridge 로 이벤트 발생을 알리기처럼 다른 AWS 서비스와 데이터를 주고받는 통합 방식들을 모은 영역.

먼저 알아야 할 것 11-04

#1문제 상황

테이블에 쌓인 데이터를 분석 도구로 옮기거나, 데이터가 바뀐 때 다른 시스템에 알려 줘야 한다. 애플리케이션 코드로 매번 옮기면 같은 일을 계속 만들어야 한다.

Using DynamoDB with other AWS services는 이런 이동을 AWS 서비스끼리 연결된 방식으로 대신해 주는 영역이다.

#2핵심 질문

테이블의 데이터를 다른 AWS 서비스로 옮기고 이벤트를 전하는 일을 어떻게 코드 없이 이어 가는가?

#3동작 예시

운영자가 테이블의 오래된 항목을 Amazon S3에 내려받아 분석한다. Import from Amazon S3로 S3의 파일을 항목으로 읽어 넣고, Export to Amazon S3로 테이블 내용을 파일로 내보낸다.

같은 문서에는 변경 사실을 EventBridge로 알리는 연결법도 적혀 있다.

#4동작 과정

  1. 보낸다Export to Amazon S3는 테이블 내용을 S3 버킷에 파일로 내보낸다. 큰 데이터는 IAM 역할 권한을 줄여 두고 작업 위임으로 처리한다.
  2. 불러온다Import from Amazon S3는 S3에 있는 파일에서 항목을 읽어 테이블에 채운다. 한 번에 쓰는 크기를 나눠 나눠 넣는다.
  3. 끊김 없이 잇는다DynamoDB zero-ETL integration으로 Amazon Redshift 같은 분석 쪽에 테이블 내용을 계속 복제해 둔다. Integrating with Amazon EventBridge는 항목 변경을 이벤트로 바꿔 다른 시스템에 알리는 연결이다.
  4. 확인해 볼 것DynamoDB 콘솔의 해당 통합 메뉴에서 연결된 대상 리소스 목록이 보이는지 확인한다.

#5한 줄 요약

다른 AWS 서비스와 잇기테이블 데이터를 내보내고 이벤트를 전하는 일을 서비스 간 연결로 대신하는 것
