1AWS Shield 개요와 DDoS 공격01-01

AWS Shield 서비스 개요

AWS가 모든 고객에게 기본 제공하는 관리형 DDoS 보호 서비스로, 항상 켜져 있는 Standard 계층과 유료 구독형 Advanced 계층으로 구성된다.

1상대의 출발점 확인

DDoS 방어가 필요했던 기업들은 DDoS 공격을 막기 위해 자체 방화벽·침입 탐지 장비를 도입하거나 별도의 DDoS 방어 업체와 계약하는 방식으로 대응해 왔다. 자체 장비를 운영하는 방식은 공격 규모가 커지면 서버 대역폭 자체가 압도되어 장비가 막아내지 못하고, 장비 구매 비용과 이를 상시 운영·관리할 인력도 필요하다는 명확한 한계가 있다. 특히 공격이 들어온 순간에만 필요한 방어를, 평소에는 유휴 상태로 유지해야 하는 구조라 비효율적이었다. AWS에서 서비스를 운영하는 고객도 이런 부담을 그대로 떠안아야 했다.

2질문 제기

AWS에서 서비스를 운영하는 고객은 별도의 장비나 업체 계약 없이도 DDoS 공격을 막을 수 없을까?

3구조적 핵심 예시

EC2 인스턴스 한 대에 웹 서비스를 올려 운영하는 신입 개발자가 있다고 하자. 이 개발자가 AWS Shield에 대해 아무것도 설정하지 않아도, 트래픽이 AWS로 들어오는 순간 AWS Shield Standard가 항상 켜진 상태로 트래픽을 감시하고 있다. 어느 날 수십 Gbps 규모의 대량 트래픽이 이 서비스로 몰려들면, Shield가 이를 DDoS 공격으로 탐지해 AWS 네트워크 경계에서 해당 트래픽을 자동으로 차단·완화(공격의 영향을 줄이는 처리)한다. 개발자는 방어 설정을 하지 않았는데도 기본 계층의 보호를 이미 받고 있는 것이다.

4단계별 동작 과정

  1. 트래픽 상시 감시AWS로 들어오는 모든 트래픽을 네트워크 경계에서 지속적으로 분석해 정상 패턴과 다른 이상 징후를 찾는다.
  2. 공격 탐지대량 트래픽 증가나 비정상 패킷(패킷은 네트워크로 전송되는 데이터 덩어리) 흐름을 DDoS 공격으로 판별한다.
  3. 자동 완화공격 트래픽을 정상 트래픽과 구분해 차단하고 서비스가 계속 동작하도록 유지한다. 더 강력한 보호가 필요하면 유료 구독형인 AWS Shield Advanced 계층을 추가로 사용한다.

→ 01-05 참조

1상대의 출발점 확인

서버는 자신이 처리할 수 있는 양의 요청만 받도록 설계되어 있다. 정상적인 상황에서는 CPU, 메모리, 네트워크 대역폭, 연결 수용 한도 같은 자원이 유지되며 요청을 처리한다. 그러나 기존의 일반적인 접근 통제 방식, 즉 접근 권한이 있는 사용자만 통과시키는 방식은 "요청 자체가 정상인지"가 아니라 "요청이 너무 많은지"를 기준으로 삼지 않기 때문에, 한꺼번에 몰려드는 대량의 요청을 막을 수 없다. 각각의 요청이 모두 유효한 형태를 갖추고 있으면 개별 요청 단위에서는 공격이라는 사실조차 드러나지 않는 것이 기존 방식의 명확한 한계다.

2질문 제기

각각은 정상처럼 보이는 요청을 공격자가 어떻게 모아 서버의 자원을 고갈시켜 정상 사용자를 차단할 수 있을까?

3구조적 핵심 예시

공격자가 미리 손상시켜 장악한 수천 대의 컴퓨터(이런 컴퓨터 집단을 봇넷이라고 한다)에 명령을 내려, 특정 시각에 모두 같은 대상 서버로 접속 요청을 보내는 상황을 보자. 수천 대의 컴퓨터가 동시에 각자 하나씩의 정상적인 요청을 보내더라도, 합산된 요청의 총량은 대상 서버가 감당할 수 있는 수준을 훨씬 넘어선다. 개별 요청은 모두 정상이지만, 그 총량이 서버의 처리 능력을 초과하면서 서버가 더 이상 요청을 받지 못하게 된다.

4단계별 동작 과정

  1. 공격 자원 동원공격자가 멀웨어(악성 소프트웨어)에 감염시켜 통제권을 얻은 다수의 컴퓨터를 봇넷으로 묶어 공격 명령을 준비한다.
  2. 동시 대량 요청 전송봇넷에 속한 컴퓨터들이 같은 대상 서버를 향해 동시에 대량의 요청이나 트래픽을 집중적으로 보낸다.
  3. 자원 고갈로 서비스 거부대상 서버의 대역폭·CPU·연결 수용 한도가 가득 차 정상 사용자의 요청을 처리하지 못하게 되어 서비스가 중단된 상태가 된다.

인프라 계층 공격(L3·L4)

대량 트래픽으로 대역폭을 압도하는 볼류메트릭 공격이나 TCP SYN flood로 연결 상태를 고갈시키는 프로토콜 공격 등 네트워크·전송 계층을 겨냥하는 유형.

→ 03-02 참조

1상대의 출발점 확인

네트워크 통신은 계층으로 나뉘어 동작한다. L3(네트워크 계층)는 IP 주소를 기준으로 데이터를 목적지까지 전달하는 역할을 하고, L4(전송 계층)는 TCP 같은 프로토콜로 연결을 맺고 포트 번호로 어떤 서비스에 보낼지 결정하는 역할을 한다. 기존의 방화벽은 IP 주소와 포트 번호를 기준으로 통과시킬 트래픽을 필터링하는데, 이 방식은 "특정 주소를 막는다"는 판단만 할 뿐 트래픽의 총량 자체를 제어하지 못한다. 따라서 단일 IP 주소 하나를 막아도 공격자는 주소만 바꿔 다시 대량 트래픽을 보낼 수 있고, 결과적으로 대역폭을 압도하거나 연결 상태 테이블을 고갈시키는 공격을 막지 못하는 한계가 있다.

2질문 제기

네트워크·전송 계층을 겨냥한 대량 트래픽은 어떻게 서버의 정상 연결 자체를 마비시키는가?

3구조적 핵심 예시

TCP SYN flood 공격이 대표적이다. TCP 통신은 연결을 맺기 전에 SYN, SYN-ACK, ACK 순서로 확인하는 절차(이를 3-way 핸드셰이크라고 한다)를 거친다. 공격자는 이 절차의 첫 단계인 SYN 요청(연결을 시작하자는 신호)만 수만 개 보내고, 서버가 답변으로 보내는 SYN-ACK 응답에는 절대 답하지 않는다. 서버는 응답을 기다리는 "반쯤 열린" 연결 상태를 테이블에 계속 쌓아 두게 되고, 이 테이블이 가득 차면 이후 들어오는 모든 새 연결을 받아들일 수 없게 된다.

4단계별 동작 과정

  1. SYN 요청 대량 전송공격자가 손상된 다수의 시스템에서 대상 서버로 연결 시작 신호인 SYN 요청을 동시에 대량으로 보낸다.
  2. 연결 대기 테이블 고갈서버가 각 요청에 SYN-ACK로 응답하고 기다리지만 공격자는 답하지 않아, 대기 중인 연결 상태가 서버의 연결 테이블을 가득 채운다.
  3. 새 연결 거부테이블이 가득 차 서버가 정상 사용자의 새 연결 요청조차 받지 못해 서비스가 마비된다.

→ 03-03 참조

1상대의 출발점 확인

L7(애플리케이션 계층)은 HTTP·HTTPS 요청이 실제로 처리되는 영역으로, 사용자의 요청에 따라 로그인 절차를 진행하거나 데이터베이스에서 값을 조회하는 등 애플리케이션의 실제 로직이 실행되는 계층이다. 인프라 계층(L3·L4) 공격을 막는 대역폭 관리나 연결 테이블 보호 방식만으로는 이 계층을 지킬 수 없다. 왜냐하면 애플리케이션 계층 공격의 요청은 겉모습이 정상적인 HTTP 요청과 동일해서, IP 주소나 패킷 구조만 보는 기존 방식으로는 공격을 구분해 내지 못하기 때문이다. 탐지조차 어렵다는 점이 기존 인프라 중심 방어의 명확한 한계다.

2질문 제기

정상적인 HTTP 요청과 모양이 같은 대량 요청은 어떻게 웹 애플리케이션의 자원을 소진시켜 서비스를 중단시키는가?

3구조적 핵심 예시

공격자가 웹 서비스의 로그인 화면이나 검색 API에 정상 사용자가 보내는 것과 똑같은 형태의 요청을 수천 대의 컴퓨터로 동시에 보내는 경우를 보자. 요청 하나하나는 정상적인 로그인 시도나 검색 요청처럼 보이므로 WAF(웹 방화벽, HTTP 요청의 내용을 검사하는 방어 장치)의 일반적인 규칙도 이를 막아내기 어렵다. 그러나 이 요청들이 몰리면 웹 서버의 CPU와 메모리, 뒤에 붙어 있는 데이터베이스의 조회 처리량이 급격히 소진되어, 정상 사용자의 요청도 응답을 받지 못하게 된다.

4단계별 동작 과정

  1. 정상형 요청 대량 전송공격자가 봇넷을 통해 정상적인 HTTP 요청과 동일한 형태의 요청을 동시에 다수 보낸다.
  2. 컴퓨팅·데이터베이스 자원 소진각 요청이 로그인 처리나 데이터베이스 조회 같은 실제 연산을 실행하면서 웹 서버와 데이터베이스의 처리 자원이 빠르게 고갈된다.
  3. 응답 지연·서비스 중단자원이 부족해진 애플리케이션이 정상 사용자의 요청도 처리하지 못해 응답이 느려지거나 완전히 중단된다.

1상대의 출발점 확인

DDoS 공격은 한 가지 형태로만 오지 않는다. 공격 계층, 공격 목표, 트래픽의 성격에 따라 유형이 나뉘며 각 유형마다 막는 방법도 다르다. 기존에는 DDoS 공격이 발생해도 어떤 계층을 겨냥한 공격인지, 어떤 자원을 고갈시키려는 것인지 파악하는 것부터가 어려웠다. 공격 유형을 제대로 구분하지 못하면 대응 방향을 잘못 잡아, 예를 들어 L7 공격에 대역폭 확충만 시도하는 식의 방어가 되어 효과를 보지 못하는 문제가 있었다.

2질문 제기

형태가 각기 다른 DDoS 공격들을 유형별로 구분하면 각 공격에 맞는 대응 방향을 정할 수 있지 않을까?

3구조적 핵심 예시

공격 벡터(공격이 들어오는 경로)를 계층별로 보면, L3·L4의 볼류메트릭 공격은 UDP flood처럼 대량의 데이터 패킷을 쏟아 대역폭을 가득 채우는 유형이고, L3·L4의 프로토콜 공격은 SYN flood처럼 연결 절차를 악용해 연결 테이블을 고갈시키는 유형이며, L7 공격은 HTTP flood처럼 정상형 웹 요청을 대량으로 보내 애플리케이션 자원을 소진시키는 유형이다. 각 유형이 고갈시키는 자원(대역폭, 연결 상태, 애플리케이션 처리 능력)이 서로 다르므로, 방어 측은 공격 유형을 확인한 뒤 그 자원을 지키는 대응을 선택해야 한다.

4단계별 동작 과정

  1. 공격 계층 확인트래픽 분석으로 공격이 네트워크·전송 계층(L3·L4)에서 발생하는지 애플리케이션 계층(L7)에서 발생하는지 판별한다.
  2. 유형 분류고갈되는 자원이 무엇인지 기준으로 볼류메트릭 공격(대역폭), 프로토콜/연결 상태 공격(연결 테이블), 웹 요청 플러드(애플리케이션 자원)로 분류한다.
  3. 유형에 맞는 대응 선택분류 결과에 따라 대역폭 차단, 연결 보호, 웹 요청 필터링 등 해당 자원을 방어하는 방법을 적용한다.

Shield의 보호 범위

Shield가 네트워크·전송 계층(L3·L4)의 대규모 인프라 공격부터 애플리케이션 계층(L7) 공격까지 알려진 벡터와 제로데이 벡터를 폭넓게 보호하는 범위.

1상대의 출발점 확인

DDoS 공격은 L3·L4의 대규모 인프라 공격부터 L7의 애플리케이션 공격까지 다양한 계층에서 발생한다. 기존에는 이 각각을 막기 위해 여러 방어 수단을 따로 조합해야 했다. L3·L4 공격은 대역폭이나 연결 상태를 보호하는 네트워크 장비로, L7 공격은 웹 요청을 검사하는 WAF(웹 방화벽)로 각각 따로 대응해야 했고, 새로 등장하는 제로데이 벡터(알려지지 않은 새로운 공격 방식)까지 대비하려면 솔루션을 추가로 계속 갱신해야 했다. 이렇게 방어 수단이 분산되어 있어 하나의 공격에도 여러 제품을 관리해야 하는 것이 기존 방식의 명확한 한계다.

3구조적 핵심 예시

  2. 알려진 벡터 자동 완화대규모 인프라 공격과 알려진 공격 벡터(공격 경로)를 탐지하면 자동으로 트래픽을 차단·완화하고, 제로데이 벡터(알려지지 않은 새 공격 방식)까지 폭넓게 학습된 패턴으로 대응한다.
  3. L7 요청 필터링애플리케이션 계층의 요청은 연동된 AWS WAF의 규칙이 검사해 정상형으로 위장한 공격 요청을 차단한다.

  2. 한도 초과 판별속도 기반 규칙에 설정된 요청 수 한도를 넘긴 IP가 있으면 공격 신호로 판별한다.

2질문 제기

DDoS 이벤트가 감지된 즉시 사람의 개입 없이 트래픽을 막아 서비스를 살려 둘 수는 없을까?

3구조적 핵심 예시

Shield가 공격을 감지하면 보호된 리소스로 향하는 트래픽을 AWS 엣지에서 자동으로 검사·필터링하기 시작한다. 예를 들어 특정 IP에서 대량 요청이 몰리면 그 트래픽만 버리고 정상 사용자의 요청은 통과시켜 서비스를 계속 유지한다. 이 완화는 감지 후 짧은 시간 안에 자동으로 시작된다.

3구조적 핵심 예시

4단계별 동작 과정

  1. 에지로 트래픽 유입사용자 요청이 CloudFront나 Route 53의 에지 지점에 먼저 도달한다. 이 단계에서 아직 실제 리소스로 전달되지 않는다.

1상대의 출발점 확인

네트워크 계층(IP 주소와 포트 단위의 트래픽 흐름)의 공격은 트래픽 양 자체로 감지할 수 있지만, 웹 애플리케이션 계층(HTTP 요청 단위)의 공격은 겉보기에 정상적인 요청처럼 보여서 단순한 필터링으로는 걸러지지 않았다. 요청 한 건 한 건이 정상 요청처럼 생겼기 때문에, 기존 방화벽은 이를 차단하지 못했고 결국 애플리케이션이 처리해야 할 요청 수가 폭증해 멈추는 문제가 있었다.

2질문 제기

정상적인 요청처럼 보이는 애플리케이션 계층 공격을 어떻게 구분해서 차단할 수 있을까?

3구조적 핵심 예시

웹 애플리케이션에 대해서는 AWS WAF 규칙과 Shield의 자동 완화를 함께 사용한다. AWS WAF(웹 요청의 내용을 보고 허용·차단을 결정하는 방화벽)가 HTTP 요청의 헤더, URI(요청이 가리키는 주소), 쿼리 문자열(주소 뒤에 붙는 파라미터) 같은 내용을 규칙과 대조해 공격 요청을 차단한다. 네트워크 규모의 공격 트래픽은 Shield가 별도로 걸러내고, WAF 규칙으로 걸러지지 않는 애플리케이션 계층 공격은 자동 완화가 추가로 처리한다.

4단계별 동작 과정

  1. 요청 도달 및 검사웹 요청이 애플리케이션에 도달하기 전에 AWS WAF가 요청 내용을 규칙과 대조해 공격 패턴을 찾는다.
  2. WAF 규칙과 자동 완화 결합규칙과 일치하는 요청은 차단하고, 트래픽 규모가 커지면 Shield의 자동 완화가 네트워크 계층 공격을 함께 걸러낸다.
  3. 정상 요청만 전달공격으로 판별된 요청은 차단되고, 정상 사용자 요청만 웹 애플리케이션에 전달되어 서비스가 유지된다.

  2. 용량과 분산 확보평소 사용량보다 넉넉한 용량을 유지하고, 리소스와 IP를 여러 위치에 분산 배치해 한 지점으로 공격이 집중되더라도 전체가 멈추지 않게 한다.
  3. 공격 중에도 서비스 유지공격 규모가 커져도 보호 계층이 완화를 적용하고 분산된 구조가 부하를 나눠 받아, 정상 사용자는 계속 서비스를 이용할 수 있다.

1상대의 출발점 확인

웹 애플리케이션을 운영할 때 흔히 서버 한 대에 모든 트래픽이 직접 몰리게 구성한다. DNS가 도메인을 서버 IP로 바로 연결하고, 사용자 요청이 곧장 그 서버로 간다. 이 구조에서는 DDoS 공격 트래픽이 서버 하나에 집중된다. 공격량이 서버의 네트워크 대역폭이나 CPU 처리 한도를 넘으면 정상 사용자 요청까지 함께 처리되지 못하고, 서버를 늘려도 공격이 그 증가분을 금방 따라잡는다. 또한 공격 트래픽을 가려낼 필터가 없어서 패킷이 실제 서버에 도달하기 전에 차단할 방법이 없다.

2질문 제기

공격 트래픽이 애플리케이션의 어느 계층으로 들어오든, 정상 사용자 요청만 통과시키고 나머지를 실제 서버에 닿기 전에 막으려면 어떻게 해야 할까?

3구조적 핵심 예시

CloudFront(콘텐츠 전송 네트워크)를 최전방에 두고, 그 뒤에 AWS WAF 웹 ACL(트래픽 차단 규칙 모음)을 연결한 뒤, 오리진(실제 콘텐츠를 제공하는 최종 서버)으로는 ALB(Application Load Balancer)와 EC2 인스턴스를 두는 구성이 대표적이다. 사용자의 요청은 먼저 CloudFront의 전 세계 엣지 로케이션(사용자와 가까운 캐시 서버 지점)에 도착하고, 여기서 대부분의 공격 트래픽이 흡수·차단된다. 정상 요청만 오리진으로 전달되므로 실제 서버는 적은 트래픽만 처리한다.

4단계별 동작 과정

  1. 엣지에서 트래픽 분산모든 요청이 CloudFront 엣지 로케이션들에 분산 도착한다. 공격 규모가 아무리 커져도 트래픽이 전 세계 지점에 나뉘어 실려 특정 서버 하나가 감당할 부담이 없고, AWS Shield가 이 지점에서 대용량 네트워크 계층 공격을 차단한다.
  2. WAF 필터링CloudFront를 통과한 요청 중 의심스러운 것은 WAF 웹 ACL이 검사한다. rate-based rule(짧은 시간에 같은 IP에서 오는 요청 수가 기준을 넘으면 차단하는 규칙) 같은 규칙이 애플리케이션 계층 공격을 걸러낸다.
  3. 오리진으로 정상 요청만 전달필터를 통과한 정상 요청만 CloudFront가 ALB와 EC2로 전달해 실제 응답이 만들어진다. 결과적으로 공격은 최전방에서 끝나고, 오리진은 정상 부하만 처리한다.

1상대의 출발점 확인

TCP/UDP 기반 애플리케이션(게임 서버, 실시간 스트리밍, IoT 통신 등)은 HTTP 기반 웹과 달리 CDN이나 WAF 같은 계층을 끼우기 어렵다. 기존 구성은 클라이언트가 Elastic IP(고정 공인 IP)를 가진 서버에 직접 접속하는 형태가 많다. 이 구조에서는 공격자가 그 IP만 알아내면 서버 한 대에 SYN Flood(연결 요청 패킷을 대량으로 보내 서버의 연결 대기 슬롯을 소진시키는 공격)나 UDP Flood(대량의 UDP 패킷을 보내 대역폭을 소진시키는 공격)를 집중시킨다. IP가 고정이라 서버를 바꿔도 공격 대상이 그대로 따라붙고, TCP/UDP는 요청 내용을 검사할 규칙 기반 필터가 원래 없어서 네트워크 계층에서 막을 방법이 마땅치 않다.

2질문 제기

내용 검사가 어려운 TCP/UDP 트래픽을 서버에 직접 닿게 하지 않으면서 대용량 네트워크 계층 공격으로부터 어떻게 보호할 수 있을까?

3구조적 핵심 예시

Network Load Balancer(NLB, TCP/UDP 트래픽을 분산하는 로드 밸런서)를 서버 앞에 두고, 사용자는 Elastic IP나 Global Accelerator(여러 AWS 리전에 걸쳐 고정 IP로 트래픽을 받아 최적 경로로 보내는 서비스)를 통해 NLB에만 접속하는 구성이 대표적이다. 공격 트래픽은 서버가 아니라 NLB의 관리형 인프라에 도달하고, AWS Shield Advanced가 이 지점에서 대용량 공격을 흡수·차단한다. 실제 서버는 NLB 뒤에서 트래픽을 받으므로 공격에 직접 노출되지 않는다.

4단계별 동작 과정

  1. 고정 접점 확보사용자 트래픽이 Elastic IP 또는 Global Accelerator의 고정 IP를 통해 NLB로 들어온다. 이 주소들이 공개 접점이 되고 실제 서버의 IP는 밖으로 드러나지 않는다.
  2. 엣지·로드 밸런서에서 공격 흡수들어온 트래픽은 Global Accelerator 엣지나 NLB의 관리형 용량이 분산 처리한다. Shield Advanced가 이 지점에서 SYN Flood, UDP Flood 같은 대용량 공격을 감지해 차단하고, 정상 트래픽만 통과시킨다.
  3. 서버로 분산 전달정상 TCP/UDP 트래픽만 NLB가 백엔드 서버들에 분산해 전달한다. 결과적으로 서버는 정상 부하만 감당하고, 공격이 증가해도 NLB 용량이 먼저 감당한다.

5본질 요약

6단계 Shield Advanced 설정

Shield Advanced 사용을 시작하려면 AWS 계정에 이 서비스를 구독하는 절차로, 구독 후 보호할 리소스를 지정할 수 있다.

1상대의 출발점 확인

AWS Shield Standard는 모든 AWS 계정에 기본으로 붙어 있지만, 기본 보호는 자동화된 대용량 공격 차단과 비용 보호가 빠져 있다. 공격이 시작돼도 실시간 알림이 오지 않고, 방어 용량이 늘어나는 것도 자동으로 처리되지 않으며, 공격으로 인한 추가 비용(예: 공격 트래픽이 로드 밸런서를 거치며 발생하는 요금)을 보상받을 수단도 없다. 이런 보호가 필요한 계정이라도 서비스를 구독하고 보호 대상을 지정하기 전까지는 Advanced 기능이 전혀 동작하지 않는다.

2질문 제기

기본 보호만으로는 부족한 대규모 DDoS 방어 기능을 내 AWS 계정에서 사용하려면 무엇부터 해야 할까?

3구조적 핵심 예시

AWS Management Console에서 Shield Advanced 서비스 페이지에 들어가 구독을 시작하는 것이 전부다. 구독 시 AWS Organizations(여러 AWS 계정을 하나로 묶어 관리하는 서비스)에 등록된 계정이면 조직 전체 계정을 함께 보호하도록 선택할 수 있고, 조직이 아니면 자기 계정만 구독한다. 구독이 완료되는 순간부터 이 계정은 Shield Advanced 기능을 쓸 수 있는 상태가 된다.

4단계별 동작 과정

  1. 구독 시작콘솔의 Shield Advanced 페이지에서 구독을 시작하고, 결제에 필요한 계정 정보와 조직 결합 여부를 확인한다. 구독은 월 요금이 부과되는 유료 서비스다.
  2. 약정 확인구독 조건(요금, 계약 기간, 보호 대상 지정 범위)을 확인하고 약정을 완료한다.
  3. 구독 완료구독이 활성화되고 이제 보호할 리소스를 지정할 수 있는 상태가 된다. 이후 단계에서 실제 보호 대상을 추가한다.

5본질 요약

유료 구독을 통해 AWS 계정에 Shield Advanced 기능을 활성화하고, 이후 보호 대상을 지정할 수 있는 상태로 만드는 것

6단계 Shield Advanced 설정

Shield Advanced로 보호할 리소스(CloudFront, Route 53, ALB, NLB, EC2 등)를 선택해 보호 대상을 추가하고 구성하는 과정이다.

1상대의 출발점 확인

Shield Advanced를 구독했다고 해서 모든 리소스가 자동으로 고급 보호를 받는 것은 아니다. 구독만 하고 보호 대상을 지정하지 않으면, 공격이 시작돼도 Shield Advanced의 전용 방어 용량, 실시간 알림, 비용 보호가 어느 리소스에도 적용되지 않는다. 또한 애플리케이션마다 트래픽 패턴이 다르고 보호가 필요한 리소스가 다르므로, 어떤 대상을 보호할지 정하는 단계가 아예 없는 구성은 공격 범위가 커도 대응할 방법이 없다.

2질문 제기

구독한 Shield Advanced가 실제로 어떤 리소스를 보호해야 할지 어떻게 지정할까?

3구조적 핵심 예시

콘솔의 Shield Advanced 보호 대상 추가 화면에서 "보호 추가"를 누르고, 보호할 리소스의 유형(CloudFront 배포, Route 53 호스팅 영역, ALB, NLB, Global Accelerator, EC2 탄력적 IP)과 실제 리소스를 고르는 것이 대표적인 예다. 리소스 유형마다 지원하는 보호 범위가 달라서(예: EC2 탄력적 IP는 네트워크 계층 공격 보호용, CloudFront는 엣지 기반 보호용) 내가 운영하는 서비스 구조에 맞는 유형을 선택해 추가한다.

4단계별 동작 과정

  1. 보호할 리소스 선택보호 추가 화면에서 리소스 유형(CloudFront, Route 53, ALB, NLB, EC2 탄력적 IP 등)을 고르고, 해당 유형에 속한 실제 리소스(배포 이름, 로드 밸런서 ARN, 탄력적 IP 등)를 지정한다.
  2. 보호 등록선택한 리소스를 Shield Advanced 보호 대상으로 등록한다. 이때 리소스에 연결된 Elastic IP나 로드 밸런서가 자동으로 보호 범위에 포함되는 방식으로 함께 등록된다.
  3. 구성 확인등록된 보호 대상 목록에서 리소스가 활성 상태인지 확인한다. 이후 이 리소스에 대해 Shield Advanced의 방어 용량과 알림이 적용된다.

6Shield Advanced 설정06-03

6단계 Shield Advanced 설정

AWS WAF 웹 ACL과 rate-based rule을 이용해 애플리케이션 계층(Layer 7)의 DDoS 공격을 탐지하고 완화하도록 보호를 구성한다.

1상대의 출발점 확인

Shield Advanced만 구독하면 네트워크 계층(패킷 수준) 공격은 막을 수 있지만, 애플리케이션 계층(Layer 7) 공격은 다른 처리가 필요하다. 애플리케이션 계층 공격은 정상 HTTP 요청처럼 생긴 요청을 대량으로 보내 서버의 CPU와 메모리를 소진시키는데, 패킷 자체는 정상이라 네트워크 장비가 가려낼 수 없다. 이런 공격을 막을 규칙이 전혀 없으면, 공격 트래픽과 정상 트래픽이 똑같이 애플리케이션에 도달해 서비스가 멈춘다.

2질문 제기

정상 요청처럼 위장한 HTTP 요청 폭주를 어떻게 구별해서 차단할 것인가?

3구조적 핵심 예시

CloudFront나 ALB에 연결된 AWS WAF 웹 ACL에 rate-based rule(짧은 시간 동안 같은 IP 주소에서 도착한 요청 수가 정해진 임계값을 넘으면 해당 IP를 일시적으로 차단하는 규칙) 하나를 추가하는 것이 대표적인 예다. 공격자가 봇으로 수천 개의 요청을 보내면 한 IP가 정상 사용자보다 훨씬 많은 요청을 만들고, 이 규칙이 그 IP의 트래픽을 일정 시간 차단해 애플리케이션 계층 폭주를 막는다.

4단계별 동작 과정

  1. 웹 ACL 생성 및 연결AWS WAF에서 웹 ACL을 만들고 보호할 리소스(CloudFront 배포, ALB, API Gateway 등)에 연결한다. 웹 ACL 없이는 어떤 규칙도 적용될 곳이 없다.
  2. rate-based rule 추가웹 ACL에 rate-based rule을 추가하고 임계값(예: 5분 동안 IP당 요청 2,000건)을 정한다. 임계값을 넘는 요청을 보낸 IP는 차단 목록에 올라간다.
  3. 차단 동작 확인임계값을 넘긴 IP의 추가 요청은 일정 시간 동안 차단되고, 정상 사용자 수준의 요청은 그대로 통과한다. 결과적으로 봇성 대량 요청만 걸러진다.

5본질 요약

WAF 웹 ACL에 rate-based rule을 두어 단일 IP의 요청 폭주를 탐지·차단함으로써 애플리케이션 계층 DDoS 공격을 막는 것

6단계 Shield Advanced 설정

Route 53 헬스 체크를 생성해 애플리케이션 가용성에 기반한 DDoS 이벤트 탐지와 완화가 동작하도록 구성한다.

1상대의 출발점 확인

기존 DDoS 대응은 트래픽 양과 패킷 특성만 보고 공격 여부를 판단한다. 그런데 대규모 공격이 아니어도 애플리케이션이 제대로 응답하지 못하는 상황이 생길 수 있고, 반대로 트래픽이 많아도 정상 영업 시간의 요청일 수 있다. 이렇게 트래픽 수치만으로는 애플리케이션이 실제로 살아 있는지 알 수 없어서, 오탐(정상을 공격으로 오인)이나 지연 탐지(이미 응답이 끊긴 뒤에야 감지)가 일어난다. 공격이 아니라 단순 장애로 서비스가 죽어도 DDoS 방어가 동작하지 않는다.

2질문 제기

트래픽 수치가 아니라 애플리케이션이 실제로 응답하는지, 즉 서비스 가용성 자체를 기준으로 공격을 탐지하려면 어떻게 해야 할까?

3구조적 핵심 예시

Route 53에서 헬스 체크(지정한 엔드포인트에 주기적으로 요청을 보내 응답이 정상인지 확인하는 기능)를 만들고, 이 헬스 체크를 애플리케이션의 엔드포인트(예: ALB의 URL이나 CloudFront 배포 주소)에 연결하는 것이 대표적인 예다. 헬스 체크가 응답 실패를 감지하면 이 정보가 Shield Advanced의 탐지에 반영되어, 트래픽 양과 관계없이 가용성 저하가 공격의 신호로 해석될 수 있다.

4단계별 동작 과정

  1. 헬스 체크 생성Route 53 콘솔에서 헬스 체크를 만들고, 검사할 엔드포인트(애플리케이션 주소)와 검사 주기·실패 기준을 설정한다. 헬스 체크는 주기적으로 그 주소에 요청을 보내 응답을 확인한다.
  2. Shield Advanced에 연결생성한 헬스 체크를 Shield Advanced의 헬스 기반 탐지 설정에 연결해, 헬스 체크 결과가 공격 탐지의 입력으로 쓰이게 한다.
  3. 가용성 기반 탐지 동작애플리케이션이 요청에 정상 응답하지 못하면 헬스 체크가 실패로 바뀌고, Shield Advanced가 이를 가용성 저하 신호로 감지해 완화 조치와 알림을 동작시킨다.

5본질 요약

Route 53 헬스 체크를 통해 애플리케이션의 실제 가용성을 주기적으로 확인하고, 그 결과를 Shield Advanced의 DDoS 탐지 기준에 연결하는 것

6Shield Advanced 설정06-05

알람과 알림 구성

CloudWatch 알람을 만들어 DDoS 공격 발생과 완화 상태를 이메일 등으로 통보받도록 알림을 설정한다.

1상대의 출발점 확인

Shield Advanced를 설정하고 나면 공격 탐지와 완화가 자동으로 일어나지만, 그 사실을 관리자가 알아채는 경로는 따로 없다. AWS 콘솔에 직접 들어가서 지표를 눈으로 확인하지 않는 한 공격이 오고 있는지, 완화가 끝났는지 전혀 알 수 없다. 사고 대응은 공격 발생 시점에 시작해야 하는데, 알림 수단이 없으면 공격이 끝난 뒤에야 상황을 알게 되는 문제가 생긴다.

2질문 제기

공격이 시작되고 완화되는 순간을 관리자가 즉시 알 수 있게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

CloudWatch 알람(CloudWatch Alarm)을 하나 만들어 보호 중인 리소스의 DDoS 지표를 감시한다. 예를 들어 "DDoS 공격 탐지" 지표(총 공격 트래픽 양)가 특정 임계값을 넘으면 알람이 ALARM 상태로 바뀌고, 연결된 SNS 주제(이메일을 받는 구독자를 가진 알림 채널)로 알림 메시지가 전송되어 관리자 이메일로 통보가 도착한다.

4단계별 동작 과정

  1. 지표 선택과 임계값 설정CloudWatch 콘솔에서 알람을 만들고, Shield Advanced가 내보내는 DDoS 관련 지표(예: DDoSDetected, 공격 완화 중 상태)를 고른 뒤 임계값을 정한다.
  2. SNS 주제 연결알림을 받을 SNS 주제(구독자에게 메시지를 배포하는 채널)를 만들고 이메일 구독을 추가한 뒤, 알람이 ALARM 상태일 때 이 주제로 메시지를 보내도록 알람에 연결한다.
  3. 알림 수신 확인공격 탐지나 완화 시작 시점에 알람이 울리고 이메일이 도착하는 것을 확인한다. "공격 없음" 상태로 돌아가는 알람도 별도로 만들어 완화 종료를 통보받을 수 있다.

완료 점검과 DDoS 대시보드

설정한 보호 구성을 점검·완료하고 DDoS 대시보드를 생성해 실시간 공격과 완화 상황을 모니터링한다.

1상대의 출발점 확인

Shield Advanced 설정은 보호 추가, 알람 구성, 선택적 AWS WAF 연동 등 여러 작업이 각각 흩어져 있는데, 각 설정이 제대로 들어갔는지 한눈에 확인하는 화면이 기본 제공되지 않는다. 설정 누락이 있어도 별도 오류가 뜨지 않기 때문에, 실제 공격이 들어오기 전까지는 보호가 빈틈인 채로 방치될 수 있다. 또 설정 완료 후에도 공격이 오고 있는지, 완화가 진행 중인지 보려면 매번 여러 콘솔을 오가야 하는 불편함이 있다.

2질문 제기

여러 설정이 빠짐없이 적용됐는지 점검하고, 공격과 완화 상황을 한 화면에서 지켜보려면 어떻게 해야 할까?

3구조적 핵심 예시

AWS WAF 콘솔의 Shield 메뉴에서 보호된 리소스 목록을 열어 각 리소스가 "보호됨(protected)" 상태인지 확인하고, 같은 화면에서 DDoS 대시보드(DDoS Dashboard)를 생성한다. 대시보드에는 DDoS 공격 탐지 건수, 완화 중인 공격, 최근 공격 이벤트 같은 지표가 그래프로 표시되어 공격 발생 시점부터 완화 종료까지의 흐름이 실시간으로 보인다.

4단계별 동작 과정

  1. 보호 상태 점검콘솔에서 리소스별 보호 상태를 확인한다. "보호됨"이 아닌 리소스가 있으면 보호 추가 절차로 돌아가 설정을 완료한다.
  2. 대시보드 생성DDoS 대시보드를 생성한다. 대시보드는 공격 트래픽 지표(탐지된 공격, 완화된 공격)를 자동으로 수집해 화면에 그래프로 배치한다.
  3. 상황 모니터링대시보드를 열어 실시간 공격 발생 여부와 완화 진행 상태를 확인한다. 알람과 연동하면 비정상 상황이 감지되는 순간 대시보드 확인과 이메일 통보가 함께 이뤄진다.

7리소스 보호 운영07-01

보호 추가·편집·해제·추적

Shield Advanced에서 리소스에 보호를 추가하고, 편집·해제하며, 보호 구성 변경을 추적하는 일련의 운영 절차.

1상대의 출발점 확인

리소스가 늘어날 때마다 매번 Shield Advanced 설정 전체를 처음부터 반복하면, 새 리소스를 보호 목록에 추가하는 것을 깜빡하거나 이미 보호가 필요 없어진 리소스를 그대로 둬 비용이 계속 나가는 문제가 생긴다. 또 누가 언제 보호를 추가했는지 기록이 남지 않으면, 보호 구성이 바뀌었을 때 원인을 추적하기 어렵다. 리소스 단위의 개별 관리 기능이 없으면 운영이 어려워진다.

2질문 제기

리소스마다 보호를 개별적으로 추가·편집·해제하고 그 변경 이력을 추적하려면 어떻게 해야 할까?

3구조적 핵심 예시

AWS WAF 콘솔의 보호된 리소스 목록(Protected Resources) 화면에서 대상 리소스를 선택하고 "보호 추가(Add protection)"를 누르면, 해당 리소스에 Shield Advanced 보호가 즉시 적용된다. 목록의 각 행에서 보호 상태를 편집하거나 "보호 해제"를 눌러 제거할 수 있고, 변경 내용은 AWS CloudTrail(계정의 API 호출 기록을 남기는 감사 서비스)에 기록되어 추적할 수 있다.

4단계별 동작 과정

  1. 보호 추가AWS WAF 콘솔에서 리소스 유형(CloudFront 배포, ALB, EC2 등)을 선택하고 보호할 리소스를 골라 추가한다. 보호 대상 수에 맞춰 비용 계산이 시작된다.
  2. 편집·해제보호된 리소스 목록에서 특정 리소스를 선택해 보호 구성을 편집하거나, 더 이상 보호가 필요 없는 리소스의 보호를 해제한다.
  3. 변경 이력 추적CloudTrail에서 보호 추가·편집·해제에 해당하는 API 호출 기록을 조회해 누가, 언제, 어떤 변경을 했는지 확인한다.

EC2·NLB 보호

Amazon EC2 인스턴스와 Network Load Balancer를 Shield Advanced가 보호하는 방식과 그 구성 방법.

1상대의 출발점 확인

CloudFront나 ALB 같은 앞단 서비스는 Shield Advanced가 트래픽을 검사할 수 있는 경로가 명확하지만, EC2 인스턴스와 Network Load Balancer(NLB)는 트래픽이 AWS의 중앙 완화 인프라를 거치지 않고 흐르는 구조라 보호 적용 방식이 다르다. EC2나 NLB를 그대로 두면 IP 기반 대용량 공격(전송 계층 DDoS)에 그대로 노출되고, 어디서 어떻게 보호가 걸리는지도 헷갈린다.

2질문 제기

중앙 완화 경로가 없는 EC2 인스턴스와 NLB의 전송 계층 트래픽은 어떻게 DDoS 공격에서 보호할까?

3구조적 핵심 예시

EC2 인스턴스의 탄력적 IP 주소(Elastic IP)를 Shield Advanced가 보호하도록 지정하면, AWS가 해당 IP로 들어오는 트래픽의 이상 패턴을 실시간 분석한다. 공격이 감지되면 AWS의 전송 계층 완화(흐름 기반 완화)가 그 IP로 향하는 대량 트래픽을 필터링해 인스턴스에 도달하기 전에 막는다. NLB는 해당 NLB의 IP 주소를 보호 목록에 추가하는 방식으로 같은 보호를 받는다.

4단계별 동작 과정

  1. 보호 대상 지정AWS WAF 콘솔에서 리소스 유형으로 EC2를 선택하고 보호할 인스턴스의 탄력적 IP를, 또는 NLB를 선택해 해당 로드 밸런서를 보호 목록에 추가한다.
  2. 트래픽 분석과 공격 탐지AWS가 보호 대상 IP로 들어오는 패킷의 양과 흐름을 분석해 DDoS 공격 패턴(대량 트래픽 급증 등)을 감지한다.
  3. 전송 계층 완화공격이 감지되면 AWS 네트워크 경계에서 해당 IP로 향하는 악성 트래픽을 필터링한다. 정상 트래픽은 그대로 통과시키고, EC2·NLB는 완화가 진행되는 동안에도 서비스를 계속 제공한다.

5본질 요약

애플리케이션 계층(L7) 보호

AWS WAF 웹 ACL과 연동하여 HTTP/HTTPS 같은 애플리케이션 계층(L7) 트래픽을 보호하는 방법.

1상대의 출발점 확인

전송 계층 보호는 패킷 단위의 대용량 공격을 막지만, HTTP/HTTPS 요청 자체를 악용하는 공격은 막지 못한다. 공격자가 정상적인 웹 요청 모양으로 대량의 요청을 보내면 전송 계층에서는 정상 트래픽과 구별이 안 되므로 완화가 걸리지 않는다. 애플리케이션 계층(HTTP 요청 내용, L7)에서 판단할 수 있는 규칙이 없으면, 요청 폭주로 웹 서버의 리소스만 고갈되는 공격에 그대로 노출된다.

2질문 제기

요청 내용을 봐야 잡아낼 수 있는 애플리케이션 계층 공격은 어떻게 완화할까?

3구조적 핵심 예시

Shield Advanced가 보호하는 CloudFront나 ALB에 AWS WAF 웹 ACL(요청마다 규칙을 검사해 허용·차단을 정하는 제어 목록)을 연결한다. 웹 ACL에 "국가별 접근 차단"이나 "특정 헤더가 없는 요청 차단" 같은 규칙을 넣어 두면, HTTP 요청 하나하나가 규칙 검사를 통과해야만 서버로 전달되고, 규칙에 걸린 악성 요청은 애플리케이션에 도달하기 전에 차단된다. Shield Advanced는 여기에 더해 웹 ACL로 완화된 공격에 대한 추가 비용까지 면제해 준다.

4단계별 동작 과정

  1. 웹 ACL 생성과 연결AWS WAF 콘솔에서 웹 ACL을 만들고, 이를 Shield Advanced가 보호하는 CloudFront 배포나 ALB에 연결한다.
  2. 규칙 검사웹 ACL이 들어오는 HTTP 요청마다 구성된 규칙(헤더·URI·IP 조건 등)을 적용해 정상 여부를 판정한다.
  3. 허용·차단 결정규칙에 부합하는 요청은 차단하고 나머지는 통과시켜 서버로 전달한다. 공격 요청은 애플리케이션 계층에서 걸러지므로 서버 리소스는 정상 트래픽 처리에만 사용된다.

5본질 요약

AWS WAF 웹 ACL을 보호 대상의 앞단에 연결해 HTTP/HTTPS 요청 내용을 규칙으로 검사하고, 규칙에 걸린 애플리케이션 계층 공격을 애플리케이션에 도달하기 전에 차단하는 것

rate-based rule 기반 보호

AWS WAF rate-based rule로 IP당 요청 비율을 제한해 애플리케이션 계층 공격을 완화하는 보호 방법.

1상대의 출발점 확인

고정 조건(IP 차단, 특정 표현 차단)만으로는 정상 요청과 구분하기 어려운 공격이 있다. 공격자가 여러 IP를 돌려 쓰면서 정상처럼 보이는 요청을 쏟아내면, 요청 하나하나는 정상이라 개별 규칙 검사만으로는 차단할 수 없다. 그러나 요청이 특정 수치를 넘어 쏟아지는 것 자체가 공격의 신호이므로, 개별 요청이 아니라 요청의 양을 기준으로 판단해야 하는 경우가 생긴다.

2질문 제기

요청 하나하나는 정상처럼 보여도, 양이 비정상적으로 많은 요청 폭주는 어떻게 차단할까?

3구조적 핵심 예시

웹 ACL에 rate-based rule(비율 기반 규칙)을 하나 만든다. 이 규칙은 "IP 주소당 5분 동안 2,000건을 초과하는 요청" 같은 임계값을 가지며, 같은 IP에서 보낸 요청 수가 임계값을 넘으면 그 IP의 요청을 일정 시간 동안 전부 차단한다. 정상 사용자가 보내는 요청은 임계값 아래라 통과하고, 요청을 대량으로 쏟아내는 클라이언트만 자동으로 제한된다.

4단계별 동작 과정

  1. 규칙 생성과 임계값 설정웹 ACL에 rate-based rule을 추가하고, IP당 허용할 요청 수와 집계 시간(예: 5분)을 정한다.
  2. 요청 수 집계웹 ACL이 각 IP의 요청 수를 시간 창 단위로 계속 집계한다. 임계값을 넘는 IP가 있는지 매 요청마다 확인한다.
  3. 과다 IP 차단임계값을 넘긴 IP의 후속 요청을 차단하고, 일정 시간(차단 기간)이 지나 요청 수가 임계값 아래로 내려가면 다시 통과시킨다.

5본질 요약

자동 애플리케이션 계층 완화

1상대의 출발점 확인

기존 방식에서는 애플리케이션 계층 공격(HTTP 요청을 악용해 서버 자원을 소모시키는 공격)을 막으려면 AWS WAF 규칙을 사람이 직접 만들고, 공격이 탐지되면 운영자가 수동으로 규칙을 활성화하거나 조정해야 한다. 탐지가 되어도 완화(차단)가 늦어지면 공격 요청이 계속 들어오면서 서버 자원이 그 시간만큼 더 소모된다. 사람이 개입하는 동안에도 공격은 멈추지 않으므로, 탐지에서 차단까지 걸리는 시간이 곧 피해 규모를 결정한다.

2질문 제기

애플리케이션 계층 공격이 탐지된 즉시, 사람이 손대지 않아도 차단 규칙이 자동으로 적용되게 하려면?

3구조적 핵심 예시

Shield Advanced가 특정 애플리케이션 계층 공격을 탐지하면, AWS가 미리 준비해 둔 AWS WAF 규칙이 해당 리소스에 자동으로 연결되어 그 공격 패턴에 맞는 요청을 차단한다. 운영자는 규칙이 자동으로 활성화되었다는 알림을 받고, 공격이 끝나면 그 규칙은 자동으로 해제되어 평소 상태로 돌아간다.

4단계별 동작 과정

  1. 공격 탐지Shield Advanced가 애플리케이션 계층(HTTP 요청 수준)에서 DDoS 공격으로 판단되는 트래픽 패턴을 감지한다.
  2. 규칙 자동 활성화AWS가 준비한 AWS WAF 규칙(웹 요청을 검사해 차단하는 규칙)이 보호된 리소스의 웹 ACL에 자동으로 추가되어 공격 요청을 차단하고, 운영자에게 활성화 사실이 알림으로 전달된다.
  3. 완화 해제공격이 종료되면 자동으로 활성화된 규칙이 해제되어 평소 트래픽 흐름으로 돌아간다.

헬스 기반 탐지와 헬스 체크

Route 53 헬스 체크를 보호된 리소스에 연결해 리소스 상태를 기준으로 DDoS 이벤트를 감지하는 방법.

1상대의 출발점 확인

기존 방식에서는 트래픽의 양이나 패턴만 보고 DDoS 공격 여부를 판단한다. 그런데 리소스가 정상인데 일시적으로 트래픽이 늘어난 경우에는 정상 상황을 공격으로 잘못 판단하는 오탐이 생길 수 있고, 반대로 서버가 이미 다운되어도 트래픽 수치에 변화가 나타나기 전까지는 판단이 늦어진다. 트래픽 수치만으로는 리소스가 실제로 정상 응답을 하고 있는지 알 수 없다는 것이 한계다.

2질문 제기

리소스 자체의 상태(헬스)를 기준으로 DDoS 공격 여부를 더 정확하게 판단할 수는 없을까?

3구조적 핵심 예시

보호된 리소스(예: 애플리케이션 서버)에 Route 53 헬스 체크(주기적으로 해당 리소스가 정상 응답을 하는지 확인하는 검사)를 연결해 둔다. 헬스 체크가 실패하기 시작하면 Shield Advanced가 이를 공격 신호로 보고 DDoS 이벤트를 발생시킨다. 트래픽 그래프만 보던 기존 방식과 달리, 리소스가 실제로 응답하지 못하는 상태를 직접 기준으로 삼는 것이다.

4단계별 동작 과정

  1. 헬스 체크 연결보호된 리소스에 Route 53 헬스 체크(정상 응답 여부를 주기적으로 점검하는 검사)를 만들어 연결한다.
  2. 상태 감시와 이벤트 생성헬스 체크가 실패하면 Shield Advanced가 리소스에 장애나 공격이 발생했을 가능성이 높은 상태로 판단해 DDoS 이벤트를 생성하고 대시보드에 표시한다.
  3. 완화 연계생성된 이벤트를 바탕으로 자동 완화(예: 자동 애플리케이션 계층 완화)가 함께 작동할 수 있는 기준이 된다.

5본질 요약

트래픽 수치가 아니라 리소스가 실제로 정상 응답하는지(헬스)를 기준으로 DDoS 이벤트를 감지해 탐지 정확도를 높이는 것

보호 그룹

여러 보호된 리소스를 하나의 그룹으로 묶어 함께 관리하고 완화 기준을 일괄 적용할 수 있는 Shield Advanced 기능.

1상대의 출발점 확인

기존 방식에서는 리소스를 개별적으로 보호했기 때문에, 리소스가 늘어날수록 각각에 대해 완화 기준을 일일이 설정해야 한다. 로드 밸런서와 CloudFront 배포가 수십 개가 되면 설정이 중복되고, 일부 리소스에만 기준이 적용되어 보호 수준이 리소스마다 달라진다. 리소스별로 관리하다 보면 어느 리소스에 어떤 기준이 적용되어 있는지 파악하는 것도 어려워진다.

2질문 제기

여러 보호된 리소스를 하나로 묶어 완화 기준을 한 번에 일괄 적용할 수는 없을까?

3구조적 핵심 예시

운영 중인 웹 애플리케이션 앞의 CloudFront 배포 3개와 로드 밸런서 5개를 하나의 보호 그룹으로 묶는다. 이후 이 그룹에 완화 기준(예: 자동 애플리케이션 계층 완화 적용)을 설정하면, 그룹에 속한 모든 리소스에 같은 기준이 한 번에 적용된다. Shield Advanced는 그룹 단위로 공격 활동을 종합해 알려준다.

4단계별 동작 과정

  1. 그룹 생성과 리소스 추가보호 그룹을 만들고 보호된 리소스들을 그룹에 추가하거나, 태그(리소스에 붙이는 분류 표시)를 기준으로 리소스가 자동으로 그룹에 포함되게 한다.
  2. 기준 일괄 적용그룹에 완화 기준과 알림 설정을 적용하면 그룹의 모든 리소스에 동일하게 적용된다.
  3. 그룹 단위 모니터링Shield Advanced가 그룹 전체의 공격 활동을 한눈에 보여주고, 그룹에 속한 리소스들의 공격 이벤트를 함께 관리한다.

SRT 지원 구성

Shield Advanced 가 SRT(Shield Response Team)가 DDoS 대응 중 계정에 접근할 수 있도록 권한을 부여하는 설정이다.

1상대의 출발점 확인

기존 방식에서는 DDoS 공격이 발생해도 AWS 측 전문가 팀이 고객 계정이나 보호 설정에 접근할 수 없었다. 전문가의 도움을 받으려면 매번 어떤 권한이 필요한지 설명하고 승인 절차를 거쳐야 하므로 대응이 늦어진다. 공격이 진행 중일 때는 그 지연 시간이 곧 피해 시간이 된다.

2질문 제기

DDoS 공격 대응이 필요할 때 AWS 보안 전문가 팀(SRT)이 바로 계정에 접근해 도와줄 수 있게 하려면?

3구조적 핵심 예시

계정에 SRT(Shield Response Team, AWS의 DDoS 대응 전문가 팀)가 사용할 수 있는 IAM 역할(권한 범위를 정의해 둔 역할)을 만들어 두고, 그 역할을 SRT에 연결해 둔다. 공격이 발생하면 SRT가 이 역할로 계정에 접근해 보호 설정과 완화 조치를 바로 수행하고, 운영자는 그 접근 사실을 기록으로 확인할 수 있다.

4단계별 동작 과정

  1. 역할 생성AWS IAM에서 SRT 전용 역할(이 팀이 맡을 권한 범위가 정의된 역할)을 만든다.
  2. 권한 부여와 위임보호된 리소스와 관련 설정에 접근할 수 있도록 역할에 필요한 권한을 부여하고, 그 역할을 SRT에 연결(위임)한다.
  3. 접근과 감사공격 대응 시 SRT가 이 역할로 계정에 접근해 작업하고, 모든 접근과 작업은 CloudTrail(계정 활동을 기록하는 서비스)에 남아 운영자가 추적할 수 있다.

5본질 요약

SRT가 공격 대응 중 계정에 접근할 수 있는 전용 권한(역할)을 미리 만들어 위임해 두어, 대응이 시작되자마자 전문가가 바로 조치를 취할 수 있게 하는 것

사전 대응(Proactive Engagement)

공격 임계값을 넘는 사건이 감지되면 SRT 가 먼저 나서서 대응하도록 연락 채널을 연결하는 기능이다.

1상대의 출발점 확인

기존 방식에서는 공격이 발생한 뒤 고객이 SRT에 연락하거나, 직접 대시보드를 보고 대응을 요청해야 했다. 공격이 진행되는 동안에도 대응이 시작되기까지 시간이 걸리고, 고객이 아직 인지하지 못한 공격 신호는 놓칠 수 있다. 대응 시작 시점이 고객의 발견 속도에 의존한다는 것이 한계다.

2질문 제기

공격 임계값을 넘는 사건이 감지되면 고객이 요청하기 전에 SRT가 먼저 나서서 대응하게 하려면?

3구조적 핵심 예시

계정에 사전 대응 설정을 켜고 연락 채널(Slack 또는 이메일)을 등록해 둔다. Shield Advanced가 설정한 임계값을 넘는 이상 징후를 감지하면 SRT가 먼저 고객에게 연락해 상황을 알리고 대응 가능 여부를 확인한다. 고객이 공격을 눈치채기 전에 전문가 대응이 시작된다.

4단계별 동작 과정

  1. 설정과 채널 연결사전 대응을 활성화하고, SRT가 연락할 채널(Slack 같은 메신저 또는 이메일)을 계정에 연결한다.
  2. 임계값 초과 감지Shield Advanced가 공격으로 판단되는 임계값을 넘는 사건을 감지하면 SRT에 이를 알린다.
  3. 선제 대응SRT가 고객에게 먼저 연락해 사건 내용을 공유하고, 합의된 범위에서 완화 조치를 시작한다.

5본질 요약

고객의 요청을 기다리지 않고, 임계값을 넘는 공격 신호가 감지되면 SRT가 먼저 연락해 대응을 시작함으로써 공격 초기부터 개입하는 것

SRT 연락과 사용자 지정 완화

공격 발생 시 SRT 에 연락하는 방법과 SRT 가 해당 리소스에 적용할 사용자 지정 완화 설정을 만드는 절차다.

1상대의 출발점 확인

SRT에 권한을 위임하고 사전 대응을 설정해도, 실제 공격이 발생했을 때 어떤 리소스가 공격받고 있고 어떤 방식으로 막을지에 대한 구체적인 전달이 없으면 SRT가 취할 수 있는 조치는 한정적이다. 공격 유형마다 최적의 차단 규칙이 다르므로, 기본 완화 규칙으로는 막기 어려운 변형 공격이 있을 수 있다는 것이 한계다.

2질문 제기

공격이 발생했을 때 SRT에 연락하는 방법과, 공격 유형에 맞춘 사용자 지정 완화(커스텀 차단 규칙)를 적용하는 절차는 어떤가?

3구조적 핵심 예시

공격이 발생하면 운영자가 지원 티켓(Case)을 열고 SRT에 공격받는 리소스와 증상을 알린다. SRT는 해당 리소스의 트래픽을 분석한 뒤, 그 공격 패턴에 맞는 사용자 지정 완화(예: 특정 요청 헤더나 지리적 출처를 차단하는 규칙)를 만들어 적용한다. 기본 규칙으로 막히지 않는 변형 공격까지 막는 것이 목적이다.

4단계별 동작 과정

  1. 연락과 정보 공유운영자가 AWS Support Case로 SRT에 연락해 공격받는 리소스와 관찰된 공격 패턴을 전달한다.
  2. 분석과 사용자 지정 완화 설계SRT가 트래픽을 분석해 공격 유형에 맞는 사용자 지정 완화(기본 완화로 커버되지 않는 공격을 막는 맞춤 규칙)를 설계한다.
  3. 적용과 해제설계된 완화가 해당 리소스에 적용되어 공격을 차단하고, 공격이 끝나 평소 트래픽으로 돌아오면 완화를 해제한다.

5본질 요약

공격 발생 시 SRT에 연락하는 창구와, 공격 유형 분석에 기반한 사용자 지정 완화를 적용하는 절차를 제공해 기본 완화로 막지 못하는 공격까지 대응하는 것

IAM 정책으로 사용자·역할별로 Shield 콘솔과 API 접근을 세밀하게 허용·제한하는 권한 관리 체계.

기존에는 Shield Advanced를 사용하는 계정의 모든 사용자가 같은 권한을 갖는 구조였다. 계정의 자격 증명(로그인 정보)을 가진 사람이라면 누구나 보호 설정을 조회하고 변경할 수 있었기 때문에, 운영 담당자만 보호를 끄고 나머지 팀원은 조회만 해야 하는 상황을 만들 수 없었다. 권한이 과도하게 열려 있으면 실수나 내부 악용으로 보호 설정이 바뀌어도 막을 방법이 없었고, "누가 무엇을 할 수 있는지"를 한곳에서 관리하기도 어려웠다.

2질문 제기

사용자·역할별로 Shield 콘솔과 API에 대한 접근 권한을 세밀하게 나누어, 필요한 사람에게만 필요한 만큼만 허용할 수는 없을까?

3구조적 핵심 예시

운영 담당자에게는 보호를 생성·수정·삭제하는 권한(shield:CreateProtection, shield:UpdateProtection 등)을 주고, 일반 개발자에게는 조회 권한(shield:ListProtections)만 주는 IAM 정책 두 개를 만든다. 그리고 각 사용자·그룹에 이 정책을 연결한다. 이후 운영 담당자는 보호 설정을 바꿀 수 있지만 개발자는 조회만 가능하며, 잘못된 권한 부여는 IAM에서 정책을 수정하는 것만으로 즉시 반영된다.

4단계별 동작 과정

  1. 정책 작성IAM 콘솔에서 Shield API 작업(예: 생성·조회·삭제)별로 허용 여부를 적은 JSON 기반 정책을 만든다.
  2. 정책 연결이 정책을 사용자, 그룹, 또는 역할에 연결해 각 주체(접근 주체, 즉 권한을 받는 대상)의 권한 범위를 정한다.
  3. 접근 판단사용자가 Shield 콘솔이나 API를 호출하면 IAM이 그 사용자에게 연결된 정책과 요청을 대조해 허용 여부를 결정하고, 허용된 작업만 실행된다.

Shield가 다른 AWS 서비스를 대신 보호·관리할 수 있도록, AWS가 미리 정의해 둔 안전한 권한 역할을 자동으로 만들고 관리할 수는 없을까?

3구조적 핵심 예시

Shield Advanced를 처음 활성화하면 AWS가 AWSServiceRoleForShield라는 서비스 연결 역할을 자동 생성한다. 이 역할에는 Shield가 CloudFront와 Route 53의 리소스를 조회·보호하는 데 필요한 권한만 정확히 담겨 있다. 관리자는 역할을 직접 만들거나 정책을 작성할 필요가 없고, 이 역할 덕분에 Shield 콘솔에서 보호할 리소스를 선택하기만 하면 해당 서비스의 리소스를 가져와 보호 대상으로 등록할 수 있다.

4단계별 동작 과정

  1. 역할 자동 생성Shield Advanced를 활성화하면 AWS가 서비스 연결 역할 AWSServiceRoleForShield를 자동으로 만든다.
  2. 권한 위임Shield가 이 역할을 사용해 CloudFront, Route 53 등 보호 대상 서비스의 리소스 목록을 조회하고 보호 설정을 적용한다.
  3. 역할 관리 위임역할 생성·정책 작성·회전(자격 증명 교체)을 AWS가 관리하므로 관리자가 직접 할 일이 없고, 리소스가 정리되면 역할도 정리된다.

5본질 요약

AWS가 미리 정의한 서비스 연결 역할을 자동 생성해, Shield가 다른 AWS 서비스의 리소스를 최소한의 필요한 권한으로 안전하게 대신 보호·관리할 수 있게 하는 것

데이터 보호와 규정 준수

Shield가 취급하는 데이터의 암호화·보존 방식과 SOC, PCI 등 규정 준수 요건을 다루는 보안 기반.

1상대의 출발점 확인

Shield Advanced는 보호 대상을 등록할 때 리소스 정보, 호출 기록, 설정 내역 등 민감한 데이터를 취급한다. 기존에는 이런 데이터가 어떤 방식으로 암호화·보존되는지, 특정 규정(예: SOC, PCI)을 지키는지가 명확히 정리되어 있지 않아서, 규제 대상 서비스를 운영하는 기업은 "이 데이터를 써도 되는지"를 내부 보안 검토로 일일이 판단해야 했다. 감사 준비 과정에서 요구되는 증빙 자료를 만들기도 어려웠다.

2질문 제기

Shield가 취급하는 데이터가 어떤 암호화·보존 방식으로 보호되고, 어떤 규정 준수 요건을 충족하는지 확인할 수는 없을까?

3구조적 핵심 예시

Shield가 주고받는 데이터는 전송 중에는 TLS로 암호화되고, 저장되는 데이터는 AWS의 관리형 키로 암호화된다. 예를 들어 DDoS 공격 대응 로그나 보호 설정 정보가 저장될 때 암호화가 적용되며, 규정 측면에서는 AWS가 SOC, PCI 등 인증 프로그램에 Shield를 포함시켜 감사 범위를 정해 둔다. 기업은 이 내용을 AWS 문서에서 확인한 뒤 자체 보안·규정 검토에 그대로 사용할 수 있다.

4단계별 동작 과정

  1. 전송·저장 암호화Shield와 AWS 서비스 간 데이터는 TLS로 전송되고, 저장 데이터는 암호화 키로 보호된다.
  2. 규정 준수 범위 확인AWS가 SOC, PCI 등 인증 프로그램에서 Shield를 취급하는 방식을 문서로 제공해, 기업이 준수 요건 충족 여부를 판단할 근거를 얻는다.
  3. 보안 검토 적용기업은 이 정보를 내부 보안·감사 검토에 활용해 Shield 사용을 규정에 맞게 승인하고 증빙 자료를 만든다.

5본질 요약

Shield가 취급하는 데이터를 암호화·보존 방식으로 보호하고, AWS의 규정 준수 인증 범위에 포함시켜 기업이 보안 요건 충족을 확인할 수 있게 하는 보안 기반

조직 전체 관리(Firewall Manager)

AWS Firewall Manager로 조직의 여러 계정과 리소스에 Shield Advanced 보호 정책을 중앙에서 일괄 적용·감사하는 기능.

1상대의 출발점 확인

기존에는 조직에 속한 여러 AWS 계정이 각자 Shield Advanced 보호를 따로 설정했다. 계정마다 담당자가 보호 정책을 직접 만들고 유지해야 했기 때문에, 보호가 적용된 계정과 빠진 계정이 뒤섞였고, 신규 리소스가 추가될 때마다 보호 등록을 잊는 일이 반복되었다. 또한 수십 개 계정 전체에 똑같은 보호 규칙이 적용되고 있는지 한눈에 감사할 방법이 없어, 조직 차원의 보안 수준을 일정하게 유지하기 어려웠다.

2질문 제기

여러 계정과 수많은 리소스에 Shield Advanced 보호 정책을 한곳에서 일괄 적용하고, 적용 상태를 조직 전체에서 감사할 수는 없을까?

3구조적 핵심 예시

조직의 중앙 관리 계정에서 Firewall Manager에 Shield Advanced 보호 정책을 하나 만든다. 이 정책에 "조직 내 모든 CloudFront 배포에 Shield Advanced 보호를 적용"이라고 범위를 지정하면, Firewall Manager가 조직의 모든 계정을 검사해 해당 조건의 리소스를 찾아 자동으로 보호를 적용한다. 나중에 새 계정이나 새 리소스가 생겨도 정책 조건에 맞기만 하면 자동으로 보호 대상이 되고, 적용 여부는 정책 대시보드에서 한눈에 확인할 수 있다.

4단계별 동작 과정

  1. 정책 생성·범위 지정Firewall Manager에서 Shield Advanced 보호 정책을 만들고, 적용할 계정 범위와 리소스 유형(예: CloudFront, ALB)을 지정한다.
  2. 자동 탐지·적용Firewall Manager가 조직의 계정을 스캔해 조건에 맞는 리소스를 찾아 Shield Advanced 보호를 자동 적용하고, 위반(보호 미적용) 상태를 보고한다.
  3. 중앙 감사·유지정책 대시보드에서 전체 적용 현황을 확인하고, 새 리소스·계정도 정책 조건에 따라 자동 관리되어 조직 전체의 보호 수준이 유지된다.

쿼터와 API 사용

Shield Advanced가 리소스 유형별로 두는 사용 한도(쿼터)와, AWS API·SDK로 Shield를 프로그래밍 방식으로 제어하는 방법.

1상대의 출발점 확인

기존에는 Shield Advanced의 리소스(보호 대상, 규칙 등)를 어디까지 만들 수 있는지, 한 번에 많은 API 호출을 보내면 어떻게 되는지가 사용자에게 명확히 공개되어 있지 않았다. 계정마다 만들 수 있는 보호 대상 수가 정해져 있다는 사실을 모른 채 리소스를 계속 추가하면 어느 순간 생성이 실패하고, 예상치 못한 오류가 나도 원인을 파악하기 어려웠다. 또 프로그래밍 방식으로 Shield를 제어하려면 API 사용법을 따로 찾아야 했다.

2질문 제기

Shield Advanced가 리소스 유형별로 두는 사용 한도(쿼터)를 미리 알고, API·SDK로 프로그래밍 방식으로 제어하는 방법을 확인할 수는 없을까?

3구조적 핵심 예시

Shield Advanced에는 리소스 유형별로 기본 쿼터가 있다. 예를 들어 계정당 만들 수 있는 보호 대상 수가 정해져 있어서, 그 수를 넘기면 새 보호 대상을 만들려는 API 호출이 오류와 함께 거부된다. 사용자는 AWS 문서에서 이 한도를 확인하고, 필요하면 증가를 요청할 수 있다. 또한 Shield는 모든 기능을 REST API로 제공하므로, 콘솔 대신 AWS CLI나 SDK로 보호 대상을 만들고 조회하며, 공격 탐지·완화 상태를 자동으로 가져오는 프로그램을 작성할 수 있다.

4단계별 동작 과정

  1. 쿼터 확인AWS 문서나 지원 요청을 통해 계정에 적용된 리소스 유형별 사용 한도를 확인하고, 한도 초과 시 증가를 요청한다.
  2. API 호출AWS CLI·SDK로 Shield API(예: 보호 대상 생성·조회, 공격 정보 확인)를 호출해 원하는 작업을 수행한다.
  3. 한도 관리·자동화한도에 가까워지면 불필요한 리소스를 정리하거나 증가를 요청하고, API 호출을 스크립트로 묶어 보호 상태 점검·대응을 자동화한다.

5본질 요약

Shield Advanced가 리소스 유형별 사용 한도(쿼터)를 두어 생성을 제어하고, API·SDK로 모든 기능을 프로그래밍 방식으로 제어·자동화할 수 있게 하는 것
