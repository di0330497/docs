1부. API Gateway 기초001

API Gateway란

서버를 직접 앞에 두지 않고 API 요청을 받아 뒤 서비스로 넘기는 관리형 서비스가 무엇인지 이해합니다

회사에서 서비스를 여러 개로 나눠 운영하면 클라이언트는 회원 서비스, 주문 서비스, 결제 서비스의 주소와 인증 방식을 각각 알아야 하고, 그중 하나가 주소를 바꾸면 앱을 다시 배포해야 합니다. API Gateway(에이피아이 게이트웨이)는 이런 요청을 한 곳에서 받아 뒤쪽 서비스로 넘기는 관리형 서비스를 말하며, 클라우드에서 서버를 직접 세우지 않고도 이 앞단을 얻을 수 있게 해줍니다.

이것은 큰 건물의 로비 안내데스크와 같습니다. 방문객은 사무실마다 위치를 몰라도 로비에서 한 번만 접수하면 되고, 안내데스크는 출입증을 확인한 뒤 목적지 사무실로 안내합니다.

이때 방문객이 클라이언트, 안내데스크가 게이트웨이, 사무실들이 뒤에 있는 서비스에 해당하며, 출입증 확인은 인증, 목적지로 보내는 일은 라우팅(요청을 알맞은 대상으로 연결하는 것)이라고 부릅니다. 안내데스크가 바뀌어도 방문객의 동선은 그대로이듯, 뒤 서비스의 주소가 바뀌어도 클라이언트가 아는 주소는 하나로 유지됩니다.

정리하면 API Gateway는 API 요청을 받는 단일 창구로, 인증과 라우팅 같은 공통 일을 대신 처리하고 실제 업무는 뒤 서비스에 맡기는 관리형 앞단입니다.

1부. API Gateway 기초002

API Gateway가 필요한 이유

API 서버를 직접 세우지 않고 운영할 때 무엇이 편해지는지 설명합니다

서비스를 세 개로 나눠 두면 인증 코드가 세 곳에 복사되고, 로그는 서버마다 다른 형식으로 흩어지며, 장애가 났을 때 어느 서비스가 문제인지 찾는 데만 한나절이 걸립니다. API Gateway가 필요한 이유는 이런 공통 작업을 요청이 들어오는 첫 지점 한 곳으로 모아, 뒤 서비스가 자기 업무에만 집중하게 만들기 위해서입니다.

아파트 단지의 경비실을 떠올리면 이해가 쉽습니다. 외부인이 동마다 직접 들어가 출입증을 검사하고 택배를 받는다면 규칙이 제각각이 되고 기록도 남지 않지만, 정문 경비실 한 곳에서 출입증을 확인하고 방문할 동을 안내하고 택배를 보관하면 단지 전체의 규칙이 하나로 정리됩니다.

여기서 경비실이 게이트웨이, 세대가 뒤 서비스, 출입증 확인이 인증, 방문 기록이 로그와 모니터링에 대응합니다. 관리 규칙이 바뀌어도 세대마다 문을 고칠 필요 없이 경비실 지침만 바꾸면 되는 것과 같습니다.

결국 API Gateway의 값어치는 기능 하나를 더하는 데 있지 않고, 인증과 로그, 모니터링 같은 공통 관심사를 한 계층으로 걷어내 운영 비용과 변경 비용을 줄이는 데 있습니다.

1부. API Gateway 기초003

API Gateway의 구성 요소

API, 리소스, 메서드, 스테이지가 어떻게 맞물려 동작하는지 큰 그림을 잡습니다

API Gateway를 쓰기로 하면 콘솔에서 가장 먼저 마주치는 것이 API, 리소스, 메서드, 스테이지라는 네 이름이고, 이 관계를 모른 채 화면만 따라가면 배포했는데 왜 404 응답이 오는지 알 수 없습니다. 이 네 가지는 하나의 식당을 운영하는 방식과 똑같이 맞물려 있습니다.

API는 식당 그 자체로, 손님이 찾아올 하나의 간판과 주소를 뜻합니다. 리소스는 메뉴판의 항목처럼 주문 하나가 가리키는 대상이고, 여기서는 주소 경로로 표현되는 자원입니다.

메서드는 그 항목에 무엇을 하겠다는 동작으로, 조회와 생성, 수정, 삭제에 해당하는 GET, POST, PUT, DELETE가 대표적입니다. 스테이지는 같은 식당을 홀 영업용과 포장 영업용으로 나눠 운영하는 것처럼, 같은 API를 개발용과 운영용으로 따로 배포해 설정을 달리 가져가는 단위입니다.

정리하면 API가 전체 틀, 리소스가 대상, 메서드가 동작, 스테이지가 배포 환경이며, 요청은 이 네 층을 차례로 통과해 뒤 서비스에 도착합니다.

1부. API Gateway 기초004

관리형 API 서비스의 책임 범위

게이트웨이가 대신 해 주는 일과 내가 직접 해야 하는 일을 구분합니다

관리형 서비스를 쓰면 서버 패치도, 장비 교체도 알아서 해 주리라 기대하기 쉽지만, 실제로는 게이트웨이가 대신 해 주는 일과 내가 직접 해야 하는 일이 분명히 갈려 있어 이 경계를 모르면 장애 때 책임 소재도 못 찾습니다. API Gateway의 책임 범위는 이 경계를 이해하는 데서 시작합니다.

임대 아파트에 사는 경우를 생각하면 쉽습니다. 건물주는 엘리베이터와 수도관, 외벽, 정문 경비 같은 공용 설비를 유지하고, 세입자는 자기 집 문 잠금장치와 가구, 생활 규칙을 스스로 관리합니다.

여기서 게이트웨이가 건물주, 내 API 설정과 뒤 서비스가 세입자에 해당하며, 요청을 받아 넘기는 배관과 정문 경비는 게이트웨이가 책임지는 구간입니다. 다만 어느 요청을 어떤 서비스로 보낼지, 어떤 키로 인증할지, 사용량 제한을 어떻게 둘지는 세입자 몫으로 남습니다.

결국 게이트웨이는 가용성과 확장, 기반 소프트웨어 유지 같은 아래쪽을 맡고, API 정의와 인증 방식, 뒤 서비스의 동작과 데이터는 내가 책임지는 위쪽으로 남는다는 것이 관리형 서비스의 기본 구도입니다.

1부. API Gateway 기초005

API Gateway와 로드 밸런서의 차이

둘 다 앞단에 있지만 무엇을 기준으로 요청을 나누는지 비교합니다

서버를 여러 대로 늘려 두고도 사용자가 특정 주소만 계속 호출하면 한 대에만 부하가 몰리고, 반대로 주소를 나눠 주면 사용자는 서비스마다 다른 주소를 외워야 합니다. 앞단에 무엇을 두면 이 문제가 풀리는지 헷갈리기 쉬운데, 로드 밸런서와 API Gateway는 요청을 나누는 기준이 서로 다릅니다.

마트를 떠올려 보면 차이가 분명해집니다. 계산대가 여러 개 있을 때 손님을 빈 계산대로 고르게 보내는 안내원이 로드 밸런서라면, 무엇을 사러 왔는지에 따라 식품관과 가전관으로 길을 알려 주는 안내데스크가 API Gateway입니다.

안내원은 손님이 누구인지, 무엇을 사는지 보지 않고 오직 어느 계산대가 비었는지만 보고, 안내데스크는 요청의 경로와 내용을 읽어 목적지를 정합니다. 그래서 계산대를 하나 늘리면 안내원의 배분 대상만 늘지만, 매장을 하나 새로 열면 안내데스크의 안내 규칙이 함께 바뀝니다.

정리하면 로드 밸런서는 같은 역할을 하는 서버들 사이에서 부하를 분산하는 장치이고, API Gateway는 서로 다른 서비스들 사이에서 요청의 목적지를 판단하는 라우팅 계층이며, 실제 구성에서는 게이트웨이 뒤에 로드 밸런서가 함께 놓이는 경우가 많습니다.

1부. API Gateway 기초006

API Gateway와 리버스 프록시의 관계

요청을 대신 받아 넘기는 프록시 계층의 원리를 게이트웨이에 대입합니다

클라이언트가 뒤쪽 서버의 주소를 직접 알고 호출하면 내부 구조가 그대로 드러나고, 서버를 옮길 때마다 클라이언트를 고쳐야 합니다. 리버스 프록시(reverse proxy)는 이런 요청을 대신 받아 안쪽 서버로 전달하는 중계 계층이고, API Gateway는 그 중계 위에 인증과 라우팅, 사용량 관리 같은 기능을 얹은 것이라고 볼 수 있습니다.

회사 대표 전화를 떠올리면 관계가 잘 드러납니다. 외부인은 대표번호 하나만 알고 걸면 교환수가 부서를 확인해 내선으로 연결해 주며, 외부에는 내선 번호가 보이지 않습니다.

여기서 교환수가 리버스 프록시, 부서들이 뒤 서비스, 내선 연결이 프록시의 전달에 해당합니다. 게이트웨이는 여기에 더해 걸려온 사람이 거래처인지 확인하고, 통화 기록을 남기고, 부서별 통화량 한도를 두는 일까지 맡는 교환수라고 생각하면 됩니다.

결국 리버스 프록시는 요청을 대신 받아 넘기는 일반 원리이고, API Gateway는 그 원리를 API 관리 기능까지 확장한 구현이며, 그래서 게이트웨이를 프록시의 한 종류로 설명하기도 합니다.

서버리스 아키텍처에서의 역할

Lambda와 함께 쓸 때 게이트웨이가 맡는 부분을 이해합니다

아파트 단지에 비유하면 각 세대는 요청을 처리하는 Lambda 함수이고, 단지 정문의 경비 초소가 API Gateway입니다. 방문객은 세대마다 직접 문을 두드리는 대신 초소에서 용건을 말하고, 초소는 신분증을 확인한 뒤 해당 세대에만 연락을 넣습니다. 세대가 늘거나 주소가 바뀌어도 방문객은 정문 하나만 알면 되고, 초소는 방문 기록을 남겨 문제가 생겼을 때 되짚을 수 있습니다.

정리하면 API Gateway는 인증과 경로 분기, 호출량 제한, 로그 기록을 함수 바깥에서 대신 맡고 요청을 알맞은 Lambda로 넘기는 앞단 관문입니다. 덕분에 함수는 비즈니스 로직에만 집중할 수 있습니다.

여러 서비스를 하나의 입구로 묶는 이유와 얻는 점을 설명합니다

서비스를 기능별로 잘게 나누면 각 팀이 따로 배포할 수 있어 편하지만, 고객 입장에서는 접속 주소가 계속 늘어나고 어느 서버가 살아 있는지 알 수 없게 됩니다. 이 문제를 하나의 입구로 정리하는 장치가 마이크로서비스 앞단의 API Gateway입니다.

덕분에 내부 구조를 자주 바꿔도 방문객이 외워야 할 주소는 하나로 유지됩니다.

실제로 API Gateway는 경로와 호스트 이름에 따라 요청을 알맞은 서비스로 라우팅하고, 인증과 사용량 제한, 로그 수집을 한곳에서 처리합니다. 클라이언트는 서비스 내부 구성이 바뀌어도 하나의 주소만 바라보면 됩니다.

API Gateway 요금 구조

요청 수와 데이터 전송량, 캐시 요금이 어떻게 붙는지 계산 감각을 잡습니다

택배 요금에 비유하면 이해가 쉽습니다. 택배는 보낸 건수마다 기본요금이 붙고, 짐이 무거울수록 추가 요금이 붙으며, 물건을 창고에 보관하면 보관료가 따로 나옵니다. API Gateway도 마찬가지로 호출 건수에 따라 요금이 매겨지고, 주고받은 데이터 양이 많을수록 전송 요금이 늘어나며, 응답을 캐시에 담아 두면 캐시 시간과 용량에 대한 요금이 더해집니다.

캐시를 켜면 원본 호출이 줄어 요청 요금은 내려갈 수 있으므로, 두 항목을 함께 견줘야 합니다.

정리하면 비용은 호출 횟수와 오간 데이터 양, 그리고 캐시를 켰는지에 따라 결정되므로, 설계 단계에서 이 세 가지를 함께 계산해 두는 것이 안전합니다.

API Gateway의 한계

엘리베이터에 비유하면, 정원과 정지 시간이 정해져 있어 아무리 급해도 한 번에 다 태울 수 없습니다. API Gateway도 하나의 요청을 기다려 주는 시간에 상한이 있어, 보통 수십 초 수준을 넘기면 작업이 끝나기 전에 연결이 끊깁니다. 또 요청과 응답으로 오갈 수 있는 데이터 크기에도 한도가 있어 큰 파일은 한 번에 통과시키지 못하고, 연결을 계속 붙들어 두는 방식도 제한됩니다.

응답을 돌려준 뒤에도 작업이 계속되어야 한다면 게이트웨이가 아니라 뒤쪽 서비스에서 비동기로 처리해야 합니다.

즉 API Gateway는 짧고 작은 요청을 빠르게 넘기는 데 맞춰져 있으므로, 긴 작업과 큰 데이터는 별도 경로로 빼는 설계가 필요합니다.

REST API와 HTTP API의 차이

두 제품이 각각 무엇을 지원하고 무엇이 빠졌는지 비교합니다

대형 마트와 편의점에 비유할 수 있습니다. 대형 마트는 물건 종류가 많고 조리와 배송, 보관 같은 부가 서비스가 붙어 있지만 동선이 길고 준비가 오래 걸립니다. 편의점은 품목이 적은 대신 들어서서 바로 계산하고 나올 수 있어 빠릅니다.

REST API는 API 키, 요청 검증, 캐시, 사용 계획 같은 기능을 폭넓게 갖추고 있고, HTTP API는 그중 꼭 필요한 라우팅과 인증에 집중해 더 가볍고 빠르며 저렴합니다.

정리하면 REST API는 기능이 많은 대신 무겁고, HTTP API는 최소한의 기능으로 빠르고 싼 길을 엽니다. 두 제품의 지원 범위는 시점에 따라 조금씩 달라지므로 도입 전에 문서로 확인해야 합니다.

이미 REST API로 만들어 둔 설정과 부가 기능을 그대로 이어 써야 한다면 옮길 이유도 줄어듭니다.

그래서 판단 기준은 이렇습니다. 요청 검증과 캐시, 사용량 관리, 세밀한 모니터링이 필요하면 REST API를, 단순한 라우팅과 낮은 비용이 우선이면 HTTP API를 고르면 됩니다.

HTTP API 선택 기준

가볍고 저렴한 HTTP API가 더 맞는 경우를 구분합니다

작은 알림 서비스 하나를 만들었을 뿐인데 웹소켓 연결 관리와 상태 유지 서버까지 따로 세팅하느라 개발 기간의 절반이 사라진다면, 그것은 필요보다 무거운 API 방식을 기본값처럼 골랐기 때문입니다. Amazon API Gateway의 HTTP API는 그런 단순한 요구에 맞춰 더 가볍고 저렴하게 만든 선택지입니다.

이 차이는 택배로 비유하면 분명해집니다. 하루 몇 건만 보내는 작은 가게가 대형 물류센터의 자동 분류 라인과 냉장 설비까지 딸린 종합 계약을 맺으면, 쓰지도 않는 기능의 요금과 관리 부담을 계속 떠안게 됩니다. HTTP API는 이런 가게에 꼭 맞는 기본 접수 창구와 같아서, 주소를 적고 무게를 재고 운송장을 발급하는 최소한의 절차만 남깁니다.

그래서 요청과 응답의 형식이 단순하고, 접근 권한 확인과 트래픽 제한 같은 필수 기능은 그대로 쓰면서 설정 항목과 비용은 줄어듭니다.

정리하면 HTTP API는 요청과 응답이 한 번씩 오가는 짧은 호출이 중심인 서비스에 적합한 선택입니다. 반대로 연결을 계속 붙잡아 두는 실시간 기능이나 복잡한 요청 변환이 필요하다면 다른 유형을 검토해야 합니다.

WebSocket API

연결을 계속 유지하며 양방향으로 주고받는 API가 필요한 상황을 이해합니다

채팅 화면을 열어 둔 사용자가 새 메시지를 받으려면 1초마다 서버에 새 소식이 있는지 물어봐야 하고, 물어볼 때마다 연결을 새로 맺었다 끊는 비용이 쌓입니다. Amazon API Gateway의 WebSocket API는 이렇게 계속 물어보는 대신 연결을 한 번 맺어 두고 양쪽이 필요할 때 바로 말을 거는 방식을 제공합니다.

이 차이는 전화와 편지로 비유하면 잘 드러납니다. 편지는 보낼 때마다 봉투를 새로 쓰고 상대가 확인할 때까지 기다려야 하지만, 전화는 한 번 연결해 두면 양쪽 누구든 말을 걸 수 있습니다.

WebSocket API도 마찬가지로, 처음 연결을 맺는 순간 그 통로에 고유한 식별자가 붙고 서버는 그 식별자를 명단에 적어 둡니다. 이후에는 클라이언트가 보낸 메시지를 서버가 받아 처리한 뒤 다른 접속자에게 되돌려 보내거나, 서버 쪽 사정으로 먼저 보낼 수도 있습니다.

정리하면 WebSocket API는 연결을 유지한 채 양방향으로 메시지를 주고받는 실시간 기능, 예컨대 채팅이나 알림, 공동 편집에 쓰입니다. 연결 상태와 접속자 식별자를 서버가 계속 들고 있어야 하므로, 단발성 요청만 있는 서비스에는 오히려 과한 선택입니다.

엔드포인트 유형 개요

리전, 엣지 최적화, 프라이빗이라는 세 가지 유형이 무엇을 뜻하는지 정리합니다

API를 만들 때 위치를 아무 생각 없이 기본값으로 정하면 해외 사용자는 응답을 몇 초씩 기다리고, 사내 전용 API는 인터넷에 그대로 열려 버립니다. Amazon API Gateway는 이 문제를 리전(Regional), 엣지 최적화(Edge-Optimized), 프라이빗(Private)이라는 세 가지 엔드포인트 유형으로 나눠, 요청이 어디서 들어오고 누가 들어올 수 있는지를 선택하게 합니다.

이 구분은 건물의 출입구에 빗대면 이해하기 쉽습니다. 리전 유형은 건물 정문 하나를 두고 그 안의 안내 데스크가 직접 응대하는 방식이고, 엣지 최적화 유형은 전국 주요 거점에 안내 데스크를 두어 손님이 가까운 곳에서 먼저 안내를 받게 하는 방식입니다. 프라이빗 유형은 외부인이 들어올 수 없는 사내 전용 통로로, 같은 단지 안에 있는 사람만 통과할 수 있습니다.

세 유형 모두 뒤쪽의 업무 처리 방식은 같고, 요청이 건물에 들어오는 경로만 다릅니다.

정리하면 엔드포인트 유형은 API가 요청을 받아들이는 진입 경로를 정하는 설정이며, 사용자 위치와 보안 경계에 따라 리전과 엣지 최적화, 프라이빗 중에서 고릅니다. 유형을 바꾸면 주소와 접근 방식이 달라지므로 처음 설계할 때 정하는 편이 좋습니다.

리전 엔드포인트(Regional)

같은 리전 안에서 요청을 처리하는 기본형의 특성과 쓰임을 압니다

고객 데이터를 특정 리전 밖으로 내보내지 않아야 하는 규제를 지키면서 그 리전 안의 사용자에게만 서비스를 제공하려는데, 전 세계를 겨냥한 배포 방식을 그대로 쓰면 데이터가 어디를 거쳐 가는지 설명하기 어렵고 비용도 불필요하게 늘어납니다. 리전(Regional) 엔드포인트는 API를 만든 리전 안에서 요청을 직접 받아 처리하는 기본형입니다.

이 방식은 동네 지점 은행에 비유할 수 있습니다. 지점 창구는 그 동네 사람을 직접 응대하고, 거래 기록도 그 지점의 금고에 그대로 남습니다.

리전 엔드포인트도 API가 있는 리전의 주소로 요청을 받고 그 리전의 컴퓨팅 자원이 처리하며, 로그와 지표도 같은 리전에 쌓입니다. 그래서 그 리전 안에서 요청하는 사용자에게는 지연이 짧고, 접근 제어나 사용량 제한 같은 정책도 리전 단위로 세밀하게 다룰 수 있습니다.

정리하면 리전 엔드포인트는 API와 같은 리전에서 요청을 받아 처리하는 기본형으로, 데이터 주권과 리전 단위 관리가 중요한 서비스에 어울립니다. 전 세계 사용자를 상대로 한다면 앞단에 별도의 배포 계층을 두는 방식을 함께 검토하게 됩니다.

API를 한 리전에만 두면 지구 반대편 사용자는 요청을 보낼 때마다 대륙을 건너 왕복하는 시간을 기다려야 하고, 화면이 뜨기까지 체감 지연이 커집니다. 엣지 최적화(Edge-Optimized) 엔드포인트는 전 세계 여러 거점에 미리 퍼뜨린 캐시 네트워크, 즉 CDN을 API 앞단에 두어 이 거리를 줄이는 방식입니다.

이 구조는 전국에 물류 거점을 둔 유통업체와 비슷합니다. 본사 창고는 하나뿐이지만 각 지역 거점에 같은 상품을 미리 쌓아 두면 고객은 가까운 거점에서 바로 받습니다.

엣지 최적화도 요청이 가까운 엣지 거점에 먼저 도착해 그곳에서 처리되거나 원래 리전까지 가장 빠른 경로로 전달됩니다. 그래서 정적인 응답은 거점에서 바로 돌려주고, 매번 새로 계산해야 하는 요청만 원본 리전까지 다녀오게 됩니다.

정리하면 엣지 최적화 엔드포인트는 CDN을 앞에 두어 지리적 거리를 줄이는 유형으로, 여러 대륙에 사용자가 흩어져 있는 공개 서비스에 적합합니다. 대신 캐시와 엣지 계층이 하나 더 끼는 만큼, 데이터가 어디에 저장되는지가 중요한 경우에는 적합성을 따져 봐야 합니다.

프라이빗 엔드포인트(Private)

VPC 안에서만 접근되는 API를 언제 쓰는지 압니다

사내 시스템끼리만 주고받아야 하는 API를 인터넷에서 접근 가능한 공개 주소로 열어 두면 외부의 무작위 접근 시도가 계속 들어오고, 사설 주소로만 통신하는 내부 서버는 그 API를 부르지도 못합니다. 프라이빗(Private) 엔드포인트는 API를 가상 사설 네트워크(VPC) 안에만 두고 같은 네트워크에 연결된 곳에서만 접근하게 하는 유형입니다.

이 방식은 외부인 출입이 막힌 사내 전용 엘리베이터와 같습니다. 건물 로비 정문을 지나지 않고도 같은 건물 안의 층과 층을 오갈 수 있지만, 외부에서 오려면 정식으로 등록된 출입 절차를 거쳐야 합니다.

프라이빗 엔드포인트도 VPC 안에 네트워크 인터페이스를 만들어 그 사설 주소로 요청을 받고, 다른 VPC나 사내망에서 연결하려면 그 연결 자체를 허용하도록 설정해야 합니다. 그래서 트래픽이 공용 인터넷을 거치지 않고, 접근은 네트워크 수준에서 통제됩니다.

정리하면 프라이빗 엔드포인트는 VPC 내부에서만 접근되는 API로, 인터넷에 노출되면 안 되는 내부 시스템 간 연동에 씁니다. 외부 공개가 목적이라면 리전이나 엣지 최적화 유형을 택해야 합니다.

그래서 사용자가 전국에 흩어져 있으면 엣지 최적화를, 같은 지역에 몰려 있거나 규제상 지역 고정이 필요하면 리저널을, 외부에 노출되면 안 되면 프라이빗을 고르게 됩니다. 핵심은 엔드포인트 유형이 성능과 보안과 비용의 맞교환을 미리 정해 두는 선택지라는 점입니다.

키가 인증 수단이 아니라 사용량을 구분하는 표식이라는 점을 이해합니다

서비스가 커지자 어느 팀이 얼마나 호출했는지 알 수 없어, 한 팀의 폭주가 전체 서비스를 마비시킨 적이 있습니다. 이때 흔히 떠올리는 것이 API 키(API Key)인데, Amazon API Gateway에서 이 키는 신원을 증명하는 인증 수단이 아니라 호출을 팀별로 구분하는 표식에 가깝습니다.

정리하면 API 키는 접근 권한을 판정하는 열쇠가 아니라 요청을 출처별로 나눠 세는 식별표입니다.

키마다 호출량과 속도를 다르게 제한하는 구조를 설명합니다

헬스장 회원권에 비유하면, 모든 회원에게 같은 무제한 이용권을 주는 대신 일반권과 프리미엄권과 단체권으로 나누어 하루 이용 횟수와 동시 입장 인원을 다르게 정하는 것과 같습니다. 사용량 계획에는 기간별 호출 한도(quota)와 초당 처리 속도 한도(throttle)가 들어가고, 여기에 API 키를 묶으면 그 키로 들어오는 요청만 그 한도를 적용받습니다. 그래서 배치 팀에는 낮은 속도 한도를, 실시간 서비스 팀에는 높은 한도를 주는 식으로 같은 API를 쓰면서도 서로를 방해하지 않게 나눌 수 있습니다. 한도에 닿은 요청은 처리되지 않고 거절되므로, 한도는 넉넉하게 잡되 실제 사용 패턴을 보고 조정해야 합니다.

결국 사용량 계획은 키를 단위로 호출량과 속도를 계층화하는 요금제 같은 장치입니다.

URL 경로를 리소스 트리로 설계하는 방법을 배웁니다

회사 문서함에 비유하면, 서류를 아무 서랍에나 넣지 않고 부서 폴더 안에 업무 폴더를, 그 안에 다시 문서를 두는 것과 같습니다. 그래서 주문 관련 경로는 orders 아래에, 그 안의 특정 주문은 orders/{id}처럼 하위 리소스로 두어 경로만 봐도 소속이 드러납니다. 리소스는 그 자체로는 아무 동작도 하지 않고, 그 아래에 메서드를 붙여야 비로소 요청을 받습니다. 중괄호로 감싼 부분은 경로 매개변수(path parameter)라서 주문 번호처럼 값이 바뀌는 자리를 나타냅니다.

정리하면 리소스는 API의 목차이자 주소 체계로, 경로를 트리로 설계하면 권한과 문서와 모니터링을 한결 쉽게 나눌 수 있습니다.

GET, POST 같은 HTTP 메서드가 게이트웨이에서 갖는 의미를 압니다

같은 주소로 요청을 보냈는데 어떤 때는 조회가 되고 어떤 때는 데이터가 지워져, 클라이언트 개발자가 원인을 찾지 못한 일이 있습니다. Amazon API Gateway의 메서드(Method)는 GET, POST 같은 HTTP 메서드를 리소스에 붙여 그 주소에서 허용할 동작을 정하는 단위입니다.

은행 창구로 비유하면, 창구 번호가 리소스이고 그 창구에서 할 수 있는 업무가 메서드입니다. 같은 창구라도 조회 창구에서는 잔액만 물어볼 수 있고 입금 창구에서는 돈을 넣는 일만 할 수 있는 것처럼, 같은 경로라도 GET은 읽기, POST는 새로 만들기, PUT은 전체 교체, DELETE는 삭제로 역할이 나뉩니다. 핵심은 메서드가 주소와 동작을 분리해, 같은 리소스에 여러 가지 일을 안전하게 나누어 붙이는 장치라는 점입니다.

경로 파라미터(Path Parameter)

경로 안의 값을 변수로 받아 뒤로 넘기는 방법을 익힙니다

온라인 쇼핑몰에서 회원 한 명의 주문 내역을 보여주려는데, 회원 수만큼 주소를 따로 만들어야 한다면 서비스는 금방 감당할 수 없게 됩니다. 이 문제를 풀기 위해 주소의 한 칸을 값이 아니라 값이 들어갈 자리로 비워 두고, 실제 값은 요청이 들어올 때마다 채워 읽는 방식을 쓰는데 이것이 경로 파라미터(Path Parameter)입니다.

아파트 우편함을 떠올려 보면 이해가 쉽습니다. 각 세대의 우편함에는 '101동 502호'처럼 미리 정해진 이름표가 붙어 있고, 택배기사는 배송지에서 읽은 동과 호수를 그 이름표에 맞춰 넣기만 하면 됩니다. 웹 주소에서 슬래시(/)로 나뉜 칸 중 값을 받도록 표시한 자리가 바로 이 이름표이고, 그 자리에 들어온 값은 경로 파라미터로 전달되어 뒤쪽 처리 담당자에게 그대로 넘어갑니다. 그래서 설계자는 주소를 회원마다 새로 만들지 않고 '/members/{id}'처럼 틀 하나만 만들어 두면 됩니다.

정리하면 경로 파라미터는 주소 경로의 일부를 변수 자리로 열어 두고, 요청마다 들어온 값을 꺼내 뒷단으로 전달하는 방식입니다. 이름표 자리는 고정되고 값만 바뀌기 때문에, 주소 하나로 셀 수 없이 많은 대상을 같은 규칙으로 처리할 수 있습니다.

쿼리 문자열(Query String)

물음표 뒤의 값을 읽고 검증하는 방법을 배웁니다

쇼핑몰 상품 목록에서 '3만 원 이하이면서 재고가 있는 것만 보여 주세요' 같은 조건을 걸고 싶을 때, 조건 조합마다 주소를 따로 만든다면 경우의 수가 걷잡을 수 없이 늘어납니다. 그래서 주소에서 실제 대상을 가리키는 부분과 조건을 적는 부분을 분리하고, 조건은 물음표(?) 뒤에 이름과 값을 짝지어 붙이도록 했는데 이것이 쿼리 문자열(Query String)입니다.

도서관에서 책을 빌리러 갈 때를 떠올려 보면 이해가 쉽습니다. 사서에게 책 제목은 한 번만 말하고, 그 뒤에 '올해 나온 판, 큰 글씨판' 같은 희망 사항을 덧붙이면 사서는 제목에 그 조건을 얹어 책을 골라 줍니다. 물음표 뒤의 '이름=값' 쌍이 바로 그 희망 사항이고, 여러 개를 붙일 때는 앰퍼샌드(&)로 이어 붙입니다. 서버는 이 값을 읽어 조건에 맞는 것만 골라 내지만, 값이 비어 있거나 숫자 자리에 글자가 들어오는 경우도 있으므로 받은 값을 그대로 믿지 않고 형식과 범위를 확인하는 검증 절차를 반드시 거칩니다.

정리하면 쿼리 문자열은 하나의 주소를 그대로 두고 조건만 바꿔 가며 결과를 달리 받는 방식입니다. 경로가 '무엇을' 가리킨다면 물음표 뒤는 '어떻게 걸러 낼지'를 담당한다고 구분해 두면 기억하기 쉽습니다.

요청 헤더(Request Header)

헤더를 읽어 조건 판단에 쓰는 방법을 이해합니다

서버가 요청을 받았는데 보낸 사람이 누구인지, 어떤 형식으로 답해 주기를 바라는지 알 수 없다면 매번 같은 질문을 되물어야 하고 그 사이 처리가 밀리게 됩니다. 이 정보를 본문과 분리해 요청 겉면에 적어 보내는 약속이 요청 헤더(Request Header)입니다.

택배 상자를 떠올려 보면 이해가 쉽습니다. 상자 안의 물건이 무엇인지와 별개로 겉면에는 운송장이 붙어 있고, 거기에는 보낸 사람, 받는 사람, 취급 주의, 결제 방식이 정해진 칸에 적혀 있습니다. 헤더도 마찬가지로 '이름: 값' 형태의 칸에 인증 정보나 원하는 응답 형식, 내용의 길이 같은 내용을 담고, 이름이 미리 약속된 표준 헤더와 서비스가 스스로 정한 사용자 정의 헤더로 나뉩니다. 서버는 이 칸들을 읽어 통과시킬지 거절할지, 어떤 언어와 형식으로 답할지를 먼저 판단한 뒤 본문 처리를 시작합니다.

정리하면 요청 헤더는 요청 내용 자체가 아니라 요청을 어떻게 다뤄야 하는지를 적어 보내는 정보 칸이며, 조건 판단과 인증의 첫 관문 역할을 합니다.

요청 본문(Request Body)

본문을 모델로 검증하고 그대로 넘기는 흐름을 익힙니다

회원 가입처럼 이름, 주소, 비밀번호를 한꺼번에 보내야 하는 요청을 주소에 모두 실으면 주소가 지저분해지고 남기기도 어려우며 길이 한계에도 금방 부딪힙니다. 그래서 전달할 내용을 주소 바깥의 별도 공간에 담아 보내는데 이 공간이 요청 본문(Request Body)입니다.

이사할 때 짐을 상자에 담아 보내는 상황과 같습니다. 상자 겉면의 운송장에는 받는 사람과 취급 주의만 적고 실제 짐은 상자 안에 넣어 포장하듯이, 요청도 겉면에 해당하는 헤더와 내용을 담은 본문을 따로 가집니다. 보내는 쪽은 본문에 데이터를 JSON 같은 형식으로 담고, 받는 쪽은 미리 정해 둔 모델(Model)이라는 서식과 대조해 필수 항목이 빠지지 않았는지, 값의 형식이 맞는지 확인합니다. 검증을 통과한 본문은 변형 없이 다음 처리 단계로 그대로 넘겨지고, 통과하지 못하면 처리에 들어가기 전에 거절됩니다.

정리하면 요청 본문은 주소에 담기 어려운 여러 항목의 데이터를 담는 공간이며, 정해진 서식으로 검증한 뒤 그대로 넘기는 것이 핵심입니다.

경로와 메서드 매칭 규칙

비슷한 경로가 여러 개일 때 어떤 규칙으로 골라지는지 압니다

비슷한 모양의 주소가 여러 개 등록되어 있을 때 어느 규칙으로 처리할지 정해져 있지 않다면, 분명히 다르게 만든 요청이 엉뚱한 처리로 흘러가고 원인을 찾기도 어려워집니다. 그래서 경로의 모양과 요청 방식(Method)을 함께 보고 가장 잘 맞는 하나를 고르는 매칭 규칙을 둡니다.

아파트 경비실에 택배가 쌓이는 상황을 떠올려 보면 이해가 쉽습니다. 경비원은 '101동'이라고만 적힌 택배와 '101동 502호'라고 호수까지 적힌 택배를 구분해, 더 자세히 적힌 쪽을 그 세대에 먼저 배정합니다. 경로 매칭도 같아서 변수로 열어 둔 자리보다 글자 그대로 적힌 구체적인 경로를 먼저 고르고, 그다음 와일드카드처럼 넓게 잡은 규칙으로 내려옵니다. 여기에 더해 조회(GET)와 등록(POST)처럼 같은 주소에 걸린 요청 방식까지 함께 대조하므로, 주소가 같아도 방식이 다르면 다른 처리가 선택됩니다.

정리하면 매칭은 경로의 구체성과 요청 방식을 함께 따져 가장 잘 맞는 규칙 하나를 고르는 과정이며, 규칙이 겹치지 않게 설계하는 것이 안전합니다.

와일드카드 경로(Greedy Path)

하위 경로 전체를 하나로 받는 패턴을 사용합니다

이미지나 문서를 다루는 서비스에서 'files/사진/2026/여름/가족.jpg'처럼 뒤쪽 경로가 끝없이 늘어나는 주소를 하나하나 등록하려 하면, 새 폴더가 생길 때마다 설정을 고쳐야 합니다. 이때 뒷부분 전체를 하나의 값으로 통째로 받아 넘기는 와일드카드 경로(Greedy Path)를 씁니다.

회사 우편실을 떠올려 보면 이해가 쉽습니다. 우편실에는 부서별로 꽂는 칸이 따로 있지만, 어느 부서인지 적혀 있지 않은 우편은 '그 외 전부'라고 쓰인 큰 바구니에 모아 두었다가 담당자가 내용을 보고 나눠 줍니다. 와일드카드 경로가 바로 그 큰 바구니이며, 표시 자리 뒤에 오는 슬래시를 포함한 나머지 전체를 하나의 문자열로 받아 다음 단계에 넘깁니다. 다만 무엇이든 삼키는 규칙인 만큼 구체적인 경로보다 항상 뒤에 두고, 경로의 맨 끝에서만 쓰며, 받은 문자열에 위험한 문자가 섞이지 않았는지 확인해야 합니다.

정리하면 와일드카드 경로는 하위 경로 전체를 하나의 값으로 받는 넓은 규칙이며, 가장 덜 구체적인 규칙으로 평가된다는 점을 기억해야 합니다.

게이트웨이 응답(Gateway Response)

백엔드를 거치지 않고 게이트웨이가 직접 돌려주는 응답을 설계합니다

모든 요청을 백엔드까지 보내 처리하면, 존재하지 않는 경로를 부르는 요청이나 형식이 잘못된 요청까지 서버 자원을 써서 응답해야 합니다. Amazon API Gateway의 게이트웨이 응답(Gateway Response)은 이런 요청에 대해 백엔드를 거치지 않고 게이트웨이가 직접 정해진 응답을 돌려주는 기능입니다.

건물 로비의 안내데스크를 떠올리면 이해가 쉽습니다. 방문객이 주차장이 어디 있느냐고 물으면 안내데스크 직원은 사무실까지 올라가 확인하지 않고 로비에 붙은 안내문을 보고 바로 답합니다.

게이트웨이도 마찬가지로, 등록되지 않은 경로로 요청이 오면 미리 정해 둔 값으로 즉시 응답을 돌려보냅니다. 이때 상태 코드(요청의 성패를 숫자로 나타내는 표준 값)와 응답 본문, 헤더를 응답 유형별로 지정해 둘 수 있습니다.

정리하면 게이트웨이 응답은 백엔드에 도달하기 전 단계에서 공통 오류나 안내 메시지를 일관된 형식으로 내보내는 장치입니다. 덕분에 백엔드는 실제 업무 처리에만 집중할 수 있습니다.

요청 처리 흐름

요청이 들어와 통합으로 넘어가고 응답이 나가는 순서를 정리합니다

클라이언트가 요청을 보냈을 때 그 요청이 어디서 검증되고 어떤 순서로 뒷단 서비스에 전달되는지 정해져 있지 않으면, 장애가 났을 때 어느 단계에서 문제가 생겼는지 찾기 어렵습니다. Amazon API Gateway는 요청이 들어와 나가는 전 과정을 정해진 단계로 나누어 처리합니다.

이 흐름은 식당의 주문 처리와 비슷합니다. 손님의 주문이 홀 직원에게 들어오면 직원은 메뉴가 맞는지 확인하고 주방에 전달하며, 주방에서 음식이 완성되면 다시 홀을 거쳐 손님에게 나갑니다.

게이트웨이에서도 요청이 먼저 도착해 인증과 권한 확인, 요청 형식 검사 같은 단계를 지나고, 그다음 통합(Integration, 게이트웨이가 뒤 서비스와 연결되는 설정)을 통해 백엔드로 전달됩니다. 백엔드가 응답을 돌려주면 게이트웨이가 이를 받아 클라이언트가 이해할 수 있는 형태로 정리해 내보냅니다.

결국 요청 처리 흐름은 요청 수신과 검증, 통합 호출, 응답 변환이라는 세 구간으로 이해하면 되고, 각 구간이 나뉘어 있어 문제 지점을 좁혀 볼 수 있습니다.

3부. REST API 구조와 요청 처리033

메서드 요청과 통합 요청

요청이 왜 두 단계로 나뉘어 있는지 이해합니다

클라이언트가 보내는 요청 형식과 백엔드가 기대하는 요청 형식이 다르면, 그 차이를 누군가 중간에서 바꿔 주어야 합니다. Amazon API Gateway는 이 변환을 메서드 요청(Method Request)과 통합 요청(Integration Request)이라는 두 단계로 나누어 처리합니다.

여행사 창구를 떠올리면 구조가 잘 보입니다. 고객은 여행사 창구에서 정해진 신청서에 목적지와 날짜를 적어 내고, 직원은 그 내용을 항공사가 요구하는 예약 형식으로 다시 옮겨 전산에 입력합니다. 여기서 고객이 작성하는 신청서가 메서드 요청이고, 직원이 항공사에 넘기는 예약 정보가 통합 요청입니다.

두 단계가 분리되어 있으면 같은 백엔드에 서로 다른 형태의 고객 요청을 붙이거나, 백엔드를 바꾸지 않고도 입력 형식을 조정할 수 있습니다.

정리하면 메서드 요청은 외부 클라이언트와의 약속, 통합 요청은 내부 백엔드와의 약속이며, 게이트웨이는 그 사이에서 형식과 값을 변환하는 역할을 맡습니다.

3부. REST API 구조와 요청 처리034

CORS 처리

브라우저의 교차 출처 요청을 게이트웨이에서 허용하는 방법을 배웁니다

웹 페이지가 다른 도메인의 API를 호출하면 브라우저가 보안 규칙에 따라 요청을 막아 버려, 서버는 정상인데도 화면에서는 오류가 나는 일이 흔합니다. Amazon API Gateway의 CORS(Cross-Origin Resource Sharing, 서로 다른 출처 간 자원 공유) 처리는 이런 교차 출처 요청을 게이트웨이에서 허용하도록 설정하는 기능입니다.

아파트 단지의 경비실 비유가 잘 맞습니다. 방문객이 다른 동에 사는 사람을 만나러 가면 경비실에서 방문 허용 명단을 먼저 확인하고, 명단에 있는 방문만 출입을 허락합니다.

브라우저도 마찬가지로, 다른 출처로 요청을 보내기 전에 허용 여부를 묻는 사전 요청(Preflight)을 먼저 보내고, 게이트웨이가 허용 헤더를 돌려주어야 실제 요청을 진행합니다. 그래서 게이트웨이의 응답에 어떤 출처와 어떤 메서드, 어떤 헤더를 허용하는지 담아 두어야 하며, 이 설정이 빠지면 브라우저는 응답을 받고도 화면에 전달하지 않습니다.

결국 CORS 처리는 브라우저의 출처 검사 규칙을 게이트웨이 응답으로 통과시키는 작업이고, 허용 출처와 메서드, 헤더를 명시하는 것이 핵심입니다.

4부. 통합(Integration)035

통합(Integration) 개념

게이트웨이가 뒤 서비스와 연결되는 방식과 유형을 이해합니다

게이트웨이가 요청을 받기만 하고 어디로 보낼지 정해져 있지 않으면, 그 요청은 처리될 곳을 찾지 못합니다. Amazon API Gateway의 통합(Integration)은 각 경로와 메서드가 어떤 뒤 서비스로 연결될지를 정의하는 설정입니다.

회사 대표 전화의 교환원을 떠올리면 이해가 쉽습니다. 걸려 온 전화를 교환원이 받아 용건에 따라 영업팀이나 기술팀으로 연결하듯, 게이트웨이는 요청을 받아 미리 정해 둔 대상으로 넘깁니다. 연결 대상은 AWS Lambda 함수일 수도 있고, 외부 HTTP 엔드포인트나 다른 AWS 서비스일 수도 있으며, 백엔드 없이 정해진 값을 돌려주는 모의(Mock) 통합도 있습니다. 연결 방식은 크게 요청과 응답을 그대로 넘기는 프록시(Proxy) 방식과, 요청과 응답을 변환해 주는 비프록시 방식으로 나뉩니다.

정리하면 통합은 경로와 메서드에 백엔드를 짝지어 주는 연결 설정이고, 그 유형과 방식에 따라 변환의 책임이 게이트웨이에 있느냐 백엔드에 있느냐가 달라집니다.

4부. 통합(Integration)036

Lambda 프록시 통합

요청 전체를 그대로 Lambda에 넘기고 응답도 그대로 받는 방식을 익힙니다

요청의 헤더나 본문을 하나하나 매핑해서 넘기면 설정이 복잡해지고, 클라이언트가 보낸 값을 빠뜨리기 쉽습니다. Amazon API Gateway의 Lambda 프록시 통합(Lambda Proxy Integration)은 요청 전체를 가공 없이 그대로 Lambda 함수에 넘기고, 함수의 응답도 그대로 클라이언트에 돌려주는 방식입니다.

택배를 중간에서 뜯지 않고 그대로 전달하는 상황과 비슷합니다. 집하 직원이 상자 내용물을 확인하지 않고 송장만 붙여 다음 구간으로 넘기면, 받는 사람은 보낸 사람이 담은 그대로를 받습니다. Lambda 프록시 통합에서도 게이트웨이는 요청의 메서드, 경로, 헤더, 본문 등을 하나의 구조로 묶어 함수에 전달하고, 함수는 상태 코드와 헤더, 본문을 담은 정해진 형식으로 응답을 돌려줍니다.

그래서 함수 안에서 요청을 자유롭게 해석할 수 있는 대신, 응답 형식을 함수가 직접 맞춰야 합니다.

결국 Lambda 프록시 통합은 변환 책임을 게이트웨이에서 함수로 넘기는 방식이며, 설정은 단순해지지만 함수가 요청 해석과 응답 형식을 스스로 책임진다는 점을 기억해야 합니다.

4부. 통합(Integration)037

Lambda 비프록시 통합

요청과 응답을 직접 매핑해 Lambda를 호출하는 방식을 배웁니다

여러분이 만든 서비스의 창구를 API Gateway로 옮기면, 가장 먼저 부딪히는 결정이 뒤쪽 코드에 요청을 어떻게 넘길지입니다. 아무 준비 없이 손님의 요청을 통째로 밀어 넣으면, 뒤쪽 코드는 창구가 어떤 형식으로 말을 거는지 몰라 매번 헤매게 됩니다.

이때 자주 쓰는 방식이 비프록시 통합(Non-proxy Integration)입니다. 회사에 우편실이 있다고 생각해 보면, 우편실 직원은 받은 서류를 그대로 갖다 주지 않고 필요한 항목만 뽑아 사내 결재 양식으로 다시 적어 담당 부서에 넘깁니다. 담당 부서가 돌려준 회신도 그대로 전달하지 않고, 고객에게 나갈 공문 형식으로 상태와 머리말을 갖춰 다시 써서 보냅니다.

API Gateway에서는 이 다시 적는 일을 매핑 템플릿(Mapping Template)이 맡고, 요청에서 어떤 값을 뽑아 넘길지와 응답을 어떤 상태 코드와 헤더로 포장할지를 개발자가 직접 정합니다.

정리하면 비프록시 통합은 요청과 응답을 개발자가 정한 형식으로 변환해 Lambda를 호출하는 방식이며, 형식을 촘촘히 다스리는 대신 매핑 규칙을 직접 관리해야 하는 선택입니다.

4부. 통합(Integration)038

HTTP 통합

기존 HTTP 엔드포인트로 요청을 넘기는 방법과 주의점을 익힙니다

기존에 이미 돌아가는 웹 서버가 있는데 API Gateway를 앞에 두려면, 그 서버를 다시 코드로 감싸야 할까요. 그럴 필요 없이 창구가 받은 요청을 기존 주소로 그대로 넘기는 방법이 HTTP 통합(HTTP Integration)입니다.

아파트마다 대표번호를 외우게 하는 대신 관리사무소 대표번호 하나만 안내하는 것과 비슷합니다. 안내원은 걸려온 전화를 담당 부서 번호로 연결하고, 연결할 때 어느 부서인지와 어떤 용건인지를 함께 알려 줍니다.

API Gateway도 백엔드 주소(URL), 메서드, 헤더, 쿼리 문자열을 설정해 두고 그 규칙대로 연결합니다. 다만 연결은 해 주지만 상대가 응답하지 않으면 기다리는 시간에 한계가 있고, 중간에 다른 주소로 넘기는 리다이렉션은 따라가지 않는다는 점을 기억해야 합니다.

즉 HTTP 통합은 이미 있는 HTTP 엔드포인트를 창구 뒤에 그대로 세우는 방식이고, 주소와 전달 규칙을 설정으로 관리하는 대신 백엔드의 응답 시간과 주소 노출을 함께 살펴야 합니다.

← 이전Lambda 비프록시 통합다음 →프라이빗 통합(VPC Link)

4부. 통합(Integration)039

프라이빗 통합(VPC Link)

VPC 안의 서비스에 사설 네트워크로 연결하는 방법을 배웁니다

보안 때문에 인터넷에서 직접 닿지 않는 사설 네트워크 안에 서비스를 두는 경우가 많습니다. 그런데 API Gateway는 기본적으로 공개된 인터넷 쪽에 있어서, 그 사설 서비스를 부르려면 문을 열어야 하는 곤란이 생깁니다.

이때 쓰는 것이 프라이빗 통합(Private Integration)과 그것을 가능하게 하는 VPC Link입니다. 외부인 출입이 금지된 건물에 정문을 열지 않고 지하 연결 통로만 뚫어 택배가 드나들게 하는 모습을 떠올리면 됩니다. 통로 입구에는 경비가 서서 허용된 사람만 들이고, 통로 끝에는 안내 데스크가 있어 어느 층으로 갈지 알려 줍니다.

VPC Link가 그 통로 역할을 하며 사설 서브넷의 로드 밸런서(Load Balancer)로 트래픽을 보내고, 보안 그룹과 리스너 규칙이 경비와 안내 데스크 몫을 합니다.

정리하면 VPC Link는 API Gateway와 VPC 안의 서비스를 사설 네트워크로 이어 주는 다리이며, 공인 인터넷에 백엔드를 노출하지 않고도 창구를 붙일 수 있게 해 줍니다.

4부. 통합(Integration)040

AWS 서비스 통합

SQS, SNS 같은 서비스를 게이트웨이에서 직접 호출하는 방법을 압니다

요청을 받아 큐에 넣기만 하면 되는 일인데, 그 일을 위해 서버를 따로 띄우고 코드를 배포하는 것은 낭비입니다. API Gateway는 그런 단순한 작업을 위해 AWS 서비스 통합(AWS Service Integration)이라는 방법을 제공합니다.

창구 직원이 직접 사내 게시판에 글을 올리는 것과 같습니다.

고객이 접수한 내용을 창구 직원이 사내 게시판에 정해진 양식으로 올리면, 뒤에서 일하는 사람들이 그 글을 보고 일을 처리합니다. 이때 창구 직원에게 게시판에 글을 쓸 권한이 있어야 하므로 서비스 역할(IAM Role)을 붙여 주고, 어떤 동작(Action)을 어떤 파라미터(Parameter)로 요청할지 정해 둡니다. 이 방식으로 SQS, SNS, Kinesis, DynamoDB, Step Functions 같은 서비스를 별도 서버 없이 호출할 수 있습니다.

즉 AWS 서비스 통합은 Lambda 같은 실행 코드를 거치지 않고 게이트웨이가 AWS 서비스에 직접 요청을 넣는 방식이며, 권한 설정과 요청 형식만 갖추면 서버 관리 부담을 크게 줄일 수 있습니다.

4부. 통합(Integration)041

모의 통합(Mock Integration)

백엔드 없이 응답을 흉내 내 API 계약을 먼저 확정합니다

프론트엔드와 백엔드가 함께 일할 때, 백엔드가 아직 없어서 화면을 만들지 못하는 상황이 자주 생깁니다. 이때 응답만 미리 흉내 내 두면 양쪽이 같은 약속을 놓고 각자 일할 수 있습니다.

모의 통합(Mock Integration)은 실제 백엔드에 연결하지 않고 게이트웨이가 정해진 응답을 그대로 돌려주는 기능입니다. 아파트를 다 짓기 전에 모델하우스를 세워 구조와 마감을 눈으로 확인하는 것과 같습니다. 방문객은 진짜 집은 아니지만 문의 위치와 창의 크기를 미리 보고 살림을 계획할 수 있고, 시공사는 그 자리에서 고객의 요구를 미리 듣고 설계를 고칩니다.

게이트웨이에서는 상태 코드와 응답 본문을 응답 템플릿(Response Template)으로 정해 두므로, 백엔드 없이도 API 계약을 먼저 확정하고 화면과 테스트를 진행할 수 있습니다.

정리하면 모의 통합은 백엔드 대신 정해진 응답을 돌려주어 API 계약을 먼저 굳히는 방법이며, 나중에 실제 통합으로 갈아 끼울 때 주소만 바꾸면 되도록 만드는 것이 핵심입니다.

4부. 통합(Integration)042

통합 타임아웃

뒤 서비스의 응답을 얼마나 기다리는지와 그 제약을 이해합니다

뒤쪽 서비스가 응답을 주지 않고 계속 붙잡고 있으면, 창구는 그 요청 하나에 매달려 다른 손님을 받지 못합니다. 그래서 어느 정도 기다리면 포기하는 시간 제한이 필요합니다.

통합 타임아웃(Integration Timeout)은 게이트웨이가 뒤 서비스의 응답을 기다리는 최대 시간입니다. 택배 기사가 문 앞에서 초인종을 누르고 기다리는 시간을 정해 두는 것과 같습니다. 아무리 오래 눌러도 문이 열리지 않으면 부재중으로 처리하고 다음 집으로 가야 하는데, 이 제한을 넘기면 게이트웨이는 기다림을 끊고 오류 응답을 돌려줍니다.

이 시간은 설정으로 늘릴 수 있는 폭이 정해져 있어서, 오래 걸리는 작업은 창구에서 붙잡고 있지 말고 작업을 큐에 넣은 뒤 접수증만 먼저 돌려주는 방식으로 바꾸는 편이 안전합니다.

즉 통합 타임아웃은 게이트웨이가 백엔드를 기다려 주는 한도를 정한 값이며, 그 한도를 넘는 일은 비동기 처리로 돌려 설계하는 것이 바람직합니다.

← 이전모의 통합(Mock Integration)다음 →통합 오류 전달

4부. 통합(Integration)043

통합 오류 전달

통합 실패가 어떤 응답으로 바뀌어 클라이언트에 전달되는지 압니다

쇼핑몰 앱에서 주문 조회를 눌렀는데 화면이 영원히 로딩 표시만 돌고 있다면 사용자는 앱이 고장 났다고 생각하고, 개발팀은 어디서 멈춘 것인지 알 방법이 없습니다. 통합 오류 전달(integration error propagation)은 API Gateway 뒤편의 백엔드에서 생긴 실패를 어떤 응답으로 바꿔 클라이언트에 돌려줄지 정하는 규칙입니다.

택배로 비유하면 집 앞에 물건을 두는 일이 통합이고, 물건이 깨졌을 때 빈 상자만 두고 가면 받는 사람은 무슨 일이 있었는지 알 수 없습니다.

그래서 택배 기사가 파손 사실을 적은 안내문을 상자에 붙여 두는 것처럼, 게이트웨이는 백엔드의 실패를 상태 코드(status code)와 오류 메시지로 포장해 돌려줍니다. 어느 단계에서 문제가 생겼는지에 따라 문구가 달라지고, 게이트웨이 자체가 실패한 경우와 백엔드가 실패한 경우를 구분해 표시합니다. 또한 모든 오류를 그대로 노출하지 않고 내부 주소나 스택처럼 민감한 내용은 감추고 클라이언트가 이해할 수 있는 형태로 다듬습니다.

정리하면 통합 오류 전달은 백엔드의 실패를 그대로 흘리지 않고 상태 코드와 메시지로 번역해 클라이언트가 대응할 수 있게 만드는 장치입니다. 게이트웨이 오류와 통합 오류를 구분하는 것, 그리고 내부 정보를 감추는 것이 핵심입니다.

통합 요청 매핑 템플릿

템플릿으로 요청을 원하는 모양으로 바꿔 넘기는 방법을 배웁니다

백엔드가 이름과 나이를 각각 firstName, age 라는 이름으로만 받는데 앱은 화면에서 입력한 값을 전혀 다른 모양으로 보낸다면, 서버는 받자마자 형식이 맞지 않는다며 거절합니다. 통합 요청 매핑 템플릿(integration request mapping template)은 클라이언트가 보낸 요청을 백엔드가 원하는 모양으로 바꿔 넘기는 중간 변환 규칙입니다.

회사 우편실에 비유하면 각 부서가 제각각인 봉투에 서류를 넣어 보내지만, 우편실 직원이 부서별 규칙에 맞는 표준 봉투로 다시 포장해 전달하는 것과 같습니다.

클라이언트의 본문, 헤더, 경로 값은 템플릿 안에서 각각 이름으로 참조되고, 그 값을 조합해 JSON 같은 원하는 형식으로 다시 씁니다. 필요하면 고정값을 덧붙이거나 날짜 형식을 바꾸는 등 백엔드가 기대하는 규격에 맞춰 손질합니다. 이 변환이 없으면 백엔드 코드를 고치거나 클라이언트마다 다른 요청을 따로 만들어야 합니다.

결국 통합 요청 매핑 템플릿은 요청을 백엔드의 규격에 맞춰 다시 포장하는 변환 계층입니다. 덕분에 백엔드는 자기 형식만 고집해도 되고 클라이언트는 그 사정을 알 필요가 없습니다.

통합 응답 매핑

백엔드의 응답을 API 응답 형식으로 변환하는 방법을 익힙니다

백엔드는 내부 사정이 담긴 원본 데이터를 그대로 돌려주는데, 그 안에는 사용자에게 보여줄 필요 없는 필드와 내부 코드가 섞여 있습니다. 통합 응답 매핑(integration response mapping)은 백엔드의 응답을 클라이언트가 기대하는 API 응답 형식으로 다시 쓰는 단계입니다.

식당에 비유하면 주방에서 나온 접시를 그대로 손님 식탁에 올리지 않고, 홀 직원이 먹기 좋게 담아내는 것과 같습니다.

백엔드가 보낸 상태 코드와 본문을 읽어 성공과 실패를 구분하고, 성공이면 필요한 값만 골라 새 형식으로 씁니다. 실패라면 오류 문구를 클라이언트가 이해할 수 있는 형태로 바꿔 내보내고, 헤더에 필요한 값을 더하기도 합니다. 이 과정 덕분에 백엔드가 교체되거나 필드 이름이 바뀌어도 클라이언트가 보는 응답 모양은 그대로 유지됩니다.

정리하면 통합 응답 매핑은 백엔드의 원본 응답을 API 계약에 맞는 모양으로 다듬는 마지막 포장 단계입니다. 내부 구조가 바뀌어도 외부에 보이는 응답을 일정하게 유지하는 것이 핵심입니다.

통합 디버깅

통합이 실패할 때 어느 지점을 확인해야 하는지 정리합니다

통합이 실패했을 때 클라이언트에는 그저 500 오류만 보이고, 게이트웨이 로그에는 요청이 들어왔다는 사실만 남아 있으면 어디를 고쳐야 할지 막막합니다. 통합 디버깅(integration debugging)은 요청이 게이트웨이를 거쳐 백엔드에 닿고 응답이 돌아오는 경로에서 어느 지점이 어긋났는지 좁혀 가는 작업입니다.

택배 분실을 찾을 때 집하장, 간선 터미널, 배송 기사 순서로 어느 단계에서 멈췄는지 확인하는 것과 같습니다.

먼저 게이트웨이가 요청을 제대로 받았는지, 권한과 경로 설정이 맞는지 확인합니다. 다음으로 매핑 템플릿이 만든 실제 요청 본문과 백엔드로 나간 주소, 돌아온 응답 코드를 로그에서 확인합니다. 백엔드가 응답했는데도 오류가 난다면 응답 매핑이나 형식 변환 쪽을 의심하고, 요청이 백엔드에 닿지도 않았다면 네트워크와 권한을 살핍니다.

결국 통합 디버깅은 요청과 응답 사이의 각 단계를 하나씩 확인해 끊긴 지점을 찾는 일입니다. 로그와 실제 요청 본문을 대조하는 습관이 가장 빠른 길입니다.

매핑 템플릿(Mapping Template)

템플릿이 언제 실행되고 무엇을 바꿀 수 있는지 이해합니다

클라이언트가 보낸 요청을 백엔드가 원하는 형식으로 바꿔야 하는데, 그 변환을 백엔드 코드 안에 넣으면 백엔드가 클라이언트마다 다른 형식을 떠안게 됩니다. 매핑 템플릿(mapping template)은 게이트웨이가 요청이나 응답을 중계하는 순간에 실행되어 데이터의 모양을 바꾸는 작은 변환 규칙입니다.

회사 문서 결재에 비유하면 부서마다 다른 서식을 결재 담당자가 정해진 양식으로 옮겨 적는 것과 같습니다.

템플릿은 요청이 백엔드로 나가기 직전과 응답이 클라이언트로 나가기 직전이라는 정해진 시점에만 실행되며, 그 밖의 시점에는 관여하지 않습니다. 실행될 때 요청 값, 경로 값, 단계 변수처럼 정해진 재료를 읽을 수 있고, 그 재료로 새 본문을 만들어 냅니다. 다만 템플릿은 데이터를 다른 모양으로 다시 쓰는 일만 하며, 백엔드 호출 자체나 권한 판단을 대신하지는 않습니다.

정리하면 매핑 템플릿은 정해진 시점에 정해진 재료만 가지고 데이터의 모양을 바꾸는 변환 규칙입니다. 언제 실행되고 무엇까지 할 수 있는지 아는 것이 안전하게 쓰는 첫걸음입니다.

5부. 요청·응답 변환과 모델048

VTL 기본 문법

매핑에 쓰는 Velocity 문법에서 꼭 필요한 부분만 익힙니다

매핑 템플릿을 쓰려면 그 안에 변환 로직을 적어야 하는데, 문법을 모르면 값을 하나 꺼내는 것조차 어렵습니다. VTL(Velocity Template Language)은 매핑 템플릿에 쓰이는 문법으로, 값 참조와 조건문, 반복문 정도만 알아도 대부분의 변환을 처리할 수 있습니다.

문서 양식에 비유하면 빈칸에 이름을 채워 넣는 일과 같습니다.

달러 기호로 시작하는 이름을 쓰면 요청이나 응답에서 꺼낸 값이 그 자리에 들어가고, 값이 없으면 빈칸으로 남습니다. 샵으로 시작하는 지시문으로 조건을 걸어 특정 값이 있을 때만 문장을 넣거나, 반복문으로 목록의 항목을 하나씩 펼칠 수 있습니다. 작은따옴표로 감싼 글자는 그대로 출력되고, 계산이나 비교 같은 간단한 식도 지원합니다.

결국 VTL은 템플릿이라는 빈 양식에 값을 채우고 조건과 반복으로 모양을 다듬는 문법입니다. 값 참조, 조건문, 반복문 세 가지만 익히면 대부분의 매핑을 만들 수 있습니다.

JSONPath와 JSON 변환

JSON에서 값을 꺼내 다른 JSON으로 재구성하는 방법을 배웁니다

여러 시스템이 JSON으로 데이터를 주고받는데, 응답 JSON 전체를 그대로 받아 필요한 값 하나를 꺼내려면 코드가 길어지고 구조가 조금만 바뀌어도 쉽게 깨집니다. 이 곤란을 줄이려고 JSON 안에서 값의 위치를 식으로 지정해 꺼내는 JSONPath와, 꺼낸 값을 다른 모양의 JSON으로 다시 조립하는 변환(mapping)이 함께 쓰입니다. 창고 비유로 보면 JSONPath는 물건을 찾는 지도이고 변환은 새 포장 상자에 물건을 옮겨 담는 작업입니다.

거대한 택배 창고에서 물건 하나를 찾을 때 모든 선반을 다 뒤지지 않고 "3번 선반 B칸"처럼 위치를 적어 두면 바로 꺼낼 수 있는데, JSONPath의 $ 기호는 창고 입구를, 점으로 이어 붙인 이름은 선반 이름을, 대괄호 안의 숫자는 몇 번째 칸인지를 뜻합니다. 조건에 맞는 것만 골라내는 필터를 붙이면 "값이 서울인 것만"처럼 범위를 좁힐 수도 있습니다.

이렇게 꺼낸 물건을 그대로 보내지 않고 새 상자의 오른쪽 칸에 왼쪽 값을 하나씩 채워 넣는 것이 변환이며, 이때 원본의 필드 이름과 순서가 달라도 새 상자 모양만 지키면 됩니다. 결국 JSONPath는 JSON 문서 안에서 원하는 값을 가리키는 경로 언어이고, 변환은 그렇게 꺼낸 값들을 원하는 구조의 JSON으로 재구성하는 규칙이라는 점이 핵심입니다.

모델(Schema Model)

요청과 응답의 구조를 스키마로 정의하는 이유와 효과를 압니다

요청 JSON의 모양이 호출할 때마다 조금씩 다르면 백엔드는 매번 다른 구조를 추측해야 하고, 문서에 적힌 형식과 실제로 오가는 데이터가 어긋나 장애 원인을 찾기 어려워집니다. API Gateway는 요청과 응답이 어떤 필드를 어떤 타입으로 가져야 하는지를 JSON Schema라는 약속으로 정의해 두는 모델 기능을 제공합니다.

아파트 관리사무소의 택배 접수 양식을 떠올리면 이해가 쉽습니다. 접수 양식에는 받는 사람, 연락처, 동, 호수 칸이 미리 정해져 있고 빈칸으로 두면 안 되는 필수 칸에는 표시가 붙어 있으며, 창구 직원은 이 양식만 보면 접수가 제대로 된 것인지 즉시 판단할 수 있습니다. 스키마도 똑같아서 필드 이름은 양식의 칸 이름, 타입은 그 칸에 들어가야 하는 값의 종류, 필수 여부는 반드시 채워야 하는 칸에 해당합니다.

이렇게 만든 모델 하나를 여러 API 경로에 함께 붙일 수 있어서, 약속을 한 곳에서 고치면 그것을 쓰는 요청과 응답의 기준이 한꺼번에 바뀝니다. 정리하면 모델은 요청과 응답의 구조를 기계가 읽을 수 있는 스키마로 못 박아, 문서와 실제 데이터가 같은 기준을 따르게 만드는 장치입니다.

5부. 요청·응답 변환과 모델051

요청 검증(Request Validation)

잘못된 요청을 백엔드에 닿기 전에 걸러내는 방법을 배웁니다

필수 값이 빠지거나 날짜 자리에 글자가 들어간 요청이 백엔드까지 도착하면 서버는 한참 데이터를 처리하다가 예외를 던지고, 그 실패가 로그를 어지럽히며 다른 정상 요청까지 느려지게 만들 수 있습니다. API Gateway는 요청을 백엔드로 넘기기 전에 미리 정의한 모델과 대조해 형식이 어긋난 요청을 그 자리에서 되돌려보내는 요청 검증 기능을 제공합니다.

회사 정문의 경비실을 떠올리면 구조가 그대로 대응됩니다. 방문객이 들어오기 전에 경비원이 방문증에 이름과 방문 목적이 적혀 있는지, 날짜 표기가 양식에 맞는지 확인하고, 하나라도 어긋나면 건물 안으로 들이지 않고 정문에서 돌려보냅니다. 게이트웨이도 같은 방식으로 필수 항목의 존재, 값의 타입, 허용된 형식을 확인하고, 통과하지 못한 요청에는 잘못됐다는 뜻의 응답을 곧바로 돌려줍니다.

다만 검증이 보는 것은 어디까지나 형식이지 내용의 참과 거짓이 아니어서, 형식이 맞는 요청이라도 업무 규칙에 어긋날 수 있다는 점은 백엔드가 따로 확인해야 합니다. 결국 요청 검증은 스키마를 기준으로 입구에서 형식을 심사해, 잘못된 요청이 내부 로직에 닿지 않게 막는 방어선입니다.

응답 검증

응답 스키마 검증이 주는 효과와 운영에서의 주의점을 압니다

백엔드가 배포 과정에서 필드 하나를 빠뜨리거나 숫자였던 값을 문자열로 바꿔 내려보내면, 클라이언트는 오류 없이 조용히 잘못된 화면을 그리다가 나중에야 문제를 발견하게 됩니다. 응답 검증은 백엔드가 돌려준 응답을 약속된 스키마와 대조해, 계약을 어긴 응답을 드러내는 기능입니다.

택배 출고대의 검수 담당자를 떠올리면 이해가 쉽습니다. 물건이 고객에게 나가기 전에 송장과 실제 물건을 맞춰 보고 수량이나 주소가 어긋나면 출고를 멈추듯이, 응답 검증도 응답이 나가는 관문에서 모양이 약속과 맞는지 확인합니다.

다만 요청 검증과 달리 응답은 이미 백엔드가 일을 끝낸 뒤에 검사하는 것이라 잘못된 응답을 되돌려 고칠 수는 없고, 대신 실패 기록과 알람을 남겨 문제를 빨리 알아차리게 하는 관측 수단에 가깝습니다. 또 스키마를 실제 응답보다 지나치게 엄격하게 잡아 두면 정상 응답이 실패로 기록되므로, 운영에서는 처음에 경고 수준으로 켜 두고 응답 모양이 안정된 뒤에 판단을 강화하는 편이 안전합니다.

정리하면 응답 검증은 응답 스키마를 계약서 삼아 백엔드와 클라이언트 사이의 약속 위반을 조기에 드러내는 안전장치입니다.

페이로드 크기 제한

큰 요청과 응답을 다룰 때의 제약과 우회 방법을 이해합니다

큰 이미지나 대량의 JSON을 한 번에 보내면 게이트웨이가 본문을 끝까지 받아내지 못하고 요청을 거절하거나, 받아 두고도 뒤쪽으로 넘기는 과정에서 실패해 원인을 찾기 어려운 오류가 납니다. 그래서 API Gateway는 요청과 응답 본문의 크기에 상한을 두고, 이를 넘는 페이로드는 애초에 통과시키지 않습니다.

화물 엘리베이터의 적재량 제한을 떠올리면 상황이 분명해집니다. 정해진 무게를 넘는 짐은 한 번에 실을 수 없으니 여러 상자로 나눠 여러 번 나르거나, 아예 엘리베이터를 쓰지 않고 창고에서 고객에게 직접 배송하는 우회로를 택합니다.

게이트웨이에서도 같은 전략을 씁니다. 큰 데이터는 잘게 나눠 여러 번 호출하는 방식으로 보내거나, 본문에 데이터를 담는 대신 파일을 따로 올려 두고 그 위치를 가리키는 주소만 주고받는 방식으로 우회합니다.

이때 상한은 요청과 응답 양쪽에 각각 적용되고, 압축을 하더라도 풀린 뒤의 크기가 아니라 실제로 오가는 바이트를 기준으로 판단된다는 점을 기억해야 합니다. 결국 페이로드 크기 제한은 게이트웨이를 지나는 본문의 물리적 한계를 정해 둔 규칙이며, 큰 데이터는 나누어 보내거나 외부 저장소로 돌리는 설계로 대응해야 합니다.

이진 데이터 처리

이미지나 파일을 주고받을 때 필요한 설정을 익힙니다

이미지나 PDF 같은 파일을 JSON 기반 API로 그대로 주고받으려 하면, 텍스트를 전제로 만들어진 규약이 중간에서 데이터를 깨뜨려 파일이 열리지 않는 일이 생깁니다. API Gateway는 이런 이진 데이터(binary data)를 안전하게 실어 나르기 위해 본문을 텍스트 형태로 변환해 감싸는 방식을 지원합니다.

액자를 우편으로 보내는 상황을 떠올리면 이해가 쉽습니다. 유리와 틀이 있는 액자를 봉투에 그대로 넣을 수 없으니 완충재로 감싸 튼튼한 상자에 넣어 보내고, 받는 쪽에서는 상자를 열어 포장을 풀어내야 원래 액자가 나옵니다.

게이트웨이도 이진 본문을 그대로 흘려보내지 않고 base64라는 방식으로 글자 형태로 바꿔 감싼 뒤 전달하며, 받는 쪽은 그 글자를 다시 원래 바이트로 풀어 사용합니다. 이때 어떤 콘텐츠 타입을 이진 데이터로 다룰지 설정에 등록해 두어야 하고, 요청과 응답의 헤더에 적힌 타입을 보고 게이트웨이가 변환 여부를 판단합니다. 변환은 데이터를 커지게 만들기 때문에 큰 파일에는 크기 제한과 함께 맞물려 문제가 되므로, 아주 큰 파일은 게이트웨이를 거치지 않고 저장소에 직접 올리고 그 주소만 주고받는 방식이 권장됩니다.

정리하면 이진 데이터 처리는 본문을 base64로 감싸 텍스트 규약 위로 안전하게 옮기고, 받는 쪽에서 다시 풀어내는 설정과 절차를 뜻합니다.

콘텐츠 협상과 헤더 변환

Accept 같은 헤더를 이용해 응답 형태를 바꾸는 방법을 배웁니다

휴대폰 앱과 브라우저가 같은 주소를 부르는데 앱은 간결한 데이터를, 브라우저는 보기 좋은 화면을 원한다고 해 보십시오. 서버가 이 요청을 구분하지 못하면 모두에게 같은 모양의 응답만 돌려주게 되고, 앱은 화면용 표시를 걸러내느라 일을 두 배로 하고 브라우저는 데이터만 받아 빈 화면을 보게 됩니다.

콘텐츠 협상(content negotiation)은 이렇게 클라이언트가 원하는 응답 형태를 미리 알려 주고 서버가 그에 맞춰 답하는 약속이며, API Gateway에서는 요청 헤더를 읽어 백엔드로 넘기는 값이나 응답 형식을 바꾸는 헤더 변환과 함께 쓰입니다. 식당 비유로 보면 손님이 주문서에 매운맛과 양을 적어 내는 칸이 협상이고, 주방에서 그 칸을 읽어 조리법을 바꾸는 일이 헤더 변환이라고 할 수 있습니다.

손님이 아무것도 적지 않았을 때를 대비해 기본 조리법을 정해 두는 것처럼, Accept 헤더가 없으면 돌려줄 기본 형식을 정해 두어야 합니다. 홀 직원이 주문서를 그대로 주방에 넘기지 않고 주방이 알아보는 말로 다시 적어 전달하는 단계가 바로 게이트웨이가 헤더를 변환하는 지점입니다.

결국 콘텐츠 협상은 Accept 같은 요청 헤더로 원하는 응답 형태를 밝히는 절차이고, 헤더 변환은 게이트웨이가 그 요청과 응답의 헤더를 백엔드가 이해하는 형태로 바꿔 주는 기능입니다.

오류 응답 표준화

오류 형식을 일관되게 만들어 클라이언트 처리를 단순하게 합니다

서비스마다 오류를 제각각 돌려주면 클라이언트는 어떤 경우에 무엇이 잘못됐는지 알기 위해 서비스 수만큼의 예외 처리를 따로 만들어야 합니다. 어떤 곳은 200을 보내면서 본문에 실패를 적고 어떤 곳은 알 수 없는 문구만 던지면, 화면에는 "알 수 없는 오류"만 뜨고 로그를 뒤져야 원인을 찾을 수 있습니다.

오류 응답 표준화는 이 문제를 없애기 위해 상태 코드와 오류 본문의 모양을 하나로 정하는 일이며, API Gateway에서는 백엔드가 낸 오류를 정해진 형식으로 다시 감싸 클라이언트에 전달하는 방식으로 구현합니다.

택배 비유로 보면 배송이 실패했을 때 각 지점이 저마다 다른 말로 전화하는 대신, 정해진 양식에 수취인과 사유와 재배송 여부를 적어 보내는 것과 같습니다. 양식이 하나면 받는 쪽은 어느 칸을 봐야 하는지 이미 알고 있으므로, 같은 오류라면 어느 서비스에서 왔든 같은 코드와 같은 설명을 읽게 됩니다.

게이트웨이는 서비스가 보낸 원래 오류를 그대로 흘리지 않고 정해진 틀에 옮겨 담는 창구 역할을 하고, 그 덕분에 클라이언트의 오류 처리 코드는 한 벌로 끝납니다. 정리하면 오류 응답 표준화는 상태 코드와 오류 본문의 구조를 공통 규약으로 맞춰, 클라이언트가 서비스별 예외 처리를 따로 만들지 않게 하는 설계입니다.

응답 형식 호환성 유지

응답 구조를 바꿀 때 기존 클라이언트를 깨지 않는 방법을 배웁니다

이미 쓰고 있는 응답에서 필드 이름을 바꾸거나 타입을 바꾸면, 그 응답을 파싱하던 앱들은 갑자기 값을 읽지 못하고 멈춥니다. 서버 쪽에서는 작은 정리였지만 배포 다음 날 모든 구버전 앱이 오류를 쏟아 내는 일이 실제로 벌어집니다.

응답 형식 호환성 유지란 이렇게 응답 구조를 바꿀 때 기존 클라이언트를 깨뜨리지 않는 방식으로만 바꾸는 원칙이며, API Gateway에서는 변환 규칙과 버전을 나눠 구버전 호출은 예전 모양으로 계속 답하게 하는 식으로 지킵니다.

아파트 비유로 보면 현관 비밀번호를 바꾸면서 예전 번호를 곧바로 막아 버리면 그 번호를 외우던 가족이 모두 들어오지 못합니다. 그래서 새 번호를 추가하고 예전 번호는 한동안 함께 열어 둔 뒤, 모든 세대가 새 번호를 쓴다는 것이 확인된 다음에야 닫는 순서를 밟습니다.

응답에 필드를 더하는 것은 보통 안전하지만 필드를 빼거나 이름과 타입을 바꾸는 것은 위험하므로, 바꿔야 한다면 새 필드를 나란히 두고 옛 필드를 유지하는 방식을 씁니다. 이렇게 하면 새 클라이언트는 새 필드를, 옛 클라이언트는 옛 필드를 읽으며 같은 기간을 함께 지나갈 수 있습니다.

결국 응답 형식 호환성 유지는 덧붙이기는 하되 갑자기 빼거나 바꾸지 않고 버전과 유예 기간을 두어 옮겨 가게 하는 운영 원칙입니다.

변환 디버깅

매핑 결과가 의도와 다를 때 확인할 지점을 정리합니다

매핑 규칙을 분명히 적었다고 생각했는데 응답에 값이 비어 있거나 전혀 다른 필드가 채워져 돌아오면, 어디서 어긋났는지부터 막막해집니다. 요청은 정상으로 보이고 백엔드도 정상이라고 하는데 게이트웨이를 지나온 결과만 틀리면 확인할 곳이 한정되지 않아 시간을 허비하기 쉽습니다.

변환 디버깅은 이때 어느 지점을 어떤 순서로 확인할지 정해 두는 절차이며, API Gateway에서는 요청 매핑과 통합 요청, 통합 응답, 응답 매핑이라는 구간을 나눠 각 구간의 실제 값을 보는 방식으로 진행합니다.

택배 비유로 보면 물건이 잘못 도착했을 때 보낸 사람이 잘못인지, 중간 허브에서 라벨이 바뀌었는지, 배송 기사가 다른 집에 놓았는지를 운송장 기록으로 하나씩 좁혀 가는 과정과 같습니다.

먼저 클라이언트가 보낸 원본 요청을 확인하고, 다음으로 게이트웨이가 백엔드로 넘긴 요청이 규칙대로 바뀌었는지 봅니다. 그다음 백엔드가 실제로 돌려준 응답을 보고, 마지막으로 그 응답이 응답 매핑을 거치며 어떻게 바뀌었는지 대조하면 어긋난 구간이 남습니다.

경로 표기나 타입 불일치, 없는 필드 참조처럼 규칙 문법의 작은 실수가 원인인 경우가 많으므로 로그와 함께 매핑 표현식을 한 줄씩 확인하는 것이 빠릅니다. 정리하면 변환 디버깅은 요청과 응답이 게이트웨이를 지나는 각 구간의 값을 순서대로 대조해, 규칙이 의도와 달라진 지점을 찾아내는 작업입니다.

인증과 인가의 차이

누구인지 확인하는 일과 무엇을 할 수 있는지 정하는 일을 구분합니다

건물에 들어온 사람에게 모든 문을 열어 주면, 출입증을 확인했다는 이유만으로 남의 사무실까지 드나드는 일이 생깁니다. 반대로 신원 확인 없이 권한만 세밀하게 나눠 두면, 누가 왔는지 모르는 채로 권한을 판단해야 하니 기준 자체가 서지 않습니다.

인증(authentication)은 이 사람이 누구인지 확인하는 일이고 인가(authorization)는 그 사람이 무엇을 할 수 있는지 정하는 일이며, API Gateway에서는 두 단계를 나란히 두고 인증이 끝난 뒤에 인가를 판단하도록 구성합니다.

아파트 비유로 보면 경비실에서 신분증과 세대를 대조해 주민임을 확인하는 것이 인증이고, 그 주민이 헬스장과 주차장 중 어디를 쓸 수 있는지 출입증 권한을 보고 판단하는 것이 인가입니다.

신분증 확인을 통과하지 못한 사람은 권한을 물을 단계까지 가지 못하고, 주민으로 확인된 사람이라도 자기 세대 권한 밖의 시설은 열리지 않습니다. 이 순서 덕분에 인가는 항상 확인된 신원을 전제로 판단할 수 있고, 인증 정보가 없을 때와 권한이 모자랄 때를 서로 다른 오류로 구분해 안내할 수 있습니다.

결국 인증은 신원을 확정하는 관문이고 인가는 확정된 신원에 허용 범위를 부여하는 단계로, 앞의 것이 뒤의 것의 전제가 됩니다.

IAM 인증

AWS 자격 증명으로 서명해 API를 호출하는 방식을 이해합니다

API를 아무나 부를 수 있게 두면, 주소만 아는 사람이 남의 계정으로 데이터를 조회하거나 지우는 요청을 마음대로 보낼 수 있습니다. 비밀 키를 코드에 적어 두는 방식으로 막으려 해도 그 키가 유출되는 순간 막을 방법이 사라집니다.

IAM 인증은 AWS의 자격 증명 체계인 IAM(Identity and Access Management)으로 요청에 서명해 호출자를 증명하는 방식이며, API Gateway에서는 서명된 요청을 받아 자격 증명의 주체와 권한을 확인한 뒤 통과시킵니다.

회사 사옥 비유로 보면 사원증에 이름과 부서와 출입 구역이 적혀 있고, 정문의 단말기가 그 사원증의 서명이 위조되지 않았는지 확인한 다음 정해진 구역만 열어 주는 것과 같습니다.

요청을 보낼 때 비밀 키 자체를 실어 보내는 것이 아니라 그 키로 계산한 서명을 붙이고, 받는 쪽은 같은 계산을 다시 해 보고 값이 맞는지로 진짜 호출자인지 판단합니다. 서명에는 요청 시각이 함께 들어가므로 한참 지난 서명은 거절되고, 그래서 가로챈 요청을 그대로 다시 보내는 일도 막힙니다.

정리하면 IAM 인증은 AWS 자격 증명으로 요청에 서명을 붙여 호출자의 신원을 증명하고, 게이트웨이가 그 서명과 권한을 검증해 API 접근을 허용하는 방식입니다.

IAM 정책과 API 권한

어떤 정책이 어떤 호출을 허용하는지 읽는 법을 배웁니다

사내 시스템을 API로 열어 두면 퇴사자의 남은 키나 테스트용으로 만든 토큰이 관리자용 삭제 호출까지 그대로 실행하는 일이 생깁니다. 이런 사고를 막으려고 AWS는 누가 어떤 호출을 할 수 있는지를 문서로 적어 두고 요청마다 판정하는 IAM 정책(IAM Policy)을 두었습니다.

이것은 회사 사옥의 출입 규정과 같습니다. 정책 문서는 누가(Principal) 어느 문으로(Action) 어디까지(Resource) 들어갈 수 있는지를 적은 규정표이고, AWS는 요청이 들어올 때마다 이 표를 펼쳐 통과인지 아닌지를 판정합니다.

규정표에 적히지 않은 문은 기본적으로 잠겨 있으며, 한 줄이라도 명시적 거부(Deny)가 있으면 다른 허용을 모두 덮습니다. 또 규정표는 사람에게 발급하는 출입증에 붙일 수도 있고 문 자체에 붙일 수도 있어서, 같은 요청도 양쪽 규정을 함께 확인합니다.

정리하면 IAM 정책은 요청의 주체와 동작, 대상을 적어 허용 여부를 판정하는 JSON 문서입니다. API Gateway에서도 특정 호출을 열어 줄지 말지를 이 문서의 판정 결과에 맡깁니다.

리소스 정책(Resource Policy)

API 쪽에서 호출 출처와 대상을 제한하는 정책을 작성합니다

API를 인터넷에 열어 두었더니 전혀 모르는 외부 계정이 우리 API를 자기 서비스의 일부처럼 호출해 요금과 로그를 남기는 일이 생깁니다. 이때 필요한 것이 호출을 받는 쪽, 즉 API나 버킷 같은 리소스에 직접 붙여 어느 계정의 누구까지 받겠다는 범위를 적는 리소스 정책(Resource Policy)입니다.

이것은 아파트 정문 경비실에 붙은 방문 허용 명단과 같습니다. 세대별 출입 카드는 개인에게 발급되는 자격 증명 정책이고, 현관에 붙은 명단은 문 쪽에서 손님을 고르는 리소스 정책입니다.

명단에는 누가(Principal) 어떤 동작(Action)을 어디까지 할 수 있는지가 적히며, 자격 증명 정책과 달리 대상 주체를 반드시 이름으로 밝혀야 합니다. 경비원은 손님이 카드를 대든 명단을 대든 두 가지를 모두 확인한 뒤 문을 열어 주고, 명단에 없는 사람은 카드가 있어도 들이지 않습니다.

정리하면 리소스 정책은 자격 증명이 아니라 보호 대상 쪽에 붙어 호출 출처와 대상을 제한하는 정책입니다. API Gateway에서는 이 정책으로 특정 계정이나 특정 네트워크에서 오는 호출만 받도록 좁힐 수 있습니다.

Lambda 권한 부여자(Lambda Authorizer)

직접 만든 인증 로직으로 요청을 검사하는 방법을 익힙니다

기본으로 제공되는 인증만으로는 우리 회사만의 규칙, 예를 들어 사내 부서 코드가 맞아야 한다거나 특정 시간대에만 호출을 허용한다는 조건을 표현할 수 없습니다. 그런 규칙을 코드로 직접 심사하게 해 주는 것이 Lambda 권한 부여자(Lambda Authorizer)입니다.

이것은 건물 로비에 따로 앉힌 전담 경비원과 같습니다. 자동 회전문은 카드가 유효한지만 보지만, 경비원은 방문 목적과 예약 명단까지 직접 대조해 우리 건물 규정에 맞는지 판단합니다.

경비원은 요청과 함께 온 토큰이나 헤더를 받아 자기 판단으로 통과 여부를 정하고, 통과시키면 그 사람의 부서와 아이디 같은 정보를 적은 허용 증명서를 돌려줍니다. 그러면 뒤쪽 문들은 그 증명서에 적힌 범위만큼만 열립니다.

정리하면 Lambda 권한 부여자는 인증 로직을 직접 작성한 함수에 맡기고 그 결과로 요청을 통과시키는 방식입니다. 그래서 사내 규칙처럼 표준만으로 표현하기 어려운 조건을 코드로 검사할 때 씁니다.

Cognito 사용자 풀 권한 부여자

로그인한 사용자의 토큰으로 API를 보호하는 방법을 배웁니다

이것은 회원제 헬스장과 같습니다. 프런트 데스크에서 가입과 로그인을 처리하고 회원증을 발급하면, 각 시설 입구에서는 회원증이 우리 것이 맞는지만 확인하면 됩니다.

Cognito 사용자 풀(User Pool)이 그 프런트 데스크 역할을 해서 가입과 로그인, 토큰 발급을 맡고, API Gateway의 권한 부여자는 입구에서 토큰의 서명과 유효기간을 확인하는 검표원 역할을 합니다. 검표를 통과하면 토큰 안의 사용자 식별자와 그룹 정보가 요청에 실려 뒤쪽 서비스까지 전달됩니다.

정리하면 Cognito 사용자 풀 권한 부여자는 이미 발급된 로그인 토큰을 검증해 API를 보호하는 방식입니다. 로그인 처리를 직접 만들지 않고도 사용자별 접근을 구분할 수 있습니다.

JWT 권한 부여자

HTTP API에서 토큰을 검증하는 방식을 익힙니다

로그인은 다른 서비스가 처리하는데 그 서비스가 표준 형식의 토큰만 내준다면, API마다 검증 코드를 새로 쓸 이유가 없습니다. HTTP API에서는 이런 표준 토큰을 설정만으로 검증하는 JWT 권한 부여자(JWT Authorizer)를 제공합니다.

이것은 규격이 통일된 여권과 같습니다. 여권은 발급국이 서명하고 유효기간과 소지자 정보를 적어 두므로, 입국 심사대는 발급자가 우리가 신뢰하는 나라인지와 서명이 위조되지 않았는지만 확인하면 됩니다.

JWT(JSON Web Token)도 발급자(issuer)와 대상(audience), 유효기간, 서명을 담고 있어서 권한 부여자는 이 항목들을 미리 정한 값과 대조합니다. 서명 검증에 필요한 공개 키는 공개된 주소에서 가져오며, 대조에 실패한 요청은 뒤쪽 서비스에 닿기 전에 거절됩니다.

정리하면 JWT 권한 부여자는 표준 형식의 토큰을 설정된 발급자와 대상, 서명 기준으로 검증하는 방식입니다. 별도 함수 없이 HTTP API에서 토큰 검사를 처리할 때 씁니다.

권한 부여자 캐싱

인증 결과를 재사용해 지연과 비용을 줄이는 방법을 압니다

모든 요청마다 권한 부여자가 토큰을 검증하면 호출량이 늘수록 지연이 쌓이고 Lambda를 쓴다면 실행 요금도 함께 늘어납니다. 같은 토큰으로 온 요청은 판정 결과를 잠시 재사용하는 것이 권한 부여자 캐싱(Authorizer Caching)입니다.

이것은 놀이공원의 재입장 도장과 같습니다. 처음 입장할 때 신분을 확인하고 손등에 도장을 찍어 두면, 같은 날 다시 들어올 때는 매표소에서 처음부터 심사하지 않고 도장만 봅니다.

권한 부여자도 첫 요청에서 토큰을 검증한 뒤 그 결과를 토큰별로 저장해 두고, 유효 시간(TTL) 안에 같은 토큰이 오면 저장된 판정을 그대로 돌려줍니다. 그래서 검증 함수 호출과 그에 따르는 지연이 줄지만, 판정을 바꾸려면 캐시가 만료되기를 기다리거나 캐시를 비워야 합니다.

정리하면 권한 부여자 캐싱은 토큰별 인증 결과를 유효 시간 동안 재사용해 지연과 비용을 줄이는 기능입니다. 대신 권한을 회수한 뒤에도 만료 전까지 이전 판정이 살아 있을 수 있다는 점을 감안해야 합니다.

권한 부여자 응답 형식

인증 결과에 어떤 정보를 담아 넘길 수 있는지 이해합니다

문 앞에서 신분을 확인했는데 확인한 사람이 아무 기록도 남기지 않고 그냥 들여보낸다면, 안에서 무슨 일이 벌어져도 누가 들어왔는지 나중에 알 수가 없습니다. Amazon API Gateway의 권한 부여자 응답 형식(Authorizer response format)은 이 확인 결과를 정해진 모양으로 남겨서, 뒤쪽 서버가 그 정보를 그대로 이어받아 쓰게 만든 장치입니다.

회사 정문 경비실을 떠올리면 이해가 쉽습니다. 경비원은 방문객을 확인한 뒤 이름과 소속을 적은 방문증을 끼워 주고, 어느 층까지 갈 수 있는지 범위를 함께 적어 줍니다.

권한 부여자도 똑같이 누구인지를 나타내는 식별자(principalId)와 어디까지 허용하는지를 적은 정책 문서(policyDocument), 그리고 이름이나 부서처럼 뒷단에 넘길 잡다한 메모(context)를 한 묶음으로 돌려줍니다. 뒷단의 서버는 이 메모를 읽어 사용자마다 다른 데이터를 보여 주거나 다르게 처리할 수 있습니다.

정리하면 권한 부여자 응답은 신원과 허용 범위와 부가 정보를 한 번에 담아 전달하는 표준 봉투이고, API Gateway는 이 봉투를 검사해 통과 여부를 정한 뒤 내용을 뒷단으로 넘깁니다. 형식은 REST API와 HTTP API에서 조금씩 다르므로 쓰는 유형의 문서를 확인해야 합니다.

공개 API와 비공개 API 구분

누구에게 열어야 하는지에 따라 보호 수준을 정합니다

사내 재고 조회 API의 주소가 외부에 알려지는 순간, 회사 직원만 보려던 숫자를 경쟁사도 그대로 읽을 수 있게 됩니다. Amazon API Gateway에서 공개 API와 비공개 API를 구분하는 일은 그래서 단순한 설정이 아니라, 누구에게 문을 열어 줄지 정하는 설계 결정입니다.

건물 출입 방식에 빗대면 차이가 분명해집니다. 로비는 누구나 들어올 수 있지만 안내 데스크에서 이름을 적고 목적을 말해야 하고, 사무실 층은 직원증이 있어야 열리며, 전산실은 별도의 잠금과 승인 명단까지 갖춥니다.

공개 API는 로비처럼 익명 호출을 허용하되 사용량 제한(Usage plan)과 키(API key)로 남용을 막고, 비공개 API는 직원증에 해당하는 리소스 정책(Resource policy)이나 가상 사설망 안에서만 통하는 엔드포인트로 접근을 좁힙니다. 같은 기능이라도 어느 쪽에 두느냐에 따라 필요한 인증 수단과 노출되는 공격 면이 달라집니다.

결국 공개와 비공개의 차이는 인증 수단의 유무가 아니라 허용할 대상의 범위를 어디까지 열어 둘 것인가에 있습니다. 먼저 소비자가 사내인지 외부인지 정하고, 그 범위에 맞춰 인증과 네트워크 경계를 겹쳐 두는 것이 안전합니다.

서비스 간 호출 인증

내부 서비스끼리 안전하게 호출하는 방법을 배웁니다

서비스 하나가 다른 서비스의 주소를 그냥 호출하면, 그 주소를 아는 누구나 내부 기능을 실행할 수 있게 됩니다. 그래서 내부 호출에도 신원을 붙이는 서비스 간 호출 인증(service-to-service authentication)이 필요하고, Amazon API Gateway는 이 경계를 만드는 접점이 됩니다.

회사 부서끼리 공문을 주고받는 모습을 떠올리면 쉽습니다. 아무 종이에나 결재를 받지 않고, 발신 부서의 직인과 문서 번호가 찍힌 공문만 접수하며, 접수처는 그 직인이 진짜인지 대조합니다.

서비스도 마찬가지로 호출하는 쪽이 자기 자격 증명으로 요청에 서명(SigV4)을 남기고, 받는 쪽은 그 서명과 권한을 확인해 통과시킵니다. 자격 증명을 코드에 박아 두기 어렵다면 권한 부여자(Authorizer)를 두어 토큰을 대신 검사하게 하고, 네트워크 수준에서는 사설 연결만 받도록 좁힐 수 있습니다.

정리하면 서비스 간 호출 인증은 내부망이라는 이유로 신뢰하지 않고, 매 요청마다 누가 보냈는지 확인하는 절차입니다. 자격 증명 관리와 서명 검증, 네트워크 경계를 함께 두는 것이 핵심입니다.

OAuth 2.0과 API Gateway

외부 인증 서버와 연동하는 전체 흐름을 이해합니다

우리 서비스가 사용자의 비밀번호를 직접 받아 들고 다른 업체의 데이터까지 대신 읽는다면, 그 비밀번호가 한 번 새는 순간 피해가 걷잡을 수 없이 커집니다. OAuth 2.0은 비밀번호 대신 위임받은 증표만 주고받자는 약속이고, API Gateway는 그 증표를 검사하는 문지기 역할을 합니다.

호텔 프런트가 객실 출입 카드를 발급하는 장면을 떠올리면 흐름이 보입니다. 사용자는 인증 서버(Authorization server)라는 프런트에서 로그인해 허용 범위(scope)가 적힌 카드, 곧 액세스 토큰(Access token)을 받고 우리 API에는 그 카드만 내밉니다.

API Gateway는 카드가 위조되지 않았는지 서명을 확인하고 유효 기간과 허용 범위를 읽어 통과 여부를 정하며, 이 검사를 JWT 권한 부여자나 Amazon Cognito 같은 서비스에 맡길 수 있습니다. 카드가 만료되면 사용자는 다시 로그인하지 않고 갱신 토큰(Refresh token)으로 새 카드를 받습니다.

결국 OAuth 2.0 연동은 비밀번호를 우리 쪽에 두지 않고, 인증 서버가 발급한 토큰을 게이트웨이가 검증하는 구조입니다. 토큰의 서명과 범위를 확인하는 지점이 곧 보안의 중심입니다.

인증 실패 응답 설계

401과 403을 언제 돌려줄지 기준을 세웁니다

로그인이 안 된 사람과 로그인은 했지만 권한이 없는 사람에게 같은 오류를 돌려주면, 클라이언트는 다시 로그인해야 하는지 문의해야 하는지 판단할 수 없습니다. 그래서 인증 실패 응답 설계에서는 401과 403을 언제 돌려줄지 기준을 먼저 세웁니다.

건물 로비의 경비원을 떠올리면 기준이 또렷해집니다. 신분증을 아예 내밀지 못한 사람에게는 신분증을 보여 달라고 요청하고, 신분증은 있지만 출입이 금지된 층으로 가려는 사람에게는 그 층은 안 된다고 알려 줍니다.

인증(Authentication)이 안 된 요청에는 401 Unauthorized를 돌려주며 어떤 방식으로 증명하면 되는지 알리는 헤더(WWW-Authenticate)를 함께 붙이고, 인증은 됐지만 허용 범위(scope)나 정책에 걸린 요청에는 403 Forbidden을 돌려줍니다. 응답 본문에는 내부 규칙이나 대상의 존재 여부를 흘리지 않고 짧고 일관된 오류 코드만 담습니다.

정리하면 401은 다시 증명하라는 뜻이고 403은 증명은 됐지만 안 된다는 뜻이며, 이 구분이 클라이언트의 재시도와 사용자 안내를 갈라 놓습니다. 상태 코드와 헤더, 본문 형식을 한 가지 규칙으로 통일해 두어야 합니다.

인증 우회 점검

건물의 모든 출입문 도면을 그려 놓고 하나씩 잠금을 확인하는 작업과 같습니다.

결국 인증 우회 점검은 한 번의 설정 검토가 아니라 라우트 목록과 실제 호출 시험을 주기적으로 맞춰 보는 일입니다. 새 경로를 추가할 때 같은 점검이 자동으로 돌아가게 해 두어야 구멍이 남지 않습니다.

스로틀링(Throttling)

초당 요청 수를 제한해 뒤 서비스를 보호하는 원리를 이해합니다

인기 상품 할인 행사가 시작되는 순간 수만 명이 동시에 앱을 열면, 아무리 잘 만든 서비스라도 뒤에서 데이터를 처리하는 서버가 순식간에 한계에 부딪혀 응답을 멈춥니다. 정상적인 사용자까지 함께 피해를 보는 이런 상황을 막기 위해, Amazon API Gateway는 들어오는 요청의 속도 자체를 제한하는 스로틀링(Throttling) 기능을 제공합니다.

이 원리는 택배 물류센터의 컨베이어 벨트와 같습니다. 아무리 많은 택배 상자가 밀려와도 벨트가 감당할 수 있는 속도만큼만 올려 보내고 나머지는 잠시 대기시키면, 뒤에서 분류하는 작업자들이 쓰러지지 않습니다.

API Gateway도 초당 처리할 수 있는 요청 수를 정해 두고 그 이상이 들어오면 받아주지 않으며, 거절된 요청에는 처리량 초과를 뜻하는 응답을 돌려보냅니다. 덕분에 뒤쪽 서버는 항상 예측 가능한 부하만 받게 됩니다.

정리하면 스로틀링은 초당 요청 수(rate)에 상한을 두어 과부하가 뒤 서비스로 번지지 않게 막는 안전장치이며, 거절된 요청은 클라이언트가 나중에 다시 시도하도록 유도하는 방식으로 동작합니다.

계정 수준과 스테이지 수준 한도

한도가 어느 범위에 적용되는지 구분합니다

서비스가 커지면 한 계정 안에 여러 스테이지와 여러 API가 섞이게 되는데, 어느 범위에 한도를 걸었는지 헷갈리면 개발 환경의 테스트 트래픽이 운영 환경의 한도를 잡아먹는 사고가 생깁니다. Amazon API Gateway는 이런 혼란을 막기 위해 한도를 계정 수준과 스테이지 수준으로 나누어 적용합니다.

아파트 단지의 물 공급을 떠올리면 이해가 쉽습니다. 단지 전체가 수도 본관과 맺은 계약 용량이 하나 있고, 각 동마다 별도로 잠근 밸브 한도가 또 있습니다.

계정 수준 한도는 이 단지 전체 계약 용량처럼 한 리전(Region)의 계정 안에서 모든 API와 스테이지가 합쳐서 쓸 수 있는 총량이고, 스테이지 수준 한도는 동별 밸브처럼 특정 스테이지 하나에 걸리는 한도입니다. 두 한도는 서로를 대체하지 않고 동시에 적용되므로, 스테이지 한도가 남아 있어도 계정 전체 총량을 다 쓰면 더 이상 요청이 통과하지 못합니다.

결국 계정 수준은 리전 단위의 전체 상한, 스테이지 수준은 개별 스테이지의 상한이며, 실제 허용량은 둘 중 먼저 걸리는 쪽에 의해 결정된다고 정리할 수 있습니다.

버스트와 지속 처리량

순간 폭주 허용량과 평균 처리량의 차이를 이해합니다

평소에는 초당 몇 건만 오던 요청이 특정 시간에만 수십 배로 몰리는 서비스에서, 순간 폭주를 그대로 막아 버리면 정상 사용자까지 거절되고 그렇다고 전부 받아 주면 뒤 서버가 버티지 못합니다. Amazon API Gateway는 이 둘 사이의 균형을 잡기 위해 버스트(Burst)와 지속 처리량(Rate)이라는 두 가지 개념으로 한도를 표현합니다.

옥상 물탱크를 떠올리면 구조가 그대로 보입니다. 탱크에는 평소에 일정한 속도로 물이 채워지는데, 이 채우는 속도가 지속 처리량입니다.

갑자기 여러 세대가 동시에 물을 쓰면 탱크에 고여 있던 물을 순간적으로 끌어다 쓰게 되고, 이 고여 있는 양이 버스트 허용량입니다. 탱크가 비면 더 이상 순간적으로 많이 쓸 수 없고 다시 채워질 때까지 기다려야 하듯, 버스트를 다 소진한 뒤에는 지속 처리량만큼만 요청이 통과합니다.

정리하면 지속 처리량은 오랜 시간 유지할 수 있는 평균 속도이고 버스트는 짧은 순간에 몰아서 쓸 수 있는 여유분이며, API Gateway는 이 둘을 함께 관리해 순간 폭주를 흡수하면서도 전체 부하는 일정하게 유지합니다.

메서드별 스로틀 설정

특정 API나 메서드만 따로 제한하는 방법을 배웁니다

하나의 API 안에서도 목록 조회는 가볍고 이미지 생성이나 대량 검색은 무거운데, 모든 메서드에 같은 한도를 걸면 가벼운 호출은 필요 이상으로 막히고 무거운 호출은 충분히 보호되지 않습니다. Amazon API Gateway는 이런 문제를 해결하려고 API나 메서드 단위로 스로틀 설정을 따로 두는 방법을 제공합니다.

놀이공원의 대기 줄을 생각하면 이해가 빠릅니다. 공원 전체 입장객 수를 제한하면서도 인기 놀이기구 하나에는 따로 대기 인원 상한을 두면, 사람이 몰리는 곳만 정밀하게 조절할 수 있습니다.

API Gateway도 마찬가지로 스테이지나 특정 메서드에 별도의 지속 처리량과 버스트 값을 지정할 수 있고, 그 값이 지정된 대상에는 계정이나 스테이지의 기본 한도 대신 그 설정이 우선 적용됩니다. 반대로 따로 정하지 않은 메서드는 기본 한도를 그대로 따릅니다.

결국 메서드별 스로틀 설정은 API의 특정 경로나 HTTP 메서드에 개별 상한을 걸어, 비용이 크거나 위험한 호출만 촘촘하게 보호하는 수단이라고 정리할 수 있습니다.

API 키별 사용량 제한

사용량 계획으로 키마다 다른 한도를 두는 방법을 익힙니다

여러 고객에게 API를 열어 주는 서비스에서 한 고객의 대량 호출이 다른 고객의 정상적인 호출까지 마비시키면, 어떤 고객이 얼마나 썼는지 구분할 방법부터 필요해집니다. Amazon API Gateway는 이때 API 키(API Key)와 사용량 계획(Usage Plan)을 묶어 키마다 다른 한도를 두는 방식을 제공합니다.

헬스장 정기권을 떠올리면 비유가 자연스럽습니다. 출입증에는 회원 번호가 적혀 있어 누가 들어왔는지 구분되고, 정기권 종류에 따라 하루 이용 횟수와 시간대가 다르게 정해집니다.

여기서 출입증이 API 키, 정기권 종류가 사용량 계획에 해당하며, 계획에는 지속 처리량과 버스트 값, 그리고 기간별 호출 총량 같은 조건이 담깁니다. 키를 발급할 때 어느 계획에 연결하느냐에 따라 그 키의 한도가 정해지고, 같은 API라도 키마다 전혀 다른 속도로 이용하게 됩니다.

정리하면 API 키는 호출자를 식별하는 표식이고 사용량 계획은 그 표식에 붙는 한도 규칙이며, 둘을 연결해 두면 고객별로 차등을 두고 문제를 일으킨 키만 좁혀서 제한할 수 있습니다.

429 응답과 재시도

한도를 넘었을 때 클라이언트가 해야 할 일을 정리합니다

한도를 넘긴 요청을 클라이언트가 아무 생각 없이 계속 다시 보내면, 서버는 거절하는 일만 반복하느라 정작 처리할 수 있었던 요청까지 밀리게 됩니다. Amazon API Gateway는 이런 악순환을 끊기 위해 한도 초과를 분명한 신호로 알리고, 클라이언트가 그 신호에 맞춰 행동하도록 설계되어 있습니다.

식당의 대기 번호를 떠올리면 상황이 같습니다. 자리가 없을 때 직원이 무작정 기다리라고 하지 않고 대기 번호를 주며 다시 오라고 안내하듯, API Gateway는 한도를 넘은 요청에 처리량 초과를 뜻하는 429 상태 코드(Too Many Requests)를 돌려보냅니다. 클라이언트는 이 응답을 받으면 즉시 재시도하지 말고 잠시 기다린 뒤 다시 보내야 하며, 재시도 간격을 시도할 때마다 두 배로 늘리는 지수 백오프(Exponential Backoff)와 대기 시간을 무작위로 흔드는 지터(Jitter)를 함께 쓰면 여러 클라이언트가 동시에 몰려드는 것을 피할 수 있습니다. 재시도에는 횟수 상한을 두어 무한 반복도 막아야 합니다.

결국 429 응답은 한도 초과를 알리는 표준 신호이고, 클라이언트는 지수 백오프와 지터로 간격을 벌리며 제한된 횟수만 재시도하는 것이 올바른 대응이라고 정리할 수 있습니다.

캐싱(Caching)

응답을 저장해 백엔드 호출을 줄이는 구조를 이해합니다

인기 상품 페이지를 열 때마다 서버가 매번 처음부터 계산해 응답을 만들면, 같은 요청이 몰리는 순간 서버는 금세 지치고 사용자는 느린 화면을 보게 됩니다. 캐싱(Caching)은 이렇게 자주 나오는 결과를 가까운 곳에 복사해 두고 다시 꺼내 쓰는 구조로, Amazon API Gateway 같은 서비스의 앞단에서 백엔드 호출을 줄이는 장치입니다.

편의점을 떠올려 보면 손님이 찾는 물건을 창고에서 매번 꺼내 오지 않고 매장 진열대에 미리 올려 둡니다. 진열대가 캐시이고 창고가 백엔드이며, 점원이 진열대에서 물건을 바로 집어 주는 동작이 캐시 적중(Cache Hit)입니다.

진열대에 없으면 그때만 창고로 가는데 이것이 캐시 미스(Cache Miss)이고, 창고에서 가져온 물건은 다시 진열대에 올려 둡니다. 진열대가 비좁으면 잘 팔리지 않는 물건부터 치워야 하므로, 무엇을 얼마나 올려 둘지 정하는 일도 캐싱의 일부입니다.

정리하면 캐싱은 응답 사본을 앞단에 저장해 두고 같은 요청이 오면 백엔드까지 가지 않고 바로 돌려주는 방식이며, 적중률이 높을수록 서버 부담과 응답 시간이 함께 줄어듭니다.

캐시 키 설계

무엇을 기준으로 캐시를 나눌지 결정합니다

캐시를 붙였는데 서로 다른 요청이 같은 응답을 돌려받아 화면이 뒤죽박죽이 되는 일이 생깁니다. 무엇을 기준으로 캐시를 나눌지 정하는 일이 캐시 키(Cache Key) 설계이고, Amazon API Gateway에서는 요청 경로와 쿼리 문자열, 헤더 같은 값의 조합으로 키를 만듭니다.

도서관에서 책을 찾을 때 제목과 저자를 함께 적은 청구기호가 서가 위치를 정해 주는 것과 같습니다. 청구기호가 캐시 키이고 서가 칸 하나하나가 캐시 항목이며, 같은 청구기호로 찾으면 늘 같은 책이 나옵니다. 만약 제목만으로 위치를 정하면 저자가 다른 동명의 책이 같은 칸에 꽂혀 엉뚱한 책이 나옵니다.

그래서 사용자마다 달라지는 값을 키에 넣을지, 언어나 기기 종류를 넣을지 하나씩 따져야 합니다.

캐시 키는 응답이 달라지는 조건을 빠짐없이 담되 필요 없는 값은 넣지 않는 균형이 핵심이며, 키가 요청의 정체성을 정확히 표현할 때 캐시가 안전하게 동작합니다.

캐시 무효화

오래된 응답을 지우고 새로 채우는 방법을 배웁니다

상품 가격을 바꿨는데 캐시에 남은 예전 가격이 계속 보이면 사용자는 잘못된 정보를 보고 구매하게 됩니다. 오래된 응답을 지우고 새 응답으로 채우는 절차가 캐시 무효화(Cache Invalidation)입니다.

회의실 화이트보드에 적힌 일정을 떠올려 보면, 일정이 바뀌면 지우개로 지우고 새로 적어야 다음 사람이 틀리지 않습니다. 화이트보드가 캐시이고 지우개로 지우는 일이 무효화(purge)이며, 새 일정을 다시 적는 일이 캐시 재적재입니다.

지우는 시점은 크게 두 가지로 나뉘는데, 정해진 시간이 지나면 자동으로 지워지는 방식과 원본 데이터가 바뀔 때 즉시 알려 지우는 방식이 있습니다. 두 방식을 섞어 쓰면 평소에는 시간에 맡기고 중요한 변경만 즉시 반영할 수 있습니다.

즉 캐시 무효화는 사본과 원본의 시차를 관리하는 작업이며, 언제 어떻게 지울지 정해 두지 않으면 캐시는 빠른 대신 틀린 답을 주는 저장소가 됩니다.

캐시 TTL과 용량

캐시 크기와 만료 시간을 정하는 감각을 잡습니다

캐시를 아무리 크게 잡아도 무한하지 않고, 오래된 응답을 계속 쌓아 두면 공간이 차서 결국 새 응답을 넣지 못합니다. 그래서 캐시에는 만료 시간(TTL, Time To Live)과 용량 제한이라는 두 가지 손잡이가 붙습니다.

냉장고를 떠올리면 선반 칸 수가 정해져 있어 자주 먹는 반찬부터 넣게 됩니다. 선반 칸 수가 캐시 용량이고 반찬마다 붙은 유통기한이 TTL이며, 기한이 지난 반찬은 버리고 새로 만듭니다.

칸이 꽉 차면 가장 오래 손대지 않은 반찬부터 버리는 것처럼, 캐시도 최근에 덜 쓰인 항목을 밀어내는 규칙으로 공간을 확보합니다. 다만 TTL을 길게 잡으면 적중률은 오르지만 오래된 값이 남고, 짧게 잡으면 최신성은 좋아지나 백엔드 호출이 늘어납니다.

TTL은 응답이 얼마나 오래 유효한지, 용량은 얼마나 많이 담을 수 있는지를 정하는 값이며, 둘을 함께 조정해야 적중률과 최신성을 동시에 얻을 수 있습니다.

캐시 사용 시 주의점

사용자별 응답과 캐시가 충돌하는 경우를 압니다

로그인한 사용자마다 다른 마이페이지 응답을 캐시에 담아 두면, 다른 사용자가 남의 정보를 받아 보는 사고가 납니다. 사용자별 응답과 공용 캐시가 충돌하는 경우를 아는 것이 캐시 도입에서 가장 조심해야 할 부분입니다.

아파트 우편함을 떠올리면 호수마다 칸이 따로 있어야 남의 우편물이 섞이지 않습니다. 우편함 번호가 사용자 식별자이고, 번호 없이 공용 바구니에 우편물을 모으면 아무나 남의 것을 집어 갑니다. 그래서 사용자마다 다른 응답에는 사용자 식별자를 캐시 키에 넣거나 아예 캐시하지 않도록 표시해야 합니다.

개인정보가 담긴 응답은 캐시를 끄는 쪽이 안전하고, 모든 사용자에게 같은 응답만 공유하는 것이 원칙입니다.

결국 캐시는 응답이 모든 사용자에게 같을 때만 공유해야 하며, 누구의 응답인지를 키에 드러내거나 저장하지 않는 선택으로 개인정보 노출을 막습니다.

트래픽 관리 설계

한도와 캐시와 재시도를 함께 설계하는 방법을 정리합니다

이벤트가 열리는 날 한꺼번에 요청이 몰리면 한도 초과로 거절되는 요청과 느려지는 요청이 뒤섞여 장애처럼 보입니다. 이때 한도(Throttling)와 캐시, 재시도(Retry)를 따로 떼어 보지 않고 함께 설계하는 것이 트래픽 관리 설계입니다.

고속도로 톨게이트를 떠올리면 차선 수와 진입 허용량이 정해져 있어 흐름이 유지됩니다. 시간당 통과 차량 수를 제한하는 것이 사용률 한도이고, 목적지가 같은 차를 우회로로 안내하는 것이 캐시이며, 잠시 막힌 차가 조금 기다렸다 다시 진입하는 것이 재시도입니다.

한도만 조이면 사용자는 거절당하고 캐시만 믿으면 새 정보가 늦어지므로, 세 장치의 역할을 나눠 정해야 합니다. 재시도에는 대기 시간을 점점 늘리는 방식과 최대 횟수 제한을 함께 두어 몰림이 오히려 커지지 않게 합니다.

정리하면 트래픽 관리 설계는 허용량과 캐시 적중률, 재시도 정책을 하나의 흐름으로 맞추는 일이며, 어느 하나만 강하게 걸면 부담이 다른 쪽으로 옮겨 갈 뿐입니다.

로그(Logging)

액세스 로그와 실행 로그가 각각 무엇을 남기는지 압니다

API를 운영하다 보면 새벽에 갑자기 요청이 실패하기 시작하는데, 서버가 살아 있는지만 확인하는 화면에서는 아무 이상이 없어 원인을 찾지 못하는 일이 생깁니다. 이런 상황을 막으려고 API Gateway는 들어온 요청 하나하나와 처리 과정에서 일어난 일을 기록으로 남기는데, 이것이 로그(Logging)입니다.

로그는 택배 물류센터에 비유할 수 있는데, 접수대에서 찍히는 접수 기록과 창고 안에서 작성하는 작업 일지가 서로 다른 역할을 합니다. 액세스 로그(Access Log)는 접수 기록처럼 요청을 보낸 사람, 시각, 경로, 응답 코드, 처리 시간처럼 요청 자체의 겉모습을 한 줄로 남깁니다. 반면 실행 로그(Execution Log)는 작업 일지처럼 그 요청이 안에서 어떤 단계를 거쳤고 어디서 오류가 났는지를 단계별로 남깁니다.

그래서 접수 기록만 보면 실패한 건이 몇 건인지 알 수 있고, 작업 일지까지 봐야 그 건이 왜 실패했는지 알 수 있습니다.

정리하면 액세스 로그는 요청의 입구에서 남는 요약 기록이고 실행 로그는 처리 과정에서 남는 상세 기록이며, 두 로그를 함께 봐야 장애의 규모와 원인을 동시에 파악할 수 있습니다. API Gateway에서는 이 두 로그를 각각 켜고 끌 수 있으므로 필요한 만큼만 수집하는 것이 비용과 분석 모두에 유리합니다.

CloudWatch Logs 연동

로그 그룹과 로그 형식을 설정하는 방법을 배웁니다

로그를 남기기로 했는데 어디에 모아 둘지 정하지 않으면, 서버마다 흩어진 기록을 사람이 일일이 찾아다녀야 하고 장애 때는 그 기록조차 금방 사라집니다. 그래서 API Gateway는 로그를 AWS의 관리형 로그 저장소인 CloudWatch Logs로 보내 보관하고 검색할 수 있게 합니다.

이 과정은 회사 문서고에 비유할 수 있습니다. 먼저 로그 그룹(Log Group)은 부서 이름이 붙은 서류 철처럼 API 하나나 스테이지 하나에 대응하는 가장 큰 보관 단위이고, 그 안의 로그 스트림(Log Stream)은 실제로 서류가 쌓이는 개별 묶음입니다.

다음으로 로그 형식(Log Format)은 서류에 어떤 항목을 어떤 순서로 적을지 정한 서식인데, JSON 형식으로 정해 두면 나중에 항목 이름으로 바로 찾을 수 있고 한 줄 텍스트로 두면 사람이 눈으로 읽기가 쉽습니다. 보관 기간도 함께 정해야 하는데, 오래 보관할수록 저장 비용이 늘어나므로 장애 조사에 필요한 기간만 남기는 편이 좋습니다.

정리하면 로그 그룹은 로그를 담는 최상위 단위, 로그 스트림은 그 안의 실제 기록 흐름, 로그 형식은 기록에 담을 항목의 약속이며, 이 세 가지를 먼저 정해야 CloudWatch Logs에서 로그를 찾고 활용할 수 있습니다. 연동은 설정 한 번으로 끝나지만 보관 기간과 접근 권한은 처음에 함께 점검하는 것이 좋습니다.

구조화 로그 설계

나중에 검색하고 집계하기 좋은 로그 형식을 만듭니다

로그를 자유로운 문장으로 남기면 결제 실패를 찾을 때 표현이 조금씩 달라 검색이 되지 않고, 오류가 몇 건인지 세려면 사람이 눈으로 하나씩 세야 합니다. 이 문제를 줄이려고 로그를 정해진 항목 이름과 값의 모음으로 남기는 설계 방식을 구조화 로그(Structured Logging)라고 합니다.

구조화 로그는 택배 송장에 비유할 수 있습니다. 송장에는 보내는 사람, 받는 사람, 물건 종류, 무게가 정해진 칸에 들어가 있어서 창고에서 칸 이름만 보고 원하는 물건을 골라낼 수 있습니다.

구조화 로그도 마찬가지로 요청 ID, 경로, 상태 코드, 처리 시간 같은 값을 정해진 이름의 칸에 담아 JSON으로 남기므로, 검색 도구가 특정 칸의 값이 일정한 조건을 넘는 기록만 골라낼 수 있습니다. 여기에 요청 ID를 모든 로그 줄에 같이 적어 두면 한 요청이 남긴 여러 줄을 한 묶음으로 이어 볼 수 있고, 사람이 읽기 위한 설명 문장은 따로 칸을 두어야 나중에 형식이 흔들리지 않습니다.

정리하면 구조화 로그는 로그를 문장이 아니라 정해진 항목의 모음으로 남기는 설계 방식이며, 항목 이름을 처음에 합의해 두면 검색과 집계가 훨씬 쉬워집니다. 값의 단위와 시간 표기까지 함께 정해 두면 여러 서비스의 로그를 한 화면에서 비교할 수 있습니다.

지표(Metrics)

호출 수와 지연, 오류율 같은 기본 지표를 읽습니다

로그는 자세하지만 건수가 너무 많아서 지금 서비스가 괜찮은지 한눈에 답하기 어렵습니다. 그래서 API Gateway는 개별 기록 대신 숫자로 요약한 지표(Metrics)를 함께 제공해, 상태가 좋은지 나쁜지를 빠르게 판단하게 합니다.

지표는 자동차 계기판에 비유할 수 있습니다. 주행 거리계가 얼마나 달렸는지 보여주듯 호출 수(Count)는 정해진 시간 동안 들어온 요청이 몇 건인지 세어 주고, 속도계가 지금 얼마나 빠른지 보여주듯 지연(Latency)은 요청 하나가 처리되어 응답될 때까지 걸린 시간을 보여 줍니다.

경고등이 문제를 알리듯 오류율(Error Rate)은 전체 요청 중 실패한 비율을 숫자 하나로 보여 주므로, 로그를 뒤지지 않고도 상태가 나빠졌는지 바로 알 수 있습니다. 다만 지표는 평균값이라 소수의 아주 느린 요청이 묻히기 쉬우므로, 최대값이나 백분위 값을 함께 보는 습관이 필요합니다.

정리하면 지표는 개별 기록을 숫자로 요약해 서비스 상태를 빠르게 판단하게 해 주는 값이며, 호출 수와 지연, 오류율은 그중에서도 가장 기본이 되는 세 가지입니다. 로그가 원인을 찾는 도구라면 지표는 이상이 있는지 먼저 알려 주는 도구입니다.

세부 지표와 차원

메서드와 스테이지별로 지표를 쪼개 보는 방법을 익힙니다

전체 오류율이 조금 올랐다는 사실만으로는 어느 경로에서 문제가 생겼는지 알 수 없어서 조사가 막히기 쉽습니다. 이때 같은 지표를 특정 기준으로 잘라 보게 해 주는 속성을 차원(Dimension)이라고 하며, 차원 덕분에 메서드별, 스테이지별로 지표를 쪼개 볼 수 있습니다.

세부 지표는 아파트 관리비 고지서에 비유할 수 있습니다. 총액 한 줄만 보면 어디서 돈이 새는지 알 수 없지만, 전기와 수도와 청소처럼 항목별로 나누고 다시 동별로 나누어 보면 유독 높은 곳이 드러납니다.

차원은 이렇게 지표를 나누는 기준의 이름이고, API Gateway에서는 메서드(GET, POST), 스테이지(운영, 개발), 리소스 경로 같은 값으로 같은 지표를 여러 갈래로 쪼개 볼 수 있습니다. 다만 차원을 많이 붙일수록 만들어지는 지표의 조합이 늘어나 비용과 화면이 함께 복잡해지므로, 자주 보는 기준 몇 개만 골라 두는 편이 좋습니다.

정리하면 차원은 하나의 지표를 특정 기준으로 나누어 보게 해 주는 속성이며, 메서드와 스테이지처럼 문제가 자주 생기는 기준으로 나누어 볼 때 원인 추적이 빨라집니다. 전체 값과 쪼갠 값을 나란히 두고 비교하는 방식이 가장 실용적입니다.

경보(Alarm) 설정

문제가 커지기 전에 알림을 받는 기준을 세웁니다

지표를 화면에 띄워 두어도 새벽에 아무도 보지 않으면 문제는 그대로 커집니다. 그래서 지표가 정한 기준을 넘으면 자동으로 알려 주는 장치가 필요한데, 이것이 경보(Alarm)입니다.

경보는 건물의 화재 경보기에 비유할 수 있습니다. 경보기는 연기가 일정 농도를 넘었는지를 계속 지켜보다가 기준을 넘으면 사이렌을 울리는데, 여기서 지켜보는 대상이 앞서 본 지표이고 넘지 말아야 할 값이 임계값(Threshold)입니다.

또 연기가 잠깐 스친 것과 계속 나는 것을 구분하듯, 경보에도 몇 분 동안 몇 번 연속 기준을 넘었을 때 울릴지 정하는 평가 기간이 있어 자주 흔들리는 지표로 새벽에 헛소리가 나는 일을 줄여 줍니다. 울릴 대상도 정해야 하는데, 사람에게 메일이나 문자를 보낼지 자동으로 서버를 늘리는 동작을 실행할지 미리 정해 두지 않으면 경보만 울리고 아무 일도 일어나지 않습니다.

정리하면 경보는 지표가 정한 임계값을 일정 기간 넘을 때 알림이나 자동 조치를 실행하는 장치이며, 임계값과 평가 기간, 알림 대상을 함께 정해야 실제로 쓸모가 있습니다. 너무 예민한 경보는 곧 무시하게 되므로 처음에는 느슨하게 두고 조금씩 조이는 편이 좋습니다.

X-Ray 추적

요청이 여러 서비스를 거치는 경로를 추적하는 방법을 배웁니다

주문 하나가 열 개의 마이크로서비스를 거쳐 처리되는데 응답이 갑자기 느려졌다면, 어느 서비스가 시간을 잡아먹는지 로그만으로는 좀처럼 알기 어렵습니다. 요청이 지나간 길을 구간별로 이어 붙여 보여 주는 것이 AWS X-Ray 추적(tracing)입니다.

택배 한 건이 여러 물류센터를 거친다고 생각해 보면, 송장번호 하나가 부여되고 각 센터를 지날 때마다 언제 들어와 언제 나갔는지 스캔 기록이 남습니다. X-Ray도 요청마다 추적 ID(trace ID)를 붙이고, 각 서비스가 자기 구간의 시작과 끝, 처리 결과를 세그먼트(segment)로 남기게 합니다. 그 조각들을 모으면 택배 배송 경로처럼 요청이 어디서 몇 밀리초를 머물렀고 어디서 오류가 났는지 한 줄로 이어진 지도가 됩니다.

여기에 하위 작업 단위인 서브세그먼트(subsegment)를 붙이면 데이터베이스 호출 하나, 외부 결제 호출 하나까지 구간이 나뉘어 보입니다. 즉 X-Ray는 개별 로그를 따로 보는 대신 요청 단위의 전체 경로를 수집하고 연결해 주는 분산 추적(distributed tracing) 서비스입니다.

로그에서 요청 추적

요청 ID로 여러 로그를 이어 붙이는 방법을 익힙니다

서비스마다 로그 파일이 따로 쌓이면, 사용자가 신고한 오류 하나를 확인하려고 여러 로그를 시간 순으로 뒤지는 일이 벌어집니다. 요청에 고유한 요청 ID(request ID)를 붙여 두면 흩어진 로그를 그 값 하나로 이어 붙일 수 있습니다. 택배로 치면 주문번호 하나로 포장, 간선 운송, 집 앞 배송 단계의 기록을 모두 조회하는 것과 같습니다.

API Gateway는 들어온 요청마다 요청 ID를 만들고 응답 헤더에 담아 돌려주며, 이 값을 백엔드 서비스로도 넘겨 줄 수 있습니다. 각 서비스가 로그에 그 ID를 함께 찍어 두면 로그 검색 도구에서 같은 값으로 걸러 시간 순으로 정렬하는 것만으로 한 요청의 생애가 재구성됩니다.

X-Ray 추적 ID를 함께 남겨 두면 로그와 추적 화면을 서로 오가며 확인할 수도 있습니다. 핵심은 요청마다 같은 식별자를 전 구간에 전파해 흩어진 로그를 하나의 이야기로 묶는 것입니다.

8부. 관찰성과 모니터링093

대시보드 구성

운영에 필요한 지표만 모아 한눈에 보는 화면을 만듭니다

지표가 수십 개 쌓이면 정작 장애가 났을 때 어느 숫자를 봐야 할지 몰라 화면만 오가게 됩니다. 운영에 필요한 지표만 골라 한 화면에 배치한 것이 대시보드(dashboard)입니다. 아파트 관리실의 계기판을 떠올려 보면, 전기와 수도와 소방처럼 이상이 생기면 바로 판단해야 하는 항목만 크게 붙여 두고 나머지는 뒤로 물립니다.

CloudWatch 대시보드는 위젯(widget)이라는 작은 칸을 원하는 만큼 배치해 지표 그래프, 로그 질의 결과, 경보 상태를 한 판에 담습니다. API Gateway 기준으로는 호출 수, 4XX와 5XX 오류율, 지연 시간(latency)의 백분위, 스로틀링 발생 수를 먼저 놓는 식입니다.

위젯마다 보는 기간을 맞춰 두면 지금이 평소와 다른지를 눈으로 바로 판단할 수 있습니다. 요약하면 대시보드는 지표를 모아 두는 곳이 아니라, 판단에 필요한 최소 지표를 한눈에 정렬해 두는 화면입니다.

8부. 관찰성과 모니터링094

이상 징후 탐지

평소와 다른 트래픽과 오류 패턴을 찾아내는 방법을 압니다

트래픽은 늘 일정하지 않아서, 사람이 정해 둔 고정 임계값만으로는 새벽의 조용한 오류나 서서히 오르는 지연을 놓치기 쉽습니다. 평소 패턴을 학습해 벗어난 지점을 알려 주는 것이 이상 징후 탐지(anomaly detection)입니다. 아파트 경비원이 아니라, 평소 출입 패턴을 기억하다가 새벽 3시에 낯선 사람이 들어오면 기록과 비교해 알려 주는 시스템을 생각하면 됩니다.

CloudWatch 이상 탐지는 지표의 계절성과 추세를 바탕으로 정상 범위의 띠(band)를 만들어 두고, 실제 값이 그 띠를 벗어나면 경보를 냅니다. API Gateway에서는 호출 수나 5XX 오류율, 지연 시간 같은 지표에 이 방식을 붙여 두면 급증과 급감을 함께 잡아냅니다.

고정 임계값과 달리 트래픽이 원래 많은 시간대와 적은 시간대를 알아서 구분한다는 점이 다릅니다. 결국 이상 탐지는 얼마면 위험하다는 사람의 기준을, 평소와 얼마나 다른가라는 비교 기준으로 바꿔 주는 기능입니다.

사용자 지정 도메인

기본 URL 대신 내 도메인으로 API를 제공하는 방법을 배웁니다

API를 만들면 기본으로 무작위 문자열이 붙은 주소가 나오는데, 이 주소를 고객에게 안내하거나 앱에 박아 두기는 곤란합니다. 내가 가진 도메인 이름으로 API를 제공하는 것이 사용자 지정 도메인(custom domain) 설정입니다. 건물에 임시로 붙은 공사용 번호판 대신 정식 도로명 주소를 붙이는 일과 같습니다.

API Gateway에서 사용자 지정 도메인을 만들면 도메인과 API 매핑(mapping)을 연결해, api.example.com 같은 주소가 특정 API의 스테이지로 향하게 합니다. 이때 기본 주소와 사용자 지정 주소가 함께 살아 있으므로 기존 호출이 바로 끊기지는 않습니다. HTTPS로 서비스하려면 도메인 소유 확인과 인증서가 필요하고, 이 인증서는 ACM에서 발급받아 연결합니다.

정리하면 사용자 지정 도메인은 API의 실제 주소와 별개로, 사용자에게 보여 줄 안정적인 이름을 얹는 계층입니다.

ACM 인증서

HTTPS에 필요한 인증서를 발급하고 연결하는 절차를 익힙니다

HTTPS 없이 API를 열어 두면 전송 구간의 내용이 그대로 노출되고, 브라우저와 앱은 안전하지 않은 연결로 표시합니다. 이를 해결하는 것이 인증서 발급과 연결이며, AWS에서는 ACM(AWS Certificate Manager)이 이 일을 맡습니다. 건물 출입구에 붙는 공인 인증 명판처럼, 발급 기관이 건물 주인을 확인하고 유효 기간을 적어 주는 셈입니다.

ACM에서 도메인 이름을 넣고 검증 방식을 고르면, DNS에 지정된 레코드를 추가하거나 이메일로 확인하는 절차를 거쳐 인증서가 발급됩니다. 발급된 인증서는 API Gateway의 사용자 지정 도메인에 연결되고, 갱신은 ACM이 만료 전에 자동으로 처리합니다.

리전과 엣지 최적화(edge-optimized) 엔드포인트에 따라 인증서를 두어야 하는 위치가 다르므로 구성 시 확인이 필요합니다. 핵심은 ACM이 인증서의 발급과 검증과 갱신을 대신 맡고, API Gateway가 그 인증서를 도메인에 묶어 HTTPS를 완성한다는 점입니다.

TLS 최소 버전 설정

오래된 암호화 프로토콜을 차단하는 설정을 이해합니다

API 게이트웨이가 아무 암호화 방식이나 받아 주면, 공격자가 오래되고 약한 암호화 방식을 일부러 요구해 통신 내용을 엿보거나 중간에서 바꿔치기할 수 있습니다. TLS 최소 버전 설정은 이렇게 낡은 암호화 프로토콜을 아예 거절하고 일정 버전 이상만 허용하는 안전장치입니다.

아파트 정문 경비실을 떠올리면 이해가 쉽습니다. 예전에 쓰던 종이 출입증은 사진도 없고 도장도 흐려서 누구나 쉽게 위조할 수 있는데, 경비원이 그런 출입증까지 다 받아 준다면 아무나 건물에 들어올 수 있습니다. 그래서 관리사무소가 새 카드형 출입증을 도입하면서 "예전 종이 출입증은 이제 받지 않는다"는 기준일을 정하는데, 이것이 바로 최소 버전을 정하는 일입니다.

실제 통신에서는 연결을 시작할 때 클라이언트와 서버가 서로 쓸 수 있는 암호화 방식을 주고받으며 협상하는데, 게이트웨이가 허용 목록에 없는 버전을 요구받으면 그 자리에서 연결을 끊습니다. 이 설정은 애플리케이션 코드가 아니라 게이트웨이의 수신 지점에서 처리되므로, 뒤에 붙은 서버들은 신경 쓰지 않아도 됩니다.

정리하면 TLS(Transport Layer Security) 최소 버전 설정은 핸드셰이크 단계에서 허용할 프로토콜 버전의 하한선을 강제하는 정책이며, 취약한 구버전을 차단해 다운그레이드 공격의 통로를 없애는 일입니다.

상호 TLS(mTLS)

클라이언트 인증서로 양방향 검증을 하는 방법을 배웁니다

보통의 HTTPS 연결은 클라이언트가 서버의 신분만 확인하고 끝나기 때문에, 서버 입장에서는 접속한 쪽이 진짜 고객사 시스템인지 아니면 인증서를 훔친 누군가인지 알 방법이 없습니다. 상호 TLS는 여기에 클라이언트 쪽 인증서 검사를 더해 양쪽이 서로의 신분을 확인하게 만드는 방식입니다.

택배 수령 절차에 빗대어 보겠습니다. 지금까지는 배송 기사가 회사 이름과 사원증을 보여 주고 물건을 맡기는 것으로 끝났는데, 이제는 회사 측에서도 받는 사람의 신분증을 요구하는 것입니다. 여기서 서버 인증서는 기사가 보여 주는 사원증에, 클라이언트 인증서는 받는 사람이 내미는 신분증에 대응하며, 신분증이 등록 명단에 없으면 물건을 건네지 않듯 서버도 신뢰 저장소에 등록된 인증서가 없으면 연결을 맺지 않습니다.

게이트웨이는 이 인증서 검사를 자기 앞단에서 대신 수행하고, 통과한 요청에만 클라이언트의 신원 정보를 담아 뒤쪽 서비스로 넘깁니다. 그래서 사내 시스템 간 통신이나 파트너사 전용 API처럼 신뢰 경계를 확실히 그어야 하는 곳에서 자주 쓰입니다.

결국 상호 TLS(mutual TLS)는 서버 인증서와 클라이언트 인증서를 함께 검증해 양방향으로 신원을 확인하는 구조이며, 인증서 발급과 갱신 관리가 함께 따라와야 제값을 하는 보안 수단입니다.

WAF 연동

웹 공격 패턴을 게이트웨이 앞단에서 막는 구조를 이해합니다

API는 정상적인 사용자뿐 아니라 악의적인 요청도 똑같은 통로로 받기 때문에, 데이터베이스 명령을 끼워 넣거나 스크립트를 심으려는 시도가 애플리케이션까지 그대로 도달합니다. WAF 연동은 이런 공격 패턴을 게이트웨이 앞단에서 미리 걸러 내는 구조입니다.

건물 로비에 설치된 금속 탐지기에 비유할 수 있습니다. 방문객은 누구나 정문을 지나야 하지만, 위험한 물건을 들고 온 사람은 엘리베이터를 타기 전에 로비에서 멈춰 서게 되는데, WAF가 바로 이 탐지기 역할을 합니다. 관리사무소가 "이런 모양의 물건은 반입 금지"라는 규칙 목록을 계속 갱신하듯, WAF도 알려진 공격 유형에 대한 규칙 집합을 유지하고 요청의 본문과 헤더를 검사해 해당되면 차단하거나 기록만 남깁니다.

게이트웨이는 요청을 받는 즉시 WAF에 검사를 위임하고, 통과한 요청에만 인증과 라우팅 같은 다음 단계를 진행합니다. 이렇게 하면 취약한 코드가 있더라도 공격이 도달하기 전에 한 겹을 더 줄일 수 있습니다.

정리하면 WAF(Web Application Firewall) 연동은 게이트웨이 앞에서 요청 내용을 규칙으로 검사해 SQL 삽입이나 교차 사이트 스크립팅 같은 공격을 차단하는 계층이며, 규칙을 방치하면 효과가 줄어드는 만큼 지속적인 관리가 필요합니다.

입력 검증과 정화

악의적인 입력을 초기에 걸러내는 습관을 들입니다

사용자가 보낸 값을 그대로 믿고 처리하면, 길이 제한을 넘는 값이나 예상하지 못한 문자가 들어와 시스템이 오작동하거나 저장된 데이터가 오염됩니다. 입력 검증과 정화는 이런 악의적이거나 잘못된 입력을 처리 초기에 걸러 내는 습관입니다.

식당 주방의 재료 검수 과정을 떠올리면 됩니다. 납품된 채소를 그대로 조리에 쓰지 않고, 상한 것은 반품하고 흙과 이물질은 씻어 낸 뒤에야 도마 위에 올리는데, 여기서 반품이 검증이고 씻어 내기가 정화입니다.

검증은 이메일 형식인지, 숫자 범위를 벗어나지 않는지처럼 값이 정해진 조건에 맞는지 확인해 맞지 않으면 거절하는 일이고, 정화는 허용된 문자만 남기고 나머지를 제거하거나 안전한 형태로 바꾸는 일입니다. 주방에서 "이 재료만 받는다"는 목록을 정해 두면 판단이 빨라지듯, 허용 목록 방식으로 받을 값을 제한하는 편이 위험한 것만 골라 막는 방식보다 안전합니다. 게이트웨이에서는 요청 스키마 검사로 형식과 필수 항목을 확인하고, 통과한 값만 뒤쪽 서비스로 전달합니다.

결국 입력 검증(validation)과 정화(sanitization)는 신뢰 경계를 지나는 모든 값의 형식과 내용을 확인하고 정리하는 절차이며, 한 곳에서만 처리하지 말고 데이터를 쓰는 지점에서도 한 번 더 확인하는 것이 원칙입니다.

DDoS 대응

대량 트래픽 공격에 대비하는 계층과 한도를 이해합니다

짧은 시간에 수많은 요청이 쏟아지면 서버 자원이 먼저 소진되어 정상 사용자까지 응답을 받지 못하게 됩니다. DDoS 대응은 이런 대량 트래픽 공격을 어느 계층에서 얼마만큼 허용할지 정해 두는 설계입니다.

대형 마트의 개점 세일 입장 관리를 생각하면 이해가 쉽습니다. 정문에 사람이 몰리면 매장 안이 엉망이 되므로, 경비는 정문 앞 대기줄을 만들고 한 번에 들여보내는 인원을 제한하며, 물건만 받으러 온 사람과 그냥 구경하러 온 사람을 구분해 대응합니다. 여기서 정문 경비와 대기줄이 네트워크 계층의 트래픽 정리이고, 입장 인원 제한이 게이트웨이의 속도 제한(throttling)이며, 사용량 계획(usage plan)과 할당량(quota)은 고객별로 받을 수 있는 입장권 수를 정하는 일에 해당합니다.

네트워크 계층에서는 대량의 연결 자체를 분산하고 걸러 내고, 애플리케이션 계층에서는 인증과 요청 단위 한도로 과도한 호출을 막는 식으로 층을 나눠 대응합니다. 이렇게 단계마다 한도를 두면 한 지점이 뚫려도 전체가 무너지는 일을 줄일 수 있습니다.

정리하면 DDoS 대응은 네트워크 계층의 트래픽 완화와 애플리케이션 계층의 속도 제한·할당량을 함께 배치해 대량 요청의 영향을 줄이는 구조이며, 공격을 완전히 없애기보다 정상 트래픽을 지키는 데 목적이 있습니다.

비밀 정보 관리

키와 토큰을 코드에 두지 않고 안전하게 보관하는 방법을 배웁니다

API 키나 데이터베이스 비밀번호를 소스 코드에 적어 두면, 저장소가 공유되거나 기록이 남는 순간 그대로 노출되고 바꾸려면 코드를 고쳐 다시 배포해야 합니다. 비밀 정보 관리는 이런 키와 토큰을 코드 밖으로 꺼내 안전하게 보관하고 필요할 때만 꺼내 쓰게 하는 방법입니다.

회사 금고와 열쇠 관리에 비유할 수 있습니다. 현금을 책상 서랍에 두지 않고 금고에 넣어 두며, 금고 열쇠는 아무에게나 주지 않고 담당자별로 권한을 나누고, 정해진 주기에 열쇠를 새로 바꾸는 것이 기본입니다. 비밀 정보 저장소는 이 금고에 해당하고, 접근 권한을 부여하는 역할 기반 정책은 열쇠를 나눠 주는 규칙이며, 주기적 교체(rotation)는 열쇠를 새로 만드는 일입니다.

애플리케이션은 코드에 값을 직접 쓰는 대신 실행 시점에 저장소에서 값을 가져오고, 게이트웨이나 서버가 갖는 권한은 필요한 비밀에만 한정합니다. 키가 코드나 로그에 남지 않게 하면 유출되더라도 피해 범위를 좁힐 수 있습니다.

결국 비밀 정보 관리는 자격 증명을 코드와 분리해 중앙 저장소에 두고 최소 권한과 정기 교체로 통제하는 체계이며, 한 번 새어 나간 키는 즉시 폐기하고 재발급하는 것이 원칙입니다.

감사와 접근 기록

누가 언제 설정을 바꿨는지 남기는 방법을 압니다

서비스가 갑자기 이상해졌는데 어제 누군가 설정을 바꾼 것 같아도, 아무 기록도 남아 있지 않으면 어디서부터 손대야 할지 알 수가 없습니다. Amazon API Gateway의 감사(Audit)와 접근 기록(Access Logging)은 이런 상황에서 "누가, 언제, 무엇을 했는지"를 남겨 두는 장치이며, 상위 개념인 클라우드 거버넌스(Cloud Governance)의 한 부분입니다.

아파트 관리사무소를 떠올려 보시면 이해가 쉽습니다. 외부 업체 기사가 들어와 설비를 만질 때마다 관리사무소는 방문 일지에 누가, 몇 시에 들어와, 어느 설비를, 무엇으로 바꿨는지 적어 두고, 입주민이 현관을 드나드는 출입 기록도 따로 남깁니다. 여기서 방문 일지가 설정 변경을 남기는 감사 기록(AWS CloudTrail)이고, 출입 기록이 요청마다 남는 접근 로그(Access Log)입니다.

나중에 문제가 생기면 두 기록을 나란히 놓고 "이 사람이 이 설정을 바꾼 직후부터 이상해졌구나"를 되짚을 수 있습니다. 기록은 요청의 시각, 호출한 사용자, 응답 코드, 지연 시간 같은 정보를 담으며, 이 기록을 남기는 것 자체가 나중의 조사를 가능하게 만듭니다.

정리하면, 감사 기록은 관리 행위를, 접근 로그는 서비스 호출을 각각 시간 순으로 남겨 문제 원인을 사후에 추적하게 해 주는 기능입니다.

최소 권한 원칙

게이트웨이와 백엔드의 권한을 필요한 만큼만 주는 방법을 익힙니다

게이트웨이를 만들 때 편하다는 이유로 관리자 권한을 통째로 붙여 두면, 그 하나가 뚫리는 순간 회사 전체가 위험해집니다. 최소 권한 원칙(Least Privilege)은 각 주체에게 일을 하는 데 꼭 필요한 권한만 주는 설계 원칙이고, Amazon API Gateway에서는 호출하는 쪽과 뒤에서 일하는 백엔드 양쪽에 모두 적용됩니다.

호텔 객실 카드키를 생각해 보시면 구조가 그대로 겹칩니다. 투숙객에게는 자기 객실 문만 열리는 카드키를 주고, 청소 담당자에게는 청소 구역만, 정비 담당자에게는 설비실만 열리는 키를 줍니다. 마스터키는 정말 필요한 관리자 한 명에게만 쥐여 주지, 모든 사람에게 나눠 주지 않습니다.

게이트웨이에서는 이 카드키가 권한 정책(IAM Policy)에 해당하고, 문이 열리는 범위는 특정 API 경로와 특정 HTTP 메서드로 좁혀집니다. 백엔드 쪽도 마찬가지여서, 게이트웨이가 백엔드를 호출할 때 쓰는 역할(Role)에는 그 함수 하나를 실행할 권한만 붙이고 데이터베이스 전체 권한은 붙이지 않습니다.

결국 최소 권한 원칙은 API Gateway의 리소스 정책과 백엔드 실행 역할을 필요한 경로와 동작으로만 한정해, 권한 하나가 새더라도 피해 범위가 그 좁은 구역에 머물게 하는 설계입니다.

보안 점검 체크리스트

배포 전에 반드시 확인할 보안 항목을 정리합니다

API는 한 번 공개되면 전 세계에서 접근할 수 있게 되므로, 배포 직전에 몇 가지만 놓쳐도 인증 없이 열린 통로가 생깁니다. 보안 점검 체크리스트(Security Checklist)는 배포 전에 반드시 확인해야 할 항목을 순서대로 정리해 둔 목록으로, Amazon API Gateway를 운영할 때 사람이 매번 기억에 의존하지 않도록 만든 안전장치입니다.

비행기가 이륙하기 전에 조종사가 점검표를 한 줄씩 읽으며 확인하는 모습을 떠올려 보시면 됩니다. 연료, 계기, 날개 상태를 순서대로 짚듯이, 게이트웨이에서는 먼저 인증 수단(Authorizer)이 모든 경로에 붙어 있는지 확인하고, 다음으로 통신이 암호화된 HTTPS로만 열려 있는지 봅니다. 이어서 과도한 호출을 막는 사용량 제한(Throttling)이 걸려 있는지, 요청을 기록하는 로그가 켜져 있는지, 의심스러운 요청을 거르는 방화벽(WAF)이 앞단에 있는지를 차례로 짚습니다.

점검표는 한 번 읽고 끝나는 문서가 아니라 배포할 때마다 같은 순서로 확인하게 해 주는 절차입니다.

정리하면, 보안 점검 체크리스트는 인증·암호화·호출 제한·로깅·방화벽 같은 항목을 배포 전에 빠짐없이 확인하도록 순서를 고정해 둔 절차이며, 사람의 기억이 아니라 목록이 최종 확인을 맡게 하는 방식입니다.

규정 준수와 데이터 보호

민감한 데이터가 로그와 응답에 남지 않게 하는 방법을 압니다

고객의 이름과 연락처가 담긴 요청을 그대로 로그에 남겨 두면, 로그를 열람할 수 있는 사람 모두가 그 개인정보를 보게 됩니다. 규정 준수(Compliance)와 데이터 보호(Data Protection)는 법과 사내 규정이 요구하는 방식으로 민감한 데이터를 다루는 일이며, Amazon API Gateway에서는 그 데이터가 로그와 응답에 남지 않도록 통제하는 문제로 나타납니다.

택배를 보낼 때를 생각해 보시면 좋습니다. 송장에는 받는 사람 주소가 필요하지만, 운송장을 스캔해 보관할 때는 뒷자리를 가리고, 창고 직원이 굳이 전화번호 전체를 볼 필요는 없습니다.

게이트웨이에서도 요청 본문(Body) 전체를 로그에 찍지 않고 필요한 항목만 골라 남기며, 주민등록번호나 카드 번호 같은 값은 가림 처리(Masking)를 합니다. 응답 쪽도 마찬가지여서, 오류가 났을 때 내부 구조와 데이터가 그대로 노출되는 상세 오류 메시지를 그대로 내보내지 않습니다. 보관 기간을 정해 오래된 로그를 지우는 것도 이 보호의 일부입니다.

결국 규정 준수와 데이터 보호는 로그에 남길 항목과 가릴 항목을 미리 정하고, 응답에서 내부 정보가 새지 않게 하며, 보관 기간을 지키는 방식으로 민감한 데이터의 노출을 줄이는 일입니다.

배포(Deployment)

API 변경이 실제로 반영되는 시점과 단계의 관계를 이해합니다

API 정의를 고쳤는데도 실제 호출은 예전 동작 그대로여서 "왜 안 바뀌지" 하고 한참 헤매는 일이 자주 생깁니다. 배포(Deployment)는 이 간극을 설명하는 개념으로, Amazon API Gateway에서 작성한 API 정의가 실제로 호출 가능한 상태가 되는 시점과 단계를 다루는 절차입니다.

연극 공연을 떠올려 보시면 이해가 됩니다. 대본을 고쳤다고 해서 관객이 보는 무대가 바로 바뀌지는 않고, 수정된 대본으로 리허설 무대를 한 번 세우고 나서야 비로소 공연에 올라갑니다.

게이트웨이에서 대본은 API 정의이고, 무대는 스테이지(Stage)라는 이름의 실행 환경이며, 대본을 무대에 올리는 행위가 바로 배포입니다. 즉 API를 수정하는 것과 그 수정을 스테이지에 배포하는 것은 서로 다른 단계이고, 배포하지 않으면 호출은 이전에 올려 둔 무대를 계속 바라봅니다. 그래서 개발용 스테이지와 운영용 스테이지를 나눠 두고, 검증한 뒤 운영 스테이지에 배포하는 순서를 밟습니다.

정리하면, 배포는 수정된 API 정의를 특정 스테이지에 올려 실제 호출에 반영되게 하는 단계이며, 정의를 바꾼 시점과 호출이 바뀌는 시점이 다르다는 점이 이 개념의 핵심입니다.

스테이지 변수

환경마다 다른 값을 주입해 같은 정의를 재사용하는 방법을 배웁니다

개발 환경과 운영 환경이 똑같은 API를 쓰는데 데이터베이스 주소만 다르다고 해서, API 정의를 두 벌로 복사해 두면 한쪽만 고쳐지는 사고가 반드시 생깁니다. 스테이지 변수(Stage Variables)는 이런 중복을 없애기 위해, 하나의 API 정의 안에 환경마다 다른 값만 바꿔 끼우는 기능입니다.

프랜차이즈 매장의 표준 매뉴얼을 생각해 보시면 정확히 같은 구조입니다. 본사가 만든 매뉴얼은 모든 지점이 똑같이 쓰지만, 표지의 지점명과 배달 전화번호만 각 지점이 채워 넣습니다.

게이트웨이에서 매뉴얼은 API 정의이고, 지점명이 들어가는 빈칸이 스테이지 변수이며, 지점은 스테이지(Stage)입니다. 개발 스테이지에는 개발용 백엔드 주소를, 운영 스테이지에는 운영용 주소를 각각 넣어 두면, 정의는 하나인데 호출은 환경에 맞는 곳으로 갑니다. 이 값은 백엔드 연결 대상이나 함수 이름 같은 설정에 참조 형태로 넣어 쓰며, 값이 바뀌면 정의를 고치는 대신 그 스테이지의 변수만 바꿉니다.

정리하면, 스테이지 변수는 API 정의를 복제하지 않고 스테이지마다 다른 값을 주입해, 같은 정의를 여러 환경에서 재사용하게 해 주는 설정값입니다.

카나리 릴리스

일부 트래픽만 새 버전으로 보내 위험을 줄이는 방법을 익힙니다

새 버전을 완성해 두고도 배포 버튼을 누르는 순간이 두려운 이유는, 모든 사용자의 요청을 한꺼번에 새 버전으로 넘겼다가 첫 화면부터 오류가 터지면 되돌리는 동안 전체 고객이 멈춘 서비스를 겪게 되기 때문입니다. 카나리 릴리스(canary release)는 그래서 전체 트래픽 가운데 아주 일부만 새 버전으로 흘려보내고, 나머지는 기존 버전에 그대로 두는 배포 방식입니다.

아파트 한 동의 엘리베이터를 새 기종으로 교체하는 상황을 떠올리면 구조가 그대로 겹칩니다. 관리사무소는 입주민 전체를 새 엘리베이터에 한꺼번에 태우지 않고, 먼저 한 대만 바꿔 며칠 동안 운행 소리와 진동, 승객 반응을 살핍니다. 이때 한 대가 곧 카나리 비율이고, 소리와 진동을 살피는 일이 모니터링(monitoring)이며, 문제가 보이면 그 한 대만 예전 기종으로 되돌리는 것이 롤백(rollback)입니다. 며칠 동안 이상이 없으면 다음 한 대, 그다음 한 대 순서로 바꾸는 것처럼, 배포도 5퍼센트에서 25퍼센트로 조금씩 비중을 늘려 갑니다.

정리하면 카나리 릴리스는 새 버전을 소수 트래픽에 먼저 노출해 관찰하고, 지표가 정상일 때만 단계적으로 확대하며, 이상이 생기면 즉시 이전 버전으로 되돌리는 배포 전략입니다. 이점은 실패의 크기를 전체가 아니라 일부로 묶어 둔다는 데 있고, 그 대가로 두 버전을 동시에 운영할 준비가 필요합니다.

API 버전 관리

경로와 헤더와 스테이지로 버전을 나누는 전략을 비교합니다

앱과 서버가 주고받는 응답 형식을 어느 날 갑자기 바꾸면, 기존에 그 형식에 맞춰 만들어진 앱들이 한꺼번에 오작동합니다. 그래서 API를 운영할 때는 요청과 응답의 모양을 판으로 나누어 두고, 새 판을 내더라도 예전 판을 당분간 함께 살려 두는 API 버전 관리가 필요합니다.

택배 회사가 송장 양식을 개정하는 일과 비슷합니다. 양식을 하루아침에 갈아치우면 기사 단말기와 거래처 관리 프로그램이 모두 새 칸을 못 읽어 배송이 멈추므로, 회사는 송장에 판 번호를 붙여 1판과 2판을 나란히 운영합니다.

경로에 판 번호를 넣는 방식(예: /v1/orders)은 송장 겉면에 판을 크게 인쇄한 것과 같고, 헤더(header)에 판을 적는 방식은 겉면은 그대로 두고 봉투 안쪽에 판을 표시하는 것과 같습니다. 스테이지(stage)로 나누는 방식은 본사 창고와 지점 창고가 각각 다른 판의 양식을 쓰게 하는 것에 대응합니다.

결론적으로 API 버전 관리는 경로, 헤더, 스테이지 가운데 무엇으로 판을 구분할지 정하고, 구버전 사용 중단 시점을 공지하며, 하위 호환성(예전 사용자가 고치지 않아도 계속 동작하는 성질)을 지키는 규칙을 함께 세우는 일입니다.

Infrastructure as Code

템플릿으로 API를 정의해 같은 환경을 다시 만드는 방법을 배웁니다

콘솔에서 마우스로 하나씩 눌러 만든 환경은 어디에도 기록이 남지 않아, 담당자가 자리를 비우면 같은 환경을 다시 만들 방법이 사라집니다. Infrastructure as Code(IaC)는 서버와 네트워크, API 같은 인프라를 사람이 클릭하는 대신 템플릿(template)이라는 문서로 정의하고, 그 문서를 실행해 같은 환경을 몇 번이든 다시 만들어 내는 방식입니다.

아파트를 짓는 과정에 견주면 이해가 빠릅니다. 설계도 없이 현장 목수의 기억만으로 벽을 세우면 그 집은 한 채밖에 못 짓지만, 도면을 그려 두면 같은 집을 다른 땅에서도 똑같이 올릴 수 있습니다.

템플릿이 도면이고, 도면을 보관하며 고친 이력을 남기는 형상 관리 저장소가 도면 보관함이며, 도면대로 시공하는 배포 자동화가 현장 작업을 대신합니다. 또 지은 집을 도면과 대조해 허가 없이 덧붙인 부분을 찾아내는 일이 드리프트(drift) 감지입니다.

정리하면 IaC는 인프라의 현재 모습을 코드로 적어 두고, 그 코드를 버전 관리하며, 코드를 실행해 환경을 재현하고 차이를 바로잡는 운영 방식입니다. 덕분에 개발과 검증, 운영 환경을 같은 모양으로 유지하고, 장애 뒤 복구도 문서를 다시 실행하는 일로 끝낼 수 있습니다.

CI/CD 파이프라인

변경을 자동으로 검증하고 배포하는 흐름을 만듭니다

손으로 빌드하고 파일을 복사해 서버에 올리는 배포는, 바쁜 날 한 단계를 건너뛰거나 순서를 바꾸는 실수로 장애를 만듭니다. CI/CD 파이프라인(continuous integration과 continuous delivery)은 코드가 저장소에 올라오는 순간부터 검증과 빌드, 배포까지를 정해진 단계로 자동 실행해 그 실수를 구조적으로 없애는 흐름입니다.

공장의 컨베이어 벨트를 떠올리면 단계가 그대로 대응됩니다. 부품이 벨트에 올라가면 첫 공정에서 치수가 맞는지 재고, 다음 공정에서 조립하고, 마지막에 포장해 출하하는데, 사람은 각 공정의 기준을 정하고 불량이 나온 곳만 들여다봅니다.

코드 커밋(commit)이 부품 투입이고, 자동 테스트가 치수 검사이며, 빌드 결과물인 아티팩트(artifact)가 포장된 제품이고, 배포가 출하입니다. 검사를 통과해야만 다음 벨트로 넘어가듯, 파이프라인도 테스트가 실패하면 배포 단계로 진행하지 않고 멈춥니다.

결론적으로 CI/CD 파이프라인은 통합과 검증을 자동화하는 CI, 그리고 언제든 배포 가능한 상태를 유지하고 실제 배포까지 자동화하는 CD를 이어 붙여, 변경의 속도와 안전을 함께 얻는 체계입니다.

설정 내보내기와 백업

API 정의를 뽑아 두고 문제가 생겼을 때 복원하는 방법을 배웁니다

콘솔에서 실수로 API 하나를 지우거나 스테이지 설정을 잘못 건드리면, 몇 달치 설정이 몇 초 만에 사라지고 다시 손으로 맞추는 데 며칠이 걸립니다. 설정 내보내기(export)와 백업은 API 정의와 관련 설정을 파일로 뽑아 두고, 문제가 생겼을 때 그 파일로 원래 상태를 되돌리는 절차입니다.

이사 전에 집 안 곳곳을 사진으로 찍고 짐 목록을 만들어 두는 일과 같습니다. 사진과 목록이 있으면 새 집에서 가구를 같은 자리에 놓을 수 있고, 무엇이 없어졌는지도 바로 알 수 있습니다.

내보내기 파일이 그 사진과 목록이고, 파일을 저장소에 넣어 변경 이력을 남기는 것이 짐 목록의 판을 관리하는 일이며, 복원(restore)이 사진을 보며 원래 배치로 되돌리는 작업입니다. 중요한 것은 백업을 한 번만 뜨는 것이 아니라 정해진 주기로 다시 뜨고, 되돌리는 연습까지 해 두어야 실제 사고 때 쓸 수 있다는 점입니다.

정리하면 설정 내보내기와 백업은 API의 정의와 배포 설정을 형상으로 남겨 두고, 사고 시 복원 가능한 지점을 확보해 두는 운영 습관입니다.

REST API와 HTTP API 마이그레이션

두 제품 사이를 옮길 때 달라지는 점과 절차를 압니다

같은 API를 REST API로 운영하다가 비용과 기능을 보고 HTTP API로 옮기려는데, 주소만 바꿔 끼우면 인증 방식과 통합 설정이 달라 클라이언트가 곧바로 깨집니다. REST API와 HTTP API 마이그레이션은 두 제품의 차이를 미리 표로 정리하고, 새 API를 나란히 세운 뒤 트래픽을 옮겨 가며 검증하는 절차입니다.

살던 집에서 새 집으로 이사하는 일과 비슷합니다. 두 집은 방 개수와 문 위치가 달라서, 짐을 그대로 옮기면 큰 가구가 문을 통과하지 못하므로 집마다의 구조를 적은 도면을 먼저 비교합니다.

인증 방식과 지원되는 통합 종류, 요청과 응답을 바꿔 주는 매핑(mapping) 설정의 차이가 그 도면 차이이고, 두 집에 잠시 짐을 나눠 두는 것이 기존 API와 새 API의 병행 운영입니다. 도메인 주소를 새 집으로 돌리는 일은 커스텀 도메인(custom domain)을 새 API 쪽으로 연결하는 것에 해당하며, 이때 일부 사용자만 새쪽으로 보내 반응을 확인하면 위험을 줄일 수 있습니다.

결론적으로 마이그레이션은 차이를 문서로 확정하고, 새 API를 병행 운영하며, 트래픽을 단계적으로 옮기고, 문제가 보이면 즉시 되돌릴 수 있게 준비하는 순서로 진행해야 합니다.

장애 대응 절차

문제가 생겼을 때 확인해야 할 순서를 정리합니다

새벽에 서비스가 갑자기 멈췄는데 담당자마다 다른 화면을 들여다보느라 원인 파악이 한 시간씩 늦어지는 일이 있습니다. 그런 혼란을 줄이려고 미리 정해 둔 확인 순서와 역할 분담이 장애 대응 절차(incident response procedure)입니다.

아파트에서 정전이 나면 관리사무소가 먼저 차단기 위치를 확인하고, 엘리베이터에 갇힌 사람이 있는지 살피고, 발전기를 돌린 뒤 원인을 조사하는 순서를 미리 정해 두는 것과 같습니다. 건물 전체를 한 사람이 뒤지지 않고 층별 담당자가 맡은 항목만 확인하기 때문에 놓치는 곳이 없습니다.

먼저 영향 범위를 확정하고, 최근 배포나 설정 변경처럼 방금 바뀐 것을 확인한 뒤, 로그와 지표를 보며 원인 후보를 좁힙니다. 복구 조치를 한 다음에는 같은 일이 다시 생기지 않도록 원인 분석 기록을 남기는 단계까지가 절차에 들어갑니다.

결국 장애 대응 절차는 감지, 영향 확인, 원인 추정, 복구, 재발 방지 기록의 순서를 역할과 함께 미리 정해 두는 운영 규칙입니다.

5xx 오류 원인 찾기

게이트웨이 자체 오류와 백엔드 오류를 구분하는 방법을 익힙니다

사용자에게 오류 화면이 뜨면 개발팀은 백엔드가 죽었다고 생각하기 쉽지만, 실제로는 게이트웨이가 요청을 넘기지 못해 생긴 오류일 때가 많습니다. 5xx 오류를 게이트웨이 자체에서 난 것과 백엔드에서 올라온 것으로 나눠 보는 것이 5xx 오류 원인 찾기입니다.

택배가 도착하지 않았을 때 판매처가 보내지 않은 것인지 배송사가 중간에 멈춘 것인지 운송장으로 구간을 확인하는 것과 같습니다.

Amazon API Gateway는 백엔드 연결 실패나 응답 시간 초과처럼 게이트웨이 쪽에서 생긴 문제로 502나 504를 돌려주고, 백엔드가 직접 만든 500은 그대로 전달하는 경우가 많습니다. 그래서 응답 본문과 헤더, 게이트웨이 로그와 백엔드 로그의 시각을 나란히 놓고 같은 요청 번호로 맞춰 보면 어느 쪽이 시작점인지 드러납니다. 게이트웨이 로그에 백엔드 응답 시간이 아예 없으면 연결 단계에서 끊긴 것이고, 그 시간이 길게 찍혀 있으면 백엔드가 늦게 답한 것입니다.

결국 5xx 원인 찾기는 응답 코드와 양쪽 로그를 대조해 게이트웨이 구간과 백엔드 구간 중 어디서 실패가 시작됐는지 가르는 일입니다.

지연 시간 튜닝

응답이 느릴 때 어느 구간을 손봐야 하는지 압니다

사용자가 화면을 눌렀는데 몇 초씩 기다리다 포기하는 일이 생기면 개발팀은 서버 성능부터 의심하게 됩니다. 하지만 응답이 느린 이유는 한 곳에 있지 않고 여러 구간에 나뉘어 있을 수 있어서, 구간별로 재는 방법을 알아 두는 것이 지연 시간 튜닝(latency tuning)입니다.

택배가 늦게 오면 보낸 집, 물류센터, 배송 기사 중 어디서 지체됐는지 확인하듯이, 요청도 클라이언트에서 게이트웨이까지, 게이트웨이 안에서의 처리, 백엔드가 답을 만드는 시간으로 나눠 봐야 합니다.

Amazon API Gateway에서는 전체 응답 시간(Latency)과 백엔드가 걸린 시간(IntegrationLatency)을 따로 볼 수 있어서 두 값의 차이로 게이트웨이 자체 처리의 비중을 가늠합니다. 차이가 크면 인증이나 요청·응답 변환, 캐시 설정을 살피고, 백엔드 쪽 값이 크면 함수의 콜드 스타트(cold start)나 데이터베이스 조회를 봅니다. 느린 요청을 전부 손보기보다 전체 시간을 많이 차지하는 소수의 요청부터 고치는 편이 효과적입니다.

결국 지연 시간 튜닝은 Latency와 IntegrationLatency를 비교해 병목이 게이트웨이 구간인지 백엔드 구간인지 먼저 가르는 일에서 시작합니다.

롤백

문제가 된 배포를 이전 상태로 되돌리는 방법을 익힙니다

새 버전을 배포한 직후 오류율이 치솟았는데 원인을 찾는 동안 사용자 피해가 계속 커지는 상황이 있습니다. 이때 새 기능을 고집하기보다 직전에 정상이던 상태로 빠르게 되돌리는 것이 롤백(rollback)입니다.

아파트 리모델링에서 새 배관 공사가 물을 새게 하면 철거를 고민하기 전에 먼저 예전 배관으로 되돌려 놓고 원인을 따지는 것과 같습니다.

Amazon API Gateway에서는 스테이지(stage)에 배포한 이력이 남아 있어서 이전 배포를 골라 다시 배포하면 설정이 그대로 복원됩니다. 다만 게이트웨이 설정만 되돌린다고 끝나지 않고, 그 뒤에 연결된 백엔드 함수나 환경 변수도 같은 시점으로 맞춰야 합니다. 되돌리는 절차를 미리 문서로 정해 두고 한 사람의 판단이 아니라 정해진 순서로 실행해야 급할 때 실수가 줄어듭니다.

결국 롤백은 배포 이력을 근거로 스테이지와 백엔드를 함께 이전 상태로 되돌려 피해 시간을 줄이는 운영 수단입니다.

비용 최적화

불필요한 요청과 캐시 설정을 조정해 비용을 줄입니다

쓰지도 않는 요청이 계속 오가는데 요금서를 열어 보면 예상보다 훨씬 큰 금액이 찍혀 있을 수 있습니다. 요청 수와 캐시 사용을 실제 트래픽에 맞게 조정해 낭비를 줄이는 것이 비용 최적화(cost optimization)입니다.

아파트 관리비가 새는 곳을 찾을 때 수도꼭지가 계속 흐르는지, 공용 전등이 낮에도 켜져 있는지를 확인하는 것과 비슷합니다.

Amazon API Gateway는 요청 수를 기준으로 과금되므로 화면 갱신용 폴링(polling)처럼 자주 부르지만 결과가 거의 같은 호출을 줄이는 것이 첫걸음입니다. 반복 조회가 많은 구간에는 스테이지 캐시(stage cache)를 붙여 백엔드 호출과 요청 처리 비용을 함께 덜 수 있지만, 캐시 자체에도 비용이 들기 때문에 실제로 재사용되는지 확인해야 합니다. 사용하지 않는 API나 스테이지를 정리하고, 로그 보관 기간과 상세 로깅 수준도 필요한 만큼만 두는 것이 좋습니다.

결국 비용 최적화는 무엇이 얼마나 호출되는지 먼저 측정하고, 줄일 호출과 켤 캐시를 근거를 가지고 고르는 일입니다.

운영 체크리스트

배포 후 주기적으로 확인할 항목을 정리해 습관으로 만듭니다

배포는 잘 끝났는데 며칠 뒤에야 인증서 만료나 할당량 초과를 발견하는 일이 반복되면 운영은 늘 사후 수습이 됩니다. 배포 뒤에 주기적으로 확인할 항목을 미리 정해 습관으로 만드는 것이 운영 체크리스트(operations checklist)입니다.

아파트 정기 점검표가 소방 설비, 승강기, 저수조를 정해진 주기마다 같은 방식으로 확인하듯이, 게이트웨이도 오류율, 지연 시간, 4xx와 5xx 비율, 스로틀링(throttling) 발생 여부를 같은 지표로 봅니다.

여기에 배포 이력과 인증서·액세스 키 만료일, 캐시 적중률과 비용 추이를 더하면 놓치기 쉬운 항목이 빠지지 않습니다. 항목마다 담당자와 확인 주기, 기준을 넘었을 때 할 일을 함께 적어 두어야 점검이 형식으로 끝나지 않습니다. 확인 결과는 짧게라도 기록으로 남겨 다음 배포 때 비교 기준으로 씁니다.

결국 운영 체크리스트는 지표와 만료일, 비용을 정해진 주기와 담당자로 확인해 작은 이상을 큰 장애로 키우지 않는 습관입니다.
