1부. 보안 운영 기초와 Security Hub의 위치001

클라우드 보안 운영이란

클라우드 보안을 사람 손이 아니라 정해진 절차와 체계로 돌린다는 뜻부터 잡는다

새벽에 걸린 경고 메일 한 통을 아침에야 발견하고, 담당자가 휴가 중이라 확인이 다음 주로 밀리는 일이 반복되면 보안은 사람의 기억력에 얹힌 운에 가까워집니다. 클라우드 보안 운영은 이렇게 사람 손에 매달린 대응을 정해진 절차와 체계 위에 올려, 누가 자리에 없어도 같은 방식으로 돌아가게 만드는 일입니다. 회사 보안 운영은 잘 짜인 야간 경비 체계와 비슷합니다. 순찰 경로와 보고 양식, 교대 인수인계 규칙이 미리 정해져 있어서 경비원이 바뀌어도 건물 상태가 같은 기준으로 기록됩니다. 어떤 이상이 감지되면 정해진 순서대로 보고되고, 처리 결과가 장부에 남아 다음 교대조가 이어받습니다.

클라우드에서도 자산 목록과 점검 항목, 알림이 흘러가는 경로, 조치를 마쳤다는 기록까지가 하나의 체계로 묶여야 비로소 운영이라고 부를 수 있습니다. 결국 클라우드 보안 운영은 도구 하나를 도입하는 일이 아니라 점검·탐지·대응·기록이 반복 가능한 절차로 정착된 상태를 뜻하며, 사람이 아니라 체계가 보안의 기준선을 지키게 만드는 것입니다.

보안 태세(Security Posture)

우리 계정이 지금 안전한 상태인지 판단하는 기준이 무엇인지 설명한다

계정을 열어 보면 저장소가 공개로 열려 있는지, 관리자 권한이 몇 명에게 몰려 있는지 한눈에 알 수 없어서, 사고가 난 뒤에야 "원래 이렇게 되어 있었다"는 말이 나오곤 합니다. 보안 태세(Security Posture)는 이렇게 흩어진 설정과 권한을 모아 지금 우리 계정이 안전한 상태인지 판단하는 기준입니다. 아파트 관리 상태를 떠올리면 이해가 쉽습니다. 정문 잠금이 작동하는지, 소화기가 유효기간 안에 있는지, 비상구 앞에 짐이 쌓이지 않았는지를 항목별로 확인해야 "이 건물은 안전하다"고 말할 수 있습니다. 하나라도 어긋나면 위험도가 올라가고, 어디가 어긋났는지 지목할 수 있어야 다음 조치도 정해집니다.

클라우드 보안 태세도 마찬가지로, 무엇을 안전하다고 볼지 정한 점검 항목과 그 항목에 비춰 본 현재 상태, 그리고 어긋난 곳의 목록이라는 세 가지로 구성됩니다. 정리하면 보안 태세는 암호화나 방화벽 같은 개별 기능이 아니라, 계정 전반의 설정이 의도한 기준에 얼마나 맞는지를 나타내는 종합적인 상태 판단입니다.

CSPM(클라우드 보안 태세 관리)

설정이 틀어진 곳을 찾아 알려주는 CSPM이 하는 일을 다룬다

클라우드 계정에는 수백 개의 설정 항목이 있고 담당자는 그중 어느 것이 위험한지 알 방법이 없어, 결국 사고가 터진 항목만 뒤늦게 손보게 됩니다. CSPM(클라우드 보안 태세 관리, Cloud Security Posture Management)은 이 설정들이 기준에서 벗어난 곳을 자동으로 찾아 알려 주는 서비스입니다. 건물의 소방 점검을 자동으로 도는 시스템을 생각해 보면 구조가 보입니다. 점검표에 적힌 항목을 정해진 주기마다 훑고, 기준에 어긋난 곳에는 "3층 비상구 앞 적재물"처럼 위치와 사유를 붙여 보고서를 만듭니다. 심각한 항목은 먼저 올려 보여 주고, 고친 뒤 다시 점검해 결과가 바뀌었는지 확인합니다.

CSPM도 점검 규칙과 주기적인 수집, 위험도에 따른 정렬, 조치 후 재확인이라는 같은 흐름으로 움직이며, 여러 계정과 리전을 한 기준으로 훑는다는 점이 사람이 손으로 하는 점검과 다릅니다. 즉 CSPM은 클라우드 설정을 지속적으로 수집해 기준과 비교하고, 어긋난 항목을 위험도 순으로 알려 주는 태세 관리 전용 도구입니다.

CSPM과 CNAPP의 관계

CSPM·CWPP·CIEM이 어떻게 나뉘고 어디서 겹치는지 정리한다

보안 담당자가 도구를 고르다 보면 설정 점검, 서버 보호, 권한 분석이 각각 다른 제품에 흩어져 있어 같은 자산을 여러 화면에서 따로 확인해야 하는 번거로움을 겪습니다. 이때 등장하는 것이 CSPM(클라우드 보안 태세 관리)과 CNAPP(클라우드 네이티브 애플리케이션 보호 플랫폼, Cloud Native Application Protection Platform)의 관계입니다. 종합 병원과 전문 진료과를 비교하면 구분이 쉽습니다. CSPM은 설정이 기준에 맞는지 보는 검진 과목이고, CWPP(클라우드 워크로드 보호, Cloud Workload Protection Platform)는 서버와 컨테이너 같은 일하는 대상 자체를 지키는 과목이며, CIEM(클라우드 인프라 권한 관리, Cloud Infrastructure Entitlement Management)은 누가 어떤 권한을 가졌는지 들여다보는 과목입니다. CNAPP는 이 과목들을 한 건물에 모아 둔 종합 병원으로, 진료 기록을 공유하니 같은 환자를 여러 번 설명하지 않아도 됩니다. 그래서 CSPM은 CNAPP 안에 들어가는 한 과목이면서, 독립 제품으로도 존재합니다. 정리하면 CSPM·CWPP·CIEM은 각각 설정·워크로드·권한을 맡는 영역이고, CNAPP는 이들을 하나의 플랫폼으로 묶어 자산과 위험 정보를 공유하게 만든 상위 개념입니다.

AWS Security Hub란

여러 보안 서비스의 결과를 한곳에 모으는 서비스라는 정의를 잡는다

AWS를 쓰는 회사는 계정마다 경고가 쏟아지는데, 설정 점검 결과는 한 화면, 위협 탐지 결과는 또 다른 화면에 있어서 지금 우리 전체가 안전한지 판단할 지점이 없습니다. AWS Security Hub는 이런 여러 보안 서비스의 결과를 한곳에 모아 보여 주는 서비스입니다. 회사 정문의 통합 관제실을 떠올리면 됩니다. 각 층의 화재 감지기, 출입 통제기, CCTV가 저마다 다른 장비인데도 관제실 화면에는 같은 형식의 경보로 올라옵니다. 관제 요원은 어느 층 어느 구역에서 무슨 일이 있었는지 한 목록에서 확인하고, 심각한 것부터 처리 순서를 정합니다. Security Hub도 여러 보안 서비스의 발견 항목을 공통된 형식으로 받아 한 목록에 쌓고, 보안 기준에 비춰 통과 여부를 표시하며, 처리 상태를 남겨 다음 사람이 이어받게 합니다.

다만 모든 서비스가 저절로 연결되는 것은 아니고, 결과를 보내도록 연동을 켜야 목록에 들어옵니다. 결국 AWS Security Hub는 탐지 자체를 하는 서비스가 아니라, 흩어진 보안 결과를 공통 형식으로 모아 기준 대비 상태와 처리 현황을 한 화면에서 관리하게 해 주는 집결지입니다.

Security Hub가 해결하는 문제

계정마다 흩어진 경고를 매일 손으로 확인하던 상황을 설명한다

계정이 다섯 개만 넘어도 담당자는 아침마다 각 계정의 보안 화면을 하나씩 열어 경고를 대조하고, 같은 내용을 손으로 표에 옮겨 적는 일을 반복하게 됩니다. 그렇게 며칠이 지나면 어떤 경고를 이미 확인했는지조차 기억나지 않고, 중요한 항목이 사소한 항목 더미에 묻혀 사라집니다. Security Hub가 해결하는 문제가 바로 이 지점입니다. 건물마다 따로 놓인 비상벨을 하나의 상황실로 모으는 일과 같습니다. 예전에는 각 건물 관리인이 벨을 듣고 전화로 알렸지만, 이제는 모든 벨이 상황실 한 화면에 같은 표시로 뜨고 어느 건물의 몇 층인지 함께 나옵니다. 상황실은 심각도에 따라 순서를 매기고, 처리한 건은 완료로 표시해 중복 확인을 없앱니다.

계정마다 흩어진 경고를 매일 손으로 훑던 일이, 한 목록을 위에서부터 처리하는 일로 바뀌는 것입니다. 정리하면 Security Hub는 계정별로 흩어진 보안 결과를 공통 형식으로 통합하고 중복 확인과 누락을 줄여, 여러 계정을 가진 조직이 하나의 기준으로 보안 상황을 판단하게 해 줍니다.

Security Hub의 구성 요소

표준·컨트롤·이슈·통합이 서로 어떻게 맞물리는지 본다

회사에 보안 담당자가 한 명뿐인데 점검해야 할 항목은 수백 개이고, 결과는 서로 다른 화면에 흩어져 있으면 어디서부터 손대야 할지 알 수가 없습니다. AWS Security Hub는 이렇게 흩어진 보안 점검을 한곳에 모아 보여 주려고 만들어진 서비스입니다.

아파트 관리사무소를 떠올리면 구조가 쉽게 잡힙니다. 표준(standard)은 관리사무소가 채택한 점검 규정집이고, 컨트롤(control)은 그 규정집에 적힌 개별 점검 항목입니다. 관리사무소 직원이 세대를 돌며 항목별로 확인해 남기는 미비 사항이 이슈(finding)이며, 정비 업체나 경비 업체의 보고서를 규정집 항목에 맞춰 받아 넣는 일이 통합(integration)입니다.

규정집 없이 점검표만 있어도, 점검표 없이 결과만 쌓여도 쓸모가 없습니다. 정리하면 Security Hub는 표준으로 기준을 정하고, 컨트롤로 항목을 정의하고, 이슈로 결과를 모으고, 통합으로 다른 서비스의 점검 결과까지 같은 형식으로 흡수하는 구조입니다.

Security Hub와 유사 서비스 비교

GuardDuty·Config·Inspector와 무엇이 다르고 어떻게 함께 쓰는지 비교한다

보안을 위해 침입 감시, 설정 점검, 취약점 진단을 각각 다른 도구로 돌리면 보고서가 세 가지 형식으로 도착하고, 정작 무엇이 가장 급한지는 아무도 말해 주지 않습니다. AWS Security Hub는 이렇게 성격이 다른 점검 결과를 하나의 기준으로 모아 순위를 매겨 주는 서비스입니다.

한 회사가 건물 관리를 위해 세 업체를 쓴다고 해 보겠습니다. GuardDuty는 건물에 침입자가 있는지 감시하는 경비 용역이고, Config는 건물이 설계 도면과 규정대로 유지되는지 기록을 대조하는 감리 업체이며, Inspector는 벽과 배관의 균열을 정밀 진단하는 점검 업체입니다. Security Hub는 이 세 업체의 보고서를 받아 하나의 기준표에 맞춰 정리하고 점수를 매기는 총무팀입니다.

용어로 다시 정리하면 GuardDuty는 위협 탐지, Config는 구성 규칙 평가, Inspector는 취약점 스캔을 맡고 Security Hub는 그 결과를 표준에 대조해 모으는 역할입니다. 세 서비스는 서로 대체 관계가 아니라 맡은 영역이 다르므로, 탐지와 점검은 각자에게 맡기고 판단과 취합은 Security Hub에서 하는 식으로 함께 쓰는 것이 자연스럽습니다.

Security Hub의 리전 구조

각 지사 사무실에 그 지사 전용 장부와 점검 담당자가 따로 있는 것과 같습니다. 그래서 서울 리전에서 켠 표준과 쌓인 이슈가 도쿄 리전에 자동으로 생기지 않고, 리전마다 따로 켜고 따로 봐야 합니다.

AWS 계정과 리전

그래서 같은 회사라도 계정이 다르면 Security Hub 설정이 공유되지 않고, 같은 계정이라도 리전이 다르면 결과가 따로 쌓입니다. 여러 계정을 하나로 묶어 관리하려면 조직(Organizations) 수준의 연결과 각 계정의 활성화가 필요하다는 점도 여기서 나옵니다. 정리하면 계정은 누가 무엇을 볼 수 있는지의 경계이고 리전은 데이터가 머무는 위치이며, Security Hub는 이 두 축의 조합마다 따로 상태를 가집니다.

IAM 사용자·역할·정책

누가 무엇을 할 수 있는지 정하는 기본 구조를 이해한다

보안 도구를 도입했는데 아무나 설정을 바꿀 수 있다면 그 도구는 오히려 위험이 됩니다. AWS Identity and Access Management는 누가 무엇을 할 수 있는지 정하는 기본 구조이며, Security Hub 운영에서도 이 위에 권한이 얹힙니다.

사원증 체계에 비유하면 이해가 빠릅니다. 사용자(user)는 사람마다 발급되는 사원증이고, 역할(role)은 사람이 아니라 직책에 붙는 권한 묶음이며, 정책(policy)은 어느 문을 몇 시에 열 수 있는지 적힌 출입 규정입니다. 역할은 사원증을 대신 내미는 방식이라, 사람이 바뀌어도 직책만 같으면 같은 권한이 그대로 적용됩니다.

Security Hub에서는 점검 결과를 읽는 사람과 기준을 바꾸는 사람을 분리하는 식으로 이 구조를 씁니다. 핵심은 권한을 사람에게 고정하지 않고 직책과 규정으로 관리한다는 점이며, 이 원칙이 지켜져야 보안 도구의 설정이 안전하게 유지됩니다.

IAM 권한 평가 순서

명시적 거부가 왜 가장 세고 권한은 어떤 순서로 판단되는지 다룬다

회사에서 새로 들어온 직원에게 업무에 필요한 만큼만 권한을 주려다 보면, 부서 권한과 개인 권한과 예외 규칙이 뒤섞여 이 사람이 이 작업을 할 수 있는지를 한눈에 답하기 어려워집니다. AWS IAM(Identity and Access Management)은 이런 혼선을 없애기 위해 요청 하나를 정해진 순서로 채점하는 권한 평가 절차를 두고 있습니다.

아파트 출입을 떠올리면 이해가 쉽습니다. 정문 경비실에는 이 명단의 사람은 무조건 통과시키는 허용 명단이 있고, 반대로 이 사람은 무조건 막는다는 금지 명단이 있으며, 두 명단에 없는 사람은 집주인이 따로 발급한 출입증을 보여야 들어갈 수 있습니다.

IAM도 똑같아서 명시적 거부(explicit deny)가 하나라도 걸려 있으면 다른 어떤 허용도 무시하고 즉시 차단하며, 거부가 없을 때만 허용 정책을 찾아보고, 허용도 없으면 기본적으로 거부하는 구조입니다. 여기에 서비스 제어 정책 같은 상한선이 걸려 있으면 허용이 있어도 그 선을 넘는 요청은 통과하지 못합니다.

즉 IAM 권한 평가는 명시적 거부가 가장 세고, 그다음 허용을 확인하며, 아무것도 없으면 암묵적 거부로 끝나는 순서로 판정하는 방식입니다.

AWS Organizations

여러 계정을 하나의 조직으로 묶어 관리하는 방법을 이해한다

회사가 커지면서 부서마다 AWS 계정을 따로 만들면 청구서도 보안 설정도 사용자 관리도 제각각이 되어, 어느 계정이 어떤 상태인지 파악하는 데만 며칠이 걸립니다. AWS Organizations는 이렇게 흩어진 계정들을 하나의 조직으로 묶어 한곳에서 관리하는 서비스입니다.

건물주가 여러 동의 임대 사무실을 하나의 관리 사무소에서 관리하는 모습을 떠올리면 됩니다.

관리 사무소 역할을 하는 관리 계정(management account)이 조직을 만들고, 나머지 구성원 계정(member account)을 초대해 하나의 나무 구조로 묶으며, 이 구조를 조직 단위(OU, Organizational Unit)로 나눠 부서별로 같은 규칙을 한 번에 적용합니다. 청구도 한 통으로 모아 부서별로 나눠 볼 수 있고, 새 계정을 만들 때 기존 계정의 설정을 복제해 일관성을 유지할 수 있습니다. 계정을 새로 들이거나 옮길 때도 이 구조 안에서 처리되므로 담당자가 일일이 손으로 맞출 필요가 없습니다.

정리하면 AWS Organizations는 관리 계정을 정점으로 여러 계정을 계층 구조로 묶어 청구와 정책을 중앙에서 다루는 서비스입니다. 덕분에 조직 전체의 기준을 한 번만 정해도 아래 계정에 그대로 퍼지게 됩니다.

서비스 제어 정책(SCP)

조직 전체에 권한의 상한을 거는 방법과 한계를 본다

조직으로 계정을 묶어도 각 계정 관리자가 실수로 모든 권한을 열어버리면 조직 전체가 위험해집니다. 서비스 제어 정책(SCP, Service Control Policy)은 그런 사고를 막기 위해 조직 차원에서 권한의 천장을 미리 정해 두는 장치입니다.

아파트 단지의 전체 출입 규정과 같습니다. 각 세대는 자기 집 현관 비밀번호를 자유롭게 바꿀 수 있지만, 단지 정문에서 새벽 두 시 이후에는 누구도 나갈 수 없다는 규정을 걸어 두면 세대별 설정과 무관하게 그 선을 넘을 수 없습니다.

SCP도 마찬가지로 허용 목록을 새로 만들어 주는 것이 아니라 이미 가진 권한 중에서 쓸 수 있는 범위의 상한만 잘라내며, 조직 루트나 OU에 붙여 아래 계정 전체로 상속됩니다. 그래서 SCP에 허용이 있어도 계정 안의 IAM 정책에 허용이 없으면 아무 일도 할 수 없습니다.

즉 SCP는 권한을 주는 도구가 아니라 최대 허용 범위를 제한하는 가드레일입니다. 그리고 이 정책이 관리 계정에는 적용되지 않는다는 점도 함께 기억해야 합니다.

위임 관리자(Delegated Administrator)

관리 계정 대신 보안 전담 계정에 운영 권한을 넘기는 방식을 설명한다

Security Hub나 GuardDuty 같은 보안 서비스를 쓰려면 조직 전체 설정을 바꿀 수 있는 관리 계정 권한이 필요하지만, 그 계정은 청구와 조직 자체를 다루는 곳이라 보안 담당자에게 함부로 넘길 수 없습니다. 위임 관리자(Delegated Administrator)는 이런 딜레마를 풀기 위해 특정 서비스의 운영 권한만 별도의 보안 전담 계정으로 넘기는 기능입니다.

회사 건물의 마스터 키를 생각하면 됩니다. 총무팀장이 들고 있는 마스터 키 하나로 모든 문을 열 수 있지만, 그 키를 경비 업체 직원에게 통째로 주는 대신 방범 설비만 조작할 수 있는 별도 키를 만들어 주는 방식입니다.

AWS Organizations에서는 관리 계정이 위임 관리자를 지정하면, 그 계정이 해당 서비스에 한해 조직의 모든 구성원 계정을 대신해 설정을 바꾸고 결과를 모아 볼 수 있습니다. 다만 위임 관리자로 지정하려면 대상 계정이 조직 구성원이어야 하고, 서비스마다 지원 여부와 지정 방식이 조금씩 다릅니다.

정리하면 위임 관리자는 관리 계정의 최상위 권한을 넘기지 않고도 서비스별 운영을 전담 계정에 맡기는 위임 구조입니다. 덕분에 보안 팀은 필요한 만큼만 권한을 갖고 일할 수 있습니다.

CloudTrail 기초

누가 무엇을 했는지 남기는 감사 로그가 어떤 역할을 하는지 본다

장애나 정보 유출이 터진 뒤에 누가 언제 이 설정을 바꿨는지 아무도 답하지 못하면 원인을 찾을 수도, 같은 일이 다시 일어나지 않게 막을 수도 없습니다. AWS CloudTrail은 계정 안에서 일어나는 API 호출을 빠짐없이 기록해 두는 감사 로그 서비스입니다.

건물 로비의 출입 기록부와 같습니다. 누가 몇 시에 어느 문으로 들어와 어떤 층에서 무엇을 했는지 차례로 적히고, 기록에는 행위자와 시각과 요청 내용과 결과가 함께 남습니다.

CloudTrail도 콘솔 접속, 명령줄 도구, SDK 호출 같은 모든 경로의 요청을 이벤트(event)로 남기고, 이 기록을 S3 버킷에 모아 보관하거나 CloudWatch 같은 도구로 넘겨 이상 징후를 감시할 수 있습니다. 다만 기록은 기본적으로 짧은 기간만 조회되고 장기 보관은 별도 설정이 필요합니다.

즉 CloudTrail은 누가 무엇을 했는지 시간 순서로 남기는 감사 추적 기록이며, 사후 분석과 규정 준수의 토대가 됩니다. 이 기록이 있어야 다른 보안 도구의 탐지 결과도 근거를 갖출 수 있습니다.

Amazon GuardDuty 기초

위협 탐지 결과가 어떤 모습으로 만들어지는지 이해한다

계정이 수백 개로 늘면 로그가 아무리 쌓여도 사람이 매일 들여다보며 이상한 점을 찾는 것은 사실상 불가능합니다. Amazon GuardDuty는 그 로그를 대신 읽고 위협으로 의심되는 행동을 찾아내는 관리형 위협 탐지 서비스입니다.

아파트 단지에 상주하는 경비원을 떠올리면 됩니다. 경비원은 출입 기록과 방범 카메라와 외부 소식을 함께 보면서 평소와 다른 움직임을 골라내 보고서를 작성합니다.

GuardDuty도 CloudTrail의 API 기록, VPC 흐름 로그, DNS 조회 기록 같은 데이터를 계속 분석해 알려진 악성 주소와의 통신이나 평소와 다른 권한 사용 같은 패턴을 찾아 결과를 발견 사항(finding)으로 만듭니다. 각 발견 사항에는 심각도와 근거가 함께 붙어 담당자가 우선순위를 정할 수 있습니다.

정리하면 GuardDuty는 여러 로그를 스스로 모아 분석해 의심 행위를 발견 사항으로 제시하는 탐지 서비스이며, 차단이 아니라 알림에 초점을 둡니다. 그래서 실제 대응은 다른 서비스나 사람의 판단과 함께 이루어집니다.

AWS Config 기초

리소스 설정 이력을 기록하고 규칙으로 평가하는 서비스를 이해한다

운영하던 서버의 보안 그룹이 어느 날 갑자기 열려 있었는데 누가 언제 바꿨는지 아무도 답하지 못하면 사고 원인을 찾는 일은 사실상 불가능해집니다. AWS Config는 이런 상황을 막기 위해 각 리소스의 설정을 시간순으로 기록하고 정해 둔 규칙에 맞는지 계속 평가하는 서비스입니다.

아파트 관리 사무소의 공사 대장을 떠올리면 이해가 쉽습니다.

세대마다 벽을 허물거나 창을 바꾸면 그 사실을 날짜와 함께 대장에 남기듯, Config는 리소스 하나하나의 설정 상태를 configuration item(설정 항목)이라는 기록으로 남깁니다. 이 기록이 쌓이면 configuration history(설정 이력)가 되어 몇 시 몇 분에 무엇이 어떻게 달라졌는지 되짚을 수 있고, 관리 규정에 해당하는 rule(규칙)을 걸어 두면 창문은 외벽 색과 같아야 한다는 조건을 어긴 세대가 즉시 목록에 올라옵니다. 규칙 묶음을 한 번에 적용하는 conformance pack(적합성 팩)은 단지 전체 공사 규정집을 통째로 배포하는 것과 같습니다.

정리하면 AWS Config는 리소스 설정의 변경 이력을 자동으로 보관하고 규칙 기반 평가로 현재 상태의 적합성을 판정하는 구성 관리 서비스입니다.

Amazon Inspector 기초

취약점 스캔 결과가 어떤 형태로 나오는지 파악한다

서버에 어떤 프로그램이 어떤 버전으로 설치되어 있는지, 그 버전에 알려진 취약점이 있는지, 외부에서 접근 가능한 통로가 뚫려 있는지를 사람이 일일이 대조하는 일은 현실적으로 불가능합니다. Amazon Inspector는 이 대조 작업을 자동으로 반복해 주는 취약점 관리 서비스입니다.

아파트 관리사무소가 매달 세대별 가스와 전기 설비를 점검하러 도는 모습을 떠올리면 비슷합니다.

점검반이 집집마다 배관 상태를 확인하듯 Inspector는 EC2 인스턴스, 컨테이너 이미지, Lambda 함수 같은 대상을 정해진 주기로 훑고 문제가 되는 부분을 finding(발견 항목)이라는 이름의 결과물로 하나씩 남깁니다. 각 발견 항목에는 얼마나 급한지 알려 주는 severity(심각도) 등급이 붙어 게시판의 빨간 딱지처럼 눈에 띄고, 네트워크가 외부에 열려 있는지까지 확인하는 reachability(도달 가능성) 점검은 현관문이 잠겨 있는지 확인하는 일에 해당합니다. 이 결과는 대시보드와 리포트 형태로 모여 관리자가 어디부터 손봐야 할지 순서를 정하게 해 줍니다.

결국 Amazon Inspector는 대상 리소스의 소프트웨어 구성과 네트워크 노출을 주기적으로 스캔하고 그 결과를 심각도가 붙은 발견 항목 목록으로 제공하는 서비스입니다.

Security Hub 활성화하기

콘솔에서 켜는 절차와 켜는 순간 실제로 벌어지는 일을 설명한다

각 층에 따로 있던 화재 감지기와 CCTV를 방재실 한 곳에 연결하듯, 콘솔에서 Security Hub를 열고 활성화를 누르면 현재 리전에 대해 서비스가 켜지고 이미 쓰고 있는 GuardDuty와 Inspector와 Config 같은 서비스와의 연동이 자동으로 이어집니다. 이때 어떤 standard(표준)로 점검할지 고르게 되는데 이는 방재실 벽에 어떤 점검 항목표를 붙일지 정하는 일이고, 켜진 직후에는 연동된 서비스들이 보내온 결과를 모아 findings(발견 항목)로 정리하고 점검 항목별 통과와 실패를 계산해 security score(보안 점수)를 매깁니다. 처음 한 번은 기존 리소스를 훑는 초기 평가가 돌기 때문에 결과가 화면에 다 차기까지 시간이 조금 걸릴 수 있습니다.

정리하면 Security Hub 활성화는 리전 단위로 서비스를 켜고 연동된 보안 서비스들의 결과를 표준에 맞춰 집계하며 그 결과를 발견 항목과 점수로 보여 주는 작업입니다.

초기 설정 흐름

먼저 지금 보고 있는 리전이 어디인지 확인하는데 이는 사무소 창구가 어느 동을 담당하는지 확인하는 일이고, 다음으로 basic standard(기본 표준)를 그대로 쓸지 다른 표준을 추가할지 고릅니다. 규정집을 정했으면 활성화를 눌러 점검을 시작하고, 이어서 어떤 보안 서비스가 연동되어 결과를 보내는지 목록에서 확인한 뒤 발견 항목과 점수 화면이 채워지는지 살펴봅니다.

이 순서를 건너뛰고 활성화부터 누르면 표준이 기본값으로 정해지므로 나중에 원하는 점검 항목으로 바꾸는 추가 작업이 필요해집니다.

결국 초기 설정 흐름은 리전 확인과 표준 선택과 활성화와 연동 서비스 확인과 결과 검토라는 다섯 단계를 순서대로 밟아 Security Hub의 평가 기준과 범위를 정하는 절차입니다.

기본 표준 선택

처음에 어떤 표준을 켤지 고르는 기준을 세운다

표준을 아무거나 켜면 점검 항목이 수백 개로 늘어나 경고가 쏟아지고, 반대로 아무 표준도 고르지 않으면 점검이 아예 돌지 않아 위험이 그대로 남습니다. 그래서 처음에는 어떤 standard(표준)를 기준으로 삼을지 신중히 고르는 일이 필요합니다.

건강검진을 받을 때 기본 검진과 정밀 검진 중 무엇을 받을지 고르는 상황과 비슷합니다.

기본 검진은 나이와 성별에 맞춰 꼭 봐야 할 항목만 담아 부담이 적고, 정밀 검진은 검사 항목이 많아 시간과 비용이 더 들지만 놓치는 병을 줄여 줍니다. Security Hub의 basic standard(기본 표준)는 AWS가 권장하는 핵심 점검 항목을 모은 것으로 기본 검진에 해당하고, CIS AWS Foundations Benchmark나 PCI DSS처럼 특정 규제나 산업 기준을 담은 표준은 정밀 검진에 해당합니다. 고르는 기준은 세 가지인데 우리가 지켜야 할 규제가 무엇인지와 그 항목을 실제로 관리할 인력이 있는지와 경고를 감당할 수 있는 양인지를 따져 보면 됩니다.

정리하면 기본 표준은 최소한의 공통 점검을 빠르게 시작하는 기준이고, 규제 대응이 필요하면 해당 표준을 추가로 켜되 운영 부담과 점검 범위를 함께 저울질해 선택해야 합니다.

리전별 활성화 전략

모든 리전을 켤지 주요 리전만 켤지 결정하는 방법을 다룬다

서울 리전만 점검을 켜 두었는데 누군가 도쿄 리전에 서버를 하나 만들면 그 서버는 어떤 점검에도 잡히지 않고, 반대로 쓰지도 않는 모든 리전을 켜 두면 같은 경고가 여러 벌 생겨 정작 중요한 문제를 놓치게 됩니다. 리전별 활성화 전략은 이 범위를 어떻게 정할지 다루는 문제입니다.

전국에 지점을 둔 회사가 CCTV를 어디까지 설치할지 정하는 일과 같습니다. 모든 지점에 카메라를 달면 빈 지점의 화면까지 보느라 인력이 낭비되고 본사만 달면 나머지 지점이 사각지대가 됩니다.

Security Hub는 리전마다 따로 켜지므로 기준이 되는 home region(기준 리전)을 하나 정하고 실제 서비스를 운영하는 리전을 linked region(연동 리전)으로 함께 활성화하는 방식이 일반적입니다. 여러 리전의 결과를 한곳에서 보려면 aggregator(집계자)를 두어 각 리전의 발견 항목을 모으면 되고, 리전마다 같은 표준을 반복 설정하는 수고를 줄이려면 central configuration(중앙 구성)으로 한 번에 배포할 수 있습니다.

정리하면 리전별 전략은 실제로 리소스를 두는 리전을 먼저 목록화하고 기준 리전과 연동 리전을 나누어 활성화한 뒤 집계와 중앙 구성으로 결과와 설정을 한곳에서 관리하는 방식입니다.

활성화 전 점검 사항

권한·로그·비용을 미리 확인하는 체크리스트를 만든다

보안 서비스를 일단 켜고 보자는 마음으로 활성화했다가 권한 오류와 예상 밖의 요금, 비어 있는 로그 화면을 한꺼번에 마주하는 경우가 많습니다. 그래서 AWS Security Hub를 켜기 전에 권한과 로그, 비용을 미리 확인하는 체크리스트를 만들어 두는 것이 좋습니다. 이는 보안 태세 관리(security posture management)라는 큰 틀 안에서 여러 계정과 리전의 점검 결과를 한곳에 모으는 첫 단추에 해당합니다.

아파트 관리사무소가 새 경비 시스템을 도입할 때와 비슷합니다. 경비원에게 어디까지 출입을 허용할지 정하고, 순찰 일지를 어디에 남길지 정하고, 관리비가 얼마나 오를지 계산한 뒤에야 시스템을 가동합니다.

Security Hub도 마찬가지로 서비스 연결 역할(service-linked role)이 계정에 만들어질 수 있는 권한이 있는지, 평가 결과를 CloudWatch Logs나 EventBridge로 내보낼 경로가 준비되어 있는지, 컨트롤(control) 수가 늘어날 때 비용이 어떻게 달라지는지를 먼저 확인해야 합니다. 특히 여러 리전을 함께 켤 계획이라면 리전마다 같은 준비가 되어 있는지도 점검 항목에 넣어야 합니다.

정리하면 활성화 전 점검은 IAM 권한, 로그와 이벤트 전달 경로, 비용 구조라는 세 가지를 사전에 확인하는 절차입니다.

서비스 연결 역할

Security Hub가 다른 서비스 결과를 읽기 위해 쓰는 역할을 이해한다

Security Hub가 다른 보안 서비스의 점검 결과를 읽으려 할 때 그럴 권한이 없으면 컨트롤이 계속 확인 불가 상태로 남습니다. 이때 등장하는 것이 서비스 연결 역할(service-linked role)로, 특정 AWS 서비스가 사용자를 대신해 다른 서비스의 정보를 읽도록 미리 정해진 권한을 담은 역할입니다.

택배가 집으로 올 때 집 열쇠를 기사에게 통째로 맡기지 않고, 경비실이 신원을 확인한 뒤 대신 문을 열어 주는 것과 같습니다. 서비스 연결 역할은 AWS가 미리 정의한 권한 범위만 가지고 있으며, 계정에서 Security Hub를 처음 활성화할 때 자동으로 만들 수 있습니다.

이 역할 덕분에 Security Hub는 AWS Config, Amazon GuardDuty 같은 서비스가 이미 모아 둔 결과를 읽어 보안 표준(security standard)의 컨트롤을 평가하고, 그 결과를 발견 항목(finding)으로 정리합니다. 사용자가 직접 권한을 넓혀 줄 필요가 없고, 역할이 삭제되면 수집도 함께 멈춘다는 점을 기억하면 됩니다.

즉 서비스 연결 역할은 Security Hub가 다른 서비스의 데이터를 읽도록 위임된 IAM 역할이며, 활성화와 함께 자동으로 연결되는 신뢰 관계입니다.

활성화 상태 확인

표준과 컨트롤이 실제로 켜졌는지 확인하는 방법을 익힌다

활성화 버튼을 누른 뒤 화면만 훑고 지나가면 표준과 컨트롤이 실제로 켜졌는지 알기 어렵습니다. 빈 요약 화면을 보고 안심했다가 나중에 점검 결과가 하나도 쌓이지 않은 것을 발견하는 일이 생기므로, 상태를 확인하는 방법을 익혀 두어야 합니다.

아파트 소방 점검 뒤 현관에 붙는 점검 완료 스티커를 떠올리면 이해하기 쉽습니다. 스티커가 붙었다는 사실만으로는 부족하고, 어느 설비를 언제 점검했는지 대장과 대조해야 진짜 확인이 됩니다.

Security Hub에서는 콘솔의 요약(summary) 화면과 보안 표준 목록에서 해당 표준이 사용 가능(enabled) 상태인지 보고, 컨트롤 목록에서 각 컨트롤이 통과 또는 실패로 평가되고 있는지 확인합니다. 자동화에는 AWS CLI의 describe-hub와 get-enabled-standards 같은 명령을 써서 활성화 여부와 켜진 표준 목록을 직접 조회할 수 있습니다.

정리하면 활성화 상태 확인은 콘솔의 표준 목록과 컨트롤 평가 결과, 그리고 API 조회를 함께 대조해 실제로 켜졌음을 확인하는 작업입니다.

3부. 활성화와 초기 설정028

비활성화와 데이터 보존

서비스를 끄면 무엇이 남고 무엇이 사라지는지 정리한다

서비스를 끄면 무엇이 사라지고 무엇이 남는지 모른 채 비활성화하면, 나중에 감사나 장애 분석을 하려는 순간 근거 자료가 없어 곤란해집니다. 그래서 끄기 전에 보존 범위를 먼저 정리해 두는 것이 안전합니다.

이사할 때 짐을 정리하는 상황과 비슷합니다. 집주인에게 돌려주는 열쇠와, 창고에 그대로 남겨 두는 서류를 구분해야 합니다.

Security Hub를 비활성화하면 서비스 연결 역할이 삭제되고 다른 리전의 결과를 모으던 집계(aggregation) 설정도 정리되며, 서비스가 직접 보관하던 발견 항목은 더 이상 조회할 수 없게 됩니다. 반면 CloudWatch Logs, Amazon S3, EventBridge 같은 다른 서비스로 이미 내보내 둔 데이터는 Security Hub와 별개로 남기 때문에, 필요한 기록은 비활성화 전에 미리 내보내 두어야 합니다.

즉 비활성화는 서비스 연결 역할과 집계 설정, 서비스 내부 발견 항목을 정리하는 일이고, 외부로 내보낸 로그와 객체는 별도 보존 정책을 따릅니다.

설정을 코드로 관리하기

CloudFormation·Terraform으로 같은 설정을 반복 적용하는 방법을 본다

리전과 계정이 늘어날수록 콘솔에서 손으로 표준을 켜는 방식은 누락되기 쉽고, 같은 설정을 다시 만들기도 어렵습니다. 이 문제를 줄이려면 활성화와 표준 지정을 코드로 적어 두고 반복 적용해야 합니다. 이는 인프라를 코드로 관리하는 방식(infrastructure as code)의 한 사례로, 보안 설정도 같은 원칙으로 다룰 수 있습니다.

아파트를 지을 때 말로 설명하는 대신 설계 도면을 남기는 것과 같습니다. 도면이 있으면 같은 건물을 다른 부지에도 똑같이 지을 수 있고, 어디가 바뀌었는지도 한눈에 보입니다.

AWS CloudFormation에서는 AWS::SecurityHub::Hub 리소스로 활성화를, AWS::SecurityHub::Standard 리소스로 어떤 표준을 켤지 적습니다. Terraform에서는 aws_securityhub_account와 aws_securityhub_standards_subscription 리소스로 같은 일을 하며, 이 코드를 여러 계정과 리전에 그대로 적용하면 설정이 사람 손을 거치지 않고 반복됩니다.

정리하면 설정을 코드로 관리한다는 것은 Security Hub의 활성화와 표준 선택을 CloudFormation이나 Terraform 같은 도구의 리소스로 선언해, 같은 구성을 재현 가능하게 유지하는 일입니다.

회사에 신입 사원이 들어왔을 때 온보딩 체크리스트를 빠뜨리는 상황과 비슷합니다. 출입증은 만들었는데 메일 계정을 열지 않았거나, 교육은 받았는데 결재 권한을 주지 않은 식입니다. Security Hub에서는 서비스 연결 역할을 만들 권한이 없어 활성화가 중간에 멈추는 경우, 여러 리전을 쓰면서 특정 리전에서만 표준을 켜 그 리전의 리소스가 평가되지 않는 경우, 그리고 표준만 켜고 예외 처리와 알림 대상을 정하지 않아 같은 경고가 쏟아지는 경우가 대표적입니다.

정리하면 초기 설정의 흔한 실수는 IAM 권한 부족, 리전 누락, 알림과 예외 설정 미비이며, 이 세 가지를 체크리스트로 확인하는 것만으로도 대부분의 문제를 줄일 수 있습니다.

4부. 표준과 컨트롤031

보안 표준(Standard)이란

표준이 여러 컨트롤을 묶은 단위라는 점을 이해한다

여러 팀이 각자 자기 방식대로 보안 점검을 하면 어떤 팀은 계정 비밀번호 정책을 보고 어떤 팀은 네트워크만 보는 식으로 기준이 제각각이 되어, 회사 전체의 안전 수준을 가늠할 수 없게 됩니다. 게다가 규제 기관이나 고객이 보안을 어떻게 확인하고 있느냐고 물을 때 보여 줄 공통된 답이 없어 매번 새로 설명해야 하는 곤란도 생깁니다. 이 문제를 풀기 위해 나온 것이 보안 표준(Standard)으로, 여러 개의 개별 점검 항목을 목적에 맞게 한 묶음으로 정리해 둔 단위입니다.

종합 건강검진 패키지를 떠올리면 이해가 쉽습니다. 표준은 기본 검진이나 정밀 검진처럼 목적별로 검사 항목을 묶어 내놓는 상품이고, 그 안의 개별 검사가 컨트롤(Control)입니다. 패키지마다 어떤 검사를 포함할지 정해져 있듯이 표준도 다루는 범위와 항목 수가 저마다 다르게 정의되며, 검진 결과가 항목별 정상과 주의로 나뉘어 종합 점수로 정리되듯 표준은 소속 항목들의 통과 여부를 모아 현재 상태를 한눈에 보여 줍니다.

그래서 같은 회사라도 결제 관련 표준과 정부 기준 표준처럼 목적이 다른 표준을 함께 적용할 수 있습니다. 결국 보안 표준은 개별 점검 항목을 목적별로 묶어 관리하는 상위 단위이며, 항목 하나하나가 아니라 묶음 전체의 상태를 판단하는 틀이라고 정리할 수 있습니다.

AWS Foundational Security Best Practices

AWS가 제공하는 기본 표준의 성격과 다루는 범위를 본다

AWS에 시스템을 올린 회사가 우리 계정이 최소한의 안전은 갖췄는지 확인하려 해도 무엇부터 봐야 하는지 알기 어렵습니다. 점검 항목을 직접 골라 만들려면 시간이 오래 걸리고, 빠뜨린 항목이 있어도 그 사실조차 알기 어렵습니다.

그래서 AWS는 자기 환경에 맞춰 미리 골라 둔 기본 점검 묶음인 AWS Foundational Security Best Practices(기본 보안 모범 사례)를 표준으로 제공합니다.

새 아파트에 입주할 때 기본으로 딸려 오는 소방과 전기 안전 점검 목록에 비유할 수 있습니다. 입주자가 따로 전문 업체를 부르지 않아도 집주인이 미리 정해 둔 항목으로 집의 기본 상태를 확인하듯, AWS가 고른 항목으로 계정의 기본 상태를 확인합니다.

이 표준은 루트 계정 보호, 암호화 설정, 로그 기록, 네트워크 노출처럼 대부분의 계정에 공통으로 해당하는 영역을 다룹니다. 다만 서비스와 기능이 계속 늘어나므로 항목 구성은 시점에 따라 달라질 수 있습니다.

결국 이 표준은 AWS가 자기 환경 기준으로 미리 묶어 둔 최소한의 기본 점검 세트라고 이해하면 됩니다.

CIS AWS Foundations Benchmark

CIS 벤치마크가 AWS에서 무엇을 요구하는지 설명한다

AWS 계정을 처음 만든 사람은 루트 계정 보호나 로그 설정 같은 기초 항목을 어디까지 해야 하는지 감이 잡히지 않습니다. 업계에서 통용되는 기준 없이 회사 나름대로 정하면 외부 감사나 고객 검토 때 그 판단의 근거를 대기 어렵습니다.

이때 참고하는 것이 CIS(Center for Internet Security)가 만든 CIS AWS Foundations Benchmark(AWS 기초 벤치마크)입니다.

건물 안전 진단 협회가 만든 표준 진단표에 비유할 수 있습니다. 협회가 업계 전문가들의 합의로 진단 항목과 판정 기준을 정해 두면 건물주는 그 표에 따라 자기 건물을 점검하고 결과를 외부에 보여 줄 수 있습니다.

이 벤치마크도 계정의 신원 관리, 로그 기록, 모니터링, 네트워킹 같은 기초 영역을 항목별로 정의하고, 난이도에 따라 기본 수준과 심화 수준으로 나눠 제시합니다. 실제 항목 번호와 내용은 벤치마크 버전에 따라 달라질 수 있으므로 적용 전에 해당 버전을 확인해야 합니다.

결국 CIS 벤치마크는 민간 전문가 합의로 만들어진 AWS 계정 기초 점검표이며, Security Hub에서는 이를 표준으로 불러와 자동 점검에 사용합니다.

PCI DSS 표준

카드 결제 규제를 점검 항목으로 옮긴 표준의 특징을 다룬다

카드 결제를 받는 회사는 카드번호와 같은 결제 정보를 잘못 다루면 고객 피해와 함께 거래 중단이라는 큰 손실을 입습니다. 그런데 어떤 보호 조치를 어느 수준까지 갖춰야 하는지는 회사마다 판단이 달라, 카드사 입장에서는 상대 회사의 안전 수준을 신뢰하기 어렵습니다.

이 문제를 해결하려고 카드 업계가 만든 공통 요구사항이 PCI DSS(Payment Card Industry Data Security Standard)입니다.

택배사가 정한 취급 주의 상품의 포장 규격서에 비유할 수 있습니다. 깨지기 쉬운 물건을 보낼 때 정해진 완충재와 겉포장 규격을 지켜야 접수가 되듯, 카드 정보를 다루는 회사도 정해진 보호 조치를 갖춰야 결제 업무를 계속할 수 있습니다.

이 표준은 카드 정보의 저장과 전송, 접근을 어떻게 제한하고 기록해야 하는지를 요구사항 묶음으로 제시하며, 회사 규모나 거래량에 따라 적용 수준이 달라집니다. 준수 여부는 정해진 절차에 따른 평가로 확인하며, 통과하지 못하면 카드 거래를 처리하는 데 제약을 받습니다.

결국 PCI DSS는 카드 정보를 안전하게 다루기 위해 업계가 합의한 보호 요구사항의 묶음이라고 정리할 수 있습니다.

NIST SP 800-53 표준

미국 정부 기준이 AWS 점검 항목에 어떻게 매핑되었는지 본다

미국 정부 기관과 거래하려는 회사는 정부가 요구하는 보안 기준을 따라야 하지만, 그 기준이 방대해 어디서부터 손대야 할지 막막합니다. 특히 클라우드에서는 정부 문서의 조항과 실제 클라우드 설정이 어떻게 대응하는지 스스로 해석해야 하는 부담이 있습니다.

이때 기준이 되는 문서가 NIST(National Institute of Standards and Technology)가 만든 NIST SP 800-53입니다.

정부가 정한 건축법과, 그 법조문을 실제 시공 항목으로 옮긴 현장 체크리스트의 관계에 비유할 수 있습니다. 건축법이 화재 시 대피가 가능해야 한다고 규정하면 시공사는 그 조항을 계단 폭이나 비상구 위치 같은 구체적 시공 항목으로 바꿔 확인합니다.

이와 같이 SP 800-53은 접근 통제, 감사 기록, 사고 대응 같은 통제 항목을 번호와 함께 정의하고, AWS는 그 항목들을 자기 서비스의 설정 점검 항목에 대응시켜 매핑합니다. 그래서 Security Hub에서 이 표준을 켜면 정부 기준의 어떤 조항이 어떤 AWS 설정과 연결되는지 확인할 수 있습니다.

결국 NIST SP 800-53은 미국 정부의 보안 요구를 정리한 문서이며, AWS 환경에서는 그 요구가 클라우드 설정 점검 항목으로 번역되어 적용됩니다.

4부. 표준과 컨트롤036

컨트롤(Control)이란

표준 안의 개별 점검 항목이 어떤 구조로 정의되는지 이해한다

보안을 점검한다고만 하면 무엇을 어떻게 확인해야 하는지가 모호해, 담당자마다 다른 것을 보고 다른 결론을 냅니다. 점검 결과가 문제 있음이라는 말로만 끝나면 무엇을 고쳐야 하는지도 알 수 없습니다.

그래서 표준 안에는 컨트롤(Control)이라는 개별 점검 항목이 하나의 구조를 갖춘 형태로 정의됩니다.

아파트 소방 점검 항목 하나를 떠올리면 그 구조가 그대로 보입니다. 소화기 압력계 바늘이 녹색 구간에 있는가라는 항목에는 무엇을 볼지, 어떤 상태면 통과인지, 어떻게 확인할지, 어긋났을 때 무엇을 할지가 함께 적혀 있습니다.

컨트롤도 마찬가지로 식별자와 설명, 점검 대상과 판정 기준, 심각도, 수정 안내를 함께 담습니다. 이 구조 덕분에 점검은 사람마다 달라지지 않고 같은 기준으로 반복될 수 있으며, 실패한 항목은 심각도에 따라 우선순위를 정해 고칠 수 있습니다.

결국 컨트롤은 표준을 이루는 최소 단위이자, 무엇을 어떤 기준으로 확인하고 어떻게 고칠지까지 담은 점검 항목이라고 정리할 수 있습니다.

4부. 표준과 컨트롤037

컨트롤 파라미터

항목마다 기준 값을 조정해 우리 환경에 맞추는 방법을 익힌다

보안 점검을 켜 두었는데도 경고가 하루에 수백 건씩 쏟아지면 담당자는 진짜 위험한 항목을 골라내지 못하고 결국 알림 전체를 꺼 버리게 됩니다. AWS Security Hub의 컨트롤 파라미터(control parameter)는 이런 곤란을 줄이기 위해 점검 항목마다 판정 기준 값을 우리 환경에 맞게 조정하는 기능입니다.

아파트 관리사무소가 오래 세워 둔 자전거를 정리한다고 할 때, 규칙 자체는 일정 기간 넘게 움직이지 않은 자전거를 치운다로 정해져 있고 실제 판단을 가르는 것은 그 일정 기간이 몇 개월이냐 하는 숫자입니다. 이때 규칙이 컨트롤이고 그 규칙에 들어가는 숫자가 파라미터(parameter)이며, 자전거가 많은 단지는 6개월, 적은 단지는 3개월로 숫자를 바꾸는 일이 파라미터 조정입니다.

숫자를 너무 짧게 잡으면 멀쩡한 자전거까지 정리 대상으로 올라와 민원이 쏟아지고, 너무 길게 잡으면 창고가 꽉 차서 규칙이 있어도 아무것도 치우지 못합니다. 그래서 관리사무소는 우리 단지의 자전거 대수와 주차 공간을 먼저 보고, 정리 대상이 손에 꼽히는 정도가 되는 숫자를 골라 규칙에 넣습니다.

실제로는 컨트롤마다 미리 정해진 기본값이 있고, 그 값을 우리 계정의 규모와 운영 방식에 맞춰 바꾸면 같은 점검 항목이 우리 환경에서는 훨씬 현실적인 결과를 내놓습니다. 파라미터는 보안을 느슨하게 푸는 장치가 아니라, 점검이 실제로 작동하도록 기준을 맞추는 조정 손잡이입니다.

4부. 표준과 컨트롤038

컨트롤 활성화와 비활성화

필요 없는 항목을 끄는 기준과 주의할 점을 정리한다

점검 항목을 전부 켜 두면 우리 회사에 해당하지도 않는 항목이 매일 실패로 잡혀 보고서가 실패 목록으로만 가득 차고, 그 사이 진짜 손봐야 할 항목은 눈에 띄지 않게 됩니다. AWS Security Hub에서 컨트롤을 켜고 끄는 일, 즉 활성화와 비활성화(enable/disable)는 이렇게 소음이 된 항목을 우리 환경 기준으로 걸러내는 작업입니다.

회사가 직원 건강검진을 단체로 예약할 때를 생각해 보면, 검진 센터가 제시하는 항목은 수십 가지지만 회사가 계약한 묶음과 직원 연령대에 따라 실제로 받는 항목은 그보다 훨씬 적습니다. 이때 검진 항목 하나하나가 컨트롤이고, 이번 검진에 넣을 항목을 체크하는 일이 활성화, 빼는 일이 비활성화입니다.

검진 센터의 전체 목록을 그대로 다 받으면 비용도 시간도 늘고 결과지에서 쓸모 있는 수치를 찾기 어려워집니다. 다만 빼는 판단에는 주의가 필요해서, 우리가 쓰지 않는 서비스라서 뺀 항목과 결과가 나쁘게 나올까 봐 뺀 항목은 겉으로 똑같이 보이지만 후자는 실제 위험을 가리는 일이 됩니다.

실제로는 컨트롤을 끄면 그 항목이 앞으로 평가되지 않고 점수에도 반영되지 않으므로, 끈 이유를 남겨 두어야 나중에 왜 이 항목이 꺼져 있는지 설명할 수 있습니다. 활성화와 비활성화는 점검 목록을 우리 환경에 맞게 줄이는 관리 행위이고, 무엇을 왜 껐는지 기록으로 남기는 것이 그 행위의 절반입니다.

4부. 표준과 컨트롤039

사용자 지정 표준

우리 조직에만 필요한 점검 묶음을 직접 만드는 방법을 다룬다

Security Hub가 기본으로 제공하는 표준은 여러 규제와 모범 사례를 폭넓게 담고 있어서, 우리 회사에는 해당하지 않는 항목이 절반 넘게 섞여 있고 정작 우리 업무에서 중요한 항목은 빠져 있기도 합니다. 사용자 지정 표준(custom standard)은 이런 기본 묶음 대신 우리 조직에 필요한 컨트롤만 골라 직접 만드는 점검 묶음입니다.

회사가 신입 교육 과정을 짤 때를 생각해 보면, 교육 본부가 만든 전사 공통 과정은 모든 부서를 아우르려다 보니 영업 부서에도 개발 보안 교육이, 개발 부서에도 영업 윤리 교육이 들어갑니다. 이때 개별 교육 과목이 컨트롤이고, 우리 부서에 필요한 과목만 골라 묶은 하나의 교육 과정표가 사용자 지정 표준입니다.

과정표를 한 번 만들어 두면 신입이 들어올 때마다 어떤 과목을 들어야 하는지 매번 새로 정하지 않아도 됩니다. 실제로는 기본 제공 표준을 복사해 출발점으로 삼고 우리에게 맞지 않는 항목을 빼거나 필요한 항목을 더하는 식으로 만들며, 같은 컨트롤이 여러 표준에 동시에 들어갈 수도 있습니다.

사용자 지정 표준은 기본 표준을 덮어쓰는 것이 아니라 별도로 추가되는 것이므로, 규제 대응용과 사내 기준용을 따로 두고 각각의 점수 변화를 따로 볼 수 있습니다. 즉 사용자 지정 표준은 남이 정해 둔 점검 목록을 그대로 받는 대신, 우리 조직의 위험 기준으로 목록을 다시 짜는 일입니다.

표준 버전 관리

표준이 개정될 때 생기는 변화와 대응 방법을 이해한다

어느 날 갑자기 보안 점수가 몇 점 떨어지고 처음 보는 실패 항목이 보고서에 올라오면, 담당자는 우리 쪽에서 무엇이 바뀐 건지부터 찾아야 하고 원인을 못 찾으면 엉뚱한 곳을 손보게 됩니다. 표준 버전 관리(version management)는 이렇게 점검 기준 자체가 개정될 때 무엇이 달라졌는지 확인하고 대응하는 절차입니다.

회사 사규집이 개정되면 개정판 번호가 붙고, 기존 조항이 문구만 다듬어지기도 하고 통째로 삭제되거나 새 조항이 생기기도 합니다. 이때 사규집이 표준, 개정판 번호가 버전, 조항 하나하나가 컨트롤이며, 개정판이 나왔다고 예전 판으로 작성된 문서가 곧바로 무효가 되지는 않습니다. 개정 내용을 확인하지 않고 새 판으로 바로 넘어가면 새로 생긴 조항 때문에 갑자기 미준수로 잡히고, 반대로 계속 예전 판에 머물면 더 이상 점검되지 않는 조항이 생깁니다. 실제로는 표준을 새 버전으로 올릴지 한동안 이전 버전을 유지할지 선택할 수 있는 경우가 많고, 새 버전에서 빠지거나 추가된 컨트롤 목록을 먼저 확인한 뒤 전환 시점을 정합니다.

버전이 올라갈 때 점수 기준도 함께 달라질 수 있으므로, 전환 전후의 점수를 같은 잣대로 비교해서는 안 됩니다. 표준 버전 관리는 개정판을 그냥 따라가는 일이 아니라, 무엇이 왜 바뀌었는지 확인하고 우리 환경의 전환 시점을 우리가 정하는 일입니다.

컨트롤 평가 방식

Config 규칙에 기대는 평가와 자체 점검이 어떻게 다른지 비교한다

같은 항목인데 어떤 날은 통과로, 어떤 날은 실패로 표시되고 그 이유를 설명하지 못하면 점검 결과 전체를 믿기 어려워집니다. 컨트롤 평가 방식은 각 항목의 통과 여부를 무엇을 근거로 판정하는지에 관한 것으로, 크게 AWS Config 규칙에 기대는 방식과 자체 점검 방식으로 나뉩니다.

회사에서 비품 재고를 확인할 때를 생각해 보면, 장부와 전산 기록을 자동으로 맞춰 보는 방법과 담당자가 창고를 돌며 직접 세는 방법이 있습니다. 이때 전산 기록을 근거로 자동 판정하는 것이 Config 규칙 기반 평가이고, 담당자가 직접 확인해 결과를 넣는 것이 자체 점검입니다.

자동 대조는 사람이 개입하지 않아도 주기적으로 반복되고 기록이 남지만, 장부에 잡히지 않는 물건은 아예 판정 대상이 되지 못합니다. 직접 세기는 장부에 없는 것까지 볼 수 있지만 사람이 돌아야 하고 판단이 사람마다 달라질 수 있습니다.

실제로는 많은 컨트롤이 뒤에서 Config 규칙 하나에 대응되어 그 규칙의 판정 결과를 그대로 받아 쓰고, 그런 규칙이 없는 항목은 별도의 자체 점검 절차로 확인합니다. 그래서 같은 실패라도 어느 방식으로 판정된 것인지에 따라 고치는 방법과 신뢰도가 달라집니다.

자동 점검 주기

컨트롤이 언제 다시 평가되는지와 결과가 늦게 오는 이유를 본다

설정을 고쳤는데도 점검 결과가 한참 동안 그대로여서 고친 것이 반영되지 않았다고 오해하거나, 반대로 아직 고치지 않은 항목이 잠시 통과로 보여 안심하게 되는 일이 생깁니다. 자동 점검 주기(re-evaluation)는 컨트롤이 언제 다시 평가되고 그 결과가 언제 반영되는지를 다루는 문제입니다.

회사 건물을 경비원이 두 시간마다 한 바퀴 도는 순찰에 비유하면, 순찰은 정해진 시각에만 이뤄지고 그 사이에 생긴 변화는 다음 순찰 때에야 확인됩니다. 이때 순찰을 도는 주기가 평가 주기이고, 순찰과 순찰 사이에 문을 고쳐 잠근 일은 다음 바퀴가 돌 때에야 기록에 남습니다.

그래서 방금 잠근 문을 두고 아직 열려 있다는 기록이 남아 있을 수 있고, 이는 기록이 틀린 것이 아니라 아직 확인하지 않은 것입니다. 반대로 어떤 항목은 설정이 바뀌는 순간 바로 평가가 다시 돌기도 해서, 모든 컨트롤이 같은 주기로 움직인다고 단정할 수는 없습니다.

실제로는 각 컨트롤이 어떤 방식으로 평가되는지에 따라 갱신 시점이 다르고, 결과가 늦게 보이는 것을 오류로 오인하지 않으려면 평가 근거와 마지막 갱신 시점을 함께 확인해야 합니다. 자동 점검 주기는 점검이 실시간 감시가 아니라 정해진 리듬으로 도는 확인이라는 점을 전제로 결과를 읽는 것입니다.

통과·실패·알 수 없음

세 가지 상태가 각각 무엇을 뜻하는지 구분한다

수백 개의 보안 점검 항목을 한 장의 표에 모아 놓고 합격과 불합격 두 가지로만 적는다면, 담당자가 아직 들여다보지도 못한 항목이 합격으로 둔갑하는 순간이 생깁니다. 그 빈자리를 메우려고 AWS Security Hub는 컨트롤(control, 개별 보안 점검 규칙)의 결과를 통과(PASSED), 실패(FAILED), 알 수 없음(NOT_AVAILABLE)이라는 세 가지 상태로 나누어 기록합니다.

아파트 소방 점검에 비유하면 이해가 쉽습니다. 점검표에는 모든 세대의 소화기와 비상등이 적혀 있고, 점검원이 문을 열어 확인해 기준을 넘겼으면 통과 도장을, 기준에 못 미쳤으면 실패 도장을 찍습니다. 그런데 세대주가 장기 출장 중이라 문을 열지 못한 집은 통과도 실패도 아닌 채로 남는데, 이것이 바로 알 수 없음입니다.

이 상태는 좋고 나쁨을 판정한 결과가 아니라 판정 자체를 하지 못했다는 표시이므로, 관리사무소는 그 집을 합격으로 세지 않고 다시 방문할 대상으로 따로 뽑아야 합니다.

정리하면 통과는 점검이 실제로 수행되어 기준을 만족했다는 뜻이고, 실패는 수행 결과가 기준을 벗어났다는 뜻이며, 알 수 없음은 근거 자료가 없어 판정이 불가능했다는 뜻입니다. 따라서 안전한 운영은 통과의 개수를 세는 일이 아니라 알 수 없음을 실패에 준해 관리하는 일에서 시작합니다.

알 수 없음(No data) 해결하기

데이터가 없다고 나올 때 원인을 찾는 순서를 따라간다

점검 결과 화면에 알 수 없음(No data)이 수십 줄 늘어서면 대부분은 무시하고 넘어가지만, 그중에는 실제로 위험한 리소스가 점검조차 받지 못하고 있는 경우가 섞여 있습니다. 그래서 데이터가 없다는 표시를 만났을 때는 추측하지 말고 원인을 좁혀 가는 정해진 순서를 따라야 합니다.

학교 출석부를 떠올려 보면 순서가 자연스럽습니다. 담임이 공란을 발견하면 먼저 그 자리에 학생이 원래 있는지 명단을 확인하고, 학생은 있는데 명단에서 빠졌는지, 명단에는 있는데 담임에게 출석부가 전달되지 않았는지, 마지막으로 학교 자체가 그날 문을 열었는지를 차례로 봅니다.

보안 점검도 같아서 점검 대상 리소스가 실제로 존재하는지, 그 리소스가 Security Hub가 수집하는 범위에 들어와 있는지, 점검에 필요한 읽기 권한이 설정되어 있는지, 해당 리전(region)이 Security Hub에서 활성화되어 있는지를 차례로 확인하면 원인의 대부분이 걸러집니다. 이 순서를 지키는 이유는 앞 단계가 해결되지 않으면 뒤 단계의 확인이 의미가 없기 때문입니다.

정리하면 알 수 없음은 점검이 실패한 것이 아니라 점검의 출발 조건이 갖춰지지 않았다는 신호이며, 리소스 존재 여부에서 시작해 수집 범위, 권한, 리전 활성화 순으로 확인하는 것이 가장 빠른 해결 경로입니다.

건강검진 결과지를 떠올리면 읽는 요령이 보입니다. 결과지 맨 위에는 검사 항목의 이름과 식별자(control ID)가 있고, 옆에는 이 항목이 얼마나 위중한지를 나타내는 심각도(severity)가 적혀 있으며, 아래쪽에는 이상이 나온 사람의 명단과 각 사람의 수치가 붙습니다.

보안 화면도 똑같아서 컨트롤 이름과 식별자로 무엇을 점검했는지 확인하고, 심각도로 고칠 순서를 정하고, 실패한 리소스 목록으로 실제 대상이 몇 개인지 세고, 함께 제공되는 설명과 해결 안내로 무엇을 바꿔야 하는지 파악합니다. 여기에 마지막으로 상태가 바뀐 시각과 어떤 보안 표준(benchmark)에 속한 항목인지를 보태면, 새로 생긴 문제인지 오래 방치된 문제인지가 드러납니다.

정리하면 컨트롤 상세 화면은 무엇을, 얼마나 위중하게, 어디에서, 어떻게 고쳐야 하는지를 순서대로 읽도록 배치된 판단 도구이며, 심각도와 리소스 수, 최근 변경 시각을 함께 보는 것이 실제 조치 순서를 정하는 핵심입니다.

리소스 단위 결과

같은 컨트롤이 리소스마다 다르게 나오는 이유를 이해한다

컨트롤 하나가 실패로 표시되었는데 같은 종류의 리소스 중에는 통과한 것도 있어서, 대체 무엇이 문제인지 헷갈리는 상황이 자주 생깁니다. Security Hub는 컨트롤 결과를 리소스 단위로 따로 기록하기 때문에, 같은 컨트롤이라도 리소스마다 다른 결과가 나오는 것이 정상입니다.

아파트 소방 점검에 다시 비유하면 분명해집니다. 점검 기준은 건물 전체에 하나로 공지되지만, 실제 도장은 세대마다 따로 찍히고 어떤 집은 소화기 유효기간이 지나 실패하고 어떤 집은 통과합니다. 기준이 같다고 결과가 같아지지 않는 이유는 세대마다 상태가 다르기 때문입니다.

보안 점검도 마찬가지로, 리소스마다 설정값이 다르고 생성 시점과 버전이 다르며, 어떤 리소스는 그 컨트롤의 점검 대상 유형에 포함되고 어떤 리소스는 아예 대상이 아니어서 결과가 갈립니다. 그래서 같은 컨트롤에서 통과한 리소스와 실패한 리소스를 나란히 견주어 보면 무엇이 다른지가 가장 빠르게 드러납니다.

정리하면 컨트롤은 기준을 정의하는 규칙이고 결과는 리소스마다 매겨지는 판정이므로, 실패를 해결할 때는 컨트롤 전체가 아니라 실패한 리소스 목록을 보고 개별 리소스의 설정 차이를 확인해야 합니다.

컨트롤 예외 처리

정당한 사유가 있는 리소스를 예외로 두는 방법을 다룬다

보안 점검을 운영하다 보면 규정상 실패로 잡히지만 실제로는 고칠 수 없거나 고칠 이유가 없는 리소스가 반드시 나옵니다. 이런 건을 매번 예외로 두는 대신 사유와 기한을 남겨 관리하지 않으면, 진짜 실패가 예외 더미에 묻혀 버립니다.

회사 지출 결재를 떠올려 보면 요령이 같습니다. 영수증이 없는 지출은 원칙적으로 반려지만, 부득이한 사유가 있으면 사유서와 승인자, 유효 기간을 붙여 예외 승인을 받습니다.

보안 점검도 같은 방식으로, 리소스마다 예외 사유와 승인한 사람, 다시 검토할 시점을 기록해 두고 그 범위에 한해 실패를 조치 대상에서 빼 둡니다. 이때 중요한 것은 예외가 사라지는 조건인데, 리소스가 삭제되거나 서비스가 종료되는 등 사유가 없어지면 예외도 함께 해제되어 다시 점검 대상으로 돌아와야 합니다. 어떤 방법으로 예외를 남길 수 있는지는 Security Hub의 기능과 워크플로 상태(workflow status) 설정에 따라 달라질 수 있으므로, 도입 전에 현재 사용 중인 환경에서 지원되는 방식을 확인하는 것이 좋습니다.

정리하면 컨트롤 예외 처리는 실패를 지우는 일이 아니라 사유·승인자·만료 조건을 갖춘 기록으로 실패를 잠시 보류하는 일이며, 예외 목록을 정기적으로 되돌아보는 절차가 함께 있어야 의미가 있습니다.

억제 규칙(Suppression)

반복되는 이슈를 자동으로 걸러내는 규칙을 만든다

같은 실패 알림이 매일 수백 건씩 올라오면 운영자는 곧 알림을 읽지 않게 되고, 그 사이에 진짜 사고가 섞여 들어갑니다. 억제 규칙(suppression rule)은 이런 반복 알림을 조건에 따라 자동으로 걸러 내어 사람이 봐야 할 것만 남기는 장치입니다.

택배 집하장의 분류기를 떠올리면 구조가 보입니다. 분류기는 송장의 주소와 크기, 보내는 곳 같은 조건을 보고 일반 택배와 반품 택배를 자동으로 갈라 각기 다른 벨트로 보내며, 조건에 맞지 않는 물건만 사람 손으로 넘깁니다.

억제 규칙도 같아서 어떤 컨트롤에서, 어떤 심각도로, 어떤 리소스에서 발생한 결과인지를 조건으로 적어 두면 그 조건에 맞는 결과가 자동으로 걸러집니다. 이때 걸러진 결과는 없어지는 것이 아니라 억제된 상태로 남아 나중에 몇 건이 걸러졌는지 확인할 수 있어야 하며, 조건을 너무 넓게 잡으면 진짜 문제까지 함께 사라지므로 컨트롤 식별자와 리소스 식별자를 좁게 지정하는 편이 안전합니다.

정리하면 억제 규칙은 반복되는 보안 결과를 조건으로 자동 분류해 사람이 판단할 대상을 줄이는 필터이며, 걸러진 양을 계속 관찰하고 조건을 좁게 유지하는 것이 운영의 핵심입니다.

컨트롤 기준 조정

Config 규칙을 바꿔 판단 기준을 우리 환경에 맞춘다

보안 점검 도구를 처음 도입하면 대부분 기본 규칙을 그대로 켜 두고 시작합니다. 그런데 그 기본값은 우리 회사 사정을 전혀 모르는 남의 잣대라서, 이미 승인된 예외까지 위반으로 쏟아지고 진짜 문제는 그 속에 묻힙니다. 이때 필요한 것이 AWS Config 규칙의 판단 기준을 우리 환경에 맞게 다시 맞추는 작업, 즉 컨트롤 기준 조정(control tuning)입니다.

아파트 관리 규정을 떠올려 보면, 관리사무소가 배포한 표준 규정집이 기본 규칙이고 우리 단지의 주차 구역과 분리수거 요일은 도면과 생활 패턴에 맞게 다시 정해야 합니다. 규칙의 임계값이나 대상 범위를 단지 사정에 맞춰 고치는 것이 파라미터 조정이고, 특정 표식이 붙은 자원만 평가하게 하는 것이 범위 조정입니다. 그리고 규정을 고칠 때는 왜 고쳤는지 입주자 대표회의 승인 기록처럼 근거를 남겨야 나중에 감사 자리에서 설명할 수 있습니다.

결국 컨트롤 기준 조정은 Config 규칙이 준수와 위반을 가르는 기준, 즉 파라미터와 평가 대상 범위를 우리 조직의 승인된 예외와 운영 방식에 맞춰 다시 설정하고 그 변경 근거를 기록으로 남기는 일입니다. 기본값은 출발점일 뿐이고, 우리 환경을 아는 사람이 손을 대야 규칙이 비로소 쓸모 있는 경고가 됩니다.

오탐과 미탐 다루기

잘못된 경고를 줄이는 현실적인 접근을 정리한다

경고가 하루에 수백 건씩 올라오면 사람은 곧 그것을 읽지 않게 됩니다. 진짜 침해 시도가 그 속에 섞여 있어도 무시하는 습관이 먼저 몸에 배는 것이 가장 위험한 결과입니다.

이 문제를 다루는 개념이 오탐(false positive)과 미탐(false negative)이고, 줄이는 작업은 화재경보기 관리와 비슷합니다. 요리 연기에 경보가 울리는 것이 오탐이고, 센서에 먼지가 끼어 불이 나도 울리지 않는 것이 미탐입니다. 집집마다 경보기를 주방에서 조금 떨어뜨리고, 감도를 조절하고, 정기적으로 먼지를 털어 주는 것처럼 보안 규칙도 위치와 감도를 환경에 맞추어 조정해야 합니다.

다만 경보가 시끄럽다고 센서를 꺼 버리면 미탐이 늘어나므로, 경고 억제(suppression)는 사유와 기한을 적어 예외로 등록하고 정기적으로 다시 검토해야 합니다.

결국 오탐과 미탐을 다루는 일은 규칙의 심각도와 예외, 억제 조건을 조정하면서도 경고를 끄는 것과 예외를 인정하는 것을 구분하고, 그 판단의 이력을 남겨 지속적으로 다듬는 과정입니다.

이슈(Finding)란

보안 이슈 하나가 어떤 정보 묶음인지 이해한다

보안 도구가 "위험합니다"라는 한 줄만 알려 주면 담당자는 어디서 무엇이 문제인지부터 다시 찾아야 합니다. 그 한 줄이 실제로는 여러 정보를 담은 묶음이어야 대응이 시작되는데, 그 묶음을 가리키는 것이 이슈(Finding)입니다.

택배 송장을 떠올리면 이해가 쉽습니다. 송장 한 장에는 보낸 사람, 받는 사람, 물건, 무게, 접수 시각이 함께 적혀 있어 그것 하나로 배송 전체를 추적합니다.

이슈도 마찬가지로 어떤 자원에서, 어떤 규칙이나 탐지에 걸렸고, 심각도는 어느 정도이며, 언제 발견되었고, 무엇을 하라고 권고하는지가 한 묶음으로 담깁니다. 그래서 같은 자원에 같은 문제가 반복되면 식별자로 묶어 하나의 이슈로 추적하고, 상태를 바꾸며 처리 경과를 남길 수 있습니다.

결국 이슈는 탐지된 보안 문제 하나에 대한 식별자와 대상 자원, 심각도, 발견 시각, 권장 조치를 담은 정보 묶음으로, 경고 한 줄이 아니라 추적 가능한 사건 기록입니다.

ASFF 형식

모든 서비스가 맞춰 보내는 공통 JSON 규격을 설명한다

서로 다른 보안 서비스가 저마다 다른 형식으로 결과를 보고하면, 그것을 한 화면에서 비교하고 집계하기가 사실상 불가능합니다. 그래서 AWS는 모든 서비스가 같은 모양으로 이슈를 보내도록 공통 규격을 정해 두었고, 그것이 ASFF(AWS Security Finding Format)입니다.

회사 공용 결재 양식과 같습니다. 부서마다 자유 형식으로 기안하면 결재선이 읽을 수 없으니, 문서 번호와 제목, 작성자, 금액, 사유 칸이 정해진 양식을 쓰게 하는 것입니다.

ASFF는 JSON(JavaScript Object Notation) 형식의 스키마로, 어떤 제품이 만들었는지, 어떤 자원인지, 심각도는 어떤지 같은 칸의 이름과 생김새를 미리 정해 둡니다. 필수 칸과 선택 칸이 나뉘어 있어 서비스는 최소한의 공통 정보를 반드시 채우고, 자기 제품에만 있는 정보는 정해진 여유 칸에 덧붙입니다.

결국 ASFF는 서로 다른 보안 서비스의 결과를 하나의 JSON 규격으로 맞춰 주는 공통 언어이고, 그 덕분에 여러 제품의 이슈를 같은 화면에서 정렬하고 합산할 수 있습니다.

ASFF 필수 필드

Id·ProductArn·Resources처럼 반드시 있어야 하는 항목을 짚는다

규격이 정해져 있어도 필수 칸을 비워 보내면 그 이슈는 받는 쪽에서 제대로 처리되지 못합니다. 등기우편 봉투에 보내는 사람과 받는 사람, 우편번호가 빠지면 배송이 시작되지 않는 것과 같습니다.

ASFF의 필수 필드 가운데 Id는 이슈 하나를 가리키는 고유 식별자로, 같은 이슈를 갱신할 때도 이 값을 기준으로 찾습니다. ProductArn은 이 이슈를 만들어 보낸 제품이 무엇인지 가리키는 식별자이고, Resources는 문제가 발견된 자원의 종류와 식별자를 담습니다. 이 세 가지가 있어야 받는 쪽이 어느 제품이 어떤 자원에 대해 어떤 사건을 말하는지 파악할 수 있습니다.

이 밖에도 생성 시각과 갱신 시각, 심각도, 이슈 유형처럼 처리를 위해 사실상 함께 채워야 하는 항목들이 있어, 필수 필드는 규격을 통과하기 위한 최소 조건으로 이해하면 됩니다.

결국 ASFF 필수 필드는 Id, ProductArn, Resources처럼 이슈의 정체와 대상, 출처를 확정해 주는 항목이며, 이것이 빠지면 나머지 정보가 아무리 자세해도 이슈로 성립하지 않습니다.

심각도 필드

심각도가 숫자와 라벨로 어떻게 표현되는지 이해한다

같은 "높음"이라는 경고라도 어떤 제품은 7점, 어떤 제품은 80점으로 표현하면 순서를 매길 수가 없습니다. 그래서 ASFF는 심각도를 사람이 읽는 라벨과 비교 가능한 숫자, 두 가지로 함께 표현합니다.

병원 응급실의 중증도 분류와 비슷합니다. 의료진은 환자를 즉시 처치, 중증, 경증 같은 색 라벨로 나누고, 그 라벨 뒤에는 대기 순서를 정할 수 있는 점수가 따로 있습니다.

ASFF의 Severity 객체에서 Label은 INFORMATIONAL, LOW, MEDIUM, HIGH, CRITICAL 같은 등급 이름이고, Normalized는 0에서 100 사이의 숫자 값입니다. 라벨은 사람이 빠르게 읽고 판단하는 데 쓰이고, 숫자는 정렬과 집계, 추세 계산에 쓰이므로 둘이 함께 있어야 실무에서 쓸모가 있습니다.

다만 이 값은 각 탐지 규칙이나 제품이 매기는 것이라 같은 사건이라도 제품에 따라 다를 수 있으므로, 중요한 판단을 라벨만 보고 단정하지 않는 것이 좋습니다.

결국 심각도 필드는 등급 라벨과 0에서 100 사이의 정규화 숫자를 함께 담아, 사람의 판단과 기계의 정렬을 동시에 가능하게 하는 항목입니다.

리소스 식별자

어떤 리소스에 대한 이슈인지 가리키는 방법을 다룬다

보안 점검 도구가 하루에 수천 건의 경고를 쏟아내는데 그 경고가 어느 서버와 어느 저장소를 가리키는지 알 수 없다면, 담당자는 고칠 대상을 찾는 데만 반나절을 쓰게 됩니다. AWS Security Hub는 이런 혼란을 막기 위해 모든 점검 결과에 리소스 식별자(resource identifier)를 붙여, 문제가 발견된 대상 자체를 정확히 가리키도록 설계했습니다.

아파트 단지에서 관리사무소가 "누수 발생"이라는 쪽지를 붙일 때 "몇 동 몇 호"라는 표시가 없으면 아무도 고칠 곳을 찾지 못합니다.

Security Hub의 리소스 식별자는 이때의 동·호수에 해당하는 주소 역할을 하며, 리소스를 가리키는 고유 문자열인 ARN(Amazon Resource Name)과 리소스 종류(ResourceType), 소속 계정(AccountId), 리전(Region) 같은 항목으로 이루어집니다. 건물 주소가 도로명과 번지, 동, 호수로 나뉘어 있듯이 하나의 리소스를 여러 각도에서 겹겹이 표시해 두면 서로 다른 계정에 같은 이름의 저장소가 있어도 헷갈리지 않습니다.

덕분에 담당자는 경고 한 줄만 보고도 어느 계정의 어떤 자원으로 달려가야 하는지 즉시 판단할 수 있습니다.

정리하면 리소스 식별자는 점검 결과가 가리키는 대상의 주소 체계입니다. ARN과 리소스 종류, 계정, 리전을 묶어 하나의 리소스를 유일하게 지정하는 정보이며, Security Hub가 여러 계정의 점검 결과를 한곳에 모을 수 있는 바탕이 됩니다.

이슈 상태(Workflow Status)

새 이슈·조사 중·해결됨을 나눠 두는 이유를 설명한다

점검 결과가 수백 건 쌓였는데 어떤 것은 이미 고쳤고 어떤 것은 아직 아무도 보지 않았다면, 목록은 그냥 소음 덩어리가 됩니다. AWS Security Hub는 이 문제를 풀기 위해 이슈마다 작업 상태(Workflow Status)를 따로 두어, 조치가 어디까지 진행됐는지를 사람이 직접 표시하게 했습니다.

택배 물류창고를 떠올려 보면 이해가 쉽습니다. 물건마다 "입고됨", "배송 중", "배송 완료"라는 상태표가 붙어 있어야 창고 직원이 무엇을 먼저 처리할지 정할 수 있는데, Security Hub의 상태값도 같은 역할을 합니다.

새로 들어온 이슈는 새 이슈(NEW)로 표시되어 아직 손대지 않은 상태임을 알리고, 담당자가 확인해 조사 중(NOTIFIED)으로 바꾸면 다른 사람에게 "지금 살펴보는 중"이라는 신호가 됩니다. 조치가 끝나면 해결됨(RESOLVED)으로, 의도된 설정이라 굳이 고칠 필요가 없으면 억제됨(SUPPRESSED)으로 표시해 목록에서 사실상 걸러 냅니다.

결국 작업 상태는 이슈의 처리 진행을 나타내는 사람이 관리하는 표식입니다. 발견 자체를 뜻하는 기록 상태와 구분되며, 팀이 같은 목록을 보면서도 서로 다른 판단을 하지 않게 만드는 장치입니다.

이슈 수명주기

이슈가 생겨서 보관되고 사라지기까지의 흐름을 따라간다

이슈가 생기면 알림이 가고, 누군가 확인하고, 고쳐지고, 한참 뒤에는 조용히 사라지기까지 각 단계마다 다른 사람과 다른 도구가 관여합니다. 이 흐름을 정해 두지 않으면 해결된 이슈가 계속 목록에 남아 진짜 위험을 가리게 되므로, AWS Security Hub는 이슈의 수명주기(lifecycle)를 명시적으로 관리합니다.

병원 진료 기록에 비유하면 흐름이 잘 보입니다. 접수 단계에서 새 기록이 만들어지고, 진료과로 배정되어 검사가 진행되고, 치료가 끝나면 완료로 표시된 뒤 일정 기간 보관되었다가 폐기됩니다.

Security Hub에서도 점검 도구가 결과를 보내면 이슈가 새로 생성되어 NEW 상태로 들어오고, 알림과 함께 담당자에게 전달되며, 조사와 조치를 거쳐 RESOLVED로 바뀝니다. 해결된 이슈는 곧바로 지워지지 않고 보관(archive) 단계로 옮겨져 기록으로 남으며, 일정 기간이 지나면 자동으로 정리됩니다.

정리하면 이슈 수명주기는 생성, 알림, 조사, 해결, 보관으로 이어지는 일련의 단계입니다. 각 단계의 상태값과 보관 규칙 덕분에 지금 목록에 보이는 것이 처리 중인 문제인지 이미 끝난 기록인지 구분할 수 있습니다.

이슈 중복 제거

같은 문제가 여러 번 올라올 때 하나로 합치는 규칙을 본다

여러 계정과 여러 점검 도구가 같은 서버의 같은 설정 오류를 각자 보고하면, 목록에는 똑같은 문제가 수십 번 나타나 담당자는 실제 위험 건수를 가늠할 수 없게 됩니다. AWS Security Hub는 이렇게 겹쳐 들어오는 이슈를 하나로 합치는 중복 제거 규칙을 두어, 같은 문제는 같은 항목으로만 남게 했습니다.

아파트 관리사무소의 민원 접수대를 떠올려 보면 비슷합니다. 같은 세대에서 같은 누수를 여러 번 전화로 알려도 접수 담당자가 "그 건은 이미 접수됨"이라며 기존 접수 건에 내용을 덧붙이면, 장부에는 민원이 하나만 남고 처리 이력은 오히려 더 풍부해집니다.

Security Hub도 각 이슈에 고유한 식별자(Id)를 부여하고, 같은 점검 도구(ProductArn)가 같은 리소스에 대해 같은 문제를 다시 보내면 새 항목을 만들지 않고 기존 항목의 갱신 시각과 내용만 바꿉니다. 그래서 반복 보고는 중복 목록이 아니라 "이 문제가 아직도 있다"는 최신 정보가 됩니다.

결국 중복 제거는 식별자와 출처, 대상 리소스를 기준으로 같은 이슈를 하나로 묶는 규칙입니다. 덕분에 목록의 건수가 실제로 손봐야 할 문제의 수와 가까워지고, 반복되는 보고는 처리 우선순위를 정하는 근거로 쓰입니다.

이슈 보관 기간

이슈가 언제까지 남고 언제 정리되는지 이해한다

보안 이슈는 고친 뒤에도 "언제 발견되었고 언제 해결되었는지"를 증명해야 할 때가 많지만, 아무리 오래된 기록까지 모두 쌓아 두면 저장 비용과 목록의 혼잡이 함께 커집니다. AWS Security Hub는 이 균형을 잡기 위해 이슈마다 보관 기간(retention)을 두어, 일정 기간이 지난 기록을 자동으로 정리합니다.

도서관의 잡지 코너를 생각하면 이해가 쉽습니다. 최근 호는 서가에 꽂아 바로 볼 수 있게 두고, 지난 호는 창고로 옮겨 두었다가 일정 기간이 지나면 폐기합니다.

Security Hub에서도 최근 이슈는 조회와 검색이 가능한 상태로 유지되고, 해결되어 더 이상 갱신되지 않는 이슈는 보관 상태로 넘어가 일반 목록에서는 빠집니다. 보관된 이슈도 일정 기간 동안은 다시 꺼내 볼 수 있지만, 그 기간이 지나면 삭제되어 더는 조회할 수 없습니다. 실제 기간 값은 서비스 정책에 따라 달라질 수 있으므로 도입 전에 문서로 확인하는 것이 안전합니다.

정리하면 보관 기간은 이슈가 언제까지 남고 언제 정리되는지를 정하는 규칙입니다. 현재 목록에 보이는 것과 보관된 것, 이미 삭제된 것을 구분해 이해해야 오래된 기록을 근거 자료로 쓸 수 있습니다.

직접 이슈 보내기

BatchImportFindings로 우리 점검 결과를 직접 넣는 방법을 익힌다

회사가 자체 스크립트로 서버 설정을 점검하고 있는데 그 결과가 Security Hub 화면에는 하나도 보이지 않는다면, 담당자는 두 개의 목록을 번갈아 보며 같은 일을 두 번 확인해야 합니다. Security Hub는 이 문제를 해결하려고 외부에서 만든 점검 결과를 직접 밀어 넣는 통로인 BatchImportFindings를 제공합니다.

사내 게시판에 비유하면 사용법이 분명해집니다. 각 부서가 만든 공지를 게시판 담당자에게 정해진 양식으로 넘기면, 담당자는 그 양식이 맞는지만 확인하고 게시판에 붙입니다.

BatchImportFindings도 같은 방식으로, 점검 도구가 이슈의 형식에 맞춘 목록을 한 번에 여러 건 보내면 Security Hub가 이를 받아 자기 이슈로 등록합니다. 이때 이슈마다 고유한 식별자와 출처, 대상 리소스, 심각도 같은 필수 항목을 채워야 하며, 이미 있는 식별자를 다시 보내면 새로 쌓이지 않고 기존 이슈가 갱신됩니다. 양식이 어긋난 항목은 거절되어 응답에서 확인할 수 있으므로, 보내는 쪽에서 결과를 반드시 확인해야 합니다.

결국 BatchImportFindings는 외부 점검 결과를 Security Hub의 이슈 형식으로 변환해 대량 등록하는 인터페이스입니다. 자체 점검을 쓰는 조직도 이 통로를 통해 모든 결과를 한 화면에서 관리할 수 있게 됩니다.

통합(Integration)의 개념

다른 서비스 결과를 받아들이는 구조가 어떻게 되어 있는지 본다

회사에 보안 장비가 다섯 대 있는데 각 장비가 자기 화면에만 경고를 띄운다면, 담당자는 아침마다 다섯 화면을 번갈아 열며 같은 사건을 다섯 번 확인해야 하고 경고마다 이름과 형식이 달라 무엇을 먼저 손봐야 할지도 판단하기 어렵습니다. AWS Security Hub의 통합(Integration)은 이렇게 흩어진 보안 결과를 하나의 공통 형식으로 받아들여 한 화면에 모아 주는 구조입니다.

통합은 택배 물류센터와 비슷합니다. 여러 공장에서 물건이 각자 다른 크기와 포장으로 도착하면, 물류센터는 규격이 정해진 표준 박스로 다시 포장해 한 라인에 올립니다.

이때 각 공장이 보내는 원본 데이터를 발견 결과(Finding)라고 부르고, Security Hub는 이를 제품 이름, 심각도, 리소스, 발생 시각 같은 정해진 항목에 맞춰 변환해 저장합니다. 그래서 서로 다른 서비스의 결과라도 같은 기준으로 정렬하고 비교할 수 있습니다.

정리하면 통합은 여러 보안 서비스의 발견 결과를 공통 형식으로 변환해 중앙에 모으는 연결 계층이며, Security Hub는 이 구조 위에서 중복 제거와 우선순위 판단을 가능하게 합니다.

GuardDuty 통합

위협 탐지 결과가 어떤 보안 이슈로 바뀌는지 확인한다

서버가 해외의 낯선 주소와 갑자기 대량으로 통신을 주고받는데 아무도 알아차리지 못한다면, 침해는 이미 몇 시간째 진행 중일 수 있습니다. GuardDuty는 계정 안의 로그를 계속 분석해 이런 위협을 찾아내지만, 그 경고를 사람이 매일 직접 확인하지 않으면 탐지의 의미가 사라지므로 Security Hub의 GuardDuty 통합이 탐지 결과를 보안 이슈로 바꿔 한 화면에 올립니다.

이 구조는 아파트 단지의 경비 시스템과 같습니다. 각 동에 설치된 감시 카메라(GuardDuty)가 수상한 움직임을 감지하면, 관제실(Security Hub)은 그 장면을 정해진 신고서 양식으로 옮겨 적고 위험도를 함께 표시합니다. 신고서에는 어떤 동에서, 어떤 종류의 이상이, 얼마나 심각하게 발생했는지가 적히며, 같은 사건이 반복되면 하나로 묶여 중복 알림이 줄어듭니다.

경비원은 여러 화면을 보지 않고 관제실의 신고 목록만 확인해 순서대로 출동하면 됩니다.

결국 GuardDuty 통합은 위협 탐지 결과를 발견 결과로 변환해 심각도와 리소스 정보를 붙이는 과정이며, 이를 통해 탐지가 실제 대응으로 이어지는 통로가 만들어집니다.

7부. 통합 서비스063

Inspector 통합

취약점 결과가 어떤 항목으로 매핑되는지 이해한다

패치가 오래된 서버가 몇 대인지, 어떤 소프트웨어 패키지가 위험한지 아무도 정확히 모른다면 취약점 대응은 감에 의존하게 됩니다. Inspector는 리소스를 스캔해 취약점을 찾아 주지만 그 결과가 다른 경고와 섞이지 않으면 조치 순서를 세우기 어려우므로, Security Hub의 Inspector 통합이 이 결과를 공통 발견 결과 형식의 항목으로 매핑해 한 화면에서 비교할 수 있게 합니다.

이 과정은 건강검진 결과표를 정리하는 일과 비슷합니다. 검사실(Inspector)이 혈압과 혈당 같은 항목을 각각 재어 원본 수치를 내면, 보건소(Security Hub)는 그 수치를 표준 결과표의 정해진 칸에 옮겨 적습니다. 결과표에는 어떤 검사였는지, 수치가 얼마나 위험한지, 어떤 대상(리소스)의 결과인지가 함께 적히고 위험한 항목부터 위쪽에 놓입니다.

그래서 담당자는 검사실을 다시 찾지 않고 결과표 한 장으로 먼저 볼 항목을 정합니다.

정리하면 Inspector 통합은 취약점 발견 항목을 심각도, 리소스, 권장 조치 같은 공통 필드로 매핑하는 작업이며, 이를 통해 스캔 결과가 우선순위가 있는 보안 이슈로 바뀝니다.

7부. 통합 서비스064

Macie 통합

민감 데이터 발견 결과가 어떤 특징으로 들어오는지 본다

고객의 주민등록번호가 담긴 파일이 어느 저장소에 있는지 아무도 모른다면, 그 파일이 공개로 열리는 순간 바로 사고가 됩니다. Macie는 S3 안의 데이터를 표본으로 살펴 민감 정보를 찾아내지만 그 발견이 담당자에게 전달되지 않으면 대응이 늦어지므로, Security Hub의 Macie 통합이 이 발견을 보안 이슈로 올립니다.

이 구조는 택배 집하장의 내용물 검사와 비슷합니다. 검사 담당(Macie)이 소포를 열어 내용물 목록을 만들면, 집하장 관리 시스템(Security Hub)은 그 목록을 민감 정보 발견이라는 정해진 항목으로 등록합니다. 항목에는 어떤 종류의 정보가 몇 건 있었는지, 어느 소포(객체)에 있었는지, 위험도가 어느 정도인지가 적히고, 같은 저장소에서 반복되면 하나의 이슈로 묶입니다.

관리자는 소포를 다시 열어 보지 않고 목록만 보고 위험한 것부터 조치합니다.

결국 Macie 통합은 민감 데이터 발견 결과를 데이터 식별자, 리소스, 심각도 항목을 가진 발견 결과로 전달하는 경로이며, 이를 통해 데이터 노출 위험이 다른 보안 이슈와 같은 기준으로 관리됩니다.

암호화가 꺼진 저장소가 언제 만들어졌는지, 누가 설정을 바꿨는지 기록이 없다면 규정 위반은 사후에야 발견됩니다. AWS Config는 리소스 설정을 계속 기록하고 규칙으로 평가해 준수 여부를 판정하지만, 그 판정이 보안 현황판과 따로 놀면 전체 상태를 한눈에 볼 수 없으므로 Security Hub의 AWS Config 통합이 이 판정을 컨트롤 결과로 연결합니다.

이 경로는 아파트 관리사무소의 점검표와 같습니다. 점검원(Config 규칙)이 각 세대의 소방 설비를 정해진 기준과 비교해 적합과 부적합을 표시하면, 관리 시스템(Security Hub)은 그 결과를 컨트롤 항목의 통과와 실패로 옮겨 적습니다. 점검표에는 어느 세대의 어떤 항목이 왜 실패했는지가 남고, 같은 기준을 여러 세대에 적용한 결과가 하나의 컨트롤 아래 모입니다.

관리자는 세대마다 따로 확인하지 않고 컨트롤별 실패 수를 보고 우선순위를 정합니다.

정리하면 AWS Config 통합은 설정 규칙의 준수 판정을 컨트롤 결과로 연결하는 경로이며, 이를 통해 리소스 설정 위반이 표준(Standard) 단위의 보안 점수로 집계됩니다.

IAM Access Analyzer 통합

우리 회사 저장소가 외부 계정과 공유되어 있다는 사실을 몇 달 뒤에야 알게 된다면, 그 기간의 노출은 되돌릴 수 없습니다. IAM Access Analyzer는 리소스 정책을 읽어 신뢰 경계 밖으로 열린 대상을 찾아내지만, 그 목록이 한 곳에 모이지 않으면 누가 먼저 닫아야 할지 알기 어려우므로 Security Hub의 IAM Access Analyzer 통합이 이 목록을 보안 이슈로 전달합니다.

이 전달 과정은 건물의 출입문 점검과 비슷합니다. 경비 담당(IAM Access Analyzer)이 문마다 잠금 상태와 출입 권한을 확인해 외부인에게 열린 문 목록을 만들면, 관제 시스템(Security Hub)은 그 목록을 발견 결과로 등록합니다. 항목에는 어떤 리소스가, 어떤 외부 주체에게, 어떤 권한으로 열려 있는지가 적히고 위험도에 따라 정렬됩니다.

건물주는 문을 하나씩 확인하지 않고 목록의 위쪽부터 잠금을 바꿉니다.

결국 IAM Access Analyzer 통합은 외부 공유 발견 결과를 리소스, 외부 주체, 심각도 항목으로 전달하는 경로이며, 이를 통해 신뢰 경계를 벗어난 노출이 다른 보안 이슈와 같은 화면에서 추적됩니다.

Firewall Manager 통합

조직 전체 정책 위반 결과를 한곳에서 보는 방법을 다룬다

회사가 계정을 수십 개 넘게 쓰기 시작하면 방화벽 규칙과 보안 정책이 계정마다 조금씩 달라지고, 어느 계정이 규칙을 어겼는지 확인하려면 관리자가 계정을 하나씩 열어 봐야 합니다. 어떤 계정은 아예 점검에서 빠져 있어서 사고가 터진 뒤에야 그 사실을 알게 되는 일도 생깁니다. AWS Security Hub(여러 계정의 보안 점검 결과를 모아 주는 서비스)와 함께 쓰는 Firewall Manager(방화벽 규칙을 조직 전체에 배포하고 관리하는 서비스)는 이 확인 작업을 한곳으로 모으기 위해 만들어졌습니다.

이 서비스는 아파트 단지 관리사무소와 비슷합니다. 관리사무소가 단지 모든 세대에 같은 소방 점검 기준을 공지하고, 각 세대의 점검 결과를 하나의 장부에 받아 적으면, 관리자는 세대마다 문을 두드리지 않고도 어느 집에 소화기가 빠졌는지 한눈에 알 수 있습니다.

Firewall Manager의 정책(policy)은 그 공지에 해당하고, 정책이 적용된 계정들의 준수 여부는 Security Hub의 통합된 결과 목록으로 장부처럼 쌓입니다. 정책을 새로 만들거나 고치면 그 내용이 조직 안의 계정들에 자동으로 배포되므로, 사람이 계정마다 규칙을 복사해 넣는 과정도 사라집니다.

정리하면 Firewall Manager는 조직 단위의 방화벽 정책을 한 번 정의해 모든 계정에 적용하고, 각 계정의 위반 여부를 Security Hub 한 화면에서 확인하게 해 주는 통합 관리 도구입니다.

Health·Trusted Advisor 연계

운영상 위험 신호를 보안 관점에서 해석한다

서버를 운영하다 보면 디스크가 거의 찼다거나 백업이 오래됐다는 알림이 쏟아지는데, 이런 운영 알림은 대개 곧 문제가 생길 수 있다는 수준에서 끝나 보안과 연결되지 않습니다. 그런데 실제 침해 사고는 이런 사소해 보이는 신호에서 시작되는 경우가 많아, 운영 상태를 보안 관점으로 다시 읽어 주는 통역이 필요합니다. AWS Health(계정과 리소스의 상태 이벤트를 알려 주는 서비스)와 Trusted Advisor(모범 사례와 어긋난 항목을 점검해 주는 서비스)의 결과를 Security Hub로 가져오는 연계가 그 역할을 합니다.

비유하자면 건강검진 결과지를 여러 과의 의사가 함께 보는 상황입니다. 내과에서 나온 혈압 수치와 정형외과에서 나온 자세 진단은 따로 보면 그냥 숫자지만, 주치의가 이 둘을 한 장에 모아 이 조합은 위험하다고 해석해 주면 비로소 의미가 생깁니다.

마찬가지로 Health의 이벤트(예: 특정 리소스의 장애나 예정된 유지보수)와 Trusted Advisor의 점검 항목(예: 공개된 스토리지, 취약한 암호화 설정)이 Security Hub의 공통 형식인 결과 목록으로 들어오면, 운영 신호가 보안 이슈와 같은 목록에서 같은 심각도 기준으로 비교됩니다. 그 덕분에 담당자는 운영 알림과 보안 경고를 따로 뒤지지 않고 우선순위를 한 번에 정할 수 있습니다.

정리하면 Health와 Trusted Advisor의 연계는 운영 상태 신호를 보안 결과와 동일한 형식으로 변환해, 놓치기 쉬운 위험을 보안 관점에서 해석하고 우선순위를 매기게 해 주는 장치입니다.

파트너·서드파티 통합

외부 보안 도구의 결과를 Security Hub로 들여오는 방법을 본다

비유하자면 여러 택배 회사에서 온 물건을 한 창고에서 받는 상황입니다. 각 회사마다 송장 양식이 달라도, 창고 입구에서 공통 양식으로 다시 적어 두면 재고를 셀 때 회사별로 나눠 볼 필요가 없습니다.

Security Hub의 AWS Finding Format(AWS가 정한 공통 결과 형식)이 그 공통 양식이고, 파트너사 제품은 통합(integration)을 통해 자기 결과를 이 형식으로 바꿔 전송합니다. 전송 방식은 각 파트너가 제공하는 커넥터나 API 호출을 쓰며, 제품에 따라 지원 범위와 설정 방법이 다르므로 도입 전에 해당 파트너 문서를 확인해야 합니다.

정리하면 파트너 통합은 외부 보안 도구의 결과를 공통 형식으로 변환해 Security Hub에 모음으로써, 도구마다 다른 화면과 용어를 하나의 목록으로 통일하는 방법입니다.

통합 문제 해결

결과가 들어오지 않을 때 확인하는 순서를 정리한다

연동을 마쳤는데도 Security Hub 화면에 새 결과가 하나도 보이지 않으면, 담당자는 설정을 처음부터 다시 의심하며 시간을 낭비하기 쉽습니다. 문제는 대개 권한, 리전, 형식 중 한 곳에서 생기는데 어디가 원인인지 알려 주지 않으므로, 확인할 순서를 미리 정해 두는 것이 중요합니다.

비유하자면 택배가 오지 않을 때 확인하는 순서와 같습니다. 먼저 보낸 사람이 실제로 발송했는지, 즉 도구 쪽에서 결과 전송이 켜져 있는지를 봅니다. 다음으로 주소가 맞는지, 즉 결과가 향하는 리전과 계정이 Security Hub를 켠 곳과 같은지 확인하고, 그다음 경비실에서 막히지 않았는지, 즉 결과를 보내는 데 필요한 권한이 허용되어 있는지를 봅니다.

이 세 가지가 모두 맞는데도 안 되면 마지막으로 물건의 형태가 규격에 맞는지, 즉 결과가 AWS Finding Format에 맞게 작성되었는지를 확인하며, 앞 단계가 통과되었다는 전제 위에서만 다음 단계가 의미가 있으므로 순서를 건너뛰지 않아야 합니다.

정리하면 통합 문제 해결은 전송 여부, 대상 리전과 계정, 권한, 결과 형식이라는 네 관문을 차례로 확인하는 절차입니다. 이 순서를 지키면 원인을 훨씬 빨리 좁힐 수 있습니다.

교차 리전 집계

여러 리전의 이슈를 한 리전에서 모아 보는 방법을 이해한다

서비스가 서울, 도쿄, 버지니아 등 여러 리전에 나뉘어 돌아가면 보안 결과도 리전마다 따로 쌓여서, 담당자는 리전을 바꿔 가며 화면을 열어야 전체 상황을 알 수 있습니다. 리전이 늘어날수록 이 왕복은 늘어나고 결국 아무도 전체를 보지 않게 되므로, 흩어진 결과를 한곳으로 모으는 장치가 필요합니다.

비유하자면 전국에 지점을 둔 회사가 매일 아침 본사에서 하나의 상황판을 보는 것과 같습니다. 각 지점은 자기 지역의 보고서를 본사로 보내고, 본사는 그것을 지점별로 따로 보관하지 않고 한 장의 판에 붙입니다.

이때 보고서를 모으는 본사가 집계 리전(aggregation Region)이고, 보고서를 보내는 각 지점이 연결된 리전(linked Region)이며, 본사 판에는 어느 지점에서 온 문제인지가 함께 표시됩니다. 원본 결과는 각 지점에 그대로 남아 있어서, 본사 판에서 문제를 발견하면 해당 지점으로 돌아가 자세히 조사할 수 있습니다.

정리하면 교차 리전 집계는 각 리전의 보안 결과를 하나의 집계 리전으로 복제해 모으는 기능입니다. 덕분에 담당자는 한 화면에서 전체 리전의 이슈를 같은 기준으로 비교하고 우선순위를 정할 수 있습니다.

집계 리전 설계

어느 리전을 집계 지점으로 삼을지 정하는 기준을 세운다

집계 리전을 정하는 일은 생각보다 되돌리기 번거로운 결정이라, 처음에 아무 리전이나 골라 두면 나중에 결과 이력이 끊기거나 담당자가 보기 어려운 곳에 상황판이 놓이게 됩니다. 어느 리전을 집계 지점으로 삼을지는 기술적 조건과 조직의 운영 방식이라는 두 가지 기준으로 함께 판단해야 합니다.

비유하자면 전국 지점의 보고서를 모을 본사를 어디에 둘지 정하는 문제와 같습니다. 본사는 사람이 가장 자주 드나드는 곳이어야 하고, 각 지점에서 오는 보고서를 받을 창구가 있어야 하며, 정전이나 통신 장애가 나도 상황판이 멈추지 않을 만큼 안정적이어야 합니다.

기술적으로는 Security Hub가 집계 리전에 요구하는 조건과 각 리전의 서비스 지원 여부를 확인하고, 조직의 데이터 보관 규칙상 결과를 한 국가에 모아도 되는지도 함께 봐야 합니다. 운영 측면에서는 보안 담당자가 실제로 자주 보는 시간대와 장애 대응 체계가 그 리전에 맞춰져 있는지를 기준으로 삼는 것이 좋습니다.

정리하면 집계 리전 설계는 접근성, 안정성, 규제 조건, 운영 체계라는 네 가지를 함께 저울질해 하나의 리전을 고르는 결정입니다. 한 번 정한 뒤에는 바꿀 때의 영향까지 미리 생각해 두어야 합니다.

교차 계정 집계

조직 전체 이슈를 한 화면에 모으는 구조를 설명한다

회사가 커지면서 서비스마다 AWS 계정(account)을 따로 만들면, 각 계정의 보안 도구는 자기 계정 안의 문제만 보여 줍니다. 그러다 보니 경영진이 전체 상황을 물으면 담당자가 계정 수만큼 화면을 넘기며 손으로 표를 만들어야 하고, 그 사이에 눈에 띄지 않은 위험한 계정 하나가 그대로 남습니다. 교차 계정 집계(cross-account aggregation)는 이 문제를 풀기 위해 관리 계정 하나가 나머지 계정의 결과를 모아 오는 구조입니다.

아파트 단지에 비유하면, 각 동마다 따로 관리 대장을 쓰던 것을 관리사무소가 동별 대장을 한 장의 단지 현황판으로 옮겨 적는 일과 같습니다. 각 동(계정)은 자기 대장을 그대로 쓰고, 관리사무소(관리 계정)는 위임받은 권한으로 그 대장을 읽어 와 한 표에 합칩니다.

이때 동별 대장의 형식이 제각각이면 합칠 수 없으므로 공통 형식으로 맞추는 작업이 먼저 필요합니다. 그리고 한 동이 문을 잠그고 대장을 내놓지 않으면 그 동만 현황판에서 빠지므로, 누락을 감시하는 장치가 함께 있어야 합니다.

결국 교차 계정 집계는 여러 계정에서 나온 발견 결과를 중앙 계정 한 곳으로 모아 하나의 목록으로 보여 주는 구조이며, 합치는 기술보다 빠진 계정이 없다는 확인이 핵심입니다.

심각도 산정 기준

서비스마다 다른 심각도를 어떻게 비교할지 다룬다

보안 점검 도구를 두 개 이상 쓰면 같은 문제가 한 곳에서는 높음, 다른 곳에서는 중간으로 표시되어 담당자는 무엇을 먼저 손댈지 판단을 멈추게 됩니다. 서비스마다 자기 기준으로 등급을 매기기 때문인데, 심각도 산정 기준(severity standard)은 이렇게 제각각인 등급을 같은 잣대로 비교할 수 있게 맞추는 약속입니다.

택배 현장에 비유하면, 여러 택배사가 긴급 표기를 제각각 붙여 물류센터가 순서를 정하지 못하는 상황과 같습니다. 센터가 깨지기 쉬운 물건이면서 당일 배송이면 최우선이라는 공통 규칙표를 만들어 두면, 어느 회사에서 온 상자든 같은 규칙으로 줄을 세울 수 있습니다.

규칙표는 어떤 조건이 몇 점인지 미리 정하고, 조건이 여러 개 겹칠 때 점수를 더할지 높은 쪽만 택할지도 함께 정합니다. 또한 원래 서비스가 붙인 등급을 지우지 않고 근거와 함께 환산해 두어야, 나중에 왜 그런 순서가 나왔는지 되짚을 수 있습니다.

결국 심각도 산정 기준은 데이터 민감도, 노출 범위, 악용 가능성 같은 항목에 점수를 매겨 서로 다른 도구의 경고를 하나의 순서로 바꾸는 규칙입니다.

보안 점수(Security Score)

표준별 점수가 무엇을 반영해 계산되는지 이해한다

대시보드에 78점이라는 숫자만 있으면 지난달보다 좋아졌는지, 어디를 고쳐야 오르는지 알 수 없어 개선의 출발점을 잡기 어렵습니다. 보안 점수(Security Score)는 통제 항목을 표준(standard)별로 묶어 충족 여부를 비율로 환산한 값으로, 이 막연함을 숫자 하나로 줄여 줍니다.

성적표에 비유하면, 배점이 다른 과목의 총점은 맞은 문항 수가 아니라 각 문항의 배점을 더해 계산됩니다. 보안 점수도 같아서, 어떤 표준에는 항목이 수십 개 있고 어떤 표준에는 몇 개뿐이라 표준마다 만점의 무게가 다릅니다.

각 항목은 통과와 실패로만 세는 것이 아니라, 리소스 개수나 사용 기간처럼 그 항목이 적용되는 범위를 가중치로 반영하기도 합니다. 그리고 검사하지 못한 항목은 통과로 치지 않고 별도로 표시해야 점수가 실제보다 부풀지 않습니다.

결국 보안 점수는 표준별 통제 항목의 충족 비율에 가중치를 얹어 계산한 요약값이며, 그 점수의 근거는 항상 어떤 항목이 빠졌는지 보여 주는 목록입니다.

점수 해석의 함정

점수가 높다고 안전하다고 말할 수 없는 이유를 짚는다

점수가 95점이니 안전하다고 보고를 올렸는데, 실제로는 그 점수를 매긴 도구가 보지 못하는 영역에서 침해가 일어나는 일이 있습니다. 점수는 측정 대상과 측정 방법을 정한 뒤에 나오는 값이라, 그 범위를 벗어난 위험은 숫자에 아예 나타나지 않습니다.

건강검진에 비유하면, 검진 항목이 20개뿐인데 모든 항목 정상이라는 결과를 받고 몸 전체가 건강하다고 말할 수 없는 것과 같습니다. 검진에 없는 병은 결과지에 없을 뿐 없어진 것이 아니고, 어제 검사한 결과가 오늘의 상태를 보장하지도 않습니다.

점수도 마찬가지로, 검사에서 빠진 서비스, 권한이 없어 읽지 못한 계정, 방금 만들어진 리소스는 감점 없이 조용히 사라집니다. 또 항목을 하나 없애거나 기준을 느슨하게 바꾸면 아무것도 고치지 않아도 점수가 오를 수 있습니다.

결국 점수는 정해진 항목을 얼마나 채웠는가의 비율일 뿐이며, 안전하다는 판단은 그 숫자와 함께 빠진 항목과 최근 변화를 봐야 내릴 수 있습니다.

우선순위 정하기

심각도·노출도·자산 중요도를 함께 놓고 순서를 정하는 법을 본다

경고가 수백 건 쌓이면 담당자는 목록 맨 위부터 처리하게 되는데, 그 순서는 대개 심각도 하나만 보고 매겨져 있어 정작 큰 위험이 뒤로 밀립니다. 우선순위 정하기는 심각도에 더해 노출도와 자산 중요도를 함께 놓고 처리 순서를 정하는 일입니다.

보안에서도 인터넷에 열려 있는지, 고객 정보가 있는지, 악용되면 얼마나 큰 피해인지에 각각 등급을 매기고 곱하거나 더해 하나의 점수로 만듭니다. 이때 세 항목의 단위가 다르므로 순위를 매겨 더하는 방식이 계산과 설명 모두에 유리합니다.

결국 우선순위는 심각도만으로 정해지지 않고 노출도와 자산 중요도를 함께 반영해 매긴 순서이며, 그 근거를 함께 남겨야 담당자가 아닌 사람도 납득할 수 있습니다.

노출된 리소스 판별

인터넷에 열린 자원을 먼저 보는 이유와 찾는 방법을 다룬다

내부에서만 쓰던 저장 공간이 설정 한 줄 때문에 인터넷에 열려 있었고, 그 사실을 침해가 일어난 뒤에야 알게 되는 일이 있습니다. 노출된 리소스 판별은 인터넷에서 접근 가능한 자원을 먼저 찾아내는 작업으로, 공격자도 같은 방식으로 훑기 때문에 가장 먼저 봐야 합니다.

집 현관에 비유하면, 방마다 잠금장치가 잘 되어 있어도 대문이 열려 있으면 소용이 없으므로 먼저 대문이 열린 집을 찾아내는 것과 같습니다. 판별은 공인 주소를 가진 자원, 외부에서 접근 가능한 통로, 인증 없이 열린 저장소를 목록으로 훑는 방식으로 이루어집니다.

그리고 설정 파일만 보고 판단하지 않고, 실제로 바깥에서 연결을 시도해 응답이 오는지 확인해야 오탐과 누락을 줄일 수 있습니다. 찾은 뒤에는 닫을 수 있는 것은 닫고, 불가피하게 열어야 하는 것은 허용 목록에 근거와 함께 남깁니다.

결국 노출된 리소스 판별은 인터넷에서 닿는 자원을 실제 연결로 확인해 목록화하는 일이며, 이 목록이 이후 모든 우선순위의 출발점이 됩니다.

인사이트(Insight)

조건으로 이슈를 묶어 추세를 보는 기능을 이해한다

보안 경고가 하루에 수천 건씩 올라오는데 그중 무엇이 진짜 위험한지 판단하지 못하면, 담당자는 결국 가장 눈에 띄는 알림만 처리하고 나머지는 흘려보내게 됩니다. AWS Security Hub의 인사이트(Insight)는 이런 상황에서 경고를 조건으로 묶어 추세를 보여 주는 기능입니다.

아파트 관리사무소에 하루 수백 건의 민원이 들어오면 직원은 건마다 대응하다 지쳐 정작 큰 문제를 놓칩니다. 이때 '누수 관련 민원만', '3일 이상 미처리된 민원만'처럼 조건을 정해 장부를 따로 떼어 보면 문제의 크기와 늘어나는 속도가 한눈에 보입니다.

인사이트도 같은 방식으로 동작해서, 미리 정한 조건에 맞는 경고만 모아 하나의 묶음으로 보여 줍니다. 관리사무소 장부에서 조건표와 묶인 목록, 기간별 건수 그래프가 각각 대응하며, 이 세 가지를 합쳐 놓은 것이 인사이트 하나입니다.

정리하면 인사이트는 Security Hub에 쌓인 발견 항목(Finding)을 조건으로 필터링해 묶음 단위로 집계하고, 그 건수 변화로 추세를 읽게 해 주는 기능입니다.

사용자 지정 인사이트

우리 조직에 필요한 관점을 직접 정의하는 방법을 익힌다

기본으로 제공되는 인사이트는 대부분의 조직에 무난하지만, 우리 회사만의 위험 기준을 담지는 못합니다. 그래서 어떤 항목을 중요하게 볼지 직접 정하는 사용자 지정 인사이트(Custom Insight)가 필요해집니다.

사용자 지정 인사이트가 바로 그 서가를 만드는 작업으로, 어떤 필드에 어떤 값을 넣을지 직접 고르고 조건을 조합해 저장합니다. 저장한 뒤에는 그 조건에 걸리는 항목 수가 자동으로 다시 계산되므로, 사서가 매일 장부를 다시 세지 않아도 추세가 보입니다.

결론적으로 사용자 지정 인사이트는 발견 항목의 속성과 심각도, 리소스 종류 같은 필드를 조합해 조직 고유의 관점을 조건으로 저장하고, 그 결과를 지속적으로 집계해 주는 기능입니다.

EventBridge 연동

이슈 변화를 이벤트로 받아 자동화를 시작하는 구조를 이해한다

Security Hub 화면을 매일 열어 새 경고가 늘었는지 확인하는 일은 사람이 붙어 있어야만 가능합니다. 그래서 경고가 생기는 순간 그 사실을 다른 서비스로 자동으로 넘기는 통로가 필요하고, 그 역할을 EventBridge 연동이 맡습니다.

택배 집하장에서 새 상자가 들어올 때마다 벨이 울리고 정해진 구역으로 자동으로 굴러가게 해 두면, 사람은 벨이 울린 상자만 보면 됩니다. Security Hub의 EventBridge 연동도 이와 같아서, 발견 항목이 새로 생기거나 상태가 바뀌면 그 사실이 이벤트(event)라는 작은 신호로 외부에 전달됩니다.

집하장의 벨과 분류기가 EventBridge의 규칙(rule)에 해당하고, 굴러간 구역에서 일하는 담당자가 Lambda 함수나 알림 대상입니다. 그래서 어떤 이벤트를 받을지 규칙으로 정해 두면, 사람이 화면을 지키지 않아도 필요한 곳에서 조치가 시작됩니다.

정리하면 EventBridge 연동은 Security Hub의 발견 항목 변화를 이벤트로 내보내고, 그 이벤트를 규칙에 따라 다른 서비스로 연결해 자동 대응의 출발점을 만드는 구조입니다.

이벤트 패턴 작성

어떤 이슈에 반응할지 조건을 쓰는 방법을 익힌다

모든 이벤트에 반응하도록 규칙을 만들면 사소한 변화에도 자동화가 쏟아져 진짜 급한 일이 묻힙니다. 그래서 어떤 이벤트만 받을지 조건을 적는 일이 필요하고, 그 조건을 적는 문법이 이벤트 패턴(event pattern)입니다.

아파트 경비실이 모든 우편물을 세대마다 올려 보내면 일이 감당되지 않습니다. 그래서 '등기우편만', '우리 동으로 온 것만'처럼 받을 조건을 적은 수취 기준표를 두고, 거기에 맞는 우편만 처리합니다.

이벤트 패턴도 같은 역할로, JSON 형식의 작은 기준표에 어떤 출처에서 온 어떤 종류의 이벤트인지, 심각도가 무엇인지 같은 값을 적어 둡니다. 기준표에 적힌 값과 실제 이벤트의 값이 맞아떨어질 때만 규칙이 실행되므로, 조건을 촘촘히 적을수록 자동화가 다루는 범위는 좁고 정확해집니다.

결국 이벤트 패턴은 이벤트의 구성 값과 내부 필드를 비교해 일치 여부를 판단하는 선언적 조건이며, 이 조건이 EventBridge 규칙의 필터 역할을 합니다.

Lambda로 자동 교정

이슈를 받아 설정을 바로 고치는 패턴을 만든다

공개로 열려 있으면 안 되는 저장소가 발견되었다는 경고를 받고도 담당자가 회의 중이라 손을 못 대면, 그 사이 노출 시간만 길어집니다. 이 간격을 없애려고 이슈를 받는 즉시 설정을 고치는 코드를 붙이는 방식이 Lambda 자동 교정입니다.

세탁실에 누수 감지 센서를 달아 두고 물이 새면 밸브가 스스로 잠기게 해 두면, 집주인이 집에 없어도 피해가 커지지 않습니다. Lambda로 자동 교정하는 패턴도 이와 같아서, 이슈가 들어오면 작은 코드 조각인 Lambda 함수가 실행되어 문제가 된 설정을 직접 바꿉니다.

센서가 이슈, 밸브를 잠그는 장치가 Lambda 함수, 실제로 잠기는 동작이 설정 변경, 남는 작업 일지가 실행 로그에 해당합니다. 다만 코드가 잘못되면 멀쩡한 설정까지 건드릴 수 있으므로, 대상 리소스와 바꿀 값을 좁게 정하고 실행 권한도 그 범위로만 주는 것이 중요합니다.

정리하면 Lambda 자동 교정은 발견 항목을 입력으로 받아 필요한 API를 호출해 설정을 바로잡고, 그 결과를 다시 Security Hub에 반영하는 대응 자동화입니다.

Systems Manager Automation

리소스 조치를 문서로 정의해 자동 실행하는 방법을 본다

여러 계정과 리전에 흩어진 리소스를 일일이 콘솔에서 찾아 고치는 방식은 사람마다 순서가 달라지고, 누가 무엇을 했는지도 남지 않습니다. 이런 조치를 절차로 정의해 두고 자동으로 실행하는 서비스가 Systems Manager Automation입니다.

건물 소방 점검을 생각해 보면, 점검 항목과 순서를 적은 매뉴얼이 있고 담당자는 그 순서대로만 움직입니다. Systems Manager Automation은 이런 매뉴얼을 문서(document) 형태로 정의해 두고, 필요할 때 정해진 절차를 자동으로 실행하게 해 줍니다.

매뉴얼의 각 점검 항목이 문서 안의 단계(action)에, 점검 대상 건물 주소가 실행 시 넘기는 파라미터에 대응하며, 점검 결과는 실행 이력으로 남습니다. 그래서 누가 실행해도 같은 순서로 같은 조치가 이루어지고, 실패한 단계에서 멈추거나 되돌리는 절차도 문서에 함께 적을 수 있습니다.

결론적으로 Systems Manager Automation은 리소스 조치 절차를 문서로 선언해 두고 파라미터를 바꿔 가며 반복 실행하는 방식이며, Security Hub의 이슈와 연결하면 교정 절차를 표준화해 자동으로 돌릴 수 있습니다.

자동 격리 패턴

침해가 의심되는 리소스를 네트워크에서 떼어내는 흐름을 설계한다

밤에 침해 의심 경보가 울렸는데 담당자가 출근할 때까지 그 서버가 외부 공격자와 계속 통신하며 자료를 빼내고 있다면, 경보를 아무리 정확하게 만들어도 소용이 없습니다. 그래서 경보와 조치 사이의 몇 시간을 없애는 설계가 필요하고, 그것이 침해가 의심되는 자원을 네트워크에서 즉시 떼어내는 자동 격리 패턴(automated isolation pattern)입니다. AWS Security Hub가 경보를 모아 주면, 그 이벤트를 자동으로 넘겨받아 대상 자원의 통신 규칙만 바꿔 버리는 흐름으로 만듭니다. 아파트 단지에 문제가 생긴 세대가 있다고 생각해 보면 이해가 쉽습니다. 관리사무소는 그 세대의 현관문과 엘리베이터 출입을 잠그지만 세대 안의 가구는 하나도 옮기지 않는데, 여기서 관리사무소가 Security Hub, 세대가 침해 의심 서버, 출입을 잠그는 행위가 보안 그룹(security group)의 규칙 교체입니다.

잠글 때는 원래 규칙을 지우지 않고 아무 통신도 허용하지 않는 규칙 한 벌로 갈아 끼워 두었다가, 조사가 끝나면 원래 규칙으로 되돌려 놓습니다. 중요한 점은 서버를 종료하지 않는 것인데, 세대를 부수면 침입 흔적이 함께 사라지기 때문입니다.

그래서 격리와 동시에 디스크 스냅샷과 로그를 따로 보관하고, 담당자에게는 왜 격리했는지와 어떻게 되돌리는지를 함께 알립니다. 정리하면 자동 격리 패턴은 Security Hub의 결과를 트리거로 삼아 보안 그룹과 서브넷 라우팅을 바꾸고, 인스턴스는 살려 둔 채 증거만 보존하는 방식입니다. 조치의 목적이 처벌이 아니라 확산 차단이라는 점을 기억하면 설계가 단순해집니다.

티켓 자동 생성

Jira·ServiceNow로 이슈를 넘겨 조치를 추적하는 방법을 다룬다

경보가 하루에 수백 건씩 쌓이면 대부분은 아무도 열어 보지 않은 채 묻히고, 정말 중요한 한 건이 그 속에 섞여 사라집니다. 그래서 경보를 사람이 실제로 처리하는 작업 항목으로 바꿔 주는 연결이 필요한데, 그것이 Jira나 ServiceNow 같은 사내 이슈 관리 도구로 자동으로 티켓을 만드는 방식입니다. AWS Security Hub는 경보를 모으는 데서 끝나지 않고, 결과를 다른 서비스로 내보내 담당 조직의 업무 흐름에 얹을 수 있게 합니다. 택배 회사의 접수 시스템을 떠올리면 구조가 보입니다. 고객 문의가 들어오면 접수 담당자가 운송장 번호를 붙여 배송팀에 넘기고, 그 번호로 어디까지 갔는지 추적하는데, 여기서 접수 담당자가 이벤트 규칙(EventBridge rule), 운송장 번호가 티켓 번호, 배송팀이 조치 담당자입니다.

자동화는 발견 항목의 제목·심각도·대상 자원·발견 시각을 티켓 항목에 그대로 옮겨 적고, 같은 문제가 반복되면 새 티켓을 만들지 않고 기존 티켓에 덧붙입니다. 또 담당자가 티켓을 닫을 때 원래 발견 항목도 함께 닫히도록 양쪽을 묶어 두어야, 조치했는데도 경보가 계속 남는 일이 생기지 않습니다. 결국 티켓 자동 생성은 Security Hub의 발견 항목을 이벤트로 바꿔 이슈 관리 도구에 등록하고, 그 번호로 조치 경과와 완료를 추적하는 구조입니다. 사람이 하는 일은 판단과 조치뿐이고, 기록과 배분은 자동화가 맡습니다.

알림 채널 설계

메일·Slack·SNS로 보낼 때 소음을 줄이는 법을 정리한다

경보를 메일과 메신저로 모두 보내기 시작하면 며칠 만에 아무도 알림을 읽지 않게 되고, 진짜 사고가 났을 때도 "또 그 알림이겠지" 하고 넘기게 됩니다. 그래서 어떤 사건을 어디로 보낼지 미리 정해 두는 알림 채널 설계가 필요하고, 이는 메일·Slack·SNS 같은 수단을 목적에 맞게 나눠 쓰는 일입니다. AWS Security Hub는 발견 항목을 이벤트로 내보낼 수 있어, 이 경로에 필터와 묶음을 얹는 방식으로 설계합니다. 건물 화재 경보기를 생각하면 판단 기준이 분명해집니다. 연기만 살짝 감지되면 경비실 표시등만 켜지고, 실제 불꽃이 감지되면 건물 전체 사이렌과 소방서 통보가 동시에 나가며, 정기 점검 안내는 게시판에만 붙습니다.

여기서 경비실 표시등이 대시보드, 사이렌이 긴급 채널, 게시판이 주간 요약 메일이고, 알림이 몰릴 때 하나로 묶어 보내는 것이 묶음 처리입니다. 같은 문제가 짧은 시간에 여러 번 반복되면 건마다 보내지 않고 한 건으로 합쳐 횟수를 적고, 업무 시간이 아닌 시간대에는 긴급 등급만 깨우도록 나눕니다. 정리하면 알림 채널 설계의 핵심은 많이 보내는 것이 아니라 등급과 목적에 따라 채널을 나누고, 중복을 묶고, 긴급한 것만 사람을 깨우는 것입니다. 이렇게 하면 알림이 줄어드는 대신 남은 알림 하나하나가 의미를 갖게 됩니다.

심각도 기반 라우팅

심각도에 따라 담당자와 채널을 나누는 방법을 익힌다

모든 경보를 한 사람에게 보내면 그 사람이 휴가를 간 순간 가장 급한 사건이 아무에게도 닿지 않고, 반대로 아무 일도 아닌 경보가 새벽에 담당자를 깨웁니다. 그래서 사건의 심각도를 기준으로 누구에게 어느 채널로 보낼지 미리 정해 두는 심각도 기반 라우팅(severity based routing)이 필요합니다. AWS Security Hub는 발견 항목마다 심각도를 붙여 주므로, 그 값을 기준으로 경로를 나누는 것이 자연스럽습니다. 병원 응급실의 분류를 떠올리면 이해가 빠릅니다. 접수 간호사가 환자를 보고 즉시 처치·응급·일반으로 나눠 각기 다른 구역으로 보내고, 가장 무거운 등급만 당직 전문의를 직접 부릅니다.

여기서 접수 간호사가 라우팅 규칙, 구역이 알림 채널, 당직 전문의 호출이 에스컬레이션(escalation)이고, 등급이 심각도입니다. 높은 등급은 즉시 알림과 함께 담당자 지정과 자동 조치를 함께 걸고, 중간 등급은 업무 시간에 모아 보내며, 낮은 등급은 주간 보고서에만 남깁니다. 여기에 한 가지를 더 붙여야 하는데, 일정 시간 안에 아무도 확인하지 않으면 자동으로 다음 담당자에게 넘어가도록 만드는 것입니다. 결국 심각도 기반 라우팅은 발견 항목의 심각도와 자원의 중요도를 함께 보고 담당자·채널·조치를 정하고, 확인이 없으면 단계적으로 올려 보내는 구조입니다. 기준을 사람마다 다르게 두지 않고 한 곳에서 정해 두는 것이 핵심입니다.

자동 대응의 안전장치

잘못 조치했을 때 되돌릴 수 있게 설계하는 법을 본다

자동 조치를 처음 켜면 반드시 한 번은 엉뚱한 서버를 멈추거나 정상 트래픽을 차단하는 일이 생기는데, 그때 되돌릴 방법이 없으면 자동화 자체가 사고가 됩니다. 그래서 조치를 되돌릴 수 있게 설계하는 안전장치가 필요하고, 이는 자동 대응을 도입할 때 가장 먼저 정해야 하는 부분입니다. AWS Security Hub를 중심으로 조치를 자동화할 때도 이 원칙이 그대로 적용됩니다. 아파트 단지의 정전 대비 설비를 생각해 보면 감이 옵니다. 비상 발전기를 시험할 때는 반드시 본선 차단기를 내리기 전에 수동 잠금을 걸고, 시험 시간을 정해 두며, 끝나면 원래 상태로 돌려놓는 절차를 지킵니다.

여기서 수동 잠금이 사람의 승인 단계, 시험 시간 제한이 조치 유효 시간, 원래 상태 복구가 롤백(rollback)입니다. 그래서 처음에는 조치를 바로 실행하지 않고 제안만 하도록 두고, 익숙해진 뒤에 승인 후 실행, 마지막에 자동 실행으로 단계를 올립니다. 조치 대상을 미리 정한 목록으로 제한하고, 한 번에 격리할 수 있는 자원 수에 상한을 두며, 무엇을 왜 바꿨는지 원래 값과 함께 기록해 두는 것도 함께 갖춰야 합니다. 정리하면 자동 대응의 안전장치는 승인 단계, 대상 제한, 변경 전 값의 기록, 되돌리는 절차라는 네 가지로 이루어집니다. 빠르게 막는 것보다 안전하게 되돌리는 것이 먼저라는 순서를 잊지 않아야 합니다.

자동화 테스트

운영에 넣기 전에 검증하는 절차를 만든다

자동 조치를 만들어 운영에 넣었는데 첫 실제 사건에서 아무 동작도 하지 않았다는 사실을 그때 알게 된다면, 그 자동화는 없는 것과 같습니다. 그래서 운영에 넣기 전에 일부러 사건을 만들어 보고 결과를 확인하는 절차가 필요한데, 이것이 보안 자동화의 테스트입니다. AWS Security Hub와 연동한 흐름이라면 발견 항목을 인위적으로 만들어 전체 경로가 제대로 이어지는지 확인할 수 있습니다. 소방 훈련을 떠올리면 무엇을 시험해야 하는지가 정리됩니다. 실제 불을 내지 않고 연기 모의 장치로 감지기를 울려 보고, 사이렌이 울리는지, 대피 안내가 나가는지, 소방서 통보가 실제로 갔는지를 단계마다 확인합니다.

여기서 모의 장치가 시험용 발견 항목, 단계별 확인이 각 연결 지점의 점검, 훈련 기록이 테스트 결과의 보관입니다. 시험은 격리된 시험 계정에서 먼저 하고, 정상 서비스가 돌아가는 환경에서 바로 하지 않습니다. 확인할 것은 조치가 실행되었는지뿐 아니라 실행되지 말아야 할 대상이 건드려지지 않았는지이며, 실패했을 때 담당자에게 알림이 갔는지도 시험 항목에 넣습니다. 결국 자동화 테스트는 시험용 발견 항목으로 트리거부터 조치와 복구까지 전 구간을 한 번씩 통과시켜 보고, 그 결과를 기록으로 남기는 절차입니다. 이 절차가 있어야 자동 대응은 만들어 둔 장난감이 아니라 실제로 믿고 맡길 수 있는 설비가 됩니다.

Organizations 통합 활성화

계정이 서른 개쯤 되는 회사에서 보안 점검 서비스를 쓰기로 하면, 담당자는 계정마다 로그인해 같은 설정을 서른 번 반복해야 합니다. 그렇게 손으로 켠 설정은 어느 계정이 빠졌는지 확인하기도 어렵고, 새로 만든 계정은 아예 빠져 있는 경우가 흔합니다. AWS Organizations 통합 활성화(Organizations integration)는 이 반복을 없애기 위해 만들어진 기능으로, 여러 계정을 하나의 조직으로 묶는 Organizations와 Security Hub를 연결해 조직 단위로 한 번에 켜는 방법입니다.

비유하자면 아파트 단지 전체의 소방 설비를 계약하는 일과 같습니다. 세대마다 따로 소방 업체를 부르는 대신 단지 관리사무소와 한 번 계약하면 모든 세대에 같은 설비가 들어가고, 새로 입주하는 세대에도 자동으로 같은 설비가 붙습니다.

여기서 관리사무소가 Organizations의 조직이고, 세대가 각 멤버 계정이며, 소방 설비 계약이 Security Hub의 활성화입니다. 그래서 관리 계정에서 통합을 켜면 그 아래 모든 계정이 같은 서비스에 연결되고, 위임 관리자(designated administrator)로 지정한 계정이 전체를 대신 관리하게 됩니다.

즉 Organizations 통합 활성화는 조직과 보안 서비스를 연결해 계정별 수작업을 조직 단위 운영으로 바꾸는 장치이며, 새 계정이 생겨도 설정이 자동으로 따라붙게 만드는 출발점입니다.

신규 계정 자동 활성화

새 계정이 만들어지면 자동으로 켜지게 하는 설정을 다룬다

비유하자면 신축 아파트의 입주 절차와 같습니다. 관리사무소가 "입주하면 소방 설비와 가스 차단기는 자동으로 설치된다"는 규칙을 미리 정해 두면, 새 세대가 들어올 때 따로 신청하지 않아도 설비가 갖춰집니다. 여기서 입주 규칙을 정하는 곳이 Organizations의 관리 계정 또는 위임 관리자이고, 새 세대가 새로 만들어지는 멤버 계정, 자동으로 붙는 설비가 Security Hub 활성화와 기본 표준(default standard) 적용입니다.

이 규칙은 조직 수준에서 한 번 켜 두면 이후 만들어지는 계정에 계속 적용되므로, 계정 생성과 보안 설정 사이의 시차가 사라집니다.

정리하면 신규 계정 자동 활성화는 조직의 기본값을 새 계정에 자동으로 상속시키는 설정이며, 보안 공백이 생기는 가장 흔한 지점인 계정 생성 시점을 막아 주는 장치입니다.

비유하자면 아파트 단지의 통합 관제실과 같습니다. 세대마다 화재 감지기를 두는 것만으로는 부족하고, 모든 세대의 신호를 한 곳에서 받아 상황을 판단하고 출동을 지시하는 관제실이 있어야 합니다. 여기서 관제실이 중앙 보안 계정이고, 각 세대의 감지기가 멤버 계정에서 수집되는 보안 결과, 관제 요원이 위임 관리자 권한을 가진 보안 팀입니다.

이 계정에는 로그와 결과를 모으는 저장 공간과 알림 통로를 두고, 다른 계정은 보안 설정만 따르도록 역할을 나누는 것이 핵심입니다.

즉 중앙 보안 계정 설계는 보안 결과의 집계와 대응을 한 계정에 모으고 나머지 계정은 표준을 따르게 하는 구조이며, 권한을 한곳에 모아 관리하면서도 각 계정의 자율성은 남기는 방식입니다.

위임 관리자 지정

실무에서 누구에게 관리 권한을 줄지 정하는 기준을 본다

조직 전체의 보안 설정을 관리 계정에서 직접 만지면, 원래 결제와 조직 관리만 해야 할 계정에 보안 권한까지 몰리게 됩니다. 관리 계정은 다른 계정보다 훨씬 조심해서 다뤄야 하는 곳이라, 잦은 보안 작업을 그곳에서 하는 것은 위험 부담이 큽니다. 위임 관리자 지정(delegated administrator)은 조직 관리 계정 대신 보안 업무를 전담할 일반 계정 하나를 골라 그 계정에 관리 권한을 넘기는 제도입니다.

비유하자면 건물주와 시설 관리 업체의 관계와 같습니다. 건물주는 중요한 계약만 직접 하고, 실제 시설 점검과 수리는 위임받은 관리 업체가 맡아 처리합니다. 여기서 건물주가 Organizations 관리 계정, 관리 업체가 위임 관리자로 지정된 계정, 점검 항목이 Security Hub의 표준과 컨트롤입니다.

위임 관리자는 조직의 다른 멤버 계정 전체에 표준을 적용하고 결과를 모아 볼 수 있지만, 조직 자체를 바꾸는 권한은 갖지 않으므로 업무 범위가 자연스럽게 분리됩니다.

정리하면 위임 관리자 지정은 조직 관리 권한과 보안 운영 권한을 서로 다른 계정으로 나누는 장치이며, 민감한 관리 계정은 최소한으로 쓰고 보안 업무는 전담 계정에 맡기게 하는 기준입니다.

조직 표준 배포

계정이 늘어날수록 "이 계정은 어떤 기준으로 점검되고 있는가"를 확인하기가 점점 어려워집니다. 어떤 계정은 강한 표준이 켜져 있고 어떤 계정은 아무 표준도 없어서, 같은 조직인데 보안 수준이 제각각이 됩니다. 조직 표준 배포는 이런 편차를 없애기 위해 표준(standard)과 컨트롤(control) 설정을 조직 전체 계정에 한 번에 밀어 넣는 방법입니다.

비유하자면 단지 전체에 같은 관리 규정을 공지하는 일과 같습니다. 관리사무소가 "모든 세대는 소화기 위치를 이렇게 두고, 복도 조명은 이 시간에 점검한다"는 규정을 정해 게시하면, 세대마다 다른 규정을 만드는 일이 없어집니다. 여기서 규정집이 보안 표준, 규정의 개별 조항이 컨트롤, 게시판이 Organizations를 통한 배포 경로입니다.

위임 관리자에서 표준을 지정하면 멤버 계정마다 같은 표준이 적용되고, 컨트롤별로 켜고 끄거나 파라미터를 조정하는 설정도 함께 내려갑니다.

즉 조직 표준 배포는 표준과 컨트롤 구성을 조직이라는 단위로 한 번에 적용하는 운영 방식이며, 계정이 늘어나도 보안 기준선이 흔들리지 않게 하는 수단입니다.

비유하자면 아파트 단지에서 특정 세대에만 다른 규정을 적용하는 것과 같습니다. 1층 상가 세대는 소방 설비 기준이 주거 세대와 다르고, 공사 중인 세대는 일정 기간 별도 점검을 받습니다. 이때 관리사무소는 예외 세대와 사유와 기간을 장부에 적어 두고, 기간이 끝나면 원래 규정으로 되돌립니다. 여기서 장부가 예외를 기록하는 문서와 설정이고, 기간 만료 후 복귀가 예외 해제입니다.

Security Hub에서는 계정을 조직 표준에서 제외하거나, 특정 컨트롤만 비활성화하고 그 사유를 남기는 방식으로 처리합니다.

정리하면 계정별 예외 관리는 예외를 금지하는 것이 아니라 이름과 이유와 기간을 붙여 관리하는 절차이며, 조직 표준을 유지하면서도 필요한 계정만 유연하게 다루게 하는 안전장치입니다.

크로스 계정 접근

집계 계정이 다른 계정 데이터를 읽는 권한 구조를 이해한다

회사가 계정을 업무별로 나눠 쓰기 시작하면 보안 경고도 계정마다 따로 쌓여, 어느 계정이 위험한지 한눈에 알기 어려워집니다. 크로스 계정 접근(cross-account access)은 이렇게 흩어진 계정의 데이터를 집계 계정 하나가 읽어 모을 수 있게 해 주는 권한 구조입니다.

아파트 단지로 비유하면 각 동마다 경비실이 있어 출입 기록을 보관하는데, 중앙 관리실이 모든 동의 기록을 확인하려면 각 동에서 이 관리실 직원은 열람 가능하다고 명단에 올려 주어야 합니다.

AWS에서도 데이터를 가진 쪽 계정이 역할(Role)을 만들고 그 역할의 신뢰 정책(trust policy)에 집계 계정을 적어 넣어야 하며, 이 허가가 없으면 집계 계정이 아무리 요청해도 문이 열리지 않습니다. 반대로 집계 계정 쪽에도 그 역할을 맡을 수 있는 권한 정책(permission policy)이 붙어 있어야 실제 조회가 성사됩니다. 즉 양쪽 계정이 각각 문을 열어 주는 이중 허가 방식이라 한쪽만 설정해서는 접근이 되지 않습니다.

정리하면 크로스 계정 접근은 데이터를 가진 계정의 신뢰 정책과 읽는 계정의 권한 정책이 짝을 이룰 때만 성립하고, Security Hub에서는 이 구조로 집계 계정이 여러 계정의 발견 항목을 한곳에서 받아 봅니다.

멀티 계정 운영의 함정

한 계정만 설정이 달라 생기는 문제들을 짚는다

계정이 여러 개로 늘어나면 대부분은 같은 설정인데 딱 한 계정만 예전 설정 그대로 남아, 그 한 곳에서 보안 경고가 새어 나갑니다. 멀티 계정 운영의 함정은 이런 사소한 차이가 전체 보안 수준을 무너뜨린다는 점입니다.

프랜차이즈 매장 스무 곳이 같은 매뉴얼로 운영되는데 한 매장만 비상구 안내판을 떼어 냈다고 생각해 보면, 본사 점검표에는 모두 정상으로 찍혀도 실제 위험은 그 한 곳에 몰립니다. 계정도 마찬가지로 새 계정을 만들 때 보안 서비스 활성화를 빠뜨리거나, 리전(region)을 다르게 켜 두거나, 예외 규칙을 급하게 추가한 채 잊어버리면 그 계정만 조용히 규정 밖으로 벗어납니다. 또 담당자가 바뀌며 문서에 없는 수동 설정이 남는 경우가 많아, 자동화된 배포만 믿으면 이런 예외는 영원히 발견되지 않습니다.

그래서 계정을 만드는 순간의 표준화와 주기적인 설정 차이 점검이 함께 필요합니다. 결국 멀티 계정 운영의 함정은 개별 계정의 작은 설정 차이에서 오므로, 계정 생성 절차를 표준화하고 모든 계정에 같은 기준을 주기적으로 대조하는 것이 해법입니다.

조직 단위 비용 배분

비용을 팀과 계정별로 나눠 보는 방법을 정리한다

계정을 팀별로 나눠 쓰면 매달 청구서 한 장에 모든 팀의 사용량이 뒤섞여 나와, 어느 팀이 얼마를 썼는지 설명하기 어려워집니다. 조직 단위 비용 배분은 이 청구서를 팀과 계정 단위로 다시 쪼개 보는 방법입니다.

아파트 한 동의 전기 요금이 한 장으로 고지되지만 세대마다 계량기가 있어 각자 쓴 만큼 나눠 내는 것과 같습니다. AWS에서는 계정을 조직(Organizations)의 조직 단위(OU) 아래 묶고, 각 계정에 붙인 태그(tag)와 계정 자체를 기준으로 비용을 나눠 조회합니다.

청구서를 모아 보는 관리 계정에서 팀별, 계정별로 필터를 걸면 어느 조직 단위가 예산을 넘겼는지 바로 드러납니다. 여기에 태그를 강제하는 규칙을 두면 이름 없는 비용이 생기는 일을 줄일 수 있습니다. 정리하면 조직 단위 비용 배분은 조직 구조와 태그를 기준으로 청구 데이터를 나눠, 계정 하나하나의 지출을 팀의 책임으로 연결하는 작업입니다.

대규모 운영 체크리스트

계정이 수백 개일 때 지켜야 할 원칙을 세운다

계정이 수십, 수백 개로 늘면 사람이 하나씩 확인하던 방식은 금세 한계에 부딪히고, 점검하지 못한 계정이 조용히 쌓입니다. 대규모 운영 체크리스트는 그런 환경에서도 빠뜨리지 않기 위해 지켜야 할 최소 원칙을 정해 둔 목록입니다.

상품이 하루 수만 개 들어오는 대형 마트에서 직원이 하나하나 뜯어 보는 대신 모든 상품이 같은 검수대를 통과하게 하고 규격이 어긋난 것만 따로 빼는 방식과 같습니다. 계정도 새로 만들 때 표준 계정 틀을 거치게 하고, 보안 서비스 활성화와 로그 수집을 자동으로 붙이며, 조직 단위로 정책을 한 번에 내려 일괄 적용합니다. 그리고 모든 계정의 설정 상태를 중앙에서 주기적으로 수집해 기준에서 벗어난 계정만 목록으로 뽑아내야 합니다.

사람이 기억해야 할 항목을 줄이고 예외만 눈에 보이게 만드는 것이 핵심입니다. 결국 대규모 운영의 원칙은 표준화와 자동화, 그리고 중앙 집계를 통한 예외 중심 점검이며, 이 세 가지가 체크리스트의 뼈대가 됩니다.

이슈 조사 절차

경고 하나를 받았을 때 따라가는 순서를 만든다

새벽에 경고 하나가 울렸을 때 담당자가 가장 당황스러운 것은 그 경고가 진짜인지, 어디서 시작됐는지, 무엇부터 손대야 하는지 알 수 없다는 점입니다. 이슈 조사 절차는 그런 순간에 순서대로 따라갈 수 있게 만든 정해진 흐름입니다.

건물 화재 경보가 울리면 먼저 어느 구역인지 확인하고, 실제 연기인지 오작동인지 살피고, 사람을 대피시킨 뒤에야 원인을 조사하는 것과 같습니다. 보안 경고도 먼저 어떤 리소스에서 언제 발생했는지 확인하고, 관련 로그로 실제 위반인지 판단하며, 영향 범위를 가늠한 뒤 조치합니다.

조사 중에는 발견한 사실과 판단을 시간 순서로 적어 두어야 나중에 같은 문제가 다시 생겼을 때 비교할 수 있습니다. 그리고 조치가 끝나면 재발을 막을 규칙이나 탐지 항목을 하나 이상 남기는 것으로 마무리합니다. 정리하면 이슈 조사 절차는 경고 확인, 사실 검증, 영향 범위 파악, 조치, 기록과 재발 방지라는 다섯 단계를 순서대로 밟는 일입니다.

증거 수집

조사에 필요한 로그와 리소스 정보를 모으는 방법을 익힌다

경고를 조사하다 보면 관련 로그를 나중에 찾으려 할 때 이미 보관 기간이 지나 사라졌거나, 리소스가 삭제되어 원래 상태를 알 수 없는 경우가 많습니다. 증거 수집은 조사를 시작하는 시점에 필요한 로그와 리소스 정보를 먼저 확보해 두는 작업입니다.

교통사고가 나면 차량을 옮기기 전에 위치와 파손 상태를 사진으로 남기고 표식을 세워 두는 것과 같습니다. 보안 사고에서도 문제가 된 리소스의 설정과 태그, 관련 계정 정보를 먼저 기록하고, 접근 기록과 흐름 로그를 별도 저장소로 복사해 보관합니다.

로그는 원본이 덮어써지거나 보관 기간이 끝나면 되돌릴 수 없으므로 조사 전에 사본을 떠 두는 것이 중요합니다. 모은 자료에는 언제 누가 무엇을 근거로 확보했는지 함께 적어 두어야 나중에 신뢰할 수 있는 기록이 됩니다. 결국 증거 수집은 리소스 상태와 로그를 조사 초기에 복사해 남기는 일이며, 이 기록이 있어야 원인 판단과 재발 방지가 근거를 갖습니다.

심각 이슈 대응

침해가 의심되는 상황에서 무엇을 먼저 하는지 정리한다

새벽에 중요 데이터가 외부로 빠져나가는 것 같다는 경보가 울렸는데 누가 무엇을 먼저 할지 정해 두지 않았다면, 담당자들은 서로 연락만 주고받다가 대응 시점을 놓치게 됩니다. 그래서 침해가 의심되는 순간의 순서와 역할을 미리 정해 둔 절차가 필요한데, 이것이 심각 이슈 대응(incident response)이며 AWS Security Hub에서는 심각도가 높게 표시된 이슈를 이 절차에 태워 처리합니다.

이는 환자가 실려 오면 접수, 중증도 분류, 처치, 기록의 순서로 움직이는 응급실과 같습니다. 접수 담당이 환자를 받아 어떤 사고인지 확인하듯, 먼저 어떤 계정과 자원이 영향을 받았는지 범위를 확인합니다.

중증도 분류가 생명이 급한 환자부터 보는 일이듯, 여기서도 데이터 유출과 관리자 권한 탈취처럼 피해가 큰 항목을 먼저 판단합니다. 이어서 처치가 상처를 막고 수술실을 준비하듯 감염된 자원을 네트워크에서 떼어 내고 접근 키를 바꾸며, 마지막으로 기록 담당이 차트를 남기듯 로그와 시각을 증거로 보존합니다.

정리하면 심각 이슈 대응은 영향 범위를 확인한 뒤 격리(containment)와 제거(eradication), 복구(recovery)로 이어 가는 절차이며, 그 전 과정을 증거 보존(evidence preservation)과 함께 남기는 일입니다. Security Hub에서 심각도가 높게 표시된 이슈도 이 순서에 따라 처리해야 대응이 흔들리지 않습니다.

이해관계자 커뮤니케이션

상황을 누구에게 어떻게 전달할지 기준을 세운다

윗집 배관이 터져 천장에서 물이 떨어지는데 관리사무소에는 연락했지만 윗집 주인은 모르고 있고 보험사는 아직 아무것도 듣지 못한 상황이라면 피해는 계속 커집니다. 사고 자체보다 누구에게 어떤 말을 언제 전하느냐가 정해지지 않아 생기는 혼란을 막는 일이 이해관계자 커뮤니케이션(stakeholder communication)입니다.

아파트 누수 현장에서는 세 갈래의 말이 동시에 필요합니다. 관리사무소에는 정확한 위치와 밸브 차단 여부를 알려 조치를 맡기고, 입주민에게는 물이 떨어지는 범위와 당장 피해야 할 행동을 짧게 알립니다. 보험사와 수리업체에는 사진과 발생 시각, 지금까지의 조치를 같은 형식으로 전달해 서로 다른 말을 하지 않게 합니다.

대상마다 필요한 정보의 깊이와 시급함이 다르므로, 누가 어떤 경로로 얼마나 자주 알릴지를 미리 정해 두는 것이 핵심입니다.

실제로는 심각도와 영향 범위, 이미 취한 조치, 다음 확인 시각을 한 장의 상황 보고로 정리해 경영진과 법무, 고객 담당에게 같은 내용을 배포하는 방식으로 운영합니다. Security Hub의 이슈 하나를 공통 근거로 삼으면 같은 사실을 서로 다르게 전달하는 일을 줄일 수 있습니다.

사후 분석

같은 문제가 반복되지 않도록 원인을 남기는 방법을 본다

장애를 겨우 수습한 뒤 모두 지쳐 원인을 더 캐지 않고 다음 업무로 넘어가기 쉽습니다. 그러면 몇 달 뒤 같은 원인으로 같은 장애가 다시 터지는데, 그때 왜 그랬는지 설명할 기록이 없는 것이 문제이며 이를 막는 일이 사후 분석(post-incident review)입니다.

이는 사고 차량의 블랙박스 영상과 현장 사진을 모아 원인을 가려내는 일과 비슷합니다. 먼저 사고 시각 전후의 기록을 시간순으로 늘어놓아 언제 무엇이 바뀌었는지 확인하고, 운전자의 착각과 도로 상태처럼 사람 요인과 환경 요인을 나눠 봅니다.

여기서 중요한 것은 누구를 탓할지가 아니라 어떤 조건이 겹쳤을 때 사고가 났는지를 밝히는 일이며, 그래야 같은 조건에서 같은 사고를 피할 수 있습니다. 마지막으로 재발 방지 항목과 담당자, 완료 기한을 적어 두면 기록이 다음 대비책으로 이어집니다.

정리하면 사후 분석은 영향 범위와 탐지 시점, 대응 과정을 시간순으로 남기고 근본 원인(root cause)과 재발 방지 조치를 문서로 확정하는 절차입니다. Security Hub의 이슈 기록은 이때 사건의 출발점을 확인하는 근거로 쓰입니다.

오탐 정리 운영

쌓여 가는 억제 규칙을 주기적으로 손보는 일을 다룬다

자동차 계기판 경고등이 하루에도 몇 번씩 이유 없이 켜지면 처음에는 정비소에 가지만 몇 번 반복하면 습관적으로 무시하게 됩니다. 보안 경보도 마찬가지여서 억제(suppression) 규칙으로 꺼 둔 알림이 계속 쌓이면 정작 진짜 경보가 왔을 때 아무도 보지 않게 되며, 오탐 정리 운영은 이렇게 쌓인 억제 규칙을 주기적으로 점검해 되돌리는 일입니다.

정비소에서 경고등 이력을 하나씩 확인하듯, 어떤 규칙이 어떤 이유로 꺼져 있는지 목록을 만들어 봅니다. 센서 고장처럼 고치면 끝나는 것과 원래 정상 동작인데 소음이 커서 꺼 둔 것은 처리가 다릅니다. 고칠 수 있는 원인은 고치고 정말 필요 없는 알림만 남기며, 억제가 끝나는 시점을 정해 두어 기간이 지나면 다시 켜지게 합니다.

이렇게 하면 경보의 양은 줄면서도 중요한 알림이 묻히지 않습니다.

정리하면 오탐 정리는 억제 규칙마다 사유와 담당자, 만료 시점을 붙이고 주기적으로 다시 평가하는 운영 절차입니다. Security Hub에서는 어떤 컨트롤을 왜 억제했는지 기록을 함께 관리해 판단 근거를 남깁니다.

설정 백업과 복구

Security Hub 설정과 이슈를 잃었을 때 되살리는 방법을 익힌다

휴대폰을 잃어버렸는데 백업을 한 적이 없다면 연락처와 사진을 그대로 잃게 됩니다. 보안 설정도 같아서 Security Hub의 표준, 컨트롤 활성화 상태, 억제해 둔 이슈 기록을 따로 남기지 않으면 계정 설정을 잘못 건드린 날 모든 기준이 처음 상태로 돌아가 버리며, 설정 백업과 복구는 이 상태를 파일과 절차로 남겨 두었다가 되살리는 일입니다.

이는 휴대폰을 새로 살 때 백업 파일로 이전하는 과정과 같습니다.

  • 먼저 무엇을 백업할지 정해야 하는데, 연락처와 사진에 해당하는 것이 표준과 컨트롤 목록, 계정별 활성화 상태, 예외 처리 기록입니다.
  • 다음으로 백업을 어디에 둘지 정하는데, 백업이 클라우드와 컴퓨터에 나뉘어 있듯 설정도 코드나 문서 형태로 저장소에 두고 변경 이력을 함께 남깁니다.
  • 마지막으로 복원을 실제로 한 번 해 보아야 하는데, 백업만 있고 복원 절차를 모르면 없는 것과 같습니다.

정리하면 설정 백업과 복구는 표준과 컨트롤 구성, 예외 기록을 재현 가능한 형태로 보관하고 정해진 절차로 다시 적용하는 일입니다. Security Hub를 여러 계정에 걸쳐 운영한다면 계정별 설정 차이까지 함께 남겨야 복구가 정확해집니다.

설정 변경 관리

표준과 컨트롤 변경을 승인 절차에 태우는 방법을 본다

아파트에서 벽을 허무는 공사를 관리사무소 승인 없이 진행했다가 옆집 배관을 건드려 온 동네가 물을 맞는 일이 있습니다. 보안 설정도 마찬가지여서 표준과 컨트롤을 담당자가 즉흥적으로 껐다 켜면 그 변경이 언제 누구에 의해 왜 있었는지 아무도 모르게 되며, 설정 변경 관리는 이런 변경을 승인 절차에 태워 기록으로 남기는 일입니다.

인테리어 공사 절차와 같습니다.

먼저 무엇을 바꿀지 도면처럼 적어 신청하고, 구조와 소방에 영향이 있는지 검토하는 단계를 거칩니다. 보안에서는 어떤 표준의 어떤 컨트롤을 왜 바꾸는지, 바꾸면 어떤 자원이 영향을 받는지 적는 것이 이 단계입니다. 검토가 끝나면 승인자와 적용 시각을 정해 한 번에 반영하고 문제가 생겼을 때 되돌릴 방법도 함께 준비합니다.

공사가 끝나면 준공 기록을 남기듯 변경 내용과 결과를 남겨 다음 점검의 근거로 씁니다.

정리하면 설정 변경 관리는 표준과 컨트롤 변경을 신청, 검토, 승인, 적용, 기록의 단계로 통제하는 절차입니다. Security Hub의 컨트롤을 끄거나 예외로 두는 일도 같은 절차와 사유 기록을 거쳐야 합니다.

서비스 업데이트 추적

새 컨트롤과 새 표준이 나올 때 대응하는 법을 정리한다

점검 도구를 한 번 설정해 두면 그것으로 끝이라고 생각하기 쉽지만, 실제로는 몇 달 만에 처음 보는 점검 항목이 수십 개씩 생겨나고 그중 무엇이 우리 서비스에 실제로 문제인지 아무도 설명하지 못하는 일이 벌어집니다. 서비스 업데이트 추적은 이런 변화를 미리 확인하고 우리 환경에 필요한 것부터 순서대로 대응하도록 만드는 운영 절차입니다.

아파트 관리사무소에 비유하면, 새로 생긴 점검 항목은 갑자기 바뀐 소방 점검 기준이고 새 기준 묶음은 관리 규약의 개정판에 해당합니다.

관리사무소가 개정 공고문을 게시판에 붙이고 세대별로 우리 집에 해당하는 조항만 표시해 두면, 입주민은 무엇을 언제까지 고쳐야 하는지 헷갈리지 않습니다. 업데이트 추적도 같은 방식으로 새로 나온 항목을 공지에서 확인하고, 이미 쓰는 설정과 견주어 영향받는 부분만 골라 담당자와 마감 시점을 정합니다. 여기에 새 항목을 바로 켤지, 먼저 시험용 계정에서만 켤지 판단하는 일이 더해집니다.

정리하면 서비스 업데이트 추적은 변경 공지(release note)를 주기적으로 확인하고, 새 컨트롤(control, 점검 항목)과 새 표준(standard, 점검 항목 묶음)이 우리 환경에 미치는 영향을 판단해 적용 시점을 정하는 운영 활동입니다. 자동으로 전부 켜기보다 확인과 판단을 먼저 두는 것이 핵심입니다.

운영 지표 만들기

우리 조직의 보안 운영 성과를 수치로 보는 방법을 다룬다

보안 사고가 없었다는 사실만으로는 우리가 일을 잘하고 있는지 알 수 없어서, 경영진에 보고할 때마다 "그래서 얼마나 좋아졌느냐"는 질문에 답하지 못합니다. 운영 지표는 이런 막연함을 숫자로 바꿔 보안 운영의 성과와 추세를 보여 주는 수단입니다.

건강검진에 비유하면 지표는 혈압과 혈당처럼 매번 같은 방식으로 재는 측정 항목이고, 한 번의 수치보다 몇 달치 흐름이 몸 상태를 더 정확히 말해 줍니다. 검진 항목을 너무 많이 잡으면 해석이 어려우므로 우리 몸에 중요한 몇 개만 골라야 하고, 재는 시점과 방법도 매번 같아야 비교가 됩니다.

보안 운영에서도 미해결 점검 결과(Finding)의 평균 해결 시간, 고위험 항목의 잔여 건수, 자동으로 교정된 비율 같은 몇 가지를 정해 같은 주기로 기록합니다. 여기에 목표선을 그어 두면 지금 상태가 나쁜지 좋은지가 한눈에 보입니다.

결국 운영 지표는 반복해서 재는 측정 항목과 목표선, 그리고 시간에 따른 추세선으로 구성되며, 보안 운영의 성과를 조직 안에서 설명하는 공통 언어가 됩니다.

Security Hub 과금 구조

무엇에 얼마를 내는지 항목별로 이해한다

보안 점검 서비스를 켜 두기만 했는데 월말 청구서에 예상하지 못한 금액이 찍혀 당황하는 일이 흔합니다. 과금 구조를 항목별로 알아 두면 무엇이 비용을 만드는지 미리 가늠할 수 있습니다.

아파트 관리비에 비유하면 기본 관리비와 세대별 사용량이 따로 붙는 구조와 비슷합니다. 먼저 실제로 검사한 양, 즉 점검 대상 자원의 수와 평가한 횟수에 따라 붙는 사용료가 있고, 여기에 여러 계정을 묶어 관리하는 기능이나 추가로 켠 기능의 요금이 더해집니다.

관리비에서 공용 전기료와 개별 수도요금이 따로 계산되듯, 어떤 표준(standard)을 켰는지와 몇 개 리전(region, 데이터센터 묶음)에서 도는지가 총액을 크게 바꿉니다. 무료로 제공되는 범위가 정해져 있는 경우도 있어 그 한도를 넘는 순간부터 요금이 발생합니다.

정리하면 Security Hub의 요금은 평가한 양을 기준으로 하는 사용료와 기능 및 범위 선택에 따른 추가 요금이 합쳐진 구조이며, 세부 단가는 시점에 따라 달라질 수 있으므로 공식 요금표를 확인해야 합니다.

비용을 줄이는 설정

평가 범위·리전·표준 선택으로 비용을 조정하는 방법을 본다

점검을 넓게 켜 둘수록 안심되지만, 쓰지 않는 계정과 리전까지 모두 평가하면 청구서만 커집니다. 평가 범위와 리전, 표준 선택을 조정하면 보안 수준을 크게 떨어뜨리지 않고 비용을 줄일 수 있습니다.

아파트 단지 방범 순찰에 비유하면 모든 동을 하루 종일 도는 대신 출입구와 주차장처럼 중요한 구역을 정해 횟수를 정하는 것과 같습니다. 순찰 구역을 정하는 일이 평가할 계정과 리전을 고르는 일이고, 순찰 횟수를 정하는 일이 점검 주기를 정하는 일입니다.

여기에 꼭 필요한 표준만 켜고, 이미 다른 도구가 보고 있는 항목은 중복해서 켜지 않으면 같은 안전을 훨씬 적은 비용으로 얻습니다. 다만 범위를 줄일 때는 왜 뺐는지를 기록해 두어야 나중에 사각지대가 생겼는지 확인할 수 있습니다.

실제로는 평가 대상 계정과 리전을 추리고, 필요한 표준만 선택하며, 중복 점검을 정리하는 세 가지 조정이 비용 절감의 중심입니다.

비용 모니터링

예상치 못한 청구를 빨리 알아차리는 방법을 익힌다

사용량은 조용히 늘어나는 경우가 많아서 청구서를 월말에 처음 보면 이미 늦어 있습니다. 비용 모니터링은 평소와 다른 지출을 일찍 감지해 원인을 확인할 시간을 벌어 주는 활동입니다.

집의 수도 계량기에 비유하면 매달 같은 양이 나오다가 갑자기 두 배가 되면 어딘가 새고 있다는 신호입니다. 평소 사용량을 기준선으로 잡아 두고 그 선을 넘을 때 알림을 받도록 해 두면, 청구서가 오기 전에 이상을 알아차립니다.

여기에 예산 한도를 정해 두고 그 비율에 도달할 때마다 경고를 받는 방식과, 계정과 리전별로 사용량이 튀는 곳을 찾아보는 방식이 함께 쓰입니다. 알림을 받은 뒤에는 새로 켠 표준이나 새로 추가된 계정처럼 최근 변경을 먼저 확인합니다.

정리하면 기준선과 예산 한도, 그리고 변경 이력 확인이라는 세 가지로 예상치 못한 청구를 빠르게 잡아냅니다.

Security Hub의 한계

이 서비스가 하지 못하는 일을 알고 다른 도구와 나누는 법을 다룬다

Security Hub를 켜면 모든 보안 문제가 해결될 것처럼 기대하지만, 실제로는 점검 결과를 모아 보여 줄 뿐 침입을 막거나 사고를 직접 수습하지는 못합니다. 이 서비스가 하지 못하는 일을 알고 다른 도구와 역할을 나누는 것이 안전한 운영의 출발점입니다.

건강검진 결과지에 비유하면 수치는 알려 주지만 약을 처방하거나 수술을 하지는 않습니다. 결과지에 이상이 찍혀도 병원에 가서 진료를 받아야 하듯, 여기서 찾은 항목은 교정 작업이나 대응 도구로 이어져야 실제 위험이 줄어듭니다.

또 결과지는 검진 항목 안에서만 판단하므로 검사하지 않는 영역은 아무리 위험해도 결과지에 나오지 않습니다. 실시간으로 오가는 트래픽을 막는 일은 방화벽이나 침입 차단 도구가, 로그를 오래 보관하고 분석하는 일은 별도 수집 도구가 맡습니다.

결국 Security Hub는 점검과 집계를 담당하는 허브이고 차단과 탐지, 대응은 다른 계층이 맡으며, 이 경계를 문서로 남겨 두는 것이 중요합니다.

로그·데이터 보관 전략

이슈와 로그를 얼마나 오래 둘지 결정한다

장애나 침해가 터진 지 석 달 뒤에야 그때 무슨 일이 있었는지 확인해야 하는 상황이 있습니다. 그때 로그를 일주일치만 남겨 두었다면 원인은 영원히 확인할 수 없고, 그래서 로그와 데이터를 얼마나 오래 둘지 미리 정하는 보관 전략이 필요합니다.

이 일은 택배 회사의 창고 운영과 비슷합니다. 모든 택배를 무한정 쌓아 두면 창고 임대료가 감당이 안 되고, 반대로 하루치만 두면 분실 사고가 났을 때 확인할 물건이 없습니다. 그래서 물건마다 성격에 따라 보관 기간을 다르게 정해 두는데, 계약서 같은 중요 서류는 길게 두고 지나가는 일반 화물은 짧게 두는 식입니다.

Security Hub 에서도 로그를 보내는 AWS 서비스마다 남기는 기간과 저장 위치를 정해 두고, 오래 볼 필요가 없는 것은 줄이고 감사에 필요한 것은 변경이 막힌 보관 저장소로 옮깁니다.

정리하면 로그 보관 전략은 수집한 보안 이벤트와 로그를 목적과 규정에 맞춰 기간·위치·접근 권한으로 나눠 두는 정책이며, Security Hub 는 그 판단에 필요한 발견 항목을 한곳에 모아 주는 역할을 합니다.

규정 준수 보고

감사 때 낼 자료를 만드는 방법을 정리한다

감사인이 특정 기간의 접근 기록과 조치 이력을 달라고 하는데, 담당자가 팀마다 흩어진 화면을 캡처해 붙이느라 몇 주를 쓰는 일이 생깁니다. 그렇게 급히 모은 자료는 빠지는 항목이 생기기 쉽고, 그래서 감사에 낼 자료를 같은 형식으로 계속 만들어 두는 규정 준수 보고가 필요합니다.

이 일은 아파트 관리사무소의 점검 일지와 비슷합니다. 매달 소방 설비와 승강기를 점검하고 그 결과를 정해진 양식에 적어 두면, 연말에 구청 점검이 나와도 서랍에서 일지 묶음만 꺼내면 됩니다. 반대로 점검은 했지만 아무 데도 적지 않았다면 그 사실을 증명할 방법이 없습니다.

Security Hub 의 보안 표준은 통제 항목별로 통과 여부를 계속 기록하므로, 보고서를 만드는 일은 그 기록을 기간과 범위로 잘라 내보내는 일이 됩니다.

결국 규정 준수 보고는 프레임워크별 통제 항목에 대한 증적을 평소에 쌓아 두고 감사 시점에 꺼내 쓰는 체계이며, Security Hub 의 표준 평가 결과가 그 증적의 바탕이 됩니다.

다른 클라우드·온프레미스 연계

AWS 밖 자산을 같은 체계로 함께 보는 방법을 본다

회사가 AWS 만 쓰면 좋겠지만, 인수한 회사의 서버는 다른 클라우드에 있고 오래된 업무 시스템은 사무실 전산실에 남아 있는 경우가 흔합니다. 이 자산들을 따로따로 들여다보면 정작 위험한 곳이 사각지대에 남기 때문에, AWS 밖 자산까지 같은 체계로 함께 보는 연계가 필요합니다.

이 상황은 지점이 여러 곳인 매장의 관제실과 비슷합니다. 각 지점에 폐쇄회로 카메라를 따로 설치하고 지점장이 자기 화면만 보면, 폐점 후 침입 같은 일은 아무도 통합해 보지 못합니다. 그래서 지점의 영상을 본사 관제센터로 모아 같은 화면과 같은 규칙으로 보게 만듭니다.

연계도 마찬가지로, 다른 클라우드나 온프레미스에서 나오는 발견 항목을 공통 형식으로 변환해 Security Hub 로 보내면 하나의 목록에서 함께 조회하고 우선순위를 매길 수 있습니다.

정리하면 연계는 서로 다른 환경의 보안 신호를 공통 형식으로 모아 단일 화면에서 관리하는 일이며, AWS 밖 자산도 같은 기준으로 평가하고 대응하기 위한 토대입니다.

보안 운영 성숙도

단계별로 지금 무엇을 하고 다음에 무엇을 할지 정한다

보안팀이 매일 경보에 쫓기며 불을 끄듯 대응하다 보면, 지금 잘하고 있는지 어디가 약한지 판단할 여유가 없습니다. 그래서 단계를 나눠 현재 위치를 확인하고 다음에 무엇을 할지 정하는 보안 운영 성숙도 모델이 쓰입니다.

이것은 태권도 급수를 올리는 과정과 비슷합니다. 흰 띠가 기본 동작을 익히고, 다음 단계에서 겨루기와 품새를 더하며, 각 단계마다 통과해야 할 과제가 정해져 있습니다. 급수를 건너뛰고 어려운 기술부터 배우면 다치기 쉽고, 반대로 자기 급수를 모르면 연습 방향을 잡지 못합니다.

성숙도도 비슷하게, 발견 항목 수집과 자동 대응, 사고 대응 절차, 지표 측정 같은 역량을 단계로 나누고 지금 단계에서 갖춰야 할 것을 먼저 채웁니다. Security Hub 는 그 단계를 판단할 때 참고할 점수와 추세를 제공하는 도구입니다.

결국 보안 운영 성숙도는 사람·절차·도구의 역량을 단계로 정의하고 현재 수준을 진단해 다음 투자 순서를 정하는 관리 방법입니다.

흔한 실패 사례

켜놓고도 아무도 보지 않는 상태가 되는 이유를 짚는다

Security Hub 를 켜고 보안 표준을 활성화한 뒤 발견 항목이 수천 건 쌓였는데, 몇 주 뒤에는 아무도 그 화면을 열지 않는 상태가 됩니다. 도구는 켜져 있지만 운영은 멈춘 셈이고, 이런 일이 생기는 이유를 아는 것이 실제 효과를 내는 출발점입니다.

이 상황은 건물마다 화재경보기를 달아 놓고 경보가 울려도 출동 절차가 없는 경우와 같습니다. 경보가 하루에도 몇 번씩 오작동하면 사람들은 결국 소리를 무시하게 되고, 진짜 불이 났을 때도 늦게 알아차립니다. 또 경보를 단 사람과 관리할 사람이 따로 있으면 아무도 책임을 지지 않습니다.

실패의 공통점은 심각도 분류와 담당자 지정, 예외 처리 기준이 없어 경보가 쌓이기만 한다는 점이며, 자동 대응이나 티켓 연동 없이 화면만 두는 것도 같은 결과로 이어집니다.

정리하면 대부분의 실패는 기능 부족이 아니라 발견 항목을 처리할 절차와 주인이 없다는 데서 오며, 켜는 일보다 걸러 내고 배정하고 닫는 흐름을 먼저 정해야 합니다.

Security Hub 학습 로드맵

지금까지 배운 것을 순서대로 다시 밟는 복습 계획을 세운다

이 과정을 처음부터 끝까지 한 번 읽고 나면 많은 개념이 머리에 남지만, 실제 화면 앞에 섰을 때 어디서부터 손대야 할지 막막해지기 쉽습니다. 그래서 배운 것을 순서대로 다시 밟는 복습 계획이 필요합니다.

이것은 운전면허를 딴 뒤 도로에 나가는 과정과 비슷합니다. 먼저 차의 기본 조작과 표지판을 익히고, 좁은 골목에서 주차를 연습한 다음, 마지막에 실제 도로를 달립니다. 순서를 바꿔 고속도로부터 나가면 두려움만 커지고 실력은 늘지 않습니다.

학습도 같은 순서로, 먼저 Security Hub 가 무엇을 모으고 무엇을 평가하는지 큰 그림을 잡고, 다음으로 표준과 통제 항목, 발견 항목의 구조를 익힌 뒤, 자동 대응과 다른 서비스 연계, 보고와 보관 전략으로 넓혀 갑니다.

결국 학습 로드맵은 개념, 설정, 자동화, 운영, 확장이라는 층을 순서대로 다시 통과하며 손으로 확인하는 계획이며, 각 단계에서 작은 점검 하나씩을 직접 해 보는 것이 핵심입니다.
