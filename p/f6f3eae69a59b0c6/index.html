인터프리터를 실행하는 방법과 명령행 옵션

python 명령으로 파이썬 소스나 스크립트를 실행하고, -c·-i·해시bang 같은 명령행 옵션으로 실행 방식을 지정하는 방법.

#1문제 상황

C언어나 Java로 만든 프로그램은 컴파일러가 소스 코드를 기계어로 바꿔 exe 같은 실행 파일을 만든 뒤 그 파일을 돌린다. 그래서 소스를 고칠 때마다 다시 빌드해야 하고, 코드를 한 줄씩 바꿔 가며 시험해 볼 수 없다. 파이썬은 컴파일 단계가 없다. 인터프리터(소스 코드를 직접 읽고 실행하는 프로그램)가 코드를 읽는 즉시 계산해 결과만 내놓는 방식이다. 덕분에 실행은 쉬워졌지만, 어떤 코드를 어떻게 돌릴지 지정하는 방법이 없으면 매번 편집기에 저장하고 터미널로 옮기는 반복이 그대로 남는다.

#2핵심 질문

소스 코드를 인터프리터에 넘겼을 때 실행 방식과 옵션을 어떻게 지정해야 결과만 바로 확인할 수 있는가?

#3동작 예시

터미널에서 python myscript.py 를 치면 인터프리터가 myscript.py 파일을 열어 위에서부터 한 줄씩 읽어 실행하고, 표준 출력으로 나온 결과가 그대로 화면에 찍힌다. 이때 인터프리터는 명령행 인자(command line argument, 프로그램 실행 시 명령줄에서 함께 넣어 주는 값)와 환경 변수(환경 변수)를 함께 훑어 프로그램 자신의 설정을 읽는다. 화면에는 파일 안에서 print()한 내용만 나타나고, 인터프리터의 작업 과정은 드러나지 않는다.

#4동작 과정

  1. 옵션과 대상 지정명령줄은 python [-bBdEhiIOPqRsSuvVWx?] [-c command | -m module-name | script | -] [args] 형태로 파싱된다. -c 는 문자열로 준 식을, -m 은 모듈을, 이름 없이 준 인자는 해당 파일을 실행 대상으로 삼는다. 대상이 무엇인지 명시적이므로 같은 명령줄에서도 매번 다른 프로그램이 뜬다.
  2. 코드 읽고 실행인터프리터가 소스를 한 줄씩 읽어 계산하고, 표준 출력에 나온 값만 사용자에게 보인다. 빌드 산출물이 없으므로 수정 후 곧바로 다시 실행하면 결과가 바뀐다.
  3. 대화형 유지-i 옵션을 주면 실행 대상을 처리한 뒤 입력을 기다리는 대화형 상태로 남는다. 마지막 결과를 바로 이어서 만질 수 있어 시험 삼아 보기 편해진다.
  4. 확인해 볼 것같은 파일을 python myscript.py 로 한 번, python -c "print(1+1)" 로 한 번 돌려 터미널에 어떤 내용이 뜨는지 비교한다.

#1문제 상황

라이브러리의 함수 이름을 알지 못하면 소스 파일을 어디까지 읽어야 그 함수가 있는지도 모르고, 매번 검색을 거쳐야 했다. 그리고 함수가 뭘 하는지는 소스 코드를 직접 읽어야 알 수 있었다. 문제는 문서가 코드에서 떨어져 있어 찾는 비용이 크고, 설명이 함수마다 형식이 제각각이라는 점이었다. pydoc(파이썬 객체의 설명문을 자동으로 모아 화면에 내보내는 도구)은 객체 안에 이미 들어 있는 설명문(docstring, 모듈·클래스·함수 바로 아래에 쓰는 설명 텍스트)을 읽어 이 문제를 대신 해결한다.

#2핵심 질문

설치된 파이썬의 어떤 객체가든 사용법과 설명을 화면 한 곳에서 즉시 꺼내 볼 수 있는가?

#3동작 예시

help() 를 쳐도 되고 help(sys) 처럼 객체를 넘겨도 된다. 그러면 그 객체의 docstring과 내부 구성원(멤버)의 docstring을 모둬 재귀적으로 찾아 콘솔에 텍스트 문서로 출력한다. docstring이 없으면 그 위의 주석 줄에서 설명을 얻어 온다. 같은 텍스트는 인터프리터 밖에서도 python -m pydoc sys 로 볼 수 있고, HTML 파일로 저장하거나 브라우저에 띄울 수도 있다.

#4동작 과정

  1. 설명문 수집pydoc이 모듈·클래스·함수·메서드의 docstring을 읽고, 설명문이 없으면 소스에서 바로 위 주석 줄을 대신 쓴다. 설명을 어디에 써도 문서가 비지 않는다.
  2. 멤버까지 재귀 전개하나의 객체에서 시작해 그 안의 구성원 설명문까지 차례로 합친다. 전체 구조를 한 화면에서 따라갈 수 있어 이름을 모르는 메서드도 발견된다.
  3. 출력 방식 선택대화형 셸의 help() 로 콘솔에 바로 띄우거나, python -m pydoc <모듈> 로 실행해 터미널에서 본다. 필요한 경우 HTML로 저장해 브라우저에서 볼 수도 있다.
  4. 확인해 볼 것대화형 셸에서 help(list) 를 치면 화면에 list 의 설명과 append·sort 같은 메서드 설명이 함께 나열되는지 본다.

#1문제 상황

부동소수점 수(floating-point, 컴퓨터가 소수점을 이진수로 근사해 저장하는 수)는 하드웨어에서 이진 분수로 표현된다. 십진 소수 중에는 이진 분수로 정확히 나타낼 수 없는 것이 많다. 그래서 0.1 을 더하고 빼면 원래 값으로 돌아오지 않고 0.0 이 안 나오며, 결과의 마지막 자리가 어긋난다. 금액이나 비율을 누적해 계산하는 코드에서는 이 어긋남이 결과 전체를 틀리게 만들고, 틀린 값을 어디서 생겼는지 찾기 어렵다. 오차가 작은 실수 대신 정확한 십진 연산과 분수 연산을 직접 선택할 수 있어야 이 문제를 피할 수 있다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 오차가 생기는 지점0.625 같은 값은 6/10 + 2/100 + 5/1000 으로 쓰이지만 이진 표기로는 1/2 + 0/4 + 1/8 이 된다. 값 자체는 같지만 십진 소수 대부분을 이진 분수로 정확히 옮길 수 없어 저장 시 근사가 발생한다.
  2. 정확한 십진으로 전환decimal 모듈의 Decimal 은 고정소수점(fixed-point) 방식으로 소수 자릿수를 그대로 유지해 계산한다. 문자열로 값을 넣어야 근사가 일어나지 않는다.
  3. 분수로 표현fractions 모듈의 Fraction 은 유리수(분자·분모로 나타낼 수 있는 수)를 분자와 분모로 분리해 보관한다. 결과가 1/3 이나 2/3 으로 정확히 표현되며 나눗셈도 오차 없이 이어진다.
  4. 확인해 볼 것대화형 셸에서 0.1 + 0.2 == 0.3 을 쳐 False 가 나오고, 같은 값으로 Decimal 을 만들어 비교하면 True 가 오는지 확인한다.

if·elif 를 값의 종류마다 늘어놓으면 같은 값을 여러 번 씻게 되고, 리스트나 딕셔너리처럼 구조가 들어 있는 값은 비교가 단계마다 늘어선다. → 02-01 의 if 체인은 조건 하나당 분기 하나를 붙이는 방식이라 경우의 수가 늘면 들여쓰기와 조건식이 계속 길어진다. 비교문(match statement)은 한 번만 값을 꺼내 놓고 패턴(구조에 어긋나는지 비교하는 규칙)만 나열하게 해, 값의 종류와 속 구조를 한 묶음으로 갈라 분기한다.

#2핵심 질문

값의 종류와 내부 구조를 한 번에 비교해 분기하면서 같은 값을 조건마다 반복해서 적지 않게 하려면 어떻게 해야 하는가?

#3동작 예시

match value: 아래에 case 0: 을 두면 값이 0일 때만 그 블록을 실행하고, case [x, y]: 는 길이 2인 시퀀스인지 확인해 두 원소를 x 와 y 에 동시에 담는다. 그 외에는 case _: 가 나머지를 모두 받는다. 일치하는 case 는 여러 개를 나열해도 하나만 실행되며, 아래 case 들은 검사하지 않는다.

#4동작 과정

  1. 대상을 한 번만 비교match 문이 대상 값을 한 번 평가해 첫 번째로 일치하는 case 의 블록을 실행한다. if 체인처럼 위에서부터 조건을 다시 계산하는 일이 없다.
  2. 패턴으로 구조까지 확인case 뒤에는 값 하나, 시퀀스, 매핑, 클래스 인스턴스 구조가 올 수 있고, 필요하면 값도 묶어 받아낸다. case [x, y] 는 두 원소를 동시에 꺼내므로 원소를 하나씩 꺼내는 if 분기가 줄어든다.
  3. 가드와 기본 분기각 case 뒤에 if 조건 형태의 가드를 붙여 패턴은 맞지만 값이 추가로 만족해야 할 때를 좁히고, case _: 가 어떤 패턴에도 걸리지 않는 나머지를 받는다. → 02-01 의 else 와 같은 자리다.
  4. 확인해 볼 것match [1, 2]: 에 case [x, y]: print(x, y) 를 두고 실행해 1 2 가 찍히고, 값이 [1, 2, 3] 일 때는 case _ 로 넘어가는지 본다.

프로그램이 조금 길어지면 같은 계산이 여러 자리에 반복되고, 값이 바뀔 때마다 같은 코드를 고쳐야 합니다. 이를 반복 문으로 감싸면 값만 바꾸고 계산은 하나만 두는 것까지는 되지만, 그래도 그 계산이 필요할 때마다 호출하는 방법이 따로 필요했습니다.

Compound statement(다른 문장들을 묶어 하나의 실행 단위로 만드는 문장)이 없으면 조건문과 반복문, 예외 처리, 함수·클래스 정의를 같은 규칙으로 묶어쓸 수 없습니다. Python 에서는 def 함수 정의도 compound statement 의 하나로 정의되며, if·while·for 와 같은 제어 흐름 구문이 같은 범주에 속합니다.

  1. 정의 시 인자 표 만들기def 문을 만나면 파라미터 이름과 기본값을 표로 만들어 함수 객체에 붙입니다. 기본값이 있는 파라미터는 그 뒤에 기본값 없는 파라미터가 올 수 없습니다.
  2. 호출 시 값 연결하기위치를 그대로 맞춘 인자는 위치 인자로, 이름을 붙여 준 인자는 키워드 인자로 받습니다. 이름이 다른 키워드 인자가 오면 실행 전에 TypeError 로 걸러집니다.
  3. 남는 인자 모으기*args(위치 인자 나머지)를 붙이면 넘긴 값이 튜플로, **kwargs(키워드 인자 나머지)를 붙이면 딕셔너리로 묶입니다. 이후 이 함수 안에서 다시 이름을 붙여 호출할 때 그대로 전달할 수 있습니다.

  3. finally 로 정리 코드를 고정하기finally: 블록은 try 안에서 오류가 나도 안 나도 반드시 마지막에 실행된다. 파일 닫기나 임시 파일 지우기처럼 남으면 곤란한 일을 여기에 둔다. 정리 코드에서 다시 오류가 나면 그 오류가 원래 오류를 대신해 위로 올라간다.
  4. 오류를 다시 위로 보내기원인만 알리고 싶으면 raise 로 현재 예외를 그대로 다시 던지거나, raise NewError(...) 로 더 구체적인 예외를 만들어 밖에서 처리하게 할 수 있다.

#1문제 상황

except 뒤에 아무것도 적지 않으면 모든 오류가 한 묶음으로 잡히고, 적어도 이름을 댄다고 해서 그 오류만 잡히는 것도 아니다. 파이썬의 예외 계층(exception hierarchy, 모든 예외가 상위 예외 아래 묶인 트리 구조)은 실제 타입이 아니라 그 타입이 상속된 부모 타입을 보고 같은 것으로 취급하기 때문이다. 즉 어떤 종류의 오류인지 구분하는 기준이 따로 없고, 처리기가 무엇을 잡을지 문서만 봐서는 알기 어렵다. 대부분은 아무것도 안 적으면 모든 오류가 함께 처리된다는 사실조차 모른다.

#2핵심 질문

수많은 예외를 분류된 트리 구조로 두어, 처리기가 원하는 종류만 골라 잡고 나머지는 그대로 위아래로 흐르게 할 수 있는가?

#3동작 예시

except IOError 처럼 파일 관련 오류를 잡는 코드가 있다고 하자. 이 오류는 OSError(파일 없음, 권한 없음 등 운영 체제 호출 실패) 아래에서 파생되어 있어, 이 except 절은 OSError 로 직접 잡든 그 자손인 FileNotFoundError 로 잡든 모두 처리한다. 반대로 이름만 같아도 상속 관계가 아니라면 같은 것으로 보지 않는다. 실행해 보면 없는 파일을 연 블록에서 except IOError 로 받은 변수에 들어 있는 오류가 파일 없음인지 권한 없음인지에 따라 달라지는 것을 볼 수 있다.

#4동작 과정

  1. 최상위 BaseException 에서 계층이 갈라진다모든 예외는 BaseException 아래로 모이며, 파이썬이 프로그램 흐름을 끊는 KeyboardInterrupt 과 SystemExit 는 BaseException 에서 직접 갈라져 예외 처리에 잡히지 않는다.
  2. 표준 예외 Exception 아래에 구체 종류가 붙는다ValueError, TypeError, ZeroDivisionError 같은 일상적인 오류와, OSError 아래의 FileNotFoundError, PermissionError 같은 세부 종류가 계층을 이룬다. 각 예외는 상세 원인을 담은 값("associated value")을 함께 갖는다.
  3. except 절은 상위 이름을 적으면 하위도 함께 받는다즉 except Exception: 은 Exception 아래 전부를 처리하고, 개발 중에는 처리기가 너무 넓어 버그까지 숨기는 일이 생기니 구체적인 이름부터 적는 편이 낫다.
  4. raise 로 원하는 예외를 직접 만든다내 코드에서 오류 조건을 점검했다면 내장 예외를 그대로 raise 할 수 있고, Exception 의 자손을 만들어 자기만의 예외 타입으로 알릴 수도 있다.
  5. 확인해 볼 것없는 파일을 열고 except Exception as e: 로 받은 뒤 print(type(e).__name__) 을 실행하면 FileNotFoundError 가 찍히고, 예외가 계층을 따라 잡혔음을 확인할 수 있다.

예외 계층은 모든 예외를 상위 예외 아래 묶은 분류 트리라, 처리기가 상위 이름을 적으면 그 아래 오류까지 한 번에 처리할 수 있게 해 줍니다.

먼저 알아야 할 것 05-01 try-except-finally 로 예외 처리하기

#1문제 상황

자원은 사용을 시작한 쪽이 정확히 같은 위치에서 되돌려야 하는데, 파이썬은 열기를 forgot 하는 관용구가 따로 없다. 파일을 열고 중간에서 오류가 나면 닫는 줄까지 도달하지 못해 파일 핸들이 남고, 잠금이나 네트워크 연결을 쓴 코드도 같은 방식으로 새어 나간다. → 05-01 의 try-except-finally 로 이를 막을 수는 있지만, 그래도 블록이 몇 겹으로 중첩되고 자원을 여는 문장과 사용하는 문장이 흩어져 읽는 사람이 마지막에 닫았는지 끝까지 눈으로 확인해야 한다. 문제는 정리가 코드의 형태에 달려 있다는 점이다.

#2핵심 질문

자원 해제를 블록의 끝에 자동으로 묶어 두어, 중간에 오류가 나도 예외 없이 빠진 자리에서 반드시 돌아오게 만들 수 있는가?

#3동작 예시

with open(path) as f: 한 줄을 쓰면 파일이 열린 채로 블록 안의 코드만 실행되고, 블록을 벗어나는 순간 파일이 닫힌다. 파일을 다시 읽으려 하거나 삭으려 해도 이미 닫힌 파일이므로 오류가 나지 않고, 블록 안에서 일부러 오류를 낸 경우에도 같은 시점에 닫힌다. 실행해 보면 블록 밖에서 f.closed 를 찍으면 True 가 나온다.

#4동작 과정

  1. __enter__ 로 들어가기with 문은 대상 객체의 __enter__ 를 호출해 그것이 반환한 값을 as 뒤의 이름에 붙인다. 기본 반환값은 self 이다.
  2. 블록을 실행하고 __exit__ 로 나오기블록이 끝나거나 블록 안에서 예외가 나거나 Ctrl+C 로 중단돼도 __exit__ 가 반드시 호출된다. 여기서 자원을 닫고, 예외를 그대로 전파할지(참을지) 결정할 수 있어 try-finally 를 대신한다.
  3. contextlib 도구로 만들기@contextlib.contextmanager 장식자를 붙인 제너레이터 함수나 contextlib.suppress 처럼 이미 만들어 둔 도구를 쓰면, 직접 __enter__/__exit__ 를 작성하지 않아도 with 에 쓸 수 있다. 비동기 버전은 __aenter__/__aexit__ 를 사용한다.
  4. 확인해 볼 것with open(...) as f: 블록 안에서 일부러 오류를 한 번 발생시키고, 블록 바깥에서 print(f.closed) 를 실행해 오류가 났는데도 True 가 찍히는지 본다.

#5한 줄 요약

with 문은 자원을 여는 동작과 반드시 되돌리는 동작을 __enter__/__exit__ 에 묶어 블록이 끝나면 자동 정리되게 하는 문장 구조입니다.

#1문제 상황

버그는 예외가 아니라 조용한 잘못된 결과로 나타나는 경우가 많다. 잘못된 값을 넣었는데도 실행은 그대로 끝나고, 그 잘못된 값이 어디에도 드러나지 않은 채 나중에 엉뚱한 곳에서 문제를 일으킨다. 값을 검증하는 코드를 넣더라도 오류로 바꾸면 정상적인 배치 실행이 멈추고, 그냥 두면 검사가 되지 않는다. 문제는 실행 중 문제를 알아챌 시점과, 그것을 오류가 아닌 알림으로만 남길지의 선택지가 없다는 점이다.

#2핵심 질문

코드가 가정하고 있는 조건이 코드 안에서 드러나게 드러나도록 실패를 즉시 알리고, 아직 오류는 아니지만 문제가 될 상황은 실행 중에 통지받을 수 있는가?

#3동작 예시

파일이 있어야 하는데 없다면 실행을 멈춰야 하는 경우, 그 조건을 assert os.path.exists(path), "입력 파일이 없습니다" 로 적어 둔다. 조건이 거짓이면 AssertionError 가 발생해 해당 지점에서 프로그램이 멈추고 메시지가 함께 출력된다. 그리고 오래된 모듈을 쓰고 싶을 때는 warnings.warn(...) 로 알린다. 이 경고는 기본적으로 표준 오류 출력에 글자로만 남고 프로그램은 계속 돌아 화면에서 메시지가 보이면서 나머지 코드도 실행된다.

#4동작 과정

  1. assert 로 조건을 검증하기assert 조건, 메시지 는 조건이 거짓일 때 AssertionError 를 던져 즉시 중단한다. 파이썬을 최적화 모드(-O)로 실행하면 assert 문 자체가 제거되므로, 나중에 사라질 값을 반드시 검증하는 용도로는 쓰지 않는다.
  2. warnings.warn() 으로 알리기warn() 은 오래된 모듈 사용처럼 아직 오류는 아닌 상황을 표준 오류로 알린다. 프로그램은 멈추지 않는다.
  3. 카테고리·필터로 통제하기경고는 UserWarning·DeprecationWarning 같은 카테고리와 메시지, 발생 위치에 따라 무시, 표시, 예외로 올리기 중 하나를 고른다. 같은 위치에서 반복된 경고는 보통 한 번만 보인다.
  4. 확인해 볼 것터미널에서 python -W error -c "import warnings; warnings.warn('x')" 를 실행하면 같은 코드가 그냥 메시지만 남는 것보다 예외로 바뀌어 멈추는지 비교해 본다.

#1문제 상황

관련된 데이터를 각각 따로 다루던 방식에서는, 데이터와 그 데이터를 다루는 동작이 떨어져 있어 함께 옮기고 재사용하기 어렵다. 함수가 여러 개를 인자로 받아 건네면 호출할 때마다 순서를 맞춰야 하고, 항목이 늘면 무엇을 넣을지 순서를 외워야 한다. 딕셔너리에 아무 키나 넣는 방법도 있지만, 키 이름에 오타가 있어도 실행은 되고 결과만 조용히 틀어진다. 문제는 데이터와 그에 대한 규칙이 언어 차원에서 하나의 덩어리로 묶이지 않는다는 점이다.

직사각형의 너비와 높이를 다룰 때, class Rect: 안에 self.width, self.height 를 넣고 area() 메서드를 정의한 뒤 Rect(3, 4) 를 호출하면 너비와 높이가 정해진 객체 하나가 나온다. 이 객체에 r.width = 5 라고 값을 바꾸면 area() 를 다시 부를 때 새 값이 반영된다. → 05-01 에서 본 변수 하나로는 형태가 달라지면 모든 사용처를 고쳐야 했던 것과 달리, 여기서는 객체 종류를 늘리는 쪽으로 확장한다.

#4동작 과정

  1. class 문으로 클래스를 정의하기클래스(class)는 데이터와 기능을 하나로 묶어 정의하며, 새로운 타입을 만들어 그 타입의 인스턴스를 찍어 내게 한다. 파이썬의 클래스 문법은 다른 언어보다 짧고, 최소한의 새 문법과 의미만 추가한 형태다.
  2. __init__ 로 초기화하기인스턴스가 만들어질 때 호출되어 self 인자로 자기 자신과 함께 받은 값을 인스턴스 속성(attribute)으로 붙인다.
  3. self 를 첫 인자로 메서드 정의하기메서드는 인스턴스를 첫 인자로 받아 그 인스턴스의 속성을 읽고 바꾼다. 호출할 때는 self 를 직접 넘기지 않는다.

  5. 확인해 볼 것같은 클래스로 인스턴스 두 개를 만들어 각각 다른 값을 넣고, 인스턴스별로 속성이 따로 저장되는지 출력해 비교한다.

#1문제 상황

연산자(operator)는 중위 표기법이라 값을 결합하는 형태가 이미 정해져 있다. 파이썬은 모든 데이터가 객체이고 모든 객체는 정체(identity, 만들어진 뒤 바뀌지 않으며 메모리 주소를 값으로 갖는 것)·타입·값을 갖는 데이터 모델(data model) 위에 서 있어서, 어떤 연산이 가능한지는 타입이 정한다. 문제는 그 결정이 사용자 코드에서 바꿀 수 없는 것처럼 보였다는 점이다. → 06-01 에서 만든 클래스에는 + 도 len() 도 걸리지 않으므로, 값을 다루려고 본래 함수를 하나씩 따로 부르는 관습이 생겼다.

#2핵심 질문

내 타입이 어떤 연산을 지원하는지 타입이 정한다는 규칙 아래에서, 그 연산을 내 클래스가 직접 정의해 기존 문법에 자연스럽게 얹힐 수 있게 할 수 있는가?

#3동작 예시

두 좌표를 다루는 클래스에 __add__ 를 정의해 self 와 다른 좌표를 받아 새 좌표를 돌려주도록 하면, 두 객체 사이에 + 를 써도 그 결과가 새 객체로 나온다. 마찬가지로 __len__ 를 정의하면 len() 에 그 값을 쓰고, __str__ 를 정의하면 print() 가 그 문자열을 출력한다. 실행해 보면 + 결과의 type() 이 새 클래스의 이름이 되고, print 결과가 기본 표시 형식이 아니라 정의한 문장이 되는 것을 확인할 수 있다.

#4동작 과정

  1. 매직 메서드 찾기파이썬은 + 를 만났을 때 실제로는 두 피연산자의 타입에서 __add__ 를 찾아 호출한다. 직접 함수 호출이 아니라 타입을 통해 규칙이 정해지는 방식이다.
  2. 문법마다 대응되는 메서드 정의하기+ 는 __add__, - 는 __sub__, < 비교는 __lt__, len() 은 __len__, 문자열로 바꾸는 __str__ 처럼 각 문법과 내장 함수가 정해진 이름의 메서드로 이어진다.
  3. 되돌림과 제자리 갱신 붙이기하나와 여러 개의 대응이 모두 가능한 연산에는 __mul__ 같은 연산과 __rmul__ 같은 반전(reflected) 메서드, __imul__ 같은 제자리 갱신 메서드를 함께 정의해 여러 입력 형태를 받는다.
  4. __repr__ 로 디버깅 표시 정하기__str__ 는 사람이 읽는 문자열을, __repr__ 는 대화형 셸과 디버거가 보여 주는 표기를 정한다. 둘을 다 정의하면 로그에서 무엇이 다르게 보이는지 비교할 수 있다.
  5. 확인해 볼 것__str__ 와 __repr__ 를 각각 다르게 정의한 객체를 print() 와 대화형 셸에 넣어 보고 두 출력이 어떻게 다른지 확인한다.

먼저 알아야 할 것 06-01 클래스·인스턴스·인스턴스 속성 만들기

#1문제 상황

비슷한 클래스를 여러 개 만들면 필드와 동작이 겹치는 부분이 반복되고, 한 곳을 고칠 때 다른 곳을 놓친다. 필요한 것만 베끼려 해도 어디까지가 공통인지 정해 둘 방법이 없다. 메서드 해석 순서(method resolution order, 메서드를 찾을 때 거슬러 올라가는 순서)는 여러 기반 클래스를 상속받으면 단순한 위에서 아래가 아니라 C3 이라는 규칙으로 정해진다는 점이 앞에서 다뤄졌다. 문제는 그 순서를 명시적으로 모르고 코드를 쓰면 같은 이름의 메서드가 어느 쪽에서 실행되는지 예측하기 어렵다는 점이다.

#2핵심 질문

기존 클래스의 메서드를 물려받아 계층을 쌓되, 여러 기반 클래스가 겹칠 때도 조상 메서드가 정해진 순서로 정확히 한 번씩 호출되게 만들 수 있는가?

#3동작 예시

기존 클래스를 상속받아 메서드 하나를 새로 정의하면, 새 메서드가 같은 이름의 기반 메서드를 덮어쓴다. 안쪽에서 super() 를 부르면 덮어쓴 메서드의 본문 다음에 기반 클래스의 같은 이름 메서드가 실행되어, 기존 동작에 작업을 덧붙인 결과를 얻는다. 예를 들어 "다음 단계로 넘어간다"만 출력하는 메서드를 상속받은 곳에서 super() 로 다시 부른 뒤 한 줄 더 출력하면, 같은 문장이 두 번 찍힌다. 여러 기반을 준 경우 print(Cls.mro()) 로 호출 순서를 직접 볼 수 있다.

#4동작 과정

  1. 상속으로 기반 클래스의 메서드를 물려받기파이썬은 여러 기반 클래스를 지정할 수 있고, 파생 클래스는 기반 메서드를 재정의하며 같은 이름의 기반 메서드를 다시 부를 수도 있다.
  2. super() 로 조상 메서드 호출하기super() 는 현재 클래스의 다음 위치를 찾아 호출하므로 기반 클래스 이름을 직접 적지 않아도 되고, 계층이 나중에 바뀌어도 안전하다.
  3. MRO 를 확인해 호출 순서를 읽기각 클래스 뒤에 붙은 __mro__ 로 해석 순서를 볼 수 있으며, 다중 상속에서는 깊이 우선이 아니라 왼쪽에서 오른쪽으로, 각 경로 안에서 위에서 아래로 가는 C3 선형화 규칙을 따른다.
  4. 동적으로 타입 만들기타입을 실행 중에 조합하면 위 계층을 코드로 만들어 낼 수도 있고, 여러 기반에서 겹치는 이름이 있으면 새 클래스를 만들 때 TypeError 로 먼저 걸러 준다.
  5. 확인해 볼 것두 기반 클래스가 같은 이름의 메서드를 갖고 있을 때 파생 클래스에서 print(Derived.__mro__) 를 실행해 순서가 어떻게 나열되는지 본다.

#5한 줄 요약

상속과 super·MRO 는 기존 클래스의 메서드를 재사용하면서 여러 기반이 겹칠 때 호출 순서를 정해 둔 규칙이라, 계층이 쌓여도 각 메서드가 어느 자리에서 실행되는지 예측할 수 있게 해 줍니다.

#1문제 상황

클래스의 값을 외부에 공개할 때 보통은 값을 그대로 저장하는 일반 속성을 쓰거나, 값을 읽고 쓰는 동작을 get_x·set_x 같은 메서드로 만들어 호출자가 직접 부르게 했다. 일반 속성은 읽기와 쓰기를 막을 수 없고, 메서드로 분리하면 호출하는 쪽마다 obj.get_x()를 써야 해서 같은 값을 읽는 코드마다 형태가 달라진다. descriptor(객체의 속성 접근을 대신 처리하는 객체) 는 이 문제를 없애고, @property(읽기·쓰기·삭제 동작을 속성 문법으로 묶는 데코레이터)를 사용해 같은 이름에 읽기 전용·검증 포함·지연 계산 같은 규칙을 붙인다.

#2핵심 질문

같은 이름의 속성 하나에 읽기와 쓰기의 규칙을 붙여, 호출하는 쪽은 obj.x 라는 문법만 쓰면서도 내부에서는 어떻게 들어오고 나가는지를 프로그램이 정할 수 있는가?

#3동작 예시

temperature 라는 값을 그냥 속성으로 두면 anyone이 obj.temperature = 999 를 대입해도 그대로 저장된다. 이 속성을 @property 로 감싸면, obj.temperature 를 읽을 때마다 함수가 실행되어 변환된 값을 반환하고, 값을 넣을 때는 먼저 0~100 범위인지 검사해 어긋나면 예외를 던진다. 읽는 코드와 쓰는 코드는 모두 obj.temperature 라는 같은 문법을 쓰고, 검사·변환 로직은 클래스 안쪽에만 남는다.

#4동작 과정

  1. descriptor 객체 정의__get__(속성 값을 읽을 때 호출되는 메서드)과 __set__(값을 대입할 때 호출되는 메서드) 를 가진 객체를 만들어 속성 이름에 두면, 파이썬은 그 이름에 접근하는 순간 descriptor 의 메서드로 대신 처리한다. → 06-05 에서 다루는 타입 계층 안에서 이 동작이 어떻게 공통 규칙으로 쓰이는지 볼 수 있다.
  2. @property 로 노출하나의 getter 함수만 데코레이터로 붙이면 읽기 전용 속성이 되고, setter 함수와 deleter 함수까지 각각 @값.setter·@값.deleter 로 이어 붙이면 쓰기와 삭제가 같은 이름에서 동작한다. 더 큰 속성을 다른 속성이나 메서드에 위임하는 예제도 문서 두 번째 절에 있다.
  3. 내장 descriptor 의 파이썬 재현문서 마지막 절은 C로 구현된 내장 도구인 @classmethod, @staticmethod, @property, __slots__ 가 함수와 클래스를 어떻게 descriptor 로 바꿔 주는지 같은 구조로 다시 구현해 보여준다. 이때 함수가 인스턴스에 묶인 bound method(함수를 객체에 묶어 첫 인자를 자동으로 넘긴 결과)가 되는 과정도 함께 드러난다.
  4. 확인해 볼 것@property 로 만든 속성에 값을 대입해 보��, 에러 메시지에 property 'xxx' of 'Cls' object has no setter 처럼 setter 가 없다는 문구가 뜨는지 확인한다.

#1문제 상황

여러 클래스가 같은 역할을 하지만 내부 구현이 다른 경우, 파이썬은 그것이 같은 규약을 지켰는지 자동으로 확인해 주지 않았다. 상속 계층이 깊어지면 호출자는 각 클래스가 반드시 제공해야 하는 메서드를 직접 기억해 시그니처에 기대고 있었다. 그래서 필요한 메서드를 빠뜨린 클래스도 인스턴스를 만들어 버리고, 엉뚱한 곳에서 AttributeError 가 나야 비로소 알 수 있었다.

#2핵심 질문

어떤 메서드는 반드시 implement 해야 한다는 것을 선언해 두고, 그걸 빠뜨린 클래스가 인스턴스가 되는 것을 막을 수 있는가?

#3동작 예시

from abc import ABC, abstractmethod 를 가져와 class Shape(ABC) 로 만들고, 그 안에 @abstractmethod 가 붙은 area() 하나를 둔다. 이 Shape 를 상속한 어떤 클래스든 area() 를 정의하지 않으면 그 클래스의 인스턴스를 만드는 순간 TypeError: Can't instantiate abstract class 가 발생한다. 반대로 area() 를 정의한 클래스만 인스턴스가 되어, 호출자는 몇 개의 구체 클래스든 shape.area() 로 동일하게 다룰 수 있다.

#4동작 과정

  1. 메타클래스로 상속을 감시ABC 를 정의할 때 쓰이는 ABCMeta(메타클래스: 클래스를 만드는 클래스) 가 상속된 클래스들을 추적하면서, 아직 필요한 메서드가 하나도 없으면 그 클래스가 추상(바로 쓸 수 없는) 상태로 남는다. 문서는 ABCMeta 를 직접 쓰는 방식과 복잡할 수 있다고 밝힌다.
  2. ABC 상속으로 추상 메서드 선언class abc.ABC 는 ABCMeta 를 메타클래스로 물려받아, 따로 메타클래스를 적지 않고도 @abstractmethod(구현을 강제하는 데코레이터)를 붙인 메서드로 인터페이스를 선언하게 해 준다. ABC 를 상속한 경우에도 타입 자체는 ABCMeta 로 남는다.
  3. collections.abc 로 인터페이스만 검사해시 가능하거나 매핑처럼 특정 규약을 제공하는지 확인만 하면 되는 경우, collections.abc 서브모듈의 ABC 를 isinstance 에 넣어 인스턴스가 그 인터페이스를 갖는지 검사할 수 있다. 어떤 ABC 에서 파생된 구체 클래스도 collections 모듈에 들어 있다. → 06-04 에서 본 descriptor 는 여기서 @classmethod 와 @property 같은 내장 도구가 감춰 둔 형태로 다시 등장한다.
  4. 확인해 볼 것@abstractmethod 를 하나만 둔 ABC 를 상속한 뒤 인스턴스를 만들어 보고, 그 타입의 __abstractmethods__ 목록에 해당 메서드 이름이 들어 있는지와 인스턴스화 시 어떤 오류가 나는지 확인한다.

#1문제 상황

데이터만 담는 클래스를 만들면 생성자에서 각 값을 하나씩 받아 순서대로 대입하고, 값을 그대로 보여 주는 표현 메서드를 손으로 적어야 했다. 필드가 늘어날 때마다 생성자와 표시 코드가 함께 늘어나고, 필드 순서를 바꿔도 대입 순서를 직접 맞춰야 해서 실수가 생기기 쉬웠다. enum(정해진 값의 집합을 나열한 타입) 과 namedtuple(이름 붙은 필드를 가진 튜플) 없이 값의 종류를 그냥 문자열로 흩어 쓰면 오타도 구분할 수 없었다.

#2핵심 질문

데이터 필드 목록만 선언하면 생성자부터 표시 방법까지 자동 만들어 주고, 값의 종류가 정해진 경우와 가벼운 튜플이 필요한 경우까지 표준 방식으로 표현할 수 있는가?

#3동작 예시

`` @dataclass class InventoryItem: name: str unit_price: float quantity_on_hand: int = 0 ` 이렇게 타입 주석만 적으면 파이썬이 __init__ 를 만들어 InventoryItem("widget", 3.0) 처럼 인자를 받는다. @dataclass` 는 init, repr, eq 인자를 각각 켜고 끌 수 있어 인쇄 방법이나 동등 비교를 바꾸고 싶을 때 설정을 바꾼다.

#4동작 과정

  1. @dataclass 로 메서드 자동 생성dataclasses 모듈은 PEP 557 로 처음 기술됐고, PEP 526 타입 주석으로 선언한 필드를 보고 __init__·__repr__ 등 여러 메서드를 만들어 붙인다. 3.7 에서 추가됐고, 클래스 안에는 적혀 있지 않은 __init__ 가 자동으로 들어간다.
  2. @dataclass 인자로 골라 쓰기@dataclass(init=True, repr=True, eq=True, order=False, unsafe_hash=False) 처럼 매개변수로 무엇을 생성할지 고른다. 필요한 표시 방법만 남기고 나머지는 끄면 작은 객체가 된다.

#4동작 과정

#1문제 상황

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 포맷 문자열로 규칙을 선언struct 에 "정수(int) 4바이트 뒤에 2바이트 정수(unsigned short) 순서"처럼 짧은 형식 문자열을 준다. → 07-04 에서 본 바이트열이 여기서 구조를 갖는다.
  2. 바이트열을 한 덩어리로 다루기pack 은 파이썬 값을 규칙대로 이어 붙이고 unpack 은 규칙대로 다시 분리한다. 이때 파이썬 쪽의 정렬과 C 쪽의 정렬이 달라서 패딩 바이트가 붙는 경우도 생기며, 외부와 주고받을 때는 바이트 순서(byte order, 큰 쪽을 먼저 쓰는지 정하는 규칙)를 직접 정해야 한다.
  3. 표현을 바꾸기base64 로 바이트열을 문자열로 옮기고 되돌리며, codecs 의 코덱 레지스트리에서 이름만으로 변환기를 고른다. 변환 결과는 다시 바이트열이므로 다른 바이트열을 이어 붙이는 용도로도 쓴다.
  4. 확인해 볼 것같은 정수 두 개를 struct.pack("HH", 1, 2) 와 struct.pack("II", 1, 2) 로 각각 만들어 len() 으로 길이를 비교한다.

#1문제 상황

#2핵심 질문

#3동작 예시

TestCase 를 상속한 클래스에 test_ 가 붙은 메서드를 만들고 그 안에서 self.assertEqual(add(2, 3), 5) 라고 적는다. 그 파일을 python -m unittest 로 실행하면 각 테스트가 통과인지 실패인지 표시되고, 기대값과 실제값이 다른 경우 두 값이 함께 출력되며 재실행된다는 사실이 남는다.

#4동작 과정

  1. 테스트를 코드로 고정한다테스트 픽스처(각 테스트에 필요한 준비와 정리 코드)를 재사용할 수 있게 묶고, TestCase 안의 테스트 메서드가 기대 결과를 assert로 선언한다. 검증을 문서화하는 셈이라 다음 사람이 무엇이 보장되어야 하는지 바로 읽힌다.
  2. 여러 테스트를 모아 돌린다테스트를 컬렉션으로 묶어 한 번에 실행하고, unittest 는 리포팅 형식과 독립적으로 동작한다. 어떤 언어로 만든 주력 테스트 프레임워크(JUnit)에서 형태를 가져왔다.
  3. 실패를 그대로 드러낸다기대한 값과 실제 값이 다르면 그 지점에서 실패로 표시되며 어떤 메서드에서 왜 실패했는지 드러난다. 코드 수정 전후로 같은 테스트를 다시 돌리면 깨진 부분이 그대로 보이는 것이 회귀를 잡아내는 근거가 된다.
  4. 확인해 볼 것테스트 파일 하나에 일부러 잘못된 assert 를 넣고 실행해, 실패 줄과 기대값·실제값이 출력되는지 본다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 가짜 객체를 넣는다unittest.mock 의 Mock 객체는 실제 동작 대신 호출 기록만 남기며, MagicMock 은 매직 메서드까지 흉내 낸다. 되돌릴 값과 필요한 속성은 일반적인 방식으로 지정한다.
  2. 동작 이후 단언한다행동(assertion) 이후 기록을 확인하는 방식이 기본이다. 어느 메서드·속성이 어떤 인자로 몇 번 호출되었는지 확인할 수 있어 호출 계약을 검증한다.
  3. 범위 안에서만 바꾼다patch() 데코레이터와 컨텍스트 매니저를 쓰면 모듈·클래스 수준 속성을 테스트 범위 중에만 바꿨다가 원상 복구된다. sentinel(값이 다르면 무조건 다른 고유 객체)로 인자가 특정 값인지 확인하기도 한다.
  4. 확인해 볼 것같은 mock 객체에서 메서드 하나를 두 번 호출한 뒤 call_count 값과 call_args_list 에 두 번의 인자가 찍히는 것을 본다.

  3. 예외 경로를 따라간다traceback 모듈은 예외의 스택 트레이스백을 꺼내 형식을 맞추고 출력해 예외가 어떤 경로로 올라왔는지 보여준다. faulthandler 를 함께 쓰면 타임아웃이나 신호 뒤에도 트레이스백을 명시적으로 덤프한다.
  4. 확인해 볼 것breakpoint() 를 넣고 실행하면 표준 입력에 (Pdb) 프롬프트가 찍히고, p 변수명 으로 그 시점 값이 출력되는지 본다.

UnixStreamServer 도 같은 방식으로 유닉스 소켓을 사용한다. bind_and_activate 가 참이면 생성자에서 server_bind() 와 server_activate() 를 자동으로 시도한다.

이 빈틈을 select 계열의 OS 기능으로 메울 수 있고, selectors 모듈은 이를 상위 수준으로 감싸 효율적인 다중 입출력(I/O multiplexing)을 제공한다. 이는 select 모듈의 기본 동작 위에 만들어졌고, 문서는 이 모듈을 권장한다.   4. 확인해 볼 것소켓 두 개를 selector 에 등록하고 select() 의 결과를 출력해 준비된 항목이 몇 개로 돌아오는지 화면에서 확인한다

argparse(명령줄 옵션과 인자를 코드에 선언해 두고 파이썬이 해석하게 만드는 표준 라이브러리 모듈)는 이 반복을 없앤다. 기본 명령줄 애플리케이션에는 이 모듈이 권장되는 방식이며, 옵션과 위치 인자가 마음대로 섞이거나 - 로 시작하는 값을 받는 등 세부 동작까지 제어해야 하는 경우에는 다른 라이브러리를 고려하라고 문서에 적혀 있다.

#2핵심 질문

옵션과 위치 인자의 이름·형식·기본값·도움말을 코드에 한 번만 선언해 두고, 그것을 파이썬이 해석하고 사용자에게 보여주게 할 수 있는가?

#3동작 예시

parser.add_argument("--count", type=int, default=1, help="반복 횟수") 라고 한 줄을 적으면 실행 시 --count 5 가 붙었을 때 값을 정수로 변환해 변수에 담고, 안 붙었으면 기본값 1을 쓰며, --help 를 치면 정의해 둔 도움말 문자열이 항목 목록으로 출력된다. 값이 숫자가 아니면 파이썬이 직접 타입 오류 메시지를 내고 종료한다.

#4동작 과정

  1. 파서 만들기argparse.ArgumentParser() 로 명령줄 규칙을 담을 자리를 만들고 설명(description)을 넣는다. 이 시점에는 아직 아무 인자도 해석하지 않는다.
  2. 옵션·인자 선언add_argument 로 옵션 이름, 타입, 기본값, 도움말을 등록한다. 등록한 항목이 곧 사용자에게 보이는 규칙이 된다.
  3. 인자 해석parse_args() 를 부르면 실제 명령줄 문자열이 선언된 규칙에 맞춰 파싱되고, 결과는 이름에 접근할 수 있는 객체로 돌아온다. 선언과 실제 파싱이 분리되어 있어 같은 규칙을 여러 명령줄에서 재사용할 수 있다.
  4. 확인해 볼 것인자를 두어 둔 스크립트를 실행하고 --help 를 쳐서 등록한 옵션 이름과 타입, 기본값, 설명이 목록으로 표시되는지 본다.

#1문제 상황

파이썬은 참조 카운팅으로 객체가 더 이상 쓰이지 않으면 즉시 메모리를 되돌린다. 이 방식은 대부분 충분하지만, 서로를 참조하는 순환 참조(두 객체가 서로를 가리켜 아무도 안 쓰게 되어도 참조 카운트가 0 이 되지 않는 구조)에서는 객체가 살아남는다. 이를 뒤늦게 회수하는 것이 gc 모듈의 순환 가비지 컬렉터다.

gc(참조 카운팅을 보완해 순환 참조를 회수하는 가비지 컬렉터) 는 이 회수를 켜고 끄고, 주기를 조정하고, 회수했으나 못 없앤 객체에 접근할 수 있게 해 준다. sys 모듈은 인터프리터 상태 정보를, weakref(참조 카운트를 세지 않는 약한 참조) 는 객체의 수명을 외부에서 감시하게 해 준다.

#2핵심 질문

#3동작 예시

두 객체가 서로를 참조하는 구조를 만든 뒤 gc.collect() 를 부르면 회수기가 순환 참조를 찾아 그 객체를 없앤다. gc.disable() 로 껐다 켜는 사이에 만들어진 순환 참조는 켠 뒤 회수 대상이 된다.

#4동작 과정

  1. 기본 회수참조 카운팅을 보완해 완성된 순환 참조를 주기적으로 회수한다. gc.disable() 로 이 자동 회수를 멈출 수 있고, gc.isenabled() 로 켜져 있는지 알 수 있다.
  2. 직접 회수와 조정gc.collect() 를 부르면 전체 회수를 즉시 실행한다. 세대(generation) 인자를 주면 지정한 세대까지만 돈다.
  3. 디버깅gc.set_debug(gc.DEBUG_LEAK) 을 켜면 회수했으나 없애지 못한 객체가 보존되어 정리를 확인한다.
  4. 수명 감시weakref 로 객체를 약하게 참조하면 그 객체가 사라졌을 때 통지받을 수 있어 캐시와 순환 구조를 안전하게 유지한다.
  5. 확인해 볼 것순환 참조를 만든 뒤 gc.collect() 를 부르고 gc.set_debug(gc.DEBUG_SAVEALL) 상태에서 회수된 객체가 목록에 남아 있는지에 보이는 출력으로 확인한다.

#1문제 상황

이름을 정하면 그 이름이 어떤 객체를 가리키는지, 예외가 어디까지 올라오는지, 모듈이 몇 번 실행되는지 같은 규칙을 소스 코드를 읽지 않으면 알기 어렵다. 프로그램이 시작될 때 무엇이 준비되고 어떤 설정 파일이 자동으로 반영되는지도 코드 밖에서 결정되기 때문에 설명하기 어렵다.

실행 모델은 코드 블록(module, 함수 본문, 클래스 정의, 인터랙티브로 입력한 한 줄, 스크립트 파일, -c 로 준 스크립트 명령, -m 으로 최상위 스크립트로 실행한 모듈, eval()·exec() 에 넘긴 문자열)이 실행 단위이며, 각 블록은 실행 프레임에서 실행된다는 규칙을 정한다. site 처리는 인터프리터 시작 때 사이트별 설정 훅을 거쳐 site-packages 와 사용자 설정을 준비하는 자리다.

#2핵심 질문

파이썬 코드가 이름 바인딩과 예외 전파, 모듈 실행을 어떤 규칙으로 처리하고 인터프리터는 시작할 때 무엇을 준비하는가?

#3동작 예시

같은 파일을 스크립트로 실행하면 최상위 코드가 __main__ 이라는 이름의 모듈로 한 번 실행된다. 이 파일을 다른 파일에서 import 하면 최상위 코드가 다시 실행되지만 모듈 이름이 그 파일 이름으로 바뀐 채 캐시에 남으므로, 다음 import 부터는 실행되지 않는다.

#4동작 과정

  1. 코드 블록과 프레임프로그램을 구성하는 코드 블록이 실행 단위가 되고, 블록마다 실행 프레임(frame, 이름과 참조를 담는 실행 단위 컨테이너) 이 생겨 이름이 거기 바인딩된다.
  2. 이름 조회 규칙이름을 찾을 때 현재 프레임에서 전역으로 나가며 각 스코프를 순서대로 확인한다. 그 결과가 뒤에서 12-04 의 참조 카운팅과 얽혀 객체 수명이 결정된다.
  3. 초기화인터프리터가 실행되면 site 처리를 통해 사이트별 설정이 적용되고 site-packages 와 사용자 설정 디렉터리가 경로에 추가된 뒤 프로그램이 시작된다.
  4. 확인해 볼 것python -c 'import sys; print(sys.path)' 를 실행해 site-packages 경로가 목록에 들어 있는 것과 파일에 print(__name__) 를 넣어 직접 실행과 import 실행에서 다른 이름이 나오는 것을 본다.
