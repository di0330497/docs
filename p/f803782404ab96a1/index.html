RDS의 정의와 DB 인스턴스

Amazon RDS는 관계형 데이터베이스를 클라우드에서 손쉽게 설정·운영·확장하도록 해 주는 AWS 관리형 서비스이며, DB 인스턴스는 그 위에서 실제로 실행되는 격리된 데이터베이스 환경이다.

#1문제 상황

관계형 데이터베이스를 직접 운영하려면 서버를 구입하고, 데이터베이스 소프트웨어를 설치하고, 패치와 백업, 장애 대응, 용량 증설을 모두 사람이 처리해야 한다. 데이터가 늘면 디스크를 늘리고 서버를 바꾸는 작업을 직접 해야 하며, 이 작업은 서비스 중단 없이 하기 어렵다. 게다가 이 모든 관리 업무가 개발자가 제품 기능을 만드는 시간을 잡아먹는다.

#2핵심 질문

서버 설치와 패치·백업·확장 같은 관리 작업을 AWS에 맡기고, 관계형 데이터베이스만 빠르게 띄워 쓸 수는 없을까?

#3동작 예시

MySQL을 쓰고 싶은 개발자가 콘솔에서 엔진으로 MySQL을 고르고, 인스턴스 클래스와 스토리지 용량을 지정한 뒤 생성을 누른다. 몇 분 뒤 AWS가 데이터베이스가 실행 중인 환경을 만들어 주고, 개발자는 그 환경의 엔드포인트 주소와 포트로 접속해 SQL을 실행한다. 서버 준비나 소프트웨어 설치를 직접 하지 않는다.

#4동작 과정

  1. 관리형 서비스가 대신 처리할 범위를 정한다RDS는 백업, 소프트웨어 패치, 장애 감지 같은 공통 데이터베이스 관리 작업을 AWS가 담당하고, 사용자는 데이터와 스키마, 쿼리 같은 자기 몫에 집중한다. 그래서 운영 부담이 줄어든다.
  2. DB 인스턴스를 만든다DB 인스턴스는 실제로 데이터베이스가 실행되는 격리된 환경으로, 엔진·클래스·스토리지를 지정해 생성한다. 생성되면 접속 가능한 하나의 데이터베이스 환경이 생긴다.
  3. 엔드포인트로 접속해 사용한다애플리케이션은 DB 인스턴스의 엔드포인트 주소로 연결해 데이터를 읽고 쓴다. 용량이 필요하면 인스턴스 사양이나 스토리지를 조정해 확장한다.

#5한 줄 요약

관계형 데이터베이스의 설치·운영·확장 부담을 AWS가 대신 지고, 사용자는 DB 인스턴스만 만들어 쓰게 하는 관리형 서비스

DB 인스턴스 클래스

DB 인스턴스 클래스는 DB 인스턴스에 할당되는 컴퓨팅·메모리 용량 조합으로, 워크로드에 맞는 CPU와 메모리 사양을 선택하는 기준이다.

#1문제 상황

데이터베이스를 돌릴 컴퓨터의 CPU와 메모리 사양을 잘못 고르면 문제가 생긴다. 너무 작게 고르면 쿼리가 밀리고 메모리 부족으로 느려지며, 너무 크게 고르면 쓰지도 않는 자원에 비용을 계속 낸다. 게다가 작업 부하에 따라 필요한 CPU와 메모리 비율이 달라서, 하나의 정해진 사양으로는 모든 경우를 감당하기 어렵다.

#2핵심 질문

내 데이터베이스 작업량에 맞는 CPU와 메모리 조합을 어떻게 골라야 할까?

#3동작 예시

메모리에 데이터를 많이 올려 두고 읽는 작업이 많은 서비스라면 메모리 최적화 클래스인 db.r6g 계열을 고른다. 여기서 db.r6g는 클래스 유형이고, 그 안에서 db.r6g.2xlarge처럼 크기를 붙여 실제 사양을 정한다. 크기가 클수록 CPU와 메모리가 함께 커지므로, 부하가 늘면 같은 유형에서 더 큰 크기로 바꾼다.

#4동작 과정

  1. 클래스 유형으로 성격을 정한다DB 인스턴스 클래스는 컴퓨팅과 메모리 용량을 결정하며, 클래스 유형과 크기 두 부분으로 이루어진다. 범용·메모리 최적화 등 유형이 작업 성격에 맞는 자원 배분을 정한다. 예를 들어 db.r6g는 AWS Graviton2 프로세서를 쓰는 메모리 최적화 유형이다.
  2. 크기로 용량을 정한다같은 유형 안에서 2xlarge 같은 크기를 골라 실제 CPU·메모리 양을 정한다. 처리량과 메모리 요구에 맞춰 크기를 선택한다.
  3. 엔진·리전 지원을 확인하고 조정한다클래스마다 지원하는 DB 엔진과 리전이 다르므로 생성 전에 지원 여부를 확인한다. 부하가 바뀌면 기존 인스턴스의 클래스를 더 크거나 작은 것으로 변경한다.

DB 인스턴스 스토리지

DB 인스턴스 스토리지는 데이터베이스 데이터와 로그를 저장하는 EBS 기반 볼륨으로, 스토리지 유형(예: gp3, io2)과 용량·IOPS를 선택해 성능을 결정한다.

#1문제 상황

데이터베이스의 데이터와 로그는 어딘가에 저장돼야 하고, 그 저장 장치의 성능이 서비스 속도를 좌우한다. 저장 장치가 느리면 초당 처리하는 입출력(I/O) 횟수가 모자라 쿼리가 대기하고, 용량이 부족하면 데이터를 더 못 받는다. 저장 방식을 잘못 고르면 필요 이상으로 비용을 쓰거나 반대로 성능이 부족해진다.

#2핵심 질문

데이터와 로그를 어떤 저장 방식으로, 얼마만큼의 용량과 성능으로 담아야 할까?

#3동작 예시

Db2, MariaDB, MySQL, PostgreSQL, Oracle, SQL Server용 RDS의 DB 인스턴스는 데이터와 로그 저장에 Amazon EBS 볼륨을 사용한다. 여기서 스토리지 유형으로 범용 SSD인 gp3나 프로비저닝된 IOPS용 SSD 같은 방식을 고르고, 용량과 초당 입출력 수(IOPS)를 지정한다. 이 값들이 데이터베이스가 낼 수 있는 저장 성능을 정한다.

#4동작 과정

  1. 스토리지 유형을 고른다범용 SSD, 프로비저닝 IOPS SSD, 마그네틱(레거시, 권장하지 않음) 중에서 성능과 비용을 보고 유형을 정한다. 유형에 따라 보장되는 성능의 성격이 달라진다.
  2. 용량과 IOPS를 지정한다저장할 데이터 크기에 맞춰 용량을, 필요한 입출력 처리량에 맞춰 IOPS를 정한다. 프로비저닝 IOPS는 사용량과 무관하게 지정한 IOPS 요율이 부과된다.
  3. 성능을 관찰하고 조정한다실제 IOPS가 지정한 값에 100퍼센트 도달하지 못할 수 있으므로 데이터베이스 성능을 모니터링한다. 필요하면 로그를 별도 볼륨에 두는 전용 로그 볼륨(DLV) 같은 추가 볼륨을 활용하거나 용량과 IOPS를 조정한다.

리전·가용 영역·기능 지원

리전은 RDS 리소스가 배포되는 지리적 AWS 영역이고 가용 영역은 리전 내의 격리된 데이터 센터 위치이며, 각 리전·엔진별로 지원되는 RDS 기능이 다르다.

#1문제 상황

서비스 사용자가 전 세계에 흩어져 있으면 한 곳에만 데이터베이스를 두었을 때 멀리 있는 사용자는 접속이 느리고, 그 한 곳에 장애가 나면 서비스 전체가 멈춘다. 그렇다고 아무 곳에나 자원을 두면 지연이 줄지 않고, 리전마다 쓸 수 있는 기능이 달라 같은 설정이 어디서는 동작하고 어디서는 안 되는 문제가 생긴다.

#2핵심 질문

사용자에게 가까운 여러 위치에 DB 인스턴스를 두고, 각 위치에서 지원되는 기능을 어떻게 확인할까?

#3동작 예시

AWS 리전은 각각 별개의 지리적 영역이고, 그 안에 여러 개의 격리된 가용 영역이 있다. 사용자가 많은 나라에 가까운 리전을 골라 DB 인스턴스를 두면 그 지역 사용자의 접속 지연이 줄어든다. 리전을 여러 개 쓰더라도 AWS가 자동으로 데이터를 다른 리전에 복제하지는 않으므로, 다른 리전에 데이터를 두려면 읽기 복제본이나 백업 복사 같은 방법을 직접 설정해야 한다.

#4동작 과정

  1. 리전과 가용 영역을 고른다리전은 지리적 영역, 가용 영역은 리전 안의 격리된 데이터 센터 위치다. 사용자와 가까운 리전을 고르고, 가용 영역을 나눠 배치하면 일부 위치에 장애가 나도 견딜 수 있다.
  2. 기능 지원 여부를 확인한다교차 리전 자동 백업, 교차 리전 읽기 복제본, Multi-AZ DB 클러스터, RDS Proxy 같은 기능은 리전과 엔진별로 지원 여부가 다르다. 쓰려는 기능이 대상 리전과 엔진에서 지원되는지 먼저 확인한다.
  3. 리전 사용 여부를 관리한다AWS 계정은 리전에 대해 옵트인·옵트아웃 방식으로 사용 여부를 관리할 수 있다. 쓰지 않는 리전에서 옵트아웃하고 필요할 때 다시 옵트인한다.

요금과 예약 인스턴스

RDS 요금은 인스턴스·스토리지·백업·데이터 전송 등 사용량 기준으로 부과되며, 예약 DB 인스턴스는 기간을 약정해 온디맨드보다 낮은 요율을 적용받는 결제 방식이다.

#1문제 상황

데이터베이스를 상시로 돌리면 비용이 계속 나가는데, 요금이 무엇으로 구성되는지 모르면 어디서 새는지 알 수 없다. 인스턴스 시간만 보다가 스토리지나 입출력 요금이 더 나오는 경우도 있고, 한동안 쓸 것이 확실한데도 매번 온디맨드 요율을 내면 같은 자원에 더 많은 돈을 쓰게 된다.

#2핵심 질문

RDS 요금은 무엇으로 구성되며, 오래 쓸 인스턴스의 비용을 어떻게 줄일까?

#3동작 예시

DB 인스턴스를 계속 켜 두면 인스턴스 시간 요금이 시간당으로 부과되고, 여기에 프로비저닝한 스토리지 용량 요금과 데이터 전송 요금 등이 더해진다. 반대로 1년처럼 오래 쓸 것이 확실하면 예약 DB 인스턴스를 구매해 기간을 약정하는 대신 온디맨드보다 낮은 요율을 적용받는다.

#4동작 과정

  1. 사용량 구성 요소별로 요금이 매겨진다DB 인스턴스 시간(인스턴스 클래스 기준), 스토리지(프로비저닝한 용량), 프로비저닝 IOPS 요율 등이 각각 부과된다. 사용량은 초 단위로 청구되며 최소 과금 시간이 있다.
  2. 온디맨드로 쓴다미리 약정하지 않고 쓴 만큼 시간당 요금을 낸다. 얼마나 오래 쓸지 정해지지 않았을 때 유연하다.
  3. 예약 인스턴스를 구매한다기간을 약정하는 예약 DB 인스턴스를 구매하면 온디맨드보다 낮은 요율이 적용된다. 구매한 예약 인스턴스의 청구 내역은 콘솔에서 확인한다.

설정과 엔진별 시작 가이드

Amazon RDS를 쓰기 위한 사전 설정(AWS 계정·IAM·보안 그룹 등)을 마치고, MySQL·PostgreSQL·MariaDB·Oracle·SQL Server 등 엔진별로 첫 DB 인스턴스를 생성·연결하는 시작 절차를 안내하는 문서다.

#1문제 상황

RDS로 첫 데이터베이스를 만들려 해도 엔진마다 생성과 접속 절차가 조금씩 다르다. Db2, MariaDB, MySQL, SQL Server, Oracle, PostgreSQL 중 무엇을 쓰느냐에 따라 선택 항목과 접속 방법이 달라지고, 그 전에 AWS 계정과 권한, 접속을 허용할 보안 그룹 같은 사전 준비를 끝내 두지 않으면 생성이 막힌다.

#2핵심 질문

사전 준비를 마친 뒤, 고른 엔진에 맞춰 첫 DB 인스턴스를 만들어 접속하려면 어떤 순서를 따라야 할까?

#3동작 예시

MySQL을 쓰기로 한 개발자가 먼저 AWS 계정과 IAM 권한, 보안 그룹 같은 설정을 마친다. 그다음 MySQL 엔진을 골라 DB 인스턴스를 생성하고, 생성된 인스턴스의 엔드포인트 주소와 포트, 자격 증명으로 데이터베이스에 연결해 쿼리를 실행한다. 확인이 끝나면 안내에 따라 인스턴스를 삭제해 자원과 비용을 정리한다.

#4동작 과정

  1. 환경을 설정한다DB 인스턴스를 만들거나 접속하기 전에 AWS 계정, 권한, 접속을 허용할 보안 그룹 같은 사전 작업을 끝낸다. 이 준비가 안 되면 생성이나 접속이 실패한다.
  2. 엔진을 골라 DB 인스턴스를 만든다Db2, MariaDB, MySQL, SQL Server, Oracle, PostgreSQL 중 쓸 엔진을 정하고, 그 엔진의 안내에 따라 인스턴스를 생성한다. 엔진마다 절차가 조금씩 다르다.
  3. 접속하고 정리한다생성한 DB 인스턴스의 데이터베이스에 연결해 동작을 확인하고, 확인이 끝나면 안내에 따라 인스턴스를 삭제한다. 남겨 두면 계속 요금이 발생한다.

#1문제 상황

DB 인스턴스를 만든 뒤에는 웹 서버나 서버리스 함수에서 그 DB에 실제로 접속해 데이터를 읽고 쓰는 코드를 붙여야 한다. 그런데 이 과정에는 VPC, 서브넷, 보안 그룹, 엔드포인트, 드라이버 설치, 자격 증명 같은 여러 설정이 얽혀 있어서, 처음 하는 사람은 어느 것을 어떤 순서로 맞춰야 하는지 알기 어렵다. 항목별 문서가 흩어져 있어 전체 흐름을 한 번에 따라가며 완성된 형태를 확인하기도 힘들다.

#2핵심 질문

EC2 웹 서버와 Lambda 함수가 RDS DB 인스턴스에 접속해 쿼리까지 실행하려면 무엇을 어떤 순서로 준비해야 하는가?

#3동작 예시

#4동작 과정

  1. EC2 인스턴스 시작DB에 접속할 EC2 인스턴스를 기본 VPC와 서브넷, 보안 그룹을 사용해 만든다. 이 인스턴스가 나중에 DB로 요청을 보내는 출발점이 된다.
  2. DB 인스턴스 생성MySQL 또는 PostgreSQL DB 인스턴스를 만들어 엔드포인트와 포트, 자격 증명을 확보한다. EC2와 DB가 같은 VPC 안에 있어야 서로 통신할 수 있다.
  3. 웹 서버 구성과 연결EC2에 Apache와 PHP를 설치하고, 접속 정보를 넣은 코드로 DB에 연결한다. Lambda로 할 경우 같은 접속 정보를 함수 환경 변수나 코드에 넣어 RDS에 접근한다.

모범 사례와 프로그래밍 접근

RDS 운영 시 지켜야 할 모범 사례와, 콘솔 외에 AWS CLI·SDK·CloudFormation 등 코드로 RDS 리소스를 다루는 프로그래밍 접근 방법을 설명한다.

#1문제 상황

RDS를 그냥 켜 두고 쓰면 시간이 지나면서 느려지거나 예상치 못한 장애를 겪기 쉽다. 메모리 부족, 오래된 엔진 버전, 부적절한 드라이버, 성능 저하의 원인을 파악하지 못한 채 방치하는 일이 반복된다. 또한 콘솔에서 손으로 리소스를 만들면 같은 구성을 여러 번 재현하기 어렵고, 변경 이력을 남기기도 힘들다.

#2핵심 질문

RDS를 안정적으로 운영하려면 무엇을 점검해야 하고, 콘솔 대신 코드로 리소스를 다루려면 어떤 수단을 쓰는가?

#3동작 예시

DB 인스턴스의 메모리 사용량과 CPU 지표를 Amazon CloudWatch에서 확인하고, Enhanced Monitoring으로 운영체제 수준의 상태를 함께 본다. 같은 구성을 반복해서 만들어야 할 때는 CloudFormation 템플릿에 인스턴스 클래스와 스토리지 용량을 적어 두고, 그 템플릿을 실행해 동일한 DB 인스턴스를 매번 생성한다.

#4동작 과정

  1. 모범 사례 점검DB 인스턴스 RAM 권장량, 최신 엔진 버전 유지, AWS가 안내하는 데이터베이스 드라이버 사용, Enhanced Monitoring과 지표 활용, 쿼리 튜닝 항목을 확인한다. 이 점검만으로도 성능 저하의 흔한 원인을 미리 줄일 수 있다.
  2. 자동화 도구 선택매번 같은 구성을 만들 때는 AWS CloudFormation으로 DB 인스턴스 생성을 자동화한다. 템플릿을 코드로 관리하므로 재현과 변경 추적이 쉬워진다.
  3. 프로그래밍 접근 적용콘솔 작업을 AWS CLI나 SDK로 대체하고, 콘솔에서 수행한 작업을 코드로 바꿔 주는 Console-to-Code 기능을 활용해 반복 작업을 스크립트로 옮긴다.

#1문제 상황

서버에 데이터베이스를 직접 설치하던 방식에서는 하드웨어를 고르고, 운영체제와 엔진을 설치하고, 메모리와 저장 공간을 직접 할당해야 했다. 게다가 그 구성이 하나의 물리 장비에 묶여 있어서, 부하가 늘면 장비를 새로 사서 옮겨야 하고 장애가 나면 복구에 시간이 걸렸다. 이런 준비와 관리 부담이 실제 서비스 개발보다 앞에 놓여 있었다.

#2핵심 질문

엔진과 사양, 저장 공간, 접속 자격 증명을 정해 클릭 몇 번으로 데이터베이스 하나를 바로 띄우려면 어떻게 하는가?

#3동작 예시

새 DB 인스턴스를 만들 때 엔진으로 MySQL을 고르고, 인스턴스 클래스로 CPU와 메모리 조합을 정하고, 스토리지 용량과 유형을 지정한 뒤, 마스터 사용자 이름과 암호를 입력한다. 같은 화면에서 가용 영역과 서브넷 그룹 같은 네트워크 설정도 함께 정해, 생성이 끝나면 바로 접속 가능한 데이터베이스가 나온다.

#4동작 과정

  1. 사전 준비DB 인스턴스는 Amazon VPC 안에만 만들 수 있고, 최소 두 개의 가용 영역이 있는 리전이어야 한다. 그래서 먼저 VPC와 서브넷, 보안 그룹 등 네트워크 환경을 갖춘다.
  2. 설정 선택엔진 종류, 인스턴스 클래스(CPU·메모리), 스토리지 용량, 자격 증명, 백업과 네트워크 옵션을 정한다. 이 값들이 인스턴스의 성격과 비용을 결정한다.
  3. 생성과 재현선택한 설정으로 DB 인스턴스를 만든다. 같은 구성을 반복해서 만들어야 하면 CloudFormation으로 생성을 자동화해 매번 동일한 결과를 얻는다.

DB 인스턴스 연결

생성한 DB 인스턴스의 엔드포인트·포트를 확인하고 클라이언트가 해당 인스턴스에 접속하도록 설정하는 방법을 설명한다.

#1문제 상황

DB 인스턴스를 만들었다고 해서 곧바로 접속되는 것은 아니다. 엔진마다 다른 표준 클라이언트를 써야 하고, 접속할 때 넣어야 할 호스트 주소와 포트를 정확히 알아야 하며, VPC 안에 있는 인스턴스는 네트워크 경로와 보안 규칙까지 맞아야 통신이 된다. 이 정보를 잘못 넣거나 보안 그룹을 열어 두지 않으면 연결이 계속 실패한다.

#2핵심 질문

만들어 둔 DB 인스턴스에 클라이언트가 접속하려면 어떤 정보를 확인하고 어떤 조건을 맞춰야 하는가?

#3동작 예시

접속 문자열(connection string)의 호스트 자리에 DB 인스턴스 엔드포인트의 DNS 주소를, 포트 자리에 엔드포인트의 포트 번호를 넣는다. 예를 들어 MySQL 워크벤치나 psql 같은 표준 클라이언트에서 이 주소와 포트, 사용자 이름과 암호를 입력하면 해당 인스턴스의 데이터베이스에 접속된다.

#4동작 과정

  1. 접속 정보 확인DB 인스턴스의 엔드포인트(DNS 주소)와 포트 번호를 확인한다. 이 두 값이 접속 문자열의 호스트와 포트가 된다.
  2. 클라이언트 준비해당 엔진에 맞는 표준 클라이언트 애플리케이션이나 유틸리티를 사용한다. 엔진별로 접속 도구와 인증 방식이 다르다.
  3. 경로와 접근 구성VPC 안 인스턴스에 접속하려면 같은 VPC의 EC2 인스턴스를 거치거나 Lambda 함수에 연결 권한을 준다. 보안 그룹 규칙과 필요 시 RDS Proxy 같은 연결 관리 수단을 함께 설정한다.

옵션 그룹

DB 인스턴스에 추가 기능(예: 특정 엔진 옵션)을 붙이기 위해 옵션을 모아 관리하고 인스턴스에 연결하는 옵션 그룹의 개념과 사용법을 설명한다.

#1문제 상황

데이터베이스 엔진에는 기본 기능 외에 추가로 켜야 하는 기능들이 있고, 그 기능을 사용하려면 별도 설정도 함께 맞춰야 한다. 이런 설정을 인스턴스마다 손으로 하나씩 켜면 같은 구성을 여러 인스턴스에 반복 적용하기 어렵고, 어떤 인스턴스에 어떤 기능이 켜져 있는지 일관되게 관리하기도 힘들다.

#2핵심 질문

여러 DB 인스턴스에 같은 추가 기능과 그 설정을 한 묶음으로 붙이고 관리하려면 어떻게 하는가?

#3동작 예시

Db2, MariaDB, MySQL, Oracle, PostgreSQL, SQL Server 같은 엔진별로 제공되는 추가 기능을 하나의 옵션 그룹에 모아 둔다. 그 옵션 그룹을 특정 DB 인스턴스에 연결하면, 그 안에 담긴 기능과 설정값이 해당 인스턴스에서 한꺼번에 활성화된다.

#4동작 과정

  1. 옵션 그룹 준비엔진에 맞는 옵션 그룹을 새로 만들거나 기존 그룹을 복사해 기준을 만든다. 그룹은 기능과 설정을 담는 단위다.
  2. 옵션 추가와 설정그룹에 필요한 옵션을 추가하고, 그 옵션이 어떻게 동작할지 설정값을 지정한다. 추가·수정·삭제가 그룹 단위로 이뤄진다.
  3. 인스턴스에 연결옵션 그룹을 DB 인스턴스에 연결하면 지정한 옵션과 설정이 그 인스턴스에 적용된다. 연결을 바꾸면 적용되는 기능 묶음도 함께 바뀐다.

파라미터 그룹

DB 엔진 파라미터 값을 인스턴스에 적용하기 위해 파라미터를 모아 관리하는 파라미터 그룹의 개념과 생성·연결·수정 방법을 설명한다.

#1문제 상황

데이터베이스가 메모리를 얼마나 쓸지, 어떤 동작을 허용할지 같은 값은 파라미터로 정해진다. 이 값을 인스턴스마다 직접 고치면 설정이 흩어져 관리가 어렵고, 같은 값을 여러 인스턴스에 똑같이 맞추기도 번거롭다. 잘못된 값을 적용하면 성능이나 동작이 의도와 달라질 수 있다.

#2핵심 질문

DB 엔진의 여러 파라미터 값을 묶음으로 관리하고 인스턴스에 일관되게 적용하려면 어떻게 하는가?

#3동작 예시

DB 인스턴스 클러스터에 파라미터 그룹을 연결해 데이터베이스 설정을 관리한다. 예를 들어 메모리 할당량을 정하는 파라미터 값을 파라미터 그룹에서 바꾸면, 그 그룹을 연결한 DB 인스턴스에 변경된 값이 적용된다. Amazon RDS는 기본 설정을 담은 파라미터 그룹을 제공하고, 사용자가 값을 바꾼 자기 그룹도 만들 수 있다.

#4동작 과정

  1. 파라미터 그룹 준비DB 인스턴스용 또는 DB 클러스터용 파라미터 그룹을 만든다. 기본 그룹을 그대로 쓰거나, 복사해 값을 바꾼 자기 그룹을 만든다.
  2. 연결과 값 수정인스턴스나 클러스터에 파라미터 그룹을 연결하고, 그 안의 파라미터 값을 수정한다. 필요하면 값을 기본값으로 되돌리거나 다른 그룹과 비교한다.
  3. 적용 결과 확인수정한 파라미터가 연결된 인스턴스에 반영되고, 그룹을 바꾸면 적용되는 설정 묶음도 바뀐다. 값을 확인하고 더 이상 필요 없으면 그룹을 삭제한다.

ElastiCache·DMS 연동

Amazon RDS 설정을 기반으로 ElastiCache 캐시를 만들거나, AWS DMS로 데이터베이스를 자동 마이그레이션하는 연동 방법을 설명한다.

#1문제 상황

RDS로 애플리케이션을 운영하다 보면 같은 데이터를 매 요청마다 DB에서 읽어 오는 구조가 병목이 된다. 읽기 지연이 밀리초 단위로 쌓이고, DB 인스턴스는 캐시가 해줄 수 있는 단순 조회까지 직접 처리하느라 부하가 커진다. 캐시를 따로 붙이려 해도 엔진 종류·포트·보안 그룹 같은 접속 설정을 RDS와 똑같이 맞춰 다시 입력해야 해서 설정 실수가 잦다. 한편 기존 데이터베이스를 RDS로 옮길 때는 스키마 변환과 지속적 복제를 직접 스크립트로 짜야 했고, 이전이 끝난 뒤에도 원본과 대상의 데이터가 어긋나지 않는지 확인할 방법이 마땅치 않았다.

#2핵심 질문

RDS 인스턴스의 접속 설정을 그대로 재사용해 캐시를 만들고, 마이그레이션까지 자동화할 수는 없을까?

#3동작 예시

RDS 콘솔에서 DB 인스턴스를 고르고 "ElastiCache 캐시 생성" 작업을 실행하면, RDS가 그 인스턴스의 엔진·포트 같은 접속 정보를 읽어 캐시 클러스터 설정 초기값으로 채운다. DMS 쪽은 다르게 동작한다. 마이그레이션을 시작하기 전에 원본 DB에 접속할 수 있는 IAM 역할과 시크릿 접근 권한을 먼저 만들고, DMS가 그 권한으로 원본을 읽어 대상 RDS에 데이터를 복제한다.

#4동작 과정

  1. 캐시 설정 재사용RDS DB 인스턴스의 엔진과 네트워크 설정을 읽어 ElastiCache 캐시 생성 화면의 초기값으로 넘긴다. 접속 정보를 두 번 입력하지 않아도 되고 설정 불일치가 줄어든다.
  2. IAM 리소스 준비DMS가 원본 DB 자격 증명에 접근하도록 시크릿 접근 정책과 역할(IAM role, AWS 서비스가 다른 서비스를 대신 호출할 때 쓰는 권한 묶음)을 먼저 만든다. DMS는 이 역할로만 원본 데이터를 읽으므로 권한 범위가 명확해진다.
  3. 마이그레이션 실행과 모니터링데이터 마이그레이션을 설정하고 시작한 뒤, 진행 상황을 모니터링하면서 완료 여부를 확인하고 마이그레이션을 관리한다. 복제가 계속 돌아 원본과 대상이 맞춰진 상태로 전환된다.

#5한 줄 요약

인스턴스 수정·중지·시작·재부팅·이름 변경

실행 중인 DB 인스턴스의 설정을 바꾸거나, 일시적으로 중지·시작하고, 재부팅하거나 식별자 이름을 바꾸는 관리 작업이다.

#1문제 상황

DB 인스턴스는 한 번 만들면 끝이 아니라 운영 중에 설정을 바꾸고, 잠깐 멈추고, 다시 켜야 하는 일이 계속 생긴다. 문제는 이런 변경이 아무 때나 즉시 적용되지 않는다는 점이다. 인스턴스 클래스나 파라미터를 바꾸면 재부팅이 필요할 수 있고, 변경 사항을 곧바로 반영하면 서비스가 끊긴다. 그래서 예약된 유지보수 기간에 적용하도록 미루는 예약 변경(deferred modification)이 필요하다. 또한 사용하지 않는 개발·테스트 인스턴스를 멈추지 않으면 비용이 계속 나가지만, 중지와 시작을 아무렇게나 하면 스냅샷·자동 백업과의 관계가 꼬인다. 식별자 이름을 바꾸는 것도 접속 문자열·모니터링·태그가 함께 따라오지 않으면 관리가 어긋난다.

#2핵심 질문

실행 중인 DB 인스턴스의 설정과 상태를, 서비스 중단을 통제하면서 안전하게 바꾸려면 어떻게 해야 할까?

#3동작 예시

개발용 MySQL 인스턴스의 인스턴스 클래스를 올려야 한다고 하자. 콘솔에서 "수정"을 열어 클래스를 바꾸고, "즉시 적용" 대신 "다음 유지보수 기간에 적용"을 고른다. 그러면 변경이 바로 반영되지 않고 예약된 상태로 남았다가, 정해진 기간에 자동으로 적용된다. 야간에만 쓰는 환경이면 "중지"로 인스턴스를 멈춰 컴퓨팅 비용을 아끼고, 다음 날 "시작"으로 다시 올린다.

#4동작 과정

  1. 설정 변경과 예약수정 작업에서 인스턴스 클래스·스토리지·파라미터 등 바꿀 항목을 지정한다. 즉시 적용할지 다음 유지보수 기간에 적용할지(예약 수정)를 고르고, 즉시 적용이 재부팅을 부르는 경우에는 예약으로 미뤄 중단을 통제한다.
  2. 중지·시작·재부팅쓰지 않는 동안 인스턴스를 중지해 비용을 줄이고 필요할 때 시작한다. 파라미터나 설정을 반영하려면 재부팅으로 인스턴스를 다시 올린다. 이때 스냅샷·자동 백업 정책과의 관계를 확인해야 한다.
  3. 식별자 이름 변경인스턴스의 식별자(인스턴스를 가리키는 고유 이름)를 바꾸고, 접속 설정과 모니터링·태그가 새 이름을 따라가도록 정리한다. 이름이 바뀌어도 데이터와 스냅샷은 그대로 유지된다.

유지보수와 엔진 업그레이드

AWS가 예약한 유지보수 기간에 패치를 적용하는 것과, 데이터베이스 엔진의 메이저·마이너 버전을 새 버전으로 올리는 작업이다.

#1문제 상황

DB 인스턴스는 그냥 두어도 안전해지지 않는다. 밑에 깔린 하드웨어, 운영체제, 데이터베이스 엔진 버전에 보안 문제가 생기면 AWS가 주기적으로 패치를 적용해야 한다. 문제는 이 패치가 공짜가 아니라는 점이다. 유지보수 항목 중 일부는 인스턴스를 잠시 오프라인으로 만들어야 하고, 운영 중에 예고 없이 적용되면 서비스가 끊긴다. 엔진 버전도 마찬가지다. 오래된 버전을 계속 쓰면 보안·호환성 문제가 쌓이는데, 메이저 버전을 올리는 작업은 데이터 형식이나 동작이 바뀔 수 있어 신중해야 한다. 게다가 지원이 끝난 버전을 계속 쓰면 추가 요금이 붙는다.

#2핵심 질문

서비스 중단을 최소화하면서 보안 패치와 엔진 버전 업그레이드를 언제, 어떻게 적용할 것인가?

#3동작 예시

인스턴스에 적용 대기 중인 유지보수가 있다고 하자. 콘솔의 "유지보수" 목록에서 보류 중인 항목을 확인하고, 미리 정해 둔 유지보수 기간에 자동 적용되도록 두거나 원하는 시점에 직접 적용한다. 엔진 업그레이드는 새 버전을 지정해 실행하고, 패치 적용 전에는 스냅샷을 남겨 문제가 생기면 그 시점으로 되돌릴 수 있게 한다. 여러 버전이 지원 종료를 앞두고 있으면 지원 날짜를 확인해 미리 올린다.

#4동작 과정

  1. 대기 중 유지보수 확인보류 중인 유지보수 항목(하드웨어·운영체제·엔진 패치)을 조회한다. 어떤 항목이 오프라인을 요구하는지 파악해 적용 시점을 계획한다.
  2. 유지보수 기간에 적용미리 정한 유지보수 기간에 패치를 적용한다. Multi-AZ 배포처럼 대기 인스턴스가 있으면 역할을 넘겨가며 중단을 줄이고, 어쩔 수 없이 오프라인이 되는 항목은 그 시간을 감수한다.
  3. 엔진 버전 업그레이드와 되돌리기새 엔진 버전을 지정해 업그레이드하고, 필요하면 보존한 스냅샷으로 되돌린다. 지원이 끝난 버전은 추가 요금이 붙으므로 지원 날짜를 확인해 그 전에 올린다.

#5한 줄 요약

보안 패치와 엔진 업그레이드를 유지보수 기간에 통제해 적용하고, 지원 종료 버전은 미리 올려 서비스 중단과 추가 비용을 함께 줄이는 것

읽기 전용 복제본

원본 DB 인스턴스의 데이터를 비동기로 복제해 읽기 전용 쿼리를 분산 처리할 수 있게 만든 별도의 DB 인스턴스다.

#1문제 상황

하나의 DB 인스턴스로 모든 요청을 처리하면, 읽기 쿼리가 몰릴 때 쓰기와 읽기가 같은 인스턴스 자원을 두고 경쟁한다. 조회 위주 서비스에서는 읽기 트래픽이 쓰기보다 훨씬 많은데, 인스턴스 하나로는 읽기 부하를 늘릴 방법이 인스턴스 크기를 키우는 것밖에 없다. 이 방식은 비용이 급격히 오르고, 그 인스턴스 한 대가 죽으면 읽기와 쓰기가 함께 멈춘다. 읽기 요청만 따로 받아 줄 사본이 있어도, 원본과 데이터가 어긋나면 잘못된 값을 돌려주게 된다.

#2핵심 질문

쓰기는 원본에서 처리하되, 읽기 부하를 원본 밖으로 늘려 확장하려면 어떻게 해야 할까?

#3동작 예시

원본(프라이머리) 인스턴스에서 읽기 전용 복제본을 하나 만든다. 애플리케이션은 쓰기 쿼리는 원본으로, 조회 쿼리는 복제본 주소로 보낸다. 원본에 데이터가 바뀌면 RDS가 DB 엔진의 복제 기능을 이용해 그 변경을 복제본으로 계속 흘려보낸다. 그래서 복제본에는 항상 원본의 최신에 가까운 사본이 있고, 그 위에서 읽기만 처리한다.

#4동작 과정

  1. 복제본 생성원본 DB 인스턴스에서 읽기 전용 복제본을 만든다. RDS가 DB 엔진의 내장 복제 기능으로 원본과 복제본을 연결하고, 원본은 프라이머리 역할을 맡는다.
  2. 읽기 분산애플리케이션이 조회 쿼리를 복제본으로 보낸다. 원본은 쓰기와 복제 전송에 집중하고, 복제본이 읽기를 나눠 처리해 읽기 부하가 원본 밖으로 분산된다.
  3. 모니터링과 승격복제가 원본보다 얼마나 뒤처졌는지(복제 지연)를 모니터링한다. 복제본을 독립된 원본으로 승격(promotion)해 쓰기까지 맡게 하거나, 리전을 넘어 복제본을 두어 다른 지역의 읽기를 담당하게 할 수 있다.

#5한 줄 요약

원본의 데이터를 비동기로 복제한 읽기 전용 사본을 만들어, 읽기 부하를 원본 밖으로 늘려 확장하는 것

스토리지 관리

DB 인스턴스에 연결된 스토리지의 용량을 늘리거나 IOPS를 조정하고, 스토리지 자동 확장을 설정하는 작업이다.

#1문제 상황

DB 인스턴스를 만들 때 고른 스토리지 크기와 유형은 처음부터 딱 맞지 않는다. 데이터가 쌓이면서 용량이 차고, 트래픽 특성이 바뀌면 처리량이나 IOPS(초당 입출력 처리 횟수)가 부족해진다. 그렇다고 인스턴스를 새로 만들어 데이터를 옮기는 것은 큰 중단을 부른다. 반대로 쓰지 않는 여유 공간을 과하게 잡아 두면 비용만 나간다. 초기 예측이 틀렸을 때 인스턴스를 갈아엎지 않고 저장 능력을 조정할 방법이 필요하다.

#2핵심 질문

서비스를 멈추지 않고 스토리지의 용량과 성능을 키우거나 자동으로 늘릴 수는 없을까?

#3동작 예시

운영 중인 인스턴스의 여유 공간이 줄어들고 있다고 하자. 콘솔에서 스토리지 크기를 늘리도록 수정하면, 기존 데이터를 유지한 채 스토리지 볼륨이 확장된다. IOPS 설정도 함께 조정해 처리량을 올릴 수 있고, 스토리지 자동 확장(autoscaling)을 켜 두면 임계치에 도달했을 때 RDS가 용량을 스스로 늘린다. 파일 시스템 업그레이드가 필요한 경우에는 그 절차가 별도로 수행된다.

#4동작 과정

  1. 볼륨 정보 확인인스턴스에 연결된 스토리지 볼륨의 유형·크기·IOPS를 확인한다. 현재 용량이 얼마나 차 있는지, 처리량이 병목인지 판단한다.
  2. 용량·성능 조정수정 작업으로 스토리지 크기를 늘리거나 유형을 바꾸고 IOPS를 조정한다. 기존 데이터를 유지한 채 확장되며, 필요한 경우 스토리지 파일 시스템 업그레이드가 수행된다.
  3. 자동 확장 설정스토리지 자동 확장을 켜 두면 여유 공간이 임계치 아래로 내려갈 때 RDS가 자동으로 용량을 늘린다. 미리 크기를 예측하지 못해도 데이터 증가에 맞춰 대응한다.

#5한 줄 요약

인스턴스를 다시 만들지 않고 스토리지의 용량과 IOPS를 조정하고 자동 확장으로 데이터 증가에 대응하는 것

태그와 ARN

RDS 리소스에 키-값 태그를 붙여 분류·과금·자동화에 활용하고, 리소스를 고유하게 가리키는 Amazon 리소스 이름(ARN)을 구성·조회하는 방법이다.

#1문제 상황

DB 인스턴스와 스냅샷이 늘어나면 어느 것이 어느 팀·환경·용도에 속하는지 알기 어려워진다. 이름만으로는 비용을 팀별로 나누거나, 특정 조건의 인스턴스만 골라 작업하기가 힘들다. 그리고 콘솔에서는 이름으로 리소스를 찾을 수 있지만, CLI나 API로 자동화할 때는 리소스를 정확히 가리키는 고유 식별자가 필요하다. 이 식별자를 직접 조립하려면 리전·계정·리소스 종류·이름을 정해진 순서로 맞춰야 해서, 조금만 틀려도 대상 지정이 실패한다.

#2핵심 질문

수많은 RDS 리소스를 분류·관리하고 자동화에서 정확히 가리키려면 어떻게 해야 할까?

#3동작 예시

DB 인스턴스에 "Environment=Production", "Team=Payments" 같은 키-값 태그를 붙여 둔다. 그러면 비용 보고서에서 팀·환경별로 지출을 나눠 볼 수 있고, "이 태그가 붙은 인스턴스만 중지" 같은 작업도 태그를 조건으로 지정해 실행할 수 있다. CLI나 API로 그 인스턴스를 다룰 때는 태그가 아니라 ARN(Amazon Resource Name, 리소스를 리전·계정·종류·이름으로 고유하게 가리키는 식별자)을 넘겨 대상을 명확히 지정한다.

#4동작 과정

  1. 태그 부여리소스에 이름(key)과 선택적 값(value)으로 이루어진 태그를 붙인다. 콘솔·CLI·API로 추가·조회·삭제할 수 있고, 태그로 인스턴스·스냅샷·클러스터 등을 용도별로 분류한다.
  2. 분류·과금·자동화 활용태그를 비용 배분과 조건별 자동 작업에 쓴다. 예를 들어 특정 태그가 붙은 인스턴스만 골라 중지하는 식으로 대상 집합을 정의한다.
  3. ARN으로 대상 지정CLI·API로 작업할 때는 리소스의 ARN을 구성해 전달한다. ARN은 리전·계정·리소스 종류·이름을 담아 리소스를 고유하게 가리키므로, 기존 ARN을 조회해 그대로 사용하면 대상 지정 오류를 줄인다.

#5한 줄 요약

키-값 태그로 RDS 리소스를 분류·과금·자동화에 활용하고, ARN으로 각 리소스를 고유하게 가리키는 것

DB 인스턴스 삭제

더 이상 필요 없는 DB 인스턴스를 종료하고, 설정에 따라 최종 스냅샷을 남기거나 함께 삭제하는 작업이다.

#1문제 상황

DB 인스턴스를 그냥 없애면 그 안에 있던 데이터가 전부 사라지고, 연결되어 있던 리소스에도 영향을 준다. 그래서 삭제는 아무 때나 눌러도 되는 버튼이 아니라, 남길 데이터를 먼저 챙겨야 하는 위험한 작업이다.

게다가 콘솔에서 만든 DB 인스턴스는 기본적으로 삭제 방지(deletion protection)가 켜져 있어, 그대로는 삭제가 진행되지 않는다. 또 다른 가용 영역에 예비 인스턴스가 있는 경우에는 삭제 순서나 대기 상태 때문에 마음대로 종료되지 않는다. 삭제하려는 사람이 이런 조건을 모르면 "왜 안 지워지지"만 반복하게 된다.

#2핵심 질문

더 이상 필요 없는 DB 인스턴스를 데이터 손실 없이 안전하게 종료하려면, 어떤 조건을 먼저 풀고 무엇을 남겨야 하는가?

#3동작 예시

운영을 끝낸 테스트용 DB 인스턴스 하나를 지운다고 하자. 삭제를 요청할 때 마지막 스냅샷 생성 여부를 함께 고르면, RDS는 인스턴스를 종료하기 직전에 그 시점의 데이터를 스냅샷으로 떠서 남긴다. 스냅샷을 남기지 않기로 하면 인스턴스와 데이터가 함께 사라진다. 즉 같은 삭제라도 마지막 스냅샷 선택 하나로 결과가 달라진다.

#4동작 과정

  1. 삭제 방지 해제삭제 방지가 켜져 있으면 인스턴스 설정을 수정(modify)해 먼저 꺼 둔다. 이 단계를 건너뛰면 삭제 요청이 거부된다.
  2. 삭제 요청과 마지막 스냅샷 선택콘솔·AWS CLI·RDS API로 삭제를 요청하면서, 최종 스냅샷을 만들지 여부를 지정한다. 스냅샷을 남기면 데이터를 나중에 복원할 여지가 생긴다.
  3. 종료와 정리인스턴스가 삭제되고, 남기기로 한 스냅샷만 보존된다. 스냅샷을 남기지 않았다면 데이터는 복구할 수 없다.

#5한 줄 요약

데이터를 남길지 결정한 뒤 삭제 방지 같은 조건을 풀고 DB 인스턴스를 안전하게 종료하는 절차

Multi-AZ DB 인스턴스 배포

프라이머리 DB 인스턴스와 다른 가용 영역(AZ)의 예비(standby) 인스턴스를 동기식으로 복제해 두고, 장애 발생 시 자동으로 예비 인스턴스로 장애 조치(failover)하는 고가용성 배포 방식.

→ 04-02 참조

#1문제 상황

DB 인스턴스를 하나만 띄워 두면, 그 인스턴스가 있는 가용 영역(AZ, 데이터센터 묶음)에 장애가 나는 순간 서비스 전체가 멈춘다. 백업이 있어도 복원에는 시간이 걸리므로, 장애가 나는 동안 계속 서비스가 죽어 있는 문제를 없애기 어렵다.

수동으로 예비 서버를 세워 두는 방법도 있지만, 프라이머리와 데이터를 계속 똑같이 맞춰 두는 일은 사람이 관리하기 버겁다. 복제가 밀리거나 어긋나면 막상 장애가 났을 때 예비 서버로 넘어가지 못한다.

#2핵심 질문

프라이머리 인스턴스에 장애가 나도 사람이 개입하지 않고 자동으로 다른 인스턴스로 서비스를 이어 갈 수 있는가?

#3동작 예시

서로 다른 가용 영역에 프라이머리와 예비(standby) 인스턴스를 하나씩 둔다. 애플리케이션은 프라이머리에만 연결해 쓰고, RDS는 같은 데이터 변경을 예비 인스턴스에도 동기식으로 반영해 둔다. 프라이머리가 죽으면 RDS가 예비 인스턴스를 새 프라이머리로 승격하고, 애플리케이션의 연결은 새 프라이머리로 넘어간다.

#4동작 과정

  1. 배포와 동기 복제RDS가 다른 가용 영역에 예비 인스턴스를 자동으로 만들고, 프라이머리에 들어온 변경을 동기식(쓰기가 양쪽에 반영될 때까지 기다리는 방식)으로 복제한다. 그래서 예비 인스턴스는 항상 최신 상태를 유지한다.
  2. 장애 감지프라이머리 인스턴스나 그 가용 영역에 문제가 생기면 RDS가 이를 감지한다. 이때 엔진에 따라 Amazon 장애 조치 기술을 쓰거나 SQL Server의 미러링·가용성 그룹을 사용한다.
  3. 자동 장애 조치예비 인스턴스가 새 프라이머리로 승격되고 연결이 그쪽으로 옮겨 간다. 사용자는 같은 엔드포인트를 그대로 쓰고, 서비스는 사람 손 없이 다시 살아난다.

#5한 줄 요약

다른 가용 영역에 동기식으로 복제된 예비 인스턴스를 두어 장애 시 자동으로 넘겨받게 하는 고가용성 배포

Multi-AZ DB 클러스터

서로 다른 세 가용 영역에 라이터 DB 인스턴스 1개와 리더 DB 인스턴스 2개를 두고 반동기식 복제로 운영하여 단일 인스턴스 방식보다 빠른 장애 조치와 읽기 확장을 제공하는 클러스터 배포 방식.

→ 04-01 참조

#1문제 상황

Multi-AZ DB 인스턴스 배포는 장애 조치를 자동으로 해 주지만, 예비 인스턴스가 읽기 요청을 처리하지는 못한다. 프라이머리 하나가 모든 읽기와 쓰기를 감당해야 하므로, 읽기 트래픽이 몰리면 성능이 한계에 부딪힌다.

또 장애 조치에 걸리는 시간도 짧지 않아, 서비스가 잠깐 멈추는 구간이 생긴다. 단일 인스턴스 구조를 그대로 두고 가용성만 얹는 방식으로는 읽기 확장과 빠른 복구를 동시에 잡기 어렵다.

#2핵심 질문

장애 조치를 더 빠르게 하면서 읽기 요청까지 여러 인스턴스로 나눠 처리할 수 있는가?

#3동작 예시

같은 리전 안의 서로 다른 세 가용 영역에 라이터 DB 인스턴스 1개와 리더 DB 인스턴스 2개를 둔다. 쓰기는 라이터가 맡고, 읽기는 리더 두 대로 분산된다. 라이터에 장애가 나면 두 리더 중 하나가 라이터로 승격되어, 단일 인스턴스 방식보다 빠르게 서비스가 이어진다.

#4동작 과정

  1. 클러스터 구성RDS가 세 가용 영역에 라이터 1개와 리더 2개를 배치하고, 반동기식(쓰기를 라이터에 반영한 뒤 복제를 이어 가는 방식) 복제로 데이터를 맞춘다. 그 결과 읽기 트래픽을 리더들로 나눌 수 있다.
  2. 읽기 분산과 연결읽기 전용 연결은 리더 인스턴스로, 쓰기 연결은 라이터로 간다. AWS가 제공하는 드라이버나 RDS Proxy를 쓰면 이 연결 선택을 애플리케이션이 직접 관리하지 않아도 된다.
  3. 장애 조치라이터에 문제가 생기면 리더 중 하나가 라이터로 승격되고 연결이 그쪽으로 넘어간다. 리더가 하나 줄 뿐 클러스터 전체는 계속 동작한다.

#5한 줄 요약

세 가용 영역에 라이터 1개와 리더 2개를 두어 읽기 확장과 빠른 장애 조치를 함께 얻는 클러스터 배포

Blue/Green 배포

현재 운영 환경(blue)과 동일하게 복제된 스테이징 환경(green)을 만들어 변경 사항을 검증한 뒤 트래픽을 green으로 전환(switchover)함으로써 다운타임과 위험을 최소화하는 배포 방식.

#1문제 상황

운영 중인 DB의 엔진 버전을 올리거나 파라미터를 바꾸려면, 보통 그 인스턴스 자체를 수정해야 한다. 이때 변경이 예상대로 되지 않으면 운영 서비스가 곧바로 영향을 받고, 문제를 되돌리는 데도 시간이 걸린다.

테스트 서버에 미리 해 보는 방법도 있지만, 실제 운영 데이터와 설정을 그대로 복제한 환경이 아니면 검증 결과를 믿기 어렵다. 결국 "검증은 따로, 적용은 운영에서"라는 간극이 사고 위험을 키운다.

#2핵심 질문

운영 환경을 건드리지 않고 변경 사항을 실제와 같은 환경에서 검증한 뒤 안전하게 적용할 수 있는가?

#3동작 예시

현재 운영 환경을 blue로 두고, 이를 그대로 복제한 staging 환경을 green으로 만든다. green에서만 엔진 버전을 올리거나 파라미터를 바꾸며 마음껏 시험한다. 준비가 끝나면 switchover(전환)를 실행해 green을 새 운영 환경으로 바꾸고, 트래픽이 green으로 넘어간다.

#4동작 과정

  1. green 환경 생성blue 운영 환경의 DB 인스턴스를 복제해 green staging 환경을 만든다. green은 blue와 계속 동기화되어 실제 운영과 같은 상태를 유지한다.
  2. 변경과 검증운영에 영향 없이 green에서만 메이저·마이너 엔진 버전 업그레이드, 파일 시스템 설정 변경, 파라미터 변경 등을 적용하고 충분히 테스트한다. 문제가 있으면 green만 버리면 되고 운영은 그대로다.
  3. switchover 전환검증이 끝나면 전환을 실행해 green이 새 운영 환경이 된다. 이름이 바뀌고 트래픽이 넘어가며, 다운타임과 위험이 최소화된다.

#5한 줄 요약

운영을 복제한 staging 환경에서 변경을 검증한 뒤 전환으로 새 환경에 넘겨 다운타임과 위험을 줄이는 배포 방식

자동 백업

RDS가 매일 자동으로 전체 스냅샷을 찍고 트랜잭션 로그를 계속 보관해, 정해진 보존 기간 안의 임의 시점으로 복구할 수 있게 해 주는 백업 방식이다.

#1문제 상황

데이터를 지키려면 백업을 사람이 직접 챙겨야 하는데, 바쁜 운영 중에 정해진 시각마다 빠짐없이 백업을 뜨는 일은 현실적으로 어렵다. 백업을 깜빡하거나 시점을 놓치면 그만큼 복구할 수 없는 구간이 생긴다.

또 하루 한 번 전체 백업만 있으면, 장애가 난 그 순간이 아니라 마지막 백업 시점으로만 되돌릴 수 있다. 백업 이후에 들어온 데이터는 복구 범위 밖으로 밀려난다.

#2핵심 질문

사람이 매번 신경 쓰지 않아도, 정해 둔 기간 안의 원하는 시점으로 데이터를 되돌릴 수 있는가?

#3동작 예시

DB 인스턴스의 백업 윈도우(백업을 수행하도록 정해 둔 시간대)가 되면, RDS가 인스턴스 전체의 스토리지 볼륨 스냅샷을 자동으로 뜬다. 여기에 트랜잭션 로그를 계속 보관해 두기 때문에, 백업 시점뿐 아니라 보존 기간 안의 임의 시점으로 복구하는 point-in-time recovery가 가능해진다.

#4동작 과정

  1. 자동 백업 생성인스턴스가 available 상태일 때 백업 윈도우에 맞춰 RDS가 전체 스토리지 볼륨 스냅샷을 만든다. 개별 데이터베이스가 아니라 인스턴스 전체를 백업하는 방식이다.
  2. 로그 보관과 보존 기간 관리트랜잭션 로그를 계속 쌓아 두고, 사용자가 지정한 백업 보존 기간에 따라 보관한다. 이 기간이 곧 되돌릴 수 있는 시점의 범위가 된다.
  3. 임의 시점 복구장애가 나면 보존 기간 안의 원하는 시점을 골라 복구한다. 백업 시점 하나가 아니라 그 사이 어느 지점으로도 되돌릴 수 있다.

#5한 줄 요약

백업 윈도우마다 전체 스냅샷과 트랜잭션 로그를 자동으로 보관해 보존 기간 안의 임의 시점으로 복구하게 하는 백업 방식

수동 스냅샷

사용자가 원하는 시점에 직접 만들어 보존 기간 제한 없이 남겨 두는 DB 스냅샷으로, 삭제하기 전까지 계속 유지된다.

#1문제 상황

자동 백업은 보존 기간이 정해져 있어, 그 기간이 지나면 오래된 백업이 사라진다. 그래서 버전 업그레이드 직전이나 중요한 배포 전처럼, 특정 시점의 상태를 오래 남겨 두고 싶은 경우에는 자동 백업만으로 부족하다.

또 자동 백업만으로는 "이 시점 데이터를 따로 보관해 두자"라는 사용자의 판단을 반영할 수 없다. 지워지면 안 되는 데이터를 장기간 붙잡아 두려면 별도의 수단이 필요하다.

#2핵심 질문

보존 기간에 묶이지 않고, 내가 원하는 시점의 데이터를 내가 지우기 전까지 계속 남길 수 있는가?

#3동작 예시

메이저 버전 업그레이드를 하기 전에, 지금 운영 중인 DB 인스턴스의 스냅샷을 손으로 하나 만든다. 이 스냅샷은 자동 백업과 달리 보존 기간의 영향을 받지 않고, 사용자가 삭제할 때까지 그대로 남는다. 업그레이드 후 문제가 생기면 이 스냅샷에서 이전 상태로 되돌릴 수 있다.

#4동작 과정

  1. 스냅샷 생성사용자가 원하는 시점에 콘솔·CLI·API로 수동 스냅샷을 만든다. Single-AZ DB 인스턴스와 Multi-AZ DB 클러스터 각각에 맞는 방식으로 생성한다.
  2. 무기한 보존만들어진 스냅샷은 보존 기간 제한 없이 계속 유지된다. 자동 백업이 정리되어도 이 스냅샷은 남는다.
  3. 삭제더 이상 필요 없으면 사용자가 직접 삭제한다. 직접 지우기 전까지는 계속 남아 있으므로 장기 보관용으로 쓸 수 있다.

#5한 줄 요약

사용자가 원하는 시점에 직접 만들어 보존 기간에 묶이지 않고 삭제할 때까지 유지되는 DB 스냅샷

복원과 시점 복구

저장된 스냅샷이나 백업에서 새 DB 인스턴스를 만들어 되돌리거나, 자동 백업 로그를 이용해 원하는 특정 시각의 상태로 복구하는 작업이다.

→ 05-01 참조

#1문제 상황

DB를 운영하다 보면 데이터가 잘못 삭제되거나, 응용 프로그램의 오류로 잘못된 값이 대량으로 덮여 쓰이는 일이 생긴다. 문제를 발견했을 때는 이미 한참 지난 뒤여서, 그 사이에 정상이던 시점을 정확히 골라 되돌려야 하는 상황이 된다. RDS는 하루 단위 전체 스냅샷만 있으면 이 중간 시점을 복구할 수 없어, 백업 시각과 사고 시각 사이의 변경분을 사람이 수작업으로 메꿔야 했다.

#2핵심 질문

스냅샷과 자동 백업 로그만으로 원하는 특정 시각의 상태로 DB를 되돌릴 수 있을까?

#3동작 예시

자동 백업이 켜진 DB에서 실수로 오늘 오전 9시 40분에 테이블 하나를 지웠다고 하자. 사용자는 9시 39분을 복구 시점으로 지정해 복원을 요청한다. RDS는 가장 가까운 스냅샷에 그 시각까지의 변경 로그를 순서대로 적용해, 삭제 직전 상태의 데이터를 담은 새 DB 인스턴스를 만들어 준다.

#4동작 과정

  1. 복구 시점 지정되돌리고 싶은 시각을 정한다. 시점 복구(point-in-time recovery)는 자동 백업 보존 기간 안의 임의 시각을 지정할 수 있고, 스냅샷 복원은 특정 스냅샷 하나를 고른다.
  2. 새 인스턴스 생성RDS는 지정한 스냅샷 위에 그 시각까지의 로그를 반영해 새 DB 인스턴스를 만든다. 기존 인스턴스에 덮어쓰는 방식이 아니라 항상 새 인스턴스가 생기며, 상태가 사용 가능(available)해지면 바로 접속할 수 있다.
  3. 백그라운드 로딩복원된 인스턴스는 데이터를 전부 다 내려받기 전에도 먼저 사용할 수 있게 열어 주고, 나머지는 뒤에서 계속 채운다. 아직 안 올라온 데이터에 접근하면 그 부분만 곧바로 저장소에서 가져온 뒤 나머지 로딩을 이어 간다.

#5한 줄 요약

저장된 스냅샷과 그 이후의 변경 로그를 원하는 시점까지 재적용해 새 DB 인스턴스로 되돌리는 것

스냅샷 복사·공유·내보내기·AWS Backup

스냅샷을 다른 리전으로 복사하거나 다른 계정과 공유하고, S3로 내보내며, AWS Backup으로 중앙 관리하는 데이터 보호 기능이다.

#1문제 상황

스냅샷은 기본적으로 만들어진 리전과 계정 안에만 머문다. 리전 장애에 대비하려면 다른 리전에 사본이 있어야 하고, 다른 팀이나 다른 계정에 데이터를 넘기려면 권한을 부여해야 한다. 또 스냅샷은 RDS가 관리하는 형식이라 외부 분석 도구로 바로 읽을 수 없고, 백업이 여러 서비스에 흩어지면 보존 정책을 한곳에서 관리하기 어렵다.

#2핵심 질문

스냅샷을 다른 리전·다른 계정으로 옮기고 외부에서 쓸 수 있게 꺼내며, 여러 백업을 한곳에서 관리하려면 어떻게 해야 할까?

#3동작 예시

운영 리전에 있는 수동 스냅샷을 재해 복구용 리전으로 복사해 두고, 같은 스냅샷을 협력 계정과 공유해 그 계정이 자기 DB 인스턴스로 복원하게 한다. 별도로 스냅샷 데이터를 Amazon S3로 내보내 외부 도구가 읽을 수 있게 하고, 자동 백업은 AWS Backup으로 중앙에서 보존 기간과 일정을 관리한다.

#4동작 과정

  1. 복사·공유스냅샷을 다른 리전으로 복사해 리전 장애에 대비한다. 다른 계정과는 공유 설정으로 접근 권한을 주며, 암호화된 스냅샷은 허용할 키 조건을 함께 지정해야 공유가 성립한다. 공유를 중단하면 상대 계정의 접근이 끊긴다.
  2. S3로 내보내기스냅샷 데이터를 Amazon S3로 내보내면 RDS 밖의 분석 도구로 읽을 수 있다. 내보내기 작업의 진행 상황을 모니터링하고, 필요하면 진행 중인 내보내기를 취소한다. 권한이나 형식 문제로 실패하면 실패 메시지로 원인을 확인한다.
  3. 중앙 관리와 확인AWS Backup에 자동 백업을 맡기면 보존·일정 정책을 여러 리소스에 한 번에 적용해 관리할 수 있다. 내보낸 파일은 정해진 명명 규칙으로 저장되고 값은 도구가 읽을 수 있는 형식으로 변환된다.

#5한 줄 요약

스냅샷을 다른 리전·계정으로 옮기고 외부에서 읽을 수 있게 꺼내며 여러 백업을 중앙에서 관리하는 것

모니터링과 로그 — 상태 파악06-01

모니터링 도구와 권장 사항

Amazon RDS가 제공하는 지표·로그·이벤트·OS 지표 등 여러 모니터링 수단의 종류와 용도를 정리하고, RDS가 제시하는 권장 사항을 확인하는 개요 영역이다.

#1문제 상황

DB 성능이 나빠지거나 장애가 났을 때, 무엇을 어디서 확인해야 하는지 모르면 원인 파악이 늦어진다. 지표, 로그, 이벤트, 운영체제 수준 정보가 서로 다른 도구에 흩어져 있어, 관리자가 어느 화면을 봐야 하는지 매번 판단해야 한다. RDS가 이미 이상 징후를 감지하고 권장 조치를 제시해 주는데도 이를 놓치면 같은 문제를 반복하게 된다.

#2핵심 질문

RDS의 여러 모니터링 수단을 어떤 기준으로 골라 쓰고, RDS가 알려 주는 권장 사항을 어떻게 확인하고 반영할까?

#3동작 예시

DB 인스턴스의 현재 상태 화면에서 인스턴스가 정상인지, RDS가 어떤 권장 사항을 띄웠는지 먼저 본다. 그다음 평소보다 CPU가 튀는지 CloudWatch 지표로 확인하고, 프로세스 단위 원인은 Enhanced Monitoring으로 좁힌다. 문제가 잡히면 권장 사항을 그대로 적용하거나, 해당 없으면 무시 처리한다.

#4동작 과정

  1. 수단 구분모니터링 도구는 자동과 수동으로 나뉜다. 자동 도구는 인스턴스 상태·권장 사항, CloudWatch 지표, Enhanced Monitoring, 연동 서비스로 구성되고, 수동 도구는 관리자가 직접 열어 확인하는 화면들이다. 되도록 자동화하도록 권장된다.
  2. 상태·권장 확인인스턴스 상태 화면에서 현재 상태 세부 정보를 보고, RDS가 제시하는 권장 사항 목록을 확인한다. 권장 사항을 그대로 적용해 조치하거나, 지금은 필요 없다고 판단되면 무시 처리해 목록에서 내린다.
  3. 재검토무시했던 권장 사항도 상황이 바뀌면 다시 활성 상태로 되돌려 검토할 수 있다. 각 권장 사항의 의미와 적용 조건은 권장 사항 참조 문서에서 확인한다.

#5한 줄 요약

흩어진 여러 모니터링 수단과 RDS의 권장 사항을 한데 모아, 문제를 빠르게 찾고 조치하도록 이끄는 것

콘솔 지표와 CloudWatch 알람

RDS 콘솔에서 DB 인스턴스의 CloudWatch 지표를 확인하고, 임계값을 기준으로 경보를 울리는 CloudWatch 알람을 생성하는 방법이다.

#1문제 상황

DB가 정상 범위 안에서 도는지 사람이 계속 화면을 들여다볼 수는 없다. 특정 지표가 임계값을 넘는 순간을 놓치면 성능 저하나 장애로 이어지는데, 지표를 봐도 어느 수준이 위험한지 기준이 없으면 판단이 늦어진다. 게다가 원인을 찾으려면 여러 지표를 시간 축으로 나란히 놓고 비교해야 한다.

#2핵심 질문

DB 지표를 콘솔에서 한눈에 보고, 위험한 임계값을 넘으면 자동으로 알림을 받으려면 어떻게 해야 할까?

#3동작 예시

RDS 콘솔의 DB 인스턴스 화면에서 CloudWatch 지표 그래프를 연다. 읽기 지연이 평소보다 치솟는 구간을 시간 축으로 확인한 뒤, 그 지표에 "이 값을 넘으면 경보"라는 임계값을 걸어 두면, 다음에 같은 상황이 오면 CloudWatch가 자동으로 알림을 보낸다.

#4동작 과정

  1. 지표 확인RDS는 CloudWatch와 연동해 다양한 DB 인스턴스 지표를 콘솔에 보여준다. 각 지표는 특정 시간 구간의 변화를 그래프로 그려 주며, 같은 지표를 CloudWatch 콘솔에서도 볼 수 있다.
  2. OS 지표 함께 보기Enhanced Monitoring을 켜 둔 인스턴스라면 콘솔에서 운영체제 수준 지표 요약도 함께 볼 수 있다. 이 지표들도 시간 구간별 그래프로 표시된다.
  3. 알람 생성특정 지표에 임계값을 정해 CloudWatch 알람을 만든다. 임계값을 넘으면 경보가 울려 관리자가 자동으로 통보받는다. 예를 들어 DB 클러스터 복제 지연 같은 지표로 알람을 구성할 수 있다.

RDS 지표를 CloudWatch와 연동해 콘솔에서 보고 임계값 기준 알람으로 위험을 자동 통보하는 것

Database Insights와 Performance Insights

DB 부하를 세션·대기 이벤트 단위로 분석하고 느린 쿼리와 자원 사용을 진단하는 Database Insights(및 그 안의 Performance Insights) 모니터링 기능이다.

→ 06-05 참조

#1문제 상황

서버 지표만 보면 CPU와 메모리가 높다는 사실은 알 수 있지만, 어떤 세션이 어떤 대기 이벤트 때문에 DB를 붙잡고 있는지는 알기 어렵다. 여러 쿼리가 섞여 돌 때 범인을 특정하지 못하면 튜닝이 감으로 흐른다. 느린 쿼리와 자원 사용을 세션·대기 단위로 쪼개 보여 주는 도구가 따로 필요하다.

#2핵심 질문

DB 부하를 세션·대기 이벤트 단위로 쪼개서 느린 쿼리와 자원 사용의 원인을 어떻게 찾아낼까?

#3동작 예시

Database Insights 화면에서 부하 그래프를 열면, 어느 시각에 어떤 대기 이벤트가 DB 시간을 많이 잡아먹었는지 조각으로 나뉘어 표시된다. 그 조각을 따라가면 그 순간 실행되던 느린 쿼리와, 그 쿼리가 최대 CPU를 얼마나 썼는지까지 확인할 수 있다.

#4동작 과정

  1. 모드 선택과 켜기Database Insights는 지원하는 엔진·리전·인스턴스 클래스 조건 안에서 사용하며, Standard 모드와 Advanced 모드 중 하나로 켠다. Advanced 모드는 쿼리·데이터베이스 카운터 단위 지표를 더 세밀하게 다루며, 필요하면 이 상세 지표를 켜고 끌 수 있다.
  2. 부하 분석DB 부하를 CloudWatch와 함께 지표로 모니터링하고, 세션·대기 이벤트 단위로 나눠 어느 작업이 시간을 잡는지 본다. 최대 CPU 같은 값으로 그 순간의 자원 사용도 확인한다. Performance Insights API로 시계열 지표를 직접 받아올 수도 있다.
  3. 느린 쿼리와 권고 활용느린 쿼리를 골라 원인을 진단하고, Database Insights가 제시하는 사전 권장 사항을 참고한다. 접근 권한은 IAM 정책과 AWS KMS 정책, 세밀한 접근 제어와 태그 기반 접근 제어로 관리하며, 호출 기록은 AWS CloudTrail로 남긴다.

Enhanced Monitoring

DB 인스턴스가 실행되는 운영체제 수준의 CPU·메모리·디스크·네트워크 지표를 초 단위로 수집해 확인하는 모니터링 기능이다.

#1문제 상황

CloudWatch의 기본 DB 지표는 인스턴스 전체 수준의 값이라, CPU가 높을 때 어떤 프로세스나 스레드가 원인인지까지는 알려 주지 않는다. 원인을 좁히려면 운영체제 안에서 벌어지는 일을 더 잘게, 더 자주 들여다봐야 한다. 기본 지표만으로는 이런 프로세스·스레드 단위 정보가 빠져 있어 진단이 막힌다.

#2핵심 질문

DB 인스턴스 운영체제의 프로세스·스레드 단위 지표를 실시간에 가깝게 보려면 어떻게 해야 할까?

#3동작 예시

DB 인스턴스에서 Enhanced Monitoring을 켜면, 운영체제 수준의 CPU·메모리·디스크·네트워크 지표를 콘솔에서 확인할 수 있다. CPU 사용이 튀는 순간 어떤 프로세스와 스레드가 그 CPU를 쓰는지까지 함께 드러나, 원인을 그 자리에서 좁힐 수 있다.

#4동작 과정

  1. 설정 켜기Enhanced Monitoring은 설정 단계에서 인스턴스별로 켠다. 켜면 RDS가 DB 인스턴스가 실행되는 운영체제의 지표를 실시간에 가깝게 수집한다.
  2. 지표 확인콘솔에서 모든 시스템 지표와 프로세스 정보를 볼 수 있다. 인스턴스마다 어떤 지표를 볼지 관리하고 대시보드를 요구에 맞게 바꿀 수 있으며, 각 지표는 시간 구간별 그래프로 표시된다.
  3. 로그로 전달Enhanced Monitoring이 수집한 지표는 관리자의 CloudWatch Logs 계정으로 전달되어, 다른 로그·지표와 나란히 보관·조회할 수 있다.

DB 인스턴스 운영체제의 지표를 프로세스·스레드 단위로 실시간 수집해 원인 진단을 돕는 것

지표 레퍼런스

RDS가 CloudWatch로 내보내는 지표와 차원(dimension), Enhanced Monitoring의 OS 지표 등 각 지표의 의미와 단위를 정리한 참조 문서다.

→ 06-03 참조

#1문제 상황

DB 인스턴스가 느려지거나 멈췄을 때, 아무 숫자나 보면 원인을 알 수 없다. CPU가 높은지 디스크 입출력이 몰리는지 메모리가 부족한지 구분하지 못하면 조치가 엉뚱해진다.

게다가 RDS는 여러 도구가 서로 다른 지표를 내보낸다. CloudWatch, Performance Insights API, Enhanced Monitoring이 각각 다른 이름과 단위로 값을 제공하므로, 어떤 지표가 무엇을 뜻하고 어느 차원으로 걸러야 하는지 모르면 관제 화면의 숫자를 해석할 수 없다.

#2핵심 질문

각 모니터링 도구가 내보내는 지표의 이름·의미·단위·차원을 한곳에서 정확히 확인하려면 어떻게 해야 하는가?

#3동작 예시

RDS 콘솔이나 CloudWatch에서 CPU 지표 하나를 본다고 하자. 이때 DBInstanceIdentifier와 Engine 같은 차원(dimension, 지표를 특정 대상으로 좁히는 식별 키)을 지정해야 "어느 인스턴스의 어느 엔진" 값인지 확정된다. 차원 없이 이름만 보면 여러 인스턴스 값이 뒤섞여 해석할 수 없다. 지표 레퍼런스는 이 이름·차원·단위를 항목별로 나열한 표다.

#4동작 과정

  1. 수집RDS가 엔진과 호스트에서 CPU, 메모리, 디스크, 연결 수 같은 값을 주기적으로 수집해 CloudWatch, Performance Insights API, Enhanced Monitoring으로 내보낸다.
  2. 분류와 게시각 지표는 정해진 이름과 단위(예: 초당 횟수, 퍼센트, 바이트)로 게시되고, 특정 인스턴스를 가리키는 차원과 함께 저장된다. Enhanced Monitoring은 운영체제(OS) 수준 지표까지 별도로 제공한다.
  3. 참조레퍼런스 문서에서 지표 이름과 그 뒤 차원·단위 설명을 확인해, 값이 정상 범위인지 판단하고 원인 분석에 쓴다. Performance Insights의 SQL 통계 지표는 엔진별(MariaDB·MySQL·Oracle·SQL Server·PostgreSQL)로 항목이 나뉜다.

이벤트와 알림

DB 인스턴스의 상태 변화·장애·유지 관리 같은 이벤트를 조회하고, 이벤트 범주별로 구독을 만들어 이메일 등으로 알림을 받는 기능이다.

#1문제 상황

DB 인스턴스는 재시작, 장애 조치, 유지 관리 시작처럼 상태가 바뀌는 순간이 있다. 이런 변화를 사람이 콘솔을 계속 열어 확인하지 않으면, 문제가 터진 뒤에야 알게 된다.

지표 그래프만 봐서는 "언제 무슨 일이 일어났는지"를 알기 어렵다. 이벤트를 조회하고 통지하는 체계가 없으면, 상태 변화를 실시간으로 통보받지 못해 대응이 늦어진다.

#2핵심 질문

DB 인스턴스의 상태 변화·장애·유지 관리 이벤트를 어떻게 조회하고, 범주별로 구독해 자동으로 통보받을 수 있는가?

#3동작 예시

인스턴스 상태가 바뀌면 RDS가 이벤트를 하나 생성한다. 사용자는 이벤트 범주(예: 생성, 삭제, 구성 변경, 장애 조치, 유지 관리)를 골라 구독(subscription)을 만들고, 통지를 받을 이메일이나 대상과 특정 인스턴스를 가리키는 소스 식별자(source identifier)를 지정한다. 이후 그 범주에 해당하는 이벤트가 생기면 구독을 통해 자동으로 알림이 전달된다.

#4동작 과정

  1. 이벤트 생성RDS 환경에 변화가 생기면(예: 인스턴스 상태 변경) 시스템이 이벤트를 기록하고, 이 이벤트는 범주와 메시지로 분류된다.
  2. 조회콘솔이나 API로 최근 이벤트를 범주·기간별로 조회해 무슨 일이 있었는지 확인한다.
  3. 구독과 통지원하는 범주에 대해 구독을 만들고 소스 식별자를 붙이면, 해당 이벤트가 발생할 때 이메일 등으로 통지가 나간다. EventBridge 규칙을 만들면 RDS 이벤트를 트리거로 다른 작업을 자동 실행할 수도 있다.

로그

RDS가 수집하는 오류 로그·슬로우 쿼리 로그·일반 로그 등을 콘솔이나 API로 보고, 필요하면 CloudWatch Logs로 게시해 모니터링하는 방법이다.

#1문제 상황

지표는 "무엇이 느린가"를 숫자로 보여주지만 "왜 그런가"는 알려주지 않는다. 오류가 왜 났는지, 어떤 쿼리가 느린지는 DB 엔진이 남기는 로그를 봐야 알 수 있다.

그런데 로그는 엔진마다 종류와 위치가 다르다. 오류 로그, 슬로우 쿼리 로그, 일반 로그 등이 각각 따로 생성되고, 인스턴스에 접속하지 않으면 파일을 볼 수 없다면 추적이 번거롭고 오래된 로그는 사라지기 쉽다.

#2핵심 질문

DB 엔진이 남기는 오류·슬로우 쿼리·일반 로그를 콘솔이나 API로 보고, 필요하면 CloudWatch Logs로 보내 계속 모니터링하려면 어떻게 해야 하는가?

#3동작 예시

엔진은 감사와 문제 해결을 위해 로그를 생성한다. 사용자는 콘솔, AWS CLI, RDS API로 DB 인스턴스의 로그 파일을 나열하고 내용을 확인하거나 내려받을 수 있다. 트랜잭션 로그는 보고 감시하거나 내려받을 수 없다는 점이 다르다. 슬로우 쿼리 로그 파일을 열면 실행 시간이 긴 쿼리 목록을 실행 시각과 함께 볼 수 있다.

#4동작 과정

  1. 로그 생성과 조회엔진이 오류·슬로우 쿼리·일반 로그 등을 파일로 남기고, 사용자는 콘솔·CLI·API로 목록을 보고 내용을 확인하거나 내려받는다.
  2. 실시간 감시특정 로그 파일을 감시(watch)하면 새로 추가되는 줄을 실시간으로 따라가며 볼 수 있어, 재현 중인 문제를 즉시 확인한다.
  3. CloudWatch Logs로 게시로그를 CloudWatch Logs로 게시(publish)하도록 설정하면, 콘솔 밖에서도 로그를 모아 검색·보관하고 알람과 연계해 모니터링할 수 있다. 엔진별로 로그 종류와 게시 방법이 다르다.

#5한 줄 요약

DB 엔진이 남기는 오류·슬로우 쿼리·일반 로그를 조회하고 CloudWatch Logs로 게시해, 문제 원인을 추적하고 계속 감시하게 해주는 로그 접근 체계

모니터링과 로그 — 상태 파악06-08

CloudTrail·Database Activity Streams·GuardDuty

RDS API 호출 감사(CloudTrail), 데이터베이스 활동 스트림(Database Activity Streams), 위협 탐지(GuardDuty RDS Protection)로 보안·감사 이벤트를 모니터링하는 기능이다.

#1문제 상황

지표·이벤트·로그만으로는 보안과 감사 요구를 다 채우지 못한다. 누가 언제 RDS 설정을 바꿨는지(제어 평면 호출), 데이터베이스 안에서 어떤 활동이 오갔는지(데이터 활동), 외부에서 위협이 들어오는지(위협 탐지)는 서로 다른 층의 감시가 필요하다.

이 셋을 따로 마련하지 않으면, 구성 변경 이력이 남지 않아 감사에서 근거를 못 대고, DB 내부 활동을 추적하지 못하며, 의심스러운 접근을 조기에 발견하지 못한다.

#2핵심 질문

RDS API 호출 감사, 데이터베이스 활동 스트림, 위협 탐지를 각각 어떻게 설정해 보안·감사 이벤트를 모니터링하는가?

#3동작 예시

누군가 API로 인스턴스 설정을 바꾸면 CloudTrail이 그 호출을 기록에 남긴다. 데이터베이스 활동 스트림(Database Activity Streams)을 시작하면 DB 안에서 일어나는 활동이 이벤트 스트림으로 흘러나온다. GuardDuty RDS Protection은 RDS에 대한 위협을 탐지해 알려준다. 셋은 서로 다른 감시 범위를 담당한다.

#4동작 과정

  1. API 호출 감사CloudTrail이 RDS API 호출을 기록해, 누가 언제 어떤 설정을 바꿨는지 추적할 수 있게 한다.
  2. 데이터 활동 스트림활동 스트림을 시작하면 DB 안의 활동이 스트림으로 생성되고, 그 상태를 조회하거나 필요할 때 수정·중지한다. 스트림은 Kinesis를 통해 꺼내 처리하며, Oracle 통합 감사·SQL Server 감사 같은 엔진별 감사 설정이 선행된다.
  3. 위협 탐지GuardDuty RDS Protection이 RDS 환경의 위협을 모니터링해 의심 활동을 알린다. 셋을 함께 구성해야 감사·활동 추적·위협 대응이 완성된다.

#5한 줄 요약

API 호출 감사·데이터베이스 활동 스트림·위협 탐지를 각각 구성해 RDS의 제어·데이터·보안 계층을 함께 감시하게 해주는 보안 모니터링 체계

RDS Custom — 관리형과 셀프 관리의 중간07-01

RDS Custom 개요

AWS가 인프라와 자동화는 관리하되 DB 엔진과 운영체제에 대한 관리자 권한을 사용자에게 열어주는, 완전관리형과 셀프관리의 중간 형태의 RDS 서비스다.

#1문제 상황

완전관리형 RDS는 백업·패치·장애 조치 같은 운영 작업을 AWS가 대신 해주지만, 데이터베이스 환경과 운영체제를 사용자가 직접 손댈 수 없다. 반대로 셀프 관리 방식은 자유도가 높은 대신 운영 부담을 사용자가 모두 진다.

서드파티 애플리케이션은 커스텀 패치나 특정 에이전트 설치처럼 손댈 수 없는 요구가 있어 완전관리형으로 옮기기 어렵다. 그래서 "관리는 AWS가 하되 엔진과 OS는 내가 만질 수 있는" 중간 형태가 필요해졌다.

#2핵심 질문

인프라와 자동화는 AWS가 관리하면서도, DB 엔진과 운영체제에는 사용자가 접근해 커스터마이즈할 수 있게 하려면 어떻게 해야 하는가?

#3동작 예시

RDS Custom에서는 데이터베이스 관리자가 데이터베이스 환경과 운영체제에 접근해 원하는 대로 설정을 바꿀 수 있다. 예를 들어 레거시·커스텀·패키지 애플리케이션이 요구하는 특정 구성을 적용할 수 있다. 이때 자동화된 데이터베이스 관리 작업과 운영은 그대로 AWS가 처리하므로, 완전관리형의 이점을 유지하면서 커스터마이즈를 얹는다.

#4동작 과정

  1. 관리 위임과 개방AWS가 백업·모니터링 같은 데이터베이스 관리 작업과 운영을 자동화하는 한편, 사용자에게 엔진과 OS 접근 권한을 연다.
  2. 커스터마이즈사용자가 인스턴스 환경과 운영체제를 레거시·패키지 애플리케이션 요구에 맞게 수정한다.
  3. 적용이렇게 만든 환경이 RDS Custom 아키텍처 위에서 동작하며, 보안 설정과 자격 증명 관리(예: 자격 증명 교체) 같은 별도 관리가 함께 따른다.

#5한 줄 요약

AWS가 인프라와 자동화는 맡되 엔진과 운영체제 접근은 사용자에게 열어, 커스터마이즈가 필요한 애플리케이션도 관리형 RDS의 이점을 누리게 해주는 중간 형태의 서비스

RDS Custom for Oracle

Oracle 데이터베이스에 OS·엔진 수준 접근이 필요한 특수 요구(커스텀 패치, 서드파티 에이전트 등)를 위해 RDS Custom으로 Oracle을 실행하는 서비스다.

#1문제 상황

Oracle 데이터베이스는 커스텀 패치, 서드파티 에이전트 설치처럼 OS·엔진 수준의 접근이 필요한 특수 요구를 자주 갖는다. 완전관리형 RDS for Oracle로는 이런 부분을 손댈 수 없어, 요구를 충족하려면 결국 직접 운영하는 쪽으로 밀려난다.

직접 운영하면 백업·패치·장애 조치 같은 운영 부담을 전부 사용자가 떠안는다. 커스터마이즈를 위해 관리형의 이점을 포기해야 하는 상황이 문제다.

#2핵심 질문

Oracle의 OS·엔진 수준 커스터마이즈가 필요할 때, 관리형 운영의 이점을 유지하면서 RDS Custom으로 실행하려면 어떻게 해야 하는가?

#3동작 예시

RDS Custom for Oracle에서는 DB 인스턴스와 운영체제에 접근해 커스터마이즈할 수 있다. 이때 사용할 Oracle 소프트웨어 구성은 CEV(Custom Engine Version, 커스터마이즈한 엔진 버전)로 만들어 관리한다. 예를 들어 커스텀 패치를 적용한 엔진 버전을 CEV로 준비해 두고, 그 CEV로 DB 인스턴스를 생성한다. Session Manager로 접속해 로그인하고 설정을 바꿀 수도 있다.

#4동작 과정

  1. 환경 준비와 CEV 생성RDS Custom for Oracle 환경을 설정하고, 커스터마이즈한 엔진 버전인 CEV를 만들어 상태를 관리하며 세부 정보를 확인한다.
  2. 인스턴스 구성과 접속CEV를 사용해 DB 인스턴스를 구성하고, Session Manager로 접속해 SYS로 로그인하는 등 엔진·OS 수준 작업을 수행한다.
  3. 운영DB 인스턴스를 관리하며, 복제본 구성·승격, 스냅샷과 특정 시점 복구, Multi-AZ 전환 같은 고가용성·백업 작업을 요구 사항과 제한 사항 안에서 처리한다.

#5한 줄 요약

Oracle에 필요한 OS·엔진 수준 커스터마이즈를 CEV와 접속 도구로 허용하면서, 관리형 RDS의 운영 자동화 위에서 실행하게 해주는 서비스

RDS Custom for SQL Server

SQL Server의 OS·엔진 수준 사용자 정의(커스텀 미디어, 에이전트 등)를 지원하기 위해 RDS Custom으로 SQL Server를 실행하는 서비스다.

#1문제 상황

기존 RDS for SQL Server는 운영체제에 접근할 수 없는 완전관리형이라, 엔진 수준의 사용자 정의 파일이나 별도 에이전트를 설치할 수 없습니다. 반대로 EC2에 SQL Server를 직접 설치하면 OS 패치·백업·복구를 모두 사용자가 떠안아야 합니다. 커스터마이징과 관리형 편의 사이의 이 빈틈이 RDS Custom이 등장한 이유입니다.

#2핵심 질문

OS와 엔진을 직접 손댈 수 있어야 하는 SQL Server를, 관리형 자동화의 이점은 유지하면서 실행하려면 어떻게 해야 할까요?

#3동작 예시

사용자가 커스텀 미디어로 만든 SQL Server AMI를 커스텀 엔진 버전(CEV, Custom Engine Version)으로 등록하면, 새 DB 인스턴스가 그 CEV를 기반으로 생성됩니다. 인스턴스 안에서는 RDS Custom 에이전트가 정해진 자동화 작업을 수행하고, 필요하면 자동화를 일시 중지해 직접 변경할 수 있습니다.

#4동작 과정

  1. 커스텀 미디어와 CEV 준비직접 준비한 SQL Server 설치 미디어로 AMI를 만들고, 이를 커스텀 엔진 버전(CEV)으로 등록합니다.
  2. DB 인스턴스 생성RDS Custom 서비스 연결 역할(service-linked role)을 통해 필요한 AWS 리소스에 접근하며, 등록한 CEV를 사용하는 DB 인스턴스를 만듭니다.
  3. 자동화 제어와 관리RDS Custom 에이전트의 자동화를 일시 중지(pause)해 OS·엔진을 직접 수정하고, 끝나면 재개해 패치·백업 같은 관리형 작업을 이어갑니다.

#5한 줄 요약

OS와 엔진을 직접 제어해야 하는 SQL Server에 관리형 자동화를 결합해, 커스터마이징과 운영 편의를 함께 제공하는 것

Amazon RDS on AWS Outposts

고객의 온프레미스 데이터 센터에 설치된 AWS Outposts 랙에서 Amazon RDS 관리형 데이터베이스를 실행해, 짧은 지연 시간이 필요한 로컬 워크로드에 RDS 기능을 제공하는 서비스다.

#1문제 상황

클라우드 리전에 있는 RDS는 애플리케이션과 물리적으로 멀면 네트워크 지연이 커지고, 데이터를 온프레미스에 두어야 하는 환경에서는 사용할 수 없습니다. 그렇다고 온프레미스에 데이터베이스를 직접 설치하면 프로비저닝·패치·백업을 모두 사용자가 관리해야 합니다. 그래서 온프레미스에서도 관리형 RDS를 쓰려는 요구가 생겼습니다.

#2핵심 질문

온프레미스에 있어야 하는 워크로드에 지연 시간을 줄이면서 RDS의 관리형 기능을 그대로 제공하려면 어떻게 해야 할까요?

#3동작 예시

AWS Outposts 랙이 설치된 고객 데이터 센터 안에서 RDS DB 인스턴스를 프로비저닝하면, 애플리케이션은 같은 로컬 네트워크의 데이터베이스에 접속합니다. 이때 사용하는 콘솔·CLI·API는 클라우드 리전의 RDS와 동일하고, 프로비저닝·OS 및 DB 패치·백업·S3 장기 보관 같은 작업은 자동화됩니다.

#4동작 과정

  1. Outposts 연결고객 데이터 센터의 Outposts 랙을 AWS 리전과 연결해, RDS가 온프레미스 하드웨어 위에서 인스턴스를 실행할 기반을 마련합니다.
  2. 로컬 DB 인스턴스 생성리전의 RDS와 같은 도구로 온프레미스 DB 인스턴스를 만들고, 필요하면 읽기 전용 복제본이나 Multi-AZ 배포를 구성합니다.

Amazon RDS Proxy

애플리케이션과 RDS 데이터베이스 사이에서 연결을 풀링하고 공유해 연결 폭주를 줄이고 장애 조치 시간을 단축해 주는 완전관리형 데이터베이스 프록시다.

#1문제 상황

애플리케이션 서버가 늘어나면 각 서버가 데이터베이스에 새 연결을 열고, 트래픽이 몰릴 때 연결이 급격히 늘어 데이터베이스가 연결 초과와 메모리·CPU 부담으로 버티지 못합니다. 또한 데이터베이스 장애 조치가 일어나면 기존 연결이 끊겨 애플리케이션이 다시 연결해야 합니다. 이 두 문제가 함께 커지면서 연결을 중간에서 관리할 계층이 필요해졌습니다.

#2핵심 질문

수많은 애플리케이션 연결을 데이터베이스 부담 없이 처리하고, 장애 조치 때도 연결을 유지하려면 어떻게 해야 할까요?

#3동작 예시

애플리케이션이 RDS Proxy 엔드포인트에 접속하면, 프록시가 미리 만들어 둔 연결 풀에서 연결을 재사용합니다. 그래서 같은 수의 애플리케이션 연결이 있어도 데이터베이스에 새로 여는 연결 수는 훨씬 적고, 접속 인증은 IAM이나 AWS Secrets Manager에 저장된 자격 증명으로 처리할 수 있습니다.

#4동작 과정

  1. 연결 풀 구성프록시를 만들 때 대상 데이터베이스와 자격 증명(IAM 인증 또는 Secrets Manager)을 지정하고, 프록시가 데이터베이스 연결 풀을 유지합니다.
  2. 애플리케이션 연결 재사용애플리케이션은 프록시 엔드포인트로 접속하고, 프록시는 풀의 유휴 연결을 빌려주어 새 연결 생성 비용을 줄입니다.
  3. 장애 조치 대응데이터베이스 장애가 나면 프록시가 대기(standby) 인스턴스로 자동 연결하고 애플리케이션 연결은 유지합니다.

Zero-ETL 통합

추출·변환·적재(ETL) 파이프라인을 직접 만들지 않고도 RDS 데이터를 Amazon Redshift 등 분석 서비스로 거의 실시간으로 복제해 바로 쿼리할 수 있게 하는 통합 기능이다.

#1문제 상황

분석을 위해 RDS의 트랜잭션 데이터를 Amazon Redshift 같은 데이터 웨어하우스로 옮기려면, 추출·변환·적재(ETL) 파이프라인을 직접 구축하고 운영해야 합니다. 파이프라인은 별도 인프라와 스케줄링, 오류 처리를 요구하고, 데이터가 목적지에 도착하기까지 지연이 생깁니다. 그래서 ETL 없이 데이터를 바로 분석할 수 있게 하려는 요구가 생겼습니다.

#2핵심 질문

ETL 파이프라인을 직접 만들지 않고 RDS 데이터를 분석 서비스에서 거의 실시간으로 쿼리하려면 어떻게 해야 할까요?

#3동작 예시

RDS 데이터베이스와 Amazon Redshift(또는 Amazon SageMaker AI 레이크하우스) 사이에 zero-ETL 통합을 만들면, RDS에 쓰인 트랜잭션 데이터가 거의 실시간으로 목적지에 반영됩니다. 그러면 목적지의 구체화된 뷰나 머신러닝 기능을 그대로 사용해 분석과 ML 작업을 돌릴 수 있습니다.

#4동작 과정

  1. 통합 생성원본 RDS 데이터베이스와 대상(Amazon Redshift 또는 SageMaker AI 레이크하우스)을 지정해 zero-ETL 통합을 만듭니다.
  2. 데이터 필터링 설정필요하면 통합에 데이터 필터를 걸어, 특정 테이블이나 조건에 맞는 데이터만 목적지로 보냅니다.
  3. 자동 복제와 쿼리RDS에 쓰인 데이터가 관리형으로 목적지에 거의 실시간 복제되고, 사용자는 목적지에서 바로 쿼리합니다.

#5한 줄 요약

ETL 파이프라인 없이 RDS의 트랜잭션 데이터를 분석 서비스로 거의 실시간 복제해, 바로 분석과 머신러닝에 쓸 수 있게 하는 것

#1문제 상황

#2핵심 질문

Db2의 운영 작업을 AWS에 맡기면서 인스턴스와 데이터는 그대로 통제하려면 어떻게 해야 할까요?

#3동작 예시

사용자가 RDS 콘솔이나 API로 Db2 DB 인스턴스를 만들면, 마스터 사용자는 DBADM 권한을 받아 데이터베이스 계정 생성 같은 관리 작업을 합니다. 인스턴스는 VPC 안에서 동작하고, 백업·스냅샷·시점 복구 같은 작업은 RDS가 관리하며, 필요하면 대기 복제본을 만들어 가용성을 높일 수 있습니다.

#4동작 과정

  1. DB 인스턴스 생성콘솔·CLI·API로 Db2 에디션과 버전을 골라 인스턴스를 만들고, VPC와 보안 그룹으로 네트워크를 구성합니다.
  2. 접속과 관리엔드포인트로 Db2 CLP나 클라이언트 도구로 접속하고, 마스터 사용자의 DBADM 권한으로 데이터베이스와 권한을 관리합니다.
  3. 복제와 백업대기 복제본을 구성해 가용성을 높이고, 스냅샷·자동 백업·시점 복구로 데이터를 보호합니다.

RDS for SQL Server — 공통 DBA 작업

RDS for SQL Server에서 tempdb·SQL Server Agent·콜레이션·복구 모델·CDC·트레이스 플래그 등 DBA가 자주 하는 관리 작업을 RDS 제약 안에서 처리하는 방법이다.

#1문제 상황

#2핵심 질문

서버 OS에 접근하지 못하는 관리형 환경에서 SQL Server의 DBA 작업을 어떻게 처리할까?

#3동작 예시

tempdb 크기를 늘리고 싶다면 OS에서 파일을 직접 고치는 대신, master 데이터베이스에서 RDS가 제공하는 rdsadmin 저장 프로시저(미리 만들어 둔 관리용 명령)를 실행한다. 그러면 RDS가 대신 tempdb의 파일 크기나 개수를 바꿔 준다. SQL Server Agent 작업 등록도 같은 방식으로 정해진 역할과 API를 통해 처리한다.

#4동작 과정

  1. 제약 확인RDS가 제공하지 않는 작업을 먼저 가려낸다. OS 접근이나 특정 시스템 명령은 막혀 있어 다른 경로를 찾아야 한다.
  2. 전용 수단 사용tempdb 옵션, 콜레이션, 사용자 생성은 rdsadmin 프로시저나 콘솔·API로 처리한다. 그래서 서버를 만지지 않고도 설정이 반영된다.
  3. 상태 점검마지막 장애 조치 시각, 복구 모델, LSN 갭으로 인한 PITR 실패 등을 조회해 결과를 확인한다. 이렇게 관리형 제약 안에서 DBA 작업이 끝난다.

RDS for Oracle — 관리·성능·복제

RDS for Oracle 인스턴스의 일상 관리 작업과 AWR 등 성능 진단, 읽기 전용 복제 및 Data Guard 스위치오버 복제 구성을 다룬다.

#1문제 상황

Oracle을 직접 운영하는 DBA는 세션을 끊고, 공유 풀을 비우고, 테이블스페이스를 늘리고, RMAN으로 백업하는 일을 OS와 SYSDBA 권한으로 처리했다. 그러나 RDS에서는 SYSDBA가 없고 OS 접근도 막혀 있어 같은 명령을 그대로 쓸 수 없다. 그래서 관리·성능·복제 작업마다 RDS가 마련한 대체 경로가 필요하다.

#2핵심 질문

SYSDBA와 OS 접근 없이 Oracle 인스턴스의 관리·성능·복제 작업을 어떻게 수행할까?

#3동작 예시

느린 SQL을 진단하려면 AWR 리포트를 뽑아 어느 세션이나 SQL이 부하를 만드는지 본다. 문제 세션은 찾아서 종료(disconnect·terminate)하고, 조회 부하가 크면 읽기 전용 복제본을 만들어 조회를 넘긴다. 이 모든 명령은 RDS가 허용한 프로시저로 실행한다.

#4동작 과정

  1. 진단AWR 같은 성능 도구로 현재 상태를 수집해 어느 세션과 SQL이 문제인지 찾는다. 그래서 추측이 아니라 근거로 조정할 수 있다.
  2. 조정세션을 끊거나 공유 풀을 비우고, 테이블스페이스·tempfile·온라인 리두 로그 크기를 바꾼다. 필요한 변경은 RDS 전용 프로시저로 실행한다.
  3. 백업·복제RMAN 백업을 돌리고, 읽기 전용 복제를 만들거나 Data Guard 스위치오버로 역할을 전환한다. 이렇게 관리형 제약 안에서 운영 작업이 이어진다.

#5한 줄 요약

SYSDBA 없이 RDS 전용 프로시저와 도구로 Oracle의 관리·성능 진단·복제를 처리하는 것

RDS for Oracle — 옵션·업그레이드·도구

RDS for Oracle에서 옵션 그룹으로 켜는 APEX·TDE·S3 연동 같은 옵션과 엔진 업그레이드, GoldenGate·SQL Developer 등 지원 도구를 다룬다.

#1문제 상황

Oracle에는 APEX, TDE 암호화, S3 연동 같은 부가 기능과 엔진 업그레이드, 데이터 이관 도구가 많다. 직접 운영하면 이런 기능을 개별적으로 설치하고 설정하고 버전도 손수 올려야 했다. RDS에서는 임의 설치가 막혀 있어, 켤 수 있는 기능은 정해진 옵션 그룹을 통해서만 활성화할 수 있다.

#2핵심 질문

임의 설치가 안 되는 환경에서 부가 기능과 업그레이드, 이관 도구를 어떻게 켜고 쓸까?

#3동작 예시

S3에 있는 파일을 DB로 가져오려면 옵션 그룹에 S3 연동 옵션을 추가하고, IAM 권한을 준 뒤 전용 프로시저로 파일을 내려받거나 올린다. APEX도 같은 방식으로 옵션 그룹에서 활성화하고 ORDS를 구성해 웹 화면을 띄운다.

#4동작 과정

  1. 옵션 그룹 구성옵션 그룹에 필요한 옵션(S3, EFS, APEX, JVM, TDE 등)을 추가하고 IAM·네트워크 권한을 맞춘다.
  2. 기능 활성화옵션을 인스턴스에 적용하면 관련 패키지와 권한이 준비된다. 인스턴스 스토어, HugePages, 확장 데이터 타입도 이 단계에서 켠다.
  3. 이관·업그레이드Data Pump, Export/Import, SQL*Loader, transportable tablespaces로 데이터를 옮기고 엔진 버전을 올린다. 필요하면 GoldenGate나 SQL Developer 같은 도구를 함께 쓴다.

#5한 줄 요약

옵션 그룹으로 부가 기능을 켜고 정해진 도구로 데이터 이관과 업그레이드를 하는 것

데이터베이스 인증과 Secrets Manager

RDS가 DB 접속 자격 증명을 확인하는 인증 방식과, 마스터 암호를 안전하게 저장·자동 교체해 주는 AWS Secrets Manager 연동을 묶은 주제다.

#1문제 상황

DB 마스터 암호를 설정 파일이나 배포 스크립트에 평문으로 적어 두면 유출 위험이 크다. 게다가 암호를 사람이 주기적으로 바꾸는 방식은 자주 잊히고, 바꿀 때마다 애플리케이션 설정도 함께 고쳐야 해 장애로 이어지기 쉽다. 직접 운영하는 DB는 이 보관과 교체를 전부 사용자가 책임져야 했다.

#2핵심 질문

DB 접속 자격 증명을 노출하지 않으면서 안전하게 보관하고 주기적으로 교체할 수 있을까?

#3동작 예시

RDS가 마스터 사용자 암호를 AWS Secrets Manager에 비밀(secret)로 저장하고, 정해진 주기에 따라 자동으로 새 암호로 바꾼다. 애플리케이션은 암호를 직접 들고 있지 않고 Secrets Manager에서 값을 조회해 접속한다. 그래서 코드나 설정 파일 어디에도 실제 암호가 남지 않는다.

#4동작 과정

  1. 비밀 생성DB 인스턴스를 만들 때 RDS가 Secrets Manager에 마스터 암호를 담은 비밀을 만든다.
  2. 자동 교체RDS가 교체 주기에 맞춰 DB와 Secrets Manager 양쪽의 암호를 함께 갱신한다. 그래서 사람이 수동으로 바꾸지 않아도 된다.
  3. 조회와 사용애플리케이션은 권한을 가진 주체로 비밀을 읽어 접속에 쓴다. 암호는 코드에 남지 않고 필요할 때만 조회된다.

#5한 줄 요약

마스터 암호를 Secrets Manager에 맡겨 자동으로 교체하고 조회로만 쓰게 하는 것

암호화와 데이터 보호

저장 데이터·스냅샷의 KMS 암호화, 전송 중 SSL/TLS 암호화, 인터넷워크 트래픽 보호 등 RDS 데이터를 보호하는 수단을 다룬다.

#1문제 상황

DB를 직접 운영하면 저장 디스크 암호화, 스냅샷 암호화, 접속 구간 암호화를 각각 따로 설정해야 했다. 하나라도 빠지면 저장된 데이터나 네트워크 구간에서 평문이 노출될 수 있고, 암호화 키 관리도 사용자 몫이었다. RDS도 공유 책임 모델에 따라 데이터를 지키는 책임의 상당 부분이 사용자에게 남는다.

#2핵심 질문

저장 데이터와 스냅샷, 전송 구간의 데이터를 각각 어떻게 암호화해 보호할까?

#3동작 예시

DB 인스턴스를 만들 때 AWS KMS 키를 골라 저장 데이터를 암호화하면, 그 인스턴스에서 만들어지는 스냅샷과 읽기 복제본도 같은 키로 암호화된다. 클라이언트가 접속할 때는 SSL/TLS로 연결을 암호화해 전송 중 데이터를 보호한다. 필요하면 SSL/TLS 인증서를 교체한다.

#4동작 과정

  1. 저장 암호화KMS 키를 지정해 DB 스토리지와 스냅샷을 암호화하고, 키 접근 권한을 IAM으로 통제한다.
  2. 전송 암호화SSL/TLS 인증서로 클라이언트와 DB 사이 연결을 암호화한다. 그래서 전송 중 데이터가 그대로 보이지 않는다.
  3. 구간 보호보안 그룹과 VPC로 인터넷워크 트래픽을 제한해 필요한 경로로만 접근하게 한다. 이렇게 저장·전송·구간을 모두 덮는다.

#5한 줄 요약

KMS와 SSL/TLS로 저장 데이터와 스냅샷, 전송 구간을 각각 암호화해 보호하는 것

IAM과 IAM 데이터베이스 인증

RDS API 접근을 제어하는 IAM 정책·역할 체계와, IAM 자격 증명으로 DB에 암호 없이 접속하는 IAM 데이터베이스 인증을 함께 설명한다.

#1문제 상황

RDS 리소스를 만들고 수정하고 삭제하려면 AWS 계정 자격 증명이 필요하다. 초기에는 계정마다 공유된 키를 돌려 쓰거나 root 자격 증명으로 관리 작업을 했는데, 이렇게 하면 누가 무엇을 했는지 구분되지 않고 권한을 좁힐 수도 없었다. 여기에 더해 DB에 접속할 때마다 마스터 사용자 이름과 비밀번호를 설정하고 여러 서버에 나눠 저장해야 했다. 비밀번호가 여러 곳에 복사되면 유출 경로가 늘고, 주기적으로 바꾸는 것도 사람 손이 필요했다.

#2핵심 질문

AWS 리소스를 다루는 권한과 데이터베이스 접속 자격 증명을 하나의 IAM 체계로 통제해, 자격 증명을 흩어 두지 않고 최소 권한만 부여하려면 어떻게 해야 하는가?

#3동작 예시

애플리케이션 서버 역할에 RDS 접속 권한을 담은 IAM 정책을 붙여 둔다. 서버가 DB에 접속할 때 비밀번호를 쓰는 대신, 자신의 IAM 자격 증명으로 서명한 인증 토큰을 생성해 접속 정보에 넣는다. RDS는 토큰이 해당 IAM 주체에게 발급된 것인지 확인한 뒤 접속을 허용한다. 비밀번호는 어디에도 저장되지 않고, 역할을 회수하면 접속도 즉시 막힌다.

#4동작 과정

  1. 정책과 역할 부여IAM 관리자가 사용자·그룹·역할에 RDS 작업 권한을 담은 정책을 붙인다. 정책은 허용·거부하는 작업과 대상 리소스를 지정하므로, 각 사용자는 맡은 일에 필요한 최소 권한만 갖게 된다.
  2. 자격 증명 발급IAM 데이터베이스 인증을 켠 DB 인스턴스에 대해, 접속하려는 주체가 임시 인증 토큰(단기간만 유효한 서명)을 생성한다. 이 토큰은 DB 사용자 이름에 매핑되어 IAM 자격 증명과 DB 계정을 연결한다.
  3. 토큰 검증 후 접속클라이언트가 토큰을 비밀번호 자리에 넣어 접속하면 RDS가 서명을 검증하고 통과시키거나 거부한다. 결과적으로 DB 비밀번호를 저장·회전할 필요 없이 IAM 권한을 바꾸는 것만으로 접속을 통제한다.

#5한 줄 요약

AWS 리소스 접근 권한과 데이터베이스 접속 자격 증명을 모두 IAM으로 통일해, 비밀번호를 흩어 두지 않고 최소 권한만으로 통제하는 것

보안 모범 사례·규정·복원력

RDS 운영 시 지켜야 할 보안 모범 사례와 규정 준수(컴플라이언스) 검증, 장애 대비 복원력 확보 방침을 정리한 주제다.

#1문제 상황

RDS를 그냥 띄워 쓰면 관리자마다 개별 계정을 만들지 않고 root 자격 증명을 공유하기 쉽고, 필요 이상으로 넓은 권한을 주게 된다. 보안 그룹이 광범위하게 열려 있거나 자격 증명을 오래 바꾸지 않으면 침해 경로가 조용히 늘어난다. 또한 규정 준수 감사에서 "접근 기록이 있는가, 장애가 나도 복구할 수 있는가"를 증명해야 하는데, 로그와 백업, 네트워크 격리를 따로 챙기지 않으면 근거를 제시하지 못한다.

#2핵심 질문

RDS를 운영할 때 접근·로깅·규정 준수·복구를 어떤 원칙으로 함께 챙겨야 사고와 감사에 모두 대응할 수 있는가?

#3동작 예시

관리자마다 개별 IAM 사용자를 만들고 RDS 리소스를 만들거나 지우는 권한은 필요한 사람에게만 준다. root 자격 증명은 RDS 관리에 쓰지 않는다. 여기에 CloudTrail 같은 로깅과 AWS Secrets Manager의 자동 회전을 붙여 두면, 누가 어떤 RDS API를 호출했는지 남고 DB 비밀번호도 사람 손 없이 갱신된다.

#4동작 과정

  1. 접근 통제와 최소 권한IAM 계정·그룹으로 RDS API 작업 권한을 관리하고, 작업별로 필요한 최소 권한만 부여한다. 개별 사용자를 만들어 누가 무엇을 했는지 구분하고 자격 증명은 주기적으로 교체한다.
  2. 로깅·모니터링과 자격 증명 보호CloudTrail과 모니터링으로 리소스 접근과 변경을 기록한다. Secrets Manager로 DB 자격 증명을 보관하고 자동 회전을 걸어 사람이 직접 비밀번호를 다루지 않게 한다.
  3. 규정 준수·복원력·네트워크 격리감사 요구에 맞춰 컴플라이언스 검증 근거를 갖추고, 백업과 다중 AZ 같은 복원력 확보 방침을 정한다. VPC 엔드포인트로 프라이빗하게 연결하고 보안 그룹으로 접근을 좁혀 네트워크를 안전하게 유지한다.

#5한 줄 요약

접근·로깅·규정 준수·복구를 하나의 원칙으로 묶어, RDS를 최소 권한과 검증 가능한 기록 위에서 안전하게 운영하는 것

VPC와 RDS

RDS DB 인스턴스를 Amazon VPC 안에서 구동해 네트워크를 격리하고 서브넷·보안 그룹으로 접근을 통제하는 방식과 관련 시나리오를 다룬다.

#1문제 상황

DB 인스턴스를 공용 네트워크에 그대로 두면 인터넷 어디서든 접속을 시도할 수 있어 노출 위험이 크다. 접근을 IP 목록으로만 막는 방식은 서버가 늘거나 옮겨질 때마다 목록을 고쳐야 하고, 어떤 경로로 들어오는 트래픽인지 통제하기 어렵다. 네트워크 주소 범위와 라우팅을 직접 정하지 못하면 기존 사내망이나 다른 클라우드 자원과 안전하게 연결하기도 어렵고, DB를 어디에 어떤 조건으로 노출하는지 일관되게 관리할 수 없다.

#2핵심 질문

DB 인스턴스를 사설 네트워크 안에 두고 서브넷·보안 그룹·라우팅으로 접근을 통제하려면 어떻게 구성해야 하는가?

#3동작 예시

DB 인스턴스를 Amazon VPC 안의 서브넷에 만든다. 애플리케이션 서버가 같은 VPC의 다른 서브넷에 있으면, 보안 그룹에서 애플리케이션 서버의 보안 그룹만 DB 포트로 들어오도록 허용한다. 그러면 인터넷을 거치지 않고 VPC 내부 통신으로만 DB에 닿으며, 다른 출처는 기본적으로 차단된다.

#4동작 과정

  1. VPC와 서브넷 지정DB 인스턴스가 들어갈 VPC와 IP 주소 범위를 고르고, 가용 영역별 서브넷(주소를 나눠 둔 하위 네트워크)을 배치한다. 기존 VPC가 없으면 계정의 기본 VPC를 쓰고, 필요하면 새 VPC를 만든다.
  2. 라우팅과 보안 그룹 설정서브넷의 라우팅과 접근 제어 목록으로 트래픽 경로를 정하고, 보안 그룹에서 DB 포트로 들어올 수 있는 출처를 특정 보안 그룹이나 대역으로 좁힌다. 이로써 허용된 대상만 DB에 도달한다.
  3. 연결 확인과 재배치애플리케이션에서 격리된 경로로 DB에 붙는지 확인한다. VPC 밖에 있던 DB 인스턴스는 VPC 안으로 옮길 수 있고, 이후 서브넷·보안 그룹을 바꿔 노출 범위를 계속 조정한다.

#5한 줄 요약

DB 인스턴스를 Amazon VPC 안에 두고 서브넷·라우팅·보안 그룹으로 접근 경로를 좁혀, 인터넷에 노출하지 않고 필요한 대상만 연결되게 하는 것

코드 예제

DB 인스턴스 생성·스냅샷·파라미터 그룹 관리 등 Amazon RDS의 주요 작업을 AWS SDK와 CLI로 수행하는 실제 예제 코드 모음.

#1문제 상황

RDS 작업을 콘솔에서 손으로 반복하면 같은 설정을 사람마다 다르게 만들기 쉽고, 인스턴스가 늘면 재현과 자동화가 어려워진다. 스냅샷을 찍고 파라미터 그룹을 고치는 일을 매번 클릭으로 처리하면 누락이나 순서 착오가 생긴다. 또한 여러 AWS SDK에서 RDS를 어떻게 호출하는지 알아야 스크립트나 서버리스 코드로 옮길 수 있는데, 함수 이름과 호출 순서를 매번 문서에서 찾는 일은 번거롭다.

#2핵심 질문

DB 인스턴스 생성·스냅샷·파라미터 그룹 관리 같은 RDS 작업을 SDK와 CLI 코드로 재현 가능하게 수행하려면 각 함수를 어떻게 호출해야 하는가?

#3동작 예시

AWS SDK로 DB 인스턴스를 만들 때 CreateDBInstance를 호출하고, 준비가 끝날 때까지 DescribeDBInstances로 상태를 조회한다. 파라미터를 바꾸려면 CreateDBParameterGroup과 ModifyDBParameterGroup을 쓰고, 백업은 CreateDBSnapshot으로 뜬 뒤 DescribeDBSnapshots로 결과를 확인한다. 같은 작업을 CLI 명령으로도 동일하게 실행할 수 있다.

#4동작 과정

  1. 기본 예제로 흐름 익히기Hello Amazon RDS와 기본 예제로 연결과 호출 방식을 익힌다. 이 단계에서 각 작업이 어떤 함수로 시작하는지 감을 잡는다.
  2. 개별 작업 함수 호출CreateDBInstance, ModifyDBInstance, RebootDBInstance처럼 동작별 함수를 호출하고, DescribeDBEngineVersions·DescribeDBParameters 같은 조회 함수로 입력에 쓸 값을 확인한다. 각 호출은 리소스 하나를 만들거나 바꾼다.
  3. 시나리오로 묶고 서버리스로 연결여러 함수를 순서대로 부르는 시나리오로 DB 인스턴스 생성이나 트래커 앱 구성을 자동화하고, Lambda 함수에서 RDS에 접속하는 예제로 확장한다. 결과적으로 반복 작업이 코드로 재현된다.

#5한 줄 요약

RDS의 주요 작업을 SDK·CLI 함수 호출로 표현해, 콘솔 수작업 대신 재현 가능한 코드로 DB를 만들고 관리하게 하는 것

할당량·API·문제 해결

Amazon RDS의 계정·리전별 할당량(인스턴스·스냅샷 수 등)과 API 참조, 장애·오류가 났을 때의 원인과 대처를 정리한 참고 문서.

#1문제 상황

RDS를 쓰다 보면 리전별로 만들 수 있는 리소스 수에 한계가 있어, 한도에 닿으면 추가 생성 호출이 예외와 함께 실패한다. 한도가 있다는 걸 모르면 장애 원인을 찾지 못하고 같은 요청을 반복하다 시간을 버린다. 이름 규칙이나 최대 연결 수 같은 제약을 벗어난 값을 넣어도 생성이 거부되는데, 어떤 제약이 있는지 확인하지 않으면 오류 메시지만 보고 원인을 헤매게 된다.

#2핵심 질문

RDS의 리소스 할당량과 제약, API 호출 방식, 오류 대처를 미리 알아 두어 한도·규칙 위반으로 인한 실패를 어떻게 피하고 해결할 수 있는가?

#3동작 예시

리전마다 DB 인스턴스나 스냅샷 수에 기본 할당량이 정해져 있고, 일부는 조정 가능하다. 새 인스턴스 생성이 예외로 실패하면 먼저 현재 리소스 수와 한도를 확인해 상한에 걸렸는지 본다. 상한이라면 불필요한 리소스를 정리하거나 할당량 조정을 요청하고, 아니라면 이름 규칙·연결 수 같은 제약 위반인지 점검한다.

#4동작 과정

  1. 할당량과 제약 확인리전별 리소스 할당량, 이름 규칙, 최대 데이터베이스 연결 수, 파일 크기 제한을 확인한다. 어떤 값이 조정 가능하고 어떤 값이 고정인지 구분해 둔다.
  2. API로 상태 조회Query API 등으로 현재 리소스와 설정을 조회해 한도 대비 여유를 파악한다. 호출이 예외로 실패하면 응답의 오류 내용을 근거로 원인을 좁힌다.
  3. 대처와 재시도한도 초과면 리소스를 정리하거나 할당량 조정을 요청하고, 제약 위반이면 입력값을 규칙에 맞게 고친다. 애플리케이션 쪽 문제라면 연결 설정과 오류 처리를 점검해 재발을 막는다.

#5한 줄 요약

RDS의 할당량·제약과 API 동작을 미리 파악해, 한도나 규칙 위반으로 생기는 실패를 원인부터 찾아 해결하게 하는 것
