1RDS라는 서비스의 정체무엇을 빌리는 것이고 무엇이 내 책임인지를 먼저 알아야, 이후의 모든 설정 선택이 '왜 내가 이걸 골라야 하는가'로 읽힌다.52인스턴스를 만들기 전에 정해야 하는 것생성 화면에서 마주치는 선택지(클래스·스토리지·네트워크)를 먼저 이해해야, 생성 절차가 단순 클릭이 아니라 설계가 된다.53인스턴스를 만들고 접속하기앞에서 정한 선택을 실제 리소스로 만들고 연결이 되는 것을 확인해야, 이후 운영·튜닝 항목에 실습할 대상이 생긴다.54인스턴스의 동작을 바꾸는 설정 묶음파라미터 그룹과 옵션 그룹은 이후의 로깅·복제·암호화·감사 기능이 모두 걸리는 손잡이라, 운영 이야기보다 먼저 알아야 한다.45살아 있는 인스턴스를 계속 운영하기만든 인스턴스는 멈추고, 커지고, 버전이 올라간다. 이 변경 작업들의 다운타임 성격을 알아야 가용성 설계를 판단할 수 있다.76장애를 견디고 읽기를 늘리는 구조단일 인스턴스 운영을 겪은 뒤에야 대기본과 복제본이 무엇을 해결하는지 이해되고, 이 구조 위에서 백업·복원의 의미가 달라진다.67백업·복원·데이터 내보내기복제는 장애를 견디게 할 뿐 실수를 되돌리지 못한다. 시점 복구와 스냅샷이 그 자리를 메우고, 여기서 처음 '과거의 데이터'를 다룬다.58누가 들어오고 무엇이 보호되는가데이터가 실제로 쌓인 뒤에 인증·암호화·권한을 다뤄야 각 통제가 무엇을 막는지 체감된다. 감사·모니터링의 전제이기도 하다.69무슨 일이 벌어지는지 보는 법구성과 보안이 끝난 인스턴스는 이제 관찰 대상이다. 지표·이벤트·로그를 읽을 수 있어야 튜닝과 문제 진단이 가능해진다.810연결과 다른 서비스로의 확장단일 DB가 안정화된 뒤에야 연결 폭주·분석 파이프라인·데이터 이관이라는 다음 문제가 생긴다. 이들은 앞의 보안·모니터링 지식을 전제로 한다.511엔진별로 갈리는 부분공통 뼈대를 다 익힌 다음에야 엔진별 예외가 '차이'로 읽힌다. 여기서 각 엔진의 고유 기능·제약·관리 작업을 정리한다.812표준 RDS의 경계와 한계, 그리고 문제가 생겼을 때모든 공통 기능을 안 다음에야 '표준 RDS로는 안 되는 경우'가 무엇인지 판단할 수 있고, 한도와 진단은 실제 운영에서 마지막에 필요해진다.5

스토리지 유형과 IOPS·처리량 특성

범용 SSD(gp2/gp3), 프로비저닝된 IOPS SSD(io1/io2), 마그네틱 중 무엇을 쓰느냐에 따라 달라지는 디스크 성능(IOPS)과 처리량 선택이다.

1상대의 출발점 확인

전통적으로 데이터베이스 서버에 부착한 물리 디스크는 하드웨어 사양이 고정되어 있었다. SSD를 달거나 회전식 디스크를 달거나, 한번 설치되면 그 성능은 바뀌지 않았다. 더 높은 성능이 필요하면 새로운 디스크로 완전히 교체하거나 서버 자체를 더 비싼 모델로 바꿔야 했다.

2질문 제기

3구조적 핵심 예시

RDS는 스토리지 유형과 IOPS를 따로 정할 수 있다. 범용 SSD인 gp3를 선택하면 기본 성능은 3000 IOPS(초당 입출력 작업 횟수)이지만, 필요하면 최대 16000 IOPS까지 높일 수 있다. io2는 더 높은 IOPS를 지원하고, 마그네틱은 비용이 낮지만 훨씬 느리다.

4단계별 동작 과정

  1. 스토리지 유형 선택gp2(범용 저가), gp3(범용 중가, IOPS 조절 가능), io1/io2(고성능 프로비저닝), 마그네틱(레거시 저비용) 중 하나를 고른다.
  2. IOPS와 처리량 지정스토리지 유형에 따라 최소/최대 IOPS 범위가 정해진다. gp3는 3000~16000 IOPS, io2는 더 높다. 처리량(MB/s)도 같은 방식으로 선택한다.
  3. 인스턴스 생성 시 적용선택한 유형과 성능으로 DB 인스턴스를 만들면, 그 후 같은 유형 내에서는 IOPS를 늘리거나 줄일 수 있다.

DB에 접속하려면 네트워크가 열려 있어야 하는데, 수동으로 보안 그룹과 서브넷을 맞춰 설정하는 것은 복잡하다. 특히 EC2 인스턴스나 Lambda 함수가 RDS에 접근할 때마다 IP 주소나 보안 그룹을 일일이 확인하고 규칙을 추가해야 한다. 설정 실수가 나면 접속이 안 되고, 원인 파악에 시간이 든다.

2질문 제기

EC2나 Lambda 같은 AWS 리소스가 RDS에 안전하게 접속하도록 하는 설정을 자동으로 맞춰주는 방법은 없을까?

3구조적 핵심 예시

RDS 콘솔의 "데이터베이스" 페이지에 "연결" 또는 "설정" 메뉴가 있다. 여기서 "EC2 인스턴스와 연결" 옵션을 누르면, 같은 리전의 EC2 인스턴스 목록이 뜬다. 연결할 EC2를 선택하면, RDS는 자동으로 그 EC2의 보안 그룹과 RDS의 보안 그룹을 수정해 트래픽이 통하도록 설정한다.

4단계별 동작 과정

  1. 접속할 리소스 선택RDS 콘솔에서 DB 인스턴스를 열고 "연결 설정" 또는 "설정" 메뉴를 클릭한다. "EC2 인스턴스와 연결" 옵션에서 연결할 EC2나 Lambda의 이름을 고른다.
  2. 자동 구성RDS가 내부적으로 EC2의 보안 그룹에 인바운드 규칙(RDS의 포트, RDS의 보안 그룹)을 추가하고, RDS의 보안 그룹에 그 EC2를 출처로 하는 인바운드 규칙을 추가한다.
  3. 즉시 접속 가능설정 완료 후 EC2나 Lambda에서 엔드포인트로 접속 시도하면, 보안 그룹 규칙이 통과해 연결된다.

1상대의 출발점 확인

일반적인 JDBC나 psql 드라이버는 연결 시 엔드포인트를 한 번 DNS 조회한 뒤, 그 IP로 접속한다. 하지만 RDS에서는 장애 복구(페일오버)가 발생할 수 있다. Multi-AZ 설정이라면, 주 인스턴스에 장애가 나면 대기 인스턴스(standby)가 새 주 인스턴스로 昇格되는데, 이때 엔드포인트는 같지만 뒤의 IP가 바뀐다. 기존 드라이버는 이미 캐시한 IP로 계속 붙으려다가 실패한다.

2질문 제기

DB 인스턴스 장애로 페일오버가 일어났을 때, 애플리케이션이 빠르게 새 인스턴스로 자동으로 다시 붙게 하려면 어떻게 해야 할까?

3구조적 핵심 예시

AWS는 전용 JDBC 드라이버와 Python 드라이버를 제공한다. 예를 들어 AWS JDBC Driver for MySQL은 일반 MySQL JDBC 드라이버 대신 쓸 수 있다. 이 드라이버는 연결할 때마다 엔드포인트의 DNS를 다시 조회하고(캐시하지 않음), 장애를 감지하면 즉시 새 IP로 재연결을 시도한다. 레이턴시 손실을 수초에서 밀리초 수준으로 줄인다.

4단계별 동작 과정

  1. AWS 드라이버 설치Maven이나 pip을 써 mysql-connector-java-aws 같은 AWS JDBC 드라이버를 프로젝트에 추가한다.
  2. 연결 문자열 변경일반 JDBC URL jdbc:mysql://... 대신 jdbc:mysql:aws://...로 수정하면, AWS 드라이버가 활성화된다.
  3. 자동 페일오버 대응AWS 드라이버는 연결 동안 엔드포인트 주소를 주기적으로 갱신하고, 네트워크 장애를 감지하면 자동으로 다시 DNS 조회 후 재연결한다.

1상대의 출발점 확인

지금까지 RDS 인스턴스를 만들 때는 AWS 콘솔(웹 페이지)에서 클릭해 설정을 입력했습니다. 문제는 이렇게 만든 인스턴스의 설정이 어디에 저장되지 않는다는 것입니다. 나중에 같은 환경을 다시 만들거나, 팀원과 설정을 공유하거나, 실수로 삭제한 인스턴스를 복구하려면 또 다시 콘솔에서 클릭해 만들어야 합니다. 설정 내용이 코드나 문서로 기록되지 않으면 재현 불가능하고, 변경 이력도 남지 않습니다.

2질문 제기

콘솔에서 클릭해 만든 RDS 구성을 코드나 템플릿 파일로 저장해서 언제든 같은 환경을 다시 만들 수 있게 하려면?

3구조적 핵심 예시

CloudFormation은 YAML이나 JSON 파일에 인스턴스 이름, 크기, 보안 그룹, 백업 설정 등을 텍스트로 적어두면, AWS가 그 파일을 읽고 자동으로 인스턴스를 만들어줍니다. Console-to-Code 기능은 이미 콘솔에서 만든 인스턴스를 CloudFormation 템플릿으로 변환해주는 것입니다.

4단계별 동작 과정

  1. 현재 인스턴스를 템플릿으로 추출콘솔의 "Export to CloudFormation" 또는 Console-to-Code 기능으로 기존 인스턴스의 모든 설정을 CloudFormation 템플릿(YAML 또는 JSON 파일)으로 변환합니다.
  2. 템플릿을 버전 관리 시스템에 저장생성된 템플릿을 Git 같은 버전 관리 도구에 저장하면 누가 언제 뭘 바꿨는지 기록이 남습니다.
  3. 템플릿으로 새 인스턴스 자동 생성나중에 이 템플릿 파일을 CloudFormation에 업로드하면 동일한 구성의 인스턴스가 자동으로 만들어집니다.

파라미터 그룹의 개념과 정적·동적 파라미터

DB 엔진의 동작을 결정하는 설정값 묶음이 파라미터 그룹이며, 값이 바로 적용되는 동적 파라미터와 재부팅해야 적용되는 정적 파라미터로 나뉜다.

1상대의 출발점 확인

DB 엔진(MySQL, PostgreSQL 등)은 수백 개의 설정값을 가지고 있습니다. 기존에는 이 설정을 바꾸려면 인스턴스 내부에서 설정 파일을 직접 수정해야 했습니다. 이 방식은 설정 실수의 위험이 크고, 어떤 설정을 바꿨는지 추적하기 어려우며, 여러 인스턴스에 같은 설정을 적용하려면 각각 들어가서 수정해야 했습니다.

2질문 제기

DB 엔진의 수백 개 설정값을 한 곳에서 묶어서 관리하고, 여러 인스턴스에 일괄로 적용할 수 있게 하려면?

3구조적 핵심 예시

파라미터 그룹은 설정값들의 모음입니다. 예를 들어 "프로덕션용 파라미터 그룹"이라는 것을 만들 때 최대 연결 수를 100으로, 캐시 크기를 2GB로 설정해두면, 이 그룹을 여러 인스턴스에 연결해서 모두 같은 설정으로 만들 수 있습니다.

4단계별 동작 과정

  1. 정적 파라미터 (Static Parameter)값을 바꾸면 즉시 적용되지 않고 인스턴스를 재부팅해야 적용되는 설정입니다. 예: 메모리 크기 관련 설정, 로그 레벨 등.
  2. 동적 파라미터 (Dynamic Parameter)값을 바꾸면 재부팅 없이 몇 초 내에 바로 적용되는 설정입니다. 예: 최대 연결 수, 타임아웃 시간 등.
  3. 인스턴스에 연결파라미터 그룹을 DB 인스턴스에 붙이면, 그 그룹의 모든 설정값이 인스턴스에 적용됩니다.

사용자 지정 파라미터 그룹을 생성해 인스턴스에 연결하고, 값을 수정하거나 두 그룹의 설정 차이를 비교하는 실제 작업 절차다.

1상대의 출발점 확인

RDS는 DB 엔진별로 기본 파라미터 그룹을 제공하지만, 이 기본 그룹은 많은 경우 일반적인 설정으로만 구성되어 있습니다. 실제 운영에서는 애플리케이션의 특성에 맞춰 설정을 조정해야 하는데, 기본 그룹을 직접 수정하면 실수로 다른 인스턴스에도 영향을 미칠 수 있습니다. 따라서 사용자 지정 파라미터 그룹을 만들고, 필요할 때마다 수정하고, 그룹 간의 차이를 비교하는 절차가 필요합니다.

2질문 제기

기본 파라미터 그룹의 영향을 받지 않으면서 독립적으로 DB 설정을 구성하고 관리하는 실제 절차는?

3구조적 핵심 예시

AWS 콘솔 또는 CLI(Command Line Interface, 명령어 인터페이스)에서 "내 커스텀 파라미터 그룹 생성"을 선택하면 빈 그룹이 만들어지고, 여기에 설정값을 추가한 후 인스턴스에 연결하면 그 인스턴스만 독립적인 설정을 가지게 됩니다.

4단계별 동작 과정

  1. 새 파라미터 그룹 생성AWS 콘솔이나 CLI에서 DB 엔진 버전을 선택해 새 그룹을 만듭니다. 이 그룹은 비어있거나 기본값으로 채워집니다.
  2. 설정값 수정 및 인스턴스 연결파라미터 그룹 내의 각 설정값을 필요에 맞춰 수정한 후, 이 그룹을 사용할 DB 인스턴스에 연결합니다. 연결 후 정적 파라미터는 재부팅을 필요로 합니다.
  3. 비교와 변경 기록여러 파라미터 그룹을 만들게 되면 그룹 간의 차이를 비교 기능으로 확인할 수 있고, 변경 내역이 자동 기록됩니다.

파라미터 값 표기법과 DB 클러스터 파라미터 그룹

파라미터 값에 쓰이는 수식·함수 표기법과, 클러스터 전체에 공통 적용되는 DB 클러스터 파라미터 그룹의 역할을 다룬다.

→ 04-01 참조

1상대의 출발점 확인

파라미터 값을 입력할 때 단순 숫자나 문자열만 쓰는 것으로는 부족합니다. 때로는 인스턴스의 크기에 따라 값을 자동 계산하거나, 하드웨어 정보를 참조하거나, 복잡한 계산식이 필요합니다. 또한 단일 인스턴스뿐 아니라 여러 인스턴스가 함께 작동하는 클러스터 전체에 공통 설정을 적용해야 하는 경우도 있습니다. 그런데 각 인스턴스마다 따로 설정하면 불일치가 발생할 수 있습니다.

2질문 제기

인스턴스 크기에 따라 자동 계산되는 파라미터 값과 클러스터 전체에 공통 적용되는 설정을 어떻게 다루는가?

3구조적 핵심 예시

파라미터 값에 {DBInstanceClassMemory * 0.25}라고 쓰면, AWS가 인스턴스의 메모리 크기를 읽고 자동으로 그 25%를 계산해서 값으로 집어넣습니다. 또는 {GREATEST(값1, 값2)}처럼 함수를 사용해 더 큰 값을 선택하도록 합니다.

4단계별 동작 과정

  1. 파라미터 값 표기법단순 숫자나 문자 대신 함수(GREATEST, LEAST 등)나 인스턴스 속성 참조({DBInstanceClassMemory})를 사용해 값을 동적으로 계산하고, 이 식은 파라미터 적용 시점에 실제 값으로 변환됩니다.

Multi-AZ DB 클러스터 운영과 제약

클러스터는 쓰기용·읽기용 엔드포인트를 따로 제공하고 장애 조치가 더 빠르지만, 지원 엔진·버전·인스턴스 클래스·리전이 제한되고 일부 기능을 쓸 수 없다.

→ 06-03 참조

1상대의 출발점 확인

기존 클래식 Multi-AZ는 거의 모든 데이터베이스 엔진, 버전, 인스턴스 클래스에서 작동했지만 장애 조치 속도가 1~2분 정도 걸리고, 대기본은 읽기에 쓸 수 없다는 한계가 있었습니다. Multi-AZ 클러스터는 더 빠른 장애 조치와 읽기 엔드포인트 분리라는 이점을 제공하지만 그 대신 지원 범위가 좁아집니다.

2질문 제기

Multi-AZ 클러스터를 쓸 때 빠른 장애 조치와 읽기 확장의 이득을 얻으면서 어떤 제약을 감수해야 할까?

3구조적 핵심 예시

MySQL 8.0.28 이상, MariaDB 10.6 이상의 특정 버전, db.r6i 같은 일부 인스턴스 클래스 조합에서만 Multi-AZ 클러스터를 만들 수 있고, Aurora는 지원하지 않습니다. 또한 읽기 복제본 승격, 교차 리전 백업 복사 같은 일부 기능을 클러스터 내에서 못 쓰기도 합니다.

4단계별 동작 과정

  1. 지원 엔진·버전·인스턴스 클래스 확인MySQL, MariaDB, PostgreSQL 중 특정 최신 버전만 지원되므로, 기존 DB와 호환성을 먼저 검증해야 합니다.
  2. 쓰기 엔드포인트와 읽기 엔드포인트 분리클러스터는 cluster-writer.xxx.rds.amazonaws.com(쓰기 전용)과 cluster-reader.xxx.rds.amazonaws.com(읽기 전용)을 별도로 제공하므로 응용 코드에서 엔드포인트를 나눠 사용해야 합니다.
  3. 제약 기능 사전 확인일부 운영 기능(읽기 복제본 생성, 자동 모니터링 기능)을 쓸 수 없으므로 대체 방안을 미리 계획해야 합니다.

읽기 복제본의 원리와 생성·승격

원본 DB의 변경 사항을 비동기로 복사해 읽기 전용으로 쓰는 인스턴스로, 읽기 부하를 분산하다가 필요하면 독립된 단독 DB로 승격시킬 수 있다.

1상대의 출발점 확인

기존 방식은 하나의 DB 인스턴스가 모든 읽기와 쓰기 요청을 혼자 처리했습니다. 읽기 요청이 늘어나면 그 인스턴스의 CPU와 메모리만 증가했고, 성능 개선을 위해 인스턴스 전체를 더 큰 사양으로 업그레이드해야 했습니다.

2질문 제기

원본 DB에 영향을 주지 않으면서 읽기 부하를 다른 인스턴스로 분산시킬 수 있을까?

3구조적 핵심 예시

원본 DB의 변경 사항(INSERT, UPDATE, DELETE)을 트랜잭션 로그 형태로 읽어 비동기로 복제본에 적용하는 방식입니다. 원본에서 쓰기가 일어나면, 그 변경 사항이 별도의 복제본에도 자동으로 반영되어 복제본은 읽기만 처리합니다.

4단계별 동작 과정

  1. 원본에서 트랜잭션 로그 기록원본 DB의 모든 쓰기 작업이 이진 로그(binary log)에 기록됩니다.
  2. 복제본으로 비동기 복사복제본이 원본의 로그를 읽어 같은 변경을 자신의 저장소에 적용하는데, 이 과정이 비동기이므로 원본 성능에 거의 영향을 주지 않습니다.
  3. 복제본에서 읽기 처리 및 필요시 승격복제본은 SELECT만 받아 처리하고, 필요하면 읽기 전용 역할을 벗고 독립된 단독 DB로 승격시킬 수 있습니다.

복제 지연 모니터링과 리전 간 읽기 복제본

비동기 복제라 원본과 복제본 사이에 지연(ReplicaLag)이 생기므로 이를 지표로 감시해야 하며, 다른 리전에 복제본을 두어 지역 재해 대비와 사용자 근처 읽기를 함께 얻을 수 있다.

→ 06-05 참조

1상대의 출발점 확인

읽기 복제본은 비동기로 작동하므로 원본과 복제본 사이에 항상 지연(복제 지연, Replica Lag)이 있습니다. 복제본이 원본의 변경을 완전히 따라잡지 못했다면, 복제본을 읽을 때 조금 낡은 데이터를 받게 되는데 이 지연이 얼마나 되는지 알 방법이 없으면 신뢰할 수 없습니다. 또한 단일 리전의 복제본만으로는 리전 전체 장애 시 대비가 부족합니다.

2질문 제기

복제 지연을 감시하면서 동시에 다른 리전에 복제본을 두어 지역 재해 대비와 낮은 지연성을 동시에 얻을 수 있을까?

3구조적 핵심 예시

원본이 서울 리전에 있고, 같은 리전의 복제본 A와 도쿄 리전의 복제본 B를 둘 다 두는 방식입니다. 복제본 A는 지연이 거의 없어 최신 데이터를 읽을 수 있고, 복제본 B는 지연이 몇 초 있지만 서울 리전 전체가 다운 되어도 도쿄에서 계속 서비스할 수 있습니다.

4단계별 동작 과정

  1. ReplicaLag 지표 모니터링CloudWatch에서 ReplicaLag 지표를 보면 원본과 복제본이 몇 초 차이나는지 확인하고, 알람 설정으로 지연이 임계값을 넘으면 알려받습니다.
  2. 리전 간 복제본 생성같은 리전 복제본 외에 다른 리전에도 읽기 복제본을 만들어, 그 리전의 사용자도 낮은 지연으로 읽을 수 있게 합니다.
  3. 지역 재해 대비와 성능 최적화원본 리전이 장애나면 다른 리전의 복제본을 승격해 서비스를 계속하고, 각 사용자가 가장 가까운 복제본에서 읽음으로써 지연도 낮춥니다.

자동 백업과 수동 스냅샷

RDS가 백업 기간에 맞춰 자동으로 받아 보존 기간이 지나면 지우는 자동 백업과, 사용자가 직접 만들어 지울 때까지 남는 수동 DB 스냅샷의 차이와 사용법.

1상대의 출발점 확인

백업이 없으면 DB 손실 시 되돌릴 방법이 없습니다. 백업을 수동으로만 만들면 깜빡할 수 있고, 필요할 때마다 찍기엔 번거롭습니다. RDS는 두 가지 백업 방식을 제공하는데, 각각의 목적과 유효 기간이 다릅니다.

2질문 제기

계속 안전하게 백업을 받으면서도 중요한 시점은 따로 보관하려면?

3구조적 핵심 예시

매일 자정에 자동으로 백업을 받되 7일만 보관(자동 삭제)하고, 월말이나 배포 전처럼 중요한 시점에는 수동으로 스냅샷을 만들어 필요할 때까지 계속 보관하는 방식입니다.

4단계별 동작 과정

  1. 자동 백업 설정 및 보존 기간BackupRetentionPeriod를 1~35일 범위에서 정해서, RDS가 매일 그 기간까지 자동 백업을 보관했다가 기간이 끝나면 자동 삭제합니다.
  2. 중요 시점에 수동 스냅샷 생성배포 전, 마이그레이션 전, 또는 감사가 필요한 시점에 수동으로 DB 스냅샷을 만들어서 별도 보관합니다.
  3. 복구 시점 선택장애나 오류 복구 시 자동 백업으로 빠르게 복구하거나, 더 오래 보관해야 하는 데이터는 수동 스냅샷에서 복원합니다.

특정 시점 복구(PITR)와 스냅샷 복원

백업과 트랜잭션 로그를 이용해 원하는 과거 시각 상태로, 또는 스냅샷 시점 상태로 '새 DB 인스턴스'를 만들어 되살리는 복원 방식.

→ 07-01 참조

1상대의 출발점 확인

스냅샷만 있으면 스냅샷을 찍은 그 시각의 상태로만 되돌릴 수 있습니다. 예를 들어 10시에 스냅샷을 찍었다면, 10시 정확한 상태로만 복구되고, 10시 30분 상태로는 복구할 수 없습니다. 만약 10시 25분에 나쁜 쿼리가 실행됐다면 그 사이 시간대 데이터는 영구 손실됩니다.

2질문 제기

스냅샷 사이의 시간대 중 원하는 정확한 시각으로 복구할 수 있을까?

3구조적 핵심 예시

스냅샷(10시 상태)과 그 이후의 모든 트랜잭션 로그(10시 1분, 10시 2분, ... , 10시 45분)를 함께 보관하면, 10시 45분 45초 정확히 그 상태로 복구할 수 있습니다. 나쁜 쿼리가 10시 25분에 실행됐다면, 10시 24분 59초 상태로 복구하면 그 손상을 피할 수 있습니다.

4단계별 동작 과정

  1. 스냅샷과 트랜잭션 로그 기반 시각 선택PITR(Point-In-Time Recovery)은 스냅샷을 시작점으로 삼고, 그 이후 모든 변경 사항을 담은 트랜잭션 로그를 이용해 원하는 시각까지 재생합니다.
  2. 그 상태의 새 DB 인스턴스 생성선택한 시각의 상태를 담은 새 DB 인스턴스를 만들어서, 기존 운영 DB는 그대로 두고 복구된 인스턴스에서 검증합니다.
  3. 검증 후 전환복구된 데이터가 맞는지 확인한 후 응용이 새 인스턴스를 가리키도록 연결 주소를 바꿉니다.

7백업·복원·데이터 내보내기07-03

스냅샷 복사·공유와 암호화 스냅샷

DB 스냅샷을 다른 리전이나 계정으로 복사·공유하는 방법과, KMS 키로 암호화된 스냅샷을 다룰 때의 제약.

1상대의 출발점 확인

스냅샷이 하나의 AWS 리전이나 계정 내에만 있으면, 다른 리전에서는 그 스냅샷을 쓸 수 없고 다른 팀이 공유받을 수도 없습니다. 또한 KMS 키로 암호화된 스냅샷은 암호화 키 관리까지 복잡해져서, 단순히 파일을 옮기듯 복사할 수 없습니다.

2질문 제기

암호화된 스냅샷을 다른 리전이나 계정으로 안전하게 옮기거나 공유할 수 있을까?

3구조적 핵심 예시

서울 리전의 암호화 스냅샷을 도쿄 리전으로 복사하는데, 복사 과정에서 서울의 KMS 키로 암호화된 데이터를 도쿄의 KMS 키로 다시 암호화하는 방식입니다. 다른 계정이면 원래 계정에서 암호화 권한을 명시적으로 부여해야 복사 권한이 생깁니다.

4단계별 동작 과정

  1. 스냅샷을 다른 리전이나 계정으로 복사 요청AWS 콘솔이나 API로 스냅샷의 복사본을 대상 리전이나 계정에 만들도록 지시합니다.
  2. 암호화 스냅샷의 KMS 키 재매핑원본이 암호화되어 있으면, 복사 과정에서 원본 리전의 KMS 키와 대상 리전의 KMS 키를 매핑해서 복사본도 같은 수준의 보안을 유지합니다. 다른 계정이면 원본 계정이 대상 계정의 KMS 키 사용 권한을 먼저 부여해야 합니다.
  3. 대상에서 복원복사된 스냅샷에서 새 DB 인스턴스를 만들면, 대상 리전이나 계정에서도 동일한 데이터로 DB를 운영할 수 있습니다.

마스터 사용자 계정 권한과 DB 사용자 관리

DB 인스턴스를 만들 때 생성되는 마스터 사용자는 관리형 서비스라서 제한된 최고 권한을 가지며, 실제 운영용 계정은 이 계정으로 따로 만들어 최소 권한만 준다.

1상대의 출발점 확인

RDS 인스턴스를 만들 때 마스터 사용자(master user)를 반드시 하나 만든다. 이 계정은 DB 내의 가장 높은 권한을 가지고 있어서 사용자 관리, 데이터베이스 생성, 권한 부여 등을 할 수 있다. 하지만 모든 개발자나 애플리케이션이 이 마스터 계정으로 접속하면 실수로 전체 데이터를 삭제하거나 변조할 위험이 크다.

2질문 제기

마스터 사용자의 높은 권한을 유지하면서도, 실제 운영에는 필요한 최소한의 권한만 가진 계정들을 어떻게 관리할 것인가?

3구조적 핵심 예시

마스터 사용자로 접속해 서로 다른 운영 계정들을 만든다. 웹 애플리케이션용 계정은 특정 테이블에서만 SELECT, INSERT, UPDATE 권한만 준다. 리포팅용 계정은 조회(SELECT)만 가능하게 한다. 마스터는 이 계정들을 만들고 권한을 관리하는 데만 사용한다.

4단계별 동작 과정

  1. 마스터 계정 생성RDS 인스턴스 생성 시 마스터 사용자 이름과 암호를 설정한다. AWS가 관리하는 서비스이기 때문에 이 계정은 완전한 최고 권한이 아니라 제한된 관리 권한을 갖는다.
  2. 운영용 계정 생성마스터 계정으로 접속해서 각 목적(웹앱, 배치 작업, 분석)에 맞는 새로운 DB 사용자를 CREATE USER 명령으로 만든다.
  3. 최소 권한 부여각 운영 계정에 필요한 테이블과 작업(SELECT, INSERT 등)에만 GRANT 권한을 준다. 예를 들어 웹앱은 고객 정보 테이블에 읽고 쓸 권한만, 분석 팀은 조회만 가능하게 한다.

RDS에 접속하는 신원을 확인하는 방법으로 DB 자체 암호 인증, IAM 자격 증명으로 토큰을 받아 접속하는 IAM 인증, AD 계정을 쓰는 Kerberos 인증 중에서 고른다.

1상대의 출발점 확인

전통적인 DB 인증은 사용자 이름과 암호(password)를 입력해 신원을 확인한다. 암호를 코드에 넣거나 설정 파일에 저장해야 하는데, 이 파일이 노출되면 DB 접근 권한을 얻을 수 있다. 또한 암호를 정기적으로 바꾸려면 코드나 설정도 함께 수정해야 하는 번거로움이 있다.

2질문 제기

암호 외에 다른 방식으로 DB 접속 신원을 확인할 수 있고, 자격 증명(credentials) 관리를 더 안전하게 할 수 있을까?

3구조적 핵심 예시

AWS에서 실행되는 애플리케이션이 RDS에 접속할 때, 암호 대신 IAM 역할(role)에서 얻은 임시 토큰을 사용한다. 토큰은 15분마다 자동 갱신되고 코드에는 보이지 않는다. 온프레미스나 Windows 환경이면 Active Directory의 Kerberos 인증을 사용해 Windows 로그인 자격으로 DB에 접속한다.

4단계별 동작 과정

  1. 인증 방식 선택RDS 인스턴스 설정에서 암호 인증, IAM 인증, 또는 Kerberos(Windows 전용) 중 하나를 활성화한다.
  2. 신원 확인암호 방식은 사용자 이름과 암호를 전달해 확인한다. IAM 인증은 AWS IAM이 발급한 임시 토큰을 검증한다. Kerberos는 Active Directory의 사용자 신원을 확인한다.
  3. 접속 허가신원 확인이 끝나면 사용자 계정이 DB에서 가진 권한에 따라 접속을 허가한다.

  2. 애플리케이션에서 조회애플리케이션이 Secrets Manager API를 호출하면 현재 유효한 암호를 받는다. 이 과정은 프로그램 실행 시나 필요할 때마다 일어날 수 있다.

SSL/TLS로 연결 암호화하고 인증서 갱신하기

애플리케이션과 DB 사이를 오가는 데이터를 SSL/TLS로 암호화하고, 만료되는 RDS 인증 기관(CA) 인증서를 제때 교체해 접속이 끊기지 않게 하는 일이다.

1상대의 출발점 확인

애플리케이션과 RDS 데이터베이스 사이의 통신이 암호화되지 않으면 네트워크상에서 데이터가 평문으로 흘러다닌다. 누군가 네트워크 패킷을 가로채면 쿼리와 결과를 모두 볼 수 있다. 또한 RDS는 자체 인증 기관(CA) 인증서를 사용하는데, 이 인증서가 만료되면 SSL/TLS 연결이 실패해 접속 오류가 발생한다.

2질문 제기

네트워크상의 데이터 도청을 막으면서도, RDS 인증서 만료로 인한 서비스 중단을 어떻게 예방할 수 있을까?

3구조적 핵심 예시

애플리케이션이 DB에 연결할 때 SSL/TLS를 활성화하면 데이터를 주고받을 때마다 암호화되고, RDS의 인증서를 검증해 정말 AWS의 RDS인지 확인한다. AWS는 RDS의 CA 인증서를 단계적으로 갱신하고 미리 공지하므로, 애플리케이션에서 새 인증서를 다운받아 설정하면 연결이 계속 유지된다.

4단계별 동작 과정

  1. SSL/TLS 활성화RDS 인스턴스 설정에서 SSL/TLS 암호화를 필수로 설정한다. 애플리케이션 연결 문자열에 SSL 옵션(예: ?sslmode=require)을 추가해 암호화된 연결을 강제한다.
  2. 인증서 검증연결 시 애플리케이션이 RDS의 CA 인증서를 검증해 정당한 AWS 엔드포인트임을 확인한다. 인증서는 /etc/ssl/certs/ 같은 시스템 경로나 애플리케이션 번들에서 로드된다.
  3. 인증서 갱신AWS가 CA 인증서를 예정된 날짜에 갱신한다. 미리 공지된 기간 내에 새 인증서를 다운받아 애플리케이션 서버에 배포하면 갱신 후에도 접속이 끊기지 않는다.

→ 08-04 참조

1상대의 출발점 확인

RDS 데이터베이스의 데이터, 스냅샷, 백업, 로그들이 디스크에 저장될 때 평문(암호화되지 않은 상태)으로 보관되면, 저장 매체(드라이브)가 물리적으로 누출되거나 데이터센터의 디스크를 악의적으로 접근하는 경우 데이터를 직접 읽을 수 있다. 이는 특히 규정 준수(HIPAA, PCI-DSS 등)가 필요한 산업에서 큰 문제다.

2질문 제기

저장되어 있는 DB 데이터, 백업, 로그를 암호화해 저장 매체 유출 시에도 내용을 읽을 수 없게 할 수 있을까?

3구조적 핵심 예시

RDS 인스턴스를 만들 때 암호화를 활성화하고 AWS KMS(Key Management Service) 키를 선택하면, 그 데이터베이스의 모든 데이터가 디스크에 저장될 때 그 KMS 키로 암호화된다. 스냅샷과 백업도 같은 키로 자동 암호화되고, 로그 파일도 암호화된다. 누군가 저장 매체를 빼내도 KMS 키 없이는 데이터를 복호화할 수 없다.

4단계별 동작 과정

  1. 암호화 설정RDS 인스턴스를 생성할 때 "암호화 활성화(Enable Encryption)" 옵션을 선택하고 사용할 KMS 키를 지정한다. 기본 AWS 관리형 키를 쓰거나, 직접 만든 고객 관리형 키(customer-managed key)를 선택할 수 있다.
  2. 저장 데이터 암호화RDS가 데이터베이스 파일, 트랜잭션 로그, 스냅샷, 백업을 모두 KMS 키로 암호화해 저장한다. 이 과정은 자동으로 일어나며 애플리케이션은 수정할 필요가 없다.
  3. 접근 제어KMS 키 권한(key policy)을 관리해 누가 암호화된 데이터를 복호화할 수 있는지 제어한다. RDS 서비스와 권한받은 IAM 계정만 복호화 가능하고, 그 외는 데이터를 읽을 수 없다.

2질문 제기

4단계별 동작 과정

  1. 누가 접근하는가 제어IAM 역할(Role)과 정책(Policy)으로 AWS 사용자 또는 애플리케이션에게 RDS 조작 권한을 부여하거나 거부한다.
  2. 어디서 접근하는가 제어VPC(Virtual Private Cloud) 안에서만 DB를 배치하고, 보안 그룹(Security Group)으로 특정 IP나 포트만 연결 가능하게 제한한다.
  3. 접근 기록 추적CloudTrail과 DB 로깅으로 모든 접근과 변경 작업을 타임스탬프와 함께 저장해서 규정 준수 감시와 사고 조사에 쓴다.

CloudWatch 지표와 경보

1상대의 출발점 확인

DB의 CPU, 메모리, 디스크 같은 수치를 사람이 수동으로 확인해야 한다면 24시간 모니터링이 불가능하다. 언제 기준을 넘었는지 모르고, 문제가 생져도 한참 뒤에야 알게 된다. 또한 어느 수준이 위험한지 기준을 미리 정할 방법이 없다.

2질문 제기

DB의 중요한 수치들을 자동으로 모아서 기준을 넘으면 즉시 알려줄 수 있을까?

3구조적 핵심 예시

CloudWatch가 매분 CPU를 측정해서 기록해 두고, "CPU가 80% 이상이면 이메일과 Slack으로 알린다" 같은 경보(Alarm)를 미리 설정해 두는 방식.

4단계별 동작 과정

  1. 지표 수집CloudWatch 에이전트나 RDS 자체에서 CPU, 메모리, 디스크 사용률, 데이터베이스 연결 수, 네트워크 처리량 같은 값을 일정 간격(보통 1분)으로 수집한다.
  2. 경보 설정"CPU가 70% 이상 5분 이상 지속" 같은 조건을 미리 정하고, 그 조건에 도달하면 실행할 액션(이메일, SMS, SNS, 자동 복구 등)을 지정한다.
  3. 알림 발송설정한 조건을 만족하면 SNS를 통해 지정한 채널로 자동 알림을 보낸다.

2질문 제기

  2. 원인 분석각 SQL 쿼리, 호스트(접속 IP), 대기 이벤트(락, I/O, CPU 등)별로 얼마나 많은 세션이 시간을 쓰고 있는지 분류한다.
  3. 시각화와 보고막대 차트로 시간 흐름에 따른 부하 추이를 보여 주고, 클릭하면 어느 쿼리가 문제인지 상세히 볼 수 있게 한다.

2질문 제기

3구조적 핵심 예시

  2. 이벤트 구독 생성SNS 주제를 생성하고, 어떤 이벤트 카테고리(백업, 가용성, 장애 복구 등)를 받을지 선택한 후, 구독 대상(이메일, SMS, Lambda, Slack 연동 등)을 설정한다.
  3. 자동 알림 발송지정한 이벤트가 발생하면 SNS가 즉시 구독자들에게 알림을 보낸다.

RDS 인스턴스가 동작하면서 생기는 오류, 느린 쿼리, 일반 활동 기록은 데이터베이스 엔진이 생성합니다. 기존에는 이 로그 파일들이 인스턴스 내부 저장소에만 쌓이므로, 문제가 발생했을 때 그 원인을 찾으려면 인스턴스에 직접 접근해서 로그 파일을 읽거나 내려받아야 했습니다. 파일이 용량 한계에 도달하면 자동으로 삭제되기도 하고, 여러 인스턴스의 로그를 한 곳에서 보기도 어렵습니다.

3구조적 핵심 예시

느린 쿼리가 발생한 상황에서, RDS는 그 느린 쿼리 기록을 로그 파일에 남기고, AWS 콘솔이나 CLI, CloudWatch Logs를 통해 그 기록에 접근할 수 있습니다. 콘솔에서 "로그 및 이벤트" 섹션을 열면 각 로그 파일이 목록으로 나타나고, 여기서 직접 내용을 읽거나 파일 전체를 다운로드할 수 있습니다.

4단계별 동작 과정

  1. 로그 파일 생성데이터베이스 엔진이 오류, 느린 쿼리, 일반 활동을 기록하면서 에러 로그, 슬로우 쿼리 로그, 일반 로그 등 여러 종류의 로그 파일을 생성합니다.
  2. 로그 접근 및 다운로드AWS 콘솔, AWS CLI, 또는 쿼리를 통해 로그 파일 목록을 확인하고, 텍스트로 읽거나 파일 전체를 다운로드할 수 있습니다.
  3. CloudWatch Logs로 내보내기로그를 장기 보관하고 검색하기 위해 RDS가 자동으로 로그를 CloudWatch Logs로 전송하도록 설정할 수 있으며, 여기서 실시간 모니터링과 분석을 수행합니다.

활동 스트림·CloudTrail·GuardDuty로 감사하기

DB 안에서 실행된 활동과 AWS API 호출 기록을 남겨 누가 무엇을 했는지 추적하고 위협을 탐지하는 감사 수단들.

1상대의 출발점 확인

데이터베이스 인스턴스가 생성되고, 설정이 변경되고, 쿼리가 실행되는 모든 사건에 대해 "누가, 언제, 무엇을 했는가"를 기록해야 합니다. 기존에는 데이터베이스 내부 감사 로그만으로는 AWS API 수준의 변경(예: 인스턴스 크기 조정, 백업 설정 변경)을 추적할 수 없었고, DB 내부의 개별 쿼리 실행 내역도 자동으로 기록되지 않는 경우가 많았습니다.

2질문 제기

데이터베이스 내부에서 어떤 데이터가 누구에 의해 조회되거나 변경되었는지, 그리고 AWS 관리 계정에서 인스턴스 구성을 어떻게 변경했는지 모두 추적할 수 있을까?

3구조적 핵심 예시

RDS 인스턴스에 접속한 사용자가 SELECT 쿼리를 실행하면, RDS의 활동 스트림이 그 행동(사용자, 쿼리, 실행 시간, 영향받은 테이블)을 기록합니다. 동시에 AWS API로 인스턴스 설정을 변경하는 행동은 CloudTrail이 기록하고, 비정상적인 접근 시도나 의심 활동은 GuardDuty가 탐지합니다.

4단계별 동작 과정

  1. DB 활동 스트림RDS가 모든 데이터베이스 연결, 쿼리 실행, 트랜잭션 변경을 실시간으로 기록하며, 암호화된 스트림으로 Amazon Kinesis 또는 CloudWatch Logs에 전송합니다.
  2. CloudTrail로 AWS API 감사콘솔이나 SDK를 통한 모든 AWS 서비스 API 호출(인스턴스 생성, 설정 변경, 백업 생성 등)을 기록해 누가 언제 어떤 작업을 했는지 추적합니다.
  3. GuardDuty의 위협 탐지이상 접근 시도, 비정상 네트워크 트래픽, 보안 주의사항(예: 보안 그룹의 과도한 개방)을 자동으로 탐지하고 알려줍니다.

RDS Proxy: 연결 풀링이 필요한 이유

애플리케이션이 만드는 수많은 DB 연결을 프록시가 모아 재사용해, 연결 폭주로 인한 메모리 고갈과 장애 시 긴 전환 시간을 줄여주는 완전관리형 연결 풀이다.

1상대의 출발점 확인

애플리케이션이 데이터베이스와 통신할 때마다 새로운 연결을 생성합니다. 연결 생성은 자격 증명 인증, 메모리 할당, 연결 초기화를 포함하는 과정으로 시간이 걸립니다. 사용자가 많아지거나 트래픽이 갑자기 증가하면, 애플리케이션이 동시에 수백 또는 수천 개의 연결을 만들려고 시도하고, 이는 데이터베이스 메모리를 빠르게 고갈시키며, 연결 거부 오류로 이어집니다. 또한 연결이 끊어졌을 때 새 연결을 기다리는 시간이 길어지면서 애플리케이션 응답 속도가 급격히 저하됩니다.

2질문 제기

애플리케이션이 만드는 수많은 데이터베이스 연결 요청을 제한하고 재사용하면서도 애플리케이션 코드는 변경하지 않는 방법은?

3구조적 핵심 예시

RDS Proxy는 애플리케이션과 데이터베이스 사이에 위치하면서, 애플리케이션의 수많은 연결 요청을 받아 내부적으로 관리하는 연결 풀에 모아 두었다가, 실제로 필요한 시점에만 데이터베이스의 적은 수의 연결을 사용합니다. 예를 들어 애플리케이션이 1000개의 동시 연결을 요청해도 프록시가 이를 받아서 데이터베이스에는 20개의 연결만 전달하는 방식입니다.

4단계별 동작 과정

  1. 연결 풀링프록시가 애플리케이션의 연결 요청을 받으면, 자신이 미리 만들어 둔 데이터베이스 연결 풀에서 유휴(사용 중이 아닌) 연결을 찾아 애플리케이션에 할당합니다.
  2. 연결 재사용애플리케이션이 쿼리를 실행한 후 연결을 반환하면, 프록시는 그 연결을 닫지 않고 풀에 돌려놓아 다른 애플리케이션 요청이 사용할 수 있게 준비합니다.
  3. 장애 전환 시간 단축데이터베이스 인스턴스에 장애가 발생해 새로운 인스턴스로 자동 전환되더라도, 프록시가 연결을 관리하므로 애플리케이션은 프록시 주소만 알고 있으면 되고, 실제 데이터베이스 전환 시간이 크게 단축됩니다.

5본질 요약

애플리케이션의 많은 연결 요청을 제한된 수의 데이터베이스 연결로 변환해 메모리 낭비를 줄이고 성능을 안정화하는 것

RDS Proxy를 어떻게 만들고 애플리케이션이 사용할 수 있도록 연결하는가?

3구조적 핵심 예시

AWS 콘솔에서 "RDS Proxy 생성" 버튼을 누르면, 몇 가지 필수 정보를 입력하는 화면이 나옵니다. 대상 데이터베이스(예: my-rds-instance)를 선택하고, AWS Secrets Manager에 저장된 자격 증명을 지정하고, 프록시가 실행될 VPC와 서브넷을 선택한 후 "생성"을 누르면 프록시가 생성되고, 콘솔에 프록시 엔드포인트 주소(예: my-proxy.proxy-abc123.us-east-1.rds.amazonaws.com)가 나타납니다. 애플리케이션의 데이터베이스 접속 주소를 이 프록시 엔드포인트로 바꾸면 됩니다.

4단계별 동작 과정

  1. 자격 증명 준비데이터베이스 사용자 이름과 비밀번호를 AWS Secrets Manager에 저장하고, 프록시가 이에 접근할 수 있도록 권한을 설정합니다.
  2. 프록시 생성 설정대상 데이터베이스 인스턴스, Secrets Manager 비밀, IAM 역할(프록시가 비밀 접근을 위해 필요), 실행할 VPC와 서브넷을 지정해 프록시를 생성합니다.
  3. 애플리케이션 연결 업데이트프록시 생성 후 얻은 엔드포인트 주소(호스트명)를 애플리케이션의 데이터베이스 연결 설정에서 기존 RDS 엔드포인트 대신 입력하면, 애플리케이션의 모든 요청이 프록시를 거쳐 전달됩니다.

RDS Proxy 운영: 핀닝 회피와 모니터링

임시 테이블·세션 변수 같은 상태를 남기면 연결이 특정 세션에 고정(pinning)되어 풀 효과가 사라지므로, 이를 피하는 사용 패턴과 CloudWatch 지표·로그로 프록시 상태를 확인하는 방법이다.

1상대의 출발점 확인

RDS Proxy가 연결 풀링을 효과적으로 작동시키려면, 한 애플리케이션 연결이 데이터베이스의 같은 연결을 계속 사용해야 합니다. 그런데 애플리케이션이 임시 테이블을 만들거나, 세션 변수를 설정하거나, 트랜잭션 내에서 특정 연결에만 의존하는 상태를 유지하면, 프록시가 그 애플리케이션 연결을 특정 데이터베이스 연결에 고정(pinning)해야 합니다. 고정되면 다른 애플리케이션이 그 데이터베이스 연결을 재사용할 수 없으므로, 풀의 효과가 사라지고 성능이 급격히 떨어집니다.

2질문 제기

애플리케이션이 불필요하게 데이터베이스 연결에 고정되지 않으면서 프록시의 연결 풀 효과를 유지하려면?

3구조적 핵심 예시

애플리케이션이 임시 테이블을 만들면 그 연결이 프록시에 의해 자동으로 특정 데이터베이스 연결에 고정됩니다. 프록시는 이를 "pinning event"로 기록하고, CloudWatch 로그에 남깁니다. 개발자는 이 로그를 보면서 어느 애플리케이션이 얼마나 자주 고정되는지 파악할 수 있고, 그 애플리케이션 코드를 수정해 임시 테이블 대신 다른 방법을 사용하도록 변경할 수 있습니다.

4단계별 동작 과정

  1. 핀닝 회피 패턴 적용애플리케이션이 임시 테이블 대신 일반 테이블이나 메모리 캐시를 사용하고, 세션 변수 대신 쿼리 파라미터를 사용하며, 명시적 트랜잭션 대신 필요시에만 트랜잭션을 사용하도록 코드를 작성합니다.
  2. CloudWatch로 핀닝 모니터링RDS Proxy가 생성하는 로그를 CloudWatch Logs에서 확인하면서 "pin_triggered"나 "pinning_event" 같은 이벤트를 추적하고, 어느 애플리케이션이 자주 고정되는지 파악합니다.
  3. 성능 지표 확인CloudWatch 대시보드에서 프록시의 활성 연결 수, 유휴 연결 수, 쿼리 지연 시간(latency) 등을 모니터링하면서 풀이 제대로 동작하고 있는지 확인합니다.

zero-ETL 통합과 다른 AWS 서비스 연동

RDS 의 데이터를 파이프라인 없이 Amazon Redshift 등으로 거의 실시간 복제하는 zero-ETL 통합을 비롯해, RDS 를 다른 AWS 분석·애플리케이션 서비스와 잇는 방법이다.

1상대의 출발점 확인

RDS의 데이터를 분석 서비스(예: Amazon Redshift)로 옮기려면, 별도의 파이프라인(ETL 또는 ELT)을 만들어야 했습니다. RDS에서 데이터를 추출하고, 변환하고, Redshift에 로드하는 과정이 필요했으며, 이는 시간이 걸리고, 비용이 들고, 실시간성이 떨어졌습니다. 또한 데이터 일관성을 보장하기 위해 복잡한 로직을 작성해야 했습니다.

2질문 제기

RDS의 데이터를 별도의 파이프라인 없이, 거의 실시간으로 다른 AWS 서비스로 옮길 수 있을까?

3구조적 핵심 예시

RDS의 zero-ETL 통합은 데이터베이스 변경(INSERT, UPDATE, DELETE)이 발생하면, RDS가 그 변경을 실시간으로 감지하고 Amazon Redshift 같은 다른 서비스에 자동으로 복제합니다. 개발자는 별도의 파이프라인 코드를 작성할 필요 없이, AWS 콘솔에서 "zero-ETL 통합 만들기" 옵션을 선택하고 대상 Redshift 클러스터를 지정하기만 하면 됩니다.

4단계별 동작 과정

  1. zero-ETL 통합 설정RDS 인스턴스에서 Redshift 클러스터로의 zero-ETL 통합을 생성하고, 복제할 데이터베이스와 테이블을 선택합니다.
  2. 실시간 데이터 복제RDS에서 데이터 변경이 발생하면, 이를 이진 로그(바이너리 로그, 변경 기록)로 감지하고, Redshift로 거의 실시간 전송합니다.
  3. 다른 AWS 서비스 연동Lambda, EventBridge(규칙 기반 자동화), DMS(Database Migration Service) 등의 서비스와 RDS를 연결해, 데이터 변경에 따라 자동으로 다른 작업(예: 알림 전송, 캐시 업데이트, 분석 트리거)이 실행되도록 설정할 수 있습니다.

5본질 요약

데이터를 RDS로 옮기는 경로

기존 온프레미스·EC2·타 DB 의 데이터를 덤프 파일 가져오기, 복제, AWS DMS 같은 방법으로 RDS 인스턴스에 적재하는 이전 경로들이다.

1상대의 출발점 확인

기존 데이터베이스(온프레미스 MySQL, EC2의 PostgreSQL, 타사 클라우드 RDS 등)에 있는 데이터를 AWS RDS로 이전(migration)해야 할 때, 데이터 손실이나 불일치가 없도록 해야 합니다. 단순히 데이터를 내려받아 업로드하는 것만으로는 부족한데, 특히 마이그레이션 중에도 기존 데이터베이스에서 계속 데이터가 변경되고 있다면 이를 따라잡아야 하기 때문입니다.

2질문 제기

기존 데이터베이스의 모든 데이터를 RDS로 정확하게 옮기면서, 마이그레이션 중 발생한 변경까지 반영하려면?

3구조적 핵심 예시

온프레미스 MySQL 서버에 있는 데이터를 RDS로 옮기는 작업에서, 먼저 mysqldump 명령으로 전체 데이터베이스를 SQL 파일로 내보내고, 이를 RDS의 mysql 클라이언트로 import합니다. 그런 다음 AWS DMS(Database Migration Service)를 사용해 마이그레이션 후에 발생한 변경을 계속해서 복제하면, 최종적으로 두 데이터베이스가 일치하는 상태에 도달합니다.

4단계별 동작 과정

  1. 초기 데이터 덤프 및 로드기존 데이터베이스에서 모든 데이터를 SQL 형식의 덤프 파일로 추출하고, 이를 RDS 인스턴스에 import하거나, AWS S3에 저장한 후 RDS의 로드 유틸리티(예: LOAD DATA FROM S3)로 적재합니다.
  2. AWS DMS로 지속적 복제AWS Database Migration Service를 설정해 초기 로드 완료 후, 기존 데이터베이스의 모든 변경(INSERT, UPDATE, DELETE)을 RDS로 거의 실시간 복제합니다.
  3. 유효성 검증 및 전환소스와 타겟 데이터가 완전히 일치하는지 검증한 후, 애플리케이션이 사용하는 데이터베이스 엔드포인트를 기존 시스템에서 RDS로 변경하면, 마이그레이션이 완료됩니다.

RDS for MySQL

오픈소스 MySQL을 RDS가 관리형으로 돌려주는 엔진으로, 지원 버전·파라미터·복제(읽기 전용 복제본)·업그레이드 방식이 MySQL 고유 규칙을 따른다.

1상대의 출발점 확인

직접 MySQL 서버를 설치해서 운영하려면 버전 업데이트, 패치 적용, 백업, 복제 구성 등을 개발팀이 직접 관리해야 합니다. MySQL의 각 버전마다 지원되는 파라미터(데이터베이스 설정값)가 다르고, 읽기 복제본을 만들려면 복제(Replication) 기능을 수동으로 설정해야 합니다. 업그레이드할 때도 MySQL의 고유한 절차를 따라야 하는데, 버전 간 호환성 문제나 데이터 손실 위험이 있을 수 있습니다.

2질문 제기

AWS가 MySQL의 이 모든 운영 작업을 대신 관리해주되, MySQL의 버전·파라미터·복제·업그레이드 규칙을 그대로 유지할 수 있을까요?

3구조적 핵심 예시

개발팀이 DB 인스턴스를 생성하면, AWS는 선택한 MySQL 버전(8.0, 5.7 등)에 해당하는 관리 환경을 구성하고, 그 버전에서 지원하는 파라미터만 노출하며, 복제 구성을 AWS 콘솔에서 클릭으로 만들 수 있게 제공합니다.

4단계별 동작 과정

  1. 버전 선택 및 파라미터 적용개발팀이 생성 시 MySQL 버전을 지정하면, RDS는 그 버전의 공식 파라미터 세트를 기본값으로 설정하고, 개발팀은 DB 파라미터 그룹(설정값 모음)을 생성해서 필요한 파라미터만 수정합니다.
  2. 읽기 복제본 생성"읽기 전용 복제본 생성" 버튼을 누르면 RDS가 MySQL의 바이너리 로그 기반 복제(Binary Log Replication) 기능을 자동으로 구성하고, 복제 지연 모니터링까지 제공합니다.
  3. 메이저 버전 업그레이드MySQL 5.7에서 8.0으로 올릴 때 RDS가 호환성 검사를 먼저 수행하고, 주요 파라미터 변경 사항을 사전 알림으로 표시한 뒤 업그레이드를 진행합니다.

RDS for MariaDB

MySQL 호환 분기인 MariaDB를 RDS에서 운영하는 엔진으로, 버전 정책과 일부 플러그인·복제 기능이 MySQL과 다르게 제공된다.

1상대의 출발점 확인

MariaDB는 MySQL에서 파생된 오픈소스 데이터베이스로, MySQL과 기본적으로 호환되지만 버전 출시 주기, 기본 제공되는 플러그인, 복제 방식에서 차이가 있습니다. MySQL의 관리 절차와 동일하게 적용하면 MariaDB 고유의 기능이나 제약을 놓치게 됩니다.

2질문 제기

MySQL 기반의 매니지드 서비스를 제공하되, MariaDB의 버전 정책과 플러그인, 복제 옵션을 별도로 지원할 수 있을까요?

3구조적 핵심 예시

RDS에서 MariaDB 엔진을 선택하면, MySQL과 별도의 버전 라인(10.3, 10.4, 10.5, 10.6, 11 등)이 표시되고, 각 버전마다 MariaDB 공식에서 제공하는 플러그인(예: Galera Cluster 관련 설정)이 DB 파라미터 그룹에서만 나타납니다.

4단계별 동작 과정

  1. MariaDB 버전 선택엔진을 MariaDB로 선택하면 MariaDB 공식 버전 라인이 표시되며, 각 버전의 지원 종료 날짜와 권장 버전이 AWS 문서에 별도로 관리됩니다.

RDS for PostgreSQL

PostgreSQL을 RDS에서 운영하는 엔진으로, 확장(extension) 설치, rds_superuser 권한 모델, 메이저 업그레이드 절차가 이 엔진 고유의 핵심 포인트다.

1상대의 출발점 확인

PostgreSQL을 직접 운영하려면 데이터 타입 확장, 함수 작성, 성능 최적화를 위해 설치형 확장(extension)을 수동으로 추가해야 합니다. PostgreSQL에는 슈퍼유저(superuser) 권한이 있는데, RDS 환경에서 는 보안상 완전한 슈퍼유저 권한을 개발팀에게 주지 않고 제한된 권한(rds_superuser)을 제공합니다. 또한 메이저 버전을 올릴 때 pg_upgrade 같은 도구로 별도 절차를 거쳐야 합니다.

2질문 제기

3구조적 핵심 예시

개발팀이 PostgreSQL을 생성하고 데이터베이스에 접속한 뒤 CREATE EXTENSION hstore; 명령을 실행하면, AWS가 사전에 검증한 확장 패키지(PostGIS, UUID 등)가 설치됩니다. 동시에 개발팀은 완전한 슈퍼유저가 아니라 rds_superuser 권한을 받아서, 확장 설치는 가능하지만 특정 시스템 수정(예: 연결 수 제한 변경)은 차단됩니다.

4단계별 동작 과정

  1. 확장(Extension) 설치 관리RDS가 검증한 확장 목록(pgcrypto, hstore, PostGIS 등)을 노출하고, 개발팀이 CREATE EXTENSION 명령으로 바로 설치할 수 있도록 하며, 충돌이나 의존성 문제가 없는지 사전 검사합니다.
  2. rds_superuser 권한 모델AWS는 완전한 superuser 대신 제한된 권한의 rds_superuser 롤을 제공하며, 여기에는 확장 설치, 사용자 관리, 데이터베이스 생성 같은 권한이 포함되지만, 서버 레벨 파라미터 변경은 불가능하게 설정합니다.
  3. 메이저 업그레이드 절차PostgreSQL 12에서 13으로 올릴 때, RDS가 내부적으로 pg_upgrade 도구를 실행하고, 업그레이드 전 호환성 검사 보고서를 제공한 뒤, 실패 시 자동 롤백을 수행합니다.

2질문 제기

3구조적 핵심 예시

RDS Oracle 인스턴스를 생성할 때 "License Included(라이선스 포함)" 또는 "BYOL(자신의 라이선스 사용)" 옵션을 선택합니다. License Included를 고르면 AWS가 Oracle 라이선스 비용을 RDS 요금에 포함시키고, BYOL을 고르면 개발팀이 이미 보유한 라이선스를 등록해서 비용을 절감할 수 있습니다. 어느 쪽을 선택하든 리스너는 AWS가 자동으로 구성하므로, 개발팀은 데이터베이스 콘텐츠만 관리하면 됩니다.

4단계별 동작 과정

  1. 에디션 및 라이선스 모델 선택Enterprise Edition, Standard Edition 2 등 Oracle 에디션을 선택하고, License Included 또는 BYOL 중 하나를 결정하면, RDS가 해당 라이선스 정책을 자동으로 적용합니다.
  2. 마스터 사용자 권한 제한RDS는 마스터 사용자에게 SYSDBA 권한을 완전히 주지 않고, 데이터 조회, 수정, 저장 프로시저 실행 같은 제한된 권한만 부여합니다. 서버 재시작이나 메모리 구성 변경 같은 시스템 작업은 AWS가 직접 수행합니다.
  3. 리스너 및 접속 방식 자동화AWS가 Oracle Net Listener를 자동으로 구성하고, 개발팀은 엔드포인트(호스트명)와 포트번호만 제공받아 SQL*Plus, JDBC, Oracle Client 등으로 접속합니다.

Amazon RDS Custom: OS·DB 접근이 필요할 때

관리형 편의를 유지하면서도 기본 운영체제와 데이터베이스에 직접 접근·커스터마이즈해야 하는 레거시·상용 앱을 위한 RDS 변형이다.

1상대의 출발점 확인

표준 RDS는 데이터베이스 수준의 작업만 허용하고, 호스트 운영체제(커널, 파일시스템, 시스템 라이브러리)는 AWS가 완전히 관리합니다. 따라서 커널 파라미터 조정, 사용자 정의 소프트웨어 설치, 또는 특정 OS 기능에 의존하는 레거시 애플리케이션(예: 타사 데이터베이스 에이전트, 감시 도구)은 표준 RDS에서 실행할 수 없습니다.

2질문 제기

데이터베이스 관리형 편의는 유지하면서 OS 수준의 커스터마이제이션은 어떻게 할 수 있을까요?

3구조적 핵심 예시

RDS Custom은 데이터베이스와 호스트 운영체제 모두에 SSH와 Systems Manager Session Manager로 직접 접근을 열어줍니다. 백업, 복제, 자동 패치 같은 AWS의 기본 관리 작업은 여전히 수행되지만, 사용자는 필요시 커널을 수정하거나 사용자 정의 에이전트를 설치할 수 있습니다.

4단계별 동작 과정

  1. 관리형 편의와 직접 접근의 결합RDS Custom 인스턴스는 데이터베이스 자동화(백업, 장애 조치)를 받으면서도, 사용자가 환경 설정 파일을 수정하거나 OS 패키지를 설치할 수 있도록 root/관리자 수준의 쉘 접근을 제공합니다.
  2. 자동화 일시중지와 재개OS 변경(커널 업데이트, 타사 소프트웨어 설치 등)을 할 때 AWS 자동화가 간섭하지 않도록 자동화를 일시중지합니다. 변경 후 자동화를 다시 시작하면 AWS가 패치 주기를 정상적으로 재개합니다.
  3. 감시와 지원 유지AWS는 호스트 수준의 변경사항을 추적(감시 기능 활성화 시)하고, 문제가 발생하면 변경 이력을 바탕으로 지원을 제공합니다.

운영 모범 사례와 문제 진단

AWS가 권장하는 RDS 운영 지침과, 연결 실패·성능 저하·용량 부족 같은 흔한 장애를 원인별로 짚어보는 방법이다.

→ 12-04 참조

1상대의 출발점 확인

RDS 인스턴스를 만들고 데이터를 넣은 후, 시간이 지나면서 연결이 끊기거나, 쿼리가 느려지거나, 디스크가 꽉 찬다는 알람이 옵니다. 이런 장애는 다양한 원인(나쁜 연결 관리, 인덱스 부족, 부적절한 파라미터, 과도한 로드)에서 비롯되는데, 근본 원인을 찾기 위한 체계적인 진단 절차가 없으면 시간만 낭비합니다.

2질문 제기

RDS의 일반적인 장애(연결 실패, 성능 저하, 용량 부족)의 원인을 빠르게 특정하고 해결하려면 무엇을 확인해야 할까요?

3구조적 핵심 예시

AWS는 Enhanced Monitoring(호스트 OS 수준 메트릭)과 Performance Insights(데이터베이스 활동 분석)라는 두 가지 진단 도구를 제공합니다. Enhanced Monitoring로 CPU, 메모리, 디스크 I/O를 시스템 레벨에서 본 후, Performance Insights로 데이터베이스 내 가장 시간을 많이 쓰는 쿼리나 대기 현상을 파악하면, 병목(데이터베이스 문제인지 인프라 문제인지)을 명확히 할 수 있습니다.

4단계별 동작 과정

  1. 모니터링 활성화와 기준선 설정Enhanced Monitoring와 Performance Insights를 활성화하고, 정상 운영 중 CPU, 메모리, 네트워크 I/O의 일반적인 수치(기준선)를 기록합니다. 나중에 문제 발생 시 기준선과의 차이로 원인을 추적합니다.
  2. 성능 저하 진단쿼리가 느려지면 Performance Insights에서 가장 오래 실행 중인 쿼리와 그것이 기다리는 리소스(락, 디스크 I/O, CPU)를 확인합니다. 동시에 Enhanced Monitoring로 호스트 자원이 충분한지 검증합니다.
  3. 장애별 대응 패턴(1) 연결 수 초과: 인스턴스 클래스 업그레이드 또는 RDS Proxy(연결 풀링) 도입, (2) 디스크 부족: 자동 저장 공간 확장 설정 또는 불필요한 데이터 정리, (3) 느린 쿼리: 인덱스 추가, 파라미터 튜닝, 또는 읽기 전용 복제본 배치.

5본질 요약

AWS의 내장 모니터링 도구(Enhanced Monitoring, Performance Insights, CloudWatch)와 공식 모범 사례를 바탕으로 RDS 장애의 근본 원인을 빠르게 특정하고 체계적으로 해결하는 운영 패턴
