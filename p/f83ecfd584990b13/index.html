SOA-C03은 AWS 운영 실무를 검증하는 어소시에이트 시험으로, 모니터링·안정성·배포자동화·보안·네트워킹 5개 콘텐츠 도메인으로 출제 범위가 나뉜다.

#1문제 상황

AWS 자격증이 존재하지 않던 시절에는 개인의 경험과 포트폴리오만으로 클라우드 엔지니어 역량을 증명해야 했습니다. 그래서 기업들은 채용 기준이 모호했고, 신입 엔지니어들은 실제 업무에 필요한 범위가 무엇인지 알 수 없었습니다. SOA-C03(AWS Certified SysOps Administrator - Associate 2024년판)은 AWS 환경을 안정적으로 운영하는 데 필요한 실무 능력을 표준화하고 검증하기 위해 만들어졌습니다.

#2핵심 질문

AWS에서 실제로 시스템을 굴리는 엔지니어에게 가장 중요한 역량은 무엇이고, 그것을 어떤 범위에서 증명할 것인가?

#3동작 예시

SOA-C03 시험은 5개의 콘텐츠 도메인으로 출제 범위를 나눕니다. 예를 들어 "모니터링과 보고" 도메인은 CloudWatch로 지표를 수집하고 알람으로 이상을 감지하는 실무 능력을, "배포, 프로비저닝, 자동화" 도메인은 CloudFormation이나 Terraform으로 인프라를 코드로 정의하는 능력을 각각 검증합니다.

#4동작 과정

  1. 시험 범위 정의AWS가 운영 엔지니어에게 필요한 5개 도메인(모니터링·보고, 신뢰성·가용성, 배포·프로비저닝·자동화, 보안·규정 준수, 네트워킹·콘텐츠 전송)을 정의하고 각각의 비중을 설정합니다.
  2. 출제 비중 결정5개 도메인 중 모니터링·보고와 신뢰성·가용성이 각 26%로 가장 많고, 나머지는 16~20% 사이로 배분되어 실무에서의 중요도를 반영합니다.
  3. 시험 문제 출제각 도메인마다 구체적인 시나리오(예: RDS 데이터베이스 장애 대응, CloudFormation 템플릿 배포 오류 등)를 담은 문제들이 총 65문항으로 출제됩니다.

#5한 줄 요약

CloudOps 엔지니어의 책임 범위와 AWS Well-Architected Framework

CloudOps 엔지니어는 이미 만들어진 AWS 환경을 안정적으로 굴리는 역할이며, Well-Architected Framework의 여섯 기둥이 그 판단 기준을 제공한다.

#1문제 상황

과거 온프레미스 환경에서는 인프라 엔지니어, 애플리케이션 개발자, 운영 담당자가 명확히 분리되었습니다. 클라우드 환경에서는 한 명의 엔지니어가 여러 역할을 동시에 수행해야 합니다. 특히 CloudOps 엔지니어는 이미 배포된 AWS 환경을 일관되고 안정적으로 운영하는 역할인데, 이렇게 다양한 책임을 효율적으로 수행하려면 판단 기준이 필요합니다.

#2핵심 질문

AWS 환경이 이미 구축되었을 때, 그것을 잘 운영하고 있다는 것을 어떻게 판정할까?

#3동작 예시

AWS Well-Architected Framework는 6개 기둥(운영 우수성, 보안, 신뢰성, 성능 효율성, 비용 최적화, 지속 가능성)으로 이루어져 있습니다. CloudOps 엔지니어가 모니터링 대시보드를 설계할 때 "운영 우수성" 기둥의 "각 애플리케이션의 상태를 실시간으로 추적해야 한다"는 원칙을 따르고, 보안 그룹을 구성할 때 "보안" 기둥의 "최소 권한 원칙"을 따릅니다.

#4동작 과정

  1. Architecture Review에서 기준 설정신규 AWS 환경이 아니라 이미 운영 중인 환경을 대상으로, 6개 기둥 각각의 현재 상태를 점검하고 개선할 부분을 식별합니다.
  2. 각 기둥의 원칙 적용예를 들어 "성능 효율성" 기둥은 Auto Scaling으로 수요에 맞춘 리소스 조정을, "비용 최적화"는 미사용 리소스 정리와 예약 인스턴스 활용을 각각 의미합니다.
  3. 지속적인 개선모니터링 데이터와 실제 운영 경험을 토대로 정기적으로 환경을 검토하고 업그레이드합니다.

#5한 줄 요약

AWS 환경의 운영 품질을 6가지 관점(운영, 보안, 안정성, 성능, 비용, 지속성)에서 측정하고 개선하는 표준 프레임워크

초기 AWS 사용자들은 계정 생성 후 루트 사용자 자격 증명(Access Key와 Secret Key)으로 모든 작업을 했습니다. 이 방식은 자격 증명이 노출되면 AWS 계정 전체가 탈취되고, 누가 어떤 작업을 했는지 감시하기 어려우며, 권한을 세밀하게 제어할 수 없었습니다.

#2핵심 질문

사람마다, 애플리케이션마다 정확하게 필요한 권한만 줄 수 있고, 자격 증명이 노출되었을 때 피해를 최소화할 수 있는 방법이 있을까?

#3동작 예시

운영 팀 소속 Alice가 EC2 인스턴스만 관리하고 S3는 건드리지 않으려면, Alice를 IAM 사용자로 만들고 "EC2 읽기·시작·중지" 권한을 담은 정책을 할당합니다. Alice의 자격 증명이 노출되어도 S3에는 접근할 수 없습니다. 반면 람다 함수가 S3에서 파일을 읽고 RDS에 데이터를 쓰려면, 그 함수에 IAM 역할을 할당해서 필요한 2개 권한만 주고, 함수 내부에 자격 증명을 하드코딩하지 않습니다.

#4동작 과정

  1. 신원 단위별 자격 증명 발급사람에게는 IAM 사용자를, 같은 권한이 필요한 사람들끼리는 그룹으로 묶어 정책을 한 번에 할당하고, AWS 서비스나 외부 애플리케이션에게는 IAM 역할(Role)을 할당합니다.
  2. 임시 자격 증명 생성IAM 사용자가 AWS에 요청할 때마다 AWS가 유효 기간이 정해진 임시 자격 증명(Access Key와 Session Token)을 발급하고, 람다나 EC2 인스턴스 같은 서비스는 이 임시 자격 증명을 역할에서 자동으로 받습니다.
  3. 권한 적용요청이 들어오면 그 신원에 붙은 정책들을 확인하고 "EC2 시작"이면 허용, "S3 삭제"면 거부 같은 식으로 판정합니다.

IAM 정책 평가: 자격 증명 기반·리소스 기반 정책, 정책 조건

요청 허용 여부는 명시적 거부가 항상 이기고 허용이 하나도 없으면 거부되는 규칙 아래, 자격 증명에 붙은 정책과 리소스에 붙은 정책, 조건 키를 합쳐 판정한다.

#1문제 상황

초기의 간단한 권한 체계는 "이 사용자는 EC2를 쓸 수 있는가 없는가"라는 이진 판정만 했습니다. 그러나 실무에서는 더 복잡한 요구사항이 생겼습니다. 예를 들어 "개발 환경 EC2는 누구나 중지할 수 있지만, 프로덕션 EC2는 관리자만 중지할 수 있다", "특정 IP 범위에서만 접근 가능", "특정 태그가 붙은 리소스만 수정 가능" 같은 세밀한 제어가 필요했습니다.

#2핵심 질문

누가, 어떤 리소스에, 어떤 조건 하에서만 특정 작업을 할 수 있게 할 것인가?

#3동작 예시

EC2 인스턴스 하나(리소스)가 있을 때, 그 인스턴스에 붙은 정책(리소스 기반 정책)으로 "특정 IAM 사용자만 중지할 수 있다"고 명시할 수 있고, 동시에 그 사용자가 가진 정책(자격 증명 기반 정책)에서는 "IP 주소가 회사 네트워크 범위일 때만 EC2 접근 허용"이라고 명시할 수 있습니다. 두 정책을 모두 만족해야만 작업이 실행됩니다.

#4동작 과정

  1. 명시적 거부 확인먼저 사용자나 리소스에 붙은 모든 정책을 검토해서 명시적인 "거부(Deny)"가 하나라도 있는지 확인합니다. 거부가 있으면 즉시 요청을 거부합니다.
  2. 허용 정책 검토명시적 거부가 없으면, 자격 증명에 붙은 정책과 리소스에 붙은 정책을 모두 검토해서 "허용(Allow)"이 하나라도 있는지, 그리고 조건(IP 범위, 태그, 시간대 등)을 만족하는지 확인합니다.
  3. 결과 판정허용과 조건을 모두 만족하면 요청을 허용하고, 하나라도 거부되거나 명시적 허용이 없으면 거부합니다.

#5한 줄 요약

"명시적 거부가 항상 이기고, 명시적 허용이 없으면 거부된다"는 규칙 아래, 사용자의 정책과 리소스의 정책, 요청 조건을 합쳐서 최종 판정하는 평가 논리

#1문제 상황

AWS 계정을 만들 때 루트 사용자(이메일 주소와 암호로 로그인)가 자동으로 생성되며, 이 루트 사용자는 결제, 계정 삭제, 루트 액세스 키 생성 등 모든 권한을 가집니다. 초기에는 많은 조직이 루트 자격 증명을 공유했고, 암호가 약했으며, 다중 인증을 쓰지 않았습니다. 그 결과 계정 탈취와 무단 사용 사건이 빈번했습니다.

#2핵심 질문

모든 권한을 가진 루트 사용자의 탈취 위험을 최소화하고, 일상 운영 작업은 안전하게 수행할 수 있는 방법은 무엇인가?

#3동작 예시

루트 사용자를 보호하는 일반적인 패턴은 다음과 같습니다. 첫째, 루트 로그인 자격 증명을 금고처럼 보안 저장소에 보관하고 평상시에는 절대 쓰지 않습니다. 둘째, 일상 작업은 관리자 권한을 가진 IAM 사용자 계정으로 합니다. 셋째, 그 IAM 사용자들의 암호는 8글자 이상, 특수문자 포함 같은 정책으로 강제하고, MFA(다중 인증)를 반드시 켜서 암호만으로는 로그인되지 않도록 합니다.

#4동작 과정

  1. 루트 사용자 잠금루트 계정에 MFA를 설정하고 액세스 키를 삭제한 후, 로그인 자격 증명은 문서화하고 진짜 긴급 상황(예: 루트 로그인 필요한 작업)이 아닌 이상 사용하지 않습니다.
  2. 일상 작업용 IAM 사용자 사용엔지니어들은 각각 IAM 사용자 계정을 가지고, 필요한 최소 권한만 갖습니다. 이들 계정의 암호는 AWS Password Policy(최소 길이, 복잡도 요구)를 만족해야 하고, MFA를 반드시 켜야 합니다.
  3. 페더레이션 ID 활용조직이 Okta·Google Workspace 같은 중앙 ID 서비스를 쓰는 경우, IAM Identity Center를 사용해 이들 ID로 AWS 계정에 로그인하게 하면 암호를 AWS에 저장하지 않고도 접근 제어와 감시를 중앙에서 합니다.

#5한 줄 요약

모든 권한을 가진 루트 사용자는 평상시에 쓰지 않도록 사용 제한하고, 일상 작업은 제한된 권한의 IAM 사용자나 페더레이션 ID로 수행하되, 암호 정책과 MFA로 탈취 위험을 다층으로 방어하는 계정 보안 전략

AWS Organizations, SCP, Control Tower, Service Catalog로 다계정 통제

여러 AWS 계정을 조직으로 묶어 SCP 로 권한 상한을 걸고, Control Tower 로 표준 랜딩 존을, Service Catalog 로 승인된 리소스 템플릿만 쓰게 하는 거버넌스 체계다.

#1문제 상황

초기에 많은 조직은 AWS 계정을 하나만 썼고, 모든 팀·프로젝트의 자원이 섞여 있었습니다. 규모가 커지면서 보안 격리, 비용 추적, 권한 분리 같은 요구사항이 생겼습니다. 예를 들어 개발팀과 재무팀이 같은 계정을 쓰면 개발팀 멤버가 실수로 청구서를 삭제하거나 재무팀이 개발 자원에 접근할 수 있습니다. 여러 계정을 개별 관리하는 것도 어려웠기 때문에 중앙 거버넌스 도구가 필요했습니다.

#2핵심 질문

여러 AWS 계정을 조직 전체에서 일관된 정책으로 통제하고, 각 팀·프로젝트는 격리된 환경에서 일하게 하면서도 중앙에서 보안·규정을 강제할 수 있을까?

#3동작 예시

대형 조직의 구조는 보통 다음과 같습니다. 관리(관리용 계정)·개발·프로덕션·보안 등 용도별로 별개 AWS 계정을 만들고, 이들을 AWS Organizations로 묶습니다. 그 다음 SCP(Service Control Policy)로 모든 계정에 "EC2 인스턴스는 프로덕션 계정에서만 t3 타입만 허용"이라는 상한 권한을 정하고, 각 계정 내에서는 IAM 정책으로 더 세밀한 제어를 합니다. Control Tower는 표준 랜딩 존 구조를 자동으로 생성해서, 새 계정을 만들 때 로깅·감시·네트워킹 같은 기본 설정을 자동으로 적용합니다.

#4동작 과정

  1. AWS Organizations로 계정 구조화관리 계정 한 개와 멤버 계정들을 조직 단위로 그룹화합니다. 조직은 OU(Organization Unit, 조직 단위)로 나뉘어 있어서 개발팀 OU·보안팀 OU 같은 식으로 정책을 분별 적용할 수 있습니다.
  2. SCP로 권한 상한 설정Organizations 정책인 SCP를 각 OU나 계정에 붙여서 "이 계정들에서는 이 작업을 절대 할 수 없다"는 상한을 정합니다. 예를 들어 "개발팀 OU의 계정들에서는 EC2 종료(terminate)만 불가"라고 해서 실수로 프로덕션 자원을 삭제하는 것을 방지합니다.
  3. Control Tower와 Service Catalog로 표준화Control Tower는 새 계정이 생성될 때마다 로깅·VPC·보안 그룹 같은 기본 리소스를 자동으로 배치하고, Service Catalog는 사전 승인된 자원 템플릿(예: "회사 표준 웹 서버 구성")만 팀이 사용하게 해서 비표준 배포를 방지합니다.

→ 02-02 참조

#1문제 상황

AWS에서 누군가가 무언가를 했을 때, 어떤 권한으로 그것이 가능했는지 확인하려면 로그 파일 속의 텍스트로 된 기록만 남아 있었다. 이들을 일일이 찾아 분석해야 했으므로, 보안 문제가 발생하면 원인을 파악하는 데 오래 걸렸고, 현재 권한이 얼마나 과하게 주어졌는지는 알 수 없었다.

#2핵심 질문

AWS 계정에서 누가 언제 무엇을 호출했고, 누가 과도한 권한을 가지고 있으며, 특정 권한이 실제로 어떻게 판정되는가?

#3동작 예시

S3에 데이터를 삭제한 요청이 왔을 때, CloudTrail은 그 요청이 누구 계정에서 언제 왔는지를 기록하고, IAM Access Analyzer는 그 계정의 권한 정책이 누구에게 S3 삭제 권한을 주고 있는지 보여주며, 정책 시뮬레이터는 그 권한 정책이 실제로 해당 액션을 허가했는지를 검증한다.

#4동작 과정

  1. CloudTrail이 API 호출 기록누가(IAM 사용자), 언제(타임스탐프), 무엇을(API 액션), 어디서(소스 IP) 호출했는지를 구조화된 로그로 남긴다.
  2. IAM Access Analyzer가 권한 분석현재 권한 정책이 누구에게 어떤 권한을 노출하고 있는지, 특히 의도하지 않은 외부 계정이나 익명 사용자에게 열려 있는 권한이 없는지 찾아낸다.
  3. 정책 시뮬레이터가 판정 검증특정 사용자가 특정 액션을 실행했을 때, 자신의 권한 정책이 그것을 실제로 허가했는지를 시뮬레이션하여 답한다.

VPC, 서브넷, CIDR 설계와 VPC IPAM

VPC는 AWS 안에 내가 만드는 논리적 사설 네트워크이고, 이를 CIDR 주소 범위로 나눈 조각이 서브넷이며, IPAM은 이 IP 주소 범위를 조직 전체에서 계획·할당·추적해 주는 서비스다.

#1문제 상황

AWS 인스턴스들을 사용할 때 네트워크 구성은 AWS가 자동으로 해 주었다. 그런데 여러 팀이 여러 인스턴스를 운영하다 보니, IP 주소 범위가 겹쳐서 충돌이 일어났고, 어느 서브넷이 어디에 배치되었는지 전체 조직에서 관리하기 어려워졌으며, 인스턴스를 추가할 때마다 남은 IP 주소가 몇 개인지 수작업으로 계산해야 했다.

#2핵심 질문

AWS 내에서 여러 팀의 인스턴스들을 격리된 논리적 네트워크로 나누고, 조직 전체의 IP 주소 범위를 계획하고 추적하려면 어떻게 해야 하는가?

#3동작 예시

회사가 172.16.0.0/16(65536개 IP)이라는 주소 범위를 소유했을 때, VPC는 그 안의 172.16.0.0/16 범위 전체를 차용하는 논리적 네트워크 경계고, 서브넷은 그 안의 172.16.1.0/24(256개 IP), 172.16.2.0/24 같은 조각으로 나누는 것이며, VPC IPAM은 조직 전체의 IP 풀에서 어느 범위가 이미 할당되었고 어디가 남아 있는지를 자동으로 추적해 주는 서비스다.

#4동작 과정

  1. VPC 생성 시 CIDR 범위 정의조직이 사용할 IP 주소 범위(예: 10.0.0.0/8)를 VPC에 할당하면, AWS는 그 범위 내의 모든 통신만 처리한다.
  2. 서브넷으로 범위 분할가용 영역(물리적 데이터 센터)마다 또는 용도별로 VPC 내의 범위를 더 작은 CIDR 블록(예: 10.0.1.0/24, 10.0.2.0/24)으로 쪼개어 서브넷을 만들어 트래픽을 분산하고 격리한다.
  3. VPC IPAM이 조직 전체 범위 관리여러 AWS 계정과 VPC에 걸쳐 어느 IP 범위가 할당되고 유휴 중인지를 중앙에서 추적하여, 새 서브넷 생성 시 자동으로 겹치지 않은 범위를 추천하고 할당한다.

#5한 줄 요약

AWS 내에서 논리적 사설 네트워크(VPC)를 만들고 CIDR 블록으로 세분화하되, 조직 전체의 IP 주소 계획을 한곳에서 중앙 관리하여 주소 충돌을 방지하고 네트워크 확장을 수월하게 하는 것

라우팅과 게이트웨이

라우팅 테이블은 서브넷의 트래픽이 어디로 갈지 정하는 이정표이고, 인터넷 게이트웨이는 퍼블릭 인터넷 출입구, NAT 게이트웨이는 프라이빗 서브넷이 밖으로만 나가게 해 주는 통로, 탄력적 IP는 고정 공인 IP다.

→ 03-01 참조

#1문제 상황

VPC 안에 여러 서브넷이 있으면, 한 서브넷의 인스턴스가 다른 서브넷의 인스턴스 또는 인터넷으로 패킷을 보낼 때 어느 길로 가야 하는지 결정해야 한다. 기존에는 각 서브넷마다 수작업으로 규칙을 입력했고, 외부 인터넷으로 나가는 경로도 마찬가지였으며, 프라이빗 서브넷이 인터넷으로 나갈 수 있게 하려면 공인 IP를 매번 새로 구해야 했다.

#2핵심 질문

VPC 내의 서브넷 간 통신, 인터넷 출입, 그리고 프라이빗 인스턴스의 아웃바운드 인터넷 접속을 어떻게 효율적으로 라우팅하는가?

#3동작 예시

라우팅 테이블은 서브넷이 받은 패킷을 목적지 주소별로 분류하여 어디로 보낼지 정하는 규칙 목록(예: 10.0.0.0/8은 로컬 전달, 0.0.0.0/0은 인터넷 게이트웨이로 보냄)이고, 인터넷 게이트웨이는 그 패킷을 실제 인터넷으로 보내며, NAT 게이트웨이는 프라이빗 인스턴스의 프라이빗 IP를 게이트웨이의 공인 IP로 변환하여 응답이 돌아올 길을 보장한다.

#4동작 과정

  1. 라우팅 테이블 설정각 서브넷에 라우팅 테이블을 붙여서, "목적지가 10.0.0.0/8이면 로컬 네트워크로, 0.0.0.0/0(모든 다른 주소)이면 인터넷 게이트웨이로" 같은 규칙을 정의한다.
  2. 인터넷 게이트웨이와 NAT 게이트웨이 배치퍼블릭 서브넷은 인터넷 게이트웨이에 직접 연결하여 인스턴스가 공인 IP를 얻고 통신하게 하고, 프라이빗 서브넷은 NAT 게이트웨이(또는 NAT 인스턴스)를 거쳐서만 아웃바운드 인터넷 접속이 가능하게 한다.
  3. 탄력적 IP 할당NAT 게이트웨이와 인스턴스에 할당될 공인 IP 주소(탄력적 IP)를 미리 예약하여, 중단되더라도 같은 IP를 재사용할 수 있도록 한다.

#5한 줄 요약

라우팅 테이블로 패킷의 경로를 정의하고, 게이트웨이로 VPC 경계를 넘는 통신을 통제하되, 프라이빗 인스턴스도 안전하게 인터넷에 접속하도록 보장하는 것

보안 그룹과 네트워크 ACL

보안 그룹은 인스턴스 단위의 상태 저장(stateful) 방화벽이고, 네트워크 ACL은 서브넷 단위의 상태 비저장(stateless) 허용·거부 규칙이다.

#1문제 상황

VPC 내의 인스턴스들이 누구와 어떻게 통신할지는 라우팅으로 결정되지만, 누구의 트래픽을 실제로 받아들이고 누구의 트래픽을 거부할지는 별도로 제어해야 한다. 기존에는 운영 체제 수준의 방화벽만 있어서 각 인스턴스마다 규칙을 설정해야 했고, 인스턴스에 대한 수신 트래픽만 거부하면 응답이 막혔는데, 요청이 돌아오는 경로까지 별도로 허가해야 한다는 점이 복잡했다.

#2핵심 질문

인스턴스 단위와 서브넷 단위에서 인바운드·아웃바운드 트래픽을 각각 어떻게 제어하는가?

#3동작 예시

보안 그룹은 인스턴스에 붙는 상태 저장 방화벽(stateful firewall)으로, 인바운드 규칙에 "포트 443만 허가"라고 적으면 아웃바운드는 자동으로 그 응답 트래픽을 돌려보내고, 네트워크 ACL은 서브넷 전체에 붙는 상태 비저장 규칙(stateless rules)으로, 인바운드와 아웃바운드를 각각 명시적으로 허가하거나 거부해야 한다.

#4동작 과정

  1. 보안 그룹 규칙 정의인스턴스에 붙일 보안 그룹마다 "어느 프로토콜(TCP, UDP 등)의 어느 포트에서 어느 출발지 IP/보안 그룹의 트래픽을 받을지"를 규칙으로 나열한다.
  2. 네트워크 ACL 규칙 정의서브넷 전체에 붙일 ACL마다, 우선순위(1~32766)와 함께 "출발지/목적지 IP, 포트, 프로토콜"의 허가·거부 규칙을 순서대로 적용한다.
  3. 패킷 필터링 적용패킷이 서브넷에 들어오면 ACL에서 먼저 걸러지고, 그 다음 인스턴스에 도착하면 보안 그룹에서 다시 걸러진다.

#5한 줄 요약

보안 그룹으로 인스턴스 단위의 신청-응답 흐름을 자동 추적하는 상태 저장 방화벽을 제공하고, 네트워크 ACL로 서브넷 단위의 명시적 인/아웃 규칙을 통해 깊이 있는 방어를 제공하는 것

프라이빗 연결

인터넷을 거치지 않고 AWS 서비스나 다른 VPC와 통신하는 방법으로, 엔드포인트·PrivateLink는 서비스로의 사설 접근을, 피어링은 1:1 연결을, Transit Gateway는 다수 VPC의 허브형 연결을 담당한다.

→ 03-02 참조

#1문제 상황

프라이빗 서브넷의 인스턴스가 AWS의 S3, DynamoDB 같은 관리형 서비스에 접근하려면 인터넷 게이트웨이나 NAT 게이트웨이를 거쳐 퍼블릭 인터넷을 통해 서비스 엔드포인트에 도달했다. 이렇게 하면 트래픽이 인터넷을 거쳐 가므로 보안 위험이 있고 인터넷 비용도 들었으며, 여러 VPC나 온프레미스 네트워크와 연결할 때도 마찬가지로 인터넷을 거쳐야 했다.

#2핵심 질문

AWS 서비스와 다른 VPC, 온프레미스 네트워크와 인터넷을 거치지 않고 사설 네트워크로 연결하려면 어떻게 해야 하는가?

#3동작 예시

VPC 엔드포인트는 VPC 안에 만드는 진입점(gateway 또는 interface 타입)으로, 인스턴스가 이 엔드포인트로 트래픽을 보내면 AWS의 사설 네트워크를 통해 S3나 DynamoDB에 도달한다. AWS PrivateLink는 AWS 서비스나 파트너 서비스 제공자가 제공하는 수신 엔드포인트로, 이를 통해 VPC가 외부 서비스에 사설 연결을 갖는다. VPC 피어링은 두 VPC를 직접 연결하는 1:1 관계고, Transit Gateway는 여러 VPC와 온프레미스 네트워크를 허브처럼 한곳으로 모아 연결하는 중앙 라우터다.

#4동작 과정

  1. VPC 엔드포인트 또는 PrivateLink로 서비스 접근프라이빗 서브넷의 인스턴스가 보낸 트래픽이 엔드포인트에 도달하면, AWS의 관리형 네트워크를 통해 S3, DynamoDB, EC2 같은 서비스로 전달되며 인터넷을 거치지 않는다.
  2. VPC 피어링 또는 Transit Gateway로 네트워크 연결VPC 피어링은 두 VPC 간의 라우팅 규칙(피어링 연결)을 만들어서 일대일로 연결하고, Transit Gateway는 여러 VPC와 온프레미스 네트워크가 중앙 허브에 연결되는 스타형 토폴로지를 제공한다.
  3. 라우팅 테이블 설정각 VPC나 서브넷의 라우팅 테이블에서 대상 주소별로 엔드포인트, 피어링, 또는 Transit Gateway로 보내도록 규칙을 설정한다.

#5한 줄 요약

인터넷을 거치지 않고 AWS 사설 네트워크 내에서 AWS 서비스, 다른 VPC, 외부 서비스에 접근하는 여러 프라이빗 연결 방식을 제공하여 보안을 높이고 데이터 전송 비용을 절감하는 것

하이브리드 연결

Site-to-Site VPN은 온프레미스 네트워크 전체를 VPC와 암호화 터널로 잇는 방식이고, Client VPN은 개별 사용자 기기가 VPC에 안전하게 접속하게 해 주는 관리형 VPN이다.

→ 03-04 참조

#1문제 상황

조직이 온프레미스 데이터 센터와 AWS를 함께 사용할 때, 두 네트워크를 연결하려면 각 건물의 라우터 간에 안전한 통신 채널을 마련해야 한다. 기존에는 고비용의 전용선(dedicated line)을 임차했거나, 인터넷 연결만 사용했는데 후자는 보안이 취약했다. 또한 재택근무 직원이 회사 네트워크에 접속하려면 VPN 클라이언트를 설치하고 관리해야 했다.

#2핵심 질문

온프레미스 네트워크 전체를 VPC와 안전하게 연결하고, 개별 사용자도 어디서나 안전하게 회사 네트워크에 접근하려면 어떻게 해야 하는가?

#3동작 예시

Site-to-Site VPN은 온프레미스 라우터(고객 게이트웨이)와 AWS VPC(VPN 게이트웨이) 간에 IPSec 암호화 터널을 만들어서, 온프레미스의 172.16.0.0/16 대역과 VPC의 10.0.0.0/16 대역을 직접 라우팅하는 방식이고, Client VPN은 사용자 개인 기기에서 VPC에 안전하게 접근하기 위해 AWS가 제공하는 관리형 VPN 서비스로, OpenVPN 프로토콜을 사용하고 사용자 인증을 IAM이나 SAML로 통제한다.

#4동작 과정

  1. Site-to-Site VPN 터널 설정온프레미스 라우터에 VPN 게이트웨이의 공인 IP, 암호화 키, 라우팅 정책을 설정하고, VPC에는 역으로 온프레미스 라우터의 정보를 입력하여 양쪽이 대칭 암호화 터널을 구성한다.
  2. Client VPN 엔드포인트 구성AWS Console에서 Client VPN 엔드포인트를 만들고, VPC 내 서브넷과 보안 그룹 규칙을 연결하며, 사용자 인증 방식(IAM, Active Directory, 인증서 등)을 설정한다.
  3. 클라이언트 연결원격 사용자가 OpenVPN 클라이언트를 실행하고 Client VPN 엔드포인트에 접속하면, 인증을 거친 뒤 VPC 내의 리소스에 직접 접근할 수 있다.

#5한 줄 요약

Site-to-Site VPN으로 온프레미스 네트워크 전체를 VPC와 암호화 터널로 연결하고, Client VPN으로 개별 사용자가 안전하게 회사 네트워크에 접근하는 두 가지 하이브리드 연결 방식을 제공하는 것

EC2 인스턴스

EC2는 AWS가 빌려주는 가상 서버로, 용도별 인스턴스 유형과 온디맨드·예약·스팟 같은 구매 옵션을 고르고 시작·중지·종료의 수명 주기를 거치며, 인스턴스 안에서 자기 정보를 조회하는 메타데이터 서비스를 제공한다.

#1문제 상황

AWS에서 가상 서버(EC2 인스턴스)를 사용할 때, 어느 정도 성능의 서버를 사려고 선택해야 하고, 언제 중단했다가 언제 다시 시작할지 관리해야 하며, 인스턴스 자신이 어느 VPC에 속해 있는지, 어느 IAM 역할을 사용하는지 같은 정보를 알아야 했다. 그런데 애플리케이션이 커지면서 여러 성능의 인스턴스가 필요했고, 비용을 줄이려면 구매 방식을 선택해야 했으며, 설정 정보를 일일이 기억하거나 별도로 저장해야 했다.

#2핵심 질문

EC2 인스턴스의 성능을 선택하고, 비용 효율적인 구매 방식을 결정하며, 인스턴스의 상태와 자신의 설정 정보를 어떻게 관리하는가?

#3동작 예시

EC2 인스턴스는 용도별 인스턴스 유형(t3는 가변 성능 범용, c6은 컴퓨팅 최적화, r6은 메모리 최적화 등)으로 나뉘고, 구매 옵션으로는 온디맨드(시간당 정가 지불, 언제든 중단 가능), 예약 인스턴스(1년 또는 3년을 미리 약정해 30~50% 할인), 스팟 인스턴스(여유 용량을 경매로 80% 이상 저렴하게 구입하되 언제든 회수될 수 있음)가 있으며, 인스턴스 메타데이터 서비스(IMDSv2)는 인스턴스 안의 애플리케이션이 자신의 ID, 붙인 IAM 역할, VPC 정보를 http 호출로 조회할 수 있게 해 준다.

#4동작 과정

  1. 인스턴스 유형과 구매 옵션 결정작업 특성에 맞는 유형(CPU, 메모리, 스토리지, 네트워크 성능 조합)을 선택하고, 사용 패턴에 맞춰 온디맨드, 예약, 스팟 중 하나 이상을 조합해서 비용 대비 성능을 최적화한다.
  2. 인스턴스 수명 주기 관리인스턴스를 시작(running 상태)하고, 필요하면 중지(stopped 상태, 비용 절감)했다가 재시작하거나, 완전히 종료(terminated)하여 제거한다.
  3. 인스턴스 메타데이터 조회인스턴스 내의 애플리케이션이 IMDSv2 엔드포인트(http://169.254.169.254)에 토큰을 요청한 뒤 메타데이터(자신의 인스턴스 ID, 가용 영역, 붙인 역할의 임시 보안 자격증명 등)를 조회하여 AWS API 호출에 사용한다.

#5한 줄 요약

용도별 인스턴스 유형과 비용 효율적인 구매 옵션으로 가상 서버를 제공하고, 인스턴스 메타데이터 서비스로 인스턴스가 자신의 정보와 권한을 동적으로 조회하게 함으로써 설정 관리의 복잡도를 낮추는 것

AMI, EC2 Image Builder, 컨테이너 이미지와 Amazon ECR

AMI는 EC2를 찍어내는 서버 템플릿이고 EC2 Image Builder는 그 템플릿을 자동으로 만들어 갱신해주며, 컨테이너 쪽에서 같은 역할을 하는 이미지를 저장하는 곳이 Amazon ECR이다.

#1문제 상황

EC2 인스턴스를 하나 띄울 때마다 운영체제를 설치하고, 필요한 소프트웨어와 설정을 손으로 입력해야 합니다. 같은 구성의 인스턴스가 필요할 때마다 이 과정을 반복하고, 시간이 지나면서 언제 어디서 뭐가 설치되었는지 기록하기 어려워집니다. 컨테이너도 마찬가지로 매번 도커 이미지를 직접 만들어야 하고, 이미지를 저장하고 배포하는 과정이 복잡합니다.

#2핵심 질문

서버 구성을 한 번만 정의해두고 계속 재사용할 수 있을까?

#3동작 예시

AMI(Amazon Machine Image)는 운영체제, 소프트웨어, 설정을 모두 담은 완성된 서버 템플릿입니다. EC2를 띄울 때 이 템플릿으로 찍어내면 동일한 환경의 인스턴스가 몇 개든 즉시 생깁니다. EC2 Image Builder는 이 AMI를 자동으로 만들고 최신 보안 패치를 적용해 갱신합니다. 컨테이너 쪽의 동일한 개념이 컨테이너 이미지이고, Amazon ECR(Elastic Container Registry)은 이 이미지를 저장하는 원격 저장소 역할을 합니다.

#4동작 과정

  1. 템플릿 정의EC2 Image Builder에서 어떤 운영체제, 어떤 소프트웨어를 설치할지 코드로 정의합니다.
  2. 자동 빌드 및 테스트정의된 규칙에 따라 AMI를 자동으로 만들고, 필요하면 여러 지역에 복사합니다. 컨테이너 이미지는 빌드 완료 후 ECR에 자동으로 푸시됩니다.
  3. 재사용 및 갱신이후 EC2 인스턴스는 만들어진 AMI로부터 몇 개든 실행할 수 있고, 보안 업데이트가 필요하면 Image Builder가 자동으로 새 버전의 AMI를 만듭니다.

Amazon EBS 볼륨 유형, 스냅샷, 인스턴스 스토어

EBS는 EC2에 붙이는 네트워크 디스크로 성능별 볼륨 유형과 백업용 스냅샷을 제공하고, 인스턴스 스토어는 인스턴스에 직접 붙어 빠르지만 중지하면 사라지는 임시 디스크다.

#1문제 상황

EC2 인스턴스가 데이터를 저장하려면 디스크가 필요합니다. 인스턴스에 직접 붙은 로컬 디스크는 빠르지만, 인스턴스가 중지되거나 재부팅되면 데이터가 모두 사라집니다. 인스턴스 크기를 늘리거나 다른 인스턴스로 옮길 때도 데이터를 옮길 방법이 없습니다. 또한 장애가 발생하면 데이터 손실을 막을 방법이 전혀 없습니다.

#2핵심 질문

인스턴스가 중지되거나 장애가 나도 데이터를 지속적으로 유지할 수 있을까?

#3동작 예시

EBS(Elastic Block Store)는 인스턴스에 네트워크로 붙는 외장 디스크입니다. 인스턴스가 중지되어도 EBS 볼륨은 살아있고, 다른 인스턴스에 다시 붙일 수 있습니다. 성능이 필요하면 높은 IOPS(초당 입출력 횟수)를 가진 볼륨 유형을 선택하고, 비용을 낮추려면 낮은 성능의 유형을 선택합니다. 스냅샷은 특정 시점의 EBS 볼륨 상태를 영구 저장하는 백업이라 재해 복구 시 그 시점으로 되돌릴 수 있습니다. 반면 인스턴스 스토어는 인스턴스에 직접 붙은 고속 임시 디스크로, 중지하면 사라지지만 아주 빠른 임시 작업용으로만 씁니다.

#4동작 과정

  1. 볼륨 선택 및 연결필요한 성능(범용/프로비저닝/고성능 중 선택)에 맞춰 EBS 볼륨을 만들고 인스턴스에 붙입니다.
  2. 데이터 저장 및 백업인스턴스는 EBS에 데이터를 저장하고, 정기적으로 스냅샷으로 백업하여 저장합니다.
  3. 복구 및 이동장애 시 스냅샷으로부터 새 볼륨을 만들어 복구하거나, 다른 인스턴스에 기존 EBS 볼륨을 재연결할 수 있습니다.

#5한 줄 요약

데이터를 인스턴스 생명주기와 분리해 네트워크 디스크로 독립적으로 관리하고, 스냅샷 백업으로 지속성을 보장하며, 필요에 따라 인스턴스 간 자유롭게 이동시키는 것

Amazon S3 버킷, 스토리지 클래스, 수명 주기 정책

S3는 파일을 객체 단위로 버킷에 담는 무제한 저장소로, 접근 빈도에 맞춘 스토리지 클래스와 오래된 객체를 자동으로 옮기거나 삭제하는 수명 주기 정책으로 비용을 조절한다.

#1문제 상황

파일을 한 곳에 저장하고 필요할 때 언제든 꺼내야 한다면, 서버에 큰 디스크를 달아야 합니다. 파일이 계속 늘어나면 서버를 교체해야 하고, 여러 지역에서 파일을 받아야 한다면 각 지역마다 복사본을 만들어야 합니다. 오래된 파일이 있는데도 비용을 계속 내야 합니다.

#2핵심 질문

제한 없이 파일을 저장하되, 자주 쓰는 파일과 거의 안 쓰는 파일에 따라 비용을 다르게 낼 수는 없을까?

#3동작 예시

S3(Simple Storage Service)는 파일을 객체 단위로 저장하는 무제한 저장소입니다. 보통 S3에 저장하면 자주 접근하는 파일은 표준 클래스(Standard)로 놔두고, 한 달에 한두 번만 접근하는 파일은 저가 저장소(Standard-IA)로 옮기고, 거의 접근 안 하는 아카이브 파일은 빙하 저장소(Glacier, Deep Archive)로 옮깁니다. 수명 주기 정책(Lifecycle Policy)을 설정하면 이 이동이 자동으로 일어나고, 더 이상 필요 없는 파일도 자동으로 삭제됩니다.

#4동작 과정

  1. 파일 업로드파일을 버킷에 객체로 저장할 때 스토리지 클래스를 결정합니다.
  2. 자동 분류 및 이동수명 주기 정책에 따라 일정 기간 후 접근이 적은 파일은 자동으로 저가 클래스로 옮겨집니다.
  3. 비용 절감접근 빈도가 낮은 파일은 낮은 가격으로 저장되고, 불필요한 파일은 자동 삭제되어 저장 비용이 최소화됩니다.

#5한 줄 요약

파일의 접근 빈도에 따라 저장 위치와 비용을 자동으로 조절해, 무제한 저장 용량과 최적화된 비용을 동시에 달성하는 것

여러 서버가 동시에 같은 파일을 읽고 쓰는 공유 파일 시스템으로, 리눅스용 EFS와 Windows·고성능용 FSx가 있고 Storage Gateway는 온프레미스와 AWS 스토리지를 이어준다.

#1문제 상황

여러 서버가 동시에 같은 파일을 읽고 쓸 때, 각 서버가 파일의 복사본을 갖는 방식은 동기화가 깨지고 충돌이 발생합니다. 서버마다 EBS 볼륨을 따로 달면 각각의 데이터가 고립됩니다. 온프레미스 서버와 AWS 클라우드의 파일을 함께 써야 하면 더 복잡해집니다.

#2핵심 질문

여러 서버와 온프레미스가 동시에 같은 파일을 공유하려면?

#3동작 예시

EFS(Elastic File System)는 리눅스 기반 여러 EC2 인스턴스가 동시에 접근할 수 있는 공유 네트워크 파일 시스템입니다. FSx는 Windows 파일 공유나 고성능 병렬 처리 용도로 만들어진 관리형 파일 시스템입니다. Storage Gateway는 온프레미스의 애플리케이션이 로컬 디스크인 줄 알고 읽고 쓰게 한 뒤, 백그라운드에서 AWS S3나 EBS로 자동 동기화하는 중간 다리 역할을 합니다.

#4동작 과정

  1. 파일 시스템 선택Linux 환경이면 EFS, Windows 또는 고성능 필요하면 FSx, 하이브리드 환경이면 Storage Gateway를 선택합니다.
  2. 마운트 및 접근각 서버가 파일 시스템을 마운트해 로컬 디렉터리인 것처럼 읽고 쓸 수 있습니다.
  3. 자동 동기화 및 백업파일 변경사항이 자동으로 모든 접근 지점에 반영되고, 필요하면 자동 백업됩니다.

#5한 줄 요약

여러 서버와 온프레미스 환경 간 파일 접근을 중앙 집중식으로 관리해, 데이터 일관성을 유지하면서 분산 환경에서 안전한 파일 공유를 가능하게 하는 것

AWS Lambda와 서버리스 실행 모델

Lambda는 서버를 직접 띄우지 않고 이벤트가 올 때만 코드를 실행하고 실행한 시간만큼만 과금하는 서버리스 컴퓨팅 서비스다.

#1문제 상황

EC2 인스턴스를 24시간 띄우면, 요청이 없을 때도 전기료를 냅니다. 간단한 작업 하나 처리하려고 서버 전체를 관리해야 합니다. 요청이 갑자기 몰려오면 인스턴스를 빠르게 늘려야 하는데, 미리 예측하기 어렵고 준비 시간이 걸립니다.

#2핵심 질문

코드 실행 시간만큼만 비용을 내고, 요청에 따라 자동으로 인스턴스가 증감될 수 있을까?

#3동작 예시

Lambda는 코드만 업로드하면 이벤트가 오는 순간만 실행하고, 실행을 멈추면 비용도 멈춥니다. 요청이 10개 오면 10개 동시에 처리하고, 요청이 0개면 아무 비용도 없습니다. 서버 관리, 운영체제 패치, 스케일링 판단을 모두 AWS가 대신합니다. API Gateway가 HTTP 요청을 받으면 Lambda 함수를 트리거하거나, S3에 파일이 업로드되면 Lambda가 자동 실행됩니다.

#4동작 과정

  1. 코드 작성 및 업로드처리 로직을 함수로 작성해 Lambda에 업로드하고, 어떤 이벤트에 반응할지 설정합니다.
  2. 이벤트 기반 자동 실행정의된 이벤트(HTTP 요청, 파일 업로드, 일정한 시각 등)가 발생하면 Lambda 함수가 자동으로 실행됩니다.
  3. 결과 반환 및 과금함수가 처리를 완료하고 결과를 반환하며, 실행 시간에 기반해 과금됩니다.

#5한 줄 요약

서버 관리 없이 코드와 이벤트만 정의하고, 자동 스케일링과 사용량 기반 과금으로 효율성을 극대화하는 컴퓨팅 모델

컨테이너 오케스트레이션: Amazon ECS와 Amazon EKS

수많은 컨테이너를 어느 서버에 몇 개씩 띄우고 죽으면 되살릴지 자동으로 관리해주는 서비스로, AWS 자체 방식이 ECS, 쿠버네티스 표준 방식이 EKS다.

→ 04-02 참조

#1문제 상황

여러 컨테이너를 여러 서버에 분산해 실행해야 한다면, 어느 서버에 몇 개씩 띄울지 수동으로 결정해야 합니다. 컨테이너가 죽으면 손으로 다시 띄워야 하고, 서버 자원이 부족하면 새 서버를 추가해야 합니다. 서비스를 업데이트하려면 오래된 컨테이너를 내리고 새 버전을 띄우는 과정을 조율해야 합니다.

#2핵심 질문

수많은 컨테이너를 어느 서버에 몇 개씩 띄우고, 죽으면 되살리고, 자원을 최적화하는 일을 자동으로 관리할 수 있을까?

#3동작 예시

ECS(Elastic Container Service)는 AWS 자체 컨테이너 오케스트레이션 서비스로, 어떤 이미지를 몇 개 인스턴스에서 실행할지 선언하면 이를 자동으로 배치하고 관리합니다. EKS(Elastic Kubernetes Service)는 쿠버네티스라는 업계 표준 오케스트레이션 프레임워크를 AWS가 관리형으로 제공하는 것입니다. 둘 다 컨테이너 배치, 자동 재시작, 부하에 따른 스케일링을 자동으로 처리합니다.

#4동작 과정

  1. 작업 정의 및 서비스 등록실행할 컨테이너 이미지, 필요 자원, 실행 개수를 ECS 또는 EKS에 선언합니다.
  2. 자동 배치 및 모니터링클러스터 내 사용 가능한 인스턴스를 자동으로 찾아 컨테이너를 배치하고, 지속적으로 상태를 모니터링합니다.
  3. 자동 복구 및 스케일링컨테이너가 실패하면 자동으로 재시작하고, CPU나 메모리 사용량에 따라 실행 개수를 자동으로 조정합니다.

#5한 줄 요약

선언된 컨테이너 상태를 자동으로 달성하고 유지하며, 자원 효율성을 극대화하고 인스턴스 장애에 자동 복구하는 클러스터 관리 자동화

관리형 데이터베이스: Amazon RDS, Aurora, DynamoDB, ElastiCache

AWS가 설치·백업·패치를 대신 해주는 데이터베이스로, 관계형 RDS와 그 고성능판 Aurora, 키-값 NoSQL DynamoDB, 메모리 캐시 ElastiCache가 있다.

#1문제 상황

데이터베이스를 직접 운영하면 설치, 업그레이드, 보안 패치, 백업을 모두 손으로 처리해야 합니다. 용량이 부족해지면 더 큰 서버로 마이그레이션해야 하고, 장애가 나면 복구 절차를 수동으로 따릅니다. 데이터베이스 튜닝으로 성능을 높이려면 전문 지식이 필요합니다.

#2핵심 질문

데이터베이스 운영의 번거로움을 없애고, 안정성과 성능만 보장받을 수 없을까?

#3동작 예시

RDS(Relational Database Service)는 MySQL, PostgreSQL, Oracle, SQL Server 같은 관계형 데이터베이스를 AWS가 관리하는 서비스로, 자동 백업, 자동 패치, 읽기 복제본 자동 생성이 포함됩니다. Aurora는 RDS의 고성능 버전으로 더 빠르고 자동 스케일링을 지원합니다. DynamoDB는 키-값 기반 NoSQL로 테이블의 처리량을 선언하면 AWS가 자동 분산 처리를 담당합니다. ElastiCache는 Redis나 Memcached 같은 메모리 캐시 서비스로, 자주 요청되는 데이터를 빠르게 제공합니다.

#4동작 과정

  1. 데이터베이스 생성원하는 데이터베이스 엔진(RDS/Aurora/DynamoDB 등)을 선택해 만들고, 백업 및 자동 페일오버 옵션을 설정합니다.
  2. 자동 운영AWS가 일일 자동 백업, 보안 패치, 소프트웨어 업그레이드를 수행하고, 고가용성을 위해 다중 가용 영역에 복제합니다.
  3. 성능 최적화 및 확장필요하면 읽기 복제본을 추가하거나 인스턴스 크기를 늘려 성능을 향상하고, DynamoDB나 Aurora는 자동으로 확장됩니다.

#5한 줄 요약

데이터베이스의 설치, 유지보수, 백업, 고가용성 설정을 AWS가 전담해, 애플리케이션은 데이터 접근과 비즈니스 로직에만 집중하게 하는 것

CloudWatch 지표, 네임스페이스, 통계와 사용자 지정 지표

AWS 리소스가 내보내는 시간별 수치를 네임스페이스와 차원으로 구분해 모으고 평균·합계 같은 통계로 보는 기본 단위이며, 직접 만든 값도 사용자 지정 지표로 올릴 수 있다.

#1문제 상황

AWS 리소스가 실행되고 있지만, 각 리소스가 얼마나 잘 작동하고 있는지 파악할 방법이 없다. CPU가 얼마나 사용되고 있는지, 네트워크 트래픽은 얼마나 되는지, 에러는 몇 개나 발생했는지 직접 확인해야 한다면 시간이 매우 오래 걸린다.

#2핵심 질문

리소스의 상태를 시간별로 측정하고 그 데이터를 한 곳에 모아서 볼 수 있는 방법은 없을까?

#3동작 예시

EC2 인스턴스에서 1분마다 CPU 사용률, 네트워크 송수신량, 디스크 활동 같은 수치를 자동으로 측정한다. 이 수치들을 시간대별로 기록하고 저장한 후, 필요할 때 평균값, 최댓값, 합계 같은 통계로 변환해서 보여주는 것이 CloudWatch 지표의 핵심이다.

#4동작 과정

  1. 자동 측정AWS 리소스가 내보내는 기본 지표(CPU, 네트워크, 상태 확인 등)를 자동으로 수집한다.
  2. 네임스페이스와 차원으로 구분각 지표는 리소스 타입별로 네임스페이스(예: AWS/EC2)로 묶이고, 특정 인스턴스나 로드 밸런서를 구분하는 차원(예: InstanceId, LoadBalancerName)이 붙는다.
  3. 통계 계산 및 저장수집한 데이터에서 평균, 최댓값, 최솟값, 합계 같은 통계를 계산하고 시간별로 저장하며, 필요시 직접 만든 값(사용자 지정 지표)도 올려서 함께 관리한다.

CloudWatch 에이전트로 EC2, ECS, EKS 지표와 로그 수집

운영체제와 컨테이너 안쪽의 메모리·디스크·로그처럼 기본 지표에 없는 값을 에이전트를 설치해 CloudWatch로 보내는 방법이다.

#1문제 상황

CloudWatch 기본 지표는 EC2의 CPU나 네트워크처럼 하이퍼바이저가 읽을 수 있는 값만 제공한다. 운영체제 안에서 실제로 얼마나 메모리를 사용하고 있는지, 디스크의 여유 공간이 얼마나 남았는지, 애플리케이션 로그가 어떻게 흐르고 있는지는 기본 지표에 나타나지 않는다.

#2핵심 질문

EC2, ECS, EKS 인스턴스 안쪽의 메모리, 디스크, 로그 같은 값들을 CloudWatch로 보낼 수 있을까?

#3동작 예시

EC2 인스턴스에 에이전트 소프트웨어를 설치한다. 이 에이전트는 운영체제 커널에 접근해서 메모리 사용률, 디스크 여유 공간, 프로세스별 리소스 사용량 같은 세부 정보를 주기적으로 읽는다. 수집한 데이터를 CloudWatch로 발송하면 CloudWatch 지표로 변환되어 저장되고 시각화된다.

#4동작 과정

#1문제 상황

CloudWatch는 AWS 네이티브 지표와 로그에 강하지만, 마이크로서비스 아키텍처에서는 부족하다. 각 서비스가 내보내는 세부 지표를 시계열 데이터베이스에 저장하고 싶지만 Prometheus 같은 오픈소스를 직접 운영하는 것은 복잡하다. 또한 요청이 여러 서비스를 거칠 때 각 구간의 지연을 파악하려면 분산 추적이 필요한데, CloudWatch 단독으로는 불가능하다.

#2핵심 질문

오픈소스 기반의 고급 지표 저장, 시각화, 분산 추적을 AWS에서 관리형으로 제공받을 수 있을까?

#3동작 예시

마이크로서비스 A가 요청을 받으면 서비스 B를 호출하고, B는 데이터베이스를 조회한 뒤 C를 호출한다. 각 서비스는 자신의 응답 시간, 에러율, 처리량 같은 지표를 Prometheus 형식으로 노출하고, 이를 AWS Managed Prometheus가 수집해서 저장한다. Managed Grafana의 대시보드에서는 이 지표들을 실시간 그래프로 표시한다. AWS X-Ray를 사용하면 요청이 A → B → DB → C를 거치는 전체 경로와 각 구간의 소요 시간을 시각화할 수 있다.

#4동작 과정

  1. 지표 수집 및 저장각 마이크로서비스가 Prometheus 형식(예: request_duration_ms)으로 지표를 노출하고, AWS Managed Service for Prometheus가 주기적으로 수집해서 저장한다. 직접 서버를 운영할 필요 없이 AWS가 확장성과 고가용성을 보장한다.
  2. 시각화 및 모니터링Managed Grafana 대시보드에서 Prometheus 데이터를 쿼리해서 시계열 그래프, 히트맵, 게이지로 표시하고, 경보 규칙을 설정한다.

#2핵심 질문

#3동작 예시

#4동작 과정

#1문제 상황

AWS의 다양한 서비스들(EC2, RDS, S3, Lambda 등)은 각각 이벤트를 발생시키지만, 이 이벤트들을 한 곳에서 모니터링하거나 조건에 따라 다른 서비스로 전달하기 어려웠습니다. 각 서비스마다 별도로 모니터링 규칙을 설정해야 했고, 이벤트에 따른 자동화된 반응도 제한적이었습니다.

#2핵심 질문

AWS 전체에서 발생하는 모든 이벤트를 한 곳에서 받아서 조건에 맞는 것만 원하는 대상으로 자동 라우팅할 수 있을까요?

#3동작 예시

EventBridge의 버스(이벤트 버스)는 중앙 수집소 역할을 합니다. EC2 인스턴스가 시작되면 이벤트가 버스로 들어오고, 사용자가 정의한 규칙("source가 ec2이고 detail-type이 'EC2 Instance State-change Notification'일 때")이 그 이벤트와 일치하면, 지정된 대상(SNS, Lambda, SQS, CloudWatch Logs 등)으로 바로 전달됩니다.

#4동작 과정

  1. 이벤트 수집AWS 서비스가 발생시킨 이벤트가 EventBridge 버스에 도착합니다.
  2. 규칙 매칭정의된 규칙 패턴(JSON으로 작성된 조건)과 이벤트가 일치하는지 확인합니다.
  3. 대상으로 전달규칙을 만족한 이벤트가 설정된 대상 서비스로 전달되거나, 지정된 시간에 실행되도록 스케줄된 이벤트가 트리거됩니다.

AWS Systems Manager 운영 기능: Session Manager, Patch Manager, State Manager, Parameter Store

Systems Manager는 SSH 키 없이 접속(Session Manager), 패치 적용(Patch Manager), 원하는 상태 유지(State Manager), 설정·비밀 값 보관(Parameter Store)을 한데 묶은 인스턴스 운영 도구 모음이다.

#1문제 상황

EC2 인스턴스를 운영할 때 개발자들은 SSH 키를 보관·관리해야 했고, 키가 노출되면 보안 위험이 발생했습니다. 또한 운영 체제 패치를 일일이 수동으로 적용해야 하고, 인스턴스 설정 변경 사항을 일일이 확인해야 했으며, 환경 변수나 암호는 각 인스턴스나 소스 코드에 흩어져 보관되어 관리가 어려웠습니다.

#2핵심 질문

SSH 키 없이 안전하게 인스턴스에 접근하고, 패치·설정·비밀값들을 중앙에서 일괄 관리할 수 있을까요?

#3동작 예시

Systems Manager는 4가지 운영 기능을 하나의 대시보드에서 제공합니다. Session Manager는 IAM 권한만으로 인스턴스에 접속 셸을 열고(SSH 키 불필요), Patch Manager는 패치 정책을 정의하면 여러 인스턴스에 자동으로 적용하며, State Manager는 설정 문서로 원하는 상태를 정의하고 자동으로 유지하고, Parameter Store는 환경 변수와 민감한 설정값을 중앙에 보관합니다.

#4동작 과정

  1. Session Manager로 접근IAM 역할이 있는 사용자는 AWS 콘솔이나 CLI에서 직접 인스턴스 셸을 열고, 모든 세션은 로깅되어 감시됩니다.
  2. Patch Manager·State Manager로 자동화패치 기준선(패치 적용 일정·대상)을 설정하거나 설정 문서(Configuration Document)로 원하는 상태를 정의하면 스케줄에 따라 자동으로 실행되고 준수 상태를 추적합니다.
  3. Parameter Store로 설정 통합데이터베이스 암호, API 키, 설정 문자열을 Parameter Store에 보관하고, 애플리케이션과 스크립트에서 필요할 때 API로 가져갑니다.

#5한 줄 요약

Systems Manager인스턴스 접근, 패치 적용, 상태 유지, 설정값 관리를 한 곳에서 일괄 처리하여 SSH 키 관리 부담을 없애고 운영 작업을 자동화하는 통합 인스턴스 운영 서비스

Automation 런북은 여러 단계(스텝)를 JSON으로 미리 정의한 것입니다. 각 단계는 AWS API 호출, Lambda 함수 실행, 대기, 조건 분기 같은 작업을 포함할 수 있으며, 런북을 실행하면 정의된 순서대로 자동으로 진행됩니다. Run Command는 여러 대상 인스턴스를 지정하면 Systems Manager가 그 인스턴스들에 에이전트를 통해 명령어를 동시에 전달하고, 각 인스턴스의 실행 결과를 중앙에서 모니터링합니다.

#4동작 과정

  1. 런북 정의YAML이나 JSON으로 자동화 문서를 작성하여, 각 단계와 그 사이의 조건·대기·에러 처리를 명시합니다.
  2. 런북 실행콘솔이나 API에서 런북을 선택하고 실행하면, Systems Manager가 정의된 순서대로 각 단계를 실행하고 결과를 기록합니다.
  3. Run Command 병행런북 내 단계에서 Run Command로 여러 인스턴스에 명령어를 동시 전달하면, 각 인스턴스의 출력과 종료 코드를 중앙에서 수집합니다.

#1문제 상황

운영자는 CloudWatch 경보를 보고 직접 판단하여 EC2를 재시작하거나 데이터베이스 연결을 초기화하는 작업을 수동으로 수행했습니다. 이 과정에서 지연이 발생하고, 반복되는 문제도 매번 사람이 개입해야 했습니다. 또한 야간이나 휴일에 긴급 상황이 발생해도 즉시 대응하기 어려웠습니다.

#2핵심 질문

#3동작 예시

자동 교정 파이프라인은 이벤트가 발생했을 때 Lambda 함수에서 먼저 문제 상황을 파악하는 진단 코드를 실행하고, Step Functions 워크플로로 그 결과에 따라 여러 교정 단계를 순서대로 실행합니다. 예를 들어 "데이터베이스 연결 타임아웃" 경보가 오면, Lambda가 현재 연결 풀 상태를 확인하고, 교정이 필요하면 Step Functions가 데이터베이스 재시작과 애플리케이션 풀 리셋을 순서대로 트리거하며, SQS 큐는 실패한 요청을 임시 보관했다가 복구 후 재처리합니다.

#4동작 과정

  1. 이벤트 감지 및 진단EventBridge나 CloudWatch 경보가 Lambda 함수를 트리거하면, 함수가 현재 리소스 상태(로그, 메트릭, API 응답)를 수집하고 문제 원인을 분류합니다.
  2. Step Functions로 교정 실행진단 결과에 따라 Step Functions 워크플로가 복수 단계(서버 재시작, 캐시 초기화, 로드 밸런서 상태 변경 등)를 병렬이나 순차로 실행하고, 각 단계의 성공·실패 여부를 추적합니다.
  3. SQS를 통한 요청 보관 및 재처리교정 중에 들어온 요청들은 SQS 큐에 임시 보관되었다가, 시스템이 정상화되면 다시 처리되거나 클라이언트에 실패 알림을 보냅니다.

CloudFormation 템플릿 구조와 내장 함수

Parameters·Mappings·Conditions·Resources·Outputs 등 섹션으로 인프라를 선언하고 Ref·Fn::GetAtt·Fn::Sub 같은 내장 함수로 값을 연결하는 JSON/YAML 템플릿 작성법.

#1문제 상황

인프라를 구성할 때 AWS 콘솔에서 수동으로 EC2, RDS, VPC를 하나씩 만들었습니다. 같은 구성을 다른 환경에 만들려면 모든 단계를 반복해야 했고, 설정 실수가 발생할 수 있었으며, 인프라 변경 내역을 추적하기 어려웠습니다.

#2핵심 질문

인프라를 코드처럼 버전 관리하면서 한 번에 여러 리소스를 일관되게 생성하고 수정할 수 있을까요?

#3동작 예시

CloudFormation 템플릿은 JSON이나 YAML로 작성된 인프라 선언문입니다. Parameters는 템플릿 사용 시 입력받을 값들(예: 인스턴스 크기, 데이터베이스 암호)을 정의하고, Resources는 만들 AWS 리소스들(EC2, RDS, S3)을 나열하며, Outputs는 생성 완료 후 사용자에게 보여줄 값(예: 로드 밸런서 DNS)을 지정합니다. Ref와 Fn::GetAtt 같은 내장 함수로 리소스 간 참조를 연결하면, CloudFormation이 자동으로 리소스 생성 순서를 결정하고 리소스 ID나 속성값을 다른 리소스에 전달합니다.

#4동작 과정

  1. 템플릿 작성Parameters·Mappings·Conditions·Resources·Outputs 섹션을 채우고, 리소스 간 의존성을 Ref와 Fn::GetAtt로 연결합니다. Fn::Sub는 문자열 내에 변수를 삽입할 때 사용합니다.
  2. 스택 생성템플릿을 CloudFormation에 업로드하면, CloudFormation이 Resources를 선언 순서에 맞게 생성하고 각 리소스의 ID를 변수에 저장합니다.
  3. 리소스 연결 및 출력Ref와 Fn::GetAtt로 지정된 참조가 자동으로 값으로 치환되고, 스택 생성 완료 후 Outputs 값들이 사용자에게 표시됩니다.

#5한 줄 요약

CloudFormation인프라를 JSON/YAML 코드로 선언하고 내장 함수로 리소스를 연결하여, 반복 가능하고 버전 관리 가능한 일관된 인프라 프로비저닝과 코드 리뷰·자동화를 구현하는 코드형 인프라(Infrastructure as Code) 서비스

CloudFormation 스택 수명 주기: 변경 세트, 드리프트 감지, 롤백

스택을 만들고 바꾸고 지우는 과정에서 변경 세트로 영향을 미리 보고, 드리프트로 수동 변경을 찾아내며, 실패 시 자동 롤백으로 이전 상태로 되돌리는 흐름.

#1문제 상황

스택을 업데이트할 때 템플릿을 수정 후 바로 적용하면 예상하지 못한 리소스 삭제나 교체가 발생할 수 있었고, 실패 후 이전 상태로 되돌리는 것이 복잡했습니다. 또한 누군가 콘솔에서 인스턴스 설정을 수동으로 바꾸면 템플릿과 실제 리소스가 불일치하는데, 이를 감지하기 어려웠습니다.

#2핵심 질문

스택 변경 전에 영향 범위를 미리 확인하고, 수동 변경을 감지하며, 문제 발생 시 자동으로 이전 상태로 되돌릴 수 있을까요?

#3동작 예시

변경 세트(Change Set)는 템플릿 변경을 먼저 검증하고 어떤 리소스가 생성·수정·삭제될지 미리 보여줍니다. 예를 들어 RDS 인스턴스의 스토리지를 늘리는 변경은 "수정(변경 없음)"이지만, 엔진 유형을 바꾸려고 하면 "교체(인스턴스 재생성)"라고 명시됩니다. 드리프트 감지(Drift Detection)는 현재 스택의 실제 리소스들(EC2, 보안 그룹, RDS)과 템플릿 정의를 비교하여 어떤 리소스가 수동으로 변경되었는지 찾아냅니다. 롤백은 스택 업데이트 실패 시 자동으로 변경 전 리소스 상태로 복원합니다.

#4동작 과정

  1. 변경 세트 검증새 템플릿으로 변경 세트를 생성하면, CloudFormation이 각 리소스별 변경 유형(생성/수정/삭제/조건부)을 나열합니다. 검토 후 승인하면 변경을 적용합니다.
  2. 드리프트 감지스택 드리프트 감지를 실행하면, CloudFormation이 각 리소스의 현재 상태를 AWS API로 조회하고 템플릿 정의와 비교하여 불일치를 보고합니다.
  3. 장애 시 자동 롤백업데이트 중 리소스 생성에 실패하면, CloudFormation이 이미 생성된 리소스들을 자동으로 정리하고 스택을 변경 전 상태로 되돌립니다.

#5한 줄 요약

CloudFormation 스택 수명 주기변경 세트로 영향을 미리 검증하고, 드리프트 감지로 수동 변경을 추적하며, 자동 롤백으로 장애를 복구하여 인프라 변경의 안정성과 추적 가능성을 보장하는 관리 메커니즘

배포 오류 진단

스택 생성 실패의 흔한 원인인 IAM 권한 부족, 서브넷 IP 고갈, 서비스 할당량 초과, 리소스 간 의존 순서 문제를 이벤트 로그로 짚어내는 방법.

→ 07-02 참조

#1문제 상황

CloudFormation 스택 생성이 실패했을 때, 기존 방식은 스택 생성 명령만 실행하고 어디서 무엇이 잘못되었는지 알기 어렵습니다. 콘솔에는 "생성 실패"라는 메시지만 뜰 뿐, 어느 리소스에서 어떤 이유로 실패했는지, IAM 권한이 없는 건지 네트워크 설정 문제인지 명확하지 않습니다.

#2핵심 질문

CloudFormation 스택이 생성 실패했을 때 원인을 정확히 파악하고 문제를 수정하려면?

#3동작 예시

스택을 생성할 때 CloudFormation이 각 리소스를 순서대로 생성하는 과정을 이벤트 로그로 볼 수 있습니다. 예를 들어 IAM 역할을 만들 권한이 없으면 "User: arn:aws:iam::123456789:user/test is not authorized to perform: iam:CreateRole"이라는 구체적인 오류 메시지가 그 리소스의 이벤트에 기록되고, 서브넷 IP가 부족하면 "InsufficientFreeAddressesInSubnet"이 뜹니다.

#4동작 과정

  1. 스택 생성 시도CloudFormation이 템플릿의 각 리소스를 정의된 순서대로 생성합니다.
  2. 오류 발생 시 이벤트 기록생성 중 어느 리소스든 실패하면, CloudFormation이 그 오류를 자세히 Events 탭에 기록합니다. 권한 부족(IAM 정책 미지정), 서브넷 고갈(CIDR 블록 부족), 할당량 초과(서비스 한도 초과), 의존성 오류(선행 리소스 미생성)가 주요 원인입니다.
  3. 로그에서 근본 원인 파악실패한 각 리소스의 Status Reason에 구체적인 오류 메시지가 있으므로, 이를 읽고 IAM 정책 추가, 서브넷 크기 조정, 할당량 증액 신청, 리소스 순서 수정 등 대응합니다.

#5한 줄 요약

CloudFormation이 각 리소스 생성 과정에서 발생한 정확한 오류를 이벤트 로그에 남겨 주므로, 그 로그를 읽어 권한·용량·순서 문제를 신속하게 파악하고 수정하는 것

다계정·다리전 배포와 공유

하나의 템플릿을 여러 계정과 리전에 한 번에 펼치는 StackSets와, 만든 리소스를 다른 계정과 나눠 쓰게 하는 AWS Resource Access Manager.

#1문제 상황

여러 AWS 계정과 리전에 같은 인프라를 배포할 때, 기존 방식은 각 계정과 리전에서 따로따로 CloudFormation 스택을 만들어야 합니다. 50개 계정에 같은 템플릿을 배포하려면 50번 배포 명령을 실행해야 하고, 템플릿을 수정할 때도 50곳을 모두 수정해야 합니다.

#2핵심 질문

하나의 CloudFormation 템플릿을 여러 계정과 리전에 동시에 배포하고 일괄 관리할 수 있을까?

#3동작 예시

StackSets라는 기능을 사용하면, 관리 계정에서 하나의 템플릿을 정의한 후 "이 템플릿을 계정 A·B·C의 us-east-1과 eu-west-1에 배포하라"고 선언하면, CloudFormation이 자동으로 6개 지역에 스택을 만듭니다. 그 후 관리 계정에서 템플릿을 수정하면, 배포된 모든 스택이 자동으로 업데이트됩니다.

#4동작 과정

  1. StackSet 생성관리 계정에서 CloudFormation 템플릿을 StackSet으로 등록합니다.
  2. 배포 대상 지정어느 계정들의 어느 리전에 배포할지 명시합니다. 같은 조건의 여러 계정에 일괄 배포할 수 있습니다.
  3. 자동 배포 및 공유 관리StackSet이 지정한 모든 대상에 스택을 자동 생성하고, AWS RAM(Resource Access Manager, 리소스를 다른 계정과 공유하는 도구)으로 생성된 리소스를 다른 계정이 함께 쓸 수 있게 권한을 설정합니다.

#5한 줄 요약

하나의 템플릿으로 여러 계정과 리전의 스택을 한 번에 만들고 관리하며, 생성된 리소스를 StackSets와 AWS RAM으로 중앙에서 통제하는 것

AWS CDK와 Terraform, Git 등 서드파티 IaC 도구

익숙한 프로그래밍 언어로 CloudFormation 템플릿을 만들어 주는 AWS CDK와, Terraform·Git 같은 외부 도구를 함께 쓰는 코드형 인프라 운영 방식.

#1문제 상황

CloudFormation을 사용할 때 기존 방식은 JSON 또는 YAML 템플릿을 손으로 작성해야 합니다. 수백 줄의 선언형 코드를 직접 입력하고, 조건문이나 반복문이 필요하면 복잡한 Intrinsic Function을 써야 하며, 코드 재사용과 테스트가 어렵습니다.

#2핵심 질문

인프라를 Python, TypeScript, Java 같은 친숙한 프로그래밍 언어로 정의할 수 있을까?

#3동작 예시

AWS CDK를 사용하면 Python에서 ec2.Instance(vpc, "MyServer", instance_type=ec2.InstanceType.of(...)) 같은 명령형 코드로 EC2를 정의하고, CDK가 이를 자동으로 CloudFormation 템플릿으로 변환해 배포합니다. 프로그래밍 언어의 반복문, 조건문, 함수를 사용할 수 있어 템플릿 코드가 단순하고 재사용성이 높습니다.

#4동작 과정

  1. 프로그래밍 언어로 코드 작성AWS CDK (또는 Terraform, 다른 IaC 도구)에서 지원하는 언어로 인프라를 코드로 정의합니다. CDK는 TypeScript·Python·Java·Go, Terraform은 HCL(HashiCorp Configuration Language)이라는 자체 언어를 사용합니다.
  2. 코드 빌드 및 변환CDK는 코드를 컴파일해 CloudFormation JSON/YAML으로 자동 생성하고, Terraform은 HCL을 읽어 리소스 생성 계획을 만듭니다.
  3. 배포생성된 템플릿이나 계획을 CloudFormation, Terraform 엔진에 보내 실제 AWS 리소스를 생성합니다.

#5한 줄 요약

프로그래밍 언어의 유연성으로 인프라 코드를 작성하고, CDK나 Terraform이 이를 클라우드 공급자가 이해하는 형식으로 자동 변환해 배포하는 것

배포 전략

새 버전을 조금씩 교체하는 롤링, 환경을 통째로 바꿔치는 블루/그린, 일부 트래픽만 먼저 보내 보는 카나리 등 서비스 중단을 줄이는 배포 방식.

#1문제 상황

새 애플리케이션 버전을 배포할 때 기존 방식은 현재 실행 중인 모든 인스턴스를 한 번에 중단하고 새 버전을 시작하는 것입니다. 이 방식은 배포 순간 서비스가 완전히 중단되고, 새 버전에 치명적 버그가 있으면 모든 사용자가 영향을 받습니다.

#2핵심 질문

서비스 중단을 최소화하면서 새 버전으로 부드럽게 전환할 수 있을까?

#3동작 예시

롤링 배포는 10개 인스턴스 중 1개씩 차례로 교체하고, 각 교체가 성공하면 다음을 진행합니다. 블루/그린 배포는 현재 환경(블루)과 동일한 새 환경(그린)을 먼저 만들어 새 버전으로 채운 후, 로드 밸런서 설정을 한 번에 블루에서 그린으로 전환합니다. 카나리 배포는 전체 트래픽 중 5%만 새 버전으로 보낸 후, 오류가 없으면 점진적으로 비율을 높입니다.

#4동작 과정

  1. 배포 방식 선택서비스 특성에 따라 롤링(점진적, 배포 시간 길음), 블루/그린(빠른 전환, 리소스 2배 필요), 카나리(위험 최소화, 모니터링 필수) 중 선택합니다.
  2. 배포 실행선택한 방식에 따라 인스턴스를 교체하거나 환경을 전환합니다. 롤링은 정해진 개수씩 순차 교체, 블루/그린은 그린 환경 생성 후 로드 밸런서 스위칭, 카나리는 트래픽 비율을 점진적으로 증가시킵니다.
  3. 모니터링 및 롤백배포 중 오류율·응답 시간·리소스 사용률을 모니터링하고, 문제가 생기면 배포를 중단하고 이전 버전으로 즉시 되돌립니다.

#5한 줄 요약

새 버전을 한 번에 교체하지 않고, 롤링·블루/그린·카나리 같은 방식으로 조금씩 또는 부분적으로 전환해 서비스 중단과 장애 범위를 최소화하는 것

EC2 Auto Scaling 그룹, 시작 템플릿, 상태 확인, 수명 주기 후크

부하에 맞춰 EC2 인스턴스 수를 자동으로 늘리고 줄이는 그룹을 만들고, 시작 템플릿으로 인스턴스 사양을 정하며, 상태 확인으로 불량 인스턴스를 교체하고 수명 주기 후크로 기동·종료 순간에 작업을 끼워 넣는 방법.

#1문제 상황

부하가 변할 때 기존 방식은 운영자가 수동으로 EC2 인스턴스를 추가하거나 제거합니다. 트래픽이 갑자기 10배 늘면 인스턴스를 10배 추가할 때까지 서비스가 느려지고, 트래픽이 낮아지면 사용하지 않는 인스턴스에 비용이 계속 나갑니다.

#2핵심 질문

부하에 따라 자동으로 EC2 인스턴스 개수를 증감할 수 있을까?

#3동작 예시

Auto Scaling 그룹(ASG)을 만들 때 최소 2개, 최대 10개, 희망 3개 인스턴스라고 설정하면, CloudWatch 메트릭(CPU 사용률 70% 초과 등)을 기준으로 ASG가 자동으로 인스턴스를 추가합니다. 부하가 낮아져 CPU가 30% 이하로 떨어지면 인스턴스를 제거해 비용을 절감합니다.

#4동작 과정

  1. 시작 템플릿 정의EC2 인스턴스가 시작할 때 사용할 AMI(Amazon Machine Image, 미리 만든 OS 이미지), 인스턴스 타입, 보안 그룹, 키 페어, 사용자 데이터(시작 스크립트) 등을 시작 템플릿에 정의합니다.
  2. Auto Scaling 그룹 생성시작 템플릿을 지정하고, 최소·최대·희망 인스턴스 개수, 가용 영역, 로드 밸런서를 설정합니다. 상태 확인 설정으로, 불량 인스턴스(응답 없음)를 자동 교체합니다.
  3. 수명 주기 후크로 기동·종료 작업 삽입새 인스턴스가 시작되기 전·후 또는 종료 전에 특정 작업(데이터 동기화, 로그 수집)을 수행할 수 있습니다.

#5한 줄 요약

시작 템플릿으로 인스턴스 사양을 정의하고, Auto Scaling 그룹이 CloudWatch 메트릭을 모니터링하여 설정된 범위 내에서 자동으로 인스턴스를 추가·제거하며, 상태 확인과 수명 주기 후크로 안정성을 높이는 것

조정 정책과 Application Auto Scaling

대상 추적·단계별·예약 조정 같은 정책으로 언제 얼마나 늘릴지 정하고, EC2 외의 ECS·DynamoDB·Aurora 같은 서비스는 Application Auto Scaling 으로 같은 방식의 자동 확장을 적용한다.

→ 08-01 참조

#1문제 상황

EC2는 Auto Scaling이 있지만, ECS(컨테이너 관리), DynamoDB(관리형 NoSQL), Aurora(관리형 RDS) 등 다른 서비스는 자동 확장 기능이 없거나, 각 서비스마다 다른 방식으로 설정해야 합니다. 서비스마다 다른 인터페이스를 학습하고 유지해야 하므로 복잡합니다.

#2핵심 질문

EC2 외의 다양한 AWS 서비스도 같은 방식의 자동 확장을 적용할 수 있을까?

#3동작 예시

Application Auto Scaling이라는 중앙 집중식 확장 서비스를 사용하면, ECS 태스크 개수, Aurora 읽기 복제본 개수, DynamoDB 처리량(읽기/쓰기 용량)을 모두 같은 방식으로 자동 조정합니다. 예를 들어 "DynamoDB 쓰기가 80% 사용되면 용량을 10% 증가"라는 규칙 하나로 여러 서비스에 적용할 수 있습니다.

#4동작 과정

  1. 조정 정책 선택대상 추적(목표 메트릭 지정, 예: CPU 70% 유지), 단계별(메트릭 범위별로 다른 조정량, 예: 80% 초과면 10% 증가, 90% 초과면 20% 증가), 예약(특정 시간에 미리 확장, 예: 월요일 오전 9시에 용량 2배) 중 선택합니다.
  2. 조정 대상과 메트릭 설정확장할 리소스(ECS 서비스·DynamoDB 테이블 등)와 모니터링할 메트릭(CPU·메모리·RequestCount 등)을 지정합니다.
  3. 자동 조정 실행Application Auto Scaling이 메트릭을 수집해 정책을 평가하고, 설정된 조건에 따라 자동으로 리소스를 증감합니다.

#5한 줄 요약

대상 추적·단계별·예약 같은 통일된 조정 정책으로 EC2·ECS·DynamoDB·Aurora 등 다양한 AWS 서비스의 확장을 중앙에서 일괄 관리하는 것

데이터베이스 확장

읽기 부하는 읽기 전용 복제본으로 분산하고, Aurora Serverless v2 는 용량을 자동으로 조절하며, RDS Proxy 는 연결을 모아 쓰고, DynamoDB 는 온디맨드/프로비저닝 용량으로 처리량을 맞춘다.

#1문제 상황

데이터베이스 부하가 높을 때 기존 방식은 인스턴스 사양을 더 큰 것으로 변경(스케일 업)하는 것입니다. 그 과정에서 인스턴스가 잠깐 중단되고, 비용이 크게 올라갑니다. 읽기 부하가 높으면 더 큰 인스턴스도 버틸 수 없고, 연결 수가 많으면 데이터베이스가 연결 한도에 도달해 새 요청을 받지 못합니다.

#2핵심 질문

데이터베이스의 읽기 부하, 연결 수 증가, 쓰기 용량 부족을 어떻게 효율적으로 처리할까?

#3동작 예시

읽기 전용 복제본을 만들면, 기본 데이터베이스는 쓰기만 처리하고 읽기 요청은 복제본들로 분산됩니다. RDS Proxy를 앞에 두면, 애플리케이션의 많은 연결을 Proxy가 모아서 데이터베이스에는 적은 수의 연결만 유지하므로 연결 고갈을 방지합니다. Aurora Serverless v2는 동시성(트래픽)에 따라 자동으로 용량을 조절하고, DynamoDB 온디맨드 모드는 사용한 만큼만 요금을 냅니다.

#4동작 과정

  1. 읽기 분산읽기 전용 복제본(RDS)을 다른 가용 영역에 생성해, 응용이 복제본에서 데이터를 읽도록 로드 밸런싱하면 기본 인스턴스의 부하가 줄어듭니다.
  2. 연결 최적화RDS Proxy를 데이터베이스 앞에 두면, 애플리케이션 서버가 Proxy에 연결하고 Proxy가 데이터베이스 연결을 풀(pool, 미리 만들어둔 재사용 가능한 연결 모음)로 관리해 연결 수를 줄입니다.
  3. 용량 자동 조정Aurora Serverless v2는 들어오는 트래픽 파악해 자동으로 용량을 증가·감소시키고, DynamoDB는 온디맨드 모드로 전환해 자동 스케일링을 활성화하거나 프로비저닝 용량을 조정합니다.

#5한 줄 요약

읽기 전용 복제본으로 읽기 부하를 분산하고, RDS Proxy로 연결을 효율화하며, Aurora Serverless v2와 DynamoDB 온디맨드/프로비저닝 모드로 용량을 자동 또는 수동 조절해 데이터베이스의 읽기·쓰기 확장성을 높이는 것

#2핵심 질문

같은 데이터를 자주 쓸 때 매번 원본 서버까지 가지 않고 더 빠르게 꺼낼 수 있을까?

#3동작 예시

사용자가 상품 정보를 요청하면 먼저 메모리에 저장된 복사본이 있는지 확인하고, 있으면 즉시 반환하고, 없으면 데이터베이스에서 가져온 후 메모리에 보관했다가 반환한다.

#4동작 과정

  1. 메모리 캐시 저장ElastiCache나 DynamoDB Accelerator는 자주 쓰는 데이터를 메모리(매우 빠른 저장소)에 복사본으로 보관한다.
  2. 요청 시 빠른 응답애플리케이션이 데이터를 요청하면 캐시를 먼저 확인해서 있으면 메모리에서 직접 반환하고, 없으면 원본(데이터베이스)에 접근한다.
  3. 콘텐츠 캐시CloudFront 엣지 로케이션은 정적 파일이나 계산 결과를 지역별로 캐시해 두어 사용자가 가까운 지점에서 빠르게 받도록 한다.

Elastic Load Balancing 유형, 리스너, 대상 그룹, 상태 확인

들어오는 트래픽을 여러 대상에 나눠 보내는 로드 밸런서로, ALB·NLB·GLB 유형을 고르고 리스너 규칙과 대상 그룹, 상태 확인으로 정상 대상에만 요청을 보낸다.

#1문제 상황

한 대의 서버로 모든 요청을 받으면 그 서버가 처리할 수 있는 양이 한정되어 많은 사용자가 접속하면 응답이 지연되거나 요청이 거절된다. 서버 한 대가 죽으면 서비스 전체가 중단된다.

#2핵심 질문

들어오는 요청을 여러 서버에 나눠서 받아서 처리 능력을 높이고 어느 한 서버 장애에 영향받지 않을 수 있을까?

#3동작 예시

요청이 들어오면 로드 밸런서가 정상으로 작동하는 서버 세 대 중 한 대를 선택해서 요청을 보낸다. 한 대가 응답하지 않으면 나머지 두 대에만 분산한다.

#4동작 과정

  1. 유형 선택과 리스너 설정ALB(애플리케이션 계층, HTTP/HTTPS 경로별 라우팅)·NLB(네트워크 계층, 초고속 처리)·GLB(게이트웨이 계층, 방화벽 같은 가상 어플라이언스 처리) 중 필요한 유형을 고르고, 리스너(어느 포트로 요청을 받을지)를 정한다.
  2. 대상 그룹 정의요청을 받을 실제 서버들(대상 그룹, 예: EC2 인스턴스 세 대)을 묶어 두고, 로드 밸런서가 어느 대상 그룹으로 보낼지를 규칙으로 정한다.

#2핵심 질문

#3동작 예시

어떤 애플리케이션은 "1시간 이내에 복구(RTO 1h), 5분 전 시점까지 복원(RPO 5m)" 목표를 정하고, PITR(특정 시점 복구) 활성화와 S3 버전 관리로 실제 그만큼 복구할 수 있도록 구성한다.

#4동작 과정

  1. RTO·RPO 정의각 서비스의 중요도에 따라 복구 목표 시간(RTO: Recovery Time Objective)과 허용 손실 시간(RPO: Recovery Point Objective)을 정하고 기록한다.
  2. PITR 활성화RDS나 DynamoDB에서 특정 시점 복구(PITR, Point-in-Time Recovery)를 켜서 과거의 어느 시점으로든 되돌릴 수 있게 한다.
  3. 객체 버전 관리S3나 FSx에서 버전 관리(versioning)를 활성화해서 실수로 삭제·덮어씌워진 파일도 이전 버전에서 복구한다.

#1문제 상황

재해 복구 방식은 복구 시간과 비용이 서로 거래 관계다. 가장 느리지만 싼 방식(백업·복원)부터 매우 빠르지만 비싼 방식(액티브·액티브)까지 여러 선택지가 있는데, 상황마다 적절한 수준을 고르지 않으면 비용을 낭비하거나 복구에 실패한다.

#2핵심 질문

#4동작 과정

  1. 백업·복원주 리전에만 실행 중이고 재해 시 백업에서 다른 리전으로 복원하는 방식으로, 복구 시간이 길지만(수 시간) 비용이 가장 낮다.
  2. 파일럿 라이트와 웜 스탠바이대기 리전에 최소 인프라(파일럿)나 축소된 인프라(웜)를 미리 두고, 재해 시 해당 리전을 확장하거나 전환하는 방식으로, 복구 시간이 중간(15분~1시간)이고 비용도 그에 따라 증가한다.
  3. 액티브·액티브두 리전이 모두 같은 수준으로 실행 중이고, 주 리전 장애 시 대기 리전이 즉시 모든 트래픽을 받는 방식으로, 복구 시간이 최소(분 단위)이지만 비용이 가장 높다.

#2핵심 질문

도메인 이름을 IP로 변환하면서 가중치, 지연시간, 장애 조치 같은 정책을 함께 적용하고, 어떤 쿼리가 일어났는지 추적할 수 있으려면?

#3동작 예시

사용자가 example.com에 접속하면, Route 53의 호스팅 영역에 등록된 A 레코드가 해당 도메인을 지정된 IP로 변환합니다. 이때 라우팅 정책을 설정하면 가중치에 따라 서로 다른 IP로 보내거나, 특정 서버가 다운되면 다른 서버로 자동 전환하며, 모든 쿼리를 로그에 기록할 수 있습니다.

#4동작 과정

  1. 호스팅 영역 생성AWS 계정에서 관리할 도메인을 Route 53의 호스팅 영역에 등록합니다. 이 영역이 해당 도메인의 DNS 레코드를 보관하는 컨테이너 역할을 합니다.
  2. 레코드 추가 및 라우팅 정책 설정A, CNAME, 별칭 같은 레코드 유형을 추가하고, 단순 라우팅, 가중치 기반, 지연시간 기반, 장애 조치, 지리적 위치 같은 정책을 선택합니다. 정책에 따라 같은 도메인에 여러 레코드를 등록할 수 있습니다.
  3. 쿼리 로깅 활성화도메인에 대한 모든 DNS 쿼리를 CloudWatch Logs로 기록해 어떤 클라이언트가 언제 어떤 도메인을 조회했고 응답이 무엇이었는지 추적합니다.

#3동작 예시

CloudFront 배포를 생성하고 S3 또는 ALB를 오리진으로 지정하면, 전 세계 엣지 로케이션(AWS의 캐시 서버)에 콘텐츠 사본이 자동으로 배치됩니다. 사용자가 콘텐츠를 요청하면 가장 가까운 엣지에서 즉시 반환되고, 캐시에 없으면 그때 원본 서버에서 가져와 캐시에 저장합니다.

#4동작 과정

  1. 배포 생성 및 오리진 연결CloudFront 배포를 만들고, 콘텐츠의 원본이 될 S3 버킷, ALB, 또는 사용자 정의 도메인(HTTP 서버)을 오리진으로 연결합니다.

#1문제 상황

#4동작 과정

여러 계층에서 기록된 로그를 어떻게 체계적으로 모아서 통신 실패나 보안 위협의 원인을 찾아낼 것인가?

#3동작 예시

특정 클라이언트에서 웹 애플리케이션에 접속할 수 없다는 보고가 들어오면, VPC 플로우 로그를 확인해서 트래픽이 허용되었는지 거부되었는지 확인하고, ELB 로그에서 요청이 백엔드에 도착했는지 확인하고, WAF 로그에서 해당 요청이 어느 규칙에 차단되었는지 추적합니다.

#4동작 과정

  1. 로그 수집VPC Flow Logs(ENI 레벨 허용·거부 기록), ELB 액세스 로그(요청 상세), WAF 로그(차단된 규칙), CloudFront 액세스 로그(캐시 상태), 컨테이너 로그(애플리케이션 오류)를 CloudWatch Logs 또는 S3에 중앙화합니다.
  2. 필터링 및 상관 관계문제가 되는 클라이언트 IP, 시간대, 요청 경로를 기준으로 모든 로그를 필터링해서 같은 요청이 각 계층에서 어떤 상태인지 추적합니다.
  3. 원인 분석거부된 단계를 찾아내고(예: VPC에서 거부 vs. WAF에서 차단 vs. 백엔드 타임아웃), 해당 계층의 설정(보안 그룹, NACL, WAF 규칙, 타임아웃)을 검토해서 해결책을 수립합니다.

12성능과 비용 최적화12-01

컴퓨팅 최적화 - 성능 지표, 리소스 태그, Compute Optimizer, 배치 그룹

EC2의 CPU·메모리·네트워크 지표와 태그 기반 분류를 바탕으로 Compute Optimizer 권장 사항과 배치 그룹으로 인스턴스 크기와 배치를 최적화하는 방법.

#1문제 상황

기존에는 EC2 인스턴스를 생성할 때 필요한 크기를 예상해서 선택했고, 실제 운영 중에 성능 문제가 생겨도 어떤 인스턴스의 리소스 사용률이 높은지, 어떤 인스턴스는 낭비되고 있는지 정확히 파악하기 어려웠다. 여러 인스턴스를 관리할 때도 각각을 일일이 모니터링하고 조정해야 했다.

#2핵심 질문

EC2 인스턴스의 실제 성능 지표를 바탕으로 어떤 크기와 타입의 인스턴스를 선택하고, 어떻게 배치해야 최적의 성능과 비용 효율을 동시에 달성할 수 있을까?

#3동작 예시

t3.xlarge 인스턴스를 사용 중인데 실제로는 CPU와 메모리 사용률이 15~20% 정도일 때, Compute Optimizer가 지난 14일간의 성능 데이터를 분석해서 t3.medium으로 변경해도 충분하다고 권장하면, 개발자는 그 제안을 검토한 후 인스턴스 타입을 변경할 수 있다.

#4동작 과정

  1. 성능 지표 수집CloudWatch에서 CPU 사용률, 메모리 사용률, 네트워크 처리량, 디스크 I/O 등을 계속 수집하고 저장한다.
  2. 리소스 태그 기반 분류태그(tag)로 인스턴스를 환경(개발/프로덕션), 용도(웹 서버/배치 작업), 팀 등으로 분류해서 같은 특성의 인스턴스들을 그룹화하고 관리한다.
  3. Compute Optimizer 분석과 배치 그룹 적용수집된 성능 지표를 바탕으로 Compute Optimizer가 더 작은 인스턴스 타입이나 다른 인스턴스 패밀리를 제안하고, 배치 그룹(여러 인스턴스를 같은 물리 하드웨어에 배치해서 네트워크 성능을 높이는 기능)을 설정해서 성능 연계성이 필요한 인스턴스들을 함께 배치한다.

#5한 줄 요약

EC2 인스턴스의 실제 성능 데이터를 수집해서 분석하고, 그 결과를 바탕으로 더 작은 인스턴스 타입으로 변경하거나 배치를 최적화함으로써 비용은 절감하면서 성능은 유지하는 것

12성능과 비용 최적화12-02

Amazon EBS 성능 분석과 볼륨 유형 최적화

IOPS·처리량·대기 시간 지표를 읽고 gp3, io2 등 볼륨 유형과 프로비저닝 값을 워크로드에 맞게 조정하는 방법.

#1문제 상황

기존에는 EBS 볼륨의 IOPS(초당 입출력 작업 수), 처리량(초당 데이터 이동량), 대기 시간(작업 완료까지 걸리는 시간)을 정확히 파악하지 못했다. 초기 설정 후 성능 문제가 생겨도 어느 부분이 병목인지 알기 어려웠고, 모든 볼륨에 같은 타입(gp2)을 사용해서 일부는 과잉 성능을 제공받는 반면 높은 IOPS가 필요한 워크로드는 성능이 부족했다.

#2핵심 질문

EBS 볼륨의 실제 성능 지표를 읽고 워크로드의 특성에 맞는 볼륨 타입과 프로비저닝 값을 어떻게 선택할까?

#3동작 예시

데이터베이스 성능이 느리다는 보고가 들어오면, CloudWatch에서 VolumeReadLatency(읽기 지연 시간)와 VolumeConsumedReadOpsPercent(프로비저닝 IOPS의 사용률)를 확인해서 현재 gp2 볼륨이 병목이라고 판단되면 더 높은 IOPS를 제공하는 io2 볼륨으로 변경하거나, 같은 gp3 타입이라도 IOPS와 처리량 프로비저닝 값을 올린다.

#4동작 과정

  1. 성능 지표 해석IOPS(프로비저닝한 입출력 성능 대비 실제 사용률), 처리량(초당 메가바이트 단위의 데이터 이동량), 대기 시간(읽기/쓰기 완료까지 걸리는 밀리초)을 CloudWatch에서 확인해서 어느 지표가 병목인지 판단한다.
  2. 워크로드 특성 파악데이터베이스는 높은 IOPS와 낮은 지연 시간이 필요하고, 로그 분석이나 데이터 파이프라인은 높은 처리량이 필요한 식으로 워크로드 종류에 따라 필요한 성능 지표를 정의한다.
  3. 볼륨 타입과 파라미터 조정gp3(범용), io2(높은 IOPS용), st1(처리량 최적화), sc1(저비용 대용량) 등 적절한 볼륨 타입을 선택하고, 각 타입에서 IOPS와 처리량 값을 워크로드에 맞게 프로비저닝한다.

#5한 줄 요약

EBS 볼륨의 성능 지표를 분석해서 워크로드에 최적의 볼륨 타입과 프로비저닝 값을 선택함으로써 성능 목표를 달성하면서 불필요한 비용을 줄이는 것

스토리지 전송·수명 주기 최적화 - 멀티파트 업로드, Transfer Acceleration, DataSync, EFS·FSx 수명 주기

대용량 데이터를 빠르게 옮기는 S3 전송 기능과 DataSync, 그리고 접근 빈도에 따라 저장 계층을 자동 이동시키는 수명 주기 정책.

#1문제 상황

기존에는 대용량 파일을 S3로 업로드할 때 오래 걸렸고, 한 번에 업로드 실패하면 처음부터 다시 시작해야 했다. 또한 S3에 저장된 데이터를 접근 빈도와 관계없이 같은 스토리지 클래스에 유지해서 오래된 데이터도 비싼 비용으로 계속 보관했다. 온프레미스에서 AWS로 이동해야 하는 대량의 데이터도 인터넷 속도에 제한을 받았다.

#2핵심 질문

대용량 데이터를 빠르게 이동시키고, 시간이 지나면서 접근 빈도에 따라 저장 비용을 자동으로 줄일 수 있을까?

#3동작 예시

100GB 파일을 S3로 업로드할 때, 멀티파트 업로드로 파일을 10GB씩 10개 조각으로 나눠서 동시에(병렬) 업로드하면 훨씬 빠르고, 중간에 실패해도 실패한 부분만 다시 업로드하면 된다. 업로드 후 수명 주기 규칙을 설정해서 30일 뒤에는 자동으로 Standard-IA(자주 안 쓰는 데이터용) 클래스로 이동하고, 90일 뒤에는 Glacier(아주 오래 보관용)로 이동하면 저장 비용이 자동으로 내려간다.

#4동작 과정

  1. 전송 최적화멀티파트 업로드로 대용량 파일을 작은 부분으로 나눠서 동시에 업로드하거나, S3 Transfer Acceleration(AWS의 엣지 서버를 통한 빠른 경로)을 켜거나, AWS DataSync(온프레미스와 AWS 사이의 자동화된 데이터 이동 도구)를 사용해서 대량의 데이터를 빠르고 안정적으로 이동시킨다.
  2. S3 수명 주기 정책 설정객체가 생성된 후 일정 기간이 지나면 저장 클래스를 자동으로 옮기도록 규칙을 정의한다. 예: 30일 후 Standard-IA, 60일 후 Glacier, 365일 후 Deep Archive로 단계별 전환.
  3. 파일 시스템 수명 주기EFS(Elastic File System)와 FSx는 자주 안 쓰는 파일을 자동으로 저가 저장소(Infrequent Access 계층)로 이동시켜서 전체 용량과 비용을 절감한다.

#5한 줄 요약

대용량 데이터를 빠르고 안정적으로 이동시키고, 접근 패턴에 따라 저장 계층을 자동으로 변경해서 스토리지 비용을 최소화하는 것

Amazon RDS Performance Insights와 데이터베이스 성능 조정

Performance Insights의 DB 부하와 대기 이벤트로 병목 쿼리를 찾아 인스턴스 클래스·파라미터·읽기 복제본을 조정하는 방법.

#1문제 상황

기존에는 데이터베이스가 느릴 때 전체 부하가 높다는 것만 알 수 있었고, 어떤 쿼리가 병목인지, 어떤 리소스(CPU, 메모리, 네트워크, 테이블 잠금 등)에서 대기하는지 정확히 파악하기 어려웠다. 성능 문제를 해결하려면 느린 쿼리 로그를 일일이 분석하거나, 무작정 인스턴스 크기를 키워야 했다.

#2핵심 질문

데이터베이스의 어떤 쿼리가 어떤 이유로 느리고, 그것을 해결하기 위해 어떤 리소스를 조정해야 할까?

#3동작 예시

Performance Insights 대시보드를 보면 "UPDATE 쿼리가 전체 DB 부하의 70%를 차지하고 있고, 그 이유는 Lock Wait Event(다른 트랜잭션이 같은 행을 잠근 상태에서 기다리는 중)"라는 것을 시각적 그래프와 색상으로 즉시 확인할 수 있다. 이를 바탕으로 인덱스를 추가하거나 쿼리 로직을 개선한다.

#4동작 과정

  1. DB 부하와 대기 이벤트 분석Performance Insights에서 DB Load(동시에 실행 중인 쿼리 수)와 Wait Event(쿼리가 어떤 리소스를 기다리고 있는지: CPU 대기, 메모리 부족, 잠금 대기 등)를 색상 코드로 시각화해서 병목 지점을 찾는다.
  2. 병목 쿼리 식별 및 최적화부하가 높은 쿼리를 찾아서 실행 계획을 분석하고, 누락된 인덱스를 추가하거나 쿼리를 다시 작성해서 불필요한 조인이나 풀 테이블 스캔을 제거한다.
  3. 인스턴스 클래스 및 읽기 복제본 조정쿼리 최적화만으로 부족하면 더 큰 인스턴스 클래스(cpu/메모리 증가)로 변경하거나, 읽기 전용 복제본(동일한 데이터를 가진 별도 DB 인스턴스)을 추가해서 읽기 부하를 분산한다.

#5한 줄 요약

Performance Insights로 데이터베이스의 부하와 대기 이벤트를 시각적으로 분석해서 병목 쿼리와 리소스를 식별하고, 그에 맞게 쿼리, 인스턴스 설정, 복제본을 조정함으로써 데이터베이스 성능을 효율적으로 개선하는 것

12성능과 비용 최적화12-05

네트워크 비용과 비용 가시성 - Cost Explorer, Cost and Usage Reports, Savings Plans

데이터 전송 요금 구조를 이해하고 Cost Explorer·CUR로 지출을 분석하며 Savings Plans로 컴퓨팅 비용을 절감하는 방법.

#1문제 상황

기존에는 월말에 AWS 청구서를 받아도 어느 서비스에서 얼마를 썼는지, 특히 데이터 전송 요금이 어디서 발생했는지 파악하기 어려웠다. 데이터 전송(데이터센터 간, 리전 간, 인터넷 아웃바운드)은 복잡한 요금 구조를 가지고 있었고, 이를 줄이는 방법도 명확하지 않았다. 컴퓨팅 비용이 높아도 어떻게 효과적으로 절감할지 알 수 없었다.

#2핵심 질문

AWS 지출의 어느 부분이 비싼지, 그리고 어떻게 비용을 효과적으로 줄일 수 있을지를 어떻게 파악할까?

#3동작 예시

Cost Explorer를 열어보면 EC2 인스턴스 요금이 월 500달러, Data Transfer Out(인터넷으로 나가는 데이터) 비용이 300달러라는 것을 확인할 수 있다. Cost and Usage Reports(CUR)로 더 상세히 파면 us-east-1에서 eu-west-1로 가는 데이터 전송이 300달러 전부라는 것을 알 수 있고, 그 리전 간 통신을 VPC 엔드포인트(AWS 내부 네트워크 경로)로 바꾸면 비용을 0으로 줄일 수 있다.

#4동작 과정

  1. 데이터 전송 요금 구조 이해같은 가용 영역 내는 무료, 다른 가용 영역(같은 리전) 간은 0.01달러/GB, 다른 리전 간은 0.02달러/GB, 인터넷 아웃바운드는 0.09달러/GB 등의 구조를 파악해서 고가 구간을 식별한다.
  2. Cost Explorer와 CUR로 지출 분석Cost Explorer는 서비스와 링크된 계정별 비용을 시각적으로 빠르게 확인하는 대시보드이고, Cost and Usage Reports(CUR)는 시간 단위, 리소스 단위, 태그 단위 등 더 세밀한 필터링이 가능해서 비용이 높은 항목의 구체적인 원인을 추적한다.
  3. Savings Plans와 최적화 적용컴퓨팅(EC2, Lambda, RDS 등) 비용을 1년 또는 3년 기간으로 미리 약정하고 할인받는 Savings Plans를 구매하고, 불필요한 데이터 전송을 VPC 엔드포인트로 줄이거나 CloudFront(콘텐츠 전송 네트워크)를 사용해서 아웃바운드 비용을 절감한다.

#5한 줄 요약

데이터 전송의 복잡한 요금 구조를 이해하고, Cost Explorer와 CUR로 지출 현황을 분석한 후, Savings Plans와 네트워크 설계 최적화를 통해 AWS 비용을 체계적으로 관리하는 것
