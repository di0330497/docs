1단계 기초 — 에이전트 이해와 첫 실행

목표를 향해 스스로 계획을 세우고 도구를 호출하며 판단을 내리는 AI 시스템과 그 기본 구성 요소를 설명하는 개념.

#1문제 상황

기존의 AI 시스템은 사용자가 질문을 주고 나면 그 질문에 대한 답을 한 번에 생성하고 끝났다. 대화형 챗봇도 사용자가 다음 질문을 던질 때까지 스스로 아무 일도 하지 않았다. 이러한 방식은 답변 생성 하나만으로는 해결할 수 없는 일, 예를 들어 여러 문서를 찾아보고, 계산을 실행하고, 그 결과를 조합해 판단을 내리는 일 앞에서 금방 한계에 부딪혔다. 시스템이 스스로 어떤 일을 해야 하는지 계획을 세우거나 필요한 작업을 실제로 실행하는 능력이 전혀 없었기 때문이다.

#2핵심 질문

사용자의 지시 한 번을 받고도 스스로 계획을 세우고 도구를 실행해 목표를 끝까지 달성하는 AI 시스템을 어떻게 만들 수 있을까?

#3동작 예시

에이전트는 "너의 목표는 이러이러하다"라는 지시와 "이런 도구들을 쓸 수 있다"라는 도구 목록을 받은 하나의 프로그램이다. 예를 들어 "내일의 날씨에 맞는 옷차림을 추천해 줘"라는 요청을 받은 에이전트는, 날씨 API라는 도구를 호출해 현재 날씨 데이터를 받아온 뒤, 그 데이터를 바탕으로 추천 문장을 생성해서 답한다. 이 과정에서 사용자는 계획을 세우지 않았고, 에이전트가 어떤 도구를 언제 쓸지 스스로 결정했다.

#4동작 과정

  1. 요청 수신과 계획사용자 입력을 받아 에이전트가 지시(어떻게 행동할지 적힌 설정)와 도구 목록을 참고해 어떤 작업을 어떤 순서로 할지 정한다.
  2. 도구 실행과 결과 수집에이전트가 결정한 도구(외부 함수나 API)를 호출해 실제 데이터를 얻고 그 결과를 자신의 판단 재료로 사용한다.
  3. 최종 응답 생성모은 결과를 바탕으로 목표에 해당하는 최종 답변을 만들어 사용자에게 돌려준다.

#5한 줄 요약

지시와 도구만 주어지면 스스로 계획을 세우고 도구 호출과 판단을 반복해 목표를 완수하는 AI 시스템

에이전트·핸드오프·가드레일·세션·트레이싱이라는 작은 프리미티브 집합으로 멀티에이전트 워크플로를 orchestrate 하는 파이썬 툴킷.

#1문제 상황

에이전트를 처음부터 직접 만들려면 모델 호출, 도구 호출 루프, 상태 관리, 여러 에이전트 사이의 전환 등 수많은 반복 작업을 일일이 구현해야 한다. 대부분의 팀은 이 공통 골격을 다시 만들어야 했고, 에이전트마다 구조가 달라져서 프로젝트를 확장할수록 유지보수가 어려워졌다. 어떤 일을 누가 처리하는지를 바꾸는 것조차 처음 설계를 손봐야 했다.

#2핵심 질문

에이전트가 반드시 갖추어야 할 공통 동작들을 몇 가지 작은 구성 요소로 묶어 누구나 쉽게 조립할 수 있게 하려면 어떻게 해야 할까?

#3동작 예시

OpenAI Agents SDK는 "에이전트" 하나를 만들 때 지시(어떻게 행동할지), 도구(무엇을 쓸 수 있는지), 모델(어떤 모델로 판단할지)을 설정 객체 하나로 묶는 방식이다. 예를 들어 에이전트를 만들 때 지시와 도구 목록만 넘겨주면, 그 뒤에 실행기(Runner)가 모델 호출과 도구 호출을 반복하는 루프를 알아서 돌린다. 사용자는 루프 구현을 신경 쓸 필요가 없다.

#4동작 과정

  1. 구성 요소 선택에이전트, 핸드오프(에이전트 간 작업 인계), 가드레일(입출력 검사), 세션(대화 상태 유지), 트레이싱(동작 기록)이라는 다섯 가지 기본 요소 중 필요한 것을 고른다.
  2. 에이전트 정의와 조립지시와 도구를 에이전트 객체에 담고, 여러 에이전트가 필요한 경우 핸드오프로 서로 연결한다.
  3. 실행과 관찰Runner 로 에이전트를 실행하고, 트레이싱으로 에이전트가 도구를 어떻게 호출했는지 기록을 확인해 디버깅한다.

에이전트·핸드오프·가드레일·세션·트레이싱이라는 작은 기본 요소들의 조합으로 멀티에이전트 워크플로를 쉽게 구성하게 해주는 파이썬 툴킷

실행 맥락이 달라질 때마다 에이전트가 받는 지시도 그때그때 달라지게 하려면 어떻게 해야 하는가?

#3동작 예시

에이전트를 정의할 때 지시문으로 상수 문자열 대신 함수를 넘긴다. 이 함수는 에이전트의 실행 시점에 호출되어, 그때의 인자와 도구 호출 결과를 파라미터로 받아 지시문을 만들어 반환한다. 같은 에이전트라도 사용자가 한국어로 요청하면 한국어로 답하라는 지시가, 영어로 요청하면 영어로 답하라는 지시가 매번 새로 생성되어 시스템 프롬프트로 들어간다. 지시가 데이터처럼 함수의 결과로 계산되는 것이 핵심이다.

#4동작 과정

  1. 지시 함수 전달에이전트 정의 시 지시문 자리에 함수를 지정한다. 함수는 실행 맥락(인자)을 인자로 받을 수 있다.
  2. 실행 시점 호출에이전트가 실행을 시작할 때 이 함수가 호출되어 현재 상황에 맞는 지시문 문자열을 반환하고, 그 문자열이 시스템 프롬프트로 설정된다.
  3. 맥락 반영된 실행에이전트는 생성된 지시를 따르며 도구 호출을 수행하고, 도구 호출 결과도 다음 지시 생성의 입력으로 쓰여 이후 행동을 결정한다.

#5한 줄 요약

에이전트의 지시문을 고정 문자열이 아니라 실행 시점에 함수로 생성하게 하여, 들어오는 인자와 도구 호출 결과에 따라 에이전트가 매번 다른 지시를 받도록 하는 것

#1문제 상황

기존 방식에서는 모델이 답변을 자유 텍스트로 내놓았다. 에이전트가 어떤 결과를 돌려줄 때 자연어 문장을 그대로 반환하므로, 그 문장을 다른 프로그램이 처리하려면 문자열을 파싱(문장을 원하는 데이터 조각으로 쪼갬)해서 필요한 값을 일일이 추출해야 했다. 이 방식은 모델이 결과를 표현하는 방식이 매번 조금씩 달라져서 파싱이 깨지기 쉽고, 결과의 형식이 프로그램에 필요한 형태와 맞지 않는 문제가 있었다.

#2핵심 질문

에이전트의 결과를 자유 텍스트 대신 프로그램이 바로 쓸 수 있는 정해진 형태로 받으려면 어떻게 해야 하는가?

#3동작 예시

에이전트에 출력 스키마(결과의 형태를 정의한 명세)를 지정한다. 예를 들어 "이름과 나이"라는 두 필드를 가진 JSON 객체를 반환하라고 스키마를 정해 두면, 모델은 문장을 늘어놓는 대신 {"이름": "...", "나이": ...} 형태의 JSON 객체를 반환한다. 받는 쪽은 파싱 없이 그 객체의 필드를 그대로 꺼내 쓰면 된다.

#4동작 과정

  1. 스키마 지정에이전트를 정의할 때 output_type에 원하는 결과 형태(예: 특정 필드를 가진 JSON 객체)를 지정한다.
  2. 형식 강제 생성모델이 답변을 생성할 때 지정된 스키마에 맞는 JSON 객체를 만들도록 강제된다. 형식이 틀어지면 모델이 다시 생성한다.
  3. 검증과 반환생성된 객체가 스키마와 일치하는지 확인된 뒤 반환되고, 호출한 코드는 객체의 필드를 바로 읽어 사용한다.

#5한 줄 요약

모델의 출력을 출력 스키마로 강제해 에이전트가 자유 텍스트 대신 정해진 형태의 JSON 객체를 반환하도록 하여, 결과를 파싱 없이 프로그램이 바로 사용할 수 있게 하는 것

모델과 제공자 선택

OpenAI 모델뿐 아니라 다른 제공자의 모델도 지정할 수 있게 해 주는 모델 선택 방법과 사용 가능한 모델·제공자 목록이다.

#1문제 상황

기존 방식에서는 에이전트가 사용할 모델이 고정되어 있었다. 에이전트를 만들 때 특정 OpenAI 모델을 지정하면, 다른 모델이나 다른 제공자의 모델을 쓰려면 프레임워크가 지원하지 않아 별도로 코드를 수정해야 했다. 이 방식은 작업 성격별로 다른 모델을 골라 쓰거나, 비용이 다른 제공자의 모델로 바꾸는 일이 어려운 한계가 있었다.

#2핵심 질문

에이전트가 OpenAI 모델이 아닌 다른 제공자와 모델도 자유롭게 사용할 수 있게 하려면 어떻게 해야 하는가?

#3동작 예시

에이전트를 만들 때 사용할 모델을 문자열로 넘긴다. 그 문자열은 "제공자 이름과 모델 이름"의 조합으로, 예를 들어 특정 제공자의 특정 모델을 지정할 수 있다. 모델이 하나로 고정되지 않고 지정 방식이 통일되어 있어, 같은 코드에서 모델 문자열만 바꾸면 다른 제공자와 모델로 에이전트를 실행할 수 있다.

#4동작 과정

  1. 모델 지정에이전트 정의 시 model 인자에 사용할 모델을 식별하는 문자열을 적는다. 지정하지 않으면 프레임워크가 정해둔 기본 모델이 사용된다.
  2. 제공자 연결지정된 문자열을 보고 해당 제공자의 모델 제공자(모델 API에 연결하는 객체)가 선택되어 연결된다.
  3. 실행 적용선택된 모델이 에이전트의 추론에 실제로 사용되고, 필요한 경우 기본 모델 대신 해당 제공자·모델의 설정으로 동작한다.

#5한 줄 요약

모델을 지정 문자열 하나로 골라 쓰게 하여 OpenAI 모델뿐 아니라 다른 제공자의 모델도 같은 방식으로 에이전트에 연결할 수 있게 하는 것

모델 설정

온도, top_p, 최대 토큰 수 등 모델 추론 동작을 세밀하게 조정하는 설정값(model_settings)으로 에이전트의 출력 성향을 제어한다.

#1문제 상황

기존 방식에서는 모델의 추론 방식을 조정할 방법이 거의 없었다. 모델을 지정하기만 하고 그 동작은 그대로 두어야 했기 때문에, 같은 질문에 대해 답변이 너무 창의적으로 나오거나, 긴 답변을 요구하는 작업에서 출력이 중간에 잘리는 일을 조절할 수 없었다. 이 방식은 작업 특성에 맞게 모델의 생성 성향을 다듬을 수 없는 한계가 있었다.

#2핵심 질문

에이전트의 출력 성향을 작업에 맞게 세밀하게 조정하려면 어떻게 해야 하는가?

#3동작 예시

에이전트를 정의할 때 model_settings라는 설정 객체를 함께 넘긴다. 이 객체에는 추론 동작을 조절하는 값들이 담긴다. 예를 들어 온도를 낮추면 답변이 일관되고 결정적이어지고, 온도를 높이면 다양해진다. top_p나 최대 토큰 수 등도 여기에 적어 넣으면 모델의 생성 방식이 그 값에 따라 달라진다.

#4동작 과정

  1. 설정 값 지정에이전트 정의 시 model_settings에 온도, top_p, 최대 토큰 수(max_tokens) 등 조정할 값을 적는다. 여기서 온도는 출력의 무작위성 정도, top_p는 확률적으로 고려할 후보의 범위, 최대 토큰 수는 답변의 최대 길이를 뜻한다.
  2. 요청에 반영에이전트가 실행될 때 이 설정값들이 모델 API에 보내는 요청에 포함되어 전달된다.
  3. 생성 제어모델은 전달된 설정에 따라 출력의 무작위성·범위·길이를 조절하여 답변을 생성한다.

#5한 줄 요약

model_settings로 온도·top_p·최대 토큰 수 등의 값을 모델 요청에 실어 보내 에이전트의 출력 성향을 작업 목적에 맞게 제어하는 것

라이프사이클 훅

에이전트 실행의 각 단계(시작·종료·평가 등)에서 호출되는 콜백으로, 로깅·계측·동작 변경을 연결하는 후킹 메커니즘이다.

#1문제 상황

기존 방식에서는 에이전트가 실행되는 동안 그 과정을 밖에서 관찰하거나 끼어들 수단이 없었다. 에이전트가 언제 시작되고, 어떤 입력을 받고, 어떤 결과를 내고 끝났는지 알 수 없어서, 실행 기록을 남기거나 특정 시점에 동작을 바꾸려면 에이전트 코드 자체를 직접 수정해야 했다. 이 방식은 에이전트 실행에 로깅(실행 기록을 남기는 일)·계측(동작 측정)·추가 동작을 붙이기 어려운 한계가 있었다.

#2핵심 질문

에이전트의 실행 자체를 건드리지 않고, 실행 각 단계에서 로깅이나 동작 변경을 연결하려면 어떻게 해야 하는가?

#3동작 예시

에이전트를 만들 때 라이프사이클 훅(실행 단계마다 호출되는 콜백 함수)을 지정한다. 훅에는 실행 시작 시 호출되는 함수와 실행 종료 시 호출되는 함수 등이 있다. 예를 들어 시작 훅에 "지금 시간과 입력을 기록하라"는 로깅 코드를 넣어 두면, 에이전트가 실행될 때마다 그 훅이 자동으로 불려 기록이 남는다. 에이전트 본문은 그대로 두고, 훅만으로 관찰과 개입이 가능하다.

#4동작 과정

  1. 훅 등록에이전트 정의 시 라이프사이클 훅에 실행 단계별로 실행할 콜백을 등록한다. 콜백은 특정 시점에 호출되는 함수다.
  2. 시점별 호출에이전트가 실행을 시작하면 시작 훅이, 종료하면 종료 훅이, 각 평가(한 번의 추론 실행) 단계에서도 해당 훅이 호출된다.
  3. 후킹 동작 실행각 훅 안에 적은 로깅·계측·동작 변경 코드가 실행되어, 에이전트의 흐름에 영향 없이 관찰과 수정이 이루어진다.

#5한 줄 요약

에이전트 실행의 시작·종료·평가 같은 각 단계에 콜백을 걸어, 에이전트 본문을 수정하지 않고도 로깅·계측·동작 변경을 연결하는 것

#2핵심 질문

기존 에이전트의 설정을 바탕으로 새 에이전트를 만들고, 도구 사용을 상황에 따라 제어하려면 어떻게 해야 하는가?

#3동작 예시

#4동작 과정

  1. 복제 생성기존 에이전트에서 clone()을 호출하면 모델·지시문·도구 목록 등 설정이 복사된 새 에이전트가 만들어진다.
  2. 부분 수정복사된 새 에이전트의 일부 설정(예: 도구 목록이나 지시문)만 바꾸어 용도에 맞는 변형을 만든다.
  3. 도구 사용 제어 적용tool_use_behavior 설정으로 도구 사용 금지, 허용 도구만 사용, 기본 동작 따르기 중 하나를 지정하면 에이전트 실행 시 그 규칙대로 도구가 사용된다.

#5한 줄 요약

clone()으로 기존 에이전트의 설정을 복사한 새 에이전트를 만들고, tool_use_behavior로 도구 사용 여부와 방식을 제어하여 설정 재사용과 도구 통제를 가능하게 하는 것

#1문제 상황

기존 방식에서는 에이전트가 모델이 가진 지식 안에서만 답변을 생성했다. 모델은 학습된 내용만 알고 있으므로, 현재 시각을 알려 달라는 요청이나 외부 시스템의 최신 데이터가 필요한 요청에는 정확히 대답할 수 없었다. 에이전트가 실제로 무언가를 수행하는 수단이 없었기 때문에, 에이전트는 생각만 하고 행동은 하지 못하는 한계가 있었다.

#2핵심 질문

#3동작 예시

#4동작 과정

  1. 도구 선택·정의작업에 필요한 기능을 기준으로 도구를 고른다. 정보 조회·계산처럼 직접 코드로 만들 수 있으면 함수 도구를 정의하고, 문서 검색 같은 제공 기능이라면 프레임워크가 제공하는 호스티드 도구를 쓴다.
  2. 도구 등록선택한 도구를 에이전트 정의에 등록하여 에이전트가 그 도구를 호출할 수 있게 한다.
  3. 호출과 결과 반영실행 중 에이전트가 필요할 때 도구를 호출하고, 도구가 반환한 결과를 받아 다음 추론과 답변에 사용한다.

#2핵심 질문

#4동작 과정

  1. 도구 등록개발자가 파이썬 함수를 작성하고 @function_tool 데코레이터를 붙이면, SDK 가 함수 시그니처(함수의 입력과 출력 형태)를 읽어 도구로 등록하고 모델에게 그 존재와 사용법을 알린다.
  2. 모델의 도구 선택과 인자 생성사용자 요청이 들어오면 모델이 어떤 도구를 쓸지 결정하고, 함수가 요구하는 인자가 무엇인지 값을 채워 실행 요청을 만든다.
  3. 실행과 결과 반환SDK 가 해당 함수를 실제로 호출하고, 반환된 결과를 모델에게 다시 보내 모델이 그것을 바탕으로 사용자에게 최종 답변을 생성한다.

#2핵심 질문

#4동작 과정

  1. 도구 선택개발자가 에이전트에 호스티드 도구 중 필요한 것(웹 검색, 웹 크롤, 파일 검색 등)을 지정한다.
  2. 에이전트 연결지정된 내장 도구가 에이전트의 사용 가능한 도구 목록에 등록되고, 모델이 그 존재를 알게 된다.
  3. 자동 활용작업 중 모델이 필요하다고 판단하면 연결된 호스티드 도구를 호출하고, OpenAI 서버에서 실행된 결과를 받아 답변에 사용한다.

#2핵심 질문

#3동작 예시

#4동작 과정

#2핵심 질문

Python 코드에서 에이전트를 직접 실행하고 그 결과를 받아, 여러 에이전트를 연결하는 흐름을 프로그래밍할 수는 없을까?

#3동작 예시

코드에서 먼저 에이전트 A를 실행해 주소 목록을 얻는다. 그 결과를 변수에 저장한 뒤, 에이전트 B를 실행할 때 그 변수를 입력으로 넘긴다. 에이전트 B는 그 입력을 이용해 배송 상태를 확인하고 결과를 돌려준다. 이렇게 코드의 일반적인 실행 순서(실행 → 결과 반환 → 다음 실행)를 그대로 따라 에이전트를 하나씩 호출해 흐름을 만든다.

#4동작 과정

  1. 첫 에이전트 실행Python 코드에서 에이전트를 실행(run)하고 반환된 결과를 변수에 받는다.
  2. 결과 전달받은 결과를 다음 에이전트의 입력으로 사용해 그 에이전트를 실행한다.
  3. 연쇄 완료필요한 만큼 에이전트를 순서대로 실행·연결하고, 마지막 결과를 코드에서 그대로 사용하거나 사용자에게 반환한다.

Python 코드에서 에이전트를 직접 실행하고 결과를 변수로 주고받으며 여러 에이전트를 연결하는 오케스트레이션을 프로그래밍하는 것

트립와이어는 가드레일 검사를 통과한 뒤 실행 중에 위험 상태가 포착되면 즉시 전체 실행을 중단시키는 장치다. 예를 들어 에이전트가 파일을 읽는 도중에 접근 금지 경로로 접근하는 신호가 감지되면, 트립와이어가 그 순간 실행을 멈추고 안전한 종료 메시지를 반환한다. 정기 검사와 달리 사건 발생 즉시 끊어내는 것이 핵심이다.

#4동작 과정

  1. 위험 신호 감지실행 중에 발생한 예외나 규칙 위반 신호를 트립와이어가 실시간으로 포착한다.
  2. 즉시 중단포착 즉시 에이전트 루프와 진행 중인 작업을 중단시키고 추가 도구 호출을 차단한다.
  3. 예외 처리·종료중단 사유를 정리하고 예외 처리 메커니즘이 초과·오류 상황을 기록한 뒤 실행을 안전하게 종료한다.

중요한 결정을 에이전트가 실행하기 전에 사람이 최종 승인하도록 만들 수 없을까?

#3동작 예시

#4동작 과정

  1. 승인 필요 지점 도달에이전트가 사람 승인이 필요한 도구 호출이나 결정 지점에 이르면 실행을 멈추고 승인 요청을 만든다.
  2. 사람 판단·응답사람이 요청 내용을 확인하고 승인·거부·수정을 결정해 응답한다.
  3. 결정 반영·재개승인이면 에이전트가 계속 실행하고, 거부나 수정이면 그 내용을 반영해 흐름을 조정한다.

#2핵심 질문

실행 중인 에이전트를 사람이 승인·일시정지·재개로 제어하고 상태를 추적할 수 없을까?

#3동작 예시

RunState는 에이전트 실행(런)이 현재 어떤 상태인지 나타내는 상태 값이다. 예를 들어 에이전트가 송금 도구 호출 지점에서 승인 대기 상태로 들어서면, 런의 RunState가 승인 대기로 전환되고 시스템이 이 상태를 기준으로 실행을 일시정지했다가 승인이 들어오면 재개 상태로 바꾼다. 실행의 현재 위치를 상태 값으로 표현하고 그 상태 전환을 제어한다는 점이 핵심이다.

#4동작 과정

  1. 런 시작·상태 추적에이전트 실행이 시작되면 런 객체가 생성되고 RunState가 초기 상태로 설정되어 이후 전환을 추적한다.
  2. 승인·일시정지 전환승인 필요 지점에 도달하면 RunState를 승인 대기·일시정지 상태로 바꿔 실행을 멈춘다.
  3. 승인 후 재개·완료사람의 승인·거부에 따라 상태를 전환해 실행을 재개하거나 중단하고, 종료 시점에 완료·실패 상태로 마무리한다.

#1문제 상황

에이전트를 정의만 하고 실행하지 않으면 아무 일도 일어나지 않는다. 기존 방식에서는 코드가 함수를 직접 호출하고 그 결과를 받아 다시 조건문으로 분기하는 식으로 흐름을 손으로 조립했다. 그 방식은 LLM 호출, 도구 실행, 결과 판단을 개발자가 일일이 이어 붙여야 해서, 응답이 도구 호출을 요청하는지 최종 답변인지 매번 판별하는 반복 코드가 여기저기 흩어진다. 한 번 더 LLM을 부를지, 도구를 실행할지, 끝낼지를 결정하는 전체 흐름을 어디에도 한곳에 담지 못하는 것이 명확한 한계다.

#2핵심 질문

에이전트가 스스로 다음 행동을 결정하며 반복하다가 완료에 이를 때까지, 누가 그 실행 루프를 돌려줘야 하는가?

#3동작 예시

Runner가 에이전트 하나를 받아 실행을 시작하면, 에이전트가 LLM에 입력을 보내고 그 응답을 받는 순간부터 루프가 돈다. LLM이 도구 호출을 요청하면 Runner는 그 도구를 실제로 실행해 결과를 다시 에이전트에게 돌려주고, LLM이 최종 답변을 내면 루프를 멈추고 그 결과를 반환한다. 에이전트는 "무엇을 할지 정하는 규칙"만 갖고 있고, "언제 반복하고 언제 멈출지"는 Runner가 관리한다.

#4동작 과정

  1. LLM 호출Runner가 에이전트의 지시와 현재까지의 입력을 모델에 보내 응답을 받는다.
  2. 응답 판단과 실행응답이 도구 호출이면 해당 도구를 실행해 그 결과를 대화 기록에 붙이고, 최종 답변이면 그대로 진행한다.
  3. 완료까지 반복최종 답변이 나올 때까지 앞 두 단계를 되풀이하고, 나오면 최대 반복 횟수에 걸리기 전에 결과 객체를 반환하며 루프를 끝낸다.

#5한 줄 요약

에이전트의 결정 규칙만 받아 LLM 호출, 도구 실행, 종료 판단을 완료 시점까지 반복해 돌려주는 실행 루프

#2핵심 질문

한 번의 실행에 적용되는 갖가지 조건을 코드를 흩뜨리지 않고 한곳에 담아 넘길 수 없을까?

#4동작 과정

  1. 설정 작성모델 선택, 타임아웃, 재시도, 사용량 한도 같은 조건을 RunConfig 객체에 담는다.
  2. 전달그 config를 Runner의 실행 호출에 같이 넘겨, 이번 실행이 따를 조건으로 등록한다.
  3. 적용Runner가 실행 루프를 돌면서 LLM 호출과 도구 실행마다 config에 적힌 조건을 적용한다.

#2핵심 질문

에이전트가 실행되는 중간중간의 진행 상황을 완료를 기다리지 않고 실시간으로 받아볼 수 없을까?

#3동작 예시

스트리밍 모드로 실행하면 Runner가 일을 마치고 결과를 주는 대신, 도구 호출이 시작될 때, 부분 응답 토큰이 생성될 때, 실행이 완료될 때 같은 사건을 그때그때 이벤트로 흘려보낸다. UI는 그 이벤트를 받는 즉시 "지금 도구를 실행하는 중", "답변을 작성하는 중" 같은 상태를 화면에 반영할 수 있다.

#4동작 과정

함수 호출로 대화 기록·외부 데이터를 실시간 생성해 프롬프트에 넣는 동적 컨텍스트 제공 방식.

→ 06-08 참조

#1문제 상황

로컬 컨텍스트 방식은 지정된 파일을 통째로 프롬프트에 넣는 정적 방식이라, 대화가 진행되면서 달라지는 내용이나 실시간으로 생성되는 데이터는 담을 수 없었습니다. 예를 들어 대화 기록 전체, 방금 검색한 검색 결과, 데이터베이스에서 조회한 최신 값 같은 것은 미리 파일로 준비되어 있지 않기 때문에 프롬프트에 넣을 수 없었습니다. 에이전트가 작업 도중 얻는 정보를 프롬프트에 반영하려면 매번 직접 코드로 문자열을 조합해 넣어야 했습니다.

#2핵심 질문

대화 기록이나 외부 데이터처럼 실행 중에 실시간으로 생기는 내용을 프롬프트에 어떻게 자동으로 넣을 수 있을까요?

#3동작 예시

컨텍스트에 함수 하나를 등록해 두면, 에이전트가 실행을 시작할 때 시스템이 그 함수를 호출해 결괏값을 받아 프롬프트에 넣습니다. 예를 들어 get_current_weather()라는 함수를 컨텍스트로 등록해 두면, 실행 시 그 함수가 호출되어 "서울, 맑음, 24도" 같은 최신 날씨 문자열이 생성되고, 그 문자열이 시스템 프롬프트에 동적으로 추가된 뒤 LLM에 전달됩니다. 함수가 만들어 내는 내용이 곧 프롬프트의 일부가 되는 방식입니다.

#4동작 과정

  1. 함수 등록컨텍스트에 호출할 함수(예: 대화 기록 조회, 외부 API 호출)를 지정합니다.
  2. 실행 시 함수 호출에이전트가 실행될 때 시스템이 그 함수를 호출해 결과 문자열을 실시간으로 생성합니다.
  3. 프롬프트에 주입 후 LLM 호출생성된 문자열을 시스템 프롬프트에 넣어 LLM에 전달하고, LLM은 최신 데이터가 포함된 프롬프트를 바탕으로 응답합니다.

#5한 줄 요약

함수 호출로 대화 기록·외부 데이터를 실행 시점에 실시간 생성해 프롬프트에 동적으로 주입함으로써, 정적 파일로는 담을 수 없는 최신 정보를 LLM 입력에 포함시키는 것

오류 처리기와 예외

실행 중 발생한 오류를 감지·완화하고(취소, 정리, 재시도) 예외를 호출자에게 전달하는 처리 장치.

#1문제 상황

에이전트 실행 코드는 보통 run(), run_streamed() 같은 호출 한 번으로 작성하지만, 그 안에서 도구 호출 실패, 모델 응답 이상, 실행 취소 같은 여러 오류가 발생할 수 있었습니다. 오류 처리를 하지 않으면 실행이 중간에 멈추고 사용자에게 알 수 없는 예외가 그대로 전달되어, 무엇이 잘못됐는지 파악하기 어려웠습니다. 또 실행이 중단될 때 일부 작업이 정리되지 않은 채 남는 문제도 있었습니다.

#2핵심 질문

실행 중 발생하는 오류를 어떻게 감지하고 처리하며, 처리할 수 없는 예외는 어떻게 호출자에게 전달할 수 있을까요?

#3동작 예시

ModelBehaviorError라는 예외 유형을 기준으로 처리기를 문법에 등록해 두면, 모델이 잘못된 응답(예: 형식에 맞지 않는 출력)을 내보낼 때 그 예외가 잡혀 등록된 함수로 전달됩니다. 그 함수가 대체 응답을 만들어 이어서 실행을 계속하게 할 수도 있고, 실행을 중단하고 예외를 호출자에게 넘길 수도 있습니다. 오류가 발생했을 때 실행 흐름이 어디로 갈지를 미리 정해 두는 방식입니다.

#4동작 과정

  1. 처리기 등록handle(ModelBehaviorError, 함수) 형태로 예외 유형마다 처리할 함수를 미리 등록합니다.
  2. 실행 중 오류 발생·감지에이전트가 실행되는 동안 지정한 유형의 예외가 발생하면 시스템이 등록된 처리 함수를 호출합니다.
  3. 처리 또는 전달처리 함수가 완화 동작(취소, 정리 작업, 재시도, 대체 응답)을 수행하거나, 처리할 수 없으면 예외를 호출자에게 그대로 전달해 호출 측에서 받아 처리합니다.

#5한 줄 요약

실행 중 발생한 오류를 예외 유형별 처리기로 감지·완화(취소, 정리, 재시도)하고, 처리할 수 없는 예외는 호출자에게 전달해 에이전트 실행을 안정적으로 제어하는 것

트레이싱 개요

에이전트가 실행되는 동안의 모든 단계(도구 호출, LLM 응답, 핸드오프 등)를 스팬(span)으로 기록해 나중에 재생·분석할 수 있게 하는 관측 기능.

#1문제 상황

에이전트가 여러 도구를 호출하고 여러 LLM 응답을 거쳐 완료될 때까지, 중간에 어떤 단계가 실제로 실행됐는지 확인할 방법이 없었습니다. 실행이 끝난 뒤에는 프롬프트에 무엇을 넣었는지, 어떤 도구가 어떤 인자로 호출됐는지, 어느 단계에서 시간이 오래 걸렸는지 알 수 없어서 문제가 생겨도 원인을 추적하기 어려웠습니다. 로그를 일일이 직접 출력하도록 코드를 작성해도 실행 전체를 시간 순서대로 연결해 보기는 힘들었습니다.

#2핵심 질문

에이전트 실행의 모든 단계를 기록해 두고 나중에 재생·분석하려면 어떻게 해야 할까요?

#3동작 예시

에이전트를 실행하면 시스템이 작업 하나(trace)를 만들고, 그 안에서 일어나는 도구 호출, LLM 응답, 핸드오프를 각각 하나의 스팬(span, 실행 구간 단위)으로 기록합니다. 예를 들어 "검색 → 요약 → 답변"으로 이어지는 실행이라면 검색 도구 호출 스팬, 요약을 만든 LLM 호출 스팬, 최종 답변 LLM 호출 스팬이 같은 트레이스 아래에 시간 순서로 쌓입니다. 실행 전체가 나중에 재생 가능한 기록으로 남는 방식입니다.

#4동작 과정

  1. 트레이스 생성에이전트 실행이 시작되면 실행 전체를 묶는 트레이스(추적 단위)가 하나 만들어집니다.
  2. 스팬 기록실행 중 일어나는 각 단계(도구 호출, LLM 응답, 핸드오프 등)가 스팬으로 기록되어 트레이스에 추가됩니다.
  3. 완료·저장실행이 끝나면 트레이스가 완료 처리되어 기록이 저장되고, 이후 분석·재생에 사용할 수 있습니다.

#5한 줄 요약

에이전트 실행 중의 모든 단계를 스팬으로 기록해 트레이스로 묶어 저장함으로써, 실행 전체를 나중에 재생·분석할 수 있게 하는 관측 기능

시각화

트레이싱으로 수집한 실행 기록을 노트북이나 웹 앱에 대시보드로 임베드해 에이전트 흐름을 눈으로 확인하는 기능.

#1문제 상황

트레이싱이 실행 기록을 수집해 주긴 하지만, 그 기록을 보려면 데이터를 직접 뒤져야 했고 실행의 흐름이 한눈에 들어오지 않았습니다. 어느 단계가 먼저 실행되고 어느 단계가 오래 걸렸는지, 도구 호출이 어떻게 이어졌는지를 텍스트로만 파악하려면 시간이 많이 걸렸습니다. 실행이 복잡해질수록 전체 그림을 그리는 일이 점점 어려워졌습니다.

#2핵심 질문

수집된 실행 기록을 어떻게 눈으로 바로 볼 수 있는 형태로 보여줄 수 있을까요?

#3동작 예시

OpenAI 대시보드에 접속하면 실행한 에이전트의 트레이스가 목록으로 보이고, 하나를 선택하면 그 안의 스팬들이 시간 순서와 소요 시간과 함께 그래프·타임라인 형태로 펼쳐집니다. 노트북에서는 RunVisualization 같은 컴포넌트에 트레이스 결과를 넣어 실행 흐름을 화면에 직접 임베드해서 볼 수 있습니다. 기록 데이터가 사람이 읽기 좋은 대시보드로 변환되는 방식입니다.

#4동작 과정

  1. 시각화 대상 선택볼 트레이스(노트북에서는 방금 실행한 결과 객체, 웹에서는 실행 ID)를 선택합니다.
  2. 데이터 렌더링시각화 컴포넌트나 대시보드가 트레이스·스팬 데이터를 읽어 단계와 소요 시간을 배치합니다.
  3. 화면 표시에이전트의 실행 흐름이 대시보드나 노트북 화면에 표시되어 눈으로 확인할 수 있습니다.

#5한 줄 요약

트레이싱으로 수집한 실행 기록을 노트북이나 웹 앱의 대시보드에 임베드해 에이전트 흐름을 눈으로 확인할 수 있게 하는 기능

사용량과 비용

에이전트 실행이 소모한 토큰 수와 이에 따른 비용을 집계·추정해 운영 비용을 파악하는 기능.

#1문제 상황

에이전트는 실행할 때마다 여러 번의 LLM 호출을 하기 때문에, 한 번의 사용자 요청이 얼마나 많은 토큰(LLM이 처리하는 텍스트 단위)을 소모하는지 단순 계산으로는 알기 어려웠습니다. 각 호출의 입력·출력 토큰 수가 제각각이고 도구 호출에 따른 추가 비용도 있어서, 실제로 지출되는 금액을 파악하려면 각 호출의 결과를 일일이 모아야 했습니다. 비용이 통제되지 않으면 에이전트를 운영할 때 예상보다 큰 지출이 발생할 위험이 있었습니다.

#2핵심 질문

에이전트 실행이 소모한 토큰과 그에 따른 비용을 어떻게 정확히 집계할 수 있을까요?

#3동작 예시

run()의 결과 객체에는 last_usage() 메서드가 있어서, 실행이 끝나면 시스템이 그 실행 동안의 모든 LLM 호출의 토큰 수를 합산한 사용량 정보를 돌려줍니다. 예를 들어 3번의 LLM 호출이 있었으면 그 3번의 입력·출력 토큰 수가 각각 합산되어, 전체 사용량과 모델별 사용량으로 나뉘어 제공됩니다. 실행 하나가 끝났을 때 그 실행의 총 소모량을 바로 얻을 수 있는 방식입니다.

#4동작 과정

  1. 실행 결과 받기에이전트 실행이 끝나면 결과 객체에 사용량 정보가 담겨 있습니다.
  2. 사용량 조회last_usage()를 호출해 이번 실행의 총 토큰 수 및 모델별 토큰 수를 가져옵니다.
  3. 비용 계산·집계가져온 토큰 수를 모델별 단가에 대입해 비용을 추정하고, 여러 실행을 모아 운영 비용을 파악합니다(트레이스 데이터와 결합해 실행별 분석도 가능).

#5한 줄 요약

에이전트 실행이 소모한 토큰 수와 이에 따른 비용을 집계·추정해 운영 비용을 파악할 수 있게 하는 기능

테스트

실제 모델 호출 없이 에이전트·샌드박스·리얼타임·음성 워크플로를 결정적으로(재현 가능하게) 검증하는 테스트 유틸리티.

#1문제 상황

#2핵심 질문

실제 모델 호출 없이 에이전트의 동작을 결정적(재현 가능)으로 검증하려면 어떻게 해야 할까요?

#3동작 예시

ModelTester와 RunConfig를 조합해 테스트 전용의 가짜 모델을 만들어 에이전트에 넣으면, 그 모델은 정해진 입력에 정해진 응답을 반환합니다. 예를 들어 "안녕"이라는 입력에는 언제나 "안녕하세요"라고 응답하도록 미리 정의된 모델을 사용해 에이전트를 실행하면, 실제 LLM 호출 없이도 에이전트가 그 응답을 바탕으로 다음 행동을 올바르게 하는지 같은 결과로 반복 검증할 수 있습니다. 실제 모델 자리를 고정된 응답을 주는 모델로 바꿔 치는 방식입니다.

#4동작 과정

#4동작 과정

  1. 대화형 셸 실행REPL 유틸리티를 시작하면 에이전트 인스턴스를 만들고 대화를 주고받을 수 있는 프롬프트가 뜬다.

MCP 개요와 통합 선택

Model Context Protocol(MCP)은 에이전트가 외부 도구·데이터에 표준화된 인터페이스로 연결하게 해주는 개방형 프로토콜로, SDK는 이 통합을 지원한다.

#1문제 상황

에이전트가 외부 도구나 데이터에 연결하려면 도구마다 서로 다른 API 형식과 인증 방식을 각각 구현해야 했다. 문제는 도구가 늘어날수록 통합 코드가 중복되고, 새 도구를 붙일 때마다 그 도구의 고유한 인터페이스를 처음부터 배워야 해서 확장이 어렵다는 점이다.

#2핵심 질문

수많은 외부 도구와 데이터를 하나의 표준화된 인터페이스로 연결할 수 없을까?

#3동작 예시

MCP(Model Context Protocol)는 도구 제공자가 "이런 이름의 도구가 이런 입력을 받아 이런 결과를 돌려준다"는 표준 형식으로 서버를 만들고, 에이전트 쪽 SDK는 그 표준 형식만 읽으면 어떤 서버든 같은 방식으로 도구를 사용할 수 있게 해준다.

#4동작 과정

  1. 통합 방식 선택SDK에서 제공하는 MCP 지원을 켜고 호스티드 MCP 또는 로컬 MCP 서버 중 사용할 연결 유형을 정한다.
  2. 서버 연결선택한 서버를 SDK 설정에 등록하면 서버가 표준 형식으로 광고하는 도구 목록이 에이전트에게 노출된다.
  3. 도구 호출에이전트는 노출된 도구를 일반 도구처럼 호출하고, 요청과 응답이 프로토콜 규격에 맞춰 서버와 주고받아진다.

#5한 줄 요약

에이전트가 외부 도구·데이터에 표준화된 인터페이스로 연결되게 해주는 개방형 프로토콜을 SDK가 지원해 통합을 단순화하는 것

#2핵심 질문

9단계 모달리티와 고급 운영 — 음성·샌드박스·배포

모델 선택, 재시도·요율 제한, 러너 정책 등 프로덕션 운영에서 전역 동작을 정하는 SDK 구성 영역이다.

#1문제 상황

기존 방식에서는 에이전트마다 실행 옵션을 일일이 지정해야 했다. 어떤 모델을 쓸지, 실패했을 때 몇 번 다시 시도할지, 요청이 너무 많을 때 어떻게 대응할지 같은 설정을 각 에이전트 코드에 하드코딩(하드코딩: 값을 코드 안에 고정해 넣는 방식)해 넣는 식이었다. 이렇게 하면 에이전트가 늘어날수록 같은 설정이 여기저기 중복되고, 설정을 바꾸려면 관련 코드를 전부 찾아 고쳐야 했다. 프로덕션(프로덕션: 실제 사용자에게 서비스가 운영되는 환경)에서 전체 동작을 일관되게 관리하기 어려운 것이 기존 방식의 한계였다.

#2핵심 질문

모든 에이전트에 공통으로 적용되는 운영 설정을 한곳에서 관리하려면 어떻게 해야 할까?

#3동작 예시

구성(Configuration) 영역은 전역 설정 객체 하나로 에이전트 전체의 동작을 정한다. 예를 들어 기본 모델을 하나 지정해 두면, 따로 모델을 명시하지 않은 모든 에이전트가 그 모델을 사용한다. 재시도 횟수나 요율 제한(요율 제한: 단위 시간당 보낼 수 있는 요청 수를 제한하는 정책)도 이 전역 설정에 두어, 개별 에이전트 코드에 설정을 흩어 넣지 않아도 전체 실행이 같은 정책 아래에서 움직인다.

#4동작 과정

  1. 전역 설정 정의모델 선택, 재시도 정책, 요율 제한, 러너 정책(러너: 에이전트를 실제로 실행시키는 실행기)을 구성 객체에 한 번에 정의한다.
  2. 에이전트 실행 시 적용에이전트가 실행될 때 개별 설정이 없다면 이 전역 구성 값이 기본값으로 적용된다.
  3. 설정 변경 반영구성을 바꾸면 코드를 고치지 않아도 이후 실행부터 새 정책이 전체에 일관되게 적용된다.

프로덕션 운영에서 모델 선택과 재시도·요율 제한·러너 정책 같은 전역 동작을 한곳에서 정하는 SDK 구성 영역

9단계 모달리티와 고급 운영 — 음성·샌드박스·배포

커스텀 핸드오프 필터·프롬프트·서드파티 어댑터·SQLAlchemy 세션 메모리 등으로 SDK 기능을 확장하는 인터페이스다.

#1문제 상황

기존 방식에서는 에이전트 간 전환(핸드오프: 한 에이전트가 대화를 다른 에이전트에게 넘기는 것) 규칙이나 프롬프트의 동작을 바꾸려면 SDK 내부 코드를 고쳐야 했다. 또 세션 메모리를 저장하려면 기본 저장소만 사용해야 해서, 외부 데이터베이스를 쓰고 싶은 경우에는 직접 연동 코드를 작성해야 했다. 이렇게 내부를 건드려야 하는 방식은 SDK가 업데이트되면 수정한 부분이 깨질 위험이 있고, 기능을 더하는 것 자체가 어려웠다. 정해진 기능만 쓰는 한계를 넘어 확장하기 어려운 것이 기존 방식의 문제였다.

#2핵심 질문

SDK 내부를 고치지 않고 핸드오프 규칙·프롬프트·메모리 저장소를 자유롭게 확장하려면 어떻게 해야 할까?

#3동작 예시

서드파티 어댑터와 확장은 공개된 인터페이스(인터페이스: 외부 기능을 붙이기 위해 SDK가 미리 열어 둔 연결 지점)를 통해 기능을 끼워 넣는 방식이다. 예를 들어 핸드오프 필터를 커스텀으로 구현해, 기본 전환 규칙 대신 내가 만든 규칙으로 에이전트가 어느 에이전트로 넘어갈지 결정하게 한다. 세션 메모리도 SQLAlchemy(파이썬에서 데이터베이스를 다루는 도구 모음) 기반 어댑터를 끼워 넣어 외부 데이터베이스에 대화 상태를 저장할 수 있다. SDK 내부 코드는 그대로 두고, 밖에서 구현한 기능을 연결만 하는 구조다.

#4동작 과정

  1. 확장 구현원하는 동작(커스텀 핸드오프 필터, 커스텀 프롬프트, SQLAlchemy 세션 메모리 등)을 SDK가 정의한 인터페이스에 맞춰 구현한다.
  2. 연결 지점에 등록구현한 확장을 에이전트나 실행 설정의 해당 연결 지점에 끼워 넣는다.
  3. 실행 시 적용에이전트가 실행될 때 기본 동작 대신 등록된 확장이 사용되어, 원하는 동작이 그대로 수행된다.

#5한 줄 요약

커스텀 핸드오프 필터·프롬프트·서드파티 어댑터·SQLAlchemy 세션 메모리 등을 공개된 연결 지점을 통해 SDK에 끼워 넣는 확장 인터페이스

9단계 모달리티와 고급 운영 — 음성·샌드박스·배포

세션 식별자로 대화 상태를 자동 영속화해 여러 실행에 걸쳐 같은 맥락으로 이어서 수행하게 하는 실행 통합 메커니즘이다.

#1문제 상황

기존 방식에서는 에이전트 실행이 끝나면 대화 상태가 모두 사라졌다. 사용자가 대화를 이어가려면 다시 시작할 때 이전 대화 내용을 프롬프트에 수동으로 넣어 주거나, 별도 코드로 대화 기록을 저장하고 불러와야 했다. 이것은 실행을 새로 시작할 때마다 맥락(맥락: 이전 대화에서 쌓인 주제·결정·정보)이 끊기는 문제를 만들었고, 여러 실행에 걸쳐 같은 대화를 이어가는 것이 번거롭고 오류가 생기기 쉬웠다. 상태 유지를 직접 처리해야 하는 것이 기존 방식의 한계였다.

#2핵심 질문

여러 번의 실행에 걸쳐 같은 대화 맥락을 자동으로 이어가려면 어떻게 해야 할까?

#3동작 예시

지속형 실행 통합은 세션 식별자(세션 ID)만 지정하면 대화 상태를 자동으로 저장하고 복원한다. 사용자가 같은 세션 ID로 다시 실행을 시작하면, 시스템이 이전 실행에서 저장한 대화 상태를 꺼내 그 위에 새 대화를 이어 붙인다. 예를 들어 첫 실행에서 세 개의 질문을 주고받았다면, 두 번째 실행은 그 질문·답변 내용을 기억한 채 네 번째 대화부터 시작한다. 대화 상태를 저장하는 코드를 직접 쓸 필요가 없다.

#4동작 과정

  1. 세션 시작과 영속화세션 ID가 지정된 첫 실행이 시작되고, 대화 상태가 저장소에 자동으로 기록된다.
  2. 다음 실행에서 복원같은 세션 ID로 새 실행이 시작되면 저장된 대화 상태를 자동으로 불러온다.
  3. 맥락 이어 수행불러온 맥락 위에 새 입력을 더해 같은 대화로서 이어서 수행하고, 결과를 다시 저장한다.

#5한 줄 요약

세션 식별자로 대화 상태를 자동 영속화해 여러 실행에 걸쳐 같은 맥락으로 이어서 수행하게 하는 실행 통합 메커니즘
