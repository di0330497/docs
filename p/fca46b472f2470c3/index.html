AWS KMS가 해결하는 문제와 서비스 범위

암호화 키를 직접 만들고 보관·교체하는 부담을 AWS 관리형 서비스에 맡겨, 키 생성·사용·접근 통제·감사를 한곳에서 처리하게 해주는 서비스다.

#1문제 상황

기존에는 조직이 암호화 키를 직접 생성하고 저장하며 정기적으로 교체하고, 누가 언제 어디서 키에 접근했는지 직접 감시해야 했다. 키를 잃어버리거나 손상되면 암호화된 모든 데이터를 복구할 수 없었고, 키가 유출되면 암호화의 의미가 없어진다. 키 관리는 단순하지만 오류가 치명적인 작업이었다.

#2핵심 질문

암호화 키 생성, 저장, 교체, 접근 제어, 감시를 모두 직접 하지 않고 AWS가 관리해주는 서비스가 있을까?

#3동작 예시

AWS KMS(Key Management Service)는 조직의 계정 안에서 암호화 키를 생성하고, 그 키를 보안 하드웨어 안에 저장한 후, 애플리케이션의 암호화 요청에만 응답하며, 모든 접근 기록을 로그에 남기고, 주기적으로 키를 자동 교체하는 전체 과정을 AWS가 대신 처리하는 서비스다.

#4동작 과정

  1. 키 생성 및 저장조직이 KMS에서 키를 생성하면 AWS가 그 키의 평문을 보안 하드웨어(HSM) 안에만 저장하고 외부로 절대 내보내지 않음
  2. 암호화 요청 처리애플리케이션이 데이터를 암호화해달라고 요청하면 KMS가 내부에서만 연산을 수행하고 암호화된 결과만 반환
  3. 접근 관리 및 감시정책(누가 이 키를 쓸 수 있는지)을 KMS에서 관리하고, 모든 접근을 로그에 남겨 감시 가능

#1문제 상황

#2핵심 질문

대용량 데이터를 빠르게 암호화하면서도 암호화 키의 보안을 유지할 방법이 있을까?

#3동작 예시

  3. 키 보호그 데이터 키를 다시 KMS 마스터 키로 감싸(암호화해) 데이터와 함께 저장하거나 전송

HSM 신뢰 모델 — FIPS 140-3 Level 3와 난수 생성

KMS 키의 평문은 FIPS 140-3 Level 3 검증 하드웨어 보안 모듈 밖으로 절대 나오지 않으며, 키와 난수도 그 안에서 생성된다.

#1문제 상황

암호화 키를 일반 컴퓨터의 메모리나 디스크에만 저장하면 해커가 서버에 접근했을 때 메모리 덤프를 뜨거나 디스크를 읽어 평문 키를 훔칠 수 있다. 소프트웨어만으로는 물리적 접근 공격을 막을 수 없다.

#2핵심 질문

암호화 키의 평문이 서버 소프트웨어에 노출되지 않으려면 어떤 하드웨어가 필요할까?

#3동작 예시

KMS는 FIPS 140-3 Level 3 검증을 받은 하드웨어 보안 모듈(HSM, 물리적 보안 칩)에 암호화 키 평문을 저장한다. 이 칩은 독립된 보안 프로세서로, 키의 평문은 이 칩 내부에만 존재하고 절대 외부로 나가지 않으며, 난수 생성과 모든 암호 연산도 이 칩 안에서만 수행된다.

#4동작 과정

  1. 키 격리 저장KMS 키의 실제 값(평문)은 HSM 칩 안에만 존재하고 네트워크나 소프트웨어를 통해 절대 나가지 않음
  2. 칩 내부 처리암호화/복호화 연산, 난수 생성, 키 로테이션 등 모든 암호 관련 작업을 HSM 칩 내부에서만 수행
  3. 검증된 보안FIPS 140-3 Level 3 인증으로 물리적, 논리적 공격으로부터 보호됨이 독립 기관에 의해 검증됨

#5한 줄 요약

#2핵심 질문

암호화 키와 관련된 민감한 요청을 인터넷을 거치지 않고 AWS와 직접 통신할 방법이 있을까?

#3동작 예시

KMS에 접근하는 경로는 4가지다: AWS 관리 콘솔(웹 UI), AWS CLI(명령줄 도구), 각 프로그래밍 언어의 AWS SDK, 그리고 회사 네트워크 안의 VPC 엔드포인트(인터넷을 우회하는 비공개 채널)다.

#4동작 과정

  1. 공개 경로콘솔, CLI, SDK로 인터넷을 통해 KMS 공개 API에 요청 (보안 인증서로 암호화된 통신)
  2. 비공개 경로VPC 엔드포인트로 회사 네트워크 안에서만 AWS와 연결되어 공개 인터넷을 거치지 않음
  3. 경로 선택보안 요구도, 성능, 네트워크 구조에 따라 조직이 경로를 선택해 사용

KMS 키란 무엇인가 — 논리 자원과 키 소재

KMS 키는 AWS 계정 안의 논리적 자원으로, 메타데이터와 실제 암호 연산에 쓰이는 키 소재를 함께 가리키며 평문 키 소재는 KMS 밖으로 나가지 않는다.

#1문제 상황

AWS에서 리소스를 만들 때 리소스는 두 부분으로 이루어진다: 실제 기능을 하는 부분(예: EC2 인스턴스의 가상 서버 컴퓨팅 자원)과 그 리소스를 관리하기 위한 메타데이터(이름, 태그, 생성 시간, 정책, 설명 등). 이 두 부분은 다르게 저장되고 관리된다.

#2핵심 질문

KMS 키도 관리 정보와 실제 암호화 핵심 정보로 나뉠까?

#3동작 예시

KMS 키는 두 부분이다: 메타데이터(논리 자원)로서 AWS 계정 안의 리소스—이름, 설명, 생성자, 태그, 접근 정책, 생성 날짜, 상태 등을 AWS 관리 콘솔에서 관리할 수 있고, 실제 암호 연산에 사용되는 키 소재(비밀 숫자)는 HSM 칩 안에만 존재해 외부로 절대 나가지 않는다.

#4동작 과정

  1. 논리 자원KMS 키의 메타데이터(이름, ARN, 생성자, 정책, 상태)는 AWS 계정 리소스로 관리되며 콘솔에서 조회·수정 가능
  2. 암호 핵심실제 암호화에 사용되는 키 소재(비밀 값)는 HSM 칩 안에만 저장되고 절대 외부로 노출되지 않음
  3. 분리된 접근메타데이터 관리(누가 이 키를 쓸 수 있나)와 실제 암호화 작업(키를 사용해 데이터 처리)은 분리되어 각각 다르게 통제됨

#5한 줄 요약

KMS 키가 AWS 계정의 논리적 자원(관리 메타데이터)과 HSM 내 격리된 암호 핵심(키 소재)이라는 두 부분으로 나뉘어, 관리와 보안을 동시에 달성하는 것

#1문제 상황

암호화와 복호화를 할 때 서로 다른 키를 쓰면 키 관리가 복잡하고, 프라이빗 키를 항상 안전하게 보관해야 한다는 부담이 생깁니다. 가장 단순하게, 암호화할 때와 복호화할 때 정확히 같은 키를 쓸 수 있다면 키 관리 부담을 줄일 수 있습니다.

#2핵심 질문

암호화와 복호화에 같은 키를 사용하면서도 키 소재가 절대 외부로 노출되지 않도록 보장할 수 있는가?

#3동작 예시

애플리케이션이 데이터를 암호화할 때, KMS에 "이 데이터를 암호화해 줘" 요청을 보내면 KMS는 내부 HSM (보안 전용 칩)에서 256비트 AES-GCM 키를 사용해 암호화를 수행한 후 암호화된 데이터만 돌려줍니다. 나중에 복호화할 때도 같은 방식으로 "이 암호화된 데이터를 복호화해 줘"를 보내면 KMS가 같은 키로 복호화합니다. 키 소재는 항상 KMS 내부에만 머물러 있습니다.

#4동작 과정

  1. 256비트 AES-GCM 키 생성KMS가 HSM 내부에서 안전한 난수 생성기로 256비트 대칭 키를 만듭니다. 생성과 동시에 HSM에 보관되며 절대 외부로 나가지 않습니다.
  2. 암호화 연산애플리케이션이 KMS Encrypt API를 호출하면 KMS는 그 256비트 키를 사용해 데이터를 암호화하고 암호화된 바이너리 데이터만 돌려줍니다.
  3. 복호화 연산나중에 애플리케이션이 KMS Decrypt API를 호출하면 KMS는 저장된 같은 키로 복호화하고 평문 데이터를 돌려줍니다.

HMAC 키

메시지 인증 코드(MAC)를 생성·검증하는 데만 쓰는 대칭 키로, 데이터의 무결성과 진위를 확인한다.

#1문제 상황

데이터가 전송 중에 변조되었는지 또는 누가 보낸 것이 맞는지 확인하려면, 데이터의 무결성과 진위를 검증할 방법이 필요합니다. 일반적인 암호화는 비밀성(누가 봤는지)만 보장하므로, 무결성 검증을 위한 별도 메커니즘이 필요합니다.

#2핵심 질문

암호화하지 않고도 데이터가 변조되지 않았으며 올바른 발신자로부터 온 것임을 증명할 수 있는가?

#3동작 예시

발신자가 256바이트 메시지와 KMS의 HMAC 키를 사용해 GenerateMac API를 호출하면, KMS는 HMAC 계산 결과인 256비트 짧은 코드를 돌려줍니다. 수신자가 같은 메시지와 같은 HMAC 키로 VerifyMac API를 호출하면, KMS가 코드를 재계산해서 일치하는지 확인하고 참/거짓을 돌려줍니다. 경로에서 메시지가 1바이트라도 바뀌면 HMAC 코드도 바뀌므로 위변조를 즉시 감지합니다.

#4동작 과정

  1. HMAC 키 생성KMS가 256비트 대칭 키를 생성하고 HSM에 보관합니다. 이 키는 HMAC 계산에만 사용됩니다.
  2. 메시지 인증 코드 생성발신자가 GenerateMac API로 메시지와 HMAC 키를 제시하면 KMS는 HMAC-SHA256 등의 알고리즘으로 고정 길이 코드를 생성하고 돌려줍니다.
  3. 코드 검증수신자가 VerifyMac API로 같은 메시지와 같은 키를 제시하면 KMS가 재계산한 코드와 일치하는지 비교하고 검증 결과를 돌려줍니다.

퍼블릭 키와 프라이빗 키 쌍으로 이뤄져 암호화 또는 서명 용도로 쓰이는 KMS 키를 만드는 방법.

#1문제 상황

공개 키를 배포하면서 프라이빗 키는 비밀로 유지해야 하는 상황에서, 프라이빗 키를 자신의 서버에만 보관하려고 하면 그 서버가 해킹당하면 프라이빗 키도 노출됩니다. KMS에서 비대칭 키 쌍을 만들면 프라이빗 키를 HSM에 보관하고 공개 키만 배포할 수 있습니다.

#2핵심 질문

공개 키는 외부에 배포하고 프라이빗 키는 KMS 내부 HSM에만 보관하는 비대칭 키 쌍을 KMS에서 어떻게 생성하는가?

#3동작 예시

AWS 콘솔의 KMS에서 "키 생성"을 누르고 키 유형으로 "비대칭"을 선택한 후, 키 사양으로 "RSA_4096" (또는 ECC_SM2, ECC_NIST 등)을 고르고, 키 용도로 "암호화" 또는 "서명"을 선택하면 RSA 4096비트 공개-프라이빗 키 쌍이 생성됩니다. 프라이빗 키는 자동으로 HSM에 보관되고, GetPublicKey API로 공개 키만 내려받아 KMS 밖에서도 암호화나 서명 검증에 사용할 수 있습니다.

#4동작 과정

  1. 비대칭 키 유형과 사양 선택콘솔이나 CreateKey API에서 키 유형을 "비대칭"으로 지정하고, 키 사양으로 RSA-2048, RSA-3072, RSA-4096, ECC_SM2, ECC_NIST 중 하나를 선택합니다.
  2. 키 용도 선택"암호화" (공개 키로 암호화, 프라이빗 키로 복호화) 또는 "서명" (프라이빗 키로 서명, 공개 키로 검증)을 지정합니다.
  3. 키 쌍 생성 및 공개 키 배포KMS가 프라이빗 키는 HSM에 보관하고, GetPublicKey API로 공개 키를 내려주면 그것을 외부 애플리케이션에 배포할 수 있습니다.

메시지가 위조되지 않았음을 검증하는 MAC 값을 생성·확인하는 데 쓰는 대칭 HMAC 키를 만드는 방법.

#1문제 상황

기존에는 메시지가 위조되지 않았음을 검증하기 위해 애플리케이션이 직접 대칭 키를 보관하고 메시지 인증 코드(HMAC, Message Authentication Code)를 계산했습니다. 대칭 키를 애플리케이션 메모리나 설정에 두면, 키가 노출되거나 도용될 위험이 있고, 키를 로테이션할 때도 복잡합니다.

#2핵심 질문

KMS에서 HMAC 키를 만들고 관리하면서 메시지 검증을 KMS에 위임할 수 있을까요?

#3동작 예시

KMS에서 HMAC 키 유형의 대칭 키를 만들면, 애플리케이션은 원본 메시지와 함께 KMS GenerateMac API를 호출하여 HMAC 값을 받습니다. 나중에 메시지를 확인할 때는 GenerateMac으로 다시 HMAC을 만들어 비교하거나, VerifyMac API로 직접 검증을 요청합니다. 키 자체는 애플리케이션에 노출되지 않고 KMS 내부에 보관됩니다.

#4동작 과정

  1. HMAC 키 생성AWS Console이나 CreateKey API로 HMAC 키 유형을 선택하여 새로운 대칭 키를 만듭니다.
  2. 메시지 인증 코드 생성 및 검증GenerateMac API로 메시지의 HMAC 값을 계산하거나, VerifyMac API로 기존 HMAC이 올바른지 검증합니다. 메시지는 KMS로 전송되지만 평문으로만 처리되고 저장되지 않습니다.
  3. 키 관리 및 로테이션HMAC 키도 일반 대칭 키처럼 자동 로테이션 정책을 설정할 수 있으며, 새 버전 키로 이전할 때 기존 HMAC 값 검증은 계속 가능합니다.

#5한 줄 요약

#2핵심 질문

#3동작 예시

KMS 공식 문서의 "Supported operations by key type" 표에서 행은 연산(Encrypt, Decrypt, GenerateDataKey, GenerateMac, Sign, Verify, GetPublicKey, GenerateRandom)이고, 열은 키 유형(대칭, 비대칭 RSA, 비대칭 ECC, HMAC)입니다. 각 셀이 체크되어 있으면 그 조합이 지원됩니다. 예를 들어 GenerateDataKey는 대칭 키에만 가능하고, Sign은 비대칭·HMAC 키에만 가능합니다.

#4동작 과정

  1. 연산 목표 선택해야 할 일을 정합니다(데이터 암호화, 메시지 서명, HMAC 검증, 난수 생성 중 하나).
  2. 매트릭스에서 호환 키 유형 찾기공식 지도에서 목표 연산이 지원되는 키 유형을 확인합니다.
  3. 키 유형에 맞게 API 호출매치하는 키 유형과 함께 해당 KMS API(GenerateDataKey, Sign, GenerateMac 등)를 호출합니다.

Encrypt·Decrypt·ReEncrypt

4KB 이하 작은 데이터를 KMS 키로 직접 암호화·복호화하고, 평문 노출 없이 다른 키로 다시 암호화하는 세 가지 기본 API.

#1문제 상황

기존에는 애플리케이션이 직접 암호화 라이브러리를 사용하여 데이터를 암호화하고 복호화했습니다. 키를 로컬에 보관하면 키 노출 위험이 있었고, 키를 교체할 때는 모든 암호화된 데이터를 새 키로 다시 암호화해야 했는데, 이 과정에서 평문이 잠시 메모리에 노출되거나 데이터 손실 위험이 있었습니다.

#2핵심 질문

KMS가 직접 4KB 이하의 작은 데이터를 암호화·복호화하고, 키 교체 시 평문 노출 없이 암호문을 다시 암호화할 수 있을까요?

#3동작 예시

Encrypt API로 평문 데이터와 키 ID를 넘기면 암호문을 받습니다. Decrypt API로 그 암호문과 같은 키 ID를 넘기면 원문을 복구합니다. 키를 교체하고 싶을 때 ReEncrypt API로 기존 암호문, 기존 키, 새 키를 함께 넘기면, KMS가 내부에서 복호화했다가 새 키로 다시 암호화한 암호문을 반환합니다. 애플리케이션은 평문을 절대 받지 않습니다.

#4동작 과정

  1. 데이터 암호화Encrypt API에 평문과 대칭 키 ID를 넘겨 암호문을 받습니다. 암호화된 데이터와 함께 데이터 키 암호화 컨텍스트(optional)가 반환됩니다.
  2. 데이터 복호화Decrypt API에 암호문을 넘기면 원래 암호화에 쓰인 키를 KMS가 자동으로 찾아 복호화하여 평문을 반환합니다.
  3. 키 교체 시 암호문 재암호화ReEncrypt API에 기존 암호문, 기존 키 ID, 새 키 ID를 넘기면, KMS가 내부에서 복호화 후 새 키로 재암호화한 새 암호문을 반환하므로, 평문이 애플리케이션으로 나오지 않습니다.

#5한 줄 요약

KMS가 작은 데이터(4KB 이하)의 암호화·복호화·재암호화를 직접 처리하여 키를 애플리케이션에 노출시키지 않고, 키 로테이션 시에도 평문을 중간에 노출하지 않도록 하는 것

데이터 키 생성과 봉투 암호화 실행

GenerateDataKey 로 평문·암호문 한 쌍의 데이터 키를 받아 큰 데이터는 로컬에서 암호화하고 데이터 키만 KMS 로 보호하는 봉투 암호화 실행법.

#1문제 상황

기존에는 모든 데이터를 KMS Encrypt API로 암호화하려고 했습니다. 그런데 KMS API는 4KB 크기 제한이 있고, 네트워크 왕복 비용도 크며, API 호출 수에 따라 비용이 증가했습니다. 큰 파일이나 대량의 데이터를 암호화할 때는 성능과 비용 문제가 심각했습니다.

#2핵심 질문

KMS의 보안을 유지하면서 큰 데이터를 로컬에서 빠르고 저렴하게 암호화할 수 있을까요?

#3동작 예시

GenerateDataKey API로 KMS 마스터 키에서 파생된 데이터 키 쌍(평문 키, 암호화된 키)을 받습니다. 애플리케이션은 평문 데이터 키로 큰 데이터를 로컬에서 직접 암호화하고, 암호화된 데이터와 함께 KMS로 암호화된 데이터 키만 저장합니다. 복호화할 때는 Decrypt API로 암호화된 데이터 키를 풀어 평문 데이터 키를 받은 후, 로컬에서 데이터를 복호화합니다.

#4동작 과정

  1. 데이터 키 생성GenerateDataKey API를 KMS 마스터 키와 함께 호출하면, 평문 데이터 키(256비트 대칭 키)와 KMS 마스터 키로 암호화된 같은 키(Encrypted Data Key) 두 가지를 받습니다.
  2. 로컬 암호화애플리케이션이 메모리에 있는 평문 데이터 키를 사용하여(표준 암호화 라이브러리, 예: AES-256 GCM) 큰 데이터를 직접 빠르게 암호화합니다.
  3. 저장 및 복호화암호화된 데이터와 함께 Encrypted Data Key를 저장합니다. 나중에 Decrypt API로 Encrypted Data Key를 풀어 평문 데이터 키를 받은 후, 로컬에서 데이터를 복호화합니다.

#5한 줄 요약

KMS에서 생성한 데이터 키로 로컬 암호화를 수행하여 KMS의 보안 성질은 유지하면서도 크기 제한을 우회하고 성능과 비용을 개선하는 것

데이터 키 페어

공개키·개인키 한 쌍을 KMS 가 만들어 주어 클라이언트 쪽 비대칭 암호화나 서명에 쓰게 하는 데이터 키 페어.

#1문제 상황

기존에는 클라이언트가 필요한 공개키·개인키 쌍을 자체적으로 생성하거나 외부 인증서 저장소에서 가져왔습니다. 이 방식의 문제는 개인키를 안전하게 저장하고 관리하기 어렵다는 것입니다. 개인키가 노출되면 비대칭 암호화의 보안이 무너집니다.

#2핵심 질문

클라이언트 쪽에서 비대칭 암호화나 메시지 서명을 해야 할 때, 안전한 공개키·개인키 쌍을 어떻게 얻고 개인키를 보호할 수 있을까요?

#3동작 예시

KMS에 요청하면 공개키와 개인키 쌍을 생성합니다. 개인키는 KMS 마스터 키로 암호화된 상태로 클라이언트에게 반환되고, 클라이언트는 그 암호화된 개인키를 저장했다가 필요할 때만 KMS로 보내 복호화·사용을 수행합니다. 개인키 평문은 클라이언트가 절대 직접 얻을 수 없습니다.

#4동작 과정

  1. 키 쌍 생성 요청클라이언트가 GenerateDataKeyPair API를 KMS로 호출하면서 어떤 비대칭 알고리즘(RSA 또는 ECC)을 원하는지 지정합니다.
  2. 암호화된 개인키 반환KMS가 공개키와 개인키를 생성한 뒤, 개인키는 KMS의 마스터 키로 암호화해 클라이언트에게 돌려줍니다. 공개키는 평문 그대로입니다.
  3. 클라이언트에서 사용클라이언트는 공개키로는 로컬에서 암호화를 수행하고, 개인키가 필요하면 암호화된 상태의 개인키를 KMS로 보내 복호화 후 사용합니다.

#5한 줄 요약

KMS가 비대칭 암호화용 키 쌍을 생성하고 개인키는 암호화된 상태로만 반환해, 클라이언트가 공개키만 자유롭게 쓰고 개인키는 KMS의 보호 아래서만 사용하도록 하는 관리 방식

#1문제 상황

#2핵심 질문

암호화된 데이터가 특정 사용 맥락에서만 복호화되도록 하고, 다른 맥락에서는 유효하지 않게 만들 수 있을까요?

#3동작 예시

주문 번호와 사용자 ID를 키-값 형태로 암호화 요청에 함께 제출합니다. KMS는 이 데이터를 암호화 과정에 포함시켜 암호문을 만들고, 복호화할 때도 정확히 같은 키-값들을 제시해야 성공합니다. 키-값이 다르면 복호화 실패입니다.

#4동작 과정

  1. 암호화 시 컨텍스트 제공Encrypt API 호출 시에 encryptionContext 파라미터로 주문ID·사용자ID 같은 메타데이터를 딕셔너리 형태로 담아 KMS로 전송합니다.
  2. 컨텍스트가 암호화에 영향KMS는 이 키-값 데이터를 암호화 연산에 포함시킵니다. 같은 평문과 같은 마스터 키여도 컨텍스트가 다르면 다른 암호문이 나옵니다.
  3. 복호화 시 동일 컨텍스트 요구Decrypt API 호출 때 정확히 같은 컨텍스트를 제시해야만 복호화됩니다. 키-값이 하나라도 다르면 거부됩니다.

#1문제 상황

메시지를 전송할 때, 수신자는 그것이 정말 신뢰할 수 있는 발신자가 보낸 것인지 확인할 수 없습니다. 로컬에서 개인키로 서명하려면 개인키를 클라이언트가 직접 가지고 있어야 하는데, 이는 키 노출의 위험이 높습니다.

#2핵심 질문

메시지가 정말 특정 KMS 키의 소유자에 의해 서명되었는지 어떻게 검증하면서, 개인키는 안전하게 보호할 수 있을까요?

#3동작 예시

Sign API로 메시지를 KMS로 보내면, KMS가 비대칭 키의 개인키로 서명을 생성해 클라이언트에게 반환합니다. 클라이언트는 그 서명과 메시지, 그리고 GetPublicKey API로 받은 공개키를 써서 로컬에서 서명을 검증할 수 있습니다. 또는 Verify API로 검증도 KMS에서 수행하도록 할 수 있습니다.

#4동작 과정

  1. 메시지 서명 요청클라이언트가 Sign API를 호출하며 메시지와 비대칭 KMS 키 ID를 전달합니다.
  2. KMS에서 서명 생성KMS가 개인키를 써서 메시지를 서명한 후 서명값을 클라이언트에게 반환합니다. 개인키 평문은 노출되지 않습니다.
  3. 서명 검증클라이언트는 공개키로 로컬에서 검증하거나(GetPublicKey API로 공개키 취득 후), Verify API를 써서 KMS에 검증을 요청합니다.

#5한 줄 요약

개인키를 KMS 내부에만 보관하면서 서명 생성과 검증은 공개키 없이도 가능하게 하는 비대칭 암호 연산

퍼블릭 키 다운로드와 오프라인 연산

비대칭 KMS 키의 공개키를 내려받아 KMS 를 호출하지 않고 로컬에서 암호화·서명 검증을 수행하는 방법.

→ 04-06 참조

#1문제 상황

비대칭 암호화를 할 때마다 KMS API를 호출하면 네트워크 왕복 비용과 레이턴시가 누적됩니다. 특히 고빈도 암호화 연산이 필요한 경우 성능 병목이 됩니다. 공개키는 비밀이 아니므로 클라이언트 로컬에서 다시 받을 필요가 없습니다.

#2핵심 질문

공개키를 미리 받아두면 KMS를 호출하지 않고도 로컬에서 암호화나 서명 검증을 수행할 수 있을까요?

#3동작 예시

GetPublicKey API로 공개키를 내려받아 로컬에 저장합니다. 이후 암호화나 서명 검증이 필요할 때는 그 공개키를 써서 클라이언트 쪽에서 직접 연산을 수행합니다. KMS는 호출되지 않습니다.

#4동작 과정

  1. 공개키 다운로드GetPublicKey API로 비대칭 KMS 키의 공개키를 받아서 클라이언트에 저장합니다.
  2. 로컬에서 암호화 또는 검증클라이언트가 그 공개키를 써서 메시지 암호화나 서명 검증을 로컬에서 수행합니다.
  3. KMS 호출 없음이 과정에서 KMS는 호출되지 않으므로 네트워크 비용과 레이턴시가 절감됩니다.

#5한 줄 요약

공개키의 수학적 성질을 이용해 개인키를 KMS에 남겨두면서 클라이언트 쪽에서 암호화·검증 연산을 독립적으로 수행하는 방식

HMAC 태그 생성·검증과 GenerateRandom

HMAC 키로 메시지 무결성 태그를 만들고 검증하며, KMS HSM 의 난수 생성기로 안전한 랜덤 바이트를 얻는 연산.

#1문제 상황

메시지 무결성을 검사하기 위해 로컬에서 해시 기반 메시지 인증 코드(HMAC)를 만들면, 해시 키를 안전하게 관리하고 저장해야 합니다. 또한 난수가 필요할 때 암호학적으로 안전한 난수를 생성하기 어렵습니다.

#2핵심 질문

KMS가 관리하는 HMAC 키로 메시지 무결성 태그를 안전하게 만들고 검증할 수 있을까요?

#3동작 예시

GenerateMac API로 메시지와 HMAC KMS 키를 보내면 KMS가 HMAC 태그를 생성해 돌려줍니다. VerifyMac API로 메시지·HMAC 키·태그를 모두 보내면 KMS가 검증을 수행합니다. GenerateRandom API로 임의의 길이의 암호학적으로 안전한 난수 바이트를 받을 수 있습니다.

#4동작 과정

  1. HMAC 태그 생성클라이언트가 GenerateMac API로 메시지와 HMAC KMS 키를 KMS로 전송하면, KMS가 HMAC을 계산하여 태그를 반환합니다.
  2. 태그와 메시지 전송클라이언트는 원본 메시지와 HMAC 태그를 함께 보냅니다.
  3. 수신 측에서 검증VerifyMac API로 메시지·HMAC 키·태그를 KMS로 보내면, KMS가 검증을 수행하고 일치 여부를 반환합니다.

메시지 무결성 검증과 안전한 난수 생성을 KMS가 관리하는 키와 HSM 리소스를 써서 수행하는 방식

KMS 권한 모델 개요 — 키 정책·IAM 정책·그랜트

KMS 키를 쓸 수 있는지는 키 정책·IAM 정책·그랜트 세 가지 권한 수단의 조합으로 결정된다.

#1문제 상황

일반적인 AWS 리소스는 IAM 정책으로만 접근을 제어합니다. 하지만 KMS 키는 보안 중요도가 높아서, 단일 정책만으로는 부족합니다. 여러 계층의 정책이 동시에 허용해야만 실제 접근이 가능해야 합니다.

#2핵심 질문

KMS 키를 쓸 수 있는지 없는지는 어떤 규칙들의 조합으로 결정될까요?

#3동작 예시

키 정책(리소스 정책) → IAM 정책(역할·사용자 정책) → 그랜트(임시 권한) 세 가지가 모두 "허용"해야만 API 호출이 성공합니다. 하나라도 거부하면 접근이 차단됩니다. 이를 "정책의 교집합"이라고 부릅니다.

#4동작 과정

  1. 키 정책 검사요청 주체(예: IAM 역할)가 이 KMS 키의 정책에서 필요한 권한을 가지는지 확인합니다. 여기서 거부되면 끝입니다.
  2. IAM 정책 검사요청 주체의 IAM 정책(혹은 그것이 속한 역할의 정책)을 확인해 해당 KMS 작업(예: Decrypt)을 허용하는지 봅니다.
  3. 그랜트 적용 및 최종 승인그랜트(임시·한정적 권한)가 있다면 그것도 함께 검토한 후, 위 세 가지가 모두 허용하면 API 호출이 승인됩니다.

#5한 줄 요약

키 정책 작성·기본 키 정책·변경

키 정책은 KMS 키에 직접 붙는 리소스 정책으로, 그 키에 대한 접근의 출발점이자 필수 관문이다.

#1문제 상황

AWS 리소스마다 권한 언어와 구조가 조금씩 다르고, 대부분은 리소스 정책이 선택사항입니다. KMS는 다릅니다. KMS 키마다 정책이 반드시 있어야 하고, 이 정책 없이는 누구도 그 키를 쓸 수 없습니다.

#2핵심 질문

KMS 키에 직접 붙는 리소스 정책은 어떤 역할을 하고, 왜 반드시 필요할까요?

#3동작 예시

키 정책은 JSON 형식의 리소스 정책으로, "누가 이 키를 어떻게 쓸 수 있는가"를 정의합니다. 키 생성 시 기본 정책이 자동으로 붙으며, 나중에 수정할 수 있습니다. 예를 들어 "루트 계정 전체에 모든 권한 허용" 또는 "특정 IAM 역할에만 Decrypt 허용" 같은 규칙을 설정합니다.

#4동작 과정

  1. 키 생성 시 기본 정책 적용KMS 키를 만들 때 AWS는 자동으로 기본 키 정책을 붙입니다. 보통 루트 계정(키 소유자)에게 모든 권한을 주는 내용입니다.
  2. 필요에 따라 정책 수정PutKeyPolicy API로 권한을 추가하거나 제거합니다. 예를 들어 특정 애플리케이션 역할을 Decrypt 권한으로 추가할 수 있습니다.
  3. IAM 정책과 함께 작동키 정책만으로는 부족하고, IAM 정책과 교집합으로 최종 권한이 결정됩니다.

IAM 정책, AWS 관리형 정책, 서비스 연결 역할

IAM 정책은 사용자·역할 쪽에 붙어 KMS 권한을 부여하며, 키 정책이 IAM 위임을 허용할 때 효력을 갖는다.

#1문제 상황

KMS 키의 접근을 제어하려고 할 때, 처음에는 키 정책(Key Policy)만 사용했습니다. 키 정책은 키 자체에 붙는 정책이므로, 그 정책에 특정 사용자나 역할을 나열하고 권한을 부여하는 방식입니다. 하지만 이 방식은 같은 권한을 여러 키에 설정할 때 각 키마다 정책을 수정해야 하고, 수백 개의 키가 있으면 관리가 매우 복잡해집니다.

#2핵심 질문

사용자나 역할 입장에서 중앙화된 방식으로 KMS 권한을 관리하려면 어떻게 해야 할까요?

#3동작 예시

IAM 정책은 사용자나 역할에 붙는 정책으로, "이 사용자는 어떤 KMS 키에 대해 어떤 행동을 할 수 있는가"를 정의합니다. 예를 들어, 사용자 alice에게 붙인 IAM 정책에 "arn:aws:kms:*:*:key/*에 대해 Decrypt 권한"이라고 쓰면, alice는 조건이 맞을 때 모든 키를 복호화할 수 있습니다.

#4동작 과정

  1. IAM 정책 작성사용자나 역할에 붙일 정책을 작성하고, 그 정책에 KMS 액션(Decrypt, GenerateDataKey 등)과 리소스(키 ARN)를 명시합니다.
  2. 키 정책이 IAM 위임 허용키 정책에서 "root 계정 또는 특정 역할이 이 키 사용을 위임할 수 있다"는 내용이 있어야만, IAM 정책이 효력을 가집니다.
  3. 사용자 요청 평가사용자가 KMS 연산을 요청할 때, AWS는 IAM 정책과 키 정책을 모두 확인하고, 둘 다 허용할 때만 연산을 실행합니다.

#5한 줄 요약

IAM 정책은 사용자나 역할 수준에서 KMS 권한을 중앙화하여 부여하는 방식으로, 키 정책이 IAM 위임을 허용할 때만 효력을 갖습니다.

그랜트 개념 — 수임 주체, 폐기 주체, 그랜트 연산

그랜트는 특정 주체에게 특정 KMS 연산을 임시로 허용하는 가볍고 세밀한 권한 수단이다.

#1문제 상황

KMS 권한을 IAM 정책이나 키 정책으로 관리할 때는 권한을 바꾸려면 정책 문서 자체를 수정해야 하고, 그 변경이 전파되는 데 약간의 시간이 걸립니다. 또한 권한이 영구적이어서, 임시로만 특정 사용자에게 특정 권한을 줄 필요가 있을 때는 정책 수정 후 나중에 다시 되돌려야 하므로 관리가 번거롭습니다.

#2핵심 질문

특정 주체에게 특정 KMS 연산을 짧은 기간 동안만 임시로 허용하려면?

#3동작 예시

그랜트는 CreateGrant API 호출로 생성되는 임시 권한 부여 장치입니다. 예를 들어 EC2 인스턴스가 30분 동안만 특정 키의 Decrypt 권한이 필요하다면, CreateGrant를 호출해 그 인스턴스 역할에 해당 권한을 부여하고, 30분 후 그랜트를 폐기하면 권한이 즉시 제거됩니다.

#4동작 과정

  1. 그랜트 생성CreateGrant를 호출해 주체(GranteePrincipal), 허용할 연산(Operations), 제약 조건(Constraints) 등을 명시하면, AWS가 그랜트 ID와 그랜트 토큰을 반환합니다.
  2. 그랜트 부여반환된 그랜트 ID와 토큰이 해당 주체에게 해당 권한을 임시로 부여함을 의미합니다.
  3. 그랜트 만료필요 없어지면 그랜트를 폐기하거나 철회하여 권한을 즉시 제거합니다.

#5한 줄 요약

그랜트는 IAM 정책이나 키 정책보다 가볍고 세밀하며 임시적인 KMS 권한 위임 수단입니다.

그랜트 만들기와 그랜트 제약

#1문제 상황

그랜트를 만들어 권한을 임시로 부여하되, 그 권한이 모든 상황에서 유효하면 의도하지 않은 사용이 발생할 수 있습니다. 예를 들어 특정 데이터베이스 애플리케이션만 키를 복호화하도록 의도했는데, 그랜트가 제약 없이 발급되면 다른 애플리케이션도 같은 권한으로 복호화할 수 있게 됩니다.

#2핵심 질문

그랜트로 부여한 권한을 특정 암호화 컨텍스트나 조건으로만 유효하게 제한하려면?

#3동작 예시

CreateGrant 호출 시 GrantConstraints 파라미터에 암호화 컨텍스트 조건을 명시합니다. 예를 들어 "암호화 컨텍스트에 Department=Finance가 포함될 때만 유효"라고 제약을 걸면, 그 주체가 복호화 요청할 때 Department=Finance 컨텍스트를 함께 보내야만 권한이 동작합니다.

#4동작 과정

  1. 그랜트 요청 시 제약 명시CreateGrant를 호출할 때 GrantConstraints에 EncryptionContextSubset 또는 EncryptionContextEquals를 지정하고, 조건으로 삼을 컨텍스트 키-값 쌍을 적습니다.
  2. 주체의 요청 시 컨텍스트 포함권한을 사용하는 주체는 Decrypt, GenerateDataKey 같은 KMS 연산을 요청할 때, 그 요청에 암호화 컨텍스트를 포함해 보냅니다.
  3. 제약 평가 및 실행AWS는 요청에 포함된 컨텍스트가 그랜트의 제약과 일치하는지 확인하고, 일치하면 연산을 실행합니다.

#5한 줄 요약

그랜트 제약은 암호화 컨텍스트 기반으로 그랜트 사용을 특정 상황으로만 제한하는 세밀한 제어 장치입니다.

그랜트는 전파에 시간이 걸리므로, 즉시 사용하려면 반환된 그랜트 토큰을 요청에 실어 보낸다.

#1문제 상황

그랜트를 CreateGrant로 생성하면 AWS 내부에서 여러 가용 영역과 시스템에 그 정보를 전파합니다. 이 전파는 보통 매우 빠르지만, 네트워크 지연이나 시스템 부하로 인해 몇십 밀리초에서 몇 초가 걸릴 수 있습니다. 따라서 그랜트 생성 직후 바로 그 권한을 사용하려고 하면 "권한이 없다"는 에러가 발생할 수 있습니다.

#2핵심 질문

그랜트를 방금 만든 직후 즉시 사용하려면?

#3동작 예시

CreateGrant 응답에는 GrantToken이라는 문자열이 포함됩니다. 이 토큰을 이후 KMS 연산(Decrypt, GenerateDataKey 등) 요청의 GrantTokens 파라미터에 실어 보내면, 그랜트 전파를 기다리지 않고 즉시 해당 권한을 사용할 수 있습니다.

#4동작 과정

  1. 그랜트 생성 및 토큰 획득CreateGrant를 호출하고, 응답에서 GrantToken을 추출합니다.
  2. KMS 연산 요청 시 토큰 포함Decrypt, GenerateDataKey 등의 API 호출 시, GrantTokens 파라미터에 방금 획득한 토큰을 배열로 실어 보냅니다.
  3. 토큰 기반 권한 검증AWS는 그랜트 전파 상태와 관계없이 토큰을 검증해 권한을 즉시 부여합니다.

#5한 줄 요약

그랜트 토큰은 그랜트 전파의 지연을 우회하여 생성 직후 즉시 권한을 사용하기 위한 임시 인증 수단입니다.

#2핵심 질문

현재 활성 중인 그랜트를 확인하고, 필요 없는 그랜트를 어떻게 제거할까요?

#3동작 예시

ListGrants를 호출해 특정 키의 모든 현재 그랜트를 조회할 수 있습니다. 조회 결과에는 그랜트 ID, 권한을 받은 주체, 허용된 연산 등이 포함됩니다. 불필요한 그랜트를 찾은 뒤, RetireGrant(주체 주도) 또는 RevokeGrant(관리자 주도)로 제거합니다.

#4동작 과정

  1. 활성 그랜트 조회ListGrants를 호출하고 KeyId를 지정하면, 해당 키에 대한 모든 현재 그랜트 목록이 반환됩니다.
  2. 불필요한 그랜트 식별반환된 그랜트 목록에서 더 이상 필요 없는 그랜트의 ID를 찾습니다.
  3. 그랜트 제거RetireGrant(권한을 받은 주체가 자신의 권한을 반납)나 RevokeGrant(관리자가 다른 주체의 권한을 취소)를 호출해 그랜트를 삭제합니다.

조건 키 — AWS 전역 조건 키와 KMS 조건 키

조건 키는 "어떤 상황에서만 허용"을 정책에 적어 넣어 권한을 정밀하게 좁히는 장치다.

#1문제 상황

IAM 정책이나 키 정책에서 권한을 부여할 때, 그 권한이 모든 상황에서 적용됩니다. 예를 들어 "사용자 alice는 이 키의 모든 권한을 가진다"고 정책을 쓰면, alice가 어떤 IP에서 요청하든, 어떤 시간에 요청하든 권한이 동작합니다. 하지만 실제로는 회사 네트워크 내에서만 접근을 허용하거나, 특정 암호화 컨텍스트에서만 사용을 허용하고 싶을 수 있습니다.

#2핵심 질문

정책 기반 권한에 상황별 제약을 더해 세밀한 접근 제어를 구현하려면?

#3동작 예시

IAM 정책이나 키 정책의 Statement에 Condition 블록을 추가하면, 그 조건이 일치할 때만 권한이 적용됩니다. 예를 들어 Condition 블록에 "aws:SourceIp"를 지정하고 값을 "10.0.0.0/8"이라고 쓰면, 이 IP 범위에서의 요청만 권한이 동작합니다.

#4동작 과정

  1. Condition 블록 작성정책의 Statement에 Condition을 추가하고, 조건 키(예: aws:SourceIp, aws:DateGreaterThan, kms:EncryptionContext)와 그 값을 명시합니다.
  2. 조건 키 선택AWS 전역 조건 키(모든 서비스가 지원)와 KMS 전용 조건 키(KMS만 지원)를 구분해 사용합니다.
  3. 요청 시 조건 평가사용자가 요청할 때, AWS는 요청의 속성(IP, 시간, 컨텍스트 등)과 정책의 Condition을 비교하고, 일치하면 허용, 불일치하면 거부합니다.

#5한 줄 요약

조건 키는 정책 기반 권한에 상황별 제약을 추가하여 IP, 시간, 리소스 태그, 암호화 컨텍스트 등 다양한 기준으로 접근을 제어하는 메커니즘입니다.

ABAC와 RBAC — 태그·별칭으로 접근 제어

키에 붙인 태그와 별칭을 조건으로 삼아, 키 하나하나를 나열하지 않고도 접근을 제어하는 방식이다.

#1문제 상황

정책에서 권한을 관리할 때 리소스를 일일이 ARN으로 나열하거나 역할 이름으로 조건을 지정했습니다. 예를 들어 정책에 "arn:aws:kms:*:*:key/12345678-1234-1234-1234-123456789012와 arn:aws:kms:*:*:key/87654321-4321-4321-4321-210987654321에만 접근"이라고 쓰면, 키가 새로 생길 때마다 정책을 수정해야 합니다. 또한 수백 개의 키를 관리하면 이 방식은 확장성이 떨어집니다.

#2핵심 질문

키를 일일이 나열하지 않고도 리소스의 특성에 따라 유연하게 접근을 제어하려면?

#3동작 예시

KMS 키에 태그(Environment=Prod, Team=Finance 등)나 별칭(alias/finance-key)을 붙이고, 정책의 Condition에서 그 태그나 별칭을 기준 삼아 권한을 설정합니다. 예를 들어 "Team=Finance 태그가 붙은 모든 키에 대해 Decrypt 권한"이라고 정책을 쓰면, 새로운 금융팀 키가 생겨도 그에 같은 태그를 붙이는 것만으로 자동으로 권한이 적용됩니다.

#4동작 과정

  1. 키에 태그 또는 별칭 부여키를 생성하거나 기존 키를 수정할 때, 태그(key-value 쌍) 또는 별칭(이름)을 붙입니다.
  2. 정책에서 태그·별칭 조건 작성IAM 정책이나 키 정책의 Condition 블록에서 조건 키를 지정합니다. 예: "kms:ResourceTag/Team"을 값 "Finance"와 비교하거나, "kms:KeyAlias"를 값 "alias/finance-key"와 비교합니다.
  3. 접근 판단요청이 들어올 때, AWS는 요청 대상 키의 태그나 별칭과 정책의 조건을 평가해 허용 또는 거부를 결정합니다.

#5한 줄 요약

ABAC와 RBAC는 키의 태그와 별칭을 조건으로 활용하여 리소스를 일일이 나열하지 않고도 유연하고 확장성 있게 접근을 제어하는 방식입니다.

교차 계정 접근과 리소스 제어 정책

다른 계정이 내 KMS 키를 쓰려면 키 정책의 허용과 그 계정 IAM 정책의 허용이 모두 필요하다.

#1문제 상황

AWS 계정 A의 KMS 키는 기본적으로 A의 사용자들만 사용할 수 있다. 한 계정의 자원은 다른 계정으로부터 격리되어 있기 때문이다. 하지만 계정 B의 사용자가 계정 A의 KMS 키로 암호화된 데이터를 복호화하거나 자신의 데이터를 암호화해야 할 때도 있다. 이런 상황에서 계정 B는 계정 A의 키에 접근할 수 없다는 한계가 생긴다.

#2핵심 질문

계정 A가 자신의 KMS 키를 계정 B에 특정 용도로만 쓰게 하려면 어떻게 제어할까?

#3동작 예시

계정 A의 KMS 키 정책에서 "계정 B의 이 역할은 암호화·복호화만 할 수 있다"고 명시하고, 계정 B의 IAM 정책에서도 "계정 A의 이 키는 암호화·복호화만 할 수 있다"고 명시할 때 비로소 계정 B에서 그 키를 그 용도로만 사용할 수 있게 된다.

#4동작 과정

  1. 키 정책 수정계정 A가 자신의 KMS 키 정책(Key Policy)을 수정해 계정 B의 특정 주체(사용자, 역할)의 접근을 명시적으로 허용한다. 이 단계에서 어떤 API 연산(암호화, 복호화, 키 메타데이터 조회 등)을 허용할지도 함께 명시한다.
  2. IAM 정책 수정계정 B 내에서 해당 주체(사용자, 역할)의 IAM 정책을 수정해 계정 A의 해당 KMS 키 사용을 명시적으로 허용한다. 이 정책도 같은 수준의 권한 세부사항을 담는다.
  3. 접근 검증계정 B의 주체가 KMS 연산을 시도할 때 AWS는 키 정책과 IAM 정책을 모두 확인한다. 둘 다 그 연산을 허용해야만 실제 접근이 이루어진다.

교차 계정 접근을 설정할 때 보통 필요한 권한보다 더 많이 준다. 예를 들어 "모든 KMS 연산을 허용"처럼 과도한 권한을 설정하곤 한다. 이렇게 하면 권한 설정은 간단해지지만 보안 위험이 커진다. 또한 키 정책과 IAM 정책, 그리고 리소스 기반 정책이 여러 개 겹쳐 있을 때는 실제로 누가 어떤 키에 접근 가능한지 추적이 어려워진다.

#2핵심 질문

최소 권한만 부여하되 복잡한 정책들이 겹쳐 있을 때 실제 유효 권한을 어떻게 판정하고 문제를 해결할 것인가?

#3동작 예시

AWS Policy Simulator 또는 Access Analyzer를 사용하면 특정 주체(사용자, 역할)가 특정 KMS 연산(예: kms:Decrypt)을 특정 키에서 수행할 수 있는지 종합 판정 결과를 보여준다. 도구가 키 정책, IAM 정책, 리소스 기반 정책, 조직 제어 정책 등을 모두 검토해 "허용", "명시적 거부", "기본 거부" 중 하나를 결정한다.

#4동작 과정

  1. 최소 권한 설계역할이나 사용자에게 필요한 최소한의 KMS 연산만 명시하고, 나머지는 거부하는 방식으로 정책을 작성한다. 예를 들어 복호화만 필요하면 kms:Decrypt와 kms:DescribeKey만 허용하고, 키 생성, 삭제, 정책 수정 등은 금지한다.
  2. 유효 권한 판정Policy Simulator나 Access Analyzer 도구에 주체, 연산, 리소스를 입력하면 실제 허용 여부를 판정한다. 도구는 모든 적용 정책을 종합해 최종 판정을 내린다.
  3. 문제 해결판정 결과가 예상과 다르면(예: 허용되어야 하는데 거부됨) 어떤 정책이 블로킹하는지 도구가 보여주고, 관리자는 해당 정책을 수정한다.

키 상태와 상태별 허용 연산, 활성화·비활성화

KMS 키는 Enabled/Disabled/PendingDeletion 같은 상태를 가지며 상태에 따라 허용되는 API 연산이 달라지고, 활성화·비활성화로 키 사용을 즉시 켜고 끌 수 있다.

#1문제 상황

KMS 키는 생성되는 순간부터 존재하지만 그 키의 생명주기 동안 여러 상태를 거친다. 생성된 직후, 어느 시점에 더 이상 필요 없어질 때, 삭제 대기 중일 때 등 각 상태마다 할 수 있는 일이 다르다. 상태를 고려하지 않고 사용하려 하면 API 호출이 실패하거나 의도하지 않은 결과가 생긴다.

#2핵심 질문

KMS 키의 각 상태에서는 어떤 API 연산이 허용되고 어떤 것은 거부될까?

#3동작 예시

Enabled 상태의 키는 암호화(Encrypt), 복호화(Decrypt), 서명, 검증 등 모든 암호화 연산을 수행할 수 있지만, Disabled 상태로 변경하면 이 연산들이 모두 거부되고 DescribeKey 같은 조회나 EnableKey 같은 관리 연산만 가능해진다. PendingDeletion 상태면 거의 모든 연산이 거부된다.

#4동작 과정

  1. Enabled 상태키가 생성되고 기본으로 설정된 상태로, 암호화·복호화·서명·검증 등 모든 암호화 연산이 허용된다.
  2. Disabled 상태DisableKey API로 전환되는 상태로, 암호화 연산은 모두 거부되지만 키 설명, 정책 조회, 키 회전 등 관리 작업은 가능하다. EnableKey로 다시 Enabled 상태로 돌릴 수 있다.
  3. PendingDeletion 상태ScheduleKeyDeletion으로 삭제를 예약할 때 설정되는 상태로, 거의 모든 연산이 거부되며 예약된 삭제 시간이 지나면 키가 영구 제거된다.

#5한 줄 요약

키 회전이 필요한 이유와 회전의 원리

같은 키로 암호화하는 데이터가 쌓일수록 위험이 커지므로 키 머티리얼을 새로 만들어 교체하되, 이전 머티리얼은 남겨 예전 암호문을 계속 복호화할 수 있게 한다.

#1문제 상황

같은 KMS 키로 암호화하는 데이터가 쌓일수록 그 키가 노출되었을 때의 피해 범위가 커진다. 예를 들어 한 키로 10년간 암호화한 모든 데이터가 있다면, 그 키가 도용당하면 10년치 데이터가 모두 노출될 수 있다. 이런 위험을 줄이려면 주기적으로 키를 교체해야 한다.

#2핵심 질문

키를 교체하되 예전 데이터는 계속 복호화할 수 있으려면 어떻게 할까?

#3동작 예시

KMS는 키 회전 시 새로운 암호화 수학 계산에 사용할 키 머티리얼(키 데이터)을 생성하고 이를 기본 버전(active version)으로 지정하며, 이전의 모든 머티리얼은 이전 버전(previous version)으로 보관해둔다. 새로운 암호화는 기본 버전으로 하고, 예전 데이터 복호화는 자동으로 해당 이전 버전을 찾아 사용한다.

#4동작 과정

  1. 새 머티리얼 생성키 회전이 실행되면 KMS가 새로운 키 머티리얼(암호화에 사용할 실제 수학 값)을 생성한다.
  2. 기본 버전 변경이 새 머티리얼이 기본 버전이 되고, 이후 모든 암호화 연산은 이 새 머티리얼을 사용한다.
  3. 이전 버전 보관회전 전의 머티리얼은 이전 버전으로 보관되어 그 머티리얼로 암호화된 데이터의 복호화에만 사용된다. 여러 번 회전되면 여러 이전 버전이 쌓인다.

#5한 줄 요약

새로운 키 머티리얼로 암호화를 전환하면서도 이전 머티리얼들을 유지해 기존 암호문도 계속 복호화할 수 있게 하는 메커니즘

자동 회전 설정과 회전 주기

대칭 암호화 키에 자동 회전을 켜면 KMS가 지정한 주기(기본 1년, 90일~2560일 설정 가능)마다 키 머티리얼을 알아서 교체해 준다.

#1문제 상황

키 회전의 필요성은 이해하지만 수동으로 주기적으로 회전을 관리하기는 번거롭다. 언제 회전했는지 추적해야 하고, 회전 일정을 놓치면 보안 정책 위반이 될 수 있다. 자동화 없이는 운영 부담이 크다.

#2핵심 질문

KMS가 정해진 주기마다 자동으로 키 회전을 실행해줄 수 있을까?

#3동작 예시

대칭 암호화 키(symmetric key)에 자동 회전(automatic rotation)을 활성화하면, KMS가 설정된 회전 주기(기본값 1년)마다 자동으로 새 머티리얼을 생성하고 기본 버전을 바꾼다. 관리자는 처음 한 번만 설정하면 이후로는 KMS가 알아서 처리한다.

#4동작 과정

  1. 자동 회전 활성화키의 자동 회전 설정을 켠다. 대칭 키에만 가능하고, 비대칭이나 HMAC 키는 지원하지 않는다.
  2. 회전 주기 설정회전 간격을 정한다. 기본값은 1년이고, 최소 90일부터 최대 2560일(약 7년)까지 사용자 정의 가능하다.
  3. 자동 회전 실행설정된 주기마다 KMS가 새 머티리얼을 생성하고 기본 버전을 변경한다. 관리자의 개입 없이 자동으로 진행된다.

#5한 줄 요약

대칭 암호화 키에 대해 자동 회전을 설정하면 KMS가 관리자의 수동 개입 없이 지정된 주기마다 키 머티리얼을 자동으로 교체해준다는 것

#1문제 상황

#2핵심 질문

자동 회전과 무관하게 필요한 순간 즉시 회전을 실행하고, 회전 이력을 추적할 수 있을까?

#3동작 예시

RotateKeyOnDemand API를 호출하면 즉시 새 머티리얼이 생성되고 기본 버전이 변경된다. ListKeyRotations API를 호출하면 그 키의 모든 회전 기록(자동, 온디맨드)을 시간순으로 조회할 수 있고, 각 회전의 머티리얼 버전 ID와 타임스탬프를 확인할 수 있다.

#4동작 과정

  1. 온디맨드 회전 실행RotateKeyOnDemand를 호출하면 즉시 새 머티리얼이 생성되고 기본 버전으로 지정된다. 자동 회전 주기와 무관하게 언제든 실행 가능하다.
  2. 회전 이력 조회ListKeyRotations를 호출하면 그 키의 전체 회전 이력이 시간순으로 반환된다. 각 항목은 회전 타임스탬프, 머티리얼 버전 ID, 회전 유형(자동 vs. 온디맨드) 등을 포함한다.
  3. 감시 및 진단이력 데이터를 통해 회전이 정상적으로 진행되는지 감시하고, 문제 발생 시 어느 버전에서 데이터가 암호화되었는지 역으로 추적할 수 있다.

수동 회전 — 새 키로 갈아타기

자동 회전이 안 되는 키(비대칭·HMAC·임포트 키 등)는 새 KMS 키를 만들고 별칭을 옮겨 애플리케이션이 새 키를 쓰게 하는 방식으로 직접 교체한다.

#1문제 상황

자동 회전은 대칭 암호화 키(symmetric key)에만 적용된다. 비대칭 키(asymmetric key), HMAC 키, 외부에서 임포트한 키(imported key) 등은 자동 회전이 불가능하다. 이런 키들도 주기적으로 교체해야 보안을 유지할 수 있다.

#2핵심 질문

자동 회전이 지원되지 않는 키는 어떻게 안전하게 교체할 것인가?

#3동작 예시

새로운 KMS 키를 생성한 후 기존 키에 붙어 있던 별칭(alias)을 새 키로 옮긴다. 애플리케이션이 별칭으로 키를 참조하도록 작성되어 있다면, 별칭 변경만으로 자동으로 새 키를 사용하게 된다. 기존 키는 보관해두어 예전 암호문의 복호화에만 사용한다.

#4동작 과정

  1. 새 키 생성자동 회전이 불가능한 기존 키를 대체할 새로운 KMS 키를 생성한다. 같은 용도의 키 스펙(비대칭, HMAC 등)으로 만든다.
  2. 별칭 이동UpdateAlias API로 기존 별칭을 새 키에 연결한다. 기존 키에서 별칭을 제거하고 새 키에 붙인다.
  3. 애플리케이션 투명한 전환애플리케이션이 키 이름 대신 별칭으로 참조하도록 설계되어 있다면, 별칭 변경 후 코드 수정 없이 새 키를 사용하게 된다. 기존 암호문은 기존 키로 복호화된다.

키의 일생 — 상태·회전·삭제06-06

키 삭제 예약과 대기 기간

KMS 키는 즉시 지울 수 없고 7~30일의 대기 기간을 둔 삭제 예약만 가능하며, 그 사이에는 언제든 취소할 수 있다.

#1문제 상황

기존에는 민감한 리소스를 지울 때 그냥 삭제 명령을 내리면 즉시 없어진다. 하지만 암호화 키는 이미 생성된 데이터를 암호화했기 때문에 키를 잘못 지우면 그 데이터에 접근할 수 없게 된다. 실수로 지운 키로는 이전 데이터를 복호화할 수 없으므로 불가역적인 데이터 손실이 발생한다.

#2핵심 질문

KMS 키를 안전하게 삭제하면서도 실수나 오동작으로 인한 즉시 손실을 막을 수 있을까?

#3동작 예시

삭제 예약은 다음과 같이 진행된다: (1) 삭제 명령 내리기 → 키가 "Pending Deletion(삭제 대기 중)" 상태로 변경, (2) 7~30일 대기 기간 경과, (3) 대기 기간 후 자동 삭제 또는 대기 중에 취소 가능.

#4동작 과정

  1. 삭제 예약 신청키에 대한 삭제 명령을 내리면 KMS는 즉시 지우지 않고 "Pending Deletion" 상태로 표시하며, 7~30일 사이의 기간을 지정한다.
  2. 대기 기간지정된 기간 동안 키는 암호화·복호화 등 어떤 작업도 수행할 수 없고, 이 기간 내 언제든 삭제를 취소하면 키가 원래 상태로 복구된다.
  3. 자동 삭제 또는 취소대기 기간이 지나면 키가 완전히 삭제되거나, 기간이 끝나기 전에 취소하면 키가 사용 가능한 상태로 돌아온다.

삭제 전 사용 여부 확인과 경보

키를 지우기 전 CloudTrail 로그로 최근 사용 흔적을 확인하고, 삭제 대기 중인 키가 사용되면 알려주는 CloudWatch 경보를 걸어 데이터 유실을 막는다.

#1문제 상황

키를 삭제 대기 상태로 두었을 때, 그 키가 실제로 아직 어딘가에서 사용되고 있는지 알 수 없다면 문제가 된다. 옛날 업무 기록이나 외부 서비스 연동 같은 예상 밖의 곳에서 계속 키를 쓰고 있을 수도 있다. 그런 상황을 모르고 키를 지우면 그 서비스들이 갑자기 작동 불능이 되거나 데이터를 복호화할 수 없게 된다.

#2핵심 질문

삭제 대기 중인 키가 어디서 여전히 사용되고 있는지 미리 알고, 문제를 피할 수 있을까?

#3동작 예시

CloudTrail 로그를 조회해 삭제하려는 키가 최근 얼마나 자주 쓰였는지 확인하고, CloudWatch 경보를 설정해 삭제 대기 중인 키가 실제로 호출되면 즉시 알려받는다.

#4동작 과정

  1. 사용 이력 확인CloudTrail(AWS의 모든 작업을 기록하는 서비스)을 통해 삭제 예약된 키가 며칠 전까지 어떤 작업(암호화, 복호화, 서명 등)에 사용됐는지 조회한다.
  2. 경보 설정CloudWatch(AWS 모니터링 서비스)에서 "이 키가 사용되면 알람 발생" 규칙을 미리 설정하면, 삭제 대기 기간 중 누군가 그 키를 사용하려 할 때 즉시 알림을 받는다.
  3. 결과 판단경보가 울린다면 예상치 못한 곳에서 키를 쓰고 있다는 뜻이므로 삭제 취소를 고려하거나 그 서비스를 먼저 새 키로 전환해야 한다.

키 소재 가져오기(BYOK)의 개념과 제약

KMS가 만든 키 대신 내가 외부에서 만든 키 소재를 KMS 키에 넣어 쓰는 방식으로, 백업과 가용성 책임을 사용자가 지는 대신 키 출처를 직접 통제한다.

#1문제 상황

보통 KMS에서는 AWS가 키를 자동으로 생성하고 AWS의 하드웨어 보안 모듈(HSM, 암호화 연산 전용 장비)에서 관리한다. 하지만 일부 조직은 규정상 키의 출처와 생성 과정을 완벽하게 자신들이 통제해야 하고, 외부(AWS 포함) 어떤 서비스도 그 키를 생성하지 못하게 해야 한다는 요구가 있다. 또한 기존에 자신들의 온프레미스 시스템에서 이미 만들어 쓰고 있던 키를 클라우드로 옮기려는 경우도 있다.

#2핵심 질문

AWS KMS가 아닌 외부에서 만든 내 키 소재를 KMS 키에 직접 집어넣어 쓸 수 있을까?

#3동작 예시

BYOK(Bring Your Own Key)는 다음과 같이 작동한다: (1) KMS에서 키 소재 없는 빈 KMS 키 객체를 만든다, (2) 사용자가 자신의 환경에서 암호화 키를 생성한다, (3) 그 키를 안전하게 KMS로 전송해 KMS 키 안에 집어넣는다.

#4동작 과정

  1. KMS 키 준비KMS에서 키 소재를 아직 안 넣은 빈 KMS 키를 생성한다(id 부여, 정책 설정 등은 완료하지만 암호화 연산 불가).
  2. 자체 키 소재 생성사용자는 자신의 환경(온프레미스, 다른 클라우드, 또는 로컬 머신)에서 안전한 난수 생성 방식으로 암호화 키 소재를 만든다.
  3. 안전한 전송 및 삽입KMS가 제공하는 공개 키로 사용자의 키를 암호화한 후 KMS로 업로드하면, KMS가 안전하게 복호화해 키 소재를 저장한다.

키 소재 가져오기 4단계 절차

키 소재 없는 KMS 키 생성 → 래핑 공개 키와 가져오기 토큰 다운로드 → 키 소재 암호화 → 가져오기, 이 네 단계로 진행한다.

#1문제 상황

BYOK를 수행할 때 단순히 "키를 보내면 KMS가 받는다"는 식으로는 보안상 위험하다. 키가 전송 중 탈취되거나 변조될 수 있고, KMS도 정말 사용자가 보낸 키가 맞는지 검증해야 한다. 또한 KMS의 공개 인프라에서 사용자의 개인 키를 안전하게 주고받는 프로토콜이 필요하다.

#2핵심 질문

사용자가 만든 키 소재를 KMS로 안전하게 옮기고 올바르게 삽입하려면 어떤 단계를 거쳐야 할까?

#3동작 예시

4단계 절차: (1) KMS 키 생성, (2) 래핑 공개 키와 가져오기 토큰 다운로드, (3) 다운로드한 공개 키로 사용자 키 암호화, (4) 암호화된 키와 토큰을 KMS로 가져오기.

#4동작 과정

  1. 키 소재 없는 KMS 키 생성사용자가 KMS 콘솔 또는 API에서 "키 소재 없음" 옵션으로 KMS 키를 생성하면, KMS가 암호화 작업은 아직 못 하는 빈 키를 만든다.
  2. 래핑 공개 키와 가져오기 토큰 다운로드KMS가 사용자의 키 소재를 암호화할 때 쓸 공개 키(래핑 공개 키, 이 키로 암호화하면 KMS만 복호화 가능)와 해당 과정을 검증하는 토큰(가져오기 토큰)을 사용자가 다운로드한다.
  3. 키 소재 암호화 및 업로드사용자가 자신의 환경에서 다운로드한 래핑 공개 키로 만든 키 소재를 암호화한 후, 가져오기 토큰과 함께 KMS로 보낸다.

가져온 키 소재의 만료·삭제·재가져오기

가져온 키 소재는 만료 시각을 지정하거나 즉시 삭제할 수 있고, 그러면 키를 쓸 수 없게 되며 같은 소재를 다시 가져와야 복구된다.

#1문제 상황

BYOK로 가져온 키는 일단 KMS 안에 있지만, 일반 KMS 키와 달리 AWS가 백업하지 않는다. 즉, 사용자가 만든 원본 키 소재도 보관해야 하고, KMS에 들어간 복사본도 관리해야 한다. 또한 보안상 키를 일정 시간 후에 자동 무효화하거나, 보안 침해 시 신속하게 키를 비활성화해야 하는 상황이 생길 수 있다.

#2핵심 질문

가져온 키 소재의 유효 기간을 설정하거나 지웠을 때 어떻게 복구할 수 있을까?

#3동작 예시

가져온 키는 다음 세 가지 라이프사이클을 가진다: (1) 만료 시각 지정 — 날짜·시간 설정 후 자동 무효화, (2) 즉시 삭제 — 키 소재를 바로 KMS에서 제거, (3) 재가져오기 — 원본 키 소재를 다시 KMS에 가져와 복구.

#4동작 과정

  1. 만료 설정 또는 즉시 삭제사용자가 가져온 키 소재에 만료 시각을 지정하면 그 시간이 되면 자동 무효화되고, 만료하지 않고 즉시 삭제를 선택하면 KMS에서 키 소재가 바로 제거된다.
  2. 사용 불가 상태키 소재가 없으면 KMS 키 객체는 남아 있지만 암호화·복호화·서명 등 어떤 암호 연산도 수행할 수 없고, 기존에 그 키로 암호화한 데이터도 복호화할 수 없다.
  3. 재가져오기로 복구사용자가 원본 키 소재를 다시 KMS로 가져오면(07-02의 4단계 절차 반복) 키가 다시 작동 가능해지고, 이전 데이터를 다시 복호화할 수 있다.

다중 리전 키 — 기본 키와 복제본 키

여러 리전에서 같은 키 ID와 같은 키 소재를 공유하는 KMS 키 집합으로, 한 리전의 기본 키를 다른 리전에 복제본으로 복사해 만든다.

#1문제 상황

일반적인 KMS 키는 한 AWS 리전(지리적 위치별 데이터 센터)에만 존재한다. 따라서 다른 리전의 서비스에서 그 키로 암호화한 데이터를 복호화하려면 먼저 데이터를 원래 키가 있는 리전으로 옮기거나, 각 리전에서 별도의 키를 만들고 관리해야 한다. 이는 관리 부담이 크고, 키들 사이의 동기화도 복잡하다.

#2핵심 질문

여러 리전에서 같은 키로 데이터를 암호화하고 복호화할 수 있을까?

#3동작 예시

다중 리전 키(Multi-Region Key, MRK)는 하나의 기본 키(Primary Key)와 여러 복제본 키(Replica Key)로 구성되며, 모두 같은 키 ID와 같은 키 소재를 공유한다. 기본 키가 있는 리전에서 복제본을 다른 리전에 복사하는 방식으로 생성된다.

#4동작 과정

  1. 기본 키 생성한 리전에서 다중 리전 키로 표시한 KMS 키를 생성한다(예: us-east-1).
  2. 복제본 키 생성KMS 콘솔이나 API에서 기본 키를 선택해 다른 리전들(예: eu-west-1, ap-southeast-1 등)로 복제하면, 각 리전에 같은 키 ID와 같은 키 소재를 가진 복제본 키가 생성된다.

#1문제 상황

#1문제 상황

CloudHSM은 AWS 계정 내의 AWS 관리 서비스이므로, AWS 인프라 밖의 외부 키 관리 시스템(예: Thales, IBM CloudHSM 등)은 연결할 수 없다. 그런 외부 시스템의 키를 KMS를 통해 사용하려면, AWS와 외부 시스템 사이의 통신 계층이 필요하다.

#2핵심 질문

AWS KMS가 AWS 밖의 외부 키 관리자에 있는 키를 어떻게 사용할 수 있을까?

#3동작 예시

KMS 외부 키 저장소(XKS)는 사용자가 배포·관리하는 XKS 프록시라는 중간 서버를 통해 작동한다. KMS는 암복호화 요청을 프록시로 보내고, 프록시가 실제 외부 키 관리자와 통신하여 연산을 수행한 뒤 결과를 KMS로 반환한다. 프록시는 사용자의 VPC나 온프레미스 환경에 배치할 수 있다.

#4동작 과정

  1. XKS 프록시 배포사용자가 제공한 프록시 소프트웨어(또는 타사 제품)를 VPC나 외부 환경에 설치·구성한다.
  2. 프록시와 외부 키 관리자 연결프록시가 외부 키 관리 시스템의 API와 연결하도록 설정하고, 인증서나 자격증명으로 보안한다.
  3. KMS와 프록시 연결KMS 콘솔에서 XKS 키 저장소를 생성할 때 프록시의 엔드포인트 주소를 등록하면, KMS가 그 주소로 요청을 보낸다.

#2핵심 질문

KMS가 어디에 있는 XKS 프록시에도 도달할 수 있도록 네트워크를 구성하는 방법이 무엇일까?

#3동작 예시

KMS는 두 가지 XKS 프록시 연결 방식을 지원한다: (1) 퍼블릭 엔드포인트 — 프록시가 인터넷에 노출된 퍼블릭 IP를 가지며, KMS가 그 IP로 HTTPS 요청을 보냄. (2) VPC 엔드포인트 서비스 — 프록시가 VPC 내부에 있고, AWS PrivateLink를 통해 KMS가 프라이빗으로 접근하는 방식.

#4동작 과정

  1. 프록시 연결 방식 선택프록시의 위치(온프레미스 vs VPC)와 보안 요구사항에 따라 퍼블릭 또는 PrivateLink 방식을 결정한다.
  2. 프록시 엔드포인트 등록선택한 방식에 맞게 프록시의 주소(퍼블릭 URL 또는 VPC 엔드포인트 서비스 이름)를 KMS에 등록한다.
  3. XKS 키 저장소 생성KMS 콘솔에서 XKS 키 저장소를 생성할 때 프록시 엔드포인트를 입력하면, KMS가 그 주소로 암복호화 요청을 전송한다.

#5한 줄 요약

AWS 서비스가 KMS를 쓰는 방식

S3·EBS 같은 AWS 서비스가 KMS 키로 데이터 키를 받아 저장 데이터를 자동 암호화하는 통합 방식이다.

#1문제 상황

기존에는 데이터를 암호화하려면 개발자가 모든 코드를 직접 작성해야 했습니다. KMS API를 호출해 데이터 키를 받고, 그 키로 데이터를 암호화하고, 복호화할 때 다시 KMS를 호출해 복호화하는 모든 로직을 애플리케이션에 넣어야 했습니다. 실수하기 쉽고, 서비스마다 다시 구현해야 합니다.

#2핵심 질문

AWS의 기존 서비스에 KMS 키를 지정하는 것만으로, 암호화·복호화를 자동으로 처리할 수 있을까요?

#3동작 예시

S3, EBS, RDS 같은 AWS 서비스는 이미 KMS와 통합되어 있습니다. 개발자가 서비스 설정에서 사용할 KMS 키를 지정하기만 하면, 그 서비스는 저장 데이터(S3 객체, EBS 볼륨, RDS 데이터베이스)에 대해 자동으로 KMS를 호출해 데이터 키를 받고, 그 키로 데이터를 암호화한 후 저장하고, 접근할 때 자동으로 복호화합니다.

#4동작 과정

  1. KMS 키 선택 및 지정서비스(S3 버킷, EBS 볼륨, RDS 인스턴스 등)의 암호화 설정에서 사용할 KMS 마스터 키를 선택하고, 서비스에 권한을 부여해 KMS를 호출하게 합니다.
  2. 서비스의 자동 KMS 호출데이터가 서비스에 저장될 때마다, 그 서비스가 내부적으로 KMS의 GenerateDataKey API를 호출해 한 번 쓸 데이터 키를 받고, 그 키로 데이터를 암호화합니다.
  3. 자동 복호화데이터에 접근할 때, 서비스가 저장된 암호화된 데이터 키를 KMS의 Decrypt API로 복호화해 원본 데이터 키를 얻고, 그것으로 데이터를 복호화해 반환합니다. 이 모든 과정이 투명하게 일어납니다.

#1문제 상황

#3동작 예시

#4동작 과정

  1. 키 지정각 서비스 설정 시점에 어떤 KMS 키를 쓸지 선택. EBS는 볼륨 생성 때, EMR은 클러스터 시작 때, Redshift는 데이터베이스 생성 때 지정한다. 이 선택은 돌이킬 수 없고, 그 이후 서비스의 모든 암호화 작업이 지정된 키를 사용.

  3. 접근 제어 통일KMS 키에 붙은 IAM 정책(그 키를 쓸 수 있는 대상을 정하는 규칙)으로 세 서비스 모두의 접근을 한 군데서 관리. "이 역할만 이 키를 쓸 수 있다"는 규칙 하나로 EBS, EMR, Redshift의 암호화 권한을 모두 제어.

SDK 코드로 보는 KMS 기본 흐름

키 생성·암호화·복호화 같은 기본 API 호출을 각 언어 SDK 예제 코드로 따라가 보는 실습 흐름이다.

#1문제 상황

KMS 문서를 읽으면 "API를 호출하세요"라는 말만 나온다. 하지만 실제 코드에서 어떤 함수를 쓰는지, 어떤 입력을 넘기고 어떤 출력이 나오는지 구체적으로 알기는 어렵다. 각 프로그래밍 언어(Python, Java, JavaScript 등)마다 SDK의 세부 사항이 다르고, "키 생성 → 암호화 → 복호화"의 전체 흐름을 한 눈에 보기 어렵다.

#2핵심 질문

KMS SDK의 기본 함수 세 개를 순서대로 호출하면서 실제 키 생성, 암호화, 복호화가 어떻게 작동하는가?

#3동작 예시

Python boto3의 기본 흐름: client.create_key() 호출 → KMS에서 새 키 생성 후 키 ID(arn:aws:kms:...) 반환 → client.encrypt(KeyId='<키ID>', Plaintext=b'hello') 호출 → KMS가 'hello'를 암호화한 바이너리 데이터 반환 → client.decrypt(CiphertextBlob=<암호문>) 호출 → KMS가 자동으로 어떤 키를 썼는지 찾아서 복호화해 원본 'hello' 반환.

#4동작 과정

  1. 키 생성create_key() API를 호출. KMS가 새로운 키를 생성하고 그 키의 고유 식별자(ARN, Amazon Resource Name)를 반환. 이 식별자가 이후 모든 암호화 작업의 대상이 됨.
  2. 데이터 암호화encrypt() 함수에 암호화할 평문 데이터와 키 ID를 넘김. KMS가 그 키로 데이터를 암호화하고 암호문(ciphertext blob이라는 바이너리)을 반환. 이 암호문에는 어떤 키로 암호화했는지 정보도 내장됨.
  3. 데이터 복호화decrypt() 함수에 암호문을 넘김. KMS가 암호문에 내장된 정보로 어떤 키를 썼는지 자동으로 파악하고, 그 키로 복호화해서 원본 평문을 반환. 사용자는 어떤 키를 쓸지 명시할 필요 없음.

표준 SDK 함수 세 개(create_key, encrypt, decrypt)를 순서대로 호출하는 것만으로 안전한 키 생성·암호화·복호화의 전 과정을 KMS에 위임하는 것

검증된 실행 환경만 키를 쓰도록, 요청에 붙은 증명 문서를 KMS가 확인해 주는 기능이다.

#1문제 상황

KMS는 IAM 정책(누가 권한을 가졌는가)만으로 접근 제어를 한다. 하지만 권한이 있는 사용자나 역할이라 해도, 그 요청이 정말 신뢰할 수 있는 환경에서 나왔는지는 확인하지 않는다. 예를 들어 악의적으로 변조된 EC2 인스턴스에서나, 침입당한 일반 서버에서도 권한만 있으면 KMS 키를 요청할 수 있다. 이것은 암호화 키가 악의적 환경에도 노출될 위험이 있다는 뜻.

#2핵심 질문

KMS가 "권한 있는 주체"뿐만 아니라 "안전한 실행 환경"에서만 요청이 나왔음을 검증하려면?

#3동작 예시

Nitro Enclave는 EC2 인스턴스 내부의 격리된 가상 머신으로, 그 안의 코드는 EC2 운영체제나 다른 프로세스로부터 완전히 고립된다. Enclave 내에서 KMS API를 호출할 때, 부착된 NitroTPM(암호화 칩)이 "이 요청은 정확히 이 Enclave의 이 코드에서 발생했다"라는 서명된 증명 문서(attestation document)를 자동 생성. KMS가 이 문서를 검증해서 안전한 환경임을 확인한 후에만 키를 반환.

#4동작 과정

  1. 안전한 환경 구성EC2 인스턴스 안에 Nitro Enclave를 하나 또는 여러 개 실행. KMS와 상호작용할 코드와 시크릿을 오직 그 Enclave 안에만 배포. Enclave 밖의 코드는 그 안의 프로세스에 접근할 수 없음.
  2. 증명 문서 자동 생성Enclave 내의 코드가 KMS로 요청을 보낼 때, 부착된 NitroTPM이 "이 특정 Enclave의 이 특정 코드가 지금 이 요청을 보냈다"는 내용의 서명된 문서를 자동으로 생성해서 요청에 붙임.
  3. KMS 검증과 응답KMS가 도착한 요청의 증명 문서 서명을 검증. AWS의 공개 인증서로 서명이 진정한지 확인하고, Enclave의 코드 해시(fingerprint)가 허용 목록에 있는지 확인. 검증 성공 시만 요청된 키를 반환. 증명이 없거나 위조되면 거부.

#5한 줄 요약

NitroTPM의 암호화 서명 증명 문서로 "이 요청이 안전한 격리 환경에서 나왔다"를 KMS가 수학적으로 검증하고, 검증된 환경하고만 암호화 키를 공유하는 것

KMS 내부 동작 — 도메인·정족수·내구성

HSM 집합을 묶은 도메인과 정족수 서명, 다중 리전 백업으로 키를 잃지 않게 하는 KMS 내부 구조다.

#1문제 상황

KMS 문서는 "당신의 키는 안전합니다"라고만 말한다. 하지만 내부에서 키가 어디에 저장되고, 어떻게 여러 곳에 분산되고, 한 곳이 장애 나도 손실되지 않는지는 설명하지 않는다. 이 불명확함은 "정말 안전한가?", "혹시 한 곳에만 보관되다가 그곳이 해킹당하면?", "재해 상황에 키가 영구 손실되지 않나?"라는 의문을 낳는다.

#2핵심 질문

암호화 키를 여러 HSM(Hardware Security Module)에 분할해서 저장하면서도 어느 하나도 완전한 키를 가지지 못하게 하려면?

#3동작 예시

키 분할의 원리(정족수 서명): 5개 조각으로 나누되, 유효한 연산에는 5개 중 3개 이상이 필요하다는 규칙. 어떤 3개를 조합해도 원래 키를 재구성할 수 있지만, 2개 이하로는 원본을 알아낼 수 없다. 각 조각을 다른 HSM에 저장하면, 3개의 HSM이 협력해야만 암호화가 완성되고, 2개의 HSM을 탈취해도 키는 복구 불가능.

#4동작 과정

  1. 도메인 구성AWS가 같은 지역의 여러 물리 데이터센터에 HSM(암호화 전용 보안 칩)을 배치. 각 HSM이 키의 일부 조각을 저장. 예: 5개 HSM이 도메인을 구성하면, 정족수 규칙에 따라 "5개 중 3개 이상의 협력"으로만 암호화 작동.
  2. 다중 리전 백업같은 키의 조각 세트를 다른 AWS 리전(지역)의 도메인에도 복제. 한 지역이 지진이나 대규모 정전으로 완전히 마비돼도, 다른 리전의 도메인에서 그 키를 복구할 수 있음.
  3. 요청 시 협력암호화나 복호화 요청이 오면, KMS 서비스가 내부적으로 도메인의 여러 HSM과 통신해서 각자의 키 조각을 써서 연산을 완성. 사용자는 이 협력 과정을 보지 못하고, 최종 결과만 받음.

#5한 줄 요약

HSM을 도메인으로 묶고 정족수 서명으로 암호화 키를 분할 보관하며 다중 리전에 백업함으로써, 어느 한 곳도 완전한 키를 소유하지 않으면서도 물리 장애와 재해로부터 강한 내구성을 갖추는 것

보안·컴플라이언스·복원력

데이터 보호, 인증 규격 준수, 장애 대비 복원력 등 KMS 운영을 뒷받침하는 보안 기준 모음이다.

#1문제 상황

암호화 기술과 인증 메커니즘, 내부 도메인 구조만으로는 실제 운영 환경의 요구사항을 충족하기 부족하다. 규제 산업(금융, 의료, 정부)은 "데이터가 정말 보호되었다"를 나중에 증명해야 한다. 또한 운영 실수도 대비해야 한다. "누가 어떤 키를 언제 썼는가"를 기록해야 하고, 실수로 중요한 키를 삭제했을 때 복구할 수 있어야 한다.

#2핵심 질문

암호화·인증·내구성만으로는 부족한 감사·규정 준수·운영 안전을 KMS가 어떻게 지원하는가?

#3동작 예시

CloudTrail(AWS의 API 호출 기록 서비스)과의 연동: KMS에서 일어나는 모든 작업(키 생성, 암호화, 복호화, 키 삭제, 정책 수정 등)이 자동으로 CloudTrail에 기록된다. 기록에는 "누가(ARN), 언제, 어디서(IP), 어떤 키로, 뭘 했는가"가 포함되고, 이는 규제 기관의 감시에 대응하거나 보안 사고 조사 시 증거로 쓰인다. 또한 키 삭제는 즉시 되지 않고 7~30일의 대기 기간을 거친다.

#4동작 과정

  1. 감시와 감사모든 KMS 작업(생성, 암호화, 복호화, 권한 변경, 삭제)이 CloudTrail에 자동 기록된다. 기록은 삭제될 수 없게 보호되며, 규제 기관이 "이 데이터가 정말 암호화되었는가"라고 물었을 때 CloudTrail의 로그를 제시해서 증명.
  2. 실수 방지 메커니즘키를 삭제하려 해도 즉시 지워지지 않는다. 7~30일의 "삭제 예정" 상태를 거친다. 이 기간에 "아, 실수했다"고 알아차리면 삭제 취소 가능. 기간이 만료되어야 영구 삭제되므로 운영 실수로부터 회복 창구 제공.
  3. 표준 준수KMS는 FIPS 140-2(미국 정부 암호화 표준), SOC 2 Type II(감시·감사 표준), PCI-DSS(결제카드 산업 표준) 등을 준수한다. 금융·의료·정부 같은 규제 산업도 믿고 사용 가능.

#5한 줄 요약

CloudTrail 감사, 키 삭제 대기 기간, 국제 암호화 표준 준수를 통합함으로써 데이터 보호와 규정 준수를 동시에 달성하고 운영 실수로부터도 복원력을 갖추는 것
