1쿠버네티스와 EKS의 기초 개념EKS는 쿠버네티스를 대신 운영해 주는 서비스이므로, 무엇을 대신해 주는지 알려면 쿠버네티스의 구성요소와 워크로드 모델이 먼저 서 있어야 한다.52첫 클러스터 만들기와 접속하기이후 모든 실습의 대상이 되는 클러스터가 있어야 하므로, 생성 경로와 접속·엔드포인트·삭제까지 클러스터 자체의 생명주기를 먼저 세운다.73접근 제어: 사람과 워크로드의 권한클러스터가 있어도 권한이 없으면 아무것도 못 하고, 뒤에 나오는 노드·애드온·워크로드가 모두 IAM 역할을 전제로 하므로 여기서 권한 모델을 확정한다.64컴퓨트: 노드를 굴리는 방법Pod가 실제로 돌 자리를 먼저 만들어야 하고, 노드 유형 선택이 이후 네트워킹·스토리지·업그레이드 방식을 모두 좌우한다.95EKS Auto Mode노드를 직접 굴리는 방법을 알고 나야 Auto Mode가 무엇을 대신 해 주고 어디까지 손댈 수 있는지가 비교로 이해된다.66네트워킹노드가 생긴 다음 Pod가 IP를 받고 서로·바깥과 통신해야 하므로, 워크로드를 노출하기 전에 IP 배정과 트래픽 경로를 정리한다.77애플리케이션 데이터 스토리지네트워크가 붙은 다음 상태 유지 워크로드를 올리려면 볼륨이 필요하고, CSI 드라이버 선택은 워크로드 종류에 따라 달라진다.58워크로드 실행과 확장컴퓨트·네트워크·스토리지가 갖춰진 클러스터 위에 실제 애플리케이션을 올리고 부하에 맞춰 늘리는 단계다.49클러스터 확장: 애드온과 EKS Capabilities직접 만든 워크로드 말고 클러스터에 필요한 공통 소프트웨어를 어떻게 설치·유지할지가 정해져야 운영이 지속 가능해진다.610관측과 비용돌아가는 클러스터의 상태를 볼 수 없으면 뒤에 나오는 보안 대응도 업그레이드 판단도 근거가 없다.511보안과 규정 준수권한·네트워크·워크로드가 모두 자리 잡은 뒤라야 무엇을 지켜야 하는지가 구체적이 되고, 운영 이관 전에 반드시 통과해야 하는 관문이다.512버전 업그레이드와 신뢰성클러스터를 오래 운영하면 반드시 마주치는 마지막 관문으로, 앞의 모든 구성요소(노드·애드온·워크로드)를 어떤 순서로 올릴지 아는 것이 목표다.4

2질문 제기

애플리케이션과 실행 환경(라이브러리, 설정)을 하나로 묶어서 어디에서나 같은 상태로 실행할 수 있으면 어떨까?

3구조적 핵심 예시

4단계별 동작 과정

  2. 컨테이너 실행그 이미지를 어느 서버든 실행하면, OS도 라이브러리도 자동으로 격리된 환경에서 구성되고 앱이 시작됩니다.
  3. 쿠버네티스의 역할이런 컨테이너를 수백 개 띄우고 자동으로 배치하고, 장애 나면 다시 띄우고, 서버가 부족하면 더 추가하는 일을 자동으로 해주는 오케스트레이터(조율 시스템)입니다.

Pod는 실행의 최소 단위이고 Deployment·StatefulSet·DaemonSet·Job은 그 Pod를 각각 무상태 복제·상태 유지·노드마다 하나·일회성 작업이라는 목적에 맞게 관리하는 상위 오브젝트다.

1상대의 출발점 확인

컨테이너 한 개를 실행하는 것은 간단하지만, 실제 서비스는 여러 복제본이 필요하고(서버 장애 시 다른 복제본이 요청 처리), 데이터베이스처럼 상태를 유지해야 하는 경우도 있고(복제본들이 같은 데이터 접근), 매 로그인 시 인증서 갱신처럼 각 노드마다 따로 돌아야 하는 작업도 있고(중복 없이), 야간 배치 작업처럼 시작했다 끝나는 작업도 있습니다.

2질문 제기

같은 컨테이너를 다양한 목적(무상태 복제, 상태 유지, 노드마다 하나씩, 일회성 작업)에 맞게 자동으로 관리할 수 있을까?

3구조적 핵심 예시

Pod는 쿠버네티스에서 실행의 최소 단위(보통 컨테이너 하나)이고, 그 Pod를 각 목적에 맞게 관리하는 상위 오브젝트가 Deployment(무상태 웹 서버 복제), StatefulSet(데이터베이스처럼 각 복제본이 고유 정체성·스토리지 필요), DaemonSet(보안 에이전트처럼 모든 노드에 하나씩), Job(배치 작업처럼 일회성)입니다.

4단계별 동작 과정

  1. 오브젝트 선언YAML로 "Deployment로 3개 복제본을 띄워라" 또는 "StatefulSet으로 상태 유지 복제본을 띄워라"고 쿠버네티스에 선언합니다.
  2. 오브젝트가 Pod 관리각 오브젝트는 지정된 Pod 수를 유지하고, 복제본이 죽으면 자동 재시작하고, StatefulSet은 각 Pod에 순서·스토리지 할당, DaemonSet은 모든 노드에 하나씩 배치합니다.
  3. 상태 모니터링컨트롤러 매니저가 계속 현재 상태를 감시해서 선언된 상태와 다르면 자동으로 맞춰줍니다.

3구조적 핵심 예시

EKS는 두 단계 게이트를 사용한다. 첫 번째 게이트는 AWS IAM이다: kubectl이 EKS API 서버로 요청을 보낼 때, AWS SigV4 서명으로 "이 사용자/역할이 정말 AWS 계정에 존재하는가"를 확인한다. 통과하면 두 번째 게이트인 쿠버네티스 RBAC으로 간다: "이 IAM 주체가 이 리소스(Pod, Service, Secret 등)에 이 작업(get, create, delete)을 할 권리가 있는가"를 쿠버네티스가 확인한다.

  1. IAM 인증kubectl 또는 AWS SDK가 요청에 AWS SigV4 서명을 붙인다. API 서버는 이 서명을 AWS에 검증한다. IAM 사용자/역할이 없거나 자격증명이 틀리면 여기서 거부된다.
  2. RBAC 인가IAM 검증을 통과한 요청은 쿠버네티스 내부로 들어온다. RBAC 엔진이 Role, RoleBinding, ClusterRole, ClusterRoleBinding을 읽어서 이 주체가 이 리소스를 이 작업으로 조작할 권리가 있는지 확인한다.
  3. 허용 또는 거부두 게이트를 모두 통과하면 요청이 실행되고, 하나라도 실패하면 거부된다.

2질문 제기

4단계별 동작 과정

  1. 노드 그룹 정의인스턴스 타입, 최소/최대/원하는 노드 개수를 지정하여 관리형 노드 그룹을 만든다.
  2. 자동 프로비저닝과 등록EKS가 EC2 인스턴스를 생성하고 쿠버네티스 에이전트를 자동으로 설치한 후 클러스터에 등록한다.
  3. 무중단 업데이트쿠버네티스 버전이나 AMI를 업데이트하면 EKS가 새 노드를 먼저 띄우고 기존 노드의 파드를 옮긴 후 기존 노드를 제거한다.

  2. Windows 노드 클러스터 지원 활성화EKS 클러스터 생성 시 Windows 노드 지원을 켜고, Windows AMI로 오토스케일링 그룹을 만든 후 클러스터에 등록한다.

1상대의 출발점 확인

EKS에서 Pod를 실행하려면 먼저 EC2 인스턴스를 프로비저닝해야 합니다. 인스턴스 타입을 정하고, 보안 그룹을 설정하고, 필요한 리소스(CPU, 메모리)를 미리 예약해야 합니다. 그런데 실제로 필요한 리소스는 시간대에 따라 변합니다. 저녁 피크 타임에는 많은 리소스가 필요하지만, 새벽에는 거의 필요 없을 수 있습니다. 이렇게 고정 크기의 노드를 미리 예약하면 사용하지 않는 리소스가 낭비됩니다.

2질문 제기

EC2 인스턴스를 전혀 관리하지 않으면서도 Pod를 실행할 수 있을까?

3구조적 핵심 예시

Fargate에서 Pod 요청이 들어오면, 사용자는 Pod에 필요한 CPU와 메모리만 명시합니다. 그러면 AWS가 그 요청에 정확히 맞는 크기의 컴퓨트 환경을 자동으로 할당하고, Pod가 실행을 마치면 그 리소스는 즉시 해제됩니다. 사용자는 노드 같은 개념을 전혀 신경 쓰지 않고 Pod 단위로만 컴퓨트를 소비합니다.

4단계별 동작 과정

  1. Fargate 프로필 정의어떤 Pod들이 Fargate에서 실행될지 지정합니다. Pod의 네임스페이스와 레이블로 선택합니다.
  2. Pod 요청개발자가 Pod 매니페스트에 CPU/메모리 리소스 요청값을 포함해 배포합니다.
  3. AWS 자동 할당 및 실행EKS가 Pod 요청을 감지하고, AWS Fargate 인프라에서 필요한 크기의 리소스를 즉시 할당해 Pod를 실행합니다. Pod 종료 시 리소스는 회수됩니다.

1상대의 출발점 확인

노드가 중단되거나 네트워크가 끊기거나 CPU/메모리가 고갈되면 그 노드에서 실행 중인 Pod들이 기능 불가 상태가 됩니다. 기존에는 운영자가 모니터링 도구로 문제를 감지한 후 수동으로 노드를 교체하거나 복구 작업을 진행했습니다. 이 과정은 지연이 발생하고, 사람이 24시간 감시해야 하며, 실수할 여지가 있습니다.

2질문 제기

노드 장애를 자동으로 감지하고 즉시 대응할 수 있을까?

3구조적 핵심 예시

EKS는 주기적으로(보통 5초마다) 각 노드에 헬스 체크 신호를 보냅니다. 응답이 없거나 비정상 신호가 오면, 그 노드는 '상태 불량(unhealthy)' 으로 표시됩니다. 자동 복구 메커니즘이 그 표시를 감지하면 노드를 즉시 종료하고 새로운 노드로 교체하는 절차를 시작합니다.

4단계별 동작 과정

  1. 지속적 헬스 체크EKS 컨트롤 플레인이 모든 노드의 상태를 주기적으로 확인합니다.
  2. 장애 진단 및 표시응답 불가, CPU/메모리 고갈, 디스크 공간 부족 등 문제를 감지하면 노드를 '상태 불량'으로 마킹합니다.
  3. 자동 복구해당 노드는 자동으로 교체되고, 그 위의 Pod들은 정상 노드로 재스케줄링됩니다.

2질문 제기

파드가 VPC 내의 다른 AWS 자원과 같은 네트워크 대역에서 직접 통신할 수 있을까요?

3구조적 핵심 예시

Amazon VPC CNI는 노드의 ENI(Elastic Network Interface, 네트워크 인터페이스)에 미리 여러 보조 IP 주소를 할당받고, 파드가 생성될 때 이 보조 IP 풀에서 하나를 파드에 직접 할당합니다. 결과적으로 파드는 VPC의 같은 IP 대역에 포함되어 VPC 내의 다른 자원과 직접 통신합니다.

4단계별 동작 과정

  1. IP 사전 할당VPC CNI가 노드 시작 시 그 노드의 ENI에 여러 보조 IP를 미리 할당받습니다. 이 IP들은 파드 생성에 대비한 예비 풀입니다.
  2. 파드 생성 시 IP 할당새 파드가 만들어지면 VPC CNI는 사전 할당받은 IP 풀에서 사용 가능한 IP를 선택해서 그 파드에 할당합니다.
  3. VPC 네이티브 통신파드는 VPC의 IP 주소를 가지므로 RDS, ElastiCache, 다른 노드의 파드와 VPC 보안 그룹 규칙만으로 직접 통신할 수 있습니다.

기존에는 EKS 클러스터의 각 Pod이 EC2 인스턴스의 서브넷에서 IP를 하나씩 받습니다. EC2 인스턴스 타입마다 붙을 수 있는 네트워크 인터페이스와 IP 주소 개수가 정해져 있으므로, 한 노드가 배치할 수 있는 Pod 개수가 제한됩니다. 더 많은 Pod을 실행하려면 노드를 계속 추가해야 합니다.

2질문 제기

3구조적 핵심 예시

기본적으로 각 Pod은 EC2 ENI(네트워크 인터페이스)에서 IP를 받는데, 프리픽스 위임을 사용하면 한 ENI에 연속된 여러 IP(/28 블록)를 한 번에 할당받아 그 안에서 Pod들에게 나눠줍니다.

4단계별 동작 과정

  1. 프리픽스 위임(Prefix Delegation)EC2가 개별 IP 주소 대신 /28 크기의 연속된 IP 블록을 한 번에 받아 노드 내부에서 Pod 여러 개에 분배합니다.
  2. 커스텀 네트워킹VPC CNI 설정을 바꿔 Pod의 네트워크 인터페이스가 EC2의 기본 서브넷이 아닌 별도의 보조 서브넷에서 IP를 받도록 합니다.

  3. 마운트생성된 스토리지가 Pod의 지정된 경로에 마운트되어 애플리케이션이 파일 시스템처럼 읽고 쓸 수 있습니다.

기존에는 Pod이 노드의 임시 로컬 스토리지만 사용할 수 있으므로 데이터가 노드에 종속됩니다. 노드를 교체하거나 재부팅하면 그 데이터는 손실됩니다. 또한 노드의 스토리지 용량이 부족하면 새 Pod을 배치할 수 없습니다.

3구조적 핵심 예시

EBS 블록 스토리지는 Pod 전용 디스크처럼 동작하며 Pod이 삭제되어도 데이터가 유지되고, 인스턴스 스토어는 노드에 물리적으로 붙은 매우 빠른 로컬 디스크이지만 노드가 중단되면 데이터가 사라집니다.

  3. 사용 분류데이터 영구성이 필요하면 EBS, 임시이면서 초고속 성능이 필요한 캐시나 임시 데이터는 인스턴스 스토어를 사용합니다.

하위 항목명

1상대의 출발점 확인

Pod이 노드의 로컬 스토리지나 EBS 볼륨을 사용하면 그 스토리지는 특정 노드나 가용 영역에만 존재합니다. 여러 Pod이 동시에 같은 데이터에 접근하려면 각각 복사본을 유지하거나 별도 데이터베이스를 써야 하는데, 이는 일관성 유지와 관리가 복잡합니다.

2질문 제기

여러 Pod과 여러 가용 영역에서 동시에 같은 파일을 읽고 쓸 수 있는 공유 스토리지를 어떻게 제공할까요?

3구조적 핵심 예시

EFS는 NFS 프로토콜을 사용하는 관리형 파일 시스템으로, AWS가 여러 가용 영역에 걸쳐 자동으로 복제하고 확장성을 보장합니다. EKS의 EFS CSI 드라이버는 이 EFS를 쿠버네티스의 PersistentVolume으로 노출하여 Pod이 마치 로컬 파일시스템처럼 접근할 수 있게 합니다.

4단계별 동작 과정

  1. EFS CSI 드라이버 설치EKS 클러스터에 EFS CSI 드라이버 애드온을 설치하면 쿠버네티스가 EFS를 스토리지 백엔드로 인식합니다.
  2. PersistentVolume 선언매니페스트에서 EFS 파일 시스템 ID를 지정한 PersistentVolume을 만들면, Pod이 마운트할 수 있는 스토리지 리소스가 준비됩니다.
  3. Pod이 마운트하여 사용Pod의 매니페스트에서 PersistentVolumeClaim으로 이 볼륨을 요청하면, 어느 노드에서나 어느 가용 영역에서나 같은 파일시스템에 접근할 수 있습니다.

2질문 제기

S3, FSx, File Cache 같은 다양한 스토리지 백엔드를 쿠버네티스 Pod에서 일관되게 사용하려면 어떻게 할까요?

3구조적 핵심 예시

CSI 드라이버는 특정 스토리지의 특성을 쿠버네티스 PersistentVolume 인터페이스로 번역합니다. S3 Mountpoint용 CSI 드라이버는 S3 버킷을 마운트 포인트로 노출하고, FSx용 드라이버는 Lustre나 NetApp 파일시스템을 노출합니다.

4단계별 동작 과정

  1. 스토리지별 CSI 드라이버 설치클러스터에 S3, FSx, File Cache 드라이버를 설치하면 각 스토리지 종류가 PersistentVolume으로 사용 가능해집니다.
  2. 매니페스트에 스토리지 선언PersistentVolume에서 S3 버킷 이름이나 FSx 파일시스템 ID를 지정하면 쿠버네티스가 그 리소스에 접근할 권한을 설정합니다.
  3. Pod이 마운트하여 활용Pod이 PersistentVolumeClaim으로 요청하면 스토리지가 마운트되어 파일시스템처럼 또는 객체 저장소처럼 접근됩니다.

5본질 요약

EKS 애드온의 개념과 지원 등급

CoreDNS·kube-proxy·VPC CNI 같은 클러스터 운영 소프트웨어를 EKS가 대신 설치·패치해 주는 관리형 패키지이며, AWS 제공 애드온과 마켓플레이스 파트너 애드온으로 나뉜다.

1상대의 출발점 확인

EKS 클러스터를 만들 때 CoreDNS(DNS 해석 서비스), kube-proxy(네트워크 트래픽 라우팅), VPC CNI(AWS 네트워크 연결)처럼 클러스터가 제대로 작동하려면 반드시 필요한 소프트웨어들이 있습니다. 애드온이 없을 때는 개발자가 이런 소프트웨어들을 직접 설치하고, 쿠버네티스 버전이 올라갈 때마다 수동으로 업데이트하고, 취약점이 발견되면 보안 패치를 적용해야 했습니다. 이 과정에서 호환되지 않는 버전을 설치하면 클러스터가 불안정해지거나, 업데이트를 놓치면 보안 위험에 노출됩니다.

2질문 제기

클러스터 필수 소프트웨어를 매번 수동으로 관리하지 않고 자동으로 설치하고 최신 상태로 유지할 수 있을까요?

3구조적 핵심 예시

4단계별 동작 과정

  1. Pod 정책 설정Pod Security Standards를 적용해 파드가 root로 실행되거나 특권 모드로 띄워지는 것을 차단한다.
  2. RBAC 최소화각 서비스 계정과 사용자가 꼭 필요한 쿠버네티스 리소스(Pod, Service, Secret 등)에만 접근하도록 Role과 RoleBinding을 정의한다.
  3. 네임스페이스 격리팀별로 네임스페이스를 나누고, 네트워크 정책으로 파드 간 통신을 제한하며, 리소스 쿼터로 CPU와 메모리 사용량을 팀별로 한정한다.

5본질 요약

2질문 제기

3구조적 핵심 예시
