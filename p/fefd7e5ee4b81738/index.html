개발자가 애플리케이션을 컨테이너로 패키징해 만들고 실행·배포·운영하는 법을 한 경로로 묶는다. 대상(컨테이너·이미지·데몬) → 실습 환경 → 이미지 → 빌드(Dockerfile/BuildKit/Buildx/Bake) → 실행·저장·네트워크·로그 → 다중 서비스(Compose) → 배포 자동화·공급망 보안(Scout) → 다중 노드(Swarm)와 도구 확장. Engine 29 의 기본 저장 백엔드가 containerd 이미지 스토어로 바뀐 점과 Compose v2·v5 구분을 현재 기준으로 삼는다.

1Docker가 다루는 대상과 구조이후 모든 명령과 파일이 조작하는 대상(컨테이너·이미지·데몬)을 먼저 정해 두어야 그 뒤의 조작법이 의미를 갖는다.52설치와 CLI 첫걸음아는 것과 해 보는 것은 별개 기술이다. 실습 환경을 만들고 CLI 문법을 끝내야 이후 모든 명령이 재현 가능하다.53이미지와 레지스트리빌드와 실행의 결과물인 이미지가 어디에 오고 가는지를 알아야 그 다음의 빌드·배포 단계가 의미를 갖는다.64컨테이너 실행과 수명주기이미지를 아는 것과 이미지를 실행해 보는 것은 다르다. 컨테이너의 상태 전이와 실행 파라미터를 여기서 익힌다.55이미지 빌드 — Dockerfile레지스트리에서 받는 이미지를 만드는 법이 Dockerfile 이다. 레이어 구조를 이해해야 캐시·크기·보안 논리가 성립한다.76BuildKit 과 BuildxDockerfile 을 실제로 실행하는 엔진이 BuildKit 이고 그것을 조종하는 CLI 가 Buildx 다. 멀티 플랫폼·원격 빌드 같은 한계가 여기서 풀린다.67데이터 저장컨테이너는 휘발된다. 데이터를 어디에 두느냐가 곧 배포 설계가 되므로 마운트 종류와 저장 백엔드를 함께 다룬다.48네트워킹컨테이너를 서로 그리고 바깥과 잇는 방법이다. 게시 방식과 드라이버 선택이 곧 보안 설정이 된다.59로깅과 관측 가능성돌아가는 컨테이너의 안을 보려면 로그와 지표가 먼저다. 데몬 운영과 문제 해결도 같은 틀에서 다룬다.510Docker Compose컨테이너 하나로는 애플리케이션이 되지 않는다. 여러 컨테이너를 파일 하나로 정의해 함께 다룬다면이 여기서 나오고, 파일 형식의 세부 규칙이 뒤따라온다.811배포 자동화와 공급망 보안만든 이미지를 반복적으로 안전하게 배포하려면 레지스트리 운영·CI 연결·공급망 검증이 함께 필요하다. 기능 추가와 보안을 분리하지 않는다.712다중 노드 운영과 도구 확장단일 데몬의 한계를 넘어 분산 실행과 도구 확장을 다루는 마지막 단계. 오케스트레이션으로 넘어가기 직전의 지점이다.5

1단계 Docker가 다루는 대상과 구조

가상머신이 자체 커널까지 통째로 담는 것과 달리, 호스트 커널을 공유한 채 프로세스·파일시스템·네트워크만 격리해 훨씬 가볍게 뜨는 실행 단위.

1문제 상황

서버마다 앱을 띄우려면 운영체제 환경까지 통째로 복제해 옮겨야 했다. 가상머신은 각 머신마다 커널과 운영체제를 그대로 담기 때문에 이미지 하나가 수십 GB까지 불어나고 부팅에도 분 단위가 걸리며, 한 서버에 수십 개만 함께 올릴 수 있었다. 필요한 서비스 하나를 실행하는 대신 운영체제 전체를 유지·보수하는 비용이 그대로 따라붙었다.

가상머신이 사용자에게 주는 것은 결국 커널까지 통째로 옮긴 무게감 있는 환경 하나다. 이 부담을 줄이지 않고도 서로 간섭하지 않는 독립 실행 단위를 만들 수 있을지, 그리고 그 단위를 얼마나 빨리 만들 수 있을지가 관건이다.

2핵심 질문

커널까지 통째로 복제하지 않고도 서로 간섭하지 않는 독립 실행 단위를 가볍게 만들 수 있을까?

3동작 예시

어떤 서버에 웹 서버와 데이터베이스를 함께 올린다고 하자. 컨테이너를 쓰면 두 앱은 호스트의 리눅스 커널을 공유한 채 프로세스 목록·파일시스템·네트워크 인터페이스만 따로 갖는다. 앱이 자기 파일시스템 밖의 경로를 보거나 다른 컨테이너의 프로세스를 볼 수 없어 물리 머신 분리 없이도 간섭하지 않는다. 부팅 단계가 없어 시작과 삭제가 즉시 끝나고, 이미지는 앱과 의존성만 담아 수십 MB 수준이다.

4동작 과정

  1. 격리 영역 만들기컨테이너가 시작될 때 프로세스 목록, 파일시스템 루트, 네트워크 인터페이스를 각각 독립된 영역으로 나눠 준다. 앱이 볼 수 있는 것은 자기 프로세스와 자기 파일시스템, 연결된 네트워크뿐이다.
  2. 자원 상한 설정하기컨테이너별로 사용할 수 있는 CPU와 메모리 상한을 지정한다. 상한을 넘으면 그 컨테이너만 영향을 받고 같은 호스트의 다른 컨테이너는 계속 실행된다.
  3. 실행 단위 올리기준비된 이미지를 읽기 전용 계층 위에 얹고 그 위에서 컨테이너 하나를 시작한다. 컨테이너를 삭제하면 남은 데이터가 함께 사라지고, 같은 이미지로 다시 즉시 만들 수 있다.

5한 줄 요약

커널은 공유하고 프로세스·파일시스템·네트워크만 분리해, 즉시 뜨고 지울 수 있는 독립 실행 단위를 제공하는 것

개발자 컴퓨터에서는 잘 돌아가는 코드가 운영 서버에서는 다른 운영체제, 다른 라이브러리 버전, 다른 설정 파일을 만나 자주 깨졌다. 개발자는 그 차이를 하나씩 맞춰 다시 설치하고 설정을 고치는 과정을 반복했고, 같은 코드가 어디서 왜 실패했는지 추적하는 데 시간이 더 쓰였다. 서버마다 설치 절차를 손으로 적어 두는 방식은 결국 환경 차이의 원인이 되었고, 재현 가능한 상태를 어디에도 남기지 못했다.

즉 문제는 코드가 아니라 코드를 실행하는 주변 환경이 매번 조금씩 다르다는 점이다. 이 환경을 어떻게면 코드가 아니라 하나의 산출물로 다룰 수 있을지 정해지지 않았다.

2핵심 질문

3동작 예시

4동작 과정

  1. 요청 전달하기docker CLI가 소켓(클라이언트와 데몬이 통신하는 통로)을 통해 요청을 보낸다. CLI는 요청을 전달하고 응답을 출력하는 역할만 맡으며 직접 컨테이너를 만들지 않는다.

  2. 엔진 패키지 설치하기패키지 관리자로 docker-ce(클라이언트와 데몬이 묶인 엔진 패키지), docker-ce-cli, containerd.io, 빌드와 Compose 플러그인을 함께 설치한다. 데몬은 부팅 시 자동 시작되도록 등록되며, 소켓 권한 설정을 바꾸면 docker 그룹에 속한 사용자도 관리자 권한 없이 명령을 쓸 수 있다.

1문제 상황

docker 명령은 관리 명령과 하위 명령이 많고, 그 결과를 사람이 읽는 표 형태로 보여 주는 방식을 기본으로 삼고 있다. 사람이 화면에서 확인하는 용도로는 괜찮지만, 이 값을 스크립트에서 다른 명령에 넘기거나 파일로 저장하려고 하면 그대로 쓸 수 없다. 문법 형태를 다시 다른 도구로 변환하는 코드를 매번 작성해야 했고, 명령마다 어떤 형태가 나올지 외워야 해서 실수도 반복됐다.

2핵심 질문

3동작 예시

4동작 과정

  1. 명령 구조 읽기모든 명령은 docker [관리 명령] [하위 명령] [옵션] [인자] 순서로 읽는다. docker image ls 는 관리 명령이 image, 하위 명령이 ls 다. 옵션은 보통 -- 형태의 긴 이름과 - 형태의 짧은 이름을 함께 쓴다.
  2. 동작 바꾸는 옵션 선택--detach 나 -d 처럼 명령의 동작 자체를 바꾸는 옵션이 있고, -it 처럼 입출력을 연결하는 옵션이 있다. 어느 위치에 써도 되는 것은 아니고 해당 명령이 정의해 둔 자리에만 쓴다.
  3. 출력 형태 지정--format 에 Go 템플릿 문법 문자열을 주면 각 결과 객체에서 원하는 필드만 골라 출력한다. 지정하지 않으면 엔진이 정한 기본 표가 나오고, 지정하면 그 문자열이 결과를 모두 대체한다.

2핵심 질문

3동작 예시

4동작 과정

  1. 파일과 실행 정보 모으기베이스 이미지를 고르고, 그 위에서 필요한 패키지와 파일을 설치·복사하고, 기본 실행 명령과 환경변수, 작업 디렉터리를 기록한다. 이 과정이 끝난 결과가 이미지의 한 상태다.
  2. 읱 전용 템플릿으로 저장만들어진 묶음은 태그 이름을 붙여 저장한다. 태그는 이름의 기본값인 latest 를 쓰거나 1.2 처럼 직접 정한다. 내용은 수정하지 않고, 새로운 변화는 새 이미지로 만든다.
  3. 컨테이너의 출발점으로 사용컨테이너를 만들 때 이미지를 지정하면 그 묶음이 그대로 복사되어 출발 상태가 된다. 이후 컨테이너 안에서 추가 설치나 파일 수정은 이 이미지를 건드리지 않고 컨테이너 안에서만 일어난다.

4동작 과정

2핵심 질문

3동작 예시

사용자 이름 myuser 아래에 저장소 webapp을 하나 만들고, 그 안의 latest, v1.2.0, v1.3.0 같은 태그가 각각 이미지 한 벌을 가리킵니다. myuser/webapp:v1.2.0으로 한 이미지를, myuser/webapp:v1.3.0으로 그 다음 이미지를 밀어 넣으면 두 버전이 같은 저장소 안에 나란히 남고, latest는 새로 밀어 넣은 이미지를 가리키도록 다시 붙입니다.

4동작 과정

  1. 저장소 생성사용자 또는 조직을 정하고 그 아래 저장소 이름(namespace/이름)을 만든다. 여기 올라가는 이미지들이 전부 이 저장소 안에서 태그 단위로 구분된다.
  2. 태그 생성과 이동태그는 이미지 한 벌을 가리키는 이름이다. 같은 태그로 다시 밀어 넣으면 그 태그가 가리키는 대상이 새 이미지로 바뀌고(기존 태그는 다른 이름으로 미리 옮겨 두고), 여러 태그를 하나의 이미지에 동시에 붙일 수도 있다.
  3. 태그 정리저장소 안의 태그 목록을 보고 필요 없는 태그를 선택해 지운다. 실제 이미지 데이터까지 함께 정리하려면 저장소 사용량 확인 후 정리 명령을 함께 쓴다.

Docker Hub에서 공식 이미지와 검증된 배포자를 신뢰의 기준으로 삼고, 이미지 안의 알려진 취약점(CVE)을 스캔해 확인하는 것입니다.

1문제 상황

Docker Hub에서 이미지를 받을 때는 태그 이름만 보고 어느 것을 쓸지 결정합니다. 하지만 태그 이름은 아무나 붙일 수 있고 내부 내용은 바뀔 수 있어서, 공식 이미지인지 누가 만든 이미지인지 확인할 단서가 없습니다. 게다가 이미지가 담고 있는 OS 패키지에는 이미 알려진 취약점이 들어 있는 경우가 많은데, 그것을 직접 추적하지 않으면 그대로 배포됩니다.

2핵심 질문

어떤 이미지를 믿고 써도 안전한지 판단하고, 그 안에 이미 알려진 취약점이 있는지를 어떻게 확인합니까?

3동작 예시

docker pull nginx를 하면 Docker Hub는 이 이름이 공식 Docker Library가 관리하는 공식 이미지인지, Docker Trusted Publisher나 Docker Scout이 검증한 배포자가 만든 이미지인지 표시해 줍니다. 그리고 이미지를 스캔해 layers에 포함된 OS 패키지 이름과 버전을 CVE 데이터베이스와 대조해, 어떤 취약점이 몇 개 있는지를 목록으로 보여 줍니다.

4동작 과정

  1. 소스 구분Docker Hub는 공식 이미지, Docker Verified Publisher가 배포한 이미지, 일반 사용자가 만든 이미지를 구분해 표시한다. 베지어 수나 다운로드 수 같은 값은 소스 자체를 증명하지는 않으므로 설치 문서와 배포자 정보를 함께 확인한다.
  2. 취약점 스캔이미지의 각 layer에 들어 있는 패키지 이름과 버전을 추출해 CVE 데이터베이스와 대조한다. 이미 존재하는 취약점만 비교하므로 아직 공개되지 않은 문제는 잡아내지 못한다.
  3. 판단과 대응스캔 결과에서 심각도 높은 항목부터 확인해, 해당 패키지를 고친 새 이미지를 빌드해 다시 올리는 방식으로 대응한다. 검사 결과를 팀 안에서 지켜보는 기준선으로 삼을 수도 있다.

5한 줄 요약

이미지의 출처를 신뢰 기준으로 삼고, 내부 패키지 대 CVE 데이터베이스를 대조해 알려진 취약점을 확인하는 것

컨테이너 수명주기와 자동 시작

컨테이너는 생성(create)·시작(start)·정지(stop)·삭제(rm) 같은 상태를 거치며, 재시작 정책을 지정해 두면 데몬이 다시 뜨거나 예기치 않게 끝난 뒤에도 컨테이너가 알아서 다시 시작된다.

1문제 상황

컨테이너는 만들어지고 실행되다가 끝나면 그 상태로 남습니다. 서버가 재부팅되거나 데몬이 죽었다 되살아나면 예전에 실행해 둔 컨테이너는 시작된 채로 방치되거나 반대로 꺼진 채로 남아, 매번 사람이 다시 띄워 줘야 합니다. 그리고 이때 같은 설정으로 다시 띄우려면 명령어와 옵션을 그대로 다시 입력해야 합니다.

2핵심 질문

컨테이너를 필요한 상태로 만들고, 예기치 않게 끝나도 같은 설정으로 알아서 다시 시작되게 하려면 어떻게 합니까?

3동작 예시

docker run -d --name web --restart unless-stopped nginx를 한 번 실행하면 컨테이너가 백그라운드로 계속 돌고, 설정이 그대로 기록됩니다. 이후 컨테이너가 어떤 이유로 끝나면 데몬이 다시 조건을 확인해 컨테이너를 자동 시작하고, 사용자가 직접 docker stop web으로 끈 경우에는 자동으로 되살리지 않습니다.

4동작 과정

  1. 생성과 시작create로 설정만 저장된 stopped 상태의 컨테이너를 만들고 start로 실행한다. run은 이 둘과 이미지 받기를 한 번에 처리하고, -d를 주면 백그라운드로 두어 명령이 바로 반환된다.
  2. 정지와 삭제stop은 SIGTERM을 보내 잠시 뒤 SIGKILL로 강제 종료하고, rm은 컨테이너 설정과 로깅된 볼륨을 지운다. kill은 SIGTERM을 생략하고 곧바로 강제 종료한다.
  3. 자동 시작 정책--restart에 no, on-failure[:n], always, unless-stopped 중 하나를 지정한다. 데몬이 재시작하거나 컨테이너가 예기치 않게 끝났을 때 이 조건에 따라 다시 시작하며, 스케줄러가 다루는 swarm 모드 전용 정책도 따로 있다.

5한 줄 요약

컨테이너를 생성·시작·정지·삭제 상태로 다루고, 재시작 정책으로 예기치 않은 종료 뒤에도 같은 설정으로 자동 시작되게 하는 것

컨테이너 기본값 덮어쓰기

이미지에 미리 들어 있는 기본값(실행 명령, 환경변수, 작업 디렉터리, 사용자 등)을 docker run 옵션으로 덮어써서 컨테이너를 원하는 설정으로 바꾸어 실행하는 것.

1문제 상황

이미지에는 실행 명령, 환경변수, 작업 디렉터리, 실행 사용자 같은 기본값이 이미 들어 있습니다. 이 값을 바꾸려면 이미지 자체를 고쳐 다시 빌드해서 다시 푸는 과정이 필요했습니다. 환경만 다른 설정까지 이미지에 섞이면 이미지 개수가 늘어나고, 그때그때 무엇을 바꿨는지 알기도 어려워집니다.

2핵심 질문

이미지를 고쳐 다시 만들지 않고 실행할 때마다 기본값을 바꿔 컨테이너를 원하는 설정으로 뜨려면 어떻게 합니까?

3동작 예시

docker run -e NODE_ENV=production -w /srv/app -u 1000:1000 myimage를 실행하면 이미지에 들어 있던 NODE_ENV, 작업 디렉터리, 실행 사용자가 모두 이 실행에만 적용되는 값으로 바뀝니다. 이미지에 있던 값이 없으면 docker run에서 준 값이 그대로 쓰이고, 이미지에 있던 값이 있으면 그 자리에 덮어씁니다. 바뀐 것은 컨테이너 하나에만 적용되고 이미지 자체는 그대로입니다.

4동작 과정

  1. 엔트리포인트와 커맨드 덮어쓰기docker run 이미지 커맨드로 이미지 기본 커맨드를 바꾸고, --entrypoint로 ENTRYPOINT(컨테이너 첫 프로세스를 정하는 설정) 자체를 교체한다. 인자만 넘겨 CMD를 뒤에 덧붙이는 것도 가능하다.
  2. 환경변수와 사용자·디렉터리 덮어쓰기-e로 환경변수를 지정하거나 -e KEY로 이미지에 있는 값을 그대로 가져오고, -u로 사용자·그룹을, -w로 작업 디렉터리를, --user 같은 방식으로 권한을 바꾼다. 사용자 설정은 Dockerfile의 USER보다 나중에 적용된다.
  3. 기타 설정 덮어쓰기-p로 포트, -v로 볼륨, --workdir 관련 항목과 --network·--dns 같은 네트워크 설정을 지정한다. 이 값들은 컨테이너의 config 파일에 기록되어 컨테이너 단위로만 유효하다.

5한 줄 요약

이미지 기본값은 그대로 둔 채 docker run 옵션으로 실행에 필요한 값만 덮어써 컨테이너를 설정하는 것

컨테이너 안에서 여러 프로세스

컨테이너는 기본적으로 프로세스 하나만 첫 프로세스로 돌지만, supervisord 같은 프로세스 관리자를 안에서 띄워 여러 프로세스를 함께 관리하고 시그널로 정리할 수도 있다.

1문제 상황

컨테이너는 하나의 프로세스만 전제로 설계되어 있습니다. 컨테이너 하나에서 웹서버와 데이터베이스를 함께 띄우려면 docker exec로 하나씩 손으로 붙여야 하고, 데몬 재시작이나 컨테이너 재시작 시 이 프로세스들은 따라오지 않습니다. 또한 docker stop은 첫 프로세스(PID 1)에게 시그널을 보내므로, 안에 있던 나머지 프로세스가 정리되지 않고 남는 경우도 생깁니다.

2핵심 질문

컨테이너 안에서 여러 프로세스를 함께 띄우고, 하나가 죽으면 함께 정리되며, 컨테이너 종료 시 나머지도 순서대로 정리하려면 어떻게 합니까?

3동작 예시

supervisord를 컨테이너 안에서 첫 프로세스로 실행하고, 웹서버와 큐 워커를 설정 파일에 프로세스로 등록합니다. 메인 프로세스인 supervisord가 자식 프로세스들을 관리하므로, 워커 하나가 죽으면 설정된 횟수만큼 다시 띄우고, 컨테이너가 정지될 때에는 supervisord가 시그널을 받아 자식들에게 같은 시그널을 전달한 뒤 마지막에 스스로 종료합니다.

4동작 과정

  1. 프로세스 관리자 실행컨테이너를 만들 때 실행 명령을 프로세스 관리자(supervisord 등) 실행으로 지정하고 그 안에서 돌릴 프로그램들을 설정 파일에 나열한다. Dockerfile에서는 ENTRYPOINT나 CMD를 관리자 실행 명령으로 지정한다.
  2. 여러 서비스 관리supervisord는 자신의 자식으로 각 프로그램을 띄우고 상태를 기록한다. 프로세스가 죽으면 설정된 재시작 횟수와 정책에 따라 다시 실행하며, supervisorctl로 상태를 조회하고 콘솔 출력을 확인한다.
  3. 시그널 전파와 종료컨테이너에 docker stop이 들어오면 시그널이 PID 1인 supervisord에 전달된다. 프로세스 그룹을 만들어 자식에게도 같은 시그널을 보내고, supervisord가 stopsignal에 지정된 시그널을 스스로 받아 종료 순서를 정리한 뒤 마지막에 종료한다.

5한 줄 요약

컨테이너 안에서 프로세스 관리자를 첫 프로세스로 띄워 여러 프로세스를 함께 관리하고 시그널로 순서대로 정리하는 것

리소스 제한과 상태 점검

메모리와 CPU 사용량에 상한을 걸어 컨테이너 하나가 호스트 자원 전체를 독점하지 않게 하고, 그 제한과 실행 상태를 stats·healthcheck 같은 명령으로 확인하는 것.

1문제 상황

기본 설정에서는 컨테이너가 호스트 자원을 사실상 제한 없이 씁니다. 한 컨테이너의 메모리 사용이 치솟거나 CPU를 계속 점유하면 같은 호스트의 다른 컨테이너와 데몬까지 영향을 받습니다. 그리고 지금 컨테이너가 얼마나 쓰고 있는지는 알 수 없어, 문제가 생기기 전에 어느 컨테이너가 병목인지 파악하기 어렵습니다.

2핵심 질문

컨테이너 하나가 메모리와 CPU를 너무 많이 쓰지 못하게 상한을 걸고, 지금 각 컨테이너가 얼마나 쓰는지 확인하려면 어떻게 합니까?

3동작 예시

docker run --memory=512m --cpus=1.5 myimage로 컨테이너를 띄우면 메모리를 512MB로, CPU를 1.5개 코어로 제한합니다. 실행 중에는 docker stats가 메모리·CPU 사용량을 주기적으로 보여 주고, HEALTHCHECK로 지정한 상태 점검 명령이 주기적으로 성공과 실패를 판정해 healthy와 unhealthy로 표시됩니다.

4동작 과정

  1. 상한 설정docker run에 --memory(메모리), --memory-swap(메모리+스왑), --cpus(CPU 비중), --cpu-shares(상대 가중치)를 주고, --blkio-weight, --pids-limit 같은 값으로 블록 I/O와 프로세스 수를 함께 제한한다. docker update로 실행 중인 컨테이너에도 바꿀 수 있다.
  2. 실사용량 확인docker stats로 현재와 누적 CPU·블록 I/O·네트워크·메모리 사용량을 보고, docker ps로 상태와 NPROC(프로세스 수), SIZE, 네트워크, 마운트 정보를 함께 확인한다. docker system df는 이미지·컨테이너·볼륨·빌드 캐시 단위의 점유를 보여 준다.
  3. 상태 점검HEALTHCHECK로 지정한 명령이 주기적으로 실행되어 성공할 때 healthy, 실패할 때 unhealthy가 된다. 상태는 시작 후 잠깐 starting을 거쳐 표시되고, 상태는 컨테이너의 중지가 아니라 오류 exit status와 구분된다.

5한 줄 요약

메모리와 CPU 상한으로 컨테이너가 호스트 자원을 독점하지 못하게 걸고, stats와 healthcheck로 제한과 실행 상태를 확인하는 것

Docker 객체 메타데이터와 정리

컨테이너·이미지·볼륨 같은 Docker 객체에 라벨이라는 키-값 정보를 붙여 분류와 필터링을 하고, 쓰이지 않는 객체는 prune 명령으로 지워 디스크를 정리하는 것.

1문제 상황

컨테이너와 이미지, 볼륨이 쌓일수록 어떤 것이 어떤 용도인지 이름만으로는 알 수 없고, 만든 사람이 누구인지도 남지 않습니다. 그래서 나중에 정리하려면 하나씩 실행해 확인해야 하고, 안 쓰는 오래된 이미지와 컨테이너, 볼륨이 디스크를 계속 차지합니다. 서버마다 따로 실행한 환경도 어느 정도 동일한지는 재현하기 어렵습니다.

2핵심 질문

Docker 객체에 메타데이터를 붙여 분류·필터링하고, 쓰이지 않는 객체만 골라 디스크를 어떻게 정리합니까?

3동작 예시

docker run -l env=prod -l team=pay nginx로 컨테이너를 만들면 env=prod, team=pay라는 키-값이 컨테이너 설정에 함께 기록됩니다. 나중에 docker ps --filter label=env=prod로 이 두 정보를 기준으로 컨테이너만 골라 볼 수 있고, docker image prune은 어떤 컨테이너에서도 쓰이지 않는 이미지를 골라 지웁니다.

4동작 과정

  1. 라벨 붙이기docker run --label key=value로 컨테이너를 만들 때 붙이고, docker build의 Dockerfile에 LABEL 지시문을 넣어 이미지·볼륨에도 남긴다. 값이 없는 키는 빈 문자열로 저장된다.
  2. 라벨로 필터링docker ps, docker images 같은 목록 명령에 --filter label=key=value를 줘서 조건에 맞는 객체만 본다. 값만 지정하면 해당 값을 가진 객체가, 키만 지정하면 그 키가 있는 객체가 나온다.
  3. 정리 명령 실행쓰지 않는 이미지·네트워크·캐시를 docker image prune, network prune, builder prune으로 지우고, 모든 대상을 한 번에 없애는 docker system prune을 쓴다. 각 명령에 -a나 --volumes를 붙이면 멈춘 컨테이너와 쓰이지 않는 볼륨까지 포함되며, -f를 주면 확인 없이 즉시 지운다.

5한 줄 요약

Docker 객체에 키-값 라벨을 붙여 분류·필터링하고, 쓰이지 않는 객체만 골라 prune 명령으로 지우는 것

빌드 개념: Dockerfile과 빌드 컨텍스트

Docker 빌드는 Dockerfile 의 지시문을 위에서 아래로 실행해 이미지를 만드는 과정이며, 이때 Dockerfile 과 함께 빌더로 전송되는 파일 묶음을 빌드 컨텍스트라고 부른다.

1문제 상황

이미지는 여러 층을 쌓아서 만들어지는데, 층 하나를 쌓을 때마다 전체를 처음부터 다시 만들어야 하면 같은 작업을 계속 반복하게 된다. 그래서 어떤 식으로 이미지를 구성할지 매번 사람이 직접 판단해 적어 두고, 빌드 도구에 넘기는 형식이 따로 정해져 있지 않았다.

또 빌드가 참고할 소스나 설정 파일이 조금만 있어도 빌드에 넘기려면 저장소 전체를 통째로 전달해야 했다. 전송에 시간이 걸리고, 빌드 로그에는 필요 없는 파일까지 잔뜩 드러났다.

2핵심 질문

이미지를 구성하는 지시문을 적은 파일과, 그 지시문이 실제로 필요로 하는 파일 묶음을 어떻게 정해 한 번에 전달할 수 있는가?

3동작 예시

애플리케이션 서버 이미지를 만든다고 하자. Dockerfile에는 베이스 이미지와 패키지 설치, 내 코드 복사 명령이 적혀 있고, 이 빌드에 필요한 파일은 소스 코드와 의존성 목록 파일뿐이다. 빌드 도구는 이 Dockerfile을 읽고 실행하면서, 함께 넘겨받은 파일 묶음에서 소스 코드만 찾아 복사한다.

4동작 과정

  1. 지시문 실행빌드 도구가 Dockerfile을 위에서 아래로 한 줄씩 읽어 실행한다. 각 줄이 끝날 때마다 이미지에 레이어 하나가 추가된다.
  2. 컨텍스트 전송빌드를 시작할 때 Dockerfile과 빌드 컨텍스트, 즉 빌드에 필요한 파일 묶음을 빌더로 한 번에 전달한다. 용량이 크면 이 전송 구간에서 시간이 가장 많이 든다.
  3. 결과 기록모든 지시문이 끝나면 레이어를 쌓은 결과물이 이미지로 만들어지고, 각 지시문별로 실행 시간과 결과가 기록된다.

5한 줄 요약

Dockerfile이라는 지시문 파일과 빌드 컨텍스트라는 파일 묶음을 빌더로 보내고, 지시문을 순서대로 실행해 이미지를 쌓는 것

Dockerfile 지시문

Dockerfile 은 FROM·RUN·COPY 같은 지시문으로 이미지 구성 방법을 적는 텍스트 파일이며, 각 지시문은 앞선 단계 위에 레이어 하나씩을 쌓아 이미지를 만든다.

1문제 상황

이미지를 만들 때 필요한 OS 패키지 설치, 소스 코드 복사, 환경 변수 설정 같은 작업이 늘 같은 순서로 반복되는데, 이 순서를 매번 사람이 기억해 명령으로 직접 실행해야 했다. 실행할 때마다 어느 버전의 도구를 썼는지, 어느 파일을 복사했는지 기록도 남지 않았다.

그 결과 같은 이미지를 만들 때마다 결과물이 조금씩 달랐고, 무엇보다 이미지 안의 내용이 왜 이렇게 됐는지 설명해 주는 파일이 없다.

2핵심 질문

이미지를 구성하는 과정을 순서대로 적은 텍스트 파일 하나로, 같은 명령을 반복 실행하지 않고 이미지를 재현할 수 있게 하는 것은 무엇인가?

3동작 예시

FROM ubuntu:24.04 로 시작하고 WORKDIR /app 을 지정한 다음 COPY . . 으로 소스를 복사하고 CMD ["python", "app.py"] 를 적으면, 빌드 도구는 이 네 줄을 순서대로 실행해 Ubuntu 위에 소스가 들어 있는 실행 가능한 이미지를 만든다. 중간에 RUN apt-get install 를 하나 더 넣으면 그 위에 레이어가 하나 더 쌓인다.

4동작 과정

  1. 베이스에서 시작FROM 으로 지정한 이미지를 출발점으로 삼고, 그 위에 계속 쌓아 나간다. WORKDIR 이나 ENV 같은 지시문은 여기서 컨테이너의 작업 디렉터리와 환경 변수를 정한다.
  2. 파일과 명령 반영COPY·ADD 가 빌드 컨텍스트에서 파일을 가져와 레이어에 담고, RUN 이 패키지 설치나 코드 실행 같은 작업을 수행한다. 각 지시문은 앞선 레이어 위에 새 레이어 하나를 만든다.
  3. 기본 동작 지정CMD·ENTRYPOINT·EXPOSE 가 컨테이너 시작 시 실행할 기본 명령과 노출할 포트를 정해, 빌드된 이미지가 실제로 뜰 때의 동작을 결정한다.

5한 줄 요약

FROM·RUN·COPY 같은 지시문으로 이미지 구성 과정을 텍스트 파일에 적어 두고, 이를 순서대로 실행해 레이어를 쌓는 것

다단계 빌드와 베이스 이미지

다단계 빌드는 Dockerfile 안의 FROM 단계를 여러 개로 나눠, 빌드 도구만 든 단계는 버리고 실행에 필요한 최소 파일만 담은 베이스 이미지 기반 최종 단계를 남기는 방식이다.

→ 03-02 참조

1문제 상황

어떤 이미지를 만들려면 컴파일러나 패키지 관리 도구 같은 빌드 도구가 필요한데, 그런 도구를 이미지에 넣어 두면 그 크기만큼 그대로 배포본에 남는다. 이미지 크기가 커지고, 필요 없는 도구 때문에 관리해야 할 대상도 늘어났다.

배포에는 실행에 필요한 최소한만 들어 있으면 되는데, 빌드 도구와 실행에 필요한 파일을 한 이미지 안에서 분리할 방법이 없었다. 빌드 도구를 빼고 나면 다시 빌드 자체가 불가능해지는 구조였다.

2핵심 질문

빌드에 필요한 도구는 쓰되 최종 이미지에는 남기지 않고, 실행에 필요한 최소한의 파일만 담은 이미지를 만들 수 있는가?

3동작 예시

Go로 작성한 서비스를 이미지 안에서 컴파일한다고 하자. 첫 번째 FROM 단계에서는 golang 이미지를 골라 소스를 빌드해 실행 파일 하나를 만들어 낸다. 두 번째 FROM 단계에서는 경량 이미지인 alpine 을 다시 시작하고, 앞 단계에서 만든 실행 파일만 복사해 넣는다. 첫 단계의 컴파일러와 중간 산출물은 최종 이미지에 포함되지 않는다.

4동작 과정

  1. 빌드 단계FROM 으로 컴파일러와 패키지 도구가 있는 이미지를 고르고, 소스를 복사해 실행 파일 같은 산출물을 만들어 낸다. 이 단계의 결과는 다음 단계로 넘기는 용도로만 쓰인다.
  2. 최종 단계새로운 FROM 으로 실행 환경만 있는 작은 이미지를 다시 시작하고, 앞 단계의 산출물만 COPY 로 복사한다. 여기서 지정하지 않은 파일은 이 단계에 존재하지 않는다.
  3. 중간 단계 제외마지막 단계를 제외한 모든 중간 단계는 최종 이미지 구성에 쓰이지 않아 결과에서 빠진다. --target 으로 어느 단계까지를 결과로 삼을지 직접 고를 수도 있다.

5한 줄 요약

빌드 도구가 있는 단계와 실행에 필요한 최소 파일만 담은 단계를 분리해, 빌드 도구는 쓰되 최종 이미지에는 남기지 않는 것

빌드 변수와 빌드 시크릿

빌드 변수는 ARG·ENV 로 빌드 시점에 값을 받아 Dockerfile 을 재사용하게 하고, 빌드 시크릿은 RUN --mount=type=secret 으로 비밀값을 이미지 기록 없이 빌드 중에만 제공하는 기능이다.

1문제 상황

서로 다른 환경에서 같은 애플리케이션을 빌드할 때 버전이나 접속 주소 같은 값이 달라져야 하는데, 값마다 Dockerfile을 복사해서 따로 관리했다. 값이 늘어날수록 여러 파일이 갈라져 어느 것이 최신인지 알기 어려웠다.

반대로 값을 Dockerfile 안에 그대로 적어 두면, 그 값이 이미지 기록과 저장소 양쪽에 그대로 남아 나중에 이를 회수해 빌드 로그나 이미지 히스토리에서 그대로 볼 수 있었다.

2핵심 질문

값이 달라지는 빌드마다 같은 Dockerfile을 재사용하면서, 빌드 시점에 값을 주입하고 그 값이 이미지에 남지 않게 할 수 있는가?

3동작 예시

ARG VERSION 으로 빌드 시점에 받을 값을 선언하고, docker build --build-arg VERSION=2.1.0 을 붙여 실행하면 해당 빌드에서만 그 값이 쓰이고 파일은 하나만 유지된다. RUN --mount=type=secret,id=npmrc npm ci 를 쓰면 비밀 파일이 빌드 중에만 임시로 연결되어 그 단계가 끝나면 연결이 끊기고, 이미지에는 비밀 파일이 남지 않는다.

4동작 과정

  1. 값 선언ARG 로 빌드 단계에서만 쓸 빌드 변수 이름을 선언하고, ENV 로 빌드가 끝난 뒤 실행 시점까지 남길 환경 변수를 선언한다. 여기서는 Dockerfile 안에서 어떤 값이 들어올 자리를 정한다.
  2. 값 주입빌드 명령에 --build-arg 를 붙여 이름을 지정해 값을 넘긴다. 같은 Dockerfile을 여러 조합으로 다시 빌드할 수 있다.
  3. 비밀값 주입RUN 에 --mount=type=secret 을 붙이면 빌드 도구가 비밀값을 빌드 중에만 임시 파일로 제공해 그 명령에서만 읽게 한다. 빌드가 끝나면 임시 파일은 사라지고 이미지 기록에도 남지 않는다.

5한 줄 요약

ARG·ENV 로 빌드 시점에 값을 받아 같은 Dockerfile을 재사용하고, RUN --mount=type=secret 으로 비밀값을 빌드 중에만 제공하는 것

멀티 플랫폼 이미지 빌드

멀티 플랫폼 빌드는 하나의 Dockerfile 로 여러 CPU 아키텍처용 이미지를 만들어 하나의 매니페스트 리스트로 묶는 것으로, Buildx 의 --platform 과 QEMU 에뮬레이션을 사용한다.

1문제 상황

컨테이너 이미지는 CPU 아키텍처마다 만들어지는 이진이 들어 있어서, x86-64용 이미지를 arm64 장비에 그대로 실행할 수 없다. 장비와 클라우드 제공자가 늘어날 때마다 그 환경에 맞는 이미지를 따로 빌드하고 따로 배포해야 했다.

그러면 Dockerfile 한 벌을 여러 번 실행해야 하고, 어떤 이미지가 어떤 아키텍처용인지 관리도 복잡해졌다. 서로 다른 빌드를 손으로 맞춰야 해서 아키텍처별로 내용이 미묘하게 달라지는 경우도 생겼다.

2핵심 질문

하나의 Dockerfile로 여러 CPU 아키텍처에서 실행되는 이미지를 한 번에 만들어 내는 것은 무엇인가?

3동작 예시

docker buildx build --platform linux/amd64,linux/arm64 -t 사내레지스트리/앱:v1 로 실행하면 같은 Dockerfile이 두 번 실행되어 각 아키텍처용 이미지가 하나씩 나온다. 빌드 도구인 Buildx 는 x86-64 장비에서 arm64 명령을 직접 돌릴 수 없으므로 QEMU 에뮬레이션으로 명령을 해석해 처리한다.

4동작 과정

  1. 플랫폼 지정--platform 에 대상 목록을 나열한다. 단일 플랫폼이면 일반 빌드와 같은 방식으로 이미지만 만들어진다.
  2. 플랫폼별 빌드Buildx 가 목록에 있는 아키텍처마다 빌드를 한 번씩 수행한다. x86-64용 이미지를 arm64에서 빌드할 때는 QEMU 에뮬레이션이 명령을 대신 실행해 준다.
  3. 단일 목록으로 묶기manifest list, 즉 어떤 태그를 치면 그 태그가 가리키는 아키텍처별 이미지 목록이 만들어진다. 이 목록 하나만 레지스트리에 올리면 클라이언트가 자기 아키텍처에 맞는 이미지를 골라 받는다.

5한 줄 요약

하나의 Dockerfile로 여러 아키텍처용 이미지를 만들어 하나의 매니페스트 리스트로 묶어, 클라이언트가 자기 환경용 이미지를 고르게 하는 것

빌드 설정 점검(Build Checks)

빌드 체크는 빌드 전에 Dockerfile 을 21종 규칙으로 자동 검사해 레거시 문법, 잘못된 표기, ARG·ENV 에 들어간 민감 데이터 같은 문제를 경고나 오류로 알려주는 기능이다.

1문제 상황

오래된 시점에 만든 Dockerfile은 문법이 바뀌어 그대로 빌드하려 하면 실패하거나, 빌드는 되지만 예상과 다른 결과가 나온다. 그런데 실패 이유가 지시문 중간쯤에서 멈춰 버려 어느 지시문이 문제인지 찾느라 빌드 로그를 여러 번 뒤져봐야 했다.

또한 민감한 값이 Dockerfile에 평문으로 들어간 채 빌드되는 경우도 알기 어렵지 않았다. 이런 문제는 이미지가 나중에 배포된 뒤에야 드러나기도 한다.

2핵심 질문

빌드를 시작하기 전에 Dockerfile을 규칙에 맞춰 자동 검사해, 문제를 빌드 전에 경고나 오류로 알려줄 수 있는가?

3동작 예시

Dockerfile에서 ENV 에 API_KEY=실제값 을 넣어 두고 빌드를 시작하면, 빌드 전에 검사기가 그 항목을 민감 데이터가 들어간 변수로 판정해 경고를 낸다. 같은 시점에 레거시 빌더 전용 문법을 쓰고 있으면, 어떤 문법이 현재 환경에서 지원되지 않는지도 함께 알려준다.

4동작 과정

  1. 검사 대상 지정Dockerfile의 어느 지시문에 규칙을 적용할지 지정한다. 아무것도 지정하지 않으면 모든 지시문이 검사 대상이 되고, 특정 지시문만 골라 검사할 수도 있다.
  2. 규칙 판정내장된 규칙 21종을 지시문별로 돌려 레거시 문법, 잘못된 표기, ARG·ENV 에 들어간 민감 데이터 같은 문제를 찾아낸다. 검사는 빌드가 시작되기 전에 수행된다.
  3. 결과 전달문제를 severity, 즉 경고 수준에 따라 분류해 출력한다. strict 모드로 두면 경고도 오류로 취급해 빌드 자체를 막을 수 있다.

5한 줄 요약

빌드 전에 Dockerfile을 규칙으로 자동 검사해 레거시 문법과 잘못된 표기, 민감 데이터 문제를 경고나 오류로 알려주는 것

5이미지 빌드 — Dockerfile05-07

빌드 결과물 내보내기와 트러블슈팅

빌드 결과물은 image·registry·local·OCI exporter 로 로컬 파일이나 레지스트리에 내보낼 수 있고, 실패한 빌드는 진행 로그와 OpenTelemetry 트레이스로 원인을 추적한다.

1문제 상황

빌드에 성공한 결과물을 로컬 이미지 저장소나 레지스트리에만 남기려면 그 자리에서 pull 해서 다시 push 하는 등 우회해야 했다. 다른 곳에서 바로 쓸 수 있는 단일 파일이나, 표준 규격으로 묶인 묶음 형태로는 결과물을 받을 방법이 없었다.

그리고 빌드가 실패하면 각 지시문이 얼마나 걸렸는지, 어디서 무엇이 실패했는지 확인할 단일된 수단이 없었다. 진행 로그를 직접 읽어야 했고, 여러 빌드를 돌렸을 때는 어느 빌드가 어느 작업인지 대응시키기도 어려웠다.

2핵심 질문

빌드 결과물을 원하는 형태로 내보내고, 실패한 빌드의 원인을 추적할 수 있는 정보를 남기는 것은 무엇인가?

3동작 예시

--output type=local,dest=./out 을 붙여 빌드하면 이미지 레이어가 out 디렉터리 일반 파일로 풀려 나오고, --output type=oci,dest=./app.oci 로 지정하면 OCI 규격 묶음 파일 하나가 만들어진다. --output type=registry 도 가능하다. 실패한 빌드에 --progress=plain 을 붙이면 지시문별 진행 로그가 줄 단위로 나오고, --trace 로 빌드 실행 전체를 OpenTelemetry 형식 트레이스로 내보내 각 단계의 소요 시간을 따로 볼 수 있다.

4동작 과정

  1. 결과물 지정--output 에 exporter, 즉 내보낼 방식과 목적지를 지정한다. image·registry·local·oci 중에서 고르고, 결과는 빌드 중에 바로 그 경로에 만들어진다.
  2. 진행 기록 남기기진행 표시 방식을 plain 으로 지정해 각 지시문의 진행 로그가 줄 단위로 남게 한다. 이 로그는 어디까지 통과했고 어디서 멈췄는지 보여 준다.
  3. 트레이스 내보내기--trace 로 OpenTelemetry 형식 트레이스를 내보내 각 지시문의 시작·종료와 소요 시간을 구조화된 데이터로 남긴다. 외부 수집기로 보내면 여러 빌드의 단계별 시간을 한곳에서 비교할 수 있다.

5한 줄 요약

빌드 결과물을 image·registry·local·oci 로 내보내고, 진행 로그와 OpenTelemetry 트레이스로 실패한 빌드의 원인을 추적하는 것

공식 문서https://docs.docker.com/build/debug/opentelemetry/

6BuildKit 과 Buildx06-01

BuildKit 이란 무엇인가

BuildKit 은 Dockerfile 의 지시를 실제로 실행해 컨테이너 이미지를 만들어 내는 빌드 엔진으로, Docker 빌드가 기본으로 사용하는 실행 주체입니다.

1문제 상황

예전 Docker 빌드는 Dockerfile의 각 줄을 읽어 컨테이너 안에서 명령을 하나씩 직접 실행하는 방식이었다. 중간에 어떤 명령을 실행했는지 구조적으로 기록하지 않아서, 같은 Dockerfile을 다시 빌드해도 이전 결과를 활용할 수 없었다. 한 단계가 바뀔 때마다 뒤 단계가 전부 처음부터 다시 실행되므로 빌드 시간이 길고, 빌드마다 결과가 조금씩 달라지기도 했다.

2핵심 질문

Dockerfile의 지시를 실행해 이미지를 만들되, 이미 계산한 결과를 재사용하고 재현 가능하게 만들 수 있는가?

3동작 예시

BuildKit은 Dockerfile을 실행할 때 각 명령어마다 입력 상태와 출력 상태를 하나의 단계로 나눠 기록한다. 예를 들어 apt-get install 앞의 파일 목록이 이전 빌드와 같다면, 그 단계는 저장해 둔 결과를 그대로 가져오고 설치를 다시 실행하지 않는다. 다음 단계는 그 결과를 입력으로 받아 계속 진행된다.

4동작 과정

  1. 빌드 그래프 구성Dockerfile의 각 명령을 노드로 만들고 앞 단계의 출력이 다음 단계의 입력이 되도록 의존 관계를 잇는다. 동시에 필요한 단계를 병렬로 처리한다.
  2. 단계별 캐시 조회각 노드의 입력 파일과 명령, 이전 결과를 해시 키로 삼아 캐시를 찾는다. 일치하는 결과가 있으면 실행하지 않고 저장된 결과를 연결한다.
  3. 캐시 미스 단계 실행해시가 달라진 노드만 컨테이너 안에서 실제로 실행하고, 그 결과를 새로운 캐시 항목으로 저장한다. 최종 결과는 Exporter를 통해 이미지 형태로 내보낸다.

5한 줄 요약

Docker 빌드를 단계별 캐시와 실행 기록을 가진 빌드 그래프 엔진으로 바꾸어, 바뀐 부분만 다시 실행하게 하는 것

6BuildKit 과 Buildx06-02

Buildx 빌더와 드라이버

Buildx 는 빌드를 요청하는 CLI 클라이언트이며, 빌드를 수행하는 BuildKit 인스턴스(빌더)와 그 인스턴스를 어떤 환경에서 띄우는지를 정하는 드라이버의 조합으로 동작합니다.

1문제 상황

기존 docker build는 Docker 엔진이 설치된 로컬 환경에서만 이미지를 만들었다. 여러 운영체제와 아키텍처용 이미지를 만들어야 할 때 다른 환경에 데스크톱 도커를 따로 설치하거나 스크립트로 명령을 반복해서 실행해야 했다. 어떤 빌드 환경으로 빌드했는지도 기록되지 않았다.

2핵심 질문

어떤 환경에서 이미지를 빌드할지 고르고, 그 환경을 재사용하면서 여러 곳에서 같은 빌드를 실행할 수 있는가?

3동작 예시

docker buildx create --driver docker-container --name ci 를 한 번 실행하면 컨테이너 안에서 도는 빌더 인스턴스가 하나 만들어진다. 이후 docker buildx build --builder ci --platform linux/amd64,linux/arm64 . 을 실행하면 그 인스턴스가 요청한 플랫폼 이미지를 만들어 낸다. 같은 이름의 빌더를 다시 선택하면 이전에 설정한 환경을 그대로 재사용한다.

4동작 과정

  1. 빌더 인스턴스 생성docker buildx create 가 이름과 드라이버를 받아 BuildKit 인스턴스를 하나 띄운다. 기본 드라이버는 기존 엔진에 붙는 docker 드라이버다.
  2. 드라이버가 환경 결정드라이버는 인스턴스를 어떤 환경에서 돌릴지 정한다. docker-container 드라이버는 컨테이너로 격리된 환경을 만들고, remote 드라이버는 원격 빌더 주소에 연결하며, kubernetes 드라이버는 클러스터에서 실행한다.
  3. 빌드 요청 전달docker buildx build CLI가 빌더 인스턴스로 요청을 보내고, 인스턴스가 BuildKit으로 실제 빌드를 수행한다. 생성된 인스턴스는 목록에 남으므로 재사용하거나 삭제할 수 있다.

5한 줄 요약

빌드 CLI와 실제 빌드를 수행하는 BuildKit 인스턴스, 그리고 그 인스턴스를 띄울 환경을 드라이버로 분리해 재사용 가능하게 만든 것

6BuildKit 과 Buildx06-03

빌드 캐시 백엔드

빌드 캐시 백엔드는 BuildKit 이 만든 레이어 캐시를 로컬 디렉터리나 레지스트리, S3 같은 외부 저장소에 보관하고 다음 빌드에서 다시 불러오게 하는 저장 위치를 말합니다.

1문제 상황

기본 빌드 캐시는 빌더를 실행 중인 로컬 디스크에 저장된다. CI 러너가 매번 새로 띄어지거나 여러 대의 머신이 같은 Dockerfile을 빌드하면 각 머신이 캐시를 따로 갖고 있어 이전 결과를 전혀 재사용하지 못했다. 캐시 없이는 의존성 설치와 컴파일이 전부 처음부터 다시 실행되어 빌드 시간이 크게 늘어난다.

2핵심 질문

빌드 중 만들어진 레이어 캐시를 여러 빌더가 공유할 수 있는 외부 저장소에 어디에 둘까?

3동작 예시

레지스트리 백엔드를 쓰면 레이어 캐시가 이미지를 푸시한 레지스트리 안에 함께 저장된다. CI에서 docker buildx build --cache-from type=registry,ref=myapp:buildcache --cache-to type=registry,ref=myapp:buildcache,mode=max . 을 실행하면, 이전 빌드가 레지스트리에 남긴 캐시를 먼저 불러오고 이번 빌드의 결과 캐시를 같은 위치에 다시 저장한다. 다음 빌드는 어느 머신에서 실행해도 그 캐시를 그대로 받는다.

4동작 과정

  1. 캐시 위치 지정빌더 생성 시 --cache-to 와 --cache-from 으로 백엔드 종류와 저장 위치를 지정한다. 로컬 디렉터리, 레지스트리, Amazon S3, Azure Blob Storage, Google Cloud Storage 등이 지원된다.
  2. 캐시 적재빌드 시작 시 지정한 위치에서 이전에 저장한 레이어 메타데이터를 가져와 현재 Dockerfile 단계와 비교한다. 일치하는 단계는 실행 없이 연결하고, 없는 단계만 실행한다.
  3. 캐시 저장빌드가 끝나면 각 단계의 실행 결과와 메타데이터를 백엔드에 규격에 맞는 형태로 기록한다. 모드 설정에 따라 최종 이미지 레이어만 저장하거나 중간 단계까지 전부 저장한다.

5한 줄 요약

BuildKit의 레이어 캐시 저장 위치를 로컬 밖의 공유 저장소로 지정해 여러 빌더와 머신이 같은 빌드 결과를 재사용하게 하는 것

공식 문서https://docs.docker.com/build/cache/backends/registry/

6BuildKit 과 Buildx06-04

빌드 결과 내보내기(Exporter)

Exporter 는 BuildKit 이 만든 빌드 결과를 로컬 이미지 저장소, 레지스트리, 로컬 tar 파일 같은 지정된 형태로 내보내는 출력 방식을 지정하는 설정입니다.

1문제 상황

기존 빌드 결과는 Docker 엔진이 관리하는 로컬 이미지 저장소에만 들어갔다. 그래서 만든 이미지를 다른 머신으로 옮기려면 docker save 로 tar 파일로 덤프한 뒤 다시 docker load 로 불러와야 했고, 원격 레지스트리에 올리려면 별도의 docker push 단계를 추가로 실행해야 했다. 결과를 어디로 보낼지 빌드 과정 안에서 지정할 방법이 없었다.

2핵심 질문

BuildKit이 만든 결과를 어떤 형태로 어디에 내보낼지를 빌드 설정에서 직접 지정할 수 있는가?

3동작 예시

docker buildx build --output type=oci,dest=./app.tar . 을 실행하면 이미지 저장소 대신 OCI 규격의 tar 파일이 만들어진다. 이 파일은 docker load 없이도 다른 도구에서 바로 읽을 수 있다. --output type=registry 를 주면 레지스트리에 직접 푸시하고, --push 를 주면 기본 이미지 Exporter가 레지스트리 푸시까지 수행한다.

4동작 과정

  1. 출력 방식 지정--output 에 Exporter 종류와 목적지를 함께 준다. 기본값은 docker Exporter로 로컬 이미지 저장소에 이미지를 기록하며, image 는 레지스트리 저장소만 만들고, oci 와 docker 는 tar 파일을 만든다.
  2. 결과 변환BuildKit이 레이어와 설정, 매니페스트를 Exporter 규격에 맞춰 조립한다. OCI Exporter는 표준 OCI 레이아웃을, registry Exporter는 레지스트리가 이해하는 매니페스트와 블롭을 만든다.
  3. 목적지 출력조립된 결과를 지정한 경로에 쓰거나 레지스트리에 업로드한다. 다중 플랫폼 빌드라면 플랫폼별 이미지와 이미지 인덱스가 함께 생성된다.

5한 줄 요약

이미지 메타데이터와 증명

이미지 메타데이터는 이미지 구성 요소에 SBOM 이나 빌드 출처 같은 증명(attestation) 정보를 함께 붙여, 이미지가 무엇으로 만들어졌는지 검증할 수 있게 하는 정보입니다.

1문제 상황

컨테이너 이미지가 실제로 어떤 소스 코드로 어떤 빌드 도구로 만들어졌는지 이미지 안에는 남지 않았다. 배포된 이미지를 나중에 확인해도 출처를 알 수 없고, 중간에 변조되었는지 검증할 방법도 없었다. 보안 점검에서는 이미지마다 사용한 패키지 목록과 빌드 기록을 따로 요청해 다시 수집해야 했다.

2핵심 질문

이미지를 만든 소스와 빌드 과정, 포함된 패키지 정보를 이미지 자체에 함께 기록해 나중에 검증할 수 있는가?

3동작 예시

docker buildx build --provenance=true --sbom=true . 을 실행하면 빌드가 끝날 때 이미지에 SBOM(포함 패키지 목록)과 provenance(빌드 출처) 문서가 증명 정보로 붙는다. 이 정보는 이미지를 푸시했을 때 레지스트리에서 OCI 참고 자료로 확인되며, docker buildx imagetools inspect 로 어떤 빌드에서 나온 이미지인지 볼 수 있다. 슬라이드 윈도우 모드를 켜면 레이어 옆에 별도 항목으로 증명이 표시된다.

4동작 과정

  1. 증명 생성BuildKit이 각 빌드 단계를 실행하면서 사용한 소스 커밋, 빌더 버전, 생성 시각, 빌드 인자를 모은 provenance 문서와, 이미지에 포함된 패키지 목록인 SBOM 문서를 만든다.
  2. 이미지에 첨부만든 증명은 이미지의 매니페스트에 OCI 참고 자료로 등록된다. 이미지 본체 레이어와 분리되어 있어 이미지 내용에는 영향을 주지 않는다.
  3. 배포 후 검증레지스트리에서 증명 문서를 꺼내 빌드 출처를 확인하거나, 정책 엔진과 비교해 이미지 허용 여부를 판단한다. 증명 없는 이미지와 서명된 이미지를 구분하는 근거로도 쓴다.

5한 줄 요약

빌드 출처와 패키지 목록을 이미지에 증명 정보로 함께 심어, 배포된 이미지의 출처와 변조 여부를 나중에 검증 가능하게 하는 것

공식 문서https://docs.docker.com/build/metadata/attestations/slsa-provenance/

Bake 로 선언형 빌드하기

Bake 는 여러 이미지의 빌드 설정을 HCL 이나 Compose 파일 같은 선언적 파일에 모아 두고 한 번에 정의하고 실행하게 해 주는 Buildx 기능입니다.

1문제 상황

여러 이미지를 함께 빌드하려면 각 이미지마다 docker buildx build 명령을 실행하고, 공통으로 쓰는 빌드 인자와 플랫폼, 캐시 설정을 명령줄에 반복해서 적어야 했다. 대상 목록이 늘어나면 명령 관리가 어려워지고, 로컬과 CI 에서 같은 설정을 다르게 쓰는 일도 생겼다.

2핵심 질문

여러 이미지의 빌드 설정을 파일 하나로 모아 두고 같은 정의를 로컬과 CI 에서 그대로 실행할 수 있는가?

3동작 예시

bake.hcl 파일 안에 group "default" 로 api 와 web 두 대상을 정의하고 각 대상의 context, dockerfile, tags, cache-from 을 선언한다. 이후 docker buildx bake 를 실행하면 Bake가 파일을 파싱해 그룹에 속한 모든 이미지를 정의된 순서대로 병렬 빌드하고, 지정한 레지스트리 태그로 푸시까지 수행한다. 대상 하나만 빌드하려면 docker buildx bake web 을 실행한다.

4동작 과정

  1. 선언 파일 읽기docker-bake.hcl 또는 compose.yaml 같은 선언 파일을 읽어 target 단위로 빌드 설정을 만든다. target은 이전 target을 상속해 공통 설정을 나눠 쓸 수 있다.
  2. 설정 병합명령줄 플래그, 환경 변수, HCL 파일, Compose 파일의 설정을 우선순위에 따라 합쳐 하나의 빌드 계획으로 만든다. 동일한 대상에 대한 설정은 나중에 지정한 것이 앞선 결과를 덮어쓴다.
  3. 일괄 실행확정된 계획의 모든 대상을 BuildKit 빌더에 병렬로 요청하고, 지정한 Exporter로 이미지를 저장하거나 푸시한다. 결과를 로컬 이미지 저장소에 남길지 출력 경로는 각 target 설정으로 정한다.

5한 줄 요약

여러 이미지의 빌드 설정을 선언 파일에 정의해 두고 한 번의 명령으로 동일하게 실행하게 하는 것

볼륨 — 데이터를 어디에 두는가

볼륨은 Docker가 관리하는 호스트 영역으로, 컨테이너를 지우고 다시 만들어도 데이터가 남는 영속 저장소다.

1문제 상황

컨테이너의 파일 시스템은 컨테이너 자체의 수명에 묶여 있다. 컨테이너를 지우고 새로 만들면 내부에 쓰던 데이터도 함께 사라진다. 데이터베이스가 저장한 파일처럼 반드시 유지돼야 하는 정보를 컨테이너 안에 두면, 이미지를 다시 만들 때마다 데이터를 옮기거나 백업해 복원해야 하는 문제가 생긴다.

2핵심 질문

컨테이너를 교체해도 사라지지 않는 데이터를 호스트의 어떤 위치에 두고 컨테이너와 어떻게 연결할까?

3동작 예시

docker volume create pgdata 를 실행하면 호스트에 볼륨이 하나 만들어진다. docker run -v pgdata:/var/lib/postgresql/data postgres 로 컨테이너를 띄우면 그 경로가 볼륨에 연결되어, 컨테이너 안에서 저장한 데이터는 볼륨 쪽에 남는다. 이후 postgres 컨테이너를 docker rm 하고 같은 볼륨 이름으로 다시 실행해도 이전 데이터가 그대로 보인다. 볼륨 이름 앞에 ro 를 붙여 읽기 전용으로 붙일 수도 있다.

4동작 과정

  1. 볼륨 생성docker volume create 가 이름과 드라이버를 받아 호스트 영역을 확보한다. 기본 드라이버는 로컬 디렉터리를 그대로 사용하고, 다른 드라이버를 지정하면 외부 저장소나 클라우드 볼륨을 쓸 수 있다.
  2. 컨테이너에 마운트docker run -v 볼륨이름:컨테이너경로 또는 --mount source=볼륨이명,target=경로 로 볼륨을 컨테이너 경로에 연결한다. 컨테이너가 경로에 쓰는 데이터가 곧 볼륨에 저장된다.
  3. 컨테이너 교체 후 유지컨테이너를 삭제해도 마운트 대상 볼륨은 삭제되지 않으므로 같은 이름으로 다시 연결해 데이터가 유지된 상태로 계속 작업할 수 있다. 마운트 지점의 소유권은 --user 로 지정한다.

5한 줄 요약

컨테이너 수명과 분리된 호스트 관리 저장 영역을 만들어, 컨테이너를 교체해도 데이터가 유지되게 하는 것

바인드 마운트 — 호스트 파일을 컨테이너에

바인드 마운트는 호스트의 특정 경로를 컨테이너의 디렉터리에 그대로 연결해, 컨테이너가 호스트의 파일을 읽고 쓰게 한다.

1문제 상황

컨테이너는 이미지 계층 위에 자체 쓰기 계층을 얹어 독립된 파일 시스템을 가진다. 그래서 컨테이너 안에서 만든 파일은 컨테이너를 지우면 함께 사라지고, 호스트에 있는 파일은 컨테이너 안에서 볼 수 없다.

데이터를 이미지 계층에 쓰면 커밋하지 않는 한 이미지 밖으로 나가지 못하고, 커밋하면 이미지 크기가 계속 커진다. 데이터를 컨테이너 안에만 두면 컨테이너를 재생성할 때마다 잃어버린다. 컨테이너 밖에서 안으로, 밖에서 밖으로 데이터를 주고받는 통로가 필요했다.

2핵심 질문

컨테이너가 사라져도 남는, 호스트의 특정 디렉터리를 컨테이너 안에서 그대로 읽고 쓰게 하는 길은 무엇인가?

3동작 예시

호스트의 /home/dev/data 를 컨테이너의 /data 로 지정해 실행하면, 컨테이너 안에서 /data/log.txt 에 저장한 내용이 컨테이너를 지우고 다시 실행해도 호스트의 /home/dev/data/log.txt 에 그대로 남는다. 두 경로가 연결되므로 복사나 동기화 과정이 없고, 어느 쪽에서 쓰든 같은 파일에 반영된다.

4동작 과정

  1. 마운트 지점 지정docker run -v /home/dev/data:/data 처럼 호스트 경로와 컨테이너 경로를 쌍으로 준다. 컨테이너는 뒤쪽 경로를 자기 파일 시스템의 한 지점으로 삼아 그 경로로 접근하면 호스트의 디렉터리에 닿는다.
  2. 경로 자동 준비호스트 쪽 디렉터리가 없으면 데몬이 만들고, 컨테이너 안의 마운트 지점도 만들어 연결한다. 디렉터리 대신 파일을 지정하면 그 파일 하나만 연결된다.
  3. 동일 경로로 읽기·쓰기컨테이너 안에서 쓴 내용이 호스트에 바로 보이고, 호스트에서 고친 내용도 컨테이너에서 바로 보인다. 실제 접근 권한은 컨테이너 안 프로세스의 사용자 권한을 따른다.

5한 줄 요약

호스트의 디렉터리를 컨테이너의 경로에 그대로 연결해, 컨테이너가 만든 데이터가 컨테이너 수명과 무관하게 호스트 쪽에 남게 하는 것

7데이터 저장07-03

tmpfs 와 이미지 마운트

tmpfs 마운트는 RAM 위에 임시 파일 시스템을 만들어 빠르지만 컨테이너가 멈추면 데이터가 사라지고, 이미지 마운트는 이미지의 디렉터리를 읽기 전용으로 붙인다.

1문제 상황

바인드 마운트는 디스크를 거치기 때문에 읽고 쓰는 속도가 느리고, 데이터가 디스크에 남아 정리가 필요해진다. 반대로 모든 데이터를 컨테이너 안에만 두면 컨테이너를 지울 때 함께 사라진다.

디스크보다 빠른 임시 공간이 필요하지만 영속성은 원하지 않는 경우, 그리고 원본을 건드리지 않고 읽기만 하고 싶은 경우가 각각 생긴다. 두 경우를 하나의 저장 방식으로는 처리할 수 없다.

2핵심 질문

디스크를 거치지 않고 메모리에서 동작하며 컨테이너 종료와 함께 사라지는 임시 저장소와, 원본 이미지를 읽기 전용으로 붙이는 방법을 어떻게 제공하는가?

3동작 예시

docker run --tmpfs /tmp:size=64m 로 빌드를 실행하면 /tmp 아래의 중간 산출물이 디스크 대신 메모리에 저장되어 빠르게 읽고 쓰인다. 컨테이너를 멈추면 그 산출물은 사라져 별도 정리를 하지 않아도 된다. --mount type=bind,ro 로 이미지의 디렉터리를 붙이면 컨테이너는 그 내용을 볼 수만 수정할 수 없다.

4동작 과정

  1. tmpfs 마운트 생성--tmpfs 나 --mount type=tmpfs,dst=/tmp 로 RAM 위에 임시 파일 시스템을 만들고, 크기와 옵션을 함께 지정한다. 디바이스를 따로 만들지 않고 커널이 메모리 영역을 곧바로 파일 시스템으로 노출한다.
  2. 수명과 자동 정리이 파일 시스템은 컨테이너와 함께 사라진다. 메모리만 쓰므로 읽고 쓰는 지연이 디스크보다 낮고, 재시작 시 이전 상태를 이어받을 필요가 없는 일회성 작업에 적합하다.
  3. 이미지 마운트이미지에 들어 있는 디렉터리를 다른 경로에 읽기 전용으로 붙여, 원본을 건드리지 않고 참조만 하거나 별도 이름으로 노출할 수 있게 한다.

5한 줄 요약

디스크 대신 메모리에 쓰는 임시 파일 시스템과 이미지의 읽기 전용 경로를 각각 제공해, 영속성이 필요 없는 작업과 원본 보기가 필요한 작업에 맞는 저장 방식을 주는 것

스토리지 드라이버와 containerd 이미지 스토어

스토리지 드라이버는 이미지와 컨테이너의 계층 데이터를 디스크에 저장하고 복원하는 엔진의 후반부이며, containerd 이미지 스토어는 이 저장을 containerd에 맡겨 이미지·아티팩트 관리를 확장하는 방식이다.

1문제 상황

이미지와 컨테이너의 데이터는 여러 개의 계층으로 쌓인다. 이 계층들을 디스크에 어떤 단위로 쓰고, 실행할 때 어떤 순서로 겹쳐 보여줄지를 엔진이 정해야 하며, 이 방식에 따라 디스크 사용량과 성능, 단일 드라이버 디스크를 다른 드라이버로 읽을 수 있는지 여부가 달라진다.

이 저장 처리를 엔진이 직접 다뤄야 하면 이미지 계층 관리 코드가 커지고, 이미지·아티팩트 관리 기능을 더 늘리기 어렵다. Docker는 저장 계층 자체를 플러그인 형태로 선택하게 하고, 이미지 저장은 기본적으로 containerd 라는 컴포넌트에 맡긴다.

2핵심 질문

계층 데이터를 디스크에 저장하고 다시 겹쳐 보여주는 일과, 이미지·아티팩트 관리를 containerd 에 맡기는 일을 어떻게 나누는가?

3동작 예시

이미지를 받아 컨테이너를 실행하면 이미지 계층은 읽기 전용으로 쌓이고, 그 위에 컨테이너 쓰기 계층이 얹혀 파일 변경이 그 층에만 기록된다. 어떤 드라이버는 계층을 자체 파일 포맷의 큰 파일 하나에 담아 저장하므로, 그 드라이버로 만든 디스크를 다른 드라이버 환경에 붙여 읽는 것이 불가능하다.

4동작 과정

  1. 저장 드라이버로 계층 기록선택된 스토리지 드라이버가 이미지와 컨테이너의 계층 데이터를 디스크에 쓰고, 이 드라이버의 격리와 용량 계산 방식에 따라 컨테이너가 만들어진다. 드라이버 종류마다 저장 단위와 성능 특성이 다르다.
  2. 쓰기 계층 구성컨테이너가 실행되면 읽기 전용 이미지 계층 위에 쓰기 가능 계층을 얹는다. 쓰기는 이 계층에만 쌓이고, 컨테이너가 사라지면 그 계층도 함께 삭제된다.
  3. containerd 이미지 스토어이미지 관련 저장을 containerd 로 넘겨 이미지와 아티팩트를 그래프 형태로 관리한다. 엔진은 컨테이너 실행에 집중하게 되고, containerd 자체 도구로 저장된 내용을 확인할 수 있다.

5한 줄 요약

계층 데이터의 저장과 복원을 스토리지 드라이버가 맡고, 이미지·아티팩트의 관리는 containerd 로 위임해 저장과 관리를 분리하는 것

브리지 네트워크와 컨테이너 간 통신

호스트의 브리지를 그대로 공유하는 기본 bridge 와, 컨테이너에 자동 DNS 이름을 붙여 이름으로 통신하게 하는 사용자 정의 bridge 로 컨테이너끼리 주고받는 구조다.

1문제 상황

컨테이너는 각각 네트워크 네임스페이스를 가져 독립된 네트워크에서 동작한다. 그래서 다른 컨테이너로 직접 통신할 수 없고, 호스트에 여러 컨테이너를 띄우면 각 컨테이너의 IP 를 따로 확인해야 한다. 컨테이너를 지우고 다시 만들면 IP 가 바뀔 수도 있다.

상태를 같이 다루는 앱과 DB 처럼 서로 붙어 있어야 하는 컨테이너를 매번 IP 로 연결하면 관리가 어려워진다. 하나의 네트워크로 묶고 이름을 통해 서로 찾을 수 있는 방법이 필요하다.

2핵심 질문

여러 컨테이너를 하나의 네트워크로 묶고, 서로 찾을 수 있는 이름을 붙여 통신시키는가?

3동작 예시

사용자 정의 브리지 네트워크를 하나 만들고 앱과 DB 컨테이너를 그 안에서 함께 실행하면, 두 컨테이너는 각자 IP 를 받으면서도 서로 통신할 수 있다. 앱 안에서 db 라는 이름으로 DB 포트에 바로 연결되고, DB 컨테이너를 재생성해 IP 가 바뀌어도 이름은 그대로다.

4동작 과정

  1. 브리지 네트워크 생성호스트에 가상의 브리지 인터페이스를 만들어 컨테이너는 그 브리지의 각 포트에 물린 것처럼 붙는다. 이 안의 컨테이너들은 서로 통신할 수 있으며, 브리지가 만들어진 네트워크를 두고선 통신하지 않는다.
  2. 격리된 주소 공간각 컨테이너는 자신의 네트워크 네임스페이스 안에서만 동작하므로, 다른 브리지에 속한 컨테이너로는 직접 접근할 수 없다. 브리지 밖으로 나갈 때는 호스트가 NAT 로 주소를 바꾼다.
  3. DNS 이름 부여사용자 정의 브리지에서는 컨테이너 이름과 별칭이 DNS 에 등록되어 이름으로 통신할 수 있다. 기본 bridge 는 IP 로만 통신하고 이 이름 등록 기능이 없다.

5한 줄 요약

컨테이너들을 호스트의 브리지 네트워크에 묶어 서로 통신하게 하고, 기본 bridge 와 달리 사용자 정의 bridge 에서는 컨테이너 이름으로 통신할 수 있게 하는 것

포트 게시로 외부에 노출하기

컨테이너의 포트를 호스트의 포트에 대응시키는 -p 게시로 외부에서 들어올 경로를 만들고, EXPOSE 는 이런 노출을 하지 않고 선언만 하는 지시다.

1문제 상황

컨테이너는 격리된 네트워크 안에서 동작하므로 외부에서 들어올 경로가 없다. 컨테이너 안의 서버가 80 포트로 떠 있어도 호스트에서는 그 포트로 접근할 수 없다.

이미지에 어떤 포트를 쓰는지를 기록해 두는 것과, 그 포트로 외부 접근이 가능해지는 것은 전혀 다른 문제다. 또 하나의 호스트에 컨테이너를 여러 개 띄우면 같은 서버 포트를 쓰면서도 각각 다른 외부 주소가 필요하다.

2핵심 질문

여러 컨테이너를 띄우면서, 각 컨테이너의 특정 포트로 외부에서 들어올 수 있는 경로를 어떻게 만드는가?

3동작 예시

docker run -p 8080:80 로 웹 서버 컨테이너를 띄우면 호스트의 8080 포트로 들어온 요청이 그 컨테이너의 80 포트로 전달된다. 컨테이너를 하나 더 띄워 -p 8081:80 을 주면 8081 이 두 번째 컨테이너로 이어져, 둘 다 80 포트를 쓰면서도 충돌하지 않는다.

4동작 과정

  1. 호스트 포트 지정-p 8080:80 은 호스트의 8080 포트를 컨테이너의 80 포트에 대응시킨다는 뜻이고, 80 처럼 한쪽만 적으면 호스트의 임의의 빈 포트가 배정된다. -p 80/udp 처럼 쓰면 UDP 로도 연다.
  2. 네트워크 규칙 등록엔진이 NAT 규칙을 만들어 외부에서 들어온 패킷을 해당 컨테이너로 넘긴다. 규칙은 컨테이너가 살아 있는 동안 유지되고, 컨테이너를 지우면 함께 사라진다.
  3. EXPOSE 는 선언만Dockerfile 의 EXPOSE 80 은 이미지가 어떤 포트를 쓸지 기록할 뿐 규칙을 만들지 않는다. 그 뒤 실행되는 모든 프로세스에 적용된다는 의미도 아니며, 쓰려면 결국 -p 가 필요하다.

5한 줄 요약

호스트의 포트를 컨테이너의 포트에 대응시켜 외부에서 들어올 경로를 만드는 것이며, EXPOSE 는 그 노출이 아니라 사용 예정 포트를 남기는 선언

네트워크 드라이버 선택

격리와 주소 배분의 필요에 따라 bridge·host·overlay·macvlan·ipvlan·none 가운데 드라이버를 고르며, host 는 호스트 스택을 그대로 공유하고 macvlan·ipvlan 은 컨테이너를 물리 머신처럼 보이게 한다.

1문제 상황

컨테이너를 서로 격리된 기본 네트워크에 묶어야 하는 경우가 있고, 네트워킹을 새로 만들지 않고 호스트의 네트워크를 그대로 써야 하는 경우도 있다. 여러 호스트에 걸친 클러스터에서 컨테이너끼리 통신해야 할 때, 그리고 컨테이너가 물리 머신의 IP 주소를 직접 달고 LAN 에 붙어야 할 때도 있다.

격리 수준과 IP 할당 방식, 호스트에 노출되는 범위가 요구사항마다 다르므로 하나의 드라이버 구조로는 전부 처리할 수 없다.

2핵심 질문

필요한 격리 수준과 주소 배분 방식에 따라 어떤 네트워크 드라이버를 골라야 하는가?

3동작 예시

호스트의 물리 인터페이스와 IP 를 그대로 사용해야 하는 성능 측정 프로그램을 띄울 때는 --network host 를 쓴다. 같은 호스트의 다른 서버가 컨테이너에 직접 닿아야 한다면 macvlan 드라이버로 서브 인터페이스를 만들고, 실제 머신처럼 보이는 주소를 컨테이너에 부여한다.

4동작 과정

  1. 격리와 통신 범위 결정다른 브리지의 컨테이너와도 communication이 필요 없으면 bridge 를 쓴다. 여러 호스트에 걸친 컨테이너가 서로를 찾아야 하면 overlay 를 쓰고, 이 단계에서 컨테이너가 어디까지 보이는지가 정해진다.
  2. 주소 배분 방식 결정macvlan 은 컨테이너가 물리 머신처럼 보이게 하고, ipvlan 은 네트워크 장비가 컨테이너의 MAC 주소를 보지 못하게 한다. 둘 다 호스트의 물리 인터페이스에 직접 붙는 방식이다.
  3. 스택 공유와 완전 차단 선택host 드라이버는 호스트의 네트워크 스택을 그대로 공유해 컨테이너가 호스트와 완전히 동일한 네트워크에 놓인다. none 드라이버는 네트워크 인터페이스를 만들지 않는다.

방화벽 연동 — iptables 와 nftables

데몬은 브리지 네트워크를 만들 때 호스트의 iptables 또는 nftables에 NAT·필터 규칙을 직접 넣고 제거하며, 데몬 설정의 iptables=false 같은 항목으로 이 자동화를 끌 수 있다.

1문제 상황

브리지를 만들면 호스트의 방화벽 규칙을 따르지 않는 통로가 생긴다. 컨테이너가 노출한 포트와 NAT 변환이 방화벽에 등록되지 않으면, 방화벽이 막기로 한 경로가 열려 있을 수 있다. 반대로 규칙을 전부 직접 쓰면 컨테이너가 계속 바뀌는 만큼 손으로 맞춰야 해서 결국 방화벽을 통째로 꺼버리게 되고, 그것은 해결이 아니다.

방화벽은 계속 켜 두고 규칙의 생성과 제거만 자동화해야 한다.

2핵심 질문

데몬이 브리지 네트워크를 만들 때 방화벽 규칙을 직접 넣고 지우는 일을 언제 그리고 어떻게 수행하는가?

3동작 예시

docker run -p 8080:80 을 실행하면 데몬이 호스트의 iptables 또는 nftables에 NAT 규칙을 추가해 8080 포트로 들어온 패킷이 그 컨테이너로 가게 한다. 이 컨테이너를 지우면 같은 규칙도 함께 걷어내진다. /etc/docker/daemon.json 에 "iptables": false 를 넣고 데몬을 다시 시작하면 이 자동 처리가 꺼져 규칙을 직접 관리해야 한다.

4동작 과정

  1. 방화벽 백엔드 선택데몬은 호스트에 iptables 가 남아 있으면 iptables 를, iptables 없이 nftables 만 있으면 nftables 를 백엔드로 삼는다. 어느 쪽이든 규칙을 직접 건드리는 방식은 동일하다.
  2. 규칙 자동 삽입과 제거네트워크를 만들 때 FORWARD 나 PUBLISH 체인에 규칙을 삽입하고, 네트워크를 지울 때 함께 제거한다. 규칙이 컨테이너 수명 동안만 존재하므로 불필요한 개방 상태가 남지 않는다.
  3. 자동화 해제iptables=false 나 ip6tables=false 같은 데몬 설정 항목으로 해당 처리를 끌 수 있다. 꺼진 상태에서는 방화벽 규칙을 운영자가 직접 만들고 관리해야 한다.

5한 줄 요약

데몬이 방화벽 규칙의 삽입과 제거를 자동으로 수행해, 브리지 네트워크가 열어 놓는 경로를 방화벽 의도에 맞게 관리하는 것

IPv6 과 프록시 설정

데몬 설정의 ipv6·fixed-cidr-v6 항목으로 컨테이너에 IPv6 주소를 배정하고, HTTP_PROXY·HTTPS_PROXY·NO_PROXY 로 데몬과 클라이언트가 외부로 나가는 경로를 지정한다.

1문제 상황

기본 Docker 브리지는 IPv4 주소만 다루기 때문에, 컨테이너를 만들면 172.17 대역의 IPv4 주소가 붙고 그 주소로만 서로 통신한다. 이 환경에서 사내망이나 외부 자원이 IPv6만 있으면 컨테이너는 그 자리에 닿지 못하고, 외부로 나갈 때도 별도 경로가 없어 인터넷을 직접 못 나간다.

IPv6 주소를 붙이려면 데몬 설정이 따로 필요하고, 방화벽이 있는 회사 환경에서는 프록시 서버를 반드시 거쳐야 하는 경우가 많다. 그런데 데몬과 컨테이너, 빌드 과정이 각각 다른 위치에서 실행되므로 어디에 어떤 값을 줘야 하는지가 정해져 있지 않다.

2핵심 질문

IPv6만 있는 자리에 컨테이너가 닿게 하고, 사내망에서는 프록시를 거쳐 나가게 하려면 데몬과 클라이언트에 무엇을 어떻게 지정해야 합니까?

3동작 예시

/etc/docker/daemon.json 에 "ipv6": true와 "fixed-cidr-v6": "2001:db8:1::/64"를 적어 두고 데몬을 재시작하면, 이후 만들어지는 컨테이너마다 2001:db8:1::a1b2 처음 128비트 IPv6 주소가 붙는다. 그리고 데몬 프로세스를 띄운 환경 변수에 HTTP_PROXY를 넣으면, 데몬이 이미지 레지스트리에 닿을 때 그 프록시로 나가는 경로가 정해진다.

4동작 과정

  1. ipv6 와 fixed-cidr-v6 로 주소 대역 지정데몬 설정에 IPv6 사용 여부와 배정할 주소 범위를 적으면 브리지가 그 범위에서 컨테이너마다 고유한 IPv6 주소를 붙인다.
  2. HTTP_PROXY·HTTPS_PROXY 로 외부 경로 지정프록시 서버 주소와 포트를 환경 변수로 주면 데몬과 컨테이너가 밖으로 나가는 요청이 그 서버를 통과한다. 인증이 필요하면 사용자 정보까지 같은 값 안에 넣는다.
  3. NO_PROXY 로 우회 대상 지정프록시를 거치면 안 되는 주소(사내망 대역, 127.0.0.1 같은 로컬 주소)를 NO_PROXY 에 나열하면 해당 대상 요청만 프록시를 건너뛰고 직접 나간다.

로그 드라이버

컨테이너가 표준 출력·오류로 출력한 내용을 어디로 보낼지 정하는 데몬 설정으로, json-file·local·journald·syslog 같은 기본 드라이버와 플러그인 드라이버가 있다.

1문제 상황

컨테이너는 표준 출력과 표준 오류로만 자기 동작을 알린다. 기본 설정에서는 그 줄단위를 json-file 드라이버가 호스트의 /var/lib/docker/containers/<id>/<id>-json.log 라는 파일에 통째로 쌓는다. 커널이 이 파일을 열고 있는 동안에도 계속 자라므로, 디스크가 차고 재시작할 수 없게 된다.

또한 한 호스트에서 돌아가는 컨테이너가 여럿이면 그 파일들이 흩어져 있고, 어디에 무슨 로그가 있는지 알 방법이 없다. 로그를 따로 모아 볼 저장소로 보내는 것도 설정으로 제공되지 않는다.

2핵심 질문

컨테이너가 남긴 표준 출력 로그를 어디로 보낼지 고르고, 용량이 무제한으로 차는 문제를 막으려면 어떻게 설정합니까?

3동작 예시

데몬 설정의 "log-driver": "local" 한 줄로 드라이버를 갈아 끼우면, 로그가 파일 하나에 모이되 드라이버가 원형 버퍼 형태로 관리해 설정한 크기까지만 남기고 오래된 줄을 지운다. 이미지 빌드 단계에 쓰인 로그는 docker buildx 명령이 만드는 빌더 데몬의 설정에서 따로 정한다.

4동작 과정

  1. 드라이버 선택json-file, local, journald, syslog, fluentd, awslogs 등 기본 드라이버나, 플러그인 드라이버 중 하나를 데몬 설정의 log-driver 에 고른다. 드라이버마다 따로 플러그인을 먼저 설치해야 하는 것도 있다.
  2. 드라이버별 옵션 지정log-opts 에 드라이버 고유의 값을 넣는다. local 은 max-size와 max-file 로 파일 크기와 개수를 정해 회전시키고, syslog 은 syslog-address 로 보낼 대상을 정한다.
  3. 컨테이너별 덮어쓰기docker run --log-driver 로 특정 컨테이너만 다른 드라이버를 쓰게 할 수 있고, 그 컨테이너에서는 표준 출력으로 나온 줄만 기록한다.

로그 포맷과 원격 로깅

로그 드라이버가 한 줄씩 남기는 형식을 log-opts와 Go 템플릿으로 바꾸는 방법과, 원격 드라이버를 쓸 때도 docker logs 로 로컬에서 읽어 보는 방법을 다룬다.

1문제 상황

원격 로그 수집 드라이버를 쓰면 컨테이너 로그는 호스트를 떠나 중앙 저장소로 바로 나간다. 구조가 잘 잡힌 저장소라면 문제없지만, 어떤 드라이버는 한 줄마다 고정된 키 이름(log, stream, time)으로 값을 채워 보낸다. 애플리케이션이 같은 이름의 필드를 이미 가진 상태에서 그 값이 뒤집히면, 원래 가지고 있던 정보가 사라진다.

또한 원격 드라이버로 바꾸면 예전처럼 docker logs 로 그 컨테이너의 내용을 볼 수 있는지가 애매해진다. 설정만 바꿨다고 로컬 파일이 그만해 생기지는 않는다.

3동작 예시

--log-opt tag="{{.Name}} {{.ID}}" 처럼 태그에 템플릿을 넣으면, myapp 컨테이너의 각 줄이 myapp.web 1a2b3c 라는 이름과 ID가 붙은 상태로 수집 서버에 도착한다. 그 상태에서 docker logs 를 실행하면 드라이버가 같은 기록을 다시 요청해 화면에 띄운다.

4동작 과정

  1. 드라이버를 원격으로 지정데몬 설정이나 컨테이너 실행 옵션으로 fluentd, awslogs, splunk 같은 원격 드라이버를 고르고, log-opts 로 보낼 서버 주소와 인증 정보를 넣는다.
  2. log-opts 와 Go 템플릿으로 포맷 지정드라이버가 남기는 한 줄의 형식을 log-opts 의 labels, tag, env, extras 같은 키와 {{.Name}}, {{.ID}} 같은 템플릿 자리표시자로 제어한다.
  3. docker logs 로 확인원격 드라이버는 일반 컨테이너에 대해 docker logs 가 아직 지원되지 않으므로, docker logs -f <컨테이너> 형태로 로컬에서 다시 읽어 보는 방식을 구분해 쓴다.

5한 줄 요약

데몬 실행과 문제 해결

dockerd 를 직접 실행해 데몬을 띄우고, 데몬 로그와 SIGUSR1 스택 트레이스를 읽어 오류와 잘못된 설정의 원인을 찾는 방법.

1문제 상황

설정을 바꾼 뒤 컨테이너가 시작되지 않으면 원인이 메시지 하나에 다 담기지 않는다. 데몬이 어떤 파일을 읽다가 멈췄는지, 어떤 설정 항목이 잘못됐는지, 드라이버 로딩에서 실패했는지 를 순서대로 따로 알려주지 않는다. 설정을 되돌리려 해도 지금 도는 데몬이 어떤 값으로 떠 있는지 먼저 확인해야 하는데 그것도 보통은 어렵다.

데몬이 살아 있는 동안 그 안에서 실행 중인 스레드가 어디서 멈춰 있는지를 볼 수 있는 수단도 기본 제공되지 않는다.

2핵심 질문

데몬이 시작되지 않거나 이상하게 동작할 때, 어떤 설정이 문제인지와 지금 어떤 상태인지를 직접 확인하려면 어떻게 합니까?

3동작 예시

dockerd --debug --log-level=debug 로 직접 실행하면 어떤 옵션이 어디서 읽혔는지와 어떤 단계에서 실패했는지 순서대로 출력된다. 여기에 kill -SIGUSR1 <dockerd PID> 를 한 번 보내면, 그 시점의 모든 고루틴 스택 트레이스가 로그로 쏟아져 어느 동작에서 막혔는지 볼 수 있다.

4동작 과정

  1. 데몬을 직접 실행해 로그를 본다dockerd 를 터미널에서 직접 실행하고 --debug 같은 로그 수준을 붙여, 설정 파싱과 드라이버 로딩 단계를 지나며 무슨 일이 일어나는지 출력으로 확인한다.
  2. SIGUSR1 로 스택 트레이스를 받는다도는 dockerd 프로세스에 SIGUSR1 신호를 보내면, 그 순간의 모든 고루틴 스택이 로그에 찍힌다.
  3. SIGUSR2 로 데몬을 종료한다정상 종료 신호인 SIGINT 나 SIGTERM 대신 SIGUSR2 를 보내면, 대기 중인 작업을 마친 뒤 종료 지점을 로그로 남기고 조용히 나간다. 실행 중인 채 검사할 때 쓰는 방식이다.

메트릭과 트레이스 수집

데몬의 Prometheus 엔드포인트에서 CPU·메모리 등 성능 지표를 긁어 모으고, docker stats 로 실행 중인 컨테이너의 수치를 실시간으로 확인하는 방법.

1문제 상황

docker ps 는 어떤 컨테이너가 떠 있는지와 상태만 알려줄 뿐, CPU나 메모리를 얼마나 쓰고 있는지는 보여주지 않는다. 컨테이너가 느려졌다고 했을 때 어느 컨테이너가 원인이며 브리지를 지나는 트래픽이 어느 정도인지를 숫자로 남겨 두지 않으면 나중에 같은 상황을 다시 재현해서 봐야 한다.

엔진 안에서 이미 쌓이는 지표가 있는데도 그것을 꺼내 보는 표준 방법이 정해져 있지 않다.

2핵심 질문

엔진과 컨테이너의 성능 지표를 정해진 형식으로 정기적으로 긁어 모을 수 있게 하려면 어떻게 설정합니까?

3동작 예시

데몬 설정의 "metrics-address": "127.0.0.1:9323" 한 줄로 노출 주소를 정해 두면, curl http://127.0.0.1:9323/metrics 를 찍는 순간 컨테이너 CPU 사용 시간, 메모리 사용 바이트, 이미지 수 같은 값들이 Prometheus 가 읽는 텍스트 형식으로 한 줄씩 나온다. Prometheus 는 이 주소 주기를 정해 두고 반복해서 긁어 간다.

4동작 과정

  1. 메트릭 엔드포인트 노출데몬 설정의 metrics-address 로 주소와 포트를 지정해 두고, 같은 항목의 metrics-path 로 경로를 바꿀 수 있다. 주소는 기본값으로 외부에서 아무나 접근하지 못하게 로컬로만 묶인다.
  2. 수집 항목 선택metrics-loglevel 값에 따라 어떤 지표를 남길지 고른다. address-groups 로 브리지 네트워크 계층 지표를 켜고, subnet-groups 로 서브넷별로 나눠 본다.
  3. 컨테이너 단위 수치 확인Prometheus 로 모은 값은 cAdvisor 같은 소비자나 /var/run/docker.sock 을 통해 docker stats 계열로도 실시간 수치를 확인할 수 있다.

Docker Desktop 화면으로 다루기

Docker Desktop 대시보드의 Containers·Images·Builds·Logs·Kubernetes 화면에서 컨테이너와 이미지를 확인하고 다루는 GUI 사용법.

1문제 상황

컨테이너를 만들고 확인하고 지우고 이미지까지 관리하는 일은 보통 명령어로 한다. 하지만 여러 대의 컴퓨터에 같은 환경을 맞추거나, 처음 Docker 를 접하는 사람에게는 명령어 하나하나가 진입 장벽이 된다. 어떤 명령이 무엇을 하는지 외우지 않은 상태에서 조작하다 보면 엉뚱한 컨테이너를 지우거나, 어떤 이미지가 어디에 쓰이는지 몰라 정리하지 못하는 상황이 생긴다.

한편 GUI 도구를 쓰면 상태가 화면 뒤에 숨어서 자동화나 스크립트로는 다시 쓸 수 없다는 문제도 생긴다.

2핵심 질문

3동작 예시

여러 컨테이너로 이루어진 애플리케이션을 하나의 단위로 정의하고 한 번에 실행·관리하게 해 주는 도구와 그 설정 파일의 총칭이다.

1문제 상황

웹 애플리케이션 하나를 띄우려면 웹 서버 컨테이너, 데이터베이스 컨테이너, 캐시 컨테이너를 각각 명령어로 만들고, 그 사이에 필요한 포트 연결과 환경 변수, 볼륨 설정을 손으로 적어 주어야 한다. 하나를 바꾸면 나머지에도 손이 가고, 순서까지 신경 써야 해서 실행 순서가 꼬이면 다시 처음부터 확인해야 한다.

이렇게 한 번에 실행해야 하는 여러 컨테이너의 조합을 문서로 남겨 두고 팀 전체가 같은 설정으로 반복해 쓰는 수단이 없다.

2핵심 질문

여러 컨테이너로 이루어진 애플리케이션을 하나의 설정으로 정의하고, 그 설정 하나만 실행하면 전부 함께 올라오게 하려면 어떻게 합니까?

3동작 예시

4동작 과정

  1. Compose 파일로 단위를 정의여러 서비스의 이미지, 환경 변수, 포트, 볼륨, 의존 관계를 하나의 YAML 파일에 적는다. 이 파일과 관련 명령 전체를 Compose 라고 부른다.
  2. 네트워크를 만들어 컨테이너를 붙인다별도 설정을 안 쓰면 프로젝트마다 Compose 가 이름이 붙은 네트워크를 하나 만들어 그 안에 있는 서비스끼리 이름으로 통신할 수 있게 하고, 정한 순서대로 컨테이너를 띄운다.
  3. 여러 기능으로 운영한다up / down 으로 전체를 함께 다루고, logs 로 지정한 서비스만 따라 보고, 파일이 바뀌면 up --build 로 다시 만든다.

Compose 파일 구조와 사양

Compose 파일은 services·networks·volumes 같은 최상위 요소로 구성되는 YAML 문서이며, 이 구조와 속성 규칙을 정한 것이 Compose Specification 이다.

1문제 상황

여러 컨테이너를 한꺼번에 띄우려면 예전에는 docker run 명령을 컨테이너 개수만큼 직접 입력해야 했습니다. 실행 순서나 네트워크 연결 조건을 명령줄에 다 적지 못하면 순서 제어가 어렵고, 같은 설정을 매번 같은 순서로 다시 입력해야 합니다.

사람마다 명령어 옵션 순서를 다르게 적어 같은 구성도 서로 다르게 실행됐습니다. 요구하는 앱의 형태를 문서 하나로 고정해 두고, 그 문서를 읽는 도구로 동일한 구성을 재현할 수 있는 방법이 필요했습니다.

2핵심 질문

여러 컨테이너로 이루어진 애플리케이션 구성을 문서 하나에 어떻게 표준으로 적고, 그 문서를 그대로 실행할 수 있는가?

3동작 예시

YAML 파일의 최상위에 services (실행할 컨테이너 목록), networks (컨테이너가 서로 붙는 네트워크), volumes (데이터를 밖으로 빼는 저장 공간) 같은 요소를 나열하고, 그 아래에 각 항목을 들여쓰기로 배치합니다. 이 파일 형식과 속성 이름·속성값의 규칙을 정한 것이 Compose Specification 이고, 이 사양을 읽고 실행하는 것이 Docker Compose 입니다.

4동작 과정

  1. 요소 분리services, networks, volumes, configs, secrets 를 최상위에 각각 둡니다. 각 요소는 이름이 붙은 덩어리이며, 서로 다른 종류의 자산을 한 파일에서 구분해 관리하게 합니다.
  2. 사양 기반 검증속성 이름과 값의 형식은 Compose Specification 이 정한 규칙을 따릅니다. 규칙에 어긋난 파일은 실행 전에 걸러지고, 사양을 따르는 도구는 어느 것이든 같은 설정을 같은 뜻으로 읽습니다.
  3. 실행docker compose up 명령이 이 파일을 읽어 최상위 요소들을 해석한 뒤, services 에 적힌 컨테이너를 이미지와 설정대로 만들어 띄웁니다. 파일 하나가 애플리케이션 전체의 구성을 정의하는 단위가 됩니다.

5한 줄 요약

여러 컨테이너로 구성한 앱의 구성을 최상위 요소로 나눠 담은 YAML 문서를 표준 사양으로 정의하고, 그 문서를 그대로 실행하게 하는 것

서비스 정의와 최상위 요소

1문제 상황

docker run 으로는 컨테이너 하나를 시작하는 것까지는 되지만, 그 컨테이너가 어떤 이미지로 만들어지고 어떤 명령을 실행하며 어떤 포트를 열어 주고 어디에 데이터를 남기는지를 전부 명령줄에 나열해야 합니다. 설정이 길어질수록 무엇이 무엇에 대응하는지 찾기 어렵고, 같은 설정을 다른 사람이 그대로 재현하기 어렵습니다.

2핵심 질문

컨테이너 실행에 필요한 모든 속성을 어디에 어떻게 적어야 여러 컨테이너 구성을 사람이 읽고 도구가 함께 다루는 형태로 정리되는가?

3동작 예시

services 아래에 web 이라는 이름을 붙인 항목 하나를 두고, 그 안에 image (어느 이미지를 쓸지), command (컨테이너 안에서 실행할 명령), ports (호스트와 어떤 포트로 연결할지), volumes (어느 디렉터리를 붙일지) 를 들여쓰기로 나열합니다. 서비스 옆에는 networks, volumes, configs, secrets 같은 최상위 요소가 붙어 네트워크와 데이터, 설정값, 비밀값을 따로 정의하고 참조합니다.

4동작 과정

  1. 서비스 항목 작성services 아래에 서비스 이름을 정하고, 그 안에 이미지·명령·환경 변수·포트·볼륨·의존 서비스 등 실행에 필요한 속성을 채웁니다. 속성 이름과 값의 형식은 Compose 파일 레퍼런스가 정한 규칙을 그대로 씁니다.
  2. 최상위 요소 정의networks 에 네트워크를, volumes 에 볼륨을 정의하고, configs 와 secrets 에 설정 파일과 비밀값을 정의합니다. 서비스 항목은 이름으로 이들을 참조만 합니다.
  3. 연결과 실행docker compose up 이 서비스 항목을 읽어 컨테이너를 만들고, 참조된 네트워크에 붙이고, 볼륨을 마운트한 뒤 컨테이너 안에서 명령을 실행합니다. 참조 대상이 정의되지 않은 이름이 있으면 실행 전에 오류가 납니다.

변수 치환과 환경 변수

Compose 파일 안의 ${변수} 표기를 실행 시점의 환경 변수나 .env 파일의 값으로 바꿔 넣는 기능으로, 하나의 파일을 여러 환경에서 재사용하게 해 준다.

개발할 때와 운영할 때 같은 애플리케이션 구성을 쓰면서도 환경마다 다른 값이 필요합니다. DB 호스트 주소, 로그 레벨, 포트 번호 같은 것을 매번 파일을 복사해 고치면 어떤 파일이 어떤 환경용인지 알 수 없고, 수정한 버전을 되돌리는 것도 어려워집니다.

2핵심 질문

값이 달라지는 자리만 파일 안에서 표시해 두고, 실제 값은 실행하는 시점에 외부에서 넣어 어떻게 하나의 파일을 여러 환경에서 재사용하는가?

3동작 예시

4동작 과정

  1. 표기 작성파일 안에서 값이 달라질 자리마다 ${변수} 또는 $변수 형태의 표기를 남깁니다. 표기는 그대로 저장해 두고 실제 값은 적지 않습니다.
  2. 값 주입실행 시점의 환경 변수, 같은 폴더의 .env 파일, 그리고 env_file 로 지정한 파일 순서로 값을 찾습니다. 여러 출처에 같은 이름이 있으면 앞의 것이 이깁니다.
  3. 치환 후 실행읽어 들인 파일의 모든 표기를 값으로 바꾼 결과를 컨테이너 생성에 사용합니다. 바꿔 넣은 값은 env 항목으로 컨테이너 안의 환경 변수로도 전달되므로, 같은 파일이 여러 환경에서 그대로 재사용됩니다.

Compose 에서 이미지 빌드하기

Compose 파일의 build 항목에 Dockerfile 과 빌드 인자를 적어 두면 docker compose build 가 그 설정대로 이미지를 만들어 컨테이너 실행에 사용한다.

1문제 상황

애플리케이션에 필요한 이미지를 만들려면 Dockerfile 을 따로 만들고 docker build 를 실행한 뒤, 그 결과를 Compose 파일의 image 항목에 이름으로 적어야 합니다. 빌드 과정에 옵션을 주려면 명령줄에 계속 덧붙여야 하고, 빌드 설정과 실행 설정이 서로 다른 곳에 흩어집니다.

2핵심 질문

어떤 Dockerfile 로 이미지를 만들고 어떤 인자를 넘길지를 실행 설정과 한 파일에 함께 적어, 이미지 빌드와 컨테이너 실행을 한 번의 선언으로 연결하는가?

3동작 예시

서비스 항목에 image: myapp:1.0, build: { context: ., dockerfile: Dockerfile } 를 적어 둡니다. docker compose build 를 실행하면 이 설정을 읽어 지정한 경로의 Dockerfile 로 이미지를 만들어 myapp:1.0 이라는 이름으로 저장하고, 이후 docker compose up 이 그 이미지를 그대로 사용합니다.

4동작 과정

  1. 빌드 설정 작성서비스 항목의 build 에 빌드 컨텍스트(어느 폴더를 빌드 대상으로 삼을지), dockerfile (사용할 Dockerfile 이름), 그리고 args(빌드 인자)를 적습니다. image 를 함께 적어두면 빌드 결과의 이름이 정해집니다.
  2. 빌드 실행docker compose build 가 각 서비스의 build 설정을 읽어 레이어를 캐시하며 이미지를 만듭니다. args 값은 Dockerfile 안의 ARG 로 전달되고, --build-arg 로 실행 시점에 덮어쓸 수도 있습니다.
  3. 실행 연결만들어진 이미지가 image 에 적은 이름으로 저장되면 docker compose up 이 그 이름을 그대로 찾아 컨테이너를 시작합니다. docker compose up --build 를 쓰면 실행 전에 빌드까지 이어서 수행합니다.

5한 줄 요약

빌드에 필요한 Dockerfile 경로와 인자를 Compose 파일의 build 항목에 적어, 이미지 제작과 컨테이너 실행을 하나의 선언으로 묶는 것

docker compose watch 처럼 소스 코드가 바뀔 때마다 컨테이너를 자동으로 다시 빌드하거나 동기화해 주는 개발 편의를 위한 기능.

개발 중에는 소스 코드를 고칠 때마다 이미지를 다시 빌드하고 컨테이너를 다시 띄워야 변경 사항이 반영됩니다. 이 과정을 매번 여러 명령으로 직접 수행하면 반복 횟수가 늘어 작업 흐름이 끊기고, 파일을 켜 둔 채 한참을 기다리는 시간이 계속 생깁니다.

2핵심 질문

소스 코드가 바뀐 사실을 감지해서 다시 빌드하거나 파일을 다시 동기화하는 작업을 자동화해, 개발 중 반복되는 리빌드를 어떻게 줄이는가?

3동작 예시

Compose 파일에 develop 항목 안에서 watch 를 적은 뒤, action: sync 와 target: /app/src 를 지정합니다. 이 상태로 컨테이너를 띄워 두고 소스 파일을 고치면, Docker 가 파일 변화를 감지해 빌드 없이 수정된 파일만 컨테이너 안의 지정 경로에 다시 복사합니다.

4동작 과정

  1. 감시 설정서비스 항목의 develop.watch 에 어느 경로를 볼지, 무시할 경로와 파일 확장자를 정합니다. 콘테이너 안에서 반영할 대상 경로도 함께 적습니다.
  2. 변화 감지컨테이너가 실행된 상태에서 파일 시스템 이벤트를 받아 대상 경로의 변경을 알아냅니다. 소스 코드, 설정 파일, 의존성 목록이 각각 다른 경로로 묶여 같은 파일을 여러 경로에 복제하는 일이 생기는 것을 막습니다.
  3. 자동 반영action: sync 면 빌드 없이 파일만 컨테이너에 복사하고, rebuild 면 이미지를 다시 만들어 컨테이너를 교체합니다. 같은 경로에 두 동작을 함께 써 순서를 정할 수도 있습니다.

실행 순서와 수명주기 제어

depends_on 과 healthcheck, pre_start 같은 훅으로 어떤 서비스를 먼저 띄우고 언제 멈출지를 정해 주는 컨테이너 실행 순서와 수명주기 제어 방식.

1문제 상황

여러 컨테이너가 서로 붙는 구성에서는 순서가 중요합니다. 웹 서버는 데이터베이스가 먼저 올라와 있어야 접속을 받을 수 있고, 마이그레이션이 끝나야 애플리케이션이 정상 동작합니다. 그런데 컨테이너가 시작되었다는 사실은 준비가 끝났다는 뜻이 아니어서, 실행 순서만 지정해서는 첫 요청이 실패하거나 처음 접속 시 오류가 납니다.

2핵심 질문

어떤 서비스가 먼저 시작하고 언제 준비가 끝난 뒤 다음 서비스가 올라와야 하는지를, 그리고 컨테이너를 어떤 순서로 멈출지를 어떻게 선언하는가?

3동작 예시

db 서비스에 healthcheck 로 pg_isready 명령을 주어 응답이 정상일 때만 healthy 로 표시하고, api 서비스에 depends_on: { db: { condition: service_healthy } } 를 적습니다. 그러면 docker compose up 이 db 컨테이너를 띄운 뒤 healthcheck 가 통과할 때까지 기다리고 나서 api 컨테이너를 시작합니다.

4동작 과정

  1. 선행 조건 선언depends_on 으로 어떤 서비스가 먼저여야 하는지 적습니다. 단순 목록만 주면 컨테이너가 시작된 시점에 다음 서비스가 올라가며, condition: service_healthy 를 주면 healthcheck 통과를 기다립니다. service_completed_successfully 은 그 서비스가 정상적으로 끝나기를 기다립니다.
  2. 상태 확인과 훅 실행Compose 는 healthcheck 명령을 주기적으로 실행해 상태를 확인하고, pre_start 훅(컨테이너가 시작되기 전에 실행되는 명령)이나 post_start 훅(시작 직후 실행되는 명령)에서 준비 작업을 수행하게 합니다. restart 설정으로 실패 시 재시도 횟수도 정합니다.
  3. 종료 순서 정하기stop_grace_period 을 주면 지정 시간 안에 정상 종료되지 않을 때 강제 종료합니다. 종료는 docker compose stop 이나 down 으로 하며, down 에 --volumes 를 붙이면 함께 만든 볼륨까지 지웁니다.

5한 줄 요약

depends_on 과 healthcheck, 훅으로 선행 서비스가 준비된 뒤 다음 서비스를 띄우고 정해진 순서로 멈추게 하는 것

운영·배포와 확장 기능

deploy 요소로 자원과 배포 방식을 정해 운영 환경에 맞추고, docker compose scale 로 서비스의 인스턴스 수를 늘리는 운영·배포와 확장 기능.

1문제 상황

개발 환경에서 컨테이너 하나씩 띄우는 구성은 운영에 그대로 쓰기 어렵습니다. 운영에서는 여러 호스트에 컨테이너를 나눠 배치하고 자원을 제한하며, 트래픽이 늘면 같은 서비스를 여러 개로 늘려야 합니다. 하지만 docker compose up 은 로컬에서 컨테이너를 만드는 데까지만 처리하고, 자원 배분과 인스턴스 수 조절을 직접 관리해야 합니다.

2핵심 질문

운영 환경에서 각 서비스에 줄 자원과 배치 방식을 어떻게 선언하고, 같은 서비스를 여러 인스턴스로 늘리는 조정은 어디서 수행하는가?

3동작 예시

서비스 항목에 deploy 를 넣어 replicas: 3 (인스턴스 3개)과 resources: { limits: { cpus: '0.50', memory: 128M } } (CPU와 메모리 상한)를 적습니다. 그리고 docker compose up -d --scale web=3 을 실행하면 web 서비스가 3개로 늘어난 채로 유지되고, 정지할 때는 역순으로 내려갑니다.

4동작 과정

  1. 운영 속성 선언deploy 아래에 replicas(인스턴스 수), resources(CPU·메모리 제한과 예약량), restart_policy(재시작 정책), placement(어느 노드에 둘지)를 적습니다. Compose 는 이 설정을 Swarm 같은 오케스트레이터에 전달하는 형태로 다룹니다.
  2. 배포 실행docker compose up -d 로 데몬 모드 백그라운드로 올리고, --scale 서비스=개수 로 인스턴스 수를 조정합니다. docker compose ps 로 상태를, logs 와 exec 로 동작을 확인합니다.
  3. 확인과 회수docker compose config 로 최종 설정을 확인하고, docker compose ps --all 으로 종료된 것까지 봅니다. 정리는 docker compose down 이 담당하며, 종료 순서는 의존 관계를 거슬러 정해집니다.

5한 줄 요약

deploy 항목으로 자원과 배포 방식을 선언하고 docker compose scale 로 서비스 인스턴스 수를 조절해, 같은 구성을 운영 환경에서 늘려 쓰는 것

Docker Hub 자동 빌드와 운영

GitHub 같은 소스 저장소에 코드가 올라오면 Docker Hub 가 대신 Dockerfile 을 빌드해 이미지를 만들고, 그 빌드와 테스트 상태를 관리하는 기능.

1문제 상황

이미지를 만들려면 개발자 컴퓨터나 빌드 서버에서 Dockerfile 을 직접 실행하고, 나온 결과를 레지스트리에push 하는 작업을 반복해야 했다. 이 과정은 같은 커밋마다 누락되고, 만든 이미지가 어느 커밋에서 나왔는지 추적하기도 어렵다.

문제는 사람이 개입하는 지점에서 생긴다. 코드가 올라간 사실과 이미지가 만들어진 시점이 서로 다른 시스템에 기록되므로, 테스트를 통과하지 못한 코드가 그대로 운영 저장소에 도착하는 일도 생겼다.

2핵심 질문

코드 저장소에 코드가 올라오는 순간, 그 코드를 바로 빌드해서 테스트까지 통과한 이미지만 등록소(Registry)에 올려 놓을 수 있는가?

3동작 예시

GitHub 저장소에 Dockerfile 과 소스 코드를 함께 올린다. Docker Hub 는 그 저장소를 감시하고 있다가 커밋이 들어오는 것을 감지하면, 서버 안에서 직접 docker build 를 실행하고 테스트를 돌린다. 통과하면 결과 이미지를 Docker Hub 의 자동 빌드 태그에 저장하고, 실패하면 빌드 상태를 실패로 표시한다. 개발자는 자기 컴퓨터에서 빌드해 볼 필요 없이, 저장소 화면의 빌드 목록에서 성공·실패만 확인한다.

4동작 과정

  1. 자동 빌드 연결Docker Hub 에서 "Automated Build" 을 켜고 GitHub 저장소를 등록한다. 등록 시 Docker Hub 가 사용하는 전용 액세스 토큰을 발급해 저장소에 설치하므로, 앞으로는 저장소 변경 사항을 Docker Hub 가 읽을 수 있다.
  2. 커밋 감지 후 빌드저장소에 새 커밋이 들어오면 Docker Hub 가 브랜치와 Dockerfile 을 읽어 이미지 빌드를 시작한다. 소스 코드와 빌드 로그가 이 요청에 함께 결속된다.
  3. 자동 테스트와 태그 반영빌드 전에 자동 테스트가 실행되고, 테스트와 빌드가 모두 성공하면 지정된 태그로 이미지를 저장한다. 실패하면 이미지는 갱신되지 않고 빌드 상태만 실패로 남는다.
  4. 자동 정리새 빌드가 성공하면 자동 빌드가 만든 이전 이미지 중 지정한 개수만 남기고 나머지를 삭제한다. 무제한으로 쌓이는 이미지 때문에 저장소 용량이 불필요하게 커지는 것을 막는다.

1문제 상황

빌드를 자동화하려면 빌드를 돌릴 서버를 따로 준비하고, 저장소 변경을 그 서버가 듣도록 연결하고, 서버에 Docker 설치와 자격 증명을 매번 심어야 했다. 서버가 몇 개로 늘어나면 그 관리 대상도 같이 늘어나고, 빌드 로그가 서버별로 흩어져 한 번에 확인하기 어려웠다.

기존의 Docker Hub 자동 빌드만 쓰면 빌드 단계에 사용자 정의 작업을 끼워 넣기 어렵고, 어떤 자원으로 빌드했는지도 제어하기 힘들었다. 빌드 과정 자체를 코드로 관리하고 싶은 수요가 생겼다.

2핵심 질문

빌드 과정을 저장소 안의 코드로 직접 정의해서, 아무 서버에서나 같은 조건으로 실행하고 결과를 이미지로 남길 수 있는가?

3동작 예시

저장소에 .github/workflows/build.yml 이라는 워크플로 파일을 둔다. 이 파일은 "main 브랜치에 push 가 일어나면, 빌더를 준비하고, 이미지를 빌드한 뒤 Docker Hub 로그인 정보로 로그인해서 push 한다"를 단계로 적어 둔다. 저장소는 이 파일을 읽고 Runner 라는 실행 환경에서 그대로 실행하며, cache-multistage, provenance, sbom 옵션으로 중간 단계 재사용과 SBOM·서명 정보 첨부를 함께 요청한다.

4동작 과정

  1. 워크플로 트리거.github/workflows/ 아래 YAML 파일에 실행 조건과 단계를 선언한다. push 나 pull_request 같은 이벤트가 조건으로 걸리면 GitHub Actions 가 Runner 를 준비해 해당 단계들을 순서대로 실행한다.
  2. 빌더 준비docker/setup-buildx 액션으로 Buildx 를 설치하고, 여러 플랫폼을 한 번에 빌드할 수 있는 빌더 드라이버(docker-container 등)를 등록한다. docker/setup-qemu-action 을 함께 쓰면 ARM64 같은 다른 아키텍처용 이미지도 같은 단계에서 만들어진다.
  3. 빌드·푸시docker/build-push-action 이 Buildx 를 통해 빌드하고 지정한 레지스트리에 push 한다. cache-from·cache-to 로 이전 빌드 계층을 가져오고 저장해 반복 빌드의 시간을 줄이며, secrets 로 로그인 자격 증명을 주입한다.
  4. 증명 정보 생성sbom: true 로 빌드 결과에 SBOM(컨테이너 안 쓰인 패키지 목록)을 붙이고, provenance: true 로 이미지가 어디서 어떤 소스로 만들어졌는지 기록하는 서명 정보를 함께 생성해 push 한다.

1문제 상황

여러 아키텍처(amd64, arm64 등) 이미지를 만들려면 크로스 컴파일 옵션을 켜거나 QEMU 로 에뮬레이션해야 한다. 후자는 빌드가 아주 느려진다. 이를 피하려면 여러 대의 빌드 머신을 직접 구비해 둘 텐데, 이 머신들은 사용하지 않을 때에도 비용이 나고 관리 대상이 된다.

로컬에서 빌드하면 사양이 좋은 개인 개발자 컴퓨터에 작업이 몰리고, 그 컴퓨터가 빌드로 묶여 있어 다른 개발을 병행하기 어렵다. 빌드 자원을 조직 밖에서 빌려 쓰면서도 빌드 정의는 그대로 코드로 관리하려는 요구가 생겼다.

2핵심 질문

빌드 머신을 직접 소유하지 않고 빌드를 원격으로 수행해 여러 아키텍처 이미지를 빠르게 만들 수 있는가?

3동작 예시

개발자는 로컬에서 평소 쓰던 명령을 그대로 실행하되, 빌드를 수행하는 대상만 Docker Build Cloud 의 관리형 빌더 주소로 지정한다. 빌드는 그 원격 환경에서 실제 CPU 로 아키텍처별 이미지를 만들어 Docker Hub 로 push 되고, 로컬에는 빌드 설정과 로그만 남는다. Docker Offload 를 쓰는 경우에는 저장소에서 정의한 빌드를 Docker Desktop 이 원격으로 그대로 실행해 결과를 가져온다.

4동작 과정

  1. 원격 빌더 연결Docker Build Cloud 에서 조직에 대응하는 빌더를 만들고 빌더 이름을 지정한다. 그 이름을 docker buildx create --builder <이름> 처럼 지정하면 이후 빌드 명령이 그 원격 빌더로 전달된다.
  2. 프록시·캐시 단계빌드 명령은 BuildKit(빌드를 실제로 수행하는 엔진)의 프록시를 통해 원격으로 전달된다. 각 계층은 이전 빌드의 결과와 비교해 그대로 재사용할 수 있는 부분은 재사용하고, 바뀌지 않은 부분만 다시 계산한다.
  3. 아키텍처별 빌드하나의 빌드 정의에서 여러 플랫폼을 지정하면 원격 빌더가 실제 해당 아키텍처 머신에서 각각 빌드해, linux/amd64 과 linux/arm64 이미지가 함께 만들어진다.
  4. 결과 이미지 저장빌드된 각 아키텍처 이미지는 매니페스트로 묶어 레지스트리에 push 되고, manifest list 라는 하나의 이름으로 배포 대상이 지정된다.

빌드 정책으로 빌드 거버넌스

빌드 시점에 규칙(정책)을 걸어 어떤 Git 저장소와 어떤 베이스 이미지를 쓸 수 있는지 제한하고 조직 규칙을 강제하는 거버넌스 장치.

1문제 상황

개발자는 Dockerfile 마다 다른 베이스 이미지를 가져오고, 조직이 금지한 레지스트리나 태그를 그대로 사용한다. 공식 베이스 이미지가 아니라 개인이 만든 이미지를 베이스로 삼는 경우까지 생겼다. 빌드가 끝난 뒤에야 이런 문제를 알면, 이미 배포된 이미지를 회수하고 다시 빌드하는 작업이 되돌아온다.

또한 소스 저장소별로 빌드를 실행하는 주체와 권한이 제각각이라, 어떤 코드가 어떤 자격으로 빌드되는지 기록되지 않는다. 조직 규칙을 문서로만 정해 두고 실제 빌드 흐름에 강제하지 않으면 개발자는 규칙을 지키지 않게 된다.

2핵심 질문

빌드가 실행되는 순간에 조직 규칙을 강제해, 허용되지 않은 소스나 베이스 이미지가 빌드에 사용되지 않게 할 수 있는가?

3동작 예시

정책 관리자 조직이 빌드 정책 문서를 만들고 빌더에 연결한다. 정책에는 "베이스 이미지는 docker.io 와 내부 레지스트리에서만 가져온다" "아키텍처는 amd64 과 arm64 만 허용한다" 같은 조건이 들어간다. 이 정책이 적용된 빌더에서 빌드를 실행하면, 정책을 위반한 Dockerfile 은 빌드가 중단되고 위반한 항목이 도달한 위치가 함께 보고된다.

4동작 과정

  1. 정책 정의빌드 정책 파일에 소스(어떤 Git 저장소에서 오는 코드인지), 베이스 이미지 출처와 아키텍처, 소스 고정 여부, 정책 위반 시 취할 동작을 규칙으로 적는다. 취할 동작은 무시, 경고, 차단 중 하나로 지정한다.
  2. 빌더에 연결정책 관리자 조직이 이 정책 파일을 하나 이상의 빌더(빌드 클라우드 빌더나 조직 내부 빌더)에 적용한다. 연결된 빌더에서 실행되는 모든 빌드는 별도 설정이 없더라도 이 정책을 거친다.
  3. 빌드 시점 검사빌드가 시작되면 베이스 이미지를 가져오는 순간, 소스 코드를 복사하는 순간, 이미지를 레지스트리에 push 하는 순간마다 정책 조건이 검사된다. 소스 고정(pin) 정책이 켜져 있으면 태그가 아니라 다이제스트로 고정된 이미지만 허용된다.
  4. 위반 처리와 보고차단 정책이면 빌드가 중단되고 위반 항목이 보고서에 남는다. Docker Scout 로 정책 위반 목록을 확인해 실제 고칠 대상을 선별하고, 예외 처리로 정책 우회를 명시적으로 기록해 둘 수 있다.

컨테이너 보안 격리와 데몬 보호

seccomp·AppArmor·사용자 네임스페이스로 컨테이너가 호스트를 건드리지 못하게 격리하고, Docker 데몬 소켓 접근을 통제해 호스트를 지키는 보안 설정.

1문제 상황

컨테이너는 호스트 커널을 공유하므로, 안에서 실행되는 프로세스가 허용된 시스템 호출만 쓰게 막지 않으면 컨테이너 하나가 호스트의 중요한 파일이나 다른 컨테이너 영역까지 손댈 수 있다. 특히 소스 코드를 빌드하고 실행하는 CI 환경에서는 외부에서 받은 코드가 그대로 커널 syscall 을 호출하는 영역까지 열어 둔다.

또 다른 문제는 Docker 데몬 접근이다. 호스트의 Docker 소켓에 연결되면 컨테이너 안에서 호스트용 Docker 명령을 실행할 수 있고, 이 경로가 열려 있으면 컨테이너 탈출과 호스트 장악으로 이어질 수 있다. 이 연결 자체를 막는 수단이 필요했다.

2핵심 질문

컨테이너가 호스트와 다른 컨테이너를 건드리지 못하도록 시스템 호출 수준에서 제한하고, 호스트 Docker 데몬 접근까지 차단할 수 있는가?

3동작 예시

컨테이너가 시작될 때 커널이 허용한 시스템 호출 목록만 담긴 seccomp 프로필을 그대로 적용한다. 예를 들어 mount, reboot, ptrace 같은 호출은 목록에서 빠져 있어, 컨테이너 안의 프로세스가 이 호출을 시도하면 커널이 즉시 실패시킰다. Docker 기본값으로도 대부분의 시나리오를 막고, 직접 만든 프로필을 넘기면 필요한 호출만 남길 수도 있다.

4동작 과정

  1. 시스템 호출 차단컨테이너 생성 시 seccomp 프로필을 지정해 허용 목록에 없는 시스템 호출을 커널 단계에서 거부한다. Docker 는 기본 프로필로 위험한 호출 대부분을 막으며, AppArmor 프로필을 함께 지정하면 파일 접근 경로까지 제한할 수 있다.
  2. 사용자 네임스페이스 격리컨테이너 안의 프로세스를 호스트 사용자 ID 가 아닌 매핑된 ID 로 실행한다. 컨테이너가 만든 파일이 호스트에서 별도 소유자로 보이고, 권한 상승(system call 을 통한 관리자 권한 획득)이 원천적으로 막힌다.
  3. 데몬 접근 차단컨테이너에 호스트의 /var/run/docker.sock 을 마운트하지 않으면 컨테이너 안에서는 Docker 명령을 실행할 수 없다. 필요할 경우 소켓 프록시를 두어 허용된 API 만 중계하게 하고, rootless 모드로 데몬 자체를 사용자 권한으로 실행하는 방법도 쓴다.
  4. 제한 범위 지정읽기 전용 루트 파일시스템, 마운트 금지(--privileged 사용 제한), 메모리·CPU 상한 같은 옵션을 함께 지정해, 설정을 통과한 코드도 임의로 확장되지 않도록 범위를 정한다.

5한 줄 요약

시스템 호출과 사용자 권한 수준에서 컨테이너의 권한을 제한해 호스트를 침범할 수 없게 만드는 것

Docker Scout 로 취약점 관리

Docker Scout 로 이미지 안의 패키지와 알려진 취약점(CVE)을 분석·추적하고, 예외 처리와 정책 평가로 실제로 고칠 대상만 골라내는 방법.

1문제 상황

이미지 하나에는 운영 체제 패키지와 응용 프로그램 패키지가 함께 들어 있어, 취약점이 있는 항목이 대개 수십 개에서 나 hundred 개까지 나온다. CVE 로 등록된 취약점 목록을 사람이 대조해 정리하려면 이미지가 바뀔 때마다 반복해서 전부 뒤져야 하고, 실제로 사용할 함수나 패키지를 쓰지 않는 항목도 결과에 섞여 그대로 보고하면 무엇을 고칠지 판단하기 어렵다.

결국 이미지 스캔 결과를 읽는 능력이 있는 사람에게 작업이 몰리고, 취약점이 있어도 조치 여부는 개인의 판단으로 방치된다. 무엇이 영향을 주는지 판단하는 기준과 그 기준을 조직에 공유하는 절차 자체가 필요하다.

2핵심 질문

이미지 안의 패키지 중 실제로 고쳐야 할 취약점만 골라내고, 그 상태를 정책로 만들어 계속 확인되게 할 수 있는가?

3동작 예시

로컬에 이미지를 받아 docker scout cves 를 실행하면 그 이미지의 레이어 단위로 SBOM(패키지 목록)을 읽어 CVE 와 매칭한다. 여기서 --only-severity critical 로 수준을 좁히고, --only-fixed 로 수정 버전이 존재하는 항목만 남기면 우선순위가 명확해진다. 같은 결과는 Docker Hub 의 이미지 화면에서도 바로 볼 수 있다.

4동작 과정

  1. SBOM 기반 분석이미지에 포함된 SBOM 을 읽어 각 패키지의 이름·버전·출처를 확인하고, 이 조합에 해당하는 알려진 취약점(CVE)과 매칭해 심각도별로 목록을 만든다.
  2. 트리 형태로 위치 확인취약점이 들어 있는 패키지가 어느 레이어에서 왔는지 트리 구조로 보여 준다. 베이스 이미지에서 들어온 것인지 자체 빌드 단계에서 추가한 것인지 구분해 조치 지점을 정할 수 있다.
  3. 예외 처리로 실제 대상 선별패키지 단위로 예외 처리를 등록해 조직이 감수하기로 한 항목은 보고서에서 제외한다. 기준이 정해지면 docker scout cves --only-severity 로 수준을 나눠 확인하고, --only-fixed 로 수정이 있는 항목만 추려 실제로 고칠 목록을 만든다.
  4. 정책 평가와 비교docker scout policies 로 기준 정책을 만들고 docker scout quickview 로 이전 기준과 현재 결과를 비교한다. 기준 대비 악화된 항목을 CI 에서 실패로 처리해, 취약점이 다시 늘지 않게 상시 확인한다.

5한 줄 요약

조직 인증과 권한 관리

Docker 조직에서 SSO·액세스 토큰·OIDC 로 인증을 붙이고, 역할(Member·Editor·Owner)과 커스텀 역할·프로비저닝으로 사람과 자동화 시스템의 권한을 나누는 관리 체계.

1문제 상황

개인 계정으로 Docker Hub 를 쓰면 계정 하나에 모든 권한이 몰리고, 누가 어떤 이미지를 만들고 지웠는지 이력이 남지 않는다. 팀원에게 계정을 나누어 주면 비밀번호를 서로 공유하게 되고, 누가 푸시했는지 구분할 수 없다. 이력을 사후에 확인하려면 결국 계정을 사람 수만큼 파고들어야 한다.

사람만 필요한 것은 아니다. CI/CD 파이프라인, 자동 배포 도구 같은 자동화 시스템도 레지스트리에 이미지를 push 하고 pull 해야 하는데, 사람이 쓰는 계정으로 하면 그 계정이 언제 어디서 쓰였는지 알 수 없다. 사람과 자동화 시스템의 권한을 분리하고 조직 단위로 통제할 수단이 필요했다.

2핵심 질문

사람과 자동화 시스템의 신원을 분리해 인증하고, 각각에게 필요한 권한만 부여하고 그 사용 이력을 남길 수 있는가?

3동작 예시

회사가 이미 쓰는 계정 체계(IdP)를 Docker 조직에 연결해 SSO(SAML 또는 OIDC)를 연다. 그 뒤 구성원 계정을 조직 소속으로 초대하고 역할(Member, Editor, Owner)을 붙인다. 이 조직 아래에 팀을 만들고 팀별로 저장소 접근 권한을 주면, 저장소 단위 권한 관리가 가능해져 개인별 권한을 일일이 조정하지 않아도 된다.

4동작 과정

  1. SSO 연결Docker 조직 설정에서 SAML 또는 OIDC 방식으로 조직의 IdP 를 연결하고 도메인 목록을 등록한다. 이후 구성원은 개인 비밀번호가 아니라 조직 계정으로 로그인하며, IdP 에서 탈퇴하면 곧바로 접근이 끊긴다.
  2. 권한 주체 등록개인은 조직에 구성원으로 초대하고 역할을 부여한다. Member 는 읽기, Editor 는 저장소 변경, Owner 는 조직과 결제 설정을 포함한 전부 권한을 갖는다. 직접 만든 역할로는 저장소 단위 권한과 특정 저장소 제한 권한을 세분화할 수 있다.
  3. 자동화 시스템용 자격 증명조직 액세스 토큰(읽기 전용·쓰기·테스트 토큰)을 발급해 CI 파이프라인에 등록한다. 개인 계정과 분리되므로 토큰이 어디에 쓰였는지 식별할 수 있고, 권한도 필요한 범위만 부여한다.
  4. 프로비저닝과 이력 관리SCIM 같은 프로비저닝으로 계정 생성과 삭제를 조직 계정 체계와 연동해 일치시키고, 조직 관리 화면에서 구성원·권한 변경 이력을 확인해 주기적으로 권한을 다시 검토한다.

5한 줄 요약

사람과 자동화 시스템의 신원을 분리해 인증하고 필요한 권한만 부여해 조직 단위로 통제하는 것

Swarm 모드 핵심 개념

여러 Docker Engine 호스트를 하나의 클러스터로 묶어 컨테이너를 Orleans 방식으로 자동 배치·재배치하는 Docker Engine 내장 오케스트레이션 기능.

1문제 상황

기존에는 docker run 으로 컨테이너를 하나씩 띄우는 방식이었다. 여러 서버에 같은 애플리케이션을 올리려면 각 서버에 접속해 같은 명령을 반복해서 실행해야 했고, 서버 하나가 꺼졌을 때 그 위에서 돌던 컨테이너를 다른 서버로 옮기는 것도 사람이 직접 처리했다. 몇 대에 몇 개를 배치할지 어디로 옮길지를 사람이 정해 실행하는 방식이라, 서버가 늘어날수록 관리 비용이 그대로 늘어난다.

2핵심 질문

여러 Docker 호스트를 하나의 클러스터로 묶고, 컨테이너 하나가 죽으면 자동으로 다른 곳에서 다시 실행되게 만들 수 있는가?

3동작 예시

docker service create --replicas 3 nginx 를 실행하면 스웜이 준비된 노드 세 곳에 같은 이미지로 태스크를 하나씩 띄운다. 그중 한 노드가 꺼졌다고 하면, 스웜은 그 노드에 있던 태스크를 살아 있는 다른 노드로 다시 배정해 실행 개수를 3개로 맞춘다. 어느 서버에 몇 개를 둘지는 사용자가 직접 고르지 않고, 스웜이 노드 상태를 보고 정한다.

4동작 과정

  1. 노드(Node)Docker Engine 이 돌아가는 서버 한 대를 가리킨다. 스웜에 편입되면 관리자(manager) 또는 작업자(worker)라는 역할이 붙는다.
  2. 서비스(Service)어떤 이미지를 몇 개 실행할지를 선언한 단위다. 스웜이 관리하는 대상은 개별 컨테이너가 아니라 이 서비스 선언이다.
  3. 태스크(Task)서비스가 노드 위에서 실제로 실행하는 컨테이너 하나다. 스웜은 서비스의 조건에 맞는 노드를 골라 태스크를 붙이고, 노드가 죽으면 그 태스크를 다른 노드로 다시 배정한다.

12다중 노드 운영과 도구 확장12-02

클러스터 생성과 노드 관리

매니저 노드를 하나 골라 스웜을 초기화한 뒤 워커·매니저 노드를 붙이고, 노드 promote/drain/rm 같은 명령으로 클러스터 구성을 관리하는 것.

1문제 상황

서버가 여러 대면 그중 한 대를 골라 스웸을 시작하고, 새로 확보한 서버를 어느 시점에 편입시킬지 정해야 한다. 편입된 서버는 상태가 다 같지 않고, 작업을 그만 받아야 하는 시점이 필요할 때도 있다. 노드가 여러 대인 만큼 이 절차를 서버마다 수동으로 실행하고, 전체 상태를 따로 확인해야 하는 부담이 생긴다.

2핵심 질문

스웸을 시작하고 서버를 편입시키는 절차를 어떻게 실행하고, 편입된 서버의 상태와 작업을 어떻게 관리하는가?

3동작 예시

관리할 서버 세 대 중 한 대에서 docker swarm init --advertise-addr <IP> 를 실행하면 그 서버가 관리자 노드가 되어 스웸이 시작된다. 나머지 서버에서는 docker swarm join --token <토큰> <관리자IP> 를 한 번 실행하기만 하면 작업자 노드로 편입된다. 편입 후 docker node ls 로 각 노드의 상태를 보고, 작업을 잠시 빼려면 docker node update --availability drain <노드> 를 실행한다.

4동작 과정

  1. 스웸 초기화와 편입docker swarm init 이 관리자 노드를 만들고 워커 조인 토큰(worker join token)을 발급한다. 다른 서버는 그 토큰으로 docker swarm join 을 실행해 작업자 노드로 등록된다.
  2. 노드 상태 확인과 역할 조정docker node ls 로 전체 노드 상태를 보고, docker node promote 으로 작업자를 관리자로 올린다. docker node update --availability drain 으로 지정한 노드에는 새 태스크를 배정하지 않고 기존 태스크만 마저 돌린다.
  3. 노드 제거drain 으로 작업을 비운 뒤 docker node rm 으로 클러스터에서 뺀다. 제거 대상 서버가 이미 꺼졌거나 복구가 불가능하면 docker swarm leave 로 그 서버에 남아 있는 스웠 정보까지 지운다.

5한 줄 요약

관리자 노드 하나를 정해 스웸을 시작하고, 워커 노드를 붙이거나 빼고 promote·drain·rm 같은 명령으로 클러스터 구성을 관리하는 것

서비스 배포와 라우팅

docker service create/update 로 이미지 복제본과 제약 조건을 선언해 여러 노드에 태스크로 스케줄하고, 서비스 이름으로 접근할 수 있게 라우팅하는 것.

1문제 상황

여러 서버에 컨테이너를 띄우려면 서버별 실행 명령이나 호스트 설정 파일에 컨테이너 목록을 직접 적어 두고 각 서버에 같은 내용을 반영해야 했다. 반영 시점이 서버마다 달라 중간에 상태가 어긋났고, 요청을 어느 서버로 보낼지 결정하는 일도 각 서버의 설정을 따랐다. 이미지나 설정을 바꾸면 전체 서버를 다시 배포하는 절차를 새로 거쳐야 했다.

2핵심 질문

이미지 몇 개를 띄울지와 어디에 띄울지 제약 조건만 선언하면, 여러 노드에 컨테이너를 나눠 배치하고 하나의 이름으로 요청을 받을 수 있는가?

3동작 예시

docker service create --name web --replicas 4 -p 8080:80 nginx:alpine 을 실행하면 스웜은 nginx 태스크 4개를 각 노드에 하나씩 배정하고, 어떤 서버에서 8080 포트로 들어온 요청이 4개 태스크 중 하나로 전달되도록 라우팅을 설정한다. 나중에 이미지를 바꾸려면 docker service update --image nginx:1.27 web 한 줄로 태스크를 하나씩 교체한다.

4동작 과정

  1. 서비스 선언docker service create 에 이미지, 복제본 수(--replicas), 포트 게시(-p), 배치 조건(--constraint, --placement-pref)을 함께 적어 원하는 상태를 선언한다.
  2. 스케줄링과 태스크 배치스웜의 스케줄러가 조건에 맞는 노드를 골라 태스크를 하나씩 붙이고, 노드가 죽으면 남은 복제본 수를 채우도록 다른 노드로 다시 배정한다.
  3. 라우팅과 롤링 업데이트ingress 오버레이 네트워크(스웜이 노드들을 이어 만든 논리적 네트워크) 위에서 서비스 이름으로 접근하게 하고, docker service update 는 태스크를 한 번에 하나씩 교체해 요청이 끊기지 않도록 갱신한다.

5한 줄 요약

이미지와 복제본 수, 배치 조건을 선언해 여러 노드에 태스크로 스케줄하고 서비스 이름으로 접근하게 라우팅하는 것

플러그인과 Docker Extensions

Docker에 기본으로 없는 기능을 플러그인이나 Docker Desktop 확장 프로그램으로 붙여 CLI·대시보드에 새로운 기능을 추가하는 방법.

1문제 상황

Docker를 설치하면 이미지 빌드, 컨테이너 실행, 스웜 관리 같은 기본 기능만 들어 있다. 볼륨 드라이버나 시크릿 보관, 네트워크 드라이버처럼 특정 환경에서만 필요한 기능이 없으면 필요한 때마다 코드를 직접 구현하거나 외부 도구를 따로 설치해 관리해야 한다. 기능이 늘어날수록 명령어와 대시보드 화면을 직접 고쳐 넣어야 하는 일이 반복된다.

2핵심 질문

Docker 기본 기능에 없는 기능을 정해진 규격으로 구현해, 기존 명령어와 대시보드에 그대로 붙일 수 있는가?

3동작 예시

새 볼륨 드라이버 플러그인을 설치하면 docker volume create 에 그 드라이버 이름을 붙여 평소 쓰던 문법 그대로 볼륨을 만들 수 있다. 플러그인 패키지에 화면 쪽 파일을 함께 넣어 두면 Docker Desktop의 확장으로 나타나서, 별도 서버를 띄우지 않고 대시보드 안에서 그 기능을 바로 켤 수 있다. 기능의 실제 동작은 플러그인 안에서 이뤄지고, 사용자는 명령 한 줄과 화면 선택 한 번만 하면 된다.

4동작 과정

  1. 플러그인 규격플러그인은 공통 규격을 따른다. CLI 플러그인은 gRPC 로 명령 요청을 주고받는 쪽이고, 관리 플러그인은 Swarm 환경에서 볼륨 드라이버·네트워크 드라이버·시크릿 저장소처럼 엔진이 직접 호출하는 역할을 맡는다.
  2. 설치와 인터페이스 구현docker plugin install 로 설치한 뒤, 플러그인 종류(VolumeDriverPlugin, NetworkDriverPlugin, SecretDriverPlugin 등)를 선언하고 엔진이 요구하는 메서드를 구현해 응답한다.
  3. Docker Extensions 로 확장플러그인 패키지에 사용자 화면 파일을 함께 포함해 Docker Desktop의 확장으로 배포하면, 대시보드 안에서 설치·활성화하고 그 기능의 화면을 바로 열 수 있다.

5한 줄 요약

정해진 플러그인 규격에 맞춰 Docker에 없는 기능을 구현해 붙이고, 화면까지 포함해 Desktop 확장으로 배포하는 것

테스트 도구와 마이그레이션

Testcontainers처럼 코드에서 컨테이너를 임시로 띄워 실제 서비스로 통합 테스트하고, 기존 자동 빌드·테스트 환경을 현대적인 CI/CD 구성으로 옮기는 방법.

1문제 상황

애플리케이션 통합 테스트에는 실제 DB나 메시지 큐 같은 외부 서비스가 필요한데, 그 서비스들을 개발자 PC나 CI 머신에 미리 직접 설치해 두는 방식이 흔했다. 설치와 버전 확인이 수동이고, 테스트가 끝난 뒤에도 데이터가 남아 다음 실행 결과를 오염시켰다. 오래된 빌드·테스트 구성은 단계가 순서대로 얽혀 있어 병렬 실행이나 일부만 다시 돌리는 것도 어려웠다.

2핵심 질문

테스트가 실행되는 그 순간에만 필요한 외부 서비스를 컨테이너로 띄워 붙이고, 끝나면 자동으로 없앨 수 있는가?

3동작 예시

Testcontainers로 테스트 코드를 실행하면 코드가 직접 Docker 엔진에 요청해 지정한 이미지의 DB 컨테이너를 임시로 띄우고, 그 컨테이너의 포트와 접속 정보를 받아 테스트를 진행한다. 테스트가 끝나면 컨테이너가 삭제되므로, 다음 실행도 같은 버전·같은 초기 상태에서 시작해 결과가 흔들리지 않는다.

4동작 과정

  1. 테스트 안에서 컨테이너 시작테스트 코드가 Testcontainers 라이브러리를 통해 이미지, 노출 포트, 환경변수 같은 실행 조건을 지정하고, 라이브러리가 엔진에 컨테이너를 띄운다.
  2. 준비 완료 확인과 연결컨테이너가 시작되자마자 쓸 수 있는 것은 아니므로 로그나 상태 확인 명령을 지정해 준비가 끝난 시점을 확인하고, 그 시점에 테스트 코드가 DB 포트로 연결한다.
  3. 종료 시 정리와 빌드 구성 마이그레이션테스트가 끝나면 컨테이너를 자동 삭제해 다음 실행에 영향을 남기지 않는다. CI/CD 쪽에서는 자동 빌드·테스트 구성을 컨테이너 단위로 다시 짜고, 캐시와 병렬 실행 단위를 나눠 실행 시간을 줄인다.

5한 줄 요약

테스트 코드에서 외부 서비스 컨테이너를 임시로 띄우고 정리해 실제 서비스로 통합 테스트하며, 기존 빌드·테스트 구성을 컨테이너 기반 CI/CD 구성으로 옮기는 것
